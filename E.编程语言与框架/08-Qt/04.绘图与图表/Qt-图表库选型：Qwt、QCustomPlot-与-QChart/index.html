本篇只回答一个问题：三个 Qt 图表库，你这个项目该用哪个。

  • 讲什么：Qwt、QCustomPlot、QtCharts 的出身与本质差异、授权协议、性能实测、功能覆盖面、上手成本、外观定制、跨平台与嵌入式、体积依赖、混合使用、按场景选型、迁移成本、易错点。
  • 不讲什么：单个库的完整 API 教程。Qwt 怎么编译、QCustomPlot 的坐标轴怎么配、QtCharts 的类层次是什么样，各自有专门篇目。本篇只把它们的接口当证据用，够判断选型就停。
  • 跨篇指路：Qwt 四篇讲编译安装、曲线坐标轴交互、QwtPlot 统计图表；QCustomPlot 三篇讲入门安装、坐标轴与性能、高阶框架；QChart 一篇讲官方模块；QPainter 两篇讲像素级手绘；图形视图框架一篇讲 QGraphicsView 本身。拿不准就看这篇，定了再翻对应篇目。

一、三个库的出身 #

三个库解决同一类问题——在 Qt 界面上画 2D 图。走的路子完全不同，后面所有的差异都是从这儿长出来的。

Qwt 是工业控件库。 它挂在 SourceForge 上，官网 qwt.sourceforge.io。重心不是「画一条好看的曲线」，是「做一台仪器的面板」。除了绘图区 QwtPlot，它还有一整套仪表控件：QwtWheel、QwtKnob、QwtDial、QwtCompass、QwtSlider、QwtThermo。刻度也是独立部件 QwtScaleWidget，能脱离绘图区单独摆。数据侧走 QwtSeriesData<T> 接口，允许直接引用外部缓冲区，一个点都不拷。素材里用的版本是 6.1.5，后来的线走到 6.2、6.3.x。

QCustomPlot 是单文件绘图库。 官网 qcustomplot.com。整个库就是 qcustomplot.h 加 qcustomplot.cpp 两个文件，拷进工程目录、.pro 里加一行 QT += printsupport，编译就能用。作者把 2D 绘图该有的东西全塞进 QCustomPlot 一个类里，设计偏扁平，没有中间层。它靠两件事吃饭：曲线性能，和接入成本。

QtCharts 是官方图表模块。 它不是第三方库，是 Qt 的一部分，类名一眼能认：QChart、QChartView、QLineSeries、QValueAxis。重点在「图种全 + 有动画 + 有主题」，折线、曲线、柱状、堆叠、饼图、散点、面积一次给齐，坐标轴、图例、标题、动画全是模块自带的能力。代价是它建在 Graphics View 上，性能上限被架构锁死。

三个库的底子摊开看：

维度 Qwt QCustomPlot QtCharts
定位 工业控件库 单文件绘图库 官方图表模块
基类 QWidget，QwtPlot 继承 QFrame QWidget QGraphicsView（QChartView）
渲染 QPainter，可选 OpenGL QPainter，可选 OpenGL Graphics View 场景图
数据容器 QwtSeriesData<T>，可引用外部缓冲区 QCPDataContainer，按 key 排序，O(log n) 范围查询 Series 内部 QVector<QPointF>
强项 刻度控件、仪表盘、频谱图、外部缓冲区 曲线性能、两文件集成、默认样式 图种覆盖、动画、主题、QML 原生

一句话记住三个库的本质：

  • Qwt 胜在「仪表」。它天生是给示波器、频谱仪、工业控制台做面板的。
  • QCustomPlot 胜在「曲线」。它在数据量大、刷新快的场合最稳，接入几乎零成本。
  • QtCharts 胜在「图种」。你要饼图、柱状、堆叠、动画，官方模块直接给。

三者的分层结构决定了性能特征，值得单独看一眼。Qwt 是分层的：画布 QwtPlotCanvas、图例 QwtLegend、坐标轴 QwtScaleWidget 各是各的部件，曲线 QwtPlotCurve、标记 QwtPlotMarker、网格 QwtPlotGrid、频谱图 QwtPlotSpectrogram 都是挂上去的绘图项（QwtPlotItem），自己往画布上画。QCustomPlot 是扁平的：数据变更 → 标记 dirty → replot() 遍历各个 Layer → 每个 Layer 能独立缓冲（lmBuffered 模式）。QtCharts 是场景图：

text
QChartView (QGraphicsView)
    └── QChart (QGraphicsWidget)
            ├── QAbstractSeries
            ├── QAbstractAxis
            └── QLegend

看清这一层，后面性能那一章的结论就不用背了：Qwt 自己能抽稀，QCustomPlot 自己能分层缓冲，QtCharts 每个元素都是 QGraphicsItem，事件分发和内存开销都压在场景上。

二、授权协议：这一条就能淘汰一半选项 #

选型的第一道筛子不是性能，是授权。性能差一点顶多让界面卡，授权错了是法务函。

先把三个库的协议摆清楚：

库 协议 闭源商业项目 做什么才合规
Qwt Qwt License 1.0，LGPL 类许可加例外条款 可以用 动态链接 + 允许用户替换库 + 附带协议与源码获取方式
QCustomPlot GPLv3 / 商业双授权 要买授权 买商业授权，或整个项目按 GPLv3 开源
QtCharts GPLv3 / 商业双授权 要买授权 买 Qt 商业授权，或整个项目按 GPLv3 开源

这张表就是筛子。三个库里只有一个能在「闭源 + 不花钱」的前提下用，就是 Qwt。

把三种项目情形过一遍：

闭源商业项目，预算里没有图形库这一项。 只剩 Qwt。QCustomPlot 和 QtCharts 都得排除。这一步跟你的曲线好不好看、跑多少帧一点关系都没有，先排除再说。

闭源商业项目，愿意买授权。 三个都能用，按技术需求选。QCustomPlot 的商业授权找作者谈；QtCharts 的授权包含在 Qt 商业许可里，也就是说你如果本来就买了 Qt 商业版，QtCharts 是现成的。这条最容易被忽略——很多团队买过 Qt 商业授权却忘了它能解锁 QtCharts。

开源项目，整体按 GPLv3 发布。 三个都能用，随便挑。GPLv3 项目用 GPLv3 的库不冲突。

LGPL 那一栏的条件要展开，它不是「免费」两个字就完了。用 Qwt 做闭源软件，得满足：

  • 动态链接。把 qwt.dll / libqwt.so 当独立库发布，不能静态链进可执行文件。
  • 用户能替换这个库。你发布的动态库版本得能被用户自己编译的版本换掉，接口不能做封闭改动。
  • 附带协议文本，并提供获取 Qwt 源码的途径。在关于对话框里放一句说明加一个链接，够了。
  • 你对 Qwt 源码的任何修改，改动的部分仍按 LGPL 发布。

静态链接也不行。素材里的编译流程产出的就是共享库（qwt.dll、libqwt.a、libqwtd.a），走这条路天然满足动态链接要求。真要静态链，那就得按 LGPL 处理——开源你的目标文件，或者干脆买授权。

QtCharts 这儿有个坑要单独提：它不是 LGPL。Qt 主体是 LGPLv3 / 商业双授权，很多人把这句话顺延到了 QtCharts 上。事实不是。QtCharts 走的是 GPLv3 / 商业双授权，LGPLv3 的选项不包含 Qt Charts。你按 LGPL 动态链接 Qt 发闭源软件，一切都合规，唯独挂上 QtCharts 就不合规了。卡在这一步的项目不少，而且往往是在发布前夕才发现。

合规的路只有三条：

  • 整个项目按 GPLv3 开源。
  • 买 Qt 商业授权。
  • 换库，换 QCustomPlot 或 Qwt。

QCustomPlot 的双授权比 QtCharts 干净。它没有 LGPL 这一档，就两条：GPLv3，或者买商业授权。所以它的判断更简单——闭源就掏钱，开源就免费用。别在它的 qcustomplot.h 头上那片注释里找「个人使用免费」之类的说法，找不到，也别拿这个当依据。

还有一个常被问到的组合：Qwt（LGPL）+ QtCharts（商业）。如果你买了 Qt 商业授权，两个都能闭源用，这时候授权不再是约束，回到性能和技术面上选。反过来，如果只买了 Qt 商业授权、没单独买 QCustomPlot，那 QCustomPlot 仍然是 GPLv3，不能闭源用——它不在 Qt 授权覆盖范围内。

记住顺序：先过授权筛，筛完再谈性能和外观。这一节能砍掉一半选项，剩下的才值得比。

三、性能对比 #

授权过了筛，才轮到性能。这一章先把「性能」拆成三个不同的问题，因为网上吵起来一半是吵的不是同一件事：

  • 单帧耗时：一次 replot() 或 replace() 花多少毫秒。
  • 能扛多少点：数据量往上翻，耗时能不能保持平。
  • 交互响应：拖拽、滚轮缩放、框选的时候跟不跟手。

这三件事的排序不一样。

素材里的原始实测 #

按数据点数量看单帧重绘耗时，单位毫秒：

数据点数 Qwt QCustomPlot QtCharts
1000 40 13.6 12.5
10000 78 21.6 13.5
100000 524 22.5 20.7
500000 未测 43.3 194.25

这张表有个细节得点出来：QtCharts 那一列的四个数字（12.5 / 13.5 / 20.7 / 194.25）跟下面 setUseOpenGL 打开时的成绩一模一样。也就是说这组对比里 QtCharts 是开着 OpenGL 加速测的，不是默认配置。关掉 OpenGL 是什么样，后面单独列。

从这张表能读出两件事，正好对应前两个问题：

  • 单帧耗时，小数据量（1000 点）：QtCharts 12.5ms，QCustomPlot 13.6ms，Qwt 40ms，越小越快。三个都在毫秒级，人眼分不出来。
  • 能扛的点数：QCustomPlot 从 1000 点 13.6ms 到 50 万点 43.3ms，几乎是一条平线；Qwt 从 40ms 涨到 524ms，10 万点这一档就掉队；QtCharts 靠 OpenGL 撑到 10 万点（20.7ms），50 万点跳到 194ms。

素材给的原始结论就两句，照录（> 读作「优于」）：

  • 绘制数据性能（单帧耗时）：QChart > QCustomPlot > Qwt。
  • 绘制数据数量（能扛多少点）：QCustomPlot > QChart > Qwt。

另一份素材的排序是 qcustomplot > qwt > qchart。跟上面不一致，原因不难猜：测的不是同一个维度，版本、编译选项、数据形态、有没有开加速也不一样。素材里两套排序都摆在这儿，我们照录，不硬凑成一套。真要给自己的项目定，拿你的真实数据跑一遍，十分钟的事。

QCustomPlot 的 alreadySorted #

QCPGraph::setData 的第三个参数控制「传进来的 key 是否已升序」，签名如下：

cpp
void QCPGraph::setData(const QVector<double> &keys,
                       const QVector<double> &values,
                       bool alreadySorted = false);

这个开关对性能的影响是实测过的：

数据点数 alreadySorted = true alreadySorted = false
1000 16.8 ms 13.6 ms
10000 21.6 ms 22.6 ms
100000 22.5 ms 43.7 ms
500000 43.3 ms 197.2 ms

结论很清楚：数据量小于 1 万时，true 和 false 差别不大，1000 点那档反而 false 更快。10 万点时 true 是 false 的 2 倍左右，50 万点时是 4.5 倍左右。你如果能保证传进去的点按 key 升序，就把它设成 true，省掉那趟排序。

反过来也成立：数据是乱序的，别硬设 true。它不会帮你排，只会让曲线画错。

QtCharts 的 setUseOpenGL #

cpp
series->setUseOpenGL(true);
数据点数 setUseOpenGL(true) setUseOpenGL(false)
1000 12.5 ms 14 ms
10000 13.5 ms 56.8 ms
100000 20.7 ms 507.4 ms
500000 194.25 ms 507.4 ms

差距在小数据量上看不出来（12.5 对 14），1 万点开始拉开，10 万点是 20.7 对 507.4，差了一个数量级还多。

但 setUseOpenGL(true) 不是免费午餐。它把渲染交给 GPU，代价是 Windows 上的远程桌面、虚拟机、老显卡驱动会出各种显示异常；另外开启之后部分抗锯齿和线型效果会变。所以这条开关的实际用法是：数据量上到 1 万点以上再开，别一上来就开。

另一组社区实测 #

数据来自 Qt Forum 和 StackOverflow，硬件不同会有差异：

场景 Qwt 6.2 QCustomPlot 2.1 QtCharts 5.15
1 万点静态渲染 ~15 ms ~20 ms ~80 ms
10 万点静态渲染 ~120 ms ~180 ms ~2500 ms+
100Hz 刷新（1000 点/次） 稳定 稳定 明显卡
拖拽平移 流畅 流畅 延迟 200–500 ms
内存（10 万点） ~8 MB ~12 MB ~45 MB

这组数据跟前面那组绝对值对不上（1 万点 Qwt 这里 15ms，前面 78ms），说明两组不是同一台机器、同一版本、同一个测法。绝对值不能横向拼，只能各自看趋势。两组的趋势是一致的：QtCharts 在 10 万点这一档掉队最狠，Qwt 也会掉，QCustomPlot 最平。

提醒一句，这份表里 Qwt 和 QCustomPlot 都还没开 OpenGL，开了还能再快 30–50%。

实时刷新这一项是最能区分场景的：Qwt 和 QCustomPlot 稳定支持 100Hz 以上，QtCharts 超过 10Hz 就开始卡。你的界面如果是「示波器式」的连续刷新，QtCharts 直接出局，这跟点数多少无关，是场景问题。

逐个写一遍。

Qwt 这边，关抗锯齿 + 点过滤是标配：

cpp
curve->setRenderHint(QwtPlotItem::RenderAntialiased, false);
curve->setCurveAttribute(QwtPlotCurve::FilterPoints);

外部缓冲区要自己实现 QwtSeriesData 的两个接口：

cpp
class ExternalData : public QwtSeriesData<QPointF>
{
public:
    ExternalData(const float *buffer, size_t size)
        : m_buffer(buffer), m_size(size) {}

    QPointF sample(size_t i) const override
    {
        return QPointF(i, m_buffer[i]);
    }

    size_t size() const override { return m_size; }

    QRectF boundingRect() const override
    {
        return QRectF(0, /* 你的 y 范围 */ 0, m_size, 1);
    }

private:
    const float *m_buffer;
    size_t m_size;
};

这条路是 Qwt 在大数据量下还能打的根本原因：数据留在你自己的环形缓冲区里，Qwt 只读不拷。100 万点的 double 是 8MB，拷一遍就是白送 8MB 内存和一次 memcpy。

QCustomPlot 四件事：

cpp
customPlot->setOpenGl(true);

QCPLayer *dataLayer = customPlot->addLayer("data");
dataLayer->setMode(QCPLayer::lmBuffered);

QVector<double> keys, values;
graph->setData(keys, values, true);

customPlot->setNoAntialiasingOnDrag(true);

分层缓冲那条的原理是：把曲线挪到自己的 Layer 上并设成 lmBuffered，replot() 时只重画脏掉的 Layer，网格、坐标轴、图例那一层不动。数据越密、静态元素越多，省得越多。

QtCharts 三条：

cpp
series->setUseOpenGL(true);

// replace 代替 append 逐点追加
QVector<QPointF> points;
series->replace(points);

chartView->setRenderHint(QPainter::Antialiasing, false);

replace() 一次换掉整个序列，比循环 append() 快一个量级。素材里的示例也是这么写的——定时器每毫秒触发一次，直接在槽里构造新的 QVector<QPointF> 然后 series->replace(point)，不是逐点加。

性能这一节的落地结论 #

按数据量分档，结论可以直接抄：

数据量 结论
1000 点以内 三个都行，毫秒级差异，人眼看不出来。按授权和外观选
1 万–10 万点 QCustomPlot 最稳；QtCharts 开 setUseOpenGL 也能用；Qwt 要开 FilterPoints 加外部缓冲区
10 万点以上还要交互 QCustomPlot；Qwt 配外部缓冲区也能撑；QtCharts 关 OpenGL 会掉到 500ms
50 万点以上 QCustomPlot 仍是 43ms 量级；QtCharts 194ms，已经卡了；Qwt 未测，按 10 万点 524ms 的趋势不乐观
100Hz 连续刷新 Qwt 或 QCustomPlot。QtCharts 超过 10Hz 就卡

再补一条硬上限：QCustomPlot 超过 100 万点就慢，得降采样。这不是配错了什么，是它的数据容器和重绘流程就到这儿。

图种这一列，QtCharts 是唯一把饼图、堆叠柱状、面积、箱线图都给齐的。Qwt 的优势在频谱 —— QwtPlotSpectrogram 原生支持频谱图和热力图，内存效率高，示波器和频谱仪用它的很多。QCustomPlot 走的是「曲线 + 色图」路线，够用，但图形种类少。

Qwt 的交互是「组件式」的，三个类各自管一件事，逐个挂到画布上：

cpp
QwtPlotZoomer *zoomer = new QwtPlotZoomer(ui->m_plot->canvas());
zoomer->setMousePattern(QwtEventPattern::MouseSelect1,
                        Qt::RightButton, Qt::ControlModifier);  // Ctrl + 右键放大，右键回退

QwtPlotMagnifier *magnifier = new QwtPlotMagnifier(ui->m_plot->canvas());
magnifier->setMouseButton(Qt::LeftButton);   // 默认滚轮，这里改成左键
magnifier->setWheelFactor(1.5);

QwtPlotPanner *panner = new QwtPlotPanner(ui->m_plot->canvas());
panner->setMouseButton(Qt::RightButton);     // 默认左键移动，这里改成右键

QCustomPlot 是「开关式」的，一行给一组能力：

cpp
ui->customPlot->setInteractions(QCP::iRangeDrag | QCP::iRangeZoom);
ui->customPlot->setInteraction(QCP::iSelectPlottables, false);
// ui->customPlot->setSelectionRectMode(QCP::SelectionRectMode::srmZoom);

QtCharts 是「重写式」的，QChartView 不带缩放平移，得自己继承重写五个鼠标事件（mousePressEvent、mouseMoveEvent、mouseReleaseEvent、mouseDoubleClickEvent、wheelEvent），还要在构造时把四个轴边界存下来供还原用。素材里那套 ChartView 代码就是这么来的，四十多行才凑齐「缩放 + 平移 + 还原 + 取最近点」。

这就是 QtCharts「上手较慢、许多功能需要重写」的具体含义。模块把图种给齐了，交互留给你。

框选放大在 QtCharts 上还有个硬毛病：用 RectangleRubberBand 时，鼠标左键如果按在画出来的线上，拉不出选框。线的图元把事件吃掉了。数据量大、线铺满整个绘图区的时候，这个操作基本没法用。素材里对这条的描述是「QChart 中绘制的线条处不能使用鼠标，所以在数据量大的时候会影响鼠标的缩放、移动图表操作」。

Qwt 的落地流程 #

Qwt 最麻烦的一步是它得自己编。完整流程走一遍：

  1. 到 qwt.sourceforge.io 下载页挑最新版本。以 6.1.5 为例，下载页给四个文件：前两个是源码包，区别只是压缩格式（.zip 和 .tar.bz2），后两个是帮助文档。
  2. 解压源码，用 Qt Creator 打开里面的 .pro，选 Release 构建。
  3. 等编译完，在 qwt-6.1.5 同级目录下会生成 build-qwt-Desktop_Qt_5_14_2_MinGW_64_bit-Release。
  4. 进 lib 目录，把 qwt.dll、qwtd.dll 拷到 Qt 安装目录的 bin 下。注意编译器位数和套件要对上——用 MinGW64 编的就拷到 mingw73_64（你机器上的版本号不一定是 73）的 bin。
  5. 把 libqwt.a、libqwtd.a 拷到同一个套件的 lib 目录。用 MSVC 编出来的是 libqwt.lib。
  6. 进 designer\plugins\designer，把 libqwt_designer_plugin.a 和 qwt_designer_plugin.dll 拷到 Qt 的 plugins\designer 下。这一步决定 Qt Designer 里能不能看到 Qwt 控件。
  7. 把解压目录里的 src 整个拷到套件的 include 下，重命名成 Qwt。名字必须是大写开头的 Qwt，因为头文件里写的是 #include <qwt_plot.h>，靠这个目录名找。
  8. 新建工程，套件选 MinGW64。进 .ui，拖一个 Frame，右键「提升为」，类名填 QwtPlot。
  9. 提升之后直接编译会报错，因为还没链接库。右键工程名 → 添加库 → 外部库 → 浏览到 libqwt.a，下一步完成。.pro 里会多出几行。
  10. 把 INCLUDEPATH 和 DEPENDPATH 改成前面那个 Qwt 头文件目录，或者干脆在代码里写全路径的 #include。

.pro 里最终长这样：

QT       += core gui
greaterThan(QT_MAJOR_VERSION, 4): QT += widgets

INCLUDEPATH += "D:/Qt/Qt5.14.2/5.14.2/mingw73_64/include/Qwt"
DEPENDPATH  += "D:/Qt/Qt5.14.2/5.14.2/mingw73_64/include/Qwt"

win32:CONFIG(release, debug|release): LIBS += -L$$PWD/../../Qt/Qt5.14.2/5.14.2/mingw73_64/lib/ -lqwt
else:win32:CONFIG(debug, debug|release): LIBS += -L$$PWD/../../Qt/Qt5.14.2/5.14.2/mingw73_64/lib/ -lqwtd

还有个小坑：高版本 Qt 直接双击 .ui 文件是用内置的 Qt Designer 打开的，那个进程不加载 Qwt 的插件，控件栏里看不到 Qwt。做法是右键 .ui → 用…打开 → 选外部的 Qt Designer。或者不折腾，直接在代码里 new QwtPlot 塞进布局，跳过提升这一步。

帮助文档也要手动挂。拿 qwt-6.1.5.qch，在 Qt Creator 里走「工具 → 选项 → 帮助 → 添加」，选那个 .qch 文件。挂完之后「帮助 → 索引」里能搜到 Qwt 的类和函数。不挂的话，F1 按下去什么也没有。

QCustomPlot 的两种用法 #

源码直接用，是它最省事的一条路：

  1. 下载页拿 QCustomPlot.tar.gz（源码）和 QCustomPlot-sharedlib.tar.gz（共享库工程）。
  2. 解压源码包，把 qcustomplot.h、qcustomplot.cpp 拷到工程目录。
  3. Qt Creator 里右键工程 → 添加现有文件，把两个文件加进去。
  4. .pro 里加一行。这行不能少，它内部用了 QPrinter 做导出和打印：
QT += printsupport
  1. 进 .ui，拖一个 Widget，右键提升为 QCustomPlot，编译运行，控件就出来了。

代价是每次全量编译都要重编 qcustomplot.cpp，这个文件两万多行，编译慢。工程一大就明显。

所以有第二条路，编成共享库：

  1. 解压 QCustomPlot-sharedlib.tar.gz，把源码包里的 qcustomplot.h、qcustomplot.cpp 复制到解压出来的目录同级。
  2. 进 qcustomplot-sharedlib/sharedlib-compilation，用 Qt Creator 打开 sharedlib-compilation.pro。
  3. Debug 或 Release 任意模式点构建。产物在 build-sharedlib-compilation-... 目录里，debug 和 release 两个子目录下各有四个文件：libqcustomplotd2.a、qcustomplotd2.dll、libqcustomplot2.a、qcustomplot2.dll。带 d 的是 debug 版。
  4. 新建一个 qcustomplot 目录，把这四个文件连同 qcustomplot.h、qcustomplot.cpp 一起放进去，当成本地第三方库。
  5. 主工程 .pro 里加 QT += printsupport，然后右键工程 → 添加库 → 静态库 → 浏览到 libqcustomplot2.a。
  6. 自动生成的语句里有个常见的笔误要手动改：把 -lqcustomplot2d 改成 -lqcustomplotd2。d 在后还是在中间，决定了链接器找的是 debug 版还是找不到。

两种用法怎么挑：一个人做的小工具，源码直用；团队项目、CI 要跑、编译时间敏感，编共享库。

QtCharts 的安装 #

三个库里它最省事，前提是装 Qt 的时候勾了。它在安装器里是独立可选组件，默认桌面套件不含。装完再补：打开 Qt Maintenance Tool → Add or remove components → 在对应 Qt 版本下勾 Qt Charts。

六、外观与定制能力 #

三个库默认长什么样，素材给了直接排序：QCustomPlot ≈ QtCharts > Qwt。

那个约等于号是有前提的。素材的原话是「这里的约等于存在作者的个人偏好」：QCustomPlot 界面简洁大方，QtCharts 界面华丽优美，作者更偏简洁的那一边。所以这个约等于不要当结论，当成「两个都比 Qwt 好看」就够了。

具体到观感：

  • QCustomPlot：简洁，轴、网格、图例的默认配色偏现代，不调也拿得出手。默认样式是现代风格是它的一大卖点。
  • QtCharts：华丽，线条平滑、有动画、有主题切换、标题和图例的排版是官方调过的。要「给领导看」的报表界面，它默认效果最好。
  • Qwt：界面老旧。素材里说得直白——「Qwt 界面老旧，在美观上不如 QCustomPlot 和 QChart，并且在使用鼠标移动图表时会产生空白区域」。

Qwt 那个「鼠标移动时产生空白区域」要单独说一句，它不只是好看不好看的问题。拖动图表的时候画布先被清成背景色，新位置的曲线还没画上去，中间那一瞬是空的。数据量大、重绘慢的时候这个空白会持续可见，看起来像卡了。这是 Qwt 的分层重绘机制在拖动时的副作用，不是配置问题。

定制能力分四档看：

定制维度 Qwt QCustomPlot QtCharts
默认观感 老旧 简洁现代 华丽，有动画
换主题 无内置主题，自己设画笔和背景 无内置主题，但单类里都能改 setTheme() 内置多套
动画 无 无 内置，系列加进图表就有
改源码 要重编库 两个文件，直接改 官方模块，改不动
自定义绘图项 继承 QwtPlotItem，体系完整 继承 QCPLayerable / QCPAbstractPlottable 继承 QGraphicsItem 塞进场景
字体刻度微调 QwtScaleWidget 独立可控，最细 axisRect 层可调 轴对象上调

Qwt 的自定义绘图项那套是三个库里最成体系的：QwtPlotItem 往下派生曲线、标记、网格、频谱图，你自己写一个类继承它，实现 draw() 就完事，跟内置的绘图项地位一样。要画很稀奇的东西，这条路最顺。

QCustomPlot 的优势不在体系，在「源码摊在你面前」。它整个库就两个文件，你要改什么直接改 qcustomplot.cpp，不用等上游发版。代价是升级时你的改动要手动合回去。素材把这条列为它的核心优点之一，确实实在——很多界面细节官方不给接口，能改源码就是最后一招。

QtCharts 反过来，改不动。它的主题和动画是官方封装的，setTheme() 一调就换一套配色，省事；但你想改某个刻度标签的绘制方式，只能往 QGraphicsItem 那一层钻，成本比前两个都高。

外观这一项的实际权重取决于你的客户是谁。给仪器操作员做界面，Qwt 的老旧不算问题，他一整天盯着的是波形清不清楚；给业务方做报表，默认观感就是需求，这时候 QCustomPlot 和 QtCharts 的差距才体现出来。

七、跨平台与嵌入式支持 #

三个库都跨平台，跨的方式不一样，成本也不一样。

平台维度 Qwt QCustomPlot QtCharts
Windows 要自己编，配 Designer 插件 两文件，随工程编 随 Qt 装
Linux 源码编，发行版包管理器也能装 两文件 随 Qt 装
macOS 源码编 两文件 随 Qt 装
嵌入式 Linux 要为交叉工具链重新编一遍 随工程交叉编，无独立库 工具链带了就有
交叉编译成本 高，qwtconfig.pri 要按目标平台调 低 无
换编译器 要重新编，且 dll 与套件强绑定 不用管 不用管

Qwt 的跨平台成本集中在一件事上：它是预编译库，编出来的东西跟工具链和 Qt 套件强绑定。你在 MinGW64 上编的 qwt.dll，只能给 MinGW64 套件的工程用；换 MSVC、换 32 位、换 ARM 交叉工具链，整套流程（编库、拷 dll、拷 lib、拷 Designer 插件、拷头文件）得重走一遍。素材里那句「注意之前使用的是 MinGW64 编译的，就将 dll 复制到 mingw73_64 的 bin 下」，说的就是这个绑定。

带 Designer 插件的库尤其麻烦。交叉编译到 ARM 板子上，你不需要 Designer 插件（板子上没 Designer），但需要 .so，所以 qwtconfig.pri 里要单独关掉插件那几项再编。这套配置项不关，编出来的东西跑不起来。

QCustomPlot 在跨平台上几乎是零成本。它是源码，跟着你的工程一起编，工具链换成什么它就用什么，没有独立的 dll 要拷，也没有 ABI 匹配问题。这是「单文件库」在工程层面最大的红利——你换平台时不用重新走一遍第三方库的安装流程。

QtCharts 的成本也是零，因为它在 Qt 里。你的交叉工具链如果带了 Charts 模块，直接可用；没带就重编 Qt 的时候勾上。它不需要单独的安装步骤。

QML 这一项要分开说，三个库都不是天生给 QML 用的：

  • QtCharts：有 QML API，ChartView 直接在 QML 里写，官方支持。
  • Qwt：没有。只能 QQuickWidget 包一层，把一个 QWidget 塞进 QML 界面。包进去能显示，但触摸事件、缩放这些交互要自己桥。
  • QCustomPlot：同样没有。QQuickWidget 包进去之后帧率会掉，素材给出的办法是「单独开 QWidget 窗口」，也就是绕开 QML 界面，弹独立窗口显示图表。

如果你的界面是 QML 写的、图表要嵌进 QML 页面里，QtCharts 是三个里唯一不用绕路的。Qwt 和 QCustomPlot 都要经过 QQuickWidget 这个中间层，性能和交互都要打折。

嵌入式这一块没有素材实测，只能说量级上的关系：Qwt 和 QCustomPlot 都是 QPainter 软件绘制为主，CPU 弱、没 GPU 的板子上靠的是抽稀和分层；一开 OpenGL 加速，嵌入式显卡驱动这一层会变成新变量，驱动支持差的板子上还不如关掉。具体能跑多少点，取决于板子的 CPU、内存带宽和你的编译优化选项，跑一遍比看文章靠谱。

QCustomPlot 在嵌入式上还有个细节：它默认带全量功能，包括导出和打印，链接 printsupport 模块。板子上的 Qt 如果裁掉了 printsupport，编译直接失败。裁减版 Qt 上第一件要确认的事就是这个模块还在不在。

八、体积与依赖 #

这一项在桌面项目里无关紧要，在安装包和嵌入式固件里会变成决策因素。

维度 Qwt QCustomPlot QtCharts
源码形态 完整工程 + 示例 + 文档 两个文件（.h + .cpp） Qt 子模块
源码规模 全套源码加示例，量级上比两个文件大得多 qcustomplot.cpp 两万多行 随 Qt 源码树
编译产物 qwt.dll + 导入库 + Designer 插件 无（源码直用）或一个共享库 独立的 Charts 模块库

三件事值得说清。

第一，printsupport 是隐性依赖。 Qwt 和 QCustomPlot 都靠它做导出和打印，QCustomPlot 尤其明显——整个库对 printsupport 的依赖是因为它内置了 PDF/图片导出。工程里漏了 QT += printsupport 的症状是链接期一堆 undefined reference to QPrinter，不是编译期，所以看着像别的问题。

第二，Qwt 的部署比另外两个多一步。 发布目录里必须带上 qwt.dll，而且必须是动态链接——这既是技术需要，也是 LGPL 的合规要求（前面授权那章说过）。windeployqt 不认识这个库，它只拷 Qt 自己的 dll，qwt.dll 得你自己拷。忘了拷的症状是双击没反应或者弹「找不到 qwt.dll」。

发布目录大致长这样：

text
发布目录/
├── myapp.exe
├── Qt5Core.dll
├── Qt5Gui.dll
├── Qt5Widgets.dll
├── Qt5PrintSupport.dll       # Qwt / QCustomPlot 都需要
├── qwt.dll                   # 只有 Qwt 需要，且必须动态链接
├── Qt5Charts.dll             # 只有 QtCharts 需要
└── platforms/
    └── qwindows.dll

第三，QCustomPlot 的体积优势是「不产生额外部署项」。 源码直用时，最后全编进你的 exe，发布目录里一个多余文件都没有。这也是它在做小工具时最舒服的地方——拷一个 exe 就能跑。

具体多少 MB，取决于编译选项、是否带调试符号、链接了哪些 Qt 模块，没有普适数字。选型的时候只需要判断一件事：你的发布约束是「一个 exe」还是「一个安装包」。前者偏向 QCustomPlot，后者三个都行。

Qwt 仪表控件 + QCustomPlot 画曲线 可行 只链 Qwt 也要满足 LGPL 唯一值得认真考虑的组合
QtCharts 报表页 + QCustomPlot 实时页 可行 QtCharts 侧仍是 GPL/商业 分页分得开才用
Qwt 主图 + QCustomPlot 局部窗 可行 两套都要合规 别做，两套坐标映射会互相拖累
Qwt + QtCharts 可行 LGPL 与 GPL 并存，闭源项目过不去 不建议

第一种组合有真价值。 Qwt 的 QwtWheel、QwtKnob、QwtDial、QwtCompass、QwtSlider、QwtThermo 是三个库里独一份的资产——旋钮、表盘、温柱这类工业控件，QCustomPlot 和 QtCharts 都没有。你要做一个控制台，左边一排旋钮调参数，右边一条实时曲线，把 Qwt 当控件库用、QCustomPlot 当绘图库用，各取所长。

这种混法有个前提：你别碰 QwtPlot。只用它的仪表控件，不引入整套绘图体系。一旦两个 QwtPlot 和 QCustomPlot 同时上屏，两套坐标映射、两套鼠标事件处理、两套重绘节奏，需要同步的地方会翻倍。

授权这边要留神：即使你只用 Qwt 的旋钮控件，链接了 qwt.dll 就受 LGPL 约束，动态链接那几条照样得满足。混用不等于绕过授权。

第二种组合在工程上说得通。 报表页数据量小、要好看、要动画，用 QtCharts；实时页数据量大、要跟手，用 QCustomPlot。两个页面互不干涉，各用各的栈。代价是安装包里同时带 Charts 模块和 QCustomPlot 的编译产物，体积翻倍；以及 QtCharts 那一侧的授权问题一分都少不了。

后两种不建议。 第三种（Qwt 主图 + QCustomPlot 局部放大窗）听起来聪明，实际做起来要在两个控件之间同步坐标范围，每次缩放都得双向同步，还会互相触发对方的 replot，一不小心就是死循环。第四种（Qwt + QtCharts）在授权上最尴尬：LGPL 和 GPLv3 两套约束同时压着，闭源项目根本走不通，开源项目又何必混。

混用还有一个隐性成本：两套 API 的心智负担。Qwt 的绘图项叫 QwtPlotItem，QCustomPlot 的叫 QCPAbstractPlottable，两套命名、两套生命周期、两套 attach 语义。团队里两个人分别维护这两块，交接的时候都要重新学。

结论就一句：混用只在「要 Qwt 的仪表控件、但不想用 QwtPlot」这一种情况下值得。其余情况选一个用到死，比两个拼起来省事。

十、按场景选型 #

把前面几章的约束串起来，决策路径是这样的：

  │

照着走之前，先把授权那道判断做实。决策树里「许可证卡不卡」这一枝，答错的代价最高。

常见场景的直接答案：

场景 推荐 理由
科学仪器 / 工业控制 Qwt LGPL 类许可、外部缓冲区、仪器控件库
快速原型 / 美观优先 QCustomPlot 双文件集成、默认样式好看
QML 原生（Qt 6.8+） Qt Graphs RHI 后端、官方推荐方向
存量商业项目 QtCharts 仅限维护已有代码
商业报表（闭源，愿买授权） QtCharts 图种全、有动画主题、交互自己写
百万点数据回放 QCustomPlot 降采样，或 Qwt + 外部缓冲区 纯性能问题

三个典型场景展开说。

工业监控，选 Qwt。 典型需求是 8 到 32 通道波形、1kHz 以上采样率、频谱图或瀑布图、7×24 不停机。Qwt 的 QwtPlotSpectrogram 原生支持频谱和热力图，内存效率高；QwtWheel、QwtKnob 这些工业控件是现成的，不用自己画。示波器、频谱仪这类产品用它的很多。这一档里 Qwt 的「界面老旧」根本不是缺点，操作员要的是波形清楚、刷新不卡。

快速原型，选 QCustomPlot。 典型需求是周期性报表、10 到 100Hz 的曲线监控、工期紧、样式要过得去。两个文件丢进工程就能用，不用配构建系统；默认样式偏现代；交互一行开关搞定；社区活跃，遇到问题搜得到示例。赶工期的项目里，这个「不用配」省下来的半天就是净赚。

QML 应用，选 Qt Graphs。 Qt 6.8 起可用，RHI 后端，官方给新项目的推荐方向。适合静态或低频更新的图表、需要 QML 深度集成的界面、饼图柱状图这类商业图表。QtCharts 在 QML 那一侧虽然也能用，但它的废弃时间表摆在那里。

素材给的四条速查，直接抄：

  • 许可证敏感 → Qwt（LGPL）。
  • 性能优先 → Qwt ≥ QCustomPlot >> QtCharts。
  • 快速集成 → QCustomPlot（两文件）> QtCharts > Qwt。
  • QML 原生 → Qt Graphs >> 其他。

「性能优先」那条要打个补丁。前面的实测数据里，10 万点以上 QCustomPlot 的曲线比 Qwt 平得多（10 万点 22.5ms 对 524ms）。Qwt ≥ QCustomPlot 这个写法成立的场景是「配了外部缓冲区、关了抗锯齿、开了点过滤」的 Qwt，不是默认配置的 Qwt。默认配置下，QCustomPlot 的曲线更稳。

还有一条时间线上的事实必须放进选型：QtCharts 在 Qt 6.10 正式废弃，官方建议新项目用 Qt Graphs。 这意味着新项目选 QtCharts 是在给未来埋一笔迁移债。存量项目继续用到维护期结束没问题，新项目就该跳过它。

十一、迁移成本 #

选错了要换，换的代价也是选型的一部分。三个方向的工作量差别不小。

迁移方向 工作量 主要改动
QtCharts → QCustomPlot 中 Series 换 graph()，轴换 xAxis / yAxis，createDefaultAxes 那套手配，动画没了，交互反而变简单
QCustomPlot → Qwt 大 扁平 API 换组件式，数据容器换 QwtSeriesData，每条曲线单独 attach，交互要挂三个类
Qwt → QCustomPlot 中偏小 反向操作，attach 省掉，仪表控件要另找替代
QtCharts → Qwt 大 图种降级（饼图没了），交互全部重做
QtCharts → Qt Graphs 中 官方迁移路径，6.10 之后必须走

横向看，从 QtCharts 迁出最容易，从 QCustomPlot 迁出最难。

原因在 API 的颗粒度。QtCharts 的抽象层级高，Series 加进 QChart，轴由 createDefaultAxes() 自动建，代码量少，替换时改动点也集中。QCustomPlot 是扁平大对象，ui->customPlot->graph(0)->setData(...) 这种写法散落在各处，每处都要改。Qwt 在两者之间，但它把交互拆成 QwtPlotZoomer、QwtPlotMagnifier、QwtPlotPanner 三个类，迁移时这三处都得重写。

想省迁移成本，唯一靠谱的办法是提前隔一层。把你的绘图需求抽成一个窄接口：

cpp
class ITrendChart
{
public:
    virtual ~ITrendChart() = default;

    virtual QWidget *widget() = 0;
    virtual void setSeries(const QVector<QPointF> &points) = 0;
    virtual void appendPoints(const QVector<QPointF> &points) = 0;
    virtual void setRange(double xMin, double xMax, double yMin, double yMax) = 0;
    virtual void clear() = 0;
};

然后为每个库写一个适配器：

cpp
class QcpTrendChart : public ITrendChart
{
public:
    QWidget *widget() override { return m_plot; }

    void setSeries(const QVector<QPointF> &points) override
    {
        QVector<double> keys, values;
        keys.reserve(points.size());
        values.reserve(points.size());
        for (const QPointF &p : points) {
            keys.append(p.x());
            values.append(p.y());
        }
        m_plot->graph(0)->setData(keys, values, true);
        m_plot->replot();
    }
    // ...

private:
    QCustomPlot *m_plot = nullptr;
};

换库的时候只改适配器的实现，业务代码一行不动。这一层的成本是前期多写几十行，收益是后面换库只需要一天。

迁移的验收清单，逐条对：

  • 同样数据量下，耗时不超过原来（或明确知道超了、且能接受）。
  • 轴范围、刻度算法、对数轴的表现一致。
  • 缩放、平移、还原的操作手感一致——这一项最容易被漏，用户的肌肉记忆比代码难改。
  • 导出格式一致，PDF 里的字体和线宽对得上。
  • 授权复核一遍，新库的协议跟你的发布方式匹配。
  • 交互相关的信号槽重新连过，尤其是取最近点这类要算的逻辑（closestPoint / pixelToCoord / mapToValue 三家的接口完全不通用）。

几条值得单独展开的。

Qwt 的 setAutoReplot(true) 别开。 素材里那句注释写得很直白：「设置自动重绘，不建议使用」。开了之后你每设一个属性（改标题、改轴范围、改画笔）都会触发一次完整重绘，初始化阶段连着设十几项就是十几次重绘。做法是全部设完，最后调一次 replot()。

cpp
// ui->m_plot->setAutoReplot(true);   // 不建议

ui->m_plot->setTitle("标题");
ui->m_plot->setCanvasBackground(Qt::white);
ui->m_plot->setAxisScale(QwtPlot::yLeft, 0.0, 1000.0);
ui->m_plot->setAxisScale(QwtPlot::xBottom, 0, 50);
ui->m_plot->setAxisTitle(QwtPlot::xBottom, "x 轴");
ui->m_plot->setAxisTitle(QwtPlot::yLeft, "y 轴");
// ... 全部设完
ui->m_plot->replot();

Qwt 的鼠标跟踪要开四层。 需求是「鼠标在画布上移动时实时读数」，光在窗口上开 setMouseTracking(true) 不够，画布是子控件，得逐层开：

cpp
setMouseTracking(true);
ui->centralwidget->setMouseTracking(true);
ui->m_plot->setMouseTracking(true);
ui->m_plot->canvas()->setMouseTracking(true);

少开一层，鼠标在画布上移动时收不到事件，看起来像「悬停提示坏了」。

QCustomPlot 的信号连接只能用旧式 SIGNAL / SLOT 宏。 它的 mouseRelease、mouseDoubleClick 这些信号，新式函数指针写法连不上，因为信号签名带的是 QMouseEvent* 指针且没加 Q_OBJECT 重载标记：

cpp
connect(ui->customPlot, SIGNAL(mouseRelease(QMouseEvent*)),
        this, SLOT(MymouseReleaseEvent(QMouseEvent*)));
connect(ui->customPlot, SIGNAL(mouseDoubleClick(QMouseEvent*)),
        this, SLOT(MymouseDoubleClickEvent(QMouseEvent*)));

写成新式语法，编译期就报「no matching signal」。

像素坐标转轴坐标，三家三套 API。 这是迁移时最容易卡住的地方：

库 从鼠标位置取数据坐标
Qwt curve->closestPoint(mousePoint) 取最近点索引，再 curve->sample(i).y()
QCustomPlot xAxis->pixelToCoord(event->x())，然后 graph(i)->data()->at(index)->value
QtCharts chart()->mapToValue(event->pos())，再在 pointsVector() 里取邻近点

QtCharts 那边还要注意 mapToValue 返回的是 QPointF 值坐标，取索引得自己 qRound：

cpp
QLineSeries *l_series = (QLineSeries *)this->chart()->series().at(0);
QVector<QPointF> l_vpointF = l_series->pointsVector();
QPointF l_curVal = this->chart()->mapToValue(event->pos());
QPointF l_pointF = l_vpointF.at(qRound(l_curVal.x()));

QtCharts 的滚轮缩放要自己算边界。 模块不带这个。素材里的做法是以鼠标位置为中心，按 1.5 的系数缩放：

cpp
void ChartView::wheelEvent(QWheelEvent *event)
{
    QPointF l_curVal = this->chart()->mapToValue(event->pos());
    QValueAxis *l_axisX = (QValueAxis *)this->chart()->axes(Qt::Horizontal).at(0);
    QValueAxis *l_axisY = (QValueAxis *)this->chart()->axes(Qt::Vertical).at(0);

    double l_fMinX = l_axisX->min(), l_fMaxX = l_axisX->max();
    double l_fMinY = l_axisY->min(), l_fMaxY = l_axisY->max();

    double l_fZoomMinX, l_fZoomMaxX, l_fZoomMinY, l_fZoomMaxY;
    if (event->delta() > 0) {   // 放大
        l_fZoomMinX = l_curVal.x() - (l_curVal.x() - l_fMinX) / 1.5;
        l_fZoomMaxX = l_curVal.x() + (l_fMaxX - l_curVal.x()) / 1.5;
        l_fZoomMinY = l_curVal.y() - (l_curVal.y() - l_fMinY) / 1.5;
        l_fZoomMaxY = l_curVal.y() + (l_fMaxY - l_curVal.y()) / 1.5;
    } else {                    // 缩小
        l_fZoomMinX = l_curVal.x() - (l_curVal.x() - l_fMinX) * 1.5;
        l_fZoomMaxX = l_curVal.x() + (l_fMaxX - l_curVal.x()) * 1.5;
        l_fZoomMinY = l_curVal.y() - (l_curVal.y() - l_fMinY) * 1.5;
        l_fZoomMaxY = l_curVal.y() + (l_fMaxY - l_curVal.y()) * 1.5;
    }

    l_axisY->setRange(l_fZoomMinY, l_fZoomMaxY);
    l_axisX->setRange(l_fZoomMinX, l_fZoomMaxX);
}

设置轴范围的顺序有讲究：先 Y 后 X。反过来的话，X 变化触发的重绘会用到旧的 Y 范围，中间那一帧图像会跳一下。

还原视图的初始范围要在构造时存。 QtCharts 没有「回到初始」的内置操作，右键双击还原得靠自己存那四个值：

cpp
ChartView::ChartView(QChart *chart, QWidget *parent) : QChartView(chart)
{
    QValueAxis *l_axisX = (QValueAxis *)this->chart()->axes(Qt::Horizontal).at(0);
    m_dMinX = l_axisX->min();
    m_dMaxX = l_axisX->max();

    QValueAxis *l_axisY = (QValueAxis *)this->chart()->axes(Qt::Vertical).at(0);
    m_dMinY = l_axisY->min();
    m_dMaxY = l_axisY->max();
}

这里有个顺序陷阱：构造函数里存范围，得保证轴已经建好了。如果你在构造 ChartView 之前没调 createDefaultAxes()，axes(Qt::Horizontal) 返回空，at(0) 直接越界。正确顺序是：建 QChart → 加所有 Series → createDefaultAxes() → 设轴范围 → 再 new ChartView(chart)。

Qwt 的曲线数据要跟着画布走，别自己攒。 定时刷新时最省事的写法是每帧填一个新数组再 setSamples()：

cpp
double x[50], y1[50];
for (int i = 0; i < 50; ++i) {
    x[i] = i;
    y1[i] = QRandomGenerator::global()->bounded(100, 1000);
}
m_curvep->setSamples(x, y1, 50);
ui->m_plot->replot();

素材里那句注释值得记住：「需要快速读写情况下建议使用数组，不使用 QVector」。setSamples 有指针重载，传裸数组它不拷贝，直接拿你的指针遍历；传 QVector 会走拷贝路径。短期数据用栈上数组最快，跨函数活着的数据才是 QVector 的场合。

最后一句：三个库都会随着年龄增长积累坑。真卡住了，QCustomPlot 直接把源码翻出来看，Qwt 去 examples 目录找最接近的那个例子，QtCharts 查官方文档和 Qt Bug Tracker。三条路都不通的时候，换库的成本已经比修它低了——这时候回头翻第十一章的迁移表。
