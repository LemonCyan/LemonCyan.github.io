这一篇讲什么：把一个跑在 Qt4 上的 C++ 工程搬到 Qt5 要动哪些地方——模块拆分、废弃 API、图形栈换代、构建脚本调整，以及分步迁移的顺序。

不讲什么：信号槽的连接语法、QObject 的对象树与内存管理、事件分发机制、插件加载器的内部实现、对象池的复用策略。这五块在同目录另外五篇里各占一篇，本篇只在迁移语境下提一句边界。

QML 动画怎么调缓动曲线、状态机怎么写，去 07.QML与Quick/动画：状态、过渡与缓动。本篇只保留 Qt5 提供的特性与模块清单。

一、Qt5 的三大变化 #

把 Qt5 当成「Qt4 换了个版本号」是最容易踩坑的假设。它改了三层东西，而且改动深度不一样。

先看官方的定位。Qt5 把力气压在三个方向上：

图形渲染质量。Qt Quick 2.0 丢掉了 Qt4 那套自绘引擎，改成直接建在 OpenGL (ES) 上的渲染场景图（Scene Graph）。2D 粒子、半透明渐变、Shader 滤镜、60 FPS 动画，在嵌入式板和桌面上都能跑起来，功耗还压得住。这条线是从根上换的。

开发者生产力。前后端分成两条轨：QML/JS 管界面与动效，C++ 管并发、数据库、网络、计算。两边靠信号槽和 ContextProperty 桥接，谁都不用等谁。设计和编码可以并行推进。

平台抽象与移植效率。Qt 5 引入 QPA（Qt Platform Abstraction），把平台相关的东西收到一小层接口后面，接一个新系统只需适配这部分。同时模块被切成必需（Essentials）与附加（Add-ons）两档，运行时体积能按需裁剪。

除了这三条，还有两件影响迁移成本的事：C++11 全面可用（lambda 进 connect、右值语义进容器），以及模块目录结构的重排。

迁移最大的麻烦不是改名 #

很多人以为升级就是照着「API 改名表」全局替换一遍。真动手会发现，报错量最大的一类跟改名没关系，而是头文件和模块对不上了。

Qt4 时代 QtGui 是个大杂烩：画图、字体、颜色、OpenGL 支持在里面，QWidget、QMainWindow、QPushButton 这些控件也在里面，连打印对话框、剪贴板都塞在一起。Qt5 把它劈成了两半：

  • QtGui 留下基础图形：QColor、QFont、QPainter、QImage、QWindow、OpenGL 相关。
  • QtWidgets 接管控件：QWidget、QMainWindow、QPushButton、QLayout、QDialog。

于是旧代码里那句 #include <QtGui>，本来能带出 QWidget，现在带不出来了。编译器给的第一句报错往往是 QMainWindow: No such file or directory，看着像头文件丢了，其实是模块名换了。

这条是整篇的主线。后面第三章列报错、第九章改 .pro、第十章排迁移顺序，都是围着它转。

二、模块拆分：widgets 从 gui 里独立 #

先看清拆分前后的对照。Qt4 的模块粒度粗，Qt5 拆得细，而且拆出去的模块名不等于原模块名的子集，需要单独引入。

Qt4 里的位置 Qt5 拆分后的模块 迁移动作
QtGui 中的控件类 QtWidgets .pro 加 QT += widgets，头文件改 QtWidgets/
QtGui 中的打印相关 QtPrintSupport .pro 加 QT += printsupport
QtCore 中的并发框架 QtConcurrent .pro 加 QT += concurrent
QtWebKit 中的控件层 QtWebKitWidgets .pro 加 QT += webkitwidgets
QtGui 中的多媒体辅助 QtMultimedia / QtMultimediaWidgets 换掉 Phonon，改用 QMediaPlayer
全局的翻译编码枚举 无（并入默认行为） 删掉 UnicodeUTF8 参数

拆分带来的直接影响有三条，按踩到的顺序排：

第一，.pro 少了 QT += widgets，链接阶段缺符号。 qmake 默认的 QT 变量不含 widgets，Qt4 工程拷过来不会自动补。表现是编译能过头文件、链接报一堆 undefined reference to QWidget::...。

第二，含混的 #include <QtGui> 全部失效。 得逐个头文件改成带模块前缀的形式，或者干脆用不带路径的短名。

第三，模块之间的依赖方向变了。 QtWidgets 依赖 QtGui，反过来不成立。以前可以在一个「纯 gui」的库里随手 new 一个 QWidget，现在这个库必须显式依赖 widgets。库的 .pro 里 QT += gui 不够用了。

头文件写法：两条路 #

Qt5 认两种包含方式，按工程习惯选一种，别混着写。

短名形式，推荐新代码用：

cpp
#include <QWidget>
#include <QMainWindow>
#include <QPushButton>

带模块前缀的形式，适合老代码批量替换：

cpp
#include <QtWidgets/QWidget>
#include <QtWidgets/QMainWindow>
#include <QtWidgets/QPushButton>

短名能用的前提是 .pro 里已经 QT += widgets，因为 qmake 会把模块的 include 目录加进编译参数。少了这一句，短名和长名一起报错。

.pro 里对应的写法：

QT += core gui widgets

Qt4 时代的模板行是 QT += core gui，多数工程只改这一行就够。用 Qt Creator 新建的 Qt5 Widgets 工程，模板默认就带 widgets，只有从旧工程拷贝时才要手工补。

三、常见的编译错误与修法 #

这一章按模块列。每条给报错原文、原因、修法，照着改就行。

1. QtWidgets：控件类找不到 #

报错长这样：

text
error: QMainWindow: No such file or directory
error: QWidget: No such file or directory

原因：所有窗口控件类（QWidget、QMainWindow、QToolButton、QLabel 等）从 QtGui 挪到了 QtWidgets。旧代码里的 #include <QtGui/QWidget> 指向了一个已经不存在的路径。

修法两步，缺一不可。.pro 里补模块：

QT += widgets

头文件改成新路径：

cpp
#include <QtWidgets/QWidget>   // 或者直接 #include <QWidget>

先把 .pro 改完再改头文件。顺序反了会看到「头文件明明在，编译器说找不到」的假象，浪费时间。

2. QtPrintSupport：打印类未定义 #

报错形态是 QPrinter 或 QPrintDialog 提示未定义，有时报在链接期。

原因：QPrinter、QPrintDialog、QPrintPreviewDialog 这一组被单独拆成 QtPrintSupport。

.pro 补一句：

QT += printsupport

代码里改成：

cpp
#include <QtPrintSupport/QPrinter>
#include <QtPrintSupport/QPrintDialog>

一个细节：QtPrintSupport 依赖 QtWidgets。只加 printsupport 不加 widgets，QPrintDialog 那部分仍然报错。

3. QtConcurrent：链接期找不到符号 #

报错出现在链接阶段：

text
undefined reference to `QtConcurrent::run(...)'

原因：Qt4 里 QtConcurrent 是 QtCore 的组成部分，#include <QtCore> 就带出来了。Qt5 把它剥离成独立模块，头文件位置和链接库都变了。

.pro 补：

QT += concurrent

头文件改成：

cpp
#include <QtConcurrent/QtConcurrent>

如果只用了 QtConcurrent::run，单独包含 <QtConcurrent/QtConcurrentRun> 也行，编译更快。

4. QtWebKitWidgets：QWebView 认不出来 #

报错是无法识别 QWebView 或 QWebFrame。

原因：QtWebKit 被拆成两层，引擎层 QtWebKit，控件层 QtWebKitWidgets。旧代码用 QWebView 属于控件层。

.pro 补：

QT += webkitwidgets

头文件改成：

cpp
#include <QtWebKitWidgets/QWebView>

这里有个现实问题：QtWebKit 在 Qt 5.6 之后不再是官方发布的一部分，被 QtWebEngine 取代。QtWebEngine 基于 Chromium，API 完全不一样，QWebView 没有对应物，要改用 QWebEngineView 加 QWebEnginePage，页面脚本交互从 QWebFrame::evaluateJavaScript 换成 QWebEnginePage::runJavaScript，且是异步回调。老工程如果重度依赖 QWebView，这一步是重写而不是替换，得单独排期。

5. 三个连带错误 #

改模块时容易带出三个次生问题，一起说掉。

链接器版本混用。undefined reference to QWidget::metaObject() 这类符号名对不上，多半是编译用 Qt5 头文件、链接链到了 Qt4 的库。清掉 build 目录，重新跑 qmake，别在旧 Makefile 上增量编译。

Q_OBJECT 与 moc 脱节。改了头文件路径后，moc 的扫描列表没更新，报 vtable for Xxx 未定义。同样清 build 目录重来。

QT += widgets 加在子工程但没加到顶层。多 .pro 的 SUBDIRS 工程里，模块变量不继承。每个用到控件的子工程都要自己写一遍。

四、废弃 API 的替换对照 #

模块拆分是硬性报错，改不改由编译器决定。废弃 API 不一样，它们多数还能编过，只是被标了 deprecated，或者在某次小版本里被直接删掉。这类问题会拖到运行期才暴露，比编译错误难查。

先把对照表放全，共十条，都是迁移时命中率高的。

序号 Qt 4.x 被废弃的 API/类 Qt 5.x 推荐替代 说明与示例
1 QString::toAscii()
QString::fromAscii()		 toLatin1() / fromLatin1()
toUtf8() / fromUtf8()		 按目标字符集选具体方法，别再依赖 Ascii 这个含糊名字。QByteArray data = str.toLatin1();
2 QCoreApplication::UnicodeUTF8 直接删掉该枚举参数 Qt5 的 tr() 一律按 UTF-8 处理，第四个参数没有意义。setWindowTitle(tr("标题"));
3 QWorkspace QMdiArea 多文档区域容器。QWorkspace 在 Qt5 里被彻底删除，没有兼容层。#include <QMdiArea>
4 qFindChildren<T>(obj, ...) obj->findChildren<T>(...) 全局泛型查找函数废弃，改为 QObject 成员函数。auto list = parentObj->findChildren<QPushButton*>();
5 qVariantValue<T>(val) val.value<T>() 取值改用成员模板方法。QTime t = val.value<QTime>();
6 qVariantCanConvert<T>(val) val.canConvert(QMetaType::Type) 类型判定改用元类型枚举。Q_ASSERT(variant.canConvert(QMetaType::QString));
7 Qt::escape(str) str.toHtmlEscaped() HTML 转义，把 < 转成 &lt; 这类。QString esc = rawStr.toHtmlEscaped();
8 QDesktopServices::storageLocation(...) QStandardPaths::writableLocation(...) 系统标准路径。standardLocations 返回列表，取单条用 writableLocation。
9 Phonon 媒体框架 QtMultimedia 模块 第三方多媒体框架下线，改用 Qt 自建引擎。QMediaPlayer 加 QVideoWidget。
10 CONFIG += qtestlib QT += testlib 测试框架的引入方式归到 QT 变量下。

下面按类别说清改的时候该注意什么。

1. 字符串编码：Ascii 这个名字要拆开 #

toAscii() 在 Qt4 里干的事其实是「按 Latin-1 转」，名字起得不准。Qt5 干脆拆成两个明确的方法：toLatin1() 走单字节，toUtf8() 走变长编码。

改的时候要判断数据下游是谁。写给老式串口设备、只认单字节的，用 toLatin1()；存文件、传网络、进 JSON 的，用 toUtf8()。原来一把 toAscii() 到底的代码，这里有真正需要决策的地方，不是纯改名。

cpp
QString text = ui->lineEdit->text();

// 走本地单字节协议
QByteArray raw = text.toLatin1();

// 走网络或持久化
QByteArray utf8 = text.toUtf8();

反向也一样，fromAscii() 拆成 fromLatin1() 与 fromUtf8()。读外部数据时选错，中文会变成问号或乱码，而且不报错。

2. 翻译编码：删掉那个参数 #

Qt4 里写 tr("标题", "context", "comment", QCoreApplication::UnicodeUTF8) 是为了指定编码。Qt5 把编码固定成 UTF-8，这个枚举被移除，留着就编不过。

cpp
// Qt4 写法
setWindowTitle(tr("标题", "MainWindow", "窗口标题", QCoreApplication::UnicodeUTF8));

// Qt5 写法
setWindowTitle(tr("标题"));

批量清理时搜 UnicodeUTF8 这个关键字，命中处删掉第四个参数即可。

3. QWorkspace：没有兼容层 #

QWorkspace 是 Qt4 早期的多文档界面容器，后来被 QMdiArea 顶替。Qt5 里 QWorkspace 被整个删掉，头文件和类都不存在。

替换不是改个类名那么轻松。两者接口不同：QMdiArea 用 addSubWindow() 添加子窗口，子窗口是 QMdiSubWindow，QWorkspace 那套 windowList()、activeWindow() 的语义要对到 subWindowList()、activeSubWindow() 上。信号也换了名：windowActivated 变 subWindowActivated。

cpp
QMdiArea *area = new QMdiArea(this);
QMdiSubWindow *sub = area->addSubWindow(new QTextEdit);
sub->setWindowTitle("文档 1");
sub->show();

工程里还有 QWorkspace 的，说明这块代码年代很早，迁移时顺手检查一下它的父类链和布局方式，别只做表面替换。

4. 查找子对象：从全局函数到成员方法 #

qFindChildren<T>() 与 qFindObjects<T>() 这一组全局模板函数在 Qt5 里废弃。替代品是 QObject 的两个成员：findChildren<T>() 和 findChild<T>()。

两者的差别不只是调用形式。成员版本支持 Qt::FindChildOptions，可以用 Qt::FindChildrenRecursively 或 Qt::FindDirectChildrenOnly 控制搜索深度，旧全局函数只能全递归。

cpp
// Qt4
QList<QPushButton*> btns = qFindChildren<QPushButton*>(this);

// Qt5
QList<QPushButton*> btns = this->findChildren<QPushButton*>();
QList<QPushButton*> direct = this->findChildren<QPushButton*>(
    QString(), Qt::FindDirectChildrenOnly);

补一句风险：findChildren 按名字或类型过滤，返回顺序与对象创建顺序相关但不保证，别拿下标当稳定索引。

5. QVariant 取值：模板方法接管 #

qVariantValue<T>() 与 qVariantCanConvert<T>() 被 value<T>()、canConvert() 取代。这条改动简单，但有个隐藏收益：成员方法能配合 QMetaType 做运行期判定，写序列化代码时更稳。

cpp
QVariant val = settings.value("startTime");

if (val.canConvert(QMetaType::QTime)) {
    QTime t = val.value<QTime>();
    timer->setStartTime(t);
}

canConvert(QMetaType::Type) 用的是元类型枚举，不再是模板参数。迁移时如果原来写的是 qVariantCanConvert<QString>(v)，改完变成 v.canConvert(QMetaType::QString)，注意枚举名别拼错。

6. HTML 转义：Qt::escape 走人 #

Qt::escape() 是 Qt4 的全局转义函数，Qt5 换成 QString::toHtmlEscaped()。功能一样，覆盖面比旧函数全一些。

cpp
QString raw = "<b>粗体</b>";
QString safe = raw.toHtmlEscaped();   // &lt;b&gt;粗体&lt;/b&gt;

在拼 HTML 字符串展示用户输入的地方必查这一处。旧函数被删后如果没改，编不过还是小事，怕的是有人图省事直接把原始字符串塞进去，埋下注入问题。

7. 标准路径：QDesktopServices 换成 QStandardPaths #

QDesktopServices::storageLocation() 与 displayName() 这一组静态方法下线，改用 QStandardPaths 的静态方法。

对应关系要记住：storageLocation 对 writableLocation，displayName 对 displayName。QStandardPaths::standardLocations() 返回的是路径列表（一个用途在 Linux 上对应多个目录），要单条路径就用 writableLocation()。

cpp
// Qt4
QString cfgDir = QDesktopServices::storageLocation(
    QDesktopServices::AppDataLocation);

// Qt5
QString cfgDir = QStandardPaths::writableLocation(
    QStandardPaths::AppDataLocation);

枚举值也全换了名：DataLocation 变 AppDataLocation，CacheLocation 变 CacheLocation（这个没变），DocumentsLocation 保留。逐个对照比全局替换安全。

8. Phonon：整块换掉，不是改名 #

Phonon 是 Qt4 时代的第三方多媒体抽象层，Qt5 不再收录。替代品是 QtMultimedia，播放器用 QMediaPlayer，画面输出用 QVideoWidget 或 QGraphicsVideoItem。

这是本篇里改动量最大的一条。Phonon 的 MediaObject、AudioOutput、VideoWidget 三件套要重新组织成 QMediaPlayer 加一个输出端，信号也从 stateChanged 换成 mediaStatusChanged 与 playbackStateChanged 两个。

cpp
QMediaPlayer *player = new QMediaPlayer(this);
QVideoWidget *view = new QVideoWidget(this);
player->setVideoOutput(view);
player->setMedia(QUrl::fromLocalFile("demo.mp4"));
player->play();

顺带要处理运行期依赖：QtMultimedia 在不同平台上后端不同（Windows 走 Media Foundation，Linux 走 GStreamer），部署时缺后端组件会静默失败。这条在桌面端调试机上测不出来，到目标机才炸。

9. 测试框架：CONFIG 移到 QT #

CONFIG += qtestlib 是 Qt4 的写法。Qt5 归到 QT 变量下：

QT += testlib

qmake 的模块解析只认 QT 里的项，写在 CONFIG 里不会拉入链接参数，报错是找不到 QTest 符号。老工程里两种写法常常共存，清理时统一成 QT +=。

五、图形栈：从 Graphics View 到 Scene Graph #

Qt4 时代的 2D 界面有两条技术路线。一条是 QWidget 加 QPainter 的直接绘制，另一条是 Graphics View 框架：QGraphicsScene 装图元，QGraphicsView 负责显示，图元继承 QGraphicsItem，靠 paint() 自己画。

Graphics View 的好处是图元管理和坐标变换做得很细，坏处是它仍然走 CPU 光栅化。动画一多，帧率就掉，尤其在半透明叠加和大量小图元同时动的时候。

Qt5 的 Qt Quick 2.0 换了一条路。它不再让每个元素自己往画布上涂，而是先建一棵渲染树，再交给 OpenGL (ES) 批量提交。这套东西叫 Scene Graph，对应的场景图节点类在 QtQuick 模块内部，走的是 GPU 路径。

两条栈的关键差别：

维度 Graphics View（Qt4 起） Scene Graph（Qt5 的 Qt Quick 2.0）
渲染路径 QPainter 软件光栅化，可选 OpenGL 视口 构建在 OpenGL (ES) 上的渲染树，GPU 提交
声明方式 C++ 里 new 图元，手工加进 scene QML 声明式描述，属性绑定驱动
动画 QPropertyAnimation 逐个驱动 属性变化即触发，Behavior 与 NumberAnimation 挂在属性上
大量元素 元素数上千时帧率下降明显 节点合并批处理，粒子与滤镜有专门优化
适用场景 传统桌面控件、图表、CAD 视图 触控界面、动效密集的展示层、嵌入式 HMI

迁移时的判断标准很直接：这段界面是「窗口里的控件」还是「一块自绘的画布」。

  • 如果是控件排布，留在 QtWidgets，改头文件和 .pro 就够，别为了迁 Qt5 硬改成 QML。
  • 如果是自绘的大画布、图元多、要缩放平移，Graphics View 在 Qt5 里照常可用，QGraphicsScene 那套 API 没被删，只是底层渲染有调整。
  • 如果要 60 FPS 的动画、粒子、滤镜、Shader 效果，才轮到 Qt Quick 出场。

有一点要提醒：Qt5 里 QGraphicsView 的视口如果设成 QGLWidget，在新版本上会遇到兼容问题，OpenGL 视口的管理搬到了 QOpenGLWidget。老代码里 setViewport(new QGLWidget) 这类写法要改成 setViewport(new QOpenGLWidget)，否则渲染上下文建不起来。

QML 动画具体怎么写、Behavior 与 Transition 怎么选、缓动曲线怎么调，本篇不展开，去 07.QML与Quick/动画：状态、过渡与缓动。这里只记结论：Qt5 的图形栈是两套并存，不是新替旧。

六、平台抽象：QPA #

Qt4 往一个新平台移植，要改的是 QWS（Qt Window System）或者各平台自己的 QPlatformXxx 分支，代码分散在 src/gui/kernel 各处，改动面大，回合并困难。

Qt5 把这一层收成了 QPA。思路是把所有平台相关操作抽象成插件接口：窗口创建、事件派发、剪贴板、光标、拖放、屏幕与 DPI 信息、字体数据库、输入法，全部落在一组 QPlatform* 类上。上层代码只跟 QWindow、QGuiApplication 打交道，底下换插件不影响业务。

对应用开发者来说，QPA 是透明的。真正会碰到的场景只有几个：

启动参数选平台插件。用 -platform 指定，或者用环境变量 QT_QPA_PLATFORM：

text
myapp -platform windows
myapp -platform offscreen

offscreen 在无显示环境里跑自动化测试时会用到，它不建真实窗口。

嵌入式板子上要选 eglfs 或 linuxfb。以前靠 QWS 那套参数，Qt5 全换成 QPA 插件名。启动脚本里残留 -qws 参数的话，Qt5 直接忽略，然后起不来，因为默认插件在无 X11 的板子上加载失败。这条是老嵌入式工程迁移时最常见的启动故障。

自建平台插件。要做定制系统（特殊显示控制器、无操作系统的裸机屏），就得写一个 QPlatformIntegration 的实现，继承 QPlatformIntegrationPlugin 并导出。这部分属于移植层工作，本篇只指路，不展开。

QPA 带来的实际收益是移植成本可量化：适配一个新系统，只需实现那几十个 QPlatform* 接口，业务代码一行不动。Qt5 官方发布的平台插件涵盖 Windows、X11、macOS、Android、iOS、Wayland、EGLFS、LinuxFB，选一个或者基于最近的改。这也是「平台抽象提升移植效率」这句话的具体含义。

七、Essential 模块清单 #

Qt5 把模块分成两档。Essentials 是任何 Qt5 程序的底座，装了 Qt 就有；Add-ons 按需引入，不进默认安装也会在编译时给你明确报错。

Essentials 一共八个模块，是做选型和排依赖时最先要背下来的：

模块 作用 迁移相关度
QtCore 非图形核心：信号槽、事件循环、元对象系统、IO、容器、线程 高。qFindChildren、QWorkspace 的替代都落在这层
QtGui 图形基础：QColor、QFont、QPainter、QImage、窗口系统与 OpenGL 支持 极高。控件被搬走了，剩的是画图那一半
QtWidgets C++ 传统窗体套件：QWidget 派生的按钮、输入框、布局管理器 极高。Qt4 的 QtGui 控件全在这里
QtNetwork 跨平台 TCP/UDP 与 HTTP 客户端网络类 中。QFtp、QHttp 已删，要换 QNetworkAccessManager
QtQml QML 引擎核心，含 JS 引擎与运行时框架 低。新引入的模块，Qt4 工程没有对应物
QtQuick 声明式前端框架，负责高动态与触控交互的渲染 低。同上，属于新增能力
QtSql 关系型数据库的 SQL 驱动层（SQLite、MySQL、Oracle 等） 中。QSqlQuery 接口大体兼容，驱动插件路径变了
QtTest 单元测试与基准测试框架 中。.pro 里从 CONFIG 挪到 QT

排依赖的顺序有讲究。QtWidgets 依赖 QtGui，QtGui 依赖 QtCore，是一条单向链。QtQml 和 QtQuick 是另一条支线，QtQuick 依赖 QtQml 与 QtGui，但不依赖 QtWidgets。一个只用 QML 的工程不需要链接 widgets，一个纯 Widgets 工程也不需要 qml。

这条依赖链解释了为什么「只用 Widgets 的程序在嵌入式上体积还是不小」：QtGui 里带着 OpenGL 支持和窗口系统接入层，砍不掉。要更小，得走 QtCore 加定制移植层这条路。

八、Add-on 模块清单 #

附加模块覆盖更高层的平台能力，装了才有，不装不影响基础功能。

模块 能力
Qt 3D 简化 3D 渲染与场景建模控制的 C++/QML API
Qt Bluetooth 发现与连接经典蓝牙及低功耗（BLE）设备
Qt Sensors 读取移动端硬件传感器：加速度计、陀螺仪、罗盘等
Qt Location 定位信息、地图图层、线路导航、地址检索
Qt System Info 读取目标系统的 CPU 负载、电池容量、存储空间

调用这几块之前先确认安装包里带了对应模块。qmake 的报错是 Project ERROR: Unknown module(s) in QT: location，出现这句不是代码问题，是 Qt 装的时候没勾选。

附加模块的另一个特点是平台支持不均匀。Qt Bluetooth 在桌面 Linux 上依赖 BlueZ，在 Windows 上依赖 WinRT 接口，同一份代码两头行为不同。Qt Location 的地图数据源要自己配插件（OSM、Mapbox 之类），空配置下地图是灰的但不报错。这类问题跟迁移本身无关，属于启用新模块时的常规排查。

九、构建系统的调整 #

迁移的实操大头在构建脚本。Qt4 的 .pro 直接扔给 Qt5 的 qmake，多数能解析，但缺的模块不会自动补。

先看一份最小的 Qt5 Widgets 工程模板：

QT += core gui widgets

greaterThan(QT_MAJOR_VERSION, 4): QT += widgets

TARGET = myapp
TEMPLATE = app

CONFIG += c++11

SOURCES += main.cpp \
           mainwindow.cpp

HEADERS += mainwindow.h

几个要点：

QT += core gui widgets 是保底写法。 Qt4 工程的 .pro 只有 core gui，补上 widgets 就能过掉大半编译错误。

greaterThan(QT_MAJOR_VERSION, 4): QT += widgets 让同一份 .pro 双版本可用。 团队里还有人跑 Qt4 时，这条能让你不必维护两个工程文件。等全部切到 Qt5，删掉它也行。

CONFIG += c++11 打开 C++11。 Qt5 的 connect 新语法、lambda 捕获、auto 都靠这个。老编译器不支持时，退回写 QMAKE_CXXFLAGS += -std=c++0x。

CONFIG += console 与 CONFIG -= app_bundle 按平台取舍。 Windows 上要控制台输出就留 console，发布版要去掉。

从 qmake 转 CMake 的工程 #

Qt5 时代开始有工程改用 CMake，写法是 find_package(Qt5 COMPONENTS Widgets) 加 target_link_libraries。关键点是把组件名显式列全，find_package 找到的每个组件都要在链接时点名：

text
find_package(Qt5 COMPONENTS Core Gui Widgets PrintSupport REQUIRED)

target_link_libraries(myapp
    Qt5::Core
    Qt5::Gui
    Qt5::Widgets
    Qt5::PrintSupport)

漏掉某个 Qt5::Xxx 的表现和 qmake 里漏 QT += 一模一样：头文件找得到，链接缺符号。另外 CMake 要开 set(CMAKE_AUTOMOC ON)，不然 Q_OBJECT 的类没有 moc 产物，报 vtable 未定义。

部署工具 #

Qt5 补了个部署工具 windeployqt，Windows 上直接把依赖的 dll 拷到可执行文件旁边：

text
windeployqt --release myapp.exe

以前手工维护 dll 清单的做法可以退场了。平台的 QPA 插件目录（platforms/qwindows.dll）一定要带上，漏了它的现象是程序启动即退出，且没有任何提示，只在命令行打印一句「This application failed to start because no Qt platform plugin could be initialized」。

十、迁移的实际步骤 #

按这个顺序做，能少走回头路。

第一步，先固定编译器与 Qt 版本。 挑一个具体的 Qt5 小版本（比如 5.9 或 5.15），全套工具链对齐。版本不定就动手，会陷入「换个机器行为不一样」的泥潭。

第二步，跑 fixqt4headers.pl。 Qt 官方在源码包的 qtbase/bin/ 下带了这个 Perl 脚本。在项目源码根目录执行，它扫全工程的 C++ 源文件，把旧的头文件包含格式改成带模块名的 Qt5 形式。

text
perl fixqt4headers.pl --dry-run
perl fixqt4headers.pl

老工程有成百上千个 #include 时，手工改是灾难。先 --dry-run 看它要改哪些，确认后再真跑。脚本只处理包含语句，.pro 里的模块变量还得自己补。

第三步，清 build 目录，重新 qmake。 旧 Makefile 里锁着 Qt4 的头文件路径与库路径，增量编译会把两代库混在一起。清干净重来，这一步不能省。

第四步，按报错改 .pro。 编译一次，把缺的模块一次性补齐：widgets、printsupport、concurrent、webkitwidgets，用到哪个加哪个。

第五步，处理废弃 API。 编译通过后开始全局搜，按第四章的表逐条替换。搜索关键字清单：toAscii、fromAscii、UnicodeUTF8、QWorkspace、qFindChildren、qVariantValue、qVariantCanConvert、Qt::escape、storageLocation、Phonon、qtestlib。

第六步，过一遍运行期行为。 这一步最容易被跳过。代码编过了不等于行为一致，重点查三处：字符串编码、路径拼装、界面尺寸。

第七步，部署验证。 在干净的目标机上跑，别在开发机上测。缺 QPA 插件、缺多媒体后端、缺数据库驱动，都只在这时候暴露。

每一步都留一次可编译的提交。全量改完再编译的做法，报错会堆成一屏，分不清因果。

十一、迁移中容易忽略的地方 #

除了报错能提示的部分，还有一批改动不报错、只在特定路径上出问题。

1. 插件声明宏换了 #

Qt4 写自定义插件用 Q_EXPORT_PLUGIN 或 Q_EXPORT_PLUGIN2 宏。这两个在 Qt5 里弃用，换成 Q_PLUGIN_METADATA：

cpp
class MyPlugin : public QObject, public MyInterface
{
    Q_OBJECT
    Q_INTERFACES(MyInterface)
    Q_PLUGIN_METADATA(IID "org.qt-project.Qt.MyInterface" FILE "myplugin.json")
};

新机制的好处在于 Qt 扫描插件信息时不用把 dll 物理加载进内存。旧做法要 dlopen 才能读到元数据，插件一多启动就慢；新做法直接读嵌入在库里的 JSON 描述，启动速度和稳定性都受益。

Q_PLUGIN_METADATA 里 IID 必须和接口类的 Q_DECLARE_INTERFACE 声明一字不差，FILE 指向的 JSON 要进 qmake 的 DISTFILES，否则发布包里缺文件，插件加载时静默失败。插件加载的完整机制在 08.对象模型与信号槽/插件系统 那篇，这里只记宏换了。

2. 平台宏被清理 #

Qt4 里的 Q_WS_WIN、Q_WS_X11、Q_WS_MAC 这一组「窗口系统」宏在 Qt5 中被删。取而代之的是 Q_OS_WIN、Q_OS_LINUX、Q_OS_MACOS 这类操作系统宏，加上 QPA 的运行期判断。

老代码里满屏的 #ifdef Q_WS_WIN 不会报错，因为未定义的宏在 #ifdef 里就是假值——整段 Windows 专用代码被静默跳过。表现是「Linux 上正常，Windows 上功能缺一块」，很难往宏上想。

cpp
// Qt4
#ifdef Q_WS_WIN
    // Windows 专用
#endif

// Qt5
#ifdef Q_OS_WIN
    // Windows 专用
#endif

全局搜 Q_WS_ 这个前缀，一处别漏。

3. OpenGL 控件换了类 #

QGLWidget 在 Qt5 里被标记过时，继任者是 QOpenGLWidget，位于 QtWidgets。两者的 initializeGL、paintGL、resizeGL 三个虚函数签名一致，改写成本不高，但上下文管理方式不同：QOpenGLWidget 渲染到 FBO 再合成，与其他控件的叠加关系更可控。

如果工程的 .pro 里有 QT += opengl，Qt5 里这个模块名仍然可用，但它只提供 QGLXxx 那套旧类。用 QOpenGLWidget 的话不需要额外模块，它就在 widgets 里。

4. 桌面信息改从 QScreen 取 #

QDesktopWidget 取屏幕尺寸的写法在 Qt5 里被标记过时，改从 QGuiApplication::primaryScreen() 拿 QScreen：

cpp
// Qt4
QRect r = QApplication::desktop()->screenGeometry();

// Qt5
QRect r = QGuiApplication::primaryScreen()->geometry();

多屏场景下 QGuiApplication::screens() 返回全部屏幕，每个 QScreen 带自己的 DPI 与可用区域。做居中、最大化、跨屏定位的代码都要重看，按 QDesktopWidget 的单屏假设写的逻辑在多屏上会错位。

5. 正则表达式建议换实现 #

Qt5 新增 QRegularExpression，基于 PCRE。旧的 QRegExp 还在，能编过，但语法与 PCRE 有差异，同一个模式两边结果未必相同。迁移时顺手把关键校验逻辑换掉，别留着两套正则跑在一个工程里。

6. 默认字体与 DPI 缩放 #

Qt5 的高 DPI 支持默认不开，从 Qt4 升上来的界面在 4K 屏上要么字小得看不清，要么布局被拉变形。开之前要确认界面代码是按固定像素写死的还是按布局管理的。

cpp
QCoreApplication::setAttribute(Qt::AA_EnableHighDpiScaling);

这条得放在 QApplication 构造之前，放晚了不生效。

7. 翻译文件格式 #

.ts 文件在 Qt5 里兼容，但 lupdate / lrelease 的行为有变化：源码里 tr() 的上下文匹配变严格，同名不同类的字符串要分开处理。翻译缺失时界面回落成英文原文，不会报错，测试时容易漏。

十二、易错点速查 #

把前面散落的坑收成一张表，迁移时对着过一遍。

现象 根因 修法
QMainWindow: No such file or directory 控件类从 QtGui 搬到 QtWidgets .pro 加 QT += widgets，头文件改 QtWidgets/
头文件找得到，链接报 undefined reference to QWidget::... .pro 缺 widgets，或子工程未单独声明 每个用到控件的 .pro 都补 QT += widgets
QPrinter 未定义 打印拆分到 QtPrintSupport QT += printsupport，且同时保证有 widgets
undefined reference to QtConcurrent::run 并发从 QtCore 剥离 QT += concurrent，头文件改 QtConcurrent/
QWebView 认不出来 QtWebKit 拆成引擎层与控件层 QT += webkitwidgets；5.6 之后考虑迁 QtWebEngine
中文变问号或乱码 toAscii() 改 toLatin1() 时选错方向 存盘/网络用 toUtf8()，老式单字节设备用 toLatin1()
QWorkspace 编不过 Qt5 彻底删除，无兼容层 换 QMdiArea，注意信号名与子窗口 API 都变了
多文档界面切窗口没反应 windowActivated 改成了 subWindowActivated 连接处改信号名
Windows 专用代码在 Windows 上不执行 Q_WS_WIN 被删，#ifdef 静默取假 换 Q_OS_WIN，全局搜 Q_WS_ 前缀
程序启动即退出，无窗口无提示 缺 QPA 平台插件 部署目录补 platforms/qwindows.dll，或用 windeployqt
vtable for Xxx 未定义 moc 没跑，或旧 build 目录混了 Qt4 产物 清 build，重跑 qmake，CMake 开 CMAKE_AUTOMOC
自定义插件加载失败且无报错 Q_PLUGIN_METADATA 的 IID 对不上，或 JSON 没进发布包 核对 Q_DECLARE_INTERFACE 里的 IID，JSON 加进 DISTFILES
高清屏上字小、布局错位 高 DPI 缩放未启用 QApplication 构造前设 AA_EnableHighDpiScaling
视频播放无声无画 QtMultimedia 平台后端缺失 目标机补装 GStreamer 或 Media Foundation 组件
地图控件一片灰 Qt Location 未配地图数据源插件 配置 OSM 等插件；报 Unknown module(s) in QT 则是模块没装

这张表的用法：迁移前通读一遍，把跟自己工程相关的行标出来；编译期盯前六行；运行期盯后九行。
