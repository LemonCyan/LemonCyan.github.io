本篇讲什么：用 Qt 做产品要过的授权关。专有与开源两种版权模式、常见许可证的条款差别、Qt 的商业 / GPL / LGPL 三套授权、动态链接与静态链接各自的合规义务。

本篇不讲什么：Qt 的 API 怎么用、模块怎么选、构建系统怎么配；Qt5 到 Qt6 的版本迁移细节。

跨篇指路：不清楚 Qt 由哪些部分组成、该按什么顺序学，看同目录的《Qt 是什么》。要建第一个工程、跑第一个窗口，看《Qt5 与 Qt6 版本差异》里的工程配置部分。

底线：这里讲的是公开的许可证常识和工程实践，不构成法律意见。真要签采购合同、真要在交付文档里承诺合规，找懂知识产权的律师。

一、为什么 Qt 的授权要单独讲 #

写业务代码的人很少管授权。选个框架，npm install 或者 cmake find_package，跑起来就算完事。用 Qt 不一样，它是少见的「同一份代码、三套授权并行」的产品。

你下载的 Qt 安装包里，同一批头文件和库文件，对应着三个身份：

  • 商业授权下的 Qt，你付钱，换来源码修改权、静态链接权、官方支持和某些专属模块。
  • GPL 下的 Qt，你白拿，代价是整个程序也要按 GPL 开源。
  • LGPL 下的 Qt，你白拿，主程序可以闭源，代价是你要让用户能换掉 Qt 库。

三条路都不算坑，坑在于很多人不知道自己站在哪条路上。

授权在项目里是架构决策 #

它不是收尾时补一份 LICENSE 文件，它在项目开头就锁死了三件事：

  1. 链接方式。动态还是静态，这个选择直接决定你走 LGPL 的哪一半义务。
  2. 分发形态。只在自己公司内网跑，和打包发给客户，法律后果完全不同。
  3. 能不能闭源。它决定你要不要掏授权费。

这三条一旦定下来再改，成本不是改文档，是改构建脚本、改打包流程、改发布渠道、重新过一遍法务。买一份商业授权的钱，财务上叫预算；把上线产品从静态链接改成动态链接，叫事故。

三个真实会遇到的岔路 #

text

        LGPL 要求交出目标文件让用户重链接，多数团队做不到

岔路二：动态链接 + 闭源 + 履行了 LGPL 义务
        合法，能卖钱，业务代码不必公开

岔路三：用了只在商业版提供的模块
        没有第二条路，开源版根本没这个模块

Qt 的模块许可并不完全一致 #

Qt 核心模块是 LGPL / GPL / 商业三选一，但不是每个附加模块都这样。部分附加模块只在商业授权或 GPL 下提供，还有些只在特定商业产品包里出现。

具体哪个模块属于哪一档，别听二手转述。查两处：Qt 官方文档里该模块的页面，以及源码树里模块目录下的许可声明文件。条款细节以官方许可文本为准。

二、版权的两种基本模式：专有与开源 #

先把地基打牢。软件的默认法律状态不是「大家随便用」，而是「保留所有权利」。作者写了代码，版权就归他。许可证是一份授权书，作者主动放弃一部分权利，换取别的东西。

两种模式的分野 #

维度 专有许可 开源许可
源码是否提供 不提供 提供
修改权 按合同，多数不给 授予
分发权 按合同，按席位或按设备 授予，附条件
费用 按合同收费 许可证本身免费
违约后果 合同纠纷，赔钱为主 版权侵权，可被要求停止分发
典型代表 大多数商业软件 GPL、LGPL、MIT、BSD、Apache

最后一行值得多看两眼。违反开源许可证不是「没付钱」那么简单，它是侵权。侵权意味着对方可以要求你停止分发，已经发出去的版本要召回，这对硬件和消费类软件是很重的后果。

开源不等于免费，免费不等于能商用，这两句被混得最多。开源指的是源码可得，并且许可证授予你修改和再分发的权利，跟价格无关。免费指的是拿到手不花钱，跟你能不能用它赚钱无关。源码可见也不等于开源，有些软件的源码你能看到，但许可证禁止商用。

分发是那个开关 #

这是整篇文章最重要的一条规则：绝大多数开源许可证的义务，由分发行为触发。

你自己写代码、自己编译、自己在公司内网部署给自己人用，没有对外分发，义务就不启动。GPL 也一样，公司内部拿 GPL 工具改一改自己用，不需要把改动公开。这条原则给企业留了很大的空间：内部工具链、内网系统、数据分析脚本，用 GPL 的东西没有额外负担。

三个例外：

  • AGPL 把「通过网络提供服务」也视同分发，SaaS 场景下义务照样启动。
  • 你分发了。给客户装机器、把安装包放官网、把固件烧进设备卖出去，都算。
  • 合同要求。客户合同或招标文件写了「交付物不得包含 GPL 组件」，那不管法律上怎么算，商业上你已经违规。

还有一类灰区：把带 GPL 组件的产品免费给外部试用、把镜像给合作伙伴、把 SDK 给第三方集成商。这些动作在不在「分发」的定义里，要看具体情形，别自己拍板。

三、常见开源许可证速览 #

许可证几十种，日常会撞上的就六七个。先按阵营分类，这是理解一切的骨架。

三大阵营 #

类型 代表协议 核心特征
Copyleft（强传染） GPL v2 / v3 衍生作品必须保持相同许可证开源
Weak Copyleft（弱传染） LGPL v2.1 / v3 仅库本身保持 Copyleft，链接程序可闭源
Permissive（宽松） MIT、BSD、Apache 2.0 允许闭源商用，仅保留版权声明

「传染」是工程界的俗称，法律文本里没有。它的意思是：你的代码和它结合到一定程度，你的代码也被要求套上同样的许可证。阵营之间的差别，本质是「要求你回馈多少」：宽松阵营只要求署名，弱传染要求库本身开源，强传染要求整个衍生作品开源。

逐个过一遍 #

许可证 阵营 能闭源分发吗 义务落在哪 典型项目
MIT 宽松 能 保留版权声明与许可文本 Ruby on Rails、Node.js
BSD 2/3-Clause 宽松 能 保留版权声明，3 条款另禁背书 FreeBSD
Apache 2.0 宽松 能 保留声明、NOTICE、专利条款 Apache HTTP Server
MPL 2.0 文件级弱传染 能（自己文件） 修改过的 MPL 文件要开源 Firefox
LGPL 2.1 / 3 弱传染 能 库源码公开，允许替换 Qt 开源版
GPL 2 / 3 强传染 不能 整个衍生作品开源 Linux 内核、Git
AGPL 3 强传染 + 网络条款 不能 同 GPL，另含网络服务场景 Nextcloud

GPL 与 LGPL #

GPL 要求如果你用了 GPL 代码，你的整个项目也必须开源。这是强制性的。Linux 内核就是 GPL，所以所有基于 Linux 的发行版都必须公开源代码。用 GPL 代码就要做好开源的准备。准确的表述是：触发点是分发，你一分发，整个衍生作品都要按 GPL 给出源码。

LGPL（Lesser General Public License）介于 GPL 和宽松协议之间。如果你用了 LGPL 授权的库，你的主程序可以闭源。前提是用户能够替换这个库的版本，而且库的源代码必须公开。Qt 就是典型的 LGPL 案例。

「用户能替换这个库」这七个字，是 LGPL 全部的技术核心。动态链接天然满足，静态链接要另外补动作。

Mozilla 许可证 #

Mozilla 许可证对代码共享比较宽松。你可以修改和分发代码，即使闭源也没问题。Firefox 就用这个协议。这意味着插件开发者可以保持代码闭源，这是它比 GPL 灵活的地方。

MPL 的传染粒度是文件。你改了一个 MPL 文件的内部实现，这个文件要按 MPL 开源；你自己新写的、跟它放一起编译的其他文件，可以闭源。这条文件级边界，是 MPL 和 GPL 最实际的区别。

四、GPL 与 LGPL 的关键差别 #

这一章是 Qt 授权的分水岭。搞混这两个，后面的判断全错。

链接方式对比 #

LGPL 的设计目标很具体：让库能被商业软件使用。它把「库」和「使用库的程序」在法律上分开对待。结果是你的主程序可以闭源，业务逻辑可以保护，也可以卖钱，但你必须让用户有能力把这个库换掉——换成他自己编译的版本，或者更新后的版本。

链接方式 你的代码需开源？ 额外义务
动态链接 否 提供协议文本，允许用户替换库
静态链接 否 提供目标文件 + 库源码 + 重链接说明

这张表是很多团队的救命表，也是很多团队翻车的地方。两行都写着「你的代码不需开源」，但第三列的成本差了一个量级。

动态链接那一行，把 dll 或 so 放在程序目录里，随包附上 LGPL 文本，写清楚用户可以用自己的版本替换，工作基本就完了。静态链接那一行，你要交出自己程序的目标文件（.o / .obj），让用户能拿着它和修改后的 Qt 重新链接出可执行文件。这不是公开源码，但对多数商业团队来说，交出目标文件的阻力比想象中大。

GPLv2 与 GPLv3 主要差异 #

要求 GPLv2 GPLv3
源码公开 分发二进制时必须 同左
保留许可证文本 是 是
标注修改内容 是 是
专利授权 无 显式授权
反 Tivoization 无 消费设备需提供安装信息
与 Apache 2.0 兼容 否 是

反 Tivoization 这一行值得单独说。它的意思是：设备厂商不能把 GPLv3 软件锁死在硬件里，让用户改不了。用 GPLv3 代码做消费设备，你要提供安装修改后固件的信息。

这条对嵌入式团队是实打实的成本。设备要做安全启动、要做固件签名校验，就会跟这一条撞上。撞上了怎么办？换许可证版本，换组件，或者买豁免——最后这条只有商业授权能给。

LGPLv2.1 与 LGPLv3 #

LGPLv3 的文本是「GPLv3 加上一组额外许可」。它继承了 GPLv3 的专利条款和反 Tivoization 条款，再把「库」的特殊待遇叠上去。

落到工程上：LGPLv2.1 没有显式专利授权，也没有安装信息要求；LGPLv3 两条都有。做消费类嵌入式设备的团队，看到 LGPLv3 要多想一步。具体到某个 Qt 版本用哪一版 LGPL，看官方许可文本和该版本的许可声明，别按记忆推断。

一句话记住分界线：GPL 管的是整个程序，LGPL 只管那个库本身。你的程序越是想闭源，越要盯着这个差别。

五、MIT、BSD 与 Apache 的区别 #

宽松阵营的三个主力，很多人当它们等价，实际有细差别。

MIT 与 BSD #

MIT 是最简单的协议，一句话概括：随便用。Ruby on Rails、Node.js 都用 MIT。只要保留版权声明，干什么都行。如果你懒得选协议，选 MIT 很少出错。

行为 是否允许 额外义务
商业使用 允许 无
修改代码 允许 无需公开修改
闭源分发 允许 保留版权声明和 MIT 协议文本
更换许可证 允许 衍生品可用任意协议
专利授权 无 无明确专利条款

最后一行是 MIT 的短板。许可证文本里没有专利条款，意味着贡献者没有明确授予你专利许可，真遇上专利纠纷，MIT 帮不了你。

BSD 很宽松，几乎没有限制。你可以闭源，可以商用，甚至不用署名（三条款版本除外）。FreeBSD 就是 BSD 协议，很多商业软件直接用了它的代码。企业喜欢 BSD 就是这个原因——省事。

变体 条款数 特殊限制
2-Clause BSD 2 保留版权 + 免责声明
3-Clause BSD 3 再加禁止使用作者名背书

三条款那条限制在宣传场景里会踩到，你不能拿原作者的名字或机构名去给产品做推广。还有个 4-Clause BSD（带广告条款），老代码里能见到，它要求衍生品的广告里致谢原项目，这条和 GPL 不兼容。

Apache 2.0 #

Apache 和 MIT 类似，但多了一些要求，主要是要保留原作者的署名和专利声明。Apache HTTP Server 用这个协议。Apache 2.0 还解决了专利授权的问题，这点比 MIT 强一些。

  • 显式专利授权：贡献者自动授予专利许可，你用这份代码时，不会因为贡献者手里的专利被反咬。
  • 专利报复条款：如果对项目发起专利诉讼，将丧失所有专利权。
  • 可闭源商用：允许将代码用于闭源商业产品。

除这三条，Apache 2.0 还有两个实操要求容易忽略：项目里如果有 NOTICE 文件，你的发行包要把里面的署名信息带上；商标不授权，许可证给的是版权和专利许可，别拿别人项目名做产品名。

三者对照 #

维度 MIT BSD 2/3-Clause Apache 2.0
闭源商用 允许 允许 允许
NOTICE 文件 无 无 要求
显式专利授权 无 无 有
专利报复 无 无 有
商标授权 无 3 条款禁背书 明确不含
与 GPLv2 兼容 兼容 兼容 不兼容
与 GPLv3 兼容 兼容 兼容 兼容

Apache 2.0 那一行「与 GPLv2 不兼容」很关键，第十四章单独拆。

怎么添加许可证 #

工程上两种做法，可以同时用。

bash
# 方式一：SPDX 标识符，写在每个源文件头部
# SPDX-License-Identifier: MIT
# Copyright (c) 2026 Your Name

# 方式二：仓库根目录放 LICENSE 文件
cat > LICENSE << 'EOF'
MIT License

Copyright (c) 2026 Your Name

Permission is hereby granted, free of charge, to any person obtaining a copy
of this software and associated documentation files (the "Software")...
EOF

SPDX 标识符的好处是机器可读，CI 里跑一遍就能列出整个仓库用了哪些许可证。仓库根目录的 LICENSE 文件是给人看的，也是给客户合规审核看的。

六、Qt 的三大授权模式 #

前面五章是通用规则，从这里开始全部落到 Qt 身上。同一份代码，三条法律通道。

对比项 商业授权 GPL 授权 LGPL 授权
费用 按合同付费 免费 免费
你的程序能否闭源 能 不能 能
静态链接 允许，无附加义务 允许，但整个程序要 GPL 允许，但要交目标文件
修改 Qt 源码 可以，不必公开 可以，必须公开 可以，必须公开
模块范围 商业包内全部模块 开源版内 GPL 模块 开源版内 LGPL 模块
官方支持 有，按合同 SLA 无 无
适合谁 闭源商业产品、设备厂商 本身就是 GPL 的项目 闭源产品里的动态链接

商业授权换来什么 #

它换来的不只是许可，还有几样工程上的东西：

  • 静态链接的许可。不用交目标文件，不用管替换权，打包成单文件 exe 也行。
  • 修改源码不公开的权利。你要给 Qt 打补丁适配自家硬件，补丁可以留在自己手里。
  • 部分专属模块。这些模块在开源版里根本不存在。
  • 官方技术支持与问题响应。出线上事故时有人接电话，这在项目后期价值很高。
  • 长期维护版本。开源版按公开节奏走，商业客户能拿到更长的维护窗口。

开源版的两条通道 #

开源版默认走 LGPLv3，部分模块走 GPLv3。同一份 Qt 源码，在不同模块上适用不同许可证，你的项目里用到的每个 Qt 模块都要单独确认许可声明。

全用核心模块的项目，走的就是 LGPL；一旦引入某个 GPL 模块，整个程序就被拉到 GPL 那一边。

Qt 公司能把同一份代码既卖商业授权又发开源授权，前提是它持有全部版权。所以 Qt 接受社区贡献时，要求贡献者签贡献者许可协议，把再授权权让渡出来。这件事对你的实际影响只有一个：你给 Qt 提的补丁，不归你独家所有。

三条通道不是互斥的。同一个产品里可以混着用，比如核心模块走 LGPL 动态链接，某个只在商业版提供的模块单独买授权。代价是合规台账变复杂：哪台设备、哪个版本、哪个模块走的哪条通道，得记清楚。审计查的就是这本账。

七、商业授权：什么时候必须买 #

判断标准不是「公司有多大」，是「你的用法撞不撞开源版的红线」。

必须买的六种情形 #

情形 为什么绕不过去
静态链接 + 闭源 + 不愿交目标文件 替换权无法满足，只剩商业授权一条路
使用仅商业版提供的模块 开源版里没有这个模块，没有替代路径
要改 Qt 源码且不公开修改 GPL 与 LGPL 都要求公开对库的修改
消费类设备锁定固件 撞上 GPLv3 / LGPLv3 的安装信息要求
公司政策禁止任何 copyleft 组件 法务红线，与代码怎么写无关
需要 SLA 与长期维护版本 开源版没有合同级别的支持承诺

第三种情形值得多说一句。很多团队觉得自己不会去改 Qt 源码，实际项目里打 Qt 补丁太常见了：适配特殊屏幕、修一个上游没修的 bug、绕开某个平台的坑。你打了补丁又闭源发布，义务就产生了。

不必买的情形 #

  • 只在自己公司内部用的工具、脚本、内网系统。没有对外分发，义务不启动。
  • 项目本身就是 GPL 或其它兼容开源许可证。走 GPL 通道就行。
  • 动态链接 + 闭源 + 愿意履行 LGPL 义务。这条路合法，能卖钱。
  • 用 Qt 写了个小工具免费放出去，源码也一起给。

采购时的几个口径 #

授权怎么算钱，以销售合同和官方许可文本为准，这里不谈数字。但有几件事会影响你报的席位数量，先问清楚：谁算一个开发者（碰 Qt 代码的、只做打包的、只做 CI 维护的，各家口径不同）；构建机算不算；外包与离岸团队怎么算；跨大版本升级是否含在订阅里；订阅到期后还能不能用已发布的版本。

把这些问清楚再签字，比事后解释便宜。

一个常见的误解是：买了 Qt 商业授权，项目就干净了。不是。商业授权只解决 Qt 本身，你项目里另外引入的 GPL 库、AGPL 库、许可证不明的库，义务独立存在。网上关于「商业授权能不能这样用」的讨论，多数是猜测，真正的答案在你签的合同和官方许可文本里，有疑问走销售渠道要书面答复。

八、GPL 授权：传染性的边界 #

GPL 是三条通道里最容易被误判的一条。误判方向有两个：把 GPL 当 LGPL 用，或者把 GPL 想得比实际更可怕。

义务仍由分发触发。你在公司内部拿 GPL 版 Qt 写个内部系统，自己人用，不分发，义务不启动。一旦把安装包给客户、把固件烧进设备卖出去、把程序放官网让人下载，分发成立，整个衍生作品都要按 GPL 提供源码。

衍生作品的定义有争议 #

这是全篇最需要如实说明的地方。GPL 要求「衍生作品」整体按 GPL 授权，但什么叫衍生作品，许可证文本没给出技术上的精确定义，法律上也没有形成统一结论。

text
同一进程 + 静态链接   → FSF 认为构成衍生作品，业界分歧最小
同一进程 + 动态链接   → FSF 认为仍构成衍生作品，业界有不同看法
独立进程 + IPC/命令行 → 多数观点认为不构成衍生作品
插件 + dlopen 动态加载 → 灰区，取决于耦合程度与数据交换方式
仅 include 头文件      → 灰区，取决于头文件里有多少实质代码

FSF（自由软件基金会）的立场一直很明确：动态链接也是结合成一个程序，属于衍生作品。这个立场不是法院判决，但它影响了很多公司的合规政策。业界的分歧点在于：动态链接只是运行时调用，两个作品各自独立存在，凭什么算一个作品。这个争论从 1990 年代持续到现在，没有定论。

现实中的判断标准 #

法律结论不确定，工程上只好用保守规则。多数公司按这条线切：

  • 跟 GPL 代码编进同一个二进制文件的，一律当衍生作品处理。
  • 跟 GPL 代码运行在同一个进程、直接调用其符号的，当衍生作品处理。
  • 通过独立进程、socket、命令行、文件交换的，按独立程序处理，各自保留自己的许可证。

这条线不是法律结论，是风险控制线。它能覆盖绝大多数场景，边界上的少数情况要单独评估。

如果一件事的法律结论不确定，而代价是把整个产品的源码交出去，那就别赌。想用 GPL 版 Qt，前提是你的项目本身就该是 GPL。开源项目、内部工具、以开源为卖点的产品，走这条路正好；闭源商业产品走这条路，等于把最贵的资产押在一个没有判例的问题上。

验证阶段用 GPL 版没问题，但要记住一件事：验证完转闭源发布前，得把链接方式和授权一起切过去，别把验证期的构建配置带到发布版里。

九、LGPL 授权：动态链接的分寸 #

LGPL 是闭源商业产品用 Qt 的主流路径。它的全部逻辑可以压成一句话：让用户能把这个库换掉。

替换权是核心 #

动态链接天然满足替换权。dll 或 so 是独立文件，用户在文件系统里换一个同名文件，程序照跑。

静态链接破坏替换权。库的代码已经编进你的可执行文件，用户没有任何办法换掉它，除非你把可执行文件拆开重新链接。LGPL 的应对办法是：静态链接也行，但你得提供让用户能重新链接的材料。

动态链接的五项义务 #

义务 具体做法 常见漏项
声明使用了 Qt 及其版本 文档、关于对话框、发行说明里写清 只在源码注释里写了
随附 LGPL 许可证文本 安装目录放 LICENSE.LGPLv3 只放了自己的 EULA
提供 Qt 源码或获取途径 附源码包，或给出书面获取要约 只说「详见官网」，没有书面承诺
保证库可被替换 库以独立文件分发，不做校验锁死 打包时把 dll 加密或做了完整性校验
不禁止调试性反向工程 EULA 里不写禁止条款 EULA 是抄来的模板，写了禁止反向工程

最后一行踩的人最多。EULA 从别的产品抄了个模板，里面一句「禁止对本软件进行反向工程、反编译」，直接跟 LGPL 的要求冲突。这一句要删掉或者加例外。

打包时的具体动作 #

bash
# Windows：收集运行时依赖到 deploy 目录
windeployqt --release --no-translations build/MyApp.exe
# 再手动补进 LICENSE.LGPLv3 与 QT-SOURCE-OFFER.txt

# Linux：确认依赖的是动态库，不是静态编进去的
ldd ./myapp | grep -i qt

最后这条检查很实用。有些构建配置默认静态链接，你自己都不知道，ldd 一跑全露出来——如果一条 Qt 都没有，就是静态编译了。

把替换权做实 #

替换权不能只是「理论上能换」。这几种做法会把它做实：库文件放在普通目录、权限正常、用户能覆盖；不把库文件嵌进加密容器或资源包；不做「库文件哈希校验失败就拒绝启动」这种设计；安装包允许用户保留自己的库版本。

反过来，这几种做法会破坏替换权：把 Qt 库编进一个大的自解压包、运行时内存加载；用代码签名绑定所有 dll，用户换一个就报错；把 dll 重命名、加壳、混淆；卸载程序检测到库文件被改就回滚。

这些做法在商业上都有正当理由，比如防篡改、防破解，但它们跟 LGPL 的替换权直接冲突。想要这两样，就买商业授权。

移动平台的现实 #

移动端要单独看。iOS 与 Android 上，Qt 应用的构建方式、库的打包方式跟桌面差别很大，静态链接在移动端更常见。一旦静态链接，你就落到静态链接的义务里，不是「移动端有豁免」。iOS 上还有个额外约束：应用商店的规则对动态加载第三方库有限制。

这块的判断要两头看：许可证文本怎么说，平台规则怎么说。哪一头不满足，就只剩商业授权这条路。这也是很多移动产品最终买 Qt 商业授权的原因。

LGPLv3 的文本结构是「GPLv3 + 额外许可」，它把 GPLv3 的显式专利授权、专利报复、反 Tivoization 都继承下来，再叠上库的特殊待遇。落到设备项目上：如果你的产品是面向消费者的「用户产品」，又用了 LGPLv3 的 Qt，安装信息要求会跟你的固件签名机制打架。LGPLv2.1 没有这些条款，所以有些老项目会专门选 LGPLv2.1 的版本。

十、静态链接 LGPL 的合规问题 #

静态链接不是禁区，它是一个代价很高的选项。先把代价算清楚，再决定要不要走。

静态链接把库的机器码复制进你的可执行文件。链接完成的那一刻，库和你自己的代码在物理上不可分，用户拿到的是一整个 exe，里面没有「Qt 那一块」可以被替换。LGPL 的处理方式是：你用静态链接可以，但要给用户重建的能力——用户能拿着材料，重新链接出一个功能等价的可执行文件。

三项义务 #

义务 交付物 目的
提供目标文件 你自己代码编译出的 .o / .obj 文件 让用户能重新链接，不必拿到你的源码
提供库源码 你使用的 Qt 版本源码，含你的修改 让用户能改库并重编
提供重链接说明 链接命令、工具链版本、构建脚本 让用户知道怎么把上面两样拼起来

关键点在第一项：交的是目标文件，不是源码。目标是让用户能重链接，不是让用户读懂你的业务逻辑。这个区别在商业谈判里很重要，目标文件仍然暴露符号名和部分结构信息，但不含源码级的实现。对多数团队来说，这是可接受的妥协；对少数团队来说，这已经越过了红线。

履行起来的具体难点 #

难点 说明
构建可复现 用户要能用自己的环境重链接，你的编译选项得写清楚
工具链一致 编译器版本、C++ 标准库版本不同，链接会失败
符号裁剪 开了 strip 或 LTO，目标文件往往不足以重链接
第三方 SDK 你用的闭源 SDK 的目标文件不能转手，义务就断链
版本匹配 Qt 源码版本必须和你链接的完全一致
长期维护 每个发布版本都要留一份完整材料

第三方 SDK 那一条最致命。你的项目里如果还链了别的闭源库，那些库的目标文件你无权分发，整个重链接方案就落不了地。

义务的边界在哪 #

这里要如实说清楚：静态链接 LGPL 的义务，在实践中被完整履行的案例不多，法律上也缺少广泛检验的判决。

text
争议点一：目标文件的范围
        是自己全部目标文件，还是只有与 Qt 交互的那部分
        主流解读是全部，因为这才能保证重链接成功

争议点二：交付对象
        随产品公开提供，还是仅对有要求的用户提供

争议点三：书面要约的效力
        给一份承诺期内的书面获取要约，是否足够替代随附交付
        实践中被广泛采用，法律效果未充分检验

这些不确定性意味着：走静态链接 LGPL，你在法律上没有一条被验证过的安全路径。你能做的是把义务履行得尽量完整，剩下的风险自己扛。对大公司来说这个风险不可接受，所以它们的做法很统一：静态链接 + 闭源，直接买商业授权，把不确定性换成合同。

三条出路摆在这：履行静态链接义务（工程成本高，每个版本都要维护交付材料，目标文件外流，法律风险仍在）；改成动态链接（一次性改造，分发体积变大）；买商业授权（按席位付费，要过预算审批）。

三条都不便宜，区别在于花在哪。我们的经验是：产品要长期维护、要多版本并行发布的，买授权省心；一次性交付、生命周期短的项目，改动态链接更划算。还有一种折中方案：核心模块动态链接，个别因为技术原因必须静态的模块单独处理，这在嵌入式项目里能见到。前提是你能把义务落到具体模块上，并且在合规台账里写清楚，做不好就变成两头都不合规。

十一、开源义务的实际履行 #

法律条文是抽象的，交付物是具体的。这一章把「履行 LGPL 义务」拆成可以放进发布清单的动作。

发布包里该有什么 #

交付物 内容 谁负责产出
许可证文本 LGPLv3 全文，加第三方组件各自的许可文本 构建脚本自动收集
声明文件 用了 Qt 哪个版本、哪些模块、哪些第三方库 开发填模板
源码获取说明 Qt 源码的获取方式，含你对 Qt 的修改 开发写，法务审
源码包或书面要约 随包附源码，或给一份书面承诺 发布负责人
可替换的库文件 独立的 dll / so，不加密、不校验锁死 打包脚本
重链接材料 只在静态链接时需要：目标文件 + 源码 + 说明 构建负责人

一个能用的目录结构 #

text
release/
├── MyApp.exe
├── Qt5Core.dll / Qt5Gui.dll / Qt5Widgets.dll
├── licenses/
│   ├── LICENSE.LGPLv3
│   └── THIRD-PARTY-NOTICES.txt
├── QT-USAGE.txt              # 用了哪个 Qt 版本、哪些模块
├── QT-SOURCE-OFFER.txt       # 源码获取的书面承诺
└── relink/                   # 仅静态链接时存在
    ├── obj/                  # 你的目标文件
    ├── qt-src.tar.xz         # Qt 源码，含修改
    └── RELINK-HOWTO.txt      # 工具链版本 + 链接命令

QT-SOURCE-OFFER.txt 不用长，关键是把承诺写死：

text
本产品使用了 Qt（版本与模块见 QT-USAGE.txt），依据 LGPLv3 授权使用。
Qt 完整源码可从 https://download.qt.io/ 对应版本目录获取，或联系
opensource@example.com。我们对源码的所有修改均已包含在内，未做隐藏修改。
您可以自行编译 Qt 并替换安装目录下的同名动态库文件，本产品不会校验
库文件的完整性，也不会因此拒绝运行。本承诺自发布之日起 3 年内一直适用。

那句「不会校验库文件的完整性」，是把替换权落到纸面。写了就要做到，代码里那个哈希校验得真的去掉。

CI 里加两道检查 #

合规不是一次性动作，每次发版都要过一遍。

bash
# 第一道：列出仓库里出现的所有 SPDX 标识，人工核对新增项
grep -rhoE 'SPDX-License-Identifier: .*' \
  --include='*.cpp' --include='*.h' --include='*.cmake' . \
  | sort | uniq -c | sort -rn

# 第二道：确认产物是动态链接，Qt 库是独立文件
ldd ./build/myapp | grep -i qt

第二道最容易被忽略，也最容易翻车。构建脚本一改，静态链接悄悄生效，这时候发出去的包已经不合规了。Windows 上换成依赖查看工具，看导入表里有没有 Qt 的 dll。

义务是持续的：新增了第三方库，许可证清单要更新；升级了 Qt 版本，源码包和声明文件要跟着换；改了 Qt 源码，修改要同步进随包的源码里；改了 EULA，要重新检查有没有跟 LGPL 冲突的条款。把它做成构建流水线的一步，比靠人记靠谱。人一忙就忘，脚本不会。

十二、第三方库的许可叠加 #

你的产品不是只有 Qt。Qt 自己也不是铁板一块，它随源码带了一批第三方组件。

Qt 树里的第三方组件 #

Qt 源码树的 src/3rdparty 目录下有一批外部代码，它们各有各的许可证。你打包 Qt 的时候，等于把这些也一起打包了。

组件 常见许可证 要注意什么
zlib zlib License 宽松，保留声明
PCRE2 BSD 3-Clause 保留声明，禁作者背书
FreeType FreeType License 或 GPLv2 双许可，选 FTL 那条
libpng libpng License 宽松，保留声明
ICU Unicode License 宽松
OpenSSL Apache 2.0（3.x 起） 与 GPLv2 的兼容存在争议

具体清单以源码树里 src/3rdparty 各目录下的许可文件为准。版本不同，带的组件和版本都不同，别按旧记忆套。

OpenSSL 有桩老争议：1.1.x 及更早用一份自定义许可证，FSF 认为它跟 GPL 不兼容，GPL 项目要用 OpenSSL 得走例外条款或者换实现。OpenSSL 3.x 改成 Apache 2.0，跟 GPLv3 兼容，跟 GPLv2 仍然不兼容。实际影响是：如果你的 Qt 应用走 GPLv2 通道又链了 OpenSSL，组合起来的合法性要单独评估；走 LGPL 动态链接的项目不受这条影响，因为主程序不是 GPL。

叠加的三种结合方式 #

结合方式 例子 许可后果
并入同一个二进制 静态链接、同一份源码里复制代码 各许可证义务叠加，取最严
运行时链接 动态链接 dll / so 各自保留自己的许可证，衍生作品判断仍在
聚合分发 安装包里放了多个独立程序 各管各的，不互相传染

「取最严」最容易出事。你的项目里只要混进一个 GPL 组件，整个二进制就被拉到 GPL。

插件架构能做的事和不能做的事 #

把第三方 GPL 库做成独立进程或者独立插件，通过 IPC 或者动态加载通信，可以让它跟主程序在法律上分开，这是很多商业软件隔离 GPL 组件的做法。边界要清楚：进程隔离 + 明确定义的接口，隔离效果最好；dlopen 加载插件，隔离效果取决于耦合程度，属于灰区；直接 include 头文件 + 调用符号，隔离基本不成立。

想做隔离，就别在接口上偷懒。传结构体指针、共享内存布局、互相 include 头文件，这些都会削弱「两个独立程序」的主张。

十三、企业项目的选型建议 #

前面都是拆解，这一章给结论。

决策顺序 #

text
程序会分发到公司外部吗？
├─ 不会（内网系统、内部工具、数据分析脚本）
│   └─ 三条通道都能用，LGPL 动态链接最省事，GPL 也不违法
└─ 会
    ├─ 项目本身是 GPL 兼容的开源项目 → 走 GPL 通道，省钱且符合定位
    └─ 要闭源
        ├─ 能动态链接 → 走 LGPL，履行动态链接的五项义务
        └─ 不能（静态链接、单文件部署、嵌入式固件）
            ├─ 能交目标文件并长期维护 → 走 LGPL 静态义务，风险自担
            └─ 不能 → 买商业授权

顺序很重要：先定分发形态，再定链接方式，最后才落到授权。反过来做，会为没有约束的场景白花钱。

场景对照 #

场景 走哪条路 理由
内部管理系统 LGPL，动态链接 不分发，义务不启动
对外销售的桌面软件 LGPL 动态链接或商业授权 动态能过就不买，静态就得买
消费类硬件固件 商业授权优先 撞安装信息要求，静态链接又没有替换权
工业设备上位机 LGPL 动态链接 有文件系统，能替换库，一般不锁死固件
开源桌面工具 GPL 通道 项目本身就是 GPL
移动端应用 商业授权优先 静态链接是常态，替换权难落实
汽车座舱、医疗设备 商业授权 行业合规要求高，需要 SLA 与版本锁定

许可证选择的通例 #

如果是你自己的代码要选许可证，参考这张表：

场景 推荐许可证 原因
商业闭源产品使用开源库 MIT / BSD / Apache 2.0 无 Copyleft 传染
企业级共享库 Apache 2.0 专利保护 + 专利报复
希望代码保持开源 GPL v3 强 Copyleft
库允许闭源程序链接 LGPL v3 弱 Copyleft
嵌入式设备 避开 GPLv3 / LGPLv3 反 Tivoization 条款

三个时间点别错过 #

  1. 立项选型时。这时候改技术栈成本最低，链接方式还没写进构建脚本。
  2. 第一次对外发布前。发布动作一旦做出，义务就产生了，补不回来。
  3. 客户合规审核前。客户的采购流程会问许可证清单，临时准备一定缺东西。

第三点最容易被低估。大客户的入库审核表里常有「交付物不得包含 GPL 组件」这类硬条款，你的包里只要有一个，整个交付就卡住。

十四、常见误解 #

把反复听到的说法列出来，逐条对。

误解 事实
开源就是免费 许可证管权利，不管价格
动态链接 GPL 库就安全 GPL 不区分动态与静态，FSF 认为都构成衍生作品
买了 Qt 商业授权项目就干净了 只覆盖 Qt，第三方库义务独立存在
内部使用也必须开源 分发才触发义务，内网使用不启动
改个名字、重写一遍就洗掉了 看代码来源与结构，不看命名
名字里带 L 的许可证都宽松 要看具体版本条款与模块许可声明
MIT 没有专利条款所以随便用 没有专利授权，风险留给使用者
Apache 2.0 到处都能用 与 GPLv2 不兼容
源码可见就是开源 带商用限制的可见源码不是开源

混淆 GPL 与 LGPL #

这是 Qt 项目里代价最高的错误。

cpp
// 错误认知：使用 GPL 库只要动态链接就没问题
// 实际：GPL 无论动态还是静态链接，整个程序都必须 GPL

// 正确：确认是 LGPL 而非 GPL
// LGPL 动态链接可免于 Copyleft

判断方法很简单：打开该模块的许可声明文件，看它写的是 GPL 还是 LGPL。别看论坛，别听同事转述。

忽略 GPLv2 与 GPLv3 不兼容 #

bash
# Linux 内核是 GPL-2.0-only
# 不能将 GPL-3.0-only 代码合入 Linux
# 除非原代码标注为 GPL-2.0-or-later

这条不只对内核成立。任何 GPLv2-only 的项目，都不能直接吸收 GPLv3 代码。反过来可以：GPLv2-or-later 的项目能升级到 GPLv3。

Apache 2.0 用于 GPLv2 项目 #

text
Apache 2.0 与 GPLv2 不兼容
Apache 2.0 与 GPLv3 兼容

若项目有 GPLv2 代码，不能引入 Apache 2.0 代码

原因在专利条款。Apache 2.0 附加了专利授权和专利报复条件，GPLv2 不允许在分发时附加额外限制，两者撞车。

选协议的时候想想：你希望别人怎么用你的代码？想闭源就选 BSD/MIT，想强制开源就选 GPL。想平衡就考虑 LGPL 或 Apache。

十五、易错点速查 #

最后一章是清单。发版前逐条过一遍，比读十篇文章管用。

检查项 正确做法 出错后果
确认模块许可证 逐个模块看许可声明，不按印象判断 把 GPL 模块当 LGPL 用，整个程序要开源
确认链接方式 用 ldd / 依赖查看工具验证产物 以为是动态链接，实际静态编进去了
随附许可文本 安装目录放全所有组件的许可文本 审核不通过，交付卡住
保留版权声明 关于对话框或文档里列出第三方组件 MIT / BSD 的署名义务没履行
EULA 措辞 删掉禁止反向工程的条款 与 LGPL 冲突，替换权失效
库文件可替换 独立文件、不加密、不做完整性校验 LGPL 主张站不住
源码获取承诺 书面承诺写清版本、地址、期限 义务无人履行
修改 Qt 源码 修改同步进随包源码 隐瞒修改，构成违约
静态链接材料 目标文件 + 源码 + 重链接说明 缺一样，链路就断
第三方库清单 从构建产物反查，不靠开发记忆 漏一个 GPL 组件，前功尽弃
商业授权范围 核对合同里的模块、席位、版本 以为买了，实际没覆盖
客户合同条款 采购前对一遍许可证清单 中标后被迫重构

三句话与四个问题 #

如果只能记住三句话，记这三句：分发才触发义务，内网自己用随便。LGPL 的核心是让用户能换掉库，动态链接天然满足，静态链接要交目标文件。静态链接 + 闭源 + 不想交目标文件，就是买 Qt 商业授权的那条线。

接到新项目，问自己四个问题，五分钟能定下方向：这个东西会给公司外部的人吗；会的话，能不能接受动态链接；用到的 Qt 模块里，有没有只在商业版出现的；客户的合同里有没有许可证限制条款。四个答案组合起来，就能定下要不要走采购流程。早点问，别等到打包那天。
