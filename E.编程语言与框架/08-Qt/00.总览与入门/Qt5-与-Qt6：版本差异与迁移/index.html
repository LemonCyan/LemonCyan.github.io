讲什么：Qt5 到 Qt6 之间真正会挡住你的东西——平台门槛、构建系统换代、模块搬家、API 移除、图形栈抽象，以及一套能落地的迁移顺序和踩坑清单。

不讲什么：框架组成与学习路线，见同目录《Qt 是什么》；LGPL/GPL/商业授权怎么选，见《Qt 的开源协议》。文中的 qmake 配置、部署命令、Qt5 代码，都只为对照迁移前后的差异，不承担 Qt5 教程的职责。

怎么读：手上已有 Qt5 工程、正在评估要不要迁的，先看第一、二章，再看第十一章；已经被编译错误顶住的，直接跳第十、十四章。

一、Qt5 与 Qt6 的分水岭 #

Qt 6.0 出在 2020 年 12 月，Qt 5 的最后一支主线是 2020 年 5 月的 5.15。这不是一次「加点新类、改改文档」的升级。删掉的 API、搬家的模块、换掉的构建系统、重写的渲染路径，四件事同时发生。

先把两边的定位摆在一起看。

维度 Qt 5.15 Qt 6
构建系统 qmake 为主，CMake 能用但不算一等公民 CMake 为主，qmake 随附但不再承载新特性
图形栈 OpenGL 直连，Windows 上走 ANGLE 转 Direct3D RHI 抽象层，后端可选 D3D11 / Vulkan / Metal / OpenGL
C++ 标准 C++11 够用 最低 C++17，降不下去
Windows 底线 32 位、Win7、Win8.1 都能跑 只认 64 位 Win10 1809 及以上
模块边界 QtCore 里塞着 QRegExp、QTextCodec、QLinkedList 这些挪进 Core5Compat
维护状态 5.15 LTS，开源版停在 5.15.2 6.2 / 6.5 / 6.8 各有 LTS 分支

Qt6 最大的变化不是 API #

这句要记住：Qt6 最大的变化不是 API，而是构建系统默认转向 CMake、图形栈抽象成 RHI。这两点决定了迁移的工作量，而不是那张长长的废弃 API 列表。

为什么是这两点：

  • CMake 不是把 .pro 里的几行翻译成几行 CMakeLists.txt。CONFIG 那套开关、include(.pri) 的复用、QMAKE_EXTRA_TARGETS 的自定义构建步骤、编译后的部署钩子，全都要在 CMake 里重新表达一遍，语言不同，思维也不同。
  • RHI 一动，凡是手碰 OpenGL 的代码都要重看：QOpenGLWidget、QQuickWindow 的 GL 回调、自己写 shader 的 QQuickItem、调 QSurfaceFormat 参数的地方。Qt6 里 Qt Quick 默认不再走 OpenGL，你原来「反正有 OpenGL」的假设直接失效。

迁移精力的实际分布，大致是这样：

工作项 占的精力 真正的卡点
换构建系统 四成 子项目依赖、自定义编译步骤、资源与翻译规则
图形栈相关 两成半 OpenGL 直连代码、ANGLE 失效、软件渲染兜底
清 API 两成半 QRegExp / QTextCodec / QVariant::type 这类高频类型
QML、打包、回归 一成 版本导入、插件打包、部署脚本

先决定迁不迁 #

能留在 Qt5 就留。5.15 是 Qt5 的 LTS，开源版停在 5.15.2，商业授权还能续，但代码是冻结的。判断标准不是你喜不喜欢新版本，而是「有没有一个必须迁的理由」。

你的情况 结论
用户里还有 Win7、Win8.1、32 位机器 留 Qt5，别迁
依赖 Qt WebEngine，要跟 Chromium 的安全更新 迁，Qt6 的 WebEngine 跟得更紧
Qt Quick 项目，想吃 Vulkan / Metal 的渲染路径 迁
代码里有大量 QtScript、QXmlPatterns、QGLWidget 先算重写成本，再决定
只是想「顺手升个级」 别迁，5.15 还能撑很久

真要迁，选版本别选 6.0。6.0 是首版，模块缺口大，很多今天理所当然的东西那时候还没有。

版本 时间 定位
6.0 2020-12 首版，缺口多，别拿它上生产
6.2 2021-09 第一个 LTS，补齐了一大批模块
6.5 2023-04 LTS，Qt5 迁移的主力落点
6.8 2024-10 LTS，当前新项目的首选

二、平台支持的变化 #

这段是硬门槛，没有商量的余地。官方文档写得足够直白：Qt6 不再支持 32 位 Windows 系统，不再支持 Windows 7、Windows 8 和 Windows 8.1，仅支持 64 位 Windows 10 1809 及后续版本；WinRT/UWP 支持已经移除。UNIX 平台的具体条目要查对应的 JIRA ticket。

两份官方 bug 单：

  • https://bugreports.qt.io/browse/QTBUG-85851
  • https://bugreports.qt.io/browse/QTBUG-85855
目标平台 Qt 5.15 Qt 6
Windows 7 支持 不支持
Windows 8 / 8.1 支持 不支持
32 位 Windows 支持 不支持
64 位 Windows 10 1809 起 支持 支持
64 位 Windows 11 支持 支持
WinRT / UWP 支持 已移除
32 位 Windows 自编译兜底 不涉及 官方不出包，自己编也没人保证

反过来推，要保住某个平台，该用哪个版本，答案是现成的：

你要保住的需求 该用的版本
继续支持 Windows 7 / WinRT / UWP Qt 5.15
继续支持 Windows 8.1 Qt 5.12
要 32 位版本 继续用 Qt5，或者自己编译 Qt6

这张表能解释很多「为什么这个项目迁到一半停住了」。不是代码改不动，是客户的机器装不上。

编译器与语言标准的门槛 #

Qt6 把 C++17 定成硬底线，编译器的门槛跟着抬。

项目 Qt 6 的要求
C++ 标准 C++17，CONFIG += c++11 这种写法直接失效
MSVC 2019 起
GCC 8 起
Clang 10 起
Apple Clang 11（Xcode 11）起
macOS 10.14 起
Android API 23 起，NDK 用 r21 及以上

老工程里那些 CONFIG += c++11、CONFIG += c++1z 的残留要一次性清掉。qmake 里对应的新写法是 CONFIG += c++17，CMake 里是 CMAKE_CXX_STANDARD 17 加 CMAKE_CXX_STANDARD_REQUIRED ON。

平台宏的变化 #

写跨平台代码的那批宏，Qt6 清掉了一些。

宏 Qt5 Qt6
Q_OS_WIN 有 用 Q_OS_WINDOWS（Qt 5.14 引入）
Q_OS_MAC 有，已废弃 移除，用 Q_OS_MACOS
Q_OS_WINRT 有 移除
WIN32 32 位和 64 位都会定义 别拿它判 64 位，用 Q_OS_WIN64 或 Q_PROCESSOR_X86_64
Q_OS_MINGW、Q_OS_ANDROID、Q_OS_IOS 有 保留

有一句提醒还算数：判断 64 位不要用 WIN32，因为 32 位和 64 位平台上它都会被定义。要判就用 Q_PROCESSOR_X86_64 这类处理器宏，或者 Q_OS_WIN64。运行时判断用 QOperatingSystemVersion 或 QSysInfo，这两个类在 Qt6 里还活着，QSysInfo::prettyProductName()、kernelVersion()、buildAbi() 这些接口照旧。

交叉编译的方式也变了 #

Qt5 那套 -xplatform 加 -device-option 的写法，在 Qt6 里被 CMake toolchain 文件取代。Qt5 时代的命令长这样：

bash
configure -xplatform win32-clang-g++ -device-option CROSS_COMPILE=x86_64-w64-mingw32-

三个坑点原样保留：CROSS_COMPILE 前面没有 -，它前面要跟一个独立的 -device-option，末尾那个 - 不能丢。迁到 Qt6 之后这条命令没有对应物，换成一份 toolchain 文件加 -DCMAKE_TOOLCHAIN_FILE，同时必须用 -DQT_HOST_PATH 指向宿主机的 Qt6 安装，否则交叉编译的 Qt 工具链（moc、rcc、uic）找不到。

部署侧的连锁反应 #

平台一改，发布包的内容也跟着改。

Qt5 在 Windows 上要带 libEGL.dll 和 libGLESv2.dll 这一对 ANGLE 文件，windeployqt 甚至有 --no-angle 参数专门用来不复制它们。Qt6 不再用 ANGLE，这两个文件从发布清单里消失，--no-angle 也就没有对象可关。反过来，platforms\qwindows.dll、styles\、platformthemes\、imageformats\ 这些插件目录一个都不能少。

三、构建系统的变化：qmake 与 CMake #

Qt6 自己就是用 CMake 构建的。你继续用 qmake 编自己的工程，Qt6 的 qmake 也认，但官方文档、示例、新特性——qt_add_qml_module、QML 模块化、大资源处理、翻译嵌入——全部以 CMake API 为准。迁 Qt6 的第一件事，就是把 .pro 换成 CMakeLists.txt。

同一个程序的两种工程文件 #

Qt5 的 .pro：

text
QT += core gui widgets network
CONFIG += c++17
TARGET = myapp
TEMPLATE = app
SOURCES += main.cpp mainwindow.cpp
HEADERS += mainwindow.h
FORMS += mainwindow.ui
RESOURCES += res.qrc
TRANSLATIONS += i18n/zh_CN.ts

Qt6 的 CMakeLists.txt：

cmake
cmake_minimum_required(VERSION 3.16)
project(myapp LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

find_package(Qt6 6.5 REQUIRED COMPONENTS Core Gui Widgets Network)
qt_standard_project_setup()

qt_add_executable(myapp
    main.cpp
    mainwindow.cpp
    mainwindow.h
    mainwindow.ui
    res.qrc
)

target_link_libraries(myapp PRIVATE
    Qt6::Core
    Qt6::Gui
    Qt6::Widgets
    Qt6::Network
)

qt_add_translations(myapp TS_FILES i18n/zh_CN.ts)

qt_standard_project_setup() 一句顶掉 Qt5 里的一堆手动配置：它打开 AUTOMOC 和 AUTOUIC，把 C++ 标准设成 17，把 CMAKE_INCLUDE_CURRENT_DIR 打开。.ui 和 .qrc 直接列进源文件列表就行，不用再手写 qt5_wrap_ui、qt5_add_resources。

qmake 到 CMake 的对照 #

qmake 写法 Qt6 的 CMake 写法
QT += widgets find_package(Qt6 COMPONENTS Widgets) 加 target_link_libraries(... Qt6::Widgets)
SOURCES / HEADERS qt_add_executable 的源文件列表
FORMS += x.ui .ui 直接进源文件列表，AUTOUIC 处理
RESOURCES += x.qrc .qrc 进源文件列表，或 qt_add_resources
qt5_add_resources qt_add_resources
qt5_add_big_resources qt_add_big_resources
CONFIG += resources_big qt_add_big_resources
qt5_add_translation qt_add_translations
CONFIG += qmltypes qt_add_qml_module 自动生成
TEMPLATE = subdirs add_subdirectory()
sub.depends += other add_dependencies(sub other)
DESTDIR = $$PWD/bin RUNTIME_OUTPUT_DIRECTORY 属性
CONFIG += console / cmdline add_executable 不加 WIN32
CONFIG += windows add_executable(... WIN32 ...)
CONFIG += skip_target_version_ext set_target_properties(... VERSION ...) 自行控制
qtHaveModule(winextras) if(TARGET Qt6::WinExtras)
qtConfig(draganddrop) if(QT_FEATURE_draganddrop)
include(x.pri) include() 或拆成 INTERFACE 库
QMAKE_EXTRA_TARGETS + POST_TARGETDEPS add_custom_command(TARGET ... POST_BUILD ...)
win32 { ... } if(WIN32) ... endif()

命令行编译也换了。Qt5 那一套是：

bash
qmake "example.pro" -spec win32-clang-g++ "CONFIG+=release"
jom qmake_all
jom
jom install

-spec 指定 mkspec，不给就用平台默认；CONFIG 给额外配置项，不给也是平台默认。这套命令全平台通用，区别只在最后的 make 工具：MinGW 用 mingw32-make，Unix 用 make。Windows 上建议用 JOM 代替 NMake 或 mingw32-make，速度差得远，但 JOM 只支持原生 Windows 环境，MinGW 这类类 Unix 环境用不了。迁到 Qt6 之后，这些位置换成 cmake --build build --config Release，生成器选 Ninja 或 MSBuild，JOM 整个退出舞台。

Qt5 的 qmake 细节，哪些在 Qt6 里还成立 #

.qmake.conf 放在 .pro 同目录，qmake 会在加载 .pro 之前先加载它，把通用配置写这里很省事。CMake 里对应的是 cmake/ 子目录加 include()，或者干脆写成一个 INTERFACE 库。

qt.conf 放在程序所在目录，用来改 Qt 加载库和翻译文件的路径。这份文件在 Qt6 里照样能用，只是代码里取路径的 API 变了：Qt5 的 QLibraryInfo::location(QLibraryInfo::TranslationsPath) 换成 Qt6 的 QLibraryInfo::path(QLibraryInfo::TranslationsPath)。这里有个坑：在 Qt Creator 里跑程序时，location() 返回的是当前 Kit 的路径，不是你在 qt.conf 里设的路径；只要不是从 Qt Creator 启动就没这个问题。

输出目录，Qt5 是 DESTDIR = $$PWD/bin，Windows 上 dll 另有 DLLDESTDIR；Qt6 用 RUNTIME_OUTPUT_DIRECTORY 和 LIBRARY_OUTPUT_DIRECTORY 两个属性。

目标文件名的调试后缀，Qt5 靠 TARGET = $$qtLibraryTarget(name) 自动加（Windows 加 d，Linux 加 _debug 并补 lib 前缀）。有个细节要盯住：别用 qt5LibraryTarget，那个会额外加 Qt5 前缀，只有 Qt 自己的库才需要。Qt6 里这个函数不存在了，CMake 侧用 set_target_properties(tgt PROPERTIES DEBUG_POSTFIX d)。

子项目，Qt5 是 TEMPLATE = subdirs 配 SUBDIRS +=、xxx.file、xxx.depends；CONFIG += ordered 表示按书写顺序生成。Qt6 换成 add_subdirectory 加 add_dependencies，顺序由依赖拓扑决定，不再需要 ordered。

qmake 的几个便利函数，在 CMake 里都有替代：判文件存在用 exists()，CMake 用 if(EXISTS)；判变量空用 isEmpty()，CMake 用 if(NOT var)；字符串拼接 Qt5 是 join(a,,,b)，替换是 replace(str,old,new)，CMake 用 string(JOIN ...) 和 string(REPLACE ...)。

versionAtLeast(QT_VERSION, 5.12.0) 这类版本判断，Qt5 里是现成函数（5.9 引入），CMake 里用 if(Qt6_VERSION VERSION_GREATER_EQUAL 6.5)。

$$[QT_INSTALL_BINS] 这种取 Qt 安装路径的写法，Qt5 有二十来个变量（QT_INSTALL_LIBS、QT_INSTALL_PLUGINS、QT_INSTALL_QML、QT_INSTALL_TRANSLATIONS、QT_HOST_BINS 等），取值时必须带方括号：

bash
bin_dir = $$[QT_INSTALL_BINS]

Qt6 里这套变量改由 qtpaths --query QT_INSTALL_BINS 输出，CMake 里则用 QT6_INSTALL_BINS 之类的变量，或直接 get_target_property 从 imported target 上取。

编译 Qt 本身的参数 #

自己编过 Qt5 的人对这些 configure 参数不陌生。Qt6 改用 CMake 配置，参数形式全变，功能还在。

Qt5 参数 作用 Qt6 对应
-opensource 开源版，LGPLv3/GPLv3 默认行为，无需显式指定
-confirm-license 跳过手动同意许可 -DQT_BUILD_TESTS=OFF 之类之外无对应，许可提示已去掉
-debug / -release 编调试版 / 发布版 -DCMAKE_BUILD_TYPE=Debug/Release
-debug-and-release 两种都编 -DCMAKE_CONFIGURATION_TYPES="Debug;Release"
-force-debug-info 发布版也带调试信息 -DCMAKE_BUILD_TYPE=RelWithDebInfo
-shared / -static 动态库 / 静态库 -DBUILD_SHARED_LIBS=ON/OFF
-static-runtime 静态链接运行时（仅 MSVC） -DCMAKE_MSVC_RUNTIME_LIBRARY
-platform / -xplatform 目标平台 / 交叉编译平台 -DCMAKE_TOOLCHAIN_FILE
-optimize-size 为大小优化 -DCMAKE_BUILD_TYPE=MinSizeRel
-ltcg 启用 LTCG/LTO -DCMAKE_INTERPROCEDURAL_OPTIMIZATION=ON
-nomake examples -nomake tests 不构建示例和测试 -DQT_BUILD_EXAMPLES=OFF -DQT_BUILD_TESTS=OFF
-skip qt3d 跳过某模块 -DQT_BUILD_SUBMODULES=qtbase;qtdeclarative 反向指定
-no-feature-<feature> 裁掉某特性（Qt Lite） -DFEATURE_<feature>=OFF
-prefix <path> 安装目录 -DCMAKE_INSTALL_PREFIX
-opengl <api> 默认 OpenGL 版本 Qt6 里由 RHI 后端决定，这个参数没了
-no-icu 禁用 ICU -DFEATURE_icu=OFF
-schannel / -no-openssl 换 TLS 后端 -DFEATURE_schannel=ON / -DFEATURE_openssl=OFF

有几条 Qt5 时代的前置条件，在 Qt6 里整体消失，因为 ANGLE 没了：编 ANGLE 要设 WindowsSdkVerBinPath 指向 fxc.exe 所在目录（常见是 C:\Program Files (x86)\Windows Kits\10\bin\10.0.17763.0，末尾那串是 Win SDK 版本号）；还要装 DirectX SDK 和 Win flex-bison。这些步骤在 Qt6 的构建文档里一个字都找不到。

留下的是稳态约束：Windows 上用 MinGW 编 Qt 不能开 LTO，会报错；Linux 上交叉编 Windows 版要装一堆 glibc 开发包（Ubuntu 上是 libc6-dev-i386、libc6-dev-amd64 那一串）；用 win32-clang-g++ 编静态 Qt 时配置阶段别加 -static-runtime，编自己的工程时 CONFIG 里反而要加 static_runtime，否则报找不到符号。

还有一条和路径有关的老坑：不要把 Qt 工程放在含非英文字符的路径下，否则编不过。换 CMake 之后这条依然成立。

四、模块的拆分与合并 #

Qt6 对 qtbase 动了一次大手术：把一堆「其实不算核心」的类挪走，把常年挂在 QtCore 底下的模块拆成独立库。好处是编译更快、依赖更干净；代价是链接目标、头文件、find_package 的 COMPONENTS 全要改。迁移时第一批编译错误里，一半来自这里。

这张表里最容易被低估的是 QAction 和 QOpenGLWidget 两条。前者不报错，但 #include <QAction> 会突然找得到又找不到，视你链的模块而定；后者一迁就变成未定义引用。

Qt5Compat 是过渡，不是归宿 #

Qt6 给了一个官方过渡模块 Qt5Compat，把 QRegExp、QTextCodec、QLinkedList、QStringRef 这些塞进去，让你先编过再慢慢改。

cmake
find_package(Qt6 REQUIRED COMPONENTS Core5Compat)
target_link_libraries(myapp PRIVATE Qt6::Core5Compat)

cpp
#include <QRegExp>   // 来自 Core5Compat，能编过，但别长期留着

用它的原则很简单：能编过、能跑通，就算阶段胜利。但 QRegExp 的匹配语义和 QRegularExpression 不同（前者是 Qt 自己的方言，后者是 PCRE），你留着它，正则相关的坑就一直是两套规则并存。过渡期控制在一个版本内，别拖。

五、Core 模块的变化 #

Core 是改动最密的地方，绝大多数编译错误在这里冒出来。按类型分块看。

QVariant 与元类型 #

QVariant::Type 整套枚举没了，全部换成 QMetaType。

Qt5 Qt6
variant.type() variant.typeId()
QVariant::Font QMetaType::QFont
variant.typeName() variant.metaType().name()
qvariant_cast<T>(v) 保留，等价于 v.value<T>() 
cpp
// Qt5
if (variant.type() == QVariant::Font) {
    const QFont font = variant.value<QFont>();
}

// Qt6
if (variant.typeId() == QMetaType::QFont) {
    const QFont font = variant.value<QFont>();
}

自己写的结构体要塞进 QVariant，规则没变，但顺序更严格：Q_DECLARE_METATYPE 写在命名空间和类的外面，qRegisterMetaType 尽早调一次、别重复调。

cpp
namespace A::B::C {
struct MyType {};
}
Q_DECLARE_METATYPE(A::B::C::MyType)   // 必须在命名空间外

要转成自定义类型又不确定能不能转，用 canConvert<T>() 先问一句，再 value<T>() 取。qHashMulti 这个辅助函数在 Qt6 里是 QHash 自定义键的标准写法，比手写异或组合省事。

正则：QRegExp 到 QRegularExpression #

不是换个头文件就完事的两套语义。QRegExp 是 Qt 自己的方言，QRegularExpression 是 PCRE 语法。逐条对：

Qt5 QRegExp Qt6 QRegularExpression
rx.exactMatch(s) QRegularExpression::anchoredPattern(p) 后再 match
setPatternSyntax(QRegExp::Wildcard) QRegularExpression::wildcardToRegularExpression()
rx.indexIn(s) rx.match(s).capturedStart()
rx.cap(n) rx.match(s).captured(n)
默认大小写敏感 默认大小写敏感，要忽略得加 CaseInsensitiveOption
QRegExp::escape QRegularExpression::escape 
cpp
// Qt5
QRegExp rx(QStringLiteral("^\\d+$"));
const bool ok = rx.exactMatch(text);

// Qt6
static const QRegularExpression rx(
    QRegularExpression::anchoredPattern(QStringLiteral("\\d+")));
const bool ok = rx.match(text).hasMatch();

anchoredPattern 这一步最容易漏。漏了它，\d+ 会匹配 abc123def，测试用例能过，线上数据会翻车。

编码：QTextCodec 到 QStringConverter #

QTextCodec 进了 Core5Compat，正统替代是 QStringConverter、QStringEncoder、QStringDecoder 三件套。

cpp
// Qt5
QTextStream out(&file);
out.setCodec("UTF-8");
out << 233 << endl;

// Qt6
QTextStream out(&file);
out.setEncoding(QStringConverter::Utf8);
out << 233 << Qt::endl;

QStringConverter 覆盖的是 UTF-8、UTF-16、UTF-32、Latin-1 和 System 这几种。GB18030 这类中文编码不在范围内，要么挂 ICU，要么接第三方库。Qt5 里 QSettings::setIniCodec() 这个接口在 Qt6 直接移除，INI 文件固定按 UTF-8 处理。

字符串与流 #

几个天天碰的点：

Qt5 Qt6
QString::SkipEmptyParts Qt::SkipEmptyParts
QString::KeepEmptyParts Qt::KeepEmptyParts
endl / flush Qt::endl / Qt::flush
QLatin1String QLatin1StringView（QLatin1String 仍是别名）
.arg(a).arg(b).arg(c) .arg(a, b, c)

多参数的 .arg() 就是所谓的 multiArgs 写法：一串 .arg() 连写的旧习惯已经废弃，QLatin1String 和 QStringView 也支持一次传多个参数。

cpp
const QString path = QStringLiteral("%1/%2.%3").arg(dir, name, ext);
const QStringList parts = text.split(QLatin1Char(','), Qt::SkipEmptyParts);

桌面与系统信息 #

QDesktopWidget 在 Qt6 彻底没了，取屏幕尺寸改用 QScreen：

cpp
const QRect total = screen()->geometry();          // 总尺寸
const QRect usable = screen()->availableGeometry(); // 去掉任务栏

QWidget::screen() 和 QWindow::screen() 都返回 QScreen *，除这两个类之外没有别的类提供这个函数。取 Qt 自身路径的 QLibraryInfo::location() 也换成了 QLibraryInfo::path()。

随机数与时间 #

qrand() / qsrand() 在 Qt6 移除，全部走 QRandomGenerator：

cpp
const quint32 v32 = QRandomGenerator::global()->generate();
const quint64 v64 = QRandomGenerator::global()->generate64();
const int v = QRandomGenerator::global()->bounded(10);      // 0..9
const int r = QRandomGenerator::global()->bounded(5, 10);   // 5..9

QDateTime 的 toTime_t() 换成 toSecsSinceEpoch()。那套写法本身就是新版的：fromString 配格式串、toMSecsSinceEpoch 来回转、fromSecsSinceEpoch 拼回字符串，在 Qt6 里一行不改。

QDataStream 的版本兼容 #

这条在迁移里特别容易翻车。QDataStream 每升级一次大版本就换一次线格式，旧文件读不出来不是 bug，是版本没设。

cpp
QFile file(QStringLiteral("my_doc.abc"));
file.open(QFile::ReadOnly);
QDataStream in(&file);

quint32 magic = 0;
in >> magic;
if (magic != 0xA0B0C0D0) {
    return BadFileFormat;
}

qint32 version = 0;
in >> version;
if (version <= 110) {
    in.setVersion(QDataStream::Qt_5_7);   // 老文件用老版本读
} else {
    in.setVersion(QDataStream::Qt_5_15);  // Qt6 里依然认 Qt_5_15
}
in >> lots_of_interesting_data;

写新文件时用 QDataStream::Qt_6_0。读旧文件时显式设回 Qt_5_15，序列化结果才和 Qt5 写出来的一致。这个「文件头存版本号、读时按版本设 QDataStream 版本」的模式，是迁移期间保住老数据的唯一办法。

自定义类型要支持 QDataStream，就重载 << 和 >>，并且用 QT_NO_DATASTREAM 包起来，否则在裁掉数据流的 Qt 上编不过。

cpp
#ifndef QT_NO_DATASTREAM
QDataStream &operator<<(QDataStream &ds, const MyType &t)
{
    ds << t.m_int << t.m_bool;
    return ds;
}
#endif

对象系统与事件 #

这块 Qt6 没怎么动，但有两处要改习惯。

inherits("QWidget") 判类型能跑，但慢。要判控件还是窗口，用 isWidgetType() 和 isWindowType()，语义等价，速度快得多。要在 QObject 派生类之间强转，用 qobject_cast，它不需要开 RTTI；dynamic_cast 那条路在关掉 RTTI 的构建里直接编不过。

事件类型还是一张长表，写 eventFilter 时按需查：

事件 含义
ApplicationFontChange 程序默认字体变了
ApplicationStateChange 程序激活或失活
Clipboard 剪贴板内容变了
LanguageChange 翻译换了，该重刷界面文字
LocaleChange 系统区域变了
WindowStateChange 最大化、最小化、全屏、还原
HoverEnter / HoverLeave / HoverMove hover 事件，要先 setAttribute(Qt::WA_Hover)
DragEnter / DragMove / DragLeave / Drop 拖放全过程

鼠标跟踪那条坑在 Qt6 里同样存在：开了 setMouseTracking(true)，指针移到子控件上时父控件的 MouseMove 就收不到了，必须靠 HoverMove，而 HoverMove 要先开 Qt::WA_Hover。

六、Widgets 的变化 #

Widgets 在 Qt6 里没被砍，桌面项目可以继续用。但 API 层动了不少，尤其是「和系统、和 DPI、和屏幕打交道」的那一圈。

高 DPI 从开关变成默认 #

Qt5 里要手动打开缩放，Qt6 默认开启，那两行设置直接删掉。

cpp
// Qt5：必须在构造 Q(Core|Gui)Application 之前执行，否则不生效
QCoreApplication::setAttribute(Qt::AA_EnableHighDpiScaling);
QCoreApplication::setAttribute(Qt::AA_UseHighDpiPixmaps);

// Qt6：删掉上面两行，写不写都不影响

QT_ENABLE_HIGHDPI_SCALING 这个环境变量（Qt 5.14 引入）在 Qt6 里失去意义。留着 AA_EnableHighDpiScaling 不报错，但它已经是个空操作，别指望它还能关掉缩放。

事件坐标与文字度量 #

鼠标、滚轮事件的取点接口换了名字，pos() 系列在 Qt6 被 position() 顶掉。

cpp
// Qt5
void MyWidget::wheelEvent(QWheelEvent *e) {
    const QPoint p = e->pos();
}

// Qt6
void MyWidget::wheelEvent(QWheelEvent *e) {
    const QPoint p = e->position().toPoint();
}

文字宽度也一样，QFontMetrics::width() 换成 horizontalAdvance()。老的 width() 是按字体的平均宽度估算，horizontalAdvance() 才算真实推进宽度，换过去之后界面上的文字排版会变准，也会变样——原来刚好放得下的标签，现在往往差几个像素。

cpp
// Qt5
const int w = fontMetrics().width(text);
// Qt6
const int w = fontMetrics().horizontalAdvance(text);

样式、图标与系统尺寸 #

QStyle::standardIcon 和 QStyle::pixelMetric 在 Qt6 里原样可用，这两个函数是被低估的那一类：标准图标枚举里躺着最小化、最大化、关闭这些形状，不用去第三方站点找素材。

cpp
QStyleOption option;
option.initFrom(this);
const QIcon icon = style()->standardIcon(
    QStyle::StandardPixmap::SP_TitleBarMinButton, &option);
const int titleBarHeight = style()->pixelMetric(
    QStyle::PixelMetric::PM_TitleBarHeight, &option);

第二参数那个 QStyleOption 指针不能省。传了它，QStyle 内部会按系统 DPI 做尺寸换算；不传，返回的是无视 DPI 的固定值，在高分屏上就是一个错位的图标。取标题栏高度同理，PM_TitleBarHeight 只是 PixelMetric 枚举里的一个，这个枚举里还有一批系统标准控件的尺寸。

继承 QWidget 之后样式表不生效，是另一个老问题。三个解法按代价从小到大排：设 setAttribute(Qt::WA_StyledBackground, true)；改成继承 QFrame（它自带的 paintEvent 会解析并绘制样式表）；自己重写 paintEvent，用 QStylePainter 画。

cpp
void MyClass::paintEvent(QPaintEvent *) {
    QStyleOption o;
    o.initFrom(this);
    QPainter p(this);
    style()->drawPrimitive(QStyle::PE_Widget, &o, &p, this);
}

带 viewport 的控件要额外注意：QTextEdit、QTableWidget、QScrollArea 这些，直接对控件本身设样式常常没反应，得对 viewport() 设。

cpp
scrollArea->viewport()->setStyleSheet(QStringLiteral("background-color:transparent;"));

尺寸策略与布局 #

QSizePolicy 这张表值得背下来，布局调不好十次有八次是它。

值 说明
QSizePolicy::Fixed 默认尺寸固定（取自 sizeHint()），既不能缩小也不能放大
QSizePolicy::Minimum 默认尺寸是最小尺寸，只能放大
QSizePolicy::Maximum 默认尺寸是最大尺寸，只能缩小
QSizePolicy::Preferred 默认尺寸最合适，可放大也可缩小（多数 QWidget 的默认值）
QSizePolicy::Expanding 尺寸合适，且尽量占满剩余空间
QSizePolicy::MinimumExpanding 最小尺寸起步，可放大，且尽量占满剩余空间
QSizePolicy::Ignored 默认尺寸被忽略，直接填满剩余空间

默认最小尺寸从哪来？重写 sizeHint() 和 minimumSizeHint() 这两个虚函数。

设置固定尺寸用 setFixedSize，它的实现就是把最小尺寸和最大尺寸设成同一个值。要还原，先 setMinimumSize(QSize(0, 0))，再 setMaximumSize(QSize(65535, 65535))。窗口固定之后鼠标移到边框上还会变成 resize 形状，想让光标也不变，Windows 上可以用 Qt::MSWindowsFixedSizeDialogHint，或者拦 WM_NCHITTEST 自己处理。

布局的两个常见错位：

  • 给 QWidget 调 setContentsMargins() 没用，要对它的布局调 QLayout::setContentsMargins()。外层布局的设置会递归传到所有内层布局。
  • 代码里改了控件尺寸、增删了控件，布局不跟着变，调一次 QLayout::invalidate() 强制刷新。
  • 想让父控件跟着所有子控件自适应，把子控件都放进布局，再对布局调 setSizeConstraint(QLayout::SetFixedSize)。这时父控件尺寸由子控件决定，要改最小尺寸得去改子控件的 minimumSize，改父控件没用。

表格控件 #

Qt 5.10 之后，QTableWidget 和 QTableView 的最小列宽默认值从 0 改成了 15。设一个小于 15 的列宽不会生效，得先放开下限：

cpp
ui->tableView->horizontalHeader()->setMinimumSectionSize(0);

一张表要顺手，几行设置省不掉：

cpp
tableView->horizontalHeader()->setStretchLastSection(true);
tableView->horizontalHeader()->setMinimumSectionSize(0);
tableView->verticalHeader()->setDefaultSectionSize(rowHeight);
tableView->setSelectionBehavior(QAbstractItemView::SelectRows);
tableView->setSelectionMode(QAbstractItemView::SingleSelection);
tableView->setEditTriggers(QAbstractItemView::NoEditTriggers);

要自定义列里的按钮、复选框、下拉框，走自定义委托 QItemDelegate。想禁用某一列，让重载的 createEditor 返回 0。委托里的控件只在进入编辑态时出现，要它一直显示，得重写 paint，用 drawPrimitive 或 drawControl 自己画。

组合框、快捷键与托盘 #

QComboBox 默认会按最长的 item 撑宽度，长文本能把整个窗口顶变形。治它的办法是 setSizeAdjustPolicy(QComboBox::AdjustToMinimumContentsLengthWithIcon)，超长部分自动省略。要给 item 挂数据，addItem(text, userData) 的第二个参数就是，取的时候用 itemData(index, role)。

QDockWidget 想自定义标题栏，别去折腾 WM_NCCALCSIZE 和 Qt::FramelessWindowHint，官方有现成的 setTitleBarWidget()。

托盘用 QSystemTrayIcon，setContextMenu() 的形参类型是 QMenu *，但 QMenu 本来就是 QWidget 的派生类，把一个普通 QWidget 传进去也能用——这条技巧绕开了 QMenu 的限制。

无边框窗口与系统消息 #

无边框是 Widgets 里坑最集中的一块。

保留系统边框特性又要去掉标题栏，用 setWindowFlags(Qt::Window | Qt::CustomizeWindowHint)。这里要盯住一点：必须用 setWindowFlags 而不是 setWindowFlag：CustomizeWindowHint 和其他 flag 冲突，用前者能顺手清掉其他 flag。QWindow 上没有 setWindowFlag(s)，对应的是 setFlag(s)。Windows 上这么做的窗口顶端会留一条几像素宽的白条，这条白条和系统边框是一体的，去不掉。

用了 Qt::FramelessWindowHint 之后收不到 DPI 改变消息，因为 Qt 内部是靠去掉 WS_THICKFRAME 加 WS_POPUP 来隐藏边框的，Windows 不给这类窗口发 DPI 消息。两个绕法：应用 flag 之后手动修复窗口样式，拦 WM_NCCALCSIZE 自己隐藏边框；或者单独开一个隐藏窗口监听 DPI 消息，收到后手动调尺寸和字体。

QWidget 调了 winId() 之后收不到 WM_NCHITTEST，原因是 QWidget 默认不是原生窗口，一旦调 winId()，Qt 会给它造一个原生父窗口，消息全被父窗口截走。

cpp
QApplication::setAttribute(Qt::AA_DontCreateNativeWidgetSiblings);
QApplication::setAttribute(Qt::AA_NativeWindows, false);
setAttribute(Qt::WA_DontCreateNativeAncestors);
setAttribute(Qt::WA_NativeWindow);

platformthemes\ 不报错，但界面退回 Win2000 风格

七、Qt Quick 与 QML 的变化 #

Qt Quick 在 Qt6 里换了引擎底座，写法上也顺手清了一批历史包袱。纯 QML 项目迁起来比 Widgets 项目轻松，前提是别踩版本导入和模块这两块。

导入不写版本号了 #

Qt6 的 QML 支持无版本导入，Qt5 时代满屏的 import QtQuick 2.15 可以简化成 import QtQuick。

text
// Qt5
import QtQuick 2.15
import QtQuick.Controls 2.15
import QtQuick.Layouts 1.15

// Qt6
import QtQuick
import QtQuick.Controls
import QtQuick.Layouts

Qt6 里也认带写法的老版本号，但一旦写了不存在的版本（比如 QtQuick 2.15 配一个只到 2.15 的 Qt6），引擎会拒绝加载。统一去掉版本号，省一堆这类问题。

required property 与内联组件 #

Qt6 给 QML 加了 required property，声明的属性必须由使用者赋值，不赋值就是运行时错误。这比「默认值兜底」可靠得多。

text
Rectangle {
    required property var cornersRadius
    required property color color
    property color borderColor: "transparent"
    property real borderWidth: 1
}

内联组件也进了语言：component TitleBar: Item { ... }，一个小文件里定义多个组件不再需要拆文件。

QML 模块化：qt_add_qml_module #

Qt5 里给 QML 插件写 qmldir、跑 qmlplugindump 生成 plugins.qmltypes、再在 .pro 里写 CONFIG += qmltypes，一套流程下来手忙脚乱。Qt6 用一条 CMake 命令收掉。

cmake
qt_add_qml_module(myapp
    URI MyApp
    VERSION 1.0
    QML_FILES
        Main.qml
        Constants.qml
    SOURCES
        mytype.cpp mytype.h
)

qmldir、类型注册、plugins.qmltypes、资源打包，全在这一步里生成。C++ 侧要暴露类型给 QML，用 QML_ELEMENT 宏加 QML_NAMED_ELEMENT，不再手写 qmlRegisterType。

老办法仍然可用，接手老项目时会看到：用 qmlplugindump 生成 plugins.qmltypes，放在和库文件同级的目录，并在 qmldir 里写一行 typeinfo plugins.qmltypes。Qt 5.15 提供了更省事的方式，.pro 里写 CONFIG += qmltypes，但仅限 QMake，CMake 的支持要等 Qt6——现在等到了。

把 .qml 编进库而不是散在外面，做法是两步：把 qml 文件塞进 qrc，然后在 C++ 里按 URL 注册。

cpp
qmlRegisterType(QUrl(QStringLiteral("qrc:/MySlider.qml")),
                "com.mycompany.myqmlcomponents", 1, 0, "Slider");

QML 单例：三步走 #

单例在 Qt5 和 Qt6 里的登记方式不同，按版本对一遍。

第一步，QML 文件开头加指令，这一步两个版本都不能少：

text
pragma Singleton

大小写敏感，多个 pragma 要分行写。

第二步，Qt6 用 CMake 打标记：

cmake
set_source_files_properties(Constants.qml PROPERTIES QT_QML_SINGLETON_TYPE TRUE)

这个标记是 Qt6 引入的，Qt5 里写了也没人读。

第三步，Qt5 靠代码注册，这一步在 Qt5 里不可缺少：

cpp
qmlRegisterSingletonType(QUrl(QStringLiteral("qrc:///qml/Constants.qml")),
                         "Demo", 1, 0, "Constants");

Qt6 里如果做了第二步，第三步可以省；多做一次也不会报错。

一段能跑的 QML：任意圆角矩形 #

Rectangle 只支持四个角同样的圆角。要四个角分别设置，得用 QtQuick.Shapes 画路径。

text
import QtQuick
import QtQuick.Shapes

Shape {
    id: shape

    required property var cornersRadius
    required property color color
    property color borderColor: "transparent"
    property real borderWidth: 1

    layer {
        enabled: true
        samples: 4
        smooth: true
        mipmap: true
    }

    ShapePath {
        startX: 0
        startY: shape.cornersRadius[0]
        fillColor: shape.color
        strokeColor: shape.borderColor
        strokeWidth: shape.borderWidth
        PathQuad { x: shape.cornersRadius[0]; y: 0; controlX: 0; controlY: 0 }
        PathLine { x: shape.width - shape.cornersRadius[1]; y: 0 }
        PathQuad { x: shape.width; y: shape.cornersRadius[1]; controlX: shape.width; controlY: 0 }
        PathLine { x: shape.width; y: shape.height - shape.cornersRadius[2] }
        PathQuad { x: shape.width - shape.cornersRadius[2]; y: shape.height; controlX: shape.width; controlY: shape.height }
        PathLine { x: shape.cornersRadius[3]; y: shape.height }
        PathQuad { x: 0; y: shape.height - shape.cornersRadius[3]; controlX: 0; controlY: shape.height }
        PathLine { x: 0; y: shape.cornersRadius[0] }
    }
}

用法就是传四个角的半径，顺序是左上、右上、右下、左下：

text
RoundedRectangle {
    width: 160
    height: 160
    color: "cyan"
    cornersRadius: [20, 0, 20, 0]
    borderWidth: 1
    borderColor: "gray"
}

layer.samples: 4 那几行是抗锯齿，去掉之后圆角边缘会有毛刺。

C++ 与 QML 互调 #

从 C++ 调 QML 里的函数或信号，还是 QMetaObject::invokeMethod。有条坑得记住：带参数时，不管参数原本是什么类型，一律用 QVariant 包，否则调不通。这不是 bug，是文档里明写的约定。

cpp
QMetaObject::invokeMethod(rootObject, "methodName",
                          Q_ARG(QVariant, param1),
                          Q_ARG(QVariant, param2));

反方向取窗口指针：用 QQmlApplicationEngine 加载时，根对象就是窗口。

cpp
QQmlApplicationEngine engine;
engine.load(QUrl(QStringLiteral("qrc:///qml/main.qml")));
auto *window = qobject_cast<QWindow *>(engine.rootObjects().at(0));

用 QQuickView 时不用这一句，它本身就是 QWindow 的派生类，直接操作自己就行。

八、图形栈的变化：从 OpenGL 到 RHI #

这是 Qt6 第二个「决定工作量」的变化。Qt5 的 Qt Quick 场景图直接跑在 OpenGL 上，Windows 上靠 ANGLE 把 GL 调用翻译成 Direct3D；Qt6 在中间插了一层 RHI（Rendering Hardware Interface），渲染后端变成可替换的。

后端 平台默认 强制方式
Direct3D 11 Windows QSG_RHI_BACKEND=d3d11
Metal macOS QSG_RHI_BACKEND=metal
Vulkan 需要手动指定 QSG_RHI_BACKEND=vulkan
OpenGL Linux QSG_RHI_BACKEND=opengl
software 无 GPU 时兜底 QSG_RHI_BACKEND=software

代码里指定后端，必须在窗口创建之前：

cpp
QQuickWindow::setGraphicsApi(QSGRendererInterface::Direct3D11);

环境变量是调试时更省事的办法。QSG_INFO=1 会让 Qt 在启动时把最终选中的后端、驱动、扩展一股脑打到控制台，排查「为什么这个机器渲染花屏」时，第一步就看这个。

ANGLE 没了，一串老办法失效 #

Qt5 在 Windows 上依赖 ANGLE，配套一堆开关：

cpp
// Qt5 的三选一，必须在 Q(Core|Gui)Application 构造前调用
QCoreApplication::setAttribute(Qt::AA_UseDesktopOpenGL);  // 桌面 OpenGL
QCoreApplication::setAttribute(Qt::AA_UseOpenGLES);       // 走 ANGLE
QCoreApplication::setAttribute(Qt::AA_UseSoftwareOpenGL); // Mesa llvmpipe

// 等价的环境变量写法
// QT_OPENGL=desktop / angle / software
// QT_ANGLE_PLATFORM=d3d11 / d3d9 / warp（仅 ANGLE 生效，大小写敏感）

Qt6 移除 ANGLE，QT_OPENGL=angle 和 QT_ANGLE_PLATFORM 一起作废。上面三个 AA_* 属性对 Qt Quick 也不再生效，因为 Qt Quick 走的是 RHI，不看这套属性——它们只对 QOpenGLWidget 这类直接要 OpenGL 上下文的代码还有意义。

QSurfaceFormat 同理。它在 Qt6 里还在，但只影响 OpenGL 后端，Qt Quick 跑在 D3D11 或 Metal 上时根本不读它。

cpp
QSurfaceFormat format = QSurfaceFormat::defaultFormat();
format.setRenderableType(QSurfaceFormat::OpenGL);
format.setVersion(4, 6);                       // 不设的话默认 2.0，很老
format.setProfile(QSurfaceFormat::CoreProfile); // 禁用废弃 API
QSurfaceFormat::setDefaultFormat(format);

这段必须在第一次创建 OpenGL 上下文之前执行。走 OpenGL ES 时版本最高别超过 3.2，超了初始化不起来。

发布包里少了一对 DLL #

Qt5 发布 Windows 程序时，libEGL.dll 和 libGLESv2.dll 是 ANGLE 的两个文件，windeployqt 有 --no-angle 专门用来跳过它们。Qt6 不再有这两个文件。opengl32sw.dll 是 Mesa 的软件模拟显卡，只有没有显卡的机器才需要，Qt5 时代就不建议随包发布——能明显减小体积。Qt6 里这条建议不变，RHI 的 software 后端不依赖这个 DLL。

迁移影响清单 #

按「碰没碰图形 API」自查：

QOpenGLWidget 模块搬家 链接 Qt6::OpenGLWidgets

九、容器与语言特性的变化 #

Qt6 把容器层做了一次合并，顺手把 C++17 的写法引进来。

Qt5 Qt6
QVector<T> QList<T> 的别名，两个名字同一个类型
QList<T>（指针数组实现） 连续内存，等价于 std::vector
QList::toVector() / QVector::toList() 移除，同一个类型没什么可转
QLinkedList 移除，用 std::list
QMap::insertMulti() QMultiMap
QHash::insertMulti() QMultiHash
QSet::toList() 用迭代器构造或 values()

QVector 变成别名这一条，看着温和，实际影响面很大：所有 QList::toVector()、QVector::toList() 的调用点全部编不过，而这类调用在 Qt5 代码里到处都是。

自定义类型进容器，规则没变，但报错信息更难读：

cpp
struct MyType {
    int m_data = 0;
    friend bool operator==(const MyType &a, const MyType &b) noexcept {
        return a.m_data == b.m_data;
    }
    friend bool operator!=(const MyType &a, const MyType &b) noexcept {
        return !(a == b);
    }
};
QList<MyType> list;   // 需要 == 和 !=

要当 QHash 的键，再加一个名字固定为 qHash 的函数，参数带 seed：

cpp
friend std::size_t qHash(const MyType &t, std::size_t seed = 0) {
    return qHashMulti(seed, t.m_int, t.m_bool, t.m_str);
}

qHashMulti 是 Qt6 里拼哈希的标准做法，别自己写异或。也可以特化 std::hash，这样 Qt 和标准库共用一份声明；两个都有时 Qt 优先用 qHash。

自定义的 flag 类型不支持位运算，是因为少了一行宏，且这行宏必须写在命名空间外：

cpp
Q_DECLARE_OPERATORS_FOR_FLAGS(MyClass::MyFlag)

语言特性带来的写法变化 #

旧写法 新写法
qAsConst(container) std::as_const(container)
Q_FOREACH (x, list) for (const auto &x : list)
QString::fromLatin1 到处用 传 QStringView 或 QLatin1StringView 减少拷贝
手写守卫类做清理 qScopeGuard

Q_FOREACH 在 Qt6 里还在，但已被视为废弃。迁 CMake 的时候定义 QT_NO_FOREACH，编译器会把每一处用它的地方都报出来，一次性换干净。

QScopeGuard 值得单独说一句：它在当前代码块结束前执行指定的清理代码，不支持抛异常。

cpp
void myFunction(int v) {
    auto cleanup = qScopeGuard([]() { /* 离开作用域时执行 */ });
    if (v == -1) {
        return;   // 提前返回也会执行 cleanup
    }
}

还有个容易忽略的构建选项：configure -qtnamespace <ns> 能把所有 Qt 符号塞进一个自定义命名空间。这种 Qt 上前置声明 Qt 类必须用宏包起来，否则编不过。

cpp
QT_BEGIN_NAMESPACE
class QWindow;
class QWidget;
QT_END_NAMESPACE

真正折磨人的不是这张表。表里的东西编不过，编不过就有报错，有报错就能改。麻烦的是「能编过但行为变了」的那批：

  • QHash 的迭代顺序。Qt6 换了哈希实现，顺序和 Qt5 不同，而且同一个程序每次启动都不一样。任何依赖「遍历顺序稳定」的代码都会挂，这类 bug 只在运行时暴露。
  • QString::split 对空串的处理。Qt6 的行为和 Qt5 有细微差别，KeepEmptyParts 是默认值，迁移时要把每一处显式参数补上。

十一、迁移的实际步骤 #

顺序错了会白干。下面这套是按「先把地基换掉、再动上层」排的。

步骤 做什么 完成标志
1 冻结 Qt5 分支，拉 release 分支打 tag 随时能出一个 Qt5 版本救火
2 定 Qt6 版本，选 LTS 写进 find_package(Qt6 6.5 REQUIRED ...)
3 在原 Qt5 上把 .pro 换成 CMake 同一份二进制，还是用 Qt5 编，但走 CMake
4 把 find_package 切到 Qt6 零编译错误
5 处理模块搬家 不再报未定义符号
6 按第十章清单逐条清 API 没有 deprecated 警告
7 按第八章自查图形栈 目标机器上渲染正常
8 QML 模块化、部署、回归 干净机器上双击能跑

第 3 步最容易被人跳过。它的价值在于：qmake 换 CMake 出错和 Qt5 换 Qt6 出错，是两类完全不同的错误。先在 Qt5 上把 CMake 跑通，第 4 步之后报的错就只剩 Qt6 相关的，排查范围砍掉一半。

第 5、6 步的次序也别倒。模块搬家会带来一批「未定义符号」，清 API 会带来一批「已废弃」。混在一起改，你分不清哪个错是哪个原因引起的。

Linux 上官方没提供类似工具，第三方有 linuxdeployqt（https://github.com/probonopd/linuxdeployqt）。把依赖库收齐之后，要在 bin 同级放一份 qt.conf：

text
[Paths]
Prefix=..
Libraries=lib
Plugins=plugins
Imports=qml
Translations=translations
Qml2Imports=qml

再放一个启动脚本，名字和二进制一致（后缀 .sh），靠它设环境变量：

bash
#!/bin/bash
BASE_DIR=$(dirname "$(readlink -f "$0")")
export LD_LIBRARY_PATH="$BASE_DIR"/lib/:"$BASE_DIR":$LD_LIBRARY_PATH
export QML_IMPORT_PATH="$BASE_DIR"/qml/:$QML_IMPORT_PATH

export QTWEBENGINEPROCESS_PATH="$BASE_DIR"/bin/QtWebEngineProcess
export QT_QPA_PLATFORM_PLUGIN_PATH="$BASE_DIR"/plugins/platforms:$QT_QPA_PLATFORM_PLUGIN_PATH
"$BASE_DIR/bin/myapp" "$@"

直接跑二进制不行，必须走脚本，否则找不到库和插件。

QML 插件要静态加载（只是能静态编译不够），Qt5 靠一段 qmake 配置：CONFIG += relative_qt_rpath、QMAKE_MOC_OPTIONS += -Muri=$$uri、静态版还要 CONFIG += builtin_resources 把 qmldir 和所有 .qml 打进资源，前缀是 /qt-project.org/imports/插件URI（点换成斜杠）。Qt6 里这一整套由 qt_add_qml_module 接管，不用手写。

十三、迁移中常见的坑 #

按出现的先后顺序排，前面的会更早撞上。

编码与资源 #

界面文字乱码，三件事一起做：所有源码文件转成 UTF-8（最好不带 BOM）；源码里不要直接写非英文半角字符，要写就用 tr() 包起来，QML 里用 qsTr()，确实不需要翻译的用 QStringLiteral；编译器打开 UTF-8 支持。

大资源文件默认编不过，Qt5 要给 CONFIG += resources_big，CMake 侧用 qt_add_big_resources。原理是处理大文件时 rcc 直接生成 .obj，跳过编译阶段只参与链接。Qt6 里函数名去掉 5：

cmake
qt_add_big_resources(myapp big.qrc)

库项目用 qrc 里的资源，必须调 Q_INIT_RESOURCE(文件名)（不带后缀）。静态库缺这一步会找不到资源，且不给任何报错。这个宏不能在命名空间内使用，否则编译通过、运行必崩。绕法是命名空间外定义一个函数调用它，命名空间内调那个函数。

路径与目录 #

QFile 不能在并不存在的目录里建文件。路径不存在就先 QDir().mkpath(dirPath)，它会把中间缺失的层级一并创建。

程序自启之后工作目录会变成系统目录，代码里读写相对路径会错位。尽早执行 QDir::setCurrent(QCoreApplication::applicationDirPath())，别放在靠后的位置。

取程序目录本身也有隐患：applicationDirPath() 和 QDir::currentPath() 都受工作目录影响，且前者在 QCoreApplication 实例化之前不能调。要稳，就用平台原生 API 拿绝对路径再截掉文件名，Windows 上是 GetModuleFileNameW，Linux 上读 /proc/self/exe，macOS 是 _NSGetExecutablePath。

解析路径时优先用 QFileInfo::canonicalFilePath()，它会把 .、.. 和快捷方式、软链接都解析掉；absoluteFilePath() 和 filePath() 不会。反过来，QDir::canonicalPath() 在目录不存在时直接返回空串，要的是「只规整字符串不管存在性」就用 QDir::cleanPath()。

对象生命周期 #

删 Qt 对象用 deleteLater()，别直接 delete。前者挑合适的时机释放，后者立即释放，在事件循环里很容易崩。批量删容器里的对象用 qDeleteAll()，它只对元素调 delete，不删容器本身，完事要自己 clear()。

类的成员里有 QScopedPointer 或 std::unique_ptr，析构函数就不能内联，写成 ~MyClass() override = default; 会编不过。这是个和编译器相关的老规矩，Qt6 里仍然成立。

QObject 是个重类，实例化慢、占内存。不碰元对象系统就别继承它，写 Qt 程序不等于什么都要派生自 QObject。

界面细节 #

控件构造期取不到准确尺寸。QWidget 在被显示出来之前不具备真实的几何信息，构造函数里读到的数字不可信，要读就等 showEvent。同理，构造函数里 windowHandle() 一定返回空指针，需要窗口句柄的活（比如设 DWM 属性）也挪到 showEvent 里做。

QDialog 默认阻塞整个应用。不想阻塞就设 setWindowModality(Qt::WindowModal) 再 exec()。

QPushButton 只显示图标不显示文字，三行不能少：

cpp
button->setIcon(QIcon(QStringLiteral(":/Icons/open.svg")));
button->setIconSize(QSize(32, 32));      // 不设会显示得极小
button->setFixedSize(button->iconSize()); // 不设大小会对不上
button->setFlat(true);                    // 去掉默认背景面板

QLCDNumber 要设样式表，得先把 segmentStyle 改成 flat。控件获取焦点后的虚边框，用 setStyleSheet("*{outline:0px;}") 去掉。

线程与 IO #

串口和网络收发默认就是异步的，操作系统自己调度，不卡界面。真正耗时的从来是运算和运算后的处理。数据量小的项目别动不动开线程，线程调度本身有开销。

数据库操作留在主线程，非要放子线程就在哪个线程用就在哪个线程开库，别在主线程开、子线程用。

QFile 不要频繁开关。每 5 毫秒写一次日志、每次都 open/close，IO 会被拖死。开着文件，等到析构或者跨天换文件时再关。
