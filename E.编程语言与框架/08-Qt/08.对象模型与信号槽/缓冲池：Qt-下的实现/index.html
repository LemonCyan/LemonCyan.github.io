这篇只讲一件事：生产数据的一方和消费数据的一方速度对不上时，中间那层内存队列该怎么设计。讲缓冲池本身——容量怎么定、满了怎么办、Qt 里用哪几个类落地。信号槽的连接语义、事件循环的派发顺序、QObject 的对象树归属，放在同目录另外几篇里，这里不重复。读完你得能回答三个问题：队列要不要加、加多深、满了之后选等还是选丢。

一、缓冲池解决什么问题 #

速度对不上是常态。磁盘顺序写几十 MB/s，网卡能在一毫秒内顶进来几万个包，UI 线程每 16 毫秒才愿意醒一次。把任意两端直接对接，快的那头必然在等慢的那头：CPU 空转，线程被挂起，或者数据被反压回去。

缓冲池就是中间插一段循环复用的内存。

text
生产端 ──写入──▶ [ 缓冲区数组 ] ──读出──▶ 消费端
                      ▲
               读写指针 + 计数器

四个核心组成 #

组件 职责
缓冲区 实际存储数据的内存区域，数据在传输过程中暂存于此
读指针 指示缓冲区中当前可读取数据的具体位置
写指针 指向缓冲区中能够写入新数据的位置
计数器 记录剩余可读数据量，以及还可写入的空闲空间大小

四个组件里只有两个是状态：指针和计数。指针管位置，计数管判断——能不能读看可读计数，能不能写看空闲计数。别拿指针相等去判断空和满，环形缓冲里 read == write 既代表空也代表满，这是经典歧义，用计数或者留一个空槽位来解决。

数据流转三阶段 #

text
阶段一 写入：数据进缓冲区，写指针后移，空闲计数 -1，可读计数 +1
阶段二 读取：目标端取数据，读指针后移，可读计数 -1，空闲计数 +1
阶段三 环绕：指针到末尾回到起点，取模算下标，不搬内存

阶段一，源设备向目标设备传输数据，数据首先进入缓冲区。此时写指针指向可写入的位置，计数器记录剩余空闲空间大小。

阶段二，目标设备从缓冲区取数据，读指针指向可读取数据的位置，计数器同时记录还有多少可读数据。读取完成后计数器减少相应数量，读指针移动到下一个可读数据位置。

阶段三，源设备传输结束后若池中仍有未被读取的数据，把读指针重置到缓冲区起始位置，池子继续接收新数据，实现循环利用，保证数据传输的连贯性。重置不是必须清空——循环利用的前提是读写指针追尾，追尾就说明旧内容已被消费完。

本质是用空间换取速率解耦 #

中间这段内存的价值不在「存」，在「隔开」。两个原本必须同步的节奏被拆成两个独立的节奏：生产方按自己的速度写，消费方按自己的速度读，两边只在队列满和队列空这两个瞬间才发生关系。

text
无缓冲：生产 10ms/次 ──阻塞等待──▶ 消费 30ms/次    总耗时 30N
有缓冲：生产 10ms/次 ─▶ [队列] ─▶ 消费 30ms/次    总耗时 30N
                 ▲ 但生产方在这段时间里可以做别的事

两行的总耗时一样。缓冲不会让慢的一方变快，它改变的是「谁在等」。加缓冲之前生产方被消费方卡住；加缓冲之后，生产方在自己的队列满之前都不被卡住。省下来的不是时间，是阻塞。

代价 #

收益 代价
生产方不再被消费方直接阻塞 内存占用 = 深度 × 单条大小
吸收瞬时突发流量 延迟增加 = 深度 ÷ 消费速率
两端独立调度、独立重试 多一份共享状态，需要同步
消费端可批量处理，摊薄单条成本 积压时故障暴露被推迟

延迟那条要算清楚。队列堆了 1000 条、消费速率 100 条/秒，放进去的第一条要等 10 秒才被处理。对音频、控制指令、鼠标事件这类实时链路，这个数字就是短板。深度不是越大越好，它是在抗突发和低延迟之间取的一个点。

二、生产者与消费者的速率差 #

缓冲池存在的唯一理由是速率差。速率差有两种，处理方式完全不同。

text
趋势性不平衡（平均 120 进 / 100 出）：
  队列长度单调上涨 ──▶ 任何有限队列都会满，缓冲只是推迟崩溃

瞬时波动（平均 100 进 / 100 出，但每秒一次 500 的突发）：
  队列长度锯齿波动 ──▶ 深度够就能完全吸收，缓冲真正有用

这是第一个要认清的事实：缓冲只能吸收波动，不能吸收趋势。平均生产速率大于平均消费速率时，加缓冲只是把 OOM 从第一天推迟到第三天。该做的是让消费端变快、加消费者、或者在源头限流。

队列深度用利特尔法则算：

text
平均队列长度 L = 到达速率 λ × 平均停留时间 W

例：λ = 2000 条/秒，要求 W ≤ 0.5 秒
    L = 2000 × 0.5 = 1000 条

反过来，定了深度 D、消费速率 μ，最坏情况下的排队延迟就是 D/μ。这两个数字必须一起报给需求方，别只报一个。

场景 生产端速率 消费端速率 缓冲要吸收的东西
串口收包 → 协议解析 115200 bps ≈ 11 KB/s 解析快，但会被日志拖慢 解析偶发卡顿
网卡收 UDP → 落盘 瞬时几十万 pps 磁盘几十 MB/s 突发包簇 + 磁盘抖动
采集卡 → UI 绘图 固定 30~60 fps 被重绘拖累 UI 卡帧
生产者线程 → 消费者线程 受调度影响 受调度影响 双方调度抖动

最后一行值得留意：即使两端平均速率完全相同，线程调度抖动也会制造瞬时速率差。生产方抢到时间片连写一万条然后睡 50ms，消费方在这 50ms 里一条都拿不到。缓冲把这种抖动抹平。

快慢还会在运行中翻转：启动阶段消费端要建索引、连数据库，慢，队列涨；稳态阶段消费端批量处理比逐条生产快，队列空。所以池子两头都得能处理——空时消费端要能等而不是空转，满时生产端要能让而不是硬塞。

三、缓冲池的三种策略 #

容量策略就三种。选哪个取决于一个判断：这条数据丢了会不会出事。

策略 满了怎么办 内存 丢数据 谁被卡 适合
无界 继续收 会涨爆 不丢（直到 OOM） 谁都不卡，最后进程死 原型、数据量有天然上限
有界阻塞 生产方等 恒定 不丢 生产方 数据不能丢、能接受反压
有界丢弃 丢最旧的 恒定 会丢 谁都不卡 实时性优先、只关心最新值

无界：最省事，也最容易把进程搞死 #

cpp
class UnboundedQueue {
public:
    void produce(const QByteArray& data) {
        QMutexLocker locker(&mutex);
        queue.enqueue(data);      // 永远成功，永远不阻塞
        cond.wakeOne();
    }
    // 私有成员：QQueue<QByteArray> queue; QMutex mutex; QWaitCondition cond;
};

produce 永不失败，调用方写起来最舒服。消费端一旦停摆（死锁、卡在 IO、被信号量堵住），生产端会一路往里塞，直到内存耗尽被 OOM killer 干掉。进程死得毫无征兆，日志里连个队列长度都没有。

无界只在一个条件下成立：数据总量有天然上限。比如一次导入任务固定一万条，那就没必要设界。

有界阻塞：安全，但生产方会被卡 #

cpp
bool produce(const QByteArray& data, int timeoutMs = -1) {
    QMutexLocker locker(&mutex);
    while (queue.size() >= capacity) {
        if (!cond.wait(&mutex, timeoutMs)) {
            return false;          // 超时，调用方自己决定重试还是放弃
        }
    }
    queue.enqueue(data);
    cond.wakeOne();
    return true;
}

内存恒定，数据一条不丢，代价是把压力传回生产方。生产方是 UI 线程，界面就假死；是网络 IO 线程，收包会停，TCP 窗口收缩，对端超时。

阻塞策略必须配超时。cond.wait(&mutex, timeoutMs) 带的那一个不是可选项，它是从卡死里爬出来的唯一出口。

有界丢弃：实时性优先，丢谁要想清楚 #

cpp
void produce(const QByteArray& data) {
    QMutexLocker locker(&mutex);
    while (queue.size() >= capacity) {
        queue.dequeue();           // 丢最旧的
        ++droppedOld;
    }
    queue.enqueue(data);
    cond.wakeOne();
}

丢最旧适合只看最新状态的场合：视频帧、传感器读数、鼠标移动事件、行情快照。旧的那帧画面已经没人看了，留着只占内存。

丢最新适合序列完整性优先的场合，逻辑上是「超出处理能力的请求直接拒掉」，produce 返回 false 让调用方知道：

cpp
bool produce(const QByteArray& data) {
    QMutexLocker locker(&mutex);
    if (queue.size() >= capacity) {
        ++droppedNew;
        return false;              // 明确拒绝，不装作成功
    }
    queue.enqueue(data);
    return true;
}

两种丢弃都必须计数。丢数据不可怕，丢了不知道丢多少才可怕，dropped() 要进监控面板。

决策点只有一个 #

text
这条数据丢了会出事吗？
├─ 会 ──▶ 能接受生产方被卡吗？
│         ├─ 能  ──▶ 有界阻塞
│         └─ 不能 ──▶ 有界阻塞 + 超时 + 溢出落盘/告警
└─ 不会 ─▶ 消费方只关心最新值吗？
          ├─ 是 ──▶ 有界丢弃（丢最旧）
          └─ 否 ──▶ 有界丢弃（丢最新并返回失败）

「丢了会不会出事」是第一个决定，也是唯一真正的决定。定了它，剩下的容量、超时、水位线都是调参。

四、Qt 里的实现方案 #

Qt 的容器和同步原语够用，不用引第三方库。

类 底层 连续内存 适用
QByteArray 引用计数字节数组 是 字节流、协议包、编解码前的载体
QVector<T> 动态数组 是 定长记录、需要下标随机访问
QQueue<T> 基于 QList 否 逻辑队列，写法最像队列
QRingBuffer 私有类，块链 否 Qt 内部（QIODevice）用，不建议外部依赖
std::deque<T> 分段连续 否 两端 push/pop，不关心 Qt 风格

要真环形缓冲，用 QVector 加两个下标自己算取模。QQueue 不是环形，头部出队不搬数据（它是指针数组），但也拿不到连续的可读区段。

类结构 #

核心成员两个：数据容器 QVector<QByteArray> 存字节数组形式的缓冲区，状态追踪 QVector<bool> 表示每个缓冲区的占用状态。

cpp
class BufferPool : public QObject {
    Q_OBJECT

public:
    explicit BufferPool(int bufferCount, int bufferSize, QObject* parent = nullptr);
    ~BufferPool() = default;

    QByteArray* getAvailableBuffer();
    void releaseBuffer(QByteArray* buffer);

    int bufferCount() const { return buffers.size(); }
    int usedCount() const;

signals:
    void bufferFull(QByteArray* buffer);   // 缓冲区已满，需要处理
    void bufferEmpty();                    // 所有缓冲区已耗尽

private:
    QVector<QByteArray> buffers;
    QVector<bool> bufferUsed;
};

初始化 #

在构造函数里创建指定数量和大小的缓冲区，并初始化使用状态：

cpp
BufferPool::BufferPool(int bufferCount, int bufferSize, QObject* parent)
    : QObject(parent)
{
    buffers.reserve(bufferCount);       // ← 先 reserve，后续 append 不重分配
    bufferUsed.reserve(bufferCount);

    for (int i = 0; i < bufferCount; ++i) {
        QByteArray buffer(bufferSize, 0);   // ← 创建指定大小的缓冲区
        buffers.append(buffer);
        bufferUsed.append(false);           // ← 初始状态为未使用
    }
}

reserve 那一行不是优化，是正确性前提。getAvailableBuffer 返回的是 &buffers[i]，一旦 buffers 扩容重分配，之前发出去的指针全成野指针。构造期一次 reserve 到最终容量，之后不再增删，指针才稳。

获取可用缓冲区 #

遍历状态向量，返回第一个未使用的缓冲区：

cpp
QByteArray* BufferPool::getAvailableBuffer()
{
    for (int i = 0; i < bufferUsed.size(); ++i) {
        if (!bufferUsed[i]) {
            bufferUsed[i] = true;
            return &buffers[i];
        }
    }
    return nullptr;                     // ← 无可用缓冲区时返回空指针
}

返回 nullptr 是契约的一部分，调用方必须判空，否则下一步就是解引用崩溃。

释放缓冲区 #

将缓冲区状态重置为未使用，以便复用：

cpp
void BufferPool::releaseBuffer(QByteArray* buffer)
{
    int index = buffers.indexOf(*buffer);
    if (index != -1) {
        bufferUsed[index] = false;
    }
}

这里用的是值比较，indexOf(*buffer) 会逐字节比较内容。缓冲区越大、池子越深，比较越慢；内容全零的两个缓冲区还会被判成同一个：

text
buffers[3] = {0x00, 0x00, ...}     内容全零
buffers[7] = {0x00, 0x00, ...}     内容也全零
indexOf(*buffers[7]) 返回 3        ← 释放错槽位

用指针对下标就没这个问题：

cpp
int BufferPool::indexOfBuffer(const QByteArray* buffer) const
{
    const qsizetype idx = buffer - buffers.constData();
    if (idx < 0 || idx >= buffers.size()) {
        return -1;
    }
    return static_cast<int>(idx);
}

void BufferPool::releaseBuffer(QByteArray* buffer)
{
    if (!buffer) return;
    const int index = indexOfBuffer(buffer);
    if (index < 0 || !bufferUsed[index]) return;   // 不在池里或重复释放
    bufferUsed[index] = false;
}

指针减法 O(1)，顺带解决了同一个 buffer 释放两次的误判。bufferUsed[index] 那层检查就是防重复释放的护栏。

使用方的合约 #

缓冲区是池子的成员，谁也不能 delete 它：

text
1. getAvailableBuffer() 返回 nullptr → 池子空了，等或者降级
2. 拿到指针 → 用完调 releaseBuffer() → 不 delete、不存进长命结构

第二条比第一条容易踩。把 QByteArray* 塞进全局 map 或者另一个线程的队列，等你想起来释放时那个指针早被复用了，数据被下一轮写入覆盖，读出来是别人家的内容。

三种实现怎么选 #

实现 适用场景 复杂度
基础缓冲池类 单线程数据处理、简单数据缓存 低
信号槽集成 事件驱动架构、GUI 应用数据流 中
多线程安全实现 生产者-消费者模式、网络数据接收 高

五、用 QQueue 实现环形缓冲 #

QQueue 只加了几个方法，底层就是 QList，写起来最省事：enqueue() 入队、dequeue() 出队、head() 看一眼不弹、size() 看深度。超出上限就丢最旧的那条：

cpp
void push(const QByteArray& packet) {
    queue.enqueue(packet);                  // 入队
    while (queue.size() > maxDepth) {
        queue.dequeue();                    // 超深就丢最旧的
        ++dropped;
    }
}

短板是元素在内存里不连续，拿不到「一段连续可读区」。想把队列里攒的十帧直接 write() 给文件描述符，只能一帧一帧拷。

真环形：QVector + 读写下标 #

要连续内存和确定容量，自己写。核心三件事：固定容量、取模、用计数消掉空满歧义。

cpp
template <typename T>
class RingBuffer {
public:
    explicit RingBuffer(int capacity)
        : data(capacity), cap(capacity) {}      // 容量固定，之后永不扩容

    bool push(const T& value) {
        if (count == cap) return false;         // 满了，交给上层决定丢还是等
        data[(head + count) % cap] = value;     // 写位置 = 读位置 + 已存量
        ++count;
        return true;
    }

    bool pop(T& out) {
        if (count == 0) return false;
        out = data[head];
        head = (head + 1) % cap;
        --count;
        return true;
    }

    bool isEmpty() const { return count == 0; }
    bool isFull()  const { return count == cap; }
    int  size()    const { return count; }

private:
    QVector<T> data;
    int cap = 0;
    int head = 0;      // 读位置
    int count = 0;     // 已存数据量 ← 空/满歧义的解药
};

(head + count) % cap 是全部的精髓：不用维护写指针，写位置永远由读位置和存量算出来，少一个需要同步的变量。

空满判断靠 count，不靠 head == tail。经典写法里 head == tail 既表示空也表示满，所以要少用一个槽位或者另加标志位，直接上计数更省事：

text
count == 0        → 空
count == cap      → 满
head              → 下一个要读的下标
(head + count) % cap → 下一个要写的下标

回绕时数据被切成两段 #

写指针绕回起点后，可读数据在物理内存上是两段：

text
cap = 8，head = 5，count = 6

下标:  0    1    2    3    4    5    6    7
内容:  d8   d9   --   --   --   d5   d6   d7
                          ▲         ▲
                       第二段     第一段起点

第一段 [head, cap)  长 3    第二段 [0, head)  长 3

要一次拷出去，得分两次：

cpp
const int firstChunk  = qMin(count, cap - head);
const int secondChunk = count - firstChunk;

dev.write(reinterpret_cast<const char*>(data.constData() + head), firstChunk * sizeof(T));
if (secondChunk > 0) {
    dev.write(reinterpret_cast<const char*>(data.constData()), secondChunk * sizeof(T));
}

写网络包、写文件、喂解码器，凡是需要连续内存的地方都要处理这个切分。忘记第二段的表现是每环绕一次就丢一截数据，而且丢得很有规律。

六、多线程下的缓冲池 #

单线程里池子只是个容器，跨线程它就是共享可变状态，每个读写点都得保护。

原语 语义 在缓冲池里的位置
QMutex 互斥锁 保护队列本身和计数器
QMutexLocker RAII 自动加解锁 替掉手写 lock()/unlock()
QWaitCondition 条件等待，释放锁并挂起 队列空时消费端等、满时生产端等
QSemaphore 计数信号量 空位数、数据数，本身就是容量控制
QReadWriteLock 读写分锁 统计、快照类读多写少的地方
QAtomicInt 无锁原子操作 只读指标计数

素材里的线程安全版 #

cpp
class ThreadSafeBufferPool : public QObject {
    Q_OBJECT
public:
    QByteArray* getAvailableBuffer();
    void releaseBuffer(QByteArray* buffer);
private:
    QMutex mutex;
    QWaitCondition bufferAvailable;
    QVector<QByteArray> buffers;
    QVector<bool> bufferUsed;
};

QByteArray* ThreadSafeBufferPool::getAvailableBuffer()
{
    QMutexLocker locker(&mutex);      // ← RAII 风格自动加解锁
    for (int i = 0; i < bufferUsed.size(); ++i) {
        if (!bufferUsed[i]) {
            bufferUsed[i] = true;
            return &buffers[i];
        }
    }
    return nullptr;
}

void ThreadSafeBufferPool::releaseBuffer(QByteArray* buffer)
{
    QMutexLocker locker(&mutex);
    const int index = indexOfBuffer(buffer);
    if (index != -1) {
        bufferUsed[index] = false;
        bufferAvailable.wakeOne();    // ← 唤醒等待缓冲区的线程
    }
}

QMutexLocker 替掉手动 lock()/unlock()，提前 return 和异常路径上锁都能正确释放。手写 unlock() 的代码里，多一个 return 就是一次死锁。

上面那个 return nullptr 是半成品：池子空了直接返回空指针，调用方只能自旋。既然已经有 QWaitCondition，就该让它等：

cpp
QByteArray* getAvailableBuffer(int timeoutMs = -1)
{
    QMutexLocker locker(&mutex);
    while (freeCount() == 0) {
        if (!bufferAvailable.wait(&mutex, timeoutMs)) {
            return nullptr;           // 超时了才返回空
        }
    }
    for (int i = 0; i < bufferUsed.size(); ++i) {
        if (!bufferUsed[i]) {
            bufferUsed[i] = true;
            return &buffers[i];
        }
    }
    return nullptr;
}

while 不能写成 if。线程被唤醒不代表条件成立——虚假唤醒会凭空返回，多生产者场景下也会出现「我醒了但空位被别的线程抢走」。醒来必须重新检查条件，这是条件变量的铁律。

信号量版本：容量控制内置在 API 里 #

cpp
explicit SemaphoreQueue(int capacity)
    : freeSlots(capacity), usedSlots(0) {}

void produce(const QByteArray& data) {
    freeSlots.acquire();              // 空位 -1；满了就停在这里
    mutex.lock();
    queue.enqueue(data);
    mutex.unlock();
    usedSlots.release();              // 可读 +1
}

QByteArray take() {
    usedSlots.acquire();              // 没数据就停在这里
    mutex.lock();
    QByteArray item = queue.dequeue();
    mutex.unlock();
    freeSlots.release();              // 空位 +1
    return item;
}

// 私有成员：QQueue<QByteArray> queue; QMutex mutex;
//           QSemaphore freeSlots;  // 剩余空位
//           QSemaphore usedSlots;  // 已有数据

两个信号量的和恒等于容量，这就是一个不用额外判断的容量控制器。顺序别写反：先拿信号量再拿锁。反过来的写法在池子满时会持锁挂起，另一个线程连 take() 都进不来，直接死锁。

跨线程用信号槽投递 #

缓冲区填满了，生产线程通知消费线程，跨线程连接走队列连接：

cpp
connect(producer, &Producer::bufferFull,
        consumer, &DataProcessor::onBufferFull,
        Qt::QueuedConnection);      // 跨线程必须显式写出来

cpp
void DataProcessor::onBufferFull(QByteArray* buffer)
{
    processData(*buffer);           // 解析数据或写入文件
    bufferPool->releaseBuffer(buffer);   // 处理完成后释放缓冲区
}

两个坑。第一，QByteArray* 默认没注册元类型，队列连接会丢参数并在控制台打印 Cannot queue arguments of type 'QByteArray*'，要在 main() 里补 qRegisterMetaType<QByteArray*>("QByteArray*")。

第二，指针跨线程传的是地址不是数据。生产线程 emit 完立刻复用那块缓冲区，消费线程收到的是一个已被改写的内容。要么确认消费完成才释放，要么把所有权随信号一起转移，用带引用计数的智能指针封装。

七、容量与阻塞策略 #

容量是唯一一个「调错了必然出事」的参数。太小天天堵，太大内存被吃掉。两头夹逼取交集：

text
下界（按突发）：容量 ≥ 峰值速率差 × 最长卡顿时长 ÷ 单条大小
上界（按内存）：容量 ≤ 内存预算 ÷ 单条大小

例：收包突发 5000 包/秒，磁盘卡顿最长 0.4 秒，单包 1.5 KB
    下界 = 5000 × 0.4 = 2000 包 ≈ 3 MB
    上界 = 100 MB ÷ 1.5 KB ≈ 68000 包
    取 2000，再留一倍余量 → 4000 包 ≈ 6 MB

留一倍余量是给「卡顿比预期长一点」留的。压着下界取值，等于假设每次卡顿都不超过历史最大值，这种假设迟早被打破。设计的核心就是平衡内存占用与吞吐——缓冲区数量过少会导致阻塞，过多则浪费内存。

参数 含义 定法
容量 队列最大深度 两头夹逼
单条大小 一条数据的字节数 固定则直接测，变长按 P95
高水位 触发限流/告警的深度 容量的 70%~80%
低水位 解除限流的深度 容量的 40%~50%
阻塞超时 生产方最多等多久 从业务 SLA 倒推
丢弃计数 累计丢了多少条 必须暴露成指标

高低水位要分开。只在满/空两个硬边界上反复阻塞唤醒，会出现「写一条立刻又满」的抖动，生产方在阻塞和运行之间高频切换：

text
硬边界（仅容量 1000）：写入 → 满 → 阻塞 → 消费 1 条 → 唤醒 → 写 1 条 → 又满
                      每秒几十次上下文切换，全是无用功
高低水位（高 800 / 低 400）：涨到 800 开始拒绝或降速 → 冷却到 400 恢复

阻塞怎么收尾，三选一：

收尾 代码 后果
永远等 wait(&mutex) 消费端挂了就永久卡死，线程池被拖住
等一会儿 wait(&mutex, 100) 有恢复机会，调用方得处理失败分支
等不到就降级 超时后改丢弃/落盘/直写 最稳，但要写降级逻辑

永远等的 wait(&mutex) 是定时炸弹。消费线程因未处理异常退出，生产线程就永远挂在那把锁上，既不上报也不退出，进程还活着，功能已经死了。

背压要一路传到底，阻塞本身不是目的，把压力传到该负责的地方才是：

text
消费瓶颈 ──▶ 队列满 ──▶ 生产方阻塞
                          ├─▶ IO 线程：停止读 socket → TCP 窗口收缩 → 对端减速
                          ├─▶ 采集线程：跳过这一帧 → 丢帧计数 +1
                          └─▶ 业务线程：返回 503 → 调用方退避重试

甩到对端让它自己慢下来，比自己撑爆内存好。

八、内存复用与对象池 #

缓冲池的「池」字，一半价值在复用上。频繁 new/delete 几十 KB 的缓冲区，代价不在分配本身，在分配器为碎片做的整理。

拷贝不贵，写才贵 #

QByteArray 是隐式共享的，拷贝构造只加引用计数：

cpp
QByteArray a(4096, 0);
QByteArray b = a;          // 不加锁、不拷贝，只 ref++，O(1)
b[0] = 'x';                // 这一刻才 detach，真复制 4096 字节

所以往队列里 enqueue 一个 QByteArray 传值不心疼，贵的是第一笔写入触发的深拷贝。要压测时不被「明明没写拷贝代码却很慢」迷惑，就在共享之后、写入之前显式调一次 detach()，把隐式开销摆到明面上。

复用缓冲区：clear 不等于释放 #

cpp
// 错误：看起来复用了，其实每次都在换新内存
void reuseWrong(QByteArray& buf, const char* src, int len) {
    buf = QByteArray(src, len);          // 直接构造新对象，旧内存归还分配器
}

// 正确：只改内容，内存不动
void reuseRight(QByteArray& buf, const char* src, int len) {
    buf.resize(len);                     // 容量够就不重新分配
    memcpy(buf.data(), src, len);
}

resize(0) 和 = QByteArray() 的差别就在这里：前者留着已分配的堆块，后者还给分配器。池子里的缓冲区必须走前者。

重置方式 代价 什么场景用
resize(0) O(1) 定长协议包，长度由包头决定
fill('\0') O(n) 内存写 内容要交给外部，不希望泄漏上一轮数据
什么都不做 0 内部使用，下一轮会完整覆盖

64 KB 缓冲区上一次 fill('\0') 是一笔实打实的 memcpy，池子每秒转一千次就是每秒 64 MB 的无效内存写。除了要把内存内容交给不受信任的一方，这个清零可以省掉。

对象池：给非 POD 对象复用 #

缓冲区是连续内存，对象池管的是带构造/析构的类型。QObject 派生类不能拷贝，只能复用指针，思路是维护一个空闲链表：

cpp
T* acquire() {
    QMutexLocker locker(&mutex);
    if (freeList.isEmpty()) return new T;   // 池子空了就现造，别让调用方等
    return freeList.takeLast();
}

void release(T* obj) {
    obj->reset();                            // 关键：清掉上一轮状态
    QMutexLocker locker(&mutex);
    if (freeList.size() >= maxIdle) { delete obj; return; }
    freeList.append(obj);
}

obj->reset() 是对象池最容易漏的一行。忘了它，下一个使用者拿到的是带着上一轮数据的对象，症状是「偶发脏数据」，排查周期以天计。maxIdle 上限也得有——池子目的是削峰，不是无限囤积，峰值过去后一堆空闲对象占着内存反而成了负担。

九、Qt 内置的缓存机制 #

Qt 里有几套现成的「拿内存换时间」机制，选错了会白写一堆代码。

类 定位 淘汰策略 容量语义
QQueue<T> 逻辑队列 无，自己控制 无上限，需自行限深
QCache<Key,T> 键值缓存 LRU，超预算自动淘汰 按 cost 计（可自定义单位）
QPixmapCache 全局图片缓存 LRU，超预算自动淘汰 全局静态，单位 KB
QContiguousCache<T> 连续区间缓存 滚出窗口即失效 按条目数

QCache：带 LRU 淘汰的缓存 #

cpp
QCache<QString, QImage> cache(64 * 1024);        // 预算 64 MB，cost 单位自定义为 KB
cache.insert(key, new QImage(img), img.sizeInBytes() / 1024);  // 所有权转移给 cache

QImage* hit = cache.object(key);                  // 命中返回指针，未命中返回 nullptr
if (!hit) {
    loadInto(cache, key);
}
cache.setMaxCost(128 * 1024);                     // 动态调预算，超了自动按 LRU 淘汰

insert 之后对象的生命周期归 QCache 管，别再 delete。要自己接手用 take()，它会把所有权还给你。用 object() 拿到的指针不能长期持有——下一次 insert 触发淘汰时它就会变成悬空指针。

QPixmapCache：全局图片缓存 #

cpp
QPixmapCache::setCacheLimit(20480);               // 单位 KB
QPixmap pm;
if (!QPixmapCache::find(key, &pm)) {
    pm.load(path);
    QPixmapCache::insert(key, pm);                // 全局静态，所有 QPixmap 共享这一份
}

它是全局的静态缓存，写进 QPixmapCache 的东西进程内任何地方都能读到。好处是图标、背景图不用自己管一份；坏处是全局状态没有归属，两个模块用同一个 key 会互相覆盖。key 一定要带命名空间前缀。

缓冲池和缓存的区别 #

text
缓冲池 → 面向「流」：数据从 A 流向 B，中间暂存，读完就作废
缓存   → 面向「重复访问」：同一份数据被多次读取，读不改变它
维度 缓冲池 缓存
目的 解耦生产与消费的速率 减少重复计算或重复 IO
数据流向 单向穿过，读完即弃 留下来，等下一次命中
淘汰依据 满的时候按策略丢/等 命中率低、预算超限时按 LRU 出
命中概念 没有命中，只有空和满 命中率是核心指标
容量语义 深度决定延迟和抗突发能力 预算决定内存上限
典型类 QQueue、自建环形缓冲 QCache、QPixmapCache

同一个结构可以同时干两件事，但指标得分开看。缓冲池盯的是队列深度和丢弃数，缓存盯的是命中率和淘汰数。混在一起统计，两边都读不懂。

十、什么时候该用缓冲池 #

加不加缓冲，先过一遍这张清单：

判断 该加 不该加
两端速率 平均相当但存在突发 平均差一个数量级，怎么缓冲都会满
延迟要求 允许几十毫秒以上排队 硬实时，多一跳都不行
内存预算 拿得出「深度 × 单条大小」 嵌入式，几百 KB 都要抠
数据可丢性 可丢（选丢弃）或可等（选阻塞） 既不能丢也不能等
消费端特性 支持批量处理，批越大越划算 必须逐条同步返回结果

不该用的时候，先看有没有更省事的替代：

text
1. 两端同线程、处理很快 → 直接调用，队列是纯开销
2. 只为了堆异步 → QThreadPool + QFutureWatcher 就够了，别再自己搭队列
3. 只是想攒批 → 给接口加个批量版本，比在中间塞队列直接
4. 生产端本来就有流控 → 让上游自己控速，队列只会掩盖问题

一个反例很常见：为了「不阻塞 UI」把每个鼠标移动事件塞进队列，队列又深又没上限，最后 UI 线程在消费端反而被拖垮。这种场景要的是丢帧加合并，不是缓冲。

十一、性能与陷阱 #

指针失效 #

getAvailableBuffer() 返回 &buffers[i]，只要 buffers 发生扩容重分配，所有已发出的指针立刻失效，而且不会崩溃——它们指向的还是合法内存，只是内容变成了别人的。症状是数据错乱而不是段错误，最难查。修法只有一条：构造期 reserve(bufferCount) 定终身上限，之后任何位置都不再 append、不再 resize 到更大值、不再 removeAt。要动态扩容，就别返回裸指针，返回下标。

锁粒度 #

一把大锁保护整个池子，所有线程排队。池子本身的分段结构天然可切：按缓冲区编号分段加锁，或者用 QAtomicInt 做空闲链表。粗粒度一把 QMutex 保护 buffers 和 bufferUsed，写法简单，核数一多就成瓶颈；细粒度每 N 个缓冲区一把锁，快，但释放和统计跟着变复杂。

先上粗锁量出瓶颈再拆，别一上来就设计无锁。多数链路的瓶颈在 IO 和拷贝，不在锁上。

其它几条 #

text
· QByteArray(size, 0) 会先 memset 一遍，几 MB 的缓冲区光构造就够慢
· 忘记 releaseBuffer 就是内存泄漏，池子最后变成永远返回 nullptr
· 队列深度必须有指标，没有监控的缓冲池等于没设计
· 缓冲区数量与大小要成对定：4 × 1 MB 和 4000 × 1 KB 行为完全不同

最后一条容易被忽略。总量相同的情况下，少而大的缓冲区适合定长大包，多而小的适合变长小包。缓冲区太大，小包会浪费内部碎片；缓冲区太小，大包要跨块拼接，多一次拷贝和一段拼装逻辑。

十二、易错点速查 #

现象 根因 处理
偶发脏数据 缓冲区复用前没重置 resize(0) 或 fill('\0')
数据错乱不崩溃 池子扩容导致返回的指针失效 构造期 reserve 定容量，或返回下标
消费线程收不到信号 QByteArray* 未注册元类型 qRegisterMetaType<QByteArray*>()
释放到了错槽位 indexOf 按值比较 用指针地址算下标
界面假死 UI 线程上有界阻塞 换丢弃策略或把等待挪出 UI 线程
内存线性上涨 无界队列 + 消费端停摆 设容量上限，加高水位告警
数据一段一段丢 环形缓冲回绕只处理了第一段 分两段读，处理 secondChunk
线程永久卡死 wait(&mutex) 无超时 必须带 timeout，加降级分支
高频阻塞唤醒 只有硬边界没有水位线 加高/低水位做滞回
吞吐上不去 一把大锁 + 逐条处理 分段锁，消费端批量取
丢数据不知道丢多少 丢弃没计数 dropped() 进监控
对象池串数据 释放时没回滚对象状态 release() 里调 reset()

这张表里的每一条，都能在真实项目里找到对应的故障单。缓冲池的代码量不大，难点全在这些边角上——它把一个「快慢不匹配」的时序问题，摊平成一组必须显式回答的问题：容量多少、满了等不等、丢了算不算、指针还能不能用。这四个问题答完，池子就成了。
