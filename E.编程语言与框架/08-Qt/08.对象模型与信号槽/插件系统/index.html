本篇只讲 Qt 自己的插件机制：一个 C++ 动态库怎么被主程序在运行时认出来、转成接口、拿到对象。 不讲 Qt Designer 控件插件、QML 插件注册、Qt Creator 整个产品的构建体系。 跨篇指路：「QObject 与对象模型」讲 metaObject 与 qt_metacast 的底子，插件能被 qobject_cast 认出来全靠它；「信号与槽」讲插件和主程序跨界 connect 为什么会静默失效；「缓冲池」讲插件内部对象复用的做法；「Qt4 到 Qt5 的迁移」讲 Q_EXPORT_PLUGIN2 被 Q_PLUGIN_METADATA 顶掉的那一段。

一、插件系统解决什么问题 #

主程序越大，编译期耦合越难拆。菜单、编辑器、版本控制、调试器全塞在一个可执行文件里，改一行头文件就要重编整个工程，链接时间按分钟算。

插件把这条链切断：

  • 主程序只认接口头文件，不认实现。实现躺在单独的 .dll / .so 里，编译期谁也不认识谁。
  • 发布时只带主程序，功能模块按需附带。
  • 团队可以并行开发，各自的插件单独编译、单独替换、单独回滚。

Qt Creator 就是这么搭起来的：一个轻量的 Core 插件负责主窗口和事件循环，其余功能全是插件。C++ 编辑器、Git 支持、调试器之间没有直接的代码依赖，只依赖 Core 暴露的扩展点。

从技术上看，一个插件就是动态链接库。Windows 下是 .dll，Linux 下是 .so，macOS 下是 .dylib。开发流程固定三步：定义接口、继承实现、编成库。

收益和代价是一起来的东西：

收益 跟着来的代价
编译期解耦 接口对不对要到运行时才知道，错误从编译期推迟到启动期
按需分发 多一个目录、多一套版本管理、多一份部署说明
独立替换 ABI 一旦不匹配，主程序直接起不来
功能边界清晰 跑在同一进程，插件崩了主程序一起陪葬

所以插件化只在「功能边界清晰 + 需要独立演进」时划算。一个总共 3 个源文件的小工具套上插件，换来的是多一倍的构建配置和一堆加载失败的排查时间。

Qt 把插件做成了两段式契约，这句话请记住，后面十章都在围着它转：

  1. 元数据 JSON：说清插件叫什么、版本多少、依赖谁。这段数据被 moc 编进库的静态数据段里，QPluginLoader 读它的时候不执行库里的任何代码。
  2. 接口声明：告诉 moc 这个类实现了哪个接口。库被加载之后，qobject_cast 靠它把 QObject * 转成 IPlugin *。

缺一段都不行。没有元数据，QPluginLoader 认不出这是个插件；没有接口声明，qobject_cast 返回空指针，后面流程全塌。

二、Qt 的两类插件：静态与动态 #

Qt 的插件分静态、动态两类，构建配置差一个 CONFIG 项。

2.1 动态插件 #

单独的库文件，运行时用 QPluginLoader 从磁盘打开。.pro 这么写：

TEMPLATE = lib
CONFIG += plugin
CONFIG -= app_bundle
TARGET = myplugin
DESTDIR = $$PWD/../plugins
INCLUDEPATH += $$PWD/../core

编出来是 myplugin.dll（或 libmyplugin.so），扔进插件目录，主程序启动时扫一遍。CONFIG += plugin 决定了 moc 生成的代码形态，也让链接器把元数据段留在最终产物里。

2.2 静态插件 #

编进主程序，不产生独立库文件。靠 Q_IMPORT_PLUGIN 把它注册进 Qt 的静态插件表：

cpp
#include <QtPlugin>
Q_IMPORT_PLUGIN(MyPlugin)   // 必须写在全局作用域，不能放在函数里

这行宏的作用是实例化 moc 生成的静态插件注册类。少了它，链接器会把这个目标文件当无用代码丢掉，插件就静默消失。

静态插件用 QPluginLoader 的静态接口来取：

cpp
const auto plugins = QPluginLoader::staticPlugins();
for (const QStaticPlugin &sp : plugins) {
    QObject *obj = sp.instance();
    if (IPlugin *p = qobject_cast<IPlugin *>(obj)) {
        p->initialize();
    }
}

注意 staticPlugins() 拿到的是描述结构，instance() 才给你对象。

2.3 两类插件对比 #

维度 动态插件 静态插件
产物 独立 .dll / .so / .dylib 编进主程序，无独立文件
构建开关 CONFIG += plugin CONFIG += plugin static
注册方式 QPluginLoader(fileName) Q_IMPORT_PLUGIN(Name)
获取对象 loader.instance() QPluginLoader::staticPlugins() 再 instance()
加载失败 运行时报错，可捕获 链接期或启动期就暴露，几乎没有失败
可否卸载 可以 unload()，但要小心 不能，生命周期等于进程
部署成本 要把依赖库一起带上 零，单文件走天下
适用场景 功能模块、可选组件、第三方扩展 功能固定但想保持代码解耦、嵌入式裁不动

关键认知：业务代码不用管静态还是动态。拿到 QObject * 之后一律 qobject_cast，差异只在加载那一步。接口层写对了，两种形态可以共用同一份实现代码。

三、QPluginLoader 与 QLibrary #

这两个类经常被搞混。一句话分界：QLibrary 是 dlopen / LoadLibrary 的薄封装，QPluginLoader 是在它上面盖了一层 Qt 插件协议。

3.1 QLibrary 只给你函数符号 #

QLibrary 不认插件，它只认得「打开一个库，按名字取一个符号地址」：

cpp
#include <QLibrary>

QLibrary lib("third_party/mathlib.dll");
if (!lib.load()) {
    qWarning() << "load failed:" << lib.errorString();
    return;
}
using CalcFn = int (*)(int, int);
auto add = reinterpret_cast<CalcFn>(lib.resolve("add"));
if (!add) {
    qWarning() << "resolve failed:" << lib.errorString();
    return;
}
qDebug() << add(1, 2);
lib.unload();

它没有元数据概念，没有 instance()，不知道 IID 是什么，更不会帮你校验 Qt 版本。它只是把 C 符号暴露出来。

3.2 QPluginLoader 多做了两件事 #

QPluginLoader 在 QLibrary 之上加了两件事：读元数据、造实例。

cpp
#include <QPluginLoader>

QPluginLoader loader("plugins/myplugin.dll");

// 先看元数据，此时还没构造插件对象
const QJsonObject meta = loader.metaData();
qDebug() << "IID:" << meta.value("IID").toString();
qDebug() << "class:" << meta.value("className").toString();

// 这一步才真正打开库、造出根组件
QObject *obj = loader.instance();
if (!obj) {
    qWarning() << "instance failed:" << loader.errorString();
    return;
}

IPlugin *plugin = qobject_cast<IPlugin *>(obj);
if (!plugin) {
    qWarning() << "cast failed: object does not implement IPlugin";
    return;
}

那个元数据是从库文件的静态数据段里读出来的，不跑插件里的构造函数，也不跑 initialize()。这条性质很重要：主程序可以先把目录里几十个插件的元数据全扫一遍，判断谁该加载、谁版本不对、谁依赖缺失，再决定要不要真把库打开。

3.3 两套 API 对照 #

能力 QLibrary QPluginLoader
打开库 load() load()，或被 instance() 隐式触发
取函数符号 resolve("name") 不提供
读插件元数据 无 metaData()
造插件实例 无 instance()
IID 与版本校验 无 内建
判断是不是插件 无 isLoaded() 配合 metaData() 是否为空
卸载 unload() unload()
失败信息 errorString() errorString()

3.4 什么时候该用哪个 #

  • 加载非 Qt 的第三方 C 库、只要函数指针：QLibrary。
  • 加载自己写的 Qt 插件、需要拿到 QObject：QPluginLoader。
  • 拿 QLibrary 去加载 Qt 插件：不行，你会丢掉元数据和类型校验，resolve 出来的符号名也跟着 moc 的实现变化，脆得很。
  • QPluginLoader 的 instance() 有缓存，同一个 loader 调多次返回同一个对象。别 delete 它，对象归 loader 管；要释放就交给 unload()，而且卸载时机得自己算清楚。

四、插件接口的定义 #

接口就是一个只有纯虚函数的类，加一个虚析构。

cpp
// iplugin.h  —— 主程序和插件共享同一个头文件
#ifndef IPLUGIN_H
#define IPLUGIN_H
#include <QString>
#include <QStringList>

class IPlugin
{
public:
    virtual ~IPlugin() {}
    virtual bool initialize(const QStringList &arguments, QString *errorMessage) = 0;
    virtual void extensionsInitialized() = 0;
    virtual void shutdown() = 0;
    virtual QString name() const = 0;
};

#endif

4.1 四条硬规则 #

  1. 析构必须 virtual。主程序握着的是 IPlugin *，库里造的对象，delete 时走非虚析构就是未定义行为。
  2. 接口里不放成员变量。一放，主程序和插件对类大小的认知就对不上。
  3. 不写 inline 函数体（空的虚析构除外）。inline 会在两边各编一份，优化级别和内联决策不同，遇到布局变化直接对不上。
  4. 参数和返回值只用 Qt 类型、POD、指针。别在接口上暴露 std::vector<自定义模板>，MSVC 的 STL 与 MinGW 的 STL 二进制不兼容，跨编译器一传就炸。

接口是 ABI 的接触面。接口上每一个字节的改动，都要当成一次破坏性变更来处理。

4.2 接口要不要继承 QObject #

写法 好处 代价
纯虚类，不继承 QObject 最轻，接口头不拖 QObject，插件想怎么实现都行 不能直接 connect，用信号槽得拿到 QObject * 那一侧
继承 QObject 能直接当 QObject 用，可参与对象池和信号槽 接口头必须引 <QObject>，虚表布局跟着 Qt 走

Qt Creator 的 IPlugin 继承 QObject，因为插件对象本身要进对象池、要发信号。你写小插件时纯虚类就够，实现类自己多继承一个 QObject 即可。

4.3 接口的版本化 #

加功能不能往老接口上改。老插件是按老虚表布局编出来的，主程序一调新虚函数就跳进垃圾地址：

cpp
class IPlugin2 : public IPlugin
{
public:
    virtual bool canReload() const = 0;
    virtual void setWarningsEnabled(bool on) = 0;
};

新接口 = 老接口 + 新纯虚函数。老插件没实现 IPlugin2，qobject_cast 自然转不过去。主程序按能力探测：

cpp
if (IPlugin2 *p2 = qobject_cast<IPlugin2 *>(obj)) {
    p2->setWarningsEnabled(true);
} else {
    qDebug() << "legacy plugin, warnings not supported";
}

这套做法让新旧插件能同时装在同一个目录里，不用一刀切。

4.4 插件的工程文件 #

QT += core
TEMPLATE = lib
CONFIG += plugin c++11
HEADERS += iplugin.h myplugin.h
SOURCES += myplugin.cpp
TARGET = myplugin
DESTDIR = $$PWD/../bin/plugins

iplugin.h 两边必须是同一份文件。把它拷一份进插件工程是灾难开端：改主程序那份忘了改插件那份，编译不报错，运行起来虚表错位。

五、Q_DECLARE_INTERFACE 与 Q_INTERFACES #

这两个宏是整篇最容易踩空的地方，因为只写一个也能把代码编过去。

5.1 分工 #

宏 写在哪 干什么
Q_DECLARE_INTERFACE(IFace, "IID") 接口头文件，类定义之后，全局写一次 给接口注册唯一字符串 IID，并让 qobject_cast 知道拿哪个字符串去比对
Q_INTERFACES(IFace) 插件实现类的类体里 告诉 moc「这个类实现了 IFace」，moc 据此在 qt_metacast 里生成 IID 比对分支
Q_PLUGIN_METADATA(IID "...") 实现类类体，紧跟 Q_OBJECT 告诉 moc「这是插件入口」，并可挂一个 JSON 文件
Q_OBJECT 实现类 生成 moc 元数据，没有它 Q_INTERFACES 无从挂载

5.2 正确写法 #

cpp
// iplugin.h
class IPlugin
{
public:
    virtual ~IPlugin() {}
    virtual QString name() const = 0;
};

#define IPlugin_iid "org.example.Blog.IPlugin/1.0"
Q_DECLARE_INTERFACE(IPlugin, IPlugin_iid)

cpp
// myplugin.h
#include <QObject>
#include <QtPlugin>
#include "iplugin.h"

class MyPlugin : public QObject, public IPlugin
{
    Q_OBJECT
    Q_PLUGIN_METADATA(IID IPlugin_iid FILE "myplugin.json")
    Q_INTERFACES(IPlugin)

public:
    bool initialize(const QStringList &arguments, QString *errorMessage) override;
    void extensionsInitialized() override;
    void shutdown() override;
    QString name() const override { return QStringLiteral("MyPlugin"); }
};

继承顺序上 QObject 必须放在前面，moc 只认第一个基类。

5.3 底层发生了什么 #

Q_INTERFACES 的作用，是让 moc 在生成的 qt_metacast 里多几条字符串比对：

cpp
void *MyPlugin::qt_metacast(const char *_clname)
{
    if (!_clname)
        return nullptr;
    if (!strcmp(_clname, "MyPlugin"))
        return static_cast<void *>(this);
    if (!strcmp(_clname, "org.example.Blog.IPlugin/1.0"))
        return static_cast<IPlugin *>(this);
    return QObject::qt_metacast(_clname);
}

qobject_cast 处理接口类型时，就是拿 IID 调 qt_metacast，看返回值是不是空。所以缺一条分支，转换就必然失败。

这也解释了三类典型症状：

  • 有 Q_DECLARE_INTERFACE、没 Q_INTERFACES：moc 不知道这个类实现了接口，qt_metacast 里没有那条分支。编译通过，运行时静默返回空指针。最难查的一种。
  • 有 Q_INTERFACES、没 Q_DECLARE_INTERFACE：IID 查不到，编译期直接报错。这种好办。
  • 两个都有、IID 字符串抄错一个字母：照样返回空。所以把 IID 定义成宏，两边都引宏，别手抄。
情况 编译 运行结果 现象
只有 Q_DECLARE_INTERFACE 通过 qobject_cast 返回 nullptr 插件加载成功，接口转不出来
只有 Q_INTERFACES 失败 — 报接口 IID 未声明
两个都有，IID 不一致 通过 qobject_cast 返回 nullptr 同上，且极难发现
两个都有，漏了 Q_OBJECT 通过或告警 没有 moc 元数据 链接期报 qt_metacall 未定义

5.4 插件 IID 与接口 IID 是两回事 #

Q_PLUGIN_METADATA 的 IID 标识插件入口，Q_DECLARE_INTERFACE 的 IID 标识接口类型。

惯例是写成同一个字符串。Qt Creator 就用 org.qt-project.Qt.QtCreatorPlugin 同时占两个位置，好处是框架可以按 IID 过滤插件目录。

不一致会怎样？qobject_cast 照样工作，因为它只看接口 IID；但任何按 IID 筛插件的加载器会认不出你的插件，插件在目录里躺着却不被加载。统一成宏最省事。

六、插件的元数据 JSON #

6.1 怎么挂上去 #

cpp
Q_PLUGIN_METADATA(IID IPlugin_iid FILE "myplugin.json")

FILE 的路径相对当前源文件，不相对工作目录，也不相对 .pro。构建目录里找不到它，moc 直接失败。

moc 把 JSON 内容原样编进库的静态数据段。元数据是编译期固化的，运行时改磁盘上的 JSON 不会有任何效果——你改的是源码里那份，必须重编。

6.2 你的字段在 MetaData 下面 #

QPluginLoader::metaData() 拿到的不是你的 JSON 本身，Qt 在外面包了一层：

json
{
    "IID": "org.example.Blog.IPlugin/1.0",
    "className": "MyPlugin",
    "debug": false,
    "version": 331520,
    "MetaData": {
        "Name": "MyPlugin",
        "Version": "1.0.0"
    }
}
  • IID、className、debug、version 是 Qt 自己填的。
  • version 是 Qt 的版本号，不是你的插件版本。
  • 你的字段全在 MetaData 下面。

取值要往下钻一层：

cpp
const QJsonObject root = loader.metaData();
const QJsonObject mine = root.value("MetaData").toObject();
const QString pluginName = mine.value("Name").toString();
const QString pluginVer  = mine.value("Version").toString();

很多人卡在这里：直接读 root.value("Name")，拿到空字符串，然后怀疑元数据没编进去。

6.3 JSON 里放什么 #

Qt 不规定字段名，全由你的框架约定。Qt Creator 的 Core.json：

json
{
    "Name" : "Core",
    "Version" : "$$QTCREATOR_VERSION",
    "Required" : true,
    "Vendor" : "The Qt Company Ltd",
    "Category" : "Qt Creator",
    "Arguments" : [
        { "Name" : "-theme", "Parameter" : "default|dark" }
    ]
}

$$QTCREATOR_VERSION 是构建系统的变量，编的时候替换成真实版本号。版本号只在构建系统里写一次，不会出现头文件写 4.10、插件 JSON 写 4.8 的对不上。

自定义插件建议留这几个键：

键 用途
Name 插件唯一标识，也是显示名
Version 插件自身版本，做依赖校验用
Required 缺失时是否阻断启动
Vendor 出问题能找到谁
Category 分组，便于 UI 与日志归类
Dependencies 依赖的插件名与版本要求

6.4 扫目录只读元数据，不加载库 #

主程序可以先探一遍插件目录：

cpp
QDir dir(pluginPath);
const auto entries = dir.entryList(QStringList() << "*.dll" << "*.so",
                                   QDir::Files);
for (const QString &fileName : entries) {
    QPluginLoader probe(dir.absoluteFilePath(fileName));
    const QJsonObject meta = probe.metaData();
    if (meta.isEmpty()) {
        qWarning() << "not a Qt plugin:" << fileName;
        continue;
    }
    if (meta.value("IID").toString() != IPlugin_iid) {
        qWarning() << "wrong IID:" << fileName;
        continue;
    }
    qDebug() << "found plugin:"
             << meta.value("MetaData").toObject().value("Name").toString();
}

这一步不跑插件里的构造函数，不跑 initialize()。主程序能在真正加载之前，就把不合适的库全筛掉。

七、插件的加载与实例化 #

7.1 一个能用的加载函数 #

cpp
#include <QPluginLoader>
#include <QJsonObject>
#include <QDebug>

IPlugin *loadPlugin(const QString &filePath)
{
    auto *loader = new QPluginLoader(filePath);
    // 1. 元数据先过关，这一步不跑插件代码
    const QJsonObject meta = loader->metaData();
    if (meta.isEmpty()) {
        qWarning() << "[skip] not a Qt plugin:" << filePath;
        delete loader;
        return nullptr;
    }
    if (meta.value("IID").toString() != IPlugin_iid) {
        qWarning() << "[skip] IID mismatch:" << filePath
                   << meta.value("IID").toString();
        delete loader;
        return nullptr;
    }
    // 2. 真正加载并造对象
    QObject *obj = loader->instance();
    if (!obj) {
        qWarning() << "[fail] instance():" << filePath
                   << loader->errorString();
        delete loader;
        return nullptr;
    }
    // 3. 转成接口
    IPlugin *plugin = qobject_cast<IPlugin *>(obj);
    if (!plugin) {
        qWarning() << "[fail] qobject_cast returned null:" << filePath;
        return nullptr;
    }
    loader->setParent(obj);   // 或者自己存到管理器里
    return plugin;
}

errorString() 里那句话往往是唯一的线索，别省掉不打。

7.2 instance() 内部做了哪些事 #

  1. 打开库文件（同 QLibrary::load()），失败返回空。
  2. 从静态数据段读元数据，确认带 IID 和 className。
  3. 校验库的 Qt 版本与构建配置，与当前进程不符就报 The plugin ... uses incompatible Qt library。
  4. 按 className 找 moc 生成的插件入口，调它的工厂函数造出根组件。
  5. 把根组件指针缓存下来，后面对同一个 loader 再调直接返回缓存。

7.3 加载不是一次 load() #

一个成熟的插件系统把加载拆成多阶段状态机，每个阶段只做一件事：

text
              readMetaData()            resolveDependencies()
  [*] ─────────────► Read ──────────────────────► Resolved
                     ▲                              │  对每个插件循环
                     └──────────────────────────────┘
                                                    │ loadPlugins()
                                                    ▼
                                                 Loaded       ← 库已进内存
                                                    │ initialize()
                                                    ▼
                                              Initialized      ← 依赖可访问
                                                    │ extensionsInitialized()
                                                    ▼
                                                Running        ← 可深度交互
                                                    │ nextDelayedInitialize()
                                                    ▼
                                                Delayed ──delayedInitialize()──► Running
                                                    │ shutdown()
                                                    ▼
                                                 Stopped ──► [*]
阶段 入口函数 库已加载 能做 不能做
Read readMetaData() 否 扫目录、读 JSON、建 PluginSpec 碰任何插件代码
Resolved resolveDependencies() 否 建依赖树、查循环、定顺序 假设顺序已经生效
Loaded loadPlugins() 是 拿到接口指针 访问依赖插件的运行期状态
Initialized initialize() 是 注册自己的对象、读命令行参数 假设依赖插件都初始化完了
Running extensionsInitialized() 是 订阅信号、注册回调、深度交互 做重活拖慢启动
Delayed delayedInitialize() 是 后台任务、索引、缓存预热 假设主窗口已经响应
Stopped shutdown() 是 存配置、断连接、释放资源 指望后面还有人调你

两个最容易搞错的地方：

  • initialize() 里只能访问「依赖插件的公共接口」，不能假设依赖插件的 initialize() 已经跑完。依赖图是按拓扑序推进的，上一层的 extensionsInitialized() 还在后头。
  • 重活放 delayedInitialize()。启动时间是从 readMetaData 算到主窗口出现的，索引、扫描、网络探测全塞进 initialize() 会让窗口白屏几秒。

7.4 主程序这一侧 #

main.cpp 把所有阶段串起来：

cpp
int main(int argc, char *argv[])
{
    QApplication app(argc, argv);
    // 1. 配置初始化（全局配置与用户配置）
    QSettings settings(QSettings::IniFormat, QSettings::UserScope,
                       "Example", "BlogPluginDemo");
    // 2. 插件管理器配置：搜索路径 + IID 校验
    PluginManager pluginManager;
    pluginManager.setPluginPaths(pluginPaths());
    pluginManager.setPluginIID(IPlugin_iid);
    // 3. 分阶段加载
    pluginManager.loadPlugins();
    // 4. 容错检查：核心插件必须存在且没报错
    PluginSpec *core = pluginManager.pluginByName("Core");
    if (!core || core->hasError()) {
        displayError(QStringLiteral("Could not load Core plugin"));
        return 1;
    }
    // 5. 进入事件循环，最后统一卸载
    const int code = app.exec();
    pluginManager.shutdown();
    return code;
}

核心插件是整棵依赖树的根。它加载不上，后面的插件全都没意义，所以第 4 步必须在 app.exec() 之前做完。

7.5 unload() 的坑 #

QPluginLoader::unload() 会把库从进程里卸掉，插件的代码段跟着消失。此时：

  • 任何还活着的插件对象都成了悬空指针，包括你在别处存下的 IPlugin *。
  • 插件发出去还没处理的信号参数，指向的内存已经没了。
  • 插件的静态变量、单例全被销毁，再加载一遍等于重新开始。

实践上，除了明确知道「插件对象已经全删、信号全断、没有别处引用」的场景，退出阶段直接让进程结束更省事。非得热卸载，就把卸载做成「先 shutdown()，再统一 delete，最后才 unload()」的三步，中间不许有别的代码插进来。

八、插件管理器与依赖 #

8.1 三个角色 #

整个结构由三部分组成：

角色 职责
插件管理器 全生命周期：扫描、加载、依赖解析、初始化、卸载，外加对象池
核心插件（Core） 提供基础设施：主窗口、菜单栏、动作管理器、事件循环，是所有插件的根依赖
普通插件 具体业务功能，依赖核心插件暴露的扩展点

结构上长这样：

text
+-------------------------------------------------------+
|               Qt Creator 主程序                        |
|  +----------------------+    +---------------------+   |
|  | PluginManager        |───►| ExtensionSystem 库   |   |
|  | 生命周期/依赖/对象池  |    | IPlugin/PluginSpec   |   |
|  +----------+-----------+    +---------------------+   |
|             │ 加载并初始化                                |
|     ┌───────┴────────┐                                 |
|     ▼                ▼                                 |
|  +--------+    +---------+    +---------+              |
|  | Core   |◄───| C++编辑器|    | Git支持 |              |
|  +--------+    +---------+    +---------+              |
+-------------------------------------------------------+

8.2 插件的规约 PluginSpec #

每个插件的磁盘形态是库文件，内存形态是一个 PluginSpec。它记录三样东西：

  • 元数据（从 JSON 读来的 Name / Version / Vendor 等）。
  • 状态（Read / Resolved / Loaded / Initialized / Running / Stopped）。
  • 依赖列表与错误信息（hasError()、errorString()）。

有了它，管理器就能在不加载任何库的前提下，先把整个插件集合的关系理清楚。

8.3 对象池 #

管理器维护一个全局对象池，供插件间通信和资源共享。核心是一个单例，底层结构大致这样：

cpp
// pluginmanager_p.h
class EXTENSIONSYSTEM_EXPORT PluginManagerPrivate : public QObject
{
    Q_OBJECT
public:
    QHash<QString, QList<PluginSpec *>> pluginCategories;
    QList<PluginSpec *> pluginSpecs;   // 插件规约列表
    QList<QObject *> allObjects;       // 全局对象池
    QReadWriteLock m_lock;             // 保护 allObjects
    // ...
};

对象池的价值在于「谁都能找到谁」：插件 A 想在插件 B 里注册一个服务，直接往池子里扔对象，别的插件遍历一遍就能拿到，不用改任何一方头文件。

代价是池子是全局可变状态，任何插件都能往里塞东西，也都能读到不属于自己的东西。要定规则。

8.4 加入与移除必须是线程安全的 #

添加对象：

cpp
void PluginManagerPrivate::addObject(QObject *obj)
{
    if (!obj) {
        qWarning() << "addObject: null object";
        return;
    }
    {
        QWriteLocker lock(&m_lock);
        if (allObjects.contains(obj)) {
            qWarning() << "addObject: duplicate" << obj;
            return;
        }
        allObjects.append(obj);
    }
    emit q->objectAdded(obj);   // 锁外发信号，避免死锁
}

四步：拿写锁、查空查重、追加进列表、发 objectAdded 信号。信号一定要在锁外发，否则槽函数里再回来调对象池就自锁了。

移除对象：

cpp
void PluginManagerPrivate::removeObject(QObject *obj)
{
    if (!obj)
        return;
    // 先通知，让依赖方提前清理
    emit q->aboutToRemoveObject(obj);

    QWriteLocker lock(&m_lock);
    allObjects.removeOne(obj);
}

顺序反过来就会出事：先移除再通知，那些还在引用这个对象的模块会在一瞬间看到空位。

8.5 依赖描述 #

cpp
struct PluginDependency
{
    enum Type { Required, Optional, Test };
    QString name;     // 依赖插件名
    QString version;  // 版本要求
    Type type;        // 依赖类型
};
类型 缺失时的行为 用在哪
Required 当前插件加载失败，报错并阻断 功能上真的离不开的依赖
Optional 照常加载，功能降级 有更好、没有也能跑
Test 只在测试构建里要求 单元测试、集成测试专用插件

规则一句话：若插件 A 依赖插件 B，则 B 必须在 A 之前加载并初始化。

依赖解析就三步：建依赖图、查环、拓扑排序。查到环直接报错，别指望运行期自己恢复：

cpp
bool PluginManagerPrivate::resolveDependencies(const QList<PluginSpec *> &specs)
{
    // 1. 先建 name -> spec 的索引
    QHash<QString, PluginSpec *> byName;
    for (PluginSpec *s : specs)
        byName.insert(s->name(), s);
    // 2. 逐条校验依赖是否存在、版本是否满足
    for (PluginSpec *s : specs) {
        for (const PluginDependency &dep : s->dependencies()) {
            PluginSpec *target = byName.value(dep.name);
            if (!target) {
                if (dep.type == PluginDependency::Required) {
                    s->setError(QStringLiteral("missing required plugin: %1")
                                    .arg(dep.name));
                }
                continue;
            }
            if (!versionSatisfies(target->version(), dep.version)) {
                s->setError(QStringLiteral("version mismatch: %1 needs %2, got %3")
                                .arg(dep.name, dep.version, target->version()));
            }
        }
    }
    // 3. 拓扑排序，顺便把环找出来
    return topologicalSort(specs);
}

版本不满足也归到 setError，后面统一在加载阶段拦下来。这样错误信息集中，不会在半个插件已经起来的进程里乱成一团。

8.6 核心插件为什么特殊 #

Core 插件是宿主，它不依赖任何插件，反而是所有插件的基础。职责有四块：

  • 注册 MimeTypes：定义文件类型处理规则。
  • 主题管理：读 .creatortheme（ini 格式）主题文件，管颜色和调色板。
  • 动作管理：初始化全局命令系统 ActionManager。
  • 主窗口：构建 IDE 的主骨架。

它的 initialize() 就是整个界面搭起来的地方：

cpp
bool CorePlugin::initialize(const QStringList &arguments, QString *errorMessage)
{
    Q_UNUSED(arguments)

    // 1. 注册 MimeTypes
    registerMimeTypes();

    // 2. 初始化主题
    if (!loadTheme(QStringLiteral("default"), errorMessage))
        return false;

    // 3. 初始化动作管理器
    new ActionManager(this);

    // 4. 创建主窗口
    m_mainWindow = new MainWindow;
    if (!m_mainWindow->init(errorMessage))
        return false;
    m_mainWindow->show();

    return true;
}

返回 false 就是告诉管理器「这个插件起不来」。核心插件返回 false，整个程序该退出，别硬撑。

九、插件与主程序的边界 #

插件和主程序跑在同一个地址空间。这是 C++ 插件全部优势的来源，也是全部风险的来源。

  • 好处：接口指针直接调，零序列化；插件对象本身就是 QObject，信号槽直接连；共享全局状态，启动快。
  • 风险：插件崩一次，主程序一起完；构建配置差一项，程序起不来；全局状态被污染，谁读谁错。

换条路线的做法是这样：

特性 Qt Creator VS Code
语言 C++（原生） JavaScript / TypeScript
运行模型 共享进程空间（DLL） 独立进程（Extension Host）
通信机制 直接指针调用 / 信号槽 IPC / RPC
性能 高，原生调用 受限 IPC
稳定性 插件崩溃会拖垮整个 IDE 插件崩溃不影响主程序
UI 扩展 ActionManager / QWidget 深度集成 受限的声明式 UI

两个取向很清楚：Qt Creator 押性能和掌控力，原生调用最快，代价是插件作者得有 C++ 底子；VS Code 押隔离，扩展跑在独立进程，卡死也拖不垮界面。

边界上守四条：

  1. 接口只传 Qt 类型、POD、指针。跨编译器传 STL 容器等于赌命。
  2. 谁 new 谁 delete。主程序 new 的对象别让插件 delete，两个堆管理器未必是同一个。
  3. 异常不跨边界。插件里的异常跑到对方的栈帧上，行为未定义。接口统一用返回值加 errorMessage。
  4. 单例不进接口。unload() 之后它就是野指针。

对象池是边界的官方通道：插件把服务对象扔进 allObjects，别的插件遍历取用，谁也不用 include 谁。菜单扩展走同一套思路，插件通过 ActionManager 往主菜单里加东西，核心代码一行不改：

cpp
// 步骤 1：取菜单容器
ActionContainer *mfile = ActionManager::actionContainer(Constants::M_FILE);

// 步骤 2：造 QAction，注册成 Command（快捷键由它统一管）
QAction *open = new QAction(tr("&Open..."), this);
Command *cmd = ActionManager::registerAction(open, Constants::OPEN);
cmd->setDefaultKeySequence(QKeySequence::Open);

// 步骤 3：挂到菜单容器上
mfile->addAction(cmd, Constants::G_FILE_OPEN);

十、版本兼容与 ABI #

ABI 是插件最硬的一道墙。插件和主程序必须用同一编译器、同一位数、同一 Qt 版本编出来。差一样，加载时就报这句话：

text
Cannot load library ...: The plugin 'xxx' uses incompatible Qt library.
Expected build key "Windows msvc2019 64 bit release",
got "Windows mingw 64 bit debug"

build key 是 Qt 编进库里的指纹，由平台、编译器、位数、debug/release、Qt 版本拼成。QPluginLoader 加载前先比这串字符，对不上直接拒绝。

失配点 症状 排查入口
编译器不同（MSVC 对 MinGW） incompatible Qt library 读 build key 里的编译器名
位数不同（x86 对 x64） incompatible 或找不到符号 读 build key 里的位数
Qt 版本不同（5.12 对 5.15） incompatible Qt library 两边的 Qt 路径是不是同一个
debug 与 release 混用 incompatible Qt library 读 build key 末尾的 release/debug
编译器小版本不同（2017 对 2019） 加载通过，一调虚函数就崩 统一工具链版本

还有一类不报 build key 的：接口本身改了（加虚函数、改参数类型、加成员）。库能加载，一调就崩。这类只能靠版本化接口来防，第四节那套 IPlugin2 就是干这个的。

十一、调试插件加载失败 #

先认清卡在哪一步：

现象 卡点 先查什么
metaData() 返回空对象 文件根本不是 Qt 插件 有没有 Q_PLUGIN_METADATA，CONFIG += plugin 加没加
instance() 空，报 incompatible 构建配置不一致 build key 原文，两边 Qt 版本与编译器
instance() 空，报 cannot load library 依赖库缺失或路径不对 dumpbin /dependents 看缺哪个 dll
instance() 成功但 qobject_cast 空 接口宏没配好 Q_INTERFACES、IID 字符串是否一致
一路通过，调接口就崩 接口布局变了 编译器版本、接口有没有加虚函数

三板斧按顺序来：

  1. 打开插件调试输出。QT_DEBUG_PLUGINS=1 会把每一步的判定全打出来，包含读到的 IID、build key 和失败原因。
  2. 每个失败分支都打 errorString()。它是 QPluginLoader 唯一愿意告诉你的东西。
  3. 依赖缺失就用 dumpbin /dependents xxx.dll（Linux 用 ldd）逐个对，缺的多半是 MSVC 运行时或另一个插件。

打开调试开关的方式：

text
cmd:          set QT_DEBUG_PLUGINS=1
PowerShell:   $env:QT_DEBUG_PLUGINS=1
bash:         export QT_DEBUG_PLUGINS=1

输出长这样，一眼能看出卡在元数据还是 build key：

text
QPluginLoader::load: "/app/plugins/myplugin.dll"
checking metadata of "/app/plugins/myplugin.dll"
Found metadata in lib /app/plugins/myplugin.dll, metadata=
{
    "IID": "org.example.Blog.IPlugin/1.0",
    "className": "MyPlugin",
    "MetaData": { "Name": "MyPlugin" },
    "version": 331520
}
Got keys from plugin meta data ("MyPlugin")
loaded library "/app/plugins/myplugin.dll"

注意最后一行有没有出现。没有 loaded library，说明库根本没进内存，问题在文件或依赖；有却没有对象，问题在接口宏。

十二、易错点速查 #

症状 根因 修法
qobject_cast 恒为空 漏了 Q_INTERFACES 在实现类类体里补上，重新 moc
qobject_cast 恒为空 IID 字符串两处不一致 定义成宏，两边引同一个
编译报 IID 未声明 漏了 Q_DECLARE_INTERFACE 在接口头文件类定义后补上
链接报 qt_metacall 未定义 实现类漏了 Q_OBJECT 补 Q_OBJECT，重新 qmake/cmake
读元数据读出空字符串 字段在 MetaData 之下 先取 MetaData 再取字段
改了 JSON 没生效 元数据是编译期固化的 重编插件，别只换磁盘文件
加载报 incompatible 编译器、位数、Qt 版本、debug/release 任一不同 用同一套工具链和同一个 Qt
加载成功但一调就崩 接口加了虚函数 新开接口继承老接口，用 qobject_cast 探测
主程序退出时崩溃 unload() 时还有对象活着 先 shutdown()，再删对象，最后 unload()
启动白屏几秒 重活塞在 initialize() 挪进 delayedInitialize()

记住三句话就够了：元数据决定「认不认得出」，接口宏决定「转不转得出去」，ABI 决定「跑不跑得起来」。三关任一关没过，插件都只是个躺在目录里的文件。
