本篇的边界：只讲 QObject 这个基类本身——它带来什么、对象树怎么管内存、元对象系统怎么支撑类型转换、生命周期有哪几道坎。信号槽的连接与分发放在《Qt 信号与槽机制》，事件循环的队列与派发放在《Qt 事件处理》，本篇只在 Q_OBJECT 宏和 deleteLater 两处点到为止。

不涉及：QML 的对象所有权、QWidget 的布局系统、QThread 的线程模型细节。这些各有专门的文章。本篇出现的所有 QWidget 代码只是举例，逻辑一律以 QObject 为准。

读法：如果你只想知道「为什么我的程序 delete 之后崩了」，直接跳到第三章和第十二章。如果你想搞清 qobject_cast 为什么比 dynamic_cast 快，看第七章。

一、QObject 是什么 #

QObject 是 Qt 里几乎所有类的根。QWidget、QMainWindow、QPushButton 这些界面控件继承它，QThread、QTimer、QTcpSocket、QFile 这些非界面类同样继承它。你在 Qt 里随手 new 出来的东西，十有八九能往上追到一个 QObject。

这个统一基类带来六件事，全部由 QObject 本体提供，跟界面无关：

能力 入口 说明
对象树 parent() / children() / setParent() 一棵可以递归删除的树，半自动内存管理
元对象 metaObject() / QMetaObject 运行期拿到类名、属性、方法、信号槽清单
类型转换 qobject_cast<T>() 不依赖编译器 RTTI 的向下转型
属性系统 setProperty() / property() 运行期按名字读写属性，含动态属性
信号槽 connect() / disconnect() 对象间解耦通信，本篇不展开
事件 event() / installEventFilter() 对象级事件分发，本篇不展开

再加两件小事：tr() 做国际化翻译，objectName 给对象起个字符串名字供查找。这两件看着不起眼，但 findChild 和 QSS 都靠 objectName 定位，用得上。

一个类只要继承 QObject，就自动接入这套体系。代价是它必须遵守 QObject 的规矩：不能拷贝、不能按值塞进容器、构造时确定线程归属。后面第十一章专门讲这些限制。

继承链的最顶上就是它：QObject 下面是 QCoreApplication、QTimer、QThread 这些非界面类，另一条支路是 QWidget——界面类的分水岭，再往下分出 QFrame、QLabel、QPushButton。你写的每个 Qt 子类，最终都挂在同一个根上。

QWidget 之所以特殊，是它在 QObject 的对象树之上又叠了一层几何关系：控件有位置、有大小、会在父控件的坐标系里画自己。但那套东西仍然是挂在 QObject 的 parent/children 上的，setParent() 一样管用，children() 一样能取到子控件。

最朴素的用法：

cpp
#include <QObject>

int main()
{
    QObject *parent = new QObject();
    QObject *child = new QObject(parent);   // 构造时把 parent 传进去

    delete parent;                          // child 跟着一起没
    return 0;
}

这段代码里没有一行 delete child，但它确实被释放了。这就是对象树在干活。

QObject 内部并不直接存这些成员，它握着一个 d_ptr 指向 QObjectData（实际是 QObjectPrivate）。父指针、子对象列表、当前线程、是否已被标记删除，全在私有数据里。这个设计让 QObject 的公开头文件在版本之间保持二进制兼容——Qt 加字段不用动你的 sizeof。对我们写业务代码的人来说，结论只有一条：QObject 的大小和布局不是你能假设的，别拿它做 memcpy，别把它当 POD。

二、对象树：parent 与 children #

每个 QObject 最多有一个父对象，可以有任意多个子对象。这个「一父多子」的关系构成一棵树，根是没有父对象的那些对象。

接口就这几个：

接口 签名 作用
取父 QObject *parent() const 没有父返回 nullptr
取子 const QObjectList &children() const 直接子对象列表，不含孙子
设父 void setParent(QObject *parent) 换父；会先把自己从旧父摘掉
判归属 bool isWidgetType() const 是否是 QWidget 派生
判祖先 bool isAncestorOf(const QObject *child) const 沿父链往上查
打树 void dumpObjectTree() 调试用，把整棵树打到 stderr
打信息 void dumpObjectInfo() 调试用，打连接信息

建立父子关系有两条路，效果一样，写法不同：

cpp
// 路子一：构造时传 parent，一步到位
auto *btn = new QPushButton("确定", this);

// 路子二：先造出来，稍后再认父
auto *btn2 = new QPushButton("取消");
btn2->setParent(this);

构造函数那条路更好，原因是它有初始化顺序上的保证：QObject(parent) 在基类构造阶段就完成了挂接，等派生类的构造函数体开始执行时，children() 里已经有它了。用 setParent() 则意味着对象存在过一小段「没有父」的时间，这段时间里别人 findChild 找不到它，也不受任何树保护。

setParent() 的行为比名字看起来多一点：

cpp
QObject *a = new QObject();
QObject *b = new QObject();
QObject *c = new QObject(a);

c->setParent(b);        // c 从 a 的子列表里被摘掉，挂到 b 下面
// 此时 a->children() 空，b->children() 里是 c

c->setParent(nullptr);  // 脱离对象树，从此没人替你删它

最后一行是个分水岭。setParent(nullptr) 之后，这个对象就是「孤儿」：没有父，也就没有人为它的内存负责，你得自己 delete，或者交给 std::unique_ptr。很多人写代码时随手脱父，然后在退出时发现一堆泄漏，根子就在这里。

setParent() 还会检查线程：

cpp
// 跨线程挂父会失败，Qt 在调试输出里给警告：
// QObject::setParent: Cannot set parent, new parent is in a different thread

对象树不跨线程。一个 QObject 的线程归属在它构造时就定了（thread() 返回创建它的那个线程），子对象必须和父对象在同一个线程。想让工作对象归到别的线程，要用 moveToThread()，而且只能在对象还没有父对象的时候搬——有父的对象搬不动，父链会把它拽回去。

这条限制的实战含义：后台线程里 new 出来的 QObject，别往界面对象的树上挂。挂不上，挂了也是隐患。

QWidget 上还有一层容易混的东西：QWidget::parentWidget() 返回的是「父控件」，类型是 QWidget *；QObject::parent() 返回的是「父对象」，类型是 QObject *。绝大多数时候两者指同一个对象，但如果你把一个非 QWidget 的 QObject 设成了某个控件的父，parent() 能拿到它，parentWidget() 拿不到（它只认 QWidget）。界面代码里用 parentWidget()，通用逻辑里用 parent()。

树是活的，对象进出都会即时反映到列表里：

cpp
QObject *root = new QObject();
QObject *n1 = new QObject(root);
QObject *n2 = new QObject(root);
QObject *leaf = new QObject(n1);

qDebug() << root->children().size();   // 2，只有 n1 和 n2
qDebug() << n1->children().size();     // 1，是 leaf
qDebug() << root->isAncestorOf(leaf);  // true，隔代也算

children() 返回的是直接子对象，不含孙子。要找孙子，得写递归，或者用第五章的 findChildren() 加递归选项。

dumpObjectTree() 值得在调试时多用，输出会把整棵树按缩进打出来，每行带类名和 objectName。花十秒钟看一眼，能省半小时猜「这个控件到底挂在谁下面」。它走 qDebug()，得跑在能看到调试输出的环境里。

对象树的存在价值不止内存管理。它同时是：

  • 归属声明：这个按钮属于这个窗口，窗口关掉按钮就该消失。
  • 查找索引：findChild 靠树遍历找对象。
  • 事件传播路径：事件先从子对象往父对象传。
  • 样式作用域：QSS 的选择器沿树生效。
  • 线程约束的载体：父链决定了一个对象不能乱跑。

这五件事共用一套结构，是 Qt 设计里省事的地方，也是它偶尔让人困惑的地方——你动一次 setParent()，五件事的语义一起变。

三、对象树怎么管内存 #

先把结论摆出来：Qt 的对象树是半自动内存管理，不是垃圾回收。

半自动的意思是：父对象销毁时，递归删掉所有子对象；但谁删父对象，Qt 不管。树的根节点仍然要你自己 delete，或者把它挂在某个会被自动清理的容器、某个栈对象、某个 main 里的局部变量上。

递归删除的机制在 QObject 的析构函数里：

cpp
// 简化示意，不是 Qt 源码原文，只表达顺序
QObject::~QObject()
{
    emit destroyed(this);        // 先通知外界：我要没了
    disconnectAll();             // 断开所有相关连接
    removeFromParentChildren();  // 从父的子列表里摘掉自己
    deleteChildren();            // 逐个 delete 子对象（子对象再递归）
}

四步的顺序有实际影响：

  1. destroyed 信号在析构早期发出。这时候派生类那部分已经析构完了（派生类析构函数先跑），所以在槽里调这个对象的成员函数是危险的。
  2. 断开连接在删子对象之前。对象没了，指向它的连接必须先失效，否则后续任何一次信号发射都会打到已释放的内存上。
  3. 摘除自己要在删子对象之前。否则父对象的列表里留着一个已死的指针。
  4. 删子对象是最后一步，也是递归的入口。

注意第 4 步的实现细节：deleteChildren() 遍历 children 列表逐个 delete，而每个子对象析构时又会把自己从父的列表里摘掉。列表在遍历过程中被修改，Qt 对此做了处理。但这个处理顺序不是你要依赖的东西——别写依赖「子对象按创建顺序析构」的代码，哪个先没是没有契约保证的。

栈上的对象是最大的坑：

cpp
void bad()
{
    QObject parent;                     // 栈上
    QObject *child = new QObject(&parent);   // 堆上，挂在栈对象底下
    // 函数返回，parent 的析构函数跑，child 被 delete —— 到这一步还没错
}

void worse()
{
    QObject parent;                     // 栈上
    QObject childStack;                 // 也是栈上
    childStack.setParent(&parent);      // 灾难：把栈对象挂进了树

    // 函数返回，析构顺序：先 childStack（后构造先析构），
    // 然后 parent 析构时，它的 children 列表里还有一个 &childStack，
    // 于是对着已经析构过的栈内存再 delete 一次 —— double free，直接崩
}

第一段代码是合法的：栈对象当父，堆对象当子，父析构时删子，干净利落。

第二段是错的：栈上的对象不能有父对象。因为栈对象的生命周期由作用域管，而它一旦成了别人的 child，父对象析构时就会来 delete 它。一块栈内存被 delete，行为是未定义的——轻则崩溃，重则把相邻内存踩烂，错误现场跑到几百行之外。

这条规矩可以压成一句话：

谁在栈上，谁就不能有 parent。 栈对象可以有 children，但 children 必须是堆上的；栈对象自己绝不能挂到别人的树上。

第二条规矩同样重要：一个堆对象只能有一个主人。

cpp
QObject *parent = new QObject();
QObject *child = new QObject(parent);
std::unique_ptr<QObject> guard(child);   // 错误：两个主人
// parent 析构时 delete child，guard 也会 delete child —— 双删

QObject *parent2 = new QObject();
QObject *child2 = new QObject();
std::unique_ptr<QObject> guard2(child2);
child2->setParent(parent2);              // 错误：还是两个主人

QObject 和智能指针混用，前提是所有权只归一边。要么交给对象树，要么交给智能指针，不能两边都交。

这套机制和智能指针的差别，值得用一张表定下来：

维度 Qt 对象树 std::unique_ptr std::shared_ptr
所有权表达 隐式，挂在 parent 上 显式，独占 显式，共享计数
释放触发 父对象析构时递归 指针离开作用域 最后一个引用消失
能管栈对象 不能（会 double free） 能 能（需自定义 deleter）
能管数组 能（逐个 delete） 需 unique_ptr<T[]> 需自定义 deleter
运行期开销 每个对象一个指针 + 一个列表节点 零 控制块 + 原子计数
支持换父 能，setParent() 不能 不能
支持查找 能，findChild 不能 不能
循环引用 会互相吊住，需人工打破 不会 会，需 weak_ptr
典型用途 GUI 控件、长生命周期对象 局部资源 共享数据

对象树的独特价值在前两列拿不到的东西：它是一棵可查询、可遍历、可重新挂接的树。unique_ptr 只管生死，不管结构。界面程序需要的恰恰是结构——一个对话框被关掉，它底下几十个控件、布局、定时器、动画对象应该一起走，谁也不用记清单。这就是对象树存在的理由。

但别把它当成 GC。它没有可达性分析，不知道谁还引用着谁，也不会在你忘记删根节点时兜底。根节点一定得有人管。

三条实践规则，按优先级排：

cpp
// 规则一：界面对象、长生命周期对象，一律挂树
auto *label = new QLabel("温度", this);
auto *timer = new QTimer(this);

// 规则二：根节点交给栈或者明确的 delete
int main(int argc, char *argv[])
{
    QApplication app(argc, argv);
    MainWindow w;            // 栈上，程序退出自动析构，整个树跟着走
    w.show();
    return app.exec();
}

// 规则三：临时资源用智能指针，别硬塞进树
auto buf = std::make_unique<QByteArray>(1024, 0);

规则二那三行是 Qt 程序最常见的骨架。MainWindow w 在栈上，app.exec() 返回后 w 析构，w 的所有子控件递归销毁。你一行 delete 都不用写，也不需要写。反过来说，如果你写成 auto *w = new MainWindow;，那就得有人负责删它——很多「关闭窗口后进程不退」的问题，根子就是主窗口没删干净或者还有对象活着。

四、构造与析构的顺序 #

对象树能工作，靠的是 C++ 构造与析构的确定性顺序。顺序记错，父子关系就挂不上，或者挂上了删不掉。

构造是从基类往派生类走：

cpp
class MyWidget : public QWidget
{
    Q_OBJECT
public:
    explicit MyWidget(QWidget *parent = nullptr)
        : QWidget(parent)          // 第 1 步：QWidget 构造，内部再调 QObject(parent)
    {
        // 第 2 步：到这里，this 已经挂在 parent 的 children 里了
        auto *btn = new QPushButton("开始", this);
        auto *lab = new QLabel("就绪", this);
        // 第 3 步：构造体结束，对象完整可用
    }
};

关键在于第 1 步。成员初始化列表里调 QWidget(parent)，一路调到 QObject(parent)，父子关系在基类构造阶段就建立了。所以派生类构造体里做任何事，this 都已经是树上的一个节点，children() 已经能正常工作。

如果你漏了初始化列表：

cpp
explicit MyWidget(QWidget *parent)   // 忘了写 : QWidget(parent)
{
    // this 现在是孤立节点，parent 完全不知道自己有这个孩子
}

后果不立刻显现，但要命：MyWidget 显示出来的时候会是个独立窗口，parent 关掉时它不会跟着关，析构时它也不会被删。这类 bug 不看初始化列表根本发现不了。写 Qt 子类，构造函数第一行永远是转交 parent。

析构是从派生类往基类走，方向正好相反：

cpp
class MyWidget : public QWidget
{
public:
    ~MyWidget() override
    {
        // 第 1 步：派生类析构体先跑
        // 此时 children 还在！btn、lab 都还活着，还能访问
    }
    // 第 2 步：派生类成员析构
    // 第 3 步：~QWidget()
    // 第 4 步：~QObject() —— 发 destroyed、断连接、删 children
};

第 1 步那个「children 还在」是很多人不知道的事实。在派生类析构函数体里，this->children() 返回的列表是完整的，子对象一个都没少。这给了你一个清理窗口：

cpp
~MyWidget() override
{
    // 想在子对象被删之前做点什么，写在这里
    // 比如保存状态、停掉定时器、断开和外部对象的连接
}

但别在这里 delete 子对象。它们会被 ~QObject() 删，你再删一次就是 double free。真要提前删某个子对象，用 child->setParent(nullptr) 脱父，之后自己管——或者干脆别提前删。

destroyed 信号发得很早，在派生类析构体已经跑完之后：

cpp
// 用法：监听某个对象即将消失
connect(obj, &QObject::destroyed, this, [](QObject *who) {
    qDebug() << "对象没了：" << who;
    // 此时 who 的派生部分已析构，只能拿它当 QObject 用
});

这个信号的价值在于「有人要没了的通知」。它比 QPointer 更早，比手写清理更可靠。但它发出时对象已经半死，别在里面调派生类的成员函数，也别访问它的成员变量。

还有一条 C++ 规则要留意：构造函数里调虚函数，执行的是当前这一层的版本，不是子类重写的版本。构造到基类那一层时，子类部分还不存在，虚表指针还指着基类的虚表。所以「需要多态的初始化」别塞进构造函数，交给构造完成之后的显式 init() 调用。

规矩很简单：构造函数里只做「这一层能做完的事」，需要多态的初始化放到构造完成之后，或者用一个显式的 init() 由调用方在对象建好后调用。

五、对象的查找：findChild 与 findChildren #

树建起来是为了查。QObject 给了两个模板函数，按类型和名字在树里找对象：

cpp
// 找一个，返回第一个匹配；找不到返回 nullptr
template <typename T>
T findChild(const QString &name = QString(),
            Qt::FindChildOptions options = Qt::FindChildrenRecursively) const;

// 找一批，返回列表（空列表表示没找到）
template <typename T>
QList<T> findChildren(const QString &name = QString(),
                      Qt::FindChildOptions options = Qt::FindChildrenRecursively) const;

两个参数都可以省。省了类型就按 QObject，省了名字就不看名字：

cpp
// 1. 按类型 + 名字找
auto *btn = findChild<QPushButton *>("okButton");
if (btn) btn->setEnabled(false);

// 2. 按类型找（第一个）
auto *anyButton = findChild<QPushButton *>();

// 3. 按名字找（不限制类型）
auto *byName = findChild<QObject *>("okButton");

// 4. 找全部
QList<QPushButton *> all = findChildren<QPushButton *>();
for (auto *b : all) b->setEnabled(true);

名字这一维匹配的是 objectName 属性。这个属性默认是空字符串，意味着你没设名字的对象用名字查不到：

cpp
auto *btn = new QPushButton("确定", this);
btn->setObjectName("okButton");        // 少了这行，下面查不到
// ...
auto *found = findChild<QPushButton *>("okButton");   // found != nullptr

objectName 还有个别的作用：QSS 用 #okButton 选择器定位控件，QDesigner 用它生成代码，自动化测试用它点按钮。给要查的对象起个名字是 Qt 里的基本习惯。

查找范围由 Qt::FindChildOptions 控制，只有两个值：

选项 含义
Qt::FindChildrenRecursively 递归整棵子树，默认值
Qt::FindDirectChildrenOnly 只看直接子对象，不往下钻 
cpp
// 只看直接子对象，快，且结果可预测
auto direct = findChildren<QWidget *>(QString(), Qt::FindDirectChildrenOnly);

递归是默认行为，也是性能陷阱的来源。一个界面里有几百个控件时，findChild 每次都要遍历子树。写在 paintEvent 或者循环里，开销就出来了。省事的做法是构造时查一次，把指针存成成员变量，之后不再查。

findChild 还有两个必须记住的行为：

找不到时返回 nullptr，不是抛异常，不是返回个空壳对象。所以每次用完都要判空，或者用 if (auto *p = findChild<T *>(...)) 的写法把判空和取值合成一句。

名字匹配是精确字符串比较，区分大小写，不支持通配符。"okButton" 和 "okbutton" 是两个不同的名字。

类型这一维靠 qobject_cast 实现，也就是第七章那套元对象转换。这意味着用 findChild 找的类型必须有 Q_OBJECT 宏，否则一律返回 nullptr。

findChildren 拿来批量操作很顺手：

cpp
// 把所有 QLineEdit 清空
for (auto *e : findChildren<QLineEdit *>())
    e->clear();

// 按名字前缀筛（不支持通配符，得自己过一遍）
for (auto *w : findChildren<QWidget *>()) {
    if (w->objectName().startsWith("opt_"))
        w->setEnabled(false);
}

排查「界面上多了个不该有的控件」这类问题，dumpObjectTree() 一遍就能看出它挂在谁底下。比自己翻 new 的地方快得多。

一个坑：findChild 返回的指针没有生命周期保证。你查到了某个对象，不代表它会一直活着。如果它会在别处被删，用 QPointer 接住（第十章），别存裸指针。

六、Q_OBJECT 宏与 moc #

Q_OBJECT 是个空宏。你在类定义里写它，编译器什么也不做；真正干活的是 moc——元对象编译器，一个在编译前跑一遍的代码生成器。

cpp
class Counter : public QObject
{
    Q_OBJECT                       // 必须写在类定义体的最前面
public:
    explicit Counter(QObject *parent = nullptr) : QObject(parent) {}
signals:
    void changed(int value);
public slots:
    void bump();
};

moc 读这个头文件，生成 moc_counter.cpp，里面塞了这些东西：

  • Counter::staticMetaObject：一个 QMetaObject 静态实例，装着类名、父类元对象指针、属性表、方法表、信号表、枚举表。
  • Counter::metaObject()：虚函数重写，返回上面那个静态实例。
  • Counter::qt_metacast()：按类名字符串做转换，qobject_cast 和 findChild 靠它。
  • Counter::qt_metacall()：按索引调用方法，信号槽的连接与分发靠它。
  • Counter::tr()：翻译函数。
  • 信号函数的实现体（信号只有声明，实现由 moc 生成）。

这些生成物加上你的类，构成「元对象系统」。它在运行期是一张可查询的表，不是编译器魔法：

cpp
const QMetaObject *mo = obj->metaObject();
qDebug() << mo->className();                    // "Counter"
qDebug() << mo->superClass()->className();      // "QObject"
qDebug() << mo->methodCount();                  // 方法总数（含信号槽）
qDebug() << mo->indexOfSignal("changed(int)");  // 信号的下标，找不到返回 -1

既然 Q_OBJECT 靠 moc 生成文件，它的使用就有几条硬规矩：

一、必须写在类定义体的第一行（注释和 public: 之前）。moc 认位置，写别处生成的东西对不上。

二、类必须直接或间继承自 QObject。 Q_OBJECT 展开后要重写 metaObject() 这类虚函数，没有 QObject 基类就没有可重写的东西，编译直接报错。

三、必须放在头文件里。 moc 扫描头文件，生成的文件要参与编译。把带 Q_OBJECT 的类写在 .cpp 里，得手工 #include "xxx.moc"，而且容易漏。

四、一个类只能有一个 Q_OBJECT。 派生类各自写各自的，别在子类里重复父类的。

五、模板类不能带 Q_OBJECT。 moc 不支持类模板，写了也生成不出东西。

六、signals / slots / emit 是宏，moc 认得，编译器不认。它们最终被展开成 public / 空，所以别拿它们当关键字用在别处。

CMake 里要开 AUTOMOC，让构建系统自动跑 moc：

text
set(CMAKE_AUTOMOC ON)
add_executable(app main.cpp counter.cpp counter.h)

AUTOMOC 会扫所有参与编译的头文件，发现 Q_OBJECT 就生成 moc 文件并塞进构建。忘了开它会报一堆「undefined reference to vtable for Counter」——这个报错几乎总是意味着 moc 没跑，不是你的代码写错了。

漏写 Q_OBJECT 会怎样？这是最容易踩的坑，因为代码能编译，问题在运行期才暴露：

症状 原因
qobject_cast<MyClass *>(obj) 返回 nullptr 元对象里没有 MyClass，转换失败
findChild<MyClass *>() 永远为空 同上，查找也走 qobject_cast
connect 编译不过或返回 false 信号没有 moc 生成的实现体
tr("...") 报找不到成员 tr() 由 moc 生成
obj->metaObject()->className() 返回父类名 元对象指针还指着基类
属性系统读不到 Q_PROPERTY 属性表没生成

其中「编译能过、运行不对」最坑，因为没有任何警告。判断方法很直接：只要这个类要用信号槽、要用 qobject_cast、要用 tr()、要用 Q_PROPERTY，它就必须有 Q_OBJECT。

信号槽的机制本篇不展开，只说清一件事：connect 的第五个参数（连接类型）决定调用是同步还是排进队列，那是《Qt 信号与槽机制》的内容。本篇只需要你记住——没有 Q_OBJECT，信号槽体系在运行期是断的。

七、qobject_cast：Qt 的类型转换 #

C++ 有 dynamic_cast，为什么 Qt 还要造一个 qobject_cast？

看用法：

cpp
QObject *obj = findChild<QObject *>("someWidget");

// Qt 的写法
if (auto *btn = qobject_cast<QPushButton *>(obj)) {
    btn->setText("点了");
}

// C++ 的写法
if (auto *btn2 = dynamic_cast<QPushButton *>(obj)) {
    btn2->setText("点了");
}

两段代码功能等价，区别在实现和约束。qobject_cast 走元对象系统：

cpp
// qobject_cast 的本质是调这个虚函数（简化示意）
void *QObject::qt_metacast(const char *clname)
{
    if (!clname) return nullptr;
    if (!strcmp(clname, "QPushButton")) return this;     // 命中自己
    return QWidget::qt_metacast(clname);                 // 继续往父类问
}

它做的事是：沿着继承链一层层比较类名字符串。命中就返回指针，走到 QObject 还没命中就返回 nullptr。

dynamic_cast 走的是编译器生成的 RTTI 类型图，要在运行期做一次完整的类型关系判定，部分实现还要处理跨虚基类的指针偏移。

两者摆在一起：

维度 qobject_cast dynamic_cast
依赖 元对象系统（Q_OBJECT + moc） 编译器 RTTI（typeid 那套）
速度 快：沿父链做字符串比较，无堆分配 慢：运行期类型图判定
需要 RTTI 开关 不需要，-fno-rtti 也能编 需要，关掉 RTTI 直接编不过
类型要求 双方都得是 QObject 派生，且目标类有 Q_OBJECT 任意多态类型
失败行为 返回 nullptr（指针）/ 抛 bad_cast（引用不支持） 返回 nullptr（指针）/ 抛 bad_cast（引用）
跨动态库 可靠，只比类名字符串 依赖编译器与 RTTI 符号一致性，跨编译器易出问题
接口类转换 需 Q_DECLARE_INTERFACE + Q_INTERFACES 不适用（非 QObject 也可）
能否转非 QObject 类型 不能 能

「比 dynamic_cast 快」不是玄学。qobject_cast 干的事是几次 strcmp 加几次虚调用，继承深度很少超过十层；dynamic_cast 要做类型图的运行期搜索，某些实现里还有缓存和锁。在信号槽、属性系统、findChild 这些高频路径上，这个差距会被放大——Qt 内部到处用 qobject_cast，正是因为它够轻。

代价是约束更严：

cpp
class Plain { };                          // 不是 QObject
class NoMacro : public QObject { };       // 是 QObject，但没有 Q_OBJECT

auto *p = qobject_cast<Plain *>(obj);     // 编译错误：不是 QObject 派生
auto *n = qobject_cast<NoMacro *>(obj);   // 编译能过，运行永远返回 nullptr

第二行是最容易困惑的：编译期不报错，运行期静默失败。原因就是 NoMacro 的元对象里没有自己的类名，qt_metacast 里没有那条 strcmp 分支。

接口类的转换要额外声明：

cpp
class IPlugin
{
public:
    virtual ~IPlugin() = default;
    virtual QString name() const = 0;
};
Q_DECLARE_INTERFACE(IPlugin, "com.example.IPlugin/1.0")

// 实现类里声明实现了哪些接口
class MyPlugin : public QObject, public IPlugin
{
    Q_OBJECT
    Q_INTERFACES(IPlugin)          // 把接口登记进元对象
public:
    QString name() const override { return "my"; }
};

// 之后就能转
auto *iface = qobject_cast<IPlugin *>(obj);   // 走 Q_INTERFACES 登记表

注意那个 IID 字符串 "com.example.IPlugin/1.0"：它是接口的唯一标识，两边必须一字不差。插件系统全靠这个字符串在运行期认出对方实现了哪个接口，这段细节放在《Qt 插件系统》。

实际代码里，判空和取值合成一句最省事：

cpp
if (auto *btn = qobject_cast<QPushButton *>(w))
    btn->click();

别写成 qobject_cast<QPushButton *>(w)->click()。转失败返回 nullptr，这一行就是空指针解引用。处理事件或者遍历 children() 时最容易踩——列表里混着各种类型，你不确定下一个是什么。

八、动态属性 setProperty #

QObject 有一张属性表，运行期能按名字读写。表里的属性分两种：编译期用 Q_PROPERTY 声明的静态属性，和运行期用 setProperty() 塞进去的动态属性。

先看静态属性：

cpp
class Meter : public QObject
{
    Q_OBJECT
    Q_PROPERTY(int level READ level WRITE setLevel NOTIFY levelChanged)
public:
    int level() const { return m_level; }
    void setLevel(int v) { m_level = v; emit levelChanged(v); }
signals:
    void levelChanged(int);
private:
    int m_level = 0;
};

// 按名字访问，编译期不认识这些字符串
Meter m;
m.setProperty("level", 42);
qDebug() << m.property("level").toInt();   // 42

再看动态属性，也就是没有 Q_PROPERTY 声明、直接写进去的：

cpp
QObject *obj = new QObject();
obj->setProperty("role", "admin");         // 表里没有 role，就新建一条
obj->setProperty("retries", 3);

qDebug() << obj->property("role").toString();        // "admin"
qDebug() << obj->property("retries").toInt();        // 3
qDebug() << obj->dynamicPropertyNames();             // ("role", "retries")
qDebug() << obj->property("nope").isValid();         // false，读不存在的属性

几条行为要记住：

  • property() 读不存在的名字，返回一个无效的 QVariant（isValid() 为 false），不是空字符串，不是 0。取值前先查 isValid()。
  • 动态属性存在一张哈希表里，每个对象一份。塞几十个属性会让每个对象变大，别拿它当万能容器。
  • 动态属性不触发 NOTIFY 信号，也没有 READ/WRITE 的访问控制。
  • setProperty() 传无效 QVariant 会删掉这条属性。

动态属性最实用的场景是给界面对象贴标签，然后让 QSS 按标签换样式：

cpp
btn->setProperty("state", "error");

// 样式表里这样写：
// QPushButton[state="error"] { color: white; background: #c0392b; }
// QPushButton[state="ok"]    { color: white; background: #27ae60; }

改完属性要让它重新套用样式：

cpp
btn->setProperty("state", "ok");
btn->style()->unpolish(btn);           // 先卸掉旧样式
btn->style()->polish(btn);             // 再套新的

少了 unpolish/polish 这两句，样式不会刷新。这个坑跟属性系统无关，属于 QSS 的刷新机制，但几乎每个用动态属性做换肤的人都会踩一次。

QMetaObject 还能反过来查属性表，用 propertyCount() 加 property(i) 逐个取出 QMetaProperty，读名字和类型。这段只遍历静态属性，动态属性不在 QMetaObject 里，得用 dynamicPropertyNames() 单独取。两种属性表在实现上是分开的。

九、deleteLater 与对象生命周期 #

deleteLater() 的用途就一句话：让事件循环在回到主循环之后才删这个对象。

先看它解决什么问题：

cpp
class Worker : public QObject
{
    Q_OBJECT
public slots:
    void onClicked()
    {
        delete this;              // 错：正在执行自己的成员函数，把自己删了
        // 这行之后，this 指向已释放内存，函数体剩下的代码全在裸奔
    }
};

delete this 在成员函数里执行时，this 的内存立刻失效，但函数还没返回。函数体后面的代码、函数返回时的栈展开、vtable 的访问，全部落在已释放的内存上。行为未定义，崩不崩看运气。

同样的坑出现在信号里：

cpp
// 错误：在槽里删掉了信号的发送者
connect(btn, &QPushButton::clicked, this, [btn]() {
    delete btn;                  // 槽函数执行中，发送者被销毁
});

clicked 是 btn 发出的，Qt 正在遍历这个信号的连接列表，你去把 btn 删了，连接列表连同 btn 一起没了。轻则崩溃，重则在别的对象上继续遍历已释放内存。

正确写法只有一句：

cpp
void onClicked()
{
    deleteLater();               // 记个账：等事件循环回来再删我
    // 函数体剩下的代码照常执行，this 仍然可用
}

deleteLater() 做的事是往事件队列里投递一个延迟删除事件（QEvent::DeferredDelete）。投递完立刻返回，函数继续跑，对象还活着。等控制权回到事件循环，队列处理到这个事件，才真正 delete。

几个必须知道的行为：

一、删不掉的情况。 如果对象所在的线程没有跑事件循环，那个事件永远不会被处理，对象也就永远不会被删。这种情况在纯计算的后台线程里会碰到——线程函数跑完就退，队列里的删除事件不了了之。这也是内存泄漏的一个隐蔽来源。

二、可以重复调用。 第一次延迟删除事件被处理、对象被删时，队列里还没处理的、发给这个对象的事件会被一并清掉。所以连调三次 deleteLater() 只会析构一次，不会 double free。

三、跨线程删除是安全的。 deleteLater() 保证对象在它自己所属的线程里被删除。这一点比 delete 强得多——在 A 线程 delete 一个属于 B 线程的 QObject，等于在错误的线程里跑析构函数，而它要碰的东西只有 B 线程才该碰。

四、删之前还有窗口期。 从调用 deleteLater() 到真正删除之间，对象仍然活着、仍然能响应信号。想避免这段时间的行为，先 disconnect() 再 deleteLater()。

五、和 delete 不能混用。 调了 deleteLater() 之后再 delete 一次，就是双删。反过来，delete 之后那个挂起的延迟删除事件还会被处理——它拿着一个已经失效的指针。

destroyed 信号和 deleteLater() 是好朋友：

cpp
QObject *obj = new QObject(this);
connect(obj, &QObject::destroyed, this, [] {
    qDebug() << "确认已销毁";
});
obj->deleteLater();

什么时候必须用 deleteLater()，什么情况可以直接 delete：

场景 做法
在自己成员函数里删自己 必须 deleteLater()
在槽里删信号发送者 必须 deleteLater()
跨线程删别的线程的对象 必须 deleteLater()
删一个正在等事件的对象的子对象 优先 deleteLater()
析构函数里正常回收成员 直接 delete（但要防重复删除）
函数里临时 new 的局部对象 直接 delete，或干脆用栈对象

分界线是：只要删除动作发生在某个对象的方法调用栈里，而那个对象还要用到自己或发送者，就等一等。

十、QPointer 与悬空指针 #

裸指针指向一个被删掉的对象，叫悬空指针。QPointer 专治这个：

cpp
#include <QPointer>

QPointer<QWidget> guard = new QWidget();   // 需要 QObject 派生类型
qDebug() << guard.isNull();                // false，可以当普通指针用

delete guard.data();                       // 或者 guard->deleteLater()
qDebug() << guard.isNull();                // true，自动置空了

它的原理是注册到对象上：对象销毁时，QObject 的析构函数会把所有指向它的 QPointer 置成 nullptr。所以你手里的 QPointer 永远是「要么指着活对象，要么为空」，不存在第三态。

用法上它长得像指针：

cpp
QPointer<QLineEdit> m_edit = new QLineEdit(this);

void doSomething()
{
    if (m_edit)                    // 判空可以当布尔用
        m_edit->setText("ok");
    // 等价写法：if (!m_edit.isNull())
}

什么时候该用：

cpp
// 场景一：持有会被别人删掉的对象
class Panel : public QWidget
{
    QPointer<QLabel> m_status;     // 标签会被别处 deleteLater
};

// 场景二：跨对象的异步引用
QPointer<QObject> self(this);
QTimer::singleShot(500, [self]() {
    if (self) self->setProperty("x", 1);   // 500ms 后对象早没了
});

// 场景三：非父子关系的对象互相持有
QPointer<QMainWindow> m_main;      // 主窗口不是我的子对象，不知道谁删了它

QPointer 的边界要清楚：

项 说明
类型限制 只能指 QObject 派生类，没有 QPointer<int>
线程安全 否，和普通指针一样，跨线程访问要自己加锁
开销 每次赋值都要注册/注销，比裸指针贵；只在必要处用
自动删除 不负责删除，只管观察
数组 不支持 QPointer<T[]>

它和几种相似工具的差别：

工具 语义 对象销毁后
QPointer<T> 弱引用，不拥有 自动置 nullptr
QWeakPointer<T> 弱引用，配 QSharedPointer 用 isNull() 为真
QSharedPointer<T> 共享所有权 计数归零时删
std::unique_ptr<T> 独占所有权 离开作用域删
裸指针 T * 无任何保证 变悬空指针

挑工具的判断很直接：管生死的用 unique_ptr 或者父子关系，只管看的用 QPointer，要共享的用 QSharedPointer。

最后一条容易忘：QPointer 只能接住「通过 QObject 析构路径销毁」的情况。用 delete 删、用 deleteLater() 删，都能被感知；但如果对象是被 free() 掉的、或者内存被别的方式释放，QPointer 不会知道。

十一、对象模型的限制 #

QObject 不是普通的 C++ 类，它换来这套能力的同时，砍掉了几个常规能力。

一、不能拷贝。 QObject 的拷贝构造函数和赋值运算符是禁用的（Q_DISABLE_COPY），你自己的子类也一样不能拷贝。

cpp
QObject a;
QObject b = a;        // 编译错误
b = a;                // 编译错误

原因很硬：元对象里存着类名、连接列表、children 列表，还有一个唯一的对象标识。深拷贝一棵对象树意味着什么？信号槽连接要不要跟着复制？parent 指向谁的副本？这些问题没有统一答案，所以直接禁掉。

要传对象，走指针、引用，或者传值语义的轻量类（QString、QDateTime、QPoint 这些都不是 QObject）。

二、不能按值放进容器。

cpp
QList<MyWidget> list;         // 编译错误：要求可拷贝
QList<MyWidget *> list2;      // 正确：指针
std::vector<std::unique_ptr<MyWidget>> v;   // 也行，但注意别和对象树冲突

三、多继承受限。 QObject 必须是第一个基类，moc 只认它。

cpp
class Good : public QObject, public IPlugin { };   // 正确
class Bad  : public IPlugin, public QObject { };   // moc 生成失败

四、模板类带不了 Q_OBJECT。 这条在第六章说过，限制的后果是：模板类没法用信号槽，也没法被 qobject_cast 识别。要写模板化的 QObject，只能把非模板部分抽成基类。

五、线程归属固定。 对象的线程在构造时确定，children 必须同线程，setParent 跨线程会失败。

六、析构必须在所属线程。 跨线程 delete 是未定义行为，要走 deleteLater()。

七、QObject 只能有一个 Q_OBJECT，且必须在类定义里。 想给已有的第三方 QObject 类加元对象能力，只能包一层。

八、Q_OBJECT 类的定义必须对 moc 可见。 只放在 .cpp 里的类要手工 #include "xxx.moc"。

这些限制合起来说明一件事：QObject 是一套运行时框架的节点，不是值类型。 把它当普通数据类用，处处别扭；把它当框架里的对象用，父子关系、元对象、属性系统才顺。

十二、易错点速查 #

症状 真因 改法
delete parent 后崩在析构里 子对象是栈上的 栈对象不能有 parent，脱父或改用堆
delete parent 后又崩一次 子对象同时被智能指针管着 一个对象只能有一个主人
子控件在父窗口关闭后还在 构造时没传 parent 初始化列表里转交 parent

排查顺序建议按这个走：

cpp
// 第 1 步：把树打出来，看结构是否符合预期
root->dumpObjectTree();

// 第 2 步：确认对象的父是谁、线程是谁
qDebug() << obj->parent() << obj->thread();

// 第 3 步：确认类型转换能成功（不能成功多半是缺 Q_OBJECT）
qDebug() << obj->metaObject()->className();
qDebug() << qobject_cast<MyClass *>(obj);

// 第 4 步：崩溃在析构里，查谁还持有这个对象的指针
// 重点看：智能指针、QPointer、全局变量、lambda 捕获的裸指针

四条规矩收尾，记住这四条，QObject 的坑能避开九成：

  1. 堆对象挂父，栈对象不挂父。 栈对象可以有 children，自己绝不能有 parent。
  2. 一个对象一个主人。 给了对象树，就别再给智能指针。
  3. 在方法栈里删对象，用 deleteLater()。 别在对象还在执行自己代码的时候删它。
  4. 要用元对象能力，就写 Q_OBJECT。 编译能过不代表运行期正确。

对象模型是 Qt 的地基。父子关系管住了内存，元对象撑起了转换和属性，deleteLater 和 QPointer 补上了生命周期里的两个缺口。这三块拼起来，才有后面信号槽、事件、插件那些东西的地盘。
