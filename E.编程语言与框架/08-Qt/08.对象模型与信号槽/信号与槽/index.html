本篇只讲信号与槽这一条线：它解决什么问题、moc 在背后生成了什么、连接语法怎么选、五种连接类型的差别、跨线程为什么静默失败、以及出问题怎么排查。

不讲 QObject 的对象树与所有权细节，不讲事件循环与事件过滤器，不讲插件加载机制——那些在同目录的《QObject 与对象模型》《事件处理》《插件系统》里。

读之前假设你能写基本的 Qt 界面代码，知道 Q_OBJECT 长什么样，见过 connect。

一、信号与槽解决什么问题 #

先看一个最朴素的场景：按钮被点了，窗口要关。谁通知谁？

第一种做法，窗口持有按钮指针，定期问按钮「你被点了吗」。轮询，白烧 CPU，还得自己管状态位。

第二种做法，按钮按住窗口指针，点击时直接调 window->close()。能跑，但按钮必须知道窗口的类型，得 include 窗口的头文件，组件之间互相咬死。换个宿主窗口，按钮的代码跟着改。

信号槽的解法绕开这两条：按钮不认识窗口，它只说一句「我被点了」。谁关心谁自己连上来。

三个概念就位：

  • 信号（signal）：对象状态变化时发出的通知。广播式，发出者不关心有没有人听，也不关心听的人是谁。
  • 槽（slot）：接收信号并执行的成员函数。
  • 连接（connect）：把某个对象的信号绑到另一个对象的槽上。

本质是观察者模式（Observer Pattern），但 Qt 的版本比教科书多两件事。一是连接带调度方式（同线程直连、跨线程排队）。二是接收者销毁时连接自动失效。

第二条比想象中重要。手写观察者最容易踩的坑就是接收者析构了，指针还挂在被观察者的通知列表里，下次一通知直接野指针。Qt 把这条保证做进了基类：~QObject 会遍历所有指向自己的连接，从发送者的连接表里记名摘除。

和回调函数的差别 #

对比项 回调函数 Qt 信号槽
方向 被调用方持有调用方的函数指针，单向 双方都不持有对方，靠 connect 现连
数量 一个信号对一个回调 一个信号可挂任意多个槽
类型安全 取决于 typedef 写得多严 函数指针版编译期检查
解绑 手动置空，容易漏 disconnect 或对象析构自动摘
跨线程 自己造队列、自己加锁 队列连接由 Qt 接管
内省 无 元对象能列出所有信号槽

和对象树的关系，只提一句 #

QObject 的对象树管内存：父对象析构时会销毁全部子对象。所以 GUI 里给控件指定了 parent，就不用手动 delete。

cpp
QDialog *dlg = new QDialog(nullptr);
QPushButton *btn = new QPushButton(dlg);   // dlg 是父对象
delete dlg;                                // btn 跟着销毁，不用手动 delete btn

对象树本身不属于信号槽，但两者在 QObject 里交汇：连接记录挂在发送者的连接表上，接收者析构时反向摘除。父对象、子对象、findChild、findChildren 的细节看同目录《QObject 与对象模型》。

一个能跑的最小例子 #

cpp
QSlider *slider = new QSlider(Qt::Horizontal, this);
QSpinBox *spin = new QSpinBox(this);

QObject::connect(slider, &QSlider::valueChanged, spin, &QSpinBox::setValue);

拖滑块，数字跟着变。没有 include 对方的头文件，没有互相持有，两个控件根本不知道对方存在。

这个「不知道」就是解耦。MVC 里模型改完只需要 emit dataChanged()，视图自己连上来；模型不需要知道有几个视图、视图长什么样、视图还在不在。

二、元对象系统：moc 做了什么 #

第一句话要记住 #

信号槽不是 C++ 语言特性。C++ 的类里没有 signals: 这个访问说明符，emit 也不是关键字。整套东西是 Qt 用「预处理器 + 代码生成」搭出来的：一个叫 moc 的工具扫你的头文件，看到 Q_OBJECT 就生成一个 moc_xxx.cpp，里面塞满了字符串表、索引数组和一个按 ID 分发的 switch。

所以真正的分发点是 moc 生成的 qt_static_metacall，不是 emit。emit 只是一个空宏。

三个前提条件 #

条件 作用 缺了会怎样
继承 QObject（直接或间接） 提供 metaObject()、connect、连接表 编译不过
类声明里写 Q_OBJECT 告诉 moc 这个类要处理 链接期报 undefined reference to vtable for Xxx
构建系统带 moc 规则 生成并编译 moc_xxx.cpp 同上，报错信息里一个信号槽的字都不提

Q_OBJECT 放在类声明最前面最省事，一个类只写一次。写在 .cpp 里的类不行——moc 只扫头文件（以及被 include 进来、带 Q_OBJECT 的 cpp）。加 Q_OBJECT 之后必须重新跑 qmake/cmake，否则 moc 不会重新生成，症状就是明明加了宏还是链接失败。

注意：元对象系统不支持 C++ 模板类。template <typename T> class Foo : public QObject 挂 Q_OBJECT 会出错，signals: 里的模板参数也没法字符串化。要模板化就让非模板基类承载信号，模板子类只做实现。

Q_OBJECT 展开成什么 #

cpp
class MyClass : public QObject {
    // ... 你自己写的成员 ...
    // === Q_OBJECT 展开出的部分 ===
public:
    static const QMetaObject staticMetaObject;
    virtual const QMetaObject *metaObject() const override;
    virtual void *qt_metacast(const char *);
    virtual int qt_metacall(QMetaObject::Call, int, void **);
private:
    static void qt_static_metacall(QObject *, QMetaObject::Call, int, void **);
};

staticMetaObject 是这个类的身份证：类名、父类元对象指针、信号槽方法表、属性表、枚举表全在里面。metaObject() 是虚函数，所以手上只有一个 QObject* 也能问出真实类型。

qt_metacast 服务 qobject_cast 和 inherits()，qt_metacall 是按 ID 调方法的入口。

moc 的六步流程 #

拿这个头文件当例子：

cpp
// widget.h
class Widget : public QObject {
    Q_OBJECT
public:
    Widget(QObject *parent = nullptr);

signals:
    void valueChanged(int newValue);
    void textChanged(const QString &text);

public slots:
    void setValue(int value);
    void reset();
};

预处理阶段调用 moc，产出 moc_widget.cpp。文件里是五样东西：

text
moc_widget.cpp
├── qt_meta_stringdata_Widget      信号槽名字的字符串表
├── qt_meta_data_Widget            元数据 uint 数组（名字索引、参数个数、参数类型、flags）
├── Widget::staticMetaObject       指向上面数组的 QMetaObject 静态实例
├── Widget::qt_static_metacall     按 ID 分发的 switch
└── valueChanged()/textChanged()   信号函数的实现体，内部调 QMetaObject::activate

分开看：

  1. 扫头文件，找出带 Q_OBJECT 的类。
  2. 字符串化：把 signals: 和 slots: 下的函数名塞进字符串表，每个名字编一个 idx。
  3. 生成元数据数组 qt_meta_data_Widget，后缀由类名决定：
cpp
static const uint qt_meta_data_Widget[] = {
    // content:
    9,       // revision
    0,       // classname，字符串表偏移
    0,    0, // classinfo
    4,   14, // methods：共 4 个方法，描述从下标 14 开始
    0,    0, // properties
    0,    0, // enums/sets
    0,    0, // constructors
    0,       // flags
    2,       // signalCount：2 个信号

    // signals: name, argc, parameters, tag, flags
    1, 1, 34, 2, 0x06,  // valueChanged(int)
    3, 1, 37, 2, 0x06,  // textChanged(QString)

    // slots:  name, argc, parameters, tag, flags
    5, 1, 40, 2, 0x0a,  // setValue(int)
    6, 0, 43, 2, 0x0a,  // reset()
};

4, 14 这组的意思是：有 4 个方法，方法描述从 qt_meta_data_Widget[14] 开始。0x06 是信号标志位，0x0a 是 public slots 的标志位。每个方法的 parameters 字段又是另一个偏移，指向参数类型表——运行时做参数匹配、QMetaMethod::parameterTypes() 取类型名，都靠这张表。

  1. 生成分发器 qt_static_metacall：
cpp
void Widget::qt_static_metacall(QObject *_o, QMetaObject::Call _c, int _id, void **_a)
{
    if (_c == QMetaObject::InvokeMetaMethod) {
        auto *_t = static_cast<Widget *>(_o);
        switch (_id) {
        case 0: _t->valueChanged((*reinterpret_cast<int*>(_a[1]))); break;
        case 1: _t->textChanged((*reinterpret_cast<QString*>(_a[1]))); break;
        case 2: _t->setValue((*reinterpret_cast<int*>(_a[1]))); break;
        case 3: _t->reset(); break;
        default: break;
        }
    }
    // 还有 InvokeMetaMethod 之外的分支，比如属性读写
}

_a 是 void** 参数数组。_a[0] 留给返回值，_a[1] 起才是实参。全部靠 reinterpret_cast 从 void* 暴力还原回原类型。类型信息在传参时被擦除，在调用点被硬还原，这就是运行时分发的代价，也是参数类型必须严格对上的原因——对不上不是「转换失败」，是直接读错内存。

  1. 生成 QMetaObject 实例，把这个类的类名、父类元对象、上面两个数组串起来。
  2. 编译。原 cpp 和 moc_widget.cpp 一起进编译器，链接成一个目标文件。

信号函数也是 moc 写的 #

这是理解整套机制的关键一环。你在头文件里写：

cpp
signals:
    void valueChanged(int newValue);

只有分号，没有函数体。纯 C++ 里这样写会链接失败——声明了却没人定义。补上定义的就是 moc，它在 moc_widget.cpp 里生成：

cpp
void Widget::valueChanged(int _t1)
{
    void *_a[] = { nullptr,
                   const_cast<void*>(reinterpret_cast<const void*>(std::addressof(_t1))) };
    QMetaObject::activate(this, &staticMetaObject, 0, _a);
}

于是几件事一次性说清了：

  • 信号只声明不实现，是 moc 补了实现，不是你漏写。
  • 信号的返回值固定 void，activate 不回传任何结果。
  • 那个 0 就是 qt_meta_data_Widget 里的方法下标。连接、分发、invokeMethod 全认这个号。
  • 你要是手写了 void Widget::valueChanged(int) {}，会和 moc 生成的撞成 multiple definition。

这套设计换来什么 #

代价摆在明面上：多一个构建步骤、C++ 里塞了准关键字、参数靠 void** 强转。换回来的是运行时的能力：

  • 按名字调用：QMetaObject::invokeMethod(obj, "setValue", Q_ARG(int, 42))。名字是字符串，所以 QML、脚本引擎、测试框架都能直接戳 C++ 方法。
  • 运行时问类型：obj->metaObject()->className()、inherits("QWidget")、qobject_cast<T*>。
  • 动态属性：obj->setProperty("state", 1)，不改类定义就能挂状态。
  • 内省：把对象的信号槽列表整个导出来，做检查工具、做连接可视化、做序列化。

qobject_cast 不走 C++ 的 dynamic_cast，它查的是元对象继承链，所以更快，也不要求开着 RTTI。这是 Qt 能在嵌入式环境里省掉一整套 RTTI 开销的原因之一。

三、连接语法：从 SIGNAL/SLOT 到函数指针 #

Qt 有两代连接写法，都还能用，但性质完全不同。这是老项目里最常见的分歧点。

两代对照 #

对比项 Qt4：SIGNAL() / SLOT() Qt5+：函数指针
写法 connect(a, SIGNAL(sig(int)), b, SLOT(slot(int))) connect(a, &A::sig, b, &B::slot)
匹配时机 运行时，字符串比对 编译期，类型推导
名字写错 编译通过，运行时一行警告 编译不过
参数类型 手写全串，必须与元数据里的名字一致 编译器自己推
重载函数 靠括号里的类型区分 要靠 QOverload / static_cast
能连什么 只认标了 slots 的函数 任意成员函数、静态函数、全局函数、lambda、仿函数
隐式转换 不做 做兼容类型转换
连接开销 每次 connect 查一遍字符串表 直接拿下标
名字重构 改名不报错，只有运行时警告 改错编译不过

新代码一律用函数指针那代。老代码不必整体返工，但改到哪个接口就把那个接口换掉。

Qt4 那代：字符串匹配 #

cpp
connect(sender, SIGNAL(valueChanged(int)), receiver, SLOT(setValue(int)));

SIGNAL() 宏把括号里的内容整个变成字符串，前面还加了个签名编码前缀，SLOT() 同理。connect 拿到四个参数后，去 sender 的元对象里按字符串找信号下标，去 receiver 的元对象里找槽下标。

问题就出在「运行时」三个字上。你把 valueChanged(int) 写成 valueChange(int)，编译器不管，链接器不管，程序跑起来 connect 返回 false，控制台打一行：

text
QObject::connect: No such signal Widget::valueChange(int)
QObject::connect:  (sender name:   'Widget')
QObject::connect:  (receiver name: 'SpinBox')

然后就没了。槽不触发，界面没反应，你得自己去输出窗口里翻。老项目里「点了没反应」九成是这一行。

还有两个暗坑：

  • 参数必须写成元对象认识的写法。SIGNAL(valueChanged(const QString&)) 里的 const QString& 和元数据里的 QString 对不上，匹配失败。
  • 没有隐式转换。信号传 int、槽要 double，字符串版直接连不上；函数指针版能过。

Qt5 起那代：函数指针 #

cpp
connect(sender, &Sender::valueChanged, receiver, &Receiver::setValue);

四个参数里两个是成员函数指针。编译期能做的事：

  • 检查 &Sender::valueChanged 真的存在，真的是信号（moc 给了它下标）。
  • 检查 &Receiver::setValue 存在，参数能对上。
  • 检查类里有 Q_OBJECT，否则拿不到下标，connect 的重载匹配不上，报 no matching function。
  • 参数类型不兼容直接编译错误。

代价只有一个：信号有重载时推导不出取哪个，见本章后面。

能连的五类目标 #

cpp
// 1. 成员函数，最常见
connect(slider, &QSlider::valueChanged, spin, &QSpinBox::setValue);

// 2. lambda
connect(btn, &QPushButton::clicked, this, [this](bool checked) {
    qDebug() << "clicked" << checked;
});

// 3. 全局函数、静态函数
connect(btn, &QPushButton::clicked, &someFreeFunction);
connect(btn, &QPushButton::clicked, &MyClass::staticHandler);

// 4. 仿函数，带 operator() 的对象
connect(btn, &QPushButton::clicked, Functor{});

// 5. 另一个信号，信号连信号
connect(btn, &QPushButton::clicked, this, &Widget::buttonClicked);

lambda 的几点实操：

  • [=] 值捕获，会连 this 一起捕获；[&] 引用捕获。跨线程队列连接时引用捕获必炸——槽真正执行时，被引用的局部变量早就没了。要跨线程就值捕获，或者捕获 QSharedPointer。
  • lambda 是匿名函数，省掉单独定义槽的样板。逻辑超过十几行就该提成成员函数，别把 lambda 写成第二个 .cpp。
  • 局部变量生命周期是 lambda 槽崩溃的头号原因。

带上下文对象的 connect #

lambda 和仿函数做槽时，Qt 没法知道「这个连接该跟谁一起死」——没有接收者对象可挂。所以要显式给一个上下文对象：

cpp
connect(m_timer, &QTimer::timeout, this, [this]() {
    ++m_count;
    updateLabel();
});

第三个参数 this 就是上下文。this 析构时这条连接自动断开。

cpp
// 危险写法：没有上下文对象
connect(m_timer, &QTimer::timeout, [this]() { updateLabel(); });

这条连接一直挂在 timer 上，捕获的 this 变成野指针，定时器下一次响就崩。Qt 5 也能这么写，所以不是版本问题，是纪律问题。Qt 6 里带上下文是标配，别省。

连接规则 #

参数个数：槽的形参个数 ≤ 信号的形参个数，槽从右往左忽略多余参数，但对得上的位置类型必须一致。

cpp
signals:
    void valueChanged(int value, const QString &unit);

// 这两个都能连
void onValue(int v);                        // 忽略 unit
void onValue(int v, const QString &unit);    // 全收

// void onValue(const QString &unit);        // 错，位置对不上

一个信号连多个槽：信号发出时按连接顺序依次调用。Qt 5 起有明确文档保证，Qt 4.6 以前是「顺序不确定」，看到「顺序不确定」的老资料别慌，那是十几年前的文档。

多个信号连一个槽：任一信号发出都调这个槽，槽里用 sender() 分辨来源。

信号连信号：

cpp
connect(obj1, &ClassA::signal1, obj2, &ClassB::signal2);

signal1 发出时 signal2 跟着发出。用来做信号透传，比如把内部子控件的信号原样转出去。

这条路上有个陷阱：信号连信号时，sender() 返回的是转发信号的那个对象，不是原始触发者。

cpp
// secondButton 点击后，转发成 firstButton 的 clicked
connect(m_secondButton, &QPushButton::clicked, m_firstButton, &QPushButton::clicked);
connect(m_firstButton,  &QPushButton::clicked, this, &MyWidget::buttonClickedSlot);

void MyWidget::buttonClickedSlot()
{
    auto button = qobject_cast<QPushButton*>(sender());
    // 无论点哪个按钮，button 永远指向 m_firstButton
}

原始发送者在这个链路上已经丢了。需要识别来源的场合别用信号连信号，改成在中间层把来源当参数带上。

重载信号的歧义 #

QSpinBox::valueChanged 在 Qt 5 里有 valueChanged(int) 和 valueChanged(QString) 两个重载。直接写：

cpp
connect(spin, &QSpinBox::valueChanged, this, &ListView::changeValue);
// 编译错误：无法推导出用哪个重载

得手动指定。两种写法：

cpp
// Qt 5.7+ 推荐
connect(spin, QOverload<int>::of(&QSpinBox::valueChanged),
        this, &ListView::changeValue);

// 纯 C++ 写法，老编译器用这个
connect(spin, static_cast<void (QSpinBox::*)(int)>(&QSpinBox::valueChanged),
        this, &ListView::changeValue);

迁移到 Qt 6 时注意：QSpinBox::valueChanged(QString) 那个重载被删了，只剩 int，原来靠它区分重载的 QOverload 反而变成多余，得一起删掉。

五种基础连接形态 #

形态 写法要点 典型用途
一对一 最普通的 connect 滑块联动数字框
一对多 同一个信号连多个接收者 一次变化触发界面刷新 + 日志 + 持久化
多对一 多个信号连同一个槽 所有按钮共用一个处理函数
信号接力 目标是另一个信号 子控件信号透传
断开 disconnect(...) 动态切换行为 
cpp
// 一对一
connect(slider, &QSlider::valueChanged, spin, &QSpinBox::setValue);

// 一对多
connect(slider, &QSlider::valueChanged, spin, &QSpinBox::setValue);
connect(slider, &QSlider::valueChanged, this, &Widget::logValue);

// 多对一
connect(pushButton, &QPushButton::clicked, this, &Widget::refresh);
connect(toolButton, &QToolButton::clicked, this, &Widget::refresh);

// 信号接力
connect(pushButton, &QPushButton::clicked, this, &Widget::buttonClicked);

// 断开
disconnect(pushButton);   // 该对象发出的全部连接
disconnect(pushButton, &QPushButton::clicked, this, &Widget::refresh);  // 精确断开

四、五种连接类型 #

connect 的第五个参数决定这次调用怎么走。默认 Qt::AutoConnection，多数人从不写它，跨线程的毛病全出在这一格。

类型 行为 同步性 用在哪
Qt::AutoConnection（默认） 收发同线程走直连，跨线程走队列 看情况 绝大多数代码
Qt::DirectConnection 在发送者所在线程立即调槽 同步 同线程高频路径；明确知道后果的跨线程
Qt::QueuedConnection 投递事件到接收者线程，稍后执行 异步 跨线程更新界面
Qt::BlockingQueuedConnection 队列式，但发送者阻塞等槽返回 同步 工作线程要向主线程要结果
Qt::UniqueConnection 与其它类型按位或，防重复连接 同被修饰的类型 会被反复调用的初始化路径
Qt::SingleShotConnection Qt 6 新增，槽执行一次后自动断开 同被修饰的类型 一次性回调

前四个是调度方式，UniqueConnection 和 SingleShotConnection 是修饰位，可以和前四个按位或。

AutoConnection #

判定依据是两个对象的线程亲和性（thread affinity），不是「谁 emit 的」。QObject::thread() 返回对象归属的线程；对象在哪个线程被创建就归哪个线程，除非显式 moveToThread。

同线程：等价于直连，同步调用。 跨线程：等价于队列，异步投递。

判定发生在 emit 那一刻，不是 connect 那一刻。所以先 connect 后 moveToThread 也能正常工作，这点常常让人误以为是 connect 时就定死了。

DirectConnection #

不排队，就在 emit 那行代码里把槽调完。谁 emit 的，槽就在谁的线程里跑。

后果：槽里操作接收者的成员时，接收者正在另一个线程里用它。跨线程用直连刷界面基本必崩，而且崩的位置和原因对不上，排查成本极高。

同线程时直连最快：没有事件分配、没有参数打包，就是一次 qt_static_metacall 的 switch 加一次成员函数调用。

QueuedConnection #

activate 把这次调用打包成一个 QMetaCallEvent（带接收者、槽下标、参数副本），postEvent 到接收者线程的事件队列。接收者线程的事件循环取到这个事件，走 qt_static_metacall 执行槽。

三个必须知道的前提：

  1. 参数要拷贝。所以参数类型必须可拷贝，且必须注册进元对象系统，否则事件投出去了，接收端取不出来——Qt 只打一行运行时警告，槽不执行。这是跨线程信号槽最常见的坑，第七章展开。
  2. 槽在接收者线程执行。此时 sender() 还能用，但发送者早就往下跑了，别假设它停在 emit 那行等你。
  3. 异步就是异步。调用方拿不到任何执行结果，异常也不跨线程传递，槽里抛的东西不会回到发送者。

BlockingQueuedConnection #

队列投递后发送者阻塞，直到槽执行完才返回。用来做反向调用：工作线程要主线程手里的一份数据。

死锁条件要背下来：收发双方在同一个线程时用 Blocking，立刻死锁。Qt 会打印 Qt: Dead lock detected in QCoreApplication::postEvent 并直接 abort。

界面上慎用。卡住事件循环就是掉帧，用户的体感是「整个窗口僵住」。

UniqueConnection #

和别的类型按位或：

cpp
connect(btn, &QPushButton::clicked, this, &Widget::onClicked, Qt::UniqueConnection);

已经存在完全相同的连接时，这次 connect 直接返回 false，不新增一条。适合放在会被调用多次的初始化函数里，比如「每次切页都重连一遍」。

限制两条：只对函数指针版有意义；用于 lambda 时判定不了两个 lambda 是否相同，会一直往上加。

五、emit 的本质 #

空宏 #

emit 在 qobjectdefs.h 里的定义是空的：

cpp
#define emit
#define signals public
#define slots
#define Q_SLOTS

所以 emit valueChanged(42); 预处理之后就是 valueChanged(42);——一次普通的成员函数调用。emit 纯粹给人看，标记「这行在发信号」。写不写行为完全一样，建议写，读代码的人省事。

顺带解释一件事：signals 展开成 public，所以写在 signals: 区里的函数天生 public。你写 private signals: 没用，private 被 public 盖掉。这也是信号必须能 public 的原因——外部要 connect，就得能取到函数地址。

信号函数长什么样 #

第二章讲过，信号函数的定义是 moc 生成的。它的函数体只干两件事：把实参攒成 void* 数组，调 QMetaObject::activate。

cpp
void Widget::valueChanged(int _t1)
{
    void *_a[] = { nullptr, const_cast<void*>(reinterpret_cast<const void*>(std::addressof(_t1))) };
    QMetaObject::activate(this, &staticMetaObject, 0, _a);
}

0 是这个信号在元数据里的下标。全部连接关系都按这个下标索引，不走字符串。

activate 干了什么 #

text
QMetaObject::activate(sender, staticMetaObject, signalIndex, args)
├── 从 sender 的连接表里取出 signalIndex 那一条链表
├── 遍历每个 {receiver, slotIndex, connectionType}
│   ├── 检查 receiver 是否还在（弱引用，析构时置空）
│   ├── DirectConnection          → 调 receiver->qt_metacall(InvokeMetaMethod, slotIndex, args)
│   ├── QueuedConnection          → new QMetaCallEvent，postEvent 到接收者线程
│   └── BlockingQueuedConnection  → postEvent + 信号量等待返回
└── 返回

连接表在 QObjectPrivate 里，是按信号下标排列的一串链表。每个节点存接收者指针、槽下标、连接类型，外加一条指回接收者的弱引用链，用于接收者析构时反向摘除自己。

于是在 emit 那一刻，开销是：查表 + 遍历接收者 + 每个接收者一次虚调用 qt_metacall。没有字符串比对——下标在 connect 时就解析好了。代价是每次都要在现场组装一个 void* 参数数组。

这也顺手解释了另外两件事：信号不能有返回值（activate 不往回传东西），以及 emit 之后不能假设槽跑完了（队列连接下它还没跑）。

由此还能推出一条用法边界：想「只通知某一个接收者」，直接调对方的成员函数就行。信号槽是广播模型，没有点对点模式。

六、自定义信号与槽 #

一个最小可用的一对 #

cpp
// newspaper.h
class Newspaper : public QObject
{
    Q_OBJECT
public:
    explicit Newspaper(const QString &name, QObject *parent = nullptr)
        : QObject(parent), m_name(name) {}

    void send() { emit newPaper(m_name); }

signals:
    void newPaper(const QString &name);   // 只声明，不实现

private:
    QString m_name;
};

// reader.h
class Reader : public QObject
{
    Q_OBJECT
public:
    void receive(const QString &name) { qDebug() << "gets" << name; }
};

cpp
Newspaper paper("Daily");
Reader reader;
QObject::connect(&paper, &Newspaper::newPaper, &reader, &Reader::receive);
paper.send();   // reader 打印 gets Daily

两个类互相不认识，Newspaper 的头文件里没有 Reader，Reader 的头文件里没有 Newspaper。只在这段装配代码里见了一面。

声明区的规矩 #

写法 含义 说明
signals: 信号声明区 展开成 public，写 private / protected 无效
public slots: 槽，外部可连 老代码常见 private slots:
Q_SIGNALS / Q_SLOTS 上面两个的别名 撞到第三方库的 signals 宏时用这个
Q_INVOKABLE 普通成员函数，但可被元对象调用 配合 invokeMethod 和 QML
emit 空宏 加上纯为可读性

槽函数不必标 slots。函数指针版的 connect 能连任意成员函数，private 的、静态的、虚的、带 const 的都行。标 slots 的实际好处只有一个：它会进元对象的方法表，能被 invokeMethod 按名字调用、能出现在 QML 里。不需要这两个能力就不标。

槽不必是成员函数 #

全局函数、静态函数、仿函数、lambda 都能当槽，第三章那五类就是全套。唯一的硬要求是能取到一个可调用对象，或者一个成员函数指针。

这种自由度是 Qt 4 时代没有的。字符串版只认 slots 标记过的成员函数，所以老代码里到处是「为了连一下而被迫新增一个槽」。

多控件复用一个槽 #

四个按钮共用一个处理函数，槽里判断是谁触发的。枚举 + objectName 是一种经典写法：

cpp
// 声明识别枚举
enum BUTTON_ID { BUTTON_1, BUTTON_2, BUTTON_3, BUTTON_4 };

// 初始化时把 ID 塞进 objectName
pushButton1->setObjectName(QString::number(BUTTON_1, 10));
pushButton2->setObjectName(QString::number(BUTTON_2, 10));
toolButton1->setObjectName(QString::number(BUTTON_3, 10));
toolButton2->setObjectName(QString::number(BUTTON_4, 10));

connect(pushButton1, &QPushButton::clicked, this, &MyWidget::changeButton);
connect(pushButton2, &QPushButton::clicked, this, &MyWidget::changeButton);
connect(toolButton1, &QToolButton::clicked, this, &MyWidget::changeButton);
connect(toolButton2, &QToolButton::clicked, this, &MyWidget::changeButton);

void MyWidget::changeButton()
{
    QObject *senderObj = sender();
    QPushButton *pushBtn = qobject_cast<QPushButton *>(senderObj);
    QToolButton *toolBtn = qobject_cast<QToolButton *>(senderObj);

    int index = -1;
    if (pushBtn)      index = pushBtn->objectName().toInt();
    else if (toolBtn) index = toolBtn->objectName().toInt();

    QString info;
    switch (index) {
    case BUTTON_1: info = "clicked Button 1"; break;
    case BUTTON_2: info = "clicked Button 2"; break;
    case BUTTON_3: info = "clicked ToolButton 3"; break;
    case BUTTON_4: info = "clicked ToolButton 4"; break;
    default:       info = "unknown widget"; break;
    }
    QMessageBox::information(this, "Title", info);
}

qobject_cast 在这里是必须的：sender() 返回 QObject*，直接 static_cast 到 QPushButton* 在类型不对时是未定义行为，qobject_cast 走元对象链，类型不对返回 nullptr。

更省事的版本是直接比指针，不折腾 objectName：

cpp
void MyWidget::onButtonClicked()
{
    QObject *s = sender();
    if (s == m_firstButton)       qDebug() << "first";
    else if (s == m_secondButton) qDebug() << "second";
}

两种写法的取舍：比指针最短，但重构时容易忘同步；objectName 能跨类，可读性好，代价是多一层字符串转换。控件数量上到十几个，两者都难看，换 QHash<QObject*, int> 存映射表。

sender() 的边界要清楚：

  • 只在槽被信号直接触发时可取。在槽里调出去的其他普通函数里调 sender()，返回 nullptr。
  • 队列连接下 sender() 仍然可用，QMetaCallEvent 里记了发送者。
  • 信号连信号时 sender() 是转发者，不是原始触发者，前面讲过。

QSignalMapper #

Qt 4 时代的老工具，把一组无参数信号翻译成带参数信号。Qt 6 里移到了 Qt5Compat 模块，新代码用 lambda 更直接。

cpp
QSignalMapper *mapper = new QSignalMapper(this);

connect(pushButton1, &QPushButton::clicked, mapper, QOverload<>::of(&QSignalMapper::map));
connect(pushButton2, &QPushButton::clicked, mapper, QOverload<>::of(&QSignalMapper::map));
connect(toolButton1, &QToolButton::clicked, mapper, QOverload<>::of(&QSignalMapper::map));
connect(toolButton2, &QToolButton::clicked, mapper, QOverload<>::of(&QSignalMapper::map));

mapper->setMapping(pushButton1, QString::number(BUTTON_1, 10));
mapper->setMapping(pushButton2, QString::number(BUTTON_2, 10));
mapper->setMapping(toolButton1, QString::number(BUTTON_3, 10));
mapper->setMapping(toolButton2, QString::number(BUTTON_4, 10));

connect(mapper, &QSignalMapper::mappedString, this, &MyWidget::changeButton);

void MyWidget::changeButton(const QString &text)
{
    int index = text.toInt();
    // switch 处理
}

mapped 有三个版本：mapped(int)、mapped(QString)、mapped(QObject*)、mappedWidget。setMapping 的第二个参数类型决定最终发哪个信号。

lambda 版的等价物，现在更常见：

cpp
for (int i = 0; i < buttons.size(); ++i) {
    connect(buttons[i], &QPushButton::clicked, this, [this, i]() { handle(i); });
}

QButtonGroup 也能干这事，idClicked(int) 直接带 ID，不用自己建映射表。

模拟用户操作 #

自动化测试里不必真点鼠标，直接调按钮的槽就行：

cpp
m_firstButton->click();             // 立即触发，走完整信号路径
m_firstButton->animateClick(100);    // 按下 100ms 再抬起，带视觉反馈
m_firstButton->toggle();             // checkable 按钮翻转选中态
m_firstButton->setChecked(true);     // 直接设状态

QPushButton 暴露出来的相关槽：

cpp
public Q_SLOTS:
    void setIconSize(const QSize &size);
    void animateClick(int msec = 100);
    void click();
    void toggle();
    void setChecked(bool);

click() 和用户真点一样，会依次发 pressed / released / clicked。setChecked(true) 只改状态，发的是 toggled，clicked 视按钮状态而定。测试里要分清「模拟交互」和「直接改状态」，混用会让断言时灵时不灵。

七、带参数与参数类型注册 #

参数怎么传 #

方式 适用 注意
const T& 大对象 首选，省掉拷贝
值 T 小 POD int / bool / 枚举直接值传
T* 不想拷贝的对象 生命周期自己管，队列连接下危险
const T* 只读大对象 同上，还是危险 
cpp
signals:
    void dataReady(const QByteArray &data);   // 好
    void dataReady(QByteArray data);          // 能跑，多一次拷贝
    void dataReady(MyBigStruct *p);           // 慎用，队列连接下会悬空

裸指针在直连下没问题：槽执行时对象还活着。队列连接下事件排到队列里，等接收者线程处理时，发送端那个对象早就析构了。这类 bug 的特征是「本地压测没事，线上偶发」——队列长度不同，时序就不同。

隐式共享让 const& 更划算 #

Qt 的 QString、QByteArray、QList、QImage、QVariant 都实现了隐式共享（Implicit Sharing），也就是写时复制（COW）：拷贝只加引用计数，修改时才真正复制一份。

cpp
QByteArray b1 = "hello";
QByteArray b2 = b1;      // 浅拷贝，共享同一块内存
b2 = "modified";         // 这时才深拷贝，b1 不受影响

信号槽传递直接受益：用 const QByteArray& 传，接收方没改动之前和发送方共享内存。队列连接会做一次拷贝，但那次拷贝也是浅拷贝，成本只有一次原子计数。

注意：不是所有 Qt 类型都隐式共享。QSize、QPoint、QRect 这类小值类就是老老实实拷贝，但体积小，拷贝无所谓。拿不准的查文档里有没有 Implicit Sharing 章节。

跨线程必须注册类型 #

这条是 Qt::QueuedConnection 的前提，也是被漏掉最多的一条。

队列连接的原理是把参数拷进 QMetaCallEvent，接收端再按元数据里记录的类型名把 void* 转回来。要做到这点，类型名必须能查到、能默认构造、能析构。自定义类型默认不在元对象系统的类型表里，于是投递那一刻找不到类型名，Qt 打一行：

text
QObject::connect: Cannot queue arguments of type 'MyData'
(Make sure 'MyData' is registered using qRegisterMetaType().)

然后槽不执行。程序不崩，界面不更新，日志干净。跨线程问题查几天就是这么来的。

三步走：

cpp
// 1. 类型定义之后，全局作用域里声明元类型
struct MyData {
    int id;
    QString name;
};
Q_DECLARE_METATYPE(MyData)

// 2. 信号里用 const MyData& 或 MyData
signals:
    void dataReady(const MyData &d);

// 3. 在 connect 之前注册进元类型系统
int main(int argc, char *argv[])
{
    QApplication app(argc, argv);
    qRegisterMetaType<MyData>("MyData");   // 字符串要和信号声明里的类型名一致
    // ...
}

细化规则：

  • Q_DECLARE_METATYPE(T) 让 T 能放进 QVariant，同时给 qRegisterMetaType<T>() 提供模板参数和类型名。自定义类型必须写，且必须写在全局命名空间，写进类里面是无效的。
  • qRegisterMetaType<T>("T") 把类型名登记到运行时名字表。Qt 6 里同线程的排队调用多数能靠模板自动注册，跨线程、按名字调用、QML 交互仍然要显式注册。
  • 类型名一字不差。带命名空间的类型写成 "MyNs::MyData"，注册成 "MyData" 对不上。
  • 参数声明成 const T& 时，注册 T 就够，Qt 会剥掉引用和 const。
  • 只在同线程直连时可以不注册，因为根本不经过 QMetaCallEvent。这解释了「本地测好的跨线程代码到 CI 上失灵」——调度路径恰好不同。

基础类型不用管：int、bool、double、QString、QByteArray、QVariant、QSize、QPoint、QDateTime 这些 Qt 内部都注册过。

用 QVariant 兜底 #

不想为每个类型写一遍声明，可以让信号只传 QVariant：

cpp
signals:
    void payloadReady(const QVariant &payload);

emit payloadReady(QVariant::fromValue(MyData{1, "x"}));   // Q_DECLARE_METATYPE 还是跑不掉

QVariant 省掉的是「注册类型名」这一步，Q_DECLARE_METATYPE 仍然要写。代价是接收端多一次 value<MyData>() 转换，错了只有在运行时知道。类型固定的场合别用 QVariant，它是给动态场景准备的。

信号不能带默认参数 #

moc 字符串化时不处理默认值，信号的形参必须写全。槽可以有默认参数，但那只是 C++ 层面的便利，connect 时按完整签名匹配。

八、断开连接与生命周期 #

disconnect 的几种形态 #

cpp
// 断开这个对象发出的所有连接
disconnect(sender, nullptr, nullptr, nullptr);
disconnect(sender);                                // 等价简写

// 断开某个信号的全部连接
disconnect(sender, &Sender::sig, nullptr, nullptr);

// 断开指定的那一对
disconnect(sender, &Sender::sig, receiver, &Receiver::slot);

// 断开某个接收者的所有连接
disconnect(nullptr, nullptr, receiver, nullptr);

// 用连接句柄
QMetaObject::Connection c = connect(...);
disconnect(c);

disconnect 是 QObject 的静态成员，代码里直接写 disconnect(...) 靠 ADL 就能找到，不必加 QObject::。

连接句柄 #

connect 返回 QMetaObject::Connection，可以存起来做判断和断开：

cpp
QMetaObject::Connection conn = connect(sender, &Sender::sig, receiver, &Receiver::slot);
if (conn) {
    // 连接成立
}
QObject::disconnect(conn);

句柄能 bool 判断：连接成功为 true，失败（比如 UniqueConnection 撞上已有的）为 false。接收者析构之后句柄本身还在，disconnect 一个失效句柄是安全的无操作，不会崩。

RAII 封装，析构自动断：

cpp
class ScopedConnection
{
public:
    ScopedConnection() = default;
    explicit ScopedConnection(QMetaObject::Connection c) : m_conn(c) {}
    ~ScopedConnection() { QObject::disconnect(m_conn); }

    ScopedConnection(const ScopedConnection &) = delete;
    ScopedConnection &operator=(const ScopedConnection &) = delete;

private:
    QMetaObject::Connection m_conn;
};

用在「临时监听一下、出了这个作用域就撤」的场合，比手动配对的 disconnect 少出错。

析构时 Qt 做了什么 #

接收者 ~QObject 时，Qt 遍历它的 QObjectPrivate::senders 链，把所有指向自己的连接从发送者的连接表里摘掉。所以「接收者没了、连接还挂着」在 Qt 里不会发生，不需要为了防崩溃手动 disconnect。

反向不成立：发送者析构时连接一起消失，但接收者收不到任何通知。你的槽不会知道「发送者已经走了」，如果槽里有依赖发送者的逻辑，得自己用 destroyed() 信号接一下：

cpp
connect(sender, &QObject::destroyed, this, [this]() { m_sender = nullptr; });

三条结论：

  • 正常析构（栈对象、parent-child、delete）都不用管连接，Qt 会摘。
  • 队列里还排着的 QMetaCallEvent 会随对象析构被清理，QObject 析构时会调 removePostedEvents，所以不会执行到已死的对象上。
  • 真会出事的是两种：裸指针加手动 disconnect 漏了一处；lambda 没给上下文对象，捕获的 this 已经析构。

连接顺序 #

同一个信号的多个槽，Qt 5 起按 connect 的先后顺序执行。这条写在文档里，是稳定行为，可以依赖。

cpp
connect(s, &S::sig, &a, &A::on);   // 先执行
connect(s, &S::sig, &b, &B::on);   // 后执行

依赖顺序的代码在注释里写清楚「顺序有意」，否则后人一重排就出问题。更稳的做法是不依赖顺序：需要先后关系就用两次 emit 或者一个中间槽显式串起来。

在槽里删掉发送者 #

合法但危险：

cpp
void Widget::onTimeout()
{
    m_timer->deleteLater();   // 对
    // delete m_timer;        // 危险：当前就在 m_timer 的 emit 栈帧里
}

delete 会析构 activate 正在遍历的那个对象。Qt 对连接表遍历做了保护（链表带引用计数），但信号函数返回之后 this 已经没了，activate 之后的代码再碰成员就是野指针。

deleteLater() 把删除推到事件循环下一轮，等当前调用栈全部退出，安全。同理，槽里要删接收者自己也用 deleteLater()。

九、连接失败的排查 #

connect 有返回值，能 bool 判断。老代码里没人查它，导致失败后只能靠猜。

症状对照表 #

症状 常见原因 怎么查
编译报 no matching function for call to connect 类里漏 Q_OBJECT；参数类型不兼容；连接了非 QObject 的类 看报错里推导出的类型
编译报 unable to deduce / 无法推导重载 信号有多个重载 加 QOverload<T>::of
编译报 multiple definition of Xxx::signal 手写了信号实现 删掉你的实现，信号只声明
链接报 undefined reference to vtable for Xxx 有 Q_OBJECT 但 moc 没跑 开 AUTOMOC，或把头文件加进构建目标
运行打 No such signal / No such slot 字符串版名字或参数写错 换函数指针版，改错编译不过
运行打 Cannot queue arguments of type 自定义类型没注册元类型 Q_DECLARE_METATYPE + qRegisterMetaType
connect 返回 false，别的没动静 参数个数或类型不匹配 检查槽的形参能不能从信号形参对上
连接正常但槽不跑 接收者线程没有事件循环；或信号压根没发 断点打在 emit 与 activate；查 QThread 是否 exec

五个必查项 #

  1. 类里有 Q_OBJECT 吗。漏了只在链接期报 vtable 未定义，报错信息里一个信号槽的字都看不到，很容易误判成构建配置问题。
  2. moc 跑了吗。CMake 里 set(CMAKE_AUTOMOC ON)，qmake 里头文件要进 HEADERS。查法：构建目录里找 moc_xxx.cpp 存不存在。
  3. connect 的返回值查了吗。临时插一行：
cpp
auto c = connect(sender, &Sender::sig, receiver, &Receiver::slot);
Q_ASSERT(c);
  1. 信号真的发了吗。在 emit 那行打断点，或者临时 qDebug()。
  2. 跨线程的话类型注册了吗。打印 obj->thread() 和 QThread::currentThread() 比一下，再确认自定义类型已经注册。

用元对象把连接关系导出来 #

连接多到理不清的老项目，直接问元对象：

cpp
const QMetaObject *mo = obj->metaObject();
for (int i = 0; i < mo->methodCount(); ++i) {
    QMetaMethod m = mo->method(i);
    qDebug() << m.methodSignature()
             << (m.methodType() == QMetaMethod::Signal ? "signal" : "slot");
}

要追运行时行为，开日志规则：QT_LOGGING_RULES="qt.core.*=true"，连接失败、事件投递的警告都在里面。

十、Qt6 的变化 #

函数指针成为唯一正经写法 #

SIGNAL() / SLOT() 两个宏在 Qt 6 里还留着，为的是源码兼容。但新写的代码没有理由用它：QML 侧的类型推导、connect 的模板实现、编译期检查，全都只对函数指针版成立。

Qt::SingleShotConnection #

槽执行一次后自动断开，不用手动 disconnect：

cpp
connect(sender, &Sender::sig, receiver, &Receiver::slot, Qt::SingleShotConnection);

// 和调度类型按位或
connect(sender, &Sender::sig, receiver, &Receiver::slot,
        Qt::QueuedConnection | Qt::SingleShotConnection);

适合初始化事件、首次操作引导、异步完成回调这类「只关心第一次」的场合。省掉一个成员标志位加一次手动断开。

QProperty 绑定系统 #

把 QML 的声明式绑定搬进 C++。属性值自动跟踪依赖，依赖变了自动重算：

cpp
QProperty<int> width{100}, height{50}, area;
area.setBinding([&]() { return width.value() * height.value(); });

width = 200;   // area 自动变成 10000

监听值变化：onValueChanged() 在值变时触发，subscribe() 立即执行一次并继续监听后续变化。

和 QObject 集成用 Q_OBJECT_BINDABLE_PROPERTY 宏配合 Q_PROPERTY，属性对 QML 可见、可绑定。批量更新用 Qt::beginPropertyUpdateGroup() / Qt::endPropertyUpdateGroup()，包住的区间里中间态不触发重算。

和信号槽的分工：

对比项 QProperty 信号槽
范式 声明式，依赖自动追踪 命令式，手动 connect
表达的是 值等于其它值的函数 事件发生了，去做点什么
适合 属性派生、UI 联动、状态派生 事件通知、业务动作、跨模块通信
失效方式 依赖图重算 手动 disconnect

Qt5 与 Qt6 对照 #

项目 Qt 5 Qt 6
连接语法 函数指针推荐，字符串可用 函数指针为主，字符串仅兼容
一次性连接 无，自己断开 Qt::SingleShotConnection
属性绑定 无 QProperty / QBindable
QSignalMapper 在 QtCore 移到 Qt5Compat 模块
QSpinBox::valueChanged(QString) 已废弃 移除，只剩 int
信号重载 常见，要 QOverload 大量减少，迁移时删掉多余的 QOverload
元类型注册 需显式 qRegisterMetaType 同线程多数可自动，跨线程仍要显式
容器 QList 与 QVector 分离 QVector 是 QList 的别名

迁移时最容易踩的是第六行：Qt 5 里为了让 valueChanged 不歧义而写的 QOverload<int>::of(...)，到 Qt 6 因为重载消失，QOverload 反而成了错误，要一并删掉。

连接句柄的稳定性 #

QMetaObject::Connection 的类型没变，可以直接做成员变量。它不持有对象，只记发送者、接收者的私有指针和信号下标，所以对象析构后句柄失效，disconnect 一个失效句柄是安全无操作。

十一、性能与适用边界 #

一次 emit 花在哪 #

环节 开销 能不能省
查连接表 一次按下标数组访问 + 链表遍历 省不了
组装参数数组 每个参数一次取地址 省不了
虚调用 qt_metacall 一次虚函数 + 一次 switch 省不了
参数拷贝 直连零拷贝；队列一次拷贝 队列省不了，但隐式共享让拷贝很轻
事件分配 队列连接要 new 一个 QMetaCallEvent 高频路径上明显

直连的开销大约是普通虚函数调用的几倍。和裸函数指针回调比，量级上慢十倍左右，但绝对时间是几百纳秒。GUI 事件响应、业务逻辑、模块间通信，这点开销可以忽略。

需要担心的是每秒几十万次的那种信号：音频采样回调、逐帧计算、串口每来一个字节发一次信号。

该动手的地方 #

  • 大对象一律 const T&，别按值传。队列连接下靠隐式共享摊薄拷贝成本。
  • 高频路径别用队列连接。事件分配的堆开销比函数调用本身大得多。
  • 高频路径别用 QVariant 装参数，多一层装箱加一次类型转换。
  • 批量数据别一条一条 emit，攒成一批发一个信号。一千次信号改成一次，收益立竿见影。
  • 确认真是瓶颈再改。用 profiler 看，别猜。

什么时候不该用信号槽 #

场景 更好的做法
每秒十万次以上的回调 直接函数调用、函数指针、std::function
一对一，且调用方明确知道被调用方是谁 直接调成员函数
需要返回值 普通函数。信号没有返回值
需要严格的同步顺序 直连或普通函数，队列连接依赖事件循环调度
大量小对象两两连线 集中的分发器或事件总线，避免连接数平方增长

信号槽的价值在解耦：发送方不知道接收方是谁、有几个、还在不在。当这三件事你都确定的时候，直接调用更简单，也更快。

十二、易错点速查 #

# 现象 原因 修法
1 链接期 vtable 未定义 有 Q_OBJECT 但 moc 没跑 开 AUTOMOC，头文件进构建；加宏后重跑构建配置
2 编译期 multiple definition 手写了信号函数体 信号只声明，实现交给 moc
3 运行打 No such signal 字符串版拼错名字或参数类型 换函数指针版
4 点了没反应，日志干净 emit 没执行，或连接压根没建起来 查 connect 返回值，断点打在 emit
5 跨线程槽不执行，只有一行警告 自定义类型没注册元类型 Q_DECLARE_METATYPE + qRegisterMetaType
6 跨线程崩在刷界面那一行 用了 DirectConnection 操作控件 用默认 Auto，或显式 Queued
7 lambda 槽偶发崩溃 没给上下文对象，this 已析构 connect(..., this, lambda)
8 同一个槽执行两次 重复 connect Qt::UniqueConnection
9 重载信号编译不过 没指定取哪个重载 QOverload<T>::of 或 static_cast
10 死锁，Qt 直接 abort Blocking 队列连接用在同一线程 改 Queued，或换线程架构
11 sender() 返回 nullptr 在槽间接调用的函数里取 sender 进入槽时取一次，当参数往下传
12 信号连信号后来源判断全错 sender() 是转发者，不是原始触发者 把来源当参数带上，别依赖 sender()
13 槽里 delete 发送者后崩 在 activate 栈帧里析构了它 deleteLater()
14 队列连接参数变野指针 传了裸指针，接收端执行时已释放 传值、传隐式共享容器、传 QSharedPointer
15 迁到 Qt6 后 QOverload 报错 那个重载在 Qt6 已被移除 拆掉 QOverload 直接取地址

一条记忆主线 #

  • emit 是空宏，信号函数是 moc 生成的，真正的分发在 qt_static_metacall 里。
  • 新代码用函数指针版。字符串版只在维护老接口时留着，且必须查 connect 返回值。
  • 跨线程的安全形态只有两种：默认 Auto 加已注册类型，或显式 Queued 加已注册类型。
  • 队列连接的参数类型没注册，就是静默失败，不崩不报错。
  • 接收者析构时连接自动摘除。会出事的是 lambda 没给上下文，和裸指针跨线程传递。
