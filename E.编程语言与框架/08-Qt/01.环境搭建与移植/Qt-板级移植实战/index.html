这篇只讲一件事：Qt 库在 PC 上编好了，怎么挪到某块具体的 ARM 板上，让程序在板子的屏幕上真的跑起来。

讲什么：板子这一侧的落地环节——确认板子底细、对齐工具链与 glibc、把 Qt 库装进板子的根文件系统、定目录、配环境变量、选显示后端、接通触摸屏、跑第一个 demo。

不讲什么：交叉工具链怎么从源码做出来、Qt 源码裁剪编译的完整细节，在《交叉编译：工具链与源码编译》里；开机自启、升级回滚、远程分发，在《部署与运行》里；完整项目实战（全志 H3、mini2440），在《完整项目》里。

一句判断标准：板子上跑不起来，问题落在三件事上——Qt 库与板子的 glibc、浮点 ABI 是否兼容；显示后端是否选对；环境变量是否指对。三样缺一样，屏幕就是黑的。

一、板级移植的通用流程 #

七篇旧稿来自五块板子、四个 Qt 版本、三个年代的 Ubuntu，流程却高度一致。先把它拍平。

步 动作 产出 / 判据 做错的表现
1 摸清板子：CPU、libc、浮点、屏幕、输入设备 一张参数纸 后面所有选择都跟着错
2 装交叉工具链，配 PATH arm-linux-gcc -v 出版本 Command not found
3 交叉编 tslib /usr/local/tslib 里有 ARM 格式的库 触摸全无、Qt 配置时 tslib functionality test failed
4 改 mkspecs 里的 qmake.conf 编译器前缀指向板子对应的那个 the specified system/compiler is not supported
5 configure + make + make install lib/、plugins/、bin/qmake 编到一半报缺库
6 库文件和插件拷进板子根文件系统 板子上能看到 libQt5Core.so.5 启动即 cannot open shared object
7 板子上配环境变量（/etc/profile） env 里能看到 QT_QPA_PLATFORM 黑屏、EGL not found、字体方块
8 编一个 demo，拷过去，命令行跑 屏幕上出现窗口 -qws 无反应 / platform plugin not found

第 1 步到第 5 步在 PC 上，第 6 步开始碰板子。真正耗时间的不是编译，是第 6 到第 8 步——库版本、路径、权限、设备节点，任何一处不对都只给你一句干巴巴的报错。

Qt4 和 Qt5 是两条路 #

老稿里一大半是 Qt4 的 -qws 时代，剩下的是 Qt5 的 QPA 时代。命令长得不一样，原理不一样，别混着抄。

维度 Qt4 / Qtopia 时代 Qt5 / QPA 时代
平台抽象 QWS 窗口系统，自带一个 server QPA 插件，每个后端一个 .so
配置开关 -embedded arm -xplatform qws/linux-arm-g++ -xplatform linux-arm-gnueabi-g++
图形后端 -qt-gfx-linuxfb、-qt-gfx-qvfb QT_QPA_DEFAULT_PLATFORM=linuxfb
触摸开关 -qt-mouse-tslib -tslib + QT_QPA_GENERIC_PLUGINS
运行命令 ./app -qws ./app -platform linuxfb
插件目录 无（编进库里） plugins/platforms/libqlinuxfb.so
字体变量 QT_QWS_FONTDIR QT_QPA_FONTDIR
输入变量 QWS_MOUSE_PROTO QT_QPA_GENERIC_PLUGINS

Qt4 里 -qws 就是「我自己起一个窗口系统」。Qt5 没有 QWS，改成问 QPA：「你要哪个平台插件」。所以 Qt4 的 QWS_MOUSE_PROTO、QT_QWS_FONTDIR 在 Qt5 上写了也没人读，反过来 Qt5 的 QT_QPA_PLATFORM 在 Qt4 上写了等于没写。

三件事，缺一不可 #

要命的三件事 具体含义 出错时的原话
库与板子兼容 交叉工具链的 glibc ≤ 板子的 glibc；浮点 ABI（gnueabi 软浮点 / gnueabihf 硬浮点）与板子一致 GLIBC_2.28 not found、Illegal instruction
显示后端选对 有 GPU 且驱动齐全走 eglfs，纯 fb 走 linuxfb，跑在 compositor 里走 wayland 黑屏、EGL not found、Could not queue DRM page flip
环境变量指对 平台插件路径、库路径、字体目录、触摸设备节点都指向板子上的真实路径 This application failed to start because no Qt platform plugin could be initialized

这三件事有个共同点：报错都发生在启动的第一秒，不会给你中间状态。所以排查顺序也从这三样倒着查——先 env 看变量，再 ls 看库和插件，最后 ldd -v 看 glibc 符号。

一次完整流程长什么样 #

text
[PC]    工具链解压 → PATH 生效 → arm-linux-gcc -v 通过
        tslib 交叉编译 → /usr/local/tslib（bin 里是 ARM 可执行文件）
        Qt 源码三份 qt-pc / qt-x86 / qt-arm → 改 mkspecs 的 qmake.conf（Qt5 加 QT_QPA_DEFAULT_PLATFORM）
        ./configure（-prefix 落地）→ make -j4 → make install → qmake 改名 qmake-arm
[板子]  cp 库 + 插件 + qml → /opt/xxx；/etc/profile 追加变量；重启；env 核对；./demo -platform linuxfb

流程只有一条。剩下的全是板级差异：工具链叫什么、库落到哪个目录、变量前缀是 QT_QWS_ 还是 QT_QPA_。差异集中在第十三章那张表里，前面各章讲的都是「为什么」。

二、确认板子的基本情况 #

动手前先把板子问清楚。七篇旧稿里所有「莫名编译失败」「拷过去跑不起来」，一半能在这里提前掐掉。

先跑这几条命令 #

板子串口登录后，或 NFS 挂载后从 PC 上 chroot 进去，把这几个结果抄下来。

bash
uname -a                          # 内核版本、架构、主机名
cat /proc/cpuinfo | head -20      # CPU 型号、核数
ldd --version                     # glibc 版本，或告诉你这是不是 uClibc
ls -l /dev/fb*                    # 有没有 framebuffer，几个
cat /proc/fb                      # fb0 绑的哪个驱动
ls -l /dev/input/                 # event0 / event1 / mice / touchscreen0
ls /usr/lib/libEGL* /usr/lib/libGLESv2*   # 有没有 EGL / GLES，eglfs 的前提
ls /usr/lib/libts*                # 板子上是否已经带了 tslib

结果对应到六个决策点。

采集项 命令 影响后面的什么
CPU 架构与浮点 cat /proc/cpuinfo、readelf -A 选 gnueabi（软浮点）还是 gnueabihf（硬浮点）工具链
libc 类型与版本 ldd --version 工具链 glibc 必须 ≤ 它；uClibc 板子得换工具链
屏幕分辨率与色深 /proc/fb、fbset Qt4 的 -depths；Qt5 linuxfb 的 :size=
输入设备节点 ls /dev/input/ TSLIB_TSDEVICE、QT_QPA_GENERIC_PLUGINS 里的 event 号
GPU 与 EGL ls /usr/lib/libEGL* 走 eglfs 还是退回 linuxfb
是否预装 Qt find / -name "libQt5Core*" 直接用官方的，还是自己编一套覆盖

glibc 这条线，先看死 #

板子的 ldd --version 给出的是上限。工具链自带的 glibc 高于它，程序能编出来，一运行就死在动态链接器上。

bash
ldd --version | head -1                    # 板子上执行，会输出 ldd (GNU libc) 2.23
arm-linux-gcc -v 2>&1 | grep -i glibc      # 工具链自带的版本，在 PC 上看
strings /opt/FriendlyARM/toolschain/4.5.1/arm-none-linux-gnueabi/libc/lib/libc.so.6 \
  | grep -m1 "GNU C Library"

板子 2.23、工具链 2.31，编出来的 Qt 会在启动时喊：

text
./demo: /lib/libc.so.6: version `GLIBC_2.28' not found (required by /opt/qt5.5.1/lib/libQt5Core.so.5)

两个解法。换一把老工具链最省事；或者把板子 rootfs 里的 libc.so.6、libpthread.so.0、libm.so.6 拷进工具链 sysroot，让链接器按老符号表干活：

bash
SYSROOT=/opt/FriendlyARM/toolschain/4.5.1/arm-none-linux-gnueabi/libc    # 覆盖前先备份
cp /path/to/board-rootfs/lib/libc.so.6      $SYSROOT/lib/
cp /path/to/board-rootfs/lib/libpthread.so.0 $SYSROOT/lib/

覆盖之后要重新 configure 重编 Qt，旧二进制里已经记死了符号版本。

浮点 ABI 别混 #

arm-linux-gnueabi- 是软浮点，arm-linux-gnueabihf- 是硬浮点。混用的表现是编得出来、跑起来 Illegal instruction。

bash
readelf -A ./demo | grep -i -E "VFP|Tag_ABI_VFP_args"

硬浮点的输出里有一行 Tag_ABI_VFP_args: VFP registers，软浮点要么没这一项，要么写着 compatible。i.MX6 那块板（Cortex-A9，带 NEON）用 arm-linux-gnueabihf-，mkspecs 里还加了 -mfloat-abi=hard -mfpu=neon；Tiny6410 那代 ARM11 用 arm-linux-gcc 软浮点，两套库绝不能互相拷。

板子自带的 Qt 要查清楚 #

厂商给的 rootfs 里塞 Qt 是常见操作。先查清楚，能省一整轮编译。

bash
find / -name "libQt5Core.so*" 2>/dev/null
find / -name "libQtCore.so*" 2>/dev/null
which qmake qmake-qt5 2>/dev/null
ls /usr/lib/qt5/plugins/platforms/ 2>/dev/null

i.MX6 那块板（主机名 M6708）的 /etc/profile 里就出现了两套路径：一套自己编的 /opt/qt5.5.1，一套系统自带的 /usr/lib/qt5。两套并存时环境变量指向谁，跑的就是谁。这种情况最容易出「我明明换了库怎么没变化」——变量被后面的 export 覆盖了。

七篇旧稿一共五块板子：友坚恒天 S3C6410（有两篇写的是同一块板、同一套流程）、FriendlyARM Tiny6410、两块没写板名的通用 ARM 板、迈瑞 M6708（i.MX6）。板子与参数的对应关系见第十三章那张表。

三、工具链与 sysroot #

工具链是整条链子的起点。它选错了，后面编出来的东西全是废的，而且是在板子上才废。

旧稿用过的几把工具链 #

工具链包 / 前缀 出处 特点
arm920t-eabi-4.1.2 → /opt/toolchains/arm920teabi/bin S3C6410 老稿 装完目录叫 arm920teabi，命令仍是 arm-linux-gcc
arm-linux-gcc-4.3.2 → /usr/local/arm/ 通用稿 默认装到 /usr/local/arm/4.3.2/bin
arm-linux-gcc-4.3.3 / 4.4.3 → /opt/FriendlyARM/toolschain/4.4.3/bin 友善之臂 PATH 里挂 4.4.3，包里名字常与版本号对不上，以实际解压结果为准
arm-linux-gcc-4.5.1-v6-vfp-20101103 → /opt/FriendlyARM/toolschain/4.5.1/bin Tiny6410 新版稿 带 v6 指令与 VFP，软浮点接口
arm-linux-gnueabi-g++ Qt5.4.2 稿 Debian 风格，软浮点
arm-linux-gnueabihf-gcc i.MX6 稿 硬浮点，Cortex-A9 只有这一条路
arm-none-linux-gnueabi- Qt4.7.4 稿 Sourcery G++ Lite，CodeSourcery 出的一套

名字里的 none 表示不指定厂商，eabi 是 ARM EABI 接口，末尾的 hf 是 hard float。前缀只是文件名，真正决定兼容性的是它内部的 glibc 和浮点配置。

装上，并让 PATH 生效 #

解压到根目录是这几套包的统一做法，包内已经带了 /opt/... 的完整层级。

bash
sudo cp arm-linux-gcc-4.5.1-v6-vfp-20101103.tgz /tmp
cd /tmp
sudo tar xvzf arm-linux-gcc-4.5.1-v6-vfp-20101103.tgz -C /    # -C 大写，后面有空格

sudo tar zxvf arm920t-eabi-4.1.2.tar.gz -C /                  # 老包，顶层目录名看解压结果
ls /opt/toolchains/arm920teabi/bin

然后挂 PATH。写哪个文件决定谁能用到它。

写入位置 谁生效 适用
~/.bashrc 当前用户 单人开发，sudo make 时不会生效
/etc/bash.bashrc 所有交互式 shell 多用户，老稿常用
/etc/profile.d/arm-toolchain.sh 登录 shell + sudo -i 相对干净，推荐 
bash
export PATH=/opt/FriendlyARM/toolschain/4.5.1/bin:$PATH    # 路径按实际解压结果改
source ~/.bashrc
arm-linux-gcc -v

-v 出得来版本信息，说明装好了。出不来先 echo $PATH，再看 ls /opt/FriendlyARM/toolschain/4.5.1/bin 里到底有没有那个可执行文件。

两个必踩的坑 #

坑一：64 位系统上提示「找不到该文件」。 二进制是 32 位的，系统缺 32 位加载器，报错却说文件不存在。判断依据：file /opt/.../bin/arm-linux-gcc 显示 ELF 32-bit LSB executable，而系统是 x86_64。

bash
sudo apt-get install g++-multilib
sudo apt-get install lsb-core       # 老系统上这一步常常是必须的
sudo apt-get install ia32-libs      # 更老的 Ubuntu 才有这个包

坑二：终端里 arm-linux-gcc -v 正常，脚本里 sudo ./build.sh 就 Command not found。 变量写在了 ~/.bashrc，那是当前用户的；sudo 换成了 root，root 的 shell 不读你的 .bashrc。Qt5.4.2 那篇稿子就卡在这里，作者的原话是「这个错误很是无厘头」。

三种解法，按干净程度排。前两种改环境：

bash
sudo -E ./build.sh                                          # 1. 透传环境变量
sudo tee /etc/profile.d/arm-toolchain.sh <<'EOF'            # 2. 给 root 也挂上 PATH
export PATH=/opt/FriendlyARM/toolschain/4.5.1/bin:$PATH
EOF

第三种改 qmake.conf，把绝对路径写死，最稳：

ini
QMAKE_CC = /opt/FriendlyARM/toolschain/4.5.1/bin/arm-linux-gcc -lts

Tiny6410 那篇用的就是第三种——sudo 是谁都无所谓。

sysroot 是什么，为什么要管 #

工具链自己带了一份「目标系统的头文件和库」，叫 sysroot。configure 期间找 stdio.h、链接时找 libc.so，都从这份副本里拿。

bash
arm-linux-gcc -print-sysroot                                # 工具链的 sysroot 在哪
echo | arm-linux-gcc -E -v - 2>&1 | sed -n '/search starts here/,/End of search list/p'

问题出在副本比板子新。板子的 /lib/libc.so.6 是 2.23，工具链 sysroot 里是 2.31，链接器就按 2.31 的符号表办事，Qt 库里带上了 GLIBC_2.28 这种新符号。

规矩一句话：sysroot 里的 libc 只能来自板子，不能比板子新。

bash
SYSROOT=$(arm-linux-gcc -print-sysroot)                     # 覆盖前先备份原目录
sudo cp -a $SYSROOT/lib $SYSROOT/lib.bak
sudo cp -a /path/to/board-rootfs/lib/libc.so.6       $SYSROOT/lib/
sudo cp -a /path/to/board-rootfs/lib/libm.so.6       $SYSROOT/lib/
sudo cp -a /path/to/board-rootfs/lib/libpthread.so.0 $SYSROOT/lib/
sudo cp -a /path/to/board-rootfs/usr/lib/libstdc++.so.6* $SYSROOT/usr/lib/

覆盖完，Qt 要重新 configure 重编。旧的 .o 已经记死了符号版本，make clean 都不够，直接删掉 build 目录最保险。

四、编 Qt 库并装到板子 #

这一步的目标不是「编译成功」，是「得到一份能躺进板子根文件系统、并且和板子 glibc 对齐的库」。

为什么要三份 qmake #

Qt4 时代的老稿子反复做同一件事：把一份源码解压成三份，编出三个 qmake。

版本 编给谁 用途 落地目录示例
qmake-x11 宿主机 x86 在 PC 上直接跑 Qt 程序，做界面设计 /usr/local/Trolltech/Qt-4.8.5
qmake-x86 宿主机 x86，-embedded x86 配合 qvfb，没有板子时模拟板子的屏幕 /usr/local/Trolltech/QtEmbedded-4.8.5
qmake-arm 目标板 ARM 真正往板子上跑的那份 /usr/local/Trolltech/QtEmbedded-4.8.5-arm

三个 qmake 同名，编完立刻改名，否则永远不知道自己在用哪一个：

bash
cd /usr/local/Trolltech/QtEmbedded-4.8.5-arm/bin && mv qmake qmake-arm && qmake-arm -v

目录准备 #

源码不支持 in-source 编译，一个目录只能编一次，所以必须复制三份：

bash
tar xzf qt-everywhere-opensource-src-4.8.5.tar.gz
sudo mkdir -p /usr/local/qt-pc /usr/local/qt-x86 /usr/local/qt-arm
sudo cp -a qt-everywhere-opensource-src-4.8.5/. /usr/local/qt-pc/
sudo cp -a qt-everywhere-opensource-src-4.8.5/. /usr/local/qt-x86/
sudo cp -a qt-everywhere-opensource-src-4.8.5/. /usr/local/qt-arm/
mkdir -p /home/qt/qt-x86 /home/qt/qt-x11 /home/qt/qt-arm /home/qt/qt-creator /home/qt/tslib

最后一行是 Qt4.7.4 那篇的目录习惯，用 /home/qt 而不是 /usr/local，两种都行。

改 mkspecs，让 Qt 知道用哪把交叉编译器 #

Qt4 走 mkspecs/qws/linux-arm-g++/qmake.conf，Qt5 走 mkspecs/linux-arm-gnueabi-g++/qmake.conf。

Tiny6410（Qt 4.8.5，绝对路径 + -lts）

ini
QMAKE_CC         = /opt/FriendlyARM/toolschain/4.5.1/bin/arm-linux-gcc -lts
QMAKE_CXX        = /opt/FriendlyARM/toolschain/4.5.1/bin/arm-linux-g++ -lts
QMAKE_LINK       = /opt/FriendlyARM/toolschain/4.5.1/bin/arm-linux-g++ -lts
QMAKE_LINK_SHLIB = /opt/FriendlyARM/toolschain/4.5.1/bin/arm-linux-g++ -lts

QMAKE_AR         = /opt/FriendlyARM/toolschain/4.5.1/bin/arm-linux-ar cqs
QMAKE_OBJCOPY    = /opt/FriendlyARM/toolschain/4.5.1/bin/arm-linux-objcopy
QMAKE_STRIP      = /opt/FriendlyARM/toolschain/4.5.1/bin/arm-linux-strip

Qt4.7.4（CodeSourcery，必须挂 -lts）

ini
QMAKE_CC = arm-none-linux-gnueabi-gcc -lts
QMAKE_CXX = arm-none-linux-gnueabi-g++ -lts
QMAKE_LINK = arm-none-linux-gnueabi-g++ -lts
QMAKE_LINK_SHLIB = arm-none-linux-gnueabi-g++ -lts

-lts 不加，编到触摸相关代码就报错。这一条老稿专门用感叹号强调过。

Qt5.4.2（软浮点，linux-arm-gnueabi-g++）

ini
QT_QPA_DEFAULT_PLATFORM = linuxfb
QMAKE_CFLAGS_RELEASE   += -O2 -march=armv7-a
QMAKE_CXXFLAGS_RELEASE += -O2 -march=armv7-a
QMAKE_CC = arm-linux-gcc
QMAKE_AR = arm-none-linux-gnueabi-ar cqs
QMAKE_OBJCOPY = arm-none-linux-gnueabi-objcopy
QMAKE_NM = arm-none-linux-gnueabi-nm -P
QMAKE_STRIP = arm-none-linux-gnueabi-strip

base 文件（linux.conf、gcc-base-unix.conf、g++-unix.conf）照 mkspecs/linux-arm-gnueabi-g++ 原样保留。QMAKE_CC 是 arm-linux-gcc，QMAKE_AR 却是 arm-none-linux-gnueabi-ar——两套前缀混写。工具链 bin 目录里两个名字都有符号链接时没事，没有就报 not found。抄别人 qmake.conf 前先 ls 一遍自己的 bin 目录。

i.MX6（Qt 5.5 / 5.9，硬浮点 + NEON）

ini
MAKEFILE_GENERATOR = UNIX
CONFIG += incremental
QMAKE_INCREMENTAL_STYLE = sublib
QT_QPA_DEFAULT_PLATFORM = linuxfb        # 走 eglfs 时改成 eglfs

include(../common/linux.conf)
include(../common/gcc-base-unix.conf)
include(../common/g++-unix.conf)

IMX6_CFLAGS = -march=armv7-a -mfloat-abi=hard -mfpu=neon -mtune=cortex-a9
QMAKE_CFLAGS   += $$IMX6_CFLAGS
QMAKE_CXXFLAGS += $$IMX6_CFLAGS

QMAKE_CC = arm-linux-gnueabihf-gcc
QMAKE_CXX = arm-linux-gnueabihf-g++
QMAKE_LINK = arm-linux-gnueabihf-g++
QMAKE_LINK_SHLIB = arm-linux-gnueabihf-g++

七、显示后端：framebuffer、linuxfb 与 eglfs #

Qt 在板子上画东西，必须先拿到一块能画的表面。三种后端就是三种拿法。

后端 依赖 性能 适用 缺东西时的报错
linuxfb 内核 framebuffer，/dev/fb0 可写 不高，纯 CPU 拷贝 无 GPU、或 GPU 驱动不全 linuxfb: Failed to open framebuffer device
eglfs EGL + GLES 驱动 + GPU 好，硬件加速 有 GPU 且驱动齐全 EGL not found、Could not create the EGL display
wayland 一个运行的 compositor（weston） 好，支持多窗口 板子上跑 Wayland 桌面 Failed to create display、连不上 socket
offscreen 无 — 无屏幕，只渲染到内存 插件缺失时才会用到
qvfb PC 上的虚拟 framebuffer — 没有板子时模拟 只在 Qt4 x86 版里存在

linuxfb 直接往 framebuffer 里写像素，最土也最稳。eglfs 把 EGL 直接绑到一个 framebuffer 或 DRM 上，跳过窗口系统，速度快但要求 GPU 驱动这一环完整。wayland 多一层 compositor，板子得先跑起来 weston，内存要求也高。

linuxfb 怎么写 #

Qt5：

bash
export QT_QPA_PLATFORM=linuxfb                            # 最简
export QT_QPA_PLATFORM=linuxfb:tty=/dev/fb0               # 指定 tty
export QT_QPA_PLATFORM=linuxfb:fb=/dev/fb0:size=800x480   # 指定尺寸

size= 不给时按 framebuffer 的驱动信息推断，推错就是画面花掉或者只占屏幕一角。

Qt4 没有 QPA，linuxfb 是编进库里的图形后端，靠编译期开关：

bash
./configure ... -qt-gfx-linuxfb -no-gfx-qvfb ...
export QWS_DISPLAY=LinuxFb:/dev/fb0                     # 运行时指定
./demo -qws -display "LinuxFb:/dev/fb0"                 # 或命令行指定

-qt-gfx-linuxfb 没加上，Qt4 的库就只认 qvfb，板子上必然黑屏。

eglfs 怎么写 #

bash
export QT_QPA_PLATFORM=eglfs
export QT_QPA_EGLFS_FB=/dev/fb0
export QT_QPA_EGLFS_TSLIB=1          # 让 eglfs 自己处理触摸
export FB_MULTI_BUFFER=2
export QT_EGLFS_IMX6_NO_FB_MULTI_BUFFER=1

前置条件是板上真的有一套能用的 EGL：

bash
ls /usr/lib/libEGL.so* /usr/lib/libGLESv2.so*
ls /usr/lib/libGAL.so /usr/lib/libVIVANTE.so 2>/dev/null   # i.MX6 的 Vivante 驱动

libGAL 是 Vivante 的硬件抽象层，eglfs_viv 后端就是通过它跟 GPU 说话。i.MX6 的 qmake.conf 里注释掉的那几行 -lEGL -lGLESv2 -lGAL，打开它们意味着编译期就链上 EGL，运行时缺库直接起不来。宁可先注释着用 linuxfb 跑通，再回头开 eglfs。

报错怎么读 #

报错 缺什么 处理
This application failed to start because no Qt platform plugin could be initialized plugins/platforms/ 没拷，或 QT_QPA_PLATFORM_PLUGIN_PATH 指错 ls plugins/platforms/ 确认 libqlinuxfb.so 在
EGL not found / Failed to create EGL display GPU 驱动、libEGL.so 缺失，或板子不支持该后端 退回 linuxfb，或补装驱动

排查插件加载过程，打开插件调试开关，它会一行行告诉你哪个 .so 被试过、为什么被拒：

bash
QT_DEBUG_PLUGINS=1 ./demo -platform linuxfb 2>&1 | head -30

这段输出里能看到 Got keys from plugin meta data ("linuxfb") 之类的行。有这个行说明插件找到了，问题在设备；没有这行，问题在路径。

八、触摸与输入设备 #

触摸屏不工作是嵌入式 Qt 的高频问题。四个条件缺一不可：硬件有触摸屏、内核加载了驱动、有校准库、程序用了校准库。

先确认驱动在 #

bash
cat /dev/input/event0 | hexdump -C | head   # 用手点屏幕，有数据滚出来就说明驱动通了
ls -l /sys/class/input/
cat /proc/bus/input/devices

点一下就出乱码，是驱动正常的标志。这个乱码是原始坐标，没校准，直接喂给程序也点不准。

交叉编 tslib #

bash
tar xzf tslib-1.4.tar.gz
cd tslib
./autogen.sh                                   # 缺工具就装 autoconf automake libtool
echo "ac_cv_func_malloc_0_nonnull=yes" > arm-linux.cache
./configure --host=arm-linux --cache-file=arm-linux.cache --prefix=/usr/local/tslib
make && make install

ac_cv_func_malloc_0_nonnull=yes 不能省。不写就报 undefined reference to 'rpl_malloc'——gnulib 的 malloc 替换检测在老系统上判错，缓存文件直接告诉它「有」就绕过去了。

--prefix 也可以写 $(pwd)/tmp 先装到临时目录，再 cp -rfd * /usr/local/tslib/ 拷进系统目录（-d 保住符号链接）。

新版 gcc 上编 ts_calibrate 会撞到这个：

text
ts_calibrate.c:229:11: error: call to '__open_missing_mode' declared with attribute error:
open with O_CREAT in second argument needs 3 arguments

O_CREAT 必须带第三个权限参数，改一行就好：

c
cal_fd = open(calfile, O_CREAT | O_RDWR);        // 修改前
cal_fd = open(calfile, O_CREAT | O_RDWR, 0777);  // 修改后

编完先验架构，这一步能挡掉一半后续问题：

bash
file /usr/local/tslib/bin/ts_test

输出应该是 ELF 32-bit LSB executable, ARM, EABI5 ...。显示 x86-64 就整个删掉重来，make clean 不管用，configure 缓存会带着错误结论继续跑。

ts.conf 的五行 #

ini
module_raw input
module pthres pmin=1
module variance delta=30
module dejitter delta=100
module linear

五行各管一段：input 从 /dev/input/eventN 读原始数据，pthres 压掉压力阈值以下的噪声，variance 过滤抖动，dejitter 再做一次时间去抖，linear 把原始坐标线性映射到屏幕坐标。第一行错成 module_rawinput（少个空格）等于没有输入源，触摸完全没反应，而且不报错——老稿里这个错字出现过好几次。

Qt4 怎么接 #

编译期必须带 -qt-mouse-tslib，运行时指定设备：

bash
export QWS_MOUSE_PROTO=Tslib:/dev/input/event1                                    # 只接触摸屏
export QWS_MOUSE_PROTO=Tslib:/dev/input/event1:MouseMan:/dev/input/mice           # 鼠标也接上

不带 -qt-mouse-tslib 编出来的库不认 Tslib: 前缀，写了也当没写。

Qt5 怎么接 #

两条路，选一条。

bash
export QT_QPA_GENERIC_PLUGINS=tslib:/dev/input/event1        # 路线一：QPA 的 generic plugin
export QT_QPA_GENERIC_PLUGINS=evdevtouch:/dev/input/event1   # 路线二：直接读内核事件

走 tslib 一定要把 libts 预加载进去，否则插件在运行时找不到符号：

bash
export LD_PRELOAD=/usr/lib/libts.so
export POINTERCAL_FILE=/etc/pointercal

LD_PRELOAD 里塞 $QTHOME1/plugins/platforms/libqoffscreen.so 是老稿的做法，作用是让动态链接器在启动阶段就把插件映射进来。副作用是这个插件必须存在，路径改了就直接 cannot open shared object。

校准 #

bash
export TSLIB_TSDEVICE=/dev/input/event1
export TSLIB_CALIBFILE=/etc/pointercal
/usr/local/tslib/bin/ts_calibrate

屏幕上依次出现十字，点完生成 /etc/pointercal。这个文件丢了就要重来，刷机之后必须重新校准。

bash
/usr/local/tslib/bin/ts_test          # 画板测试，笔迹跟手就说明校准成功
cat /etc/pointercal                   # 七个数，屏幕坐标映射系数

触摸不工作的排查顺序 #

顺序 检查 命令 结论
1 硬件有没有 cat /proc/bus/input/devices 没有设备名就是驱动没加载
2 事件节点对不对 点屏幕看 cat /dev/input/event1 有乱码说明节点选对了

九、跑第一个程序 #

前面所有工作都是为这一步。第一个程序跑通，后面才是写代码的事。

编一个 demo #

bash

qmake-arm -project        # Qt4 用改名后的 qmake，Qt5 用 qmake

make

-project 生成 .pro，再跑一次 qmake 生成 Makefile，make 出可执行文件。三步缺一步就是「没有规则可制作目标」。老稿更省事，直接用源码里的样例：把 .../demos/embedded 整个拷到 /home/nfs/，进去 ls 能看到三个小测试程序，一起编或单个编都行。

拷过去，跑起来 #

bash

./demo -platform linuxfb                            # Qt5

-qws 是 Qt4 启 QWS server 的开关。不带它，程序会去找一个已经在跑的 QWS，找不到就停在 QWS: cannot connect to socket。Qt5 改用 -platform 给后端名，命令行参数优先级高于 QT_QPA_PLATFORM 环境变量，调试时拿它临时切后端最快。屏幕亮起来、画面占满、能点能拖，第一步就算过了。

没有板子时怎么验 #

bash

缺库的土办法 #

板子上喊缺某个 .so，先别急着重编，满盘找一遍：

bash
locate libts-1.0.so.0
find / -name "libts-1.0.so.0*" 2>/dev/null       # 没有 locate 数据库时用它
ls /opt/toolchains/*/arm-linux/lib/libts*        # 交叉编译器目录里的那份
ls /usr/local/Trolltech/QtEmbedded-4.5.3/lib/libts*

拷的时候把软链接一起带上，只拷 .so.0 不拷 .so，链接期还是找不到：

bash
cp -a libts-1.0.so.0 libts-1.0.so.0.0.0 /home/nfs/opt/Qtopia/lib/

拷完必须重启板子。运行中的进程已经把旧的动态库映射进内存了。ldd 只看「能不能找到」，LD_DEBUG=libs ./demo 才告诉你「它去哪些路径找过」——排查时后者信息量大得多。

NFS 这条调试线 #

sudo /etc/init.d/portmap restart && sudo /etc/init.d/nfs-kernel-server restart

这串依次是：板子 IP、服务器 IP、网关、掩码、主机名、网卡、自动配置开关，最后是串口控制台。SAC0 是三星 SoC 的串口名，别的板子上叫 ttyS0 或 ttymxc0。三个 IP 必须同网段（板子、虚拟机、Windows 主机），虚拟机用桥接或 NAT 都行，但桥接下板子找得到虚拟机，NAT 下经常不行。

十一、IMX6 的移植要点 #

i.MX6 和 ARM11 老板子的差别集中在三处：硬浮点、GPU、Qt5。

维度 Tiny6410 i.MX6
CPU ARM11 (ARMv6) Cortex-A9 (ARMv7-A)
浮点 软浮点 硬浮点 + NEON
工具链前缀 arm-linux-gcc arm-linux-gnueabihf-
编译选项 无特殊 -march=armv7-a -mfloat-abi=hard -mfpu=neon -mtune=cortex-a9
GPU 无 Vivante，eglfs_viv
Qt 4.x，-qws 5.5.1 / 5.9.2，QPA
典型后端 linuxfb linuxfb 起步，eglfs 加速

Qt5 的 mkspecs 位置在 qtbase 下面，比 Qt4 深一层：

bash
$QTHOME/qtbase/mkspecs/linux-arm-gnueabi-g++/qmake.conf

qmake.conf 里要加的三组东西：QT_QPA_DEFAULT_PLATFORM、IMX6_CFLAGS、硬浮点前缀（完整内容见第四章）。

编译前先把依赖包装齐，少一个就在 configure 阶段停住：

bash
sudo apt-get install gawk wget git-core diffstat unzip texinfo gcc-multilib \
  build-essential chrpath socat libsdl1.2-dev xterm sed cvs subversion coreutils \
  texi2html docbook-utils python-pysqlite2 help2man make gcc g++ \
  desktop-file-utils libgl1-mesa-dev libglu1-mesa-dev mercurial \
  autoconf automake groff curl lzop asciidoc u-boot-tools

这套清单来自 Yocto 的宿主机依赖，编 Qt5 也用得上。libgl1-mesa-dev、libglu1-mesa-dev 是给 configure 探测 OpenGL 用的，即使最后 -no-opengl 也建议先装上，能少一轮报错。

编译安装之后，把编好树里的 lib、plugins、qml 三个目录拷到板子 /opt/qt5.5.1/ 下，落地结构是 /opt/qt5.5.1/{lib,plugins,qml}。

/etc/profile 的变量照第六章那两段贴。i.MX6 特有的几个：

变量 值 作用
QT_QPA_EGLFS_FB /dev/fb0 eglfs 绑哪块 fb
QT_QPA_EGLFS_TSLIB 1 让 eglfs 自己读 tslib
FB_MULTI_BUFFER 2 双缓冲
QT_EGLFS_IMX6_NO_FB_MULTI_BUFFER 1 关掉 fb 多缓冲，交给 Vivante
QT_QPA_PLATFORM_PLUGIN_PATH $QTHOME1/plugins 插件根
QT_PLUGIN_PATH $QTHOME1/qt5/plugins 系统 Qt 那套的插件根

FB_MULTI_BUFFER=2 和 QT_EGLFS_IMX6_NO_FB_MULTI_BUFFER=1 看着矛盾，实际是两层：前者对通用 eglfs 生效，后者是 i.MX6 专属开关，优先于前者。同时存在时 Vivante 后端自己管缓冲。

先 linuxfb 跑通，再切 eglfs。切换只改一个变量：

bash
export QT_QPA_PLATFORM=linuxfb:tty=/dev/fb0
export QT_QPA_PLATFORM=eglfs:fb=/dev/fb0        # 切到 GPU

切过去黑屏，就退回 linuxfb，先确认 libEGL、libGAL 在不在，再查 GPU 驱动有没有加载。i.MX6 的 GPU 驱动在 /usr/lib/libGAL.so，没有这个文件，eglfs_viv 一定起不来。板子上如果已经有系统自带的 Qt（/usr/lib/qt5），两套并存时环境变量指向谁就跑谁；想彻底避免混淆，把没用那套的 plugins 目录改名，或者干脆只留一套。

十二、其他板子与常见差异 #

前面讲的流程换个板子照样走，变的是参数，不是步骤。几种典型情况。

板子类型 能不能 eglfs 走什么后端 关键差异
无 GPU 的 ARM9/ARM11 不能 linuxfb 别在 eglfs 上耗时间，一定 EGL not found
有 GPU 但驱动没给 不能 linuxfb 先 ls /usr/lib/libEGL*，没有就是没有
有 GPU 且 BSP 完整（i.MX6） 能 eglfs 或 linuxfb 要 eglfs_viv，要 libGAL.so
uClibc 工控板 看板子 linuxfb 工具链必须是 uClibc 的，glibc 编的库一律不能用
自带发行版 Qt 的板 看板子 跟随发行版 直接用 /usr/lib/qt5，只配变量

通用 ARMv7 板（Qt5.4.2 那篇的板子）。 工具链 arm-linux-gcc 软浮点，-march=armv7-a，库落到 /usr/local/Trolltech/QtEmbedded-5.4.2-arm，后端 linuxfb。这套配置最通用，换板子只要改 -prefix 和后缀。

uClibc 的板子。 厂商 BSP 用 uClibc，那就必须找一把 uClibc 的工具链。glibc 编出来的 Qt 库在 uClibc 系统上一个符号都对不上，报错还特别含糊（Segmentation fault 或 cannot execute binary file）。判断方法：ldd --version 报 uClibc，或者板子上有 /lib/ld-uClibc.so.0。

自带 Qt 的板子省一轮编译。 i.MX6 那块（M6708）的 /usr/lib/qt5 就是一套能用的 Qt5，plugins 齐全。这种板子只需要配几个变量：

bash
export QT_QPA_PLATFORM_PLUGIN_PATH=/usr/lib/qt5/plugins
export QT_QPA_PLATFORM=linuxfb:tty=/dev/fb0
export QT_QPA_FONTDIR=/usr/lib/fonts
export LD_LIBRARY_PATH=/usr/lib:/lib:$LD_LIBRARY_PATH

代价是版本被厂商锁死，想用新特性还得自己编。

Qt4 和 Qt5 要在同一块板子上共存。 两套库的 soname 不同（libQtCore.so.4 和 libQt5Core.so.5），可以并存。切换靠变量：跑 Qt4 程序时 QTDIR 指向老的 QtEmbedded-4.5.3，跑 Qt5 时把 QT_QPA_PLATFORM_PLUGIN_PATH 指向新的 plugins。别指望一套变量同时喂饱两边——QT_QWS_* 和 QT_QPA_* 各管各的。

没有板子、或者板子还没到。 先用 x86 版 + qvfb 把界面跑通（第九章），等硬件到了只换编译目标，代码一行不用改。这是老稿子里最实用的习惯。全志 H3 和 mini2440 的完整项目实战在《完整项目》里，那边讲的是从建工程到发布的整条线，板级落地这一环直接套用本篇。

最后一条最不显眼：make install 阶段空间不够，报的却是一堆链接错误。板子存储小于 256MB 时，-nomake examples -nomake tools -nomake tests 三个必须全带上。

把三件事记牢，剩下的都是查表：库和板子的 glibc、浮点 ABI 对得上；显示后端和板子的 GPU 情况对得上；环境变量和库在板子上的真实路径对得上。三样对上，屏幕就亮；对不上，报错一定会指回来。板级移植没什么玄学，就是把这三次核对做实。
