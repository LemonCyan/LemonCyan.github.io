这篇只讲一件事：交叉编译出来的 Qt 程序，怎么在 ARM 板上真正跑起来。

讲什么：库依赖怎么查、库怎么带上板、库搜索路径怎么设、Qt 插件放哪、环境变量完整清单、缺库报错怎么解、开机自启与启动脚本、拔掉网线后怎么看日志。

不讲什么：工具链怎么搭，见同目录《交叉编译》；Qt 源码怎么往板上移，见《板级移植实战》；一个完整项目怎么从零组织，见《完整项目》。

阅读前提：你手上有一个 file 显示为 ARM 的可执行文件，或者在板上敲命令时被 error while loading shared libraries 挡回来了。

一、编译通过不等于能跑 #

链接器只看符号，不看板子 #

交叉编译时，-L 指的是 sysroot 里的库目录。链接器从 .so 里读符号表，名字对得上、符号全都解析得掉，就交付一个可执行文件。它不检查板上 /usr/lib 有没有同名文件，也不管你板子上是哪个版本的 glibc。

host 上 make 一路绿灯，拷到板上第一句就是 cannot open shared object file。这不是编译出错，是两个阶段各管各的：链接问「符号够不够」，运行问「文件找不找得到」。

三种失败，占九成 #

  1. 库没拷：板子上确实没有这个 .so。
  2. 路径没设：库在板上躺着，ld.so 不去那个目录找。
  3. 版本不配套：文件在、路径也对，架构或 ABI 对不上，报 wrong ELF class、version 'GLIBC_2.4' not found、undefined symbol。

分清这三件事，比背二十条命令有用。ldd 能把前两种当场指出来，第三种靠 file 和 readelf -V 判。

一个真实开场 #

text
/opt/qt4.8.5/apps/lincom: error while loading shared libraries: libts-1.0.so.0:
cannot open shared object file: No such file or directory

飞凌 OKMX6Q-C 板子上跑自编程序，第一句就是这个。libts-1.0.so.0 是 tslib 的库，触摸屏走它。板子启动过程里没有加载 tslib 与 qt4.8.5 的环境变量，LD_LIBRARY_PATH 中没有 $TSLIB_ROOT/lib 这一段，库文件放在那儿也找不到。第九章会把这条报错拆到底。

判「能跑」有三条：ldd ./app 没有 not found；界面正常上屏、触摸有反应、字体不是方块；串口拔掉、ssh 断开，程序还在跑，没被 SIGHUP 带走。三条都过才算部署完，第一条只是入场券。

二、程序依赖了哪些库 #

直接依赖看 NEEDED #

bash
arm-linux-gnueabihf-readelf -d WifiCarV2 | grep NEEDED

text
 0x00000001 (NEEDED)  Shared library: [libQtGui.so.4]
 0x00000001 (NEEDED)  Shared library: [libQtNetwork.so.4]
 0x00000001 (NEEDED)  Shared library: [libQtCore.so.4]
 0x00000001 (NEEDED)  Shared library: [libts-1.0.so.0]
 0x00000001 (NEEDED)  Shared library: [libstdc++.so.6]
 0x00000001 (NEEDED)  Shared library: [libgcc_s.so.1]
 0x00000001 (NEEDED)  Shared library: [libpthread.so.0]
 0x00000001 (NEEDED)  Shared library: [libc.so.6]

NEEDED 只列直接依赖。libQtGui.so.4 自己还拉着 libfreetype、libpng、libz，那是间接依赖，readelf 不展开，板上加载时一样得找到。查依赖要递归往下走，别只盯这张表。

Qt4 窗口程序要带什么 #

库 从哪来 干什么 缺了会怎样
libQtCore.so.4 Qt 构建目录 lib/ 事件循环、容器、文件 程序根本起不来
libQtGui.so.4 Qt 构建目录 lib/ 控件、绘图、字体 报 libQtGui.so.4 找不到
libQtNetwork.so.4 Qt 构建目录 lib/ socket、HTTP 用了 QT += network 就必带
libts-1.0.so.0 tslib 触摸读取与校准 触摸没反应，或直接报缺库
libstdc++.so.6 工具链 sysroot C++ 运行时 version 'GLIBCXX_3.4.9' not found
libgcc_s.so.1 工具链 sysroot 异常、栈展开 抛异常即崩
libfreetype.so.6 板子或自编 字形栅格化 字体全变方块
libpng、libjpeg 板子或自编 图片编解码 png/jpg 图标不显示
libz.so.1 板子 压缩 间接依赖，上层库加载不下去

libts-1.0.so.0 最容易漏：它不在 Qt 的 lib/ 里，在 tslib 安装目录，很多人拷库时只拷了 Qt 那一坨。

Qt5 的差异 #

GUI 拆成 libQt5Widgets、libQt5Gui、libQt5Core，还多一个 libQt5DBus（哪怕没用 dbus，libQt5Gui 在某些构建配置下也拉着它）。插件机制从 QWS 换成 QPA，平台插件仍叫 libqlinuxfb.so，但位置与加载方式都变了，第七章讲。

板子上原本有什么 #

拿板上已有库和 host 侧 sysroot 做差集，差出来的就是拷贝清单：

bash
ls /usr/lib /lib /usr/local/lib 2>/dev/null | sort -u > /tmp/board_libs.txt   # 板上执行

bash
ls /opt/qt4.8.6-arm/sysroot/usr/lib | sort -u > /tmp/host_libs.txt
diff /tmp/host_libs.txt /tmp/board_libs.txt | grep '^<'   # host 上执行

< 开头的行就是 host 有、板子没有的。这份清单直接当拷贝清单用，比凭记忆一个个拷靠谱。

别整目录往系统目录倒 #

把 host 的 /usr/lib 整个盖到板上 /usr/lib，核心库会被换掉，ldconfig 一跑，动态链接器自己都起不来，板子连 ls 都敲不了，只能重刷镜像。要么一个库一个库挑着拷，要么整目录拷到你自建的 /QtProgram/lib，系统目录一个字节不动。

三、用 ldd 查依赖 #

只在板上跑 ldd #

ldd 是拿本机的动态链接器去试解析。在 x86 的 host 上对一个 ARM 文件跑 ldd，它要么报 not a dynamic executable，要么拿 host 的库路径凑答案，结论不成立。

bash
cd /opt/qt4.8.5/apps && ldd ./lincom

text
        libts-1.0.so.0 => not found
        libQtGui.so.4 => /usr/local/Trolltech/QtEmbedded-4.8.6-arm/lib/libQtGui.so.4 (0x4002b000)
        libQtCore.so.4 => /usr/local/Trolltech/QtEmbedded-4.8.6-arm/lib/libQtCore.so.4 (0x400a1000)
        libstdc++.so.6 => /lib/libstdc++.so.6 (0x401a5000)
        libm.so.6 => /lib/libm.so.6 (0x401c1000)
        libc.so.6 => /lib/libc.so.6 (0x401d6000)
        /lib/ld-linux-armhf.so.3 (0x40000000)

三列读法：左边是 NEEDED 里的名字，中间是实际解析到的绝对路径，右边是加载基址。中间写着 not found，就是这条没解析成功，程序进不到 main。

bash
ldd ./lincom | grep 'not found'

一行都没有，说明库这一层过了，问题在插件或环境变量，跳到第七章。有输出，把名字抄下来进第四章。

库在板上，ldd 却说没有 #

bash
find / -name 'libts-1.0.so*' 2>/dev/null

2>/dev/null 别省，不然 /proc 和 /sys 会刷一屏权限错误。查到路径后看它是否落在搜索路径覆盖的目录里。落在 /opt/xxx/lib 这种自定义目录，就得靠 LD_LIBRARY_PATH 或 ld.so.conf 把它拉进来。

再确认文件本身没坏：

bash
file /usr/local/tslib/lib/libts-1.0.so.0; ls -l /usr/local/tslib/lib/libts-1.0.so.0

正确输出是 ELF 32-bit LSB shared object, ARM, EABI5。显示 x86-64 就是把 host 的库传上来了；大小为 0 或只有几百字节，就是 scp 断了只拷一半。权限不是 rwxr-xr-x 同样加载不了。

递归一层 #

ldd 只对能找到的库往下展开，not found 的它没法继续。所以顺序是：先修掉 not found，再跑一次 ldd，新冒出来的 not found 才是下一层的问题。这是收敛过程，不会一次到底。

四、库的三种带法 #

方式 做法 优点 缺点 适用场景
A 系统目录 + 配置 拷到 /usr/local/lib，配 ld.so.conf 或 LD_LIBRARY_PATH 所有程序共用，一次配好 污染系统目录，换版本容易打架 板子只跑一个 Qt 版本
B 程序目录 + rpath 库放进 /QtProgram/lib，链接时写 rpath 自包含，整目录迁移 每个程序多几十 MB，要重链接 交付、量产、多版本并存
C 静态链接 -static，库编进可执行文件 只有一个文件，没有库路径问题 体积大，插件仍是动态，字体仍要配 命令行小工具、单文件诊断程序

方式 A：拷到系统目录 #

bash
scp -r /opt/qt4.8.6-arm/lib/*.so* root@192.168.1.20:/usr/local/lib/    # host 上推
scp -r /usr/local/tslib/lib/*.so* root@192.168.1.20:/usr/local/lib/

bash
ldconfig; ldconfig -p | grep libts    # 板上执行

板上没有 ldconfig（BusyBox 精简版常砍掉），就退回 LD_LIBRARY_PATH，或者把 /usr/local/lib 写进环境变量脚本，第十章的开机自启里会带上。这条路的问题是升级：新版本盖旧版本，别的程序跟着变行为，出事难回溯。

方式 B：库跟着程序走 #

bash
mkdir -p /QtProgram/lib /QtProgram/plugins

bash
scp -r /opt/qt4.8.6-arm/lib/*.so* root@192.168.1.20:/QtProgram/lib/
scp -r /opt/qt4.8.6-arm/plugins/* root@192.168.1.20:/QtProgram/plugins/
scp WifiCarV2 root@192.168.1.20:/QtProgram/

再在链接阶段把 rpath 写进去，第六章给参数。这条路把所有依赖收在一个目录，tar 打包丢到另一块同型号板子上，解压就能跑，不用再配环境。量产镜像选它。

方式 C：静态链接 #

bash
QMAKE_LFLAGS += -static

前提是有一套静态编出来的 Qt。三条实情：静态 Qt 的插件（图片格式、sql 驱动）还是动态加载，静态不了；字体仍然要靠 QT_QWS_FONTDIR 指过去；全静态程序出段错误时，栈里连库名都没有，只能拿地址回查。

静态适合「拷过去就得跑起来看看」的诊断小工具，不适合带界面的正式程序。

裁一刀 #

bash
cp libQtGui.so.4 libQtGui.so.4.orig
arm-linux-gnueabihf-strip --strip-unneeded libQtGui.so.4
ls -l libQtGui.so.4.orig libQtGui.so.4

--strip-unneeded 掉调试符号，能砍掉一半到七成。别对同一份文件反复 strip 又反复用；先在 host 上跑一遍 ldd 确认依赖没断，再上板。.so 的符号表里有一部分是给动态链接器用的，砍错了表现是加载即崩、连报错都没有。

五、库搜索路径：LD_LIBRARY_PATH 与 ld.so.conf #

顺序 来源 谁决定 改完要不要重启
1 DT_RPATH（且没定义 DT_RUNPATH） 链接时的 -Wl,-rpath 重链接或 patchelf
2 LD_LIBRARY_PATH 当前环境变量 新开 shell 即生效
3 DT_RUNPATH 链接时 -Wl,--enable-new-dtags 重链接或 patchelf
4 /etc/ld.so.cache ld.so.conf + ldconfig 必须重跑 ldconfig
5 /lib、/usr/lib 链接器内置默认 不用改

知道这个顺序，就知道为什么「我明明 export 了还是找不到」，或者反过来「我没设环境变量它自己能跑」——走的是不同分支。

LD_LIBRARY_PATH 是临时的 #

bash
export LD_LIBRARY_PATH=/usr/local/Trolltech/QtEmbedded-4.8.6-arm/lib:$LD_LIBRARY_PATH
export LD_LIBRARY_PATH=/usr/local/tslib/lib:$LD_LIBRARY_PATH
./WifiCarV2 -qws

只在当前 shell 和它的子进程里生效。关终端、重开 ssh、换个 tty，全部失效。三个坑：

  • 尾部不写 :$LD_LIBRARY_PATH，会把系统原值整个覆盖掉，连 /lib 都不找。
  • su 到别的用户、sudo 执行，环境按 secure_path 重置，白设。
  • 开机脚本里 export 了，但脚本以 sh -c 跑、没 source 到，也白设。

ld.so.conf 是永久的 #

bash
echo /usr/local/Trolltech/QtEmbedded-4.8.6-arm/lib > /etc/ld.so.conf.d/qt.conf
echo /usr/local/tslib/lib > /etc/ld.so.conf.d/tslib.conf
ldconfig

先确认主配置确实 include 了子目录，BusyBox 系统里这一步经常是空的：

bash
cat /etc/ld.so.conf

text
include /etc/ld.so.conf.d/*.conf

拷了新库必须重跑 ldconfig #

/etc/ld.so.cache 是二进制索引。新目录写进 .conf 之后不跑 ldconfig，索引里没有它，链接器照旧找不到。这是「配置明明写了还是 not found」的头号原因。

bash
ldconfig; ldconfig -p | grep -i qt4

ldconfig -p 打的是缓存内容。这里看不到刚加的库，就是缓存没更新或目录写错了。

板上没有 ldconfig #

精简 rootfs 常常把 ldconfig 砍掉。三条退路：环境脚本里 export（第十一章干这事）；rpath 写进可执行文件（第六章）；调试时让链接器自己带路径：

bash
/lib/ld-linux-armhf.so.3 --library-path /QtProgram/lib:/usr/local/tslib/lib ./WifiCarV2 -qws

最后这条不依赖任何配置文件，用来判定「到底是库不在，还是路径没配」最干净。

一句话分工：LD_LIBRARY_PATH 给调试用，改完立刻生效；rpath 给交付用，写进文件跟着走。

六、rpath 与 $ORIGIN #

链接时写进去 #

bash
arm-linux-gnueabihf-g++ -o WifiCarV2 *.o \
  -L/opt/qt4.8.6-arm/lib \
  -lQtGui -lQtCore -lQtNetwork -lts \
  -Wl,-rpath,'$ORIGIN/lib'

两个细节，踩过一次就记住：

  • 必须是单引号。用双引号，shell 先把 $ORIGIN 展开成空串，rpath 变成 /lib，编译不报错，运行才出事。
  • $ORIGIN 是占位符，由动态链接器运行时替换成「可执行文件所在目录」，走实际路径，不认软链接的源路径。

qmake 工程里怎么写 #

bash
QMAKE_LFLAGS += -Wl,-rpath,\'\$\$ORIGIN/lib\'

\$\$ 是 qmake 的变量转义，\' 让生成的 Makefile 里保留单引号，绕开 qmake 与 shell 两层展开。写完 make 去 Makefile 里搜 rpath，看到 '$ORIGIN/lib' 原样在才算对。

配了不等于库到位 #

$ORIGIN/lib 目录不存在，动态链接器不会说「rpath 无效」，它默默跳过，最后统一报 cannot open shared object file。配完必须回读 ELF：

bash
readelf -d WifiCarV2 | grep -E 'RPATH|RUNPATH'

text
 0x0000000f (RPATH)  Library rpath: [$ORIGIN/lib:$ORIGIN/../lib]

RUNPATH 也算对，差别是它优先级比 LD_LIBRARY_PATH 低，且不向依赖库传递。想要老式 RPATH：

bash
-Wl,--disable-new-dtags,-rpath,'$ORIGIN/lib'

事后改：patchelf #

bash
patchelf --set-rpath '$ORIGIN/lib' WifiCarV2; patchelf --print-rpath WifiCarV2

host 上装的 patchelf 改 ARM 文件同样管用，它只动 ELF 的字符串段，不关心目标架构。改完拷到板上再用 readelf -d 复核，别只信 host 上的输出。

两者的分工 #

维度 LD_LIBRARY_PATH rpath
生效方式 环境变量，进程启动时读 写进 ELF 的 DT_RPATH / DT_RUNPATH
生效范围 当前 shell 与子进程 这个可执行文件，DT_RPATH 还向依赖库传递
持久性 关终端即失效 跟着文件走，重启不变
漏设概率 高：漏 export、漏 source、换用户丢 低：路径相对，整目录迁移不用改
调试成本 改完立刻生效，不重编 要重链接或 patchelf
能否被覆盖 用户可用 LD_LIBRARY_PATH 抢先 同左，但仍比 rpath 之后
适合干什么 临时验证、开机脚本兜底 生产交付、量产镜像

结论很直白：调试阶段用 LD_LIBRARY_PATH 快速试，定稿切 rpath，交付镜像里只认 rpath。让产线或客户去 export 环境变量，一定会漏。

七、Qt 插件的路径问题 #

插件不是普通库 #

platforms/libqlinuxfb.so、imageformats/libqjpeg.so、sqldrivers/libqsqlite.so，这些不靠 NEEDED 链拉起，Qt 运行时按名字去插件目录里 dlopen。于是出现一种很迷惑的场面：ldd 输出干干净净，一个 not found 都没有，程序还是起不来。原因就是 ldd 完全不管插件。

典型报错长这样 #

text
This application failed to start because no Qt platform plugin could be initialized.
Reinstalling the application may fix this problem.

Available platform plugins are: linuxfb, minimal, offscreen.

Qt4 用 QWS，报错换成另一套：

text
QWSDisplay::Data::init: Unable to connect to socket /tmp/qtembedded-0/QtEmbedded-0

或者干脆没窗口、没报错，程序默默退了。看到这两类信息，先怀疑插件目录，而不是库不全。

插件目录的结构 #

按可执行文件同级放 plugins/：

text
/QtProgram/
├── WifiCarV2
├── lib/
│   ├── libQtGui.so.4
│   └── libts-1.0.so.0
└── plugins/
    ├── platforms/libqlinuxfb.so
    ├── imageformats/libqjpeg.so
    └── sqldrivers/libqsqlite.so

platforms/ 这一层目录名不能改，Qt 按这个名字查；里面的 .so 也不能改名，加载器拼的是 libq + 平台名 + .so。

用环境变量指过去 #

bash
export QT_PLUGIN_PATH=/QtProgram/plugins
export QT_QPA_PLATFORM_PLUGIN_PATH=/QtProgram/plugins/platforms
export QT_QPA_PLATFORM=linuxfb
export QT_QWS_FONTDIR=/QtProgram/lib/fonts

Qt4 认 QT_PLUGIN_PATH，QWS 程序靠命令行 -qws 起服务端；Qt5 认 QT_QPA_PLATFORM_PLUGIN_PATH 加 QT_QPA_PLATFORM。两套都设上不冲突，混用同一份启动脚本时省心。

qt.conf 更省事 #

text
[Paths]
Prefix = /QtProgram
Plugins = plugins
Libraries = lib

放在可执行文件同目录。一份文件同时解决插件路径与库路径，不用 export 任何东西，也不用担心登录方式不同导致变量丢。迁移目录只改 Prefix 一行。

查它加载了哪个插件 #

bash
export QT_DEBUG_PLUGINS=1 && ./WifiCarV2 2>&1 | head -40
strace -f -e trace=open,openat ./WifiCarV2 -qws 2>&1 | grep -i plugin > /dev/ttySAC0

第一行给 Qt5，输出里写着试过哪些目录、哪个 .so 加载失败、失败原因。第二行给 Qt4，没有 QT_DEBUG_PLUGINS 就用 strace 看它开了哪些文件。

两个漏了就白干的插件 #

  • platforms/libqlinuxfb.so：不带，程序直接起不来，报上面那句 platform plugin。
  • imageformats/libqjpeg.so：不带，png 图标正常、jpg 图片全白。很多人以为图丢了，其实是解码插件没拷。

触摸那一环 #

TSLIB_PLUGINDIR 指错，触摸就废。Qt 靠 QWS_MOUSE_PROTO=tslib:/dev/input/event2 去调 tslib，tslib 再去 TSLIB_PLUGINDIR 里找模块。中间任何一环路径不对，表现都是「界面出来了，点屏幕没反应」，日志里只有一句设备打不开。

八、环境变量的完整清单 #

变量 作用 典型值 不设的后果
TSLIB_ROOT tslib 安装前缀 /usr/local/tslib 后续变量没法引用，整段失效
TSLIB_TSDEVICE 触摸设备节点 /dev/input/event1 触摸无响应
TSLIB_TSEVENTTYPE 事件类型 input tslib 按旧接口读，校准失败
TSLIB_CONSOLEDEVICE 控制台设备 none 校准程序往控制台画字符，屏幕花
TSLIB_CALIBFILE 校准结果文件 /etc/pointercal 每次启动都要重新校准
TSLIB_CONFFILE tslib 模块配置 $TSLIB_ROOT/etc/ts.conf 加载不到模块配置，触摸失效
TSLIB_PLUGINDIR tslib 模块目录 $TSLIB_ROOT/lib/ts 报模块找不到
TSLIB_FBDEVICE framebuffer 节点 /dev/fb0 校准画不出十字线
QTDIR Qt 安装前缀 /usr/local/Trolltech/QtEmbedded-4.8.6-arm/ 后面几条全错
PATH 可执行文件搜索路径 $QTDIR/bin:$PATH qmake、moc 用不了
LD_LIBRARY_PATH 库搜索路径 $QTDIR/lib:$TSLIB_ROOT/lib:... 报缺库
QT_PLUGIN_PATH Qt 插件根目录 $QTDIR/plugins 平台插件、图片格式全丢
QT_QWS_FONTDIR Qt4 字体目录 $QTDIR/lib/fonts 界面文字变方块
QWS_DISPLAY 显示后端与参数 LinuxFB:mmWidth200:0 起不来，或分辨率、字号不对
QWS_MOUSE_PROTO 鼠标与触摸协议 Tslib:/dev/input/event1 点不动
QWS_KEYBOARD 键盘设备 TTY:/dev/tty1 输入框收不到键
HOME 用户主目录 /root Qt 找不到配置目录，报警告
KDEDIR KDE 前缀（历史遗留） /opt/kde 无害，个别旧程序会抱怨
QTAPP 程序所在目录 $PWD 或写死 脚本里引用相对资源时找不到

合并成一份脚本 #

两块板子的写法有差异，取并集，落到 /etc/qt4_env：

bash
#!/bin/sh

if [ -c /dev/input/event0 ]; then
    INPUT_PATH=/dev/input
else
    INPUT_PATH=/dev
fi

##tslib
export TSLIB_ROOT=/usr/local/tslib
export TSLIB_TSDEVICE=$INPUT_PATH/event1
export TSLIB_TSEVENTTYPE=input
export TSLIB_CONSOLEDEVICE=none
export TSLIB_CALIBFILE=/etc/pointercal
export TSLIB_CONFFILE=$TSLIB_ROOT/etc/ts.conf
export TSLIB_PLUGINDIR=$TSLIB_ROOT/lib/ts
export TSLIB_FBDEVICE=/dev/fb0
export PATH=$TSLIB_ROOT/bin:$PATH
export LD_LIBRARY_PATH=$TSLIB_ROOT/lib:$LD_LIBRARY_PATH

##qt4.8.6
export QTDIR=/usr/local/Trolltech/QtEmbedded-4.8.6-arm/
export PATH=$QTDIR/bin:$PATH
export LD_LIBRARY_PATH=$QTDIR/lib:$LD_LIBRARY_PATH
export QT_PLUGIN_PATH=$QTDIR/plugins
export QT_QWS_FONTDIR=$QTDIR/lib/fonts

##qws
export QWS_DISPLAY="LinuxFB:mmWidth200:0"
export QWS_MOUSE_PROTO="Tslib:$INPUT_PATH/event1 MouseMan:$INPUT_PATH/mouse1"
export QWS_KEYBOARD=TTY:/dev/tty1

export KDEDIR=/opt/kde
export HOME=/root

LD_LIBRARY_PATH 分两行追加，先后顺序就是优先级：后写的那条排在前面。要让 Qt 的库优先，就把 Qt 那行放到最后。

两块板子的实际差异 #

项 Tiny4412（QtEmbedded-4.8.6-arm） OKMX6Q-C（qt4.8.5）
Qt 前缀 /usr/local/Trolltech/QtEmbedded-4.8.6-arm/ /opt/qt4.8.5
tslib 插件目录 /usr/lib/ts /usr/local/tslib/lib/ts
触摸设备 /dev/input/event1 /dev/input/event2
显示参数 LinuxFB:mmWidth200:0 linuxfb:mmWidth50:mmHeight130:0
鼠标协议 Tslib + MouseMan:/dev/input/mice tslib + mouseman:/dev/input/mice
环境脚本位置 /etc/qt4_env /etc/rc.d/qt_env.sh

数值别照抄。这是两块板子各自跑通的值，event1 与 event2 换板子就变，mmWidth 更是跟屏幕物理尺寸绑定。

怎么定位自己的值 #

bash
cat /proc/bus/input/devices | grep -E 'Name|Handlers'   # 触摸是哪个 event
ls /dev/fb*                                             # framebuffer 几个
find / -name 'libQtCore.so.4' 2>/dev/null               # Qt 装在哪
find / -name 'ts.conf' 2>/dev/null                      # tslib 模块在哪

Name= 是设备名，Handlers= 后面那个 event2 就是答案。别猜，猜错了排查方向全歪。

环境变量写哪个文件 #

位置 什么时候被读 适合放什么
/etc/profile 登录 shell 启动时 串口、ssh 登录后手动跑程序
/etc/qt4_env + 脚本里 . /etc/qt4_env 谁 source 谁生效 开机自启、启动脚本
程序同目录 qt.conf Qt 初始化时 插件与库路径，不依赖 shell
可执行文件的 rpath 加载时 库路径，最稳

这里有个真坑：开机自启的脚本不是登录 shell，/etc/profile 那套在它里面根本不执行。所以「我写进 profile 了，登录能跑，开机不起来」是必然结果，不是玄学。第九章 imx6 案例的第二种解法讲的就是这件事，第十一章会把两者接起来。

九、缺少库文件的典型报错 #

报错片段 真实含义 属于哪一类 怎么处理
libts-1.0.so.0: cannot open shared object file 板上没有这个库，或者路径不通 没拷 / 路径 拷库 + 设 LD_LIBRARY_PATH
Permission denied（接在上一行后面） 文件在，权限不可读 路径 chmod 755
wrong ELF class: ELFCLASS64 64 位库配了 32 位程序 版本 file 逐一核对，换同架构
Exec format error 整个程序是 x86 的 版本 交叉编译产物拷错了
version 'GLIBC_2.4' not found 板上 glibc 比编译时用的旧 版本 换同版本 sysroot 重编
version 'GLIBCXX_3.4.9' not found libstdc++.so.6 太旧 版本 拷工具链配套的 libstdc++
undefined symbol: _ZN7QWidget... 头文件与运行库不是同一版 Qt 版本 统一版本，别混 4.8.5 与 4.8.6
文件明明在，却报 No such file or directory 缺动态链接器 /lib/ld-linux-armhf.so.3 版本 工具链 ABI 不符（gnueabi 与 gnueabihf）
只有 libQtGui.so.4，没有 libQtGui.so 缺开发用符号链接 路径 ln -s libQtGui.so.4 libQtGui.so
This application failed to start because no Qt platform plugin... 插件不在插件路径里 插件 见第七章

前两条是「库没拷 / 路径没设」，中间六条是「版本不配套」，最后一条根本不是库的问题。拿这张表对一遍，比逐条搜论坛快。

OKMX6Q-C 那个案例 #

飞凌 OKMX6Q-C 板子上跑自编程序，报的就是：

text
/opt/qt4.8.5/apps/lincom: error while loading shared libraries: libts-1.0.so.0:
cannot open shared object file: No such file or directory

libts-1.0.so.0 是 tslib 的库。板子启动过程中没有加载 tslib 和 qt4.8.5 的环境变量，这些变量原本躺在 /etc/rc.d/qt_env.sh 里。库文件在板上，路径没进搜索范围——属于「路径没设」，不是「库没拷」。

解法一：先 source，再跑 #

bash
root@freescale /$ source /etc/rc.d/qt_env.sh
calibrated
root@freescale /$ ./dog

calibrated 是脚本里 ts_calibrate 打的，说明校准文件生成了。这一招适合当场验证，关掉终端就失效。

解法二：写进 /etc/profile #

把 qt_env.sh 里 tslib 与 qt4.8.5 两段搬进 /etc/profile，开机后直接跑程序：

bash
##tslib
export TSLIB_ROOT=/usr/local/tslib
export TSLIB_TSDEVICE=/dev/input/event2
export TSLIB_TSEVENTTYPE=input
export TSLIB_CONSOLEDEVICE=none
export TSLIB_CALIBFILE=/etc/pointercal
export TSLIB_CONFFILE=$TSLIB_ROOT/etc/ts.conf
export TSLIB_PLUGINDIR=$TSLIB_ROOT/lib/ts
export TSLIB_FBDEVICE=/dev/fb0
export PATH=$TSLIB_ROOT/bin:$PATH
export LD_LIBRARY_PATH=$TSLIB_ROOT/lib:$LD_LIBRARY_PATH

##qt4.8.5
export QTDIR=/opt/qt4.8.5
export PATH=$QTDIR/bin:$PATH
export LD_LIBRARY_PATH=$QTDIR/lib:$LD_LIBRARY_PATH
export QT_PLUGIN_PATH=$QTDIR/plugins
export QT_QWS_FONTDIR=$QTDIR/lib/fonts
export QWS_MOUSE_PROTO="tslib:/dev/input/event2 mouseman:/dev/input/mice"
export QWS_DISPLAY="linuxfb:mmWidth50:mmHeight130:0"

改完 sync 落盘再跑程序。QWS_MOUSE_PROTO 里 mouseman 那半段留着，触摸和 USB 鼠标能同时用；只写触摸，插鼠标就没反应。这两个解法只解决「路径」，库真缺的时候还是得先拷库。

五步排查 #

  1. ldd ./app | grep 'not found'，把缺的名字抄下来。
  2. find / -name '名字' 2>/dev/null，确认板上到底有没有。
  3. file 库路径，确认是 ARM 而不是 x86-64。
  4. echo $LD_LIBRARY_PATH，确认路径里有没有它所在的目录。
  5. ldd 干净了还起不来，转第七章查插件。

十、开机自启动 #

友善系的 qt4.d 套路 #

qt4_env 放 /etc，qt4.d 放 /etc/init.d，再让 rc 脚本调用它：

bash
cp qt4_env /etc/qt4_env && chmod 755 /etc/qt4_env
cp qt4.d /etc/init.d/qt4.d && chmod 755 /etc/init.d/qt4.d
reboot

/etc/init.d/qt4.d 就干三件事：引环境、保校准、启程序。

bash
#!/bin/sh
source /etc/qt4_env

if [ -f /etc/pointercal ]; then
    echo "use exist pointercal file ..."
else
    echo "touch screen to create pointercal file ..."
    /bin/ts_calibrate
fi

/QtProgram/start_qt.sh &

素材原文写的是 if [ -f etc/pointercal ]，少了开头的斜杠。cwd 是 / 时碰巧成立，开机脚本的 cwd 不一定是 /，照抄就会每次开机都重新校准。绝对路径别省。

关掉板子自带的 qtopia #

友善的板子自带 qtopia 桌面，它自己占着 QWS server。两个程序抢同一个 /tmp/qtembedded-0/QtEmbedded-0 socket，先起的占住，后起的直接退，表现是你的程序一启动就没影。禁掉它的启动：

bash
chmod -x /etc/init.d/qtopia

或者去 rc 脚本里把 qtopia 那行注释掉。禁用以后触摸也归自己的程序用，不再打架。

几种启动方式对照 #

方式 写在哪 触发时机 环境变量从哪来 适合
SysV 风格 init.d /etc/init.d/qt4.d + rc 链接 按 rc 序号 脚本里 source 友善系、老 rootfs
rcS 追加 /etc/init.d/rcS 挂载完根文件系统 脚本里 source BusyBox 精简系统
/etc/rc.local 文件本身 多用户启动末尾 有基础 PATH，其余自己设 临时验证
systemd /etc/systemd/system/*.service 按 target 与依赖 只认 Environment= 新一些的发行版
/etc/inittab respawn inittab 一行 进程退出即重启 继承 init 要求常驻不退出
登录 shell 自动跑 ~/.bash_profile 有人登录时 全都有 调试，不算自启

systemd 写法 #

text
[Unit]
Description=WifiCar Qt App
After=local-fs.target

[Service]
Type=simple
Environment=QTDIR=/opt/qt4.8.5
Environment=LD_LIBRARY_PATH=/opt/qt4.8.5/lib:/usr/local/tslib/lib
Environment=QT_QPA_PLATFORM=linuxfb
Environment=QT_PLUGIN_PATH=/opt/qt4.8.5/plugins
ExecStart=/QtProgram/start_qt.sh
Restart=always

[Install]
WantedBy=multi-user.target

bash
systemctl daemon-reload && systemctl enable --now wificar && journalctl -u wificar -n 50

Environment= 只认这里写的，/etc/profile 里那堆它一律不看。要么全写在 Unit 里，要么让 start_qt.sh 自己 source。

等设备节点出现 #

开机脚本跑得比驱动早，/dev/fb0 还没生成，程序就报打不开 framebuffer。加一句等：

bash
while [ ! -e /dev/fb0 ]; do sleep 1; done

十一、启动脚本怎么写 #

bash
#!/bin/sh

[ -e /etc/friendlyarm-ts-input.conf ] && . /etc/friendlyarm-ts-input.conf
[ -e /etc/qt4_env ] && . /etc/qt4_env

: ${TSLIB_TSDEVICE:=/dev/touchscreen}

if grep -Ei "\<ctp=(1|2|3)\>" /proc/cmdline >/dev/null; then
    TSLIB_CONFFILE=/etc/ts-mt.conf
    echo "-27 13757 -2071768 -9105 -32 34531248 65536 800 480" > /etc/pointercal
    sync
else
    TSLIB_CONFFILE=/etc/ts.conf
fi

export TSLIB_TSDEVICE
export TSLIB_CONFFILE
export TSLIB_PLUGINDIR=/usr/lib/ts
export TSLIB_CALIBFILE=/etc/pointercal

export QTAPP=/QtProgram
export QTDIR=/opt/qt4.8.5
export PATH=/bin:/sbin:/usr/bin:/usr/sbin:/usr/local/bin
export LD_LIBRARY_PATH=$QTDIR/lib:/usr/local/tslib/lib:/usr/local/lib
export QT_PLUGIN_PATH=$QTDIR/plugins
export QT_QWS_FONTDIR=$QTDIR/lib/fonts
export QWS_DISPLAY="LinuxFB:mmWidth200:0"
export QWS_KEYBOARD=TTY:/dev/tty1
export HOME=/root
export KDEDIR=/opt/kde

if [ -c "$TSLIB_TSDEVICE" ]; then
    export QWS_MOUSE_PROTO="Tslib:$TSLIB_TSDEVICE MouseMan:/dev/input/mice"
    if [ ! -s /etc/pointercal ]; then
        rm -f /etc/pointercal
        /usr/bin/ts_calibrate
    fi
else
    export QWS_MOUSE_PROTO="MouseMan:/dev/input/mice"
fi

cd /QtProgram || exit 1
exec ./WifiCarV2 -qws >> /var/log/qt_app.log 2>&1

逐段说清 #

  • true ${TSLIB_TSDEVICE:=/dev/touchscreen} 在素材里是这么写的，true 是内建命令，借它触发赋值不报错。写成 : ${VAR:=默认值} 更干净，效果一样。
  • /etc/friendlyarm-ts-input.conf 是友善给触摸板型打的标记，有就 source，没有就跳过。
  • /proc/cmdline 里 ctp=1|2|3 表示电容屏，校准参数不同，所以分两支，电容屏那支直接写死 pointercal。
  • 素材里 export QTAPP=$PWD 在开机场景下是错的，cwd 是 /。写死路径。
  • 素材里 export PATH=$QRDIR/bin:$PATH 把 QTDIR 敲成了 QRDIR，export LD_LIBRARY=$QTDIR/lib 少写了 _PATH。两处都得改，不改则库压根没进搜索路径，症状和没设一样。
  • exec 让程序替换掉 shell，PID 不变，systemd 或 init 发信号它能收到。
  • 日志用 >> 追加。用 > 每次启动覆盖，崩溃现场留不下来。

校准要能超时退出 #

ts_calibrate 是阻塞的，等你在屏上点五个十字。屏没接、触摸没通，脚本就永远卡在这，开机自启的效果就是黑屏。

bash
timeout 30 /usr/bin/ts_calibrate

BusyBox 没有 timeout，自己拼：后台跑、sleep 30、kill。

日志想留现场 #

bash
exec ./WifiCarV2 -qws >> /data/log/qt_app.log 2>&1
exec ./WifiCarV2 -qws >/dev/ttySAC0 2>&1

/var/log 常常是 tmpfs，重启即空，要留现场就放 /data 或挂 U 盘。串口设备名各板不同，/dev/ttySAC0、/dev/ttyO0、/dev/ttyAMA0 都见过，ls /dev/ttyS* 对一下。

调试时在脚本开头加 set -x，每条命令连展开后的参数一起打到串口，环境变量到底设成什么值一眼看见。

十二、远程调试与日志 #

通道 怎么连 优点 局限
串口 picocom -b 115200 /dev/ttyUSB0 网没通也能用，能看内核日志 慢，滚屏快，拷文件麻烦
ssh ssh root@192.168.1.20 能传文件、能开多窗口 网络没起来就废
日志文件 启动脚本重定向 事后可查，能带回 host 分析 要有可写分区

板子网络起不来、又没串口线，只能拔 SD 卡，把日志分区挂到 host 上看。

bash
strace -f -e trace=open,openat -o /tmp/trace.txt ./WifiCarV2 -qws
grep ENOENT /tmp/trace.txt | grep '\.so'

ENOENT 那些行就是动态链接器试过、但没有的路径。这份列表比任何文档都准，因为它就是你板子上的真实搜索顺序。

bash
export LD_DEBUG=libs && ./WifiCarV2 -qws 2>&1 | head -60 && unset LD_DEBUG

打出每个库从哪个目录找到、被谁依赖。LD_DEBUG=all 太吵，libs 够用；查完记得 unset，不然日志会把串口刷满。

bash
gdbserver :2345 ./WifiCarV2 -qws            # 板上
arm-linux-gnueabihf-gdb ./WifiCarV2         # host，然后 target remote 192.168.1.20:2345

host 上这份二进制必须是同一份、没 strip 的产物。strip 过的符号表没了，bt 出来全是地址。

十三、易错点速查 #

现象 根因 处理
ldd 全绿，程序还是起不来 插件没带或插件路径没设 QT_PLUGIN_PATH / qt.conf
登录后手动跑正常，开机不起来 开机脚本不是登录 shell，/etc/profile 没执行 脚本里 . /etc/qt4_env

文字全变方块 QT_QWS_FONTDIR 没设，或字体目录空 指到 lib/fonts，确认有 .ttf
wrong ELF class 32/64 位库混用 file 逐一核对
GLIBCXX_3.4.x not found 板上 libstdc++ 比工具链旧 拷工具链配套版本
