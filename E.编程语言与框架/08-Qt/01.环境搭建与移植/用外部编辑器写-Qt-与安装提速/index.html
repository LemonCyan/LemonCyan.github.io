这篇只讲两件事：不用 Qt Creator，改用 VS Code 这类外部编辑器写 Qt 怎么配；装 Qt 时下载龟速怎么提速。

讲这些：Qt Creator 到底替我们做了什么、外部编辑器要补哪几块能力、VS Code 的插件与路径配置、.pro 与 CMake 两条线怎么让编辑器认识、IntelliSense 的 include 路径与宏从哪来、构建与调试怎么落成配置文件、Qt 在线安装慢的根因与换源做法、安装器的网络参数。

不讲这些：Qt 的语法与控件教学、qmake 与 CMake 的完整语法、Qt for Android 的 SDK 与 NDK 链路、Windows 下 Visual Studio 的集成。这些归同目录其他篇和后续章节。

同目录另有两篇。Qt for Android 那篇走 Android SDK、NDK、Gradle 那条线；Windows 与 Visual Studio 集成那篇讲 MSVC 工具链、Qt VS Tools、.vcxproj 与 windeployqt。本篇只负责编辑器和下载速度这两件事。

一、为什么可以不用 Qt Creator #

先说一个容易混的事：Qt Creator 不是 Qt 的一部分。

Qt 的安装包给的是库加工具链：头文件、导入库、动态库、qmake.exe、moc.exe、uic.exe、rcc.exe。Qt Creator 是另一套东西，它把这些零件用一套工程模型串起来，再加上编辑器、调试前端和 Designer。串起来这件事有价值，但它独占不了任何环节——它按钮背后调的都是能单独调的命令行程序。拆开看更清楚：

环节 谁在真正干活 换掉 Qt Creator 后谁来干
编辑代码 Qt Creator 内置编辑器 VS Code、Trae，或任何编辑器
解析 .pro 与 CMakeLists qmake 与 CMake 本身 同一套工具，加编辑器插件
跑 moc、uic、rcc 构建系统里写死的规则 同一套规则（AUTOMOC 或 qmake 内置）
选编译器、拼编译命令行 Qt Creator 的 Kit 系统 环境变量 PATH 加 kit 配置
增量构建 构建按钮 CMake Tools、tasks.json、手敲命令
断点调试 内置的 gdb/cdb 前端 launch.json 加 cppdbg
拖控件画界面 集成的 Qt Designer 单独开 Designer，或直接手写 .ui

看最后一列就明白：没有一栏是「只有 Qt Creator 能做」。它省的是配置劳动，不是能力。

那为什么还有必要留一份 Qt Creator？三个场景值得留：要拖界面的时候 Designer 顺手；要动 Android kit 的时候它管 SDK 与 NDK 的分层；要跑 QML Profiler 或者看 Qt 自己的调试辅助输出的时候，它接得比自己拼的配置顺。其余时间，编辑器随你。

选哪一款，我们按实际用过的感受摆一起：

编辑器 可定制程度 AI 权限 配置成本 适合谁
VS Code 最高 中，AI 改不了编辑器以外的环境 高，要自己拼插件与配置文件 想完全掌控流程的人
Trae 中 高，能让 AI 直接配环境、改文件 低 不想折腾、要立刻写代码的人
Cursor / Antigravity 中 高 低 习惯在对话里改代码的人
纯命令行 最高 无关 最低，但全靠自己 命令行熟手

我们自己的用法是：日常写代码用 Trae，环境让它自己配；命令行里挂 opencode 做批处理。VS Code 留着当对照，因为它的配置项最全，能看清每一步到底发生了什么。

一句结论：不想做复杂配置，直接用 Trae。 想搞明白每个环节，往下读。

二、外部编辑器要具备什么能力 #

核心只有一句：外部编辑器缺的不是编辑能力，是「理解 Qt 构建流程」的能力。

文本编辑谁都会，可 Qt 工程不是把 .cpp 丢进编译器就能出 exe 的。一个带 Q_OBJECT 的类、一个 .ui、一个 .qrc，直接喂给 g++ 会死在三个地方：

text
widget.h     含 Q_OBJECT，g++ 编过去也不生成元对象代码
widget.ui    Qt Designer 的 XML，不是 C++
res.qrc      资源清单，不是 C++

Qt 的构建流程在编译器前面插了三道工序，加一道工程生成：

text
widget.h   --moc-->   moc_widget.cpp        信号槽与元对象代码
widget.ui  --uic-->   ui_widget.h           控件树变成 C++ 类
res.qrc    --rcc-->   qrc_res.cpp           资源编成字节数组
*.pro      --qmake--> Makefile 或 .vcxproj   源文件清单与编译规则

这四步 Qt Creator 在后台替我们跑了，换成 VS Code，就得靠插件或者构建系统自己接上。接不上，症状分三层：

text
编不过：fatal error: ui_widget.h: No such file or directory
链不过：undefined reference to `vtable for Widget'
跑不过：程序起来了，图片和图标全丢

第一层是 uic 没跑，第二层是 moc 没跑，第三层是 rcc 没跑。三个症状对应三道工序，认错了会白折腾半天。

所以外部编辑器要补齐的能力，列成清单是这些：

能力 具体要求 缺了会怎样
语法与补全 认得 Qt 头文件、认得 signals/slots 宏 满屏红线，跳转全失效
构建系统识别 能读 .pro 或 CMakeLists.txt 不知道工程里有哪些源文件
代码生成 触发 moc、uic、rcc 链接期缺 vtable，或 ui 头文件不存在
编译命令行 拼出 include 路径、库路径、宏定义 编译期找不到头文件
运行与调试 接 gdb 或 cdb，运行时能找到 DLL 断点打不上，或启动就报缺 DLL
任务编排 一键 build、run、debug 每次手敲四五条命令

补齐这三条路，任选：

路径 做法 适合
插件补齐 装 C/C++、CMake Tools、Qt 相关插件，让它读工程文件 想留在编辑器里点按钮
配置补齐 自己写 c_cpp_properties.json、tasks.json、launch.json 想每一步都看得见
脚本补齐 写几条 shell 或 bat，编辑器只当记事本 就想要最少的活动件

三条路可以混着用，但同一个环节别配两套。CMake Tools 管构建的时候，tasks.json 里再塞一份 cmake --build，两边的生成目录会打架。

三、VS Code 的 Qt 开发插件 #

VS Code 本体只是个编辑器，Qt 支持全部来自扩展。要装的就这么几个：

插件 管什么 不管什么
C/C++ 语法高亮、补全、跳转、IntelliSense 构建、启动调试
Qt Configure 记住 Qt 安装目录，按模板新建 Qt 工程 编译、调试
Qt Tools 调 qmake、uic、rcc 这类 Qt 工具 CMake 工程
CMake CMake 语法高亮与语言服务 选 kit、跑构建
CMake Tools 选 kit、configure、build、run、debug，加状态栏按钮 Qt 专属路径

安装方式两条：左侧扩展面板按名字搜，或者命令行：

bash
code --install-extension ms-vscode.cpptools
code --install-extension ms-vscode.cmake-tools

Qt 相关的两个插件去扩展市场搜名字装，别照抄网上抄来的 ID，各家改过。

装完先做一件事：设置 Qt 安装目录。

  1. 按 Ctrl + Shift + P 开命令面板
  2. 输入 >Set Qt Dir，回车
  3. 选 Qt 安装的根目录，比如 D:\Qt\Qt5.14.2

再打开 Qt Configure 的设置页，三个字段填满：

设置项 填什么 例子
QtDir Qt 安装根目录 D:\Qt\Qt5.14.2
MingwPath MinGW 工具链根目录 D:\Qt\Qt5.14.2\Tools\mingw730_64
Qt Kit Dir Kit 目录，多数时候同 MinGW 根 D:\Qt\Qt5.14.2\Tools\mingw730_64

填完记得选「应用到所有工作区」。只填当前工作区的话，换个项目又要来一遍。

想让它直接建工程，命令面板里敲 >New Qt Project，按提示走：

text
1. 输入项目名称
2. 选项目套件（kit）
3. 选 CMake 还是 qmake
4. 选要不要带 UI 组件

插件职责有重叠，这点要认：CMake Tools 已经能选 kit 和构建，Qt Tools 也能调一部分 Qt 工具，两个都开着就会互相抢生成目录。我们的做法是 CMake 工程只留 CMake Tools 管构建，Qt Tools 只用来调 uic 之类的小工具。

四、配置编译器与调试器 #

编译器不在 Qt 库里。Windows 上 Qt 安装器把 MinGW 和 CMake 当独立组件列在工具分类里，装 Qt 的时候要勾上；老版本的安装器里这两项在 Tools 下面单列。没勾的话，qmake 在，g++ 不在，配置怎么弄都编不过。

装完做一件事：让命令行能找到它们。先找到这三个目录。

text
路径1（MinGW 编译器）：C:\Qt\Tools\mingw1310_64\bin
路径2（CMake 工具）：  C:\Qt\Tools\CMake_64\bin
路径3（Qt 库）：        C:\Qt\6.8.0\mingw_64\bin

版本号一定和你的不一样。mingw1310_64 你机器上会是 mingw1120_64 之类，6.8.0 会是 6.5.0、6.7.0、6.10.1。照实际看到的目录名抄，别照抄这篇。

加进 PATH：

text
1. 按 Win 键，搜索「环境变量」
2. 点「编辑系统环境变量」
3. 点右下角「环境变量(N)...」
4. 在下方「系统变量」里找到 Path，双击
5. 点「新建」，粘贴第一条路径
6. 再点「新建」，粘贴第二条路径
7. 再点「新建」，粘贴第三条路径
8. 「确定」→「确定」→「确定」，三次全部关掉

三条都要加。只加前两条，g++ 和 cmake 有了，运行时找不到 Qt6Core.dll；只加第三条，qmake 有了，g++ 还是没有。

验证之前，把已经开着的终端和编辑器全关掉。PATH 是进程启动时读的，老进程读的是老值。

bash
gcc --version

text
gcc (x86_64-posix-seh-rev1, Built by MinGW-Builds) 13.1.0

bash
cmake --version

text
cmake version 3.27.7

bash
qmake --version

text
QMake version 3.1
Using Qt version 6.8.0 in C:/Qt/6.8.0/mingw_64/lib

第三条输出里的 Using Qt version ... in ... 是重点。它报的路径就是这套 Qt 的真实位置，后面配 CMake 的 CMAKE_PREFIX_PATH、配 IntelliSense 的 include 路径，都从这一行抄。

调试器单独说一句。MinGW 版配的是 gdb.exe，就在 MinGW 的 bin 目录里：

text
C:\Qt\Tools\mingw1310_64\bin\gdb.exe

gdb 和 gcc 必须是同一套工具链出的。拿一个 MinGW 的 gdb 去调 MSVC 编的程序，符号格式对不上，断点会变成摆设。

这一章踩过的坑，收成一张表：

症状 原因 处理
命令提示符里 gcc 说不是内部命令 PATH 没加，或加了没重开终端 重开终端；必要时重启编辑器
qmake 能用，编译找不到 QApplication 只加了 Qt\bin，没加 MinGW 和 CMake 三条路径补齐
编译过了，运行报缺 DLL Qt\6.x\mingw_64\bin 不在 PATH 加上，或把这些 DLL 拷到 exe 旁
断点打不上 gdb 与 gcc 不是同一套 用同一目录下的 gdb
32 位工程链 64 位库 PATH 里混了 32 位工具链 只留一套，位数对齐

五、让编辑器认识 .pro 与 CMake #

编辑器不读构建文件，就只认得「刚才点开过哪几个文件」。源文件清单、include 路径、链接哪些库，全在 .pro 或 CMakeLists.txt 里。让编辑器读进去，才谈得上补全和构建。两条路，各走一套。

先看 qmake。一个最小可用的 .pro：

text
QT       += core gui widgets
TARGET    = HelloQt
TEMPLATE  = app

SOURCES  += src/main.cpp src/widget.cpp
HEADERS  += src/widget.h
FORMS    += src/widget.ui
RESOURCES += src/res.qrc

这七行把 Qt 工程的骨架说全了：要哪些模块、工程类型是什么、源文件与头文件在哪、有几个 .ui 和 .qrc。qmake 读它，算出编译规则，生成 Makefile。

bash
qmake HelloQt.pro

生成物里有两样东西值得看：Makefile 和 Makefile.Debug 之类的变体，以及隐式规则里对 moc、uic、rcc 的调用。Qt Creator 点击构建时跑的就是这些。

这里有个必须认清的事实：VS Code 的 C/C++ 插件不认 .pro。 它只当普通文本，高亮都没有。想让编辑器理解 .pro，得靠 Qt Tools 之类的插件，或者干脆绕开——用 tasks.json 直接把 qmake 和 mingw32-make 串起来（见第七章）。

再看 CMake。Qt 6 起 CMake 是默认构建系统，一份能跑的 CMakeLists.txt：

cmake
cmake_minimum_required(VERSION 3.16)

project(HelloQt LANGUAGES CXX)

set(CMAKE_AUTOMOC ON)
set(CMAKE_AUTOUIC ON)
set(CMAKE_AUTORCC ON)
set(CMAKE_INCLUDE_CURRENT_DIR ON)

set(CMAKE_CXX_STANDARD 11)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

set(CMAKE_PREFIX_PATH "D:/Qt/6.10.1/mingw_64")

set(CMAKE_RUNTIME_OUTPUT_DIRECTORY ${CMAKE_SOURCE_DIR}/bin)

find_package(Qt6 REQUIRED COMPONENTS Widgets)

file(GLOB SOURCE_FILE   ${PROJECT_SOURCE_DIR}/src/*.cpp)
file(GLOB HEADER_FILE   ${PROJECT_SOURCE_DIR}/src/*.h)
file(GLOB UI_FILE       ${PROJECT_SOURCE_DIR}/src/*.ui)
file(GLOB RESOURCE_FILE ${PROJECT_SOURCE_DIR}/src/*.qrc)

add_executable(${PROJECT_NAME}
    ${SOURCE_FILE}
    ${HEADER_FILE}
    ${UI_FILE}
    ${RESOURCE_FILE}
)

target_link_libraries(${PROJECT_NAME} PRIVATE Qt6::Widgets)

几个关键点，一条条说：

CMAKE_AUTOMOC、CMAKE_AUTOUIC、CMAKE_AUTORCC 这三个开关，就是替 Qt Creator 干那三道工序的。关掉它们，Q_OBJECT 不生成 moc_*.cpp，链接期直接报 undefined reference to vtable for Widget。

CMAKE_PREFIX_PATH 指向 Qt 安装目录，CMake 靠它找 lib/cmake/Qt6。它配错，find_package(Qt6) 会报找不到。

file(GLOB ...) 省事，但有个坑：新加一个 .cpp 不会自动触发重新 configure，构建还按老清单走，表现为「文件明明在，符号找不到」。稳妥的写法是加 CONFIGURE_DEPENDS：

cmake
file(GLOB SOURCE_FILE CONFIGURE_DEPENDS ${PROJECT_SOURCE_DIR}/src/*.cpp)

网上流传的那份模板有个硬伤：写了两个 add_executable，一个是 add_executable(HelloQt main.cpp)，另一个才是带全部源文件的，还混进了 find_package(Qt5 COMPONENTS Widgets REQUIRED)。抄下来会撞两个错：

症状 来源 处理
multiple definition of main 两次 add_executable 都带 main.cpp 只留一个
找不到 Qt5::Widgets 或链接到 Qt5 库 Qt5 与 Qt6 混用 全篇统一 Qt6

两条路的概念对应，摆一起看：

概念 .pro CMakeLists.txt
工程类型 TEMPLATE = app add_executable(...)
源文件 SOURCES += add_executable 里列，或 GLOB
头文件 HEADERS += 可省，AUTOMOC 靠它识别
界面文件 FORMS += AUTOUIC 自动扫
资源文件 RESOURCES += AUTORCC 自动扫
模块依赖 QT += core gui widgets find_package 加 target_link_libraries
输出目录 DESTDIR CMAKE_RUNTIME_OUTPUT_DIRECTORY
生成物 Makefile 或 .vcxproj build/ 下的 Ninja 或 Makefile

六、IntelliSense 与头文件路径 #

满屏红线，根因只有两个：include 路径没给，宏定义没给。

先记住一个容易搞混的点：CMake Tools 和 C/C++ 插件是两套解析器。CMake 配通了、能编译了，IntelliSense 照样可以红一片，因为 C/C++ 插件不吃 CMakeLists.txt 的 include_directories，它只吃自己那份配置。

路径从哪来？问 qmake 最准，它知道这套 Qt 装在哪儿：

bash
qmake -query

text
QT_INSTALL_HEADERS:C:/Qt/6.8.0/mingw_64/include
QT_INSTALL_LIBS:C:/Qt/6.8.0/mingw_64/lib
QT_INSTALL_BINS:C:/Qt/6.8.0/mingw_64/bin
QT_INSTALL_PLUGINS:C:/Qt/6.8.0/mingw_64/plugins
QT_VERSION:6.8.0

QT_INSTALL_HEADERS 那一行就是要抄的东西。Qt 的头文件按模块分目录，QApplication 在 include/QtWidgets 下，QString 在 include/QtCore 下，所以光加一个 include 不够，得把模块目录也列进去。

工作区里建 .vscode/c_cpp_properties.json：

json
{
  "version": 4,
  "configurations": [
    {
      "name": "Qt-MinGW",
      "compilerPath": "C:/Qt/Tools/mingw1310_64/bin/g++.exe",
      "includePath": [
        "${workspaceFolder}/**",
        "C:/Qt/6.8.0/mingw_64/include",
        "C:/Qt/6.8.0/mingw_64/include/QtCore",
        "C:/Qt/6.8.0/mingw_64/include/QtGui",
        "C:/Qt/6.8.0/mingw_64/include/QtWidgets"
      ],
      "defines": [
        "QT_CORE_LIB",
        "QT_GUI_LIB",
        "QT_WIDGETS_LIB",
        "UNICODE",
        "_UNICODE"
      ],
      "cStandard": "c11",
      "cppStandard": "c++17",
      "intelliSenseMode": "windows-gcc-x64"
    }
  ]
}

defines 那几行不是凑数的。Qt 的头文件里有大量 #ifdef：QT_WIDGETS_LIB、QT_GUI_LIB、QT_CORE_LIB 决定走哪个分支、导出符号用 Q_DECL_IMPORT 还是 Q_DECL_EXPORT。宏不给，解析器走的是另一条分支，症状是「能打开的类反而标红」。

intelliSenseMode 要和工具链的位数对齐。64 位 MinGW 写 windows-gcc-x64，写错成 windows-gcc-x86，补齐会错乱，报一堆类型不匹配。

运行期还有个宏容易被忽略：Windows 上 qtmain 会把 main 重定向，工程里用的是 WinMain 风格入口时，需要 QT_NEEDS_QMAIN。纯 Widgets 工程碰不到，但报 undefined reference to WinMain 的时候，先回来查这条。

第二条路是吃编译数据库。让 CMake 把每条编译命令吐成 JSON，C/C++ 插件或 clangd 直接读：

bash
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON

产物是 build/compile_commands.json。两个设置项指向它：

json
{
  "cmake.exportCompileCommandsFile": true,
  "C_Cpp.default.compileCommands": "${workspaceFolder}/build/compile_commands.json"
}

这条路的优点是永远和真实编译命令一致：include 路径、宏、标准版本全从构建系统里来，不用手抄。缺点是要先 configure 一次，工程都编不过的时候它也没有。

红线排错，按症状对：

现象 原因 处理
#include <QApplication> 找不到 includePath 缺 include/QtWidgets 补模块目录
打开 Qt 头文件满屏红 defines 里缺 QT_WIDGETS_LIB 之类 补宏
ui_widget.h 标红 它是构建产物，在 build/ 下 includePath 加 build 目录，或先构建一次
补全有了，跳转进不去 Qt 源码 没有编译数据库 导出 compile_commands.json
只有 Qt 头文件报类型错误 intelliSenseMode 位数不对 改 windows-gcc-x64
改完配置没反应 配置写进了用户级，被工作区级覆盖 检查设置作用域

七、构建与任务配置 #

装了 CMake Tools，构建就变成一串按钮。顺序是固定的：先选 kit，再 configure，再 build。

text
Ctrl+Shift+P → CMake: Select a Kit
Ctrl+Shift+P → CMake: Configure
F7           → 构建（等同 CMake: Build）
Ctrl+Shift+P → CMake: Run Without Debugging

CMake: Select a Kit 弹出的列表长这样，挑带 MinGW 的那项：

text
GCC 13.1.0 x86_64-w64-mingw32        ← 选这个
Visual Studio Community 2022 Release - amd64
[Scan for kits]

列表里没有 MinGW，不是插件坏了，是它还没扫到。先跑一遍扫描再选：

text
1. Ctrl+Shift+P
2. 输入 CMake: Scan for Kits
3. 回车，等它扫完
4. 再执行 CMake: Select a Kit

扫不到的原因多数是 g++.exe 不在 PATH 里，或者 PATH 改完没重开编辑器。

工具装了好几份的时候，CMake Tools 抓到的未必是想要那个。设置里把 cmake.cmakePath 指死：

json
{
  "cmake.cmakePath": "D:/Qt/Tools/CMake_64/bin/cmake.exe",
  "cmake.generator": "MinGW Makefiles"
}

cmake.generator 也要写死。默认它容易挑 Visual Studio 的生成器，编出来的程序和 MinGW 的 Qt 库对不上，报一堆链接错误。现象很像「找不到编译信息」，实际是生成器选错了。

CMake: Configure 跑通，输出面板会打出这几行：

text
[cmake] -- The CXX compiler identification is GNU 13.1.0
[cmake] -- Found Qt6: C:/Qt/6.8.0/mingw_64/lib/cmake/Qt6
[cmake] -- Configuring done
[cmake] -- Generating done
[cmake] -- Build files have been written to: D:/QtProjects/HelloQt/build

Found Qt6 那行是关键。没有它、报 Could NOT find Qt6，就去工作区设置里补一条：

json
{
  "cmake.configureArgs": [
    "-DCMAKE_PREFIX_PATH=C:/Qt/6.8.0/mingw_64"
  ]
}

存盘后再跑一次 CMake: Configure。这条和 CMakeLists.txt 里的 set(CMAKE_PREFIX_PATH ...) 是两处，谁先谁后都行，冲突时以命令行参数为准。

构建成功的样子：

text
[build] [5/5] Linking CXX executable HelloQt.exe
[build] Build finished with exit code 0

看到 exit code 0 就算过。不是 0 就先修第一条错误，后面的多半是连锁反应。

不装插件也能构建，纯命令行四条命令：

bash
cd build
cmake ..
cmake --build .
../bin/test.exe

第一次跑要指定生成器，MinGW 环境下别让它默认去找 Visual Studio：

bash
mkdir build
cd build
cmake -G "MinGW Makefiles" ..
cmake --build .

跑 ../bin/test.exe 这个路径不是凭空写的，CMakeLists.txt 里设了 CMAKE_RUNTIME_OUTPUT_DIRECTORY，产物落在 bin/。直接双击这个 exe 多半起不来，因为它旁边没有 Qt 的 DLL。三种解法：PATH 里有 Qt\6.x\mingw_64\bin、把 DLL 拷到 exe 同目录、或者跑 windeployqt。

想把构建绑到快捷键上，写 .vscode/tasks.json：

json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "qmake 构建",
      "type": "shell",
      "command": "qmake ${workspaceFolder}/HelloQt.pro && mingw32-make -j8",
      "group": { "kind": "build", "isDefault": true },
      "problemMatcher": ["$gcc"]
    },
    {
      "label": "cmake 构建",
      "type": "shell",
      "command": "cmake --build build",
      "group": "build",
      "problemMatcher": ["$gcc"]
    }
  ]
}

两处细节：qmake 路线配的 make 是 mingw32-make，不是 make，MinGW 的包里就没那个名字；problemMatcher 给 $gcc，编译错误才能点着跳到行号。

两条命令线的对照：

动作 qmake 路线 CMake 路线
生成 Visual Studio 工程 qmake -tp vc cmake -G "Visual Studio 17 2022"
生成 Makefile qmake cmake -G "MinGW Makefiles"
构建 mingw32-make cmake --build .
清理 mingw32-make clean cmake --build . --target clean
加并发 mingw32-make -j8 cmake --build . -j 8

八、调试配置 #

构建通了，调试是另一份配置。.vscode/launch.json：

json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "QtBuild",
      "type": "cppdbg",
      "request": "launch",
      "program": "${command:cmake.launchTargetPath}",
      "args": [],
      "stopAtEntry": false,
      "cwd": "${workspaceRoot}",
      "environment": [
        {
          "name": "PATH",
          "value": "D:/Qt/Qt5.14.2/5.14.2/mingw73_64/bin"
        }
      ],
      "externalConsole": false,
      "MIMode": "gdb",
      "miDebuggerPath": "D:/Qt/Qt5.14.2/Tools/mingw730_64/bin/gdb.exe",
      "setupCommands": [
        {
          "description": "为 gdb 启用整齐打印",
          "text": "-enable-pretty-printing",
          "ignoreFailures": true
        }
      ]
    }
  ]
}

每一段都在干一件具体的事：

字段 作用 写错的表现
program 要调试的 exe 用 ${command:cmake.launchTargetPath} 自动取当前构建目标，不用手写路径
cwd 进程工作目录 程序按相对路径读文件时会找不到
environment 里的 PATH 让调试器和程序找到 Qt DLL 启动即退出，报缺 Qt6Widgets.dll
miDebuggerPath gdb 的位置 断点变空心圈，提示无法启动调试器
MIMode 调试协议，cppdbg 必填 缺了调试会话起不来
externalConsole 用不用独立控制台窗口 用 std::cin 的程序读不到输入时改成 true
setupCommands 给 gdb 的启动指令 -enable-pretty-printing 让 QString 这类类型显示得能看

MIMode 是网上抄来的配置里最常漏的一行。只有 type: cppdbg 没有 MIMode，调试器不知道该说 MI 协议还是别的，直接拒绝启动。

program 有两种写法。吃 CMake Tools 的用 ${command:cmake.launchTargetPath}，它跟着当前选中的构建目标走；纯命令行的直接写死：

json
"program": "${workspaceFolder}/bin/HelloQt.exe"

写死的坏处是换 Debug 与 Release 要改两处，好处是不依赖插件。

打断点的流程：

text
1. 在代码行号左侧点一下，出现红点
2. 按 F5，或 Ctrl+Shift+P → CMake: Debug
3. 程序停在断点上，左侧看变量、调用栈，顶部单步走

断点踩空，对症查：

现象 原因 处理
断点是空心灰圈 符号没加载上 确认构建类型是 Debug，带 -g
程序一闪而过，断点没停 program 指向的不是刚构建的 exe 换成 ${command:cmake.launchTargetPath}
提示找不到 gdb.exe miDebuggerPath 路径错，或该目录没有 gdb 指到 MinGW 的 bin/gdb.exe
起来就退，没有任何输出 缺 Qt DLL environment 里补 PATH
断点位置和源码错位 编译产物和源码不是同一份 全量重建一次
调试会话无法启动 少了 MIMode 补 "MIMode": "gdb"

用 MSVC 编的 Qt，这套 cppdbg 要换成 cppvsdbg，miDebuggerPath 删掉，改由 Visual Studio 的调试引擎接手。两边的字段不通用，混写会报配置无效。

九、其他编辑器与通用思路 #

VS Code 只是其中一条路。同一套流程换到别的编辑器，差别只在「谁替你写那几个配置文件」。

Trae 是我们日常用的。它和 VS Code 同一个内核，插件能通用，但 AI 权限更高，能直接动文件、跑命令。配置这件事可以整段丢给它：

text
我的 Qt 装在 D:\Qt\6.8.0\mingw_64，工具链在 D:\Qt\Tools\mingw1310_64。
帮我在当前工作区配好：c_cpp_properties.json 的 include 路径和 QT_WIDGETS_LIB 宏、
tasks.json 的构建任务、launch.json 的 cppdbg 调试。
改完把每个文件的作用说一遍，并告诉我哪一项是我需要自己核对的。

要求它「说一遍每个文件的作用」这句别省。AI 配错路径的时候，能讲清依据的那个版本一眼能看出来。

Cursor 和 Antigravity 走的是另一条产品思路，重心在对话本身，代码区和聊天区分得没那么清。写 Qt 这种要反复看头文件、翻生成物的活，我们觉得不如前两个顺手，这是习惯问题，不是能力问题。

纯命令行也完全可行，挂个 opencode 之类的工具，剩下全靠手敲：

bash
cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_PREFIX_PATH=D:/Qt/6.8.0/mingw_64
cmake --build build -j8

看明白共同点就明白这章为什么能放在最后：换哪个编辑器，要补的都是同一组东西。 摊开只有三件事：

要补的 具体内容 谁都能做到的原因
让它知道工程长什么样 源文件清单、模块依赖 .pro 和 CMakeLists.txt 都是纯文本，命令行工具读得懂
让它知道头文件在哪 include 路径、宏定义 qmake -query 与编译数据库都会吐出来
让它能跑起来、停下来 外部构建命令、gdb/cdb 接入 构建和调试都是独立进程，编辑器只负责拉起

能做好这三件事的编辑器，就能写 Qt。做不好，或者只能靠插件糊住的，那就是编辑器的问题，不是 Qt 的问题。

还有一条更省事的路：clangd 加编译数据库。生成 compile_commands.json 之后，clangd 用它做补全和跳转，比 C/C++ 插件轻，跨平台表现也一致。代价是要先 configure 一次，工程本身编不过的时候它给不出东西。

十、Qt 在线安装慢的原因 #

根源是一句话：新版本只剩在线安装器，包体从境外服务器一个一个拉。

Qt 5.15 之后，官方不再提供离线安装包。现在下载页上给的是 qt-unified-windows-x64-XXX-online.exe 或者 qt-unified-linux-x64-XXX-online.run。这类安装器本身很小，真正的 Qt 库、工具链、示例全靠运行时下载。

慢在哪几段，拆开看：

环节 发生了什么 症状
拉元数据 先下组件清单与版本索引，从境外站点取 卡在启动界面，进度条不动
拉包体 每个组件单独一个 7z 包，几十到几百 MB 单线程，几十 KB/s 慢慢磨
校验 下完算校验和，对不上就重下 下到 80% 突然回到 0%
跨境链路 国际出口拥塞，晚高峰更差 白天能跑，晚上不动
组件叠加 勾了 Android、Sources、Examples 之后总量翻几倍 装一上午

安装器是 Qt Installer Framework 打的包，它自己支持换源，这才是解法所在。网上大量教程讲用 Fiddler 抓包改响应，把下载地址劫持到镜像站——这招能用，但只对走了 HTTP 代理的进程起作用，Linux 上的安装器不认 Windows 那套代理设置，通用性差。

所以别在抓包上耗时间，往下看换源。

十一、换源的几种做法 #

主线做法只有一条：给安装器加 --mirror 参数，让它从镜像站拉。

方法一：安装器加 --mirror

正常运行安装脚本是这么敲的：

bash
./qt-unified-linux-x64-XXX-online.run

带上镜像参数：

bash
./qt-unified-linux-x64-XXX-online.run --mirror https://mirrors.tuna.tsinghua.edu.cn/qt

这一条是实测过的，清华 TUNA 的 qt 目录同步了 Qt 的仓库结构。Windows 同理，在 exe 后面接同样的参数：

bash
qt-unified-windows-x64-XXX-online.exe --mirror https://mirrors.tuna.tsinghua.edu.cn/qt

这个地址不是唯一选择。国内几所高校的镜像站都有 Qt 目录，同步进度与保留版本各不相同。手上那条断了，就搜「Qt 镜像源」，挑同步了 qt/ 目录的站点，把根地址填进 --mirror。别照抄某篇博客里的地址就用，镜像站下线或者改了路径是常事。

方法二：挂代理

镜像站覆盖不到组件（比如某些版本的 Android 套件），就走代理。安装器吃系统代理，也吃环境变量：

bash
export http_proxy=http://127.0.0.1:7890
export https_proxy=http://127.0.0.1:7890
./qt-unified-linux-x64-XXX-online.run

Windows 上在「设置 → 网络和 Internet → 代理」里配好，安装器启动时会沿用。这条路对全流程生效，包括元数据那一段，比只改下载地址彻底。

方法三：离线分发

安装器下完的包会留在本地缓存里，把它们连同安装器一起打包，同网段的其他机器就能直接用，不用一台一台重新下。团队里装机，这条路最省事。

方法四：包管理器

Linux 上直接用发行版的 Qt 包，绕开官方安装器：

bash
sudo apt install qt6-base-dev qt6-tools-dev

macOS 上 brew install qt。这两条路拿到的是打包者编的版本，版本号比官方滞后，但下载走的是本地源，速度不是问题。

几种做法摆一起：

做法 适用平台 管不管元数据那段 代价
--mirror 换源 Windows、Linux、macOS 管 镜像站要有对应组件
系统代理或环境变量 全平台 管 要有可用的代理出口
离线分发缓存 全平台 不管，直接给现成的 要先有一台装好的机器
发行版包管理器 Linux、macOS 不涉及 版本滞后，组件不全

Ubuntu 上装完 Qt 还有一步容易漏：缺 OpenGL 相关的开发文件，后面编译带界面的程序会报错，先补上：

bash
sudo apt-get install mesa-common-dev

十二、安装器的网络参数 #

--mirror 的用法只有一条规则要记死：传的是镜像站的仓库根，不是某个具体组件目录。

text
对：https://<镜像站>/qt
错：https://<镜像站>/qt/online/qtsdkrepository
错：https://<镜像站>/qt/6.8.0

安装器自己会在根地址后面拼它需要的路径。多写一层，它就到错的地方找索引，表现为「连上了但一个组件都列不出来」。

参数不多，够用的就这些：

参数 作用 用法注意
--mirror <URL> 指定包体与元数据的来源 必须是仓库根地址，结尾别加多余路径
-h、--help 打印当前版本支持的全部参数 版本不同支持的开关不同，先查再用
无参数启动 走官方源 官方源能用时不需要加任何东西

验证换源有没有生效，别看网速感觉，看安装器的下载详情：

text
1. 安装器进入组件下载阶段
2. 点开「显示细节」或展开下载项
3. 看每条下载 URL 的前缀
4. 前缀是镜像站域名，说明生效；还是官方域名，说明参数没被读到

参数没被读到的三个原因，按顺序查：

现象 原因 处理
URL 还是官方域名 --mirror 写在脚本名前面了 参数放在可执行文件之后
组件列表是空的 镜像地址写到了子目录 退回仓库根地址
下载报校验失败 镜像未同步完，或包体不完整 换一个镜像站，或改用代理
Windows 下参数被忽略 用了快捷方式启动，没带参数 从命令行启动 exe，参数跟在后面
装到一半卡住 镜像站限速或断流 换源重试，已下载的包会复用

安装器本身还有个前置动作：登录 Qt 账号。开源版账号可以用，这一步走的是官方接口，换源不影响它。账号这关过不去，先解决网络到官方站点的连通性，镜像帮不上。

十三、易错点速查 #

两件事的坑收在一张表里，出事按症状查。

症状 真正的原因 处理
命令行里有 qmake，没有 g++ 装 Qt 时没勾 MinGW 组件 重跑安装器补装工具链
三条路径加进 PATH 还是找不到 没关掉老终端和编辑器 全关掉重开
编译过，运行报缺 Qt6Widgets.dll Qt\6.x\mingw_64\bin 不在 PATH 加进 PATH，或把 DLL 拷到 exe 旁
undefined reference to vtable for ... moc 没跑，Q_OBJECT 没被处理 开 CMAKE_AUTOMOC，或确认 .pro 里有 HEADERS
fatal error: ui_widget.h 找不到 uic 没跑，或构建目录没进 include 开 CMAKE_AUTOUIC，include 路径补 build 目录
图标与图片运行时全丢 rcc 没跑，资源没编进去 开 CMAKE_AUTORCC，.qrc 进源文件列表
multiple definition of main CMakeLists.txt 里有两个 add_executable 删掉多余的
Could NOT find Qt6 CMAKE_PREFIX_PATH 没指对 补 configureArgs 或用 -D 传入
IntelliSense 满屏红但能编译 两套解析器，C/C++ 插件没配 写 c_cpp_properties.json
QString 带红线 defines 里缺 QT_CORE_LIB 这类宏 补宏
新增 .cpp 编译不进去 file(GLOB) 没触发重新 configure 加 CONFIGURE_DEPENDS，或手动重新 configure
选不上 MinGW kit 工具链不在 PATH，插件没扫到 CMake: Scan for Kits 后重选
断点空心灰圈 构建类型不是 Debug，没符号 切 Debug 重建
调试会话起不来 launch.json 少了 MIMode 补 "MIMode": "gdb"
gdb 报符号格式不对 gdb 与 gcc 不是同一套工具链 用同一目录里的 gdb.exe
安装器一直卡在启动界面 官方源元数据拉不下来 加 --mirror，或挂代理
换源后组件列表空 镜像地址写成了子目录 退回仓库根地址
下载进度反复归零 镜像站包体不同步，校验失败 换镜像站，或改走代理
Ubuntu 编译报 OpenGL 缺失 缺 mesa-common-dev sudo apt-get install mesa-common-dev

这份表里有一半是配置问题，一半是工具链问题。分辨办法很简单：命令能跑通，是配置问题；命令本身就找不到，是工具链没装齐。先查 gcc --version、cmake --version、qmake --version 这三条，全绿了再动配置文件。
