这篇只讲一件事：编译 Qt、或者用 Qt 编译自己的项目时，屏幕上一堆报错怎么读、怎么定位、怎么修。讲判断顺序，讲每类错误的成因与解法。不讲源码 configure 的完整参数表，那是《Linux 上编译 Qt 源码》的范围；不讲数据库驱动的单独编译流程，那是《数据库驱动编译》的范围。三条线各管一段，交叉的地方我指过去。

一、读错误信息的方法 #

报错刷屏时，人的第一反应是往上翻，从头读第一条。这个习惯在 make 输出里是错的。make 逐个编译单元打进度，前面几百行都正常，真正的原因往往在最后二十行。从下往上读，先定位带 error 的那行，再看它上文。

先分清谁在说话 #

构建链上不止一个程序在输出。同一个 error 前缀，出自不同程序，含义完全不同。

输出片段 谁在说话 去哪里找
configure: error: 源码树的 configure 脚本 依赖包、configure 参数
ERROR: Feature 'xcb' was enabled, but the pre-condition ... failed configure 脚本 缺的依赖项
Project ERROR: Unknown module(s) in QT: qmake .pro 里的 QT +=
Project MESSAGE: / Project WARNING: qmake .pro、.pri、路径
fatal error: xxx.h: No such file or directory 编译器预处理 头文件路径、-dev 包
error: 'xxx' was not declared in this scope 编译器 C++ 代码本身
cannot find -lxxx 链接器 ld 库是否存在、-L 路径
undefined reference to ... 链接器 ld 库有没有链、链接顺序
collect2: error: ld returned 1 exit status 链接器收尾 上面那条真正的 ld 报错
QObject::connect: No such slot 运行期的 Qt 信号槽声明与拼写

看到 Project ERROR 就别翻 C++ 代码了，那是 qmake 在读 .pro。看到 collect2 也别慌，它只是收尾那句，真正的信息在它上面一行。

抓住三个字段 #

编译错误有固定格式，main.cpp:42:5 是位置，error 是级别，后半句才是原因：

text
main.cpp:42:5: error: 'QString' was not declared in this scope

位置告诉你去看哪一行，原因告诉你为什么。后面跟的 note: 常常比 error 行有用，比如 note: candidate function not viable: no known conversion from 'int' to 'const QString'，候选函数和参数类型都列出来了。

链接错误没有行号，只给符号名：

text
undefined reference to `MyClass::doWork(int)'

符号名是唯一线索，拿它去全工程搜：

bash
grep -rn "doWork" --include=*.h --include=*.cpp .

搜到声明没搜到定义，就是没实现；声明和定义都有，就查这个 .cpp 有没有被编进目标。搜报错时把路径、行号、自己的类型名删掉，只留句式骨架，error: no matching function for call to 这种骨架才搜得到东西。

把日志留下来 #

终端滚动缓冲有限，make -j8 的输出能瞬间冲掉关键几行。

bash
make -j8 2>&1 | tee build.log

2>&1 把 stderr 并进 stdout，tee 让屏幕和文件都有。别用 >，gcc 的诊断信息走 stderr，> 只接 stdout，日志里会只剩进度。

修掉第一条再 make 是另一条规矩。后面的错误很多是前面带出来的级联——头文件没找到，后面几十条「类型未定义」全是它的后果，逐条硬修会把自己绕进去。

二、错误出在哪个阶段 #

这是本篇最该记住的一节。报错先分阶段，阶段判对，查错范围直接缩掉九成。

Qt 的构建链是四段：configure 探环境、qmake 生成 Makefile、make 编译并链接、make install 落盘。每段的报错面相不一样。

三阶段对照 #

阶段 谁在执行 典型报错开头 主要怀疑对象
configure 源码树的 configure 脚本 configure: error:、pre-condition ... failed 缺依赖、缺工具链、参数写错
qmake qmake 可执行文件 Project ERROR:、Project WARNING: .pro 内容、模块名、路径
编译 gcc / clang，逐文件 fatal error:、error: 加文件名行号 头文件、语法、C++ 标准
链接 ld、collect2 cannot find -lxxx、undefined reference 库位置、库名字、链接顺序
安装 make install Permission denied、cannot create directory 权限、prefix 指向
运行 你的程序 error while loading shared libraries LD_LIBRARY_PATH、插件路径

一眼判断的硬指标 #

  • 输出里有 .cpp 文件名加行号，就是编译段，跟「库没链」无关。
  • 只有符号名、没有文件行号，就是链接段。
  • 报错里出现 -l 开头的东西，就是链接段。
  • 报错带 Project 前缀，就是 qmake 段，编译还没开始。
  • 一行编译命令都没打出来就停了，就是 configure 段。

边界要划清：undefined reference 有时是编译段留下的坑，比如某个带实现的 .cpp 忘了加进 SOURCES，表现仍然落在链接段。判阶段只为缩小范围，不是下判决。

看清真正执行的命令 #

make 默认把命令藏起来，只打 g++ -c ... 这种缩写。要看完整的头文件路径和库顺序：

bash
make VERBOSE=1        # qmake 项目也可以用 make V=1
cmake --build . --verbose

把最后那条链接命令复制出来，数一数 -l 有几个、-L 指到哪、顺序怎么排。链接期的问题九成在这条命令里就能看出来。

改 .pro 之后必须重新跑 qmake，改头文件里的 Q_OBJECT 之后必须重新 moc。make 的依赖判断有时跟不上，报错会一直挂在那，你改的代码明明是对的。怀疑增量状态不对就清掉重来：

bash
make clean && make -j8

三、依赖库缺失 #

缺依赖是最常见的一类。但「缺」有两种，修法不一样，先分清。

头文件缺失 #

text
fatal error: curl/curl.h: No such file or directory

这是编译段，预处理阶段找不到头文件。原因几乎都是只装了运行时库，没装开发包。发行版把同一个库拆成两个包：运行时包给 libcurl.so.4，开发包给 curl/curl.h 和 libcurl.so 这个符号链接。

头文件 Ubuntu / Debian CentOS / RHEL
curl/curl.h libcurl4-openssl-dev libcurl-devel
openssl/ssl.h libssl-dev openssl-devel
sqlite3.h libsqlite3-dev sqlite-devel
zlib.h zlib1g-dev zlib-devel
fontconfig/fontconfig.h libfontconfig1-dev fontconfig-devel
png.h libpng-dev libpng-devel
jpeg.h libjpeg-dev libjpeg-turbo-devel
X11/Xlib.h libx11-dev libX11-devel
xkbcommon/xkbcommon.h libxkbcommon-dev libxkbcommon-devel
GL/gl.h libgl1-mesa-dev mesa-libGL-devel

cURL 的三平台装法：

平台 安装命令
Ubuntu/Debian sudo apt install libcurl4-openssl-dev
CentOS/RHEL sudo yum install libcurl-devel
macOS (Homebrew) brew install curl

装完还是找不到头文件，就手动指路径：

bash
g++ -I/usr/include/curl ...
# 或设置环境变量
export CPATH=/path/to/curl/include:$CPATH

CPATH 会被 gcc 当成额外的头文件搜索目录，对所有编译单元生效。写进 .pro 更稳，别人 clone 下来不用配环境：INCLUDEPATH += /opt/curl/include。

库文件缺失 #

text
cannot find -lcurl: No such file or directory

这条是链接段。-lcurl 让 ld 去找 libcurl.so 或 libcurl.a，找不到就报这句。两种情况：库压根没装，或者装了但不在 ld 的搜索路径里。先问 pkg-config：

bash
pkg-config --cflags --libs libcurl

有输出说明开发包在，把输出原样搬进构建脚本。报 Package libcurl was not found 说明开发包确实没装。再用 ldconfig -p | grep libcurl 确认库本身在不在——能查到 libcurl.so.4 却查不到 libcurl.so，就是缺开发包，不带版本号的那个文件由开发包提供，链接器只认它。

把路径补进构建 #

qmake 侧：

INCLUDEPATH += /opt/curl/include
LIBS += -L/opt/curl/lib -lcurl

CMake 侧，自定义前缀装在 /opt 下时先用 cmake .. -DCMAKE_PREFIX_PATH=/opt/curl 让它去那里找，再正常 find_package(CURL REQUIRED) 配 target_link_libraries(app PRIVATE CURL::libcurl)。

四、X11 与 OpenGL 相关错误 #

Qt 在 Linux 上跑 GUI，依赖三样东西：xcb 平台插件、OpenGL、fontconfig。这三样在 configure 阶段被逐个探测，缺哪个报哪个。

cannot find -lGL #

text
-1: error: cannot find -lGL: No such file or directory

-1 前缀说明报错来自 IDE 的构建面板，不是编译器本身，它把链接错误归到了第一个虚拟文件，本质还是 ld 找不到 libGL.so。原因和 -lcurl 同构：运行时包只给 libGL.so.1，开发包才给不带版本号的 libGL.so。

  1. 安装开发库
bash
sudo apt update
sudo apt install libgl1-mesa-dev

CentOS 系装 mesa-libGL-devel。

  1. 检查库文件是否存在
bash
find / -name "libGL.so*"

只看到 libGL.so.1、libGL.so.1.7.0 这类带版本号的文件，说明装的是运行时库。看到 libGL.so 才算齐。

  1. 配置库路径

库存在但链接器找不到时，把路径加进环境变量：

bash
# 临时生效
export LD_LIBRARY_PATH=/path/to/library:$LD_LIBRARY_PATH

# 永久生效 (添加到 ~/.bashrc)
echo 'export LD_LIBRARY_PATH=/path/to/library:$LD_LIBRARY_PATH' >> ~/.bashrc
source ~/.bashrc

这条只管当前 shell，换终端就没了。真正决定链接期去哪找库的是 -L，LD_LIBRARY_PATH 是辅助搜索路径，运行期加载器也认它。长期方案写进构建文件。

  1. 项目配置 (.pro)
LIBS += -lGL

库在非默认路径时补 -L：LIBS += -L/usr/lib/x86_64-linux-gnu -lGL。

GL 头文件缺失 #

text
fatal error: GL/gl.h: No such file or directory

libgl1-mesa-dev 一起解决。GLU 用 libglu1-mesa-dev，GLEW 用 libglew-dev，EGL 用 libegl1-mesa-dev。只想要软件渲染、不碰 OpenGL 时，configure 加 -no-opengl，无显卡的服务器上能省一大堆依赖。

xcb 相关的一大串 #

configure 会逐个探测 xcb 的扩展库，少一个停一次。

text
ERROR: Feature 'xcb' was enabled, but the pre-condition 'features.thread && libs.xcb' failed.

读法：Feature 'xcb' was enabled 是你要的功能，pre-condition 里 failed 的那项就是缺的东西。带 && 的多项条件，挨个验。

检查项 Ubuntu 包 报错特征
xcb 基础 libxcb1-dev cannot find -lxcb
xcb-icccm libxcb-icccm4-dev cannot find -lxcb-icccm
xcb-image libxcb-image0-dev cannot find -lxcb-image
xcb-keysyms libxcb-keysyms1-dev cannot find -lxcb-keysyms
xcb-render-util libxcb-render-util0-dev cannot find -lxcb-render-util
xcb-shape libxcb-shape0-dev cannot find -lxcb-shape
xcb-xkb libxcb-xkb-dev cannot find -lxcb-xkb
xcb-xinerama libxcb-xinerama0-dev cannot find -lxcb-xinerama
xcb-sync libxcb-sync-dev cannot find -lxcb-sync
xcb-randr libxcb-randr0-dev cannot find -lxcb-randr
xcb-shm libxcb-shm0-dev cannot find -lxcb-shm
xkbcommon-x11 libxkbcommon-x11-dev cannot find -lxkbcommon-x11
X11-XCB libx11-xcb-dev cannot find -lX11-xcb
Xrender libxrender-dev cannot find -lXrender
Xext / Xfixes libxext-dev libxfixes-dev cannot find -lXext

一次装齐（Ubuntu）：

bash
sudo apt install libxcb1-dev libxcb-icccm4-dev libxcb-image0-dev \
    libxcb-keysyms1-dev libxcb-render-util0-dev libxcb-shape0-dev \
    libxcb-xkb-dev libxcb-xinerama0-dev libxcb-sync-dev libxcb-randr0-dev \
    libxcb-shm0-dev libxcb-util0-dev libx11-xcb-dev libxkbcommon-x11-dev

cannot find -lxcb-xxx 和 cannot find -lGL 是同一类问题，都缺 -dev 包，区别只在包名长、容易漏。

fontconfig 与中文字体 #

text
fatal error: fontconfig/fontconfig.h: No such file or directory

bash
sudo apt install libfontconfig1-dev libfreetype6-dev

Qt 的字体数据库走 fontconfig，freetype 是它的后端，两个一起装。装完用 fc-list :lang=zh | head 查系统里有没有中文字体；一条都不出的话，程序能编译能启动，但中文全变方块。这个坑不报编译错误，只在运行期露头，见第十一章。

五、moc、uic、rcc 的报错 #

Qt 的构建比普通 C++ 项目多三个代码生成器，它们跑在编译之前，报错长得像编译器，其实不是。

工具 输入 输出 何时跑
moc 带 Q_OBJECT、Q_GADGET 的头文件 moc_xxx.cpp 编译前
uic .ui 文件 ui_xxx.h 编译前
rcc .qrc 资源清单 qrc_xxx.cpp 编译前

moc 报错的三类成因 #

moc 本身很少直接报错，它的失败几乎都变成后续的链接错误或编译错误。三类成因：

  1. 头文件里没有 Q_OBJECT 宏。
  2. 有 Q_OBJECT，但头文件没被 moc 处理——不在 HEADERS 里，或 CMake 没开 AUTOMOC。
  3. 在 .cpp 里直接定义带 Q_OBJECT 的类，又忘了在文件末尾 #include "xxx.moc"。

第一条最隐蔽。信号槽照旧能连，因为 connect 走字符串匹配时运行期才校验；但 qobject_cast、tr()、属性系统全都不认这个类。

典型报错：undefined reference to vtable #

text
undefined reference to `vtable for MyClass'

链接阶段报错，成因在 moc，不在链接器。

原因分析

  • 类定义中使用了 Q_OBJECT 宏，但 moc 未运行或未重新生成 moc_*.cpp 文件
  • 虚函数未实现（尤其是析构函数）

解决方案

  1. 检查 Q_OBJECT 宏：确保继承自 QObject 的类包含该宏
  2. 重新运行构建系统：
    • qmake：右键项目 → 「执行 qmake」 → 「重新构建」
    • CMake：删除 build 目录，重新运行 cmake 配置

补一句为什么。Q_OBJECT 宏展开后会往类里塞 metaObject()、qt_metacall 和虚表锚点，这些符号由 moc 生成的 moc_xxx.cpp 提供。头文件没进 moc，类声明里有、符号表里没有，链接器就找不着 vtable。

第二条「虚函数未实现」也报同一个错，但位置不同：它指向第一个未实现的虚函数，不是 moc 的锚点。看符号名能分开——vtable for MyClass 是 moc 问题，MyClass::~MyClass() 是没写析构实现。

CMake 项目要开 CMAKE_AUTOMOC、CMAKE_AUTOUIC、CMAKE_AUTORCC 三个开关，qmake 项目自动处理，前提是头文件写进 HEADERS：

HEADERS += myclass.h
SOURCES += myclass.cpp main.cpp

.cpp 里的类要加尾包含，这一行必须在文件最后：#include "myclass.moc"。它拼的是当前 .cpp 对应的 moc 输出，跟头文件版本不是一回事。

uic 与 rcc 报错 #

text
uic: File 'mainwindow.ui' is not valid

.ui 被手改坏了，XML 标签不闭合，或者控件类名写成了不存在的类型。用 Qt Designer 打开存一次，让它自己修正格式。

ui_xxx.h: No such file or directory 是另一回事，说明 uic 压根没跑。qmake 查 FORMS += mainwindow.ui，CMake 查 CMAKE_AUTOUIC 有没有开、.ui 有没有进源列表。

RCC: Error in 'res.qrc': Cannot find file 'icons/app.png'——.qrc 里的 <file> 是相对 .qrc 的位置，不是相对工程根目录，也不是相对 .pro。另有 listed twice，说明同一个文件在两个 <qresource prefix> 下重复登记。

生成器本身找不到 #

make: /opt/qt/bin/moc: No such file or directory——Qt 装了但 qmake 指到了别处。qmake -query QT_INSTALL_BINS 看它认为的 bin 在哪，再核对里面的 moc 在不在。跨版本混装是最常见的原因：PATH 先命中了 Qt 5 的 qmake，编的却是 Qt 6 的库。

六、qmake 相关的错误 #

qmake 在编译之前就把 .pro 读完，它报错时一行 C++ 都还没编。

qmake: command not found #

Qt 装好了，但 bin 目录不在 PATH 里。

bash
export PATH=/opt/qt-5.15.2/bin:$PATH
qmake -v

输出的 Using Qt version ... 那行必须跟你以为的版本一致。装了两套 Qt 的机器上，这一条能排掉一半怪问题。找不到 qmake 在哪就 find /opt -name qmake -type f 2>/dev/null。

Project ERROR: Unknown module(s) in QT #

text
Project ERROR: Unknown module(s) in QT: webenginewidgets

Qt 5 迁到 Qt 6 时最常撞的一条。名字变了、模块拆了，或者组件根本没装。

模块 处理方式
WebEngine 确认已安装 Qt WebEngine 组件；注意部分版本不支持 MinGW，需使用 MSVC
Multimedia Qt 6 中 API 有较大变动，需检查代码兼容性
其他模块 使用 Qt Maintenance Tool 确认勾选了对应模块

Qt 6 里几个高频变化：

Qt 5 写法 Qt 6 情况
QT += script 移除，改用 QJSEngine（QT += qml）
QT += xmlpatterns 移除
QT += multimedia 模块名保留，类名有调整
QT += webenginewidgets 组件需单独安装

查本机装了哪些模块：ls $(qmake -query QT_INSTALL_LIBS)/cmake | head -40。每个 Qt6Xxx 目录就是一个可用模块，目录不在，.pro 里写了也白写。

Project ERROR: Cannot run compiler 'g++' #

qmake 在探测编译器。g++ 没装，或者装了但 32 位库缺失导致试编译失败。

bash
sudo apt install build-essential
g++ --version

交叉编译时改 QMAKE_CXX：

QMAKE_CC  = arm-linux-gnueabihf-gcc
QMAKE_CXX = arm-linux-gnueabihf-g++

.pro 语法与路径 #

Project ERROR: Unknown file 这类多半是路径写错。$$PWD 是 .pro 所在目录，$$OUT_PWD 是构建目录：

INCLUDEPATH += $$PWD/include
LIBS += -L$$PWD/lib -lfoo
DESTDIR = $$OUT_PWD/bin

> 和 += 混用也会出事。QT = core gui 会把之前的模块全清掉，只剩这两个，习惯上永远用 +=。CONFIG += c++17 是加特性，CONFIG -= app_bundle 是去特性，减号删掉的东西别人加不回来。

七、编译器版本与 C++ 标准 #

Qt 对编译器有硬门槛。版本不够，报错不在 Qt 的代码里，而在标准库头文件里，读起来很吓人。

Qt 版本 C++ 标准 最低 GCC
Qt 5.9 ～ 5.15 C++11 GCC 5
Qt 6.0 ～ 6.1 C++17 GCC 8
Qt 6.2 及以上 C++17 GCC 9

GCC 版本低于门槛时，最先撞上的不是语法错误，而是标准库特性缺失：

text
error: 'auto' not allowed in function return type without trailing return type
error: expected ';' at end of member declaration

看到一堆这种，先查 g++ --version，别急着改代码。

Qt 6 必须 C++17 #

text
error: #error "Qt requires a C++17 compiler"

Qt 6 的头文件里有静态断言，直接挡在没有 C++17 的编译器前面。Ubuntu 16.04 自带的 GCC 5 撑不住，要么升 GCC，要么降 Qt。

CONFIG += c++17

cmake
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

CMAKE_CXX_STANDARD_REQUIRED ON 别省。少了它编译器会自己降级，降完又是一堆模板报错。

unrecognized option -std #

text
cc1plus: error: unrecognized command line option '-std=c++1z'

老 GCC 不认识新标准的选项名。GCC 5 之前没有 -std=c++1z，用 -std=c++14；GCC 4.8 用 -std=c++11。

选项名对应：c++0x 是 C++11 草案名，c++1y 是 C++14，c++1z 是 C++17，c++2a 是 C++20。新 GCC 两种写法都认，老 GCC 只认它出生时那个。

gcc 和 g++ 混用 #

text
undefined reference to `std::cout'

用 gcc 编 C++ 文件就会这样。gcc 驱动不链 libstdc++，g++ 才链。

QMAKE_CC  = gcc
QMAKE_CXX = g++   # 这个必须是 g++

链接命令最后交给 QMAKE_LINK，它默认跟 QMAKE_CXX 一致。动过这两个变量就要一起检查。

ABI 与 -fPIC #

用 GCC 编的 .so 拿给 Clang 编的程序链，语言层面能过，运行期会崩在析构或者异常展开上。_GLIBCXX_USE_CXX11_ABI 也要一致，一边按旧 ABI 编、一边按新 ABI 编，std::string 传过去就是野指针。用 nm -C /opt/lib/libfoo.so | grep "std::__cxx11" 查：出现 std::__cxx11::basic_string 说明这个库用新 ABI，你的程序必须也开。

编静态库给动态库用时没加 -fPIC，64 位上一定报 relocation R_X86_64_32 ... recompile with -fPIC，32 位有时能侥幸过去。qmake 侧加 QMAKE_CXXFLAGS += -fPIC 和 QMAKE_CFLAGS += -fPIC。

八、链接错误：undefined reference #

链接期报错只有一个句式，同一个句式，成因分两大类。分清这两类，这类问题就从「最卡人的」变成「五分钟能定位的」。

text
undefined reference to `符号名'
成因 现象特征 修法
库没链 符号属于外部库，链接命令里没有对应的 -l 补 LIBS += -lxxx
链接顺序错 库链了，但排在引用它的目标前面 把被依赖的库挪到后面
符号真没实现 符号属于自己工程，.cpp 没进构建 补 SOURCES 或 CMake 源列表
架构不匹配 符号在库里有，但位数不同 换 32/64 位对应的库
Debug/Release 混用 链接期缺带后缀的符号 按配置链对应后缀的库

前两类最容易混。判断方法：把链接命令原样贴出来，看符号属于哪个库，再看那个库的 -l 在命令里的位置。

成因一：库没链 #

符号名能看出归属。curl_easy_init 是 cURL，PKCS5_PBKDF2_HMAC 是 OpenSSL，png_create_read_struct 是 libpng。按归属补库：

LIBS += -lcurl
LIBS += -lssl -lcrypto
LIBS += -lpng

补完还报就是路径问题，加 -L：LIBS += -L/opt/curl/lib -lcurl。CMake 侧用 target_link_libraries(app PRIVATE CURL::libcurl OpenSSL::SSL OpenSSL::Crypto)，顺序由 CMake 自己排，比手写 -l 省心。

成因二：链接顺序错 #

这是最卡人的一类。GNU ld 对静态库是单趟扫描：从左往右走，遇到 .a 就把当时还没解析的符号从里面取出来，走过去就不再回头。所以被依赖的库必须放在依赖它的目标后面。

bash
# 错：libfoo 里的符号在被 main.o 引用之前就扫过了
g++ main.o -lfoo -lbar
# 对：引用者在前，被依赖者靠后
g++ main.o -lbar -lfoo

判定方法很土但很快：把同一个 -l 挪到最后再链一次，报错消失就是顺序问题。链接器还有个开关能暴力验证：

bash
g++ main.o -Wl,--start-group -lfoo -lbar -Wl,--end-group

--start-group 与 --end-group 之间的库会被循环扫描，直到没有新符号可解。它能治顺序问题，代价是链接变慢，而且掩盖了真实的依赖关系。调的时候可以用，长期方案还是把顺序排对。

qmake 侧控制顺序就是控制 LIBS 的书写顺序，LIBS += -lA 之后再来 LIBS += -lB，拼给 ld 的就是 -lA -lB；CMake 侧别用全局 link_libraries，它会插到命令开头，顺序又乱。

Windows 侧的对应报错 #

平台 错误信息
Windows (MSVC) error LNK2019: unresolved external symbol ...
Linux (GCC/Clang) undefined reference to ...

原因分析

  • 函数声明了但未实现
  • 依赖的库未链接（.lib / .a / .so）
  • 库的架构（x86/x64）与项目不匹配

解决方案

  1. 检查报错函数是否已在 .cpp 文件中实现
  2. 在 .pro 中添加库链接：LIBS += -L/path -lName
  3. 确认第三方库的位数（32位/64位）与编译器一致

MSVC 会把符号的完整修饰名打出来，比如 ?doWork@MyClass@@QEAAXH@Z，拿 dumpbin /symbols mylib.lib | findstr doWork 去库里查。LNK2001 和 LNK2019 是一家人，前者「找不到外部符号」，后者「解析不了外部符号」，成因一样，修法一样。

Debug/Release 模式混用 #

程序运行时崩溃，或出现堆破坏（Heap Corruption）错误，常见于 Windows 平台。原因是在 Debug 模式下链接了 Release 版本的库，或者反过来。Qt 的 Debug 库带 d 后缀：

模式 库文件示例
Debug Qt6Cored.lib
Release Qt6Core.lib

Linux 上同样的错不叫堆破坏，叫段错误或者 free(): invalid pointer，成因一致：两套库对 new、delete 的内存布局假设不同，Debug 版多一层红区标记。

CONFIG(debug, debug|release) {
    LIBS += -L$$PWD/libs -lmylib_d
} else {
    LIBS += -L$$PWD/libs -lmylib
}

CMake 侧用生成器表达式把 Debug 库挂到对应配置上，写法是 $<$<CONFIG:Debug>:mylib_d>，非 Debug 走另一支。

这一条在 Linux 上不报链接错误，只在运行期炸，比 Windows 更隐蔽，因为编译链接一路绿灯。

collect2 不是根因 #

text
collect2: error: ld returned 1 exit status

collect2 是 gcc 调 ld 的包装层，它只是转述 ld 的失败，真正的信息在它上面。还有一种 warning: libfoo.so.1, needed by libbar.so, not found (try using -rpath or -rpath-link)，是间接依赖找不到，补 -Wl,-rpath-link,/opt/lib。-rpath-link 只在链接期用，-rpath 会写进 ELF 的运行期搜索路径，两个不是一回事。

九、内存不足与并行编译 #

text
c++: fatal error: Killed signal terminated program cc1plus
virtual memory exhausted: Cannot allocate memory

第一种不是编译器主动退的，是被内核的 OOM killer 杀了。Qt 的模板展开很吃内存，一个 qquickitem.cpp 编到 1.5 GB 不稀奇，-j16 一起上就把内存吃干。确认是不是 OOM：

bash
dmesg | tail -20

看到 Out of memory: Killed process ... (cc1plus) 就是它。按机器内存收并发数：

物理内存 建议 -j
4 GB 2
8 GB 4
16 GB 6 ～ 8
32 GB 以上 核数的一半起

只编需要的模块，别把示例和测试一起带上：

bash
./configure -nomake examples -nomake tests -prefix /opt/qt-5.15.2

重编时开 ccache，重复文件的编译能直接命中缓存（./configure -ccache ...，用 ccache -s 看命中率）。加 swap 也能救急，代价是慢：sudo fallocate -l 8G /swapfile，再 sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile。

链接阶段也会吃内存，ld 合并巨大 .so 时会顶到上限，加 -Wl,--no-keep-memory 能让它少占一点。还有一种「内存不足」是假象：

text
No space left on device

磁盘满，跟内存无关，但报在同一个位置，容易看错。df -h 先看一眼，Qt 完整构建产物在十几 GB 量级，留 20 GB 起步。

十、权限与路径问题 #

make install 权限不足 #

text
install: cannot create regular file '/usr/local/lib/libQt5Core.so.5.15.2': Permission denied

prefix 指到了 /usr 或 /opt 下，当前用户没写权限。三条路：sudo make install 装到系统目录；./configure -prefix ~/qt-5.15.2 装到用户目录；make install INSTALL_ROOT=/tmp/stage 打包时用。

sudo make 之后目录属主变了 #

用 sudo make 编过一次，build 目录里一堆文件属主成了 root，之后用普通用户 make 会报 Permission denied 或者莫名其妙的 Error 1。用 sudo chown -R $USER:$USER . 修回来。

规矩是 sudo 只给 make install，不给 make。构建全程用普通用户。

路径里有中文或空格 #

qmake 生成的 Makefile 对空格处理很差，路径带空格会裂成两个参数，报错指向一个不存在的文件。工程路径、构建路径、安装路径全部用纯 ASCII 无空格。中文路径在 moc 和 rcc 上更容易出事，生成的 .cpp 里路径被截断，报 No such file or directory，但文件明明在。

报「文件不存在」但文件真在 #

./app: No such file or directory，而文件在、ls 也看得到——两种原因：加载器不存在，或者架构不对。用 file ./app 和 ldd ./app 分开验：file 显示 ELF 64-bit 而系统是 32 位，就是这个错；ldd 显示 not a dynamic executable 说明是静态链接的，那就是 ld-linux 路径问题。还有一条常被忽略：Linux 区分大小写，include/Foo.h 和 #include "foo.h" 不是一回事，Windows 上编得好好的工程搬过来报头文件找不到，先查大小写。

十一、编译通过但运行报错 #

找不到共享库 #

text
error while loading shared libraries: libQt5Core.so.5: cannot open shared object file

编译链接都过了，运行期加载器找不到 .so。最直接的修法：

bash
export LD_LIBRARY_PATH=/opt/qt-5.15.2/lib:$LD_LIBRARY_PATH   # 临时

写进 ~/.bashrc 是长期方案。工程自己用，写 qt.conf 更干净——放在可执行文件旁边，内容就两行 [Paths] 和 Prefix = /opt/qt-5.15.2，Qt 自己读，不污染环境变量。打包分发时用 rpath 把路径焊进 ELF：g++ main.o -Wl,-rpath,/opt/qt-5.15.2/lib -o app。

平台插件加载失败 #

text
This application failed to start because no Qt platform plugin could be initialized.
qt.qpa.plugin: Could not load the Qt platform plugin "xcb" in "" even though it was found.

第一种是插件目录没找到，第二种是插件找到了但依赖缺。先 ls /opt/qt-5.15.2/plugins/platforms/ 看插件在不在，再 ldd /opt/qt-5.15.2/plugins/platforms/libqxcb.so | grep "not found" 看它自己的依赖。缺 libxcb-xinerama.so.0 是最常见的一条，装 libxcb-xinerama0。插件路径也能手动指定：export QT_QPA_PLATFORM_PLUGIN_PATH=/opt/qt-5.15.2/plugins/platforms。

无 GUI 的机器上跑命令行程序，切到 offscreen 平台能绕过整套图形依赖：export QT_QPA_PLATFORM=offscreen。

WSL 中文乱码 #

在 WSL 里跑 GUI 程序，中文字符显示为方框。原因是 WSL 默认缺少中文字体。借用 Windows 宿主机的字体库：

bash
# 创建软链接
sudo ln -s /mnt/c/Windows/Fonts /usr/share/fonts/windows-fonts

# 刷新字体缓存
fc-cache -fv

若仍有乱码，安装中文语言包：sudo apt install language-pack-zh-hans。

装完用 fc-list :lang=zh | head 复核，能列出字体才算生效。

信号槽连接运行时警告 #

编译通过，控制台输出：

text
QObject::connect: No such slot ...
QObject::connect: No such signal ...

原因分析

  • 信号或槽函数名称拼写错误
  • 参数类型不匹配
  • 使用了旧版 SIGNAL/SLOT 宏且函数名错误

解决方案

用 Qt 5/6 的函数指针语法，错误在编译期就暴露：

cpp
// 推荐写法 (编译期检查)
connect(sender, &Sender::signalName, receiver, &Receiver::slotName);

// 旧式写法 (仅运行时检查，易出错)
connect(sender, SIGNAL(signalName()), receiver, SLOT(slotName()));

旧写法里那对字符串在编译期完全不校验，宏展开后就是普通字符串，拼错了编译器不管，运行期才在控制台打一行警告。函数指针写法直接取地址，名字错、参数错都编不过。槽函数还要写在 slots: 区里才能被字符串写法找到，用函数指针写法时这条限制就没了。另有一类编译期完全查不出的问题：Debug 库配 Release 程序，或者反过来，编译链接全过，一进来就崩，排查手段只有一条——两边配置对齐，见第八章末尾。

十三、易错点速查 #

易错点 为什么会踩 怎么防
从头读报错 make 输出前几百行都是正常进度 从最后一行往上找 error
改完 .pro 直接 make Makefile 还是旧的 先跑 qmake，或 make clean
QT = core gui 覆盖了已有模块列表 一律用 +=
头文件没进 HEADERS qmake 不 moc 它 加进 HEADERS，CMake 开 AUTOMOC
.cpp 里的 Q_OBJECT 类 尾包含 xxx.moc 漏了 文件最后一行 #include "xxx.moc"
库链了还是报 undefined 顺序错，ld 只单趟扫描 被依赖的库往后放
只装运行时库 缺 .so 符号链接 装 -dev / -devel 包
sudo make 编整个工程 产物属主变 root sudo 只给 make install
-j 开满 Qt 单文件吃内存大 按内存定并发，dmesg 查 OOM
用 gcc 编 C++ 不链 libstdc++ 链接驱动用 g++
路径带中文或空格 Makefile 拼参数裂开 全 ASCII 无空格

这些条目的共同点是：都不报编译错误，或者报的位置和根因隔着一层。判阶段的习惯养起来，加上一张速查表，Qt 的构建报错就没什么可怕的了。
