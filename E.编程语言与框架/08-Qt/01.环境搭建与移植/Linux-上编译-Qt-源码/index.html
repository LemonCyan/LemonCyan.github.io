这篇讲「从源码自己编一套 Qt」：为什么编、装什么依赖、configure 怎么配、make 多久、装完怎么验，以及编不动时最常见的那几个坑。

不讲 X11 与 Wayland 的底层机制，不讲 qmake 与 CMake 的语法细节，也不讲某个项目的代码怎么写。

只覆盖与「编 Qt 本身」相关的报错。装完跑程序报错、链接报错、插件加载失败，看同子目录的《Qt 编译常见错误》；MySQL、PostgreSQL、ODBC 驱动要单独编插件，看《数据库驱动编译》。

主线是 Linux 桌面（x86_64）上的桌面版 Qt。交叉编到 ARM 的思路一致，只是多一层工具链和 sysroot。

一、什么时候需要自己编译 Qt #

先说结论：自己编 Qt 的意义是按需裁剪与交叉编译，不是「装不上时的备选方案」。

官方 .run 安装包、仓库里的 qt5-default，装起来快，十分钟跑出一个窗口。代价是拿到的是别人替你做的决定：模块全塞进去，configure 选项按大众口味定，编译器和 ABI 也锁死了。

场景 官方二进制包能干吗 自己编解决什么
目标是 ARM 嵌入式 Linux 不提供二进制 用 arm-linux-gcc 交叉编出自己的库，唯一可行的路
只用 QtCore + QtWidgets，产物要小 全模块装下来一大坨 -skip 掉用不上的模块
要静态链接 基本不给 -static 编一份，部署不带一堆 .so
系统编译器版本特殊 二进制包是别的 GCC 编的 用本机编译器重编，ABI 对齐
要 -developer-build 调试 Qt 内部 不能 开着调试符号编

「编译器与 Qt 库必须配套」是理解整件事的入口。Qt 本质就是一个 C++ 类库，配 Qt 环境本质是配一套 C++ 环境再把库塞进去，顺带附上 designer、linguist、qmake 这些工具。

Qt 是跨平台的库，在哪个平台用都需要一个编译器。Windows 下用 VS2010 当编译器，就得下 VS2010 版本的 Qt 二进制库；装了 VS2010 的库，就必须用 VS2010 编程序。不同编译器编出来的同一段代码，生成的库不能互相替代——VS2008 编的 Qt 库，拿到 VS2010 的编译器下面用不了。这条规矩在 Linux 上一样成立：仓库里的 Qt 是某个 GCC 编的，你换了大版本或换了 libstdc++，链接和运行时就出说不清的问题。

大部分平台官网都有二进制库：Windows、Linux、Android、iOS、macOS。嵌入式 Linux（比如毕设用的 ARM 板子）官方不给，所以要先有交叉编译器 arm-linux-gcc，再下 Qt 源码，用它去编。

一个能干活的环境，拆开是四样东西：

text
编译器     g++ / arm-linux-gcc，把 C++ 编成目标代码
Qt 库      与编译器 ABI 匹配的 libQt5*.so，提供 Qt 的类和符号
调试器     gdb（MinGW/GCC 路线）或 CDB（MSVC 路线）
构建套件   Kit，把上面三样打包绑定，供工程选用

在 Qt Creator 的「工具 → 选项 → 构建和运行」里配，探不到就手动点「添加」填路径。报错时按这四层定位：编译不过看编译器，链接缺符号看 Qt 库版本，调试没反应看调试器，提示「没找到合适的套件」看 Kit。

二、编译前要装哪些依赖 #

Qt 源码里没有第三方库的副本，缺什么就编不下去。装依赖偷懒，后面 configure 会一条一条还给你。

bash
# Ubuntu / Debian
sudo apt-get update
sudo apt-get install -y build-essential perl python3 \
    libgl1-mesa-dev libglu1-mesa-dev freeglut3-dev \
    libxcb1-dev libxcb-xinerama0-dev libxcb-icccm4-dev libxcb-image0-dev \
    libxcb-keysyms1-dev libxcb-randr0-dev libxcb-render-util0-dev \
    libxcb-shape0-dev libxcb-xfixes0-dev libxcb-xkb-dev \
    libxkbcommon-x11-dev libxkbcommon-dev libx11-xcb-dev libxext-dev \
    libfontconfig1-dev libfreetype6-dev libssl-dev libsqlite3-dev \
    libicu-dev libdbus-1-dev libpng-dev libjpeg-dev

# CentOS / RHEL
sudo yum groupinstall "Development Tools"
sudo yum install -y perl python3 libxcb libxcb-devel xcb-util xcb-util-devel \
    libX11-devel libXext-devel mesa-libGL-devel mesa-libGLU-devel \
    freeglut-devel fontconfig-devel libpng-devel openssl-devel sqlite-devel

xcb 这一族最容易被漏掉，一句粗暴但管用的原话是 yum install xcb*。

依赖 缺了会怎样 装什么
C++ 编译器与 make configure 直接退出 build-essential / gcc-c++ make
perl / python3 生成脚本与构建脚本跑不动 perl、python3
xcb 系列 error libxcb: the test for linking against libxcb ... failed libxcb*-dev / xcb*
OpenGL（GL/GLU） cannot find -lGL libgl1-mesa-dev、libglu1-mesa-dev
freeglut 部分示例与测试编译失败 freeglut3-dev
OpenSSL 网络模块没有 SSL 支持 libssl-dev
sqlite3 QtSql 少了 SQLite 驱动 libsqlite3-dev
xkbcommon 键盘布局相关编不过 libxkbcommon-x11-dev

装之前先看编译器版本，这一步能省掉后面几小时返工：

bash
gcc -v
g++ -v
nproc         # 多少核，决定 make -j 开多少
df -h .       # 源码目录所在分区还剩多少空间
free -g       # 内存多少，决定 -j 开多大而不被 OOM 杀掉

g++ 低于 4.8 时，configure 或编译阶段会冒出：

text
cc1plus: error: unrecognized command line option "-std=c++11"

意思是编译器不认识 C++11 的标准开关，不是 Qt 的问题，是编译器太老。解法只有一条：升 GCC，步骤在第九章。

三、configure 的关键选项 #

qt-everywhere-opensource-src-5.7.x 解压后根目录就有 configure。别在源码树里直接跑，先建独立构建目录：

bash
tar -jxvf qt-everywhere-opensource-src-5.7.0.tar.bz2
mkdir build-5.7.0 && cd build-5.7.0
../qt-everywhere-opensource-src-5.7.0/configure -help

-help 输出几百个开关，真正决定成败的就那么几个：

选项 作用 典型值
-prefix 装到哪 /opt/Qt-5.7.0
-opensource 按开源版授权编译 配 -confirm-license
-confirm-license 跳过交互式授权确认 脚本化必须有
-release / -debug 发行版 / 调试版 交付用 -release
-nomake examples / -nomake tests 不编示例 / 不编测试 两个都加
-skip <module> 整块跳过某个模块 -skip qtwebengine
-static / -shared 静态 / 动态库 默认 -shared
-qt-xcb 用 Qt 自带 xcb 实现，少依赖系统库 系统 xcb 版本怪时用
-no-xcb 完全不编 xcb 平台插件 无图形环境时用
-platform <spec> 目标平台 mkspec linux-g++
-xplatform <spec> 交叉编译的目标 mkspec arm-linux-gnueabihf-g++
-opengl desktop / -opengl es2 OpenGL 后端 桌面用 desktop
-sysroot <path> 交叉编译的系统根 /opt/sysroot
-developer-build 开发者构建，产物留源码树 调 Qt 内部时

一条能直接抄的完整命令：

bash
../qt-everywhere-opensource-src-5.7.0/configure \
    -prefix /opt/Qt-5.7.0 \
    -opensource -confirm-license \
    -release \
    -nomake examples -nomake tests \
    -skip qtwebengine -qt-xcb \
    -opengl desktop -platform linux-g++

configure 跑完会打一张汇总表，把「要编的模块」和「被跳过的模块」分别列出来。这张表要看完再 make。 里面写着 Qt WebEngine: no 之类的行，就是刚才那些开关的效果。少看一眼，等三小时后发现少了模块，就得重来。

configure 本身也会失败，最常见的两类：

text
The specified system/compiler is not supported:
/home/sdb/qt-everywhere-opensource-src-5.7.0/qtbase/mkspecs//opt/qt-everywhere-opensource-src-5.7.0/mkspecs/default
Please see the README file for a complete list.

QMAKESPEC 没设，或者设的版本对不上：

bash
export QMAKESPEC=/home/sdb/qt-everywhere-opensource-src-5.7.0/qtbase/mkspecs/linux-g++

text
error libxcb: the test for linking against libxcb and support libraries failed!
you might need install dependency packages, or pass -qt-xcb

提示里给了两条路：装 xcb 依赖，或者加 -qt-xcb 用 Qt 自带实现。CentOS 上 yum install xcb*，Ubuntu 上 apt-get install libxcb*-dev。

四、编译参数怎么选：-prefix、-opensource、-nomake #

-prefix：装哪 #

-prefix 决定 make install 把东西放哪。装完 qmake -query QT_INSTALL_PREFIX 输出的就是它。

-prefix 好处 风险
/opt/Qt-5.7.0 与系统包彻底隔离，多版本共存，删掉就是删目录 要在 PATH 里加 bin，Kit 里手填 qmake 路径
/usr/local/Qt-5.7.0 在默认搜索路径里 和 /usr/local 下别的东西混在一起
/usr 命令随处可用 和发行版的 Qt 打架，包管理器管不了这批文件

建议在 /opt 下按版本号建目录，多装两个版本互不干扰，Creator 里加几个 Kit 分别指过去。

-prefix 在 configure 阶段只是「先记下来」，make install 时才真去写。中途想换路径不必从零编，改 -prefix 重跑 configure 和 make 就行，但 make 会因为配置变了重扫一遍，时间省不了多少。

-opensource：授权 #

-opensource 告诉 configure 按开源版编译，走 LGPLv3 / GPLv3 那套。商业授权用 -commercial。

bash
# 手工编，交互确认；脚本里编，第二行一次过
../qt-everywhere-opensource-src-5.7.0/configure -prefix /opt/Qt-5.7.0 -opensource
../qt-everywhere-opensource-src-5.7.0/configure -prefix /opt/Qt-5.7.0 -opensource -confirm-license

不带 -confirm-license，configure 会停在交互提示上等按 y 回车。手工编一次无所谓，写脚本批量编或者跑在 CI 里就会卡死在那儿，看起来像编译卡住不动。授权方式选错不是编译问题，是法务问题，静态链接 LGPL 版 Qt 有额外义务，第十一章再说。

-nomake examples -nomake tests：省时间 #

源码树里那一大堆示例和测试不是给你用的，是 Qt 自己验证功能用的，默认会一起编进去，能占掉构建时间的一大截。

参数组合 编什么 时间量级
默认 库 + 工具 + 示例 + 测试 最长
-nomake examples 库 + 工具 + 测试 短一截
-nomake examples -nomake tests 库 + 工具 再短一截
再加 -skip <用不上的模块> 只编你要的部分 视跳掉多少而定

示例源码在源码包里一直都在，需要时单独进去 qmake && make，不必在编 Qt 时顺手编一遍。

-skip：跳过模块 #

-skip 一次跳一个模块，可以写多行：

bash
-skip qtwebengine     # 基于 Chromium，编一次能要命，不用网页控件就跳
-skip qtwebkit        # 老版网页控件
-skip qtdeclarative   # QML 引擎本身
-skip qtquickcontrols # QML 控件样式
-skip qt3d            # 三维渲染
-skip qtcharts        # 图表控件
-skip qtmultimedia    # 音视频播放、摄像头
-skip qtserialport    # 串口通信

跳掉之后想加回来，得重新 configure 再编。上次用的全套参数在构建目录的 config.status 里，想改就在它基础上改。判断要不要跳的简单办法：先问项目 .pro 里写了哪些 QT +=。写了 QT += webenginewidgets 的，-skip qtwebengine 一定出问题。

一组取舍实例：

bash
# 桌面 GUI 工具，只要 Widgets，不要 QML，不要多媒体
../qt-everywhere-opensource-src-5.7.0/configure \
    -prefix /opt/Qt-5.7.0-min \
    -opensource -confirm-license -release \
    -nomake examples -nomake tests \
    -skip qtwebengine -skip qtwebkit -skip qtquickcontrols \
    -skip qt3d -skip qtcharts -skip qtdatavis3d -skip qtmultimedia \
    -qt-xcb -opengl desktop -platform linux-g++

五、编译过程与耗时 #

configure 成功之后就是 make，这步没什么技巧，主要是别把机器拖死：

bash
make -j$(nproc) 2>&1 | tee build.log
内存 建议 -j 原因
4G 以下 2 到 4 并行度高了会被 OOM killer 杀掉
8G nproc 或核数的一半 平衡
16G 以上 nproc 或 nproc + 1 吃满 CPU

-j 开太大，最典型的表现是这样一行突然出现在日志里：

text
c++: fatal error: Killed signal terminated program cc1plus

或者干脆 make: *** [xxx] Error 137。不是代码有错，是内存不够，编译器进程被系统杀了。把 -j 降下来重跑，make 会从断了的地方接着编。

耗时没有标准答案，视机器而定，动辄数小时。核数少、内存小、还留着 examples 和 tests 的，时间往长了走；服务器 32 核一路 -j32、又 -skip 掉一堆模块的，能压到很短。别在教程里找「我用了多少分钟」当参照，机器不一样，数字没意义。

编译过程中一直往外打内容，说明它好好活着。有句话说得挺对：看它一直在输出没有立刻停下来，应该开心。真停下来不动了，才是要处理问题的时候。

make 分三段推进：

text
一  qmake 扫 mkspecs，生成各模块的 Makefile
二  编 qtbase，这是地基，QtCore / QtGui / QtWidgets 都在这里
三  并行编其余模块与 tools（qmake、moc、uic、rcc、designer、linguist）

qtbase 卡住时后面什么都动不了，所以它的报错要第一时间解决，别指望「后面说不定能过」。

bash
make -k              # 出错不退出，把能编的都编完，一次性收集所有错误
make clean           # 清掉编译产物，保留 Makefile
make distclean       # 连 Makefile 一起清，回到 configure 之前

make distclean 之后就等于没 configure 过。真到了「怎么改都不对」的地步，重新来一遍比跟 Makefile 较劲快。长时间编译的常规做法是后台跑、日志落文件，SSH 断了也不会把编译带走：

bash
nohup make -j8 > build.log 2>&1 &
tail -f build.log

六、安装与验证 #

bash
sudo make install

装到 /opt 下要 root，装到自己家目录（-prefix $HOME/Qt-5.7.0）就不需要。权限不对会在最后一步全盘失败，白等几小时。

装完先把路径接上：

bash
export PATH=/opt/Qt-5.7.0/bin:$PATH
export QTDIR=/opt/Qt-5.7.0
export LD_LIBRARY_PATH=/opt/Qt-5.7.0/lib:$LD_LIBRARY_PATH

# 更干净的做法：交给系统管
echo "/opt/Qt-5.7.0/lib" | sudo tee /etc/ld.so.conf.d/qt-5.7.0.conf
sudo ldconfig

ldconfig 之后 ldd 才找得到 libQt5Core.so.5，否则跑程序直接报 error while loading shared libraries。写进 ~/.bashrc 就长期管用。

验证按顺序做，一层一层来（下文 $PREFIX 就是 configure 时 -prefix 那个目录）：

验证项 命令 期望
qmake 是不是新的 which qmake、qmake -v 路径在 /opt/Qt-5.7.0/bin 下，版本号对
安装前缀 qmake -query QT_INSTALL_PREFIX 输出 configure 时的 -prefix
平台插件在不在 ls $PREFIX/plugins/platforms/ 有 libqxcb.so（桌面版）
库文件 ls $PREFIX/lib/libQt5Core.so* 有 .so、.so.5、.so.5.7.0
真能编译 见下面的 hello 工程 编过、跑起来、出窗口 
cpp
// main.cpp
#include <QApplication>
#include <QLabel>
int main(int argc, char *argv[])
{
    QApplication app(argc, argv);
    QLabel label("hello qt");
    label.show();
    return app.exec();
}

bash
printf 'QT += widgets\nSOURCES += main.cpp\n' > qthello.pro
qmake && make && ./qthello

窗口弹出来，源码编译这条路就通了。窗口没弹但编译过了，多半是 DISPLAY 没设或者 libqxcb.so 加载失败，看《Qt 编译常见错误》。

最后把它接进 Qt Creator。「工具 → 选项 → 构建和运行」里三页要填：Qt Versions 页添加 /opt/Qt-5.7.0/bin/qmake，Creator 自动读出这套 Qt 的信息；编译器页填 gcc / g++ 路径，交叉编译时填 arm-linux-gcc；构建套件页新建 Kit，把上面两个和一个调试器绑起来。

Kit 这层抽象解决的是「机器上装了好几套 Qt」这个现实问题。同一台机器上有 MinGW 版 Qt 4.7 和 VS2010 版 Qt 4.8，编的时候用哪套？靠 Kit 选。

一个 Qt 工程在编译时必须至少绑定一个 Kit，绑定关系存在工程目录的 xxx.pro.user 里。所以拿到别人的代码一打开就提示「没找到合适的套件」——对方交付时删了 xxx.pro.user。就算不删，工程换到你的机器上也会提示「无用的构建套件」，两台机器的编译环境很难一模一样。到这一步去 Kit 页重指一遍，别改代码。xxx.pro.user 不进版本库，是常规做法。

七、Ubuntu 下 Qt5.3.1 的安装与卸载 #

这一节讲另一条路：官方 .run 二进制安装包。装的是别人编好的成品，不能裁剪、不能交叉编译，但十分钟能完事，适合先跑起来看看 Qt 长什么样。以 Ubuntu 14.04、Qt 5.3.1 为例。

安装 #

下载 qt-opensource-linux-x86-5.3.1.run（「Qt 5.3.1 for Linux 32-bit」），进到文件所在目录：

bash
chmod u+x qt-opensource-linux-x86-5.3.1.run
./qt-opensource-linux-x86-5.3.1.run
cd Qt5.3.1/Tools/QtCreator/bin/ && ./qtcreator

图形界面里一路下一步：组件选择处点 select all（全选），授权协议选 LGPL，装。最后那句是启动 Qt Creator，也可以在文件管理器里双击 qtcreator。

OpenGL 库：系统里已经装了就跳过，没装的话：

bash
sudo apt-get install freeglut3-dev

不装这一条，后面编 GUI 程序多半卡在 cannot find -lGL。

建桌面快捷方式 #

Ubuntu 的桌面图标是 .desktop 文件。在桌面新建 Qt5.3.1.desktop：

ini
[Desktop Entry]
Categories=Development;
Comment[zh_CN]=
Comment=
Exec=/home/warsllon/SoftWare/Qt5.3.1/Tools/QtCreator/bin/qtcreator
GenericName[zh_CN]=IDE
GenericName=IDE
Icon=/home/warsllon/Pictures/Qt.png
MimeType=
Name[zh_CN]=Qt5.3.1
Name=Qt5.3.1
Path=
StartupNotify=true
Terminal=false
Type=Application
X-DBUS-ServiceName=
X-DBUS-StartupType=
X-KDE-SubstituteUID=false
X-KDE-Username=warsllon

真正要改的只有三行：Exec 填 qtcreator 可执行文件的完整路径，Icon 填图标 png 的完整路径，Name 填桌面图标显示的名字。然后赋执行权限：

bash
cd /home/warsllon/Desktop && chmod +x Qt5.3.1.desktop

图标变成可双击的样子，快捷方式就建好了。有些 Ubuntu 版本要求把文件放到 ~/.local/share/applications/ 才会出现在应用列表里，桌面那份只是快捷入口。

卸载 #

.run 装的 Qt 不能靠 apt-get remove 卸，它有自己的卸载器：

bash
cd /home/warsllon/SoftWare/Qt5.3.1
./MaintenanceTool

进图形界面按提示选卸载即可。装在哪就进哪个目录找 MaintenanceTool，-prefix 那套说法的对应物就是安装时选的目录。

编程序时报 cannot find -lGL #

text
cannot find -lGL

装 OpenGL 相关的开发包，三个任选其一或多个：

bash
sudo apt-get update
sudo apt-get install libqt4-dev
sudo apt-get install libgl1-mesa-dev
sudo apt-get install libglu1-mesa-dev

装之前先更新索引，源最好换成国内镜像再更新，不然等半天。libqt4-dev 这个名字有点误导，它拉进来的是一批底层图形依赖，Qt5 的工程照样受用；真想干净一点，直接上 libgl1-mesa-dev。

两条路的对比 #

维度 .run 二进制安装 源码编译
耗时 十分钟 数小时
能否裁剪模块 只能整体选装 -skip 精确裁
能否交叉编到 ARM 不能 能，唯一路子
编译器与 ABI 官方锁定 自己定，与本机对齐
卸载 MaintenanceTool 删掉 -prefix 目录
打补丁 不行 改源码重编

先用 .run 把环境跑通，确定要交付的东西对体积、目标平台有要求了，再转源码编译。反过来先花半天编一份，结果发现只需要写个 hello，不合算。

八、编译器版本的影响 #

Qt 每个版本对编译器都有最低要求，写在官方 Supported Platforms 页上，也实打实体现在 configure 和编译过程里。大致对应关系（具体数字随小版本变化，以官方页面为准）：

Qt 系列 编译器最低要求 语言标准
Qt 4.x GCC 3.4 往上 C++98
Qt 5.0 ~ 5.6 GCC 4.5 往上 C++98 / 部分 C++11
Qt 5.2.1 GCC 4.8.2（实测结论，要 C++11 特性） C++11
Qt 5.7 GCC 4.7 往上 C++11
Qt 5.9 ~ 5.12 GCC 4.8 / 5 往上 C++11
Qt 5.15 GCC 5 往上 C++11 / C++14
Qt 6.x GCC 8 往上 C++17

具体例子：CentOS 6.5 自带的 GCC 是 4.4，而 Qt 5.2.1 需要 4.8.2 的支持（C++11 特性），所以必须先升 GCC。CentOS 7 默认的 GCC 就是 4.8.2，这条坑它天然躲过去了。

版本不够时症状长这样：

text
cc1plus: error: unrecognized command line option "-std=c++11"

g++ -v 一看，4.4.8，太旧，不认识这个开关。改代码没用，改 configure 参数也没用，只能换编译器。

还有一类更隐蔽的：编译器版本够，但 libstdc++ 太旧。

text
./myapp: /usr/lib64/libstdc++.so.6: version `GLIBCXX_3.4.20' not found

编译机上用的是新 GCC 对应的 libstdc++，运行环境里还是老的那份。strings /usr/lib64/libstdc++.so.6 | grep GLIBCXX 能看到它最高支持到哪个版本。要么把运行环境的 libstdc++ 一起升上去，要么用老编译器编。

为什么 Qt 库和编译器必须配套，根子上是三条：

text
ABI        C++ 的名字修饰、异常处理、虚表布局，编译器之间不一定一致
libstdc++  库是用某个版本的 C++ 标准库编的，换版本就有符号对不上
特性开关   有的 Qt 库开了 C++11，有的没开，混链会缺符号

所以「我机器上有个现成的 Qt 库，拿来用」这件事，得先问清它是谁编的。仓库里的 Qt 配仓库里的 GCC，是最稳的组合。自己升了 GCC 之后，仓库那份预编译 Qt 就不一定能用了，这也是自己编一份的理由之一。

九、GCC 版本不匹配的问题 #

这一节把「系统 GCC 太旧、先升 GCC」这条完整走一遍。这里有两个版本：CentOS 6.5 + GCC 4.8.2 的完整流程，和 Ubuntu + GCC 4.8.0 的精简流程。

9.1 编译安装 GCC 4.8.2（CentOS 6.5 场景） #

bash
tar -jxvf gcc-4.8.2.tar.bz2
cd gcc-4.8.2
./contrib/download_prerequisites    # 联网时，脚本自动 wget 依赖包并编译

GCC 4.8 需要三个依赖包，版本号是死的：

依赖 版本
MPFR mpfr-2.4.2
GMP gmp-4.3.2
MPC mpc-0.8.1

断网时手动下载，严格按版本号，并且按 GMP → MPFR → MPC 的顺序编译，顺序错了 GCC 的 make 会失败：

text
GMP    http://ftp.gnu.org/gnu/gmp/                       gmp-5.1.3.tar.bz2
MPFR   http://ftp.gnu.org/gnu/mpfr/                      mpfr-3.1.2.tar.gz
MPC    http://www.cise.ufl.edu/mirrors/GNU/pub/gnu/mpc   mpc-1.0.1.tar.gz

装 GMP。make check 这一步别省，它查有没有文件不匹配或缺失，最后会打一堆结果，翻一遍看有没有 error 之类的提示：

bash
cd gmp-5.1.3
./configure && make && make check && make install

装完要记住头文件和库文件落在哪：这次安装会进 /usr/local/include 和 /usr/local/lib，下一步装 MPFR 要用这两个路径。

bash
cd ../mpfr-3.1.2
./configure --with-gmp-include=/usr/local/include --with-gmp-lib=/usr/local/lib
make && make check && make install

cd ../mpc-1.0.1
./configure && make && make check && make install

那两个 --with-gmp-* 就是在告诉它「上一步那个 GMP 在这儿」。每步跑完都看一眼有没有报错，别一口气跑到底再回头找。

三个都装好之后，把 /usr/local/lib 加进库搜索路径，GCC 编译时要用：

bash
export LD_LIBRARY_PATH=$LD_LIBRARY_PATH:/usr/local/lib

第三步，配置 GCC 编译选项。和编 Qt 一样建独立目录，别在源码树里编：

bash
cd ..
mkdir gcc-build-4.8.2 && cd gcc-build-4.8.2
../gcc-4.8.2/configure --enable-checking=release --enable-languages=c,c++ --disable-multilib
make -j4
sudo make install
gcc -v

注意路径是 ../gcc-4.8.2/，少一层就找不到；配置完会生成 Makefile。编源码时新建目录的意义就在这儿：编出来的文件全在当前目录，不会和源码混在一起。

  • -j4 是四个作业并行，能提速度。这一步耗时很长，经验值是一个小时上下，机器差的话更久。
  • make install 要 root。切换 root 之后注意把工作目录切回 gcc-build-4.8.2，不然找不到 Makefile。
  • 最后的 gcc -v 是检测。

configure 那几个参数值得单独说清：

参数 含义
--prefix GCC 的安装目录，CentOS 6.5 下装到默认的 /usr 最省事
--enable-languages 这套 GCC 能编哪些语言，逗号分隔，如 c,c++,java；只写 c,c++ 就不带 Java、Fortran
--disable-multilib 关掉交叉位宽编译。默认能在 64 位系统上编 32 位程序、在 32 位系统上编 64 位程序；加上就只编本机字长
--enable-checking=release 关掉内部一致性检查，编出来的编译器跑得更快

9.2 编译安装 GCC 4.8.0（精简流程） #

同一件事的另一条记录，步骤更短：

bash
wget http://ftp.gnu.org/gnu/gcc/gcc-4.8.0/gcc-4.8.0.tar.bz2
tar -jxvf gcc-4.8.0.tar.bz2 && cd gcc-4.8.0
./contrib/download_prerequisites && cd ..
mkdir gcc-build-4.8.0 && cd gcc-build-4.8.0
../gcc-4.8.0/configure --enable-checking=release --enable-languages=c,c++ --disable-multilib
make -j4 && sudo make install

下载地址别写错，是 ftp.gnu.org，不是 http: 后面直接跟路径。这一步耐心等，它一直在输出说明在好好干活，真停下来不动了才要处理。

9.3 切到新 GCC #

新 GCC 装完，/usr/bin/gcc 还是系统那个老的。先确认新版在哪：

bash
ls /usr/local/bin | grep gcc

想按文件名找，可以先 updatedb，再用 locate gcc-4.8 | tail。新版默认落在 /usr/local/bin 下，名字带三元组前缀，比如 i686-pc-linux-gnu-gcc。

bash
sudo update-alternatives --install /usr/bin/gcc gcc /usr/local/bin/i686-pc-linux-gnu-gcc 40

几个位置参数的含义：

text
/usr/bin/gcc                          要接管的链接
gcc                                   这组候选的名字
/usr/local/bin/i686-pc-linux-gnu-gcc  新 GCC 的实际路径
40                                    优先级，数字大的自动胜出

优先级设大一些，装上就自动用新版。g++ 也要照样来一遍，只切 gcc 不切 g++，C++ 那边还是老版本。切完用 gcc -v、g++ -v 确认。

9.4 切了但版本没变 #

有个挺典型的坑：远程 SSH 登录上去切完 GCC，gcc -v 还是旧版本号。断开重连，重新开一个会话，就变成 4.8 了——原因是 shell 的命令路径缓存（hash）和已经载入的环境。

现象 处理
同一会话里 gcc -v 还是旧版 断开重连，或 hash -r 清掉路径缓存
which gcc 指到 /usr/bin/gcc 但版本没变 新 GCC 没装在 alternatives 指的路径上，ls 确认
重连后还是旧版 update-alternatives 装的时候优先级没设，或者 PATH 里 /usr/bin 在前
g++ -v 和 gcc -v 不一致 g++ 那组候选没切
新版在但一跑就报库找不到 /usr/local/lib 没进 LD_LIBRARY_PATH

update-alternatives --config gcc 能看到所有候选并手动选一个，比反复 install 干净。

十、编译中的常见问题 #

现象 根因 处理
The specified system/compiler is not supported QMAKESPEC 没设，或指到了错路径 export QMAKESPEC=...mkspecs/linux-g++
unrecognized command line option "-std=c++11" g++ 低于 4.8 先升 GCC，见第九章
error libxcb: the test for linking against libxcb ... failed 缺 xcb 依赖 yum install xcb* 或 -qt-xcb
cannot find -lGL 缺 OpenGL 开发包 libgl1-mesa-dev、libglu1-mesa-dev
Killed signal terminated program cc1plus 内存不够 降 -j，加 swap
No space left on device 磁盘满 清空间，换分区
qmake -v 显示旧版本 PATH 里系统 qmake 在前 调 PATH 顺序
error while loading shared libraries: libQt5Core.so.5 库路径没进 ldconfig 加 ld.so.conf.d 后 ldconfig
Project ERROR: Unknown module(s) in QT: xxx 那个模块被 -skip 了 重新 configure 加回来

QMAKESPEC #

text
The specified system/compiler is not supported:
/home/sdb/qt-everywhere-opensource-src-5.7.0/qtbase/mkspecs//opt/qt-everywhere-opensource-src-5.7.0/mkspecs/default
Please see the README file for a complete list.

报错里那串路径本身就有问题：mkspecs/ 后面又拼了一段完整路径，说明 QMAKESPEC 要么没设、要么设成了另一个版本源码树的路径。

bash
export QMAKESPEC=/home/sdb/qt-everywhere-opensource-src-5.7.0/qtbase/mkspecs/linux-g++

路径要指到具体那个 mkspec 目录（linux-g++），不能只指到 mkspecs。指向 mkspecs/default 也不通，default 是个软链接，链到它对不对全看运气。QMAKESPEC 一旦写进环境变量，就会一直影响后续所有 qmake 调用；多版本 Qt 共存时，编哪套就先设哪套。

报 -std=c++11 不认识 #

g++ -v 确认版本，4.4.8 这类老版本不认识 C++11 开关。低于 4.8 就编一份新的，按第九章走。别去 configure 里关掉 C++11 指望绕过去——Qt5 的很多模块代码里直接用了 C++11 语法，关了开关只是把报错推到编译阶段，问题一点没少。

libxcb 链接测试失败 #

text
error libxcb: the test for linking against libxcb and support libraries failed!
you might need install dependency packages, or pass -qt-xcb

提示写得很直白，两条路：

bash
# 路线一：补依赖
sudo yum install xcb*              # CentOS
sudo apt-get install libxcb*-dev   # Ubuntu

# 路线二：用 Qt 自带的 xcb 实现，绕开系统库版本问题
../qt-everywhere-opensource-src-5.7.0/configure ... -qt-xcb

路线一干净，路线二快。系统 xcb 版本太新太旧导致链接失败时，路线二是省事的解法。

内存、磁盘与库路径 #

Killed signal terminated program cc1plus 出现在日志里，free -g 看一眼就明白了。-j 从 nproc 降到 nproc/2 再试；不想降并行度就加 swap，但 swap 上的编译速度会拖下来。qtwebengine 是吃内存大户，编它的时候内存占用会跳一个量级，不用网页控件就 -skip 掉。No space left on device 是另一头：源码包两三个 G，编完十几 G 到几十 G，df -h . 提前看，-developer-build 更占地方。

text
error while loading shared libraries: libQt5Core.so.5: cannot open shared object file

ldd ./myapp | grep "not found" 确认是哪个库，然后：

bash
echo "/opt/Qt-5.7.0/lib" | sudo tee /etc/ld.so.conf.d/qt.conf
sudo ldconfig

临时凑合可以用 LD_LIBRARY_PATH，但别让它长期留在 .bashrc 里。

平台插件加载失败 #

libqxcb.so 在 $PREFIX/plugins/platforms/ 下。要么 QT_QPA_PLATFORM_PLUGIN_PATH 指过去，要么确认它的依赖都能找到——ldd $PREFIX/plugins/platforms/libqxcb.so 看有没有 not found。QT_PLUGIN_PATH 设错导致加载了另一套 Qt 的插件，症状也是这个。

十一、静态编译与动态编译 #

默认是动态编译（-shared），编出来的是一堆 .so，程序运行时去加载。-static 编的是静态库，链接时把代码打进可执行文件。

维度 动态（-shared，默认） 静态（-static）
产物 libQt5Core.so.5、libQt5Gui.so.5、… libQt5Core.a、libQt5Gui.a、…
单个可执行文件大小 几百 K 十几 M 起
部署 要带一堆 .so，或依赖目标机的库 一个文件拿走就能跑
依赖系统库 依赖多 仍然依赖 libc、libstdc++
升级 Qt 换 .so 即可 重新链接
插件机制 .so 动态加载 要 Q_IMPORT_PLUGIN 静态导入
编译耗时 短 长，且更容易踩依赖坑
授权 LGPL 相对宽松 LGPL 静态链接有额外义务 
bash
../qt-everywhere-opensource-src-5.7.0/configure \
    -prefix /opt/Qt-5.7.0-static \
    -opensource -confirm-license -release -static \
    -nomake examples -nomake tests \
    -skip qtwebengine -qt-xcb -opengl desktop

-prefix 换个目录，别和动态版装一起。两套 Qt 的 bin/qmake 完全一样地叫这个名字，混装必然出乱子。

静态编译之后插件不会自动进可执行文件，用到哪个要手动导入：

cpp
#include <QtPlugin>
Q_IMPORT_PLUGIN(QXcbIntegrationPlugin)   // 并在 .pro 里加 QTPLUGIN += qxcb

这一步不做，程序启动就报 could not find or load the Qt platform plugin "xcb"——静态版根本没地方去找外部插件。

LGPL 的事要说明白：静态链接 Qt 属于「分发时把库并进了自己的程序」，LGPLv3 要求你能让最终用户用修改过的 Qt 重新组出这个程序。实操上就是提供目标的 .o 文件或者开源你的代码。交付给客户的商业项目要用静态 Qt，先去确认授权，别编到一半才发现不合规。

text
目标机没有包管理器、装不了库，或者要拷一个文件到 U 盘到处跑 -> 静态
开发调试，或者要用大量 Qt 插件（图片格式、SQL 驱动）        -> 动态更省心

十二、裁剪模块减小体积 #

裁剪是自编 Qt 的主要理由。入口有三个，从粗到细：

text
-skip <module>          整块模块不编，最粗也最省事
-nomake examples/tests  不编示例和测试
-no-feature-<feature>   模块内的单个特性关掉，最细

-skip 按「这个模块到底提供什么」来判断：

模块 提供什么 什么情况下可以跳
qtwebengine 基于 Chromium 的浏览器控件 不用网页控件，太占资源
qtwebkit 老版网页控件 新项目不用
qtdeclarative QML 引擎本身 不做 QML
qtquickcontrols QML 控件样式 不做 QML
qt3d 三维渲染 不做 3D
qtcharts 图表控件，含三维数据可视化 不画图表
qtmultimedia 音视频播放、摄像头 不播不算
qtserialport 串口通信 不接串口
qtsensors 传感器 不读传感器
qtwebchannel C++ 与网页互调 不用网页
qtconnectivity 蓝牙、NFC 不碰蓝牙
qtvirtualkeyboard 虚拟键盘 没有触摸屏
qtwayland Wayland 平台插件 只用 X11

特性级别的开关：

bash
-no-icu            # 不要 ICU，省一大截体积，编码转换能力减弱
-no-openssl        # 不要 SSL
-no-gtk            # 不要 GTK 平台主题
-no-feature-dbus   # 关掉 D-Bus 特性

关特性要留意依赖关系：-no-openssl 之后 QtNetwork 的 HTTPS 请求会直接失败，而错误信息出现在运行期，不在编译期。跳之前想清楚这个特性有没有被间接用到。

裁完这样验证：

bash
grep -i -A1 "yes$" config.summary      # 看哪些被打开
ls $PREFIX/lib/libQt5*.so | wc -l      # 编出来多少个模块
du -sh $PREFIX                         # 整套占多少
ls $PREFIX/plugins/sqldrivers/         # SQL 驱动还在不在

config.summary 是构造完的模块清单，比 configure -help 的输出更能说明这次到底编了什么。

裁剪的边界要知道在哪。跳模块能减体积，但减不掉 QtCore、QtGui、QtWidgets 这三个地基——它们几乎是所有 Qt 程序的前提。想再往下减，就是换技术栈的事了。

十三、易错点速查 #

# 现象或时机 处理
1 configure 卡住不动，没报错 少了 -confirm-license，在等交互确认
2 The specified system/compiler is not supported QMAKESPEC 指到 mkspecs/linux-g++
3 unrecognized command line option "-std=c++11" g++ 低于 4.8，先编新 GCC
4 编完 GCC 但 gcc -v 还是旧版 断开重连，或 hash -r；g++ 那组也要切
5 cannot find -lGL libgl1-mesa-dev、libglu1-mesa-dev
6 Killed signal terminated program cc1plus -j 调小，或加 swap
7 编到一半 No space left on device 先 df -h，产物比源码大得多
8 make install 报权限不足 sudo，且目录要切回构建目录
9 qmake -v 指向系统 Qt PATH 顺序，which -a qmake 确认
10 libQt5Core.so.5: cannot open shared object file ld.so.conf.d + ldconfig
11 工程打开提示「没找到合适的套件」 Kit 没绑，去 Creator 里重指，不动代码
12 Project ERROR: Unknown module(s) in QT: xxx 该模块被 -skip，重新 configure
13 编完想换 -prefix 重跑 configure 再 make install，不用从零编
14 多个版本 Qt 混装到同一目录 分开 -prefix 目录，删的时候整目录删

编 Qt 这件事，八成时间花在两处：装依赖，和等 make。剩下的两成是各种版本对不齐。把第二章那张依赖表、第三章那张 configure 选项表、第九章那条升 GCC 的路走顺，剩下就是等。

编之前先想清楚三件事：装到哪（-prefix）、要不要示例和测试（-nomake）、哪些模块真的用不上（-skip）。这三个决定做对了，后面几小时的等待才有意义。做错了，就得从头再来一遍。
