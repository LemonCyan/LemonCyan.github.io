本篇讲什么。 Qt Creator 这个 IDE 本身：它由哪几块组成、左侧模式选择器怎么用、Kit 是什么、怎么配出一个能编译能调试的 Kit、断点怎么打、项目文件和构建流程怎么走、快捷键怎么记。

本篇不讲什么。 Qt 库怎么下载怎么装（看同目录《Qt5.15 的下载与安装》），从空机器到跑出第一个窗口的最短路径（看《Qt 基本环境搭建》），信号槽、模型视图、QML 语法这些语言层内容。

一个前置判断。 装完 Qt，打开 Creator 新建项目就报错，八成不是代码写错了，是 Kit 没配好。这篇的重心在第四到第六章。

一、Qt Creator 是什么：不只是编辑器 #

Qt Creator 是 Qt 官方为自家框架做的 IDE，跨 Windows、macOS、Linux 三个平台，对 C++ 和 QML/Qt Quick 做了针对性优化，界面份量很轻，启动和构建都快。

要理解它，先拆开一个常见的混淆：Qt 这个「东西」其实是两半。

  • Qt Library：编程要用的类库，就是那一堆头文件和 .lib/.a/.so 文件。QWidget、QString、QNetworkAccessManager 全在这里。
  • Qt Creator：IDE，本质是个空壳子。它能编辑、能编译、能调试，但它自己一行代码都不编译，一个库都不带。

这个区分非常关键。因为 Creator 是空壳，所以它必须被「告诉」：用哪个编译器编译、用哪套 Qt 库链接、用哪个调试器调试。这三件事拼起来，就是 Kit。

归 Creator 管 不归 Creator 管
代码编辑、语法高亮、补全 编译器本身（MinGW/MSVC/GCC）
调用 qmake/CMake 生成构建文件 Qt 库文件（.dll/.lib/.a）
调用 make/ninja/mingw32-make 调试器后端（gdb/cdb）
调试器前端（断点、变量、调用栈） 目标设备与操作系统
项目管理、版本控制集成 第三方库（QWT、OpenCV 之类）

还有一个常被误会的关系：Qt Creator 的版本和 Qt 库的版本各走各的。Creator 4.x 配 Qt 5.15 库完全正常，Creator 10 配 Qt 5.9 也能跑。它们通过 Kit 里的 qmake 路径对接，没有强绑定。

跟另两个选择比一比，位置就更清楚了。Visual Studio 只擅长 MSVC 那一套，做 Qt 要装 Qt VS Tools 插件；VS Code 靠插件拼装，qmake 支持一直半生不熟。要做 Qt 开发，Creator 的 Kit 模型和 Designer 集成是省事的。

二、界面布局与常用面板 #

启动 Creator，最左边是一条纵向的 模式选择器。它按开发流程划好了几步，点一下切一个工作区。

模式 英文 用途
欢迎 Welcome 新建工程、管理会话（Sessions）、翻历史项目、跑官方 Demo
编辑 Edit 主战场：代码区 + 项目文件树 + 大纲视图 + 类视图
设计 Design 拖拽式 Qt Designer（C++ UI）或 QML 可视化设计器
调试 Debug 单步、看变量、看堆栈、看内存地址、看 QML 剖析数据
项目 Projects 管 Kit、切 Debug/Release、改构建目录、配环境变量
分析 Analyze 查内存泄漏、定位渲染瓶颈（原稿写作「瓦片瓶颈」，属笔误）
帮助 Help 内置 Qt Assistant，离线 API 文档

七个模式里，日常九成时间在「编辑」，剩下时间里「项目」和「调试」各占一半。新手最容易忽略「项目」，而 Kit 恰恰只在那里改。

编辑模式内部又分几块：

面板 位置 用途
项目树 左侧 按目录展示源码、头文件、.ui、资源、.pro
打开文档 左侧 当前打开的文件列表
书签 左侧 手动标记的行，跨文件跳
文件系统 左侧 直接按磁盘目录看，不受项目包含关系限制
大纲 右侧 当前文件的类、函数、宏清单
类视图 左侧 整个项目的类继承树
代码编辑区 中间 支持分标签、代码折叠、行内错误提示
输出面板 底部 编译输出、应用输出、问题、搜索结果、测试结果

底部输出面板有几个标签值得记住：「编译输出」看编译器和链接器原话，「问题」把错误聚成可双击跳转的列表，「应用输出」接 qDebug() 和 printf 的 stdout，「常规消息」记录 Creator 自己干了什么（比如 qmake 调用参数）。

面板被关掉了怎么找回来：菜单 视图 → 面板（View → Panels）里逐个勾回来。整个布局乱了，去 工具 → 选项 → 环境 → 界面 里重置。低头看输出面板时按 Esc 直接关掉它、焦点回代码区，这个动作一天能用几十次。

三、项目与 .pro、CMakeLists #

新建项目走 文件 → 新建文件或项目。向导里模板很多，容易挑花眼，实际常用的就四个。

模板 生成什么 适合谁
Qt Widgets Application main.cpp + 主窗口类 + .ui + .pro 传统桌面程序，控件式界面
Qt Quick Application main.cpp + main.qml + 资源文件 纯 QML/JS 界面，做动画和交互
Qt Quick Extension Plugin 一个 QML 能直接 import 的 C++ 插件骨架 把 C++ 底层能力封给 QML 用
Empty Qmake Project 只有一个 .pro，别的什么都没有 老手从零手写，或做纯逻辑库

选模板的本质是选「向导帮你写多少样板」。Qt Quick Extension Plugin 这类要留意的点是：它产出的是插件（DLL），不是可执行程序，得由别的 QML 应用加载才会跑起来。

.pro 是 qmake 的工程描述文件，语法像简化版 Makefile。一个能用的最小例子：

text
QT       += core gui widgets
TARGET    = hello
TEMPLATE  = app
SOURCES  += main.cpp
HEADERS  += mainwindow.h
FORMS    += mainwindow.ui
CONFIG   += c++17

QT += 决定链接哪些 Qt 模块。这里有个经典坑：Qt 5 把 widgets 从 gui 里拆出来了，只写 QT += core gui 的话，#include <QApplication> 会在编译阶段就报找不到头文件。用向导建的项目会自动带上，手写 .pro 或从旧项目拷过来的，一定检查这一行。

其他常用变量：

text
QT += network sql          # 加模块
LIBS += -L"C:\Qwt-6.1.2\lib" -lqwt   # 加第三方库：-L 路径，-l 库名（去掉 lib 前缀和后缀）
INCLUDEPATH += C:/Qwt-6.1.2/include  # 加头文件搜索路径
DEFINES += QT_NO_DEBUG_OUTPUT        # 加宏
CONFIG(debug, debug|release) { ... } # 按构建类型分支

LIBS 那一行是所有第三方库集成的通用写法。QWT 装好后就是这么接进项目的，-L 后面给库目录，-lqwt 表示找 libqwt.a 或 qwt.lib。路径里带空格就加引号。

不用 Creator 也能走完整流程，手工三步是理解构建过程最直接的方式：

bash
qmake -project        # 扫描当前目录，生成 xxx.pro
qmake                 # 读 .pro，生成 Makefile
make                  # 按 Makefile 编译、链接

Windows 上把 make 换成 mingw32-make。跑完目录里会多出 .o 和可执行文件。这条链路暴露了一个事实：qmake 只负责「翻译」，真正干活的是 make 和编译器。Creator 点的那个「构建」按钮，做的也是同样的事，只是把参数拼好了。

CMake 项目是另一条路，Qt 6 起是官方主推。CMakeLists.txt 长这样：

cmake
cmake_minimum_required(VERSION 3.16)
project(hello LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_AUTOMOC ON)
set(CMAKE_AUTOUIC ON)
set(CMAKE_AUTORCC ON)

find_package(Qt5 COMPONENTS Widgets REQUIRED)

add_executable(hello main.cpp mainwindow.cpp mainwindow.h mainwindow.ui)
target_link_libraries(hello PRIVATE Qt5::Widgets)

AUTOMOC/AUTOUIC/AUTORCC 三个开关必须开，否则带 Q_OBJECT 的类会缺 moc 产物，链接阶段报一堆 undefined reference to vtable。

CMake 项目找 Qt 靠 find_package，而 find_package 靠 CMAKE_PREFIX_PATH 指路。这一条和 Kit 直接挂钩：Kit 里配的 Qt 版本，本质上就是给 CMake 传这个路径。找不到 Qt 的报错，多数时候都能追到这儿。

四、构建套件 Kit：Qt Creator 的核心概念 #

如果说 Qt Creator 有哪个概念必须先搞懂，那就是 Kit。

Kit 的定义： 一个 Kit = 一个 Qt 版本 + 一个编译器 + 一个调试器，再加上构建引擎（qmake 还是 CMake）和目标运行设备（Desktop / Android / 嵌入式）。没有配好并激活的 Kit，项目编译不起来。

为什么非要这么一层抽象？因为 Creator 是空壳。你按「构建」，它得知道调哪个 g++.exe 或 cl.exe；按「运行」，它得知道去哪找 Qt5Core.dll；按「调试」，它得知道启动 gdb.exe 还是 cdb.exe。这些答案全打包在 Kit 里。

换个说法：Kit 是 Creator 眼里「一套可用的开发环境」的完整描述。一台机器上可以有好几个 Kit 并存——Qt 5.15 + MinGW 一个、Qt 5.15 + MSVC2019 一个、Qt 6.5 + MSVC2022 一个，各自独立，互不干扰。项目可以在这些 Kit 之间切换，切完重新构建即可。

这也解释了为什么「装完 Qt 却用不了」几乎都是 Kit 的问题：

  • 安装程序装了库，但没装编译器（MinGW 版 Qt 的 MinGW 在 Tools 目录里，要单独勾）。
  • 安装程序自动建了 Kit，但路径是安装时的临时路径，移动过 Qt 目录就全废。
  • 手动建的 Kit，Qt 版本和编译器不是一套（MSVC 版 Qt 配 MinGW 编译器），Creator 不拦你，构建时才炸。
  • 同事发来的项目里带了 .pro.user，里面存的是他那台机器的 Kit ID，你这边对不上号。

Kit 不匹配的典型表现，认准这张表，能省几小时：

现象 出问题的阶段 根因 处理
undefined reference to 'QApplication::QApplication(int&, char**)' 链接 Kit 里 Qt 版本与编译器不同源（MSVC 库 + MinGW 编译器，或反着来） 换 Kit，Qt 与编译器必须同源
undefined reference to 'vtable for XxxWidget' 链接 CMake 项目没开 AUTOMOC，或 .pro 漏了 HEADERS 开 AUTOMOC / 补 HEADERS
QtWidgets/QApplication: No such file or directory 编译 .pro 少 QT += widgets，或 Kit 指向了不带该模块的 Qt 补 .pro，核对 Kit 的 Qt 路径
Could not find a package configuration file provided by "Qt5Widgets" CMake 配置 CMAKE_PREFIX_PATH 没指到该 Kit 的 Qt 安装目录 Kit 的 CMake 参数里加 -DCMAKE_PREFIX_PATH=...
LNK1112: 模块计算机类型"x64"与目标计算机类型"x86"冲突 链接 32 位 Qt 配了 64 位编译器 位数对齐，重建 Kit
程序启动报缺 Qt5Core.dll 运行 运行时 PATH 里没有该 Kit 的 bin 目录 用 windeployqt 拷 dll，或配运行环境变量
调试按钮灰着，或提示找不到调试器 调试启动 MSVC 版 Qt 没装 Debugging Tools for Windows，缺 cdb.exe 装 Windows SDK 的调试工具，回 Kit 里补路径
编译秒过、运行时白屏或闪退 运行 构建类型选错（Release 版程序配 Debug 库），或 Kit 的 Qt 是另一套的 dll 清理重建，检查输出目录里的 dll 来源

注意表的第二、四行：编译能过，链接或配置阶段才炸，这种「半路死」的问题最迷惑人。它的信号很明确——编译器找到了头文件（所以编译过了），但链接器拿到的是另一套库。头文件和库不是一对，就是 Kit 的锅。

判断方法很土但很准：打开 项目 模式，看当前激活的是哪个 Kit；再对比 .pro 里 QT += 的模块，和这个 Kit 对应 Qt 目录下 lib 里到底有没有那些库文件。对不上，就是它。

五、Kit 的组成：Qt 版本、编译器、调试器 #

把 Kit 拆到字段级别，才知道每一栏该填什么。

Qt 版本 #

Qt 版本这一栏填的不是一串版本号，而是一个 qmake.exe 的绝对路径。Creator 拿到路径后，自己执行一次 qmake -query，把这套 Qt 的所有关键路径问出来。

text
QT_INSTALL_PREFIX:C:/Qt/5.15.2/mingw81_64
QT_INSTALL_BINS:C:/Qt/5.15.2/mingw81_64/bin
QT_INSTALL_LIBS:C:/Qt/5.15.2/mingw81_64/lib
QT_INSTALL_HEADERS:C:/Qt/5.15.2/mingw81_64/include
QMAKE_XSPEC:win32-g++
QT_VERSION:5.15.2

这份输出就是 Kit 的「身份证」。QMAKE_XSPEC 这一项尤其关键，它指向 mkspecs 目录下的哪套配置——win32-g++ 代表 MinGW，win32-msvc 代表 MSVC。编译器、ABI、异常模型、默认链接参数全由它决定。

这也解释了一件事：为什么 MSVC 版 Qt 不能用 MinGW 编译。不是 Creator 想限制你，是那套库的 ABI 从一开始就按 MSVC 编的。

编译器 #

C++ 编译器，三选一：MinGW 的 g++.exe、MSVC 的 cl.exe、Linux 下的 g++。

硬规则只有一条：位数必须与 Qt 库一致。32 位的 libQt5Core.a 只能被 32 位编译器链接，混了就报 LNK1112 或 cannot find -lQt5Core。

MSVC 编译器不是一个 exe，而是一堆环境变量（INCLUDE、LIB、PATH）。Creator 靠「编译器条目」记录这套环境，自动探测时从注册表里读 VS 安装信息。VS 装了但没勾「使用 C++ 的桌面开发」工作负载，Creator 就找不到 cl.exe。

调试器 #

平台/Qt 版本 调试器 说明
MinGW 版 Qt gdb.exe 跟 MinGW 一起装在 Tools 目录
MSVC 版 Qt cdb.exe 来自 Debugging Tools for Windows
想用 VS 那套 VS Debugger 需要 VS 在，Creator 支持有限
内核/驱动 WinDbg 内核态调试，常规开发用不上

Windows 上的调试器选择容易乱：VS 自带的那套叫 VS Debugger，还有 cdb、windbg 两个独立工具。MSVC 编译的 Qt 配的是 cdb，不是 VS Debugger。所以只装 VS 不装 Debugging Tools for Windows，Kit 里调试器那一栏就是空的，调试按钮点不动。cdb.exe 在 Windows SDK 的 Debuggers\x64\ 目录下。

MinGW 那边省事，gdb.exe 跟编译器在同一个 bin 目录，一路配下来不用额外装东西。

剩下两项 #

字段 取值 什么时候要动
构建引擎 qmake / CMake 项目用哪个就选哪个，CMake 项目必须选 CMake
目标设备 Desktop / Android / 嵌入式 / MCU 交叉编译时才改，桌面开发保持 Desktop

一个 Kit 的完整字段清单，配完对着核一遍：

字段 典型值 配错的后果
名称 Desktop Qt 5.15.2 MinGW 64-bit 只是标签，随便起
设备类型 Desktop 选错会找不到运行目标
编译器 C++ ...\mingw81_64\bin\g++.exe 报找不到编译器，或 ABI 冲突
调试器 ...\mingw81_64\bin\gdb.exe 调试按钮灰，或断点不停
Qt 版本 ...\mingw81_64\bin\qmake.exe 编译期找不到头文件
CMake Tool 系统 CMake 或 Qt 自带 CMake 项目配不了
CMake Generator MinGW Makefiles / Ninja 生成器与编译器不搭，构建失败

六、配置一个可用的 Kit #

配置入口只有一个：工具 → 选项 → 构建和运行（Tools → Options → Build & Run），里面三个标签页：Qt 版本、编译器、Kit。

先看清装了什么 #

动手前先认目录结构，后面填路径全靠它。

text
C:\Qt\
├─ 5.15.2\
│  ├─ mingw81_64\          ← MinGW 版 Qt 库
│  │  ├─ bin\qmake.exe      ← Kit 里"Qt 版本"要指到这里
│  │  ├─ lib\               ← .a 静态库 / .dll.a 导入库
│  │  └─ mkspecs\win32-g++\
│  └─ msvc2019_64\          ← MSVC 版 Qt 库
│     └─ bin\qmake.exe
└─ Tools\
   ├─ mingw810_64\bin\      ← 编译器 g++.exe + 调试器 gdb.exe
   └─ CMake\bin\cmake.exe

一个 5.15.2 目录下能有多个 xxx_64 子目录，每个对应一套不同的编译器。这就是为什么同一台机器上会有好几个 Kit。

三步配完 #

  1. 注册 Qt 版本。 进 Qt 版本 标签页，点 添加，浏览到 Qt 库 bin 目录下的 qmake.exe。Creator 会立刻执行 qmake -query 并填好版本号，成功的话列表里出现一行 Qt 5.15.2 MinGW 64-bit。
  2. 注册编译器。 多数情况这一步自动完成，Creator 启动时会扫已知路径。没有的话在 编译器 标签页点 添加 → GCC → C++，指到 g++.exe。
  3. 建 Kit。 进 Kit 标签页，添加，把上面注册的 Qt 版本、编译器、调试器三样关联起来，设备类型选 Desktop，然后 Apply。

三步里第三步最容易漏：只注册了 Qt 版本、没建 Kit，项目里依然看不到可用的构建配置。

配完看 Kit 列表左边的小图标：没有黄色感叹号、没有红色警告，就算通了。有感叹号就把鼠标悬上去，Creator 会写清楚缺哪一项。

MinGW 版的具体路径 #

以 Qt 5.5 的 32 位 MinGW 包为例，填的东西是这些：

字段 路径
Qt 版本 5.5/mingw492_32/bin/qmake.exe
编译器 tools/mingw492_32/bin/g++.exe
调试器 tools/mingw492_32/bin/gdb.exe

装 Qt 时如果没勾 MinGW 组件，就得自己下一个 MinGW 装上，路径按自己装的位置填。勾了的话它默认在 Tools 目录下，直接照上表填。

MSVC 版的具体路径 #

MSVC 版要多一步前置：先装对应版本的 Visual Studio，再装 Debugging Tools for Windows，后者提供 cdb。

字段 路径 / 取值
Qt 版本 5.5/msvc2013_64/bin/qmake.exe
编译器 Microsoft Visual C++ Compiler 12.0 (amd64)
调试器 Debugging Tools for Windows (x64)/cdb.exe

32 位同理，全都换 x86。位数上不能有半点含糊：Qt 是 msvc2013_64，编译器就得是 amd64，调试器就得是 x64 那份 cdb。

静态编译的 Kit #

静态编译把要用的库代码直接塞进 exe，产出单个文件就能发。配这种环境的 Qt 版本，走同一套流程，只是 qmake 路径换成静态库目录。

先编出静态 Qt（细节看环境搭建那篇，核心是 configure 带 -static、-platform win32-g++，然后 mingw32-make 加 mingw32-make install），装到 C:\Qt\5.6.0_MinGW_static。然后：

  1. 工具 → 选项 → 构建和运行 → Qt 版本 → 添加，指到 C:\Qt\5.6.0_MinGW_static\bin\qmake.exe。
  2. 用记事本打开 C:\Qt\5.6.0_MinGW_static\mkspecs\win32-g++\qmake.conf，找到 QMAKE_LFLAGS 和 QMAKE_LFLAGS_DLL 两行，在值后面各加上 -static。
  3. 回 Kit 页面新建一个 Kit，Qt 版本选刚加的这个，编译器调试器沿用 MinGW 那套。

第二步是静态链接能成的关键。不改 qmake.conf，qmake 生成的链接命令里不带 -static，产出的 exe 依然会去找 dll。

Linux 下源码编译的 Qt #

源码编译完的 Qt 不在系统默认路径里，qmake 命令会直接报 command not found。先修环境变量，在 ~/.bashrc 末尾加一行：

bash
export PATH=$PATH:/usr/local/Trolltech/Qt-4.8.5/bin
source ~/.bashrc
qmake -v

输出 QMake version 3.0 和 Using Qt version 4.8.5 in ... 才算通。通了之后回 Creator 的 Qt 版本 页 添加，指到同一个 bin 目录下的 qmake。

配完自检 #

  • Kit 列表无感叹号，名称能看清是哪套 Qt 加哪个编译器。
  • 项目 模式里能看到这个 Kit，且能选中。
  • 新建一个空项目，按 Ctrl+B 能编过。
  • 按 F5 能启动并停在 main() 第一个断点。

四条全过，环境就没问题了。有一条不过，回第五章的表里对症状。

七、构建与运行 #

构建类型 #

Creator 支持 Debug、Release、Profile 三种。Debug 带全部符号、不开优化，能单步能看变量；Release 开 -O2、剥符号，体积小、跑得快、断点基本失效；Profile 介于两者之间，用来做性能分析。

三种类型各自有独立的构建目录，互不覆盖，所以能在 Debug 和 Release 之间来回切而不用清理。左下角那排小按钮就是切换入口。

影子构建 #

Creator 默认开影子构建（shadow build）：构建产物不落在源码目录，而是放在旁边一个平行目录，名字带上了 Kit 和构建类型。

text
D:\work\
├─ hello\                                              ← 源码目录，只有源码
└─ build-hello-Desktop_Qt_5_15_2_MinGW_64_bit-Debug\   ← 构建目录
   ├─ Makefile
   ├─ debug\hello.exe
   └─ .qmake.stash

这个设计让源码目录保持干净，同一个项目也能同时有多套构建产物。副作用是路径很长，Windows 上偶尔会撞 260 字符上限，把项目挪到盘符根附近就好。

改构建目录：项目 模式 → Build 页 → 构建目录。

构建流程 #

按一次 Ctrl+B，Creator 内部走四步：

text
1. 生成阶段   qmake hello.pro -spec win32-g++  → Makefile
2. 编译阶段   mingw32-make -f Makefile.Debug    → .o / moc_*.cpp
3. 链接阶段   g++ -o hello.exe ... -lQt5Widgets → hello.exe
4. 收尾       更新 .qmake.stash，刷新代码模型

.pro 改了、Kit 换了、qmake 参数变了，第一步会重跑。只改 .cpp 的话，第二步直接增量编译，只重编动过的文件。

编译输出面板能看到每一步的完整命令。链接失败时，别只看最后那句 error，往上翻到那条以 g++ 或 link 开头的长命令——参数里写的是哪个 -L 目录、哪个 -l 库，问题往往就在那儿。

运行配置 #

项目 模式 → Run 页能改三件事：命令行参数、工作目录、运行环境变量。

工作目录别忽略。程序按相对路径读配置文件、读图片，读的是工作目录不是 exe 所在目录。调试时读不到文件，先看这一栏。

运行时缺 dll 是 Windows 上的老问题。Debug 版少 Qt5Cored.dll，Release 版少 Qt5Core.dll，都是运行时的 PATH 里没有 Qt 的 bin。两种解法：

bash
windeployqt.exe --debug C:\path\to\build\debug\hello.exe    # 解法一：把依赖 dll 拷到 exe 旁边
PATH=C:\Qt\5.15.2\mingw81_64\bin;%PATH%                     # 解法二：在 Run Environment 里加 Qt 的 bin

静态编译的 exe 不用这一步，代价是体积大。嫌大的话上 UPX 压一把，先把 upx.exe 拷到 C:\Windows\System32：

bash
upx C:\path\to\hello.exe

压缩比在 40% 上下，压完直接能跑，代价是启动时多一步自解压。

清理的时机 #

遇到这些情况，构建 → 清理 之后再重建，比反复按构建省时间：

  • 换了 Kit 或改了 Qt 版本。
  • 改了 qmake.conf、mkspecs、CMakeLists.txt。
  • 升级了 Qt 小版本。
  • 出现找不到 ui_xxx.h、moc_xxx.cpp 这类生成文件。

八、调试：断点与变量 #

调试器配对了，按 F5 启动。程序跑到第一个断点停住，界面从编辑模式切到调试模式。

断点 #

F9 在光标行打/取消断点。红点表示已生效，空心圈加感叹号表示这个位置放不了断点（头文件里、注释行、被优化掉的代码）。

右键断点能设条件，这是排查「循环第 100 次才出错」的唯一省事办法：

cpp
// 行断点上右键 → 设置断点条件
i == 100            // 命中才停
text.isEmpty()      // 表达式为真才停

还能设「忽略前 N 次」，适合大循环。断点列表在右下角 断点 面板，能一次性禁用全部、按文件分组、给每个断点写备注。

MSVC + cdb 组合下还有数据断点，监视某块内存被写时停下，查野指针很管用，MinGW 的 gdb 对这块支持弱一些。

单步 #

操作 快捷键 含义
继续 F5 跑到下一个断点或结束
跳过 F10 执行完当前行，不进函数
进入 F11 进到被调用函数第一行
跳出 Shift + F11 跑完当前函数，回到调用处
运行到光标 Ctrl + F10 跑到光标所在行

判断用哪个：想知道「这个函数内部干了什么」按 F11，只想知道「它返回了什么」按 F10。进错层了就 Shift + F11 退回来。

调试视图 #

面板 看什么
局部变量 当前栈帧的局部变量和参数
观察器 手动输入的表达式，可加 *ptr、vec[3]、obj->field
调用栈 从 main 到当前行的完整调用链，点一层切一层栈帧
线程 所有线程和各自状态，多线程死锁必看
寄存器 CPU 寄存器值，查汇编级问题时用
内存 指定地址的内存内容，十六进制
模块 已加载的 dll/so 及路径，确认加载的是哪一份
断点 所有断点集中管理
反汇编 当前函数的机器码，与源码对照

调用栈 是定位崩溃的第一站。程序崩了别急着重跑，先看栈：崩溃点在哪一层、上一层是谁调的、参数是什么。顺着栈往上翻两三层，问题原因基本就出来了。

Qt 类型在调试器里有额外支持。QString 不会只显示一个内部指针，而是直接给你文本内容；QList、QVector、QMap 也能展开成元素列表。这套东西靠调试器的 pretty printer 实现，装的是 MinGW 版 Qt 就自带；用 MSVC 版 Qt 加 cdb，个别 Qt 版本上会退化，看到 d = 0x... 这种就是没生效。

QML 调试 #

调 QML 要先在 .pro 里开调试支持：

text
CONFIG += qml_debug

qml_debug 加上 CONFIG += debug，才能用 QML 调试器：在 .qml 文件里打断点、看 QML 元素树、看属性绑定关系、看 JavaScript 表达式实时求值。少了这个宏，断点在 .qml 里根本不生效。

性能类的问题不在调试模式看。到 分析 模式里开 QML Profiler，看渲染、动画、绑定求值各花了多少时间。

调试不通，先怀疑 Kit #

F5 点不动、断点不停、调试器启动就退出，先别怀疑代码。按顺序查三样：

  1. Kit 的「调试器」一栏是不是空的。
  2. 构建类型是不是 Release（Release 不开优化调试信息，断点失效很正常）。
  3. 是不是在调试线程 A、断点打在线程 B（断点面板里能看到）。

这三样都正常，再去 工具 → 选项 → 构建和运行 → Kit，看调试器旁边有没有警告图标。

九、代码导航与重构 #

读别人代码的时间远多于写自己的。Creator 的导航能力靠两套东西撑着：符号索引和定位器。

跟随符号 #

光标停在 QPushButton 或 myFunc() 上按 F2，直接跳到它的声明处；再按一次 F2 跳到定义处。头文件里的声明和 .cpp 里的实现之间，F4 一键往返——这是全篇最值得养成肌肉记忆的键。

Alt + ← 和 Alt + → 管光标历史。F2 跳了七八层找不到北，连按几次 Alt + ← 回到出发点，比在标签页里乱点快得多。

定位器 #

按 Ctrl + K，左下角弹出输入框。定位器不只是一个文件名搜索框，加前缀能换搜索维度。

输入 搜什么
直接敲文件名 在当前项目里找文件，支持 * 通配
: 类名或函数名 搜当前项目的 C++ 类、符号定义
? QML 元素名 在离线 Qt 帮助文档里查该元素说明
l 加行号 跳到当前文件的指定行
a 加文件名 在整个硬盘或包含目录里找附加文件

前缀和关键字之间用空格隔开。不同 Creator 版本支持的前缀不一样，输入前缀后定位器下方会列出可用项，照着选就行。

a 前缀那个「在整个硬盘找」很有用：想翻一份 Qt 自带的示例源码，或者找一个不知道放哪的 .ui 文件，a 比在资源管理器里翻快。

全局搜索 #

Ctrl + Shift + F 打开全局搜索，在「整个项目 / 当前文件 / 指定目录」里找一个字符串，支持正则、区分大小写、按文件类型过滤。结果聚在底部面板，双击跳转。

一个组合用法：先用全局搜索定位「这个常量在哪被用了」，再用 F2 一层层看清调用关系。查配置项、查魔法数字、查废弃 API 的残留，都靠这个。

重构 #

真正跨文件的安全改名是 Ctrl + Shift + R（重命名符号）。它走代码模型，改了之后所有引用点一起变，包括其他文件里的调用。

要在编辑器里直接搜替换字符串，用 Ctrl + F；那是不看语义的纯文本替换，改完容易漏。

想改函数签名，改完声明 Creator 会提示「是否同步修改定义」，选是就一起改了。改完编译一遍，编译器会把所有调用点指出来。

代码模型 #

补全、报错标红、跳转，全都依赖背后跑着的 Clang Code Model 插件。它跟不上文件规模时，编辑区会卡、补全出不来，表现是「打字有延迟」。

这时候两个选择：等它建完索引（第一次打开大项目要几分钟），或者在 帮助 → 关于插件（新版本在选项的插件页）里把它关掉，退回 Creator 内置的简易模型。关掉之后补全变弱，但打字不卡了。

上下文帮助 #

光标停在任意 Qt 类名或函数上按 F1，右侧边栏直接切到该符号的离线文档。这是查参数顺序、返回值类型最快的路径，不用切浏览器。

按 F1 再按一次 F1 会展开完整帮助模式。离线文档跟 Qt 库一起装，装 Qt 时勾了 Documentation 组件才会有。

十一、插件与外部工具 #

Creator 本身功能不算多，加插件才完整。插件管理入口跟版本走：4.x 在 帮助 → 关于插件，较新的版本把插件页挪进了 工具 → 选项，找不到就在选项里翻一圈。

值得开的插件 #

插件 作用
Clang Code Model 补全、跳转、报错的底层，默认开
Git / Subversion 版本控制集成（见下一章）
QML Profiler 分析模式里的 QML 性能剖析
FakeVim 在编辑区用 Vim 键位
Cppcheck 静态检查，编译前先抓一遍明显错误
Beautifier 调用 clang-format / astyle 统一代码风格
Serial Terminal 内置串口终端，调嵌入式省一个工具
Android / BareMetal 交叉编译与裸机调试目标

插件之间偶尔会打架，装上某个插件后 Creator 启动崩了，进 工具 → 选项 前按住不放能进安全模式，先把出问题的插件禁掉再排查。

外部工具 #

工具 → 外部 → 配置 能把任意命令行程序挂进菜单。常用的三个：

text
windeployqt   参数：%{buildDir}/debug/%{CurrentProject:Name}.exe
upx           参数：%{buildDir}/debug/%{CurrentProject:Name}.exe
git-bash      参数：--cd=%{CurrentProject:Path}

挂好之后一个菜单项就能打包部署，不用开终端敲路径。%{...} 是 Creator 的变量，能拿到当前项目名、构建目录、当前文件路径。

Designer 插件机制 #

Qt Designer 的控件箱是可扩展的。第三方控件库只要往 plugins/designer 目录丢一个插件 dll，重启 Designer 后控件箱里就会多一栏。

以 QWT 为例，装完之后要拷三个文件到 Qt 安装目录：

text
qwt-6.1.2\lib\qwt.dll        →  Qt\5.5\mingw492_32\bin\
qwt-6.1.2\lib\libqwt.a       →  Qt\5.5\mingw492_32\lib\
qwt-6.1.2\plugins\designer\qwt_designer_plugin.dll
                             →  Qt\5.5\mingw492_32\plugins\designer\

头文件单独处理：在 ...\mingw492_32\include 下新建 Qwt 文件夹，把 C:\Qwt-6.1.2\include 里的东西全拷进去。之后 .pro 里加 INCLUDEPATH += .../include/Qwt 和 LIBS += -L... -lqwt 就能用。

第三个 dll 是给 Designer 看的，和编译无关。只拷前两个的话代码能编过，但打开 .ui 文件时控件箱里没有 Qwt 控件，QwtPlot 拖不出来。这就是「插件」这个词在两个层面的含义，别混。

分析模式 #

分析 模式对性能问题。Linux 下挂 Valgrind 查内存泄漏和越界；Windows 下用 heob 或 Visual Studio 的内存分析器。QML 那边用 QML Profiler 看绑定求值、动画、渲染各花多少毫秒。

这些工具都要在 Kit 里配对目标程序路径才跑得起来，报错说找不到可执行文件，回 项目 → Run 核对。

十二、版本控制集成 #

Creator 对 Git 的支持够日常用，绝大多数操作不用切终端。

先配环境 #

工具 → 选项 → 版本控制 → Git，填 git.exe 的路径（装了 Git for Windows 的话 Creator 多数能自动找到），再把作者名和邮箱填上。这两项没填，第一次提交会报 Please tell me who you are。

同一个页面往下还有 Subversion、Mercurial、Perforce 的配置，用到哪个配哪个。

界面里能干什么 #

位置 功能
项目树文件名颜色 改过是蓝色，新增是绿色，冲突是红色
右键 → Git 提交、还原、暂存、打标签、看当前文件日志
Ctrl + Shift + L 类似入口 提交编辑器，逐行选择要提交的改动
差异视图 并排显示改动前后，逐块接受或丢弃
分支管理 右下角切分支、新建分支、合并
Blame 每行显示最后修改它的提交和作者

提交编辑器里的「逐行暂存」是它比命令行顺手的地方。改了一大片但只想提交其中两个函数，在差异视图里右键选「暂存块」就行。

Blame 这类操作 Creator 会调 git blame 并把结果叠在行号旁边，看某行代码是谁哪次提交写的、当时改了什么，不用切窗口。

哪些东西不要提交 #

qmake 项目的 .gitignore 写成这样：

text
build-*/
*.user
*.user.*
*.autosave
Makefile
*.o
*.obj
debug/
release/
.qmake.stash

*.user 和 .pro.user 这两条最要紧。.pro.user 里存的是本机的 Kit ID、构建目录、运行配置全是绝对路径。提交上去，同事拉下来打开项目，Creator 会因为 Kit ID 对不上而弹一堆提示，甚至直接构建失败。

换机器、换 Qt 版本、重装系统，第一步就是删掉 .pro.user 让 Creator 重新生成。 这一条能解决相当一部分「项目在别人机器上好好的，我这儿打不开」。

CMake 项目忽略 build/ 和 CMakeCache.txt 就够了，CMakeLists.txt 和 *.cmake 必须进版本控制。

命令行还得留着 #

Creator 的 Git 集成覆盖日常八成操作，剩下两成——rebase -i 整理提交、stash 暂存、reflog 找回误删分支——还是得敲命令。工具 → 外部 → 配置 里挂一个 Git Bash 入口，或者直接 Alt + Tab 切终端。

十三、常见配置问题 #

下面这张表按「报错原文 → 根因 → 处理」组织，遇到问题先 Ctrl+F 搜报错里的关键字。

现象 根因 处理
/usr/bin/ld: cannot find -lGL Linux 缺 OpenGL 开发库 sudo apt-get install mesa-common-dev libgl1-mesa-dev libglu1-mesa-dev freeglut3-dev
qmake: command not found Qt 的 bin 不在 PATH ~/.bashrc 里加 export PATH=$PATH:<Qt>/bin，再 source
Kit 名字后面有黄色感叹号 三要素里缺项 鼠标悬停看提示，回 Kit 页面补
undefined reference to 'vtable for Xxx' 没跑 moc，或 CMake 没开 AUTOMOC qmake 项目把类写进 HEADERS；CMake 开 CMAKE_AUTOMOC
QtWidgets/QApplication: No such file .pro 少 QT += widgets 补上，重新构建
CMake 报找不到 Qt5Widgets CMAKE_PREFIX_PATH 没指对 Kit 的 CMake 参数加 -DCMAKE_PREFIX_PATH=<Qt>/lib/cmake
LNK1112 模块计算机类型冲突 32/64 位混用 Qt、编译器、调试器三者位数对齐
断点打上但不停 Release 构建，或没调试信息 切 Debug，检查 .pro 里没有 CONFIG -= debug
启动报缺 Qt5Core.dll 运行时找不到库 windeployqt 拷 dll，或运行环境加 PATH
.pro.user 报错打不开项目 存的是别人机器的 Kit 删掉 .pro.user，重开项目重选 Kit
编译越编越慢 增量编译状态脏了 构建 → 清理 后重建，删构建目录更彻底
中文注释在编译器里报错 源文件编码与编译器假设不一致 文件存成 UTF-8，.pro 加 QMAKE_CXXFLAGS += -finput-charset=UTF-8
编辑器打字卡顿 Clang Code Model 索引没建完或过载 等索引建完，或禁掉该插件
静态编译的 exe 还是找 dll qmake.conf 没加 -static 改 QMAKE_LFLAGS 和 QMAKE_LFLAGS_DLL，再加 -static

几个值得单独说的。

cannot find -lGL 这个报错在 Linux 上几乎人人遇到一次。含义直白：链接器要 libGL，系统里没有。装完上面那串包（mesa-common-dev、libgl1-mesa-dev、libglu1-mesa-dev、freeglut3-dev）就解决了。这是系统层面的缺库，跟 Kit 无关，但报错出现在链接阶段，很容易误判成 Kit 配置问题。

中文乱码分两个层面。文件存成 GBK，编辑器按 UTF-8 读出来就是乱码，改回 UTF-8 保存即可；文件是 UTF-8 但没 BOM，MSVC 会按本地代码页猜，编译时中文串变乱码，这时加 /utf-8 编译选项（MSVC）或 -finput-charset=UTF-8（MinGW）。MSVC 2015 之后开了 /utf-8 就稳了，在 Kit 的编译器选项或 QMAKE_CXXFLAGS 里加。

编译慢多是两件事叠加：构建目录被反复污染、没开并行编译。.pro 里加 QMAKE_CXXFLAGS += -O0 只影响 Debug；真要快，构建页的 Make 参数加 -j8（数字取 CPU 核数）。CMake 项目换 Ninja 生成器，比 MinGW Makefiles 快一截。

找不到 moc 产物（ui_mainwindow.h、moc_mainwindow.cpp）这类报错，九成是构建目录状态坏了。清理重建，或者直接把 build-* 目录删掉重来，比逐个排查快。

十四、易错点速查 #

收尾一张清单，都是踩过的坑，扫一眼能少走弯路。

易错点 正确做法
以为 Qt Creator 自带编译器和 Qt 库 它是空壳，编译器和库都要单独装、单独配
分不清 Creator 版本和 Qt 库版本 两者独立，靠 Kit 里的 qmake 路径对接
装完 Qt 就以为能用 打开 工具 → 选项 → 构建和运行，确认 Kit 无警告
Kit 里 Qt 版本和编译器不同源 MSVC 版 Qt 配 MSVC 编译器，MinGW 版配 MinGW
位数混用（32 位 Qt + 64 位编译器） Qt、编译器、调试器三者位数一致
只注册 Qt 版本，忘了建 Kit 两个步骤都要做，Kit 才是项目能用的那一层
手写 .pro 漏了 QT += widgets Qt 5 起 widgets 独立成模块，必须显式加
用 undefined reference 报错直接怀疑代码 先怀疑 Kit：编译过、链接炸，说明头文件和库不是一对
CMake 项目找不到 Qt 给 Kit 的 CMake 参数配 CMAKE_PREFIX_PATH
Release 构建里调断点 切 Debug，Release 剥了符号
MSVC 版 Qt 找不到调试器 装 Windows SDK 的 Debugging Tools for Windows，拿 cdb.exe
把 .pro.user 提交进 Git 忽略它，换机器先删再重开项目
构建产物混在源码目录 保持影子构建开着，构建目录独立
静态编译只改 .pro 不改 qmake.conf 静态链接要在 qmake.conf 的 QMAKE_LFLAGS 里加 -static
以为拷 qwt.dll 就能在 Designer 里拖控件 控件箱靠 plugins/designer 下的插件 dll
全局替换变量名 用 Ctrl + Shift + R 重命名符号，走代码模型
忘了 F4 和 F2 头/源切换、跳声明定义，这两个键省下大量翻文件时间
输出面板挡住了代码 按 Esc 关掉，焦点回编辑区
报错只看最后一行 往上翻到完整的 g++ / link 命令，参数才是真相
项目路径深且长 Windows 有 260 字符上限，构建目录放盘符根附近

把 Kit 这一层想清楚，后面所有问题都有了解释的起点：编译器找不到、库链不上、断点不停、dll 缺失，全部能落到「Qt 版本、编译器、调试器」三栏里的某一栏上。下次再遇到构建失败，先打开 项目 模式看一眼当前 Kit，再决定是改代码还是改配置。
