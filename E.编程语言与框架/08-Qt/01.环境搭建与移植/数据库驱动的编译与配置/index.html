这篇讲 Qt 的 SQL 数据库驱动：为什么装好 Qt 也连不上数据库、驱动怎么自己编、编完往哪放。

讲什么：Qt SQL 模块的分层、驱动为什么是插件而不是编进库、QSqlDatabase::drivers() 怎么查、mysql.pro 怎么用 qmake 编、Windows 下 MSVC 一条路和 Linux 下一条路、编出来的 .dll/.so 放到哪、连不上怎么查。

不讲什么：Qt 源码整体怎么编（看同目录的《Linux 上编译 Qt 源码》），Qt 编译期那一堆报错怎么解（看《Qt 编译常见错误》），qmake 与 CMake 工程本身的语法。

先把一句话摆在这，后面九成的坑都能靠它对上号：「Qt 的 SQL 驱动是插件，不是编译进 Qt 库里的。」

一、Qt SQL 模块的架构 #

写 QSqlDatabase::addDatabase("QMYSQL") 的人，大多把 QMYSQL 当成一个枚举值。它不是。它是一把钥匙，Qt 拿这把钥匙去插件目录里找对应的驱动文件。

Qt SQL 模块是分层的。从上往下数：

text
你的业务代码
    |
    v
QSqlDatabase   QSqlQuery   QSqlTableModel   QSqlRelationalTableModel
    |                （统一接口，跟具体数据库无关）
    v
QSqlDriver  <--- 抽象基类，真正的翻译官
    |
    +-- QSQLITE  -> sqlite3        （Qt 自带源码）
    +-- QMYSQL   -> libmysqlclient / libmysql.lib
    +-- QPSQL    -> libpq
    +-- QODBC    -> 系统的 ODBC 驱动管理器

一层一层说清它们的职责。

第一层：QSqlDatabase。 管连接。一个连接有个名字，可以是默认连接，也可以起名做多连接。addDatabase(type) 传的是驱动名，setHostName、setDatabaseName、setUserName、setPassword 传的是参数。这一层不知道对面是 MySQL 还是 PostgreSQL。

第二层：QSqlQuery、QSqlTableModel 这些。 它们只认 QSqlDriver 接口。QSqlQuery::exec() 往下走，走到驱动，驱动再翻译成某个数据库能听懂的方言。

第三层：QSqlDriver。 抽象基类，每个数据库一个子类，比如 QSQLiteDriver、QMYSQLDriver、QPSQLDriver。谁来实现它？驱动插件。插件的 .dll/.so 里就装着这个子类的实现。

第四层：第三方客户端库。 MySQL 驱动自己不会说 MySQL 协议，它调 libmysqlclient（Windows 上是 libmysql.lib 静态导入、libmysql.dll 运行时加载）发报文。PostgreSQL 驱动调 libpq。SQLite 驱动特殊，它直接把 sqlite3 的源码编进去了，不要外部库。

层 职责 谁提供
QSqlDatabase / QSqlQuery 统一 API，连接管理与结果集 Qt 核心库 QtSql
QSqlDriver 抽象接口层，把 API 调用翻成数据库方言 Qt 核心库声明，驱动插件实现
驱动插件 具体数据库的 QSqlDriver 子类 plugins/sqldrivers/ 下的 .dll/.so
客户端库 真正的网络协议与认证 MySQL / PostgreSQL 官方，或 Qt 自带的 sqlite3

看清这张表，driver not loaded 就没什么神秘的了：第一层想找第三层，第三层文件不在位，直接断链。

二、为什么驱动要单独编译 #

有人问过：Qt 都把 sqlite 编进去了，为什么不顺手把 MySQL 也编进去？

三个原因，缺一个都轮不到你去按下 nmake。

原因一：许可。 MySQL 的客户端库由 Oracle 分发，条款跟 Qt 的 LGPL 不是一路的。Qt 官方发布的二进制包如果把某个第三方客户端库塞进去一起发，等于替这个库做分发，责任和条款都跟着来。SQLite 是 public domain，塞进去没人管。所以官方包里的驱动只有一个 SQLite，剩下的留给你自己决定。

原因二：依赖库得在编译时才拿得到。 编 MySQL 驱动要 mysql.h 和 libmysql.lib，编 PostgreSQL 驱动要 libpq 的头和库。这些不在 Qt 源码里，在数据库厂商的开发包里。Qt 发二进制包的时候不知道你机器上装的是哪个版本、放在哪、几位。

原因三：编译器必须同一条链。 Qt 库是拿某个编译器编的，驱动插件是同一个进程里动态加载的 .dll，必须跟宿主同一个 ABI。你拿 MinGW 编出来的 .dll 递给 MSVC 版的 Qt，文件名对得上也加载不了。所以官方就算想发，也得对每一种编译器、每一个位数各发一份，工程量不小。你自己的环境，你最清楚，自己编最省事。

于是有了一条分界线，这条线要记牢：

驱动 Qt 是否自带 是否需要外部库 你要做的事
QSQLITE 自带，QtSql 里就有 不需要，sqlite3 源码随 Qt 一起编 一行代码，直接用
QMYSQL 看版本：较早的版本不带，后来的官方安装包带预编译版 需要 libmysqlclient / libmysql.lib 缺了就自己编，然后部署客户端库
QPSQL 不带 需要 libpq 自己编
QODBC 带 依赖系统里的 ODBC 驱动管理器 配好系统 DSN 就能用
QDB2 / QIBASE 等 不带 各自的客户端库 有需要再编

一句话：SQLite 装好就能用，MySQL 和 PostgreSQL 得自己动手。 这篇后面所有内容，都是围绕这句话展开的。

三、驱动是插件：sqldrivers 目录 #

Qt 加载插件走 QPluginLoader。每个插件文件的元数据里写着它能提供什么接口，Qt 拿接口名去筛。SQL 驱动插件声明的接口名是 org.qt-project.Qt.QSqlDriverFactoryInterface——你不用记这个名字，只要知道：驱动不是被链接进来的，是被搜出来的。

搜的位置在哪？Qt 有一套插件搜索路径，sqldrivers 是其中的一个子目录：

text
<Qt 安装目录>/<编译器套件>/plugins/
    ├── platforms/      平台插件（qwindows.dll 之类）
    ├── imageformats/   图片格式插件（qjpeg.dll 之类）
    ├── sqldrivers/     <-- SQL 驱动就在这
    │     ├── qsqlite.dll
    │     ├── qsqlmysql.dll
    │     └── qsqlpsql.dll
    └── ...

文件名有规矩。Windows 上是 qsql<驱动名小写>.dll，Debug 版末尾多一个 d。Linux 上是 libqsql<驱动名小写>.so。

平台 Release 文件名 Debug 文件名 说明
Windows (MSVC / MinGW) qsqlmysql.dll qsqlmysqld.dll Debug 版加 d 后缀
Linux libqsqlmysql.so 同名，可带 .debug 调试符号 靠构建类型区分
macOS libqsqlmysql.dylib 同名 打包时进 .app/Contents/PlugIns/sqldrivers/

为什么这个设计值得留意？因为它解释了两件事。

一是为什么同一个程序在你机器上能跑，拷到别人机器上就报 driver not loaded。你机器上 plugins/sqldrivers/ 里有那个文件，别人机器上没有。Qt 不会因为链接过 QtSql 就自动带上驱动。

二是为什么部署时不用改一行代码。把文件放进 sqldrivers/ 就生效，删掉就失效。驱动是可选件，装一个是一个。

如果不想用 Qt 安装目录下的 sqldrivers，也可以自己指定搜索路径：程序启动后往 QCoreApplication::addLibraryPath() 里塞一个目录，或者在可执行文件旁边放一个 qt.conf，写清楚 Plugins 指向哪。发布程序常这么干，把所有插件跟 exe 放一起，不依赖用户机器上的 Qt。

四、查看当前有哪些驱动 #

动手编之前，先看清现状。一行代码的事。

新建一个控制台工程，.pro 里写：

text
QT += core sql
CONFIG += console

main.cpp：

cpp
#include <QCoreApplication>
#include <QSqlDatabase>
#include <QDebug>

int main(int argc, char *argv[])
{
    QCoreApplication app(argc, argv);

    const QStringList drivers = QSqlDatabase::drivers();
    qDebug() << "available drivers:" << drivers;

    for (const QString &name : drivers) {
        qDebug() << "  -" << name
                 << "available:" << QSqlDatabase::isDriverAvailable(name);
    }
    return 0;
}

跑起来，输出长这样：

text
available drivers: ("QSQLITE", "QODBC", "QPSQL")
  - "QSQLITE" available: true
  - "QODBC" available: true
  - "QPSQL" available: true

你机器上的列表跟这个不一样，太正常了。列表里有什么，取决于 sqldrivers/ 目录里有什么。

两个细节值得记一下。

QSqlDatabase::drivers() 返回的是已成功加载的驱动名。文件在目录里但加载失败（缺依赖库、位数不对），它不会出现在列表里，只在 qDebug 输出里留一行黄字警告：

text
QSqlDatabase: QMYSQL driver not loaded
QSqlDatabase: available drivers: QSQLITE QODBC QPSQL

看到这两行连着出现，问题就已经定位了：不是你的连接参数写错，不是库没链上，是那个 .dll/.so 没被加载。下一章开始，就是怎么把缺的补上。

QSqlDatabase::isDriverAvailable("QMYSQL") 是单独的查询接口，返回布尔值。写自检代码时用它比解析 drivers() 的列表省事。

顺手还能确认一件事：即便 QMYSQL 不在列表里，QSqlDatabase::addDatabase("QMYSQL") 也不会崩，它只是返回一个无效的 QSqlDatabase。等你 open() 的时候才失败。所以报错时机跟你想的不一样，别在 addDatabase 那一行打转。

五、SQLite：自带可用的那个 #

先把最容易的那条路走通，心里有个对照组。

SQLite 不需要服务端。它就是个文件，打开就是数据库，关掉就是一个文件。Qt 的 QSQLITE 驱动把 sqlite3 的源码直接编进了 qsqlite.dll / libqsqlite.so，不依赖你机器上装了什么。

cpp
#include <QCoreApplication>
#include <QSqlDatabase>
#include <QSqlQuery>
#include <QSqlError>
#include <QDebug>

int main(int argc, char *argv[])
{
    QCoreApplication app(argc, argv);

    QSqlDatabase db = QSqlDatabase::addDatabase("QSQLITE");
    db.setDatabaseName("demo.db");          // 不写路径就是当前工作目录

    if (!db.open()) {
        qDebug() << "open failed:" << db.lastError().text();
        return 1;
    }

    QSqlQuery q(db);
    q.exec("CREATE TABLE IF NOT EXISTS t (id INTEGER PRIMARY KEY, name TEXT)");
    q.exec("INSERT INTO t (name) VALUES ('hello')");

    if (q.exec("SELECT id, name FROM t")) {
        while (q.next()) {
            qDebug() << q.value(0).toInt() << q.value(1).toString();
        }
    }
    db.close();
    return 0;
}

这段代码不需要任何编译期开关，不需要额外的 .pro 配置（QT += sql 就够了），也不需要拷任何库文件。跑通它，说明 QtSql 这一层是活的，缺的只是 MySQL 那个驱动。这个对照组的意义在于：同样是 QSqlDatabase，SQLite 通了而 MySQL 不通，问题一定在驱动，不在你的代码。

三种常见驱动的差别，摆在表里看：

项目 QSQLITE QMYSQL QPSQL
连接对象 本地文件 服务端（TCP / 命名管道 / socket） 服务端（TCP / Unix socket）
外部客户端库 无，sqlite3 源码随 Qt 编译 libmysqlclient / libmysql.lib libpq
Qt 是否随包提供驱动 是 看版本，较早的版本不带 否
默认端口 无 3306 5432
编译难度 无需编译 要编 要编

SQLite 也有它的边界：单写者，高并发写会排队；没有用户与权限体系，文件权限就是权限。选型的事这里不展开，只记住一点——它之所以「装好就能用」，是因为它的依赖为零。

六、MySQL 驱动为什么缺失 #

把时间线拉直。

Qt 5.2 之前，官方安装包不含 QMYSQL。要用 MySQL，必须自己拿 Qt 源码里的驱动工程，配合你的编译器和 MySQL SDK，编出一个 qsqlmysql.dll。

从 Qt 5.2 开始，官方 Windows 安装包里带了预编译的 QMYSQL 驱动插件。装了就有，不用编。但这是「有插件」而不是「能用」——插件本身还依赖 libmysql.dll，那东西不在 Qt 安装目录里，得你自己放。

所以「缺驱动」有三种完全不同的情形，症状看着一样，病根不一样：

text
情形 A：sqldrivers 目录里根本没有 qsqlmysql.dll
        -> 驱动从来没编过，或者装的是精简包
        -> 症状：QSqlDatabase: QMYSQL driver not loaded

情形 B：qsqlmysql.dll 在目录里，但配套的 libmysql.dll 找不到
        -> 插件加载时依赖解析失败，被 Qt 丢弃
        -> 症状：同样一行 not loaded，但目录里明明有文件

情形 C：文件和依赖库都在，但位数或编译器不匹配
        -> 32 位宿主进程加载 64 位插件，或 MinGW 插件给 MSVC 的 Qt 用
        -> 症状：还是 not loaded，外加系统层面的一般性加载失败

这三种情形都指向同一个结论：driver not loaded 不是代码错，是驱动文件不在位。 你在 addDatabase 前后加十个 qDebug 也没用，去 sqldrivers 目录里 ls 一下才是正事。

Windows 上排查 B、C 两种情形有个开关，跑之前设上环境变量：

text
set QT_DEBUG_PLUGINS=1

再启动程序，Qt 会把每个插件的搜索路径、元数据、加载失败原因全打出来。哪个 .dll 因为什么被拒，日志里写得明明白白，比猜快得多。

七、编译 MySQL 驱动的前提 #

自己编之前，把这几样凑齐。少一样，qmake 或 nmake 就会在中间某一步停下。

前提 具体要求 怎么确认
Qt 版本与套件 知道自己的 Qt 装在哪、是哪个编译器套件编的 Qt Creator 的「构建和运行」里看编译器一栏
Qt 源码 安装时必须勾选 Sources 组件，里面有驱动插件源码 到 qtbase/src/plugins/sqldrivers/mysql 看有没有 mysql.pro
编译器 与 Qt 库同一条链（MSVC 对 MSVC，MinGW 对 MinGW） qmake -v 与编译器版本对得上
位数 32 位宿主配 32 位插件配 32 位客户端库 统一，不许混
MySQL 开发包 需要 include 头文件与 lib 库文件，不是只有 Server 目录里能看到 mysql.h 与 libmysql.lib
qmake 可用 用该套件自带的 qmake，不是系统里另一个 打开对应套件的命令行，qmake -v 看路径
目标目录可写 编译产物要落在能写的地方 别把源码放在只读目录

最关键的是 Qt 源码这一条。很多人装 Qt 时只勾了预编译库，没勾 Sources，然后在 qtbase 目录里翻半天找不到 mysql 文件夹。回去用维护工具补装 Sources 就行，不用重装整个 Qt。

驱动工程的目录长得这样：

text
<Qt 源码根>/qtbase/src/plugins/sqldrivers/
    ├── sqldrivers.pro          总工程，会带上所有子目录
    ├── sqlite/
    │     └── sqlite.pro
    ├── mysql/
    │     ├── mysql.pro         <-- 我们编的是这个
    │     └── main.cpp
    ├── psql/
    │     └── psql.pro
    └── odbc/
        └── odbc.pro

mysql.pro 是个 qmake 工程，默认什么路径都不指。头文件路径和库路径靠命令行上的 INCLUDEPATH 和 LIBS 传进去，这就是为什么后面那行 qmake 那么长。

八、Windows 下用 MSVC 编译 #

下面这套流程来自一份实打实的工程记录，环境是 VS2010（MSVC 2010）+ Qt 5.2 源码 + 32 位 MySQL 压缩包。版本号是当年的，流程本身搬到今天照样成立，把路径和版本号换成你自己的即可。

8.1 开发环境与前置准备 #

  • 开发工具：Visual Studio 2010 + Qt 5.2（MSVC 2010 的 32 位 / 64 位离线安装包）
  • Qt Visual Studio Add-in 插件（用于在 VS 里管理 Qt 项目）
  • Qt 源码：安装 Qt 时必须勾选 Sources（源码） 组件，我们要用到其中的数据库驱动插件源码
  • MySQL 开发包：
    1. 去 MySQL 官网下载 Windows 版的 MySQL Community Server 压缩包（示例是 32 位的 mysql-5.6.15-win32）
    2. 解压后放到指定目录（示例是 D:\mysql-5.6.15-win32），我们要的是它的 include 头文件与 lib 库文件

关于位数，说一句重的：下载哪一版不看你的操作系统，看你的 Qt 是几位。系统是 64 位，Qt 装的 32 位套件，你就得下 32 位的 MySQL 包。这一条错了，编得出来也跑不起来。

8.2 编译配置步骤 #

第一步：用 Qt 命令行生成 Makefile。

  1. 从开始菜单进入：开始菜单 → 所有程序 → Qt5.2.0 → MSVC 2010 → 打开 Qt 5.2.0 for Desktop (MSVC 2010) 终端。

    这个终端已经把该套件的 qmake 和编译器路径设好了。用系统的 cmd 自己敲 qmake，容易敲到另一个 Qt 上去。

  2. 切到 Qt 源码里的 MySQL 驱动源码目录（路径按你的实际安装位置改）：

    text
    cd D:\Software\Qt\Qt5.2.0\5.2.0\Src\qtbase\src\plugins\sqldrivers\mysql

  3. 执行 qmake，把 MySQL 头文件与库文件的物理路径指进去：

    text
    qmake "INCLUDEPATH+=D:\mysql-5.6.15-win32\include" "LIBS+=D:\mysql-5.6.15-win32\lib\libmysql.lib" mysql.pro

    执行成功后，这个目录下会生成编译用的 Makefile。这一步没生成 Makefile，先别急着往下走，看它吐了什么。

这两条命令里有三个点要注意。

INCLUDEPATH 指的是 include 目录，里面该有 mysql.h。注意有的 MySQL 压缩包多套一层，实际头文件在 include\mysql\ 下，那就得指到那一层，否则编译时报找不到头文件。

LIBS 指的是 libmysql.lib，是导入库，不是运行库。lib 目录里那个 libmysql.dll 是运行时才用的，编译期只需要 .lib。两个都要，但用处不同。

mysql.pro 必须写在最后。它是这次 qmake 的输入工程。

第二步：用 VS 命令提示进行编译。

  1. 从开始菜单进入：开始菜单 → 所有程序 → Microsoft Visual Studio 2010 → Visual Studio Tools → 打开 Visual Studio 命令提示 (2010)。

    为什么要换到 VS 的命令行？因为要用 nmake，而 nmake、cl.exe、link.exe 这些工具的环境变量只有这个终端里才有。用普通的 cmd 敲 nmake，得到的是「不是内部或外部命令」。

  2. 在这个命令行里进入上一步的同一个目录。跨盘符要单独敲一次盘符：

    text
    D:
cd D:\Software\Qt\Qt5.2.0\5.2.0\Src\qtbase\src\plugins\sqldrivers\mysql

  3. 执行编译：

    text
    nmake

    编译成功后，当前目录里会生成对应的 QMYSQL 插件文件：qsqlmysql.dll（Release 版）和 qsqlmysqld.dll（Debug 版）。

nmake 结束后先在目录里看一眼产物。两个 .dll 是目标，中间那堆 .obj、.cpp、.moc 不用管。只出一个 .dll 也正常，取决于 mysql.pro 里怎么配的 CONFIG。

如果 nmake 报的是链接错误、提示找不到 libmysql.lib 里的符号，回头查第一步的 LIBS 路径是不是写错了；如果是 LNK1112 之类的机器类型冲突，那就是位数错了——Qt 的 qmake 是 32 位，你给的 .lib 是 64 位。

九、Linux 下编译的步骤 #

Linux 上没有 VS 命令行这一层，g++ 和 make 本来就在 PATH 里。流程短一截，前提一样。

第一步：装 MySQL 客户端开发包。

bash
# Debian / Ubuntu
sudo apt install libmysqlclient-dev

# RHEL / CentOS / Fedora
sudo dnf install mysql-devel

装完确认头文件在位。位置视发行版与安装方式而定，别硬记路径：

bash
mysql_config --include
mysql_config --libs

mysql_config 是随开发包一起装的，它输出的就是该机器上正确的头文件与库参数。有它就别猜路径。

第二步：进源码目录，跑 qmake。

bash
cd <Qt 源码根>/qtbase/src/plugins/sqldrivers/mysql
qmake "INCLUDEPATH+=<头文件目录>" "LIBS+=-L<库目录> -lmysqlclient" mysql.pro
make

INCLUDEPATH 与 LIBS 的具体值用上一步 mysql_config 的输出填。-lmysqlclient 这个库名在各发行版上一致，路径不一致。

用 mysql_config 的结果直接拼进 qmake，少写几个字：

bash
qmake "INCLUDEPATH+=$(mysql_config --include | sed 's/^-I//')" \
      "LIBS+=$(mysql_config --libs)" mysql.pro
make

第三步：找产物。

bash
find . -name "libqsqlmysql.so*"

一般在构建目录下的 plugins/sqldrivers/ 里。有些配置下 make install 会把它装进 Qt 前缀的 plugins/sqldrivers/，有些不会，取决于当初编 Qt 时的前缀与安装设置。不确定就手动拷，参照下一章。

Linux 上还有一条容易忽略：你用的 qmake 必须是编这套 Qt 的那个 qmake。系统里同时装了两三套 Qt 是常态，用错了 qmake，编出来的 .so 跟宿主 Qt 的 ABI 对不上，加载时报版本或符号错误。先跑 qmake -v 看一眼路径，比事后查日志省力。

十、PostgreSQL 与其他驱动 #

MySQL 走通了，别的驱动就是换个名字的事。sqldrivers 目录下每个子目录一个驱动，套路完全一样：装开发包 → 进目录 → qmake 带路径 → make/nmake。

PostgreSQL 驱动 QPSQL：

bash
# Debian / Ubuntu
sudo apt install libpq-dev
# RHEL 系
sudo dnf install postgresql-devel

cd <Qt 源码根>/qtbase/src/plugins/sqldrivers/psql
qmake "INCLUDEPATH+=<libpq 头文件目录>" "LIBS+=-L<libpq 库目录> -lpq" psql.pro
make

产物是 libqsqlpsql.so 或 qsqlpsql.dll。它对 libpq 的版本有要求，版本太老会缺符号，装开发包时装最新那个就行。

其余驱动，按需取用：

驱动名 源码子目录 依赖的客户端库 使用门槛
QPSQL psql/ libpq 低，装 libpq-dev 即可
QODBC odbc/ 系统 ODBC 驱动管理器（unixODBC / Windows 自带） 中，要在系统里配好 DSN
QDB2 db2/ IBM DB2 CLI 驱动 高，库要单独找
QIBASE ibase/ Firebird 客户端库 高
QOCI oci/ Oracle 客户端（Instant Client） 高，库与头文件都得配

QODBC 值得单独说一句。它是 Windows 上绕开原生驱动的通用办法：只要系统里装了某个数据库的 ODBC 驱动，QODBC 就能连，不用为每种数据库编一个 Qt 插件。代价是多一层转发，参数与类型映射隔着一层，调试起来不直观。临时接一个冷门数据库，用它比编插件快；长期跑的核心业务，还是原生驱动稳。

一个判断思路：数据库有官方 C 客户端库、并且这个库在发行版仓库里有 -dev 包，这个驱动就好编；库要手动下、要注册、要 license 文件的，就麻烦。 MySQL 和 PostgreSQL 属于前者。

十一、驱动的部署 #

编出来了不代表能用。这一步是全文最容易翻车的地方，也是最容易被跳过的地方。

11.1 Windows：两个位置，两份文件 #

要拷的文件分两类，去处不一样。

第一类：Qt 驱动插件本身。 把编译生成的 qsqlmysql.dll 与 qsqlmysqld.dll 两个插件库文件，拷到 Qt 编译器套件的插件目录：

text
<Qt 安装目录>\<编译器套件>\plugins\sqldrivers\

示例路径（视你的安装位置而定）：

text
D:\Software\Qt\Qt5.2.0\5.2.0\msvc2010_opengl\plugins\sqldrivers\

msvc2010_opengl 这一段是你的套件名，装的是 msvc2019_64 就换成它。放错了套件目录，等于没放——Qt 只在自己那个套件下找插件。

第二类：MySQL 运行时依赖库。 Qt 驱动插件底层是基于 MySQL 提供的客户端链接库构建的，缺了它插件加载不起来。把 MySQL 安装目录下 lib 文件夹里的 libmysql.dll 拷到 Qt 套件的 bin 目录：

text
<Qt 安装目录>\<编译器套件>\bin\

Debug 测试的话，把 libmysqld.dll 也一起带上。

还有一个位置必须处理：发布程序包时，libmysql.dll 要放在与你的 .exe 同级的根目录下，程序才能正常链接数据库。开发机上靠 Qt 的 bin 目录，发布机上没有那个目录，只能靠 exe 同级。

两张表对照着看：

文件 开发期放哪 发布期放哪 缺了会怎样
qsqlmysql.dll / qsqlmysqld.dll <套件>\plugins\sqldrivers\ sqldrivers\（挨着 exe） driver not loaded
libmysql.dll <套件>\bin\ exe 同级目录 插件加载失败，仍是 driver not loaded
libmysqld.dll <套件>\bin\（Debug 测试） Debug 包的 exe 同级 Debug 版加载失败

发布时的顺序别弄反：先把驱动 .dll 放进 Qt 套件的 sqldrivers 目录，再跑 windeployqt。 反过来的话，windeployqt 扫的是 Qt 安装目录里的插件清单，你后放进去的那几个它不会认，发布包里的 sqldrivers 就是空的。

windeployqt 也不管 libmysql.dll，那是第三方库，得手动拷。这条可以记成一句：Qt 的交给工具，第三方的自己拿。

11.2 Linux：.so 放插件目录，客户端库靠搜索路径 #

驱动插件放这里：

text
<Qt 安装前缀>/plugins/sqldrivers/libqsqlmysql.so

Qt 自编自装的场景，前缀是你 ./configure -prefix 时给的值，路径视安装位置而定。

libmysqlclient.so 的处理跟 Windows 不一样。Linux 有动态库搜索路径，三种办法挑一种：

bash
# 办法一：装系统包，让动态链接器自己找（推荐）
sudo apt install libmysqlclient21

# 办法二：临时指定搜索路径
export LD_LIBRARY_PATH=/path/to/mysql/lib:$LD_LIBRARY_PATH

# 办法三：编进 rpath，发布时不依赖环境变量
qmake "QMAKE_RPATHDIR+=<库目录>" ...

办法一最省心，客户端库交给包管理器维护，升级不用管。办法三适合打包发给别人，代价是路径写死在二进制里，目标机器上位置得一样。

拷完用 ldd 验一下依赖有没有断：

bash
ldd <Qt 前缀>/plugins/sqldrivers/libqsqlmysql.so | grep -i mysql

输出里看到 libmysqlclient.so.x => not found，就是路径没配好。看到正经路径，说明链接关系通了。

11.3 不在 Qt 安装目录里放，行不行 #

行。程序启动后指定插件路径：

cpp
#include <QCoreApplication>
int main(int argc, char *argv[])
{
    QCoreApplication app(argc, argv);
    QCoreApplication::addLibraryPath("D:/MyApp/plugins");
    // 之后 addDatabase("QMYSQL") 就会到 D:/MyApp/plugins/sqldrivers/ 里找
    ...
}

或者更省事，在 exe 旁边放一个 qt.conf：

text
[Paths]
Plugins = plugins

有了它，Qt 的插件根目录就指向 exe 旁边的 plugins，你的 plugins/sqldrivers/qsqlmysql.dll 立刻生效。绿色版、免安装版常这么干，用户机器上不装 Qt 也能跑。

十二、连接测试与排错 #

驱动放好了，写一段最小的连接代码验证。别在业务代码里试，单独建个控制台工程。

cpp
#include <QCoreApplication>
#include <QSqlDatabase>
#include <QSqlError>
#include <QSqlQuery>
#include <QDebug>

int main(int argc, char *argv[])
{
    QCoreApplication app(argc, argv);

    qDebug() << "drivers:" << QSqlDatabase::drivers();

    QSqlDatabase db = QSqlDatabase::addDatabase("QMYSQL");
    db.setHostName("127.0.0.1");
    db.setPort(3306);
    db.setDatabaseName("testdb");
    db.setUserName("root");
    db.setPassword("your-password");
    db.setConnectOptions("MYSQL_OPT_CONNECT_TIMEOUT=5");

    if (!db.open()) {
        qDebug() << "open failed:" << db.lastError().text();
        qDebug() << "native code:" << db.lastError().nativeErrorCode();
        return 1;
    }

    qDebug() << "connected, driver:" << db.driverName();

    QSqlQuery q(db);
    if (q.exec("SELECT VERSION()")) {
        while (q.next()) {
            qDebug() << "server version:" << q.value(0).toString();
        }
    }
    db.close();
    return 0;
}

setConnectOptions 那一行不是必写，但强烈建议加上。默认连接超时在连不上的时候能让你等到失去耐心，设个 5 秒，报错来得快。

db.lastError().text() 与 nativeErrorCode() 要分开看。前者是 Qt 包了一层的话，后者是 MySQL 客户端库返回的原始错误码，查 MySQL 文档按后者查。

常见报错，按出现频率排：

现象 真实原因 处理
QSqlDatabase: QMYSQL driver not loaded sqldrivers 里没有驱动文件，或文件加载失败 拷贝 qsqlmysql.dll；开 QT_DEBUG_PLUGINS=1 看拒载原因
同一行报错，但目录里明明有 .dll 缺 libmysql.dll，依赖解析失败 把 libmysql.dll 拷到 Qt 的 bin 或 exe 同级
程序启动就闪退，事件查看器报 0xc000007b 32 位与 64 位混用 统一 Qt、插件、libmysql.dll 的位数
Access denied for user 'root'@'localhost' 账号密码错，或该账号无此库权限 先用命令行客户端登一次，确认凭据本身是对的
Unknown database 'testdb' 库名写错，或库还没建 CREATE DATABASE testdb;
Can't connect to MySQL server on '127.0.0.1' 服务没起、端口不对、防火墙挡了 确认服务在跑；换 localhost 与 127.0.0.1 各试一次
Linux 下 libmysqlclient.so.x => not found 动态库搜索路径里没有它 装系统包，或设 LD_LIBRARY_PATH
连上了但中文乱码 连接字符集不是 utf8mb4 建库建表统一用 utf8mb4，连接上执行 SET NAMES utf8mb4

排错的顺序建议固定下来，别乱撞：

text
1. QSqlDatabase::drivers() 里有没有 QMYSQL
      没有 -> 回第十一章查部署，别看连接参数
2. 有 -> 连接参数对不对（主机、端口、库名、账号）
3. 参数对 -> 看 lastError().nativeErrorCode() 的具体码
4. 还是不通 -> 用命令行客户端 mysql -h ... 试同一组参数
      命令行也不通 -> 问题在数据库侧，不在 Qt
      命令行通而 Qt 不通 -> 问题在驱动侧

第 4 步是分水岭。命令行客户端能连、Qt 连不上，你不用再怀疑网络和账号，直接回驱动与依赖库上找。

十三、易错点速查 #

最后把这一路会踩的坑列成表，编之前扫一遍，能省几小时。

易错点 症状 正确做法
把驱动当库，以为 QT += sql 就够 driver not loaded QT += sql 只链 QtSql，驱动是独立插件文件
装 Qt 时没勾 Sources 找不到 mysql.pro 用维护工具补装 Sources 组件
用系统 cmd 里的 qmake 编出的 .dll 加载失败 用 Qt 对应套件的专用命令行终端
nmake 报「不是内部或外部命令」 编译第一步就断 在 VS 的「命令提示」里跑，环境变量才在
位数混用 0xc000007b，或加载失败 Qt、插件、MySQL 客户端库三者位数统一
只拷了 qsqlmysql.dll，忘了 libmysql.dll 目录里有文件，仍报 not loaded 两个都拷，位置不同
拷到别人的套件目录 一点效果没有 确认套件名，如 msvc2019_64
Debug 版找不到驱动 Release 能跑，Debug 不能 补 qsqlmysqld.dll 与 libmysqld.dll
跨盘符只用 cd 目录没切过去，编的是原目录 先敲盘符 D:，再 cd
INCLUDEPATH 少一层 mysql 报找不到 mysql.h 指到头文件真正所在的那一层
发布时先 windeployqt 后放驱动 发布包 sqldrivers 是空的 先放驱动，再跑部署工具
忘了发布 libmysql.dll 到 exe 同级 开发机正常，用户机器报错 发布包里带上，放 exe 同级
Linux 用错 qmake 加载时报符号或版本错误 qmake -v 确认路径是目标 Qt
只在本机试，不测干净环境 上线才发现 找台没装 Qt 的机器跑一遍

整篇的骨架就一句话：驱动是插件，Qt 只负责找，不负责带。 找得到就用，找不到就报错，找到但依赖不全也报错。所以每一次「连不上」，都先把 sqldrivers 目录翻开看一眼，再回头看代码。
