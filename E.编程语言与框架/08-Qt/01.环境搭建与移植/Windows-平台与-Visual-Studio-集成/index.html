这篇只讲一件事：在 Windows 上用 Qt 写桌面程序，工具链怎么挑、Visual Studio 怎么接、装完的 exe 怎么发出去。

讲这些：MSVC 与 MinGW 两条线的差别与选择、装 Qt 的 MSVC 版之前要准备什么、Qt VS Tools 插件装了到底管什么、.pro 与 .vcxproj 怎么互相转换、调试器怎么指、Visual Assist X 的 Qt 补全怎么配、windeployqt 怎么用、发布包里该有哪几个文件。

不讲这些：Linux 与 macOS 上的移植、交叉编译、qmake 与 CMake 的语法教学、QWidget 与 QML 的控件写法。这些内容归同目录的其他篇和后续章节。

同目录另有两篇。Qt for Android 那篇走 NDK、Gradle、Android SDK 那条线；编辑器与安装提速那篇讲 Qt Creator 的配置和下载加速。Windows 桌面这条线，本篇讲完。

一、Windows 上的两套工具链 #

Qt 官方给 Windows 出的预编译包，从来不是一个包打天下，而是按编译器分成两条线。你下载页面上看到的那些名字，就是两条线的目录名：

  • MSVC 线：msvc2015_64、msvc2017、msvc2019_64、msvc2022_64 之类
  • MinGW 线：mingw73_32、mingw81_64、mingw1120_64 之类

目录名里那个 msvc20xx 或 mingw81，不是随便起的标签，它标的是「这套库文件是用哪个编译器、按哪个 ABI 编出来的」。名字换个字，二进制就对不上。

一套 Qt 包里面装的是这些东西：

内容 位置 说明
头文件 include/QtCore、include/QtWidgets 等 每个模块一个目录
导入库 lib/*.lib 或 lib/*.a 链接期用，本身不含实现
动态库 bin/Qt5Core.dll、bin/Qt6Widgets.dll 运行期用
构建工具 bin/qmake.exe、bin/moc.exe、bin/uic.exe、bin/rcc.exe 生成工程与生成代码
插件 plugins/platforms/qwindows.dll 等 运行期按需加载
工具 bin/windeployqt.exe 部署用

编译器本身不在这套包里。MSVC 版要靠你装 Visual Studio 拿 cl.exe，MinGW 版要么用安装器勾选的工具链，要么自己装一份，再在 Qt Creator 的 Kit 里把路径指过去。

两条线的对照：

维度 MSVC 版 Qt MinGW 版 Qt
编译器 cl.exe，随 Visual Studio 装 g++.exe，随 Qt 安装器或单独装
导入库格式 COFF 归档的 .lib ar 归档的 .a
库文件名 Qt5Core.lib libQt5Core.a
C++ 运行时 msvcp140.dll、vcruntime140.dll、concrt140.dll libstdc++-6.dll、libgcc_s_seh-1.dll、libwinpthread-1.dll
构建工具 nmake 或 MSBuild mingw32-make
调试器 cdb.exe 或 VS 内置调试器 gdb.exe
异常模型 SEH SjLj 或 SEH，看工具链编法
ABI 归属 跟 MSVC 工具集版本绑定 跟 GCC 版本绑定

这里有个必须记死的事：MSVC 版 Qt 只能用 MSVC 编，MinGW 版只能用 MinGW 编。 这不是风格偏好，是二进制契约。导入库的归档格式不同，符号修饰规则也不同——MSVC 对 C++ 函数做名字改编（name mangling），GCC 用的是 Itanium ABI 那套规则，两边互相看不懂对方导出的名字。

混用的后果在编译期往往风平浪静，到链接期一次性爆出来，两种典型症状：

text
LINK : fatal error LNK1112: 模块计算机类型“x64”与目标计算机类型“x86”冲突

text
undefined reference to `_imp___ZN7QWidgetC1EP7QWidget6QFlagsINS_6WindowTypeEE'

第一类是位数错配（32 位工程去链 64 位库，或者反过来），第二类是 ABI 错配。两者都别去改代码，先去查 Kit 和工程的位数、编译器族是不是统一。

MinGW 的工具链喜欢把 .a 和 .dll 混着放，容易让人误以为能直接喂给 MSVC 链接器。MSVC 的链接器看到 .a 会当普通输入文件处理，然后吐一堆找不到的符号。反过来，MinGW 的 -lQt5Core 去找 libQt5Core.a，你给它一个 Qt5Core.lib，它连文件名都对不上。

一个进程里只能有一套 C++ 运行时。别想着「主程序用 MSVC 编，动态加载一个 MinGW 编的插件」，两套 CRT 各自管理堆，跨 DLL 传 std::string 或 new/delete 配对，崩溃是迟早的事。要么全 MSVC，要么全 MinGW。

二、MSVC 与 MinGW 怎么选 #

不用在这件事上纠结太久，看几个硬条件就能定。

判断依据 选 MSVC 选 MinGW
主力 IDE Visual Studio Qt Creator
第三方库 只给了 .lib + .dll，或者是 COM 组件 有源码，或者给了 MinGW 版预编译包
硬件厂商 SDK 一般只出 MSVC 版 少见
团队已有工程 已有 .sln、.vcxproj 干干净净的新项目
发布包体积 要额外带 CRT 或装 vcredist 静态链 libstdc++、libgcc 后能压到只剩几个 Qt DLL
调试体验 VS 调试器与 PDB 符号很省心 gdb 能用，看 Qt 容器时体验差一些
编译速度 中等，MSBuild 增量做得不错 小项目快，大项目单线程跑得慢
许可 商用要留意 VS 授权条款 GCC 运行时带例外条款，分发上更省事

实操里最常见的两种局面：

一种是上位机、工业设备、机器视觉这类项目。厂商给的相机 SDK、运动控制卡 SDK、加密狗驱动，清一色 MSVC 版，有的还只给 32 位。这种局面没得选，直接上 MSVC，位数跟着 SDK 走，SDK 只有 x86 就整条线都用 x86。

另一种是工具类小软件、内部脚本界面、给开源项目写个 GUI。这种局面用 MinGW 更轻：不用装几个 GB 的 VS，Qt Creator 装上就能跑，静态链接之后发一个 exe 出去，用户那边不用装任何运行时。

两套都装也不冲突。Qt Creator 里建两个 Kit，一个指 MSVC 的 qmake.exe，一个指 MinGW 的，切换 Kit 就切换工具链。只在切换之后重新构建一遍，别在同一个 build 目录里混着编——旧的 .obj 和新的 .o 会一起被塞进链接命令，症状就是前面说的 LNK1112。

三、装 Qt 的 MSVC 版需要什么 #

装 Qt 的 MSVC 版之前，先确认一件事：你的 Visual Studio 版本和 Qt 包目录名对不对得上。

对应关系大致是这样，版本号往后延续，规则不变：

Qt 版本线 可用的 MSVC 包 注意事项
Qt 5.6 以前 msvc2010、msvc2013 工具集老，v100/v120 与新版不兼容
Qt 5.9 ~ 5.12 msvc2015、msvc2017 v140/v141 与后续版本二进制兼容
Qt 5.12 ~ 5.15 msvc2017、msvc2019 这两个包用 VS2022 也能编
Qt 6.x msvc2019_64、msvc2022_64 需要 C++17，32 位支持已经砍掉

微软对 v140（VS2015）、v141（VS2017）、v142（VS2019）、v143（VS2022）承诺二进制兼容。所以 Qt 的 msvc2019 包，拿 VS2022 打开照样能编能链。但 v120（VS2013）及更早的不在这个承诺范围内，跨代混用会出问题。

位数要从目录名读。msvc2019_64 是 64 位，msvc2019 不带后缀是 32 位。这一条坑过不少人——装完发现 Qt5Core.lib 链不上，查半天才发现工程是 x64、Qt 包是 32 位。

Visual Studio 那边要勾的组件：

  • 使用 C++ 的桌面开发 工作负载（必勾，它带 MSVC 工具集和 Windows SDK）
  • 具体版本的 MSVC 生成工具，比如 MSVC v143 - VS 2022 C++ x64/x86 生成工具
  • Windows 10 SDK 或 Windows 11 SDK
  • 要跑 cdb 调试的话，装 Windows 调试工具（Debugging Tools for Windows），它在 Windows SDK 安装项里

Qt 安装器那边，勾对应编译器的包。装 Qt 5 的话，msvc2019_64 就是一个可勾选项；装 Qt 6 的话，安装器会把 MSVC 2019 64-bit 单独列出来。

安装路径的规矩，编码问题之外还有一条：路径不要带中文、空格、特殊字符。

text
错误：D:\Program Files\Qt\Qt5.2.0
推荐：D:\Software\Qt\Qt5.2.0

带空格的时候，make 生成的编译脚本没有给路径加引号，命令行被空格截断，报出来的错和真实原因八竿子打不着——莫名奇妙的「找不到文件」，或者编译到一半中断，或者链接器把路径的后半截当成一个输入文件名。

为了少踩这类坑，安装时就选一个短路径。C:\Qt 或者 D:\Qt 就挺好，别往 Program Files 里塞。

四、Visual Studio 集成：Qt VS Tools #

先把这一节的核心说清：Qt VS Tools 的作用，是让 Visual Studio 认识 Qt 的工程文件和资源文件，并且在编译前自动调 moc、uic、rcc。没有它，VS 就只是个纯 C++ 编辑器。

这句话值得拆开讲。Qt 有三个「非标准 C++」的环节，标准 C++ 编译器完全不管：

  • 头文件里写了 Q_OBJECT 宏的类，需要一个 moc_xxx.cpp 参与编译，否则链接时 vtable for MyWidget 和 staticMetaObject 全是未定义符号
  • .ui 文件是 XML，需要一个 ui_xxx.h 才能在代码里用 ui->setupUi(this)
  • .qrc 是资源清单，需要一个 qrc_xxx.cpp 把图片、翻译文件编进二进制

moc、uic、rcc 都是 Qt 自带的命令行工具。手工跑一遍也能编过，但每次改完头文件都要记得重跑，漏一次就是半小时的排错。插件的价值就在这儿：它把这几个工具挂进 MSBuild 的编译依赖里，改了就重跑，不用你操心。

插件的形态在历史上换过一次：

年代 形态 安装方式
Qt 5 早期（VS2010 那阵） Visual Studio Add-in，独立安装包 单独下载 exe 装上
VS2015 之后 Qt Visual Studio Tools，VSIX 扩展 VS 里「扩展和更新」搜，或从市场下 .vsix

老项目里还能看到 Visual Studio Add-in 1.2.2 for Qt5 这种包。新版 VS 上装不了它，直接用 Qt VS Tools。

装完之后，VS 顶部菜单栏会多出一个 Qt5（新版叫 Qt VS Tools）菜单。接下来把 Qt 的安装位置登记进去：

  1. 点 Qt5 → Qt Options（新版是 Qt VS Tools → Qt Versions）
  2. 在弹窗里点 Add
  3. 填一个版本识别名，比如 5.2.0。这个名字随你起，只是个标签
  4. Path 一栏指到 Qt 套件的安装目录，例如：
text
D:\Software\Qt\Qt5.2.0\5.2.0\msvc2010_opengl
  1. 保存，把它设为 Default Qt Version

路径要指到带编译器后缀的那一层，不是指到 Qt5.2.0 这个父目录。判断方法很简单：这一层目录下应该同时有 bin、include、lib、mkspecs 四个子目录。

插件登记完 Qt 版本之后，它到底替我干了哪些活：

能力 具体行为
登记 Qt 版本 记住路径，从 bin/qmake.exe 反查头文件、库、mkspecs
关联文件类型 .pro、.pri、.ui、.qrc、.ts 在解决方案里显示成 Qt 的图标，双击走对应编辑器
自动 moc 扫描源文件里的 Q_OBJECT，生成 moc_*.cpp 并加入编译
自动 uic .ui 变更时生成 ui_*.h 到中间目录
自动 rcc .qrc 变更时生成 qrc_*.cpp，把资源编进二进制
工程转换 .pro 与 .vcxproj 双向转换
调试可视化 注册 Qt 的 natvis 规则，调试窗口里 QString、QList 能看到内容而不是一坨指针

最后一条容易被忽略。没有 natvis，你在 VS 的监视窗口里看一个 QString，只能看到 d 指针和一个 sizeof 相关的整数，想确认它到底是什么内容得手写表达式。装上插件之后，监视窗口直接显示字符串本身。

五、在 VS 里创建 Qt 项目 #

两条路，看你手上有的是 .pro 还是空目录。

路径一：从已有的 .pro 导入 #

Qt Creator 里写好的工程，不用重做。菜单点 Qt5 → Open Qt Project File (.pro)...，选中那个 .pro，插件会生成 .sln 和 .vcxproj，顺带把 HEADERS、SOURCES、FORMS、RESOURCES 四类文件按类型塞进对应的筛选器。

这一步底下干的事，是调一遍 qmake -tp vc。所以 .pro 里那些平台判断（win32 { }、contains(QT_MAJOR_VERSION, 6)）在转换时就求值了，转出来的 .vcxproj 是求值后的结果。你要是后来改了 .pro 里的条件分支，得重新转一次，不是刷新一下就完事。

路径二：在 VS 里新建 #

文件 → 新建 → 项目 → 左侧展开 Qt5 Projects（新版是 Qt）→ 选 Qt Application → 填项目名 → 下一步。

向导会问你要勾哪些 Qt 模块。按需勾：

模块 勾不勾 用到什么场景
QtCore 必勾 信号槽、容器、文件、时间、线程，全在这
QtGui 桌面项目必勾 字体、绘图、事件，QtWidgets 依赖它
QtWidgets 传统桌面界面必勾 QWidget、QMainWindow、布局
QtNetwork 要发 HTTP 请求就勾 QTcpSocket、QNetworkAccessManager
QtSql 要连数据库就勾 QSqlDatabase
QtXml / QtXmlPatterns 要解析 XML 就勾 DOM、SAX、XPath
QtConcurrent 要并行处理就勾 QtConcurrent::run、QFuture
QtMultimedia 要放音视频就勾 QMediaPlayer

勾完确定，工程里会生成一套标准的 Qt 结构：

text
项目名/
├── 项目名.vcxproj
├── 项目名.vcxproj.filters
├── 项目名.sln
├── main.cpp
├── 项目名.h
├── 项目名.cpp
└── 项目名.ui

main.cpp 里是那个标准骨架：QApplication app(argc, argv);、实例化主窗口、w.show();、return app.exec();。.ui 里已经有一个空的主窗口，.h 里已经声明了 Q_OBJECT 和 Ui::项目名Class 成员。

新建项目这一步别忘了选对 Qt 版本：向导第一屏或属性页里有个 Qt Version 下拉框，默认值来自 Qt Options 里设的 Default Qt Version。项目多了之后，很容易出现「这个工程用 5.12、那个工程用 5.15」的情况，改版本要在这个下拉框里改，改环境变量没用。

一个易被误解的地方 #

在 VS 里改 .ui 文件，是要走 Qt Designer 的。插件装好之后，双击 .ui 会启动 designer.exe，拖控件、连信号槽都在那边做。保存退出，回到 VS 编译，uic 才会重新生成 ui_xxx.h。

有人双击 .ui 打开的是 XML 源码视图，那是因为文件关联没建上。检查 Qt Options 里的路径是否指对，.ui 的编辑器注册是靠这一层路径推出来的。

六、.pro 与 .vcxproj 的关系 #

这两个文件是同一个工程的两份描述，格式完全不搭界。

维度 .pro .vcxproj
归属 qmake MSBuild
格式 键值加作用域的自定义语法 XML
构建工具 qmake + nmake/mingw32-make MSBuild
平台判断 win32 { }、unix { }、msvc { } 条件属性 Condition="'$(Configuration)'=='Debug'"
Qt 模块声明 QT += core widgets network 一堆 <QtMocInclude>、附加依赖项
生成者 手写，或 qmake 反向导出 手写，或插件从 .pro 转换
谁认它 Qt Creator、命令行 qmake Visual Studio、msbuild 命令行

概念上的映射大致是这样：

.pro 里的变量 在 .vcxproj 里变成什么
HEADERS += <ClInclude>，同时挂 moc 的自定义生成步骤
SOURCES += <ClCompile>
FORMS += <QtUic> 项，编译期生成 ui_*.h
RESOURCES += <QtRcc> 项，编译期生成 qrc_*.cpp
QT += widgets 附加包含目录加 include/QtWidgets，附加依赖项加 Qt5Widgets.lib
INCLUDEPATH += 附加包含目录
LIBS += -L... -lxxx 附加库目录加附加依赖项
DEFINES += XXX 预处理器定义
CONFIG += debug Configuration 选 Debug

转换是单向的默认行为，但不是死路。插件提供反向导出：

  • Qt5 → Create Basic .pro File...：从当前 .vcxproj 反推一个 .pro 出来
  • 反向导出出来的是「基础版」，只含文件清单和模块依赖，手工加的编译选项、自定义生成步骤不会完整带回去

维护上只有一条建议：一个工程只留一个事实来源。

一个团队里，如果 Qt Creator 那边有人手改 .pro，VS 这边有人手改 .vcxproj，两边各自加文件、各自改宏定义，几次提交之后就分叉了。转一次丢一次，最后没人知道哪份是对的。选一边当主，另一边当生成物，并且把生成物一起提交进仓库——不然新同事克隆下来直接打不开。

纯 qmake 的工程，.pro 当主；纯 VS 的工程，.vcxproj 当主。要两边都能开，就在 .pro 里写清楚，用转换工具单向生成，生成完立刻提交。

七、调试器配置 #

编译能过、链接能过，接下来是单步。调试器这块，两条工具链走的完全是两套东西。

工具链 调试器 可执行文件 符号格式
MSVC VS 内置调试器 无（VS 自己实现） PDB
MSVC cdb.exe Windows SDK 自带 PDB
MinGW gdb.exe 随工具链 DWARF

在 Visual Studio 里按 F5，用的是 VS 自己的调试引擎，不需要额外配置。这条路最省事——只要 .pdb 和 .exe 在同一个目录，断点、调用栈、变量全都有。

在 Qt Creator 里调试 MSVC 编的程序，就得靠 cdb。配置步骤：

  1. 装 Windows SDK 时勾上 Debugging Tools for Windows
  2. 记下 cdb.exe 的路径，典型位置：
text
C:\Program Files (x86)\Windows Kits\10\Debuggers\x64\cdb.exe
C:\Program Files (x86)\Windows Kits\10\Debuggers\x86\cdb.exe
  1. Qt Creator 里 工具 → 选项 → Kits → 选中那个 MSVC Kit → Debugger 一栏点 Edit，指到 cdb.exe
  2. 同一个 Kit 的 Compiler 一栏要指到 cl.exe，两条路径都指对，Kit 才不报黄叹号

位数要对齐。64 位程序配 x64\cdb.exe，32 位程序配 x86\cdb.exe。配反了不会报错，只是断点打不上，或者打上了也不停——因为调试器根本没挂到那个进程上。

符号服务器这块，调 Qt 库内部或者系统 DLL 的时候有用。设一个环境变量：

text
_NT_SYMBOL_PATH=srv*C:\Symbols*https://msdl.microsoft.com/download/symbols

这样 cdb 缺符号时会自己下。只调自己的代码就不用设，设了反而拖慢启动——每次第一次碰到新模块都要去网上拉一遍。

MinGW 那边简单：Qt Creator 会自动找到同工具链里的 gdb.exe，一般不用手配。要确认的话看 工具 → 选项 → Kits 里 Debugger 那一栏是不是自动填好了。

混合调试的一个死角 #

崩溃位置在 Qt 库里，而 Qt 库是 Release 版没符号，栈上全是地址。这种情况先别急着翻源码，用 dumpbin 确认依赖关系：

bash
dumpbin /dependents MyApp.exe

输出会列出这个 exe 直接依赖的所有 DLL。如果里面出现了你没预期的 Qt DLL（比如本该只依赖 Qt5Core，结果冒出 Qt5Quick），说明链接阶段混进了别的库，或者有第三方依赖拖着走。位数也能这么查：

bash
dumpbin /headers MyApp.exe | findstr machine

machine (x64) 和 machine (x86) 一眼就分出来。

八、Visual Assist X 这类辅助插件 #

Visual Assist X（圈里叫「西红柿插件」）是 Whole Tomato 出的 Visual Studio 插件，给 VS 补强 C++ 的代码理解和导航。它不改你的工程，只改编辑器里那层体验。

它能干什么 #

语言覆盖面比较宽，C/C++、C#、ASP、VB、Java、HTML 都认。对 C++ 这块，它自己建一套符号表，扫描关键字、系统函数、成员变量，然后做几件事：

  • 输入时按上下文补全，少敲键盘，也少打错单词
  • 大小写打错了自动纠
  • 语法隐患高亮，比如 = 写成 ==
  • 鼠标悬停看定义，不用跳走

四个用得最多的能力：

  1. 写代码快：补全按类型上下文给候选，不是按字母顺序罗列
  2. 读代码快：类、函数、宏着色更细，一眼能分出类型名和变量名
  3. 重构：重命名类、函数、变量时跨文件一起改；提取方法、改函数签名，会把调用点一起处理
  4. 跳转：Shift + Alt + O 按文件名跳文件，Shift + Alt + S 按符号名跳符号，大工程里这两个键能省下大量翻目录的时间

官网是 Whole Tomato 的站点，版本更新去那儿看。

为什么 Qt 的补全一开始是哑的 #

导入 Qt 工程之后，你会发现 QString、QWidget 这些类名没有补全，ui-> 后面点不出来东西。

原因是 Visual Assist X 的符号表只扫描解决方案里的文件和你告诉它的包含目录。Qt 的头文件在解决方案目录之外，它不知道去哪儿找。VS 自己的 IntelliSense 能认，是因为项目属性里有附加包含目录；Visual Assist X 用自己的一套配置。

手工把 Qt 头文件目录加进去 #

  1. VS 顶部菜单 VAssistX → Visual Assist X Options...
  2. 左侧选 Projects → C/C++ Directories
  3. 右侧 Platform 下拉框选 Custom（自定义平台）
  4. 下方 Show Directories for 下拉列表选 Stable include files（静态包含文件）
  5. 点新建路径图标，逐个加 Qt 模块的头文件目录。典型的桌面项目要加三个：
text
C:\Qt\Qt5.1.1\5.1.1\msvc2012\include\QtCore
C:\Qt\Qt5.1.1\5.1.1\msvc2012\include\QtGui
C:\Qt\Qt5.1.1\5.1.1\msvc2012\include\QtWidgets
  1. 点 OK 关掉对话框

加完它会后台重扫这些目录，建索引。等几秒，再敲 QS 就有候选了。

加目录时注意两件事：

一是路径要指到模块级目录，include\QtCore，不是 include。指到 include 的话，QtCore/qstring.h 这种写法能找到，但 Qt 源码里大量是 #include <qstring.h> 直接引的，指到模块级才对。

二是 Qt 换了版本或换了编译器包，这几个路径要跟着改。msvc2012 变成 msvc2019_64 之后，旧路径还在列表里，指向一个已经删掉的目录，Visual Assist X 不报错，只是补全悄悄失效——查起来要费点劲。

什么情况下不装 #

装是可选。VS 自带的 IntelliSense 在 C++17 之后进步不小，日常补全够用。Visual Assist X 的价值主要在大工程、老代码、需要频繁跨文件跳转的场景。

Qt Creator 那边也有一套自己的补全，配好 Kit 就能用，不需要这个插件。

九、Windows 下的部署：windeployqt #

开发机上跑得好好的程序，拷到没装 Qt 的电脑上双击就报错。这一节解决这个。

它解决的是什么问题 #

windeployqt.exe 在 Qt 的 bin 目录下。它干的事：读你给的 exe 或 dll 的 PE 导入表，找出这个程序直接依赖哪些 Qt DLL，再根据 Qt 内部的插件元数据，把这些 DLL 依赖的插件也一并带上，然后全部拷到你指定的目录。

一条命令：

bash
windeployqt.exe --release --compiler-runtime D:\build\MyApp\release\MyApp.exe

跑完，exe 同级目录里就多了一堆 Qt 的 DLL 和几个插件子目录。把这个目录整个打包，才算能发出去。

常用参数 #

参数 作用
--release / --debug 指定按哪种配置推断依赖，默认会自己嗅探
--compiler-runtime 把编译器运行时 DLL 一起拷过来（MSVC 的 msvcp140.dll 等）
--dir <目录> 输出到指定目录，默认是 exe 所在目录
--qmldir <目录> QML 项目必加，扫描 QML 里 import 了哪些模块
--no-translations 不拷 translations 目录
--no-system-d3d-compiler 不拷 D3D 编译器相关 DLL，减小体积
--no-opengl-sw 不拷软件 OpenGL 实现（opengl32sw.dll，个头不小）
--list <文件> 只把依赖清单写到文件里，不实际拷贝，用来核对
--verbose 打印每一步在干什么，排查漏拷时用

--list 这个参数值得单独提一句。发布前先跑一遍：

bash
windeployqt.exe --release --list deps.txt MyApp.exe

看一眼 deps.txt 里有没有你预期之外的东西，比事后在客户机器上猜要省时间。

编译器运行时它管不全 #

windeployqt 管的是 Qt 自己的 DLL 和 Qt 的插件。编译器运行时是另一码事。

MSVC 编出来的程序，依赖微软的 C++ 运行时：

text
msvcp140.dll      C++ 标准库
vcruntime140.dll  C 运行时
concrt140.dll     并发运行时
msvcp140_1.dll    并行算法相关

加 --compiler-runtime 参数，windeployqt 会从 VS 的 redist 目录把这些拷过来。但这条路有前提：装 Qt 和 VS 的机器上得有对应的 redist 目录，而且拷过去的那几个 DLL 要和你的编译工具集版本一致。

MinGW 编出来的程序，依赖 GCC 的运行时：

text
libstdc++-6.dll
libgcc_s_seh-1.dll
libwinpthread-1.dll

这三个 windeployqt 一概不管，得自己从 MinGW 的 bin 目录拷。想彻底躲开这件事，链接时加静态参数：

bash
g++ -static-libgcc -static-libstdc++ -o MyApp.exe ...

这样运行时被编进 exe 里，发布包少三个文件。

「并行配置不正确」是怎么回事 #

双击 exe，Windows 直接弹系统报错：

由于应用程序配置不正确，应用程序未能启动。

或者提示「并行配置不正确」。

这不是 Qt 的问题，是 MSVC 运行时缺失。程序由 MSVC 编译，清单里声明了要某个版本的 CRT，目标机器上找不到，Windows 的 Side-by-Side 机制就直接拒绝启动，连 main 都没进去。

三种处理方式：

方式一：拷 CRT 目录（适合本机调试）

去开发机 VS 的安装路径下，把整个 CRT 子目录拷到 exe 同级。目录里有 Microsoft.VCxx.CRT.manifest 加 msvcrxx.dll、msvcpxx.dll。

text
Debug 版参考：D:\SoftWare\Microsoft Visual Studio 9.0\VC\redist\Debug_NonRedist\x86\Microsoft.VC90.DebugCRT
Release 版参考：D:\SoftWare\Microsoft Visual Studio 9.0\VC\redist\x86\Microsoft.VC90.CRT

Debug 版的 CRT 不能分发，只在自己机器上验证问题用。发布包要是带了 Debug_NonRedist 里的东西，属于违规分发。

方式二：装 Redist 包（生产用这个）

微软官方给每个工具集出 vcredist_x86.exe 和 vcredist_x64.exe。在安装包脚本里静默跑一遍：

text
vcredist_x64.exe /install /quiet /norestart

NSIS 用 ExecWait，Inno Setup 用 [Run] 段。装完再启动主程序，SxS 就能找到运行时。

方式三：静态链接 CRT

工程属性里把 运行库 从 多线程 DLL (/MD) 改成 多线程 (/MT)。这样 CRT 编进 exe，不再依赖外部 DLL，也就不需要 vcredist。

代价是 exe 变大，而且所有依赖的静态库也得用 /MT 编——混着 /MT 和 /MD 编出来的 obj 一起链接，会报 LNK2038: 检测到“RuntimeLibrary”的不匹配项。

部署流程按顺序走 #

text
1. Qt Creator / VS 里切 Release 配置，重新构建
2. 从干净目录重新构建，别用带旧 obj 的 build 目录
3. 拷 exe 到一个空的发布目录
4. 在发布目录里跑 windeployqt --release --compiler-runtime
5. 手工补编译器运行时（MinGW 三个 dll，或确认 vcredist 已覆盖）
6. 在一台没装 Qt、没装 VS 的机器上双击测试
7. 逐个功能过一遍：界面、中文、图片、网络、数据库
8. 打压缩包或做安装包

第 6 步不能省。开发机上永远测不出缺 DLL，因为 PATH 里什么都有。找一台干净虚拟机，或者一个从没装过开发环境的同事的电脑。

十、发布包要带哪些文件 #

windeployqt 跑完不等于发布包齐了。它只保证 Qt 层面的依赖，业务层面的东西还得自己对。

清单 #

文件或目录 必须 说明
MyApp.exe 是 主程序
Qt5Core.dll、Qt5Gui.dll、Qt5Widgets.dll 等 是 用到的模块，windeployqt 自动拷
platforms\qwindows.dll 是 Windows 平台插件，缺了程序起不来
styles\qwindowsvistastyle.dll 视情况 原生风格，缺了界面变丑但不崩
imageformats\*.dll 视情况 要显示 jpg/gif/webp 就得带，Qt 只内置 png
iconengines\qsvgicon.dll 视情况 用 SVG 图标才需要
sqldrivers\qsqlite.dll 等 视情况 用 Qt SQL 才需要
bearer\*.dll 视情况 Qt5 的网络承载插件，用 QNetworkAccessManager 要带
tls\*.dll 视情况 Qt6 的 TLS 后端，要发 HTTPS 请求必须带
translations\*.qm 视情况 中文界面必须带，见下文
QML 模块目录 视情况 QML 项目必须，--qmldir 会处理
msvcp140.dll 等 是（MSVC） 编译器运行时，--compiler-runtime 或 vcredist
libstdc++-6.dll 等 是（MinGW） 编译器运行时，手工拷或静态链接
*.qm 业务翻译 视情况 自己的翻译文件
配置文件、资源目录 视情况 业务自己的东西

平台插件缺失：最经典的一个 #

双击报错：

This application failed to start because it could not find or load the Qt platform plugin "windows"

原因只有一个：platforms\qwindows.dll 没在 exe 同级目录的 platforms 文件夹里。

Qt 5 之后，平台插件是运行时按目录动态加载的。只拷 Qt5Gui.dll 不够，那个 DLL 里没有平台实现，它要去 platforms 目录找 qwindows.dll。少了这个目录，进程在初始化 QApplication 的时候就退出了。

手工补的办法：

text
发布目录\
├── MyApp.exe
├── Qt5Core.dll
├── Qt5Gui.dll
├── Qt5Widgets.dll
└── platforms\
    └── qwindows.dll

qwindows.dll 从 Qt 安装目录的 plugins\platforms\ 下拷，不是从 bin 拷——bin 里没有这个文件。

排查时开一下调试输出，能看到它到底在哪些目录里找插件：

bash
set QT_DEBUG_PLUGINS=1
MyApp.exe

环境变量打开后，控制台会打印每个插件的搜索路径和加载结果。这一招能定位九成的插件问题。

中文全变英文：翻译文件没带 #

开发机上明明汉化好了，装到用户机器上，标准对话框的按钮变成 OK / Cancel，自己的控件也回到英文。

原因是 .qm 翻译文件没跟出去。国际化是运行时加载 .qm 生效的，文件不在，QTranslator::load() 返回 false，Qt 就回退到英文。

两种修法：

方案 A：把 .qm 放在 exe 同级或 translations 目录分发

简单，但散落文件容易在打包时漏掉某一个。用 QTranslator::load() 时路径要写对，相对路径是按工作目录算的，不是按 exe 位置算的。

方案 B：编进资源（推荐）

把 .qm 塞进 .qrc：

xml
<qresource prefix="/translations">
    <file>my_app_zh.qm</file>
    <file>qt_zh_CN.qm</file>
</qresource>

代码里走资源路径加载：

cpp
QTranslator translator;
translator.load(":/translations/my_app_zh.qm");
app.installTranslator(&translator);

这样 .qm 变成二进制里的字节，漏不掉。代价是改翻译要重新编译，不能热替换。

注意 qt_zh_CN.qm 是 Qt 自己那套标准对话框的翻译，在 Qt 安装目录的 translations 下。你要在发布时把它拷进工程目录再加进 .qrc，因为构建时它得在磁盘上存在。

装到 C 盘就不能运行：UAC 提权 #

现象很怪：在开发目录双击好好的，用安装包装到 C:\Program Files\ 之后，双击无响应，或者界面出来了但写配置文件、写数据库全失败。右键「以管理员身份运行」就正常。

原因在 UAC。从 Vista 起，普通权限的进程不能往 Program Files、Windows、HKLM 注册表这些位置写东西。程序里拿 QStandardPaths::writableLocation(QStandardPaths::AppDataLocation) 拼路径就没事，硬编码往 exe 同级写就会失败。

三种处理方式，按推荐顺序：

优先方案：改路径

把配置、日志、数据库全放到 QStandardPaths 给的目录（%APPDATA% 或 %LOCALAPPDATA%），不要往安装目录写。这是 Windows 应用的规范做法，也不需要提权。

方式 A：VS 工程里改清单

  1. 右键工程 → 属性
  2. 展开 链接器 → 清单文件
  3. 把 UAC 执行级别 改成 requireAdministrator

重新构建后，程序启动时会弹 UAC 盾牌提示。用户点确认才继续。

方式 B：qmake 里注入链接参数

Qt Creator 构建、.pro 管理工程的话，在 .pro 里追加：

text
win32-msvc* {
    QMAKE_LFLAGS += /MANIFESTUAC:\"level=\'requireAdministrator\'\"
}

只对 MSVC 生效。MinGW 那边没有 /MANIFESTUAC 这个开关，要靠自定义 .rc 资源文件或单独写一个 .manifest 文件，再在链接时用 -Wl,--manifest 之类的方式挂上去。

提权不是没有代价的：程序以管理员身份跑，拖放文件会失效（UIPI 限制），从资源管理器拖进来的文件路径拿不到。用户日常用的工具类软件，尽量别提权，走前面那个改路径的方案。

十一、常见故障与现象 #

现象 原因 处理
LNK1112: 模块计算机类型冲突 32 位工程链 64 位库，或 MSVC 与 MinGW 混用 统一 Kit、Qt 包、工程三者的位数与编译器族
undefined reference to _imp__ZN... MinGW 链接器吃到 MSVC 的 .lib 换 MinGW 版 Qt；不要拿 .lib 喂 g++
LNK2019: 无法解析的外部符号 "public: virtual struct QMetaObject..." 头文件有 Q_OBJECT 但没跑 moc 装 Qt VS Tools 并让头文件在项目里；或手跑 moc
LNK2001: 无法解析的外部符号 "public: virtual void * __cdecl MyWidget::qt_metacast" 同上，moc 产物没参与编译 检查 moc_*.cpp 是否在生成目录并被加入编译
启动报「找不到 Qt5Core.dll」 DLL 不在 exe 同级，也不在 PATH 跑 windeployqt；或开发期把 Qt 的 bin 加进 PATH
启动报「could not find or load the Qt platform plugin "windows"」 缺 platforms\qwindows.dll 建 platforms 目录，从 plugins\platforms 拷进去
启动报「并行配置不正确」 缺 MSVC 运行时 装 vcredist，或拷 CRT DLL，或改 /MT
界面中文全变英文 .qm 没带或路径错 分发 .qm 或编进 .qrc
双击无响应，提权后正常 UAC 拒写 Program Files 改写到 QStandardPaths 目录，或改清单提权
一张 jpg 图片显示不出来 缺 imageformats\qjpeg.dll 拷 imageformats 目录
HTTPS 请求全失败 Qt6 缺 TLS 后端 拷 tls 目录，或装 OpenSSL
提示数据库驱动未加载 缺 sqldrivers\qsqlite.dll 拷 sqldrivers 目录
VS 里 .ui 双击是 XML .ui 关联没建上 检查 Qt Options 里的路径
断点打不上、打上了不停 调试器位数与程序位不符 64 位程序配 x64\cdb.exe
编译报「找不到文件」，路径里带空格 路径含空格导致命令行截断 把 Qt 和工程挪到无空格路径
LNK2038: RuntimeLibrary 不匹配 /MT 与 /MD 混用 全工程统一运行库选项
补全里没有 QString Visual Assist X 没配 Qt 头目录 在 C/C++ Directories 里加模块级 include 目录
发布包在开发机好、客户机崩 漏了某个插件目录 QT_DEBUG_PLUGINS=1 看搜索路径

十二、易错点速查 #

易错点 后果 正确做法
MSVC 版 Qt 配 MinGW 编译器 链接期报一堆未定义符号 版本与编译器严格配对
装 Qt 时没看目录名后缀 32 位工程链 64 位库，报 LNK1112 msvc2019 是 32 位，msvc2019_64 才是 64 位
Qt 装在 Program Files 下 构建脚本路径截断，报错莫名 装到 C:\Qt 或 D:\Qt
路径带中文 编译工具解析失败 全英文路径
不装 Qt VS Tools 就在 VS 里开 Qt 工程 .ui 不编译，moc 不跑 先装插件，再建工程
Qt Options 里路径指到父目录 插件找不到 mkspecs 指到 msvc20xx_64 那一层
同时改 .pro 和 .vcxproj 两份描述分叉，互相覆盖 只留一个事实来源
.pro 改了平台条件后没重转 .vcxproj 里还是旧的分支求值结果 重新执行一次转换
只拷 Qt DLL 不建 platforms 目录 程序在 QApplication 构造时退出 必带 platforms\qwindows.dll
以为 windeployqt 会带上 CRT 客户机报并行配置不正确 加 --compiler-runtime，或装 vcredist
MinGW 发布包漏 libstdc++-6.dll 启动时缺 DLL 弹窗 手工拷，或 -static-libstdc++
Debug 版 CRT 打进发布包 违规分发，且依赖调试库 Release 配 release 版 CRT
在带旧 obj 的目录里重构建 两套工具链的中间文件混进链接 切 Kit 后清干净重建
提权清单加在所有程序上 拖放失效、UAC 弹窗惹用户烦 先改写到 QStandardPaths 目录
翻译文件放 translations 但路径按工作目录算 换启动方式就加载不到 用 :/ 资源路径，或按 exe 位置拼绝对路径
只在开发机测发布包 PATH 里什么都有，测不出缺 DLL 找干净机器或虚拟机测
调试器位数配反 断点静默失效，浪费半天 程序位数与 cdb 位数对齐
便携版 Qt 包不用安装器 缺 qmake、缺 mkspecs，Kit 起不来 用官方安装器，或补全整个套件

Windows 上这条线的坑，大半都能归结到一句话：版本、位数、编译器族，三个东西必须一致。 Qt 包、编译器、调试器、第三方库，四项对齐了，剩下的都是路径和文件清单的问题。
