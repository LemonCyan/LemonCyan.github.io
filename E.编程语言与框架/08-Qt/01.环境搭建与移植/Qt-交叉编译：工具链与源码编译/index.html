这篇讲怎么把 Qt 交叉编译到 ARM 板上：工具链怎么备、sysroot 从哪来、mkspec 怎么写、configure 参数怎么给、WebEngine 卡在哪一步。

不讲板子的 U-Boot 与内核裁剪，不讲编完的库怎么丢到板子上跑起来，也不讲一个完整项目从零到上线的全过程。这三块看同子目录的《板级移植实战》《部署与运行》《完整项目》。

也不讲 Qt 在 x86 桌面上自己编一遍的流程，那是《Linux 上编译 Qt 源码》。这里默认你已经跑通过 configure 与 make，只关心「目标换成 ARM」之后多出来的那一层。

素材横跨 Qt 4.7 到 Qt 5.9.6，板子从 s3c2410、AM335x 到 i.MX6、RK3288。Qt 4 的 qws 与 Qt 5 的 QPA 是两套东西，文中分开说。

一、交叉编译 Qt 的整体流程 #

一句话：交叉编译 Qt 的核心，是让 qmake 拿着你的 ARM 编译器去编库，同时用一个宿主机的编译器去编 qmake、moc、rcc 这些要在构建机上跑的工具。

这句是全文的主线。搞不清这条，后面每一个报错都只能靠猜。

Qt 的构建自带一层自举结构：它先编出 qmake 这个可执行文件，再用 qmake 生成 Makefile，最后用 Makefile 编库和工具。如果整条链子都用一个编译器，编出来的 qmake 就是 ARM 二进制，在你的 x86 机器上根本跑不起来，下一步就断了。所以必须把两类东西拆开：

类别 用谁的编译器 产物跑在哪 典型代表
构建工具 宿主机 g++ 你的 x86 构建机 qmake、moc、rcc、uic
目标库与插件 交叉编译器 开发板的 ARM libQt5Core.so、plugins/platforms/
目标侧辅助工具 交叉编译器 开发板 qmlscene 之类要上板跑的程序

configure 里那两个看着像双胞胎的参数就是干这个的：-platform 指宿主机，-xplatform 指目标。填错一个，就变成「用 ARM 编译器去编 x86 的 qmake」，报出来的是 File format not recognized 这种看着莫名其妙的话。

整条流水线拆开是八步：

阶段 干什么 产物 出错先看哪
备工具链 解压交叉编译器，配好 PATH arm-linux-gnueabihf-g++ 能调用 command -v、-v 打出的 target
备 sysroot 拿到板子的 /lib、/usr/lib、/usr/include 一棵与板子同构的目录树 里面有没有 libdbus-1.so
写 mkspec 复制模板，填编译器前缀与架构参数 qtbase/mkspecs/<名字>/qmake.conf qmake -query 的输出
configure 让脚本做一轮探测，生成 Makefile config.summary、config.log summary 里显示 No 的那几行
编 qtbase 先只编基础库 libQt5Core.so 等 第一次 relocation 报错
编全量 make -j 全部模块 3rdparty 漏编
install make install extprefix 下的 bin/、lib/、plugins/ 单线程重跑一遍
验证 file、readelf、上板跑 一个跑得起来的 hello 非法指令、找不到 .so

构建机上的目录要分清三个，混了就装错地方：

text
源码目录     qt-everywhere-src-5.9.6/           解压出来的原始代码，一般不动
构建目录     build-qt/                          进这里跑 configure，产物落在这
安装目录     /usr/local/qtarm590/               -extprefix 指定的地方
             └─ 注意：-prefix 指的是「板子上的路径」，不是构建机路径

先编 qtbase，编通了再编全量。 素材里那位写得很直白：除非你用的是八核十六线程的机器能 make -j16，否则先单独把 qtbase 啃下来，省得每次都在第 40 分钟才发现工具链配错了。qtbase 是整个工程的地基，它编不过，后面全是空谈。

二、交叉工具链的准备 #

交叉编译器就是一堆带同一个前缀的可执行文件，前缀那段字符串本身编码了目标信息。

文件 干什么 少了会怎样
<前缀>-gcc / <前缀>-g++ 编 C / C++ configure 第一步就退出
<前缀>-ar 打包静态库 静态库产不出来
<前缀>-ld 链接 链接期各种 undefined
<前缀>-nm 读符号表 Qt 的符号检查探测失败
<前缀>-objcopy / <前缀>-strip 转换目标文件 / 去符号 部分模块编不过，产物偏大
<前缀>-readelf 读 ELF 头与架构属性 你没法验证产物对不对
<前缀>-gdb / gdbserver 调试 Qt Creator 里点调试没反应

前缀的命名规则是 架构-厂商-系统-ABI，拿 arm-linux-gnueabihf- 拆：

text
arm            目标架构
linux          目标操作系统
gnueabihf      GNU EABI，hard-float，硬浮点

最后那个 hf 是生死攸关的两个字母。gnueabi 是软浮点 ABI，gnueabihf 是硬浮点 ABI，两者编出来的目标文件不能混链。素材里出现过的三种前缀，各对应一类板子：

前缀 浮点 出处素材 备注
arm-arago-linux-gnueabi- 软 TI arago SDK 老 AM335x SDK 常见，配 -march=armv7-a
arm-linux-gnueabihf- 硬 Linaro 5.3.1 素材里 RK3288、Firefly 用的这套
arm-poky-linux-gnueabi- 硬 Yocto / i.MX6 名字里没 hf，但 cortexa9hf 说明是硬浮点
arm-none-linux-gnueabi- 软 老 s3c2410 工具链 gcc 4.3.2，编 Qt 4 那个年代的东西

注意 poky 那套：编译器目录叫 cortexa9hf-vfp-neon-poky-linux-gnueabi/，前缀却写成 arm-poky-linux-gnueabi-。别看到目录里没 hf 就以为它是软浮点，看目录名里的 cortexa9hf 与 neon。

编译器版本有一条硬线：新版本 Qt 用了 C++11 语法，工具链至少 gcc 4.8.0。再往上，WebEngine 又要求 gcc 5.0 起步，这条在第九章展开。

装完先验一遍，别急着 configure：

bash
  # 工具链能不能跑，target 对不对
  arm-linux-gnueabihf-gcc -v

  # 看一眼它默认往哪个 sysroot 找头文件
  arm-linux-gnueabihf-gcc -print-sysroot

  # 编个空文件，确认产物是 ARM
  echo 'int main(void){return 0;}' > /tmp/t.c
arm-linux-gnueabihf-gcc /tmp/t.c -o /tmp/t
file /tmp/t

file 打出 ELF 32-bit LSB executable, ARM, EABI5 才算过关。打出 x86-64 就说明你调的是宿主机 gcc，PATH 里那个目录根本没生效。

sysroot 从哪来 #

sysroot 是目标板的根文件系统镜像，configure 拿它找头文件和依赖库。三条路：

做法 怎么搞 好坏
NFS 挂载板子的根文件系统 内核开 NFS，板子把 / 挂到构建机的 /home/yy/mntnfs 最准，板子上有什么就能链什么，改完立刻可见
把板子上的三个目录拷回来 cp -a 板子的 /lib、/usr/lib、/usr/include 能用，但库没装对时白拷一遍，返工成本高
用 Yocto 生成的 sysroot 构建镜像时顺手产出 tmp/sysroots/<机器名> 干净、完整，i.MX6 那套就是这么来的

素材里的态度很明确：优先 NFS。因为 configure 的结果直接取决于 sysroot 里有什么库，拷一份静态的目录，等发现少了东西又要重来一轮。

Yocto 的 sysroot 有个专属坑：它里面往往残留着上一版 Qt 的动态库。i.MX6 的 sysroot 里 usr/lib/libQt* 和 usr/lib/qt5 是旧版本留下的，不清掉就会去链旧库，编出来的东西行为诡异。动手前先清：

bash
cd /opt/zhaozhongxiang/hwzt_yc_3.10.53/build-x11/tmp/sysroots/imx6qsabresd
sudo rm -rf ./usr/lib/libQt*
sudo rm -rf ./usr/lib/qt5

sysroot 太精简也会出事。缺的库只能自己交叉编一份塞进去，这一步没有捷径。

构建机上要装的包 #

母系统是 64 位 Ubuntu，要编 32 位 ARM 程序，得先让本机能编 32 位代码：

bash
sudo apt-get install gcc-multilib g++-multilib
sudo apt-get install gcc-4.8-multilib g++-4.8-multilib
sudo apt-get install libc6-dev-i386
sudo apt-get install gperf bison
sudo apt-get install ninja-build

gperf 与 ninja-build 是 WebEngine 的构建依赖，不编 WebEngine 也建议装上，省得后面又回头补。-4.8-multilib 那几个跟着你的 gcc 版本走，装的是对应版本的 32 位支持。

板子侧要装的库（如果板子能联网，或者你能往它根文件系统里塞包）：

bash
sudo apt-get install build-essential
sudo apt-get install libfontconfig1 libfontconfig1-dev
sudo apt-get install libxrender-dev libxrender1 libxkbcommon-dev libxkbcommon0
sudo apt-get install libxkbcommon-x11-0 libxkbcommon-x11-dev
sudo apt-get install libglib2.0-dev libglib2.0-0
sudo apt-get install libfreetype6 libfreetype6-dev

这份清单是按 xcb 与字体那一路配的。缺什么，回头翻 config.log 一条条补——它会把探测失败的库名原样写进去。

环境变量先铺好 #

i.MX6 那套在 /etc/bash.bashrc 末尾加这一段，把宿主机的 native 编译器和交叉编译器分开：

bash
  # Native Compiler
export AR_host="ar"
export CC_host="gcc"
export CXX_host="g++"
export LINK_host="g++"

  # freescale imx.6 cross compiler，指向 cortexa9hf 那套工具链
export ARCH=arm
export PATH=/opt/zhaozhongxiang/hwzt_yc_3.10.53/build-x11/tmp/sysroots/x86_64-linux/usr/bin/cortexa9hf-vfp-neon-poky-linux-gnueabi/:$PATH

那四个 _host 变量是给 WebEngine 的构建系统看的——它要编一批宿主工具，必须明确告诉它用 native 编译器，不能拿交叉编译器顶上。PATH 改完要重开一个终端才生效。

三、mkspec：qmake 怎么知道目标平台 #

mkspec 就是一份配置文件，放在 qtbase/mkspecs/ 下。它回答 qmake 三个问题：

text
用什么编译器       QMAKE_CC / QMAKE_CXX / QMAKE_LINK
编译参数是什么     QMAKE_CFLAGS / QMAKE_CXXFLAGS / QMAKE_LDFLAGS
这是哪个平台       QT_QPA_DEFAULT_PLATFORM 以及一堆 CONFIG 开关

工具链装对了、mkspec 没配，configure 就还是用宿主机的 gcc。 这句是本篇最该记住的一句。很多人装完工具链就直奔 configure，看到最后产出的 .so 是 x86 的，回头怀疑编译器坏了，其实只是 mkspec 没指过去。

目录长这样：

text
qtbase/mkspecs/
├── common/                        各平台共用的片段
│   ├── linux.conf                 目标系统的通用规则
│   ├── gcc-base-unix.conf         gcc 在类 Unix 上的通用规则
│   └── g++-unix.conf              g++ 的补充规则
├── linux-g++/                    宿主机 x86 Linux，-platform 默认用它
├── linux-arm-gnueabi-g++/        ARM 模板，写 mkspec 的起点
├── linux-arm-gnueabihf-g++/      硬浮点 ARM 模板
├── devices/                      具体开发板的设备描述
│   ├── linux-imx6-g++/
│   ├── linux-arm-am335x-g++/
│   └── ...
└── qws/                          Qt 4 时代的东西，Qt 5 里还能看到残影
    ├── linux-arm-gnueabi-g++/
    └── ...

qmake.conf 里干的事，全是在给变量赋值。常用字段：

字段 作用 填错的表现
MAKEFILE_GENERATOR 生成哪种 Makefile，固定 UNIX 拼出来的 Makefile 语法全错
CONFIG 开关集合，加上 incremental 支持增量 每次改一行全量重编
QMAKE_INCREMENTAL_STYLE 增量风格，sublib 同上
QT_QPA_DEFAULT_PLATFORM 默认 QPA 插件，如 linuxfb、eglfs 程序起来后找不到平台插件
QMAKE_CC C 编译器，可写绝对路径 还在用宿主机 gcc
QMAKE_CXX C++ 编译器 同上
QMAKE_LINK / QMAKE_LINK_SHLIB 链接可执行文件 / 共享库 链接阶段报跨架构
QMAKE_AR 打包工具，注意后面带 cqs 静态库产不出来
QMAKE_OBJCOPY / QMAKE_NM / QMAKE_STRIP 目标文件工具三件套，nm 带 -P 符号探测失败、strip 报格式错
QMAKE_CFLAGS_RELEASE / QMAKE_CXXFLAGS_RELEASE 架构与优化参数 编出来跑不了，或性能极差
QMAKE_INCDIR / QMAKE_LIBDIR 额外的头文件、库目录 找不到 tslib 之类的第三方库
load(qt_config) 载入 Qt 自己的配置收尾 少了它整个 mkspec 不生效

文件末尾那行 load(qt_config) 不能漏。它把上面这些变量喂进 Qt 的构建体系，并补上剩下没写的默认值。

三个平台参数各管什么 #

参数 指谁 典型值 写错的后果
-platform 构建机（宿主机） linux-g++ 宿主工具编不出来
-xplatform 目标板 linux-arm-gnueabihf-g++ 用宿主编译器编目标库，产物是 x86
-device 具体开发板 linux-imx6-g++ 板级参数（内存、GPU、QPA）不对

-xplatform 是最容易搞错的那个。素材里那位把 5.7.1 的 -xplatform 写成了 linux-g++，结果 Qt 认为这次就是在编本机，于是用交叉编译器去链接 x86 的 .o，报出来：

text
project.o: file not recognized: File format not recognized

这句话的翻译是：链接器看到的目标文件架构和它自己不是一路的。看到它，先去检查 -xplatform。

-platform 与 -xplatform 的关系可以这么理解：

text
qmake 的编译链
  ├─ 宿主侧（-platform）      用 linux-g++  →  产出 bin/qmake、bin/moc
  └─ 目标侧（-xplatform）     用 linux-arm-* →  产出 lib/libQt5*.so

想知道 qmake 最后认了什么，装完直接问它：

bash
./bin/qmake -query

输出里这几行是关键：

text
QT_HOST_PREFIX
QT_INSTALL_PREFIX
QT_ARCH                    arm
QMAKE_XSPEC                linux-arm-gnueabihf-g++
QMAKE_SPEC                 linux-g++

QT_ARCH 是 arm、QMAKE_XSPEC 是你的目标 mkspec，这两个对上了，说明 mkspec 生效了。QT_ARCH 还是 x86_64，回去查 -xplatform 的拼写，以及 mkspec 目录名和参数是不是一字不差。

qmake 找 mkspec 的顺序也值得记一笔：先看 -xplatform 给的相对路径，再在 mkspecs/ 下按名字找。所以你把模板复制成 linux-arm 放在 mkspecs/ 根下，-xplatform linux-arm 就能用；放在 mkspecs/devices/ 下，参数就要写成 -device linux-arm。

Qt 4 时代这套写法长得不一样，-xplatform 要带 qws/ 前缀：

bash
-xplatform qws/linux-arm-gnueabi-g++

Qt 5 把 qws 换成了 QPA，模板也换到了 mkspecs/ 根下与 devices/ 下。老教程里带 qws/ 的写法，拿到 Qt 5 上会直接找不到文件。

四、写一个自己的 mkspec #

模板不要从零写。linux-arm-gnueabi-g++ 那个目录已经把所有该有的 include() 摆好了，复制一份改名，只动你要动的那几行。

bash
cd qtbase/mkspecs

  # 复制一份软浮点 ARM 模板，改名成自己的
cp -a linux-arm-gnueabi-g++ linux-arm

  # 进去改 qmake.conf
vi linux-arm/qmake.conf

一个能用的 qmake.conf，按 TSLib 变量取路径的写法：

ini
  #
  # qmake configuration for building with arm-linux-gnueabi-g++
  #

MAKEFILE_GENERATOR      = UNIX
CONFIG                 += incremental
QMAKE_INCREMENTAL_STYLE = sublib

  # 默认 QPA 平台，跑起来先找 linuxfb 插件
QT_QPA_DEFAULT_PLATFORM = linuxfb

  # 架构与优化，按板子的 CPU 改
QMAKE_CFLAGS_RELEASE   += -O2 -march=armv7-a
QMAKE_CXXFLAGS_RELEASE += -O2 -march=armv7-a

  # 第三方库路径，$(TSLIB) 从环境变量来
QMAKE_INCDIR += $(TSLIB)/include
QMAKE_LIBDIR += $(TSLIB)/lib

include(../common/linux.conf)
include(../common/gcc-base-unix.conf)
include(../common/g++-unix.conf)

  # modifications to g++.conf，换成你自己的前缀
QMAKE_CC                = arm-arago-linux-gnueabi-gcc
QMAKE_CXX               = arm-arago-linux-gnueabi-g++
QMAKE_LINK              = arm-arago-linux-gnueabi-g++
QMAKE_LINK_SHLIB        = arm-arago-linux-gnueabi-g++

  # modifications to linux.conf
QMAKE_AR                = arm-arago-linux-gnueabi-ar cqs
QMAKE_OBJCOPY           = arm-arago-linux-gnueabi-objcopy
QMAKE_NM                = arm-arago-linux-gnueabi-nm -P
QMAKE_STRIP             = arm-arago-linux-gnueabi-strip

load(qt_config)

逐块说一遍，哪些要改、哪些别动：

块 改不改 说明
MAKEFILE_GENERATOR 三行 不改 UNIX + incremental，增量编译靠它们
QT_QPA_DEFAULT_PLATFORM 要改 板子跑 linuxfb 就写 linuxfb，跑 GPU 就写 eglfs
QMAKE_*FLAGS_RELEASE 要改 -march=armv7-a 跟你板子的 CPU 对齐
QMAKE_INCDIR / QMAKE_LIBDIR 要改 第三方库（tslib）在哪
三个 include() 不改 顺序也别动，前面依赖后面
QMAKE_CC 一行 必改 不改成你的前缀，编出来就是 x86
QMAKE_LINK / LINK_SHLIB 必改 同上
QMAKE_AR 四行 必改 注意 cqs 与 -P 这两个尾巴不能削
load(qt_config) 不改 删了整份文件白写

$(TSLIB) 这种写法要求你在 shell 里先 export TSLIB=/home/linux/tslib。不想多一个环境变量，就直接写绝对路径。

再看一份带完整搜索路径的，头文件与库都在 sysroot 里：

ini
  # 头文件：sysroot 的两个 include 都要给
QMAKE_CXXFLAGS += -I/home/yy/mntnfs/usr/include
QMAKE_CXXFLAGS += -I/home/yy/mntnfs/usr/include/arm-linux-gnueabihf
QMAKE_CFLAGS   += -I/home/yy/mntnfs/usr/include
QMAKE_CFLAGS   += -I/home/yy/mntnfs/usr/include/arm-linux-gnueabihf

  # 库搜索路径。lib/arm-linux-gnueabihf 必须排在 usr/lib/arm-linux-gnueabihf 前面
QMAKE_LFLAGS += -L/home/yy/mntnfs/lib/arm-linux-gnueabihf
QMAKE_LFLAGS += -Wl,-rpath-link,/home/yy/mntnfs/lib/arm-linux-gnueabihf
QMAKE_LFLAGS += -L/home/yy/mntnfs/usr/lib/arm-linux-gnueabihf
QMAKE_LFLAGS += -Wl,-rpath-link,/home/yy/mntnfs/usr/lib/arm-linux-gnueabihf
QMAKE_LFLAGS += -L/home/yy/mntnfs/lib
QMAKE_LFLAGS += -Wl,-rpath-link,/home/yy/mntnfs/lib
QMAKE_LFLAGS += -L/home/yy/mntnfs/usr/lib
QMAKE_LFLAGS += -Wl,-rpath-link,/home/yy/mntnfs/usr/lib

  # 应付检测不到 gstreamer 与 glib 的怪问题
QMAKE_LIBS += -lpthread -lgobject-2.0 -lglib-2.0 -lpcre

  # 硬浮点 + NEON，四个参数缺一不可
QMAKE_CFLAGS   += -O2 -march=armv7-a -mfpu=neon -mfloat-abi=hard
QMAKE_CXXFLAGS += -O2 -march=armv7-a -mfpu=neon -mfloat-abi=hard

编译器那几行也可以写成绝对路径，比如 QMAKE_CC = /home/yy/linaro-gnueabihf/bin/arm-linux-gnueabihf-gcc，QMAKE_AR 后面照样带 cqs。好处是绕开 PATH 没生效这类破事，坏处是换台机器全要改。

五条铁律 #

第一条：库绝不能塞进编译器命令。 有人的 qmake.conf 写成这样：

ini
QMAKE_CC  = arm-linux-gnueabihf-gcc -lts
QMAKE_CXX = arm-linux-gnueabihf-g++ -lts

编 Qt 库本身时看着没事，但 configure 阶段要先编 qmake 这个宿主工具。那一刻交叉工具链的链接目录里还没有 tslib 的搜索路径，于是：

text
/usr/local/sbin/arm-linux-gnueabihf/bin/../lib/gcc/arm-linux-gnueabihf/6.2.1/../../../../arm-linux-gnueabihf/bin/ld: cannot find -lts
collect2: error: ld returned 1 exit status
Makefile:149: recipe for target '../bin/qmake' failed

库的包含只有两个合法位置：configure 阶段的 -I / -L，或者 qmake.conf 里的 QMAKE_LIBS / QMAKE_LFLAGS。写进 QMAKE_CC 就是埋雷。

第二条：include 路径要排在最前面。 板子上如果已经装过一套 Qt 5（发行版 apt 装的），/usr/include 里那套头文件会先被找到，编到一半就对不上版本。把 sysroot 的 include 顶到最前，让编译器先看见板子的头文件。

第三条：-L 的顺序决定链接谁。 lib/arm-linux-gnueabihf 放在 usr/lib/arm-linux-gnueabihf 前面，原因是板子上 /usr/lib/arm-linux-gnueabihf 里很多 .so 是指向 /lib/arm-linux-gnueabihf 的符号链接。这些链接在板子上管用，在构建机上如果是拷回来的目录就断了。

第四条：-mfloat-abi 要跟工具链一致。 工具链是 gnueabihf，编译参数就得有 -mfloat-abi=hard；写成 soft 或漏掉，链接期一堆 uses VFP register arguments, output does not 之类的废话。

第五条：改完 mkspec 必须重跑 configure。 Makefile 里的编译器路径是 configure 时写死进去的，光改 qmake.conf 不重新配置，编出来还是老样子。

devices 下的板级 mkspec #

mkspecs/devices/ 里那份不是给 -xplatform 用的，是给 -device 用的。它比通用模板多一层板级描述，i.MX6 那份里长这样：

ini
  # 编译器前缀由 -device-option CROSS_COMPILE= 传进来
QMAKE_CROSS_COMPILE = $$CROSS_COMPILE
QMAKE_CC            = $${CROSS_COMPILE}gcc
QMAKE_CXX           = $${CROSS_COMPILE}g++
QMAKE_LINK          = $${CROSS_COMPILE}g++

所以 -device-option 的作用就是往这份文件里灌变量：

bash
-device linux-imx6-g++
-device-option CROSS_COMPILE=/opt/.../cortexa9hf-vfp-neon-poky-linux-gnueabi/arm-poky-linux-gnueabi-

换成自己的板子，先把 devices/ 下最像的那份复制一份改名，再改里面的 CPU 参数与 QPA 默认值。

写法 找哪份文件 什么时候用
-xplatform linux-arm-xxx-g++ mkspecs/linux-arm-xxx-g++/qmake.conf 自己写的通用 ARM 模板
-device linux-imx6-g++ mkspecs/devices/linux-imx6-g++/qmake.conf 有现成板级模板，还要传 CROSS_COMPILE
-platform linux-g++ mkspecs/linux-g++/qmake.conf 宿主机侧，默认就够
-xplatform linux-g++ 同上 错的，见第三章那个 File format not recognized

五、configure 的关键参数 #

configure 干两件事：探测你的环境，然后生成 Makefile。所有参数最终都落在两个产物里——config.summary 是你该看的，config.log 是出问题该翻的。

参数有六个是必须搞懂的：

参数 指什么 典型写法 写错的表现
-platform 构建机平台 linux-g++ 宿主工具编不出来
-xplatform 目标板平台 linux-arm-gnueabihf-g++ 产物是 x86 的 .so
-sysroot 目标根文件系统 /home/yy/mntnfs 全去宿主机找库，找不到一片
-prefix 板子上的安装路径 /usr/local/Qt-5.9.6 配合 sysroot 会把东西写进板子镜像
-extprefix 构建机上的安装路径 /usr/local/qtarm590 产物混进 sysroot，清理麻烦
-device + -device-option 板级 mkspec 与变量 linux-imx6-g++ + CROSS_COMPILE=... 板级参数与编译器前缀对不上

-prefix / -extprefix / -hostprefix #

这三个最绕，先看官方那三行原文：

text
-prefix ....    部署目录，从目标设备的角度看。（默认 /usr/local/Qt-5.6.0）
-extprefix ..   安装目录，从构建机的角度看。（默认 SYSROOT/PREFIX）
-hostprefix .   构建机上运行的构建工具的安装目录。（默认 EXTPREFIX）

翻译成人话：

参数 谁看这个路径 交叉编译时怎么给
-prefix 板子上的 ld.so 与 qmake -query 给板子上你打算放 Qt 的路径，比如 /usr/local/Qt-5.9.6
-extprefix 你，构建机上的人 给构建机上一个干净目录，编完从这里拷到板子
-hostprefix 构建机上的 qmake、moc 不写就跟着 extprefix

素材里踩过一次：指定了 -sysroot 又用 -prefix /usr/local/qtarm580，结果 make install 往 sysroot 里装，等于直接写进了板子的根文件系统镜像。原话是「不要使用 -prefix，在指定了 sysroot 的情况下，-prefix 会把东西安装到开发板里」。

规则记成一句：有 sysroot 就用 -extprefix，让产物落在构建机上。

别加 -no-gcc-sysroot #

网上有教程说交叉编译要加 -no-gcc-sysroot。素材里那位给了四个字评价：纯属误导，不要加。这个开关会在某些 configure 场景下让编译器忽略自己的 sysroot 设定，本来能找到的头文件反而找不到了。除非你有明确的理由，比如工具链自带的 sysroot 与板子那份冲突，才去动它。

目录细调 #

把 -prefix 定好之后，各路目录还能单独改。这一族在交叉编译里用得不多，知道有这么回事就够：

参数 默认位置 改它的场景
-bindir PREFIX/bin 板子上要按 FHS 分开放
-libdir PREFIX/lib 板子是 32 位、库要进 /usr/lib
-headerdir PREFIX/include 要给板子上的编译留头文件
-plugindir ARCHDATADIR/plugins 插件目录受只读文件系统限制
-libexecdir ARCHDATADIR/libexec 无
-archdatadir PREFIX 架构相关数据要单独分区
-datadir PREFIX 架构无关数据
-importdir / -qmldir ARCHDATADIR/imports、/qml QML 工程路径要改
-docdir / -examplesdir / -testsdir PREFIX 下 不想装文档与示例
-translationdir / -sysconfdir DATADIR/translations、PREFIX/etc/xdg 多语言、配置文件位置
-hostbindir / -hostlibdir / -hostdatadir HOSTPREFIX 下 宿主工具要单独隔离

除 -sysconfdir，其余目录都该落在 -prefix 或 -hostprefix 底下，别写到外面去，否则卸载时找不全。

构建类型与通用开关 #

参数 含义 交叉编译怎么选
-release 关掉调试信息编 首选，产物小、跑得快
-debug 带调试信息编 要上板调 Qt 内部才用；-debug-and-release 是 Mac 专属，Linux 上不给
-force-debug-info release 也生成符号表 要单独留符号文件时用
-developer-build 带开发者选项与自测 改 Qt 源码的人用
-shared 动态库 首选，板子上多个程序共用一份
-static 静态库 板子文件系统极简、只有一个程序时用
-opensource + -confirm-license 开源版，自动确认许可 必给，否则 configure 会停下来等人回答；-commercial 是有 license 才用的商业版
-optimized-qmake qmake 本身也带优化编 加上，configure 快一截
-no-pch / -pch 预编译头开关 交叉编译建议 -no-pch，出问题好定位
-c++std c++11 C++ 标准 Qt 5.9 之后默认就够，别乱降
-silent / -verbose 少打日志 / 详细日志 第一次配置给 -v，探测过程全在里面
-continue 出错继续往下走 想一次看完所有缺什么时用
-no-rpath / -rpath 是否写入运行时库路径 交叉编译建议 -no-rpath，运行时用 LD_LIBRARY_PATH 控

第三方库：-qt-* 还是 -system-* #

这一族选项是移植阶段最容易吵起来的地方。两篇素材的结论看着相反：一篇说一律用 -qt-zlib，因为「系统的是 X86 架构的」；另一篇用 -system-zlib、-system-libjpeg、-system-libpng。

两边都对，区别在于 sysroot 有没有配对：

场景 -system-* 会链到 该选
没给 -sysroot，或 sysroot 是空的 构建机上的 x86 库 -qt-*，用 Qt 自带的源码编
给了 -sysroot 且里面是板子的 ARM 库 板子上的 ARM 库 -system-*，省编译时间，ABI 与板子一致
sysroot 里的库版本太老，缺符号 链接期或运行期报错 -qt-* 绕开

判断标准就一条：-system-* 找到的库是哪个架构的。 是 ARM 就放心用，是 x86 就必须换 -qt-*。

库 选项 交叉编译取舍
zlib -qt-zlib / -system-zlib 板子有就用 system，省事
libpng -qt-libpng / -system-libpng / -no-libpng 不需要 PNG 就 -no-libpng
libjpeg -qt-libjpeg / -system-libjpeg / -no-libjpeg 同上，按需
freetype -qt-freetype / -system-freetype / -no-freetype 板子要显示中文就得留一个
harfbuzz -qt-harfbuzz / -system-harfbuzz 文字排版复杂就留，-qt- 更稳
pcre -qt-pcre / -system-pcre 用 -qt-pcre，版本对不上会崩
openssl -no-openssl / -openssl / -openssl-linked 板子没 https 需求就 -no-openssl
xcb 一族 -qt-xcb / -system-xcb 走 linuxfb 就直接 -no-xcb
gif -no-gif / -gif 不要就关掉
icu -no-icu / -icu 板子没 icu 库就 -no-icu
tslib -tslib / -no-tslib 有触摸屏就开，后面还要配环境变量
glib -no-glib / -glib 板子没 glib 就 -no-glib，素材里几篇都是关的
dbus -no-dbus / -dbus 桌面环境才要，嵌入式多数关掉
libproxy -no-libproxy / -libproxy 关掉，别去搭宿主机
cups -no-cups / -cups 板子不打印，关掉
iconv -no-iconv / -iconv 编码转换，用不上就关

素材里那句经验很到位：只要是关乎操作系统的库，看见 system 字眼先停一下。这个「停一下」不是一律拒绝，而是先确认它找到的到底是谁的库。

六、平台插件与设备参数 #

Qt 5 把「怎么把窗口画到屏幕上」抽象成 QPA（Qt Platform Abstraction）。一套 Qt 库编出来可以带好几个平台插件，跑的时候按 QT_QPA_PLATFORM 挑一个。

插件 画到哪 要不要 X11 依赖
linuxfb 直接写 /dev/fb0 不要 内核 framebuffer
eglfs 直接走 EGL + OpenGL ES 不要 GPU 驱动、EGL 库
xcb X11 桌面里开窗口 要 xcb 一族库
vnc 自己起 vncserver 不要 无
minimal / offscreen 什么都不画 / 渲染到内存 不要 无，只用来跑通逻辑

编译期把哪个插件编进去，靠这些开关：

开关 作用
-linuxfb / -no-linuxfb 编不编 linuxfb 插件
-eglfs / -no-eglfs 编不编 eglfs 插件
-xcb / -no-xcb 编不编 xcb 插件
-qpa <名字> 指定默认插件，等价于写进 mkspec 的 QT_QPA_DEFAULT_PLATFORM
-no-opengl / -opengl es2 有没有 OpenGL，eglfs 与 WebEngine 都要它
-egl 开 EGL 支持，走 eglfs 必须给
-no-kms / -kms 内核模式设置，老内核上关掉

-qpa 与 -linuxfb 不是一回事：-linuxfb 决定这个插件编不编，-qpa linuxfb 决定程序默认用哪个。两个都给才对得上。

输入设备相关 #

开关 管什么 嵌入式怎么选
-evdev / -no-evdev 直接读 /dev/input/event* 保留，触摸屏与键盘都要
-libinput / -no-libinput 用 libinput 统一管理输入 板子上没 libinput 就关
-libudev 靠 udev 自动发现输入设备 板子有 udev 就开，没有就关
-xinput2 / -no-xinput2 X11 的多点触摸扩展 走 xcb 才用得上
-tslib / -no-tslib tslib 触摸屏校准 电阻屏必开，电容屏可关
-mtdev / -no-mtdev 多点触摸协议转换 单点屏不需要
-xkb 键盘布局 走 xcb 时给

运行期的环境变量 #

库编完只是半件事，插件与字体路径要环境变量指出来。板子上写 /etc/default/locale（注意这文件里不能用变量引用别的变量）：

bash
QT_QPA_PLATFORM_PLUGIN_PATH=/home/firefly/qt5.8-arm/plugins
LD_LIBRARY_PATH=/home/firefly/gnueabihf/lib:/home/firefly/qt5.8-arm/lib
QT_QPA_PLATFORM=xcb
QT_QPA_FONTDIR=/usr/share/fonts/truetype/droid
QT_QPA_EVDEV_MOUSE_PARAMETERS=Intellimouse:/dev/input/event2
QT_QPA_EVDEV_KEYBOARD_PARAMETERS=Linuxinput:/dev/input/event3
QML_IMPORT_PATH=/home/firefly/qt5.8-arm/plugins/qml
QML2_IMPORT_PATH=/home/firefly/qt5.8-arm/plugins/qml
变量 作用 不设的后果
QT_QPA_PLATFORM 挑平台插件 起不来，报找不到平台插件
QT_QPA_PLATFORM_PLUGIN_PATH 插件目录 同上，尤其 Qt 装在非标准路径时
LD_LIBRARY_PATH 库搜索路径 error while loading shared libraries
QT_QPA_FONTDIR 字体目录 程序能起，一个字都不显示
QT_QPA_EVDEV_MOUSE_PARAMETERS 鼠标/触摸设备节点 点不动
QT_QPA_EVDEV_KEYBOARD_PARAMETERS 键盘设备节点 打不了字
QML_IMPORT_PATH / QML2_IMPORT_PATH QML 模块路径 QML 程序报模块找不到

QT_QPA_PLATFORM 三个取值的脾气，素材里讲得挺细：

值 行为 注意
linuxfb 无视 X11，直接往 framebuffer 上画 得先按 Ctrl+Alt+F1~F6 进纯终端再跑程序；花屏就是因为它在无视桌面画
vnc 自己起一个 vncserver，界面走 VNC 能开 X11 时就没必要用它
xcb 在 X11 桌面里正常开窗 板子上跑 X11 才选

linuxfb 还能带参数指定 framebuffer 与终端：

bash
export QT_QPA_PLATFORM=linuxfb:fb=/dev/fb0:tty=/dev/tty1

tty 那个参数决定画在哪个控制台上。板子上按 Ctrl+Alt+F1 没反应、按 Ctrl+Alt+F7 反而能退出，说明内核没编纯终端驱动，得回去补内核配置。

先把 tslib 编出来 #

电阻屏要靠 tslib 做校准。它不在 apt 里，得自己交叉编：

bash
  # 解压后先跑 autogen.sh 生成 configure
./autogen.sh

  # 报 autoreconf: not found 就补这几个包
sudo apt-get install autoconf automake libtool autotools-dev

  # 生成 configure 并指定交叉编译器前缀
echo "ac_cv_func_malloc_0_nonnull=yes" > $ARCH-linux.cache
./configure --host=arm-none-linux-gnueabi \
            --prefix=/home/linux/tslib \
            --cache-file=$ARCH-linux.cache

make
make install

--host 填的就是交叉编译器前缀，编译器叫 arm-linux-gcc 就填 arm-linux，叫 arm-none-linux-gnueabi-gcc 就填 arm-none-linux-gnueabi。--prefix 是安装目录，不能跟源码目录相同。

装完拷到板子根文件系统，然后改 ts.conf：

bash
cp -a /home/linux/tslib /rootfs
vi /rootfs/tslib/etc/ts.conf

把第二行的 #module_raw input 改成 module_raw input。这一行必须顶格写，前面留了空格，程序跑起来就报读取 ts.conf 失败。

板子侧的环境变量：

变量 含义
TSLIB_TSDEVICE 触摸屏设备节点，如 /dev/event0
TSLIB_CALIBFILE 校准数据文件，ts_calibrate 生成
TSLIB_CONFFILE 配置文件路径
TSLIB_PLUGINDIR 插件目录
TSLIB_CONSOLEDEVICE 控制台设备，写 none
TSLIB_FBDEVICE framebuffer 设备，如 /dev/fb0
POINTERCAL_FILE 指针校准文件
QWS_MOUSE_PROTO Qt 4 的鼠标协议，如 Tslib:/dev/event0
QWS_DISPLAY Qt 4 的显示设备，如 LinuxFb:mmWidth100:mmHeight130:0

这些设备节点必须跟你板子 /dev 下的真实节点对上，写错一个就是「程序不报错但点不动」。跑一次校准：

bash
/tslib/bin/ts_calibrate

校准会在 /etc 下写一个 pointercal。NFS 挂载时目录权限不够就写不进去，chmod 777 etc 先放开。

QWS_DISPLAY 里的 mmWidth / mmHeight 决定字体大小。素材里那位发现 LCD 上字特别小，把两个数值都改成一半，字就正常了——这数值本是屏的物理尺寸，填错了 DPI 就算错。这是 Qt 4 的 QWS 才有的问题，Qt 5 的 linuxfb 走 QT_QPA_FONTDIR 与字体字号。

  -fontconfig \
  -no-opengl -opengl es2 -egl -no-openvg \
  -system-zlib -system-libjpeg -system-libpng -system-xcb \
  -openssl-linked -qt-pcre -pulseaudio -no-sm \
  -no-sql-db2 -no-sql-ibase -no-sql-mysql -no-sql-oci -no-sql-odbc \
  -no-sql-psql -no-sql-sqlite2 -no-sql-tds \
  -widgets -xkb

几处值得单独点出来：

写法 为什么这么给
-no-gcc-sysroot 这份用 Yocto sysroot 加 -device，工具链自带的 sysroot 与 -sysroot 给的不是一回事，显式关掉。没有这种冲突就不要加
-no-opengl -opengl es2 两个都写了，后面的 es2 覆盖前面的 no。看着矛盾，实际是历史遗留，留一行 -opengl es2 就够
-egl -no-openvg 走 eglfs 必须要 -egl；OpenVG 是另一套矢量图形 API，板子不用就关
-system-* 那一串 因为 -sysroot 指到 i.MX6 的根文件系统，这些 system 库全是 ARM 的，可以直接链
-no-sql-* 那一长串 关掉用不上的 SQL 驱动，省编译时间，也省掉板子上不存在的依赖

make 的顺序 #

bash
  # 先只编基础模块，编通了再往下走
make -j4

  # 出错处理完接着编，不用重新 configure
make -j4

  # 再跑一遍，抓多进程刷掉的那些失败
make -j4

  # 安装必须单线程，出错才看得见
sudo make install

  # 再跑一遍 install，补漏装的
sudo make install

make 跑两遍是有讲究的：多进程编译时某个模块失败，make 会继续编别的，滚过去几百行日志，那条报错就刷没了。第二遍 make 只编没做完的部分，错误会重新冒出来。

make install 不要用 -j。素材里的原话是：一旦出错，错误信息会被其余未完成 job 的输出淹掉，看不出它到底成没成。

config.cache 必须删 #

改完「设备依赖库」这类东西重新配置时，先删缓存：

bash
rm config.cache
./build_configure.sh

不删 config.cache，configure 会复用上次的探测结果，新换的库它看都不看，config.summary 里那一栏还是 No。素材里换完 GPU 版 EGL 库之后就是靠这一步让配置刷新的。

八、验证产物：file 与 readelf #

编完先别急着拷板子，在构建机上把产物验一遍。三条命令够用：

bash
  # 架构对不对
file lib/libQt5Core.so.5.9.6

  # ELF 头：机器类型、ABI
readelf -h lib/libQt5Core.so.5.9.6

  # ARM 属性段：指令集、浮点 ABI、NEON
readelf -A lib/libQt5Core.so.5.9.6

readelf -A 那段输出是判死刑的地方，重点看四行：

text
Attribute Section: aeabi
File Attributes
  Tag_CPU_arch: v7
  Tag_FP_arch: VFPv3-D16
  Tag_ABI_VFP_args: VFP registers
  Tag_ABI_HardFP_use: SP and DP
输出 说明 不对怎么办
Machine: ARM 架构对了 打成 Advanced Micro Devices X86-64 就是 -xplatform 没生效
Tag_CPU_arch: v7 ARMv7 板子是 ARMv5 就回去改 -march
Tag_ABI_VFP_args: VFP registers 硬浮点 这行写 Tag_ABI_VFP_args: compatible 说明浮点 ABI 是软的
Tag_FP_arch: VFPv3-D16 有浮点单元 整段缺失说明工具链是 soft-float 的

平台插件也顺手看一眼，platforms/ 下至少得有那么一两个：

bash
ls lib/plugins/platforms/
  # libqlinuxfb.so   libqeglfs.so   libqxcb.so

一个都没有，说明 -linuxfb / -eglfs / -xcb 一个都没给，程序上板必报找不到平台插件。

上板跑一个最小程序 #

库的架构对不对是一层，能不能跑起来是另一层。写个按钮程序，用你刚编的 qmake 编它：

bash
mkdir hello && cd hello

text
// main.cpp
#include <QApplication>
#include <QPushButton>

int main(int argc, char **argv)
{
    QApplication app(argc, argv);
    QPushButton pushButton(QPushButton::tr("hello world"));
    pushButton.show();
    return app.exec();
}

bash
/path/to/qtarm/bin/qmake -project
/path/to/qtarm/bin/qmake
make

Qt 4 时代跑起来要带 -qws：./test -qws。Qt 5 不需要这个参数，平台插件由 QT_QPA_PLATFORM 决定。屏幕上出现一个按钮，这套 Qt 就算真的能用了。

.pro 里那两行要按板子路径改，别留着默认值：

ini
  # 注释掉原来的 target.path 与 INSTALLS
target.path = /home/firefly/test
INSTALLS += target

链接期提示某个库找不到它依赖的库，用 rpath 补上：

ini
LIBS += -Wl,-rpath,/home/yy/mntnfs/lib/arm-linux-gnueabihf \
        -Wl,-rpath,/home/yy/mntnfs/usr/lib/arm-linux-gnueabihf

Linaro 那套工具链默认只搜 /lib 与 /usr/lib，不带 /lib/arm-linux-gnueabihf，所以要手动指。

程序起来了但一个字都不显示，是字体路径没对。把字体拷进 Qt 的 fonts 目录，或者用变量指过去：

bash
cp simsun.ttc /source/rootfs/qt-everywhere/lib/fonts/
export QT_QPA_FONTDIR=/qt-everywhere/lib/fonts

界面要出中文，还得走一遍翻译链：

bash
lupdate test.pro          # 扫源码，产出 zh_CN.ts
linguist zh_CN.ts         # 逐条填译文，另存
lrelease zh_CN.ts -qm zh_CN.qm   # 压成程序用的 .qm

.pro 里加一行 TRANSLATIONS += zh_CN.ts，程序里 QTranslator::load("zh_CN", ".") 再 installTranslator，把 .qm 拷到板上同目录即可。字太小就在 main 里指定字体：app.setFont(QFont("simsun", 10))。

九、WebEngine 的额外要求 #

WebEngine 不是「Qt 的一个模块」那么简单，它底层捆着 Chromium。编它等于在你的板子上重启一遍浏览器移植工程。

维度 门槛 不满足的表现
内核版本 4.4 LTS 以上 沙箱相关系统调用缺失，运行期崩
工具链 GCC 5.0 以上，支持 C++11 编译期语法错误一片
浮点 ABI 必须 hard-float WebEngine 直接跳过不编
NEON 要开 JS 引擎与音视频解析跑不动
glibc 不能太老，要有现代符号 链接期 undefined
dbus / udev 板子上要有 模块探测失败
宿主工具 python2、bison、flex、gperf、pkg-config、bzip2、ninja、gcc-multilib、libc6-dev-i386 生成步骤中断，工具链跑不起来
内存 8GB 起，配 swap 单个编译单元 OOM，make 被杀
磁盘 20GB 起 编到一半空间满
图形栈 eglfs + OpenGL ES 2 网页黑屏

内核这条不是玄学。Chromium 用 user namespaces 做沙箱隔离，Linux 3.8 里这套机制还不完整，跑到 WebEngine 初始化就出问题。TI 官方在 SDK 里给出带 WebEngine 的 Qt，靠的是把整条链子一起抬上去：内核升到 4.4 LTS、编译器 GCC 5.3、Qt 5.6.2。AM3352 那块板子停在 Linux 3.8，正是这篇素材的来源场景。

软浮点工具链编不出 WebEngine。 它不是报错，是 configure 阶段就把 WebEngine 判为「不满足条件」，直接从构建列表里划掉。你 make 完一切正常，就是找不到 libQt5WebEngine.so，然后编译自己的程序时报：

text
Project ERROR: Unknown module(s) in QT: webenginewidgets

浮点 ABI 用 readelf -A 验，方法见上一章。

宿主机上的构建依赖清单，照着装：

bash
sudo apt-get install python bison flex gperf pkg-config bzip2
sudo apt-get install ninja-build
sudo apt-get install libc6-dev-i386

python 指的是 python2。WebEngine 的构建脚本里有一批 python2 写的生成器，python3 跑不起来。系统里只有 python3 时装个 python-is-python3 之外还得单独留一份 python2。

内存这条容易被低估。Chromium 里有几个巨型编译单元，单个 .cpp 峰值就能吃掉 2GB 内存。ninja -j8 一开，8GB 的机器直接开始杀进程。稳妥的做法是 -j4 甚至 -j2，或者挂一块 swap。

十、WebEngine 编译的坑 #

坑一：-xplatform 写成 linux-g++。第三章讲过它对宿主编译器的影响，放到 WebEngine 上后果更直接——libQt5WebEngine.so 根本没生成，因为那一路的构建条件全被当成本机满足不了，直接跳过。ARM 交叉编译该写 linux-arm-gnueabi-g++ 或 linux-arm-gnueabihf-g++。

坑二：把 -lts 塞进编译器命令。第四章讲过 cannot find -lts，WebEngine 上它来得更早，因为 QtWebEngine 的构建要先编一批宿主工具。库路径走 -I / -L 或 QMAKE_LFLAGS。

坑三：Unknown module(s) in QT: webenginewidgets。这个报错只说结论不说原因，按四步排查：

顺序 查什么 怎么查
1 产物在不在 ls lib/libQt5WebEngine*.so*
2 configure 怎么判的 翻 config.summary 里 WebEngine 那一栏
3 为什么判否 看 summary 后面附的原因，或 config.log 里对应的探测段
4 依赖齐不齐 宿主机工具、硬件浮点、dbus、udev 逐条对

config.summary 是这一步的核心证据。它把每个模块的结论列成一张表，WebEngine ... No 后面就跟着一句为什么。别去猜，去翻。

坑四：sysroot 里 EGL 库不是 GPU 版本。i.MX6 那次配置完，config.summary 里 EGLFS i.MX6 ... No，原因写得清楚：sysroot 里的 EGL 依赖库是通用版本，不是 GPU 厂商提供的那份。换掉才能开启：

bash
  # 从板子厂商的 GPU 驱动包里取，覆盖 sysroot 里那几份
cp libEGL.so* libGLESv2.so* <sysroot>/usr/lib/

  # 删缓存再重新配置，否则探测结果不刷新
rm config.cache
./build_configure.sh

坑五：WebEngine 页面黑屏。嵌入式设备上 QtWebEngine 必须走 eglfs 渲染，走 linuxfb 或 xcb 就是一片黑。-eglfs 要给，-egl 要给，-opengl es2 要给，运行期 QT_QPA_PLATFORM=eglfs。四个条件缺一个，表现都是黑屏而不是报错。

坑六：html 里 select 下拉框跑到屏幕左上角。Qt 5.9.6 的已知 bug，改 qtbase/src/widgets/kernel/qwidgetbackingstore.cpp 里的 findTextureWidgetsRecursively，给 ToolTip 类型的窗口单独走一条取几何的路径：

text
if (wd->renderToTexture) {
    QPlatformTextureList::Flags flags = 0;
    if (widget->testAttribute(Qt::WA_AlwaysStackOnTop))
        flags |= QPlatformTextureList::StacksOnTop;
    if ((widget->windowFlags() & Qt::WindowType_Mask) == Qt::ToolTip) {
        const QRect rect(widget->pos(), widget->size());
        widgetTextures->appendTexture(widget, wd->textureId(), rect, wd->clipRect(), flags);
    } else {
        const QRect rect(widget->mapTo(tlw, QPoint()), widget->size());
        widgetTextures->appendTexture(widget, wd->textureId(), rect, wd->clipRect(), flags);
    }
}

改完要重编 qtbase，然后重编 WebEngine。这段补丁不影响其他模块，放心打。

坑七：sysroot 里残留旧版 Qt。清干净再 configure，见第二章那两条 rm -rf。

十一、裁剪：只编需要的模块 #

全量编一遍 Qt 是四小时起步，带 WebEngine 是十几个小时。板子用不上的模块，早点关掉。

参数 作用 嵌入式怎么给
-make libs 只编库 必给，宿主工具用不着往板子上装
-nomake examples 不编示例 必给，省一半时间
-nomake tests 不编单元测试 必给
-nomake docs 不编文档 给
-nomake tools 不编 designer 之类的工具 板子上不画界面就用不上
-no-compile-examples 只装示例源码不编 想留示例参考时用
-skip <模块> 整个模块跳过 一次能写多个
-no-gui / -no-widgets 不编 GUI、Widgets 只做后台服务才关
-no-sql-<驱动> 关单个 SQL 驱动 不连数据库就全关

-skip 的常见对象：

bash
-skip qtandroidextras \
-skip qtpurchasing \
-skip qtvirtualkeyboard \
-skip qtdoc \
-skip qtwebengine

-skip qtwebengine 是最省的一条：不写它，configure 就会花十几分钟去探测 Chromium 那堆依赖，最后告诉你不行，白白浪费时间。

模块之间有依赖，跳之前先看一眼：

你要的东西 必须有 说明
QtWidgets QtGui、QtCore 关掉 -no-gui，Widgets 一起没了
QtQuick / QML QtGui、QtQml、QtNetwork 只留 QtCore 是跑不了 QML 的
QtWebEngine QtCore、QtGui、QtNetwork、QtQuick、OpenGL ES 缺一个就整块跳过
QtMultimedia QtNetwork、板子上的音频后端 -no-alsa 之后基本废了
QtSql 对应的驱动库 驱动编不进来，模块在也没用

板子上只跑一个固定界面的程序，最小集合是 QtCore + QtGui + QtWidgets + 平台插件。这套编下来装完几百兆，比全量小一个数量级。

十二、编译失败怎么查 #

查错有三个入口，按顺序用：

bash
  # 1. 配置阶段的结论全在这
grep -n "WebEngine\|EGLFS\|QPA\|XCB" config.summary

  # 2. 探测细节与真实报错
less config.log

  # 3. 单线程重跑一次，让错误浮出来
make -j1 2>&1 | tee /tmp/build.log

config.log 是 configure 期间的完整输出，每个探测都是一小段编译链接测试。找不到 libglib-2.0 这类问题，答案就在里面那段测试代码和它的报错行。

常见失败对照：

现象 原因 处理
cannot find -lts -lts 写进了 QMAKE_CC 移到 QMAKE_LFLAGS 或用 -L 传给 configure
file not recognized: File format not recognized -xplatform 指成了宿主机 改成 linux-arm-* 模板
链接时链上了 .a 而不是 .so 库路径里 .so 是断链，只找到静态库 在板子 /lib/arm-linux-gnueabihf 建符号链接
提示某库找不到，但板子上明明有 /usr/lib/.../libxxx.so 指向 /lib/...，跨目录链接在构建机失效 在 /lib/arm-linux-gnueabihf 里补 ln -s libxxx.so.x.x.x libxxx.so
undefined reference to QSGDefaultImageNode::setAnisotropyLevel Qt 5.9.0 不带 OpenGL 的已知 bug 注释 qtlocation/src/location/maps/qgeotiledmapscene.cpp 第 609、634 行的 if(ogl) 分支
报 qmapbox 相关错误 同上，没带 OpenGL 注释 qtlocation/src/plugins/plugins.pro 最后一行
找不到 lchip2tri lpoly2tri lclipper Qt 自身的 3rdparty 没编 进 qtlocation/src/3rdparty 单独 make，再回去 make install
qt_linux_find_symbol_sys 相关 来源不明 试着补 -platform linux-g++
make 顺利结束但少东西 多进程把失败刷掉了 再跑一遍 make
改了配置但 summary 没变 config.cache 复用了旧探测 rm config.cache 重来

链接时链上 .a 而不是 .so 那个坑，值得多说一句。板子上 /usr/lib/arm-linux-gnueabihf/libm.so 往往是指向 /lib/arm-linux-gnueabihf/libm-2.21.so 的软链。目录整个拷到构建机之后，这个相对关系还在，但 -L 指到 usr/lib 那里时，链接器顺着链接找到的目标路径不对，于是回退去链 libm.a。静态库进了共享库的链接，报出来的是 relocation 一类的话：

text
relocation R_ARM_MOVW_ABS_NC against `xxx' can not be used when making a shared object

处理办法就是在板子上把缺失的软链补齐，再把目录重新同步一次：

bash
ln -s libm-2.21.so libm.so
ln -s libxxx.so.x.x.x libxxx.so

十三、易错点速查 #

症状 一句话处理
configure 过了，产物是 x86 -xplatform 没给或拼错，mkspec 没生效
编出来的 qmake 在构建机上跑不了 整条链子都用了交叉编译器，-platform 要给 linux-g++
找不到平台插件 -linuxfb / -eglfs 没给，或 QT_QPA_PLATFORM_PLUGIN_PATH 没设
程序起来一片黑 WebEngine 必须 eglfs，-egl 与 -opengl es2 一起给

点不动屏幕 QT_QPA_EVDEV_*_PARAMETERS 的设备节点写错，或 tslib 没开
ts.conf 读取失败 module_raw input 前面有空格，必须顶格
ts_calibrate 写不出 pointercal NFS 目录权限不够，chmod 777 etc
装完发现装进了 sysroot 用了 -prefix，改 -extprefix
板子上 error while loading shared libraries LD_LIBRARY_PATH 没含 Qt 的 lib 目录
链接报跨架构 QMAKE_AR 那几行还是宿主机工具
