一、从单点知识到完整程序 #

教程里的代码片段和能交付的程序之间，差的不只是代码量。一个二十行的 ReadFile()，open、readAll、close，跑得通。放进真实程序，立刻要回答它没管的问题：用户点了对话框取消，传进来空路径怎么办？文件没有读权限，open 返回 false，谁告诉用户？文件是 200 MB 二进制，readAll() 直接把内存吃掉，要不要拦？GBK 编码的老文本读出来是乱码，编码从哪来？用户改了没存就点关闭，程序要不要拦一下？

这五个问题没有一个是语法问题。它们属于同一类：出错之后怎么办。

任何带持久化的桌面程序都分四块：

层 干什么 本篇对应
界面层 显示、接收输入、把用户意图变成一次操作 第九章的 MainWindow
数据层 内存里的当前状态：文本、当前路径、是否已修改 ui->textEdit、fileName
持久层 把状态写出去、读回来 QFile、.qrc、QSettings
错误出口 出错时谁负责表态 第七章、第八章

写教程代码时你只关心数据层。写程序时，后两层才是花时间的地方。

还有一条容易忽略的区分：程序要持久化的东西不是一类，是两类。

一类是程序自带的、发布后不再变的——图标、样式表、默认模板、翻译文件。它们跟着可执行文件走，用户不该改也不需要改。另一类是运行时会变的——用户编辑的文档、窗口位置、上次打开的目录、最近文件列表。它们必须写在用户能写的地方。

这两类混在一起，就是本篇要反复强调的那条线。先记住一句话：.qrc 是编译进二进制的只读数据，普通文件是运行时可变的。 第三章到第四章把这句话拆开讲透。

二、文件读写 #

QFile 的三步 #

读一个文本文件永远是三步：打开、读写、关闭。

cpp
#include <QFile>
#include <QTextStream>
#include <QDebug>

void ReadFile(const QString &filename)
{
    // QFile 提供读写文件的接口，文本、二进制、资源文件都能读
    QFile my_file(filename);
    if (!my_file.open(QIODevice::ReadOnly | QIODevice::Text)) {
        qDebug() << "Could not open file for Reading:" << my_file.errorString();
        return;
    }
    // QTextStream 提供读写文本的接口，负责字节和 QString 之间的转换
    QTextStream outText(&my_file);
    qDebug() << outText.readAll();
    my_file.close();
}

QFile my_file(filename); 这一行不能省。原稿这里漏了构造，直接 my_file.open()，编译不过。QFile 有两个构造：带路径的 QFile(const QString &name)，和不带路径的 QFile() 之后 setFileName()。两种都行，对象得先有名字。

open() 的模式是位标志组合：

模式 含义 典型用途
ReadOnly 只读打开，文件必须存在 打开文档
WriteOnly 只写打开，不存在则创建，存在则清空 覆盖保存
ReadWrite 读写打开 就地修改
Append 追加写，写指针在末尾 日志
Truncate 打开时清空已有内容 配合 WriteOnly
Text 文本模式，读写时转换换行符 所有文本文件

Text 这一位单独说。它在 Windows 上做两件事：读的时候把 \r\n 折成 \n，写的时候把 \n 展开成 \r\n。不加这一位，你在记事本里打开自己写的文件会看到一整行。

写文件与 flush #

cpp
void WriteFile(const QString &filename)
{
    QFile my_file(filename);
    if (!my_file.open(QIODevice::WriteOnly | QIODevice::Text)) {
        qDebug() << "Could not open file for Writing:" << my_file.errorString();
        return;
    }
    QTextStream inText(&my_file);
    inText << "Hello World!";
    inText.flush();      // 把 QTextStream 缓冲区推给 QFile
    my_file.flush();     // 把 QFile 缓冲区推给操作系统
    my_file.close();
}

flush() 为什么不可少：QTextStream 自己有一层缓冲，QFile 底下还有一层。<< 只是把字符放进第一层，不保证到了磁盘。不 flush，程序崩了，缓冲区里的内容就没了。close() 内部会 flush，但写完还要继续用这个句柄（比如接着 seek(0) 再读），就得手动推一次。

编码 #

QTextStream 不指定编码时用系统默认。Qt5 在中文 Windows 上这个默认是 GBK（代码页 936）。本机写、本机读没事，文件发给用 UTF-8 的同事就是满屏乱码。

cpp
QTextStream out(&file);
out.setCodec("UTF-8");                // Qt5 的写法，参数是编码名

QTextStream in(&file);
in.setCodec("UTF-8");

Qt5 是 setCodec()，Qt6 换成了 setEncoding(QStringConverter::Utf8)。项目里统一约定：文本文件一律 UTF-8、不加 BOM，除非要迁就 Windows 上的老记事本和 Excel，那时加 setGenerateByteOrderMark(true)。

保存不要直接覆盖 #

WriteOnly 打开的那一刻，原文件已经被清空了。写到一半崩了、磁盘满了、用户拔了 U 盘，你得到的是一个空文件，原文没了。

QSaveFile 先写临时文件，commit() 成功才替换：

cpp
bool SaveText(const QString &filename, const QString &text)
{
    QSaveFile file(filename);
    if (!file.open(QIODevice::WriteOnly | QIODevice::Text)) {
        return false;
    }
    QTextStream out(&file);
    out.setCodec("UTF-8");
    out << text;
    return file.commit();          // 要么全成，要么原文件不动
}

只有 QFile 时，退一步的做法是先写 filename + ".tmp"，close() 之后 QFile::remove() 加 QFile::rename() 替换。多几行，效果一样。

读之前顺手用 QFileInfo 做便宜的前置检查：exists()、isFile()、size()、isWritable()、lastModified()。状态栏显示「上次修改时间」就靠最后一个。QTextStream 三个读法：readAll() 整篇进内存，小文件用；while (!in.atEnd()) in.readLine() 按行，大文件用；in >> word 按空白切词。编辑器的「打开」用 readAll()，因为 QTextEdit 本来就要整篇进内存。

三、资源文件 .qrc #

资源系统解决什么问题 #

程序总要带一批固定文件：图标、样式表、默认模板、翻译文件。放可执行文件旁边，一个 icons/ 目录。问题立刻来：用户移动了 exe，图标没了；打包时忘了拷贝目录，图标没了；有人删了文件，图标没了。文件系统里的东西会丢，这是它的本性。

Qt 的资源系统（Resource System）针对的正是这件事：把一组文件嵌进可执行文件，运行时用 :/ 前缀访问，跨平台，不会丢。

原理不复杂。.qrc 是一份 XML 清单，构建系统用 rcc 把清单里列的文件全部转成一个 C++ 源文件——一堆 unsigned char 数组加索引表，然后编进二进制。程序启动后这些字节已经在进程的内存镜像里，QFile(":/xxx") 拿到的是内存中的一段。

写一个 .qrc #

xml
<RCC>
    <qresource prefix="/">
        <file>icons/new.png</file>
        <file>icons/open.png</file>
        <file>icons/save.png</file>
        <file>style/app.qss</file>
        <file>templates/welcome.txt</file>
    </qresource>
</RCC>

路径相对 .qrc 所在目录。拼出来的访问路径是「前缀 + 相对路径」：

.qrc 里的写法 代码里的访问路径
prefix="/" + icons/new.png :/icons/new.png
prefix="/icons" + new.png :/icons/new.png
prefix="/" + style/app.qss :/style/app.qss

两种写法结果一样，区别在组织方式。文件多时用 prefix 分组，清单读起来清楚。alias 可以改名，把长路径压短：

xml
<file alias="new.png">icons/24x24/actions/new.png</file>

这样 :/new.png 就能拿到那张图。

在项目里挂上它 #

qmake 一行，CMake 两行：

RESOURCES += res.qrc

cmake
set(CMAKE_AUTORCC ON)
add_executable(EasyPad main.cpp mainwindow.cpp mainwindow.h mainwindow.ui res.qrc)

用 Qt Creator 新建项目时，右键 →「Add New」→「Qt」→「Qt Resource File」，会自动生成 .qrc 并挂进 .pro。在 Designer 里给动作加图标时，点图标输入框旁的小方块弹出「Choose Resource」，能直接浏览 :/ 下的内容——前提是 .qrc 已挂上并编译过一次。没挂上时那个对话框是空的，很多人卡在这一步。

资源怎么用 #

QFile、QPixmap、QIcon、QTextStream 全部认 :/ 路径：

cpp
ui->actionNew->setIcon(QIcon(":/icons/new.png"));      // 图标
ui->label->setPixmap(QPixmap(":/icons/logo.png"));     // 图片

QFile qss(":/style/app.qss");                          // 样式表
if (qss.open(QIODevice::ReadOnly | QIODevice::Text)) {
    qApp->setStyleSheet(QString::fromUtf8(qss.readAll()));
    qss.close();
}

QFile tpl(":/templates/welcome.txt");                  // 模板，读法同第二章的 ReadFile

第二章那个 ReadFile() 能直接复用，原因就在这：QFile 是「I/O 设备」的抽象，磁盘文件和资源文件在它眼里是同一种东西。同一份读代码，传 "F:/test.txt" 读磁盘，传 ":/templates/welcome.txt" 读资源。

资源也能当目录遍历（QDir(":/icons") 加 entryInfoList()），判断存在用 QFile::exists(":/icons/new.png")。

只读，别想着往里写 #

资源系统最硬的一条约束：.qrc 里的内容运行时不可写。

cpp
QFile f(":/config/settings.ini");
f.open(QIODevice::WriteOnly);     // 必然失败，返回 false

原因简单：它已经编进二进制了，那块内存是只读段。改它等于改 exe 本身，运行时没人允许你这么干。「把用户配置写进 .qrc」这件事不存在。

程序里 res.qrc 只放一类东西：发布后不会再变、丢了会影响功能的文件。icons/ 放菜单与工具条图标、应用图标；style/ 放 QSS；templates/ 放新建文档的默认内容；translations/ 放 .qm；fonts/ 放随程序分发的字体。反过来，日志、缓存、用户文档、数据库、导出结果一律别往里塞。

一个坑：改了图不生效 #

最常见的疑问：换了 icons/new.png，重新编译，界面上还是旧图。三个原因，按概率排：

  1. 构建系统没重跑 rcc。.qrc 里列的是文件名，图片内容变了但 .qrc 时间戳没变，增量构建认为资源没变，跳过。解法是「重新构建项目」而不是「构建」，或者直接删构建目录重来。
  2. 改的不是同一个文件。项目里有两份 new.png，.qrc 指向 icons/ 下的，你改的是桌面上那份。
  3. .qrc 里用 alias 改名了。代码访问 :/new.png，实际指向 icons/24x24/actions/new.png。

后两条都是路径问题，QFile::exists() 加 qDebug() 一查就清楚。

四、资源与文件的取舍 #

维度 .qrc 资源 普通文件
存放位置 编进可执行文件 磁盘上的独立文件
运行时可变 不能写，只读 可读可写
路径形式 :/icons/new.png C:/data/a.txt、/home/u/a.txt
是否随 exe 丢失 不会，永远在 会，挪动、删错、打包漏了
体积影响 增大 exe 不占 exe
换内容要重新发布 要，得重新编译 不要，直接替换文件
用户可见可改 否 是
读性能 快，内存映像 走文件系统
适合 图标、样式、默认模板、翻译 文档、配置、日志、导出

判据只有一条：这个文件，用户装上程序之后会不会变？不会变就进 .qrc，会变就走文件系统。

图标不会变，用户不会去改菜单上的小图。默认模板不会变。这些进 .qrc。用户写的文档会变，窗口位置会变，最近文件列表会变。这些走文件系统或 QSettings。

混淆这两者，会得到两个典型故障。

故障一：改了图片不生效。 图编进了二进制，你换磁盘上的 png 没用，得重新编译；重新编译还得确保 rcc 真重跑了。客户现场最尴尬：「你们这个图标不对」，你改完发过去，对方还是看到旧的，因为发的是旧 exe。

故障二：装到只读目录写不进去。 程序把用户数据写在 exe 旁边，而 exe 被装到了 C:\Program Files\...。这个目录普通用户没有写权限，open(WriteOnly) 直接失败。开发机上一切正常，因为你在自己桌面上跑；一装到标准位置就崩。搬到 Linux，/usr/bin 和 /opt 也是 root 的。还有更隐蔽的变体：企业统一部署、绿色版放只读共享盘。

所以规则是：凡是 exe 所在目录，都当作只读对待。

用户数据该放哪，分三摊：

数据 放哪 用什么
用户文档（.txt） 用户自己选，默认「文档」目录 QFileDialog + QStandardPaths
程序配置（窗口大小、上次目录） 系统规定的位置 QSettings
缓存、日志、导出 AppDataLocation 一类标准路径 QStandardPaths

QStandardPaths 负责跨平台路径翻译，别自己拼 "C:/Users/xxx/AppData"：QString dir = QStandardPaths::writableLocation(QStandardPaths::AppDataLocation); QDir().mkpath(dir); 之后 dir + "/easypad.log" 就是日志路径。

有一种情况两者都用：图标走 .qrc 保证不丢，同时允许用户自定义皮肤——默认 :/icons/new.png，QFile::exists(configDir + "/skin/new.png") 成立就改用外部文件。内置一份兜底，外部覆盖优先。

五、QSettings：配置持久化 #

窗口大小、上次打开的目录、工具栏显不显示、字号、最近文件列表。这些东西必须在程序退出后活下来。

自己写一个 config.ini 也能干，但你得处理：文件放哪、跨平台怎么放、格式怎么定、读写怎么容错。这些琐事加起来两三百行，每个项目重写一遍。QSettings 就是别人替你写完的那两三百行。

两种构造方式 #

cpp
// 推荐：给组织名和应用名，剩下全交给系统
QSettings settings("Wayne", "EasyPad");

// 指定格式和绝对路径：位置完全由你决定
QSettings settings("/home/u/.easypad/easypad.ini", QSettings::IniFormat);

单例式用法也常见——不构造对象，直接用静态函数：

cpp
QSettings settings;                      // 用 QCoreApplication 里设的 org/app 名

前提是 main() 里设过 a.setOrganizationName("Wayne"); a.setApplicationName("EasyPad");。设了之后全项目不用重复传名字。

读写的基本动作 #

四个函数够用一辈子：

cpp
QSettings s("Wayne", "EasyPad");

s.setValue("MainWindow/width", 800);          // 写
int w = s.value("MainWindow/width", 800).toInt();   // 读，带默认值
bool has = s.contains("MainWindow/width");     // 有没有
s.remove("MainWindow/width");                  // 删掉

value() 的第二个参数是默认值，键不存在时返回它。不传默认值时，键不存在返回一个无效 QVariant，toInt() 得到 0——窗口宽度变成 0，你就看到一个缩成一条线的窗口。读配置一律给默认值，这是最小防线。

存的类型自己定，QVariant 都能装：

cpp
s.setValue("MainWindow/x", 100);                                  // int
s.setValue("MainWindow/maximized", true);                         // bool
s.setValue("Editor/fontFamily", "Consolas");                      // QString
s.setValue("Editor/wordWrap", QPoint(0, 0));                      // 可序列化类型
s.setValue("Files/recent", QStringList() << "a.txt" << "b.txt");   // 列表

QStringList、QByteArray、QRect、QPoint、QSize 都能直接存，内部会转成文本。第五篇讲过 QVariant，这里是它的主场。

beginGroup / endGroup #

配置项一多，key 就成了长串。beginGroup() 加前缀，endGroup() 恢复：

cpp
void Dialog::SaveSettings()
{
    QSettings setting("Wayne", "MyApp");
    setting.beginGroup("MainWindow");      // 后面的 key 都带 MainWindow/ 前缀
    setting.setValue("geometry", saveGeometry());
    setting.setValue("state", saveState());
    setting.setValue("fontSize", ui->textEdit->font().pointSize());
    setting.endGroup();                    // 前缀复位
    qDebug() << "Saved";
}

beginGroup("MainWindow") 之后 setValue("geometry", ...) 实际写的键是 MainWindow/geometry，可以嵌套。两者要配对。中间 return 了，endGroup 就没执行，后面所有写入都会带着错误的前缀。

存取窗口几何 #

QWidget 自带两个函数：saveGeometry() 返回位置、大小、是否最大化的 QByteArray，restoreGeometry() 还原；QMainWindow 另有 saveState() / restoreState()，管工具条和停靠窗口的位置。

cpp
// 关闭时
QSettings s("Wayne", "EasyPad");
s.beginGroup("MainWindow");
s.setValue("geometry", saveGeometry());
s.setValue("state", saveState());
s.endGroup();

// 启动时
QSettings s("Wayne", "EasyPad");
s.beginGroup("MainWindow");
restoreGeometry(s.value("geometry").toByteArray());
restoreState(s.value("state").toByteArray());
s.endGroup();

restoreGeometry() 返回 bool：数据为空、格式不对、或者屏幕分辨率变了放不下，返回 false，窗口保持默认位置。多显示器拔掉之后上次的坐标会落到屏幕外，Qt 会自己纠正。

自己存坐标的版本更直白：SaveSettings() 里 beginGroup("MainWindow") 之后连写 setValue("x", pos().x())、setValue("width", size().width()) 四项，再 endGroup()，末尾 qDebug() << "Saved"；LoadSettings() 用 s.value("x", 100).toInt() 逐项读回，最后 setGeometry(x, y, w, h)，打完 qDebug() << "Loaded" 收工。

按下 Save 存，按下 Load 恢复，窗口就变回上次的大小。这个例子短，但把 QSettings 的套路用完了：beginGroup、setValue、value 带默认值、endGroup。区别在于 saveGeometry() 连最大化状态一起存，自己存坐标还得另存一个 bool。

什么时候写 #

时机 写法 评价
每次改动立即写 setValue 直接调 简单，键一多就是频繁 I/O
关窗口时写 closeEvent() 里集中写 推荐，一次落盘
定时写 QTimer 每 30 秒 防崩溃丢配置，配合第二种用

closeEvent() 里集中写最干净：一次打开、一次落盘，不做频繁 I/O。完整实现见第十章。

QSettings 析构时会同步写盘，函数结束对象销毁，不用手动 sync()。

六、配置的存储位置 #

QSettings 最值得单独讲的一节：同一行 QSettings s("Wayne", "EasyPad")，在三个系统上落到三个完全不同的地方。

系统 默认格式 落地位置
Windows 系统注册表 HKEY_CURRENT_USER\Software\Wayne\EasyPad
Linux INI 文本 ~/.config/Wayne/EasyPad.conf
macOS plist ~/Library/Preferences/com.Wayne.EasyPad.plist

Windows 上不生成任何文件，直接进注册表。用 regedit 打开 HKEY_CURRENT_USER\Software，能找到你的组织名，下面挂着应用名，再下面是键值。

Linux 上是一个纯文本 INI，路径遵循 XDG 规范。cat ~/.config/Wayne/EasyPad.conf 能看到全部内容，改一行就生效。macOS 上是 plist，defaults read com.Wayne.EasyPad 读得出来。

三种格式互相不认识。Windows 上导出的配置拷到 Linux 不起作用——路径不同、格式不同、key 的组织方式也不同。

位置是三层拼出来的：

层 来源 上面例子里的值
组织名 setOrganizationName() 或构造参数 Wayne
应用名 setApplicationName() 或构造参数 EasyPad
键路径 beginGroup() 加 setValue() 的 key MainWindow/geometry

组织名和应用名一换，位置整体就换。这意味着：已经发布过的程序，别改这两个名字。 改了之后老用户的配置读不到，窗口位置和上次目录全部丢失，看起来像程序坏了。

想指定位置：IniFormat + 绝对路径 #

默认行为省事，但有时你必须自己定位置：便携版配置要跟 exe 放一起、多个模块要共用一个配置文件、配置文件要给用户手工编辑、配置要放共享目录。

cpp
// 绝对路径 + IniFormat：写哪儿完全由你决定
QSettings s("D:/EasyPad/config/easypad.ini", QSettings::IniFormat);
s.setValue("MainWindow/width", 800);

生成的 .ini 是标准文本：

text
[MainWindow]
width=800
height=600
geometry=@ByteArray(\x1\xd9\xd0\xcb\0\x2\0\0...)

三个注意点：

  1. 父目录必须存在。QSettings 会创建文件，但不会创建目录。不 mkpath，写就静默失败。
  2. 路径用绝对路径。相对路径以当前工作目录为基准，而工作目录会是任何地方，双击打开文件时尤其不可控。
  3. 格式显式指定。不给 IniFormat，Qt 会按扩展名猜；自定义扩展名（.cfg、.dat）猜错的概率不低。

便携版的写法有个前提——applicationDirPath() 会是只读目录。装进 Program Files 就不再便携，得回退：

cpp
QString cfg = QCoreApplication::applicationDirPath() + "/easypad.ini";
QSettings probe(cfg, QSettings::IniFormat);
probe.setValue("probe/ok", true);
probe.sync();
if (probe.status() != QSettings::NoError) {          // 目录写不了，退回标准位置
    cfg = QStandardPaths::writableLocation(QStandardPaths::AppConfigLocation) + "/easypad.ini";
    QDir().mkpath(QFileInfo(cfg).absolutePath());
}

status() 返回 NoError、AccessError、FormatError 之一。这是判断「到底写没写进去」的唯一可靠方式——setValue() 本身没有返回值。

一个程序可以有两个 QSettings 对象，各管一摊：用户配置存窗口大小、字体这些个人偏好，跟人走；程序目录里的 ini 存公司统一的服务器地址、模板路径，跟环境走。

直接看文件确认 #

调试配置问题时别看代码，看落地的文件：

系统 命令
Windows reg query HKCU\Software\Wayne\EasyPad /s
Linux cat ~/.config/Wayne/EasyPad.conf
macOS defaults read com.Wayne.EasyPad
指定路径 直接打开那个 .ini 文件

QSettings 也有三个函数能自报家门：s.fileName() 给出实际写入的文件（Windows 注册表下返回空），s.allKeys() 列出当前所有键，s.format() 返回 NativeFormat 或 IniFormat。

allKeys() 是排查「读不到配置」的第一件武器：键不在列表里，说明写失败了，或者写到别的 QSettings 实例里去了。

七、错误处理的基本套路 #

静默失败是最贵的 bug #

错误分几类，处理方式完全不同：

类别 例子 谁来兜
用户操作错误 打开一个不存在的文件 提示用户，不崩
环境错误 目录没写权限、磁盘满 提示用户，给出替代方案
程序 bug 数组越界、空指针 崩掉，越早越好
外部依赖错误 网络断开、服务端返回 500 重试或降级

第三类不该用错误处理盖住。崩掉、留下调用栈，比「程序假装正常继续跑、把数据写坏」好一百倍。

一二四类必须处理，而且必须让用户知道。这就是本节的全部要义：每个有失败风险的操作都要检查返回值，失败时给出可读的提示。

反例，这种代码在项目里到处都是：

cpp
QFile f(filename);
f.open(QIODevice::ReadOnly);              // 返回值被丢掉
QString text = QTextStream(&f).readAll(); // 没打开就成了空字符串

打开失败时 readAll() 返回空串，界面上一片空白。用户以为文件空了，一保存，把原来几百 KB 的内容覆盖成空文件。数据就这么没了。最贵的 bug 从来不是崩溃，是安安静静地做错事。

Qt 的错误处理风格 #

Qt 不用异常做日常错误处理，用「返回值 + 错误信息」。理由是异常在跨模块、跨编译器边界时行为不一致，而且 QFile 这类对象在异常里容易漏掉清理。

三个接口：

cpp
bool ok = file.open(...);                    // 成功 true / 失败 false
QFileDevice::FileError err = file.error();   // 错误码，可编程判断
QString msg = file.errorString();            // 错误文本，给人看

错误码常打交道的几个：

错误码 含义 常见场景
NoError 没有错误 —
OpenError 打不开 路径不存在、权限不足
PermissionsError 权限不足 Program Files 下写文件
ReadError 读失败 文件被占用、介质拔出
WriteError 写失败 磁盘满、只读介质
ResourceError 资源不存在 :/xxx.png 拼错
UnspecifiedError 其他 兜底

errorString() 给人看，语言跟着系统 locale 走；error() 给程序判断。要分支处理用 error()，要拼提示用 errorString()。别去 if (msg.contains("denied"))，字符串一变就断。

try-catch 的位置 #

C++ 的 try-catch 在 Qt 项目里不是主流，但该用的时候得会：

cpp
#include <QCoreApplication>
#include <QDebug>

int main(int argc, char *argv[])
{
    QCoreApplication a(argc, argv);

    try {
        qDebug() << "Before";
        throw QString("Something went wrong");
        qDebug() << "This line never runs";
    }
    catch (const QString &err) {              // 按类型捕获
        qDebug() << "Caught:" << err;
    }

    return a.exec();
}

几条硬规则：try 和 catch 必须成对，只写 catch 编译不过；按类型捕获，catch(QString) 接不住 int，没人接就 std::terminate；末尾加一个 catch (...) 兜底；抛引用、捕引用，省一次拷贝也避免切片；QString 不是最好的异常类型，标准做法是继承 std::exception 带错误码和消息。

cpp
class ParseError : public std::exception {
public:
    explicit ParseError(QString text) : m_what(std::move(text).toUtf8()) {}
    const char *what() const noexcept override { return m_what.constData(); }
private:
    QByteArray m_what;      // 存成员里，不然 what() 返回悬空指针
};

同一层能就地处理就用返回值，需要跨层报错才用异常；失败常见、Qt 自带 API、性能敏感这三条都指向返回值。Qt 自己的 API 全按返回值设计，跟着它的风格走，代码一致性最好。

还有一条：槽函数里别让异常逃出去。 信号槽调用链是事件循环触发的，异常从槽里抛到事件循环，行为未定义。槽里的异常就地 catch 掉，转成提示。

组合起来的最小套路 #

一个「有失败风险的操作」的完整写法，六步：

cpp
bool OpenFile(const QString &path, QString *outText, QString *outError)
{
    QFileInfo info(path);
    if (!info.exists()) {
        *outError = QObject::tr("文件不存在：%1").arg(path);
        return false;
    }
    if (!info.isReadable()) {
        *outError = QObject::tr("没有读取权限：%1").arg(path);
        return false;
    }

    QFile f(path);
    if (!f.open(QIODevice::ReadOnly | QIODevice::Text)) {
        *outError = QObject::tr("打开失败：%1").arg(f.errorString());
        return false;
    }

    QTextStream in(&f);
    in.setCodec("UTF-8");
    *outText = in.readAll();

    if (f.error() != QFileDevice::NoError) {
        *outError = QObject::tr("读取中断：%1").arg(f.errorString());
        f.close();
        return false;
    }

    f.close();
    return true;
}

调用方拿到 false 就必须表态，不能接着往下走：

cpp
QString text, err;
if (!OpenFile(path, &text, &err)) {
    QMessageBox::warning(this, tr("打开失败"), err);
    return;
}
ui->textEdit->setPlainText(text);

前置检查、执行、检查返回值、干活、检查过程错误、清理——六步就是这个套路的全部，写多了是肌肉记忆。提示文本用 tr() 包一层，将来要出英文版只需补 .ts 文件。

八、把错误告诉用户 #

三档输出与提示文案 #

函数 级别 什么时候用
qDebug() 调试 开发期追踪，发布版可以关掉
qWarning() 警告 能继续，但有异常情况
qCritical() 严重 功能坏了，会影响数据
qFatal() 致命 直接 abort，真不能继续时用

这些输出都进 stderr，发布版用户看不到。日志不等于提示：日志给开发者，提示给用户，两条路都要走。界面上的提示有三条要求：说清楚发生了什么（「打开失败」不够，得说「没有读取权限：D:/data/a.txt」）；说清楚怎么办（「请检查文件是否被其他程序占用，或改用另存为保存到其他位置」）；别用技术黑话（别把 PermissionsError 直接丢给用户）。

差 好
Error: -1 保存失败：目标目录没有写入权限
open failed 打不开 D:/data/a.txt，文件正被其他程序使用
（什么都不弹） 磁盘空间不足，无法保存。已保留原文件，请清理后重试

QMessageBox 四种，按严重程度用：

cpp
QMessageBox::information(this, tr("提示"), tr("已保存"));       // 纯通知
QMessageBox::warning(this, tr("保存失败"),                      // 操作失败必用
                     tr("无法写入 %1\n%2").arg(path, file.errorString()));
QMessageBox::critical(this, tr("错误"), tr("配置文件损坏，程序将退出"));

int ret = QMessageBox::question(this, tr("未保存"),             // 要用户拿主意
                                tr("文档已修改，是否保存？"),
                                QMessageBox::Save | QMessageBox::Discard | QMessageBox::Cancel,
                                QMessageBox::Save);

question 的第四个参数是按钮组合，第五个是默认选中项。破坏性操作（删除、丢弃）不能做默认项，用户手快按回车就没了。

弹窗还有个数量问题。循环里对 1000 个文件做操作，每个失败弹一个框，用户得点 1000 次。三条对策：批量操作先计数后汇总一次（「12 个成功，3 个失败」加可展开详情）；同一个错误只提示一次；非致命问题进状态栏不进弹窗，比如 statusBar()->showMessage(tr("配置读取失败，已使用默认值"), 5000);。

发布版还该把日志落进文件。qInstallMessageHandler 接管 qDebug/qWarning，把带时间戳的行追加到 AppDataLocation 下的 app.log，顺手 fprintf(stderr, ...) 一份给控制台。日志路径同样别选 exe 目录，超过 5 MB 就滚动（app.log → app.log.1），否则用户的磁盘会被悄悄吃满。

用 Qt Creator 新建「Qt Widgets Application」，主窗口类 MainWindow，勾上「Generate form」。.ui 里只有一个控件：中间放一个 QTextEdit，objectName 改成 textEdit。菜单和工具条用「Action Editor」加动作：

命名规则就是连接 #

on_actionOpen_triggered() 这种槽名不是随便起的，是 Qt 的自动连接约定：on_<objectName>_<signalName>(参数)。ui->setupUi(this) 里会调 QMetaObject::connectSlotsByName(this)，把符合这个模式的所有槽自动连到对应对象的对应信号上。

名字拼错一个字母（on_actoinOpen_triggered），编译能过，点击没反应，也不报错。这是新手最常见的「按钮没反应」原因。两种连接方式别混用——自动连上之后又手写一次 connect，槽会被调两次，表现为「打开文件弹两次对话框」。

十、打开、保存与另存为 #

新建与打开 #

cpp
void MainWindow::on_actionNew_triggered()
{
    if (!maybeSave()) return;
    fileName.clear();
    ui->textEdit->clear();
    ui->textEdit->document()->setModified(false);   // 清空不算修改
    modified = false;
    setCurrentFile(QString());
}

void MainWindow::on_actionOpen_triggered()
{
    if (!maybeSave()) return;
    QString path = QFileDialog::getOpenFileName(
        this, tr("打开文件"), lastDir,
        tr("文本文件 (*.txt *.md *.log);;所有文件 (*.*)"));
    if (path.isEmpty()) return;                     // 用户点了取消
    loadFile(path);
}

void MainWindow::loadFile(const QString &path)
{
    QFile file(path);
    if (!file.open(QIODevice::ReadOnly | QIODevice::Text)) {
        QMessageBox::warning(this, tr("打开失败"),
                             tr("无法打开 %1\n%2").arg(path, file.errorString()));
        return;
    }
    QTextStream in(&file);
    in.setCodec("UTF-8");
    ui->textEdit->setPlainText(in.readAll());
    QString errStr = file.errorString();            // 先存下来，close 之后还能用
    bool readFailed = file.error() != QFileDevice::NoError;
    file.close();
    if (readFailed) {
        QMessageBox::warning(this, tr("读取中断"),
                             tr("读取 %1 时出错：%2").arg(path, errStr));
    }
    lastDir = QFileInfo(path).absolutePath();
    setCurrentFile(path);
    ui->textEdit->document()->setModified(false);
    modified = false;
}

clear() 之后 document()->modified() 会变成 true——Qt 认为内容变了，要显式 setModified(false)，否则标题上一直挂个星号。对话框第三个参数给 lastDir，下次打开停在上次的位置；过滤器用双分号分组；setPlainText 而不是 setText——后者按富文本解析，<b> 会被当标签吃掉。

保存与另存为 #

cpp
void MainWindow::on_actionSave_triggered()
{
    if (fileName.isEmpty()) {                 // 从没存过，走另存为
        on_actionSave_as_triggered();
        return;
    }
    if (saveFile(fileName)) {
        statusBar()->showMessage(tr("已保存 %1").arg(displayName()), 3000);
    }
}

bool MainWindow::saveFile(const QString &path)
{
    QSaveFile file(path);                     // 原子写，写坏不留半截文件
    if (!file.open(QIODevice::WriteOnly | QIODevice::Text)) {
        QMessageBox::warning(this, tr("保存失败"),
                             tr("无法写入 %1\n%2").arg(path, file.errorString()));
        return false;
    }
    QTextStream out(&file);
    out.setCodec("UTF-8");
    out << ui->textEdit->toPlainText();
    out.flush();
    if (!file.commit()) {                     // 提交失败，原文件未被破坏
        QMessageBox::warning(this, tr("保存失败"),
                             tr("写入 %1 时出错：%2").arg(path, file.errorString()));
        return false;
    }
    lastDir = QFileInfo(path).absolutePath();
    setCurrentFile(path);
    ui->textEdit->document()->setModified(false);
    modified = false;
    return true;
}

void MainWindow::on_actionSave_as_triggered()
{
    QString path = QFileDialog::getSaveFileName(
        this, tr("另存为"), lastDir,
        tr("文本文件 (*.txt);;Markdown (*.md);;所有文件 (*.*)"));
    if (path.isEmpty()) return;
    if (QFileInfo(path).suffix().isEmpty()) {     // Qt 不自动补扩展名
        path += ".txt";
    }
    saveFile(path);
}

toPlainText() 拿纯文本，toHtml() 拿富文本。我们的编辑器不做富文本，统一用纯文本。getSaveFileName 会提示「文件已存在，是否覆盖」，返回的路径已经过确认，但确认和真正写入之间有时间差，别在这中间干别的事。

关闭前拦截 #

cpp
bool MainWindow::maybeSave()
{
    if (!modified) return true;
    int ret = QMessageBox::warning(
        this, tr("Easy Pad"),
        tr("文档「%1」有未保存的修改，是否保存？").arg(displayName()),
        QMessageBox::Save | QMessageBox::Discard | QMessageBox::Cancel,
        QMessageBox::Save);

    if (ret == QMessageBox::Save) {
        on_actionSave_triggered();
        return !modified;          // 保存失败的话，modified 还是 true
    }
    if (ret == QMessageBox::Discard) return true;
    return false;                  // Cancel
}

void MainWindow::closeEvent(QCloseEvent *event)
{
    if (!maybeSave()) {
        event->ignore();           // 拦住，窗口不关
        return;
    }
    QSettings s("Wayne", "EasyPad");
    s.beginGroup("MainWindow");
    s.setValue("geometry", saveGeometry());
    s.setValue("state", saveState());
    s.setValue("lastDir", lastDir);
    s.endGroup();
    event->accept();
}

event->ignore() 是这个函数的全部技巧。不写它，maybeSave() 返回 false 之后窗口照样关，未保存的内容就没了。

点窗口的 X 走 closeEvent，点菜单「退出」也走它。但程序被任务管理器杀掉、断电、崩溃，什么都不会走——这个缺口只能靠定时自动保存补，QTimer 每两分钟写一次临时文件，第六篇有 QTimer 的用法。

编辑器还缺什么？查找替换要 QTextDocument::find() 加一个 QDialog；字体字号用 QFontDialog，结果存进 QSettings；编码选择要探测 BOM 再让用户手动改；最近文件列表用 QSettings 存 QStringList 配 QMenu 动态项；行号要左侧挂一个自绘 QWidget 跟滚动条联动；命令行走 QCommandLineParser；拖放打开要 dragEnterEvent 和 dropEvent。每条都能独立成篇，真正的编辑器是把这张单子全做完的结果。

十一、收尾：这套教程之后 #

九篇走完，手里有什么：会建工程、会连信号槽、知道对象树和事件循环；会用布局把控件摆满窗口；知道 QList、QMap、QVariant 怎么选怎么遍历；会用 QString 的正则和算法函数处理文本；知道模型视图分离；会用 QTimer、会写 TCP 客户端；会读写文本文件、会解析 XML；会画图会写动画；会把上面这些拼成一个能存盘、能记配置、出错会提示的程序。

这个程度够写多数内部工具和小工具。往下走按方向挑：界面更复杂，去看自定义控件、QGraphicsView 和 QSS 深度用法，入口是 Qt 自带的 widgets 示例集。数据更多，看 QAbstractTableModel 自定义和代理（delegate）。要联网看 QNetworkAccessManager、QWebSocket 与 JSON；要并发看 QThread 和 QtConcurrent；要存数据从 QtSql 的 SQLite 起步；要上手机转 QML 与 Qt Quick；要发布就上 windeployqt；换 Qt6 主要改两处——编码（setCodec → setEncoding）和正则（QRegExp → QRegularExpression）。

三条建议。读源码比读教程快，Qt 装完 Qt/5.x/Src 里有全部源码，QFile 就两千行，读一遍比看十篇文章值。示例目录是最好的文档，Qt/5.x/Examples 里几百个能编译能跑的项目，遇到「怎么用」先去里面 grep。别追新版本，Qt5 的 LTS（5.15）现在仍在大量项目里跑，资料最全；Qt6 除了编码和正则的改动，绝大部分 API 一样。

最后一句：教程里的代码都是「能跑」的水平，不是「能交付」的水平。能交付的那部分——权限、异常路径、日志、恢复——本篇讲完了骨架，剩下靠你在真实项目里被 bug 打几次。

# 易错点 症状 正解
1 open() 返回值丢掉 界面空白，一保存覆盖掉原文 if (!f.open(...))
2 写完不 flush 程序崩了内容丢一半 out.flush() 加 close()
3 不设编码 中文乱码，跨机器不一致 in.setCodec("UTF-8")
4 WriteOnly 直接覆盖 写一半失败，原文件成空 QSaveFile 加 commit()
5 往 .qrc 里写 open(WriteOnly) 永远失败 资源只读，改走文件系统
6 改了资源里的图不重编 界面还是旧图 重新构建或删构建目录
7 .qrc 没挂进项目 Choose Resource 里是空的 RESOURCES += res.qrc
8 资源路径前缀写错 :/icons//new.png 找不到 对照 prefix 和 alias
9 用户数据写在 exe 旁 装到 Program Files 后存不了 QSettings 与 QStandardPaths
10 QSettings 不给默认值 窗口缩成一条线 value(key, 默认值)
11 beginGroup 漏 endGroup 键全跑到错误前缀下 成对写，中途别 return
12 IniFormat 父目录不存在 配置写不进去且不报错 先 QDir().mkpath()
13 改组织名／应用名 老用户配置全丢 发布后名字别动
14 槽名拼错 点菜单没反应，不报错 核对 on_<objectName>_<signal>
15 忘写 Q_OBJECT 运行时找不到信号槽 类声明里加上
16 closeEvent 不 ignore() 取消保存后窗口照样关 event->ignore(); return;
17 clear() 后没清 modified 标题一直挂星号 document()->setModified(false)
18 标题没写 [*] setWindowModified 无效果 tr("%1[*] - 标题")
19 用 setText 读纯文本 <b> 之类被当标签吃掉 setPlainText
20 异常处理写不全 槽里逃出异常，或只 catch 已知类型 槽内就地 catch，末尾加 catch (...)
21 错误只 qDebug 不提示 用户以为操作成功了 日志与提示两条路都走
