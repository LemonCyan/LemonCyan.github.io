这是 9 篇 Qt5 入门教程的第六篇。前面五篇做的是「摆好就不动」的活儿：控件、布局、容器、算法、模型视图。这一篇换一类问题——等。定时器等时间到，网络等数据到。两件事看着无关，底座是同一个东西：Qt 的事件循环。

本篇讲什么：QTimer 的三种用法、单次与重复触发的区别、精度边界；TCP 与 UDP 的分工、QTcpServer / QTcpSocket / QUdpSocket 的写法、广播与组播、TCP 粘包怎么处理。不讲什么：HTTP 客户端（那是 QNetworkAccessManager 的活）、SSL/TLS、线程同步原语的细节、异步框架的架构设计。

跨篇指路：事件循环本身在第一篇《Qt 入门与信号槽》里讲过 exec() 三件套，本篇只补它跟定时器、套接字的关系；收到的字节怎么解析成文本、怎么读 XML，看第七篇《文本流与 XML》；服务端程序怎么拆工程、怎么打包发布，看第九篇《工程实践》。

一、定时器与事件循环 #

先把一件事钉死：QTimer 不是闹钟，也不是线程。

它只做两件事——记住一个毫秒数，到期后往当前线程的事件队列里塞一个定时器事件。真正把 timeout() 发出来的是事件循环。循环跑到那一条，才会调用你连上去的槽。

text
timer->start(1000)
   │
   ▼
底层定时器记着 1000ms
   │  到点
   ▼
事件队列里多一条 QTimerEvent
   │
   ▼
QCoreApplication::exec() 取事件、派发
   │
   ▼
QTimer 发出 timeout()
   │
   ▼
你的槽函数被调用

这条链上任何一环断了，timeout() 都不会来。最容易断的是倒数第二环：没有 exec()。

cpp
// 反例：没有 exec()，timeout() 一次也不会发
#include <QCoreApplication>
#include <QTimer>
#include <QDebug>

int main(int argc, char *argv[])
{
    QCoreApplication a(argc, argv);
    QTimer timer;
    QObject::connect(&timer, &QTimer::timeout, [](){
        qDebug() << "永远不会打印";
    });
    timer.start(1000);
    return 0;        // 直接退出，事件循环根本没跑起来
}

程序几乎瞬间结束，控制台一行都没有。不是 start() 失败，是没人派发那个事件。

第二种断法更隐蔽：exec() 在跑，但被你的代码堵住了。

cpp
// 反例：在槽里干重活，把事件循环堵死
QObject::connect(&timer, &QTimer::timeout, [&](){
    QThread::sleep(3);    // 这三秒里界面卡死，别的定时器全部迟到
});

事件循环是单线程排队的。谁在里面睡三秒，所有事件一起等三秒。定时器、网络、重绘、鼠标点击，全在同一支队伍里。

三个角色分清：QTimer 只管记间隔、到期往队列投一条，不新开线程，也不打断你正在跑的代码；exec() 从队列取事件、派发，它不抢占、不插队，不管你跑多久；timeout() 只保证「不早于」，不保证准时——它可以晚很多，晚多少看队列前面排了多少活。

还有一条容易踩：QTimer 属于创建它的那个线程。在 A 线程 new 的定时器，只在 A 线程的事件循环里工作。扔到 B 线程去 start()，它不会触发——除非 B 线程自己也跑了 exec()。这条规律对套接字同样成立，第十章再用一次。

二、QTimer 的三种用法 #

Qt 给了三条路，别看到定时器就只想到 new QTimer。

用法 写法 适合什么场景
单次触发 QTimer::singleShot(ms, ...) 延迟做一件事，做完就完
成员定时器 new QTimer(this) + connect + start() 周期任务，随时改间隔、随时停
定时器事件 startTimer(ms) + 重写 timerEvent() 类里已有事件处理，不想多一个对象

先看第二种，最常见的那个。下面这个类来自本系列的旧稿，结构保留，破损处补全。

mytimer.h：

cpp
#ifndef MYTIMER_H
#define MYTIMER_H

#include <QObject>
#include <QTimer>

// 想用信号槽，任何类都必须是 QObject 的派生类
class MyTimer : public QObject
{
    Q_OBJECT        // 用信号槽的类，这个宏必须写在这个类里
public:
    MyTimer();

public slots:
    void MySlots();       // 公有的槽

private:
    QTimer *timer;
};

#endif // MYTIMER_H

mytimer.cpp：

cpp
#include "mytimer.h"
#include <QDebug>

MyTimer::MyTimer()
{
    // QTimer 提供重复触发和单次触发两种定时器，是高层接口
    timer = new QTimer(this);   // 传 this，父对象析构时自动删掉它
    // 到达设定间隔时发 timeout()，连到我们的槽
    connect(timer, SIGNAL(timeout()), this, SLOT(MySlots()));
    timer->start(1000);         // 单位毫秒，1000 就是每秒一次
}

void MyTimer::MySlots()
{
    qDebug() << "TimerExecuted";   // 控制台每秒打一行提示
}

main.cpp：

cpp
#include <QCoreApplication>
#include "mytimer.h"

int main(int argc, char *argv[])
{
    QCoreApplication a(argc, argv);
    MyTimer timer;
    return a.exec();      // 事件循环跑起来，定时器才开始工作
}

.pro 里核心模块就够，控制台程序不要 GUI：QT += core、QT -= gui、CONFIG += console c++11，再列上 SOURCES 和 HEADERS。

跑起来，控制台每间隔一秒输出一行 TimerExecuted。用 QCoreApplication 而不是 QApplication——没有窗口，启动更快，体积也小。

第二种用法的本事都在那几个成员上：start(ms) 启动（对运行中的定时器再调一次是重置计时，不是叠加）、stop() 停下、isActive() 查状态、setInterval() 改间隔、remainingTime() 读剩余、setSingleShot() 改单次、setTimerType() 改精度档位。

第一种用法，单次延迟。为了等一次而 new 一个 QTimer 太啰嗦：

cpp
QTimer::singleShot(1000, [](){ qDebug() << "一秒后只来一次"; });      // 无上下文
QTimer::singleShot(1000, this, SLOT(onTimeout()));                   // 老写法
QTimer::singleShot(1000, this, [this](){ doSomething(); });          // Qt 5.4 起带上下文

带上下文的重载防的是「对象已析构，回调还在跑」。Lambda 不挂在对象树上，上下文对象补上这层保护。

第三种，重写 timerEvent()。QObject 自己就带定时器能力：

cpp
class Poller : public QObject
{
    Q_OBJECT
public:
    Poller() { m_id = startTimer(500); }     // 返回定时器 id，不是对象

protected:
    void timerEvent(QTimerEvent *e) override
    {
        if (e->timerId() == m_id)
            qDebug() << "500ms 到了";
        else
            QObject::timerEvent(e);          // 不是自己的，交回父类
    }

private:
    int m_id = 0;
};

要点三条：startTimer() 返回 int id，没有对象可以 delete；一个类起了多个定时器时，事件全进同一个 timerEvent()，靠 timerId() 区分，那个 if 不能省；不要了 killTimer(m_id)，对象析构时会自动清掉自己的定时器。

三种用法怎么挑：只延迟一次用 singleShot；周期任务要能在运行时停、改间隔，用成员 QTimer；类里已有一堆事件处理，顺手用 startTimer 最省事。

三、单次与重复触发 #

QTimer 默认重复触发。start(1000) 之后每秒一次，一直不停，直到 stop() 或者对象没了。

要单次，两条路：

cpp
QTimer t;
t.setSingleShot(true);
t.start(1000);        // 一秒后触发一次，之后自动停，isActive() 变 false

QTimer::singleShot(1000, ...);   // 压根不留对象，一次性

区别在生命周期。singleShot 适合「过一会儿做一件事」，成员 QTimer 适合「这件事我要重复做，只是现在先来一次」。

这里有个常被误解的点：对正在跑的定时器再 start()，不是叠加，是重置。

cpp
QTimer t;
t.start(1000);    // 0ms 时开始计时
// …500ms 后…
t.start(1000);    // 计时清零重来，下一次触发在 1500ms，不是 1000ms

restart() 是这句的语义化写法，等价于 stop() 加 start()。写「超时就重新计时」的逻辑，用它更清楚。

单次定时器配合重新 start()，是实现有限次重试的常见写法：

cpp
class Retryer : public QObject
{
    Q_OBJECT
public:
    explicit Retryer(QObject *parent = nullptr) : QObject(parent)
    {
        m_timer = new QTimer(this);
        m_timer->setSingleShot(true);              // 下一次触发由我们自己排
        connect(m_timer, &QTimer::timeout, this, &Retryer::tryOnce);
    }
    void start(int maxTimes = 3) { m_left = maxTimes; m_timer->start(500); }

private slots:
    void tryOnce()
    {
        if (doRequest()) return;                   // 成功了就不再来
        if (--m_left > 0) m_timer->start(1000);    // 单次定时器，重新起一次
    }

private:
    QTimer *m_timer;
    int m_left = 0;
};

为什么不用「重复定时器 + 计数器」？因为重试间隔往往要变（退避），而且间隔该从「上一次处理完」算起。重复定时器是固定节拍，处理慢了就堆积。

堆积这件事值得单说。重复定时器的语义是「每隔 N 毫秒尝试触发一次」，如果回调耗时超过 N，事件会在队列里排队，表现是回调连着跑，节奏全乱。要严格串行，改成单次 + 末尾重新 start()：

cpp
void onTimeout()
{
    doTheJob();              // 干多久都行
    m_timer->start(1000);    // 干完了再排下一次
}

代价是实际周期变成「1000ms + 干活耗时」，好处是永远不堆积。start() 对运行中的定时器是重置计时，stop() 之后对象还在、还能再 start()，setSingleShot(true) 则会在触发一次后自动变 false。

四、定时器的精度 #

到现在我们都在说「一秒一次」。真实情况是：不精确。

Qt 把精度分成三档，用 setTimerType() 选：

类型 行为 开销 什么时候用
Qt::PreciseTimer 尽量准，毫秒级靠拢 高，唤醒次数多 动画节奏、采样、短间隔循环
Qt::CoarseTimer 默认值，允许 5% 误差，时间点对齐到整毫秒 中 绝大多数业务定时
Qt::VeryCoarseTimer 只按整秒对齐，Qt 5.4 起才有 低，省电 十几分钟一次的清理、心跳

算笔账：start(1000) 用默认 CoarseTimer，5% 容差就是 950ms 到 1050ms 都算合规。加上回调在队列里排队的时间，间隔还能更散。

误差有四个来源：CoarseTimer 的 5% 容差让间隔天生带抖动；事件队列排队，前面有重活你就等着；回调自身耗时，把周期任务的实际节拍拉长；系统省电策略，睡眠降频时定时器整体变慢。

cpp
QTimer t;
t.setTimerType(Qt::PreciseTimer);
t.start(1000);

所以别拿定时器当秒表。要算「从开始到现在过了多少」，用 QElapsedTimer：start() 起算，elapsed() 读毫秒数。做倒计时显示就按它反推，别自己累加 interval()——累加一分钟，名义值和实际的差距会稳定往上爬。

还有一条判断线：低于 10ms 的节奏控制，定时器不是合适的工具。它受操作系统调度管，抖动轻松到几毫秒。真要微秒级，得上硬件定时器、实时内核或者采集卡，那不在这篇的范围。

五、TCP 与 UDP 的分工 #

写网络代码之前先选协议。选错了，后面写多少行都白搭。

一句话的分界线：丢一条数据，你的业务会不会出错。会，就用 TCP；不会，就用 UDP。

维度 TCP UDP
连接 三次握手建连，双向，长期保持 无连接，拿地址端口直接发
可靠性 确认、重传、校验，丢了会补 丢了就是丢了，不补
顺序 按发送顺序交付 不保证，会乱序
消息边界 没有，是字节流，应用层自己拼帧 有，一次一个数据报
单包上限 不设限，靠流式传输 一条约 65507 字节，还受 MTU 影响
头部开销 20 字节起，加确认与重传 8 字节，没有握手
拥塞控制 有，网络差时自动降速 没有，你发多快就多快
Qt 里的类 QTcpServer + QTcpSocket QUdpSocket
典型用途 文件传输、HTTP、数据库、登录、指令下发 设备发现、音视频、游戏状态同步、DNS、日志上报

几个具体判断。局域网里找设备，一条广播出去谁在谁应答，丢了下一次再发——UDP 的场子，TCP 做不到「一次问所有人」。给设备发「关机」指令，丢了要重发，重复执行出问题，顺序不能乱——TCP。实时音视频丢一帧人眼看不出来，补一帧的延迟立刻让人不适——UDP，宁可花屏不要卡。

麻烦也不同。TCP 有粘包、半包、断线重连；UDP 有丢包、乱序、重复。两边都得写代码，没有白捡的便宜。

地址先记住这几个写法：

写法 含义
QHostAddress::Any 所有网卡，IPv4 和 IPv6 都听
QHostAddress::AnyIPv4 只 IPv4 的所有网卡
QHostAddress::LocalHost 只有回环，外部连不进来
QHostAddress::Broadcast 广播地址 255.255.255.255
QHostAddress("192.168.1.10") 指定某个地址

端口 0 到 65535。1024 以下的端口系统保留，Linux 上要权限才能绑；0 表示「随便给我一个」，绑完用 localPort() 问实际值。

本篇用到的类，先摆一张对照：

类 角色 头文件 关键信号
QTcpServer 监听端口、接受连接，不管收发 <QTcpServer> newConnection()
QTcpSocket 一条 TCP 连接，两端都用它 <QTcpSocket> connected / readyRead / disconnected / error
QUdpSocket 收发数据报 <QUdpSocket> readyRead
QHostAddress IP 地址 <QHostAddress> 无

.pro 少一行就编不过：

QT += core network

漏掉时常见报错是 fatal error: QTcpSocket: No such file or directory。看到这个先翻 .pro，别怀疑头文件路径。

六、QTcpServer：服务端 #

QTcpServer 只做一件事：监听端口，把进来的连接交给你。它不负责收发。每个连接都是一个 QTcpSocket，读写在那边做。

myserver.h：

cpp
#ifndef MYSERVER_H
#define MYSERVER_H

#include <QObject>
#include <QDebug>
#include <QTcpServer>
#include <QTcpSocket>

class MyServer : public QObject
{
    Q_OBJECT
public:
    explicit MyServer(QObject *parent = nullptr);

public slots:
    void newConnection();      // 有客户端连进来
    void onReadyRead();        // 某个客户端发了数据

private:
    // 能接受传入的 TCP 连接。端口可以指定，也可以让 QTcpServer 自动选；
    // 地址可以只听一个网卡，也可以听全部网卡
    QTcpServer *server;
};

#endif // MYSERVER_H

myserver.cpp：

cpp
#include "myserver.h"

MyServer::MyServer(QObject *parent) : QObject(parent)
{
    server = new QTcpServer(this);

    // 每当一个新连接建立，newConnection() 信号就发出来。
    // 这里信号和槽同名，但不是同一件东西：左边是 QTcpServer 的信号，右边是我们的槽
    connect(server, SIGNAL(newConnection()), this, SLOT(newConnection()));

    // listen() 告诉服务器监听按地址或端口传入的连接。端口给 0 就自动选；
    // 地址给 QHostAddress::Any 就监听所有网络接口。成功返回 true，失败返回 false
    if (!server->listen(QHostAddress::Any, 1234)) {
        qDebug() << "Server could not start!";
    } else {
        qDebug() << "Server started on port" << server->serverPort();
    }
}

void MyServer::newConnection()
{
    // 一次会同时进来好几个连接，while 取干净
    while (server->hasPendingConnections()) {
        // nextPendingConnection() 把下一个挂起的连接以 QTcpSocket 对象的形式返回
        QTcpSocket *socket = server->nextPendingConnection();

        qDebug() << "client:" << socket->peerAddress().toString()
                 << socket->peerPort();

        connect(socket, &QTcpSocket::readyRead, this, &MyServer::onReadyRead);
        // 对端断开后 socket 归我们管，交给 deleteLater 按计划删
        connect(socket, &QTcpSocket::disconnected, socket, &QTcpSocket::deleteLater);

        socket->write("hello from Qt server\r\n");
        socket->flush();          // 刷新缓冲，把数据推出去
    }
}

void MyServer::onReadyRead()
{
    // 多个 socket 共用一个槽，靠 sender() 找回是谁
    QTcpSocket *socket = qobject_cast<QTcpSocket *>(sender());
    if (!socket) return;

    QByteArray data = socket->readAll();
    qDebug() << "recv from" << socket->peerPort() << ":" << data;
    socket->write("echo: " + data);       // 原样回一份
}

main.cpp 里 new 一个 MyServer，然后 return a.exec();。少一行 exec()，newConnection() 永远不来。

验证：命令行敲 telnet 127.0.0.1 1234，或者 nc 127.0.0.1 1234。连上敲几个字回车，服务端打出 client: ...，数据用 readAll() 取，写法和第七章客户端一样。Windows 10 默认没装 telnet 客户端，在「启用或关闭 Windows 功能」里勾一下。

listen() 失败九成是端口被占、权限不够，或者地址写错。地址写 LocalHost 时外部机器连不进来，这个坑最常见。原因看 errorString()。

QTcpServer 的常用成员：

成员 作用
listen(addr, port) / isListening() 开始监听 / 是否在听
serverAddress() / serverPort() 实际绑上的地址和端口
hasPendingConnections() / nextPendingConnection() 有没有没取走的 / 取一个
setMaxPendingConnections(int) 挂起队列上限，默认 30
close() / errorString() 停止监听（已建连接不受影响）/ 失败原因

最容易忽略的是那个「默认 30」：只 listen() 却从不调 nextPendingConnection()，连接会一直挂在队列里，攒满 30 个系统就不再接受，客户端看着像连不上，服务端一点报错都没有。

上面那个版本，所有客户端挤在一个事件循环里，一个客户端处理慢了大家互相拖。要隔离就换每连接一个线程的版本，旧稿给过，这里补全。

思路：从 QTcpServer 派生，重写 incomingConnection()，每来一个连接开一条线程，把描述符交给线程里的 QTcpSocket。

cpp
// myserver.h
#ifndef MYSERVER_H
#define MYSERVER_H

#include <QTcpServer>
#include <QDebug>
#include "mythread.h"

class MyServer : public QTcpServer
{
    Q_OBJECT
public:
    explicit MyServer(QObject *parent = nullptr);
    void startServer();

protected:
    // Qt 5 的参数类型是 qintptr，Qt 4 是 int，抄错类型编不过
    void incomingConnection(qintptr socketDescriptor) override;
};

#endif // MYSERVER_H

cpp
// myserver.cpp
#include "myserver.h"

MyServer::MyServer(QObject *parent) : QTcpServer(parent) {}

void MyServer::startServer()
{
    if (!this->listen(QHostAddress::Any, 1234))
        qDebug() << "Could not start server";
    else
        qDebug() << "Listening on 1234 ...";
}

void MyServer::incomingConnection(qintptr socketDescriptor)
{
    qDebug() << socketDescriptor << "Connecting...";

    MyThread *thread = new MyThread(socketDescriptor, this);
    // 线程处理完毕发 finished()，用它把线程对象按计划删掉
    connect(thread, &QThread::finished, thread, &QObject::deleteLater);
    thread->start();      // 启动线程，进入 run()
}

cpp
// mythread.h
#ifndef MYTHREAD_H
#define MYTHREAD_H

#include <QThread>
#include <QTcpSocket>

class MyThread : public QThread
{
    Q_OBJECT
public:
    explicit MyThread(qintptr ID, QObject *parent = nullptr);
    void run() override;

signals:
    void error(QTcpSocket::SocketError socketError);   // 出错把错误码递出去

private slots:
    void readyRead();
    void disconnected();

private:
    QTcpSocket *socket;
    qintptr socketDescriptor;      // 不同 socket 的标志
};

#endif // MYTHREAD_H

cpp
// mythread.cpp
#include "mythread.h"
#include <QDebug>

MyThread::MyThread(qintptr ID, QObject *parent)
    : QThread(parent), socketDescriptor(ID) {}

void MyThread::run()
{
    // 线程从这里开始跑
    qDebug() << socketDescriptor << "Starting thread";

    socket = new QTcpSocket();      // 必须在线程里 new，socket 才属于这条线程

    if (!socket->setSocketDescriptor(socketDescriptor)) {
        emit error(socket->error());
        return;
    }

    // DirectConnection：槽在发信号的线程里直接跑，也就是这条工作线程
    connect(socket, &QTcpSocket::readyRead,
            this, &MyThread::readyRead, Qt::DirectConnection);
    connect(socket, &QTcpSocket::disconnected,
            this, &MyThread::disconnected, Qt::DirectConnection);

    exec();      // 线程内部也要有事件循环，否则 readyRead 永远不会来

    socket->deleteLater();
}

void MyThread::readyRead()
{
    QByteArray data = socket->readAll();
    qDebug() << socketDescriptor << "recv:" << data;
    socket->write(data);
}

void MyThread::disconnected()
{
    socket->deleteLater();
    quit();      // 退出 exec()，让 finished() 发出去
}

exec() 那一行是全篇的关键之一。QThread::run() 默认什么都不做，切进去就退出，除非你在里面自己跑事件循环。没有 exec()，readyRead() 一次也不会触发，只能靠 waitForReadyRead() 硬等——那又回到阻塞的老路。

两种结构怎么挑：连接几十个、报文处理很快，单事件循环够用，代码也少；连接上百、单个请求耗时长，或者要调阻塞库，就每连接一线程，代价是多线程的生命周期和竞争自己盯。再往上一档是线程池和事件驱动框架，不在这篇。

七、QTcpSocket：连接与收发 #

QTcpSocket 是连接本身。客户端用它连服务端，服务端的每个连接也是它。同一个类，两种角色。

cpp
class TcpClient : public QObject
{
    Q_OBJECT
public:
    explicit TcpClient(QObject *parent = nullptr) : QObject(parent)
    {
        m_socket = new QTcpSocket(this);
        connect(m_socket, &QTcpSocket::connected,    this, &TcpClient::onConnected);
        connect(m_socket, &QTcpSocket::readyRead,    this, &TcpClient::onReadyRead);
        connect(m_socket, &QTcpSocket::disconnected, this, &TcpClient::onDisconnected);
        connect(m_socket,
                QOverload<QAbstractSocket::SocketError>::of(&QTcpSocket::error),
                this, &TcpClient::onError);
    }
    void connectTo(const QString &host, quint16 port)
    {
        m_socket->connectToHost(host, port);   // 立刻返回，不等连接建成
    }

private slots:
    void onConnected()    { qDebug() << "连上了"; m_socket->write("hello\r\n"); }
    void onReadyRead()    { m_buf += m_socket->readAll(); }   // 先攒着，拆帧看第十一章
    void onDisconnected() { qDebug() << "对端断开"; }
    void onError(QAbstractSocket::SocketError e)
    {
        qDebug() << "错误码" << e << m_socket->errorString();
    }

private:
    QTcpSocket *m_socket;
    QByteArray m_buf;
};

connectToHost() 是异步的，调用完立刻返回，建好连接才发 connected()。后面一行立刻写数据是错的，必须等信号。

读、写、状态三组 API：

分组 成员 说明
连接 connectToHost(host, port) 发起连接，异步
disconnectFromHost() / abort() 正常断开（发完缓冲再关）/ 立刻断
state() UnconnectedState → HostLookupState → ConnectingState → ConnectedState → ClosingState
读 readyRead() 信号 / bytesAvailable() 有新数据 / 缓冲里有多少
readAll() / read(n) 全取 / 取 n 字节
readLine() / canReadLine() 按行取，需要 \n 结尾
写 write(data) 塞进发送缓冲，返回入队字节数
bytesToWrite() / flush() 还有多少没发 / 尽量推给系统
waitForBytesWritten(ms) 阻塞等写出去
信息 peerAddress() / peerPort() 对端地址端口
localPort() / errorString() 本端端口 / 最近一次错误

write() 的返回值不是「已经发出去多少」，是「塞进队列多少」。真正发送在后台，靠事件循环推。别拿它判断对端收没收到。

错误信号有个版本坑。Qt 5.15 之前叫 error(QAbstractSocket::SocketError)，5.15 起新增 errorOccurred()，因为 error() 和同名的取值函数撞了。要兼容就用上面那个 QOverload<...>::of(&QTcpSocket::error)；只跑新版本就直接连 errorOccurred。

服务端的 disconnected() 一定要处理：对端断了，这个 QTcpSocket 就没人用了，得 deleteLater()。

八、QUdpSocket：无连接传输 #

UDP（用户数据报协议）是轻量的、不可靠的、面向数据报的、无连接的协议。可靠性不重要时用它。跟 TCP 比，它不保证送达、不保证顺序，但省掉握手和确认，发小数据报很划算。

myudp.h：

cpp
#ifndef MYUDP_H
#define MYUDP_H

#include <QObject>
#include <QDebug>
#include <QUdpSocket>
#include <QHostAddress>

class MyUDP : public QObject
{
    Q_OBJECT
public:
    explicit MyUDP(QObject *parent = nullptr);
    void SayHello();

public slots:
    void ReadyRead();

private:
    QUdpSocket *socket;
};

#endif // MYUDP_H

myudp.cpp：

cpp
#include "myudp.h"

MyUDP::MyUDP(QObject *parent) : QObject(parent)
{
    socket = new QUdpSocket(this);
    // 绑到本机回环地址的 1234 端口，才能收到这个端口上的数据报
    socket->bind(QHostAddress::LocalHost, 1234);
    connect(socket, SIGNAL(readyRead()), this, SLOT(ReadyRead()));
}

void MyUDP::SayHello()
{
    QByteArray Data = "Hello";
    // writeDatagram() 按一定尺寸向指定地址端口发送数据报
    socket->writeDatagram(Data, QHostAddress::LocalHost, 1234);
}

void MyUDP::ReadyRead()
{
    QByteArray Buffer;
    // 先问第一个挂起的数据报有多大，再分配缓冲
    Buffer.resize(socket->pendingDatagramSize());

    QHostAddress sender;      // 发送方地址
    quint16 senderPort;       // 发送方端口

    // 读一条，sender / senderPort 由 readDatagram 回填
    socket->readDatagram(Buffer.data(), Buffer.size(), &sender, &senderPort);

    // 输出接收到的数据报的信息
    qDebug() << "Message from:" << sender.toString() << "port:" << senderPort;
    qDebug() << "Message:" << Buffer;
}

main.cpp：

cpp
#include <QCoreApplication>
#include "myudp.h"

int main(int argc, char *argv[])
{
    QCoreApplication a(argc, argv);
    MyUDP client;      // 一个对象既是发送端也是接收端
    client.SayHello();
    return a.exec();   // 没有它，readyRead 不会来
}

这个例子自己发给自己：SayHello() 往 127.0.0.1:1234 发，同一端口绑着的 socket 收到，走 ReadyRead()，控制台打出 Hello 和来源地址端口。

readDatagram 有三个容易写错的地方。pendingDatagramSize() 必须在 readDatagram() 之前问，读完复位成 -1。缓冲区要够大，小了会被截断，返回值告诉你实际读了多少。地址和端口的指针可以传 nullptr，不关心就不传。

一次 readyRead() 只说明「有新数据报到了」，不代表只有一条。跟 TCP 一样要循环取干净：while (socket->hasPendingDatagrams()) 里反复 pendingDatagramSize() 加 readDatagram()，直到 hasPendingDatagrams() 为假。Qt 5.8 起还有个更省事的 receiveDatagram()，直接把数据连同来源打包成 QNetworkDatagram，省掉三个参数。

旧稿的结论是「实际应用多数用 TCP，UDP 了解即可」。放到设备发现、局域网通知、音视频这几类场景，这句得改：UDP 不是配角，它解决的是 TCP 解决不了的问题——一次问所有人。

九、广播与组播 #

一台机器要给局域网里所有设备发消息，没法一个个去连。两条路：广播和组播。

广播最粗。255.255.255.255 是全局广播，192.168.1.255 是某网段的定向广播。广播不跨路由器，出不了本网段。

cpp
QUdpSocket sender;
qint64 n = sender.writeDatagram("DISCOVER:anyone?", QHostAddress::Broadcast, 45454);
if (n == -1) qDebug() << "send failed:" << sender.errorString();

// 接收端绑到所有网卡的同一端口
QUdpSocket recver;
recver.bind(QHostAddress::AnyIPv4, 45454);

发出去没人收，先查三件事：防火墙放行没有、接收端 bind 的地址是不是 AnyIPv4（绑成 LocalHost 就只收本机）、两台机器在不在同一网段。

组播比广播省。它只发给「声明过要听这个组」的机器，交换机也只在需要的端口转发。地址在 224.0.0.0 到 239.255.255.255 之间，本地管理用 239.0.0.0/8。

cpp
// 接收端：绑定 + 加入组播组
QUdpSocket recver;
recver.bind(QHostAddress::AnyIPv4, 45454, QUdpSocket::ShareAddress);
recver.joinMulticastGroup(QHostAddress("239.255.43.21"));

// 发送端：TTL 决定能过几个路由器
QUdpSocket sender;
sender.setSocketOption(QAbstractSocket::MulticastTtlOption, 1);   // 1 = 只在本网段
sender.writeDatagram("PING", QHostAddress("239.255.43.21"), 45454);

ShareAddress 不能省。同一台机器上多个进程听同一个端口时，默认第二个 bind 失败，加上它才能共享。TTL 那行也别忘，默认是 1，够局域网用；调到 32 能跨几跳，再大要看网络设备给不给过。

维度 广播 组播
目标 本网段所有主机 加入该组的主机
地址 255.255.255.255 或定向广播 224.0.0.0 – 239.255.255.255
跨路由器 不能 可以，看 TTL 和设备配置
接收端要求 绑对端口就行 必须 joinMulticastGroup
网段开销 人人有份，都得分拣 只有交换机相关端口转发
典型用途 设备发现、DHCP、局域网通知 视频流、行情推送、集群心跳

不再收听就 leaveMulticastGroup(addr)。不退出不致命，但网卡会一直收着那组流量。

十、网络编程的异步模型 #

到这里可以把前面两半合起来了。QTcpSocket、QUdpSocket 全是非阻塞的，读写都靠事件循环发信号。readyRead() 就是网络版的 timeout()。

所以第一章那句话再念一遍：在不跑 exec() 的线程里，定时器和套接字都不工作。

cpp
class Worker : public QThread
{
    void run() override
    {
        QTcpSocket s;
        s.connectToHost("127.0.0.1", 1234);
        // 没有 exec()，readyRead 永远不会来
        s.waitForReadyRead(3000);   // 只能靠阻塞函数硬等
    }
};

waitForConnected、waitForReadyRead、waitForBytesWritten 这些是同步版，只在命令行工具或者非 GUI 线程里用。主线程里调 waitForConnected(3000)，界面就冻住三秒——这三秒里事件循环一步也走不动。

要让网络在后台跑又不想碰阻塞，正路是 worker 对象加 moveToThread：

cpp
class NetWorker : public QObject
{
    Q_OBJECT
public slots:
    void start() { m_socket = new QTcpSocket(this); /* 再 connect + connectToHost */ }
private slots:
    void onReadyRead() { qDebug() << m_socket->readAll(); }
private:
    QTcpSocket *m_socket = nullptr;
};

QThread thread;
NetWorker *w = new NetWorker;
w->moveToThread(&thread);                             // 对象搬家
connect(&thread, &QThread::started, w, &NetWorker::start);
thread.start();      // 线程的默认 run() 自带 exec()，信号能送到 w 的槽

四种做法各有场合：主线程连信号、异步收发，是 GUI 程序的默认选择；主线程 waitForXxx()，只适合一次性脚本和命令行工具；子类化 QThread 在 run() 里跑 exec()，适合每连接一个 socket 的服务端；worker 对象加 moveToThread，适合后台长跑的网络逻辑，也是这份清单里我推荐的那个。

moveToThread 的规矩：只能在对象没有父对象时搬；搬完它的事件处理全在新线程；QThread 对象本身还留在原来的线程，别把它的槽当成工作线程的槽。

十一、粘包与数据完整性 #

TCP 最容易栽的地方在这。发送端 write("ABC") 再 write("DEF")，接收端收到的有时是 ABCDEF 一次 readyRead()，有时是 AB 和 CDEF 两次，有时是 ABCD 加 EF。TCP 只保证字节顺序，不保证按你的写入边界交付。

readyRead() 的意思只有一句：读缓冲区里有新数据了。它不告诉你「有几条消息」。

三条铁律：不要假设一次 readyRead() 就是一条消息；不要把 readAll() 的返回值当成一条完整消息；每次 readyRead() 都先往自己的缓冲里追加，再循环从中取整帧。

拼帧方案三选一：

方案 做法 能否传二进制 典型协议
长度前缀 先发 4 字节长度，再发载荷 能 多数私有二进制协议
分隔符 每条以 \n 或 \r\n 结尾 不能，载荷里不能有分隔符 文本协议、telnet、SMTP
定长 每条固定 N 字节 能 简单的定长报文

长度前缀最通用。发送端：

cpp
void sendFrame(QTcpSocket *s, const QByteArray &payload)
{
    QByteArray block;
    QDataStream out(&block, QIODevice::WriteOnly);
    out.setVersion(QDataStream::Qt_5_12);
    out << quint32(0) << payload;              // 长度先占位
    out.device()->seek(0);
    out << quint32(block.size() - sizeof(quint32));   // 回填真实长度
    s->write(block);
}

接收端，成员里留一个 QByteArray m_buf：

cpp
void onReadyRead()
{
    m_buf += m_socket->readAll();              // 先全部收下

    while (m_buf.size() >= int(sizeof(quint32))) {
        QDataStream in(&m_buf, QIODevice::ReadOnly);
        in.setVersion(QDataStream::Qt_5_12);
        quint32 len = 0;
        in >> len;
        if (len > 8 * 1024 * 1024) { m_buf.clear(); return; }   // 上限，防被撑爆
        if (m_buf.size() < int(sizeof(quint32) + len)) return;  // 半帧，等下一次

        QByteArray payload = m_buf.mid(sizeof(quint32), len);
        m_buf.remove(0, sizeof(quint32) + len);
        handle(payload);                       // 拿到完整一帧了
    }
}

分隔符方案更适合文本，短得多：往成员缓冲里追加 readAll()，indexOf('\n') 找切点，切出一条就 remove 掉，循环到找不着为止。收到的行末尾带 \r 就 chop(1)，兼容 \r\n。

QTcpSocket 自带 canReadLine() 加 readLine()，能直接按行取。但别和 readAll() 混用——两者争同一个读缓冲，混着用必丢数据。选一个，一路走到底。

那条长度上限不能省。对端只要发个 0xFFFFFFFF，你不校验就 resize，内存当场炸掉。

UDP 这边不用拼帧，一次 readDatagram() 就是一条完整报文，边界天然存在。代价是它会丢、会乱序、会重复，要可靠就在应用层自己做序号、确认和去重。

十二、易错点速查 #

现象 原因 改法
定时器完全不触发 没跑 exec()，或对象所在线程没事件循环 在主线程建，或在那个线程起 exec()
定时器触发但界面卡死 回调里做了耗时操作 拆成单次任务，或挪到工作线程
每秒一次变成 1.05 秒 CoarseTimer 的 5% 容差加回调耗时 setTimerType(Qt::PreciseTimer)，或用 QElapsedTimer 记账
listen() 返回 false 端口被占、权限不够、地址写错 看 errorString()，换端口，1024 以下要权限
只处理了第一个连接 用了 if 而不是 while while (hasPendingConnections())
客户端连不上，服务端无报错 挂起连接攒满 30 个没取走 每次都 nextPendingConnection()
readyRead 只拿到半条 TCP 粘包 应用层拼帧，长度前缀或分隔符
子类化 QThread 后 readyRead 不来 run() 里没有 exec() run() 末尾 exec()，或连 DirectConnection
worker 的槽在主线程执行 接收者 QThread 对象属于原线程 用 worker QObject + moveToThread
主线程 waitForConnected 卡界面 用了阻塞 API 只连信号，或挪到线程
QUdpSocket 收不到包 bind 地址端口不对，或防火墙 绑 AnyIPv4 加正确端口，先本机回环验证
一次 readyRead 少收几条 UDP 没循环 hasPendingDatagrams() while 取干净
广播没人收到 跨网段，或被防火墙拦 同网段验证，接收端别绑 LocalHost
组播收不到 没 joinMulticastGroup，或缺 ShareAddress 绑 AnyIPv4 + ShareAddress，再入组
客户端断开后对象泄漏 没处理 disconnected() 连到 deleteLater
编译报 QTcpSocket: No such file .pro 漏了模块 加 QT += network

定时器和套接字的共同点是：你不推它，它不动。事件循环在转，它们就转；你把循环堵住，它们全停。把这条记牢，剩下的都是查文档的活儿。
