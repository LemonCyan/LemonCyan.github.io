这篇讲什么：一个已经能跑起来的 Qt 桌面程序，怎么接上 AI 能力。分两种身份看——你自己写代码时借 AI 提效，和你的产品里给客户跑 AI。

不讲什么：不讲模型怎么训练、不讲提示词玄学、不列某年某月的模型参数排行榜。参数、体积、速度这类数字变化太快，抄进来三个月就过期，本篇只给判断方法。

跨篇指路：调云端 API 的落地细节（QNetworkAccessManager、超时、重试、JSON 解析）在《网络应用实例》里已经写过一遍，这里只点关键处不重复展开。做完了 AI 集成，接下来怎么把几百兆的东西塞进安装包看《打包分发应用》；要给本地模型文件上锁看《Qt之加密算法》与《Qt资源文件加密方案详解》；推理崩了要留证据看《Qt之日志输出文件》；上线后发现界面卡、CPU 打满看《Qt程序CPU占用率较高的解决办法》。

一、桌面程序接 AI 的三条路 #

先把话说死：桌面程序接 AI，只有两条路——调远端 API，或者本地跑模型。 第三条所谓「路」其实不算路，是开发期的事，跟你交付给客户的 exe 没关系。

三条并列着看，是为了让选型时分得清哪些是「我写代码时爽」，哪些是「用户运行时爽」。

序号 形态 跑在哪 谁受益 交付物里有没有它
1 开发期辅助：IDE 补全、终端 Agent 你的开发机 / 远端 你 没有
2 运行期调云端 API 厂商机房 你的用户 只有一个 HTTP 客户端
3 运行期本地推理 用户机器 你的用户 模型文件 + 推理库，几百兆起

前两条容易混在一起谈，其实工程上天差地别。第 1 条你不写一行集成代码，装个插件就完事；第 2、3 条你要写代码、要设计线程、要考虑打包体积，是真正的产品工作。

1.1 先认清开发期那两条 #

写代码时借 AI 提效，底层机制值得知道，因为它决定了工具能不能接你自己的私服。

Qt Creator（13.0 以后版本）原生支持 GitHub Copilot，也能接本地跑的 Ollama。这套东西的基础是 LSP（Language Server Protocol）。

LSP 干的事，说穿了就是给「语言分析逻辑」和「编辑器前端」之间拉一根通用数据总线。在没有它之前，同一套补全能力要分别给 VSCode、Qt Creator、Vim 各写一遍插件，重复劳动。有了 LSP，AST 解析、上下文联想这些重活全部挪到后端的 Server 上，前端 IDE 退化成渲染层——只负责把光标位置丢出去，再把后端吐回来的代码片渲染出来。集成 AI 的工程门槛就落到了「实现一个 Server」这一件事上。

补全请求的一条链路大致是这样：

text
Qt Creator（编辑器）
   │  当前文件内容 + 光标位置 + 上下文范围
   ▼
AI Assistant 插件
   │  组装成请求体（AST 片段、前后文、语言、候选数）
   ▼
本地 LSP / Node.js 代理进程
   │  HTTP POST，JSON，流式返回
   ▼
大模型（云端或本机 Ollama）
   │  一截一截吐 token
   ▼
代理进程解析组装 → 插件 → 编辑器渲染灰字提示

注意链路里「流式」两个字。补全要让人感觉不到等待，靠的是边生成边渲染，而不是等整个结果回来。这个思路后面在第八章会原样搬到 Qt 里。

比补全更重的是 Agent 类工具。补全只在单个文件里贴代码，Agent 会自己翻文件、自己改、自己加依赖。这一档工具的形态一直在变：

  • 网页版对话：纯问答，代码要你复制粘贴回 IDE，上下文反复断裂。
  • IDE 侧边栏/对话框：挂在环境里，能读当前工程的文件，改动要人工点确认。
  • AI 原生 IDE：多文件重写，改起来连贯，代价是整套工作流要迁移，用惯了 MSVC 或某个特定 Qt Creator 插件的老项目搬起来疼。
  • 命令行终端 Agent：无头（headless）架构，跟编辑器脱钩。

终端这一档值得单独说。它的好处是不绑定任何开发环境——你今天在全键盘 Vim 里手搓，还是在 Qt Creator 里拖 QML，只要那个终端还开着，AI 就在旁边。

举个具体场景。需求是：把 mainwindow.cpp 里读配置文件的那段同步 I/O 改成异步加载，加个加载动画，加上互斥锁防重复点击。

传统写法你要动的地方：头文件加 QMutex 成员、写新的 slot、定线程池或 QtConcurrent 任务、把进度用信号槽送回主线程、最后再改 UI 加 QProgressDialog。

用终端 Agent，一条自然语言下去：

bash
opencode "将 mainwindow 中用于读取本地配置文件的同步 I/O 改为 QtConcurrent 异步加载，读取期间界面保持响应并显示 QProgressDialog，同时用 QMutex 防止重复点击。"

它内部会走一套连贯动作：

  1. 工程索引：翻 mainwindow.h、mainwindow.cpp，顺手看 CMakeLists.txt 或 .pro 里有没有链上 Concurrent 模块。
  2. 逻辑推演与修改：挂 QMutex，把后台线程的进度通过信号槽同步回 GUI 线程，避免跨线程直接碰控件。
  3. 提交改动：全链路改完，你在 git diff 里 review。

这套机制的核心是代理自主性：它不需要你像网页版那样一行行比对差异。面对几千行没人敢动的老代码，这个心理门槛降得比技术门槛还多。

开发期的东西到此为止，剩下的篇幅全给产品运行期——你的 exe 里怎么跑 AI。

二、第一条：调云端 API #

这条路最短。你的程序不碰模型，只发 HTTP 请求，模型跑在厂商机房。

2.1 它长什么样 #

一次对话请求，本质就是一个 HTTPS POST，body 是 JSON：

text
POST https://<厂商域名>/v1/chat/completions
Authorization: Bearer <你的 Key>
Content-Type: application/json

{
  "model": "<模型名>",
  "messages": [
    {"role": "system", "content": "你是一个只回答 JSON 的助手"},
    {"role": "user",   "content": "把下面这段日志按错误级别归类"}
  ],
  "stream": true,
  "temperature": 0.2
}

这就是全部。Qt 侧需要的能力，QNetworkAccessManager 全有：

cpp
// AiClient.h —— 最小可用封装
#pragma once
#include <QObject>
#include <QNetworkAccessManager>
#include <QNetworkReply>

class AiClient : public QObject {
    Q_OBJECT
public:
    explicit AiClient(QObject* parent = nullptr) : QObject(parent) {}

    void ask(const QString& prompt) {
        QNetworkRequest req{QUrl(m_baseUrl + "/v1/chat/completions")};
        req.setHeader(QNetworkRequest::ContentTypeHeader, "application/json");
        req.setRawHeader("Authorization", "Bearer " + m_key.toUtf8());

        QJsonArray messages;
        messages.append(QJsonObject{{"role", "system"}, {"content", m_system}});
        messages.append(QJsonObject{{"role", "user"},   {"content", prompt}});

        QJsonObject body{
            {"model", m_model},
            {"messages", messages},
            {"stream", m_stream},
            {"temperature", 0.2}
        };

        QNetworkReply* reply = m_nam.post(req, QJsonDocument(body).toJson(QJsonDocument::Compact));
        connect(reply, &QNetworkReply::readyRead, this, [this, reply] {
            emit chunk(reply->readAll());   // 流式：边到边吐
        });
        connect(reply, &QNetworkReply::finished, this, [this, reply] {
            if (reply->error() != QNetworkReply::NoError)
                emit failed(reply->errorString());
            else
                emit done();
            reply->deleteLater();
        });
    }

signals:
    void chunk(const QByteArray& raw);
    void done();
    void failed(const QString& msg);

private:
    QNetworkAccessManager m_nam;
    QString m_baseUrl, m_key, m_model = QStringLiteral("your-model");
    QString m_system = QStringLiteral("你是桌面助手，回答简短。");
    bool m_stream = true;
};

上面这段是骨架。真要上线，还得补超时、重试、取消、以及 SSE 分帧的粘包处理这几件事，都在《网络应用实例》里。

厂商大致分两拨：国产这一档（GLM、MiniMax、DeepSeek、Qwen 的代码向版本）中文理解和报价都好说话，工具链对国内网络也友好；国外顶流那一档（GPT、Claude-Opus、Gemini 的高阶版本）在复杂重构上还留着一手。型号名和版本号几个月换一轮，别写进代码逻辑，做成配置文件里的字符串。

2.2 爽在哪 #

  • 不用操心算力。用户那台办公本是什么样的机器，跟你无关。
  • 模型随时能换。改字符串就行，改完重启程序，能力直接升一档。
  • 中文理解、长上下文、复杂推理都在同一档里，省了挑显卡。
  • 升级路径平坦。厂商上新模型，你填个名字。

2.3 坑在哪 #

钱。按 token 计费。用户每次点一下「分析」都在花钱，长文档一贴，token 数字蹭蹭往上走。日积月累是笔真金白银，尤其当你的程序是免费下载的时候——有人在替你付账。

网络。断网就废。用户在公司内网、在飞机上、在客户机房，说断就断。你还得处理转发代理、企业证书、SSL 中间人这类破事。

合规与隐私。这条最硬。绝大多数公司的核心业务数据不允许明文出网。客户把内部文档丢进你的软件，你的软件再把它 POST 到境外服务器——这个链条一旦被审计抓到，项目当场结束。做政企、医疗、金融的单子，这一条常常是硬性红线，不是建议。

Key 不能写死在客户端。反编译出来就是一个能刷爆你余额的凭证。正确做法是自己架一层中转网关，客户端只认你的域名，Key 留在服务端，顺便在网关做限流和审计。

三、第二条：本地推理 #

另一条路是把模型搬到用户机器上跑。你的 exe 目录里除了 Qt 的 dll，还躺着一个模型文件和一个推理库。

3.1 两条实现路线 #

C++ 里做这件事，主流就两个方向，定位完全不同：

维度 llama.cpp ONNX Runtime
定位 专做 LLM 推理的纯 C/C++ 实现 通用推理框架
依赖 零依赖，编译进去就用 一个运行时库，按需装执行后端
输入形态 文本（token 流） 文本、语音、图像、任意张量
硬件加速 CPU 为主，部分 GPU 后端 CUDA、TensorRT、DirectML、CoreML、CPU
模型格式 GGUF（自带量化档位） ONNX
体积 小，好嵌入 比 llama.cpp 大，还能再挂插件
适合谁 只做文本对话 多模态、要压硬件算力

一句话选型：只做文本对话用 llama.cpp，要跑多模态或者要压榨硬件算力用 ONNX Runtime。

这两条都不需要用户在机器上装 Python，也就不存在「打包一个 Python 环境结果 1.5G 起」的老问题。

3.2 本地跑的代价 #

  • 体积。模型文件动辄几百兆到几个 G，安装包瞬间从 30M 变成 2G。
  • 速度受硬件限制。同一份模型在老办公本和带独显的机器上差出一个数量级，这不是代码能救的。
  • 质量不如云端。开发机能跑的多是 7B 到 32B 这个量级的量化模型，碰上复杂重构容易忘上下文，也更容易一本正经地编出编译不过的代码。
  • 硬件兼容的坑。显卡驱动、指令集、内存不够，各种组合都能让推理库在用户机器上崩。

但换来的是两个东西：代码和数据不出机器，以及没有按次计费。这两点在某些项目里，比上面所有缺点加起来都值钱。

四、llama.cpp：零依赖的 C++ 方案 #

4.1 它的定位 #

llama.cpp 是专为 LLM 推理写的纯 C/C++ 实现。注意「专为 LLM」这个限定——它不做图像分类、不做语音识别，它只干一件事：给定一段 token 序列，预测下一个 token，循环下去。

这个限定换来了它的核心优势：零依赖。没有 Python 运行时，没有 protobuf，没有一堆需要跟着发布的第三方 dll。源码直接编进你的工程，产出一个静态库或者一个 dll，扔进安装目录就完事。对 Qt 项目来说，这一点极其省心——windeployqt 该怎么跑还怎么跑，不会因为多了个 AI 模块就把依赖链搞成一团乱麻。

它配套的模型格式是 GGUF：一个文件里同时装权重、词表、量化参数、对话模板元数据。单文件，直接 mmap 映射，加载不进内存也能开工。

Apple Silicon 上的 Metal 后端、x86 上的 AVX/AVX2/AVX512、部分显卡的 CUDA 后端它都有，但覆盖面和成熟度不如 ONNX Runtime 的执行后端体系。它的强项是 CPU 上跑得比你以为的快。

4.2 编进 CMake #

两种接法。一种是自己编，CMakeLists.txt 里把源码目录挂进工程（路径按你实际的第三方目录调整）：

text
set(LLAMA_BUILD_TESTS  OFF CACHE BOOL "" FORCE)
set(LLAMA_BUILD_EXAMPLES OFF CACHE BOOL "" FORCE)
set(LLAMA_BUILD_SERVER OFF CACHE BOOL "" FORCE)
add_subdirectory(third_party/llama.cpp EXCLUDE_FROM_ALL)

target_link_libraries(YourApp PRIVATE llama)

另一种更省事：官方仓库的 release 里有预编译包，直接链 .lib / .a 加头文件。缺点是编译选项（指令集、后端）你改不了，某些老 CPU 上会起不来，得靠运行时分发多份二进制。

关掉 examples 和 server 很重要。不关，你的构建时间会翻几倍，产出的中间文件也能塞满硬盘。

4.3 推理流程 #

llama.cpp 的 C API 分几层：llama_model 管权重，llama_context 管一次运行的 KV cache 和计算状态。权重加载一次就够，context 可以按会话复用。

cpp
// 简化到骨架：加载 → 拼 prompt → 逐 token 采样 → 回调
llama_backend_init();

llama_model_params mp = llama_model_default_params();
mp.n_gpu_layers = 0;                       // 纯 CPU；有 GPU 后端时按显存往上调
llama_model* model = llama_model_load_from_file(
    QFile::encodeName(modelPath).constData(), mp);
if (!model) return false;

llama_context_params cp = llama_context_default_params();
cp.n_ctx   = 4096;                         // 上下文长度，越大越吃内存
cp.n_batch = 512;
llama_context* ctx = llama_init_from_model(model, cp);

// 把 prompt 切成 token，喂进去
const llama_vocab* vocab = llama_model_get_vocab(model);
std::vector<llama_token> toks(prompt.size() + 8);
int n = llama_tokenize(vocab, prompt.toUtf8().constData(), prompt.toUtf8().size(),
                       toks.data(), (int)toks.size(), true, true);
toks.resize(n);

llama_batch batch = llama_batch_get_one(toks.data(), n);
if (llama_decode(ctx, batch) != 0) { /* 处理失败 */ }

// 自回归：每轮采一个 token，回调出去，再喂回去
for (int i = 0; i < maxNewTokens; ++i) {
    float* logits = llama_get_logits_ith(ctx, -1);
    llama_token id = llama_sampler_sample(sampler, ctx, -1);
    if (llama_vocab_is_eog(vocab, id)) break;   // 遇到结束符收工

    char buf[256];
    int len = llama_token_to_piece(vocab, id, buf, sizeof(buf), 0, true);
    if (len > 0) emit onToken(QByteArray(buf, len));   // 关键：流式吐字

    llama_batch one = llama_batch_get_one(&id, 1);
    if (llama_decode(ctx, one) != 0) break;
}

三个点要盯住：

  • onToken 是流式的。别攒完整个回答再一次性显示，用户等十秒看不到任何动静，会以为程序卡死了。
  • n_ctx 是内存开关。上下文翻倍，KV cache 跟着翻倍，在内存紧张的机器上这就是崩溃点。
  • 采样器决定「手感」。temperature 调低给代码，调高给闲聊，这属于参数活，不是工程活。

用完记得 llama_free(ctx)、llama_model_free(model)、llama_backend_free()。顺序别反，先 context 后 model。

4.4 什么时候别选它 #

  • 你要的不只是文本——语音转写、图像识别、向量化都得上，那它不是对手。
  • 你要在 Windows 上靠 DirectML 吃核显或者 A 卡算力，它给不了你要的后端覆盖。
  • 你团队里没人愿意碰 C 风格 API 和内存生命周期，那用通用框架更稳。

五、ONNX Runtime：多硬件后端 #

5.1 它的定位 #

ONNX Runtime 是通用推理框架，不是 LLM 专用。它的模型格式是 ONNX，一份模型可以在 CPU、CUDA、TensorRT、DirectML、CoreML 上跑——换的是「执行后端」（Execution Provider，简称 EP），上层代码几乎不动。

这个「一份模型，多种硬件」的抽象，是它最值钱的地方。你要给客户交付一个 Windows 桌面软件，客户机器有的是核显、有的是 N 卡、有的是纯 CPU，用 ORT 你只需要按机器情况挑 EP，代码路径统一。

它也能跑 LLM，但那是它的一个用例，不是它的全部。要用它跑对话，得自己处理 tokenizer、KV cache、采样循环这些 llama.cpp 已经帮你做完的事，工作量不小。

5.2 多模态才是它的主场 #

Qt 桌面程序需要 AI 的地方，很多时候根本不是聊天：

需求 模型类型 输入输出
语音输入、会议记录 语音识别 音频波形 → 文本
扫描件、发票、截图取字 OCR / 检测 图像 → 文本 + 坐标框
照片分类、缺陷检测 CNN / ViT 图像 → 类别分数
语义搜索、去重 嵌入模型 文本 → 向量
表格结构还原 检测 + 结构模型 图像 → 结构化 JSON

这些全是 ONNX 那一套里的常规活。llama.cpp 在这些场景上帮不了你，ORT 正好。

5.3 接进 Qt #

cpp
// 一次会话的骨架：环境 → 会话 → 输入张量 → 跑 → 取输出
Ort::Env env(ORT_LOGGING_LEVEL_WARNING, "qt-app");
Ort::SessionOptions opts;
opts.SetIntraOpNumThreads(4);
opts.SetGraphOptimizationLevel(GraphOptimizationLevel::ORT_ENABLE_ALL);

#ifdef _WIN32
// 有独显就试 DirectML，失败回落到 CPU，别让程序起不来
try {
    Ort::ThrowOnError(OrtSessionOptionsAppendExecutionProvider_DML(opts, 0));
} catch (const Ort::Exception&) {
    qWarning() << "DirectML 不可用，回落 CPU";
}
#endif

Ort::Session session(env, ORT_TSTR("model.onnx"), opts);

// 张量准备：形状、类型、数据都得对，错了直接抛异常
std::array<int64_t, 4> shape{1, 3, 224, 224};
std::vector<float> input(1 * 3 * 224 * 224, 0.0f);
Ort::MemoryInfo mem = Ort::MemoryInfo::CreateCpu(
    OrtArenaAllocator, OrtMemTypeDefault);
Ort::Value tensor = Ort::Value::CreateTensor<float>(
    mem, input.data(), input.size(), shape.data(), shape.size());

const char* inNames[]  = {"input"};
const char* outNames[] = {"output"};
auto outputs = session.Run(Ort::RunOptions{nullptr},
                           inNames, &tensor, 1, outNames, 1);

踩坑点集中在这几处：

  • 输入形状和预处理必须跟训练时一致。归一化系数差一点，结果就全歪，而且不报错，只是不准。这是最难查的一类问题。
  • EP 要能给失败留退路。用户机器上没有对应驱动时，别让 Session 构造直接抛到上层炸掉，捕获、回落、记日志。
  • DLL 要跟着走。onnxruntime.dll 加上你选的后端 dll，打包时一个都不能漏（第九章细说）。
  • 线程数别写死。SetIntraOpNumThreads 给太大，在多核办公本上反而拖慢界面线程。

5.4 一张表收尾对比 #

你的场景 选 llama.cpp 选 ONNX Runtime
只做文本对话 ✅ 能做，但要多写不少胶水
离线代码补全 ✅ 一般
语音 + 文本混合 ❌ ✅
图像/OCR/检测 ❌ ✅
要 DirectML / CoreML 支持有限 ✅
安装包体积敏感 ✅ 中等
团队只想要一个 dll ✅ 中等

六、模型怎么选与量化 #

6.1 先选「任务」，再选「模型」 #

别一上来就问「哪个模型最好」。先回答：你的程序到底要让模型干什么？

  • 补全 / 改写代码 → 挑代码向的模型，词表对 C++ 友好，上下文要够长。
  • 中文问答、文档摘要 → 挑中文语料喂得多的通用模型。
  • 固定格式抽取（日志分类、字段识别）→ 小模型就够，甚至不用 LLM，规则加分类器更快。
  • 语音 / 图像 → 走 ONNX 那套的专用模型，别用 LLM 硬顶。

任务对不上，参数量翻倍也救不了。

6.2 量化：把模型压小的唯一手段 #

原始权重是 16 位浮点。量化的意思是把它压成 4 位、5 位、8 位整数，再配一套反量化参数。文件体积接近线性下降，质量非线性下降。

算体积的方法很简单：文件大小 ≈ 参数量 × 每参比特数 ÷ 8。剩下的零头是词表和元数据。所以拿到一个「X B 参数、Y 位量化」的模型，你自己就能估出它占多少硬盘，不用信广告。

GGUF 的量化档位大致这么几档，命名里的 K 是分块量化的意思：

档位 每参大致位数 体积 质量 建议
Q8_0 8 最大 几乎无感损失 内存充裕、要保真时用
Q6_K 6 上下 大 很接近原始 有富余显存时用
Q5_K_M 5 上下 中偏大 差异很小 折中选择
Q4_K_M 4 上下 中 可用，代码任务略掉点 通用默认档
Q3_K_M 3 上下 小 开始能感觉到变笨 只在小内存机器上用
Q2_K 2 上下 最小 明显退化，容易胡言 不建议发货

_M 是 medium 混合策略：关键的层用高精度，不关键的层压得更狠。同档位里 _S 更小更糙，_L 更大更稳。

一条实战经验：先选能塞进内存的最大档位，再决定要不要降模型规模。 同样内存预算下，一个小模型的高精度版本，对话质量往往比一个大模型的低精度版本更靠谱——尤其代码任务，低精度最先坏的就是符号和缩进。

6.3 内存预算怎么估 #

推理时占的不只是模型权重，还有 KV cache。

text
总占用 ≈ 权重文件大小
       + KV cache（跟 n_ctx、层数、隐藏维度成正比）
       + 推理过程中的临时张量
       + 你的 Qt 程序本身

给用户机器留余量：权重是 4G 的模型，别指望在 8G 内存的办公本上舒服地跑，因为系统、浏览器、你的程序都要占。发货前拿最低配机器实测，别拿自己的开发机测。

6.4 选型速查 #

约束 怎么选
用户机器 8G 内存、无独显 小参数量 + Q4 量化，或者干脆走云端
只做文本、要离线 llama.cpp + GGUF
有 N 卡、要低延迟 ORT + CUDA/TensorRT，或 llama.cpp 的 GPU 后端
要 OCR / 语音 ONNX Runtime
交付给政企、要过审计 本地推理，模型文件随包分发
免费软件、用户量大 云端 API + 你自己的中转网关（控成本）

七、把推理嵌进 Qt 程序 #

7.1 分成两层写 #

别把推理代码和窗口类搅在一起。分两层：

  • 后端层：纯 C++，不含 QObject，只管加载模型、跑推理、吐文本。这一层以后换成云端 API 也能用。
  • 适配层：QObject 子类，把后端的回调翻译成信号，负责线程、生命周期、错误上报。

这么分的好处是，同一套界面可以在「云端」和「本地」两个后端之间切换，改一行注入代码的事。

7.2 后端接口 #

cpp
// IAiBackend.h —— 纯 C++ 接口，两个实现：CloudBackend / LocalBackend
class IAiBackend {
public:
    virtual ~IAiBackend() = default;
    virtual bool load(const QString& modelPathOrUrl) = 0;
    virtual void generate(const QString& prompt,
                          std::function<void(const QString&)> onToken,
                          std::function<void(const QString&)> onError) = 0;
    virtual void cancel() = 0;
    virtual QString name() const = 0;
};

onToken 是流式回调，cancel() 是必须项——用户点了「停止」，你得真能停下来，而不是等它把 2000 个 token 吐完。

7.3 适配层 #

cpp
class AiAssistant : public QObject {
    Q_OBJECT
public:
    explicit AiAssistant(QObject* parent = nullptr) : QObject(parent) {}

    void setBackend(std::unique_ptr<IAiBackend> b) { m_backend = std::move(b); }

    bool loadModel(const QString& path) {
        if (!m_backend) return false;
        return m_backend->load(path);          // 耗时！必须放到工作线程里调
    }

public slots:
    void ask(const QString& prompt) {
        if (!m_backend) { emit failed(QStringLiteral("后端未初始化")); return; }
        emit started();
        m_backend->generate(
            prompt,
            [this](const QString& t) { emit token(t); },        // 适配层只转发
            [this](const QString& e) { emit failed(e); });
    }

signals:
    void started();
    void token(const QString& piece);
    void failed(const QString& msg);
    void finished();

private:
    std::unique_ptr<IAiBackend> m_backend;
};

界面侧只连三个信号：

cpp
connect(assistant, &AiAssistant::started, this, [this] {
    m_view->clear();
    m_stopBtn->setEnabled(true);
});
connect(assistant, &AiAssistant::token, this, [this](const QString& t) {
    m_view->moveCursor(QTextCursor::End);
    m_view->insertPlainText(t);        // 主线程里碰控件，安全
});
connect(assistant, &AiAssistant::failed, this, [this](const QString& e) {
    QMessageBox::warning(this, QStringLiteral("推理失败"), e);
});

token 信号的连接方式保持默认的自动连接即可——只要 AiAssistant 活在工作线程里，Qt 会把它排队送回主线程。前提是你真的把它 moveToThread 了，这在下一章说。

7.4 生命周期 #

  • 模型加载一次，全程复用。每次提问都重新加载，用户会以为软件坏了。
  • 加载是耗时操作。几秒级别很常见，放在启动画面后面，别在主线程里同步调。
  • 卸载要干净。程序退出前释放 context 和 model，不然会有概率在退出时崩在析构里，日志里还看不到原因。
  • 多实例要拦住。两个线程同时往一个 llama_context 里塞请求，结果不可预测。要么加锁，要么一请求一 context。

八、异步与不卡界面 #

8.1 为什么必须异步 #

这条是红线：模型加载和推理都是耗时操作，绝不能放在主线程。 加载几秒，推理一次几秒到几十秒，期间主线程一阻塞，窗口就白屏、拖不动、任务管理器标「未响应」。用户不会管你后面在算什么，他只会点关闭。

三种做法，各有适用面：

方案 实现 优点 代价
QThread + worker 对象 手动 moveToThread 控制细，能长期持有模型 生命周期要自己管
QtConcurrent::run 一行扔进线程池 写起来快 取消麻烦，不适合长驻模型
独立进程 + 本地接口 QProcess 起子进程 崩溃隔离，进程能重启 多一层 IPC，部署复杂

8.2 QtConcurrent 的用法与边界 #

一次性、无状态的推理任务，用 QtConcurrent 最省事：

cpp
// 注意：capture 的东西必须活得比任务久，别捕 this 又不保证对象存在
auto* watcher = new QFutureWatcher<QString>(this);
connect(watcher, &QFutureWatcher<QString>::finished, this, [this, watcher] {
    m_view->setPlainText(watcher->result());
    watcher->deleteLater();
});

QFuture<QString> f = QtConcurrent::run([prompt, modelPath] {
    LocalBackend backend;              // 在池线程里构造，别跨线程共享
    backend.load(modelPath);
    return backend.generateBlocking(prompt);
});
watcher->setFuture(f);

边界在哪：模型对象别在多个池线程之间共享。QThreadPool 的线程是复用的，你不知道下一次任务落在哪个线程上，共享一个有内部状态的 llama_context 就是给自己埋雷。

工程 .pro 里记得加：

QT += concurrent

CMake 那边是 find_package(Qt6 COMPONENTS Concurrent REQUIRED) 加 target_link_libraries(... Qt6::Concurrent)。忘了这一句，报的是「找不到 QtConcurrent 头文件」，跟 AI 一点关系没有，纯属自找。

8.3 QThread + worker：长驻模型的标准写法 #

模型要一直驻留内存时，这个写法更合适。

cpp
class InferenceWorker : public QObject {
    Q_OBJECT
public:
    explicit InferenceWorker(QObject* parent = nullptr) : QObject(parent) {}

public slots:
    void init(const QString& modelPath) {           // 在子线程里执行
        m_ok = m_backend.load(modelPath);
        emit ready(m_ok);
    }
    void doGenerate(const QString& prompt) {        // 也在子线程
        if (!m_ok) { emit failed(QStringLiteral("模型未就绪")); return; }
        m_backend.generate(prompt,
            [this](const QString& t) { emit token(t); },
            [this](const QString& e) { emit failed(e); });
        emit finished();
    }

signals:
    void ready(bool ok);
    void token(const QString& piece);
    void failed(const QString& msg);
    void finished();

private:
    LocalBackend m_backend;
    bool m_ok = false;
};

装配：

cpp
auto* thread = new QThread(this);
auto* worker = new InferenceWorker;          // 绝对不能带 parent！
worker->moveToThread(thread);

connect(thread, &QThread::started, worker, [=] { worker->init(modelPath); });
connect(this, &MainWindow::requestGenerate, worker, &InferenceWorker::doGenerate);
connect(worker, &InferenceWorker::token, this, &MainWindow::onToken);
connect(worker, &InferenceWorker::finished, this, [=] { m_stopBtn->setEnabled(false); });

thread->start();

两个必踩的坑：

  • 带 parent 的 QObject 不能 moveToThread。运行时会打印一条 warning，然后 moveToThread 静默失败，任务还在主线程跑，界面照卡。new InferenceWorker 后面那个括号里什么都别填。
  • 析构顺序。退出时先 thread->quit()、thread->wait()，再 delete worker。反了就是退出崩溃。

8.4 独立进程方案 #

把推理塞进一个子进程，通过本地 HTTP 或者 stdin/stdout 通信。多出来的这层麻烦，换来两个好处：

  • 崩溃隔离。推理库在用户机器上崩了，主程序还活着，重启子进程即可。
  • 可以借现成的服务端。llama.cpp 官方带一个 llama-server，起来就是一个兼容 OpenAI 格式的本地 HTTP 接口。

后端代码改都不用改，把 baseUrl 指向 http://127.0.0.1:<端口>，本地推理就走成了「云端 API」的形状。这也是 Ollama 那套玩法的原理：它把底层 llama.cpp 的编译配置全封了，对外丢一个兼容 OpenAI 格式的 HTTP 接口。装完服务，一句 ollama run <模型名> 把模型拉下来跑起来；默认地址是 http://127.0.0.1:11434，工具里的 Base URL 填 http://127.0.0.1:11434/v1，API Key 随便写几个字母糊弄过去（本地服务不校验），模型名填你刚拉的那个。改完这三项，任何支持自定义 Endpoint 的工具就接上了本地私服，拔网线照样干活。

这套路对 Qt 特别友好：云端和本地共用同一个 QNetworkAccessManager 客户端，第七章那个 IAiBackend 的两个实现直接合成一个。

代价是进程管理。用户手动 kill 子进程、端口被占、子进程没跟着主程序退出变成孤儿——都得写代码兜住。

8.5 取消 #

用户点「停止」，必须真停。

  • 云端：reply->abort()。
  • llama.cpp：在生成循环里查一个 std::atomic<bool> m_cancel，置位就 break。
  • ORT：一次 Run 是原子的，粗粒度只能等它跑完；细粒度要拆成多次调用，用 RunOptions 配合终止标志。

不写取消的后果很实在：用户嫌慢点了关闭，程序僵在那等推理收尾，看起来就是死机。

九、打包时的大文件问题 #

9.1 模型放哪 #

三条路，看你的发行方式选：

策略 安装包体积 首次可用 适合
模型内置进安装包 大（几百兆到几个 G） 装完就能用 内网分发、政企交付、无外网环境
首次启动下载 小 要等下载 互联网分发、免费软件
内置小模型 + 可选下载大模型 中 装完能用基础功能 大多数商业软件

内置的代价是安装包体积和下载耗时；下载的代价是首启体验，以及要自己写断点续传、校验、失败重试。

**别把模型塞进 qrc。**资源文件会被编译进二进制，几 G 的模型会让编译过程吃掉几十 G 内存，链出来的 exe 大得离谱，运行时还得整块解压到内存。模型文件当普通外部文件拷进安装目录，或者放用户数据目录。

9.2 路径与权限 #

模型该放哪，取决于它是只读资源还是可更新资源：

cpp
// 只读、随安装包分发 —— 跟 exe 放一起
QString bundled = QCoreApplication::applicationDirPath() + "/models/llm.gguf";

// 可下载、可更新 —— 放用户数据目录，避开 Program Files 的写权限问题
QString dataDir = QStandardPaths::writableLocation(
                      QStandardPaths::AppDataLocation) + "/models";
QDir().mkpath(dataDir);
QString downloaded = dataDir + "/llm.gguf";

Program Files 下普通用户没有写权限。把下载的模型往 applicationDirPath() 里怼，装到 C:\Program Files 的用户会直接失败——而且这个 bug 只在非管理员账号上复现，你的开发机永远测不出来。

9.3 依赖 dll 别漏 #

windeployqt 只认 Qt 自己的依赖，第三方库得你手动补：

text
安装目录
├─ YourApp.exe
├─ Qt6Core.dll / Qt6Gui.dll / Qt6Widgets.dll / Qt6Network.dll ...
├─ platforms/qwindows.dll
├─ llama.dll                      ← llama.cpp 动态库
│   （静态链接则不需要，推荐静态）
└─ models/llm.gguf                ← 模型文件

ORT 方案额外要：
├─ onnxruntime.dll
├─ onnxruntime_providers_shared.dll
└─ DirectML.dll 或 CUDA 相关 dll   ← 你选了哪个 EP 就带哪个

ORT 的 EP dll 是运行期加载的，缺了不会在启动时报错，会在构造 Session 时抛异常。打包完在一台干净机器上实跑一遍，别只看编译通过。

9.4 安装包本身 #

  • 压缩率。NSIS 用 solid LZMA 压模型文件，压缩比不高但耗时很长，装一次要好几分钟。模型文件本身已经是量化后的近似随机数据，压不动，考虑对 models/ 目录跳过压缩。
  • 安装进度要真实。几百兆的解压过程不给反馈，用户会以为卡死并强杀安装程序，留下半残的安装目录。
  • 校验。下载路径上务必带 SHA256，校验失败就重下。网络中断留下的半截模型文件，加载时会给你一个看不懂的错误码。

这些在《打包分发应用》里讲得更细，包括 NSIS 脚本怎么写、静默安装参数怎么传。

十、成本与隐私的权衡 #

10.1 一张表看清 #

维度 调云端 API 本地推理
首次可用门槛 有 Key 就能用 要先下模型
安装包体积 几乎不增 几百兆到几个 G
按次成本 有，随用量线性涨 无，一次性摊到硬件上
断网可用 不行 行
数据出机器 出 不出
用户机器要求 极低 内存与显卡定生死
延迟 取决于网络，多数情况可接受 取决于硬件，老机器上慢
模型升级 改字符串 重新下发模型文件
出事时的定位难度 看厂商日志 看自己日志，好查
合规审计 难过 好过

10.2 混合：敏感在本地，闲聊上云端 #

多数商业软件最后会走到混合。判断逻辑简单：

  1. 输入里有没有客户的名字、身份证、合同金额、内部代码？有 → 本地或者干脆不上 AI。
  2. 是不是高频轻量任务（润色、分类、格式化）？是 → 本地小模型，零边际成本。
  3. 是不是低频重任务（长文档分析、复杂推理）？是 → 云端，一次几分钱，用户能接受等待。

实现上不难，第七章那个 IAiBackend 接口就是为了这个。路由逻辑写在一个 Router 里，按任务类型挑后端，界面完全不知道背后换了谁。

10.3 成本控制的两个落点 #

  • 中转网关。客户端不直连厂商，走你自己的服务。好处：Key 不落客户端、能按用户限流、能记账、能随时换厂商不更新客户端。
  • 缓存。同一个 prompt 反复问（比如固定的「这段报错什么意思」），本地缓存答案。桌面程序的输入重复率比你想的高。

10.4 隐私的最小要求 #

就算走云端，也有几条不能省：

  • 传之前提醒用户，并给一个开关。
  • 日志里不要打完整 prompt，脱敏后再记。
  • 别把整个工程目录打包上传，只传用户明确选中的内容。
  • 明确写清楚数据发给了谁、留存多久。

十一、别把 AI 当万能 #

11.1 它会一本正经地错 #

模型的输出是概率采样，不是查数据库。它会编出不存在的函数名、编出不存在的 Qt 枚举、编出长得像那么回事但编译不过的代码。这在本地小模型上更明显。

所以：

  • AI 生成的代码必须过 review。这条没有例外。
  • 别让 AI 的输出直接写进生产数据，尤其是格式抽取类任务，加一层校验。
  • 给它可验证的上下文。同一段代码，喂了头文件和签名再问，比只贴两行问要准得多。

开发期也一样。用 Agent 改完，git diff 要自己看，别一键 commit。

11.2 端侧推理要克制 #

在真正交付给客户的商业软件里塞端侧推理，得先想清楚一件事：这是不是硬需求？ 除非甲方明确要求纯物理断网且数据机密，否则别去死磕巨大的显存占用和五花八门的硬件报错。等到真被要求了，再动用 ONNX Runtime 或 llama.cpp 把几百兆的引擎压进客户端也不迟。

先把云端跑通，把产品逻辑跑顺，再考虑本地化。倒过来做，多半是花两个月解决一堆用户根本感知不到的兼容问题。

11.3 三种用法，各归各位 #

实际干活的时候，我的习惯是「见招拆招，组合出击」：

  1. 光标级补全：用成肌肉记忆。不管是自带的 Copilot 还是挂的本地 Ollama，让它在后台把那些 Getter/Setter、又长又烂的信号槽绑定铺好，把脑力留给架构。
  2. 大架构重构：交给终端 Agent。要改一堆头文件、加减 CMakeLists.txt 依赖、动到复杂的 Widget 结构时，别在 IDE 里一个个文件寻址，直接把自然语言扔进终端。
  3. 产品里原生内嵌：克制使用，只在有明确理由时上。

顺带说一句角色的事。AI 把「敲代码」这一步的成本压下去之后，比拼的就不是手速了。得多往后退一步，当系统的设计者，当那个审代码的人。

十二、易错点速查 #

现象 原因 处理
一问问题窗口就白屏 推理跑在主线程 QThread 或 QtConcurrent，见第八章
moveToThread 不生效 对象带了 parent new 时不传 parent
退出时必崩 worker 析构顺序反了 先 quit+wait，再 delete
第二次提问报内存错 llama_context 被多线程共享 加锁，或一请求一 context
模型加载失败但错误码看不懂 文件不完整或量化档位不支持 SHA256 校验，确认库版本能吃这个 GGUF
装到 Program Files 后下载模型失败 目录无写权限 落 QStandardPaths::AppDataLocation
编译器吃光内存 模型被塞进 qrc 模型当外部文件拷
打包后 ORT 起不来 缺 onnxruntime_providers_shared.dll 或 EP dll 补齐，并在干净机器实测
DirectML 机器上闪退 EP 初始化失败没兜住 try/catch 后回落 CPU
有独显却只用 CPU 跑 n_gpu_layers 还是 0 按显存往上调，调不动就查后端是否编进去
长文档一贴就炸 n_ctx 太小或内存不够 提到目标长度，或者分片处理
回答显示成乱码 字节流直接 QString 构造，没按 UTF-8 解 QString::fromUtf8()，注意跨 chunk 的半个字符
流式输出一卡一卡 每个 token 都 setText 整段重绘 批量追加，或者用定时器合并刷新
用户点停止没反应 没实现 cancel 生成循环里查原子标志位
免费软件账单爆了 Key 写在客户端被人扒了 走自己的中转网关

最后一句：这一章里的坑，八成都不是 AI 的坑，是线程、路径、打包的坑。AI 只是把这些问题放大了——它让你不得不在一个桌面程序里，跟几百兆的文件和不听你话的硬件打交道。
