程序写完只是做了一半。另一半是把它交出去：依赖怎么带、图标怎么打、安装包怎么做。

这篇讲什么：静态编译与动态编译的取舍、Qt 程序的三类依赖、windeployqt / macdeployqt / linuxdeployqt 怎么用、CMake 里的部署 API、exe 图标与版本资源、NSIS 安装包从零到出 setup.exe、发布目录怎么摆才不出事。

这篇不讲什么：代码混淆与授权校验（见《程序加密与授权》）、PDF 导出与打印（见《PDF 与打印》）、日志落盘与开机自启（见《日志与开机自启》）、接入大模型（见《Qt 接入 AI 能力》）、发布之后的崩溃率与启动耗时（见《发布后的性能问题》）。

主线只有一句：Qt 程序发布的核心问题是「依赖」，不是「把 exe 拷出去」。依赖没整明白，后面每一步都是猜。

一、发布方式有几种 #

交付形式就三类，选哪类看用户是谁、多久更一次。

形式 长什么样 适合谁 代价
单文件绿色版 一个 exe，双击就跑 内部工具、验证 Demo、丢给同事试用 只能走静态编译，体积 50~100MB 起
绿色文件夹 zip 里一堆 dll + 插件目录 + exe 免安装场景、便携软件、CI 直接出产物 用户自己解压，没快捷方式，也没卸载
安装包 setup.exe / .dmg / .AppImage 面向普通用户的正式产品 得写脚本，得配卸载逻辑，得管升级

三种形式不互斥。真实项目里的常见组合是：给普通用户发安装包，同时给运维和自动化测试发一个 zip。两条产物线共用同一个部署目录，只是打包动作不同。

三种形式背后还藏着一次技术选择：静态编译还是动态编译。它决定了你的交付物到底是一个 exe 还是一个目录，下一章展开。

二、静态编译与动态编译 #

两种方式干的活不一样，先把边界说清。

  • 静态编译：Qt 库、编译器运行时、插件全部链接进一个 exe，exe 自己就是完整程序。
  • 动态编译：exe 里只留符号引用，运行时到同级目录、PATH、系统库目录里找 .dll / .so / .dylib。
维度 静态编译 动态编译
原理 所有关联库编译进 .exe 运行时从同级目录或系统目录加载库
可执行文件 单一文件，50~100MB+ 几百 K，外加一堆 DLL，总量相近
插件支持 得手动 Q_IMPORT_PLUGIN 导入 丢进对应子目录就能用
更新方式 改个标点也要全量重发 换个 DLL 就行
内存占用 每个进程独占一份 Qt 代码 多个 Qt 程序共享同一份库
部署难度 极简，就一个 exe 繁琐，要带一大家子依赖
LGPL 合规 必须公开目标文件或源码 不改 Qt 源码即可闭源商用

静态编译的三笔账 #

第一笔：体积。静态链接会把用到的 Qt 模块整段搬进 exe。一个 Widgets 程序 30MB 上下打底，带上 WebEngine 直接飙到 150MB 以上。压缩能救一点，改不了量级。

第二笔：授权。LGPLv3 允许闭源程序动态链接 Qt，前提是用户能替换掉 Qt 库。静态链接把这个前提抹掉了，你必须向用户提供目标文件（.o / .obj）或源码，让人家能重新链接。做不到就得买商业许可。所以「静态编译 + 闭源商用 + 不买许可」是有法律风险的三件套，别自己骗自己。

第三笔：插件。动态加载的插件在静态链接下找不到入口，必须显式导入：

text
#include <QtPlugin>

Q_IMPORT_PLUGIN(QWindowsIntegrationPlugin)
Q_IMPORT_PLUGIN(QJpegPlugin)
Q_IMPORT_PLUGIN(QSQLiteDriverPlugin)

CMake 项目可以直接声明：

cmake
qt_import_plugins(myapp
    INCLUDE Qt::QWindowsIntegrationPlugin
            Qt::QJpegPlugin
            Qt::QSQLiteDriverPlugin
)

漏了 QWindowsIntegrationPlugin 的后果和动态部署漏 platforms/qwindows.dll 一样，程序启动就报找不到平台插件。区别只在于一个在链接期、一个在运行期。

静态编译的配置走 configure -static -release -skip qtwebengine 这一套，自己编一次静态 Qt，机器上要留几十 G 空间，跑一两个小时。不是每个团队都愿意为「单文件」付这个成本。

动态编译的代价 #

动态编译的账全在交付现场：

  • exe 起来了，但图标全是空白——imageformats 目录没带。
  • 主窗口开了，一点「导出 PDF」就崩——打印插件没带。
  • 能连 SQLite 的机器能跑，客户的机器打不开数据库——sqldrivers 没带。
  • 开发机好好的，客户机器报「缺少 VCRUNTIME140.dll」——编译器运行时没带。

这些问题都指向同一件事：动态编译的交付物不是一个 exe，是一个目录。目录里每一层都有意义，少一层就少一块功能。这也是为什么后面要花整整一章讲 windeployqt，再用一章讲目录组织。

怎么选 #

按场景对号入座：

  • 内部工具、验证 Demo → 静态编译。发给同事测一下，还要人家装环境或者解压，太折腾。单文件发过去直接跑。
  • 正经商业软件 → 动态编译。LGPL 的账要算，你也不希望每次发版让用户下几百兆的更新包。
  • 开源项目 → 两种都行。动态编译让用户能自己换 Qt 库（比如修个底层 Bug），更符合开源的分发习惯。
  • 要进容器、要跑 CI → 绿色文件夹或静态版。容器里没有安装向导，也不该有。

结论先摆在这：动态链接 + 规范部署是多数项目的选择，静态编译留给单文件诉求明确、且能接受体积与授权代价的场景。排除掉这两种极端，剩下的项目都该老老实实做部署目录。

三、找出程序的依赖 #

依赖不是一个整体，是三类东西。三类缺一类，现象完全不同，排查思路也不同。

依赖类别 典型文件 缺了会怎样
Qt 模块库 Qt6Core.dll、Qt6Gui.dll、Qt6Widgets.dll 进程直接起不来，提示找不到 DLL
插件（按目录分） platforms/qwindows.dll、imageformats/qjpeg.dll、sqldrivers/qsqlite.dll 平台插件缺失 = 起不来；其他插件缺失 = 功能残缺
编译器运行时 libgcc_s_seh-1.dll、libstdc++-6.dll、msvcp140.dll、VCRUNTIME140.dll 起不来，报缺少运行库
第三方库 OpenSSL、zlib、FFmpeg、各种 SDK 的 dll 相应功能模块失效或直接崩

三类之外还有一类隐性依赖：系统自带的 opengl32.dll、d3dcompiler_47.dll、Win32 API 集合。这部分不用你带全，但版本差异会咬人，后面第十一章单独说。

常见 Qt 依赖库清单 #

动态发布时，客户电脑上必须凑齐这些文件。按用途分组：

分组 文件 说明
Qt 核心模块 Qt5Core.dll、Qt5Gui.dll、Qt5Widgets.dll Qt 6 换成 Qt6Core.dll 等，结构与命名一致
ICU 字符集 icudt51.dll、icuin51.dll、icuuc51.dll Qt 5 强制依赖，Qt 6 已编进 Core
EGL 渲染 libEGL.dll、libGLESv2.dll 用到 OpenGL / ANGLE 的项目要带
平台与功能插件 platforms/、mediaservice/、imageformats/、sqldrivers/、styles/、iconengines/、tls/ 每个目录装一类 dll，目录名固定
MSVC 运行时 msvcp140.dll、msvcr140.dll、vcruntime140.dll 按编译器版本对号，VS2010 是 100 系列，VS2013 是 120 系列

插件目录是独立于普通依赖的 #

这一点最容易翻车，单独拎出来说。

windeployqt 不会把 qwindows.dll 直接丢在 exe 旁边，它会建一个 platforms/ 子目录放在里面。imageformats/、sqldrivers/、styles/ 同理。这些子目录名是 Qt 写死的，必须跟 exe 保持固定的相对位置，一个字符都不能改。

myapp/
├── myapp.exe
├── Qt6Core.dll
├── Qt6Gui.dll
├── Qt6Widgets.dll
├── platforms/
│   └── qwindows.dll        ← 必须在这层，不能挪到根目录
├── imageformats/
│   └── qjpeg.dll
└── sqldrivers/
    └── qsqlite.dll

把 qwindows.dll 挪到 exe 同级，或者把整个 platforms 目录改名成 plugin，程序启动就报：

text
This application failed to start because no Qt platform plugin could be initialized.
Reinstalling the application may fix this problem.

窗口一个都不出现，任务管理器里进程闪一下就没了——第一次遇到容易怀疑编译器，其实是路径问题。Qt 找插件的顺序是：exe 同级目录下的 platforms/ → qt.conf 里指定的 Plugins 路径 → 环境变量 QT_PLUGIN_PATH → 编译时写死的 Qt 安装路径。发布机上不能指望最后一项，只能靠前两项。

插件根目录想换到别的层级，用 qt.conf 的 [Paths] / Plugins 指定，第十章有完整写法。目录可以自定义，但 platforms 这一层不能动。

Debug 与 Release 的 d 后缀 #

Debug 版的 Qt 库文件名带 d，Release 版不带：

类型 库文件名 能发给用户吗
Debug Qt5Cored.dll、Qt5Guid.dll 不能，还依赖调试版 CRT
Release Qt5Core.dll、Qt5Gui.dll 可以

发出去的包必须是 Release 编译。混着 Debug 库跑的后果是启动就崩，或者弹一个「程序无法正常启动 (0xc000007b)」。这一条每年都能撞见几次。

查依赖的工具 #

工具 平台 说明
Dependencies Windows Dependency Walker 的现代替代品，支持 API Set 和延迟加载
Dependency Walker Windows 老工具，对现代 DLL 兼容性差，仅作兜底
ldd Linux 列动态库依赖
otool -L macOS 列动态库依赖
objdump -p / dumpbin /dependents Win / Linux 命令行看导入表

Windows 用 Dependencies

bash
# 从 https://github.com/lucasg/Dependencies/releases 下载
Dependencies.exe myapp.exe

把 exe 拖进窗口，列表里标红问号或感叹号的就是找不到的库。一层层往下看，缺失的库会连带把它的依赖也标红，从最底层开始补。

Linux 用 ldd

bash
# 看全部依赖
ldd ./myapp

# 只看缺的
ldd ./myapp | grep "not found"

ldd 输出里的 not found 就是硬伤。还有一种软伤：库找到了，但版本不对，ldd 不报错，运行时报 symbol lookup error。这种只能拿 objdump -T 对比符号表。

macOS 用 otool

bash
otool -L MyApp.app/Contents/MacOS/MyApp

输出里会出现 /usr/local/opt/qt/lib/QtCore.framework/... 这类绝对路径，说明库是链到本机 Homebrew 上的，换台机器就废。这种情况必须用 install_name_tool 或 macdeployqt 把路径改成 @executable_path/../Frameworks/。

手工补依赖的顺序 #

自动化工具不是万能的，遇到工具认不出的第三方库，得手工补。顺序是：

  1. 先把 Release 版 exe 拷到一个空目录，只放 exe。
  2. 跑 windeployqt，让它把 Qt 侧的依赖拉齐。
  3. 用 Dependencies 再扫一遍，看还剩哪些红。
  4. 剩下的红色项基本是自己的第三方库，从编译机 bin 目录或 SDK 里拷。
  5. 每补一批就重扫一次，直到列表全绿。
  6. 在一台没装 Qt、没装 VS 运行库的干净机器上跑一遍。开发机上永远是好的，这一条不能省。

第 6 步是分水岭。开发机上 PATH 里有 Qt 的 bin，缺什么都能被兜住；干净机器才暴露真实依赖。

四、windeployqt 与 linuxdeployqt #

Qt 官方提供了一套部署工具，作用都是同一件事：扫你的可执行文件，把用到的库和插件复制到指定目录。三个平台三套工具，名字和参数各有脾气。

Windows：windeployqt #

指哪打哪。把 exe 扔给它，它把缺的 Qt 模块、插件、翻译文件一股脑复制过来。

bash
# 1. 用 Release 模式编译

# 2. 把 exe 复制到单独目录
mkdir F:\deploy && copy release\myapp.exe F:\deploy\

# 3. 跑 windeployqt
cd F:\deploy
windeployqt myapp.exe

跑完目录里会多出：Qt6Core.dll 一系的模块库、platforms/qwindows.dll、imageformats/、styles/、translations/，以及一堆 vc_redist 相关的运行时（取决于参数）。

常用参数 #

参数 作用
--release / --debug 指定编译类型，选错会拷错一套库
--qmldir <path> QML 应用必须加，扫 QML 里的 import 找模块
--compiler-runtime 复制 MSVC / MinGW 运行库
--no-translations 不复制翻译文件，包小一截
--no-opengl-sw 不复制软件 OpenGL（opengl32sw.dll 有 20MB+）
--no-system-d3d-compiler 不复制 D3D 编译器
--no-quick-import 不扫 QML 的导入模块，纯 Widgets 项目可用
--list <option> 只列依赖不复制，option 取 source / target / relative / mapping
--dir <path> 输出目录，不指定就放在 exe 同级
--verbose <level> 详细程度 0~2，排查时开到 2
--plugindir <path> 插件复制到哪个子目录

--list target 在排查时特别顺手，它告诉你哪些库会被拷、哪些被判定为系统库跳过，不用真的复制一遍。

实际部署命令 #

QML 应用要全套，--qmldir 不能省：

bash
windeployqt ^
    --release ^
    --qmldir D:\project\qml ^
    --compiler-runtime ^
    --no-translations ^
    myapp.exe

纯 Widgets 应用可以砍掉一半体积：

bash
windeployqt ^
    --release ^
    --no-translations ^
    --no-opengl-sw ^
    --no-system-d3d-compiler ^
    myapp.exe

QML 项目漏了 --qmldir 的典型症状是：窗口能开，但界面一片白，控制台刷 qrc:/main.qml: module "QtQuick.Controls" is not installed。

CMake 里自动调用 #

手工跑一次容易忘，挂到构建流程里更稳：

cmake
if(WIN32)
    find_program(WINDEPLOYQT_EXECUTABLE windeployqt
        HINTS "${Qt6_DIR}/../../../bin")

    add_custom_command(TARGET ${PROJECT_NAME} POST_BUILD
        COMMAND ${WINDEPLOYQT_EXECUTABLE}
            --release
            --no-translations
            $<TARGET_FILE:${PROJECT_NAME}>
        COMMENT "Running windeployqt..."
    )
endif()

注意这段挂在 POST_BUILD 上，每次编译都会往输出目录里补文件。调试构建下跑 --release 参数会拷错库，记得用生成器等判断，别写死。

windeployqt 解决不了什么 #

它能扫出 Qt 自己的模块，扫不出你代码里的第三方依赖。这一条决定了它只是部署流程的前半段。

场景 windeployqt 能不能处理
Qt 模块库（Core / Gui / Widgets / Network） 能
平台插件、图片插件、SQL 驱动 能
QML 模块（加了 --qmldir） 能
MinGW 运行时（加了 --compiler-runtime） 能
OpenSSL（libssl / libcrypto） 不能，Qt 通过运行时加载，扫不到
自己链的 SDK、FFmpeg、私有 dll 不能
通过 LoadLibrary 动态加载的库 不能
数据文件、配置文件、模型文件 不能

规律很简单：链接期能看到的依赖它管，运行期偷偷加载的它不管。所以流程永远是「先 windeployqt，再拿 Dependencies 扫一遍补漏」，两步都做完才算齐。

macOS：macdeployqt #

bash
macdeployqt MyApp.app -dmg

它把 Qt 框架拷进 MyApp.app/Contents/Frameworks/，重写 install_name，顺带生成 dmg。要签名的项目得在签名之前跑，顺序反了签名就失效。

插件目录在 MyApp.app/Contents/PlugIns/，platforms/libqcocoa.dylib 必须存在，逻辑和 Windows 的 platforms/qwindows.dll 一一对应。

Linux：linuxdeployqt #

bash
./linuxdeployqt-continuous-x86_64.AppImage myapp -appimage

基于 AppImage 那套做法，把 Qt 库、插件、依赖一起打进一个可执行文件。它对发行版版本比较敏感，Ubuntu 18.04 上打出来的包未必能在 22.04 上跑，反过来也未必。跨发行版交付时，用最老的目标系统做构建机更保险。

三个平台工具对照 #

工具 平台 产物 局限
windeployqt Windows 一个目录（exe + dll + 插件） 不认第三方库
macdeployqt macOS .app bundle，可出 dmg 签名需在部署之后
linuxdeployqt Linux AppImage 或目录 受构建机发行版版本影响

五、CMake 的部署配置 #

到 Qt 6，CMake 里能直接调部署 API，不用再手写一堆 file(COPY)。比自己攒的 copy 命令可靠，跨平台也不用写三套。

Qt 6 部署 API #

cmake
cmake_minimum_required(VERSION 3.21)
project(MyApp VERSION 1.0.0 LANGUAGES CXX)

find_package(Qt6 REQUIRED COMPONENTS Core Widgets)
qt_standard_project_setup()

qt_add_executable(MyApp
    main.cpp
    mainwindow.cpp
)

target_link_libraries(MyApp PRIVATE Qt6::Core Qt6::Widgets)

# 生成部署脚本
qt_generate_deploy_app_script(
    TARGET MyApp
    OUTPUT_SCRIPT deploy_script
    NO_UNSUPPORTED_PLATFORM_ERROR
)

# 安装目标
install(TARGETS MyApp
    BUNDLE DESTINATION .
    RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR}
)

# 执行部署脚本
install(SCRIPT ${deploy_script})

三个要点：

  • cmake_minimum_required 至少 3.21，低版本没有这套 API。
  • qt_generate_deploy_app_script 只生成脚本，不执行。真正干活的是后面的 install(SCRIPT ...)。
  • NO_UNSUPPORTED_PLATFORM_ERROR 让不支持的平台上跳过报错，而不是中断整个 install。

跑 cmake --install build --prefix dist 之后，dist/bin 里就是能直接发的目录，插件子目录结构由脚本自动摆好。

QML 项目再加一行：

cmake
qt_generate_deploy_qml_app_script(
    TARGET MyApp
    OUTPUT_SCRIPT deploy_script
    NO_UNSUPPORTED_PLATFORM_ERROR
)

它等效于手工跑 windeployqt --qmldir，省掉手填路径。

RPATH 配置 #

Linux 和 macOS 上，让应用按相对路径找共享库，别依赖系统 /usr/lib：

cmake
set_target_properties(MyApp PROPERTIES
    INSTALL_RPATH "$ORIGIN/../lib"
    INSTALL_RPATH_USE_LINK_PATH TRUE
    BUILD_WITH_INSTALL_RPATH TRUE
)

逐条解释：

属性 作用
INSTALL_RPATH 安装后的库搜索路径，$ORIGIN 指可执行文件所在目录
INSTALL_RPATH_USE_LINK_PATH 把链接期用到的非系统路径也加进去
BUILD_WITH_INSTALL_RPATH 构建产物直接用安装期 RPATH，免得装完才暴露问题

macOS 上是 @executable_path/../Frameworks，不用 $ORIGIN。写错了的表现是程序在构建目录能跑，装到 /opt 下就报库找不到。

打包成压缩包 #

CMake 自带 CPack，set(CPACK_GENERATOR "ZIP") 加 include(CPack) 两行，cpack -G ZIP 就出部署目录的压缩版。对内部交付够用，对普通用户还是得做安装包，下一章开始讲。

六、应用程序图标与元数据 #

图标是脸面，版本号是身份证。这两样得在编译前埋进资源段，Windows 上尤其明显：没有资源段，exe 是空白图标，右键属性里全是空白。

设置应用程序图标（qmake） #

  1. 准备 ICO 文件。用 Photoshop 或 ConvertICO 这类在线工具把 PNG/JPG 转成 ICO，里面放 16×16、32×32、48×48、256×256 多个尺寸。只放一个 256 的，任务栏小图标会糊。
  2. 放项目目录，跟 .pro 文件同级。
  3. 改 .pro 文件，加一行 RC_ICONS = app.ico。
  4. 重新编译。先跑一遍 qmake 再编译，exe 就带图标了。只改 .pro 不重跑 qmake，图标不会变。

设置应用程序图标（CMake） #

cmake
# 方法一：用 RC 文件
# 建个 resources/app.rc，里面写：
# IDI_ICON1 ICON "app.ico"

qt_add_executable(MyApp
    main.cpp
    ${CMAKE_SOURCE_DIR}/resources/app.rc
)

# 方法二：设置 Windows 应用属性
set_target_properties(MyApp PROPERTIES
    WIN32_EXECUTABLE TRUE
)

WIN32_EXECUTABLE TRUE 同时做两件事：用 WinMain 而不是 main 作为入口，以及不弹控制台窗口。不带它的话，双击 exe 会先闪一个黑色命令行窗口，用户第一眼就觉得这软件不正经。

Windows 版本信息 #

版本信息写在 exe 的资源段里，右键「属性 → 详细信息」能看到。要手写两个文件：version.h 放宏，version.rc 放资源定义。

text
#ifndef VERSION_H
#define VERSION_H

#define VER_FILEVERSION             1,0,0,0
#define VER_FILEVERSION_STR         "1.0.0.0"
#define VER_PRODUCTVERSION          1,0,0,0
#define VER_PRODUCTVERSION_STR      "1.0.0"

#define VER_COMPANYNAME_STR         "Your Company"
#define VER_FILEDESCRIPTION_STR     "My Application"
#define VER_INTERNALNAME_STR        "myapp"
#define VER_LEGALCOPYRIGHT_STR      "Copyright (C) 2025"
#define VER_ORIGINALFILENAME_STR    "myapp.exe"
#define VER_PRODUCTNAME_STR         "My Application"

#endif // VERSION_H

text
#include <windows.h>
#include "version.h"

IDI_ICON1 ICON "app.ico"

VS_VERSION_INFO VERSIONINFO
FILEVERSION     VER_FILEVERSION
PRODUCTVERSION  VER_PRODUCTVERSION
FILEFLAGSMASK   VS_FFI_FILEFLAGSMASK
FILEFLAGS       0
FILEOS          VOS_NT_WINDOWS32
FILETYPE        VFT_APP
FILESUBTYPE     VFT2_UNKNOWN
BEGIN
    BLOCK "StringFileInfo"
    BEGIN
        BLOCK "040904B0"  // 英文(美国), Unicode
        BEGIN
            VALUE "CompanyName",      VER_COMPANYNAME_STR
            VALUE "FileDescription",  VER_FILEDESCRIPTION_STR
            VALUE "FileVersion",      VER_FILEVERSION_STR
            VALUE "InternalName",     VER_INTERNALNAME_STR
            VALUE "LegalCopyright",   VER_LEGALCOPYRIGHT_STR
            VALUE "OriginalFilename", VER_ORIGINALFILENAME_STR
            VALUE "ProductName",      VER_PRODUCTNAME_STR
            VALUE "ProductVersion",   VER_PRODUCTVERSION_STR
        END
    END
    BLOCK "VarFileInfo"
    BEGIN
        VALUE "Translation", 0x0409, 1200  // 英文, Unicode
    END
END

VALUE 那一行里两个字符串的顺序不能调换，一个是显示名，一个是实际值。名字写错（比如 FileVersion 写成 FileVer）不报错，只是在属性页里不显示。

qmake 集成 #

text
VERSION = 1.0.0
QMAKE_TARGET_COMPANY = "Your Company"
QMAKE_TARGET_PRODUCT = "My Application"
QMAKE_TARGET_DESCRIPTION = "Application Description"
QMAKE_TARGET_COPYRIGHT = "Copyright (C) 2025"

RC_ICONS = app.ico
RC_FILE = version.rc

用了 RC_FILE 之后，version.rc 里已经写了 IDI_ICON1 ICON，RC_ICONS 就该删掉，两份都留会让图标资源重复定义。

CMake 集成（configure_file） #

版本号不该手写两遍。用模板让 CMake 生成：

cmake
# version.rc.in 是模板文件
set(PROJECT_VERSION_MAJOR 1)
set(PROJECT_VERSION_MINOR 0)
set(PROJECT_VERSION_PATCH 0)

configure_file(
    ${CMAKE_SOURCE_DIR}/resources/version.rc.in
    ${CMAKE_BINARY_DIR}/version.rc
    @ONLY
)

qt_add_executable(MyApp
    main.cpp
    ${CMAKE_BINARY_DIR}/version.rc
)

@ONLY 是关键，它只替换 @VAR@ 形式的占位符，不动 .rc 里那些 "040904B0" 之类的花括号写法。

macOS 那边的对应物是 Info.plist（图标是 .icns，用 iconutil 从 PNG 打出来），Linux 是 app.desktop（Exec= 与 Icon= 两个字段必填）。三个平台三份元数据，图标源文件留一个 1024×1024 的 PNG，其他格式都从它派生。

七、NSIS 安装包基础 #

依赖找齐只是第一步。你总不能给用户发个压缩包，让他自己解压、自己建快捷方式、自己删目录。得做个安装程序。

安装包工具怎么选 #

工具 平台 在线更新 组件化安装 上手难度 包体积
NSIS 只有 Windows 要自己写 靠脚本实现 中等 小
Qt IFW Windows / macOS / Linux 自带 支持 中等偏上 大，带框架
Inno Setup 只有 Windows 要另找方案 基本不行 容易 小

选法：只要 Windows、包要小、愿意写点脚本 → NSIS。要跨平台、要在线更新、要组件勾选安装 → Qt IFW。想十分钟出一个能用的安装包 → Inno Setup。

Qt Installer Framework（IFW） #

Qt 官方的安装程序框架，跨平台，支持在线更新和组件化安装。它自己就是一套 Qt 程序，安装界面是 Qt 画的。

目录结构：

text
installer/
├── config/
│   └── config.xml          # 全局配置
└── packages/
    └── com.yourcompany.myapp/
        ├── meta/
        │   └── package.xml  # 组件配置
        └── data/
            └── ...          # 应用文件，原样拷进去

config/config.xml：

text
<?xml version="1.0" encoding="UTF-8"?>
<Installer>
    <Name>My Application</Name>
    <Version>1.0.0</Version>
    <Title>My Application Installer</Title>
    <Publisher>Your Company</Publisher>
    <StartMenuDir>My Application</StartMenuDir>
    <TargetDir>@ApplicationsDir@/MyApp</TargetDir>

    <!-- 安装程序图标 -->
    <InstallerWindowIcon>installer_icon</InstallerWindowIcon>
    <InstallerApplicationIcon>installer_icon</InstallerApplicationIcon>

    <!-- 维护工具 -->
    <MaintenanceToolName>MaintenanceTool</MaintenanceToolName>

    <!-- 在线仓库，可选 -->
    <!-- <RemoteRepositories>
        <Repository>
            <Url>https://your-server.com/repository</Url>
            <Enabled>1</Enabled>
        </Repository>
    </RemoteRepositories> -->
</Installer>

packages/com.yourcompany.myapp/meta/package.xml：

text
<?xml version="1.0" encoding="UTF-8"?>
<Package>
    <DisplayName>My Application</DisplayName>
    <Description>Core application files</Description>
    <Version>1.0.0</Version>
    <ReleaseDate>2025-01-22</ReleaseDate>
    <Default>true</Default>
    <Script>installscript.qs</Script>
</Package>

生成安装程序：

bash
# binarycreator 在 Qt 安装目录下
# Windows: Qt\Tools\QtInstallerFramework\4.x\bin\binarycreator.exe
# Linux/macOS: ~/Qt/Tools/QtInstallerFramework/4.x/bin/binarycreator

# 离线安装程序
binarycreator -c config/config.xml -p packages MyAppInstaller

# 在线安装程序
binarycreator -c config/config.xml -p packages -n MyAppOnlineInstaller

data/ 目录里放的就是前面部署好的整个目录，包括 platforms/。IFW 按原样打包，目录结构不会被打乱，这一点比手写脚本省心。

在线安装要额外跑一个 repogen 生成仓库，把仓库目录挂到服务器上，config.xml 里的 RemoteRepositories 指向它。升级时用户点维护工具里的「更新」，不用重新下载整个包。

Inno Setup #

老牌 Windows 安装包工具，配置简单，脚本比 NSIS 好读。

从 Inno Setup 官网 下载装好，打开 Inno Setup Compiler，File → New 新建脚本。

text
#define MyAppName "My Application"
#define MyAppVersion "1.0.0"
#define MyAppPublisher "Your Company"
#define MyAppURL "https://www.example.com/"
#define MyAppExeName "myapp.exe"

[Setup]
AppId={{XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX}
AppName={#MyAppName}
AppVersion={#MyAppVersion}
DefaultDirName={autopf}\{#MyAppName}
OutputDir=.\output
SetupIconFile=app.ico
Compression=lzma
SolidCompression=yes

[Files]
Source: "deploy\*"; DestDir: "{app}"; Flags: ignoreversion recursesubdirs

[Icons]
Name: "{group}\{#MyAppName}"; Filename: "{app}\{#MyAppExeName}"
Name: "{commondesktop}\{#MyAppName}"; Filename: "{app}\{#MyAppExeName}"

[Files] 段那条 recursesubdirs 是命门。少了它，platforms/、imageformats/ 里的文件不会被装进去，装完就是一个打不开的程序。这是 Inno Setup 最常踩的坑。

AppId 要固定一个 GUID 并一直用下去。换了 GUID，新版本会被当成另一个软件安装，旧版本留在控制面板里删不掉。

NSIS 是什么 #

NSIS（Nullsoft Scriptable Install System）是一套 Windows 安装/卸载制作系统，免费开源，体积轻量，脚本驱动。核心是编译器 makensis.exe，配一个带脚本向导的可视化 IDE（HM NIS Edit）。编译产物是自解压 exe，里面塞着压缩后的文件和一个安装引擎，安装时引擎把文件解出来、写注册表、建快捷方式。

bash
makensis myapp.nsi

NSIS 有几个特点决定了它适合发 Qt 程序：

特性 说明
单文件输出 所有文件打进一个 setup.exe，LZMA 压缩
目录结构保真 File /r 或逐段 SetOutPath 都能原样保留子目录
脚本可控 注册表、环境变量、服务、静默安装都能写
卸载器自动生成 写个 Uninstall.exe 段就有卸载程序
多语言 MUI_LANGUAGE 挂多少种语言都行
免费 开源，商用不收费

八、NSIS 脚本结构 #

.nsi 是纯文本脚本，从上往下读。理解它只需要认清四类东西：属性指令、界面宏、Section（安装段）、Function（回调函数）。

脚本骨架 #

nsis
; ========== 1. 编译期定义 ==========
!include "MUI2.nsh"
!include "FileFunc.nsh"

!define APP_NAME "MyQtApp"
!define APP_VERSION "1.0.0"
!define APP_PUBLISHER "Your Company"
!define APP_EXE "MyQtApp.exe"
!define APP_KEY "Software\${APP_NAME}"

; ========== 2. 安装包属性 ==========
Name "${APP_NAME}"
OutFile "MyQtApp-Setup-${APP_VERSION}.exe"
InstallDir "$PROGRAMFILES64\${APP_NAME}"
InstallDirRegKey HKLM "${APP_KEY}" "InstallDir"
RequestExecutionLevel admin
Unicode true
SetCompressor /SOLID lzma
BrandingText "${APP_PUBLISHER}"

; ========== 3. 界面 ==========
!define MUI_ABORTWARNING
!define MUI_ICON "app.ico"
!define MUI_UNICON "uninst.ico"
!insertmacro MUI_PAGE_WELCOME
!insertmacro MUI_PAGE_LICENSE "license.txt"
!insertmacro MUI_PAGE_DIRECTORY
!insertmacro MUI_PAGE_INSTFILES
!define MUI_FINISHPAGE_RUN "$INSTDIR\${APP_EXE}"
!insertmacro MUI_PAGE_FINISH
!insertmacro MUI_UNPAGE_CONFIRM
!insertmacro MUI_UNPAGE_INSTFILES
!insertmacro MUI_LANGUAGE "SimpChinese"
!insertmacro MUI_LANGUAGE "English"

; ========== 4. 安装段 ==========
Section "主程序" SEC_MAIN
  SectionIn RO
  SetOutPath "$INSTDIR"
  File "D:\Deploy\MyQtApp.exe"
  File "D:\Deploy\Qt6Core.dll"
  File "D:\Deploy\Qt6Gui.dll"
  File "D:\Deploy\Qt6Widgets.dll"

  ; 插件必须按原目录层次安装
  SetOutPath "$INSTDIR\platforms"
  File "D:\Deploy\platforms\qwindows.dll"

  SetOutPath "$INSTDIR\imageformats"
  File "D:\Deploy\imageformats\qjpeg.dll"
  File "D:\Deploy\imageformats\qgif.dll"

  SetOutPath "$INSTDIR\sqldrivers"
  File "D:\Deploy\sqldrivers\qsqlite.dll"
SectionEnd

Section "开始菜单快捷方式" SEC_LNK
  CreateDirectory "$SMPROGRAMS\${APP_NAME}"
  CreateShortCut "$SMPROGRAMS\${APP_NAME}\${APP_NAME}.lnk" "$INSTDIR\${APP_EXE}"
  CreateShortCut "$SMPROGRAMS\${APP_NAME}\卸载 ${APP_NAME}.lnk" "$INSTDIR\Uninstall.exe"
  CreateShortCut "$DESKTOP\${APP_NAME}.lnk" "$INSTDIR\${APP_EXE}"
SectionEnd

; ========== 5. 收尾：注册表与卸载器 ==========
Section "卸载信息" SEC_REG
  WriteRegStr HKLM "${APP_KEY}" "InstallDir" "$INSTDIR"
  WriteRegStr HKLM "${APP_KEY}" "Version" "${APP_VERSION}"

  WriteRegStr HKLM "Software\Microsoft\Windows\CurrentVersion\Uninstall\${APP_NAME}" \
      "DisplayName" "${APP_NAME}"
  WriteRegStr HKLM "Software\Microsoft\Windows\CurrentVersion\Uninstall\${APP_NAME}" \
      "DisplayVersion" "${APP_VERSION}"
  WriteRegStr HKLM "Software\Microsoft\Windows\CurrentVersion\Uninstall\${APP_NAME}" \
      "Publisher" "${APP_PUBLISHER}"
  WriteRegStr HKLM "Software\Microsoft\Windows\CurrentVersion\Uninstall\${APP_NAME}" \
      "UninstallString" "$INSTDIR\Uninstall.exe"

  WriteUninstaller "$INSTDIR\Uninstall.exe"
SectionEnd

; ========== 6. 卸载段 ==========
Section "Uninstall"
  Delete "$INSTDIR\${APP_EXE}"
  Delete "$INSTDIR\*.dll"
  Delete "$INSTDIR\Uninstall.exe"
  RMDir /r "$INSTDIR\platforms"
  RMDir /r "$INSTDIR\imageformats"
  RMDir /r "$INSTDIR\sqldrivers"
  RMDir "$INSTDIR"

  Delete "$SMPROGRAMS\${APP_NAME}\*.lnk"
  RMDir "$SMPROGRAMS\${APP_NAME}"
  Delete "$DESKTOP\${APP_NAME}.lnk"

  DeleteRegKey HKLM "${APP_KEY}"
  DeleteRegKey HKLM "Software\Microsoft\Windows\CurrentVersion\Uninstall\${APP_NAME}"
SectionEnd

这个骨架能直接编。改 !define 里的名字、改 File 后面的路径就能用。

关键指令 #

指令 作用 坑点
InstallDir 默认安装路径 $PROGRAMFILES64 在 32 位系统上会退化
InstallDirRegKey 从注册表读上次安装路径，升级时直接覆盖 首次安装读不到就用 InstallDir
RequestExecutionLevel 提权要求 写 HKLM 必须 admin，否则静默失败
Unicode true 生成 Unicode 安装包 不写，中文路径会乱码
SetCompressor /SOLID lzma 压缩方式 /SOLID 压得最小，但解压慢一点
SetOutPath 后续 File 的目标目录 决定插件子目录结构
File / File /r 打包单个文件 / 递归打包整个目录 /r 保留子目录，也会把调试文件卷进去
SectionIn RO 该段强制安装、不可取消 主程序段必须加
WriteUninstaller 生成卸载程序 必须在安装段里调

插件子目录怎么进安装包 #

这是 NSIS 打 Qt 程序唯一需要动脑的地方。

File 只负责「把文件从哪拷到 $INSTDIR 或当前 SetOutPath」，它不会自己造中间目录。所以插件必须分两段写：先 SetOutPath 切到子目录，再 File。

nsis
SetOutPath "$INSTDIR\platforms"
File "D:\Deploy\platforms\qwindows.dll"

写错成下面这样就废了：

nsis
SetOutPath "$INSTDIR"
File "D:\Deploy\platforms\qwindows.dll"   ; 插件被拍平到根目录

qwindows.dll 落在 exe 旁边，Qt 不会去那里找。装完双击，就是那句 no Qt platform plugin could be initialized。

要一次带整个目录，也可以用：

nsis
SetOutPath "$INSTDIR"
File /r "D:\Deploy\*.*"

/r 会递归保留 platforms/、imageformats/ 的层次，省掉逐条写。代价是 D:\Deploy 里有什么就带什么，调试文件、日志、临时产物都会被卷进去。部署目录干净的话，这一条最省事。

静默安装与卸载 #

NSIS 生成的安装包支持命令行参数，运维批量部署靠这个：MyQtApp-Setup.exe /S /D=C:\Program Files\MyQtApp 静默安装，Uninstall.exe /S 静默卸载。/S 必须在最前面，/D= 必须在最后且不带引号，顺序搞反参数就被忽略，然后弹一个界面卡住批处理。

编译与调试 #

bash
# /V4 是日志详细级别（0~4），路径找不到、文件重复这类问题全在日志里
makensis /V4 myapp.nsi

!echo 是编译期打印，只在日志里出现，不进最终安装包，排查 !define 拼接错误时很好用。

九、用 HM NIS Edit 做安装包 #

手写 .nsi 上手快，但第一次做还是向导省事。HM NIS Edit 的「新建脚本向导」能把属性、界面、文件、快捷方式一次问完，直接生成可编译的脚本。

向导步骤 #

  1. 启动向导。打开 HM NIS Edit，文件 → 新建脚本向导。
  2. 填写程序基本信息。软件名称、版本号、官方网站、开发作者。这几项会进 Name、OutFile 和控制面板的卸载信息。
  3. 设置安装选项。安装程序语言选 SimpChinese（简体中文），需要多语言就勾上英文。
  4. 目录与授权。指定默认安装路径（例如 $PROGRAMFILES\MySoft），指定许可协议文件（.txt 或 .rtf）。
  5. 添加发布文件。选中 .exe，再把依赖的 .dll 和含插件的整个文件夹加进来。
  6. 创建快捷方式。开始菜单、桌面各勾一下，顺便指定卸载图标。
  7. 编译脚本。勾上「保存脚本」和「编译运行」，NSIS 生成独立的 setup.exe。

第 5 步有个开关必须勾：添加文件夹时选「包含子目录」，并确认输出目标路径是 $INSTDIR。不勾，platforms/ 里的文件会被拍平，第三章讲的那种毛病当场复发。

向导生成的脚本片段 #

nsis
; 确保包含多语言支持
!insertmacro MUI_LANGUAGE "SimpChinese"

; 定义安装目录
InstallDir "$PROGRAMFILES\MyQtApp"

; 安装段落
Section "MainSection" SEC01
  SetOutPath "$INSTDIR"
  File "D:\Deploy\MyQtApp.exe"
  File "D:\Deploy\Qt5Core.dll"

  ; 保持插件子目录结构
  SetOutPath "$INSTDIR\platforms"
  File "D:\Deploy\platforms\qwindows.dll"
SectionEnd

向导生成的只是骨架，手动还得补三块：

  • 卸载段。向导会生成基础的 Uninstall 段，但注册表清理、桌面快捷方式删除要自己补全。
  • Unicode true。老版本向导生成的脚本不一定带这一行，中文路径会乱码。
  • RequestExecutionLevel admin。要写 HKLM 就必须有，缺了安装过程中静默失败，还不报错。

改完 .nsi 之后可以继续往上加：自定义注册表项、配置环境变量、调用第三方安装包做静默安装。安装流程的每一步都能改，不用迁就工具的固定套路。

十、发布包的目录组织 #

前面各章都在解决「文件从哪来」，这一章解决「文件往哪放」。目录摆错，前面全白干。

标准目录树 #

text
MyApp/
├── MyApp.exe
├── qt.conf
├── Qt6Core.dll
├── Qt6Gui.dll
├── Qt6Widgets.dll
├── libgcc_s_seh-1.dll
├── libstdc++-6.dll
├── libwinpthread-1.dll
├── platforms/
│   └── qwindows.dll
├── imageformats/
│   ├── qjpeg.dll
│   └── qsvg.dll
├── sqldrivers/
│   └── qsqlite.dll
├── styles/
│   └── qmodernwindowsstyle.dll
├── tls/
│   ├── qopensslbackend.dll
│   └── qschannelbackend.dll
└── translations/
    └── qt_zh_CN.qm
位置 内容 能少吗
根目录 exe、模块 dll、编译器运行时 不能，缺一个就起不来
platforms/ qwindows.dll 不能，缺了没有窗口
imageformats/ 图片格式插件 缺了图标和图片显示空白
sqldrivers/ 数据库驱动 用了数据库就不能少
styles/ 控件样式 缺了界面会退回老样式
tls/ TLS 后端 走 HTTPS 就不能少
translations/ 语言包 不要中文界面可以删

三条铁律：

  1. 子目录名不能改。platforms 就是 platforms，改成 plugins 再去指路，只会多一层麻烦。
  2. 子目录和 exe 的相对位置不能变。整个目录一起拷可以，单独把 exe 拎出去不行。
  3. exe 只认自己所在的目录。不是「程序的安装目录」，是「exe 所在目录」。快捷方式指向别处，插件就找不到。

qt.conf 的用法 #

Qt 找插件时会先看 QT_PLUGIN_PATH，再看 exe 所在目录，最后翻编译期写死的 Qt 安装目录。最后那一条在你的开发机上成立，在客户机上永远不成立。用 qt.conf 把搜索范围摁在程序目录：

text
[Paths]
Prefix = .
Plugins = .

Plugins = . 的意思是插件根目录就是 exe 所在的目录，于是 Qt 去找 ./platforms/qwindows.dll，正好对上标准布局。想验证这一条，把上面三行存成 qt.conf 放到 exe 旁边，再故意把 platforms 改名成 platform——报错会立刻出现，说明配置生效了。

想把插件收进一个子目录（根目录看着干净），换成：

text
[Paths]
Prefix = .
Plugins = plugins

插件路径就变成 ./plugins/platforms/qwindows.dll，安装包脚本里的目标路径也得跟着改。两个方案不要混着用，混用之后谁都说不清 Qt 到底在找哪。

qt.conf 必须和 exe 同级，文件名全小写，存成 UTF-8。放错层级，或者写成 Qt.conf，Qt 直接忽略，症状和没写这个文件完全一样。

打包前的检查清单 #

检查项 怎么查
用的是 Release 编译 exe 属性里的版本信息，或看有没有带 d 的库名
依赖全绿 Dependencies 扫一遍，没有红色问号
插件目录结构完整 platforms/qwindows.dll 存在，且和 exe 同级
没有调试残留 没有 .pdb、.ilk、*.log、.qmlc 缓存目录
干净机器能跑 找一台没装 Qt、没装 VS 运行库的虚拟机试
中文路径能跑 把目录改成 D:\测试\我的程序 再试一次
杀软不误报 拿安装包过一遍主流杀软，没签名的 NSIS 包被判风险程序是常事

版本与文件命名 #

发出去的包命名要写全四段：版本号、平台、架构、包类型，例如 MyApp-1.0.0-win64-setup.exe 或 MyApp-1.0.0-win64-portable.zip。别出现 setup(1).exe、新建文件夹.zip 这种东西，用户手里攒三个版本之后自己都分不清。

十一、常见错误与排查 #

症状和原因先列成表，赶时间直接对号入座。

现象 多半原因 处理
双击没反应，进程闪退 platforms/qwindows.dll 缺失或位置错 检查目录结构，或重跑 windeployqt
弹窗 no Qt platform plugin could be initialized 同上，插件目录被改名或被拍平 恢复 platforms/ 目录
提示缺少 VCRUNTIME140.dll MSVC 运行时没带 加 --compiler-runtime，或装 vc_redist
提示缺少 libgcc_s_seh-1.dll MinGW 运行时没带 从 MinGW 的 bin 拷三个 dll
报错 0xc000007b 32/64 位混用，或 Debug/Release 混用 统一架构，统一 Release
界面全白，控制台提示模块未安装 QML 模块没部署 加 --qmldir 重跑 windeployqt
图片显示不出来 imageformats 缺失 补 qjpeg.dll 等插件
数据库连不上 sqldrivers 缺失 补对应驱动 dll
exe 图标是空白 资源段没编译进去 检查 RC_ICONS / RC_FILE，重跑 qmake
中文乱码 安装包不是 Unicode NSIS 加 Unicode true

平台插件报错怎么查 #

这是新人撞坑率最高的一个。现象有两种：双击完全没反应；或者弹出 This application failed to start because no Qt platform plugin could be initialized。

排查顺序：

  1. 看目录。platforms/qwindows.dll 在不在 exe 同级？有没有被别的打包脚本拍平到根目录？
  2. 看名字。目录是不是被改成了 platform（少个 s）？是不是多了个空格？
  3. 手动指定。建 qt.conf，写 [Paths] / Plugins = .，把插件搜索范围摁在程序目录。
  4. 开日志。设 QT_DEBUG_PLUGINS=1，重跑，控制台会打出它找过的每一个路径，以及为什么放弃。

第 4 步最好用，日志里会清清楚楚写着 Cannot load library ... qwindows.dll: The specified module could not be found，后面跟着它试过的路径。看一眼就知道错在哪一层。

MinGW 运行库缺失 #

用 MinGW 编译的话，还得复制这三个 dll，从 MinGW 的 bin 目录拿：

text
├── libgcc_s_seh-1.dll    （64 位，SEH 异常模型）
├── libgcc_s_dw2-1.dll    （32 位，DWARF 异常模型）
├── libstdc++-6.dll
└── libwinpthread-1.dll

seh 和 dw2 按架构选，别两个都拷。拷错了的表现和缺文件一样，都是起不来。

OpenGL 相关 #

用了 OpenGL 的应用需要这些文件：

text
├── libEGL.dll
├── libGLESv2.dll
├── opengl32sw.dll        （软件渲染，20MB+）
└── d3dcompiler_47.dll    （ANGLE 后端要用）

目标机器有独显的话，多数不需要 opengl32sw.dll。加 --no-opengl-sw 把它排除，包能小 20MB。反过来，交付给一堆老集显办公机的场景，opengl32sw.dll 得留着，那是最后的兜底渲染路径。

调试用的环境变量 #

设了这些变量能看到详细日志：

bash
# Windows (PowerShell)
$env:QT_DEBUG_PLUGINS = 1
$env:QT_PLUGIN_PATH = "C:\path\to\plugins"
./myapp.exe

# Linux/macOS
QT_DEBUG_PLUGINS=1 ./myapp
变量 作用
QT_DEBUG_PLUGINS 打印插件加载全过程，排查平台插件首选
QT_PLUGIN_PATH 额外插件搜索路径，临时验证用
QT_LOGGING_RULES 按类别开关日志，如 qt.qpa.*=true
QT_QPA_PLATFORM 指定平台插件，如 windows、offscreen

QT_QPA_PLATFORM=offscreen 在无界面的 CI 机器上跑 GUI 测试时很有用，不弹窗也能初始化。

十二、易错点速查 #

# 易错点 正确做法
1 只发 exe 发整个目录，或做成安装包
2 把 platforms/ 里的 dll 拷到根目录 保持子目录结构，一个字符都不改
3 用 Debug 版打包 一律 Release，注意库名的 d 后缀
4 32 位库配 64 位 exe 架构统一，0xc000007b 多半是这个
5 忘了 Qt 之外的第三方库 windeployqt 之后再扫一遍 Dependencies
6 开发机上验证通过就发版 找一台干净机器跑，这是唯一可信的验证
7 静态编译还闭源卖 补目标文件或买商业许可
8 静态编译忘了 Q_IMPORT_PLUGIN 平台插件、图片插件都得显式导入
9 装完图标空白 检查 .rc 是否进了编译，qmake 要重跑
10 NSIS 里 File 直接拷插件 先 SetOutPath 切到子目录
11 安装包换 AppId 固定一个 GUID，升级才不会装出两份
12 发布包里留 .pdb 和日志 发布前过滤，pdb 另外归档留作崩溃分析

这 12 条不用背，打完第一个正式包基本都会撞一遍。其余那些单点问题，前面每一章末尾都交代过了。

发布这件事没有终点，只有一个又一个被踩平的坑。依赖带齐、目录摆对、安装包能装能卸，第一版就算过关。剩下的崩溃率、启动耗时、静默升级，都是下一轮的事。
