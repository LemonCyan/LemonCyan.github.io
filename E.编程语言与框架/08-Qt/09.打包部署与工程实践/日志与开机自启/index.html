先说边界：这篇只讲程序上线之后的两件运维事——日志怎么落地、程序怎么自己起来。

不讲安装包怎么做、依赖怎么打进去，那是本目录《打包与分发》的范围；不讲代码混淆与授权校验，那是《加密》那一篇；不讲 PDF 导出、打印排版，也不讲模型接入。

日志这块从 Qt 的消息机制讲到写盘、加锁、滚动、分级；自启这块从原理讲到 Windows 注册表、Linux 的 autostart 与 systemd，最后单独一节讲权限拦截。

我们假定你已经能编出一个能发给客户的 .exe 或可执行文件，剩下的问题是：它跑起来之后，你还看不看得见它。

一、上线之后的两件事 #

开发阶段我们靠 qDebug() 打天下。控制台一刷，走到哪个分支、变量是什么值，一眼就看明白。

程序装到客户机器上，这套办法当场失效。同时发生三件事：

  1. 控制台没了。用户双击图标启动，没有终端窗口，qDebug() 的输出落到 OutputDebugString，得挂 DebugView 才看得见。
  2. 用户不会复现。他只会说「它闪退了」「昨天还好好的」，然后等你远程。
  3. 电脑一重启，程序得自己爬起来。工控机、收银机、值班室的常驻程序，没人会天天手动双击。

前两条合成一个词：日志。第三条是自启。

这两件事有个共同点：都不是业务逻辑，却决定了上线之后的维护成本。功能写得再花，客户现场崩一次，你手里没有一份 .log，就只能靠猜。

维度 开发期 上线后
输出目标 终端 / IDE 的 Application Output 磁盘文件
谁来看 你自己 你，以及被你远程指挥的客户
时间差 当场 几小时到几天
输出量 想打多少打多少 必须可控，不能撑爆硬盘
关键问题 能不能看见 崩了之后，现场还在不在

日志要解决三个层次的诉求，我们对号入座：

  • 崩溃当场：qFatal 触发、程序 abort，最后那几行必须已经落在磁盘上，而不是还躺在缓冲区里。
  • 运行期异常：客户说「昨天下午卡过」，你得能把那段时间的 Warning 挑出来。
  • 长期回溯：文件不能无限长，得有滚动、有上限、有清理。

自启要解决的只有一个诉求：开机进桌面，程序在跑，而且不需要用户点一下「是」。

二、Qt 的日志体系 #

Qt 的日志不是「一个函数」，是一套分层的机制。分四层看：

第一层：打印宏。 qDebug()、qInfo()、qWarning()、qCritical()、qFatal()。这五个宏走同一条管道，只是级别不同。qFatal 特殊，打完就 abort()。

第二层：分类（category）。 QLoggingCategory 给日志打上模块标签，配合 qCDebug(cat) 用。它让「只开串口模块的日志」这种需求变得可行，而不是全局一把梭。

第三层：消息处理器（message handler）。 一个全局函数指针。所有日志最终都汇聚到它手上。这是我们接管输出的唯一入口，也是本篇的主角。

第四层：输出目标。 默认是 stderr（Windows 下同时走 OutputDebugString）。qInstallMessageHandler 换掉它，就变成文件、网络、界面控件，随便你。

默认输出长这样，一眼能看出没经过任何加工：

text
Debug: 串口打开成功
Warning: 校验和错误, 期望 0x1A 实际 0x00

老版本和新版本的接管 API 不一样，这是第一个坑：

cpp
// Qt 4.x 的旧接口，2013 年之后就不建议用了
Qt::qInstallMsgHandler(QtMsgHandler handler);

// Qt 5.x / Qt 6.x 的接口
Qt::qInstallMessageHandler(QtMessageHandler handler);

新接口多了一个 const QMessageLogContext & 参数。它不是摆设——通过它能直接拿到这条日志由 哪个源文件、第几行、哪个函数 打出来的。旧接口只能拿到类型和字符串，出问题时你只知道「有个 warning」，不知道在哪。

日志方式 输出目标 上线后能用 主要问题
裸 qDebug() 不管 stderr / 调试器 否 发布版用户看不到任何东西
qDebug() + 消息处理器写文件 磁盘 .log 是 要自己处理加锁、滚动
QLoggingCategory + 规则过滤 同上 是 多一层分类维护成本
QT_LOGGING_RULES 环境变量 同上 是 只能过滤，不能改格式
第三方库（spdlog / qsLog） 看库 是 多一个依赖，异步模型要自己调
系统日志（syslog / journald） 系统 是 客户导日志时找不到文件

对于绝大多数桌面程序，第二行就够了。写完发现文件撑大了，再加第六行的滚动。

还有一个不写代码也能用的开关：QT_LOGGING_RULES 环境变量。设成 *.debug=true;qt.*.debug=false，就是打开全部 debug、同时关掉 qt.* 内部模块的噪音，排查现场问题很顺手。

qSetMessagePattern() 能把默认输出改成 "[%{time yyyy-MM-dd hh:mm:ss.zzz}] %{type} %{message}" 这类格式，但它对我们写文件没有帮助——一旦 qInstallMessageHandler 接管，模式串就不再生效，格式得自己在 handler 里拼。第七章会再对一次账。

三、qInstallMessageHandler 的用法 #

先看原型：

cpp
typedef void (*QtMessageHandler)(QtMsgType type,
                                 const QMessageLogContext &context,
                                 const QString &msg);

QtMessageHandler qInstallMessageHandler(QtMessageHandler handler);

三件事必须刻在脑子里。

第一件：它是全局钩子，会拦截所有 qDebug / qWarning 输出。

不管这条日志是从主线程打的、从工作线程打的、还是从 Qt 自己的内部模块打的，全部流进你写的这个函数。没有例外，没有白名单（分类过滤要在更上游做）。反过来说，只要装上它，你程序里所有日志的出口就只有一个，格式、落盘、脱敏全在这一处收口。

第二件：这个函数在「打日志的那个线程」里同步执行。

qDebug() 调用返回之前，你的 handler 已经跑完了。工作线程调用 qDebug()，handler 就在工作线程里跑。这意味着两件事：

  • handler 里写的代码必须是线程安全的。多线程同时打日志时，会并发进入这个函数。
  • handler 里不能放耗时操作。你在这里 sleep(100)，所有正在打日志的线程一起陪睡，界面直接卡住。

第三件：返回旧处理器，传 nullptr 恢复默认。

它返回上一次安装的 handler，可以做链式接管（先过滤再落盘）。传 nullptr 就退回 Qt 的默认输出，调试时想临时关掉文件写入很方便。

最小可用的注册位置：

cpp
#include <QApplication>

int main(int argc, char *argv[])
{
    QApplication app(argc, argv);

    // 装得越早越好：QApplication 之后、任何业务代码之前
    qInstallMessageHandler(fileMessageHandler);

    qDebug() << "程序启动";
    return app.exec();
}

为什么强调「之后、之前」：

  • 放在 QApplication 构造之前，app 自己的初始化日志也会被接管，handler 里如果访问了还没初始化的全局对象就危险。
  • 放在业务代码之后，前面那些日志就漏掉了。启动阶段恰恰是最容易出问题的地方。

context 参数怎么用，有个必踩的坑。QMessageLogContext 的 file、function 是两个 const char *，在 Release 构建下它们往往是空指针。为什么？因为 Qt 默认在发布配置里关掉了这部分元信息来省体积（构建时定义 QT_NO_DEBUG_OUTPUT / 关闭 message context 收集）。直接 QString(context.file) 在 Debug 下跑得好好的，发到客户手里就段错误。

必须做非空判断：

cpp
QString filePath    = context.file     ? QString::fromUtf8(context.file) : QStringLiteral("UnknownFile");
QString funcName    = context.function ? QString::fromUtf8(context.function) : QStringLiteral("UnknownFunction");
int     lineNo      = context.line;
QString category    = context.category ? QString::fromUtf8(context.category) : QStringLiteral("default");

想强制保留这些信息，构建时把宏打开（代价是二进制大一点）：

ini
# qmake
DEFINES += QT_MESSAGELOGCONTEXT

# CMake
add_definitions(-DQT_MESSAGELOGCONTEXT)

QtFatalMsg 要单独说。handler 收到它，意味着程序马上就要 abort()。你在这个分支里必须保证日志已经落盘——flush() + close() 一步都不能省，否则别的分支的缓冲可以慢慢来，这一个不行。至于 qFatal 之后弹框，Qt 自己没有这个能力，得在 handler 里自己拉一个 QMessageBox（注意此时未必在主线程，要 QMetaObject::invokeMethod 转过去）。

还有一条纪律：handler 里不要再用 qDebug()。它会把日志重新送进 handler，轻则重复输出，重则递归打爆栈。要记录 handler 自己的错误，用 fprintf(stderr, ...) 或者直接不记。

四、日志重定向到文件 #

思路很直白：handler 里拼好一行字符串，追加写进文件。

写之前先定三件事：文件放哪、什么时候打开、按什么编码写。

文件放哪。 别写相对路径。QFile("app_run_log.txt") 用的是当前工作目录，从桌面快捷方式启动和从 C:\Windows\System32 启动，落点完全不同，客户拍给你的截图里根本找不到文件。用 QStandardPaths 拿系统给的规范目录：

cpp
QString logDir = QStandardPaths::writableLocation(QStandardPaths::AppDataLocation);
QDir().mkpath(logDir);                       // 目录不一定存在，先建
QString logPath = logDir + "/app_run_log.txt";

Windows 下落点是 C:\Users\<用户>\AppData\Roaming\<组织>\<应用名>，Linux 下是 ~/.local/share/<应用名>。这两个位置普通用户有写权限，不用提权，也不会被 UAC 拦。

什么时候打开。 最简单的写法是每行 open / close 一次。简单，正确，但慢——一行日志一次文件系统调用。日志密集时这部分开销能占满一个核。更好的做法是常开一个文件对象，用静态或单例持有，退出时 close。常开就要配合第六章的滚动逻辑，否则文件句柄一直指着旧文件。

按什么编码写。 QTextStream 默认跟随系统区域设置，中文在 GBK 环境下写出来的文件换台机器看就是乱码。显式指定编码。这里 Qt5 和 Qt6 的 API 不一样，是编译期就会报的硬错：

cpp
// Qt5：setCodec
stream.setCodec("UTF-8");

// Qt6：setCodec 被移除，改 setEncoding
stream.setEncoding(QStringConverter::Utf8);

完整实现，可以直接抄：

cpp
#include <QApplication>
#include <QDateTime>
#include <QDir>
#include <QFile>
#include <QMessageLogContext>
#include <QMutex>
#include <QMutexLocker>
#include <QStandardPaths>
#include <QTextStream>

static QMutex   g_logMutex;         // 保护下面三个静态状态
static QFile   *g_logFile   = nullptr;
static QString  g_logPath;

static QString levelName(QtMsgType type)
{
    switch (type) {
    case QtDebugMsg:    return QStringLiteral("Debug");
    case QtInfoMsg:     return QStringLiteral("Info");      // Qt 5.5+ 才有
    case QtWarningMsg:  return QStringLiteral("Warning");
    case QtCriticalMsg: return QStringLiteral("Critical");
    case QtFatalMsg:    return QStringLiteral("Fatal");
    }
    return QStringLiteral("Unknown");
}

void fileMessageHandler(QtMsgType type, const QMessageLogContext &context, const QString &msg)
{
    // 第一步永远是拿锁，不是拼字符串
    QMutexLocker locker(&g_logMutex);

    if (!g_logFile) {
        QString dir = QStandardPaths::writableLocation(QStandardPaths::AppDataLocation);
        QDir().mkpath(dir);
        g_logPath = dir + QStringLiteral("/app_run_log.txt");
        g_logFile = new QFile(g_logPath);
        g_logFile->open(QIODevice::WriteOnly | QIODevice::Append | QIODevice::Text);
    }
    if (!g_logFile->isOpen())
        return;                       // 打不开就静默放弃，不要在 handler 里抛异常

    // Release 下 file / function 为空指针，必须判空
    const QString file  = context.file     ? QString::fromUtf8(context.file)     : QStringLiteral("?");
    const QString func  = context.function ? QString::fromUtf8(context.function) : QStringLiteral("?");
    const QString cat   = context.category ? QString::fromUtf8(context.category) : QStringLiteral("default");

    const QString line = QStringLiteral("[%1] [%2] [%3] (%4:%5, %6) %7")
            .arg(QDateTime::currentDateTime().toString(QStringLiteral("yyyy-MM-dd hh:mm:ss.zzz")))
            .arg(levelName(type).leftJustified(8, QLatin1Char(' ')))
            .arg(cat)
            .arg(file)
            .arg(context.line)
            .arg(func)
            .arg(msg);

    QTextStream stream(g_logFile);
    stream.setEncoding(QStringConverter::Utf8);   // Qt5 用 setCodec("UTF-8")
    stream << line << '\n';
    stream.flush();          // 关键：刷出去，别留在缓冲区

    if (type == QtFatalMsg) {
        g_logFile->flush();
        g_logFile->close();  // 程序马上就 abort，这里必须收尾
    }
}

里面有三处容易被省掉、然后又回来找你的细节：

  • stream.flush()：不写这句，程序被任务管理器杀掉时，最后几行还在 QTextStream 的缓冲区里，跟着进程一起没了。而最后几行恰恰最值钱。
  • QDir().mkpath(dir)：第一次在干净机器上跑，AppData\Roaming\<你的组织> 这层目录不存在，open 直接失败，日志一个字节都没有。
  • isOpen() 判空：U 盘只读、目录被安全软件锁、磁盘满，都会让 open 失败。handler 里不能崩，也不能死循环重试。

顺带一句，QTextStream 每次构造都带一点开销，日志量大时可以把它也做成静态成员，生命周期和 g_logFile 对齐。不过要先解决第五章的问题。

五、日志为什么要加锁 #

这一节是整篇日志部分的重点，得讲透。

先看代码骨架里的两行：

cpp
static QMutex g_logMutex;
QMutexLocker locker(&g_logMutex);

为什么要加锁？不加会怎么样？

原因一：并发进入是常态，不是意外。

现代 Qt 程序里跑着一堆后台线程：网络请求线程、串口解析线程、定时任务线程、数据库轮询线程。每个线程都会打日志。而 handler 是全局的，这些线程调用 qDebug() 时，会在同一时刻并发进入同一个函数。你写的那几行代码，实际上是个多线程临界区，只是它长得不像。

原因二：两个线程同时写同一个文件，行会交错。

这是不加锁最直接的后果。假设线程 A 要写 [10:00:01] [Debug] 串口收到 128 字节，线程 B 要写 [10:00:01] [Debug] 网络心跳超时。没有锁，两边的 stream << line 会互相插进对方的输出流：

text
[10:00:01] [Debug] 串口收[10:00:01] [Debug] 网络心跳超时
到 128 字节

一条记录被劈成两半，中间塞进另一条的开头。这不是审美问题——你的日志解析脚本按行读，[10:00:01] [Debug] 串口收[10:00:01]... 这一行里两个时间戳、两个级别，正则直接报废。客户发来的日志里全是这种碎片，你连「崩之前最后一条是什么」都读不出来。

原因三：文件结构被写坏。

比交错更难查的是文件本身被写坏。两个线程同时 open(QIODevice::Append)，同时持有各自的写位置偏移，同时 flush，落盘的内容会出现覆盖、空洞、甚至半条 UTF-8 多字节字符（一个汉字被劈成两半，文件后半段全变乱码）。极端情况下 QFile 内部状态被多线程同时改，直接崩在写日志这一步——程序为了记录崩溃而崩溃。

原因四：静态初始化的竞争。

if (!g_logFile) { g_logFile = new QFile(...); } 这段第一次调用时的懒初始化，本身就要求互斥。两个线程同时进来，会 new 两个 QFile，一个泄漏，另一个被覆盖，两次 open 指向同一个文件但偏移不同。这就是为什么锁要拿在函数第一行，而不是拿到写文件那一步才拿。

那用 lock() / unlock() 行不行？

行，但别这么写。看这个结构：

cpp
g_logMutex.lock();
if (!g_logFile->open(...)) {
    return;                  // ← 提前 return，mutex 永远锁着
}
// ... 中间任何一处 return 或抛异常，都会漏掉 unlock
g_logMutex.unlock();

只要有一个出口漏掉 unlock()，锁就永远不释放。下一个打日志的线程卡死在 lock()，界面线程也跟着卡——因为界面线程也在打日志。表现为程序整体卡死，任务管理器里 CPU 占用为 0，你很难第一时间想到是日志锁的问题。

用 QMutexLocker：

cpp
QMutexLocker locker(&g_logMutex);

它靠 C++ 的析构保证解锁。函数从哪个出口退出、中途是否抛异常、是否提前 return，栈对象销毁时都会解锁。这是 RAII 的经典用法，别自己手写。

锁的粒度也要注意。锁只保护写文件这一段，不要连格式化字符串、取时间这些纯本地计算一起包进去。粒度太大，日志线程之间互相等，程序吞吐掉得看得见。我们上面那版实现里，锁是从函数头拿到函数尾——因为 g_logFile 的懒初始化需要它。如果改成 main() 里预先初始化好文件对象，锁的范围就能缩到只剩 QTextStream 那几行。

还有一个隐藏问题：锁只能保证同一进程内的串行。客户在同一台机器上开了两个实例、写同一个文件，QMutex 完全无效，还是交错。要么用单实例锁（QLockFile）把进程挡住，要么把文件名带上 PID：

cpp
g_logPath = dir + QStringLiteral("/app_run_log_%1.txt").arg(QCoreApplication::applicationPid());

六、日志滚动与清理 #

不滚动的日志文件唯一的下场是撑爆硬盘。工控机上跑三个月，一天二十万行，一个文件能干到几个 G。客户发现时是「磁盘满了，数据库写不进去」，而不是「日志太大了」。

滚动策略就三种，选一种就够，别都上：

策略 触发条件 优点 缺点
按大小 单文件超过 N MB 实现简单，上限可控 大日志集中的那天会切得很碎
按天 跨过 0 点 按日期找文件，现场友好 一天写爆时拦不住
按启动 每次启动新建 直接按运行批次分文件 频繁重启会堆一堆小文件

按大小滚动最通用。逻辑：写之前查 g_logFile->size()，超了就关掉、改名、开新文件。

cpp
static const qint64 kMaxSize  = 10LL * 1024 * 1024;   // 10 MB
static const int    kMaxFiles = 5;                     // 连当前文件共 5 个

static void rotateIfNeeded()
{
    if (g_logFile->size() < kMaxSize)
        return;

    g_logFile->close();

    // app_run_log.txt -> app_run_log.1.txt，逐个后移
    for (int i = kMaxFiles - 1; i >= 1; --i) {
        QString from = QStringLiteral("%1.%2.txt").arg(g_logBase).arg(i);
        QString to   = QStringLiteral("%1.%2.txt").arg(g_logBase).arg(i + 1);
        if (QFile::exists(to))
            QFile::remove(to);
        if (QFile::exists(from))
            QFile::rename(from, to);
    }
    QFile::rename(g_logPath, QStringLiteral("%1.1.txt").arg(g_logBase));

    g_logFile->open(QIODevice::WriteOnly | QIODevice::Append | QIODevice::Text);
}

rotateIfNeeded() 必须在已经持锁的情况下调用，否则改名窗口里另一个线程正往旧文件写，写到一半文件被 rename，Windows 下 rename 直接失败（文件被占用）。

按天滚动更适合客户支持：文件名带日期，客户说「昨天下午」，你让他直接把 app_run_log_2026-11-16.txt 发过来。

cpp
QString today = QDate::currentDate().toString(QStringLiteral("yyyy-MM-dd"));
QString want  = QStringLiteral("%1/app_run_log_%2.txt").arg(logDir, today);
if (want != g_logPath) {
    g_logFile->close();
    g_logPath = want;
    g_logFile->setFileName(want);
    g_logFile->open(QIODevice::WriteOnly | QIODevice::Append | QIODevice::Text);
}

清理这一半比滚动更容易忘。滚动只保证「总量有上限」，前提是你的序号链真的在删旧文件；只要有一处 remove 写漏，上限就是假的。另外两个地方会漏：

  • 崩溃转储目录：QStandardPaths 的 AppLocalDataLocation 下留的 .dmp，一份几十 MB，没人清。
  • 按天滚动的历史文件：客户装了一年，365 个文件，总量还是没上限。

启动时扫一遍目录，删掉超过 N 天或总量超上限的：

cpp
void cleanupOldLogs(const QString &dir, int keepDays)
{
    QDir d(dir);
    QDateTime cutoff = QDateTime::currentDateTime().addDays(-keepDays);
    const auto list = d.entryInfoList(QStringList() << QStringLiteral("*.txt"), QDir::Files);
    for (const QFileInfo &fi : list) {
        if (fi.lastModified() < cutoff)
            QFile::remove(fi.absoluteFilePath());
    }
}

这个函数放在 main() 里、装 handler 之前跑一次，不进 handler，也就不参与那把锁。

七、日志级别与格式化 #

级别不是装饰，是过滤的依据。发布版该打什么、不打什么，靠级别决定。

级别 宏 用途 发布版建议
Debug qDebug() 变量值、分支走向 默认关闭或只留关键模块
Info qInfo() 启动、配置加载、状态切换 保留
Warning qWarning() 可恢复的异常、降级 保留
Critical qCritical() 功能不可用、外部依赖失败 保留，且值得告警
Fatal qFatal() 致命错误，打完即 abort() 保留，必须落盘

五个级别里只有 qInfo() 是后加的（Qt 5.5），工程里如果还要兼容更老的 Qt，得自己 #if 或者在 handler 里用 default 兜住。

qDebug() 默认在发布版不是自动关闭的。很多人以为 Qt 会像 assert 那样在 Release 里剔掉它——不会。想关，两条路：

ini
# .pro：彻底移除 debug 输出，编译期就没了
DEFINES += QT_NO_DEBUG_OUTPUT

cpp
// 运行期：用规则过滤，发布版也能临时打开
qSetMessagePattern(...);        // 无效，接管后不起作用
QLoggingCategory::setFilterRules(QStringLiteral("*.debug=false"));

规则串在客户现场很好用，让客户自己改配置就能开日志：*.debug=true 打开全部，qt.*.debug=false 关掉框架噪音，serial.debug=true 只留串口模块。分隔符不一样——setFilterRules() 用换行，QT_LOGGING_RULES 环境变量用分号。

格式化这块，一行日志至少要能回答五个问题：什么时候、什么级别、哪个模块、哪个位置、发生了什么。我们的格式串是：

text
[2026-11-17 10:32:07.451] [Warning ] [serial] (serialport.cpp:214, onReadyRead) 校验和错误, 期望 0x1A 实际 0x00

五个字段对应 context 的五个成员：context.category、context.file、context.line、context.function，加上自己取的时间。

对齐用 leftJustified()。级别名长短不一（Debug 5 个字符，Critical 8 个），不对齐的话后续字段左右跳，肉眼扫起来很累：

cpp
.arg(levelName(type).leftJustified(8, QLatin1Char(' ')))

注意 leftJustified 的参数是字符数，Critical 正好 8 个，Debug 补 3 个空格。中文日志内容不要参与对齐，一个汉字占两个显示宽度，QString 的长度算不对。

context.file 拿到的是编译时的完整路径，比如 C:/build/project/src/net/serialport.cpp。直接写进日志又长又暴露构建机目录结构，取文件名就够：

cpp
QString shortFile = QFileInfo(file).fileName();

最后是时间格式。yyyy-MM-dd hh:mm:ss.zzz 带毫秒，多线程日志排序靠它；不带毫秒的话同一秒内的十几行顺序是乱的。QDateTime::currentDateTime() 每次调用有系统调用开销，日志量特别大时可以缓存毫秒值，但别为此引入复杂度——先量一下再优化。

八、开机自启的实现原理 #

系统怎么知道该启动哪些程序？

答案很朴素：系统在你登录（或开机）时，去几个固定位置读一份名单，逐条执行。 没有魔法，没有进程间通知。你想自启，就把自己写进那份名单。

名单有五个常见位置，按「谁来执行」分两类：

  • 桌面会话类：资源管理器 / 桌面会话在用户登录后执行。Windows 的 Run 键、启动文件夹，Linux 的 autostart 目录都属于这类。跑在用户会话里，有界面，能弹窗。
  • 服务类：系统的服务管理器在开机早期拉起。Windows 的服务、Linux 的 systemd 系统级服务属于这类。跑在会话 0 或独立会话里，没有桌面，不能直接建窗口。

这个分类决定了后面所有坑的形态。放错位置，程序要么不启动，要么启动后白屏。

再看「谁的身份」：

位置 生效范围 触发时机 有界面 需要管理员
HKCU\...\Run 当前用户 用户登录后 有 否
HKLM\...\Run 所有用户 用户登录后 有 是
启动文件夹 shell:startup 当前用户 用户登录后 有 否
计划任务（用户级） 指定用户 登录或定时 有 否
计划任务（最高权限） 指定用户 登录或定时 有 创建时需要
Windows 服务 全机 开机早期 无 是
~/.config/autostart/*.desktop 当前用户 桌面会话启动后 有 否
/etc/xdg/autostart/*.desktop 所有用户 桌面会话启动后 有 是
systemd --user 服务 当前用户 用户 session 建立 取决于会话 否
systemd 系统服务 全机 开机早期 无 是

「有界面」这一列最关键。Qt 程序只要创建 QApplication 并 show() 一个窗口，就必须放在有界面的那一类。把 GUI 程序塞进 Windows 服务，或用系统级 systemd 服务拉起，症状是：进程在，日志在，窗口永远不出现。

自启还有一个和手动启动的根本差异，很多人在这里翻车：自启时的运行环境和你双击时不一样。

  • 工作目录不是程序目录，而是系统目录。所有相对路径全部失效，配置读不到、日志写不出。
  • PATH 更短，依赖的 DLL / 库搜索路径缺项。
  • 启动时机太早，网络还没就绪，数据库服务还没起来。
  • Windows 下映射的网络驱动器尚未恢复，Linux 下 $DISPLAY 还没设。

对应三条纪律：路径一律用绝对路径；启动后延迟几秒再干重活；连不上就重试，别第一次失败就退出。

九、Windows 下的注册表方式 #

Windows 存放当前用户开机启动项的注册表路径：

text
HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run

登录时，资源管理器读这个键下的所有值，键名是显示名，值是命令行，逐条 CreateProcess。所以自启的本质就是写一条「名字 → 命令行」的键值。

在 Qt 里读写它不用碰 Win32 API，QSettings 的 NativeFormat 在 Windows 下直接映射到注册表：

cpp
#include <QApplication>
#include <QDir>
#include <QSettings>

#define REG_RUN "HKEY_CURRENT_USER\\Software\\Microsoft\\Windows\\CurrentVersion\\Run"

/**
 * @brief 设置程序是否开机自启动
 * @param is_auto_start true 为开启自启动，false 为取消自启动
 */
void SettingDialog::setAutoStart(bool is_auto_start)
{
    // 获取应用程序名称（用作注册表中的键名）
    QString application_name = QApplication::applicationName();

    // 实例化 QSettings 对象，指定 NativeFormat（Windows 下即为读写注册表）
    QSettings settings(QStringLiteral(REG_RUN), QSettings::NativeFormat);

    if (is_auto_start)
    {
        // 取当前可执行文件的绝对路径
        QString application_path = QApplication::applicationFilePath();

        // Windows 路径用反斜杠，Qt 默认返回正斜杠，必须替换
        application_path.replace(QLatin1Char('/'), QLatin1Char('\\'));

        // 路径里有空格时必须整体加引号，否则命令行会被拆开
        if (application_path.contains(QLatin1Char(' ')))
            application_path = QLatin1Char('"') + application_path + QLatin1Char('"');

        settings.setValue(application_name, application_path);
    }
    else
    {
        // 从注册表中移除启动项
        settings.remove(application_name);
    }
}

四个 API 各管一段：

  • QApplication::applicationName()：拿程序名，作为注册表键值对的 Key。它来自 setApplicationName()，没设过就取可执行文件名。
  • QApplication::applicationFilePath()：拿可执行文件完整路径，作为 Value。注意它返回的是正斜杠路径。
  • replace('/', "\\")：注册表命令行要反斜杠。路径分隔符不对，登录时启动直接失败，事件查看器里连条错误都没有。
  • 引号：C:\Program Files\QtDemo\QtDemo.exe 不加引号，CreateProcess 把它当命令 C:\Program 加参数 Files\QtDemo\...，静默失败。这是最阴的一个坑，很多示例代码里就漏了这一步。

QSettings 用完就析构，不要 new 出来再 delete——栈对象更安全，异常路径也不会泄漏。

验证。 别靠猜，直接看。

  1. Win + R，输入 regedit，回车。
  2. 展开到 HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run。
  3. 右侧应出现一条以程序名为键、以可执行文件路径为值的数据。

命令行验证也行，适合写进自动化脚本：

bash
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Run" /v QtDemo

UI 上的开关得有初始状态。 用户上次勾了自启，重开设置页面必须是勾着的。判断方法不是「键存在」，而是「值等于当前路径」——程序被移动过目录，旧路径的键就是脏数据，该重写。实现上就一行：用同一个 QSettings 取 value(applicationName()).toString()，和 applicationFilePath() 按上面的规则转义（反斜杠 + 空格加引号）之后的结果比一次字符串。

键名要唯一。 用 applicationName() 当键名有个风险：两个不同厂商的程序重名，后写的覆盖先写的。稳妥做法是用带组织名的固定串，比如 LiuLuhua.QtDemo。

卸载要清。 安装包卸载时如果删了目录却留下 Run 键，下次开机系统会尝试启动一个不存在的 exe，部分机器会弹错误框。卸载脚本里加一句：

bash
reg delete "HKCU\Software\Microsoft\Windows\CurrentVersion\Run" /v QtDemo /f

RunOnce 与启动文件夹。 同一个位置下还有个 RunOnce 键，值执行完自动删除，适合「装完重启一次跑配置向导」。启动文件夹的等价物是 %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup，在资源管理器地址栏输入 shell:startup 直达，往里面丢快捷方式即可——不想改注册表时用这个，副作用是用户能自己删。

32/64 位重定向。 64 位系统上，32 位程序访问 HKLM\Software\... 会被重定向到 Wow6432Node。HKCU\...\Run 这一支不受影响，所以写自启尽量用 HKCU，同时避开这个坑和提权问题。

十、Linux 下的 autostart 与 systemd #

Linux 桌面没有注册表。等价的机制是 XDG Autostart：桌面会话启动时，扫描两个目录里的 .desktop 文件并逐个执行。

text
~/.config/autostart/            # 当前用户
/etc/xdg/autostart/             # 全机，需要 root

写一个 .desktop 就行，不用改任何系统配置：

ini
[Desktop Entry]
Type=Application
Name=QtDemo
Comment=开机自启的 Qt 程序
Exec=/opt/qtdemo/QtDemo --tray
Path=/opt/qtdemo
Terminal=false
Hidden=false
X-GNOME-Autostart-enabled=true

几个字段各有各的脾气：

  • Exec 必须绝对路径。自启时 PATH 和你登录 shell 里的不一样，写个 QtDemo 会找不到。
  • Path 是工作目录。它决定了程序里相对路径的基准，不写就是 $HOME。
  • Terminal=false。设成 true 会拉一个终端窗口出来，用户第一眼就是满屏黑框。
  • X-GNOME-Autostart-enabled=true 是 GNOME 系的开关，KDE 忽略它但也不报错。
  • Hidden=true 表示禁用但不删文件，做「取消自启」时用它比删文件平滑。

权限要给对：文件 644，属主是自己。600 某些实现会拒绝读取。

用 Qt 生成这个文件，顺带处理「删掉旧的」：

cpp
void setAutoStartLinux(bool enable)
{
    const QString dir  = QDir::homePath() + QStringLiteral("/.config/autostart");
    const QString path = dir + QStringLiteral("/qtdemo.desktop");
    if (!enable) { QFile::remove(path); return; }

    QDir().mkpath(dir);
    QFile f(path);
    if (!f.open(QIODevice::WriteOnly | QIODevice::Truncate | QIODevice::Text))
        return;

    QTextStream out(&f);
    out.setEncoding(QStringConverter::Utf8);   // Qt5 用 setCodec("UTF-8")
    out << "[Desktop Entry]\n" << "Type=Application\n" << "Name=QtDemo\n"
        << "Exec=" << QCoreApplication::applicationFilePath() << "\n"
        << "Terminal=false\n" << "X-GNOME-Autostart-enabled=true\n";
    f.close();
    QFile::setPermissions(path, QFile::ReadOwner | QFile::WriteOwner
                               | QFile::ReadGroup | QFile::ReadOther);
}

装完可以本地校验一下，写错了字段名它直接告诉你：

bash
desktop-file-validate ~/.config/autostart/qtdemo.desktop

autostart 的边界很清楚：它只在桌面会话里生效。没有桌面的服务器、开机就要跑的守护进程，得用 systemd。

systemd 用户服务。 适合「用户登录后常驻、要重启自愈」的程序。文件放 ~/.config/systemd/user/qtdemo.service：

ini
[Unit]
Description=QtDemo 常驻服务
After=graphical-session.target

[Service]
Type=simple
ExecStart=/opt/qtdemo/QtDemo
Restart=always
RestartSec=3
Environment=DISPLAY=:0
Environment=QT_QPA_PLATFORM=xcb

[Install]
WantedBy=default.target

启用：

bash
systemctl --user daemon-reload
systemctl --user enable --now qtdemo.service
systemctl --user status qtdemo.service

Restart=always 是 systemd 相对 autostart 的核心优势：程序崩了自动拉起来，客户不用打电话告诉你「它自己没了」。autostart 没有这能力，它只负责登录那一次。

两个必须知道的差异：

  • --user 服务要有用户 session。 通过 SSH 登录的用户，systemctl --user 需要 loginctl enable-linger <user> 才在未登录时也运行。
  • 图形程序要 DISPLAY。 Environment=DISPLAY=:0 是硬编码，多显示器或 Wayland 下不一定成立。Wayland 会话下该用 QT_QPA_PLATFORM=wayland，或者干脆退回 autostart 让桌面会话自己去处理环境。

系统级服务。 放 /etc/systemd/system/qtdemo.service，WantedBy=multi-user.target，User= 指定运行身份。这一层开机早期就启动，没有 X 会话。除非你的程序是纯后台（托盘都不要），否则不要用。

macOS 顺带一句。 ~/Library/LaunchAgents/*.plist 加 launchctl load，等价于 Windows 的 Run 键。本目录的程序面向 Windows / Linux 为主，这里不展开。

十一、权限与 UAC 拦截 #

这一节是自启部分真正的难点，把因果理清。

先分清两件事，它们的表现完全不同。

第一件：写 Run 键本身要不要管理员？不要。

HKEY_CURRENT_USER 是当前用户自己的分支，普通权限可写。所以 QSettings 往 HKCU\...\Run 写值，不会弹 UAC，也不需要 requireAdministrator。常听到的说法是「改注册表涉及系统安全，会被拦」——被拦的是 HKEY_LOCAL_MACHINE，或者被安全软件的行为规则拦，不是 UAC。写 HKLM 才需要提权，而且提权之后写进去的键属于「所有用户」，卸载时你还得有权限删。

第二件（真正的坑）：exe 声明了 requireAdministrator，Run 键就废了。

这是最关键的一条，也是最容易被只讲一半的地方。

程序的清单（manifest）里如果写了 requireAdministrator，那么每次启动它都必须经过 UAC 确认。你双击，弹框，点「是」，正常。但登录时由资源管理器通过 Run 键拉起它，没有任何界面可以弹——UAC 无法在登录早期向用户请求确认，于是启动被直接拒绝。表现为：注册表里键在，路径对，重启之后程序就是不出现。事件日志里能找到一条 740 之类的错误，但客户不会去看。

结论：要管理员权限的程序，不能用 Run 键自启，也不能用启动文件夹。

正确的三条路：

做法 权限 是否弹 UAC 适用
HKCU\...\Run 普通用户 否 不需要提权的普通程序
计划任务 + 「使用最高权限运行」 管理员 创建时一次 需要提权，要界面
Windows 服务 LocalSystem 否 纯后台，不要界面
启动时手动右键「以管理员身份运行」 管理员 每次都弹 不可接受的方案

方案一：计划任务。 这是提权自启的标准答案。任务创建时登记一次，之后每次触发都以最高权限运行，不再弹 UAC。

bash
schtasks /create /tn "QtDemo" /tr "C:\Program Files\QtDemo\QtDemo.exe" ^
         /sc onlogon /rl highest /f
  • /sc onlogon：用户登录时触发，等价于 Run 键的时机。
  • /rl highest：以最高权限运行，这是关键参数。
  • /f：覆盖同名任务。

想开机就跑（不等登录），用 /sc onstart，但那条要求任务以 SYSTEM 身份运行（/ru SYSTEM），此时的进程在会话 0，界面出不来。

Qt 里直接 QProcess 调这条命令就行，参数逐个塞进 setArguments()，注意它会闪一下黑框——要消掉得给进程加 CREATE_NO_WINDOW，或者干脆调 ITaskService COM 接口。/tr 的路径要加引号（/tr "\"C:\Program Files\...\""），而且创建 highest 级别的任务本身需要管理员权限，这件事放在安装阶段做最合适：安装包本来就在提权状态下跑。

方案二：Windows 服务。 程序本身要能当服务跑（QCoreApplication，无窗口，实现 SERVICE_MAIN_FUNCTION 或套一层 QService），用 sc 注册：

bash
sc create QtDemo binPath= "C:\Program Files\QtDemo\QtDemo.exe" start= auto
sc failure QtDemo reset= 86400 actions= restart/5000/restart/5000/restart/5000

start= auto 让它在开机时自动启动，sc failure 配的是崩溃自愈。这条路的代价是：没有界面。要跟用户交互，得让服务再 CreateProcessAsUser 拉起一个 GUI 进程，复杂度上一个量级。非必要不走这条。

改清单这条路。 让程序默认以管理员身份运行。Visual Studio 下：

  1. 工程上右键 → 属性
  2. 链接器 (Linker) → 清单文件 (Manifest File)
  3. UAC 执行级别 (UAC Execution Level) 设为 requireAdministrator

重新生成后，.exe 图标右下角会多一个小盾牌，表示每次启动都要申请管理员权限。

这个设置能解决「需要写系统目录 / 改 HKLM / 装驱动」的场景，但代价要一并算清楚：

  • 每次启动都弹 UAC，用户会烦。开机自启这条路直接堵死（见上）。
  • 拖拽文件到窗口失效。UIPI 隔离下，普通权限的资源管理器不能把数据丢给高权限进程，WM_DROPFILES 收不到。
  • QSettings 的 HKCU 变成了「管理员账户的 HKCU」。同一个 Windows 账户提权后写的是同一份注册表，但如果用户是标准账户、UAC 提权用的是另一个管理员账户，配置就串了——用户在设置里改的选项，下次启动读不到。
  • 程序写出的文件属主是管理员，普通权限的后续进程改不了。

所以判断标准只有一条：能不整体提权，就不要整体提权。 只把需要提权的动作拆到一个小的 helper 进程里，主程序保持普通权限，主程序的 Run 键自启照常工作。

手动调低 UAC 级别。 还有另一条思路：指导用户在控制面板里把 UAC 滑块调低，让拦截不再发生。技术上可行，实操上不建议——降低的是全系统的防护等级，为一个程序的便利去改用户的机器安全设置，代价不对等，而且企业环境里往往被组策略锁死，改不动。

安全软件拦截。 写 Run 键是勒索软件和木马的经典行为，杀软的行为引擎会盯这一处。症状：注册表写入成功，重启后程序没起来，或者干脆写入就被静默回滚。三条对策：给安装包和 exe 做代码签名；在杀软里加目录白名单（安装包里预置）；把自启改成安装时由安装程序完成（安装过程本身是被信任的用户动作）。

再补三条不写在表里、但值得记住的：

一、自启和日志要在同一个人手里管。 自启的程序崩在启动早期，用户只看到「没反应」。这时候唯一能定位问题的就是启动头几行日志，所以日志要在 QApplication 构造之后立刻装好，越早越好。

二、别在 handler 里做任何会失败、需要重试的事。 网络上报、弹窗、读配置，全都不行。handler 只干一件事：把字符串写下去。

三、自启开关要有反馈。 用户点完「开机自启」，注册表写没写成功、.desktop 文件建没建出来，界面得给个明确结果。写失败了还显示「已开启」，客户下次重启发现没起来，信任就没了。
