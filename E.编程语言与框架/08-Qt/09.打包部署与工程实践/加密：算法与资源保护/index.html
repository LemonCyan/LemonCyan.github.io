开篇边界说明

这篇讲两件事：程序里要用加密算法时怎么选、怎么落地；.qrc 里的资源怎么做到不被随手抠出来。

不讲密码学的数学推导，不讲 TLS 握手细节，也不讲服务端密钥管理体系的搭建。Qt 自己没有加密模块，真正加解密的代码全落在第三方库上，这篇把库的边界和接法说清，不写成密码学教材。

跨篇指路：资源怎么打进二进制、windeployqt 怎么裁依赖，看同目录的打包与分发那篇；发布后体积和启动速度怎么算账，看发布后的性能问题那篇。这里只谈数据保护。

先把话说在开头：只要密钥在客户端，就一定能被找到。 下面所有方案的目标都是抬高提取成本，没有一种能承诺绝对安全。

一、加密要解决的三个问题 #

新手把「加密」当一个动作，老手知道它其实是三件事。你手上有一段数据，要保护它，先问自己到底怕哪一种损失。

问题 要回答的疑问 对应手段 用错会怎样
机密性 别人拿到字节，能不能读懂 对称加密、非对称加密 用哈希代替加密，数据直接丢失
完整性 数据有没有被改过一位 哈希校验、HMAC、AEAD 不校验，被篡改的配置照样加载
身份 这份数据是谁给的 数字签名、证书链 不验签，伪造的更新包直接装上

三个问题里，容易混淆的是第一个和第二个。哈希能验完整性，但它不可逆，拿哈希当「加密」用，原始数据就再也拿不回来了。这个错误在 Qt 项目里出现频率很高，因为我们手上唯一的原生密码学类就是算哈希的。

还有第四个隐含问题：密钥怎么送到用它的地方。 它不属于上面三者，但决定整个方案能不能成立。对称加密快，密钥分发难；非对称加密慢，但能解决分发。这条主线会贯穿全文。

判断需求时先落一句话：我要防的是「看不见内容」，还是「改了不知道」，还是「冒充发送方」。三者的技术选型完全不同，混着做就一定会做错。

二、Qt 自带的密码学能力 #

Qt 在密码学上非常克制。QtCore 里跟密码学沾边的只有几个类，QtNetwork 里那几个只是 OpenSSL 的包装。先把边界摸清，后面才不会到处找不存在的 API。

2.1 QCryptographicHash #

QCryptographicHash 是 QtCore 提供的密码散列生成类，可以算二进制或文本数据的摘要。它在 QtCore 4.3 引入。

公共类型只有一个枚举：

cpp
enum Algorithm {
    Md4, Md5, Sha1, Sha224, Sha256, Sha384, Sha512,
    Sha3_224, Sha3_256, Sha3_384, Sha3_512
};

枚举值与引入版本：

QCryptographicHash::Sha1 2 生成一个 SHA-1 散列 QtCore 4.3
QCryptographicHash::Sha224 3 生成一个 SHA-224 散列（SHA-2） Qt 5.0
QCryptographicHash::Sha256 4 生成一个 SHA-256 散列（SHA-2） Qt 5.0

静态方法只有一个，也是最常用的那个：

cpp
QByteArray QCryptographicHash::hash(const QByteArray &data, Algorithm method);

看到这里要记住一个事实：这个类只能算散列，算不出原文，也没有任何解密接口。 它的用途是校验和指纹，不是加密。类名里的 Cryptographic 指的是算法属性，不是能力属性。

这张表建议贴在工位上，省掉一半翻文档的时间。

三、哈希与校验 #

散列是 Qt 里唯一能直接用的密码学能力，所以也最容易被用错。

3.1 两种写法 #

对一个内容为 password 的字符串算 MD5，两种写法等价。

静态方法，一次性数据用它最省事：

cpp
QByteArray byte_array;
byte_array.append("password");
QByteArray hash_byte_array = QCryptographicHash::hash(byte_array, QCryptographicHash::Md5);
QString md5 = hash_byte_array.toHex();

对象方式，适合分多次喂数据：

cpp
QByteArray byte_array;
byte_array.append("password");

QCryptographicHash hash(QCryptographicHash::Md5);
hash.addData(byte_array);              // 添加数据到散列计算
QByteArray result_byte_array = hash.result();   // 返回最终散列值
QString md5 = result_byte_array.toHex();

两种写法得到同一个结果：

text
5f4dcc3b5aa765d61d8327deb882cf99

这个值可以在任意在线 MD5 工具里验证。它就是 password 这六个字符的 MD5，一个人人都在用的口令样本，用途仅限于验证你的代码写对了没有。

result() 返回的是 QByteArray 原始字节，长度按算法不同而不同。直接 qDebug() 打出来是乱码，必须 toHex() 转成十六进制字符串才是我们平时看到的那串。

3.2 大文件与流式校验 #

校验一个 2 GB 的安装包，不能整个读进内存。addData(QIODevice *) 就是为这个场景准备的：

cpp
bool fileDigest(const QString &path, QByteArray *out)
{
    QFile f(path);
    if (!f.open(QIODevice::ReadOnly))
        return false;

    QCryptographicHash hash(QCryptographicHash::Sha256);
    if (!hash.addData(&f))          // 读到底，失败返回 false
        return false;

    *out = hash.result();
    return true;
}

用法：

cpp
QByteArray digest;
if (fileDigest("setup.exe", &digest))
    qInfo() << digest.toHex();

addData(QIODevice *) 内部按块读，内存占用不随文件大小增长。这是 Qt 里做大文件校验最省心的写法，不需要自己写 while (read()) 循环。

对象可以 reset() 后复用。批量校验一堆文件时，省掉反复构造的开销。

3.3 加盐 #

同样的口令，散列值永远一样。这意味着两件事：攻击者可以拿预计算表直接反查；两个用户口令相同，你能从库里看出来。

加盐就是往口令前后拼一段随机字节再散列：

cpp
QByteArray saltedHash(const QByteArray &password, const QByteArray &salt)
{
    QCryptographicHash h(QCryptographicHash::Sha256);
    h.addData(salt);
    h.addData(password);
    return h.result();
}

盐要每个用户一份，随散列值一起存，本身不需要保密。盐的作用是让预计算表失效，让相同口令产生不同结果。

但盐挡不住暴力枚举，它只让「一次算好、反复查表」变贵。真要存口令，用 QPasswordDigestor::deriveKeyPbkdf2，把迭代次数拉上去，让每次尝试都变慢。慢就是这里的防御手段本身。

3.4 MD5 与 SHA-1 的差别 #

两者都由 MD4 导出，结构相似，强度和特性也接近。差别有三点。

维度 MD5 SHA-1
摘要长度 128 位 160 位，比 MD5 长 32 位
抗暴力碰撞 找到同摘要报文约 2^128 量级操作 约 2^160 量级操作
抗密码分析 设计上更易受密码分析攻击 结构上更稳一些
速度 同硬件上更快 比 MD5 慢

摘要长 32 位带来的差距不是 32 倍，是指数级的量级差。这也是 SHA-1 在抗强攻击上占优的原因。

3.5 碰撞是怎么回事 #

散列函数输出定长，输出空间是有限集合；输入可以是任意长度的信息，是无限集合。两个集合之间不存在一一对应，就一定存在不同的明文算出同一个散列值的情况，这就是碰撞。

这个结论是数学上的必然，跟算法好坏无关。算法好坏决定的是「找到碰撞有多难」。

MD5 与 SHA-1 曾被当作足够安全的散列算法。后来的研究让短时间内构造碰撞成为现实，王小云教授的方法在这件事上有公开的贡献记录。这不等于两种算法「失效」了——散列的部分原有用途仍然成立，但新项目做安全用途时不要选它们，选 SHA-256。

素材里给过一个组合思路：把数据 A 做 MD5 得 B，再做 SHA 得 C，把 B 与 C 结合（比如相加）后再散列一次，用组合降低碰撞概率。这个思路在当年有意义，今天没必要——直接用 SHA-256 或 SHA-3，长度和抗碰撞性都比拼接两个弱散列更可靠，还少一次计算。不建议用于新项目的东西就别再包装一层继续用。

四、对称加密 #

一把钥匙，加密用它，解密也用它。速度快、开销小，适合大批量数据。

4.1 常见算法对照 #

算法 类型 块/流 密钥长度 现状
AES 对称 分组，128 位块 128 / 192 / 256 位 主流选择
ChaCha20 对称 流式 256 位 移动端与无 AES 硬件加速时更合适
DES 对称 分组，64 位块 56 位 不建议用于新项目
3DES 对称 分组，64 位块 112 / 168 位 不建议用于新项目
SM4 对称 分组，128 位块 128 位 国内合规场景

密钥长度不是随便填的。AES-128 的密钥必须正好 16 字节，AES-256 必须 32 字节。长度不对，库会直接报错或者悄悄截断，后者更麻烦。

4.2 分组模式比算法更容易出错 #

同一个 AES，配上不同模式，安全性差别很大。

模式 要 IV 要填充 自带完整性校验 能不能用
ECB 否 是 否 不要用，相同明文块出相同密文块
CBC 是 是 否 能用，但必须配 HMAC
CTR 是 否 否 能用，同样要配校验
GCM 是（nonce） 否 是 首选，一次搞定机密性与完整性

ECB 的问题很直观：它把每个 16 字节块独立加密，同一张图里相同的色块加密后还是相同的色块，图像轮廓一眼能看出来。这跟「加密强度」无关，是模式的结构缺陷。

GCM 属于 AEAD，加密的同时产出认证标签。解密时标签对不上就拒绝输出，篡改当场被发现。自己用 CBC 加 HMAC 也能达到同样效果，但顺序和密钥分离容易写错，能用 GCM 就用 GCM。

4.3 IV 与 nonce #

IV 不是密钥，不需要保密，但每次加密都必须不同。CBC 下 IV 要随机且不可预测；GCM 下 nonce 重复是致命错误，会导致密钥流复用。

IV 随密文一起存储，明文放着就行。常见的存法是文件头里留 16 字节：

text
[ 16 字节 IV ][ N 字节密文 ][ 可选 16 字节 GCM tag ]

把 IV 写死在代码里，等于所有文件用同一条密钥流，CBC 下相同前缀的明文会产出相同前缀的密文。素材里的示例脚本把 KEY 和 IV 都写成常量，那是演示代码，生产环境这两行都得换掉。

4.4 用 OpenSSL 做 AES #

Qt 没有 AES，用 OpenSSL 的 EVP 接口。EVP 是一层统一封装，换算法只改几个参数。

cpp
#include <openssl/evp.h>
#include <openssl/rand.h>

QByteArray aesGcmEncrypt(const QByteArray &plain, const QByteArray &key)
{
    QByteArray iv(12, Qt::Uninitialized);
    if (RAND_bytes(reinterpret_cast<unsigned char *>(iv.data()), iv.size()) != 1)
        return {};

    EVP_CIPHER_CTX *ctx = EVP_CIPHER_CTX_new();
    if (!ctx)
        return {};

    QByteArray out(plain.size() + 16, Qt::Uninitialized);
    int len = 0, total = 0;

    EVP_EncryptInit_ex(ctx, EVP_aes_256_gcm(), nullptr, nullptr, nullptr);
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_IVLEN, iv.size(), nullptr);
    EVP_EncryptInit_ex(ctx, nullptr, nullptr,
                       reinterpret_cast<const unsigned char *>(key.constData()),
                       reinterpret_cast<const unsigned char *>(iv.constData()));

    EVP_EncryptUpdate(ctx, reinterpret_cast<unsigned char *>(out.data()), &len,
                      reinterpret_cast<const unsigned char *>(plain.constData()),
                      plain.size());
    total = len;

    EVP_EncryptFinal_ex(ctx, reinterpret_cast<unsigned char *>(out.data()) + len, &len);
    total += len;

    unsigned char tag[16];
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_GET_TAG, sizeof(tag), tag);
    EVP_CIPHER_CTX_free(ctx);

    out.resize(total);
    return iv + out + QByteArray(reinterpret_cast<char *>(tag), sizeof(tag));
}

解密时把 EVP_Encrypt* 换成 EVP_Decrypt*，并在 EVP_DecryptFinal_ex 之前用 EVP_CTRL_GCM_SET_TAG 把 tag 喂进去。EVP_DecryptFinal_ex 返回 ≤ 0 就是校验失败，此时不要使用解出来的明文。

RAND_bytes 取随机数，失败返回非 1。这个返回值必须检查，随机源不可用时生成的 IV 就是可预测的。

4.5 大文件要分块 #

一次性把 500 MB 读进内存不可行。EVP 支持分段喂数据，EVP_EncryptUpdate 可以反复调用：

cpp
constexpr int kBufSize = 64 * 1024;
QByteArray buf(kBufSize, Qt::Uninitialized);

while (true) {
    qint64 n = in.read(buf.data(), kBufSize);
    if (n <= 0)
        break;
    int len = 0;
    EVP_EncryptUpdate(ctx, outBuf, &len,
                      reinterpret_cast<const unsigned char *>(buf.constData()),
                      static_cast<int>(n));
    out.write(reinterpret_cast<char *>(outBuf), len);
}

分块大小对齐到 16 字节不是必须的，EVP 内部会缓冲不完整块。真正必须对齐的场景是自己实现分组逻辑，用库就别操这个心。

五、非对称加密与签名 #

两把钥匙：公钥公开，私钥自己留着。公钥加密的只有私钥能解，私钥签名的只有公钥能验。

5.1 对称与非对称的分工 #

维度 对称加密 非对称加密
密钥 一把，双方共享 一对，公钥公开 / 私钥自持
速度 快 慢，差几个数量级
适合的数据量 大，几百 MB 无压力 小，几十到几百字节
密钥分发 难，怎么安全送过去是问题 易，公钥可以随便发
典型用途 数据本体 传密钥、签名、身份认证

分工就一句话：非对称传密钥，对称传数据。

这就是混合加密，也是 TLS、PGP、各类加密文件格式的统一做法。流程固定：

text
1. 发送方随机生成一个对称密钥 K（会话密钥）
2. 用 K 对称加密数据本体，得到密文 C
3. 用接收方的公钥加密 K，得到 K'
4. 把 K' 和 C 一起发出去
5. 接收方用私钥解出 K，再用 K 解 C

对称加密负责吞吐，非对称加密负责把 K 安全送到对端。两边各干擅长的事。

直接用 RSA 加密数据本体是常见误用。RSA 能加密的数据长度受密钥长度限制，2048 位密钥配 PKCS#1 v1.5 填充，实际只能加密两百多字节。拿它加密一张图片，第一步就会失败。

5.2 签名和加密是反的 #

加密解决「别人不能读」，签名解决「别人不能改、不能冒充」。

操作 用哪把钥匙 谁能验证
加密 接收方的公钥 只有接收方的私钥能解
签名 发送方的私钥 任何人都能用发送方的公钥验
验签 发送方的公钥 验签通过说明私钥持有者签过

签名实际签的是数据的哈希，不是数据本身。所以签名和散列是配套的，流程是「先算摘要，再对摘要签名」。

在 Qt 项目里，签名最实用的场景是更新包校验：私钥留在发布机器上，公钥硬编码进客户端。客户端下载完新版本，验签通过才允许替换文件。

5.3 RSA 与 ECC #

项 RSA ECC
数学基础 大整数分解 椭圆曲线离散对数
常用参数 2048 / 3072 / 4096 位 P-256、P-384、Curve25519
密钥体积 大 小得多
运算速度 慢，密钥越长越慢 快
移动端友好度 一般 好
兼容性 到处都支持 老系统要确认

ECC 用短得多的密钥达到与 RSA 同等的安全级别，这是它被移动端偏爱的原因。兼容性上 RSA 更稳，对接老系统、老硬件时先确认对方支持哪些曲线。

不管选哪个，密钥都不该写死在客户端里。私钥进客户端，等于把签名权发给所有人。

六、引入第三方加密库 #

Qt 官方态度很明确：不做通用加密，交给第三方库。选型看三件事——许可证、二进制体积、你要不要 TLS。

库 许可证 体积 覆盖范围 适合
OpenSSL Apache 2.0 大 全，含 TLS 需要证书、TLS、各种算法
Botan BSD 2-Clause 中 全，C++ 原生接口 想要 C++ 风格的 API
libsodium ISC 小 现代算法，API 防误用 只要加解密与签名
mbedTLS Apache 2.0 / GPL 很小 精简，嵌入式友好 资源受限设备

OpenSSL 最通用，坑也最多；libsodium 的 API 设计成「用不错」，代价是算法选择空间小；mbedTLS 适合塞进 MCU 或对体积敏感的场景。

6.1 CMake 接法 #

OpenSSL 用 find_package 找，找不到就让配置阶段直接失败，别拖到链接期：

cmake
find_package(OpenSSL REQUIRED)
if (NOT OpenSSL_FOUND)
    message(FATAL_ERROR "OpenSSL not found")
endif()

target_link_libraries(myapp PRIVATE
    Qt6::Core
    OpenSSL::Crypto     # 只用加解密与散列，不要 SSL
)

OpenSSL::Crypto 与 OpenSSL::SSL 分开链接。只做资源加密与散列时链接 Crypto 就够，能省掉一截依赖。

qmake 工程：

LIBS += -lcrypto -lssl
INCLUDEPATH += $$OPENSSL_ROOT/include

6.2 Windows 上的坑 #

libcrypto-3-x64.dll 和 libssl-3-x64.dll 必须跟 exe 放在一起，或者装进系统目录。忘了这两个 DLL，程序启动就报「找不到入口点」或者干脆闪退，而且报错信息跟加密毫无关系，排查方向容易跑偏。

windeployqt 默认只搬 Qt 的库，不管 OpenSSL。打包脚本里要单独把它们拷过去：

bash
copy "%OPENSSL_ROOT%\bin\libcrypto-3-x64.dll" dist\
copy "%OPENSSL_ROOT%\bin\libssl-3-x64.dll"  dist\

想彻底摆脱这两个 DLL，可以静态链接 OpenSSL，代价是编译麻烦、exe 变大、许可证合规要看清。许可证这块在商业项目上别拍脑袋，让法务过一遍。

七、密钥怎么存 #

这一章没有正确答案，只有成本高低。先接受一个前提：客户端里的密钥，最终都能被找出来。

手段 逆向成本 挡得住谁 明显缺陷
明文硬编码在源码里 极低 几乎没人 strings 一扫就出
拆成几段拼接 低 随手翻源码的人 拼接点一看就懂
XOR 混淆后存字节数组 低 不会写脚本的人 写个循环就还原
编译期计算 / 宏展开 中 静态分析的人 运行时内存里是明文
运行时由机器码派生 中 换机器拷文件的人 换台机器就解不开
联网向服务端要 高 断网分析的人 不能离线用，服务端要做鉴权

机器码派生值得展开两句。把 CPU 序列号、主板 ID、硬盘序列号之类拼起来算个哈希，再拿来当密钥的一部分。这样资源文件拷到别的机器上解不开，等于把「密钥」和「设备」绑在一起。代价是用户换硬件就得重新授权，售后成本会上升。

联网获取是最强的一档，但引入两个问题：离线场景直接不能用；服务端必须做身份鉴权，否则谁都能来要密钥。做成这样，密钥管理的重心就从客户端转到了服务端。

7.1 密钥不该做的事 #

  • 不要在源码里出现 KEY = "..." 这种字面量。编译进二进制的字符串，strings 一条命令就捞出来。
  • 不要把密钥写进 .qrc。资源文件是明文的，等于换个地方硬编码。
  • 不要把密钥打进日志、崩溃报告、qDebug() 输出。
  • 不要用固定 IV，也不要用 rand() 生成 IV。rand() 不是密码学随机源。
  • 不要复用同一把密钥加密所有东西。按用途分开，资源一把、配置一把。

7.2 用一把还是用多把 #

资源加密、配置加密、通信加密，用途不同就该分开。一把钥匙开所有锁，泄露一次全线失守。

分开还有一个工程上的好处：换密钥时只影响一类数据，不用全量重新加密。

八、.qrc 资源的困境 #

前面七章讲的是「怎么加密」，这一章讲的是「为什么加密在这儿特别难」。答案藏在 rcc 的工作方式里。

8.1 qrc 到底解决了什么 #

.qrc 是 Qt 的资源集合，把图片、QML、配置文件打包成二进制数据。它首先是个工程工具，不是安全工具。

工程痛点 qrc 的解法
路径地狱 统一用 :/ 协议访问，抹掉 Windows \ 与 Linux / 的差异
部署复杂 打包成单一二进制，避免散乱文件丢失，也绕开 Windows 句柄数限制
加载性能 底层用内存映射，加载速度和内存占用优于文件流读取

这三条都是真问题，所以 qrc 值得用。问题出在很多人顺手把「打包成二进制」理解成「加密了」。

8.2 rcc 的两种输出模式 #

rcc 是资源编译器，两种输出模式。

内嵌模式，编译成 C++ 源码数组，直接进可执行文件。核心 UI、图标这类必需资源走这条路：

bash
rcc -name assets assets.qrc -o qrc_assets.cpp

外挂模式，编译成独立的 .rcc 二进制，运行时动态加载。主题包、DLC 内容、多语言包适合这条路：

bash
rcc -binary assets.qrc -o assets.rcc

运行时注册：

cpp
#include <QResource>

int main(int argc, char *argv[]) {
    QApplication app(argc, argv);

    if (!QResource::registerResource("skins/dark_theme.rcc")) {
        qWarning() << "Failed to load theme resource";
    }
    return app.exec();
}

registerResource 返回 false 就是没加载上，此时所有 :/ 路径都会失效，界面会缺图少字。这个返回值一定要判断，别默默继续跑。

注册之后，内部资源和外部资源用同一套协议访问：

cpp
// C++
QPixmap pixmap(":/images/logo.png");

qml
// QML
Image { source: "qrc:/images/logo.png" }

换肤功能就是靠 registerResource / unregisterResource 这对组合做的。加载新的 dark_theme.rcc，卸掉旧的，:/ 路径指向的内容就变了。

8.3 关键事实：资源是明文躺在二进制里的 #

这里要说清楚一件事，很多人到这一步才反应过来。

rcc 做的是序列化，不是加密。它把文件内容按自己的格式排布，再拼进二进制。数据本身一个字节都没变。

所以，把 exe 或者 .rcc 丢给 strings：

bash
strings app.exe | findstr /C:"qml" /C:"png"

或者直接：

bash
strings assets.rcc > dump.txt

dump.txt 里就是你的 QML 源码、文本配置、界面上的每一句中文字。图片是二进制，strings 抠不出来原文，但用十六进制编辑器能看见 PNG 文件头，按偏移量切出来就是原图。

手段 目的 结果
strings 捞可打印字符串 QML 源码、配置文本直接可读
十六进制编辑器（如 010 Editor） 看结构 QML 以 ASCII 明文呈现
rcc-extractor 之类开源工具 一键扫描 完整还原目录树与文件名
直接按 PNG 头切分 提取图片 原图无损还原

第三条最要命。这类工具能扫 exe 也能扫 .rcc，扫完连目录结构都给你摆出来，连文件名都不丢。也就是说，「资源打包进二进制」这件事，对提取者只增加了一条命令的成本。

8.4 为什么 Qt 原生不做资源加密 #

不是 Qt 偷懒，是接口决定了这件事。

QResource 为了保证加载速度，要求传入的数据必须符合标准 RCC 结构布局。它内部直接按偏移量定位条目，跳过校验和解析。你把 AES 加密后的文件喂给它，它按 RCC 格式去解读密文，读出来的是垃圾。

所以要实现资源保护，绕不过一件事：接管资源的加载环节。 在数据交给 QResource 之前，先把它还原成明文。这就进入了下一章。

九、资源加密的几种做法 #

四种做法，成本从低到高。

方案 原理 提取门槛 性能 适用
标准 rcc 二进制序列化 一条命令 无损耗 普通图标、UI 素材
外挂 .rcc + 自校验 独立包，加载前比对摘要 略高，要过校验 轻微 皮肤包、语言包
Qt Quick Compiler QML 转 C++ 字节码 中等，逻辑混淆但字符串可读 正向提升 性能敏感场景
自定义加密管线 自定算法加密存储，运行时解密 高，要逆向解密算法与密钥 轻微 核心 IP、商业授权保护

第一列到第四列，防的不是「破解」，是「顺手抄」。这个定位要摆正。

9.1 管线架构 #

思路三步：加密存储 → 内存解密 → 内存加载。 磁盘上的资源是密文，运行时在内存里还原成明文，再交给 Qt 引擎。

text
构建阶段                     运行阶段
─────────                    ─────────
原始资源                      引擎请求 e-qrc://main.qml
   │                              │
   ▼                              ▼
AES 加密                     自定义加载器
   │                              │
   ▼                              ▼
assets.dat  ──── 部署 ────►  读密文 → 解密 → 内存 ByteData
                                  │
                                  ▼
                             返回给引擎（不落临时文件）

关键在最后一步：解密后的数据只在内存里存在，不写临时文件。写临时文件等于把明文又落回磁盘，白加密一场。

9.2 构建时：生成加密资源 #

Python 脚本负责打包加密，随便用什么语言，构建脚本的职责就是把明文资源变成密文：

python
# build_encrypt.py
from Crypto.Cipher import AES
from Crypto.Util.Padding import pad

# 生产环境应从环境变量或密钥管理系统获取
KEY = b'YourSuperSecretKey123456789012'  # 32 bytes
IV = b'1234567890123456'

def encrypt_file(filepath):
    with open(filepath, 'rb') as f:
        data = f.read()
    cipher = AES.new(KEY, AES.MODE_CBC, IV)
    return cipher.encrypt(pad(data, AES.block_size))

这段代码能跑，但两个地方要改：KEY 和 IV 不能硬编码，注释里那句提示是认真的；IV 固定会让相同前缀的文件产生相同前缀的密文，每个文件都要重新随机生成并写进文件头。

9.3 运行时：拦截 #

QML 应用的资源请求走 QNetworkAccessManager，拦截它就能接管加载。实现 QQmlNetworkAccessManagerFactory，定义一个自定义协议，比如 e-qrc://。

先做自定义 NetworkReply，把内存块伪装成网络响应：

cpp
// EncryptedNetworkReply.h
class EncryptedNetworkReply : public QNetworkReply {
    Q_OBJECT
public:
    EncryptedNetworkReply(const QUrl &url, const QByteArray &decryptedData,
                          QObject *parent = nullptr)
        : QNetworkReply(parent), m_data(decryptedData)
    {
        setOperation(QNetworkAccessManager::GetOperation);
        setRequest(QNetworkRequest(url));
        setUrl(url);
        open(QIODevice::ReadOnly);
        setHeader(QNetworkRequest::ContentLengthHeader, m_data.size()); // ← 关键

        QTimer::singleShot(0, this, &EncryptedNetworkReply::finished);
        QTimer::singleShot(0, this, &EncryptedNetworkReply::readyRead);
    }

    qint64 readData(char *data, qint64 maxSize) override {
        qint64 amount = qMin(maxSize, (qint64)m_data.size() - m_pos);
        memcpy(data, m_data.constData() + m_pos, amount);
        m_pos += amount;
        return amount;
    }

    qint64 bytesAvailable() const override { return m_data.size() - m_pos; }
    void abort() override {}
    bool isSequential() const override { return true; }

private:
    QByteArray m_data;
    qint64 m_pos = 0;
};

两个细节决定成败。ContentLengthHeader 必须设，QML 引擎靠它判断资源长度，缺了这个头，某些资源的加载会卡在等待。finished 和 readyRead 用 singleShot(0) 异步发，不能在构造函数里同步发——那时候对象还没交到调用方手里，信号会丢。

再做 Manager 工厂，把特定 scheme 的请求截走：

cpp
// SecurityNetworkManager.cpp
QNetworkReply* SecurityNetworkManager::createRequest(
    Operation op, const QNetworkRequest &req, QIODevice *outgoingData)
{
    if (req.url().scheme() == "e-qrc") {
        QString path = req.url().path();
        QByteArray decrypted = AssetManager::instance()->loadAndDecrypt(path);
        return new EncryptedNetworkReply(req.url(), decrypted, this);
    }
    return QNetworkAccessManager::createRequest(op, req, outgoingData);
}

非 e-qrc 的请求原样交回父类，别自己实现网络栈。

引擎接入：

cpp
// main.cpp
QQmlApplicationEngine engine;
engine.setNetworkAccessManagerFactory(new SecurityNetworkFactory());
engine.load(QUrl("e-qrc://main.qml"));

注意 setNetworkAccessManagerFactory 必须在 load() 之前调用。放后面，第一批资源请求已经用默认工厂处理完了，拦不到。

9.4 替代方案：Loader 模式 #

不想重写网络层，可以直接用 QQmlComponent::setData 加载解密后的字节。适合单入口的简单应用：

cpp
QByteArray scriptData = DecryptUtils::readFile(":/encrypted/main.qml.enc");

QQmlComponent component(&engine);
component.setData(scriptData, QUrl("qrc:/virtual/main.qml"));  // ← BaseUrl 确保相对导入正确
component.create();

第二个参数的 QUrl 是 BaseUrl，不是随便填的。QML 里的相对导入（import "components"）和相对资源路径都基于它解析。填错，界面能起来但组件全丢。

这个方案有个明显限制：所有 QML 文件都得手动解密、手动 setData，入口一多就变成体力活。拦截方案能自动处理任意路径，扩展性更好。

9.5 还有几种变体 #

按思路归一下类：

变体 做法 代价
外挂包加密 .rcc 加密成 .dat，加载前解密到内存再 registerResource 需要一块临时缓冲区
单文件资源包 自定格式，头部存索引，正文分块加密 要自己写索引与解析
逐文件加密 资源保留在文件系统，加密后逐个解密 部署从单文件退化成多文件
流式解密 基于 mbedTLS 之类的库边读边解 实现复杂，适合超大资源

registerResource 只能吃符合 RCC 格式的数据。所以外挂包加密的路子是：解密到内存，用 QResource::registerResource 的另一个重载——直接传 QByteArray，绕开文件系统。

十、加密与打包的配合 #

加密不是加个函数就完事，它得塞进构建流水线，否则每次发布都要手工跑一遍脚本，早晚出错。

10.1 构建顺序 #

text
1. 收集资源      →  assets/ 目录
2. rcc 打包      →  assets.rcc 或 qrc_assets.cpp
3. 加密          →  assets.dat
4. 编译链接      →  exe
5. windeployqt   →  dist/
6. 补第三方 DLL  →  OpenSSL 等
7. 签名 / 打包   →  安装包

第 2 步和第 3 步的顺序不能反。先加密再 rcc，rcc 会把密文当普通文件打包，编译进 exe 的还是密文，看起来也对——但运行时你要解密的是「RCC 结构里的一个条目」，取出来还得先按 RCC 解析，多一层麻烦。先 rcc 再加密，加密对象是一整个 .rcc 文件，边界清晰。

10.2 CMake 集成 #

内嵌模式走 qt_add_resources，加密资源走自定义命令：

cmake
# 标准资源，交给 Qt 处理
qt_add_resources(myapp "assets"
    PREFIX "/"
    FILES images/logo.png
)

# 加密资源：构建时生成，不参与编译
set(ENC_OUT "${CMAKE_BINARY_DIR}/assets.dat")
add_custom_command(
    OUTPUT  ${ENC_OUT}
    COMMAND ${Python3_EXECUTABLE} ${CMAKE_SOURCE_DIR}/tools/build_encrypt.py
            --in  ${CMAKE_SOURCE_DIR}/assets
            --out ${ENC_OUT}
    DEPENDS ${CMAKE_SOURCE_DIR}/tools/build_encrypt.py
    COMMENT "Encrypting resources"
)
add_custom_target(encrypted_assets ALL DEPENDS ${ENC_OUT})

DEPENDS 里挂上脚本本身。改了脚本不重跑，构建系统不知道，你会花半天排查「为什么改了加密逻辑没生效」。

10.3 内嵌与外挂怎么选 #

场景 选内嵌 选外挂
必需资源，缺了程序起不来 ✓
主题包、语言包 ✓
频繁更新、不重发主程序 ✓
想减小 exe 体积 ✓
加密后希望整体一起被保护 ✓
需要独立分发、单独授权 ✓

加密方案对两种模式都适用，区别只在解密时机：内嵌的进内存后在启动阶段解，外挂的在 registerResource 之前解。

10.4 密钥轮换 #

密钥硬编码进 exe，换密钥就得重发整个程序。这件事在方案设计阶段就要想清楚。

留一条后路：密文文件头里放一个密钥版本号，客户端内置一张「版本号 → 密钥」的小表。轮换时新版本资源用新密钥加密，老版本资源还能读。表会越变越长，但总比强制全量升级友好。

10.5 别忘了签名 #

加密保护的是「内容不被读」，签名保护的是「内容不被换」。

只有加密没有签名，攻击者不需要解密——他直接拿自己加密的一份资源替换掉你的 .dat，程序照样解、照样跑，只是内容变成了他的。资源包里塞一句伪造的提示、一张改过的二维码，都能生效。

所以发布包的最后一步是签名，客户端启动或加载资源前验签。私钥不在客户端，这一步才立得住。

十一、哪些做法其实没用 #

这一章劝退。下面这些做法在项目里出现过，花了时间，收益接近零。

做法 为什么没用
改扩展名（.qrc → .dat → .bin） 后缀不参与任何判断，file 命令挨个试就认出来
Base64 编码当加密 Base64 是编码不是加密，任何人都能一行代码还原
XOR 一个固定字节 单字节 XOR 的密文频率分布能肉眼统计，写脚本还原只要几行
把密钥拆成三段拼接 拼接点就写在源码里，strings 捞不全也能反编译看到
只加密 QML，图片原样打包 提取者照样拿全套素材，只剩代码
自创加密算法 自己设计的算法没有公开分析，你无法证明它够用
变量名混淆 + strip 符号 减少可读性，不保护数据，资源还是明文
加壳工具当加密用 提高逆向门槛，资源仍要解密到内存，dump 一样拿到
反调试检测 抬高调试成本，改个跳转就绕过

自创算法这条要单独说。密码学算法的安全性靠长期公开分析积累，不靠设计巧妙。自己憋一套「移位 + 异或 + 换表」的流程，看着复杂，实际强度取决于最短的那一环，而且没有同行帮你找漏洞。用库里的标准算法，把精力花在密钥管理上。

11.1 原理上的上限 #

讲完这么多方案，回到开头那句话。

只要密钥在客户端，就一定能被找到。 原因很直接：程序要在没有你参与的情况下自动解密，就必须在本地拿到密钥，也必须有解密逻辑。运行到解密那一刻，密钥在内存里一定是明文形态；解密后的资源在内存里也一定是明文形态。

能拦住的是不会写代码的人。拦不住的是愿意花时间的人：

text
1. 反调试 → 绕过反调试
2. 找不到密钥 → 在解密函数下断点，看寄存器
3. 加壳 → 脱壳，或者直接 dump 内存
4. 数据在内存是密文 → 那程序自己就读不了，这不是加密方案

第 2 步是通用解法，跟算法无关，跟实现无关。断点打对位置，密钥和明文一起出现。

所以资源加密的目标要摆在正确的位置：抬高提取成本，让顺手抄的人放弃，让批量扒素材的脚本失效。 这已经能挡住绝大多数情况。把它当「防破解」卖，是给自己挖坑——真被扒了，你没法交代。

反过来，如果你的核心价值是一段算法或一份模型，别指望客户端加密。放到服务端，客户端只拿结果。这是唯一在原理上站得住的方案。

十二、易错点速查 #

现象 原因 修法
解密后数据乱码 密钥长度不对，被库截断或补齐 AES-128 要 16 字节，AES-256 要 32 字节，先断言长度
换台机器解不开 密钥由机器码派生 属于设计预期，换硬件要重新授权
相同文件密文相同 IV 固定或没写进文件头 每次加密重新生成 IV，随密文一起存
程序启动报找不到入口点 缺 libcrypto-3-x64.dll 打包脚本补拷 OpenSSL DLL
QML 界面起不来、组件全丢 setData 的 BaseUrl 填错 BaseUrl 要与相对导入的基准路径一致
自定义协议资源加载卡住 没设 ContentLengthHeader 在 NetworkReply 构造函数里设上
拦截器完全不生效 工厂设置在 load() 之后 挪到 load() 之前
信号丢了、回调不触发 构造函数里同步发 finished 改用 QTimer::singleShot(0, ...) 异步发
registerResource 后资源还是 404 返回值没判断，加载其实失败了 判断返回值，失败就打日志
加密资源后体积暴涨 存了 Base64 文本 存原始二进制，别转文本
校验总和线上不一致 文本模式读文件，换行被转换 用 QIODevice::ReadOnly，别加 Text
口令散列被反查出来 无盐 MD5 加盐，用 deriveKeyPbkdf2 拉高迭代次数
算出的散列跟工具对不上 直接拿 result() 当字符串用 必须 toHex() 再比较
单元测试里解密通过、真机失败 真机资源没更新，还是老密文 校验资源版本号，构建流水线重跑加密

最后一条最容易踩。加密脚本挂在构建流程外，本地跑测试用的是新生成的 .dat，真机装的是安装包里那份旧的。两边代码一样，数据不一样，排查方向会一路跑到算法上去。

清单之外还有一条判断标准：如果一个方案需要你在发布前手工执行某个步骤，它早晚会被漏掉。把加密、签名、拷贝 DLL 全部塞进构建脚本，让流程自己保证正确，比写一份发布检查表可靠。
