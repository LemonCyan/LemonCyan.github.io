开篇边界说明

这篇只讲一件事：程序发到用户机器上之后，反馈「风扇一直转」「笔记本发烫」「点一下卡两秒」时，我们怎么从 CPU 占用这条线索把问题挖出来、改掉、再验证。

不讲打包流程和依赖裁剪，那是同目录的打包与分发那篇；不讲日志落盘和开机自启，那是日志与开机自启那篇；不讲 PDF 出图和加密，各有专篇。内存泄漏看的是内存曲线，不是 CPU 曲线，这里也不展开。

跨篇指路：怀疑是发布包缺了运行库导致反复重试，先回打包那篇对一遍依赖。

先把立场摆在开头：不测量就优化，等于拿用户的机器当试验台。 下面十二节的顺序不会变——先看清哪个线程在烧 CPU、烧在哪个函数，再决定动哪一行代码。

一、CPU 高的六种典型原因 #

接到「CPU 高」的反馈，别急着翻代码。先把它归到一类里去。归类错了，后面所有努力都是白费。

我们把手上的案例和公开的排查经验收了一遍，落到六类。六类之外还有第七类，叫「不是我们的锅」——显卡驱动、杀毒软件实时扫描、系统索引。分不清这一点，会花三天去优化一段根本没问题的代码。

编号 原因 典型表现 代码层面的样子 对应章节
1 忙等待与空转 空载也吃满一个核，界面还能动 while(true) 循环里没有阻塞点 三
2 定时器用得太密 摆着不动也有稳定的 CPU 底噪 QTimer::start(0)、10ms 级轮询 四
3 重绘风暴 拖动窗口、滚动时 CPU 尖峰 paintEvent 里调 update() 或 repaint() 五
4 主线程被阻塞 界面卡死、点不动，CPU 反而不高 主线程里跑重计算、同步等待 六
5 信号槽风暴 数据量一上来就飙 每来一条数据就 emit 一次跨线程信号 七
6 线程数与并行度失配 少核机器卡，多核机器也卡 线程数远超核数、浮点运算不做拆分 八

这张表看着像一张清单，实际是一条定位路径。第 1、2 类的特征是空载就高；第 3、5 类是有操作、有数据才高；第 4 类的特征更怪——CPU 不高，但用户体感最差。

素材里那个案例很典型，值得完整讲一遍。程序开了多个接收子线程，同时从网口收数据并解析，另有一个融合子线程，把各接收线程解析出来的结果做融合。接收线程和融合线程之间，靠 Qt 的信号槽机制传数据。

排查下来发现：各子线程跑起来之后就进入了死循环状态。即使此刻根本没有待接收、待处理的数据，线程也在空转。CPU 就是这么被吃掉的。

这段描述里藏了两个问题，不是两个问题的叠加，是互相放大的。第一个是空转：循环里没有阻塞点，没活干也不肯让出 CPU。第二个是交互方式：线程之间用信号槽硬连，数据一到就唤醒对方，唤醒频率跟着数据帧率走，没人做节流。

素材还列了另外几条：在 paintEvent 里调 update 形成无限循环、频繁刷新数据、复杂的浮点运算、paintEvent 里操作太多。这五条一条都没浪费——update 循环和 paintEvent 操作太多归到第三节的重绘风暴，频繁刷新数据归到同一个地方的刷新节流，复杂浮点运算归到第八节的并行度，死循环归到第三节的忙等待。线索散着看是碎片，归了类就是路线图。

有一点要先说清：CPU 高本身不是 bug，CPU 高而没在干有用的事才是。 视频解码吃满八个核是正常的，一个串口接收程序吃满一个核是不正常的。判断标准不是绝对的占用数字，是「这段时间里它在不在做用户要它做的事」。

二、先测量再动手 #

第一章给了六个筐，这一章讲怎么把现象准确地扔进对应的筐里。工具不复杂，难的是忍住不猜。

拿到反馈先问三个问题，按顺序问：

第一，哪个线程在吃 CPU。注意是线程，不是进程。一个进程 CPU 30%，一种情形是主线程 29%、其余线程分摊 1%，另一种是六个线程各 5%。这两种情况的修法完全相反。

第二，吃在哪个函数里。同一个线程，卡在 paintEvent 和卡在 while 循环里，处理方式差着一个数量级。

第三，什么条件下才高。空载时高、拖动窗口时高、来数据时高、跑够两小时才高——四种条件对应四个不同的筐。

三个问题里，第一个和第二个必须靠工具回答，靠读代码猜的准确率很低。人性有个偏差：我们总在自己的代码里找，而问题常常在第三方库里，或者在事件循环的某个角落。Windows 上最省事的起点是任务管理器。切到「详细信息」，加一列「线程数」，先看进程级的 CPU 是不是真的高。任务管理器显示的百分比是相对整机的，八核机器上进程占 12.5% 就等于吃满一个核，别看到 12% 就以为没事。

要看单线程，换 Process Explorer。双击进程，进「线程」页，按 CPU 列排序，最上面那个线程的 TID 就是嫌疑犯。拿到 TID 之后，用调试器 attach 上去看它的调用栈，或者干脆在代码里对 QThread::currentThreadId() 打点。

Linux 上起点是 top，按 H 切到线程视图。top 里的 %CPU 是按核累加的，单个线程最多 100%，整个进程可以到 nproc × 100%。看到 380% 别慌，那是四个线程在跑。

要继续往下钻，perf 是最直接的手段：

bash
perf top -p $(pgrep -f myapp)          # 采样整个进程，看热点函数

perf record -F 99 -g -p $(pgrep -f myapp) -- sleep 10   # 录 10 秒，出火焰图数据
perf report --stdio | head -60

-F 99 是每秒采样 99 次。不要用 1000，采样频率太高会自己引入可观开销，把被测对象干扰了。99 这个数字是为了避开定时器整数倍带来的采样偏差，属于采样分析的常规做法。

没有 perf 权限的机器，gdb 也能凑合：

bash
for i in $(seq 1 5); do        # 连抓 5 次，看谁老停在同一处
    gdb -p $(pgrep -f myapp) -batch -ex "thread apply all bt" 2>/dev/null | grep -A3 "Thread"
    sleep 1
done

抓五次，同一个线程五次都停在同一个函数里，那就是它。这种手采样的精度不如 perf，但不需要任何额外权限。

跨平台的活儿，用 Qt Creator 自带的分析器。它集成了性能分析入口，能在 IDE 里直接看函数级耗时，不用来回切终端。QML 界面另有一套 QML Profiler，能看每帧的渲染耗时，那是 QML 专属的路子，这里不展开。

工具讲完，讲最容易被忽略的一招：在代码里打点。工具告诉你哪个函数热，打点告诉你这个函数每次调用花多久、被调了多少次。两个数据合起来才有决策价值。

QElapsedTimer 是 Qt 里做这个的首选，单调时钟，不受系统时间调整影响：

cpp
#include <QElapsedTimer>
#include <QDebug>

void Worker::handleFrame(const Frame &f)
{
    QElapsedTimer t;
    t.start();

    parse(f);            // 可疑代码

    const qint64 us = t.nsecsElapsed() / 1000;
    if (us > 5000) {     // 超过 5ms 才打，别刷屏
        qWarning() << "parse slow:" << us << "us, bytes:" << f.size();
    }
}

这个打点有三处讲究。一是只在超阈值时打印，否则日志本身就是新的性能问题。二是把输入规模一起打出来，us 和 bytes 放在一起才能算出单位成本。三是用 nsecsElapsed() 而不是 elapsed()，后者是毫秒精度，短函数全被抹成 0。

阈值怎么定？拿需求反推。要求 60 帧，一帧 16ms，这个函数占 1ms 以上就该看。要求 20ms 一个数据包，处理超过 2ms 就该看。没有需求时，先打一轮不设阈值的统计，看分布再定。

打点打多了会失真。每次 qWarning 都涉及格式化、加锁、写设备，几十微秒起步。密集路径上把打点留着，测出来的数字里有一半是打点自己的开销。正确做法是先粗测定位到函数，再删掉大部分打点，只留目标那几处精测。测的时候一定要测空载基线——程序启动、连上设备、不给任何数据、不碰鼠标键盘，放一分钟，看平均 CPU。这一步把六类原因劈成两半：

观察到的现象 指向哪一类
空载就高，曲线平直 忙等待与空转、定时器过密
空载低，一操作就尖峰 重绘风暴
空载低，一有数据就高 信号槽风暴、解析算力不足
单核逼近 100%，其余核空闲 单线程瓶颈，需要拆并行
所有核都被拉起来 线程数过多或并行粒度太细
曲线一路爬升不回落 累积型问题：容器只增不减、信号重复连接
CPU 不高但界面卡 主线程被阻塞

这张表不是判据，是筛子。它把六个候选砍到一两个，剩下的交给后面几章的代码级检查。

还有一个反直觉的点：反馈说「卡」的时候，要先确认到底是 CPU 问题还是渲染问题。 界面卡顿的来源有两处：主线程阻塞，或者垂直同步没开、显卡驱动在软件渲染。这两种情况 CPU 曲线完全不同，先看一眼曲线再动手。

最后一句，关于基准。同一个程序在两台机器上的绝对 CPU 占用没有可比性，核数、频率、超线程、后台负载全不一样。能做对比的只有同一台机器、同一份数据、改动前后的差异。所有「优化了 X%」的说法，都要带上这个前提才有意义。

三、忙等待与轮询 #

六类里排第一的是它。不是因为它出现次数最多，而是因为它写出来最像「正常代码」——一段循环，检查条件，看着天经地义。

先把本质说破：程序在等某件事，但用的是「不停问」而不是「等通知」。 CPU 不是被「等」烧掉的，是被「问」烧掉的。

问这个动作本身要花时间：读内存、比较、跳转。一秒钟能问几百万次。没有活干的时候，这几百万次就是纯粹的浪费，而且它占着调度器的时间片，别的线程拿不到。

忙等待有四种常见长相：

写法 代码样子 为什么烧 CPU 该怎么改
空循环 while(cond) {} 循环体没有阻塞点，占满一个核 换条件变量
短睡轮询 while(...) { ...; msleep(0); } 只让出时间片，醒来立刻再问 换阻塞队列
定时器轮询 QTimer::start(0) 每轮事件循环都跑一次 换事件驱动
标志位轮询 while(!m_stop) { ... } 同空循环 QWaitCondition

素材里那个程序踩的是第一种和第三种。多个接收子线程从网口收数据并解析，一个融合子线程做融合，线程之间靠信号槽传数据。分析下来，各子线程运行之后都处于死循环状态——即使此刻没有待接收、待处理的数据，线程也在空转。 CPU 就是这么被吃掉的。注意这句话里的「即使」：程序的功能是对的，数据一条不丢，界面也正常，用户唯一的感受是风扇响。这种 bug 最难被开发者自己发现，因为本地开发机上跑十秒看不出来，装机跑一天才会被投诉。

QThread 提供了三个挂起函数：sleep()、msleep()、usleep()，单位分别是秒、毫秒、微秒。指定时间一过，线程自动唤醒。素材给的第一个方案是用 sleep(0)，等价于 msleep(0)：

cpp
void ReceiverThread::run()
{
    while (true)
    {
        Frame f;
        if (tryReadFrame(f)) {
            parseAndEmit(f);
        }
        // 循环末尾让出时间片
        msleep(0);
    }
}

msleep(0) 在理论上不会让线程挂起任何时间。它做的是另一件事：主动放弃当前剩余的时间片，让系统把这段时间分给别的线程。这一让，就把「一个核被独占」变成了「多个线程轮流用同一个核」。子线程数量少的时候，这一招够用。素材里的程序子线程多，实测 msleep(0) 没有明显效果——因为让出之后立刻又被调度回来，问的频率还是很高，几个线程一起问，CPU 照样顶上去。

于是改成按数据量给一个真实的挂起时间。最终每个子线程在循环末尾挂起 15ms：

cpp
while(true)
{
	...
	msleep(15);
}

这个 15 不是拍脑袋来的，可以算。挂起时间 T 决定了线程多久查一次数据，也就是轮询频率 1/T。15ms 对应每秒约 66 次。

判断 T 取值合不合适，看两个数：单次数据处理耗时 p，数据到达的平均间隔 d。

  • T 远大于 d：会积压，队列越堆越长，延迟持续增长。
  • T 接近 p：线程几乎一直在干活，省不下来 CPU。
  • T 落在 p 和 d 之间：既能睡下去，又跟得上。

素材里的做法就是这个思路——「根据子线程数量以及子线程循环中需要实时处理的数据量的多少来给子线程添加合适的休眠时间」。线程多就睡长一点，数据密就睡短一点。

要把这笔账算明白，还得承认 sleep 的代价：它把「空转烧 CPU」换成了「有延迟但不烧 CPU」。 这是止损，不是修复。睡 15ms 意味着最坏情况下数据要等 15ms 才被处理，如果你的业务要求 5ms 内响应，这条路走不通。

真正的修法是换掉「问」这个动作。等通知的三种形态，按推荐程度排：

第一种，条件变量。这是最正统的做法。没有数据时线程真的睡在内核里，CPU 占用是 0；数据来了被别人叫醒，唤醒延迟在微秒级。

cpp
class FrameQueue
{
public:
    void push(const Frame &f)
    {
        QMutexLocker lock(&m_mutex);
        m_queue.enqueue(f);
        m_cond.wakeOne();          // 叫醒一个等的人
    }

    bool pop(Frame &f, int timeoutMs = 200)
    {
        QMutexLocker lock(&m_mutex);
        while (m_queue.isEmpty()) {
            if (!m_cond.wait(&m_mutex, timeoutMs))
                return false;      // 超时，让外层有机会检查退出标志
        }
        f = m_queue.dequeue();
        return true;
    }

private:
    QMutex        m_mutex;
    QWaitCondition m_cond;
    QQueue<Frame> m_queue;
};

这段代码的关键在 while 那一行。wait 返回不代表条件成立——它会被虚假唤醒，也会被别的 wakeOne 顺带叫醒。所以必须重新检查条件，用 while 而不是 if。这是条件变量的老规矩，写成 if 会在压力测试里偶尔丢一帧。超时参数要留着：纯阻塞的 wait() 在没有数据时会永远睡着，程序退出时叫不醒它，关窗口就卡住。给个 200ms 上限，醒来发现队列还是空的就返回 false，外层顺势检查退出标志。

第二种，QSemaphore。适合「计数型」的等待，比如「缓冲区里有几个空槽」。用法和条件变量等价，语义更窄，写错的机会少一些。第三种，干脆别写循环。网口数据的接收天生是事件驱动的：Qt 的 socket 类在数据到达时发 readyRead，你接上这个信号，处理函数被调用一次处理一次，没有数据时事件循环在睡觉。用阻塞式 recv 收包也不需要 sleep——阻塞式调用本身就是「等通知」，它挂起在内核里，不占 CPU。

真正烧 CPU 的只有一种：非阻塞 socket 加 while 循环加 select 超时设成 0。这种写法把「等」退化成了「问」，性能特征和空循环一样。

什么时候 msleep 够用，什么时候必须换条件变量，给个判据：

情形 建议
子线程一两个，数据稀疏，延迟要求宽松 msleep 可以接受
子线程多，数据密集 条件变量或阻塞队列
数据源本身事件驱动（socket、串口 readyRead） 别写循环，接信号
需要周期性统计、上报、看门狗 QTimer，别用循环
循环里要检查退出标志 QWaitCondition 带超时，别用 sleep 拼

最后一条判据最实用：看到 while 加条件检查，就该问一句「能不能换成阻塞等待」。 十次里有九次能。

四、定时器用得太密 #

QTimer 本身不贵，贵的是频率和数量。

先说一个反直觉的点：start(0) 的 0 不是「立刻执行一次」，是「尽快执行，而且每次超时后重新排队」。它的实际频率等于事件循环跑一轮的速度。事件循环闲着的时候一轮只要几十微秒，等于不限速。

cpp
// 反例：0ms 周期定时器，等于让事件循环满速空转
QTimer *t = new QTimer(this);
connect(t, &QTimer::timeout, this, &Worker::pollOnce);
t->start(0);

这就是空载 CPU 底噪最常见的样子。程序看着什么都没干，pollOnce 每秒被调用上万次，每次都判断一下「有没有新数据」，答案永远是没有。pollOnce 里如果还有别的事，问题会成倍放大：一次查询、一次字符串拼接、一次 update()，乘以每秒上万次，就是一条笔直的 CPU 曲线。

第二种密度问题来自精度设置。QTimer 的精度分三档：

精度 行为 代价
Qt::PreciseTimer 尽量准，误差控制在毫秒级 系统要频繁唤醒，功耗高
Qt::CoarseTimer 允许 5% 偏差，默认值 一般够用
Qt::VeryCoarseTimer 只保证整秒级对齐 省电，但抖动大

精度越高，CPU 越不容易进低功耗状态。笔记本上「插电不烫、用电池烫」的怪现象，有时就是一批 PreciseTimer 把处理器一直钉在高频档。第三种密度问题是数量。十个 50ms 的定时器不等于五倍的 CPU，因为系统的唤醒会合并。真正的问题在每个 timeout 里做的事：十个定时器各自触发一次重算、一次全窗口重绘，加起来就是十次。

处理办法是把「触发」和「执行」分开。界面更新用一个固定的渲染节拍，所有数据变化只负责打脏标记：

cpp
void Collector::onValueChanged(int v)
{
    m_pending = v;
    m_dirty   = true;          // 只打标记，不干活
}

void Collector::flush()
{
    if (!m_dirty) return;
    m_dirty = false;
    applyToUi(m_pending);      // 真正的活在这里，一个节拍一次
}

// 初始化时挂一个节拍
m_flushTimer.setInterval(16);  // 约 60 帧
connect(&m_flushTimer, &QTimer::timeout, this, &Collector::flush);
m_flushTimer.start();

16ms 这个数来自屏幕刷新率。60Hz 的屏 16.7ms 画一帧，你刷得比它快，多出来的帧没人看得见，白烧 CPU。图省事取 16 或 20 都行。

还有一种写法制造的密度问题：在循环里不停地 new QTimer::singleShot(0, ...)。每个都往事件队列里塞一个事件，队列越塞越长，处理速度追不上塞的速度，内存和 CPU 一起涨：

cpp
// 反例：每个元素一个延期调用，队列爆炸
for (int i = 0; i < items.size(); ++i) {
    QTimer::singleShot(0, this, [this, i] { process(items[i]); });
}

// 正解：一次处理一批，或者直接同步循环
for (int i = 0; i < items.size(); ++i) {
    process(items[i]);
    if (i % 32 == 31)
        QCoreApplication::processEvents();   // 分批让出，见第六章的警告
}

QTimer 的正确用途是这些：周期性上报、心跳、超时看门狗、UI 节流。不是用来「等某个条件成立」——那是条件变量的活，用定时器做就是轮询的变种。

排查定时器密度有个土办法：给每个 QTimer 起个 objectName，在 timeout 里累加计数，每秒打印一次所有定时器的触发次数。哪个数字大得离谱，哪个就是问题。

五、重绘风暴 #

这一类跟界面强相关，症状很直观：拖动窗口、滚动列表、悬停高亮的时候 CPU 冲上去，松手就落回来。

先分清两个函数，这是 Qt 界面性能里最容易混的一对：

调用 行为 时机 合并 适用
repaint() 立即同步重绘 函数返回前就画完 不合并 极少数需要立刻可见
update() 标记脏区，异步重绘 回到事件循环后统一处理 同一区域多次合并成一次 绝大多数场合

repaint() 会立刻走完整个绘制流程。在循环里调它，循环多少次就画多少次，中间没有任何喘息。update() 只是把一块矩形标成脏的，事件循环转到绘制阶段才真正画，而且同一块区域被标了十次也只画一次。绝大多数场合应该用 update()。 repaint() 留给「必须在这一行代码之后立刻反映到屏幕上」的极个别场景，比如摄像头预览前的清屏。

素材里的第一条就是重绘风暴的经典形态：在 paintEvent 里调用 update，造成无限循环。

cpp
void Widget::paintEvent(QPaintEvent *e)
{
    QPainter p(this);
    drawContent(&p);
    update();     // 反例：每次重绘都请求下一次重绘
}

链路是这样的：update() 标脏 → 事件循环派发 paintEvent → 里面又 update() → 又标脏 → 下一轮再派发。永不停止。CPU 单核打满，界面还在「活着」，甚至动画看着挺流畅，所以没人觉得有问题。修法不在绘制里，在触发源上：数据变了才 update()，paintEvent 只管画，不负责决定什么时候再画。

cpp
void Widget::onDataChanged(const Data &d)
{
    m_data = d;
    update();          // 只有数据变化才触发
}

void Widget::paintEvent(QPaintEvent *e)
{
    QPainter p(this);
    drawContent(&p);   // 只画，不改状态
}

第二条是频繁刷新数据。数据源每秒来一千帧，每帧都 update()，绘制就跟着一千帧跑。屏幕只有 60Hz，剩下九百多帧是纯浪费。

改法是加一层节流。数据照收，模型照更新，但重绘固定在一个节拍上——就是第四章那个脏标记加 16ms 定时器的结构。数据来得再密，一秒也只画六十次。

第三条是 paintEvent 里操作太多。这个函数会被极其频繁地调用，里面每一行都被乘以调用次数。不该出现的东西：

别在 paintEvent 里做 原因 挪到哪
拼接、格式化字符串 每次重绘都重建一遍 数据变化时算好存成员
加载图片、缩放图片 缩放是重活，还每帧做 预缩放后缓存 QPixmap
查询数据库、读文件 IO 阻塞绘制，窗口直接白 另开线程预取
重建大路径、大字体度量 构造开销远超绘制 缓存，尺寸变化时重建
反复 new 临时对象 分配器压力 成员变量或栈上复用

素材把这个归为「paintEvent 里操作太多」，落到代码上就是一句话：paintEvent 里只做绘制，所有能提前算的都提前算。

还有两个降低重绘成本的手段：

cpp
void TileWidget::onValueChanged(int v)
{
    if (v == m_value) return;       // 值没变，连脏标记都别打
    m_value = v;
    update(m_valueRect);            // 只脏这一小块，不脏整窗
}

update(rect) 限定脏区，绘制时只处理这一块。控件多、格子密的界面，这一招省下的量相当可观。

setAttribute(Qt::WA_OpaquePaintEvent) 声明控件完全不透明，Qt 就不再做背景填充这一步。代价是你必须在 paintEvent 里把整块矩形画满，漏一块就是花屏。

判断有没有重绘风暴，最快的办法是在 paintEvent 第一行计数：

cpp
void Widget::paintEvent(QPaintEvent *e)
{
    static QElapsedTimer timer;
    static int count = 0;
    if (!timer.isValid()) timer.start();
    if (timer.elapsed() >= 1000) {
        if (count > 200)
            qWarning() << "repaint storm:" << count << "/s";
        count = 0;
        timer.restart();
    }
    ++count;
    // 正常绘制……
}

一秒画两百次以上就该查。正常界面在静止时是零次到几次，动起来顶多六十次。数字上万，那是 update 写在 paintEvent 里了。

六、主线程被阻塞 #

这一类最容易被误判，因为它的 CPU 曲线往往是低的。用户反馈「卡」，你打开任务管理器，CPU 20%，一切正常，然后就不知道该查什么了。

先把认知摆正：主线程只有一件事要做，就是跑事件循环。 事件循环转一圈，界面才能响应一次鼠标、重绘一次、处理一个定时器。主线程被占住多久，界面就冻多久。素材里的「复杂的浮点运算」属于这一类。它到底归第六章还是第八章，取决于它在哪个线程跑：在主线程跑就是阻塞，在工作线程跑但只用一个核就是并行度不足。

主线程上的重活清单，长这样：

类型 例子 表现
重计算 浮点积分、矩阵运算、大数排序 点按钮后界面停住数秒
同步 IO 读大文件、QSqlQuery::exec、同步 HTTP 窗口白屏，标题栏显示未响应
图像处理 scaled()、滤镜、逐像素遍历 拖动窗口时撕裂
等待 wait()、sleep、等锁、等信号量 界面完全冻死
海量字符串 全量格式化、正则回溯 启动或切换页时长时间无响应

有个常见的错误补救办法：用 processEvents() 强行让界面「活着」。

cpp
// 反例：靠 processEvents 续命
for (int i = 0; i < n; ++i) {
    heavyStep(i);
    QCoreApplication::processEvents();
}

这段代码会带来三个新问题。一是重入：processEvents 期间用户又点了一次按钮，同一个函数被嵌套调用一次，状态全乱。二是事件风暴：处理事件本身要花时间，总时长反而更长。三是它没解决根本问题，只是把一次长冻拆成很多次短冻，帧率依然上不去。

正确的做法只有一条：搬到别的线程。

cpp
#include <QtConcurrent>
#include <QFutureWatcher>

void MainWindow::startCompute()
{
    ui->btnStart->setEnabled(false);

    auto *watcher = new QFutureWatcher<Result>(this);
    connect(watcher, &QFutureWatcher<Result>::finished, this, [this, watcher] {
        applyResult(watcher->result());
        watcher->deleteLater();
        ui->btnStart->setEnabled(true);
    });
    watcher->setFuture(QtConcurrent::run(computeHeavy, m_input));
}

这个结构里有三处值得学。用 QFutureWatcher 而不是 waitForFinished()，主线程全程不阻塞。用 deleteLater() 而不是 delete，避免在槽函数里销毁发信号的对象。按钮的禁用与恢复放在信号两端，状态机和生命周期对齐。

只在需要结果的时候才回主线程。计算中间过程要显示进度，就发节流过的进度信号，不是每一步都发。

还有一类隐蔽的阻塞：死锁式等待。主线程 wait() 工作线程，工作线程又用 Qt::BlockingQueuedConnection 回主线程要数据，两边互等，程序挂死。

cpp
// 反例：双向等待，教科书级死锁
// 主线程
worker->wait();                                   // 等 worker 结束
// worker 内部
emit needConfig();    // BlockingQueuedConnection，等主线程槽返回

主线程在 wait() 里不转事件循环，槽永远等不到；wait() 也永远返回不了。看到「界面卡住但 CPU 是 0」，先怀疑这个。

修法：单向依赖。工作线程要数据，主线程在启动时一次性给它，别在跑的过程中回头要。非要回头要，用普通队列连接，异步送过去。

七、信号槽风暴 #

信号槽本身很快。Qt::DirectConnection 就是一次函数调用加一次数组遍历，开销可以忽略。贵的是三件事：跨线程的队列投递、每次只传一条、连接重复。素材里的架构正好踩在前两件事上：接收子线程解析完一帧数据就 emit 一次，融合子线程的槽被唤醒一次。数据稀疏时一切正常，数据一密就出事。

跨线程的信号槽默认是 Qt::QueuedConnection。每次 emit 要做这些事：把参数打包、分配一个事件对象、加锁投进目标线程的事件队列、目标线程的事件循环取出来、解包、调用槽。一条数据一趟。

帧率一千，每秒就是一千趟。事件队列里堆积的速度超过消费速度时，队列变长，内存上升，锁竞争加剧，CPU 跟着上去——这就是曲线「随时间爬升不回落」的典型来源。

第一条修法是合并，攒一批发一次：

cpp
// 反例：每条数据一个信号
emit frameReady(frame);

// 正解：攒一批再发
m_batch.append(frame);
if (m_batch.size() >= 64 || m_batchTimer.elapsed() >= 16) {
    emit batchReady(m_batch);
    m_batch.clear();
    m_batchTimer.restart();
}

批量的两个触发条件要同时有：按数量攒，防止数据稀疏时一直不发；按时间攒，防止数据密集时批次太大导致延迟。批量本身有代价，队列连接会拷贝参数。m_batch 是个容器，emit 时整个拷一遍，量大了拷贝成本就顶上来。两个规避方向：一是传 QSharedPointer<const QVector<Frame>>，只拷指针；二是接受拷贝，但把批次大小压到一个合理区间，别攒到几万条。

第二条修法是减少连接数。重复 connect 是隐蔽的坑：

cpp
// 反例：每次刷新设置都连一次
connect(m_device, &Device::changed, this, &Panel::onChanged);

// 正解：加 Qt::UniqueConnection，或者连一次就够
connect(m_device, &Device::changed, this, &Panel::onChanged, Qt::UniqueConnection);

同一个信号连了三次，槽就被调三次。连的地方在「打开设备」函数里，用户开关十次设备，槽就被调十次，CPU 随着使用时长往上走。这类 bug 用一次跑十分钟测不出来，得跑够时间。

第三条是别用信号槽当数据泵。高频数据搬运有更省的路子：共享一块环形缓冲，用信号只发一个「有新数据」的通知，接收方自己去取。

传输方式 每帧成本 适用
每条数据一个信号 事件对象 + 参数拷贝 + 两次加锁 低频控制消息
批量信号 上式摊薄到 1/64 中高频数据
共享缓冲 + 通知信号 一次通知 高频数据流

还有一处容易忽略：Qt::BlockingQueuedConnection 会让发送方阻塞到槽执行完。用在每条数据的通路上，等于把两个线程串行化，还埋了第六章那个死锁。

排查信号槽风暴，直接在槽里计数：

cpp
void FusionWorker::onBatch(const QVector<Frame> &batch)
{
    static int n = 0;
    if (++n % 200 == 0)
        qDebug() << "slot calls:" << n << "queue size:" << batch.size();
    // 处理……
}

顺便看一眼目标线程的事件队列长度。队列只涨不落，就是生产快过消费，合并或加线程，二选一。

八、线程数与并行度 #

前六章讲的是「干了不该干的事」。这一章讲另一半：活是该干的，但干法不对。

素材里提到「复杂的浮点运算」。浮点运算本身不慢，慢的是两种情形：一是算法复杂度选错了，二是算了但只用一个核。

先看第一种。一次卷积该用 O(n) 的滑动窗口，写成了 O(n²) 的两重循环，核数再多也救不回来。优化算法比并行化划算一个数量级，顺序不能反——先把复杂度降下来，再谈并行。

第二种是并行度。QThread::idealThreadCount() 返回的是当前机器上适合跑计算密集型任务的线程数，取值等于逻辑核数：

cpp
const int n = QThread::idealThreadCount();
qDebug() << "ideal threads:" << n;

这个数不是随便取的，它考虑了物理核与超线程。用超线程凑出来的「双倍核数」，跑浮点运算的收益有限，所以拿它当计算任务的分片数是个合理起点。

线程数超过这个值的代价是真实的：

线程数相对核数 现象 原因
少于核数 有核闲着，总时长没降下来 并行度不足
等于核数 最省总时长 每核一个线程，无争抢
略多于核数 总时长持平，CPU 曲线更满 上下文切换开始抵消收益
远超核数 曲线满但更慢 切换开销、缓存反复失效

第四行是最容易踩的。有人以为线程开得多就跑得快，实际上每个线程都要抢 CPU、抢缓存，切换一次要保存恢复寄存器、污染 L1/L2。核数是八，开八十个线程，多出来的七十二个全在排队。

并行化的写法，别手搓线程池：

cpp
#include <QtConcurrent>
#include <QFuture>

QVector<double> chunks = splitRange(range, QThread::idealThreadCount());

// 每个分片一个任务，线程数由全局线程池决定
QFuture<double> f = QtConcurrent::mappedReduced(
    chunks,
    [](const QVector<double> &c) {
        double s = 0.0;
        for (double v : c) s += v;
        return s;
    },
    [](double &result, const double &partial) { result += partial; }
);
f.waitForFinished();
const double total = f.result();

mappedReduced 把「分片计算」和「结果合并」拆开，线程池按 idealThreadCount() 分配工作线程，你不管线程生命周期。合并那一步是串行的，所以分片数量别太多——每个分片的合并开销乘以分片数，最后会变成瓶颈。

判断该往哪个方向改，看 CPU 曲线形状：

  • 单核逼近 100%，其余核闲着：并行度不足，拆。
  • 所有核都被拉满，总时长还是长：算法或数据量的问题，别再加线程。
  • 核数拉满但大量时间在等锁：锁粒度太粗，先减争用。

第三种情况在多线程融合的场景里最常见。融合线程要汇总各接收线程的结果，如果用一把大锁护住整个汇总过程，所有线程排队等它，CPU 曲线是满的，吞吐是死的。改法是把锁拆细，或者每个线程维护自己的局部结果，最后合并一次。

九、诊断工具与方法 #

工具不用多，够用就行。按「能回答什么问题」来选，比按平台选更省事。

工具 平台 能回答什么 局限
任务管理器 Windows 进程级 CPU、线程数 看不到单个线程
Process Explorer Windows 哪个 TID 在吃 CPU 栈要另接调试器
top / htop Linux 线程级实时占用 只有瞬时值
perf Linux 函数级热点、调用栈 需要采样权限
gdb 手采样 跨平台 卡在哪个函数 精度粗，靠重复确认
VS 诊断工具 Windows 函数级耗时 对调试符号有要求
Qt Creator 分析器 跨平台 函数级耗时、QML 帧耗时 需要 Qt 的调试构建
QElapsedTimer 跨平台 某段代码的实际耗时 要改代码
日志计数 跨平台 调用频次、队列长度 要改代码，且有开销

用法按四步走，别跳步：

第一步，进程级确认。CPU 到底高不高，是不是我们的进程。这一步排除掉杀毒、索引、驱动。

第二步，线程级定位。找出吃 CPU 的那个 TID。到这一步，问题已经从「程序慢」缩到「某个线程」。

第三步，函数级采样。用 perf、VS 诊断工具或 Qt Creator 分析器，看这个线程的时间花在哪些函数上。排前几名的函数就是嫌疑人。

第四步，插桩确认。在嫌疑人函数里加 QElapsedTimer，测调用次数和单次耗时。到这一步才有资格改代码。

采样和插桩的取舍要清楚：

手段 优点 缺点 用在哪一步
采样 不改代码，能看到全貌 精度受采样率限制，短函数抓不到 第三、四步之间
插桩 精确到单次调用 要改代码，本身有开销 锁定嫌疑人之后

采样的盲区是短函数。一个函数每次只跑 20 微秒，但每秒被调一百万次，采样几乎抓不到它，它却是 CPU 消耗的大头。这种情况要靠插桩的调用计数补上——QElapsedTimer 测单次，一个静态计数器测频次，两个数一乘就是总消耗。

十、二分定位法 #

热点找不到、代码路径又长的时候，用二分。它不需要工具，需要的是耐心和一个可重复的现象。

基本动作：关掉一半，看曲线。曲线降下来，问题在被关掉的一半里；没降，在另一半。重复。

三个二分维度，按使用顺序排：

维度 怎么切一半 适合查什么
代码路径 注释掉一个子系统、一段初始化 开机就高、某功能启用后才高
数据量 把输入规模减半 与数据量成正比的消耗
版本 git bisect 找引入点 「上个版本还好好的」

第一个维度的操作要具体。假设程序有接收、解析、融合、存储、显示五个子系统，先把显示相关的 update() 和定时器全注掉，跑一分钟看曲线。掉下来就说明问题在显示侧，接着二分显示内部（只注绘制 / 只注定时的调用点）。

注释有风险：注掉一段会让另一段不再被调用，曲线下降的原因是「功能没跑」而不是「问题被移除」。所以每次注释之后要确认功能确实还在跑，只是路径变短了。用日志确认，别用眼睛看界面。

第二个维度用在「消耗跟数据量线性相关」的场景。把输入帧率减半，CPU 也减半，说明每帧成本固定，优化方向是批处理和合并；CPU 只降一点点，说明有固定开销在前面，跟数据量无关，优化方向是启动路径和轮询。

第三个维度是 git bisect，适合「新版本才出问题」：

bash
git bisect start
git bisect bad v1.4.0
git bisect good v1.3.0
git bisect good          # 每轮手动构建、测试之后标记，直到锁定引入提交

用之前先准备好一个能自动判定「好坏」的脚本，否则十几轮手动测试很容易放弃。判定条件别用肉眼感觉，用可测的数字，比如「空载一分钟的平均 CPU 超过阈值」。

二分有一条铁律：一次只改一个变量。 同时注释两个子系统，曲线降了，你不知道是哪个的功劳；曲线没降，你不知道是不是一个降一个升互相抵消了。

十一、改完怎么验证 #

改完不等于修好。验证要做三件事：同条件对比、多场景覆盖、够长时间。

同条件的意思是：同一台机器、同一份数据、同样的操作序列、同样的时长。跨机器比数字没有意义，第八章说过原因。

指标别只盯平均值。平均 CPU 从 30% 降到 25% 看着不错，但峰值从 60% 冲到 90%，风扇照样响，用户体验更差。

指标 怎么看 为什么重要
平均 CPU 一分钟以上取均值 反映持续负载
峰值 CPU 记录尖峰出现的时刻 决定风扇会不会转
曲线形状 平直还是有锯齿 锯齿说明有周期性重活
响应延迟 操作到界面反应的间隔 防止拿延迟换 CPU
内存 长跑是否持续增长 顺手排掉累积型问题

三个场景都要覆盖：

  • 空载：启动后不操作，放五分钟。这一项专门针对忙等待和定时器过密。
  • 典型负载：按真实用法跑。这一项针对重绘和信号槽。
  • 极限负载：数据量翻倍或并发拉满。这一项看曲线是否饱和退化成卡死。

长跑不能省。累积型问题（重复 connect、容器只增不减、事件队列堆积）在十分钟的测试里完全看不出来。跑够两小时，曲线还平，才算过。

最后一个陷阱：把阻塞换成了延迟。原来主线程算 800ms 界面冻住，现在丢到工作线程，CPU 曲线好看了，但用户点按钮还是 800ms 没反应。这是把问题搬了地方，不是修好。验证时一定要测端到端的响应时间，别只测 CPU。

现象 错误做法 正确做法
空载 CPU 高 直接加 sleep 先查是不是 start(0) 定时器或空循环
paintEvent 里调 update 改成 repaint 删掉 update，把触发移到数据变化处
界面卡但 CPU 低 查 CPU 占用 查主线程阻塞和死锁
用 processEvents 救界面 在循环里密集调用 把重活搬到工作线程
拖窗口才卡 换显卡、关动画 查重绘频率和 paintEvent 里的重活
数据越多越卡 加线程 先批量合并信号，再加线程
越用越卡 重启程序 查重复 connect 和队列堆积
