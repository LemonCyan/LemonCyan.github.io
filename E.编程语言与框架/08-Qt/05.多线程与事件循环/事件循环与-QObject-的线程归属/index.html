这篇只讲 Qt 事件驱动机制的三根柱子：事件循环怎么转、QObject 为什么带「线程归属」、跨线程的信号槽到底靠什么把一次调用送到另一个线程。

不讲：QThread 子类化与 moveToThread 的完整工程写法（见同目录《QThread 的正确用法》）；线程池与并发任务的调度策略（见《线程管理与线程间通信》）；自定义事件类的定义与 postEvent 投递细节（见《自定义事件与跨线程投递》）；QTimer 的精度与替代方案（见《定时器》）。这里把「事件怎么走、对象归谁、调用落在哪个线程」讲透，其余留给邻篇。

示例是 C++，QThread::currentThreadId() 打出来的值每次都不一样，结论不变。凡是打印线程 id 的代码，你照着敲一遍比读十遍管用。

一、事件驱动模型 #

Qt 程序的主干不是 main()，是一个循环。main() 交代完初始化就调用 exec()，把控制权交出去，自己再也不回来——直到程序要退出。

循环里跑的东西有两类：事件和信号。两者容易混，先把账分清。

对比项 事件（event） 信号（signal）
目标 有，明确指向一个 QObject 无，谁连上谁收
载体 QEvent 的子类对象 moc 生成的信号函数
传递 进目标对象所属线程的事件队列 直接调用槽，或入队后调用槽
处理 QObject::event() 再分发到具体 handler 槽函数 / lambda / 可调用对象
多播 一对一 一对多

一句话：事件是「寄给某个对象的信」，信号是「广播」。

事件的类型用 QEvent::Type 标识，所有事件类都从 QEvent 派生。目标对象确定后，处理入口固定在虚函数 QObject::event()。想拦本对象的事件，重写它。

cpp
// 所有事件都是 QEvent 的子类，类型由 Type 枚举区分
class Watcher : public QObject
{
protected:
    bool event(QEvent *e) override
    {
        switch (e->type())
        {
        case QEvent::User:
            qDebug() << "user event";
            return true;            // 吃掉，不再往下传
        case QEvent::Timer:
            qDebug() << "timer event";
            break;                  // 继续交给基类
        default:
            break;
        }
        return QObject::event(e);   // 基类按类型分发给 mousePressEvent 等
    }
};

QObject::event() 本身是个分发中枢。QWidget::event() 重载了它，把 QEvent::MouseButtonPress 转给 mousePressEvent()，把 QEvent::KeyPress 转给 keyPressEvent()，把 QEvent::Paint 转给 paintEvent()。你在子类里重写 mousePressEvent() 能收到鼠标，是因为有人替你做了那一跳。

事件类型 处理函数
QEvent::MouseButtonPress QWidget::mousePressEvent()
QEvent::KeyPress QWidget::keyPressEvent()
QEvent::Paint QWidget::paintEvent()
QEvent::Timer QObject::timerEvent()
QEvent::DeferredDelete 直接析构对象，不经过 event()
QEvent::User 及以上 你自己在 event() 里判断

再往上还有一层 QApplication::notify(receiver, event)。它是投递的总入口，sendEvent() 和 postEvent() 最后都要走它。想全局拦截事件（做调试、做审计、做输入过滤）就覆写 notify()，别去改每个 widget。

三件套到此凑齐：一个事件对象、一个目标对象、一个正在运行的事件循环。缺任何一件，事件都动不了。目标对象没活着，事件没人收；事件循环没跑，事件在队列里烂掉。

二、事件循环在做什么 #

事件循环的骨架短到可以背下来。

text
while (is_active)
{
    while (!event_queue_is_empty)
        dispatch_next_event();      // 把队列掏空

    wait_for_more_events();         // 没事件就睡在这里
}

内层循环把队列清空，外层阻塞等待。注意 wait_for_more_events() 被调用时队列一定是空的，也就是说此刻能产生新事件的只能是外部资源：窗口系统、socket、定时器超时、别的线程投递。内部该发的都发完了。

唤醒机制跟平台有关，思路一样：

  • Unix/X11 下，窗口系统通过 socket（Unix 域或 TCP/IP）通知应用；分发器用 select(2) / poll(2) / epoll 监控一批描述符，超时也返回。
  • Windows 下是消息队列加 MsgWaitForMultipleObjects。
  • 跨线程投递靠 socketpair(2) 或 eventfd 把目标线程的分发器叫醒。

select() 返回后，Qt 要做的事就是把「某个 fd 可读」翻译成一个具体的 QEvent 子类，塞进队列。事件循环里装的就是这些翻译好的东西。

进主循环的入口是 QCoreApplication::exec()，它会阻塞，直到 exit() 或 quit() 被调用。

cpp
int main(int argc, char *argv[])
{
    QCoreApplication app(argc, argv);

    qDebug() << "main thread:" << QThread::currentThreadId();

    // ... 建对象、连信号槽
    return app.exec();   // 阻塞在这里，直到 quit()/exit()
}

quit() 等价于 exit(0)。exec() 返回时，循环已经结束，后面的清理代码才会跑。

事件循环不是全进程唯一。每个调用 exec() 的线程有自己的一份。QThread::run() 里写 exec()，开的就是该线程的局部循环。这也解释了为什么「线程」和「事件循环」是两件事：线程一定在跑，循环不一定开。

不开主循环也能临时转一圈。QEventLoop 是同一套机制的可重入版本：

cpp
// 局部事件循环：等一个操作完成，又不想把主循环让出去
QEventLoop loop;
QTimer::singleShot(1000, &loop, &QEventLoop::quit);
loop.exec();
qDebug() << "1 秒后到这里";

QTimer::singleShot 带 context 对象的重载在 Qt 5 之后才有，Qt 4 时代要写 QObject::connect(&timer, SIGNAL(timeout()), &loop, SLOT(quit()))。

三、事件从哪里来 #

来源归四类，落到队列里都是同一个形态：一个 QEvent 对象 + 一个目标 QObject。

来源 典型事件 唤醒方式
窗口系统 QKeyEvent、QMouseEvent、QWheelEvent、QExposeEvent 窗口系统 socket / 系统消息
操作系统定时器 QTimerEvent select() 超时
socket 活动 内部 QSocketNotifier，转成 readyRead/connected 等信号 fd 可读可写
应用内部 QChildEvent、QPaintEvent、QMetaCallEvent、QDeferredDeleteEvent 本线程直接入队
其他线程 任意 QEvent，含 QMetaCallEvent socketpair/eventfd 唤醒对方分发器

窗口系统。键盘、鼠标、滚轮、窗口暴露，全部由窗口管理器送进来。这类事件有明确目标：鼠标在哪个 widget 上按下，事件就投给谁。

定时器。startTimer() 只是登记，登记完什么都不发生。超时那一刻由事件循环投递 QTimerEvent。

cpp
class Ticker : public QObject
{
public:
    void start() { m_id = startTimer(500); }   // 需要有一个在跑的事件循环

protected:
    void timerEvent(QTimerEvent *e) override
    {
        if (e->timerId() == m_id)
            qDebug() << "tick" << QThread::currentThreadId();
    }

private:
    int m_id = 0;
};

socket。Qt 的网络类天生异步。read() 只是把已经到达的数据取出来，write() 只是把数据排进发送计划，真正的读写发生在事件循环返回、fd 就绪的时候。waitFor* 那一族是同步封装，代价是把事件循环堵住，除非你明确知道自己在干什么，否则别用。

应用内部。QWidget::update() 不打画笔，它只标记脏区、发一个更新请求，QPaintEvent 由事件循环稍后派发。deleteLater() 不删对象，它发一个 QDeferredDeleteEvent。队列连接的信号槽，本质就是往目标线程投一个 QMetaCallEvent。

其他线程。QCoreApplication::postEvent() 是线程安全的，它把事件加进目标对象所属线程的队列，然后唤醒那个线程的分发器。这是 Qt 跨线程通信的唯一底层通道，信号槽只是包在它外面的一层皮。

事件不会在产生的那一刻被派发。sendEvent() 是唯一的例外——它是同步直投，绕开队列。这个区别后面单独讲。

归纳一句：事件的产生是异步的，派发是被动的，落到哪个线程由目标对象的线程归属决定。

四、事件的产生与分发 #

投递只有两条路，区别在于要不要经过队列。

对比项 sendEvent() postEvent()
时机 立即调用 notify() → event() 入队，稍后由事件循环派发
执行线程 调用者线程，同步返回 目标对象所属线程
事件对象所有权 调用者持有，可复用、可自己 delete Qt 接管，派发后自动 delete
优先级 无 可传 Qt::HighEventPriority 等
跨线程 禁止，等于在错误线程里跑槽 线程安全，跨线程的唯一正解
返回值 bool，反映事件是否被接受 void，只表示是否入队成功

签名摆在一起看：

cpp
bool QCoreApplication::sendEvent(QObject *receiver, QEvent *event);
void QCoreApplication::postEvent(QObject *receiver, QEvent *event,
                                 int priority = Qt::NormalEventPriority);

同一个事件分别走两条路，打印顺序立刻不同。

cpp
class Receiver : public QObject
{
protected:
    bool event(QEvent *e) override
    {
        qDebug() << "delivered in" << QThread::currentThreadId()
                 << "type" << e->type();
        return true;
    }
};

// 主线程里
Receiver r;

auto *e1 = new QEvent(QEvent::User);
QCoreApplication::sendEvent(&r, e1);    // 同步，立刻打印；e1 归你 delete
qDebug() << "after sendEvent";

auto *e2 = new QEvent(QEvent::User);
QCoreApplication::postEvent(&r, e2);    // 只入队，e2 归 Qt 管
qDebug() << "after postEvent";          // 这行比 e2 的派发先出来

text
delivered in 0x1a40 type 52
after sendEvent
after postEvent

最后那个事件的打印要等事件循环转一圈，所以不在这一段里。这个顺序差异是理解后面所有跨线程行为的钥匙：postEvent 只是把东西交出去，什么时候执行由对方线程决定。

再看一次完整的调用栈，把「事件」和「槽」串起来。一个按钮被点击，槽里干了三秒活：

text
main(int, char**)
  QApplication::exec()
    [...]
    QWidget::event(QEvent*)                    // notify() 送进来的鼠标事件
      Button::mousePressEvent(QMouseEvent*)    // 基类按类型分发
        Button::clicked()                      // 你 emit 的信号
          [...]
          Worker::doWork()                     // 直连的槽，同步跑三秒

事件循环派发鼠标事件，一路下沉到 mousePressEvent()，emit clicked() 触发直连的槽，槽在同一个调用栈里跑完。doWork() 不返回，事件循环就卡在这一层，一个事件都派不出去。

后果是一串的：

  • 窗口不重绘，QPaintEvent 在队列里排队。
  • 点击、键盘不再有反应，输入事件进不来。
  • 定时器不走，超时事件投不出来。
  • 网络数据堆在内核缓冲区，没人读。
  • 窗口管理器判定程序无响应，标题栏变灰，弹「not responding」。
  • 更糟的情况是数据到达速度超过你处理速度，内核缓冲填满、丢包，传输速率断崖下跌。

这不是风格问题，是机制决定的。所以规则只有一条：槽要短，活要拆，重活挪线程。

分发链路上的每一环都能插手：

text
postEvent() → 事件队列 → 分发器 → notify() → event() → 具体 handler

QApplication::notify() 在 Qt 里还处理鼠标捕获、快捷键、Enter 键默认按钮这些全局逻辑，处理完再交给 receiver->event()。要全局审计事件流向，覆写 notify()，别去动每个 widget。

五、QObject 的线程归属 #

每个 QObject 有一个「线程归属」（thread affinity），就是它落在哪个 QThread 上。它收到的事件在那个线程的事件循环里派发，它的队列连接槽也在那个线程执行。整套跨线程机制就立在这一个概念上。

判定规则只有一条：对象归属于创建它的那个线程，准确说是构造那一刻正在运行的那个线程。

cpp
class MyThread : public QThread
{
public:
    MyThread()
    {
        otherObj = new QObject;        // 谁 new 的？执行构造函数的线程
    }

private:
    QObject obj;                       // 成员，构造时创建
    QObject *otherObj = nullptr;
    QScopedPointer<QObject> yetAnotherObj;
};

这个 MyThread 在主线程里 new 出来，构造函数就在主线程跑。obj、otherObj 全是主线程的。它们和 MyThread 管理的那个次线程毫无关系，尽管它们长在同一个类里。

对象 谁创建 归属线程
MyThread 实例本身 主线程 new 主线程
obj（成员） 构造时初始化 主线程
otherObj 构造函数里 new 主线程
run() 里的局部对象 次线程 次线程
run() 里 new 的对象 次线程 次线程
run() 里 new QObject(this) 次线程，parent 在主线程 冲突，别这么写

查询用两个函数，返回都是 QThread*：

cpp
QObject *obj = new QObject;
qDebug() << "obj lives in" << obj->thread()
         << "current thread is" << QThread::currentThread();

if (obj->thread() == QThread::currentThread())
    qDebug() << "归我，可以直接碰";
else
    qDebug() << "不归我，只能 postEvent / 队列调用";

这个判断值得写进任何跨线程函数的入口，比加一堆 mutex 便宜。

有个边界情况：QCoreApplication 构造之前创建的 QObject 没有归属，thread() 返回 nullptr。那时还没有代表主线程的 QThread 对象，也就没人给它派发事件，投进去的事件永远不会被处理。QCoreApplication 的构造顺带建了代表主线程的那个 QThread。

改归属用 moveToThread()。规则不多，但每条都硬：

  • 只能在对象当前所属线程里调用。从别的线程调等于「拉」，Qt 不允许，你会看到警告。
  • 对象有 parent 就不能移。
  • 移了对象，它的 children 一起移。Qt 要求 child 与 parent 同线程。
  • 移的是归属，不是正在执行的调用栈。移完以后产生的事件才去新线程。
cpp
QThread thread;
Worker worker;                       // worker 此时归主线程
qDebug() << (worker.thread() == QThread::currentThread());   // true

worker.moveToThread(&thread);        // 必须在主线程里调
thread.start();                      // run() 里要有 exec() 才有循环

QMetaObject::invokeMethod(&worker, "doWork", Qt::QueuedConnection);

thread.start() 之前 move 和之后 move 都行，但只要工作对象已经在新线程里跑起来，就不该再动它的归属。

错误写法长这样，一眼能看出来是 parent 冲突：

cpp
class Thread : public QThread
{
protected:
    void run() override
    {
        QObject *obj = new QObject(this);   // 错：this 归主线程，obj 生在次线程
    }
};

QThread 对象归属主线程，this 当 parent 就等于要求 obj 也在主线程，可它偏偏是次线程 new 的。Qt 会警告，行为也别指望。

销毁顺序同样受归属约束。对象要在代表线程的 QThread 销毁之前删掉，省事的做法是在 run() 里创建，函数返回时自然析构。跨线程删对象必须走 deleteLater()。

cpp
// 错误：在 A 线程 delete 一个归属 B 线程的对象
delete obj;

// 正确：投一个 QDeferredDeleteEvent，回到 B 线程再删
obj->deleteLater();

理由很直接：delete 立刻跑析构，析构会碰那些正被 B 线程事件处理的数据。deleteLater 把删除动作也排进 B 的队列，和 B 的事件串行执行。

补充两条边界：QObject 不是线程安全的（是可重入的），多线程访问同一个对象要自己加锁；QWidget 和所有 GUI 相关类连可重入都不是，必须待在 GUI 线程。QPixmap 这类不是 QObject 的 GUI 类同样如此。

六、thread() 与当前线程不是一回事 #

这一节最容易绕晕。先记一句：**QThread 对象不是线程，它是操控线程的句柄。**句柄归属创建它的线程，线程本体在 run() 里跑。

Bradley T. Hughes 的说法：QThread 应该被看作操作系统线程的接口或控制点，它不该包含需要在新线程里运行的代码；要跑的代码放进 QObject 子类，再把这个对象 move 到新线程。Qt 4.4 之后 run() 默认调用 QThread::exec()，不子类化 QThread 也能有事件循环，这个建议才真正好用。

三个实验，都打印线程 id。主线程记作 M，次线程记作 S。

实验一，信号在主线程发，槽写在 QThread 子类里：

cpp
class Dummy : public QObject
{
    Q_OBJECT
public slots:
    void emitSig() { emit sig(); }
signals:
    void sig();
};

class Thread : public QThread
{
    Q_OBJECT
public slots:
    void slotMain() { qDebug() << "slot:" << QThread::currentThreadId(); }
protected:
    void run() override
    {
        qDebug() << "run: " << QThread::currentThreadId();
        exec();
    }
};

int main(int argc, char *argv[])
{
    QCoreApplication app(argc, argv);
    qDebug() << "main:" << QThread::currentThreadId();

    Thread thread;
    Dummy dummy;
    QObject::connect(&dummy, SIGNAL(sig()), &thread, SLOT(slotMain()));

    thread.start();
    dummy.emitSig();          // 信号在主线程发射

    const int ret = app.exec();
    thread.quit();
    thread.wait();            // 不 wait 就直接析构，Qt 会报线程仍在运行
    return ret;
}

text
main: 0x1a40
run:  0x1a48
slot: 0x1a40

槽在主线程。dummy 在主线程发信号，thread 对象归属主线程，AutoConnection 判定两端同线程，走直连，在发射线程里同步调完。次线程那个 exec() 跟这个槽没有半点关系。

「thread.start() 之后 Thread 的槽就归次线程了」——这个念头是绝大多数 QThread 误用的起点。

顺带解释一个老现象：slotMain() 在主线程跑，run() 在次线程跑，两者碰同一个成员时是真的并发。Qt 自带的例子凡是让槽和 run() 共同操作一个对象，一律用 QMutex 锁住。这不是 Qt 啰嗦，是归属规则推出来的必然结果。

实验二，想让它进次线程，最直觉的做法是在构造函数里 moveToThread(this)。确实生效，但这是被明确反对的用法。

cpp
class Thread : public QThread
{
    Q_OBJECT
public:
    Thread(QObject *parent = nullptr) : QThread(parent)
    {
        moveToThread(this);    // 能用，但别用
    }
    // ...
};

text
main: 0x13c0
run:  0x1de0
slot: 0x1de0

槽进了次线程。代价是 QThread 对象自己搬进它管理的线程里，控制面和执行面糊成一团，quit()、wait()、对象销毁顺序全变得难推理。真实的工程代码里，这个写法会连着带来退出时崩溃。

实验三，信号在 run() 里发，接收者留在主线程：

cpp
class Thread : public QThread
{
    Q_OBJECT
public slots:
    void slotThread() { qDebug() << "slot:" << QThread::currentThreadId(); }
signals:
    void sig();
protected:
    void run() override
    {
        qDebug() << "run: " << QThread::currentThreadId();
        Dummy dummy;                                  // 次线程里的局部对象
        connect(&dummy, SIGNAL(sig()), this, SLOT(slotThread()));
        dummy.emitSig();                              // 信号在次线程发射
        exec();
    }
};

text
main: 0x15c0
run:  0x1750
slot: 0x15c0

槽还是主线程。this（Thread 对象）归主线程，AutoConnection 看到发射线程 S ≠ 接收者线程 M，走队列连接，事件投进主线程队列，主线程的循环里执行。

四种组合摆成表：

场景 信号发射线程 接收者归属 连接方式 槽实际运行
实验一 主线程 主线程 直连 主线程
实验二（moveToThread(this)） 主线程 次线程 队列 次线程
实验三 次线程 主线程 队列 主线程
工作者对象已 move 到次线程，在次线程里被调用 次线程 次线程 直连 次线程

最后一行是正路：把工作对象 move 到次线程，让调用落在次线程里，不碰 QThread 子类。

一句话收尾：QThread 对象的槽默认在主线程跑，别指望它替你干重活；想让代码在次线程跑，就把对象挪过去，把调用投过去。

七、事件队列与跨线程投递 #

每个线程一份事件队列，由 QAbstractEventDispatcher 管着。这三条不变量记住，后面的现象全能推出来：

  1. 队列按线程分，不按对象分。一个线程里所有 QObject 共用一个队列。
  2. 事件进哪个队列，由目标对象的 thread() 决定，跟谁投的没关系。
  3. 队列里的东西，只有那个线程的分发器在转的时候才会被取出来。

第 2 条是跨线程投递的全部秘密。你在 A 线程 postEvent 一个归属 B 线程的对象，事件就跑进 B 的队列，A 只管塞进去然后叫醒 B 的分发器。

cpp
// 线程安全，可从任意线程调用
bool QCoreApplication::postEvent(QObject *receiver, QEvent *event,
                                 int priority = Qt::NormalEventPriority);

Qt 5 起返回 bool，表示是否入队成功。事件对象 new 出来交给 Qt，别自己 delete，也别重复投同一个。

优先级影响取用顺序，不影响线程归属：

cpp
QCoreApplication::postEvent(obj, new QEvent(QEvent::User), Qt::HighEventPriority);

postEvent 没有队列长度上限。生产者比消费者快，队列会一直长，内存跟着涨。这是「内存缓慢上涨」类故障的常见源头，排查思路是数队列长度而不是加 sleep。

手动冲刷本线程队列：

cpp
QCoreApplication::sendPostedEvents();     // 处理本线程所有已入队事件
QCoreApplication::processEvents();        // 更狠：连窗口系统事件一起处理

这两个都是「我暂时让出控制权」的意思，后面讲重入时会看到它们的代价。

跨线程投递除了原始事件，还有一层更好用的封装：QMetaObject::invokeMethod。

cpp
class Worker : public QObject
{
    Q_OBJECT
public slots:
    void compute(int n, const QString &tag)
    {
        qDebug() << "compute in" << QThread::currentThreadId() << n << tag;
    }
};

// 主线程里
QThread thread;
Worker worker;
worker.moveToThread(&thread);
thread.start();

QMetaObject::invokeMethod(&worker, "compute", Qt::QueuedConnection,
                          Q_ARG(int, 42), Q_ARG(QString, QStringLiteral("job")));

invokeMethod 的队列模式内部就是造一个 QMetaCallEvent，postEvent 到 worker.thread()。参数要能在事件对象里存下来，所以必须可拷贝。

自定义类型要过两道关：

cpp
struct Job
{
    int id = 0;
    QString name;
};

Q_DECLARE_METATYPE(Job)          // 让 QVariant 认识它

// 在第一次 connect / invokeMethod 之前调用
qRegisterMetaType<Job>("Job");

缺了 qRegisterMetaType，运行时会甩一句「Cannot queue arguments of type 'Job'」，槽根本不执行。这是队列连接最经典的哑火原因。

投递方式横向对照：

方式 同步性 要求 实际执行线程
postEvent() 异步 事件对象交 Qt 管 目标对象归属线程
sendEvent() 同步 目标对象在调用线程 调用者线程
invokeMethod(..., Direct) 同步 方法是槽或 Q_INVOKABLE 调用者线程
invokeMethod(..., Queued) 异步 同上 + 参数可拷贝 目标对象归属线程
invokeMethod(..., BlockingQueued) 同步阻塞 同上 目标对象归属线程

八、信号槽的跨线程连接 #

QObject::connect 的第五个参数决定连接类型，默认是 Qt::AutoConnection。队列连接背后是一条完整的投递链：

text
emit sig(args)                       // 发射线程
  → moc 生成的信号函数
    → QMetaObject::activate()
      → 遍历连接表
        → 队列连接：new QMetaCallEvent（参数已深拷贝）
          → QCoreApplication::postEvent(receiver, event)
            → 进 receiver->thread() 的队列
              → 该线程事件循环取出
                → QObject::event() → qt_static_metacall()
                  → 槽被调用，此时已在接收者线程

看懂这条链，四个结论直接落袋：

  • 队列连接的槽和发射点彻底解耦，发射线程发完就返回。
  • 槽里拿到的是参数副本，原始对象怎么改都不影响已投递的调用。
  • 传指针等于传共享内存，指针指向的数据照样有竞争。
  • 返回值拿不到。队列连接是单向的，槽的返回值被丢掉。

只有信号、槽、Q_INVOKABLE 标记的方法能被这样调用。原因在 moc：只有它们被记进了元对象表，activate() 才有东西可查。

一个能直接跑的最小例子，验证「槽在次线程执行」：

cpp
class Producer : public QObject
{
    Q_OBJECT
public slots:
    void produce() { emit ready(7); }
signals:
    void ready(int value);
};

class Consumer : public QObject
{
    Q_OBJECT
public slots:
    void onReady(int value)
    {
        qDebug() << "consumer got" << value << "in" << QThread::currentThreadId();
    }
};

int main(int argc, char *argv[])
{
    QCoreApplication app(argc, argv);
    qDebug() << "main:" << QThread::currentThreadId();

    QThread thread;
    Consumer consumer;
    consumer.moveToThread(&thread);
    thread.start();                       // run() 里默认调 exec()，循环有了

    Producer producer;
    QObject::connect(&producer, &Producer::ready,
                     &consumer, &Consumer::onReady);   // 默认 AutoConnection

    producer.produce();                   // 主线程发射
    qDebug() << "produce returned";

    QTimer::singleShot(500, &app, &QCoreApplication::quit);
    const int ret = app.exec();
    thread.quit();
    thread.wait();                        // 先收线程，再析构 consumer
    return ret;
}

text
main: 0x1a40
produce returned
consumer got 7 in 0x1a48

注意第二行和第三行的顺序：produce() 先返回，槽后执行。这就是队列连接。把输出顺序反过来，说明连接被判定成了直连，回头查 moveToThread 有没有生效。

反方向同理：次线程里 emit，接收者留在主线程，槽就回主线程执行。谁归属哪个线程，调用就落在哪个线程，方向不影响规则。

九、QueuedConnection 与 DirectConnection #

五种连接类型，一张表理清：

连接类型 枚举值 槽的执行线程 同步性 要事件循环 参数传递
直连 Qt::DirectConnection 发射信号的线程 同步，立即执行 不要 引用
队列 Qt::QueuedConnection 接收者归属线程 异步 要 拷贝
阻塞队列 Qt::BlockingQueuedConnection 接收者归属线程 同步，发射线程被挂起 要 拷贝
自动 Qt::AutoConnection 判定后同直连或队列 视判定 视判定 视判定
唯一 Qt::UniqueConnection 与上面按位或使用 — — 防重复连接

直连。槽就是一次普通函数调用，栈帧长在发射点里面。

cpp
QObject::connect(&a, &A::sig, &b, &B::slot, Qt::DirectConnection);

同线程里用直连没问题，效率也高。跨线程用直连就是在发射线程里跑接收者的代码，接收者的数据此刻正被它自己的线程改——数据竞争，随机崩溃，最难查的那类 bug。

队列。投一个事件，发射点立刻返回。

cpp
QObject::connect(&producer, &Producer::ready,
                 &consumer, &Consumer::onReady, Qt::QueuedConnection);

队列连接保序：同一个发送者到同一个接收者的多次发射，按发射顺序执行。跨线程传状态时这条性质很有用，不用额外维护序号。

阻塞队列。发射线程挂起，直到接收者线程把槽执行完。

cpp
QObject::connect(&producer, &Producer::ready,
                 &consumer, &Consumer::onReady, Qt::BlockingQueuedConnection);

用在「投出去必须等结果」的场合，比如让次线程读一次硬件寄存器、初始化一份配置。两条红线：

  • 同线程里用阻塞队列连接一定死锁，自己等自己。Qt 会打 warning，但进程照样卡死。
  • 接收者线程如果没有事件循环，发射线程永久阻塞，整个程序挂住。

一个对照实验，三种连接各来一发：

cpp
class Sender : public QObject
{
    Q_OBJECT
signals:
    void sig();
};

class Receiver : public QObject
{
    Q_OBJECT
public slots:
    void viaDirect() { qDebug() << "direct:" << QThread::currentThreadId(); }
    void viaQueued() { qDebug() << "queued:" << QThread::currentThreadId(); }
    void viaBlocking() { qDebug() << "blocking:" << QThread::currentThreadId(); }
};

int main(int argc, char *argv[])
{
    QCoreApplication app(argc, argv);
    qDebug() << "main:" << QThread::currentThreadId();

    QThread thread;
    Receiver r;
    r.moveToThread(&thread);
    thread.start();

    Sender s;
    QObject::connect(&s, &Sender::sig, &r, &Receiver::viaDirect,
                     Qt::DirectConnection);
    QObject::connect(&s, &Sender::sig, &r, &Receiver::viaQueued,
                     Qt::QueuedConnection);
    QObject::connect(&s, &Sender::sig, &r, &Receiver::viaBlocking,
                     Qt::BlockingQueuedConnection);

    emit s.sig();        // 一次发射，三个槽

    const int ret = app.exec();
    thread.quit();
    thread.wait();       // 先停线程，再析构归它管的 r
    return ret;
}

text
main: 0x1a40
direct: 0x1a40        // 直连，就在发射线程
blocking: 0x1a48      // 阻塞队列，次线程执行完才返回
queued: 0x1a48        // 队列，异步，最后才轮到

direct 第一行，因为它同步执行；blocking 第二行，因为发射线程要等它做完；queued 最后，因为它是排进队列的，而且这里已经进了主循环。三个槽的执行顺序就是三种连接语义的活体展示。

十、AutoConnection 怎么判断 #

默认参数是 Qt::AutoConnection，connect 时判定一次，判定逻辑只有三行：

text
if (receiver->thread() == QThread::currentThread())   // 发射那一刻的线程
    → DirectConnection
else
    → QueuedConnection

比的是「接收者的归属线程」和「发射信号的线程」。发送者对象归哪个线程，完全不参与判定。

这一点 Qt 4.7.1 的文档写错了，原文说「如果发射者和接收者在同一线程，其行为与 DirectConnection 相同」，把「发送者对象」和「发射线程」混成一个东西。发送者对象归 A 线程，代码却在 B 线程里 emit 它的信号——这种写法少见，但正是最容易踩的坑。

四种组合：

发射线程 接收者归属线程 AutoConnection 判定 槽在哪跑
M M 直连 M
S M 队列 M
M S 队列 S
S S 直连 S

第一种和第四种是直连，槽就在调用栈里同步执行。跨了线程的那两种走队列。

例子一，两个对象都在主线程，信号却在次线程发：

cpp
class Thread : public QThread
{
    Q_OBJECT
signals:
    void aSignal();
protected:
    void run() override { emit aSignal(); }
};

Thread thread;      // 归主线程
Object obj;         // 归主线程
QObject::connect(&thread, SIGNAL(aSignal()), &obj, SLOT(aSlot()));
thread.start();

thread 和 obj 同在主线程，很多人据此认定是直连。可信号是在 run() 里发的，发射线程是 S，接收者归属 M，判定结果是队列。发送者对象的归属在这里毫无权重。

例子二，反过来，也是真实项目里更常见的坑：

cpp
class Thread : public QThread
{
    Q_OBJECT
public slots:
    void aSlot()
    {
        // 访问 m_buffer —— 而 run() 正在次线程里读写它
        m_buffer.append("x");
    }
protected:
    void run() override
    {
        while (m_running)
        {
            m_buffer.clear();
            QThread::msleep(10);
        }
    }
private:
    QStringList m_buffer;
    bool m_running = true;
};

Thread thread;
Object obj;
QObject::connect(&obj, SIGNAL(aSignal()), &thread, SLOT(aSlot()));
thread.start();
obj.emitSignal();       // 主线程发射

obj 在主线程 emit，thread 归属主线程，判定为直连，aSlot() 在主线程执行。看着「槽在主线程」挺安全，实际上 m_buffer 正在被次线程的 run() 反复清空——没有锁，读写撕裂，崩在随机位置。

这就是「灾难配方」那个说法的出处。修法有三种，只有第一种算正解：

做法 效果 代价
工作对象拆出来 moveToThread 槽在次线程，与 run() 无关，数据只有一个人碰 要重构控制面与执行面
显式改成 QueuedConnection 槽回主线程执行 共享数据仍在两线程，还是得加锁
直连 + QMutex 保护 能跑 锁粒度难调，容易连带阻塞
moveToThread(this) 槽进次线程 QThread 对象与它管理的线程纠缠，退出时容易崩

表里第四行是网上流传最广的那个「解决方案」，也是被 Qt 作者明确反对的做法。它能工作，因为它确实改掉了接收者的线程归属，但它同时在骂 QThread 的设计意图：QThread 对象是控制句柄，不是干活的实体。

判定链记住了，排查就简单。槽没在预期的线程执行，先打印三个值：

cpp
qDebug() << "emit from" << QThread::currentThreadId()
         << "receiver lives in" << receiver.thread()
         << "current is" << QThread::currentThread();

receiver.thread() 和第二个值比一下，答案就出来了。别猜，打印。

十一、没有事件循环会怎样 #

先说清一个前提：线程和事件循环是两件事。QThread::run() 从 Qt 4.4 起默认调用 QThread::exec()，所以不覆写 run() 的 QThread 天然带循环。你一旦覆写 run()，循环有没有就全看你写不写 exec()。

run() 的地位值得单独记住一句话：**run() 之于线程，相当于 main() 之于程序。**它是线程的入口，起点在 run() 的那条调用栈上的一切代码都在新线程里执行，函数返回，线程结束。

于是 QThread 的用法就分成两支，差别只在有没有 exec()：

用法 写法 线程里有循环吗 适合什么
无循环 子类化 QThread，run() 里放一个 while/for，用标志位退出 没有 一次性的批处理、纯计算、轮询式采集
有循环 run() 里调 QThread::exec() 有 要被队列调用、要用定时器、socket、deleteLater

第二支里有个历史包袱：Qt 4.3 及之前 run() 是纯虚函数，必须子类化才能用；Qt 4.4 起 run() 默认就是 exec()，于是不子类化 QThread 也能有循环，只要把一个 QObject 子类 moveToThread 过去。这也是后来推荐的写法。

不写 exec() 的线程照样能跑代码，只是投给它的事件没人收。它跑完 run() 就结束，队列里剩下的东西一起消失。

后果可以逐条列出来：

依赖的东西 接收者线程没有循环时的表现
队列连接 事件留在队列，槽不执行
postEvent() 事件永不派发，内存持续上涨
invokeMethod(..., Queued) 同上，调用静默丢失
BlockingQueuedConnection 发射线程永久阻塞，程序卡死
deleteLater() 对象永不删除，内存泄漏
QTimer 到点不响，QTimerEvent 投不出去
socket 异步通知 收不到 readyRead、connected
QPaintEvent 不重绘
moveToThread 过去的对象 与外界失联，只能靠直连硬闯

注意表头是「接收者线程」，这是最容易搞错的地方。**决定事情成不成的是接收者所在线程有没有循环，不是发射方。**发射方没循环、接收方有，队列连接照常工作——事件进的是接收方的队列。这也是为什么在 run() 里 emit 信号能安全地把结果送回主线程。

反过来，接收方没循环，就彻底哑火。最典型的现场：

cpp
class Worker : public QObject
{
    Q_OBJECT
public slots:
    void onStart()
    {
        qDebug() << "slot runs in" << QThread::currentThreadId();
    }
};

class BadThread : public QThread
{
protected:
    void run() override
    {
        qDebug() << "run in" << QThread::currentThreadId();
        QThread::sleep(5);        // 干完就走，没有 exec()
    }
};

// 主线程
BadThread thread;
Worker worker;
worker.moveToThread(&thread);     // worker 归次线程
thread.start();

QMetaObject::invokeMethod(&worker, "onStart", Qt::QueuedConnection);

connect 成功，invokeMethod 返回 true，槽一次都不执行。因为那个事件被塞进了次线程的队列，而次线程从头到尾没有分发器在转。

改一个字就能救活：

cpp
class BadThread : public QThread
{
protected:
    void run() override
    {
        exec();                   // 有循环了，队列开始被消费
    }
};

再补四种连带故障，都是同一个根因的不同面孔。

一是泄漏。deleteLater() 靠 QDeferredDeleteEvent 生效，没有循环就永远不删。程序退出时资源没释放，用 ASan 或 Valgrind 跑一遍能看见。

cpp
// 次线程里执行，而次线程没有事件循环
obj->deleteLater();      // 对象活到进程结束

二是死锁。阻塞队列连接的发射线程要等接收者处理完事件，接收者压根不处理。

cpp
QObject::connect(&worker, &Worker::done, this, &Controller::onDone,
                 Qt::BlockingQueuedConnection);

worker 线程没循环，主线程就卡在 emit 那一行，界面冻住，Ctrl+C 都未必管用。

三是定时器不响。QTimer::start() 只是登记，超时靠事件循环投 QTimerEvent。

cpp
QTimer timer;
timer.start(1000);       // 所在线程没有循环，一秒后什么都不会发生

四是退出顺序出错。对象要在代表线程的 QThread 销毁之前删掉，靠的是循环把 deleteLater 消化掉。循环不在，顺序就得手动保证。

到底该不该有循环，按需要列个清单：

需求 要不要 exec()
只做一次计算，发信号把结果送出去 不要，覆写 run() 直接算完返回
要被队列调用（信号投过来、invokeMethod 投过来） 要
要用 QTimer、socket 异步通知 要
要靠 deleteLater() 释放对象 要
要接收 BlockingQueuedConnection 的调用 要

判断某个线程当前有没有循环在转，打印一句就够：

cpp
qDebug() << "loop level" << QThread::currentThread()->loopLevel();

返回 0 就是没有循环。Qt 5 提供这个函数，Qt 4 时代只能靠 QAbstractEventDispatcher::instance() 是否为空来猜。

十二、模态对话框与嵌套事件循环 #

QDialog::exec() 不是把程序停住，它是又开了一层事件循环。QMenu::exec()、QEventLoop::exec() 同理。所以模态对话框弹着的时候，主循环其实还在转，只是转在里层。

text
QApplication::exec()              // 外层循环
  [...]
  QDialog::exec()                 // 内层循环开始
    → 对话框自己的事件在这层派发
    → 主窗口的事件也在这层派发，只是被模态挡住
  ← 对话框关闭，内层循环退出
[...]                             // 回到外层

这也解释了为什么模态对话框期间定时器还在走、网络还在收。循环没停，只是换了一层。

嵌套的代价全在「你以为不会发生的事发生了」。四条最容易撞。

一、deleteLater() 在嵌套循环里被执行。你以为删除要等外层循环，结果内层循环先把它消化了。

cpp
QObject *object = new QObject;
object->deleteLater();       // 排进队列

QDialog dialog;
dialog.exec();               // 内层循环把删除事件处理掉了

// 现在 object 是野指针，dialog 关得越久，这段代码越确定会炸
object->setObjectName("x");

QEventLoop 版本一模一样：

cpp
QObject *object = new QObject;
object->deleteLater();

QEventLoop loop;
QTimer::singleShot(0, &loop, &QEventLoop::quit);
loop.exec();                 // 局部循环一趟，object 已经没了

注意 processEvents() 从 Qt 4.3 之后默认不派发延迟删除事件，但局部 exec() 会。这两者的差别骗过不少人。

二、processEvents() 递归重入。为了不卡界面，在耗时循环里手动让出控制权，结果用户再点一次按钮，同一个槽叠了第二层。

cpp
void Worker::doWork()
{
    for (int i = 0; i < 100; ++i)
    {
        heavyStep(i);
        QCoreApplication::processEvents();   // 让出控制权，事件在这里被派发
    }
}

text
QApplication::exec()
  QWidget::event(QEvent*)
    Button::mousePressEvent(QMouseEvent*)
      Button::clicked()
        Worker::doWork()                     // 第一层
          QCoreApplication::processEvents()
            QWidget::event(QEvent*)          // 又派发进来一个点击
              Button::mousePressEvent(QMouseEvent*)
                Button::clicked()
                  Worker::doWork()           // 第二层，重入

栈越叠越深，i 各自独立地跑，状态互相踩。两种情况能治：

cpp
// 治法一：派发时不带用户输入，点击留在队列里等这一轮跑完
QCoreApplication::processEvents(QEventLoop::ExcludeUserInputEvents);

// 治法二：重入保护
void Worker::doWork()
{
    if (m_busy)
        return;
    QScopedValueRollback<bool> guard(m_busy, true);
    // ...
}

治法一治的是标，治法二治的是本。两者一起用最稳。

三、QDialog::exec() 返回后指针失效。对话框是栈上对象时，exec() 里被 deleteLater() 的兄弟对象已经没了；对话框是 new 出来的且设了 WA_DeleteOnClose，exec() 返回后 this 也没了。

四、内层循环退出条件写漏。QEventLoop 没有 quit() 就永远转，界面看着活着，逻辑已经卡死。给每个局部循环配一个超时兜底：

cpp
QEventLoop loop;
QTimer::singleShot(5000, &loop, &QEventLoop::quit);   // 兜底
QObject::connect(reply, &QNetworkReply::finished, &loop, &QEventLoop::quit);
loop.exec();

if (reply->isFinished())
    qDebug() << "拿到结果";
else
    qDebug() << "超时，放弃";

「同步外观、异步内核」的标准写法就是这一段。QNetworkReply 没有阻塞式 API，因为它必须靠事件循环；想同步等，就自己开一层循环等它完成。

cpp
QNetworkAccessManager nam;
QNetworkReply *reply = nam.get(QNetworkRequest(QUrl("https://example.com")));

QEventLoop loop;
QObject::connect(reply, &QNetworkReply::finished, &loop, &QEventLoop::quit);
loop.exec();

const QByteArray data = reply->readAll();
reply->deleteLater();          // 别 delete，让 Qt 在安全的时机删

Qt 4.5 之后 QDialog 多了 open()，弹窗但不进局部循环，window-modal 语义，结果通过信号回传：

cpp
QDialog dialog;
dialog.open();                 // 立刻返回，主循环继续转
QObject::connect(&dialog, &QDialog::finished,
                 this, &Controller::onDialogClosed);

三种「暂时跑一下循环」的方式摆在一起：

方式 是否新开一层循环 主要风险
processEvents() 不新开，只冲刷当前队列 重入、调用栈增长
QEventLoop::exec() 新开一层 延迟删除提前执行、退出条件写漏
QDialog::exec() 新开一层，带模态 同上，外加对象生命周期误判

嵌套循环本身不是错。错的是在嵌套期间假设外层的对象还活着、状态没变。写局部循环的时候，把它当成一次「别人随时会动我的数据」的窗口，心态就对了。

十三、常见故障与现象 #

九个现场，按「现象 → 根因 → 定位 → 修法」整理。前三条占了实际项目里的大头。

现象 根因 修法
信号发了，槽一次不执行 接收者线程没循环 / 参数类型没注册 / 对象已死 补 exec()、qRegisterMetaType()、改用 deleteLater()
槽执行了，线程不对，界面卡住 接收者归属错了（多半是 QThread 子类对象） 工作对象 moveToThread
界面间歇性卡死 槽里干了重活，阻塞了事件循环 拆块或挪到次线程
退出时崩在析构 对象比线程活得久，或线程没停就析构 quit() + wait() 后再销毁
内存缓慢上涨 postEvent 洪水 / deleteLater 没人执行 限流、确保循环在跑
偶尔崩在随机位置 跨线程直连碰共享数据，或跨线程 delete 走队列连接，删对象用 deleteLater()
阻塞队列连接卡死 同线程使用，或接收者没循环 只跨线程用，且对方有循环
局部循环之后指针失效 deleteLater() 被嵌套循环提前执行 别在内层循环期间假设对象还活着
QTimer 到点不响 所在线程没循环，或 timer 建在别的线程 在有循环的线程里建

槽不执行。三种情形，按概率排：接收者线程没有事件循环；参数类型没注册；对象在投递和派发之间被删了。检查只需要一次打印：

cpp
const bool ok = QObject::connect(&producer, &Producer::ready,
                                 &consumer, &Consumer::onReady);
qDebug() << "connected" << ok
         << "receiver lives in" << consumer.thread()
         << "loop level" << consumer.thread()->loopLevel();

ok 为 false 就是签名不匹配；receiver lives in 指向一个 loopLevel() 为 0 的线程就是没循环；日志里出现 Cannot queue arguments of type 'Job' 就是没注册元类型。

槽在错误线程。多线程代码里八成是这么来的：把槽写在 QThread 子类里，然后指望 start() 之后它就在次线程跑。前面三个实验已经证明不是这样。修法不是加锁，是把工作对象挪出去。

cpp
QThread thread;
Worker worker;                  // 独立 QObject，不继承 QThread
worker.moveToThread(&thread);
QObject::connect(&controller, &Controller::start, &worker, &Worker::doWork);
thread.start();

界面卡死。QThread::sleep()、waitFor*()、大文件解析、同步数据库查询，任何超过几十毫秒的同步动作都在吃事件循环。判断标准很土：这行代码跑完之前，窗口能不能重绘。

退出崩溃。析构顺序是重灾区。线程还在跑的时候销毁它对应的对象，或者 QThread 对象本身在错误的线程里析构，都会炸。

cpp
class Controller : public QObject
{
public:
    ~Controller() override
    {
        m_thread.quit();          // 让 exec() 返回
        m_thread.wait(3000);      // 等 run() 真正结束
    }

private:
    QThread m_thread;
};

quit() 只是给循环发退出请求，wait() 才是等线程收尾。少了 wait()，析构和 run() 并行赛跑。

内存上涨。两种来源：事件投递速度超过消费速度，队列无限膨胀；deleteLater() 排进了一个不转的队列。前者监控队列长度，后者检查循环。

随机崩溃。跨线程直连、跨线程 delete、对象归属在运行中被改——这类问题不靠猜，靠打印。三个值一摆，路径就出来了：

cpp
void Receiver::onData(const QByteArray &data)
{
    qDebug() << "slot in" << QThread::currentThreadId()
             << "owned by" << thread()
             << "data size" << data.size();
}

阻塞队列卡死。两条红线在前面写过：同线程使用必死；接收者没循环也必死。第二种更难发现，因为 connect 不报错，程序就那么静静地挂住。

野指针。deleteLater() 之后又开了一层 QDialog::exec() 或 QEventLoop::exec()，对象在内层被删，返回后接着用。

十四、易错点速查 #

十四条，扫一眼对号入座。

易错点 症状 正确做法
以为 QThread 子类的槽在次线程跑 槽卡住主线程 工作对象 moveToThread，别继承 QThread
构造函数里 moveToThread(this) 退出崩溃、无法推理 整个写法放弃
run() 里 new QObject(this) 启动警告、归属冲突 不设 parent，或改在 run() 里 new
手写 Qt::DirectConnection 图省事 跨线程数据竞争，随机崩 不写第五参数，用默认判定
覆写 run() 忘了 exec() 队列连接全部静默丢失 需要收事件就 exec()
自定义类型没 qRegisterMetaType 运行时警告，槽不执行 首次 connect 前注册一次
在发射方线程等结果 界面锁死 信号回传，或 BlockingQueuedConnection
跨线程 delete 对象 崩在析构 deleteLater()
在 QThread 构造函数里建大对象 对象留在主线程 挪进 run() 或 moveToThread
connect 后不管对象生死 对象死了信号还来 用带 context 的 connect 重载
processEvents() 满地撒 重入、栈越叠越深 ExcludeUserInputEvents 加重入保护
局部 QEventLoop 没退出条件 逻辑卡死，界面还活着 配一个超时 singleShot 兜底
假设 QObject 线程安全 数据撕裂、偶发崩 加锁，或按归属隔离访问
以为 postEvent 是同步的 顺序错乱、对象提前释放 记住它只入队，执行在对方线程

这张表里最值得盯的是第一行和第五行。前者是 QThread 误用的总根源，后者是新手最容易踩的静默失败——程序不报错、不崩溃，只是槽永远不执行，然后你怀疑人生。

把五条钉在工位上：每个线程一个队列；对象归创建它的线程；跨线程走队列连接；判定看接收者不看发送者；接收者没有循环就没有投递。剩下所有现象，都是这五条的推论。
