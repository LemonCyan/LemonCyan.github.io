本篇只谈一件事：线程之间怎么安全地交换数据。同步原语怎么选，跨线程通信走哪条路，哪些写法看着能跑、一上多核就崩。

不展开的部分：QThread 为什么设计得这么怪、事件循环跟 QObject 的线程归属怎么判定、自定义事件怎么从零写、QTimer 实际跑在哪个线程。这四块在同目录另外四篇里，本篇只在需要交代前提的地方点一句。

先记住一句话：Qt 里跨线程直接访问对象，默认就是错的。正确的路只有三条——信号槽、事件投递、以及你自己加锁保护的共享数据。

一、线程为什么需要同步 #

一个进程里的所有线程共享同一片地址空间。栈是各自的，堆、全局变量、静态变量、对象成员全是共用的。共用就意味着：A 线程正在读的那块内存，B 线程随时能改。C++ 标准没给这种并发读写定义任何顺序，编译器重排、CPU 乱序执行、缓存一致性协议，任何一环都能把结果打乱。所以问题不在于「要不要加锁」，而在于「这块数据到底被几个线程碰」。

先看清线程是怎么来的。Qt 里两条主干：QThread（底层控制，手动管生命周期，适合常驻后台任务）和 QThreadPool（线程复用，适合大量短时并行任务）。

特性 moveToThread 子类化 QThread 线程池 QThreadPool
生命周期 手动管理 手动管理 自动回收
开销 较高（每任务一线程） 较高 极低（线程复用）
解耦度 极高 低 高
适用场景 网络通信、常驻监控 底层控制、死循环 扫描任务、高并发计算

QThread 的常用控制接口：

API 作用 使用要点
start() 启动线程，触发 started() 信号 内部调用重载的 run()
run() 线程入口 子类化时重写它
exit(int) / quit() 通知事件循环退出 quit() 等价于 exit(0)
terminate() 强制杀线程 危险操作，资源不释放、锁不释放
isRunning() / isFinished() 查状态 只做判断，别当同步手段
wait(unsigned long) 阻塞等线程结束 带超时，超时返回 false
finished 信号 线程即将结束 接 deleteLater 做自动释放

子类化路线的最小例子。标志位用原子量，别用裸 bool——它是跨线程写的。

cpp
// mythread.h
class MyThread : public QThread
{
    Q_OBJECT
public:
    explicit MyThread(QObject *parent = nullptr);
    void requestStop();
protected:
    void run() override;
private:
    QAtomicInt m_stop;                  // 跨线程标志，不用裸 bool
};

// mythread.cpp
MyThread::MyThread(QObject *parent) : QThread(parent), m_stop(0) {}
void MyThread::requestStop() { m_stop.storeRelease(1); }
void MyThread::run()
{
    for (int i = 0; i < 1000; ++i) {
        if (m_stop.loadAcquire()) break;
        qDebug() << i;
        QThread::sleep(1);
    }
}

// 使用侧：启动 -> 通知停 -> 等它真的退出
MyThread th;
th.start();
QThread::sleep(10);
th.requestStop();
th.wait();                             // 不 wait 就析构，等于悬空线程

子类化有个反直觉的点：QThread 对象本身属于创建它的线程（老线程），只有 run() 函数体跑在新线程。所以构造函数里 new 的成员归老线程管，run() 里 new 的才归新线程。想在子线程里收信号槽，得在 run() 里调一次 exec() 把事件循环开起来，否则队列信号永远躺在队列里。

线程池走 QRunnable：子类实现 run()，再 QThreadPool::globalInstance()->start(new MyTask()) 提交，池子自己安排线程。

项 说明
QThreadPool::globalInstance() 进程内预定义的全局池，拿来就用
自动删除 跑完的 QRunnable 默认被池 delete，别自己再删
setMaxThreadCount() 并发上限，缺省是 CPU 核心数
setExpiryTimeout() 闲置线程回收时间，缺省 30 秒后销毁
QThread::idealThreadCount() CPU 理想并发数，maxThreadCount 的缺省依据

实战场景，批量扫网段：

cpp
class ScanIpTask : public QRunnable
{
public:
    explicit ScanIpTask(const QString &addr) : ip(addr) {}
    void run() override
    {
        int code = QProcess::execute("ping", {"-n", "1", "-w", "500", ip});
        qDebug() << ip << (code == 0 ? "存活" : "无法访问");
    }
private:
    QString ip;
};

for (int i = 1; i < 255; ++i)
    QThreadPool::globalInstance()->start(new ScanIpTask(QString("192.168.1.%1").arg(i)));

线程拉起来了，麻烦才开始。++i 在汇编层面是三条指令——读、加、写回。两个线程交错执行，各读到 5、各写回 6，加两次只涨一次。

text
线程 A                线程 B                内存里的 n
load  n  -> 5
                      load  n  -> 5
add   5+1 -> 6
                      add   5+1 -> 6
store 6  -> n
                      store 6  -> n        结果 6，不是 7

凡是「多个线程读、至少一个线程写」的共享变量，都要有人管顺序。

二、竞态条件与临界区 #

两个概念要分清。竞态条件：程序正确性取决于线程调度顺序，跑一百次对九十九次，第一百次错。临界区：一段访问共享资源的代码，同一时刻只允许一个线程进去。

看个能跑的坏例子：

cpp
static int g_counter = 0;              // 共享变量，没有保护

class Adder : public QThread
{
public:
    void run() override
    {
        for (int i = 0; i < 1000000; ++i) ++g_counter;
    }
};

Adder t1, t2;
t1.start(); t2.start();
t1.wait();  t2.wait();
qDebug() << "期望 2000000，实际" << g_counter;    // 每次都不一样

输出随机漂在 190 万到 200 万之间。它不报错、不崩溃，只是安静地少加了几千次。这类 bug 测试环境躲得过，客户现场才炸。

加锁之后：

cpp
QMutex g_mutex;

class SafeAdder : public QThread
{
public:
    void run() override
    {
        for (int i = 0; i < 1000000; ++i) {
            QMutexLocker locker(&g_mutex);
            ++g_counter;
        }
    }
};

临界区要满足三条：互斥（同一时刻只有一个线程在内）、前进（没人卡在门外永久等）、有限等待（等的时间有上界）。任何一条破了，就不是同步而是卡死。

怎么判断是不是竞态？看症状。

症状 指向
结果偶尔少一点，不报错 计数器、累加类竞态
崩在跟业务无关的一行 对象被别的线程提前析构
Debug 正常、Release 崩 编译器重排暴露了无锁读写
单核正常、多核崩 真并发，缓存一致性问题
加日志后就不复现 时序被 printf 改变了，标准的竞态特征

Linux 上编一版带 -fsanitize=thread 的二进制跑一遍，命中率比肉眼高得多。

三、QMutex：互斥锁 #

先把最关键的一件事说清。Qt 的同步原语与 C++ 标准库的是两套东西，同名不同源，不能当一种用。

QMutex 来自 Qt，std::mutex 来自 <mutex>。两者作用相同——给临界区加互斥——但接口、超时能力、可重入语义都不一样。混着用会出两种事：把 QMutex* 传给要 std::mutex& 的函数，编译不过；或者有人以为 QMutex 能自动解锁，结果裸调了 lock() 忘了 unlock()。

QMutex 的常用接口：

接口 行为
lock() 阻塞直到拿到锁
tryLock() 试一次，拿到返回 true，拿不到返回 false，不进阻塞
tryLock(int ms) 等最多 ms 毫秒
unlock() 释放，必须由加锁的线程调用
QMutex::Recursive 构造参数，让同一线程重复加锁不死锁

最朴素的用法，手工配对：

cpp
QMutex mutex;
int sharedCounter = 0;

void bump()
{
    mutex.lock();
    if (sharedCounter > 100) {
        mutex.unlock();                // 每个 return 分支都得记得解锁
        return;
    }
    ++sharedCounter;
    mutex.unlock();
}

能跑，但是个定时炸弹。多一个 return、多一个 throw、多一个 continue，就漏一次解锁。漏一次，下一个线程永远停在 lock() 上，界面直接假死。

跟标准库同名接口比一比：

维度 QMutex std::mutex
加锁 / 解锁 lock() / unlock() lock() / unlock()
尝试 tryLock()、tryLock(ms) try_lock()，无超时
可重入 构造参数 QMutex::Recursive 另一个类型 std::recursive_mutex
自动解锁 QMutexLocker std::lock_guard / std::unique_lock
超时加锁 内置 要换 std::timed_mutex

建议很直接：一个工程里选一套。既然在 Qt 里写业务，就用 Qt 这套，理由在下一章。

四、QMutexLocker：RAII 的用法 #

QMutexLocker 是 QMutex 比 std::mutex 更顺手的点——构造时加锁，析构时解锁，跟栈对象的作用域绑死。函数怎么返回都行，异常也好、提前 return 也好，退出作用域那一刻锁自动放掉。

cpp
void bump()
{
    QMutexLocker locker(&mutex);
    if (sharedCounter > 100)
        return;                        // 这里 return，锁照样释放
    ++sharedCounter;
}                                      // locker 析构，unlock 自动发生

锁的范围越小，并发度越高。需要收窄的时候把 QMutexLocker 放进一对嵌套花括号里，出块即解锁；拷贝数据只持锁拷完，解析这种慢活儿一律挪到锁外面做。

搭个自增 ID 生成器，RAII 最典型的用法，读和写都走同一把锁。

cpp
class KeyGenerator
{
public:
    int createKey()
    {
        QMutexLocker locker(&m_mutex);
        ++m_key;
        return m_key;
    }
    int value() const
    {
        QMutexLocker locker(&m_mutex); // 成员函数是 const，锁得声明 mutable
        return m_key;
    }
private:
    int m_key = 0;
    mutable QMutex m_mutex;
};

value() const 里要改锁的状态，m_mutex 必须 mutable，否则编译不过。这是新手第一个卡点。

三个 RAII 包装对照：

类 来源 加锁时机 能提前解锁 能延迟加锁
QMutexLocker Qt 构造即加锁 调 unlock() 手工放 不能
QReadLocker / QWriteLocker Qt 构造即加锁 调 unlock() 手工放 不能
std::lock_guard C++11 构造即加锁 不能 不能
std::unique_lock C++11 构造加锁 unlock() 支持 std::defer_lock

Qt 6 里 QMutexLocker 变成了模板 QMutexLocker<QMutexType>，写 QMutexLocker locker(&mutex) 依然成立，类型自动推导。同时编 Qt 5 和 Qt 6 的代码别写显式模板参数。

一个常见误区：以为 QMutexLocker 保证线程安全。它只保证这一段临界区互斥。你把不该共享的东西共享出去，加了锁照样错。

五、QReadWriteLock：读写分离 #

QMutex 的问题是太严——两个线程都只读，也排成队。读多写少的场景，这是白扔性能。QReadWriteLock 把访问分两类：多个读者同时进，写者独占。读者之间不互斥，读者与写者互斥，写者之间互斥。

cpp
class ConfigStore
{
public:
    void set(const QString &key, const QString &val)
    {
        QWriteLocker locker(&m_lock);
        m_map.insert(key, val);
    }
    QString get(const QString &key) const
    {
        QReadLocker locker(&m_lock);   // 多线程同时 get 不排队
        return m_map.value(key);
    }
private:
    QHash<QString, QString> m_map;
    mutable QReadWriteLock m_lock;
};
接口 说明
lockForRead() 拿读锁，写者持锁时阻塞
lockForWrite() 拿写锁，任何其他锁持有者都会挡住它
tryLockForRead(ms) / tryLockForWrite(ms) 带超时的版本
unlock() 两种锁共用一个解锁函数
QReadLocker / QWriteLocker 对应的 RAII 包装

跟 QMutex 的取舍：

场景 选 QMutex 选 QReadWriteLock
读写各半 合适 写者容易饥饿，变慢
读远多于写（10:1 以上） 浪费并发 收益明显
临界区极短（几条指令） 更轻 自身开销盖过收益
需要递归加锁 支持 Recursive 不支持递归写锁

最后一行要留心。QReadWriteLock 缺省不保证写优先，读者源源不断时写请求会一直排队。Qt 的 QReadWriteLock::Recursive 解决重入，不解决饥饿。

标准库对应物是 std::shared_mutex（C++17）：

维度 QReadWriteLock std::shared_mutex
读锁 lockForRead() lock_shared()
写锁 lockForWrite() lock()
RAII 读 / 写 QReadLocker / QWriteLocker std::shared_lock / std::unique_lock
可用版本 Qt 5.0 起 C++17 起

判断标准就一条：临界区里有没有写。纯读的代码段用写锁包起来，等于把 QReadWriteLock 当 QMutex 用，白搭。

六、QSemaphore：计数信号量 #

互斥锁管的是「一次一个人」，信号量管的是「一次 N 个人」。它维护一个整数计数，acquire() 尝试减一，减到负数就阻塞；release() 加一，顺手叫醒一个等待者。

接口 行为
acquire(int n = 1) 申请 n 个资源，不够就阻塞
tryAcquire(int n = 1) 不阻塞，拿不到返回 false
tryAcquire(int n, int ms) 等最多 ms 毫秒
release(int n = 1) 归还 n 个资源，可跨线程调用
available() 当前可用数量

release() 不要求由 acquire() 的那个线程调。这点跟互斥锁完全不同——锁讲究谁加谁解，信号量只是记账。

最典型的用法是环形缓冲的生产者-消费者。两个信号量分工：一个记空位，一个记数据。

cpp
const int DataSize   = 100000;
const int BufferSize = 8192;

int buffer[BufferSize];
QSemaphore freeBytes(BufferSize);      // 初始全空，8192 个空位
QSemaphore usedBytes(0);               // 初始无数据

class Producer : public QThread
{
public:
    void run() override
    {
        for (int i = 0; i < DataSize; ++i) {
            freeBytes.acquire();       // 等一个空位，没有就睡
            buffer[i % BufferSize] = i;
            usedBytes.release();       // 交出一份数据
        }
    }
};

class Consumer : public QThread
{
public:
    void run() override
    {
        for (int i = 0; i < DataSize; ++i) {
            usedBytes.acquire();       // 等一份数据
            fprintf(stderr, "%d ", buffer[i % BufferSize]);
            if (i % 16 == 0 && i != 0) fprintf(stderr, "\n");
            freeBytes.release();       // 归还一个空位
        }
        fprintf(stderr, "\n");
    }
};

int main(int argc, char *argv[])
{
    QCoreApplication app(argc, argv);
    Producer producer;
    Consumer consumer;
    producer.start();
    consumer.start();
    producer.wait();
    consumer.wait();
    return 0;
}

谁快谁慢都无所谓。生产者跑到 8192 个就卡在 freeBytes.acquire() 上睡过去，消费者读走一个，freeBytes.release() 就把它叫醒。全程没有一把大锁，缓冲区读写的区段由两个计数器的此消彼长天然隔开。

信号量还有个副作用好用的地方：控制并发度。最多同时 4 个下载任务，QSemaphore slots(4)，进任务前 slots.acquire()，出任务后 slots.release()，第 5 个自然排队。

跟标准库比：

维度 QSemaphore std::counting_semaphore
标准 Qt 5.0 起 C++20
申请 / 归还 acquire() / release(n) acquire() / release(n)
带超时 tryAcquire(n, ms) try_acquire_for()
计数上限 int 模板参数 LeastMaxValue

QSemaphore 不能替代互斥锁做「保护一段代码」。它只保证同时最多 N 个线程进入，N 大于 1 时两个线程照样能同时改同一个变量。

七、QWaitCondition：等待与唤醒 #

信号量适合计数，但它表达不了「等某个条件成立」——等队列非空、等下载完成、等状态变成 Ready。这类等待要的是条件变量。

接口 行为
wait(QMutex *m) 原子地「解锁 m 并睡眠」，被唤醒时重新加锁 m
wait(QMutex *m, unsigned long ms) 带超时，超时返回 false
wakeOne() 叫醒一个等待者
wakeAll() 叫醒全部等待者

用法有三条铁律，缺一条就出 bug。

第一，wait() 必须传一把已经加锁的 QMutex。函数内部先解锁再睡，醒来前重新加锁。传一把没锁的锁是未定义行为，传 QReadWriteLock 编译不过。

第二，条件判断必须用 while，不能用 if。wait() 返回不代表条件成立——既有虚假唤醒（操作系统层面允许），也有被 wakeAll() 叫醒后发现资源已被别人抢走的情况。醒来第一件事是重新检查条件，不成立就继续睡。

第三，改条件的人和 wake 的人要在同一把锁的保护下。

用 if 写的版本，被虚假唤醒时会直接往下读 buffer[rIndex]，而 numUsedBytes 还是 0，读到脏数据。正确写法是把判断包在循环里：

cpp
mutex.lock();
while (numUsedBytes == 0)              // if 换成 while，醒来重查
    bufferFull.wait(&mutex);
int v = buffer[rIndex];
mutex.unlock();

完整的生产者-消费者，用条件变量重写一遍：

cpp
const int DataSize   = 10000;
const int BufferSize = 8192;

int buffer[BufferSize];
QWaitCondition bufferEmpty;            // 有空格了
QWaitCondition bufferFull;             // 有数据了
QMutex mutex;
QAtomicInt numUsedBytes(0);
QAtomicInt producerDone(0);
int rIndex = 0;

class Producer : public QThread
{
public:
    void run() override
    {
        for (int i = 0; i < DataSize; ++i) {
            mutex.lock();
            while (numUsedBytes.loadAcquire() == BufferSize)
                bufferEmpty.wait(&mutex);          // 满了就睡，wait 内部先解锁
            buffer[i % BufferSize] = numUsedBytes.loadAcquire();
            numUsedBytes.fetchAndAddOrdered(1);
            bufferFull.wakeAll();
            mutex.unlock();
        }
        producerDone.storeRelease(1);
        mutex.lock();
        bufferFull.wakeAll();                      // 叫醒还在等的消费者去收尾
        mutex.unlock();
    }
};

class Consumer : public QThread
{
public:
    void run() override
    {
        for (;;) {
            mutex.lock();
            while (numUsedBytes.loadAcquire() == 0 && !producerDone.loadAcquire())
                bufferFull.wait(&mutex);           // 空了就睡
            if (numUsedBytes.loadAcquire() == 0 && producerDone.loadAcquire()) {
                mutex.unlock();
                break;                             // 没数据且上游结束，退出
            }
            printf("%lu::[%d]=%d\n",
                   static_cast<unsigned long>(QThread::currentThreadId()),
                   rIndex, buffer[rIndex]);
            rIndex = (rIndex + 1) % BufferSize;
            numUsedBytes.fetchAndAddOrdered(-1);
            bufferEmpty.wakeAll();
            mutex.unlock();
        }
    }
};

int main(int argc, char *argv[])
{
    QCoreApplication app(argc, argv);
    for (int i = 0; i < BufferSize; ++i) buffer[i] = -1;

    Producer producer;
    Consumer consumerA, consumerB;
    producer.start();
    consumerA.start();
    consumerB.start();
    producer.wait();
    consumerA.wait();
    consumerB.wait();
    return 0;
}

把消费者循环次数写死成 DataSize 是最常见的写法，可两个消费者各跑 DataSize 次，总数超过生产者产出，晚到的那个永远卡在 wait() 上；改成 forever 无限循环，生产者停了它又退不出去。上面那版加了 producerDone 标志，就是把这个收尾补上。

wakeOne() 和 wakeAll() 怎么选：只有一个等待者、或者等待者之间互斥时用 wakeOne()，避开惊群；多个等待者都会因同一个条件被满足时用 wakeAll()。双消费者抢同一份数据，必须让两个都醒来重新竞争。

维度 QWaitCondition std::condition_variable
等待 wait(&mutex) wait(ulock)
谓词版 自己写 while wait(lock, pred) 内置循环
唤醒一个 / 全部 wakeOne() / wakeAll() notify_one() / notify_all()
配套锁 QMutex std::unique_lock<std::mutex>
超时 wait(&mutex, ms) wait_for() / wait_until()

标准库的谓词版等价于你手写的 while 循环，编译器帮你写好了。用 Qt 就得自己敲。

八、四种同步原语的对照 #

四把工具放一张表里看。

原语 语义 谁解锁 阻塞条件 典型场景 标准库对应
QMutex 互斥，一次一个 加锁者 锁被占 保护任意共享变量 std::mutex
QReadWriteLock 读共享，写独占 加锁者 有写者或有读者 读多写少的配置、缓存 std::shared_mutex

各自的代价与边界：

选型按这个顺序问自己：

text
这段数据会被多线程同时写吗？
├─ 不会，只有读 ──────────────> 不用锁，但要用 QAtomicInt 保证可见性
└─ 会

   ├─ 只是计数 / 限流 ────────> QSemaphore

最后重申那个核心判断：Qt 这套原语和 <mutex>、<atomic>、<condition_variable> 那套是并列的两套实现，作用相同、接口不同。QMutexLocker 是 Qt 这边比 std::lock_guard 更早、用起来也更顺的东西——Qt 4 就有它，而 RAII 包装进标准是 C++11 的事。一个工程挑一套用到底，混着写只会让后来的人翻两份文档。

九、跨线程通信的几种方式 #

锁解决的是「共享内存怎么访问」。但很多时候你要的根本不是共享内存，而是「把一件事从 A 线程交给 B 线程做」。这是通信问题，不是同步问题。Qt 里能走的路只有四条。

方式 要不要自己加锁 前提 用途
直接调对方方法 要，而且远不够 无 应该禁止
信号槽（队列连接） 不要 接收者线程有事件循环 默认选择
事件投递 postEvent 不要 接收者线程有事件循环 无信号可发、要自定义事件
共享数据 + 同步原语 要 无 高频大数据、环形缓冲

先说为什么不能直接调。worker->doWork() 在主线程执行，函数体也在主线程执行。所谓「对象在子线程」，指的是它的事件循环在子线程、它的槽由子线程的循环派发。直接调方法就绕过了整个派发机制，成员变量同时被子线程改着而没有锁，碰上 socket、定时器、图形上下文这类只属于子线程的资源，行为未定义。Qt 会在部分地方拦一下并打印警告，比如 QObject::startTimer: Timers cannot be started from another thread。看到这类警告，说明你已经越界了。

再看事件循环这个前提。队列连接、postEvent 都要求接收者线程在跑事件循环。子类化 QThread 且 run() 里没有 exec() 的，收不到队列信号——事件进了队列，没人取。这个坑比忘记解锁更隐蔽，因为它不崩，只是槽函数不执行。

对象归哪个线程只有一条规则：在哪个线程创建就属于哪个线程，除非有人对它调了 moveToThread()。线程归属决定它的槽在哪执行、定时器在哪触发。这条的细节在「事件循环与 QObject 的线程归属」那篇，这里当已知条件用。

十、信号槽方式 #

信号槽是 Qt 给出的推荐答案。跨线程的信号槽默认就是队列连接——发送方 emit 完立刻返回，参数被拷贝一份塞进接收者线程的事件队列，接收者下次循环时取出执行。

类型 行为 执行线程
Qt::AutoConnection 比较收发双方线程，自动选 Direct 或 Queued 由判定决定
Qt::DirectConnection 立即调用，等同函数调用 发送者线程
Qt::QueuedConnection 入队，异步执行 接收者线程
Qt::BlockingQueuedConnection 入队并阻塞等执行完 接收者线程
Qt::UniqueConnection 与上面按位或，防重复连接 同基类型

AutoConnection 的判定只有一句：发送时比较 QThread::currentThread() 和接收者的 thread()，相同走 Direct，不同走 Queued。

发送者线程 接收者所属线程 Auto 解析结果
主线程 主线程 DirectConnection
子线程 主线程 QueuedConnection
主线程 子线程 QueuedConnection

队列连接对参数有要求：类型必须能拷贝，还要被元对象系统认识，否则运行时报 Cannot queue arguments of type 'XXX'。

cpp
struct FrameInfo { int index; QByteArray payload; };
Q_DECLARE_METATYPE(FrameInfo)                  // 头文件里，类外

qRegisterMetaType<FrameInfo>("FrameInfo");     // 初始化时注册一次

Q_DECLARE_METATYPE 让类型能装进 QVariant，qRegisterMetaType 让它在运行时按名字被找到。两个都要写，少一个都会在队列连接时失败。基础类型和 QString、QByteArray、QImage 已经注册过，不用管。

跨线程发信号的完整骨架：

cpp
class Worker : public QObject
{
    Q_OBJECT
public slots:
    void doWork()
    {
        for (int i = 0; i < 100; ++i) {
            emit progress(i);              // 队列连接，安全
            QThread::msleep(10);
        }
        emit finished(100);
    }
signals:
    void progress(int percent);
    void finished(int total);
};

Worker *worker = new Worker;
QThread *thread = new QThread(this);
worker->moveToThread(thread);
connect(thread, &QThread::finished, worker, &QObject::deleteLater);
connect(thread, &QThread::finished, thread, &QObject::deleteLater);
connect(this, &Controller::startWork, worker, &Worker::doWork);   // 排进子线程队列
connect(worker, &Worker::progress, this, &Controller::onProgress); // 回到主线程
thread->start();
emit startWork();

有个细节值得记住：startWork 是在主线程 emit 的，接收者是子线程的 worker，走队列；doWork() 真正执行时 QThread::currentThread() 是子线程。业务代码里不要假设「我被调用了，我就还在主线程」。

BlockingQueuedConnection 单独说一句：它阻塞发送者直到槽执行完。用在同一线程内会立刻死锁，Qt 会检测并报错；跨线程用安全，但等于把异步退化成同步，还多一次上下文切换，只在必须拿到返回值的少数场景用。

界面更新是信号槽的经典战场。Qt 的 GUI 类不是线程安全的，所有 QWidget 操作必须在主线程做。子线程算完直接调 label->setText() 是错的，正确做法是发信号回主线程，第十三章有能跑的例子。

十一、事件投递方式 #

信号槽方便，但不是所有东西都能塞进信号。类型没注册又不想注册、要走事件过滤器、代码里压根没有 QObject，这些场合用事件投递。

接口 行为 同步性
QCoreApplication::postEvent(receiver, ev) 投进 receiver 所属线程的事件队列 异步，立即返回
QCoreApplication::sendEvent(receiver, ev) 直接派发 同步，在当前线程执行
QCoreApplication::processEvents() 处理手头待处理的事件 手动泵消息

postEvent 有三条硬规矩。事件对象必须 new 在堆上，投递后所有权交给 Qt，派发完由事件循环 delete，你别自己删。同一个事件对象只能投一次，投两次就是 double free。receiver 必须活着，它先析构的话队列里的事件会被丢掉。

自定义事件从 QEvent::User 起步，多个自定类型往后排 User + 1、User + 2：

cpp
class DataEvent : public QEvent
{
public:
    explicit DataEvent(const QByteArray &d) : QEvent(QEvent::User), data(d) {}
    QByteArray data;
};

QCoreApplication::postEvent(receiver, new DataEvent(payload));   // 任何线程都能调

bool Widget::event(QEvent *e)
{
    if (e->type() == QEvent::User) {
        auto *de = static_cast<DataEvent *>(e);
        handle(de->data);
        return true;
    }
    return QWidget::event(e);
}

事件投递跟条件变量配合，就是前面提到的高频采集方案：工作线程采一块数据，用 postEvent 把「有新数据」这个通知甩给界面线程，界面线程在自己的循环里取走。两边各跑各的节奏，界面不卡，采集不丢，还省掉信号槽那一层元对象查找，每秒上千次的场景更划算。

十二、共享内存方式 #

先划清一条界线：QSharedMemory 是进程间共享内存，不是线程间。线程本来就共享同一个地址空间，用不着它。拿它做线程通信是概念错位，凭空多一层系统调用。

线程之间的「共享内存」就是普通对象，两种用法。第一种，共享只读快照：数据生产完就定型，用 QSharedPointer<const T> 传出去，接收方只读，不需要锁，因为没人写。

cpp
typedef QSharedPointer<const QByteArray> FramePtr;

FramePtr frame(new QByteArray(capture()));     // 生产者线程
emit frameReady(frame);                        // 队列连接，参数可拷贝

void onFrameReady(FramePtr frame)              // 消费者槽，主线程
{
    render(*frame);                            // 只读，无需加锁
}

QSharedPointer 的引用计数是原子的，跨线程拷贝这个指针本身安全。

第二种，共享可变缓冲加锁。高频数据（音频采样、视频帧）不适合走信号槽，每条都入队会让事件队列堆成一坨。这时用环形缓冲配信号量或条件变量，第六、七章那两个例子就是这个模式的原型。

方式 拷贝次数 延迟 要不要锁 适合的数据
信号槽传值 1~2 次 中 不要 控制消息、状态、小数据
信号槽传 QSharedPointer 1 次指针 中 不要 中大块只读数据
环形缓冲 + 信号量 0 次 低 由原语保证 音频、视频、高频采样

Qt 容器的隐式共享要单独提一句：QString、QByteArray、QList 是写时复制，引用计数原子，但对象本身不是线程安全的。两个线程同时改同一个 QString 实例，照样崩。只读共享安全，写就得加锁或者各持一份。

十三、主线程与子线程之间的数据传递 #

把前面几章拼起来做个能跑的东西：主线程上有 start / stop / reset 三个按钮，子线程每秒往主线程发一个数字，主线程把它填到 QLabel 上。子线程这一侧，信号负责往上走，槽负责接命令。

cpp
class Thread : public QThread
{
    Q_OBJECT
public:
    explicit Thread(QObject *parent = nullptr) : QThread(parent) {}
signals:
    void updateSignal(int num);        // 子线程 -> 主线程
public slots:
    void resetSlot();                  // 主线程 -> 子线程
protected:
    void run() override;
private:
    QAtomicInt m_number{0};
    QAtomicInt m_stop{0};
};

void Thread::run()
{
    while (!m_stop.loadAcquire()) {
        emit updateSignal(m_number.loadAcquire());   // 入队，不是立即执行
        m_number.fetchAndAddOrdered(1);
        sleep(1);                                     // 一秒一次
    }
}

void Thread::resetSlot()
{
    m_number.storeRelease(0);
    emit updateSignal(0);
}

主线程这一侧，构造、连线、四个槽：

cpp
Widget::Widget(QWidget *parent) : QWidget(parent)
{
    label = new QLabel("empty", this);
    startButton = new QPushButton("start", this);
    stopButton  = new QPushButton("stop", this);
    resetButton = new QPushButton("reset", this);
    auto *layout = new QVBoxLayout(this);
    layout->addWidget(label);
    layout->addWidget(startButton);
    layout->addWidget(stopButton);
    layout->addWidget(resetButton);

    myThread = new Thread(this);
    connect(startButton, &QPushButton::clicked, this, &Widget::onStart);
    connect(stopButton,  &QPushButton::clicked, this, &Widget::onStop);
    connect(resetButton, &QPushButton::clicked, this, &Widget::onClear);
    connect(myThread, &Thread::updateSignal, this, &Widget::onUpdate);
    connect(this, &Widget::resetSignal, myThread, &Thread::resetSlot);

    setWindowTitle("Thread Test");
    resize(200, 200);
    myThread->start();
}

void Widget::onUpdate(int num) { label->setText(QString::number(num)); }  // 主线程，安全
void Widget::onStart()         { myThread->start(); }
void Widget::onClear()         { emit resetSignal(); }

void Widget::onStop()
{
    myThread->requestInterruption();   // 别用 terminate()
    myThread->wait(2000);
}

updateSignal 由子线程 emit，接收者是主线程的 Widget，AutoConnection 判定为队列连接，onUpdate 就在主线程执行。这条链是整个例子的骨架。

这个例子有两处最容易写错。一是 onStop 用 terminate()：强杀线程时 m_number 正在被改，锁也没机会释放，跑久了必出问题。用 requestInterruption() 或原子标志让 run() 自己退，再 wait() 收尸。二是 connect(this, &Widget::resetSignal, myThread, &Thread::resetSlot) 这条连接：它跨线程、走队列，resetSlot 要由子线程的事件循环派发，而 run() 里是纯 while 循环、没有 exec()，事件进了队列没人取，reset 按钮点了没反应。

修法有两条。把 reset 做成原子标志，类里加一个 QAtomicInt m_resetRequested{0};，run() 循环里检查并清零，最快：

cpp
void Thread::requestReset() { m_resetRequested.storeRelease(1); }

void Thread::run()
{
    while (!m_stop.loadAcquire()) {
        if (m_resetRequested.testAndSetOrdered(1, 0)) {
            m_number.storeRelease(0);
            emit updateSignal(0);
        }
        emit updateSignal(m_number.loadAcquire());
        m_number.fetchAndAddOrdered(1);
        sleep(1);
    }
}

另一条是改成 moveToThread，让对象活在子线程的事件循环里，槽自然能被派发。这是 Qt 的设计意图，具体写法看同目录「QThread 的正确用法」那篇。

两个方向的方法对照：

方向 手段 前提
子线程 → 主线程 信号槽（队列）、postEvent 主线程有事件循环，天然满足
子线程 → 主线程 共享数据 + 锁 无
主线程 → 子线程 信号槽（队列） 子线程有事件循环
主线程 → 子线程 原子标志 / 条件变量 无，但子线程要主动查
主线程 → 子线程 BlockingQueuedConnection 子线程有事件循环，且不能同线程

只有「子线程有事件循环」这一栏会咬人。run() 里没有 exec()，主线程发过去的队列信号就永远停在队列里。

十四、死锁的产生与规避 #

死锁是四个条件同时成立才发生的。

条件 含义 在我们的代码里长什么样
互斥 资源一次只能一个线程持有 两个 QMutex 各自独占
持有并等待 拿着一个，还去要另一个 锁 A 没放就 lock() 锁 B
不可剥夺 别人不能强抢 QMutex 没有抢占接口
循环等待 等待关系成环 A 等 B，B 等 A

破坏任意一条就破局，实践里最常破的是第四条。典型的反序加锁：

cpp
// 线程 1
{ QMutexLocker l1(&mutexA); QMutexLocker l2(&mutexB); transfer(); }  // 持 A 等 B

// 线程 2
{ QMutexLocker l1(&mutexB); QMutexLocker l2(&mutexA); transfer(); }  // 持 B 等 A

两边各持一把、各等一把，永远卡住，CPU 占用还是 0%，看着像卡死。

规避手段按优先级排：

手段 做法 说明
固定加锁顺序 全局约定「先 A 后 B」，所有代码遵守 最省事，靠规范兜住
一次只持一把锁 缩小临界区，锁内不做跨模块调用 从根上避免嵌套
加超时 tryLock(ms) 失败就回退重试 兜底，不当主策略
锁内不发信号 emit 前先解锁 槽会同步执行并回头拿锁
别拿递归锁代替拆分 同线程重入不再等自己 治标，掩盖结构问题

还有一类不是锁引起的假死：BlockingQueuedConnection 发到自己的线程、wait() 等一个已结束但没回收的线程、事件循环里跑长任务把队列饿死。表现出来都是「界面不动了」，原因完全不同。排查时先分清是抢锁还是等事件。

十五、易错点速查 #

易错点 后果 正确做法
跨线程直接调对方方法 数据竞争、偶发崩溃 走队列信号槽或 postEvent
子线程里动 QWidget 随机崩溃、绘制错乱 发信号回主线程再改
lock() 后提前 return 锁永不释放，线程卡死 QMutexLocker
if 判断后 wait() 虚假唤醒读到脏数据 用 while 重查条件
wait() 传没加锁的 mutex 未定义行为 先 lock() 再 wait()
terminate() 停线程 资源泄漏、锁残留 原子标志 + wait()
子类化 QThread 在构造函数里 new 成员 成员归属老线程 在 run() 里创建，或 moveToThread
run() 里没 exec() 还想收队列信号 槽不执行，静默失败 加 exec()，或改用原子标志
postEvent 投栈上对象 崩溃 new 出来，交给 Qt 删
同一事件对象投两次 double free 每次投新的
队列连接传自定义类型 运行时报无法排队 Q_DECLARE_METATYPE + qRegisterMetaType
QSemaphore 当互斥锁用 并发数大于 1，照样竞争 保护代码段用 QMutex
两个锁反序加锁 死锁 全局固定顺序
deleteLater 后再访问对象 悬空指针 用 QPointer 观察
单例懒初始化裸指针 两个线程各建一份 静态局部变量或 QMutex 保护
拿 QSharedMemory 做线程通信 概念错位，多一层系统调用 线程间直接共享对象加锁

收尾给一份自检清单，写新线程代码前过一遍：

text
1. 这段数据有几个线程写？>1 就必须有锁或原子量。
2. 锁的持有范围是不是最小？锁内有没有 emit / 回调 / 阻塞 IO？
3. 有没有两个锁反序的地方？全工程加锁顺序是否统一？
4. 跨线程的调用走信号槽还是直接调？接收者线程有事件循环吗？
5. 界面控件只在主线程碰了吗？
6. 线程退出靠标志还是 terminate？退出前 wait() 了吗？
7. 队列连接的参数类型注册了吗？对象析构时队列里还有事件吗？

锁不是为了让代码看起来安全，是为了让「谁先谁后」这件事有确定答案。想不清顺序的地方，加锁也只是把崩溃换成卡死。
