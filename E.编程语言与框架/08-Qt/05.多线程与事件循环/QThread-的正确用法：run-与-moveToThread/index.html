这篇只谈一件事：在 Qt 里跑后台代码，是继承 QThread 重写 run()，还是拿一个普通 QObject 用 moveToThread() 搬进线程。

讲什么：两种用法的完整可编译代码、run() 与槽函数各自落在哪个线程、moveToThread() 的调用顺序、quit() / wait() 的配合、常见误用清单。

不讲什么：QMutex、QWaitCondition、读写锁这些同步原语的细节；跨线程自定义事件的投递流程；QTimer 在各线程里的行为。这三块在同目录另外四篇里。先把这篇的线程归属规则吃透，那几篇读起来会轻很多。

读者假设：你写过 connect()，知道信号槽是什么，被 QObject::startTimer: Timers can only be used with threads started with QThread 这类警告烦过，想知道到底谁在哪个线程。

一、Qt 里为什么需要线程 #

GUI 线程不能被堵。这是 Qt 多线程的第一前提。

主线程负责事件循环：收鼠标键盘、派发重绘、跑动画、响应窗口管理器。它一旦卡住，窗口就不刷新，用户点按钮没反应，操作系统就会给你盖一层「未响应」的灰膜。所以凡是会等很久的活，都得挪出去。

三类活最典型：

  • 阻塞式 I/O：同步读文件、QTcpSocket::waitForReadyRead() 这类同步等待、串口轮询。
  • 重计算：图像处理、解压、加密、语法分析、批量生成缩略图。
  • 常驻服务：一直活着的对象，随时接收指令干活，比如硬件采集、日志落盘、协议解析。

第一种和第三种占用时间不可预测，第二种纯粹是想吃满多核。三者处理方式不同，这也是后面「怎么选」那一章的依据。

动手起线程之前，先看看有没有更便宜的办法。Qt 官方文档列了几种替代方案：

替代技术 适用场景 代价
QEventLoop::processEvents() 长计算里插空处理事件，防界面假死 调用频率不好拿捏，太密浪费、太疏还是卡，可伸缩性差
QTimer 后台活能拆成周期性触发的槽 只适合非阻塞、可切片的任务
QSocketNotifier / QNetworkAccessManager / QIODevice::readyRead() 慢速网络、设备 I/O 的等待 阻塞读要改写成事件驱动，代码结构得动

第三种其实是被低估的选项。一个线程在慢速socket上做阻塞读，不如把读操作挂到事件循环上。只要响应部分能快速跑完，事件驱动比同步等待更不容易出错，也更省电，很多场合还更快。

真要用线程，先摆正心态：启动线程是一行代码的事，保证共享数据一致才是难点。线程 bug 的恶心之处在于偶发——跑一万次没事，换个 CPU、换个核数、换个负载就崩。写测试代码不能证明线程是对的，只能在 Linux 上靠 Valgrind 和 Helgrind 帮你抓一部分。

Qt 的线程方案按生命周期分成这么几档：

生命周期 开发任务 方案
一次调用 另一个线程里跑个函数，跑完就退出 QtConcurrent::run()；或派生 QRunnable 交给 QThreadPool::globalInstance()->start()；或继承 QThread 重写 run() 后 start()
一次调用，处理容器全部元素 用满所有核，典型是批量生成缩略图 QtConcurrent::map() / filter() / reduce()
一次调用，耗时操作 + 过程状态回报 搬到工作线程，边跑边发信号 继承 QThread 重写 run()，在 run() 里发信号，用队列连接接回 GUI
常驻，双向通信 对象活在线程里，按需执行不同任务 QObject 子类 + moveToThread() 搬到有事件循环的线程，队列连接通信
常驻，轮询端口 重复任务 + 与 GUI 通信 同上，工作线程内用定时器轮询；先考虑用 QSocketNotifier 干掉轮询

这张表里后两行就是本篇的主题，前几行属于「一次性任务」，QtConcurrent 更省事。真到需要通信、需要状态、需要常驻，才会撞上 QThread 的用法之争。

Qt 多线程的推荐模型是消息传递，不是共享内存加锁。工作线程算完，发个信号，参数打包带上；主线程在槽里更新界面。两边不碰同一块数据，就不需要锁，也就没有死锁。这个模型能成立，靠的是 Qt 事件循环和队列连接。理解它的前提，是先理解 QThread 到底是个什么东西。

二、QThread 是什么：它不是线程，是线程控制器 #

新手最容易错的一步：把 QThread 对象当成线程本身。

它不是。QThread 是个 QObject，是 C++ 对象，有线程归属（thread affinity），归属于创建它的那个线程。它同时还是一个句柄，内部持有平台原生线程的 ID 和状态，负责 start()、quit()、wait()、isRunning() 这些动作。

所以一个 QThread 实例身上挂着两个线程：

概念 指什么 由谁决定
QThread 对象所依附的线程 执行 QThread t; 或 new QThread 语句的那个线程，对象的事件、槽都在这跑 创建位置
QThread 所管理的线程 start() 之后真正新建的原生线程，入口是 run() start() 调用

主线程里写 QThread t;，t 就依附于主线程，t 的槽函数在主线程执行；而 t.start() 拉起来的那个线程，只负责跑 t.run()。

一句话记住：QThread 对象属于创建它的线程，只有 run() 里的代码跑在新线程。 后面所有的混乱，包括「槽函数怎么跑到主线程去了」「定时器怎么报线程错误」，根都在这一句。

看个最小例子，把两个线程 ID 打出来：

cpp
#include <QCoreApplication>
#include <QThread>
#include <QDebug>

class Thread : public QThread
{
protected:
    void run() override
    {
        qDebug() << "worker thread:" << QThread::currentThreadId();
    }
};

int main(int argc, char *argv[])
{
    QCoreApplication a(argc, argv);
    qDebug() << "main thread:  " << QThread::currentThreadId();

    Thread t;
    QObject::connect(&t, &QThread::finished, &a, &QCoreApplication::quit);
    t.start();

    return a.exec();
}

输出大致是：

text
main thread:   0x15a8
worker thread: 0x128c

两个 ID 不同，说明 run() 确实在另一个线程。注意 main 里那行 qDebug() 和 t.start() 都在主线程，t 的构造也在主线程。

这里有段文档原文值得抄下来，它是后面所有判断的公理：

text
The run() implementation is for a thread what the main() entry point is for the application.
All code executed in a call stack that starts in the run() function is executed by the new thread,
and the thread finishes when the function returns.

run() 对线程，相当于 main() 对进程。以 run() 为起点的整条调用栈，全部在新线程里跑；run() 返回，线程就结束。

反过来说也同样硬：没有从 run() 出发的代码，就不在新线程里。 构造函数不在，槽函数不在，stop() 这样的普通成员函数也不在。

还有一条版本相关的历史要交代。Qt 4.3 及更早，run() 是纯虚的，必须子类化才能用。从 Qt 4.4 起，QThread::run() 的默认实现就是调用 exec()：

cpp
// qthread.cpp 里默认的 run()
void QThread::run()
{
    (void) exec();
}

这意味着线程一 start() 就自动进入事件循环，直到 quit()、exit() 或 terminate() 才退出。也意味着你不再必须子类化 QThread——只要有个 QObject 被搬进这个线程，它的槽就能靠这个事件循环被调用。

这就是第二种用法成立的根。它不依赖别的魔法，只依赖「run() 默认调了 exec()」这一个事实。

三、两种用法的由来 #

QThread 的用法之争不是网友瞎吵，它是一段真实的 API 演化史。

最早只有一种推荐写法：继承 QThread，重写 run()。原因很直白，run() 是线程入口，把活写进入口最符合直觉。至今 Qt 文档里仍然保留这种写法，也仍然有一堆合理场景。

问题出在「工作线程里要用槽和事件循环」的时候。2010 年，Qt 核心开发者 Bradley T. Hughes 写了一篇著名的 You're doing it wrong，主张别子类化，改用 worker object 加 moveToThread()。文章语气很冲，很多人第一反应是小题大做。

随后另一位核心开发者 Olivier Goffart 写了 QThread you were not doing so wrong，给子类化的用户说了句公道话：子类化本身没错，错的是在子类里塞槽函数和事件循环。最后官方文档把两种用法都收了进去。

所以结论不是「一种对一种错」，而是：

  • 子类化 QThread 没错，但只在 run() 里干活时才对。
  • 需要事件循环、需要槽、需要双向通信时，worker object + moveToThread() 更省心。

真正被两边一致反对的只有一种写法：在 QThread 子类的构造函数里写 moveToThread(this)。这点后面单独一章拆。

下面按时间顺序把用法演进摆一遍：先看子类化怎么写、坑在哪，再看 moveToThread() 怎么绕过去。每一段代码都能单独编译跑。

四、用法一：继承 QThread 重写 run #

最直白的写法：派生一个类，覆盖 run()，把耗时活写进去。

cpp
#include <QCoreApplication>
#include <QThread>
#include <QDebug>

class Thread : public QThread
{
    Q_OBJECT
protected:
    void run() override
    {
        qDebug() << "From worker thread:" << QThread::currentThreadId();
        for (int i = 0; i < 3; ++i) {
            msleep(100);
            emit progress(i);
        }
    }
signals:
    void progress(int i);
};

int main(int argc, char *argv[])
{
    QCoreApplication a(argc, argv);
    qDebug() << "From main thread:  " << QThread::currentThreadId();

    Thread t;
    QObject::connect(&t, &Thread::progress, &a, [](int i) {
        qDebug() << "progress" << i << "arrived in" << QThread::currentThreadId();
    });
    QObject::connect(&t, &QThread::finished, &a, &QCoreApplication::quit);

    t.start();
    return a.exec();
}

#include "main.moc"

输出：

text
From main thread:   0x13a8
From worker thread: 0xab8
progress 0 arrived in 0x13a8
progress 1 arrived in 0x13a8
progress 2 arrived in 0x13a8

progress 的槽跑在主线程，和发起信号的工作线程不是同一个。原因不在 connect 写错，而在接收者——这里把 &a 当上下文对象，a 依附主线程，队列连接把调用投递回主线程。上下文对象换成 &t，落点也是主线程；干脆不传上下文，连接退化成直连，槽就在工作线程里跑。这条规则第九章展开。

run() 里能直接调 msleep()、usleep()、sleep()，因为这几个是静态函数，作用对象是「当前线程」，此刻当前线程就是新线程。在 run() 之外调它们，睡的是调用者所在的线程，那多半不是你想要的结果。

上面这种写法只能跑完就走。要能中途停，就得加个标志位。经典写法：

cpp
#include <QCoreApplication>
#include <QtWidgets>
#include <QMutex>
#include <QMutexLocker>

class Thread : public QThread
{
    Q_OBJECT
public:
    Thread() : m_stop(false) {}

public slots:
    void stop()
    {
        qDebug() << "Thread::stop called from:" << QThread::currentThreadId();
        QMutexLocker locker(&m_mutex);
        m_stop = true;
    }

protected:
    void run() override
    {
        qDebug() << "From worker thread:" << QThread::currentThreadId();
        while (true) {
            {
                QMutexLocker locker(&m_mutex);
                if (m_stop)
                    break;
            }
            msleep(10);
        }
    }

private:
    QMutex m_mutex;
    bool m_stop;
};

int main(int argc, char *argv[])
{
    QApplication a(argc, argv);
    qDebug() << "From main thread:" << QThread::currentThreadId();

    QPushButton btn(QStringLiteral("Stop Thread"));
    Thread t;

    QObject::connect(&btn, &QPushButton::clicked, &t, &Thread::stop);
    QObject::connect(&t, &QThread::finished, &a, &QApplication::quit);

    t.start();
    btn.show();

    int ret = a.exec();
    t.stop();       // 兜底：用户直接关窗口、没点按钮的情况
    t.wait();
    return ret;
}

#include "main.moc"

输出：

text
From main thread:   0x13a8
From worker thread: 0xab8
Thread::stop called from: 0x13a8

第三行是重点。按钮点击触发的 stop() 跑在主线程，0x13a8 就是主线程 ID。m_stop 被两个线程同时访问，所以必须上锁——不是因为 stop() 内部多线程，而是因为它和 run() 的读取处在不同线程。

再补一个 GUI 里最典型的用法：工作线程算数，边算边发信号，界面跟着更新。

cpp
// mythread.h
#ifndef MYTHREAD_H
#define MYTHREAD_H

#include <QThread>

class MyThread : public QThread
{
    Q_OBJECT
public:
    explicit MyThread(QObject *parent = nullptr);
    bool Stop;

signals:
    void NumberChanged(int value);

protected:
    void run() override;
};

#endif // MYTHREAD_H

cpp
// mythread.cpp
#include "mythread.h"
#include <QMutex>
#include <QDebug>

MyThread::MyThread(QObject *parent)
    : QThread(parent), Stop(false)
{
}

void MyThread::run()
{
    for (int i = 0; i != 10000; ++i) {
        {
            QMutex mutex;
            mutex.lock();
            if (Stop) {
                mutex.unlock();
                break;
            }
            mutex.unlock();
        }
        emit NumberChanged(i);
        msleep(100);
    }
}

cpp
// dialog.cpp 片段
Dialog::Dialog(QWidget *parent)
    : QDialog(parent), ui(new Ui::Dialog)
{
    ui->setupUi(this);
    thread = new MyThread(this);
    connect(thread, &MyThread::NumberChanged, this, &Dialog::onNumberChanged);
}

void Dialog::onNumberChanged(int number)
{
    ui->label->setText(QString::number(number));
}

Dialog::~Dialog()
{
    thread->Stop = true;      // 先让 run() 的循环退出
    thread->wait();           // 再等线程结束，之后才轮到子对象析构
    delete ui;
}

void Dialog::on_pushButton_clicked()      { thread->start(); }
void Dialog::on_pushButton_2_clicked()    { thread->Stop = true; }

这段代码能跑，但 thread->Stop = true 就是上面说的跨线程裸访问，只是 bool 赋值在多数平台上是原子的，看起来没炸。真要严谨，换成 QAtomicInt 或者走 stop() 槽加锁。

run() 里那个局部 QMutex 是原教程的写法，作用域只在花括号内，拦不住跨线程访问同一个成员——它自己是个临时对象，两个线程各拿各的。真要用锁，得把 QMutex 和 Stop 都做成成员，读写两端都走 QMutexLocker。锁要对同一把才有意义，这条同目录讲线程同步的那篇写得细。

工程配置这一关别漏。Q_OBJECT 宏要求 moc 参与构建，否则编译报 undefined reference to vtable：

text
cmake_minimum_required(VERSION 3.16)
project(qthread_demo LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_AUTOMOC ON)              # 关键：让 CMake 自动跑 moc

find_package(Qt6 REQUIRED COMPONENTS Core)
add_executable(qthread_demo main.cpp)
target_link_libraries(qthread_demo PRIVATE Qt6::Core)

用 qmake 的话：

text
QT += core
CONFIG += c++17 console
CONFIG -= app_bundle
SOURCES += main.cpp

要点就三条：

  1. CMAKE_AUTOMOC ON 或 qmake 的默认 AUTOMOC 必须开着。
  2. 单文件示例末尾那行 #include "main.moc" 不能删，它把 moc 生成的元对象代码拼进来。
  3. 用 QApplication 和 QPushButton 时 CMake 得加 Widgets 组件，find_package(Qt6 REQUIRED COMPONENTS Core Widgets)，链接 Qt6::Widgets。

五、run 里的代码跑在哪个线程 #

再抄一遍公理：以 run() 为起点的调用栈在新线程，其余在旧线程。

把常见的代码位置逐条对照：

代码位置 所在线程 说明
run() 函数体的每一行 新线程 唯一确定的入口
run() 里 new 出来、无 parent 的对象 新线程 对象的线程归属取创建时的当前线程
run() 里创建对象并把 this 当 parent 非法 parent 在旧线程，跨线程父子关系 Qt 直接报错
run() 里调用的普通函数、msleep() 新线程 属于这条调用栈
子类构造函数 旧线程 构造发生在 start() 之前
子类的自定义槽函数 旧线程 对象依附旧线程，队列连接投递回旧线程
start() / quit() / wait() / isRunning() 旧线程 这些是控制接口，设计上就是从旧线程调
exec() 新线程 只在 run() 里调

父子关系的坑最容易踩。文档写得很死：QObject 必须和它的 parent 在同一个线程。所以 run() 里这么写是错的：

cpp
void HelloThread::run()
{
    QObject *object1 = new QObject(this);        // 错误：parent 在旧线程
    QObject object2;                             // 正确：栈上对象，属于新线程
    QSharedPointer<QObject> object3(new QObject); // 正确：无 parent，属于新线程
}

同一段代码在构造函数里写就对，因为构造函数本身就在旧线程。判断标准只有一条：这行代码执行时，当前线程是哪个，对象就归哪个。

子类里除 run() 以外的成员，两个线程都能碰，同步责任在你自己。稳妥的策略是三段式：

  • start() 之前，主线程把参数（成员变量）统统设好。
  • 线程跑起来之后，主线程不碰其他成员。
  • 线程结束后（wait() 返回或收到 finished()），主线程再来收结果。

这个模式不用加锁，因为访问在时间上是错开的。它也是子类化 QThread 唯一能称得上「安全」的共享方式。

反过来，构造函数里创建的东西不属于新线程，这个后果会以警告的形式冒出来：

text
QObject::startTimer: Timers can only be used with threads started with QThread

原因是在构造函数里 new QTimer 或者建了 QTcpSocket，对象落在主线程，之后在 run() 里 start() 定时器——定时器属于另一个线程，Qt 拒绝。要么把对象建在 run() 里，要么别在子类构造函数里碰线程相关资源。

到这一步，子类化的问题已经露头了：能安全共享的方式只有「开始前设、结束后收」，中间要通信就得绕。 而一旦工作线程里想要事件循环、想用定时器、想收信号，绕法就开始难看了。下一章的两种错法，就是从这儿来的。

六、用法二：moveToThread #

换思路：不继承 QThread，写一个普通 QObject 派生类当 worker，把它的对象搬进线程。

搬的动作是 QObject::moveToThread(QThread *)，语义是改这个对象的线程归属。搬完之后，所有投递给它的队列连接都会落到新线程的事件循环里执行，槽函数也就跟着跑到新线程了。

最小例子：

cpp
#include <QCoreApplication>
#include <QObject>
#include <QThread>
#include <QDebug>

class Dummy : public QObject
{
    Q_OBJECT
signals:
    void sig();
public slots:
    void emitsig() { emit sig(); }
};

class Worker : public QObject
{
    Q_OBJECT
public slots:
    void onTimeout()
    {
        qDebug() << "Worker::onTimeout from:" << QThread::currentThreadId();
        QThread::currentThread()->quit();     // 槽跑完让工作线程退出
    }
};

int main(int argc, char *argv[])
{
    QCoreApplication a(argc, argv);
    qDebug() << "main thread:  " << QThread::currentThreadId();

    QThread t;
    Dummy dummy;
    Worker worker;

    QObject::connect(&dummy, &Dummy::sig, &worker, &Worker::onTimeout);
    worker.moveToThread(&t);          // 关键一行：Worker 归属改到 t 管理的线程
    t.start();

    dummy.emitsig();                  // 在主线程发射，槽跑到新线程执行
    t.wait();                         // 等槽跑完、线程退出

    return 0;
}

#include "main.moc"

输出：

text
main thread:   0x1a5c
Worker::onTimeout from: 0x186c

两个 ID 不一样，槽在工作线程执行。注意这条连接的发射方在主线程、接收方在工作线程，connect 时用的是默认的 Qt::AutoConnection，运行期自动判定成队列连接。

再看实际项目里的样子。这是 Qt 文档推的写法：

cpp
class Worker : public QObject
{
    Q_OBJECT
public slots:
    void doWork(const QString &parameter)
    {
        QString result = parameter.toUpper();   // 换成任意耗时操作
        emit resultReady(result);
    }
signals:
    void resultReady(const QString &result);
};

class Controller : public QObject
{
    Q_OBJECT
    QThread workerThread;

public:
    Controller()
    {
        Worker *worker = new Worker;                       // 不能给 parent
        worker->moveToThread(&workerThread);
        connect(&workerThread, &QThread::finished,
                worker, &QObject::deleteLater);            // 线程结束再删对象
        connect(this, &Controller::operate,
                worker, &Worker::doWork);                  // 跨线程，队列连接
        connect(worker, &Worker::resultReady,
                this, &Controller::handleResults);         // 回到主线程
        workerThread.start();
    }

    ~Controller()
    {
        workerThread.quit();
        workerThread.wait();
    }

public slots:
    void handleResults(const QString &s) { qDebug() << "result:" << s; }

signals:
    void operate(const QString &parameter);
};

几个细节值得单独说：

  • worker 没有 parent。有 parent 的对象不能 moveToThread()，Qt 会拒绝。
  • Controller 里 workerThread 是值成员，析构顺序靠后，所以 worker 的 deleteLater 一定在 workerThread 还活着时被处理。
  • quit() 之后必须 wait()。否则 workerThread 析构时线程还在跑，程序直接崩溃，报 QThread: Destroyed while thread is still running。
  • handleResults 写起来跟单线程没区别，不用锁，不用信号量。跨线程的排队、唤醒、参数拷贝，事件循环全包了。

两种改坏它的写法也在文档里出现过：

cpp
// 写法一：强制直连。槽在主线程执行，因为信号是主线程发的
connect(this, &Controller::operate, worker, &Worker::doWork, Qt::DirectConnection);

// 写法二：干脆直接调。函数体在主线程执行，worker 的归属形同虚设
worker->doWork(QStringLiteral("data"));

第一种把槽拽回发射线程，等于白搬。第二种更直接，绕过信号槽，函数就在调用者线程跑。两种写法都会让「耗时的活挪到后台」这个目的落空。

这套用法有个真实约束：worker 的某个槽一旦阻塞，这个线程的事件循环就停了，其他投给该线程的槽也全部排队等着。 你想在同一线程里并发两个耗时槽，做不到，得开两个线程。这条经常被误认为 bug，其实是一线程一事件循环的必然结果。

七、moveToThread 的完整流程 #

搬对象这件事有严格顺序，乱一步就白搭。完整流程如下：

步骤 代码 要点
1. 准备线程对象 QThread t; 或 new QThread 可以是成员或栈对象，此刻还没启动
2. 创建 worker Worker *w = new Worker; 严禁给 parent，否则不能搬
3. 连接信号槽 connect(...) 放在搬之前或之后都行，连接类型在发射那一刻判定
4. 搬进线程 w->moveToThread(&t); 必须在 w 当前所属的线程里调用
5. 启动线程 t.start(); 之后 run() 进入 exec()，事件循环开始转
6. 收尾 t.quit(); t.wait(); 顺序不能反，quit() 只是让 exec() 返回

第 4 步的「必须在当前所属线程调用」是硬约束。在主线程创建的对象，就只能由主线程搬；让工作线程去搬主线程的对象，Qt 会警告 Cannot move object with a parent 或者直接不生效。

一个完整的、带定时器的 worker 长这样：

cpp
#include <QCoreApplication>
#include <QObject>
#include <QThread>
#include <QTimer>
#include <QDateTime>
#include <QDebug>

class Collector : public QObject
{
    Q_OBJECT
public slots:
    void init()                       // 这个槽在 worker 线程执行
    {
        m_timer = new QTimer(this);   // 在哪个线程建，就归哪个线程
        connect(m_timer, &QTimer::timeout, this, &Collector::tick);
        m_timer->start(1000);
    }

    void tick()
    {
        qDebug() << "tick in" << QThread::currentThreadId();
        emit sample(QDateTime::currentMSecsSinceEpoch());
    }

    void shutdown()
    {
        if (m_timer)
            m_timer->stop();
    }

signals:
    void sample(qint64 stamp);

private:
    QTimer *m_timer = nullptr;
};

int main(int argc, char *argv[])
{
    QCoreApplication a(argc, argv);
    qDebug() << "main thread:" << QThread::currentThreadId();

    QThread t;
    Collector *c = new Collector;

    c->moveToThread(&t);
    QObject::connect(&t, &QThread::started, c, &Collector::init);
    QObject::connect(&t, &QThread::finished, c, &QObject::deleteLater);
    QObject::connect(&t, &QThread::finished, &a, &QCoreApplication::quit);
    QObject::connect(c, &Collector::sample, &a, [](qint64 stamp) {
        qDebug() << "sample" << stamp << "handled in" << QThread::currentThreadId();
    });

    t.start();
    QTimer::singleShot(3500, &a, [&t]() { t.quit(); });
    int ret = a.exec();
    t.wait();
    return ret;
}

#include "main.moc"

关键几处：

  • QThread::started 信号发在工作线程里，所以 init() 在新线程执行，在里面 new QTimer(this) 父子同线程，合法。
  • 如果反过来，在 main 里 new QTimer 再传进去，就会报 Timers can only be used with threads started with QThread。
  • finished 直接接 deleteLater，worker 在主线程被删，但此时它已经不在新线程里了，删除是安全的。
  • finished 再接一个 &a 的 quit，主线程的事件循环才有退出的理由，否则 a.exec() 一直不返回。

搬动还有个连带效果：子对象跟着走。moveToThread 会把这个对象的所有 children() 一起搬过去。所以给 worker 建子对象要么在搬之前建好，要么等搬完之后在新线程里建，别在中间状态乱塞。

早期代码里还见过这种写法：

cpp
QThread t;
QTimer timer;
Worker worker;

QObject::connect(&timer, &QTimer::timeout, &worker, &Worker::onTimeout);
timer.start(1000);

timer.moveToThread(&t);      // 这行其实可以去掉
worker.moveToThread(&t);

t.start();

timer.moveToThread(&t) 是多余的。timer 留在主线程照样能工作，区别只在于连接类型：

  • 两个对象都搬进 t：timeout() 在新线程发射，同线程 → 直连，槽就在发射线程里跑。
  • 只搬 worker：timeout() 在主线程发射，跨线程 → 队列连接，槽在 worker 所属的新线程里跑。

两种都能让槽落在新线程，只是路径不同。这也是理解连接类型的最短例子：槽的位置取决于接收者在哪个线程，不取决于信号从哪来。

八、两种用法的根本区别 #

把两者摆到一张表上：

对照项 继承 QThread 重写 run() moveToThread()
新线程里跑什么 只有 run() 函数体 搬过去的对象的全部槽
入口数量 一个，run() 多个，任意可连接的槽
事件循环 要自己写 exec() run() 默认就 exec()，白拿
其他成员函数在哪 创建线程，即主线程 新线程
槽函数在哪 主线程（除非直连或 moveToThread(this)） 新线程
与主线程通信 靠信号从 run() 里发出 双向队列连接
状态共享 成员变量跨线程裸访问，得加锁 数据都在 worker 线程内，只在内部访问，不用锁
停止方式 标志位 / requestInterruption()，quit() 对无事件循环的 run() 无效 quit() 让 exec() 返回
适合场景 一次性长任务、纯计算、阻塞循环 常驻对象、需要定时器、需要反复接收指令
主要风险 除 run() 外的代码都在旧线程，容易误判 worker 阻塞会堵住整个线程的事件循环

差别可以压缩成一句：继承时只有 run() 是新线程的，其余全是旧线程的；moveToThread() 时对象整体搬走，它的每个槽都是新线程的。

这就是推荐 moveToThread() 的全部理由，不多不少。子类化本身没毛病，毛病在于「部分在里、部分在外」这种割裂状态。人脑记不住哪行代码在哪个线程，于是就写错。把对象整体搬走，割裂消失，判断成本归零。

反过来也有代价。moveToThread() 把「什么时候开始干」交给信号，你必须有个发射方；纯计算的批处理任务，用 run() 反而干净，没有事件循环也就不存在「槽被堵住」的问题。

机制上两者没有高下，都是同一个 QThread，都是一个原生线程加一个事件循环。区别只在「你的代码以什么形态进入那根线程」：一个是被重写的入口函数，一个是被搬进去的对象槽。

九、槽函数在哪个线程执行 #

这是 Qt 多线程里最容易搞错的一点，也是所有「明明搬进线程了怎么还在主线程」问题的答案。

先把 connect() 的最后一个参数列全：

连接类型 槽在哪里执行 备注
Qt::AutoConnection 发射线程与接收者线程相同 → 直连，在发射线程；不同 → 队列，在接收者线程 默认值，运行期判定
Qt::DirectConnection 发射线程，无视接收者归属 等于普通函数调用
Qt::QueuedConnection 接收者线程，要求该线程事件循环在转 参数要能拷贝
Qt::BlockingQueuedConnection 接收者线程，发射方阻塞等槽返回 同线程使用立刻死锁
Qt::UniqueConnection 行为同 AutoConnection 附加效果：同信号同槽不能重复连
Qt::AutoCompatConnection 行为同 AutoConnection Qt3 兼容遗留，别用

判定规则一句话：槽函数在哪个线程执行，取决于接收者对象的线程归属，跟信号从哪个线程发出无关。

这句话在直连下要加个补丁——直连时接收者归属完全不起作用，槽就在发射线程跑。所以精确表述是：队列连接看接收者，直连看发射者，自动连接先比较两者再决定用哪种。

把常见组合列成判定表：

发射信号的线程 接收者对象的线程归属 连接类型 槽的执行线程
主线程 主线程 Auto 主线程（退化为直连）
主线程 工作线程 Auto 工作线程（队列）
工作线程（run() 里 emit） 主线程 Auto 主线程（队列）
工作线程 工作线程 Auto 工作线程（直连）
任意 任意 Direct 发射线程
任意 任意，且两者不同 Queued 接收者线程，需事件循环
任意 任意，且两者不同 BlockingQueued 接收者线程，发射方被阻塞

第三行是重灾区。信号确实是从工作线程发出来的，槽却在主线程执行，原因就一个：接收者对象在主线程。

五个实验把这张表跑一遍。实验一：主线程发信号给 QThread 子类的槽。

cpp
#include <QCoreApplication>
#include <QObject>
#include <QThread>
#include <QDebug>

class Dummy : public QObject
{
    Q_OBJECT
public:
    Dummy(QObject *parent = nullptr) : QObject(parent) {}
signals:
    void sig();
public slots:
    void emitsig() { emit sig(); }
};

class Thread : public QThread
{
    Q_OBJECT
public:
    Thread(QObject *parent = nullptr) : QThread(parent)
    {
        // moveToThread(this);      // 实验三再打开这行
    }
public slots:
    void slot_main()
    {
        qDebug() << "from thread slot_main:" << QThread::currentThreadId();
        quit();              // 收尾：主线程里调 quit()，让工作线程的 exec() 返回
    }
protected:
    void run() override
    {
        qDebug() << "thread thread:" << QThread::currentThreadId();
        exec();
    }
};

int main(int argc, char *argv[])
{
    QCoreApplication a(argc, argv);
    qDebug() << "main thread:" << QThread::currentThreadId();

    Thread thread;
    Dummy dummy;

    QObject::connect(&thread, &QThread::finished, &a, &QCoreApplication::quit);
    QObject::connect(&dummy, &Dummy::sig, &thread, &Thread::slot_main);

    dummy.emitsig();

    int ret = a.exec();
    thread.wait();
    return ret;
}

输出（具体数值每次变，结论不变）：

text

from thread slot_main: 0x1a40
thread thread: 0x1a48

slot_main 和主线程同 ID。thread 是在 main 里构造的对象，归属主线程，队列连接把它投递回主线程。

实验二：把发射方挪进 run()，信号从工作线程发出，接收者仍是 thread 对象。

cpp
class Thread : public QThread
{
    Q_OBJECT
public slots:
    void slot_thread()
    {
        qDebug() << "from thread slot_thread:" << QThread::currentThreadId();
        quit();              // 收尾：这个槽在主线程跑，调 quit() 让 work 线程的 exec() 返回
    }
signals:
    void sig();
protected:
    void run() override
    {
        qDebug() << "thread thread:" << QThread::currentThreadId();
        Dummy dummy;                                   // 在 run 里建，归属新线程
        connect(&dummy, &Dummy::sig, this, &Thread::slot_thread);
        dummy.emitsig();
        exec();
    }
};

int main(int argc, char *argv[])
{
    QCoreApplication a(argc, argv);
    qDebug() << "main thread:" << QThread::currentThreadId();
    Thread thread;
    QObject::connect(&thread, &QThread::finished, &a, &QCoreApplication::quit);
    thread.start();
    int ret = a.exec();
    thread.wait();
    return ret;
}

输出：

text
main thread: 0x15c0
thread thread: 0x1750
from thread slot_thread: 0x15c0

信号从 0x1750 发出，槽在 0x15c0 执行。接收者是 thread，thread 在主线程，答案早就定了。

实验三：把构造函数里那行 moveToThread(this) 的注释去掉。

text
main thread: 0x13c0
thread thread: 0x1de0
from thread slot_main: 0x1de0

槽跑到次线程了。能工作，但这是 Bradley T. Hughes 明确反对的写法——它把 QThread 的控制接口搬进了工作线程，后面第十章专门说为什么这是坑。

实验四：不改归属，改连接类型，用直连。

cpp
connect(&dummy, &Dummy::sig, this, &Thread::slot_thread, Qt::DirectConnection);

槽在发射线程执行。实验二的场景下就是 0x1750，也就是工作线程。代价是：现在 slot_thread 和工作线程里的 run() 共享数据，得自己加 QMutex。等于把「用事件循环省掉的锁」又请回来了。

实验五：标准答案，worker 搬过去。

cpp
class Object : public QObject
{
    Q_OBJECT
public slots:
    void slot()
    {
        qDebug() << "from thread slot:" << QThread::currentThreadId();
        QThread::currentThread()->quit();     // 收尾：槽跑完让线程退出
    }
};

int main(int argc, char *argv[])
{
    QCoreApplication a(argc, argv);
    qDebug() << "main thread:" << QThread::currentThreadId();

    QThread thread;
    Object obj;
    Dummy dummy;

    QObject::connect(&thread, &QThread::finished, &a, &QCoreApplication::quit);
    obj.moveToThread(&thread);
    QObject::connect(&dummy, &Dummy::sig, &obj, &Object::slot);
    thread.start();
    dummy.emitsig();

    int ret = a.exec();
    thread.wait();
    return ret;
}

#include "main.moc"

输出：

text
main thread: 0x1a5c
from thread slot: 0x186c

槽稳稳落在工作线程。整个过程中没写一行锁代码，也没动连接类型。

还有两个附带条件必须记住：

  • 队列连接要有事件循环才生效。如果 run() 里是个死循环、没调 exec()，投递过去的事件永远堆在队列里，槽一次都不会执行。
  • Qt::BlockingQueuedConnection 只能跨线程用。发射方和接收者在同一线程时用它，程序立刻死锁——发射方在等槽返回，槽在等发射方让出事件循环。

调试时最省事的判断手段是打印 obj->thread()：

cpp
qDebug() << "worker lives in" << worker->thread()
         << "current is" << QThread::currentThread();

两个指针相同就是同线程，不同就是跨线程。槽在哪执行，看前一个值。

十、QThread 对象的归属陷阱 #

QThread 对象归属创建它的线程，这条事实能解释一半的坑。逐个拆。

第一个坑：moveToThread(this)。

cpp
Thread::Thread(QObject *parent) : QThread(parent)
{
    moveToThread(this);      // 把控制接口搬进它自己管理的线程
}

看起来聪明，实际是把 start()、quit()、wait()、isRunning() 这些控制接口挪到了工作线程。之后主线程再调 thread.quit()，就变成跨线程操作一个不属于自己的对象。Qt 文档说得很直白：QThread 的所有成员方法都是按「从创建线程调用」设计的，不要用 moveToThread() 把这套接口搬走。

第二个坑：run() 里拿 this 当 parent。

cpp
void Thread::run()
{
    QObject *obj = new QObject(this);   // parent 在主线程，对象在新线程，非法
}

QObject 必须和 parent 同线程。这行代码要么直接告警，要么留下一个随机崩的雷。

第三个坑：在子类构造函数里创建线程相关资源。

cpp
Thread::Thread(QObject *parent) : QThread(parent)
{
    m_timer = new QTimer(this);   // 定时器落在主线程
}

void Thread::run()
{
    m_timer->start(100);          // 在工作线程启动主线程的定时器
}

运行时报：

text
QObject::startTimer: Timers can only be used with threads started with QThread

定时器的线程归属是创建它的线程，在工作线程里启动它，Qt 不认。要在线程里用定时器，就在 run() 里建，或者把定时器对象也搬进去。

第四个坑：绕过信号槽直接调 worker 的函数。

cpp
worker->doWork(data);    // 主线程里直接调，就在主线程执行

这种情况下还会撞见另一类警告：

text
QObject::killTimer: timers cannot be stopped from another thread

因为 doWork 内部想停掉属于工作线程的定时器，实际执行却发生在主线程。函数的执行线程和对象归属不一致，Qt 一检测到就拒绝。

第五个坑：QThread 对象先死，线程还活着。

cpp
void f()
{
    QThread t;
    t.start();
}   // t 析构，线程还在跑

报 QThread: Destroyed while thread is still running，多数平台直接 abort。解决方式只有两种：确保 wait() 返回后再析构，或者用 new 加 finished → deleteLater 让它自己收尾。

把这几条收成一张表：

陷阱写法 后果 正确做法
moveToThread(this) 控制接口跑到工作线程，quit() / wait() 变成跨线程调用 永不搬 QThread 自己
new QObject(this) 写在 run() 里 父子跨线程，未定义行为 无 parent 创建，或用栈对象
构造函数里 new QTimer(this) startTimer 警告，定时器不工作 在 run() 或工作线程的槽里创建
直接调 worker->doWork() 函数在主线程执行，与对象归属不符 一律走信号槽
QThread 值对象先析构 Destroyed while thread is still running 先 quit() + wait()，或 deleteLater
run() 里不调 exec() 却指望队列连接 槽永不执行 要么加 exec()，要么改用直连并加锁

十一、start 与 quit、wait 的配合 #

start() 有个重载接受优先级：

cpp
void QThread::start(Priority priority = InheritPriority);
优先级 含义
QThread::IdlePriority 系统空闲才调度
QThread::LowestPriority 比低优先级还低
QThread::LowPriority 低
QThread::NormalPriority 默认档，与创建它的线程同级
QThread::HighPriority 高
QThread::HighestPriority 比高还高
QThread::TimeCriticalPriority 最高，尽量别用
QThread::InheritPriority 默认参数，继承创建者的优先级

三个线程不同优先级跑起来：

cpp
MyThread mThread1, mThread2, mThread3;
mThread1.name = QStringLiteral("mThread1");
mThread2.name = QStringLiteral("mThread2");
mThread3.name = QStringLiteral("mThread3");

mThread1.start(QThread::HighPriority);
mThread2.start();                          // InheritPriority
mThread3.start(QThread::LowPriority);

return a.exec();

优先级只是调度权重，不是执行顺序保证。高优先级的线程拿到 CPU 时间片的概率大，输出里它跑得更靠前，但别把它当同步手段用。这类例子的正确用法是观察现象，不是依赖行为。

start() 是幂等的：线程已在运行时再调一次，什么也不做，不会起第二个线程。

quit() 和 exit(int) 的语义常常被误解。它们做的事只有一件——让该线程的事件循环退出：

cpp
void QThread::quit()   // 等价于 exit(0)

所以：

  • run() 里调了 exec()：quit() 生效，exec() 返回，run() 返回，线程结束。
  • run() 里是个 while 循环、没调 exec()：quit() 完全无效。事件循环都不存在，退什么？

第二种情况下要退出，只有两条路：

cpp
// 路子一：标志位（推荐）
void Thread::run()
{
    while (m_run) {
        // do something
    }
}

// 路子二：中断请求（Qt 5.2+，内部带互锁）
void Thread::run()
{
    while (!isInterruptionRequested()) {
        // do something
    }
}

// 外部：thread.requestInterruption();

terminate() 是最后手段。它从外部强杀线程，线程持有的锁不会释放，栈上的对象不会析构，共享数据会停在半路。用它换来的「立刻停」，往往要拿一个更难查的崩溃去还。

wait() 是同步收尾：

cpp
bool QThread::wait(QDeadlineTimer deadline = QDeadlineTimer(QDeadlineTimer::Forever));
bool QThread::wait(unsigned long time);     // 毫秒，超时返回 false

它阻塞调用者直到线程结束。返回 true 表示线程确实退出了，false 表示超时。注意一个反直觉的点：调 quit() 之后再 wait()，是让事件循环返回、run() 返回、线程结束，而不是让 run() 立刻中断。

正确的收尾顺序固定是这三步：

cpp
workerThread.quit();       // 1. 让 exec() 返回
workerThread.wait();       // 2. 等线程真正结束
// 3. 此时才能安全析构 QThread 对象、释放关联资源

顺序反转成 wait() 再 quit()，wait() 会一直阻塞下去，因为事件循环永远不退出。这是死锁的常见来源。

另外，quit() 不会打断正在执行的槽。当前槽跑完，控制权回到事件循环，才轮到退出。所以一个跑十分钟的槽，quit() 之后你还是得等十分钟。想让 quit() 快，就别在槽里写长循环，把工作拆成小块重新入队。

finished() 信号在线程真正结束时发出，此时 run() 已经返回。它是清理 worker 的最佳时机：

cpp
QObject::connect(&workerThread, &QThread::finished, worker, &QObject::deleteLater);
QObject::connect(&workerThread, &QThread::finished, &workerThread, &QObject::deleteLater);

两条连接都指向 deleteLater 时，worker 和 QThread 会在事件循环的空隙里被回收，不用手动 delete，也不用担心在信号处理中途删对象。

十二、常见的错误用法 #

把踩过的坑排一遍，按出现频率从高到低：

错误写法 现象 原因 正确做法
子类里加槽，指望它在工作线程跑 槽打出来的 ID 和主线程一样 子类对象归属主线程，队列连接投递回主线程 用 moveToThread()，或接受它在主线程跑
构造函数里 moveToThread(this) 能跑，但 quit() / wait() 行为古怪 控制接口被搬进工作线程 删掉这行
worker->moveToThread() 前给了 parent 搬不动，槽还在主线程 有 parent 的对象不能改归属 new Worker 不给 parent
在 run() 里 new QObject(this) 告警或随机崩 父子跨线程 无 parent 创建，或用栈对象
quit() 用在没 exec() 的 run() 上 线程不退出 没有事件循环可退 用标志位或 requestInterruption()
quit() 后忘了 wait() 程序退出时崩 QThread 析构而线程在跑 quit() 紧跟 wait()
直接调 worker->doWork() 活在主线程干，界面照样卡 函数在调用者线程执行 走信号槽
跨线程强行 DirectConnection 偶尔崩，偶发数据错乱 槽跑在发射线程，与对象数据竞争 保持队列连接，或自己加锁
同线程用 BlockingQueuedConnection 界面直接卡死 发射方等槽，槽等事件循环 只在跨线程用
想在一个线程里并发跑两个耗时槽 第二个槽迟迟不开始 一线程一事件循环，槽是串行的 开两个线程
用 terminate() 收尾 偶发死锁、资源泄漏 线程被强杀，锁不释放 标志位 + quit() + wait()
把 QThread 当值对象用完就析构 Destroyed while thread is still running 线程生命周期长于对象 先停线程，或 deleteLater

最坑的是第一条。代码长这样：

cpp
class Thread : public QThread
{
    Q_OBJECT
public slots:
    void doHeavyWork()      // 作者以为这在工作线程
    {
        // ... 十秒的活 ...
    }
protected:
    void run() override
    {
        exec();             // 事件循环在工作线程转起来了
    }
};

// 主线程
Thread t;
t.start();
QMetaObject::invokeMethod(&t, "doHeavyWork", Qt::QueuedConnection);   // 界面卡十秒

事件循环确实在工作线程转，invokeMethod 也确实投递成功了。但投递目标是 t，而 t 归属主线程，队列连接把调用送回了主线程。exec() 起的那个循环是给「归属新线程的对象」服务的，t 自己不在其列。

还有一条流传很广的说法要纠正：「继承 QThread 就能让 run() 里的消息机制留在主线程，moveToThread 就会跟到子线程」。这个说法把因果搞反了。槽在哪个线程，从来不由你选了哪种用法决定，只由接收者对象的线程归属和连接类型决定。第五、九两章的判定表才是唯一依据。

十三、怎么选 #

不看场景直接背结论没用，按任务形态对号入座：

任务形态 选什么
一次性跑个函数，拿返回值 QtConcurrent::run()，配合 QFutureWatcher
一次性批处理容器，吃满多核 QtConcurrent::map() / filter() / reduce()
一次性长任务，无事件循环需求 继承 QThread 重写 run()，结束发信号
常驻对象，反复接指令 QObject + moveToThread()，队列连接收发
常驻对象，需要定时器轮询 同上，定时器在工作线程里创建
已有子类化代码能正常工作 别动。改写的收益往往小于引入 bug 的风险

优先级给三条经验：

  1. 手上有「对象」要长期活着、要反复被调用，走 moveToThread()。它给你的是一整个线程的事件循环，不是一次函数调用。
  2. 手上有「一段代码」要跑完就完，走 run() 或 QtConcurrent。硬套 worker object 只会多出无意义的信号槽。
  3. 拿不准时，先写 run()，发现需要在里面 connect 或者想要 QTimer 的那一刻，就该换成 moveToThread()。这个转折点很清晰，出现了就是信号。

评审代码时看三处：moveToThread 的调用位置在不在对象所属线程；quit() 后面有没有 wait()；子类里除了 run() 之外还有没有别的方法被当成「在线程里跑」使用。三处都对，就没什么大问题。

十四、易错点速查 #

要点 结论
QThread 对象在哪 创建它的线程，不是 run() 跑的线程
新线程里跑什么 只有 run() 的调用栈；moveToThread() 后是对象的槽
槽在哪个线程 看接收者归属（队列），或发射者（直连）
信号从哪发重要吗 队列连接下不重要
默认连接类型 AutoConnection，发射时比较双方线程再定
队列连接的前提 接收者线程有事件循环在转
run() 默认实现 调 exec()（Qt 4.4 起）
quit() 管什么 只让事件循环退出，不管 run() 里的死循环
wait() 必须在哪 quit() 之后，析构之前
能不能搬 QThread 自己 不能。moveToThread(this) 是公认坏实践
worker 有 parent 能否搬 不能
run() 里能 new QObject(this) 吗 不能，parent 在旧线程
定时器归谁 创建它的线程，跨线程 start() 会告警
一个线程能并发跑几个槽 一次一个，槽是串行排队的
同线程 BlockingQueuedConnection 死锁
最稳的收尾顺序 quit() → wait() → 析构

写 Qt 多线程，脑子里只留一句话就够：对象有归属，槽跟着对象走，信号只是触发器。把每个对象的线程归属列清楚，余下的 API 细节都是查文档的事。
