这是 Qt 多线程与事件循环系列的第四篇。前三篇把 QThread 的用法、事件循环怎么转、QObject 归哪个线程讲完了，这一篇接着往下落，讲事件机制的两个实际应用：自己造事件，以及按时间触发。

讲什么：QEvent::Type 与自定义事件的注册、QEvent 子类的写法、postEvent 与 sendEvent 的语义差异、事件怎么被接收和分发、子线程往主线程投递事件的完整链路、processEvents 的重入风险与递归栈溢出、QTimer 的几种用法与 API 面、定时器精度与 Qt::TimerType、微秒级高精度方案、定时器与线程的绑定关系、替代方案。

不讲什么：QEventLoop 的内部实现细节、信号槽四种连接类型的逐条剖析、QtConcurrent 和 QThreadPool。这些散在系列其他篇里。

跨篇指路：QThread 怎么用才对，看《QThread 的正确用法》；事件循环本体与 QObject 的线程归属，看《事件循环与 QObject 的线程归属》；线程管理和线程间通信，看《线程管理与线程间通信》。本篇默认你已经知道 exec() 是在跑一个循环，也默认你知道一个对象有个「所属线程」。

一、事件的类型与自定义事件 #

Qt 里每个事件都带一个类型值，类型就是个整数。QEvent::Type 是枚举，底层是 int，所以它天然是个可以自己填数的东西。

这个整数空间被 Qt 分成了几段，规矩是死的：

区间 归属 说明
0 ~ 999 Qt 框架保留 QEvent::MouseButtonPress、QEvent::Timer、QEvent::User 之前的全部内置类型
1000 ~ 65535 用户自定义 QEvent::User = 1000 是起点，QEvent::MaxUser = 65535 是终点
65535 以上 溢出区 别碰，行为不保证

QEvent::User 不是给你直接用的类型，它是个分界桩。真正的做法是拿 QEvent::registerEventType() 去申请一个空闲值。

cpp
// 静态函数，签名：
// static int QEvent::registerEventType(int hint = -1);

QEvent::Type myEvent1 = static_cast<QEvent::Type>(QEvent::registerEventType());
QEvent::Type myEvent2 = static_cast<QEvent::Type>(QEvent::registerEventType());

hint 传 -1，Qt 自己在 User ~ MaxUser 里找一个没被占的值给你。也可以传个具体的数当偏好，比如 registerEventType(2000)，但被占了它不会报错，而是另找一个返回，所以别假设返回值一定等于你传的 hint。

这个函数是线程安全的，内部有锁。多个线程同时注册不会撞车。所以注册动作可以放在静态成员的初始化里，交给编译器在 main() 之前完成。

造自定义事件有三条路，从轻到重：

做法 代码量 能带数据 适用
只用 QEvent::Type + 现成的 QEvent 最少 不能 纯通知，类似「踢一脚」
派生 QEvent 子类 中 能 需要携带 payload，绝大多数场景
手写常量 QEvent::User + 1 最少 不能 不推荐，会撞车

第三条路要单独骂一句。QEvent::User + 1 这种写法在单文件小 demo 里能跑，一旦工程里两个模块都这么写，类型就重了，event() 里两个分支抢同一个值，调试起来能让人怀疑人生。用 registerEventType()，别省这两行。

二、QEvent 子类的定义 #

先说最省的写法，只用一个 Type，把数据塞在别处（比如 sender 的成员变量）——这种只适合纯通知。

cpp
// widget.h
class Widget : public QWidget
{
    Q_OBJECT
protected:
    bool event(QEvent *e) override;
private slots:
    void on_pushButton_clicked();
private:
    Ui::Widget *ui;
    QEvent::Type myEvent1, myEvent2;
};

cpp
// widget.cpp
Widget::Widget(QWidget *parent) : QWidget(parent), ui(new Ui::Widget)
{
    ui->setupUi(this);
    myEvent1 = static_cast<QEvent::Type>(QEvent::registerEventType());
    myEvent2 = static_cast<QEvent::Type>(QEvent::registerEventType());
}

bool Widget::event(QEvent *e)
{
    if (e->type() == myEvent1) {
        QMessageBox::warning(this, tr("event"), tr("myEvent1"), QMessageBox::Yes);
        return true;
    } else if (e->type() == myEvent2) {
        QMessageBox::warning(this, tr("event"), tr("myEvent2"), QMessageBox::Yes);
        return true;
    }
    return QWidget::event(e);
}

void Widget::on_pushButton_clicked()
{
    QCoreApplication::sendEvent(this, &QEvent(myEvent1));
    QCoreApplication::sendEvent(this, &QEvent(myEvent2));
}

注意按钮槽里那两行：&QEvent(myEvent1) 是个临时对象，取地址传给 sendEvent。能这么干就是因为 sendEvent 是同步的，函数返回时事件对象已经被处理完了，栈上的临时对象生命周期够用。换成 postEvent 立刻就是野指针。

现在说带数据的写法。派生一个类，类型值做成静态成员，构造函数把类型透传给基类。

cpp
// myevent.h
#ifndef MYEVENT_H
#define MYEVENT_H

#include <QEvent>
#include <QString>

class MyEvent : public QEvent
{
public:
    explicit MyEvent(Type type, const QString &payload = QString());
    QString payload() const { return m_payload; }

    static Type m_event1;
    static Type m_event2;
    static Type m_event3;
private:
    QString m_payload;
};
#endif // MYEVENT_H

cpp
// myevent.cpp
#include "myevent.h"

QEvent::Type MyEvent::m_event1 = static_cast<QEvent::Type>(QEvent::registerEventType());
QEvent::Type MyEvent::m_event2 = static_cast<QEvent::Type>(QEvent::registerEventType());
QEvent::Type MyEvent::m_event3 = static_cast<QEvent::Type>(QEvent::registerEventType());

MyEvent::MyEvent(Type type, const QString &payload)
    : QEvent(type), m_payload(payload)
{
}

三个静态成员在 main() 之前就注册完了，全程只注册一次。QEvent 的构造函数只接一个 Type，子类想多拿参数就在自己这层加。

有一点容易踩：QEvent 的拷贝构造是公开的，但不要拷贝一个已经投递出去的事件。事件的所有权转移规则在下一章讲，先记住「造一个新的」永远比「复制一个旧的」安全。

组件里发事件：

cpp
void Widget::on_pushButton_clicked()
{
    MyEvent e(MyEvent::m_event1, QStringLiteral("hello"));
    QCoreApplication::sendEvent(this, &e);
}

event() 里的分支：

cpp
bool Widget::event(QEvent *e)
{
    if (e->type() == MyEvent::m_event1) {
        QMessageBox::warning(this, tr("myEvent"), tr("m_event1"), QMessageBox::Yes);
        return true;
    } else if (e->type() == MyEvent::m_event2) {
        QMessageBox::warning(this, tr("myEvent"), tr("m_event2"), QMessageBox::Yes);
        return true;
    } else if (e->type() == MyEvent::m_event3) {
        auto *me = static_cast<MyEvent *>(e);
        qDebug() << "payload:" << me->payload();
        return true;
    }
    return QWidget::event(e);
}

static_cast 在这里是安全的，因为类型值只会是我们自己注册的那几个，别的对象发不出这个 type。想让编译器帮你把类型对上，用 QEvent::type() 判断之后再 cast，顺序不能反。

前一步写的 sendEvent 版本和这一步的派生类版本，功能上等价，区别在于数据怎么带：

维度 只注册 Type 派生 QEvent 子类
数据传递 得靠外部变量 事件对象自带
类型安全 纯整数比较 可以 static_cast 到具体类
生命周期 简单 投递到堆上时要管好释放
扩展性 加字段就得改全局 加成员就行

三、postEvent 与 sendEvent 的区别 #

这两个函数名字像，语义完全不是一回事。选错了要么卡界面，要么崩。

先看签名：

cpp
bool QCoreApplication::sendEvent(QObject *receiver, QEvent *event);
void QCoreApplication::postEvent(QObject *receiver, QEvent *event,
                                 int priority = Qt::NormalEventPriority);

sendEvent 返回 bool，那是接收者 event() 的返回值，表示「处理了没有」。postEvent 返回 void，没有任何反馈——事件进队列那一刻，它就不归你管了。

sendEvent 干的事：直接调 receiver->event(event)，把它跑完，然后返回。整个过程在你的调用栈上完成。事件对象是你在栈上建的，用完就没了，编译器自动回收。

postEvent 干的事：把事件对象挂到 receiver 所属线程的事件队列里，然后立刻返回。真正的处理要等那个线程的事件循环转到这一条。事件对象必须是在堆上用 new 建的，因为函数返回后它还得活着。

核心区别压成一句话：sendEvent 是同步直接调用，postEvent 是异步投递进队列。

这个区别决定了三件事——

  1. 会不会阻塞：sendEvent 会。接收者在 event() 里干多久，你就得等多久。如果接收者在同一个线程，而且它弹了个模态框，那你的函数就一直卡在那行。
  2. 在哪个线程执行：sendEvent 在你的当前线程同步执行，所以你必须自己在接收者所属线程里调它，跨线程直接调是错的。postEvent 交给了事件循环，事件循环在哪个线程转，就在哪个线程执行。
  3. 事件对象归谁：sendEvent 不接管所有权，栈上、堆上随你，你自己管。postEvent 接管所有权，接收者处理完之后负责 delete，你绝对不能再碰那个指针。

完整的对照表：

维度 sendEvent postEvent
语义 同步直接调用 异步投递入队
返回 立即返回处理结果 bool 立即返回，无结果
阻塞调用者 会，直到处理完毕 不会
执行线程 调用者所在线程 接收者所属线程的事件循环
事件对象内存 栈或堆皆可，调用者管理 必须在堆上 new，接收者管理
跨线程使用 不允许 允许
线程安全 否 是
可取消 否 可以，removePostedEvents()
可调优先级 否 可以，priority 参数

还有一条容易忽略的差异：postEvent 可以批量攒着一起发。它有个 priority 参数，取值 Qt::HighEventPriority（1）、Qt::NormalEventPriority（0）、Qt::LowEventPriority（-1）。同优先级按投递顺序 FIFO，高优先级的插到前面。sendPostedEvents(receiver, eventType) 能主动把队列里的事件抽出来立刻处理，removePostedEvents(receiver, eventType) 能直接扔掉。

这套关系和 update() 与 repaint() 很像，讲的是同一件事：update() 把重绘请求挂进队列，等事件循环空闲了合并成一次重绘，跨线程调也安全；repaint() 立刻走一遍绘制流程，调用返回时像素已经变了，只能在本线程用。谁想立刻生效、谁愿意等一等，代码里的选择逻辑是一样的。

四、自定义事件的接收与处理 #

postEvent 把事件送到队列，队列最终把事件喂给 receiver->event(e)。所以接收端的入口只有一个：重写 event()。

cpp
bool Widget::event(QEvent *e)
{
    switch (e->type()) {
    case MyEvent::m_event1:
        handleEvent1();
        return true;
    case MyEvent::m_event2:
        handleEvent2();
        return true;
    default:
        break;
    }
    return QWidget::event(e);   // 不认识的，交回父类
}

返回值是合同：true 表示「我处理完了，别再往下传」；false 表示「我不认识，交回去」。QWidget::event() 拿到 false 会继续分发给 mousePressEvent()、keyPressEvent() 这些专门的处理函数，最后会再传给父 widget。

忘了 return QWidget::event(e) 的后果是整条链断掉——按钮点不动、键盘没反应、重绘不触发。这类 bug 排查起来很闷，因为代码看着没错。

对 type() >= QEvent::User 的事件，QObject::event() 内部会转调另一个虚函数 customEvent()。所以还有第二种入口：

cpp
class Widget : public QWidget
{
protected:
    void customEvent(QEvent *e) override
    {
        if (e->type() == MyEvent::m_event1) {
            handleEvent1();
        }
    }
};

customEvent() 不返回 bool，没有「传下去」的概念，收到就处理。它的好处是不用碰 event() 那一大串 if-else，业务代码和框架分发逻辑分开了。坏处是只有 User 以上的类型才走这条路，QEvent::Timer 这类内置类型进不来。

第三种是事件过滤器，不改接收者，在外部拦截：

cpp
class Watcher : public QObject
{
protected:
    bool eventFilter(QObject *watched, QEvent *e) override
    {
        if (e->type() == MyEvent::m_event1) {
            qDebug() << "intercepted for" << watched;
            return true;    // true: 吃掉，不再交给 watched
        }
        return QObject::eventFilter(watched, e);
    }
};

// 装配
watcher->installEventFilter(someWidget);

三条路的取舍：

方式 入口 需要改接收者 适用
重写 event() bool event(QEvent*) 是 业务类型多，需要统一分支
重写 customEvent() void customEvent(QEvent*) 是 只处理自定义类型，想隔离
事件过滤器 eventFilter(QObject*, QEvent*) 否 想外部拦截、想监视别的对象

最后一条规则要记牢：postEvent 投出去的事件，不管接收者处不处理、认不认识、返回 true 还是 false，事件循环都会在分发完之后 delete 它。所以你不能在 postEvent 之后再去读那个事件对象的字段——那是已释放内存。要拿数据，就在接收端读。

五、子线程向主线程投递事件 #

GUI 类不是线程安全的。QLabel::setText()、QProgressBar::setValue()、QWidget::update() 这些，在子线程里直接调就是给自己埋雷——轻则画面错乱，重则随机崩在绘制代码里。规矩只有一条：界面操作在主线程做。

那子线程算出来的结果怎么回主线程？三条路：

路径 机制 跨线程安全 要不要 exec()
postEvent 投自定义事件 事件队列 安全 主线程要有事件循环
信号槽 + Qt::QueuedConnection 事件队列（内部也是 postEvent） 安全 接收方线程要有事件循环
QMetaObject::invokeMethod(..., Qt::QueuedConnection) 事件队列 安全 同上
直接调方法 函数调用 不安全 不需要

看清楚一件事：后两条本质也是往队列里塞东西，和 postEvent 是同一套地基。区别只在于，postEvent 允许你把任意结构塞进事件里，而信号槽只传声明过的参数类型。

完整的投递示例。先造事件类：

cpp
// myevent.h
#ifndef MYEVENT_H
#define MYEVENT_H
#include <QEvent>
#include <QString>

class MyEvent : public QEvent
{
public:
    MyEvent(Type type, const QString &text) : QEvent(type), m_text(text) {}
    QString text() const { return m_text; }
    static Type m_event2;
private:
    QString m_text;
};
#endif // MYEVENT_H

子线程从 QThread 派生，重写 run()：

cpp
// mythread.h
#ifndef MYTHREAD_H
#define MYTHREAD_H
#include <QThread>

class MyThread : public QThread
{
    Q_OBJECT
public:
    explicit MyThread(QObject *parent = nullptr) : QThread(parent) {}
protected:
    void run() override;
};
#endif // MYTHREAD_H

cpp
// mythread.cpp
#include "mythread.h"
#include "myevent.h"
#include <QCoreApplication>

void MyThread::run()
{
    // 干活
    QString result = doHeavyWork();

    // 结果回主线程：new 出来的事件，所有权交给接收者
    QCoreApplication::postEvent(parent(),
                                new MyEvent(MyEvent::m_event2, result));

    // 这里不需要 exec()，投递完就退出
}

主线程侧接收：

cpp
// widget.cpp
Widget::Widget(QWidget *parent)
    : QWidget(parent), ui(new Ui::Widget), m_pThread(new MyThread(this))
{
    ui->setupUi(this);
}

Widget::~Widget()
{
    m_pThread->wait();     // 先收线程，再拆界面
    delete ui;
}

bool Widget::event(QEvent *e)
{
    if (e->type() == MyEvent::m_event2) {
        auto *me = static_cast<MyEvent *>(e);
        ui->label->setText(me->text());   // 在主线程，安全
        return true;
    }
    return QWidget::event(e);
}

void Widget::on_pushButton_2_clicked()
{
    m_pThread->start();
}

这段代码里有几个点，每一个都能独立把程序搞崩。

第一，parent() 是谁。MyThread 的 parent 是 Widget，而 Widget 住在主线程。所以 postEvent(parent(), ...) 是把事件投给主线程的队列，主线程的事件循环来处理。如果 MyThread 没有 parent，就得额外存一个接收者指针。

第二，MyThread 对象本身住在主线程，但它的 run() 跑在新线程。QObject::parent() 只是个普通 getter，在新线程里读它是安全的，因为它就是个成员变量，没被改。

第三，为什么必须是 postEvent。原素材里那句话说得对：要保证子线程退出之前，如果事件还没被主线程处理，这条消息仍然可用。sendEvent 传栈对象，子线程一返回，栈就没了，主线程再去看那条事件就是读脏内存。postEvent 传堆对象，所有权已经移交给了接收者的队列，子线程的死活跟它无关。

第四，接收者必须活着。如果 Widget 在事件还没处理完就析构了，队列里挂着的事件会被 Qt 清掉（QObject 析构时会做），但如果你自己 delete 了事件又留了指针，就是另一回事。一句话：只在接收端读事件，别在投递端留指针。

第五，wait() 要加。Widget 析构时如果 MyThread 还在跑，run() 里访问 parent() 就是访问已析构对象。wait() 挡一下，把线程收尸完再往下走。

还有一种更省事的写法，用 QMetaObject::invokeMethod 就不需要造事件类：

cpp
QMetaObject::invokeMethod(mainWindow, [mainWindow, result]() {
    mainWindow->setResultLabel(result);
}, Qt::QueuedConnection);

Qt 5.10 之后支持 functor 版本。lambda 会被包装成一个 QMetaCallEvent 投进队列，本质还是 postEvent。参数里有引用捕获的，注意对象生命周期，队列里的调用会晚上不少。

六、processEvents 的用法与风险 #

QCoreApplication::processEvents() 的官方语义很短：把事件队列里当前所有事件处理完，然后返回给调用者。

两个重载：

cpp
// 处理队列里现有的事件，然后返回
static void QCoreApplication::processEvents(QEventLoop::ProcessEventsFlags flags = QEventLoop::AllEvents);

// 最多花 maxtime 毫秒
static void QCoreApplication::processEvents(QEventLoop::ProcessEventsFlags flags, int maxtime);

它存在的理由很直接：你有一段耗时任务跑在主线程，界面会假死。中途插一句 processEvents()，让重绘、鼠标点击这些排队的事件有机会被处理掉，进度条才能动。

cpp
void Widget::on_startButton_clicked()
{
    const int total = 100000;
    for (int i = 0; i < total; ++i) {
        doOneUnitOfWork(i);

        if (i % 100 == 0) {
            progressBar->setValue(i * 100 / total);
            QCoreApplication::processEvents();   // 让界面喘口气
        }
    }
}

这段能跑，进度条会动，取消按钮也能点。但它只适合「我知道自己在干什么」的场景。风险清单如下：

风险 表现 起因
事件循环重入 上一个操作没做完，新的又进来 队列里的事件会回调到当前正在执行的函数
递归导致栈溢出 崩溃，调用栈一屏都是同几个函数 重入一次套一层，重入无限次就爆栈
对象被销毁 崩溃在 this 上 重入期间用户点了关闭，widget 被 delete
定时器提前触发 计数比预期多 processEvents() 把定时器事件一起处理了
deleteLater 不生效 对象泄漏 DeferredDelete 事件要回到真正的循环才处理
性能下降 循环变慢 每次都遍历队列

最后一条容易被忽略：deleteLater() 投的是 QEvent::DeferredDelete，这个类型的事件由外层事件循环特殊处理，processEvents() 不会把它当普通事件处理掉。想让它在局部循环里生效，得显式来一句：

cpp
QCoreApplication::sendPostedEvents(nullptr, QEvent::DeferredDelete);

想要比 processEvents() 更可控的等待，用局部 QEventLoop：

cpp
// 等一个信号，最多 3 秒，期间不阻塞界面
QEventLoop loop;
QTimer::singleShot(3000, &loop, &QEventLoop::quit);
connect(someObject, &SomeObject::finished, &loop, &QEventLoop::quit);
loop.exec();

这个写法比裸调 processEvents() 好在：它有明确的退出条件，事件处理范围受控，而且不会把整个队列无条件抽干。exec() 会阻塞当前函数，但界面还在响应。

七、processEvents 递归崩溃的原因 #

这是本篇最值得看的一段。一个真实案例，代码短，崩得干净。

cpp
// bugthread.h
class BugThread : public QThread
{
    Q_OBJECT
public:
    BugThread(QObject *parent = nullptr) : QThread(parent) {}
signals:
    void sigBugSignal();          // 无穷无尽地发
protected:
    void run() override
    {
        while (true)
            emit sigBugSignal();
    }
};

// bugs.cpp —— Bugs 是 QMainWindow，只多一个槽 onBugSlot()
Bugs::Bugs(QWidget *parent) : QMainWindow(parent)
{
    ui.setupUi(this);
    auto *bt = new BugThread(this);
    connect(bt, SIGNAL(sigBugSignal()), this, SLOT(onBugSlot()));
    bt->start();
}

void Bugs::onBugSlot()
{
    Sleep(1);
    QApplication::processEvents();
}

跑起来，栈溢出，崩。

拆开看这条链路：

  1. BugThread::run() 是个 while (true)，不停 emit sigBugSignal()。发射频率极高，队列里始终堆着一堆待处理项。
  2. 信号从子线程发出，接收者 Bugs 在主线程，连接类型自动判定为 Qt::QueuedConnection（跨线程自动走队列）。于是每次 emit 都往主线程队列投一条 QMetaCallEvent。
  3. 主线程事件循环取到第一条，调 onBugSlot()。这时它进了槽函数，栈上有了一帧。
  4. onBugSlot() 里调 processEvents()。这一句把队列里现有的事件全部抽出来处理。
  5. 队列里躺着的是什么？还是 sigBugSignal 的排队调用。于是又一次进入 onBugSlot()。栈上第二帧。
  6. 第二个 onBugSlot() 里又调 processEvents()，队列里还有，再进一次。第三帧。
  7. 子线程还在狂发，队列永远抽不干。栈帧一层层堆上去，堆到栈空间用完，程序被系统干掉。

这就是重入。关键在第五步：processEvents() 没有「我在处理这个事件时不要重进」的概念，它只知道「队列里有东西，处理掉」。而你正在处理的这个槽，恰好就是队列里的东西。

栈长这样：

text
onBugSlot()                     <- processEvents()
  └─ onBugSlot()                <- processEvents()
       └─ onBugSlot()           <- processEvents()
            └─ onBugSlot()      <- processEvents()
                 └─ ...         <- 直到栈溢出

注意 Sleep(1) 那一句。它不但没帮忙，还让每一帧在栈上多待一会儿——虽然崩溃是必定的，但这段睡眠把「每帧耗时」放大了，观感上更容易复现。

修复分几个层次，从治标到治本：

手段 做法 效果
别在槽里 processEvents 删掉那一行 治本，但界面会卡
防重入标志 static bool inSlot 挡住自己 治标，事件还是堆着
改用局部 QEventLoop 带退出条件 好很多，范围可控
投递端限流 子线程加 QThread::msleep() 治本，减少队列压力
分片处理数据 一次只处理一小块 治本，业界常规做法
换 Qt::DirectConnection 改成直连 更糟，槽直接在子线程跑，界面操作直接崩

防重入标志是最小改动：

cpp
void Bugs::onBugSlot()
{
    static bool inSlot = false;
    if (inSlot)
        return;              // 重入直接弹回，不再往下套
    inSlot = true;
    doSomething();
    QApplication::processEvents();
    inSlot = false;
}

这段能挡住递归，但它把「本不该在槽里处理的事件」也丢了——那些排队调用被 return 掉，一次都没执行。如果业务上不能丢，就得改成攒队列：

cpp
void Bugs::onBugSlot()
{
    m_pending.append(takeResult());   // 只入袋，不处理
    if (m_draining)
        return;                       // 正在处理中，直接返回
    m_draining = true;
    while (!m_pending.isEmpty()) {
        handleOne(m_pending.takeFirst());
        QCoreApplication::processEvents(QEventLoop::ExcludeUserInputEvents);
    }
    m_draining = false;
}

ExcludeUserInputEvents 这个 flag 很实用，它让 processEvents() 跳过鼠标键盘事件，只处理重绘之类的东西。用户点不动界面，但画面会刷新，重入面也窄了。

根上的问题还是那个 while (true) emit。发射端没有任何节流，接收端再怎么防守都是被动的。给子线程加个 msleep(1)，队列压力降两个量级，问题立刻消失。这不是「绕过」，是把错误的位置纠正回来——信号是用来通知状态变化的，不是用来跑满 CPU 总线的。

八、QTimer 的三种用法 #

定时器和事件是一套东西。QEvent::Timer 是内置事件类型，QTimer 只是它外面包的一层信号槽皮。所以定时器能不能跑，取决于事件循环转不转——exec() 没起来，start(1000) 调一百遍也不会触发。

QTimer 继承 QObject，能干的事就这么几件：

API 作用
new QTimer(QObject *parent = nullptr) 构造，传 parent 交给对象树管内存
setInterval(int msec) / interval() 读写信超时间隔
start(int msec) 设间隔并启动，等价于 setInterval + start()
start() 用当前 interval 启动；interval 默认 0
stop() 停止
isActive() 正在跑返回 true
setSingleShot(bool) / isSingleShot() 单次触发开关
remainingTime() / timerId() 距下次超时还剩多少毫秒 / 底层定时器 id，未启动都返回 -1
setTimerType(Qt::TimerType) 精度档位
static singleShot(int msec, ...) 一次性延时，静态版

老代码里会看到 changeInterval(msec)，那是 Qt 3 的 API，Qt 4 之后没了。功能上等价于——运行中调用会先停再重启，未运行会直接启动：

cpp
timer->stop();
timer->setInterval(msec);
timer->start();

三种用法，按场景分。

用法一：重复定时器 + 信号槽。 主线用法，绝大多数场景就是它。

cpp
QTimer *timer = new QTimer(this);                     // 挂到 this 上，随 this 一起销毁
connect(timer, &QTimer::timeout, this, &MyClass::onTimeout);
timer->setInterval(1000);
timer->start();

timeout() 每次超时发一次。不用的时候 stop() 掉——一个空转的定时器照样占着一次系统唤醒，一直在耗电。原作者提过一句「虽然 QTimer 简单易用，但是比较耗内存，所以在不必要的时候就必须终止它」，指的是同一件事：定时器是有成本的，别让它闲着。

用法二：静态 singleShot。 只要延时一次，不想留成员变量。

cpp
QTimer::singleShot(200, this, &MyClass::delayedAction);
QTimer::singleShot(200, [this]() { statusLabel->setText("done"); });

第一个参数是毫秒，第二个是上下文对象。传 this 的意义在于：如果 this 在 200ms 内被销毁，这条定时器会自动取消，不会回调到野指针。传 nullptr 就没有这层保护。

用法三：零间隔定时器。 interval 为 0 的定时器，在队列里所有待处理事件处理完之后立刻超时一次，然后又排回队尾。它不占 CPU 满速，是「队列空了就跑一轮」的语义。

cpp
QTimer *timer = new QTimer(this);
connect(timer, &QTimer::timeout, this, &MyClass::processOneItem);
timer->start();      // interval 默认 0

这个模式用来分片处理大批数据：一次只啃一小块，啃完让出控制权，界面保持响应。随着多线程铺开，这类活越来越多地交给 QThread，但零间隔定时器在不想引线程的场合仍然好用。

三种用法摆一起：

用法 典型写法 触发次数 适用
重复定时器 timer->start(1000) 反复 轮询、刷新、心跳
单次定时器 QTimer::singleShot(200, ...) 一次 延时执行、防抖
零间隔定时器 timer->start() 队列空闲即触发 分片处理、保持响应

完整例子，进度条每秒涨 1%，到 100% 停：

cpp
MyWidget::MyWidget(QWidget *parent)
    : QWidget(parent), progress_value(0)
{
    setFixedSize(400, 300);

    progress_bar = new QProgressBar(this);
    progress_bar->setGeometry(50, 50, 150, 20);
    progress_bar->setValue(0);

    timer = new QTimer(this);          // 带上 this，交给对象树
    timer->setInterval(1000);
    timer->start();
    connect(timer, SIGNAL(timeout()), this, SLOT(changeValue()));
}

void MyWidget::changeValue()
{
    progress_value++;
    if (progress_value > 100)
        timer->stop();
    progress_bar->setValue(progress_value);
}

new QTimer(this) 带上 this 这一步别省。省了就得在析构函数里手动 delete，忘了就是泄漏。Qt 的对象树会自动回收子对象，白给的机制不用是浪费。

九、单次触发与重复触发 #

定时器的默认行为是重复触发：超时一次，重新计时，再来一次，直到你 stop()。

改成一次性的开关是 setSingleShot(true)：

cpp
QTimer timer;
timer.setSingleShot(true);
connect(&timer, &QTimer::timeout, this, &MyClass::once);
timer.start(200);

单次定时器超时后自动停止，isActive() 变回 false。要再来一次，得重新 start()。

几个行为细节，踩过才知道：

  1. 运行中改间隔会重启整个计时。 start(500) 在运行中的定时器上再调一次，计时从零开始，不是从上次超时点续。想改间隔但不重置，只能等这次超时后再说。
  2. 槽里 stop() 是安全的。 槽执行期间定时器已经在重新计时了，stop() 把它掐掉，不会有多余的一次触发。
  3. 错过多次只发一次。 系统忙的时候定时器没法准时，会连积压好几轮。Qt 的处理是合并——只发一次 timeout()，然后按正常间隔继续。它不会补发一串信号让你去追平。这条很重要，意味着你在槽里数「触发了几次」来推算时间是不成立的。
  4. 重复触发会漂移。 每秒触发一次不等于每 1000ms 精确一次。每次的超时点是「上一轮超时点 + 间隔 + 处理延迟」，误差会累积。要按绝对时间对齐，就在槽里读时钟自己算偏差，别指望定时器替你保证。
  5. remainingTime() 能救场。 想减小漂移，用「距上次该触发的时刻还差多少」来动态 start()，而不是盲目重开。
cpp
void MyClass::onTick()
{
    // 每次都按墙钟对齐，误差不累积
    const qint64 now = QDateTime::currentMSecsSinceEpoch();
    const qint64 next = m_nextDue + 1000;
    m_nextDue = next;
    const int delay = static_cast<int>(qMax<qint64>(0, next - now));
    timer->start(delay);
}

单次和重复的差别压成一张表：

维度 单次 重复
默认值 setSingleShot(true) 默认就是它
超时后 自动 stop() 自动重新计时
start() 后又超时 不会再触发 一直触发
典型用途 延时执行、超时检测、防抖 轮询、刷新、心跳

十、定时器的精度与误差 #

QTimer 的精度不是它自己说了算，是操作系统说了算，再加上事件队列的排队情况。间隔写 10ms，实际是 11ms、15ms、30ms，取决于系统当时在忙什么。

精度档位由 Qt::TimerType 控制：

类型 精度目标 平台实现 适用
Qt::PreciseTimer 毫秒级，尽量准时 Windows 走多媒体定时器 动画、实时处理
Qt::CoarseTimer ±5% 误差 标准系统定时器 常规业务逻辑，默认值
Qt::VeryCoarseTimer 整秒，把毫秒四舍五入掉 标准系统定时器 超时检测、心跳

默认是 CoarseTimer。想改：

cpp
QTimer *timer = new QTimer(this);
timer->setTimerType(Qt::PreciseTimer);
timer->start(10);

平台差异值得说清楚：

  • UNIX 系（Linux、macOS、iOS）上，CoarseTimer 会把触发时间相近的多个定时器对齐到同一个唤醒点，减少 CPU 唤醒次数，省电。代价是精度被牺牲。这个行为是被设计出来的，不是 bug。
  • Windows 上，PreciseTimer 走多媒体定时器路径，能好一些；CoarseTimer 和 VeryCoarseTimer 走标准 Windows 定时器。

底层能力的典型值：

平台 典型精度
Windows 2000 15 ms
现代 Linux / macOS 1 ms
Windows 10/11 默认 约 15.6 ms（64Hz 时间片）

间隔上限也有硬顶：int 是有符号 32 位，毫秒数最大约 2147483647，折合 24.8 天。想定一个月以后的事，QTimer 干不了。做法是拆——先定一个短的，触发后在槽里继续往后推。

还有两条容易忘的：

  • 系统繁忙时，三种类型都会延迟。精度档位只影响「尽量准时」的力度，不给你硬保证。
  • 定时器数量有上限。部分操作系统对单个进程能开的定时器数有限制，Qt 内部会尝试绕开，但高频大量定时器的场景必须实测目标平台。

十一、高精度定时器 #

先说结论：Qt 跑在通用操作系统上，不是 RTOS。硬实时保证不了，能做到的是软实时——把延迟压低、把抖动控制住。

延迟从哪来，三处：

  1. 系统调度粒度。 Windows 默认时间片约 15.6ms（64Hz）。不动系统定时器精度，QTimer 的最小分辨率就卡在这。
  2. 事件循环的固定开销。 从内核唤醒线程，到 Qt 分发事件，再到调你的槽，这条链每一环都要时间。
  3. 同线程的其他事件。 你在同一个线程里渲染界面、读文件，高精度定时器就只能排队，抖动不可预测。

要突破毫秒级，先动操作系统和线程策略。

Windows 上把系统定时器分辨率调上去：

cpp
#include <windows.h>

void setupWindowsTimer()
{
    // 1ms 分辨率，部分硬件支持 0.5ms。会增加 CPU 唤醒频率和功耗
    timeBeginPeriod(1);
}

void cleanupWindowsTimer()
{
    timeEndPeriod(1);   // 退出前务必恢复
}

timeBeginPeriod 和 timeEndPeriod 必须成对，只调前者会让整个系统的功耗上升。即便设了 1ms，Sleep(1) 的实际睡眠仍在 1~2ms 之间浮动，比默认的 15.6ms 是质的改善。

Linux 上走实时调度策略和 CPU 亲和性：

bash
chrt -p <pid>                       # 查看当前策略
sudo chrt -f -p 99 <pid>            # FIFO 策略，优先级 99（最高）

把关键线程绑到固定核心，能避免线程在核心间迁移导致的缓存失效和上下文切换开销。需要 sched_setaffinity，或者 taskset。

线程优先级在 Qt 里就一行：

cpp
QThread::currentThread()->setPriority(QThread::TimeCriticalPriority);

Windows 对应 THREAD_PRIORITY_TIME_CRITICAL，Linux 上取决于用户权限，普通用户改不动实时优先级。

代码层面两条路。

方案 A：QChronoTimer（Qt 6.8 起）。 支持 std::chrono::nanoseconds，底层适配了精度更高的系统定时器（Windows 上是 CreateWaitableTimerEx）。

cpp
#include <QChronoTimer>

auto timer = new QChronoTimer(this);
timer->setInterval(std::chrono::microseconds(500));   // 500us
timer->setTimerType(Qt::PreciseTimer);

connect(timer, &QChronoTimer::timeout, this, []() {
    // 高频任务。这里绝对不能有耗时操作，否则事件积压
});

timer->start();

方案 B：独立线程 + 混合等待。 需求压到 100us 以下，靠操作系统的 Sleep 已经没戏。硬办法是自旋等待，或者「长睡眠 + 短自旋」的混合策略，跑在独立线程里。

cpp
#include <QThread>
#include <QElapsedTimer>
#include <atomic>

class MicrosecondWorker : public QThread
{
public:
    void stop() { m_running = false; }

protected:
    void run() override
    {
        setPriority(QThread::TimeCriticalPriority);       // 1. 提优先级
        QElapsedTimer clock;
        clock.start();                                    // 2. 高精度计时

        qint64 last = clock.nsecsElapsed();
        const qint64 intervalNs = 500 * 1000;             // 500us

        m_running = true;
        while (m_running) {
            const qint64 now = clock.nsecsElapsed();
            if (now - last >= intervalNs) {
                performRealtimeTask();
                last += intervalNs;                       // 3. 保持相位，误差不累积
            } else if (intervalNs - (now - last) > 2000000) {
                QThread::msleep(1);                       // 4. 还早，让出 CPU
            } else {
                while (clock.nsecsElapsed() < last + intervalNs) {
                    // _mm_pause();  最后几微秒靠自旋
                }
            }
        }
    }

private:
    std::atomic<bool> m_running{false};
    void performRealtimeTask() { /* 实时业务 */ }
};

这段会吃满一个核，所以必须绑核。last += intervalNs 而不是 last = now 是关键，前者保持相位，后者每次都把误差吃进去。

优化完必须测，别靠感觉。QElapsedTimer 在 Windows 走 QueryPerformanceCounter，Linux 走 clock_gettime(CLOCK_MONOTONIC)，纳秒级：

cpp
QElapsedTimer t;
t.start();

// 待测代码

qDebug() << "took" << t.nsecsElapsed() << "ns";

四种方案的实测区间：

方案 实际最小间隔 抖动 适用
默认 Windows 设置 约 15.6 ms 高 普通 GUI 刷新
timeBeginPeriod(1) 约 1.0 ms 中 多媒体播放、简单动画
QChronoTimer + PreciseTimer 约 1.0 ms（受 OS 限制） 中 高频定时任务
独立线程 + 自旋 小于 10 us 极低 工业控制、高频采集

如果业务对实时性是硬要求（错过截止时间就等于失败），别在 Qt 里硬扛。把控制回路放到 PLC、FPGA 或者专用实时控制器，Qt 只做上位机 HMI。这是工程取舍，不是妥协。

十二、定时器与线程的关系 #

定时器不是一个独立的线程，它绑在某个线程的事件循环上。绑在哪个线程，由「谁创建了它」决定——这就是线程亲和性。

操作 线程要求
创建定时器 任意线程
启动 / 停止定时器 必须在定时器所属线程
接收 timeout 信号 由定时器所属线程发出
改间隔 / 改类型 必须在定时器所属线程

第三行是关键：timeout() 从定时器所属线程发出，不是从接收者所在线程发出。跨线程连接时连接类型自动变成 Qt::QueuedConnection，槽在接收者线程执行——前提是接收者线程有事件循环在转。

在非 GUI 线程里用定时器，必须自己把循环跑起来：

cpp
class WorkerThread : public QThread
{
    void run() override
    {
        QTimer timer;
        connect(&timer, &QTimer::timeout, this, &WorkerThread::doWork);
        timer.start(1000);
        exec();          // 关键：没有这一句，定时器永远不触发
    }
};

run() 里没有 exec()，线程干完活就退出了，事件循环根本不存在，timeout() 无处可发。

现在看一个真实案例。有人在窗口类里写：

cpp
// optimization.cpp
warningThread = new QThread;
timer2 = new QTimer(this);            // 注意这个 this
Worker worker;                        // 栈上局部对象
worker.moveToThread(warningThread);
timer2->start(5000);

QObject::connect(timer2, SIGNAL(timeout()), &worker, SLOT(onTimeout()));  // 不响应
QObject::connect(timer2, SIGNAL(timeout()), this, SLOT(time2outslot()));  // 能响应
warningThread->start();

现象：连到 worker 的槽死活不执行，连到 this 的正常。

两个错叠在一起。

错误一：Worker worker 是栈对象。 这段代码在构造函数里，构造一返回，worker 立刻析构。moveToThread 只是把线程亲和性改了一下，管不了生命周期。定时器超时的时候，&worker 指向的是已经释放的内存。信号发出去，接收者已经不存在，Qt 检测到接收者失效会静默丢弃，所以你看到的是「不响应」而不是崩溃。

错误二：new QTimer(this) 让定时器留在了主线程。 this 是窗口，住在主线程。所以这个定时器的 timeout() 由主线程发出，它压根没进次线程。想让定时器在次线程干活，得让定时器也搬过去。

修法：

cpp
// optimization.h —— 三个都改成指针成员
class Optimization : public QWidget
{
    Q_OBJECT
private:
    QThread *m_warningThread = nullptr;
    QTimer *m_timer2 = nullptr;
    Worker *m_worker = nullptr;
};

// optimization.cpp
m_warningThread = new QThread(this);
m_worker = new Worker;                  // 堆上，生命周期跟着窗口
m_worker->moveToThread(m_warningThread);

m_timer2 = new QTimer;                  // 不传 this，先让它没有主人
m_timer2->moveToThread(m_warningThread); // 定时器搬进次线程
m_timer2->setInterval(5000);

connect(m_warningThread, &QThread::finished, m_worker, &QObject::deleteLater);
connect(m_timer2, &QTimer::timeout, m_worker, &Worker::onTimeout);
connect(m_timer2, &QTimer::timeout, this, &Optimization::time2outslot);

m_warningThread->start();
QMetaObject::invokeMethod(m_timer2, [t = m_timer2]() { t->start(); });  // 在次线程启动

最后一行是新手最容易漏的：start() 必须在定时器所属线程调。定时器搬过去了，你就得用 invokeMethod 把启动动作也投递过去。直接在主线程 m_timer2->start()，行为未定义——Qt 会打警告，甚至什么都不发生。

一个更省事的替代：干脆不要 moveToThread，直接在 worker 线程里创建定时器。前面 WorkerThread::run() 的写法就是这一类。

错误写法 后果
栈上创建 worker 又 moveToThread 定时器超时后接收者已析构，槽不执行
new QTimer(this) 后想让它跨线程 定时器留在主线程，timeout 从主线程发出
在 A 线程创建、在 B 线程 start() 未定义行为，Qt 报警告
次线程 run() 里没有 exec() 定时器不触发
定时器 moveToThread 后直接 start() 同上，必须在所属线程启动

十三、定时器的替代方案 #

QTimer 不是唯一选择。Qt 给了三层，从重到轻。

底层：QObject::startTimer() + timerEvent()。 返回一个整数 id，你自己存着。

cpp
class MyWidget : public QWidget
{
protected:
    void timerEvent(QTimerEvent *event) override
    {
        if (event->timerId() == m_timerId)
            doWork();
    }
private:
    int m_timerId = startTimer(1000);
};

startTimer(1000) 返回 id，重复触发，直到 killTimer(id)。优点是不需要额外对象，轻。缺点是没有信号槽、没有单次定时器的概念、多个定时器时全靠 id 判断，代码很快就糊。

中间层：QBasicTimer。 把那个 id 包起来，省掉自己管 id 的麻烦。

cpp
class MyWidget : public QWidget
{
protected:
    void timerEvent(QTimerEvent *event) override
    {
        if (event->timerId() == m_timer.timerId())
            doWork();
    }
public:
    void startWork() { m_timer.start(1000, this); }
private:
    QBasicTimer m_timer;
};

QBasicTimer 不可拷贝，随对象析构自动 killTimer，比裸 id 安全。start() 的第二个参数是接收 timerEvent 的对象。缺点一样：还是得手写 timerEvent()。

上层：QTimer。 信号槽接好就能用，支持单次、支持精度档位、支持对象树管理，代码最少。

怎么选，一句话一条：要信号槽、要挂多个接收者，用 QTimer；已经是 QObject 子类又不想多一个对象，用 QBasicTimer；只需要一个裸 id、随手清理，用 startTimer()。

三者摆一起：

方案 额外对象 信号槽 单次定时 手动清 id 适用
QTimer 需要 有 支持 不需要 默认选择
QBasicTimer 一个成员 无 自己写 不需要 已有 QObject，量小
startTimer() 无 无 自己写 需要 极限轻量、临时用

还有一条路由：大量短命延时不要开一堆 QTimer。用 QTimer::singleShot 就够了，它会自己清理。反过来，几万个同时活跃的定时器会把事件循环压垮，那种场景该换成时间轮或者统一的调度器。

十四、常见故障与现象 #

排查定时器和自定义事件的问题，现象比代码更能提示方向。

现象 多半原因 处理
start() 了但槽不执行 事件循环没跑，或缺 exec() 检查 exec() / 确认定时器线程有循环
子线程投的事件不进 event() 接收者销毁了，或投错了对象 检查 postEvent 的第一个参数
程序崩在 event() 里读字段 读了已投递出去的事件对象 只在接收端读 postEvent 的事件
界面卡住几秒 主线程里用了同步等待或 Sleep 换局部 QEventLoop 或挪到子线程
栈溢出，栈里全是同一个槽 processEvents 导致重入 加防重入标志，或去掉 processEvents
定时器越来越不准 误差累积，间隔在漂 槽里按墙钟重算下次间隔
定时器触发次数比预期少 忙时合并，错过多次只发一次 别用触发次数推算时间
关闭窗口时崩 线程还在跑，析构先发生了 析构里 quit() + wait()
精度差得离谱（差 15ms） 用了默认 CoarseTimer 设 Qt::PreciseTimer
次线程的定时器槽不响应 接收者是栈对象，或定时器没搬线程 改成成员变量 / moveToThread

有一条心法：定时器不触发，先问「事件循环在转吗」；事件到了但处理错，先问「对象还活着吗」。这两问能覆盖八成故障。

十五、易错点速查 #

收尾，全是踩过的坑，一条一句。

易错点 正确做法
用 QEvent::User + 1 当自定义类型 用 QEvent::registerEventType() 注册，避免撞车
假设 registerEventType(2000) 返回 2000 被占用时它会换一个值，只认返回值
postEvent 传栈对象地址 必须 new，所有权移交给接收者
postEvent 之后还读事件对象 处理完就被 delete，读即脏内存
在接收者以外的线程调 sendEvent 只能在自己线程同步调，跨线程用 postEvent
event() 里忘了 return QWidget::event(e) 记住返回父类，否则整条分发链断掉
重写 event() 却用 customEvent() 的逻辑 只有 type() >= QEvent::User 才走 customEvent()
窗口还没显示就 postEvent 给它 事件进了队列但没人处理，等 exec() 起来才会分发
在槽里裸调 processEvents() 会重入，加防重入标志或换局部 QEventLoop
用 while(true) emit 发信号 加节流，或用分片处理，别把队列抽干成死循环
子线程直接调 setText() 走 postEvent 或队列连接，界面只在主线程动
析构时不 wait() 线程 先 quit() 再 wait()，别留下裸奔的线程
用 changeInterval() Qt 4 之后没了，用 setInterval + start
在主线程启停次线程的定时器 必须在定时器所属线程调
靠 timeout 次数算时间 忙时会合并触发，只发一次
设了 timeBeginPeriod 不恢复 必须配 timeEndPeriod，否则全系统耗电上升
认为 Qt 能给硬实时 硬要求交给 PLC / FPGA，Qt 做 HMI
拿 QElapsedTimer 的秒数算微秒 用 nsecsElapsed()，别丢精度
