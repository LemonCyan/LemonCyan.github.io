这篇讲两件事：Qt 程序怎么跟外部进程打交道，以及怎么保证程序只跑一个实例。

前半段是 QProcess：启动外部程序、传参、读输出、写输入、同步与异步、退出清理、孤儿进程。后半段是单实例：为什么只跑一个、三种实现、二次唤醒。

不讲：Qt 网络编程、串口通信、JSON 与 XML、数据库、文件配置与表格、系统信息、二维码扫描。这些都在同目录其他篇里。这里只留跟外部进程相关的最小代码，协议细节不展开。

一、QProcess 是什么 #

QProcess 继承自 QIODevice。这个继承关系决定了它的全部用法：它把外部进程包装成一个可读写的 I/O 设备。你操作文件用什么姿势，操作子进程就用什么姿势——write() 写、read() 读、有数据了发信号。

跟老写法对比一下：

对比维度 system() QProcess
执行方式 同步阻塞，调用处停住 异步，start() 立即返回
输出捕获 拿不到 stdout / stderr 都能读
输入交互 不支持 能写 stdin
进程控制 无 可等待、可终止、可取退出码
跨平台 命令要手动适配 Qt 处理参数转义与分派

system("...") 一行能跑，代价是整条线程陪着等，界面卡死，输出还拿不回来。桌面程序要长期跟外部程序打交道，QProcess 是唯一顺手的工具。

1.1 数据流方向 #

text
  你的 Qt 进程                         外部进程
  ------------                         --------
  write(data)  ---------- stdin ------>  程序逻辑
  readAllStandardOutput() <-- stdout --  标准输出
  readAllStandardError()  <-- stderr --  错误打印

一句话：写进 QProcess 的数据走子进程的 stdin，从 QProcess 读出来的是子进程的 stdout 和 stderr。方向搞反的人不少，记住「喂进去、收回来」。另外子进程不认「行」这个概念，它只认字节流，你写 dir 它不执行，写 dir\n 才执行。

1.2 平台支持 #

不支持的平台：VxWorks、iOS、tvOS、watchOS、UWP。这些系统出于沙箱或内核限制，不提供标准进程机制。桌面三平台（Windows、macOS、Linux）全支持，底层 Unix 系走 fork() + exec()，Windows 走 CreateProcess()，Qt 把这些差异吃掉。

1.3 主要方法一览 #

方法 作用 阻塞界面
start(program, args) 启动程序，立即返回 否
startDetached(...) 脱离父进程启动，父进程退出它照跑 否
write(data) 写入子进程 stdin 否
closeWriteChannel() 关闭 stdin，告诉子进程输入结束 否
readAllStandardOutput() 取走 stdout 缓冲区里的全部数据 否
readAllStandardError() 取走 stderr 缓冲区 否
waitForStarted(ms) 等启动完成 是
waitForReadyRead(ms) 等有新输出到达 是
waitForFinished(ms) 等进程结束 是
terminate() 请求子进程退出 否
kill() 强杀 否
exitCode() / exitStatus() 取退出码 / 退出状态 否
state() NotRunning / Starting / Running 否
pid() 子进程 ID 否

带 waitFor 前缀的三个函数会阻塞。它们在后台线程和命令行工具里没问题，在主线程里会把界面冻住，这条线要一直记着。

1.4 状态流转 #

text
NotRunning --start()--> Starting --启动成功--> Running
Running --正常退出 / 崩溃 / 被杀--> NotRunning

状态变化信号是 stateChanged(QProcess::ProcessState)。判断当前状态直接调 state()，别自己维护布尔值。

二、启动一个外部程序 #

2.1 两种写法，效果一样 #

一体化写法，程序路径和参数一次传进去：

cpp
QProcess process;
process.start("notepad.exe", QStringList() << "C:\\temp\\readme.txt");

分离式写法，先配后启：

cpp
QProcess process;
process.setProgram("notepad.exe");
process.setArguments({"C:\\temp\\readme.txt"});
process.start();          // 等价于 process.open(QIODevice::ReadWrite)

分离式的价值在于「配置」和「启动」能分开，参数按用户选择动态拼的时候，先 setArguments() 再 start() 比反复构造 QStringList 干净。open() 是 start() 的老名字，新代码用 start()。

2.2 start() 返回时，进程还没起来 #

这是最容易被忽略的一点。start() 是异步的——它把启动请求丢给系统，然后立刻返回。返回那一刻，子进程多半还在创建中。

所以下面这段代码是错的：

cpp
QProcess process;
process.start("ffmpeg", {"-version"});
qDebug() << process.readAllStandardOutput();   // 空,一个字节都拿不到

启动成功的标志是 started() 信号：

cpp
QProcess *process = new QProcess(this);
connect(process, &QProcess::started, this, [process]() {
    qDebug() << "子进程起来了,pid =" << process->pid();
});
process->start("ffmpeg", {"-version"});

输出也是同理。子进程写出来的东西不会凭空出现在你的变量里，要等 readyReadStandardOutput() 信号。信号没来，缓冲区就是空的。

2.3 启动失败怎么知道 #

连接 errorOccurred() 信号，异步拿错误：

cpp
connect(process, &QProcess::errorOccurred,
        this, [](QProcess::ProcessError err) {
    if (err == QProcess::FailedToStart)
        qDebug() << "启动失败:" << process.errorString();
});

在后台线程里也可以 waitForStarted(3000) 明确等一次，超时就看 errorString()。errorString() 是人能读的描述，error() 是枚举，排查时两个都打出来。

错误枚举要分清楚，处理方式完全不同：

枚举值 含义 处理建议
FailedToStart 程序不存在或无执行权限 提示用户检查路径
Crashed 启动后异常终止 看 stderr 与退出码
Timedout waitFor* 超时 提示超时，决定是否 kill()
WriteError 写 stdin 失败 检查子进程是否已退出
ReadError 读 stdout 失败 检查通道状态
UnknownError 其他 打日志

Qt 4 时代的信号叫 error(QProcess::ProcessError)，Qt 5 改名成 errorOccurred()。老代码里的 SIGNAL(error(QProcess::ProcessError)) 在新版本上连不上，要一起改。

2.4 只想打开文件或网页，不用 QProcess #

需求只是「用系统默认程序打开一个 URL、一个文件、一个目录」，QDesktopServices::openUrl() 更合适：

cpp
QDesktopServices::openUrl(QUrl::fromLocalFile("C:\\report.pdf"));
QDesktopServices::openUrl(QUrl("https://doc.qt.io"));

成功返回 true，失败返回 false。它不管被打开的程序是什么、也不给你进程句柄——这正好是这里想要的效果。要控制子进程、要读它的输出，才回到 QProcess。

2.5 一个完整的按钮启动例子 #

界面上放个按钮，点一下拉起外部程序，出错弹框：

cpp
MyWidget::MyWidget(QWidget *parent) : QWidget(parent)
{
    QPushButton *btn = new QPushButton("启动", this);
    connect(btn, &QPushButton::clicked, this, &MyWidget::startProcess);

    m_process = new QProcess(this);
    connect(m_process, &QProcess::errorOccurred,
            this, &MyWidget::onProcessError);
}

void MyWidget::startProcess()
{
    m_process->start("E:\\a\\b.exe");
}

void MyWidget::onProcessError(QProcess::ProcessError error)
{
    QString msg;
    switch (error) {
    case QProcess::FailedToStart: msg = "程序不存在或没有执行权限"; break;
    case QProcess::Crashed:       msg = "子进程异常终止";           break;
    case QProcess::Timedout:      msg = "等待子进程超时";           break;
    case QProcess::WriteError:    msg = "写入 stdin 失败";          break;
    case QProcess::ReadError:     msg = "读取 stdout 失败";         break;
    case QProcess::UnknownError:  msg = m_process->errorString();  break;
    }
    QMessageBox::information(this, "外部程序出错", msg);
}

m_process 用 new 分配并传 this 作父对象，窗口析构时它跟着走，不用手写 delete。这跟第七章的清理直接相关。

三、传参与工作目录 #

3.1 用 QStringList 传参，别自己拼字符串 #

参数放在 QStringList 里，空格和引号由 Qt 负责转义：

cpp
QStringList args;
args << "--input" << "C:\\Program Files\\data.txt" << "--out" << "result.mp4";
process.start("ffmpeg", args);

实际执行的命令行是 ffmpeg --input "C:\Program Files\data.txt" --out result.mp4，路径里的空格不用你管。

反过来，把整条命令拼成一个字符串塞给 start()，Qt 找不到那个「程序名」：

cpp
// 错误:Qt 会去找一个叫 "ffmpeg -i a.mp4 b.mp4" 的可执行文件
process.start("ffmpeg -i a.mp4 b.mp4");

// 正确
process.start("ffmpeg", {"-i", "a.mp4", "b.mp4"});

这条规则还有安全含义：参数走列表，用户输入里带空格、带引号、带 & 都只是普通字符；拼成字符串再交给 shell，用户输入就能变成命令注入。凡是变量拼进命令的地方，一律改成列表。

3.2 Windows 内部命令要过 cmd #

dir、type、copy、echo 不是独立程序，是 cmd.exe 的内置命令。直接 start("dir") 会得到 FailedToStart：

cpp
// 错误:系统里没有 dir.exe
process.start("dir");

// 正确
process.start("cmd", {"/c", "dir C:\\"});

cmd 的两个开关：

参数 含义
/c 执行完命令后退出 cmd
/k 执行后保留窗口

多条命令用 & 或 && 串起来交给同一个 cmd：process.start("cmd", {"/c", "cd /d D: & dir & echo Done"});。& 无论前一条成功与否都执行，&& 前一条成功才执行，这条规则是 cmd 的，不是 Qt 的。

3.3 Linux / macOS 的管道与重定向要过 bash #

|、>、>>、* 是 shell 语法，不是程序参数。QProcess 不解释它们，它只会找一个名字里带竖线的可执行文件：

cpp
// 错误:Qt 会寻找名为 "ps -ef | grep main" 的程序
process.start("ps -ef | grep main");

// 正确:交给 bash 解释
process.start("bash", {"-c", "ps -ef | grep main"});

// 重定向同理
process.start("bash", {"-c", "ls -la > listing.txt"});

管道要多个进程协作，QProcess 只起一个进程，这种活必须交给 shell。用 bash -c 的代价是多一层 shell 进程，清理时要注意——杀掉的只是 bash，它拉起来的子进程还在。

3.4 设置工作目录 #

子进程的相对路径、相对输出目录都以工作目录为基准：

cpp
process.setWorkingDirectory("C:\\output");
process.start("converter.exe");

converter.exe 会在 C:\output 下运行，它写出的相对路径文件也落在那里。不设这一项，子进程继承父进程的当前工作目录——那多半是程序启动时的目录，不是 exe 所在目录。QNX 平台有个特例：设置工作目录会让其他线程短暂冻结，桌面平台不用管。

3.5 设置环境变量 #

QProcessEnvironment 拿系统环境，改完再塞回去：

cpp
QProcessEnvironment env = QProcessEnvironment::systemEnvironment();
env.insert("PATH", env.value("PATH") + ":/usr/local/bin");
env.insert("MY_CONFIG", "/etc/app.conf");
env.remove("UNWANTED_VAR");

process.setProcessEnvironment(env);

注意 setProcessEnvironment() 是整体替换，不是合并。直接 env.insert("FOO", "bar") 然后设进去，子进程就只剩 FOO 一个环境变量了，PATH 全没了，连 ls 都找不到。要继承，必须先 systemEnvironment() 打底；不调用这个函数时，子进程默认继承父进程的完整环境。

四、读取子进程的输出 #

4.1 两个通道，分开读 #

外部进程有两条输出通道：

  • stdout：正常输出，程序算出来的结果
  • stderr：错误输出，警告和异常信息

QProcess 把它们分别缓冲，分别发信号：

cpp
QByteArray m_allOutput;   // 成员变量，留着存档

connect(&process, &QProcess::readyReadStandardOutput, this, [&]() {
    m_allOutput += process.readAllStandardOutput();   // 追加，不是覆盖
    qDebug() << "stdout:" << m_allOutput;
});

connect(&process, &QProcess::readyReadStandardError, this, [&]() {
    qDebug() << "stderr:" << process.readAllStandardError();
});

readAllStandardOutput() 会把缓冲区取走并清空，读一次就没了。要留着就自己追加到成员变量，否则想回头查完整日志只能去翻控制台——而 GUI 程序没有控制台。

4.2 合并通道 #

有时只关心「有输出」，不关心走的哪条通道。设成合并模式，stderr 会被并进 stdout：

cpp
process.setProcessChannelMode(QProcess::MergedChannels);
process.start("myapp.exe");

// 全部从 readAllStandardOutput() 取,stderr 那条信号不再发

代价是 readAllStandardError() 永远为空。原来写在 stderr 分支里的处理逻辑会静默失效，改成合并模式时要把这些分支清掉。

4.3 转发通道 #

转发模式让子进程的输出直接打到父进程的控制台，不经过你的代码：

cpp
process.setProcessChannelMode(QProcess::ForwardedChannels);        // 两条都转
process.setProcessChannelMode(QProcess::ForwardedOutputChannel);   // Qt 6.6，只转 stdout
process.setProcessChannelMode(QProcess::ForwardedErrorChannel);    // Qt 6.6，只转 stderr

子进程是自带控制台的命令行工具、你也只想在终端看它吐什么的时候，这个模式最省事。

GUI 应用慎用转发。Windows 上双击启动的程序默认没有控制台，转发的输出直接消失，用户什么都看不到。调试时看着正常的程序，发给用户就「没反应」，原因常在这里。

4.4 三种读取姿势 #

方式 适用场景 是否阻塞
信号槽 GUI 应用、长时间运行的进程 否
waitForReadyRead() 后台线程、命令行工具 是
轮询 bytesAvailable() 需要自己控制节奏的特殊场景 看实现

信号槽是默认选择，写法见 4.1；阻塞式写法留给线程里跑的代码：waitForReadyRead(5000) 最多等 5 秒，之后 readAll() 取数据。返回 false 有两种含义：超时，或者进程已经结束。判断是哪一种，看 state()。

4.5 输出编码 #

QProcess 给你的是 QByteArray，不是 QString。转字符串时选错编码，中文全是乱码：

cpp
// Windows 控制台程序多数输出本地编码(GBK)
QString text = QString::fromLocal8Bit(process.readAllStandardOutput());

// 明确知道子进程输出 UTF-8(git、ffmpeg、多数跨平台工具)
QString text2 = QString::fromUtf8(process.readAllStandardOutput());

在 Windows 上跑 cmd /c dir，fromUtf8() 会得到一堆问号，用 fromLocal8Bit() 才对；跑 git status，反过来。编码没有统一答案，取决于子进程，先拿一条输出试一次，认准了再写死。

4.6 输出量大时别攒着 #

子进程吐得快、槽函数处理得慢，缓冲区会一直涨，日志类程序跑一天能吃掉几个 GB 内存。用 readLine() 按行读，读完立即消费，别整段攒在成员变量里：

cpp
while (m_process->bytesAvailable() > 0) {
    QByteArray chunk = m_process->readLine();   // 按行取
    if (chunk.isEmpty())
        break;                                  // 没遇到换行时返回全部内容
    handleLine(chunk);                          // 立即消费，不累积
}

子进程输出不带换行（进度条）时，readLine() 返回当前缓冲区全部内容，所以循环里必须判空，否则死转。

五、标准输入与交互 #

5.1 写数据必须带换行 #

write() 写的是裸字节。交互式程序靠换行符判断一条命令结束，少了它，命令会一直躺在缓冲区里等着：

cpp
process.write("dir\r\n");    // Windows
process.write("ls\n");       // Linux / macOS

这个坑踩起来难受：程序不报错，write() 返回的字节数也对，就是「什么都没发生」——对方还在等这一行的结尾。

想两边都兼容又不判断平台，除了老老实实加 #ifdef Q_OS_WIN 没有别的魔法：Windows 控制台程序多数要 \r\n，Unix 系要 \n。

5.2 关闭写通道 #

子进程读到 EOF 才知道输入完了。不关写通道，像 gzip -c、cat 这类「读到结尾才输出」的程序会一直等：

cpp
QProcess gzip;
gzip.start("gzip", {"-c"});

gzip.write("Hello Qt!");
gzip.closeWriteChannel();     // 关键:告诉 gzip 没有更多输入了

closeWriteChannel() 只关写方向，读方向照旧可用。这是半关闭，不是终止进程。

5.3 交互式程序的完整流程 #

拉起一个能一问一答的子进程，流程是：启动 → 等它说话 → 读 → 写 → 再等 → 关写 → 等结束。

cpp
QProcess proc;
proc.setProgram("python");
proc.setArguments({"-i"});

connect(&proc, &QProcess::readyReadStandardOutput, this, [&]() {
    QByteArray out = proc.readAllStandardOutput();
    qDebug() << "输出:" << QString::fromLocal8Bit(out);
});

proc.start();
if (!proc.waitForStarted(3000))
    return;

proc.write("print(1+1)\n");        // 交互式解释器认 \n
proc.waitForBytesWritten(3000);

waitForBytesWritten() 确认数据真的进了管道。管道写满时 write() 只是放进内部缓冲就返回，不确认的话，以为发出去了，其实还堆在你这边。真实项目里别用 waitFor* 处理交互，改成「收到输出就做下一步」的状态机，同步等待和异步信号混着用，逻辑会拧成麻花。

5.4 输出「半天不来」不是丢了 #

很多程序的 stdout 是块缓冲，攒够 4KB 才吐一次；子进程被拉起时没有终端，stdout 从行缓冲变成全缓冲。不是 QProcess 丢了数据，是对方还没刷。让它用无缓冲模式（Python 的 -u、stdbuf -oL、--line-buffered），或者自己调 fflush。

六、同步执行与异步执行 #

6.1 同步：等它跑完再往下 #

后台线程或命令行工具里，同步写法读起来最直：

cpp
QProcess gzip;
gzip.start("gzip", {"-c"});

if (!gzip.waitForStarted())
    return false;

gzip.write("Hello Qt!");
gzip.closeWriteChannel();

if (!gzip.waitForFinished(30000)) {    // 30 秒超时
    gzip.kill();
    return false;
}

QByteArray compressed = gzip.readAll();

三件事要记：检查 waitForStarted() 的返回值、写完关通道、waitForFinished() 必须给超时。

6.2 同步与异步怎么选 #

维度 同步（waitFor*） 异步（信号槽）
调用后是否返回 阻塞到条件满足或超时 立即返回
界面响应 冻住 正常
代码形态 一条直线，顺序读得懂 状态分散在槽函数里
出错处理 看返回值 看信号
适用位置 工作线程、CLI 工具 GUI 主线程

主线程里禁止调用 waitFor*。 事件循环停了，界面不重绘、不响应点击，超时 30 秒就是卡 30 秒，这不是「偶尔慢一下」，是彻底失去响应。真要同步语义又不想卡界面，把 QProcess 丢进工作线程，或者用 QtConcurrent::run 包一层，结果通过信号回到主线程。

6.3 异步：包成一个类 #

GUI 里推荐的做法是把 QProcess 包进一个 QObject，对外只暴露信号：

cpp
class ProcessController : public QObject
{
    Q_OBJECT
public:
    explicit ProcessController(QObject *parent = nullptr) : QObject(parent)
    {
        connect(&m_proc, &QProcess::readyReadStandardOutput,
                this, &ProcessController::onOutput);
        connect(&m_proc, &QProcess::readyReadStandardError,
                this, &ProcessController::onErrorOutput);
        connect(&m_proc, &QProcess::finished,
                this, &ProcessController::onFinished);
    }

    void run(const QString &program, const QStringList &args)
    {
        m_proc.start(program, args);
    }

signals:
    void outputReady(const QString &text);
    void errorReady(const QString &text);
    void completed(int exitCode);

private slots:
    void onOutput()
    {
        emit outputReady(QString::fromLocal8Bit(m_proc.readAllStandardOutput()));
    }
    void onErrorOutput()
    {
        emit errorReady(QString::fromLocal8Bit(m_proc.readAllStandardError()));
    }
    void onFinished(int code, QProcess::ExitStatus status)
    {
        emit completed(status == QProcess::NormalExit ? code : -1);
    }

private:
    QProcess m_proc;
};

外部只管连信号，不用碰 waitFor*，也不管子进程什么时候起、什么时候回。界面始终保持可响应。

6.4 超时与分级终止 #

异步模式下没有 waitForFinished(timeout)，超时要自己拿 QTimer 做：

cpp
QTimer::singleShot(30000, this, [this]() {
    if (m_proc.state() != QProcess::NotRunning) {
        m_proc.terminate();                        // 先请求退出
        QTimer::singleShot(5000, this, [this]() {
            if (m_proc.state() != QProcess::NotRunning)
                m_proc.kill();                     // 还不走就强杀
        });
    }
});

同步版本一模一样：waitForFinished(30000) 超时就先 terminate()，再 waitForFinished(5000)，还不走就 kill()。先礼后兵，terminate() 给子进程保存现场、删临时文件的机会，kill() 直接掐死。第七章展开这两者的区别。

6.5 一个同步封装工具类 #

后台任务里要跑一堆命令，每次都写 start + waitForStarted + waitForFinished 太啰嗦。封成一个类：

cpp
class CrossPlatformProcess : public QObject
{
    Q_OBJECT
public:
    bool execute(const QString &command, int timeoutMs = 30000)
    {
        m_stdout.clear();
        m_stderr.clear();
        m_error.clear();

#ifdef Q_OS_WIN
        m_process.start("cmd", {"/c", command});
#else
        m_process.start("bash", {"-c", command});
#endif
        if (!m_process.waitForStarted(3000)) {
            m_error = "启动失败:" + m_process.errorString();
            return false;
        }

        if (!m_process.waitForFinished(timeoutMs)) {
            m_error = "执行超时";
            m_process.kill();
            m_process.waitForFinished(2000);
            return false;
        }

        m_stdout = m_process.readAllStandardOutput();
        m_stderr = m_process.readAllStandardError();
        return m_process.exitStatus() == QProcess::NormalExit
               && m_process.exitCode() == 0;
    }

    QByteArray standardOutput() const { return m_stdout; }
    QByteArray standardError() const { return m_stderr; }
    QString lastError() const { return m_error; }

private:
    QProcess m_process;
    QByteArray m_stdout;
    QByteArray m_stderr;
    QString m_error;
};

用法：

cpp
CrossPlatformProcess proc;
if (proc.execute("git status")) {
    qDebug() << proc.standardOutput();
} else {
    qDebug() << "错误:" << proc.lastError() << proc.standardError();
}

这个类只能在非 GUI 线程里用——它整个是阻塞的。放主线程里，git status 慢一点界面就卡一下。

七、进程的退出与清理 #

7.1 进程怎么结束，看 finished #

子进程结束（正常退出、崩溃、被杀）都会发 finished(int exitCode, QProcess::ExitStatus status)：

cpp
connect(&process, &QProcess::finished,
        this, [](int exitCode, QProcess::ExitStatus status) {
    if (status == QProcess::NormalExit)
        qDebug() << "正常退出,退出码" << exitCode;
    else
        qDebug() << "崩溃退出";
});

exitCode() 和 exitStatus() 随时能查，不用非在槽里取，但它们会在下一次 start() 时被重置，想留档就先存下来。

ExitStatus 含义
NormalExit 进程自己走完了，退出码看 exitCode()
CrashExit 崩溃或被信号杀死，exitCode() 无意义

注意 NormalExit 不等于成功。退出码非 0 也是正常退出——grep 没匹配到返回 1，diff 发现差异返回 1，都是正常退出。要判成功，得同时看 exitStatus() == NormalExit 和 exitCode() == 0。

7.2 terminate 与 kill #

方式 行为 子进程能否保存 推荐度
terminate() 发退出请求（SIGTERM / WM_CLOSE） 能，有机会清理现场 首选
kill() 直接强杀（SIGKILL / TerminateProcess） 不能，立刻断掉 兜底

先 terminate()，给几秒，不走再 kill()。kill() 不给子进程任何反应时间：没写完的文件留在半截，锁文件没删，临时目录残留，数据库事务悬着。这些烂摊子下次启动时才暴露，查起来毫无线索。

terminate() 也不是万能。子进程自己没处理退出请求、卡在死循环里，它就永远不退，所以后面必须有 kill() 兜底，再加一个 waitForFinished() 确认真的死了。

7.3 不清理会怎样 #

QProcess 对象销毁时，如果子进程还在跑，默认它不会跟着退出。父程序关掉了，外部程序还在任务管理器里挂着，一直跑。

这不是理论问题。拉起 FFmpeg 转码，用户中途关掉主窗口，转码进程继续写文件；再打开程序，两个 FFmpeg 抢同一个输出文件。

老代码里常见这种补救：

cpp
if (process) {
    process->close();
    delete process;
    process = NULL;
}

close() 关闭所有通道并结束进程（内部走 kill()），delete 释放对象。能用，但粗暴——没有 terminate() 的机会，也没有等它退出。新代码别照抄。

7.4 两个正确的清理位置 #

位置一：析构函数。QProcess 作为成员，在宿主对象析构时收尾：判断 state() != NotRunning，先 terminate()，waitForFinished(3000) 不回来再 kill()。

**位置二：aboutToQuit。**程序退出前的最后一站，适合清理全局唯一的进程：

cpp
connect(qApp, &QCoreApplication::aboutToQuit, this, [this]() {
    stopChildProcess();
});

aboutToQuit 在事件循环即将停止时触发，这时还能用 waitForFinished()——事件循环要停了，短暂的阻塞等待在这个时点可以接受。

7.5 一个可复用的清理函数 #

cpp
void MyWidget::stopChildProcess()
{
    if (!m_process || m_process->state() == QProcess::NotRunning)
        return;

    m_process->closeWriteChannel();       // 先告诉它没有输入了
    m_process->terminate();               // 再请求退出

    if (!m_process->waitForFinished(3000)) {
        m_process->kill();                // 还不走就强杀
        m_process->waitForFinished(1000); // 等系统回收句柄
    }
}

三步走：关输入 → 请求退出 → 强杀兜底。每次等完都要再确认状态，别假设 terminate() 一定成功。

八、进程树与孤儿进程 #

8.1 孤儿是怎么产生的 #

父进程退出、子进程还活着，这个子进程就成了孤儿。

  • Unix 系：孤儿被 init（pid 1）收养，继续跑，你再也管不到它
  • Windows：没有收养机制，进程独立存活，直到自己退出或被任务管理器结束

QProcess 的父子关系是「管理关系」，不是「生命周期绑定」。父对象析构时 Qt 会尝试结束子进程，但程序被强杀（taskkill /F、崩溃、断电）时，没有任何清理代码能跑，子进程一定留下。

8.2 kill 杀不到孙子 #

kill() 只杀 QProcess 直接持有的那个进程，不管它自己拉起的进程。bash -c "ffmpeg -i a.mp4 b.mp4" 这条命令，QProcess 持有的是 bash，kill() 干掉 bash，ffmpeg 变成孤儿继续转码。你看到的现象是「进程关了，文件还在长」。

Windows 用 taskkill 杀整棵树，/T 是连同子树一起杀，/F 是强制：

cpp
QProcess::execute("taskkill", {"/PID", QString::number(m_process->pid()),
                               "/T", "/F"});

Linux 杀整个进程组，启动时先让它自成一组，结束时按组杀：

cpp
// 启动时
process.setChildProcessModifier([]() {
    ::setpgid(0, 0);          // 自成进程组
});

// 结束时
::kill(-pid, SIGTERM);        // 负号 = 杀整组

setChildProcessModifier() 是 Qt 6.0 起提供的接口，Qt 5 里没有，得自己包一层 setsid，或者用 bash -c 配合 exec。

8.3 什么时候该让它活下来 #

不是所有子进程都该跟着父进程死。调起系统浏览器、用默认程序打开 PDF、启动一个独立工具，本来就该脱离父进程：

cpp
bool ok = QProcess::startDetached("notepad.exe", {"C:\\temp\\a.txt"});

startDetached() 是静态方法，拉起后跟父进程完全脱钩，父进程退出它照跑，这里没有 QProcess 对象可管，也就没有清理问题。

判断标准很简单：产出属于当前会话就绑住它，属于用户之后就放它走。

8.4 崩溃场景的兜底 #

程序被强杀时清理代码不执行，只能靠外部机制：Windows 上把子进程绑进 Job Object 并设 JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE，父进程一死系统自动清理整组；Linux 上用 prctl(PR_SET_PDEATHSIG, SIGTERM) 让子进程在父进程死亡时收到信号。两套都要写平台代码，更省事的路子是让子进程自己带心跳，发现父进程没了就退。

九、单实例：为什么要只跑一个 #

9.1 多开的代价 #

桌面程序被双击两次很常见。用户不觉得这是「开了两个」，他只是又点了一下图标。没做单实例保护，两份实例同时跑，麻烦立刻出现：

  • 配置文件互相覆盖：A 读配置、B 改配置、A 保存，把 B 的改动冲掉
  • 同一份数据被两个进程写：日志文件交错、数据库锁冲突
  • 端口冲突：内嵌 HTTP 服务、本地 socket 服务，第二个实例绑定失败
  • 托盘图标出现两个：用户以为程序出问题了
  • 定时任务执行两遍：备份、同步、上报，数据翻倍

单实例要解决的就是这一件事：第二个实例发现已有实例在跑，自己退出，并把已有实例的窗口顶到前面。

9.2 靠进程名查，不靠谱 #

最直觉的做法是遍历进程列表找同名进程，这条路问题不少：

  • 跨平台各写一套：Windows 用 EnumProcesses + GetModuleBaseName，Linux 读 /proc，macOS 用 sysctl
  • 权限不够时读不到别人的进程信息，查不到就当成「没有实例」，保护失效
  • 名字被改（用户重命名 exe、绿色版、不同安装路径）或同名的其他程序，都会误判

单实例要的是「全局唯一的标记」，不是「名字相同」。Qt 提供了两个现成的标记机制：QLocalServer 占一个本地 socket 名，QSharedMemory 占一段共享内存。加上文件锁，一共三条路。

9.3 三种方案的取舍 #

方案 原理 跨平台 崩溃后能否自动恢复 能否传递数据
QLocalServer / QLocalSocket 占一个本地 socket 名 是 是（需处理残留） 能，可发消息唤醒
QSharedMemory 占一段共享内存 key 是 Linux 上不能 不能，只做标记
QLockFile 占一个锁文件 是 是（有陈旧锁检测） 不能，只做标记

三条路都能实现「只跑一个」，差别在能不能唤醒已有实例、崩溃之后能不能自愈。第十章逐个实现。

十、单实例的三种实现 #

10.1 QLocalServer / QLocalSocket #

思路：第一个实例监听一个本地服务名，后来者去连这个名字。连得上说明已经有人占了，自己退出；连不上说明自己是第一个，那就把这个服务建起来。类里两个成员：bool m_isRunning 和 QLocalServer *m_server，isRunning() 就是返回那个布尔值。

cpp
void MainWidget::initLocalConnection()
{
    m_isRunning = false;

    QCoreApplication::setApplicationName("localserver");
    QString serverName = QCoreApplication::applicationName();

    QLocalSocket socket;
    socket.connectToServer(serverName);
    if (socket.waitForConnected(500)) {
        m_isRunning = true;      // 连上了,说明已有实例
        return;
    }

    // 连不上,自己当服务端
    m_server = new QLocalServer(this);
    connect(m_server, &QLocalServer::newConnection,
            this, &MainWidget::newLocalConnection);

    if (!m_server->listen(serverName)) {
        // 上次崩溃留下同名服务,清掉再试
        if (m_server->serverError() == QAbstractSocket::AddressInUseError
            && QFile::exists(m_server->serverName())) {
            QFile::remove(m_server->serverName());
            m_server->listen(serverName);
        }
    }
}

void MainWidget::newLocalConnection()
{
    QLocalSocket *socket = m_server->nextPendingConnection();
    if (!socket)
        return;

    socket->waitForReadyRead(1000);
    QByteArray msg = socket->readAll();    // 第二个实例发来的消息，第十一章用
    delete socket;
}

listen() 失败要处理 AddressInUseError。程序上次被强杀，Unix 系的 socket 文件还躺在 /tmp 里，listen() 会失败。先删掉残留文件再监听，是这段代码里唯一容易被删掉、删掉后又出一个「偶发启动失败」的地方。Qt 5.10 起还有 QLocalServer::removeServer(name)，比自己 QFile::remove 干净，Windows 上的命名管道也能清。

判断放在 main() 里：

cpp
int main(int argc, char *argv[])
{
    QApplication app(argc, argv);

    MainWidget w;
    if (!w.isRunning()) {
        w.showNormal();
        w.raise();
        w.activateWindow();
        return app.exec();
    }
    return 0;
}

10.2 QSharedMemory #

思路：用一段共享内存当「占位牌」。能创建成功说明没人占，attach() 成功说明别人已经占了。

cpp
int main(int argc, char *argv[])
{
    QApplication app(argc, argv);
    QSharedMemory shared_memory;
    shared_memory.setKey("MyApp_SingleInstance_Key");

    if (shared_memory.attach()) {
        return 0;                 // 已有一个实例在跑,直接退
    }
    if (shared_memory.create(1)) {
        MainWidget w;
        w.showNormal();
        w.raise();
        w.activateWindow();
        return app.exec();
    }
    return 0;
}

create(1) 分配 1 字节，占个位而已，内容不重要。判断「是否已有实例」靠 attach()，不是靠读那 1 字节。

**这个方案的已知缺陷在 Linux 上。**共享内存在进程崩溃时不会被系统回收，段还挂在系统里。下次启动 attach() 依然成功，程序认定「已有实例」，于是拒绝启动——用户再也打不开这个程序，直到手动删掉段或者重启。这是 QSharedMemory 在 Unix 上的老问题，不是代码写错了；Windows 上内核对象随进程销毁自动释放，没有这个现象。

绕过办法只有两个：一是让程序在 Linux 上换用 QLocalServer 或 QLockFile；二是 attach() 成功后再判断持有者 pid 是否还活着，pid 不在就强制 detach() 覆盖，这要读 /proc 或 kill(pid, 0)，还是平台代码。

**正式项目用 QLocalServer，别用 QSharedMemory。**它多写二十行，换来崩溃后能自愈。

10.3 QLockFile #

思路：用一个锁文件占位。Qt 5.1 起提供，自己处理了「进程死了锁没释放」的陈旧锁问题。

cpp
int main(int argc, char *argv[])
{
    QApplication app(argc, argv);

    QLockFile lock(QDir::tempPath() + "/MyApp.lock");
    lock.setStaleLockTime(0);          // 由 tryLock 的时长控制

    if (!lock.tryLock(100)) {
        return 0;                      // 拿不到锁 = 已有实例
    }

    MainWidget w;
    w.show();
    return app.exec();                 // lock 在作用域结束时析构并解锁
}

tryLock(0) 立即返回，tryLock(100) 最多等 100 毫秒。默认陈旧锁阈值是 30 秒：锁文件里的时间戳超过 30 秒没更新，QLockFile 就认定持有者已死，自动清掉。

锁文件要放在 QDir::tempPath()，不要放在安装目录。安装目录在 Windows 的 Program Files 下，普通用户没有写权限，tryLock() 会一直失败，程序永远起不来。

10.4 怎么选 #

你的情况 选
需要把第二个实例的参数传给第一个 QLocalServer
只要拦掉第二个，不需要传数据 QLockFile
代码从别处搬来，已经在用共享内存 保留，但补上 pid 存活检测
要兼容 Linux 且不能加平台代码 QLocalServer

十一、单实例与二次唤醒 #

11.1 只拦掉不够 #

第二个实例退出了，但用户的诉求还没满足。他双击图标，是希望看到那个程序。所以第二个实例退出之前要做三件事：

  1. 通知已有实例「用户又点了图标」
  2. 已有实例把窗口从最小化恢复、提到最前、激活
  3. 第二个实例退出

showNormal() + raise() + activateWindow() 这三个连着调，是「把窗口顶到前面」的标准动作，少一个效果都不一样：showNormal() 只恢复最小化，raise() 只管 Z 序，activateWindow() 才抢焦点。Windows 上有前台窗口锁定，后台程序抢焦点会被系统拦下，任务栏图标闪一下了事，这是系统行为，不是代码没写对。

11.2 用 socket 传消息 #

第二个实例连上之后，先发一条消息再退出：

cpp
void MainWidget::initLocalConnection()
{
    m_isRunning = false;
    const QString serverName = QCoreApplication::applicationName();

    QLocalSocket socket;
    socket.connectToServer(serverName);
    if (socket.waitForConnected(500)) {
        m_isRunning = true;
        socket.write("raise");              // 唤醒指令
        socket.flush();
        socket.waitForBytesWritten(500);
        socket.disconnectFromServer();
        return;
    }
    // ... 建服务端的代码同前
}

服务端在 newLocalConnection() 里读到 "raise"，就把自己的窗口顶上来：

cpp
void MainWidget::newLocalConnection()
{
    QLocalSocket *socket = m_server->nextPendingConnection();
    if (!socket)
        return;

    connect(socket, &QLocalSocket::readyRead, this, [this, socket]() {
        QByteArray msg = socket->readAll();
        if (msg.startsWith("raise")) {
            showNormal();
            raise();
            activateWindow();
        }
    });
    connect(socket, &QLocalSocket::disconnected,
            socket, &QLocalSocket::deleteLater);
}

注意这里是等 readyRead 信号再读，不是立刻 readAll()。第二个实例连上之后数据还没写完，立刻读会得到空字节。用 waitForReadyRead(1000) 也行，但那是阻塞等待，GUI 线程里能避就避。

消息别只发一个裸字符串。很快会出现新需求：第二个实例要把命令行参数、文件路径一起交给第一个实例。约定一行 JSON 就够，比如 {"cmd":"open","args":["C:\\a.myapp"]}，用 \n 收尾，服务端按行读、按 cmd 分发。用户双击一个 .myapp 文件时，系统拉起新实例，新实例把路径转发给老实例就退出，用户看到的是老实例里打开了文件。

11.3 检查的位置要早 #

单实例检查要在窗口创建之前、事件循环启动之前做完。放到窗口构造之后，用户会看到窗口闪一下再关掉。

顺序是：QApplication → 单实例检查 → 建窗口或者退出。用 QSharedMemory 时这个顺序不能变，因为 QApplication 之前拿不到 applicationName()。

十二、易错点速查 #

现象 原因 处理
start() 后立刻读输出，拿到空 进程还没起来，异步 等 readyReadStandardOutput()
start("带参数的命令") 直接失败 整条命令当成了程序名 用 QStringList 分开传
start("dir") 报 FailedToStart dir 是 cmd 内置命令 cmd /c dir
ps -ef | grep 找不到程序 管道是 shell 语法 bash -c "..."
写完 write("dir") 毫无反应 缺换行符 write("dir\r\n")
gzip 一直不结束 没关写通道 closeWriteChannel()
界面卡住几十秒 主线程调了 waitFor* 改信号槽或用工作线程
中文输出全是问号 编码选错 试 fromLocal8Bit() / fromUtf8()
子进程写了一半文件 退出时只 kill() 先 terminate()，超时再 kill()
主程序关了，外部程序还在跑 没做清理 析构或 aboutToQuit 里终止
kill() 后孙子进程还在 只杀了直接子进程 Windows taskkill /T，Linux 杀进程组
环境变量设完，子进程连 ls 都找不到 setProcessEnvironment() 整体替换 用 systemEnvironment() 打底
第二个实例退出了，窗口没出来 没做唤醒 QLocalSocket 发消息 + activateWindow()

这张表里的每一条，都是「代码能编译、运行时行为不对」的类型。QProcess 的错误不抛异常，只会安静地不工作，或者安静地卡住。整篇的主线也就两句：QProcess 是异步的，start() 返回时进程还没起来，输出要等信号；单实例别用共享内存，QLocalServer 或 QLockFile 才是能长期跑的选择。

外部进程和单实例这两件事经常一起出现：你的程序既要保证自己只跑一个，又要管好自己拉起来的那些进程。前者靠一个本地名字，后者靠退出路径上的三行清理代码——都不复杂，复杂的是漏掉它们之后要面对的现场。
