本篇只讲 Qt 网络模块的骨架：QTcpSocket、QTcpServer、QUdpSocket、QNetworkAccessManager，外加 QHostInfo、QNetworkInterface 这一组查本机网络信息的类。重点三件事：把「异步、信号驱动」说透，把 TCP 粘包的应用层处理说透，把 HTTP 请求里 Manager 复用与抓包调试说透。

不讲成型的网络应用（下载器、聊天室、文件收发器），那些在同目录的《网络应用实例》里。串口走的是 QSerialPort，属于另一套 IO 模型，见《串口通信》。回包里的 JSON 与 XML 怎么解析，见《JSON 与 XML》，本篇只在 HTTP 那章点到。进程间通信、数据库连接不在本篇范围内。

代码按 Qt 5 / Qt 6 通用的写法给，只在 Qt 6 才有的接口会单独标注。

一、Qt 网络模块的组成 #

网络能力不在 Qt Core 里，它在 QtNetwork 子模块。第一步永远是改工程文件。

QT += network

CMake 工程换成 find_package(Qt6 REQUIRED COMPONENTS Network) 加 target_link_libraries(你的目标 PRIVATE Qt6::Network)。模块名和链接目标少了任何一个，链接期就找不到符号。

头文件按需引入：

cpp
#include <QTcpSocket>
#include <QTcpServer>
#include <QUdpSocket>
#include <QNetworkAccessManager>
#include <QNetworkRequest>
#include <QNetworkReply>
#include <QHostInfo>
#include <QHostAddress>
#include <QNetworkInterface>
#include <QNetworkAddressEntry>

1.1 三套网络类，三种抽象层级 #

Qt 把网络能力分成三层。用哪一层，取决于你对面坐的是谁。

层级 代表类 对面是什么 有连接吗 边界要自己处理吗
应用层协议 QNetworkAccessManager + QNetworkRequest / QNetworkReply HTTP / HTTPS 服务器 有，连接池内部托管 不用，一个请求对应一个 QNetworkReply
传输层字节流 QTcpSocket / QTcpServer 任意 TCP 端点 有，三次握手 必须，字节流没有消息边界
传输层数据报 QUdpSocket 任意 UDP 端点 无 不用，一报一边界，但会丢、会乱序

三层的差别不在 API 好不好看，在「谁负责切消息」。HTTP 由协议自己定义了 Content-Length 和 chunked 分块，你拿到的就是一个完整回包。TCP 什么都没有，它只保证字节按序到达，至于这一堆字节从哪里切开，全靠应用层自己约定。UDP 帮你切好了，代价是不保证送达。

1.2 核心类速查 #

类名 职责 关键点
QNetworkAccessManager HTTP/HTTPS 请求总调度 一个应用一个实例，内部带连接池、Cookie、缓存
QNetworkRequest 描述一个出站请求 URL、请求头、超时、重定向策略
QNetworkReply 承载一次回包 是 QIODevice，用 finished 信号通知，必须 deleteLater()
QTcpSocket TCP 客户端与连接实体 是 QIODevice，read / write 和读写文件一个手感
QTcpServer TCP 监听与 Accept newConnection 信号，重写 incomingConnection 可接管多线程
QUdpSocket UDP 数据报 支持单播、广播、组播
QSslSocket 加密套接字 接口与 QTcpSocket 兼容，需要 OpenSSL
QHostInfo 主机名与 DNS 解析 fromName 派生类同名静态接口有阻塞版和异步版两套
QNetworkInterface 本机网卡枚举 allInterfaces / allAddresses
QNetworkAddressEntry 网卡上的一组 IP 三元组 IP、掩码、广播地址

1.3 一个绕不开的前提：它们全是异步的 #

这是 Qt 网络编程的第一课，也是最容易翻车的一课。

cpp
QTcpSocket socket;
socket.connectToHost("127.0.0.1", 8080);
// 走到这一行，连接还没建立
socket.write("hello");   // 什么也发不出去

connectToHost 只是把连接请求丢进了事件循环，函数返回时状态还是 ConnectingState。真正的连接完成要靠 connected() 信号告诉你。数据同理，write 只是把数据塞进 Qt 的发送缓冲区，什么时候真正上线由内核决定；对端来了数据，Qt 发 readyRead() 通知你。

这条规则对 QNetworkAccessManager 一样成立：get() / post() 立刻返回，回包在 finished 里拿。

为什么这么设计？GUI 主线程只有一个事件循环，任何阻塞调用都会让界面停止重绘、停止响应点击。想拿同步语义，得自己套一层事件循环，代价在第七章说。

二、QTcpSocket 与 QTcpServer #

2.1 QTcpSocket 是 QIODevice #

继承链是 QObject → QIODevice → QAbstractSocket → QTcpSocket。这条链决定了你能白拿一堆能力：

能力 接口 说明
读 read / readAll / readLine / peek 和读 QFile 一模一样
写 write / writeData 写入缓冲区，返回实际接受字节数
可读字节数 bytesAvailable() 在 readyRead 里判断长度最方便
就绪通知 readyRead() 信号 有新数据到达
写完通知 bytesWritten(qint64) 信号 缓冲区里的数据真正发出去了
事务 startTransaction / commitTransaction / rollbackTransaction 读一半发现不够时可以回滚

所以「用 QTcpSocket 收文件」和「用 QFile 读文件」在代码结构上可以写得非常像，差别只在于数据什么时候到不由你决定。

2.2 状态机 #

QAbstractSocket::SocketState 一共有六个状态，排查问题时按状态看最直接。

状态 含义 到了这个状态该做什么
UnconnectedState 未连接 初始状态，或断开之后
HostLookupState 正在解析主机名 域名解析要走 DNS，耗时不固定
ConnectingState 正在握手 此阶段 write 的数据会进缓冲，连上后补发
ConnectedState 已连接 可以正常收发
BoundState 已绑定端口（UDP / 服务端） UDP 监听中
ClosingState 正在关闭 还有数据没发完

配套的信号：stateChanged(SocketState)、connected()、disconnected()、hostFound()、readyRead()、bytesWritten(qint64)、errorOccurred(SocketError)。Qt 5.15 之前错误信号叫 error()，和取错误码的 error() 函数重名，后来改成了 errorOccurred。写新代码用后者。

2.3 套接字有「线程归属」 #

这一点比状态机更容易踩。每个 QObject 都有一个所属线程，QTcpSocket 内部的 QSocketNotifier 必须跑在套接字所属的那个线程里。你在别的线程调它的方法，运行时会甩出：

text
QSocketNotifier: socket notifiers cannot be enabled from another thread

规则很硬：套接字对象在哪个线程创建，它的接口就只能在哪个线程调用。想让它跑在子线程，两条路：

  1. 把套接字对象本身 moveToThread 到子线程；
  2. 让套接字在子线程里被创建（在 Worker 的槽函数里 new）。

两者都要求：之后所有对它的调用，都要转换到它所在的线程执行。具体做法见第三章。

有个实测结论值得记下来：如果一个 TCP 对象被归属到子线程 X，那么 readyRead、connected、disconnected 这些信号的发射线程，都是 X。不是主线程。

2.4 QTcpServer 的四个接口 #

QTcpServer 本身很薄，常用的就五个接口：listen(QHostAddress, quint16) 开始监听，端口传 0 由系统分配；serverPort() 读回实际端口，单元测试里好用；isListening() 查状态；close() 停掉监听；hasPendingConnections() 判断有没有待取连接。

cpp
QTcpServer server;
if (!server.listen(QHostAddress::Any, 8080))      // Any 表示所有网卡
    qWarning() << "listen failed" << server.errorString();
quint16 port = server.serverPort();
server.close();

有新连接进来时，newConnection() 信号发出。在槽里取套接字：

cpp
connect(&server, &QTcpServer::newConnection, this, [&]() {
    while (server.hasPendingConnections()) {
        QTcpSocket *client = server.nextPendingConnection();
        // client 的 parent 是 server，不用手动删
        connect(client, &QTcpSocket::readyRead, this, [client]() {
            qDebug() << client->readAll();
        });
        connect(client, &QTcpSocket::disconnected, client, &QObject::deleteLater);
    }
});

注意两点。nextPendingConnection 拿到的套接字父对象是 server，销毁由 server 兜底，但更稳的做法是在 disconnected 后 deleteLater，否则高并发下对象会一直攒着。循环用 while (hasPendingConnections()) 而不是 if，因为一次事件循环里会积压多个连接。

真正想接管连接、自己安排线程时，重写 incomingConnection(qintptr socketDescriptor)。这是第四章的内容。

要加密就把 QTcpSocket 换成 QSslSocket，接口兼容。客户端用 connectToHostEncrypted(host, port)；服务端先 setLocalCertificate("server.crt")、setPrivateKey("server.key")，再 startServerEncryption()。底下的 OpenSSL 要能加载，否则握手直接失败。

三、写一个 TCP 客户端 #

3.1 最小可用客户端 #

先写一个能跑的最小版本，所有信号都用上，把流程看全。

cpp
class TcpClient : public QObject
{
    Q_OBJECT
public:
    explicit TcpClient(QObject *parent = nullptr) : QObject(parent)
    {
        m_socket = new QTcpSocket(this);

        connect(m_socket, &QTcpSocket::connected, this, [this]() {
            qDebug() << "connected, local port" << m_socket->localPort();
            m_socket->write("hello server\r\n");
        });

        connect(m_socket, &QTcpSocket::readyRead, this, [this]() {
            QByteArray chunk = m_socket->readAll();
            qDebug() << "recv" << chunk.size() << "bytes";
        });

        connect(m_socket, &QTcpSocket::disconnected, this, []() {
            qDebug() << "peer closed";
        });

        connect(m_socket, &QTcpSocket::errorOccurred, this,
                [this](QAbstractSocket::SocketError e) {
            qWarning() << "error" << e << m_socket->errorString();
        });
    }

    void start(const QString &host, quint16 port)
    {
        m_socket->connectToHost(host, port);   // 立刻返回，还没连上
    }

private:
    QTcpSocket *m_socket = nullptr;
};

注意 errorOccurred 是 Qt 5.15 起的新名字。老工程里写 QOverload<QAbstractSocket::SocketError>::of(&QTcpSocket::error)，或者直接 SIGNAL(error(QAbstractSocket::SocketError))。

3.2 connectToHost 之后别急着 write #

新手最常写的顺序是：

cpp
socket->connectToHost(host, port);
socket->waitForConnected(3000);
socket->write(data);

这能跑，但 waitForConnected 会挂住当前线程。主线程里挂住就是界面假死。

正确姿势是把 write 放进 connected 的槽里。如果确实有数据要抢在连接前塞进去，也可以直接 write——Qt 会把它存进写缓冲区，连接建立后自动补发。但这个行为只对 ConnectingState 成立，连接失败时缓冲区里的数据就丢了，不会有任何提示。所以还是等信号更实在。

3.3 放进子线程：Worker + moveToThread #

高频收发会占满主线程的事件循环，界面就一顿一顿。标准解法是 Worker + moveToThread，不要继承 QThread。

分工是这样的：

  1. Worker 类继承 QObject，里面持有 QTcpSocket 指针；
  2. 主线程创建 QThread 和 Worker；
  3. Worker moveToThread 进新线程；
  4. 所有对套接字的操作，都通过信号或 QMetaObject::invokeMethod 投递到 Worker 线程执行。
cpp
class TcpWorker : public QObject
{
    Q_OBJECT
    QTcpSocket *m_socket = nullptr;

public slots:
    void doConnect(const QString &host, quint16 port)
    {
        // 关键：套接字在这个线程里创建，归属才对
        m_socket = new QTcpSocket(this);

        connect(m_socket, &QTcpSocket::readyRead, this, [this]() {
            QByteArray data = m_socket->readAll();
            // 这里补粘包处理，见第十一章
            emit messageReceived(data);
        });
        connect(m_socket, &QTcpSocket::disconnected, this, [this]() {
            m_socket->deleteLater();
            m_socket = nullptr;
            emit closed();
        });

        m_socket->connectToHost(host, port);
    }

    void doSend(const QByteArray &data)
    {
        if (m_socket && m_socket->state() == QAbstractSocket::ConnectedState)
            m_socket->write(data);
    }

    void doDisconnect()
    {
        if (m_socket) m_socket->disconnectFromHost();
    }

signals:
    void messageReceived(const QByteArray &data);
    void closed();
};

主线程那一侧：

cpp
void setupThread()
{
    QThread *thread = new QThread;
    TcpWorker *worker = new TcpWorker;      // 不能指定 parent
    worker->moveToThread(thread);

    // 线程生命周期：线程结束，Worker 跟着回收
    connect(thread, &QThread::finished, worker, &QObject::deleteLater);
    connect(thread, &QThread::finished, thread, &QObject::deleteLater);
    thread->start();

    // 跨线程调用 doConnect：方式一用信号（推荐），方式二用 invokeMethod
    // connect(this, &MainWindow::requestConnect, worker, &TcpWorker::doConnect);
    // emit requestConnect("127.0.0.1", 8080);
    QMetaObject::invokeMethod(worker, "doConnect",
                              Q_ARG(QString, "127.0.0.1"), Q_ARG(quint16, 8080));
}

这里有个坑要写死在脑子里：套接字必须在 doConnect 里 new，不能在 TcpWorker 的构造函数里 new。构造函数跑在主线程，那时 Worker 还没 moveToThread，套接字跟着落在主线程，之后在子线程里操作它就报 QSocketNotifier 的错。

worker 不能带 parent，因为它要 moveToThread。带 parent 的对象不能跨线程搬。同理，thread->finished 连到 worker->deleteLater，是让 Worker 随线程一起回收。

3.4 另一种封装：继承 QTcpSocket 用信号转发 #

有些老工程走的是另一条路：直接继承 QTcpSocket，把「跨线程调用」这件事用信号转发掉。这个类的设计要点是——所有对外接口都只发信号，真正的操作在内部槽里执行。

cpp
// tcp_client.h
#pragma once
#include <QTcpSocket>

class TcpClient : public QTcpSocket
{
    Q_OBJECT
public:
    explicit TcpClient(QObject *parent = nullptr);
    void clientConnectToHost(const QString &address, quint16 port);
    void clientSendData(const QByteArray &data);
    bool isOnline() const { return m_online; }

signals:
    void requestConnect(const QString &address, quint16 port);
    void requestSend(const QByteArray &data);
    void publishFrame(const QString &frame);   // 解析完的整条消息

private:
    bool m_online = false;
    QByteArray m_buffer;      // 半个包先攒着
};

cpp
// tcp_client.cpp
TcpClient::TcpClient(QObject *parent) : QTcpSocket(parent)
{
    // AutoConnection：发射时判断，跨线程自动转队列连接
    connect(this, &TcpClient::requestConnect, this,
            [this](const QString &address, quint16 port) {
        connectToHost(address, port, QIODevice::ReadWrite);
    }, Qt::AutoConnection);

    connect(this, &QAbstractSocket::connected, this, [this]() {
        m_online = true;
    }, Qt::DirectConnection);

    connect(this, &QAbstractSocket::disconnected, this, [this]() {
        m_online = false;
    }, Qt::DirectConnection);

    connect(this, &QIODevice::readyRead, this, [this]() {
        m_buffer.append(readAll());
        int pos = m_buffer.indexOf("\r\n");
        while (pos != -1) {
            QString frame = QString::fromUtf8(m_buffer.left(pos));
            emit publishFrame(frame);
            m_buffer.remove(0, pos + 2);
            pos = m_buffer.indexOf("\r\n");
        }
    }, Qt::DirectConnection);

    connect(this, &TcpClient::requestSend, this, [this](const QByteArray &data) {
        write(data);
    }, Qt::AutoConnection);
}

void TcpClient::clientConnectToHost(const QString &address, quint16 port)
{
    emit requestConnect(address, port);       // 跨线程的唯一入口
}

void TcpClient::clientSendData(const QByteArray &data)
{
    emit requestSend(data);
}

主线程这样用：

cpp
m_tcpClient = new TcpClient();
m_thread = new QThread();
m_tcpClient->moveToThread(m_thread);   // 套接字整体搬到子线程
m_thread->start();

connect(ui.pushButtonConnect, &QPushButton::clicked, this, [this]() {
    m_tcpClient->clientConnectToHost(m_ip, SERVER_PORT);
});

// 子线程 -> 主线程，队列连接，UI 更新安全
connect(m_tcpClient, &TcpClient::publishFrame, this, [this](const QString &frame) {
    ui.textEdit->append(frame);
    if (ui.textEdit->toPlainText().size() > 2 * 1024 * 1024)
        ui.textEdit->clear();      // 日志滚太长就清空
}, Qt::AutoConnection);

两种封装各有取舍。Worker 方案里套接字是 Worker 的私有成员，外部碰不到，封装更干净。继承方案省掉了 Worker 这一层，但套接字自己的公开接口还暴露着，谁手一抖在错误线程直接 write，问题就来了。新代码走 Worker。

3.5 连接类型怎么选 #

connect 的第五个参数经常被忽略，默认是 Qt::AutoConnection，行为在信号发射的那一刻才确定。

类型 行为 什么场景用
Qt::AutoConnection 同线程走直接调用，跨线程转队列 默认值，九成场景用它
Qt::DirectConnection 立刻在发射信号的线程里同步调用 确认槽函数不碰 UI、且必须立刻生效
Qt::QueuedConnection 投递到接收者线程的事件循环，稍后执行 明确要异步、要脱离当前调用栈
Qt::BlockingQueuedConnection 投递并阻塞等待槽返回 同线程用会死锁，慎用
Qt::UniqueConnection 与前面按位或，防重复连接 可和以上任一组合

这里有个实测结论：readyRead 用 DirectConnection 连接，槽里的 QThread::currentThreadId() 打印出来是子线程 ID。这说明信号确实是从套接字所在线程发出的，套接字的线程归属决定了信号发射线程。

还有一个细节容易看漏：用 lambda 当槽时，connect(sender, signal, functor) 这个三参数版本没有连接类型参数，默认按直接连接处理。要指定类型，得用五参数版本，把接收者对象 context 显式传进去：

cpp
// 三参数：没有连接类型，按直接连接
connect(sender, &Sender::sig, [](){ /* ... */ });

// 五参数：可以指定类型
connect(sender, &Sender::sig, this, [](){ /* ... */ }, Qt::QueuedConnection);

Qt::UniqueConnection 对 lambda 不生效，别指望用它去重。

AutoConnection 的判定时机也值得说一句：是在 emit 的时候判定，不是 connect 的时候。所以先 moveToThread 还是先 connect，顺序不影响结果。

四、写一个 TCP 服务端 #

4.1 单线程服务端 #

连接数不多、每个连接的数据量也不大时，单线程服务端足够，代码也最短。

cpp
class SimpleServer : public QObject
{
    Q_OBJECT
public:
    bool start(quint16 port)
    {
        connect(&m_server, &QTcpServer::newConnection, this, &SimpleServer::onNewConnection);
        return m_server.listen(QHostAddress::Any, port);
    }

private slots:
    void onNewConnection()
    {
        while (m_server.hasPendingConnections()) {
            QTcpSocket *client = m_server.nextPendingConnection();

            connect(client, &QTcpSocket::readyRead, this, [client]() {
                client->write("echo:" + client->readAll());
            });
            connect(client, &QTcpSocket::disconnected, client, &QObject::deleteLater);
        }
    }

private:
    QTcpServer m_server;
};

QHostAddress::Any 是双栈监听，IPv4 和 IPv6 都收。只想听 IPv4 写 QHostAddress::AnyIPv4，只想听本机写 QHostAddress::LocalHost。端口传 0 让系统分配，再用 serverPort() 读回来，做单元测试时很方便。

4.2 多线程 Accept：重写 incomingConnection #

连接一多，单线程里所有套接字挤一个事件循环，一个慢客户端就能拖住所有人。这时重写 incomingConnection，给每个连接配一个线程。

cpp
class ThreadedServer : public QTcpServer
{
    Q_OBJECT
protected:
    void incomingConnection(qintptr socketDescriptor) override
    {
        QThread *thread = new QThread;
        ClientHandler *handler = new ClientHandler(socketDescriptor);

        handler->moveToThread(thread);
        connect(thread, &QThread::started, handler, &ClientHandler::process);
        connect(handler, &ClientHandler::finished, thread, &QThread::quit);
        connect(handler, &ClientHandler::finished, handler, &QObject::deleteLater);
        connect(thread, &QThread::finished, thread, &QObject::deleteLater);

        thread->start();
    }
};

关键参数是 qintptr socketDescriptor——一个已经建立好的原生套接字句柄。注意：重写之后 newConnection 信号不会再发出，nextPendingConnection 也没东西可取，连接全归你自己管。

4.3 ClientHandler 的阻塞写法 #

在独立线程里干活，反而可以用阻塞 API，代码直白很多。

cpp
class ClientHandler : public QObject
{
    Q_OBJECT
public:
    explicit ClientHandler(qintptr descriptor) : m_descriptor(descriptor) {}

public slots:
    void process()
    {
        QTcpSocket socket;   // 栈上对象，线程内生命周期干净
        if (!socket.setSocketDescriptor(m_descriptor)) {
            emit finished();
            return;
        }

        // 独立线程里阻塞等待，不拖累别人
        while (socket.state() == QAbstractSocket::ConnectedState) {
            if (!socket.waitForReadyRead(30000))
                break;
            QByteArray data = socket.readAll();
            // 业务处理
            socket.write("ok\r\n");
            socket.waitForBytesWritten(5000);
        }

        socket.disconnectFromHost();
        emit finished();
    }

signals:
    void finished();

private:
    qintptr m_descriptor;
};

setSocketDescriptor 把原生句柄接管过来，套接字就归这个线程了。这里用阻塞 waitForReadyRead 是合理的：这个线程只服务这一个连接，阻塞它不会影响别人。主线程里这么写就是灾难。

一个连接一个线程的代价是线程数随连接数线性上涨，几千连接就撑不住了。真上量要换事件驱动模型或者 IO 复用，那已经超出 Qt 网络模块的舒适区。

五、QUdpSocket：无连接的传输 #

5.1 收发数据报 #

UDP 没有握手，绑上端口就能收发。

cpp
QUdpSocket udp;
if (!udp.bind(QHostAddress::AnyIPv4, 9999)) {
    qWarning() << "bind failed" << udp.errorString();
    return;
}

connect(&udp, &QUdpSocket::readyRead, this, [&udp]() {
    // 一次 readyRead 里堆着多个数据报，必须 while 取干净
    while (udp.hasPendingDatagrams()) {
        QNetworkDatagram dgram = udp.receiveDatagram();
        qDebug() << "from" << dgram.senderAddress().toString()
                 << dgram.senderPort()
                 << "size" << dgram.data().size()
                 << "data" << dgram.data();
    }
});

// 发送
udp.writeDatagram("hello", QHostAddress("192.168.1.100"), 8888);

hasPendingDatagrams() 加 while 是必须的。一个 UDP 包到一个 readyRead 事件，但事件循环忙的时候会把多个包攒在一次通知里给你，只读一次就漏包。这和 TCP 的 readAll 是同一个思路：能读多少读多少。

老写法是 readDatagram(char*, qint64, QHostAddress*, quint16*)，自己开一块 64 KB 缓冲区接。Qt 5.8 之后有了 QNetworkDatagram，封装发送方地址、端口、目的地址，还能顺带取 hopLimit，新代码用它。

5.2 广播与组播 #

广播往网段广播地址发，或者直接发 QHostAddress::Broadcast（255.255.255.255）。设备发现就是这套路子：丢一个包出去，谁应答谁在线。路由器不转发广播，所以只在本局域网里转。

cpp
// 发广播
udp.writeDatagram("discover", QHostAddress::Broadcast, 9999);

// 收广播：绑端口并允许端口复用，本机才能收到自己发的广播
udp.bind(9999, QUdpSocket::ShareAddress | QUdpSocket::ReuseAddressHint);

要跨网段就用组播。绑定后加入组播组，组里所有成员都能收到，交换机只在你加入之后才把流量转给你：

cpp
if (!udp.bind(QHostAddress::AnyIPv4, 45454, QUdpSocket::ShareAddress)) {
    qWarning() << "bind failed";
    return;
}
udp.joinMulticastGroup(QHostAddress("224.0.0.100"));
// 离开：udp.leaveMulticastGroup(QHostAddress("224.0.0.100"));

5.3 TCP 与 UDP 怎么选 #

维度 TCP UDP
连接 三次握手，有连接状态 无连接，发完就不管
可靠性 不丢、不重、按序 会丢、会重、会乱序
消息边界 没有，字节流，要自己划 有，一个数据报一个边界
单包大小 不限，靠分片重组 单包上限约 64 KB，实际受 MTU 限制
开销 头 20 字节起，有握手与确认 头 8 字节，没有确认
延迟 有重传，抖动大 低，适合实时
一对一 / 一对多 只能一对一 单播、广播、组播都行
典型用途 文件传输、HTTP、登录鉴权 视频流、语音、设备发现、日志上报

一句判断标准：数据丢一条就出问题，用 TCP；丢一条只是少一帧画面，用 UDP。

六、QNetworkAccessManager：HTTP 请求 #

6.1 三个类，一条链 #

QNetworkAccessManager 只负责发起和分发，请求本身由 QNetworkRequest 描述，回包由 QNetworkReply 承载。

类 干什么 什么时候创建
QNetworkAccessManager 发起请求、分发回包、管理连接与 Cookie 整个应用一个，成员变量
QNetworkRequest 装 URL、请求头、超时、重定向策略 每次请求一个，栈上即可
QNetworkReply 装状态码、回包体、错误信息 由 Manager 创建，你要负责删

6.2 GET 请求 #

cpp
void HttpApi::fetchUser(int id)
{
    QNetworkRequest req(QUrl(QString("https://api.example.com/user/%1").arg(id)));
    req.setHeader(QNetworkRequest::UserAgentHeader, "MyQtApp/1.0");
    req.setRawHeader("Accept", "application/json");

    QNetworkReply *reply = m_manager->get(req);

    connect(reply, &QNetworkReply::finished, this, [this, reply]() {
        if (reply->error() == QNetworkReply::NoError) {
            QJsonObject obj = QJsonDocument::fromJson(reply->readAll()).object();
            emit userReady(obj);
        } else {
            qWarning() << "GET failed" << reply->errorString();
            emit failed(reply->errorString());
        }
        reply->deleteLater();     // 必须
    });
}

reply->readAll() 只能在 finished 之后读。想在下载过程中显示进度，连 readyRead 和 downloadProgress(qint64, qint64) 信号。

6.3 POST 表单 #

登录接口不走 URL 参数，走 POST 体，内容类型 application/x-www-form-urlencoded。

cpp
void HttpApi::sendLogin(const QString &user, const QString &pwd)
{
    QNetworkRequest req;
    req.setUrl(QUrl("http://10.0.33.5:80/cloudstor/index.php?r=api/user/login"));

    QByteArray body;
    body += "user=" + user.toUtf8() + "&password=" + pwd.toUtf8() +
            "&domain=sugon&client=windowstool&version=1.1.1.1";

    req.setHeader(QNetworkRequest::ContentTypeHeader,
                  "application/x-www-form-urlencoded");
    req.setHeader(QNetworkRequest::ContentLengthHeader, body.length());

    QNetworkReply *reply = m_manager->post(req, body);
    connect(reply, &QNetworkReply::finished, this, [this, reply]() {
        onLoginFinished(reply);
    });
}

两个头别漏。ContentTypeHeader 漏了，服务端解析不出表单；ContentLengthHeader 不设 Qt 也会补，但显式写更清楚。

处理回包时把状态码和错误分开看：

cpp
void HttpApi::onLoginFinished(QNetworkReply *reply)
{
    if (!reply) return;

    QVariant code = reply->attribute(QNetworkRequest::HttpStatusCodeAttribute);
    qDebug() << "HTTP status" << code.toInt();

    if (reply->error() == QNetworkReply::NoError) {
        QByteArray bytes = reply->readAll();
        qDebug() << "body" << QString::fromUtf8(bytes);
    } else {
        qDebug() << "network error" << reply->errorString();
    }
    reply->deleteLater();
}

状态码和 error() 是两套东西。服务端返回 404、500，error() 都不是 NoError，回包体还在，该读还是要读出来——错误页里经常带着服务端的报错原因，丢掉就查不到原因了。

释放回包只能用 deleteLater()，不能 delete reply。finished 发出来的时候，QNetworkReply 内部还有些清理事件挂在当前事件循环里，直接析构就是野指针。

6.4 POST JSON #

cpp
QNetworkRequest req(QUrl("https://api.example.com/device/report"));
req.setHeader(QNetworkRequest::ContentTypeHeader, "application/json");

QJsonObject obj;
obj["sn"] = "SN20240001";
obj["status"] = 1;
obj["ts"] = QDateTime::currentSecsSinceEpoch();

QNetworkReply *reply = m_manager->post(req, QJsonDocument(obj).toJson(QJsonDocument::Compact));

toJson() 默认带缩进，toJson(QJsonDocument::Compact) 输出紧凑格式。回包解析是 QJsonDocument::fromJson(...)，细节见《JSON 与 XML》。

6.5 文件上传 #

表单文件上传用 QHttpMultiPart 拼 multipart/form-data：

cpp
QHttpMultiPart *multiPart = new QHttpMultiPart(QHttpMultiPart::FormDataType);

QHttpPart textPart;
textPart.setHeader(QNetworkRequest::ContentDispositionHeader, QVariant("form-data; name=\"desc\""));
textPart.setBody("firmware upgrade");

QHttpPart filePart;
filePart.setHeader(QNetworkRequest::ContentTypeHeader, QVariant("application/octet-stream"));
filePart.setHeader(QNetworkRequest::ContentDispositionHeader,
                   QVariant("form-data; name=\"file\"; filename=\"fw.bin\""));
QFile *file = new QFile("fw.bin");
file->open(QIODevice::ReadOnly);
filePart.setBodyDevice(file);
file->setParent(multiPart);              // 文件对象挂到 multiPart 上

multiPart->append(textPart);
multiPart->append(filePart);

QNetworkReply *reply = m_manager->post(req, multiPart);
multiPart->setParent(reply);             // multipart 再挂到回包上

file->setParent(multiPart) 和 multiPart->setParent(reply) 这两行不是可选项。生命周期一路挂到回包上，否则 reply->deleteLater() 之后这两个对象泄漏着。

6.6 Manager 必须复用 #

这是 HTTP 这一章最要紧的一条。QNetworkAccessManager 内部维护连接池、DNS 缓存、Cookie、认证信息，一个 Manager 就是一个会话。

cpp
// 错：每次请求 new 一个
void bad() {
    QNetworkAccessManager *m = new QNetworkAccessManager(this);  // 越攒越多
    m->get(req);
}

// 对：全应用一个，成员变量
class HttpApi : public QObject {
    QNetworkAccessManager *m_manager = new QNetworkAccessManager(this);
};

每 new 一个 Manager 就是一套新的连接池。请求频繁时会出现两种后果：对同一个服务器开出大量并发的 TCP 连接，把本机端口和服务端的连接数上限都耗掉；每个连接都要重新握手、重新做 TLS，延迟白白翻倍。

还会出现一个更隐蔽的现象：Cookie 和 Session 全丢。因为你换了一个 Manager，上一个 Manager 里存着的会话信息就找不到了，服务端一直认为你没登录。

一个应用一个 Manager，跨线程使用它也行——QNetworkAccessManager 是线程安全的，但回包会投递到它所属的线程，所以更稳的做法是每个线程一个，别跨线程共享。

6.7 Cookie 与会话保持 #

登录成功后紧接着请求别的接口却提示「登录超时」，八成是 Cookie 没带上。服务端用 Session 维护登录态，靠 Set-Cookie 下发 Session ID，客户端后续每个请求都要回传。

QNetworkAccessManager 自带 Cookie 支持，但默认不启用持久化。开启方式：

cpp
#include <QNetworkCookieJar>

// 同一个 Manager 下的后续请求自动带上 Cookie
m_manager->setCookieJar(new QNetworkCookieJar(this));

想自己控制 Cookie 的读写（比如存盘、重启后复用），继承 QNetworkCookieJar，重写 setCookiesFromUrl 和 cookiesForUrl，在里面接上自己的存储。

6.8 设置超时 #

Qt 5.15 起有 setTransferTimeout，最省事：

cpp
m_manager->setTransferTimeout(5000);      // 单位毫秒，作用于该 Manager 所有请求

// 或者只给单个请求
req.setTransferTimeout(3000);

Qt 5.15 之前得自己挂 QTimer：

cpp
QTimer *timer = new QTimer(reply);
timer->setSingleShot(true);
connect(timer, &QTimer::timeout, reply, &QNetworkReply::abort);
timer->start(5000);
connect(reply, &QNetworkReply::finished, timer, &QTimer::stop);

没有超时的 HTTP 请求是个定时炸弹。服务端把连接一挂不断开，你的 finished 就永远不来，界面上的转圈也就永远转。

6.9 抓包与调试 #

服务端收不到参数时，别靠猜。上 Wireshark 或 Fiddler 看原始请求，四项对齐：Content-Type 是不是 application/x-www-form-urlencoded（漏了服务端解析不出表单体）；字节序列是不是 UTF-8（该 UTF-8 的用了本地编码，中文变乱码）；Content-Length 和实际字节数是否一致；第二次请求有没有带上第一次 Set-Cookie 下发的 Session ID（没带就会被判未登录）。再把 URL 里中文和特殊字符的转义核对一遍。抓到的请求和代码逐项对齐，比读服务端日志快得多。

七、同步与异步的取舍 #

7.1 四个阻塞接口 #

QAbstractSocket 提供了四个阻塞等待接口，它们内部会跑自己的事件循环：

接口 等什么 返回值
waitForConnected(int ms) 握手完成 bool
waitForReadyRead(int ms) 有数据可读 bool
waitForBytesWritten(int ms) 缓冲区数据发出 bool
waitForDisconnected(int ms) 连接断开 bool

还有一组 waitFor* 是 QIODevice 层面的：QNetworkReply 继承自 QIODevice，也有 waitForReadyRead，但 HTTP 回包靠 finished 判定更准确。

7.2 在 GUI 线程里套同步的代价 #

有时确实需要「发一个请求，等结果，再往下走」这种直线逻辑。做法是套局部事件循环：

cpp
QByteArray syncGet(const QUrl &url, int timeoutMs)
{
    QNetworkReply *reply = m_manager->get(QNetworkRequest(url));

    QEventLoop loop;
    QTimer timer;
    timer.setSingleShot(true);
    connect(reply, &QNetworkReply::finished, &loop, &QEventLoop::quit);
    connect(&timer, &QTimer::timeout, &loop, &QEventLoop::quit);
    timer.start(timeoutMs);
    loop.exec();                       // 这里会重入事件循环

    QByteArray result;
    if (reply->isFinished() && reply->error() == QNetworkReply::NoError)
        result = reply->readAll();
    reply->deleteLater();
    return result;
}

能跑，但要知道自己在干什么。loop.exec() 会重入事件循环，意味着这段时间里用户还能点按钮、还能触发别的网络请求、还能把这个函数再进一次。重入带来的时序问题，比一开始就写异步回调难查得多。

7.3 什么时候可以用阻塞 #

场景 能用阻塞吗 说明
GUI 主线程的按钮响应 不行 直接卡界面
独立工作线程里的单连接 可以 阻塞只影响这个线程
服务端每连接一线程的处理 可以 第四章 ClientHandler::process 就是这种
启动阶段的一次性探测 勉强可以 此时还没有界面要响应
单元测试 可以 要的是直线逻辑，不在乎卡

判断标准只有一条：这段阻塞代码会不会挡住必须响应的东西。

不用阻塞，代码也不一定就散。组织方式有三种：信号槽加状态机，每个网络动作一个槽，状态用枚举管住，别拿一堆 bool 拼；回包处理收拢到一个对象，避免 lambda 套 lambda；或者 QFuture + QtConcurrent，把阻塞调用丢进线程池，主线程用 QFutureWatcher 收结果。

八、获取本机网络信息 #

做监听要本机 IP，做授权要 MAC，做日志要用户名和主机名。Windows 命令行下 ipconfig /all 能看，代码里靠 QtNetwork 的四个类：QHostInfo 查主机名与 DNS，QHostAddress 装 IPv4/IPv6 地址，QNetworkInterface 枚举网卡，QNetworkAddressEntry 装网卡上的 IP、掩码、广播三元组。

8.1 登录用户名与主机名 #

环境变量用 qgetenv 读，比 getenv 返回值包装得干净。

cpp
// Windows 用 USERNAME，Linux/macOS 用 USER
QString userName = qgetenv("USERNAME");
if (userName.isEmpty())
    userName = qgetenv("USER");
qDebug() << "User Name:" << userName;      // "wangl-d"

QString hostName = QHostInfo::localHostName();
qDebug() << "Host Name:" << hostName;      // "wangl-d-pc"

8.2 主机名换 IP 列表 #

cpp
QHostInfo info = QHostInfo::fromName(QHostInfo::localHostName());
foreach (const QHostAddress &address, info.addresses()) {
    if (address.protocol() == QAbstractSocket::IPv4Protocol)
        qDebug() << "IPv4:" << address.toString();   // "192.168.118.55"
}

fromName 是阻塞版，内部要过 DNS，域名不在本地缓存时能挂几百毫秒。异步版是 QHostInfo::lookupHost(name, receiver, SLOT(slot))，走 hostFound / lookupFinished 信号。本机名解析很快，用它图省事；解析外网域名就换异步版，别在主线程里等。

8.3 直接拿全部本机地址 #

不想走主机名这一圈，用 QNetworkInterface::allAddresses()。它读的是网卡配置，不进 DNS，立刻返回，包含回环地址 127.0.0.1 和 ::1。

cpp
foreach (const QHostAddress &address, QNetworkInterface::allAddresses())
    qDebug() << "Address:" << address.toString();

8.4 遍历网卡拿 MAC、掩码、广播地址 #

一台机器上经常有多块网卡：无线、双以太网口、虚拟机虚拟网卡、VPN 隧道。要精确到某一块，就遍历 QNetworkInterface::allInterfaces()。

cpp
void queryLocalInterfaces()
{
    const auto interfaces = QNetworkInterface::allInterfaces();
    foreach (const QNetworkInterface &netInterface, interfaces) {
        // 跳过已断开的网卡
        if (!netInterface.flags().testFlag(QNetworkInterface::IsUp))
            continue;

        qDebug() << "Device Name:" << netInterface.name();                 // eth0 / uuid
        qDebug() << "Display Name:" << netInterface.humanReadableName();   // 友好名
        qDebug() << "MAC Address:" << netInterface.hardwareAddress();      // 物理 MAC

        foreach (const QNetworkAddressEntry &entry, netInterface.addressEntries()) {
            if (entry.ip().protocol() == QAbstractSocket::IPv4Protocol) {
                qDebug() << "  IP:" << entry.ip().toString();
                qDebug() << "  Netmask:" << entry.netmask().toString();
                qDebug() << "  Broadcast:" << entry.broadcast().toString();
            } else if (entry.ip().protocol() == QAbstractSocket::IPv6Protocol) {
                qDebug() << "  IPv6:" << entry.ip().toString();
            }
        }
        qDebug() << "===============";
    }
}

输出：

text
Device Name: "{4C5C2613-C18F-416A-A21F-47B707C3B935}"
Display Name: "本地连接"
MAC Address: "74:D4:35:1B:A6:2F"
  IP: 192.168.118.55
  Netmask: 255.255.255.0
  Broadcast: 192.168.118.255
===============
Display Name: "Loopback Pseudo-Interface 1"
MAC Address: ""
  IP: 127.0.0.1
  Netmask: 255.0.0.0

几个细节。name() 在 Windows 上返回接口 GUID，Linux 上是 eth0 这类设备名，跨平台判断网卡别靠它，靠 humanReadableName() 或 MAC 前缀。回环网卡没有 MAC，hardwareAddress() 返回空串，别当异常。广播地址允许为空，说明该网卡没配广播。虚拟网卡也在列表里，做设备绑定前要按 MAC 或描述过滤掉。

九、网络状态与错误处理 #

9.1 两套错误来源 #

来源 判定接口 典型值
TCP/UDP errorOccurred 信号 + errorString() ConnectionRefusedError、HostNotFoundError、RemoteHostClosedError、SocketTimeoutError
HTTP reply->error() + HttpStatusCodeAttribute NotFoundError、InternalServerError、TimeoutError，状态码另取

RemoteHostClosedError 在 TCP 里很常见：对端正常关了连接，Qt 把它报成错误。处理断线逻辑时要认这个值，不要一律当故障。

9.2 判断在线别靠自己的 bool #

自己维护一个 bool m_online，在 connected 里置真、disconnected 里置假，这是可行的（第三章那个继承版就这么写），但它只在信号到达后才更新，有窗口期。要判断当下能不能发数据，直接问状态机：socket->state() == QAbstractSocket::ConnectedState。

errorString() 是给开发者看的，直接弹到界面上不友好。做一层映射：连不上说「服务未启动或网络不通」，解析失败说「地址解析失败，检查网络或域名」，超时说「服务器响应超时」。日志里把原始 errorString() 和错误码都记下来。

十、断线与重连 #

移动网络切换、Wi-Fi 掉线、服务端重启，断线是常态，不是异常。要有重连策略。

cpp
class Link : public QObject
{
    Q_OBJECT
public:
    void connectTo(const QString &host, quint16 port)
    {
        m_host = host; m_port = port;
        m_retryDelay = 1000;                 // 手动重连时重置退避
        m_socket->connectToHost(host, port);
    }

private:
    void onDisconnected()
    {
        // 指数退避：1s、2s、4s、8s，封顶 30s
        m_retryDelay = qMin(m_retryDelay * 2, 30000);
        QTimer::singleShot(m_retryDelay, this, [this]() {
            m_socket->connectToHost(m_host, m_port);
        });
    }

    QTcpSocket *m_socket;
    QString m_host;
    quint16 m_port = 0;
    int m_retryDelay = 1000;
};

三条经验。退避别用固定间隔，一百个客户端同时拿 1 秒重试会把刚重启的服务端再打趴一次。重连前先 abort() 把旧套接字状态清干净，deleteLater 只适用于要换对象的情形。重连期间禁掉界面上的发送按钮，别让数据写进一个连不上的套接字缓冲区里堆着。还有一种情况要防：write 返回的字节数小于传入长度，说明发送缓冲区满了，剩下那部分没被接受。要么等 bytesWritten 再补发，要么自己维护发送队列，别假设 write 一次写完整份数据。

十一、传输自定义数据结构 #

11.1 TCP 是字节流，不是消息流 #

这是 TCP 编程的第二课，比第一课更容易出线上事故。

你在客户端 write 了两次，每次 10 字节。对端看到的是这三种之一：

对端看到的情况 说明
一次 readyRead，20 字节 两次 write 被合并了
两次 readyRead，各 10 字节 正常
两次 readyRead，7 字节 + 13 字节 在中间任意位置被切开了

三种都合法。TCP 只保证字节按序到达，不保证你写的边界就是对方读的边界。这就是粘包与半包。协议里没有消息边界这回事，边界必须由应用层定义。

11.2 三种划线方式 #

方式 怎么划 优点 缺点
长度前缀 头部固定 4 字节存长度，后面跟包体 二进制安全，解析确定 要防脏数据里的超大长度
分隔符 用 \r\n 或 \0 结尾 文本协议直观，可 telnet 手测 包体里不能出现分隔符，要转义
固定长度 每条消息定长 解析最简单 不灵活，短消息浪费带宽

第三章那个继承版客户端用的是分隔符方案，indexOf("\r\n") 配合 remove 从缓冲区里逐条切。文本协议够用。

二进制协议走长度前缀。

11.3 长度前缀的收发实现 #

cpp
// 发送：先写长度，再写包体，一次 write 送出去
void sendFrame(QTcpSocket *socket, const QByteArray &payload)
{
    QByteArray block;
    QDataStream out(&block, QIODevice::WriteOnly);
    out.setByteOrder(QDataStream::BigEndian);
    out << quint32(payload.size());
    block.append(payload);
    socket->write(block);
}

// 接收：缓冲区里凑够一条就切一条，循环到切不出为止
void consumeFrames(QTcpSocket *socket, QByteArray &buffer)
{
    buffer.append(socket->readAll());

    while (true) {
        if (buffer.size() < 4)
            return;                          // 连长度头都没齐，等下次

        QDataStream in(buffer);
        in.setByteOrder(QDataStream::BigEndian);
        quint32 len = 0;
        in >> len;

        if (len > 16 * 1024 * 1024) {        // 脏数据保护
            socket->abort();
            buffer.clear();
            return;
        }
        if (buffer.size() < 4 + int(len))
            return;                          // 包体没齐，等下次

        QByteArray payload = buffer.mid(4, len);
        buffer.remove(0, 4 + len);
        handlePayload(payload);
    }
}

四个要点。buffer 必须是长生命周期成员，不能放在槽函数里当局部变量，否则每次 readyRead 都是新的空缓冲区，半个包永远拼不起来。QDataStream 要显式设字节序，默认是大端，写出来省得后来的人去猜。长度字段要设上限，收到一个 0xFFFFFFFF 就是内存直接爆掉。QDataStream 的版本随 Qt 版本变，序列化结构体时用 setVersion(QDataStream::Qt_5_15) 固定住，否则升级 Qt 之后新旧版本对不上。

11.4 封装成帧对象 #

协议一复杂，就把「攒缓冲区、切帧、分发」封成一个类，对外只发 frameReady(QByteArray) 信号。第三章的 TcpClient::publishFrame 就是这个角色。业务层只处理完整的帧，永远不碰 readyRead 原始字节。这条边界划清楚，粘包问题就只在封帧类里出现一次。

十二、易错点速查 #

症状 原因 处理
QSocketNotifier: ... another thread 套接字方法在非所属线程调用 套接字在该线程创建，或 moveToThread 后只用信号投递调用
connectToHost 后立刻 write 发不出去 连接还没建立 把 write 放进 connected 槽
界面卡死 主线程里调了 waitFor* 或 loop.exec() 换异步信号，或把阻塞逻辑搬到工作线程
数据只收到一半 TCP 粘包/半包 应用层定长度前缀或分隔符，缓冲区用成员变量
readyRead 只读一次就丢包 一次通知里有多个数据报或半包 while (hasPendingDatagrams()) 或循环切帧
HTTP 请求一直不返回 没设超时 setTransferTimeout 或自己挂 QTimer 调 abort
登录后接口提示未登录 Cookie 没带上 给 Manager 设 QNetworkCookieJar，并保持同一个 Manager
服务端连接数被耗光 每次请求 new 一个 Manager 全应用复用一个 Manager
delete reply 崩在事件循环里 回包还在事件循环中 只用 deleteLater()
上传文件后崩溃或泄漏 QHttpMultiPart / QFile 生命周期没挂到 reply setParent(reply)、setParent(multiPart)
中文参数到服务端变乱码 编码不是 UTF-8，或没做 URL 编码 toUtf8() + QUrl::toPercentEncoding，抓包核对
服务端重写 incomingConnection 后收不到连接 重写后 newConnection 不再发出 在重写里自己接管 socketDescriptor，别再等信号
广播包自己收不到 本机不回环自己发的广播 bind 时带 ShareAddress | ReuseAddressHint
