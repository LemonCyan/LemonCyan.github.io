本篇讲 QSerialPort 在 Qt 里怎么用：模块怎么引、口怎么开、参数怎么对、字节流怎么拼帧、配置怎么存、线被拔了怎么收场。

先划边界。USB 转串口芯片的驱动安装不在这里展开；RS485 的接线、终端电阻属于硬件话题；你手上那台设备的私有协议规范，比我有权威。

找邻居：TCP/UDP 看《Qt 网络编程》，组包思路两边共用；报文是 JSON 的看《JSON 与 XML》；配置读写的基础看《文件配置与表格》。

一、串口在 Qt 里的位置 #

串口是 PC 上最老的设备接口之一，也是工控、仪表、单片机调试里最不容易被淘汰的那个。Qt 从 5.1 起把它收进标准模块——再早叫 QtSerialPort add-on，得自己编。

三条性质值得记住：

  • 异步事件驱动，走信号槽，贴合 Qt 事件循环，收数据不卡界面。
  • 继承自 QIODevice。API 和 QFile、QTcpSocket 一样：read、readAll、write、bytesAvailable、readyRead。会用一个就会用另外两个。
  • QSerialPortInfo 能枚举系统串口，拿到端口名、描述、制造商、VID/PID、系统路径。

第三条在实战里值钱。上位机卖到现场，用户不知道转换器插在第几个口，你按 VID/PID 匹配，比让他数「COM 几」靠谱。

1.1 什么时候下潜原生 #

特性 Qt QSerialPort termios (Unix) Win32 API
跨平台 ✓ 仅 Unix 仅 Windows
抽象层级 高 低 低
依赖 Qt 框架 系统原生 系统原生
性能开销 轻微 最小 最小

工程里已经有 Qt，就用 Qt 的；几十 KB 的命令行工具不想带运行库，才去写 termios 或 Win32。原生实现在第十一章给出一版精简实现，用途是排查——Qt 收不到数据时跑一遍，能立刻判断问题在 Qt 这层还是在设备那层。

1.2 两种通信模式 #

模式 适用线程 优点 缺点 场景
异步 (Signal/Slot) UI 主线程 不卡界面 状态管理稍复杂 90% 上位机应用
同步 (waitFor...) Worker 子线程 逻辑线性 禁止在 UI 线程使用 简单协议脚本

默认选异步。只有无 GUI 的采集脚本、或者已经有独立线程且逻辑就是「发一条等一条」的问答式交互，才考虑同步。

1.3 前提：串口是字节流 #

这一节不写代码，但它是后面所有坑的源头。

把串口想成水管，不是快递盒。设备发 8 个字节，readyRead 触发时 readAll 给 3 个、给 8 个、给 8 个外加下一条指令的头 2 个，三种都正常。中间隔着 USB 转换芯片缓冲、驱动缓冲、内核队列、Qt 内部缓冲，任何一层都能把数据切开或合并。

readyRead 只表示「有新字节可读」，不表示「收到一帧」。

这和 TCP 一样。写 TCP 的人都知道要处理粘包，写串口时却常忘——串口助手把收到的字节按行打出来，看着整齐，让人误以为一次回调就是一帧。等上现场，波特率一低、帧一长，程序开始随机丢包。结论：必须在应用层自己拼帧，定长、分隔符、长度前缀选一种。

二、启用 QtSerialPort 模块 #

模块没引，代码写得再对也编不过。

QT += serialport

qmake 一行搞定，Qt5 与 Qt6 都认。放在 QT += core gui 附近，别塞进文件末尾的条件块。

CMake（Qt6 主流写法）：

cmake
find_package(Qt6 REQUIRED COMPONENTS SerialPort)
target_link_libraries(MyApp PRIVATE Qt6::SerialPort)

find_package 里的 SerialPort 是组件名，target_link_libraries 里的 Qt6::SerialPort 是导入目标名，两处都不能少。Qt5 对应 find_package(Qt5 COMPONENTS SerialPort) 加 Qt5::SerialPort。

cpp
#include <QSerialPort>
#include <QSerialPortInfo>

QSerialPortInfo 是单独的类，只引 QSerialPort 拿不到 availablePorts()。

2.1 漏了模块会报什么 #

text
undefined reference to `QSerialPort::QSerialPort(QObject*)'
undefined reference to `QSerialPort::setPortName(QString const&)'
undefined reference to `QSerialPort::open(QIODevice::OpenModeFlag)'
undefined reference to `QSerialPortInfo::availablePorts()'

MSVC 下是 LNK2019，MinGW 下是上面这种。链接器还常附带 vtable for QSerialPort，别被带偏——不是虚函数没实现，是库没链上。

还有一种更隐蔽的：Qt 安装时没勾 SerialPort 组件。这时目录下没有 Qt6SerialPort.dll 和对应 .lib，QT += serialport 会直接报 Unknown module(s) in QT: serialport。错误发生在 qmake 阶段，比链接错误好认，去 Maintenance Tool 补装 Qt Serial Port。

发布时别忘带库：Windows 靠 windeployqt 自动收集 Qt6SerialPort.dll，Linux 把 libQt6SerialPort.so.6 打进包。ldd 能查缺哪个 so。

三、枚举与打开串口 #

cpp
void listAvailablePorts() {
    for (const QSerialPortInfo &info : QSerialPortInfo::availablePorts()) {
        qDebug() << "Port:" << info.portName()
                 << "Description:" << info.description()
                 << "Manufacturer:" << info.manufacturer()
                 << "VID:" << QString::number(info.vendorIdentifier(), 16)
                 << "PID:" << QString::number(info.productIdentifier(), 16);
    }
}

availablePorts() 每次调用都重扫系统。字段用途：

字段 内容 用途
portName() COM3 或 ttyUSB0 传给 setPortName
description() 驱动给的描述串 界面上给人看
manufacturer() 制造商 区分自家设备和第三方
serialNumber() 序列号（有就给） 多台同型号时认准某一台
systemLocation() 系统路径 日志里定位
vendorIdentifier() VID，无则 0 按厂商筛选
productIdentifier() PID，无则 0 按型号筛选

portName() 不带前缀：Windows 上没有 \\.\，Linux 上没有 /dev/。Linux 下拿到 ttyUSB0，setPortName 只认这个名字——自己拼成 /dev/ttyUSB0 传进去反而打不开。

按设备自动选口就扫 VID/PID：遍历 availablePorts()，先查 hasVendorIdentifier() 和 hasProductIdentifier() 再比数值——虚拟串口对（com0com 这类）和部分板载口拿不到 VID/PID，返回 0，直接比较 0 会误匹配。匹配上就返回 info.portName()，拿不到再退回让用户手选。

3.1 配置参数并打开 #

cpp
QSerialPort serial;
serial.setPortName("COM3");  // Windows: COMx, Linux: /dev/ttyUSBx
serial.setBaudRate(QSerialPort::Baud115200);
serial.setDataBits(QSerialPort::Data8);
serial.setParity(QSerialPort::NoParity);
serial.setStopBits(QSerialPort::OneStop);
serial.setFlowControl(QSerialPort::NoFlowControl);

注释和上面不冲突：setPortName("COM3") 在 Windows 上对，Linux 下要传 "ttyUSB0"。这一行是移植时最常见的翻车点。

参数在 open() 之前配好，open() 时一次性写进驱动。open() 之后改也生效，Qt 会立即下发，但要和读写错开，别在 readyRead 回调里改波特率。

cpp
if (serial.open(QIODevice::ReadWrite)) {
    serial.clear();
    qDebug() << "Serial opened successfully";
} else {
    // 常见错误：PermissionDenied, DeviceNotFoundError
    qDebug() << "Failed to open:" << serial.errorString();
}

模式用 QIODevice::ReadWrite，别写 QIODevice::Unbuffered——串口读写走的就是缓冲，去掉之后 readAll 的语义难以预测。

clear() 清的是驱动和 Qt 两层的收发缓冲。口刚打开时，缓冲里常躺着上次程序退出前没读走的残字节，不清掉，你拼帧的第一帧就是脏的。Qt 5.4 之后无参版本废弃：

cpp
serial.clear(QSerialPort::AllDirections);   // 收和发都清
serial.clear(QSerialPort::Input);           // 只清接收

3.2 打开失败的三类原因 #

open() 返回 false 时，先看 serial.error() 的枚举，再看 errorString()。三类原因占九成：

原因 枚举值 errorString() 长相 怎么确认
口被别的程序占用 PermissionError Permission denied / Access is denied 关掉串口助手、另一实例、厂商上位机
权限不足（Linux） PermissionError Permission denied ls -l /dev/ttyUSB0 看属主和组
口名写错 DeviceNotFoundError No such file or directory 对着 availablePorts() 核

被占用。 Windows 上格外常见：串口是独占资源，一个程序开了，第二个 open 不了。用户桌面上常年挂着串口助手、厂商工具、上次没退干净的自家进程。处理方式不是重试，是把话说清楚——弹框告诉用户「COM3 被占用，请关闭占用该端口的程序」，比一句 Failed to open 有用得多。

权限。 Linux 下普通用户默认进不了串口设备，节点长这样：

text
crw-rw---- 1 root dialout 188, 0 Nov 17 10:22 /dev/ttyUSB0

属主 root，属组 dialout。当前用户不在组里，open 就是 Permission denied，而错误码和「被占用」共用 PermissionError，光看枚举分不出来，得看 errorString() 加系统环境。把自己加进去：

bash
sudo usermod -aG dialout $USER

加完必须重新登录（或 newgrp dialout）才生效。groups 里能看到 dialout 了，但跑着的终端和 IDE 还是旧凭据。Ubuntu 上部分发行版用 uucp 组，ls -l 看清楚再加。

口名写错。 Windows 是 COM3，Linux 是 ttyUSB0（USB 转串口）、ttyS0（板载）或 ttyACM0（CDC 类）。写错返回 DeviceNotFoundError，和权限问题能区分开。设备管理器里明明有 COM10、代码写 COM1，也报这个错。转换器每次插拔分到的 COM 号会变，别把口名写死，交给第七章。

3.3 关闭 #

cpp
if (serial.isOpen()) {
    serial.close();
}

close() 之后对象能复用，重新 setPortName、open 就行。QSerialPort 析构时会自动关闭，但别指望析构——对象挂在堆上而程序异常退出，口不会及时释放，下次启动就撞「被占用」。在 closeEvent 里显式关一次，成本很低。

想确保最后一条指令真的发完：

cpp
serial.waitForBytesWritten(100);
serial.close();

不 wait 直接 close，还在 Qt 写缓冲里的字节会被丢掉。发「关机」「复位」这类指令时，这一句加上。

四、串口参数：波特率、数据位、停止位、校验 #

硬规矩：两端五个参数必须逐项一致。差一项，收到的就是乱码或者干脆收不到，而且不报错——串口没有握手来告诉参数不对。

参数 设置函数 常用值 说明
波特率 setBaudRate() 9600、19200、115200 每秒电平变化次数，不是字节数
数据位 setDataBits() 8（少数老设备 7） 一帧里数据位的个数
停止位 setStopBits() 1（少数 2） 一帧结束的标志位
校验 setParity() None（少数 Even/Odd） 单字节奇偶校验
流控 setFlowControl() None（RS485 场景常 None） 硬件 RTS/CTS 或软件 XON/XOFF 
text
BaudRate   : Baud1200 Baud2400 Baud4800 Baud9600 Baud19200 Baud38400
             Baud57600 Baud115200（也可直接传 qint32 整数）
DataBits   : Data5 Data6 Data7 Data8
StopBits   : OneStop OneAndHalfStop TwoStop
Parity     : NoParity EvenParity OddParity SpaceParity MarkParity
FlowControl: NoFlowControl HardwareControl SoftwareControl

setBaudRate() 接受 qint32，非标波特率直接给数：serial.setBaudRate(256000) 能给进去，3000000 也能，前提是芯片和驱动撑得住。

4.1 常见组合与错配现象 #

组合 表示法 出现在哪
115200 8N1 115200, Data8, NoParity, OneStop 现代单片机、ESP32、调试口
9600 8N1 9600, Data8, NoParity, OneStop 老仪表、PLC、条码枪
19200 8E1 19200, Data8, EvenParity, OneStop Modbus RTU 常见配置
57600 8N1 57600, Data8, NoParity, OneStop 部分 GPS 模块、工控屏

「8N1」是行话：8 数据位、N 无校验、1 停止位。看设备手册先找这一串。

错在哪 现象
波特率不一致 一堆乱码字节，或整帧都是 0xFF/0x00
数据位不一致 每字节高位或低位被截断，ASCII 明显变形
校验方式不一致 大部分帧能过，个别字节错，校验位被当成数据读进来
停止位不一致 偶尔多一个伪字节，帧边界整体偏移
流控开了但没接线 只发不收，或发几个字节后卡死（等 CTS 释放）

最后一条值得单说。设备和上位机没接 RTS/CTS 线，代码里却设了 HardwareControl，write() 会把数据堆在缓冲里等 CTS，CTS 永远不来，表现就是「能连上、发不出去」。RS485 半双工的方向控制脚是另外处理的，别指望 HardwareControl 帮你。

4.2 一次配全，检查返回值 #

cpp
bool configurePort(QSerialPort &serial) {
    if (!serial.setBaudRate(115200)) {
        qWarning() << "baud rate not supported";
        return false;
    }
    if (!serial.setDataBits(QSerialPort::Data8))  return false;
    if (!serial.setParity(QSerialPort::NoParity)) return false;
    if (!serial.setStopBits(QSerialPort::OneStop)) return false;
    if (!serial.setFlowControl(QSerialPort::NoFlowControl)) return false;
    return true;
}

这些 setter 都返回 bool。false 表示驱动不接受这个值——非标波特率在劣质转换器上就是如此，比如 CH340 跑 3000000 会失败。

4.3 波特率换算成吞吐 #

一个字节在线路上占 10 位：1 起始位 + 8 数据位 + 1 停止位（无校验）。

text
115200 bps  → 11520 字节/秒 ≈ 11 KB/s
57600  bps  →  5760 字节/秒 ≈ 5.6 KB/s
9600   bps  →   960 字节/秒 ≈ 0.94 KB/s

记住这组数，它能提前拦住一类架构错误。9600 下每秒只能过 960 字节，采集需求要是 1000Hz × 每帧 16 字节（16 KB/s），硬件根本不够，程序写得再好也没用。反过来，115200 下 11 KB/s 的余量，意味着写缓冲被堆满只能是发送逻辑太快、设备消费太慢——第五章的流控就是为这个准备的。

五、读写数据 #

5.1 写：write() 不阻塞 #

cpp
qint64 n = serial.write("Hello Device");

write() 把数据拷进 Qt 内部写缓冲就返回，真正推到硬件是事件循环干的活。返回值是「被接受的字节数」，不是「已发出的字节数」。

cpp
connect(&serial, &QSerialPort::bytesWritten, this, [](qint64 n){
    qDebug() << "written" << n;      // 已写入硬件的字节数
});

qDebug() << "pending:" << serial.bytesToWrite();   // 还在缓冲里的

5.2 高频发送的流控 #

发送频率高（比如 1ms 一次），波特率又不高时，内部写缓冲会迅速堆积，涨到几 MB 才开始卡顿，甚至把内存吃光。原因是 write() 从不拒绝你，它只负责收。

cpp
void safeWrite(const QByteArray &data) {
    // bytesToWrite() 返回尚未写入硬件的字节数
    if (serial->bytesToWrite() > 10240) {
        qWarning() << "Output buffer overflow, dropping packet!";
        return;
    }
    serial->write(data);
}

阈值按场景定。115200 下 10 KB 差不多是 0.9 秒的存量，超过就说明设备消费不动了，此时丢新包比堆内存合理——迟到的数据往往还不如没有。丢完在界面上亮个计数器，静默丢包是现场最难查的问题，因为日志里一切正常。

5.3 同步模式：waitFor... #

无 GUI 的采集脚本，或者已经跑在独立线程里的逻辑，可以写成线性代码：

cpp
void Worker::run() {
    QSerialPort serial;
    // ... 配置 ...
    serial.open(QIODevice::ReadWrite);

    serial.write("CMD");
    if (!serial.waitForBytesWritten(100)) return;

    if (serial.waitForReadyRead(5000)) {
        QByteArray resp = serial.readAll();
        while (serial.waitForReadyRead(10)) {
            resp += serial.readAll();
        }
        emit resultReady(resp);
    } else {
        qDebug() << "Timeout or Error";
    }
}

注意那个 while (serial.waitForReadyRead(10))：第一条 waitForReadyRead(5000) 只保证「来了至少一个字节」，后面用 10ms 小超时反复收尾，是在等设备的后续字节。这个收尾逻辑本身就承认了字节流会断——只是用时间窗糊过去，不如第六章的拼帧严谨。

禁止在 GUI 线程用这套。 waitForReadyRead(5000) 把主线程挂起 5 秒，界面白屏、不响应、任务管理器显示「无响应」，用户以为程序崩了。Qt 不拦你，编译器也不拦，只能自己记住。

5.4 读：read 家族怎么选 #

方法 拿什么 什么时候用
readAll() 当前缓冲全部字节 拼帧缓冲的原料，最常用
read(n) 前 n 字节 已知帧长，精确取
readLine() 到 \n 为止 文本协议，带行长上限
peek(n) 看前 n 字节不取走 判帧头、等够长度再取
bytesAvailable() 可读字节数 循环条件、拼帧判断

常用组合：readyRead 里只做「搬字节」，解析放进独立的 parseBuffer()，两件事分开，谁出问题查谁。

cpp
void MyClass::handleReadyRead() {
    QByteArray data = serial.readAll();
    buffer.append(data);
    parseBuffer();  // 尝试解析完整帧
}

readLine() 看着省事，坑在默认上限：一行超长就分段返回。文本协议用它，要么设 serial.setReadBufferSize()，要么在协议里约定单行最大长度。

六、readyRead 与数据接收的完整性 #

6.1 两种撕裂 #

串口是流式传输，接收端看到的只是字节流：

  • 断包：一条长指令分两次才收全。第一次 readyRead 给前半截，第二次给后半截。
  • 粘包：两条指令一次性收到。一次 readAll 里躺着两帧。

低波特率、长帧、USB 转串口上，这两种更常见。USB 转换器尤其明显：芯片内部按 1ms 或按缓冲块往上报，一次报多少跟你发多少没关系。

6.2 判断逻辑 #

text
readyRead → m_buffer.append(readAll())
  ↓
size >= 最小帧长？ ── 否 ──→ 退出，等下次
  ↓ 是
帧头正确？ ── 否 ──→ 丢首字节（滑动窗口），重试
  ↓ 是
够一整帧？ ── 否 ──→ 退出，等更多数据
  ↓ 是
截帧 → 移除已处理字节 → 校验 → 分发 → 回到第二步

两个容易忽略的设计点。

帧头不对就滑一个字节，不是清空缓冲。出现脏字节时，真正的帧往往紧跟在后面几个字节处，清空等于把好数据一起扔了。

判断和退出要成对。while 循环的每个 break 都必须保留剩余数据，continue 才往前走。这两条写反，程序会表现为「一收多帧就卡死」或「内存持续增长」。

6.3 长度前缀 + 校验的完整实现 #

帧格式：0x55 0xAA | len（2 字节，大端）| payload | checksum。

cpp
QByteArray m_buffer;

void onReadyRead() {
    m_buffer.append(serial->readAll());

    while (m_buffer.size() >= MIN_PACKET_SIZE) {
        // 寻找帧头 0x55AA
        if ((quint8)m_buffer[0] != 0x55 || (quint8)m_buffer[1] != 0xAA) {
            m_buffer.remove(0, 1);  // 滑动窗口
            continue;
        }

        quint16 len = (quint8)m_buffer[2] << 8 | (quint8)m_buffer[3];
        if (m_buffer.size() < len + HEADER_SIZE) break;  // 等待更多数据

        QByteArray packet = m_buffer.left(len + HEADER_SIZE);
        m_buffer.remove(0, len + HEADER_SIZE);

        if (checkSum(packet)) {
            emit newPacket(packet);
        }
    }
}

常量按协议填：HEADER_SIZE 是帧头加长度字段的字节数（这里 4），MIN_PACKET_SIZE 是「能读到长度字段」的最小量（也是 4）。

三处必须补的防护，缺一个都是现场隐患。

len 不可信。 设备发疯或干扰时 len 报出 60000，于是 m_buffer.size() < len + HEADER_SIZE 永远成立，程序一直等，缓冲一直涨。

cpp
if (len == 0 || len > MAX_PAYLOAD) {   // MAX_PAYLOAD 按协议定，比如 1024
    m_buffer.remove(0, 1);             // 当作脏帧头，滑一个字节重来
    continue;
}

缓冲总长要有上限。 帧头对、长度字段被干扰成合法大值时，上一条挡不住：

cpp
if (m_buffer.size() > 65536) {
    qWarning() << "buffer overflow, drop";
    m_buffer.clear();
}

quint8 强转别省。 QByteArray::operator[] 返回 char，在 char 有符号的平台上 0xAA 会变成 -86，直接跟 0xAA 比较永远不等。代码里那些 (quint8) 看着多余，删了必崩。

6.4 校验函数 #

cpp
// 1. 异或校验，单片机协议里最常见
quint8 xor8(const QByteArray &d) {
    quint8 x = 0;
    for (char c : d) x ^= (quint8)c;
    return x;
}

// 2. CRC16/Modbus，多项式 0xA001（反向），初值 0xFFFF
quint16 crc16Modbus(const QByteArray &d) {
    quint16 crc = 0xFFFF;
    for (char c : d) {
        crc ^= (quint8)c;
        for (int i = 0; i < 8; ++i)
            crc = (crc & 1) ? ((crc >> 1) ^ 0xA001) : (crc >> 1);
    }
    return crc;   // 上线时低字节在前
}

还有最简单的累加和：把所有字节按 quint8 相加，取低 8 位。校验不是可选项——线长、干扰大、地线还常没接好，偶发位翻转是常态。没有校验的协议在实验室跑一天没问题，到现场每天错几次。

6.5 多线程下的接收：缓冲池 #

有种架构是「一个线程死循环轮询，主线程画界面」。while(1) 转太快时信号槽来不及处理，readAll 被反复调用而数据没人管。这种架构用 waitFor* 阻塞加缓冲池做线程安全交换：

cpp
struct BufferNode {
    QMutex nodeMutex;
    int nodeStatus;      // 0: 空闲, 1: 待处理
    QByteArray nodeData;
};

BufferNode sendMsg[INDEX_OF_BUFF];
BufferNode recvMsg[INDEX_OF_BUFF];

void threadSendLoop() {
    for (int i = 0; i < INDEX_OF_BUFF; i++) {
        if (sendMsg[i].nodeMutex.tryLock()) {
            if (sendMsg[i].nodeStatus == 1) {
                serial->write(sendMsg[i].nodeData);
                serial->waitForBytesWritten(5);
                sendMsg[i].nodeStatus = 0;
            }
            sendMsg[i].nodeMutex.unlock();
        }
    }
}

void threadRecvLoop() {
    serial->waitForReadyRead(1);
    if (serial->bytesAvailable() > 0) {
        for (int i = 0; i < INDEX_OF_BUFF; i++) {
            if (recvMsg[i].nodeMutex.tryLock()) {
                if (recvMsg[i].nodeStatus == 0) {
                    recvMsg[i].nodeStatus = 1;
                    recvMsg[i].nodeData = serial->readAll();
                    recvMsg[i].nodeMutex.unlock();
                    return;
                }
                recvMsg[i].nodeMutex.unlock();
            }
        }
    }
}

要点在 tryLock 而不是 lock：拿不到锁就跳下一个节点，不让一个线程等另一个线程。代价是池子满了会丢数据，上面没处理，得自己加计数。这套写法在 QThread + 死循环的项目里能用，但不如「串口对象留在工作线程，收到字节用 queued 连接丢给主线程」干净——后者不需要锁，新项目别从缓冲池起步。

6.6 高频数据的处理原则 #

EEG 1000Hz 采样、振动传感器、电表高速轮询，都属于这一类。

  1. 数据解耦：IO 线程和 UI 渲染线程分开。读到的原始字节不做界面更新，只拼帧丢队列。
  2. 别逐字节 append：1000Hz × 每帧 16 字节，一天就是 13 亿次调用。用 memcpy 或预分配 QByteArray（reserve()）减少重分配。
  3. 绘制降频：1000Hz 采样按 60Hz 刷新。用 QTimer 把这段时间的数据聚合成一批再提交绘图，曲线只画抽稀后的点。

第三条最容易被忽略。把每帧都塞进 QChart 或 QCustomPlot，界面会卡到没法看，而串口那边一点问题没有——瓶颈在绘图，不在通信。

七、串口的配置持久化 #

7.1 为什么必须存 #

COM3 不是设备自带的。USB 转串口插到不同 USB 口，Windows 分到的号会变；换台机器，号从零重排。把口名写死在代码里，程序在开发机上跑得好，到现场就要用户手动选。

串口参数同理。设备出厂 9600，现场被改成 115200，程序还按 9600 发，收到的全是乱码。

7.2 存与取 #

cpp
void saveSerialSettings(const QSerialPort &serial) {
    QSettings s;                       // 依赖已设置的组织名/应用名
    s.beginGroup("serial");
    s.setValue("portName",   serial.portName());
    s.setValue("baudRate",   serial.baudRate());
    s.setValue("dataBits",   int(serial.dataBits()));
    s.setValue("parity",     int(serial.parity()));
    s.setValue("stopBits",   int(serial.stopBits()));
    s.setValue("flowControl",int(serial.flowControl()));
    s.endGroup();
}

bool loadSerialSettings(QSerialPort &serial) {
    QSettings s;
    s.beginGroup("serial");
    const QString port = s.value("portName").toString();
    if (port.isEmpty()) { s.endGroup(); return false; }
    serial.setPortName(port);
    serial.setBaudRate(s.value("baudRate", 115200).toInt());
    serial.setDataBits(QSerialPort::DataBits(s.value("dataBits", 8).toInt()));
    serial.setParity(QSerialPort::Parity(s.value("parity", 0).toInt()));
    serial.setStopBits(QSerialPort::StopBits(s.value("stopBits", 1).toInt()));
    serial.setFlowControl(QSerialPort::FlowControl(s.value("flowControl", 0).toInt()));
    s.endGroup();
    return true;
}

枚举存成 int，读回来再强转。QSettings 不认自定义枚举，别指望它序列化 QSerialPort::Parity。

7.3 两个前提 #

cpp
QCoreApplication::setOrganizationName("YourCompany");
QCoreApplication::setApplicationName("YourApp");

必须在任何 QSettings 使用之前设。不设，配置落到一个叫 Unknown Organization 的位置，卸载时清不干净。落盘位置：Windows 在注册表 HKEY_CURRENT_USER\Software\YourCompany\YourApp，Linux 在 ~/.config/YourCompany/YourApp.conf。

想让配置跟着程序目录走（绿色版、U 盘部署）：

cpp
QSettings::setDefaultFormat(QSettings::IniFormat);
QSettings::setPath(QSettings::IniFormat, QSettings::UserScope,
                   QCoreApplication::applicationDirPath());

7.4 存「上次成功的口」，不是「界面上的口」 #

容易犯的错：用户在下拉框选了 COM5，程序立刻存盘；COM5 其实打不开。下次启动自动连 COM5，又失败，用户以为程序坏了。正确时机是 open() 成功之后：

cpp
if (serial.open(QIODevice::ReadWrite)) {
    saveSerialSettings(serial);      // 只在成功时落盘
    // ...
}

7.5 恢复不等于能连上 #

启动时读出口名，先用 QSerialPortInfo::availablePorts() 扫一遍确认它还在。不在，就把下拉框定位到第一个可用口并提示「上次使用的 COM5 已不存在」——用户不知道 COM 号会变，他只知道「昨天还好好的」，这条提示能省掉大量售后沟通。

QSettings 写入是延迟刷盘的，sync() 能强制落盘，别每次写都调。配置项的其余玩法（分组、类型转换、迁移旧键名）看《文件配置与表格》。

八、热插拔与串口消失 #

8.1 拔线的第一现场 #

cpp
connect(&serial, &QSerialPort::errorOccurred, this, [](QSerialPort::SerialPortError error){
    if (error == QSerialPort::NoError) return;
    qWarning() << "Serial error:" << error;

    if (error == QSerialPort::ResourceError) {
        qCritical() << "Device disconnected physically!";
        // 触发自动重连逻辑...
    }
});

回调里先滤掉 NoError。这个信号在正常打开、正常关闭时也会带着 NoError 进来一次，不滤的话日志全是噪音。

枚举值 含义 典型场景
ResourceError 设备消失 USB 拔掉、设备断电、驱动卸载
PermissionError 无权限或被占用 口被别人打开、Linux 缺 dialout
DeviceNotFoundError 设备不存在 口名写错、还没插上就 open
OpenError 打开失败 参数不被驱动接受
ReadError / WriteError 读写出错 线松、干扰、设备复位
TimeoutError 超时 只在使用 waitFor* 时出现
NotOpenError 没打开就操作 顺序写错

8.2 ResourceError 之后必须手动 close() #

最容易漏的一步。设备被拔掉时 serial.isOpen() 依然返回 true——Qt 没替你关句柄。于是后续 write() 全部失败、bytesToWrite() 一直涨、重连时 open() 报「被占用」（自己还占着）。

cpp
if (error == QSerialPort::ResourceError) {
    serial.close();                 // 必须显式关
    m_state = Disconnected;
    scheduleReconnect();            // 再排一次重连
}

close() 之后再 open() 同一个对象没问题，setPortName 重新设一遍更保险。

8.3 轮询端口集合，兜住漏报 #

个别驱动、个别 Windows 版本上，拔线后 ResourceError 不一定触发，或者来得极晚。加一个低频轮询比等信号可靠：

cpp
void PortWatcher::poll() {
    QSet<QString> now;
    for (const QSerialPortInfo &info : QSerialPortInfo::availablePorts())
        now.insert(info.portName());

    const QSet<QString> added   = now - m_known;
    const QSet<QString> removed = m_known - now;
    m_known = now;

    for (const QString &p : removed) emit portRemoved(p);
    for (const QString &p : added)   emit portAdded(p);
}

QSet 的差集要求元素可哈希，QString 满足。轮询间隔 1000ms 足够，别设 100ms——availablePorts() 每次都要枚举设备，Windows 上这个调用不便宜。

用途有两个：自动发现新插的设备（一键连接），以及检测「我正用着的口没了」。第二种和 ResourceError 是双保险。

8.4 自动重连要有退避 #

cpp
void MainWindow::scheduleReconnect() {
    if (m_retry >= 5) { m_retry = 0; return; }
    const int delay = 1000 * (1 << m_retry);   // 1s, 2s, 4s, 8s, 16s
    ++m_retry;
    QTimer::singleShot(delay, this, [this]{
        if (tryOpen()) { m_retry = 0; }
        else           { scheduleReconnect(); }
    });
}

singleShot 加 this 作上下文，窗口关了定时器自动失效，不用手动撤。指数退避的作用是避免设备没插、程序却在每 100ms 撞一次 open，把日志刷满。

重连成功后把拼帧缓冲清掉。上一次会话的半帧留在 m_buffer 里，新连接的第一帧会被它污染。

8.5 拔线时正在发的数据 #

拔线瞬间，Qt 写缓冲里的字节直接蒸发。所以「发完关机指令再拔线」，程序侧能做的是发完立刻 waitForBytesWritten(100)，确认推给驱动了再算完成。真到硬件层面，还得靠设备的应答帧确认。

同理，ResourceError 之前 readAll() 拿到的最后一批数据是完整的，别在错误处理里把缓冲一清了事：

cpp
if (error == QSerialPort::ResourceError) {
    m_buffer.append(serial.readAll());   // 抢救最后的字节
    serial.close();
    parseBuffer();                       // 缓冲里够一帧的，仍然处理掉
}

九、协议解析：定长、分隔符与校验 #

第六章给了长度前缀的实现。三种拼帧方式都要会选。

方式 优点 缺点 适用
定长 实现最简单，判断一次就够 载荷长度固定，扩展难 传感器定长上报、读寄存器
分隔符 载荷长度自由 载荷里不能出现分隔符，要转义 文本协议、AT 指令、NMEA
长度前缀 载荷随意，效率高 长度字段被干扰会连累后续帧 二进制协议、自定义帧

选哪种看设备协议，不是你说了算。只有协议由你定的时候才选长度前缀——它最不容易出错。

9.1 定长 #

帧长 16 字节，第 0 字节是 0xA5 帧头，第 15 字节是累加和。

cpp
void onReadyReadFixed() {
    m_buffer.append(serial->readAll());

    while (m_buffer.size() >= FRAME_LEN) {
        if ((quint8)m_buffer[0] != 0xA5) {
            m_buffer.remove(0, 1);
            continue;
        }
        const QByteArray frame = m_buffer.left(FRAME_LEN);
        m_buffer.remove(0, FRAME_LEN);

        quint8 sum = 0;
        for (int i = 0; i < FRAME_LEN - 1; ++i) sum += (quint8)frame[i];
        if (sum != (quint8)frame[FRAME_LEN - 1]) {
            qWarning() << "frame checksum error";
            continue;                    // 丢这一帧，继续下 16 字节
        }
        handleFrame(frame);
    }
}

定长的坑在「帧头对但整体错位一个字节」。数据里恰好有个 0xA5，程序从这里截 16 字节，后面全歪。校验和能拦住大部分，拦不住的会当成正常帧处理。所以定长协议的帧头要选载荷里几乎不出现的值，0xA5、0x55、0x7E 都是这么来的。

9.2 分隔符 #

文本协议最省事，也最容易踩行长和转义两个坑。

cpp
void onReadyReadLine() {
    m_buffer.append(serial->readAll());

    int idx;
    while ((idx = m_buffer.indexOf('\n')) >= 0) {
        QByteArray line = m_buffer.left(idx);
        m_buffer.remove(0, idx + 1);            // 连同 '\n' 一起移除

        if (line.endsWith('\r')) line.chop(1);  // 兼容 \r\n
        if (line.isEmpty()) continue;

        handleLine(line);
    }

    if (m_buffer.size() > MAX_LINE) {           // 半行卡死保护
        qWarning() << "line too long, drop buffer";
        m_buffer.clear();
    }
}

\r\n 和 \n 都要兼容。设备手册写「以 CRLF 结尾」，实际固件只发 \n，这种事常见，代码里两种都处理，省一次往返沟通。

MAX_LINE 必须有。设备发出一个 \n 都没有的长数据流（比如被干扰成一串连续字节），indexOf('\n') 永远返回 -1，缓冲无限增长。

帧头不固定、载荷长度靠内容判断的协议，改成逐字节状态机（WaitHead1 → WaitHead2 → WaitLen → WaitPayload → WaitSum）更好维护，把「我在等什么」变成显式状态，跨回调保留，天然处理断包。

9.3 半帧超时 #

有一种帧永远完不成：前 5 个字节来了，后面再也不来。原因多半是设备复位、线松了一瞬、干扰吃掉几个字节。协议有「帧间静默」约定时（Modbus RTU 的 3.5 字符时间），用定时器兜底：

cpp
m_idleTimer = new QTimer(this);
m_idleTimer->setSingleShot(true);
m_idleTimer->setInterval(50);              // 50ms 静默就认为一帧结束
connect(m_idleTimer, &QTimer::timeout, this, [this]{
    if (!m_buffer.isEmpty()) {
        qWarning() << "incomplete frame, dropped" << m_buffer.size();
        m_buffer.clear();
    }
});
m_idleTimer->start();                      // 每次 readyRead 里重启

50ms 对应 115200 下约 576 字节。低速波特率要放大，9600 下 100ms 才传得动 96 字节，用 50ms 会把正常的长帧切断。

9.4 现成协议栈：Modbus RTU #

协议是 Modbus 的话别手写，Qt 有 QtSerialBus 模块，里面是 QModbusRtuSerialMaster。

QT += serialbus

cmake
find_package(Qt6 REQUIRED COMPONENTS SerialBus)
target_link_libraries(MyApp PRIVATE Qt6::SerialBus)

cpp
#include <QModbusRtuSerialMaster>

auto modbus = new QModbusRtuSerialMaster(this);
modbus->setConnectionParameter(QModbusDevice::SerialPortNameParameter, "COM3");
modbus->setConnectionParameter(QModbusDevice::SerialBaudRateParameter, 19200);
modbus->setConnectionParameter(QModbusDevice::SerialDataBitsParameter, QSerialPort::Data8);
modbus->setConnectionParameter(QModbusDevice::SerialParityParameter, QSerialPort::EvenParity);

if (!modbus->connectDevice()) {
    qDebug() << "Connect failed";
    return;
}

auto reply = modbus->sendReadRequest(
    QModbusDataUnit(QModbusDataUnit::HoldingRegisters, 0, 10),
    1  // Slave ID
);

if (reply && !reply->isFinished()) {
    connect(reply, &QModbusReply::finished, this, [reply](){
        if (reply->error() == QModbusDevice::NoError) {
            qDebug() << "Data:" << reply->result().values();
        }
        reply->deleteLater();
    });
}
  • setConnectionParameter 的值是 QVariant。波特率传 int，数据位和校验传 QSerialPort 的枚举——传 QSerialPort::NoParity 而不是 0。
  • 超时和重试自己设：modbus->setTimeout(1000)、modbus->setNumberOfRetries(3)。默认值在长线、慢设备上不够。
  • reply 必须 deleteLater()，不删会泄漏，QModbusReply 不会自动回收。
  • 一个主站对象同时只能有一个未完成请求。连续读多个从站要排队，别在循环里连发。

私有协议回 9.1 到 9.3 手写。拼帧逻辑就那点东西，封装成 FrameParser 类，串口这层就干净了。

十、十六进制与文本模式 #

10.1 数据本身没有「模式」 #

QByteArray 存的是字节，不是字符。所谓十六进制模式和文本模式，是人看它和打字给它的两种方式。这句想通，一半的乱码问题就不存在了。

cpp
QByteArray data = serial->readAll();
qDebug() << data.toHex(' ');        // "55 aa 01 0f"，Qt 5.9+ 支持分隔符

toHex() 不带参数是连写的 55aa010f，带分隔符好读得多。

从界面输入十六进制字符串：

cpp
QString s = ui->hexEdit->text();          // "AA BB 01 02"
s.remove(QRegularExpression("\\s+"));     // 空格、换行、制表符全清掉
const QByteArray bytes = QByteArray::fromHex(s.toLatin1());
serial->write(bytes);

fromHex() 遇到非法字符会跳过，不报错。用户输入 AA BB 0G 会静默变成别的字节，输入框上做一次正则校验，比出错后排查省事。

10.2 文本模式的两个编码坑 #

cpp
QString text  = QString::fromUtf8(bytes);     // 设备发 UTF-8
QString text2 = QString::fromLatin1(bytes);   // 设备发 ASCII

坑一，把 QByteArray 直接丢给 QString 构造，走的是 fromUtf8，而老设备发的多半是 GBK，中文必然乱码。ASCII 内容两种编码结果一样，所以「英文正常、中文乱码」是编码问题的典型长相。

坑二，Qt6 里 QStringDecoder 支持的编码有限，GBK 不在其中。要解 GBK 得引 core5compat 的 QTextCodec：

QT += core5compat

cpp
#include <QTextCodec>
QTextCodec *gbk = QTextCodec::codecForName("GBK");
QString text = gbk->toUnicode(bytes);         // 收
serial->write(gbk->fromUnicode("开始测量"));   // 发

不做这一步，Qt 默认按 UTF-8 发，设备固件按 GBK 解析，屏幕上是问号。

10.3 发送端别混用 #

想发的东西 正确写法 错误写法
二进制指令 write(QByteArray::fromHex("A5 01 00")) write("A5 01 00")
ASCII 文本 write("AT+RESET\r\n") 少写 \r\n
中文文本 write(gbk->fromUnicode(s)) write(s.toUtf8()) 给 GBK 设备
单个字节 write(QByteArray(1, char(0xA5))) write("\xA5")，转义边界易错

最后一条值得记：字符串字面量里 "\xA5" 合法，但紧跟十六进制字符时编译器吃掉几位，不同实现行为不一。用 QByteArray(1, char(0xA5)) 或 fromHex 绕开。

十一、常见故障与现象 #

11.1 现象对照 #

现象 先查什么
open() 返回 false 三类原因：被占用 / 权限 / 口名，见 3.2
打开成功，一个字节都收不到 接线：TX/RX 是否交叉、地线、设备是否上电
收到数据但全是乱码 波特率、数据位、校验，逐项对设备手册
收到大片 0x00 波特率差太多，或设备还没启动完成
偶发帧错位 没拼帧，直接拿 readAll 当一帧用
发几条后卡住不动 流控设了 HardwareControl 但没接 CTS
程序退出后再启动打不开 上次没 close()，口还在被自己占着
拔线后卡死或崩 ResourceError 没处理，write 到失效句柄
中文显示成问号 编码：设备 GBK，程序按 UTF-8 解
数据量一大就丢 没做流控 / 没降频绘制 / 缓冲无上限

排查顺序别跳步：系统能不能看到这个口（设备管理器、ls /dev/ttyUSB*）→ 用 minicom 或串口助手试收发 → 换工具打开你的口确认没被占 → 短接 TX/RX 做回环。

回环测试两分钟能省掉半天争论：

cpp
serial.write(QByteArray("LOOP"));
// 短接后，readyRead 里应当收到同样的 4 个字节

11.2 用原生 API 交叉验证 #

Qt 收不到数据时，下一个判断是「问题在 Qt 这层还是操作系统这层」。用最裸的 API 跑一遍，界线立刻清楚。Linux 的 termios：

c
int fd = open("/dev/ttyUSB0", O_RDWR | O_NOCTTY | O_NDELAY);
if (fd == -1) return -1;
if (!isatty(fd)) { close(fd); return -1; }         // 不是终端设备

struct termios tty = {0}, original;
tcgetattr(fd, &original);                          // 留存，退出时还原
cfsetispeed(&tty, B115200);
cfsetospeed(&tty, B115200);

tty.c_cflag |= (CLOCAL | CREAD);                   // 忽略调制解调器控制线，启用接收
tty.c_cflag &= ~CSIZE; tty.c_cflag |= CS8;         // 8 数据位
tty.c_cflag &= ~PARENB;                            // 无校验
tty.c_cflag &= ~CSTOPB;                            // 1 停止位
tty.c_cflag &= ~CRTSCTS;                           // 无硬件流控
tty.c_lflag &= ~(ICANON | ECHO | ECHOE | ISIG);    // 原始模式，关回显、关行缓冲
tty.c_iflag &= ~(IXON | IXOFF | IXANY);            // 关软件流控
tty.c_oflag &= ~OPOST;                             // 原始输出
tty.c_cc[VMIN] = 1;                                // 至少收到 1 字节才返回
tty.c_cc[VTIME] = 10;                              // 单位 100ms，即 1s 超时

tcflush(fd, TCIOFLUSH);
tcsetattr(fd, TCSANOW, &tty);
fcntl(fd, F_SETFL, 0);

写用 write(fd, ...) 加 tcdrain(fd) 等数据真正发完；读用 select() 等可读再 read()；收尾 tcsetattr(fd, TCSANOW, &original) 还原——不还原的话，那个口会保持你设的参数。

Windows 的 Win32 API 关键几行：

text
CreateFileA("\\\\.\\COM3", GENERIC_READ|GENERIC_WRITE, 0, NULL, OPEN_EXISTING, 0, NULL)
  → "\\\\.\\" 前缀必须加，COM10 及以上不加直接失败（Qt 内部替你加了）
DCB: BaudRate / ByteSize=8 / StopBits=ONESTOPBIT / Parity=NOPARITY
     fDtrControl=DTR_CONTROL_ENABLE / fRtsControl=RTS_CONTROL_ENABLE
     fOutxCtsFlow=FALSE（不接 CTS 时必须关）
SetCommTimeouts: ReadIntervalTimeout=50, ReadTotalTimeoutConstant=2000
PurgeComm(h, PURGE_RXCLEAR | PURGE_TXCLEAR)   ← 对应 Qt 的 clear()

SetCommTimeouts 对应 Qt 的 waitFor* 超时，PurgeComm 对应 clear()。这两段跑通能收到数据，说明串口和驱动都没问题，回去查 Qt 那边的参数和拼帧；跑不通，就别在 Qt 里绕了。

十二、易错点速查 #

易错点 后果 对策
忘写 QT += serialport 一堆 undefined reference 见 2.1 的症状清单
不检查 open() 返回值 后续全是 NotOpenError if (!serial.open(...)) 必判
把 readAll() 当一帧 粘包断包，随机丢包 应用层拼帧，第六章
在 UI 线程 waitForReadyRead 界面假死 只用异步，同步放工作线程
不处理 ResourceError 拔线后写失效句柄，崩 显式 close() 再重连
拔线后不 close() 重连报「被占用」 同上，isOpen() 不可信
QString 直接塞二进制 中文乱码、0x00 截断 二进制走 QByteArray
拼帧缓冲无上限 内存持续增长到崩 上限 + 超时清理
忽略 (quint8) 强转 帧头比较永远不等 operator[] 返回 char
端口名写死 换插口就连不上 QSettings 存，第七章
Linux 没加 dialout 组 Permission denied usermod -aG 后重新登录
高波特率逐字节 append CPU 打满、界面卡 reserve() + 定时器聚合
多线程直接操作同个 QSerialPort 随机崩溃、数据错乱 串口对象归属单一线程

这十三条里，前六条能解释现场八成的「串口不通」。剩下的多半是协议理解偏了——设备手册写的帧格式和固件实际发的对不上。

抓包在串口上就是打印：收一个字节打一行 toHex()，把设备实际发的和你以为它该发的并排放，差异立刻现形。别嫌日志丑，它比任何推理都快。
