本篇讲二维码在 Qt 里的两件事：把数据生成图形，把图形识别回数据。这两件事在工程上是两个问题，用的库也不一样，选型时必须拆开看。

生成端可以自己画，也可以调编码库，工作量在编码逻辑不在绘制；识别端必须用成熟库，自己写二值化加定位加解码，性价比极低。

边界：不展开码制的国家标准文本，不复述 Reed-Solomon 的数学推导，不涉及扫码枪与工业读码器硬件，不碰相机标定。摄像头那部分只讲到拿到帧为止。

找邻居：识别结果要上报服务端，协议部分看《Qt 网络编程：TCP、UDP 与 HTTP》；报文格式看《JSON 与 XML 数据处理》；批量扫描的清单要落盘，看《文件、配置与表格》；外挂命令行工具看《进程：QProcess 与单实例控制》。

一、二维码是什么 #

二维码（QR Code，Quick Response Code）使用特定的几何图形按一定规律在平面（二维方向）上分布的黑白相间图形来记录数据符号信息。作为移动互联网时代最常见的信息入口，它已经用在了产品防伪溯源、名片交流、商品交易和移动支付这些场景里。

理解它的第一步，是把它和一维码摆在一起看。

1.1 一维码与二维码 #

一维码只能在水平方向上表达信息，信息量小，一般只能容纳几十个字符，也多由数字和字母组成，对磨损和褶皱的容错性极低。二维码在水平和垂直两个方向都能存储和传递信息，容量大得多，汉字、数字、二进制流、网址甚至图片信息都能装，还带纠错机制，部分区域污损或撕裂依然能正常解码。

维度 一维码 二维码
信息方向 仅水平 水平 + 垂直
容量 几十个字符 可达数千字符
字符集 数字与字母为主 汉字、数字、二进制流、网址、图片信息
纠错 无，只有校验位 L、M、Q、H 四级纠错
破损容忍 极低 局部污损或撕裂仍可解码
典型载体 商品条码、物流单号 支付码、名片、门票、设备铭牌

一句话概括差别：一维码是「一行数据加个校验」，二维码是「一块数据加一套能自我修复的冗余」。前者读不出来就是读不出来，后者还能从残缺里算回原文。

1.2 常用码制 #

二维码不是只有 QR 一种。工程上会碰到的码制有这么几种：

码制 定位方式 常见场合
QR Code 三个回字形定位图案 支付、名片、网址、屏显
Data Matrix L 形实边加交替边 小面积零件标记、电子元件
PDF417 行首行尾起始符 证件、货运单据
Aztec 中心同心方块 车票、登机牌
MaxiCode 中心靶心图案 高速物流分拣

本篇只讲 QR Code。原因是它在 Qt 这套工具链里支持最全，生成和识别都有现成库可用；其余几种要么识别库要另外买，要么在开源侧只有单项支持。

1.3 生成与识别是两件独立的事 #

这是本篇最该先立住的一条认知。很多项目上来就问「有没有一个好用的二维码库」，问法就错了——你得先分清自己要的是哪一半。

项 生成 识别
输入 数据（字符串或字节流） 图像（灰度或彩色位图）
输出 模块矩阵或位图 原始字符串
核心工作 分段编码、纠错码计算、掩码选择 二值化、定位、透视校正、解码
依赖规模 几十 KB 的纯 C 库就够 数千行的图像处理加解码实现
能否自研 能，短内容、固定版式场景可行 不建议
Qt 侧常用 libqrencode、QZXing 自带编码器 QZXing、ZBar、quirc

生成是把「数据」编译成「图形」，本质是编码问题，输出可以逐字节验证，对错一目了然。识别是把「图形」还原成「数据」，本质是图像处理问题，输入是脏的、歪的、糊的、有噪的，容错策略决定成败。

把这两件事混在一起想，就会得到一个贪心的结论：找一个「既会生成又会识别」的库。现实里这种库确实有（ZXing 就是），但它在生成端的接口往往比专用生成库啰嗦，在识别端的体积又比专用识别库大。分开选，两边都能拿到更合适的那个。

1.4 Qt 在这两件事里的角色 #

Qt 不做编解码，Qt 做的是外围那群脏活：

  • 把生成的位图塞进控件、写进文件、打到打印机、贴到界面上。
  • 从摄像头拿到 QVideoFrame 转成 QImage，交给解码库，把结果发信号槽。
  • 处理线程、节流、重试、批量遍历。

所以你会在后面看到大量的 QImage、QPainter、QVideoSink，而真正的编码解码只有几行。

二、QR 码的结构与纠错 #

要让识别率可控，得知道识别器在看什么。QR 码不是「一堆随机黑白块」，它有明确的分区，每一块都有活干。

2.1 模块与版本 #

QR 码是一格一格的黑白方块拼出来的，这一格叫模块（module）。规范定义 40 个版本，边长按固定公式走：

text
边长（模块数） = 17 + 4 × 版本号

版本 1 是 21×21，版本 40 是 177×177。版本越高装得越多，单模块的物理尺寸越小。这个公式是结构常量，识别器也靠它反推版本。

2.2 功能图形 #

一张 QR 码里，真正装数据的地方只占一部分，其余位置给了功能图形。

图形 位置 作用 坏了的后果
定位图案 finder pattern 左上、右上、左下 7×7 回字形，黑白按 1:1:3:1:1 排列，用来找码和定方向 根本找不到码，或者方向判反
分隔符 separator 定位图案外侧一圈白 把定位图案和数据区隔开 边界糊，定位精度下降
定时图案 timing pattern 第 6 行与第 6 列 黑白交替，用来推算单个模块的尺寸 模块尺寸估错，整片栅格错位
校正图案 alignment pattern 版本 2 起出现，数量随版本增长 5×5 小方块，抗透视畸变与曲面形变 斜拍、弯折表面上的码解不出
格式信息 定位图案旁，存两份 记纠错等级与掩码号 等级读错，解码全盘失败
版本信息 版本 7 起出现 标明版本号 高版本码被判成低版本
数据与纠错码字区 除上述图形外的位置 装实际比特流 坏了靠纠错等级救
静区 quiet zone 四周至少 4 个模块宽 给扫描器留白边 贴边裁切，定位图案黏到背景上

三个定位图案给的是坐标系，定时图案给的是比例尺，校正图案给的是形变补偿。识别器第一步永远是找这三个回字，找不到就什么都不用谈。

这也解释了为什么二维码四个角里只有三个有定位图案：第四个角空出来，是为了让你一眼就能判断码的正方向——回字围成的是左上、右上、左下，缺的那个角是右下。

2.3 一张码是怎么编出来的 #

从字符串到黑白方块，中间要走七步：

text
1. 数据分析      判断用哪种模式：数字、字母数字、字节、汉字
2. 数据编码      按模式把内容转成比特流
3. 纠错编码      分块后逐块算 Reed-Solomon 纠错码字
4. 构造最终序列  数据码字与纠错码字按规则交织
5. 布置模块      先放功能图形，剩下的位置按蛇形填数据
6. 掩码          试 8 种掩码，按惩罚分选最不容易误判的一种
7. 写格式信息    把纠错等级与掩码号写进格式区

第 6 步最容易出问题。掩码的目的是打散大片同色区域，避免出现和定位图案相似的块导致误判。掩码选错不会立刻出错，只在特定图案下让识别率变差——这类问题在测试集里很难复现。

2.4 四档纠错等级 #

QR 码的纠错分四档，用字母表示：

等级 可恢复的码字比例（约） 直观印象 典型用途
L（Low） 7% 低 屏显、干净印刷、内容偏长
M（Medium） 15% 中 常规印刷品、名片、宣传页
Q（Quartile） 25% 较高 有磨损风险的贴纸、户外铭牌
H（High） 30% 高 中间要压 logo、表面易脏、长期暴露

这三个百分比说的是纠错码字能修复的比例，不是「能撕掉 30% 的面积」。这个区别在实际项目里被反复误解：

  • 损伤落在数据区，纠错码字能算回原文。
  • 损伤落在定位图案、定时图案或格式信息上，纠错等级再高也救不回来。
  • 损伤分散且面积大，局部看起来只坏了一点，但坏掉的是同一条纠错块里的太多码字，仍然失败。

所以 H 不是万能护身符。它的作用是「容忍码字级错误」，不是「容忍任意破损」。

三、容量与纠错等级的取舍 #

容量不是一个固定数字，它同时受三件事约束：版本、纠错等级、编码模式。素材里说二维码可达数千字符，这是上限附近的量级；具体一张码能装多少，视版本与纠错等级而定。

3.1 三个变量 #

  • 版本。版本决定模块总数，也就决定了总码字数。版本越高装得越多。
  • 纠错等级。纠错码字和数据码字共用总容量，纠错占比越高，留给数据的位置越少。
  • 编码模式。数字模式最省，一个字符占不到一字节；字母数字模式次之；字节模式每个字符固定 8 bit；汉字模式按固定宽度编码。

同一条内容，纠错等级从 L 升到 H，需要的纠错码字变多，版本就得往上走；版本上不去，内容就得砍。这就是容量与鲁棒性之间的直接交换。

3.2 怎么选等级 #

场景 建议等级 理由
屏幕显示、内容偏长（带参数的 URL） L 或 M 屏显没有物理磨损，省下的容量换更低的版本
普通印刷品、名片、宣传页 M 折痕与油墨扩散在 M 的容忍范围内
设备铭牌、户外标签、易脏表面 Q 有油污、刮擦、日照老化
中间要压 logo、码面会被部分遮挡 H 遮挡必须落在纠错能力之内
面积被卡死、又必须装长内容 优先降版本 硬升等级会把模块压到印不出来

3.3 三个反直觉的地方 #

第一，等级升高不总等于识别率升高。等级升高，同版本容量变少，想装同样内容只能升版本，版本升高模块变多，同一块物理面积里每模块占的像素就变少。在指甲盖大小的贴纸上，Q 往往比 H 好读，因为 H 把模块压到打印机的分辨极限以下了。

第二，内容别硬塞。一个带三个查询参数的长 URL 和一条短链，就是两个版本的差距。版本差一档，模块数差一圈，能不能扫出来是另一回事。

第三，静区不占容量但必须留。它不参与编码，只是四周的空白，排版时忘了留，定位图案直接和背景粘在一起，识别器连码在哪都判断不出来。素材里的生成示例之所以都带 margin 参数，就是这个原因。

四、生成：用 qrencode 系列库 #

生成端的第一选择是 libqrencode，常被写成 QRencode 或 qrencode。它是使用纯 C 语言编写的、用于将字符串编码为二维码的程序库，执行速度快，极易嵌入到各种微控制系统或移动应用中。项目地址：http://fukuchi.org/works/qrencode/。

它有两个使用身份，别混：

  1. 命令行程序 qrencode，把内容直接输出成 PNG、EPS、SVG 或终端点阵。
  2. 动态库 libqrencode，头文件 qrencode.h，返回一个 QRcode 结构。

只生成、不改内容，用命令行最省事；要在程序里批量生成、要自己控图案，就链库。

4.1 用命令行生成 #

text
qrencode -o card.png -s 8 -l Q -m 4 "https://example.com/device?id=A1024"

四个参数各管一件事：-s 是每个模块的像素数，-l 是纠错等级，-m 是静区模块数，-o 是输出文件。要交印刷厂，把输出类型换成矢量：-t EPS 或 -t SVG。

Qt 里用 QProcess 调它：

cpp
QProcess proc;
proc.setProgram("qrencode");
proc.setArguments({"-o", outPath, "-s", "8", "-l", "Q", "-m", "4", payload});
proc.start();
if (!proc.waitForFinished(5000) || proc.exitCode() != 0) {
    qDebug() << "qrencode failed:" << proc.readAllStandardError();
}

这条路的代价是多一个外部依赖：发布时得把 qrencode.exe 一起打包，还得处理它的路径和临时文件。程序里只有「偶尔导出一张码」这个需求时，值得；做成产品功能，就别这么干。

4.2 直接链库 #

QT += core gui
INCLUDEPATH += $$PWD/third_party/qrencode
LIBS += -L$$PWD/third_party/qrencode/lib -lqrencode

Windows 上要么把 libqrencode.lib 放进工程，要么把源码目录整个编进来。源码方式的文件不多，省掉了链接配置和运行动态库的麻烦，静态发布时这条路更稳。

4.3 典型调用形态 #

cpp
#include <QImage>
#include "qrencode.h"

QImage makeQrImage(const QByteArray &payload, int scale, int margin)
{
    // 版本传 0 表示让库自己挑最小的能装下的版本
    QRcode *code = QRcode_encodeString(payload.constData(),
                                       0,             // 版本：0 = 自动
                                       QR_ECLEVEL_Q,  // 纠错等级
                                       QR_MODE_8,     // 字节模式
                                       1);            // 区分大小写
    if (!code) {
        return QImage();
    }

    const int modules = code->width;                  // 边长，单位是模块数
    const int side    = (modules + margin * 2) * scale;
    QImage img(side, side, QImage::Format_Grayscale8);
    img.fill(255);

    // data 里每字节对应一个模块，最低位为 1 表示深色
    const unsigned char *bits = code->data;
    for (int y = 0; y < modules; ++y) {
        for (int x = 0; x < modules; ++x) {
            if (!(bits[y * modules + x] & 1)) {
                continue;
            }
            const int px = (x + margin) * scale;
            const int py = (y + margin) * scale;
            for (int dy = 0; dy < scale; ++dy) {
                unsigned char *line = img.scanLine(py + dy);
                for (int dx = 0; dx < scale; ++dx) {
                    line[px + dx] = 0;
                }
            }
        }
    }

    QRcode_free(code);
    return img;
}

这段代码里要你核对的只有两处：枚举名的写法，以及 QRcode 结构体的字段名。不同年份的发行版在这上面有细微出入，以你手上那份 qrencode.h 为准。字段语义倒是多年没变——width 是模块边长，data 每字节一个模块，最低位为 1 表示深色。

手动填像素而不是用 QPainter 画矩形，是因为这里画的是纯黑白图，一个模块就是一块实心方块，直接改 scanLine 比走绘图管线快，也不用担心抗锯齿。

4.4 生成端的四个注意点 #

scale 取整数。2.5 这种值会让模块边界落在半像素上，边缘出现灰色过渡带，二值化之后模块栅格偏移，识别率掉得莫名其妙。margin 至少 4 个模块，库本身不会替你加，静区是你的责任。

内容用 QByteArray 传，别用 QString::toLatin1() 糊弄。中文走 UTF-8 字节流，落进字节模式，识别端按 UTF-8 解回来，两头都按字节对齐。生成的开销很小，瓶颈在 I/O 和内存分配，不在编码本身——也不值得为生成做缓存层。

4.5 QZXing 自带的编码器 #

QZXing 除了识别，也带了一个二维码编码器。工程里已经引了 QZXing，就不必再拉一套 libqrencode，少一个依赖。编码接口的参数和可选范围，看你自己那份源码里的头文件——不同分支的能力差别不小。

五、生成：纯 Qt 实现思路 #

有时候不能引第三方库：静态编译、嵌入式裁剪、合规审查、只生成一张固定内容的码。这时候会想到「用 Qt 自己画一个」。

先把话说明白：Qt 能画，但不能编。这一节讲的是编码逻辑之外的那部分——怎么把模块矩阵变成一张合格的图。

5.1 工作量在编码，不在绘制 #

真正的活是：分段、查表、生成纠错码字、交织、掩码评分、写格式信息。这套逻辑从零写一遍，等于把规范抄一遍，还得自己找测试向量验证每一档等级、每一个版本。

所以纯 Qt 方案只在一类场景成立：内容固定、尺寸固定、版本固定，团队愿意维护那几百行编码逻辑。要做通用工具，老老实实调库。

绘制部分是另一回事。这部分 Qt 干得比谁都顺手，一个双重循环加一个 QPainter 就完事。

5.2 绘制代码 #

cpp
QImage renderMatrix(const QVector<QVector<bool>> &matrix, int scale, int margin)
{
    const int modules = matrix.size();
    const int side    = (modules + margin * 2) * scale;

    QImage img(side, side, QImage::Format_Grayscale8);
    img.fill(255);

    QPainter p(&img);
    p.setRenderHint(QPainter::Antialiasing, false);   // 必须关
    p.setPen(Qt::NoPen);
    p.setBrush(Qt::black);

    for (int y = 0; y < modules; ++y) {
        for (int x = 0; x < modules; ++x) {
            if (matrix[y][x]) {
                p.drawRect((x + margin) * scale, (y + margin) * scale,
                           scale, scale);
            }
        }
    }
    p.end();
    return img;
}

关掉抗锯齿是关键一步。开着确实让边缘看着平滑，但模块边界会带半透明像素，二值化之后边界位置随机偏移一像素。识别器靠定时图案推算模块尺寸，一像素的偏移在低版本码上就是整片栅格错位。

5.3 逐行合并少调用 #

上面的写法每个深色模块调一次 drawRect。版本 1 是 441 次，版本 10 是 57×57 三千多次，调用开销开始显形。优化办法是把同一行里连续的深色模块合成一条宽矩形：从 (x + margin) * scale 画到 (x + run + margin) * scale，一条顶若干个。调用次数降一个量级。单张偶尔生成不必写这段，早跑完了。

5.4 输出到屏幕与纸面 #

  • 屏幕显示。控件里用 QLabel::setPixmap，或者自己在 paintEvent 里画，别让图片被 scaled 拉伸到非整数倍，Qt::FastTransformation 在这里比平滑缩放好。
  • 打印。每模块像素数取整，还需要把 DPI 设对：img.setDotsPerMeterX(...)、setDotsPerMeterY(...)。不设的话，打印机按自己的默认 DPI 换算，一张名片大小的码能印成邮票。
  • 印刷厂。要矢量。QPainter 换到 QPdfWriter 或 QSvgGenerator 上画同一套矩形，交 PDF 或 SVG 出去，让印厂自己 RIP。交 PNG 是给自己找返工。

5.5 什么时候别自己画 #

只做「矩阵转图片」这件事，libqrencode 已经给了位图，自己画没有收益。自己画的理由只有一个：要在码中间压 logo、要按模板排版、要出一张带标题和编号的标签。这类版面活本来就是 QPainter 的地盘。

六、识别：QZXing 的集成 #

识别端不要自己写。这不是保守，是算术：二值化、连通域、定位图案检测、透视变换、格式信息纠错、掩码还原、分块解交织、Reed-Solomon 纠错，每一步都有边界条件，一套跑通的实现是一万多行的量级。

Qt 项目里的主流选择是 QZXing。

6.1 QZXing 是什么 #

QZXing 是对 ZXing（C++ 移植版）进行的 Qt 风格封装库。它将复杂的图像条码解析过程高度抽象，为 Qt/QML 程序开发提供了便利的接口支持。项目地址：http://sourceforge.net/projects/qzxing。

一句话理解它：把 ZXing 那套 Java 风格的 C++ 移植代码，用 QImage 和 QString 包了一层，让你三行就能解一张码。

它的职责边界要清楚：它只做识别（外加一个可选编码器），不负责摄像头取帧、不负责界面、不负责重试节流。这些是第七章和第九章的事。

6.2 集成到工程 #

两条路。第一条，把 qzxing.pri include 进来：

QT += core gui
include($$PWD/third_party/QZXing/src/QZXing.pri)

路径按你拉下来的目录结构调整。pri 里已经写好了源码文件列表和大部分编译配置，你要确认的是 C++ 标准版本够不够，以及有没有和工程里的其它宏冲突。

第二条，把 QZXing 的源码目录直接加进 SOURCES 和 HEADERS。啰嗦，但静态编译时省事——原因见第十章。

6.3 基本调用 #

cpp
#include <QImage>
#include <QDebug>
#include "QZXing.h"

void decodeQRCode(const QString &imagePath)
{
    QImage image(imagePath);
    if (image.isNull()) {
        qDebug() << "Failed to load image:" << imagePath;
        return;
    }

    QZXing decoder;
    // 只解二维码，省掉一维码和其它码制的尝试，识别更快
    decoder.setDecoder(QZXing::DecoderFormat_QR_CODE);

    const QString result = decoder.decodeImage(image);
    if (result.isEmpty()) {
        qDebug() << "Decode failed: no QR code found.";
    } else {
        qDebug() << "QR Code decoded:" << result;
    }
}

两个细节值得说。setDecoder(QZXing::DecoderFormat_QR_CODE) 是性能开关，默认开着多种码制，每解一帧都要挨个试一遍；只解二维码就只跑 QR 那一条路。decodeImage 返回空 QString 表示没解出来，它不区分「图里没有码」和「有码但解不开」，这两种情况在第九章要用不同策略处理。

6.4 对象复用、线程与 QML #

QZXing 构造时会准备内部状态。循环解码时把它提到循环外，别每张图 new 一个。要并发，每线程一个实例，不要跨线程共享同一个对象——它的内部缓冲不是线程安全的。decodeImage 还是同步阻塞的，放在 GUI 线程里连续调用界面就定格了；第七章给的做法是节流加单飞，彻底的做法是挪进 worker 线程。

QML 侧它带注册入口，能把 QZXingFilter 直接挂在 VideoOutput 上，省掉手写的取帧转发。过滤器的解码发生在自己的线程，结果显示到 UI 要经由信号；线程、节流、重试策略写在 C++ 侧更好控。

6.5 常见库对照 #

库 语言 生成 识别 Qt 集成难度 备注
libqrencode C ✓ ✗ 低 只做 QR，生成端首选，速度快、易嵌入
ZXing Java 为主 ✓ ✓ 中 谷歌主导的多格式 1D/2D 条码图像处理库，有 C++/C#/Python/Android 等移植
QZXing C++ / Qt 有限 ✓ 低 ZXing C++ 移植的 Qt 封装，Qt 项目识别主流选择
ZBar C ✗ ✓ 低 支持摄像头视频流与静态图片，跨 Windows/Linux/iOS，C/C++ API 易用
quirc C ✗ ✓ 低 单文件实现，只认 QR，代码量小，适合裁剪

选型的顺序是：只生成，用 libqrencode；只识别 QR，看重体积用 quirc、看重兼容用 QZXing；还要认一维码或要从视频流里持续扫，ZBar 的流式支持更顺手；要在多语言、多端共用一套解码逻辑，直接看 ZXing 上游。

七、识别：从摄像头取图 #

静态图片识别是「一次性」问题，摄像头识别是「流」问题。差别不在解码，在取帧、节流、线程。

7.1 Qt5 与 Qt6 的取帧路线不同 #

环节 Qt5 Qt6
设备 QCamera QCamera
会话 无此概念，直接 setViewfinder QMediaCaptureSession
取帧 QVideoProbe 或自写 QAbstractVideoSurface QVideoSink::videoFrameChanged
帧转图 QVideoFrame::image() QVideoFrame::toImage()
模块 multimedia multimedia + multimediawidgets

Qt6 把 QVideoProbe 拿掉了，换成了 QVideoSink。老代码迁移时这一处必须改，编译不过就是卡在这里。

7.2 三条硬规矩 #

摄像头跑 30 fps，一帧 640×480，每帧都丢给解码器，界面和 CPU 一起遭殃。第一，节流：用 QElapsedTimer 记上次解码的时刻，间隔不足就直接丢帧。解码一次几十毫秒，人眼不需要每秒三十次结果。

第二，单飞。上一次解码还没返回，新帧不进去。用一个原子标志守住即可。不做这一步，任务会在信号队列里越堆越多，最后卡死在解码上。

第三，下采样。1600×1200 的帧先缩到工作宽度；模块够大就行，多余像素只是让解码器多扫几圈。

7.3 Qt6 的实现 #

cpp
class QrScanner : public QObject
{
    Q_OBJECT
public:
    explicit QrScanner(QObject *parent = nullptr) : QObject(parent)
    {
        m_decoder.setDecoder(QZXing::DecoderFormat_QR_CODE);
        m_clock.start();
    }

public slots:
    void onFrame(const QVideoFrame &frame)
    {
        if (!frame.isValid() || m_busy.loadAcquire()) {
            return;
        }
        if (m_clock.elapsed() < 200) {          // 节流：200 ms 内不重复解码
            return;
        }

        QImage img = frame.toImage();           // Qt6 的接口
        if (img.isNull()) {
            return;
        }

        m_clock.restart();
        m_busy.storeRelease(1);

        if (img.width() > 800) {                // 缩到工作尺寸
            img = img.scaledToWidth(800, Qt::FastTransformation);
        }
        img = img.convertToFormat(QImage::Format_Grayscale8);

        const QString text = m_decoder.decodeImage(img);
        m_busy.storeRelease(0);

        if (!text.isEmpty()) {
            emit decoded(text);
        }
    }

signals:
    void decoded(const QString &text);

private:
    QZXing        m_decoder;
    QElapsedTimer m_clock;
    QAtomicInt    m_busy{0};
};

接线：

cpp
auto *sink = new QVideoSink(this);
auto *session = new QMediaCaptureSession(this);
session->setCamera(camera);
session->setVideoSink(sink);
connect(sink, &QVideoSink::videoFrameChanged, scanner, &QrScanner::onFrame);

QVideoSink 归 QMediaCaptureSession 管，QrScanner 只认 QVideoFrame。这两层拆开之后，换设备、换后端都不用动解码代码。

7.4 挪进线程 #

上面的写法跑在 GUI 线程里，靠节流把卡顿压到可接受。要彻底不卡，把 QrScanner 挪到 worker 线程：new QThread(this) 加 scanner->moveToThread(thread)，再 thread->start()，三行的事。

注意两件事。一是 QZXing 实例跟着它所在的线程走，moveToThread 要在构造完成之后、开始使用之前调用。二是跨线程传 QImage 会走隐式共享的拷贝，帧率高的场景下这份开销也要算进去——这正是节流必须存在的原因。

7.5 摄像头本身的坑 #

近距对焦。扫码的常用距离在十几厘米到几十厘米，定焦摄像头在这个距离上就是糊的。选支持自动对焦的模组，或者引导用户退远一点、把码对准画面中央。

分辨率。低于 640×480 时，稍远的小码解不出；上到 1920×1080 只是让解码更慢。中间那档最舒服。

帧格式。有些后端 toImage() 给的是 YUV 转换过来的图，色偏明显。先转灰度再解码，比拿彩色图硬解稳。

画面方向。手机模组常是横装竖用，QVideoFrame 给出来的图是旋转的。这一点在真机上才会暴露，模拟器和桌面摄像头看不出来。

八、识别：从图片文件取图 #

摄像头之外，剩下的输入都是文件：用户选的一张图、服务器下发的一批图、扫描仪导出的一叠图。

8.1 一行代码，和它背后的坑 #

QImage image(path); 就够了——前提是 imageformats 插件在位。这个问题开发机上永远看不到，因为开发机装了完整 Qt，插件齐全；拷到裸机上，QImage 直接返回 null，isNull() 判空，你得到「图片加载失败」，而文件明明在那儿。原因和补法见第十章。

判断失败原因时，QImage 的 null 没有信息量，换 QImageReader：

cpp
QImageReader reader(path);
reader.setAutoTransform(true);      // 按 EXIF 方向摆正，手机照片必须
const QImage img = reader.read();
if (img.isNull()) {
    qDebug() << "read failed:" << reader.errorString()
             << "supported:" << QImageReader::supportedImageFormats();
}

setAutoTransform 这一行是必须的。QImage(path) 不读 EXIF 方向，手机竖拍的照片存成横向像素加一个旋转标记，直接解会得到一张躺倒的码，识别器照样找不到定位图案。

8.2 大图先缩，解不出再回退 #

4000×3000 的手机照片直接进解码器，时间全花在扫描整幅图上。做法是先缩一版解一次，解不出再回退到更大的尺度。缩放用 Qt::SmoothTransformation，避免把模块锯齿化。

cpp
QString decodeWithRetry(QZXing &decoder, const QImage &src)
{
    const QList<int> widths = {1600, 1000, 640};
    for (int w : widths) {
        QImage img = src;
        if (img.width() > w) {
            img = img.scaledToWidth(w, Qt::SmoothTransformation);
        }
        img = img.convertToFormat(QImage::Format_Grayscale8);

        QString text = decoder.decodeImage(img);
        if (!text.isEmpty()) {
            return text;
        }

        QImage inverted = img;
        inverted.invertPixels();        // 深底浅码，屏显截图里常见
        text = decoder.decodeImage(inverted);
        if (!text.isEmpty()) {
            return text;
        }
    }
    return QString();
}

尺度别贪多，三个够用。每多一个就是一次全图扫描，批量场景里这份开销会翻倍。

8.3 批量场景 #

扫目录里的图，逐张过，失败项记日志而不是弹窗。用 QDirIterator 带上后缀过滤遍历，别把整批图一次性读进内存。QZXing 实例放在循环外复用——每张图 new 一个，构造开销会盖过解码本身。

九、识别率与预处理 #

识别失败时，先判断是哪一类失败，再动预处理。乱加步骤只会让本来就慢的流程更慢。

现象 原因 处理
整体解不出，肉眼能看清 深底浅码、反色显示 invertPixels() 后重试
大图慢且解不出 模块被算法当成噪点 降尺度，或裁 ROI 再解
小图解不出 模块只有一两个像素 双线性放大 2~3 倍再解
斜拍解不出 透视形变超出校正图案能力 减小拍摄角度；低版本码没有校正图案
局部污损解不出 错误超出纠错等级 源头升等级，识别端无解
屏显拍照解不出 摩尔纹、刷新条纹 换距离或角度，降亮度
贴边裁切解不出 静区被裁 解码前给图外扩一圈白边
模糊 对焦不准、运动模糊 换对焦方式，别指望锐化救回来

两条实践结论。第一，预处理不要做成流水线，做成「按序尝试、成功即停」：先原图，再反色，再放大，再缩小的顺序跑一遍，命中就返回。第二，识别率的上限由源头的生成质量决定——纠错等级、静区、打印尺寸在生成端定死，识别端只能弥补，不能创造信息。

十、打包发布注意事项 #

这一章的坑，在开发机上全都看不见。

10.1 图片格式插件 #

在 Windows 平台上用 Qt 编写并打包发布二维码扫描程序（生成的 .exe）时，常会碰到一个现象：开发机上运行一切正常，拷贝到其他裸机电脑上却无法识别和读取 JPG、PNG 等格式的图片。

原因是 Qt 加载除基本 BMP 以外的图片格式时，要靠底层格式插件，而这些插件不在 exe 里。

解法：

  1. 在可执行程序目录（如 release/）下新建一个名为 imageformats 的文件夹。
  2. 从 Qt 安装目录的插件目录里，把对应的插件动态库拷进去。必须包含 qjpeg.dll（JPG 支持）、qgif.dll（GIF 支持）、qico.dll 等。
  3. 保持这样的目录层级：
text
YourApp/
  |-- YourApp.exe
  |-- Qt5Core.dll
  |-- Qt5Gui.dll
  |-- imageformats/
        |-- qjpeg.dll
        |-- qgif.dll
        |-- qico.dll

Qt6 下这些 dll 同名前缀是 Qt6，插件文件名不变。用 windeployqt 会自动带上 imageformats 目录，手工拷贝时最容易漏——漏了就是「图片加载失败」，而错误信息看不出是插件问题。

10.2 QZXing 的编码表与资源 #

QZXing 内部带着编码表数据与图标资源。常规动态构建时，这些内容编进库里，你感知不到；静态编译或把源码塞进工程时，资源要靠自己的 .qrc 一起编进去。

漏了的表现是：编译链接全过，程序启动正常，一解码就返回空。没有崩溃、没有警告，最难查。

补法有两条，任选一条：

  • 把 QZXing 自带的 .qrc 加进工程的 RESOURCES，让 rcc 一起处理。
  • 直接把 QZXing 的源码目录整体加入 SOURCES 与 HEADERS，别只链 .a 或 .lib。

第二条是静态发布里更省心的做法——源码进工程，资源、编码表、编译选项都跟着走，不依赖别人编好的二进制。

10.3 静态编译的插件注册 #

静态版本的 Qt 不会自动发现插件，得手工注册：

cpp
#include <QtPlugin>
Q_IMPORT_PLUGIN(QJpegPlugin)
Q_IMPORT_PLUGIN(QGifPlugin)

不写这两行，静态版同样读不了 JPG 和 GIF，表现和忘了带 imageformats 目录一模一样。

10.4 发布清单 #

漏带的东西 现象 补法
imageformats/ 目录 裸机上读不了 JPG/PNG，开发机正常 目录与插件一起拷，或用 windeployqt
QZXing 的 .qrc 编译通过，解码恒返回空 资源加进工程，或源码整体编入
静态插件注册 静态版读图失败，同上 加 Q_IMPORT_PLUGIN
platforms/qwindows.dll 程序起不来，报缺少平台插件 与 imageformats 同级一起带
摄像头后端 能开界面，出不了画面 确认 multimedia 相关 dll 与后端插件在位

打包这件事没有聪明办法，只有一张清单加一台干净的虚拟机。开发机上跑通不算数，裸机上跑通才算。

十一、性能与适用场景 #

11.1 两端的成本结构完全不同 #

项 生成 识别
典型耗时 很短，可实时、可批量 明显更长，跟分辨率与内容成正比
瓶颈 I/O、内存分配、文件编码 全图扫描、二值化、纠错计算
线程建议 UI 线程可直接做 连续解码放 worker 线程
优化手段 代码量极少，几乎不用优化 降分辨率、裁 ROI、节流、单飞、限定码制
失败代价 无，输入输出确定 有，需重试与兜底

11.2 什么时候用二维码，什么时候别用 #

场景 判断
扫码登录、支付、票务核销 用，内容短、环境可控
设备配网、参数下发 用，比手输 IP 与密钥靠谱
工业追溯、铭牌标识 用，但选 Q 或 H，配合耐磨标签材质
极小面积标记 换 Data Matrix，同等面积密度更高
高速运动物体 别用，改成 RFID 或固定式读码器
强反光金属表面 别用，改打标方式或换读码硬件
承载几百 KB 数据 别用，二维码存索引，内容放服务端

最后一条在工程上最常被违背。二维码的定位是「轻量入口」，不是存储介质。几百 KB 的配置塞进码里，生成出来是版本 40 的满屏方块，拍摄条件稍差就解不出。

十二、易错点速查 #

现象或写法 原因 改法
