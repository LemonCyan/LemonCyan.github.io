讲什么：一个网络应用从发请求到出声的全过程。用 QNetworkAccessManager 发出 HTTP 请求，用 QJsonDocument 系列类解开响应，把结果填进列表控件，用 QMediaPlayer 把在线音频放出来，最后拿 lrc 歌词和时间轴对上。

不讲什么：HTTP 报文结构、TLS 握手过程、音频编解码原理。这些是网络课和音视频课的内容，这里只用到接口层面。也不展开 QNetworkAccessManager 的类级细节，比如代理配置、磁盘缓存、cookie 策略。

跨篇指路：QNetworkAccessManager 的完整用法（代理、缓存、SSL、上传下载进度）在「Qt 网络编程」一篇；QJsonValue 的转换规则、XML 的读写、两种格式的取舍在「JSON 与 XML」一篇；播放器的界面搭建、进度条与音量条在多媒体相关篇目里。本篇只做一件事：把一次真实可跑的应用从头串到尾。

先说一处现实问题。素材里的两个接口地址来自百度音乐的旧公开接口，早已停止服务。正文保留它们，标注为「历史地址」，用于说明参数结构。你动手时换成任一公开音乐 API，下面讲的流程一行都不用改。第十一章专门讲这件事的应对办法。

一、这个实例串起了什么 #

四步流程：搜歌、取地址、解析、播放。素材给的流程图是 mermaid，这里换成纯文本，看得更直接：

text
用户输入关键字
      |
      |  QNetworkAccessManager::get()
      v
调用音乐搜索接口  ---------->  JSON 响应
      |
      |  QJsonDocument 解析，取出 song / song_id
      v
按 song_id 请求详情接口  ---->  songLink / lrcLink
      |
      +---> QMediaPlayer::setMedia(QUrl(songLink)) ---> 在线播放
      |
      +---> QNetworkAccessManager::get(lrcLink) -----> 逐行解析 lrc
                                                          |
                                        positionChanged(qint64) 驱动滚动

每一步都有明确的输入输出，这是这个实例能串起来的原因：

步骤 动作 用到的东西 产出
1 拼查询地址 QUrl、QUrlQuery 一个完整的 GET 地址
2 发请求 QNetworkAccessManager::get 一个 QNetworkReply*
3 等回调 QNetworkReply::finished 信号 可读的 QByteArray
4 解析 QJsonDocument、QJsonArray、QJsonObject 歌名、song_id
5 二次请求 同一个 manager songLink、lrcLink
6 播放 QMediaPlayer::setMedia + play 声音
7 歌词同步 positionChanged 滚动的歌词行

这里真正的新东西只有三块：网络请求、JSON 解析、媒体播放。其余全是 Qt 常规的信号槽连接。

这三块有个共同点，也是本篇要反复强调的地方：它们的每一步都是异步的。调用发出去了，事情还没发生。所有后续处理只能写在槽里，写在外面就是空指针或者空数据。

二、发起一次 HTTP 请求 #

QNetworkAccessManager 是 Qt 网络模块的入口。它一个实例管所有请求，内部维护连接复用、缓存、cookie 和代理。这一点直接决定了用法：把它做成成员变量，或者做成一个更上层的单例，不要在每次请求时 new 一个新的出来。

素材里的写法是在函数里 new QNetworkAccessManager(this)，能跑，但每搜一次就多一个 manager、多一套连接池。写小例子可以，写应用要把这句提到类成员里。

请求本身用 QNetworkRequest 描述：地址、头部、附加属性。然后交给 manager：

cpp
#include <QNetworkAccessManager>
#include <QNetworkRequest>
#include <QNetworkReply>

#define MP3_URL "http://mp3.baidu.com/dev/api/?"   // 历史地址，已停服

void HttpManager::searchMusic(const QString &keyword)
{
    // 构造请求参数
    QByteArray queryParams;
    queryParams.append("tn=getinfo");
    queryParams.append("&ct=0");
    queryParams.append("&ie=utf-8");
    queryParams.append("&word=" + keyword);   // 输入的歌手或歌名
    queryParams.append("&format=json");

    QString url = QString(MP3_URL) + QString(queryParams);

    QNetworkAccessManager *network_manager = new QNetworkAccessManager(this);
    QNetworkRequest network_request;

    // 绑定请求完成的槽函数
    connect(network_manager, &QNetworkAccessManager::finished,
            this, &HttpManager::replyFinished);

    network_request.setUrl(QUrl(url));
    network_manager->get(network_request);   // 发送异步 GET 请求
}

这段代码的技术骨架是对的：拼参数、建请求、绑槽、调用。但有三处要改。

第一处，QByteArray 相加再转 QString 的写法不做百分号编码。关键字里带空格、&、+、中文，拼出来的地址就是坏的。搜「周杰伦 稻香」时 word= 后面那个空格会把 URL 截断，服务端只收到「周杰伦」，后半截当成新参数。用 QUrlQuery 处理这件事：

cpp
#include <QUrl>
#include <QUrlQuery>

QUrl buildSearchUrl(const QString &keyword)
{
    QUrl url(QStringLiteral("https://api.example.com/music/search"));

    QUrlQuery query;
    query.addQueryItem("tn", "getinfo");
    query.addQueryItem("ct", "0");
    query.addQueryItem("ie", "utf-8");
    query.addQueryItem("word", keyword);      // 自动做百分号编码
    query.addQueryItem("format", "json");

    url.setQuery(query);
    return url;
}

QUrlQuery::addQueryItem 替你完成转义，word 里放大括号、空格、中文都安全。取回来用 queryItemValue("word")，它给的是解码后的原值。

第二处，manager 提到成员里，请求头也能集中设置。公共 API 往往要求 Accept 或者某些站点要 User-Agent：

cpp
class HttpManager : public QObject
{
    Q_OBJECT
public:
    void searchMusic(const QString &keyword);
    void fetchSongDetail(const QString &songId);

signals:
    void searchFinished(const QJsonArray &songs);
    void detailFinished(const QString &songLink, const QString &lrcLink);
    void failed(const QString &message);

private:
    QNetworkRequest makeRequest(const QUrl &url) const;

    // 一个 manager 复用到底，别每次请求都 new
    QNetworkAccessManager *m_manager = new QNetworkAccessManager(this);
    QNetworkReply *m_searchReply = nullptr;
    QNetworkReply *m_detailReply = nullptr;
};

QNetworkRequest HttpManager::makeRequest(const QUrl &url) const
{
    QNetworkRequest request(url);
    request.setHeader(QNetworkRequest::UserAgentHeader,
                      QStringLiteral("BlogQtDemo/1.0"));
    request.setRawHeader("Accept", "application/json");
    return request;
}

第三处，别把地址写死在宏里。接口会换，域名会改，写死之后改一处漏一处。把基址做成变量或者配置项，路径拼在后面，这一条后面第十一章还会回来看。

GET 与 POST 的差别只在调用方法上，一条对照表：

动作 调用 请求体 典型场景
查列表、查详情 manager->get(request) 无 搜歌、取音频地址
提交表单 manager->post(request, body) QByteArray 登录、上报播放记录
表单编码 post(request, "application/x-www-form-urlencoded", query.toString().toUtf8()) 已编码字符串 老式接口
上传 JSON post(request, "application/json", doc.toJson()) JSON 字节 现代 REST 接口
只放头部 manager->sendCustomRequest(request, "HEAD") 无 探测文件是否存在

对搜索接口这种「只读」的调用，GET 就够了。POST 留给有副作用或者参数超长的动作。

还有一个细节值得当场记住：get() 的返回值就是那个 QNetworkReply*。素材里把它扔掉了，靠 manager 的 finished 信号在槽里取回来。丢掉返回值不是错，但等于放弃了对单个请求的精细控制，下一节和第十章都会讲这样做的代价。

三、QNetworkReply 的生命周期 #

这是 Qt 网络编程里最常踩的坑，放在显眼位置说：QNetworkReply 是 QObject，finished() 发出之后它不会自己销毁。你不管它，它就一直在堆上，一次请求漏一个。

看素材的槽，最后那句是关键：

cpp
void HttpManager::replyFinished(QNetworkReply *reply)
{
    // 检查 HTTP 状态码是否为 200 (正常)
    QVariant statusCode = reply->attribute(QNetworkRequest::HttpStatusCodeAttribute);

    if (reply->error() == QNetworkReply::NoError)
    {
        QByteArray bytes = reply->readAll();
        QString result(bytes);
        parseJson(result);          // 调用解析函数
    }
    else
    {
        // 处理网络请求错误
    }
    reply->deleteLater();           // 这一句不能漏
}

注意是 deleteLater()，不是 delete。原因在于此刻你正站在 reply 自己发出的信号调用栈里。直接 delete 会在对象还在派发信号的栈帧里把它销毁，后面所有对它的访问都是野指针，崩溃点常在你看不到的地方。deleteLater() 把销毁推迟到事件循环下一轮，安全。

两个必需的释放路径都要写：成功分支和失败分支。if 里 return 之前也要删。

一个对象的完整时间线：

阶段 谁在做事 对象状态 你能碰它吗
创建 manager->get() 返回 打开，等待 能，可设属性、可 abort()
传输中 内部读 socket isRunning() 为真 能，readAll() 只拿到已有部分
完成 发出 finished() 可读全部数据 能，这是唯一合适的读取窗口
你处理 槽函数执行 数据可读 能，readAll()、读 attribute()
延迟销毁 deleteLater() 排队 等待删除 不要再碰

围绕它有几个规律值得记住：

  1. finished() 只在结束时发一次，不管成功失败。判断成败看 error()，别看有没有数据。
  2. readAll() 是消耗性读取。第一次拿走全部，第二次读到空。想读两遍就先存进 QByteArray。
  3. attribute() 里的 HTTP 状态码在失败时同样能取到。404、500 都会走 finished()，只是 error() 非 NoError。
  4. 上传或者流式下载时，readyRead() 会多次触发，那是另一套读法。本篇的请求都小，等 finished() 一次读完就行。

QNetworkReply 常用的属性与状态判断：

用途 调用 说明
有没有出错 reply->error() 等于 NoError 才算成功
错误描述 reply->errorString() 可直接显示给用户
HTTP 状态码 attribute(QNetworkRequest::HttpStatusCodeAttribute) QVariant，转 int
内容类型 attribute(QNetworkRequest::ContentTypeHeader) application/json 之类
重定向目标 attribute(QNetworkRequest::RedirectionTargetAttribute) 需要二次请求
响应头 reply->rawHeader("Content-Length") 下载进度要用
请求对象 reply->request() 取回自己塞进去的 URL

connect 有两种写法，选错了会让槽变得难写。素材用的是 manager 的 finished：

cpp
connect(network_manager, &QNetworkAccessManager::finished,
        this, &HttpManager::replyFinished);

这种写法的问题是，manager 复用之后所有请求的完成都进同一个槽。搜歌的响应和取详情的响应长得完全不一样，槽里得靠 reply->request().url() 或者 reply->url() 反推这次是哪个请求。请求一多，这个判断就变成一团 if。

更稳的写法是给每个 reply 单独绑，用 lambda 把上下文带进去：

cpp
void HttpManager::fetchSongDetail(const QString &songId)
{
    QUrl url(QStringLiteral("https://api.example.com/music/links"));
    QUrlQuery query;
    query.addQueryItem("songIds", songId);
    url.setQuery(query);

    m_detailReply = m_manager->get(makeRequest(url));

    connect(m_detailReply, &QNetworkReply::finished, this, [this]() {
        QNetworkReply *reply = m_detailReply;
        m_detailReply = nullptr;

        if (reply->error() != QNetworkReply::NoError)
        {
            emit failed(reply->errorString());
            reply->deleteLater();
            return;
        }

        const QByteArray body = reply->readAll();
        reply->deleteLater();

        // 上下文齐全：这里是「取详情」的结果，不用猜
        emit detailFinished(parseSongLink(body), parseLrcLink(body));
    });
}

lambda 里捕获 this，connect 的第三个参数是 this，this 销毁时连接自动断开，槽不会打到野指针上。这是 Qt5 起信号槽的基本保障，用就对了。

四、解析 JSON 响应 #

Qt 自带 JSON 支持，不用引入任何第三方库。三个类够用：QJsonDocument 管整体，QJsonArray 管方括号，QJsonObject 管花括号。

素材的解析函数，先完整保留：

cpp
#include <QJsonDocument>
#include <QJsonObject>
#include <QJsonArray>

void HttpManager::parseJson(const QString &jsonData)
{
    QByteArray byte_array;
    QJsonParseError json_error;

    // 解析 JSON 文本
    QJsonDocument parse_document = QJsonDocument::fromJson(byte_array.append(jsonData), &json_error);

    if (json_error.error == QJsonParseError::NoError)
    {
        // 搜索接口返回的是一个数组列表
        if (parse_document.isArray())
        {
            QJsonArray array = parse_document.array();
            int size = array.size();
            for (int i = 0; i < size; ++i)
            {
                QJsonValue value = array.at(i);
                if (value.isObject())
                {
                    QJsonObject object = value.toObject();
                    QString song_name = "";
                    QString song_id = "";

                    // 获取歌曲名字
                    if (object.contains("song")) {
                        song_name = object.take("song").toString();
                    }

                    // 获取歌曲唯一的 ID
                    if (object.contains("song_id")) {
                        song_id = object.take("song_id").toString();
                    }

                    // 将解析到的结果填入界面上的歌曲列表控件 (如 QListWidget)
                    if (!song_name.isEmpty()) {
                        QListWidgetItem *item = new QListWidgetItem(song_name);
                        item->setData(Qt::UserRole, song_id);   // 绑定歌曲 ID
                        ui->listWidget->addItem(item);
                    }
                }
            }
        }
    }
}

结构是清楚的：判错、判类型、遍历、取值、填界面。四个细节值得展开。

第一，byte_array.append(jsonData) 这段多余。jsonData 本身就是 QString，fromJson 要的是 QByteArray，直接 jsonData.toUtf8() 就行。先声明空 QByteArray 再 append 一次，只增加阅读成本。

第二，QJsonParseError 必须检查。接口挂了的时候，返回的是一段 HTML 错误页，fromJson 会失败，parse_document 变成空文档。不检查就往下 isArray()，安静地什么都不做，你以为是「搜不到歌」。

第三，顶层类型不固定。搜索接口回数组，详情接口回对象，同一个应用里两种都要处理。写成两条分支，比强转稳妥：

cpp
void HttpManager::parseSongs(const QByteArray &body)
{
    QJsonParseError err;
    const QJsonDocument doc = QJsonDocument::fromJson(body, &err);
    if (err.error != QJsonParseError::NoError) {
        emit failed(QStringLiteral("JSON 解析失败：%1").arg(err.errorString()));
        return;
    }

    QJsonArray array;
    if (doc.isArray()) {
        array = doc.array();
    } else if (doc.isObject()) {
        // 有些接口把列表包在 data.songList 里
        array = doc.object().value("data").toObject().value("songList").toArray();
    }

    emit searchFinished(array);
}

第四，take() 和 value() 的区别要清楚。take() 把键从对象里摘掉并返回，value() 只读取不摘。素材遍历时用的是副本，摘不摘无所谓；只读场景用 value()，语义更直白，也不会有「取过一次就没了」的意外。

还有一个值类型的坑，比上面几条都隐蔽。QJsonValue::toString() 只在值确实是字符串时给内容，遇到数字返回空字符串。接口里 song_id 是数字 31626524 还是字符串 "31626524"，换个接口就变。用 toVariant().toString() 两种都能转：

cpp
QString songIdOf(const QJsonObject &obj)
{
    const QJsonValue v = obj.value("song_id");
    if (v.isString()) {
        return v.toString();
    }
    return v.toVariant().toString();   // 数字、布尔都能落到字符串
}

数字还有一种更坏的情况：song_id 超过了 2^53，JSON 里的双精度浮点会丢精度，末尾几位变成别的数。接口真用这种 ID 时，得让服务端给字符串形式。这不是 Qt 的问题，是 JSON 数字的固有边界。

解析多层的响应时，逐层下沉，不要一次写完一条长链：

cpp
void HttpManager::parseDetail(const QByteArray &body)
{
    const QJsonDocument doc = QJsonDocument::fromJson(body);
    const QJsonObject root = doc.object();

    const QJsonArray list = root.value("data").toObject()
                                .value("songList").toArray();
    if (list.isEmpty()) {
        emit failed(QStringLiteral("没有取到音频地址"));
        return;
    }

    const QJsonObject first = list.at(0).toObject();
    const QString songLink = first.value("songLink").toString();
    const QString lrcLink  = first.value("lrcLink").toString();

    emit detailFinished(songLink, lrcLink);
}

素材里提到的两个字段 songLink 和 lrcLink 就是从这里取出来的。换成别的公开 API，键名会变，取值的套路不变。

五、把结果绑到界面上 #

界面承接用的是 QListWidget。QListWidgetItem 只有一行文字，额外的 song_id 没地方放，Qt 的解法是给 item 挂任意数据：

cpp
QListWidgetItem *item = new QListWidgetItem(song_name);
item->setData(Qt::UserRole, song_id);
ui->listWidget->addItem(item);

Qt::UserRole 是自定义数据的起始编号。一个 item 要挂多个字段，从 Qt::UserRole 往上排：

角色 用途 取法
Qt::DisplayRole 显示的文字 item->text()
Qt::UserRole 第一个自定义字段，这里放 song_id item->data(Qt::UserRole).toString()
Qt::UserRole + 1 第二个字段，比如歌手名 item->data(Qt::UserRole + 1)
Qt::UserRole + 2 第三个字段，比如时长 同上

双击一首歌，把 song_id 取回来发第二个请求：

cpp
connect(ui->listWidget, &QListWidget::itemDoubleClicked,
        this, [this](QListWidgetItem *item) {
    const QString songId = item->data(Qt::UserRole).toString();
    if (songId.isEmpty()) {
        return;
    }
    m_http->fetchSongDetail(songId);     // 异步，结果从信号回来
});

填列表之前记得清空。搜第二次时不清，两次结果会叠在一起。重复项在 Qt::UserRole 里的 song_id 相同，加个判重就够，不必额外维护集合。

clear() 会把 item 一起删掉，不用手动 delete。这一点和 QNetworkReply 相反，别搞混：容器里的控件归容器管，网络回执归你管。

六、QMediaPlayer 与播放列表 #

素材的播放入口，只做了三件事：设地址、设音量、开播：

cpp
#include <QMediaPlayer>

void MusicPlayer::playOnlineStream(const QString &song_link)
{
    QMediaPlayer *player = new QMediaPlayer(this);

    // 加载网络音频链接
    player->setMedia(QUrl(song_link));

    // 设置初始音量为 50%
    player->setVolume(50);

    // 开始在线试听播放
    player->play();
}

两个版本差异必须先说清，否则代码贴到 Qt6 里编不过：

动作 Qt 5 Qt 6
设置媒体 player->setMedia(QUrl(link)) player->setSource(QUrl(link))
取当前媒体 player->currentMedia() player->source()
播放列表 QMediaPlaylist 已被移除，自己维护 QList<QUrl>
元数据 player->metaData("Title") player->metaData().value(QMediaMetaData::Title)
错误信号 error(QMediaPlayer::Error) errorOccurred(QMediaPlayer::Error, const QString &)

QMediaPlaylist 在 Qt6 里被删掉这件事容易卡人。老教程里的 playlist->addMedia()、playlist->setCurrentIndex()、setPlaybackMode(Loop) 全没了。替代做法简单：自己拿一个容器存地址，换歌时重新 setSource()：

cpp
class PlayQueue : public QObject
{
    Q_OBJECT
public:
    void setList(const QList<QUrl> &urls);
    void playAt(int index);

private:
    QMediaPlayer *m_player = nullptr;
    QList<QUrl> m_urls;
    int m_index = -1;
};

void PlayQueue::playAt(int index)
{
    if (index < 0 || index >= m_urls.size()) {
        return;
    }
    m_index = index;
    m_player->setSource(m_urls.at(index));
    m_player->play();
}

Qt5 里要 QMediaPlaylist 的话，写成这样（地址从搜索结果的 songLink 来）：

cpp
QMediaPlaylist *playlist = new QMediaPlaylist(this);
playlist->addMedia(QUrl(songLink1));
playlist->addMedia(QUrl(songLink2));
playlist->setCurrentIndex(0);
playlist->setPlaybackMode(QMediaPlaylist::Loop);

QMediaPlayer *player = new QMediaPlayer(this);
player->setPlaylist(playlist);
player->setVolume(50);
player->play();

播放状态和媒体状态是两回事，看不懂就做不出「正在加载…」这类提示：

状态组 取值 含义
播放状态 StoppedState 停下，进度归零
PlayingState 正在出声音
PausedState 暂停，位置保留
媒体状态 NoMedia 没设地址
LoadingMedia 正在连服务器
LoadedMedia 加载完，还没播
BufferedMedia 缓冲够了，可流畅播
StalledMedia 卡住了，等数据
InvalidMedia 地址或格式不对
EndOfMedia 播完

两组状态各发各的信号。stateChanged 管按钮图标，mediaStatusChanged 管加载提示，别混着用。

播放控制这几个接口够用：

需求 调用 备注
播放 / 暂停 play() / pause() 暂停后 play() 从原位置续
停止 stop() 位置回 0
拖动进度 setPosition(ms) 超过时长会被钳制
音量 setVolume(0~100) 线性映射，听感不是线性的
静音 setMuted(true) 不动当前音量值
当前进度 position() 配 positionChanged 用
总时长 duration() 流媒体在加载完之前是 0

时长这个坑要留意：网络流刚开始播时 duration() 往往是 0，因为播放器还没拿到完整头部。做进度条得等 durationChanged(qint64) 来了再设范围，别在 setSource 之后马上读。

七、流媒体的加载 #

QMediaPlayer 拿到一个 http 地址就能播，不需要你先下载再喂给它。它内部自己发请求、自己缓冲、自己解码，你只给地址。这是它和「先 get() 到本地文件再 setSource(file://…)」的分界：在线试听走前者，离线缓存走后者。

三个前提条件不满足就播不出来：

条件 不满足的表现 检查方法
地址能直连（无鉴权、无防盗链） mediaStatusChanged 停在 LoadingMedia 然后 InvalidMedia 浏览器里直接打开这个地址
后端有对应格式的解码器 InvalidMedia，但地址本身能下 Windows 上靠 Media Foundation，换 mp3 试
Qt 的 TLS 后端可用 https 地址全部失败，http 正常 打印 QSslSocket::supportsSsl()

加载过程在 mediaStatusChanged 里看得见。做一个状态提示，比干等强：

cpp
connect(m_player, &QMediaPlayer::mediaStatusChanged, this,
        [this](QMediaPlayer::MediaStatus status) {
    switch (status) {
    case QMediaPlayer::LoadingMedia:
        ui->statusLabel->setText(QStringLiteral("正在连接…"));
        break;
    case QMediaPlayer::StalledMedia:
        ui->statusLabel->setText(QStringLiteral("网络卡顿，正在等待…"));
        break;
    case QMediaPlayer::InvalidMedia:
        ui->statusLabel->setText(QStringLiteral("无法播放：地址或格式不对"));
        break;
    default:
        break;
    }
});

重定向要留意。多数后端会跟 3xx，但 http 跳 https、跨域跳转这两种情况有后端不跟，表现就是 LoadingMedia 一直转。取到 songLink 之后先自己请求一次拿 Location，把最终地址交给播放器，能绕开这类问题。

八、歌词与元数据 #

素材里这句要保留：从接口拿到的 lrcLink 可以拼接成绝对地址，比如 http://ting.baidu.com/data2/lrc/31626524/31626524.lrc。接口有时给的是 /data2/lrc/… 这样的相对路径，得用歌词站点的基址补全，不能拿搜索结果页的域名去拼。

下载 lrc 和下载 JSON 是同一套动作，区别只在读回来的是文本。有一个坑：.lrc 文件不少是 GBK 编码，直接 QString(bytes) 会得到乱码。按 UTF-8 试一次，含替换字符再走本地编码转换：

cpp
QString decodeLyric(const QByteArray &raw)
{
    QTextCodec *utf8 = QTextCodec::codecForName("UTF-8");
    QString text = utf8->toUnicode(raw);
    if (!text.contains(QChar::ReplacementCharacter)) {
        return text;
    }
    QTextCodec *gbk = QTextCodec::codecForName("GB18030");
    return gbk ? gbk->toUnicode(raw) : text;
}

Qt6 里 QTextCodec 移到了 Core5Compat 模块，改用 QStringDecoder，逻辑一样：先 UTF-8，失败再 GB18030。

[01:23.45] 歌词内容 这种时间标签，用一条正则全吃下来：

cpp
#include <QRegularExpression>

struct LyricLine
{
    qint64 timeMs = 0;
    QString text;
};

QVector<LyricLine> parseLrc(const QString &content)
{
    QVector<LyricLine> lines;
    const QRegularExpression re(QStringLiteral("\\[(\\d+):(\\d+)(?:[.:](\\d+))?\\](.*)"));

    for (const QString &raw : content.split('\n')) {
        const auto m = re.match(raw.trimmed());
        if (!m.hasMatch()) {
            continue;
        }
        const qint64 min = m.captured(1).toLongLong();
        const qint64 sec = m.captured(2).toLongLong();
        const qint64 frac = m.captured(3).toLongLong();

        LyricLine line;
        line.timeMs = min * 60000 + sec * 1000 + frac * 10;   // 两位小数即厘秒
        line.text = m.captured(4).trimmed();
        lines.append(line);
    }

    std::sort(lines.begin(), lines.end(),
              [](const LyricLine &a, const LyricLine &b) {
        return a.timeMs < b.timeMs;
    });
    return lines;
}

素材说的联动方式是 positionChanged(qint64)。槽里拿到当前毫秒，把指针往前推，只有跨过某一行的时间才更新显示：

cpp
connect(m_player, &QMediaPlayer::positionChanged, this,
        [this](qint64 pos) {
    while (m_lyricIndex + 1 < m_lyrics.size()
           && m_lyrics.at(m_lyricIndex + 1).timeMs <= pos) {
        ++m_lyricIndex;
        ui->lyricLabel->setText(m_lyrics.at(m_lyricIndex).text);
    }
});

拖动进度条会往回跳，这时 pos 突然变小，上面的 while 不再前进，歌词就停在旧行。加一条回退判断：pos 小于当前行时间时，用二分查找重新定位 m_lyricIndex。

元数据不用自己解析标签，播放器能读出来：

需求 Qt 5 Qt 6
标题 player->metaData("Title").toString() player->metaData().value(QMediaMetaData::Title)
歌手 player->metaData("Author") QMediaMetaData::Author
专辑 player->metaData("AlbumTitle") QMediaMetaData::AlbumTitle
时长 player->metaData("Duration") QMediaMetaData::Duration
封面 player->metaData("CoverArtImage") QMediaMetaData::CoverArtImage

网络流在 LoadedMedia 之前读元数据，多数是空 QVariant。等 metaDataChanged() 信号来了再填界面，这是唯一可靠时机。

九、错误处理与超时 #

这个应用有三层错误，各有各的判断方式，不能混在一处处理：

层 判断依据 典型原因
网络层 reply->error() != NoError 断网、DNS 失败、404、超时
数据层 QJsonParseError::error != NoError 返回了 HTML 错误页、接口结构变了
播放层 player->error() != NoError 解码器缺失、地址失效、格式不支持

网络层的错误码，这几个最常见：

枚举 含义 你的动作
ConnectionRefusedError 服务端拒绝 提示服务未启动，别自动重试
HostNotFoundError 域名解析失败 检查网络和地址拼写
TimeoutError 超时 可以重试一次
OperationCanceledError 被 abort() 掉 用户主动取消，不报错
ContentNotFoundError HTTP 404 接口路径变了
ProtocolUnknownError 协议不认识 地址少了 http://
SslHandshakeFailedError TLS 握手失败 证书问题，别绕过校验了事

播放层的错误用 errorOccurred 接：

cpp
connect(m_player, &QMediaPlayer::errorOccurred, this,
        [this](QMediaPlayer::Error err, const QString &msg) {
    if (err == QMediaPlayer::NoError) {
        return;
    }
    ui->statusLabel->setText(QStringLiteral("播放失败：%1").arg(msg));
});

超时素材没写，但必须补。不设超时，弱网下 finished() 迟迟不来，槽不执行，界面永远停在「搜索中」。Qt 5.15 起可以直接设：

cpp
request.setTransferTimeout(8000);   // 毫秒，Qt 5.15+

更老的版本用定时器兜底，abort() 会触发 finished()，槽照常执行，error() 是 OperationCanceledError：

cpp
m_searchReply = m_manager->get(makeRequest(url));

auto *timer = new QTimer(this);
timer->setSingleShot(true);
connect(timer, &QTimer::timeout, m_searchReply, [this]() {
    if (m_searchReply && m_searchReply->isRunning()) {
        m_searchReply->abort();
    }
});
connect(m_searchReply, &QNetworkReply::finished, timer, &QTimer::deleteLater);
timer->start(8000);

失败要不要重试，看错误码。TimeoutError、TemporaryNetworkFailureError 值得重试一次，加 1 到 2 秒延迟。ContentNotFoundError、HostNotFoundError 重试没有意义，重试只会让用户多等一轮。

十、请求的并发与取消 #

一个 QNetworkAccessManager 同时跑多个请求是正常的，每个请求有自己的 QNetworkReply，互不干扰。所以并发不需要额外做什么，只要别把 reply 指针存进同一个成员变量。

取消很简单，reply->abort()。取消之后 finished() 照样发，槽里那句 deleteLater() 照样要执行。把取消当成一次普通失败处理，代码路径就只需要一条。

真正要防的是结果错位。用户输入「周」，请求 A 发出；还没回来，用户又输入「周杰伦」，请求 B 发出。A 比 B 先回来，界面先显示 A 的结果，然后 B 回来覆盖成正确结果，看起来没事。反过来 B 先回、A 后回，界面就停在了错误的搜索结果上。

场景 做法 目的
输入框边打边搜 加 300ms 防抖定时器 少发请求
新请求发出前 if (m_searchReply) m_searchReply->abort() 旧结果作废
一定要旧请求跑完 给每个请求编号，回来时比对序号 丢弃过期响应
页面关闭 / 对象析构 依赖 QObject 父子关系，reply 挂 this 不泄漏
下载大文件 readyRead() 增量写文件 不占内存

序号比对的做法最省事：成员里存一个自增 m_seq，请求时记下当前值，lambda 里捕获这个值，回来时和 m_seq 比，不等就丢弃。

十一、公共 API 不可用的应对 #

素材里的两个地址都来自百度音乐的旧接口：

用途 历史地址 现状
搜索 http://mp3.baidu.com/dev/api/?tn=getinfo&ct=0&ie=utf-8&word=&format= 已停止服务
取音频与歌词地址 http://ting.baidu.com/data/music/links?songIds= 已停止服务

这两个域名现在请求过去，得到的是跳转页或者错误页，不是 JSON。这不是代码写错了，是接口没了。当年那套参数结构（tn、ct、ie、word、format）现在只作为「拼查询参数」的示例看。

换成任一公开音乐 API，下面这些全都不用改：

不变 会变
用 QNetworkAccessManager 发 GET 域名与路径
用 QUrlQuery 拼参数 参数名
在 finished() 槽里读数据 响应结构、键名
用 QJsonDocument 解析 列表在第几层
用 item->setData 绑定 ID ID 字段叫什么
用 QMediaPlayer 播 songLink 音频地址给的是直链还是跳转

挑接口时的三个现实约束：直链能不能直接访问（有的要带 Referer）、有没有请求频率限制、返回的音频地址有没有时效（不少地址带过期签名，缓存下来隔天就失效）。这三件事决定了你要不要加 setRawHeader("Referer", …)、要不要做延迟重取。

拿到新接口，第一步不是写代码，是打开浏览器开发者工具的 Network 面板，看一次真实响应长什么样。把响应体存成文件，照着它写解析函数，比猜字段名快得多，也避免把「键取错」误判成「接口挂了」。

把基址提出来做配置，是这一章唯一需要落到代码上的建议：

cpp
QString baseUrl() const
{
    return QSettings().value("api/musicBase",
                             QStringLiteral("https://api.example.com")).toString();
}

十二、易错点速查 #

现象 原因 改法
程序跑久了内存一直涨 reply 没删 每个分支都 deleteLater()
崩溃在 finished 之后 用了 delete 换 deleteLater()
搜不到结果，也没报错 返回了 HTML，fromJson 失败 检查 QJsonParseError
歌名带空格就搜错 手拼 URL 未编码 用 QUrlQuery
song_id 取出来是空串 JSON 里是数字，toString() 返回空 toVariant().toString()
界面一直停在「搜索中」 没设超时 setTransferTimeout 或定时器 abort
结果列表越搜越长 没清空控件 先 clear()
换歌后进度条范围不对 在 setSource 后立刻读 duration() 等 durationChanged
Qt6 编不过 QMediaPlaylist 该类型已移除 自己维护 QList<QUrl>
歌词显示乱码 .lrc 是 GBK 先 UTF-8 再 GB18030
拖动进度条后歌词不回退 只在往前走 加二分重定位
定时重试把接口打挂 没区分错误码 只对超时类重试一次

四句话收尾，也是这个实例真正的收获：

请求发出去就返回了，结果在槽里，不在下一行。

回执对象是 QObject，谁创建谁负责，deleteLater() 一句不能少。

播放器只吃地址，加载慢和格式错表现不同，别把两种失败写成一种提示。

接口会停服，参数会改名，流程不会变。把域名做成配置，把解析写成独立函数，下次换接口时你只动两处。
