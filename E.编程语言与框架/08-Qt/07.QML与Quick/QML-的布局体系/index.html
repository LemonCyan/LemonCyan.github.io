这篇只讲一件事：QML 里怎么把元素摆到该在的位置上。锚、定位器、布局三套手段，各自的边界、脾气、踩坑点，一次说清。

讲什么：x/y 原始定位、anchors 的锚线与 fill/centerIn、锚的冲突、四种定位器（Row/Column/Grid/Flow）、三种 Layout（RowLayout/ColumnLayout/GridLayout）与 Layout.* 附加属性、三者怎么配合、尺寸变化时的行为、易错点速查。

不讲什么：控件自身的属性（Text 怎么设字体、Button 怎么接 clicked）、动画与状态切换、对话框。这些在同目录各有独立一篇，重复写只会让两处对不上。

指路：控件从哪来，看三大模块那篇；文本怎么排，看文本与标签那篇；按钮怎么响应点击，看按钮与鼠标那篇。本文只关心「元素之间的相对关系」。

一、QML 的三种布局手段 #

先给结论，后面十一章都是这三句话的展开。

QML 摆元素，路子有四条，从原始到高级排：

手段 一句话 管位置 管尺寸
直接坐标 x: 40; y: 20 硬写 你 你
锚 anchors 贴着谁、离多远 引擎 部分（fill 会顺带定尺寸）
定位器 排队 定位器 不管
布局 Layout 排队，还分空间 布局 管

任务书里说的「三种手段」，指的是后三条：锚、定位器、布局。x/y 严格讲不算手段，它是地基——引擎算完账，最后写进去的仍然是元素的 x、y、width、height 这四个数。

这句话要记牢，它能解释后面所有的怪现象：

无论你用锚还是用布局，最终都落到 x、y、width、height 上。

所以「布局没生效」这种抱怨，十有八九是某个地方还有行手写的 width 或 x 在跟引擎抢方向盘。谁最后写、谁覆盖谁，取决于绑定依赖，不是取决于你写代码的顺序。

定位器和布局，差在一个字 #

这是全篇最要紧的分界线，先把它钉死。

定位器只管「摆在哪」，Layout 还管「占多大」。

拿两个按钮放进 Row 里：

qml
Row {
    spacing: 8

    Button { text: "确定" }
    Button { text: "取消" }
}

你把窗口拉宽到两千像素，这两个按钮还是原来那么宽，只是整排位置跟着变。Row 从头到尾没动过它们的宽度，它只负责把它们一个挨一个排好。

换成 RowLayout，加上一行附加属性：

qml
import QtQuick.Layouts 1.3

RowLayout {
    spacing: 8

    Button {
        text: "确定"
        Layout.fillWidth: true
    }
    Button {
        text: "取消"
        Layout.fillWidth: true
    }
}

这才是平分宽度。Layout.fillWidth: true 的意思是「剩余空间按比例分给我」，两个都开了，就各分一半。

同一个界面需求，两套名字只差一个 Layout 后缀，行为却完全不同。QML 布局的坑，七成出在这个后缀上。

三套手段的选择顺序 #

实用主义的选法，从上往下试，能用上面的就别用下面的：元素跟父级或兄弟有明确相对关系，用锚；一排一列元素数量固定、尺寸固定，用定位器；要随窗口拉伸、要平分、要有上下限，用 Layout；位置是算出来的、要跟随鼠标或滚动偏移，才轮到 x/y 绑定。别跳级，明明锚能搞定的地方硬套 RowLayout，代码长一倍，性能还差一截。

二、x 与 y：最原始的定位 #

Item 的坐标原点在父级的左上角，不是屏幕左上角。x 向右为正，y 向下为正。这点跟数学课的坐标系反着来，跟绝大多数 GUI 框架一致。

qml
Rectangle {
    width: 400; height: 300
    color: "#eeeeee"

    Rectangle {
        x: 40; y: 20
        width: 100; height: 60
        color: "steelblue"
    }
}

蓝色方块左上角落在父级左上角往右 40、往下 20 的位置。写死就是写死，父级怎么变它都不动。

坐标也能绑定 #

x/y 一样可以写表达式，这才是它真正有用的时候：

qml
Rectangle {
    id: box
    width: 200; height: 120

    Rectangle {
        width: 40; height: 40
        color: "tomato"
        x: box.width - width      // 贴右边
        y: (box.height - height) / 2   // 垂直居中
    }
}

父级变宽，红方块自动跟到右边。这种写法在手写布局年代很常见，现在仍然有用——比如跟随滚动偏移的小滑块，或者拖拽时的临时定位。

手算坐标的三个硬伤 #

一、每加一个元素，就要多算一遍。 元素一多，加减号堆成山，改一个尺寸要牵动一排数字。

二、兄弟之间没有关系。 你想让 B 紧贴 A 的右边，只能写 x: a.x + a.width + 8。A 挪了位置、改了宽度，表达式跟着变，看着能用；可一旦 A 是动态生成的，或者 A 的宽度来自布局，这条链子就断了。

三、它不知道「谁该让谁」。 父级缩到比子项还小时，子项直接被裁掉，没有任何协商余地。

结论：x/y 当底层机制理解，当调试手段用，日常布局别拿它当主力。

三、锚布局 anchors #

锚是 QML 最招牌的东西。一句话描述它的工作方式：你指定自己的某条边，贴到另一个元素的某条边上。

qml
Rectangle {
    id: panel
    width: 400; height: 300
    color: "#f0f0f0"

    Rectangle {
        id: header
        height: 40
        color: "steelblue"
        anchors.left: parent.left
        anchors.right: parent.right
        anchors.top: parent.top
    }

    Rectangle {
        id: badge
        width: 80; height: 24
        color: "orange"
        anchors.top: header.bottom
        anchors.topMargin: 8
        anchors.horizontalCenter: parent.horizontalCenter
    }
}

header 同时锚了左、右、上三条边，宽度就不用手写了——引擎按左右两条锚线算出它该多宽。父级一拉伸，它跟着拉伸。badge 只锚了上边和水平中线，尺寸还是自己给的 80×24，位置由锚推。

这就是锚的能力边界：锚能推位置，也能在两条平行锚线同时存在时推出尺寸，但推不出来的是「按比例分配」。

锚线清单 #

Item 提供四条边线、两条中心线、一条基线，外加两个组合快捷属性：

锚线/属性 含义 说明
anchors.left 左边 指向另一元素的 left/right 等边线
anchors.right 右边 同上
anchors.top 上边 同上
anchors.bottom 下边 同上
anchors.horizontalCenter 水平中线 指向另一元素的水平中线或某条边
anchors.verticalCenter 垂直中线 指向另一元素的垂直中线或某条边
anchors.baseline 文字基线 文本类元素才有意义，对齐文字常用
anchors.fill 四条边全锚上 等价于 left+right+top+bottom 同时设
anchors.centerIn 两条中线 等价于 horizontalCenter+verticalCenter 同时设
anchors.margins 四边外边距 一次性设四个 margin
anchors.leftMargin 等 单边外边距 topMargin、rightMargin、bottomMargin

每个锚线属性接收一个边对象，不是数字。写 anchors.left: 10 是错的，要写 anchors.left: parent.left 再配 anchors.leftMargin: 10。这条是新手第一道坎。

fill 与 centerIn #

这两个是语法糖，省掉四行或两行代码，但它们的语义比写法重要。

qml
// 两种写法完全等价
Rectangle {
    anchors.fill: parent
}
Rectangle {
    anchors.left: parent.left
    anchors.right: parent.right
    anchors.top: parent.top
    anchors.bottom: parent.bottom
}

fill 铺满父级。它不是「设一个 fill 属性」，而是一次性设了四条锚线。这个等价关系在下一章讲冲突时会变得很关键。

centerIn 同理，等价于两条中线全设，只居中不定尺寸。

qml
Rectangle {
    width: 60; height: 60
    color: "tomato"
    anchors.centerIn: parent   // 尺寸仍是 60×60，只是居中
}

锚的 margins 与偏移 #

margins 是锚的外边距，让元素跟自己锚到的位置之间留出一段距离；跟 CSS 的 margin 概念接近。还有一类是偏移量 horizontalCenterOffset、verticalCenterOffset、baselineOffset，用在需要「居中再挪一点」的场合。

qml
Rectangle {
    width: 120; height: 40
    color: "seagreen"
    anchors.horizontalCenter: parent.horizontalCenter
    anchors.horizontalCenterOffset: 20   // 居中后再右移 20
    anchors.bottom: parent.bottom
    anchors.bottomMargin: 16
}

margins 和 offset 别混用。外边距是「跟锚线保持距离」，偏移是「从中线平移」。同一个方向上写两种，结果不会是你想要的。

四、锚的冲突与优先级 #

锚线不是随便堆的，它们按方向分组。同一组里只能生效一条，这是硬规则。

方向组 组内成员 约束
水平 left、right、horizontalCenter、fill、centerIn 五选一
垂直 top、bottom、verticalCenter、baseline、fill、centerIn 五选一
尺寸派生 水平两条平行锚同时存在 → 推出 width 不能手写 width
尺寸派生 垂直两条平行锚同时存在 → 推出 height 不能手写 height

fill 和 centerIn 之所以出现在两个组里，是因为它们一次性动了两个方向——fill 四条边全设，centerIn 两条中线全设。

fill 与单条锚线打架 #

这是最常见的一种冲突。你以为 fill 之后再用 left 做微调，实际是两条水平锚线同时存在。

qml
// 错：fill 已经设了 left 和 right，又追加一条 left
Rectangle {
    anchors.fill: parent
    anchors.left: parent.left      // 冲突
    anchors.leftMargin: 12
}

跑起来控制台会打一条警告，大意是同一个元素上不能同时指定多个水平方向的锚线。结果不是「后写的覆盖先写的」，而是其中一条被忽略——被丢的是哪一条，不该去猜。

要留边距，正确写法是给 fill 配 margins：

qml
Rectangle {
    anchors.fill: parent
    anchors.margins: 12    // 四边各内缩 12，不产生冲突
}

想要只缩左右两边，就别用 fill，老老实实把四条锚线写全：

qml
Rectangle {
    anchors.top: parent.top
    anchors.bottom: parent.bottom
    anchors.left: parent.left
    anchors.right: parent.right
    anchors.leftMargin: 12
    anchors.rightMargin: 12
    anchors.topMargin: 6
    anchors.bottomMargin: 6
}

啰嗦，但没有歧义。

优先级不是「后来居上」 #

不少人以为锚冲突时后写的赢。不对。锚属性在 QML 里各自独立，没有先后语义。冲突时引擎要么忽略其中一条并警告，要么干脆一个都不生效——具体到哪个属性被丢，跟声明顺序无关。

正确的态度是：不要制造冲突。写完先看控制台，QML 的锚冲突警告给得很直接，嫌它吵而关掉，等于把最便宜的诊断工具扔了。

锚循环 #

两个元素互相锚对方，形成环：

qml
// 错：互相咬死，谁也算不出来
Rectangle { id: a; anchors.right: b.left }
Rectangle { id: b; anchors.left: a.right }

a 的右边依赖 b 的左边，b 的左边依赖 a 的右边，哪个都算不出来。引擎检测到环之后会报锚循环警告，两个元素的位置停在上一次算出来的值，界面看着错位但不崩。

锚的方向要有传递性，不能成环。A → B → C 可以，A → B → A 不行。

锚的目标有身份要求 #

锚线的右边，必须是一个同一父级下的兄弟元素，或者父级自己 parent。跨父级锚定不成立：

qml
// 错：不同父级，锚不上
Item {
    id: leftSide
    Rectangle { id: inner }
}
Item {
    id: rightSide
    Rectangle {
        anchors.left: inner.right    // inner 不是兄弟，也不是 parent
    }
}

这种代码在运行时找不到锚目标，控制台会报错，元素停在原点。想在两个容器里对齐元素，得靠绑定算坐标，或者把两者放进同一个 Layout 里用列对齐。

父级和兄弟可以同时锚 #

parent 只有一个，但锚线可以指向不同的对象。锚父级的 top、锚兄弟的 left，两条并存，互不干扰——不同方向的组各自独立。这条规则比想象中宽松，用起来不别扭。

五、定位器：Row 与 Column #

定位器是「排队」的抽象。Row 横着排，Column 竖着排，写起来最短。

qml
Row {
    spacing: 8

    Rectangle { width: 40; height: 40; color: "tomato" }
    Rectangle { width: 60; height: 40; color: "seagreen" }
    Rectangle { width: 80; height: 40; color: "steelblue" }
}

三块从左往右依次摆开，间距 8。Column 把 Row 的名字换掉，其余照旧，方向变成从上往下。

qml
Column {
    spacing: 6

    Text { text: "用户名"; font.pixelSize: 14 }
    TextField { width: 200 }
    Text { text: "密码"; font.pixelSize: 14 }
    TextField { width: 200 }
}

定位器的尺寸从哪来 #

定位器自己不生产尺寸，它汇总子项的尺寸：

属性 含义
spacing 相邻子项之间的间隙
implicitWidth（Row） 所有子项宽度之和 + spacing × (数量 - 1)
implicitHeight（Row） 最高的那个子项的高度
implicitWidth（Column） 最宽的那个子项的宽度
implicitHeight（Column） 所有子项高度之和 + spacing × (数量 - 1)

你没给 Row 写 width，它就贴着内容走。给了 width 大于内容的，多余空间空着，元素不会自己散开——Row 没有「分配」的概念。

定位器内的锚线被限制 #

这条规则很多人踩。在 Row 里给子项设水平方向锚线，在 Column 里给子项设垂直方向锚线，都会被忽略并触发警告。

原因是分工：那条轴由定位器接管了，你再插一手就是打架。

qml
// 错：Row 里给子项设水平锚线，被忽略
Row {
    Rectangle {
        anchors.left: parent.left    // 无效
    }
}

qml
// 对：Row 内只锚垂直方向，水平交给 Row
Row {
    spacing: 8
    Rectangle {
        width: 60
        height: 40
        anchors.verticalCenter: parent.verticalCenter   // 这个可以
    }
}

记住一条：定位器接管的那条轴，子项别再碰。

六、定位器：Grid 与 Flow #

Grid 是二维的排队：按列填，填满了换行。

qml
Grid {
    columns: 3
    spacing: 10

    Repeater {
        model: 9
        Rectangle { width: 50; height: 50; color: Qt.hsla(index / 9, 0.6, 0.7, 1) }
    }
}

九个方块排成三行三列。columns: 3 定了列数，行数由子项数量自动算出来。

rows 和 columns 二选一，只给一个，另一个自动推。两个都给会打架——子项数量跟行数、列数对不上时，多出来的子项要么换行超出网格，要么被塞进新的一行。实际写代码时只设一个。

qml
Grid {
    rows: 2          // 定 2 行，列数自动
    flow: Grid.LeftToRight   // 默认：先横着填，填满换行
    spacing: 10

    Repeater { model: 6; Rectangle { width: 50; height: 50 } }
}

flow 决定填充方向：Grid.LeftToRight 是横着填，Grid.TopToBottom 是竖着填。默认前者。

spacing 设横竖统一间距，rowSpacing 和 columnSpacing 分开设。分方向设的时候，对应方向以分方向那个为准，写一种就够，别两处都写。

Flow：按宽度自动换行 #

Flow 是「宽度不够就换行」。它跟 Row 的关系，类似文字排版里的自动折行跟手动换行。

qml
Flow {
    width: 300
    spacing: 8

    Repeater {
        model: 20
        Rectangle { width: 60; height: 30; color: "steelblue" }
    }
}

宽度锁死 300，一行放得下四个（60×4 + 8×3 = 264，第五个会溢出），剩下的自动折到下一行。窗口拉宽，一行能放的更多，折行位置跟着变。

flow 属性切成 Flow.TopToBottom 之后，变成竖着往下填，高度不够就往右开新列——这时候起作用的是 height，不是 width。

qml
Flow {
    width: 300          // 必须给宽度，否则 Flow 会撑到内容总宽，永远不折行
    flow: Flow.LeftToRight
    spacing: 8
}

不给 width 是 Flow 最经典的失效原因：它按内容撑开自己，宽度永远够用，自然一行都折不出来。

定位器不是视图 #

容易混的一点：Grid、Flow 是定位器，一次性把所有子项都创建出来、都摆在场景里。GridView、ListView 是视图控件，带模型代理、滚动、元素回收。

数据量小、全是静态元素，用定位器。数据量大、要滚动、要按需创建，用视图控件，别拿 Repeater 硬堆几千个元素。

七、定位器不管尺寸 #

现在回到本篇的核心分界线上来。前一章说过定位器只汇总尺寸，这一章把话说透。

看这个界面：一行两个按钮，你想让它们平分窗口宽度。

qml
// 错：写成 Row，两个按钮永远不会平分
Row {
    spacing: 8
    width: parent.width

    Button { text: "确定"; width: 100 }
    Button { text: "取消"; width: 100 }
}

窗口宽 200，两个 100 的按钮加 8 的间距，溢出。窗口宽 1000，两个按钮还是 100 宽，右边空出 800 像素。

Row 从头到尾没有写过子项的 width。它读子项宽度，算自己该多宽，然后把子项挨个摆好——只读不写。

定位器自身的尺寸也不反向传播 #

qml
Row {
    spacing: 8
    Rectangle { width: 50; height: 50 }
    Rectangle { width: 50; height: 50 }
    // Row 的 implicitWidth = 108，但它不会把这个宽度分给子项
}

Row 的 implicitWidth 是 108，父级若按内容定尺寸，Row 就占 108。子项仍然是各 50。尺寸信息只往上走，不往下走。

想在定位器里撑开，只能手写 #

办法有，但都不好看：

qml
Row {
    spacing: 8
    width: parent.width
    Rectangle { width: (parent.width - 8) / 2; height: 40 }   // 硬算一半
    Rectangle { width: (parent.width - 8) / 2; height: 40 }
}

数量固定两个能算，改成三个就要改公式，间距、边距一动全得重算。这就是 Row 的能力上限——它不解决「空间怎么分」，只解决「摆的顺序」。

一张表看穿差别 #

维度 Row / Column RowLayout / ColumnLayout
管的轴 只管一条轴的排列 排列 + 尺寸分配

剩余空间 空着 按 fillWidth 分掉
子项最小/最大约束 无 Layout.minimumWidth / maximumWidth
子项尺寸来源 width／height preferredWidth → implicitWidth → width
是否可嵌套分配 嵌套后仍是各管各的 嵌套布局会逐层传递约束
引入模块 QtQuick 自带 要 import QtQuick.Layouts

最后一行是个实用信号：Row 不用 import，RowLayout 要。忘了 import，RowLayout 直接报类型未定义，反而好排查；写错了名字却不报错的情况才是麻烦。

八、Layout：会分配尺寸的布局 #

RowLayout、ColumnLayout、GridLayout 三个，来自 QtQuick.Layouts 模块。它们做的事比定位器多一步：除了排列，还要在子项之间分配空间。

qml
import QtQuick 2.12
import QtQuick.Controls 2.12
import QtQuick.Layouts 1.12

ApplicationWindow {
    width: 480; height: 160
    visible: true

    RowLayout {
        anchors.fill: parent
        anchors.margins: 12
        spacing: 8

        Button { text: "确定"; Layout.fillWidth: true }
        Button { text: "取消"; Layout.fillWidth: true }
    }
}

两个按钮各占一半，窗口怎么拉都各占一半。同样一段代码把 RowLayout 换成 Row、去掉两行 Layout.fillWidth，就退化成第七章那个「按钮纹丝不动」的版本。

名字只差一个后缀 #

第一章那段对比再看一遍：Row 里写死 width: 80 的两个矩形，父级多宽都是 80；同样两个矩形塞进 RowLayout，各加一行 Layout.fillWidth: true，父级多宽就各占一半。名字差一个后缀，行为差一个维度。

三个 Layout 的职责 #

类型 排列方式 附加属性里跟它相关的 典型场景
RowLayout 横排，每个子项占一列 fillWidth、preferredWidth、minimumWidth、maximumWidth 工具栏、按钮条、表单一行多格
ColumnLayout 竖排，每个子项占一行 fillHeight、preferredHeight、minimumHeight、maximumHeight 表单纵向堆叠、侧栏
GridLayout 网格，行列可跨 row、column、rowSpan、columnSpan 计算器键盘、仪表盘

三个可以互相嵌套。ColumnLayout 里放一个 RowLayout，就是「上下两块，上面那块再横向分栏」，写法在第十章。

Layout 引入的两条新规则 #

一、子项的尺寸该由 Layout.preferredWidth 之类的附加属性给，不该写 width。 附加属性是给布局看的「申请单」，width 是最终结果。布局算完会把结果写进 width，你手写的那个 width 会被覆盖。

二、附加属性写在子项里，语义属于父布局。 Layout.fillWidth 写在 Button 内部，但它描述的是「这个 Button 在它所属的那个 Layout 里怎么分配」。所以同一个元素换一个父布局，这些附加属性的效果跟着变。

九、Layout 的附加属性 #

这一章是整篇的技术底座。Layout 本身不是一个类型，它是一组附加属性（attached properties），挂到 GridLayout、RowLayout、ColumnLayout 的子项上，告诉布局「我该怎么被摆、能被拉多大」。

完整清单：

附加属性 类型 默认值 作用
Layout.alignment Qt.Alignment 0（即 AlignVCenter | AlignLeft） 在该格内的对齐方式
Layout.row int 0 GridLayout 中的行位置
Layout.column int 0 GridLayout 中的列位置
Layout.rowSpan int 1 跨几行
Layout.columnSpan int 1 跨几列
Layout.fillWidth bool false（布局自身为 true） 是否横向吃掉剩余空间
Layout.fillHeight bool false（布局自身为 true） 是否纵向吃掉剩余空间
Layout.preferredWidth real -1 首选宽度
Layout.preferredHeight real -1 首选高度
Layout.minimumWidth real 隐式最小宽度 最小宽度
Layout.minimumHeight real 隐式最小高度 最小高度
Layout.maximumWidth real 隐式最大宽度 最大宽度
Layout.maximumHeight real 隐式最大高度 最大高度
Layout.margins real 0 四周外边距

尺寸的三档：最小、首选、最大 #

布局调整大小时，子项会变大或变小。为此每个子项都有三个尺寸档位：最小尺寸、首选尺寸、最大尺寸。

首选尺寸从哪来？按顺序找，找到就用：

顺序 来源 说明
1 Layout.preferredWidth / preferredHeight 你显式写的，最高优先
2 元素自身的 implicitWidth / implicitHeight 内容撑出来的尺寸
3 元素自身的 width / height 最后兜底

想覆盖首选尺寸，就写 Layout.preferredWidth。别去改 width —— 那只是第三顺位的兜底值，布局一算就把你手写的盖掉了。

最小尺寸没显式指定时是 0，最大尺寸没显式指定时是 Number.POSITIVE_INFINITY。也就是说，一个子项默认可以被压到零宽，也可以被无限拉大——除非你用 Layout.minimumWidth/maximumWidth 拦住。

布局自身的隐式最小和最大尺寸，取决于布局里的内容，逐层往上汇总。

Layout.minimumWidth、maximumWidth、minimumHeight、maximumHeight 这四个，设成 -1 就是撤销，回到隐式算出来的值。Layout.preferredWidth/preferredHeight 的 -1 含义不同：它表示「这个值无效，改用 implicitWidth/implicitHeight」，也是默认状态。

qml
RowLayout {
    spacing: 8

    Rectangle {
        Layout.preferredWidth: 120    // 首选 120
        Layout.minimumWidth: 60       // 最小压到 60
        Layout.maximumWidth: 200      // 最多撑到 200
        Layout.preferredHeight: 40
        color: "steelblue"
    }
    Rectangle {
        Layout.fillWidth: true        // 吃掉剩下的全部
        Layout.preferredHeight: 40
        color: "seagreen"
    }
}

第一个矩形没开 Layout.fillWidth，尺寸固定在首选的 120，那个 200 的上限在它身上根本用不到。第二个开了，把剩余空间全吃掉。可见三档尺寸是给「可伸缩的项」准备的，不伸缩就没有档位可言。

fillWidth 与 fillHeight #

这两个决定子项是「固定」还是「可伸缩」：

  • 为 false：尺寸固定为首选尺寸，布局不动它。
  • 为 true：在最小尺寸和最大尺寸之间伸缩，把剩余空间分掉。

默认值是 false。但这句话有个尾巴：布局自身的 fillWidth/fillHeight 默认为 true。嵌套布局时，内层布局默认会撑满外层分给它的格子。

qml
RowLayout {
    Rectangle {
        Layout.fillWidth: true       // 多个开了 fillWidth 的子项，按比例分
        Layout.preferredWidth: 200   // 比例以首选宽度为权重
        color: "tomato"
    }
    Rectangle { Layout.fillWidth: true; Layout.preferredWidth: 100; color: "seagreen" }
}

两个都开 fillWidth，谁分得多？按首选宽度加权：200 比 100，2:1。不是五五平分。要真平分，把两个 preferredWidth 设成相同的值，或者都别写（默认取各自 implicitWidth，尺寸相同的元素才能平分）。

alignment：格内对齐 #

Layout.alignment 指定元素在自己的格子内怎么对齐。默认值是 0，语义上等于 Qt.AlignVCenter | Qt.AlignLeft，也就是垂直居中、水平靠左。

qml
RowLayout {
    Rectangle {
        Layout.preferredWidth: 40
        Layout.preferredHeight: 30
        Layout.alignment: Qt.AlignRight | Qt.AlignVCenter
        color: "tomato"
    }
}

注意它跟 anchors 的分工：alignment 只在「格子比元素大」时有意义。格子跟元素一样大，对齐无从谈起。

row、column 与跨格 #

Layout.row 和 Layout.column 只在 GridLayout 里有意义，指定元素落在第几行第几列，从 0 开始。两个都不写时，由布局按顺序自动分配格子。

qml
GridLayout {
    columns: 2
    columnSpacing: 8
    rowSpacing: 6

    Text { text: "姓名" }
    TextField { Layout.fillWidth: true }

    Text { text: "备注" }
    TextField { Layout.fillWidth: true }

    Rectangle { Layout.columnSpan: 2; Layout.fillWidth: true; Layout.preferredHeight: 1; color: "#cccccc" }  // 横跨两列的分隔线
}

rowSpan 和 columnSpan 默认都是 1。跨格时，元素的尺寸约束要能覆盖被跨的那几格，否则它会挤在一格里。

别在布局里绑 x、y、width、height #

这条是硬禁忌：别在布局的子项上绑定 x、y、width、height。

原因不是风格问题。布局自己会写这四个属性，你也在写，两边抢同一个属性，绑定相互触发，轻则布局算错，重则绑定循环、界面卡死。

qml
// 错：跟布局抢 width 和 height
RowLayout {
    Rectangle { width: parent.width / 2; height: 40; Layout.fillWidth: true }
}

qml
// 对：尺寸全交给附加属性
RowLayout {
    Rectangle {
        Layout.fillWidth: true
        Layout.preferredHeight: 40
    }
}

要设尺寸就用 Layout.*，要让位置由布局决定就别碰 x/y。这条守住，Layout 的怪问题少一大半。

十、三种手段怎么配合 #

锚、定位器、布局，单个用都好说，混在一起才是事故现场。

同一个元素只能选一种 #

最硬的规矩：一个元素，要么归锚管，要么归布局管，不能两头都写。

qml
// 错：既锚又进布局
RowLayout {
    Rectangle {
        anchors.left: parent.left    // 跟布局抢水平位置
        Layout.fillWidth: true
    }
}

RowLayout 会给子项算 x，anchors.left 也要写 x。两边都写，Qt 会报锚与布局冲突的警告，几何结果别去赌——它不会是你想要的那个。

同理，布局的子项里写 anchors.fill: parent 是想「铺满这个格子」，结果铺满的是整个布局，元素直接盖住兄弟。

qml
// 对：位置交给布局，格子内对齐用 Layout.alignment
RowLayout {
    spacing: 8

    Rectangle {
        Layout.fillWidth: true
        Layout.preferredHeight: 40
        Layout.alignment: Qt.AlignVCenter
        color: "steelblue"
    }
}

分层混用是可以的 #

不同层级用不同手段，完全合法，而且推荐：

qml
Rectangle {
    width: 600; height: 400

    ColumnLayout {
        anchors.fill: parent        // 外层：锚
        anchors.margins: 12
        spacing: 10

        Text { text: "设置"; font.pixelSize: 16 }

        RowLayout {                 // 内层：布局
            Layout.fillWidth: true
            Layout.fillHeight: true
            spacing: 8

            Rectangle { Layout.fillWidth: true; Layout.fillHeight: true; color: "#fafafa" }
            Rectangle { Layout.preferredWidth: 120; Layout.fillHeight: true; color: "#e0e0e0" }
        }
    }
}

外层用 anchors.fill 把布局钉在父级上，内部全交给 Layout.*。层级分明，互不干扰。

判断标准很简单：看这个元素的直接父级是谁。 父级是普通 Item 或 Rectangle，用锚；父级是 Layout，用 Layout.*；父级是定位器，只用另一条轴的锚。

组合方式对照 #

组合 是否可用 说明
锚 + 坐标绑定 可以 不同方向上各管各的
锚 + 定位器（不同轴） 可以 Row 内锚垂直方向
锚 + 定位器（同轴） 不行 被忽略并警告
锚 + Layout（同一元素） 不行 抢 x/y/width/height，警告
隐式尺寸 + Layout 可以 布局读 implicitWidth 当首选尺寸
显式 width + Layout 不推荐 被布局覆盖，且容易形成绑定循环
定位器 + 显式 width 可以 定位器不改子项尺寸

十一、响应式与尺寸变化 #

QML 的响应式不是「监听 resize 事件再算」，而是绑定依赖自动重算。这根链条是：父级尺寸变 → 依赖它的表达式重算 → 布局收到新约束 → 布局重新分配 → 子项 x/y/width/height 被写入。

你一行事件处理代码都不用写。这也是为什么在布局里手写 width 是灾难——你插进了链条中间，把自动重算踩断了。

三套手段在缩放时的表现 #

手段 父级变大时 父级变小时
x/y 硬写 元素纹丝不动 元素被裁掉
x/y 绑定 按表达式跟随，需自己写公式 同上，会算出负值
锚 按锚线跟随，两条平行锚自动拉伸 按锚线压缩，可压到零
定位器 排列顺序不变，整排位置跟着移动 子项不压缩，溢出容器
Layout 按 fillWidth 与 min/max 重新分配 压到 minimum 为止，不再缩

最后一格是布局的关键价值：它知道下限。 窗口缩小时，RowLayout 会按 minimum 停住——没设最小就是 0——而不是算出一个负数。

让布局跟着窗口长 #

最外层那个布局，自己也是元素，需要一个锚把它钉在父级上：

qml
ApplicationWindow {
    width: 800; height: 600
    visible: true

    RowLayout {
        anchors.fill: parent     // 没有这一行，布局只有内容那么大
        spacing: 12

        Rectangle { Layout.fillWidth: true; Layout.fillHeight: true; color: "#f5f5f5" }
    }
}

忘了 anchors.fill，RowLayout 就缩成内容尺寸，窗口拉多大它都不动。这个坑跟 Flow 忘了给 width 是同一类：容器没有边界，就谈不上分配。

别用赋值去救 #

有人写 onWidthChanged: layout.width = width。这是把声明式改成命令式，出现多个触发源时属性被反复写入，绑定被破坏，界面开始抖。要布局跟着走，两条就够：anchors.fill 让容器铺满，Layout.fillWidth 让子项吃掉剩余。

尺寸约束放在对的地方 #

想达到的效果 写法
元素随容器拉伸 anchors.left + anchors.right，或 Layout.fillWidth: true
元素固定大小、靠右 anchors.right: parent.right + width 固定
元素铺满并留边 anchors.fill: parent + anchors.margins
元素在容器居中 anchors.centerIn: parent
平分剩余空间 RowLayout + 每个子项 Layout.fillWidth: true
允许压缩但不小于某值 Layout.minimumWidth
允许拉伸但不超过某值 Layout.maximumWidth

这张表覆盖了日常九成的布局需求。剩下的边角情况，才需要回到 x/y 绑定。

十二、易错点速查 #

写布局时出问题，先照这张表过一遍。

现象 病因 修法
按钮拉窗口时不跟着变宽 用了 Row，定位器不管尺寸 换 RowLayout + Layout.fillWidth: true
RowLayout 里元素还是不变宽 没设 Layout.fillWidth，默认 false 给要伸缩的子项加 Layout.fillWidth: true
控制台报锚冲突警告 anchors.fill 之后又设了单条锚线 用 anchors.margins，或拆成四条独立锚线
布局里元素位置乱跳 子项上还写了 x/y/width/height 尺寸改用 Layout.preferredWidth 等附加属性
元素盖住了兄弟 布局子项里写了 anchors.fill: parent 删掉，用 Layout.fillWidth/fillHeight
RowLayout 报类型未定义 没 import QtQuick.Layouts 补上模块导入
Flow 永远不换行 没给 width，容器撑到内容宽 显式设 width
Grid 行列数对不上 rows 和 columns 同时指定 只留一个，另一个自动推
嵌套布局不跟着外层走 内层布局没设 Layout.fillWidth/fillHeight 给内层布局补上
布局整体不动 最外层布局没锚到父级 anchors.fill: parent
元素被压成零宽 没设 Layout.minimumWidth，默认最小为 0 补最小宽度约束
元素撑爆容器 没设 Layout.maximumWidth，默认上限是无穷 补最大宽度约束
运行时警告锚循环 两个元素互相锚定 拆掉一环，改成单向依赖
布局算出的尺寸跟写的 width 不符 width 只是第三顺位兜底 改用 Layout.preferredWidth

三条能省下大量调试时间的原则 #

一、先定父级，再定写法。 父级是 Layout 就用 Layout.*，是普通元素就用锚，是定位器就只管另一条轴。写完先看控制台，警告不能留着。

二、尺寸只在一个地方说。 要么 width，要么 anchors 双锚线，要么 Layout.preferredWidth。同一个维度上有两个来源，就一定有一次覆盖，覆盖顺序不该靠猜。

三、要分空间就上布局。 只要脑子里的需求出现了「平分」「吃掉剩余」「按比例」这些词，Row、Column 就不用考虑了，直接 RowLayout。定位器解决不了分配问题，写再多绑定也只是把公式搬到别处。

最后留一句自己的体会：QML 的布局体系看着有三套，其实只有一条主线——位置和尺寸是两件事，别指望一套语法把两件事都办了。 锚擅长位置，定位器擅长顺序，布局擅长分配。认清这一点，剩下全是细节。
