这一篇只干一件事：把「画界面」和「写逻辑」拆成两件能分别干的事。

讲什么：.ui 的本质、uic 在编译期生成了什么、继承法与组合法两种落笔写法、QUiLoader 运行时加载、三种方式的取舍、信号槽怎么搭到 .ui 里的控件上、自定义控件提升、.qrc 与界面怎么配合。

不讲什么：布局管理器怎么摆控件在《容器与布局管理》；QSS 语法与换肤细节在 03-自定义窗口与样式；单个控件的行为参数在 01-控件基础与用法。MVC、MVVM 这类分层思想只在第一章交代边界，不展开成架构教程。

一、界面与逻辑为什么要分离 #

一句话：UI 归 UI，逻辑归逻辑，别混着写。新手最容易写出的东西长这样：

cpp
void MainWindow::on_calcButton_clicked()
{
    QString exp = ui->lineEdit->text();          // 读界面

    // ... 三十行解析、优先级判断、错误弹框全塞在这

    ui->resultLabel->setText(/* 结果 */);        // 回写界面

    QFile f("history.txt");                      // 顺手落盘
    f.open(QFile::Append);
    f.write(exp.toUtf8());
}

能跑，但三件事焊死在一起：读界面、算表达式、写文件。想给算法写单测，得先造一个 MainWindow，还得有屏幕。想换存储方式，得动界面类。想做命令行版本，整段抄一遍。

拆开以后，好处是实打实的：

好处 具体表现
互不干扰 改布局、调间距、换配色，不碰业务代码；改算法，界面一行不动
并行开发 一个人拖 Designer，一个人写算法，两边只对齐接口
易于测试 逻辑层不依赖 QtWidgets，裸 main() 或 QTest 就能跑
复用 同一套逻辑，给窗口版、命令行版、脚本版各配一层壳
换肤 样式抽到 .qss，加载哪个文件决定长什么样

一个典型程序就是两块：

模块 职责 依赖方向
用户界面模块（UI） 接收输入、展示数据 依赖逻辑的接口
业务逻辑模块 按需求处理数据 不依赖任何界面头文件

界面代码不许直接算业务，业务逻辑不许伸手去 setText()。

1.1 设计原则 #

强内聚、弱耦合，六个字刻脑子里。

  • 单一职责：一个模块只干一件事，MainWindow 不负责算数。
  • 模块组成：模块内部的子模块只服务这一个功能。
  • 交互规则：模块之间走约定好的接口，不走后门。
  • 单向依赖：A 依赖 B 可以，A 和 B 互相依赖就是设计出了问题。

循环依赖是糟糕设计的典型标志。两个类互相 #include，编译期就跟你翻脸。

接口这个词说清楚：广义上是模块之间的契约；C++ 里就是只含公开纯虚函数的抽象类；接口不写实现，实现方必须有类去接。

cpp
class ICalculator {
public:
    virtual bool expression(const QString &exp) = 0;
    virtual QString result() const = 0;
    virtual ~ICalculator() = default;
};

界面类只认 ICalculator*。哪天算法换成云端调用，界面代码一个字不用改。

1.2 Qt 的三种开发模式 #

模式 界面怎么来 逻辑写在哪 适用
纯代码 手写 QWidget、QLayout、new 控件 C++ 控件少、要动态生成、行为高度定制
Designer 拖控件存 .ui，构建时 uic 生成代码 C++ 大部分业务软件，界面稳定、控件多
QML 混合 .qml 描述界面，JS 写交互 C++ 做后端 动效多、触摸屏、嵌入式大屏

纯代码的代价是行数，20 个控件的表单手写三百行起步。Designer 的代价是多一层间接，你得知道 uic 干了什么，否则报错看不懂。QML 那条线不在本篇范围，下面都是 QtWidgets 这一支。

二、.ui 文件是什么 #

先纠正一个误解：.ui 不是界面，它连「能跑的界面」都不是。它是一个 XML 文本文件，UTF-8 编码，只描述「有哪些控件、叫什么名字、什么类型、怎么摆、什么属性」。Qt 运行时没有任何代码直接读 .ui 把它变成窗口——除了第七章要讲的 QUiLoader，那是另一条路。

拿记事本打开一个最小可用的 .ui：

xml
<?xml version="1.0" encoding="UTF-8"?>
<ui version="4.0">
 <class>MainWindow</class>
 <widget class="QMainWindow" name="MainWindow">
  <property name="windowTitle">
   <string>表达式计算器</string>
  </property>
  <widget class="QWidget" name="centralwidget">
   <layout class="QVBoxLayout" name="verticalLayout">
    <item>
     <widget class="QLineEdit" name="lineEdit"/>
    </item>
    <item>
     <widget class="QPushButton" name="calcButton"/>
    </item>
    <!-- 同层还有一个 QLabel，name="resultLabel"，写法同上，省略 -->
   </layout>
  </widget>
 </widget>
</ui>

几何信息在真实文件里还有一段 <property name="geometry"><rect>... ，这里省掉了。注意三个名字的区别，这是最容易绕晕的地方：

名字 出现位置 含义
MainWindow（<class>） 生成 Ui::MainWindow uic 用的类名
MainWindow（<widget name>） 根控件的 objectName 运行时对象名，findChild 靠它
lineEdit / calcButton 子控件 objectName 代码里 ui->lineEdit 的来源

<class> 和你的窗口类名对不上不会报错，但会让你 ui-> 后面点不出东西。

2.1 元素速查 #

元素 作用 uic 怎么处理
<class> 界面类名 拼出 Ui_<名字>
<widget> 一个控件，class 是类型，name 是 objectName 生成成员指针 + new + setObjectName
<layout> 挂在控件上的布局 生成布局并 addWidget / addItem
<item> 布局里的一个子项 按顺序塞进上一个布局
<property> 属性名与值 生成 setXxx() 调用
<connection> 信号槽连线 生成 connect(...)
<customwidget> 提升过的自定义控件 生成 #include 并换类型
<resources> 引用的 .qrc 参与资源编译

<property> 的套路：名字对应 Qt 属性名，类型标签决定怎么写值。<string>、<bool>、<number>、<enum>、<rect>、<size>、<font>，写错了 uic 直接报解析错误。<tabstops> 生成 setTabOrder()，<buttongroups> 生成 new QButtonGroup。

2.2 为什么它不能直接跑 #

.ui 里只有数据，没有一句 C++。控件怎么 new、父对象是谁、布局怎么 addWidget、属性怎么 set，全靠另外两个角色：

角色 时机 干什么
uic 编译期（构建时） 把 .ui 翻译成 ui_xxx.h，里面是纯 C++
QUiLoader 运行期 读 .ui，反射建对象，当场拼一个 QWidget

记住这条主线：.ui 是 XML，不是可执行界面。它必须经过 uic 变成 C++ 代码（编译期），或者被 QUiLoader 解析（运行时），Qt 才认识它。跳过这两步，.ui 在你程序眼里就是一个普通文本文件。

顺带一个结论：.ui 是纯文本，能进 Git，能 diff，能合并。二进制资源做不到。

三、uic 的工作：编译期生成代码 #

uic 全称 User Interface Compiler，输入 .ui，输出 .h。

text
uic mainwindow.ui -o ui_mainwindow.h

平时不用手敲，构建系统替你跑：

FORMS += mainwindow.ui       # 声明 .ui，构建系统自动调 uic

CMake 那边开 AUTOUIC，Qt5 和 Qt6 都认：

cmake
set(CMAKE_AUTOUIC ON)        # 自动扫 FORMS 与 add_executable 里的 .ui
qt_add_executable(app main.cpp mainwindow.cpp mainwindow.ui)

开了 AUTOUIC 之后，在 mainwindow.cpp 里 #include "ui_mainwindow.h" 就能编过。这个头文件不在源码目录，在构建目录，IDE 跳不过去是正常的。想看某个 .ui 会被翻译成什么，直接 uic form.ui 打到标准输出，比翻构建目录快。

3.1 生成出来的东西长什么样 #

假设 .ui 里 <class> 写的是 MainWindow，uic 生成这个结构（省了属性细节）：

cpp
// ui_mainwindow.h —— uic 生成，不要手改
#ifndef UI_MAINWINDOW_H
#define UI_MAINWINDOW_H

#include <QtWidgets/QApplication>
#include <QtWidgets/QMainWindow>
#include <QtWidgets/QVBoxLayout>
// 其余 QLabel / QLineEdit / QPushButton 的头文件按控件逐个补，此处省略

QT_BEGIN_NAMESPACE

class Ui_MainWindow
{
public:
    QWidget *centralwidget;
    QVBoxLayout *verticalLayout;
    QLineEdit *lineEdit;
    QPushButton *calcButton;
    QLabel *resultLabel;

    void setupUi(QMainWindow *MainWindow)
    {
        if (MainWindow->objectName().isEmpty())
            MainWindow->setObjectName(QString::fromUtf8("MainWindow"));
        MainWindow->resize(420, 180);

        centralwidget = new QWidget(MainWindow);
        verticalLayout = new QVBoxLayout(centralwidget);

        lineEdit = new QLineEdit(centralwidget);
        lineEdit->setObjectName(QString::fromUtf8("lineEdit"));
        verticalLayout->addWidget(lineEdit);
        calcButton = new QPushButton(centralwidget);
        calcButton->setObjectName(QString::fromUtf8("calcButton"));
        verticalLayout->addWidget(calcButton);
        resultLabel = new QLabel(centralwidget);
        resultLabel->setObjectName(QString::fromUtf8("resultLabel"));
        verticalLayout->addWidget(resultLabel);

        MainWindow->setCentralWidget(centralwidget);
        retranslateUi(MainWindow);                    // 末尾两句别漏
        QMetaObject::connectSlotsByName(MainWindow);
    }

    void retranslateUi(QMainWindow *MainWindow)
    {
        MainWindow->setWindowTitle(QCoreApplication::translate(
            "MainWindow", "\350\241\250\350\276\276\345\274\217", nullptr));
        // 每个可见字符串都在这重新赋一次，供 lupdate 抽进 .ts
    }
};

namespace Ui {
class MainWindow: public Ui_MainWindow {};
} // namespace Ui

QT_END_NAMESPACE
#endif // UI_MAINWINDOW_H

五件事必须看懂：

  1. Ui_MainWindow 是普通类，不是 QObject。没有 Q_OBJECT，没有信号槽，就是一个装指针的壳子。
  2. 子控件是公有成员指针，new 时把 centralwidget 设成 parent，生命周期挂在窗口上，uic 不管 delete。
  3. setupUi() 干两件事：建对象、设属性，末尾调 retranslateUi 和 connectSlotsByName。
  4. namespace Ui 里那个派生类是给你的，写 Ui::MainWindow *ui 用的是它。
  5. 中文变成八进制转义。"\350\241\250..." 是 UTF-8 字节的八进制写法，QString::fromUtf8 拼回来就是正常中文。别手改产物，下次构建就没了。

uic 的产物不带任何业务判断。它不知道按钮点了要干什么，只负责把界面搭出来。这就是「分离」的物理基础——这部分代码永远不用你维护。

3.2 与构建流程的关系 #

Designer 存出 .ui → uic 转成 ui_mainwindow.h → 编译器连同 mainwindow.cpp 编成目标文件 → 链接器加上 Qt5Widgets 产出可执行文件。改 .ui 只重跑后三步，.cpp 一个字不动；改 .cpp 只重编不重生成。两边独立，这是 Designer 方案能提高开发效率的根子。

四、三种使用 .ui 的方式 #

有了 ui_xxx.h，代码层面还有三种写法，项目里经常同时存在。

方式 谁生成界面 何时 代码里怎么拿控件 典型场景
继承法 uic 生成 Ui::Xxx，自己类持有指针 编译期 ui->lineEdit 常规窗口，占九成
组合法 同上，Ui::Xxx 作为私有成员藏起来 编译期 内部 m_ui->lineEdit，外部走接口 控件库、想藏实现
QUiLoader 运行时解析 .ui 运行期 findChild<QLineEdit *>("lineEdit") 换皮肤、插件、动态表单

继承法和组合法的差别不在 uic，在「Ui::Xxx 这个壳子放在哪」。两种写法下 uic 产物完全一样，都是 setupUi(容器指针)。

选哪条，按这个顺序问自己：

text
界面在编译前定死了吗？
├── 是 → 继承法（首选），需要对外隐藏 ui 成员就换组合法
└── 否 → 界面要运行期替换 / 下发 / 热插拔吗？
    ├── 是 → QUiLoader
    └── 否 → 纯代码写

三条路的共同点：都能拿到同一批控件，都能连信号槽，都能挂 QSS。区别只在「界面何时变成对象」和「编译期能不能查出问题」。

五、继承法：最常用的做法 #

这个名字有点误导，它不是说窗口类去继承 Ui::MainWindow，而是「窗口类持有 Ui::MainWindow 指针，两者一对一」。Creator 新建窗体给的就是这个模板。

头文件里只放前置声明：

cpp
// mainwindow.h
#ifndef MAINWINDOW_H
#define MAINWINDOW_H

#include <QMainWindow>

QT_BEGIN_NAMESPACE
namespace Ui { class MainWindow; }   // 前置声明，故意不 include ui_mainwindow.h
QT_END_NAMESPACE

class MainWindow : public QMainWindow
{
    Q_OBJECT

public:
    explicit MainWindow(QWidget *parent = nullptr);
    ~MainWindow() override;

private slots:
    void onCalc();

private:
    Ui::MainWindow *ui;   // 指针，不是值
};

#endif // MAINWINDOW_H

实现文件里才 include 产物：

cpp
// mainwindow.cpp
#include "mainwindow.h"
#include "ui_mainwindow.h"       // uic 产物，在构建目录里

MainWindow::MainWindow(QWidget *parent)
    : QMainWindow(parent)
    , ui(new Ui::MainWindow)     // 先建壳子
{
    ui->setupUi(this);           // 再让壳子往 this 上挂控件
    connect(ui->calcButton, &QPushButton::clicked, this, &MainWindow::onCalc);
}

MainWindow::~MainWindow() { delete ui; }

void MainWindow::onCalc()
{
    const QString exp = ui->lineEdit->text();
    ui->resultLabel->setText(exp);
}

三个顺序问题，踩过一次就记住：

顺序 要求 写错的后果
1 ui(new Ui::MainWindow) 在初始化列表里 ui->setupUi(this) 空指针崩溃
2 setupUi(this) 之后才能碰 ui->xxx 控件还没建，成员指针是野值
3 析构里 delete ui 泄漏，一次几 KB，跑一天就明显

第 3 条有人会想「控件 parent 都是 this，QObject 树会帮我删」。控件确实被删了，但 Ui::MainWindow 这个壳子不是 QObject，它不在树上，得手动收。

5.1 为什么不 include 生成的头文件 #

因为产物在构建目录，而 mainwindow.h 会被别处 include。塞进去等于把构建产物变成公共依赖：

写法 头文件依赖 改 .ui 后重编译范围
前置声明 + 指针 只需 QMainWindow 只重编 mainwindow.cpp
头文件里 include ui_xxx.h 拖进 QVariant 和一堆 QtWidgets 所有 include 了 mainwindow.h 的文件

第二种能编过，代价是编译时间。改个按钮位置全项目重编，那个酸爽。

六、组合法：把 ui 当成员 #

组合法在同一套 uic 产物上换摆法：Ui::CalcWidget 不出现在头文件里，窗口类对外只暴露自己的方法。

cpp
// calcwidget.h
#include <QWidget>

namespace Ui { class CalcWidget; }   // 依然前置声明

class CalcWidget : public QWidget
{
    Q_OBJECT

public:
    explicit CalcWidget(QWidget *parent = nullptr);
    ~CalcWidget() override;

    void setExpression(const QString &exp);   // 对外接口，不暴露 ui 细节
    QString resultText() const;

signals:
    void calcRequested(const QString &exp);

private:
    Ui::CalcWidget *m_ui;   // 命名上跟继承法的 ui 区分开
};

#endif // CALCWIDGET_H

cpp
// calcwidget.cpp
#include "calcwidget.h"
#include "ui_calcwidget.h"      // uic 产物，命名规则是 ui_ + .ui 文件名

CalcWidget::CalcWidget(QWidget *parent)
    : QWidget(parent)
    , m_ui(new Ui::CalcWidget)
{
    m_ui->setupUi(this);
    connect(m_ui->calcButton, &QPushButton::clicked, this, [this] {
        emit calcRequested(m_ui->lineEdit->text());
    });
}

CalcWidget::~CalcWidget() { delete m_ui; }

// 对外只给这两个口子，界面上有多少控件外面不知道
void CalcWidget::setExpression(const QString &exp) { m_ui->lineEdit->setText(exp); }
QString CalcWidget::resultText() const { return m_ui->resultLabel->text(); }

结构上和继承法几乎一样，差别在「控件怎么出去」：继承法里任何拿到 MainWindow* 的人都能 include ui_mainwindow.h 摸到全部控件；组合法里外部只能调 setExpression()，界面内部换布局外面不知道。

组合法的取舍：

维度 情况
封装性 好，ui 不出现在任何头文件里
编译时间 好，改 .ui 只重编一个 .cpp
啰嗦度 高，每处写 m_ui->，还要手写对外接口
适合 控件库、插件、被别的模块大量复用的窗口
不适合 只在 main 里 show() 一次的主窗口，包一层纯属自找麻烦

Ui::CalcWidget 用指针还是用值，也是一次取舍：用指针只需前置声明，代价是多一次堆分配和手动 delete；用值不用管生命周期，代价是头文件必须 include ui_calcwidget.h，重编译范围跟着变大。两种写法代码量差距不大，差的是「谁有权碰界面」。项目里有人抱怨「界面一改别的模块全崩」，多数是继承法把 ui 漏出去了。

七、QUiLoader：运行时加载 #

前面两条路的界面在编译期就焊进可执行文件了。有些场景做不到：

  • 客户换皮肤，改完 .ui 不想重新发版；
  • 插件式软件，插件带着自己的 .ui 进来，主程序事先不知道有哪些控件；
  • 表单由配置生成，字段在部署现场才定。

这时候用 QUiLoader。它在运行期读 .ui，反射建对象，给你一个 QWidget*。

7.1 工程配置 #

QUiLoader 在 uitools 模块里，不是 widgets 的默认成员。.pro 里补上：

QT += core gui widgets uitools

cmake
find_package(Qt6 REQUIRED COMPONENTS Widgets UiTools)   # CMake 等价写法
target_link_libraries(app PRIVATE Qt6::Widgets Qt6::UiTools)

源文件里包含 QUiLoader、QFile、QWidget、QPushButton 四个头。发布时别忘 Qt6UiTools.dll，漏了在客户机器上起不来，本地开发一切正常。

7.2 加载与通信 #

QUiLoader::load() 返回 QWidget*。找控件靠 findChild<T>()，参数是 .ui 里那个 objectName。

主窗口按继承法搭，另外加一个成员存动态窗体：QWidget *m_dynamicWidget = nullptr;。

cpp
// MainWindow.cpp
#include "MainWindow.h"
#include "ui_mainwindow.h"
#include <QUiLoader>
#include <QFile>
#include <QCoreApplication>
#include <QPushButton>
#include <QDebug>

MainWindow::MainWindow(QWidget *parent)
    : QMainWindow(parent), ui(new Ui::MainWindow)
{
    ui->setupUi(this);
    connect(ui->pushButton, &QPushButton::clicked, this, &MainWindow::showWidget);
}

MainWindow::~MainWindow()
{
    delete m_dynamicWidget;   // 不在 QObject 树上，自己收
    delete ui;
}

void MainWindow::showWidget()
{
    if (!m_dynamicWidget)
    {
        QUiLoader loader;
        // 相对可执行文件定位，别把本机绝对路径写进代码
        QFile file(QCoreApplication::applicationDirPath() + QStringLiteral("/skins/Test.ui"));
        if (!file.open(QFile::ReadOnly)) {
            qWarning() << "打开失败:" << file.fileName() << file.errorString();
            return;
        }

        m_dynamicWidget = loader.load(&file);   // 解析并实例化
        file.close();

        // 关键一步：按 objectName 找控件
        if (QPushButton *btn = m_dynamicWidget->findChild<QPushButton *>("pushButton"))
            connect(btn, &QPushButton::clicked, this, &MainWindow::changeText);
        else
            qWarning() << "Test.ui 里没有名为 pushButton 的 QPushButton";
    }
    m_dynamicWidget->show();
}

changeText() 就是给主界面按钮换文字和底色的一段 QSS 演示，跟加载无关，这里不展开。

findChild 的返回值得判空。名字对不上时它返回 nullptr，不抛异常、不打印，按钮点了没反应——这种静默失败很费时间，加一句 qWarning 一次定位。

类型参数也得对。按 qobject_cast 匹配，不做隐式转换，.ui 里是 QPushButton，写 findChild<QLineEdit *> 拿到的是空。

load() 返回的是通用 QWidget*，根控件是别的类型时要转型：

根控件类型 转型写法
QWidget / QFrame 直接用
QDialog qobject_cast<QDialog *>(loader.load(&file))
QMainWindow qobject_cast<QMainWindow *>(loader.load(&file))
任意子控件 widget->findChild<QPushButton *>("okButton")

C 风格强转 (QDialog*)p 也能过，类型不对就是未定义行为；qobject_cast 失败返回空指针，能判。

7.3 生命周期与坑 #

load() 出来的控件没有父对象，三种收法选一种：显式 delete m_dynamicWidget;；或 setParent(this) 挂到窗口上跟窗口一起死；或 setAttribute(Qt::WA_DeleteOnClose) 关掉即销毁。

坑 现象 处理
指针不释放 反复加载内存一路上涨 delete 或 setParent
反复 load() 同一文件 同位置叠出多个窗口 缓存指针，判空再加载
绝对路径写死 换机器就崩 applicationDirPath() 拼相对路径
名字拼错 界面出来了，按钮没反应 findChild 后判空加日志
忘了 uitools 编译期报 QUiLoader 未定义 QT += uitools
样式表没生效 动态窗体一片灰 在 show() 前设样式

样式表这条值得说：动态部件跟着 QApplication 和父窗口的样式表走，因为 QSS 匹配靠对象树。.ui 里给单个控件写的 styleSheet 属性也会被应用，按就近覆盖。换肤场景把配色全放外部 .qss，加载完窗体再刷一次。

7.4 QUiLoader 做不到的事 #

能力 状态
标准控件、布局、属性、字体、图标 全支持
提升成自定义控件的部件 要 registerCustomWidget() 注册，否则退化成基类
.ui 里的 <connection> 由 loader 建，槽必须能被元对象找到；建议自己 findChild + connect
.ui 里的资源 :/xxx、多语言 tr() 资源要求已编进主程序，翻译文件名要与 <class> 一致

自定义控件那条是硬伤。.ui 里写了 class="MyGauge"，程序里没有对应元对象，loader 建不出来，直接退化成 QWidget，界面上就是一个空白方块。

八、三种方式的对比与取舍 #

维度 继承法 组合法 QUiLoader
界面何时变对象 编译期 编译期 运行期
谁干活 uic 生成 C++ uic 生成 C++ 反射
取控件写法 ui->lineEdit 内部 m_ui->lineEdit findChild<...>("lineEdit")
编译期检查 有 有 无，名字错了运行期才知道
改界面要重编译 要 要 不用
代码量 最少 多一层接口 中等，加错误处理
自定义控件 天然支持 天然支持 要注册，否则退化
IDE 补全 完整 完整 无，全靠字符串
适用 常规窗口 控件库、插件 换肤、动态表单、热插拔

uic 和 QUiLoader 的对照，本质是「编译期翻译」与「运行期解释」的老话题：

对比项 uic QUiLoader
输入 .ui .ui
输出 ui_xxx.h 里的 C++ 内存里的 QWidget 树
错误发现 编译时报错 运行期返回空指针
界面可替换 不能，除非重编译 能，换个文件就行
性能开销 零 解析、反射、属性设置
交叉引用 编译期全知道 只有字符串

实际项目基本混着用：

text
主窗口、设置页、业务对话框      → 继承法（绝大多数）
带 ui 的通用控件                → 组合法（藏 ui，对外只给接口）
皮肤包、插件界面、配置表单      → QUiLoader

判断标准很好用：界面文件的改动者是程序员还是别人。只有程序员改，继承法；客户、实施、配置表要改，QUiLoader。

反面的教训也要记住：把主窗口改成 QUiLoader，图的是「改界面不重编译」，结果是取控件全靠字符串，重构工具失效，改个名字得全局搜。编译期检查值这个钱的时候，别省。

九、信号槽怎么连到 ui 里的控件 #

界面拆出来了，逻辑类怎么知道按钮被点了？三条路。

方式 写法 谁建的连接 检查时机
手动 connect connect(ui->calcButton, &QPushButton::clicked, this, &MainWindow::onCalc) 你，构造函数里 编译期
自动连接 槽名写成 on_calcButton_clicked() connectSlotsByName，在 setupUi 里 运行期，名字错就静默不连
Designer 连线 .ui 里存 <connection> uic 生成 connect 编译期

手动连接最直白，也最好搜：

cpp
MainWindow::MainWindow(QWidget *parent)
    : QMainWindow(parent), ui(new Ui::MainWindow)
{
    ui->setupUi(this);
    connect(ui->calcButton, &QPushButton::clicked, this, &MainWindow::onCalc);
    connect(ui->lineEdit, &QLineEdit::returnPressed, this, &MainWindow::onCalc);
    // 重载信号必须指明是哪一个
    connect(ui->comboBox, QOverload<int>::of(&QComboBox::currentIndexChanged),
            this, &MainWindow::onIndexChanged);
}

自动连接靠命名约定，函数名必须是 on_<objectName>_<信号名>，参数照抄信号参数：

cpp
private slots:
    void on_calcButton_clicked();                        // 对应 calcButton 的 clicked()
    void on_lineEdit_textChanged(const QString &text);
    void on_comboBox_currentIndexChanged(int index);

它生效的前提是 connectSlotsByName(this) 在 setupUi() 末尾被调过，且此时控件已存在。setupUi() 之后自己 new 的控件不参与自动连接，只能手动 connect。自动连接的可搜索性差——看不出谁连的，改 objectName 就静默断掉，所以大项目推荐手动 connect，只在临时原型里用自动连接。

界面类不该直接连业务层，正确的链条是两级：

cpp
// 界面类：把控件事件翻译成自己的信号
connect(ui->calcButton, &QPushButton::clicked, this, [this] {
    emit calcRequested(ui->lineEdit->text());
});
// 组装层：把界面信号接到逻辑对象
connect(m_ui, &MainWindow::calcRequested, m_logic, &Calculator::expression);
// 逻辑结果回来，界面自己刷新
connect(m_logic, &Calculator::finished, this, [this](const QString &r) {
    ui->resultLabel->setText(r);
});

界面不知道 Calculator 存在，Calculator 不知道 QPushButton 存在。哪天把计算挪进线程，只在组装层加一句 moveToThread，界面代码不动。

十、自定义控件提升 #

界面里放了个 QWidget，后来想换成自己的 MyGauge——继承 QWidget，自己 paintEvent 画表盘。Designer 不认识你的类，重新拖一个行不通，这时候用「提升」（Promote）。

提升的本质：.ui 里那个部件仍写成标准控件的标签，但多一段 <customwidget> 声明，告诉 uic「这个位置实例化时换成 MyGauge」。

先准备类，构造函数签名必须带默认参数：

cpp
// mygauge.h
#include <QWidget>

class MyGauge : public QWidget
{
    Q_OBJECT

public:
    explicit MyGauge(QWidget *parent = nullptr);   // parent 默认参数不能省
    void setValue(int v);

protected:
    void paintEvent(QPaintEvent *event) override;

private:
    int m_value = 0;
};

然后在 Designer 里操作：

步骤 操作 结果
1 从控件箱拖一个 QWidget（或任何基类）到窗体 有个占位框
2 右键 → Promote to... 弹出提升对话框
3 Promoted class name 填 MyGauge 类名，不带命名空间前缀
4 Header file 填 mygauge.h uic 生成的 #include 就用它
5 点 Add，再点 Promote 控件箱里出现 MyGauge
6 以后从控件箱拖 MyGauge 进来 自动带提升声明

.ui 里会多出这一段：

xml
<customwidgets>
 <customwidget>
  <class>MyGauge</class>
  <extends>QWidget</extends>
  <header>mygauge.h</header>
  <container>0</container>
 </customwidget>
</customwidgets>

uic 就把成员指针的类型和 new 的对象都换掉：

cpp
// ui_mainwindow.h 片段
#include "mygauge.h"      // 由 <header> 决定

MyGauge *gauge;           // 不再是 QWidget

gauge = new MyGauge(centralwidget);
gauge->setObjectName(QString::fromUtf8("gauge"));
verticalLayout->addWidget(gauge);

三处字段都要填对，错一个就编不过或者退化成基类：

字段 填错的后果
Promoted class name 与 C++ 类名不一致，报 MyGauge is not a type
Header file 生成的 #include 找不到文件，报 No such file
extends 类型不匹配，addWidget 参数对不上

提升的坑集中在来源上：

  • 头文件名填成 mygauge（漏了 .h），uic 生成 #include "mygauge"，多数平台报错。
  • 提升的类没有继承 QWidget 家族。QVBoxLayout::addWidget 只收 QWidget*，错误会跑到 uic 产物里，看着像 Qt 的问题。
  • 头文件不在 include 路径。工程里加 INCLUDEPATH += $$PWD/controls。
  • 全局提升和本次提升混着用。前者写进 Designer 全局配置，别人没这个配置，拖进来的同名控件不生效。团队统一把提升信息写进 .ui。
  • 用了 QUiLoader 加载。提升的类得先 registerCustomWidget() 注册，否则退化成基类，界面上一片空白。

提升后的控件在 Designer 里显示成基类外观，看不出你的绘制效果，这是正常的。运行起来才准。

十一、资源文件与界面 #

界面要用图标、背景图，这些文件不该散在硬盘上等程序拼路径。Qt 的做法是编进可执行文件：.qrc。

xml
<!-- res.qrc -->
<RCC>
 <qresource prefix="/">
  <file>icons/ok.png</file>
  <file>icons/cancel.png</file>
  <file>styles/dark.qss</file>
 </qresource>
</RCC>

RESOURCES += res.qrc          # CMake 里对应 set(CMAKE_AUTORCC ON) + 把 res.qrc 列进目标源
路径写法 指向
:/icons/ok.png 资源里的绝对路径（prefix 为 /）
qrc:/icons/ok.png QML 写法，QtWidgets 用不到

.ui 里要引用资源，得让 <ui> 记住 .qrc，之后 Designer 里设图标写的就是 :/icons/ok.png：

xml
<resources>
 <include location="res.qrc"/>
</resources>

xml
<property name="icon">
 <iconset resource="res.qrc">
  <normaloff>:/icons/ok.png</normaloff>
 </iconset>
</property>

QSS 里同样走 :/：

cpp
QFile f(":/styles/dark.qss");
if (f.open(QFile::ReadOnly | QFile::Text))
    qApp->setStyleSheet(QString::fromUtf8(f.readAll()));

三条经验：

事项 说明
大小写 资源路径区分大小写，Windows 上也区分，写错运行期就是白图；文件名别用中文和空格
动态加载 .ui 里的 :/xxx 要求资源已编进主程序；换皮肤换的是 .ui 和 .qss，资源仍在 exe 里

真要运行期换图片，走磁盘绝对路径或 QDir::searchPaths，别指望 qrc。

十二、易错点速查 #

症状 根因 处理
ui_mainwindow.h: No such file 没把 .ui 加进 FORMS / 没开 AUTOUIC 构建系统里声明 .ui，清理后重建
ui->lineEdit 编译报不存在 .ui 里控件的 objectName 不是 lineEdit 回 Designer 改 objectName
启动即崩在 setupUi ui 没 new，或 setupUi 前就用了控件 初始化列表里 new，之后才碰控件
按钮点了没反应 on_xxx_clicked 名字对不上，或 findChild 返回空 用 qWarning 打出 findChild 结果
提升的控件显示空白 .ui 里类名/头文件名填错，或 loader 没注册 对照 <customwidget> 三个字段逐项核
改 .ui 后界面没变 增量构建没重跑 uic 删构建目录里的 ui_*.h 再编
换机器找不到 .ui 路径写死成本机绝对路径 applicationDirPath() 拼相对路径
QUiLoader 未定义 没链 uitools QT += uitools，发布带上 UiTools 库

交代码前过一遍自查清单：

text
□ .ui 只描述界面，里面没有任何业务值
□ 窗口类的头文件没有 include ui_xxx.h
□ setupUi 之后才访问 ui-> 成员
□ 析构里有 delete ui（或 delete m_ui）
□ 控件事件先变成界面类的信号，再由组装层连到逻辑
□ 逻辑类没有 include 任何 QtWidgets 头
□ 动态加载的窗体有明确的删除路径；提升的类名与头文件名和代码一致

界面和逻辑分开，不是为了让目录看起来整齐。是为了改界面的时候不动逻辑，改逻辑的时候不怕界面。这条线一旦划清，后面加皮肤、加插件、加单测，都是顺着这条线长出来的。
