这一篇只讲一件事：Qt 界面里那层「和系统直接打交道」的能力。键盘按键怎么进到控件、Esc 与 Tab 怎么改、焦点顺序怎么排、屏幕和窗口怎么截、摄像头怎么开、日志怎么打到窗口里、Windows 原生属性框怎么调出来。

不讲布局管理器、样式表、模型视图、信号槽底层、打包发布，那些归别的篇目。跨篇看「事件处理」看分发机制，看「对话框：模态与非模态」看窗口生命周期，看「日志输出文件」看落盘方案。

边界划在「单个控件的输入与输出」：输入是键盘与焦点，输出是屏幕像素、摄像头帧、日志文本、系统对话框。代码基于 Qt 5，主力平台 Windows，Wayland 与 macOS 的差异单独标出。

一、键盘事件的处理链路 #

先把结论摆在最前面，后面每一节都在用它：

键盘事件能不能到达一个控件，取决于这个控件有没有焦点。控件没有焦点，keyPressEvent 一次都不会被调用。

「按键没反应」绝大多数不是业务代码写错，而是控件压根没资格收键盘。没资格只有两种原因：没开焦点策略，或者焦点被别的控件拿走了。排查顺序固定——先 hasFocus() 打一行日志，再确认 focusPolicy()，最后才读 keyPressEvent 里的分支。

1.1 一次按键要走完的六步 #

步骤 出手对象 发生了什么 你能插手的位置
1 平台插件 窗口系统把按键投给当前焦点窗口 无
2 QApplication::notify 组装 QKeyEvent，先发 QEvent::ShortcutOverride 重写 event() 抓 ShortcutOverride
3 快捷键表 QShortcut、QAction、Alt 助记符匹配，命中就被吃掉 注册 QShortcut 或 QAction
4 QWidget::event 进 KeyPress 分支，横插一道焦点链判断 重写 event()
5 keyPressEvent 控件的业务处理入口 重写 keyPressEvent()
6 父控件链 被 ignore() 后向上冒泡，直到顶层或有人接住 父控件的 keyPressEvent

第 5 步大家最熟，但它前面第 4 步还有一道闸：QWidget::event() 对这个分支里的 Tab、Shift+Tab 做了硬编码判断，先交给焦点链，处理完直接 return true，keyPressEvent 轮不到。这是本篇第二个要点，第三节专门拆。

1.2 看清按键死在哪一层 #

cpp
class KeyProbe : public QWidget
{
    Q_OBJECT
protected:
    bool event(QEvent *e) override
    {
        if (e->type() == QEvent::KeyPress)
            qDebug() << "event()  key =" << static_cast<QKeyEvent *>(e)->key();
        return QWidget::event(e);         // 交给基类，别自己吞
    }
    void keyPressEvent(QKeyEvent *e) override
    {
        qDebug() << "keyPress key =" << e->key();
        e->ignore();                      // 不处理就还给父控件
    }
};

构造函数里补上 setFocusPolicy(Qt::StrongFocus); setFocus();，两条日志都出现；注释掉，两条同时消失。这就是本篇开头那句话的可复现版本。

1.3 事件对象里该读的字段 #

接口 返回 用途
key() Qt::Key 枚举值 判物理键，与键盘布局无关
text() QString 判输入字符，受输入法影响
modifiers() Qt::KeyboardModifiers 判 Ctrl、Shift、Alt 组合
isAutoRepeat() bool 过滤长按重复事件

判功能键用 key()，判文字输入用 text()。做快捷键一律用 key()，别拿 text() 比大小写——中文输入法一开，text() 给的是候选字。

accept() 表示「处理完了」，传播到此为止；ignore() 表示「我不处理」，事件转给父控件。keyPressEvent 的默认实现就是 ignore()，所以不想管的键什么都不写就对了。反过来，在某个分支里写了 accept() 却什么都没做，这个键就被彻底吞掉，上层再也看不见。

二、Esc 键的三种用法 #

QDialog 有个默认行为：按下 Esc，对话框关掉。很多人以为这是 close()，于是在 closeEvent() 里弹确认框，结果键盘一敲窗口照退。

2.1 默认链路：Esc 走的是 reject() #

QDialog 对 Esc 的处理，接近下面这段：

cpp
// QDialog 的默认实现，等价逻辑
void QDialog::keyPressEvent(QKeyEvent *e)
{
    if (e->key() == Qt::Key_Escape) {
        reject();                 // 注意：不是 close()
        return;
    }
    QWidget::keyPressEvent(e);
}

reject() 是个 virtual protected slot，内部调 done(QDialog::Rejected)，后者干三件事：隐藏窗口、设置 result()、发 finished(int)。

closeEvent() 在 QWidget::close() 那条路上。Esc 从头到尾没碰 close()，所以重写 closeEvent() 拦不住 Esc。这个错位是「明明写了确认弹窗，Esc 还是把窗口关了」的唯一原因。

QDialog::closeEvent() 内部又反过来调 reject()。于是两条路在同一个点碰头——右上角红叉 → close() → closeEvent() → reject()；Esc → keyPressEvent() → reject()。改 reject() 一处，两条路一起管住。

2.2 用法一：接受默认，在 reject 里做清理 #

确认框、工具窗、向导取消页，Esc 退出就是设计意图。什么都不改，但清理逻辑要挂对地方。

停定时器、断连接这些动作写在 reject() 里最保险——Esc 与红叉都会经过这里，末尾再调一次 QDialog::reject() 让基类完成隐藏与 finished 信号。

别把清理只写在析构里。reject() 之后对话框对象常常还活着（栈对象或复用对象），资源不释放，下次打开就是脏状态。

2.3 用法二：重写 reject() #

要拦 Esc 也拦红叉，这是最短路径。

cpp
// 头文件
class LoginDialog : public QDialog
{
    Q_OBJECT
protected:
    void reject() override;
};

// 源文件
void LoginDialog::reject()
{
    // 警告：这里不要调 QDialog::reject()，否则照样隐藏退出
    QMessageBox::StandardButton btn = QMessageBox::question(
        this, QStringLiteral("确认"),
        QStringLiteral("确认要放弃当前录入并关闭窗口吗？"),
        QMessageBox::Yes | QMessageBox::No, QMessageBox::No);

    if (btn == QMessageBox::Yes)
        this->close();          // 确认后走正常关闭流程
    // 用户点 No，函数返回，窗口留在原地
}

连确认都不要，纯屏蔽就是 return; 一句话。这种写法必须另配出口（比如「取消」按钮里显式调 done(QDialog::Rejected)），否则用户没有退路，只能杀进程。

2.4 用法三：重写 keyPressEvent 只吃 Esc #

只想接管 Esc，其他键（Enter 激活默认按钮、Tab 切焦点）原样保留，就落到按键层。

cpp
// 头文件
class LoginDialog : public QDialog
{
    Q_OBJECT
protected:
    void keyPressEvent(QKeyEvent *event) override;
};

// 源文件
void LoginDialog::keyPressEvent(QKeyEvent *event)
{
    switch (event->key()) {
    case Qt::Key_Escape:
        event->accept();        // 标记已处理，不做任何响应
        break;
    default:
        QDialog::keyPressEvent(event);   // 极重要：交还基类
    }
}

default 分支漏了会怎样：Enter 不再触发默认按钮，Esc 之外的所有按键行为集体失效，而且现象时好时坏——取决于焦点当时在哪个控件上。这类 bug 排查成本极高。

2.5 普通 QWidget 想要 Esc 关窗 #

QWidget 基类没有 reject()，用法二用不了。只剩一条路：抓到 Qt::Key_Escape 后自己 close()。

cpp
class FloatingPanel : public QWidget
{
    Q_OBJECT
public:
    explicit FloatingPanel(QWidget *parent = nullptr) : QWidget(parent)
    {
        setFocusPolicy(Qt::StrongFocus);   // 没有焦点，Esc 一样收不到
    }
protected:
    void keyPressEvent(QKeyEvent *e) override
    {
        if (e->key() == Qt::Key_Escape) {
            close();
            e->accept();
            return;
        }
        QWidget::keyPressEvent(e);
    }
};

前提还是焦点。面板上的 QLineEdit 拿到焦点时，Esc 先送到 QLineEdit，它不处理就冒泡到面板，面板收得到。面板里嵌了 QTextEdit 就不一定，它自己会消费一部分按键，这类控件上的 Esc 要用事件过滤器兜。

2.6 三法对比 #

做法 改动量 管住 Esc 管住红叉 适用场景
接受默认 0 行 是 是 确认框、工具窗、向导取消页
重写 reject() 10 行上下 是 是（closeEvent 也调它） 表单对话框、有数据要确认
重写 keyPressEvent() 8 行上下 是 否（红叉仍走默认 reject()） 只改 Esc，其他键行为要保留
事件过滤器 20 行上下 是 否 子控件把 Esc 吃掉了，或统一管多个窗口

选型一句话：QDialog 上优先重写 reject()，一个点管两条路；QWidget 上只能用 keyPressEvent()，抓到后自己 close()。

三、Tab 键与焦点链 #

Tab 是 Qt 里唯一被框架预留的按键。其他键老实走 keyPressEvent，只有 Tab 与 Shift+Tab 在进 keyPressEvent 之前就被焦点链截走。

3.1 焦点链是内建能力 #

QWidget::focusNextPrevChild(bool next) 负责这件事，next = true 找下一个焦点控件，false 找上一个。找到了就 setFocus() 返回 true，没找到返回 false。

默认查找顺序由子控件插入顺序决定，也就是对象树里的顺序，不是屏幕上的几何顺序。用 Designer 拖界面时，这个顺序就是对象浏览器里控件的排列。所以「视觉上从上到下」跟「Tab 从上到下」对不上，是常见现象。

3.2 keyPressEvent 里拿不到 Tab 的原因 #

QWidget::event() 的 KeyPress 分支，结构接近这段：

cpp
case QEvent::KeyPress: {
    QKeyEvent *k = static_cast<QKeyEvent *>(event);
    bool res = false;

    if (!(k->modifiers() & (Qt::ControlModifier | Qt::AltModifier))) {
        if (k->key() == Qt::Key_Backtab
            || (k->key() == Qt::Key_Tab && (k->modifiers() & Qt::ShiftModifier)))
            res = focusNextPrevChild(false);       // 反向
        else if (k->key() == Qt::Key_Tab)
            res = focusNextPrevChild(true);        // 正向

        if (res)
            break;                                 // 直接跳出，keyPressEvent 不执行
    }
    keyPressEvent(k);
    break;
}

看到 break 就明白了：只要焦点链成功切走，keyPressEvent 永远等不到 Tab。这不是 bug，是设计——Tab 属于焦点系统，不属于控件业务。

QTextEdit、QPlainTextEdit 这类要输入制表符的控件自己重写了 event()，绕开了这条规则。从它们里按 Tab 出来时往往要连按两次或加 Ctrl，原因就在这里。

3.3 接管 Tab 的两步 #

第一步，给控件焦点资格：setFocusPolicy(Qt::StrongFocus)。 没有这一步，控件连焦点都拿不到，event() 收到的按键是零。

第二步，重写 event()，在 QEvent::KeyPress 里拦 Qt::Key_Tab，返回 true 吃掉事件。

两个条件缺一不可。只写第二步，事件不来；只写第一步，Tab 还是被焦点链拿走。

cpp
class TabConsumer : public QWidget
{
    Q_OBJECT
public:
    explicit TabConsumer(QWidget *parent = nullptr) : QWidget(parent)
    {
        setFocusPolicy(Qt::StrongFocus);   // 第一步：先有焦点资格
    }
protected:
    bool event(QEvent *e) override
    {
        if (e->type() == QEvent::KeyPress) {
            QKeyEvent *k = static_cast<QKeyEvent *>(e);
            if (k->key() == Qt::Key_Tab) {         // 正向
                nextField();
                return true;                        // 吃掉，焦点链不再动
            }
            if (k->key() == Qt::Key_Backtab) {     // Shift+Tab，反向
                prevField();
                return true;
            }
        }
        return QWidget::event(e);                   // 其他事件交给基类
    }
private:
    void nextField();
    void prevField();
};

Shift+Tab 在 Qt 里的枚举值不是 Key_Tab 加个修饰位，是单独一个 Qt::Key_Backtab。按 Key_Tab 去判 Shift 组合，代码永远进不去分支。这是本节最容易踩的一脚。

3.4 更规整的一条路：focusNextPrevChild #

event() 里那段判断，最终调的就是虚函数 focusNextPrevChild(bool next)。重写它等于在分岔口换道：找到目标就 setFocus(Qt::TabFocusReason) 再 return true，基类不再切；Shift+Tab 自动变成 next = false，不用自己判 Key_Backtab。代价是它影响整个窗口的焦点链，只适合容器级别用。

四条路的层次摆在一起看：重写 keyPressEvent() 太靠后，Tab 已被截走，拿不到；重写 event() 能拿到，但要自己判 Key_Backtab；重写 focusNextPrevChild() 在分岔口换道，next 参数直接给出方向；事件过滤器最靠前，留给「要跨多个控件统一管」的场景。

四、自定义焦点顺序 #

默认顺序按插入顺序走，业务上经常要改。改法两条：静态排链，或者事件过滤器做条件跳转。

4.1 静态排链：setTabOrder #

QWidget::setTabOrder(first, second) 是静态函数，把 second 挪到 first 后面。它只改「这两个相邻」的关系，不用写全整条链，Qt 内部维护链表的 next 指针。

cpp
// 链式调用：realm -> user -> password -> checkBox -> loginButton
QWidget::setTabOrder(ui->realmLineEdit,    ui->userLineEdit);
QWidget::setTabOrder(ui->userLineEdit,     ui->passwordLineEdit);
QWidget::setTabOrder(ui->passwordLineEdit, ui->checkBox);
QWidget::setTabOrder(ui->checkBox,         ui->loginButton);

三条硬规矩：两个控件必须在同一窗口内，跨窗口调静默失败不打日志；调用时机在控件全部构造完之后，构造函数末尾或 showEvent 里都行，放在 ui->setupUi() 之前指针还是空；Shift+Tab 的逆向回跳由框架自动处理，不用再排反向链。

QTabWidget 的内页要每页单独排，页与页之间让 Tab 落在 tabBar() 上；QSplitter、QDockWidget 的顺序会被容器逻辑覆盖，得在容器 show 之后重排一次；控件动态增删会让链断在删除点，增删后重排受影响的相邻对；控件被 hide() 时自动跳过，不占链位。

4.2 条件跳转：事件过滤器 #

业务要求「账号没填不许走」，setTabOrder 做不到，它没有拦截点。这时用 installEventFilter() 把 Tab 的处置权收到父窗口手里。

cpp
void LoginDialog::initTabFilters()
{
    m_chain << ui->realmLineEdit << ui->userLineEdit << ui->passwordLineEdit
            << ui->checkBox << ui->loginButton << ui->closeButton;
    for (QWidget *w : m_chain)
        w->installEventFilter(this);
}

bool LoginDialog::eventFilter(QObject *obj, QEvent *event)
{
    QWidget *w = qobject_cast<QWidget *>(obj);
    if (!w || !m_chain.contains(w) || event->type() != QEvent::KeyPress)
        return QDialog::eventFilter(obj, event);

    QKeyEvent *ke = static_cast<QKeyEvent *>(event);
    const int count = m_chain.size();
    const int idx   = m_chain.indexOf(w);

    if (ke->key() == Qt::Key_Tab) {                 // 正向
        // 业务校验：账号为空不放行，焦点留在原控件
        if (w == ui->userLineEdit && ui->userLineEdit->text().isEmpty()) {
            ui->userLineEdit->setToolTip(QStringLiteral("账号不能为空"));
            return true;                            // 吃掉事件，焦点链不动
        }
        m_chain.at((idx + 1) % count)->setFocus(Qt::TabFocusReason);
        return true;
    }

    if (ke->key() == Qt::Key_Backtab) {             // 反向
        m_chain.at((idx - 1 + count) % count)->setFocus(Qt::BacktabFocusReason);
        return true;
    }

    return QDialog::eventFilter(obj, event);        // 其余原样放行
}

两个细节值得单说。

过滤器装在被监控的控件上，函数写在窗口里。事件先到过滤器，再到控件自己的 event()，所以过滤器有机会抢在焦点链之前处理 Tab。这是它能盖住框架默认行为的唯一原因。

return true 与 return QDialog::eventFilter(...) 的分界要划清。返回 true 表示「处理完了」，控件和框架都收不到；返回基类调用结果表示「我没管」，事件继续流转。全 return true 的写法会让 Enter 激活默认按钮、输入法上屏这类行为一起失灵。

setFocus() 带上 Qt::TabFocusReason，样式表的 :focus 状态与无障碍朗读都会正确响应。图省事用无参版本，行为一样但丢失焦点原因，某些自绘控件会画错状态。

4.3 两条路怎么选 #

维度 setTabOrder 事件过滤器
代码量 一行一对 二十行起步
能加业务校验 不能 能
能跳过只读控件 不能 能
能循环回跳 不能（到末位离开窗口） 能，取模实现
出错概率 低 中，容易漏 return
适用 常规表单 强校验表单、锁屏、证书登录

常规表单直接用 setTabOrder，别为了「灵活」上过滤器，多出来的二十行只会带来新 bug。只有「切换前必须满足某条件」时才值得上过滤器。

五、焦点策略 setFocusPolicy #

setFocusPolicy() 决定控件「怎么拿到焦点」，不决定能不能处理键盘——拿到焦点，keyPressEvent 就会来；拿不到，写再多分支都是死代码。

5.1 五种策略 #

策略 获得焦点的方式 典型默认使用者
Qt::NoFocus 拿不到，setFocus() 也无效 QLabel、QProgressBar、裸 QWidget
Qt::TabFocus 只能用 Tab 切进来 少数只做展示的输入项
Qt::ClickFocus 只能鼠标点击进来 图形视图里的自绘项
Qt::StrongFocus Tab 与鼠标点击都可以 QLineEdit、QPushButton、QCheckBox
Qt::WheelFocus 在 StrongFocus 上加滚轮进入 滚动区域里的控件

Qt::WheelFocus 慎用。滚轮能把焦点卷进来，用户在长表单里滚页面时焦点乱跳，接着滚轮就变成改数值。默认都别选它。

5.2 让控件真正开始收键盘 #

构造函数里三行就够：setFocusPolicy(Qt::StrongFocus) 给资格，setFocus(Qt::OtherFocusReason) 主动拿一次不等用户点，setAttribute(Qt::WA_KeyCompression, false) 别压缩按键事件。WA_KeyCompression 默认是关的，打开以后长按期间的事件被合并，连发逻辑的按键数会少。

5.3 拿不到焦点的五种情形 #

hasFocus()、setFocus(reason)、clearFocus()、setFocusProxy()、focusInEvent()/focusOutEvent() 这几个接口够用。调试时连 QApplication::focusChanged，类名和地址一起打，焦点跑哪去了当场可见。

排查「按键没反应」按这个表过一遍，命中率极高。

情形 判断 解法
策略是 NoFocus focusPolicy() == Qt::NoFocus 改 StrongFocus
控件被禁用 isEnabled() == false setEnabled(true)
控件被隐藏 isVisible() == false 先 show()，隐藏控件拿不到焦点
焦点被别人抢 focusWidget() 指向别的控件 查多余的 setFocus()
在不接受焦点的容器里 父链某一级是 NoFocus 且没开代理 给容器开策略或设 focusProxy

最后一条最隐蔽：QScrollArea 的视口、QGraphicsView 的场景项，焦点都停在容器上，而不是你想的那个控件。

六、截屏：屏幕与窗口 #

Qt 5 把截图接口从 QPixmap::grabWindow 挪到了 QScreen 上，旧接口已废弃。新接口只有几个参数形态，差别在「抓多大范围」。

6.1 两种范围 #

调用 抓取范围 典型用途 平台限制
screen->grabWindow(0) 整个屏幕的全部像素 全屏截图、录制帧 Wayland 下返回空或全黑
screen->grabWindow(winId) 指定的那个窗口 窗口镜像、后台预览 Windows 与 X11 可靠，Wayland 不行
screen->grabWindow(winId, x, y, w, h) 窗口内的矩形 局部截图、区域选择 同上，坐标是窗口内逻辑坐标

winId 是 WId 类型，取自 QWidget::winId()。传 0 表示桌面根窗口，也就是全屏。

6.2 全屏截图的标准封装 #

cpp
#include <QGuiApplication>
#include <QScreen>
#include <QPixmap>
#include <QDateTime>

QPixmap captureScreen(QScreen *screen = nullptr)
{
    if (!screen) screen = QGuiApplication::primaryScreen();
    if (!screen) return QPixmap();
    return screen->grabWindow(0);        // 0 = 整屏
}

void saveScreenshot()
{
    QPixmap pixmap = captureScreen();
    if (pixmap.isNull()) {
        qWarning() << "grab failed";
        return;
    }
    QString name = QDateTime::currentDateTime()
                       .toString(QStringLiteral("yyyyMMdd_HHmmss"))
                   + QStringLiteral(".png");
    pixmap.save(name);
}

多屏要抓全部，得自己拼：取 QGuiApplication::screens()，按每块屏 geometry() 的偏移贴到大画布上。偏移量按物理像素算，缩放比例不同的两块屏混用逻辑坐标会错位。

6.3 高 DPI：devicePixelRatio 别忽略 #

这是截图最容易出问题的地方，分两种情况。

保存到磁盘时，QPixmap::save() 只写像素，不看 devicePixelRatio。200% 缩放的屏、逻辑分辨率 1920×1080，grabWindow(0) 给的是 3840×2160 物理像素，存下来清晰度没问题。

把图显示回界面时才出问题。抓到的 QPixmap 自带 devicePixelRatio() == 2.0，塞进 QLabel 会按物理像素铺开，控件装不下就被压缩，看着糊。正确做法是分两份：

cpp
QPixmap shot = screen->grabWindow(0);

ui->previewLabel->setPixmap(shot);   // 显示：保留原 dpr，像素不丢

QPixmap forSave = shot;              // 落盘：dpr 归 1，避免再被缩放
forSave.setDevicePixelRatio(1.0);
forSave.save(QStringLiteral("shot.png"));

反过来，手工造画布再 QPainter 往上画，不设 dpr 就是一张逻辑尺寸的图，缩放到高分屏上一定糊——QPixmap canvas(size * dpr) 之后紧跟一句 canvas.setDevicePixelRatio(dpr)，这行不能省。 判断规则很简单：抓来的图不碰 dpr，手工造的图必须设 dpr。 搞反了就是「截图糊了」和「截图多了一倍空白」。

6.4 指定窗口的截图 #

cpp
QPixmap captureWidgetWindow(QWidget *w)
{
    if (!w) return QPixmap();

    // 必须取顶层窗口 ID，用控件自己的 winId 只会抓到那一小块
    WId id = w->window()->winId();
    QScreen *screen = w->window()->screen();
    if (!screen) screen = QGuiApplication::primaryScreen();

    return screen->grabWindow(id);
}

窗口被别的窗口遮住时，Windows 上抓到的是被遮住之后的画面。要抓完整内容，让它切到前台，或者走 PrintWindow 那套 GDI 调用。

6.5 Wayland 与 macOS：抓不到不是代码的问题 #

现代合成器出于安全设计，禁止应用读取别的窗口像素。grabWindow() 在 Wayland 下返回黑色或全透明图像，在 macOS 10.15 以上会触发录屏授权弹窗，没授权时只剩桌面壁纸。

X11 与 Windows 属于老架构，应用能直接读帧缓冲，grabWindow() 底层就是 XGetImage 或 GDI 的 BitBlt，一路畅通。

Wayland 下的正路是 XDG Desktop Portal 的 DBus 接口，Flameshot、Spectacle 都这么干：

cpp
QDBusInterface portal(QStringLiteral("org.freedesktop.portal.Desktop"),
                      QStringLiteral("/org/freedesktop/portal/desktop"),
                      QStringLiteral("org.freedesktop.portal.Screenshot"),
                      QDBusConnection::sessionBus());
if (!portal.isValid()) { qWarning() << "portal not available"; return; }

QVariantMap options;
options.insert(QStringLiteral("handle_token"),
               QStringLiteral("token_")
                   + QString::number(QDateTime::currentMSecsSinceEpoch()));
options.insert(QStringLiteral("interactive"), true);

portal.call(QStringLiteral("Screenshot"), QString(), options);   // 父窗口为空

这条路是异步的：调用返回 handle，真正的图通过 Response 信号带回一个 URI，再读那个文件。同步等待会卡住界面，必须用信号接。

macOS 的权限没有 Info.plist 键能自定义提示文案，权限由系统统一管。首次弹一次，用户拒了以后要去「系统设置 → 隐私与安全 → 屏幕录制」手动勾。

6.6 四个绕不开的局限 #

局限 表现 处理
不含鼠标光标 图里没有箭头 取 QCursor::pos()，用 QPainter 把光标图标画上去
OpenGL 内容发黑 3D 视口抓到旧帧或纯黑 改用 QOpenGLWidget::grabFramebuffer()
视频层发黑 硬件解码的播放器抓空 关硬件加速，或用播放器自己的截图接口
多屏拼图错位 偏移算错 按物理像素算偏移量

光标叠加要注意 dpr：在带 dpr 的 pixmap 上作画，坐标得乘 dpr，否则画到一半的位置。

6.7 方案对比 #

方案 适用架构 优点 缺点 核心接口
Qt 原生 X11、Windows、部分 macOS 代码极少，无额外依赖 Wayland 不可用，macOS 要授权 QScreen::grabWindow
直接调 X11 仅 X11 快，能穿透部分覆盖层 无法移植，内存管理复杂，已过时 XGetImage / XShm
DBus Portal Wayland、Flatpak Wayland 下的标准解，沙箱兼容 异步，依赖外部服务，每次弹窗确认 org.freedesktop.portal
开源库移植 跨平台 差异已被抹平 引入 KDE 依赖，或自抽核心代码 Flameshot / Spectacle

落地分三层：先试 grabWindow(0)；返回空或 XDG_SESSION_TYPE=wayland 时降级到 DBus Portal；要做标注这类复杂功能，去读 Flameshot 的 CaptureTool 与 SelectionWidget，抄逻辑，别从零写选区。

七、摄像头调用 #

Qt 5 的多媒体模块把摄像头拆成三个类，各管一段，缺一个都跑不起来。

7.3 构造流程 #

八步，顺序不能乱。setViewfinder() 必须在 start() 之前，setCaptureMode() 必须在 capture() 之前。

cpp
CameraDialog::CameraDialog(QWidget *parent) : QDialog(parent)
{
    resize(700, 450);
    setWindowTitle(QStringLiteral("摄像头采集测试"));
    initUI();

    m_camera     = new QCamera(this);                          // 1. 设备，默认主摄像头
    m_viewFinder = new QCameraViewfinder(this);                // 2. 取景器
    m_camera->setViewfinder(m_viewFinder);                     //    绑到设备上
    m_imageCapture = new QCameraImageCapture(m_camera, this);  // 3. 抓拍器，父对象是设备
    m_camera->setCaptureMode(QCamera::CaptureStillImage);      // 4. 静态照片模式
    m_imageCapture->setCaptureDestination(                     // 5. 输出目的地
        QCameraImageCapture::CaptureToFile);

    connect(m_captureButton, &QPushButton::clicked,
            this, &CameraDialog::slotCaptureImage);            // 6. 信号槽
    connect(m_saveButton, &QPushButton::clicked,
            this, &CameraDialog::slotSaveImage);
    connect(m_exitButton, &QPushButton::clicked, this, &CameraDialog::close);
    connect(m_imageCapture, &QCameraImageCapture::imageCaptured,
            this, &CameraDialog::slotDisplayImage);

    auto *right = new QVBoxLayout;                             // 7. 布局
    right->addWidget(m_previewLabel);
    right->addStretch();
    right->addWidget(m_captureButton);
    right->addWidget(m_saveButton);
    right->addWidget(m_exitButton);

    auto *main = new QHBoxLayout(this);
    main->addWidget(m_viewFinder, 1);                          // 取景器占大头
    main->addLayout(right);

    m_camera->start();                                         // 8. 起流
}

CameraDialog::~CameraDialog()
{
    m_camera->stop();     // 不停流，设备句柄不释放，下次进界面黑屏
}

    m_previewLabel = new QLabel(this);
    m_previewLabel->setFixedSize(160, 120);

7.4 状态机与错误处理 #

QCamera 是个状态机，capture() 在非活动状态下调用无效，什么都不发生，也不报错。

状态 含义 能做的事
UnloadedState 未加载，设备没打开 只能配参数
LoadingState 正在打开 等待
LoadedState 已打开，未起流 可以 start()
ActiveState 正在采集 可以 capture()
UnavailableState 没有可用设备或被占用 提示用户 
cpp
connect(m_camera, &QCamera::stateChanged, this, [this](QCamera::State s) {
    m_captureButton->setEnabled(s == QCamera::ActiveState);
    if (s == QCamera::UnavailableState)
        qWarning() << "camera unavailable";
});

connect(m_imageCapture, &QCameraImageCapture::error, this,
        [this](int id, QCameraImageCapture::Error err, const QString &msg) {
    qWarning() << "capture error" << id << err << msg;
    QMessageBox::warning(this, QStringLiteral("抓拍失败"), msg);
});

设备枚举不靠猜：QCameraInfo::availableCameras() 返回设备列表，deviceName() 与 description() 逐个打印，指定设备就 new QCamera(QCameraInfo::defaultCamera(), this)。

Windows 上还有系统层前置条件：系统设置里把「相机」开关关掉，QCamera 直接进 UnavailableState，代码全对也出不了画面。这类问题只能靠状态机日志定位。

八、图像采集与保存 #

抓拍器的输出目的地决定拿到的数据形态，也决定保存逻辑写在哪。

8.1 两种目的地 #

目的地 行为 何时用
CaptureToFile 直接写文件，名字由抓拍器生成 只存不预览
CaptureToBuffer 只留内存，不落盘 要预处理、要自己命名
两者按位或 既存又留内存 预览与存盘都要 
cpp
m_imageCapture->setCaptureDestination(
    QCameraImageCapture::CaptureToFile | QCameraImageCapture::CaptureToBuffer);

按位或这个写法很多人不知道。参数是 QFlags，两个值能叠加。

8.2 两个信号的分工 #

信号 参数 触发时机 典型用途
imageCaptured int id, const QImage & 抓拍完成，图在内存 界面预览、图像处理
imageSaved int id, const QString & 文件已写完 记录路径、写数据库
imageAvailable int id, QVideoFrame 缓冲区模式下的原始帧 逐帧处理

只走 CaptureToFile 时 imageCaptured 依然会发，图已在内存，能直接显示。两个信号都接上，预览与路径记录互不干扰。

8.3 预览与落盘 #

cpp
void CameraDialog::slotCaptureImage()
{
    m_imageCapture->capture();          // 触发单帧
}

void CameraDialog::slotDisplayImage(int id, const QImage &image)
{
    Q_UNUSED(id);
    m_lastImage = image;                                  // 原始帧留底
    m_previewLabel->setPixmap(QPixmap::fromImage(image));
}

void CameraDialog::slotSaveImage()
{
    const QPixmap *pixmap = m_previewLabel->pixmap();
    if (!pixmap || pixmap->isNull()) {
        QMessageBox::warning(this, QStringLiteral("警告"),
                             QStringLiteral("预览区无图片，请先拍照！"));
        return;
    }

    QString path = QFileDialog::getSaveFileName(
        this, QStringLiteral("保存图片"), QDir::currentPath(),
        QStringLiteral("Images (*.jpg *.png *.bmp)"));
    if (path.isEmpty())
        return;                                   // 用户取消

    if (pixmap->save(path))
        QMessageBox::information(this, QStringLiteral("成功"),
                                 QStringLiteral("图片保存成功！"));
    else
        QMessageBox::critical(this, QStringLiteral("错误"),
                              QStringLiteral("图片保存失败，请检查写入权限。"));
}

QPixmap::save() 的格式由扩展名决定，扩展名不合法返回 false。用户在对话框里手打一个 .tiff，save 失败，那条 critical 弹窗就是给这种情况兜底的。

slotSaveImage 取的是预览里的 QPixmap，也就是屏幕上那份。要存原始分辨率，得把 imageCaptured 里的 QImage 存成成员变量——QImage 存原始像素，QPixmap 是显示优化形态。要处理、要存盘一律用 QImage，只在屏幕上画才转 QPixmap。

8.4 自己做文件命名 #

按业务规则命名就把目的地设成 CaptureToBuffer，在 imageAvailable 里接帧自己存：frame.image() 取到 QImage，判空后 img.save() 按序号拼名字。

三个坑摆在这里。QVideoFrame::image() 的格式依赖后端，多数是 Format_RGB32，个别平台给 Format_YUV420P，用 imageFormatFromPixelFormat() 判一下再处理。id 是抓拍序号，从 1 开始，每次 capture() 自增，多摄像头时两个设备的序号各自独立，拼文件名要带设备标识，否则互相覆盖。存盘在 GUI 线程做，单张没事，连续抓拍会掉帧，高频保存要开工作线程把 QImage 拷贝进去排队写。

九、日志输出窗口的实现 #

qDebug() 默认打到控制台，发布版没有控制台，日志就消失了。qInstallMessageHandler() 能把日志分流到任意地方：文件、网络、或者一个窗口。调试期窗口方案最合适——不占文件、实时可见、一键清屏。

9.1 三个要点 #

要点 说明
handler 必须是自由函数 接口收函数指针，成员函数塞不进去，要写全局函数转一手
窗口指针要防野指针 全局 QPointer<LogBrowser>，窗口销毁后自动置 nullptr
控件不是线程安全的 handler 在任意线程被调用，跨线程写控件要转到 GUI 线程

9.2 窗口类 #

9.3 日志落进窗口 #

QtMsgType 四档，逐档加前缀。append() 自带换行与自动滚底，别用 insertPlainText() 自己拼。

cpp
void LogBrowser::outputMessage(QtMsgType type, const QMessageLogContext &context,
                               const QString &msg)
{
    Q_UNUSED(context);
    QString prefix;

    switch (type) {
    case QtDebugMsg:    prefix = QStringLiteral("Debug:");    break;
    case QtWarningMsg:  prefix = QStringLiteral("Warning:");  break;
    case QtCriticalMsg: prefix = QStringLiteral("Critical:"); break;
    case QtFatalMsg:    prefix = QStringLiteral("Fatal:");    break;
    }
    browser->append(prefix + msg);
}

压测按钮，一口气打一百万条，看窗口扛不扛得住：

cpp
void LogBrowser::start()
{
    if (is_finished) return;

    for (int i = 0; i < 1000000; ++i) {
        QCoreApplication::processEvents();       // 让重绘有机会插队
        qDebug() << QStringLiteral("This is a Qt log browser ")
                        + QString::number(i, 10);
    }
    is_finished = true;
}

processEvents() 在这里不是装饰。没有它，事件循环被 for 循环占死，append() 只往文档里写、界面一次不刷，窗口表现为「假死然后瞬间刷完」。加进去以后才是逐条滚动，能直观看到性能边界在哪。

关窗要问一句，避免手滑销毁现场：

cpp
void LogBrowser::closeEvent(QCloseEvent *event)
{
    QMessageBox::StandardButton answer = QMessageBox::question(
        this, QStringLiteral("Close Log Browser?"),
        QStringLiteral("Do you really want to close the log browser?"),
        QMessageBox::Yes | QMessageBox::No);

    if (answer == QMessageBox::Yes) event->accept();
    else                            event->ignore();
}

void LogBrowser::keyPressEvent(QKeyEvent *event)
{
    event->ignore();        // 一个键都不消费，全部上交
}

closeEvent 里必须二选一 accept 或 ignore。两样都不写，窗口关不掉，用户只能杀进程。

9.4 装配到 main #

cpp
#include <QApplication>
#include <QPointer>
#include "log_browser.h"

QPointer<LogBrowser> log_browser;    // 全局弱引用，窗口析构即置空

void outputMessage(QtMsgType type, const QMessageLogContext &context,
                   const QString &msg)
{
    if (log_browser)                 // 判空，别省这一步
        log_browser->outputMessage(type, context, msg);
}

int main(int argc, char *argv[])
{
    QApplication a(argc, argv);

    log_browser = new LogBrowser;
    log_browser->show();

    qInstallMessageHandler(outputMessage);   // 装完这行，qDebug 才有去处
    return a.exec();
}

顺序不能反：先有窗口，再装 handler。装早了 log_browser 还是空指针，那段时间的日志静默丢掉。

多线程场景要转一次线程：qRegisterMetaType<QtMsgType>("QtMsgType") 之后，用 QMetaObject::invokeMethod(log_browser, "outputMessage", Qt::QueuedConnection, ...) 把三参数打包过去。前提是 outputMessage 声明成 slots 或 Q_INVOKABLE。工作线程直接 browser->append() 属于未定义行为，崩不崩看运气。

十、日志滚动与自动清理 #

QTextBrowser 的内容只增不减。压测跑完一百万条，内存与排版耗时跟着涨，滚到后面卡成幻灯片。上限必须设。

10.1 块数上限 #

cpp
browser->document()->setMaximumBlockCount(5000);

一行搞定。超过上限时最早的块自动删除，滚动条位置不跳，等于「只留最近 5000 行」。QPlainTextEdit 与 QTextBrowser 都支持这个接口。

10.2 手动裁剪与滚动 #

要按业务规则切（保留某段时间、保留含关键字的行），用 QTextCursor 从 Start 往下选中前若干块再 removeSelectedText()，块数由 doc->blockCount() 减去保留行数算出。

append() 自带滚底；用游标插文字就不带，要补 moveCursor(QTextCursor::End) 加 ensureCursorVisible()。用户往上翻历史时自动滚底会把人拽回底部，先判 verticalScrollBar()->value() == maximum() 再决定。

10.3 清理节奏 #

位置 手段 触发时机
控件内 setMaximumBlockCount 每次 append() 自动发生
控件内 游标裁剪 定时器或行数到阈值
文件侧 查 QFileInfo::size()，超限改名轮转 启动时或每日
文件侧 按日期建文件，旧的压缩归档 定时任务

日志窗口只负责「看最近的」，历史归文件。把两者混在一个窗口里，早晚会因为一次手滑的循环 qDebug 把界面卡住。

十一、调用系统对话框 #

Qt 没有对外接口能弹 Windows「属性」窗。那个带「常规」「安全」「详细信息」页签的原生窗体，要靠 ShellExecuteEx 的动词参数调出来。

11.1 ShellExecuteEx 弹原生属性窗 #

cpp
#include <windows.h>
#include <shellapi.h>

void showWindowsPropertiesDialog(const QString &filePath)
{
    std::wstring wPath = filePath.toStdWString();   // QString -> LPCWSTR

    SHELLEXECUTEINFO info;
    ZeroMemory(&info, sizeof(info));

    info.cbSize       = sizeof(SHELLEXECUTEINFO);
    info.fMask        = SEE_MASK_INVOKEIDLIST;   // 走 IDList，非文件路径目标也能用
    info.lpVerb       = L"properties";           // 动词：弹属性窗体
    info.lpFile       = wPath.c_str();
    info.lpParameters = L"";
    info.lpDirectory  = NULL;
    info.nShow        = SW_SHOW;
    info.hInstApp     = NULL;

    ShellExecuteEx(&info);
}

// 用法
showWindowsPropertiesDialog(QStringLiteral("C:\\Windows\\regedit.exe"));

lpVerb 是全部要点。"properties" 弹属性，"open" 打开文件，"edit" 打开编辑器，"runas" 走 UAC 提权。同一个函数，动词换一个，行为完全不同。

fMask 里的 SEE_MASK_INVOKEIDLIST 决定这条路走 IDList，不是纯路径字符串。控制面板项、虚拟文件夹这类没有真实路径的目标，靠它才能弹出来。

11.2 链接 shell32 #

text
win32: LIBS += -lshell32

CMake 写 target_link_libraries(${PROJECT_NAME} PRIVATE shell32)。漏了这步的典型现象是编译通过、链接报 LNK2019，提示 ShellExecuteExW 未解析。

11.3 跨平台的替代写法 #

非 Windows 平台，或者要完全自定义展示内容，就读 QFileInfo 自己画：

cpp
QString fileDetails(const QString &path)
{
    QFileInfo info(path);
    QString d;
    d += QStringLiteral("文件名：%1\n").arg(info.fileName());
    d += QStringLiteral("类型：%1文件\n").arg(info.suffix().toUpper());
    d += QStringLiteral("位置：%1\n").arg(info.absolutePath());
    d += QStringLiteral("大小：%1 字节\n").arg(info.size());
    d += QStringLiteral("创建时间：%1\n")
             .arg(info.birthTime().toString(QStringLiteral("yyyy-MM-dd hh:mm:ss")));
    d += QStringLiteral("最后修改：%1\n")
             .arg(info.lastModified().toString(QStringLiteral("yyyy-MM-dd hh:mm:ss")));
    d += QStringLiteral("只读：%1")
             .arg(info.isWritable() ? QStringLiteral("否") : QStringLiteral("是"));
    return d;
}

QMessageBox::information(nullptr, QStringLiteral("文件属性"), fileDetails(path));
方式 平台支持 自定义度 实现复杂度
ShellExecuteEx("properties") Windows 专属 无，原生系统窗体 极低
QFileInfo + 自定义 QDialog 跨平台 完全自由 中等

QFileInfo::birthTime() 在部分 Linux 文件系统上返回无效时间，isValid() 判一下再显示，别直接扔个 1970 年给用户。

Qt 自己那几个对话框默认也走系统原生实现：QFileDialog、QColorDialog、QFontDialog、QMessageBox。想让它们和自绘界面一致，用 QFileDialog::DontUseNativeDialog 或全局 QApplication::setAttribute(Qt::AA_DontUseNativeDialogs) 关掉原生实现。

十二、易错点速查 #

按现象查原因，都是本篇出现过的坑。

现象 原因 解法
按键完全没反应 焦点策略是 NoFocus setFocusPolicy(Qt::StrongFocus)
加了策略仍没反应 控件被禁用或隐藏 查 isEnabled()、isVisible()
时好时坏 焦点被别的控件抢走 QApplication::focusWidget() 定位
Esc 绕过 closeEvent 的确认 Esc 走 reject()，不碰 close() 重写 reject()
keyPressEvent 收不到 Tab 在 QWidget::event() 被焦点链截走 重写 event() 或 focusNextPrevChild()
Shift+Tab 分支进不去 枚举值是 Qt::Key_Backtab 判 Key_Backtab
只处理 Esc，Enter 失灵 default 分支没交还基类 末尾调基类 keyPressEvent
Tab 顺序与视觉顺序不一致 默认按创建顺序排 setTabOrder() 重排
截图全黑 Wayland 或 macOS 未授权 走 DBus Portal，或去系统设置授权
截图糊 显示时 dpr 被抹掉 显示保留 dpr，落盘副本归 1
截窗口只抓到一小块 用了子控件 winId() 改 window()->winId()
capture() 毫无反应 摄像头不在 ActiveState 接 stateChanged()，活动态再使能按钮
第二次打开摄像头黑屏 析构里没 stop() ~CameraDialog() 里停流
日志窗口越用越卡 没设块数上限 setMaximumBlockCount()
日志 handler 偶尔崩溃 工作线程直接写控件 队列连接转到 GUI 线程
属性窗弹不出来 没链 shell32 win32: LIBS += -lshell32

排查顺序固定下来，比记住结论更值钱。

第一层看焦点。hasFocus()、focusPolicy()、QApplication::focusWidget()，三个调用排掉一半案例。

第二层看事件到没到。在 event() 与 keyPressEvent() 各打一行日志，哪行没打印，指针就停在哪一层。Tab 类问题一定停在第 4 步那个 break 上。

第三层看平台。截图、摄像头、原生对话框这三样，代码正确也会因为合成器协议、系统权限、链接库缺失而失效，日志里带上平台与状态机取值。

第四层看资源。设备没停、文件没关、日志没上限，这些问题不在第一次运行时暴露，在第三次、第三天暴露。

把顺序养成习惯，「Qt 的按键、截图、摄像头不好使」这类问题基本都能在十分钟内定位到具体那一行。
