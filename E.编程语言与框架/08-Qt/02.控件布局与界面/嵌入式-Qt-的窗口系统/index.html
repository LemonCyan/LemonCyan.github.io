开篇边界 这篇只讲一件事：嵌入式板上没有 X11、没有窗口管理器，Qt 的界面靠什么画到屏幕上，靠哪些环境变量把程序指到对的显示后端上。 讲的：Qt5 的 QPA、linuxfb 与 eglfs 两个主力后端、Qt4 的 QWS、输入设备（evdev / libinput / tslib）、多屏与虚拟桌面、旋转与分辨率、字体回退、故障现象。素材里那一大堆 QT_QPA_* 变量全部保留，一条不删。 不讲的：控件怎么写、布局怎么排、QML 语法。那些在本目录其他篇里。交叉编译工具链的搭建也不展开，只在 configure 那一段点到。 前提：下文所有环境变量都在启动程序的那个 shell 里 export，或者写进 systemd 单元的 Environment=。写进 ~/.bashrc 只对交互式登录生效，服务起不来的时候先查这一点。

一、嵌入式为什么没有标准窗口系统 #

桌面 Linux 上，一个像素从 Qt 走到屏幕要过四道手：内核的 DRM/KMS 驱动、X11 或 Wayland 显示服务器、窗口管理器、最后才是应用。每一道都在做同一件事——仲裁谁有资格画、画在哪儿。

嵌入式把中间两道砍掉了。理由很朴素：板子上就一块屏、一个程序，砍掉两层等于省内存、省启动时间、省一整条进程间通信链路。代价是原本由那两层承担的活儿，现在得有人干。

层 桌面 Linux 典型嵌入式
内核显示驱动 DRM/KMS fbdev（/dev/fb0）或 DRM/KMS
显示服务器 X11 / Wayland 没有，或被 QPA 插件顶替
窗口管理器 Mutter / KWin / i3 没有
合成器 有，负责混合各窗口 QPA 插件代做
应用窗口数 多进程多窗口 一个进程，一个全屏窗口

于是有四条后果，后面每一章都在还这笔账：

  1. 从头到尾只有一个原生窗口。谁先创建顶级窗口，谁就是这个窗口的主人，剩下的都往它里面画。
  2. 坐标系就是整块屏。(0,0) 是屏幕左上角，不是某个窗口的左上角。
  3. 没有 Z 序仲裁。多窗口要么程序自己管，要么就别多窗口。
  4. 输入设备得自己读。没有 X server 帮你把 /dev/input/event* 的原始事件翻译成「点到某个窗口的某个控件」。

Qt4 与 Qt5 的分界线 #

Qt 5.0 是一个硬分界。从这一版起，Qt 不再包含自己的窗口系统实现（QWS）。

  • 单进程的界面，用平台抽象插件（QPA）直接对着内核显示设备画。这是嵌入式的主流路径。
  • 多进程、要多窗口合成，用 Wayland。Wayland 的合成器承担了原来窗口系统的角色。

所以你在旧文档里看到的 -qws 参数，在 Qt5 上一个都不存在。看到 QWSDisplay、QWSServer 这种类名，那是 Qt4 的代码，得改。

可选的平台插件 #

嵌入式 Linux 上可用的插件有四个，用不用得上取决于 Qt 编译时开了什么：

插件 后端依赖 谁在用
eglfs EGL + OpenGL ES 2.0 + GPU 驱动 带 GPU 的开发板，多数厂商镜像的默认值
linuxfb /dev/fbN 或 DRM dumb buffer 无 GPU 的工控板、点屏设备
directfb DirectFB 库 老设备，现在很少见
wayland 一个 Wayland 合成器 需要多进程各自出窗口的场合

默认值不合用的时候，两条路改：环境变量 QT_QPA_PLATFORM，或者命令行 -platform。两者语法一样。

bash
# 命令行方式，适合临时试
./myapp -platform linuxfb

# 环境变量方式，适合写进启动脚本
export QT_QPA_PLATFORM=eglfs
./myapp

bash
# 带参数，冒号分隔
export QT_QPA_PLATFORM=linuxfb:fb=/dev/fb1:size=1024x600
./myapp

带参数的语法是 插件名:键=值:键=值。每个插件认哪些键，取决于它的实现，第四章和第五章逐个列。

二、QPA：Qt 平台抽象层 #

QPA 是 Qt Platform Abstraction。它把「跟具体显示环境打交道」的那部分从 Qt 核心代码里切出来，做成一组接口：QPlatformIntegration、QPlatformScreen、QPlatformWindow、QPlatformBackingStore、QPlatformInputContext 等。每套实现编译成一个平台插件（.so），扔在 plugins/platforms/ 下，运行时按名字加载。

QPA 抽象掉的是平台差异，不是窗口系统。 这句话要记牢。它让你同一份程序、同一个二进制，通过 -platform linuxfb 或 QT_QPA_PLATFORM=eglfs 就能在完全不同的显示环境上跑——一个没有 GPU 只认 framebuffer 的板子，和一个有 Mali GPU 走 DRM 的板子，源码一行不改。

加载顺序 #

Qt 决定用哪个插件，按这个优先级：

  1. 命令行 -platform <名字>，优先级最高。
  2. 环境变量 QT_QPA_PLATFORM。
  3. 编译进 Qt 的默认值，也就是 configure 时的 -qpa 参数，或者设备 mkspec 里写死的那个。
  4. 都没有的时候，按内建列表挨个尝试，全失败就报错退出。

第 3 条是很多板子的实际来源。厂商给你一个预编译的 Qt，-platform 不写它也能起来，就是因为默认值在编译时定了。

插件装上没有 #

程序报 This application failed to start because no Qt platform plugin could be initialized，九成是这一步。

bash
# 看看你的 Qt 到底带了哪些平台插件
ls $QT_PLUGIN_PATH/platforms/
# 典型输出：libqeglfs.so libqlinuxfb.so libqminimal.so libqoffscreen.so libqvnc.so

QT_PLUGIN_PATH 没设的时候，Qt 按自身安装前缀去找 plugins/platforms。交叉编译部署到板子上时，这个目录经常漏拷。查一下环境：

bash
export QT_DEBUG_PLUGINS=1
./myapp

这个变量会把插件扫描过程一条条打出来：找了哪些目录、哪个被拒绝、拒绝原因是什么。排这类问题别猜，直接开它。

configure 输出里的 QPA 段 #

Qt 编译完之后，configure 的输出里有一段 QPA backends:，能用的插件后面写 yes，不能用的写 no。树莓派上用了 Broadcom 专有驱动的构建，应该看到这样的结果：

text
QPA backends:
  EGLFS .................................. yes
  EGLFS details:
    EGLFS i.Mx6 .......................... no
    EGLFS i.Mx6 Wayland .................. no
    EGLFS EGLDevice ...................... no
    EGLFS GBM ............................ no
    EGLFS mali ........................... no
    EGLFS Rasberry Pi .................... yes
  EGL on X11 ............................. no
  LinuxFB ................................ yes
  DirectFB ............................... no

这里要是没有 EGLFS Rasberry Pi ... yes，构建就没必要继续了——缺了板级后端，加速图形不会工作，哪怕 Qt 其余部分编得再干净。

no 的来源往往是两个：libudev 或 libinput 的开发文件没在 sysroot 里。这类问题会直接体现在 configure 输出上，别等到运行时才发现。要看清每个配置测试到底调了什么编译命令、链接了什么，加 -v：

bash
./configure -release -opengl es2 -device linux-rasp-pi2-g++ \
    -device-option CROSS_COMPILE=$TOOLCHAIN/bin/arm-linux-gnueabihf- \
    -sysroot $ROOTFS -prefix /usr/local/qt5 -v

报「缺头文件」「缺库」「链接器莫名失败」的时候，先怀疑 sysroot 不完整或者被污染了。这类错误跟 Qt 无关，Qt 也修不了，得回头收拾 rootfs 或者工具链。

设备 mkspec 与 sysroot #

给一块具体的板子编译 Qt，需要两样东西：一个工具链，一个 sysroot。带 GPU 的设备还要厂商特定的 EGL / OpenGL ES 2.0 适配代码。不带加速的平台（比如只用 LinuxFB 的板子）不需要这些，纯软件渲染。

qtbase/mkspecs/devices 下放着一堆设备的配置。比如 linux-rasp-pi2-g++ 里既有树莓派 2 该用的编译器和链接器 flag，也有 eglfs 钩子的实现信息，或者一条指向合适 eglfs 设备集成插件的引用。选设备用 -device 参数，后面的名字至少要部分匹配 devices 下的某个子目录。

最要紧的两个参数是 -device 和 -sysroot：

bash
./configure -release -opengl es2 -device linux-rasp-pi2-g++ \
    -device-option CROSS_COMPILE=$TOOLCHAIN/arm-bcm2708/gcc-linaro-arm-linux-gnueabihf-raspbian/bin/arm-linux-gnueabihf- \
    -sysroot $ROOTFS -prefix /usr/local/qt5

-sysroot 指定之后，configure 做特性检测时读的头文件和库、以及编译 Qt 本身，都从指定位置取，不看主机 PC 的标准路径。这一条很关键：想在主机上装个开发包混过去是没用的。要 libinput 支持，只把 libinput 的头文件和库装在主机上不算数，目标架构（比如 ARM）的头和库得出现在 sysroot 里。

交叉编译时 pkg-config 也被支持。configure 会自动把 PKG_CONFIG_LIBDIR 指到 sysroot，让 pkg-config 报告目标的编译和链接参数，多数情况下不用额外调。但 PKG_CONFIG_PATH 得在跑 configure 之前由你手工清掉或者设对，否则 Qt 构建会从主机系统拿到不该用的头文件和库，编译出一个链接不到目标库的东西。

-sysroot 会顺带在调用编译器时加上 --sysroot 参数。个别情况下你不想要这个行为，用 -no-gcc-sysroot 关掉。

-prefix、-extprefix、-hostprefix 控制装到哪儿。上面例子里的 /usr/local/qt5 是目标设备上的路径。注意 make install 并不会往设备上部署任何东西，它只是装到 extprefix，而 extprefix 默认等于 sysroot + prefix。也就是说默认会往 sysroot 里写，很多人嫌把 sysroot 弄脏，那就显式给 -extprefix。-hostprefix 单独把主机工具（qmake、rcc、uic）分出去，不给它的话这些工具跟目标库装在一起，交叉编译的项目里容易混。

三、QWS：Qt4 时代的老方案 #

QWS 是 Qt Window System 的缩写。Qt4 自带的一套轻量窗口系统，干的是 X11 加窗口管理器的活儿，只不过只服务 Qt 程序。

它的进程模型是 server/client：一个程序用 -qws 启动，它就变成 server，自己占住 framebuffer，负责合成所有窗口、分发输入事件；其他 Qt 程序作为 client 通过 socket 连上去，各自画到自己的离屏缓冲里，由 server 混合后上屏。

bash
# Qt4 的典型启动方式
./app -qws
# 或者显式指定显示设备与几何尺寸
QWS_DISPLAY=LinuxFb:/dev/fb0 ./app -qws

为什么被换掉 #

QWS 的问题在 Qt4 后期越来越明显：

  • 私有协议，只有 Qt 认。想让一个非 Qt 的程序上屏，没门。
  • server 一旦崩，所有 client 一起完蛋，没有隔离。
  • 多进程调试很别扭，断点打了不知道停在谁身上。
  • GPU 加速路径弱。QWS 时代的 OpenGL 支持要靠厂商打补丁，各家花样不同。
  • 跟桌面那套东西不通，代码在 PC 和板子之间搬来搬去总要动。

Qt 5.0 直接把它从主线里删了。替代方案分两路：单进程用 QPA 后端（linuxfb / eglfs）直连显示设备，多进程用 Wayland 的合成器协议。

两代机制对照 #

维度 QWS（Qt4） QPA（Qt5）
定位 Qt 自带的窗口系统 平台适配层，本身不是窗口系统
进程模型 server + client，多进程 单进程为主，多进程交给 Wayland
窗口管理 QWS server 提供 没有，程序自己管
启动参数 -qws -platform <名字>
显示设备 QWS_DISPLAY QT_QPA_PLATFORM 及插件参数
GPU 加速 依赖厂商补丁 eglfs 原生走 EGL + GLES2
现状 已从主线移除 唯一路径

迁移时的机械动作 #

从 Qt4 代码搬过来，跟窗口系统有关的这些要清掉：

cpp
// Qt4 写法，Qt5 编不过
#include <QWSServer>
QWSServer::setCursorVisible(false);

// Qt5 对应做法：环境变量，不用改代码
// export QT_QPA_EGLFS_HIDECURSOR=1

还有 QWSDisplay::setTransformation() 这类调用，Qt5 里换成 QT_QPA_EGLFS_ROTATION 环境变量，或者 QML 场景里的 transform。启动脚本里的 -qws 一律删掉，改成 -platform。

四、linuxfb：直接写 framebuffer #

linuxfb 干的事一句话能说完：打开 /dev/fb0，把它 mmap 到用户空间，Qt 的 backing store 把光栅化后的像素直接写进那块内存。

没有显卡参与，没有 EGL，没有上下文切换。所有绘制——线段、渐变、抗锯齿、图片缩放、文字栅格化——全在 CPU 上算完再写内存。

只支持软件渲染内容。 这句话的含义是：Qt Quick 的线程化渲染循环、QOpenGLWidget、任何直接调 OpenGL 的代码，在 linuxfb 上都没有意义。QWidget 那套 painter 体系照常工作，因为它本来就是 CPU 画图。

代价是显示性能受限制。分辨率越高、重绘面积越大、混合层数越多，CPU 吃得越狠。

加载与参数 #

参数有两个入口：QT_QPA_PLATFORM 环境变量，或者 -platform 命令行。多个设置用冒号分开。

bash
# 指定 /dev/fb1，不要默认的 fb0
export QT_QPA_PLATFORM=linuxfb:fb=/dev/fb1

# 厂家给的 fb 尺寸查询不准，手工钉死
export QT_QPA_PLATFORM=linuxfb:fb=/dev/fb0:size=1024x600:mmsize=222x125
参数 含义 说明
fb=/dev/fbN 帧缓冲设备 多显示设置下可以让不同程序跑在不同屏上
size=<宽>x<高> 逻辑分辨率（像素） 查询不准时必须手工给
mmsize=<宽>x<高> 物理尺寸（毫米） 直接决定 DPI 与字号外观
offset=<宽>x<高> 屏幕左上角像素偏移 默认 0x0
nographicsmodeswitch 不把虚拟终端切到图形模式（KD_GRAPHICS） 同时跳过关光标、关屏幕消隐这两步
tty=/dev/ttyN 覆盖虚拟控制台 仅在没设 nographicsmodeswitch 时生效

一个限制要提前知道：同一个 Qt 应用没法用多个帧缓冲。 fb= 只是选一个，不是选一组。要一块板子带两块屏各跑一个程序，就起两个进程，各带各自的 fb=。想在一个程序里画两块屏，得换 eglfs 的 KMS/DRM 后端。

offset 这个参数在拼接屏的场景里用得上。一块物理屏被切成几个 framebuffer 区域，一个程序占左边，另一个占右边，靠 offset 定位。

DRM dumb buffer 路径 #

Qt 5.9 起多了一条路。因为 fbdev 子系统在内核里已经被标为弃用，新内核很多直接不编 CONFIG_FB，/dev/fb0 压根不存在。这时候 linuxfb 插件可以不碰 fbdev，改走 DRM 的 dumb buffer。

bash
# 打开 DRM dumb buffer 路径
export QT_QPA_FB_DRM=1
export QT_QPA_PLATFORM=linuxfb
./myapp

设成非零值之后，只要系统支持 dumb buffer，/dev/fb0 就不会被访问。渲染通过 DRM API 建立，思路跟 eglfs_kms 的后端类似，输出是双缓冲加 page flip，软件渲染内容也能拿到正常的 vsync。

走 dumb buffer 的时候，上面那张表里的参数全部失效。 物理尺寸、逻辑尺寸这些属性都由 DRM 自动查询，fb=、size=、mmsize=、offset= 给了也没用。

这是一条很好用的路径：没有 GPU 的板子，配上 4.x 以后的内核，用 linuxfb + QT_QPA_FB_DRM=1 既能上屏又能消掉撕裂，比死磕 fbdev 干净。

全屏策略 #

Qt 5.9 起，eglfs 和 linuxfb 的窗口尺寸策略被统一了：第一个顶级窗口被强制铺满整个屏幕。 你的 resize(640, 480) 会被无视。

老代码依赖旧行为的，用这个变量退回去：

bash
export QT_QPA_FB_FORCE_FULLSCREEN=0

性能边界在哪儿 #

给几个能直接对号入座的判断：

  • 800×480、界面是几个按钮加一块数值显示、每秒重绘一两次——CPU 完全够，一个 ARM9 都能跑。
  • 1024×600 以上、每帧整屏重绘、带半透明叠加和动画——CPU 会吃满，界面卡成幻灯片。
  • 想在 linuxfb 上跑 Qt Quick——别想。要么换 eglfs，要么用 Qt Quick 的软件渲染后端（QT_QUICK_BACKEND=software），后者把场景图也交给 CPU，性能同样受限于第一条和第二条。

真要在这类板子上做流畅界面，办法是减少重绘面积。update(rect) 只传脏矩形，别调无参的 update()；背景用纯色别用渐变；动画用定时器改数值而不是整屏搬图。

五、eglfs：GPU 加速的一体化后端 #

eglfs 是给「没有真正窗口系统」的环境准备的平台插件。它架在 EGL 和 OpenGL ES 2.0 之上，让 Qt5 程序在没有 X11、没有 Wayland 的板子上拿到 GPU 加速。

EGL 负责什么，不负责什么 #

EGL 是 OpenGL 和本机窗口系统之间的接口。Qt 用它管上下文（context）和表面（surface）的创建、绑定、交换。

但 EGL 的 API 里没有「创建一个原生窗口」这件事。创建原生窗口（注意，这不一定是用户眼睛里看到的那个窗口）仍然要靠平台特定的办法。所以每一块板子、每一款 GPU，都得有对应的适配代码。这套代码在 eglfs 里叫钩子（hook），或者叫 EGL 设备集成。

形式上两种：

  1. 单个源文件，编译时直接编进平台插件里。老做法，现在很少见了。
  2. 做成独立的动态加载插件，比如 eglfs_kms.so、eglfs_mali.so。几乎所有后端都迁到了这个形式。

设备制造商会在他家的 mkspec 里塞一条 EGLFS_DEVICE_INTEGRATION，写着这块板的首选后端名字。这条是可选的，但很有用——目标系统里装了多个集成插件时，有它就不用每次手工设环境变量去挑。

能画哪三类东西 #

内容类型 走什么路径 备注
Qt Quick 2 场景 GL 直接渲染 首选场景
原生 OpenGL（QWindow + GL、QOpenGLWindow） GL 直接渲染 只允许一个全屏 GL 窗口
软件渲染的 QWidget CPU 画进 QImage，上传成纹理，插件合成 能用，多一次上传开销

最后一行是很多人忽略的一点：eglfs 也能渲染软件渲染的窗口，比如 QWidget。 机制是小部件的内容先由 CPU 渲染成一张图像，再上传成纹理，由插件做合成处理。所以 QWidget 程序在 eglfs 上跑得起来，只是没享受到 GPU 的绘制能力，只享受到了 GPU 的上屏能力。

强制全屏与根窗口 #

用 eglfs 时，系统强制第一个顶级窗口（可以是 QWidget 主窗口，也可以是 QQuickView）全屏运行。这个窗口同时被选为根部件窗口，所有其他顶级窗口——对话框、弹出菜单、下拉列表——都会被合成到它里面。

这不是 Qt 偷懒，是环境决定的：eglfs 的运行环境里从头到尾只有一个原生窗口和一个 EGL window surface，这两个东西由第一个创建出来的窗口生成。

所以这套设计在一种情形下工作得非常好：主窗口在整个应用生命周期里一直存在，其他窗口要么是非顶级的，要么在主窗口之后创建。

GL 窗口的硬限制 #

从 Qt 5.3 起，eglfs 支持一个全屏 GL 窗口（基于 OpenGL 的 QWindow、QQuickView 或 QGLWidget）。

一旦你想开第二个 OpenGL 窗口，或者把 GL 窗口的内容和 QWidget 内容混在一起，系统就不再支持，直接终止应用，同时给出错误消息。

这条限制对复杂界面的设计有实际影响。要在一个带 3D 视图的界面里弹出一个普通的 Qt 对话框，这个对话框必须走软件渲染那条路合成进根窗口，不能自己是个 GL 窗口。

eglfs 环境变量全表 #

这些变量在启动程序前设好，全部由 eglfs 插件读取。

变量 作用 取值与默认
QT_QPA_EGLFS_INTEGRATION 强制指定一个集成插件 如 eglfs_kms；特殊值 none 见下
QT_QPA_EGLFS_PHYSICAL_WIDTH 物理屏宽，毫米 查不到时按 DPI 100 折算
QT_QPA_EGLFS_PHYSICAL_HEIGHT 物理屏高，毫米 同上
QT_QPA_EGLFS_ROTATION 软件渲染内容的旋转 90 / 180 / -90
QT_QPA_EGLFS_FORCEVSYNC 每次 eglSwapBuffers() 后请求 FBIO_WAITFORVSYNC 仅 fbdev 类后端生效
QT_QPA_EGLFS_FORCE888 强制每通道 8 位 治 5-6-5 / 4-4-4 的面板
QT_QPA_EGLFS_FB 覆盖帧缓冲设备 默认 /dev/fb0

QT_QPA_EGLFS_HEIGHT 屏幕像素高 查询失败时用
QT_QPA_EGLFS_DEPTH 覆盖 QScreen 报告的色深 默认 32，只影响报告值

几条要单独说清。

QT_QPA_EGLFS_INTEGRATION 是绕过编译期钩子、在运行期点名的办法。设成 eglfs_kms 就走 KMS/DRM 后端。设成 none 是另一回事，它表示「用 EGL 直接配 framebuffer，不需要特殊集成」——某些板子确实这样，此时不会加载任何插件。系统里存在 DISPLAY 时（说明有桌面在跑），KMS 或 X11 后端优先。

QT_QPA_EGLFS_PHYSICAL_WIDTH 和 _HEIGHT 的重要性被低估得厉害。在无法从 /dev/fb0 或其他途径查询物理尺寸的平台上，Qt 按默认 DPI 100 算。基于 QWidget 或 Qt Quick Controls 的程序靠这两个值做字号和控件尺寸换算，硬编码的结果就是界面元素跟屏幕不匹配——要么小得看不清，要么大得放不下。

QT_QPA_EGLFS_ROTATION 只管软件渲染的内容，取值 90、180、-90。它不作用于基于 OpenGL 的窗口，包括 Qt Quick——后者要在 QML 场景里自己做变换。不管什么应用类型，标准 eglfs 鼠标光标都会考虑这个值，指针图像的位置和朝向跟着转；特殊的光标实现（比如 KMS/DRM 后端的硬件光标）不支持旋转。

QT_QPA_EGLFS_FORCEVSYNC 针对依赖 fbdev 子系统的老后端。默认交换间隔是 1，Qt 假定 eglSwapBuffers() 自己会处理 vsync。驱动有 bug 没处理就会撕裂，这时把它设成非零，让插件在每次 swap 后显式请求 FBIO_WAITFORVSYNC。

QT_QPA_EGLFS_FORCE888 治色带。有些设备默认选到每像素少于 32 或 24 位的配置（5-6-5、4-4-4），渐变出一圈圈条纹。设上它，创建上下文、窗口或离屏表面时忽略 RGB 通道大小，直接要求每通道 8 位，比改应用代码省事。

QT_QPA_EGLFS_DEPTH 容易误解：只改 QScreen 报告的颜色深度值，跟 EGL 配置和实际渲染色深无关。QT_QPA_EGLFS_SWAPINTERVAL 默认 1，让渲染跟垂直刷新同步；传 0 关掉交换阻塞，能刷多快刷多快，功耗和发热跟着上去。QT_QPA_EGLFS_DEBUG 打开后，创建新上下文时打印输入的 QSurfaceFormat 和最终选中的 EGL 配置属性，跟 QSG_INFO 一起用排查 EGL 配置问题。

KMS/DRM 的 JSON 配置 #

KMS/DRM 后端支持用一份 JSON 覆盖默认配置。环境变量指向文件：

bash
export QT_QPA_EGLFS_KMS_CONFIG=/etc/qt/kms.json

文件也可以嵌进 Qt 资源系统里，部署时少一个外部文件。

json
{
  "device": "/dev/dri/card1",
  "hwcursor": false,
  "pbuffers": true,
  "outputs": [
    { "name": "VGA1", "mode": "off" },
    { "name": "HDMI1", "mode": "1024x768" }
  ]
}

这份配置干了三件事：

  • 不用硬件光标（退回用 OpenGL 渲染鼠标指针；默认是开硬件光标的，因为效率更高）。
  • 用标准 EGL pbuffer 表面来返回 QOffscreenSurface（默认关掉这个，改用 gbm 表面）。
  • VGA 接口上的输出被关掉，HDMI 输出打开，分辨率 1024×768。

顺带还禁掉了通过 libudev 查找设备这一步，直接用 device 指定的那个。

mode 不写的时候，系统选它报告为首选的模式。可接受的值：off、current、preferred、宽x高、或者一整行模式行字符串。

六、三种后端的选择 #

现场条件 选什么 理由
有 GPU，厂商给了 EGL / GLES2 驱动 eglfs 硬件加速，Qt Quick 的正路
要跑 Qt Quick eglfs 场景图需要 GL
无 GPU，界面全是 QWidget linuxfb 不需要 EGL 依赖，部署简单
只有 /dev/fb0，内核没开 DRM linuxfb 唯一选择
内核 4.x 以上，fbdev 被裁掉 linuxfb + QT_QPA_FB_DRM=1 拿到 vsync 和 page flip
要多个进程各出各的窗口 wayland 有合成器做仲裁
板子上已经跑了 X xcb 能跑，但性能不占优
一个程序要输出到两块屏 eglfs + KMS/DRM 只有这条路径支持多输出

三个判断点，按顺序问自己：

驱动在不在。 有 GPU 但厂商没给 EGL/GLES2 驱动，eglfs 编不出来也用不了。查 configure 输出里 EGLFS details 那几行，看你板子的后端是不是 yes。

Qt Quick 要不要。 要，就只能走 GL 路径或者软件渲染后端。软件渲染后端在嵌入式上很吃力，等于用 CPU 模拟一个 GPU 的活儿。

多屏要不要。 除了 eglfs 的 KMS/DRM 和 EGLDevice 后端，其他后端对多显示器的支持都是「有限或不支持」。linuxfb 的 fb= 一次只能选一块。

XCB 和 Wayland 什么时候用 #

XCB 是桌面 Linux 上的 X11 插件，嵌入式里也有应用，需要 X11 的组件和开发文件，用法跟桌面 PC 一样。它有两个麻烦：某些设备上 EGL 实现跟 Xlib 不兼容，EGL 和 OpenGL 支持直接缺失，插件就在没有 EGL 支持的情况下编出来，这种环境里 Qt Quick 2 或任何依赖 OpenGL 的程序都跑不了（QWidget 软件渲染不受影响）；只用 XCB 的性能和内存开销在嵌入式上难满足需求，多出来的 X server 进程本身就是浪费。

Wayland 提供客户端和显示服务器之间的现代协议，Qt 有 Qt Wayland 模块让程序作为客户端连上去。上它的唯一硬理由是你需要多个进程各自出窗口，并且希望有人帮你合成、管焦点；纯单应用全屏的场合上 Wayland 是给自己加一层。一个已知坑：用 Weston 当参考合成器时触摸屏输入会出问题，表现为事件识别不了或者反应迟钝，换合成器或者调 Weston 的输入配置，别在 Qt 这边绕。

七、窗口管理器的角色 #

前面说了没有窗口管理器，但没说清少了它到底少了什么。这一章把账算明白。

桌面上的窗口管理器替你做了这些事：

  • 决定谁在谁上面（Z 序）。
  • 决定谁接收键盘（焦点）。
  • 画标题栏、边框、关闭按钮（窗口装饰）。
  • 响应拖动标题栏、双击标题栏最大化（命中测试与交互）。
  • 提供 Alt+Tab、任务栏、工作区。
  • 维护「正常 / 最大化 / 最小化 / 全屏」这四种状态的语义。
  • 处理窗口之间不重叠的布局（平铺型 WM）。

嵌入式上这些全没了。Qt 也不打算替你补。QPA 插件的职责是把像素送上屏、把输入事件读进来，它不管窗口之间的关系。

三种 show 在嵌入式的真实行为 #

桌面程序员习惯的那套 showNormal() / showMaximized() / showFullScreen()，在没有 WM 的环境里长出完全不同的性格。

调用 桌面上 eglfs / linuxfb 上
showFullScreen() 铺满屏幕，可退出 尺寸等于屏幕尺寸，唯一语义正确的一个
showMaximized() 铺满工作区，保留装饰 尺寸跟全屏差不多，但没有「最大化」状态位，不能还原
showNormal() 恢复上次几何尺寸 窗口想多大就多大，位置在 (0,0)，没人给它装饰，用户也拖不动
setGeometry() 生效并由 WM 尊重 第一个顶级窗口的被后端覆盖；后续窗口的被接受，但只影响合成位置
move() 生效 只影响在根窗口里的合成位置

showMaximized() 那一行值得多说两句。在 eglfs 和 linuxfb 下，第一个顶级窗口本来就被强制铺满，所以你调 showMaximized() 看到的画面跟 showFullScreen() 一模一样。但状态标志里没有 Qt::WindowMaximized，靠它做分支的代码会走错方向。写嵌入式界面就统一用 showFullScreen()，别留第二种写法。

位置是程序自己说了算 #

没有 WM，QWidget::move(200, 100) 不会有人拦着，也真的会生效——但生效的含义跟在桌面上不同：它不是「请求窗口管理器把窗口挪到那儿」，而是「告诉后端合成时往这个偏移画」。

这带来一个副作用：两个窗口重叠时，谁压谁由创建顺序和 Qt 的图层顺序决定，你没法通过点击让底下的窗口浮上来。

把 WM 的活儿自己干 #

多数嵌入式项目的做法是不做 WM，只做「一个全屏窗口 + 内部页面切换」。真要模拟出一点 WM 的味道，最小实现是这样几件事：

cpp
// 把 WM 缺的三件事补上：挂父、居中、抬层
void adopt(QWidget *root, QWidget *dlg)
{
    dlg->setParent(root, Qt::Dialog);      // 挂到根窗口里
    dlg->setWindowFlags(Qt::Dialog);
    QRect g = dlg->geometry();
    g.moveCenter(root->rect().center());   // 居中，别让它跑到屏外
    dlg->setGeometry(g);
    dlg->show();
    dlg->raise();
}

这段代码没有窗口装饰、没有拖动，就三件事：挂到根窗口、居中、抬到最上层。嵌入式界面要的往往就是这三件。

八、多窗口与层级 #

没有窗口管理器，多窗口这条路上只有四种走法，从简到繁。

走法一：只有一个全屏窗口。 所有内容都在一个 QMainWindow 或 QWidget 里，靠内部布局切换。这是嵌入式的默认答案，也最稳，跟 eglfs 的「第一个顶级窗口 + 根窗口」模型天然对齐，不会踩任何坑。

走法二：QStackedWidget 切页面。 需求里出现「主界面 / 设置页 / 参数编辑页」的时候，用一个 QStackedWidget 装这几页，换 setCurrentIndex()。

cpp
auto *stack = new QStackedWidget(this);
stack->addWidget(new HomePage);      // 0
stack->addWidget(new SettingPage);   // 1
stack->addWidget(new ParamPage);     // 2

auto *lay = new QVBoxLayout(this);
lay->setContentsMargins(0, 0, 0, 0);
lay->addWidget(stack);

// 页面回连：想进设置页就切到 1
connect(homePage, &HomePage::gotoSetting, this, [stack]{ stack->setCurrentIndex(1); });

showFullScreen();

几层页面就是几个全屏 widget 互相切换，屏幕上永远只有一个顶级窗口。eglfs 的限制一个都碰不到。

走法三：弹窗，接受被合成。 QDialog、QMessageBox、QComboBox 的下拉列表，在 eglfs 下都会被合成进根窗口。它们看起来是「弹出来的」，实际是根窗口的一个子表面。两个后果：弹窗坐标是相对屏幕的，move() 的效果就是它在整块屏上的位置，想居中拿 screen()->geometry() 算；eglfs 只有一个原生窗口，弹窗越多合成开销越大，叠四五层半透明对话框帧率掉得肉眼可见。QMessageBox::exec() 这种模态调用照常工作，因为模态只是 Qt 内部的事件循环阻塞，跟 WM 无关。

走法四：真多顶层窗口。 QWindow 这套 API 允许你创建多个顶层窗口，Qt 也维护了它们之间的层级关系。但在没有 WM 的环境里，这个层级关系的实际意义只有「合成顺序」。用户点不到后面那个，也没法在窗口之间切换焦点。需要真正的多窗口多任务就上 Wayland，别在 eglfs 上硬拗。

多屏：一块大虚拟桌面 #

KMS/DRM 后端接多块屏时，默认把 DRM 层报告的所有屏幕当成一块大的虚拟桌面。鼠标光标实现会考虑这一点，在屏幕上按预期移动。

cpp
// 逐个列举屏幕，这是查多屏是否被识别的最快办法
for (QScreen *s : QGuiApplication::screens()) {
    qDebug() << s->name() << s->geometry() << s->physicalSize();
}
需求 配置项
换左右顺序 outputs[].virtualIndex，从 0 开始
竖着堆（上下而不是左右） virtualDesktopLayout: "vertical"
精确指定某屏左上角坐标 outputs[].virtualPos，如 "0,1080"
指定主屏 outputs[].primary: true
每屏单独的物理尺寸 outputs[].physicalWidth / physicalHeight
关掉虚拟桌面，各屏独立 separateScreens: false 
json
{
  "device": "drm-nvdc",
  "outputs": [
    { "name": "HDMI1", "virtualIndex": 0 },
    { "name": "DP1",   "virtualIndex": 1 }
  ]
}

上面这份让左边的屏是 HDMI 口那块，右边是 DisplayPort 那块。数组元素顺序无关紧要，没写 virtualIndex 的输出排在所有指定了索引的后面，内部保持 DRM 连接器列表的原始顺序。要竖着排（从上到下堆叠），在 device 后面加一个 "virtualDesktopLayout": "vertical"。

primary 决定 QGuiApplication::primaryScreen() 返回谁。不设的时候主屏是第一个注册的屏幕，也就是按 DRM 连接器顺序定的。要让 VGA 那块当主屏而不让 HDMI 抢走：

json
{
  "device": "/dev/dri/card0",
  "outputs": [
    { "name": "HDMI1" },
    { "name": "VGA1", "mode": "1280x720", "primary": true },
    { "name": "LVDS1", "mode": "off" }
  ]
}

几个坑先摆出来：

  • virtualPos 拼出来的非线性布局，鼠标会走得很怪。有鼠标需求的场合别这么配，触摸没这个问题。
  • 虚拟桌面里所有屏最好用同一分辨率，否则鼠标光标这类元素在一块屏上会表现异常。
  • 不同物理尺寸、不同逻辑 DPI 也别用，某些图形栈组件只认第一块屏的 DPI 值。
  • 嵌入式环境的虚拟桌面比完整窗口系统弱得多。跨屏重叠、非全屏窗口、在屏之间拖动窗口，这些都别做。

每个屏幕一个全屏窗口这条限制仍然在，而且窗口 show() 之后再改屏幕不支持。

cpp
// 必须在 show() 之前把所有 setScreen() 做完
view->setScreen(screen);
view->showFullScreen();     // 这之后再 setScreen 无效

最常用也最受支持的用法是每屏开一个独立的 QQuickWindow 或 QQuickView：

cpp
int main(int argc, char **argv)
{
    QGuiApplication app(argc, argv);
    QVector<QQuickView *> views;
    for (QScreen *screen : app.screens()) {
        QQuickView *view = new QQuickView;
        view->setScreen(screen);
        view->setResizeMode(QQuickView::SizeRootObjectToView);
        view->setSource(QUrl("qrc:/main.qml"));
        QObject::connect(view->engine(), &QQmlEngine::quit,
                         qGuiApp, &QCoreApplication::quit);
        views.append(view);
        view->showFullScreen();
    }
    int result = app.exec();
    qDeleteAll(views);
    return result;
}

运行效果取决于 Qt Quick 用哪个渲染循环。默认的 threaded 循环下，每个窗口拿到自己的渲染线程，线程按 vsync 各自调节，互不干扰，这正是我们要的。换成 basic 循环会出问题，动画变差。

要验证板子和驱动在多屏下工作正常，用 hellowindow 示例最快：

bash
./hellowindow -platform eglfs --multiscreen --timeout 5000

每块连着的屏幕上会有一个转动的 Qt 标志，转五秒退出。哪块屏没出东西，问题就在那块屏的驱动或连接器配置上。

九、输入设备与 tslib #

没有窗口系统，输入就得自己读。鼠标、键盘、触摸全部通过直接读 evdev，或者借助 libinput、tslib 这类辅助库拿到。

前提一条：/dev/input/event* 这些设备节点得对运行程序的用户可读。要么用 root 跑，要么把用户加进 input 组，要么写一条 udev 规则改权限。这一条不满足，后面所有配置都是白费。

eglfs 和 linuxfb 都编进了全套输入处理代码，不需要额外装什么。

两条路径与三个参数变量 #

Qt 自己挑一条走。

路径 依赖 怎么触发
libinput libudev + libinput（键盘还要 xkbcommon） 编译时找到就用；linuxfb 默认走这条
内置 evdev 无 libinput 不可用，或设了 QT_QPA_EGLFS_NO_LIBINPUT

要用 libinput，libudev 和 libinput 的开发文件在配置和构建 Qt 时都得在 sysroot 里。linuxfb 默认就用它，不需要额外动作。

bash
# 强制回落到 Qt 自带的 evdev 处理器
export QT_QPA_EGLFS_NO_LIBINPUT=1

设备节点名这类参数走三个环境变量，条目之间用冒号分隔。

环境变量 控制的设备
QT_QPA_EVDEV_MOUSE_PARAMETERS 鼠标
QT_QPA_EVDEV_KEYBOARD_PARAMETERS 键盘
QT_QPA_EVDEV_TOUCHSCREEN_PARAMETERS 触摸屏

这套变量是 -plugin 命令行参数里那些设置的替代品。对 eglfs 和 linuxfb 来说它还是唯一的途径——这两个后端用内置输入处理器，-plugin 不带单独参数。

bash
export QT_QPA_EVDEV_MOUSE_PARAMETERS=/dev/input/event2:grab=1
export QT_QPA_EVDEV_KEYBOARD_PARAMETERS=/dev/input/event1
export QT_QPA_EVDEV_TOUCHSCREEN_PARAMETERS=/dev/input/event5:rotate=180

# 整个关掉内置处理器（linuxfb 的变量名是 FB，不是 LINUXFB）
export QT_QPA_EGLFS_DISABLE_INPUT=1
export QT_QPA_FB_DISABLE_INPUT=1

鼠标、键盘、触摸认的参数 #

参数 适用 作用

grab 鼠标 / 键盘 设 1 时独占抓取设备
nocompress 鼠标 关掉事件压缩。默认压掉不改变位置的事件，只在位置或按键变化时才发新事件
dejitter 鼠标 抖动限制。默认不启用消抖

keymap 键盘 指定自定义键盘映射文件
enable-compose 键盘 启用 compose 组合键

光标什么时候显示：QT_QPA_EGLFS_HIDECURSOR（eglfs）或 QT_QPA_FB_HIDECURSOR（linuxfb）没设，并且 Qt 基于 libudev 的设备发现报告至少有一个鼠标可用。没有 libudev 支持时光标一直显示，除非显式禁用——没插鼠标却有个箭头杵在屏幕中间，就是这个原因。

热插拔只在 Qt 配了 libudev 支持时可用（configure 时 sysroot 里有 libudev 开发头）。配了之后能在程序运行中插拔输入设备。

终端抢键盘 #

没关掉终端会话的系统上，按键行为很迷惑：同一个键既进了界面，又进了 tty，因为事件被 Qt 应用和 tty 两头处理。三种解法：

一、靠 Qt 关掉终端键盘。 eglfs 和 linuxfb 启动时把 tty 的键盘模式设成 K_OFF，阻止按键进终端。要恢复标准行为：QT_QPA_ENABLE_TERMINAL_KEYBOARD=1。这一步只在程序从远程控制台（比如 ssh）启动、并且终端键盘输入保持启用时才行。

二、抢设备。 QT_QPA_EVDEV_KEYBOARD_PARAMETERS=grab=1。抓取成功后，只要 Qt 程序在跑，系统里没有别的组件能从这个设备收到事件。远程启动的程序更适合这一招，它不需要访问 tty 设备。

三、干脆不要 getty。 专用嵌入式镜像没必要起标准终端会话。Yocto 做镜像时把 SYSVINIT_ENABLED_GETTYS 取消设置，任何虚拟终端上都不跑 getty，也就没有输入被抢。具体做法看你构建环境的文档。

自定义键盘映射 #

内置映射不够用，两条路：keymap 参数指定一个 .qmap 文件；或者用 eglfs 专属的 loadKeymap() 在运行时切换——后者要求走 eglfs 的内置键盘处理器，通过 -plugin 加载时不支持。

控制台切换（Ctrl+Alt+Fx）、zap（Ctrl+Alt+Backspace）这类系统组合键不支持，会被忽略。

生成 .qmap 用 kmap2qmap（在 qttools 模块里）。源文件必须是标准 Linux kmap 格式，也就是内核 loadkeys 认的。来源三条：Linux Console Tools（LCT）项目；Xorg 的 X11 键盘映射用 ckbcomp 转成 kmap；kmap 是纯文本，手写。

用法是至少两个参数，最后一个是要生成的 .qmap，前面所有参数都当输入 kmap 解析：

bash
kmap2qmap i386/qwertz/de-latin1-nodeadkeys.kmap \
    include/compose.latin1.inc de-latin1-nodeadkeys.qmap

转换标准键盘图会刷一堆警告，说什么 Show_Registers、Hex_A 不支持。可以安全忽略——kmap2qmap 不支持内核的全部（伪）符号。

触摸屏与 tslib #

一些电阻式单点触摸屏要退回用 tslib，不能依赖 Linux 的多点触控协议和事件设备。现代电容触摸屏不需要 tslib。

bash
# 打开 tslib 支持
export QT_QPA_EGLFS_TSLIB=1     # eglfs
export QT_QPA_FB_TSLIB=1        # linuxfb

# 换设备
export TSLIB_TSDEVICE=/dev/input/event6

tslib 和 evdevtouch 产出的东西不一样。 tslib 输入处理器生成鼠标事件，只支持单点；evdevtouch 生成真正的多点触控 QTouchEvent。要用 QPinchGesture、双指缩放这类多点手势，只能走 evdevtouch。

屏幕方向和触摸方向对不上时，用 rotate / invertx / inverty 三个参数对齐：

bash
export QT_QPA_EVDEV_TOUCHSCREEN_PARAMETERS=/dev/input/event5:rotate=180

多屏系统的触摸路由 #

多屏上触摸事件必须路由到正确的虚拟屏幕，这要求触摸设备和显示器输出之间有明确映射。映射写在 QT_QPA_EGLFS_KMS_CONFIG 那份 JSON 里：outputs 数组的元素里出现 touchDevice 时，这个值被当成设备节点，触摸设备绑到对应的显示输出上。

json
{
  "device": "drm-nvdc",
  "outputs": [
    { "name": "HDMI1", "touchDevice": "/dev/input/event5", "virtualIndex": 1 },
    { "name": "DP1", "virtualIndex": 0 }
  ]
}

这段配置说的是：HDMI 那块屏（虚拟桌面里排第二）上贴着一块触摸屏，节点是 /dev/input/event5，它的触摸事件（以及由此合成的鼠标事件）都归到 HDMI 这块屏。

Qt 5.8 起这套映射只对 evdevtouch 后端成立，基于 libinput 的变体仍然把事件送到主屏。系统里存在多个输入后端时要强迫用 evdevtouch，就设 QT_QPA_EGLFS_NO_LIBINPUT=1。

拿不准用哪个节点、哪块屏的时候，开全量日志：

bash
QT_LOGGING_RULES="qt.qpa.*=true" ./myapp

图形和输入子系统的日志全出来。识别输入设备节点靠它，发现输出配置问题也靠它。

笔式平板与输入调试 #

evdevtablet 给 Wacom 和类似的笔输入平板提供基本支持，只产生 QTabletEvent。用 QT_QPA_GENERIC_PLUGINS=evdevtablet 让它自发现设备，或者写成 QT_QPA_GENERIC_PLUGINS=evdevtablet:/dev/event1 直接指定节点（libudev 发现不起作用、行为不对时用）。命令行等价写法是 -plugin evdevtablet。

查「到底在用哪个设备」「这个设备为什么没被识别」，开这一条：

bash
export QT_LOGGING_RULES="qt.qpa.input=true"

设备的探测、打开、事件处理都会打出来。

自定义鼠标光标图像 #

eglfs 自带一套 32×32 的鼠标光标。不够用就把 QT_QPA_EGLFS_CURSOR 指向一个 JSON 图集文件，这个文件也能嵌进 Qt 资源系统，省一个外部依赖。

json
{
  "image": ":/cursor-atlas.png",
  "cursorsPerRow": 8,
  "hotspots": [[7, 2], [12, 3], [12, 12]]
}

hotspots 是每个光标的点击热点，按光标顺序排列。图集必须为所有支持的光标都提供图像，少一个就出错。图像要紧紧打包，单个光标的宽高由总图像尺寸和 cursorsPerRow 算出来，不留空隙。

Unix 信号处理 #

面向控制台的平台插件（eglfs 和 linuxfb）默认会装信号处理器，捕获 SIGINT、SIGTSTP / SIGCONT、SIGTERM。目的是在程序被 kill、Ctrl+C、Ctrl+Z 暂停或恢复、终止时，把键盘模式、终端光标、还有其他图形状态还原回去。通过键盘终止或暂停只在设了 QT_QPA_ENABLE_TERMINAL_KEYBOARD 时才行。

捕获 SIGINT 会打断远程调试（gdb 靠它停程序）。要退出全部内置信号处理就设 QT_QPA_NO_SIGNAL_HANDLER=1，代价是程序被杀之后终端状态没人收拾，得手工 reset。

十、屏幕旋转与分辨率 #

旋转这件事有三层，改哪一层结果完全不同。

层 手段 影响范围
驱动 / KMS DRM plane 的 rotation 属性、内核 cmdline 整块屏，含光标和 GL
QPA QT_QPA_EGLFS_ROTATION 只管软件渲染的 QWidget 内容
应用 QML 的 rotation / transform、QGraphicsView::rotate 只管自己的场景

最省事的是驱动层，最常踩坑的是 QPA 层——因为它只转一半的东西。

bash
# 竖屏板子：把软件渲染内容转 90 度
export QT_QPA_EGLFS_ROTATION=90
# 触摸坐标必须跟着转，否则点哪儿哪儿不对
export QT_QPA_EVDEV_TOUCHSCREEN_PARAMETERS=/dev/input/event5:rotate=90

QT_QPA_EGLFS_ROTATION 支持 90、180、-90。它不动基于 OpenGL 的窗口，Qt Quick 要在 QML 场景里自己变换。光标的位置和朝向会跟着转，但 KMS/DRM 的硬件光标不支持旋转。

分辨率从哪儿来，按后端分：

场景 手段
eglfs 走 DRM 自动读连接器的模式
eglfs 查询失败 QT_QPA_EGLFS_WIDTH / _HEIGHT 覆盖像素尺寸
KMS 配置里指定 outputs[].mode，取值见下
linuxfb size=<宽>x<高>，查询不准时必须给
物理尺寸 QT_QPA_EGLFS_PHYSICAL_WIDTH / _HEIGHT；多屏时用 outputs[] 的 physicalWidth / physicalHeight

mode 可接受的值：off、current、preferred、宽x高、或者一整行模式行字符串。不写就选系统报告为首选的那个。QT_QPA_EGLFS_DEPTH 只改 QScreen 报告的值，真正改不了渲染色深。

EGLDevice 后端的几个开关 #

Tegra 一类设备走 eglfs_kms_egldevice，它依赖 EGLDevice 和 EGLStream 扩展，不用 GBM。Qt 5.7 起它跟基于 GBM 的后端共享大量内部实现，多屏和 QT_QPA_EGLFS_KMS_CONFIG 都支持，但 hwcursor 和 pbuffers 两个配置项不适用。

后端默认给每个输出的默认平面自动选 EGL 层。要用 QT_QPA_EGLFS_LAYER_INDEX 指定层索引——注意它不支持多输出，只能用在单屏系统上。需要绑定到特定连接器的覆盖平面时，用 QT_QPA_EGLFS_KMS_CONNECTOR_INDEX 和 QT_QPA_EGLFS_KMS_PLANE_INDEX，设了之后只有指定的连接器和平面被使用，其他输出全部忽略。

屏已经报了目标分辨率但还是黑着，说明启动时没设视频模式。QT_QPA_EGLFS_ALWAYS_SET_MODE 设非零再重启程序。EGLStream 的行为由 QT_QPA_EGLFS_STREAM_FIFO_LENGTH 控制（前提是系统支持 KHR_stream_fifo）：默认 mailbox 模式，设 1 或更大切到 FIFO，值就是这个流最多能缓存几帧。

多输出别指望太多 #

除了 KMS/DRM 和 EGLDevice，其他 eglfs 后端对多显示器的支持都是有限或不支持。i.MX6 配 Vivante GPU 的板子跟 linuxfb 一样，QT_QPA_EGLFS_FB 只能指定一块帧缓冲。树莓派用 QT_QPA_EGLFS_DISPMANX_ID 指定输出屏（值对应 DISPMANX_ID_ 常量，查 Dispmanx 文档）。这些方法都不能从一个程序输出到多块屏。

带固定专用显存的系统要留个心：跑 Qt Quick 或 QOpenGLWidget 之前，全高清屏下默认设置会不够用，程序会以莫名其妙的方式失败。至少给 GPU 留 128 MB。显存不是固定预留的系统没这个问题。

十一、字体与中文显示 #

Qt 找字体有两条路。系统里有 fontconfig，就用它访问系统字体；没有，回退到 QBasicFontDatabase，去 Qt 的 lib/fonts 目录下翻，自动识别预渲染字体和 TrueType。

bash
# 指定自己的字体目录
export QT_QPA_FONTDIR=/opt/fonts

Qt 不再在 lib/fonts 里装任何字体。 字体由平台镜像提供，交叉编译部署完发现界面全是方块，第一件事就是查板子上到底有没有字体文件。

中文变方块 #

嵌入式 rootfs 里常见的是只有 DejaVu 一套，中文全部渲染成空心方块。修法三步：

  1. 把中文字体（思源黑体、Noto Sans CJK）拷进 /usr/share/fonts 或者 QT_QPA_FONTDIR 指的目录。
  2. 跑一次 fc-cache -fv，或者直接设 QT_QPA_FONTDIR 让 Qt 自己去扫。
  3. 程序里确认字体族名真的存在。
cpp
// 第一手段：打印板子上认到的所有字体族
for (const QString &f : QFontDatabase().families())
    qDebug() << f;

中文界面还有两个连带问题。一是字体文件体积，Noto Sans CJK 全量几十 MB，嵌入式得裁剪字集或者用点阵字体。二是 DPI：物理尺寸报错的板子上字号会小到看不清，用 QT_QPA_EGLFS_PHYSICAL_WIDTH / _HEIGHT 修正，别去改字号常量。
