本篇讲 Qt 界面程序里那些不挂控件名头、但每天都要用的工具类：正则匹配、容器排序、调用系统打开文件与网址、取文件图标和类型、基础类型互转。

不讲的：各 QWidget 派生控件的绘制、布局与事件分发，见同目录控件篇；模型/视图架构见模型篇；QProcess 完整用法单独成篇，这里只借它开个文件夹。

版本基线 Qt 5.12 到 Qt 6.x。凡是 Qt 5 已废弃、Qt 6 被移除的接口，都点明替代写法，别照着十年前的博客直接抄。

一、QRegExp 与 QRegularExpression #

Qt 里写正则，你会同时撞见两个类。老项目满屏 QRegExp，新代码只有 QRegularExpression。这不是风格偏好，是两代引擎。

QRegExp 是 Qt 4 时代自研的引擎，语法参考 Perl 但不等于 Perl。QRegularExpression 从 Qt 5.0 引入，底层直接挂 PCRE（Qt 6 起是 PCRE2），语法、边界行为、性能都对得上主流实现。

官方态度很明确：Qt 5.15 把 QRegExp 标记废弃，Qt 6 把它从 QtCore 挪进 Qt5Compat 模块。Qt 6 项目里 #include <QRegExp> 直接找不到文件，要么改代码，要么链 Qt6::Core5Compat 续命。

维度 QRegExp QRegularExpression
引入版本 Qt 4.0 Qt 5.0
引擎 Trolltech 自研 PCRE / PCRE2
语法 类 Perl 的方言 PCRE，与 PHP、Python 的 re 大体一致
性能 回溯实现较慢 支持 JIT，Qt 5.4 起自动启用
捕获组 cap(n)、capturedTexts() captured(n)，另有命名组
整体匹配 exactMatch() 一个函数搞定 match() 返回 QRegularExpressionMatch，需锚定
Qt 6 状态 移出 QtCore，仅在 Qt5Compat 标准接口
新代码 不要用 用这个

同一个需求的两种写法，先看差异：

cpp
// 老写法
#include <QRegExp>
QRegExp re("[0-9]{4}");
bool ok = re.exactMatch("2015");              // true，只认整串

// 新写法
#include <QRegularExpression>
QRegularExpression re("[0-9]{4}");
bool ok = re.match("2015").hasMatch();        // true
bool ok2 = re.match("年份 2015").hasMatch(); // 也是 true！

注意第二个结果。match() 的语义是「在串里搜索一次」，不是整串比对。老代码从 exactMatch 迁过来，最典型的翻车就是这个：原来守得住的 "abc2015xyz"，现在放行了。

三条路可以还原整串语义：

cpp
// 1. 手动加锚点：\A 串首、\z 串尾，不受多行模式影响
QRegularExpression re("\\A[0-9]{4}\\z");
bool ok = re.match(text).hasMatch();

// 2. anchoredPattern 包一层（Qt 5.12+），内部就是 \A(?:...)\z
QRegularExpression anchored =
    QRegularExpression::anchoredPattern("[0-9]{4}");
bool ok2 = anchored.match(text).hasMatch();

// 3. 查匹配区间，判是否覆盖全串
QRegularExpressionMatch m = re.match(text);
bool ok3 = m.hasMatch() && m.capturedStart() == 0
                        && m.capturedLength() == text.length();

anchoredPattern() 比手写 ^...$ 稳，因为 ^ $ 在多行模式下会漂移。

迁移时还有一批方法名要一起换：

QRegExp QRegularExpression
exactMatch(s) anchoredPattern(...) 后 match(s).hasMatch()
indexIn(s) match(s).capturedStart()
lastIndexIn(s) globalMatch(s) 循环取最后一个
cap(n) captured(n)
numCaptures() captureCount()
setPatternSyntax(QRegExp::Wildcard) wildcardToRegularExpression()
QRegExpValidator QRegularExpressionValidator

通配符那行值得单独说。*.txt 这种 shell 通配，QRegExp 设个 Wildcard 语法就完事；QRegularExpression 没有语法开关，要用 wildcardToRegularExpression("*.txt") 转成正则串，再叠一个 CaseInsensitiveOption 就能匹到 readme.TXT。

结论：新代码一律 QRegularExpression。老代码不用立刻全改，但凡是动到的正则顺手换掉；换的时候盯住 exactMatch 与 hasMatch 这一处语义差，其余都是机械替换。

二、正则的常用模式 #

Qt 项目里用到的模式就那么几类。先把字符类钉死，再往上搭。

写法 含义
. 任意字符，默认不含换行
\d \w \s 数字、单词字符（字母数字下划线）、空白
[abc] / [^abc] 括号内任一字符 / 除括号内字符外的任意字符
{6,20} {6,} {6} 6 到 20 次 / 至少 6 次 / 恰好 6 次
* + ? 0 次以上 / 1 次以上 / 0 或 1 次
\A \z 串首、串尾绝对锚点
(?<name>...) 命名捕获组
(?:...) 非捕获组，只分组不占编号

第一类，汉字与「非汉字」：

cpp
// 只要非汉字，6 到 20 位
QRegularExpression nonChinese("[^\\x{4E00}-\\x{9FA5}]{6,20}");

\x{4E00} 到 \x{9FA5} 是 CJK 统一表意文字的基本区，覆盖日常汉字。老稿写的是 [^\u4E00-\u9FA5]{6,20}，那是 QRegExp 的转义习惯；PCRE 不认 \u 前缀，迁过来要改成 \x{4E00}，写成 C++ 字符串就是 "\\x{4E00}"。

也可以把汉字直接写进字符类，可读性更好：[^一-龥]{6,20}。一 是 U+4E00，龥 是 U+9FA5。

第二类，用户名。字母数字下划线，长度受限：

cpp
QRegularExpression userRe("[A-Za-z0-9_]{6,30}");

第三类，数字范围。这里别急着上正则，QIntValidator 更省事，还能顺手卡范围：

cpp
QIntValidator *portValidator = new QIntValidator(0, 65535, this);   // 端口

真要用正则，\d{1,5} 只卡位数，卡不住 99999 越界。范围交 QIntValidator 或者自己转 int 再比。

再补一批常见模式，直接抄（IPv4 单段是四选一，竖线塞不进表格，单独列成 C++ 串：(25[0-5]|2[0-4]\\d|1\\d\\d|[1-9]?\\d)，四段用 {3} 重复、句点分隔）：

用途 模式
邮箱（宽松版） [A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,}
中国大陆手机号 1[3-9]\\d{9}
日期 YYYY-MM-DD (\\d{4})-(\\d{2})-(\\d{2})
十六进制颜色 #[0-9A-Fa-f]{6}
连续空白压缩 \\s+
行尾空白 \\s+\\z

贪婪与懒惰是另一处高频。默认量词贪婪，.* 会一路吃到串尾再回溯：

cpp
QString html = "<b>粗体</b>和<i>斜体</i>";
QRegularExpression greedy("<.*>");
QRegularExpression lazy("<.*?>");

qDebug() << greedy.match(html).captured(0);   // <b>粗体</b>和<i>斜体</i>
qDebug() << lazy.match(html).captured(0);     // <b>粗体</b>

量词后加 ? 就变懒惰。解析标签、切分被包裹的片段，懒惰版基本都更符合直觉。

命名捕获组在业务代码里比数字下标好维护：

cpp
QRegularExpression re("(\\d{4})-(\\d{2})-(\\d{2})");
QRegularExpressionMatch m = re.match("2013-04-03");
if (m.hasMatch()) {
    int year  = m.captured(1).toInt();
    int month = m.captured(2).toInt();
}

// 命名组，读代码的人不用数括号
QRegularExpression named("(?<year>\\d{4})-(?<month>\\d{2})-(?<day>\\d{2})");
QRegularExpressionMatch nm = named.match("2013-04-03");
if (nm.hasMatch())
    int year = nm.captured("year").toInt();

全局查找与替换各一行：

cpp
QRegularExpression re("\\d+");
QRegularExpressionMatchIterator it = re.globalMatch("a1 b22 c333");
while (it.hasNext())
    qDebug() << it.next().captured(0);        // 1 / 22 / 333

QString s = "2013-04-03";
s.replace(QRegularExpression("(\\d{4})-(\\d{2})-(\\d{2})"), "\\2/\\3/\\1");
// 结果 04/03/2013

性能上有一条硬提醒：别在循环里反复构造 QRegularExpression。构造时要编译模式，开销远大于匹配本身。把它提到循环外，或者写成 static const QRegularExpression digitsOnly("^\\d+$");，编译一次、复用到底。

三、用正则做输入校验 #

Qt 把校验拆成两层：输入框上的 validator 管「能不能敲进去」，提交时的显式匹配管「交上来的对不对」。

第一层是 QValidator。QLineEdit::setValidator() 接一个校验器，键盘输入时逐字符过滤：

校验器 用途
QIntValidator(min, max) 整数范围，如端口 0-65535
QDoubleValidator(min, max, decimals) 浮点范围与小数位
QRegularExpressionValidator(re) 正则约束，用户名、密码等

正则校验器的新旧写法：

cpp
// 老项目
#include <QRegExpValidator>
QRegExp passwordRegExp("[^\\u4E00-\\u9FA5]{6,20}");
QRegExpValidator *oldValidator = new QRegExpValidator(passwordRegExp, this);

// Qt 5 / Qt 6
#include <QRegularExpressionValidator>
QRegularExpression passwordRe("[^\\x{4E00}-\\x{9FA5}]{6,20}");
QRegularExpressionValidator *passwordValidator =
    new QRegularExpressionValidator(passwordRe, this);

QLineEdit *passwordLineEdit = new QLineEdit(this);
passwordLineEdit->setValidator(passwordValidator);

QRegularExpressionValidator 内部是整串锚定语义，与 exactMatch 等价，这点不用担心。

第二层是提交校验。老稿的思路是掏出 validator 里的模式再跑一次整串匹配，思路对，代码要跟着引擎换：

cpp
passwordLineEdit->setText("密码正则ok");   // ← validator 拦不住这一行
QString password = passwordLineEdit->text();

// 老写法：QRegExpValidator::regExp() 拿到模式，再 exactMatch
if (!oldValidator->regExp().exactMatch(password))
    return false;

// 新写法：QRegularExpressionValidator::regularExpression()，没有 exactMatch
if (!passwordValidator->regularExpression().match(password).hasMatch())
    return false;

为什么不能只靠 validator？setText() 走的是程序赋值，不经过键盘过滤，validator 不会把值弹回去。从配置文件读回来、从剪贴板粘进去，全都绕过第一层。所以第二层不能省。

走 validate() 时注意它的三种返回值，别只判 != Invalid：

返回值 含义 处理
Invalid 怎么改都合法不了 直接拒绝
Intermediate 目前不完整，继续输入还有救 允许留在输入框里
Acceptable 合法 放行 
cpp
QString input = passwordLineEdit->text();
int pos = 0;
if (passwordValidator->validate(input, pos) != QValidator::Acceptable)
    return false;   // 只认 Acceptable

数字框用 QIntValidator 最省心，端口一行就够：

cpp
QLineEdit *portEdit = new QLineEdit(this);
portEdit->setValidator(new QIntValidator(0, 65535, this));

它只认十进制数字和正负号，非数字敲不进去，范围在提交时判定。老稿写 new QIntValidator(0, 65535)、没传 parent，对象就得自己管生命周期，补上 this 省心。

密码加用户名这种组合校验，封成小函数，界面逻辑里只留一行调用：

cpp
bool validateAccount(const QString &user, const QString &password, QString *error)
{
    static const QRegularExpression userRe("\\A[A-Za-z0-9_]{6,30}\\z");
    static const QRegularExpression pwdRe("\\A[^\\x{4E00}-\\x{9FA5}]{6,20}\\z");

    if (!userRe.match(user).hasMatch()) {
        if (error) *error = "用户名需 6-30 位字母、数字或下划线";
        return false;
    }
    if (!pwdRe.match(password).hasMatch()) {
        if (error) *error = "密码需 6-20 位且不含汉字";
        return false;
    }
    return true;
}

边界要说清：正则只是界面层的顺手拦截，真正的约束得在数据库或服务端再做一遍。客户端能被绕过，这一点不因为用了 Qt 而改变。

四、排序：qSort 与其替代 #

qSort 是 Qt 早年给容器用的模板排序函数，头文件 <qalgorithms.h>，实现是快速排序：

cpp
template <typename RandomAccessIterator, typename LessThan>
void qSort(RandomAccessIterator begin, RandomAccessIterator end, LessThan lessThan);

只给两个迭代器时，它用元素类型的 operator< 做升序；第三个参数塞比较器，规则自己定。

现状说得直白些：Qt 5.2 起标记废弃，Qt 6 里已经删掉。Qt 6 项目里写 qSort(...) 是编译错误，没有兼容层可救。

替代品是 <algorithm> 里的 std::sort，传参结构一样，几乎逐字替换：

cpp
// 老写法
#include <QList>
#include <qalgorithms.h>
QList<int> list;
list << 33 << 12 << 68 << 6 << 12;
qSort(list.begin(), list.end());          // [ 6, 12, 12, 33, 68 ]

// 新写法
#include <algorithm>
QList<int> list2;
list2 << 33 << 12 << 68 << 6 << 12;
std::sort(list2.begin(), list2.end());    // 结果一致

四种排序方式对照：

方式 头文件 稳定性 最坏复杂度 Qt 6
qSort <qalgorithms.h> 不稳定 快排，退化到 O(N²) 已移除
qStableSort <qalgorithms.h> 稳定 归并，额外内存 已移除
std::sort <algorithm> 不稳定 内省排序，O(N log N) 可用
std::stable_sort <algorithm> 稳定 O(N log N)，额外内存 可用
QList::sort() <QList> 不稳定 内部即 std::sort 可用

QList::sort() 在 Qt 5 与 Qt 6 都能用，本质包了一层 std::sort，不带比较器时按 operator< 升序。容器就是 QList 时这个写法最短：

cpp
QList<int> list{33, 12, 68, 6, 12};
list.sort();                              // 升序

要自定义规则，还是 std::sort 传比较器更清楚。Qt 6 里 QList 和 QVector 已经合并成同一个类，老代码的 QVector<int> 一样用 std::sort。

稳定性值得多说一句。键值相等的元素保持原相对顺序，这叫稳定。表格按「等级」排序，同等级的行若还要维持录入顺序，就得用 std::stable_sort。用 std::sort 时相等元素的顺序未定义，测试环境看着对，换台机器就会变。

五、自定义比较规则 #

比较器的契约只有一条：comp(a, b) 表示「a 是否严格排在 b 前面」。返回 bool，入参是两个常引用。

第一条实战需求，英文串忽略大小写排序。默认 operator< 按字符编码比，DELTA 会排到 beTA 前面，因为大写字母编码更小：

cpp
#include <QStringList>
#include <algorithm>

bool caseInsensitiveLessThan(const QString &s1, const QString &s2)
{
    return s1.toLower() < s2.toLower();
}

QStringList list;
list << "AlPha" << "beTA" << "gamma" << "DELTA";
std::sort(list.begin(), list.end(), caseInsensitiveLessThan);
// [ "AlPha", "beTA", "DELTA", "gamma" ]

比较器可以是函数指针、lambda、仿函数，std::sort 都吃：

cpp
// lambda，就地定义，省一个全局函数
std::sort(v.begin(), v.end(), [](const QString &a, const QString &b) {
    return a.toLower() < b.toLower();
});

// 需要携带状态时用仿函数：CompareByColumn{2} 表示按第 2 列排序

第二条需求来自真实业务：结构体多字段排序。钢筋计划量列表，按「钢筋级别」升序，级别相同再按「直径」比。

cpp
struct BarAmount
{
    int barLevel;           // 钢筋级别，1、2、3
    QString diameter;       // 直径描述，"12-菱"、"14"
    double planAmount;      // 计划量
    double purchaseAmount;  // 采购量
    double amount;          // 总量
};

// 直径比较：抠出数字按数值比，"9" 要排在 "12" 前面
int compareDiameterDescription(const QString &d1, const QString &d2)
{
    static const QRegularExpression numRe("(\\d+(?:\\.\\d+)?)");
    QRegularExpressionMatch m1 = numRe.match(d1);
    QRegularExpressionMatch m2 = numRe.match(d2);

    double n1 = m1.hasMatch() ? m1.captured(1).toDouble() : 0.0;
    double n2 = m2.hasMatch() ? m2.captured(1).toDouble() : 0.0;

    if (n1 < n2) return -1;
    if (n1 > n2) return 1;
    return QString::compare(d1, d2);   // 数值相同退回字典序，保证全序
}

有了辅助函数，多级比较写出来是这样：

cpp
bool compareBarData(const BarAmount &bar1, const BarAmount &bar2)
{
    // 第一优先级：钢筋级别
    if (bar1.barLevel < bar2.barLevel)
        return true;
    if (bar1.barLevel > bar2.barLevel)
        return false;

    // 第二优先级：级别相同，比直径
    int r = compareDiameterDescription(bar1.diameter, bar2.diameter);
    if (r == -1) return true;
    if (r == 1)  return false;

    // 全部相等
    return false;
}

最后那个 return false 是硬要求。std::sort 要求比较器满足严格弱序：comp(a, a) 必须为假。老稿这里写的是 return true;，注释还写着「属性一致，维持原有相对顺序」——塞进 std::sort，MSVC 的 debug 版会弹 invalid comparator 断言，release 版是未定义行为，轻则顺序乱，重则越界崩。

想清楚这行表达什么：比较器不负责「维持原顺序」，那是稳定排序干的事。相等就老实返回 false。

同样的多级逻辑，用 lambda 加 std::tie 写更短，它的字典序比较天生满足严格弱序，不会踩上面那个坑：

cpp
#include <tuple>
#include <algorithm>

std::sort(list.begin(), list.end(), [](const BarAmount &a, const BarAmount &b) {
    return std::tie(a.barLevel, a.diameter)
         < std::tie(b.barLevel, b.diameter);   // 逐字段按字典序比
});

std::sort(v.begin(), v.end(), std::greater<int>());   // 纯降序

规则藏在 lambda 里复用不方便，多字段还要自定义转换（比如直径按数值比）时，还是老实写函数。

比较器里做重活（拼字符串、查库、构造 QRegularExpression）会把排序从 O(N log N) 次比较膨胀成 O(N log N) 次重操作。预处理一次，把比较键提前算进结构体字段，比在比较器里现算快得多。

六、QDesktopServices：调用系统能力 #

QDesktopServices 只有几个静态函数，职责单一：把 QUrl 交给操作系统的默认处理程序。打开浏览器、打开文件夹、打开文档、发邮件，都走它。核心接口一个：

cpp
bool QDesktopServices::openUrl(const QUrl &url);

返回值表示「请求是否交给了系统」，不表示「打开成功」。用户点了取消、系统没装关联程序、协议没人认领，返回值照样是 true。想确认结果只能自己盯进程，或者用 setUrlHandler() 注册处理器。

支持的协议看 scheme：

scheme 系统动作
http / https 默认浏览器
file 默认程序打开文件，或文件管理器打开目录
ftp 默认 FTP 客户端
mailto 默认邮件客户端
自定义 scheme 注册过的外部程序

老稿打开网页是这么写的：

cpp
QUrl url(QString("www.google.com"));
bool is_open = QDesktopServices::openUrl(url);

能跑，但别学。QUrl("www.google.com") 解析出来 scheme 是空的，www.google.com 落在 path 上。openUrl 拿到没有协议的 URL 只能交给系统猜，Windows 上多数时候会兜到浏览器，别的平台未必。写全协议：

cpp
bool ok = QDesktopServices::openUrl(QUrl("https://www.google.com"));

取系统目录要重点说，老代码全在这上面翻车。QDesktopServices::storageLocation() 在 Qt 5.0 就废弃了，Qt 6 直接删掉，替代品是 QStandardPaths：

cpp
// 老写法：Qt 5 编译有警告，Qt 6 编译不过
QString desktop = QDesktopServices::storageLocation(QDesktopServices::DesktopLocation);

// 新写法
#include <QStandardPaths>
QString desktop2 = QStandardPaths::writableLocation(QStandardPaths::DesktopLocation);

枚举名一模一样，换个类名就行，是最省事的一处迁移：

需求 老接口 新接口
桌面、文档、主目录、程序目录、临时目录 QDesktopServices::XxxLocation QStandardPaths::XxxLocation，枚举名不变
配置目录 无对应 QStandardPaths::AppConfigLocation
数据目录 无对应 QStandardPaths::AppDataLocation
exe 所在目录 无对应 QCoreApplication::applicationDirPath()

writableLocation() 有返回空串的情形（比如 Linux 上没有 XDG_DESKTOP_DIR），拿到结果先判空。要枚举全部候选目录用 standardLocations()，它返回按优先级排的字符串列表，writableLocation() 取的就是第一个。

七、打开文件、目录与网址 #

这一节的写法全是可复制粘贴的，按场景分。打开网址：

cpp
QDesktopServices::openUrl(QUrl("https://www.google.com"));
QDesktopServices::openUrl(QUrl("mailto:someone@example.com?subject=反馈"));

打开本地文件，用系统默认程序：

cpp
QString path = "E:/文档/报表.xlsx";
bool ok = QDesktopServices::openUrl(QUrl::fromLocalFile(path));

QUrl::fromLocalFile() 比手动拼 "file:///" + path 强，原因有两个。一是它把路径里的中文、空格、#、? 正确转义，手拼的字符串遇到这些字符就断在中间；二是它处理盘符与分隔符，Windows 的反斜杠也能吃。

老稿的拼法是 "file:///" + local_path，再给 QUrl 挂个 QUrl::TolerantMode。TolerantMode 容忍一些非法字符，是个补丁不是解法：路径里有 # 时它照样把后面当片段分隔符切掉，文件就打不开了。

打开文件夹，并在资源管理器里选中某个文件：

cpp
#ifdef Q_OS_WIN
QString target = "E:/文档/报表.xlsx";
// /select, 后面不能有空格，路径用参数列表传，避免空格截断
QProcess::startDetached("explorer.exe",
                        {"/select,", QDir::toNativeSeparators(target)});
#endif

只打开文件夹不定位，openUrl(QUrl::fromLocalFile(folder)) 就够，跨平台。

打开可执行程序：

cpp
// 方式一：交给系统关联
QDesktopServices::openUrl(QUrl::fromLocalFile("E:/tools/ffmpeg-gui.exe"));

// 方式二：自己起进程，能传参
QProcess::startDetached("E:/tools/ffmpeg-gui.exe", {"-i", "input.mp4"});

老稿用字符串拼接起进程：QProcess::startDetached("explorer " + local_path)。能通，但路径里有空格就断。第二个参数是 QStringList，一个元素一个参数，不经过 shell 解析，空格和中文都不用转义，写成 startDetached("explorer.exe", {QDir::toNativeSeparators(local_path)}) 即可。

相对路径是另一个高频雷区。程序要跟着用户的环境走，路径就得相对可执行文件算：

cpp
QString baseDir  = QCoreApplication::applicationDirPath();
QString filePath = QDir(baseDir).filePath("resources/help.pdf");
QDesktopServices::openUrl(QUrl::fromLocalFile(filePath));

QDir::currentPath() 与 applicationDirPath() 不是一回事。前者是启动时的工作目录，从快捷方式启动、双击运行、IDE 里跑，三者各不相同；后者才是 exe 所在目录，稳得多。

场景与写法对照：

场景 写法
打开网页 openUrl(QUrl("https://..."))
打开本地文件 openUrl(QUrl::fromLocalFile(absPath))
打开文件夹 openUrl(QUrl::fromLocalFile(dirPath))
文件夹里选中文件 startDetached("explorer.exe", {"/select,", native})，仅 Windows
启动外部程序带参 QProcess::startDetached(prog, args)
发邮件 openUrl(QUrl("mailto:..."))
取系统目录 QStandardPaths::writableLocation(...)

openUrl 在 UI 线程上是同步调用，但它只发消息给 shell，很快返回，不卡界面。真正会卡的是路径检查：网络盘、掉线的映射盘上 QFileInfo::exists() 能卡好几秒。网络路径先在后台线程探一遍再决定要不要打开。

八、QFileIconProvider：取文件图标 #

写文件浏览器、下载器、附件列表，都要给每个条目配图标。系统里那套图标（文件夹、txt、pdf、docx 各不相同）不用自己画，QFileIconProvider 干的就是这件事。

它原本是 QFileSystemModel 的内部依赖，也可以单独拿出来用。公开接口：

cpp
QIcon icon(QFileIconProvider::IconType type) const;
QIcon icon(const QFileInfo &info) const;                                    // 文件必须存在
QIcon icon(QFileIconProvider::IconType type, const QFileInfo &info) const;  // Qt 5.10+
QString type(const QFileInfo &info) const;
QString type(QFileIconProvider::IconType type) const;

第一种吃枚举，拿系统预置的通用图标：

cpp
#include <QFileIconProvider>
#include <QIcon>

QFileIconProvider icon_provider;
QIcon folderIcon = icon_provider.icon(QFileIconProvider::Folder);
QIcon fileIcon   = icon_provider.icon(QFileIconProvider::File);

枚举全表：

枚举值 图标含义 备注
Computer 本机 我的电脑
Desktop 桌面
Trashcan 回收站 Linux 上常为空图标
Network 网络
Drive 磁盘驱动器 软驱、光驱也算
Folder 文件夹 最常用
File 通用文件 没有关联程序时的兜底

第二种吃 QFileInfo，按具体文件查系统关联图标。.docx 返回 Word 的蓝色图标，.pdf 返回阅读器图标：

cpp
#include <QFileInfo>

QFileInfo fileInfo("C:/test_document.docx");
QFileIconProvider provider;

QIcon docxIcon   = provider.icon(fileInfo);
QString docxType = provider.type(fileInfo);   // "Microsoft Word 文档" 之类

这里有个前提：文件必须真实存在于本地。Windows 上的实现是去问 shell「这个路径的图标是什么」，路径不存在，shell 只能回一个通用图标，或者干脆不给。这就是「先建临时空文件再取图标」那套偏方出现的由来，也是有人宁可直接调 Win32 API 的原因。

三个平台的行为差异要知道：

平台 实现方式 已知差异
Windows SHGetFileInfo 图标尺寸随系统 DPI 变，取到的是大图标
macOS NSWorkspace 返回应用图标，文件类型图标较少
Linux QIcon::fromTheme 依赖桌面主题包，缺主题时全是通用图标

type(info) 返回本地化字符串，中文系统上是「文本文档」「文件夹」，英文系统上是「Text Document」。这串字只能拿去显示，不能拿去判断类型，第九章细讲。

九、文件类型判断 #

先说结论：拿 QFileIconProvider::type() 做业务判断是错的。它是给人看的文案，随系统语言变，随系统版本变，同一个 .log 在不同机器上能返回三种说法。

判断类型有四条路径，各有代价：

判断目标 做法 说明
只看后缀 QFileInfo::suffix() 最快，文件可以随便改名
看复合后缀 QFileInfo::completeSuffix() .tar.gz 能整段取出来
看真实类型 QMimeDatabase::mimeTypeForFile() 读文件头，可靠，有 IO 开销
看系统描述 QFileIconProvider::type() 只用于界面显示

后缀提取有几个容易写错的地方：

cpp
QFileInfo fi("C:/data/report.tar.gz");
QString suffix = fi.suffix();           // "gz"
QString full   = fi.completeSuffix();   // "tar.gz"
QString base   = fi.completeBaseName(); // "report"

自己从文件名抠后缀，别用 Java 那套 lastIndexOf(".")。Qt 的 QString::lastIndexOf 接 QChar，传字符串匹配到的是别的东西，老稿代码里就是 file_name.lastIndexOf(".")，从 Java 直接搬过来的：

cpp
int index = file_name.lastIndexOf('.');    // 字符用单引号
if (index > 0)                             // 注意 > 0，排除 ".bashrc"
    QString suffix = file_name.mid(index).toLower();   // ".txt"

判 > 0 而不是 >= 0，因为 .bashrc 最后一个点在 0 位，那不是后缀。大小写也要统一，Windows 上一个 README.TXT 能让只认小写的分支全崩。

QMimeDatabase 才是可靠判断：

cpp
#include <QMimeDatabase>
#include <QMimeType>

QMimeDatabase db;
QMimeType mime = db.mimeTypeForFile("C:/data/report.pdf",
                                    QMimeDatabase::MatchContent);  // 读内容
qDebug() << mime.name();      // "application/pdf"
qDebug() << mime.comment();   // "PDF document"

MatchContent 打开文件读头部字节，可靠但慢；MatchExtension 只看名字，快但能被骗；默认的 MatchDefault 先看名字、不确定再看内容。

回到 Windows 那条特殊路线。有些场景 QFileIconProvider 根本不适用：文件列表来自网络、来自数据库、来自用户输入的虚拟条目，磁盘上压根没有这个文件。这时按「建临时空文件」的办法做，几千个条目就是几千次磁盘写，界面直接卡死。

Windows 上有个标志位专治这件事：SHGetFileInfo 配 SHGFI_USEFILEATTRIBUTES。加了它，API 不再碰磁盘，只按你给的文件名和属性查系统图标缓存，文件存不存在都能返回结果。

cpp
#include <windows.h>
#include <shellapi.h>
#include <QIcon>
#include <QFileInfo>

class FileHelper
{
public:
    static QIcon   getFileIcon(const QString &file_name);
    static QString getFileType(const QString &file_name);
    static QIcon   getFolderIcon();
    static QString getFolderType();
};

// 取扩展名，带点；取不到就退回占位名
static QString suffixOf(const QString &file_name)
{
    int index = file_name.lastIndexOf('.');
    return index > 0 ? file_name.mid(index) : QString("file");
}

// 按扩展名取系统图标，不要求文件存在
QIcon FileHelper::getFileIcon(const QString &file_name)
{
    if (file_name.isEmpty())
        return QIcon(":/icon/file");

    SHFILEINFOA info = {0};
    if (SHGetFileInfoA(suffixOf(file_name).toLocal8Bit().constData(),
                       FILE_ATTRIBUTE_NORMAL, &info, sizeof(info),
                       SHGFI_ICON | SHGFI_USEFILEATTRIBUTES)) {
        HICON hIcon = info.hIcon;
        QIcon icon = iconFromHIcon(hIcon);
        DestroyIcon(hIcon);                 // 必须释放，否则句柄泄漏
        return icon;
    }
    return QIcon(":/icon/file");            // 兜底图标
}

QString FileHelper::getFileType(const QString &file_name)
{
    if (file_name.isEmpty())
        return "file";

    SHFILEINFOA info = {0};
    if (SHGetFileInfoA(suffixOf(file_name).toLocal8Bit().constData(),
                       FILE_ATTRIBUTE_NORMAL, &info, sizeof(info),
                       SHGFI_TYPENAME | SHGFI_USEFILEATTRIBUTES))
        return QString::fromLocal8Bit(info.szTypeName);
    return "file";
}

// 文件夹：属性位换 FILE_ATTRIBUTE_DIRECTORY
QIcon FileHelper::getFolderIcon()
{
    SHFILEINFOA info = {0};
    if (SHGetFileInfoA("folder", FILE_ATTRIBUTE_DIRECTORY, &info, sizeof(info),
                       SHGFI_ICON | SHGFI_USEFILEATTRIBUTES)) {
        HICON hIcon = info.hIcon;
        QIcon icon = iconFromHIcon(hIcon);
        DestroyIcon(hIcon);
        return icon;
    }
    return QIcon(":/icon/folder");
}

QString FileHelper::getFolderType()
{
    SHFILEINFOA info = {0};
    if (SHGetFileInfoA("folder", FILE_ATTRIBUTE_DIRECTORY, &info, sizeof(info),
                       SHGFI_TYPENAME | SHGFI_USEFILEATTRIBUTES))
        return QString::fromLocal8Bit(info.szTypeName);
    return "folder";
}

几个点单独拎出来：

  • 传给 API 的是扩展名（带点）或占位名（如 "folder"）。有 SHGFI_USEFILEATTRIBUTES 时，API 完全不看这个名字在磁盘上有没有。
  • 用 A 后缀版本（SHGetFileInfoA、SHFILEINFOA）配 toLocal8Bit()；用 W 版本则配 reinterpret_cast<LPCWSTR>(str.utf16())，两种别混。
  • SHGFI_ICON 给 HICON，SHGFI_SYSICONINDEX 给系统图标列表的索引。只要图标就选前者，配 SHGFI_LARGEICON 或 SHGFI_SMALLICON 控尺寸。
  • DestroyIcon 一行都不能漏。每次调用都新建一个图标句柄，不销毁就是实打实的泄漏，循环几千次进程就胖了。

跨平台项目里有第三条路：QTemporaryFile 加 QFileIconProvider。思路是造一个真文件骗过「必须存在」的限制，取完立刻删。

cpp
QIcon FileIcon::fileExtensionIcon(const QString &extension) const
{
    QFileIconProvider provider;
    QIcon icon;

    // 模板里的 XXXXXX 会被替换成随机串，保证并发安全
    QTemporaryFile tmp(QDir::tempPath() + QDir::separator()
                       + QCoreApplication::applicationName()
                       + "_XXXXXX" + extension);
    tmp.setAutoRemove(false);          // 手动删，避免析构时机不可控
    if (tmp.open()) {
        QString fileName = tmp.fileName();
        tmp.write(QByteArray());       // 写空内容，只为让文件落地
        tmp.close();
        icon = provider.icon(QFileInfo(fileName));
        tmp.remove();
    } else {
        qCritical() << QString("failed to write temporary file %1")
                           .arg(tmp.fileName());
    }
    return icon;
}

取类型版本一模一样，只把 provider.icon(...) 换成 provider.type(...)，返回值类型从 QIcon 改成 QString，函数名换成 fileExtensionType。

这段代码能用，但只在两种情况下值得用：一是非 Windows 平台没有 SHGetFileInfo，二是需要图标的扩展名就固定几个。条目多的时候别用，每调一次就是创建文件、写、删的磁盘往返，几十条就能看出卡顿。

十、图标缓存与性能 #

取一个图标要多久？走 SHGetFileInfo 几十微秒到几毫秒，走临时文件是毫秒级。单个无所谓，列表滚动刷新就是几百上千次，差别立刻显形。

最省事也最见效的优化：按扩展名缓存。图标是按类型重复的，一千个文件往往只有八种后缀。

cpp
class IconCache
{
public:
    static IconCache &instance() { static IconCache c; return c; }

    QIcon iconForSuffix(const QString &suffix)
    {
        const QString key = suffix.toLower();      // 统一大小写，避免重复缓存
        {
            QMutexLocker locker(&m_mutex);
            auto it = m_icons.constFind(key);
            if (it != m_icons.constEnd())
                return it.value();
        }
        QIcon icon = FileHelper::getFileIcon(key); // 慢操作放在锁外
        QMutexLocker locker(&m_mutex);
        m_icons.insert(key, icon);
        return icon;
    }

private:
    IconCache() = default;
    QHash<QString, QIcon> m_icons;
    QMutex m_mutex;
};

缓存键只留扩展名，别用完整文件名。用文件名缓存命中率几乎为零，还白占内存。其余手段按投入产出排：SHGFI_USEFILEATTRIBUTES 免磁盘（仅 Windows）、图标尺寸固定成 16 或 32 免掉按 DPI 重算、先给首屏延迟加载再补图标、自备图标资源包做到零系统调用。

QIcon 本身带内部 pixmap 缓存，同一个 QIcon 对象多次 pixmap() 不会重复渲染，所以缓存 QIcon 就够，不必自己再包一层 QPixmap。

还有一处 Qt 5 的断点：QPixmap::fromWinHICON() 在 Qt 5 里被删了，前面那个 iconFromHIcon() 得自己实现。Qt 5 可以链 Qt5WinExtras，QtWin::fromHICON(hIcon) 一行换掉；Qt 6 把这个模块整个去掉了，只能用 DrawIconEx 把图标画进 QImage 缓冲区再封成 QIcon——申请兼容位图与内存 DC、GetDIBits 取 32 位像素、biHeight 取负值表示自上而下、DeleteObject 收尾，四十行左右，代价是要自己处理 devicePixelRatio，否则高 DPI 屏上糊成一团。

缓存加好之后，第一屏的图标开销还剩系统查询那一次。界面启动就能确定要显示哪几类文件时（比如固定的附件类型），在窗口构造后先跑一遍预热，把常见后缀填进缓存，列表首次绘制就不会有一排空图标闪一下。

十一、基本类型的相互转换 #

Qt 里字符串有三套：QString（UTF-16 字符）、QByteArray（原始字节）、char *（C 风格指针）。三套之间来回倒，加上数值类型，构成了日常一半以上的「编译不过」。

先看对照表：

从 到 写法
char * const char * 直接赋值，会有警告
const char * char * const_cast<char *>()
char QString QString(QChar(ch))
QString char * str.toLocal8Bit().data()，注意生命周期
QByteArray char * byte.data()
char * QByteArray QByteArray(ch)
QString QByteArray toUtf8() / toLocal8Bit() / toLatin1()
QByteArray QString QString::fromUtf8() / QString(byte)
int QString QString::number(n)
QString int str.toInt(&ok)
double QString QString::number(d, 'f', 2)
QString double str.toDouble(&ok)
任意 QVariant QVariant::fromValue(v)
QVariant 任意 var.value<T>()

char * 与 const char * 这一对，C++ 里就带着坑：

cpp
char *ch1 = "hello11";        // C++11 起非法，字面量是 const 的
const char *ch2 = "hello22";

ch2 = ch1;                    // 合法，加 const 是收紧
ch1 = (char *)ch2;            // 编得过，但不该写

char buf[] = "hello11";       // 要可写的缓冲区就用数组
buf[0] = 'H';                 // ok

ch1 = (char *)ch2; 能过编译，但 ch2 多半指向字符串字面量，落在只读段。转完写它一个字节，进程立刻挂。现代编译器对这行会给警告，别顺手 -Wno- 掉。

char 转 QString，用 QChar 包一层：

cpp
char a = 'b';
QString str = QString(QChar(a));            // "b"
QString str2 = QString::fromLatin1(&a, 1);  // 等价写法

直接写 QString(a) 会撞上 QString(int size, QChar ch) 那个重载的决议，行为不是你要的，别偷这个懒。

QString 转 char * 是最容易写出悬空指针的地方：

cpp
QString str = "abc";

// 错：toLatin1() 返回临时 QByteArray，语句结束就析构，ch 悬空
const char *ch = str.toLatin1().data();

// 对：先落地成有名字的 QByteArray，生命周期覆盖使用范围
QByteArray ba = str.toLocal8Bit();
const char *ch2 = ba.constData();       // 只读用 constData()

data() 返回的指针不拥有内存。ba 一旦析构、或被修改触发重分配，指针立刻失效。要跨函数传就传 QByteArray 或 std::string，别传裸指针。

编码三选一是另一个分水岭：

方法 编码 用在哪
toUtf8() UTF-8 写文件、网络、JSON、跨平台存储
toLocal8Bit() 系统本地编码 调 Win32 API、调 fopen 之类 C 接口
toLatin1() Latin-1 纯 ASCII 场景，中文变 ?

中文项目里用 toLatin1() 是事故源头："中文".toLatin1() 得到两个问号，存进文件再也回不来。存盘一律 toUtf8()，传给系统 API 一律 toLocal8Bit()。

数值转换带上成功标志，别信默认值：

cpp
bool ok = false;
int n = QString("120").toInt(&ok);      // ok=true，n=120
int m = QString("12a").toInt(&ok);      // ok=false，m=0

QString hex   = QString::number(255, 16);                // "ff"
QString msg   = QString("端口 %1，超时 %2 毫秒").arg(8080).arg(3000);
QString pad   = QString("%1").arg(7, 3, 10, QChar('0')); // "007"

toInt() 不传 &ok 时失败返回 0，和真实值 0 无法区分。解析用户输入、读配置文件，必须传 &ok。

十二、QVariant 的中转作用 #

QVariant 是 Qt 的万能类型容器。一个变量能装 int、QString、QDateTime、QStringList、QIcon、QFont，以及用 Q_DECLARE_METATYPE 注册过的自定义结构体。

它存在的理由是元对象系统需要一个统一的参数类型：信号槽跨线程投递、属性系统的 setProperty、模型/视图的 data()、QSettings 的读写，接口签名里都只有一个 QVariant 的位置。

接口 用途
isValid() / isNull() 是否装了东西 / 是否为空值
typeName() / typeId() 当前实际类型
toString() toInt(&ok) toBool() 转成具体类型
value<T>() 模板取值，自定义类型走这个
canConvert<T>() 能不能转，用在分支判断前
QVariant::fromValue(v) 从任意类型构造

两条取值路径要分清：

cpp
QVariant var = QVariant::fromValue(42);
int a = var.value<int>();          // 路径一：模板方法，读着顺，新代码用它
int b = qvariant_cast<int>(var);   // 路径二：老式自由函数，同一套实现

// 自定义类型必须注册，两个路径都依赖它
struct BarAmount { int barLevel; QString diameter; };
Q_DECLARE_METATYPE(BarAmount)

QVariant v = QVariant::fromValue(BarAmount{3, "12-菱"});
BarAmount back = v.value<BarAmount>();     // ok

三个真实场景，全在界面层：

cpp
// 一、QComboBox 的 userData：显示文本和背后数据分离
QComboBox *combo = new QComboBox(this);
combo->addItem("低优先级", QVariant(0));
combo->addItem("高优先级", QVariant(2));
combo->addItem("钢筋 12-菱", QVariant::fromValue(BarAmount{1, "12-菱"}));

int level      = combo->currentData().toInt();
BarAmount bar  = combo->currentData().value<BarAmount>();

// 二、QSettings 读写：所有值都过 QVariant
QSettings settings("MyOrg", "MyApp");
settings.setValue("ui/font", QFont("微软雅黑", 10));
settings.setValue("ui/recent", QStringList{"a.txt", "b.txt"});

QFont font    = settings.value("ui/font").value<QFont>();
int timeout   = settings.value("net/timeout", 5000).toInt();  // 带缺省值

// 三、模型里塞图标：图标的成果靠 QVariant 进视图
QVariant MyModel::data(const QModelIndex &index, int role) const
{
    if (role == Qt::DecorationRole)
        return QVariant(IconCache::instance().iconForSuffix("txt"));
    if (role == Qt::UserRole)
        return QVariant::fromValue(m_rows.at(index.row()));
    return QVariant();
}

userData 那条路比「把 id 拼进显示文本再解析」干净得多，界面文案随便改，数据不受影响。currentData() 是 Qt 5 的接口，Qt 4 里用 itemData(index)。

QFileIconProvider 吐出来的 QIcon、type() 吐出来的 QString，要穿过模型、穿过 userData、穿过信号槽，全靠 QVariant 包一层。这就是「中转」的含义：它不是终点，是各接口之间的通用货币。

一处易错：QVariant 转自定义类型时类型名必须完全一致。两个命名空间里各声明一个同名结构体，value<T>() 会静默返回默认构造的对象，不报错。排查先打 var.typeName()。

十三、易错点速查 #

把散落的坑收进一张表，改代码时对着扫一遍。

易错点 现象 改法
QRegExp 迁到 QRegularExpression 校验突然变宽松 exactMatch 换锚定后的 match().hasMatch()
\u4E00 转义 模式不匹配 改 \x{4E00}，或写 一-龥
循环里构造正则 列表滚动卡顿 提到循环外或 static const
validator 加 setText 非法值照样进去了 提交时再校验一遍
validate() 只判 Invalid Intermediate 被误放行 必须判 == Acceptable
qSort Qt 6 编译不过 换 std::sort
比较器相等返回 true debug 弹 invalid comparator 相等返回 false
用 std::sort 求稳定 同键元素顺序乱跳 换 std::stable_sort
QUrl("www.xxx.com") 有时打得开有时打不开 写全 https://
手拼 file:/// 加路径 中文、#、空格截断 QUrl::fromLocalFile()
storageLocation() Qt 6 编译不过 QStandardPaths::writableLocation()
lastIndexOf(".") 编译失败或匹配错位 字符用单引号 '.'
lastIndexOf('.') >= 0 .bashrc 被当成后缀 判 > 0
用 type() 判文件类型 换语言系统后逻辑崩 用 suffix() 或 QMimeDatabase
SHGetFileInfo 不删 HICON 进程内存持续上涨 每次 DestroyIcon
每个条目建临时文件 列表滚动卡死 按扩展名缓存，或走 SHGFI_USEFILEATTRIBUTES
toLatin1().data() 中文变问号、指针悬空 toUtf8() 且落地成 QByteArray
toInt() 不传 &ok 解析失败与 0 无法区分 传 &ok 并判断

value<T>() 拿到默认值 自定义类型没注册 Q_DECLARE_METATYPE，查 typeName()
