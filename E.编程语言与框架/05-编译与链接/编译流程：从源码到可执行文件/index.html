一、从源码到程序：四个阶段 #

先给结论：gcc main.c -o app 这一条命令，背后是四个程序接力跑完的。

text
main.c
  │  cpp    预处理：展开 #include、替换宏、过滤条件编译
  ▼
main.i
  │  cc1    编译：词法 → 语法 → 语义 → 优化 → 生成汇编
  ▼
main.s
  │  as     汇编：助记符翻成机器码、切段、记符号
  ▼
main.o
  │  ld     链接：合并同名字段、解析符号、重定位
  ▼
app

四个阶段的对照表，先记住这张：

阶段 真正干活的程序 输入 输出 输出格式 停止选项
预处理 cpp（cc1 内部亦可用 -E） .c .i 纯文本 -E
编译 cc1（C++ 是 cc1plus） .i .s 纯文本汇编 -S
汇编 as .s .o ELF 可重定位目标 -c
链接 ld（经 collect2 调度） .o + 库 可执行文件 ELF 可执行 无，默认跑到最后

把这张表刻进脑子，后面所有选项都只是「在第几个阶段停下」和「给第几个阶段加料」。

产物长什么样 #

写个最小程序，逐阶段看产物：

c
/* main.c */
#include <stdio.h>

int main(void) {
    printf("hello\n");
    return 0;
}

跑一遍四步：

bash
gcc -E main.c -o main.i
gcc -S main.c -o main.s
gcc -c main.c -o main.o
gcc main.o -o app
./app

用 file 看一眼每样东西的真面目：

bash
file main.c main.i main.s main.o app

text
main.i: C source, ASCII text
main.s: assembler source, ASCII text
main.o: ELF 64-bit LSB relocatable, x86-64, not stripped
app:    ELF 64-bit LSB pie executable, x86-64, dynamically linked, not stripped

前三个是文本，.o 之后是二进制。.i 里几千行几乎全是头文件展开的内容，main 函数被压到了文件末尾。

分步的意义 #

日常开发一条命令就够，但要排错，就必须知道错在哪个阶段。判据很简单：

现象 出错阶段 谁报的
fatal error: xxx.h: No such file or directory 预处理 cpp
error: expected ';' before ... 编译 cc1
assembler messages: Error: ... 汇编 as
undefined reference to 'xxx' 链接 ld

编译器报错时带的行号、列号和源码片段，是 cc1 打的；链接器报错只有符号名，没有行号，因为那时源码早被翻译完了。

二、GCC 是什么：编译驱动程序 #

gcc 本身不解析 C 代码。它是个驱动程序（driver），做的事是：读你的命令行，翻译成子程序参数，按顺序把 cpp、cc1、as、ld 拉起来，再把它们的输出串起来。

想验证这一点，加 -v 让它把每次调用都吐出来：

bash
gcc -v main.c -o app

输出里能抓到四段关键调用（路径随发行版变化）：

text
/usr/lib/gcc/x86_64-linux-gnu/11/cc1 -quiet -I ... main.c -o /tmp/ccXy12.i
/usr/lib/gcc/x86_64-linux-gnu/11/cc1 -quiet /tmp/ccXy12.i -o /tmp/ccAb34.s
as -v --64 -o /tmp/ccCd56.o /tmp/ccAb34.s
/usr/bin/ld -pie --dynamic-linker /lib64/ld-linux-x86-64.so.2 ... -o app

注意第一行：现代 GCC 里预处理也走 cc1，cc1 自己带上 -E 的行为。cpp 是可独立调用的预处理器前端，gcc -E 时由驱动决定用哪个。

只想看调用而不真的执行，用 gcc -### -c main.c，它把命令打印出来但立刻退出。

常用探查命令：

bash
gcc --version                    # 版本
gcc -dumpmachine                 # 目标三元组，如 x86_64-pc-linux-gnu
gcc -print-prog-name=cc1         # cc1 的真实路径，ld 同理
gcc -print-search-dirs           # 头文件与库的搜索目录

gcc 与 g++ 的区别 #

两个命令共用一个后端，差别在默认行为：

行为 gcc g++
处理 .c 文件 当 C 编译 当 C++ 编译
处理 .cpp 文件 当 C++ 编译 当 C++ 编译
链接时自动加 -lstdc++ 否 是
默认引用的标准库头文件 libc libstdc++ + libc

用 gcc 链接 C++ 目标文件，一定会撞上 undefined reference to 'std::cout' 之类的一堆符号。手动补 -lstdc++ 也能过，但直接用 g++ 更省事。

bash
g++ -c main.cpp -o main.o
g++ main.o -o app            # 正确：自动带上 libstdc++
gcc main.o -o app -lstdc++   # 也能过，只是多打字

三、预处理：宏、头文件与条件编译 #

预处理是纯文本手术，只认 # 开头的行，不认识任何 C 语法。

它做四件事：

  • 头文件展开：#include 处把目标文件内容整块复制进来，逐层递归。
  • 宏替换：把 #define 定义的名字换成对应的值或代码片段。
  • 条件编译：按 #if / #ifdef / #elif / #else / #endif 丢掉不成立的分支。
  • 注释去除：// 与 /* */ 被替换成空白，保留换行位置。

命令：

bash
gcc -E main.c -o main.i       # C 预处理，产物 .i
g++ -E main.cpp -o main.ii    # C++ 预处理，产物 .ii

不加 -o 就打到标准输出，配合 grep 查宏是否生效：gcc -E main.c | grep -n 'printf'。

看展开结果 #

写点宏，验证替换：

c
/* macro.c */
#include <stdio.h>

#define MAX(a, b) ((a) > (b) ? (a) : (b))
#define VERSION 3

int main(void) {
    int x = 7, y = 9;
    /* 这行注释会消失 */
    printf("ver=%d max=%d\n", VERSION, MAX(x, y));
    return 0;
}

bash
gcc -E macro.c -o macro.i
tail -20 macro.i

text
# 5 "macro.c"
int main(void) {
    int x = 7, y = 9;

    printf("ver=%d max=%d\n", 3, ((x) > (y) ? (x) : (y)));
    return 0;
}

三件事同时发生了：VERSION 变 3，MAX(x, y) 整块展开，注释位置只剩空行。# 5 "macro.c" 是行号标记（line marker），告诉后续阶段这行对应哪个源文件第几行，报错定位靠它。

保留注释加 -C，去掉行号标记加 -P：gcc -E -C main.c -o with_comment.i、gcc -E -P main.c -o no_marker.i。

宏定义从命令行注入 #

工程里大量用编译期开关，不走源码改：

选项 作用
-DMACRO 等价于 #define MACRO 1
-DMACRO=DEFN 等价于 #define MACRO DEFN
-UMACRO 取消已定义的 MACRO
-I DIR 追加头文件搜索目录
-include FILE 强制在源码第一行之前包含 FILE 
bash
gcc -DDEBUG -DVERSION_STR='"1.2.3"' -I./include -c main.c -o main.o
gcc -UDEBUG -c main.c -o main_release.o

-DDEBUG 让 #ifdef DEBUG 分支成立，-UDEBUG 让它失效。两条命令编同一个源文件，得到两份行为不同的目标文件。

#include "x.h" 与 #include <x.h> 的搜索顺序不同：

text
"x.h"  → 当前源文件所在目录 → -I 目录 → 系统目录
<x.h>  → -I 目录 → 系统目录

用 -I 加目录，加 -iquote 只影响引号形式的包含。

条件编译与诊断宏 #

条件编译最实用的场景是同一份代码编出多套行为：

c
#include <stdio.h>

int main(void) {
#ifdef DEBUG
    printf("[debug] build at %s %s\n", __DATE__, __TIME__);
#endif
#if defined(__x86_64__)
    printf("arch: x86_64\n");
#elif defined(__aarch64__)
    printf("arch: aarch64\n");
#else
    printf("arch: unknown\n");
#endif
    return 0;
}

bash
gcc -DDEBUG cond.c -o cond && ./cond

标准内置的诊断宏，写日志时直接用：

宏 展开为
__FILE__ 当前源文件路径字符串
__LINE__ 当前行号整型常数
__DATE__ 编译日期，如 "Nov 17 2026"
__TIME__ 编译时间，如 "13:46:46"
__func__ 当前函数名字符串
__STDC__ C 标准下为 1
__VERSION__ 编译器版本字符串

把它糊成一条日志宏：

c
#define log_debug(format, ...) \
    printf("[%s:%d] " format "\n", __FILE__, __LINE__, ##__VA_ARGS__)

##__VA_ARGS__ 的作用是消掉可变参数为空时多出来的那个逗号，log_debug("start") 也能编过。这是 GCC 扩展，-std=c99 -pedantic 下会告警。

生成依赖关系 #

改一个头文件，哪个 .o 需要重编？让编译器自己算：

bash
gcc -M main.c                  # 全部依赖，含系统头文件
gcc -MM main.c                 # 只列项目内头文件，排除系统头
gcc -MM -MT main.o main.c      # 指定目标名，输出可直接喂给 make

-MM 的输出形如 main.o: main.c include/util.h，正是 Makefile 需要的那一行。怎么用，看《Makefile 与构建自动化》。

四、编译：从 C 代码到汇编 #

这一阶段最重。cc1（C++ 是 cc1plus）拿到预处理后的文本，做五件事：

  • 词法分析：切成 Token，区分关键字、标识符、字面量、运算符。
  • 语法分析：按文法把 Token 序列组织成抽象语法树（AST）。
  • 语义分析：查类型匹配、函数参数个数、隐式转换是否合法。
  • 中间表示与优化：转成 GIMPLE / RTL 等中间形式，按优化等级改写。
  • 汇编生成：把中间表示降级为目标 CPU 的汇编指令。
bash
gcc -S main.i -o main.s      # 从预处理结果继续
gcc -S main.c -o main.s      # 从源码直接到汇编，跳过 -E 手动步骤

-S 的停止点是汇编文本，产物 .s 仍然是纯文本，能读。

看一眼生成的汇编 #

bash
gcc -S -O2 -fverbose-asm main.c -o main.s
cat main.s

x86-64 下 main 附近大致长这样：

text
main:
.LFB0:
	.cfi_startproc
	subq	$8, %rsp
	movl	$.LC0, %edi
	call	puts
	xorl	%eax, %eax
	addq	$8, %rsp
	ret
	.cfi_endproc

printf("hello\n") 被优化成 puts，return 0 变成 xorl %eax, %eax。.cfi_* 是调用帧信息，供调试器与异常展开用。

-fverbose-asm 会在每行汇编前加注释，标出这条指令对应哪个 C 变量，读起来省力。默认是 AT&T 语法（源操作数在前），换 Intel 语法：

bash
gcc -S -masm=intel main.c -o main_intel.s

中间表示留在哪 #

想看编译器内部怎么想，让它把中间表示倒出来：

bash
gcc -fdump-tree-original main.c      # 最原始的一棵 GIMPLE 树
gcc -fdump-tree-gimple main.c        # 规范化之后的 GIMPLE
gcc -fdump-tree-optimized main.c     # 优化完的最终形态
gcc -fdump-rtl-expand main.c         # RTL 展开阶段

每个选项会在当前目录生成一个 main.c.<序号>t.<阶段> 文件。这类 dump 是排查「代码被优化没了」「常量折叠算错了」的第一手材料。

C++ 下用 g++ -fdump-class-hierarchy -c main.cpp 专看类布局：类的内存偏移、vptr 位置、虚函数表里的符号顺序，诊断多重继承的地址重叠时用得着。

五、汇编：从汇编到目标文件 #

汇编器 as 干三件事，把文本变成二进制：

  • 指令转换：mov、push、add、call 这些助记符翻成对应的机器码字节。
  • 切段：代码进 .text，已初始化全局变量进 .data，未初始化全局变量进 .bss，字符串常量进 .rodata。
  • 记符号：把本文件定义的全局符号记进符号表，把引用了但没定义的符号标成未解析，留给链接器。
bash
gcc -c main.s -o main.o      # 从汇编文件继续
gcc -c main.c -o main.o      # 从源码直接到目标文件
as main.s -o main.o          # 绕过驱动，直接调汇编器

-c 的停止点是目标文件，不链接。产物 .o 是 ELF 可重定位文件（ET_REL），直接执行会报 cannot execute binary file。

目标文件里有什么 #

bash
readelf -h main.o            # ELF 头，看 Type: REL
readelf -S main.o            # 段表

text
[Nr] Name              Type             Address           Offset
 [ 1] .text             PROGBITS         0000000000000000  00000040
 [ 2] .rela.text        RELA             0000000000000000  000001a8
 [ 4] .bss              NOBITS           0000000000000000  00000074
 [ 7] .symtab           SYMTAB           0000000000000000  000000b0

段落含义：

段 内容 是否占文件空间
.text 机器指令 是
.rodata 只读常量、字符串字面量 是
.data 有初值的全局 / 静态变量 是
.bss 无初值的全局 / 静态变量 否，运行时清零
.rela.text 重定位表，记录哪些位置待填地址 是
.symtab 符号表 是
.comment 编译器版本字符串 是

.bss 是 NOBITS 类型，只记大小不占文件体积，所以全局数组 int buf[1<<20]; 不加初值时 .o 不会变大。

反汇编与符号 #

bash
objdump -d main.o            # 反汇编 .text
objdump -dr main.o           # 带重定位信息，能看到待填的地址槽
nm main.o                    # 符号表
size main.o                  # 各段字节数

nm 输出的符号类型是关键信息：

标记 含义
T / t 在 .text 里定义（大写全局，小写局部）
D / d 在 .data 里定义
B / b 在 .bss 里定义
R / r 在 .rodata 里定义
U 未定义，本文件引用、别处定义
W / w 弱符号

main.o 里会看到一个 U puts——printf 已经被优化成 puts，但这个地址还是空的。填这个洞是链接器的工作。

直接改汇编再汇编 #

因为 .s 是文本，可以手改。这是验证「汇编就是机器码的文本形式」最直接的办法：

bash
gcc -S main.c -o main.s
sed -i 's/hello/HELLO/' main.s   # 改字符串常量
gcc -c main.s -o main_mod.o
gcc main_mod.o -o app_mod && ./app_mod

打印出来的就是 HELLO。同理，纯汇编源文件 .s 可以直接交给 gcc，驱动会认扩展名并只走汇编与链接两步：

bash
gcc -c start.s -o start.o

六、链接：把目标文件拼成程序 #

链接器 ld 收一堆 .o 和库，产出可执行文件。三件事：

  • 段合并与地址分配：把各 .o 的 .text 拼成一个 .text，.data 拼成一个 .data，再按链接脚本给每段分配虚拟地址。
  • 符号解析：每个 U 符号都要在别处找到一个定义，且只能有一个强定义。
  • 重定位：把那些留空的地址槽按最终地址填上，或用相对偏移算好。
bash
gcc main.o -o app            # 驱动调 collect2，collect2 再调 ld
ld main.o -o app             # 直接调 ld，会因为缺启动文件而失败

第二条会失败，报 undefined reference to '_start' 之类。因为 gcc 帮你做了很多默认动作：加启动文件 crt1.o、crti.o、crtn.o，加 -lc，加动态链接器路径，加默认链接脚本。ld 原样调用什么都不带。

看 gcc 把哪些东西喂给了 ld：

bash
gcc -v main.o -o app 2>&1 | grep 'collect2\|/ld '

text
/usr/bin/ld -pie --dynamic-linker /lib64/ld-linux-x86-64.so.2 \
  -o app /usr/lib/x86_64-linux-gnu/Scrt1.o /usr/lib/x86_64-linux-gnu/crti.o \
  /usr/lib/gcc/x86_64-linux-gnu/11/crtbeginS.o \
  main.o -lgcc --as-needed -lgcc_s --no-as-needed -lc -lgcc \
  /usr/lib/gcc/x86_64-linux-gnu/11/crtendS.o /usr/lib/x86_64-linux-gnu/crtn.o

顺序有意义：Scrt1.o 在前提供 _start，crtn.o 在后收尾，main.o 夹在中间，-lc 在最后。

缺一个 .o 会怎样 #

两个文件，一个定义、一个调用：

c
/* utils.c */
int add(int a, int b) { return a + b; }

/* main.c */
#include <stdio.h>
int add(int a, int b);
int main(void) {
    printf("%d\n", add(2, 3));
    return 0;
}

只编 main.c 就链接：

bash
gcc -c main.c -o main.o
gcc main.o -o app

text
main.o: In function `main':
main.c:(.text+0x12): undefined reference to `add'
collect2: error: ld returned 1 exit status

把两个都给他就好了：

bash
gcc main.c utils.c -o app

预处理、编译、汇编三步都过了，错误在第四步。main.c 里那句 int add(int, int); 是声明，只管语法，链接器要的是定义。

库的搜索顺序 #

-l 的解析是单向的，从左往右扫。被依赖的库必须写在依赖它的库后面：

bash
gcc main.o -lfoo -lbar -o app     # 对：foo 依赖 bar
gcc main.o -lbar -lfoo -o app     # 错：扫到 foo 时 bar 已经扫过了

静态库重复扫描可以靠 -Wl,--start-group ... -Wl,--end-group 兜底，但正确写法还是排好顺序。

-L 指定库目录，-l 指定库名，命名约定是固定的：

库文件名 链接写法 类型
libhelper.a -lhelper 静态库
libhelper.so -lhelper 动态库

同名两者都在时，默认选 .so。强制静态加 -static 或 -Wl,-Bstatic。完整写法是 gcc main.o -L./lib -lhelper -o app。

静态链接、动态链接与裸链接 #

bash
gcc main.o -o app                        # 默认：动态链接 libc
gcc main.o -static -o app_static         # 全静态，产物大、可移植
gcc -shared -fPIC util.o -o libutil.so   # 生成动态库
ldd app                                  # 运行时依赖，not found 说明路径没配对

不链标准库的三个开关，裸机与内核开发用：-nostdlib 不链启动文件也不链任何标准库；-nodefaultlibs 保留启动文件但不自动链 libc 与 libgcc；-nolibc 不链 C 标准库，其余依赖照链。

链接期的 C++ 专属错误 #

C++ 项目常见一类只在链接期冒出来的错：

text
undefined reference to `vtable for MyClass'

原因在「关键函数」（key function）规则：一个类只要有虚函数，编译器就要为它生成虚函数表，而这张表默认生成在该类第一个非内联虚函数的定义所在的编译单元里。

头文件里声明了虚析构函数，.cpp 里忘了写函数体，编译器就找不到该在哪输出 vtable，于是报这个错。修法：

cpp
// myclass.h
class MyClass {
public:
    virtual ~MyClass();      // 只声明
    virtual void run();
};

// myclass.cpp — 必须给出定义，哪怕函数体是空的
MyClass::~MyClass() {}
void MyClass::run() {}

检查顺序：先看所有虚函数是否都有定义，再看虚析构函数是否漏了。空函数体也得写，~MyClass() {} 这五个字符能救一个下午。

七、一步到位与分步执行 #

一条命令和四条命令，做的事完全一样：

bash
# 一条
gcc main.c -o app

# 四条，逐步验证
gcc -E main.c -o main.i
gcc -S main.i -o main.s
gcc -c main.s -o main.o
gcc main.o -o app

分步的价值在于每步都能停下来看、能只重跑一部分。工程上的增量编译就是这个思路：头文件没动、源码没动，.o 就不用重生成。

想一条命令跑完又想把中间产物留下来，用 -save-temps：

bash
gcc -save-temps main.c -o app     # 当前目录留下 main.i / main.s / main.o
gcc -save-temps=obj main.c -o app # 中间文件跟着输出目录走

各阶段停止选项汇总，这张表直接背：

想要的东西 命令 产物
预处理结果 gcc -E main.c -o main.i main.i 文本
汇编代码 gcc -S main.c -o main.s main.s 文本
目标文件 gcc -c main.c -o main.o main.o ELF
可执行文件 gcc main.c -o app app
中间产物全留 gcc -save-temps main.c -o app 全部
只查语法不产出 gcc -fsyntax-only main.c 无

-fsyntax-only 只做词法、语法、语义检查，不生成任何文件，改完代码想快速确认没写错时用它，比完整编译快一个数量级。

输入文件的扩展名决定 gcc 从哪个阶段进入：

扩展名 进入阶段 处理方式
.c 预处理 C 源码
.i 编译 已预处理 C
.ii 编译 已预处理 C++
.s 汇编 汇编源码
.S 预处理 带预处理指令的汇编
.o 链接 目标文件
.a / .so 链接 库

所以 gcc main.o utils.o -o app 只跑链接一步，gcc main.i -o app 从编译开始跑三步。

八、常用选项：-c、-o、-I、-L #

把高频选项按作用归类。这张表可以贴在显示器边上：

选项 作用阶段 说明 示例
-c 汇编后停 只生成 .o，不链接 gcc -c main.c
-o FILE 全程 指定输出文件名 gcc main.c -o app
-E 预处理后停 输出到 stdout 或 -o gcc -E main.c
-S 编译后停 生成 .s gcc -S main.c
-I DIR 预处理 追加头文件搜索目录 gcc -I./include
-L DIR 链接 追加库搜索目录 gcc -L./lib
-l NAME 链接 链接 libNAME.so/.a gcc -lhelper
-D M[=V] 预处理 定义宏 gcc -DDEBUG
-U M 预处理 取消宏 gcc -UDEBUG
-g 编译 生成调试信息 gcc -g main.c
-O N 编译 优化等级 gcc -O2 main.c
-std= 编译 指定语言标准 gcc -std=c11
-w 编译 关闭所有警告 gcc -w main.c
-Wall 编译 开启常用警告 gcc -Wall main.c
-Werror 编译 警告当错误 gcc -Werror main.c
-shared 链接 生成共享库 gcc -shared -fPIC
-static 链接 禁止动态链接 gcc -static main.c
-ansi 编译 等价 -std=c89，并关掉 GNU 扩展 gcc -ansi main.c
-m486 编译 针对 486 生成代码（历史选项） 现代用 -march=
-pthread 编译+链接 开线程支持并链 pthread gcc -pthread t.c
-v 全程 打印版本与子命令 gcc -v main.c
-fPIC 编译 位置无关代码，做 .so 必需 gcc -fPIC -c a.c

几条容易被忽略的细节。

-o 不给时用默认名，各阶段不同：

bash
gcc main.c        # 无 -o：输出 a.out
gcc -c main.c     # 无 -o：输出 main.o
gcc -S main.c     # 无 -o：输出 main.s

-c 与 -o 一起用且一次给多个源文件时会报错，因为 -o 只能指一个输出：

bash
gcc -c a.c b.c          # 对：生成 a.o b.o
gcc -c a.c b.c -o x.o   # 错：fatal error: cannot specify -o with -c with multiple files

-l 与 -L 分开写，-l 后面不能有空格：

bash
gcc main.o -L./lib -lhelper -o app   # 对
gcc main.o -L./lib -l helper -o app  # 错

-ansi 是老写法，等价于 -std=c89 并加上 -pedantic 的效果，会禁掉 asm、typeof 这类 GNU 扩展。新代码用 -std=，原因见第十二章。

想给链接器或汇编器直传参数，用透传开关：

bash
gcc main.o -Wl,-Map=app.map -o app    # -Wl, 后面给 ld
gcc -Wa,-alh main.c -o app            # -Wa, 后面给 as

map 文件记录了每个符号最终落在哪个地址、来自哪个 .o，定位「符号被谁占了」时好用。

九、警告与诊断：-Wall、-Wextra #

GCC 默认只报最明显的问题，想让它说实话得自己开口。

选项 作用
-Wall 打开绝大多数常用警告，包括未使用变量、未初始化、隐式函数声明
-Wextra 补充 -Wall 未覆盖的项，含未使用参数、符号比较、空语句体
-Werror 所有警告升级为错误，编译直接失败
-w 关掉所有警告
-Wno-NAME 单独关掉某个警告
-Wpedantic 严格按标准挑刺，报所有非标准扩展
-Wshadow 局部变量遮蔽外层同名变量时告警
-Wconversion 隐式类型转换会改变值时告警
-Wformat=2 严格的 printf 格式串检查，含非字面量格式串
-Wcast-align 指针强转导致对齐要求提高时告警

一段有毛病的代码，看默认与开全的区别：

c
/* warn.c */
#include <stdio.h>

int calc(int a, int b) {
    int tmp;
    if (a > b) {
        tmp = a - b;
    }
    return tmp;          /* b >= a 时返回未初始化值 */
}

int main(void) {
    int unused = 42;
    printf("%d\n", calc(1, 2));
}

bash
gcc warn.c -o warn
gcc -Wall -Wextra warn.c -o warn

第二条会吐出：

text
warn.c: In function 'calc':
warn.c:5:9: warning: 'tmp' may be used uninitialized [-Wmaybe-uninitialized]
warn.c: In function 'main':
warn.c:13:9: warning: unused variable 'unused' [-Wunused-variable]
warn.c:4:16: warning: unused parameter 'b' [-Wunused-parameter]

注意第三行：-Wunused-parameter 只有加了 -Wextra 才报，单 -Wall 是看不到的。

警告要当错误用 #

bash
gcc -Wall -Wextra -Werror main.c -o app

加上 -Werror 后，任何一条 warning 都会折断构建。新项目建议一开始就开，代码量上去之后再补的代价是几百条噪音。老项目用 -Wno-error=NAME 局部豁免：

bash
gcc -Wall -Wextra -Werror -Wno-error=unused-parameter main.c -o app

-Wno-error=xxx 把某一类降回 warning，其余仍是 error。

消除无用参数告警 #

c
void handler(int sig) {
    (void)sig;    /* 显式声明知道它存在，就是不用 */
}

(void)xxx; 是标准做法，比 #pragma 和 __attribute__((unused)) 更可移植。

改完代码想快速确认没写错，用 gcc -fsyntax-only -Wall -Wextra main.c：不出文件，只查错，放进编辑器的保存钩子里比等整个工程编完再发现少个分号舒服。

十、调试信息：-g 与符号表 #

-g 让编译器把源文件名、行号映射、变量名、类型定义写进产物，格式是 DWARF。

bash
gcc -g main.c -o app_debug
gcc -g -O2 main.c -o app_rel      # 优化与调试信息共存，行号会跳
gcc -g0 main.c -o app             # 显式关闭
gcc -ggdb main.c -o app           # 生成 GDB 专用的扩展调试信息
gcc -gdwarf-4 -g main.c -o app    # 指定 DWARF 版本，兼容老 gdb

编译和链接两步都要带 -g，只给编译步的话链接器会把调试段丢掉。

代价是体积，size app app_debug 一比就知道。带 -g 的产物比不带的大三到五倍是常态。调试段不占内存，只占磁盘，但生产环境还是该剥。

bash
strip app_debug -o app_stripped
strip --strip-debug app_debug
readelf -S app_debug | grep debug      # 剥之前能看到 .debug_info 等段

想连注释段和 ABI 标记一起擦，用 objcopy 精确删除：

bash
objcopy --remove-section=.comment --remove-section=.note.ABI-tag app app_slim

.comment 存编译器版本字符串，.note.ABI-tag 存内核 ABI 兼容标记，两个都在运行时用不上。

调试信息和二进制分离，保留排障能力又不动发布体：objcopy --only-keep-debug app app.debug 抽出调试段，objcopy --strip-debug 剥干净发布件，objcopy --add-gnu-debuglink=app.debug 把两者挂上钩。

用符号做源码级调试和反汇编 #

bash
gdb ./app_debug           # break main / run / bt / info locals
objdump -S app_debug      # 反汇编与源码交错打印，前提是带 -g

没有 -g 也能下断点，但 bt 只能给你地址，看不到函数名和行号。读优化后的汇编对不上号时，用 -O0 -g 重新编一份对照。

十一、优化等级：-O0 到 -O3 #

等级 含义 编译速度 运行速度 调试体验 适用
-O0 不优化，默认 最快 最慢 与源码逐行对应 开发期、单步调试
-O1 基础优化 快 提升明显 大致可跟 编译时间敏感
-O2 生产标配 中 好 变量会被优化掉 发布构建
-O3 激进优化 慢 多数更快 难跟 计算密集循环
-Os 优化体积 中 略慢于 -O2 一般 嵌入式、固件
-Ofast 牺牲标准换速度 慢 快 难跟 数值计算

-O2 在生产环境是安全区。-O3 在 -O2 基础上再加函数内联、循环向量化，代码体积上去，少数复杂指针场景下的语义也会变，上生产前要跑基准测试。

-Ofast 会打开 -ffast-math，允许违反 IEEE-754，浮点结果和 -O2 对不上。做数值比对的项目不能用。

优化等级是子开关的组合 #

每个 -O 等级只是按预设打开一批 -f 开关：

子开关 由哪级开启 做什么
-fdefer-pop -O1 推迟函数调用后的栈清理，合并多余指令
-fthread-jumps -O1 跳转指向跳转时直连最终目标，省一次中间跳
-fomit-frame-pointer -O2 释放 %rbp 当通用寄存器，省入栈出栈
-fstrict-aliasing -O2 假设不同类型指针不指向同一地址，放开寄存器装载
-finline-functions -O3 小函数直接内联展开，消掉调用开销
-ftree-vectorize -O3 无依赖循环转成 SIMD 指令并行计算

-fomit-frame-pointer 有个副作用：GDB 的 bt 在部分帧上会断链。调试构建加 -fno-omit-frame-pointer 补回来。

反过来也可以单独开关：gcc -O2 -fno-strict-aliasing main.c（老代码类型双关多，先关掉它）、gcc -O2 -fno-inline main.c（保留调用边界，方便打桩）。

链接期优化 #

单文件优化看不到别的编译单元。-flto 把优化推迟到链接阶段，跨模块做内联和死代码消除：

bash
gcc -flto -O2 main.c utils.c -o app_lto

编译与链接两步都要带 -flto，否则链接器拿到的还是普通机器码。实测体积能缩 10%~20%，热点路径有 5%~15% 的提升，代价是链接变慢、nm 里符号变少。

度量编译本身 #

bash
gcc -time main.c -o app        # 打印预处理/编译/汇编/链接各步耗时
gcc -Q -O2 main.c -o app       # 逐函数打印名字与编译耗时
gcc -fstack-usage -c main.c    # 生成 main.su，记录每个函数的栈帧字节数

-fstack-usage 的产物是纯文本，一行一个函数（main.c:5:5:main 16 static），后面那个数字就是栈帧字节数，嵌入式项目拿它卡栈深度上限。

-O3 反而更慢的情况 #

-O3 的循环展开会让指令体积膨胀，超出 L1/L2 指令缓存容量，I-Cache 未命中率上升，实测反而慢。做法是拿 perf 在关键路径上对比：

bash
perf stat -e instructions,cycles,cache-misses ./app_O2
perf stat -e instructions,cycles,cache-misses ./app_O3

热点函数单独降级比全局降级划算：

c
__attribute__((optimize("O2")))
void hot_path(void) { /* 这段别用 O3 */ }

十二、标准与语言特性：-std= #

不指定时，GCC 用自己的默认标准，且这个默认值随版本变：GCC 11 起默认 gnu17，更早的版本是 gnu11 或 gnu89。同一份代码在不同机器上编出不同结果，多半就是这里。

显式指定：

bash
gcc -std=c11 main.c -o app
gcc -std=gnu11 main.c -o app      # c11 + GNU 扩展，Linux 项目常用
gcc -std=c17 -pedantic main.c -o app
g++ -std=c++17 main.cpp -o app
g++ -std=c++20 main.cpp -o app
写法 含义
-std=c89 / -std=c90 经典 C，变量必须声明在块首
-std=c99 加 // 注释、for 内声明、变长数组、stdint.h
-std=c11 加 _Static_assert、匿名结构体、_Generic
-std=c17 C11 的修订版，修 bug 为主
-std=c2x 下一代草案，typeof、constexpr 等
-std=gnu89 … -std=gnu17 对应 C 标准 + GNU 扩展
-std=c++11/14/17/20/23 C++ 各版本
-ansi 等价 -std=c89，并关掉 GNU 扩展

-std=c11 与 -std=gnu11 的差别在扩展：typeof、asm、语句表达式、零长数组这些在 c11 下会报 error: implicit declaration 或 warning: ISO C forbids ...。内核代码、驱动代码离不开 GNU 扩展，只能选 gnu*。

-pedantic 让编译器按标准逐条挑刺，-pedantic-errors 把这些挑刺变成错误：

bash
gcc -std=c11 -pedantic -Wall main.c -o app

版本不支持的 -std 会直接报错，形如 error: unrecognized command line option '-std=c++20'; did you mean '-std=c++11'?。

看当前编译器认识哪些标准：gcc -std=foo main.c 2>&1 | grep -o 'c++[0-9a-z]*' | sort -u。

C 与 C++ 混编时还有一件事：C++ 会做名字修饰（name mangling），int add(int, int) 编出来的符号是 _Z3addii，C 编译器给的是 add。头文件里必须包一层：

c
#ifdef __cplusplus
extern "C" {
#endif

int add(int a, int b);

#ifdef __cplusplus
}
#endif

漏了这层，链接期就是 undefined reference to 'add(int, int)'。

十三、多文件工程的编译 #

工程一上多文件，编法就三种。假设布局是 include/util.h、src/main.c、src/util.c。

bash
# 1. 一把梭：所有 .c 交给 gcc，内部逐个编译再统一链接
gcc -I./include src/main.c src/util.c -o app

# 2. 分步：每个源文件单独成 .o，再链接
gcc -I./include -c src/main.c -o main.o
gcc -I./include -c src/util.c -o util.o
gcc main.o util.o -o app

# 3. 只改了 util.c：只重编 util.o，再重链
gcc -I./include -c src/util.c -o util.o && gcc main.o util.o -o app
方式 命令 适合
一把梭 gcc -I./include src/*.c -o app 验证、脚本级小程序
分步 gcc -c 各文件 + gcc *.o 多文件工程、增量编译
构建工具 make / cmake 依赖复杂、要自动化

跨编译单元的四条规矩：

  • 函数与全局变量在头文件里用 extern 声明，在且仅在一个 .c 里定义。
  • 只在本文件用的函数加 static，不导出符号，也不会与别处同名函数打架。
  • 头文件加 include guard（#ifndef / #define / #endif）或 #pragma once。
  • .o 的先后无所谓，库的位置有所谓，被依赖的库放后面。

把这些串成自动化，看《Makefile 与构建自动化》。

十四、常见编译错误与排错 #

报错 阶段 原因 修法
fatal error: xxx.h: No such file or directory 预处理 头文件不在当前目录也不在系统路径 加 -I./include，或改 #include 的写法
expected identifier or '(' before '{' token 编译 结构体或函数声明末尾漏分号，宏展开破坏了语法 检查刚改过的头文件，补齐 ;
variable-sized object may not be initialized 编译 变长数组声明时用 {0} 初始化 先声明，再用 memset() 清零
cast from 'void*' to 'int' loses precision 编译 64 位下指针 8 字节、int 4 字节，地址高位被截 转成 uintptr_t 或 long 再接整型
control reaches end of non-void function 编译 有返回值的函数存在没写 return 的分支 补全分支，或末尾加兜底 return
undefined reference to 'xxx' 链接 只有声明没有定义，或漏了 .o / -l 补上源文件，或加 -L 与 -l
multiple definition of 'xxx' 链接 头文件里写了变量定义，被多个编译单元包含 头文件改 extern，C++17 可用 inline
unrecognized command line option '-std=c++20' 命令行 编译器版本不认这个参数 降标准，或升级工具链

排查顺序，从便宜的到贵的：

bash
gcc -fsyntax-only -Wall -Wextra main.c   # 只查语法语义，不出文件
gcc -v main.c -o app                     # 看驱动到底调了哪些子程序
gcc -E main.c | less                     # 宏展开成了什么样
nm main.o | grep ' U '                   # 哪些符号还没找到定义

multiple definition 的正解只有一套：

cpp
extern int global_val;     // global.h：只声明，不占空间
int global_val = 10;       // once.cpp：唯一定义，只此一份

十五、易错点速查 #

写法 出什么问题 怎么改
gcc -c a.c b.c -o x.o 多个源文件配一个 -o，直接报错 分开编，或用 -save-temps 查产物
gcc -l helper -l 与库名之间有空格，被当成文件 写成 -lhelper，不留空格
gcc main.o -lbar -lfoo 被依赖的库排前面，扫过了不再回头 把 -lfoo 放到 -lbar 前面
只编 main.c 就链接 别的 .c 里的函数没有定义 把所有 .c 一起编，或先编成 .o
只在链接步加 -g 调试段没生成，bt 只有地址 编译步也加 -g，两步都带
gcc -shared util.o .o 不是位置无关代码，加载时报错 编译时加 -fPIC
gcc main.o -o app（C++ 目标文件） 一堆 std:: 符号未定义 改用 g++，或补 -lstdc++
改了 .h 只重编 .c 依赖它的 .o 用了旧结构体布局 用 -MM 生成依赖，让构建系统重编
-O2 下单步调试 变量被优化进寄存器，print x 报没有该符号 调试用 -O0 -g
C/C++ 混编不写 extern "C" 链接期符号名对不上，报 undefined reference 头文件里包 #ifdef __cplusplus

四阶段、停止选项、常用开关这三张表记熟，编译器出错时就知道该停在哪一步看。到这一步，.c 到可执行文件的路已经走通。
