一、手写 Makefile 的困境 #

先说结论：Makefile 不是写不出来，是维护不住。一个真实的中等项目，三个子目录、四十来个源文件、依赖两个第三方库。开头手写出来是这样的：

makefile
CC      := gcc
CFLAGS  := -O2 -Wall -Iinclude -Isrc/core -Isrc/net
LDFLAGS := -L/opt/foo/lib
LDLIBS  := -lfoo -lpthread -lm

SRCS := $(wildcard src/*.c) $(wildcard src/core/*.c) $(wildcard src/net/*.c)
OBJS := $(SRCS:.c=.o)

app: $(OBJS)
	$(CC) $(OBJS) -o $@ $(LDFLAGS) $(LDLIBS)

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

这段代码能跑。问题从第二个星期开始显现：头文件依赖是断的——%.o: %.c 只认 .c 不认 .h，你改了 include/core.h 里一个结构体字段，make 回你一句 make: 'app' is up to date.，得补 -MMD -MP 生成 .d 文件、再用 -include $(OBJS:.o=.d) 接回来。加库要动 LDFLAGS 的顺序——GNU ld 单趟扫描，-lfoo 写在使用它的目标文件前面就报 undefined reference，依赖一深就出现 -la -lb -la 这种回环写法。

换平台等于重写——Windows 上 cl.exe 的 -Wall 变 /W3、-o 变 /Fe、-I 变 /I，想同时喂 gcc 和 cl 就得两套变量加一堆 ifeq ($(OS),Windows_NT)；Debug / Release / RelWithDebInfo 三套 flag 再乘上 sanitizer、乘上 LTO，ifeq 就套到三层。递归 make 的并行是假的——顶层 $(MAKE) -C src 一个个进子目录，-j8 只在子目录内部生效，子目录之间的依赖顶层并不知道。第三方库全靠手工探测——想用 zlib 得自己判断头文件在 /usr/include 还是 /usr/local/include、库是 libz.a 还是 libz.so，再手写 -I -L -lz，换台机器路径一变又得改。把这些需求列成一张表，手写方案的代价一眼就看出来了：

需求 手写 Makefile 的做法 失效方式
头文件依赖 -MMD -MP + -include *.d 忘加 -MP，删掉头文件后报 No rule to make target
多配置 三套 CFLAGS_DEBUG / CFLAGS_RELEASE + ifeq 漏一个变量，Release 里混进 -g
跨平台 ifeq ($(OS),Windows_NT) 分支 分支只有两台机器验证过，第三台崩
找库 手写 -I -L -l 路径写死，迁移到别的发行版就断
并行 顶层逐个 $(MAKE) 子目录之间无依赖，-j 只在小范围内生效
单元测试 手写 test: 目标和测试脚本 没法和编译共享同一套 flag
安装 手写 install: 加 install -m 644 路径前缀写死，DESTDIR 打包要另写

这些不是 Make 的错。Make 的职责是「照着一份依赖图，把该跑的命令跑起来」，它做得很好。让它同时承担「探测编译器、搜索第三方库、按平台生成图」的活，是超纲。

二、构建系统与构建系统生成器 #

核心就一句：CMake 不编译任何东西。它读 CMakeLists.txt，吐出一份 Makefile 或者 build.ninja。真正调用 gcc -c 的是 Make 或 Ninja。

text
CMakeLists.txt ──┐
                 ├──► cmake (configure) ──► Makefile / build.ninja ──► make / ninja ──► gcc / as / ld ──► app
meson.build    ──┘       生成器               生成物（不手改）          执行器

从上图能切出三种角色，分清楚这三个词，后面一切顺：

层次 名字 代表 输入 输出
生成器层 build system generator CMake、Meson、Autotools、Premake、GYP CMakeLists.txt、meson.build、configure.ac Makefile、build.ninja、.vcxproj、.sln
执行器层 build system Make、Ninja、MSBuild、bjam Makefile、build.ninja .o、.a、.so、可执行文件
工具层 compiler / linker gcc、clang、cl.exe、ld、lld 源文件 目标文件、最终产物

CMake 这一层里还分两个阶段，这两个阶段是理解它的前提：

阶段 命令 干什么 慢不慢
configure（配置） cmake -S . -B build 探测编译器、试编译、找库、展开变量、算依赖图 慢，几秒到几十秒
generate（生成） 同上，configure 末尾自动做 把内存里的模型写成 Makefile / build.ninja 快
build（构建） cmake --build build 交给执行器，只编译改过的文件 按改动量

configure 只跑一次，build 跑几百次——这就是两段式划得来的地方。三个实际好处：依赖图在配置阶段就摊平了，Ninja 拿到的是一张扁平的静态 DAG，构建时不解析规则、不求值字符串，这是它比 Make 快的原因；换后端只改一个参数，同一份 CMakeLists.txt 在 Linux 上 -G Ninja 出 build.ninja、-G "Unix Makefiles" 出 Makefile、在 Windows 上 -G "Visual Studio 17 2022" 出 .sln，IDE 直接打开就能调试；平台差异集中到一处，if(WIN32) / if(APPLE) / if(CMAKE_SYSTEM_NAME STREQUAL "Linux") 写在配置里，执行层的 Makefile 不需要知道自己在哪个系统上跑。

out-of-source：构建必须在源码目录之外 #

第二个必须建立的习惯：所有生成物都落在独立的 build/ 里。

text
myproj/
├── CMakeLists.txt
├── include/demo.h
├── src/main.c
└── build/              ← 全部生成物在这里（CMakeCache.txt、CMakeFiles/、Makefile、bin/）

bash
cmake -S . -B build
cmake --build build -j8

四条理由，每条都踩过坑。源码目录保持干净：git status 不会冒出两百个 .o 和一堆 CMakeFiles/，.gitignore 只写一行 build/。rm -rf build 就是彻底 clean：Makefile 里的 clean 目标经常漏东西，生成的 moc 文件、qm 文件、配置头文件，写 clean 的人自己都记不全。

一份源码可以并存多个构建目录：build-debug、build-release、build-arm64 各有独立的 CMakeCache.txt，随时切换。in-source 构建会把自己锁死：缓存里写死了编译器路径和所有变量值，你改工具链、改 build type，CMake 直接拒绝。

text
CMake Error: The current CMakeCache.txt directory
  /home/you/myproj/CMakeCache.txt
is different than the directory /home/you/myproj/build
where CMakeCache.txt was created.

遇到这个报错，唯一解法是删掉缓存重配。老写法 mkdir build && cd build && cmake .. 和 cmake -S . -B build 完全等价，后者少两次 cd，脚本里更好写。

三、CMake 是什么 #

一句话：跨平台的构建系统生成器，用 CMake 自己的脚本语言描述工程，输出各家后端能吃的构建文件。

命令名大小写不敏感（add_executable 和 ADD_EXECUTABLE 一样），参数和变量名大小写敏感。所有值都是字符串，set(N 42) 里的 42 是 "42"，算数要走 math(EXPR)。列表是分号分隔的字符串，set(SRCS a.c b.c) 存的是 "a.c;b.c"，${SRCS} 展开后按分号拆成多个参数——所以 set(SRCS "a.c b.c") 是一个带空格的单元素列表，不是两个。

if() 自带真假值规则：if(VAR) 判断值本身（空、0、OFF、NO、FALSE、NOTFOUND 为假），if(${VAR}) 是把值展开成参数再判断，VAR 为空时这行退化成 if()，行为完全不同。判空用 if(NOT VAR) 或 if("${VAR}" STREQUAL "")。进入工程后还会看到这些文件，各自的身份如下：

路径 是什么 能动吗
CMakeLists.txt 你写的输入，唯一的真相来源 要改的就是它
build/CMakeCache.txt 配置结果缓存：编译器路径、所有 CACHE 变量 不手改，要改就 -D 或删缓存
build/CMakeFiles/ 内部脚本、编译器探测结果、.d 依赖文件 不看
build/cmake_install.cmake cmake --install 执行的安装脚本 不看
build/Makefile、build/build.ninja 生成物 绝不手改，下次 configure 直接覆盖
CMakePresets.json 预设的 configure / build 参数组合 该写

命令行这一层，常用的就十来条：

命令 作用
cmake -S . -B build 配置，源码在 .，构建在 build
cmake -S . -B build -G Ninja 指定生成器（默认 Unix Makefiles，Windows 上是 VS）
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release 指定构建类型，覆盖脚本里的默认值
cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=toolchain.cmake 交叉编译入口
cmake -S . -B build -DCMAKE_INSTALL_PREFIX=/usr 指定安装前缀
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON 导出 compile_commands.json，给 clangd 用
cmake --build build -j8 构建，等价于在 build 里 make -j8
cmake --build build --target clean 只删产物，保留配置
cmake --build build --target demo 只构建一个 target
cmake --install build --prefix /tmp/stage 安装，--prefix 覆盖 CMAKE_INSTALL_PREFIX
ctest --test-dir build 跑测试
cmake -LAH -N build 列出所有缓存变量及其帮助文本

生成器选哪个直接决定后端：

生成器（-G） 平台 后端产物
Unix Makefiles Linux / macOS / MSYS Makefile
Ninja 全平台 build.ninja
Ninja Multi-Config 全平台 一份配置出多个 build type，不用换目录
MinGW Makefiles Windows + MinGW Makefile（cmd 下能跑）
MSYS Makefiles Windows + MSYS2 Makefile（需要 MSYS shell）
NMake Makefiles Windows + MSVC Makefile（nmake 执行）
NMake Makefiles JOM Windows + Qt Makefile（jom 并行执行）
Visual Studio 17 2022 Windows + MSVC .sln + .vcxproj
Xcode macOS .xcodeproj
Watcom WMake、Borland Makefiles、Green Hills MULTI 老工具链 各自的 makefile

VS 生成器还要带架构，用 -A 指定：Win32、x64、ARM、ARM64。工具链版本用 -T。三个参数一起写就是：

bash
cmake -G"Visual Studio 16 2019" -A Win32 -Thost=x86 ..

cmake_minimum_required 不只是版本检查，它还决定 CMake 按哪一代的「策略」干活。写 VERSION 3.20 就是把 3.20 之前所有 CMP00xx 策略设成新行为。写低了（比如 2.8），CMake 会按十几年前的行为解析你的脚本，并一路警告。

四、CMakeLists.txt 的基本写法 #

最小可跑的版本是四行：

cmake
cmake_minimum_required(VERSION 3.20)
project(hello LANGUAGES C)
add_executable(hello src/main.c)

bash
cmake -S . -B build
cmake --build build
./build/hello

逐条拆：cmake_minimum_required(VERSION 3.20) 定了版本基线，也定了策略集，加上 FATAL_ERROR 可以在版本不够时直接中断配置（3.0 之后默认就中断，写上是给读代码的人看）。

project(hello VERSION 1.0.0 LANGUAGES C) —— 声明工程名、版本、启用的语言。写了 VERSION 就自动得到 PROJECT_VERSION、PROJECT_VERSION_MAJOR、PROJECT_VERSION_MINOR、PROJECT_VERSION_PATCH、PROJECT_VERSION_TWEAK，以及对应的 CMAKE_PROJECT_VERSION*。LANGUAGES 不写时默认是 C 和 CXX。纯 C 工程写上 LANGUAGES C，CMake 就不会去探测 C++ 编译器，configure 快一点。add_executable(hello src/main.c) 声明一个可执行目标，源文件列在后面。真实工程还要把标准、警告、默认构建类型定下来：

cmake
cmake_minimum_required(VERSION 3.20)
project(hello VERSION 1.0.0 LANGUAGES C CXX)

set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)      # 关掉 gnu++17，用纯 c++17

# 单配置生成器（Makefiles / Ninja）需要显式给 build type
if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
    set(CMAKE_BUILD_TYPE Release CACHE STRING "build type" FORCE)
endif()

add_executable(hello src/main.c src/util.c)
target_compile_options(hello PRIVATE -Wall -Wextra)

CMAKE_CONFIGURATION_TYPES 只在多配置生成器（VS、Xcode、Ninja Multi-Config）里非空。那些生成器不需要 CMAKE_BUILD_TYPE，一份工程同时支持 Debug 和 Release，构建时用 --config 选。

语法上有六条规则值得记。注释用 #，多行注释用 #[[ 开头、]] 结尾。命令名大小写不敏感，参数大小写敏感。参数里有空格、分号、(、)、# 时必须加双引号，路径带空格（Windows 上 C:/Program Files）不加引号会被拆成两个参数。

列表是分号字符串，set(SRCS a.c b.c) 的元素在 ${SRCS} 展开时按分号拆成独立参数，传给 add_executable 正好；想加一项用 list(APPEND SRCS c.c)。变量作用域是「目录 + 函数」，add_subdirectory 会开新作用域，子目录里 set 的普通变量出不来，set(... PARENT_SCOPE) 才能往上抛；CACHE 变量全局可见，写进 CMakeCache.txt。

-D 和脚本里的 set 谁赢？-D 写的是缓存变量，脚本里不带 CACHE 的 set(VAR val) 会在当前目录作用域里把它盖掉。想让 -D 生效，脚本必须写成 set(VAR default CACHE STRING "说明")——这行在变量已存在时不覆盖，默认值让位给 -D。

五、目标：可执行文件与库 #

CMake 的第一公民是 target（目标），不是文件、不是变量。所有属性都挂在 target 上，下游通过 target 名字继承，不靠全局开关。

add_executable 和 add_library 的各种变形：

写法 产物 用途
add_executable(app ...) app / app.exe 控制台程序
add_executable(app WIN32 ...) app.exe，子系统是 GUI 入口必须是 WinMain / wWinMain，写成 main 会链接失败
add_library(foo STATIC ...) libfoo.a / foo.lib 静态库，代码复制进最终产物
add_library(foo SHARED ...) libfoo.so / foo.dll + foo.lib 动态库，运行时加载
add_library(foo MODULE ...) foo.so / foo.dll 插件，不会被 target_link_libraries 链接，只给 dlopen 用
add_library(foo OBJECT ...) 只有 .o，不归档 多个 target 共享一批编译结果，省重复编译
add_library(foo INTERFACE) 无产物 纯头文件库，只携带 usage requirements
add_library(ns::foo ALIAS foo) 无产物 给 target 起个别名，下游统一写 ns::foo

add_library(foo ...) 不带 STATIC / SHARED 时看全局变量 BUILD_SHARED_LIBS：ON 出动态库，OFF（默认）出静态库，set(BUILD_SHARED_LIBS ON) 写在声明之前，影响之后所有的 add_library。改产物属性用 set_target_properties：

cmake
set_target_properties(demo_math PROPERTIES
    OUTPUT_NAME        demo_math        # 改产物文件名，不动 target 名
    DEBUG_POSTFIX      "_d"              # Debug 版加后缀，允许 debug/release 同目录共存
    VERSION            1.2.0             # libdemo_math.so.1.2.0
    SOVERSION          1                 # libdemo_math.so.1 → 上面的软链
    POSITION_INDEPENDENT_CODE ON         # 静态库将来要进 .so 时必须有
)

OUTPUT_NAME 不影响 DEBUG_POSTFIX，两者叠加。给单个 target 加后缀等价于给全局变量加后缀：四个构建类型各有一个（CMAKE_DEBUG_POSTFIX、CMAKE_RELEASE_POSTFIX、CMAKE_MINSIZEREL_POSTFIX、CMAKE_RELWITHDEBINFO_POSTFIX），设一次就够，不用按 target 写。输出目录也按产物类型分三个变量，每个都有 _DEBUG / _RELEASE / _MINSIZEREL / _RELWITHDEBINFO 变体，供多配置生成器把不同配置丢进不同子目录：

cmake
set(CMAKE_RUNTIME_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/bin)  # exe、dll
set(CMAKE_LIBRARY_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/lib)  # so、dylib、module
set(CMAKE_ARCHIVE_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/lib)  # a、lib（静态库的导入库）

text
demo/
├── CMakeLists.txt
├── include/demo/math.h
└── src/
    ├── math.c
    └── main.c

三个源文件，一个 math 库加一个 main：

c
/* include/demo/math.h */
#ifndef DEMO_MATH_H
#define DEMO_MATH_H
int demo_add(int a, int b);
int demo_mul(int a, int b);
#endif

/* src/math.c */
#include "demo/math.h"
int demo_add(int a, int b) { return a + b; }
int demo_mul(int a, int b) { return a * b; }

/* src/main.c */
#include <stdio.h>
#include "demo/math.h"
int main(void) {
    printf("add=%d mul=%d\n", demo_add(2, 3), demo_mul(2, 3));
    return 0;
}

CMakeLists.txt：

cmake
cmake_minimum_required(VERSION 3.20)
project(demo VERSION 1.2.0 LANGUAGES C)
set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)
set(CMAKE_POSITION_INDEPENDENT_CODE ON)
set(CMAKE_RUNTIME_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/bin)
set(CMAKE_LIBRARY_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/lib)
set(CMAKE_ARCHIVE_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/lib)

add_library(demo_math STATIC src/math.c)
target_include_directories(demo_math PUBLIC
    $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
    $<INSTALL_INTERFACE:include>)

add_executable(demo src/main.c)
target_link_libraries(demo PRIVATE demo_math)

install(TARGETS demo demo_math
        RUNTIME DESTINATION bin
        LIBRARY DESTINATION lib
        ARCHIVE DESTINATION lib)
install(DIRECTORY include/ DESTINATION include)

跑起来：

bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j8
./build/bin/demo                      # 输出 add=5 mul=6
cmake --install build --prefix /tmp/stage

装到 /tmp/stage 之后就是 bin/demo、include/demo/math.h、lib/libdemo_math.a 三样。

install 的另外两种形式覆盖剩下的场景：

cmake
install(FILES COPYING README.md DESTINATION share/doc/demo)   # 单个文件
install(DIRECTORY include/ DESTINATION include)               # 整个目录，注意末尾的斜杠

DESTINATION 是相对路径，拼在 CMAKE_INSTALL_PREFIX 后面。默认前缀 Linux 是 /usr/local，Windows 是 C:/Program Files/<项目名>。打包发布时不改前缀，用 GNU 约定的 DESTDIR 重定向：

bash
DESTDIR=/tmp/pkgroot cmake --install build --prefix /usr

MSVC 的运行时 DLL（vcruntime140.dll、msvcp140.dll）默认不会跟着装。要带上的话，在 CMakeLists 里 include 一个模块：

cmake
include(InstallRequiredSystemLibraries)     # 只对 MSVC 生效
set(CMAKE_INSTALL_UCRT_LIBRARIES TRUE)      # 连 UCRT 一起复制
set(CMAKE_INSTALL_MFC_LIBRARIES TRUE)       # 连 MFC 一起复制
set(CMAKE_INSTALL_OPENMP_LIBRARIES TRUE)    # 连 OpenMP 运行时一起复制
set(CMAKE_WINDOWS_KITS_10_DIR "C:/Program Files (x86)/Windows Kits/10")   # 自定义 SDK 路径，非必需
set(CMAKE_INSTALL_SYSTEM_RUNTIME_DESTINATION bin64)                       # 复制到哪，默认 Windows 是 bin

六、头文件路径与库依赖 #

头文件路径和库路径有两套写法：全局的，按 target 的。只用后者。

全局（老写法） 按 target（用这个） 落到命令行是什么
include_directories() target_include_directories() -I
link_directories() target_link_directories() -L
link_libraries() target_link_libraries() -l 和库文件路径
add_compile_options() target_compile_options() 编译 flag
add_compile_definitions() target_compile_definitions() -D
add_link_options() target_link_options() 链接 flag

全局命令的作用域是「从这里往下」。它影响之后声明的所有 target，也影响 add_subdirectory 进来的所有子目录。后果是一个库的内部头文件路径泄漏到整棵依赖树，最后你把所有 target 的 -I 加起来会发现几十条路径。

按 target 的写法要回答一个问题：这份路径是给自己用，还是给下游用。三个关键字：

关键字 编译自己时生效 传给下游 典型用途
PRIVATE 是 不传 内部头文件、警告开关、内部依赖
INTERFACE 不生效 传 纯头文件库里声明的东西
PUBLIC 是 传 公开头文件目录、下游也要用的宏

一句话：PUBLIC = PRIVATE + INTERFACE。

cmake
# 内部实现目录，只有自己编译时可见
target_include_directories(demo_math PRIVATE ${CMAKE_CURRENT_SOURCE_DIR}/src)
# 公开头文件，下游写 #include "demo/math.h" 时用得到
target_include_directories(demo_math PUBLIC ${CMAKE_CURRENT_SOURCE_DIR}/include)
# 警告开关只影响自己
target_compile_options(demo_math PRIVATE -Wall -Wextra)
# 版本宏下游也要用，给 INTERFACE
target_compile_definitions(demo_math INTERFACE DEMO_VERSION="${PROJECT_VERSION}")

判断标准很直接：如果某个 #include 出现在你要交给别人的头文件里，那对应的目录必须是 PUBLIC 或 INTERFACE，否则下游编译时报找不到头文件。链接同理，一行就够：

cmake
target_link_libraries(demo PRIVATE demo_math)

链接顺序不用你操心。target_link_libraries(app PRIVATE a b) 里 a 依赖 b，CMake 生成的构建文件会自己补上重复和顺序，手写 Makefile 那套 -la -lb -la 的循环写法在这里消失了，因为依赖关系是 target 之间的，不是库名字符串。link_directories 尽量别碰：它只是把 -L 塞给链接器，具体链到哪个库要看搜索顺序，机器不同结果不同。要指定具体文件，两条路：

cmake
# 一、直接给完整路径
target_link_libraries(demo PRIVATE /opt/foo/lib/libfoo.so)
# 二、包成 imported target，路径、头文件、依赖一次说清
add_library(foo::foo SHARED IMPORTED)
set_target_properties(foo::foo PROPERTIES
    IMPORTED_LOCATION             /opt/foo/lib/libfoo.so
    INTERFACE_INCLUDE_DIRECTORIES /opt/foo/include)
target_link_libraries(demo PRIVATE foo::foo)

静态库和动态库的文件名不一样（.a / .lib、.so / .dll），imported target 能按平台切换：

cmake
add_library(foo::foo STATIC IMPORTED)
if(WIN32)
    set_target_properties(foo::foo PROPERTIES IMPORTED_LOCATION ${FOO_DIR}/lib/foo.lib)
else()
    set_target_properties(foo::foo PROPERTIES IMPORTED_LOCATION ${FOO_DIR}/lib/libfoo.a)
endif()

最后是 build 和 install 两种语境的路径问题。构建时用源码树里的绝对路径，安装后给别人用时用相对安装前缀的路径，生成器表达式一次写清：

cmake
target_include_directories(demo_math PUBLIC
    "$<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>"   # 构建时：源码树绝对路径
    "$<INSTALL_INTERFACE:include>"                             # 安装后：相对前缀的 include
)

链接期代码生成（LTCG / LTO / IPO）同样能探测，编译不过时不至于让整次配置失败：

cmake
cmake_policy(SET CMP0069 NEW)          # 3.9 以前只给 Linux 上的 ICC 开 IPO
include(CheckIPOSupported)
check_ipo_supported(RESULT ipo_ok OUTPUT ipo_err)
if(ipo_ok)
    set_property(TARGET demo PROPERTY INTERPROCEDURAL_OPTIMIZATION TRUE)
else()
    message(WARNING "IPO is not supported: ${ipo_err}")
endif()

check_ipo_supported() 不带参数时是「不支持就中断配置」。把 CMAKE_INTERPROCEDURAL_OPTIMIZATION 设成 ON 是全局无条件开 IPO，编译器不支持就直接报错。

@ONLY 只替换 @VAR@，不碰 ${VAR}。写模板时统一用 @VAR@ 并加 @ONLY，能避开「模板里本来就想写 ${} 给人看」被误替换的情况。#cmakedefine 比 #define 好——变量为假时它生成注释，不会留下一个值为空的定义。

八、子目录与工程组织 #

工程超过五个源文件就该分目录了。每个目录一个 CMakeLists.txt，顶层用 add_subdirectory 串起来：

text
demo/
├── CMakeLists.txt          ← 顶层：版本、选项、输出目录、install
├── include/demo/math.h
├── lib/
│   ├── CMakeLists.txt
│   └── math.c
└── app/
    ├── CMakeLists.txt
    └── main.c

顶层 CMakeLists.txt 管版本、选项、输出目录和子目录顺序：

cmake
cmake_minimum_required(VERSION 3.20)
project(demo VERSION 1.2.0 LANGUAGES C)
set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)
set(CMAKE_POSITION_INDEPENDENT_CODE ON)
set(CMAKE_RUNTIME_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/bin)
set(CMAKE_ARCHIVE_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/lib)
option(ENABLE_TESTS "构建测试" OFF)
add_subdirectory(lib)
add_subdirectory(app)
if(ENABLE_TESTS)
    enable_testing()
    add_subdirectory(tests)
endif()

两个子目录各自只管自己的 target：

cmake
# lib/CMakeLists.txt
add_library(demo_math STATIC math.c)
target_include_directories(demo_math PUBLIC ${PROJECT_SOURCE_DIR}/include)
target_compile_options(demo_math PRIVATE -Wall -Wextra)
install(TARGETS demo_math ARCHIVE DESTINATION lib)

# app/CMakeLists.txt
add_executable(demo main.c)
target_link_libraries(demo PRIVATE demo_math)
target_compile_options(demo PRIVATE -Wall -Wextra)
install(TARGETS demo RUNTIME DESTINATION bin)

bash
cmake -S . -B build -DENABLE_TESTS=ON && cmake --build build -j8

四个要点。target 是全局的，但引入顺序有讲究：add_subdirectory(lib) 必须先于 app，否则 app 里写 target_link_libraries(demo PRIVATE demo_math) 时 demo_math 还不存在，CMake 会把它当成库名字符串，链接期才报错。变量作用域是向下的：顶层 set 的普通变量在子目录可见，子目录 set 的变量出不来，除非 set(VAR val PARENT_SCOPE)；缓存变量（CACHE）全局可见，这就是选项写在顶层的原因。

CMAKE_CURRENT_SOURCE_DIR 是「当前处理到的 CMakeLists.txt 所在目录」，随 add_subdirectory 变化；PROJECT_SOURCE_DIR 恒为 project() 那一层的目录，子目录里引用公共头文件用后者。顶层别用全局命令：include_directories 写在顶层会传给所有子目录，连它内部的私有目录一起传下去，路径和选项一律挂在具体 target 上。源文件多到懒得列的时候，用 file(GLOB_RECURSE ... CONFIGURE_DEPENDS)：

cmake
file(GLOB_RECURSE HEADERS FOLLOW_SYMLINKS LIST_DIRECTORIES false CONFIGURE_DEPENDS *.h)
file(GLOB_RECURSE SOURCES FOLLOW_SYMLINKS LIST_DIRECTORIES false CONFIGURE_DEPENDS *.cpp)
file(GLOB_RECURSE FORMS   FOLLOW_SYMLINKS LIST_DIRECTORIES false CONFIGURE_DEPENDS *.ui)
add_executable(demo ${HEADERS} ${SOURCES} ${FORMS})

CONFIGURE_DEPENDS 是关键。没有它，新增源文件不会被自动发现，得手动重跑 configure；有它，每次 cmake --build 会检查 glob 结果，变了就重配。仍然建议在库里显式列源文件——glob 把「谁属于这个 target」这件事藏起来了。

九、外部依赖：find_package #

find_package 找的是「别人装好的包」，两种模式：

模式 找什么 谁提供 特点
MODULE（默认先试） Find<包名>.cmake 脚本 CMake 自带，或 CMAKE_MODULE_PATH 里自己的 脚本手写探测逻辑，适合没有包配置的老库
CONFIG <包名>Config.cmake 或 <包名>-config.cmake 包自己安装时写入 包自己声明 target，信息最准，优先用 
cmake
find_package(Qt5 COMPONENTS Core Gui Widgets CONFIG REQUIRED)   # 显式 CONFIG，找不到就中断
find_package(ZLIB REQUIRED)                                     # 默认模式，先 MODULE 后 CONFIG
写法 含义
find_package(Foo) 找到就用，找不到继续
find_package(Foo REQUIRED) 找不到直接 FATAL_ERROR 中断
find_package(Foo 3.2) 要求版本 ≥ 3.2
find_package(Foo 3.2 EXACT) 要求版本正好 3.2
find_package(Foo COMPONENTS net ssl) 只要其中几个组件
find_package(Foo CONFIG) 只走 CONFIG 模式
find_package(Foo QUIET) 找不到不吭声
find_package(Foo MODULE) 只走 MODULE 模式

结果变量以包名开头：Foo_FOUND、Foo_VERSION、Foo_DIR、Foo_INCLUDE_DIRS、Foo_LIBRARIES。CONFIG 模式的包还会提供 imported target，名字形如 Foo::Bar，直接链接就行。搜索路径按顺序是：<包名>_DIR（缓存变量，直接指到 config 文件所在目录）→ CMAKE_PREFIX_PATH → 系统默认的 /usr、/usr/local，Windows 上还有注册表，手工装的库用 CMAKE_PREFIX_PATH 最直接：

bash
cmake -S . -B build -DCMAKE_PREFIX_PATH=~/qt/6.5.0/gcc_64

一个完整的 Qt 工程，把 find_package、自动 moc/uic/rcc、install 全串起来：

cmake
cmake_minimum_required(VERSION 3.20)
project(qtdemo VERSION 1.2.3 LANGUAGES CXX)
set(CMAKE_INCLUDE_CURRENT_DIR ON)
set(CMAKE_AUTOMOC ON)      # 自动跑 moc 处理 Q_OBJECT
set(CMAKE_AUTOUIC ON)      # 自动把 .ui 转成 ui_*.h
set(CMAKE_AUTORCC ON)      # 自动编译 .qrc 资源
find_package(Qt5 COMPONENTS Core Gui Widgets REQUIRED)
set(HEADERS   mainwindow.h)
set(SOURCES   mainwindow.cpp main.cpp)
set(RESOURCES demo.qrc)
set(FORMS     mainwindow.ui)
add_executable(demo WIN32 ${HEADERS} ${SOURCES} ${FORMS} ${RESOURCES})
target_link_libraries(demo PRIVATE Qt5::Core Qt5::Gui Qt5::Widgets)
install(TARGETS demo DESTINATION bin)
install(DIRECTORY ${PROJECT_SOURCE_DIR}/themes DESTINATION bin/themes)
install(FILES ${PROJECT_SOURCE_DIR}/i18n/*.qm DESTINATION bin/translations)

WIN32 只能给 Windows GUI 程序加，加了它 CMake 会去找 WinMain，你写成普通 main 就链接失败。

Qt 的翻译文件也归 CMake 管，LinguistTools 组件提供两个宏：

cmake
find_package(Qt5 COMPONENTS LinguistTools)
if(Qt5LinguistTools_FOUND)                 # 找到会自动定义这个宏
    # qt5_add_translation：只跑 lrelease，要求 ts 已存在，不能传额外参数
    # qt5_create_translation：ts 不存在会新建、存在则更新，源文件可以是 .ui / .cpp
    qt5_create_translation(QM_FILES ${CMAKE_SOURCE_DIR} english.ts french.ts)
    # qm 生成在构建目录，而 qrc 里写的是相对路径，所以先把 qrc 拷过去
    configure_file(translations.qrc ${CMAKE_BINARY_DIR} COPYONLY)
    add_executable(demo main.cpp ${CMAKE_BINARY_DIR}/translations.qrc ${QM_FILES})
    target_link_libraries(demo Qt5::Widgets)
endif()

把 ${QM_FILES} 塞进 add_executable 的依赖里，翻译更新后就会重新构建。但 qt5_create_translation 在 make clean 或 rebuild 时会把所有 ts 删掉重生成（QTBUG-41736），已经翻译好的文本全丢，官方没修——手动生成 ts 再配 qt5_add_translation 更稳。

不是所有库都装 .cmake 配置文件，一批 Linux 库只给 .pc，走 pkg-config：

cmake
find_package(PkgConfig REQUIRED)
pkg_check_modules(DRM REQUIRED IMPORTED_TARGET libdrm>=2.4.100)
target_link_libraries(demo PRIVATE PkgConfig::DRM)

IMPORTED_TARGET 会把结果包成一个 target，头文件路径和 -l 全带过来，不用手写 ${DRM_INCLUDE_DIRS}。交叉编译时 pkg-config 必须重定向到目标 sysroot，否则拿到的是宿主机的路径——见第十三章。包找不到时有三种姿态，最稳的是带降级：

cmake
find_package(ZLIB QUIET)
if(ZLIB_FOUND)
    target_link_libraries(demo PRIVATE ZLIB::ZLIB)
    target_compile_definitions(demo PRIVATE HAVE_ZLIB=1)
else()
    message(STATUS "zlib not found, building without compression")
endif()

十、交叉编译的 CMake 配置 #

交叉编译不能在 CMakeLists.txt 里写死编译器。CMake 的规矩是：所有跟目标平台相关的东西放进一个 toolchain 文件，命令行用 -DCMAKE_TOOLCHAIN_FILE 引入。工程本身一行不改，宿主机上原生编译、交叉编译、换架构，共用同一份 CMakeLists.txt。一个 arm64 Linux 的 toolchain-aarch64.cmake 长这样：

cmake
# 目标系统。这一行不写，CMake 就当成原生编译，后面全部白设
set(CMAKE_SYSTEM_NAME      Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)
# 交叉工具链
set(CMAKE_C_COMPILER   aarch64-linux-gnu-gcc)

cmake

    get_target_property(QT_QMAKE_EXECUTABLE Qt::qmake IMPORTED_LOCATION)
endif()

if(WIN32)
    add_custom_command(TARGET demo POST_BUILD
        COMMAND ${QT_DEPLOY_EXECUTABLE} "$<TARGET_FILE:demo>")
elseif(APPLE)

        COMMAND ${QT_DEPLOY_EXECUTABLE} "$<TARGET_BUNDLE_DIR:demo>")

$<TARGET_FILE:demo> 是生成器表达式，展开成产物的完整路径。POST_BUILD 挂在 target 上，所以只在真的重新链接之后才跑。

十二、Meson 是什么 #

Meson 和 CMake 是同一层的东西：构建系统生成器。你写 meson.build，meson setup 生成 build.ninja，ninja 去调编译器，区别在语法和取舍。Meson 用类 Python 的语法，强类型，没有 CMake 那种「一切都是字符串」的历史包袱，空格敏感，缩进是语法的一部分。

project('demo', 'c', version : '1.0.0')
executable('demo', 'main.c')

三行就是完整工程。它默认生成 Ninja 文件，不带 Makefile 后端，可选后端只剩 Ninja 和 vs2010/vs2015/vs2017/xcode 这几个 IDE。默认选 Ninja 是因为快：Wayland / Weston、Mesa 3D、GStreamer、systemd、GTK 的部分组件、PipeWire、libdrm 全都迁到了 Meson，想把它们的库移植到板子上，绕不开 Meson。

命令就这几条：

命令 作用
meson setup build 配置，生成 build/build.ninja
meson compile -C build 构建，内部就是调 ninja
ninja -C build 直接构建，等价于上一条
meson install -C build 安装
meson test -C build 跑测试
meson configure build 查看 / 修改构建选项

工程目录里只有三样东西值得记：meson.build（你写的）、subprojects/（内置依赖）、build/（全部生成物，同样是 out-of-source，里面有 build.ninja、meson-info/、meson-private/）。

十三、meson.build 的写法 #

入口 meson.build 第一行永远是 project()：

project('demo_project', 'c', 'cpp',
  version : '1.0.0',
  license : 'MIT',
  default_options : ['warning_level=3', 'cpp_std=c++17', 'buildtype=debugoptimized']
)

第一个参数是工程名，后面跟启用的语言（'c'、'cpp'、'rust'……）。default_options 里的键值对就是编译选项，warning_level=3 对应 -Wall -Wextra -Wpedantic，buildtype 取 debug、debugoptimized、release、minsize。

拿编译器句柄，做能力探测：

cc  = meson.get_compiler('c')
cpp = meson.get_compiler('cpp')
if cc.has_argument('-Wno-unused-parameter')
  add_project_arguments('-Wno-unused-parameter', language : 'c')
endif

语法要点，和 CMake 对照着记：

概念 Meson 写法 说明
变量赋值 x = 'abc' 无 set，没有声明，直接赋
字符串 '单引号'、'''三引号''' 用 f'... @var@ ...' 做插值
列表 ['a', 'b'] 逗号分隔，可 + 拼接
字典 {'k' : 'v'} 键值对
函数调用 executable('app', 'main.c') 位置参数 + 关键字参数 key : value
方法调用 target.link_with(other) 对象上的方法
条件 if ... elif ... else ... endif 缩进是语法
循环 foreach s : sources ... endforeach 遍历列表
注释 # 没有多行注释
子目录 subdir('src') 进子目录读它的 meson.build

生成目标，四种库加一种可执行：

exe = executable('app', 'main.cpp',            # 可执行文件
  include_directories : include_directories('include'),
  dependencies : [thread_dep],
  link_with : my_lib,
  install : true)
shared_library('myplugin', 'plugin.cpp', dependencies : [drm_dep], install : true)
static_library('mycore', 'core.cpp', install : true)
both_libraries('mylib', 'lib.cpp')             # 静态 + 动态同源，编两遍
declare_dependency(include_directories : include_directories('include'))   # 纯头文件依赖
add_project_arguments('-D_GNU_SOURCE', language : 'c')                     # 全局编译参数

include_directories() 返回目录对象，dependency() 返回依赖对象，link_with 接 target 对象。这三样都不是字符串，传错类型 meson setup 阶段就报错——比 CMake 的链接期报错早得多。生成配置头文件，对应 CMake 的 configure_file：

conf_data = configuration_data()
conf_data.set('VERSION', '1.2.3')
conf_data.set('ENABLE_DEBUG', 1)
conf_data.set_quoted('PACKAGE_NAME', 'demo')   # 带引号的字符串，写进 C 代码

configure_file(input : 'config.h.in',
               output : 'config.h',
               configuration : conf_data)

config.h.in 里写 #mesondefine ENABLE_DEBUG，和 CMake 的 #cmakedefine 一个意思。

单元测试内建，声明完直接跑：

test_exe = executable('test_suite', 'test_main.cpp')
test('basic_unit_test', test_exe, args : ['--run-all'])

bash
meson test -C build_dir              # 并行跑，出汇总
meson test -C build_dir --verbose    # 看每个用例的输出

交叉编译这块，Meson 的规矩比 CMake 更硬：交叉编译必须用 cross file，meson.build 里禁止写任何跟架构绑定的东西。cross file 是 INI 格式，五个 section：

section 放什么
[binaries] 目标平台的编译器、ar、strip、ld、pkgconfig 的路径
[properties] sys_root、pkg_config_libdir、skip_sanity_check 这类属性
[built-in options] 全局编译/链接 flag，如 -O2、--sysroot
[host_machine] 运行产物的机器（板子），填 system、cpu_family、cpu、endian
[target_machine] 只在编译编译器本身时用，可以忽略

GNU 那套 Host/Build/Target 和 Meson 的定义是错位的，这点先拧清：Meson 里跑 meson setup 的机器叫 build_machine（你的 x86_64 宿主机），编出来的程序要跑的机器叫 host_machine（RK3588 板子）。GNU 里那个「host」在 Meson 里叫 build。Android NDK 的 LLVM 工具链写成 android_arm64.txt：

十四、Ninja：更快的执行器 #

Ninja 只干一件事：按一张已经摊平的依赖图，把该跑的命令并行跑起来。它没有变量、没有函数、没有隐含规则、没有条件判断，build.ninja 就三种语句：

rule cc
  command = gcc -MD -MF $out.d -c $in -o $out
  depfile = $out.d
  description = CC $out
rule link
  command = gcc $in -o $out
build main.o: cc ../src/main.c
build math.o: cc ../src/math.c
build demo: link main.o math.o
default demo

$in 是输入，$out 是输出，build 输出: 规则 输入 就是一条边。依赖图在配置阶段算完，Ninja 构建时不做任何解析，只比对文件时间戳、拓扑排序、拉起进程。

命令 作用
ninja -C build 在 build 目录里构建
ninja -C build -j8 指定并行度，默认按 CPU 核数 + 2
ninja -C build -k 0 出错不中断，把所有能编的都编一遍，最后汇总错误
ninja -C build -v 打印完整命令行，不打印 CC foo.o 这种摘要
ninja -C build -t targets all 列出所有目标
ninja -C build -t compdb > compile_commands.json 导出编译数据库，给 clangd 和 IDE 用
ninja -C build -d explain 解释「这条命令为什么又要跑」，排查虚假重建
ninja -C build -w dupbuild=err 把重复的输出文件当错误，及早发现工程写错

Ninja 和 Make 的差别不在功能，在取舍：

维度 Make Ninja
规则表达能力 变量、函数、模式规则、条件、include 只有 rule / build / 变量
依赖图 构建时解析 Makefile，边跑边算 配置阶段算好，扁平清单
增量判断 时间戳 + .d 文件 时间戳 + depfile
大工程构建开销 解析开销随工程规模线性增长 几乎恒定
人写还是机写 人写 机器生成，不手改

build.ninja 是给人看的输出，不是输入，改它等于白改。CMake 和 Meson 都能生成它，所以「换构建系统」在 Ninja 这一层没有成本。-d explain 是排查「每次构建都重编同一个文件」的唯一可靠手段，输出会告诉你是因为输入时间戳更新，还是因为命令行变了（Ninja 把命令行也算进哈希）。

十五、Meson 的依赖与子项目 #

dependency() 一行搞定一个外部库，它会依次查 pkg-config、CMake 包配置、子项目：

写法 含义
dependency('threads') 找 pthread，特殊名，不需要 pkg-config
dependency('libdrm', version : '>=2.4.100') 版本约束，不满足就报错
dependency('zlib', required : false) 找不到返回「未找到」对象，不中断配置
dependency('foo', fallback : ['foo', 'foo_dep']) 系统里没有就用子项目 foo 里的 foo_dep 变量
dependency('foo', static : true) 只要静态库
dependency('foo', method : 'pkg-config') 限定查找方式，取值 pkg-config、cmake、config-tool、extraframework

fallback 这条是 Meson 移植大型库时的主力。依赖源码放进 subprojects/ 目录，Meson 自己下载、配置、合并编译。声明一个 .wrap 文件描述从哪拉：

ini
# subprojects/zlib.wrap
[wrap-git]
directory = zlib
url = https://github.com/madler/zlib.git
revision = v1.2.11
depth = 1
[provide]
dependency_name = zlib

[provide] 是关键：它告诉 Meson「这个子项目能满足谁」。主工程里只要写了 fallback，系统里没有 zlib 就会走到这里：

zlib_dep = dependency('zlib', fallback : ['zlib', 'zlib_dep'])
executable('my_app', 'main.cpp', dependencies : [zlib_dep])

验证用的是最直接的链接命令，test.cpp 里调 boost::thread：

bash
# 动态链接：运行时 .so 要拷到板子的 /usr/lib 或进 LD_LIBRARY_PATH
arm-none-linux-gnueabi-g++ test.cpp -o test_dynamic -I./ -L./stage/lib \
  -lboost_system -lboost_thread
# 静态链接：直接给 .a 的路径，不怕运行期找不到库
arm-none-linux-gnueabi-g++ -o test_static test.cpp -I./ \
  ./stage/lib/libboost_thread.a ./stage/lib/libboost_system.a -lpthread

拷到板子上跑，动态链接版报这个：

text
Inconsistency detected by ld.so: dl-deps.c: 622: _dl_map_object_deps: Assertion `nlist > 1' failed!

动态链接器 ld-linux.so 在做依赖树深度优先搜索、建符号映射表时一致性校验失败。两个成因：同一个 SONAME 从两条路径加载——程序直接链了 libboost_system.so，运行时又通过 dlopen 或间接依赖加载了另一个同 SONAME、不同绝对路径的同名库（一个在 /lib，一个在 /usr/local/lib）；工具链 sysroot 里的 glibc 和板子上的不一致——用 glibc 2.35 编，板子上跑的是 2.23，ld.so 的依赖表结构对不上。

排查两步，都在板子上做：

bash
# 1. 看解释器是不是板子上的那一个
readelf -l ./test_dynamic | grep interpreter

# 2. 追踪到底加载了哪几个 .so
LD_DEBUG=files ./test_dynamic

LD_DEBUG=files 输出的最后几行会列出触发断言前加载的库路径，多出来的那个就是元凶。删掉冲突的库，或者统一依赖关系重编。

十六、CMake 与 Meson 对比 #

维度 CMake Meson
语言 自有命令语言，一切都是字符串 类 Python，强类型，缩进敏感
后端 Make、Ninja、VS、Xcode、NMake、Watcom 等十余种 Ninja 为主，另有 VS、Xcode 后端
配置命令 cmake -S . -B build meson setup build
构建命令 cmake --build build ninja -C build
构建选项 -DVAR=VAL，脚本里用 set(... CACHE) 声明 -Doption=val，meson_options.txt 声明
查看选项 cmake -LAH -N build meson configure build
依赖查找 find_package，MODULE / CONFIG 两种模式 dependency()，自动串 pkg-config、cmake、子项目
子项目 FetchContent、add_subdirectory + 手工放置 subprojects/ + .wrap 文件，自动下载
交叉编译 toolchain 文件，-DCMAKE_TOOLCHAIN_FILE= cross file，--cross-file=
交叉编译默认值 不设 CMAKE_SYSTEM_NAME 就当原生 用了 cross file 就一定是交叉
单元测试 需 enable_testing() + add_test() + CTest 内建 test()，meson test 直接跑
配置头文件 configure_file + #cmakedefine configuration_data + #mesondefine
构建速度 生成 Makefile 时偏慢，Ninja 后端下与 Meson 持平 配置阶段快，Ninja 后端下增量最快
第三方库支持 几乎所有 C/C++ 库都提供 FindXXX 或 config 文件 主流开源项目覆盖好，老库要靠 pkg-config
主要负担 语法历史包袱、作用域规则、字符串求值 版本更新带来的语法变动，老工程升级要改脚本

选型就三句话。引用了大量第三方库、要在 Windows 上出 VS 工程、团队里已有 CMake 代码——选 CMake，它是事实标准，没有替代品。

工程自己控制全部依赖、面向 Linux/嵌入式、主要构建对象是 Mesa / Weston / GStreamer 这类项目——用 Meson。语法干净，交叉编译的规矩强制得对。

只想要最快的增量构建，两边都可以，配 Ninja 后端即可。真正的差距在配置阶段，不在构建阶段。

十七、易错点速查 #

易错点 症状 处理
CMake 里 set(VAR val) 覆盖了 -D 命令行传的值不生效 脚本改成 set(VAR default CACHE STRING "说明")
单配置生成器不给 CMAKE_BUILD_TYPE Release 里带 -g，或者根本没优化 显式 -DCMAKE_BUILD_TYPE=Release
在源码目录里 configure 出现 CMakeCache.txt 与目录不匹配的错误 永远 -S . -B build
换编译器/换 toolchain 用同一个 build 目录 报编译器变了，或者静默用旧编译器 新建构建目录
include_directories 写在顶层 所有子目录都吃到私有路径 改 target_include_directories，分清 PRIVATE / PUBLIC
公开头文件的目录设成 PRIVATE 下游编译报找不到头文件 改 PUBLIC 或 INTERFACE
静态库进 .so 报 recompile with -fPIC 链接期报 PC32 重定位错误 开 POSITION_INDEPENDENT_CODE
add_executable(... WIN32 ...) 配普通 main 链接报找不到 WinMain 去掉 WIN32，或者实现 wWinMain
file(GLOB) 没加 CONFIGURE_DEPENDS 新增文件不参与编译 加上，或显式列源文件
CMAKE_SYSROOT 和 --sysroot 同时设 找不到 crt1.o，路径重复拼接 只留一处
交叉编译时 find_package 找到宿主机库 链接报架构不匹配 设 CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY
Meson 的 cross file 只写了编译器名 Cross compiler not found 写绝对路径，或确认它在 PATH 里
Meson 交叉编译没配 pkg_config_libdir 报缺 X11 / 图形库 指向 sysroot 内的 pkgconfig 目录
Meson dependency() 找不到包 Dependency "foo" not found 加 fallback 走子项目，或 required : false 降级处理
每次构建都重编同一个文件 说不清是输入变了还是命令行变了 ninja -d explain 看 ninja 的理由
