一、链接器在做什么 #

链接器的输入是一堆可重定位目标文件（.o）和库文件（.a、.so），输出是一个可执行文件或者一个共享库。它把若干个编译单元拼成一个模块。

编译器对每个 .c 单独干活，它只看得见当前这个文件。你在这一个文件里调用了 printf，编译器不知道 printf 在哪，它只管把调用指令生成出来，地址先留空。填充这个空位的活，归链接器。

1. 两个阶段：符号解析与重定位 #

链接过程切成两半看，一切就清楚了。

符号解析（symbol resolution）：每个 .o 都有一张符号表，表里既记录「我定义了谁」，也记录「我引用了谁」。链接器把这些表收上来，给每一个引用找到唯一的定义。找不到就是 undefined reference，找到两个就是 multiple definition。

重定位（relocation）：.o 里的代码和数据地址都是从 0 开始算的，因为编译这一个文件时，它不知道自己会被放在最终映像的哪个位置。链接器合并所有输入之后，知道每个符号的最终地址了，于是回过头去，把代码里那些留空的机器码字段一一填上正确地址。这个过程叫重定位，.o 里必须有重定位表来告诉链接器「第几个字节要改、按什么规则改、改成哪个符号」。

顺序不能颠倒。先解析，知道谁是谁；再重定位，才知道填什么值进去。

2. .o 里地址为什么从 0 开始 #

一个 .o 文件不是给 CPU 执行的，它是给链接器读的中间产物。既然是中间产物，就没有「运行时地址」这个概念。

所以在 readelf 的输出里，.o 文件中每个 section 的 Addr 都是 0，Entry point address 也是 0，program header 的数量也是 0——它根本不会被加载，要 program header 做什么。

反过来说，可执行文件和共享库才有真实的地址分配、才有加载相关的段。这条分界线贯穿全篇：.o 面向链接，可执行文件与 .so 面向加载。

3. 编译器懂 CPU，链接器不懂 #

编译器非常了解目标平台，它知道寄存器叫什么、指令怎么编码、对齐要求几字节；链接器不需要懂这些，它只做拼装和填地址。这个信息差要靠 .o 来填平：编译器会在 .o 里塞进平台信息，比如 ARM 上的 .ARM.attributes 会记下 Tag_CPU_arch: v5TE、Tag_ABI_enum_size: int、Tag_ABI_align8_needed: Yes 这类属性，链接器靠它判断输入的这些 .o 是不是同一个 ABI 下的东西，混进不兼容的目标文件就报错。再加上链接脚本（linker script）描述「哪个 section 放到哪个地址、按什么顺序放」，链接器就能在不认识指令的前提下把整个映像摆好。

4. 静态链接器与动态链接器是两个程序 #

对比项 静态链接器 ld 动态链接器 ld.so
运行时机 编译期，构建流程中 运行期，每次启动程序
输入 .o、.a、.so（只读符号） 已经编译好的 ELF 文件
输出 一个新的 ELF 文件 不产生文件，改写进程内存
主要工作 合并 section、分配地址、改机器码 映射 .so、填 GOT、绑符号
能否改 .text 能，写文件 不能，正文段只读
谁调用它 gcc 通过 collect2 调 内核根据 .interp 调

最后一行的差异直接决定了后面 PIC 为什么必须存在：静态链接器可以随便改正文段的内容，动态链接器在运行期改不了。

5. 几个容易踩的细节 #

gcc 在链接阶段实际调用的常常是 collect2，而不是裸的 ld。collect2 是 ld 的马甲，顺手处理 C++ 的构造/析构函数收集，最终还是要调 ld。

ld -r 可以把多个 .o 合并成一个 .o，而不是生成可执行文件：

bash
ld -r -o result.o a.o b.o c.o

-r 是 relocatable，输出仍是可重定位文件，重定位信息保留，还能继续参与链接。这个用法适合做部分链接，但打包一堆 .o 时静态库更好用，第七章再讲。

链接脚本不是玄学，直接打出来看：

bash
ld --verbose | head -40

没有显式 -T 时，链接器用内置默认脚本。你随手敲 gcc hello.c 能出可执行文件，靠的就是它。

二、ELF 文件的全貌：四种类型 #

.o、可执行文件、.so、core dump，这四样东西是同一个格式：ELF，全称 Executable and Linkable Format。

同一个格式服务两个视角，这是 ELF 设计的核心取舍。左边是链接视图，右边是执行视图：

text
      链接视图 (Linking View)             执行视图 (Execution View)
      +----------------------+            +----------------------+
      |     ELF Header       |            |     ELF Header       |
      +----------------------+            +----------------------+
      | Program Header Table |  <------>  | Program Header Table |
      |       (可选)          |            |       (必需)          |
      +----------------------+            +----------------------+
      |  .text .data .bss    |            |  Segment (LOAD)      |
      |  .rodata .symtab     |            |   含多个 section      |
      |  .rel.text ...       |            +----------------------+
      +----------------------+            | Section Header Table |
      | Section Header Table |            |       (可选)          |
      +----------------------+            +----------------------+

一句话记住：静态链接器按链接视图读 ELF，动态链接器按执行视图读 ELF。

链接视图可以没有段表（program header table），.o 就是这样；执行视图可以没有节表（section header table），strip 之后的可执行文件接近这样。两者共用同一个文件头。

1. e_type：四种文件类型 #

文件头里第一个关键字段就是 e_type。

e_type 含义 典型产物 有 program header 能直接执行
ET_REL 可重定位文件 gcc -c 出来的 .o 没有 不能
ET_EXEC 可执行文件 -no-pie 编译的可执行文件 有，地址固定 能
ET_DYN 共享对象 .so、PIE 可执行文件 有，地址浮动 .so 不能，PIE 能
ET_CORE core dump 崩溃时吐出的 core 有 不能

ET_DYN 这一行值得盯住：加了 -pie 编译出来的可执行文件，类型也是 ET_DYN，和 .so 一模一样。区分它们的不是文件头，而是「有没有定义 main、有没有链接 libc」。第十六章会拿这个特性做文章。

2. 文件头结构 #

ELF 的结构声明在系统头文件 elf.h 里，32 位和 64 位的差别主要在字段宽度，重定位类型也略有区别。

c
#define EI_NIDENT (16)
typedef struct
{
    unsigned char e_ident[EI_NIDENT]; /* Magic number and other info */
    Elf_Half      e_type;             /* Object file type */
    Elf_Half      e_machine;          /* Architecture */
    Elf_Word      e_version;          /* Object file version */
    Elf_Addr      e_entry;            /* Entry point virtual address */
    Elf_Off       e_phoff;            /* Program header table file offset */
    Elf_Off       e_shoff;            /* Section header table file offset */
    Elf_Word      e_flags;            /* Processor-specific flags */
    Elf_Half      e_ehsize;           /* ELF header size in bytes */
    Elf_Half      e_phentsize;        /* Program header table entry size */
    Elf_Half      e_phnum;            /* Program header table entry count */
    Elf_Half      e_shentsize;        /* Section header table entry size */
    Elf_Half      e_shnum;            /* Section header table entry count */
    Elf_Half      e_shstrndx;         /* Section header string table index */
} Elf_Ehdr;

内核里对应的结构体是 Elf32_Ehdr 和 Elf64_Ehdr。

e_ident 那 16 个字节逐位都有含义：

偏移 名字 含义
0~3 EI_MAG 固定 0x7f 'E' 'L' 'F'，认文件的魔数
4 EI_CLASS ELFCLASS32 / ELFCLASS64，32 位还是 64 位
5 EI_DATA ELFDATA2LSB 小端，ELFDATA2MSB 大端
6 EI_VERSION 固定 EV_CURRENT（1）
7 EI_OSABI 目标 OS 的 ABI 标识，实际很少用
8 EI_ABIVERSION ABI 版本，实际很少用
9~15 填充 对齐用，无意义

e_machine 标架构：EM_386 是 32 位 x86，EM_X86_64 是 x86-64，EM_ARM 是 ARM（含 Thumb、Thumb2），EM_AARCH64 是 ARM64。架构对不上，链接器直接拒绝，这是「在 x86 上链接 ARM 的 .o」报错的根源。

e_entry 是入口虚拟地址，不是 main 的地址，而是 _start 的地址。对 ET_REL 文件这个字段没有意义（值是 0）；对 PIE 可执行文件，这个字段是相对偏移，不是运行时绝对地址。

其余的字段大多在描述两张表的位置：e_phoff / e_phnum / e_phentsize 描述段表，e_shoff / e_shnum / e_shentsize 描述节表，e_shstrndx 指出节表里哪一项是节名字符串表。两张表都可以看成数组，ELF 头只负责给出起始偏移、元素个数、元素大小。位置和长度随 section/segment 数量变化，而 ELF 头永远在最开头、长度固定，所以想找两张表必须先读它。

三、ELF 的段与节 #

段（segment）和节（section）是两个词，经常被混着说。区别就一句：节是给链接器看的，段是给加载器看的。

一个段可以包含多个节。readelf -l 里的 Section to Segment mapping 就是这张对照关系表。

bash
readelf -l main1 | sed -n '/Section to Segment/,$p'

输出大致如下：

text
 Section to Segment mapping:
  Segment Sections...
   01     .interp
   02     .interp .note.ABI-tag .note.gnu.build-id .gnu.hash .dynsym .dynstr
          .gnu.version .gnu.version_r .rel.dyn .rel.plt .init .plt .plt.got
          .text .fini .rodata .eh_frame_hdr .eh_frame
   03     .init_array .fini_array .dynamic .got .got.plt .data .bss
   04     .dynamic
   08     .init_array .fini_array .dynamic .got

看第 02 段：可读可执行的代码段，把 .text、.rodata、.plt、.init、.dynsym 一锅端。第 03 段是可读写的数据段，装着 .got、.data、.bss、.dynamic。段是按内存权限组织的，节是按用途组织的。

1. 节头结构 #

节表是一个数组，位置在 e_shoff，共 e_shnum 个元素，每个元素 e_shentsize 字节。

c
typedef struct
{
  Elf32_Word sh_name;      /* Section name (string tbl index) */
  Elf32_Word sh_type;      /* Section type */
  Elf32_Word sh_flags;     /* Section flags */
  Elf32_Addr sh_addr;      /* Section virtual addr at execution */
  Elf32_Off  sh_offset;    /* Section file offset */
  Elf32_Word sh_size;      /* Section size in bytes */
  Elf32_Word sh_link;      /* Link to another section */
  Elf32_Word sh_info;      /* Additional section information */
  Elf32_Word sh_addralign; /* Section alignment */
  Elf32_Word sh_entsize;   /* Entry size if section holds table */
} Elf32_Shdr;

对应内核里的 Elf32_Shdr / Elf64_Shdr。

sh_name 不是字符串本身，而是一个偏移，指向 .shstrtab 里的某处。这样做的好处是节头长度固定、字符串可以复用，ELF 里所有名字都这么处理。

sh_type 标类型，SPEC 里定义了几十种，常见的就这么几个：

sh_type 含义 例子
SHT_NULL 无效项，第 0 项固定是它 占位
SHT_PROGBITS 内容由程序决定 .text、.data、.plt
SHT_SYMTAB 符号表 .symtab
SHT_DYNSYM 动态符号表 .dynsym
SHT_STRTAB 字符串表 .strtab、.shstrtab、.dynstr
SHT_REL / SHT_RELA 重定位项 .rel.text、.rela.plt
SHT_DYNAMIC 动态链接信息 .dynamic
SHT_NOBITS 不占文件空间 .bss

内容位置由三个字段决定：sh_offset 是文件内偏移，sh_size 是长度，sh_entsize 是针对「内容本身也是个数组」的那种节（比如 .symtab、.rel.text）的元素大小。

运行时相关的字段是 sh_addr（加载后的虚拟地址）、sh_addralign（对齐，要求 sh_addr % sh_addralign == 0）、sh_flags（SHF_WRITE / SHF_ALLOC / SHF_EXECINSTR 的组合）。

sh_link 和 sh_info 的含义跟着 sh_type 变。符号表用 sh_link 指向它的字符串表、sh_info 指出第一个非 LOCAL 符号的下标；重定位节用 sh_link 指向符号表、sh_info 指向被作用的那个节。

2. 常见节一览 #

节名 装什么 属性 运行时在不在内存
.text 机器指令 AX 在，只读可执行
.rodata 常量、字符串字面量 A 在，只读
.data 已初始化的全局/静态变量 WA 在，可读写
.bss 未初始化的全局/静态变量 WA（NOBITS） 在，可读写，清零
.symtab / .strtab / .shstrtab 符号表与配套字符串（给静态链接器） 无 A 不在
.rel.text / .rel.data 正文段/数据段的重定位项 无 A 不在
.dynsym / .dynstr 动态符号表与配套字符串（给动态链接器） A 在
.dynamic 动态链接所需的 tag 数组 WA 在
.interp 动态链接器路径字符串 A 在
.plt / .got / .got.plt 跳转桩与地址表 AX / WA 在
.init / .fini / .init_array / .fini_array 模块初始化与退出（代码或函数指针数组） AX / WA 在
.tdata / .tbss 线程局部存储的初值/零值 WA 在
.comment / .note.GNU-stack 编译器版本信息、栈可执行标记 无 A 不在
.debug_* 调试信息 无 A 不在

这张表够用了。有个规律很值得记：带 A 标记的节会进内存，不带 A 的节只在文件里存在。符号表、重定位表、调试信息都只在构建期有用，跑起来之后 CPU 不看它们——所以 strip 删掉它们不影响程序执行。

.note.GNU-stack 值得单独说一句。它是一个 0 字节的节，专门用来告诉链接器「这个 .o 不需要可执行栈」。缓冲区溢出攻击靠的就是在栈上执行代码，如果所有输入 .o 都带这个标记，链接结果也不会要求可执行栈，程序加载时就能以不可执行栈的方式运行。这是编译期就埋下的一道防线。

.comment 里躺着编译器指纹，objdump -s --section .comment hello.o 一跑就露底：

text
Contents of section .comment:

 0010 65727920 536f7572 63657279 20472b2b  ery Sourcery G++

3. 段头结构 #

段表同样是数组，位置在 e_phoff，e_phnum 个元素，每个 e_phentsize 字节。它描述的是「内核怎么把这个文件映射成进程映像」。

c
typedef struct
{
  Elf32_Word p_type;   /* Segment type */
  Elf32_Off  p_offset; /* Segment file offset */
  Elf32_Addr p_vaddr;  /* Segment virtual address */
  Elf32_Addr p_paddr;  /* Segment physical address */
  Elf32_Word p_filesz; /* Segment size in file */
  Elf32_Word p_memsz;  /* Segment size in memory */
  Elf32_Word p_flags;  /* Segment flags */
  Elf32_Word p_align;  /* Segment alignment */
} Elf32_Phdr;

对应内核里的 Elf32_Phdr / Elf64_Phdr。p_offset 是文件内偏移，p_vaddr 是映射到的虚拟地址，p_filesz 是文件里的大小，p_memsz 是内存里的大小（必须 >= p_filesz），p_flags 是 R/W/X 权限，p_align 是对齐（要求 p_offset % p_align == p_vaddr % p_align）。

p_memsz > p_filesz 这种情况很常见。多出来的部分在文件里没有内容，加载时被清零——这正是 .bss 的实现方式：不占文件空间，但占内存。一个塞满 int buf[1024 * 1024] 的程序，文件只有几 KB，跑起来占 4 MB，全靠这个差额。

p_type 标段类型，常用的几个是：

p_type 含义 备注
PT_NULL 未使用 占位
PT_LOAD 可加载段 内核按它做 mmap，多个 PT_LOAD 按虚拟地址递增排列
PT_DYNAMIC 动态链接信息 对应 .dynamic，多为 RW，因为 ld.so 要改里面的入口
PT_INTERP 解释器路径 指向 .interp，值是 /lib64/ld-linux-x86-64.so.2 之类
PT_NOTE 附加信息 对应 .note.*
PT_PHDR 段表自身 如果有，必须在所有可加载段之前，且只能出现一次
PT_GNU_STACK 栈属性 控制栈是否可执行
PT_GNU_RELRO 只读重定位 加载后把一部分数据段改成只读，加固用

.o 文件里 e_phnum 等于 0，没有段表；可执行文件和 .so 才有。这一条判断，扫一眼 readelf -h 就能区分文件的性质。

四、可重定位目标文件的结构 #

理论说完，动手。拿一段最简单的代码，把 .o 拆开看。

c
#include <stdio.h>

int hello_world_data = 0x1234;

int hello_world_bss;

int hello_world(void)
{
    int tmp;

    printf("hello world!\n");

    tmp = hello_world_data + hello_world_bss;

    return tmp;
}

编译它：

bash
gcc -c hello_world.c -o hello_world.o

一个 200 多字节的 .c，编译完变成 1 KB 多的 .o。多出来的内容全是给链接器准备的信息。具体要准备这几类：

内容 落在哪个节 给谁用
执行代码 .text CPU 执行
已初始化全局数据 .data CPU 访问
未初始化全局数据 .bss（不占文件） 加载时清零
只读数据（字符串常量等） .rodata CPU 只读访问
定义的符号与引用的符号 .symtab + .strtab 链接器做符号解析
重定位信息 .rel.text、.rel.data 链接器做重定位
平台属性 .ARM.attributes 等 链接器做兼容性检查

函数内部的临时变量不在这个列表里。它们在栈上，运行时才存在，符号表里也没有它们的名字。

1. 先看文件头 #

两条命令把 .o 的全部家底打出来：

bash
readelf -a hello_world.o > hello_world.elf
objdump -D -h hello_world.o > hello_world.txt

readelf -a 输出里第一段是文件头。下面是 32 位 ARM 平台的一个实例：

text

  Class:                             ELF32
  Data:                              2's complement, little endian
  Version:                           1 (current)
  OS/ABI:                            UNIX - System V
  ABI Version:                       0
  Type:                              REL (Relocatable file)
  Machine:                           ARM

  Start of program headers:          0 (bytes into file)

逐行对照前面讲的定义，处处对得上：Type: REL 说明这是可重定位文件；Machine: ARM 是目标平台；Entry point address: 0x0 因为 .o 不会被加载执行；三个 program header 字段全零因为根本没有段表；节表从偏移 368 开始，12 个节头每个 40 字节，共 480 字节。

几个点值得停下来看：

第 0 项是空的。 NULL 类型，所有字段为 0。这是规范要求的占位，好处是「第 0 号节」可以用来表示 SHN_UNDEF 这个特殊索引，符号表里未定义符号的 Ndx 就写 0。

AX 和 WA 这些标记。 .text 是 AX，占内存且可执行；.data 和 .bss 是 WA，占内存且可写；.rodata 是 A，占内存、只读。而 .symtab、.strtab、.rel.text、.comment 都没有 A 标记——它们和程序执行无关，纯粹服务链接器。

.bss 的 Size 是 0，类型是 NOBITS。 未初始化的全局变量 hello_world_bss 在这个节里，但 .o 里一个字节都不占。NOBITS 的意思是「有大小、无内容」，装载时按 size 分配内存并清零。.o 阶段它的 size 甚至是 0，具体大小要等链接器数完所有输入才算得出来。

ES 是 entry size。 .rel.text 的 ES 是 8，因为内容是一条条 8 字节的重定位项；.symtab 的 ES 是 16。.text 的 ES 是 0，因为正文段不是数组。

.rodata 的 size 是 16。 字符串 "hello world!\n" 只有 13 个字节，加结尾 \0 是 14。但 Al 那一列写着 4，这个节按 4 字节对齐，所以补到 16。

Lk 和 Inf 两列是有含义的引用。 .symtab 的 Lk 是 11，指向 11 号节 .strtab——符号名存在那里。Inf 是 12，表示 12 号之前的符号项都是 LOCAL 的。.rel.text 的 Lk 是 10，指向符号表；Inf 是 1，表示这堆重定位作用在 1 号节 .text 上。

在 x86-64 上自己跑一遍，看到的规律一样，只是段名和重定位类型不同：

bash

readelf -h hello_world.o; readelf -S hello_world.o
objdump -h hello_world.o; readelf -r hello_world.o; readelf -s hello_world.o

这五条分别是看头、看节表、看节表摘要、看重定位、看符号表。readelf 按 ELF 规范直译，objdump 多一层 BFD 抽象，输出更贴近链接器的口味；两边都看一遍，理解更深。

1. 我们定义的三个符号在哪 #

源码里定义了 hello_world_data、hello_world_bss、hello_world，表里都在：

  • 12 号 hello_world_data：OBJECT 类型，Size 是 4，Ndx 是 3（.data）
  • 13 号 hello_world：FUNC 类型，Size 是 72，Ndx 是 1（.text）
  • 15 号 hello_world_bss：OBJECT 类型，Size 是 4，Ndx 是 COM

Size 是符号本体占的字节数。函数的 Size 就是它的机器码长度，调试器和性能工具靠这个区分函数边界。

Value 是符号的地址。对 .o 里的符号，这个值是一个相对所在节的偏移，不是绝对地址。

2. COM 是个什么东西 #

hello_world_bss 的 Ndx 不是 4（.bss），而是 COM。COM 是一个特殊的节索引，表示这个符号在 common block 里。

背景是这样：传统 Unix C 编译器允许你在多个 .c 文件里各定义一个同名的未初始化全局变量，编译不报错。编译器把这些变量放进 common block，而不是直接塞进 .bss。

为什么不直接放 .bss？因为放进 .bss 就等于「已经分配地址了」，运行时占内存。多个 .o 合并时，链接器一数 .bss 就会发现同名符号重复定义，直接报错。放进 common block 相当于说「这个符号先记着，谁要谁拿走，最后只留一份」。

这个约定会给粗心的程序员制造很难查的 bug：两个文件里各写一个 int flag;，你以为各自独立，实际链接后共享同一块内存，改一个另一个跟着变。

关掉这个行为用 -fno-common：

bash
gcc -fno-common -c a.c
gcc -fno-common -c b.c
gcc a.o b.o -o app

此时同名未初始化全局变量会直接报 multiple definition。新版本的 GCC 已经把 -fno-common 设成默认，这个坑少了很多。

3. Bind：LOCAL、GLOBAL、WEAK #

Bind 那一列控制符号的可见范围和行为。

Bind 含义 C 语言里对应什么
LOCAL 只在本 .o 内可见 static 修饰的变量和函数
GLOBAL 对所有 .o 可见，全程序唯一 普通全局函数、已初始化全局变量
WEAK 对外可见，但遇到同名 GLOBAL 就让位 __attribute__((weak))
UNIQUE GNU 扩展，同一名字全程序一份 -fno-common 之后的 C++ 模板静态成员

LOCAL 符号有个容易误解的地方：函数内部的临时变量不是 LOCAL 符号，它们压根不在符号表里。栈上的东西编译期没有固定地址，链接器不需要知道。

但如果函数内的局部变量加了 static，它就会进符号表：

c
#include <stdio.h>

extern int pp;

static int *gw_si = &pp;   /* 模块级 static，有初值 */

static int gw_sui;         /* 模块级 static，无初值 */

static int goodbye_world(void)
{
    int tmp;

    static int gw_si = 0x5678;   /* 函数内 static，有初值 */
    static int gw_sui;           /* 函数内 static，无初值 */

    printf("goodbye world!\n");

    tmp = gw_si + gw_sui;

    return tmp;
}

编译后符号表里会出现四项：

text
 5: 00000000     4 OBJECT  LOCAL  DEFAULT    3 gw_si
 7: 00000000     4 OBJECT  LOCAL  DEFAULT    5 gw_sui.2142
 8: 00000004     4 OBJECT  LOCAL  DEFAULT    3 gw_si.2141
13: 00000004     4 OBJECT  LOCAL  DEFAULT    5 gw_sui

注意名字的变化。模块级 gw_si 保持原名；函数内的同名 gw_si 被改名成 gw_si.2141，那个数字是编译器生成的序号，用来避免和模块级同名字符号冲突。你在源码里写 gw_si，编译器在符号表里叫它 gw_si.2141——这就是为什么 nm 的输出里偶尔会看到带点号的怪名字。

还有位置信息：有初值的 static 变量放 .data（Ndx 是 3），无初值的放 .bss（Ndx 是 5）。C 标准要求 static 对象在程序启动前完成初始化，指针置 NULL、整数置 0，这个语义和 .bss 的「清零」正好对上，所以能塞进 .bss 省文件空间。

全部这四个符号都是 LOCAL，包括那个 static 的 goodbye_world 函数。static 的本质就是「把符号从 GLOBAL 降级成 LOCAL」。

4. 那些看不懂的项 #

FILE 类型（1 号）：hello_world.c，Ndx 是 ABS。它记录这个 .o 是从哪个源文件来的，ABS 表示「绝对，后续重定位不改它」。

SECTION 类型（2、3、4、6、9、10、11 号）：每个都对应一个节，Ndx 就是节号。它们主要服务重定位——重定位项需要指向「某个节的起始位置」时，就引用这些符号。

NOTYPE 的 UND（14 号）：puts，Size 是 0，Ndx 是 UND。这是本模块引用了但没定义的符号。源码里写的是 printf，编译出来变成 puts——编译器发现你只传了一个常量字符串加换行，没有格式符，于是把 printf 优化成了 puts。这个替换说明一件事：符号表里出现的名字，是编译器优化之后的真实调用。

带 $ 的符号（5、7、8 号）：这些是 ARM 平台的 mapping symbol，不是 C 语言的东西。$a 表示后面那段是 ARM 指令，$t 表示 Thumb 指令，$d 表示数据。反汇编器靠它们区分代码和数据，不然一串 4 字节没法判断该当指令还是当常量。

5. 符号类型速查 #

Type 含义 典型来源
NOTYPE 未指定类型 汇编里的裸标签、UND 的引用符号
OBJECT 数据对象 全局变量、static 变量
FUNC 函数 函数定义
SECTION 节本身 每个节一个
FILE 源文件名 每个 .o 一个
COMMON 未初始化的全局数据 旧的 -fcommon 行为
TLS 线程局部存储 __thread 变量
GNU_IFUNC 运行时选实现 glibc 的 memcpy 之类

6. 同名符号，链接器听谁的 #

把 Bind 和 Ndx 合起来看，能推出一套裁决规则。这套规则在第六章会用到：

情况 链接器行为
多个同名 GLOBAL 报错 multiple definition
一个 GLOBAL + 多个 WEAK 选 GLOBAL，WEAK 被忽略
一个 GLOBAL + 多个 COMMON 选 GLOBAL
多个同名 WEAK 任选一个
一个 WEAK + 多个 COMMON 忽略 WEAK，选 COMMON
多个同名 COMMON 任选一个，取最大的那块

用一句话概括这套规则：未初始化的全局变量在链接器眼里就是弱符号。这就是为什么 common block 那套机制能和 weak 和平共处。

规则背下来不如跑一遍。写两个文件各定义一个同名变量，改初始化与否、改 -fcommon / -fno-common，四种组合跑完，规则就刻在脑子里了。

六、符号解析与重定位 #

符号表告诉你「谁定义了谁」，重定位表告诉你「哪里要改」。两张表合起来，链接器才能干活。

1. 重定位表长什么样 #

接着 hello_world.o 往下看：

text
Relocation section '.rel.text' at offset 0x498 contains 4 entries:
 Offset     Info    Type            Sym.Value  Sym. Name
00000010  00000e1c R_ARM_CALL        00000000   puts
0000003c  00000602 R_ARM_ABS32       00000000   .rodata
00000040  00000c02 R_ARM_ABS32       00000000   hello_world_data
00000044  00000f02 R_ARM_ABS32       00000004   hello_world_bss

四条重定位，意思分别是：

Offset 类型 目标符号 要做什么
0x10 R_ARM_CALL puts 改这条 bl 指令的跳转偏移
0x3c R_ARM_ABS32 .rodata 在这 4 字节里填字符串地址
0x40 R_ARM_ABS32 hello_world_data 在这 4 字节里填变量地址
0x44 R_ARM_ABS32 hello_world_bss 在这 4 字节里填变量地址

Offset 是相对 .text 节的偏移，也就是链接器要动手改的那个位置。

对照反汇编看：

armasm

0x10 那条 bl 0 就是等着被改的：目标地址还不知道，先填个 0 占位。链接器解析出 puts 的最终地址后，会回来算出相对偏移，写进这条指令的低 24 位。

0x3c、0x40、0x44 三处是数据，位于正文段末尾。ldr r0, [pc, #40] 从 0x3c 处取一个 32 位值，这个值就是 .rodata 的地址——目前是 0，要等链接器填。同理 0x40 处放 hello_world_data 的地址，0x44 处放 hello_world_bss 的地址。正文段实际长度是 0x48，反汇编只显示到 0x38，后面那 16 个字节在 dump 里是省略号，因为它们全是 0，还没被重定位填过。

R_ARM_CALL 和 R_ARM_ABS32 的差别是本质性的：

  • R_ARM_CALL 改的是指令内部字段，结果是一个相对偏移。ARM 的 BL 只能用 24 位有符号立即数表示相对偏移，偏移量左移 2 位后符号扩展，能覆盖正负 32 MB。它跳不到 4 GB 的任何地方。
  • R_ARM_ABS32 改的是数据，结果是一个绝对地址。32 位 ARM 上这种重定位没有约束，可以填 4 GB 空间里任意地址。

这个区别决定了后面 PIC 的必要性：绝对地址一旦写死，代码就无法被搬到别的地址执行。

重定位项的结构在 Elf32_Rel / Elf32_Rela 里：

c
typedef struct {
    Elf32_Addr r_offset;  /* 要修改的位置 */
    Elf32_Word r_info;    /* 符号索引 + 重定位类型 */
} Elf32_Rel;

typedef struct {
    Elf32_Addr  r_offset; /* 要修改的位置 */
    Elf32_Word  r_info;   /* 符号索引 + 重定位类型 */
    Elf32_Sword r_addend; /* 显式加数 */
} Elf32_Rela;

r_info 把「符号索引」和「重定位类型」压进一个 word，高位是符号索引，低位是类型。ARM 32 位的布局是高 24 位符号、低 8 位类型，所以 00000e1c 拆开是「符号 14（puts）、类型 0x1c」。

Rel 和 Rela 的区别只在加数：Rela 把加数显式存在表项里，Rel 把加数藏在被修改的那个位置本身。ARM 32 位用 Rel，x86-64 用 Rela。这也解释了为什么 x86-64 的重定位节叫 .rela.text 而不是 .rel.text。

常见的重定位类型：

类型 平台 含义
R_ARM_CALL / R_ARM_PLT32 ARM 改 BL/BLX 的跳转偏移，或改走 PLT 桩
R_ARM_ABS32 ARM 填一个 32 位绝对地址
R_ARM_BASE_PREL / R_ARM_GOT_BREL ARM 填 GOT 相对当前指令的偏移 / 符号在 GOT 内的偏移
R_ARM_GLOB_DAT ARM 在 GOT 项里填符号的绝对地址
R_X86_64_PC32 / R_X86_64_32 x86-64 填 32 位 PC 相对偏移 / 32 位绝对地址（后者不能用于 .so）
R_X86_64_JUMP_SLOT x86-64 填 GOT 里的函数地址，延迟绑定用

R_X86_64_32 这一条要记住。它写的是 32 位绝对地址，而 .so 会被加载到 4 GB 以上的地址，装不下。所以用这种重定位的 .o 无法链接成共享库——这是第十七章那个经典报错的根源。

2. 符号解析的三个集合 #

链接器从左到右扫描输入文件，扫描过程中维护三个集合：

集合 装什么
E 所有要合并进输出的 .o 文件
U 目前还没找到定义的符号（undefined）
D 已经收集到的已定义符号（defined）

初始状态三个都是空。扫描规则分两种：

遇到 .o 文件：整个文件无条件加入 E。分析它的符号表，把定义加入 D；把引用拿出来，逐个在 D 里找，找到就解析完，找不到就加入 U。

遇到 .a 库文件：不整个吞下去。对 U 里每一个未定义符号，在库的成员里找「定义了它的那个 .o」，找到就把这个成员加入 E，同时更新 D 和 U。这个过程反复迭代，直到 U 和 D 不再变化。

这个迭代很关键：新加入的 .o 会引入新的未定义符号，这些新符号又意味着要从同一个库里再拉出新的成员。库里的其他成员，只要没被用到，就不进 E——这就是静态库能省空间的机制。

扫描到最后一个文件时，如果 U 还是非空，报 undefined reference。

3. 顺序问题：库必须放在后面 #

上面那套规则直接推出一个反直觉的结论：

bash
gcc -static -o result libaa.a a.o     # 报错
gcc -static -o result a.o libaa.a     # 正确

第一种写法里，链接器先扫 libaa.a，此时 U 是空的，一个符号都不需要，库里的成员一个都不抽取，直接掠过。再扫 a.o，发现它引用了 ahead，U 变成 {ahead}，但库已经扫完了，链接器不会回头。最后报 undefined reference to ahead。

所以规矩就一条：.o 在前，库在后。多个库之间也有依赖顺序，被依赖的放后面。

如果库之间真的循环依赖，用 --start-group 包起来：

bash
gcc -o app main.o -Wl,--start-group -lA -lB -lC -Wl,--end-group

被这两个参数夹住的库会被反复扫描，直到没有新的未定义符号冒出来。代价是链接变慢，所以只在小范围用。

4. 链接脚本：地址是怎么定下来的 #

链接器按脚本干活。默认脚本藏在 ld 里，直接打印看：

bash
ld --verbose | head -20

text
OUTPUT_FORMAT("elf64-x86-64", "elf64-x86-64", "elf64-x86-64")
OUTPUT_ARCH(i386:x86-64)
ENTRY(_start)
SEARCH_DIR("=/usr/local/lib/x86_64-linux-gnu"); SEARCH_DIR("=/lib/x86_64-linux-gnu");
SEARCH_DIR("=/usr/lib/x86_64-linux-gnu"); SEARCH_DIR("=/usr/lib64"); SEARCH_DIR("=/lib64");
指令 作用 等价命令行
OUTPUT_FORMAT(default, big, little) 输出文件格式 -EL / -EB 选大小端
OUTPUT_ARCH(arch) 目标平台 -m 指定 emulation
ENTRY(_start) 程序入口符号 -e
SEARCH_DIR("path") 库搜索目录 -L path

SEARCH_DIR 那几个路径透露了 Linux 的库分层：/lib 放系统级核心库，/usr/lib 放多用户共用的库，/usr/local/lib 留给本地自己编的东西。装东西别乱塞。

主体是 SECTIONS 块：

text
SECTIONS
{
  PROVIDE (__executable_start = SEGMENT_START("text-segment", 0x400000));
  . = SEGMENT_START("text-segment", 0x400000) + SIZEOF_HEADERS;
  .interp         : { *(.interp) }
  .text           :
  {
    *(.text.unlikely .text.*_unlikely)
    *(.text.exit .text.exit.*)
    *(.text.startup .text.startup.*)
    *(.text.hot .text.hot.*)
    *(.text .stub .text.* .gnu.linkonce.t.*)
  }
  ...
}

*(.text) 里的 * 是通配，表示「所有输入文件的 .text 节」。整个 SECTIONS 的语义是：把各输入 .o 里同名的节，按这里写的顺序倒进输出文件的对应节，同时给每个输出节分配运行地址。. 是位置计数器（location counter），. = 0x400000 + SIZEOF_HEADERS 把当前位置挪到「基址 + 文件头大小」处，第一个节从这里开始。

脚本里还能定义符号，这些符号会进输出符号表，C 代码能访问：

c
#include <stdio.h>

extern char __executable_start;

int main(void)
{
    printf("__executable_start = %p\n", &__executable_start);
    return 0;
}

x86-64 上跑出来在 0x400000 附近（PIE 编译会变），32 位 x86 上是 0x08048000。

这里有个必须分清的区别。C 里 int xyz = 0x1234; 干了两件事：分配 4 字节内存存值，在符号表里记下地址。链接脚本里定义符号只做第二件事——不分配内存。所以 __executable_start 这个「变量」在内存里不存在，它的「地址」就是 0x400000 这个数本身。访问脚本符号必须取地址，直接写 __executable_start 会去读 0x400000 那块内存，得到野值。

PROVIDE 是条件定义：输入 .o 里已有同名符号就用输入的那个，没有才用脚本里的。

七、静态库：.a 是什么 #

静态库要解决的问题很朴素：标准函数（数学、字符串、IO）每个程序都要用，不能每次重写。

1. 四种方案，为什么选了最后一种 #

方案 做法 问题
带源码 编译器发行时附带标准库 .c 库和编译器绑太死，改一个 bug 就要重发整个编译器
一个大 .o 把所有库函数编成一个 libc.o 文件巨大，用到用不到全被塞进可执行文件
一堆 .o 散装 .o 放一个目录 程序员得自己记住调了哪些函数、依赖哪些 .o
静态库 打包成 .a，链接器按需抽取 无（在静态链接范畴内）

散装 .o 那个方案已经能工作了，只是用起来烦。静态库就是在它外面加了一层索引：还是那堆 .o，但多了一张「哪个 .o 定义了哪些符号」的表，链接器查表就能精确定位，不用一个个打开看。

2. .a 就是一个加了索引的归档 #

bash
gcc -c hello.c -o hello.o
ar rcs libmyhello.a hello.o

ar 是归档工具，rcs 三个字母各有含义：r 替换已有成员，c 创建归档，s 写入符号索引表。少了 s，链接器就得线性搜索，慢；s 就是那张索引表，等价于老式的 ranlib。

看库里有什么：

bash
ar -t libmyhello.a        # 列出成员（.o 文件）名
nm -a libmyhello.a        # 列出所有符号
nm -s libmyhello.a        # 连索引一起列

ar -t libgcc.a 会打出一长串名字，全是 .o：_divsi3.o、_udivsi3.o、_muldi3.o……这些是编译器在目标 CPU 缺少对应指令时调用的辅助函数。

举个实例。ARM 处理器没有整数除法指令，C 代码里写 / 时，编译器生成不了单条 div，于是改成调用库函数：

c
int div_test(int a, int b)
{
    return a / b;
}

bash
gcc -c div_test.c -o div_test.o
objdump -d div_test.o | grep bl

你会看到 bl __aeabi_idiv。这个函数来自 libgcc.a 里的 _divsi3.o。同样的机制还有 64 位乘法、浮点软件模拟等。

.a 里每个成员仍然是完整的 .o，带着自己的符号表和重定位表。归档本身不做任何合并，只做打包加索引。

3. 用 .a 链接 #

bash
gcc main.c -L. -lmyhello -o app_static

三个细节：

  • -L. 把当前目录加入库搜索路径
  • -lmyhello 简称，链接器会自动补成 libmyhello.a（或 libmyhello.so，优先 .so）
  • 想要强制静态，加 -static，或者直接写文件名 gcc main.c ./libmyhello.a -o app_static

-static 的含义要精确理解：它让链接器在整个链接过程中不使用任何共享库，包括 libc。所以产物是一个完全自包含的可执行文件，扔到任何同架构的 Linux 上都能跑，前提是内核版本别太老。

验证「库代码被复制进去了」很简单：

bash
./app_static            # 能跑
rm libmyhello.a         # 删掉静态库
./app_static            # 依然能跑
file app_static         # 显示 statically linked

删掉库还能跑，就是静态链接最硬的证据。库的机器码已经躺在可执行文件里了，跟原库文件再没关系。

4. 静态库的三个代价 #

静态链接不是没有成本，代价在这三处：

体积。每个可执行文件都带一份库代码。十个程序都用 printf，磁盘上就有十份 printf 的机器码。

升级。库里修了个安全漏洞，你得重新编译、重新分发每一个用到它的程序。没有别的办法，因为代码是复制过去的。

内存。同时跑十个这样的程序，物理内存里有十份完全相同的库代码页，无法共享。

这三条加起来，就是动态库存在的全部理由。第八章把静态链接走完整，第九章开始讲动态库怎么解决它们。

八、静态链接的过程 #

拿 hello world 走一遍完整的静态链接。

bash
gcc -c main.c -o main.o
ar rcs libmyhello.a hello.o
gcc main.o -static -L. -lmyhello -o hello
./hello
file hello

file hello 会告诉你 statically linked。想看清链接器到底被喂了什么，加 -v：

bash
gcc -v -static -o hello main.c 2>&1 | grep collect2

输出是一行长得离谱的命令，实际调的是 collect2，参数里有这么几段：

参数 含义
--sysroot=... 系统库根目录，替代编译时配置的默认值
-Bstatic 后续库按静态方式解析，不和 .so 纠缠
-dynamic-linker /lib/ld-linux.so.3 指定动态链接器，静态链接场景下写了也没用
-X 丢弃编译器生成的 .L 前缀临时符号
-m armelf_linux_eabi 指定 emulation 模式，决定用哪份链接脚本
--start-group -lgcc -lgcc_eh -lc --end-group 这三个库循环扫描，直到符号不再新增
crt1.o、crti.o、crtbeginT.o、crtend.o、crtn.o C 运行时的启动/收尾代码

那 5 个 crt*.o 值得展开。你在源码里写的入口是 main，但 main 不是 ELF 的入口。ELF 入口是 _start，它住在 crt1.o 里（有些系统叫 crt0.o）。这段引导代码所有程序共用，所以被单独抽出来，链接时拼进去。

反汇编 crt1.o 的 _start：

armasm
00000000 <_start>:
   0:    e59fc024     ldr    ip, [pc, #36]    ; 2c
   4:    e3a0b000     mov    fp, #0
   8:    e49d1004     ldr    r1, [sp], #4     ; r1 = argc, sp += 4
   c:    e1a0200d     mov    r2, sp           ; r2 = argv
  10:    e52d2004     str    r2, [sp, #-4]!   ; 压入 stack_end
  14:    e52d0004     str    r0, [sp, #-4]!   ; 压入 rtld_fini
  18:    e59f0010     ldr    r0, [pc, #16]    ; 30 -> main 函数指针
  1c:    e59f3010     ldr    r3, [pc, #16]    ; 34 -> __libc_csu_init
  20:    e52dc004     str    ip, [sp, #-4]!   ; 压入 fini
  24:    ebfffffe     bl     0 <__libc_start_main>

_start 干的事只有一件：给 __libc_start_main 准备参数，然后把控制权交给 C 库。原型大致是 int __libc_start_main(int (*main)(int, char **, char **), int argc, char **argv, void (*init)(void), void (*fini)(void), void (*rtld_fini)(void), void *stack_end)。前 4 个参数走 r0~r3 寄存器，后 3 个压栈，和 AAPCS 规定一致。mov fp, #0 是刻意为之：fp 清零标记「最外层栈帧」，调试器回溯栈时看到 fp == 0 就知道到底了。

内核往用户态跳的那一刻，只精确设定三个寄存器：PC 指向 _start，SP 指向用户栈（栈上已经摆好 argc、argv、envp），r0 按平台约定放一个 atexit 用的 handler（3.14 内核里这个值是 NULL）。其余寄存器不管。

.note.ABI-tag 描述操作系统的 ABI 要求，dump 出来是八个 word：vendor name 长度 4、data 长度 0x10、note type 1、"GNU"（0x00554e47）、0 表示 Linux、后面三个 word 是内核版本 2.6.14。

.init 装的是「进 main 之前要跑的东西」，C++ 里全局对象的构造函数就走这条路：

.tdata 和 .tbss 是线程局部存储的初值镜像。一个 hello world 也有这两个节，因为 libc 自己要用——errno 在多线程环境里必须是每线程一份。线程创建时以 .tdata / .tbss 为蓝本复制私有副本，之后所有访问都落在自己的副本上。

3. 为什么起始地址是 0x8000 #

第一个页不能映射。程序要能捕获空指针访问，0 地址那块必须留着不建页表，NULL 一解引用就触发缺页异常，内核给进程发 SIGSEGV。

那为什么不在 0x1000 开始，而是 0x8000？起始地址跟 MMU 支持的最大页大小挂钩。链接器的 MAXPAGESIZE 是编译时定死的（这套工具链里是 32 KB），所以基址是 0x8000。-z max-page-size=value 可以改它。

代码段长度 0x8000 + 0x6ed50 = 0x76d50，按 0x8000 对齐该落在 0x78000，实际却是 0x7f000。差的那段由链接脚本算出来：

text
. = ALIGN (0x8000) - ((0x8000 - .) & (0x8000 - 1));
. = DATA_SEGMENT_ALIGN (0x8000, 0x1000);

DATA_SEGMENT_ALIGN(maxpagesize, commonpagesize) 的算法是 ALIGN(maxpagesize) + (. & (maxpagesize - commonpagesize))，代入落定 0x7f000。

为什么要两个页大小？代码段长，用小页要建大量页表项，用大页划算；数据段短，用 32 KB 大页去装 1 KB 数据是浪费物理内存。所以代码段按 max page size 对齐，数据段按 common page size（4 KB）对齐。

九、动态库：.so 与共享对象 #

静态库的三个代价，动态库一次全解决。核心思路只有一句：不复制代码，只留名字，运行时再去找。

这个决策的连锁反应比想象中大。链接时库不在场，所以代码里的地址不能写死；不写死，就得靠间接寻址；间接寻址，就有了 GOT 和 PLT。第十章到第十二章全在填这个坑。

1. 造一个动态库 #

c
int xxx = 0x1234;

int yyy;

int foo(void)
{
    yyy = 0x5678;
    return xxx;
}

bash
gcc -fPIC -shared -o libfoo.so foo.c

两个选项缺一不可：-shared 让链接器产出共享对象，-fPIC 让编译器生成位置无关代码。少了 -fPIC，链接阶段就会碰壁。

2. .so 的段表 #

text
Program Headers:
  Type           Offset   VirtAddr   PhysAddr   FileSiz MemSiz  Flg Align
  LOAD           0x000000 0x00000000 0x00000000 0x005c0 0x005c0 R E 0x8000
  LOAD           0x0005c0 0x000085c0 0x000085c0 0x00118 0x00120 RW  0x8000
  DYNAMIC        0x0005cc 0x000085cc 0x000085cc 0x000e0 0x000e0 RW  0x4
  GNU_STACK      0x000000 0x00000000 0x00000000 0x00000 0x00000 RW  0x4

第一个 LOAD 的 VirtAddr 是 0。这就是 PIC 的直接证据：代码段没有固定加载地址，加载到哪都行。相比之下，静态可执行文件的 VirtAddr 是写死的 0x8000。

第二个 LOAD 的 VirtAddr 是 0x85c0，不是 0x5c0。因为代码段按 0x8000 对齐，数据段得跟在后面；库被加载到基址 X 时，数据段的运行时地址就是 X + 0x85c0。代码段在物理内存里只有一份，被所有进程共享——各进程页表指向同一批物理页；数据段不行，每个进程一份私有副本（写时复制）。DYNAMIC 段没有 LOAD 标记，不占进程地址空间，它是给 ld.so 看的说明书。

4. 两张符号表 #

十、位置无关代码 PIC #

动态库能被映射到任意地址，这件事本身就是 PIC 存在的全部理由。假设四个库 A、B、C、D，程序 P1 用 A B，P2 用 C D。如果库必须在编译时确定的地址加载，A B 和 C D 的地址段不重叠就够了，P1、P2 能同时跑。现在来了 P3，同时用 A B C D，四段地址必须互不重叠，得重新分配；改完之后 P1 虽然不用 C D，它的地址空间里也得给 C D 留着空位。地址空间是宝贵资源，这么留是浪费。

更麻烦的是升级：C 库版本更新、体积变大，原来那段地址装不下了，得重新找地方加载。库一多，这种地址编排就没法管理了。解法就是让库不管被放到哪都能跑，PIC，Position Independent Code。

1. 非 PIC 的代码长什么样 #

c
int xxx = 0x1234;

int yyy;

int foo(void)
{
    yyy = 0x5678;
    return xxx;
}

bash
gcc -c foo.c -o foo.o
readelf -r foo.o

text
00000030  00000e1c R_ARM_CALL        00000000   printf
00000044  00000f02 R_ARM_ABS32       00000004   yyy
0000004c  00000c02 R_ARM_ABS32       00000000   xxx

R_ARM_ABS32 要往代码里填一个 32 位绝对地址。反汇编看清怎么填的：

armasm
   8:   e59f2034        ldr     r2, [pc, #52]   ; 44 <.text+0x44>
   c:   e59f3034        ldr     r3, [pc, #52]   ; 48
  10:   e5823000        str     r3, [r2]
  44:   00000000        .word   0x00000000      ; 这里放 yyy 的地址
  48:   00005678        .word   0x00005678      ; 要写入的值

做法很直接：在正文段末尾（0x44）留一个 32 位槽保存 yyy 的运行时地址。代码和数据在同一个正文段，相对距离固定，用 ldr r2, [pc, #52] 取到槽的地址，再 str r3, [r2] 把值写进去。

问题就在这个槽。它存的是绝对地址，链接时填死；库被加载到别的位置，这个值就是错的。而且它在 .text 里，正文段只读，运行时改不了。R_ARM_CALL（bl 指令）稍微好一点，它是 PC 相对的，偏移量在 ±32 MB 内都能跳，但库被加载到哪里不知道，相对偏移也算不出来。

2. PIC 的代码怎么改 #

bash
gcc -fPIC -c foo.c -o foo_pic.o
readelf -r foo_pic.o

text
Relocation section '.rel.text' at offset 0x4e0 contains 5 entries:
 Offset     Info    Type            Sym.Value  Sym. Name
00000048  00000f1b R_ARM_PLT32       00000000   printf
00000064  00001019 R_ARM_BASE_PREL   00000000   _GLOBAL_OFFSET_TABLE_
00000068  0000111a R_ARM_GOT_BREL    00000004   yyy
00000070  00000d1a R_ARM_GOT_BREL    00000000   xxx

R_ARM_ABS32 全没了，换成三种新类型：

类型 作用
R_ARM_PLT32 函数调用走 PLT 桩，填桩的相对偏移
R_ARM_BASE_PREL 填「GOT 起始地址相对当前指令」的偏移
R_ARM_GOT_BREL 填「某符号的 GOT 项相对 GOT 起始地址」的偏移

核心思路是引入一层中间人：GOT（Global Offset Table）。代码不再直接引用符号地址，而是去 GOT 里取；GOT 在数据段，可写，由 ld.so 在加载后填入真实地址。

GOT 的位置由 _GLOBAL_OFFSET_TABLE_ 这个符号标记。它在 .o 阶段还只是个占位，R_ARM_BASE_PREL 那条重定位等最终链接完成就消失了。

反汇编 PIC 版本：

armasm
   c:   e59f4050        ldr     r4, [pc, #80]   ; 64 取 GOT 相对偏移
  10:   e08f4004        add     r4, pc, r4           ; r4 = GOT 首地址
  14:   e59f304c        ldr     r3, [pc, #76]   ; 68 取 yyy 在 GOT 内的偏移
  18:   e7942003        ldr     r2, [r4, r3]         ; r2 = yyy 的运行时地址
  1c:   e59f3048        ldr     r3, [pc, #72]   ; 6c
  20:   e5823000        str     r3, [r2]             ; *yyy = 0x5678
  64:   0000004c        .word   0x0000004c           ; 指令到 GOT 的偏移
  68:   00000000        .word   0x00000000           ; yyy 在 GOT 内的偏移
  6c:   00005678        .word   0x00005678

四步：算出 GOT 基址（add r4, pc, r4，用 PC 相对偏移叠加，全程不出现绝对地址）→ 取出符号在 GOT 内的偏移 → 从 GOT 项里读出真实地址 → 用它访问数据。

GOT 内的偏移在链接时确定，指令到 GOT 的偏移也在链接时确定，两者都是「相对量」，所以整段代码搬到哪都能跑。这就是位置无关。

代价是多了一次内存间接访问。每次访问全局变量，多一次 ldr。这是拿性能换灵活性，而且只能在数据段做文章，不能再改正文段。

3. PIC 和 PIE 不是一回事 #

目的 多进程共享同一份物理页 支持 ASLR，防止地址可预测
编译选项 -fPIC + -shared -fPIE + -pie

开了 PIE，主程序的代码段、栈、堆地址每次运行都变（ASLR）。缓冲区溢出加 ROP 的攻击链条需要知道 gadget 地址，地址随机化之后这个前提就没了。主流发行版现在默认开 PIE。

十一、GOT 与 PLT：延迟绑定 #

PIC 解决了「能不能搬」，GOT/PLT 解决「搬了之后怎么高效地找到函数」。

1. GOT 的内存布局 #

GOT 是一张指针表，每个需要间接引用的符号占一项，项里存该符号的运行时绝对地址。它在数据段，可读写，由 ld.so 在加载（或首次调用）时填。

.so 里查 GOT 的位置：

text
 56: 000086ac     0 OBJECT  LOCAL  HIDDEN  ABS _GLOBAL_OFFSET_TABLE_

0x86ac 是偏移，不是运行时地址。库被加载到基址 A 时，GOT 实际在 A + 0x86ac。

yyy 这个变量在 GOT 里占的项，由 .rel.dyn 里的一条重定位描述：

text
000086bc  00000815 R_ARM_GLOB_DAT    000086dc   yyy

0x86bc 就是 yyy 的 GOT 项位置。R_ARM_GLOB_DAT 的意思是「把符号的最终地址填进这个 GOT 项」。ld.so 干活的时候，把 yyy 的真实地址写到 A + 0x86bc 处。

.so 里访问 yyy 的代码：

armasm
 568:   e59f202c     ldr    r2, [pc, #44]   ; 59c 取得 GOT 相对偏移
 56c:   e08f2002     add    r2, pc, r2           ; GOT 绝对地址
 570:   e59f3028     ldr    r3, [pc, #40]   ; 5a0 yyy 在 GOT 内的偏移
 574:   e7921003     ldr    r1, [r2, r3]         ; 从 GOT 项取出 yyy 地址
 578:   e59f3024     ldr    r3, [pc, #36]   ; 5a4
 57c:   e5813000     str    r3, [r1]             ; *yyy = 0x5678
 59c:   00008138     .word  0x00008138           ; 指令到 GOT 的偏移
 5a0:   00000010     .word  0x00000010           ; yyy 在 GOT 内的偏移

和第十章那段一个套路。区别在于这里的偏移 0x8138 是链接完就定死的常量——代码段和数据段的相对位置在链接时固定，加载时也按这个关系映射，所以能拿 PC 加常量算出 GOT 地址。

2. PLT：延迟绑定 #

函数调用比数据访问多一层麻烦。GOT 里每个函数项都要在加载时填好地址，那 ld.so 就得解析所有函数——一个几百个符号的程序，启动时全解析一遍，慢。延迟绑定（lazy binding）的做法是：第一次调用才解析。PLT（Procedure Linkage Table）在代码段，只读，每个外部函数一个桩；GOT（对函数而言是 .got.plt）在数据段，可写，每项存函数地址。

首次调用 foo() 的流程：

text
 用户代码         PLT (.plt)           GOT (.got.plt)        ld.so
+--------+     +----------------+    +---------------+   +--------------+
|call foo+---->| foo@plt:       |    | foo@got:      |   |              |
+--------+     |  jmp *foo@got  +--->|  指向 plt+6   |   |              |
               |  push reloc_arg|<---+ (未解析时回跳)|   | 1. 查 foo 地址|
               |  jmp resolve   |                        | 2. 写 foo@got |
               +-------|--------+                        | 3. 跳过去执行 |
                       v                                 |              |
               +----------------+                        |              |
               | resolve:       |                        |              |
               |  调用 ld.so    +----------------------->|              |
               +----------------+                        +--------------+
  1. call foo@plt 跳到桩里
  2. 桩执行 jmp *foo@got，此时 GOT 项还没填好，值是「回跳指令的地址」，于是控制流回到桩里下一条指令
  3. 压入一个重定位参数（表示「我要解析 3 号函数」），跳进解析器
  4. 解析器调 ld.so 找到 foo 的地址，写进 foo@got，然后跳过去执行
  5. 第二次调用时，foo@got 已经是真地址，jmp *foo@got 直接到位，只花一次间接寻址
对比项 GOT PLT
位置 数据段（.got、.got.plt） 代码段（.plt、.plt.sec）
权限 可读写 只读可执行
存什么 符号的绝对地址 一段跳转桩代码
谁改它 ld.so 不改，只读

想关掉延迟绑定，让所有符号在启动时解析完：

bash
LD_BIND_NOW=1 ./app
gcc -Wl,-z,now -o app main.c -lmyfunc

-z now 在现代发行版里已是默认，因为延迟绑定让控制流在运行时可变，给攻击者留了改写 GOT 的机会。-z relro -z now 一起用，加载完就把 .got.plt 段设成只读。

十二、动态链接器的工作 #

程序启动时，内核不负责加载 .so，它只负责把 ld.so 拉起来，剩下的事交给 ld.so。

1. 入口在 .interp 里 #

bash
readelf -l ./app | grep interpreter

text
      [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]

内核读段表，找到 PT_INTERP，取出那个路径字符串，把 ld.so 和执行文件一起映射进进程空间，然后把 PC 设到 ld.so 的入口。

所以「谁加载谁」的链条是：内核查 .interp → 加载 ld.so → ld.so 加载所有依赖库 → ld.so 把控制权交给 _start。

2. ld.so 的五步 #

  1. 读依赖：解析 .dynamic，把 NEEDED 项全捞出来，这就是依赖库的 Soname 清单
  2. 找库：按搜索顺序定位每个 .so 文件
  3. 映射：用 mmap 把库的 PT_LOAD 段落映射进虚拟地址空间
  4. 重定位：解析符号，填 GOT，做延迟绑定的准备工作
  5. 初始化：跑 .init / .init_array，然后跳 _start

3. 库搜索顺序 #

ld.so 找一个 Soname 时不带路径的库，优先级从高到低：

优先级 机制 配置方式 说明
1 DT_RPATH 编译期 -Wl,-rpath 旧机制，存在 DT_RUNPATH 时被忽略
2 LD_LIBRARY_PATH 运行期环境变量 调试常用，setuid 程序会忽略它
3 DT_RUNPATH -Wl,-rpath,--enable-new-dtags 现代做法，优先级低于环境变量
4 /etc/ld.so.cache ldconfig 扫 /etc/ld.so.conf 生成 系统标准库的索引缓存
5 默认路径 固定 /lib、/usr/lib、/lib64、/usr/lib64

Linux 的 ld.so 不在当前目录找库。这和 Windows 优先找 EXE 同级目录的行为相反。.so 和程序放一起却跑不起来，原因就在这。

4. RPATH 与 RUNPATH #

早期 ld 写的是 DT_RPATH，它比 LD_LIBRARY_PATH 优先级高，于是运维遇到难题：测试想用环境变量切到新版本 .so 覆盖，做不到。DT_RUNPATH 就是来修这个的，它排在 LD_LIBRARY_PATH 之后。加 --enable-new-dtags 之后，现代 ld 会两个都写，ld.so 看到 RUNPATH 就忽略 RPATH。

bash
readelf -d ./app | grep -E '(RPATH|RUNPATH)'

text
 0x000000000000000f (RPATH)              Library rpath: [/data/lib]
 0x000000000000001d (RUNPATH)            Library runpath: [/data/lib]

5. $ORIGIN：相对自身定位 #

软件要装到客户机器的未知路径，又不能要求用户配环境变量，用 $ORIGIN：

bash
gcc -Wl,-rpath,'$ORIGIN/../lib' -o bin/app src/main.c -Llib -lmyfunc

$ORIGIN 是 ld.so 的内置宏，代表可执行文件所在目录的绝对路径。程序装在 /opt/myapp/bin，库在 /opt/myapp/lib，ld.so 自动算出正确路径；整套目录搬到 /home/user/myapp 也不用改。注意必须加单引号，否则 shell 会把 $ORIGIN 当自己的变量展开成空串。

6. 看清搜索过程 #

bash
strace -e trace=open,openat ./app
LD_DEBUG=files ./app

strace 看重试了哪些路径，LD_DEBUG 看 ld.so 自己的决策日志，输出形如 find library=libdl.so.2 [0]; searching、search cache=/etc/ld.so.cache、trying file=/lib64/libdl.so.2。LD_DEBUG 的取值：files 看加载与搜索，symbols 看符号解析轨迹，bindings 看绑定结果，versions 看版本校验，all 全开。符号被谁覆盖、库从哪来，这几条命令一跑就清楚。

ldconfig 相关的动作要记住：改完 /etc/ld.so.conf（或往 /etc/ld.so.conf.d/ 丢一个 .conf）必须 sudo ldconfig 刷新缓存，否则新目录不生效。

十三、运行时加载：dlopen 与 dlsym #

编译期链接是「一开始就绑死」，dlopen 是「跑起来再说」。插件系统、热更新、可选依赖都靠它。

接口 原型 作用
dlopen void *dlopen(const char *file, int flag) 加载 .so，返回句柄；NULL 表示主程序自己
dlsym void *dlsym(void *handle, const char *sym) 按名字取符号地址
dlerror char *dlerror(void) 取最近一次错误描述，成功返回 NULL
dlclose int dlclose(void *handle) 引用计数减一，归零则卸载

dlopen 的 flag 是重点：

标志 含义
RTLD_LAZY 用到才解析符号
RTLD_NOW 立刻解析全部符号，有未定义的就失败
RTLD_GLOBAL 导出的符号可被后续加载的库看到
RTLD_LOCAL 默认值，符号只在本库内可见

1. 一个能跑的完整例子 #

c
/* libmath.c */
int add(int a, int b) { return a + b; }
int sub(int a, int b) { return a - b; }

c
/* main.c */
#include <stdio.h>
#include <dlfcn.h>

typedef int (*binop_t)(int, int);

int main(void)
{
    void *h = dlopen("./libmath.so", RTLD_NOW);
    if (!h) { fprintf(stderr, "dlopen: %s\n", dlerror()); return 1; }

    binop_t add = (binop_t)dlsym(h, "add");
    binop_t sub = (binop_t)dlsym(h, "sub");
    const char *err = dlerror();
    if (err) { fprintf(stderr, "dlsym: %s\n", err); dlclose(h); return 1; }

    printf("3 + 4 = %d\n", add(3, 4));
    printf("3 - 4 = %d\n", sub(3, 4));
    dlclose(h);
    return 0;
}

bash
gcc -fPIC -shared -o libmath.so libmath.c
gcc main.c -o app -ldl
./app

-ldl 必须加（glibc 2.34 之后 dl* 并入 libc，老代码加上也无害）。dlsym 返回 void *，C 标准不允许它直接转函数指针，所以要显式强转；GCC 在 -pedantic 下会警告，实践中照转不误。

2. 插件反向调主程序：-rdynamic #

插件里如果引用了主程序定义的符号，dlopen 会报 undefined symbol。原因是主程序的符号默认没导出到动态符号表。

bash
gcc main.c -rdynamic -o app -ldl

-rdynamic 等价于 -Wl,--export-dynamic，让主程序的符号进 .dynsym。另一个办法是先把依赖库用 RTLD_GLOBAL 打开，再开插件。

3. LD_PRELOAD：抢先装载 #

LD_PRELOAD 指定的库排在所有依赖库之前加载，同名符号先被它抢到。拿它 hook malloc：

c
#define _GNU_SOURCE
#include <stdio.h>
#include <dlfcn.h>

void *malloc(size_t size)
{
    static void *(*real_malloc)(size_t) = NULL;
    if (!real_malloc)
        real_malloc = dlsym(RTLD_NEXT, "malloc");

    fprintf(stderr, "[hook] malloc(%zu)\n", size);
    return real_malloc(size);
}

bash
gcc -fPIC -shared -o libhook.so hook.c -ldl
LD_PRELOAD=./libhook.so ls

RTLD_NEXT 是关键：它让 dlsym 跳过自己，去找下一个定义了这个符号的库，也就是真正的 libc malloc。没有它就会递归调自己，栈溢出。同一个机制可以用来做内存泄漏检测、系统调用审计、故障注入。

4. C++ 类怎么动态加载 #

dlsym 只认符号名，取不到 C++ 类的构造函数——类名不是符号名。做法是导出 extern "C" 工厂函数，跨库只传 C 指针：

cpp
struct shape { virtual ~shape() {} virtual void draw() = 0; };

class circle : public shape {
public:
    void draw() override { puts("circle"); }
};

extern "C" shape *create_shape(void) { return new circle(); }
extern "C" void destroy_shape(shape *s) { delete s; }
extern "C" void shape_draw(shape *s) { s->draw(); }

bash
g++ -fPIC -shared -o libplugin.so plugin.cpp
g++ main.cpp -o app -ldl          # 主程序 dlsym(h, "create_shape") 拿工厂

虚表、name mangling、异常处理全被挡在库内部，跨库传递的只有裸指针。

5. 符号冲突：先加载的赢 #

libA.so 和 libB.so 都导出了 foo()，主程序两个都链接，调 foo() 走哪个？

ld.so 的规则是「先入为主」：符号解析按加载顺序进行，第一个提供 foo 的库拿到绑定。后面那个库里的 foo 虽然存在，但永远调不到。这种 bug 极难查，因为代码看起来完全正常。

三种防法：

手段 做法
收窄导出 -fvisibility=hidden，只导出必需接口
链接期包装 gcc main.o -Wl,--wrap=foo，把 foo 调用重定向到 __wrap_foo
隔离命名 内部符号加模块前缀

--wrap 的用法值得记：链接器把所有对 foo 的引用改成 __wrap_foo，同时把所有对 __real_foo 的引用改成 foo。你在 __wrap_foo 里决定调真的还是干别的。

十四、符号可见性与版本 #

第五章讲 Bind（LOCAL / GLOBAL / WEAK）时提过一句：它服务的是 .o 之间的解析，静态链接器用。到了动态链接，光有 Bind 不够，还得有 Visibility——它管的是运行模块之间的可见性。

readelf -s 输出里那一列 Vis 就是它。

场景：A.o、B.o、C.o 链接成 libABC.so，A.o 要调 B.o 里的 bb()。bb 必须是 GLOBAL，否则静态链接器都过不去。但 bb 不是这个库的对外接口，不应该被外部看到。如果整个库把所有 GLOBAL 符号都导出，符号污染、命名冲突、加载变慢全来了。

可见性 含义 行为
DEFAULT 公开 导出，参与动态链接，可被覆盖
PROTECTED 公开但不可覆盖 导出，但库内部引用优先绑到自己这份
HIDDEN 隐藏 不导出，不参与动态链接
INTERNAL 内部 别的模块不能访问

两种控制方式：

bash
gcc -fPIC -shared -fvisibility=hidden -o libfoo.so foo.c

c
__attribute__((visibility("default"))) void api_func(void);
__attribute__((visibility("hidden")))  void internal_func(void);

-fvisibility=hidden 把默认行为改成「全隐藏」，然后用属性逐个把要导出的接口点亮。这是写库的标准姿势：默认关，显式开。

static 也能隐藏，但它只能管本 .o，多个 .o 组成的库内互相调用就废了。要在一个 .so 内部跨 .o 共享、对外不导出，只能用 visibility。

1. extern "C" 与名字修饰 #

C++ 为了支持重载，会把参数类型编进符号名：void hello(int) 变成 _Z5helloi。C 编译器不做这件事，void hello() 的符号名就是 hello。

于是 C++ 程序链接 C 库时，去找 _Z5helloi，库里只有 hello，链接器报 undefined reference。

c
#ifdef __cplusplus
extern "C" {
#endif

void print_hello(const char *name);
int add_numbers(int a, int b);

#ifdef __cplusplus
}
#endif

extern "C" 关掉这一段的名字修饰。头文件这么写，C 和 C++ 都能用。

验证一下修饰结果：

bash
echo 'void hello(int){}' | g++ -x c++ -c - -o t.o && nm t.o

输出里是 T _Z5helloi。改成 extern "C" 再编，输出变 T hello。

2. 弱符号 #

c
__attribute__((weak)) void custom_logger(const char *msg)
{
    printf("[default] %s\n", msg);
}

void do_work(void) { custom_logger("running"); }

库给一个默认实现，主程序如果定义了同名的强符号，链接器自动用主程序那份，库里的被丢弃。框架留钩子、驱动做硬件抽象、单元测试替换依赖，都用这一招。配合 if (custom_logger) 可以判断外部有没有提供实现——弱符号未定义时它的地址是 0。

3. 符号版本 #

nm -D 的输出里常见 puts@@GLIBC_2.2.5 这种带 @ 的写法。@ 后面是版本号，@@ 表示默认版本，单个 @ 表示兼容用的旧版本。libc 靠这个让同一个符号有多个 ABI 变体：老二进制找 memcpy@GLIBC_2.2.5，新二进制找 memcpy@@GLIBC_2.14，两套实现共存于一个 libc.so.6 里。这就是为什么二十年前编的程序在今天的系统上还能跑。

自己写库也能用版本脚本控制：

text
/* libfoo.map */
FOO_1.0 {
    global:
        foo_init;
        foo_run;
    local:
        *;
};

FOO_2.0 {
    global:
        foo_run_v2;
} FOO_1.0;

bash
gcc -fPIC -shared -Wl,--version-script=libfoo.map -o libfoo.so foo.c

local: *; 把没列出的符号全藏起来，等价于 -fvisibility=hidden 的效果。版本节点之间有继承关系（FOO_2.0 继承 FOO_1.0），旧接口保持不变，新接口挂在新的版本节点上。

查看版本需求：

bash
readelf -V ./app
objdump -T libfoo.so | grep FOO

十五、查看与调试工具：nm、objdump、readelf、ldd #

手上有一套工具，链接问题不用猜。

工具 看什么 典型命令
file 文件类型、静态还是动态链接 file ./app
readelf ELF 结构，按规范直译 readelf -h/-S/-l/-s/-r/-d/-V
objdump 反汇编、节内容、符号、重定位 objdump -d/-D/-t/-T/-h/-s/-r
nm 符号清单，带类型字母 nm -a/-D/-u/-g/--defined-only
ar 静态库的成员管理 ar -t/-x/-r/-s
ldd 运行期依赖库及解析结果 ldd ./app
strings 文件里的可打印字符串 strings -a libfoo.so
strip 删除符号表与调试信息 strip libfoo.so
ldd/LD_DEBUG 动态链接器决策日志 LD_DEBUG=files ./app

readelf 的参数记住这七个就够：-h 文件头、-l 段表、-S 节表、-s 符号表、-r 重定位、-d 动态段、-V 版本。

1. nm 的符号字母 #

bash
nm -s a.out
nm -u libfoo.so
nm -D --defined-only libfoo.so
字母 含义
T / t 正文段（代码），大写全局、小写局部
D / d 已初始化数据段
B / b .bss 段
R / r 只读数据段
U 未定义，需要外部提供
W / w 弱符号
A 绝对地址（链接脚本符号、FILE 符号）
C common 符号
N 调试符号
? 类型未知

-D 看动态符号表，-u 只看未定义，-g 只看外部，--defined-only 只看已定义，-C 把 C++ 修饰名还原成可读形式，-l 显示源码行号（要求编了 -g），--size-sort 按大小排序。查「这个库到底导出了什么」，用 nm -D --defined-only；查「这个库依赖谁」，用 nm -u。

2. objdump 常用选项 #

选项 作用
-h / -x 节表摘要 / 所有头信息（等价 -a -f -h -r -t）
-t / -T 符号表 / 动态符号表（类似 nm -s 与 nm -D）
-d / -D 反汇编含指令的节 / 反汇编所有节
-r / -R 重定位入口 / 动态重定位入口
-s / -j name 指定节的完整内容 / 只看指定节
-S / -C / -l 反汇编插入源码 / 还原 C++ 修饰名 / 标注行号 
bash
objdump -h libtest.o
objdump -t libtest.o
objdump -d -j .text libtest.o
objdump -s -j .comment hello.o
objdump -T libfoo.so | grep foo

objdump -h 输出里每个节后面带属性：CONTENTS 有内容、ALLOC 占内存、LOAD 需加载、RELOC 有重定位、READONLY 只读、CODE 是代码。.o 里 .text 常同时带 CONTENTS, ALLOC, LOAD, RELOC, READONLY, CODE——RELOC 这一项就是在说「这个节还没重定位完」。

3. ar 的成员管理 #

操作 作用
ar -t lib.a / ar tv lib.a 列出成员名 / 带权限、大小、时间列成员
ar -x lib.a / ar -p lib.a member.o 解出全部成员 / 把指定成员打到标准输出
ar rcs lib.a a.o b.o 创建/替换并建索引
ar d lib.a a.o / ar s lib.a 删除成员 / 只更新符号索引（等价 ranlib）

-s 建的那张索引表就是链接器「按符号找成员」的依据。缺了它，链接器只能线性扫，慢得明显；而且如果库是用 q 追加的，索引会过期，得补一次 ar s。

4. ldd 的坑 #

ldd 看着人畜无害，实际上它会把文件当程序跑起来（老版本靠设置 LD_TRACE_LOADED_OBJECTS 让 ld.so 打印依赖）。拿到来源不明的 ELF 就跑 ldd，等于给了它一次执行机会，安全替代是 objdump -p ./app | grep NEEDED 或 readelf -d ./app | grep NEEDED。输出里出现 not found 就是缺库，出现 => /path 就是解析成功。

十六、ELF 的滥用：解释器劫持与脱壳 #

知道结构之后，这些玩法都是自然推论。

1. 解释器劫持 #

场景：目标机器把可写盘挂成 noexec，或者内核监控非系统路径的程序执行。

bash
gcc hello.c -o hello
./hello                     # 正常
chmod -x hello
./hello                     # Permission denied
/lib64/ld-linux-x86-64.so.2 ./hello   # 又跑起来了

ld.so 本来应该是内核调的，但它的 main 就是个普通函数，你可以直接把它当程序调，参数传目标 ELF 路径。strace 能看到真正的 execve 打给的是 ld.so：

text
execve("/lib64/ld-linux-x86-64.so.2", ["/lib64/ld-linux-x86-64.so.2", "./hello"], ...) = 0

这条路径绕过了「文件有执行权限才可执行」的检查，也绕开了针对 execve 的监控规则，因为被执行的二进制是系统路径下的 ld.so。反过来还能改目标文件的 .interp，让它指向自己的程序：

bash
patchelf --set-interpreter /tmp/my_interp ./target

内核读到 PT_INTERP 就把控制权交给 /tmp/my_interp，于是任意代码在目标程序的进程里先跑起来——典型的前置劫持。

ldd 也沾这个风险。glibc 2.27 之前的 ld.so 会调用 ELF 指定的 interpreter，对可疑样本跑 ldd 等于执行了它的 interpreter。

2. 脱壳：删符号与破坏节表 #

bash
strip ./app

strip 前后 readelf -S 对比，删掉的是 .debug_aranges、.debug_info、.debug_abbrev、.debug_line、.debug_str、.symtab、.strtab、.shstrtab 这八个节，节头数量从 35 掉到 28。删的全是没有 ALLOC 标记的节，程序照样跑——因为执行只依赖段表。

再狠一点：既然节表对执行不是必需品，那就故意破坏它。IDA、Ghidra 这类工具构建视图时要读节信息，节表一坏，分析工具报错退出；逆向人员只能改用动态调试，把内存 dump 出来，再按段表还原。线索就在段和节的映射关系里：一个段包含多个节，节按内存权限和特征分布。有详细日志的程序，还能写脚本从日志里批量恢复符号名。

3. Fuzzing：把函数抽出来单独跑 #

分析 IoT 固件里的定制 httpd，想 fuzz 某个处理输入的函数。走网络请求变异效率太低，前面的解析路径也太长。ELF 给了另一条路：动态链接的可执行文件是 ET_DYN，和 .so 类型相同。

bash
readelf -h hello | grep Type

text
  Type:  DYN (Shared object file)

两者真正的差别只在「有没有连 libc、有没有 main」。既然 .so 可以 dlopen 出来按符号调，那把一个可执行文件改造成 .so，把目标函数导出到 .dynamic/.dynsym，修一下文件头，就能直接 dlsym 拿到那个函数。这活有人做过了，lief 的 bin2lib 就是；hugsy 用这个路子复现了 Exim 的溢出漏洞（CVE-2018-6789）。函数从完整程序里抽出来，输入直接喂，效率比走网络高几个数量级。

4. 加壳那一侧 #

反过来，保护程序的人在做相反的事：把 ELF 头加密，运行前再解。用户空间用 HMAVIC 之类的标记前缀重写文件开头，把 e_ident 之后的 ELF header（可选加上 program header table、section header table）用异或或 RSA 覆写，此时 readelf -h a.run 已经读不出来，xxd -l 100 a.run 能看到那个前缀。内核空间在 binfmt_elf 处理之前插一层，识别到前缀就解密回原样，再交回内核正常流程。

密钥不硬编码在模块里，走内核密钥环——用 openssl req -x509 -nodes 生成自签名证书，在内核配置里打开 CONFIG_SYSTEM_TRUSTED_KEYRING 并用 CONFIG_SYSTEM_TRUSTED_KEYS="certs/kernel_key.pem" 把证书编进去，编译时能看到 EXTRACT_CERTS certs/kernel_key.pem，烧录后 /proc/keys 里能查到这把钥匙。之后模块里用 verify_pkcs7_signature() 验签，验过才解密。

这条链子建立在同一个前提上：ELF 头格式固定、位置死板、必须明文才能被内核读懂。谁掌握了「在哪改、改什么」，谁就能加密它，也就能破解它。

十八、易错点速查 #

易错点 真相
以为 -static 只影响自己的库 它让整个链接不用任何 .so，包括 libc，产物体积暴涨
以为 -lfoo 只找 .a 优先找 libfoo.so，要静态得写 -static 或直接给 .a 路径
以为库放哪都行 必须放在引用它的 .o 之后，链接器只从左到右扫一遍
以为 .o 里有地址 .o 里全是相对偏移，Addr 字段一律 0
以为符号表删了程序就废 静态链接的程序 strip 后照跑，动态链接的删 .dynsym 才废
以为 main 是入口 入口是 _start（crt1.o），它调 __libc_start_main，后者才调 main
以为 .bss 占文件空间 它 NOBITS，文件里不占字节，只在内存里占
以为动态库只有一张符号表 .symtab 给静态链接器/调试器，.dynsym 给 ld.so
以为 -fPIC 可有可无 只要产物是 .so，所有参与链接的 .o 都必须 -fPIC
以为 GOT 是代码 GOT 在数据段，可读写；PLT 在代码段，只读
以为延迟绑定没代价 首次调用要走一遍解析器，安全上还允许运行期改 GOT
以为 LD_LIBRARY_PATH 万能 setuid 程序会忽略它，那种场景只能靠 RPATH/RUNPATH
以为 ld.so 会找当前目录 不会。要么配路径，要么 $ORIGIN
以为 soname 是文件全名 它是运行期别名，libfoo.so.1，不带次版本号
以为同名函数会报冲突 动态链接下先加载的赢，后加载的静默失效
以为 strip 能保护代码 只能提高阅读成本，逻辑还在，动态调试照样能还原
以为 ldd 只是读文件 它会执行目标程序，可疑样本别用它

一条链串起来记：源码 .o 里符号是待定的 → 静态链接把库代码复制进来、地址全部填死 → 动态链接只留名字，靠 PIC 让代码可搬、靠 GOT 让地址可改、靠 PLT 让解析推迟到首次调用 → ld.so 在启动时补齐这一切。体积、升级、部署上的所有差别，都是从「复制代码」还是「只留名字」这一个选择派生出来的。
