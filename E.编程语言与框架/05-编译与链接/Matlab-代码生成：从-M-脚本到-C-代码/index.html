本篇讲「算法怎么落到板子上」这条工具链：怎么把 .m 函数或 .slx 框图变成一堆 .c/.h，怎么打包成 .so 让别的程序加载，怎么验证生成的代码跟 Matlab 里跑的是一个东西。不讲算法本身怎么写，不讲滤波器怎么设计、控制器怎么整定——那是信号处理和控制理论的地盘；也不讲 MCU 外设怎么配，那在驱动那一卷。读完你要能做到：拿到一份 Matlab 算法，判断它能不能生成代码；能生成的话，知道走哪条路、卡在哪、怎么验。

一、为什么要把 Matlab 变成 C #

Matlab 是研发环境，不是运行环境。滤波器在 Matlab 里调好、频响验证完、数据跑通，接下来要放到板子上——板子上没有 Matlab。

跑不了的原因很直接：解释器加运行时太大，塞不进多数 MCU 的 Flash；产品出货不能捆绑 Matlab 运行时和许可证；自动内存管理让最坏执行时间算不出来，而实时控制要的是确定性。

所以只能翻译成 C。手工抄当然可以，小算法半天抄完。问题在于抄错一个索引边界条件就差一，输出飘了还看不出来；算法迭代一次 C 代码要跟着改一遍；别人审你的 C，没法跟 Matlab 原稿对上。代码生成解决的就是这三件事，产物是「从原稿机械翻译出来的 C」，改算法只改 Matlab，重新生成一次。

1.1 难点不是翻译，是对齐语义 #

看着都是「算一个矩阵乘」，底下的假设完全不同：

维度 Matlab C
类型 动态，运行时决定 静态，编译期固定
变量大小 随时可变 声明时定死，或显式申请堆
内存 自动管理 静态区、栈、堆，你选一个
索引 从 1 开始 从 0 开始
矩阵 语言内建，A*B 就是矩阵乘 没有内建，自己写循环或调库
复数 原生支持 自己定结构体
越界访问 报错并中止 未定义行为，不报错
整数溢出 饱和或报错，看设置 静默回绕
函数重载 按参数类型自动选 不支持，要改名

这张表里任何一行都是代码生成要处理的问题。别把它当格式转换，它是语义翻译。

1.2 本质：把动态语义翻成固定结构 #

代码生成的本质，是把 Matlab 的动态语义，翻译成一份固定的 C 结构。

Matlab 允许第 10 行 x 是标量、第 20 行变成 100×100 矩阵；C 不允许，x 声明那一刻大小就死了。Matlab 允许 y = x + 1 里 x 是 double、int32、single 自动提升；C 不允许，类型不同得自己转、自己防溢出。Matlab 允许 a = [] 然后循环里 a(end+1) = v 一直长；C 不允许，数组长度是编译期常量。

生成工具做的事，就是在编译期把这些动态的东西推到静态：变量尺寸从输入样例或显式声明推出来定死，数据类型同样定死，内存分配全部静态或明确走 malloc（嵌入式目标多数禁用）。凡是推不出来的，就生成不了。 这是本篇的主线，后面所有失败案例本质都是「有个东西没定死」。

1.3 「能生成」和「能上板」是两回事 #

codegen 跑通、.c 出来了、报告绿勾一片——这只证明语法层面翻译成功，不证明能在你的板子上跑。生成的 double 运算，MCU 没 FPU 全靠软件浮点模拟，一次除法几百个周期，控制周期直接拉爆；生成的 64 位 double 在 32 位 MCU 上每次运算拆成多条指令；生成的代码带 malloc，你的工程没有堆；栈帧几百字节，任务栈只给 512 字节，一跑就 HardFault。

能生成是语法问题，能上板是资源问题。 中间隔着一步定点化，那是第六章。

二、三条代码生成路径 #

MathWorks 拆了三个产品，名字很像，作用完全不同。

项 MATLAB Coder Simulink Coder Embedded Coder
输入 .m 函数 .slx/.mdl 框图 前两者任一
产物 C/C++ 源码、MEX、静态库 C/C++ 源码含调度框架 同上，外加优化与合规配置
输入规格 给「输入样例」定类型定尺寸 框图本身是规格，端口类型在图上 同左
适合什么 数学函数、信号处理函数、单个模块 控制系统、状态机、多速率调度 要过 MISRA、要上定点、要针对芯片优化
要不要手写入口 要，得写一个能生成的入口函数 不要，框图就是入口 不要
授权 单独授权 单独授权 单独授权，且依赖前两者

三点：三个是分别授权的产品，你的 license 有没有、含哪些工具箱，去看自己的 license 清单，别照抄网上说法；Embedded Coder 不是「更好的 MATLAB Coder」，是给量产准备的配置层，能配代码风格、生成符合 MISRA-C 的子集、做处理器特定替换（比如把乘法换成芯片的 MAC 指令）、生成不依赖浮点库的定点代码；三者不互斥，常见做法是 MATLAB Coder 出算法函数，Simulink Coder 出调度框架，Embedded Coder 管代码规范和芯片优化。

2.1 选哪条：看算法有没有「时间」 #

判断标准很朴素：算法有没有「状态随时间推进」这回事。

没有——纯函数，输入进去结果出来，跟上一刻无关，比如 FFT、矩阵求逆、CRC、查表插值。走 MATLAB Coder，写个入口函数、给几个输入样例，生成完事。

有——一堆状态变量按固定周期往前推，比如 PID、卡尔曼滤波、状态机、多速率采样。走 Simulink Coder。框图天然表达了「这个模块每周期执行一次」「这个 10ms 跑、那个 1ms 跑」，这些信息在 .m 里要写一大堆样板代码才表达得清。

2.2 框图本身就是可执行规格 #

写 .m 时「这些代码按什么顺序、多久跑一次」是隐含在调用者里的，你的 step() 被谁调、多久调一次，代码里看不出来。框图不一样：连线方向就是数据流方向，采样时间标在模块上，求解器配置决定整个模型怎么推进。把 .slx 给同事看，他能直接说出控制器结构；把 .m 给他，他得读一遍代码才明白。模型本身就是一份可执行的设计文档——这是控制算法更适合走 Simulink 的根本原因。

三、MATLAB Coder 的约束 #

这些约束不是工具的缺陷，是 C 语言的物理限制投影到工具上。

3.1 第一道门槛：%#codegen #

matlab
function c = foo(a, b) %#codegen
% 该函数用于计算参数 a 和 b 的乘积
c = a * b; % 执行乘法操作

作用：告诉编辑器「这个函数要拿去生成代码」，于是按代码生成的规则检查语法，把不兼容的写法标出来。写 eval、syms、只在桌面环境能用的函数，编辑器直接给波浪线。它不是注释摆设——少了它，你会在 codegen 那一步才发现问题，报错信息还不如编辑器提示直观。位置有讲究：必须在 function 语句同一行末尾。

3.2 第二道门槛：所有变量尺寸必须定死 #

Matlab 里循环里 y = [y, x(k)] 让长度一直变，这生成不了。长度取决于运行时数据，而 C 的数组长度是编译期常量。两种改法。

改法一：定上界，用长度变量。

matlab
function [y, n] = grow(x) %#codegen
% x 最多 64 个元素, y 按上界开, n 是实际长度
y = zeros(1, 64, 'like', x);
n = 0;
for k = 1:numel(x)
    if x(k) > 0
        n = n + 1;
        y(n) = x(k);
    end
end

生成的 C 里 y 是固定 64 元素数组，n 是 int32_t，调用者拿 n 判断实际范围。这是 C 里处理变长数据的标准做法，工具只是把这个惯例强加给你。

改法二：真需要变长，用 coder.varsize 声明上界。

matlab
function y = grow2(x) %#codegen
coder.varsize('y', [1 64], [0 1]);   % 第二维可变, 上界 64
y = [];
for k = 1:numel(x)
    if x(k) > 0
        y = [y, x(k)];
    end
end

[1 64] 是上界形状，[0 1] 表示第一维固定、第二维可变，这一维写错会报 dimension 不匹配。生成的 C 是「数据缓冲区 + 当前长度字段」的结构体，底层仍是定长数组不是 malloc。两者差别：改法一生成裸数组加一个长度参数，干净好嵌；改法二生成结构体，接口多一层但用起来更接近 Matlab 写法。嵌入式优先改法一。

3.3 第三道门槛：数据类型必须显式 #

Matlab 默认 double，你不写类型，所有东西都是 double，生成到 C 里就是一排 double。图像处理里像素值多用 8 位无符号整数（uint8），值域 0 到 255，正好适合灰度图；音频采样值用 16 位有符号整数（int16），覆盖 -32768 到 32767 的幅度。这些类型在 C 里要显式写出来才能省内存：

c
uint8_t pixel_value;  /* 用于存储图像的像素值 */
int16_t sample_value; /* 用于存储音频的采样值 */

Matlab 侧要在入口函数里锁死类型，转换写在函数体里，或者通过 -args 传入已知类型的样例：

matlab
function y = img_gain(x, g) %#codegen
x = uint8(x);
g = uint16(g);
y = uint8(min(255, uint16(x) .* g / 256));

工具不会替你猜「这个变量用 uint8 就够了」——它只看到 double，就老老实实生成 double。常见错误是只在注释里写「这里应该是 uint8」，代码没转，最后怀疑工具。

3.4 内存必须静态分配 #

Matlab 允许变量大小动态变化，嵌入式不行，要在编译时把内存分配完。处理固定尺寸图像时先定义数组：

c
uint8_t image[HEIGHT][WIDTH]; /* 预定义图像的高度和宽度 */

收益是可预测性：栈帧固定、没有碎片、最坏执行时间能算。代价是提前知道最大尺寸，而且一直占着 RAM 不管用没用满。要真开了动态内存（配置里允许变长数组走堆），生成代码里会出现 malloc/free，嵌入式目标一般显式禁掉。

3.5 不能用的东西：一张清单 #

下面这些写了就生成不了，不是「生成得不好」，是直接报错。

写法 为什么不行 替代
eval/evalin/assignin 运行时解释字符串，C 没这层 显式分支或查表
syms/符号运算 需要符号引擎 事先解析成数值表达式
cell 数组 元素类型和大小未必相同 结构体数组，或按类型拆分
递归调用 栈深度运行时才确定 显式栈的迭代写法
函数句柄当参数传 运行时分派 switch 选分支
绝大多数工具箱函数 工具箱是解释器上的库 自己实现，或 coder.ceval 混编
try/catch C 没有异常机制 返回错误码
类与多数 OOP 特性 动态绑定 结构体 + 函数
隐式共享的全局变量 生成代码里语义会变 显式传参
isempty 后直接索引 尺寸不定 先定上界

工具箱函数这条要展开。它们可以视作模板——告诉你「这个功能这么做」，但本身进不了资源受限的目标。实时系统里复杂的界面相关工具箱函数根本没有实现，你得用基础数学函数把核心算法重写一遍。基础数学函数还有个附带好处：在生成代码里常能被内联成几条指令，比调库快。

生成前先做兼容性检查，看报告里 Code Generation Readiness 那一栏：

matlab
codegen -config:lib myfunc -args {zeros(3,1)} -report

红色是硬阻塞，黄色是「能生成但结果未必跟 Matlab 一致」——后者更危险，因为它不报错。

四、一个完整的生成流程 #

走一遍最小可用流程。用 foo.m 做例子，两个数相乘，看着没意义，但流程完整。

4.1 写入口函数、选编译器 #

matlab
function c = foo(a, b) %#codegen
% 该函数用于计算参数 a 和 b 的乘积
c = a * b; % 执行乘法操作

三条规矩：一个函数只做一件事（下游函数会被一起生成，但入口参数越少越好）；参数类型要能从样例推出来，或在函数体内显式转换；不要有脚本级副作用——不 load 文件、不 save、不画图、不读串口。

选编译器跑 mex -setup，列出机器上已装编译器，选一个，Windows 上常见 Microsoft Visual C++，选完可以再跑 mex -setup C 单独确认。这步不做也能生成代码（只出源码不编译），但做不了 MEX 验证，没法在 Matlab 里直接调生成函数比对结果。

4.2 命令行生成 #

matlab
codegen -config:lib myfunc -args {zeros(3,1)}

拆开看：-config:lib 是输出静态库，其他选项 -config:mex（生成 MEX，Matlab 内直接调）、-config:dll（动态库）；myfunc 是入口函数名；-args {zeros(3,1)} 是输入样例，多个参数写 {zeros(3,1), zeros(3,1), 1.0}。

样例不只是举例，它决定了生成的函数签名。zeros(3,1) 意味着生成的 C 第一个参数是 const double x[3]；改成 zeros(3,3) 就变成 const double x[9]。跑完在 codegen/lib/myfunc/ 下拿到：

text
codegen/lib/myfunc/
├── myfunc.c          主实现
├── myfunc.h          对外声明（你在 C 里 include 这个）
├── myfunc_types.h    自定义类型（有结构体时才有）
├── rt_nonfinite.c/h  非有限值处理
├── rtGetInf.c/h      Inf 常量
├── rtGetNaN.c/h      NaN 常量
├── rtwtypes.h        uint8_t/int32_t 等基础类型映射
├── myfunc_data.c     常量数据（有查表时才有）
├── buildInfo.mat     构建信息
└── html/             报告

你只需要 myfunc.h 加全部 .c，其余是报告和构建信息。

4.3 图形界面走一遍 #

不想记命令行就点界面。命令窗口输 coder 回车弹出 MATLAB Coder Project 对话框；New 选项卡里 Name 填 foo.prj，OK 进入 MEX Function 对话框；Overview 选项卡点 Add files 选 foo.m；选中变量 a 点 Define by Example…，MATLAB Expression 填 5，OK，b 同样操作填 6——这一步就是命令行里 -args 干的事；Build 选项卡把 Output type 设为 c/c++ Static Library，勾上 Generate code only，产物就是静态库源码而非可执行文件，方便后续在其他语言里调用；More settings → General → Language 设为 C++，Interface 里把所有选项去掉保证生成代码简洁兼容，Close；点 Build，完成后点 View report，报告列出 a、b、c 的类型和尺寸。

看报告这步别跳。它写清每个变量的推断类型，一眼就能看出有没有意外变成 double。

4.4 在主程序里调用 #

foo.h 大致是 #ifndef FOO_H / #define FOO_H / #include "rtwtypes.h" 三行头，加一句 extern double foo(double a, double b);（具体名字看报告）。调用就一行：

c
#include <stdio.h>
#include "foo.h"

int main(void)
{
    double a = 0.0, b = 0.0, c = 0.0;
    printf("Enter two numbers: ");
    if (scanf("%lf %lf", &a, &b) != 2) {
        return 1;
    }
    c = foo(a, b); /* 调用生成的 foo 函数执行乘法运算 */
    printf("c = %f\n", c);
    return 0;
}

编译时把生成目录下所有 .c 都编进去，包括看起来没用的 rt_nonfinite.c、rtGetInf.c，缺了会报链接错误：

bash
gcc -I codegen/lib/foo *.c -o test

4.5 老版本的 emlc 与 C 混编 #

早期工具叫 emlc（嵌入式 Matlab），新工程直接 codegen。老资料里这套写法仍然可用：

matlab
>> emlc adaptive-stats-roi.m -eg<In> -c -report

-report 生成一份 HTML 报告，里面有 C 源文件的超链接，同时自动生成需要的头文件。它的价值是把「Matlab 哪一行对应 C 哪一行」标出来了，review 好用。

另一个老功能是 C 混编。已经写好的 C 函数库不想重写，可以在 Matlab 里直接调：

c
Bool c_sort(float U[], int n, int m) {
    /* C function implementation for sorting */
}

用 eml_ceval 把输入输出传进去，替代原来的 Matlab 实现。比如 roi_stats.m 里原来调 mysort，换成调已有的 c_sort：

matlab
% Sort the sub-matrix only
sorted = eml_ceval('c_sort', eml_rref(V(1)), eml_wref(V(1)), count, int32(numel(V)));

eml_rref/eml_wref 是传引用/传写的包装。这条路适合「算法主体用 Matlab，热点用手写 C」——Matlab 侧能跑通完整流程，性能热点换成 C 实现，两边同一套接口。注意新旧命名对应：emlc → codegen，eml_ceval → coder.ceval，emlmex → codegen -config:mex。老文档里的名字现在还能见到，看到别懵。

五、Simulink Coder 与框图 #

框图的生成路径跟 .m 完全不同：没有「入口函数」这回事，模型本身就是入口。但配置项更多，也更容易配错。

5.1 搭框图、配求解器 #

用 Simulink 搭仿真框图，存成 .slx（老的 .mdl 也行）。两点注意：模块输入输出类型要显式，默认全是 double，等要定点化时才发现全是浮点端口，改动量很大；采样时间要标，多速率系统里不同模块跑在不同周期，这信息必须在图上。

菜单 Simulink → Model Configuration Parameters 进 Solver 页。Type 选 Fixed-step——变步长求解器的步长运行时才算出来，跟实时调度冲突，上不了板。Solver 选定步长算法，控制模型常用 ode4（四阶龙格库塔）解微分方程，简单模型用 ode1（欧拉）也行，快但精度低。Fixed-step size 填步长，可以先用 auto 跑通，后期按实际控制周期二次设置，比如 0.001 对应 1ms。

有个细节：.slx 里设 0.001，生成代码会用它作为基础采样时间，但实际调度周期由你的定时器决定。模型算的是「每 1ms 推进一次」，你得保证真每 1ms 调一次 step，否则内部积分会漂。

5.2 目标文件选 ert.tlc #

Code Generation 页，System target file 选 ert.tlc。ert = Embedded Real-Time，生成嵌入式风格的 C/C++，没有 OS 依赖、没有文件 IO，入口是 step 函数加 initialize/terminate，语言可选 C 或 C++。

目标文件 用途
grt.tlc 通用实时，带完整运行时，桌面仿真和快速原型
ert.tlc 嵌入式，精简运行时，无 OS 依赖，适合裸机
ert_shrlib.tlc 嵌入式 + 共享库，产物是 .dll/.so
autosar.tlc AUTOSAR 组件，汽车电子专用

上板选 ert.tlc。要生成能在别的程序里 dlopen 的库，选 ert_shrlib.tlc，或者用 ert.tlc 生成后再自己 gcc -shared 打包。

Interface 页勾上 continuous time（模型里有连续状态时必须），其余保持默认。这页决定接口形态：Code interface packaging 选 Nonreusable function（单实例，最简单）还是 Reusable function（可多实例，每实例一份状态）；多实例相关选项决定状态变量是全局的还是通过结构体指针传入。单实例最省事，多实例才能在一块板子上跑两份同样的控制器，选错了后期改要动调用方代码。

5.3 点按钮生成 #

生成成功后，模型同目录下出现两个文件夹：slprj/ert/（中间产物、缓存、共享工具函数）和 test_ert_rtw/。后者里是 test.c（模型主实现）、test.h（对外接口）、test_private.h（内部声明）、test_types.h（端口类型、状态结构体）、test_data.c（参数与常量）、ert_main.c（示例主程序，可参考可删）、rtwtypes.h（基础类型）、test.mk（生成的 makefile）、msvc/（Visual Studio 工程）。

test.c 里会有 test_initialize()（初始化建状态）、test_step()（单步推进，周期调用）、test_terminate()（收尾）。test.h 里还有 extern 的输入输出结构体，名字类似 test_U、test_Y。

5.4 在宿主上跑起来 #

msvc/ 目录下有 test.sln，用 Visual Studio 2013 打开（文件 → 打开 → 项目/解决方案），添加后编译运行。主文件骨架：

c
#include "test.h"

int main(void)
{
    test_initialize();               /* 先初始化 */

    while (1) {
        test_U.In1 = 1.0;            /* 给输入赋值 */
        test_step();                 /* 单步执行 */
        /* test_Y.Out1 里是本次输出 */
    }

    test_terminate();                /* 正常不会走到这 */
    return 0;
}

带积分环节的模型，可以通过 test_M->Timing.stepSize0 重新设置仿真步长——这个字段在 test.c 里定义为全局结构体，改它就是改模型内部认为的步长。验证方法：每次给输入设常值，看第五次调用后的输出。若模型是 y = 2u 加一个积分器，输入 1.0，输出应在 5.0 附近。对得上说明生成正确、调度顺序正确。

生成的 ert_main.c 是示例，写了 while(1) 死循环加一个 rt_OneStep() 处理定时中断标志位。上板时一般不用它：把 initialize/step/terminate 接到自己的调度器里——定时器中断置标志，主循环看到标志就调 step，ert_main.c 删掉或排除在编译之外。但先读一遍，它展示了正确的调用顺序和定时模型，比文档直观。

六、定点化：能不能上 MCU 的关键 #

前面反复说「能生成」不等于「能上板」。这一章讲为什么，以及怎么解决。

6.1 差距在浮点 #

Matlab 默认 double。生成的代码如果算法主体全是 double，到 MCU 上会发生这些事：没有 FPU 的芯片，加减乘除全靠软件库模拟，一次乘法几十到上百周期、一次除法更贵，1ms 控制周期里跑几百次浮点运算，时间预算直接爆掉；有 FPU 但只做单精度的芯片，double 还是要软件模拟；软浮点库本身占几 KB 到十几 KB Flash，double 常量每个 8 字节，查表就占满；软浮点函数栈帧不小，中断里跑一次就足以压穿任务栈。所以第一个判断是：你的板子有没有 FPU，是单精度还是双精度。

芯片档位 FPU 生成的浮点代码能不能跑
Cortex-M0/M0+ 无 慢，只能跑很轻的算法
Cortex-M3 无 同上，一般不用浮点
Cortex-M4F 单精度 float 可接受，double 不可接受
Cortex-M7F 单精度（部分双精度） 同上，看具体型号
Cortex-A 系列 有，多为双精度 浮点没问题，但要算功耗和成本

这就是门槛所在：生成的 C 是浮点的，而 MCU 经常没有 FPU。定点化是把「能生成」变成「能上板」的那一步。

6.2 定点是什么 #

思路很朴素：用一个整数代表小数，约定小数点在第几位。Q8 格式（8 位小数位）用 int32_t 存值，真实值 = 存储值 / 256：

c
#define FIXED_POINT_SHIFT 8
int32_t fixed_point_value = (int32_t)(input_value * (1 << FIXED_POINT_SHIFT));

1.5 存成 384，读的时候除 256 还原。整个算法严格用定点类型，浮点运算全转成定点，乘除靠左右移位：

c
int32_t multiply_fixed_point(int32_t a, int32_t b) {
    return (int32_t)(((int64_t)a * b) >> FIXED_POINT_SHIFT); /* 定点乘法 */
}

注意中间那个 (int64_t)。两个 Q8 的 int32_t 相乘，结果范围需要 64 位才不溢出。少了这步就是经典 bug：小数值算得对，大数值直接飞掉。

横向对比：

项 浮点（float/double） 定点（Q 格式整数）
无 FPU 时的速度 慢，几十到上百周期 快，1~2 周期
有 FPU 时的速度 快 也快，差别不大
动态范围 极大 窄，看位宽和小数位分配
精度 均匀（相对精度） 绝对值均匀，大数时相对精度差
溢出行为 饱和到 Inf 静默回绕，必须自己防
代码体积 要带软浮点库 小
移植难度 换芯片即用 换芯片或换量程要重算 Q 值
调试难度 直观 要换算，看波形先除 2^n

最后一行最容易被低估。定点输出在调试器里是一堆看着没意义的整数，你得手工除 256 才能对上物理量。

6.3 用 Fixed-Point Designer 做转换 #

手算 Q 值、手写移位能行，但容易错。Fixed-Point Designer 干的是这件事：把已有的浮点算法自动转成定点，并用浮点结果作「黄金参考」比对误差。

流程：先准备一份跑得通、结果正确的 double 实现；给输入数据定范围（工具靠数据统计每个变量的实际取值范围，范围给错 Q 值就分配错）；用 fi 对象逐变量标注类型：

matlab
% 有符号 16 位, 12 位小数位, 值域约 [-8, 8)
x = fi(0, 1, 16, 12);

% 用 numerictype 描述类型, 便于复用
T = numerictype(1, 16, 12);
y = fi(0, T);

然后跑一遍比对，看误差是否在容许范围内；超了要么加位宽，要么调整小数位分配（范围大的变量少给小数位，精度敏感的变量多给）。两种做法：全手工标注，或者用工具自动推导（fiaccel 配合定点建议）。自动推导给的是起点，最终仍要人工看一遍——它按数据驱动，你的测试数据没覆盖到的分支，它给的类型就未必对。

6.4 定点化的三个取舍 #

位宽。 16 位够不够取决于动态范围要求。Q12 的 16 位定点值域是 ±8、分辨率 1/4096。够就 16 位，不够就 32 位。32 位定点在 Cortex-M0 上要两次 16 位乘加，比 16 位慢但还能接受。

小数位分配。 一个 Q 值不能同时满足大范围和高精度。PI 控制器的积分项容易累积到很大，误差项又要求高精度，两者常常要分配不同小数位，中间还要做移位对齐。

溢出怎么处理。 定点溢出是静默回绕，32767 + 1 变成 -32768，符号直接翻转，控制回路里这一下就是输出满偏。要么加饱和（if (x > MAX) x = MAX;），要么设计时留足余量。饱和本身有分支开销，实时循环里要算进去。

七、生成的代码怎么用 #

拿到一堆 .c/.h，怎么塞进工程。这章讲文件组织、接口约定和几个常见坑。

7.1 哪些文件要，哪些不要 #

判断标准：编译报错说缺什么就加什么，说重复就删什么。

必留：入口函数的 .c/.h（myfunc.c、myfunc.h）、rtwtypes.h（基础类型映射，几乎所有文件都 include）、rt_nonfinite.c/h 与 rtGetInf.c/h、rtGetNaN.c/h（处理 Inf/NaN，缺了链接不过）。按需：*_types.h（算法里有结构体时才有）、*_data.c（有大的常量表，比如滤波器系数时才有）、buildInfo.mat 与 html/（报告和构建信息，不编进去）。

工程里有多个生成模块时，每个模块都会生成一份 rtwtypes.h、rt_nonfinite.c，这时不能全塞——会重复定义。留一份，其余删掉，或者按目录分开编译。

7.2 接口约定 #

生成的签名由输入样例决定。double 输入的 3×1 向量，签名是：

c
extern void myfunc(const double x[3], double y[3]);

返回值不是 return 而是出参，原因很直接：C 不能返回数组。几个细节：不改动输入就带 const，编译器优化更好也防误改；const double x[3] 在 C 里就是 const double *x，sizeof(x) 得到指针大小不是数组大小；参数顺序是输入在前输出在后，多个输出按 -args 声明顺序排；结构体类型用 myfunc_types.h 里的定义，别自己再定义一遍。

7.2 首次调用有初始化 #

有些生成代码带一次性初始化（查表预计算、状态清零）。生成 -config:lib 时，初始化多内联在第一次调用里，或者有个 _init() 要手动调。看 .h 里有没有声明，有就调：

c
#include "myfunc.h"

void app_init(void)
{
    myfunc_init();   /* 有声明就必须调 */
}

void app_loop(void)
{
    double in[3]  = { 1.0, 2.0, 3.0 };
    double out[3] = { 0 };
    myfunc(in, out);
}

7.3 调用节奏与三个坑 #

Simulink 生成的代码是典型的三段式，接到调度器里：

c
#include "test.h"

void ctrl_task_1ms(void)   /* 定时器中断或主循环里 1ms 调一次 */
{
    test_U.In1 = read_sensor();
    test_step();
    write_actuator(test_Y.Out1);
}

int main(void)
{
    board_init();
    test_initialize();
    scheduler_start();       /* 之后每秒 1000 次进 ctrl_task_1ms */
    test_terminate();
    return 0;
}

要点：test_initialize() 必须在第一次 test_step() 前调，且只调一次；test_step() 的调用周期必须跟模型里配的固定步长一致，模型设 1ms 你 2ms 调一次，内部积分就会慢一倍；test_step() 不能并发调用，多个任务同时调会踩状态变量，得用互斥或者把模型拆成多实例。

栈溢出。 生成的函数会开很大的局部数组，默认任务栈几百字节的话一进去就 HardFault。查 myfunc.c 里的局部变量，或直接看编译器给的栈使用报告。大了就改成静态全局缓冲区传进去。

类型名冲突。 rtwtypes.h 里定义了 boolean_T、int8_T 之类，工程别处有同名定义就编译报重复。改名或者用命名空间包一层。

重入。 生成代码的静态变量就是模块状态，同一份代码重入会互相污染。要重入就得生成 Reusable function 形式，把状态放到结构体里，每个实例一份。

八、做成动态库 #

前面讲的是把生成的代码编进主程序。还有一条路：打包成 .so，主程序运行时加载。这是素材第三篇的主题。

8.1 为什么这么做、先编成 .so #

算法和主程序编在一起，每次改算法都要重新链接、重新出固件、重新烧写。现场设备在线的话，改一次算法要走一遍完整发布流程。做成动态库之后，算法（.so）和主程序（可执行文件）是两件东西，改算法只换 .so，主程序二进制不动。对现场升级来说，这能省掉一次全量固件发布。

bash
gcc -shared -fPIC -o libmyfunc.so *.c

三个关键点：-shared 产共享库而非可执行文件；-fPIC 是位置无关代码，共享库必须加，否则加载时重定位失败，漏了会报 relocation R_X86_64_PC32 against symbol ... can not be used when making a shared object；*.c 把生成目录下所有 .c 都编进去，包括 rt_nonfinite.c 那些。

交叉编译到 ARM 板子，把 gcc 换成工具链的编译器。用 Makefile 组织更清爽：

makefile
CC:= arm-none-linux-gnueabi-gcc
OBJS:=$(patsubst %.c, %.o, $(wildcard *.c))
PRO_NAME:= libmatlab.so

$(PRO_NAME):$(OBJS)
	$(CC) -shared -o $(PRO_NAME) $(OBJS)

%.o:%.c
	$(CC) -c -Wall -I. -o $@ $<

clean:
	rm -rf *.o $(PRO_NAME)

拆开看：CC 是交叉编译器，这里指定 arm-none-linux-gnueabi-gcc，编出来的代码跑在 ARM 上；OBJS 用 wildcard + patsubst 自动把当前目录下所有 .c 变成 .o 列表，加文件不用改 Makefile；PRO_NAME 是产物名 libmatlab.so，lib 前缀是 Linux 动态库的命名约定；第一条规则把 .o 用 -shared 链成 .so；第二条规则把每个 .c 编成 .o，-Wall 开警告，-I. 是头文件搜索路径（生成的头文件就在同目录）；clean 清中间产物和库文件。

这是给 Linux 目标的写法（.so）。交叉编译 Windows 目标是 .dll，链接选项不同。这里没加 -fPIC 是因为该工具链默认已开位置无关，换工具链要自己确认。执行 make，生成 libmatlab.so。

8.2 部署到板子 #

拷到开发板 /opt 下（user 和 your_board_ip 换成实际值）：

bash
scp libmatlab.so user@your_board_ip:/opt

然后让工程在链接时找得到它，Qt 工程在 .pro 的 LIBS 里加：

plaintext
-L./extlibrary/matlab -lmatlab -Wl,-rpath,/opt

三段：-L 指定库文件所在目录；-lmatlab 是库名，约定是写 -lxxx 就找 libxxx.so，前面的 lib 和后面的 .so 都要去掉；-Wl,-rpath,/opt 让链接器把 /opt 写进 ELF 的运行时搜索路径。不加这个，运行时就会报 error while loading shared libraries: libmatlab.so: cannot open shared object file——因为 /opt 不在默认搜索路径里。

最后把头文件和库都复制进工程目录，编译器要能找到头文件（include/），链接器要能找到库（lib/）：

bash
cp /path/to/matlab/headers/*.h /path/to/your/project/include/
cp /opt/libmatlab.so /path/to/your/project/lib/

8.3 dlopen 手动加载 #

不写 -l 做链接，也可以运行时自己加载。这条路更灵活，改算法连主程序都不用重编，只要 .so 里的符号名不变：

c
#include <dlfcn.h>
#include <stdio.h>

typedef int (*algo_fn)(const double *in, double *out);

int main(void)
{
    void *h = dlopen("/opt/libmatlab.so", RTLD_NOW);
    if (!h) { fprintf(stderr, "dlopen failed: %s\n", dlerror()); return 1; }

    algo_fn algo = (algo_fn)dlsym(h, "myfunc");
    if (!algo) {
        fprintf(stderr, "dlsym failed: %s\n", dlerror());
        dlclose(h);
        return 1;
    }

    double in[3]  = { 1.0, 2.0, 3.0 };
    double out[3] = { 0 };
    algo(in, out);

    dlclose(h);
    return 0;
}

编译加 -ldl：gcc main.c -o main -ldl。

几个要点：RTLD_NOW 是加载时立刻解析所有符号，出错马上知道；RTLD_LAZY 是第一次调用才解析，错误延后暴露，调试用 NOW；dlerror() 一定要看，dlopen 返 NULL 的原因（路径错、依赖缺、架构不匹配）都在里面；dlsym 返回 void*，转成函数指针是标准做法，但类型必须跟 .so 里的实际签名完全一致，对不上不报错，直接是未定义行为；用完 dlclose，不关会漏掉映射。

8.4 动态库的代价 #

项 优点 代价
加载方式 运行时按需加载 dlopen 有毫秒级开销，启动变慢
更新 只换 .so，主程序不动 接口一变两边都要改，等于没解耦
内存 多进程可共享代码段 每进程仍有私有数据段
符号 模块边界清楚 全局符号会撞车，静默用错版本
调试 可单独替换某个模块 崩溃栈跨库，缺符号表就是一堆地址
部署 增量更新 多一个文件要管，版本对不上就是灾难

符号冲突最隐蔽。 你的 .so 里有个全局函数 init，主程序里也有个 init，谁赢取决于加载顺序和符号可见性，编译器不报错。生成的代码带 myfunc_init 这种名字撞上的概率低，但工具链自带的软浮点函数、memcpy 之类会撞。用 -fvisibility=hidden 把内部符号藏起来，只导出对外那几个。

调试成本最实际。 程序崩在 .so 里，栈回溯显示的是没有符号的地址，得手工拿 addr2line 换算。现场设备出问题，日志里只有一串地址，定位时间按小时算。编译时留 .so 的调试信息副本，否则事后没法查。

8.5 老路子：deploytool 打包 #

早期还有个 deploytool 路线，把 Matlab 代码打包成 .NET Assembly 或 DLL。它跟 codegen 不是一回事：打的是 Matlab 运行时，产物需要目标机器装 MCR（MATLAB Compiler Runtime）。流程（老工具，看现有项目是否还在用）：先在命令行依次跑 mbuild -setup、mex -setup、deploytool，各自选 C++ 选项；打开 deploytool 后选 Library Compiler 进打包界面；选 .NET Assembly，添加相关脚本文件，类名自定义（比如 airplane），确认后点 Package 打包；打包完生成几个文件夹，里面就是 DLL 和配套文件。

判断标准很清楚：要 C 源码、要裸机跑、不依赖 Matlab 运行时——用 codegen；要快速把一堆 Matlab 函数包成桌面程序能调的 DLL、且能接受目标机器装几个 GB 的 MCR——用 deploytool。 两边产物完全不是一回事，别混。

九、验证：SIL 与 PIL #

生成代码跟 Matlab 结果对不上，是最难查的一类问题——它不报错，只是数不对。

层 验证什么 怎么验 成本
MEX 比对 语义翻译对不对 生成 MEX，在 Matlab 里跟原函数比对 极低
SIL 生成的 C 逻辑对不对 宿主机编译成库，跟 Matlab 比对 低
PIL 在目标芯片上对不对 真实 MCU 上跑，跟 Matlab 比对 高

顺序不能反。 先 MEX、再 SIL、再 PIL，前面的通过了才有意义。反过来做，PIL 出问题时你分不清是代码生成错了还是硬件配错了。

9.1 MEX：最快的比对 #

codegen -config:mex 生成的 MEX 是二进制插件，能在 Matlab 里当函数直接调：

matlab
codegen -config:mex myfunc -args {zeros(3,1)}   % 生成 MEX

x = randn(3, 1);
y_ref = myfunc_ref(x);   % 原始 .m 的浮点版本
y_gen = myfunc_mex(x);   % 生成的 MEX
err = max(abs(y_ref(:) - y_gen(:)));
assert(err == 0, 'MEX 结果不一致, err=%g', err);

这层验的是「翻译有没有改语义」。索引从 0 还是 1 开始、整数除法取整方向、溢出怎么处理——这些差异在这一层暴露。MEX 过而 SIL 不过，问题多出在编译器优化或类型映射，不在算法逻辑。

9.2 SIL：软件在环 #

SIL 是把生成的 C 在宿主机上编成库或可执行文件，再跟 Matlab 结果对比。Simulink 有现成配置：Configuration Parameters → Code Generation → Verification → Create block 选 SIL，模型会生成一个 SIL 模块替换原模块，仿真时走生成的 C。.m 路线要自己搭：生成 -config:lib 后写个小 driver 输出数据到文件，再拿回 Matlab 比。

c
/* driver.c —— 把输入喂进生成函数, 结果打到 stdout */
#include <stdio.h>
#include "myfunc.h"
int main(void)
{
    double in[3], out[3];
    while (scanf("%lf %lf %lf", &in[0], &in[1], &in[2]) == 3) {
        myfunc(in, out);
        printf("%.17g %.17g %.17g\n", out[0], out[1], out[2]);
    }
    return 0;
}

用 %.17g，这是 double 能无损往返的最短格式。用 %f 会丢精度，比对就失去意义。

浮点结果不要期望逐位相等。 换编译器、换优化级别、换指令顺序，浮点累加的结合律就变了，末位会差。用相对误差判断：

matlab
rel_err = max(abs(y_ref - y_gen) ./ max(abs(y_ref), 1e-12));
assert(rel_err < 1e-10, 'SIL 超出容差');

定点结果要逐位相等。 定点没有舍入的不确定性，整数运算顺序不影响结果。定点对不上一定是实现错了，没有「浮点误差」这个借口。

9.3 PIL 与测试数据 #

PIL 把生成的代码放到真实芯片上跑，Matlab 通过串口或调试口送输入、读输出。这层验的东西前两层验不到：目标芯片字长（32 位 vs 64 位）导致的差异；编译器对目标架构的优化引入的差异（比如 double 换成软浮点）；定点在真实位宽下的溢出行为；芯片的字节序和对齐要求。做 PIL 要配通信链路和 pilot 目标，成本高，只在「算法要上量产」时做。原型阶段 SIL 过了就够。

测试数据的选取比验证方法更影响结论。边界值：输入取 INT16_MAX、INT16_MIN、0、1、-1，溢出和符号翻转都在这几个点上。真实数据：录一段现场信号喂进去，合成数据（正弦、白噪声）覆盖不到真实信号的病态情况。长序列：状态型算法跑一万步看有没有累积漂移，跑 100 步正常不代表跑 10000 步正常。异常输入：NaN、Inf、全零、超量程的值——生成的代码对 NaN 的处理跟 Matlab 未必一致。

十、常见失败原因 #

按报错频率排。看到类似错误先查这里。

10.1 不支持函数、尺寸不定、递归 #

不支持函数的症状是 The function 'xxx' is not supported for code generation.。高频名单：eval、evalin、assignin、syms、solve、dsolve、sprintf（部分格式）、写文件的 fprintf、input、keyboard、figure、plot、uicontrol、webread、readtable、xlsread、audioread（部分）。用 codegen 的检查模式跑一遍，报告会列出所有不支持的行号，逐条替换。策略：动态执行改 switch 分支；符号运算提前手算出表达式写成数值代码；文件 IO 挪到生成代码外面由 C 侧负责，算法函数只处理内存数据；绘图直接删掉。

尺寸不定的症状是 Size mismatch、All dimension sizes must be fixed、Variable 'x' is not fully defined，根因是某个变量的尺寸依赖运行时数据。用 -report 看每个变量的推断尺寸，Dimensions 那栏如果是 :3 或 ?x? 就是没定死。修法按 3.2 节两种改法处理。

递归的症状是 Recursive function calls are not supported.。C 的栈深度编译期不可知，嵌入式里递归本身就是禁忌。改成显式栈的迭代写法，阶乘用循环：

matlab
function y = fact_iter(n) %#codegen
y = 1;
for k = 1:n
    y = y * k;
end

树遍历这类天然递归的算法，用一个定长数组当栈，top 指针加减代替入栈出栈。

10.2 动态内存与 cell #

动态内存的症状是生成代码里出现 malloc/free，或报 Dynamic memory allocation is not supported for this configuration。根因是变长数组没设上界，或者配置开了 variable-size 却没配上界。给所有变长数组设显式上界，配置里把 DynamicMemoryAllocation 设成 'Off' 或 'Threshold'。

cell 数组的症状是 Cell arrays are not supported。cell 里每个元素可以不同类型不同尺寸，C 里没有对应概念。同类同尺寸改二维数组或结构体数组；同类不同尺寸按最大尺寸开数组加长度字段；不同类型拆成多个数组，或定义一个覆盖所有情况的 struct——{1, 'abc', [1 2 3]} 这种不能留，改成 struct('id', 0, 'name', zeros(1, 32, 'uint8'), 'buf', zeros(1, 16))。

10.3 其他高频 #

症状 根因 修法
Index expression out of bounds 索引越界风险，工具证明不了安全 加 assert 或限制索引范围
Undefined function or variable 变量在某分支没赋值 所有分支都赋值，或开头初始化
类型不一致警告 隐式类型转换 显式 cast 或指定类型
For loop index must be integer 循环变量是浮点 用 int32，或 coder.loop 提示

十一、与手写 C 的取舍 #

代码生成不是免费午餐。这章讲什么时候该用，什么时候该手写。

项 代码生成 手写 C
起步速度 快，算法跑通就能生成 慢，要从头实现
改算法成本 改 .m 重新生成 重写受影响的全部代码
可追溯性 Matlab 原稿就是设计文档 只有代码，设计意图丢失
代码体积 偏大，带运行时框架和防御检查 可控，能优化到指令级
执行效率 良好，但不是最优 可针对芯片手调
可读性 中等，命名和结构固定 想写多清楚就多清楚
依赖 Matlab 加工具箱授权 零依赖
团队门槛 要会 Matlab 要会 C 和算法
定点化 工具辅助，有黄金参考比对 全靠手算和测试
验证 SIL/PIL 有现成支持 全部自己搭

11.1 场景划分 #

该用代码生成： 算法还在迭代期——改十次 Matlab 比改十次 C 便宜得多；算法复杂到手工翻译容易错——矩阵运算、滤波器组、状态观测器，手抄一遍就是 bug 温床；团队主力是算法工程师不是嵌入式工程师；有 SIL/PIL 验证要求，需要「Matlab 结果 vs C 结果」的可追溯比对；代码要过评审，需要证明实现跟设计一致。

该手写 C： 抠死的资源和时序要求——生成的代码为通用性要加防御，手写能省掉；算法简单且稳定——一个二阶 IIR 滤波器手写二十行，生成出来几百行还带一堆运行时；不允许引入工具链依赖——开源项目、要给别人复现的代码、授权受限的环境；需要精细控制内存布局——DMA 缓冲区对齐、cache line 对齐这些，生成的代码管不了；算法本身是位操作密集的——CRC、加解密、编解码，手写更强。

11.2 混合路线 #

实战里最常见是混着来：算法主体用生成（滤波器、控制器、观测器，Matlab 里验证过再生成）；接口层手写（ADC 采样、DMA 搬运、通信协议）；热点手写，用 coder.ceval 把某个函数换成手写实现，其余不变：

matlab
function y = fast_path(x) %#codegen
% 热点函数调手写 C 实现
y = coder.ceval('my_asm_dot', x, int32(numel(x)));

这样 Matlab 侧能跑通完整流程，生成的代码里那个函数调的是你手写的版本。验证时注意：这条路径下的 SIL 比对不再是纯 Matlab 语义，容差要放宽，或者改成定点逐位比对。

十二、易错点速查 #

按流程顺序排，开工前扫一眼能省几小时。

12.4 四条线收束 #

代码生成的本质，是把 Matlab 的动态语义翻译成固定的 C 结构。生成前所有工作的归结是一件事：把动态的东西一个个定死——尺寸、类型、内存、分支。定得死就生成得了，定不死就改写算法或者换手写。

定死之后是第二道关：能生成不等于能上板。浮点代码在没有 FPU 的 MCU 上跑不动，定点化才是落地门槛。两道关都过了是第三件事：验证。MEX、SIL、PIL 三层，前面的通过才有意义，别跳。

最后一件事是接口。动态库让算法和主程序解耦，现场改算法只换 .so，代价是加载开销、符号冲突和更难调的崩溃栈。接口一旦变形，解耦就变成两边都要改——这时候老实重新发布，别为了「不重编主程序」硬扛。
