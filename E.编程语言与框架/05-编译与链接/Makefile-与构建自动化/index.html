一、make 解决什么问题 #

先说结论：make 不编译任何东西。它只做一件事——读一个描述文件，算出「哪些命令现在该跑」，然后帮你把命令跑掉。

这个定位很重要。很多人把 make 当成编译器，于是写出 gcc xxx 挨个排列的 Makefile，出了问题就去查 gcc 选项，方向从一开始就偏了。

真正的痛点在重复劳动。一个二十个源文件的项目，改一行 main.c，你手动敲：

bash
gcc -c main.c -o main.o
gcc main.o utils.o net.o proto.o \
    -o app -lm -lpthread

两个问题。第一，参数越长越容易敲错，漏一个 -lpthread 就是一堆 undefined reference。第二，也是最关键的：你把所有 .o 全部重新编译了一遍，可实际上只有一个文件变了。

规模上去以后，全量编译的时间开销是灾难。Linux 内核几十万个源文件，全编一次按小时算。改一行代码等一小时，这不是开发，是排队。

make 的解法很朴素：记下每个目标文件和它的依赖的关系，比对两者的最后修改时间，只跑那些「依赖比目标新」的命令。1977 年 Stuart Feldman 在贝尔实验室写下第一版 make，机制至今没变。

注意 make 与语言无关。它眼里只有两种东西：

text
一个文件  ←— 命令 ——  若干文件
（目标）                （依赖）

cat b.txt c.txt > a.txt 是这么一条，gcc -c main.c -o main.o 也是这么一条。make 不知道什么是 C，它只知道「a.txt 比 b.txt 旧，所以该跑那条猫命令」。

调用关系长这样：

text
make
 └─ 读 Makefile，建依赖图
     └─ 从默认目标（第一个）出发
         └─ 递归看每个依赖：存在吗？比目标新吗？
             ├─ 需要更新 → 跑命令行
             └─ 不需要   → 跳过，打印 up to date

摊到一个 C 项目上：app 依赖三个 .o，每个 .o 依赖一个 .c 加若干头文件。改了 defs.h，main.o 和 net.o 的时间戳落后于它，两条编译命令跑起来；app 要不要重链，再看上一层的比对结果。一张图一次算清，这就是 make 全部的本事。

二、第一条规则：目标、依赖与命令 #

规则是 Makefile 唯一的骨架。语法三行：

makefile
target ... : prerequisites ...
	command
	...

拆开看：

组成 名称 说明
target 目标 要生成的文件，或一个动作名（伪目标）
prerequisites 前置条件、依赖 生成目标所需的文件，可空
command 命令 Shell 命令，可多条，可空

三者里目标必须有。依赖和命令至少有一个，否则这条规则什么也不说。

2.1 命令必须以 Tab 开头 #

这是新人撞的第一堵墙，也是本篇要反复强调的一条：规则的命令行，第一个字符必须是 Tab，四个空格不行。

makefile
# 错：命令前是四个空格
all:
    echo hello

报错就一句：

text
Makefile:2: *** missing separator.  Stop.

missing separator 翻译过来是「缺少分隔符」，但真相跟分隔符毫无关系——make 在用 Tab 判断「这一行是命令，还是新的一条规则、变量赋值」。它扫到行首不是 Tab，就按普通语法去解析 echo hello，解析不出来，于是报错。

一个能跑的最小 Makefile（照抄可执行）：

makefile
a.txt: b.txt c.txt
	cat b.txt c.txt > a.txt

注意 cat 前面那个看不见的字符是 Tab。写的时候别让编辑器帮你转空格。

想换掉 Tab，用 .RECIPEPREFIX：

makefile
.RECIPEPREFIX = >
all:
> echo Hello, world

声明之后，命令行的起首字符变成 >，Tab 不再特殊。这个变量只在 GNU make 3.82 以后存在，老项目里看不到，你自己的项目里也不建议用——所有教程、所有代码片段都按 Tab 写的，改了这一条，贴别人的规则就全废了。

2.2 注释、空行与续行 #

# 到行尾是注释。行首的 # 是整行注释，行中出现的也是注释：

makefile
# 整行注释
result.txt: source.txt
	cp source.txt result.txt   # 行尾注释也是注释

但命令里的 # 属于 Shell，取决于 Shell 的解释，别指望 make 帮你剥掉。

行尾一个反斜杠 \ 表示续行，把下一行接到本行末尾：

makefile
SRCS = main.c \
       utils.c \
       net.c

续行后的内容会被拼成一整行，中间补一个空格。

2.3 默认目标与指定目标 #

不带参数运行 make，跑的是 Makefile 里出现的第一个目标，与它叫什么无关。这就是为什么大家把 all 写在最前面。

bash
make            # 跑第一个目标
make a.txt      # 指定目标
make clean      # 跑清理
make -f rules.txt a.txt   # 换一个规则文件

-f 也可以写成 --file= 或 --makefile=。不指定时 make 按顺序找 GNUmakefile、makefile、Makefile，找到哪个用哪个。所以项目里放着 Makefile 和 makefile 两份，只有前者生效，这个坑很常见。

2.4 一个目标，多条命令 #

命令行可以有多条，逐行执行：

makefile
all:
	@echo "start"
	mkdir -p build
	@echo "done"

命令前的 @ 表示不回显这条命令本身，只输出它的执行结果。上面两条 echo 加了 @，mkdir 没加，所以终端里会看到两行文字加一行 mkdir -p build。

2.5 多个目标与聚合目标 #

一行里写多个目标，冒号后面的依赖和命令对每个目标都生效。$@ 是自动变量，指代当前构建的那个目标名：

makefile
a.txt b.txt:
	touch $@

只写依赖、不写命令，规则就变成「打成一包」的聚合入口。不带参数敲 make 等于敲 make all：

makefile
.PHONY: all
all: app1 app2 app3

2.6 跑一遍看清楚 #

建三个文件验证：printf 'x\n' > b.txt、printf 'y\n' > c.txt，再 make a.txt，终端回显 cat b.txt c.txt > a.txt 并生成结果。再敲一次，只得到一句 make: 'a.txt' is up to date.。为什么第二次什么都不做，是下一章要拆的东西。

三、时间戳：make 怎么判断要不要重编 #

make 的决策依据只有一个：文件的 mtime（最后修改时间）。没有哈希，没有内容比对，没有编辑器状态，就是 stat 出来的那个时间戳。

3.1 判断链条 #

对一个目标 T，依赖列表 P1 P2 ... Pn，make 按这个顺序问：

text
1. T 存在吗？
   ├─ 不存在 → 跑命令生成 T
   └─ 存在   → 继续

2. 对每个 Pi：
   ├─ Pi 不存在，但有规则能生成 → 先递归把 Pi 做出来
   ├─ Pi 不存在，也没有规则     → 报 No rule to make target
   └─ Pi 存在                   → 记下它的 mtime

3. 有没有哪个 Pi 的 mtime 比 T 的 mtime 更新？
   ├─ 有   → 跑命令，重建 T
   └─ 没有 → 跳过，T 视为最新

整棵树递归下去，每个节点都走一遍这套判断。

3.2 源码没改，但依赖改了 #

这是「增量编译」最值钱的地方。b.txt 不动，只往 c.txt 追加一行，再 make a.txt，cat 又跑了一次，因为 c.txt 的 mtime 追上了 a.txt。整个过程中 make 只比了两个数字，没有读任何文件内容。

再跑第三次，什么都不改：

text
make: 'a.txt' is up to date.

这句话不代表「构建成功」，只代表「没有任何依赖比目标新」。要么是真的没问题，要么是你的依赖列表漏了东西——两种情况在输出上一模一样，这是 make 最阴的地方。

3.3 $?：到底哪些依赖更新了 #

自动变量 $? 专门给出「比目标新的那些依赖」：

makefile
a.txt: b.txt c.txt
	@echo "需要更新的依赖: $?"
	cat $? > a.txt

只改 c.txt 时，$? 就是 c.txt。这个变量在只处理变动部分的场景里有用，比如增量打补丁。

3.4 改了头文件却没重编，根因只有一个 #

经典的困惑：改了 config.h，make 报 is up to date，程序行为没变，以为编译器出鬼了。

根因在第一行就写死了：

makefile
main.o: main.c
	gcc -c main.c -o main.o

这条规则的依赖只有 main.c。config.h 根本不在依赖里，make 从没见过它，自然不会为它重建 main.o。.o 生成之后，只要 main.c 比 .o 旧，一律跳过。

三种解法，从粗到细：

makefile
# 解法一：手动把用到的头文件列进依赖
main.o: main.c config.h defs.h
	gcc -c main.c -o main.o

makefile
# 解法二：让编译器自己吐依赖，一条 -MMD 解决
%.o: %.c
	$(CC) $(CFLAGS) -MMD -MP -c $< -o $@
-include $(OBJS:.o=.d)

makefile
# 解法三：头文件全量兜底，粗暴且慢，小项目够用
%.o: %.c $(wildcard *.h)
	$(CC) $(CFLAGS) -c $< -o $@

解法二是正路，第十二章展开。解法三会让任何头文件变动触发全量重编，项目一大就废。

3.5 目录 mtime 的坑与秩序依赖 #

想让 .o 落到 build/ 下，得先有 build/ 目录。于是有人这么写：

makefile
build/main.o: src/main.c build
	gcc -c $< -o $@

build:
	mkdir -p build

埋了颗雷。build 是普通依赖，而目录的 mtime 会随着目录内任何文件的增删改而更新。今天编出 main.o，明天新增一个 other.o，build/ 的 mtime 跳了一下，main.o 立刻被判为过期，白白重编。文件越编越多，每次都要重编一遍。

解法是秩序依赖（order-only prerequisites），竖线 | 右边的东西只保证存在，不参与时间戳比对：

makefile
build/%.o: src/%.c | build
	$(CC) $(CFLAGS) -c $< -o $@

build:
	mkdir -p build

build/ 不存在时先建出来；存在了就完全不看它的 mtime。这条语法在多目录工程里出现频率极高，看到 | 别以为是管道。

四、变量：定义、引用与四种赋值 #

Makefile 的变量不是类型化变量，全部是字符串，什么时候展开取决于你用了哪个运算符。变量名区分大小写，习惯上全大写，与内置变量保持一致。

引用有两种写法，效果一样：

makefile
CC = gcc
$(CC) --version
${CC} --version

单字符变量可以省括号，$X 就是变量 X。多字符必须带括号，$CFLAGS 会被当成「变量 C 后面跟着字面量 FLAGS」。

4.1 四种赋值对照 #

运算符 名称 展开时机 典型用途
= 递归展开、延时赋值 变量被使用时才展开 引用后面才定义的变量
:= 简单展开、立即赋值 定义那一行立刻展开 依赖 $(shell ...) 的结果
?= 条件赋值 未定义过才赋值 允许环境或命令行覆盖默认值
+= 追加赋值 依原变量类型而定 拼装源文件列表、编译选项

逐个看。

= 存原始文本，用到时才解析，所以能引用后面才定义的变量：

makefile
A = $(B)
B = hello      # A 展开为 hello
A = $(A) x     # 这么写会无限递归，make 报错退出

:= 在赋值那一刻就算完右边的引用，后面再改被引用的变量也影响不到它：

makefile
B = hello
A := $(B) world
B = bye        # A 仍是 hello world

右边带命令替换时必须用 :=，否则每引用一次就 fork 一个 Shell：

makefile
NOW = $(shell date +%s)     # 每引用一次跑一次 date
NOW := $(shell date +%s)    # 解析时只跑一次

?= 判断的是「变量是否为空」，不是「从哪儿来」。命令行传了 make CC=clang，CC 已有值，?= 就不动手，这是给用户留覆盖入口的标准做法：

makefile
CC ?= gcc
CFLAGS ?= -O2 -Wall

+= 追加，中间自动补一个空格。对 = 型变量追加的部分保持延时展开，对 := 型变量追加的部分当场展开：

makefile
SRCS = main.c
SRCS += utils.c      # main.c utils.c

4.2 变量的优先级 #

同一个变量会在四处出现，优先级从高到低：

text
命令行（make CFLAGS=-O3）      ← 最高，除非 Makefile 用 override 顶回去
Makefile 内的赋值
环境变量                        ← Makefile 里没赋值时才轮到它
make 内置默认值（default）

override 是强制的，用户传什么都盖不掉，除非 make -e。少用，用户传参被无声无视，排障很折腾。

4.3 目标特定变量 #

变量可以只对某个目标生效，语法是 target : VAR = value：

makefile
app: CFLAGS = -O3

app: main.o
	$(CC) $(CFLAGS) main.o -o app

main.o: main.c
	$(CC) $(CFLAGS) -c main.c -o main.o

make app 时 app 这条规则看到 -O3，main.o 看到的还是全局的 CFLAGS。作用域沿依赖链向下传递，但子规则自己写的赋值优先。用它做 Debug / Release 分流：

makefile
release: CFLAGS = -O2 -DNDEBUG
release: app

4.4 内置变量 #

这些变量 make 已经预置好了值，你覆盖就是改行为，不覆盖就是默认：

变量 默认值 含义
CC cc C 编译器
CXX g++ C++ 编译器
CPP $(CC) -E 预处理器
CFLAGS 空 给 C 编译器的选项
CXXFLAGS 空 给 C++ 编译器的选项
CPPFLAGS 空 给预处理器的选项，放 -I、-D
LDFLAGS 空 给链接器的选项，放 -L
LDLIBS 空 链接的库，放 -lpthread 这类
AR ar 静态库打包工具
RM rm -f 删除命令
MAKE make 当前 make 的调用路径

CC 默认是 cc 而不是 gcc，这是历史包袱，Linux 上 cc 一般是指向 gcc 或 clang 的软链。写 Makefile 时把 CC ?= gcc 显式声明上，跨机器少一类问题。

CPPFLAGS 和 CFLAGS 别混。-I、-D 放 CPPFLAGS，-O、-g、-Wall 放 CFLAGS，理由是很多第三方构建脚本会分别覆盖这两个变量，混着放会被冲掉。

五、自动变量：$@、$<、$^ #

自动变量的值是「当前这条规则」的上下文，规则不同值就不同。它们让一条规则能套用到无数文件上。

变量 含义 示例（规则 app: main.o utils.o）
$@ 当前目标名 app
$< 第一个依赖 main.o
$^ 所有依赖，去重 main.o utils.o
$+ 所有依赖，不去重 main.o utils.o
$? 比目标新的依赖 视 mtime 而定
$* 模式规则里 % 匹配到的部分 main
$(@D) $@ 的目录部分 .
$(@F) $@ 的文件名部分 app
$(<D) $< 的目录部分 .
$(<F) $< 的文件名部分 main.o

$^ 会去重，$+ 不去重。链接场景下重复的 .o 会报重复定义，用 $^。

有了自动变量，规则的命令就和具体文件名解耦了，加一个依赖，命令一个字不用改：

makefile
main.o: main.c my_header.h
	gcc -c $< -o $@

价值在模式规则里才完全体现——一条命令覆盖所有 .c 文件，因为 $< 和 $@ 会随目标变化。

$* 只在模式规则和后缀规则里有意义。规则 %.o: %.c 匹配 main.o 时，$* 是 main。

$(@D) 和 $(@F) 在把产物往不同目录塞的时候很有用：

makefile
build/%.o: src/%.c
	@mkdir -p $(@D)
	$(CC) -c $< -o $@

$@ 是 build/foo.o，$(@D) 就是 build，目录不存在时让 mkdir -p 建出来。这行是第十章多目录工程的关键。

$< 和 $@ 带上目录前缀后，跨目录搬文件也是一条命令的事：

makefile
dest/%.txt: src/%.txt
	@[ -d dest ] || mkdir dest
	cp $< $@

六、模式规则与后缀规则 #

6.1 百分号模式规则 #

项目有一百个 .c，手写一百条规则是自虐。百分号 % 是通配占位，匹配任意非空字符串：

makefile
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

这条规则的意思是：任何 xxx.o，如果存在对应的 xxx.c，就用这条命令编译。% 在目标和依赖里代表同一段字符串，这叫词干（stem），也就是 $* 的值。

%.o: %.c 这一条能顶掉整页的手工规则，这是 Makefile 从「一堆散装 Shell」变成「构建系统」的分水岭。

% 还能带目录前缀，build/net/http.o 由 src/net/http.c 生成，词干是 net/http，第十章展开。

注意模式规则里的 % 和函数里的 % 是两套东西。$(patsubst %.c,%.o,$(SRCS)) 里的 % 属于函数语法，规则里的 % 属于目标匹配，别混为一谈。

6.2 静态模式规则 #

普通模式规则对全目录生效，静态模式把它限制在指定列表内：

makefile
objects = main.o utils.o

$(objects): %.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

三个冒号段：目标列表、目标模式、依赖模式。只有 objects 里的文件会套用这条命令，目录里其他无关的 .c 不会被顺手编译。

为什么要它？因为模式规则是「谁能匹配就套谁」，一旦目录里混进无用的测试文件，make 会替你编译一堆不想要的东西。静态模式把匹配范围钉死，行为可预测。

6.3 后缀规则 #

老项目里会看到双后缀规则：

makefile
.c.o:
	$(CC) $(CFLAGS) -c $< -o $@

意思等同 %.o: %.c。还有单后缀规则：

makefile
.c:
	$(CC) $(CFLAGS) $< -o $@

意思是从 xxx.c 直接生成可执行文件 xxx。这类写法出现在 1990 年代的代码里，早期的 Linux 内核和 GNU 工具都用过。

后缀规则依赖 .SUFFIXES 列表，列表里没声明的后缀不生效：

makefile
.SUFFIXES:
.SUFFIXES: .c .o .s

第一行清空后缀列表，第二行重新声明。写 .SUFFIXES: 空一行，等于把所有后缀规则全关掉。

新项目一律用 % 模式规则。后缀规则可读性差、调试信息少，GNU make 保留它只为兼容。

6.4 隐含规则与它的搜索算法 #

即使你只写一行 main.o: main.c，不给命令，make 也能编出来。这是内置的隐含规则在起作用，等价于：

makefile
main.o: main.c
	$(CC) $(CFLAGS) $(CPPFLAGS) -c -o $@ $<

make 内部数据库里存着几十条这类规则（.c → .o、.cc → .o、.s → .o、.o → 可执行文件……）。构建一个没有显式命令的目标时，它按这套流程找规则：

text
1. 拆名：把目标拆成目录部分 D 和文件名部分 F
2. 匹配：在数据库里找目标模式能匹配 F 的规则（如 %.o）
3. 校验：该规则的依赖（如 %.c）在磁盘上存在吗？
          不存在的话，能通过别的规则生成吗？
4. 绑定：找到满足条件的最短依赖链，把命令挂到当前目标上

这套机制能省事，也能坑人。你以为没写规则的 .o 会报错，结果 make 悄悄用内置规则编了一个，用的还是默认 cc 和空 CFLAGS，产物行为和你的预期完全不符。

想彻底关掉默认推导，给一条空命令的模式规则：

makefile
%.o: %.c

没有命令，等于告诉 make「这条链走不通」。这种写法叫「取消隐含规则」。追求行为可控的项目在开头就写上它，然后用显式的变量覆盖（CC、CFLAGS、CPPFLAGS、LDFLAGS、LDLIBS，见 4.4 的表）来定行为。

七、伪目标 .PHONY #

目标不一定是文件。clean、all、install 都只是动作名。

7.1 clean 失效的现场 #

makefile
clean:
	rm -f *.o app

正常跑没问题。但假设目录里恰好有个叫 clean 的文件——要么是你调试时 touch clean 留下的，要么是某个工具的产物——再跑 make clean：

text
make: 'clean' is up to date.

rm 一次都没执行。原因还是第三章那套逻辑：clean 这条规则没有依赖，目标文件 clean 又存在，make 找不到任何「比目标新」的依赖，于是判定无事可做。

7.2 用 .PHONY 声明 #

makefile
.PHONY: clean
clean:
	rm -f *.o app

声明之后，make 不再去磁盘上找同名文件，也不做时间戳比对，每次调用都无条件执行命令。

.PHONY 的声明可以合并且必须写在规则之前（写在后面也生效，但可读性差）：

makefile
.PHONY: all clean distclean install uninstall test

一个容易忽略的点：.PHONY 目标的依赖也会被当作伪目标处理。all: app 里的 all 是伪目标，app 不会因此变成伪目标。

7.3 该声明哪些 #

目标 是否该 .PHONY 理由
all 是 纯聚合入口，不对应文件
clean 是 动作名，且容易撞名
distclean 是 同上
install 是 动作名
test 是 动作名
print 是 调试用，每次都该跑
可执行文件名 否 真文件，要参与增量判断

判断标准一句话：这个目标是不是真的会在磁盘上产生同名文件？不会，就声明 .PHONY。

7.4 FORCE 惯用法 #

.PHONY 之前的老写法，用一个永远不存在的依赖强制重建：

makefile
FORCE:

clean: FORCE
	rm -f *.o app

FORCE 没有依赖也没有命令，永远不存在，于是 clean 永远被判为过期。效果和 .PHONY 一样，出现在老代码里，新代码用 .PHONY。把它接到真实文件上还能做「每次都跑」的检查点，比如版本号注入：

makefile
version.h: FORCE
	@echo "#define BUILD_TS \"$$(date +%F)\"" > $@

代价是 version.h 每次重写，mtime 一跳，依赖它的东西全重编。要不要这么干，先算清重编的代价。

八、函数：wildcard、patsubst、foreach #

函数的调用语法和变量引用长得一样：

makefile
$(function arguments)
${function arguments}

参数用逗号分隔。函数名和第一个参数之间的空格会被吃掉，但第二个逗号后的空格会被当成参数的一部分，这是无数诡异 bug 的来源。写的时候逗号后面不要留空格。

8.1 字符串函数 #

函数 作用 示例
subst 字面替换 $(subst ee,EE,feet) → fEEt
patsubst 模式替换 $(patsubst %.c,%.o,a.c b.c) → a.o b.o
strip 去首尾空格，压缩中间空白 $(strip a b ) → a b
findstring 找子串，找到返回子串 $(findstring clang,$(CC))
filter 保留匹配模式的词 $(filter %.c,$(SRCS))
filter-out 去掉匹配模式的词 $(filter-out main.c,$(SRCS))
sort 排序并去重 $(sort c a b a) → a b c
word 取第 n 个词 $(word 2,a b c) → b
words 数词个数 $(words a b c) → 3
firstword 第一个词 $(firstword a b c) → a
lastword 最后一个词 $(lastword a b c) → c

subst 是纯字面替换，patsubst 带 % 通配，两者别混。patsubst 只处理「词」，按空白切分后逐个匹配：

makefile
SRCS = main.c utils.c
OBJS = $(patsubst %.c, %.o, $(SRCS))   # main.o utils.o

简写是变量名加冒号，$(SRCS:.c=.o) 与上面等价，但只能做后缀替换；前缀搬家还得靠 patsubst：$(patsubst src/%.c,build/%.o,$(SRCS))。

8.2 文件名与路径函数 #

函数 作用 示例
wildcard 展开通配符，取文件列表 $(wildcard src/*.c)
dir 取目录部分，带斜杠 $(dir src/main.c) → src/
notdir 取文件名部分 $(notdir src/main.c) → main.c
suffix 取后缀 $(suffix src/main.c) → .c
basename 取去后缀的名字 $(basename src/main.c) → src/main
addsuffix 批量加后缀 $(addsuffix .o,a b) → a.o b.o
addprefix 批量加前缀 $(addprefix build/,a.o) → build/a.o
join 两列表逐项拼接 $(join a b,.c .o) → a.c b.o

wildcard 只展开一层，不递归子目录，要递归得靠 Shell：

makefile
SRCS = $(wildcard src/*.c)              # 只有 src 一层
SRCS = $(shell find src -name "*.c")    # 递归所有子目录

wildcard 由 make 自己展开，不 fork 进程。dir 配 sort 能把需要创建的目录一次收齐：

makefile
DIRS = $(sort $(dir $(OBJS)))   # build/net/ build/

这份列表交给 mkdir -p，一条命令建完整个目录树。

8.3 流程控制函数 #

函数 作用
foreach 遍历列表，对每项展开一段文本
if 二选一
or 返回第一个非空值
and 全部非空才返回最后一个
call 调用带参数的变量（宏）
value 取变量未展开的原始文本
eval 把文本当 Makefile 语句再解析一遍
origin 查变量的来源
flavor 查变量的类型
shell 执行 Shell 命令并取输出
info / warning / error 打印信息、警告、终止

foreach 的语法是 $(foreach var,list,text)，var 在 text 里临时绑定。它只产出文本，不执行命令：

makefile
$(foreach d,src include lib,[$(d)])   # [src] [include] [lib]

想让它触发规则，得配合 eval：

makefile
MODULES = parser renderer net

define MODULE_RULE
$(1)_OBJS := $$(patsubst src/$(1)/%.c,build/$(1)/%.o,$$(wildcard src/$(1)/*.c))
OBJS += $$($(1)_OBJS)
endef

$(foreach m,$(MODULES),$(eval $(call MODULE_RULE,$(m))))

这段看着绕，做的事很直白：给三个模块各生成一组变量和规则。$(1) 是 call 传进来的第一个参数，$$ 是留给下一层展开的转义。eval 会把展开后的文本重新喂给 make 解析器，等价于你手写了那些行。

call 配 define 就是 Makefile 版的宏：

makefile
define compile-template
	@echo "compiling $(1) -> $(2)"
	@mkdir -p $(dir $(2))
	$(CC) $(CFLAGS) -c $(1) -o $(2)
endef

build/main.o: src/main.c
	$(call compile-template,src/main.c,build/main.o)

info 在解析阶段就打印，不用跑到任何目标；error 直接终止解析。写错依赖路径时，先用 $(info ...) 看一眼变量展开成什么样：

makefile
$(info SRCS = $(SRCS))
$(error 没有找到任何源文件，检查 src 目录)

shell 执行命令并吃掉输出，末尾换行换成空格。它有副作用，每引用一次就跑一遍，所以用 :=：

makefile
GIT_HASH := $(shell git rev-parse --short HEAD)
CPPFLAGS += -DGIT_HASH=\"$(GIT_HASH)\"

九、条件判断与包含 #

9.1 四个条件指令 #

指令 判断内容
ifeq (a,b) 两个参数相等
ifneq (a,b) 两个参数不等
ifdef VAR 变量已定义且非空
ifndef VAR 变量未定义或为空

ifeq 有两种写法，效果一样。括号写法里逗号后的空格被忽略，引号写法里空格属于字符串内容，"gcc " 不等于 "gcc"：

makefile
ifeq ($(CC), gcc)
	libs = -lgnu
endif

ifeq "$(CC)" "gcc"
	libs = -lgnu
endif

ifdef 只看「值是否非空」，不看「是否被赋值过」。EMPTY = 之后再 ifdef EMPTY，判为假。

完整分支带 else：

makefile
CONFIG ?= debug

ifeq ($(CONFIG), release)
	CFLAGS = -O2 -DNDEBUG
else
	CFLAGS = -O0 -g -DDEBUG
endif

配合命令行：

bash
make CONFIG=release

?= 让用户在没指定时拿到 debug，指定时取用户值，一条命令切换两种构建形态。

9.2 三条硬规则 #

第一，条件指令不能以 Tab 开头。行首可以有空格，但一旦第一个字符是 Tab，make 会把它当命令行，报 recipe commences before first target。

第二，条件块里的变量赋值也不能以 Tab 开头。下面这段是错的：

makefile
ifeq ($(CONFIG), release)
	CFLAGS = -O2
endif

那个 Tab 会让 make 认为 CFLAGS = -O2 是一条待执行的命令。去掉 Tab，顶格写。

第三，条件在解析阶段求值，规则内的变量在命令执行阶段才存在。在规则命令里赋的值，ifeq 永远看不到，$(MODE) 展开只会是空。要按运行时的值分支，只能用 Shell 的 if：

makefile
all:
	@if [ "$(MODE)" = "release" ]; then echo release; else echo debug; fi

9.3 include：把 Makefile 拆开 #

include 把别的文件原样读进来，位置就在这一行：

makefile
include config.mk
include rules/common.mk

被包含的文件可以继续包含，形成树。MAKEFILE_LIST 记录所有已读文件的列表，可以拿来防重复包含或做调试：

makefile
$(info 已读入: $(MAKEFILE_LIST))

include 找不到文件会直接报错终止。不想因文件缺失中断，用 -include（等价写法 sinclude）：

makefile
-include $(DEPS)
-include local.mk

这行的作用是「有就读，没有就算了」，自动依赖生成全靠它。第十二章会用到。

拆文件的实用套路：把随机器变化的东西写进 local.mk，加进 .gitignore，主 Makefile 末尾 -include local.mk。团队其他人拿到仓库照样能编，本地路径各自维护。

十、多目录工程的 Makefile 组织 #

单个目录靠 wildcard *.c 就够。源码分散在 src/net/、src/http/、src/db/ 下面，事情就变了：产物往哪儿放，目录怎么建，头文件去哪找。

先定目录结构：

text
project/
├── Makefile
├── include/            # 对外头文件
│   ├── helper.h
│   └── protocol.h
├── src/                # 源码，可多层
│   ├── main.c
│   ├── helper.c
│   └── protocol/
│       └── protocol.c
├── build/              # 中间产物 .o .d，make 自动创建
└── bin/                # 最终可执行文件

build/ 这一层的意义是把中间产物的路径与源码路径一一对应：src/protocol/protocol.c 编译出的 .o 落在 build/protocol/protocol.o。源码树永远是干净的，rm -rf build 就等于回到初始状态。

10.1 VPATH 与 vpath #

依赖不在当前目录时，make 有两条搜索路径。

VPATH 是全局变量，任何找不到的文件都去这些目录里翻。UNIX 上用冒号分隔，Windows/DOS 上用分号：

makefile
VPATH = src:../headers

vpath 是关键字，按文件类型分别指定，命中面更窄：

makefile
vpath %.h include
vpath %.c src
vpath %.c src/generated   # 可以叠加多条
vpath %.h                  # 只写模式，清除该模式的搜索路径

VPATH 一开，所有文件都在那几个目录里找，容易撞名；vpath 按后缀分流，.h 只在 include/ 里找，.c 只在 src/ 里找。找到之后 make 会把依赖路径重写成实际路径，$< 也跟着变成 src/foo.c，所以 %.o: %.c 配 $(CC) -c $< -o $@ 照样能跑。

vpath 只改变「去哪儿找依赖」，不改变「命令怎么写」。-I 该加还得加，.o 的落点该指定还得指定。

10.2 源文件到目标文件的映射 #

三行变量把整个映射关系建起来：

makefile
SRCS = $(shell find src -name "*.c" | sort)
OBJS = $(patsubst src/%.c, build/%.o, $(SRCS))
DEPS = $(patsubst src/%.c, build/%.d, $(SRCS))

find 递归拿到所有 .c，patsubst 保留相对目录结构做前缀替换：src/a/b.c 对应 build/a/b.o。wildcard 只有一层，递归只能靠 find，代价是解析时 fork 一次进程，几十个文件的项目可以忽略。

末尾的 | sort 是为了顺序稳定。find 的默认顺序不保证，链接顺序、-j 的调度、日志对比都会跟着飘，出问题时没法复现。

10.3 构建目录自动创建 #

build/a/b.o 这个目标需要 build/a/ 目录先存在，否则 GCC 直接报 No such file or directory。两种做法：

makefile
# 做法一：每个目标自己的目录自己建
build/%.o: src/%.c
	@mkdir -p $(@D)
	$(CC) $(CFLAGS) $(CPPFLAGS) -c $< -o $@

# 做法二：解析阶段一次性建好所有目录
BUILD_DIRS := $(sort $(dir $(OBJS)))
$(shell mkdir -p $(BUILD_DIRS))

做法一在命令里建目录，$(@D) 就是目标所在目录，-p 保证已存在也不报错；命令前那个 @ 是必须的，否则每次编译都打印一行 mkdir。做法二把 mkdir 提到解析期，编译时少 fork 几百次进程。

10.4 一份完整可用的多目录模板 #

下面这份可以直接拷进项目用，改 TARGET 和 INCLUDES 就行：

makefile
# ---------- 工具与选项 ----------
CC       := gcc
CFLAGS   := -Wall -Wextra -O2 -g -std=c11 -MMD -MP
CPPFLAGS := -I./include
LDFLAGS  :=
LDLIBS   := -lm

# ---------- 目录与产物 ----------
SRC_DIR   := src
BUILD_DIR := build
BIN_DIR   := bin
TARGET    := $(BIN_DIR)/my_app

# ---------- 文件映射 ----------
SRCS := $(shell find $(SRC_DIR) -name "*.c" | sort)
OBJS := $(patsubst $(SRC_DIR)/%.c,$(BUILD_DIR)/%.o,$(SRCS))
DEPS := $(OBJS:.o=.d)

# ---------- 目标 ----------
.PHONY: all clean rebuild print

all: $(TARGET)

$(TARGET): $(OBJS)
	@mkdir -p $(@D)
	$(CC) $(OBJS) $(LDFLAGS) -o $@ $(LDLIBS)
	@echo "built: $@"

# 每个 .o 依赖同名 .c，同时生成 .d
$(BUILD_DIR)/%.o: $(SRC_DIR)/%.c
	@mkdir -p $(@D)
	$(CC) $(CFLAGS) $(CPPFLAGS) -c $< -o $@

# 引入编译器生成的依赖
-include $(DEPS)

# ---------- 辅助 ----------
print:
	@echo "SRCS = $(SRCS)"
	@echo "OBJS = $(OBJS)"
	@echo "DEPS = $(DEPS)"

rebuild: clean all

clean:
	$(RM) -r $(BUILD_DIR) $(BIN_DIR)

验证它真能跑，先造一个最小源码树：

bash
mkdir -p src/protocol include
printf '#include <stdio.h>\nint main(void){puts("ok");return 0;}\n' > src/main.c
make print

make print 会输出三行：SRCS = src/main.c、OBJS = build/main.o、DEPS = build/main.d；make 编出 bin/my_app。clean 里的 $(RM) 内置就是 rm -f，写成 $(RM) -r 等于 rm -f -r。

10.5 一个工程出多个产物 #

真实项目除了主程序还要出自研动态库，目录拆成 app/ 和 libs/，头文件跟着库走。两个产物、两条链接规则：

makefile
CFLAGS   := -Wall -Wextra -O2 -fPIC -MMD -MP
CPPFLAGS := -I./libs

LIB      := build/libcalculator.so
APP      := bin/app
LIB_OBJS := build/calculator.o
APP_OBJS := build/main.o
DEPS     := $(LIB_OBJS:.o=.d) $(APP_OBJS:.o=.d)

.PHONY: all clean
all: $(LIB) $(APP)

$(LIB): $(LIB_OBJS)
	@mkdir -p $(@D)
	$(CC) -shared $^ -o $@

$(APP): $(APP_OBJS) $(LIB)
	@mkdir -p $(@D)
	$(CC) $(APP_OBJS) -L$(dir $(LIB)) -lcalculator \
	      -Wl,-rpath,'$$ORIGIN/../build' -o $@

build/%.o: libs/%.c
	@mkdir -p $(@D)
	$(CC) $(CFLAGS) $(CPPFLAGS) -c $< -o $@

build/%.o: app/%.c
	@mkdir -p $(@D)
	$(CC) $(CFLAGS) $(CPPFLAGS) -c $< -o $@

-include $(DEPS)

clean:
	$(RM) -r build bin

四点值得说。

-fPIC 是 .so 的前提，必须加在编译阶段，加在链接阶段没用。

链接主程序时把 $(LIB) 写进依赖，make 才知道「库变了要重链程序」。漏了这一条，改了库不重链，跑起来还是旧逻辑。

$$ORIGIN 必须双写 $，第一个 $ 被 make 吃掉，传给链接器的是 $ORIGIN——动态链接器的运行时变量，指可执行文件所在目录。单引号是给 Shell 的，防止它先展开。

build/%.o: libs/%.c 和 build/%.o: app/%.c 两条同目标模式规则不冲突，make 按「哪个依赖真实存在」来挑。

十一、递归 make 与非递归写法 #

11.1 递归调用 #

每个子目录放一份自己的 Makefile，顶级文件挨个进去调：

makefile
SUBDIRS := src/parser src/renderer src/net

.PHONY: all $(SUBDIRS)

all: $(SUBDIRS)

$(SUBDIRS):
	$(MAKE) -C $@

-C 让 make 先 cd 进那个目录再找 Makefile。$@ 就是当前子目录名。

三点必须注意。

用 $(MAKE) 而不是写死 make。$(MAKE) 会带上父进程的 -n、-t、-j 等参数，保证 make -n 真的只是干跑；写死 make 会让子目录里的命令真的被执行，-n 形同虚设。

$(SUBDIRS) 要声明 .PHONY，否则目录名和文件同名时递归失效。

子目录之间有序依赖时，别指望 SUBDIRS 的顺序管用——加了 -j 它们会并行跑，顺序完全由依赖图决定。要固定先后，就在父 Makefile 里写成依赖：src/renderer: src/parser。

11.2 递归的三个隐患 #

递归把一张完整的依赖图切成了互不相识的几块，问题都从这儿来。

顺序错乱。模块 A 要链接模块 B 产出的库。并行 make -j8 时 A 的子 make 会先启动，找不到 .so 直接失败。要治，得在父 Makefile 里把 B 写成 A 的依赖，等于人为补一张图。

重复编译。多个子模块共用一份工具代码，各自目录里都有一份拷贝，就编多遍。抽成公共子目录，又要处理「谁来编、谁先编」。

变量传递靠 export。父 Makefile 的变量默认不进子 make，得显式 export CC CFLAGS CPPFLAGS，或者用 make -e 让环境变量压过子 Makefile 的赋值。忘了就是「父目录编得好好的，进子目录一编就报错」。

错误信息也难读。子 make 报的错前面挂一层目录名，多层嵌套之后一行错误要倒着看。

11.3 非递归：一个文件管全工程 #

非递归的做法是把所有源文件摊平到一张依赖图里，第十章那份模板就是：

makefile
SRCS := $(shell find src -name "*.c" | sort)
OBJS := $(patsubst src/%.c,build/%.o,$(SRCS))

不管源码在几层目录下，一条模式规则 build/%.o: src/%.c 全包，mkdir -p $(@D) 负责建目录。整个工程的依赖完整可见，-j 能正确并行，不会有跨模块的顺序问题。

代价是 Makefile 得自己维护目录结构。模块多了以后，find 会把所有目录的源码混在一起，想给某个模块单独加编译选项，就得退回静态模式规则或者 eval 生成规则。

选择标准很简单：模块之间耦合少、构建规则一致，用非递归扁平化；模块需要独立构建、独立发布，用递归。内核那种规模，两个都用——顶层递归进子系统，子系统内部扁平。

十二、依赖关系自动生成 #

第三章那个「改头文件没重编」的坑，靠人肉维护依赖列表治不好。一个 .c 引了十几个头文件，头文件又互相引，手写必漏。

正路是让编译器自己算。

12.1 -MMD 与 -MP #

GCC/Clang 在编译时能顺手吐出一份依赖描述：

bash
gcc -c -MMD -MP -I./include src/main.c -o build/main.o

跑完多了个 build/main.d：

makefile
build/main.o: src/main.c include/helper.h include/protocol.h
include/helper.h:
include/protocol.h:

第一行是真正的依赖关系，后面几行是 -MP 加的占位空目标。去掉 -MP 就只有第一行。

三个选项的区别：

选项 生成的依赖范围
-M 所有头文件，含系统头
-MM 排除系统头，只留项目内头文件
-MD 同 -M，但同时继续正常编译
-MMD 同 -MM，但同时继续正常编译

-M 系列只算依赖不编译，-MD 系列边算边编。构建系统里用 -MMD，既拿到依赖又完成编译，一趟搞定。

12.2 在 Makefile 里接上 #

makefile
CFLAGS  += -MMD -MP
DEPS    := $(OBJS:.o=.d)
-include $(DEPS)

三行。.d 文件在第一次编译时还不存在，所以必须用 -include，不能是 include——否则第一次跑 make 直接报文件找不到。

顺序很重要：-include 放到文件末尾。放在中间也能工作，但 make 会在解析到这一行时重读一遍 Makefile，因为引入的依赖改变了已知规则。

机制拆开看：第一次编译生成 main.d，里面写着 build/main.o: src/main.c include/helper.h。第二次跑 make，-include 把这个依赖并进全局图，main.o 的依赖里就多了 include/helper.h。此后改 helper.h，main.o 的 mtime 落后，自动重编。

12.3 头文件被删为什么会报错 #

.d 文件是快照。删掉 include/helper.h，build/main.d 里那一行还写着它。下次 make 读到这个依赖，发现文件不存在、也没有规则能生成它，直接终止：

text
make: *** No rule to make target 'include/helper.h', needed by 'build/main.o'.  Stop.

-MP 就是治这个的。它给每个头文件生成一条无依赖、无命令的空目标 include/helper.h:，等于告诉 make「这东西不存在也算正常，别找规则，别报错」。头文件真被删了，make 只是默默跳过，编译阶段再由 #include 报出正常错误。

12.4 老式的 sed 后处理写法 #

在 -MMD 普及之前，常见做法是用 gcc -M 生成依赖，再用 sed 改写行首：

makefile
%.d: %.c
	@set -e; rm -f $@; \
	$(CC) -M $(CPPFLAGS) $< > $@.$$$$; \
	sed 's,\($*\)\.o[ :]*,$$*.o $@ : ,g' < $@.$$$$ > $@; \
	rm -f $@.$$$$

拆开读。$$$$ 展开成 Shell 看到的 $$，也就是当前 Shell 的 PID，用它做临时文件名，避免并行编译时互相覆盖。set -e 让任何一步失败都立刻退出，不留半成品。

sed 那一行是核心：把 main.o: main.c ... 改写成 main.o main.d: main.c ...——让 .d 文件本身也依赖那些头文件。这样头文件一改，.d 会先被重新生成，依赖信息永不过期。

代价是每个 .c 要跑两次编译器（一次 -M，一次真正的编译），构建时间翻倍。有了 -MMD 之后，这套写法只该出现在老项目的维护现场。

12.5 几个实操细节 #

.d 和 .o 放在同一个目录，$(OBJS:.o=.d) 就是它们的列表，clean 把整个 build/ 一删就都清了——这也是中间产物集中存放的好处。用 patsubst 从 SRCS 直接算也行，效果一样。

.d 里的路径相对编译时的工作目录。在 build/ 里跑 make -f ../Makefile，.d 记的路径会错位。规则是：永远在工程根目录跑 make，别切进去。

十三、增量编译与并行 make #

13.1 增量编译靠什么生效 #

整套机制只有一个输入：mtime。目标比所有依赖新，就跳过；有一个依赖更新，就跑命令。没有任何缓存、指纹、编译命令哈希——这一点和 Bazel 那类工具的根本区别在这儿。

由此推出一串推论。

touch src/main.c 不改一个字符，make 照样重编 main.o。mtime 变了。

cp -p、rsync -a、git checkout 恢复文件，mtime 会变成操作发生的时间。从旧分支切回来，整棵树的文件看着都「刚改过」，于是全量重编。想避开就在检出后用 touch 统一对齐时间，或者接受这一遍全编。

系统时间被回拨，所有产物都「比源码新」，make 会安静地什么都不做，你还以为编译成功了。改完时钟记得 make clean。

最麻烦的是「改了依赖却没重编」和「没改却全编」这两类症状。前者查依赖是否列全（第三章、第十二章），后者查是不是有目录混进了依赖列表（第三章末尾的秩序依赖）。

13.2 并行：-j #

bash
make -j8          # 最多 8 个任务同时跑
make -j$(nproc)   # 按 CPU 核数
make -j           # 不限，能起多少起多少

-j 让互不依赖的目标同时构建，编译型项目的提速主要来自这里。

前提是依赖图正确。图错了，并行不会报错，会给出随机的失败——两个命令同时往一个文件里写，或者链接先于编译。这类问题的特征是「单独编能过，-j8 偶发失败」，看到就先去查依赖，别怀疑编译器。

-j 不带数字在大型项目上会把内存吃光。gcc 编 C++ 模板能吃掉几个 G，-j$(nproc) 在 16 核机器上就是 16 个进程同时啃内存。稳妥取值是核数或核数的一半，看单文件的内存占用。

-l 是负载限制，按系统 load average 卡住新任务：

bash
make -j8 -l4

两个 mkdir 竞争的场景要提一句。目录作为普通依赖时，并行下两个进程会同时 mkdir，其中一个报 File exists 退出。用 mkdir -p（幂等），或者把目录做成秩序依赖 |，冲突就没了。

不想让某个目标并行，声明 .NOTPARALLEL：

makefile
.NOTPARALLEL: clean install

13.3 失败时留下半成品 #

命令跑到一半失败，目标文件会残缺。下一次 make 看到目标存在且时间戳新，判定「已完成」，拿着一个坏文件继续往下走。这种错误极难查。

.DELETE_ON_ERROR 让 make 在命令失败时删掉那个目标：

makefile
.DELETE_ON_ERROR:

一条声明，全局生效。构建脚本里加上它，能省掉一整类诡异问题。

13.4 递归 make 与 -j #

父 make 收到 -j8，会通过 $(MAKE) 把参数带给子 make，于是每个子目录又开 8 个任务。八个子目录就是 64 个进程。

控制办法是给父进程一个 jobserver，子 make 通过它共享配额——前提是子进程用 $(MAKE) 而不是 make。写死 make 就绕过了 jobserver，配额失效。

十四、调试 Makefile #

Makefile 出问题，症状往往是「没跑」或「跑了不该跑的」。用这几个开关定位。

选项 作用
-n 只打印要执行的命令，不真执行
-s 静默，不回显命令
-p 打印内部规则数据库（变量、规则、隐含规则）
-d 打印极详细的决策过程
--debug=b 只打印「基础」决策，比 -d 干净得多
--trace 逐条打印「为什么重建这个目标」
-r 禁用所有内置隐含规则
-w 打印进入和离开的目录，递归时有用
-j1 单线程，排查并行竞争

14.1 先看要跑什么 #

make -n 是干跑。想确认「改了头文件会不会重编」，一眼就看出来——有编译命令说明判断正确，只有 up to date 说明依赖没接上。

-n 有个陷阱：带 @ 的命令照样打印，但 $(shell ...) 在解析阶段已经执行完，-n 拦不住。

make --trace 更直接，逐条打印重建原因：

text
Makefile:31: update target 'build/main.o' due to: src/main.c

比 -d 的几百行日志好读得多。

14.2 看变量到底是多少 #

最常用的手段是在 Makefile 里插一行 $(info SRCS = $(SRCS))。解析阶段就打印，不用跑任何目标；@echo 得挂在某个目标下，还得先跑到那个目标。

也可以做成一个专用目标，随时调用：

makefile
.PHONY: print
print:
	@echo "SRCS = $(SRCS)"
	@echo "OBJS = $(OBJS)"
	@echo "DEPS = $(DEPS)"

-p 打印的是 make 内部数据库，包含所有变量、所有规则、所有隐含规则，输出几百上千行。用法是重定向到文件再搜：

bash
make -p -f /dev/null 2>/dev/null | less

-f /dev/null 表示不读任何 Makefile，只 dump 内置规则，用来查「内置的 %.o 规则到底长什么样」。

14.3 查变量从哪儿来 #

origin 函数返回变量的出生地，flavor 返回它是递归展开还是简单展开：

makefile
$(info CC origin = $(origin CC))     # default / file / environment / command line
$(info CC flavor = $(flavor CC))     # recursive / simple

批量看所有变量：

makefile
.PHONY: debug-vars
debug-vars:
	@:$(foreach V,$(sort $(.VARIABLES)),\
		$(if $(filter-out default automatic,$(origin $(V))),\
			$(info $(V) = $($(V)) [$(origin $(V))])))

.VARIABLES 是 make 记录的全部变量名。filter-out 剔掉内置的和自动的，剩下的就是你自己的。@: 是个空命令占位，让这一行在语法上算一条命令。

14.4 递归与并行专属 #

递归调用时错误信息不带路径，加 -w 让 make 打印 Entering directory 和 Leaving directory，一眼看出错在哪一层。

并行偶发失败，先用 -j1 跑一遍。单线程能稳定复现就是依赖图缺边；单线程正常、多线程失败，九成是竞争写同一个文件。

十五、Makefile 的常见坑 #

按现场出现频率排，前六个占了八成。

坑 症状 修法
命令行用空格缩进 missing separator. Stop. 改成 Tab，别让编辑器转空格
每行命令独立 Shell cd 之后下一行又回原目录 写在同一行，cd x && make
$ 没转义 Shell 变量变成空 传给 Shell 的写 $$
条件块里 Tab 缩进 recipe commences before first target 条件内语句顶格
头文件未进依赖 改了 .h 报 is up to date -MMD -MP + -include
目录当普通依赖 每次 make 全量重编 用秩序依赖 |
.PHONY 漏声明 make clean 什么都没做 声明 .PHONY: clean
文件名带空格 变量展开后文件被拆成两个 项目里禁用空格，统一下划线
变量名大小写混用 $(cflags) 展开为空 统一大写，与内置变量对齐
隐含规则悄悄接管 没写规则的 .o 也被编出来 空命令模式规则取消它
行尾多余空格 变量值尾部带空格，比较失败 编辑器开「显示空白字符」

几个值得展开的。

每行命令一个 Shell。这是 Makefile 和 Shell 脚本最大的行为差异：

makefile
all:
	cd src
	pwd          # 还是原目录

两行命令跑在两个互不相干的子进程里，第一行的 cd 随进程退出而消失。要保住上下文，就合并成一行 cd src && pwd，或者用反斜杠续行把两行拼成一条命令。

再或者用 .ONESHELL: 让整条规则的命令走同一个 Shell：

makefile
.ONESHELL:
all:
	cd src
	pwd          # 这次在 src

$$ 转义。make 先吃掉一个 $，剩下的交给 Shell：

makefile
test:
	@echo $$HOME        # 输出 $HOME 的值
	@echo $(HOME)       # make 的变量 HOME，多半是空的

Shell 循环里也一样：

makefile
LIST = one two three
all:
	@for i in $(LIST); do echo $$i; done

$i 必须写成 $$i，否则 make 会去找名为 i 的 make 变量。

文件名带空格。make 用空格切分文件名列表，my source.c 会被当成两个文件。没有干净的解法。规矩定在项目初期：文件名与路径禁止空格，用下划线。历史遗留的，只能把命令整段塞进 $(shell ...) 用双引号包起来，或者干脆改文件名。

ifeq 判不了运行时值。第九章说过，条件在解析期求值，规则内的赋值在执行期发生。想在运行时分支，用 Shell 的 if。

模式规则写错，隐含规则顶上。%.o: %.cpp 写成 %.o: %.c，make 匹配不上，转身用内置的 .c → .o 规则，用默认 cc 和空 CFLAGS 编了一份。产物行为不对，但编译不报错。查这种问题用 --trace，看看到底哪条规则被绑定了。

十六、易错点速查 #

最后压成一张表，出问题时按症状查。

症状 根因 处置
missing separator 命令行不是 Tab 开头 换 Tab；或设 .RECIPEPREFIX
No rule to make target 'x' 目标不存在，也没有规则能生成 查路径拼写；make print 看变量展开
No rule to make target 'x.h', needed by 'y.o' .d 里记着已删除的头文件 加 -MP，或 make clean 重来
recipe commences before first target 条件块或变量赋值被 Tab 缩进 顶格写
is up to date 但代码明明改了 依赖列表漏了头文件 -MMD -MP + -include $(DEPS)
make clean 不执行 目录里有同名文件 .PHONY: clean
每次 make 都全量重编 目录被当成普通依赖 改成秩序依赖 |
命令没回显 行首有 @ 去掉 @；或 make -n 看全量命令
输出两遍同样的命令 递归调用写死 make，-n 失效 换 $(MAKE)
Shell 变量取不到值 $ 没写成 $$ 写 $$
-j8 偶发失败，单线程正常 依赖图缺边或竞争写同一文件 补依赖；mkdir -p；.NOTPARALLEL
改一行代码编了整个工程 $(wildcard *.h) 之类兜底依赖 换成编译器生成的 .d
变量展开为空 大小写错，或多字符变量没加括号 $(CFLAGS) 而不是 $CFLAGS
变量值尾巴多空格 赋值行结尾的空格被算进值 清掉行尾空白
递归 make 里变量丢了 父变量没 export export CC CFLAGS 或命令行传参
命令失败但 make 说成功 用 ; 连接，前一条失败被吞 改用 &&
编译报找不到头文件 vpath 只管依赖搜索，不管 -I 显式加 -I./include
链接报重复定义 用 $+ 而不是 $^ 换 $^ 去重

再补三条不算坑但容易忘的。

clean 之前先 make -n clean，看清它要删什么。rm -rf $(BUILD_DIR) 里变量为空，就变成 rm -rf，Shell 会拒绝执行空参数，但换个写法 rm -rf $(BUILD_DIR)/ 就真的从根上删了。

改了 Makefile 本身，已生成的目标不会自动重建。make 不把 Makefile 当依赖，除非你显式写：

makefile
$(OBJS): Makefile

这条加上之后，动一下 Makefile 就全量重编。值不值得，看项目大小。

最后一条，别把构建逻辑写进 Makefile 的规则命令里。规则命令应该是幂等的、可从零重跑的。需要判断、需要循环、需要状态，就写成脚本，Makefile 只负责调它——这样 make -n、并行、增量三件事都不会被破坏。
