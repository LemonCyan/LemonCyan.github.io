一、交叉编译是什么：为什么需要 #

交叉编译就一句话：在 A 架构的机器上，产出只能在 B 架构机器上跑的二进制。A 叫宿主机，B 叫目标机，两边指令集不同，编出来的机器码互相看不懂。

为什么非要绕这一圈？因为目标平台没有编译能力。

这不是性能偏好，是物理条件不允许。拿一块典型的嵌入式 ARM 板子看：

硬件项 常见规格 对「直接在板子上编译」意味着什么
CPU Cortex-A7 单核 800MHz ～ 1.2GHz 编一个中等规模 C 项目按小时算
内存 128MB ～ 512MB DDR3 GCC 编单个大文件就能吃掉 500MB，直接 OOM
存储 8MB SPI Flash，或者 4GB eMMC 装不下一套 GCC 工具链，解压后 1GB 起
系统 裁剪过的 BusyBox rootfs 没有 make，没有 python，没有 git，连 shell 都是残缺的
散热供电 无风扇被动散热，5V/2A 长时间满载编译会热降频，甚至掉电重启

还有一条更硬的：板子上只有运行库，没有开发库。rootfs 里有 libc.so.6，没有 stdio.h，没有 crt1.o，没有 libc.a。链接这一步压根做不了。

有人会说，那把编译器也装到板子上行不行？行，但你得先有一套能在板子上跑的编译器。而编这套编译器，又需要一套交叉工具链。绕回原点。这条路只在极端场景下有人走（板子就是最终交付环境，客户要求现场自编译），代价是先花一周做自举。

更实际的问题是迭代速度。改一行代码，等 40 分钟看结果，这个循环没人受得了。换到 32 核的 x86 服务器上并行编译，同一个工程两分钟出结果。一次配置，还能顺手给整条产品线十几块板子编同一份代码。

维度 本地编译 交叉编译
编译器所在 CPU 与程序运行的 CPU 相同 不同（x86 上跑，ARM 上跑程序）
编译器名字 就是 gcc 带前缀，如 arm-linux-gnueabihf-gcc
链接时找的库 系统自带的 /usr/lib 目标平台的 sysroot
头文件来源 /usr/include sysroot 里的 usr/include
跑起来验证 直接执行 qemu 模拟，或拷到真机
出错暴露位置 编译期和运行期都在同一台机器 编译期在宿主机通过，错要等上板才暴露

代价也得说清楚。本地编译时，编译器自己知道去哪找头文件和库，你敲 gcc main.c 就完事。交叉编译时，编译器对目标平台一无所知，一切都要你显式告诉它：编译器路径、sysroot 在哪、pkg-config 该查哪个目录、链接器去哪找间接依赖。漏掉任何一项，症状都不是「报错说找不到」，而是「悄悄用了宿主机的库，编出来能过，上板就崩」。

最后，什么时候你其实不需要交叉编译：编 x86 服务器上的服务、编跑在同一台机器上的桌面程序、在 CI 容器里编容器自己要跑的代码。这些场景本地编译就够了，硬上交叉编译只会给自己加活。

二、三元组：host、build 与 target #

GNU 编译系统里有三个机器角色，名字起得极容易混。先记住一句话：这三个词描述的是三段不同的旅程，不是三台不同的机器。

名字 中文 谁在上面跑 用来描述什么
build 构建平台 编译命令 你现在敲 make 的那台机器
host 宿主平台 编译出来的产物 产物将来在哪台机器上运行
target 目标平台 编译器生成的代码 只在编编译器自身时才用得上

看出问题了吗。host 这个词，在「编一个普通程序」时指的是「程序要跑的那台机器」；在「编一个编译器」时指的是「编译器自己要跑的那台机器」。同一个词，两层意思。

判定规则就三条：

关系 叫什么 例子
build == host == target 本地编译 x86 上编 x86 程序
build == host != target 交叉编译器自身的编译 x86 上编一个「跑在 x86、产出 ARM 代码」的 GCC
build != host 交叉编译（Canadian Cross） x86 上编一个「跑在 ARM、产出 ARM 代码」的 GCC，再搬到板子上用

日常做嵌入式，你干的是第二行：编出一个 host 是 x86、target 是 ARM 的 GCC。这个 GCC 装在 x86 上，build 和 host 都是 x86，它吐出来的代码是 ARM 的。

三元组名字怎么读 #

交叉工具链的可执行文件一律带前缀，格式是：

text
arch-vendor-os-abi

四个字段，拆开看 arm-linux-gnueabihf：

字段 这一段的值 含义 写错的后果
arch 架构 arm 目标 CPU 指令集 写成 aarch64 编出 64 位码，在 32 位板子上第一条指令就非法
vendor 厂商 省略（等价 unknown、none） 工具链出品方，纯命名用 不影响功能，但前缀对不上 PATH 里的文件名，就是 command not found
os 系统 linux 目标操作系统 写成 none 就丢掉 Linux 系统调用，printf 还能用，open 不行
abi 接口 gnueabi + hf C 库实现 + 调用约定 + 浮点约定 软浮点编的库和硬浮点程序混链，浮点参数全乱，且不报错

再拆 arm-none-linux-gnueabi：arm 架构，none 厂商（占了位但无实际含义），linux 系统，gnueabi 走 glibc + EABI 调用约定、浮点走软浮点或 softfp。

abi 这一段是复合的，gnueabihf 要读成三截：gnu（C 库是 glibc）、eabi（遵循 ARM EABI 调用标准）、hf（hard float，硬浮点）。少读一截就会把 gnueabi 和 gnueabihf 当成同一个东西，而这两个恰好不兼容。

五款常见工具链，谁是谁 #

前缀 出品方 定位 浮点 / ABI 适用范围
arm-none-linux-gnueabi- CodeSourcery（后并入 Mentor，再并入 Siemens） 32 位 ARM + Linux EABI，软浮点或 softfp 裸机、U-Boot、内核、rootfs、应用，全流程都能编
arm-linux-gnueabihf- Linaro 及各家发行版构建 32 位 ARM + Linux EABI + 硬浮点，浮点参数走 VFP/NEON 寄存器 同上一行，且 CPU 带 FPU
aarch64-linux-gnu- Linaro ARMv8 64 位 + Linux LP64，硬浮点 树莓派 4、RK3568、飞腾
arm-none-eabi- GNU 官方与芯片厂商 裸机，无操作系统 EABI + Newlib STM32、Cortex-M、FreeRTOS、RT-Thread
arm-none-elf- 同上 裸机，输出标准 ELF EABI 老项目，现在多被 arm-none-eabi- 取代

硬浮点与软浮点 #

这是 ARM 交叉编译里第二个大坑，比三元组还隐蔽，因为它不报错。

模式 机制 函数调用怎么传浮点参数 速度 兼容性
软浮点 soft CPU 不用 FPU，所有浮点运算编成 libgcc 里的软件函数调用 走通用寄存器（r0-r3） 慢，float a = b * 3.14f 都是一串函数调用 好，没有 FPU 的 ARM9 也能跑
softfp 指令用 FPU，但调用约定仍走通用寄存器 走通用寄存器，中间要搬进搬出 中 与软浮点目标文件可混链
硬浮点 hard（hf） 直接生成 FPU 指令，浮点数直接装进硬件浮点寄存器 走 s0-s15 / d0-d7 快 与软浮点完全不兼容

名字上的区分点：

  • arm-linux-gnueabi-：软浮点或 softfp。
  • arm-linux-gnueabihf-：硬浮点，hf 就是 hard float。

混链的症状特别难受：链接器不报错，因为两边的符号名一样，只是参数传递约定不同。程序跑起来，浮点参数拿到的是垃圾值，或者函数返回后栈被踩。查三天也未必查到是浮点 ABI 的问题。

判断板子支不支持硬浮点，看内核启动日志：

bash
# 在板子上执行
cat /proc/cpuinfo | grep -i -E 'features|vfp|neon'
# 输出里出现 vfp / vfpv3 / vfpv4 / neon，说明有 FPU，可以用 hf 工具链

选型三句话 #

  • 玩单片机，Cortex-M，没有 Linux：arm-none-eabi-gcc，没有第二个选项。
  • 做嵌入式 Linux，Cortex-A（IMX6、Exynos4412、AM335x）：CPU 有 FPU 就用 arm-linux-gnueabihf-gcc，没有就用 arm-none-linux-gnueabi-gcc。
  • 做 64 位 ARM Linux（树莓派 4、RK3568、飞腾）：aarch64-linux-gnu-gcc。

一个必须拆开的同名陷阱 #

./configure 的 --host 和 GCC 三元组的 host 不是一回事。autoconf 的三个参数含义是：

autoconf 参数 含义 对应 GCC 三元组里的
--build 执行编译的那台机器 build
--host 编出来的程序将来运行的机器 target
--target 只有编译编译器时才填 target 的 target

所以移植第三方库时写 ./configure --host=arm-linux，意思是「我要一个跑在 arm-linux 上的程序」，等价于告诉 GCC「target 是 arm-linux」。它跟 GCC 三元组里的 host 恰好错开一层。这个概念错位是从 autoconf 继承来的历史包袱，解释不清就会一直有人写反。

验证你手上这套工具链到底是给谁的，三条命令足够：

bash
arm-linux-gnueabihf-gcc -dumpmachine          # 输出 target，即 arm-linux-gnueabihf
arm-linux-gnueabihf-gcc -print-sysroot        # 默认去哪找头文件和库
arm-linux-gnueabihf-gcc -v 2>&1 | tail -n 20  # 看 --target= 与 --host= 分别是什么

三、交叉工具链的组成 #

一套交叉工具链不是「一个 gcc 文件」。它是几十个可执行文件加一堆库和头文件，咬合在一起才能干活。你想只拷一个 gcc 到别的机器上编译，跑不起来。

text
[ Binutils: as ld ar objdump ]  +  [ GCC: cc1/cc1plus ]  +  [ C 运行库: glibc/musl ]
                                        |
                                   [ sysroot: usr/include + usr/lib ]

Binutils：所有工作的地基 #

Binutils 处理的是二进制机器码和 ELF 文件本身，不碰源码语义。

工具 干什么 在交叉环境里什么时候用
as 汇编器，把 .s 翻成 .o GCC 内部调用，你不直接敲
ld 链接器，合并 .o、重定位符号、产出可执行文件 间接调用；排查依赖时直接调
ar 归档器，把多个 .o 打成 .a 静态库 打包自己的库
objdump 反汇编、看段信息、看依赖 查「这个程序要什么 glibc 版本」
readelf 解析 ELF 头、段、动态段 查解释器路径、查 .dynamic
nm 列出符号表 查未定义符号从哪来，ranlib 给 .a 建索引也走这条路
strip 删调试符号，缩体积 出厂固件前必做
objcopy 格式转换、段抽取 .elf 转 .bin、.hex

交叉环境里的 binutils 是独立一套，名字带前缀：arm-linux-gnueabihf-ld、arm-linux-gnueabihf-objdump。你敲 objdump 用的是宿主机的，它解析 ARM ELF 会报 File format not recognized。

GCC：前端加优化加代码生成 #

GCC 在交叉工具链里是三个可执行文件的分工：cc1（C 前端）或 cc1plus（C++ 前端）读源码、做语法语义分析、生成中间表示；优化和指令选择在这一层完成，输出的直接是目标平台汇编；最后调 as 变成 .o。

关键点：GCC 里不含目标平台的 C 库。它知道怎么生成 ARM 指令，但不知道 printf 的实现在哪。那部分靠 C 库和 sysroot 补。

C 库：决定程序能不能在板子上活下来 #

C 库 体积量级 动态链接 静态链接 典型用途
glibc 大，几十 MB 完整支持 有坑，见第九章 通用嵌入式 Linux、Ubuntu/Debian rootfs
musl 小，几百 KB 支持 干净，无 NSS 外部依赖 静态单文件分发、Alpine、极简 rootfs
uClibc-ng 更小 支持 可用 内存敏感的路由器固件、老式工控
newlib 极小 无（裸机不需要） 就是静态 Cortex-M 裸机、RTOS
bionic 中 支持 受限 Android

工具链里的 C 库版本必须和目标板上跑的版本对得上。低版本程序在高版本 glibc 上跑没问题（向下兼容），反过来必崩。所以规则是一条单向的：工具链的 glibc 版本 ≤ 板子上 rootfs 的 glibc 版本。

为什么要花半小时自己编 #

因为工具链是分好几轮才长成的。一步到位编不出来，原因是鸡生蛋：

  1. 先用宿主机的 gcc 编出目标平台的 binutils（as、ld）。
  2. 装目标平台的内核头文件（linux-libc-headers）。
  3. 用目标 binutils 编一遍只有 C 前端、没有 C 库的 GCC，让它能产目标代码。
  4. 用这个残缺 GCC 编目标平台的 C 库（glibc 或 musl）。
  5. 用完整的 C 库重编一遍 GCC，这次它才带上完整的头文件搜索路径、crt*.o、libgcc。

这就是 crosstool-ng 在后台干的事，也是它为什么要跑半小时到一小时。手搓这五步，任何一步参数写错，前面全部重来。

四、sysroot 与头部文件 #

sysroot 是整套交叉编译的核心概念，理解它，一半的坑自动消失。

sysroot 就是一个目录，里面按目标板的根文件系统布局摆好了头文件和库。编译器被明确告知「你的世界只有这个目录」，从此不再往宿主机的 /usr/include 和 /usr/lib 看。

text
/opt/x-tools/arm-linux-gnueabihf/arm-linux-gnueabihf/sysroot/
├── usr/
│   ├── include/                   # C 库头：stdio.h、stdlib.h、pthread.h
│   │   └── linux/  asm/  bits/    # 内核头（来自 linux-libc-headers）+ glibc 私有头
│   └── lib/
│       ├── crt1.o  crti.o  crtn.o # 程序启动/退出胶水代码
│       └── libc.so  libc.a  libpthread.a
├── lib/
│   ├── ld-linux-armhf.so.3        # 动态链接器，路径会写进 ELF 的 INTERP 段
│   └── libc.so.6
└── etc/

三层头文件必须分清，混了就会出「struct stat 大小不对」这类灵异问题：

头文件层 来源 位置 作用
编译器内建头 GCC 自带 lib/gcc/<tuple>/<ver>/include stddef.h、stdarg.h，与平台无关
内核头 linux-libc-headers sysroot usr/include/linux、usr/include/asm 系统调用号、ioctl 编号、结构体布局
C 库头 glibc / musl sysroot usr/include stdio.h、pthread.h 这些

内核头和板子上跑的内核版本也要对齐。内核头比板子内核新，编出来的程序调了板子内核不认识的 ioctl，运行期返回 EINVAL，编译期一点提示都没有。

显式指定 sysroot 有两种写法：单条命令传 --sysroot=，或者先 export SYSROOT 再引用（后者连 ld、as 一起受影响）：

bash
SYSROOT=/opt/x-tools/arm-linux-gnueabihf/arm-linux-gnueabihf/sysroot
arm-linux-gnueabihf-gcc --sysroot=$SYSROOT main.c -o app

检查头文件到底从哪来，别看猜，让编译器自己报：

bash
# 打印头文件搜索顺序，注意前面挂的 sysroot 前缀
arm-linux-gnueabihf-gcc -E -v -x c /dev/null 2>&1 | sed -n '/search starts here:/,/End of search list/p'

# 打印库搜索顺序
arm-linux-gnueabihf-gcc -print-search-dirs

# 确认默认 sysroot
arm-linux-gnueabihf-gcc -print-sysroot

搜索列表里只要出现没有 sysroot 前缀的 /usr/include，就说明有东西在往宿主机串。查两个地方：CPATH、C_INCLUDE_PATH 环境变量，还有自己 -I 手工加的路径。

sysroot 和板子上真实 rootfs 是两份东西，必须保持一致。板子上 glibc 是 2.31，你拿 glibc 2.35 的工具链编，装到板子上报 GLIBC_2.34 not found。反过来，工具链比板子老，能跑。想省事，把板子的 rootfs 整个 rsync 下来当 sysroot 用，这是最稳的做法。

五、用 crosstool-ng 构建工具链 #

拿到交叉工具链有三条路，先认清代价。

路子 做法 耗时 适合谁
用现成的 发行版仓库、Linaro、ARM 官方、芯片厂商 SDK 5 分钟 95% 的场景，优先选这条
纯手搓 自己编 binutils、内核头、GCC、glibc，一步步拼 一到几天，成功率低 学原理、教学
用构建器 crosstool-ng（配 glibc）、buildroot（配 uClibc/musl） 30 分钟到 1 小时 需要定制 glibc 版本、定制 CPU 参数、定制前缀

第二条路先劝退一下：需要下载十几个源码包，编三轮 GCC，参数几百个，任何一步错都要从头来。经验再足的人手搓一整套，也要折腾一天。uClibc 比 glibc 小，在已有接口上兼容，但没把 glibc 的接口实现全。

所以真正的选择是第三条。crosstool-ng 提供一套跟 Linux 内核 menuconfig 一样的图形配置菜单，把几十个包的版本、参数、补丁全管起来。

5.1 装依赖 #

bash
sudo apt update
sudo apt install -y autoconf automake bison flex g++ gawk \
    libtool-bin libncurses5-dev libtool make patch python3-dev \
    texinfo unzip help2man wget rsync cvs git \
    libgmp-dev libmpfr-dev libmpc-dev

最后三个是 GCC 自身要的高精度数学库开发头文件，缺了会在编 GCC 时断在 gmp.h: No such file or directory。

5.2 编 crosstool-ng 自身 #

bash
wget http://crosstool-ng.org/download/crosstool-ng/crosstool-ng-1.25.0.tar.xz
tar -xf crosstool-ng-1.25.0.tar.xz
cd crosstool-ng-1.25.0

./configure --prefix=/opt/crosstool-ng
make
sudo make install
export PATH=$PATH:/opt/crosstool-ng/bin

验证装好了：

bash
ct-ng version

5.3 选模板、进菜单 #

bash
mkdir -p ~/build-toolchain
cd ~/build-toolchain

# 用 ct-ng 内置的板级模板起手，这里以 Cortex-A9 带 NEON 为例
ct-ng arm-cortexa9_neon-linux-gnueabihf

# 看还有哪些模板可用
ct-ng list-samples

# 进图形配置
ct-ng menuconfig

菜单里四个位置要你亲自定，剩下的保持默认。

菜单 选项 怎么填
Paths and misc options Try features marked as EXPERIMENTAL 要用高版本 GCC 时勾上，否则版本列表被截断
Paths and misc options Local tarballs directory 设成固定物理目录，如 /home/dev/src，下载的源码包留着复用
Target options Architecture level 填板子真实架构，如 armv7-a
Target options Instruction set ARM 模式还是 Thumb 模式，见第七章
Target options Floating point 勾 hardware (FPU)，再选 FPU 类型，如 neon-vfpv4
Toolchain options Tuple's vendor string 自定义厂商名。填 geek，前缀就是 arm-geek-linux-gnueabihf-
C library C library glibc 还是 musl，按板子空间定
Operating System 目标 OS 跑 Linux 填 linux，裸机填 bare-metal

Architecture level 和 Floating point 填错，编出来的指令板子跑不了，报 Illegal instruction。查板子支持什么，看 cat /proc/cpuinfo 的 Features 行，或者芯片手册的 core 型号。

5.6 裸机固件：走 newlib #

给 STM32 这类 Cortex-M 单片机、或者跑 FreeRTOS 的固件，目标不是 arm-linux-gnueabihf，是 arm-none-eabi。两者的差别是硬性的：

项 arm-linux-gnueabihf- arm-none-eabi-
目标 OS Linux 无（bare-metal）
C 库 glibc / musl Newlib / Newlib-nano
系统调用 有，走 svc 进内核 没有，_write、_sbrk 要自己实现
程序入口 _start 由 crt1.o 提供 复位向量，链接脚本指定
产物 ELF 可执行文件，带 INTERP .elf，再 objcopy 成 .bin/.hex
刷写 scp 或 nfs ST-Link、J-Link、串口 ISP

配置方法：ct-ng menuconfig → Operating System 选 bare-metal → C library 选 newlib。编出来的前缀自动变成 arm-none-eabi-。要压体积，C library 里再勾 newlib-nano。

裸机工具链的 C 库要自己补底层桩函数，printf 想输出到串口就得实现 _write：

c
/* syscalls.c —— 裸机 newlib 的重定向桩，给 printf 接到串口 */
int _write(int fd, const char *buf, int len)
{
    for (int i = 0; i < len; i++) {
        while (!(USART1->SR & USART_SR_TXE)) { }
        USART1->DR = buf[i];
    }
    return len;
}
/* 其余桩函数按需补：_read / _close / _fstat / _isatty / _lseek / _exit */

7.1 ARM 模式与 Thumb 模式 #

ARM 有两种指令编码，选哪种直接影响体积和速度，编译参数就能切。

模式 参数 指令宽度 代码体积 执行效率 适合
ARM -marm 全 32 位 大 高，流水线吃满 计算密集的核心算法
Thumb-2 -mthumb 多为 16 位，少数 32 位 小 30% ～ 40% 比 ARM 低 5% ～ 10% Flash 紧张的上层逻辑、协议栈 
bash
# 榨性能
arm-linux-gnueabihf-gcc -marm -O3 main.c -o app_arm

# 榨体积
arm-linux-gnueabihf-gcc -mthumb -Os main.c -o app_thumb

# 对比一下差多少
size app_arm app_thumb

实际项目里多半混用：音频编解码、加解密这类热点编成 ARM 模式，控制逻辑和网络协议栈编成 Thumb。要按函数切，用 __attribute__((target("arm"))) 和 __attribute__((target("thumb"))) 分别标在函数声明前。前提是板子的 CPU 支持 Thumb-2（Cortex-A7 及以上都支持，ARM7TDMI 只有老 Thumb，没有 32 位混合指令）。

7.2 移植开源库的固定套路 #

zlib、openssl、libpng 这类库，交叉编译的流程都一样，只是参数名各家不同。

bash
# 五个变量顶掉 configure 自己拼出来的前缀
export CC=arm-linux-gnueabihf-gcc CXX=arm-linux-gnueabihf-g++ AR=arm-linux-gnueabihf-ar
export RANLIB=arm-linux-gnueabihf-ranlib STRIP=arm-linux-gnueabihf-strip

# --host 说产物跑在 arm-linux 上（注意第二章那个同名陷阱）
# --prefix 指向独立的本地目录，别装进宿主机的 /usr/local
./configure --host=arm-linux --prefix=/home/dev/dist_zlib --enable-shared --enable-static
make -j$(nproc) && make install

--host=arm-linux 不需要写全四段。configure 只拿它拼前缀去找 arm-linux-gcc，匹配到就认。但你的工具链叫 arm-linux-gnueabihf-gcc，拼出来对不上，所以要么写全 --host=arm-linux-gnueabihf，要么靠上面那几个 CC/AR 环境变量顶掉。第二种更稳。

装出来的东西分两堆，去向不同：

bash

cp -a /home/dev/dist_zlib/lib/*.so*  $SYSROOT/usr/lib/
cp -a /home/dev/dist_zlib/lib/*.a    $SYSROOT/usr/lib/

# 运行库：进板子的 /usr/lib

7.3 CMake 工程怎么交叉编 #

CMake 工程不能直接 cmake .，得喂一个 toolchain 文件。写在文件里比一堆 -D 参数可靠。

cmake
# arm_toolchain.cmake
# 1. 目标系统与架构
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR arm)

# 2. 编译器物理路径，用绝对路径，别指望 PATH
set(CMAKE_C_COMPILER   /home/dev/x-tools/arm-geek-linux-gnueabihf/bin/arm-geek-linux-gnueabihf-gcc)
set(CMAKE_CXX_COMPILER /home/dev/x-tools/arm-geek-linux-gnueabihf/bin/arm-geek-linux-gnueabihf-g++)

# 3. sysroot：头文件和库只从这找
set(CMAKE_SYSROOT /home/dev/x-tools/arm-geek-linux-gnueabihf/arm-geek-linux-gnueabihf/sysroot)

# 4. 搜索范围：程序用宿主机的，库和头只认目标平台
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)

bash
cmake -DCMAKE_TOOLCHAIN_FILE=arm_toolchain.cmake -B build_arm -G Ninja
cmake --build build_arm -j8

三行 FIND_ROOT_PATH_MODE 是最关键的部分。少了 LIBRARY ONLY，find_library(ZLIB ...) 会先命中宿主机的 /usr/lib/x86_64-linux-gnu/libz.so，链接期报架构不匹配，或者更糟——静态库里混进 x86 目标文件。PROGRAM NEVER 是为了让 find_program 还能找到宿主机的 protoc、flex 这些构建期工具。

九、交叉编译的三类常见错误 #

交叉编译的报错看着五花八门，归到根上就三类。先看总表，对号入座。

类别 典型症状 出错阶段 根本原因
运行期找不到解释器或符号 No such file or directory、GLIBC_2.34 not found 上板运行 工具链 glibc 比板子新，或解释器路径不存在
链接期找不到库 cannot find -lX、undefined reference to xxx ld 阶段 间接依赖没告诉链接器去哪找，或 sysroot 缺库
编译期串到宿主机 编得过、上板崩；struct 大小不对；x86 目标文件混进静态库 编译 / 链接 sysroot 没生效，/usr/include、/usr/lib 泄漏

9.1 运行期报 No such file or directory #

文件明明在，ls 看得见，chmod +x 也加过，一跑就说找不到。这是最经典的坑。

text
-sh: ./my_app: No such file or directory

这个错误说的不是 my_app 找不到，是 ELF 头里写的解释器路径在板子上找不到。

bash
# 在宿主机上看它到底要哪个解释器
readelf -l ./my_app | grep interpreter
#   [Requesting program interpreter: /lib/ld-linux-armhf.so.3]

拿去板子上比对：

bash
ls -l /lib/ld-linux-armhf.so.3
# 没有 → 板子 rootfs 太老，或者用的是软浮点 rootfs

三种修法，按推荐度排：

修法 操作 代价
换匹配的工具链 用和板子 glibc 对齐的工具链重编 最干净，推荐
建软链接 ln -s /lib/ld-2.23.so /lib/ld-linux-armhf.so.3 快，但 ABI 不匹配时仍会崩
静态链接 -static，连解释器都不用 体积大，glibc 静态有坑，见 9.4

软链接那招能救急，但要确认两件事：板子上真实存在的解释器名字（ls /lib/ld-*.so*），以及它是硬浮点还是软浮点。软浮点的 ld-linux.so.3 硬链到硬浮点程序上，程序能启动，浮点运算全错。

9.2 链接期找不到库与符号版本 #

间接依赖断裂。 你的程序链了共享库 A，A 内部又隐式依赖 B。链接期，ld 要找 B 才能校验符号，但它不知道去哪找——因为交叉链接器默认拒绝查宿主机的 /usr/lib，这是安全设计，防止把 x86 的库链进来。

text
/usr/bin/ld: warning: libB.so.1, needed by ./libs/libA.so, not found (try using -rpath or -rpath-link)
./libs/libA.so: undefined reference to `func_in_b'

解法是 -rpath-link，只影响链接期，不写进最终 ELF：

bash
aarch64-linux-gnu-gcc main.o -L./libs -lA \
    -Wl,-rpath-link,$SYSROOT/usr/lib \
    -o app

-rpath-link 和 -rpath 别混：-rpath 会写进 ELF 的 RPATH/RUNPATH，影响运行期搜索路径；-rpath-link 只在链接这一秒起作用。

glibc 符号版本不匹配。 glibc 用符号版本化维持向下兼容，每个符号绑着版本号。

text
/lib/libc.so.6: version `GLIBC_2.34' not found (required by ./my_app)

查是谁绑了高版本：

bash
objdump -p ./my_app | grep -A30 'Version References'
# 或者
readelf -V ./my_app

查出 memcpy@@GLIBC_2.34 这类绑定，可以在源码里强指老版本：

c
/* 把 memcpy 绑定到板子上存在的 GLIBC_2.2.5 */
__asm__(".symver memcpy,memcpy@GLIBC_2.2.5");

把它放在一个必被链接的头文件里，全工程生效。这招只适合零星几个符号被抬版本的情况。大面积不匹配就别打补丁了，换工具链，或者把板子 rootfs 升级。

更稳的路子是反过来做：先查板子 glibc 版本，再挑一个不比它新的工具链。

bash
# 板子上
ldd --version | head -n 1
# ldd (GNU libc) 2.31  → 工具链的 glibc 必须 ≤ 2.31

# 宿主机上查工具链自带的 glibc 版本
$SYSROOT/lib/libc.so.6 | head -n 1

9.3 编译期串到宿主机 #

这一类最阴，因为它不报错。

症状长这样：编过了，链接过了，上板崩；或者 sizeof(struct stat) 在宿主机上算出来 144，板子上是 88；或者静态库里翻出 .o 是 x86-64 格式。

bash
# 一眼看出静态库里的目标文件架构对不对
arm-linux-gnueabihf-ar t libfoo.a
arm-linux-gnueabihf-objdump -f libfoo.a | grep -E 'architecture|file format'
# architecture: i386:x86-64  ← 完了，混进宿主机的东西了

查泄漏源，按顺序排：

bash
# 1. 头文件搜索路径里有没有裸的 /usr/include
arm-linux-gnueabihf-gcc -E -v -x c /dev/null 2>&1 | sed -n '/search starts here:/,/End of search list/p'
# 2. 环境变量污染
env | grep -E '^(CPATH|C_INCLUDE_PATH|CPLUS_INCLUDE_PATH|LIBRARY_PATH|LD_LIBRARY_PATH)='
# 3. pkg-config 给的是不是宿主机路径（见第十章）
pkg-config --cflags --libs zlib

常见泄漏源就三个：自己 -I/usr/include 加的；pkg-config 吐出来的宿主机路径；LIBRARY_PATH 环境变量。清掉它们，或者用第十章的办法把 pkg-config 关进 sysroot。

9.4 静态链接的坑与 musl 的解法 #

想给板子一个单文件、不依赖 .so 的程序，-static 看起来很省事：arm-linux-gnueabihf-gcc -static hello.c -o hello_static。用 glibc 静态链接会刷一屏警告，原因在 glibc 内部：

  • 名称服务开关（NSS）在运行时要 dlopen，libnss_files.so、libnss_dns.so 这些没法静态打进去。
  • getaddrinfo 做域名解析走的就是 NSS 这条路。

结果：程序静态链接成功，体积 800KB，跑到板子上 printf 正常，一调 getaddrinfo 就失败。你以为拿到了零依赖，其实只是把依赖藏起来了。

C 库 静态链接表现 单文件分发
glibc 有 NSS/dlopen 残留，域名解析会失败 不可靠
musl 无 NSS，所有接口静态打包 可靠，体积小
uClibc-ng 基本可用，功能子集 可用，功能少

要真正的零依赖单文件，把 crosstool-ng 的 C library 从 glibc 换成 musl 重编一套：

bash
# 换库重编 → 用新工具链静态编译
musl-gcc -static -Os hello.c -o hello_musl
file hello_musl
# ELF 32-bit LSB executable, ARM, EABI5, statically linked

uClibc-ng 走另一条路：面向内存极敏感的 Linux 路由器固件，功能是 glibc 的子集。选它之前先确认你的代码没用它缺的接口。

十、pkg-config 与交叉编译 #

pkg-config 是交叉编译里第二个污染源。它读 .pc 文件，.pc 里的路径写的是宿主机的绝对路径，直接喂给交叉编译器就串了。

bash
# 宿主机上的输出，全是 x86 路径
pkg-config --cflags --libs zlib
# -I/usr/include -lz

三个环境变量把它关进 sysroot：

变量 作用 该填什么
PKG_CONFIG_SYSROOT_DIR 给所有 .pc 里的路径加前缀 $SYSROOT
PKG_CONFIG_LIBDIR 覆盖默认的 .pc 搜索目录 $SYSROOT/usr/lib/pkgconfig:$SYSROOT/usr/share/pkgconfig
PKG_CONFIG_PATH 追加搜索目录 交叉编出来的库自己的 .pc 目录

PKG_CONFIG_LIBDIR 和 PKG_CONFIG_PATH 的差别要记牢：LIBDIR 是替换默认列表，PATH 是追加。用 PATH 而不清空默认列表，宿主机 /usr/lib/pkgconfig 还在里面，照样串。所以交叉编译只用 LIBDIR。

标准写法：

bash
export SYSROOT=$HOME/x-tools/arm-geek-linux-gnueabihf/arm-geek-linux-gnueabihf/sysroot
export PKG_CONFIG_SYSROOT_DIR=$SYSROOT
export PKG_CONFIG_LIBDIR=$SYSROOT/usr/lib/pkgconfig:$SYSROOT/usr/share/pkgconfig
unset PKG_CONFIG_PATH

# 验证：输出里每一项都应该带 sysroot 前缀
pkg-config --cflags --libs zlib
# -I$SYSROOT/usr/include -L$SYSROOT/usr/lib -lz

再配一个 wrapper 更省事，写进 ~/bin/arm-pkg-config：把上面三个变量固定住，然后 exec pkg-config "$@"。这样 make 里只要 PKG_CONFIG=arm-pkg-config，团队里谁都不用记这些变量名。

CMake 里对应这么写，别用 FindPkgConfig 的默认行为：

cmake
set(ENV{PKG_CONFIG_SYSROOT_DIR} ${CMAKE_SYSROOT})
set(ENV{PKG_CONFIG_LIBDIR} "${CMAKE_SYSROOT}/usr/lib/pkgconfig:${CMAKE_SYSROOT}/usr/share/pkgconfig")
set(ENV{PKG_CONFIG_PATH} "")
find_package(PkgConfig REQUIRED)
pkg_check_modules(ZLIB REQUIRED IMPORTED_TARGET zlib)
target_link_libraries(app PRIVATE PkgConfig::ZLIB)

还有个坑：.pc 文件里的 prefix=/usr 是相对路径风格，靠 PKG_CONFIG_SYSROOT_DIR 补前缀。但有些库的 .pc 写死了绝对路径 prefix=/home/build/xxx，加了 sysroot 前缀就变成 $SYSROOT/home/build/xxx，路径根本不存在。这类 .pc 只能手工改，或者干脆绕过 pkg-config，直接写 -I 和 -L。

十一、Windows 下的编译环境概览 #

换到 Windows，问题变成另一副样子：不是「目标平台没编译器」，而是「同一台机器上有好几套互不兼容的 C++ ABI，你选错一套就链不上」。

主流的几条路：

方案 编译器 C 运行库 C++ ABI 产物依赖 适合

同一个函数，两边编出来的符号名完全不同，链接器当然对不上。

十三、MinGW 与 MinGW-w64 #

MinGW 是 Minimalist GNU for Windows：把 GCC 工具集、make、gawk、grep 这些搬到 Windows 上，让 Windows 也能用 vim、gcc、python 干活。官方首页 http://www.mingw.org/。

但你现在要装的不是它，是 MinGW-w64：

项 MinGW（老） MinGW-w64
目标架构 只有 32 位 i686 i686 与 x86_64 都有
Win32 API 头 老 SDK，缺很多接口 完整的 Win32/Win64 API
64 位异常处理 无 支持 SEH
UCRT 无 支持
维护状态 基本停更 活跃

两个构建选项决定 ABI，装之前必须选对：

选项 取值 怎么选
线程模型 posix / win32 要用 std::thread、std::mutex、libwinpthread 就选 posix
异常处理（64 位） seh 64 位只有 seh 一个答案
异常处理（32 位） sjlj / dwarf / seh 优先 sjlj，兼容老系统；dwarf 性能略好但栈展开受限

运行时依赖三个 DLL，产物拷到别人机器上就必须一起带：

text
libgcc_s_seh-1.dll      # SEH 版本的 libgcc（32 位 sjlj 版叫 libgcc_s_sjlj-1.dll）
libstdc++-6.dll         # C++ 标准库
libwinpthread-1.dll     # posix 线程模型

不想带就静态链：

bash
gcc main.c -o app.exe -static-libgcc -static-libstdc++ \
    -Wl,-Bstatic,--whole-archive -lwinpthread -Wl,--no-whole-archive

mingw32-make 就是 make，并行加 -jN，N 是你的核数：

bash
mingw32-make -j8

十四、MSYS2 与开发环境搭建 #

现在装 MinGW-w64 的正路是 MSYS2：一个包管理器加一套 POSIX 环境，用 pacman 装工具链。

bash
# 首次：更新全部包，中途要重开终端
pacman -Syu

# 装 64 位工具链全家桶（gcc、g++、gdb、make、binutils）
pacman -S mingw-w64-x86_64-toolchain

# 按需补
pacman -S mingw-w64-x86_64-cmake mingw-w64-x86_64-ninja mingw-w64-x86_64-pkgconf

# 装完验证
gcc --version

MSYS2 里有四个并列环境，选错环境就装错工具链：

环境 前缀 运行时 用途
UCRT64 /ucrt64 UCRT 推荐，跟 MSVC 用同一套 C 运行库
MINGW64 /mingw64 msvcrt 要兼容 Windows 7 老系统时用
CLANG64 /clang64 UCRT 要用 Clang 时
MSYS /usr msys-2.0.dll 只放 shell 工具，不放编译器

MSYS 环境里的 gcc 编出来的是依赖 msys-2.0.dll 的程序，只能在 MSYS 里跑。要产出原生 exe，认准 UCRT64 或 MINGW64 的终端。

如果被要求维护一个老工程，用老 MinGW 加 MSYS 1.0 的流程是这样：

  1. 下载 mingw-get-setup.exe 并运行。默认装到 C:\MinGW，没特殊需求就用默认。
  2. 安装器会拉起「MinGW Installation Manager」，勾选要装的组件：mingw32-base、mingw32-gcc-g++（要编 C++ 就勾）、msys-base。
  3. 应用更改，等它按网速下载完。
  4. 开始菜单进 MinGW Shell，或者用 mingw-get 装 minTTY：mingw-get install msys-mintty。
  5. 桌面建个快捷方式指向 C:\MinGW\msys\1.0\msys.bat --mintty，比默认的 cmd 窗口好用。
  6. 顺手配 vim 和 /etc/profile，把常用别名挂上。

不管走哪条路，第一个程序都这么验：

bash
gcc main.c                 # 不指定 -o，Windows 上产物叫 a.exe
./a.exe

text
[xxx@xxx ~]# ./a.exe
Hello world

MSYS2 的坑在于 PATH 顺序。系统里同时装了 MSYS2、老 MinGW、Strawberry Perl、Anaconda 之后，gcc 到底命中哪个全看 PATH 先后：

bash
which -a gcc               # 列出所有 gcc，看顺序对不对
type -a gcc

把不要的路径从系统环境变量里删掉，比在终端里反复 export PATH 靠谱。

十五、Windows 下的库与链接 #

从 Linux 过来的人最先懵的是 .lib 文件：它有两种完全不同的身份。

文件 内容 谁生成 对应 Linux
静态库 .lib 一堆 .obj 打成的包 lib.exe /OUT:a.lib a.obj b.obj libfoo.a
导入库 .lib 只有符号桩，运行时指到 DLL 链接 DLL 时自动产，或 lib /def:foo.def libfoo.so 的链接符号
.dll 真正的可执行模块 link /DLL .so
.exp 导出表，配导入库用 link /DLL 一并产出 无
.pdb 调试符号 /Zi 时产出 .debug 段 / 独立 debug 文件

函数要能跨 DLL 使用，必须显式导出。GCC 的默认可见性在 Windows 上不生效：

c
/* 头文件里统一开关，导出和导入写一套代码 */
#ifdef BUILDING_MYLIB
#  define MYLIB_API __declspec(dllexport)
#else
#  define MYLIB_API __declspec(dllimport)
#endif

MYLIB_API int my_add(int a, int b);

或者不改源码，用 .def 文件列导出名：

text
LIBRARY mylib
EXPORTS
    my_add
    my_sub

DLL 的搜索顺序跟 Linux 的 RPATH 完全不同，LoadLibrary 和依赖加载按这个顺序找：

text
1. exe 所在目录
2. 系统目录 C:\Windows\System32
3. 16 位系统目录 C:\Windows\System
4. C:\Windows
5. 当前工作目录
6. PATH 里的目录

第 5 条是最坑的：改一下工作目录，程序加载的 DLL 就换了版本。正经做法是把 DLL 放在 exe 旁边，或者用 SetDllDirectory / manifest 显式指定。

跨工具链链接的可行性，一张表说清：

场景 能不能链 条件
MSVC 静态库 + MSVC 程序 能 /MD 与 /MT 必须一致
MSVC .dll + MinGW 程序（纯 C 接口） 能 生成导入库 lib /def:，接口只用基础类型
MSVC .dll + MinGW 程序（C++ 接口） 不能 ABI 不同，符号修饰和数据布局都对不上
MinGW .dll + MSVC 程序（纯 C 接口） 能 同上，别跨边界传 STL 对象
MinGW .dll + MSVC 程序（C++ 接口） 不能 例外同上
32 位库 + 64 位程序 不能 位数必须一致，报 LNK1112: module machine type conflict
