一、性能问题从哪来 #

先分类，再动手。程序慢，落到硬件上只有三种消耗：CPU 在跑指令、CPU 在等 I/O、CPU 在等锁或者被调度走。体积是第四种问题：代码大到装不进 cache，或者大到 Flash 读不完。

同一个「启动慢 3 秒」，背后的账完全不同。先看这张归属表，把现象映射到层面：

现象 真实瓶颈 归属层面 在哪一章
上电到首帧 3 秒，串口日志刷满屏 控制台打印 + 服务串行启动 启动链路 七
上电到首帧 3 秒，但 CPU 有大段空转 等设备就绪、等不存在的文件 I/O 等待 十二
跑起来比预期慢一倍 优化等级低、没开 LTO 编译期 二 ~ 五
固件塞不进 32MB 分区 调试符号、没裁剪的库、-O0 体积 六、十一
换成 -O3 反而更慢 代码膨胀打爆 I-cache 编译期 三

优化的杠杆只有四处，记住位置比记选项有用：

text
源代码
 ├─ 编译期：-O?  -march  -mtune  -flto  -ffunction-sections
 ├─ 链接期：--gc-sections  -Wl,--as-needed  自定义链接脚本
 ├─ 装载期：动态链接器符号解析、重定位、构造函数
 └─ 运行期：系统调用次数、内存分配、锁竞争、线程调度

一句老话值得贴在显示器上：最快的代码是不执行的代码，最少的数据是不加载的数据。后面所有手段，无非是让某些指令不存在、让某些字节不被读。

动手之前先立三条基线，缺一个你就是在凭感觉调：

bash
size ./app                      # 体积基线：text / data / bss
/usr/bin/time -v ./app          # 时间与峰值内存基线
strace -c ./app                 # 系统调用次数与耗时基线

这三条数字每次改动都重测一遍。没有基线，你只能感觉到「好像快了」，而 -O3 让程序变慢 8% 这种事，肉眼永远感觉不到。

还有三件事编译器帮不了你，别在编译选项里找答案：

  • 等 I/O：open 一个不存在的文件、read 一个慢设备、等硬件上电就绪。
  • 算法复杂度：O(n²) 的循环，-O3 也只能把它压常数倍。
  • 锁竞争与调度：线程数超过核数、临界区里做 I/O。

二、优化等级：编译器替你做什么 #

-O 后面的数字不是「好坏刻度」，是「允许编译器做多激进的变换」。先记住这张表：

等级 干什么 体积 什么时候用
-O0 不优化，语句与源码一一对应，变量全落栈 最大 单步调试、定位未定义行为
-O1 删死代码、合并常量、简单寄存器分配 中 编译太慢时的折中，调试还能看
-O2 在 O1 上加：小函数内联、循环优化、CSE、强度削弱、尾调用 中偏大 默认起点，绝大多数程序
-O3 在 O2 上打开向量化、循环展开、更激进的内联 最大 数值计算、热点在内层循环
-Os O2 关掉会增大体积的项（对齐、展开），打开 -fno-align-* 一类 小 固件、I-cache 紧张
-Oz GCC 12 起，比 -Os 压得更狠 最小 体积上不封顶地抠
-Og O1 级别的优化 + 保留调试体验 中大 开发期想断点又不要太慢
-Ofast -O3 加 -ffast-math，放弃 IEEE 浮点语义 最大 数值容错的计算，别用在业务里

-O2 到底做了什么，看一个函数就明白：

c
/* sum.c */
int sum(const int *a, int n) {
    int s = 0;
    for (int i = 0; i < n; i++)
        s += a[i];
    return s;
}

bash
gcc -O0 -S sum.c -o sum_O0.s
gcc -O2 -S sum.c -o sum_O2.s
gcc -O2 -c sum.c -o sum.o && objdump -d sum.o

-O0 的循环体每轮都从栈上重新读 i、s、a，一轮十几条指令；-O2 把三者全提到寄存器，循环体只剩一条 add 加一条 cmp/jne。这就是「优化」的本来面目：不是让 CPU 更快，是让指令更少。

优化等级改的不只是速度，还有可见行为。-fstrict-aliasing 从 -O2 起生效，用不同类型指针访问同一块内存的写法会被优化器判为「不会发生」，于是出现「-O0 能跑，-O2 崩」的经典现象。先怀疑别名，一条命令就能验证：

bash
gcc -O2 -fno-strict-aliasing -o app main.c

如果加上这行就正常，问题在你的代码，不在编译器。

再补一句：生产固件不要用 -O0。-O0 的 bug 不复现，-O2 的 bug 才是真 bug；反过来，-O0 下测出来的耗时也没有参考价值。

要用 perf 采样，给编译命令补两行，否则调用栈全是 [unknown]：

bash
gcc -O2 -g -fno-omit-frame-pointer -o app main.c

三、-O2 与 -O3 的取舍 #

先给结论：优化等级越高不一定越快。-O3 变慢是常态，尤其在 ARM 小核上，具体有四个原因。

一是代码膨胀。循环展开和内联让 .text 变大，而 L1 I-cache 只有 32KB（Cortex-A7、Cortex-A53 都是这个数）。热代码一旦超过这个容量，每次取指都往 L2 走，延迟从 1~2 周期变成 10 周期以上。

二是向量化带检查。-O3 生成 SIMD 循环时，前面会插一段别名与对齐检查，数据量小时这段检查比循环本身还贵。

三是内联过度。热点函数被复制到十几个调用点，指令缓存里存着十份同样的代码，寄存器也被挤爆。

四是构建成本。-O3 加 -flto 的编译时间能翻倍，迭代速度是隐性成本。

项目 -O2 -O3
内联阈值 保守 更激进
自动向量化 基本关闭 打开
循环展开 少 多
.text 体积 基准 +10% ~ +50%
适合 通用业务、启动时间敏感、体积中等 内层循环吃满 CPU 的算子

别猜，跑一版对照：

bash
cat > bench.sh <<'EOF'
#!/bin/sh
for opt in O0 O1 O2 O3 Os; do
    gcc -$opt -o app_$opt main.c
    printf '%-4s text=%-8s ' "-$opt" "$(size app_$opt | awk 'NR==2{print $1}')"
    /usr/bin/time -f 'wall=%es maxrss=%MKB' ./app_$opt > /dev/null
done
EOF
chmod +x bench.sh && ./bench.sh

典型输出长这样，注意 -O3 那行：

text
-O0  text=4212     wall=1.83s maxrss=3120KB
-O1  text=2861     wall=0.94s maxrss=2896KB
-O2  text=3120     wall=0.61s maxrss=2872KB
-O3  text=4408     wall=0.65s maxrss=2904KB
-Os  text=2740     wall=0.72s maxrss=2880KB

-O3 的 .text 比 -O2 大了 41%，wall 时间反而长了。想确认是 cache 的锅，用 perf stat 看两个数：

bash
perf stat -e instructions,cycles,L1-icache-load-misses ./app_O2
perf stat -e instructions,cycles,L1-icache-load-misses ./app_O3

如果 -O3 的指令数没降、L1-icache-load-misses 翻倍，这就是膨胀的代价，切回 -O2。

选法定下来三条：

  • 默认 -O2，全工程都吃这个等级。
  • 单个热点函数要 -O3，能拆文件就拆文件；拆不动再用函数属性，但要清楚它挡跨函数优化：
c
__attribute__((optimize("O3")))
static float dot(const float *a, const float *b, int n) {
    float s = 0.0f;
    for (int i = 0; i < n; i++) s += a[i] * b[i];
    return s;
}
  • 固件体积敏感、启动时间敏感，先试 -Os。启动阶段读的字节数下降，Flash 上省下来的时间比循环里多跑几条指令值钱。

四、内联与 LTO #

内联是 O2/O3 里收益最大、也最容易失控的变换。四个旋钮，先分清哪个是建议、哪个是命令：

写法 效果
inline / static inline 只是建议，编译器可以拒绝
__attribute__((always_inline)) 强制内联，编译不过就报错
-fno-inline 全局关掉内联，用于对比测试
--param max-inline-insns-single=N 调内联阈值

内联的边界在翻译单元（.c 文件）里。a.c 的函数想内联进 b.c，编译器看不到 a.c 的代码，只能留一个 call。这就是 LTO（Link Time Optimization）要解决的问题：编译期不生成最终机器码，只在 .o 里留 GIMPLE 中间表示，链接期把所有单元合起来整体优化，再落地成机器码。

bash
# 编译期与链接期都要给 -flto，缺一边就退化
gcc -O2 -flto -c a.c -o a.o
gcc -O2 -flto -c b.c -o b.o
gcc -O2 -flto a.o b.o -o app

# 并行 LTO，大工程必开
gcc -O2 -flto=auto a.o b.o -o app

静态库要换归档工具，否则普通 ar 会丢掉 LTO 元数据：

bash
gcc -O2 -flto -c util.c -o util.o
gcc-ar rcs libutil.a util.o

LTO 与 --gc-sections 是一对：-ffunction-sections 在编译期把每个函数切到独立 section，-Wl,--gc-sections 在链接期按调用关系删掉没人引用的 section。开了 LTO，这个删除是跨文件的，比不开干净得多。

bash
gcc -O2 -flto -ffunction-sections -fdata-sections -Wl,--gc-sections -o app a.c b.c

体积差多少，自己看：

bash
size app_nolto app_lto

LTO 的代价要认：

  • 构建时间显著变长，全量重链接一次几分钟很常见。
  • strip 之后符号更少，coredump 回溯更难。
  • 老 binutils 遇到 LTO 对象会说 plugin needed to handle lto object，升级工具链即可。
  • 想让 .o 既能被 LTO 链接也能被普通链接器直接用，加 -ffat-lto-objects（体积翻倍）。

五、针对具体 CPU 优化：-march 与 -mtune #

这两个选项最常被混用，区别一句话：-march 决定「能用哪些指令」，-mtune 只决定「指令怎么排」。

选项 影响指令集 影响调度 用途
-march=x86-64-v3 是 是 允许 AVX2、BMI2，二进制只能在支持的机器上跑
-mtune=cortex-a7 否 是 只按目标核的流水线调顺序，二进制仍能跑老核
-mcpu=cortex-a53（ARM） 是 是 ARM 上把 march 与 tune 合成一个
-march=native 是 是 本机编译本机跑，CI 里禁用

先看本机到底会生成什么：

bash
gcc -march=native -Q --help=target | grep -E '^\s+-m(arch|tune)='
gcc -march=native -E -v - </dev/null 2>&1 | grep cc1

给具体目标：

bash
gcc -march=x86-64-v2 -O2 -o app main.c
gcc -mtune=cortex-a7 -O2 -o app main.c        # 只调调度，不改指令集
arm-linux-gnueabihf-gcc -march=armv7-a -mtune=cortex-a7 \
    -mfpu=neon-vfpv4 -mfloat-abi=hard -O2 -o app main.c

ARM 上还有一个独立维度：指令编码宽度。ARM 模式全是 32-bit 定长指令，执行效率高、代码密度低；Thumb-2 是 16-bit 与 32-bit 混合编码，体积能小 20%~30%。

bash
arm-linux-gnueabihf-gcc -marm   -O2 -o app_arm   main.c
arm-linux-gnueabihf-gcc -mthumb -march=armv7-a -O2 -o app_thumb main.c
size app_arm app_thumb

实测数据（同一套 BusyBox + 业务程序打出来的 rootfs）：

构建方式 rootfs 总大小 性能
ARM 模式 3.79 MB 基准
Thumb-2 模式 3.10 MB 差距小于 5%，部分负载更好

体积降 18%。性能差不到 5% 的原因在现代核的分支预测与 cache：Thumb-2 指令占的 L1 I-cache 空间更少，命中率反而高，缓存敏感的负载里能反超。存储紧张、指令 cache 小的板子，直接选 Thumb-2。

-march=native 有两个坑，记住就不会踩：

  • 在 CI、容器或者别人的机器上编译，产物发到老机器上跑，第一条新指令就是 SIGILL。
  • 交叉编译时 native 指的是宿主机（x86），不是目标板，写了等于没写。

六、减少体积：-Os 与 strip #

体积这件事在嵌入式里不是审美问题。Flash 读得越少，启动越快；代码越紧凑，I-cache 命中越高。先看体积都花在哪：

体积来源 占比（典型固件） 手段
调试符号与符号表 40% ~ 70% strip、--strip-debug
未被调用的函数与数据 5% ~ 30% -ffunction-sections + --gc-sections
未被引用的库 5% ~ 20% -Wl,--as-needed、静态库分文件
对齐填充与循环展开 3% ~ 15% -Os、-fno-align-functions
C 库本体 差异巨大 换 musl / uClibc-ng

-Os 的规则很直白：在 -O2 的基础上，凡是会让代码变大的优化一律关掉。循环不展开、函数不对齐到 32 字节、不做激进内联。

bash
gcc -Os -o app main.c
gcc -Os -fno-align-functions -fno-align-jumps -fno-align-loops -o app main.c
gcc -Oz -o app main.c            # GCC 12 起，比 -Os 更狠

死代码清理要用一对选项，编译期切段、链接期回收，缺一个都不生效：

bash
# 编译期：每个函数、每个全局变量切到独立 section（.text.func_name）
arm-linux-gnueabihf-g++ -Os -ffunction-sections -fdata-sections -c main.cpp -o main.o
# 链接期：按调用关系扫描，没人引用的 section 整段删掉
arm-linux-gnueabihf-g++ -Wl,--gc-sections main.o -o app

默认情况下链接器把整个 .o 的 .text 当一块合并，一个没调用过的函数照样进最终二进制。切段之后，链接器才有粒度可删。链接时想看删了什么，加 -Wl,--print-gc-sections。

剥离符号是投产前的最后一步，也是性价比最高的一步：

bash
strip --strip-unneeded ./app          # 保留动态符号，删本地符号与调试信息
strip --strip-debug ./app             # 只删调试信息
gcc -s -o app main.c                  # 链接期直接不给符号表

符号删了，线上 coredump 就没法回溯。正解是把调试信息单独留一份：

bash
objcopy --only-keep-debug app app.debug
strip --strip-debug app
objcopy --add-gnu-debuglink=app.debug app

app.debug 收进制品库，跟版本号一起存。线上崩了拿它配 addr2line 或 gdb 还原行号。

体积还有一个来源是链接顺序。从 Flash 顺序读代码时，如果启动阶段高频调用的函数在物理上散得极开，MTD 驱动就得反复随机寻址，大块预读白做，I/O 延迟全花在跳来跳去上。做法是采集启动期的调用序列，再按序列排段：

  1. 编译时打开 -finstrument-functions（或者干脆用 -ffunction-sections 拿到每个函数的独立段）。
  2. 跑一次应用，抓启动阶段触发的函数地址与调用流。
  3. 生成链接脚本，把这段函数按调用时序连续摆放，再交给 -Wl,-T 使用。

收益取决于函数分布有多散，Flash 越慢、启动路径越长，收益越大。

C 库的选择对体积影响最大，一张表看清：

特性 Glibc uClibc-ng musl
设计目标 功能最全、GNU 兼容 面向嵌入式、高度可配置 现代、规范、轻
静态 hello 体积 约 700KB+ 约 60KB 约 7KB
动态库体积 约 2.0MB 约 300KB 约 600KB
内存开销 高（复杂分配器、线程缓存多） 很低 很低
兼容性 POSIX + GNU 扩展全支持 部分 GNU 扩展未实现，要改代码 POSIX 全支持，GNU 扩展较全

同一份 hello.c，GCC 6.3 + ARM，静态链接实测：

库 二进制大小
Glibc 492,792 字节（约 492KB）
uClibc-ng 67,204 字节（约 67KB）
musl 7,300 字节（约 7KB）

静态 BusyBox 1.26.2 的对照：

库 二进制大小
Glibc 755,088 字节
uClibc-ng 210,620 字节
musl 183,348 字节

Flash 只有 8MB / 16MB 的板子，工具链直接选 musl 或 uClibc-ng，rootfs 能省下 20%~30% 空间。省的不只是空间：引导时从 SPI Flash 读进 RAM 的字节数同比下降，这段 I/O 时间是等比例减少的。

七、启动时间的构成 #

启动开销分四段，每段的责任人不同，砍法也不同：

阶段 干什么 典型占比 主要负责人
Bootloader 硬件初始化，把内核映像搬进 RAM 5% ~ 15% U-Boot / SPL
Kernel 驱动 probe、挂载 rootfs、拉起 init 20% ~ 40% 内核配置与驱动
Init 跑第一个用户空间进程，解析启动脚本 30% ~ 50% systemd / 自研 init
App 启动业务程序，完成首帧或首个响应 20% ~ 40% 你自己的代码

某条车载倒车影像链路的拆分长这样（冷启动 2.4 秒）：U-Boot 0.35s、Kernel 0.9s、Init 0.8s、App 0.35s。占比最大的往往不是你以为的那个。

测准了才有优化。两种拿到高精度时间的方法，都记下来。

方案 A，硬件电平法，工业界最准。上电瞬间让一个 GPIO 拉高，应用画出第一帧或者网络连上之后再拉低，示波器量两个跳变之间的宽度。用户空间拨 GPIO 的代码如下（sysfs 接口，老内核可用；新内核换 libgpiod）：

c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <string.h>

void toggle_gpio(int pin, int value) {
    char path[64];

    /* 导出 GPIO，已经导出过会返回 EBUSY，忽略即可 */
    int fd = open("/sys/class/gpio/export", O_WRONLY);
    if (fd >= 0) {
        char pin_str[10];
        snprintf(pin_str, sizeof(pin_str), "%d", pin);
        write(fd, pin_str, strlen(pin_str));
        close(fd);
    }

    /* 方向设为输出 */
    snprintf(path, sizeof(path), "/sys/class/gpio/gpio%d/direction", pin);
    fd = open(path, O_WRONLY);
    if (fd >= 0) {
        write(fd, "out", 3);
        close(fd);
    }

    /* 写电平：0 或 1 */
    snprintf(path, sizeof(path), "/sys/class/gpio/gpio%d/value", pin);
    fd = open(path, O_WRONLY);
    if (fd >= 0) {
        char val_str[2];
        snprintf(val_str, sizeof(val_str), "%d", value);
        write(fd, val_str, 1);
        close(fd);
    }
}

方案 B，串口时间戳法，没有示波器就用它。grabserial 给串口收到的每一行日志打相对时间戳：

bash
python grabserial -p /dev/ttyUSB0 -b 115200 -e "Starting app finished" -t

输出两列时间，第一列是从收到第一包数据算起的绝对相对时间，第二列是行间增量：

text
[0.000 0.000] U-Boot 2020.04
[0.120 0.120] Loading Kernel...
[1.240 1.120] Starting Kernel...
[1.850 0.610] Mounting Rootfs...
[2.350 0.500] Starting app finished

一眼就能看出 1.12 秒花在「Loading Kernel」到「Starting Kernel」之间。注意串口本身有带宽上限，115200 波特率下每秒只能吐约 11.5KB 字符，日志太多时测出来的时间是「打印时间」而不是「启动时间」，这类时间要在 quiet 之后再测一遍对比。

内核侧三件事，按收益排序。

一是关掉控制台打印。生产环境在内核命令行 bootargs 里加 quiet，立刻省 200ms ~ 800ms。原理在 UART：波特率固定，字符一个个排队发，内核 printk 把发送缓冲区写满之后，线程只能阻塞等串口吐完。少打印不只是省 CPU，是把整条阻塞链掐掉。

bash
# 命令行里加，或者写进 U-Boot 的 bootargs
quiet loglevel=3

quiet 不是把日志全扔掉，dmesg 里还在，需要时 dmesg | tail 照看。

二是裁掉不用的驱动。网卡、显卡、声卡、用不到的文件系统（比如只需要只读 SQUASHFS，就把 EXT4 关掉），每个不用的驱动都带着 probe 时间、内存占用和 initcall 排队位置。

三是选对内核压缩算法：

算法 解压速度 压缩率 适合
LZO / LZ4 极快 偏低 CPU 慢、I/O 快的设备
GZIP 中 中 折中
XZ 慢 最高 存储小、CPU 强的设备

压缩率换的是「读 Flash 的字节数」，解压速度换的是「CPU 周期」。存储快、CPU 弱就选 LZ4；存储慢、CPU 强就选 XZ。这条取舍在十二节用 perf 定量。

驱动 probe 串行是内核阶段最大的隐性开销。bootargs 里加 initcall_debug，每个 initcall 的进入与退出都会打时间戳：

bash
# 1. 采集
initcall_debug

# 2. 把 dmesg 转成甘特图
./scripts/bootgraph.pl /var/log/dmesg > bootgraph.svg

图上那条最长的横条就是罪魁。耗时长的非关键驱动改成异步 probe（驱动里返回 -EPROBE_DEFER 或者走 async probe 路径），别让一个等硬件的驱动把后面所有驱动卡住。

八、动态链接的启动开销 #

动态链接的程序，main 之前还要跑一段你不写的代码：内核把 ld-linux.so 映射进来，ld.so 再去找 DT_NEEDED 里列的每个库、映射、解析符号、做重定位、调用各库的构造函数。这些都在你的第一行代码之前完成。

先看它到底要加载什么：

bash
readelf -d ./app | grep NEEDED
ldd ./app

动态链接器自己会报账：

bash
LD_DEBUG=statistics ./app
LD_DEBUG=libs ./app 2>&1 | head -40

statistics 的输出里重点看三项：total startup time in dynamic loader、number of relocations、time needed for relocation。

开销分四块：

环节 干什么 量级
open + mmap 每个库 找文件、建映射 每个库 0.1ms ~ 1ms（冷缓存更贵）
符号解析 在动态符号表里查名字 与重定位条数成正比
重定位处理 填 GOT、改地址 数千条重定位 = 数毫秒
构造函数 .init_array 里每个函数跑一遍 C++ 全局对象多时很明显

C++ 项目里这块尤其肉疼：libstdc++ 一加载，iostream 的静态初始化就跟着跑，几百微秒起步，而你一个 printf 都没用。

压这块的手段按顺序：

  • 砍库的数量。-Wl,--as-needed 让链接器只保留真正被用到的 DT_NEEDED，能少一个是一个。
  • 隐藏符号。-fvisibility=hidden 减少动态符号表条数，解析更快。
  • 关 PIE。-no-pie 省掉装载期的基址重定位，代价是失去 ASLR。
  • 少用 C++ 全局对象，尤其 iostream。
  • 冷启动要按冷缓存量。热缓存的启动时间没有参考价值：
bash
sync; echo 3 > /proc/sys/vm/drop_caches    # root，清 page cache 后再测

九、静态链接与启动速度 #

把库塞进可执行文件，ld.so 就没事可做：没有库文件要 open，没有库符号要解析，没有跨库重定位。启动链上直接少一层。

bash
gcc -static -O2 -o app_static main.c
file ./app_static          # 应显示 statically linked
ldd ./app_static           # 应显示 not a dynamic executable

同一块 Cortex-A7 板子上量的量级对比（程序逻辑一样，冷缓存）：

构建方式 启动到 main 结束 二进制体积
动态链接 glibc 约 12ms 装载开销 16KB
静态链接 glibc 约 2ms 780KB
静态链接 musl 约 1ms 40KB

动态链接的开销在 PC 上可以忽略，在启动时间以毫秒计的嵌入式板子上就不能忽略。devicetree 之外，initramfs 里的核心业务程序几乎都该静态链接。

代价要算清：

  • 体积涨。glibc 静态一个 hello 就 700KB+，用 musl 才 7KB。
  • glibc 静态链接有坑：getaddrinfo、dlopen、NSS 在静态模式下会告警或者行为异常，要用 --enable-static-nss 的定制 glibc，或者干脆换 musl。
  • 库更新要重新链接整个程序，不能只换 .so。

还有一个折中选项：-static-pie，静态链接但保留 PIE 能力（体积更大，装载时要做自重定位）；以及 -no-pie，非 PIE 的普通可执行文件，装载最快，但放弃地址随机化。启动时间优先的固件，-static -no-pie 是常见组合。

十、预链接与延迟加载 #

预链接（prelink）是老办法：在构建时把共享库的重定位提前算好，写进 ELF 的 PT_GNU_PRELINKED 段，装载时 ld.so 直接跳过重定位计算。

bash
# 预链接所有库与可执行文件，-R 随机化基址，-m 保留虚拟地址
prelink -amR
prelink -u ./app        # 撤销

为什么现在少用它：预链接会改共享库文件本身，一次库更新就让所有预链接结果失效；它和 ASLR 抢地址空间，安全上也不好；现代发行版默认 PIE，prelink 基本退出历史。老系统上还能用，新系统别折腾。

延迟加载是另一半故事。ELF 默认就是延迟绑定：函数第一次被调用时才解析符号（-Wl,-z,lazy，默认值）。这对启动有利——没调用的函数不花解析时间。反过来，-Wl,-z,now 强制启动时全解析，启动变慢，但运行时没有第一次调用的抖动。策略是一句话：启动时间优先用 lazy，实时性优先（不能容忍首次调用抖动）用 now。

bash
readelf -d ./app | grep -E 'BIND_NOW|FLAGS'
LD_BIND_NOW=1 ./app        # 强制全解析，用来量化延迟绑定的收益

延迟加载的另一层含义在应用自己手里：不是所有初始化都要在启动路径上做完。把非首帧必需的活挪到后台线程：

c
#include <pthread.h>

static void *deferred_init(void *arg) {
    (void)arg;
    init_telemetry();     /* 埋点上报 */
    init_ota();           /* 升级检查 */
    scan_media_files();   /* 媒体库扫描 */
    return NULL;
}

int main(void) {
    pthread_t t;
    init_display();                     /* 首帧必需，同步做 */
    pthread_create(&t, NULL, deferred_init, NULL);
    pthread_detach(t);
    render_first_frame();
    for (;;) pause();
}

前提取清楚：推迟的必须是不影响首帧、不影响用户第一眼判断的活。网络保活、媒体扫描、日志上传都可以推迟；显示参数、输入设备、音视频管线不能推迟。推迟错了，首帧画面就是错的。

还有一招是减少读取的字节数。posix_fadvise(fd, 0, 0, POSIX_FADV_WILLNEED) 让内核对马上要读的文件提前预读，readahead 命令同理。启动脚本里把核心资源文件提前刷进 page cache，比逐次 read 等待磁盘快得多。

十一、库的裁剪 #

前面的手段都在砍自己的代码，这一节砍依赖。链接时少带一个库，装载期就少一次 open 和一轮重定位。

手段 作用 命令
--as-needed 只保留被真正引用的 DT_NEEDED gcc -Wl,--as-needed -o app main.o -lfoo -lbar
隐藏符号 减少动态符号表条数 gcc -fvisibility=hidden
version script 精确控制导出符号集 gcc -Wl,--version-script=exports.map
静态库分文件 一个符号只拉它所在的 .o 每函数一文件编译再 ar rcs
去 C++ 冗余 关异常、关 RTTI、静态链 libstdc++ -fno-exceptions -fno-rtti -static-libstdc++
换库 musl / uClibc-ng 替 glibc 换工具链重编
--gc-sections 删未被引用的函数与数据 见第六节

先看当前带了什么，再决定砍谁：

bash
readelf -d ./app | grep NEEDED
nm -D --defined-only ./app | wc -l       # 导出的动态符号条数
size ./app

--as-needed 要放在库前面，位置写错等于没写：

bash
gcc -O2 -Wl,--as-needed -o app main.o -lfoo -lbar

静态库的删除粒度是目标文件，不是一个函数。一个 util.c 里塞了二十个函数、只用到其中一个，链接器照样把整个 .o 拉进去，连带它的静态数据与依赖。拆文件是零成本的优化：

bash
gcc -Os -ffunction-sections -fdata-sections -c util_a.c -o util_a.o
gcc -Os -ffunction-sections -fdata-sections -c util_b.c -o util_b.o
ar rcs libutil.a util_a.o util_b.o

C++ 项目的体积大头往往是 libstdc++ 和异常表。业务不用异常就不用付这个税：

bash
g++ -Os -fno-exceptions -fno-rtti -static-libstdc++ -o app main.cpp

注意 -fno-exceptions 必须整个工程一致，第三方库编着异常、你这边关掉，链接期就会报 undefined reference to __cxa_throw。

C 库本身的可裁剪项在工具链里，不在命令行：uClibc-ng 有 menuconfig 式的配置界面，把 locale、NSS、宽字符、libm 的边角函数关掉，体积能再降一截。musl 没有配置项，但默认就小。

十二、测量：怎么知道优化有没有用 #

这一节是全文的地基。没测过的优化等于没做，测错口径的优化比没做更糟。先把工具对号入座：

工具 看什么 命令
time 端到端 wall / user / sys time ./app
/usr/bin/time -v 峰值 RSS、page fault、上下文切换 /usr/bin/time -v ./app
perf stat IPC、cache miss、分支预测失败 perf stat -e cycles,instructions ./app
perf record / perf report 函数级 CPU 热点与调用栈 perf record -g ./app
strace -c 系统调用次数与耗时排名 strace -c ./app
strace -tt -T 单次调用耗时、调用之间的空档 strace -tt -T -o log ./app
ltrace 库函数调用 ltrace -c ./app
oprofile 全系统热点，含内核与中断 opreport -l ./app
valgrind --tool=callgrind 指令级精确计数（慢 20~50 倍） valgrind --tool=callgrind ./app
size 段体积 size ./app
grabserial 启动阶段逐行时间戳 grabserial -e "done"
systemd-analyze 服务启动树与串行链 systemd-analyze blame

口径先统一，否则数据不可比：

bash
# 锁频，别让调频器把测量搅乱
echo performance | tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor
# 关掉调试串口打印，或者至少把日志等级压下来
# 每个版本跑 10 次，取中位数，不看最好那次
for i in $(seq 1 10); do
    /usr/bin/time -f "%e" ./app 2>&1 >/dev/null
done | sort -n | sed -n '5,6p'

perf stat 看整体效率，两个数最有用：IPC（instructions / cycles）和 cache miss。IPC 掉下去、指令数没涨，说明在等内存。

bash
perf stat -e cycles,instructions,cache-misses,cache-references,branch-misses ./app
perf stat -r 10 -e task-clock ./app

perf record 找函数级热点，-F 99 是采样频率，-g 抓调用栈：

bash
# 盯住一个已经在跑的进程，采 10 秒
perf record -F 99 -g -p <PID> -- sleep 10
perf report

perf report 里层层展开调用树，能落到具体函数，比如某个 JSON 解析器、某个死循环。要火焰图就 perf script | stackcollapse-perf.pl | flamegraph.pl > out.svg。跑在板子上时把 perf.data 拷回 PC，用交叉版本或者同版本 perf 打开，符号表记得留着。

strace 找系统调用层面的罪。先看总账：

bash
strace -c ./app

text
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- -----------
 56.40    0.012300          42       292           read
 20.10    0.004383         101        43        20 open
 12.30    0.002685           5       512           mmap2

read 和 open 吃掉七成时间，问题就不在 CPU 上。再看细节，-tt 带微秒时间戳，-T 给每次调用标耗时，-f 跟子进程，-o 写文件：

bash
strace -tt -T -v -f -o strace_boot.log ./app

日志里捞超过 10ms 的调用：

bash
awk -F'<' '{t=$NF; gsub(/>/,"",t); if (t+0 > 0.01) print}' strace_boot.log | head -20

text
10:12:05.123456 open("/etc/config.bin", O_RDONLY) = -1 ENOENT (No such file or directory) <0.012450>

打开一个不存在的配置文件花了 12ms，这种「等不存在的设备文件」是最典型的启动延时来源，改一行路径就没了。

还有一个经典判断：CPU 忙还是在等硬件。系统调用耗时短、但两次调用之间有大跨度空档，CPU 在跑计算或者卡在锁上；系统调用耗时长（read、select、ioctl 都是几毫秒以上），在等驱动或外设。

oprofile 是另一套全系统采样，能看内核驱动与中断处理，内核要开 CONFIG_OPROFILE=y：

bash
opcontrol --vmlinux=/path/to/vmlinux
opcontrol --start
./my_performance_test
opcontrol --stop

# 生成函数级热点报告
opreport -l ./my_performance_test

perf 需要内核开 CONFIG_PERF_EVENTS=y。两个工具二选一，perf 更新、更通用；老内核只有 oprofile 时就用它。

症状到工具，最后收一张对照：

症状 先开哪个工具 看什么
整机启动慢，不知道卡在哪段 grabserial / 示波器 阶段边界时间戳
服务启动互相等待 systemd-analyze critical-chain 串行依赖链
驱动初始化慢 initcall_debug + bootgraph.pl 最长的那条 initcall
程序 CPU 高 perf record / perf top 热点函数
程序 CPU 不高但慢 strace -c 系统调用耗时
内存涨、page fault 多 /usr/bin/time -v maxrss、major fault
首帧前卡住 strace -tt -T 调用之间的空档

十三、常见优化手法与陷阱 #

先看账本。下面这些动作在嵌入式 Linux 上被反复验证过，收益量级写在第三列，实际数字取决于你的板子：

维度 措施 预期缩减
Bootloader bootdelay 设 0，裁掉 USB / Ethernet / PCIe 300ms ~ 1s
Bootloader 开 Falcon Mode，SPL 直载内核 500ms ~ 1.5s
Kernel bootargs 加 quiet 200ms ~ 800ms
Kernel 裁无用驱动 + 换 LZ4 / LZO 压缩 300ms ~ 1.2s
Rootfs 换 SquashFS 只读压缩文件系统 100ms ~ 500ms
Init 极简 /init 脚本替掉 systemd / SysV 500ms ~ 3s
Toolchain musl / uClibc-ng 替 glibc 100ms ~ 300ms
App --gc-sections + strip 50ms ~ 200ms

U-Boot 侧三刀，按顺序砍：

bash
# 1. 去掉上电倒计时，别再等串口敲键
setenv bootdelay 0
saveenv

# 2. 配置里关掉启动不用的总线与外设：CONFIG_USB、CONFIG_PCI、CONFIG_DM_ETH
# 3. Falcon Mode：SPL 直接引导内核，跳过整个 U-Boot proper

Falcon Mode 省的是 U-Boot proper 的体积与初始化时间，500ms ~ 1.5s。代价要说明白：救援 shell 没了，量产后刷机得留一条后路（按键进 DFU、或者保留一个可跳过的环境变量分支）。

存储介质是物理下限，选型阶段就该定：

介质 读速度 特点 用在哪
SPI NOR Flash 几十 MB/s 随机寻址好，容量小 极小系统、boot 分区
eMMC 100 ~ 250MB/s 支持并行多通道 中高端平台主力
SD 卡 看卡等级（Class 10 / UHS-I） 质量参差，不适合量产 调试与原型

根文件系统上 SquashFS，只读、压缩比高，rootfs 能压到原体积的 30% 左右。解压要花 CPU，但启动时读的字节数大幅下降，小文件密集加载的场景整体更快。

初始化系统是收益最大的一刀。先定位再砍，systemd 自带三把尺子：

bash
systemd-analyze                    # 三个总数：firmware / loader / userspace
systemd-analyze blame              # 每个服务耗时排名
systemd-analyze critical-chain     # 串行依赖链，找真正的阻塞点
systemd-analyze plot > boot_analysis.svg   # 整张启动甘特图，浏览器直接看

blame 排第一的往往是个无关服务：网络配置等待、时钟同步、ModemManager 探测。停掉它们比优化业务代码快得多。倒车影像这类必须在 2 秒内出画面的业务，直接跳过绝大多数系统初始化：

ini
# /etc/systemd/system/reverse-cam.service
[Unit]
Description=Reverse Camera App
DefaultDependencies=no
Conflicts=shutdown.target
Before=sysinit.target shutdown.target

[Service]
Type=simple
ExecStart=/usr/bin/reverse-cam-app
OOMScoreAdjust=-1000

[Install]
WantedBy=sysinit.target

三个参数是关键：DefaultDependencies=no 切断 systemd 自动加的那一堆默认依赖（网络在线、文件系统挂完、日志服务就绪），服务在 systemd 刚起来就能跑；Before=sysinit.target 让它排在系统初始化核心目标之前；WantedBy=sysinit.target 把它挂进早期阶段。OOMScoreAdjust=-1000 让它在内存紧张时不被 OOM killer 挑走。

再狠一点，用 initramfs 替掉磁盘 rootfs：

sh
#!/bin/sh
# /init，initramfs 里的第一个用户空间程序
mount -t proc proc /proc
mount -t sysfs sysfs /sys

# 核心业务先跑，后台运行，别阻塞后续引导
/bin/reverse-cam-app &

# 再拉起其他挂载和守护进程
exec /bin/sh

initramfs 是压进内核镜像的临时根文件系统，内核解压完直接在内存里跑，不用等存储驱动 probe 再挂分区。体积控制在 2MB ~ 5MB：/init、静态编译的 BusyBox、必需的内核模块、业务程序本身。业务程序一定静态链接，省掉装载 ld-linux.so 和解析符号的时间。

陷阱都在代价那一侧：

手法 代价 / 风险
-O3 全工程铺开 代码膨胀打爆 I-cache，反而更慢
-flto 构建时间翻倍，strip 后回溯更难
-march=native 换机器跑就是 SIGILL
-Ofast 改浮点语义，数值结果与 -O2 不一致
strip 线上 coredump 无法定位，必须配 debuglink
quiet 故障时看不到内核日志，靠 dmesg 兜底
Falcon Mode 没有 U-Boot 救援 shell
后台推迟初始化 推迟错了，首帧数据是错的
-no-pie 失去 ASLR
initramfs 体积塞进内核镜像，压缩算法与启动内存都要重算

还有几个纯操作层面的坑，踩一次记一辈子：

  • 编译期给了 -ffunction-sections、链接期忘了 -Wl,--gc-sections，白干。
  • 编译期给了 -flto、链接期忘了，链接器报 plugin needed to handle lto object。
  • 静态库用普通 ar 归档 LTO 对象，元数据丢了，LTO 静默失效。
  • 用热缓存测启动，测出来的是 page cache 的速度，不是 Flash 的速度。
  • 只跑一次就下结论，一次测量里混着 CPU 调频、后台 cron、SD 卡抖动。
  • 串口日志开最详细级别测启动，测的是 UART 带宽。
