一、为什么需要面向对象 #

先看一段没有对象的代码。学生成绩管理，C 写法：

c
typedef struct {
    char  name[32];
    int   score;
} Student;

void print_student(const char *name, int score);
void sort_students(Student *arr, int n);
void save_students(const Student *arr, int n, const char *path);

功能少的时候这种写法很舒服。加一个需求：学生要带班级、要带学号、要能从文件读回来。于是每个函数的参数表都变长，或者全改成传 Student* 加一个 n。再到后面，谁都能直接改 arr[i].score，把一个负数写进去，没有任何地方拦得住。

崩坏是渐进的：

  1. 数据和操作分家。函数知道结构体长什么样，结构体不知道谁能动它。
  2. 没有不变式。字段公开，任何一行代码都能把状态改坏。
  3. 加一种新类型要改所有 switch。今天是学生，明天是老师，后天是助教，每个函数里都得加分支。
  4. 无法复用「一半的行为」。想复用排序逻辑，只能复制粘贴再改类型名。

面向对象就是把这四件事一起处理：把数据和对数据的操作放进同一个单元（封装），让新类型能复用老类型的行为（继承），让同一句调用在不同对象上落到不同实现（多态）。三个特性各管一段，缺一段都不完整。

三个特性对照：

特性 解决的问题 手段 代价
封装 状态被外部乱改、内部实现暴露 访问控制，只公开接口 多写一层转发函数
继承 行为复用、类型归类 is-a 派生，共享基类实现 强耦合，父类一动子类全抖
多态 同一调用不同实现，去掉 switch 虚函数 / 函数指针 / 模板 一次间接跳转，调试时看不清落点

也得说清反面：面向对象不是唯一答案。数据结构与算法这一层，纯 C 的过程式写法往往更直接——qsort 比一堆 Shape 子类干净。判断标准只有一条：这段代码是不是要长期被人改、被人扩。是一锤子买卖的脚本，套类只会多打字。

二、类与对象 #

三个词先钉住。

对象是一个自包含的实体，用一组可识别的特性和行为来标识。一只猫有名字、年龄、颜色，会叫，这就是一个对象。

类是具有相同属性和功能的对象的抽象集合。它定义对象的特性（属性）和可执行的操作（方法）。C++ 用 class 声明。

实例是真实存在的对象，实例化是创建对象的过程，new 或栈上直接定义都算。

命名习惯上，类名大写字母开头，多词用驼峰，如 Animal、DogHouse；成员字段小写开头或加下划线前缀，如 age、_age；对外公开的方法用 public 修饰。

构造方法 #

构造方法（构造函数）是初始化类的特殊方法：名字与类名相同，没有返回值，连 void 都不写。

规则只有两条：

  1. 所有类都有构造方法。没有显式定义时，编译器给一个默认构造；一旦自定义了，默认构造就不再自动生成。
  2. 成员初始化优先用初始化列表，别在函数体里赋值。const 成员和引用成员只能在初始化列表里初始化。
cpp
#include <string>

class Car {
public:
    Car() : color_("white"), speed_(0) {}          // 默认构造
    explicit Car(std::string color) : color_(std::move(color)), speed_(0) {}
    ~Car() {}                                       // 析构：对象销毁时自动调用

private:
    std::string color_;
    int         speed_;
};

Car c1; 走默认构造，Car c2("red"); 走带参构造。explicit 挡住 Car c = "red"; 这种隐式转换，单参数构造函数都该加。

方法重载 #

同一个类里可以有多个同名方法，只要参数类型或个数不同。返回值不同不算重载。

cpp
class Geometry {
public:
    double CalculateArea(int radius);                    // 圆
    double CalculateArea(double length, double width);   // 矩形
    double CalculateArea(double a, double b, double c);  // 三角形（海伦公式）
};

好处是不用给每个版本编新名字（areaCircle、areaRect、areaTri），调用方按参数形状选。编译器在编译期就把重载解析成具体函数地址，这叫静态绑定，和多态的运行时绑定是两回事。

属性 #

字段私有的叫字段，对外暴露访问的叫属性。属性的标准形态是一对访问器：get 返回字段的值，set 接收一个隐式参数写入字段。C# 有 get { return age; } 这种语法糖，C++ 里老老实实写两个函数：

cpp
class Cat {
public:
    int  age() const { return age_; }               // getter，const 表示不改对象
    void set_age(int v) { if (v >= 0) age_ = v; }   // setter 挡住脏数据
private:
    int age_ = 0;
};

cat.set_age(3) 比 cat.age = 3 多打几个字，换来的东西是：负年龄进不来，以后想把内部存储换成 unsigned char 也不影响调用方。

一个完整的类，把上面几样凑齐：

cpp
#include <iostream>
#include <string>

class Cat {
public:
    Cat() : name_("unknown"), age_(0) {}
    Cat(std::string name, int age) : name_(std::move(name)), age_(0) {
        set_age(age);
    }

    std::string name() const { return name_; }
    int         age() const { return age_; }

    void set_age(int v) {
        if (v < 0 || v > 40) return;
        age_ = v;
    }

    void speak() const { std::cout << name_ << ": 喵\n"; }

private:
    std::string name_;
    int         age_;
};

int main() {
    Cat a;
    Cat b("mimi", 3);
    a.set_age(-5);          // 被挡掉，仍是 0
    b.speak();
    std::cout << a.age() << " " << b.age() << "\n";
}

三、封装 #

封装的定义很短：每个对象把它操作所需的所有信息包在一起，执行操作时不依赖外部因素。落到代码上就一句话——状态私有，入口统一。

封装真正买到的是降低耦合：类的内部实现随便改，只要公开接口不变，调用方一行都不用动。

cpp
#include <stdexcept>

class Account {
public:
    explicit Account(double balance) : balance_(balance) {}

    void deposit(double amount) {
        if (amount <= 0) throw std::invalid_argument("amount must be positive");
        balance_ += amount;
    }

    bool withdraw(double amount) {
        if (amount <= 0 || amount > balance_) return false;
        balance_ -= amount;
        return true;
    }

    double balance() const { return balance_; }

private:
    double balance_;
};

balance_ 里永远不可能出现负数，这个性质叫不变式（invariant）。它只在所有修改都走 deposit/withdraw 时成立；字段一旦公开，不变式就是纸糊的。

再落到日常系统：手机应用里用户信息的管理，对外提供 get_profile()、update_email()，内部是存本地 SQLite 还是存内存缓存，调用方不用管，也管不着。数据安全性和完整性靠这层边界守着。

封装不是把所有字段无脑配上 getter/setter。全公开等于没封装，只是把 a.x 改写成 a.x()。判断标准：这个字段真有被外部读写的需要吗？有没有必须一起维护的约束？约束为零、读写随意，那它就是个数据载体，用 struct 更诚实。

四、继承 #

继承描述对象之间的 is-a 关系。若「B 是 A」这句话成立，B 就能继承 A。换个说法，继承是在被继承者的基础上做特殊化。

cpp
class Animal {
public:
    Animal(std::string name, int age) : name_(name), age_(age) {}
    virtual ~Animal() = default;

    virtual void sound() const { std::cout << "...\n"; }
    int age() const { return age_; }

protected:
    std::string name_;
    int         age_;
};

class Dog : public Animal {
public:
    using Animal::Animal;                 // 继承构造函数
    void sound() const override { std::cout << "汪\n"; }
    void bark() const { std::cout << "Woof!\n"; }   // 子类独有
};

class Cat : public Animal {
public:
    using Animal::Animal;
    void sound() const override { std::cout << "喵\n"; }
    void chase_mouse() const {}
};

子类拿到父类所有非 private 成员（protected 也能拿），自己再添新成员，还能重写父类方法。

继承买到的复用是真的：age()、name_ 写一遍，十个子类都能用。代价也是真的——父类一改，子类全抖。这在工程里有个名字叫脆弱基类（fragile base class）：你在基类里加一个虚函数，所有子类的虚函数表布局都变；你在基类里调一个虚函数，子类重写的行为会在你没预期的地方被触发。

C++ 还有两件继承特有的麻烦：

  • 菱形继承。A 派生出 B、C，D 同时继承 B、C，D 里就有两份 A 的数据。解决办法是 B : virtual public A、C : virtual public A 做虚继承，让 D 里只保留一份。虚继承的代价是对象布局变复杂，访问基类成员多一次间接，别乱用。
  • 继承方式的坑。class Dog : Animal 在 C++ 里是私有继承，Animal 的成员全变 private，外面拿不到 sound()。写 : public Animal，除非你真想要「用 A 实现 B」而不是「B 是 A」。

继承的代价清单：

代价 表现 缓解
强耦合 基类改签名，所有子类编译失败 基类接口定稳，少改
层次爆炸 形状 × 颜色 = 6 个类，再加一维就 12 个 改用组合
白盒复用 子类看得见基类的 protected 细节 组合 + 接口
布局锁定 加虚函数、加成员即 ABI 变更 预留虚析构，接口类不改

五、多态 #

多态的定义：不同类型的对象执行同一个操作，具体实现由各自代码决定。猫的 sound 出「喵」，狗的出「汪」，调用方写的是同一句 a->sound()。

多态分两类，别混：

类型 绑定时机 实现手段 例子
编译期多态 编译时确定 函数重载、模板、宏 CalculateArea(int) / CalculateArea(double,double)
运行期多态 运行时确定 虚函数表、函数指针 Shape* 调 area()

子类能当父类用，但有边界 #

Animal* p = new Cat("mimi", 3); 合法，子类对象可以被当成父类实例使用。但通过 p 只能访问 Animal 声明过的成员，Cat 独有的 chase_mouse() 拿不到——因为编译器只认静态类型。

要拿回来得显式向下转型，用 dynamic_cast 并且检查结果：

cpp
Animal* p = new Cat("mimi", 3);
if (auto* c = dynamic_cast<Cat*>(p)) {
    c->chase_mouse();          // 类型对上了才走这里
}
delete p;

dynamic_cast 需要 RTTI，有运行时代价，乱转说明设计有问题。

虚函数与虚函数表 #

要让子类完全接管父类的成员，父类里的这个成员必须声明为 virtual。虚函数可以有函数体，也可以纯虚（= 0）。

cpp
#include <iostream>

class Shape {
public:
    virtual double area() const = 0;
    virtual const char* name() const { return "Shape"; }
    virtual ~Shape() = default;                 // 基类析构必须是虚的
};

class Circle : public Shape {
public:
    explicit Circle(double r) : r_(r) {}
    double area() const override { return 3.14159265358979 * r_ * r_; }
    const char* name() const override { return "Circle"; }
private:
    double r_;
};

class Rect : public Shape {
public:
    Rect(double w, double h) : w_(w), h_(h) {}
    double area() const override { return w_ * h_; }
    const char* name() const override { return "Rect"; }
private:
    double w_, h_;
};

void print_area(const Shape& s) { std::cout << s.name() << " " << s.area() << "\n"; }

int main() {
    print_area(Circle(2.0));      // Circle 12.5664
    print_area(Rect(3.0, 4.0));   // Rect 12
}

print_area 只编译一次，传 Circle 走圆的公式，传 Rect 走矩形的公式。落地方式是虚函数表（vtable）。

C++ 编译器给每个含虚函数的类生成一张静态表，表里按声明顺序放虚函数地址。每个对象里塞一个隐藏指针（vptr，8 字节）指向这张表。继承时子类复制父类的表，把重写过的槽位换成自己的函数地址。

text
Circle 对象 (16 字节)          Circle 的 vtable (静态, 全类共用一张)
+------------------+          +---------------------------+
| vptr  -----------|--------->| [0] Circle::area          |
| r_ = 2.0         |          | [1] Circle::name          |
+------------------+          | [2] Circle::~Circle       |
                              +---------------------------+

Rect 对象 (24 字节)            Rect 的 vtable
+------------------+          +---------------------------+
| vptr  -----------|--------->| [0] Rect::area            |
| w_ = 3.0         |          | [1] Rect::name            |
| h_ = 4.0         |          | [2] Rect::~Rect           |
+------------------+          +---------------------------+

s.area() 编译成三步：取对象的 vptr，按固定槽位偏移取出函数地址，间接跳转。这就是动态绑定——编译期不知道 s 的实际类型，只知道槽位。

三个由此推出的结论：

  1. 虚函数调用比普通函数多一次内存读和一次间接跳转，热循环里别滥用。
  2. 通过基类指针 delete 时，析构函数不是虚的，就只调基类析构，子类资源泄漏。基类析构必须 virtual。
  3. 构造期间 vptr 还指向基类的表，构造/析构函数里调虚函数，落到基类版本，不是子类的。

对象切片是另一个常见事故：Shape s = c; 按值拷贝，vptr 被拷成 Circle 的表，但 Circle 的成员被切掉了；Shape s = c; 实际发生的是基类部分拷贝，之后调 s.area() 走基类版本。多态只在指针和引用上成立。

虚函数的重写 #

子类用 override 替换父类实现。加了 override，签名写错时编译器直接报错，别省这个关键字。final 封住重写链条。

cpp
class Animal2 {
public:
    virtual void make_sound() const { std::cout << "?\n"; }
    virtual ~Animal2() = default;
};

class Cat2 : public Animal2 {
public:
    void make_sound() const override { std::cout << "喵\n"; }
};

void run(const Animal2& a) { a.make_sound(); }   // 落到实际类型

多态语境下，即使对象被转成父类引用，被调用的也是继承链最末端那个实现——动态绑定看的是运行时类型，不是编译时类型。

C 怎么写多态：函数指针表 #

C 没有虚函数，但有一模一样的东西：结构体里放函数指针。手工把 vtable 搭出来。

c
#include <stdio.h>
#include <stdlib.h>

typedef struct Shape Shape;
typedef struct { double (*area)(const Shape *); void (*destroy)(Shape *); } ShapeVTable;

struct Shape { const ShapeVTable *vptr; };            /* 表指针必须放第一个 */

typedef struct { Shape base; double r; }    Circle;    /* 基类子对象也放最前 */
typedef struct { Shape base; double w, h; } Rect;

static double circle_area(const Shape *self) {
    const Circle *c = (const Circle *)self;           /* 偏移 0，强转安全 */
    return 3.14159265358979 * c->r * c->r;
}

static double rect_area(const Shape *self) {
    const Rect *r = (const Rect *)self;
    return r->w * r->h;
}

static void destroy(Shape *self) { free(self); }

static const ShapeVTable CIRCLE_VT = { circle_area, destroy };
static const ShapeVTable RECT_VT   = { rect_area,   destroy };

static void attach(Shape *s, const ShapeVTable *vt) { s->vptr = vt; }   /* 手动挂表 */

void print_area(const Shape *s) {
    printf("%.4f\n", s->vptr->area(s));               /* 动态绑定在这里发生 */
}

int main(void) {
    Circle c = { { 0 }, 2.0 };
    Rect   r = { { 0 }, 3.0, 4.0 };
    attach(&c.base, &CIRCLE_VT);
    attach(&r.base, &RECT_VT);
    print_area(&c.base);
    print_area(&r.base);
    return 0;
}

几个关键点：

  • vptr 放在结构体第一个字段，Circle* 和 Shape* 地址相同，强转不做偏移。
  • 函数表是 const 静态数组，全类型共用一份，不占对象空间。
  • 每个「构造函数」必须记得挂表，忘了就是空指针崩溃。C 里没人替你干这事。
  • 继承就是把父结构体当第一个字段嵌进去，多级继承照样成立。
  • 析构要靠 destroy 里的 free，C 不会自动调。

这也是 Linux 内核里 struct file_operations、struct net_device_ops 的做法，几万个驱动共用一个抽象层。C++ 的 vtable 是同一个套路，只是编译器替你填表。

参数化多态：模板与泛型 #

编译期多态的另一半是模板。类型当参数传，同一份代码对 int、double、自定义类型各生成一份实例，零运行时开销。

cpp
template <typename T>
class Box {
public:
    void set(T value) { value_ = value; }
    T    get() const  { return value_; }
private:
    T value_{};
};

template <typename T>
T max_of(T a, T b) { return a < b ? b : a; }

Box<int>、Box<std::string> 是两个独立的类，编译器各生成一份。C# 和 Java 的泛型思路接近，实现不同：C# 在运行时保留类型参数，Java 走类型擦除。共同点在于——类型检查在编译期做完，容器里装什么类型不再靠 void* 加强制转换，运行时类型错配直接消失。数据结构与算法这一层尤其吃这个特性：写一遍链表模板，List<int>、List<Point> 都能用，不用为每种元素类型复制一份代码。

六、抽象类与接口 #

抽象类 #

类的实例化没有意义时，把类和方法声明为抽象。abstract 在 C++ 里就是纯虚函数。

cpp
class AbstractShape {
public:
    virtual double area() const = 0;        // 纯虚：子类必须实现
    virtual ~AbstractShape() = default;
    void describe() const {                 // 普通成员：公共代码集中在这
        std::cout << "area = " << area() << "\n";
    }
};

规则：抽象类不能直接实例化；含纯虚函数的类就是抽象类；子类不实现全部纯虚函数，子类也是抽象类。

设计抽象类时把公共代码尽量往上收，数据成员越少越好。它在继承结构里扮演树枝节点，末端的叶子节点才是具体类。

接口 #

接口是一组隐式公共方法和属性的集合，用来封装特定功能，不提供任何实现。C++ 没有 interface 关键字，用「全纯虚 + 无数据成员 + 无构造函数 + 虚析构」的类模拟，命名习惯加 I 前缀。

cpp
class ISerializable {
public:
    virtual std::string serialize() const = 0;
    virtual ~ISerializable() = default;
};

class IComparable {
public:
    virtual int compare(const IComparable& other) const = 0;
    virtual ~IComparable() = default;
};

class Point : public ISerializable, public IComparable {   // 实现多个接口
public:
    Point(int x, int y) : x_(x), y_(y) {}
    std::string serialize() const override {
        return "(" + std::to_string(x_) + "," + std::to_string(y_) + ")";
    }
    int compare(const IComparable& other) const override {
        const auto& o = dynamic_cast<const Point&>(other);
        return (x_ * x_ + y_ * y_) - (o.x_ * o.x_ + o.y_ * o.y_);
    }
private:
    int x_, y_;
};

实现接口的类必须覆盖接口里所有方法；一个类可以继承一个抽象类，但能实现任意多个接口。

维度 抽象类 接口

语义 是对类的抽象，is-a 是对行为的抽象，can-do
演化成本 加个带默认实现的方法，子类不用改 加个方法，所有实现类都得改
复用方式 子类复用父类的代码 只约定契约，不共享代码

选哪个看一句话：需要跨越互不相似的类给出同一个契约，用接口；几个类本来就相似、要共享代码，用抽象类。

抽象类是从子类里发现公共特性后往上泛化出来的父类，接口是在实现上留白，只给预先定义好的方法声明。前者管「是什么」，后者管「能干什么」。

七、组合优于继承 #

这条是设计原则里最实用的一条，值得单独一章。

继承是强耦合：子类编译期就绑死在父类上，父类的成员、布局、行为语义全都要继承。组合是弱耦合：一个对象持有另一个对象的引用，只依赖对方的接口，运行时还能换。

看个具体的坑。需求是「不同形状 × 不同颜色」。用继承：RedCircle、BlueCircle、RedRect、BlueRect……两个维度一乘就是 4 个类，加一个绿色变 6 个，加一个三角形变 9 个。这叫类爆炸。

用组合：形状持有颜色。

cpp
#include <iostream>
#include <memory>
#include <string>

class Color {                                  // 实现维度：颜色
public:
    virtual std::string fill() const = 0;
    virtual ~Color() = default;
};

class Red : public Color {
public:
    std::string fill() const override { return "red"; }
};

class Blue : public Color {
public:
    std::string fill() const override { return "blue"; }
};

class Shape {                                  // 抽象维度：形状
public:
    explicit Shape(std::unique_ptr<Color> c) : color_(std::move(c)) {}
    virtual ~Shape() = default;

    void set_color(std::unique_ptr<Color> c) { color_ = std::move(c); }   // 运行时换
    virtual void draw() const = 0;

protected:
    std::unique_ptr<Color> color_;
};

class Circle : public Shape {
public:
    using Shape::Shape;
    void draw() const override {
        std::cout << "circle in " << color_->fill() << "\n";
    }
};

class Square : public Shape {
public:
    using Shape::Shape;
    void draw() const override {
        std::cout << "square in " << color_->fill() << "\n";
    }
};

现在加形状只写形状，加颜色只写颜色，2 + 2 = 4 个类覆盖 4 种组合；再加一种颜色，只多 1 个类。这就是「桥接」的骨架，也是组合优于继承最典型的账。

再换个日常例子：汽车和引擎。汽车有一个引擎，不是是一个引擎。用继承写成 class ElectricCar : public Car，那混动车怎么办？只能再派生。用组合：

cpp
class Car {
public:
    explicit Car(std::unique_ptr<Engine> e) : engine_(std::move(e)) {}
    void swap_engine(std::unique_ptr<Engine> e) { engine_ = std::move(e); }
    void start() { engine_->start(); }        // 委托：转发给成员
private:
    std::unique_ptr<Engine> engine_;
};

Engine 是抽象基类，GasEngine 打印「轰」，ElectricEngine 打印「嗡」，各自实现 start()。

Car 对 Engine 只知道「有个 start()」，不知道是油是电。发动机换代，Car 一个字不用改。

对照 继承 组合
关系 is-a has-a
绑定时机 编译期写死 运行时替换
可见性 白盒，子类看得到父类细节 黑盒，只依赖接口
影响面 父类改动波及所有子类 只影响被持有的那个实现
扩展方式 加子类 换实现对象

也别走到另一个极端：接口继承（纯虚类、无实现）本质上是「实现契约」，耦合很轻，该用就用。这条原则反对的是为了复用代码而继承实现。

Design Patterns 里那句原话翻过来就是：优先用对象组合，而不是类继承。

八、设计模式是什么：不是银弹 #

先有原则，后有模式 #

四条原则是所有模式的地基。

原则 一句话 违反后的症状
单一职责 SRP 一个类只该有一个引起它变化的原因 改订单的支付逻辑，把订单查询也改坏了
开放-封闭 OCP 对扩展开放，对修改封闭 加一种报表类型要改 5 个 switch
依赖倒转 DIP 高层依赖抽象，不依赖具体实现 业务层 #include 了某个数据库驱动的头文件
迪米特法则 LoD 只和直接朋友说话，别顺着链子摸内部 order.getCustomer().getAddress().getCity()

落到代码上就有味道了。订单处理类如果同时管创建、支付、状态更新，就有三个变化原因（业务规则、支付渠道、状态机），拆成三个类，改支付渠道不会碰到订单创建。图形程序起初只有圆和矩形，加三角形就新增一个类，不碰老代码——判断标准很硬：加功能时老文件的 diff 是不是空的。数据访问层依赖 IDatabaseAccess 接口而非 SqlDatabaseAccess 类，从 SQL Server 换 MongoDB 只加一个实现，业务层零改动。项目管理系统里 Project 要成员邮箱时调 getTeamMemberEmails() 让 Team 自己吐，别顺着 team 摸到 member 再摸到 email，链条一长，Team 一改 Project 就编不过。

模式是命名，不是模板 #

设计模式（Design Pattern）是对「反复出现的设计问题」的命名。它记录三件事：这个问题的形状、一套被验证过的解法结构、以及这套解法的后果。

关键词是命名。它让你在评审时说一句「这里用观察者」，对方立刻知道你的意思，不用画半小时图。词汇的价值比代码模板大得多。

反面也在这：模式一旦被当成必须套用的模板，代码就开始变复杂。

举个真事。需求是导出一张报表，两种格式，CSV 和 PDF。直接写：

cpp
void export_report(const Report& r, bool pdf) {
    if (pdf) write_pdf(r); else write_csv(r);
}

有人一看，这是「可扩展的多算法」，于是上策略模式：IExportStrategy 接口、CsvExportStrategy、PdfExportStrategy、一个 ExportContext；既然后面要「按配置选策略」，再来个 ExportStrategyFactory；工厂全局唯一，干脆上单例；导出完成后要通知进度条，加观察者。

结果：一个 5 行的函数变成 9 个文件 300 行，改一个需求要在 6 个文件之间跳。而真实需求是——一年加了第三种格式，if 改成三行，收工。

判断要不要上模式的硬标准：

  1. 这段代码会变吗？只写一次的脚本，别抽。
  2. 变的方向确定吗？知道有几个分支，if/switch 就够。
  3. 抽出来之后，新加的代码比原来少吗？多出来的类如果只是把 if 换成虚函数，收益是零。
  4. 有人要读它吗？一个人维护的项目，抽象成本全由自己付。

三条都过不了，就写最笨的那个版本。模式是事后归纳出来的，不是事前设计出来的。第三次写重复代码的时候再抽，这叫三次法则。

重构和模式的关系 #

重构是改善已有代码设计的方法，目标是提高可读性和可维护性，同时不改变外部行为——这条约束是硬的，测试得先绿。

重构和模式是一对前后脚：先让代码跑通、测试覆盖住，再通过重构把重复的地方收敛成模式。反过来，先设计一堆模式再往里填逻辑，就是上面那个 9 文件的报表。

敏捷开发强调短迭代、持续反馈、团队协作和适应变化。重构是它的常规动作，模式是重构的产物之一。顺序颠倒，两边都做不好。

九、设计模式的分类：创建型、结构型、行为型 #

GoF 那本书收了 23 种，按「管什么」分成三族。

  • 创建型 5 种：管对象怎么造出来。
  • 结构型 7 种：管类和对象怎么拼成更大的结构。
  • 行为型 11 种：管对象之间怎么分工和通信。

先说清一个编外成员：简单工厂不属于 GoF 的 23 种，它是编程习惯，不是模式，但工程里用得最多。后面照讲。

创建型五种 #

模式 意图 典型场景 代价

十、单例模式 #

意图：保证一个类只有一个实例，并给一个全局访问点。场景很实在——日志记录器、配置管理器、连接池。多个实例会带来资源浪费或者状态不一致。

现代 C++ 的推荐写法只有一种：

cpp
#include <iostream>
#include <string>

class Logger {
public:
    static Logger& instance() {
        static Logger inst;            // C++11 起，局部静态的初始化是线程安全的
        return inst;
    }

    void log(const std::string& msg) { std::cout << "[log] " << msg << "\n"; }

    Logger(const Logger&)            = delete;   // 禁拷贝
    Logger& operator=(const Logger&) = delete;   // 禁赋值

private:
    Logger() = default;
};

int main() {
    Logger::instance().log("start");
    Logger::instance().log("stop");   // 同一个对象
}

为什么这样写就够：static 局部变量在第一次调用 instance() 时构造，编译器生成的守卫变量保证多线程下只构造一次；析构在程序退出时自动发生，不用管释放。拷贝构造和赋值删掉，别人就造不出第二个。

老写法里那些坑值得知道：

  • 饿汉：static Logger inst; 定义在类外，程序启动就构造。简单，但启动顺序不可控，全局对象初始化时未必能用。
  • 懒汉加锁：if (!inst) { lock; if (!inst) inst = new Logger; }，双检锁。C++11 之前这个写法在内存模型上不成立（指令重排会让别的线程拿到半构造的对象），C++11 之后靠 std::atomic 加内存序才对。局部静态版本把这些活全干了，没理由再手写。
  • 不删拷贝：Logger a = Logger::instance(); 直接造出第二个实例，单例名存实亡。

单例的代价也说清楚：它是全局可变状态，单元测试之间互相污染；它把依赖藏起来了，函数签名看不出用了日志器，替换不掉。能用依赖注入传进去的，别用单例。要单例的场景收敛到两个：进程级唯一资源（日志落盘、配置快照）、框架强制的全局入口。

十一、工厂模式 #

工厂族有三种，按复杂度从小到大：简单工厂、工厂方法、抽象工厂。前两种常被混着叫，实际差一层继承。

简单工厂 #

一个工厂类加一个参数，根据参数决定造哪个具体类。Clients 只依赖工厂，不依赖具体类。

cpp
#include <memory>
#include <string>
#include <iostream>

class Car {
public:
    virtual void drive() const = 0;
    virtual ~Car() = default;
};

class Sedan : public Car {
public:
    void drive() const override { std::cout << "sedan\n"; }
};

class SUV : public Car {
public:
    void drive() const override { std::cout << "suv\n"; }
};

class CarFactory {
public:
    static std::unique_ptr<Car> create(const std::string& type) {
        if (type == "sedan") return std::make_unique<Sedan>();
        if (type == "suv")   return std::make_unique<SUV>();
        return nullptr;
    }
};

加一种车型要改 create 的 if 链，违反开放-封闭。产品种类少、变化不频繁时，这个代价比多写三个类划算。

工厂方法 #

把实例化推迟到子类：基类只声明「怎么造」，具体造什么由子类决定。

cpp
class Creator {
public:
    virtual std::unique_ptr<Car> factory_method() const = 0;   // 工厂方法
    void plan() const {                                        // 骨架用工厂方法
        auto c = factory_method();
        c->drive();
    }
    virtual ~Creator() = default;
};

class SedanCreator : public Creator {
public:
    std::unique_ptr<Car> factory_method() const override {
        return std::make_unique<Sedan>();
    }
};

加车型只加一个 Creator 子类，Creator::plan 一个字不用改。代价是类数量翻倍：每种产品配一个工厂。

抽象工厂 #

一次造一族相关对象，且不指定具体类。跨平台 UI 组件库是标准案例：Windows 皮肤和 Mac 皮肤各自一整套按钮、复选框，不能混搭。

cpp
class Button   { public: virtual void paint() const = 0; virtual ~Button() = default; };
class Checkbox { public: virtual void check() const = 0; virtual ~Checkbox() = default; };

class WinButton : public Button {
public: void paint() const override { std::cout << "win button\n"; }
};
class WinCheckbox : public Checkbox {
public: void check() const override { std::cout << "win check\n"; }
};

class GUIFactory {                                  // 抽象工厂：一族产品的接口
public:
    virtual std::unique_ptr<Button>   create_button()   const = 0;
    virtual std::unique_ptr<Checkbox> create_checkbox() const = 0;
    virtual ~GUIFactory() = default;
};

class WinFactory : public GUIFactory {
public:
    std::unique_ptr<Button>   create_button()   const override { return std::make_unique<WinButton>(); }
    std::unique_ptr<Checkbox> create_checkbox() const override { return std::make_unique<WinCheckbox>(); }
};

换皮肤只换工厂对象，业务代码不动，而且从类型上就保证了「同一族」。加一个新的产品种类（比如 Slider）要改 GUIFactory 接口和所有子工厂——这是抽象工厂的硬伤，也是它比工厂方法重的地方。

三种怎么选：产品一种维度变化，简单工厂；产品种类会持续加，工厂方法；产品成族出现且必须配套，抽象工厂。

十二、建造者模式 #

意图：把复杂对象的构建过程与它的表示分离，同样的构建过程能产出不同表示。用在场合适——构造参数十几项、有几项必须一起给、构建有先后顺序。

cpp
#include <string>
#include <iostream>
#include <memory>

class Car {
public:
    void set_engine(const std::string& e) { engine_ = e; }
    void set_wheels(int n)               { wheels_ = n; }
    void set_color(const std::string& c) { color_ = c; }
    void show() const {
        std::cout << engine_ << " " << wheels_ << "w " << color_ << "\n";
    }
private:
    std::string engine_ = "none";
    int         wheels_ = 4;
    std::string color_  = "white";
};

class CarBuilder {
public:
    CarBuilder& engine(const std::string& e) { car_->set_engine(e); return *this; }
    CarBuilder& wheels(int n)                { car_->set_wheels(n); return *this; }
    CarBuilder& color(const std::string& c)  { car_->set_color(c);  return *this; }

    std::unique_ptr<Car> build() { return std::move(car_); }

private:
    std::unique_ptr<Car> car_ = std::make_unique<Car>();
};

int main() {
    auto car = CarBuilder().engine("V6").wheels(4).color("black").build();
    car->show();
}

要点三条：链式返回 *this 让调用像句子；build() 之前对象不完整，调用方拿不到半成品；要防重入就在 build() 里 std::move 掉内部指针，同一个 Builder 造第二次直接崩，比悄悄造出两个更安全。

Car 的构造函数参数表能压到 3 个以内时,建造者就是纯负担——直接写构造函数。

十三、适配器与装饰器 #

这两个都叫「包装」，区别在目的：适配器改接口，装饰器加职责。

适配器 #

把已有的接口转成客户端期望的接口，让本来不兼容的两边能一起工作。

现实类比：欧洲标准的插头是两根圆针，美标是两根扁脚。一台只吃美标的设备插不进欧标插座，中间加一个转换头就行。

cpp
#include <iostream>

class Target {                          // 客户端只认这个接口
public:
    virtual void request() = 0;
    virtual ~Target() = default;
};

class Adaptee {                         // 现成的、接口不兼容的类
public:
    void specific_request() { std::cout << "Called specificRequest\n"; }
};

class Adapter : public Target {         // 对象适配器：持有 Adaptee
public:
    explicit Adapter(Adaptee* a) : adaptee_(a) {}
    void request() override { adaptee_->specific_request(); }
private:
    Adaptee* adaptee_;
};

价值在接缝处：接第三方 SDK、接十年前的祖传模块，写一个适配器就够，不用改对方也不用重写自己。类适配器（同时继承 Target 和 Adaptee）也能做，但它把两个类硬绑在一起，还占用唯一的继承位，用对象适配器。

装饰器 #

不改原对象的结构，运行时往上加职责。比子类化灵活：子类组合是编译期定死的，装饰器可以按顺序叠。

咖啡的例子最直观。基础咖啡，加奶 +0.5，加糖 +0.2，要几样加几样。

cpp
#include <iostream>
#include <memory>
#include <string>

class Coffee {
public:
    virtual std::string desc() const = 0;
    virtual double      cost() const = 0;
    virtual ~Coffee() = default;
};

class SimpleCoffee : public Coffee {
public:
    std::string desc() const override { return "coffee"; }
    double      cost() const override { return 1.00; }
};

class CoffeeDecorator : public Coffee {          // 装饰器基类：继承 + 持有同一个接口
public:
    explicit CoffeeDecorator(std::unique_ptr<Coffee> c) : inner_(std::move(c)) {}
    std::string desc() const override { return inner_->desc(); }
    double      cost() const override { return inner_->cost(); }
protected:
    std::unique_ptr<Coffee> inner_;
};

class Milk : public CoffeeDecorator {
public:
    using CoffeeDecorator::CoffeeDecorator;
    std::string desc() const override { return inner_->desc() + ", milk"; }
    double      cost() const override { return inner_->cost() + 0.50; }
};

class Sugar : public CoffeeDecorator {
public:
    using CoffeeDecorator::CoffeeDecorator;
    std::string desc() const override { return inner_->desc() + ", sugar"; }
    double      cost() const override { return inner_->cost() + 0.20; }
};

int main() {
    std::unique_ptr<Coffee> c = std::make_unique<SimpleCoffee>();
    c = std::make_unique<Milk>(std::move(c));
    c = std::make_unique<Sugar>(std::move(c));
    std::cout << c->desc() << " = " << c->cost() << "\n";   // coffee, milk, sugar = 1.7
}

关键结构是「继承同一个接口 + 持有同一个接口」。继承是为了能替换回原位置，持有是为了往里套。std::unique_ptr 传参要 std::move，这个所有权转移写起来比 Java 啰嗦，但意图很清楚。

装饰器和代理长得很像，区别是意图：装饰器是为了加功能，可以层层叠加；代理是为了控制访问，一般只有一层。

另外四种结构型，速览 #

组合（Composite）：把对象拼成树，叶子和容器用同一个接口。Directory 和 ImageFile 都实现 display()，容器里存子节点，逐层往下调。

cpp
class Node {
public:
    virtual void display(int depth = 0) const = 0;    // 叶子与容器共用
    virtual ~Node() = default;
};
class ImageFile : public Node {                       // 叶子
public:
    explicit ImageFile(std::string n) : name_(std::move(n)) {}
    void display(int depth) const override {
        std::cout << std::string(depth, ' ') << name_ << "\n";
    }
private:
    std::string name_;
};
class Directory : public Node {                       // 容器：自己 + 一堆子节点
public:
    explicit Directory(std::string n) : name_(std::move(n)) {}
    void add(std::unique_ptr<Node> n) { children_.push_back(std::move(n)); }
    void display(int depth) const override {
        std::cout << std::string(depth, ' ') << name_ << "/\n";
        for (const auto& c : children_) c->display(depth + 2);
    }
private:
    std::string name_;
    std::vector<std::unique_ptr<Node>> children_;
};

调用方一句 display() 走到底，不用判断「这是文件还是目录」。

外观（Facade）：一堆子系统，给一个统一入口。多媒体播放最典型——音频、视频、字幕三套 API，用户只想按一个「播放」。门面持有三个子系统，play() 里依次转发 audio_.play()、video_.play()、subtitle_.show()，stop() 反向关闭。外观不禁止直接调子系统，它只是给常见路径铺了条直路；别让门面长成什么都往里塞的上帝类。

享元（Flyweight）：大量细粒度对象里，把可共享的部分抽出来共用。一篇十万字的文档有一万多个「的」，共享之后内存掉一个量级——工厂用 std::unordered_map<char, CharFlyweight> 查表，命中就返回同一个对象，未命中才 emplace 一个。要点是分清两种状态：内蕴状态（字符本身，可共享）和外蕴状态（字号、位置、颜色，每个实例不同，放外面）。享元只共享内蕴状态。

桥接（Bridge）：第七章那个形状 × 颜色的例子就是它，不重复。它的定位是「两个维度各自独立扩展」，和策略的区别在于桥接拆的是结构，策略换的是算法。

十四、代理模式 #

意图：给目标对象一个代理，由代理控制对目标的访问。客户端以为自己直接在用目标，其实中间隔了一层。

cpp
#include <iostream>
#include <memory>
#include <string>

class Image {
public:
    virtual void display() = 0;
    virtual ~Image() = default;
};

class RealImage : public Image {
public:
    explicit RealImage(std::string filename) : filename_(std::move(filename)) {
        load_from_disk();
    }
    void display() override { std::cout << "displaying " << filename_ << "\n"; }
private:
    void load_from_disk() { std::cout << "loading " << filename_ << "\n"; }
    std::string filename_;
};

class ProxyImage : public Image {          // 懒加载代理
public:
    explicit ProxyImage(std::string filename) : filename_(std::move(filename)) {}
    void display() override {
        if (!real_) real_ = std::make_unique<RealImage>(filename_);   // 第一次才真加载
        real_->display();
    }
private:
    std::unique_ptr<RealImage> real_;
    std::string filename_;
};

RealImage 的构造函数里就加载磁盘，代价高。代理推迟到 display()，图片墙滚到哪加载哪，这就是虚拟代理。

代理的用途不止转发：

类型 干什么 例子
虚拟代理 延迟创建昂贵对象 图片懒加载、大文件读入
保护代理 转发前查权限 需要登录的服务调用
远程代理 本地代表远端对象 RPC stub、代理服务器
缓存代理 命中就返回，未命中才转发 接口结果缓存、CDN

保护代理的写法就是在 display() 前面加一道检查：代理持有一个 std::unique_ptr<Image> inner_ 和一个 authed_ 标志，未通过就打印 denied 直接返回，通过才 inner_->display()。

和装饰器的分辨方法再强调一次：装饰器往里加，代理往外挡。结构一样，意图不同，代码评审时说错名字比写错代码更容易误导人。

十五、观察者模式 #

意图：定义一对多依赖，主题状态一变，所有依赖它的对象都收到通知并自动更新。

场景遍地都是：气象站的温度、湿度、气压一变，电子屏、手机应用、Web 面板同时刷新；新闻站的订阅，用户订了专题，更新时邮件或推送直接送到门口。

cpp
#include <functional>
#include <vector>
#include <iostream>

class WeatherStation {                        // Subject
public:
    using Observer = std::function<void(double)>;

    void subscribe(Observer o) { observers_.push_back(std::move(o)); }

    void set_temp(double t) {
        temp_ = t;
        for (auto& o : observers_) o(temp_);   // 一对多，逐个通知
    }

private:
    std::vector<Observer> observers_;
    double temp_ = 0;
};

int main() {
    WeatherStation s;
    s.subscribe([](double t) { std::cout << "screen: " << t << "\n"; });
    s.subscribe([](double t) { std::cout << "phone: " << t << "\n"; });
    s.set_temp(26.5);      // 两个观察者各收一次
}

用 std::function 省掉 IObserver 接口，注册处直接传 lambda。要支持退订就得存 id 或者用 std::weak_ptr，否则对象销毁后回调悬空。

接口版本的结构一样：Subject 里存 std::vector<Observer*>，notify() 遍历调 update()，ConcreteObserver 实现自己的更新逻辑。

三个坑：

  1. 通知期间改列表。观察者在回调里退订，遍历中的 vector 迭代器失效。解法是先拷一份再遍历，或者标记删除、通知完再清理。
  2. 重入。观察者回调里又触发 set_temp，通知套通知。加个 notifying_ 标志挡住，或者把通知改成事件队列异步发。
  3. 顺序无保证。依赖顺序的逻辑别写成两个观察者，合成一个。

观察者的本质是「别让主题知道谁在听」。主题只认一个签名，观察者随便加，加一个显示面板不用碰主题一行代码。

十六、策略模式 #

意图：定义一族可互换的算法，各自封装，运行时挑一个用。

购物车结算是标准案例：满减、百分比折扣、会员价，每种算法独立实现，结账时按用户情况选一个。

cpp
#include <memory>
#include <iostream>

class DiscountStrategy {
public:
    virtual double apply(double price) const = 0;
    virtual ~DiscountStrategy() = default;
};

class FullReduction : public DiscountStrategy {          // 满 200 减 50
public:
    double apply(double p) const override { return p >= 200 ? p - 50 : p; }
};

class Percentage : public DiscountStrategy {             // 九折
public:
    double apply(double p) const override { return p * 0.9; }
};

class Checkout {
public:
    explicit Checkout(std::unique_ptr<DiscountStrategy> s) : s_(std::move(s)) {}
    void set_strategy(std::unique_ptr<DiscountStrategy> s) { s_ = std::move(s); }
    double total(double price) const { return s_->apply(price); }
private:
    std::unique_ptr<DiscountStrategy> s_;
};

Checkout 只知道「有个 apply」，加一种促销只加一个类。std::sort 传比较器是同一个思路——把可变的算法抽出去，把稳定的流程留下来。

策略、状态、命令三个长得像，差别在「谁驱动切换」：

模式 切换由谁发起 对象之间知道彼此吗 典型场景
策略 客户端主动换 各策略互不知情 折扣、比较器、压缩算法
状态 对象内部按事件换 状态知道下一个状态是谁 订单状态机、角色动作
命令 调用方排队或撤销 命令持有接收者 编辑器撤销、任务队列

一句话分辨：策略是「你选一个算法」，状态是「我自己走到下一步」，命令是「把这次动作存起来」。

状态模式的骨架：Character 持有一个 std::unique_ptr<State> state_，action() 转发给 state_->handle(*this)；IdleState、WalkingState、AttackState 各实现 handle()，在里面调 c.set_state(...) 完成转移。转移表藏在这些类里，比一屏 switch 好维护。

命令模式把请求变成对象，Command 只留两个纯虚函数 execute() 和 undo()，CutCommand、CopyCommand 各自实现它们，撤销栈就是一个 std::vector<std::unique_ptr<Command>>，回退时倒着弹。

十七、模板方法 #

意图：把算法的骨架定在基类，把可变步骤留成虚函数交给子类。骨架的顺序不变，步骤可以换。

烘焙是最好的类比：预热烤箱、准备材料、混合、烘焙，这个顺序换不了；巧克力蛋糕和香草蛋糕只在材料和配比上不同。

cpp
#include <iostream>

class AbstractBaker {
public:
    void bake() {                       // 骨架：子类改不了顺序
        preheat();
        prepare();
        mix();
        cool_down();                    // 钩子：默认空实现
    }
    virtual ~AbstractBaker() = default;

protected:
    virtual void prepare() = 0;
    virtual void mix()     = 0;
    virtual void cool_down() {}         // 钩子方法，子类按需覆盖

private:
    void preheat() { std::cout << "preheat 180C\n"; }
};

class ChocolateBaker : public AbstractBaker {
protected:
    void prepare() override { std::cout << "chocolate + flour\n"; }
    void mix()     override { std::cout << "stir 3 min\n"; }
};

要点：bake() 不加 virtual，子类只能填空不能改流程；固定步骤用 private 藏起来；可变步骤用 protected 纯虚；可选步骤给默认空实现的钩子。

模板方法和策略是解决同一件事的两条路：模板方法用继承固定骨架，编译期绑定，只能换步骤不能换流程；策略用组合换整个算法，运行时替换。骨架真的稳定就选模板方法，否则选策略——这也是「组合优于继承」在模式层的体现。

其余行为型，速览 #

剩下的几种在同一张表里对齐，代码骨架都是「一个接口 + 若干实现」的变体：

模式 骨架长什么样 一句话记住
职责链 每个处理器持有一个 next 指针 我不处理就往下传
中介者 一个中介持有所有同事的引用 别互相喊，都跟中介说
备忘录 save() 返回快照，restore() 塞回去 存档、读档
迭代器 has_next() + next() 只看元素，不看内部结构
访问者 元素 accept(v)，访问者 visit(el) 加操作不改元素类
解释器 每个语法节点一个 interpret() 小语言自己解释自己

职责链的写法最短，客服分级就是它：基类 Handler 持一个 Handler* next_，handle(level) 先试 can_handle(level)，能处理就走 do_handle(level)，不能就 next_->handle(level) 往下传。一级处理简单问题，二级处理技术问题，都不处理就落到 nullptr——链尾必须有兜底，否则请求静默丢失。

中介者把网状通信收成星形：聊天室里用户不直接互发，全走服务器转发，send_message 遍历除发送者外的所有人。服务器顺手就能做消息存储、在线状态管理。

备忘录保存内部状态而不暴露内部结构：Memento 只让 restore 读，编辑器每次编辑前 save() 一份，撤销就是 restore(history.back())。快照多了一定要设上限，不然内存吃光。

迭代器提供顺序访问又不暴露内部结构：ShoppingCart 内部是 vector 还是链表，调用方不用知道，拿一个 Iterator 逐个走完就行。C++ 的 begin()/end() 是它的语言级形态，范围 for 直接吃。真正的遍历实现看《线性表与数组》和《链表》。

访问者解决「结构稳定、操作常变」：图形库里有圆、方、三角，要加「导出 SVG」「算面积」「算周长」三种操作。用虚函数就得改每个图形类；用访问者只加一个新类，元素只留一个 accept(Visitor& v) { v.visit(*this); }。accept 里的 *this 是静态类型，重载决议在编译期就选对了 visit(Circle&)——这是双重分派，访问者模式最容易讲不清的地方。

解释器给一门小语言定义文法并解释执行：Number、Addition、Multiply 各自实现 interpret()，3 + 5 * 2 建成的表达式树递归求值就是结果。文法一复杂（要优先级、要括号、要变量）就该上正经的解析器，解释器只适合极小的规则集。

十八、模式怎么选 #

先看信号，再看模式。这张表是反向索引：

你遇到的症状 候选模式 什么情况下别用
一堆 if/else 按类型分支，且分支还在加 策略、工厂方法 分支固定两三支，写 if
构造参数十几项、有必填项搭配 建造者 参数 3 个以内，直接构造函数
创建开销大，想延迟到真正用时 代理（虚拟）、单例（懒） 创建很便宜，没必要
两个类接口对不上，改哪边都疼 适配器 能改源码就直接改
想在运行时给对象加功能 装饰器 组合是固定的，用继承
一个改动要通知一堆模块 观察者 只有一个消费者，直接调用
两个维度各自扩展、类数量相乘爆炸 桥接、组合 只有一个维度，别拆
树形结构，叶子与容器要统一对待 组合 结构只有一层
一族对象必须配套使用 抽象工厂 产品不成族，用工厂方法
大流程固定、个别步骤要变 模板方法 整个流程都要能换，用策略
请求要排队、要撤销、要留日志 命令 不需要撤销，直接调函数
全进程只要一份的东西 单例 能被注入的依赖，别用单例

选之前先过四道闸：

  1. 会不会变。只写一次的东西不抽。抽出来的类如果只是把 if 换成虚函数，收益为零。
  2. 变化的维度有几个。一个维度用策略或工厂，两个独立维度用桥接，一个也不能预判就先别拆。
  3. 谁跟谁耦合。顺着「谁造对象、谁持有谁、谁通知谁」三个问题找族，比背 23 个名字管用。
  4. 有没有人维护。一个人维护的小项目，抽象成本全自己付，宁可直接写。

还有一条更硬的：模式名是沟通工具，不是验收标准。代码评审时被问「这里为什么不用观察者」，答「因为只有一个订阅者，直接调更清楚」是合格答案。

十九、易错点速查 #

坑 症状 改法
基类析构不是虚的 delete base_ptr 后子类资源泄漏，无报错 基类析构一律 virtual
对象切片 Shape s = circle; 之后调不到子类实现 传指针或引用
忘记 override 签名写错变成新函数，静默不重写 每个重写都加 override
构造/析构里调虚函数 落到基类版本，子类初始化没生效 构造函数里别调虚函数
硬套模式 5 行函数变 300 行、9 个文件 三次法则：重复三次再抽
单例当全局变量用 单测互相污染，依赖藏起来 改成注入

这份表里前四条全是多态的地基问题，出错时现象都很怪——没有编译错误，只有运行时的空指针或者「为什么没调到我的函数」。查这类问题的顺序：先看析构是不是虚的，再看有没有切片，再看签名对不对得上。

后面几条属于设计层面的账。模式用错的成本不会立刻显现，它一年后才显现——加个功能要改六个文件，改的时候还得先花半天搞明白那堆接口在干什么。

把这篇文章压缩成一句：面向对象的三特性解决「代码怎么组织」，设计模式解决「组织方式怎么命名和复用」，前者是能力，后者是词汇表。词汇表背得再熟，句子还得自己写。
