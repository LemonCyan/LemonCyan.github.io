一、段错误是什么 #

先摆结论：段错误不是一种错误，而是内核向进程递送 SIGSEGV 的结果。真正的原因在进程自己——它算出了一个不该算的地址，或者用了一个它没有的权限。内核没有制造错误，内核只是检查地址翻译时发现了非法访问，然后执行了保护。

把链路拆开，一共六步。

  1. 进程执行一条访存指令，给出虚拟地址。mov -0x8(%rbp),%rax 之后紧跟 movb $0x58,(%rax)，%rax 里装的就是那个虚拟地址。
  2. MMU 拿地址查页表，x86-64 是四级页表，一路查到物理页帧号。
  3. 页表项不存在，或者存在但权限位不匹配（往只读页写、用户态碰内核页、执行不可执行的页），MMU 当场抛缺页异常（#PF），把出错地址写进 CR2，把错误码压进内核栈。
  4. 内核 do_page_fault 接管，问两个问题：这个地址落在本进程的某个 VMA 里吗？落在的话，能当场补一页吗？
  5. 补得上就是正常缺页中断，进程继续跑，用户无感。补不上就 force_sig_fault(SIGSEGV, ...)，把信号挂到待处理队列。
  6. 内核态返回用户态的路上，do_signal 发现待处理信号是 SIGSEGV 且处置为 SIG_DFL，于是打印、转储、终止。

这里有个容易忽略的分界：访问未映射的地址，不等于段错误。malloc 之后第一次写、mmap 一个文件页、fork 之后的写时复制，全都会触发缺页异常，内核补页之后程序照常运行，只有第 5 步那个分支才升级成 SIGSEGV。「非法访问」和「崩溃」之间还隔着内核的一次判断。

反向的坑同样重要：不是所有内存错误都会当场崩。free 之后那块内存还映射着，越界写到相邻的合法页里，内核根本不管。这类错误会在很久以后以完全无关的形式爆出来——这就是为什么 core 文件里的崩溃点经常不是根因所在的那行。

1.1 地址空间里的三个禁区 #

三处要记住：.rodata 是只读映射，写常量字符串会在第 3 步的权限检查失败；0 号页故意留空，落到 0x0 附近这一整页的访问全非法；图中相邻的两段之间都是未映射空洞，指针加飞了一般就掉进这些洞。

1.3 那行字是谁打的 #

屏幕上那句 Segmentation fault 不是你的程序打的，是 shell 打的。程序被信号打死之后，shell 用 wait 拿状态，WIFSIGNALED 为真，WTERMSIG 返回 11，于是查表翻成人话；如果内核确实写了 core，WCOREDUMP 为真，shell 补一个括号。

bash
$ ./segfault_demo
Segmentation fault (core dumped)
$ echo $?
139

两段输出只差一个括号，含义完全不同。有 (core dumped) 说明转储成功，可以去 core_pattern 指向的目录捞文件；没有这个括号说明内核没写，第八章那条 ulimit -c 的线索就从这里开始。

二、段错误的常见成因 #

成因分两类：地址本身不对（算出来的地址没映射，或落在禁区），地址对但权限不对（页表项在，权限位拦住你）。分类不是为了背概念，而是崩溃后拿到出错地址时，能立刻判断往哪个方向查。

成因 典型代码 崩溃地址特征 信号
空指针解引用 p = NULL; p->field = 1; 0 或很小的偏移量 SIGSEGV
未初始化指针 char *p; *p = 'a'; 随机值，常是 0xcccc 之类 SIGSEGV
悬空指针 / UAF free(p); p->x = 1; 落在已释放的堆块里 SIGSEGV
写只读段 char *s = "abc"; s[0] = 'A'; .rodata 段内的合法地址 SIGSEGV
栈上数组越界 int a[10]; a[100] = 1; 栈区地址，常伴随返回地址被改写 SIGSEGV / SIGILL
堆上缓冲区溢出 strcpy(buf, 长串) 堆区地址，破坏 malloc 控制块 SIGSEGV / SIGABRT
栈溢出（深递归） 无终止条件的递归 紧贴栈顶边界 SIGSEGV
双重释放 free(p); free(p); 无访存，glibc 主动中止 SIGABRT
未对齐访问 强转指针后访问多字节整数 地址低位不为 0 SIGBUS
类型截断 int 存指针再取回 高 32 位被抹掉 SIGSEGV

2.1 空指针解引用 #

c
#include <stdio.h>

int main(void) {
    char *p = NULL;
    *p = 'X';            /* 往 0 号页写，必炸 */
    printf("%c\n", *p);  /* 到不了这里 */
    return 0;
}

bash
$ gcc -g -O0 -Wall -Wextra null_deref.c -o null_deref
$ ./null_deref
Segmentation fault (core dumped)

*p = 'X' 能编译通过，零警告。-Wall -Wextra 也拦不住，编译器不知道 p 是空的。这类错误只能靠运行期工具或者人眼 review。

2.2 写只读段 #

c
#include <stdio.h>
#include <string.h>

int main(void) {
    char *s = "Hello World";   /* 字面量在 .rodata，只读映射 */
    s[0] = 'h';                /* 写只读页，炸 */

    char t[] = "Hello World";  /* 数组会把字面量拷到栈上 */
    t[0] = 'h';                /* 合法 */
    strcpy(t, "TEST");         /* 只要不超长也合法 */
    return 0;
}

差别只有一个 []。同族陷阱是 char *p = "test"; strcpy(p, "TEST");——把字面量当地址传给写函数。

2.3 未初始化指针 #

c
void bad(void) {
    char *p;        /* 栈上的垃圾值 */
    *p = 'a';       /* 往随机地址写 */
}

崩溃地址看起来毫无规律，0x7f8a3c... 或者 0xbebebebe 这种。同一程序跑两次地址会变，因为栈上残留的内容取决于上一个函数留下什么。看到 0xbebebebe、0xcdcdcdcd、0xcccccccc 是好消息：这些是调试版分配器或编译器插的填充模式，等于直接确认「读了没初始化的内存」。

2.4 数组越界与栈破坏 #

越界写本身不一定会崩，因为相邻地址往往还映射着。真正致命的是它改掉了不该改的东西——函数返回地址、栈帧指针、堆的 malloc_chunk 头。

c
#include <stdio.h>
#include <string.h>

void overflow(void) {
    char buf[8];
    strcpy(buf, "0123456789ABCDEF");   /* 16 字节写进 8 字节的框 */
}

int main(void) {
    overflow();
    printf("returned\n");
    return 0;
}

加 -fstack-protector-all 编译，这类写入会在函数返回前被 canary 拦下，报 *** stack smashing detected ***，信号变成 SIGABRT 而不是 SIGSEGV。看到这句提示，方向就明确了：某个栈上缓冲区被写爆了。

2.5 堆破坏与双重释放 #

c
#include <stdlib.h>
#include <string.h>

int main(void) {
    char *p = malloc(10);
    strcpy(p, "12345678901234567890");  /* 20 字节踩坏控制块 */
    free(p);
    free(p);                            /* 二次释放，glibc 检测到并中止 */
    return 0;
}

bash
$ ./heap_bad
free(): double free detected in tcache 2
Aborted (core dumped)

信号是 SIGABRT（6），退出码 134。堆破坏的恶劣之处是崩溃点离根因很远：踩坏控制块的那一刻没事，等下一次 malloc / free 才炸，bt 里全是分配器内部帧。遇到这种栈不要盯着 _int_free 看，去找上一次写这块内存的地方。

2.6 类型截断 #

把指针塞进 int 再取回，64 位下必然丢掉高 32 位，拼回来是个无效地址。这类错误在 32 位程序移植到 64 位时集中爆发。编译时开 -Wint-to-pointer-cast -Wpointer-to-int-cast 能抓一批。

三、空指针为什么偏移 0x160 #

崩溃日志里写着 dereference at 0000000000000160。地址是 0x160 不是 0x0，于是有人判断这不是空指针、是野指针指到了 0x160，方向跑偏半天。

真实原因是访问结构体成员时算的是成员地址。

c
struct conn *c = NULL;
c->flags = 1;

text
地址 = (unsigned long)c + offsetof(struct conn, flags)
     = 0 + 352
     = 0x160

指针确实是空的，只是它没有直接解引用自己，而是先加了一个偏移。报出来的地址是偏移量，不是指针值。崩溃地址小于一页大小，就按空指针链路查。

3.1 一个能跑的复现 #

c
#include <stdio.h>
#include <stddef.h>

struct conn {
    char         rbuf[256];   /* offset   0  */
    char         wbuf[64];    /* offset 256  */
    int          rlen;        /* offset 320  */
    int          wlen;        /* offset 324  */
    int          state;       /* offset 328  */
    int          err;         /* offset 332  */
    short        family;      /* offset 336  */
    short        port;        /* offset 338  */
    unsigned int peer;        /* offset 340  */
    unsigned int local;       /* offset 344  */
    unsigned int seq;         /* offset 348  */
    unsigned int flags;       /* offset 352 = 0x160 */
};

int main(void) {
    printf("sizeof = %zu, offsetof(flags) = %zu (0x%zx)\n",
           sizeof(struct conn),
           offsetof(struct conn, flags),
           offsetof(struct conn, flags));

    struct conn *c = NULL;
    c->flags = 1;   /* 实际写地址 = 0 + 0x160 */
    return 0;
}

bash
$ gcc -g -O0 offset160.c -o offset160
$ ./offset160
sizeof = 356, offsetof(flags) = 352 (0x160)
Segmentation fault (core dumped)

打印出来的 352 和日志里的 0x160 是同一个数，疑点消除。

3.2 为什么 0 附近一整段都非法 #

页表的最小映射单位是一页，主流平台 4KB。所以保护不是只保护 0x0 这一个字节，而是 0x0 ~ 0xfff 整段，落在这一页里的任何访问都触发异常。内核故意不给 0 号页任何权限，原因很直白：让空指针访问立刻暴露，而不是悄悄读写到某个真实物理页上。

现代内核还多一层，/proc/sys/vm/mmap_min_addr 默认 65536，用户态连把内存映射到低地址都不允许。

bash
$ cat /proc/sys/vm/mmap_min_addr
65536

两条规则叠起来：小于 0x10000 的崩溃地址，一律先当空指针处理。判别成本极低，收益极高。

3.3 用 GDB 反查是哪个成员 #

知道偏移是 0x160，下一步要回答「这是哪个字段」。ptype /o 直接把布局列出来：

(gdb) ptype /o struct conn

/*      0      |     256 */    char rbuf[256];
/*    256      |      64 */    char wbuf[64];

/*    324      |       4 */    int wlen;
/*    328      |       4 */    int state;
/*    332      |       4 */    int err;
/*    336      |       2 */    short family;
/*    338      |       2 */    short port;

0x160 对上 352，锁定 flags。装了 pahole 的话命令行也能做同样的事：pahole -C conn ./offset160。

3.4 两个干扰项 #

编译器优化会改变崩溃地址的形态，方向有两个。开 -O2 之后，编译器会把「基址 + 偏移」提前算好，甚至直接生成「往绝对地址 0x160 写」的指令，汇编里看不到 %rax 里装着 0，地址常量直接出现在指令里。反过来，一旦编译器证明 c == NULL，按 C 标准这已经是未定义行为，它会把整个分支优化掉——段错误「消失」了，不是修好了，是代码被删了。所以用 core 定位时，-O0 编的那份二进制是黄金标准。

另一个方向：崩溃地址大也不代表跟空指针无关。

c
struct conn *c = get_conn();   /* 返回 NULL */
c->rbuf[1024] = 0;             /* 地址 = 0 + 0 + 1024 = 0x400 */

rbuf 偏移为 0，加上下标 1024，地址跑到 0x400，仍在一页之内，仍是空指针。判别方法不变：地址在低 64KB 内，先怀疑空指针；真要区分就看 bt 里那个函数实参是不是 0x0。

四、野指针与悬空指针 #

两个词经常混着用，指的不是一回事，排查手法也不一样。野指针的关键词是「没初始化」，悬空指针的关键词是「生命周期结束了但指针还活着」。前者靠编译警告和代码规范挡，后者靠所有权设计挡。

名字 指针值 谁造成的 崩溃地址特征
空指针 0x0 显式赋值 NULL，或函数返回 NULL 没检查 0 到 0x10000 之间
野指针 垃圾值 局部变量没初始化、结构体没清零 随机，跨进程不稳定
悬空指针 曾经的合法地址 指向的对象已 free、已出作用域、已被重分配 落在堆区或已回收的栈区

4.1 悬空指针是怎么活的 #

c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void) {
    char *p = malloc(32);
    strcpy(p, "hello");
    free(p);                          /* p 变成悬空指针 */

    printf("after free: %s\n", p);    /* 读已释放的块，多半不崩 */
    strcpy(p, "world");               /* 写已释放的块，踩坏 tcache 链表 */
    printf("wrote ok\n");
    return 0;
}

bash
$ gcc -g -O0 dangling.c -o dangling && ./dangling
after free:
wrote ok
$ echo $?
0

退出码 0，这就是最麻烦的情况：悬空指针的错误不报，只污染。free 之后那块内存还映射着，内核不拦你；hello 读成空是因为 glibc 在 free 时把 tcache 的 next 指针写进了前 8 字节。等下一次 malloc 恰好拿到这块内存，或者 free 发现链表被踩坏，才会在别的地方炸——core 里的崩溃点，又一次不是根因。

同一段代码交给 ASan，错误当场暴露：

text

    #0 0x4c8f20 in main dangling.c:12

报告里有三个地址：出错点、释放点、分配点。三样凑齐，根因没地方藏。注意错误类型是 heap-use-after-free 而不是段错误——ASan 在访问的瞬间中断，不需要等内核出手。

4.2 返回局部变量的地址 #

c
char *make_name(void) {
    char buf[32];
    snprintf(buf, sizeof(buf), "worker");
    return buf;      /* 返回栈地址，函数一返回就失效 */
}

编译时开 -Wreturn-local-addr，警告直接给到 warning: function returns address of local variable。这类警告必须当错误处理。同族问题还有返回指向函数内 static 缓冲区的指针——那个不崩，但多线程下互相覆盖，属于另一类故障。

4.3 C++ 的迭代器失效 #

cpp
std::vector<int> v;
v.push_back(1);
int *p = &v[0];                 /* 指着旧 buffer */
for (int i = 0; i < 100; ++i) {
    v.push_back(i);             /* 触发扩容，旧 buffer 被 delete[] */
}
std::printf("%d\n", *p);        /* use-after-free */

规矩很硬：容器一旦会变，就不要留裸指针或迭代器，要用就每轮重新取，或者用下标。

4.4 怎么把这类错误钉死 #

按成本从低到高：free 之后立刻把指针置 NULL，让二次释放退化成无害的空指针释放；把所有权写进接口注释，谁分配谁释放；单元测试里开 -fsanitize=address 跑一遍，这一条能覆盖绝大多数 UAF；稳定性测试时用 ASAN_OPTIONS=detect_leaks=0 把 UAF 和泄漏分开看。

五、栈溢出与越界访问 #

栈是固定大小的区域，默认 8MB，向上够不着堆、向下长到边界就停。ulimit -s 报的就是这个数（单位 KB）。每个线程都有自己的栈，pthread_attr_setstacksize 可以改，主线程的栈由 ulimit -s 决定。

5.1 一帧里都放了什么 #

text
高地址
+----------------------------+
| 调用者的栈帧                |
+----------------------------+
| 返回地址      <-- 越界写到这里 = 控制流被劫持
+----------------------------+
| 保存的 rbp / canary         |
+----------------------------+
| 局部变量 buf[8]  <-- 越界从这里往上写
+----------------------------+
低地址（rsp）

局部变量在低地址，返回地址在高地址。一个 strcpy 写过头，先踩 canary，再踩 rbp，最后改写返回地址；函数 ret 那一刻跳到垃圾地址上，症状就从 SIGSEGV 变成 SIGILL 或者别的奇怪东西。

5.2 深度递归打穿栈 #

c
#include <stdio.h>

static int depth = 0;

void recurse(void) {
    char pad[4096];          /* 每层压 4KB，快速吃掉栈 */
    pad[0] = (char)depth;
    if (++depth % 1000 == 0) printf("depth = %d\n", depth);
    recurse();               /* 没有终止条件 */
}

int main(void) { recurse(); return 0; }

bash
$ gcc -g -O0 -fno-optimize-sibling-calls stack_deep.c -o stack_deep
$ ./stack_deep
depth = 1000
depth = 2000
Segmentation fault (core dumped)

必须加 -fno-optimize-sibling-calls，否则 -O2 会把尾递归优化成循环，程序永远不崩，你会以为代码没问题。崩溃地址紧贴栈底边界，bt 会打出上千个相同的帧，这种现场用 bt -20 只看最内 20 帧——无穷递归看内层没意义，看它是从哪条路径进来的才有意义。

5.3 单个超大局部变量 #

c
void big(void) {
    char buf[16 * 1024 * 1024];   /* 16MB，超过 8MB 默认栈 */
    buf[0] = 1;
    printf("%d\n", buf[0]);
}

栈顶下方有一个 guard page。栈指针跳过 guard page 直接访问更远的地址，内核认为这不是正常栈增长，判为非法。注意这和「栈慢慢长到边界」不是一回事：一次性跳太远，连增长的机会都没有。修法两条：大数组改 static 挪到 .bss，或者 malloc 到堆上。嵌入式环境里栈往往只有几十 KB，这个坑踩得更频繁。

5.4 堆越界与全局越界 #

c
char *buf = malloc(16);
memset(buf, 'A', 16);
strcpy(buf + 16, "overflow");   /* 写到块外面 */

越界写落到堆的空隙里不崩，落到未映射的页才崩。ASan 会精确报出边界：

text
==41302==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x602000000020
WRITE of size 9 at 0x602000000020 thread T0
    #0 0x4c9a3a in main heap_overflow.c:8
0x602000000020 is located 0 bytes to the right of 16-byte region
allocated by thread T0 here:
    #0 0x4b3d07 in malloc
    #1 0x4c98ed in main heap_overflow.c:6

0 bytes to the right of 16-byte region 就是结论：写的位置刚好在 16 字节块右边界外一字节。全局数组更隐蔽，它在 .bss 里两头都挨着别的全局变量，越界几乎不崩，只会静默改掉隔壁：

c
int table[4];
int victim = 0x1234;
table[7] = 0;                       /* 越界 3 个 int */
printf("victim = 0x%x\n", victim);  /* 变成 0，程序正常退出 */

这类只能靠 ASan 的全局红区检测或者 code review。

六、信号：SIGSEGV 与 SIGBUS #

段错误是结果，信号是内核表达这个结果的方式。把信号认清楚，能省下大量瞎猜。

信号 值 含义 典型触发 默认动作
SIGSEGV 11 段错误 访问未映射地址、写只读页、栈溢出 终止 + core
SIGBUS 7 总线错误 地址未对齐、mmap 文件被截断 终止 + core
SIGILL 4 非法指令 执行损坏的指令、跳到数据区 终止 + core
SIGFPE 8 算术异常 整数除零、INT_MIN / -1 终止 + core
SIGABRT 6 主动中止 abort()、glibc 检测到堆破坏、assert 失败 终止 + core
SIGTRAP 5 断点陷阱 int3、调试器断点 终止 + core
SIGSYS 31 非法系统调用 seccomp 拦截 终止 + core
SIGXCPU 24 CPU 时间超限 RLIMIT_CPU 触发 终止 + core
SIGXFSZ 25 文件大小超限 RLIMIT_FSIZE 触发 终止 + core

退出码换算固定是 128 + 信号值：139 是 SIGSEGV，134 是 SIGABRT，135 是 SIGBUS，136 是 SIGFPE。看到 139 先确认是不是 shell 报的，别急着下结论。

6.1 SIGSEGV 和 SIGBUS 的边界 #

两者都叫内存访问出错，区别在于地址有没有映射。SIGSEGV 是地址根本没有对应页表项，或者有页表项但权限不允许；SIGBUS 是页表项在、映射也在，但这个地址在这个映射里不合法。典型场景是 mmap 一个文件然后把文件截短：

c
int fd = open("/tmp/bus_demo.bin", O_RDWR | O_CREAT | O_TRUNC, 0644);
ftruncate(fd, 4096);
char *p = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
printf("byte at 0: %d\n", p[0]);   /* 正常 */
ftruncate(fd, 0);                  /* 文件被截断，映射还在 */
printf("byte at 0: %d\n", p[0]);   /* 访问已不存在的页 -> SIGBUS */

bash
$ ./bus_demo
byte at 0: 0
Bus error (core dumped)
$ echo $?
135

135 = 128 + 7。看到这个信号，第一反应应该是「有人动了文件或者动了映射」，而不是去查指针。另一个 SIGBUS 来源是未对齐访问：x86 对大部分未对齐访问容忍，ARM 上不开 unaligned 支持就直接 SIGBUS，*(int *)(buf + 1) 这种强转就是。

6.2 在代码里拦住崩溃并打印堆栈 #

生产环境磁盘只读、容器不让写 core、客户现场拿不到文件，这些情况下让程序自己在死之前把现场打进日志，是唯一可行的手段。

c
#define _GNU_SOURCE
#include <stdio.h>
#include <signal.h>
#include <string.h>
#include <unistd.h>
#include <execinfo.h>

static void crash_handler(int sig, siginfo_t *si, void *uc) {
    void *frames[32];
    int n = backtrace(frames, 32);
    char head[160];
    int len = snprintf(head, sizeof(head),
                       "\n=== CRASH sig=%d(%s) addr=%p ===\n",
                       sig, strsignal(sig), si->si_addr);
    write(STDERR_FILENO, head, (size_t)len);       /* 不用 printf */
    backtrace_symbols_fd(frames, n, STDERR_FILENO);
    signal(sig, SIG_DFL);                          /* 恢复默认，否则没 core */
    raise(sig);
}

static void install_handlers(void) {
    struct sigaction sa;
    memset(&sa, 0, sizeof(sa));
    sa.sa_sigaction = crash_handler;
    sa.sa_flags = SA_SIGINFO | SA_RESETHAND;
    sigemptyset(&sa.sa_mask);
    sigaction(SIGSEGV, &sa, NULL);
    sigaction(SIGBUS,  &sa, NULL);
    sigaction(SIGILL,  &sa, NULL);
    sigaction(SIGFPE,  &sa, NULL);
    sigaction(SIGABRT, &sa, NULL);
}

int main(void) { install_handlers(); char *p = NULL; *p = 'X'; return 0; }

bash
$ gcc -g -O0 -rdynamic crash_log.c -o crash_log && ./crash_log
=== CRASH sig=11(Segmentation fault) addr=(nil) ===
./crash_log(+0x1369) [0x5612a1b2c369]
./crash_log(main+0x2a) [0x5612a1b2c24a]
/lib/x86_64-linux-gnu/libc.so.6(__libc_start_main+0xf3) [0x7f4a2c1a40b3]

三个关键点缺一不可：-rdynamic 必须加，否则只能打印 (+0x1369) 而没有 main 这样的名字；SA_SIGINFO 必须加，否则拿不到 si->si_addr，也就看不到那个 0x160；handler 里只能用异步信号安全的函数，printf、malloc、free 都不能碰，因为崩溃时它们内部正持有锁，snprintf、write、backtrace_symbols_fd 可以。

si->si_addr 就是内核写进 CR2 的地址，等于把 GDB 里 p $_siginfo._sifields._sigfault.si_addr 的结果提前拿到了。还有一件事必须记住：装了 handler 就不会有 core 文件，内核决定要不要转储时会检查信号处置是不是 SIG_DFL（第十章会看到这段判断）。所以 handler 的最后一步必须是 signal(sig, SIG_DFL); raise(sig);，把自己摘出去让内核接手。忘了这一步，日志有了，core 没了。

七、core dump 是什么 #

进程被致命信号打死的时候，内核可以把它此刻的整个地址空间抓一份下来存成文件，这就是 core dump。它不是文本日志，是 ELF 格式的二进制。

bash
$ file core-segfault_demo-28564-1689587421
core-segfault_demo-28564-1689587421: ELF 64-bit LSB core file, x86-64, version 1 (SYSV), SVR4-style, from './segfault_demo'

readelf -n 能看到里面装了什么，几类 note 各有分工：NT_PRSTATUS 是每个线程的寄存器组（含 rip、rsp、rbp），定位崩溃指令全靠它；NT_PRPSINFO 是进程信息、命令行、PID、UID；NT_SIGINFO 是崩溃信号号和 si_addr；NT_FILE 记录了崩溃时映射了哪些文件、映射到哪个地址段，GDB 靠它找回共享库符号；NT_AUXV 是 ELF 辅助向量。

7.1 里面有啥，没有啥 #

内容 在不在 core 里 说明
用户态内存（栈、堆、.data、.bss） 在 默认全抓，所以文件很大
私有文件映射（MAP_PRIVATE） 在 已修改的页会写进去
共享文件映射（MAP_SHARED） 不在 只记录映射关系，内容回原文件读
CPU 寄存器 在 每个线程一份
信号信息 在 信号号 + 出错地址
打开的文件描述符 不在 只有编号，没有内容
内核态栈 不在 用户态 core 不含内核栈

「共享映射不在」影响很大：程序 mmap 了一个大文件，core 里不会有它，GDB 分析时会回去读原文件；原文件被改过或删了，相关地址在 GDB 里就显示 Cannot access memory at address ...。

7.2 为什么那么大 #

默认抓整个用户态内存，一个跑了几天的服务堆里几个 GB 的缓存，core 就是几个 GB，磁盘瞬间打满——这是生产环境默认关掉 core dump 的直接原因。控制手段有三层：ulimit -c 限制单个文件大小，core_pattern 换存放位置（tmpfs 或管道压缩），/proc/<pid>/coredump_filter 按内存类型挑着抓。

bash
$ cat /proc/self/coredump_filter
00000033

这个位图每一位对应一类内存页，0x33 是默认值：抓匿名私有页、匿名共享页、ELF 头、私有文件映射。只要栈和堆可以改 0x23，跳过巨大的匿名映射还能再小一圈。把 core 从 GB 级压到 MB 级，这一招最省事。

八、开启 core dump #

「为什么没有 core 文件」九成的答案都在这一章。内核写不写 core，先看进程的 RLIMIT_CORE——这个值是 0 的时候 do_coredump 直接返回，一个字节都不写。而主流发行版出于磁盘空间的考虑默认就设成 0。

bash
$ ulimit -c
0

看到这个 0，后面所有关于 core 的讨论都不成立，先把它改掉。

8.1 ulimit 到底在改什么 #

ulimit 是 shell 内建命令，改的是当前 shell 自己的资源上限，这个上限会被所有子进程继承。于是它有三个性质：只影响这个 shell 和它启动的进程，另开终端还是旧值；不能改已经跑起来的进程；软限制不能超过硬限制，只有 root 能抬硬限制。

选项 含义 单位 与段错误的关系
-c core 文件最大尺寸 块 设 0 等于禁用转储，首要排查点
-s 线程栈大小 KB 调小会让深递归更早崩，调大能缓解
-v 虚拟内存上限 KB 设太小时 malloc 返回 NULL，间接制造空指针
-n 打开文件数 个 满了会让 open 失败，库拿到 NULL 就解引用
-H / -S 操作硬限制 / 软限制 — 只有 root 能抬硬限制

-c 后面的数字是块数不是字节数。一块到底多少字节，bash 和 POSIX 的说法不一致，所以别算，要么直接写 unlimited，要么写一个远大于需求的数字。

bash
$ ulimit -a | grep -E 'core|stack|open files'
core file size          (blocks, -c) 0
stack size              (kbytes, -s) 8192
open files                      (-n) 1024

8.2 临时打开 #

bash
$ ulimit -c unlimited
$ ulimit -c
unlimited
$ ulimit -c unlimited && ./segfault_demo     # 顺序不能反

顺序是硬要求：先 ulimit，再启动程序。写成 ./segfault_demo && ulimit -c unlimited 就完全无效——程序都崩完了才去开开关，这个错误在排障现场非常常见，尤其是把命令贴进 sh -c 的时候。

8.3 永久打开 #

方案 A：普通登录用户改 /etc/security/limits.conf。

*          soft    core    unlimited
*          hard    core    unlimited
root       soft    core    unlimited
root       hard    core    unlimited

* 不包含 root，所以 root 要单列。这个文件由 pam_limits.so 在登录时读取，改完要重新登录才生效，source 没用。

方案 B：systemd 服务改 unit。

ini
[Service]
LimitCORE=infinity

infinity 是关键字不是数字。改完 systemctl daemon-reload 再 restart，用 systemctl show -p LimitCORE <svc> 确认改到了。全局改则写 /etc/systemd/system.conf 里的 DefaultLimitCORE=infinity。

方案 C：容器里的进程。

bash
$ docker run --ulimit core=-1 --rm -it debian bash -c 'ulimit -c'
unlimited

不写这个参数，容器里的 core file size 就是 0。你在容器里 ulimit -c unlimited 也没用，因为硬限制是 0，普通用户抬不上去——这是容器里拿不到 core 的头号原因。

8.4 setuid 程序不写 core #

bash
$ cat /proc/sys/fs/suid_dumpable
0
值 行为
0 setuid / setgid 进程一律不转储（默认）
1 所有进程都转储，包括 setuid（会把内存里的密钥写进普通用户可读的文件）
2 转储，文件归 root 所有、权限 0600，只有 root 能读

守护进程带 setuid 位时，ulimit -c unlimited 也没用，卡在这里。生产环境用 2，别用 1。

8.5 一张总表 #

层次 位置 作用 典型故障
进程资源上限 ulimit -c / RLIMIT_CORE 决定写不写、最多写多大 值为 0，什么都不产生
全局开关 /proc/sys/fs/suid_dumpable 决定 setuid 程序写不写 值为 0，守护进程没 core
存放位置与命名 /proc/sys/kernel/core_pattern 决定写到哪、叫什么 目录不存在，写入失败
内容裁剪 /proc/<pid>/coredump_filter 决定抓哪些类型的页 什么都没裁，core 几十 GB
用户态接管 systemd-coredump / apport 内核把 core 交给用户态程序 core 不在磁盘上，在 coredumpctl 里
容器限制 docker run --ulimit core= 覆盖容器内硬限制 容器内硬限制为 0，抬不动

排查顺序照这张表从上往下走，多数问题在第一行就结束了。

九、core 文件的命名与存放 #

ulimit -c 放开了还是找不到文件，多半是命名和路径的问题。

bash
$ cat /proc/sys/kernel/core_pattern
core

值是 core 的时候，文件生成在崩溃进程的当前工作目录，名字就叫 core。于是程序 cd 到别处再崩，文件就在别处；同一目录崩两次会互相覆盖；daemon 的 cwd 是 /，就有了 /core，普通用户还写不进去。

9.1 core_pattern 的占位符 #

占位符 展开成 备注
%e 可执行文件名 最长 15 字符，受 comm 长度限制
%p 崩溃进程的 PID 名字带 PID 就不会互相覆盖
%t 崩溃时刻的 UNIX 时间戳 秒级
%u / %g 实际用户 ID / 组 ID
%s 导致崩溃的信号值 SIGSEGV 时是 11
%h 主机名 多机共用存储时有用
%E 可执行文件路径，/ 换成 ! 路径长的程序用它
%c core 文件大小上限（RLIMIT_CORE）
%i 线程组 ID（TGID） 多线程程序用它区分进程
%P 全局 PID 容器里和 %p 不一样

一个够用的组合：

bash
$ sudo sysctl -w kernel.core_pattern="/tmp/cores/core-%e-%p-%t"
kernel.core_pattern = /tmp/cores/core-%e-%p-%t
$ ./segfault_demo
$ ls /tmp/cores/
core-segfault_demo-28564-1689587421

程序名、PID、时间戳三个信息都在名字里，翻历史 core 时不用猜。

9.2 永久生效与那个必须建的目录 #

sysctl -w 重启就没了，写进 /etc/sysctl.conf：

kernel.core_pattern = /var/log/cores/core-%e-%p-%t

bash
$ sudo mkdir -p /var/log/cores
$ sudo chmod 1777 /var/log/cores
$ sudo sysctl -p

目录漏建，内核写 core 会失败，日志里只留一句 core dump to /var/log/cores/core-... failed，你在目标目录里什么也看不到。写失败的 core 不重试，也不降级到当前目录。

另外别写相对路径。kernel.core_pattern="cores/core-%p" 的文件落在崩溃进程的 cwd 下面，而 cwd 随时会变，新内核还会往 dmesg 里塞一条警告说相对路径不可靠。统一用绝对路径，能省掉一整类「文件到底去哪了」。

9.3 管道模式：交给用户态程序 #

core_pattern 以 | 开头的时候，内核不再自己写文件，而是把 core 数据从管道丢给一个用户态程序的 stdin。

bash
$ cat /proc/sys/kernel/core_pattern
|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h

这是 systemd 发行版的默认值。所以core 文件不在任何目录里，它被 systemd-coredump 收走了。

bash
$ coredumpctl list
TIME                         PID   UID   GID SIG     COREFILE EXE
Sun 2026-11-17 14:02:31 CST 28564  1000  1000 SIGSEGV present  /home/dev/segfault_demo

$ coredumpctl info 28564        # 直接打出 bt、寄存器、映射表
$ coredumpctl gdb 28564         # GDB 直接起在崩溃现场
$ coredumpctl dump 28564 --output /tmp/core-28564

coredumpctl gdb 比手工拼路径快得多，日常排障优先用它。

9.4 Ubuntu 的 apport 与容器错位 #

Ubuntu 桌面版默认 core_pattern 是 |/usr/share/apport/apport %p %s %c %d %P，core 被 apport 接走，落在 /var/crash/，名字形如 _usr_bin_xxx.1000.crash。这种 .crash 不是纯 ELF core，套了一层包装，用 sudo apport-unpack <crash文件> /tmp/unpacked 拆开，/tmp/unpacked/CoreDump 才是能喂给 GDB 的本体。不想用 apport，sudo sysctl -w kernel.core_pattern="core-%e-%p" 关掉它。

容器里的坑是另一回事：core_pattern 是内核全局参数，容器里看到的就是宿主机的值。你在容器里配成 /tmp/cores/core-%p，文件实际写在宿主机上，容器里看不到。两个办法——配成绝对路径再把宿主机那个目录 bind mount 进容器，或者改用 gdbserver 在线调试。

9.5 命名规则该定成什么样 #

场景 配置值
单机排障，留全信息 /tmp/cores/core-%e-%p-%t
多机共用存储，带主机名（目录要事先建） /data/cores/%h/core-%e-%p-%t
直接压缩，省磁盘（脚本见第十章） 管道调 /usr/local/bin/core_helper %e %p

十、coredump 的内核实现 #

到这里该往下一层看：内核在什么条件下决定转储，怎么转储。

10.1 触发条件：致命信号加默认处置 #

内核把所有会引发 core dump 的信号攒成一个掩码。

c
/* include/linux/signal.h */
#define SIG_KERNEL_COREDUMP_MASK (\
        rt_sigmask(SIGQUIT)   |  rt_sigmask(SIGILL)  | \
        rt_sigmask(SIGTRAP)   |  rt_sigmask(SIGABRT) | \
        rt_sigmask(SIGFPE)    |  rt_sigmask(SIGSEGV) | \
        rt_sigmask(SIGBUS)    |  rt_sigmask(SIGSYS)  | \
        rt_sigmask(SIGXCPU)   |  rt_sigmask(SIGXFSZ) | \
        SIGEMT_MASK)

十个信号：SIGQUIT、SIGILL、SIGTRAP、SIGABRT、SIGFPE、SIGSEGV、SIGBUS、SIGSYS、SIGXCPU、SIGXFSZ，再加部分架构才有的 SIGEMT。段错误落在 SIGSEGV 这一位上。SIGKILL 和 SIGSTOP 不在里面——这两个信号用户态抓不住，内核也不给它们转储的机会。所以进程被 kill -9 打死永远没有 core 文件，被 OOM killer 盯上的进程收到的是 SIGKILL，现场直接消失。

光有信号还不够，第二个条件是信号处置必须是默认值。

c
/* kernel/signal.c, get_signal() */
if (ka->sa.sa_handler != SIG_DFL) {
        /* Run the handler. */
        ksig->ka = *ka;

        if (ka->sa.sa_flags & SA_ONESHOT)
                ka->sa.sa_handler = SIG_DFL;

        break;   /* will return non-zero "signr" value */
}

这是内核遍历待处理信号时的分支。一旦发现 sa_handler 不是 SIG_DFL（用户装了 handler），就地 break 跳出查找，转去执行用户的自定义处理函数，根本不走到 coredump 分支。这解释了两件事：第六章那个 crash_handler 为什么不写 signal(sig, SIG_DFL); raise(sig); 就没有 core；为什么很多人「加了崩溃日志之后 core 就没了」——不是 ulimit 变了，是 handler 把转储路径挡掉了。

10.2 转储分支 #

c
/* kernel/signal.c */
if (sig_kernel_coredump(signr)) {
        if (print_fatal_signals)
                print_fatal_signal(ksig->info.si_signo);
        proc_coredump_connector(current);
        /*
         * If it was able to dump core, this kills all
         * other threads in the group and synchronizes with
         * their demise.
         */
        do_coredump(&ksig->info);
}

三件事按顺序发生：打日志、通知连接器、真正转储。注释还说明了一个细节：多个线程同时踩到崩溃时只有一个线程能赢下这场竞争，其余的沿用赢家设置的退出码。所以一个线程组崩掉只会留下一个 core 文件。

10.4 do_coredump 的三个阶段 #

核心步骤在 fs/coredump.c，可以归成三步。

第一步，让线程组里所有线程停下来。 拷贝内存之前必须保证没有别的线程还在改这块内存。内核给线程组里剩下的线程发一个 SIGKILL，然后等它们全部进入不可运行状态。这一步不做，抓下来的就是一个撕裂的快照——一半旧一半新，分析出来的结论全是假的。这也是为什么多线程程序崩溃之后，bt 里只有出事那个线程有栈。

第二步，写文件。 core_pattern 不带 | 时，内核自己在 kernel_write 里把 ELF core 一段段写出去：先写 ELF 头和 PT_NOTE（寄存器、信号、映射表），再按 VMA 逐个写内存内容。

第三步，走管道。 core_pattern 带 | 时情况变了，内核 fork 一个子进程（call_usermodehelper），两者之间建一条管道，内核这端负责写，子进程那端的管道被 dup 到标准输入上。

text
内核 ====== 写入管道 ======> 用户态进程（压缩/收集） ======> 文件

这条设计的巧妙之处在于内核不需要知道压缩、加密、上传这些事，所有花活都在用户态做，内核只管把字节灌进管道。子进程可以是任何程序：gzip、systemd-coredump、你自己的收集器。

10.5 自己写一个压缩 helper #

脚本存在 /usr/local/bin/core_helper，两个参数分别是 %e（程序名）和 %p（PID）：

bash
#!/bin/sh
exec gzip - > /root/"$1".core."$2".gz

bash
$ sudo chmod +x /usr/local/bin/core_helper
$ sudo sysctl -w kernel.core_pattern="|/usr/local/bin/core_helper %e %p"
$ ulimit -c unlimited && ./segfault_demo
$ ls -lh /root/segfault_demo.core.*.gz
-rw-r--r-- 1 root root 128K Nov 17 14:10 /root/segfault_demo.core.28601.gz
$ gunzip -c /root/segfault_demo.core.28601.gz > /tmp/core-28601
$ gdb ./segfault_demo /tmp/core-28601

管道模式照样受 RLIMIT_CORE 约束，ulimit -c 必须放开，这一点常被漏掉。另一个要当心的点：helper 的 stdin 是管道，如果 helper 自己崩了或提前退出，内核写管道会收到 EPIPE，core 就丢了。所以 helper 要尽量简单，别在里面做网络请求、别 exec 一个会失败的路径。写错路径的后果是静默丢失，日志里只有一行 Core dump to |/bad/path pipe failed。

10.6 从触发到落盘 #

阶段 发生了什么 分叉
1 访存指令 → MMU 查页表失败 → #PF → do_page_fault 合法缺页则补页继续，非法访问才继续往下
2 force_sig_fault(SIGSEGV) 信号挂到待处理队列
3 返回用户态，do_signal 处理 sa_handler != SIG_DFL 则跑用户 handler，handler 里 raise(SIG_DFL) 后回到本行
4 sig_kernel_coredump(signr) 为真 进入 do_coredump
5 do_coredump 按 core_pattern 分叉 无 | 则内核自己写 ELF，有 | 则 fork helper 走管道
6 落盘 磁盘上的 core 文件，或用户态程序接管

排障时只关心三个节点：ulimit -c 是不是 0、core_pattern 指向哪、sa_handler 是不是 SIG_DFL。这三处全对，core 就一定会出现。

11.1 必修的四条命令 #

(gdb) bt
#0  0x00000000004005aa in trigger_crash (data=0x4006c0 "...") at segfault_demo.c:9
#1  0x00000000004005cf in func_b (data=0x4006c0 "...") at segfault_demo.c:15
#2  0x00000000004005df in func_a (data=0x4006c0 "...") at segfault_demo.c:19
#3  0x0000000000400605 in main (argc=1, argv=0x7ffe178a9c48) at segfault_demo.c:25

bt 是诊断的第一个动作，帧号、地址、函数名、实参、行号五样齐了，剩下的只是读。逐帧看形参值，能直接看出「这一帧还是好的、下一帧就没了」的交接点——绝大多数坏指针不是在崩溃点产生的，是一层层传下来的。

(gdb) frame 1          # 切到 func_b 帧，之后所有命令都在这个上下文里
15	    trigger_crash(data);
(gdb) info locals      # 看局部变量，崩溃点那帧已经乱了，父帧的变量才是证据
(gdb) list             # 源码上下文，默认前后各 5 行
8	    char* null_ptr = NULL;
9	    *null_ptr = 'X';
(gdb) print null_ptr
$1 = (char *) 0x0
(gdb) p *conn          # 整个结构体直接打
(gdb) p/x conn         # 按十六进制打，看地址用

core 里不含源码，list 是回磁盘上找的，源文件路径变了就什么都看不到。编译时 -g 记的是相对路径，换机器调试要把源码放在同样的相对位置。

11.2 没有源码时下到汇编 #

开了 -O3，行号对不上，或者手上只有 release 二进制，就得看寄存器和指令。

(gdb) info registers rip rsp rbp rax
rip            0x4005aa   0x4005aa <trigger_crash+38>
rsp            0x7ffe178a9be0   0x7ffe178a9be0
rbp            0x7ffe178a9c00   0x7ffe178a9c00
rax            0x0        0

rip 是出错指令地址，rsp 是栈顶，rbp 是当前帧基址，rax 在这里是 0——就是那个空指针。

(gdb) disassemble trigger_crash
   0x000000000040059c <+24>:	movq   $0x0,-0x8(%rbp)
=> 0x00000000004005aa <+38>:	mov    -0x8(%rbp),%rax
   0x00000000004005ae <+42>:	movb   $0x58,(%rax)

逐句读：先把 0 存到 %rbp-8（那就是 null_ptr），再把 0 装进 %rax，然后往 %rax 指向的地址写 0x58（字符 'X'）。=> 是 rip 停的位置——写操作在这条指令之后才真正执行，所以崩溃点显示在 load 那条上，这是 MMU 报错时的典型形态。

x 命令用来直接看内存：x/8xb 0x7ffe178a9be0 按字节看，x/4dw 按双字看，x/s 0x4006c0 当字符串读，x/10i $rip-20 从 rip-20 开始反汇编 10 条。x/s 和 x/10i 在 core 分析里出现频率最高。

11.3 一套固定的分析流程 #

十二、没有 core 文件怎么办 #

按下面这张表从上往下查，多数情况能在五分钟内定位到卡在哪一层。

现象 主要原因 查法 处理
连 (core dumped) 都没有 ulimit -c 是 0 ulimit -c ulimit -c unlimited 后重跑
有 (core dumped) 但找不到文件 core_pattern 指向别处 cat /proc/sys/kernel/core_pattern 按该路径找，或改绝对路径
路径对但没有文件 目录不存在或不可写 手工 touch 一试 建目录、改权限
只有空文件或很小的文件 磁盘满 / RLIMIT_CORE 很小 df -h、ulimit -c 清盘，或改到 tmpfs
装了崩溃 handler 之后没 core handler 没恢复 SIG_DFL 看代码有没有 raise(sig) 补 signal(sig, SIG_DFL); raise(sig);

setuid 程序没 core suid_dumpable = 0 cat /proc/sys/fs/suid_dumpable 设为 2
容器里没 core 硬限制是 0，抬不动 容器内 ulimit -Hc docker run --ulimit core=-1
core 文件不是 ELF 被 apport / systemd 包了一层 file 看类型 coredumpctl dump 或 apport-unpack

几条补充。先看退出码再找 core：139 是 SIGSEGV，134 是 SIGABRT，135 是 SIGBUS，137 是被 SIGKILL；如果是 0 或 1，根本没有信号参与，该去查程序自己的错误处理。用 sh -c 或 CI 跑的时候 ulimit 不会自动继承，每次都显式写一遍：sh -c 'ulimit -c unlimited; exec ./segfault_demo'。bt 全在 memcpy、strlen、free 里，说明你的指针传错了而不是库有 bug，往上翻一帧看实参。

老工具 catchsegv 在没 core 时能应急，它靠 LD_PRELOAD 挂一个库进去，捕获 SIGSEGV 后把寄存器、栈回溯、映射表一起打出来：

bash
$ catchsegv ./segfault3

它属于 glibc 遗留工具，部分发行版已经删了，能用就用，别当主力。

十三、系统日志与 dmesg 里的线索 #

没有 core、来不及 attach、程序一闪而过，剩下的线索全在系统日志里。

bash
$ dmesg | grep -i segfault
[ 2329.479037] segfault3[2700]: segfault at 80484e0 ip 00d2906a sp bfbbec3c error 7 in libc-2.10.1.so[cb4000+13e000]

这一行六个字段，一个一个读。

字段 例子 含义
segfault3[2700] 程序名[PID] 谁崩的
segfault at 80484e0 出错地址 就是 si_addr，也就是 CR2
ip 00d2906a 指令指针 崩在哪条指令，配二进制能反查到函数
sp bfbbec3c 栈指针 当时的栈顶，判断栈有没有被打穿
error 7 错误码 位图，下面拆
in libc-2.10.1.so[cb4000+13e000] 所在映射 出错指令属于哪个库、映射基址与长度

error 7 值得单独拆，x86 的页错误错误码是位图。

位 值 含义
bit 0 1 保护违规（页存在但权限不够）；0 表示页不存在
bit 1 2 写操作；0 表示读
bit 2 4 在用户态发生；0 表示内核态
bit 3 8 保留位被改写（罕见）
bit 4 16 取指令时触发（跳到不可执行页）

7 = 1 + 2 + 4，含义是「用户态写一个存在但没有写权限的页」。这一句就够了：不是野指针跑到空洞里，是往只读页写，直接去查 .rodata 上的写操作。常见组合对照：error 4 用户态读不存在的页（空指针、野指针），error 6 用户态写不存在的页（空指针写、越界写），error 5 用户态读存在但无权限的页，error 7 用户态写只读页（常量字符串），error 15 用户态取指碰到不可执行页（栈被改成数据，或者跳飞了）。

ip 那个地址换算成函数名用 addr2line：

bash
$ addr2line -e ./segfault3 -f -C 0x00d2906a

静态链接的程序直接出函数名和行号；动态库里的地址要先减去映射基址（[cb4000+...] 那个 cb4000），再拿对应的 .so 去查。

查日志的几条常用命令：dmesg -T | grep -i -E 'segfault|traps' 带人类可读时间戳；journalctl -k | grep -i segfault 看内核日志；journalctl -u myapp --since "10 min ago" 只看某个服务。三者的内容是同源的，dmesg 读 ring buffer，journalctl 读持久化日志并且带上了服务名。

13.1 nm、objdump、ldd #

没有符号或者怀疑库的时候，这三个工具补位。

bash

080483e4 T main
08048420 T trigger_crash
$ objdump -d ./segfault3 | grep -A20 '<trigger_crash>'
$ ldd ./segfault3

nm 列符号表，T 是代码段的全局符号，拿到 ip 后找地址最接近且小于它的那个 T 就是所在函数，nm -C 能解 C++ 的 mangle 名。objdump -d 反汇编全程序，-S 混排源码（要求 -g 编译），没装 GDB 的时候只能靠它。ldd 看依赖库解析到了哪个文件，多版本共存的环境里 libfoo.so.1 指错版本是常事——注意 ldd 会执行目标程序的动态链接器，不要对不信任的二进制跑它，改用 objdump -p | grep NEEDED。

十四、预防：静态检查与运行检查 #

core 是事后取证，能前置拦截的尽量前置。

手段 开关 拦什么
基础警告 -Wall -Wextra 未初始化、隐式声明、类型不匹配
未初始化专项 -Wuninitialized -Wmaybe-uninitialized 野指针的一大来源
返回局部地址 -Wreturn-local-addr 悬空指针
指针截断 -Wint-to-pointer-cast -Wpointer-to-int-cast 64 位下的截断
格式化字符串 -Wformat=2 参数错位，一类隐蔽崩溃
栈保护 -fstack-protector-strong 返回地址被改写
源码加固 -D_FORTIFY_SOURCE=2 strcpy、memcpy 溢出
静态分析 -fanalyzer GCC 自带的数据流分析
链接加固 -Wl,-z,relro -Wl,-z,now GOT 表被改写 
bash
$ gcc -g -O2 -Wall -Wextra -Wformat=2 -Wreturn-local-addr \
      -fstack-protector-strong -D_FORTIFY_SOURCE=2 \
      -Wl,-z,relro -Wl,-z,now segfault_demo.c -o segfault_demo

这一行该进 Makefile 或 CMake 的默认配置，不要留给人手工敲。嵌入式工具链先确认 libssp 在不在，再加 -fstack-protector-strong。CppCheck 补编译器看不出来的那部分，cppcheck --enable=warning,style,performance --inconclusive src/，它不做完整编译、靠模式匹配找空指针解引用和越界，误报比编译器多，放 CI 里当参考别当门禁。

运行期的组合是这样：开发阶段开 ASan（-fsanitize=address -fno-omit-frame-pointer），它在访问非法内存的瞬间中断；UBSan（-fsanitize=undefined）抓有符号溢出、空指针运算这类「没崩但是错了」的行为；集成阶段跑 Valgrind Memcheck，不用重编译直接跑二进制，慢 20 到 50 倍，适合单测回归；生产环境靠 core。开发阶段开 ASan，集成阶段跑 Valgrind，生产环境靠 core，这三句记住就够了，具体报告解读见《内存问题与泄漏检测》一篇。

编码习惯上真正管用的几条：指针定义即初始化，char *p = NULL; 多一个字符省掉一类随机崩溃；free 之后置 NULL，挡住二次释放和大部分释放后再用；数组访问带边界，sizeof(buf)/sizeof(buf[0]) 别写魔法数字，strncpy 记得手动补 '\0'；接口注释里写清谁释放返回值，跨模块传裸指针是 UAF 的温床；格式化字符串严格对齐，%d 传 long 在某些 ABI 上会把栈读错位；别把指针塞进 int；深递归改迭代，大数组挪到堆。

十五、易错点速查 #

误判 事实 怎么确认
「段错误是一种错误」 它是内核发 SIGSEGV 的结果，原因在进程自己 bt 看是谁算出的地址
「崩溃地址是 0x160，所以是野指针」 地址 = 基址 + 成员偏移，基址是 0 ptype /o 查偏移是不是 352
「地址不是 0，就不是空指针」 低 64KB 全在保护区，偏移量和下标都会让地址变大 cat /proc/sys/vm/mmap_min_addr
「没有 core 就是内核有问题」 九成是 ulimit -c 0 ulimit -c
「我设了 ulimit -c unlimited」 设在了另一个 shell，或设在启动程序之后 ulimit -c && ./prog 写成一行
「程序里有转储开关」 装了 handler，内核就不转储 代码里有没有 signal(sig, SIG_DFL)
「(core dumped) 就一定有文件」 写失败也照打这句 看 core_pattern 后去该目录找
「core 在当前目录」 systemd / apport 会把 core 收走 coredumpctl list
「kill -9 之后应该有 core」 SIGKILL 不在转储信号集里 echo $? 是 137
「bt 全是 ?? 是 core 坏了」 二进制被 strip 了 file ./prog 看 stripped
「用最新编译的二进制读旧 core」 地址对不上，结论全错 归档发版的 unstripped + build-id
「崩溃点就是根因」 堆破坏的崩溃点常在很久之后、很远的地方 用 ASan 跑一遍找第一现场
「段错误都是 SIGSEGV」 SIGBUS 是未对齐或文件被截断，SIGABRT 是堆破坏 echo $?：139 / 135 / 134
「加了 -g 就一定能看到行号」 -O2 之后行号错位 用 -O0 版本复现，或 disassemble
「ASan 能替代 core」 ASan 慢、内存占用高，生产上不了 开发用 ASan，生产留 core
「多线程崩溃要每个线程都有 core」 一个线程组只产生一份 core info threads 看其他线程状态

三条最容易反复踩的，单拎出来。

ulimit -c 和启动程序的顺序。写成 ./prog && ulimit -c unlimited 的人不少，程序都崩完了才去开开关。

handler 挡掉 core。加了崩溃日志之后 core 消失，第一反应常是「内核配置变了」，实际是自己装了 SIGSEGV 的 handler。第十章那段 sa_handler != SIG_DFL 的判断就是答案。

二进制版本错配。core 里的地址来自那一份二进制，用新编译的版本去读，bt 会给出完全错误但看起来很合理的函数名——这是最危险的一种错，因为它不报错。每次发版必须归档 unstripped 二进制，靠 build-id 对齐：

bash
$ readelf -n ./prog | grep 'Build ID'
$ readelf -n core-28564 | grep 'Build ID'

两个 ID 一致，core 才和二进制配套。
