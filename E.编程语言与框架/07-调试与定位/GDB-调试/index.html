一、GDB 是什么 #

GDB 是 GNU 工具链里的调试器。它干的事很窄：让程序在你指定的位置停下来，然后让你看它此刻的样子。停下来的手段就四类：

想让程序停在哪 命令 排查什么
某一行 break 怀疑某个分支从没进去过
一步一步走 next / step 摸清真实执行路径
数据变了就停 watch 变量莫名被改
崩了再回头查 gdb ./demo core 事后取证，复现不了也能查

停下来之后能看的：变量值、表达式结果、内存原始字节、寄存器、调用栈、线程列表。GDB 的能力有边界——编译器擦掉的东西它看不到，没编进调试信息的符号它也看不到。第二条是新手觉得 GDB「什么都不对」的头号原因。

先备一个能跑的样例，存成 demo.c：

c
#include <stdio.h>

int change(int *a, int b)
{
    int t = *a;
    *a = b;
    b = t;
    return t;
}

int main(void)
{
    int a = 5;
    int b = 8;
    int s;

    s = change(&a, b);
    printf("a=%d b=%d s=%d\n", a, b, s);
    return 0;
}

int a = 5; 在第 13 行，s = change(&a, b); 在第 17 行。后面所有会话都基于它。

bash
gcc -g -O0 demo.c -o demo && ./demo    # 输出 a=8 b=8 s=5

换成不带 -g 编一次，看 GDB 的表现：

text
$ gcc -O0 demo.c -o demo-nog && gdb -q ./demo-nog
Reading symbols from ./demo-nog...
(No debugging symbols found in ./demo-nog)
(gdb) break main
Breakpoint 1 at 0x1149
(gdb) list
No symbol table is loaded.  Use the "file" command.
(gdb) print a
No symbol "a" in current context.

三种报错，一件事：没有调试信息，GDB 手里只剩地址。断点能下，落在裸地址 0x1149；list 找不到源码；print 找不到变量名。带 -g 的同一份代码，同一条 break main：

text
Reading symbols from ./demo...
(gdb) break main
Breakpoint 1 at 0x1149: file demo.c, line 13.

差别就在这里：有符号才认得出 demo.c:13。这就是 -g 的全部意义。

二、编译时为什么要加 -g #

-g 让编译器把调试信息一并写进目标文件和可执行文件。GCC 的格式叫 DWARF，里面记：源码文件名、每行对应的指令地址区间、变量名与类型、变量在栈帧或寄存器里的位置、函数参数、内联关系。

没有这份东西，GDB 只剩 ELF 符号表（strip 之后连这个都没了）。它知道有个 main，但不知道 main 里第 13 行在哪、a 存在哪。

bash
gcc -g -O0 demo.c -o demo

多文件项目每个 .c 都要带 -g，链接也要带。漏掉一个 .o 的 -g，那个文件里的函数就退化成地址，bt 里一半是 demo.c:13，一半是 ?? ()——这种「一半好一半坏」最难查：

bash
gcc -g -O0 -c main.c -o main.o
gcc -g -O0 main.o util.o -o app

确认二进制里有没有调试信息：

bash
file demo                        # ... with debug_info, not stripped
readelf -S demo | grep -i debug  # .debug_info / .debug_line 都在

with debug_info, not stripped 是目标状态。看到 stripped 就回头查构建脚本，发布前的 strip 会把调试信息一刀切掉。.debug_info 管变量，.debug_line 管行号，两个都要在。

第二个必须保住的是源码文件本身。GDB 不把源码编进可执行文件，它只记住「这个地址对应 demo.c 第 13 行」，显示源码时还要去读 demo.c。把文件挪走：

text
(gdb) list
13      demo.c: No such file or directory.

断点和单步还能用（地址信息在二进制里），但你看不到代码了。第六章讲怎么把路径指回去。

接下来是最容易被忽略的一条：优化级别。-g 和 -O2 不冲突，能一起编，但优化过的代码不适合调试：

  • 变量被放进寄存器，栈里没位置，print a 回 <optimized out>
  • 语句重排，第 13 行和第 14 行的指令交叉执行，next 来回跳
  • 循环展开、常量折叠，一行源码对应的指令数变了
  • 函数内联，change 被塞进 main，bt 里看不到这一层

四种现象归到一句话：源码与机器码的对应关系被破坏了，而 GDB 的每一步操作都建立在这个对应关系上。同一份 demo.c 编 -O2 看实际效果：

text
$ gcc -g -O2 demo.c -o demo-o2 && gdb -q ./demo-o2
(gdb) start
Temporary breakpoint 1, main () at demo.c:13
13          int a = 5;
(gdb) print a
$1 = <optimized out>
(gdb) next
14          int b = 8;
(gdb) next
18          printf("a=%d b=%d s=%d\n", a, b, s);

第 17 行的 change 调用被内联展开，next 从 14 行直接落到 18 行，15、16、17 全没了；a 只在一个地方用，被塞进寄存器，print 拿不到值。

编译选项 GDB 里的表现 调试可用性
-g -O0 变量、行号、栈帧齐全，next 严格逐行 日常调试就用它
-g -O1 部分变量进寄存器，个别语句合并 能凑合，看到 <optimized out> 别意外
-g -O2 / -O3 内联、重排、循环展开，栈帧对不上 只在复现 release 版专属 bug 时才用
无 -g 只有地址，list / print 全失效 调试源码无从谈起

做法很直接：调试阶段一律 -g -O0，交付前再用 -O2 编一遍跑测试。如果 bug 只在 release 版出现，就用 -g -O2 编一份，接受那些别扭，重点看 bt 和内存，别指望单步。-g3 比 -g 多带宏定义，-ggdb 生成 GDB 专用扩展信息，日常 -g 够用。

三、启动 GDB 的几种方式 #

命令行下只有一个 gdb，差别在带什么参数。

启动方式 干什么 用在什么时候
gdb ./demo 加载可执行文件 最常用，从头调
gdb 空启动，之后 file ./demo 想先改几项设置再加载
gdb ./demo core 可执行文件 + core 转储 程序已经崩了，事后分析
gdb -p 12345 attach 到正在跑的进程 服务不能停，就地查
gdb --args ./demo 10 20 带命令行参数加载 程序要参数才走对分支
gdb -q ./demo 不打印版权横幅 干净，建议默认带上
gdb -x cmds.gdb ./demo 启动即执行命令文件 自动化，第十二章讲
gdb -batch -ex run -ex bt ./demo 跑完就退，只留输出 塞进脚本、CI 
bash
gdb ./demo          # 等价于 gdb demo，'./' 只是路径

带参数的程序别把参数写在 gdb 后面傻等，用 --args，或者进 GDB 之后再设：

text
(gdb) show args
Argument list to give program being debugged when it is started is "10 20".
(gdb) set args 10 20

程序崩了留下 core 文件，两个参数一起给，GDB 加载崩溃瞬间的内存快照，停在你出事的那一行：

bash
gdb ./demo core

这条链路（ulimit -c unlimited、core 文件路径、bt 看栈）在 段错误与 core dump 那篇展开，这里只留命令形态。

进程已经跑起来了，先拿 PID 再 attach：ps -ef | grep demo 找到 PID，gdb -p 12345 挂上去，GDB 打出 Attaching to process 12345 和符号加载信息，之后 bt 照常用。

attach 会暂停目标进程，detach 之前程序一直冻着，线上环境手别抖。进了 (gdb) 之后，几个环境类命令先记住：

text
(gdb) help                 # 总帮助，help break 看具体命令
(gdb) apropos watch        # 按关键词搜命令
(gdb) shell ls -l          # 临时执行一条 shell 命令
(gdb) cd /home/user/src    # 切换 GDB 的工作目录
(gdb) set pagination off   # 关掉分页，输出一口气刷完
(gdb) set width 0          # 不按宽度换行，日志更好读
(gdb) quit                 # 退出，简写 q

set pagination off 和 set width 0 写进 ~/.gdbinit，省得每次敲。

四、断点：break 与 tb #

断点是 GDB 里用得最多的命令，也是新手第一个坑：break 只是「登记」了一个断点，程序根本没跑，必须再敲 run 或 start 才会停。最省事的入口是 start：

text
(gdb) start
Temporary breakpoint 1 at 0x11a8: file demo.c, line 13.
Starting program: /home/user/demo

Temporary breakpoint 1, main () at demo.c:13
13          int a = 5;

start 等于「在 main 第一行下临时断点 + run」。临时断点命中一次自动删除，后面 info break 里看不到它。想停在别处就用 break，简写 b：

text
(gdb) break demo.c:13
Breakpoint 2 at 0x11a8: file demo.c, line 13.
(gdb) break change
Breakpoint 3 at 0x1149: file demo.c, line 5.
(gdb) break 17
Breakpoint 4 at 0x11c9: file demo.c, line 17.

四种定址方式：break 行号 指当前文件那一行（多文件项目容易下错地方）；break 文件名:行号 明确到文件，最稳；break 函数名 停在入口；break *地址 停在裸地址，反汇编时用，地址前必须有 *。

命令格式 作用 用在哪
break 行号 / break 函数名 当前文件某行 / 函数入口 单文件小 demo
break 文件名:行号 指定文件的指定行 多文件项目，推荐
break *0x... 内存地址处 没有源码、看反汇编时
break 行号 if 条件 条件断点，为真才停 大循环里只抓第 N 次
tbreak / tb 临时断点，命中一次删除 只想停一次
rbreak 正则 给匹配的函数批量下断点 一族函数一起看
info breakpoints / info break 列出所有断点、观察点 断点乱了先看这个
clear 行号 / delete 编号 按行号清除 / 按编号删除 delete 不带编号删全部
disable 编号 / enable 编号 保留但失效 / 重新生效 临时关掉，还要用回来
enable once 编号 / enable delete 编号 命中一次后失效 / 删除 介于临时与普通之间
ignore 编号 次数 跳过前 N 次命中 第 100 次才出问题
condition 编号 条件 给已有断点补条件 下完才想起要过滤

info break 把编号、类型、启用状态、命中次数、位置一次给全：

text
(gdb) info break
Num     Type           Disp Enb Address            What
2       breakpoint     keep y   0x00005555555551a8 in main at demo.c:13
3       breakpoint     keep y   0x0000555555555149 in change at demo.c:5

Disp 列 keep 是永久断点，del 是命中后删除（临时断点的标记）；Enb 列 y 启用、n 禁用。编号不因删除而重排，删了 2 号，下一个新建的还是 3 号，别按顺序数。

条件断点值得单独说。循环里出错，你没法手动 continue 一万次：

text
(gdb) break demo.c:22 if buf[i] < 0
Breakpoint 5 at 0x11f0: file demo.c, line 22.
(gdb) ignore 5 9999
Will ignore next 9999 crossings of breakpoint 5.

GDB 每次跑到这行都要对条件求值一次，代价是慢；ignore 直接跳过前 N 次命中，更快。条件表达式本身还能调函数（break demo.c:22 if strcmp(name, "abc") == 0），那 GDB 每次都会真的去调，副作用自己担着。断点下错地方不用删了重来，condition 5 新条件 覆盖即可。

临时断点省事，Disp 直接是 del，跑过一次就消失：

text
(gdb) tbreak change
Temporary breakpoint 6 at 0x1149: file demo.c, line 5.

disable 不带编号作用到全部，配合 enable 3 单独放行某一条。还有个初始化阶段的坑：断点只对「下完之后」的代码生效。想抓 main 之前的东西（全局对象构造、__attribute__((constructor)) 函数、库初始化），start 已经错过了，要在加载可执行文件后、run 之前下断点：

text
(gdb) break some_init
(gdb) run

五、运行控制：run、next、step、continue #

断点下好，程序得跑起来。先摆对照表：

命令 简写 行为 遇到函数调用
run r 从头启动，跑到第一个断点 直接跑到断点
start — 停在 main 第一行 同上
next n 执行到本函数下一行 把整个调用当一步，跳过
step s 执行到下一行 进入被调函数第一行
next N / step N n N / s N 连续执行 N 步 同上规则
continue c 跑到下一个断点或程序结束 不进入
finish — 跑完当前函数，停到调用处 从当前函数弹出
until 行号 / until u 运行到指定行 / 跳出循环 不进入
nexti / stepi ni / si 按机器指令走一步 按指令算
return 值 — 结束当前函数并强制返回指定值 —
jump 行号 j 跳到指定行继续执行 不经过中间代码

step 和 next 的差别是新人最先混的一对，一句话：next 把「下一行」当单位，函数调用算一行；step 把「下一条指令」当单位，函数调用会被追进去。

停在第 17 行 s = change(&a, b);，敲 n 直接到第 18 行 printf，change 内部干了什么完全不知道：

text
(gdb) start
Temporary breakpoint 1, main () at demo.c:13
13          int a = 5;
(gdb) next
14          int b = 8;
(gdb) next
17          s = change(&a, b);
(gdb) next
18          printf("a=%d b=%d s=%d\n", a, b, s);
(gdb) p a
$1 = 8

三次 next 一路平推到 printf，停在 18 行时 a 已经是 8。这就是 next 的性格：只看主线，不看细节。

同一行换 step，程序钻进函数内部：

text
(gdb) start
(gdb) step
14          int b = 8;
(gdb) step
17          s = change(&a, b);
(gdb) step
change (a=0x7fffffffdc4c, b=8) at demo.c:5
5           int t = *a;

停下来的那一行是 change 函数体的第 5 行，上面那行 change (a=0x7fffffffdc4c, b=8) 是 GDB 回显的入参——实参已经赋给形参：a 拿到的是 main 里 a 的地址，b 拿到的是 8，断点同时定位到函数体第一条语句。

两者的分界不看源码行，看「这一行有没有函数调用」。纯赋值、纯算术，n 和 s 行为一样；差别只在调用点。实战节奏是：主线用 n 快速推进，到起疑的调用处换 s 钻进去。

一个特例：库函数也照进不误。在 printf 那行敲 s，你会掉进 glibc 的 printf，栈里全是 __printf 之类的帧，想出来得靠 finish。这时候该用 n，或者临时断点 tbreak printf 再 continue。

continue 是最常用的加速键：设两个断点，c 两次，两个位置依次停一遍。

text
(gdb) continue
Breakpoint 3, change (a=0x7fffffffdc4c, b=8) at demo.c:5
(gdb) continue
Breakpoint 4, main () at demo.c:17

GDB 有个默认约定：从一次 continue 或 step 开始，后续连续的 continue 不会重复命中同一个断点，你一定能往前走，不会原地打转。finish 是「退出当前函数」的正规做法，附带返回值：

text
(gdb) finish
Run till exit from #0  change (a=0x7fffffffdc4c, b=8) at demo.c:5
17          s = change(&a, b);
Value returned is $2 = 5

$2 是便捷变量，后面能 print $2 反复引用。until 用在循环里最省事，从循环体里敲，一直跑到循环条件不成立之后那行，中间碰到的断点照样会停；写成 until 25 就是跑到第 25 行。

参数传错、程序跑飞了想重来，run 就行；GDB 会问是否重新开始，脚本里加 set confirm off 就不问。run 后面跟参数等价于 set args 参数 && run，run 10 20 启动的就是带参数的版本。

程序卡住不动，怀疑死循环或阻塞在系统调用，别干等，Ctrl+C 打断：

text
^C
Program received signal SIGINT, Program terminated.

在 GDB 里按 Ctrl+C 只中断程序，不退出 GDB；被打断后先 bt 看卡在哪一层，这是排查卡死的第一步动作。最后是 nexti / stepi，按机器指令走，配合 layout asm（TUI 模式，Ctrl+X A 切换）能看清每步寄存器怎么变。搞不清「这行源码编译成了什么」时用它。

六、查看代码：list 与源码路径 #

list 是 l，默认显示当前位置附近 10 行。后续每次 list 接着往下刷 10 行；回车不敲命令也一样，GDB 重复上一条命令——这是它最省手的设定：

text
(gdb) list
1       #include <stdio.h>
2
3       int change(int *a, int b)
4       {
5           int t = *a;
6           *a = b;
7           b = t;
8           return t;
9       }
10
命令 显示什么
list / list - 当前位置往下 / 往上 10 行
list 20 / list 13,25 第 20 行上下 / 第 13 到 25 行
list main / list change 指定函数
list demo.c:13 指定文件的行
set listsize 20 / show listsize 改 / 查每次显示行数
info line 17 第 17 行对应的地址范围
info source / info sources 当前源码信息 / 所有已加载源码

info line 是查「这行有没有代码」的顺手命令。断点下在某行没停下来，先查它：

text
(gdb) info line 16
No line 16 in file "demo.c".

第 16 行是空行，没生成任何指令，断点自然落不下去。GDB 会把断点自动挪到下一行有指令的位置并提示：Breakpoint 7 at 0x11c9: file demo.c, line 17.

源码路径是 list 最常出错的地方。GDB 记的是编译时的绝对路径，换机器、挪目录、Docker 里挂载进来，路径就对不上：

text
(gdb) list
13      /root/project/demo.c: No such file or directory.
(gdb) dir /home/user/src
Source directories searched: /home/user/src:$cdir:$cwd

dir 可以叠很多层，show directories 看当前列表，dir 不带参数清空。$cdir 是编译时记录的目录，$cwd 是当前工作目录。

永久解决就编译时改掉路径，GCC 7 以上支持：

bash
gcc -g -O0 -fdebug-prefix-map=/root/project=. demo.c -o demo

二进制里记录的 /root/project/demo.c 变成 ./demo.c，换个目录也能找到。老 gcc 没这个选项，退回 dir。前缀成批替换用 set substitute-path，意思是调试信息里记的旧前缀，实际去新前缀读：

text
(gdb) set substitute-path /root/project /home/user/src

CI 机器上编、本机上调，就靠它。set sysroot 是交叉编译和嵌入式场景用的，把目标机根目录指到本地拷贝上，归 嵌入式调试手段 那篇。

info source 还能反查这份文件是怎么编的：

text
(gdb) info source
Current source file is demo.c
Compilation directory is /home/user
Contains 20 lines.  Source language is c.
Producer is GNU C17 12.1.0 -mtune=generic -march=x86-64 -g -O0.

Producer 那行直接告诉你有没有 -g、优化级别多少。怀疑「我明明加了 -g」，先看这里。源码实在没有，还有兜底手段：反汇编。

text
(gdb) disassemble main
   0x00005555555551a9 <+8>:     movl   $0x5,-0x4(%rbp)
   0x00005555555551c9 <+40>:    call   0x555555555149 <change>
End of assembler dump.

disassemble /m main 把源码混在汇编里显示，/r 带机器码字节。没有源码时这是唯一出路，也是确认「这行源码编译成了哪几条指令」的最终手段。

七、查看变量与表达式 #

print 是 p，GDB 里第二大常用命令。

text
(gdb) start
Temporary breakpoint 1, main () at demo.c:13
13          int a = 5;
(gdb) print a
$1 = 32767
(gdb) next
14          int b = 8;
(gdb) print a
$2 = 5
(gdb) print change
$3 = {int (int *, int)} 0x555555555149 <change>

为什么不是 5？程序刚停在 int a = 5; 这行还没执行，a 所在的位置是栈上的垃圾值，往下走一步它就正了。print a + b 这类算式同样能算。

print 吃整个 C 表达式：成员访问、指针解引用、类型转换、函数调用都能算，函数名本身也能打印成「类型 + 地址」。格式修饰用 p/x（十六进制）、p/d（十进制）、p/c（字符）、p/s（字符串）。

& 和 0x 这对符号贯穿整个调试过程：

text
(gdb) print &a
$5 = (int *) 0x7fffffffdc4c
(gdb) print &b
$6 = (int *) 0x7fffffffdc50

& 是取地址，print &a 拿到变量 a 自己的内存地址；0x 是十六进制前缀，地址一律用这个形式表示。两个地址差 4 字节，正好是一个 int，栈上 b 紧挨在 a 下面。

指针和「地址里存的值」必须分清：

c
int b = 8;
int *pa = &b;     /* pa 存的是 b 的地址 */
int t1 = *pa;     /* t1 = 8，取地址里的值 */
int *t2 = pa;     /* t2 = 0x7fffffffdc4c，取地址本身 */

* 是解引用，取「地址里存的值」；不带 * 就是「地址本身」。差一个星号，结果差一个整数和一片内存。在 demo 里看对应关系：

text
(gdb) break change
(gdb) continue
Breakpoint 3, change (a=0x7fffffffdc4c, b=8) at demo.c:5
(gdb) print a
$7 = (int *) 0x7fffffffdc4c
(gdb) print *a
$8 = 5

形参 a 是 int *，本身是个地址，*a 才是它指向的整数 5。这就是「传指针不等于传值」：形参拿到的是地址，不是值。地址里那串十六进制数字每次跑都不一样（ASLR 会随机化栈基址），换成别的机器更是另一组数，看关系即可。

看内存内容用 x（examine），格式是 x/NFU 地址：N 是输出几个，F 是格式，U 是单位。

text
(gdb) x/3d 0x7fffffffdc4c
0x7fffffffdc4c: 5       8       32767

拆开读：x 是命令，/3 连续输出 3 个值，d 表示用十进制输出，三者缺一不可。

格式 含义 示例输出
x 十六进制 0x5
d 有符号十进制 5
u 无符号十进制 5
c 字符 5 '\005'
f 浮点 3.14
s 字符串 "abc"
a 地址 0x7fffffffdc4c
i 反汇编一条指令 mov eax,0x5

单位字母：b 单字节、h 双字节（2）、w 四字节（4）、g 八字节（8）。不写单位时按上次格式走，第一次默认 w。几个常用组合：

text
(gdb) x/12xb 0x7fffffffdc4c    # 12 个字节，看内存布局
0x7fffffffdc4c: 0x05    0x00    0x00    0x00    0x08    0x00    0x00    0x00
(gdb) x/4dw &a                 # 地址参数直接写表达式
(gdb) x/4i $pc                 # 从当前指令往后反汇编 4 条
(gdb) x/s 0x555555556004       # 当字符串打印

5 和 8 在内存里都是小端排列：05 00 00 00 就是 5。x 最实用的场合是数组越界：int buf[4] 越界写到第 5 个元素，x/8dw buf 一眼看到第 5、6 个槽里躺着什么，是不是踩了别人的栈。这类内存问题的完整排查归 内存问题与泄漏检测 那篇，这里只留手段。

除了 print，还有两条习惯值得养成。一是 display，让表达式每次停下来自动打印：

text
(gdb) display a
1: a = 5
(gdb) display b
2: b = 8
(gdb) next
14          int b = 8;
1: a = 5
2: b = 8

print 只在你敲的时候算一次，display 是持续监视，循环里盯关键变量就用它。配套命令：info display 列出所有自动显示项，undisplay 编号 或 delete display 编号 删掉某一项，disable display 编号 / enable display 编号 暂时关闭和恢复。

二是 whatis 和 ptype 查类型，前者给类型名，后者给完整定义：

text
(gdb) whatis a
type = int
(gdb) ptype struct Point
type = struct Point {
    int x;
    int y;
}

结构体成员直接点出来，set print pretty on 让嵌套结构体按缩进换行，不开这个多层结构体没法看。数组切片用 @，它是 GDB 特有的「从这块地址开始取 N 个」，指针指向的数组、malloc 出来的缓冲区只能靠它看：

text
(gdb) print p.x
$9 = 1
(gdb) print *p
$10 = {x = 1, y = 2}
(gdb) print buf[2]@3      # 从 buf[2] 起取 3 个
$11 = {3, 4, 5}

寄存器也是变量的一种：info registers 打全部快照，p $pc 单独取指令指针，x/i $pc 看当前指令。变量名找不到时，先怀疑三件事：编译没带 -g、当前不在那个作用域、名字被优化掉了。前两个好查（info source、bt），第三个只能靠 -O0 重编。

八、调用栈：bt 与 frame #

bt（backtrace）打印调用栈，每层一行，编号 0 是最内层，也就是你此刻停着的函数。

text
(gdb) break change
(gdb) continue
Breakpoint 3, change (a=0x7fffffffdc4c, b=8) at demo.c:5
(gdb) bt
#0  change (a=0x7fffffffdc4c, b=8) at demo.c:5
#1  0x00005555555551ce in main () at demo.c:17

读法：编号 0 是 change，定位在第 5 行；编号 1 是 main，定位在第 17 行，也就是调用 change 的那一行。编号 0 在最上层，所以「你现在在 change 里」；行号随代码走，换一份源码就是另一组数字。

frame（简写 f）切换上下文，进去之后 print、list、info locals 全按那一层算：

text
(gdb) f 1
#1  0x00005555555551ce in main () at demo.c:17
(gdb) info locals
a = 8
b = 8
s = 5

停在 0 号帧时 info locals 只有 t，看不到 main 的 a、b——作用域按帧算，这也是「变量名找不到」的第二个原因。info args 打当前帧的入参，info locals 打局部变量。

命令 作用
bt / backtrace 打印完整调用栈
bt 3 / bt -3 只看最内 3 层 / 最外 3 层
bt full 每层附带局部变量值
frame N / f N 切到第 N 层
up / down 上一层 / 下一层
info frame 当前帧详情，含栈地址与保存的寄存器
info args / info locals 当前帧的入参 / 局部变量
info stack / info reg 堆栈情况 / 寄存器快照

崩溃现场靠 bt 吃饭。core 文件加载后第一条命令永远是 bt：

text
$ gdb ./demo core
Program terminated with signal SIGSEGV, Segmentation fault.
#0  0x0000555555555160 in change (a=0x0, b=8) at demo.c:5
5           int t = *a;

a=0x0 直接告诉你空指针被解引用了，第 5 行 *a 是肇事点。剩下的排查流程在 段错误与 core dump 那篇。bt 还有一个诊断价值：栈被越界写坏时输出会乱跳——函数名对不上调用关系、地址是乱的、层数明显过多，这时先怀疑栈溢出，用 x 看栈区原始字节，别急着相信 bt 的每一行。

九、监视点 watch #

断点看「代码走到哪」，监视点看「数据什么时候变」。watch 盯一个变量，值变了就停：

text
(gdb) break main
(gdb) run
Breakpoint 1, main () at demo.c:13
(gdb) watch a
Hardware watchpoint 2: a
(gdb) continue
Hardware watchpoint 2: a

Old value = 5
New value = 8
change (a=0x7fffffffdc4c, b=8) at demo.c:6
6           *a = b;

GDB 把「谁改的」直接报给你：旧值 5、新值 8，改动发生在 demo.c:6 的 *a = b;。这是查「变量莫名被改」最快的路径，比在可疑位置撒断点快得多。

命令 触发条件
watch 变量 被写时停
rwatch 变量 被读时停
awatch 变量 被读或被写都停
info watchpoints 列出所有监视点

watch 靠硬件观察点实现，x86 上一共 4 个槽位，同时挂 5 个 GDB 会报错，删掉不用的再挂。软件观察点极慢（单步跑完全程比对值），硬件槽位不够时 GDB 才会退到那条路。

两个实操细节。一是 watch 要求变量在作用域内，程序还没进 main 时 watch a 会报 No symbol "a" in current context.，先 break main、run，等 a 可见了再 watch。二是表达式也能 watch：watch buf[3] 盯数组元素，watch *p 盯指针指向的内容，watch p != NULL 在指针第一次被赋值时停。删监视点和删断点共用 delete 编号，编号在一套体系里。

十、多线程调试 #

多线程程序一跑起来，bt 只给你一个线程的栈，先要把线程列表打出来。

text
(gdb) info threads
  Id   Target Id                                  Frame
* 1    Thread 0x7ffff7d8f740 (LWP 12034) "demo"   main () at demo.c:17
  2    Thread 0x7ffff7d8e700 (LWP 12035) "demo"   worker (arg=0x7fffffffd) at demo.c:31
  3    Thread 0x7ffff7d8d700 (LWP 12036) "demo"   worker (arg=0x0) at demo.c:33

前面带 * 的是当前线程。每个线程停在哪一行，在这张表里一字排开，比翻日志快。thread N 切过去，之后 bt、print、list 都按那个线程算：

text
(gdb) thread 2
[Switching to thread 2 (Thread 0x7ffff7d8e700 (LWP 12035))]
#0  worker (arg=0x7fffffffd) at demo.c:31
(gdb) thread apply all bt

thread apply all bt 是多线程 bug 的起手式，死锁和卡死时把所有线程的栈拉出来，看谁拿着锁在等谁。断点只对某线程生效，把 thread 写进断点定义：

text
(gdb) break demo.c:31 thread 3
Breakpoint 4 at 0x11c0: file demo.c, line 31

不带 thread 则任何线程命中都停，哪来的在 info threads 里查。线程调度也能控：

text
(gdb) set scheduler-locking on      # 只让当前线程跑，其它冻住
(gdb) set scheduler-locking step    # 单步时只当前线程跑
(gdb) set scheduler-locking off     # 恢复自由调度

调多线程逻辑时先 on，把其它线程冻住，眼前的执行流才可控；查并发 bug 时反而要 off，让竞态露出来。不设这个开关，一个断点上停了四个线程，你敲 next 都不知道是哪个在动。

info threads 里 Id 是 GDB 的线程号，Target Id 里的 LWP 是内核线程号，两者不是一回事。命令行上没有 GDB 时用 ps -L -p PID 看 LWP，再 attach 上去用 info threads 对号。

十一、改变程序状态：set 与 jump #

调试不光能看，还能改。改完继续跑，等于「假设这里是对的，后面会怎样」。改变量：

text
(gdb) set var a = 100
(gdb) print a
$1 = 100
(gdb) print a = 200      # print 后面跟赋值，赋值真的会发生
$2 = 200

set var 是完整写法，set a = 100 也行，GDB 会自己猜；print a = 200 最省手，返回值是赋值后的结果。改寄存器同理：set var $rax = 0，而 set $pc = 0x5555555551c9 就是跳转。

set 系列的环境类命令也在这一族里：set args / show args 管运行参数，set width 和 set height 管输出尺寸，set pagination off 关分页，set confirm off 关二次确认，set print pretty on 让结构体多行打印，set print elements 0 让数组和字符串不截断，cd 切工作目录，shell 执行 shell 命令。

jump（简写 j）直接跳到指定行，中间代码一概不执行：

text
(gdb) break demo.c:17
(gdb) run
(gdb) jump 19
Continuing at 0x5555555551d8.
19          return 0;

跳过去之后 a、b、s 全是跳之前的值，因为第 18 行的 printf 没执行。这就是 jump 的边界：它改的是指令指针，不补执行中间代码。栈上的局部变量不会重新初始化，跳进另一分支时那些变量是脏的。优化过的代码里 jump 尤其不可靠，行号与指令早不是一一对应。

return 换一种思路，不跳行，直接结束当前函数并给一个返回值：

text
(gdb) return 42
Make change return now? (y or n) y
#0  main () at demo.c:17

return 42 让 change 立刻返回 42，s 拿到的就是这个值，函数体剩下的代码一行都不跑。测「如果这个函数返回异常值，上层会不会处理」时，用它比改代码重编快。

call（或 print 函数(...)）在当前位置同步执行一个函数：

text
(gdb) call change(&b, 99)
$3 = 8
(gdb) print b
$4 = 99

call 是真的把函数跑一遍，内存会被改动，拿它做验证前先确认副作用可控，别在一个 free 过的指针上 call。改程序状态改的是内存里的值，不是源码，下次 run 一切还原。

十二、GDB 的命令文件与自动化 #

手动敲几十条命令调一个 bug，下次复现还得重敲。GDB 允许把命令写成文件，启动时批量执行。~/.gdbinit 是全局初始化文件，每次启动都读：

text
set pagination off
set width 0
set confirm off
set print pretty on

项目目录下也可以放 .gdbinit，GDB 默认不读项目里的（有安全考虑），要读得在全局文件里加 set auto-load safe-path /。或者启动时显式指定命令文件：

bash
gdb -x setup.gdb ./demo

setup.gdb 里就是普通命令，一行一条，比如 break change、break demo.c:17、run、bt、info locals；会话中途加载用 source setup.gdb。

断点上挂命令序列更实用，命中断点时自动跑：

text
(gdb) break change
(gdb) commands 1
Type commands for breakpoint(s) 1, one per line.
End with a line saying just "end".
>silent
>printf "hit change, a=%p b=%d\n", a, b
>bt 2
>continue
>end

silent 抑制「Breakpoint 1, change(...)」那行回显，printf 打自定义格式（只支持 %d、%x、%s、%p、%c），continue 让程序自己往下走。整套挂上去，一个断点就变成了探针，跑完一次拿到一条干净的执行轨迹。

自定义命令用 define，把一串常用动作包成一个词：define dumpstate 之后依次输入 bt、info locals、info args，最后一行 end 收尾，此后敲 dumpstate 就等于连跑这三条。define 出来的命令带参数用 $arg0、$arg1 取，document dumpstate 写说明，help dumpstate 就能看到。

完全非交互的跑法，塞进 CI 或者脚本：

bash
gdb -batch -ex run -ex bt -ex "info locals" ./demo

-batch 表示跑完就退，-ex 后面跟一条命令，可以叠很多个。程序崩溃时退出码非 0，所以 gdb -batch -ex run -ex bt ./demo > crash.log 2>&1 能直接塞进 if ! 判真假。

要把会话完整存下来用自带日志，老版本是 set logging on / set logging off，新版本是 set logging enabled on，配 set logging file session.log 指定文件名。日志里带上所有命令和输出，贴进 issue 比截图强。
