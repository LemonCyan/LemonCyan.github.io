一、嵌入式调试难在哪 #

写代码这么多年，有个结论没变过：没有百分之百正确的代码。结果一不符合预期，就得知道问题出在哪。

在 PC 上写应用，这件事不难。模拟器、调试器随便用，每一行代码的执行过程和执行结果都能跟到，找问题只是花时间。

换到嵌入式，麻烦立刻出现。核心只有一个词：可观测性差。

具体差在四个地方。

第一，没有输出界面。 PC 上你可以 printf、可以弹窗、可以看返回值。板子上电那一刻，串口还没配好，屏幕还没点亮，你手里什么输出都没有。

第二，不能随手挂调试器。 量产机器上根本没有调试口。开发板上就算有，也得预留排针、得插得上、得电脑在旁边。生产现场、客户机房里，这些条件一个都不满足。

第三，跑飞了看不到现场。 PC 上进程崩了有 core dump，栈、寄存器、信号全给你存下来。单片机上跑飞，一个 HardFault 进来，默认处理函数往往是个死循环，你连它停在哪都不知道，更别说为什么停。

第四，时序问题不重现。 中断晚到 3 微秒、SPI 时钟多一个毛刺、某段代码偶尔超时——这些在单步调试下根本不出现，因为你一按暂停，整个世界都停了。

把这几条合起来说：PC 上你是站在程序外面看它，嵌入式里你是埋在程序内部往外爬。你能看到的东西，只有你事先埋好的那几个点。

反过来讲，这也说明了一件事：嵌入式调试的能力上限，不取决于你的工具多贵，取决于你事先留了多少观测口。

维度 PC 应用 嵌入式目标
输出 终端、文件、弹窗 串口、LED、GPIO 引脚
现场保存 core dump 自动落盘 栈上几个字，得自己取
调试器 随时 attach 有接口才能用，无接口只能烧写
断点代价 停一个线程 停整个系统，时序全变
复现难度 日志重放即可 时序相关，断电就没了
观测口 想加就加，重新编译 影响时序和体积，加之前要想清楚

二、两种基本手段：硬件调试器与日志 #

在嵌入式环境下，能用的手段无外乎两种，这句是行业里说了几十年的老话：

  1. 使用硬件仿真器定位问题；
  2. 使用日志输出定位问题。

对嵌入式工程师，特别是 Linux 工程师来说，硬件仿真器的麻烦不少：成本高，没法保证人手一个；硬件连接复杂，板子上得预留特定接口；用起来也不方便，插拔、驱动、权限一堆事。所以日志输出几乎成了主要的、很多时候是唯一的调试手段。

但总会有例外，而且这个例外很要命：

系统刚刚启动，在日志输出的通道（多数时候是 UART 接口）ready 之前，怎么 debug？

这时候日志还没通，仿真器又不一定插得上。在不得不翻出仿真器之前，还有一个很土但极好用的办法：点 LED 灯。

两种手段摆在一起，各自的位置很清楚。

对比项 硬件调试器（JTAG/SWD） 日志输出（UART/日志缓冲）
看的是什么 活的现场：寄存器、内存、调用栈 你主动打印的东西
需要硬件 需要调试接口和 probe 只需要一根串口线或一块缓冲
侵入性 断点会停整个系统 占用 CPU 和通道带宽
早期可用性 接口起了就能用 要等通道 ready
看时序问题 基本没用，一停就失真 有干扰但能看趋势
量产设备 一般没有接口 有串口就能用，或者看存储的日志
成本 一个 probe，几块到几千 接近零

日志之所以成为主食，还有一个没法明说的理由：它让你在客户现场也能取证。仿真器做不到这一点，你不会背着 probe 去每个出问题的现场。

但日志有它的死穴，就是开头 ready 之前那一段。u-boot、内核早期初始化、电源管理芯片的启动时序，全在这段时间里。所以真正完整的手段清单，是三层：

  1. 日志通道 ready 之前——LED、GPIO；
  2. 日志通道 ready 之后——串口日志、环形缓冲；
  3. 日志也说不清的时候——上调试器、上示波器。

三、JTAG 与 SWD #

硬件调试器不是一个东西，背后是几种不同的调试接口。ARM 体系里最常遇到两种：JTAG 和 SWD。

JTAG 是老资格，边界扫描出身，五根线：TCK 时钟、TMS 状态机、TDI 数据进、TDO 数据出、TRST 复位（可选）。它能串成一链，一块板子上多个芯片共用一组线，这在多芯片系统里有用。

SWD 是 ARM 后来推的两线接口，只用 SWCLK 和 SWIO。它复用 JTAG 的 TCK 和 TMS 两根引脚，所以同一组排针可以两种模式都支持，靠时序切换。Cortex-M 上 SWD 是默认选择。

对比项 JTAG SWD
引脚数 5（TCK/TMS/TDI/TDO/TRST） 2（SWCLK/SWIO）
引脚复用 独立四线 复用 TCK/TMS
最高速率 与器件和走线相关 与器件和走线相关，短线上更容易跑高
占板面积 大 小，两针排针就够
常见场景 老平台、多芯片、FPGA 旁 Cortex-M、小体积板卡

接线这件事，坑比参数多，列几条实打实的。

GND 一定要接，而且别只接一根细线。 调试器掉线、识别不到芯片，八成先查地。

目标板要自己供电，别用 probe 的电。 probe 的电带不动整板，一带就复位。同时确认两边电平一致，3.3V 目标接 5V probe 会出事。

复位线建议接上。 只接 SWCLK/SWIO/GND 也能连，但一旦程序把时钟配错、把调试引脚复用成普通 GPIO，就只能靠复位引脚把芯片拽回来。有的板子还得勾「connect under reset」。

低功耗模式会关掉调试口。 芯片进 deep sleep 后调试口掉线是正常现象，不是坏了。调试期间先把低功耗关掉。出厂设了读保护（RDP、安全启动）的芯片同理，probe 连上也只能看到一片空白，别怀疑线。

四、调试器能做什么、不能做什么 #

probe 买回来，很多人只用来烧程序，其实它能干的事不少。

能做的：

  • 单步执行、源码级断点、条件断点
  • 看和改任意内存、任意寄存器，包括外设寄存器
  • 看调用栈，还原函数调用链
  • 看变量，包括全局变量和局部变量（要符号表）
  • 在线烧写、擦除、读回校验
  • 半主机（semihosting）输出，用调试通道代替串口打印
  • 数据观察点（watchpoint），某个地址被写就停下来

做不了的，或者说做了会骗你的：

  • 测时间。 断点一停，CPU 停了，定时器还在跑，中断还挂着，你测出来的耗时全是假的。
  • 看真实时序。 单步走一段中断密集的代码，中断的到达时刻完全变了。
  • 长期在线。 probe 长时间挂着，USB 掉线、驱动崩、调试会话断了是常态。客户现场靠它取证不现实。
  • 看低功耗下的行为。 一进 sleep 就掉线。
  • 没有符号表的时候看变量。 优化过的代码，变量被塞进寄存器，-O2 下看局部变量经常是 <optimized out>。
  • 多核异构系统的全局视图。 一个 probe 管一个核，核间交互得靠别的手段。

结论就是一句话：调试器适合回答现在是什么状态，不适合回答「刚才发生了什么」。后一个问题要交给日志和示波器。

五、串口日志：最常用的手段 #

串口日志是嵌入式的 printf，115200 8N1 是绝大多数板子的默认配置。它的价值不在于好看，在于它几乎是唯一能在几秒钟内加上的观测手段。

关键在于早期日志怎么写。系统刚起来的时候，中断没配、DMA 没初始化、缓冲区还没分配，你不能调用一个依赖这些的打印函数。

早期日志只有一条路：轮询发送。

c
/* 早期调试输出：不依赖中断、不依赖 DMA、不依赖任何动态内存 */
#define UART_EARLY_BASE   0x10000000u   /* 板级定义，改成本板的地址 */
#define UART_THR          0x00u
#define UART_LSR          0x14u
#define UART_LSR_THRE     0x20u

static inline void early_putc(char c)
{
    volatile unsigned char *base = (volatile unsigned char *)UART_EARLY_BASE;

    /* 等到发送保持寄存器空，再加超时，避免串口没初始化时死等 */
    for (unsigned int i = 0; i < 100000u; i++) {
        if (base[UART_LSR] & UART_LSR_THRE)
            break;
    }
    base[UART_THR] = (unsigned char)c;
}

void early_puts(const char *s)
{
    while (*s) {
        if (*s == '\n')
            early_putc('\r');
        early_putc(*s++);
    }
}

void early_hex32(unsigned int v)
{
    static const char hex[] = "0123456789abcdef";
    early_puts("0x");
    for (int i = 28; i >= 0; i -= 4)
        early_putc(hex[(v >> i) & 0xf]);
}

这段代码的三个要点，值得单独说。

用轮询，不用中断。 中断控制器还没初始化，中断一开就进错向量表。

加超时。 串口时钟还没使能的时候，THRE 永远不会置位，纯等待就是死循环。加了超时，至少还能往下走。

自己转 \r\n。 裸串口不认 \n，终端会显示成阶梯状，看着难受。

日志通了之后，还有一堆坑。

  • 日志本身改变时序。 一条 80 字符的日志，115200 下要 7 毫秒左右。你在中断里打一条，中断就多了 7 毫秒。查到问题就赶紧删掉。
  • printf 不可重入。 主循环和中断都在打印，输出就会互相插字。要么加锁，要么中断里用一个独立的无锁单字符输出。
  • 浮点格式化会让代码体积暴涨。 为了让 %f 能用，链接进来几 KB 的库，小 flash 的片子直接爆。
  • 日志缓冲区被踩了。 打印出来是乱码，先别怀疑串口线，先怀疑有人越界写了你的缓冲区。
  • 日志分级没做好。 上线前关不掉，最后靠 #if 0 一个个注释，注释错了就是一次事故。

六、日志要输出什么 #

日志写得多不等于有用。一堆 enter func、exit func 打印了几百行，真出问题时你翻五分钟找不出关键那一行。

给日志定个格式，逼自己写全字段。

字段 为什么需要 缺了会怎样
时间戳 判断先后、算间隔、找慢在哪 说不清两个事件谁先谁后
位置 文件名与行号，或用模块编号 不知道是哪段代码打的
级别 错误、警告、信息、调试 上线时关不掉，或者全关掉了
事件 做了什么，一句话说清 只有一串数字，看不懂
关键值 出错时的入参、返回值、状态码 知道了位置还是不知道为什么
上下文 重试次数、队列长度、连接状态 单条日志看不出趋势

时间戳这件事有讲究。上电到日志通道 ready 之间没有墙钟，只能用启动后的计数值。等系统有了 RTC 或者网络时间，再把早期日志的时间戳换算过去，否则后面对不上。

别在日志里调业务函数，这是最常见的一类自杀。

c
/* 反例：这条日志本身就能把系统搞挂 */
LOG_INFO("config = %s", get_config_string());

get_config_string() 里如果加锁，而日志又在中断上下文里打的，直接死锁。日志只打印已经在手里的值。

c
/* 正例：先取值，再打印，值不好打就打个地址或长度 */
const char *p = get_config_string();
LOG_INFO("config=%p", (void *)p);

产线上取不到串口的时候，环形缓冲就派上用场了。把日志写进一块固定大小的数组，崩了之后重启，从 RAM 里捞出来。

c
#define LOG_BUF_SIZE  4096u

static char     g_log_buf[LOG_BUF_SIZE];
static unsigned g_log_head;          /* 写位置 */
static unsigned g_log_tail;          /* 覆盖时丢掉的最老位置 */

static void log_push(char c)
{
    unsigned next = (g_log_head + 1u) % LOG_BUF_SIZE;

    if (next == g_log_tail)              /* 满了，丢掉最老的一个字节 */
        g_log_tail = (g_log_tail + 1u) % LOG_BUF_SIZE;

    g_log_buf[g_log_head] = c;
    g_log_head = next;
}

这块内存要是放在不掉电区域（备份 SRAM、带电池的 RAM），掉电重启后内容还在，一次复位能留下完整现场。这是嵌入式里最接近 core dump 的东西。

还有一条经验：日志要在出错时才有信息量，在正常时尽量安静。 只打「我进来了」，等于没打。

七、LED 打点：最原始的断点 #

先把这套方法完整说一遍。它简单到不像个方法，但真管用。

1）单 LED。 如果系统只有一个 LED，就在代码里正确执行完某一个步骤之后点亮它。以此类推，一步一步检查代码执行得对不对。灯亮了，说明这一步过了；灯不亮，说明卡在上一步和这一步之间。

2）多 LED 编码。 如果系统有多个 LED，例如四个，就可以把这四个 LED 编码成一个 4bit 的数字（0~15），表示更多状态。四个灯能表达十六种位置，够你把一段启动代码切成十几段来定位。

下面是 X Project 基于 bubblegum-96 平台实现的一个简单接口：

c
/* https://github.com/wowotechX/u-boot/blob/x_integration/board/actions/bubblegum/board.c */

/*
 * A simple debug function for early debug, in which,
 * we use four LEDs to display sixteen debug codes, from 0 to 15.
 * Using it, we can know, at least roughly, at where our code is run.
 */
void bubblegum_early_debug(int debug_code)
{
    uint8_t val;

    val = debug_code & 0x1;
    setbits_le32(GPIOA_OUTEN, 1 << DEBUG_LED0_GPIO);
    clrsetbits_le32(GPIOA_OUTDAT, 1 << DEBUG_LED0_GPIO,
            val << DEBUG_LED0_GPIO);

    val = (debug_code >> 1) & 0x1;
    setbits_le32(GPIOA_OUTEN, 1 << DEBUG_LED1_GPIO);
    clrsetbits_le32(GPIOA_OUTDAT, 1 << DEBUG_LED1_GPIO,
            val << DEBUG_LED1_GPIO);

    val = (debug_code >> 2) & 0x1;
    setbits_le32(GPIOF_OUTEN, 1 << DEBUG_LED2_GPIO);
    clrsetbits_le32(GPIOF_OUTDAT, 1 << DEBUG_LED2_GPIO,
            val << DEBUG_LED2_GPIO);

    val = (debug_code >> 3) & 0x1;
    setbits_le32(GPIOF_OUTEN, 1 << DEBUG_LED3_GPIO);
    clrsetbits_le32(GPIOF_OUTDAT, 1 << DEBUG_LED3_GPIO,
            val << DEBUG_LED3_GPIO);
}

代码逻辑本身不复杂：把 debug_code 的四个 bit 分别摊到四个 GPIO 上，先使能输出，再改电平。注意 OUTEN 每次进来都设，是为了防止前面的代码把引脚复用改掉了——早期启动阶段，谁改了什么没人记得。

这段代码的实际用法，看下面这个真实案例。

串口驱动写完之后，发现系统会死在 owl_serial_probe 中。于是照着上面的思路，在每一步后面加一个点灯操作：

c
/* https://github.com/wowotechX/u-boot/blob/x_integration/drivers/serial/serial_owl.c */

extern void bubblegum_early_debug(int debug_code);

static int owl_serial_probe(struct udevice *dev)
{
    /* only for UART2, TODO */
    bubblegum_early_debug(4);

    /* pinmux */
    setbits_le32(MFP_CTL2, 1 << 22);

    bubblegum_early_debug(5);

    /* device clock enable */
    setbits_le32(CMU_DEVCLKEN1, 1 << 8);

    bubblegum_early_debug(6);

    /* reset de-assert */
    setbits_le32(CMU_DEVRST1, 1 << 7);

    bubblegum_early_debug(7);

    /* set default baudrate and enable UART */
    owl_serial_setbrg(dev, 115200);

    /* enable uart */
    setbits_le32(UART2_BASE + UART_CTL, UART_CTL_EN);

    bubblegum_early_debug(8);
    return 0;
}

结果灯停在 4 和 5 之间——LED2 和 LED0 亮，正好是 5（0101）。也就是说，系统执行完了 pinmux 那一步，但在「使能设备时钟」这一步上卡住了：

c
setbits_le32(CMU_DEVCLKEN1, 1 << 8);

单独看这一行，看不出任何问题。它就是在置位一个寄存器。可它偏偏就是死的。经过仔细检查，发现 CMU_DEVCLKEN1 这个寄存器定义错了，多半是抄 Action 的代码时笔误了。

这个案例的价值在哪里？它把一个「系统死在串口驱动里」这种毫无头绪的问题，压缩成了「这一行寄存器定义写错了」这种五分钟能查完的问题。 灯不会告诉你为什么，但它会告诉你在哪。而定位问题这件事，十次里有九次是「找到在哪」比「搞清为什么」更难。

再往上走一步，LED 打点还有一个很少被提起来的价值：它是最便宜的时间戳。

GPIO 翻转不占 CPU、不占串口带宽、不改变中断时序。在函数开头拉高，结尾拉低，用示波器看这个引脚的高电平宽度，你就得到了这段代码的耗时。这比在两个位置各打一条 printf 准得多——因为 printf 本身就要花掉几毫秒，你测出来的是「代码加打印」的时间，不是代码的时间。

所以 LED 或者 GPIO 打点这件事，不只是「亮不亮」的二分信息。它同时是：

  • 一个断点：执行到这就亮，说明走到了；
  • 一个状态码：四个灯，十六种位置；
  • 一个时间戳：翻转配合示波器，量出耗时；
  • 一个活动信号：主循环里循环翻转，灯闪说明系统还活着。

八、GPIO 与示波器配合 #

把 LED 换成任意一个空闲 GPIO，方法立刻从「看状态」升级到「测时间」。因为示波器能测微秒甚至纳秒级的变化，而人的眼睛只能分辨几十毫秒。

用两个宏包住，代码里塞起来不心疼：

c
/* 调试引脚：选一个没被占用的 GPIO，接到示波器探头上 */
#define DBG_PIN_SET()   do { GPIO_OUT |=  (1u << DBG_PIN); } while (0)
#define DBG_PIN_CLR()   do { GPIO_OUT &= ~(1u << DBG_PIN); } while (0)
#define DBG_PIN_TOG()   do { GPIO_OUT ^=  (1u << DBG_PIN); } while (0)

量一段临界区或者一个算法的耗时：

c
void do_something(void)
{
    DBG_PIN_SET();
    /* 被测代码，绝对不要在这里放 printf */
    process_frame();
    DBG_PIN_CLR();
}

示波器上一看，高电平宽度就是 process_frame() 的执行时间。函数被优化掉、被内联、被中断打断，全都在波形里写着。

更值钱的用法是测中断。

c
void TIMER_IRQHandler(void)
{
    DBG_PIN_SET();
    clear_interrupt_flag();
    handle_timer_event();
    DBG_PIN_CLR();
}

你能直接看到三件事：中断多久进来一次、每次处理花多久、两次中断之间主循环还剩多少时间。如果处理时间接近中断周期，系统就是在崩溃边缘跑——这在纯日志里完全看不出来，因为日志本身就在偷时间。

几个必须知道的误差来源：

  • 翻转开销很小但不是零。 一条 GPIO 置位指令加上总线写，几十纳秒量级。测微秒级的东西可以忽略，测几十纳秒的东西就不行。
  • 编译器会重排。 调试宏里的写操作对 volatile 指针做，别让编译器把它优化掉或者挪位置。
  • 波形上的毛刺要分清。 探头接地不好会看到振铃，别把振铃当成代码里的抖动。
  • 一次只能看一个点。 要看两个事件的先后，得用双通道或者逻辑分析仪。

九、逻辑分析仪看时序 #

示波器看的是「电压随时间怎么变」，逻辑分析仪看的是「若干根线上电平的组合随时间怎么变」。嵌入式里排时序问题，后者更顺手。

对比项 示波器 逻辑分析仪
看什么 模拟波形、上升沿、毛刺、噪声 多路数字电平与协议内容
通道数 2~4 路常见 8、16 路起，几十路也有
采样率 高，能看纳秒细节 中等，够看总线时序
协议解码 少量支持 I2C、SPI、UART、CAN 都能解
典型用途 电源纹波、信号完整性、毛刺 总线时序、片选与时钟关系、握手
触发 边沿、脉宽、协议 边沿、码型、协议内容

用它查问题的姿势很直接：把怀疑的几根线全接上，设一个触发条件，等它自己抓到出事那一刻。

几个实际场景：

  • SPI 读不到数据。接上 SCLK、MOSI、MISO、CS 四根线，看片选拉低之后时钟有没有来、时钟来了几个字节、MISO 上是不是全高。全高说明从设备根本没驱动总线。
  • I2C 上设备不应答。看 START 之后的第九个时钟，SDA 是不是被拉低。不拉低就是没 ACK，地址错或者设备没上电。
  • 串口收到乱码。解出来一看波特率偏差，或者帧错误位，就知道是时钟配置偏了还是线太长。
  • 上电时序不对。看复位信号释放和时钟稳定的先后，很多「偶尔起不来」的板子问题都在这。

逻辑分析仪最大的优势是不占 CPU、不改变程序。程序该跑多快还跑多快，你只是在旁边看。这一点是日志和调试器都做不到的。

它的局限也要说清楚：只能看引脚上出现的信号。芯片内部的变量、状态机、队列长度，一根线都看不到。所以它是配合用的，不是替代用的。

十、HardFault 怎么定位 #

Cortex-M 上程序跑飞，最后几乎都会落到 HardFault。默认的 HardFault_Handler 是个空死循环，你只能看到它停了，看不到为什么停。

其实现场没丢。异常发生时，处理器会自动把八个字压到栈上。

顺序（低地址到高地址） 内容
1 R0
2 R1
3 R2
4 R3
5 R12
6 LR（R14），异常发生时的返回地址
7 PC（R15），出错的那条指令地址
8 xPSR

拿到 PC，就能反汇编定位到具体是哪条指令出的错；拿到 LR，就知道是从哪个函数调进去的。

取出这个栈帧的代码，得用汇编写，因为编译器会改栈指针，而且这个函数返回之后就没法再取现场了。

c
/* HardFault 现场还原：把自动压栈的八个字取出来 */
#include <stdint.h>

typedef struct {
    uint32_t r0;
    uint32_t r1;
    uint32_t r2;
    uint32_t r3;
    uint32_t r12;
    uint32_t lr;
    uint32_t pc;
    uint32_t psr;
} fault_frame_t;

void hardfault_report(const fault_frame_t *f);

void HardFault_Handler(void)
{
    __asm volatile (
        "tst   lr, #4          \n"  /* 看 EXC_RETURN 的 bit2 */
        "ite   eq              \n"
        "mrseq r0, msp         \n"  /* bit2=0，用的是主栈 */
        "mrsne r0, psp         \n"  /* bit2=1，用的是进程栈 */
        "b     hardfault_report\n"
    );
}

那两个分支不能省。用 RTOS 的时候，线程跑在 PSP 上，中断跑在 MSP 上。取错栈，看到的就是一堆垃圾。

hardfault_report 里把现场打出去，能打串口打串口，打不出就存进不掉电 RAM：

c
void hardfault_report(const fault_frame_t *f)
{
    early_puts("\n*** HardFault ***\n");
    early_puts("PC = "); early_hex32(f->pc);  early_puts("\n");
    early_puts("LR = "); early_hex32(f->lr);  early_puts("\n");
    early_puts("PSR= "); early_hex32(f->psr); early_puts("\n");
    /* R0~R3 同理，按需打出来 */

    /* 关键：把 PC 落到具体函数和指令上 */
    extern void print_symbol_for(uint32_t addr);
    print_symbol_for(f->pc);

    for (;;)
        ;
}

拿到 PC 之后怎么查？三种办法，从糙到细：

  1. 对着 map 文件找。 链接生成的 .map 里每个函数都有起止地址，PC 落在哪个区间就是哪个函数。
  2. 用工具反查。 arm-none-eabi-addr2line -e app.elf 0x08001a3c，直接给你文件名和行号。
  3. 反汇编看指令。 arm-none-eabi-objdump -d app.elf，找到那个地址，看它是不是在访问一个可疑的指针。

还有一层信息别漏了：故障状态寄存器。Cortex-M 有一组 CFSR、HFSR、MMFAR、BFAR，里面写着是总线错误、用法错误还是存储器管理错误，以及出错的地址。把这些也一起打出来，能省掉一半猜测。

CFSR 位域 含义 常见原因
IACCVIOL 取指违例 跳到了不可执行的区域，函数指针是野指针
PRECISERR 精确数据总线错误 访问了没使能时钟的外设
IMPRECISERR 不精确总线错误 写缓冲导致的晚到错误，最麻烦的一种
UNDEFINSTR 未定义指令 PC 跑飞到了数据区
INVSTATE 非法状态 函数指针的 bit0 为 0，跳转后不是 Thumb 状态
UNALIGNED 非对齐访问 用指针强转读结构体成员

其中 UNALIGNED 和 INVSTATE 这两条，抓到的多半是真正的代码 bug，而不是硬件问题，值得优先看。

最后一句实话：HardFault 是一个结果，不是一个原因。 PC 指到哪，只说明它在哪一刻炸的。真正写坏内存的那行代码，往往在几百条指令之前。所以拿到现场之后，下一步往往是查内存踩踏，也就是第十二章那套办法。

十一、看门狗与死机复位 #

死机这件事在嵌入式里太常见了。板子跑几天，突然不响应，断电重启又是好的。这种问题抓不到现场，装个看门狗至少能让它自己活过来。

看门狗是一个独立计数的定时器，程序必须定期「喂」它。超时不喂，它就复位整个芯片。

类型 特点 适合场景
独立看门狗 独立时钟源，主时钟挂了也能复位 通用兜底，强烈建议开
窗口看门狗 只在特定时间窗口内喂狗才算合法 要求程序节奏严格，防止喂太快
外部看门狗芯片 完全独立于 MCU 高可靠设备、安防、车载

窗口看门狗这个设计值得多说一句。它不只管「别喂太晚」，还管「别喂太早」。如果你的主循环本身已经卡死，却有个中断在按时喂狗，普通看门狗是被骗过去的，窗口看门狗能抓住这种情况。

喂狗的位置是设计问题，不是随手加一句就行。

  • 喂在主循环末尾。 主循环跑完一遍才喂，说明整条逻辑都活着。
  • 别喂在定时器中断里。 主循环死了，中断照样跑，狗照样被喂，看门狗彻底失效。这条几乎每个项目都犯过。
  • 别在多个地方喂。 一个项目里出现三处喂狗，等于没有看门狗。
  • 喂狗前后加个标记。 复位之后能看出是喂得太慢还是根本没喂。

比看门狗本身更有用的是复位之后能知道上一次为什么死的。多数 MCU 都有一个复位原因寄存器，读出来能区分上电、看门狗、软件、引脚、欠压几种情况。

c
/* 复位原因识别 + 启动计数，用于判断「是不是反复重启」 */
void log_reset_cause(void)
{
    uint32_t cause = RESET_CAUSE_REG;

    early_puts("reset: ");
    if (cause & RST_POWER_ON)   early_puts("power-on ");
    if (cause & RST_WATCHDOG)   early_puts("watchdog ");
    if (cause & RST_SOFTWARE)   early_puts("software ");
    if (cause & RST_EXTERNAL)   early_puts("external ");
    if (cause & RST_BROWNOUT)   early_puts("brownout ");
    early_puts("\n");

    /* 启动次数存在不掉电区域，清复位标志之前先加一 */
    boot_count = boot_count + 1;
    if (boot_count > 3) {
        early_puts("reset loop detected, hold here\n");
        for (;;)
            ;
    }
}

那个「重启超过三次就停下来」的判断，实际价值很高。现场设备反复重启，日志还没打出来就被下一次重启冲掉了，永远看不到错误信息。停在原地等人来，比一直重启有用。

排查「为什么被看门狗复位」，思路是这样：

  1. 确认狗超时是多长，主循环正常跑完要多久，两者留没留余量。
  2. 在喂狗处翻一个 GPIO，示波器上看翻转间隔，看它是不是偶尔超时。
  3. 把喂狗间隔和主循环最慢路径对比，找那一段偶发的长耗时。
  4. 拿到复位原因之后，配合不掉电 RAM 里的日志，还原死之前的最后几条。

十二、内存踩踏的排查 #

内存踩踏的症状很好认，也很让人抓狂：

  • 改一个变量，另一个不相干的变量跟着变了；
  • 数组越界之后没报错，但结构体里的指针变成了乱码；
  • 随机 HardFault，PC 指向一个根本不该执行的地方；
  • 单独跑没问题，多任务一起跑就出问题。

原因是有人写了不该写的地方。麻烦在于写坏的地方和爆炸的地方不在一处，中间隔着几百条指令和一个调度周期。

排查手段按由轻到重排：

一、哨兵值（canary）。 在每个缓冲区的头尾各放一个固定图案，定期检查有没有被改。

c
#define CANARY_MAGIC  0xDEADBEEFu

typedef struct {
    uint32_t head;
    uint8_t  data[256];
    uint32_t tail;
} guarded_buf_t;

static guarded_buf_t g_buf = { CANARY_MAGIC, {0}, CANARY_MAGIC };

/* 主循环里定期调用，越界写在哪一次检查时被发现，范围就缩小了 */
void canary_check(void)
{
    if (g_buf.head != CANARY_MAGIC) { early_puts("buffer underrun!\n"); for (;;) ; }
    if (g_buf.tail != CANARY_MAGIC) { early_puts("buffer overrun!\n");  for (;;) ; }
}

head 被改说明有人往前写，tail 被改说明有人往后写。这两个信息指向的方向完全不同，别混。

二、填充图案。 启动时把整块 RAM 填成 0xAA 或者 0x55，用 memset 或者一个四行的循环就够，然后用调试器看内存。没被用到的区域还是一大片 0xAA，被踩的区域会出现零星几个奇怪的字节——那几个字节就是踩踏者留下的指纹。

三、栈使用量测量。 启动时把栈区填满图案，跑一段时间之后从栈底往上找第一个不是图案的字节，就知道栈最深用到了哪里。写个不到十行的循环就能算出来，栈是从高地址往低地址长的，找到的那个位置和栈底之间的距离就是峰值用量。这个数字比任何估算都准，留 20% 余量，别贴着上限跑。

四、看 map 文件。 .map 里写了每个段的大小和位置。看到 .bss 快把 RAM 撑满、堆和栈挨在一起，那就是结构性问题，改代码之前先改布局。

五、静态分配。 嵌入式中能不用 malloc 就不用。所有缓冲区在编译期定死大小，越界至少是可控的。真要用动态分配，用固定块的内存池，别用通用堆。

六、MPU。 有 MPU 的芯片，把栈区后面放一页不可访问的区域，栈一溢出立刻触发 MemManage 异常，比随机 HardFault 好定位得多。

十三、实时性问题的观测 #

有一类问题不属于「错」，属于「慢」：偶发丢包、偶发超时、偶尔一帧数据延迟几十毫秒。它不崩，只是不达标。

这类问题不能靠断点查，一停就没了。要的是在不停机的前提下统计时间分布。

最省事的办法是内核自带的周期计数器。Cortex-M 的 DWT 里有个 CYCCNT，直接数 CPU 周期。

c
/* 用 DWT 周期计数器测一段代码的耗时 */
static inline void dwt_init(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
    DWT->CYCCNT = 0;
    DWT->CTRL  |= DWT_CTRL_CYCCNTENA_Msk;
}

void measure_once(void)
{
    uint32_t t0 = DWT->CYCCNT;

    handle_frame();

    uint32_t dt = DWT->CYCCNT - t0;     /* 无符号相减，溢出自动处理 */
    if (dt > g_max_cycles)
        g_max_cycles = dt;              /* 只记最大值，不打印 */
}

注意这里只记录最大值，不打印。打印会把时间拉长，测出来的就不是原来的东西了。

这一轮测完，主循环空闲时再用 early_hex32 把 g_max_cycles 打出去。只看最坏值，别看平均值——平均值会把偶发超时抹平。

如果问题出在多个事件的相对关系上，就用 GPIO 加逻辑分析仪。把「中断进入」「任务开始」「总线访问」各引一根线出来，多通道同时抓，谁挡了谁一眼就能看出来。

现象 可疑的方向 观测手段
中断偶尔迟到 临界区太长、关中断太久 GPIO 翻在临界区前后，逻辑分析仪看间隔
单次处理超时 某个分支里有循环等待 DWT 计数器，抓最大值
数据偶尔丢 缓冲区小、消费者被阻塞 打印队列水位，看趋势
上电后一段时间才不正常 时钟切换、功耗模式 示波器看时钟与电源

十四、调试手段的选择 #

把所有手段摆在一起，选择这件事其实有很清楚的顺序。

第一步：先想清楚要回答什么问题。 是「程序卡在哪」，还是「为什么会卡」？是「这段花了多久」，还是「这两个事件谁先」？问题不同，工具完全不同。

第二步：按「通道 ready 了没有」选。 早期启动阶段，串口不通，就只剩 LED 和 GPIO。这个顺序没法绕。

第三步：按「能不能停机」选。 能停机的静态问题用调试器最快。不能停机的时序问题，一律上 GPIO、逻辑分析仪、周期计数器。

场景 首选手段 备选 说明
启动流程某一步没过去 多 LED 编码 串口日志 四个灯十六种状态够用
驱动 probe 失败 逐步打点 单步调试 打点先缩范围，再上调试器
偶发 HardFault 栈帧还原 + map 文件 逻辑分析仪 先拿到 PC，再查内存
内存被踩 canary + 填充图案 MPU 越界点与爆炸点不在一处
总线读不到数据 逻辑分析仪 示波器 看片选、时钟、应答
电源或信号完整性 示波器 —— 逻辑分析仪看不到模拟量
现场设备反复重启 复位原因 + 不掉电日志 看门狗 先让它别重启，再取证据
客户现场出问题 环形缓冲日志 事后 dump 带不了 probe 过去

有一条经验值得单独讲：先用最粗糙的手段把范围缩小，再用最精细的手段看细节。 一上来就挂调试器单步，往往花两小时还没定位到函数；先用四个灯把问题压到某一行，再去看那一行，十分钟就完了。

X Project 那篇记录里有一句话，我觉得说到点上了：步骤很简单，之所以还要专门写一篇，是想告诉大家——嵌入式开发其实挺简单的，只要有足够的细心和耐心。

细心是指你写寄存器的时候会去对一遍手册，抄代码的时候会核一遍定义；耐心是指你愿意为了一行可疑的代码，老老实实在它前后各插一次点灯。工具再贵，也替代不了这两样。

十五、易错点速查 #

易错点 后果 正确做法
早期日志用中断或 DMA 发送 中断没初始化，直接进错向量 用轮询发送，加超时
在中断里打长日志 中断耗时翻几十倍，逻辑被打乱 中断里只置标志，主循环打印
调完不删调试打印 上线后时序全变，性能掉一半 用编译开关整体关掉
喂狗放在定时器中断里 主循环死了狗照样被喂 喂狗放主循环末尾，只放一处
复位后不看复位原因 分不清是掉电还是跑飞 开头就读复位原因寄存器
HardFault 里取了错误的栈 RTOS 下取到一堆垃圾 看 EXC_RETURN 的 bit2 决定 MSP 还是 PSP
断点调试实时性问题 一停就复现不了 用 GPIO 或周期计数器
