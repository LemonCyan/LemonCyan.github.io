一、C 的内存管理为什么容易出错 #

C 把内存交给你，也把责任一起交给你。malloc 拿到一块堆内存，free 还回去，中间没有任何人替你记账。栈上的局部变量出了作用域自动消失，全局变量活到进程结束，堆上的东西则完全靠人记住。

这套设计换来的是速度和可控性：没有 GC 停顿，没有隐藏的对象头，sizeof 是多少就是多少。代价是每一次分配都要有人在某处记得释放。

三个结构性原因，让内存 bug 从「偶尔写错」变成「必然会写错」：

  1. 分配点和释放点隔得远。malloc 在初始化函数里，free 在清理函数里，中间隔着几百行和三层调用。删掉一行 free，编译器不会吭声。
  2. 指针没有所有权语义。char *p 这个类型不告诉你它是谁的、该不该由你释放、能不能改。传参传进去一个裸指针，被调函数拿它干了什么，调用方不知道。
  3. 编译期和运行期都不检查。数组下标越界不会报错，释放后继续用不会报错，释放两次在有的分配器上也不报错。程序带着病继续跑，跑到哪一步崩，看运气。

症状和病因不在同一处 #

这是内存问题最麻烦的地方，比「难修」更麻烦。

你今天漏掉一次 free，程序当场什么事都没有。内存漏在堆里，进程照常响应，测试照常通过。要到几天后，或者压测到两小时的时候，malloc 返回 NULL，或者 OOM killer 把进程干掉，你才看见症状。这时候去看崩溃点，那是一句无辜的 malloc。

越界写更阴。你往 p[10] 写了一个 0，p 是 10 个 int 的数组，多出来的 4 个字节压到了堆上相邻的块头，或者压到了另一个结构体的字段上。程序继续跑，被写坏的那个变量在几百行之后才被读到，读出来的值不对，于是逻辑跑偏，最后崩在一个跟内存毫无关系的地方。

c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

struct session {
    char *user;
    int   fd;
};

struct session *session_new(const char *user, int fd)
{
    struct session *s = malloc(sizeof(*s));
    if (s == NULL)
        return NULL;
    s->user = strdup(user);   /* 第二块内存，独立的 */
    s->fd   = fd;
    return s;
}

void session_free(struct session *s)
{
    free(s);                  /* 只还了结构体，s->user 那 16 字节没人管 */
}

int main(void)
{
    for (int i = 0; i < 1000; i++) {
        struct session *s = session_new("alice", i);
        session_free(s);
    }
    return 0;
}

这段代码每次循环漏 6 字节（"alice" 加结尾 0，分配器按 16 字节给）。跑一千次漏 16KB，眼睛看不出来，ps 也看不出来。跑到一千万次，进程占的内存能吓你一跳。

越界的版本更短：struct msg { int type; char text[8]; }; 里往 text 写 "12345678"，8 个字符加结尾 0 是 9 字节，多出来的那个 0 落进结构体尾部的填充区。free 时分配器读块头，读到一个被改过的值，于是 abort 在 free 里。你看栈回溯，指向 free，指向 main，跟那句 strcpy 一点关系都没有。

把这两件事连起来就是一句：内存 bug 的报错位置不是它的作案位置。所以排查思路必须反过来——不能等崩了再看现场，要在开发期让工具盯着每一次分配和访问，把病因当场抓出来。

这也解释了为什么内存工具都长得像「解释器」：它们要看清每一次内存操作，就必须在程序和你之间插一层。

二、内存问题的六个类型 #

把常见的堆内存 bug 归一下类，一共六种。后面所有的章节、所有的工具输出，都是围着这张表转。

类型 干的事 典型症状 崩在哪
未初始化读 读了没赋过值的变量或缓冲区 结果随机、时对时错、换个机器就变 不崩，逻辑错
越界读写 访问了分配范围之外的字节 数据被莫名改掉、结构体字段串味 别的 free 里、别的函数里
重复释放 同一块内存 free 两次 分配器报 double free，或者直接段错误 第二次 free
释放后使用 指针已还回去，又拿它读写 读到脏数据，写坏别人的内存 不确定
分配释放不匹配 malloc 配 delete、new[] 配 free 堆结构被破坏、崩溃 后续任一次分配
内存泄漏 分配了没释放，指针也丢了 内存缓慢上涨，最终 OOM 很久以后

前五种是「错误」，第六种是「遗漏」。遗漏比错误更难发现，因为程序的行为一直是对的，只有资源在悄悄减少。

逐条说清它们各自长什么样。示例都能单独编译跑。

未初始化读 #

全局变量和 static 变量由加载器清零，局部变量和 malloc 出来的内存不清零。栈上的值取决于这块栈之前被谁用过，堆上的值取决于分配器上次在这里放过什么。

c
#include <stdio.h>
#include <stdlib.h>

void example(void)
{
    int a[5];              /* 局部数组，5 个随机值 */
    printf("%d\n", a[0]);  /* 直接读 */
}

int main(void)
{
    example();
    return 0;
}

gcc -g -O0 badloop.c -o badloop 编译，跑起来打印 0 还是 32764，全看栈的残留。加 -Wall 也不一定警告，因为编译器看不出这是错。memcheck 的输出是这样的：

text
==12345== Use of uninitialised value of size 4
==12345==    at 0x4005A1: example (badloop.c:5)

第 5 行，a[0]，位置精确到行。这是工具比人强的地方：人能看出「这里没初始化」，但人看不出一万行代码里哪一处没初始化。

越界读写 #

数组下标超了，或者对 void * 做了错的偏移。int pt[4] 却循环写到 p[4]，多出来的 4 字节落在块外。栈数组越界当场不报，堆数组越界 memcheck 能抓：

text
==12345== Invalid write of size 4
==12345==    at 0x4005A1: example (badacc.cpp:6)
==12345==  Address 0x602010 is 4 bytes after a block of size 16 alloc'd

「4 bytes after a block of size 16」，一句话把越界的距离和原块的边界都说清了。第九章讲为什么栈上的抓不到。

内存覆盖 #

这一类归到越界里也行，但值得单列：源和目标重叠时，strcpy、memcpy 的行为是未定义的。strcpy(x + 10, x) 这种写法，dst 就在 src 后面十个字节，拷着拷着源就被自己盖掉了。badlap.cpp 的输出是 Invalid write of size 1 加行号 badlap.cpp:4。遇到重叠要用 memmove，这点老手都知道，但复制粘贴出来的那段没人再看一眼。

分配释放不匹配 #

C 和 C++ 各有两套分配释放函数，配错了堆会被搞坏：

分配 必须配的释放 配错的后果
malloc / calloc / realloc free 用 delete 释放，大小对不上，堆头被破坏
new delete 用 free 释放，不调析构
new[] delete[] 用 delete 释放，只析构第一个元素

malloc 出来的指针交给 delete，memcheck 报 Mismatched free() / delete / delete []，位置直接指到那一行。

内存泄漏 #

分配了，指针丢了，那块内存再也拿不回来。new Node 之后没有 delete，指针又被局部变量带走，memcheck 报：

text
==12345== 8 bytes in 1 blocks are definitely lost in loss record 1 of 1

definitely lost 是泄漏分类里最硬的一档，第十章细讲这四个档位。

六类的共同点 #

这六种错误有同一个结构：都发生在某一次内存操作上，症状都出现在别的地方。区别只在于延后多远、以什么形式出现。工具的价值就在于把「延后」压到零，让症状和病因重合在同一行代码上。

三、内存泄漏：定义与危害 #

内存泄漏说的是堆内存泄漏。堆是程序运行期从系统要来的、大小可以动态定的那块内存，用完必须显式还回去。malloc、realloc、calloc、new 都要还，忘了还，这块内存就既不属于你也不再属于任何人。

栈上的东西不用你还，出作用域自动回收；全局变量活到进程退出，系统一并收回。所以精确地说：泄漏只发生在堆上，只有堆内存需要人负责。

为什么泄漏一定要治 #

三个层面的代价，从轻到重：

  1. 进程变胖。常驻内存涨上去，同机部署的其他服务开始挨饿，容器被限制时容易触发 OOM kill。
  2. 延迟变差。堆碎片化之后，malloc 每次要走更长的空闲链表，缓存局部性变差，慢了但还没崩，最难查。
  3. 直接崩。32 位进程地址空间用完，malloc 返回 NULL，代码没判空就直接解引用，段错误。

第三条经常是前三条的终点。而它出现的位置和泄漏点的距离，可以是几周。

三种时间尺度 #

按暴露速度分三档，处理策略完全不同：

  • 秒级：大块泄漏，几秒就吃光内存。压测一眼看出来，top 上内存曲线陡直上升。好查。
  • 分钟到小时级：泄漏速度中等，跑业务一会儿就起来了。用长稳测试能抓到，用 Valgrind 也能抓到。
  • 天到周级：最恶心的一档。跑一天涨几 MB，跑一周才崩。你没法在 Valgrind 下跑一周——它慢十倍以上，压测根本做不了。这档只能靠工具在开发期提前抓，或者靠长稳环境的周期性抓堆快照。

用 ps 先看趋势 #

在动工具之前，先确认「确实在涨」。最土也最快的办法是隔一段时间看一次 ps：

bash
ps -aux | head -n 1
ps -aux | grep ./server | grep -v grep

看 RSS 那一列。跑业务十分钟，记一次；再跑十分钟，再记一次。单调上涨且不回落的，基本就是泄漏。中间会涨会落的，是缓存或者正常的峰值，先别急着当泄漏查。

有个细节要注意：RSS 不降不能直接当证据。free 还回去的内存，glibc 不一定会还给内核，会留在自己的 arena 里复用。要看真账，用 /proc/<pid>/status 里的 VmRSS 配合 mallinfo，或者在进程里挂上 memcheck 的统计。判断标准是「空闲块有没有被复用」，不是「RSS 有没有降」。

泄漏的定义要卡死一点 #

不是所有「没 free 的内存」都是泄漏。进程退出时操作系统统一回收，退出前没释放的内存技术上没人受害。真正的定义是：内存在程序的剩余生命周期内不再可达，也不再有用。

按这个定义，泄漏分四类，memcheck 的输出就是按这四类分的：

分类 含义 要不要治
definitely lost 指向它的指针全丢了 必须治
indirectly lost 从某个 definitely lost 的块里指过来的 治了上游就没了
possibly lost 块内部某个位置有指针指向它，但不在块首 要看，多半是 bug
still reachable 退出时还有指针能到达 一般不算泄漏

still reachable 常见于全局的结构、单例、没关的资源池。这类不治也能跑，但排查时容易干扰视线，所以跑 memcheck 时就用 --show-leak-kinds=definite,indirect 把它过滤掉。

四、泄漏的常见形态 #

按触发条件分四类，这个分法比按「大小」分有用，因为它直接决定你怎么复现。

常发性泄漏 #

每次执行到那段代码就漏一点。放在循环里、放在请求处理路径上、放在递归里，量随调用次数线性增长。

c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int handle(const char *para)
{
    if (para == NULL)
        return -1;

    char *logmsg = malloc(128);
    if (logmsg == NULL)
        return -2;

    snprintf(logmsg, 128, "handle exit: '%s'.\n", para);
    puts(logmsg);
    return 0;              /* 忘了 free(logmsg) */
}

int main(void)
{
    for (int i = 0; i < 100; i++)
        handle("testcase1");
    return 0;
}

这段跑一百次漏 12800 字节。它是本章四类里最好查的一类：memcheck 一次运行就能看见，泄漏报告的调用栈直接指到 handle 的 malloc 那一行。

偶发性泄漏 #

只有特定条件才触发。典型是错误分支：

c
int parse(const char *buf, int len)
{
    char *tmp = malloc(len + 1);
    if (tmp == NULL)
        return -1;
    memcpy(tmp, buf, len);
    tmp[len] = '\0';

    char *out = malloc(len * 2);
    if (out == NULL)
        return -1;         /* 直接返回，tmp 漏了 */

    free(tmp);
    free(out);
    return 0;
}

正常路径不漏，内存紧张时漏。你压测三天碰不到，线上高负载时它每秒钟漏一点。这类泄漏的特征是「跟你跑的业务量强相关」，复现要压到低内存。

查法：构造失败路径的测试，把 malloc 打成必失败（用 LD_PRELOAD 挡一层，或者用 failmalloc），让每条错误分支都走一遍。

一次性泄漏 #

只在初始化时漏一次，之后就再也不会。比如启动时分配的那块配置缓冲，程序结束前从来没释放过。

这类听起来无害，实际上有两个坑：一是它占的量会很大，一上来就是几十 MB；二是它会掩盖真问题，泄漏报告里混着它，你分不清哪条是每天在涨的。

处理办法是分级：definitely lost 里那些调用栈指向 main 或初始化的，先标成已知项，用 suppression 压掉，剩下的才是真目标。

隐式泄漏 #

程序在退出时会释放所有内存，所以压测、单次跑、CI 全绿。但它是常驻服务，跑一个月不退出。

典型样本是各种缓存表、连接池、事件注册表。东西只进不出，add 写得漂漂亮亮，remove 忘了写或者写了没人调用。

c
struct entry { int key; char *val; struct entry *next; };

static struct entry *table[64];

void put(int key, const char *val)
{
    struct entry *e = malloc(sizeof(*e));
    if (e == NULL)
        return;
    e->key  = key;
    e->val  = strdup(val);
    e->next = table[key % 64];
    table[key % 64] = e;      /* 没有 del，也没有容量上限 */
}

这种泄漏在 memcheck 里显示成 still reachable，因为全局数组里还有指针指着它们。工具不会报警，因为从工具的角度看，这些内存还可达、还有用。

隐式泄漏是工具查不到的那一类，只能靠人盯设计：任何只增不减的容器，都要问一句「它的上界在哪」。

不只是堆：句柄和系统资源 #

内存泄漏有个孪生兄弟：资源泄漏。文件描述符、socket、互斥锁、Windows 的 GDI 对象，都遵循同一条铁律——拿了就必须还，忘了就耗尽。

open 不 close，跑一阵子就 EMFILE: Too many open files。这个症状和内存泄漏一模一样：不是当场报错，是累积到上限才炸。

Windows 上的系统资源是个更极端的例子。每个进程的界面对象存在两块特殊的堆里：

资源堆 管理者 单个堆上限
16 位用户堆（User Heap） User.exe 64KB
32 位窗口堆（Windows Heap） User.exe 2MB
32 位用户菜单堆（User Menu Heap） User.exe 2MB
16 位 GDI 堆（GDI Heap） Gdi.exe 64KB
32 位 GDI 堆（GDI） Gdi.exe 2MB

这五块合起来叫系统资源堆。上限是操作系统写死的，跟你机器有 8MB 还是 1GB 内存、CPU 是 486 还是 P4 完全无关。所以一个 CreateWindow 之后忘了 DestroyWindow 的循环，能把整个桌面拖死，任务管理器里看内存却一切正常。

Windows 的任务管理器把「可用用户资源」「可用 GDI 资源」按百分比摆出来，就是让你盯这两个数。Linux 上对应的是 lsof -p <pid> | wc -l 和 /proc/<pid>/fd。

排查方法跟内存一样：先看趋势，再定位置。区别只是工具不同——valgrind --track-fds=yes 能报文件描述符，memcheck 不管句柄。

五、越界访问与缓冲区溢出 #

越界是内存 bug 里破坏力最大的一类。泄漏只是浪费，越界是改别人的东西。改的是自己的数据，逻辑跑偏；改的是堆块头，下一次分配就崩；改的是返回地址，直接可以被拿来做攻击。

off-by-one：最常见的一种 #

循环条件写成 <=，或者字符串长度算错一位。

c
#include <stdio.h>
#include <string.h>

void copy_name(char *dst, const char *src)
{
    size_t n = strlen(src);
    for (size_t i = 0; i <= n; i++)   /* <= 写错了，多拷一个 */
        dst[i] = src[i];
}

int main(void)
{
    char name[8];
    copy_name(name, "12345678");   /* 8 个字符 + 0 = 9 字节 */
    printf("%s\n", name);
    return 0;
}

name 是栈上的 8 字节，copy_name 写了 9 字节，多出的那个 0 落在栈上相邻的位置。它压到哪个对象由栈帧布局决定——name 前面的对齐填充、main 的某个局部变量、或者保存的帧指针。压到帧指针，函数返回时跳飞。

这种错误用眼睛看很难，因为 i <= n 和 i < n 只差一个字符，而代码里这样的循环有几十个。

从栈越界到堆越界 #

同一个越界，落在栈上和落在堆上，后果差一个量级。

位置 越界后压到什么 何时暴露
栈上数组 相邻局部变量、保存的寄存器、返回地址 函数返回时，或者相邻变量被读时
堆上块 分配器的块头、相邻块的用户数据 下一次 free 或 malloc 时
全局数组 相邻全局变量、.bss 里的其他数据 那个变量被读时
结构体内 同结构体的后续字段 读那个字段时
mmap 匿名页 下一页，或者 SIGSEGV 立刻

栈上的越界最危险，因为返回地址就在旁边。堆上的越界最隐蔽，因为它破坏了分配器的元数据，症状延后到下一次分配。

字符串函数是重灾区 #

C 标准库那批不带长度参数的函数，全部是「写到哪算哪」：

函数 问题 替换
strcpy 不检查目标容量 snprintf / strlcpy
strcat 同上，还要先算已有长度 snprintf 追加 / strlcat
sprintf 完全不管长度 snprintf
gets 连长度参数都没有 fgets
memcpy 长度靠人算 长度用 sizeof 或显式校验
strncpy 不保证结尾 0 手动补 0，或者干脆别用

sprintf 换成 snprintf 有个常见的写错法：把 sizeof(指针) 当成数组大小。

c
void bad(char *buf)                 /* buf 是个指针，sizeof(buf) == 8 */
{
    snprintf(buf, sizeof(buf), "%s", "一段很长的内容");
}

void good(void)
{
    char buf[64];
    snprintf(buf, sizeof(buf), "%s", "一段很长的内容");
}

数组作为参数传进函数就退化成指针，sizeof 拿到的是指针大小。所有接受 char * 的函数，都得额外传一个 size_t cap。

缓冲区溢出为什么是安全问题 #

往栈上数组写过长的输入，覆盖到返回地址，返回地址就变成了攻击者可控的值。这是经典栈溢出攻击的基本盘。现代系统靠几层机制挡：

  • 栈保护（-fstack-protector-strong）：在返回地址前放一个 canary，函数返回前校验，被改了就 __stack_chk_fail。
  • 不可执行栈（NX / DEP）：栈上不能执行代码，注入的 shellcode 跑不起来。
  • 地址随机化（ASLR / PIE）：每次运行的地址都不同，跳转目标猜不准。
  • FORTIFY_SOURCE：编译期把 strcpy 这类调用换成带检查的版本，能检查出显式的越界。

这些都只是「提高门槛」，不是「消灭越界」。代码里那个 i <= n 还在，只是打不进去了。

越界的两种查法 #

工具能查的部分：堆上越界、mmap 区越界、全局数组越界（ASan 全覆盖）。工具查不到的部分：栈上局部数组的越界，memcheck 完全不报，ASan 能报（靠红区）。

所以排查顺序是：先上 ASan 拿到行号，再上 memcheck 看有没有连带的内存泄漏。这条顺序后面第十二、十三章还会展开。

六、重复释放与野指针 #

free 两次，或者 free 一个不是 malloc 返回的地址，都属于这一类。

重复释放的三种来路 #

第一种，错误分支和 goto 清理块混用。清理块统一释放所有指针，中间就绝不能再单独 free 一次：

c
int load3(const char *path)
{
    char *a = malloc(16);
    char *b = NULL;
    if (a == NULL)
        return -1;

    b = malloc(16);
    if (b == NULL) {
        free(a);
        goto out;           /* a 已经被 free 过 */
    }

out:
    free(a);                /* 第二次 free(a) */
    free(b);
    return 0;
}

清理块一旦统一 free 所有指针，中间就绝不能再单独 free。两条规矩选一条：要么全程用清理块，要么全程显式释放。

第二种，指针被复制过，或者结构体里两个字段指向同一块。这类别名在释放函数里最容易被 free 两次：

c
char *p = malloc(32);
char *q = p;          /* 别名 */
free(p);
free(q);              /* 同一块内存，第二次释放 */

重复释放的检测逻辑是分配器自带的：glibc 在块头记状态，第二次 free 时报 double free or corruption。但这条检查只在某些条件下触发，新版本 glibc 加了 tcache 检测，老版本和老分配器上更宽松。「我机器上跑着没事」不能当证据。

memcheck 的输出很直接：

text
==3167== Invalid free() / delete / delete[]
==3167==    at 0x4C2EDEB: free (vg_replace_malloc.c:530)
==3167==    by 0x4005F2: main (val.c:8)
==3167==  Address 0x51b0040 is 0 bytes inside a block of size 1 free'd

「0 bytes inside a block of size 1 free'd」这句话同时告诉你：地址在哪、这块多大、它已经被释放过了。

野指针的四种形态 #

「野指针」是泛指：指针的值不再指向一个可访问的对象。细分有四种：

形态 来源 症状
未初始化指针 char *p; 之后直接用 读到一个垃圾地址，段错误或脏数据
悬空指针 free(p) 之后继续用 p 读到别人的数据，或者写坏别人的内存
越界指针 p + 100 超出对象 取决于算到哪
悬空到已销毁对象 返回局部数组地址、指向已释放的结构体 时对时错

未初始化指针的示例：

c
#include <stdio.h>

int main(void)
{
    char *p;             /* 没初始化 */
    char c = *p;         /* 解引用一个随机地址 */
    printf("[%c]\n", c);
    return 0;
}

memcheck 的输出：

text
==2862== Use of uninitialised value of size 8
==2862==    at 0x400530: main (val.c:8)

size 8 是因为 64 位下指针 8 字节。

释放后置空是纪律，不是万能药 #

c
free(p);
p = NULL;      /* 防重复释放，防误用 */

这条能防住「free 两次」和「free 完立刻用」，防不住「有两个指针指向同一块」。别名存在时，你置空了 p，q 还指着那块废内存。

真正管用的是在所有权层面约定清楚：谁分配谁释放，指针传参一律标 const 表示只借不改，需要转移所有权时函数名里写明 _take / _steal。约定比置空管用。

七、未初始化与悬空指针 #

未初始化比想象中常见 #

malloc 不清零，栈变量不清零。三种写法都在制造未初始化读：

c
#include <stdlib.h>
#include <string.h>

void f1(void)
{
    int a[5];
    int s = 0;
    for (int i = 0; i < 5; i++)
        s += a[i];        /* a 全是随机值 */
    (void)s;
}

void f2(void)
{
    struct cfg { int port; char host[32]; int flags; } c;
    c.port = 8080;
    strcpy(c.host, "127.0.0.1");
    /* c.flags 没赋值，后面读它决定行为 */
}

void f3(void)
{
    char *buf = malloc(64);
    if (buf == NULL)
        return;
    buf[0] = 'a';         /* 只写了 buf[0]，读 buf[1..63] 全是垃圾 */
    free(buf);
}

f2 这种最坑。结构体有三个字段，初始化了两个，第三个在几百行之后被读。它会「大多数时候是 0」——因为那块栈刚好被清零过——于是本地测试全绿，换个优化级别就崩。

三个习惯能挡掉大部分：

  • malloc 出来的缓冲区立刻 memset(buf, 0, size)，或者干脆用 calloc。
  • 结构体初始化写全，或者用 = {0} 起手。
  • 局部数组声明时就初始化：int a[5] = {0};。

悬空指针：返回局部地址 #

c
#include <stdio.h>

char *get_name(void)
{
    char buf[32] = "hello";
    return buf;           /* 返回栈地址，函数一返回就失效 */
}

int main(void)
{
    char *p = get_name();
    printf("%s\n", p);    /* 已经失效了 */
    return 0;
}

-Wall 会给一条 -Wreturn-local-addr 警告，别把这条警告关掉。运行时它打印什么完全取决于栈被谁覆写——在 printf 之前再调一个函数，内容就变了。

悬空指针：扩容让旧指针失效 #

realloc 会搬家，搬完家旧地址失效。写错的版本是在 realloc 的返回值落定之前就继续用旧指针：

c
int append_bad(char **arr, size_t *cap, const char *s)
{
    *arr = realloc(*arr, *cap * 2);   /* 失败时原地址丢了，泄漏 */
    if (*arr == NULL)
        return -1;
    strcpy(*arr + *cap, s);
    *cap *= 2;
    return 0;
}

这段有两种病：realloc 失败时原块泄漏；失败后 *arr 被覆盖成 NULL，谁也别想再拿到它。正确写法是先存进临时变量，判完空再赋回。C++ 里对应容器扩容后迭代器失效，push_back 之后接着用旧的 iterator 或 data()，症状一样。

一个能复现的完整例子 #

把上面几种病凑一起，写一个能一次跑出来的：

c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

struct user { char name[8]; int id; };

int main(void)
{
    struct user *u = malloc(sizeof(*u));
    if (u == NULL)
        return 1;
    memset(u, 0, sizeof(*u));
    strncpy(u->name, "wangwei", sizeof(u->name) - 1);
    u->name[sizeof(u->name) - 1] = '\0';
    u->id = 7;

    printf("%s %d\n", u->name, u->id);
    free(u);
    printf("%s\n", u->name);    /* 释放后使用 */
    return 0;
}

wangwei 恰好 7 个字符，strncpy 拷 7 个，补的 0 落在第 8 个字节，不越界；名字再长，多出来的也被 0 填满，这就是留一位的好处。最后那句 printf 是硬伤，memcheck 报 Invalid read of size 8。

八、Valgrind 是什么 #

Valgrind 是一套 Linux 下的开源动态分析工具集，GPL V2 授权，支持 x86、x86_64、ppc32、ARM 等架构。它不碰你的源码，直接对编译好的二进制做分析——这一点是它跟 ASan 的分水岭。

结构：内核加插件 #

Valgrind 自身分两层：

  • 内核（core）：一个模拟 CPU 的框架，把被调试程序的机器码翻译成中间表示（VEX IR），再在中间表示上插桩。所有工具都跑在这层之上。
  • 工具（tool）：以插件形式挂在核心里，各自关心不同的东西。--tool=<name> 选一个。

这种设计让「新增一个分析工具」变成「写一个插件」，不用重做 CPU 模拟。

七个内置工具 #

工具 关注点 典型使用场景
memcheck 堆内存错误、泄漏、未初始化读 默认工具，日常首选
cachegrind 缓存命中率、分支预测 优化热点循环的数据布局
callgrind 函数调用次数、调用图 找热点函数，配 KCachegrind 看
helgrind 多线程竞争、锁顺序 数据竞争、死锁排查
drd 数据竞争（比 helgrind 轻） 同上，噪声少一些
massif 堆内存占用快照 找出谁吃掉了堆
lackey / nulgrind 教学演示、空工具 写自己的工具的模板

massif 值得单独说一句：它按时间采样堆的使用量，画出「谁在什么时候占了多少」。当你的程序内存涨上去，memcheck 只说「泄漏了」，massif 能说「是这棵树的节点吃掉的」。抓内存热点，看 massif 的图比看代码快。

memcheck 的原理 #

memcheck 维护两张全局表，按字节记录状态：

  • Valid-Value 表（V bits）：进程地址空间里每个字节配 8 个 bit，标记这个字节的值是否「已初始化且可读」。每个 CPU 寄存器也有一份对应的 bit 向量。
  • Valid-Address 表（A bits）：每个字节配 1 个 bit，标记这个地址是否可读写。

每一条内存访问都被改写成一段检查代码：

  1. 读写前先查 A bit，无效就报 Invalid read/write；
  2. 读到寄存器里的值，V bits 跟着一起进虚拟 CPU；
  3. 这个值一旦用来算地址、或者影响输出（分支、系统调用参数），就检查 V bits，有未初始化的位就报 Use of uninitialised value；
  4. malloc 时登记块边界，free 时标记整块为不可访问，退出时把没释放的块按可达性分类。

因为它在虚拟 CPU 里跑，每条原始指令都会变成几十条插桩指令。这就是代价的来源。

代价：慢 10~50 倍，内存约两倍 #

必须把这件事说清楚，不然你会拿它去压测然后怀疑人生。

  • 速度：程序会慢 10 到 50 倍。原来 10 秒的活，在 memcheck 下跑 2 到 8 分钟。这个量级来自逐条指令插桩加影子内存查表，不是配置问题，调不掉。
  • 内存：Valgrind 自身加上影子表，占用大约是原程序需求的两倍。你要 100MB，它要 200MB。在内存受限的嵌入式板子上，这一条经常直接卡死。
  • 结论：只在调试期用，用来跑功能用例和单元测试，不要用来做性能测试和压力测试。压测要看的是 QPS 和延迟曲线，插桩之后这两个数全失真。

还有个限制要知道：memcheck 不跟踪栈上静态数组的边界。这段代码它一声不响：

c
int main(void)
{
    char x[10];
    x[11] = 'a';      /* 栈上越界，memcheck 不报 */
    return 0;
}

栈帧是一整块可读写区域，memcheck 只标记了它「可访问」，没标记里面哪个字节属于哪个数组。想让它报，得把数组改成 malloc 出来的：

c
#include <stdlib.h>

int main(void)
{
    char *x = malloc(10);
    if (x == NULL)
        return 1;
    x[11] = 'a';      /* 堆上越界，memcheck 报 Invalid write */
    free(x);
    return 0;
}

这条限制正是 ASan 存在的理由之一，它靠编译期插桩在栈变量周围放红区，栈越界也能抓。

九、memcheck 的用法 #

先编译对 #

两个编译选项决定你能不能看懂输出：

bash
gcc -g -O0 sample.c -o sample

-g 把调试符号写进二进制，Valgrind 才能把地址翻译成 文件:行号。没有它，你只能看到 (in /path/to/a.out)，等于拿不到位置。

-O0 关优化。-O2 会把变量优化进寄存器、把代码重排、把函数内联，你看到的行号会指到奇怪的地方，甚至指向不存在的语句。调试内存问题时不要开优化。

一个硬性前提：二进制不能被 strip 过。发布版本的构建如果剥掉符号表，Valgrind 只能给地址。要定位就得留一份带符号的调试构建。

基本命令 #

bash
valgrind [valgrind-options] your-prog [your-prog-options]

不写 --tool 时默认就是 memcheck：

bash
valgrind ./sample
valgrind --tool=memcheck ./a.out

参数分两类：核心参数对所有工具生效，工具参数只对选中的工具生效。日常排查九成场景用下面这几个就够。

选项 作用 备注
--leak-check=full 每个泄漏块都给完整调用栈 必开
--show-leak-kinds=all 四类泄漏全展示 只想看真泄漏就写 definite,indirect
--track-origins=yes 追未初始化值的来源 开了更慢，值得
--error-exitcode=1 有错时进程退出码为 1 接 CI 必须加
--log-file=vg.log 输出写文件，不混进程序自己的 stderr 程序输出多时必用
--num-callers=30 调用栈深度 默认 12，深层调用调大
--track-fds=yes 报告未关闭的文件描述符 查句柄泄漏
-v 打印被抑制的错误统计 怀疑漏报时看

一个完整示例 #

一个程序同时带两种病，一次跑全暴露，这就是动态分析比人快的地方：

c
#include <stdio.h>
#include <stdlib.h>

void fun(void)
{
    int *p = malloc(10 * sizeof(int));
    if (p == NULL)
        return;
    p[10] = 0;      /* 越界写：合法下标是 0..9 */
    /* free(p); 忘了释放，泄漏 40 字节 */
}

{
    fun();
    return 0;
}

bash

十、读懂 Valgrind 的输出 #

看不懂输出等于没用。这一章把每一段拆开。

输出的稳定结构 #

memcheck 的每一行都以 ==<pid>== 开头。这个前缀是给 grep 用的，程序自己的输出不带它。

text
==19226== Memcheck, a memory error detector
==19226== Copyright (C) 2002-2012, and GNU GPL'd, by Julian Seward et al.
==19226== Using Valgrind-3.8.1 and LibVEX; rerun with -h for copyright info
==19226== Command: ./a.out

前四行是版本和命令行，排查环境问题时有用：你贴日志给人看，对方能立刻知道你用的哪个版本、跑的哪条命令。

接着是错误区，一条错误一段：

text
==19226== Invalid write of size 4
==19226==    at 0x4005B5: fun (test.cpp:5)
==19226==  Address 0x51b0040 is 0 bytes after a block of size 40 alloc'd
==19226==    at 0x4C278FE: malloc (vg_replace_malloc.c:270)
==19226==    by 0x4005A5: fun (test.cpp:4)
==19226==    by 0x4005CC: main (test.cpp:11)

三块信息依次是：错误类型（Invalid write of size 4）、出错位置（第一段调用栈）、地址的来历（这块内存是在哪分配的）。第三块是 memcheck 最值钱的地方——它不只说「你写错了」，还说「这块内存当初是谁申请的、申请的多少」，你立刻能对上号。

HEAP SUMMARY 与 LEAK SUMMARY #

程序退出时，先给堆的总账：

text
==19226== HEAP SUMMARY:
==19226==     in use at exit: 30 bytes in 1 blocks
==19226==   total heap usage: 1 allocs, 0 frees, 30 bytes allocated

1 allocs, 0 frees 这一行几乎可以一眼定罪：分配过 1 次，释放 0 次。

然后是逐条泄漏记录：

text
==19226== 30 bytes in 1 blocks are definitely lost in loss record 1 of 1
==19226==    at 0x4C278FE: malloc (vg_replace_malloc.c:270)
==19226==    by 0x4005B5: getMemory() (test.cpp:5)
==19226==    by 0x4005CC: main (test.cpp:11)

读法：test.cpp 第 5 行的 malloc 申请了 30 字节，调用者是 test.cpp 第 11 行的 main。位置直接给到行。

最后是分类汇总：

text
==19226== LEAK SUMMARY:
==19226==    definitely lost: 30 bytes in 1 blocks
==19226==    indirectly lost: 0 bytes in 0 blocks
==19226==      possibly lost: 0 bytes in 0 blocks
==19226==    still reachable: 0 bytes in 0 blocks
==19226==       suppressed: 0 bytes in 0 blocks

四档加一档抑制，含义在第三章讲过。这里补一个实战判据：definitely lost 是必须修的，indirectly lost 跟着上游一起修，possibly lost 要打开那块内存看是不是指针只指到了块内部（常见于 C++ 有虚表的对象被 char * 偏移过），still reachable 先记着不修。

有没有 -g，差别在这 #

不带 -g 编译，栈里只有文件名，没有行号：

text
==19226==    by 0x4005B5: getMemory() (in /root/valgrind/bin/a.out)
==19226==    by 0x4005CC: main (in /root/valgrind/bin/a.out)

带 -g，同一段变成 getMemory() (test.cpp:5) 和 main (test.cpp:11)。一行号之差，排查时间差一个数量级，所以 CI 上的内存检查任务，构建类型必须是 Debug。

修好之后长什么样 #

把 getMemory 的返回值 free 掉再跑：

text
==21033==     in use at exit: 0 bytes in 0 blocks
==21033==   total heap usage: 1 allocs, 1 frees, 30 bytes allocated
==21033== All heap blocks were freed -- no leaks are possible
==21033== ERROR SUMMARY: 0 errors from 0 contexts (suppressed: 6 from 6)

All heap blocks were freed -- no leaks are possible 是目标状态，ERROR SUMMARY: 0 errors 是接 CI 的判据。suppressed: 6 from 6 不用管，那是库函数里的已知噪声被默认规则挡掉了。

追未初始化值的源头 #

Use of uninitialised value 只告诉你「这里用了脏值」，不告诉你脏值哪来的。加 --track-origins=yes：

bash
valgrind --track-origins=yes --leak-check=full ./sample

text
==25001== Use of uninitialised value of size 4
==25001==    at 0x4005A1: check (logic.c:22)
==25001==  Uninitialised value was created by a heap allocation
==25001==    at 0x4C2DB8F: malloc (vg_replace_malloc.c:299)
==25001==    by 0x4006A2: load (logic.c:14)

「这个脏值是 logic.c 第 14 行 malloc 出来的」，第 22 行只是用它的地方。有这一段，因果链就接上了。代价是更慢，按需开。

抑制文件 #

系统库、第三方库里有一些「已知但改不了」的报错。每次都刷屏会淹掉真问题，用 suppression 压掉：

bash
valgrind --leak-check=full --gen-suppressions=all ./sample 2>&1 | tee vg.txt

--gen-suppressions=all 会把每条错误同时打印成一段可用的抑制规则，复制进 my.supp，然后：

bash
valgrind --suppressions=my.supp --leak-check=full ./sample

规矩只有一条：抑制列表要写在版本库里，并且每条都要有注释说明为什么可以压。压掉的东西不会消失，它只是不报了。

十一、Valgrind 的其他工具 #

memcheck 是入口，另外几个工具解决不同的问题，命令形态一样，只换 --tool。

工具 命令 输出怎么看
cachegrind valgrind --tool=cachegrind ./prog 打印 I1/D1/LL 三级缓存的 miss 率
callgrind valgrind --tool=callgrind ./prog 生成 callgrind.out.<pid>，用 KCacheGrind 打开
helgrind valgrind --tool=helgrind ./prog 报数据竞争和锁顺序问题
drd valgrind --tool=drd ./prog 同上，噪声更少
massif valgrind --tool=massif ./prog 生成 massif.out.<pid>，ms_print 看堆曲线

callgrind 配 KCacheGrind 是性能排查的老组合，图形化看调用树和每行耗时。Qt Creator 内置了 Valgrind 前端，点几下就能跑 memcheck，适合不想记参数的人。

massif 值得单独用一次：程序内存涨，memcheck 说「泄漏 20MB」，massif 能按时间轴告诉你「第 12 秒到这 20MB 全是 parse_json 分配的」。查内存热点，它比 memcheck 更直接。

在 ARM 目标板上跑 #

交叉编译到 ARM，坑集中在三处：架构匹配、安装路径、库权限。

bash
wget http://valgrind.org/downloads/valgrind-3.12.0.tar.bz2
tar xvf valgrind-3.12.0.tar.bz2 && cd valgrind-3.12.0
apt-get install automake && ./autogen.sh
vi configure        # 找到 armv7*) ，改成 armv7*|arm)
./configure --host=arm-linux CC=arm-none-linux-gnueabi-gcc \
    CPP=arm-none-linux-gnueabi-cpp CXX=arm-none-linux-gnueabi-g++
make && make install --prefix=/home/dcj/valgrind

老版本的 configure 只认 armv7，把 arm 漏了。不改这一行，配置阶段就认错平台。--prefix 装完有 bin、include、lib、share 四个子目录，路径必须和板子上的一致，Valgrind 按编译时写死的路径找自己的工具库，不一致就报：

text
valgrind: failed to start tool 'memcheck' for platform 'arm-linux': No such file or directory

把目录拷到板子上，补执行位和环境变量：

bash
chmod -R +x /home/dcj/valgrind/bin/
chmod -R +x /home/dcj/valgrind/lib/valgrind/
export VALGRIND_LIB="/home/dcj/valgrind/lib/valgrind"

报 Permission denied 而不是 No such file，就是库文件缺执行位或者 VALGRIND_LIB 指错了。跑之前算内存账：Valgrind 占用约为原程序两倍，板上 64MB 内存、程序要 40MB 的场合 memcheck 起不来，换 ASan 交叉编译，或者只在小用例上跑。

十二、AddressSanitizer 与 UBSan #

ASan 是另一条路：不模拟指令，改在编译期插桩。

怎么开 #

bash
gcc -fsanitize=address -g -O1 -fno-omit-frame-pointer sample.c -o sample
./sample

三个关键点：

  • -fsanitize=address 打开 ASan，链接时也会自动带上运行时库。
  • -fno-omit-frame-pointer 保留帧指针，调用栈才完整。
  • 优化级别用 -O1。ASan 不支持 -O0 之外的极端优化，-O2 下部分错误会被优化掉。

GCC 从 4.8 起支持，Clang 从 3.1 起支持。

原理：影子内存 #

ASan 在进程里额外映射一块「影子内存」，每 8 字节真实内存对应 1 字节影子，记录这 8 字节里有几个是「可访问前缀」。一次 8 字节访问，先查影子字节，值合法就放行，不合法就报错。

分配时在每块前后各加一段红区（redzone），红区在影子里被标成不可访问。越界碰到红区，立刻被抓。

这个设计的开销是：内存约增加 1.5 到 2 倍，速度慢约 2 倍。跟 memcheck 的 10 到 50 倍不是一个量级。

报错长什么样 #

c
#include <stdlib.h>

int main(void)
{
    int *p = malloc(10 * sizeof(int));
    if (p == NULL)
        return 1;
    p[10] = 0;      /* 越界 */
    free(p);
    return 0;
}

text
=================================================================
==1234==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x602000000038
WRITE of size 4 at 0x602000000038 thread T0
    #0 0x400b4d in main sample.c:8
    #1 0x7f... in __libc_start_main
0x602000000038 is located 0 bytes to the right of 40-byte region
allocated by thread T0 here:
    #0 0x7f... in malloc
    #1 0x400a9e in main sample.c:5
SUMMARY: AddressSanitizer: heap-buffer-overflow sample.c:8 in main

结构跟 memcheck 一样：错误类型、出错位置、内存来历。区别是 ASan 的地址旁边直接标了「0 bytes to the right of 40-byte region」，边界关系说得更明白。

ASan 能抓的类型比 memcheck 多一项关键能力：栈上和全局变量的越界。它靠给栈变量插红区实现，memcheck 做不到这一点。

泄漏检测 #

Linux 上 ASan 自带 LeakSanitizer，程序退出时自动检查：

bash
ASAN_OPTIONS=detect_leaks=1 ./sample

输出会列出泄漏块和分配栈。想关掉（比如跑性能用例时）就 detect_leaks=0。其他两个常用选项：

bash
ASAN_OPTIONS=halt_on_error=0:log_path=/tmp/asan ./sample

halt_on_error=0 让它在第一次报错后继续跑，一次运行收集多个错误；log_path 把报告写文件，避免和程序输出混在一起。

UBSan 管另一摊 #

UBSan 查的是未定义行为，不是内存错误：有符号整数溢出、除零、移位越界、nullptr 解引用、对齐违规、越界的枚举值。

bash
gcc -fsanitize=undefined -fno-sanitize-recover=all -g sample.c -o sample

-fno-sanitize-recover=all 让它在第一次 UB 时直接 abort，默认行为是打印警告后继续。

text
sample.c:7:13: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'

UBSan 几乎没有运行开销，可以常开在 Debug 构建里。它抓的是「编译器没义务给你正确结果」的那些地方，这类 bug 换个编译器版本就复现不了，最难查。

几种 sanitizer 的关系 #

名称 查什么 编译选项 能否与其他共存
ASan 堆/栈/全局越界、释放后使用、泄漏 -fsanitize=address 与 TSan、MSan 互斥
UBSan 未定义行为 -fsanitize=undefined 可与 ASan 同时开
TSan 数据竞争 -fsanitize=thread 与 ASan 互斥
MSan 未初始化读（需要全链路插桩） -fsanitize=memory 与 ASan 互斥

ASan 和 UBSan 可以一起开：-fsanitize=address,undefined。这是 CI 上性价比最高的一行配置。

十三、检测工具横向对比 #

没有哪个工具能全包。选型只看两件事：你现在手上是源码还是二进制，以及你能不能接受重编译。

工具 插桩方式 速度损失 要重编译吗 主要能力
Valgrind memcheck 动态二进制插桩 慢 10~50 倍 不要 堆越界、泄漏、未初始化、双 free
Valgrind massif 动态插桩 慢 不要 堆占用时间轴
AddressSanitizer 编译期插桩 慢约 2 倍 要 堆/栈/全局越界、UAF、泄漏
LeakSanitizer 编译期插桩 近乎零 要 只查泄漏
MemorySanitizer 编译期插桩 慢约 3 倍 要，全链路 未初始化读
ThreadSanitizer 编译期插桩 慢 5~15 倍 要 数据竞争
Rational Purify 换编译器插桩 慢 要 内存错误、多进程
静态分析 不运行 零 不要 配对缺失、未初始化

分工怎么划 #

ASan 快，但必须重新编译。开发机上、单元测试里、CI 的每个提交，默认开 ASan 加 UBSan。它慢两倍，跑测试用例完全能接受。

Valgrind 不用重编，但慢 10 到 50 倍。它的场景是：手里只有一个编好的二进制，不知道它怎么构建的；或者线上出问题的那个版本部署在别人机器上，你只有可执行文件。压测、性能对比、长稳跑，一律不要用 Valgrind，那个速度下拿到的延迟数据全是假的。

一个实用的顺序：日常提交跑 ASan + UBSan，版本发布前对关键路径跑一遍 memcheck（双保险，memcheck 的泄漏分类比 LSan 细），ARM 上因为内存翻倍跑不动 memcheck，就只保留 ASan。

静态分析顶在前面 #

静态分析不运行程序，成本最低，能在提交之前拦住一类问题。BEAM 能查四类：未初始化变量、废弃的空指针、内存泄漏、冗余计算，平台覆盖 Linux x86、s390、PowerPC、AIX、Windows 2000 以上。

分配和释放写在同一段代码里的那种泄漏，静态工具一眼能看出来：

cpp
int LeakTest(char *Para)
{
    char *Logmsg = new char[128];
    if ((Para == NULL) || (Logmsg == NULL))
        return -1;
    sprintf(Logmsg, "LeakTest routine exit: '%s'.\n", Para);
    return 0;        /* 漏了 delete[] Logmsg */
}

bash
./beam-3.4.2/bin/beam_configure --c gcc
./beam-3.4.2/bin/beam_compile --beam::compiler=compiler_cpp_config.tcl -cpp code2.cpp

同类的还有 Splint、PC-LINT、cppcheck。静态分析的短板是跨函数的数据流看不清——所以它替代不了动态工具，只能放在前面当第一道过滤。

Purify 这类需要重编的 #

Purify 通过替换编译器插桩，改 Makefile 里的 CC 就行：

makefile
CC = purify gcc

bash
./purifyplus_setup.sh
make
purify g++ -g test3.cpp -o test

-g 一样不能省，不然定位不到行。Purify 的长处是能跟着多进程程序走，每个子进程都能查。

十四、把工具接进构建流程 #

工具再好，靠人记得手动跑就等于没有。接进构建只有三步。

第一步，Debug 构建把 sanitizer 挂上。CMake 写法：

cmake
option(ENABLE_SANITIZER "build with asan+ubsan" OFF)
if(ENABLE_SANITIZER)
  add_compile_options(-fsanitize=address,undefined -fno-omit-frame-pointer -g)
  add_link_options(-fsanitize=address,undefined)
endif()

第二步，CI 里加一条内存检查任务，用 --error-exitcode=1 把内存错误变成构建失败：

bash
valgrind --error-exitcode=1 --leak-check=full \
    --show-leak-kinds=definite,indirect \
    --suppressions=tools/valgrind.supp \
    ./build/unit_test

--error-exitcode=1 是关键。没有它，Valgrind 报完错照样返回 0，CI 一片绿，等于没接。

第三步，抑制文件入库。tools/valgrind.supp 跟着代码走，每条抑制带一行注释写清为什么可以压。没有这一步，第三方库的噪声第三天就会让人把整条任务注释掉。

分档的说法：提交时用 cppcheck 加 -Wall -Wextra 挡新增警告，用 ASan + UBSan 跑单测（退出码非 0 即失败），每日构建用 memcheck 跑集成用例盯 ERROR SUMMARY: 0 errors，发布前用 massif 看堆曲线加 24 小时长稳，目标板上只留 ASan 交叉编译版本。

十五、预防胜于检测 #

工具能抓的是「已经写错的」，减少写错得靠规矩。下面几条是投入产出比最高的。

规矩 挡住什么
谁分配谁释放，转移所有权时函数名写 _take / _steal 泄漏、重复释放
指针参数只借不改的加 const 意外改写调用方内存
每个函数只有一个出口收尾（清理块） 错误分支漏 free
malloc 后立刻判空，free 后立刻置 NULL 空指针解引用、误用野指针
缓冲区一律带容量参数 (char *buf, size_t cap) 越界写
字符串用 snprintf、复制用 memmove 溢出、重叠覆盖
结构体声明时 = {0}，malloc 出来的 memset 未初始化读
只增不减的容器必须写上界和淘汰 隐式泄漏

清理块的标准写法，一个函数里所有资源一个出口：

c
int process(const char *path)
{
    int ret = -1;
    char *buf = NULL;
    FILE *fp = NULL;

    buf = malloc(4096);
    if (buf == NULL)
        goto out;

    fp = fopen(path, "r");
    if (fp == NULL)
        goto out;

    ret = 0;

out:
    if (fp != NULL)
        fclose(fp);
    free(buf);
    return ret;
}

goto out 只有一个方向，out 里只做释放，不做业务。这条规矩能把「错误分支漏释放」这一类直接清零。

编译选项也算预防的一部分：

bash
gcc -Wall -Wextra -Wreturn-local-addr -fstack-protector-strong \
    -D_FORTIFY_SOURCE=2 -O2 app.c -o app

-Wreturn-local-addr 抓返回局部地址，-fstack-protector-strong 在返回地址前放 canary，FORTIFY_SOURCE 把 strcpy 换成带长度检查的版本。三条都是白给的。

十六、易错点速查 #

现象 先查什么 用什么
内存缓慢上涨，几小时到几天 只增不减的容器、错误分支漏 free ps 看趋势，memcheck --leak-check=full
一压测就掉，重启就好 泄漏加碎片，malloc 返回 NULL 没判空 memcheck 加 --track-origins=yes
free 里崩，栈回溯指向无辜代码 堆越界写坏了块头 ASan 拿行号，再看 memcheck
double free or corruption 清理块和显式 free 混用、指针别名 代码审查加 memcheck
结果时对时错，换机器就变 未初始化读 ASan + MSan，或 memcheck 的 --track-origins
越界在栈上，memcheck 不报 memcheck 不跟踪栈数组边界 换 ASan
EMFILE: Too many open files open 没 close，错误分支漏关 valgrind --track-fds=yes
函数返回后数据变成垃圾 返回了局部数组地址 -Wreturn-local-addr
报内存不足但 ps 显示正常 Windows 系统资源堆打满 任务管理器看可用用户/GDI 资源
CI 全绿但线上崩 内存检查任务没加 --error-exitcode=1 改构建脚本

最后回一句本篇的出发点：内存 bug 的病因和症状不在一处，工具的作用就是把它们挪到同一处。你今天在开发机上多花的那两分钟，换的是线上不用花两天去追一个 OOM。
