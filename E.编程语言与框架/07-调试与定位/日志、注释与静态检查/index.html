一、调试的三种层次 #

我们查一个问题，手上其实只有三类动作。

第一类是看。代码不跑，靠工具读源码，找空指针、数组越界、未初始化变量、复制粘贴写错的判断。这是静态检查。第二类是记。代码跑起来，把关键状态写进日志，事后翻。这是日志。第三类是停。代码跑到某一行卡住，让我们看变量、看栈、看内存。这是调试器。

层次 手段 介入时机 能看到什么 主要代价 生产环境可用
静态检查 CppCheck、编译器告警 写完代码，编译前后 可疑写法、越界、资源泄漏 误报要人筛 是
日志 printf、printk、日志库 运行时持续记录 历史状态、调用顺序、耗时 影响时序、占空间 是
调试器 GDB、VS Debugger、JTAG 问题复现的当下 变量、栈、内存、寄存器 要停程序、要符号、要权限 否

三者不是替代关系。写的时候靠静态检查，跑的时候靠日志，卡住了才上调试器。调试器有硬门槛：得有符号，得能 attach，得有权限。桌面程序要 Debugger，嵌入式要仿真器。早年做嵌入式，机房就一台 JTAG，为了插空用上，只能挑周末别人不加班的时候去。这种等待的成本，比在函数里写十行日志高得多。后来转做 Linux driver，见识到 printk 的用法，仿真器和调试器就很少再碰了。

线上更直接。客户现场的程序在跑，你停不了它。core dump 是事后补救，日志才是事中记录。一个线上问题从报障到定位的时间，跟日志里有没有那三行关键信息强相关。

所以本文的顺序是：先日志，再注释，最后静态检查。

二、printf 调试：最原始也最直接 #

多数人写的第一个程序就是 printf("Hello world\n")。很多人以为它只会打印字符串，其实它是我们手里最灵活的探针。道理很简单。程序出问题，只有两种状态：我们以为它走到了某处，和它实际走到了某处。printf 干的事，就是在两者之间插旗子。旗子没亮，说明根本没走到；旗子亮了但值不对，说明问题在这一段里。

先看现象。一个报文解析函数返回 -1，而函数里有两条 if 都能返回 -1。到底挂在第一条还是第二条？靠猜。

插上旗子，答案立刻出来。

c
#include <stdio.h>
#include <string.h>

struct frame {
    unsigned char  magic;
    unsigned char  type;
    unsigned short len;
};

static int parse_frame(const unsigned char *buf, int n)
{
    struct frame f;

    printf("[%s:%d] enter, n=%d\n", __FILE__, __LINE__, n);

    if (n < (int)sizeof(f)) {
        printf("[%s:%d] short frame\n", __FILE__, __LINE__);
        return -1;
    }

    memcpy(&f, buf, sizeof(f));
    printf("[%s:%d] magic=%02x type=%02x len=%u\n",
           __FILE__, __LINE__, f.magic, f.type, (unsigned)f.len);

    if (f.len > n - (int)sizeof(f)) {
        printf("[%s:%d] len overflow: need=%u have=%d\n",
               __FILE__, __LINE__, (unsigned)f.len, n - (int)sizeof(f));
        return -1;
    }

    return f.len;
}

int main(void)
{
    unsigned char buf[8] = { 0x5a, 0x01, 0x20, 0x00, 0, 0, 0, 0 };

    printf("[%s:%d] result = %d\n", __FILE__, __LINE__,
           parse_frame(buf, (int)sizeof(buf)));
    return 0;
}

输出：

text
[parse.c:11] enter, n=8
[parse.c:19] magic=5a type=01 len=32
[parse.c:23] len overflow: need=32 have=4
[parse.c:38] result = -1

四个位置，四行日志，问题当场锁定：报文字段 len 写的是 32，实际缓冲区只剩 4 字节。

几条打点的经验。

每行日志都带 __FILE__ 和 __LINE__。不带位置，几十条打印对不上代码，等于白打。手写太啰嗦，封成宏：

c
#define P(fmt, ...) \
    printf("[%s:%d] " fmt "\n", __FILE__, __LINE__, ##__VA_ARGS__)

长函数别从头打到尾。先在函数入口和出口各打一行，确认它到底有没有被调用、返回值是多少。范围不对，再对半插。十次二十次的二分，比五十行打印管用。

打边界值，不打过程值。循环体里塞一句 printf，能刷出几万行，还会拖慢时序，把要复现的时序问题直接赶跑。打完记得留个后路，要么删干净，要么走下一章的宏开关。留在代码里的裸 printf，是发布版本的定时炸弹。

裸 printf 当调试器用，有三个短板：关不掉、分不了级、输出位置写死。想打到串口、想写进文件、想只留错误级别的输出，就得自己搭一层。这就是日志系统。

三、日志分级：DEBUG 到 FATAL #

日志的第一件事不是「怎么打」，是「打多重要」。

所有日志一律同级，结果是两种结局：要么全开，刷爆磁盘和串口带宽；要么全关，出事时两眼一黑。分级就是给每条日志贴一个重要性，再给每个模块配一个门槛。

级别 什么时候用 内容特征 生产环境
DISABLE 全部关闭 不输出任何日志 特殊场景
FATAL 致命错误，进程将要退出 出错点、错误码、现场关键变量 必开
ERR 错误，业务无法继续 出错函数、参数、errno 必开
WARN 异常但可继续 降级、重试、超时、兜底 建议开
INFO 关键业务节点 启动、初始化完成、连接建立、配置加载 建议开
DEBUG 排查细节 中间变量、分支走向、报文内容 关闭

用一个枚举把门槛写死。

c
/*
 * debug level,
 *   DEBUG_LEVEL_DISABLE : 一条都不输出
 *   DEBUG_LEVEL_ERR     : 只输出 ERR
 *   DEBUG_LEVEL_INFO    : 输出 ERR 和 INFO
 *   DEBUG_LEVEL_DEBUG   : 全部输出
 */
enum debug_level {
    DEBUG_LEVEL_DISABLE = 0,
    DEBUG_LEVEL_ERR,
    DEBUG_LEVEL_INFO,
    DEBUG_LEVEL_DEBUG
};

级别是门槛，不是标签。设成 DEBUG_LEVEL_INFO，ERR 和 INFO 都出，DEBUG 不出。含义是「这个级别及以上都放行」，所以枚举值必须是从小到大排的。再往下就是定义宏。

c
#define ASSERT()                                        \
do {                                                    \
    PRINT("ASSERT: %s %s %d\n",                         \
          __FILE__, __FUNCTION__, __LINE__);            \
    while (1);                                          \
} while (0)

#define ERR(...)                                        \
do {                                                    \
    if (dbg_level >= DEBUG_LEVEL_ERR) {                 \
        PRINT(__VA_ARGS__);                             \
    }                                                   \
} while (0)

#define INFO(...)                                       \
do {                                                    \
    if (dbg_level >= DEBUG_LEVEL_INFO) {                \
        PRINT(__VA_ARGS__);                             \
    }                                                   \
} while (0)

#define DEBUG(...)                                      \
do {                                                    \
    if (dbg_level >= DEBUG_LEVEL_DEBUG) {               \
        PRINT(__VA_ARGS__);                             \
    }                                                   \
} while (0)

三个写法上的讲究。外裹 do { } while (0)，这样宏在 if / else 里能当单条语句用，敲个分号也不会错；写成 { ... } 不加 do-while，if (x) DEBUG(...); else ... 会直接编译失败。PRINT(__VA_ARGS__) 里保留调用方传进来的格式串，别在宏里拼 "%s" 去吞参数，否则编译器对 %d / %s 的类型检查就断了，-Wformat 也帮不上忙。ASSERT 用 while (1) 而不是 abort()，嵌入式上 abort 的行为依赖 libc 实现，还牵扯信号处理；死循环更可控，配合看门狗就是一次干净复位。

用起来就是这样，只有第一行会出来。改一行宏参数，第二行就出来了。

c
#include "debug.h"

DEBUG_SET_LEVEL(DEBUG_LEVEL_ERR);

int main(void)
{
    ERR("open %s failed, errno=%d\n", "/dev/ttyS0", 13);
    INFO("this line is filtered out\n");
    DEBUG("this line is filtered out too\n");
    return 0;
}

只有第一行会出来。改一行宏参数，第二行就出来了。

四、日志该打什么、不该打什么 #

日志的价值不在数量，在「出事那一刻，翻得出来吗」。

该打 不该打
状态发生变化：连接建立、状态机跳转、配置生效 「我到这里了」「程序运行中」
函数入口的参数、函数出口的返回值与耗时 每个局部变量的中间值
错误分支：错误码、errno、出错参数 循环体里的逐次打印
外部输入的第一手数据：报文长度、命令字 整块内存的十六进制 dump
降级、重试、超时、兜底路径 密码、令牌、身份证、完整手机号
资源申请与释放的配对点 库内部已经会打的重复信息

打「状态变了」，不打「我还活着」。INFO("enter func"); INFO("leave func"); 这种日志，写完当天看着舒服，一个月后只剩噪音。

出事时你想知道的三件事：谁调用了我，参数是什么，我返回了什么。一条好的错误日志把这三样装齐。

c
static int read_config(const char *path, struct config *out)
{
    FILE *fp;
    int   ret;

    if (path == NULL || out == NULL) {
        ERR("read_config: bad arg, path=%p out=%p\n",
            (void *)path, (void *)out);
        return -EINVAL;
    }

    fp = fopen(path, "r");
    if (fp == NULL) {
        ERR("read_config: fopen %s failed, errno=%d\n", path, errno);
        return -ENOENT;
    }

    ret = parse_config(fp, out);
    fclose(fp);
    if (ret != 0) {
        ERR("read_config: parse %s failed, ret=%d\n", path, ret);
        return ret;
    }

    INFO("read_config: %s loaded, %d items\n", path, out->count);
    return 0;
}

三条日志各自装齐了这三样：出错的函数名、入参、错误码或返回值。翻日志的人不用看代码就知道坏在哪一步。

敏感信息一个字符都别进日志。日志文件的权限比配置文件松，会被打包进故障报告，会被上传到工单系统，会躺在别人电脑的下载目录里。大块数据打长度不打内容，真要看报文就打前 16 字节加总长度，再配一个能单独打开的调试开关。

五、日志的开关与条件编译 #

开关分三层：全局总闸、文件级门槛、编译期剔除。

全局总闸放头文件里，一行宏管所有。

c
#ifndef __DEBUG_H__
#define __DEBUG_H__

#include <stdio.h>

/*
 * 全局总开关：注释掉这一行，所有日志在编译期整体消失
 */
#define CONFIG_ENABLE_DEBUG

#ifdef CONFIG_ENABLE_DEBUG
/* 换成写文件、写串口、写环形缓冲，只改这一行 */
#define PRINT               printf
#define DEBUG_SET_LEVEL(x)  static int dbg_level = (x)
#else
#define PRINT(...)          do { } while (0)
#define ASSERT()            do { } while (0)
#define ERR(...)            do { } while (0)
#define INFO(...)           do { } while (0)
#define DEBUG(...)          do { } while (0)
#define DEBUG_SET_LEVEL(x)  do { } while (0)
#endif

#endif

关掉的时候把宏直接定义成空，不是靠 if 判假。空宏在编译期就被抹掉，连参数表达式都不求值，二进制里不留痕迹，时序一点不受影响。这是嵌入式场景最要紧的一点。

文件级门槛，每个要打日志的 .c 里写一行。

c
#include "debug.h"

/* 定义本文件的日志级别，其余说明见 debug.h */
DEBUG_SET_LEVEL(DEBUG_LEVEL_ERR);

DEBUG_SET_LEVEL 展开成 static int dbg_level = ...，也就是每个 .c 文件各自一份静态变量，互不干扰。想让 uart.c 出 INFO、net.c 只出 ERR，各写各的就行。这就是「为每个模块提供单独的日志开关」最省事的实现方式。

编译期和运行期的区别，值得记住。

方式 关闭后的开销 能不能运行时改
编译期宏剔除 零，代码不存在 不能，要重编
运行期级别判断 一次比较加一个分支 能，改全局变量即可

两个都要。发布版本用编译期剔除，调试版本用运行期级别。构建脚本里加 -DCONFIG_ENABLE_DEBUG，或者干脆用 -DNDEBUG 反向控制，取决于你怎么组织这批宏。

还有一条容易忽略的：日志语句本身能顶掉一部分注释。INFO("retry %d/%d, sleep 200ms") 比在函数头写「这里会重试三次」信息量大得多，而且它不会过时。代码改了日志一般会跟着改，注释不会。

六、日志的输出位置 #

不要在业务代码里直接写 printf 或者 printk。日志的落点会变：开发时打屏幕，联调时打串口助手，现场要写进文件，云端要发 syslog。每一处 printf 都是一个硬编码的出口，改落点就得全仓库搜替换，改漏一个就是隐患。

正确做法是把所有出口收成一个宏，改落点只改这一处。

c
/* 换成文件、串口、环形缓冲，都只动这一行 */
#include <stdio.h>
#define PRINT               printf
落点 适用场景 特点
标准输出 PC 上本地调试 最简单，会被重定向影响
标准错误 错误日志 默认无缓冲，崩溃时也留得下
普通文件 现场、服务端 能回看历史，要管大小和轮转
串口 嵌入式板子 带宽极低，格式要短
环形缓冲 崩溃现场保留 复位后还能读出来
syslog Linux 系统服务 有分级、有轮转、能远程收

写文件最省事的版本，一个宏搞定。

c
#define TRACEOUT(p)                                          \
do {                                                         \
    time_t timeval;                                          \
    FILE  *log;                                              \
    timeval = time(NULL);                                    \
    log = fopen("log.txt", "a");                             \
    if (log != NULL) {                                       \
        fprintf(log, "%s -- %s", (p), ctime(&timeval));      \
        fclose(log);                                         \
    }                                                        \
} while (0)

两个细节。用 "a" 追加模式，别用 "w"，否则每写一条就把上一条冲掉。ctime() 的返回值自带一个换行，格式串里再写 \n 会多出空行。宏还能多带一个路径参数，日志文件的位置就可配了。

宏版本的短板：每次都 fopen / fclose，频繁打日志时文件系统开销明显；也没法统一加时间戳和位置。要正经一点，换成带变参的函数。

c
#include <stdarg.h>
#include <stdio.h>
#include <time.h>

#define LOG_FILE        "./a.log"
#define LOG_DEFAULT(fmt, ...)        log_out(LOG_FILE, __FILE__, __LINE__, fmt, ##__VA_ARGS__)
#define LOG_TOXFILE(flog, fmt, ...)  log_out(flog, __FILE__, __LINE__, fmt, ##__VA_ARGS__)

int log_out(const char *flog, const char *file, int line, const char *fmt, ...)
{
    va_list     arg;
    char        pre[128];
    char        tmp[1024];
    time_t      now;
    struct tm  *c_ptr;
    FILE       *fp;

    time(&now);
    c_ptr = localtime(&now);
    snprintf(pre, sizeof(pre), "[%04d%02d%02d%02d%02d%02d_%s.%d]",
             c_ptr->tm_year + 1900, c_ptr->tm_mon + 1, c_ptr->tm_mday,
             c_ptr->tm_hour, c_ptr->tm_min, c_ptr->tm_sec, file, line);

    va_start(arg, fmt);
    vsnprintf(tmp, sizeof(tmp), fmt, arg);
    va_end(arg);

    /* 没给文件名就打到标准输出 */
    if (flog == NULL) {
        printf("%-32.32s  %s", pre, tmp);
        return 0;
    }

    fp = fopen(flog, "at");
    if (fp == NULL) {
        return -1;
    }
    fprintf(fp, "%-32.32s  %s", pre, tmp);
    fclose(fp);

    return 0;
}

调用方式就两个宏。LOG_DEFAULT 打到默认日志文件 ./a.log；LOG_TOXFILE 打到指定文件，第一个参数传 NULL 就走标准输出。

%-32.32s 是把前缀按 32 字符宽左对齐并截断，好处是对齐好看，坏处是 __FILE__ 给的是完整路径，路径一长就被切掉头，只剩文件名尾巴。想让前缀留全，改成 %s；想缩短，编译时加 -D__FILE__='"$(notdir $<)"' 之类的工程技巧，或者自己在宏里传 __FILE_NAME__。用 vsnprintf 而不是 vsprintf，前者最多写 sizeof(tmp) - 1 字节，后者在格式化串比缓冲长时直接越界，这类 bug 在日志代码里特别常见，因为日志往往打印的是最不可控的外部数据。

七、日志的坑：缓冲与多线程 #

这是本文最要紧的一节。踩过这个坑的人，会从此对日志缓冲保持警惕。C 标准库的 stdout 有三种缓冲策略：

缓冲区类型 触发条件 典型场景
全缓冲 缓冲满、fflush、fclose、正常 exit 重定向到文件、管道
行缓冲 每遇一个 \n 连接到终端
无缓冲 立即写出 stderr、setvbuf(_IONBF)

关键点在于：同一个 printf，在终端上打是行缓冲，一条一行立刻可见；一旦 > 重定向到文件，或者被 systemd 接管，就变成全缓冲，攒够一个块才吐出去。程序正常退出时 exit() 会刷缓冲区，看不出问题；程序被信号干掉时不会。

c
#include <stdio.h>

int main(void)
{
    printf("step 1\n");
    printf("step 2\n");

    {
        char *p = NULL;
        *p = 1;          /* 这里崩，SIGSEGV */
    }

    printf("step 3\n");
    return 0;
}

直接跑，终端上能看到 step 1 和 step 2。改成 ./a.out > out.txt 再跑，out.txt 多半是空的。最该出现的两行日志，恰好因为崩溃而丢掉，段错误现场最后那几条线索就这么没了。三种解法，按场景选。

c
/* 1. 无缓冲，代价是每条日志一次系统调用 */
setvbuf(stdout, NULL, _IONBF, 0);

/* 2. 关键节点显式刷一次，代价最小 */
printf("[%s:%d] about to touch p\n", __FILE__, __LINE__);
fflush(stdout);
*p = 1;

/* 3. 错误日志走 stderr，它默认无缓冲 */
fprintf(stderr, "[ERROR] %s:%d bad pointer\n", __FILE__, __LINE__);

嵌入式还有一种做法：日志先写进一块静态环形缓冲区，崩溃后靠复位重启读回来，顺便还能把缓冲区内容搬进保留内存。这比往串口直接打更抗崩。

多线程下还有两层坑。printf 内部有锁，单次调用不会被打断，所以不会出现两个线程的字符交叉拼成乱码；但一条日志拆成多次调用就会交错。

c
/* 错：三行日志会跟别的线程穿插 */
printf("[%s:%d] ", __FILE__, __LINE__);
printf("recv len=%d ", len);
printf("type=%d\n", type);

正确做法是一次调用打完整行，或者先格式化进本地缓冲，再一次写出。

c
char line[256];
int  n = snprintf(line, sizeof(line), "[%s:%d] recv len=%d type=%d\n",
                  __FILE__, __LINE__, len, type);
if (n > 0) {
    fwrite(line, 1, (size_t)n, stdout);
}

fork 也有坑。子进程会复制父进程的缓冲区，父子双双 exit 时，同一批日志会被写两遍。fork 之前 fflush(NULL) 一次就干净了。写守护进程时这一步别省。

八、注释不是文档 #

先把两件事分开。

注释是写给下一个改这段代码的人看的，它就贴在代码旁边，跟着代码一起演进。文档是给使用者看的，讲接口、讲用法、讲约束，独立成册。两者不能互相顶替：指望注释当文档，结果是使用者得去翻实现；指望文档替代注释，结果是改代码的人看不到约束。

Doxygen 这类工具存在的意义就在这：它不是让你多写一遍文档，而是把注释按约定格式重新组织，直接从源码结构生成参考手册。写一次，两处用。它的前提是注释得守规矩——Doxygen 只处理与程序结构相关的注释，函数、类、文件的说明它管，函数体内部的普通注释它不管。

所以注释要分层：

层 位置 读者 格式要求
文件头 文件最上面 接手整个模块的人 固定字段，便于检索
接口 函数声明、类声明前 调用方 Doxygen 指令，能生成文档
实现 函数体内 改这段逻辑的人 自由行文，讲取舍和坑
数据 全局变量、结构体成员后 读数据含义的人 取值范围、单位、谁改

同一句注释，位置错了，价值就归零。把「这个参数不能传 NULL」写在函数体内部，调用方永远看不到。

还有一条底线：过时的注释比没有注释更糟。注释说「这里不会为 NULL」，代码却早就允许传 NULL 了，下一个人照注释写，就是一次崩溃。改代码时顺手改注释，是硬要求。

九、注释该写什么：写为什么，不写是什么 #

一条原则就够用：代码说明「做了什么」，注释说明「为什么这么做」。代码是精确的、可执行的、能被编译器检查的。任何用自然语言复述代码的注释，都在制造第二份需要同步维护的真相，而且这份真相没人检查。

坏注释 问题 改法
i++; /* i 加一 */ 复述代码 删除
/* 循环 10 次 */ for (i=0;i<10;i++) 复述代码 删除
/* 返回错误 */ return -1; 复述代码 说明哪种情况返回、调用方怎么处理
/* 打开文件 */ 复述代码 说明为什么用这个模式、失败怎么兜底
/* 这里加 1 */ 复述代码 说明这个 1 的来历，比如包头长度
/* TODO */ 没有信息 写清要做什么、什么条件下能做
/* 修改于 2019 */ 版本库已有 删除，看 git log

看个典型例子。

c
/* 差：整段都在复述代码 */
static int check_len(int len)
{
    if (len > 1024) {      /* 如果 len 大于 1024 */
        return -1;         /* 返回 -1 */
    }
    return 0;              /* 返回 0 */
}

这段注释删掉，代码一点没变难懂。它唯一的贡献是占了六行。

换成讲「为什么」：

c
/*
 * 1024 不是随便定的：下位机固件把接收缓冲固定成 1024 字节，
 * 超出部分会被它直接丢弃且不回错误码，所以这里必须先拦住。
 * 固件升级到 2.x 之后这个上限会变成 4096。
 */
#define MAX_RECV_LEN 1024

static int check_len(int len)
{
    if (len > MAX_RECV_LEN) {
        return -1;
    }
    return 0;
}

这段注释回答的是「为什么是 1024」和「什么时候可以改」。这两件事，代码永远说不出来。

值得写的「为什么」有五类，共同点是代码本身说不出来。

反直觉的决策：为什么这里用轮询不用中断，为什么锁要加在这行而不是上一行。

绕开的坑：哪些写法试过、为什么不能用。

c
/*
 * 这里不能用 memcpy：目标缓冲由上层传入，不保证 4 字节对齐，
 * 在 ARMv7 上会触发对齐异常。逐字节拷贝慢，但安全。
 */
for (i = 0; i < n; i++) {
    dst[i] = src[i];
}

外部约束：协议里某个字段的口径、某个寄存器的时序要求、某个库的历史 bug。

c
/*
 * 必须先写 CTRL 再写 DATA。芯片手册 12.4 节：
 * 顺序反过来时 DATA 会被下一拍的 CTRL 覆盖，实测偶发丢字节。
 */

取舍的代价：为什么明知这段代码丑还留着。还没做的事：带条件的 TODO 比裸 TODO 有用。

c
/*
 * 临时兼容 2018 年前出厂的板子：它们的 EEPROM 校验和算错了一位。
 * 等这批设备退网（预计 2027 年）后可以整段删掉。
 */

/* TODO(zhang): 现在每次重连都重建整个连接池。
 * 等 3.2 的连接复用上线后，这里改成增量更新。 */

判断标准很简单：一句注释删掉之后，读者会不会多花五分钟。会，就留；不会，就删。

十、函数头注释的规范 #

接口层的注释要能批量生成文档，就得用固定字段。字段固定了，人才扫得快，工具也才有东西可抓。

函数头用这一套。

c
/*************************************************
 * Function:       函数名称
 * Description:    函数功能、性能上的说明
 * Calls:          本函数调用的其它函数清单
 * Called By:      调用本函数的函数清单
 * Input:          每个入参的作用、取值说明及参数间关系
 * Output:         输出参数说明
 * Return:         返回值说明
 * Others:         其它说明
 * Table Accessed: 被读取的表（仅涉及数据库操作时填）
 * Table Updated:  被写入的表（仅涉及数据库操作时填）
 *************************************************/

Calls 和 Called By 常被当成形式主义，其实它们是一张现成的调用图。要改函数签名、要删一个看似没人用的函数，先扫一眼 Called By，影响面当场就出来了。大型工程里这两个字段省下的排查时间，比写它们的时间多。

全局变量的注释要交代三件事：它是什么、能取哪些值、谁能改。

c
/*
 * SCCP 转换错误码。
 *
 * 含义：SCCP 做全局码（GT）翻译失败时，记录最近一次失败原因。
 * 取值：0 = SUCCESS
 *       1 = GT 表项错误
 *       2 = GT 翻译失败
 *       其它 = 未使用
 * 修改：本模块内只允许 SCCPTranslate() 写；
 *       其它模块通过 GetGTTransErrorCode() 读。
 */
static int g_gt_trans_err;

「取值」这一项最容易被漏掉，而它恰是最有用的。看到一个整型变量返回 2，没有这张表，你得去翻实现才知道 2 是什么。

文件头放文件最上面，字段和函数头不同。

c
/************************************************************
 * Copyright (C), 1988-1999, Huawei Tech. Co., Ltd.
 * FileName:    test.c
 * Author:      Version:    Date:
 * Description: 模块职责，与其它模块的接口、输出值含义、
 *              参数间的控制与依赖关系
 * Function List:
 *   1. InitXxx()     完成初始化
 *   2. ProcessXxx()  主处理循环
 * History:
 *   <author>  <time>    <version>  <desc>
 *   David     96/10/12  1.0        创建
 ***********************************************************/

配置文件也顺手写上，格式一样，字段换成配置项的含义。

text
/*************************************************
 * File name:   app.cfg
 * Author:      Version:  Date:
 * Description: 各配置项的含义、取值范围、参数之间的
 *              控制、顺序、独立或依赖关系
 * Others:      其它说明
 * Function List: 主要函数列表，每条含函数名及简要功能
 * History:
 *   1. Date:  Author:  Modification:
 *************************************************/

History 字段在有了 Git 之后价值下降，但对外交付的代码仍然有用：客户手上那版是多少号、改了什么，文件头里一眼能看到。要让这批注释变成可检索的文档，就上 Doxygen。

安装三件套。Doxygen 本体必须有；graphviz 用来画类之间和文件之间的调用关系图，不需要这功能可以不装；Windows Help Workshop 用来生成 CHM，只出 HTML 就不用装。流程三步：源码里按 Doxygen 格式写注释，用 Doxywizard 配一次，跑 Doxygen 生成。

注释格式有四种写法，选一种用到底。

c
/* 多行用这两种，等价 */
/**
 * JavaDoc 风格
 */
/*!
 * Qt 风格
 */

/* 单行用这两种，连续多行会合并成一段 */
/// 单行注释
//! 单行注释的另一种写法

/* 写在代码后面要反过来写，标记放前面，
 * 只能用于结构体成员和函数参数 */
/*!< 后置注释 */
/**< 后置注释 */
//!< 后置注释
///< 后置注释

Doxygen 默认认为注释是在解释它后面的代码，所以后置注释必须用带 < 的形式，否则会被算到下一个成员头上。

指令是 Doxygen 的另一半。常用的这几个：

指令 用途
@file 文件级说明，注释要放在文件开头
@brief 一句话简易说明
@author 作者信息
@param 参数名加说明，格式 @param 名字 说明
@return 返回值整体说明
@retval 某个具体返回值的含义，格式 @retval 值 说明

\ 和 @ 完全等价，\file 就是 @file，看团队习惯选一个。简易说明和详细说明的划分规则：第一段到空行（或第一个句点）为止是简易说明，之后算详细说明。列表页只显示简易说明，所以用 @brief 明确标出来更稳，别指望工具靠段落猜。落成代码就是这样。

c
/**
 * @file example.h
 * @brief 本范例的 include 文件，只定义 Example 结构和它的接口。
 * @author garylee@localhost
 */

#define EXAMPLE_OK  0     ///< 定义 EXAMPLE_OK 宏为 0

/** @brief Example 结构，只用于演示注释格式，不含业务逻辑 */
struct example {
    int var1;             ///< 私有语义，仅本模块使用
    int var2;             ///< 公开语义，外部可读
};

/**
 * @brief 两个参数相加，不做溢出检查，调用方自己保证不越界。
 *
 * @param a 加数，取值 0~127。
 * @param b 加数，按 char 传入，函数内提升为 int。
 * @return 两个参数之和。
 */
int ex_add(int a, char b)
{
    return a + b;
}

/**
 * @brief 原样返回传入的指针。
 *
 * @param c 字符串指针，允许为 NULL。
 * @retval NULL     传入的是空指针。
 * @retval 非 NULL  与入参相同。
 */
char *ex_echo(char *c)
{
    return c;
}

填完注释，一次命令出文档。

bash
doxygen -g Doxyfile          # 生成配置文件
doxygen Doxyfile             # 出 HTML 到 html/ 目录

十一、注释的常见坏味道 #

坏味道 表现 处理
复述代码 i++; // i 自增 删
日记式 // 2021.3.5 张三 改了点东西 删，看 git log
注释掉的代码 大段 // 掉的旧实现 删，版本库里有
#if 0 垃圾场 一堆永不编译的分支 删或说明保留原因
与代码不符 注释说不会为 NULL，代码说会 立刻改，这是缺陷
猜谜式 TODO // TODO 修一下 写清做什么、什么条件下能做
分隔线过量 //===== 分割 ===== 满屏 留少量，别当装饰

重点说两个。被注释掉的代码必须删。它的存在只说明一件事：作者不确定以后要不要用。这份不确定应该留在版本库的提交里，不能留在源码里。留在源码里的结果，是下一个人读代码时被迫跳过一大片灰色文字，还得判断它到底还有没有用。

与代码不符的注释是最危险的一类，因为它会主动误导人。注释说「调用前必须持锁」，代码却在函数内部自己加锁——照注释写的人会在外面再锁一次，直接死锁。改代码时看到附近有不一致的注释，顺手改掉，这是纪律。

十二、静态检查是什么 #

静态检查是不运行程序，只用工具读源码，找可疑写法。它落在三层里的最前面。

工具 抓什么 是否运行程序
编译器告警 类型不匹配、未使用变量、格式串错误 否
CppCheck 越界、空指针解引用、资源泄漏、可疑逻辑 否
运行期工具 真实内存错误、真实竞态 是

编译器告警是第一道，也是最便宜的一道。开 -Wall -Wextra，把它当错误处理（-Werror），能拦掉一大片低级问题。很多人跳过这一步直接找静态检查工具，顺序反了。

CppCheck 的定位很明确：专注编译器抓不到的 bug，不纠缠语法错误的检查。语法错了编译器会拦，CppCheck 不重复这件事，它把力气花在「语法对但逻辑可疑」上。例如这段。

c
int n = 10;
char *buffer = (char *)malloc(n);
buffer[n] = 0;

语法完全合法，编译器不会有意见。CppCheck 会指出来：buffer 只有 10 字节，合法下标是 0~9，buffer[10] 越界一个字节。这类错一位的写法，后果从「程序悄无声息地改坏了相邻内存」到「直接崩溃」都有。顺带还能发现 malloc 没判 NULL、以及后续没有对应的 free，一次检查，三个问题。

同类工具里还有 pc-lint，功能更全，但收费，配置也复杂。CppCheck 免费开源，装完就能跑，适合日常用。两者不冲突，正式项目可以都用。静态检查的边界也要清楚：它靠模式匹配和抽象解释，不懂你的业务。它报的问题有真也有假，报得越多，人工筛的成本越高。所以规则要挑，不能全开。

十三、CppCheck 的用法 #

装法按平台选一个，Windows 去官网下安装包，装完有 cppcheck 和 cppcheck-gui 两个可执行文件。

bash
sudo apt install cppcheck     # Ubuntu / Debian
brew install cppcheck         # macOS

命令行最常用，一条就能跑整个目录。

bash
cppcheck --enable=all --inconclusive -I include src/

参数不少，记住下面这些够日常用。

参数 作用
--enable=all 打开全部检查项
--enable=warning,style,performance 按类别选，不写 all 时默认只开 error
--inconclusive 连低确定度的结论一起报，宁可多报
-I <dir> 加头文件搜索路径
-D<macro> 定义宏，配合条件编译
--std=c99 指定语言标准，C 工程必加
--template=gcc 输出格式，配 IDE 能点击跳转
--output-file=result.txt 结果写文件，方便存档和比对
--suppress=<id> 抑制某条规则
--quiet 不打印进度和统计
--verbose 打印更详细的进度
--check-config 只检查头文件和宏配置是否找得全

--check-config 值得单独提。头文件路径漏了一个，CppCheck 会因为看不到声明而沉默地少报很多问题，你以为干净了，其实它根本没看懂那段代码。第一次接入新工程，先跑这个。

GUI 版本 cppcheck-gui 适合看结果：选文件或目录，勾检查项，点一下开始，问题列表可点击跳到源码。适合单人排查，不适合自动化。嵌进 IDE 里用更顺手。

Visual Studio：工具 => 外部工具 => 添加，标题填 Cppcheck，命令填 C:\Program Files (x86)\Cppcheck\cppcheck.exe（按实际路径改），参数填 --quiet --verbose --template=vs $(ItemPath)，初始目录填 $(ItemDir)，勾上「使用输出窗口」，然后一路「上移」把它挪到列表顶部。确定之后，工具菜单里就能直接对当前文件跑检查，双击结果跳行。

Qt Creator：工具 => 外部 => 配置... => 添加，命令填 CppCheck 可执行文件路径，参数填 --enable=all，初始目录填项目根目录。之后 工具 => 外部 => CppCheck 就能检查指定目录。

参数里的 --template 是重点。--template=vs 输出 文件(行): 错误 的格式，VS 认；换成 gcc 就是 GCC 的格式，Qt Creator 和 Vim 的 quickfix 认。格式对了，IDE 才能把它当编译错误一样跳转。

十四、检查规则的选择与抑制 #

--enable 后面跟的是检查类别，全开不等于查得好。

类别 查什么 建议
error 确定性的错误，默认开启 必须开
warning 可疑写法，默认开启 必须开
style 未使用函数、冗余赋值、多余作用域 稳定后开
performance 按值传大对象、循环里反复算长度 建议开
portability 位域、类型宽度、非标准扩展 跨平台时开
information 纯信息，噪音最多 按需

上手顺序是阶梯式的。先把 error 和 warning 清到零，再加 style，最后看 performance。一次开 --enable=all --inconclusive，几千条结果糊在屏幕上，人只会关掉它，不会修它。误报要抑制，但别无声抑制。

bash
cppcheck --enable=all --suppress=missingIncludeSystem src/             # 临时排查
cppcheck --enable=all --suppressions-list=cppcheck-suppress.txt src/   # 工程级清单

单点抑制写在代码里，就近生效。

c
/* 这个数组下标由上面的 if 保证了范围，cppcheck 看不出来 */
/* cppcheck-suppress arrayIndexOutOfBounds */
buf[header_len + i] = 0;

三种方式对应三种性质：临时排查用命令行，规则级的用清单文件，单点的用内联。清单文件要进版本库，否则换台机器结果就不同。抑制必须写理由，一条没有理由的 cppcheck-suppress，下一个人不敢删也不知道该不该删，最后它就一直留着，掩盖真问题。还要认清边界：CppCheck 靠模式匹配和抽象解释，它不懂你的业务规则，也没有运行时信息。它说是 bug 的地方有一半要人工判断，它说没问题的地方也会藏着 bug。它是筛子，不是门神。

十五、把检查接进 CI #

靠人记得跑 = 没人跑。接到 CI 里，它才会真的执行。

bash
#!/bin/bash
set -u

cppcheck --version

cppcheck --enable=warning,style,performance \
         --inconclusive --std=c99 \
         --template=gcc \
         --output-file=cppcheck.log \
         -I include src/ 2>&1

if grep -qE ':[0-9]+:.*(error|warning):' cppcheck.log; then
    cat cppcheck.log
    exit 1
fi

几个实操细节。不写 set -e，因为 CppCheck 检测到问题会返回非零，set -e 会让脚本在拿到完整日志之前就退出，看不到现场。--template=gcc 是为了让 CI 平台能把结果解析成注释，直接贴在合并请求的对应行上。全量检查在工程大了之后会变慢，日常只查改动文件。

bash
git diff --name-only origin/main...HEAD -- '*.c' '*.h' | \
    xargs -r cppcheck --enable=warning,style --template=gcc

存量问题一次修不完的，做基线。第一次全量跑，把结果存成基线文件，只对新增的问题卡门禁。这样老代码不被拖进来，新代码拦住。本地再加一道 pre-commit 钩子，改了 .c / .h 就顺手跑一次单文件检查，三秒的事，比等 CI 报错快得多。

一个顺序值得记住：编译器告警当错误处理，CppCheck 卡在 CI，日志覆盖关键路径。三件都做到，很多问题在提交之前就没了。

十六、易错点速查 #

现象 原因 处理
崩溃前最后几行日志不见了 全缓冲，缓冲区没刷 fflush，或 setvbuf(_IONBF)，或改走 stderr
终端上正常，重定向到文件就没日志 行缓冲变全缓冲 同上
一条日志被劈成两半 多线程里拆成多次 printf 先 vsnprintf 进本地缓冲，再一次写出
日志重复打印两遍 fork 复制了缓冲区 fork 前 fflush(NULL)
发布版本还在打日志 只做了运行期判断 加编译期宏剔除
关掉日志后时序问题消失了 日志本身影响了时序 降级别，不靠删日志定位
日志里出现密码和身份证号 打印了原始结构体 敏感字段白名单打
注释说参数不会为 NULL，代码却崩了 注释过时 改代码的同一次提交里改注释
函数头的 Called By 空着 调用关系变了没同步 删函数前用 grep 复核
生成的文档里函数说明是空的 注释写在函数体内，或没用 /** 移到声明前，用文档注释格式
CppCheck 什么都没报 头文件路径不全，没看懂代码 先跑 --check-config
抑制标记越来越多 没有基线和理由 抑制必须写原因，清单进版本库
IDE 里结果点不动 --template 格式不匹配 VS 用 vs，GCC 系用 gcc
有内存越界但 CppCheck 放过 下标来自运行期数据 靠 ASan、Valgrind 补位

最后收一句。日志解决「事后能查」，注释解决「下一个人看得懂」，静态检查解决「还没跑就发现」。三样都不需要停下程序，所以它们是生产环境里唯一可用的排障手段。
