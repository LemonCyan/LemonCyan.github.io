第15章 预处理器与宏 #

本章目标：能读懂并写出正确的对象宏与带参宏，能用条件编译组织跨平台代码与头文件卫哨，能识别宏展开导致的求值陷阱与优先级陷阱。

15.1 引子：为什么需要这一章 #

C 程序在交给编译器之前，先经过一个独立的处理阶段——预处理（preprocessing）。它既不认识 int，也不懂函数调用与类型，只做一件事：按行扫描源文件，把以 # 开头的指令执行掉，再把处理后的文本交给编译器。宏替换、文件包含、条件编译全部发生在这一层。

理解这一层有三个实际理由。其一，宏是 C 中唯一不产生函数调用开销的抽象手段，代价是完全没有类型检查，副作用由使用者承担，稍不留神就会出现「同一表达式被求值两次」这类缺陷。其二，条件编译是跨平台差异与调试开关的标准做法，读任何真实 C 工程都躲不开 #ifdef。其三，很多看似莫名其妙的工程现象——头文件包含两次就报重复定义、明明写了函数却报找不到符号——根因都在预处理阶段。

本章与 第16章 是同一条线索的两段：本章讲预处理对文本做了什么，第16章 讲这些文本被编译成目标文件之后如何拼装成一个可执行程序。

15.2 预处理指令概览 #

按照 ANSI 标准的定义，预处理程序负责处理一系列指令，这些指令都以符号 # 开始且必须独占一行；预处理在编译之前分析和修改代码，使源代码可以被更灵活地编译。它与普通语句的书写习惯不同：指令不加分号，行尾若误加分号，该分号会被当作替换文本原样保留。

指令 作用 书写要点
#define 定义宏（macro），把名字替换为指定文本 不加分号；替换文本在行末结束
#undef 取消一个已定义的宏 之后可以重新定义同名宏
#include 把指定文件的全部内容复制到该行位置 双引号与尖括号的搜索路径不同
#if / #elif / #else / #endif 按常量表达式选择性地编译代码 必须以 #endif 收口
#ifdef / #ifndef 按宏「是否已定义」选择性地编译代码 常与 #define 配对做包含卫哨
#error 立即中断编译并输出指定信息 常用于检查编译环境
#line 改写 __LINE__ 与 __FILE__ 的值 多用于代码生成器
#pragma 向编译器传递实现相关的特殊要求 不支持该选项的编译器会忽略它

预处理阶段工作在字符与记号这一级：它不认识类型，除字符串与括号配对之外也不做语法检查。正因为如此，宏在替换阶段不会报出「参数类型不对」，只会在后续的编译阶段以别的形式暴露问题——这是本章所有陷阱的总根源。

15.3 #define 与对象式宏 #

宏定义的基本形式是宏名加替换文本，两者之间可以有多个空白符，替换文本的结束只能以新行终止：

c
#define macro-name char-sequence

例如用两条指令定义两个方向常量：#define LEFT 1 与 #define RIGHT 0。 此后源程序中每遇到 LEFT 或 RIGHT，预处理程序都会把它替换为 1 或 0。已经定义的宏可以在别的宏里被引用，因此多个相关常量可以层层构造：

c
#define ONE 1
#define TWO ONE + ONE

宏也被用来定义标准化的提示信息：

c
#define ERROR_MSG "An error has occurred."

如果替换文本长于一行，可以在行尾写一个反斜线 \ 表示续行，下一行接着算同一条指令：

c
#define LONG_STRING "This is a very very long \
string that continues here."

使用对象式宏时有三条容易忽略的规则：

规则 说明 违反后的后果
不写分号 宏定义本身是一条指令，不是语句 分号进入替换文本，展开处出现多余符号
宏体不能递归 预处理器展开一个宏时禁止同名宏再次展开 不会得到递归调用，只会停在第一层
没有作用域 从定义行起对其后全部代码生效，直到文件结束或被 #undef 取消 头文件里的宏污染所有包含它的源文件

下面这段程序把对象宏与标准输出配合起来使用，注意 #include 单独成行、指令行末尾没有分号：

c
#include <stdio.h>

#define LEFT  1
#define RIGHT 0
#define ERROR_MSG "An error has occurred."

int main(void) {
    int dir = LEFT;                 /* 预处理后这一行是 int dir = 1; */
    if (dir == RIGHT) {
        printf("%s\n", ERROR_MSG);
    }
    return 0;
}

15.4 带参宏：括号、空格与副作用 #

把宏做成「像函数一样」调用，是 C 里最常用的技巧，也是最容易出错的地方。一个交换两个变量的宏看上去很简洁：

c
#define SWAP(a, b) { int temp = a; a = b; b = temp; }

调用 SWAP(x, y) 时整行被替换为一个语句块。它在单独一条语句中成立，但放进 if 分支就出问题：if (x) SWAP(a, b); else ... 展开后花括号后面多了一个分号，else 失去了可配对的 if。惯用修法是用 do { ... } while (0) 包住语句序列，让整条宏在任何位置都表现得像一条普通语句：

c
#define SWAP(a, b) do { int temp = (a); (a) = (b); (b) = temp; } while (0)

15.4.1 缺少括号会破坏优先级 #

宏展开是纯粹的文本替换，不包含任何优先级判断。下面两个对照宏说明了后果：

c
#define FUN1(a, b) a * b
#define FUN2(a, b) (a) * (b)

调用 FUN1(2 + 3, 3 + 2) 时展开结果是 2 + 3 * 3 + 2，按乘法优先计算得到 13；而 FUN2 展开为 (2 + 3) * (3 + 2)，结果是 25。结论很明确：替换文本中的每一个形参都要单独加一层括号，整个替换文本最好再加一层。

同理，判断奇偶的宏若写成 #define IS_ODD(x) x % 2，在 IS_ODD(a + b) 处会展开成 a + b % 2，语义完全变了。正确写法是 #define IS_ODD(x) (((x) % 2) != 0)。

15.4.2 宏名与左括号之间不能有空格 #

定义带参宏时，宏名与后面的左括号必须紧挨着：

c
#define S(r) 3.14 * r * r    /* 正确的带参宏 */
#define S (r) 3.14 * r * r   /* 错误：S 被当成对象宏，替换文本是 "(r) 3.14 * r * r" */

第二种写法里，预处理器只把 S 看作宏名，后面整串都是替换文本，此时它不再接收参数。此后代码中任何 S 都会被换成这串文本，函数式调用 S(2) 会展开成毫无意义的 (r) 3.14 * r * r(2)，报错信息还会指向莫名其妙的位置。

15.4.3 参数被多次求值 #

即使括号全部加对，带参宏仍然有一个函数不会有的问题：形参在替换文本中出现几次，实参就会被求值几次。求最大值的宏是经典反例：

c
#define MAX(a, b) ((a) > (b) ? (a) : (b))

int i = 3;
int j = 5;
int m = MAX(i++, j);   /* 展开后 i++ 出现两次，i 被自增两次 */

这个表达式的意图是「比较之后取较大的那个」，但 i++ 同时出现在条件与取值两处，实际执行了两次自增，两次求值之间副作用还可能改变另一个操作数。凡是实参带有 ++、--、赋值或函数调用，都不能交给这类宏。

彻底的解决办法是把宏换成一个真正的函数，让编译器决定是否内联：

c
#include <stdio.h>

static inline int max_int(int a, int b) {
    return (a > b) ? a : b;
}

int main(void) {
    int i = 3;
    int j = 5;
    int m = max_int(i++, j);     /* 实参只求值一次，i 只自增一次 */
    printf("%d %d\n", m, i);
    return 0;
}

内联函数（inline function）既有函数级别的类型检查与单次求值语义，又能通过 inline 关键字建议编译器把函数体就地展开，从而保住宏的性能优势。static inline 写在头文件里的做法、以及它在不同编译单元中的链接语义，参见 第19章「内联函数与语言级性能手段」。

15.4.4 宏与函数的取舍 #

素材把两者的关系概括为「以时间和空间进行权衡的策略」：宏用更快的方式替代代码，函数则通过严格的类型检查和更好的内存管理保证安全性与可维护性。按这个思路整理如下：

维度 带参宏 函数
展开时机 预处理阶段做文本替换 运行时调用
类型检查 没有，只要文本能拼起来就通过 有，实参与形参类型必须匹配
参数求值次数 替换文本中出现几次就求值几次 每次调用只求值一次
调用开销 无压栈出栈 有调用开销，可用 inline 缓解
代码体积 每次展开都复制一份代码 全程序只有一份
调试体验 断点难落在宏内部，报错行号指向调用点 可以直接单步进入
适用场景 常量、条件编译、日志、无法用函数表达的场景 一切含有逻辑的代码

15.5 # 字符串化与 ## 记号粘连 #

两个操作符只能在宏定义中使用，它们决定了宏能构造出怎样的代码形态。

15.5.1 # 把实参变成字符串 #

# 操作符（字符串化 stringification）作用于宏形参，把实参的原始拼写整体包进一对双引号，得到字符串字面量（string literal）：

c
#include <stdio.h>

#define mkstr(s) #s

int main(void) {
    printf(mkstr(I like C));
    return 0;
}

展开后是 printf("I like C")，输出 I like C。这个能力常与日志宏配合，用来把「表达式原文」和「表达式取值」一起打印出来，排查问题时无需手写重复的字符串。

15.5.2 ## 把两个记号粘成一个 #

## 操作符（记号粘连 token pasting）把左右两侧的记号拼接成单个记号，常用于批量生成类型化代码：

c
#include <stdint.h>

#define def_u32_array(__name, __size) uint32_t array_##__name[__size]

def_u32_array(sample_buffer, 64)

最后一行展开为 uint32_t array_sample_buffer[64]，一次定义就得到名为 array_sample_buffer 的数组。

素材还给出了另一种用法：把宏参数粘到函数名前缀上，生成一族按类型命名的排序函数，调用处再用函数指针取出具体实现：

c
#define SORT(X) sortFunction##X

调用 SORT(3)(array, elements, element_size) 展开为 sortFunction3(array, elements, element_size)。配合函数指针表，这就是 C 里实现「泛型分发」的常见手法。

使用 ## 时要注意两点：粘连只在预处理阶段生效，参与拼接的两段必须是合法的记号；粘出来的名字若在程序中不存在，报错会出现在编译或链接阶段，而错误信息里只有拼好的名字，看不出它来自哪个宏。

15.6 可变参数宏 #

形参列表以省略号结尾，就得到可变参数宏（variadic macro）。函数宏体中的 __VA_ARGS__ 代表省略号捕获到的全部实参：

c
#include <stdio.h>

#define log_info(__STRING, ...) printf(__STRING, __VA_ARGS__)

int main(void) {
    log_info("count = %d\n", 10);
    return 0;
}

调用 log_info("count = %d\n", 10) 展开为 printf("count = %d\n", 10)。问题出在没有可变实参的时候：log_info("done\n") 会展开成 printf("done\n", )，多出一个逗号，编译无法通过。

C99 引入的 GNU 扩展写法 ,##__VA_ARGS__ 用来解决这个矛盾：当 __VA_ARGS__ 为空时，它连同前面的逗号一起被删除，因此下面这条宏在两种调用下都成立：

c
#define log_info(__STRING, ...) printf(__STRING, ##__VA_ARGS__)

注意：,##__VA_ARGS__ 是 GCC 与部分编译器的扩展，不属于 C 标准语法。标准 C99 只在省略号至少匹配一个实参时才保证展开结果合法，需要「可省略的尾部参数」时应先确认目标编译器是否支持该扩展，或改用显式写法的宏。

素材还展示了利用「逗号 + 默认值」的写法：把可选参数前的那段逗号表达式当作默认值来用，例如

c
#define EXAMPLE(...) (默认值 ,##__VA_ARGS__)
#define XXXX_INIT(...) xxxx_init((NULL ,##__VA_ARGS__))

有实参时，逗号表达式取最后一个操作数，实参生效；没有实参时，逗号被删除，只剩默认值生效。这类技巧本质上依赖于逗号运算符与预处理删除逗号的组合，可读性较差，在需要频繁维护的代码里应写清注释或改用函数重载式的命名区分。

15.7 条件编译 #

条件编译（conditional compilation）让同一份源码在不同环境下编译出不同结果，调试开关、平台差异、兼容旧接口都依赖它。最基本的三种形态如下：

c
#if 条件表达式
    /* 条件为真时参与编译 */
#else
    /* 条件为假时参与编译 */
#endif

c
#ifdef 宏名
    /* 宏已定义时参与编译 */
#else
    /* 宏未定义时参与编译 */
#endif

c
#ifndef 宏名
    /* 宏未定义时参与编译 */
#endif

#if 后接的是常量表达式，可以比较宏的取值，因此版本判断可以写成 #if VERSION >= 2 这样的形式；#ifdef 与 #ifndef 只关心「有没有定义」，不关心值是多少。三个以上分支用 #elif 串联：

c
#define PLATFORM 2

#if PLATFORM == 1
    #define PATH_SEP '/'
#elif PLATFORM == 2
    #define PATH_SEP '\\'
#else
    #error "未知平台，请检查 PLATFORM 的取值"
#endif

#undef 用于取消已有定义，使同名宏可以被重新定义。素材给出的用法是：在需要临时屏蔽某个宏的代码段前后分别使用 #undef 与 #define，避免宏的语义扩散到不该生效的位置。

组合宏是否存在时，标准写法是 #if defined(MY) 与 #if !defined(DEBUG)，其中 defined 是预处理阶段专用的运算符，只能出现在 #if 与 #elif 的表达式里。多个条件可以用 && 与 || 连接：

注意：defined 是运算符而不是宏，书写时不要给它加括号写成 #if definedX(MY) 之类；也不要写成 #ifdef defined(MY)，把两个不同层次的机制混用会得到与预期相反的结果。

条件编译最容易出问题的地方是「被排除的代码也必须能通过词法检查」。#if 0 ... #endif 里被跳过的代码不会参与编译，但预处理阶段仍会把它们切分成记号，因此括号或注释不配对时，报错位置会指向整个 #if 块的末尾，而不是真正出错的那一行。

15.8 #include 与包含卫哨 #

#include 的作用是把目标文件的全部内容复制到该行所在位置，之后与其他代码一同参与编译。尖括号与双引号的区别在于搜索起点：

写法 搜索顺序 典型用途
#include <stdio.h> 只在系统目录（如 /usr/include）与编译器的内建路径中查找 标准库头文件
#include "myheader.h" 先在源文件所在目录查找，找不到再到系统目录查找 工程自己的头文件

需要把额外的目录加入搜索路径时，用编译选项 -I 指定，例如 gcc -I /home/fs/include main.c 会把 /home/fs/include 排在系统目录之前。嵌套包含的深度上限由具体实现决定，不要依赖某个固定数字。

同一个头文件被两条路径包含两次，是最常见的工程问题。解决办法是在头文件里写上包含卫哨（include guard）：

c
#ifndef _TEST_H_
#define _TEST_H_

/* 这里放声明：宏常量、结构体、函数原型、extern 变量声明 */

#endif

第一次包含时 _TEST_H_ 尚未定义，条件成立，内容被展开并把该宏定义下来；第二次包含时条件不成立，整段内容被跳过。注意卫哨宏名应当全局唯一，用文件名衍生的写法（如 _TEST_H_）比 TEST_H 之类泛名更安全。

注意：包含卫哨只能防止「同一编译单元内重复包含」，无法阻止两个不同的源文件各自包含一份。凡是把变量定义或函数实现写进头文件的写法，都会在链接阶段变成重复定义的符号，处理办法见 第16章。

15.9 #error、#line 与 #pragma #

15.9.1 #error 在编译期给出明确提示 #

#error 让编译立即终止并打印指定信息。它的参数直接写成记号序列即可，不需要加引号；加了引号反而会把引号一并输出：

c
#ifndef __STDC__
    #error "本程序需要一个符合 ANSI 标准的 C 编译器"
#endif

在大型工程里，把「不满足前提条件」的情况交给 #error 处理，比让编译器在几百行之后报一个语法错误要友好得多。

15.9.2 #line 改写行号与文件名 #

#line 把紧随其后那一行的 __LINE__ 改成指定值，并可同时改写 __FILE__：

c
#line 100 "generated.c"

这条指令的主要使用者是代码生成器与模板工具：生成的代码需要把报错位置映射回模板源文件，而不是映射到那份自动拼出来的中间文件。

15.9.3 #pragma 与实现相关的编译控制 #

#pragma 用于向编译器传递实现相关的特殊要求，标准并未规定它的具体内容，因此换一个编译器可能完全不起作用，也可能被忽略。素材整理的常用形态如下：

形式 作用 平台
#pragma once 当前头文件只被包含一次，替代包含卫哨 MSVC、GCC、Clang 均支持
#pragma warning(push) / #pragma warning(disable:4996) / #pragma warning(pop) 保存、关闭、恢复指定编号的警告 MSVC
#pragma pack(push, 1) / #pragma pack(pop) 按 1 字节对齐结构体成员，取消填充 编译器相关但普遍支持
#pragma message("...") 编译时输出一条提示，不中断编译 MSVC、GCC
#pragma weak 符号 把符号声明为弱符号，允许被同名强符号覆盖 GCC
#pragma poison 标识符 使用该标识符即报错，用来禁止危险函数 GCC
#pragma GCC optimize("O3") 对指定范围的函数改用指定优化级别 GCC
#pragma GCC target("sse4.2") 对指定范围的函数启用指定指令集 GCC

#pragma pack 是最常用的一个，它直接改变结构体的内存布局。素材给出的例子是：结构体包含 char a、int b、short c 三个成员，默认对齐下成员之间会插入填充字节，按 1 字节对齐后紧凑排列，sizeof 的结果随之变小：

c
#include <stdio.h>

#pragma pack(push, 1)
struct Example {
    char a;
    int b;
    short c;
};
#pragma pack(pop)

int main(void) {
    /* 1 字节对齐时三个成员紧密相邻，不再插入填充 */
    printf("%zu\n", sizeof(struct Example));
    return 0;
}

注意：收紧对齐会降低访问效率，某些架构上对未对齐地址的访问甚至不受支持。跨进程通信、写文件格式、网络协议这类必须固定布局的场景才值得使用，并且应当用 #pragma pack(push, ...) 与 #pragma pack(pop) 成对包裹，把影响限制在目标结构体的范围内。

#pragma once 与包含卫哨的作用相同，写法更短，但不是标准语法。可移植性优先的工程通常仍用 #ifndef 卫哨；两者混用没有问题，只是重复劳动。

15.10 预定义宏 #

编译器预先定义了一批宏，用来在代码里获取位置信息与编译环境。下表是素材中列出的常用项：

宏 展开结果 说明
__LINE__ 一个整数 当前所在的行号
__FILE__ 一个字符串 当前源文件的文件名
__DATE__ 形如 May 15 2024 的字符串 编译发生的日期，格式为「月 日 年」
__TIME__ 形如 10:30:45 的字符串 编译发生的时刻，格式为「时:分:秒」
__STDC__ 整数 1 表示编译器符合标准 C 的定义

__DATE__ 与 __TIME__ 记录的是编译时刻而不是运行时刻，每次重新编译都会变化，因此不能当作版本号使用，也没有必要在每次运行中打印它们。

用 __FILE__ 与 __LINE__ 组合出一个定位函数，是调试期常见做法：

c
#include <stdio.h>

void print_location(void) {
    printf("当前文件：%s，当前行：%d\n", __FILE__, __LINE__);
}

int main(void) {
    print_location();     /* 打印的是函数体内那一行的行号，不是调用处 */
    return 0;
}

15.11 typedef 与 #define 的区别 #

两者都能给类型起别名，但层次完全不同。typedef 是关键字，由编译器处理，做的是类型级别的重命名；#define 是预处理指令，做的是纯文本替换。素材以链表结点为例说明了差异：

c
typedef struct listnode {
    int data;
    struct listnode *next;
} *linklist;

此后 linklist 是一个类型名，可以像 int 一样声明指针。若改用 #define linklist struct listnode *，则 linklist p, q; 展开为 struct listnode * p, q;，只有 p 是指针，q 成了普通结构体变量。这是文本替换不理解语法的直接后果。

对比项 typedef #define
处理阶段 编译阶段，由编译器识别 预处理阶段，文本替换
作用对象 类型 任意记号序列
是否理解语法 是，p, q 的声明语义正确 否，容易产生意外的声明含义
调试器可见性 类型名对调试信息可见 展开后原宏名消失
适用场景 类型别名、函数指针类型、结构体标签 常量、条件编译、代码片段生成

注意：typedef 定义的类型名不能被 #undef 取消，也不能通过条件编译在同一个作用域内重复定义同名类型；若需要按平台切换类型，应配合 #ifdef 把整段 typedef 分别写在不同分支里。

15.12 小结 #

  • 预处理是编译之前的一个独立阶段，只处理以 # 开头的指令，不理解类型，除记号切分与括号配对外不做语法检查。
  • 对象式宏用于常量与文本片段，替换文本在行末结束，不加分号，可用反斜线续行，宏体内不能递归引用自身。
  • 带参宏是纯文本替换：形参不加括号会破坏优先级，宏名与左括号之间不能有空格，实参出现几次就求值几次。
  • MAX(a, b) 这类求值敏感的宏应改写为 static inline 函数，同时获得类型检查、单次求值与内联展开。
  • # 把实参字符串化，## 把记号粘成新标识符，两者只在宏定义内有效。
  • 可变参数宏用 __VA_ARGS__ 接收实参，空实参导致的逗号问题可用 ,##__VA_ARGS__ 消解，但该写法属于编译器扩展。
  • 条件编译用 #if、#ifdef、#ifndef、#elif、#undef 组织，defined 只用于 #if 表达式。
  • 头文件用包含卫哨或 #pragma once 防止重复包含；#pragma 是实现相关的开关，换编译器前应确认支持情况。

15.13 常见错误与陷阱 #

  • 宏定义行尾加了分号 → 分号成为替换文本的一部分，展开处出现多余符号并报语法错误 → 宏定义不加分号，只在调用处的语句末尾加分号。
  • 带参宏定义写成 #define S (r) ... → 宏名与左括号之间有空格，被识别为对象宏，之后所有 S 都被整体替换 → 宏名与左括号必须紧挨，定义后立即用 gcc -E 看一眼展开结果。
  • 实参带自增运算交给 MAX 宏 → 形参在替换文本中出现两次，实参被求值两次，变量被多自增一次 → 改用 static inline 函数或先把实参存入临时变量。
  • 多语句宏没有用 do { ... } while (0) 包裹 → 在 if 分支中被展开后留下空语句，else 无法配对 → 统一用 do { ... } while (0) 形式，或在宏体内不放分号。
  • 构造成员名字时误用 # 与 ## → # 给实参加引号得到字符串而不是标识符，## 拼出的名字不存在 → 按用途选择：要字符串用 #，要标识符用 ##。
  • 可变参数宏在无实参时编译失败 → 展开后多出一个逗号，如 printf("done\n", ) → 使用 ,##__VA_ARGS__（编译器扩展）或改用 printf("%s", "done\n") 这类不带尾参数的写法。
  • 头文件漏写包含卫哨 → 同一头文件被包含两次，类型与宏重复定义 → 在头文件首行加 #ifndef / #define / #endif，或用 #pragma once。
  • 用 #define 定义指针类型别名 → 文本替换导致 linklist p, q; 中只有 p 是指针 → 用 typedef 定义类型别名，让编译器按类型规则处理。

第16章 多文件工程、链接与动态库 #

本章目标：能把一个程序拆成多个源文件正确组织，掌握预处理、编译、汇编、链接各阶段的产物与分工，能在 Windows 与 Linux 上分别生成并使用静态库与动态库。

16.1 引子：为什么需要这一章 #

单文件程序写到几百行就会失控：变量名互相冲突、改一处要重编全部代码、两个人在同一个文件上改动必然互相踩踏。工程化的第一步是把代码拆成多个源文件，第二步是让这些文件能被正确拼装成一个可执行程序——而这一步由链接器（linker）完成，它并不属于编译器，出错时给出的信息形式也完全不同。

拆文件立刻带来三个新问题。第一，一个文件要用另一个文件里的函数，凭什么知道它长什么样？答案是把声明抽到共同的头文件里。第二，头文件被两个源文件包含后，里面的内容会不会被定义两次？答案取决于写的是声明还是定义，这也是 extern 与 static 在链接期语义上的分水岭。第三，一堆目标文件如何打包成库、库运行时又从哪里被找到？答案对应静态库、动态库与运行时库搜索路径。

这三件事构成本章的主线，也是 第17章 排查链接期报错的全部背景：只有知道链接器在找什么符号、按什么顺序找，才能读懂 undefined reference 一类的信息。

16.2 从源文件到可执行文件：四个阶段 #

C 程序的构建并不是「一步编译」，而是依次经过四个阶段，每个阶段都有独立的工具与中间产物：

阶段 输入 输出 常用命令 产物性质

汇编 .s .o 目标文件 gcc hello.s -c -o hello.o 机器码，但符号地址尚未最终确定
