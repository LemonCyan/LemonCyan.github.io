如何使用本教程 #

本教程按「篇—章—小节」组织，章号全局连续（第1章至第20章），既可顺序研读，也可按目录跳读。每章开头用「本章目标」说明学完能得到什么，章末固定两节：「小结」回收该章的关键结论，「常见错误与陷阱」集中列出最容易写错、最容易误解的地方，建议写完代码后回看。正文里出现「参见 第X章」的交叉引用，指向全书对应章节；需要速查零散知识点时，见 第六篇 附录A–G。

示例代码的取舍标准是「能编译、能运行」。凡是给出完整程序的，一律带 #include 与 main；凡只讲语法片段的，用 /* ... */ 省略不影响语义的部分。读者应把示例亲手敲一遍再编译，编译器给出的报错与警告往往比正文更能加深理解。素材之间互相矛盾、或者素材本身写错的少数地方，正文用「> 注意」显式标注，并给出以标准文本与实测结果为准的结论。

编译与运行（gcc 常用命令） #

C 是编译型语言：源文件（扩展名 .c）要先经预处理、编译、汇编、链接四步，生成可执行文件后才能运行。以 GNU 编译器 gcc 为例，最常用的命令是：

bash
gcc hello.c -o hello        # 编译并链接，生成名为 hello 的可执行文件
./hello                     # 运行（Windows 下为 hello.exe）
gcc -Wall -Wextra hello.c   # 打开常用警告，强烈建议始终加上
gcc -std=c99 -Wall hello.c  # 指定 C 标准版本

说明：-o 指定输出文件名，省略时默认生成 a.out（Windows 下为 a.exe）；-Wall 打开绝大多数警告，-Wextra 再补一批，两者同时打开能把「用了未初始化变量」「printf 格式与参数不匹配」这类问题在编译期抓出来。想看到中间产物，可以单独停在某一阶段：

bash
gcc hello.c -E -o hello.i   # 只做预处理，得到展开后的文本
gcc hello.i -S -o hello.s   # 只做编译，得到汇编源文件
gcc hello.s -c -o hello.o   # 只做汇编，得到目标文件（机器码）
gcc hello.o -o hello        # 只做链接，得到可执行文件

多文件工程、静态库与动态库的完整做法见 第16章；编译期报错的逐类解读见 第17章。

术语与代码约定 #

  • 全教程统一使用「运算符」而不写「操作符」，统一使用「形参」与「实参」而不混用「参数」；指针变量写作「指针」，其指向的对象写作「所指对象」，避免「指针指向指针」这类含混说法。
  • 首次出现的术语附英文原词，例如 预处理 preprocessor、编译 compilation、汇编 assembly、链接 linking、目标文件 object file、存储类 storage class、作用域 scope、链接属性 linkage、未定义行为 undefined behavior、序列点 sequence point。
  • 代码块一律用三反引号加 c 标注，命令行用 bash 标注；缩进 4 空格；#include <...> 用尖括号且单独成行；注释用中文。
  • 素材中剪藏残留的水印、转载信息、孤立数字、把 sizeof 写成 sizefof、把 extern 写成 exter n 之类的 OCR 破损均已清洗订正；需要罗列的清单（优先级、存储类、函数原型等）一律改用 Markdown 表格。
  • 涉及「实现定义」与「未定义行为」的地方一律显式标注，不以某台机器的实测结果冒充标准结论。

第1章 从 C 语言说起：程序结构、编译与运行 #

本章目标：说清 C 语言在编程语言谱系中的位置，写出并编译运行第一个程序，掌握「源文件 → 可执行文件」的四个阶段与 gcc 对应选项，能按规范书写标识符，并会用 man 手册查函数原型。

1.1 引子：为什么需要这一章 #

学任何一门语言，最省力的起点都是先让一个最小程序跑起来，再回头弄清它每一行的作用。C 语言尤其如此：它离硬件很近，很多概念（存储类、指针、内存段）在后面会反复出现，如果一开始就没搞清「我写的这行字是怎么变成 CPU 能执行的机器码的」，后面的学习就会退化成背语法。

本章不铺开语法，只建立一条主线：源文件 → 预处理 → 编译 → 汇编 → 链接 → 运行。理解这条流水线之后，很多「编译报错」「链接报错」「明明改了代码却没生效」的问题都会变得有迹可循。

1.2 C 语言的定位与程序的四种形态 #

C 语言诞生于 1972 年的贝尔实验室，最初用于重写 UNIX 操作系统。它的特点是：语法简洁、贴近硬件、可移植性由标准保证、没有运行时垃圾回收、编译产物直接是机器码。今天它仍然占据三个难以替代的位置：操作系统与嵌入式固件、需要与硬件寄存器打交道的驱动、以及作为其他语言的底层实现（Python 解释器、Linux 内核、SQLite 等都由 C 写成）。

一个 C 程序从人写的文本，到最后在 CPU 上跑起来，会经历四种形态，这也是本章后面反复引用的主线：

形态 文件扩展名 内容 人能读吗
源文件 .c 预处理指令 + C 语句 能读，人写的
预处理后的展开文本 .i 宏已展开、头文件已拼接、注释已删除 能读，但很长
汇编源文件 .s 目标 CPU 的汇编指令 能读，需要汇编知识
目标文件 .o 机器码 + 符号表 + 重定位信息 不能读，二进制
可执行文件 无（如 hello） 多个 .o 与库链接后的完整程序 不能读，二进制

注意：.i 与 .s 都是纯文本，调试宏展开错误时直接用编辑器打开 .i 文件，比盯着 #define 猜要快得多；而 .o 已经是机器码，用文本编辑器打开只会看到乱码，要看它得用 objdump、nm、readelf 这类工具（见 第16章）。

1.3 第一个程序：逐行拆解 #

c
#include <stdio.h>

int main(void)
{
    printf("Hello, World!\n");
    return 0;
}

保存为 hello.c，执行 gcc hello.c -o hello 再运行 ./hello，屏幕上输出 Hello, World!。这个程序只有五行有效代码，但每一行都对应一个必须理解的概念：

行 代码 作用 常见误解
1 #include <stdio.h> 把标准输入输出头文件的内容原样拼进来，使 printf 的原型可见 以为它是「导入库」；其实只是文本拼接，真正的库在链接阶段才接上
3 int main(void) 程序入口，返回 int 给操作系统 写成 void main()；在托管环境下这是非标准的
4–6 { ... } 函数体，一对花括号划定作用域 以为花括号可省；函数体的花括号不能省
5 printf("Hello, World!\n"); 调用标准库函数输出字符串 漏写分号；把 \n 写成 /n
6 return 0; 把退出码 0 交给操作系统，0 表示成功 以为可以不写；C99 起 main 末尾不写 return 等价于 return 0，但显式写出更清楚

几点必须一开始就建立的观念：

  1. C 是自由格式语言。换行、缩进、空格对编译器几乎无意义，语句靠分号结束、代码块靠花括号界定。缩进是为了人读，不是给编译器的。
  2. main 是入口但不特殊到可以乱写。托管环境（有操作系统）下标准形式是 int main(void) 或 int main(int argc, char *argv[])，返回值会变成进程退出码，在 Shell 里用 echo $? 可以看到。裸机环境（单片机）没有操作系统接收返回值，才常见 void main()。
  3. printf 不是关键字，是库函数。它来自 stdio.h，行为由标准库实现决定，这也是为什么第 13 章要专门列一张标准库函数速查表。

1.4 从源文件到可执行文件：四个阶段 #

把 hello.c 变成可执行文件，gcc 内部实际做了四件事。理解这张表，等于理解了后面所有编译报错与链接报错的来源。

阶段 核心任务 输入 输出 对应命令
预处理 Preprocessing 删注释、展开 #include、做宏替换、处理条件编译 .c .i gcc hello.c -E -o hello.i
编译 Compilation 词法、语法、语义检查；翻译成汇编 .i .s gcc hello.i -S -o hello.s
汇编 Assembly 汇编指令逐句翻译成机器码，生成符号表与重定位表 .s .o gcc hello.s -c -o hello.o
链接 Linking 把多个 .o 与库（.a / .so）合并，解析外部符号，确定最终地址 .o + 库 可执行文件 gcc hello.o -o hello

这条流水线解释了四类常见现象：

  • **「未定义的引用 undefined reference to xxx」**出现在第四阶段。说明编译都过了，但有符号只声明没定义 —— 常见原因是漏了某个 .c 文件、漏了 -l 库、或者把定义写进了头文件而没被任何源文件包含。
  • **「隐式声明函数 implicit declaration of function」**出现在第二阶段的语义检查。说明调用点之前没有可见的原型，多半是漏了 #include。C99 起这是错误而非警告。
  • **「语法错误 expected ';'」**出现在第二阶段。注意报错行号常常比真正的错误位置晚一行，因为编译器要读到下一个记号才能确认上一句没结束。
  • **「改了代码却没生效」**多发生在增量构建：.o 比 .c 新，make 就不重编。这时 make clean 重来一次。

注意：-E、-S、-c 三个选项是「停在哪一步」的开关：-E 停在预处理后，-S 停在编译后，-c 停在汇编后（生成 .o 但不链接）。理解这一点，就能在排查宏、内联、模板展开这类问题时把中间产物掏出来看。

1.5 标识符、关键字与书写规范 #

标识符是给变量、函数、类型起的名字，必须满足三条硬性约束：

  1. 字符集：只能由字母、数字、下划线 _ 组成，且首字符必须是字母或下划线，不能是数字。
  2. 大小写敏感：data、Data、DATA 是三个不同的标识符。
  3. 不得与关键字重名：C89/C90 定义了 32 个关键字，例如 auto、break、case、char、const、continue、default、do、double、else、enum、extern、float、for、goto、if、int、long、register、return、short、signed、sizeof、static、struct、switch、typedef、union、unsigned、void、volatile、while。

在此之上是工程惯例（不是语法强制，但违反会让人读代码时不断踩坑）：

  • 变量与函数用小写下划线风格（file_size、get_file_size）；宏与常量用全大写（MAX_LEN、BUFFER_SIZE）；类型名用 _t 结尾（size_t、node_t）。
  • 名字要能自解释：i、j 只用于最内层的循环计数器，出了三层循环就该改名。
  • 不要把 l（小写 L）、I（大写 i）、1（数字一）、O（大写 o）、0（数字零）混用；l 与 1 在多数字体下几乎无法区分。

注意：sizeof 是关键字而不是函数，这决定了它可以不带括号用于类型：sizeof(int) 与 sizeof int 都合法，因为它在编译期由编译器求值成常量，不存在「函数调用」。同理 sizeof(int) * p 被解析为 (sizeof(int)) * p，是一次普通的乘法。

1.6 学会查文档：man 手册分卷 #

C 的标准库函数、系统调用、设备文件都靠 man 手册查。关键在于理解后面的分卷号：同名条目可能同时存在于多个分卷中，查错卷会得到完全不同的东西。

分卷 内容 例子
1 Shell 命令 man 1 ls、man 1 cd
2 系统调用（直接与内核打交道） man 2 open、man 2 write
3 C 标准库函数 man 3 printf、man 3 malloc
4 特殊设备与设备文件说明 man 4 null
5 配置文件格式 man 5 passwd
6 游戏与娱乐 man 6 fortune
7 杂项：惯例、协议、宏 man 7 signal
8 系统管理命令（通常需 root） man 8 ifconfig
9 Linux 内核例程文档 驱动与子系统相关

最典型的一次「查错卷」是 open：man open 默认打开 1 卷（打开文件的桌面程序），而写 C 代码要用的是 man 2 open；printf 则要 man 3 printf。如果记不清在哪一卷，用 man -k 关键词 按描述搜索，或者 man -f 函数名 只列各卷里的同名条目。

C 语言本身的语法标准不在 man 里，而在 ISO/IEC 9899 标准文本里；查语法细节时，man 只能告诉你函数怎么用，不能告诉你语言规则。

1.7 小结 #

  • C 程序经历 源文件 → 预处理 → 编译 → 汇编 → 链接 → 可执行文件；-E、-S、-c 分别停在第一、二、三阶段之后。
  • 「编译错误」定位在语法与语义检查，「链接错误」定位在符号解析，两者排查方向完全不同。
  • 标识符只用字母、数字、下划线，首字符不能是数字；sizeof 是关键字，编译期求值。
  • main 在托管环境下返回 int，退出码会传给操作系统；printf 是库函数，来自 stdio.h。
  • 查文档先判断分卷号：系统调用查 2 卷、库函数查 3 卷。

1.8 常见错误与陷阱 #

  • ❌ 把 #include 当成「导入库」。它只是文本拼接；函数真正的实现体在链接阶段从库中取。因此「头文件包含了」不等于「库链接上了」，-lm（数学库）这类漏写 -l 的链接错误要在第四阶段找。
  • ❌ 语句末尾漏分号。报错行号通常指向下一行，因为编译器要读到下一个记号才能确认。
  • ❌ 把 void main() 当成标准写法。托管环境应为 int main(void)；void main 在部分编译器上能过，但退出码是垃圾值，脚本里的 $? 判断会失效。
  • ❌ printf 里把 \n 写成 /n。前者是换行转义符，后者会被原样输出为 /n 两个字符。
  • ❌ 改了代码没重编译就运行，或者 .o 比 .c 新导致增量构建跳过。怀疑时 make clean 后重来。
  • ❌ 查错 man 分卷，例如用 man open 而不是 man 2 open，看到的是桌面程序而不是系统调用。

第2章 数据类型、常量与存储类 #

本章目标：掌握基本类型的大小与 sizeof 的用法，理解补码表示与截断，会写各类字面量与常量，能准确说出五个存储类各自决定的是「存储期」「作用域」还是「链接属性」，并讲清 static 三种用法与 volatile 的作用。

2.1 引子：为什么需要这一章 #

程序里每一个名字都同时携带三重身份：它是什么类型（决定占几个字节、怎么解释这些字节）、活多久（存储期）、谁能看见它（作用域与链接属性）。初学者往往只关注第一重，于是写出「函数返回了局部数组的地址」「两个文件里定义了同名全局变量引起重复定义」「static 变量居然不会被重置」这类 bug。

本章把这三重身份拆开讲清。类型部分只讲标准保证的内容，凡「实现定义」的地方一律标注；存储类部分则以「存储期 + 作用域 + 链接属性」三张表为主线，最后落到 static、extern、const、volatile 这几个最容易被误解的关键字上。

2.2 基本数据类型与 sizeof #

C 的基本类型只有四族：整型（char/short/int/long/long long）、浮点型（float/double/long double）、void，以及由它们派生的指针与聚合类型。标准只保证相对大小（char ≤ short ≤ int ≤ long ≤ long long，且 char 恒为 1 字节），不保证绝对字节数。常见平台上 32 位与 64 位 Linux 的典型取值是：

类型 32 位 Linux 64 位 Linux 说明
char 1 1 1 字节 = 8 位，CHAR_BIT 由 limits.h 给出
short 2 2 至少 16 位
int 4 4 至少 16 位，实际几乎都是 32 位
long 4 8 唯一随位数变化的整型，这正是移植 bug 的常见来源
long long 8 8 C99 引入，至少 64 位
float 4 4 IEEE 754 单精度，约 7 位有效十进制数字
double 8 8 IEEE 754 双精度，约 15–16 位有效数字
long double 16 16 x86 上为 80 位扩展精度的存储形态
指针 4 8 与地址宽度一致

写可移植代码时不要把这些数字写死，而用 sizeof 求值：

c
#include <stdio.h>

int main(void)
{
    printf("char=%zu short=%zu int=%zu long=%zu long long=%zu\n",
           sizeof(char), sizeof(short), sizeof(int), sizeof(long), sizeof(long long));
    printf("float=%zu double=%zu long double=%zu ptr=%zu\n",
           sizeof(float), sizeof(double), sizeof(long double), sizeof(void *));
    return 0;
}

关于 sizeof 必须记住三点：

  1. 它是编译期求值的关键字，不是函数，所以 sizeof int 合法；除变长数组外，结果在编译时就已确定。
  2. 它的结果是 size_t（无符号整型），用 %zu 打印。用 %d 打印 sizeof 的结果在 64 位平台上是未定义行为。
  3. 对数组求值得到整个数组的字节数，对指针求值得到指针本身的宽度。这一点是 第7章 数组与指针分野的关键，凡是「sizeof 结果突然变成 8」的地方，都是数组退化成了指针。

2.3 补码：整数在内存里的样子 #

整型在内存里用补码（two's complement）存储。设类型宽度为 n 位，则：

  • 非负数：直接存二进制，最高位为 0。
  • 负数：取其绝对值的二进制，按位取反再加 1；等价于 2^n - |x|。
  • 表示范围：有符号 [-2^(n-1), 2^(n-1) - 1]，无符号 [0, 2^n - 1]。

以 8 位的 char 为例，-1 的补码是 1111 1111，-128 是 1000 0000（它没有对应的正数，所以 -(-128) 仍为 -128，这是补码的一个著名边角）。用补码的好处是：减法可以统一成加法，a - b 直接算 a + (-b)，硬件不必为减法单独设计电路。

赋值给较窄类型时会发生截断：只保留低位，高位直接丢弃。

c
#include <stdio.h>

int main(void)
{
    char c;
    c = 1222;                      /* 1222 的二进制低 8 位是 1100 0110 */
    printf("%d %c\n", c, c);        /* 按有符号解释为 -58；按字符打印是不可见字符 */
    return 0;
}

1222 & 0xFF 得 0xC6，最高位为 1，按有符号 char 解释就是 -58。同一段代码在「char 默认无符号」的编译器上会打印 198，因为 char 的符号性是实现定义的。

注意：char 是 C 里唯一不默认等价于 signed 的整型，它的符号性由编译器和编译选项决定。因此凡是把 8 位数据当数值用（协议字段、图像像素、校验和），都应显式写 signed char 或 unsigned char，只把 char 留给字符。

2.4 常量与字面量 #

字面量（literal）是直接写在代码里的值。它的类型由写法决定，不写后缀时按「能装下它的最小类型」推断，这经常导致意外：

写法 类型 说明
42 int 十进制无后缀
42U unsigned int U/u 后缀，强烈建议所有无符号常量都带上
42L long L/l 后缀，避免用小写 l（像数字 1）
42UL unsigned long 后缀可组合，顺序不限
0x1F int 十六进制，常用于掩码与寄存器值
0b1010 int 二进制前缀，C23 起为标准；GCC 早已作为扩展支持
017 int 八进制，前导 0 是八进制标记，值是 15 不是 17
3.14 double 浮点字面量默认是 double，不是 float
3.14f float f 后缀
3.14L long double L 后缀
'A' int 字符常量在 C 里是 int 类型，不是 char
"abc" char[4] 字符串字面量，隐含结尾 '\0'，故 3 个字符占 4 字节

字符转义序列是另一处高频错误来源：'\n'（换行）、'\t'（制表）、'\0'（空字符）、'\\\\'（反斜杠自身）、'\''（单引号）、'\"'（双引号）。八进制转义写 '\101'，十六进制转义写 '\x41'，两者都是字符 'A'。

定义符号常量有三种做法，优先级从高到低：

  1. const 限定变量：const int max_limit = 100; 有类型检查、可被调试器看到，推荐。
  2. enum 常量：enum { MAX_LEN = 128 }; 只能是整型，但能被编译器当作编译期常量用于数组维度。
  3. #define 宏：#define MAX_LEN 128 只是文本替换，没有类型，且容易在表达式里被错误结合 —— 详见 第15章。

2.5 变量的声明、定义与初始化 #

「声明」告诉编译器这个名字存在、类型是什么；「定义」则为它分配存储。同一个实体可以声明多次，但只能定义一次。

c
extern int counter;      /* 声明：只说 counter 是 int，不分配存储 */
int counter = 0;         /* 定义：分配存储并初始化为 0 */
int counter;             /* 定义（暂定义 tentative definition）：未显式初始化，最终按 0 处理 */

初始化规则按存储期区分：

  • 静态存储期（全局变量、static 变量）：未显式初始化时自动置 0，这是标准保证的。
  • 自动存储期（局部变量）：未初始化时值不确定，读到它就是未定义行为。int a; 之后的 printf("%d", a) 可能打印 0，也可能打印任何值，还可能因优化而完全不同。
  • 数组聚合初始化：int a[10] = {0}; 把首元素设为 0、其余元素按「剩余元素补 0」规则全部置 0，这是清零数组的惯用法；写成 int a[10] = {1}; 则只有 a[0] 是 1，其余为 0。

指定初始化器（C99）可以按成员名或下标赋值，且未指明的成员一律置 0：

c
struct point { int x; int y; };
struct point p = { .y = 5 };        /* p.x 为 0，p.y 为 5 */
int arr[5] = { [2] = 7, [4] = 9 };  /* 其余元素为 0 */

2.6 五个存储类 #

C 的存储类说明符有五个：auto、register、static、extern，以及 C11 加入的 _Thread_local。它们决定的不是「值放在哪」这么简单，而是三个互相独立的属性：

存储类 存储期 作用域 链接属性 声明位置与写法
auto 自动（进入块时创建，离开块时销毁） 代码块 无 块内，auto int x;（几乎总是省略）
register 自动 代码块 无 块内，register int i;
外部链接静态 静态（程序整个运行期） 文件 外部 所有函数之外，int g;
内部链接静态 静态 文件 内部 所有函数之外，static int g;
无链接静态 静态 代码块 无 块内，static int s;

逐个说明：

auto：唯一作用是显式声明「自动存储期」，因为这是块内变量的默认值，所以实际上从不写。它的实际含义是：变量在栈上分配，函数返回即失效。

register：只是请求把变量放进 CPU 寄存器，编译器可以不理会。它有两条硬性约束：不能对它使用取地址运算符 &（寄存器没有内存地址）；类型必须是寄存器装得下的标量（结构体、数组不能声明为 register）。现代编译器在 -O2 下的寄存器分配比人手动标注合理得多，因此 register 在今天基本只剩下「明确表示不需要地址」的文档价值。

static：见 2.8 节，它有三个互不相同的身份。

extern：声明「这个实体在别处定义」，本身不分配存储、不能初始化。extern int i; 若写在函数内部，它的作用是把函数内的名字 i 绑定到全局的 i，而不是新建一个局部变量 —— 这正是「局部变量遮蔽全局变量」的解法。注意 extern int i; 与 extern int i = 1; 在语义上完全不同：带初始化器就是定义，会分配存储。

_Thread_local（C11）：每个线程各有一份副本，存储期与线程相同。它与 static/extern 可以组合，例如 static _Thread_local int err_flag; 表示「文件内可见、每线程一份」。线程与锁的完整讨论属于并发专题，本书只在语义层面提及。

一张对照表总结「变量类型 × 是否 static」的效果：

变量类型 声明位置 是否在栈上 作用域 加 static 后的变化
全局 所有代码块之外 否 从声明处到文件尾 不允许从其他源文件访问
局部 代码块起始处 是 整个代码块 不再位于栈上，值在程序整个执行期保持
形参 函数头部 是 整个函数 不允许（语法上不能修饰形参）

2.7 作用域、链接与存储期 #

这三个概念经常被混为一谈，必须分开：

  • 作用域（scope）：名字在源码中「能被看见」的范围。分块作用域、文件作用域、函数原型作用域。离开作用域后名字不可用，但对象可能还活着。
  • 链接属性（linkage）：同名标识符在多个翻译单元之间是否指同一个实体。分外部链接（跨文件可见）、内部链接（仅本文件）、无链接（局部）。
  • 存储期（storage duration）：对象的生命周期，与「能不能按名字访问」无关。分自动、静态、动态（malloc 分配，见 第11章）。

最典型的例子是 static 局部变量：它的作用域仍是块（出了块就不能按名字访问），但存储期是静态的（值一直活到程序结束，下次进块还是上次的值）。所以「static 让局部变量变成全局变量」这个说法是错的 —— 它只改变了存储期，没有改变作用域。

遮蔽（shadowing）与链接属性交互的几个要点：

  • 块内声明与形参同名的变量是非法的，因为二者作用域相同。
  • 块内局部变量会遮蔽同名的全局变量；要访问被遮蔽的全局变量，需在块内用 extern 重新声明。
  • static 全局变量与 extern 不能配对：static 意味着内部链接，extern 要求外部链接，在另一个文件中用 extern 引用 static 变量必然链接失败（undefined reference）。

2.8 static 的三种身份 #

static 是 C 里最多义的关键字，三种用法必须分清：

其一，修饰局部变量 —— 改变存储期。 变量被移出栈、放进静态数据区，只初始化一次，函数多次调用之间保持上次的值：

c
#include <stdio.h>

void counter(void)
{
    static int n = 0;   /* 只在第一次调用时初始化为 0 */
    n++;
    printf("第 %d 次调用\n", n);
}

这是「统计函数被调用次数」最干净的做法：计数器与函数绑定，不会与别处的同名变量冲突。

其二，修饰全局变量 —— 改变链接属性。 变量的作用域被限制在本文件，其他文件即使写 extern 也访问不到。好处有两条：不会与其他文件的同名变量冲突；明确表达「这是本模块私有状态」的设计意图。

其三，修饰函数 —— 同样改变链接属性。 函数默认为外部链接，加 static 后变成内部链接，只在声明它的文件内可见，因此可以与别的模块里的同名函数共存而互不干扰。头文件里的辅助函数一律应加 static（或 static inline），否则多个源文件包含同一头文件时会出现重复定义。

注意：「static 函数在内存中只有一份、普通函数每次调用维持一份拷贝」是流传很广的错误说法。普通函数在内存里也只有一份机器码，每次调用压入栈的是栈帧（返回地址、形参、局部变量），不是函数本身的副本。

2.9 volatile 与 const #

const 声明「当前线程不会通过这个名字修改它」，它与 volatile 无冲突，二者可组合。三点提醒：

  • const 修饰的变量不是编译期常量（除 static const 的整型常量表达式外），不能用它做数组维度（除非编译器支持变长数组扩展），需要编译期常量请用 enum 或宏。
  • const char *p 是「指向常量的指针」（不能改内容，可以改指向）；char * const p 是「常量指针」（可以改内容，不能改指向）；const char * const p 两者都锁死。读声明的方法见 第8章。
  • 把 const 对象的地址赋给普通指针会丢掉 const 限定，编译期给警告，但强转后强行写入可能落在只读段上直接崩溃。

volatile 声明「这个值可能被程序之外的力量修改」，要求编译器每次访问都真正读写内存，不要缓存在寄存器里，也不要跨访问做重排优化。三类典型场景：

  1. 内存映射 I/O（MMIO）：硬件寄存器被映射到某个固定地址，值由外设改变。
c
/* 假设 0x40003000 是映射到硬件状态寄存器的地址 */
volatile unsigned int *status = (volatile unsigned int *)0x40003000;

while (*status != 255) {
    /* 等待外设把状态改成 255 */
}

如果漏掉 volatile，优化器会认为循环体内没有修改 *status 的语句，从而「证明」条件恒为真或恒为假，直接把循环优化成死循环或整段删掉。

  1. 信号处理函数与主流程共享的变量：处理函数随时可能打断主流程，必须让编译器每次都重新读内存。

  2. 多线程共享的无锁标志位：注意 volatile 不提供原子性与内存序，只阻止编译器的寄存器缓存优化，不能替代原子操作或互斥锁。在互斥锁保护的临界区内部，锁本身带有内存屏障，通常不必再用 volatile；临界区之外被多线程轮询的共享变量才需要它。

2.10 小结 #

  • 基本类型只保证相对大小与「char 恰为 1 字节」，绝对值用 sizeof 求，打印用 %zu。
  • 整型以补码存储；赋给窄类型会截断低位；char 的符号性由实现决定。
  • 字面量的类型由写法决定：3.14 是 double，017 是八进制，42 是 int。
  • 静态存储期对象未初始化时自动为 0，自动存储期对象未初始化时值不确定。
  • 存储类决定的是「存储期 + 作用域 + 链接属性」三件不同的事，static 按修饰对象不同分别改变存储期或链接属性。
  • volatile 只阻止优化，不提供同步语义。

2.11 常见错误与陷阱 #

  • ❌ 用 %d 打印 sizeof。sizeof 是 size_t（无符号），在 64 位上用 %d 是未定义行为，应用 %zu（或转成 (unsigned long) 配 %lu）。
  • ❌ 把「作用域」与「生命周期」混为一谈。static 局部变量出了块就不能按名字访问，但值仍在；反过来说，指针越界使用已离开作用域的局部对象的地址，是悬垂指针（见 第8章）。
  • ❌ 以为 static 全局变量加 extern 就能跨文件用。内部链接与外部链接直接冲突，链接期报 undefined reference。
  • ❌ 在头文件里定义变量或函数。多个 .c 包含同一头文件就会重复定义；头文件里只能放声明（extern）、类型定义、宏与 static inline 函数。
  • ❌ 用 volatile 代替锁。它不保证原子性也不保证顺序，多线程计数照样出错。
  • ❌ 局部变量未初始化就参与运算。int sum; sum += a; 是未定义行为，可能得到任何值，且在 -O2 下表现与 -O0 完全不同。
  • ❌ #define MAX 100 期望它有类型。宏是文本替换，MAX / 3 的类型由参与运算的字面量决定；需要类型就用 const 或 enum。

第3章 运算符、表达式与优先级 #

本章目标：掌握 15 级优先级与「只有三个右结合」的规则，能正确写出带短路求值、复合赋值、条件运算符与逗号运算符的表达式，理解隐式转换与强制转换各自的代价，并识别求值顺序引起的未定义行为。

3.1 引子：为什么需要这一章 #

C 的表达式语法极其精简：运算符有 40 多个，优先级分 15 级，其中只有单目、条件、赋值三个从右往左结合。这种设计让表达式写起来很短，也让错误藏得很深 —— a & b == c、x = y = z、i++ + ++i 三行代码，各自踩中一个不同的坑。

本章先建立「目数」与「优先级/结合性」两把尺子，再逐个过一遍主要运算符，最后落到求值顺序与类型转换上。想跳过推导直接查表时，看 附录A 的完整优先级表。

3.2 运算符的分类与三个属性 #

按操作数个数（目数）分三类：

  • 单目（1 个操作数）：!、~、++、--、-（负号）、+（正号）、*（解引用）、&（取地址）、sizeof、(类型)。
  • 双目（2 个操作数）：算术 + - * / %、关系 < <= > >=、相等 == !=、位 & | ^、移位 << >>、逻辑 && ||、赋值 = 及其复合形式。
  • 三目（3 个操作数）：只有一个，条件运算符 ?:。
