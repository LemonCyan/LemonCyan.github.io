第20章 有限状态机与工程实践 #

本章目标：能用状态机模型重写层层嵌套的判断逻辑，独立实现空格压缩、引号字段解析、注释剥离与协议帧解析，并在 switch 与函数指针表之间做出合理选择。

20.1 引子：为什么需要这一章 #

前面的章节按语法点推进：类型、运算符、控制结构、函数、数组、指针、字符串、结构体、内存、文件、标准库。每一个知识点单独看都不难，真正难的是把它们组合起来解决一个「有过程」的问题——比如把一段源码里的注释全部删掉。

这件事用直白的思路写出来是这样的：读到 / 时往后看一个字符，如果是 / 就进入单行注释直到换行；如果是 * 就进入多行注释直到 * 后面跟 /；但如果这个 / 出现在字符串字面量里，它就不是注释的开头；如果字符串里还有转义的反斜杠，判断又要再拐一层。每加一条规则，就多一层 if 嵌套，多一组标志位，多一点记不清的先后顺序。

有限状态机（finite state machine，FSM）是这类问题的标准答案。它的想法很朴素：把「程序此刻处于什么处境」显式地提取出来，变成一个变量；每一轮只回答两个问题——我现在处于哪个状态、这次读到的字符是什么；然后查表决定「输出什么、跳到哪个状态」。规则增加时，改的是表，而不是嵌套深度。

本章先给出状态机在 C 语言里的标准骨架，再用三个由浅入深的实例把它压实：压缩连续空格、带引号保护的空格压缩、C 源码注释剥离器。三个实例逐步加入新的状态，正好演示状态机「加一条规则就加一个状态」的扩展方式。之后把状态机表格化，讨论它在协议解析中的位置，最后比较 enum 加 switch 与函数指针表两种实现。

20.2 状态机的三个要素与标准骨架 #

一个状态机由三样东西构成，缺一不可：

要素 英文 在 C 语言中的载体 作用
状态集 state set enum 定义的枚举常量 穷举程序可能处于的全部处境
状态变量 state variable 一个 enum 类型的局部变量 记录此刻所处的是哪一个状态
转移规则 transition switch (state) 内的分支 由「当前状态 + 本次输入」决定输出与下一个状态

在 C 语言中，标准实现框架是：用 enum 定义状态集，用一个状态变量记录当前状态，在逐字节读取的循环里用 switch 针对不同状态与输入事件分流决策。骨架如下：

c
#include <stdio.h>

/* 第一步：用 enum 穷举所有状态 */
enum State {
    STATE_A,
    STATE_B
};

int main(void)
{
    int ch;
    /* 第二步：状态变量，初值决定从哪个状态开始 */
    enum State state = STATE_A;

    /* 第三步：逐字节读取，每一轮只处理一个字符 */
    while ((ch = getchar()) != EOF) {
        switch (state) {
            case STATE_A:
                /* 针对「当前是 A 状态 + 读到 ch」做出动作并决定去向 */
                state = STATE_B;
                break;

            case STATE_B:
                state = STATE_A;
                break;
        }
    }
    return 0;
}

这个骨架值得注意的地方有三处。第一，读取用 int ch 而不是 char ch——getchar 返回 int，只有用 int 才能既装下 0 到 255 的全部字节值，又能与 EOF（通常是 -1）区分开。第二，每一轮循环只读一个字符，状态转移也就只发生在相邻字符之间，不存在「一次读完再回头处理」的麻烦。第三，switch 的每个分支都必须显式给出下一个状态，包括「保持原状态」也要写清楚，否则读者无法从代码看出状态转移的全貌。

注意：状态机的正确性依赖「状态集是完备的」——任何时刻程序都必须落在某个已定义的状态里。新增规则时若只想在某个状态里加一条转移，却不小心让其他状态漏掉了这条输入的处理，程序就会出现「某个字符被悄悄吞掉」这类难以定位的错误。

20.3 实例一：压缩连续空格 #

题目：把输入字符串中连续的多个空格压缩成一个空格。输入 H el lo 应输出 H el lo。

状态设计。只需要两个状态就够了，关键在于把「上一个字符是空格」这件事从判断里提取出来变成状态本身：

状态 含义 读到非空格 读到空格
STATE_CHAR 当前不在连续空格中，可以正常输出 输出该字符，保持 STATE_CHAR 输出这一个空格，转移到 STATE_SPACE
STATE_SPACE 已经输出过一个空格，后续空格应当被屏蔽 输出该字符，转移回 STATE_CHAR 忽略不输出，保持 STATE_SPACE

完整程序：

c
#include <stdio.h>

/* 只有两个状态：正常输出态、已输出一个空格的等待态 */
enum State {
    STATE_CHAR,
    STATE_SPACE
};

int main(void)
{
    int ch;
    enum State state = STATE_CHAR;   /* 初始处于正常输出态 */

    while ((ch = getchar()) != EOF) {
        switch (state) {
            case STATE_CHAR:
                putchar(ch);
                if (ch == ' ') {
                    state = STATE_SPACE;   /* 吐出第一个空格后转入屏蔽态 */
                }
                break;

            case STATE_SPACE:
                if (ch != ' ') {
                    putchar(ch);
                    state = STATE_CHAR;    /* 遇到非空格，恢复正常输出 */
                }
                /* 若仍是空格则什么都不做，这就是「压缩」生效的位置 */
                break;
        }
    }
    return 0;
}

编译并运行：

bash
gcc -Wall -o compress compress.c
echo 'H   el   lo' | ./compress

输出：

text
H el lo

这段代码的精妙之处在于：判断「该不该输出这个空格」时不需要往前看、也不需要往回改，只看「我现在是不是已经在空格态」。若换成直白写法，就得保留一个 prev 变量记录上一个字符，而 prev 与 state 其实是同一件事的两种叫法——状态机只是把它命名得更清楚。

注意：素材给出的注释写的是「输入空格：打印当前空格，状态转移到 STATE_SPACE」。这里有一个边界值得确认：行首连续空格也会被压缩成一个，而不是被全部丢弃。若业务需要「行首空格全部去掉」，那是另一条规则，应再加一个「行首态」，不能靠在现有两个状态里打补丁。

20.4 实例二：带引号保护与转义的字段解析 #

题目：在实例一的基础上增加两条规则：包裹在双引号内部的连续空格必须原样保留；引号内允许用反斜杠转义，\" 表示一个真正的引号字符、\\ 表示一个反斜杠。输入 H el "wo rld" lo 应输出 H el "wo rld" lo。

状态设计。在实例一的两个状态之外，再加「引号内」与「转义中」两个状态：

状态 含义 读到双引号 读到反斜杠 读到空格 读到其他字符
STATE_CHAR 正常输出态 输出并进入 STATE_IN_QUOTE 输出，保持 输出一个空格后进入 STATE_SPACE 输出，保持
STATE_SPACE 已输出过空格 输出并进入 STATE_IN_QUOTE 输出并回到 STATE_CHAR 忽略，保持 输出并回到 STATE_CHAR
STATE_IN_QUOTE 引号内部，空格不得压缩 输出并退出到 STATE_CHAR 输出并进入 STATE_ESCAPE 输出，保持 输出，保持
STATE_ESCAPE 刚读到转义符，下一个字符按字面处理 输出，回到 STATE_IN_QUOTE 输出，回到 STATE_IN_QUOTE 输出，回到 STATE_IN_QUOTE 输出，回到 STATE_IN_QUOTE

完整程序：

c
#include <stdio.h>

/* 四个状态：正常、空格屏蔽、引号内、转义中 */
enum State {
    STATE_CHAR,
    STATE_SPACE,
    STATE_IN_QUOTE,
    STATE_ESCAPE
};

int main(void)
{
    int ch;
    enum State state = STATE_CHAR;

    while ((ch = getchar()) != EOF) {
        switch (state) {
            case STATE_CHAR:
                putchar(ch);
                if (ch == '"') {
                    state = STATE_IN_QUOTE;     /* 进入引号保护区 */
                } else if (ch == ' ') {
                    state = STATE_SPACE;        /* 吐出第一个空格，开始屏蔽 */
                }
                break;

            case STATE_SPACE:
                if (ch == '"') {
                    putchar(ch);
                    state = STATE_IN_QUOTE;
                } else if (ch != ' ') {
                    putchar(ch);
                    state = STATE_CHAR;
                }
                break;

            case STATE_IN_QUOTE:
                putchar(ch);                    /* 引号内的空格一律原样输出 */
                if (ch == '\\') {
                    state = STATE_ESCAPE;       /* 转义符后一个字符不参与结构判断 */
                } else if (ch == '"') {
                    state = STATE_CHAR;
                }
                break;

            case STATE_ESCAPE:
                putchar(ch);                    /* 被转义的字符按字面输出 */
                state = STATE_IN_QUOTE;         /* 处理完立刻回到引号内 */
                break;
        }
    }
    return 0;
}

编译并运行：

bash
gcc -Wall -o quote quote.c
echo 'H   el  "wo   rld"   lo' | ./quote
echo 'a  "x\"  y"  b'   | ./quote

输出：

text
H el "wo   rld" lo
a "x\"  y" b

第二条测试是关键：字符串 a "x\" y" b 中间那个被转义的双引号并没有关闭保护区，所以它后面的两个空格被正确保留下来。如果省掉 STATE_ESCAPE，这一点就会失败——程序会在转义双引号处误判为引号结束，把后面的空格压缩掉。

注意：素材中的案例二只有三个状态（正常、空格、引号内），没有处理转义。本节按「字段解析要能处理转义」的工程需求补上了 STATE_ESCAPE，其转移规则是在三状态版本之上叠加的，不影响原有两条规则。

20.5 实例三：C 源码注释剥离器 #

题目：读入一段 C 源码，把单行注释 // 与多行注释 /* */ 全部剔除后输出，但必须保证字符串字面量里的 // 和 /* 不被误当作注释开头。

状态设计。这是三个实例里状态最多的一个，共七个：

状态 含义 关键转移
STATE_NORMAL 常规代码 遇到 / 转 STATE_SLASH，遇到 \" 转 STATE_IN_STRING，其余原样输出
STATE_SLASH 刚读到 /，可能是注释前兆 再遇 / 转单行注释，遇 * 转块注释，否则补打 / 与当前字符并回到常规态
STATE_LINE_COMMENT 单行注释中 遇换行符输出换行并回到常规态，其余全部丢弃
STATE_BLOCK_COMMENT 块注释中 遇 * 转 STATE_STAR 以准备匹配结束，其余丢弃
STATE_STAR 块注释中刚读到 * 遇 / 结束块注释，遇另一个 * 保持，其余回到块注释态
STATE_IN_STRING 字符串字面量内 遇 \\ 转 STATE_STRING_ESCAPE，遇 \" 回到常规态，其余原样输出
STATE_STRING_ESCAPE 字符串内刚读到反斜杠 下一个字符原样输出并回到字符串态

完整程序：

c
#include <stdio.h>

/* 七个状态：常规、斜杠待定、行注释、块注释、星号待定、字符串内、字符串转义 */
enum CommentState {
    STATE_NORMAL,
    STATE_SLASH,
    STATE_LINE_COMMENT,
    STATE_BLOCK_COMMENT,
    STATE_STAR,
    STATE_IN_STRING,
    STATE_STRING_ESCAPE
};

int main(void)
{
    int ch;
    enum CommentState state = STATE_NORMAL;

    while ((ch = getchar()) != EOF) {
        switch (state) {
            case STATE_NORMAL:
                if (ch == '/') {
                    state = STATE_SLASH;        /* 先挂起，不输出，等下一个字符裁决 */
                } else if (ch == '"') {
                    putchar(ch);
                    state = STATE_IN_STRING;    /* 进入字符串，屏蔽注释识别 */
                } else {
                    putchar(ch);
                }
                break;

            case STATE_SLASH:
                if (ch == '/') {
                    state = STATE_LINE_COMMENT;     /* 确认是单行注释 */
                } else if (ch == '*') {
                    state = STATE_BLOCK_COMMENT;    /* 确认是多行注释 */
                } else {
                    putchar('/');                   /* 虚惊一场，把挂起的斜杠补打出来 */
                    putchar(ch);
                    state = STATE_NORMAL;
                }
                break;

            case STATE_LINE_COMMENT:
                if (ch == '\n') {
                    putchar('\n');                 /* 换行符本身保留，保持行号不变 */
                    state = STATE_NORMAL;
                }
                break;

            case STATE_BLOCK_COMMENT:
                if (ch == '*') {
                    state = STATE_STAR;             /* 可能是结束标记的前半 */
                }
                break;

            case STATE_STAR:
                if (ch == '/') {
                    state = STATE_NORMAL;           /* 结束，整段丢弃 */
                } else if (ch != '*') {
                    state = STATE_BLOCK_COMMENT;    /* 只是一个普通星号，回到块注释态 */
                }
                break;

            case STATE_IN_STRING:
                putchar(ch);
                if (ch == '\\') {
                    state = STATE_STRING_ESCAPE;
                } else if (ch == '"') {
                    state = STATE_NORMAL;
                }
                break;

            case STATE_STRING_ESCAPE:
                putchar(ch);                        /* 被转义的字符原样输出 */
                state = STATE_IN_STRING;
                break;
        }
    }
    return 0;
}

编译并运行（源码文件自身就含有注释与字符串，正好可作测试样本）：

bash
gcc -Wall -o strip strip.c
./strip < test.c > out.c

测试样本与输出对照：

输入片段 输出片段 说明
int a = 1; // 行尾注释 int a = 1; 行注释被剥离，换行保留
/* 块注释 */ 空 块注释整段丢弃
const char *p = "// 不是注释"; 原样保留 字符串状态屏蔽了注释识别
const char *q = "/* 也不是 */"; 原样保留 同上，且 */ 不会被当作块注释结束
int b = a / c; int b = a / c; 单独的斜杠不是注释，挂起后正常补写
int c = 1; /* a ** b */ int c = 1; 块注释中间出现连续星号也能正确结束

注意：剥离器只做词法层面的删除，不负责把被注释掉的代码替换成空白，因此原来在同一行的后续代码会向前顶。若需要保持列位置，可在丢弃注释时输出等量空格，这只需给 STATE_LINE_COMMENT 与 STATE_BLOCK_COMMENT 各加一句 putchar(' '); 即可，状态集不变。

20.6 表格化写法：状态转移表与动作函数指针数组 #

一旦状态数超过四五个，switch 就会变成一张又长又难改的清单：每个分支重复着相似的判断，加一个状态要记得回头修改所有分支。状态机的另一条实现路线是把规则从代码里搬进数据——用表格描述「当前状态 + 本次事件 → 下一个状态」，用函数指针数组描述「在这个状态该做什么」。

先把实例一改写成完全表格化的形式，体会两者的差别：

c
#include <stdio.h>

/* 状态集与事件集都显式枚举，各自的 COUNT 用于定义表格维度 */
enum St { ST_CHAR, ST_SPACE, ST_COUNT };
enum Ev { EV_SPACE, EV_OTHER, EV_COUNT };

/* 转移表：trans[当前状态][本次事件] = 下一个状态 */
static const enum St trans[ST_COUNT][EV_COUNT] = {
    /*              EV_SPACE    EV_OTHER   */
    /* ST_CHAR  */ { ST_SPACE,  ST_CHAR   },
    /* ST_SPACE */ { ST_SPACE,  ST_CHAR   }
};

/* 输出表：1 表示这个字符要打印，0 表示丢弃 */
static const int out[ST_COUNT][EV_COUNT] = {
    /*              EV_SPACE    EV_OTHER   */
    /* ST_CHAR  */ { 1,          1        },
    /* ST_SPACE */ { 0,          1        }
};

/* 把字符归入事件类别，事件分类与状态判断彻底分开 */
static enum Ev classify(int ch)
{
    return (ch == ' ') ? EV_SPACE : EV_OTHER;
}

int main(void)
{
    int ch;
    enum St state = ST_CHAR;

    while ((ch = getchar()) != EOF) {
        enum Ev ev = classify(ch);

        if (out[state][ev]) {
            putchar(ch);
        }
        state = trans[state][ev];
    }
    return 0;
}

行为与 20.3 的 switch 版本完全一致，但规则集中到了两张表里：要新增一种「输入是制表符也算空白」的规则，只需要在 classify 里加一行、在两张表里各扩一列，整个控制流程一行都不用动。这就是「数据驱动」的直接收益。

再进一步，把「动作」也变成数据。协议解析器是最典型的场景：每个状态要处理的逻辑差别很大（有的只比较帧头，有的要累加校验和），用纯转移表表达很不自然，而用函数指针数组则恰好。先统一签名：所有处理函数都接收「解析器上下文指针」与「本次的字节」，自己决定下一个状态。

c
#include <stdio.h>

#define MAX_BODY 32

enum PState {
    PS_WAIT_HEAD1,   /* 等待帧头第一字节 */
    PS_WAIT_HEAD2,   /* 等待帧头第二字节 */
    PS_WAIT_LEN,     /* 读取长度字节 */
    PS_READ_BODY,    /* 逐个读取载荷 */
    PS_WAIT_SUM,     /* 读取校验和 */
    PS_COUNT
};

struct parser {
    enum PState state;
    unsigned char len;
    unsigned char body[MAX_BODY];
    unsigned int pos;
    unsigned int sum;
    unsigned int ok;      /* 成功解析出的帧数 */
    unsigned int bad;     /* 校验失败或长度非法的帧数 */
};

static void on_head1(struct parser *p, unsigned char byte)
{
    if (byte == 0xAA) {
        p->state = PS_WAIT_HEAD2;
    }
}

static void on_head2(struct parser *p, unsigned char byte)
{
    if (byte == 0x55) {
        p->state = PS_WAIT_LEN;
    } else {
        p->state = PS_WAIT_HEAD1;    /* 帧头不完整，重新同步 */
    }
}

static void on_len(struct parser *p, unsigned char byte)
{
    if (byte == 0 || byte > MAX_BODY) {
        p->bad++;
        p->state = PS_WAIT_HEAD1;    /* 长度非法，丢弃并重新同步 */
        return;
    }
    p->len = byte;
    p->pos = 0;
    p->sum = 0;
    p->state = PS_READ_BODY;
}

static void on_body(struct parser *p, unsigned char byte)
{
    p->body[p->pos++] = byte;
    p->sum += byte;
    if (p->pos == p->len) {
        p->state = PS_WAIT_SUM;
    }
}

static void on_sum(struct parser *p, unsigned char byte)
{
    if ((p->sum & 0xFF) == byte) {
        p->ok++;
        printf("frame ok, len = %u\n", p->len);
    } else {
        p->bad++;
        printf("frame bad, expect %u got %u\n", p->sum & 0xFF, byte);
    }
    p->state = PS_WAIT_HEAD1;
}

/* 动作函数指针数组：下标就是状态，因此不需要 switch */
static void (*const on_byte[PS_COUNT])(struct parser *, unsigned char) = {
    on_head1,   /* PS_WAIT_HEAD1 */
    on_head2,   /* PS_WAIT_HEAD2 */
    on_len,     /* PS_WAIT_LEN   */
    on_body,    /* PS_READ_BODY  */
    on_sum      /* PS_WAIT_SUM   */
};

/* 单一入口：无论一次喂多少字节，都按字节推进状态 */
static void feed(struct parser *p, const unsigned char *buf, unsigned int n)
{
    unsigned int i;

    for (i = 0; i < n; i++) {
        on_byte[p->state](p, buf[i]);
    }
}

int main(void)
{
    /* 帧头 0xAA 0x55，长度 3，载荷 0x10 0x20 0x30，校验和 0x60 */
    const unsigned char frame[] = { 0xAA, 0x55, 0x03, 0x10, 0x20, 0x30, 0x60 };
    struct parser p;

    p.state = PS_WAIT_HEAD1;
    p.len = 0;
    p.pos = 0;
    p.sum = 0;
    p.ok = 0;
    p.bad = 0;

    /* 故意拆成两段喂入，验证流式解析与分片无关 */
    feed(&p, frame, 2);
    feed(&p, frame + 2, sizeof(frame) - 2);

    printf("ok = %u, bad = %u\n", p.ok, p.bad);
    return 0;
}

输出：

text
frame ok, len = 3
ok = 1, bad = 0

两处细节决定了这份代码的质量。其一，feed 是唯一的入口，所有字节都从它进来，调试时只要在这一个循环里插一句打印就能看到完整的状态轨迹。其二，struct parser 把全部状态打包在一起，函数只通过参数访问它，没有全局变量，因此可以同时解析多条链路。

main 里故意把一帧拆成「2 字节 + 5 字节」两次喂入，结果与一次喂完完全相同，这就是「状态推进只依赖读到的字节，与一次读多少无关」的直接证明。
