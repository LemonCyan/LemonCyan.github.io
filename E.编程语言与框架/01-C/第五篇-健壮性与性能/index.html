第18章 未定义行为与常见陷阱 #

本章目标：能识别本书前四篇代码里最常见的十余类未定义行为，说出每一类的后果与检测手段，并改写成带边界检查、初始化保证与所有权约定的防御性写法。

18.1 引子：为什么需要这一章 #

C 语言最反直觉的地方在于：写出了错误，编译器往往不报错，程序也常常照常跑完。一个未初始化的指针可能刚好指到一块可写的内存，一段越界的写操作可能只覆盖了一个无关的填充字节，一次格式串与实参类型不匹配可能只是在屏幕上打印出一个诡异的数字。这些错误在当时都被吞掉了，等到换台机器、换个优化等级、换批输入数据，才突然变成段错误（segmentation fault）或结果错乱。排查的成本在这个延迟里被放大了几十倍。

这正是 未定义行为（undefined behavior，以下简称 UB）的可怕之处：它不是「会报错的错误」，而是「标准没有规定会发生什么」的状态。既然标准没有规定，编译器就可以假定它永远不会发生，据此删掉或重排代码。于是同一个错误，在 -O0 下表现正常，在 -O2 下直接崩掉，这种「优化一开就出问题」的现象几乎都能追溯到 UB。

本章的组织方式和普通教材不同：先用一张总表把全部陷阱摆出来，让读者在写代码或查故障时能按症状快速定位；再按类逐条展开，把「错误写法 → 编译器看到什么 → 运行时发生什么 → 怎么改」这条链路走通。读者不必一次记全，但应当记住一个习惯：凡是从外部拿到的长度、下标、指针，在解引用之前都要有一次显式的信任边界。

注意：本章关于 UB 的分类与判定以 C 语言标准的一般约定为依据，具体到某个编译器、某个优化等级下的表现会不同。凡是素材未覆盖、只能靠通用规范说明的地方，正文会显式说明依据，不冒充某份具体文档的结论。

18.2 未定义行为、未指定行为与实现定义行为 #

初学时常把三种「没有唯一答案」的行为混为一谈，实际上它们的严重程度完全不同：

类别 英语原词 标准的态度 典型例子 危害
未定义行为 undefined behavior 不规定任何结果，程序整体失去意义 解引用未初始化的指针、数组下标越界、有符号整数溢出 最高，编译器可据此做任意优化
未指定行为 unspecified behavior 给出若干合法结果，由实现挑选，但不必说明挑哪个 函数实参的求值顺序、a + f() + b 中 f 的调用时机 中，结果不确定但程序仍然有效
实现定义行为 implementation-defined behavior 必须挑选一个结果，并且必须在文档中说明 char 是否有符号、负数右移补 0 还是补 1、int 的位宽 低，可移植性受影响但行为可查

三者的分界对写代码有直接指导意义：

  • 遇到未定义行为，唯一的正确做法是改掉它，不能靠「加个判断碰运气」绕过。
  • 遇到未指定行为，不要依赖某个特定顺序，凡是依赖求值顺序的表达式都拆成多条语句。
  • 遇到实现定义行为，要么写清假设并用 sizeof 与 limits.h 之类的常量做静态检查，要么把它隔离在一个平台适配层里。

一个必须记住的推论是：UB 不是「运行时的错误」，而是「程序不再是程序」。因此讨论「这段 UB 代码在我的机器上输出 42」没有意义——它输出什么都是合法的，包括把整个函数优化成空操作。

18.3 陷阱总表：速查 #

下表是本章的索引，后续各节按编号展开。「检测手段」一栏区分编译期与运行期：编译期手段便宜、应先开满；运行期手段昂贵、按需开启。

编号 陷阱 典型触发写法 后果 检测手段 防御写法
T1 野指针 uninitialized pointer int *p; *p = 1; 写入随机地址，段错误或静默破坏他处内存 编译警告 -Wuninitialized、AddressSanitizer 声明即初始化为 NULL，解引用前判空
T2 悬垂指针 dangling pointer 函数返回栈上局部数组的地址 读到已被复用的栈帧，得到垃圾数据 编译警告 -Wreturn-local-addr 由调用者传缓冲区，或 static、堆分配
T3 释放后使用、重复释放 free(p); free(p); 堆管理结构被破坏，崩溃点远离出错点 AddressSanitizer、Valgrind free 后立即 p = NULL，所有权单一
T4 数组越界与缓冲区溢出 a[5] 访问长度 5 的数组 覆盖相邻变量或返回地址 AddressSanitizer、下标断言 长度与下标成对传递，入口处统一校验
T5 scanf / gets 越界 char b[8]; gets(b); 栈溢出，输入可劫持控制流 编译警告（gets 已被禁用）、长度断言 改用 fgets，scanf 必须带宽度上限
T6 格式化字符串与实参不匹配 printf("%d", 1.5); 按错误宽度取参，读到栈上垃圾 编译警告 -Wformat 格式串与类型逐一对齐，长度修饰符不省
T7 有符号整数溢出 INT_MAX + 1 UB，优化后比较结果被改写 UBSan（-fsanitize=undefined） 运算前先做范围检查，或改用无符号配合显式回绕
T8 隐式符号转换 if (a + b > 0)，b 为 unsigned 且为负 负数变成极大正数，判断恒真 编译警告 -Wsign-compare 无符号常量加 U 后缀，混合运算显式强转
T9 移位位数越界、负数右移 x << 32、-1 >> 1 UB 或结果依赖实现 UBSan、-Wshift-count-overflow 移位量先对位宽取模并断言；负数右移改用除法
T10 指针算术越界 for (vp = &a[n-1]; vp >= &a[0]; vp--) 比较越界指针，UB 或死循环 代码评审、UBSan 只在一个数组对象内（含末尾后一位）做算术
T11 未初始化变量 int sum; sum += x; 初值是栈上残留数据，结果不可复现 编译警告 -Wmaybe-uninitialized 声明即初始化；malloc 后 memset
T12 可变参数类型不匹配 printf("%s", 100); 把整数当指针解引用，崩溃 -Wformat、自定义 format 属性 统一用带类型检查的封装，或不省长度修饰符

表中 T1 与 T2、T3 常被混称「野指针」，实际来历不同：T1 是从没赋过有效地址，T3 是地址曾经有效但指向的对象已经死了，T2 则是指向的对象在函数返回时就被销毁。三者防御手法相近（判空、置空、明确所有权），但排查时的突破口不同。

18.4 四类来源：UB 到底从哪来 #

把全部陷阱按「错误发生在哪一层」归类，比按语法特征归类更好记，也更容易在设计阶段预防：

来源 本质 涉及对象 典型陷阱 参见
生命周期失效 对象已经不存在，指针还在用 栈帧、堆块 悬垂指针、释放后使用、返回局部变量地址 第11章 内存布局
边界失效 对象存在，访问越过了它的范围 数组、字符缓冲区、堆块 越界读写、gets 溢出、指针算术越界 第7章 数组、第9章 字符串
类型失效 存储的位模式与解释方式不一致 整型、指针、可变参数 格式化字符串不匹配、符号混算、强转跨大小 第2章 数据类型、第10章 自定义类型
求值与状态失效 值本身没有确定来源 局部变量、表达式 未初始化变量、有符号溢出、移位越界 第3章 运算符、第5章 控制结构

四类之中，生命周期失效最危险，因为它不会立刻出错：被释放的堆块往往还留在原地，内容要等到被重新分配给别的对象时才被覆盖，于是故障现场与真正的错误现场隔了几百行代码。边界失效最常见，因为几乎所有外部输入（命令行、文件、网络、用户键入）都要先落进一块固定大小的缓冲区。类型失效最难查，因为编译器的类型检查在 printf 这类可变参数函数前面是失效的。求值失效最容易防，只要养成「声明即初始化」的习惯，一大半就消失了。

18.5 指针类陷阱 #

18.5.1 野指针：从没指向过有效对象 #

野指针（wild pointer）指声明之后从未赋过有效地址、内部是一个不确定垃圾值的指针。对野指针解引用或通过它读取输入，是 C 语言里最常见的致命错误之一。素材给出的一组对照写法，把三类相关错误放在一起，正好能说明「地址」与「地址里的值」被混淆的后果：

c
#include <stdio.h>

int main()
{
    int *p, a = 1, b;

    /* 错误示范一：把输入的数值当地址写进指针变量本身 */
    scanf("%d", &p);          /* 编译器警告：期望 int *，实参却是 int ** */

    /* 错误示范二：p 未初始化，内部是随机垃圾地址 */
    scanf("%d", &b);
    *p = b;                   /* 运行直接段错误：向随机地址写入 */

    /* 错误示范三：传入了 *p 即 b 的值（未初始化的随机数），而非地址 */
    p = &b;
    scanf("%d", *p);          /* 编译器警告：期望 int *，实参却是 int */

    return 0;
}

三段错误各有各的机理，值得逐句对照：

写法 编译器看到什么 运行时发生什么 正确写法
scanf("%d", &p); p 是 int *，取地址得 int **，与 %d 要求的 int * 不符 把读到的整数写进指针变量自身的存储单元，指针指向被彻底破坏 scanf("%d", p);（p 已指向有效对象时）
*p = b;（p 未初始化） 语法合法，编译器无从判断 向一个随机地址写 4 字节，段错误或静默破坏他处内存 先 p = &b; 再解引用
scanf("%d", *p); *p 是 int，与 %d 要求的 int * 不符 把 b 的随机值当作地址写入 scanf("%d", p);

同一素材给出的正确顺序是「先定位、再输入、后解引用」：

c
#include <stdio.h>

int main()
{
    int *p, a = 1, b;

    p = &b;           /* 第一步：初始化 p，让它指向有效内存 b */
    scanf("%d", p);   /* 第二步：正确传入指针变量 p（即 b 的地址） */
    *p = a;           /* 第三步：安全解引用，把 a 的值写入 b */

    return 0;
}

注意：上例中 scanf 的返回值被忽略了。工业代码应当检查返回值：返回值是成功赋值的参数个数，输入格式不匹配或到达文件尾时返回 0 或 EOF。把「输入成功」当作既成事实，是野指针之外的另一类高频事故。

18.5.2 悬垂指针：地址有效过，对象已经不在了 #

悬垂指针（dangling pointer）指曾经指向一个合法对象，但该对象已经销毁的指针。最典型的来源是函数返回栈上局部变量的地址：函数返回时栈帧被回收，那块内存随时会被下一次调用复用，此时读到的就是别的函数留下的残渣。

c
#include <stdio.h>

/* 错误：返回局部数组的首地址 */
char *make_name(void)
{
    char buf[16] = "worker";

    return buf;        /* 编译警告：函数返回了局部变量的地址 */
}

int main()
{
    char *name = make_name();

    printf("%s\n", name);   /* 栈帧已回收，输出内容不可预期 */

    return 0;
}

正确的三种改法，按推荐程度排列：

方案 写法要点 适用场景 代价
调用者提供缓冲区 void make_name(char *out, size_t n) 绝大多数场合，所有权最清晰 调用方要负责确定容量
返回 static 缓冲区 static char buf[16]; 单线程、结果立即用完的工具函数 不可重入，两次调用互相覆盖
堆分配并转移所有权 char *p = malloc(16); 生命周期需要跨越调用边界 调用方必须 free，否则泄漏

素材列出的七类内存错误中，另外两类同样属于生命周期问题：结构体成员指针未初始化（声明结构体后直接解引用其中的指针成员）与结构体动态分配空间不足（malloc 少算了成员的实际大小，写入时污染相邻内存）。这两类错误的共同原因是「以为声明了就存在了」——指针成员只是一个地址变量，它指向的对象需要单独创建。

18.5.3 释放后使用与重复释放 #

c
#include <stdlib.h>

int main(void)
{
    int *p = (int *)malloc(sizeof(int));

    if (p == NULL) {
        return 1;
    }
    *p = 10;
    free(p);        /* 对象到此结束 */
    *p = 20;        /* 错误：释放后使用，写进已归还的堆块 */
    free(p);        /* 错误：重复释放，堆管理结构被破坏 */

    return 0;
}
  • 释放后使用（use after free）：堆块已被归还给分配器，内容可能在下次 malloc 时被别的数据覆盖。写入它会破坏别的对象，读取它则拿到垃圾值。
  • 重复释放（double free）：同一块内存归还两次，分配器的空闲链表被串成环，崩溃往往发生在之后某次无关的 malloc 上，故障点远离错误点。

防御手段只有一条是所有场合都成立的：free 之后立即把指针置空，即 free(p); p = NULL;。置空之后，重复释放与部分释放后使用都会变成空指针访问，故障立刻暴露在错误现场，而不是延迟到几百行之后。与之配套的是所有权约定：一块堆内存由谁申请、由谁释放、能否转移，必须在函数注释里写清，参见 第11章「内存布局与动态内存管理」。

注意：把指针置空只能防住「通过同一个指针名再次访问」的情形。如果同一块内存被两个指针同时持有（别名），置空其中一个并不能保护另一个。要彻底解决，需要让所有权单一化，或改用引用计数之类的显式管理结构。

18.6 边界类陷阱 #

18.6.1 数组越界与缓冲区溢出 #

数组越界（out-of-bounds access）是写入或读取了下标范围之外的元素。素材给出的判定原则很实用，可以据此决定哪里必须检查：

下标来源 是否需要每次检查 理由 建议做法
程序内部循环计数器，范围由 0..size-1 严格确定 不必重复检查 逻辑上已被循环条件约束 保持循环边界写法统一，避免 <= 手误
用户键入、命令行参数、配置文件 必须检查 值完全不受控 入口处统一校验，越界直接拒绝
网络数据包、文件读入的长度字段 必须检查 攻击者可以构造任意值 校验长度上限并截断，不信任任何外部长度
由其他函数计算出的偏移量 视情况检查 取决于该函数的正确性 关键路径上加断言

一旦越界的是栈上的数组，后果不止是「读错数据」，而是缓冲区溢出（buffer overflow）：相邻的局部变量、保存的栈帧指针、函数返回地址都可能被覆盖，程序的控制流因此被改写。这是安全漏洞最常见的一类成因，也是「能编译、能运行、但会被攻击」的根源。

18.6.2 指针算术的合法边界 #

C 语言允许指针在同一个数组对象内做加减与比较，并且允许取得「最后一个元素之后那一位」的地址用于比较，但禁止解引用它，也禁止把指针移动到数组起始位置之前。素材用三种数组清零写法把这条边界讲得很清楚：

c
#define N_VALUES 5
float values[N_VALUES];
float *vp;

/* 写法一：顺序清零，安全 */
for (vp = &values[0]; vp < &values[N_VALUES]; )
    *vp++ = 0;

/* 写法二：逆序清零，先自减再解引用，安全 */
for (vp = &values[N_VALUES]; vp > &values[0]; )
    *--vp = 0;

/* 写法三：逆序清零，危险，存在未定义行为 */
for (vp = &values[N_VALUES - 1]; vp >= &values[0]; vp--)
    *vp = 0;
写法 终止时 vp 的位置 是否越界比较 结论
顺序清零 &values[N_VALUES]，即末尾后一位 未越界，标准允许取得该地址做比较，且未解引用 安全
逆序清零 A &values[0] 未越界，进入循环体前先 --vp 回到有效范围 安全
逆序清零 B 处理完 values[0] 后 vp-- 变成 &values[-1] 越界，且用越界指针参与 >= 比较 未定义行为，可能死循环或崩溃

写法三的教训值得单独记住：vp-- 之后的值本身就已经非法，哪怕下一句只是拿它做比较、没有解引用，UB 也已经产生。编译器完全可以把 vp >= &values[0] 优化成恒真的判断，于是循环永不结束。

18.6.3 scanf 与 gets：输入函数的越界面 #

函数 原型 是否有长度限制 风险 替代方案
gets char *gets(char *string); 无 绝不检查目标缓冲区大小，超出长度即栈溢出，已被标准移除 fgets
fgets char *fgets(char *s, int n, FILE *stream); 有，最多读 n-1 个字符并自动补 \0 换行符会保留在缓冲区里，需自行剥离 本身就是推荐方案
scanf("%s", buf) 以空白分隔读入 无上限 与 gets 同级的溢出风险 scanf("%7s", buf) 显式给宽度
scanf("%d", &n) 读整数 不涉及缓冲区长度 返回值被忽略时，后续逻辑用到未赋值的 n 检查返回值，失败时清空输入缓冲

fgets 的两个细节最容易漏：一是它保留换行符，用 strlen 判断末尾并手动改写成 \0；二是它以 n-1 为上限，缓冲区长度为 n 时绝不会多写一个字节。相比之下 scanf("%7s", buf) 的宽度必须与缓冲区容量对应（7 个字符加 1 个结尾符正好 8 字节），一旦缓冲区改小却忘了改宽度，防线立刻失效，因此更推荐统一使用 fgets。

与之相关的还有输入缓冲区残留的换行符：连续读字符时，第二次 getchar 往往直接取走了上一次回车留下的 '\n'，表现为「输入被跳过」。解决办法是在两次读取之间空读一次，或用循环把直到换行或文件结束前的残余字符全部吞掉。

18.6.4 格式化字符串与实参不匹配 #

printf 与 scanf 都是可变参数函数，编译器在类型检查上处于弱势：它只能按格式串推断每个实参应有的类型，无法像普通函数那样用形参声明约束。

c
#include <stdio.h>

int main(void)
{
    int n = 42;
    double d = 1.5;
    char name[8] = "worker";

    printf("%d\n", 1.5);        /* 错误：用 %d 取 double 实参 */
    printf("%s\n", n);          /* 错误：把整数 42 当指针解引用 */
    printf("%d\n", name);       /* 错误：把数组地址当 int 打印 */
    scanf("%d", &d);             /* 错误：&d 是 double *，%d 要 int * */

    return 0;
}
错误类型 后果 后果为什么不可预测
%d 对应 double 按 4 字节读，但实参占 8 字节，后续实参全部错位 浮点实参常通过另一组寄存器传递，取值规则与整型不同
%s 对应整数 把 42 当地址解引用 42 不是合法地址，通常立即段错误
%d 对应数组名 打印地址的低 32 位 高 32 位被丢弃，得到的数字看似正常却毫无意义
scanf 中 %d 对应 double * 按 4 字节写入 8 字节对象的前半部分 该对象后半部分残留旧数据，浮点值被破坏

防御的核心只有一句：格式串与实参逐一对齐，长度修饰符一律不省。long 用 %ld、double 用 %lf（printf 中 %f 亦可）、short 用 %hd、size_t 用 %zu。凡是自己写可变参数函数，应当给它加上格式串检查属性，让编译器替你核对，写法参见 第6章「函数：参数传递、递归与可变参数」。

18.7 类型与求值类陷阱 #

18.7.1 有符号整数溢出 #

有符号整型溢出在 C 语言里是 UB，不是「回绕成一个负数」。这一点与无符号整型恰好相反：无符号整型按模运算回绕，行为有明确定义。

c
#include <stdio.h>
#include <limits.h>

int main(void)
{
    int big = INT_MAX;

    big = big + 1;              /* 未定义行为：有符号整型溢出 */
    printf("%d\n", big);

    unsigned int u = UINT_MAX;

    u = u + 1;                  /* 有定义：回绕为 0 */
    printf("%u\n", u);

    return 0;
}

UB 的实际危害不在于「算错」，而在于编译器会假定它不发生，从而删掉本该成立的判断：

c
/* 编译器可以把这个函数整体优化成恒返回 1 */
int will_overflow(int x)
{
    if (x + 1 > x) {
        return 1;
    }
    return 0;       /* 这行可能被彻底删除 */
}

在编译器看来，x + 1 若不溢出则必然大于 x，若溢出则程序已经是 UB、无需给出任何结果，因此 return 0 分支是死代码。这段代码在 -O0 下可能真的返回 0，在 -O2 下永远返回 1，是「优化一开就出错」的典型样本。

正确的写法是先检查、后运算，并用不会溢出的形式表达检查条件：

场景 错误写法 安全写法
加法的上溢检查 if (a + b < a) if (b > INT_MAX - a)
加法的下溢检查 if (a + b > a) if (b < INT_MIN - a)
乘法 if (a * b / a != b) 先判断 a != 0 && b > INT_MAX / a
无符号的回绕是有定义的 需要回绕语义时误用 int 明确用 unsigned，并在注释里说明这是按模运算

18.7.2 隐式符号转换：最容易被判断为「编译器有空」的坑 #

当有符号与无符号整型混在同一个表达式里，有符号的那个会被转换成无符号，负数于是变成一个极大的正数。素材给出的经典例子是：

c
#include <stdio.h>

int main(void)
{
    int a = 1;
    unsigned int b = -6;

    if (a + b > 0) {
        printf("yes\n");       /* 实际输出 yes */
    } else {
        printf("no\n");
    }

    printf("%d\n", a + b);     /* 按有符号解析：-5 */
    printf("%u\n", a + b);     /* 按无符号解析：4294967291 */

    return 0;
}

机理是：b 声明为 unsigned int 并初始化为 -6，存储时按模回转成一个极大值；计算 a + b 时 a 也被提升为无符号，结果自然恒大于 0。同一份位模式用 %d 打印得到 -5，用 %u 打印得到 4294967291——这正是「类型失效」的教科书例子：值没有变，解释方式变了。

防御习惯有三条：给所有无符号常量加 U 后缀（如 10U、0xFFFFU）；避免把有符号与无符号放进同一个比较；开启 -Wsign-compare 并认真对待它的每一条警告。

18.7.3 移位：位数越界与负数右移 #

表达式 是否合法 说明
x << 3 合法 等价于乘以 8，前提是不溢出
x << 32（x 为 32 位） UB 移位量必须小于操作数位宽
x << -1 UB 移位量为负
-1 >> 1 实现定义 补 0 为逻辑右移，补 1 为算术右移，多数平台补 1
1u << 31 合法 无符号左移，结果 2147483648
1 << 31（int） UB 有符号左移溢出到符号位

防御写法是把移位量当作外部输入对待：

c
#include <limits.h>

unsigned int mask_of(int k)
{
    /* 移位量先做范围约束，再参与运算 */
    if (k < 0 || k >= (int)(sizeof(unsigned int) * CHAR_BIT)) {
        return 0U;
    }
    return 1U << k;
}

用 CHAR_BIT（每字节位数）而不是硬编码 8，可以在位数不同的平台上仍然正确，这也是「用常量代替魔数」的实际收益之一。

18.7.4 未初始化变量 #

局部变量如果没有初始化，它的值是栈上残留的任意数据——可能是上一个函数留下的返回值，也可能是根本不该被解释为整数的字节。malloc 返回的堆内存同样不清零，直接读取得到的是系统垃圾数据。

c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int sum;                        /* 未初始化 */
    int i;

    for (i = 1; i <= 3; i++) {
        sum += i;                   /* 累加到一个随机初值上 */
    }
    printf("%d\n", sum);

    int *heap = (int *)malloc(8 * sizeof(int));

    if (heap == NULL) {
        return 1;
    }
    printf("%d\n", heap[0]);        /* 堆内存未清零，读到垃圾值 */
    free(heap);

    return 0;
}

两条防御规则足以覆盖绝大多数情况：局部变量声明即初始化（int sum = 0;）；动态申请的内存若要先读后写，或用 calloc、或紧跟一句 memset 清零。

18.7.5 可变参数的类型不匹配 #

可变参数函数（variadic function）在读取参数时只知道「格式串说要什么类型」，没有任何类型信息可供核对。第6章讲过 va_arg 必须指定准确类型，此处补充它带来的两类陷阱：

陷阱 写法 后果
整型宽度不匹配 printf("%d", (long)big) 只取 4 字节，后续参数错位
浮点提升被忽略 自己用 va_arg(ap, float) 取参 实参已被提升为 double，按 float 取会读到错误位
指针与整数混用 printf("%s", 100) 把 100 当地址解引用，通常立即崩溃
结尾缺少哨兵 自定义函数用指针列表却忘了传 NULL 循环读到栈上垃圾指针

防御手法与 18.6.4 一致：优先使用编译器能检查的调用形式，自定义可变参数函数时把格式串属性写上，让 -Wformat 覆盖到自己的函数。

18.8 检测手段：把看不见的错误变成看得见的报错 #

上述陷阱大多不会让编译器直接报错，因此需要主动开启检测工具。下表按「成本从低到高」排列，前三项应当作为日常开发的默认配置：

手段 开启方式 能发现哪些陷阱 代价
编译警告全开 gcc -Wall -Wextra -Wformat -Wsign-compare T1、T2、T6、T8、T11 的一部分 几乎为零，只多读几条警告
静态断言与运行时断言 assert(p != NULL);、assert(i < n); T4、T10、参数前置条件 运行时开销，Release 可用 NDEBUG 去掉
UBSan -fsanitize=undefined T7、T9 及各类非法运算 约 2 倍运行时开销
AddressSanitizer -fsanitize=address -g T2、T3、T4、T5、T10 约 2 倍内存与较大运行时开销
Valgrind valgrind --leak-check=full ./a.out T3、未初始化读取、内存泄漏 数十倍变慢，适合小规模复现

几点经验：

  • 断言是给「本不该发生」的情况用的，不是用来处理用户输入错误。参数校验、下标范围这类前置条件适合断言；用户输错格式应当走正常的错误分支，不能靠 assert 崩掉程序。
  • assert 在定义了 NDEBUG 之后会被整体去掉，因此断言表达式里不能写有副作用的代码，例如 assert(p = malloc(8) != NULL) 在 Release 版本下会连分配都不执行。
  • AddressSanitizer 与 UBSan 可以在同一次编译里同时开启，代价相加但通常能一次跑出多个问题，是排查「偶发崩溃」性价比最高的组合。
  • 崩溃点不等于错误点。堆相关的错误（重复释放、越界写）往往在很久之后才表现，遇到这类现象应先用 AddressSanitizer 跑一遍再动手改代码。

18.9 防御性写法：四条可执行的约定 #

前面各节的防御手段可以收敛成四条约定，写新代码时逐条落实，能消掉本章总表里的大半条目：

约定 具体做法 消灭的陷阱
声明即初始化 指针一律初始化为 NULL，整型与浮点初始化为 0，数组与堆块先清零 T1、T3（部分）、T11
所有权单一 一块内存只由一个指针负责释放；转移所有权在注释里写明 T2、T3
长度与指针成对传递 形参写成 (char *buf, size_t n)，绝不让被调函数猜容量 T4、T5
外部输入先校验 下标、长度、格式串在入口处统一检查，越界直接拒绝 T4、T5、T7、T9

第四条需要强调：校验要发生在使用之前，而且要校验真正被使用的那个变量。常见错误是校验了 len 却使用了 len + 1，或校验了输入字符串的长度却对截断后的副本做写操作。校验与使用之间只要插入任何一次运算，就必须重新确认。

18.10 小结 #

  • 未定义行为 undefined behavior 不是「结果随机」，而是标准不再对程序作任何承诺：编译器可以假定它永不发生，并据此删掉你写的检查。
  • 本章的十二类陷阱可以归到四个来源：对象生命周期、边界、类型、求值与状态失效。定位问题时先问一句「这块内存、这个值此刻是否还归我管」。
  • 指针类错误的共同根源是「指针与所指对象的生命周期脱钩」，最低成本的两条防线是声明即初始化为 NULL 与释放后立即置空。
  • 边界类错误的共同根源是「长度与指针分开传递」，让所有写操作都经过同一个带容量检查的入口，就不会出现「这个函数该写到哪一位」的猜测。
  • 输入函数的选择直接决定安全边界：gets 不存在安全用法，scanf 的 %s 与 %[ 必须带宽度，需要跨行读取时用 fgets 读整行再解析。
  • 格式串里的每个转换说明都是对实参类型的一次断言，编译器能在 -Wformat 下替你核对，这项免费的检查没有理由关掉（参见 第13章 标准库函数速查）。
  • 有符号整数溢出、移位位数越界、指针算术越界在标准里同属未定义行为，编译器可以合法地把「溢出后回绕」的写法优化成完全不同的结果，所以「我测试时是对的」不构成论证。
  • 工具链上先开 -Wall -Wextra，再按需叠加 UBSan 与 AddressSanitizer；崩溃点往往不是错误点，堆相关的错误要回到分配与释放的现场去看（参见 第11章 内存布局与动态内存管理）。
