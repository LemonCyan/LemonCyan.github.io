一、终端、Shell、控制台：三个容易混的概念 #

三个词天天一起出现，但不在同一个层面。混着用，排查问题时就容易找错方向。

概念 本质 处在哪一层 典型实体
终端 设备，或模拟设备的程序 设备层，最外层 屏幕加键盘、vt100、xterm、gnome-terminal
Shell 命令解释器 用户态程序层，中间 bash、zsh、ash、tcsh
控制台 内核的一个输出通道 内核层，最里层 /dev/console、tty1

一句话记住：终端是设备，Shell 是程序，控制台是内核的一个输出通道。

按这个划分，几个日常混淆就能拆开：

  • 你在 gnome-terminal 里敲 ls。gnome-terminal 是终端（模拟器），ls 是 Shell 起的子进程，输出被写回终端。
  • 按 Ctrl+Alt+F3 看到的黑屏界面。那是虚拟终端，同时充当控制台。
  • 服务启动失败时内核打印的 Oops。它进不了任何用户终端，只进控制台和内核环形缓冲区。

层次弄清楚，后面两件事才有解释力：计划任务为什么跑不起来，同一个程序为什么在终端里正常、在服务里乱码。两者的根源相同——跨过某一层时，进程的运行环境被换掉了。

二、终端：从物理设备到伪终端 #

2.1 物理终端 #

终端（terminal，也叫物理终端）是一种设备，不是一个程序。说的就是能提供命令行用户界面的设备，典型形态是屏幕加键盘，或者别的专用终端机。

这个概念来自多人共用一台计算机的年代。计算机贵，一台机器要给多个人同时用，就得接上许多套键盘和显示器。当时专门有这种设备：只有显示器、键盘和简单的处理电路，本身不具备处理信息的能力，靠串口连到一台真正的主机上，登录进去操作。

它有三个特征：是附加设备，主机上没有它照样能跑；通过串口、电缆连接，不在主机机箱里；自己不算计算机，只负责输入输出的搬运。

真正的串口终端今天已经很罕见，但还是存在。也有人拿 386、486 的老电脑装个串口通信软件，连到一台主机上模拟终端用，达到一机多人使用的效果。

2.2 虚拟终端 #

屏幕和键盘只有一个，不够用，又不想增加设备投入，就产生了虚拟终端。一台主机的显卡和键盘被内核切成若干个逻辑终端，用快捷键切换。

Linux 上是 6 个，tty1 到 tty6。字符模式下按 Alt+F1 到 F6 直接切；在 X 或 Wayland 会话里要加 Ctrl，也就是 Ctrl+Alt+F1 到 F6。切回图形界面看你的显示管理器占了哪个 tty，一般是最先空出来的那个。

2.3 终端模拟器 #

gnome-terminal、urxvt、mlterm、xterm 都是程序，职责是模拟终端设备。它们和虚拟终端的区别，表面上看是以 GUI 窗口的形式出现，内部则是程序结构和系统控制结构有所不同，本质差不多。

软件栈上一直是一条链：

text
字符程序 <---> 虚拟终端 <---> 图像显示
shell    <---> xterm       <---> X11

2.4 vt100 与终端标准 #

早期硬件终端厂家不同、遵循的标准不同，于是有不同的型号：vt100、vt220、vt52 等等。vt100 就是一个标准。

今天的终端模拟器大多实现一套 vt100 超集，加上颜色、光标定位、鼠标上报之类的扩展。TERM 环境变量就是在声明自己按哪个标准工作，echo $TERM 在常见的图形终端里输出 xterm-256color。

不同的终端模拟软件符合不同的标准，有些同时符合多种。gnome-terminal 早期在配置里能直接选出好几种终端标准，设置一下就行；新版把这个选项收进了 profile，实际生效的仍是 TERM。

2.5 伪终端 #

SSH 进来、tmux 里开窗口、图形终端里敲命令，拿到的都不是真设备，而是伪终端（pty）。一个 pty 是一对设备：主端（master）由 sshd、tmux、终端模拟器持有，从端（slave）交给 Shell，路径形如 /dev/pts/3。

节点 含义
/dev/tty1 起 内核虚拟终端，编号从 1 开始，上限跟内核配置有关
/dev/console 系统控制台
/dev/pts/N 伪终端从端，SSH、tmux、终端窗口都用它
/dev/tty 当前进程的控制终端，一个别名 
bash
tty
ps -o pid,tty,comm -p $$

text
/dev/pts/1
  PID TT       COMMAND
 4211 pts/1    bash

tty 报 not a tty，说明当前进程没有终端。cron、systemd 服务、ssh host 'cmd'（不带 -t）都是这种状态。后面第九章的坑全从这里长出来。

三、Shell：命令的解释器 #

3.1 Shell 是什么 #

Shell 是一个抽象概念。它的一切操作都在计算机内部，负责处理人机交互、执行脚本，是操作系统能正常运行的重要组成部分。

bash、ash、zsh、tcsh 是 Shell 这个抽象概念的具体实现，都是程序，都能生成一个进程对象。

实现 定位
sh POSIX 规定的接口，各发行版链接到 dash 或 bash
bash Linux 上的默认选择，交互与脚本通用
dash Debian、Ubuntu 的 /bin/sh，启动快，只认 POSIX
zsh 交互体验好，插件与主题多，配置量大
ash / busybox sh 嵌入式、容器镜像里常见，功能最精简
tcsh / csh C 风格语法，写脚本的人少

3.2 换一个 Shell #

改 /etc/passwd 里对应用户的最后一个字段，把 /bin/bash 换成想要的 Shell：

text
liuluhua:x:1000:1000::/home/liuluhua:/bin/bash

或者用 chsh 命令：

bash
chsh -s /bin/zsh
cat /etc/shells

/etc/shells 列出系统认可的登录 Shell。名字不在这个文件里，chsh 会拒绝，su、FTP 这类需要登录 Shell 的入口会跟着拒绝。

3.3 Shell 和终端的关系 #

Shell 把一些信息适当输送到终端设备，同时接收来自终端设备的输入。每个 Shell 进程一般有一个终端关联，也可以没有。

有终端时，Shell 走交互路径：读命令、显示提示符、处理 Ctrl+C、支持作业控制。

没有终端时：

bash
bash -c 'echo hi > /tmp/x.txt'
nohup ./server >> server.log 2>&1 &
echo 'x' | zsh

作业控制、read 读输入、Ctrl+C 转信号全都不成立，Shell 读完脚本就退。

3.4 交互与非交互、登录与非登录 #

这两个正交的维度决定 Shell 读哪些启动文件，也就决定你的环境变量从哪来。

组合 典型场景 读哪些文件（bash）
交互 + 登录 tty 登录、ssh host /etc/profile、~/.bash_profile 或 ~/.bash_login 或 ~/.profile
交互 + 非登录 桌面里开终端窗口、再套一层 bash ~/.bashrc
非交互 + 非登录 bash script.sh、cron、systemd 服务 只读 $BASH_ENV 指向的文件，默认没有

确认当前状态：

bash
echo $-                       # 含 i 表示交互式
shopt -q login_shell && echo login || echo non-login

关键点：cron 和 systemd 起的进程是「非交互 + 非登录」，上表那一列文件一个都不读。别名、函数、PATH 追加、代理变量，统统没有。这条在第九章会反复用到。

四、控制台：内核的输出窗口 #

4.1 定义 #

显示系统消息的终端就叫控制台。Linux 默认所有虚拟终端都是控制台，都能显示系统消息。

有时它专指 CLI 下模拟终端设备的一个程序，和 gnome-terminal、urxvt、mlterm、xterm 属于同一类，只是 CLI 和 GUI 界面的区别。

console 一般有 6 个，tty1 到 tty6，Ctrl+Alt+F1 到 F6 切换。

4.2 历史来源：为什么控制台只有一个 #

回到多人共用的年代。学机电的人知道，一台机床或者数控设备的控制箱，叫的就是控制台——顾名思义，一个直接控制设备的台面，上面一排按钮。

挪到计算机里，直接把连着主机的那套键盘和显示器叫控制台。它和终端的区别在这几点：

  • 终端是通过串口连上来的，不是计算机本身就有的设备
  • 控制台是计算机本身就有的设备，一台计算机只有一个
  • 启动时所有信息都显示到控制台，不会显示到终端
  • 内核消息、后台服务消息可以显示到控制台，不会显示到终端

控制台是基本设备，终端是附加设备。控制台也有终端一样的功能，所以日常被模糊地统称为终端。

4.3 Linux 的做法：淡化区别 #

bash
echo "hello,world" > /dev/console

目的是把 hello,world 显示到控制台，/dev/console 是控制台设备的设备名。在字符模式下，无论在哪个虚拟终端执行这条命令，字符串都显示在当前虚拟终端上——Linux 把当前终端当作控制台看待。控制台和终端的区别在这里已经完全淡化了。

4.4 别的 UNIX：区别很明显 #

FreeBSD 上只有第一个终端才是真正的控制台，也就是按 Alt+F1 得到的那个。无论在哪个虚拟终端执行上面那条命令，哪怕是在通过网络连过来的伪终端上执行，hello,world 都显示到第一个终端上。

系统内部信息也一样：哪个用户在哪个终端登录、系统有什么严重错误警告，全都显示在这个真正的控制台。其他 UNIX 类系统也是这种处理。

Tru64 UNIX 在 X 下有一个控制台模拟软件，无论在哪输入 echo "hello,world" > /dev/console，hello,world 都显示在那个控制台模拟器里。

X 界面下输入命令的那些软件，xterm、rxvt、gnome-terminal 等等，都应该叫终端模拟软件，和控制台模拟软件是两回事。Linux 上基本没有控制台模拟软件这种东西。

4.5 一个能复现的实验 #

字符方式登录系统，进第一个虚拟终端，startx 启动 X 服务器，再打开 xterm 执行：

bash
echo "hello,world" > /dev/console

字符串显示在第一个虚拟终端上。按 Ctrl+Alt+F1 回到启动 X 的那个终端，就能看到它。这条实验把「控制台」和「终端窗口」的边界摆得最清楚。

日常很少直接往 /dev/console 写东西，但控制台一直在干活：dmesg、journalctl -k 读的是内核环形缓冲区，cat /dev/kmsg 直接跟内核消息流，Ctrl+Alt+F1 切过去的虚拟终端就是最接近控制台的位置。

简化记法：控制台是直接和计算机相连的原生设备，终端是通过电缆、网络等等和主机连接的设备。这些设备正从视野里退出，概念也慢慢淡化。普通用户可以简单地把终端和控制台理解为「能输入命令行、并显示程序运行信息与运行结果的窗口」，不必要严格区分这两者。

五、三者的层次关系 #

一条命令从键盘到输出，要穿过五层：

text
用户
  │  敲键盘 / 看屏幕
  ▼
[终端层]      物理终端、虚拟终端 tty1、终端模拟器 xterm、SSH 客户端
  │  字符流：读 stdin，写 stdout / stderr
  ▼
[终端驱动层]  tty 驱动、pty 主从对、行规程
  │
  ▼
[Shell 层]    bash / zsh 进程：解析命令行、做展开、fork + exec
  │
  ▼
[命令进程层]  ls、tar、python、你的 Qt 程序
  │  系统调用
  ▼
[内核层]      控制台 /dev/console、内核日志、设备驱动

抽出来看各自的职责：

层 归属 管什么 出问题时的表现
终端 用户态设备或程序 收键盘、画字符 显示错位、TERM 不识别、画面乱码
行规程 内核 tty 子系统 回显、行编辑、Ctrl+C 转信号 退格失灵、Ctrl+C 无效
Shell 用户态程序 解析、展开、起子进程 命令找不到、引号不配对
命令进程 用户态程序 真正干活，写 stdout / stderr 报错、退出码非 0
控制台 内核 承接内核和服务的消息 只在显示器上，进不了日志

要害只有一句：跨层时环境会被替换。

  • 从行规程往上，是有终端的路径。Shell 能读 ~/.bashrc，LANG 从登录那一串流程里带下来，PATH 被 profile 追加过。
  • 绕开终端直接起进程，比如 cron、systemd、ssh host 'cmd'，环境由启动者重新给一份，默认是极简的一套。

所以「终端里跑得好好的脚本，放进 cron 就报 command not found」和「同一个程序，手动启动日志正常，用 service 启动就乱码」，本质是一件事：换了入口，也就换了环境。第七到第十五章讲的全是如何确认这份环境、如何补上。

六、登录时都发生了什么 #

一次 tty 登录的流程：

  1. 内核和 agetty 打开 /dev/tty1，显示登录提示
  2. 你输入用户名密码，login 校验，通过后读 /etc/passwd
  3. 取出最后一个字段，也就是登录 Shell 的路径，exec 它
  4. Shell 作为登录 Shell 启动，依次读 /etc/profile、~/.profile（bash 先找 ~/.bash_profile、~/.bash_login）
  5. 环境变量由 /etc/environment、PAM 模块、profile 脚本共同拼出来
  6. 提示符出现

SSH 登录是同一套流程，区别在链条前半段：

text
sshd → 分配 pty（/dev/pts/N）→ 登录 shell → profile 脚本

桌面里点终端图标开的窗口又不一样：

text
显示管理器 → 图形会话 → gnome-terminal → 申请 pty → 非登录交互 shell

它读 ~/.bashrc，不读 /etc/profile。这解释了为什么在终端窗口里追加的 PATH，在 tty1 登录后看不到。

入口 有终端 Shell 类型 启动文件 LANG 来源
tty 登录 /dev/tty1 交互 + 登录 /etc/profile、~/.profile /etc/environment、PAM
SSH 交互 /dev/pts/N 交互 + 登录 同上 同上，另加 sshd 的 AcceptEnv
桌面终端窗口 /dev/pts/N 交互 + 非登录 ~/.bashrc 图形会话环境
cron 无 非交互 + 非登录 不读 crond 自己那套
systemd 服务 无 非交互 + 非登录 不读 unit 里的 Environment=

确认自己现在处在哪一档：

bash
echo $0
echo $LANG $LC_ALL
tty
cat /proc/$$/environ | tr '\0' '\n' | grep -E '^(LANG|LC_)'

echo $0 输出 -bash 时，前面那道横杠表示登录 shell。

/proc/<pid>/environ 是查环境最硬的证据。程序自己打印的「当前环境」会被改过，这个文件不会。

七、计划任务：cron #

cron 是个守护进程（crond），每分钟醒来一次，扫一遍所有 crontab，把到点的任务 fork 出去。粒度就是分钟。

crontab 有四个放置位置，字段格式不一样：

位置 字段格式 说明
crontab -e 编辑的用户表 五字段 + 命令 存在 /var/spool/cron/crontabs/<user>（Debian 系）或 /var/spool/cron/<user>（RHEL 系）
/etc/crontab 五字段 + 用户名 + 命令 系统级，手工维护
/etc/cron.d/* 五字段 + 用户名 + 命令 装包时投放
/etc/cron.{hourly,daily,weekly,monthly}/ 只放可执行脚本 由 run-parts 调用，不写时间

7.1 四个操作 #

bash
crontab -e
crontab -l
crontab -r
crontab -u root -e

-e 创建、编辑当前用户的计划任务，-l 查看，-r 删除，-u <user> 操作他人的表（需 root）。

-r 要单独提醒：它删的是整张表，不是某一条。素材里写成「删除某条计划任务」，实际操作时一条都不剩，删单条只能用 -e 进去删那一行。动之前先备份：

bash
crontab -l > /root/crontab.bak

7.2 一个能用的例子 #

crontab -e 打开编辑器，写一行：

text
25 3 * * 1,3,5 /usr/bin/tar -czvf /var/backups/wwwroot.tar /home/wwwroot

保存退出，crontab -l 能原样看到这行，说明已经装进去了。它的意思是每周一、三、五的 03:25，用 /usr/bin/tar 把 /home/wwwroot 打包到 /var/backups/wwwroot.tar。

/usr/bin/tar 为什么写全路径？cron 的 PATH 很短，裸写 tar 能不能命中要看运气。查路径用 whereis：

bash
whereis rm

text
rm: /usr/bin/rm /usr/share/man/man1/rm.1.gz

它给出二进制、源码、手册页的位置，crontab 里抄第一段。command -v rm 也能查到解析后的路径。

八、crontab 的五个时间字段 #

用户 crontab 的一行是「五个时间字段 + 命令」，系统 crontab 和 /etc/cron.d 里的行中间多一个用户名字段。

序 字段 取值范围 可用符号
1 分钟 0-59 * , - /
2 小时 0-23 同上
3 日期 1-31 同上
4 月份 1-12，或 jan 到 dec 同上
5 星期 0-7，0 和 7 都是周日，或 sun 到 sat 同上
6 用户名 只有系统 crontab 与 /etc/cron.d 有 —
末位 命令 要运行的命令 按 shell 语法

素材里那串 25 3 * * 1,3,5，依次是分钟、小时、日期、月份、星期：25 分、3 点、每月任意一天、任意月份、周一和周三和周五。四个符号的含义：* 是每个取值都算，, 是枚举，- 是区间，/ 是步长（*/5 每 5 分钟，0-30/10 是 0 到 30 分之间每 10 分钟）。

text
25 3 * * 1,3,5    每周一、三、五 03:25
*/5 * * * *       每 5 分钟
0 2 * * *         每天 02:00
0 2 1 * *         每月 1 日 02:00
30 4 * * 0        每周日 04:30
0 */6 * * *       每 6 小时整点

@ 开头的简写：

写法 等价于
@reboot 开机后执行一次
@hourly 0 * * * *
@daily 或 @midnight 0 0 * * *
@weekly 0 0 * * 0
@monthly 0 0 1 * *
@yearly 或 @annually 0 0 1 1 *

两条边角规则。日期位和星期位都不是 * 时，Vixie cron 按「或」处理，任一边匹配就执行；要「每月 1 日、且那天正好是周一」这种交集，得在命令里自己判断。还有，crontab 没有秒，要秒级精度用 systemd timer 的 OnCalendar。

cron 没有 dry-run。验证时间字段只有一招：把命令那段单独手跑一遍，确认能跑通，再放进 crontab。

九、cron 的常见坑 #

计划任务失败，九成落在这几条里。

9.1 PATH 和登录 shell 不同 #

crond 给任务的 PATH 是极简值，常见就是 /usr/bin:/bin。登录 shell 的 PATH 长得多：/usr/local/bin、~/.local/bin、nvm 目录、pyenv 的 shims。于是终端里敲 backup.sh 能跑，crontab 里报 command not found。

text
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
25 3 * * 1,3,5 /usr/local/bin/backup.sh

放 crontab 顶部对整张表生效，或者每行都写绝对路径，或者把 PATH 写进脚本。

9.2 不读 .bashrc，也不读 .profile #

cron 用 /bin/sh -c 执行那一行，是「非交互 + 非登录」shell，~/.bashrc、~/.profile、/etc/profile 一个都不读。你写进 ~/.bashrc 的别名、函数、PATH 追加、export HTTP_PROXY，在 cron 里全不存在。

把环境搬进脚本头部：

bash
#!/bin/bash
export PATH=/usr/local/bin:/usr/bin:/bin
export LANG=zh_CN.UTF-8
cd /home/wwwroot || exit 1
./backup.sh

#!/bin/bash 也别省。Debian 系的 /bin/sh 是 dash，不认 [[ ]]、数组、source，脚本在终端里跑得好，被 cron 用 sh 起就语法报错。要换解释器，在 crontab 顶部写 SHELL=/bin/bash。

9.3 % 必须转义 #

crontab 里 % 表示换行，% 之后的内容被当成命令的标准输入。带日期的命令会被从 % 处切断：date +%F 实际只执行到 date +，tar 报参数错误。

text
25 3 * * 1,3,5 /usr/bin/tar -czf /var/backups/www-$(date +\%F).tar.gz /home/wwwroot

%H、%Y、%m 全都这样处理。嫌麻烦就把这段逻辑包进脚本，crontab 里只写 /usr/local/bin/backup.sh。

9.4 工作目录不是你以为的那个 #

用户 crontab 执行任务时当前目录是 $HOME。素材里那句 tar -czvf backup.tar ... 中的 backup.tar 会落在 /root 或 /home/<user> 下，跑成功了但找不到文件。命令路径、输入路径、输出路径全写绝对。

9.5 输出默认走邮件 #

cron 把任务的 stdout、stderr 当邮件发给 MAILTO。机器上没配 MTA，这些输出直接消失，你只知道「任务没生效」，看不到原因。

text
25 3 * * 1,3,5 /usr/bin/tar -czvf /var/backups/wwwroot.tar /home/wwwroot >> /var/log/backup.log 2>&1

2>&1 一定要跟。只重定向 stdout，报错还是走邮件，等于没记。

9.6 其余几条 #

坑 表现 处理
crontab -r 手滑 整张表消失 改之前 crontab -l > file
文件末尾没有换行 最后一行不执行 用 crontab -e 编辑，别用脚本拼文件
任务重叠 两轮备份抢同一个输出文件 flock -n /tmp/x.lock cmd
时区 夏令时前后跳过或重复一次 需要固定时区时写 CRON_TZ=Asia/Shanghai
以为有秒 9:00:30 和 9:00:59 没区别 crontab 最小粒度是分钟

任务重叠的写法：

text
*/10 * * * * /usr/bin/flock -n /tmp/backup.lock /usr/local/bin/backup.sh

-n 表示拿不到锁就立刻退出，不排队等。上一轮没跑完，新一轮直接跳过。

十、systemd timer #

systemd 的机器上还有一套：一个 .service 定义跑什么，一个 .timer 定义什么时候跑，两个文件都放 /etc/systemd/system/。

backup.service：

ini
[Unit]
Description=Backup wwwroot

[Service]
Type=oneshot
Environment=LANG=zh_CN.UTF-8
ExecStart=/usr/local/bin/backup.sh

backup.timer：

ini
[Unit]
Description=Run backup on Mon, Wed, Fri at 03:25

[Timer]
OnCalendar=Mon,Wed,Fri 03:25
Persistent=true
Unit=backup.service

[Install]
WantedBy=timers.target

Type=oneshot 表示跑完就退的短任务，不常驻。Unit= 省略时，foo.timer 自动去找 foo.service。

bash
sudo systemctl daemon-reload
sudo systemctl enable --now backup.timer
systemctl list-timers --all
systemctl status backup.timer
journalctl -u backup.service -n 50 --no-pager

daemon-reload 别漏。改完 unit 不 reload，enable 起来的还是旧内容。

写法 含义
Mon,Wed,Fri 03:25 每周一三五 03:25
Mon..Fri 09:00 周一到周五 09:00
*-*-* 02:00:00 每天 02:00
daily / hourly / weekly 等价的简写
*:0/15 每 15 分钟
*-*-* 03:25:30 带秒，cron 做不到

写之前先验证，它会报出下次触发的具体时间：

bash
systemd-analyze calendar 'Mon,Wed,Fri 03:25'
项 cron systemd timer
配置位置 crontab 或 /etc/cron.d/ /etc/systemd/system/ 下两个 unit
最小粒度 1 分钟 1 秒
环境变量 crond 给的极简环境 Environment= / EnvironmentFile= 显式声明
输出去哪 邮件，没配 MTA 就丢 journal，journalctl -u 直接看
关机期间错过 不补 Persistent=true 开机补一次
依赖顺序 无 After=、Requires= 能排
看下次执行时间 没有 systemctl list-timers
手动跑一次 复制命令手跑 systemctl start backup.service

Persistent=true 是这套东西比 cron 顺手的地方：机器关机、笔记本合盖，错过的触发点开机后补跑一次。反过来，容器里没 systemd，还是一行 crontab 省事。

十一、一次性定时任务：at #

at 时间 是命令行工具，用于在指定的时间执行一次性任务。通过它可以把命令或脚本安排到将来某个时间点运行。

时间参数支持多种格式：HH:MM、HH:MM AM/PM、2pm，以及 tomorrow、midnight、teatime、now + 1 hour。

bash
at 2pm < /usr/local/bin/backup.sh

不加重定向时进入交互输入，一行一条命令，Ctrl+D 结束：

bash
echo '/usr/local/bin/backup.sh' | at 2pm
命令 作用
at -l 或 atq 列出当前计划的 at 任务，含任务序号、执行时间、队列
atrm 1 取消序号为 1 的 at 任务，序号来自 at -l
at -c 1 打印序号 1 的任务原文，含执行时的环境变量

at 只往队列塞文件，真正执行的是 atd：

bash
sudo systemctl enable --now atd
systemctl status atd

atd 没起，at 照样提交成功，到点什么都不发生。这是 at 最安静的一种失败。

十二、任务的日志去哪了 #

任务类型 输出默认去向 查看方式
用户 crontab 按 MAILTO 发邮件，没 MTA 就丢 重定向到文件；journalctl -t CRON
/etc/cron.d、系统 crontab 同上 同上
systemd timer journal journalctl -u backup.service
at 邮件发给提交者 重定向；at -c 看任务原文

cron 执行那一刻，日志里只有「要跑这条命令」，不含命令的输出：

bash
journalctl -u cron --since today | grep -i backup

内容形如 (root) CMD (/usr/bin/tar ...)。有 CMD，说明 cron 认了这行也起了进程，任务失败就是命令本身或它环境的问题；没有 CMD，问题在时间字段、语法，或者表根本没保存成功。排查第一步先看有没有 CMD，一次把范围砍成两半。RHEL 系日志在 /var/log/cron，Debian 系在 /var/log/syslog 或 journal 里。

systemd 那边按 unit 过滤，不用在几千行 syslog 里翻：

bash
journalctl -u backup.service --since '1 day ago'
systemctl status backup.service

最稳的做法还是自己写日志。脚本开头把输出全接进文件：

bash
#!/bin/bash
exec >>/var/log/backup.log 2>&1
echo "=== $(date '+%F %T') start"
/usr/local/bin/backup.sh
echo "=== $(date '+%F %T') done, exit=$?"

exec 改写的是当前 shell 的所有输出，之后脚本里每条命令的 stdout、stderr 都进日志，crontab 那行不用再挂 >>。有了时间戳，「昨天那次到底跑了没有」就是翻一行的事。

日志写对了，下一个问题才会露出来：日志里全是乱码。

十三、服务启动程序时的日志乱码 #

现象很短：用 service 启动 Qt 程序，输出的日志是中文乱码；直接启动程序，输出的日志却是正常的。

同一个二进制、同一份配置、同一段中文日志，差别只在启动方式。范围就此限死在环境上，不是程序 bug，也不是日志文件坏了。

13.1 直接启动为什么正常 #

你在终端里敲 ./app，父进程是 Shell。Shell 环境里有 LANG=zh_CN.UTF-8（或 en_US.UTF-8），变量被继承给 app。Qt 初始化时读 QLocale::system() 和 QTextCodec::codecForLocale()，拿到 UTF-8，中文按 UTF-8 编好写出去，终端也按 UTF-8 解回来，前后一致，显示正常。

13.2 方案一：给 service 脚本补回 LANG #

素材里的做法是编辑 service 脚本：

bash
vim /sbin/service

在 env -i 后面加上 LANG="$LANG"，让启动命令长这样：

bash
exec env -i LANG="$LANG" PATH="$PATH" "$@"

env -i 的作用是清空环境变量再 exec，服务因此拿到一个干净环境。干净的含义是 LANG 也没了，程序落到 C locale，等价于 LANG=C。把这一项补回去，编码就和终端一致了。

前提是系统本身支持中文语言包。locale -a 里没有 zh_CN.UTF-8，补变量也没用，得先装语言包或者 locale-gen。

13.3 方案二：在启动脚本里引入环境变量 #

不碰系统脚本，改自己的启动脚本，头部把变量导出去：

bash
#!/bin/bash
export LANG=zh_CN.UTF-8
export LC_ALL=zh_CN.UTF-8
exec /opt/app/bin/app "$@"

service 的启动命令指到这个 wrapper 就行。这就是素材里的方案二：在启动脚本中引入环境变量。

13.4 更稳的落点：unit 文件 #

改 /sbin/service 有个副作用：这个文件归包管理所有，升级时会被覆盖回去，补丁悄无声息地失效，下次重启又乱码。现在多数发行版的服务由 systemd 拉起，/sbin/service 只是兼容入口，把变量写进 unit：

ini
[Service]
Environment=LANG=zh_CN.UTF-8
Environment=LC_ALL=zh_CN.UTF-8
ExecStart=/opt/app/bin/app

变量多的时候用 EnvironmentFile=/etc/app/env 指向一个文件，一行一个键值。

改完 systemctl daemon-reload，再 restart。

做法 改动位置 升级会丢吗 适用
补 env -i /sbin/service 会，被包升级覆盖 临时救火
脚本里 export 自己维护的 wrapper 不会 sysvinit 与 systemd 都行
unit 的 Environment= /etc/systemd/system/*.service 不会 systemd 发行版

十四、locale 与编码 #

14.1 locale 是一组类别 #

locale 不是单个值，是一组类别设置。LANG 给所有类别一个默认值，LC_* 单独覆盖某一类，LC_ALL 覆盖全部。

变量 管什么 影响
LANG 所有类别的默认值 没被单独设置的类别都取它
LC_ALL 强制覆盖全部类别 排查时用，优先级最高
LC_CTYPE 字符分类、大小写转换、多字节编码 中文能不能被正确识别，主要看它
LC_MESSAGES 程序提示信息的语言 报错是中文还是英文
LC_COLLATE 字符串排序规则 sort、ls 的顺序
LC_TIME 日期时间格式 date 的月名、星期名
LC_NUMERIC 小数点与千分位 影响 printf 和部分库的解析
LANGUAGE gettext 消息的优先语言列表 GNU 扩展，只管翻译

优先级：LC_ALL 高于 LC_<类别>，LC_<类别> 高于 LANG。

14.2 查看与设置 #

bash
locale

text
LANG=zh_CN.UTF-8
LC_CTYPE="zh_CN.UTF-8"
LC_ALL=

LC_ALL= 为空表示没设，此时按 LANG 走。LANG=C 或 LANG=POSIX 是 ASCII，中文一律出不来。

bash
locale -a | grep -i zh
localectl status
sudo locale-gen zh_CN.UTF-8
sudo localectl set-locale LANG=zh_CN.UTF-8

locale -a 列出系统已生成的 locale，名字不在这个列表里，设了也不生效。这就是素材里那句「系统本身需支持中文语言包」的意思。

14.3 UTF-8 和 GBK #

项 UTF-8 GBK
编码单位 变长，1 到 4 字节 双字节
一个中文占几字节 3 2
ASCII 兼容 单字节部分与 ASCII 相同 单字节部分与 ASCII 相同
覆盖范围 Unicode 全集 中文与部分东亚字符
自同步 有，从任意位置能找回字符边界 无
常出现的场合 Linux 默认、网页、JSON 中文 Windows 的代码页 936

乱码的本质只有一句：字节没变，解码用的编码和编码时用的编码不是同一个。一条链上有三个环节——写入时编码、存储时保持原样、读取时解码，任意两个不一致就出花。

现象 根因 处理

一片 ???? 目标编码不支持中文，字符被替换 设 LANG，别停在 C locale
方块、黑菱形 字体缺字形，不是编码问题 装中文字体
一段正常一段乱 两种编码写进了同一个文件 统一源文件编码

十五、排查乱码的步骤 #

按顺序走，每一步都能砍掉一批嫌疑。

  1. 固定触发条件。终端启动正常、服务启动乱码，问题在环境；两种都乱，问题在程序或查看端。
  2. 看进程的真实环境：
bash
tr '\0' '\n' < /proc/<pid>/environ | grep -E '^(LANG|LC_)'

空输出就是没设，等于 C locale。这一步是证据，不是猜测。

  1. 手动复现，把环境清空再跑：
bash
env -i /opt/app/bin/app

能复现，就确认是 locale 造成的。

  1. 看字节，别看显示：
bash
file -i app.log
hexdump -C app.log | head

file -i 报 charset=utf-8，说明文件编码没错，错在显示端。中文 UTF-8 的字节多以 E4 到 E9 开头，跟 %PDF 这种一眼能认的前缀一样好用。

  1. 确认 locale 存在：locale -a | grep zh_CN。

  2. 补上变量再验。unit 里加 Environment=，或脚本里 export，重启服务看新日志。旧日志不会因为改了配置而变正常。

  3. 程序侧兜底。Qt 里显式指定 QTextCodec::setCodecForLocale(QTextCodec::codecForName("UTF-8"))；Python 给标准输出定编码，在 unit 里加一条 Environment=PYTHONIOENCODING=utf-8。

  4. 还乱就拆环节。先确认文件本身是不是合法 UTF-8：

bash
iconv -f UTF-8 -t UTF-8 app.log > /dev/null && echo "valid utf-8"

能过就是合法 UTF-8，问题在查看端；报 invalid input 说明原始字节就不是 UTF-8，回头查写入端。

十六、易错点速查 #

现象 原因 处理
三个概念混着说 不在同一层 终端是设备，Shell 是程序，控制台是内核输出通道
chsh 拒绝换 shell 路径不在 /etc/shells 先追加路径，再 chsh -s
> /dev/console 写到了别处 别的 UNIX 控制台只有一个 FreeBSD 上那是第一个虚拟终端
cron 报 command not found PATH 是极简值 crontab 顶部设 PATH，或写绝对路径
cron 里别名、函数不认 不读 .bashrc 环境写进脚本头部
带日期的命令被截断 % 没转义 写成 \%，或者包进脚本
任务跑了但没有产物 cwd 是 $HOME 输入输出全写绝对路径
任务失败却没有任何输出 输出走邮件，MTA 没配 >> log 2>&1
crontab -r 之后表空了 删的是整张表 先 crontab -l > bak
at 提交成功却不执行 atd 没起 systemctl enable --now atd
服务日志中文乱码 env -i 清掉了 LANG unit 的 Environment=，或脚本里 export
locale -a 没有中文项 语言包没生成 locale-gen 或装语言包
中文显示成方块 字体缺字形 装中文字体，别改编码

最后三条主线收在这里：终端是设备、Shell 是程序、控制台是内核的一个输出通道，三者不在同一层，跨层时环境被换掉；计划任务不读你的 ~/.bashrc、PATH 很短、% 要转义，先看日志里有没有 CMD 再谈命令本身；乱码永远是两次编码不一致，先用 /proc/<pid>/environ 和 locale 把程序真实的环境拿出来，再决定改哪一侧。
