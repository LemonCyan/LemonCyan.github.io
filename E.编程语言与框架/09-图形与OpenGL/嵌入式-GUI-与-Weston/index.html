这篇讲两件事：嵌入式设备上跑图形界面有哪些路子，以及 Wayland/Weston 这条路怎么从源码搭起来。

不讲什么：DRM/GBM/EGL 的内核与用户态接口细节、Mali-T860 这类 GPU 的驱动移植、OpenGL 管线与着色器。这三块在同目录另外三篇里，本篇只在边界上点一句，要深入就翻过去。

读法：前三章建立判断标准，四到六章过方案谱系，七到九章讲清 Wayland 的架构与 Weston 的定位，十到十三章是能照着敲的构建与配置，最后两章给选型和排错。手上没板子也能读，有板子边读边敲更快。

一、嵌入式为什么要专门的 GUI #

把桌面那套栈搬到板子上，问题从来不是「能不能跑」，而是「跑起来还剩多少」。

先算硬件账。一块典型的 HMI 板子：Cortex-A7/A53 双核到四核，512MB 到 2GB DDR，7 到 10 寸屏，分辨率 1024×600 到 1920×1080，输入只有电容触摸，没鼠标键盘。桌面发行版起一个 GNOME 会话，常驻内存吃掉 800MB 往上，再加 X Server 和各种守护进程，1GB 的板子开机就被榨干。

再算需求账。工业 HMI、车载中控、医疗面板、门禁屏，界面形态是固定的：一个主界面、几个子页、一排状态栏、一个设置页。它不需要窗口叠放，不需要多任务切换，不需要拖拽改窗口大小。整套窗口管理器的抽象在这里空转。

最后算时间账。开机到界面能用，工业设备常见的要求是 3 到 10 秒。桌面栈从内核起 DRM、起 display manager、起会话、起合成器，一圈走完十几秒很常见。

三笔账算下来，结论是：嵌入式要的不是「小一号的桌面」，而是砍掉用不上的层，把剩下的压成一条直线。

维度 桌面机的假设 嵌入式设备的现实 对 GUI 的要求

「没有 GPU」这件事影响最大。带 GPU 的板子（RK3399 的 Mali-T860、i.MX8 的 GC 系列、AM62 的 AXE）能走 EGL 加 GLES 渲染路径，合成可以交给 GPU。没有 GPU 的板子（AM335x、全志 F1C、各种 Cortex-A7 裸板）只有一条路：CPU 往 framebuffer 里写像素，或者 CPU 往内存里的 buffer 写完再拷给显示控制器。

这条差别直接决定后面所有选择。framebuffer 是内核提供的一块显存映射，mmap 之后就是一个二维数组，你往里面写 RGB 值，屏幕上就变色。它没有任何图形能力，画线、画圆、贴图、抗锯齿、半透明，全部要自己算。所以嵌入式 GUI 框架的价值，一半在控件，一半在「帮你把像素算完再一次性刷上去」。

还有一个现实约束容易被忽略：显示控制器（LCDIF、DC、VOP）多数不支持硬件图层混合，或者只支持有限的几层。你要做「视频上面盖一层半透明 OSD」，就得靠 CPU 合成，来不及就掉帧。图形栈的选择要在这条线上算清楚，而不是先挑界面好不好看。

二、桌面 GUI 与嵌入式 GUI 的差别 #

桌面 Linux 的图形栈是分层堆出来的，每一层解决一类问题。理解这个分层，才能看出嵌入式到底砍了哪几层。

从 X Window System 的逻辑出发，Linux 的 GUI 架构大致划分成六层：

  • X Server：管显示输出、管输入设备（键盘、鼠标、触摸），把事件分发给对应程序；
  • Graphic Library：底层绘图函数库，提供画点、画线、画矩形、画圆、上色这些原语；
  • Toolkits：把按钮、滚动条这类构件抽象出来，Qt、GTK+ 属于这一层；
  • Window Manager：管窗口之间的切换、放大、缩小、装饰；
  • 桌面环境：浏览器、邮件客户端、文件管理器、配置工具一整套程序，KDE 与 GNOME 是两大流派；
  • I18N：字符编码、输入法、文字排版。

一层层看下来，逻辑很自然。屏幕上是几百万个像素点，让人直接去点这些点等于自找麻烦，于是有了绘图库：draw_line(x1,y1,x2,y2) 一调用，线就出来了，画线要点几个点、怎么让显示器认这些点，库替你处理。有了点线面，写窗口程序还是慢，于是把按钮、滚动条这些反复出现的东西抽成 Widgets（Windows 下叫控件），配上一组组织它们的语法，就是 Toolkits。有了 Toolkit，每个程序只能管自己窗口里的事，窗口之间谁在上面、谁被最小化就没人管了，Window Manager 补上这块。光有 WM 还没东西给它管，桌面环境提供一整套应用。最后是 I18N，中文、日文、韩文都是双字节，处理一个字符耗的资源比 ASCII 多，西方主导的项目在取舍时容易把它牺牲掉，所以嵌入式 Linux GUI 的 I18N 程度往往不如 PC 端，只有真有人用才专门调校。

这个分层在桌面上很合理，在嵌入式里却很奢侈。每一层之间都有协议、有进程、有内存拷贝。嵌入式 GUI 系统常见的做法是把几层合并，甚至全部绑进一个进程：图形库、控件、窗口策略、甚至字体渲染，一个可执行文件搞定。牺牲的是弹性和功能，换回来的是几十 MB 的内存和更短的启动时间。这是一笔明确的权衡，不是技术落后。

对比项 桌面 GUI 嵌入式 GUI
分层 X Server、绘图库、Toolkit、WM、DE 各自独立进程 多层合并，甚至单进程单库
进程模型 多客户端并行，跨进程通信 单应用为主，少量守护进程
渲染 交给 X Server 或合成器光栅化 应用自己往 buffer 里画
内存基线 数百 MB 起 几 MB 到几十 MB
输入模型 指针加键盘焦点 触摸、按键、编码器，无焦点概念
裁剪能力 只能整包装或整包不装 按模块裁，编译期去掉用不上的
升级方式 包管理器增量更新 整镜像烧写，OTA 差分包
授权成本 多为自由软件 商业方案常见，要算授权费

还有一条隐性差别：桌面上几乎不用管「谁来合成」，阴影、渐隐动画、vsync 都有合成器和 GPU 兜住。嵌入式里这些要自己决定要不要得起——一道 20ms 的渐隐动画，在 60fps 的屏上只给了 1.2 帧的合成预算，CPU 软合成一帧都撑不住。

三、常见嵌入式 GUI 方案概览 #

方案多，但按渲染底座归类只有四种：直接怼 framebuffer、走 GPU 的 EGL/GLES、走 Wayland 合成器、走 X11。上面跑的框架换个底座就能换个活法，比如 Qt 既能跑 framebuffer 也能跑 Wayland。

这里要先点清一个概念：Wayland 不是 GUI 框架，它是协议。你在 Wayland 上仍然用 Qt 或 GTK+ 画界面，只是把「画好的东西交给谁」从 X Server 换成了 compositor。把 Wayland 当成 Qt 的竞品是常见误解，后面第七、八章会把这件事讲透。

四、Qt 与 QML #

Qt 是一个跨平台的 C++ 图形用户界面库，出自挪威 TrollTech 公司（后来被诺基亚收购，再后来归 Qt Company）。它最早的形态是一组配套工具：

  • Qt 本体：C++ 类库；
  • 基于 Framebuffer 的 Qt Embedded（后来这条线演变成 Qtopia）；
  • Qt Designer：界面快速开发工具；
  • Qt Linguist：国际化翻译工具。

Qt 立住脚的几条理由：

  • 跨平台。支持列表很长：Windows 95/98、Windows NT、Linux、Solaris、SunOS、HP-UX、Digital UNIX（OSF/1、Tru64）、Irix、FreeBSD、BSD/OS、SCO、AIX、OS390、QNX。同一份代码在这些平台编译就能跑，不用改源码，界面风格按平台自动适配。
  • 面向对象。封装机制让模块化程度高，可重用性好，写业务的不用关心底层。
  • signals/slots。用类型安全的信号槽代替回调函数指针，元件之间协同变简单，签名不匹配在编译期就报出来。
  • API 覆盖广。2D/3D 渲染、容器、XML 解析、数据库、Socket 全在库里，不用满世界找第三方库，也不必为了解析一个 XML 引入五个依赖。
  • 文档量大。每个类都配示例，这是 Qt 最实在的资产。

让 Qt 在 Lesstif、GTK+、EZWGL、Xforms、FLTK 这一堆 Widgets 里站住的，是 KDE 这个重量级用户。反过来 KDE 也把 Qt 推成了事实标准。

Qt 在嵌入式上有三代形态，名字容易混，得分开看：

形态 大致年代 渲染底座 说明
Qt/X11 1990 年代起 Xlib 桌面上最早那版，必须配 X Server
Qt/Embedded（Qt/E、Qte） 2000 到 2010 直接对 framebuffer 自己取代 X Server 与 Xlib 的角色
Qt for Embedded Linux 2011 之后 QPA 插件（eglfs、linuxfb、wayland） 现在的说法，API 与桌面同一套

Qt/E 的那几条特色，放到今天看依然成立：

  • 与桌面 Qt 用同一套 API，学一套接口，基于 Qt 或 Qte 开发的程序维护一份代码，就能跑在 Windows、X11、Mac OS X 或者嵌入式 Linux 上；
  • 针对嵌入式专门设计，做出来的程序占的内存和 Flash 都更少；
  • 自带窗口系统，不再需要别的底层库支撑，装完就能在上面开发和运行图形程序；
  • 外观可配置，方便做一套自己的视觉；
  • 完全模块化，用不上的功能模块编译期去掉，省资源；
  • 源码开放，能深入调，也能看实现；
  • 与 Qtopia 整合。

这里有个概念要掰清楚：Qt/E 本质还是库；Qtopia 是拿这个库写出来的一整套应用环境，地位类似 PC 上的 KDE。很多开发板或设备上看到的那套界面，其实就是 Qtopia。Qtopia 在 Android 起来之前用得不少，2009 年之后不再更新。没有特定历史包袱，不要花时间学它。

Qt 5/6 在嵌入式上靠 QPA 插件切后端，一个环境变量就能换：

QT_QPA_PLATFORM 取值 后端 前提
eglfs DRM/KMS 加 EGL 有 GPU 和 EGL 驱动
linuxfb 直接写 /dev/fb0 无 GPU 也能跑
wayland Wayland 客户端 有 compositor 在跑
xcb X11 客户端 X Server 在跑
vnc 无本地显示，走 VNC 调试用 
bash
# 让 Qt 走 Wayland
export QT_QPA_PLATFORM=wayland

# 没有 GPU 的板子直接怼 framebuffer
export QT_QPA_PLATFORM=linuxfb:fb=/dev/fb0

QML 与 Qt Quick 是另一条线：

  • QML 是声明式语言，界面用 QML 描述，逻辑用 JavaScript 或 C++ 写；
  • 渲染走场景图（scene graph），Qt 5 默认 OpenGL ES，Qt 6 换成 RHI，可以落到 Vulkan、Metal、D3D 或软件后端；
  • 属性绑定加内建动画，触摸屏上的滑动、渐变、状态切换写起来省事；Widgets 那套是像素对齐的桌面风格，QML 自由绘制，做嵌入式界面更顺手。

QML 的代价要提前知道。场景图默认假设有 GPU，没有 GPU 的板子得显式开软件渲染：

bash
export QT_QUICK_BACKEND=software

软件后端能跑，帧率就别指望了。全屏 1080p 刷一帧，CPU 软光栅的耗时按毫秒算，动画多了直接掉到十几帧。板子没 GPU 又要 QML，先拿 qmlscene 跑个真实界面测帧率，别等联调时才发现。

授权要算清楚。Qt 5.15 之后开源版是 LGPLv3，动态链接、允许用户替换 Qt 库，闭源产品可以用；静态链接或者要改库不公开，就得买商业授权。设备出厂固件锁死、用户无法替换库的场景，法律上站不住，别抱侥幸。

五、GTK 与 DirectFB #

GTK+（GIMP Tool Kit）是一个图形用户界面库。它基于 LGPL 授权，用它开发开源软件、自由软件，甚至商业的、非自由的软件都行，不用为授权费或版权费掏一分钱。GNOME 就是建在它上面的。

GTK+ 用一系列称为「构件」的对象搭界面，提供了窗口、标签、命令按钮、开关按钮、检查按钮、无线按钮、框架、列表框、组合框、树、列表视图、笔记本、状态条这些构件，组合起来能做很丰富的界面。

本质上它是面向对象的 API。GObject 这套面向对象机制给 GTK+ 绑定了多种开发语言：库完全用 C 写，但靠类和回调函数（指向函数的指针）实现，所以在 Linux 下写 GTK 程序用 C 最顺。配 Glade 这个图形化界面生成器，能快速生成创建界面的 C 源码。Python、Vala、Rust 也都有绑定，选哪个看团队。

GtkFB 是 GTK+ 针对嵌入式推出的方案，思路和 Qt/E 一致：跳过 X，直接跟 framebuffer 打交道。它的好处：

  • 能用 GTK+ 那一大套构件，已有软件迁移成本低；跳过体积巨大的 X，适合 PDA 这类设备；API 与桌面完全一样，桌面 PC 和设备之间移植软件、共享代码很容易；
  • 完全免费、完全公开，基于 LGPL，自己写的代码不用公开，改过的库文件要公开；
  • 不走 X 协议，天然没有 X 协议那些特有的毛病。

它的毛病也同样明确：

  • 只能跑在单处理器系统上。没法拿别的处理器去隔离、保护系统的不同部分，做大型系统吃力；
  • 有些基于 GTK+ 的程序直接调 X，不改代码在 GtkFB 上跑不起来。GNOME 的一些库就直接调 X，基于它的程序要动；
  • X 有大量成熟驱动，硬件加速做得好。GtkFB 也支持硬件加速，但这块进展很小，大屏上明显慢；
  • framebuffer 不支持 X 的一些特性，比如网络透明、DGA。

DirectFB 是 framebuffer 之上的一层轻量图形库。它把一块裸 framebuffer 包装成一个带图层、带 surface、带 alpha 混合、带输入抽象的图形子系统：

  • 能在 /dev/fb0 上开出多个 surface，做窗口叠放；
  • 支持 alpha 混合、YUV 叠加、硬件光标；
  • 把键盘、鼠标、触摸屏、遥控器统一成输入设备接口；
  • 能挂各家的 2D 加速后端，把 fill、blit、blend 交给硬件。

在嵌入式 Linux 的黄金年代，DirectFB 是「要图形但装不起 X」的标准答案，GtkFB 的一个后端就是它，Qt 也出过 DirectFB 的 QPA 插件。项目在 2015 年前后基本停摆，新板子不建议选，维护老设备时才碰它。三者的差别摆平了看：

维度 裸 framebuffer DirectFB X11
抽象层级 一块像素内存 图层、surface、输入设备 窗口、绘图请求、事件
多窗口 自己做 内建 内建
输入处理 自己读 /dev/input 统一接口 X Server 处理
硬件加速 自己写 可选后端 驱动成熟
体积 最小 小 大
现状 稳定 停滞 维护中，逐步让位 Wayland

六、MiniGUI、emWin 与其他 #

Microwindows 是一个老牌的开源嵌入式 GUI，遵循 MPL 协议，目标是把图形视窗环境带进跑 Linux 的小型设备。

作为 X Window System 的替代品，它用 100K 到 600K 的 RAM 和存储空间就能提供与 X 相似的功能。设计者可以往里加各种显示设备、鼠标、触摸屏和键盘。可移植性很好：基本用 C 实现，只有少数关键代码用汇编提速，支持 ARM 芯片；内部的可移植结构建立在一个相对简单的屏幕设备接口上，所以在很多 RTOS 甚至裸机上都能跑。

它提供两套图形编程接口，这是它当年最聪明的地方：

  • Microsoft Windows Win32/WinCE 的图形显示接口（GDI），让大量 Windows 程序员直接上手；
  • Xlib-like 接口，也就是 Nano-X，位于 Linux X 插件集的最底层，让 Unix 程序员用熟悉的习惯写。

MiniGUI 是国内做得比较好的自由软件之一，本质是在 Linux 控制台上跑的多窗口图形系统，能在基于 Linux 的应用平台上提供一个简单可行的 GUI 支持系统。

小是它的特色。机顶盒、实时控制系统、掌上电脑这类场合都能用。因为是自己开发的 GUI 系统，中文支持做得最好：支持 GB2312 与 BIG5 字符集，其他字符集也很容易加进去。

跨操作系统的范围铺得广：普通嵌入式 Linux、uClinux、VxWorks、eCos、uC/OS-II、pSOS、ThreadX、Nucleus、OSE 都在支持列表里，还提供 Win32 平台上的 SDK 开发包，方便开发调试。它很适合 eCos、uC/OS-II、ThreadX 这类没有文件系统的实时嵌入式系统。授权是 GPL 加商业双轨，做闭源产品要买商业授权。

emWin 系是三兄弟，名字最容易搞错：

名称 谁做的 授权 备注
emWin SEGGER（就是做 J-Link 仿真器那家） 商业 老牌，十几年历史，架构与功能成熟
ucGUI SEGGER 为 Micrium（uC/OS 所属公司）定制 商业，要交版权费 只在 Micrium 的体系里出现
STemWin SEGGER 为 ST 定制 ST 芯片上免费 用 ST 的片子就不用掏钱

emWin 的问题在于做炫效果很麻烦，不支持较复杂的控件。它能干活，界面观感停在十年前。

TouchGFX 走的是另一条路。非开源，以界面流畅和 TouchGFX Designer 出名，做出来的效果接近手机 App。它已经被 ST 收购，在 ST 的 MCU、MPU 上可以免费用。

用 TouchGFX 开发 STM32 界面有两条路：

  • 用 TouchGFX Designer，图片和控件拖拽，快速生成能在 KEIL 或 IAR 里打开的项目工程；
  • 用 STM32CubeMX，5.0 版本之后增加了对 TouchGFX 的支持，可以直接在 CubeMX 里配。

它的渲染靠 LTDC 出图、DMA2D（Chrom-ART）做填充和混合。片子上没有 DMA2D，动画帧率会掉得很难看。

TARA 是德国 TARA System 公司的一套嵌入式 GUI 开发工具，出现得比 emWin 和 TouchGFX 都晚，以界面华丽、GUIBuilder 好用著称，官方称支持几乎任意平台。收费。

LVGL 是这几年 MCU 圈里用得最多的一支，MIT 协议，C 写，控件风格现代。它对底层的要求低到只有一个 flush 回调：你把一块像素刷到屏上就行，接 framebuffer、接 SPI 屏、接内存 buffer 都可以。缺点是没有官方免费的可视化设计器，复杂动画还是吃 CPU。

裸机自绘是最原始也最可控的一条路，也该会：

bash
cat /sys/class/graphics/fb0/virtual_size
cat /sys/class/graphics/fb0/bits_per_pixel
cat /sys/class/graphics/fb0/stride
cat frame.rgb565 > /dev/fb0     # RGB565 的原始数据可以直接刷进显存

写代码的话就是 open("/dev/fb0")、ioctl(FBIOGET_VSCREENINFO)、mmap，然后往映射地址里按 line_length 逐行写 RGB。要双缓冲就申请两块显存，切页用 FBIOPAN_DISPLAY，等垂直同步用 FBIO_WAITFORVSYNC。单屏指示类设备，一两百行代码就能跑起来。

最后一层判断：小型嵌入式系统的 GUI 与桌面 Windows、Linux 不同，也与手机平板上的 Android、iOS 不同。这类系统界面往往定制，要显示的内容有限，没有复杂应用；硬件平台是 MCU，没有 GPU、没有 3D 单元，跑不了大型操作系统，桌面和移动端的成熟 GUI 跟它对不上，也装不上去。

所以 MCU 上选 GUI 先问四个问题：

  • 应用场景：主要显示什么，显示得复杂不复杂；
  • 与操作系统的结合：移植难度有多大；
  • 硬件平台：这块芯片有没有现成可用的 GUI 已经适配过；
  • 开源协议：收不收费，产品要不要公开源码。

这四个问题问完，答案往往只剩两个候选，再拿内存占用和帧率一对比就定了。

七、Wayland 协议是什么 #

Wayland 是一个现代化的显示服务器协议，官网在 wayland.freedesktop.org，构建说明在 Wayland Building Guide。它的设计目标是取代用了近三十年的 X 图形系统。

先把最容易搞错的一点说清：Wayland 不是服务器程序，也不是图形库。它是一份协议规范，外加几个实现这份规范的小库：

  • libwayland-client：客户端侧，应用拿它连 compositor、发请求；
  • libwayland-server：服务端侧，compositor 拿它接连接、收请求；
  • wayland-scanner：把 XML 里的协议描述编译成 C 头文件和胶水代码，构建时就要用；
  • libwayland-egl：把 wl_surface 和 EGL 的窗口系统绑定接起来。

协议本身用 XML 写，一个接口就是一段 <interface>，里面列方法（request）、事件（event）和枚举。谁想加功能就加一份 XML，不碰核心协议。这决定了 Wayland 的形态：核心协议很小，能力都长在扩展上。今天做桌面应用，实际只用 xdg-shell 那一套扩展，核心协议只提供 surface 和 buffer 这些原料。

通信走本机 Unix socket。compositor 在 $XDG_RUNTIME_DIR 下建一个 socket，名字由 $WAYLAND_DISPLAY 指定（默认 wayland-0），客户端连上去开始交换消息。消息是二进制的，对象用 32 位 id 标识，参数按签名序列化。想看消息流就设 WAYLAND_DEBUG=1，所有请求和事件都打到 stderr，跟 X11 的 xtrace 是一个用途。

一个客户端和 compositor 的完整握手长这样：

text
客户端 ──connect($XDG_RUNTIME_DIR/$WAYLAND_DISPLAY)──> compositor
      ──wl_registry.bind(wl_compositor / wl_shm / wl_seat / xdg_wm_base)──>
      ──wl_surface.attach(buffer) + commit──────────>
      <──────────── wl_keyboard.key / wl_pointer.motion

核心接口不多，一张表能列完：

接口 作用
wl_display 连接本身，收发消息的总入口
wl_registry 全局对象发现，compositor 有什么能力都从这里播出来
wl_compositor 创建 wl_surface 和 wl_region
wl_surface 一块可以被合成的画布，attach buffer 加 commit 才出现
wl_shm 共享内存池，软件渲染用它当 buffer 来源
wl_seat 一组输入设备，再派生 pointer、keyboard、touch
wl_output、wl_subcompositor、wl_data_device 显示器信息、子表面（视频叠加与字幕层）、剪贴板与拖放

扩展协议里最要紧的几个：

扩展 解决什么
xdg-shell 桌面式窗口：顶层窗口、弹窗、最小化、最大化、移动、缩放
wlr-layer-shell 面板、壁纸、锁屏这种固定层，wlroots 系合成器的事实标准
ivi-shell / ivi-application 车载场景，按 id 给应用分配显示区域
fullscreen-shell 只放全屏客户端，嵌入式单应用场景常用
zwp_linux_dmabuf_v1 客户端直接交 dma-buf fd，GPU 显存零拷贝
xdg-decoration 服务端或客户端画窗口装饰的协商

buffer 是理解 Wayland 的关键。两种来源：

  • wl_shm：客户端在共享内存里开一块池，自己用 CPU 画好像素，attach 上去。没有 GPU 的板子走这条，compositor 读同一块内存合成。
  • zwp_linux_dmabuf_v1：客户端用 EGL/GLES 渲染到 GPU 的 dma-buf 上，只把 fd 传过去，compositor 直接拿纹理合成。有 GPU 的板子走这条，全程不拷贝。

fd 通过 socket 的 SCM_RIGHTS 传，这是 Unix 域套接字的能力，也是为什么 Wayland 只做本机。协议里没有「服务器地址」这种概念，设计上就没打算跨网络。

八、Wayland 与 X11 的架构差别 #

一句话概括：X11 是「客户端画到服务器」，Wayland 是「客户端直接画，合成器只做合成」。

这句话的信息量比看起来大，两边所有差异都由它推导出来。X11 的模型里，客户端不碰像素。它发的是绘图请求：在 (x,y) 画一条从 a 到 b 的线、颜色是多少、线宽多少。X Server 收到请求，自己光栅化成像素，再交给显示硬件。窗口也是 server 侧的资源，server 维护一棵窗口树，知道谁盖住谁、哪块区域需要重绘。输入进 server，server 按焦点和指针位置决定送给哪个客户端。

这套体系 1984 年由 MIT 做出来，X 在字母表里是 W（indows）的下一个字母，寓意下一代 GUI。它拆成三块：X Server 管显示输出与鼠标键盘输入，每个要显示图形的主机都得跑一个；X Client 指需要图形界面的应用，浏览器、终端、播放器都算；两者之间走 X Protocol。你按一下字母 c，server 拿到事件转发给焦点客户端，客户端回一条「在 (x,y) 画一个大小 xx、颜色 xx、字体 xx 的 c」的请求，server 照着画出来。

这套模型的初衷是网络透明。X 协议设计成与硬件无关，客户端和服务端可以在不同机器、不同架构、不同操作系统上（Windows 上跑 Xmanager 当 server，远程连 Linux 上的 X 客户端，就是这么来的）。代价是每一种绘图操作都要定义成协议请求，server 里塞满了图形算法：画线、画弧、填充、字体渲染、图像缩放。

Wayland 的模型里，compositor 不碰像素内容。客户端自己拿到一个 buffer，用 EGL/GLES 或者 CPU 在里面画完，attach 到 wl_surface 上，commit。compositor 收到的已经是一张画好的图，它做的事只有一件：把这些图按 z 序合成到屏幕上，然后 scanout。

text
X11：
  app ──绘图请求(X protocol)──> X Server ──光栅化──> 显存 ──> 屏幕
       <──事件(键盘/鼠标)──────

Wayland：
  app ──自己渲染──> buffer ──attach+commit──> compositor ──合成──> 显存 ──> 屏幕
       <──────────────事件(键盘/触摸)──────────

X Server 当年干的很多活，现在有了更好的地方去：

  • 显示模式设置、page flip、vsync 交给内核 DRM/KMS；
  • 输入设备读取交给 evdev，策略交给 libinput；
  • 光栅化交给 pixman 或 cairo；
  • 字体交给 fontconfig 与 freetype。

X Server 里这些功能变成了重复实现，还得多一次进程间通信。Wayland 干脆把中间层去掉。

维度 X11 Wayland
谁光栅化 X Server 客户端自己
客户端发什么 绘图请求 画好的 buffer
中间层 X Server 一个常驻进程 没有，只有 compositor
输入路径 硬件 → server → 焦点窗口 硬件 → compositor → 焦点 surface
网络透明 有，X 协议跨网络 没有，只走本机 socket
每帧拷贝次数 至少一次（client 到 server） 零次（dma-buf）或一次（shm）
窗口管理 独立 WM 进程，X 协议规定 合成器内部的 shell 插件
客户端要求 会发 X 请求 必须会渲染（EGL 或 shm）
安全隔离 客户端能读全屏、能注入事件 默认拿不到别人的 buffer
成熟度 三十年积累 十年，主流桌面已切换

省资源省在哪，算得出来。X11 下一个窗口动画，客户端每次变化都发请求，server 重新光栅化那块区域，再把结果推到显存。Wayland 下客户端渲染到 GPU buffer，compositor 只做一次纹理合成加 page flip。帧率一样时，Wayland 的 CPU 占用低一截，延迟也低一截，因为少了一个进程和一次同步。

但代价同样明确，这也是很多人踩坑的根源：

  • 客户端必须自己会渲染。纯 Xlib 画图那套写法没法平移到 Wayland，要么上 GTK/Qt 这类已经适配好的工具包，要么自己写 EGL 或 shm 渲染循环。嵌入式上如果只有 framebuffer 没有 GPU，Wayland 客户端就得走 wl_shm 软件渲染，性能不一定比直接怼 framebuffer 好。
  • 没有网络透明。想在开发机上显示板子的界面，得靠 VNC、RDP 或 waypipe 这类额外工具，而 X11 是协议自带。
  • 窗口管理器这个概念没有了。合成器和窗口管理合成一个进程，窗口策略写进 shell 插件。想换一套窗口行为，改的是 compositor 的代码或配置，不是换个 WM。
  • 老程序要兼容层。XWayland 在 compositor 里起一个 X Server，让 X 客户端以为自己在 X 上跑，实际输出到 Wayland surface。能用，但多一层，输入焦点和缩放上偶有怪问题。
  • 协议扩展各自为政。核心协议不定义「窗口」长什么样，xdg-shell 才定义。合成器支持哪套扩展，客户端就得适配哪套，跨合成器移植要试。

还有一条容易被营销话术带偏：Wayland 不等于一定更快。它省的是架构开销，不省渲染成本。GPU 弱、compositor 只能软合成时，Wayland 一样卡。板子上评估性能，永远拿真实界面跑，别看架构图。

九、Weston：Wayland 的参考合成器 #

Weston 是 Wayland 的参考实现。这句话有两个含义，缺一个都会理解错：

第一，它是参考实现。协议该怎么用、扩展该怎么实现、边界情况怎么处理，看 Weston 的代码是标准答案。新协议进 wayland-protocols 之前，几乎都在 Weston 里先跑通。

第二，它本身就是个合成器（compositor），不是窗口管理器。这一点必须讲清，否则配置时会一直找错地方。

合成器干的活是：从各个客户端收 buffer，按 z 序合成，交给显示硬件，同时把输入事件分发给正确的 surface。窗口管理器干的活是：决定窗口怎么摆、怎么装饰、怎么最小化、任务栏放哪。在 X11 里这是两个进程（X Server 加 WM），在 Wayland 里没有独立的 WM 进程，窗口策略塞进 compositor 里的一个 shell 插件。

归属 职责 在 X11 里的对应物
compositor 核心 收 buffer、合成、scanout、输入分发 X Server
渲染后端 决定用 GL 还是 pixman 画 X Server 的绘图引擎
backend 决定输出到 DRM、X11 窗口还是内存 X Server 的 DDX 驱动
shell 插件 决定窗口怎么摆、有没有面板 窗口管理器

Weston 的代码结构就是按这张表分层的：

  • libweston：合成器的可复用核心，别的合成器项目可以直接链接它；
  • compositor/：主程序，解析参数、加载 backend 和 shell；
  • libweston/backends/：输出后端；
  • shell 插件：窗口策略；
  • clients/：一堆测试与示例程序，就是第十章之后要跑的那些。

后端决定画面往哪去，这是嵌入式上最先要选的东西：

backend 输出到哪 用在什么场合
drm-backend.so DRM/KMS，直接接管显示控制器 板子上的正式运行方式
headless-backend.so 没有真实输出，只渲染到内存 CI 测试、离屏渲染
fbdev-backend.so /dev/fb0 极老的内核或没有 KMS 的板子
x11-backend.so、wayland-backend.so 一个 X11 窗口，或另一个 compositor 的 surface 桌面上嵌套调试、套娃
rdp-backend.so 远程桌面协议 远程看板子界面

shell 插件决定窗口策略：desktop-shell 是类桌面（面板、背景、窗口可拖动缩放），fullscreen-shell 让每个客户端占满一个输出，ivi-shell 按 ivi id 分配区域、没有窗口概念（车载），kiosk-shell 单窗口全屏、比 fullscreen 更适合产品。

渲染方式两种：gl-renderer 走 EGL/GLES，有 GPU 时用它；pixman-renderer 走 CPU，没有 GPU 或者 GPU 驱动不通时用它。跑 weston --help 或者看启动日志里那行 Using the ... renderer，就知道当前用的是哪个。

对嵌入式来说，Weston 的价值在三件事：代码规模可控（能裁到几百 KB 级别）、backend 抽象干净（同一份应用逻辑在 DRM、X11、headless 之间切换不用改代码）、以及它是协议的标准答案（遇到怪问题，上游代码里能找到解释）。它不是为了做桌面发行版设计的，桌面用户嫌它简陋，嵌入式嫌它功能多的场景反而少。

十、构建 Wayland #

先装工具。这一组在 Debian/Ubuntu 上直接能跑：

bash
sudo apt install python3-pip git ninja-build cmake
pip3 install --user meson
sudo apt install libffi-dev libxml2-dev graphviz doxygen xsltproc xmlto

每个包干什么：

包 作用
python3-pip、meson meson 是 Python 写的构建系统前端，读 meson.build 生成 ninja 文件
git 拉源码
ninja-build、cmake 真正执行编译的构建器，比 make 快得多；cmake 是少数依赖的门槛
libffi-dev、libxml2-dev libwayland 的事件分发与协议 XML 处理
graphviz、doxygen、xsltproc、xmlto 生成 API 文档，只在建文档时用，不装 meson 配不过

Ninja 也从源码走一遍。系统包版本够新可以直接 apt install ninja-build，源码编最新版没副作用：

bash
git clone https://github.com/ninja-build/ninja.git
cd ninja
./configure.py --bootstrap
cp ./ninja /usr/bin/

克隆下来，用自带的 configure.py 做一次 self-bootstrap，编出来的单文件 ninja 拷进系统路径。ninja --version 能出版本号就算过。

装哪里，先定。装到自己的目录，不动系统库，出问题好回退：

bash
export WLD=$HOME/install
export LD_LIBRARY_PATH=$WLD/lib
export PKG_CONFIG_PATH=$WLD/lib/pkgconfig/:$WLD/share/pkgconfig/
export PATH=$WLD/bin:$PATH

四行各有各的用处。WLD 定安装前缀；LD_LIBRARY_PATH 让运行时找得到刚装进去的 .so；PKG_CONFIG_PATH 让下一个包的 meson 找得到上一个包装出来的 .pc 文件；PATH 让 wayland-scanner 这类构建期工具能被调用。四个变量必须成组 export，缺哪个的症状都很隐蔽。这几行写进 ~/.bashrc，或者单独存一个 env.sh 每次 source，新开终端忘了设，ninja 阶段就抱怨找不到库。

想装进 /usr，把 WLD 直接改掉，后面所有 meson 命令换成这一组：

bash
export WLD=/usr
# 之后所有 meson 构建命令改成
meson build/ --prefix=$WLD --libdir=/usr/lib --sysconfdir=/etc
ninja -C build/
sudo ninja -C build/ install

多出来的两个参数有原因。--libdir 显式指到 /usr/lib，因为 64 位 Debian 系默认往 /usr/lib/x86_64-linux-gnu 装，别人给你的 .pc 文件对不上；--sysconfdir 指到 /etc，配置才会落到 /etc/xdg 而不是 /usr/etc。install 那步要 sudo，装到 $HOME/install 时不要加，否则文件归 root，后面编译时读得到改不了。

装法 优点 代价 适合
$HOME/install 不动系统、免 sudo、好回退 每个 shell 都得设环境变量 开发调试、试版本
/usr 免环境变量、与系统包一致 污染系统、易与 apt 版本冲突 出产品镜像、交叉编译 sysroot

构建 Wayland 本体：

bash
git clone https://gitlab.freedesktop.org/wayland/wayland.git
cd wayland
meson build/ --prefix=$WLD
ninja -C build/ install

三步：拉源码、meson 配 build 目录、ninja 装。装到 $HOME/install 不加 sudo。

接着是协议库：

bash
git clone https://gitlab.freedesktop.org/wayland/wayland-protocols.git
cd wayland-protocols
meson build/ --prefix=$WLD
ninja -C build/ install

命令一模一样，内容不同：这个仓库没有 C 代码，全是 XML 协议描述。它装的是 stable/、staging/、unstable/ 下的协议文件，供客户端和 compositor 用 wayland-scanner 生成代码。少装它的症状很典型，编译任何用 xdg-shell 的东西都报 Package 'wayland-protocols' required but not found。

验收：

bash
pkg-config --modversion wayland-client wayland-server
wayland-scanner --version
pkg-config --variable=pkgdatadir wayland-protocols

第二条要出版本号，第三条要指向 $WLD/share/wayland-protocols。这两条对不上，后面 Weston 一定编不过，别往下走。

板子上跑就得交叉编译，meson 用 cross file 描述目标环境：

ini
[binaries]
c = 'aarch64-linux-gnu-gcc'
cpp = 'aarch64-linux-gnu-g++'
ar = 'aarch64-linux-gnu-ar'
strip = 'aarch64-linux-gnu-strip'
pkgconfig = 'pkg-config'

[host_machine]
system = 'linux'
cpu_family = 'aarch64'
cpu = 'cortex-a53'
endian = 'little'

bash
export PKG_CONFIG_SYSROOT_DIR=/opt/sysroot
export PKG_CONFIG_LIBDIR=/opt/sysroot/usr/lib/pkgconfig:/opt/sysroot/usr/share/pkgconfig
meson build/ --cross-file=aarch64-cross.ini --prefix=/usr
ninja -C build/

两个 pkg-config 变量要一起设。PKG_CONFIG_LIBDIR 覆盖默认搜索路径，PKG_CONFIG_SYSROOT_DIR 把 .pc 里的 /usr 前缀改写成 sysroot 下的路径。只设一个，编出来的东西会因为链到宿主机的库而出现各种怪错。

wayland-scanner 是构建期要跑在宿主机上的程序，不能是目标板的可执行文件。交叉编译卡在这一步，先给宿主机装一份 wayland（apt install libwayland-dev 或者自己编一份），让 meson 找到宿主机那个。

十一、构建 Weston #

Wayland 装完才能编 Weston，因为它依赖 libwayland 与 wayland-protocols。

补依赖：

bash
sudo apt install libdrm-dev libgbm-dev libinput-dev libxkbcommon-dev \
  libpixman-1-dev libcairo2-dev libpango1.0-dev libjpeg-dev libwebp-dev \
  libudev-dev libevdev-dev libmtdev-dev libseat-dev \
  libgles2-mesa-dev libxcursor-dev libxrandr-dev libxi-dev libxkbcommon-x11-dev
依赖 谁在用
libwayland-dev、wayland-protocols 协议本体与扫描器
libdrm-dev、libgbm-dev DRM backend，EGL 分配 buffer
libinput-dev、libevdev-dev、libmtdev-dev、libudev-dev 输入设备枚举与事件
libxkbcommon-dev、libxcursor-dev、libxrandr-dev、libxi-dev、libxkbcommon-x11-dev 键盘映射，以及 X11 backend 与 XWayland
libpixman-1-dev、libgles2-mesa-dev 软件渲染器与 GL renderer
libcairo2-dev、libpango1.0-dev、libjpeg-dev、libwebp-dev 客户端绘制与 weston-image 读图
libseat-dev 没有 logind 时接管 seat 与会话

配 meson 时按需开关，嵌入式上常见的一套：

bash
cd weston
meson build/ --prefix=$WLD \
  -Dbackend-drm=true \
  -Dbackend-headless=true \
  -Dbackend-x11=true \
  -Dbackend-fbdev=false \
  -Dxwayland=false \
  -Ddemo-clients=true \
  -Dsimple-clients=all \
  -Dscreenshare=false \
  -Dsystemd=false \
  -Dtests=false

新版 Weston 把一堆 backend-* 合并成了列表选项，写法是 -Dbackends=drm,headless,x11。选项名以你手上那份源码为准，别照抄旧教程：

bash
cd weston
meson configure build/
grep -E "option\(" meson_options.txt

第一条列出这个版本认的所有选项和当前值，第二条看源码里定义了哪些。花十分钟省掉一串 unknown option。

选项 作用 嵌入式建议
-Dbackend-drm 直接接管 DRM/KMS 开，产品运行方式
-Dbackend-headless 无输出，只渲染到内存 开，方便 CI 与截图
-Dbackend-x11 输出到一个 X 窗口 开发机开，发布可关
-Dbackend-fbdev 老式 framebuffer 内核没有 KMS 才开
-Dxwayland 兼容 X 客户端 要跑老 X 程序才开，吃内存
-Ddemo-clients、-Dsimple-clients 编示例客户端 开发开，产品关
-Dtests、-Dscreenshare、-Dsystemd 测试、共享、会话集成 板子上按需，不用就关

编和装：

bash
ninja -C build/
sudo ninja -C build/ install
sudo ldconfig

装到 $HOME/install 时不用 sudo，也不用 ldconfig（LD_LIBRARY_PATH 已经覆盖）。装到 /usr 之后跑一次 ldconfig，否则运行时还在用系统里那份旧 libweston。

交叉编译加 --cross-file，--prefix 指到板子根或 sysroot，其余不用改。验收：

bash
weston --version
weston --help
ls $WLD/lib/weston/

lib/weston/ 下应该有 drm-backend.so、gl-renderer.so、desktop-shell.so 这些。缺哪个就是对应选项没开。

十二、运行 Weston #

第一次跑，八成的失败栽在两个变量上。XDG_RUNTIME_DIR 必须指向一个存在、属于当前用户、权限 0700 的目录：

bash
export XDG_RUNTIME_DIR=/tmp/.xdg
mkdir -p $XDG_RUNTIME_DIR && chmod 0700 $XDG_RUNTIME_DIR

不设它报 XDG_RUNTIME_DIR is not set；设了但权限是 0755，报的是目录不属于当前用户或者 permissions 0755 instead of 0700。后一种更常见，自己写启动脚本时 mkdir 完忘了 chmod。

装好之后直接敲：

bash
weston

会起一个默认的 desktop-shell 桌面，黑底加一个面板，终端被占住。在这个会话里敲 weston-terminal 就能开终端窗口。

产品化的启动带全套参数：

bash
weston -c /etc/xdg/weston/weston.ini --tty=2 --idle-time=0 --log=/var/log/weston.log &
参数 作用
-c /path/weston.ini 指定配置文件，绕过搜索路径
--tty=2 在 tty2 上跑，避开占着 tty1 的 getty 或 X
--idle-time=0 永不进入 idle，屏幕不黑
--log=/var/log/weston.log 日志落文件，出问题能查
--backend=drm 指定后端，新版写 drm，老版写 drm-backend.so
--width、--height、--shell、--no-config headless 虚拟分辨率、shell 插件、完全忽略 weston.ini

后端切换：

bash
# 直接接管板子的显示控制器
weston --backend=drm-backend.so --tty=2

# 在桌面上嵌一个窗口调试，或者纯离屏渲染
weston --backend=x11-backend.so --width=1280 --height=720
weston --backend=headless-backend.so --width=1024 --height=600

DRM 后端要能打开 /dev/dri/card0 并成为 DRM master，两条路拿权限：有 systemd 就通过 libseat 向 logind 要 seat，用户必须在同一个会话里，SSH 远程直接跑会失败；没有 systemd 的 rootfs 用 seatd，或者把用户加进 video 组后从 tty 启动。板子上最常见的失败是 X 还在跑，X 占着 DRM master，Weston 报 failed to become DRM master，切 tty 或者先停 X。

Weston 自带一整套客户端，跑起来能验证各条渲染路径通不通。这些程序必须在 Weston 会话内部跑，也就是 WAYLAND_DISPLAY 指向 Weston 的 socket：

bash
weston-terminal            # 终端模拟器
weston-flower              # 画一朵花，测框架协议
weston-gears               # 类 GLX Gears，测图形性能
weston-smoke               # 测共享内存（wl_shm）缓冲区
weston-image a.png         # 加载并显示命令行传入的图像
weston-view a.pdf          # 对 PDF 做类似的事
weston-resizor             # 演示平滑调整窗口大小，上下键改尺寸
weston-eventdemo           # 把 libtoytoolkit 的事件打到控制台
程序 测什么 跑不起来说明
weston-terminal 输入设备与软键盘 输入路径断
weston-gears GL renderer 与 EGL GPU 驱动或 gl-renderer.so 有问题
weston-smoke wl_shm 共享内存 软件渲染路径断
weston-flower 框架协议与 surface 合成 compositor 没起来或 shell 没加载
weston-image 图像解码与 buffer 上屏 jpeg、webp 库没编进去

剩下三个是配角：weston-view 报错查 cairo 与 poppler，weston-resizor 异常查合成器的 resize 路径，weston-eventdemo 没输出查 libtoytoolkit 的事件分发，它的 --help 会打出可用参数。

开机自启，Buildroot 或 sysvinit 的 rootfs 把脚本放 /etc/init.d/：

bash
#!/bin/sh
#
# Start weston
#

case "$1" in
  start)
        printf "Starting weston"
        source /etc/profile.d/env.sh
        weston -c /etc/xdg/weston/weston.ini --tty=2 --idle-time=0 --log=/var/log/weston.log &
        ;;
  stop)
        killall weston
        printf "stop finished"
        ;;
  *)
        echo "Usage: $0 {start|stop}"
        exit 1
        ;;
esac
exit 0

存成 /etc/init.d/S31weston，加执行权限，S31 这个序号决定启动顺序。关键是 source /etc/profile.d/env.sh 那一行：init 脚本的环境是干净的，不 source 就拿不到 XDG_RUNTIME_DIR 和 QT_QPA_PLATFORM，Weston 会以几乎无输出的方式失败。

十三、Weston 的配置 #

Weston 的配置有两个来源：命令行参数和配置文件 weston.ini。命令行优先，weston.ini 兜底。

weston.ini 的搜索顺序是这样，先找到的先用：

  • $XDG_CONFIG_HOME/weston.ini（设置了 $XDG_CONFIG_HOME 时）；
  • $HOME/.config/weston.ini（设置了 $HOME 时）；
  • $XDG_CONFIG_DIRS 里每个目录下的 weston/weston.ini（设置了 $XDG_CONFIG_DIRS 时）；
  • /etc/xdg/weston/weston.ini（上面都没设时的默认位置）。

板子上直接用 /etc/xdg/weston/weston.ini，配合 -c 显式指定更稳，因为 init 脚本里的 $HOME 往往是 /root，容易命中第二条把系统配置盖掉。

weston.ini 由若干段落组成，段落顺序无关，各管一摊：

段落 常用键 管什么
[core] modules、xwayland、require-input、idle-time、repaint-window 加载哪些合成器模块，以及全局开关
[libinput] enable-tap、tap-to-click、natural-scroll、calibration 输入设备行为
[shell] panel-position、background-image、close-animation、startup-animation、locking 桌面外观与交互
[launcher] path、icon、watch 往面板上放启动器
[output] name、mode、transform、scale、position、virtualIndex 输出设置
[input-method] path 屏幕键盘输入法的可执行文件路径
[keyboard] keymap_rules、keymap_model、keymap_layout、keymap_option、repeat-rate、repeat-delay 键盘布局与重复速率
[terminal] font、font-size、term、color weston-terminal 的字体与配色
[xwayland] allow-untested XWayland 的放行开关
[screen-share] command 屏幕共享用哪条命令

键盘那组的取值跟 X Keyboard 配置同源，规则名、模型名、布局名都对得上 xkeyboard-config 的那套命名，写 keymap_layout=us 或者 keymap_layout=cn 都行。

一块 RK3399 加 Buildroot 的板子，weston.ini 精简到两段就够：

ini
[core]
# Boards could have not any input device, and only use
# removable input device like usb(keyboard, mouse).
#require-input=false

[shell]
panel-position=none

require-input=false 那行的意思是：没有输入设备也允许启动。有些板子只靠 USB 热插拔键鼠，开机那一刻一个输入设备都没有，Weston 会因为「找不到输入」直接退出。默认值是 true，板子上经常要放开。

配套的环境变量单独放一个文件，/etc/profile.d/env.sh：

bash
#!/bin/sh

export LC_ALL='zh_CN.utf8'
export QT_QPA_PLATFORM=wayland
#export WESTON_DRM_MIRROR=1
export WESTON_DRM_KEEP_RATIO=1
export QT_GSTREAMER_WINDOW_VIDEOSINK=waylandsink
mkdir -p /tmp/.xdg &&  chmod 0700 /tmp/.xdg
export XDG_RUNTIME_DIR=/tmp/.xdg
export PATH=$PATH:/usr/bin/cmd
export QT_QPA_GENERIC_PLUGINS=evdevkeyboard

逐行看，每一行都对应一个具体的坑：

  • LC_ALL='zh_CN.utf8'：不设的话中文界面里全是方块或者问号；
  • QT_QPA_PLATFORM=wayland：不设的话 Qt 程序默认去连 X，报 xcb 插件找不到；
  • WESTON_DRM_MIRROR=1 被注释掉了：镜像模式，单屏设备用不上，多屏同显时才打开；
  • WESTON_DRM_KEEP_RATIO=1：缩放时保持宽高比，不做拉伸变形；
  • QT_GSTREAMER_WINDOW_VIDEOSINK=waylandsink：让 QtMultimedia 把视频帧直接送进 Wayland surface，而不是绕一圈 CPU；
  • mkdir -p /tmp/.xdg && chmod 0700：/tmp 是 tmpfs，每次重启都清空，所以每次启动都要重建，权限必须是 0700；
  • PATH=$PATH:/usr/bin/cmd：把自定义命令目录加进去，按自己产品改；
  • QT_QPA_GENERIC_PLUGINS=evdevkeyboard：没有 libinput 集成时，让 Qt 直接读 evdev 键盘。

屏幕方向靠 [output] 段落扭，不用改代码。比如 MIPI 屏装反了，转 90 度：

ini
[output]
name=DSI-1
transform=90

transform 收 normal、90、180、270，以及 flipped、flipped-90、flipped-180、flipped-270 这一组翻转值。改完用同一套参数重启：

bash
weston -c /etc/xdg/weston/weston.ini --tty=2 --idle-time=0 --log=/var/log/weston.log &

输出名不知道叫什么，从日志里捞：

bash
cat /var/log/weston.log | grep Output

text
[06:35:51.270] Output repaint window is 15 ms maximum.
[06:35:51.510] Output DSI-1, (connector 91, crtc 83)

DSI-1 就是要填进 name 的值。拿不到日志时，直接看内核认了哪些 DRM 设备：

bash
ls /sys/class/drm/

text
card0/  card0-DPI-1/  card0-HDMI-A-1/  card1/  controlD64/  renderD128/  renderD129/  version

card0- 后面那段就是连接器名，HDMI-A-1、DSI-1、DPI-1 都在这里出现。一个输出一个目录。

双屏要指定谁在哪个虚拟位置：

ini
[output]
name=HDMI-A-1
virtualIndex=0

[output]
name=DSI-1
virtualIndex=1

virtualIndex 决定叠放顺序与排布，同一个 index 写两次会让后一个覆盖前一个，屏幕上只剩一路。

配置改完别急着重启整机，先拿 --no-config 对比一次，排除掉「配置文件写错」这个因素，再看是不是程序本身的问题。手册页在 weston.ini(5) 与 weston-drm(7)，另一个可查的地方是 manpages.org 的 weston.ini。版本对不上的时候，以源码里 man/weston.ini.5 为准，那份永远跟你的二进制一致。

十四、方案怎么选 #

选型不靠喜好，靠三句话就能框住大部分场景：资源紧到只剩几百 KB 内存，选 DirectFB 或裸 framebuffer；要一整套现成控件、要跨平台、要长期维护，选 Qt；要现代协议、要低延迟、要多应用共存，选 Wayland。

场景 首选 次选 判断依据
无 OS 或 RTOS 的 MCU 单色小屏 emWin、LVGL 裸机自绘 内存与授权
MCU 带 LTDC 的彩色屏，要动画 TouchGFX LVGL 加 DMA2D Designer 省人力
Linux 无 GPU，单应用全屏 裸 framebuffer 自绘 Qt Widgets 加 linuxfb 省掉整套合成开销
Linux 无 GPU，要成熟控件 Qt Widgets 加 linuxfb GTK+ 加 GtkFB 控件数量与文档
Linux 有 GPU，多应用多窗口 Weston 加 Qt X11 协议新、省一次拷贝
车载多区域显示 Weston 加 ivi-shell 单进程多视图 协议自带区域管理
要跑一堆老 X 程序 X11 直接跑 Weston 加 XWayland 少一层转换
要远程看板子界面 X11 Weston 加 rdp-backend 协议自带网络透明
界面团队只会网页技术 Qt for WebAssembly 或 Flutter 自研 Web UI 加 compositor 人比技术重要
产品要卖五年以上 Qt 商业授权、GTK+、LVGL 停更方案慎选 上游活跃度

框架和后端不是绑死的，同一套界面代码换个后端就换了渲染路径。这张矩阵决定了你能不能在开发机上写完、再原样搬到板子上：

框架 裸 framebuffer EGL/DRM Wayland X11
Qt Widgets linuxfb eglfs wayland xcb
Qt Quick 软件后端，帧率低 eglfs wayland xcb
GTK+ GtkFB 弱 原生 原生
LVGL fbdev 或 DRM 有限 第三方 无

Qt 在四个后端之间切换的代价只是一行环境变量，这是它能在嵌入式站住的现实原因：开发机 xcb、板子 wayland、退路 linuxfb，同一份代码。

选完之后做一个动作：拿真实的界面资源，在目标板上跑一次冷启动，掐表算秒数，再看 top 里的常驻内存。表上的数字都是别人板子上的，你这块板子的数字只有跑出来才算。

十五、易错点速查 #

下面这些是嵌入式图形栈里反复出现的坑，按「现象、原因、处理」列出来，黑屏时从上往下过一遍。

现象 原因 处理
Weston 启动即退，日志只有 XDG_RUNTIME_DIR is not set 没设运行时目录 export XDG_RUNTIME_DIR=/tmp/.xdg
报 permissions 0755 instead of 0700 目录权限不对 chmod 0700 $XDG_RUNTIME_DIR
报 failed to become DRM master X 或其他程序占着 DRM 换 tty，先停 X
报 failed to open /dev/dri/card0: Permission denied 用户不在 video 组，或没有 seat usermod -aG video user，或起 seatd
Weston 起来了但屏幕全黑 renderer 或 shell 没加载 日志里找 Using the ... renderer，检查 --shell
客户端报 failed to create display WAYLAND_DISPLAY 不对 ls $XDG_RUNTIME_DIR 看 socket 名
Qt 程序报 xcb 插件错误 QT_QPA_PLATFORM 没设 export QT_QPA_PLATFORM=wayland
Qt 报 could not find or load the Qt platform plugin wayland Qt 没编 wayland 插件 装 qtwayland 或重编 Qt
weston-gears 起不来，其他程序正常 GL renderer 或 EGL 有问题 换 pixman 渲染器验证，再查 GPU 驱动
meson 报 Dependency wayland-client found: NO PKG_CONFIG_PATH 没设 重新 source env.sh
meson 报 unknown option 选项名随版本变 grep -E "option\(" meson_options.txt
ninja: command not found 只装了 meson apt install ninja-build
构建时报 wayland-scanner: command not found PATH 少了 $WLD/bin 补 export
交叉编译产出的还是 x86 二进制 cross file 没生效 file build/xxx 确认架构
输出转了 90 度，触摸坐标错位 transform 只转画面 配 libinput 校准矩阵，或升级到按输出自动变换的版本
面板盖住了应用，全屏需求做不到 用了 desktop-shell 换 kiosk-shell，或 panel-position=none
中文显示成方块 缺字体或 locale 不对 装中文字体，设 LC_ALL
画面偶发撕裂 重绘窗口与垂直同步没对齐 检查 repaint-window，确认走了 KMS page flip
视频放不出来 缺 waylandsink 装 gstreamer 插件，设 QT_GSTREAMER_WINDOW_VIDEOSINK
重启后一切配置失效 /tmp 是 tmpfs 启动脚本里每次都 mkdir 加 chmod
