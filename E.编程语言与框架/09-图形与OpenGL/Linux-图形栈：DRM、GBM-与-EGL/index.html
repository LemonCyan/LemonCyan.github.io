本篇讲 Linux 上一个像素从应用到屏幕要经过哪几层：内核里的 DRM 管显示控制和显存，用户态的 GBM 管缓冲区分配，跨平台的 EGL 把应用和厂商驱动接起来。再往下是两个命令行工具 modetest 和 xrandr，用它们把上面这些层看穿、调通。

讲什么：DRM 的 KMS 与 GEM 两套机制、CRTC/encoder/connector/plane 四个对象的选路关系、/dev/dri/card0 与 renderD128 的分工、GBM 的 buffer 分配、EGL 的 display/context/surface 生命周期、Wayland 与 X11 两条路径的差别，以及 modetest、xrandr、drm_info 这些工具怎么用。

不讲什么：GPU 寄存器级编程、Mesa 内部编译器（NIR/ACO）的实现、具体 GPU 的性能数字。这些不在本篇射程内。

跨篇指路：具体 GPU 的驱动栈看《Mali-T860 GPU 驱动：Panfrost 与 mesa》；Weston 作为 compositor 怎么跑起来看《嵌入式 GUI 与 Weston》；GLU、GLFW、GLUT 这些辅助库和着色器本身看《OpenGL 编程：从 GLUT 到 OpenGL SC》。

一、一帧图像要经过哪几层 #

先摆结论：四层，三次接力。应用写渲染循环，EGL 把这次循环接到某个具体的图形 API 实现上，GBM 负责掏出一块能被 GPU 写、也能被显示控制器读的内存，DRM 负责把这块内存挂到某块屏上，让它在下一个垂直消隐期变成光。

把这三家的分工压成一句话记：DRM 管显示与显存，GBM 分配 buffer，EGL 把应用和驱动接起来。它们是接力关系，不是替代关系——少了任何一环，链路就断在中间，前面画的全都留在内存里出不去。

层 在哪 典型组件 职责 断掉时的现象
应用 用户态进程 你的渲染循环 决定画什么 画面内容不对，但流程在跑
EGL 用户态库 libEGL.so、Mesa、厂商 blob 选择配置、创建上下文和表面、交换缓冲 eglInitialize 失败，或拿到软件渲染
GBM 用户态库 libgbm.so 分配能被 GPU 和显示端共用的 buffer gbm_bo_create 返回 NULL
DRM 内核子系统 drivers/gpu/drm/ KMS 控制显示、GEM 管显存、提交渲染命令 屏幕黑、/dev/dri 打不开、modetest 报错
硬件 硅片 GPU + 显示控制器 + PHY 算像素、扫出行场信号 时序不对、花屏、无信号

画成纵向的栈就是：应用写渲染循环 → EGL 提供 display/config/context/surface → GBM 提供 gbm_device/gbm_surface/gbm_bo → DRM 内核侧做 KMS 显示、GEM 显存和命令提交 → 硬件算像素、扫出行场信号。上层不知道下层用的什么硬件，下层不知道上层画的是什么，各层之间只靠约定好的对象和句柄交接。

一次 eglSwapBuffers 落地，链路是这样走的：

  1. 应用调 glDrawElements 之类，命令进了 GPU 的命令队列。
  2. 命令写的是 GBM 给出来的那块 buffer，buffer 本身是 DRM 分配的一段显存，被映射进进程地址空间。
  3. eglSwapBuffers 到 EGL。EGL 问平台层：下一块可用的 buffer 在哪。
  4. 平台层是 GBM。gbm_surface_lock_front_buffer 把刚渲染完的那块交出来，封成一个 gbm_bo。
  5. compositor 或者显示端把这个 gbm_bo 的 handle 转成 DRM 的 framebuffer ID（drmModeAddFB2）。
  6. 一次 atomic commit：把这个 framebuffer 挂到某个 CRTC 的某个 plane 上。
  7. 内核在下一个垂直消隐期把 plane 的内容合成为扫描输出，屏幕亮。

七步里，第 2 步是 GBM 的地盘，第 5、6 步是 DRM 的地盘，第 3、4 步的交接由 EGL 和 GBM 一起完成。谁出问题，症状落在哪一层，看表就知道该往哪儿查——这是本篇最实用的一张图。

1.1 三条边界 #

三条边界容易混：内存归谁——GBM 分配、DRM 记账；显示归谁——分辨率、刷新率、plane 合成都是内核说了算；API 归谁——EGL 决定用哪个实现，eglQueryString(EGL_VENDOR) 给的就是答案。有一点要提前说破：EGL 不画像素，它只安排「在哪儿画、画到哪块内存、用哪套状态」，真正执行绘制调用的是背后绑定的那个 GL 实现。

1.2 为什么嵌入式上要关心这些 #

桌面环境里这三层被发行版和 X server 藏得很好，你写个 glxgears 就出画面。嵌入式不是这样：没有 X server，没有现成的 compositor，板子上电之后 /dev/dri/card0 是一个裸设备，谁去设置模式、谁去分配 buffer、谁去建上下文，全得自己来。所以在这类板子上，图形栈不是背景知识，是启动流程的一部分。

二、DRM：内核的显示与渲染管理器 #

DRM（Direct Rendering Manager）是 Linux 内核中的一个子系统，用于管理图形硬件的驱动程序。它提供了一种通用的接口，允许用户空间程序直接与硬件交互，通过设备文件 /dev/dri/cardX 访问。DRM 提供了诸如模式设置、显示控制、渲染加速等功能。

在 DRM 出现之前，用户态程序想用 GPU 得直接 mmap 显存、自己管 DMA、自己跟 X server 抢设备。DRM 把这些收进内核，做成一层统一抽象：设备是文件，资源是对象，操作是 ioctl。

2.1 DRM 管的三类事 #

类别 具体内容 用户态入口
模式设置 分辨率、刷新率、像素格式、扫描方向、DPMS drmModeSetCrtc、atomic commit
显存管理 buffer 的创建、映射、共享、释放 GEM ioctl、dumb buffer ioctl
渲染调度与同步 命令提交、GPU 上下文、围栏与时间线 驱动私有 ioctl、drm_syncobj

三类事的边界感很强：前两类是所有驱动共有的公共接口，第三类是驱动私有的。这也解释了一个现象——写跨平台的显示代码很容易，写跨平台的渲染提交代码几乎做不到，因为提交路径每家 GPU 都不一样，只有 Mesa 这种体量的项目才会去逐个适配。

2.2 两代 ioctl：legacy 与 atomic #

DRM 的显示接口有两代。老接口一次改一个东西：drmModeSetCrtc 设模式，drmModeCursor 移光标，drmModePageFlip 翻页。改三个东西要发三次 ioctl，中间那一瞬间屏幕上的状态是拼出来的，撕裂和闪烁就从这儿来。

新接口叫 atomic，一次 ioctl 把整帧要变的属性全带上，内核先检查可行性，全部通过才一起生效：

c
drmModeAtomicReq *req = drmModeAtomicAlloc();

drmModeAtomicAddProperty(req, plane_id, prop_fb_id, fb_id);
drmModeAtomicAddProperty(req, plane_id, prop_crtc_id, crtc_id);
drmModeAtomicAddProperty(req, plane_id, prop_crtc_w, crtc_w);
drmModeAtomicAddProperty(req, conn_id, prop_crtc_id, crtc_id);

/* 最后两个参数：DRM_MODE_ATOMIC_NONBLOCK 与 allow_modeset */
drmModeAtomicCommit(fd, req, DRM_MODE_ATOMIC_ALLOW_MODESET, NULL);
drmModeAtomicFree(req);

两个 flag 值得记住。带 DRM_MODE_ATOMIC_ALLOW_MODESET 表示这次提交会改时序，内核要重新配置 PHY，耗时在毫秒级；不带它就只能改动 plane 的位置和内容，走的是快速的翻页路径。带 DRM_MODE_ATOMIC_TEST_ONLY 表示只检查不生效，用来试探「这个组合能不能配出来」——比真去配一遍再回滚安全得多。

2.3 打开设备的正确姿势 #

modeset_open 这类辅助函数干的事就一件：打开作为参数给出的 DRM 设备节点。成功时新的 fd 存进输出参数，失败返回负的错误码。

c
static int modeset_open(int *out, const char *node)
{
    int fd, ret;
    uint64_t has_dumb;

    fd = open(node, O_RDWR | O_CLOEXEC);
    if (fd < 0) {
        ret = -errno;
        fprintf(stderr, "cannot open '%s': %m\n", node);
        return ret;
    }

    /* 关键一步：确认驱动支持 dumb buffer */
    if (drmGetCap(fd, DRM_CAP_DUMB_BUFFER, &has_dumb) < 0 || !has_dumb) {
        fprintf(stderr, "driver does not support dumb buffers\n");
        close(fd);
        return -EOPNOTSUPP;
    }

    *out = fd;
    return 0;
}

打开文件之后必须查 DRM_CAP_DUMB_BUFFER，这一步不能省。驱动支持这个 capability，意味着你可以只用公共 ioctl 就创建出能映射、能画的简单缓冲区，一行 radeon、nvidia、intel 的私有代码都不用写。不支持就只能走各家自己的分配路径，跨平台代码到此为止。

DUMB_BUFFER 的能力有限：格式单一（XRGB8888 居多）、不能给 GPU 直接渲染（多数驱动只给你 CPU 映射）、没有格式修饰符。所以它适合做教学 demo、做 framebuffer console、做快速验证，不适合做真正的渲染目标。真渲染还是要走 GBM。

三、KMS：显示控制 #

KMS 是 Kernel Mode Setting 的缩写，直译「内核模式设置」。它解决的问题在名字里：模式设置这件事，从用户态搬进内核。

早期 X server 自己算时序、自己写显示控制器寄存器，这叫 UMS（Userspace Mode Setting）。后果是切换 VT 会黑屏闪一下、挂起恢复会花屏、两个显示服务器不能共存。KMS 把这些操作收进内核，谁想改显示状态都得走 DRM ioctl，内核负责串行化和状态一致性。

3.1 KMS 管的东西 #

能力 说明 谁来设
时序 像素时钟、前后沿、同步脉宽 从 EDID 或 modeline 算出来
分辨率与刷新率 一组预置模式，或显式给的详细时序 connector 上的 mode list
像素格式与叠层 XRGB8888、ARGB8888、NV12；primary/overlay/cursor 三层 plane 的属性与 zpos
缩放、裁剪、电源与色彩 plane 的 src/dst 矩形；DPMS 四态；伽马表与 CTM plane、connector、CRTC 属性

这张表里每一行都对应一个 DRM property。KMS 的配置面本质上是「一堆带名字和类型的属性」，atomic commit 就是「一组属性赋值」。

3.2 属性与 blob #

属性分两类。定长的是整数、布尔、枚举，直接塞进 64 位字段；变长的是 blob，比如 EDID 原始数据、模式时序表、伽马表，这类属性存的是一个 ID，数据本身在另一个地方：

bash
$ modetest -M rockchip -c     # 列出 connector 及其属性
$ modetest -M rockchip -p     # 列出 CRTC 与 plane
$ modetest -M rockchip -a     # 完整资源树，所有属性都给出来

$ cat /sys/class/drm/card0-HDMI-A-1/edid | edid-decode   # EDID 走 sysfs 读

调试时最常看的是三种属性：connector 的 CRTC_ID（这块屏接到哪个控制器）、plane 的 FB_ID（这层画面用的哪个 framebuffer）、connector 的 DPMS（屏是不是被关掉了）。三个值一对，问题基本能定位。

3.3 一次完整的模式设置 #

从上电到出画面，KMS 侧的动作顺序是固定的：

  1. 枚举资源，拿到 connector / encoder / CRTC / plane 的 ID 列表。
  2. 轮询每个 connector 的 status，筛出 connected 的那些。
  3. 读 connector 的 modes，挑一个目标分辨率。
  4. 从 connector 的 encoder_id 找到 encoder，再从 encoder 的 possible_crtcs 位图里挑一个没人用的 CRTC。
  5. 分配 framebuffer：GBM 或 dumb buffer 拿内存，drmModeAddFB2 转成 fb ID。
  6. 一次 atomic commit，把 CRTC、connector、plane 的绑定关系和模式一起生效。
  7. 之后每帧只改 plane 的 FB_ID，走翻页路径。

第 4 步的位图是理解 KMS 的关键：possible_crtcs 是一个位掩码，第 n 位为 1 表示这个 encoder 能被第 n 个 CRTC 驱动。选了不被支持的组合，内核在 commit 阶段直接返回 -EINVAL，屏幕一点反应都没有。

四、GEM：显存管理 #

GEM 是 Graphics Execution Manager，2008 年从 i915 驱动里长出来，后来成了 DRM 的公共显存管理层。它管的不是「显存」这两个字面意思，而是一段 buffer object 的生命周期：谁分配、谁引用、谁能映射、什么时候能回收。

在 GEM 之前，每家的显存分配接口各写各的，同一个 buffer 想在两个进程之间传，只能走 X server 转发或者自己实现一套 IPC。GEM 把这件事收成一套 ioctl，于是跨进程、跨设备共享有了公共语言。

4.1 三个标识符 #

GEM 里同一个 buffer 有三种身份，混用是初学阶段最常见的错误来源。

标识 作用域 怎么来 用在哪
handle 单个进程，进程内唯一 DRM_IOCTL_GEM_CREATE 返回 本进程内的所有操作
name 全系统，靠 flink 生成 DRM_IOCTL_GEM_FLINK 老式的跨进程共享，不安全，别用
dma-buf fd 内核文件描述符，可传递 DRM_IOCTL_PRIME_HANDLE_TO_FD 跨设备、跨子系统共享，现代做法

handle 是进程私有的，这一点要记牢：A 进程拿到的 handle 值 3，在 B 进程里指向的完全是另一块内存。想把 buffer 传给别的进程，必须转成 dma-buf fd，通过 Unix socket 的 SCM_RIGHTS 传过去，对方再用 DRM_IOCTL_PRIME_FD_TO_HANDLE 换成本进程的 handle。

4.2 GEM 的 ioctl 清单 #

ioctl 干什么
DRM_IOCTL_GEM_CREATE 分配一个 buffer object，返回 handle
DRM_IOCTL_GEM_CLOSE 释放本进程对这个 handle 的引用
DRM_IOCTL_GEM_FLINK / GEM_OPEN handle 与全局 name 互相转换
DRM_IOCTL_PRIME_HANDLE_TO_FD handle 转 dma-buf fd
DRM_IOCTL_PRIME_FD_TO_HANDLE dma-buf fd 转 handle
DRM_IOCTL_MODE_CREATE_DUMB 分配 dumb buffer，比 GEM_CREATE 多带尺寸信息
DRM_IOCTL_MODE_MAP_DUMB 拿到 mmap 需要的偏移量
DRM_IOCTL_MODE_DESTROY_DUMB 释放 dumb buffer

注意 GEM_CREATE 和 MODE_CREATE_DUMB 的区别：前者只问「要多大」，驱动自己决定布局；后者显式给出宽、高、bpp，驱动按扫描输出的要求排布，所以能直接当 framebuffer 用。这也是为什么教学 demo 全用 dumb buffer——它省掉了 pitch、tiling、modifier 这一堆麻烦。

4.3 一块 dumb buffer 从生到死 #

c
#include <xf86drm.h>
#include <xf86drmMode.h>

struct dumb_fb {
    uint32_t width, height, pitch, handle, fb_id;
    uint64_t size;
    uint8_t *map;
};

static int dumb_fb_create(int fd, struct dumb_fb *fb, uint32_t w, uint32_t h)
{
    struct drm_mode_create_dumb creq = {0};
    struct drm_mode_map_dumb mreq = {0};

    creq.width  = w;
    creq.height = h;
    creq.bpp    = 32;

    if (drmIoctl(fd, DRM_IOCTL_MODE_CREATE_DUMB, &creq) < 0)
        return -errno;

    fb->width  = w;
    fb->height = h;
    fb->pitch  = creq.pitch;
    fb->size   = creq.size;
    fb->handle = creq.handle;

    /* 转成 framebuffer 对象，才有资格挂到 CRTC 上 */
    if (drmModeAddFB(fd, w, h, 24, 32, fb->pitch, fb->handle, &fb->fb_id))
        return -errno;

    mreq.handle = fb->handle;
    if (drmIoctl(fd, DRM_IOCTL_MODE_MAP_DUMB, &mreq) < 0)
        return -errno;

    fb->map = mmap(NULL, fb->size, PROT_READ | PROT_WRITE,
                   MAP_SHARED, fd, mreq.offset);
    return fb->map == MAP_FAILED ? -errno : 0;
}

static void dumb_fb_destroy(int fd, struct dumb_fb *fb)
{
    munmap(fb->map, fb->size);
    drmModeRmFB(fd, fb->fb_id);

    struct drm_mode_destroy_dumb dreq = { .handle = fb->handle };
    drmIoctl(fd, DRM_IOCTL_MODE_DESTROY_DUMB, &dreq);
}

四个注意点。pitch 不是 width * 4，驱动会对齐到 64 或 256 字节，写像素必须按 pitch 算行偏移，按 width 算必然斜切。drmModeAddFB 的 depth 参数给 24、bpp 给 32，因为 XRGB8888 是 32 位存储、24 位承载颜色。mmap 的偏移量来自 MAP_DUMB 返回的 offset，不是 0。creq.size 才是真正要映射的字节数，它等于 pitch * height，比 width * height * 4 大。

4.4 内存到底在哪儿 #

「显存」这个词有误导性，GEM 管的 buffer 不一定在独立显存里。独立显卡（amdgpu、nouveau）大部分放 VRAM，紧张时换出到系统内存；集成显卡（i915、rockchip、msm）直接用系统内存，CPU 与 GPU 共享同一块物理页；嵌入式 SoC 上的图形 buffer 多数落在 CMA 区域，物理连续。

所以嵌入式板子上 gbm_bo_map 拿到的指针和 GPU 看到的是同一块物理内存，cache 一致性靠驱动的 begin/end_cpu_access 处理。忘了刷 cache，就会出现「CPU 写的图 GPU 看不到」这种幽灵问题。

GEM 早期用 TTM（Translation Table Manager）做内存迁移，后来 i915 换成了自己的 shmem-backed 方案。现在说「GEM/TTM」指的是这一整类显存管理机制，不特指某个结构体。

五、四个核心对象：CRTC、encoder、connector、plane #

KMS 的东西全在这四个对象上。把它们的关系搞清楚，modetest 的输出和内核的报错就都能读了。

对象 是什么 一句话 关键属性
Connector 物理输出口 接哪块屏 status、modes、CRTC_ID、DPMS、EDID
Encoder 信号编码器 用哪条输出通道 encoder_type、possible_crtcs、CRTC_ID
CRTC 显示控制器 用哪个扫描引擎 mode_id、ACTIVE、gamma、OUT_FENCE_PTR
Plane 图层 第几层画面 FB_ID、CRTC_ID、SRC_*、CRTC_*、zpos、type

5.1 三个对象的原始定义 #

CRTC（Cathode Ray Tube Controller）：名字是显像管时代留下的，现在叫显示控制器更贴切。CRTC 控制着实际显示设备的扫描和刷新操作，负责生成该显示设备的图像信号。一个显卡可以有多个 CRTC，每个 CRTC 控制一个显示输出。

Encoder（编码器）：Encoder 是 CRTC 输出信号的编码器，把图像数据转换为特定格式的信号，以便发送到显示设备。Encoder 与特定类型的连接器（HDMI、DVI、VGA 等）相关联，以便把图像数据转成对应的视频信号格式。一个 CRTC 可以与多个 Encoder 相关联，意味着它能同时支持多种连接器类型。

Connector（连接器）：Connector 表示与显卡相连的物理显示端口，如 HDMI 接口、DVI 接口。每个 Connector 对应一个实际的显示输出接口。每个 Connector 都与一个 Encoder 相关联，该 Encoder 负责把图像数据编码成连接器所需的信号格式。

素材里的流程描述是这样的：用户空间通过 DRM 选择一个 Connector，创建一个 CRTC 并把它与所选 Connector 关联；然后创建一个 Encoder 并与之关联，以便把图像数据编码成正确的信号格式；最后把帧缓冲的内容提交给 CRTC，CRTC 收到后发给关联的 Encoder，最终显示到 Connector 所代表的设备上。

这段描述的方向是对的，只有一处要纠正：Encoder 不是用户空间创建的，是驱动在初始化时预置好的。用户态做的是选择——从 connector 的 encoders 数组里挑一个，检查它的 possible_crtcs 位图，从里面挑一个空闲的 CRTC。创建权在内核，选择权在用户态。

5.2 选路的四个问题 #

应用想显示一帧，逐个回答四个问题就够：

  1. 选 connector——接哪个屏？看 status 是否 connected，看 modes 里有没有你想要的分辨率。
  2. 选 encoder——用哪条输出？从 connector 的 encoder 列表里挑，或者直接用它当前的 encoder_id。
  3. 选 CRTC——用哪个控制器？在 encoder 的 possible_crtcs 位图里找一个没被别人占的。
  4. 选 plane——哪层画面？主画面用 primary，叠一层视频用 overlay，鼠标用 cursor。

链路是 connector → encoder → CRTC → plane，单向下行，不能反着配。四个问题答完，一次 atomic commit 把所有绑定关系定下来。

有一条硬约束：每个 CRTC 同一时刻只能驱动一个 connector。想要双屏镜像，得用两个 CRTC 输出同样的内容；想要双屏扩展，两个 CRTC 各带一个 connector。硬件上 CRTC 数量决定了能同时点亮的屏数，跟接口数量无关。

5.3 plane 的三种类型 #

primary 是主画面，每个 CRTC 一个，必须有；overlay 是视频层、字幕层、第二画面，数量从 0 到多个；cursor 是硬件光标，固定尺寸，不能缩放。

plane 靠 zpos 属性决定叠放顺序，靠 SRC_X/Y/W/H 指定从 buffer 里裁哪块，靠 CRTC_X/Y/W/H 指定贴到屏幕的哪儿。两个矩形尺寸不一样就是硬件缩放，缩放器不支持时会返回 -EINVAL。

5.4 用 libdrm 把设备找出来 #

需要一个容器装「已经配好的那一对」：每成功初始化一对 connector + CRTC + framebuffer，就建一个 struct modeset_dev，推到全局链表里。后面翻页时遍历这个链表逐个提交。

c
struct modeset_dev {
    struct modeset_dev *next;
    uint32_t fb_id, crtc_id;
    unsigned int width, height;
    drmModeConnector *conn;
    drmModeEncoder *enc;
    drmModeCrtc *saved_crtc;   /* 退出时恢复原状态 */
};

static struct modeset_dev *modeset_list = NULL;

资源信息从 drmModeGetResources(fd) 拿，用完 drmModeFreeResources(res) 释放。返回的 drmModeRes 里装着所有 connector、encoder、CRTC 的 ID 数组。

c
static int modeset_prepare(int fd)
{
    drmModeRes *res = drmModeGetResources(fd);
    if (!res) return -errno;

    for (unsigned int i = 0; i < res->count_connectors; ++i) {
        drmModeConnector *conn = drmModeGetConnector(fd, res->connectors[i]);
        if (!conn) continue;

        struct modeset_dev *dev = calloc(1, sizeof(*dev));
        dev->conn = conn;

        int ret = modeset_setup_dev(fd, res, conn, dev);
        if (ret) {
            /* -ENOENT 表示这个口没插屏，正常跳过 */
            if (ret != -ENOENT)
                fprintf(stderr, "connector %u: %s\n",
                        conn->connector_id, strerror(-ret));
            free(dev);
            continue;
        }

        dev->next = modeset_list;
        modeset_list = dev;
    }

    drmModeFreeResources(res);
    return 0;
}

modeset_setup_dev 第一步就检查 connector 是不是真在用——conn->connection != DRM_MODE_CONNECTED 或者 conn->count_modes == 0，直接返回 -ENOENT。没插屏的口在资源表里照样存在，不筛掉后面全会失败。

找 CRTC 的逻辑两段式：先试 connector 上已激活的 encoder 和 CRTC，找不到再全量枚举。先试现成组合的原因很实际——已配好的链路说明硬件支持，沿用它能避开一次完整模式设置，屏幕不闪。

c
static int modeset_find_crtc(int fd, drmModeRes *res, drmModeConnector *conn,
                             struct modeset_dev *dev)
{
    /* 第一段：沿用 connector 上已激活的组合 */
    drmModeEncoder *enc = conn->encoder_id
                        ? drmModeGetEncoder(fd, conn->encoder_id) : NULL;
    if (enc) {
        if (enc->crtc_id && !crtc_used_elsewhere(enc->crtc_id)) {
            dev->crtc_id = enc->crtc_id;
            drmModeFreeEncoder(enc);
            return 0;
        }
        drmModeFreeEncoder(enc);
    }

    /* 第二段：枚举 encoder，在 possible_crtcs 位图里找空闲 CRTC */
    for (unsigned int i = 0; i < conn->count_encoders; ++i) {
        enc = drmModeGetEncoder(fd, conn->encoders[i]);
        if (!enc) continue;

        for (unsigned int j = 0; j < res->count_crtcs; ++j) {
            if (!(enc->possible_crtcs & (1 << j)))  continue;  /* 硬件不支持 */
            if (crtc_used_elsewhere(res->crtcs[j])) continue;  /* 已被占用  */

            dev->crtc_id = res->crtcs[j];
            drmModeFreeEncoder(enc);
            return 0;
        }
        drmModeFreeEncoder(enc);
    }
    return -ENOENT;
}

两个判断缺一不可。possible_crtcs 管硬件可行性，crtc_used_elsewhere 管软件占用。漏掉第一个，commit 被内核拒绝；漏掉第二个，第二块屏会把第一块顶掉——现象是「插上第二个显示器，第一个黑了」。crtc_used_elsewhere 的实现就是遍历 modeset_list 看这个 CRTC 有没有被前面的设备记下来，这印证了那条硬约束：一个 CRTC 只能带一个 connector。

六、/dev/dri/card0 与 renderD128 #

Linux 内核检测到机器上的显卡时，会加载对应的设备驱动程序（源码在 drivers/gpu/drm/<厂商目录> 下），并提供两个字符设备来控制显卡。udev（或任何热插拔管理程序）会把它们创建成：

text
/dev/dri/card0
/dev/dri/controlD64

controlD64 是老的控制节点，留给 X server 的 UMS 时代，KMS 之后基本不用。真正要打开的是第一个。有多块显卡时，还会有 /dev/dri/card1、/dev/dri/card2。

路径可以硬编码进程序，但更好的做法是用 libudev 枚举——这样才支持热插拔和多座（multi-seat）。硬编码在开发板上够用，在产品里迟早出问题。

bash
$ ls -l /dev/dri/
crw-rw----+ 1 root video  226,   0 11月 17 09:12 card0
crw-rw----+ 1 root video  226,   1 11月 17 09:12 card1
crw-rw----+ 1 root render 226, 128 11月 17 09:12 renderD128
crw-rw----+ 1 root render 226, 129 11月 17 09:12 renderD129

6.1 两个节点的分工 #

对比项 cardN renderD128
主设备号 226 226
属组 video render
能做什么 显示控制 + 渲染 只做渲染
能做 atomic commit 能 不能
需要 DRM master 显示操作需要 不需要
典型用户 compositor、X server、modetest 无窗口的应用、计算、编解码
多卡对应关系 card0/card1 各一个 renderD128/renderD129 各一个

分工的理由是权限。显示控制是全局资源，谁拿到 DRM master 谁说了算，所以要卡在 video 组；渲染只用 GPU 算东西，不碰显示，权限可以放宽到 render 组。服务器上跑 headless 渲染任务，只需要进 render 组，不用给用户 video 权限。

编号不一定对齐：card0 不一定配 renderD128。要看对应关系读 sysfs：cat /sys/class/drm/renderD128/device/uevent 查驱动名，udevadm info -q property -n /dev/dri/card0 | grep ID_PATH 查物理路径。多卡机器上这一步必须先做，不然调了半天发现调的是另一块卡。

6.2 DRM master #

cardN 上的显示操作需要一个身份：DRM master，同一个 card 节点同一时刻只能有一个。

c
if (drmSetMaster(fd) < 0)      /* 抢，失败说明已经有人占着 */
    fprintf(stderr, "another DRM master is active\n");
drmDropMaster(fd);             /* 用完放手 */

X server 和 Weston 启动时都会抢 master。所以在跑着桌面的机器上直接 modetest -s ...，要么直接失败，要么把桌面的显示配置改掉、退出时不恢复。调试显示问题最好切到文本 VT，或者用 -d 让 modetest 设完模式就放手——画面留在 framebuffer 里不动，master 身份已经交出去，后续起 compositor 不会被挡。

七、GBM：分配图形缓冲区 #

GBM（Generic Buffer Manager，Mesa 里叫 Generic Buffer Management）是一个图形缓冲区管理库，属于 Mesa 3D 的一部分，主要服务于 Linux 平台，为 DRM 内核子系统提供用户空间 API。它提供了一套统一接口，用于管理图形缓冲区和设备之间的交互。

它要解决的痛点很具体：基于 GEM/TTM 的驱动对外没有统一的内存管理接口，至少 Buffer Object 的创建、销毁这些操作，需要各家自己提供设备相关的实现。用户态没有统一接口管缓冲区，某些特定程序的开发就变得很难——最典型的就是 Wayland compositor，它必须在没有窗口系统的环境下自己分配能被 GPU 渲染、又能直接送去扫描输出的内存。

一句话概括：GBM 的作用就是把 DRM 设备（gbm_device）变成 EGL 的本地平台，它创建的句柄可以用来初始化 EGL，并创建渲染目标缓冲区。

7.1 GBM 的 API 面 #

函数 干什么
gbm_create_device(fd) 用一个 DRM fd 建 gbm_device
gbm_bo_create(dev, w, h, format, flags) 分配一块 buffer object
gbm_bo_map(bo, ...) / gbm_bo_unmap 映射到 CPU 地址空间
gbm_bo_get_fd(bo) 导出 dma-buf fd，用于跨进程/跨设备
gbm_bo_import(dev, type, buffer, flags) 把外部 dma-buf 导入成 gbm_bo
gbm_surface_create(dev, w, h, format, flags) 建一个渲染表面，内部是双缓冲或三缓冲
gbm_surface_lock_front_buffer(surf) 取出刚渲染完的那块 bo
gbm_surface_release_buffer(surf, bo) 还回去，让 GBM 复用

gbm_surface_create 的 flags 里最常用的是 GBM_BO_USE_SCANOUT | GBM_BO_USE_RENDERING。前者告诉驱动「这块要能直接送去扫描输出」，后者告诉它「这块要能被 GPU 渲染」。两个都要，缺一个就会在某个环节被拒。

7.2 从 fd 到 surface #

c
struct egl_gbm {
    int render_fd;
    struct gbm_device *gbm_device;
    struct gbm_surface *surface;
    EGLDisplay display;
};

static int gbm_init(struct egl_gbm *g, const char *path, uint32_t w, uint32_t h)
{
    /* path 取 "/dev/dri/renderD128" 或 "/dev/dri/card0" */
    g->render_fd  = open(path, O_RDWR | O_CLOEXEC);
    g->gbm_device = gbm_create_device(g->render_fd);
    assert(g->render_fd >= 0 && g->gbm_device);

    g->surface = gbm_surface_create(g->gbm_device, w, h, GBM_FORMAT_XRGB8888,
                                    GBM_BO_USE_SCANOUT | GBM_BO_USE_RENDERING);
    assert(g->surface);
    return 0;
}

渲染循环里三件套的配合是这样的：

c
/* 1. 用 gbm_surface 建 EGL 窗口表面（EGL 的 native window 就是 gbm_surface） */
EGLSurface egl_surf = eglCreateWindowSurface(g->display, config,
                                             (EGLNativeWindowType)g->surface,
                                             NULL);

/* 2. 渲染一帧 */
render_frame();
eglSwapBuffers(g->display, egl_surf);        /* 换缓冲，不阻塞 */

/* 3. 取出刚渲染完的那块 bo，交给 KMS 显示 */
struct gbm_bo *bo = gbm_surface_lock_front_buffer(g->surface);
uint32_t fb_id;
drmModeAddFB(g->render_fd, gbm_bo_get_width(bo), gbm_bo_get_height(bo),
             24, 32, gbm_bo_get_stride(bo), gbm_bo_get_handle(bo).u32,
             &fb_id);

/* 4. 提交到 CRTC，下一帧再还回去 */
drmModePageFlip(fd, crtc_id, fb_id, DRM_MODE_PAGE_FLIP_EVENT, NULL);

第三步里 gbm_bo_get_handle(bo).u32 那个联合体成员值得看一眼：它是 GBM 把 GEM handle 透出来的通道。GBM 自己不发明 buffer 标识，它就是 GEM handle 的一层包装。

7.3 格式修饰符 #

现代 GPU 的 framebuffer 在内存里不是线性排布的，有的按 4x4 块平铺（tiling），有的压缩，有的分块交错。这些布局用「格式修饰符」（format modifier）描述，一个 64 位整数，高 8 位是厂商码，低位是布局细节。

c
uint64_t modifier = gbm_bo_get_modifier(bo);
printf("modifier = 0x%016lx\n", modifier);   /* 0x0 是线性排布 */

修饰符不对的后果很具体：GBM 按线性布局分配，GPU 按平铺布局渲染，屏幕上出现横条纹或者完全错位的色块。drmModeAddFB2WithModifiers 就是为这个存在的——它把修饰符一起告诉内核，让扫描输出端按同样的布局去读。modetest 的 @ 格式参数也支持写修饰符，调试时可以强制指定某种布局，验证是不是这里协商出了问题。

GBM 和 Wayland 常被放在一起讲，实际没有依赖关系。compositor 同时用两者，是因为它需要用 Wayland 跟客户端说话、用 GBM 分配自己的扫描输出 buffer。一个只用 DRM 不用 Wayland 的裸机播放器，照样需要 GBM；一个跑在 X11 上的程序，完全碰不到 GBM。

八、EGL：跨平台的图形接口 #

EGL 是 Khronos 渲染 API（OpenGL、OpenGL ES、OpenVG）与底层本地平台窗口系统之间的接口。它自己不做渲染，负责的是三件事：图形上下文管理、Buffer 管理、渲染同步。

把它理解成一层适配层更准确。上面是 GL 的状态机，下面可以是 X11 窗口、Wayland surface、GBM surface、pbuffer，甚至是完全离屏的像素缓冲。EGL 的职责是把这两种世界对上，让同一份 GL 代码能在四种平台上跑。

8.1 四个对象 #

对象 含义 关键点
EGLDisplay 对实际显示设备/窗口系统的抽象 一切操作的入口，先拿到它
EGLConfig 一组能力描述：RGBA 位宽、深度、模板、采样数 由 eglChooseConfig 从一堆候选里筛
EGLSurface 存储图像的内存区域 窗口表面、pbuffer、pixmap 三种
EGLContext 存储渲染 API 的状态信息 每个线程同时只能绑一个

EGLConfig 是最容易忽略的一个。它不是「你创建的」，是「你挑的」——驱动报出一堆配置，你按需求筛出第一个满足的。筛的条件写错，比如要求 32 位 alpha 但屏幕只支持 XRGB，eglChooseConfig 返回零个匹配，后面 eglCreateWindowSurface 拿着一个无效 config 直接失败。

8.2 一套标准的 EGL 绘制流程 #

十二步，顺序固定：

  1. 获取 EGLDisplay 对象：eglGetDisplay
  2. 初始化与 EGLDisplay 之间的连接：eglInitialize
  3. 获取 EGLConfig 对象：eglChooseConfig / eglGetConfigs
  4. 创建 EGLContext 实例：eglCreateContext
  5. 创建 EGLSurface 实例：eglCreateWindowSurface / eglCreatePbufferSurface
  6. 连接 EGLContext 和 EGLSurface：eglMakeCurrent
  7. 使用 OpenGL ES API 绘制图形：gl*
  8. 切换 front buffer 和 back buffer 显示：eglSwapBuffers
  9. 断开 EGLSurface 关联的 EGLContext：eglMakeCurrent(dpy, EGL_NO_SURFACE, EGL_NO_SURFACE, EGL_NO_CONTEXT)
  10. 删除 EGLSurface 对象：eglDestroySurface
  11. 删除 EGLContext 对象：eglDestroyContext
  12. 终止与 EGLDisplay 之间的连接：eglTerminate

落成代码：

c
EGLDisplay dpy = eglGetDisplay((EGLNativeDisplayType)gbm_device);
if (dpy == EGL_NO_DISPLAY) { /* 拿不到 display，链路第一环就断了 */ }

EGLint major, minor;
if (!eglInitialize(dpy, &major, &minor))
    fprintf(stderr, "eglInitialize: 0x%x\n", eglGetError());

EGLint cfg_attr[] = {
    EGL_SURFACE_TYPE,    EGL_WINDOW_BIT,
    EGL_RENDERABLE_TYPE, EGL_OPENGL_ES2_BIT,
    EGL_RED_SIZE, 8, EGL_GREEN_SIZE, 8, EGL_BLUE_SIZE, 8, EGL_ALPHA_SIZE, 0,
    EGL_NONE
};
EGLConfig cfg;
EGLint n = 0;
eglChooseConfig(dpy, cfg_attr, &cfg, 1, &n);
if (n == 0) { /* 没有满足条件的配置，多半是属性写太严 */ }

EGLint ctx_attr[] = { EGL_CONTEXT_CLIENT_VERSION, 2, EGL_NONE };
EGLContext ctx = eglCreateContext(dpy, cfg, EGL_NO_CONTEXT, ctx_attr);
EGLSurface surf = eglCreateWindowSurface(dpy, cfg,
                                         (EGLNativeWindowType)gbm_surface,
                                         NULL);

eglMakeCurrent(dpy, surf, surf, ctx);
/* ... 这里是 gl* 调用的地盘 ... */
eglSwapBuffers(dpy, surf);

两个细节。eglSwapBuffers 是带 s 的复数形式，素材里写作 eglSwapBuffer、eglCratePbufferSurface、eglRelease 的地方都是笔误，正确拼写是 eglSwapBuffers、eglCreatePbufferSurface，最后那个「释放」动作由 eglMakeCurrent 传入 EGL_NO_CONTEXT 完成，没有单独的 eglRelease。eglMakeCurrent 的 draw 和 read 参数这里都传 surf，只做离屏渲染时传 EGL_NO_SURFACE 配一个 pbuffer 上下文。

8.3 拿 Display 的三种方式 #

c
EGLDisplay eglGetDisplay(NativeDisplayType native_display);
EGLDisplay eglGetPlatformDisplay(EGLenum platform, void *native_display,
                                 const EGLAttrib *attrib_list);
EGLDisplay eglGetPlatformDisplayEXT(EGLenum platform, void *native_display,
                                    const EGLint *attrib_list);

三者的差别在「平台是谁决定的」。eglGetDisplay 根据当前环境推断默认的原生窗口系统——有 WAYLAND_DISPLAY 就走 Wayland，有 DISPLAY 就走 X11。后两个必须显式指定平台，行为可预测。

compositor 的处境特殊：它相当于裸机运行，没有窗口环境，环境变量一个都没有，eglGetDisplay 无从推断。所以它必须走 GBM 或者 EGL_PLATFORM_DEVICE_EXT 扩展这两条路之一来获取 EGLDisplay。

c
/* 三条等效写法，从 GBM 拿 display */
display = eglGetDisplay((EGLNativeDisplayType)gbm_device);
display = eglGetPlatformDisplay(EGL_PLATFORM_GBM_KHR, gbm_device, NULL);
display = eglGetPlatformDisplayEXT(EGL_PLATFORM_GBM_MESA, gbm_device, NULL);

三个平台枚举值要分清：

枚举 谁定义 用途
EGL_PLATFORM_GBM_KHR Khronos 扩展 通用 GBM 平台，跨实现
EGL_PLATFORM_GBM_MESA Mesa 私有 Mesa 的 GBM 平台，比 KHR 版本早
EGL_PLATFORM_DEVICE_EXT EGL_EXT_platform_device 直接指定 EGL 设备，绕开窗口系统

wlroots 里从严谨性讲，通过 GBM 获取 EGL Display 时，eglGetPlatformDisplayEXT 后面跟的参数应该是 EGL_PLATFORM_GBM_MESA 而不是 EGL_PLATFORM_GBM_KHR。EXT 版本是 Mesa 先实现的私有扩展，枚举值跟后来的 KHR 标准化版本不是一回事；值恰好相同是巧合，语义上该用 MESA。混用不报错，但换驱动或者换 Mesa 版本时行为会变。

九、EGL 与 OpenGL ES 的关系 #

两者是上下层，不是同一件事。

对比项 EGL OpenGL ES
管什么 资源、上下文、表面、同步 绘制状态机与绘制调用
谁调用谁 先 EGL，后 GL GL 必须在 EGL 之后
依赖窗口系统吗 依赖，需要平台适配 不依赖，纯 GPU
头文件与库 <EGL/egl.h>，-lEGL <GLES2/gl2.h>，-lGLESv2

一句话：EGL 决定「在哪儿画、画到哪块内存」，GL 决定「画成什么样」。所以 EGL 出错时症状是「根本没画面」，GL 出错时症状是「有画面但画错了」。

9.1 一个常被问的问题：Mesa Project 是不是软件渲染 #

跑 eglinfo 或者任何查 EGL 信息的程序，看到 EGL_VENDOR 输出 Mesa Project，第一反应往往是「我是不是没用上显卡」。这个判断需要更细的证据。

Mesa 源码 src/egl/main/egldefines.h 里定义了 EGL_VENDOR：

c
#define _EGL_VENDOR_STRING "Mesa Project"

输出 Mesa Project 说明你连的是 Mesa 的 libEGL.so，确认输出无误——这个字符串跟走硬件还是走软件无关。Mesa 的硬件驱动和软件驱动共用同一个 EGL 前端，vendor 串是前端填的。

真正能分辨的是 EGL_RENDERER 和 GL 侧的 GL_RENDERER：

bash
$ eglinfo 2>/dev/null | head -6
EGL client APIs: OpenGL OpenGL_ES
EGL vendor string: Mesa Project
...
OpenGL ES 2.0 Renderer: Mali-T860          # 这一行才是结论

$ glxinfo -B | grep -E 'OpenGL renderer'
OpenGL renderer string: llvmpipe (LLVM 15.0.7, 256 bits)

llvmpipe、softpipe、swrast 这三个名字出现，才是软件渲染的铁证。看到 GPU 型号，就是硬件路径。这条串的来历在 askubuntu 上有完整讨论：Why is OpenGL vendor Mesa Project。

9.2 glxinfo 的视野有限 #

glxinfo 告诉你的是「你正在跑的这个 X11 server 用的是哪套 GL」，它不告诉你「一个不走 X11 的程序会用哪套 GL」。桌面里跑着 Xorg，Mesa 通过 GLX 走 i915 硬件驱动，glxinfo 报硬件渲染器；同一个机器上跑一个直接用 GBM + EGL、环境里没有 DISPLAY 的程序，它连的是另一个 EGL 显示，落到软件渲染也正常。

Nvidia 的机器上这个差异更明显：装了闭源驱动之后，libEGL.so 往往有多份（Mesa 一份在 /usr/lib，Nvidia 一份在 /usr/lib/nvidia-xxx），谁先被 ld.so 找到取决于链接路径和具体程序的需要。

9.3 一条完整的排查链 #

显卡是 Nvidia，EGL_VENDOR 报 Mesa Project，eglChooseConfig 拿不到想要的配置。按这个顺序查：

  1. 确认 EGL 实现是谁：ldd ./your_app | grep -E 'EGL|GL'，看加载的是 Nvidia 的库还是 Mesa 的。
  2. 确认渲染器是谁：查 EGL_RENDERER 或 GL_RENDERER，出现 llvmpipe 就是软件路径。
  3. 确认设备节点权限：ls -l /dev/dri/，当前用户是否在 video 和 render 组里。
  4. 确认 config 需求是否合理：属性里要求了 EGL_ALPHA_SIZE 8 但硬件只支持 XRGB，就会零匹配。

结论有两条。其一，没有正确启用显卡，EGL 采用了 Mesa 软件渲染，因而提供不了正确的 config——第 2、3 步给的就是这个证据。其二，这条路走不通就该换：走 GLX 让 X server 帮忙选实现，或者切到 Wayland 会话，让 compositor 从 GBM 初始化 EGL。两条都比在 X11 + EGL 上死磕厂商驱动容易。

十、Wayland 与 X11 下的图形路径差异 #

同一份渲染代码，换个显示服务器，底下走的路径完全不同。差异的根子在谁负责合成。

10.1 四条关系 #

Wayland 与 DRM：Wayland 是图形显示服务器协议，DRM 是 Linux 内核中管理图形硬件驱动的子系统。在 Wayland 里，客户端应用通过 Wayland 协议与显示服务器通信，而 Wayland 服务器（compositor）通过 DRM 接口与底层图形硬件交互。

DRM 与 GBM：DRM 管硬件驱动，GBM 是用户态库，提供一套标准接口用于分配、管理和操作图形内存，与 DRM 配合使用。应用用 GBM 接口分配和管理缓冲区，以便做硬件加速渲染。GBM 与 Wayland 无直接关联，特定场景下才会一起用。

GBM 与 EGL：两者结合使用，在硬件加速渲染中创建和管理图形表面。EGL 提供通用接口，用于创建和管理 OpenGL、OpenGL ES 的上下文、表面和相关对象。

EGL 与 OpenGL API：EGL 管理上下文和表面，应用才能用 OpenGL API 做图形操作；它提供标准接口，在不同图形系统里创建和管理上下文与表面，实现跨平台渲染。

四条串起来就是接力链：Wayland 协议 → compositor → GBM 分配 → EGL 初始化 → GL 绘制 → DRM 提交。

10.2 两条路径的对比 #

text
X11 路径：
  应用 → GLX/EGL → X server（DRI3 传 dma-buf）→ X server 合成 → DRM 提交
                     ↑ buffer 由 X server 或驱动分配

Wayland 路径：
  应用 → EGL(GBM) → 自己渲染到 gbm_bo → wl_surface 提交 dma-buf
                                        → compositor 合成 → DRM 提交
对比项 X11 Wayland
谁分配扫描输出 buffer X server 客户端自己（经 GBM）或 compositor
buffer 怎么给出去 DRI3 传 dma-buf fd，Present 扩展提交 wl_surface.attach 传 dma-buf
合成在哪 X server 或 compositor compositor 独占
swap 语义 双缓冲，会撕裂 隐式同步，compositor 决定何时上屏
客户端的 GL 接口 GLX 为主，EGL 为辅 EGL 为主，GLX 用不上
环境变量 DISPLAY=:0 WAYLAND_DISPLAY=wayland-0
没被合成时的现象 窗口黑块、花屏 客户端卡在 wl_display_dispatch

最本质的一行：X11 下 buffer 的归属由 X server 决定，Wayland 下由客户端自己决定。所以 Wayland 客户端必须懂 GBM，X11 客户端可以完全不懂。

10.3 怎么知道自己现在在哪条路径上 #

bash
$ echo "DISPLAY=$DISPLAY  WAYLAND_DISPLAY=$WAYLAND_DISPLAY"
DISPLAY=:0  WAYLAND_DISPLAY=wayland-0
$ loginctl show-session $XDG_SESSION_ID -p Type
Type=wayland

两个变量都在，说明这是 Wayland 会话下的 XWayland，走 X11 的程序被 XWayland 接住，多一层转发。想把程序强制切到原生 Wayland，unset DISPLAY 再跑，或者用程序自己的 backend 参数（GTK 是 GDK_BACKEND=wayland，Qt 是 QT_QPA_PLATFORM=wayland）。调试显示问题前先确认自己在哪条路径上，对着 Wayland 会话调 xrandr 改不动任何东西。

十一、modetest：查看与测试显示 #

modetest 是 libdrm 自带的测试工具，直接对 /dev/dri/cardN 打 ioctl，不依赖 X server，也不依赖 Wayland。板子上没有桌面、串口登录，能用的显示工具就它一个。

选项 作用
-M <module> 指定驱动模块名，如 rockchip、i915、msm
-D <device> 直接指定设备节点；和 -M 二选一
-c 列出所有 connector
-e 列出所有 encoder
-p 列出所有 CRTC 和 plane
-f 列出所有 framebuffer
-a 完整资源树，含全部属性
-s <conn>[@<crtc>]:<mode> 给指定 connector 设置模式
-w <obj>:<prop>:<value> 设置任意属性
-P <crtc>:<w>x<h>[@<fmt>] 在指定 CRTC 上配一个 plane
-d 设完模式就 drop master，方便接力

11.1 先看有哪些屏 #

bash
$ modetest -M rockchip -c
Connectors:
id      encoder status          name            size (mm)       modes   encoders
38      37      connected       HDMI-A-1        520x320         14      37
41      0       disconnected    DP-1            0x0             0       40

这五行信息量很大。id 38 是 connector 号，后面 -s 要用。encoder 37 是它当前挂的 encoder——非 0 说明这条链路已经配上了。status connected 表示插着线并且协商成功。modes 14 表示 EDID 报上来 14 个可用模式。encoders 37 是这个 connector 能用的 encoder 列表。

disconnected 的那个口照样出现在表里，encoder 0、modes 0，这就是前面 modeset_setup_dev 要返回 -ENOENT 的原因——不筛掉它，后面选 CRTC 必然失败。

modetest -M rockchip -c -s 38 会把每个模式的序号打出来，形如 #0 1920x1080 60.00 Hz ... 148.500 MHz。这个 #0 就是 -s 参数里 <mode index> 要填的值。

11.2 点一块屏 #

bash
$ modetest -M rockchip -s 38:#0                  # 用第一个模式点亮 HDMI-A-1
$ modetest -M rockchip -s 38:1920x1080           # 指定分辨率，刷新率由内核挑
$ modetest -M rockchip -s 38@35:1920x1080@XR24   # 指定 CRTC 与像素格式
$ modetest -M rockchip -d -s 38:#0               # 设完就放手，方便接着起 weston

设完之后屏幕上会出现一个彩条测试图，那是 modetest 自己画的。看到彩条，说明从 DRM 到接口到屏这一整条路是通的，问题只出在应用层。没看到彩条，说明 DRM 以下就有问题，往上查没有意义。

改模式之前有个坑：modetest 退出时默认不恢复原状。在跑着桌面的机器上这么搞，桌面会停在错误的分辨率上。切到文本 VT 再做，或者用 -d。

11.3 改属性和 plane #

bash
$ modetest -M rockchip -w 38:DPMS:off                      # 关掉这块屏
$ modetest -M rockchip -w 38:DPMS:on                       # 再打开
$ modetest -M rockchip -P 35@19:640x480+100+100@XR24       # fb 19 贴到 CRTC 35 的 (100,100)
$ modetest -M rockchip -f                                  # 列出所有 framebuffer

-w 是万能的。凡是 -a 输出里能看到的属性，都能用 -w 改。调试色彩问题改 gamma，调试叠层问题改 plane 的 zpos，验证硬件光标改 CURSOR_W、CURSOR_H。

十二、xrandr：X11 下的显示配置 #

xrandr 是 X11 的 RandR 扩展客户端。它只对 X server 说话，所以在 Wayland 会话里跑它，要么连不上、要么改的是 XWayland 的虚拟屏，看不到效果。

bash
$ xrandr
Screen 0: minimum 320 x 200, current 1920 x 1080, maximum 8192 x 8192
HDMI-1 connected primary 1920x1080+0+0 (normal left inverted right x axis y axis) 520mm x 320mm
   1920x1080     60.00*+  59.94    50.00
   1280x720      60.00    59.94
DP-1 disconnected (normal left inverted right x axis y axis)

读懂这几行：current 1920 x 1080 是当前整屏尺寸；HDMI-1 connected primary 表示接上了且是主屏；1920x1080+0+0 里的 +0+0 是这块屏在整个画布里的偏移；60.00*+ 里星号是当前模式，加号是首选模式；下面缩进的就是可选模式列表。

12.1 常用命令 #

bash
$ xrandr --output HDMI-1 --mode 1920x1080        # 改分辨率
$ xrandr --output HDMI-1 --mode 1920x1080 --rate 59.94   # 改刷新率
$ xrandr --output HDMI-1 --auto                  # 自动挑一个模式
$ xrandr --output DP-1 --off                     # 关掉一个输出
$ xrandr --output HDMI-1 --primary               # 设主屏
$ xrandr --output HDMI-1 --rotate left           # 旋转
$ xrandr --fb 3840x1080                          # 虚拟画布，双屏要够大
$ xrandr --output DP-1 --mode 1920x1080 --output HDMI-1 --mode 1920x1080 --right-of DP-1
$ xrandr --output DP-1 --mode 1920x1080 --output HDMI-1 --mode 1920x1080 --same-as DP-1

最后两条是双屏扩展和双屏镜像。扩展时 --right-of DP-1 决定 HDMI-1 摆在哪一侧，镜像用 --same-as 让两个输出共享同一块画布区域。

素材里记过一条配合用法：xrandr --output HDMI-1 --mode 1920x1080 | ./a.out。这里的管道符要改成 &&——xrandr 的 stdout 是一行行文本，不是可执行内容，管道过去等于把输出喂给 a.out 的 stdin。想要「先改分辨率再跑程序」，写成 xrandr --output HDMI-1 --mode 1920x1080 && ./a.out，这样 xrandr 返回 0 之后才启动程序。用管道的话，两个进程同时启动，程序先跑起来，分辨率还没改完，测出来的结果不可信。

12.2 modetest 与 xrandr 的分工 #

对比项 modetest xrandr
依赖 只要 DRM 设备节点 必须有 X server
层 直接打 KMS ioctl 通过 RandR 扩展，间接改 KMS
Wayland 下能用吗 能（要抢 master） 不能
能看属性、能设 plane 吗 能，-a 全列，-P 直接配 只能看 RandR 暴露的那部分，plane 碰不到
典型用途 裸机验证、板级 bring-up 桌面里调多屏布局

一句话分界：没有 X server 用 modetest，有 X server 用 xrandr。两者改的都是同一份内核状态，只是入口不同。

除了上面两个大件，这些工具在具体场景里更快。

工具或文件 看什么 怎么用

十四、常见故障与现象 #

屏幕不亮的原因可以有很多层，但症状和原因的对应关系相当固定。

现象 最常见的原因 先查什么
/dev/dri/card0 不存在 驱动没加载，或没编进内核 dmesg、lsmod、/sys/class/drm
打开设备返回 EACCES 用户不在 video / render 组 id、ls -l /dev/dri/
modetest 报 Permission denied 别的进程拿着 DRM master 停掉桌面，或切文本 VT
connected 但 modes 0 EDID 读不到 换线、查 edid-decode
一直是 disconnected 线、口、HPD 检测 换线换口；查 dmesg 的 HPD 日志
commit 返回 EINVAL CRTC/encoder/plane 组合不合法 查 possible_crtcs 位图
屏幕亮但全黑 plane 的 FB_ID 是 0，或 CRTC 没 ACTIVE modetest -p 看属性
花屏、横条纹 格式或修饰符不匹配 格式改 XR24 试，查 modifier
画面斜切、错位 按 width 算行偏移，没用 pitch 代码里改成 pitch * y + x * 4
能画但撕裂 没走翻页，直接写前台缓冲 用 drmModePageFlip 或 atomic commit

十五、易错点速查 #

易错点 为什么错 正确做法
把 DRM、GBM、EGL 当成三选一 它们是接力关系 DRM 管显示与显存，GBM 分配 buffer，EGL 接应用
以为 EGL 会画像素 EGL 只安排资源和同步 绘制是 GL 实现的事
以为 EGL_VENDOR 是 Mesa Project 就是软件渲染 厂商串由 EGL 前端填，跟硬件无关 看 GL_RENDERER 是不是 llvmpipe
用 card0 做纯渲染 会和显示端抢 master 渲染走 renderD128
硬编码 /dev/dri/card0 多卡机器上编号会变 用 libudev 枚举
打开设备不查 DRM_CAP_DUMB_BUFFER 后续 ioctl 全失败且不好定位 打开后立刻 drmGetCap 检查
按 width * 4 算行偏移 驱动会把 pitch 对齐到 64/256 一律用 pitch
先 DESTROY_DUMB 再 RmFB framebuffer 指向已释放内存 顺序反过来
一个 CRTC 挂两个 connector 硬件约束，一个 CRTC 只能带一个口 双屏用两个 CRTC
不查 possible_crtcs 就配 组合硬件不支持，commit 返回 EINVAL 按位图筛，再查是否被占用
忘了排除 disconnected 的 connector 没插屏的也会出现在资源表里 检查 status 和 count_modes
混用 EGL_PLATFORM_GBM_KHR 与 ..._GBM_MESA 语义不同，换实现就变行为 EXT 版本用 MESA
在 Wayland 会话里用 xrandr 改的是 XWayland，看不到效果 换 modetest，或切 X11 会话
用管道串 xrandr 和程序 两个进程同时启动，顺序没保证 用 &&
忽略格式修饰符 GPU 按平铺布局渲染，屏幕出条纹 用 drmModeAddFB2WithModifiers
commit 时随手加 ALLOW_MODESET 每次提交都走重配时序的慢路径 只有真改分辨率才加

这十五条里有大半是同一个根源：把接力链上某一环的职责错记到另一环头上。记住 connector → encoder → CRTC → plane 这条下行链路，记住 buffer 从 GBM 出、显示从 KMS 出、上下文从 EGL 出，剩下的问题都能顺着链路往前找——找到哪一环开始不对，就是哪一环的事。
