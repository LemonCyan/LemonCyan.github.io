这篇讲一件事：RK3399 上的 Mali-T860 怎么在 mainline Linux 上把 GPU 真正跑起来。链路是两段——内核侧的 Panfrost 驱动，用户态的 mesa 实现。两段各自装好还不算完，内核驱动和 mesa 版本要对得上，对不上就会出各种看不懂的报错。

讲什么：Panfrost 在内核里的位置与配置、RK3399 的设备树与 GPU 供电、mesa 怎么在开发板上从源码编出来、OpenCL 的两条路子（clover 与 rusticl）、验证手段与踩坑记录。

不讲什么：DRM/GBM/EGL 这套用户态图形栈的分层原理不在这里展开，Weston 之类的合成器配置也不在这里，OpenGL API 本身的编程教学也不在这里。这三块各自有专篇，同目录下依次是《DRM、GBM 与 EGL：用户态图形栈三件套》《嵌入式 GUI 与 Weston》《OpenGL 编程》，按需连读。

硬件基线：NanoPC-T4 / RK3399 / Mali-T860（Midgard 架构）/ 4GB LPDDR3 / 16GB eMMC / HDMI 15.6 寸屏 / u-boot 2023.04 / Linux 6.3，内容对 5.2.8 同样适用。

一、从卡顿问题说起 #

板子移植完 u-boot 2023.04、Linux 6.3 和 Ubuntu 20.04.4 根文件系统，进桌面用起来就发现问题：Firefox 随便开个网页，视频加载慢得离谱，同时 CPU 占用率直线飙高。

这种情况只有两个源头：

原因 表现 出路
SoC 本身没带 3D 加速 任何渲染都走 CPU 只能换轻量界面，别指望 GNOME/KDE
SoC 带了 GPU 但没跑起来 驱动缺失或没配对 本篇要解决的就是这个

选板子之前先查主控有没有 GPU，这条路没有补救办法。GNOME、KDE 的合成与渲染全靠 CPU 顶上，很难跑得动。

第二个坑更常见。RK3399、S912 这些芯片挂着 ARM Mali GPU，性能不差，可 mainline 内核里缺对应驱动。GPU 驱动天生分两半：

位置 内容 开源情况
内核态 寄存器操作、内存管理、中断、任务提交 ARM 只放出了这一半
用户态 上对应用提供标准 API，下操作内核驱动 ARM 完全不开源

用户态那一半要提供的 API 大致是这些：OpenGL ES 1.1/2.0/3.0/3.1/3.2、OpenCL 1.1/1.2/2.0、Vulkan 1.0、RenderScript（具体能开到哪些，看二进制和 GPU 型号）。

ARM 放出的内核驱动还有个硬伤：没按 Linux 内核规范用 DRM 框架实现，mainline 不收。用户态那块只以二进制的形式给到买了 Mali 授权的 SoC 厂（Rockchip、Amlogic 这些），而且这套代码主要是给 Android 写的，放到 Debian、Ubuntu 上兼容性很差。

这不是 ARM 独创的玩法，Nvidia、Vivante、Imagination 都一样。Linus 为这事对 Nvidia 竖过中指，那句「Nvidia, F*K you!」流传很广。

结果就是：想用 GPU，只能用 SoC 原厂那套老内核加定制系统；想跑 mainline，就只能放弃 GPU 加速。大部分跑 mainline 的开发板不开图形加速，原因就在这。

有几个黑客不接受这个局面，逆向了 ARM 的二进制库，重写开源驱动，在 Linux 5.2 发布时合进了 mainline：

  • Mali-400/450 走 Lima；
  • Mali-T6xx/T7xx/T8xx 和 G 系列走 Panfrost；
  • 用户态的开源库是 mesa，对 Mali 的支持从 mesa 19.2 起。

RK3399 集成的是 Mali-T860，所以这条路是：内核 Panfrost + 用户态 mesa，3D 加速就能开。

判断 GPU 到底有没有在工作，两个土办法就够：

bash
# 看 job / gpu / mmu 三个中断是否在涨
cat /proc/interrupts | grep panfrost

# 看 CPU 占用，GPU 没跑起来时渲染全靠 CPU
top

二、GPU 与图形 API 的关系 #

把这条链路想清楚，后面配置就不会乱。应用调 API，API 落到用户态驱动，用户态驱动通过 ioctl 敲内核驱动，内核驱动把任务丢给 GPU。

图形 API 这一层，常见的有这几个：

API 定位 谁在维护 在本文的位置
OpenGL 桌面级 2D/3D 规范 Khronos mesa 提供实现
OpenGL ES OpenGL 的嵌入式子集，省内存 Khronos 移动与嵌入式主力
EGL OpenGL ES 与本地窗口系统之间的中间层 Khronos 依赖具体系统实现
Vulkan 贴近硬件的低开销 API Khronos panfrost 有 Vulkan 驱动
OpenCL 跨平台并行计算 Khronos clover / rusticl
WebGL JavaScript 绑定的 GLES 2.0 Khronos 浏览器里的 3D

Khronos 只定规范，不做实现。各家 GPU 厂商（NVIDIA、AMD、Intel）各写各的驱动，只要符合规范就能互通。落到 Linux 上，实现有三类：mesa 这套开源的、厂商自己的闭源驱动（NVIDIA 的 .run、AMD 的 amdgpu-pro）、以及 Apple 那种跟系统深度绑定的实现。

WebGL 的价值在于把 GLES 2.0 和 JavaScript 接起来，给 HTML5 Canvas 提供硬件加速的 3D 渲染。它不需要浏览器插件，靠的是底层图形硬件加速，而这个加速最终又落回 OpenGL 接口。

OpenCL 的模型要多说一句，因为它跟后面的 ICD 直接相关：

  • 一个 OpenCL 平台对应一个供应商，平台下面挂一到多个设备；
  • 同一台设备可以有多个厂商的 OpenCL 实现，设备不隶属于唯一平台；
  • 平台的 OpenCL 版本和设备的 OpenCL 版本不必一致。

ICD 是 Installable Client Driver，指某个设备专属的 OpenCL 实现，实体是 libIntelOpenCL.so、libnvidia-opencl.so、libMesaOpenCL.so 这类文件。从 OpenCL 1.2 起有了 cl_khr_icd 扩展，允许不同厂商的多个驱动共存于同一台主机。

ICD Loader 就是那个二传手。它导出全部 OpenCL API 符号，但不做实现，只按平台 ID 把调用转给对应的 ICD：

角色 实体 职责
应用 你的程序 调 OpenCL API
ICD Loader libOpenCL.so 占位 + 分发，全机只一个
ICD libMesaOpenCL.so、libRusticlOpenCL.so 真正的实现，一平台一个
ICD 定义文件 /etc/OpenCL/vendors/*.icd 告诉 Loader 去加载谁

有了这一层，代码就不依赖任何厂商 SDK，没装 SDK 也能编译，可以动态加载也可以静态链进去。

Linux 上写 OpenCL 程序需要三样东西：头文件 CL/cl.h、Loader 库 libOpenCL.so、以及 /etc/OpenCL/vendors/ 下的 .icd 文件。每个 .icd 里就一行库文件路径，系统加载 OpenCL 时扫这个目录，据此确定有哪些可用平台。

Vulkan 与 OpenGL 的设计取向不同：它基于 AMD 的 Mantle 演化而来，驱动层只做薄封装，把内存管理、线程管理、命令缓冲、队列提交全部交给应用。驱动干的事少了，隐藏的 bug 也少了，代价是应用侧要自己处理线程同步，对写代码的人要求更高。Panfrost 的 Vulkan 驱动是实验性质的，能够编出来，但别指望生产可用。

三、Mali 的开源驱动路线：Panfrost 与 Lima #

先解决一个常被搞混的问题：手上的 Mali 该用哪个驱动。

维度 Lima Panfrost
架构 Utgard Midgard、Bifrost
典型型号 Mali-400、Mali-450 T604/T624/T628/T720/T760/T820/T830/T860/T880、G 系列
上游时间 Linux 5.2 Linux 5.2
mesa 驱动 lima_dri.so panfrost_dri.so
能力 GLES 2.0 为主 GLES 3.1、部分 GL 3.1
本篇涉及 否 是（T860）

T860 属于 Midgard，走 Panfrost，这点必须记牢。T860 是 RK3399 用的那颗，四核 Mali-T860 MP4。

Panfrost 在 panfrost_drv.c 里用 of_device_id 表列出了支持的型号，设备树的 compatible 命中哪一条，就由哪一条的 data 决定特性集：

c
static const struct of_device_id dt_match[] = {
        /* Set first to probe before the generic compatibles */
        { .compatible = "amlogic,meson-gxm-mali",
          .data = &amlogic_data, },
        { .compatible = "amlogic,meson-g12a-mali",
          .data = &amlogic_data, },
        { .compatible = "arm,mali-t604", .data = &default_data, },
        { .compatible = "arm,mali-t624", .data = &default_data, },
        { .compatible = "arm,mali-t628", .data = &default_data, },
        { .compatible = "arm,mali-t720", .data = &default_data, },
        { .compatible = "arm,mali-t760", .data = &default_data, },
        { .compatible = "arm,mali-t820", .data = &default_data, },
        { .compatible = "arm,mali-t830", .data = &default_data, },
        { .compatible = "arm,mali-t860", .data = &default_data, },
        { .compatible = "arm,mali-t880", .data = &default_data, },
        { .compatible = "arm,mali-bifrost", .data = &default_data, },
        { .compatible = "arm,mali-valhall-jm", .data = &default_data, },
        { .compatible = "mediatek,mt8183-mali", .data = &mediatek_mt8183_data },
        {}
};
MODULE_DEVICE_TABLE(of, dt_match);

这张表说明三件事：

  • 表里没有的型号（T604 之外的早期芯片、G71 这些）暂时用不了；
  • Amlogic 和 MT8183 有专门的 data，说明它们有平台特有的 quirk；
  • arm,mali-t860 对应 default_data，RK3399 走的是最通用那条。

内核驱动只负责把任务喂进 GPU，真正让应用看到 OpenGL 3.1 的是 mesa 里的 panfrost gallium 驱动。它要干五件事：

职责 具体内容
指令解析与翻译 把应用发的 GL 指令翻成 Mali GPU 的底层指令，含顶点、片元、纹理、着色器
状态管理 跟踪 GL 状态机的变化并正确应用
内存管理 把图形数据放进 GPU 可见内存，用完释放
管线控制 顶点处理、着色器执行、光栅化的调度
版本兼容 对同一 API 的不同版本提供一致行为

当前版本的 Panfrost 只管 OpenGL 与 OpenGL ES。Vulkan 有独立驱动，OpenCL 走 mesa 的 clover 或 rusticl，三条线互不替代。

整条驱动栈落成文件是这样：

文件 作用
/dev/dri/renderD128 渲染节点，OpenGL/Vulkan/编解码都走它
panfrost_dri.so panfrost 的 DRI 驱动，与内核驱动对话、管资源、跑渲染
libgallium_dri.so gallium 通用层，一套代码支撑多种硬件
libEGL.so EGL 实现，接窗口系统与 GL/GLES
libGLESv1_CM.so、libGLESv2.so OpenGL ES 实现
libgbm.so 缓冲区分配管理，Wayland 与 DRI 场景用
libglapi.so GL API 的间接层
libGL.so、libOpenGL.so 桌面 OpenGL，后者走 GLVND 架构
libOpenCL.so ICD Loader
libMesaOpenCL.so、libRusticlOpenCL.so 两套 OpenCL 实现

看清这张表，就能理解为什么「装个驱动」在 ARM 上是一堆包的事：一个 OpenGL 应用要跑起来，至少要渲染节点、DRI 驱动、EGL、GLES、gbm 五样齐全，版本还得互相咬合。

四、内核侧的 Panfrost 驱动 #

内核的下载、配置、编译流程在《Rockchip RK3399 - 移植 u-boot 2023.04 & Linux 6.3》里，这里只补 GPU 相关的部分。

在内核根目录执行 make menuconfig，把 Panfrost 打开：

text
Device Drivers  --->
    Graphics support  --->
        <*> Panfrost (DRM support for ARM Mali Midgard/Bifrost GPUs)

编进内核或者编成模块都行。驱动源码在 drivers/gpu/drm/panfrost/ 下，十几个文件，分工大致是：

文件 职责
panfrost_drv.c 驱动入口，of_device_id 匹配表、probe/remove、平台驱动注册
panfrost_device.c 设备初始化，时钟、电源、reset 的上电时序
panfrost_gpu.c 读 GPU 的 feature 寄存器，识别型号与能力
panfrost_job.c 任务提交与调度，job 中断处理
panfrost_mmu.c MMU 与地址空间管理
panfrost_gem.c GEM 缓冲区对象
panfrost_devfreq.c 动态调频
panfrost_features.h、panfrost_issues.h 各型号的能力位与已知硬件缺陷
panfrost_regs.h 寄存器定义

panfrost_drv.c 末尾就是标准的平台驱动注册：

c
static struct platform_driver panfrost_driver = {
        .probe          = panfrost_probe,
        .remove         = panfrost_remove,
        .driver         = {
                .name   = "panfrost",
                .pm     = pm_ptr(&panfrost_pm_ops),
                .of_match_table = dt_match,
        },
};
module_platform_driver(panfrost_driver);

设备树里的 compatible 命中 arm,mali-t860，panfrost_probe 就被调用，后面的 panfrost_device_init 完成上电与寄存器探测。

五、设备树与固件 #

RK3399 的 GPU 节点定义在 arch/arm64/boot/dts/rockchip/rk3399.dtsi：

dts
gpu: gpu@ff9a0000 {
        compatible = "rockchip,rk3399-mali", "arm,mali-t860";
        reg = <0x0 0xff9a0000 0x0 0x10000>;
        interrupts = <GIC_SPI 20 IRQ_TYPE_LEVEL_HIGH 0>,
                     <GIC_SPI 21 IRQ_TYPE_LEVEL_HIGH 0>,
                     <GIC_SPI 19 IRQ_TYPE_LEVEL_HIGH 0>;
        interrupt-names = "job", "mmu", "gpu";
        clocks = <&cru ACLK_GPU>;
        #cooling-cells = <2>;
        power-domains = <&power RK3399_PD_GPU>;
        status = "disabled";
};

逐个属性看：

属性 值 说明
compatible rockchip,rk3399-mali、arm,mali-t860 第二个是 Panfrost 的匹配项，命中即 probe
reg 0xff9a0000，长度 0x10000 寄存器基地址与大小
interrupts GIC_SPI 20 / 21 / 19 job、mmu、gpu 三路中断，电平触发
interrupt-names job、mmu、gpu 与 interrupts 顺序一一对应
clocks &cru ACLK_GPU GPU 时钟由 CRU 提供
power-domains RK3399_PD_GPU 归属的电源域
#cooling-cells <2> 可作为温控冷却设备
status disabled 默认关闭，板级 dts 要覆盖

SoC 级的 dtsi 保持 disabled，板级文件里打开。在 arch/arm64/boot/dts/rockchip/rk3399-evb.dts 里加：

dts
&gpu {
        mali-supply = <&vdd_gpu>;
        status = "okay";
};

mali-supply 指向 GPU 的供电 regulator，status = "okay" 把节点启用。少了 mali-supply，驱动上电时会因为拿不到稳压器而 probe 失败。

vdd_gpu 是 I2C0 下面的子节点，对应板上的 SYR838 降压芯片：

dts
vdd_gpu: regulator@41 {
        compatible = "silergy,syr828";
        reg = <0x41>;
        fcs,suspend-voltage-selector = <1>;
        pinctrl-names = "default";
        pinctrl-0 = <&gpu_sleep>;
        regulator-always-on;
        regulator-boot-on;
        regulator-min-microvolt = <712500>;
        regulator-max-microvolt = <1500000>;
        regulator-name = "vdd_gpu";
        regulator-ramp-delay = <1000>;
        vin-supply = <&vcc3v3_sys>;

        regulator-state-mem {
                regulator-off-in-suspend;
        };
};
属性 含义
compatible 稳压器驱动类型，syr828
reg I2C 从地址 0x41
fcs,suspend-voltage-selector 睡眠态电压选择
pinctrl-0 默认引脚状态指向 gpu_sleep
regulator-always-on 常开，不随引用计数关闭
regulator-boot-on 启动即开
regulator-min/max-microvolt 输出范围 0.7125V ~ 1.5V
regulator-ramp-delay 电压爬升延迟 1000us
vin-supply 输入来自 vcc3v3_sys

板上的 VDD_GPU 由 SYR838PKC 输出。SYR837/SYR838 是同步降压 DC/DC，几个关键指标：最大输出 6A、输入 2.6V~5.5V、集成主开关与同步开关所以导通损耗低、输出电压可经 I2C 编程，范围 0.7125V~1.5V。

这颗芯片带 I2C 接口，主控可以改输出电压做 DVS（电压缩放），对应不同负载与功耗需求。I2C 最高 3.4MHz，标准命令，芯片永远是从设备，7 位地址加一位读写标志寻址。SYR837 出厂地址 0x40，SYR838 是 0x41，所以节点写成 reg = <0x41>。

gpu_sleep 引脚配置在 pinctrl 节点下：

dts
pmic {
        cpu_b_sleep: cpu-b-sleep {
                rockchip,pins = <1 RK_PC1 RK_FUNC_GPIO &pcfg_pull_down>;
        };

        gpu_sleep: gpu-sleep {
                rockchip,pins = <1 RK_PB6 RK_FUNC_GPIO &pcfg_pull_down>;
        };

        pmic_int_l: pmic-int-l {
                rockchip,pins = <1 RK_PC5 RK_FUNC_GPIO &pcfg_pull_up>;
        };
};

GPIO1_B6 被配成普通 GPIO，电气特性下拉。这根线接的就是 SYR838 的 VSEL 引脚，睡眠时用它切电压档。

vcc3v3_sys 更简单，是个固定输出的稳压器，芯片是 NB680GD，输出恒为 3.3V：

dts
vcc3v3_sys: vcc3v3-sys {
        compatible = "regulator-fixed";
        regulator-always-on;
        regulator-boot-on;
        regulator-min-microvolt = <3300000>;
        regulator-max-microvolt = <3300000>;
        regulator-name = "vcc3v3_sys";
};

固件这块分平台看。RK3399 这条链路不需要往根文件系统塞任何 GPU 固件文件，设备树里的 regulator 与 power-domain 就足以完成上电；Amlogic 的 meson 平台在 dts 里带 firmware 节点，那种情况才要从 /lib/firmware 提供文件，而 Panfrost 里走的是 Amlogic 专用 data。判断方法很简单：probe 日志里没提 firmware 加载，就说明这套板子不依赖它。

设备树改完要重新编内核、打包、烧写，步骤在第四章。改动只落在 dts 时，make -j8 会连着 dtb 一起更新，最后仍要生成 itb 再烧。

六、用户态的 mesa #

内核把 GPU 点着了，/dev/dri/renderD128 也有了，可此时 glxinfo 只会报 llvmpipe——用户态还没人接活。接活的就是 mesa。

mesa（也叫 mesa3D、mesa 3D 图形库）是 OpenGL、Vulkan 等规范的开源实现，把这些 API 翻译成具体硬件的驱动。项目最早只是 OpenGL 的开源实现，后来扩展到 OpenGL ES、OpenCL、OpenMAX、VDPAU、VA-API、Vulkan 和 EGL。

对 Panfrost 来说，mesa 里那套 panfrost gallium 驱动就是整条链路的用户态一半。它向下敲 /dev/dri/renderD128，向上给出 libGL.so、libGLESv2.so、libEGL.so 这些入口。

七、mesa 的编译流程 #

apt 装到的 21.2.6 够用，但它有两个局限：版本锁死在发行版，而且不带 rusticl。要 22.0.0 或 24.0.0 就得自己编。

重头戏是 meson 参数。它决定编出哪些库、装到哪。22.0.0 那套参数长这样：

参数逐个解释：

参数 作用 不写会怎样
-Dplatforms=x11 支持哪些窗口系统，auto 表示全开 按 auto 全开，编进一堆用不上的平台

9.3 clover 为什么列不出设备 #

装完 Loader 跑 clinfo，平台有了，设备是 0：

原因在 clover 的源码里。clover 在 src/gallium/frontends/clover 下，clGetPlatformInfo 实现在 api/platform.cpp：

CLOVER_ICD_API cl_int
clGetPlatformInfo(cl_platform_id d_platform, cl_platform_info param,
                  size_t size, void *r_buf, size_t *r_size) {
   return GetPlatformInfo(d_platform, param, size, r_buf, r_size);
}

往里走一层，名字和厂商是写死的：

text
cl_int
clover::GetPlatformInfo(cl_platform_id d_platform, cl_platform_info param,
                        size_t size, void *r_buf, size_t *r_size) try {
   property_buffer buf { r_buf, size, r_size };
   auto &platform = find_platform(d_platform);

   switch (param) {
   case CL_PLATFORM_VERSION: {
      buf.as_string() = "OpenCL " + platform.platform_version_as_string() + " Mesa " PACKAGE_VERSION MESA_GIT_SHA1;
      break;
   }
   case CL_PLATFORM_NAME:
      buf.as_string() = "Clover";
      break;
   case CL_PLATFORM_VENDOR:
      buf.as_string() = "Mesa";
      break;
   case CL_PLATFORM_ICD_SUFFIX_KHR:
      buf.as_string() = "MESA";
      break;
   default:
      throw error(CL_INVALID_VALUE);
   }
   return CL_SUCCESS;
} catch (error &e) {
   return e.get();
}

CL_PLATFORM_NAME 返回 Clover，CL_PLATFORM_VENDOR 返回 Mesa，就是这么来的。

设备列表在 api/device.cpp 的 clGetDeviceIDs：

text
CLOVER_API cl_int
clGetDeviceIDs(cl_platform_id d_platform, cl_device_type device_type,
               cl_uint num_entries, cl_device_id *rd_devices,
               cl_uint *rnum_devices) try {
   auto &platform = obj(d_platform);
   std::vector<cl_device_id> d_devs;

   // Collect matching devices
   for (device &dev : platform) {
      if (((device_type & CL_DEVICE_TYPE_DEFAULT) &&
           dev == platform.front()) ||
          (device_type & dev.type()))
         d_devs.push_back(desc(dev));
   }

   if (d_devs.empty())
      throw error(CL_DEVICE_NOT_FOUND);
   ...
} catch (error &e) {
   return e.get();
}

平台下没有可用设备，d_devs 为空，直接 throw error(CL_DEVICE_NOT_FOUND)，返回 -1。clover 的 gallium 后端压根没把 T860 列进来，所以这条路对 Mali 是死的。

9.4 写个程序验证 #

建工程目录，写一份最小可跑的 OpenCL 代码：

bash
root@rk3399:/opt# mkdir -p opencl-project/platform

c
#include <stdio.h>
#include <CL/cl.h>

#define MAX_PLATFORMS 10
#define MAX_DEVICES 10

int main() {
    cl_platform_id platforms[MAX_PLATFORMS];
    cl_device_id devices[MAX_DEVICES];
    cl_uint num_platforms, num_devices;
    cl_int ret;

    // 枚举平台并打印名字与厂商
    if (clGetPlatformIDs(MAX_PLATFORMS, platforms, &num_platforms) != CL_SUCCESS) {
        printf("Failed to get platform IDs\n");
        return -1;
    }
    printf("Number of platforms: %u\n", num_platforms);
    for (cl_uint i = 0; i < num_platforms; i++) {
        char name[128], vendor[128];
        clGetPlatformInfo(platforms[i], CL_PLATFORM_NAME, sizeof(name), name, NULL);
        clGetPlatformInfo(platforms[i], CL_PLATFORM_VENDOR, sizeof(vendor), vendor, NULL);
        printf("Platform %u:\n    Name: %s\n    Vendor: %s\n\n", i, name, vendor);
    }

    // 取第 0 个平台下的 GPU 设备
    if (clGetDeviceIDs(platforms[0], CL_DEVICE_TYPE_GPU, MAX_DEVICES, devices, &num_devices) != CL_SUCCESS) {
        printf("Failed to get device IDs\n");
        return -1;
    }

    cl_context ctx = clCreateContext(NULL, num_devices, devices, NULL, NULL, &ret);
    cl_command_queue q = clCreateCommandQueue(ctx, devices[0], 0, &ret);

    // 内核源码：只打印一行
    const char *src = "__kernel void hello_world() {\n"
                      "    printf(\"Hello, World!\\n\");\n"
                      "}\n";
    cl_program program = clCreateProgramWithSource(ctx, 1, &src, NULL, &ret);
    if (clBuildProgram(program, num_devices, devices, NULL, NULL, NULL) != CL_SUCCESS) {
        printf("Failed to build program\n");
        return -1;
    }

    cl_kernel kernel = clCreateKernel(program, "hello_world", &ret);
    if (clEnqueueTask(q, kernel, 0, NULL, NULL) != CL_SUCCESS) {
        printf("Failed to enqueue task\n");
        return -1;
    }
    clFinish(q);
    printf("Kernel executed successfully\n");

    clReleaseKernel(kernel);
    clReleaseProgram(program);
    clReleaseCommandQueue(q);
    clReleaseContext(ctx);

    return 0;
}

libGL error 那一类故障有个固定的补救命令，把发行版那批 mesa 包全部重装回去：

bash
root@rk3399:/opt# apt install --reinstall libegl-mesa0 libgl1-mesa-dri libglapi-mesa \
    libglu1-mesa libglx-mesa0 mesa-va-drivers mesa-vdpau-drivers mesa-vulkan-drivers \
    libopengl0 libgl1 libgles2 libegl1 libglx0 libglvnd0

原理是自编的 mesa 覆盖了 /usr/lib/aarch64-linux-gnu 下的 libGL、libglapi、dri/*，而发行版的其他组件还在用旧版本。版本号一旦对不上，_glapi_add_dispatch 的断言就会把你踹出来。这也是 24.0.0 那版干脆关掉 -Dopengl 的原因。

十二、易错点速查 #

三条主线记牢，剩下的都是细节。

第一，Panfrost 是内核驱动，mesa 是用户态实现，两者必须配套。

层 版本来源 不配套会怎样
内核 Panfrost 内核版本决定，6.3 里是 1.2.0 太老会缺 ioctl，新 mesa 直接报错
用户态 mesa 自选，21.2.6 / 22.0.0 / 23.0.4 / 24.0.0 与内核或发行版其余部分冲突

内核 5.2 起的 Panfrost 就能跑 T860，mesa 那边 19.2 起支持 Mali。这条链路里最容易出事的是「自编 mesa 覆盖发行版 mesa」，而不是内核驱动。

第二，T860 是 Midgard，走 Panfrost 不走 Lima。 型号与架构的对应关系见第三章那张表，搞错了会发现 /dev/dri 有了但设备名是别的。

第三，OpenCL 要用 rusticl，且必须显式点名。

bash
RUSTICL_ENABLE=panfrost ./your_program
RUSTICL_ENABLE=panfrost clinfo

不带这个环境变量，rusticl 的平台不会激活，你会一直看到 Clover 那个 0 设备的平台，然后误判成「OpenCL 不支持 Mali」。

剩下的零碎坑按顺序检查：

检查项 正确状态
/etc/OpenCL/vendors/ 有 mesa.icd，24.0.0 时有 rusticl.icd
libOpenCL.so 软链 指向 libOpenCL.so.1，缺了就用 ln -s 补
dri/panfrost_dri.so 存在，且与 libGL 出自同一次构建
llvm-config --version 报 11 或 15，与 mesa 配置一致
-Dprefix 自编覆盖系统用 /usr，只想观察就换 /opt/mesa
builddir 编译失败不清空，解决错误后原地重跑
内核镜像打包 mkimage 不带 -E
设备树 status 板级 dts 里是 okay

最后一句：这套东西一次跑通不难，难的是版本对齐。先把 glxinfo -B 那三行盯住，再看 /proc/interrupts 的三个计数，中间那些报错都能顺藤摸瓜找到源头。
