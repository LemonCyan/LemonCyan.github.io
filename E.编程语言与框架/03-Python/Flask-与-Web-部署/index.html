一、Python Web 的两种形态：框架与 WSGI #

一个 Web 应用进门只有三件事：把 URL 分发给对应的函数、从请求里抠出参数、把返回值变成 HTTP 响应。再加一件模板渲染。这四件事自己写一遍，你就是在造框架。

拿 aiohttp 举例，最底层的写法长这样：

python
from aiohttp import web

def index(request):
    return web.Response(body=b"<h1>Awesome</h1>")

app = web.Application()
app.router.add_route("GET", "/", index)

能跑，但业务写起来很啰嗦。每写一个 URL 处理函数，你得重复三遍同样的动作：

python
async def handle_url_xxx(request):
    url_param = request.match_info["key"]
    query_params = parse_qs(request.query_string)
    text = render("template", data)
    return web.Response(body=text.encode("utf-8"))

取路径参数、解查询串、拼 Response。于是有人把这些动作封进装饰器：

python
def get(path):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kw):
            return func(*args, **kw)
        wrapper.__method__ = "GET"
        wrapper.__route__ = path
        return wrapper
    return decorator

有了 @get("/blog/{id}")，处理函数变成 def get_blog(id) 这么干净：路由信息挂在函数属性上，一个 RequestHandler 类负责从 request 解析参数、调用函数、把返回值转成响应对象，最后用 add_routes(app, "handlers") 扫一遍模块自动注册。

再往上，通用的横切逻辑抽成 middleware：

python
async def logger_factory(app, handler):
    async def logger(request):
        logging.info("Request: %s %s" % (request.method, request.path))
        return await handler(request)
    return logger

logger 记一条日志再放行。同理写一个 response_factory，把 str、bytes、dict 统一转成响应，视图函数从此只负责返回数据。

这一段造出来的东西，Flask 早就给你了：路由装饰器、请求对象、响应对象、中间件机制（before_request / after_request）、模板引擎（Jinja2）。你要做的是判断「用现成的还是自己造」。绝大多数业务选现成的。

第二种形态的分界线在服务器接口上，也就是 WSGI 与 ASGI 之争：

形态 接口 并发模型 代表框架 代表服务器
同步 WSGI 进程/线程，一个请求占一个 worker Flask、Django（传统） Gunicorn（sync/gevent）、uWSGI
异步 ASGI 事件循环，一个线程扛大量协程 FastAPI、Starlette、aiohttp Uvicorn、Hypercorn、Daphne

选异步要付代价：一旦决定异步，整条链路都得异步。数据库驱动、HTTP 客户端、缓存客户端全是异步库，中间夹一个同步 IO，事件循环就被堵住，全部请求一起卡。所以 Flask 项目里用 requests、pymysql 没问题；aiohttp / FastAPI 项目里就得换 httpx、aiomysql。开弓没有回头箭，这句话在选型阶段最值钱。

二、Flask 的最小应用 #

装依赖：

bash
pip install flask

最小应用三行就能跑：

python
from flask import Flask

app = Flask(__name__)

@app.route("/")
def index():
    return "Hello, Flask"

if __name__ == "__main__":
    app.run(host="127.0.0.1", port=5000, debug=True)

python app.py 起来，浏览器打开 http://127.0.0.1:5000/ 看到文字。host="0.0.0.0" 才能被局域网访问，127.0.0.1 只监听本机。

新版 Flask 提供了 CLI，不必写 if __name__：

bash
flask --app app run --debug
flask --app app run --host 0.0.0.0 --port 5000

--debug 打开两件事：改动代码自动重载、出错时返回调试器页面。调试器页面带交互式控制台，谁看到谁就能执行代码——生产环境绝对不能开 debug。

Flask(__name__) 里的参数决定 Flask 从哪里找模板和静态文件。传模块名字符串（__name__）就按模块所在目录算根；写成包里的 app 对象，根目录就跟着包走。

Flask 的特点决定了它的用法：

  • 轻。核心只有路由、请求、响应、模板，没有强制的目录结构，也没有内置 ORM。
  • 可拆可合。单文件能跑，几百个接口也能靠蓝图拆开。
  • 扩展化。数据库用 SQLAlchemy，表单用 WTForms，登录用 Flask-Login，迁移用 Flask-Migrate，实时通信用 Flask-SocketIO，邮件用 Flask-Mail。核心不背这些包，按需装。

一个能上生产的入口文件要留出工厂函数的口子，后面蓝图、配置、扩展都靠它装配：

python
def create_app(config=None):
    app = Flask(__name__)
    if config:
        app.config.from_object(config)
    from .views import bp
    app.register_blueprint(bp)
    return app

三、路由与视图函数 #

@app.route() 把 URL 规则绑到视图函数。默认只接受 GET，其他方法一律 405：

python
@app.route("/login", methods=["GET", "POST"])
def login():
    return "ok"

动态段用尖括号，默认转换器是 string（不匹配斜杠）：

python
@app.route("/blog/<int:blog_id>")
def blog(blog_id):
    return f"blog {blog_id}"
转换器 匹配内容 不匹配的情况
string 任意文本，不含 / a/b
int 非负整数 -1、abc、1.5
float 浮点数 abc
path 含 / 的路径 空串
uuid 标准 UUID 字符串 长度不对的串

path 常用来接文件路径：@app.route("/raw/<path:filepath>")。

视图函数返回什么，Flask 就按类型处理：

python
return "text"                              # 200, text/html
return "<h1>hi</h1>", 201                  # 自定义状态码
return {"ok": True}                        # 自动转 JSON
return {"ok": True}, 202                   # JSON + 状态码
return "body", 200, {"X-Trace": "abc"}     # 附带响应头

视图函数名在应用内唯一。同一个名字注册两次，后一个覆盖前一个，而且不报错——改完路由一定用 flask --app app routes 看一眼实际注册表。

反向生成 URL 用 url_for，传的是端点名（默认就是函数名）：

python
@app.route("/blog/<int:blog_id>")
def blog(blog_id):
    return url_for("blog", blog_id=blog_id)     # /blog/7

url_for 比手写字符串强的地方：规则改了不用全局搜索替换；自动处理应用挂在前缀下的情况（APPLICATION_ROOT、蓝图 url_prefix）；自动对参数做 URL 编码。

末尾斜杠的行为要记牢：

规则 请求 结果
/blog /blog 200
/blog /blog/ 404
/blog/ /blog/ 200
/blog/ /blog 308 跳转到 /blog/

带斜杠的规则会做重定向，不带的不做。所以资源集合写 /blogs/，单条资源写 /blogs/<int:id>，行为一致。

请求钩子用来在每个视图前后插入逻辑：

python
@app.before_request
def require_admin():
    if request.path.startswith("/manage/") and not is_admin():
        return redirect(url_for("signin"))

@app.after_request
def add_header(resp):
    resp.headers["X-App"] = "blog"
    return resp

before_request 返回非 None 值会短路，后面的视图不执行，直接拿这个返回值当响应。权限拦截就靠这个特性，比在每个视图里写一遍判断干净。

错误处理按状态码或异常类型注册：

python
@app.errorhandler(404)
def not_found(e):
    return render_template("404.html"), 404

视图内部主动抛错用 abort(404)。

四、请求与响应 #

request 是请求上下文里的代理对象，直接 import 就能用，不用当参数传。数据藏在哪个属性里，取决于前端怎么发：

位置 前端怎么发 Flask 怎么读
查询串 GET /s?q=flask request.args.get("q")
表单 application/x-www-form-urlencoded request.form.get("name")
JSON Content-Type: application/json + body request.get_json()
原始字节 任意 request.data
文件 multipart/form-data request.files["f"]
请求头 Header request.headers.get("X-Token")
Cookie Cookie request.cookies.get("session") 
python
@app.route("/fetch-sub-url", methods=["GET", "POST"])
def fetch_sub_url():
    url = request.args.get("url")
    page = request.args.get("page", "1", type=int)
    return f"{url} {page}"

request.args 是 MultiDict，同名参数出现两次用 getlist：

python
tags = request.args.getlist("tag")      # ?tag=a&tag=b -> ["a", "b"]

读 JSON 有个高频坑。前端没带 Content-Type: application/json 的时候，request.get_json() 直接抛 415。要么让前端带对头，要么容错成 request.get_json(silent=True) or {}。

上传文件：

python
@app.route("/upload", methods=["POST"])
def upload():
    f = request.files["file"]
    if f.filename == "":
        return "empty", 400
    f.save(os.path.join(UPLOAD_DIR, secure_filename(f.filename)))
    return {"ok": True}

secure_filename 必须调用。用户能把文件名写成 ../../etc/passwd，不洗就直接拼路径，等于给自己开后门。

需要精细控制响应时用 make_response：

python
@app.route("/download")
def download():
    resp = make_response("file content")
    resp.headers["Content-Disposition"] = 'attachment; filename="a.txt"'
    resp.headers["Cache-Control"] = "no-store"
    return resp

JSON 接口用 jsonify 或直接返回 dict：

python
@app.route("/api/users")
def api_users():
    users = [{"id": 1, "name": "a"}]
    resp = jsonify(users=users, total=len(users))
    resp.status_code = 200
    return resp

给浏览器种 cookie 用 set_cookie：

python
resp = make_response("ok")
resp.set_cookie("token", value, max_age=86400, httponly=True, samesite="Lax")

httponly=True 让 JS 读不到这个 cookie，XSS 拿到了也偷不走；samesite="Lax" 挡掉绝大多数跨站请求伪造；secure=True 只在 HTTPS 下发送，上线必须加。

跳转和下发文件：

python
return redirect(url_for("signin"))
return send_from_directory(STATIC_DIR, "report.pdf", as_attachment=True)

做服务端转发（替前端拉一次别人的页面再返回）必须加超时，不加超时就是给自己埋超时事故：

python
r = requests.get(url, timeout=5)
return r.text, r.status_code, {"Content-Type": "text/plain"}

return r.text 会被 Flask 当成 text/html 塞给浏览器，等于把别人的 HTML（含脚本）放进自己域名下执行。要么显式指定类型，要么只返回 JSON。

五、模板与静态文件 #

模板放在 templates/，Flask 自动认。渲染用 render_template：

python
@app.route("/blogs/")
def blog_list():
    blogs = query_blogs()
    return render_template("blogs.html", blogs=blogs, title="日志")

模板里拿变量、循环、判断：

html
<h1>{{ title }}</h1>
{% for blog in blogs %}
  <article>
    <h2><a href="/blog/{{ blog.id }}">{{ blog.name }}</a></h2>
    <p>{{ blog.summary }}</p>
  </article>
{% else %}
  <p>还没有日志</p>
{% endfor %}

模板复用两条路。少量局部用 include，整页结构用 extends。父模板 base.html 挖坑：

html
<!DOCTYPE html>
<html>
<head>
  <meta charset="utf-8">
  <title>{% block title %}Blog{% endblock %}</title>
  <link rel="stylesheet" href="{{ url_for('static', filename='css/app.css') }}">
</head>
<body>
  {% block content %}{% endblock %}
</body>
</html>

子模板填坑：

html
{% extends "base.html" %}
{% block title %}日志{% endblock %}
{% block content %}
  <h1>日志</h1>
  <p>{{ blogs|length }} 篇</p>
{% endblock %}

extends 要写在第一行，{% block %} 只能填父模板挖过的坑。多层继承能一直套下去。

自动转义是默认开的。变量里的 <script> 会被转成实体，塞不进 DOM：

写法 结果
{{ text }} HTML 转义后输出
{{ text|safe }} 原样输出，不转义
{{ text|striptags }} 剥掉所有标签

|safe 只给完全可信的内容用。用户提交的富文本想保留标签，先过一遍白名单清洗（bleach 之类）再 |safe。直接 |safe 就是存储型 XSS。

自定义过滤器解决显示问题。时间戳存的是 float，模板里要显示成「几分钟前」：

python
def datetime_filter(t):
    delta = int(time.time() - t)
    if delta < 60:
        return "1分钟前"
    if delta < 3600:
        return "%s分钟前" % (delta // 60)
    if delta < 86400:
        return "%s小时前" % (delta // 3600)
    dt = datetime.fromtimestamp(t)
    return "%s年%s月%s日" % (dt.year, dt.month, dt.day)

app.jinja_env.filters["datetime"] = datetime_filter

模板里写 {{ blog.created_at|datetime }}。时间在数据库里存 float 而不是 datetime，好处是不用管数据库时区、排序是纯数值比较、显示层再做一次转换就行。

常用语法速查：

需求 写法
默认值 {{ name or "匿名" }}
长度 {{ items|length }}
截断 {{ text|truncate(50) }}
循环序号 {{ loop.index }}、{{ loop.index0 }}
拼接静态地址 {{ url_for("static", filename="js/app.js") }}
生成视图地址 {{ url_for("blog", blog_id=1) }}

静态文件放 static/，URL 前缀默认 /static，目录按类型分（css/、js/、img/、fonts/）：

python
app = Flask(__name__, static_folder="static", static_url_path="/static")

开发期静态文件由 Flask 送出，性能无所谓。生产期交给 Nginx 直接吐，Python 进程一个字节都别碰。这条分界线在第十四章展开。

六、蓝图与项目结构 #

单文件撑到十几个接口就开始乱。蓝图的作用是把一组视图打包，挂一个前缀，独立成模块：

python
# views/blog.py
bp = Blueprint("blog", __name__, url_prefix="/blog")

@bp.route("/")
def index():
    return render_template("blog/list.html")

@bp.route("/<int:blog_id>")
def detail(blog_id):
    return render_template("blog/detail.html", blog_id=blog_id)

注册：

python
app = Flask(__name__)
app.register_blueprint(blog_bp)
app.register_blueprint(auth_bp)

注册后端点名变成 蓝图名.函数名，反向生成要带前缀：url_for("blog.detail", blog_id=7) 得到 /blog/7。

蓝图可以重复注册，所以同一个蓝图挂两个前缀做多版本都行，但 name= 不能省，否则重名冲突直接抛异常：

python
app.register_blueprint(blog_bp)
app.register_blueprint(blog_bp, url_prefix="/api/v1", name="blog_v1")

一个能长到几百个接口的目录结构：

text
blogapp/
├── app.py                  # create_app 工厂
├── config.py               # 配置装配
├── config_default.py       # 开发默认配置
├── config_override.py      # 生产覆盖配置
├── requirements.txt
├── models/
├── views/                  # 蓝图：blog.py auth.py api.py
├── templates/              # base.html 与各页面模板
├── static/                 # css/ js/ img/
├── log/
└── tests/

配套的工厂函数：

python
def create_app(env="default"):
    app = Flask(__name__)
    app.config.update(configs[env])

    from views.blog import bp as blog_bp
    from views.auth import bp as auth_bp
    app.register_blueprint(blog_bp)
    app.register_blueprint(auth_bp)
    return app

蓝图里 import app 会成环。所有跨模块共享的东西靠工厂函数注入，或者放进一个 extensions.py：

python
# extensions.py
db = SQLAlchemy()

视图里 from extensions import db，工厂里 db.init_app(app)。这是解循环导入的标准姿势。

七、配置与环境变量 #

app.config 是个字典，所有配置项都往这里塞：

python
app.config["SECRET_KEY"] = "change-me"
app.config["SQLALCHEMY_DATABASE_URI"] = "sqlite:///app.db"

配置来源按优先级叠加，后加载的覆盖前面的：

python
app.config.from_object("config_default")                      # 默认值
app.config.from_pyfile("config_override.py", silent=True)     # 覆盖
app.config.from_envvar("APP_CONFIG", silent=True)             # 环境变量指路

用 Python 文件做配置省掉解析器，config_default.py 直接是模块：

python
# config_default.py
configs = {
    "db": {
        "host": "127.0.0.1",
        "port": 3306,
        "user": "www-data",
        "password": "www-data",
        "database": "awesome",
    },
    "session": {"secret": "AwEsOmE"},
}

生产环境要改的只有几项，单独写 config_override.py，不碰默认文件：

python
# config_override.py
configs = {"db": {"host": "192.168.0.100"}}

装配时深合并，默认值打底，覆盖值压上：

python
# config.py
import config_default

def merge(defaults, override):
    r = {}
    for k, v in defaults.items():
        if k in override:
            r[k] = merge(v, override[k]) if isinstance(v, dict) else override[k]
        else:
            r[k] = v
    return r

configs = {"default": config_default.configs}
try:
    import config_override
    configs["default"] = merge(config_default.configs, config_override.configs)
except ImportError:
    pass

密码不上代码库，走环境变量，os.environ.get 加默认值兜底：

python
app.config["SECRET_KEY"] = os.environ.get("SECRET_KEY", "dev-only")
app.config["DATABASE_URL"] = os.environ.get("DATABASE_URL", "sqlite:///app.db")
app.config["DEBUG"] = os.environ.get("FLASK_DEBUG", "0") == "1"

关键配置项清单：

配置项 作用 生产建议
SECRET_KEY 签名 session、CSRF token 环境变量注入，长度够长，不要提交
DEBUG 调试器、自动重载 必须为 False
SQLALCHEMY_DATABASE_URI 数据库地址 环境变量
MAX_CONTENT_LENGTH 上传体积上限 按业务定，防止被大包打死
PREFERRED_URL_SCHEME url_for 生成的协议 反代后为 https
SESSION_COOKIE_SECURE cookie 只走 HTTPS True
SESSION_COOKIE_HTTPONLY JS 读不到 cookie True
SESSION_COOKIE_SAMESITE CSRF 防护 Lax

SECRET_KEY 泄露等于 session 伪造，所有用户都能被冒充。轮换 key 会让线上已登录用户全部掉线，所以平时就要想好怎么灰度切。

MAX_CONTENT_LENGTH 不设，一个 POST 传 10G 就能把内存打满：

python
app.config["MAX_CONTENT_LENGTH"] = 16 * 1024 * 1024     # 16MB

超限时 Flask 直接返回 413，视图中途不会执行。这个值和 Nginx 的 client_max_body_size 要保持一致，两边不一致时先撞上的那个决定你能传多大。

八、CORS：为什么浏览器会拦跨域请求 #

同源策略是浏览器的限制，不是服务器的。这句话得先钉死。

「同源」= 协议 + 主机 + 端口三者全同。http://127.0.0.1:8080 和 http://127.0.0.1:5000 端口不同，不同源；http://a.com 和 https://a.com 协议不同，不同源；http://a.com 和 http://b.a.com 主机不同，不同源。

浏览器在跨源请求上做两件事：发得出去，但响应不给你的 JS 看。服务器其实收到了请求、正常处理、也返回了 200——只是响应回到浏览器时，浏览器检查响应头里有没有 Access-Control-Allow-Origin 且值匹配当前页面源。没有或对不上，就把响应体丢掉，控制台报一行：

text
Access-Control-Allow-Origin header is missing

所以排查跨域时，看到「请求 200 但前端拿不到数据」，别怀疑后端逻辑，先看响应头。

CORS 就是服务器在响应头里声明「允许哪个源读这个响应」。几个头撑起九成场景：

响应头 作用 示例
Access-Control-Allow-Origin 允许的源，* 表示任意 http://127.0.0.1:8080
Access-Control-Allow-Methods 允许的方法，预检时用 GET, POST, PUT, DELETE
Access-Control-Allow-Headers 允许的自定义请求头 Content-Type, X-Token
Access-Control-Allow-Credentials 允许携带 cookie true
Access-Control-Max-Age 预检结果缓存秒数 600
Access-Control-Expose-Headers 允许 JS 读的响应头 X-Total-Count

Access-Control-Allow-Origin: * 和 Allow-Credentials: true 不能同时用。带 cookie 的请求必须回具体的源，浏览器拒绝 *。

两个坑顺手记下。CORS 不是鉴权：任何网页都能给你发请求，只是读不到响应，有副作用的接口（下单、扣款、改密码）必须自己校验身份和来源，别指望 CORS 挡 CSRF。另一件事，CORS 配对了但回 502/504，那是代理层的事，跟跨域无关。

预检请求：什么时候会多发一个 OPTIONS #

不是所有跨源请求都要预检。满足下面全部条件的是「简单请求」，浏览器直接发：

  • 方法是 GET、HEAD、POST 之一；
  • 请求头只有白名单里的（Accept、Accept-Language、Content-Language、Content-Type、Range 等）；
  • Content-Type 只能是 application/x-www-form-urlencoded、multipart/form-data、text/plain 三者之一。

任意一条不满足，浏览器先发一个 OPTIONS 预检，问服务器「我能不能这么发」。预检拦住的情况按常见度排：

触发条件 例子
方法不是 GET/HEAD/POST PUT、DELETE、PATCH
Content-Type: application/json 前端 fetch 带 JSON body，最常见
带自定义请求头 X-Token、Authorization、X-Requested-With
跨源且 credentials 为 include 带 cookie 的接口

这就是为什么「前后端分离项目里九成的跨域报错都出在 JSON 接口上」：Content-Type: application/json 不在白名单，必然触发预检。

预检请求长这样：

text
OPTIONS /api/users HTTP/1.1
Origin: http://127.0.0.1:8080
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type

服务器要回：

text
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: http://127.0.0.1:8080
Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type, X-Token
Access-Control-Max-Age: 600

Access-Control-Max-Age 让浏览器把这次预检结果缓存 10 分钟，期间同样的请求不再发 OPTIONS。设太小，每个业务请求都搭一个预检，请求量直接翻倍。

预检返回非 2xx（常见是 405），浏览器判定失败，业务请求根本发不出去。所以路由必须允许 OPTIONS——Flask 会自动加，但如果你写了 methods=["POST"]，预检这条就过不去。

九、Flask-CORS 的配置 #

bash
pip install flask
pip install flask-cors

最小用法一行，给所有路由挂上 Access-Control-Allow-Origin: *：

python
from flask_cors import CORS

app = Flask(__name__)
CORS(app)

开发期够用，别拿去上线。按业务收紧，只放开指定的源：

python
CORS(app, origins=["http://127.0.0.1:8080", "http://124.222.246.202"])

带 cookie 时必须显式给源，同时开 supports_credentials：

python
CORS(
    app,
    origins=["http://127.0.0.1:8080"],
    supports_credentials=True,
    allow_headers=["Content-Type", "X-Token"],
    expose_headers=["X-Total-Count"],
    max_age=600,
)

按资源给不同策略，resources 用正则匹配路径：

python
CORS(
    app,
    resources={
        r"/api/*": {
            "origins": ["http://127.0.0.1:8080"],
            "methods": ["GET", "POST", "PUT", "DELETE", "OPTIONS"],
            "allow_headers": ["Content-Type", "X-Token"],
            "max_age": 600,
        },
        r"/public/*": {"origins": "*"},
    },
)

只给某个蓝图开，别在全局开：

python
api = Blueprint("api", __name__, url_prefix="/api")
CORS(api, origins=["http://127.0.0.1:8080"])

只给单个视图开，用装饰器：

python
@app.route("/open/data")
@cross_origin(origins=["http://127.0.0.1:8080"], methods=["GET"])
def open_data():
    return {"ok": True}

cross_origin 要放在 @app.route 下面（离函数更近）。顺序反了不生效，这个坑很静默。

前端从任意子域名访问、源不可枚举时用正则：

python
CORS(app, origins=[r"https?://.*\.example\.com(:\d+)?$"])

匹配逻辑是「整个 Origin 值匹配任一模式」。写成 https?://.* 就退化成全放开，等于没设。

参数 含义 默认
origins 允许的源，列表、字符串、正则 *
methods 允许的方法 全部
allow_headers 允许的请求头 *（跟随请求）
expose_headers 暴露给 JS 的响应头 无
supports_credentials 允许带 cookie False
max_age 预检缓存秒数 无
send_wildcard 回 * 而不是回具体源 False
vary_header 加 Vary: Origin True

vary_header 别关。它让 CDN 和浏览器知道「这个响应跟 Origin 有关，不同源不能复用缓存」。关掉之后，A 源拿到的响应一旦被缓存，就会原样回给 B 源，跨域策略直接失效。

十、手写 CORS 响应头 #

不装扩展也能做，after_request 里补头就行。逻辑完全可见：

python
ALLOWED = {"http://127.0.0.1:8080", "http://124.222.246.202"}

@app.after_request
def add_cors(resp):
    origin = request.headers.get("Origin")
    if origin in ALLOWED:
        resp.headers["Access-Control-Allow-Origin"] = origin
        resp.headers["Access-Control-Allow-Credentials"] = "true"
        resp.headers["Access-Control-Allow-Methods"] = "GET, POST, PUT, DELETE, OPTIONS"
        resp.headers["Access-Control-Allow-Headers"] = "Content-Type, X-Token"
        resp.headers["Access-Control-Max-Age"] = "600"
        resp.headers["Vary"] = "Origin"
    return resp

预检由 Flask 自动路由到对应视图（自动补 OPTIONS），after_request 会给它补上头，所以上面这段能覆盖预检。前提是路由没有把 OPTIONS 排掉。

不想靠自动行为，就显式接住预检，一次性返回 204：

python
@app.before_request
def handle_preflight():
    if request.method == "OPTIONS":
        resp = make_response("", 204)
        origin = request.headers.get("Origin")
        if origin in ALLOWED:
            resp.headers["Access-Control-Allow-Origin"] = origin
            resp.headers["Access-Control-Allow-Methods"] = "GET, POST, PUT, DELETE, OPTIONS"
            resp.headers["Access-Control-Allow-Headers"] = request.headers.get(
                "Access-Control-Request-Headers", "Content-Type"
            )
            resp.headers["Access-Control-Max-Age"] = "600"
        return resp

回显 Access-Control-Request-Headers 最省事：前端要什么就给什么，不用维护白名单。生产上还是固定白名单更稳，回显等于放开了所有自定义头。

手写有两条必须遵守的细节：

  • Access-Control-Allow-Origin 只能有一个值。写成 "http://a.com, http://b.com" 浏览器直接拒；多个源就按 Origin 动态回显一个。
  • 别在 4xx/5xx 上跳过 CORS 头。错误响应没有 CORS 头，前端只能看到 net::ERR_FAILED，看不到你构造的错误消息。这也是用 after_request 的原因——它连错误处理器的输出也会过一遍。

用 curl 直接看头，比翻控制台快：

bash
curl -i -X OPTIONS http://127.0.0.1:5000/api/items \
  -H "Origin: http://127.0.0.1:8080" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type"

十一、开发服务器与生产服务器的差别 #

app.run() 起的是 Werkzeug 自带的开发服务器。它从设计上就不是给生产用的，官方文档在 app.run 一节写得很清楚。

维度 开发服务器 flask run 生产服务器 gunicorn/uwsgi
进程模型 单进程，可选多线程 多进程 master + worker
并发能力 一个请求占一个线程，线程池默认很小 多 worker 并行，可配协程
超时控制 无 有 --timeout，卡住的 worker 被杀掉重启
worker 崩溃 整个服务挂掉 主进程拉起新 worker，服务不断
配置能力 几乎为零 并发、超时、日志、平滑重启全可配
静态文件 由 Python 进程送出 交给 Nginx，Python 不碰
安全 debug 模式暴露交互式控制台 无调试接口
性能 几十 QPS 到顶 单机上千 QPS 起步

单进程是致命伤。一个请求在等数据库，其他请求全排队。更糟的是没有任何超时：一个慢查询能把进程钉死，表现出来就是「网站白屏、连接不超时、也不报错」。

开发服务器还会干两件生产环境不能忍的事：改动代码自动重载（文件监视器会在生产环境重复 fork），以及 debug 模式下把异常堆栈和交互式控制台吐给浏览器。

判断自己有没有误用，看启动日志：

text
WARNING: This is a development server. Do not use it in a production deployment.

看到这行 WARNING 就是开发服务器。生产环境的启动日志应该是 [INFO] Booting worker with pid: xxx。

正确的生产结构是三段：

text
浏览器 → Nginx（80/443，TLS、静态文件、限流）
       → WSGI 服务器（127.0.0.1:8000，跑 Python 应用）
       → Flask app

Nginx 对外，WSGI 服务器只监听回环地址，应用进程只被 WSGI 服务器管理。任何一段都不能省：让 gunicorn 直接对外，等于少一层缓冲，慢请求、恶意大包、TLS 握手全打在 Python 上。

十二、WSGI：应用与服务器之间的约定 #

WSGI 是一份约定，把「应用」和「服务器」解耦。双方只认这一个接口，所以任何 WSGI 应用都能跑在任何 WSGI 服务器上，换服务器不改代码。

约定在应用这一端就是一个可调用对象：

python
def application(environ, start_response):
    status = "200 OK"
    headers = [("Content-Type", "text/plain; charset=utf-8")]
    start_response(status, headers)
    return [b"Hello WSGI"]

三条硬规则：

  • 调用方传两个参数：environ（装着请求一切的字典）和 start_response（回调，用来交状态码和响应头）。
  • 应用先调 start_response(status, headers)，再返回可迭代对象。
  • 返回的可迭代元素必须是 bytes，不能直接返回字符串。

Flask 应用本身就是个 WSGI 可调用对象。Gunicorn 命令 app:app 说的就是「从 app 模块取名为 app 的那个 WSGI app」。

environ 里常用的键：

键 含义
REQUEST_METHOD GET、POST
PATH_INFO 路径，/blog/7
QUERY_STRING ? 后面那段
CONTENT_TYPE / CONTENT_LENGTH 请求体类型与长度
wsgi.input 读请求体的流
HTTP_X_FORWARDED_FOR 原样搬来的请求头，- 变 _，转大写

最后一行是反向代理后必踩的坑：Nginx 转发的 X-Forwarded-For、X-Forwarded-Proto 到了 environ 里是 HTTP_X_FORWARDED_FOR、HTTP_X_FORWARDED_PROTO，但 request.remote_addr 拿到的还是 Nginx 的 127.0.0.1，request.scheme 拿到的还是 http。要 Flask 认这些头，套 Werkzeug 的中间件：

python
from werkzeug.middleware.proxy_fix import ProxyFix

app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1, x_proto=1, x_host=1)

x_for=1 意思是「信任一层代理，从 X-Forwarded-For 里取最后一个 IP」。层数写错就取错，套了 CDN 就写 2。不配这个，日志里全是 127.0.0.1，url_for(_external=True) 生成的全是 http:// 链接，微信回调校验签名也会因为拿不到真实客户端 IP 而失败。

因为 WSGI 就是个函数签名，中间件可以像洋葱一样一层层套，每层接收一个 app、返回一个新的可调用对象。ProxyFix 就是读 environ、改写 environ、再往内层传。

WSGI 的局限是同步：一个请求占一个 worker 直到返回。这就是为什么部署时要开多个 worker 进程，也是为什么 Flask 的并发能力最终靠「进程数 × 每进程线程数」堆出来。

十三、Gunicorn 与 uWSGI #

两者都实现 WSGI，都能跑 Flask。区别在工程成熟度和周边支持。

维度 Gunicorn uWSGI
语言 纯 Python，无编译 C 实现
安装 pip install gunicorn pip install uwsgi，有的环境要编译
配置 命令行参数 + Python 配置文件 ini/xml 配置 + 命令行
进程模型 master + worker master + worker
协程 gevent、eventlet worker gevent、协程支持
协议 HTTP、Unix socket HTTP、uwsgi 协议、FastCGI、WebSocket
上手成本 低 中，参数多
周边支持 Flask 文档推荐 Django 社区用得多

选一个就行，别同时装两套互相打架。新项目选 Gunicorn。

bash
pip install gunicorn
gunicorn -w 4 -b 127.0.0.1:8000 app:app

完整参数：

bash
gunicorn \
  --workers 4 \                      # worker 进程数
  --worker-class sync \              # worker 类型
  --bind 127.0.0.1:8000 \            # 监听地址
  --timeout 30 \                     # worker 超时秒数，超了被杀
  --graceful-timeout 30 \            # 平滑重启的等待时间
  --keep-alive 5 \                   # 长连接保持
  --max-requests 1000 \              # 处理多少请求后重启 worker，防内存泄漏
  --max-requests-jitter 100 \
  --access-logfile logs/access.log \
  --error-logfile logs/error.log \
  --log-level info \
  app:app

worker 数按经验公式 2 * CPU核数 + 1 定，前提是同步 worker、请求里主要是阻塞 IO。4 核机器给 9 个。CPU 密集的接口调小，纯 IO 等待的接口调大或者换协程 worker。

worker 类 并发方式 适用
sync 一线程一请求 默认，代码是同步阻塞的
gthread 线程池 同步代码 + 需要更高并发
gevent 协程（greenlet） 大量 IO 等待，需装 gevent
eventlet 协程 同 gevent，老项目常见

用 gevent 先 pip install gevent，再 --worker-class gevent --worker-connections 1000。别在协程 worker 里跑 CPU 密集代码，一个协程卡住整个 worker。

配置文件比长命令行好维护，存 gunicorn.conf.py：

python
import multiprocessing

bind = "127.0.0.1:8000"
workers = multiprocessing.cpu_count() * 2 + 1
worker_class = "sync"
timeout = 30
graceful_timeout = 30
keepalive = 5
max_requests = 1000
max_requests_jitter = 100
accesslog = "/srv/blogapp/log/access.log"
errorlog = "/srv/blogapp/log/error.log"
loglevel = "info"
proc_name = "blogapp"

bash
gunicorn -c gunicorn.conf.py app:app

重载与停止靠信号，不用 kill -9：

bash
kill -HUP  <master_pid>     # 平滑重载 worker，不中断连接
kill -TERM <master_pid>     # 平滑停止
kill -QUIT <master_pid>     # 快速停止

systemctl reload 背后就是发 HUP。

uWSGI 走 ini：

ini
; uwsgi.ini
[uwsgi]
module = app:app
master = true
processes = 4
threads = 2
socket = 127.0.0.1:8000
chmod-socket = 660
vacuum = true
die-on-term = true
pidfile = /srv/blogapp/uwsgi.pid
logto = /srv/blogapp/log/uwsgi.log

bash
uwsgi --ini uwsgi.ini

die-on-term = true 必须写。默认 uWSGI 忽略 SIGTERM，systemd 停服务时会卡到超时再 SIGKILL，日志里全是「stop operation timed out」。

参数 作用
socket 监听地址，配 Nginx 用 uwsgi_pass
http 直接说 HTTP 协议
processes / threads 进程数 / 每进程线程数
harakiri 请求超时杀进程（对应 gunicorn 的 timeout）
max-requests 请求数上限后重启 worker
buffer-size 请求头缓冲，报 invalid request block size 时调大
stats 开状态端口，配合 uwsgitop 监控

跑起来先自测，别急着接 Nginx：curl -i http://127.0.0.1:8000/ 回 200 且内容对，再往下走。

十四、Nginx 反向代理 #

Nginx 干三件事：终结 TLS、直接吐静态文件、把动态请求转给 WSGI 服务器。Python 进程不处理静态请求，也不处理 TLS 握手。

站点配置放 /etc/nginx/sites-available/blogapp：

nginx
server {
    listen 80;
    server_name blog.example.com;

    root /srv/blogapp/www;
    access_log /srv/blogapp/log/access_log;
    error_log  /srv/blogapp/log/error_log;

    client_max_body_size 16m;

    # 静态资源直出，不走 Python
    location /static/ {
        alias /srv/blogapp/www/static/;
        expires 30d;
        access_log off;
    }

    location = /favicon.ico {
        alias /srv/blogapp/www/static/favicon.ico;
        access_log off;
        log_not_found off;
    }

    # 动态请求转发
    location / {
        proxy_pass         http://127.0.0.1:8000;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_redirect     off;

        proxy_connect_timeout 10s;
        proxy_read_timeout    60s;
    }
}

proxy_read_timeout 要大于应用的响应时间，但别大到失去意义。默认 60s，接口里跑长任务就调大，反过来它也是「请求卡住」的第一处检查点。

指令 作用 配错的表现
listen 监听端口 80 被占，服务起不来
server_name 匹配域名 不匹配就落到默认 server
root / alias 文件根目录 alias 要写到目录级，少个斜杠就 404
location 路由匹配 = 精确、^~ 前缀优先、~ 正则
proxy_pass 转发目标 末尾带 / 会改写路径
proxy_set_header 传原始头 不传 Host，应用生成的链接全错
client_max_body_size 请求体上限 默认 1m，超了报 413
expires 缓存时间 静态资源不带缓存，每次都回源

proxy_pass 末尾斜杠的差别必须记牢：

nginx
# 后端收到的路径是 /static/a.css
location /static/ { proxy_pass http://127.0.0.1:8000; }

# 后端收到的路径是 /a.css（/static/ 被替换掉）
location /static/ { proxy_pass http://127.0.0.1:8000/; }

启用站点用软链接，别直接改 sites-enabled：

bash
sudo ln -s /etc/nginx/sites-available/blogapp /etc/nginx/sites-enabled/blogapp
sudo nginx -t
sudo systemctl reload nginx

nginx -t 是硬规矩。配置语法错的时候 reload 会失败但旧进程继续跑，不测就上线等于闭眼改生产。

十五、HTTPS 与证书 #

配 HTTPS 只要两样东西：证书链（fullchain.pem）和私钥（privkey.pem）。证书从 CA 申请，Let's Encrypt 免费且能自动续期。

bash
sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d blog.example.com

certbot 会自己改 Nginx 配置、加 443 监听、加 80 跳转、装续期定时器。手动模式只申请证书不改配置：

bash
sudo certbot certonly --webroot -w /srv/blogapp/www -d blog.example.com

证书落在 /etc/letsencrypt/live/blog.example.com/，四个文件的分工：

文件 用途 配到哪
fullchain.pem 服务器证书 + 中间证书 ssl_certificate
privkey.pem 私钥 ssl_certificate_key
chain.pem 中间证书 很少单独用，fullchain 已含
cert.pem 只有服务器证书 一般不用

只配 cert.pem 是常见错误：部分客户端拿不到中间证书，报「证书链不完整」。

nginx
server {
    listen 443 ssl http2;
    server_name blog.example.com;

    ssl_certificate     /etc/letsencrypt/live/blog.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/blog.example.com/privkey.pem;

    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 10m;

    add_header Strict-Transport-Security "max-age=31536000" always;

    root /srv/blogapp/www;
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

server {
    listen 80;
    server_name blog.example.com;
    return 301 https://$host$request_uri;
}

走 HTTPS 之后，应用侧还有三件事要跟上：

python
app.config["PREFERRED_URL_SCHEME"] = "https"
app.config["SESSION_COOKIE_SECURE"] = True
app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1, x_proto=1, x_host=1)

不配 ProxyFix，request.scheme 永远是 http，url_for(_external=True) 生成 http:// 链接，浏览器在 HTTPS 页面里加载这些资源会被当成混合内容拦掉。

HSTS 头一旦下发，浏览器在 max-age 期间强制走 HTTPS，中途想退回 HTTP 都退不了。本地测试环境别加，先确认证书链没问题再加。

续期靠 certbot 的定时器，验证一下：

bash
sudo systemctl status certbot.timer
sudo certbot renew --dry-run

--dry-run 走一遍完整流程但不换证书，能过就说明续期没问题。

十六、进程管理与开机自启 #

裸跑 gunicorn 的进程，机器重启就没了，进程崩了也没人拉。systemd 负责这件事。

单元文件放 /etc/systemd/system/blogapp.service：

ini
[Unit]
Description=Blog Backend With Flask
After=network.target

[Service]
Type=simple
WorkingDirectory=/srv/blogapp/www
ExecStart=/srv/blogapp/venv/bin/gunicorn -c /srv/blogapp/gunicorn.conf.py app:app
User=www-data
Group=www-data
Environment="PYTHONPATH=/srv/blogapp/venv/lib/python3.10/site-packages"
Environment="APP_ENV=production"
Restart=always
RestartSec=3
KillSignal=SIGTERM
TimeoutStopSec=30

[Install]
WantedBy=multi-user.target
配置 含义 写错的后果
After=network.target 网络就绪后再起 启动时连不上数据库
Type=simple ExecStart 是前台进程 Type=idle 只适合脚本，配 gunicorn 会误判
WorkingDirectory 工作目录 相对路径全错，模板找不到
ExecStart 启动命令，必须绝对路径 写 gunicorn 报 No such file
User / Group 运行身份 用 root 跑，权限放大
Environment 环境变量 PYTHONPATH 不设就 import 失败
Restart=always 崩溃自动拉起 崩了就真崩了
RestartSec 重启间隔 设 0 会疯狂重启刷日志
TimeoutStopSec 停止等待 比应用平滑退出的时间短会被强杀

ExecStart 里必须用虚拟环境里的绝对路径。service 不读你 shell 的 PATH。

bash
sudo cp blogapp.service /etc/systemd/system/
sudo systemctl daemon-reload          # 改了 unit 文件必须执行
sudo systemctl enable blogapp         # 开机自启
sudo systemctl start blogapp
sudo systemctl status blogapp
sudo systemctl restart blogapp

daemon-reload 是最容易漏的一步：改完 unit 文件不 reload，start 用的还是旧配置，表现出来就是「我明明改了但没生效」。

看日志走 journald：

bash
sudo journalctl -u blogapp -f
sudo journalctl -u blogapp --since "10 min ago"

应用自己往文件写日志时，unit 里就不用再配 StandardOutput，两边都配会让日志分裂到两个地方。同一台机器只能有一个进程管理工具管同一个进程，supervisor 和 systemd 二选一。

十七、日志与监控 #

默认日志在生产环境没用：级别太低、没有文件、不轮转、没有请求耗时。三处日志分开配。

应用日志走 Flask 的 logger：

python
from logging.handlers import RotatingFileHandler

def setup_logging(app):
    handler = RotatingFileHandler(
        "/srv/blogapp/log/app.log", maxBytes=50 * 1024 * 1024,
        backupCount=10, encoding="utf-8",
    )
    handler.setFormatter(logging.Formatter(
        "%(asctime)s %(levelname)s [%(module)s:%(lineno)d] %(message)s"
    ))
    handler.setLevel(logging.INFO)
    app.logger.setLevel(logging.INFO)
    app.logger.addHandler(handler)

要让日志带上请求信息，加一对钩子：

python
@app.before_request
def start_timer():
    g._start = time.time()

@app.after_request
def log_request(resp):
    cost = (time.time() - g._start) * 1000
    app.logger.info(
        "%s %s %s %.1fms", request.method, request.path, resp.status_code, cost
    )
    return resp

没有耗时字段的访问日志等于没有。排查「慢」的时候，你只能靠猜。

WSGI 服务器日志单独配，Gunicorn 用 accesslog / errorlog。访问日志格式含 %({x-forwarded-for}i)s 才能拿到真实客户端 IP：

python
access_log_format = '%({x-forwarded-for}i)s %(t)s "%(r)s" %(s)s %(b)s %(L)s'

日志无限增长会撑爆磁盘。应用自己用 RotatingFileHandler 轮转，Gunicorn 和 Nginx 的日志交给 logrotate：

text
/srv/blogapp/log/*.log {
    daily
    rotate 14
    missingok
    notifempty
    compress
    delaycompress
    sharedscripts
    postrotate
        systemctl reload nginx > /dev/null 2>&1 || true
    endscript
}

放 /etc/logrotate.d/blogapp。Nginx 重新打开日志句柄必须 reload，否则它一直往删掉的旧 inode 写，磁盘空间不放。

监控从两个探针做起：

python
@app.route("/healthz")
def healthz():
    return {"status": "ok"}, 200

@app.route("/readyz")
def readyz():
    try:
        db.session.execute("SELECT 1")
    except Exception:
        app.logger.exception("db not ready")
        return {"status": "db down"}, 503
    return {"status": "ok"}, 200

healthz 只证明进程活着，readyz 证明依赖可用。负载均衡和 systemd 用前者，发布流程用后者。

要看的是四个数：QPS、P95 延迟、5xx 比例、worker 数。前三个判断业务健康，第四个判断进程健康——worker 一直按 --max-requests 的节奏重启，说明有内存泄漏。uWSGI 有现成状态端口（stats = 127.0.0.1:1717，配 uwsgitop 看），Gunicorn 靠探针加进程监控。

十八、常见部署故障 #

按「浏览器看到什么」倒推，比按日志猜快。

现象 常见原因 定位方式
502 Bad Gateway WSGI 服务器没起、端口错、socket 权限 curl 127.0.0.1:8000；查 error_log
504 Gateway Timeout 应用响应超过 proxy_read_timeout 调大超时；查日志里的慢请求
静态资源 404 root 与 alias 用错、路径多一层 curl -I /static/app.css 看实际路径
413 Request Entity Too Large 超过 client_max_body_size 同步调大 Nginx 与 MAX_CONTENT_LENGTH
401/403 全站 目录权限、User 与文件属主不一致 ls -l 看属主；sudo -u www-data cat 试读
502 且日志 Permission denied Unix socket 权限 chmod-socket = 660，或改用 TCP 回环
ModuleNotFoundError PYTHONPATH 没配、venv 没激活 which python、unit 里的 ExecStart
页面白屏 DEBUG=False 掩盖了异常 看 error.log，别为排查开 debug
响应头里 Allow-Origin 出现两次 Nginx 和 Flask 各加了一遍 只在一层加
上传大文件后进程被杀 内存不够，worker 被 OOM 看 dmesg，调 max_requests 和 body 上限
改了代码不生效 没重启、漏了 daemon-reload、软链接没换 看 systemctl show -p ExecMainStartTimestamp

「502 排查五步」值得背下来：

bash
systemctl status blogapp                              # 1. 进程活着吗
ss -lntp | grep 8000                                  # 2. 端口在听吗
curl -i http://127.0.0.1:8000/healthz                 # 3. 直连后端通吗
sudo nginx -t                                         # 4. 配置对吗
sudo tail -50 /var/log/nginx/error.log                # 5. 谁在报错

「部署后样式全丢」是另一个高频场景，八成是这三件事：

  • location /static/ 用了 root 而不是 alias，实际去找 /srv/blogapp/www/static/static/；
  • 部署打包的 includes 漏了 static，静态目录根本没上传；
  • 软链接换了但 Nginx 有 open_file_cache，需要 reload 才认新目录。

先确认请求到底打到了哪个进程。在视图里临时回一行版本号，比对着配置文件猜半小时快得多：

python
@app.route("/version")
def version():
    return {"build": BUILD_ID, "pid": os.getpid()}
