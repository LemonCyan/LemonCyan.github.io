VibePrompt
  • C — Concise（精簡）：直奔主題，砍掉廢話。
  • L — Logical（有邏輯）：拆成步驟或條列，先做 A 再做 B。
  • E — Explicit（明確）：講清楚要／不要、輸出格式、範例。
  • A — Adaptive（可調整）：不滿意就迭代指示「在哪裡改」。
  • R — Reflective（反思）：做完請 AI 總結，把成功做法存成模板。

第一原则 #

不要告诉 AI「怎么做」，告诉 AI「什么算好」。你要给的不是“任务”，而是 评价标准。工程能力 = 判断力，而不是实现力

❌ 传统写法（非 Vibe）：

“用 Python 写一个日志分析工具，支持过滤和统计。”

问题是：

  • 太宽
  • AI 会随意发挥
  • 结果像教程代码

要素 #

  1. ✅ 明确角色
  2. ✅ 明确长期维护
  3. ✅ 点出了架构约束，而不是实现细节
    • 核心框架稳定
    • 变化点外置
    • 模块边界

① 角色（你希望它是谁） #

  • 不是：你是 AI。
  • 而是：你是一个有 5 年经验的 Python 工具链工程师

② 使用场景（什么时候用） #

  • 不是：写一个工具。
  • 而是：这是一个每天要用的命令行工具

③ 厌恶点（你不想看到什么） #

这是最重要的部分。比如：

  • 不要一堆 if-else
  • 不要所有逻辑写在 main
  • 不要难以测试

④ 成功标准（什么叫“对了”） #

比如：

  • 目录结构一眼就懂
  • 新功能不用改老代码
  • 没用到的东西不要出现

示例 #

你不用现在就跑，先感受语言的差别：

你是一个经验丰富的 Python CLI 工具作者。
这个工具会被我长期使用和维护。
我讨厌臃肿的结构、示例式代码和把所有逻辑堆在 main 里。
请设计一个清晰、可扩展、易测试的项目结构，用于分析日志文件。
如果将来要增加新的分析规则，不应该修改已有核心代码。

校准阶段-否定法则 #

不是让 AI 更努力，而是让 AI 更克制。我们要做的不是推翻一切，而是精准压制它的坏习惯。

  • 用 “否定约束版 Prompt”
  • 再生成一次项目结构

一般的 4 个高频原因 #

  • 模块名“看起来对，但味道不对”
    • core
    • common
    • utils
    • base
  • 框架感太重，但业务感太弱
    • 有 framework
    • 有 plugin
    • 但不知道业务到底从哪开始
  • 项目像 Java / Python
    • 目录抽象过度
    • 生命周期不清晰
    • 边界模糊
  • 扩展点是“理论上的”
    • 说是插件
    • 但看不出 怎么加一个新设备

「否定模板」 #

因为 AI 默认会：

  •   教学化
  •   抽象过度
  •   用 core / common / utils 糊你
  • “我不希望看到 core / common / utils 这种模糊模块”
  • “我不希望这是一个‘框架先行’的项目”
  • “我不希望这是‘看起来可扩展，但不知道怎么用’的设计”
  • “我不希望 Qt 项目被设计成非 Qt 风格”

System 和 User #

system = 不能被用户推翻的规则
user = 本次要做的具体事情

因为大模型在内部会做一件事：优先级排序。大致是：

system > developer > user

  • 用 system 塑造 AI 的人格
  • 用 user 驱动具体产出
  • 多轮生成时保持风格一致
你想写的内容 放哪 原因
身份 / 风格 system 长期约束
架构原则 system 不可动摇
输出格式 system 防止跑偏
这次做什么 user 每次不同
这次偏好 user 可被覆盖
临时示例 user 不影响规则

system 世界观 + 行为边界 #

  • system 是用来定义：
    • 你是谁（身份）
    • 你要用什么风格思考
    • 什么是绝对不能做的
    • 输出必须遵守的格式
  • system 的特点
    • 一次定义，长期生效
    • 用户说了也不能改
    • 决定“这是不是工程级输出”

user 这一次要干什么 #

  • user 的作用是：
    • 描述本次需求
    • 描述变化
    • 描述当前目标
  • user 的特点
    • 每次都可以变
    • 是“请求”，不是“规则”
    • 不能破坏 system 里定的边界

推荐拆法 #

  • system（长期固定） 你是一个有丰富工程经验的 Qt/C++ 高级开发工程师。 你擅长设计可长期维护的工程结构。 你厌恶示例式代码、臃肿结构和模糊模块。 你强调稳定核心与可扩展边界。 你的输出必须是工程级的项目结构。
  • user（每次变化） 请设计一个网络连接状态检测工具。 需要支持多种设备、IP 和网址。 本次重点是结构清晰，而不是功能完整。

其他 #

不要把这些放进 user：

  • “你要像一个资深工程师一样”
  • “请注意架构设计”
  • “不要写示例代码” 👉 因为 user 是弱约束 。模型在复杂任务下会忽略它 当你犹豫一句话该放哪时，问自己：「这句话 3 个月后还成立吗？」
  • 是 → system
  • 否 → user 这个判断 永远不会错。

双层 Prompt 模板 #

System Prompt（长期不变） #

  • System 的职责只有 4 个：
    1. 身份（你是谁）
    2. 价值观 / 审美
    3. 架构原则
    4. 输出硬约束

⚠️ System 里 不出现具体业务
⚠️ 不写“这次要做什么”

cpp
prompt:
你是一个有丰富工程经验的 Qt / C++ 高级开发工程师，遵循以下原则： 
	- 设计可长期维护、可演进和持续扩展的软件工程结构
	- 核心框架应保持稳定 
	- 重视模块边界、职责清晰和扩展点设计
	- 反感示例式代码、臃肿结构和模糊模块（如 core / common / utils）
	- 变化点必须外置，通过模块或插件扩展 
	- 新功能不应修改已有核心代码 
	- 结构应一眼能看出职责划分  
你的输出必须是工程级项目设计，而不是教学示例。你避免以下设计
	- 模糊职责的通用模块（core / common / utils）
	- 为了扩展而扩展的空壳插件
	- 仅在文档中存在、但无法直观使用的扩展点
	- 把业务流程隐藏在抽象层之后

User Prompt（每次变化） #

  • User 只回答 3 个问题：
    1. 现在要做什么？
    2. 关注点是什么？
    3. 这次的限制是什么？
cpp
项目用途： 
	（这是干嘛的）  
本次关注点： 
	（结构 / 扩展性 / 可测试性 / 性能 等）  
额外约束： 
	（这次特别在意的点）


项目用途： 开发一款网络连接状态检测工具，用于检测设备、IP 和网址的可达性。  
本次关注点： 项目结构设计，强调模块解耦和扩展边界清晰。  
额外约束： 新增设备类型或检测规则时，不应修改核心模块。

多轮演化 #

  •   同一个 system
  •   user 一次次修正
  •   项目逐步进化

第 1 轮（只看结构）

text
项目用途：
网络连接状态检测工具
本次关注点：
模块边界与扩展方式
额外约束：
新增检测对象不修改核心

第 2 轮（针对“别扭点”）

text
在上一次设计的基础上：
我不希望出现模糊职责的模块；
希望能一眼看出检测流程从哪里开始，到哪里结束。

👉 这是审美修正，不是需求变更

第 3 轮（确认稳定点）

text
请明确哪些模块是稳定核心，
哪些是预期会频繁变化的扩展点。

👉 你在逼 AI 显式表达架构意图

判断标准 = 当你发现自己开始说：“这个结构我能接受长期维护”说明结构阶段结束。
