LAMP 与 LNMP 环境搭建与全栈运维管理

在 Web 基础设施与服务器运维领域，LAMP（Linux + Apache + MySQL/MariaDB + PHP）与 LNMP（Linux + Nginx + MySQL/MariaDB + PHP）是历经数十年检验的两大经典技术栈。理解两者的底层差异、掌握生产级搭建流程、调优核心性能参数并具备全套故障排查能力，是每一位服务器运维与全栈开发工程师的必备功底。

1. 架构深度解析：LAMP vs LNMP

1.1 核心组件与工作模型对比

评估维度 LAMP (Apache) LNMP (Nginx) 生产选型建议
并发模型 传统多进程 (Prefork) 或多进程+多线程 (Worker/Event) 单线程多进程异步非阻塞事件驱动模型 (epoll/kqueue) 高并发、高连接数场景首选 LNMP
静态资源性能 资源开销相对较大，每个连接占用固定线程/进程 内存极度轻量，零拷贝 (sendfile)，静态吞吐量极大 静态网站、大文件下载、高频小资源直连选 LNMP
动态 PHP 处理 支持 mod_php 嵌入式模块（免 IPC 开销）或 mod_proxy_fcgi 仅支持通过 FastCGI 协议代理至独立的 PHP-FPM 进程 需要精细化控制 PHP 资源池时选 LNMP
配置灵活性 支持目录级 .htaccess 运行时动态覆盖，无需重启服务 所有规则必须写在主配置文件中，修改需 reload 多租户、虚拟主机平台用 Apache；高性能自营选 Nginx
模块热加载 支持 DSO（Dynamic Shared Objects）动态扩展 传统 Nginx 需编译内置（现代 Nginx 支持部分动态模块） 追求极端稳定性选 Nginx，频繁改动模块选 Apache
内存占用 随并发量线性增长，高并发时内存压力大 极低（数万并发仅占用数十兆至数百兆内存） 内存有限的低配 VPS（如 1G/2G）强烈推荐 LNMP

1.2 PHP 运行模式剖析：mod_php vs PHP-FPM

  1. mod_php（Apache 专用）：
    • 将 PHP 解释器作为 Apache 的子模块编译进 Web 服务器进程。
    • 优点：无需跨进程网络/套接字通信，单次调用延迟极低。
    • 致命缺点：即使请求一张纯静态图片，Apache 派生的进程依然携带整个 PHP 解释器，白白浪费海量内存。
  2. PHP-FPM（FastCGI Process Manager，Nginx & Apache 推荐）：
    • PHP 作为独立的服务守护进程运行，管理一个动态或静态的工作进程池（Worker Pools）。
    • 优点：Web 服务器与应用解释器彻底解耦。静态资源全部由 Nginx 极速处理，动态请求才通过 Unix Domain Socket 转发给 PHP-FPM，资源利用率提升数倍。

10. 常见故障排查表

故障现象 根因分析 针对性排查手段
502 Bad Gateway PHP-FPM 未启动、进程崩溃或 Socket 路径与 Nginx fastcgi_pass 不一致 检查 systemctl status php*-fpm，核对 Socket 文件权限及路径
504 Gateway Time-out 后端 PHP 脚本执行超时或数据库发生死锁阻塞 检查 php.ini 中的 max_execution_time，调大 Nginx fastcgi_read_timeout
File not found (404) Nginx 的 SCRIPT_FILENAME 参数传递错误，找不到 PHP 文件 检查 fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
Too many connections MySQL 并发连接数超出 max_connections 阈值 临时调大 SET GLOBAL max_connections = 500;，排查慢查询或长连接泄漏
413 Request Entity Too Large 上传的文件体积超过了 Nginx 默认的 1MB 限制 在 Nginx 配置中增加 client_max_body_size 64M; 并同步修改 upload_max_filesize
