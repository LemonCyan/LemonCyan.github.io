Git 服务器搭建与运维 #

一个「Git 服务器」剥掉外壳只有两样东西：仓库数据（若干裸 .git 目录，自包含、内容寻址）和传输通道（SSH / HTTP / Web 平台）。通道可以随便换，数据永远搬得走——想通这一点，选型和迁移就不再纠结。

本文合并了原先的「Git 服务器环境搭建和客户端使用」「GitServer 部署与运维使用手册」「Git 服务器实施方案（Windows / OpenSSH）」三篇，并吸收了「Gitea 自建私有 Git 服务器部署指南」「GitLab 部署」中的实施细节与避坑条目。

零、先选型：四条路，按"要不要 Web 界面"分叉 #

text
要不要 Web 界面（浏览代码 / PR / Issue / 权限管理）？
├── 不要 → 方案 A：OpenSSH + 裸仓库（几十 MB 内存，零额外软件）
└── 要
    ├── 资源很小（512MB~2GB，个人 / 小团队 / NAS）→ 方案 B：Gitea / Forgejo
    └── 企业级多团队、要完整 DevOps 流水线（≥8GB）→ 方案 C：GitLab CE
对比项 A. OpenSSH + 裸仓库 B. Gitea C. GitLab CE
额外软件 无（系统自带 SSH） 单个 Go 二进制 / 一个容器 一大套 Ruby + PostgreSQL + Redis + Sidekiq
常驻内存 < 10 MB 50 ~ 150 MB 4 ~ 8 GB+
Web 界面 无 轻量 GitHub 体验（代码浏览、PR、Issue、Wiki、Actions） 全功能
数据库 无 自带 SQLite 或用 MySQL/PostgreSQL 必须 PostgreSQL
维护成本 近乎为零 换二进制 + 重启 跟版本、跑迁移、盯内存
迁移成本 极低（拷目录即可） 中（dump 后要改 app.ini 里的地址） 高
适合 自动化同步通道、极简私有仓库、教学 绝大多数自建场景 上百人以上的团队

第一性原理：Git 仓库没有"中心注册表"，一个 .git 目录就含全部历史与分支。所以"服务器"只是"一块能 ssh 进来的磁盘 + 一个会调 git-receive-pack 的 shell"。方案 A 之所以值得作为默认起点，正是因为它是这个定义的直译；需要 Web 时再在其上套 Gitea 也不冲突。

一、方案 A：裸仓库 + SSH #

1.1 为什么是裸仓库 #

text
普通仓库：  my-project/
              ├── .git/        ← 版本库（对象库 + 引用）
              └── 工作区文件    ← 可以编辑
裸仓库：    my-project.git/
              └── objects/  refs/  HEAD  config  hooks/
                  （没有工作区）

服务端不需要检出文件给人改，只需要被 push / fetch，所以用 --bare。好处是没有工作区就不会出现"服务器上有人直接改文件导致 push 冲突"，坏处是不能在服务端直接看代码——要看得 clone 出来。

钩子（hooks/）在裸仓库里反而是主角：post-receive 可以在收到 push 后把代码检出到网站目录，这就是"推送即部署"。

1.2 Linux：git-shell + authorized_keys（最小实现） #

bash
# 1) 装 git
sudo apt update && sudo apt install -y git

# 2) 建专职账号，登录 shell 锁死为 git-shell（关键：禁止交互式登录）
sudo adduser --system --shell "$(which git-shell)" --group --disabled-password --home /home/git git
which git-shell | sudo tee -a /etc/shells

# 3) 公钥
sudo mkdir -p /home/git/.ssh && sudo touch /home/git/.ssh/authorized_keys
echo "ssh-ed25519 AAAA... you@laptop" | sudo tee -a /home/git/.ssh/authorized_keys
sudo chmod 700 /home/git/.ssh
sudo chmod 600 /home/git/.ssh/authorized_keys
sudo chown -R git:git /home/git/.ssh

# 4) 建裸仓库
sudo mkdir -p /srv/git
sudo git init --bare /srv/git/my-project.git
sudo chown -R git:git /srv/git && sudo chmod -R 775 /srv/git

客户端：

bash
git clone git@<server>:/srv/git/my-project.git
cd my-project && echo "# hi" > README.md
git add . && git commit -m "init" && git push -u origin main

若沿用普通用户（老教程里的 /home/git + 改 /etc/passwd 把 shell 换成 /usr/bin/git-shell），要点完全一样：shell 必须是 git-shell，公钥目录权限必须是 700/600。权限多一位，OpenSSH 就静默拒绝加载 authorized_keys，表现是"公钥配了还让输密码"。

每新建一个仓库，最后一步都是 chown -R git:git <仓库>，忘了就是"推送时报 permission denied"。

1.3 Windows：OpenSSH Server + 目录联接 #

Windows 上没有 Gitea 又想长期跑，最省事的做法是用系统自带的 OpenSSH Server，直接把 D:\GitServer\repos 暴露成 ssh://host/c/GitServer/repos/xxx.git。

目录设计（这一步是整个"可迁移"设计的核心）

text
D:\GitServer\            ← 真实数据盘
    ├── repos\           ← 所有裸仓库
    ├── config\          ← sshd_config 原件、脚本
    └── backup\          ← 镜像备份
C:\GitServer\            ← 逻辑入口（Junction，指向 D:\GitServer）

所有 clone 地址、钩子脚本一律写 C:\GitServer\...。将来数据搬到 E 盘，只重建联接，所有客户端零改动。

powershell
# 1) 安装 OpenSSH Server（管理员 PowerShell）
Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Start-Service sshd
Set-Service -Name sshd -StartupType Automatic
Get-Service sshd | Format-Table Name, Status, StartType
#  若报 0x800f0954（WSUS 禁了可选功能）：改用「设置 → 系统 → 可选功能 → 添加功能 → OpenSSH 服务器」

# 2) 目录 + 联接
New-Item -ItemType Directory -Force -Path 'D:\GitServer\repos','D:\GitServer\config','D:\GitServer\backup'
New-Item -ItemType Junction -Path 'C:\GitServer' -Value 'D:\GitServer'
cmd /c dir C:\GitServer

sshd_config（C:\ProgramData\ssh\sshd_config，注意不是 Program Files）

ini
Port 22
PubkeyAuthentication yes
AuthorizedKeysFile .ssh/authorized_keys
PasswordAuthentication yes          ; 先开着，验收通过后再改 no

powershell
Copy-Item 'C:\ProgramData\ssh\sshd_config' 'D:\GitServer\config\sshd_config.orig' -Force
Get-Content 'C:\ProgramData\ssh\sshd_config' | Select-String 'Match Group|AuthorizedKeysFile'
Restart-Service sshd

最坑的一条：文件末尾若有未注释的 Match Group administrators / AuthorizedKeysFile __PROGRAMDATA__/ssh/administrators_authorized_keys， 管理员账号会改从 C:\ProgramData\ssh\administrators_authorized_keys 读公钥，你放在用户目录的公钥完全失效——表现就是反复要密码。二选一：注释掉（用用户目录），或保留并把公钥写进 administrators_authorized_keys 再严格设 ACL。不要两个都配。

公钥与 ACL

powershell
$ak = "$env:USERPROFILE\.ssh"
New-Item -ItemType Directory -Force -Path $ak
New-Item -ItemType File -Force -Path "$ak\authorized_keys"
Add-Content -Path "$ak\authorized_keys" -Value 'ssh-ed25519 AAAA... you@laptop' -Encoding UTF8

icacls.exe "$ak\authorized_keys" /inheritance:r
icacls.exe "$ak\authorized_keys" /grant "SYSTEM:(F)" "Administrators:(F)" "$env:USERNAME:(R)"
icacls.exe "$ak\authorized_keys"

输出里不能出现 Users、Everyone、Authenticated Users——只要有一个组有写权限，OpenSSH 就静默拒绝。这是"公钥无效"的第一命中项。

建仓库与客户端

bash
git init --bare C:/GitServer/repos/demo.git            # 单人或统一账号
git init --bare --shared C:/GitServer/repos/team.git   # 多人共享（组可写）

text
# 客户端 ~/.ssh/config
Host git-server
    HostName PC                 # 用主机名，别写 DHCP 会变的 IP
    User liuluhua
    Port 22
    IdentityFile ~/.ssh/id_ed25519

bash
git clone ssh://git-server/c/GitServer/repos/demo.git
# 拆开看：ssh:// + 主机别名 + /c/GitServer/repos/仓库名.git
# 盘符小写 c，路径用正斜杠

主机名而非 IP、逻辑入口而非真实盘符——这两条能在"IP 变了""换盘了"时救你一次。

1.4 验收（按顺序跑，任一项失败先停） #

bash
ssh git-server                                  # T1 免密登录，不应提示输密码
ssh git-server "where git"                      # T2 服务端解析到官方 git，不是便携版
ssh git-server "dir C:\GitServer\repos"         # T3 服务端能看到仓库目录
git clone ssh://git-server/c/GitServer/repos/demo.git /tmp/t1                        # T4 克隆
cd /tmp/t1 && echo hi > a.txt && git add . && git commit -m t && git push            # T5 推送
git clone ssh://git-server/c/GitServer/repos/demo.git /tmp/t2 && cd /tmp/t2 && git log --oneline -1   # T6 另一处取回

T1~T6 全绿之后，才回头把 PasswordAuthentication 改成 no 并重启 sshd，然后重跑 T1 确认还能进。

先开密码、后关密码。反过来一旦密钥配错，你就把自己锁在门外了。

二、方案 A 的运维：钩子、备份、瘦身、迁移 #

2.1 post-receive：推送即部署 #

bash
#!/usr/bin/env bash
# /srv/git/my-project.git/hooks/post-receive
TARGET_BRANCH="main"
DEPLOY_DIR="/var/www/my-website"
GIT_DIR="/srv/git/my-project.git"

while read -r oldrev newrev ref; do
    BRANCH=$(git rev-parse --symbolic --abbrev-ref "$ref")
    if [ "$BRANCH" = "$TARGET_BRANCH" ]; then
        echo "==> 检出 $TARGET_BRANCH 到 $DEPLOY_DIR"
        mkdir -p "$DEPLOY_DIR"
        git --work-tree="$DEPLOY_DIR" --git-dir="$GIT_DIR" checkout -f "$TARGET_BRANCH"
        chown -R www-data:www-data "$DEPLOY_DIR"
        # cd "$DEPLOY_DIR" && npm ci && npm run build
        # systemctl reload nginx
        echo "==> 上线完成"
    else
        echo "==> 分支 $BRANCH 非发布分支，跳过"
    fi
done

bash
sudo chmod +x /srv/git/my-project.git/hooks/post-receive

三个必须知道的点：

  1. 钩子脚本必须 LF 换行。Windows 下用记事本写成 CRLF，会报 /bin/sh^M: bad interpreter。
  2. 钩子是在服务端跑的任意代码，能以 push 者的权限执行任何命令——多人共享服务器时要收紧 hooks/ 目录权限（chown root + 不可写）。
  3. checkout -f 会丢弃目标目录的本地修改，部署目录里不要放手工改过的文件。

2.2 备份：镜像克隆 + 定时 #

bash
# 单仓库镜像（不是普通 clone，含所有分支/标签/引用）
git clone --mirror /srv/git/my-project.git /backup/my-project.git

# 之后每次增量更新
cd /backup/my-project.git && git remote update

bash
# /root/scripts/backup_gitserver.sh
BACKUP_DEST="/data/backups/git"; DATE=$(date +%Y%m%d_%H%M%S)
mkdir -p "$BACKUP_DEST"
tar -zcf "$BACKUP_DEST/native_repos_${DATE}.tar.gz" -C /srv git
find "$BACKUP_DEST" -type f -name "*.tar.gz" -mtime +30 -delete

# crontab：每天 02:30
# 30 2 * * * /root/scripts/backup_gitserver.sh >> /var/log/git_backup.log 2>&1

备份必须落在另一块物理盘（或移动硬盘 / 远端）。D:\GitServer 和 D:\GitServer\backup 在同一块盘上，只能防误删，防不了硬盘故障。

2.3 完整性校验与瘦身 #

bash
cd /srv/git/my-project.git
git fsck --full --strict              # 检查损坏对象
git count-objects -vH                 # 看对象数与体积
git gc --prune=now                    # 清理无引用对象并打包
git gc --aggressive --prune=now       # 深度重打包（慢，慎用在大仓库）
git commit-graph write --reachable    # 建提交图索引，加快 log/clone

2.4 彻底删除误提交的大文件 #

git rm 只能删"以后"，历史里的副本还在。要抹掉历史必须重写：

bash
pip install git-filter-repo
git clone --mirror git@git.example.com:user/proj.git && cd proj.git
git-filter-repo --invert-paths --path "path/to/huge_backup.dump"
git push --force --mirror origin     # 覆盖远端

重写历史后所有协作者都必须重新 clone，旧的 SHA 全部作废。这是"动全队"的操作，务必先通知。

2.5 迁移 #

场景 操作
换盘（D: → E:） 停 sshd → robocopy D:\GitServer E:\GitServer /MIR → 校验 → 删旧 Junction 并重建 → 起 sshd。客户端零改动
换机器 新机按第一章重做一遍 → 搬 repos → 建联接 → 跑校验比对对象数与提交数 → 客户端只改 HostName
只是加 Web 界面 装 Gitea，把 repos 当仓库根挂进去；SSH 通道可继续沿用系统 sshd（START_SSH_SERVER=false）

删 Junction 只能用 cmd /c rmdir C:\GitServer（不带 /S）。rmdir /S 或 Remove-Item -Recurse 在部分 Windows 版本上会顺着联接删掉目标目录里的真实数据。

三、方案 B：Gitea（需要 Web 界面时的默认选择） #

3.1 三种部署形态 #

形态 适用 数据位置
Docker Compose 全平台首选，升级=换镜像 ./gitea-data
Linux 单二进制 + systemd 服务器免 Docker，性能极高 /var/lib/gitea，配置 /etc/gitea/app.ini
Windows 单 exe + 系统服务 办公室闲置 PC / 工控机 D:\Gitea\custom\conf\app.ini

Docker Compose

yaml
version: "3.8"
services:
  server:
    image: gitea/gitea:latest
    container_name: gitea
    restart: always
    environment:
      - USER_UID=1000
      - USER_GID=1000
      - GITEA__database__DB_TYPE=sqlite3
      - TZ=Asia/Shanghai          # 跨平台时区，别挂 /etc/localtime
    volumes:
      - ./gitea-data:/data        # 配置 + SQLite + 全部仓库，备份只拷这里
    ports:
      - "3000:3000"               # Web
      - "2222:22"                 # SSH（避开宿主机 22）

bash
mkdir -p /opt/gitea && cd /opt/gitea && docker compose up -d

Windows 上的 Docker Desktop 里千万不要挂 /etc/timezone、/etc/localtime——Windows 没这两个文件，会报错或建出空目录。用 TZ 环境变量。

Linux 单二进制 + systemd

bash
sudo apt install -y git
sudo adduser --system --shell /bin/bash --group --disabled-password --home /home/git git

sudo wget -O /usr/local/bin/gitea https://dl.gitea.com/gitea/latest/gitea-latest-linux-amd64
sudo chmod +x /usr/local/bin/gitea

sudo mkdir -p /var/lib/gitea/custom /var/lib/gitea/data /var/lib/gitea/log
sudo chown -R git:git /var/lib/gitea && sudo chmod -R 750 /var/lib/gitea
sudo mkdir /etc/gitea && sudo chown root:git /etc/gitea && sudo chmod 770 /etc/gitea

ini
; /etc/systemd/system/gitea.service
[Unit]
Description=Gitea (Git with a cup of tea)
After=network.target

[Service]
RestartSec=2s
Type=simple
User=git
Group=git
WorkingDirectory=/var/lib/gitea/
ExecStart=/usr/local/bin/gitea web --config /etc/gitea/app.ini
Restart=always
Environment=USER=git HOME=/home/git GITEA_WORK_DIR=/var/lib/gitea

[Install]
WantedBy=multi-user.target

bash
sudo systemctl daemon-reload && sudo systemctl enable --now gitea
sudo systemctl status gitea
sudo ufw allow 3000/tcp        # 或 firewall-cmd --permanent --add-port=3000/tcp && firewall-cmd --reload
# 网页初始化完成后收紧配置权限
sudo chmod 750 /etc/gitea && sudo chmod 640 /etc/gitea/app.ini

Windows 单 exe

powershell
New-Item -ItemType Directory -Path "D:\Gitea"
# 下载 gitea-windows-*-amd64.exe 改名 gitea.exe 放进去
cd D:\Gitea; .\gitea.exe web          # 首次前台跑一遍，浏览器完成向导

powershell
# 方式 A：sc.exe 注册服务
sc.exe create gitea start= auto binPath= "\"D:\Gitea\gitea.exe\" web --config \"D:\Gitea\custom\conf\app.ini\""
sc.exe start gitea
# 方式 B：NSSM（崩溃自动拉起，推荐）
nssm install gitea "D:\Gitea\gitea.exe" "web"
nssm set gitea AppDirectory "D:\Gitea"
nssm start gitea

3.2 首次网页向导的四个必填项 #

text
数据库类型:        SQLite3
域名 (Domain):     192.168.1.100        ← 别填 localhost
SSH 服务端口:      2222                 ← 避开宿主机 22
HTTP 端口 / ROOT_URL: http://192.168.1.100:3000/
管理员账号:        就在这里建（不填则第一个注册的普通账号自动升为超管）
  • ROOT_URL 留 localhost → 别人从网页复制的 clone 地址是 http://localhost:3000/...，在自己机器上永远 clone 不下来。这是自建 Gitea 最高频的"局域网连不上"。
  • SSH 端口若沿用 22 会与系统 sshd 冲突；团队内部也可以干脆只用 HTTP/HTTPS，凭据管理器会记住密码。
  • 禁止自主注册 + 必须登录才能看仓库，局域网内建议当场勾上。

3.3 app.ini 常用项 #

ini
[server]
DOMAIN           = 192.168.1.100
HTTP_PORT        = 3000
ROOT_URL         = http://192.168.1.100:3000/
SSH_PORT         = 2222
START_SSH_SERVER = true       ; 用 Gitea 内置 SSH；若复用系统 sshd 设 false
[service]
DISABLE_REGISTRATION = true   ; 禁止访客注册
REQUIRE_SIGNIN_VIEW  = true   ; 必须登录才能看仓库
[repository]
DEFAULT_BRANCH = main

配置文件位置：Docker /data/gitea/conf/app.ini（宿主机 ./gitea-data/gitea/conf/app.ini）、Linux /etc/gitea/app.ini、Windows D:\Gitea\custom\conf\app.ini。改完重启服务生效。

3.4 反代 + HTTPS（对外必做） #

nginx
server {
    listen 80;
    server_name git.example.com;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl http2;
    server_name git.example.com;
    ssl_certificate     /etc/letsencrypt/live/git.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/git.example.com/privkey.pem;

    client_max_body_size 512M;       # 大包推送
    proxy_read_timeout  600s;        # 大仓库推送不中断
    proxy_connect_timeout 600s;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

bash
sudo ln -s /etc/nginx/sites-available/git.example.com.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

反向代理后，app.ini 里的 ROOT_URL 要改成对外的 https://git.example.com/，否则网页生成的地址还是内网 IP。

3.5 备份与迁移 #

bash
sudo -u git /usr/local/bin/gitea dump -c /etc/gitea/app.ini --work-path /var/lib/gitea
# Windows:  .\gitea.exe dump -c "custom\conf\app.ini"
# Docker :  docker exec -u git -it gitea /app/gitea/gitea dump -c /data/gitea/conf/app.ini

得到一个 gitea-dump-*.zip（含仓库、SQLite、配置、附件）。换机器解压还原即可，不用单独 dump 数据库——这是 Gitea 相比 GitLab 最舒服的一点。

3.6 Gitea Actions（轻量 CI） #

yaml
# docker-compose.yml 里追加
  runner:
    image: gitea/act_runner:latest
    restart: always
    environment:
      - GITEA_INSTANCE_URL=http://gitea:3000
      - GITEA_RUNNER_REGISTRATION_TOKEN=你的注册Token   # 管理面板 → Actions → Runners

yaml
# 项目根 .gitea/workflows/build.yml
name: build
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-node@v3
        with: { node-version: '20' }
      - run: npm ci && npm test && npm run build

语法与 GitHub Actions 基本一致，迁移成本极低。

四、方案 C：GitLab CE（有多少人、多少内存，才上） #

bash
# RHEL/CentOS 系

curl https://packages.gitlab.com/install/repositories/gitlab/gitlab-ce/script.rpm.sh | sudo bash
sudo EXTERNAL_URL="http://<公网IP或域名>" yum install -y gitlab-ce

安装完成后首次访问 EXTERNAL_URL 会强制设置 root 密码，之后：

  1. 客户端 ssh-keygen 生成密钥，cat ~/.ssh/id_rsa.pub 贴进 GitLab 的 SSH Keys；
  2. 网页 New Project 建项目，复制 SSH 地址；
  3. git clone git@<host>:root/test.git → 改文件 → git add → git commit → git push -u origin master；
  4. 网页刷新能看到 test.sh 说明同步成功。

装 GitLab 前先算内存：4 GB 是最低门槛，8 GB 才能舒服，16 GB 才敢开 CI。装在 1 GB 小机器上的结果通常是"打开一个页面等十秒"。

五、Git LFS：大文件别硬塞进对象库 #

bash
git lfs install
git lfs track "*.zip" "*.onnx" "*.mp4" "*.bin"   # 生成/更新 .gitattributes
git add .gitattributes && git commit -m "chore: enable lfs"
git add big_model.onnx && git commit -m "feat: add model" && git push

仓库里存的是指针文件，实体存在 LFS 存储目录。自建场景下：Gitea 安装时启用 LFS 即可；裸仓库方案需要单独跑 LFS 服务，或者干脆把大文件放在别处。

单文件超过 50 MB 就该考虑 LFS；仓库总大小超过 1~2 GB 之后，clone 的体验下降是断崖式的——因为每个版本的二进制都被完整保留。

6.2 SSH 访问审计（原生裸仓库方案） #

bash
# 实时看 git 用户的认证与操作
sudo tail -f /var/log/auth.log | grep sshd | grep git      # Debian/Ubuntu
sudo tail -f /var/log/secure   | grep sshd | grep git      # CentOS/RHEL

# 统计高频来源 IP（谁在猛 clone）
sudo grep 'Accepted publickey for git' /var/log/auth.log | awk '{print $11}' | sort | uniq -c | sort -nr

裸仓库方案没有 Web 界面，auth.log 就是唯一的操作审计入口；Gitea 则在管理面板的「操作日志」里看。

七、排障速查 #

现象 排查顺序
Permission denied (publickey)，配了公钥还要密码 ① authorized_keys 的 ACL 有多余组可写（Windows 用 icacls，Linux 用 chmod 600）② Windows 的 Match Group administrators 未注释 ③ 改了配置没重启 sshd ④ 公钥被换行截断（必须一整行）⑤ 看事件查看器 → OpenSSH/Operational，或 /var/log/auth.log
git-upload-pack: command not found sshd 读的是机器级 PATH，不是你终端的 PATH。用 ssh host "where git" / ssh host "which git" 从外部验证；必要时把 git 目录加进系统 PATH 再重启服务
推送时报 permission denied（目录层面） 仓库所有权不是 git：chown -R git:git <repo>
连不上 22 端口 防火墙/安全组：New-NetFirewallRule ... -LocalPort 22、ufw allow 22、云厂商安全组
钩子报 bad interpreter 脚本存成了 CRLF，改 LF
局域网别人 clone 不下来 Gitea 的 ROOT_URL 还是 localhost；或用了 DHCP 地址，改成主机名/固定 IP
大包推送中断 反代 client_max_body_size 与 proxy_read_timeout 调大；或改用 SSH 通道
仓库越来越慢 git gc --prune=now + 查找历史大文件后用 filter-repo 清理
