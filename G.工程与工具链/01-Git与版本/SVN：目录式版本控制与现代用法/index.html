这篇只讲一件事：SVN 的分支是目录拷贝，Git 的分支是指针。理解这一条，SVN 那些看起来别扭的行为就都有解释了——建分支为什么在服务器上瞬间完成、换分支为什么要专门敲 svn switch、合并为什么要在目录上记一本 mergeinfo、tags 为什么不是真正的标签。

讲什么：集中式与分布式的差别、trunk/branches/tags 三目录约定、基础命令、目录式分支、合并与 mergeinfo、冲突、文件锁、忽略规则、TortoiseSVN 的图形合并。

不讲什么：Subversion 服务端安装、svnserve/Apache 配置、hooks 脚本细节、LDAP 集成。Git 的对应内容在《Git 命令与工作流》《Git 服务器搭建与运维》两篇。

一、SVN 是什么 #

Subversion，命令行程序叫 svn，Windows 上那套右键菜单叫 TortoiseSVN。2000 年从 CollabNet 起步，目标是替代 CVS：提交原子化、重命名保留历史、二进制文件不再被当文本去 diff。

它的模型里只有两个角色：

  • 中央仓库（repository）：跑在服务器上，存着全部历史，地址形如 https://svn.example.com/repo。
  • 工作副本（working copy）：你从仓库签出来的那份目录，带一个隐藏的 .svn。

所有操作都是这两者之间的搬运。没有第三个角色，没有本地仓库，没有暂存区。这一点决定了后面每一章的走向。

一个数字概括它：整个仓库共用一条递增整数序列，r1、r2、……、r1234。你一次提交三个文件，它们一起变成 r1235。想知道某个文件在 r1200 时是什么样，敲 svn cat -r 1200 去问服务器。

一个习惯概括它：仓库里放三个目录，trunk 是主线，branches 放并行开发线，tags 放发布快照。SVN 本身不检查这三个名字，但几乎所有项目都这么摆。

图形客户端和命令行操作的是同一份工作副本、同一套元数据，混着用没问题。团队里常见的分工是：日常提交、更新用右键菜单，批量操作和排错用命令行。

二、集中式与分布式的根本差别 #

「集中式」和「分布式」说的不是部署方式，是数据模型。Git 克隆下来的是一整个仓库，SVN 检出下来的只是一份工作副本。

2.1 一张总表 #

维度 SVN（集中式） Git（分布式）
仓库数量 一个权威仓库，所有人共用 每个克隆都是完整仓库
本地有什么 工作副本 + 每个文件的原始副本，没有历史 完整历史 + 全部分支 + 全部标签
看旧版本 必须连服务器 本地就有
提交去哪 直接写中央仓库 先写本地对象库，push 才上网
离线能力 只能改文件，不能提交、不能看历史 能提交、能开分支、能看历史，只有同步要网络
版本标识 全局递增整数 r1234 内容哈希 a1b2c3d…
分支实现 仓库里的一个目录 一个指向提交的指针
合并记录 svn:mergeinfo 属性 提交图上的祖先关系
权限粒度 路径级，能精确到目录 仓库级，靠平台的分支保护近似
单点风险 服务器挂了全员停摆 本地照常干活，恢复后再同步
大二进制文件 习惯性放得下 会撑爆 .git，要上 LFS

2.2 版本号：递增整数 vs 内容哈希 #

r1234 是整个仓库的第 1234 次提交，不是文件的版本，也不是内容指纹。好处是短、好念、好算差值：r1200 到 r1235 之间就是 35 次提交。局限有两个：跨仓库没有意义，两个仓库各自从 r1 数起；无法用来判断内容是否相同，两个 revision 号不同而内容一模一样的情况很常见。

Git 的哈希是内容算出来的，同样的目录树加同样的父提交，算出的 ID 必然相同。所以 Git 能说「这两个提交是同一个东西」，SVN 说不出这句话。代价是 40 位十六进制，人记不住，只能靠标签和分支名做锚点。

2.3 分支：目录拷贝 vs 指针 #

这是全篇的核心。

text
SVN：分支 = 仓库里多了一个目录
  /trunk/MyProject/            ← 主线目录
  /branches/feature-x/         ← 另一个目录，内容从 trunk 拷来

Git：分支 = 一个引用文件
  .git/refs/heads/feature-x  →  内容是一行提交哈希
动作 SVN Git
建分支 服务器端复制目录，产生一个新 revision，几乎不占空间 写一个引用文件
换分支 svn switch，改工作副本绑定的 URL，下载两棵树的差异 git switch，挪指针，工作区跟着变
分支在哪 服务器上，别人也看得见 本地，push 之后别人才看见
删分支 svn delete 一个目录，产生 revision git branch -d，删一个文件

由此推出三条后果，后面反复出现：

第一，建分支不占本地空间，但换分支要动工作副本。 工作副本是「一棵绑定了某个 URL 的树」。svn switch 换掉绑定目标，再把两边的差异搬过来，改动量取决于两个目录差多少。

第二，分支是目录，合并就是路径对路径的操作。 你必须告诉 SVN「从哪个 URL 合到当前这个副本」，不是 Git 那种「把这个提交合进当前分支」。这也解释了 TortoiseSVN 的合并对话框为什么一上来就问 URL to merge from。

第三，分支是目录，所以它能被改。 没有「分支锁定」这回事，谁有写权限谁就能改 /branches/feature-x 里的文件。Git 里推进分支只能靠提交挪指针，两者在「分支会不会被意外改动」上的风险不同。

2.4 提交：进服务器 vs 进本地 #

commit 直接走网络写服务器，服务器接受才分配 revision 号。提交是原子的：三个文件要么全进，要么全不进。

它没有暂存区。svn commit 提交的是工作副本里所有已版本化文件的所有改动。想只提交一部分，只能在命令后跟路径列表，或者在图形界面里勾文件——那是挑文件，不是挑代码块。Git 的 git add -p 那种按行挑选，SVN 没有。

由此得到两条纪律：

  • 提交前一定 svn diff。没有暂存区做二次过滤，你手上所有改动会被一起送上去，包括调试用的 console.log 和临时改的配置。
  • 提交后撤销只能反向合并。SVN 没有 git reset --soft，也不能改写历史。要撤掉 r1235，做法是 svn merge -c -1235 .，把那次改动反向应用一遍，再提交成 r1236。历史只增不减。

2.5 目录是唯一的组织维度 #

分支是路径、标签是路径、权限是路径、合并的源和目标也是路径。^/ 是仓库根的缩写。遇到 E160013: URL not found，第一反应该是「路径写错或被改名了」，不是去怀疑权限。

三、trunk、branches、tags 三个目录 #

3.1 惯例布局 #

text
https://svn.example.com/repo/
├── trunk/
│   └── MyProject/              正在开发的主线
├── branches/
│   ├── feature-x/              功能分支
│   └── hotfix-20240115/        紧急修复
└── tags/
    ├── v1.0/
    └── v1.1/

骨架三条命令搞定，一次提交一个 revision：

bash
svn mkdir ^/trunk ^/branches ^/tags -m "init layout"

3.2 它只是约定，不是机制 #

SVN 不管你叫 trunk 还是叫 main。这套布局来自早期社区实践，后来所有工具（包括 TortoiseSVN 的仓库浏览器）都默认按这套名字识别，于是成了事实标准。有的团队把项目再嵌一层：^/trunk/MyProject、^/branches/MyProject/feature-x。素材里的操作右键点在 /trunk/MyProject 上，说明仓库是「一个仓库装多个项目」的摆法。

3.3 tags 是拷贝出来的目录，不是标签 #

bash
svn copy ^/trunk ^/tags/v1.0 -m "release v1.0"

它做的事和建分支完全一样：服务器端拷贝一个目录，产生一个新 revision。区别只在「大家约定 tags 下面的目录不许改」。

所以 SVN 的 tag 没有只读属性。谁有写权限，谁就能提交进 /tags/v1.0，把已经发出去的 1.0 改掉。现实中的三道防线：服务端配 pre-commit hook 拒绝任何对 /tags/ 的写操作（最硬，要运维配合）；目录权限只给发布负责人写权限；全靠自觉（最常见，也最容易出事）。

对照 Git：git tag v1.0 写的是 refs/tags/v1.0，指向一个提交对象，改它要 git tag -f 显式覆盖，而且它不携带工作树，你没法「在 tag 里改个文件再提交」。Git 的 tag 是一个指向提交的名字，SVN 的 tag 是一个长得像快照的目录。

3.4 一个仓库放几个项目 #

摆法 路径长相 好处 代价
单仓库多项目 /trunk/prjA、/trunk/prjB 跨项目引用方便，一套权限 revision 号全局共享
单仓库单项目 /prjA/trunk、/prjB/trunk revision 号只属于自己 仓库多，权限和备份要铺开
多仓库单项目 每个项目一个 URL 隔离彻底，权限独立 跨项目共享靠 svn:externals

「为什么我们的 revision 号跳得这么快」的答案在第一行：全公司一个仓库，每个项目的每次提交都在推同一个计数器。这不是 bug，是设计。

3.4 分支命名与改名的代价 #

命名没有标准，团队统一就行。常见的三族：feature-<短描述> 合回 trunk 后删掉；hotfix-<日期或版本> 合回 trunk 的同时也要合进当前 release 线；release-<版本号> 只接受修复不接受新功能。

分支目录名定下就别改。改了名，别人的工作副本还绑在旧 URL 上，svn update 报 E160013。让所有人 svn switch 到新地址，或者重新 checkout。svn switch --relocate 救不了——它只处理「服务器地址变了、路径没变」。

四、基础命令全流程 #

4.1 命令总表 #

目的 命令 要点
检出 svn checkout URL [PATH] 只拿当前版本，不拿历史
更新 svn update 拉服务器改动，保留本地修改
看状态 svn status 本地改了哪些、哪些没纳入版本控制
添加 svn add FILE 新文件必须先 add
删除 svn delete FILE 本地立刻删，提交后才从服务器删
改名 svn move A B 保住历史，别用资源管理器拖
提交 svn commit -m "..." 直接进服务器，没有中间站
看差异 svn diff / -c N 提交前最后一道检查
看历史 svn log -v -l 10 -v 带改动文件列表
撤销本地改动 svn revert FILE 目录要加 -R
清锁 svn cleanup 报 E155004 时敲
换分支 svn switch URL 改工作副本绑定的地址
合并 svn merge SOURCE 见第六章
打标签 svn copy ^/trunk ^/tags/v1.0 本质是建分支
只读查询 svn cat / list / info / blame 不检出也能查远端
导出干净副本 svn export URL DIR 不带 .svn，打发布包用它

4.2 checkout：把仓库搬下来 #

bash
svn checkout https://svn.example.com/repo/trunk/MyProject MyProject
svn checkout --depth immediates URL   # 只拿第一层，目录是空壳
svn checkout -r 1200 URL              # 直接检出某个历史版本

第二个参数是本地目录名，省掉就用 URL 最后一段。检出完目录里多一个 .svn。1.7 之后只在根上有一个，更早的版本每层目录各放一个——在老项目里看到满屏 .svn 那是老格式，svn upgrade 可升级。大仓库只关心某个子目录时，--depth 能省大量时间。

4.3 update：把别人的改动拉下来 #

bash
svn update
svn update -r 1200    # 把工作副本整体搬到某个状态，查完再 update 回最新

它把服务器上比你新的改动写进工作副本，同时尽量保留你本地的未提交修改。输出是一串单字母：

字母 含义
U 文件被更新
G 服务器改动与本地改动合并成功
C 冲突，需手工处理（第七章）
A 服务器新增的文件落到本地
D 服务器删除的文件从本地删掉
B 锁被破坏，多伴随一次中断的操作

-r 是「整体搬到那个状态」，不是撤销。撤销是反向合并，见 6.5。

4.4 status：本地到底动了什么 #

标记 含义 处理
M 内容被修改 提交即可
A 计划添加 提交即可
D 计划删除 提交即可
C 冲突 必须先解决再提交
? 未纳入版本控制 svn add 或加进忽略
! 文件被非 svn 手段删掉 svn delete 或 svn revert
R 被替换（删了又建同名） 确认历史是否断掉
~ 被未版本化的同名东西挡住 挪走那个东西
I / X 已忽略 / 外部引用目录 不用管

第二列出现 M 说明改的是属性而不是内容，比如 svn:ignore、svn:mergeinfo。两个常用参数：svn status -u 顺带问服务器别人改了哪些（要联网），--no-ignore 连被忽略的也列出来。

? 最容易出事。新人加了一堆新文件却忘了 svn add，提交显示成功，别人更新下来少文件，构建直接崩。提交前扫一眼，有 ? 就问自己一句「这个该不该进库」。

4.5 add / delete / move #

bash
svn add newfile.txt          # 单个文件
svn add --force .            # 当前目录下所有未版本化文件都加进来
svn delete oldfile.txt       # 本地立即删除，并标记为待删除
svn delete --keep-local log/ # 只在服务器上删，本地留着
svn move a.txt b.txt         # 改名，历史跟着走

svn delete 有个反直觉的点：敲完文件就从磁盘上没了。想「服务器删、本地留」，必须加 --keep-local。很多人第一次用以为是打标记，回头发现文件不见了。改名一律用 svn move，用资源管理器改名再 svn add 也行，但历史会断成两段。

4.6 commit：一脚踏进服务器 #

bash
svn commit -m "fix: 修正导出时的空指针"
svn commit a.c b.c -m "只提交这两个"    # 指定路径，等于挑选文件
svn commit -F msg.txt                    # 从文件读提交说明

不带路径就是整个工作副本递归提交。没有暂存区做缓冲，所有 M/A/D 一起送上去。提交失败的三种常见原因：

  1. out of date：别人先提交了，先 svn update。SVN 不允许在过期基线上提交，这比 Git 严格——Git 允许基于旧提交提交，冲突留到 push 才暴露。
  2. 锁冲突：文件被别人 svn lock 了，见第八章。
  3. hook 拒绝：服务端 pre-commit 脚本拦了，打印原因，比如提交说明太短、路径不在允许范围。

4.7 diff 与 log #

bash
svn diff                       # 工作副本 vs 基线
svn diff -r 1230:1235          # 两个 revision 之间
svn diff -c 1235               # 只看 1235 这一次提交
svn diff --summarize -r 1230:1235   # 只列文件名
svn log -v -l 10               # 最近 10 条，带改动文件列表
svn log -r 1200:1235           # 指定区间
svn log URL                    # 不检出也能看远程路径的历史

-v 会列出每次提交碰过的路径以及动作（M/A/D/R）。追「谁把那个目录删了」时，它是唯一管用的手段。

4.8 revert 与 cleanup #

bash
svn revert file.c
svn revert -R .          # 递归撤销当前目录下所有本地改动
svn cleanup              # 解锁工作副本

revert 不联网，拿 .svn 里保存的原始副本覆盖回工作副本。撤销完就真没了，SVN 没有 reflog。目录必须加 -R：不加的话只会撤销目录节点自身的属性改动，里面文件的修改一个都不动。

cleanup 对付的是 E155004: Working copy locked、E200031: sqlite: database is locked、E155037: Previous operation has not finished 这类报错，原因基本是上次操作被强行中断：杀进程、断网、磁盘满、拔了移动硬盘。它删掉 .svn 里的操作锁、回滚没做完的事务、清理临时文件，不会动你的代码。它救不回来时，最后一招是重新 checkout 到新目录再把改动拷过去。

五、目录式分支怎么用 #

5.1 五种操作一览 #

操作 命令 在哪执行 产生新 revision
建分支 svn copy ^/trunk ^/branches/x -m "..." 服务器端 是
切分支 svn switch ^/branches/x 本地工作副本 否
合并 svn merge ^/branches/x 本地工作副本 否（提交才产生）
打标签 svn copy ^/trunk ^/tags/v1.0 -m "..." 服务器端 是
删分支 svn delete ^/branches/x -m "..." 服务器端 是

switch 只改你本地这份副本绑哪儿，仓库里什么都没变；delete 是直接删服务器上的目录，所有人下次 update 都会发现分支没了。

5.2 建分支 #

bash
svn copy ^/trunk ^/branches/feature-x -m "create branch feature-x from trunk"
svn copy -r 1200 ^/trunk ^/branches/hotfix-1200 -m "branch from r1200"

在服务器端完成，本地不产生任何文件，不占你的磁盘。返回信息里有一个新 revision 号，说明这次复制被记进了全局序列。加 -r 就从某个历史点切一条线出来，一条命令。两个 URL 都必须是仓库内路径，^/ 是仓库根，写全了就是 https://svn.example.com/repo/trunk。

5.3 switch：把工作副本切到分支 #

bash
svn switch ^/branches/feature-x
svn switch ^/branches/feature-x/src ./src    # 只切某个子目录

执行后本地这棵树的绑定 URL 从 trunk 变成分支，文件内容自动调整成分支上的样子。输出里那串 U/A/D 就是两棵树的差异被搬过来。switch 会尽量保留你的本地未提交修改：改得少的文件能带过去，改得多的、正好撞上差异的会产生冲突。第二行那招在大仓库里很实用——主干和分支只在某个子目录有差别，就不用整棵树来回切。

切过去之后所有操作和主干上一样：svn update、svn status、svn commit。提交进的是分支目录，revision 号还是那个全局序列。提交前敲一次 svn info | grep URL 确认自己在哪条线上。在主干上以为自己在分支上提交，是 SVN 最常见的事故，而且事后很难看——那条提交混进了主干，要撤只能反向合并。

5.4 合并回主干：命令版 #

顺序不能反：

bash
svn switch ^/trunk                # 1. 工作副本先回到 trunk
svn update                        # 2. 拉到最新，别在旧基线上合
svn merge ^/branches/feature-x    # 3. 合分支的改动进来
svn status                        # 4. 看合进来哪些文件
svn diff                          # 5. 逐行看，这一步别省
svn commit -m "merge feature-x into trunk"   # 6. 提交

第 3 步的语义是「把源 URL 上尚未合并过的 revision 应用到当前工作副本」。当前副本是谁，改动就落到谁身上。所以必须先在 trunk 的工作副本里执行，在分支里执行就是把 trunk 的改动往分支灌。

第 6 步之前，合并结果只存在于你的本地磁盘。素材里那句话说得准确：合并发生在本地 working copy，不提交就不影响 repository。这是 SVN 里少有的「有本地缓冲」的时刻，值得利用——合并完先跑一遍测试再提交。

5.5 删分支 #

bash
svn delete ^/branches/feature-x -m "remove merged branch"
svn copy -r 1200 ^/branches/feature-x ^/branches/feature-x-restored -m "restore"

服务端操作，产生一个 revision。删掉的目录还在历史里，svn log -v ^/branches 看得到它曾经存在，第二条命令能从旧版本把它复活。合并完就删，别留着。分支目录越堆越多，svn list ^/branches 一屏刷不完的时候，没人知道哪条还能删。

六、合并与 mergeinfo #

6.1 三种合并语义 #

对应 TortoiseSVN 合并对话框里的三个选项：

模式 命令行 语义 场景
合并一段修订 svn merge -r N:M SOURCE 把 SOURCE 上 N 到 M 之间的改动应用到当前副本 日常同步、分支合回主干
合并两棵树 svn merge SOURCE1@R1 SOURCE2@R2 算两棵树的差异整体应用 两个无血缘关系的分支搬代码
重整合并 svn merge --reintegrate ^/branches/x 把分支全部改动一次性搬回父线 功能分支收尾

第三种在 1.8 之后不用手动加了，SVN 自己判断该不该走重整合并。老教程里到处是 --reintegrate，那是 1.5 到 1.7 的写法。第一种模式还支持单次修订：

bash
svn merge -c 1235 ^/branches/feature-x      # 只合 1235 这一次
svn merge -c -1235 .                        # 反向合并，撤销 1235
svn merge -r 1230:1235 ^/branches/feature-x # 合 1230 到 1235 这一段
svn merge --dry-run ^/branches/feature-x    # 只试跑不落盘

--dry-run 只打印结果。素材里 TortoiseSVN 的 Test merge 按钮，命令行等价物就是它。

6.2 mergeinfo 是什么 #

svn merge 执行完，会在目标目录上写一个属性 svn:mergeinfo，内容是「哪些来源的哪些 revision 已经合过了」：

text
/branches/feature-x:10-25,30,32-35

意思是：/branches/feature-x 上的 10 到 25、30、32 到 35 都已经合进这个目录。下次再执行同样的 svn merge，SVN 跳过这些号，只合新的。

这就是 SVN 避免重复合并的机制。它在 1.5 引入，之前没有 merge tracking，只能靠人记「上次合到几号」。

bash
svn propget svn:mergeinfo -R .                            # 当前副本全树的合并记录
svn mergeinfo --show-revs eligible ^/branches/feature-x .  # 还没合的
svn mergeinfo --show-revs merged ^/branches/feature-x .    # 已经合过的

合并前跑一次 eligible，就知道这次会合进来哪些 revision，比盲合安全。

6.3 mergeinfo 为什么会乱 #

它记在目录属性上，而属性会被各种操作意外带走：

  1. 手工拷贝目录。用 svn copy 复制一个已合并过的目录，mergeinfo 跟着复制，新目录「声称」自己合过一堆东西。
  2. --ignore-ancestry。它让 SVN 忽略两个路径的祖先关系、把源当成无关的树来 diff，对 mergeinfo 的处理也跟着变，用完容易出现该记的没记。
  3. 只 revert 文件不 revert 属性。合并后没提交，svn revert -R . 退回是对的；只 revert 文件不动属性，状态就不一致了。
  4. 合并后不提交就 switch。带着未提交的 mergeinfo 换到另一条线上。

症状两种，都难查：漏合并——mergeinfo 说合过了实际没合，代码缺一块，测试才发现；重复合并——没记上，同样的改动被应用两次，产生大量假冲突或重复代码。

6.4 出问题怎么查 #

显示已合并、代码里却没有，先别硬合。找出什么时候记错的靠 svn diff -c N 看某次提交有没有改 svn:mergeinfo，然后清掉重合：

bash
svn propdel svn:mergeinfo .
svn commit -m "reset mergeinfo"
svn merge ^/branches/feature-x
svn commit -m "re-merge feature-x"

合之前逐条过一遍：svn info 确认在哪个目录、svn status 确认没有未提交改动、svn update 拉最新、svn mergeinfo --show-revs eligible 看会合进来哪些号、svn merge --dry-run 试跑一次。合完把这次合到哪个号写进提交说明——mergeinfo 之外，人的记录是第二道保险。反过来，只要源和目标都是老实按 svn copy 建的关系、合并都用 svn merge 在工作副本里执行、合完立刻提交，mergeinfo 很少出错。它出问题几乎都出在「绕过了标准动作」的时候。

6.5 反向合并：SVN 的「撤销」 #

SVN 不能改写历史，撤销只能再提交一次反向改动：

bash
svn merge -c -1235 .        # 在受影响的工作副本里执行，注意负号
svn status                  # 确认文件被改回去了
svn commit -m "revert r1235"

对应的 mergeinfo 会记成「-1235 已合并」，意思是反向操作也记进账了，下次正向合并 1235 还是会被跳过——这一点经常让人困惑：明明撤销了，为什么再合还合不进来。这时候得显式 -c 1235 强制一次。

对比 Git：git revert 1235 生成一个反向提交，逻辑一样，但 Git 不维护 mergeinfo，靠提交图判断祖先关系。同一个需求，两套答案。

七、冲突的处理 #

7.1 冲突从哪来 #

两种操作会把两边的改动往一处叠：svn update（服务器 vs 你的本地）和 svn merge（源分支 vs 当前副本）。同一行被两边改过，SVN 就停下来把 C 打给你看。

text
$ svn update
Conflict discovered in 'src/export.c'.
Select: (p) postpone, (df) diff-full, (e) edit,
        (mc) mine-conflict, (tc) theirs-conflict, ...

回车直接选 p（推迟）也可以，SVN 会把冲突留在文件里，让你用编辑器慢慢处理。

7.2 三个临时文件 #

处理 src/export.c 的冲突时，目录里会多出：

文件 内容
export.c.mine 你本地改动后的版本
export.c.r1200 冲突基线的版本（旧版）
export.c.r1235 服务器上那个版本（新版）

export.c 本身被写入冲突标记：

text
<<<<<<< .mine
    return do_export_v2(path);
=======
    return do_export(path, flags);
>>>>>>> .r1235

<<<<<<< 到 ======= 是你这边，======= 到 >>>>>>> 是服务器那边。手工改成你要的结果，三行标记全部删掉。

7.3 resolve #

改完必须显式告诉 SVN「处理好了」：

bash
svn resolve --accept working src/export.c
取值 意思
working 保留你磁盘上的内容（手工合并后用这个）
mine-full 整份用我的，丢掉别人的
theirs-full 整份用别人的，丢掉我的
base 退回冲突前的基线，两边改动都不要

svn resolve 干两件事：删掉那三个临时文件，把状态从 C 改回正常。老版本里这条命令叫 svn resolved，现在还能用。不 resolve 就提交会被直接拒绝，报 E155015: 'src/export.c' remains in conflict。

7.4 树冲突 #

另一种冲突发生在目录层面：一边改文件一边把文件删了；一边改目录名一边往里加文件。这类冲突 svn status 标 C，但文件里没有冲突标记——争的不是行，是「这个路径该不该存在」。

text
      C src/legacy/
  >   local edit, incoming delete upon update

先想清楚要哪个结果，再显式声明：

bash
svn resolve --accept working src/legacy      # 保留本地这一份
svn resolve --accept theirs-full src/legacy  # 接受服务器删掉它

树冲突没有自动合并这个选项，它要你做一个业务判断。

处理时几条经验：冲突文件多时先 svn status 列出全部 C，一个一个过，别边看边改；合并前把三个文件都打开对比，.mine 是你的意图，.rNEW 是别人的意图，基线告诉你原来长什么样；改完立刻 svn resolve，别攒到最后一起处理，攒着容易忘记哪个处理过了；拿不准就 svn revert 退回基线，找改它的那个人对一遍，比凭猜改错强。

八、文件锁与二进制资产 #

8.1 锁为什么存在 #

文本文件冲突可以手工合并，二进制冲突不行。一张改过的 PSD、一份被人同时编辑的 xlsx，三方合并没有意义——你只能在「我的」和「他的」之间二选一，输的那一方工作白做。

bash
svn lock images/logo.psd -m "在改 logo，预计两小时"
svn unlock images/logo.psd
svn lock                        # 列出当前工作副本里的锁
svn info images/logo.psd        # 看某个文件被谁锁了

锁存在服务器上，别人提交被锁的文件会被拒绝，报错里带着锁的持有者和留言。

8.2 配合 svn:needs-lock #

光靠人记得 svn lock 不现实。给二进制文件打上 svn:needs-lock 属性后规则自动生效：

bash
svn propset svn:needs-lock yes images/logo.psd
svn commit -m "logo.psd needs lock"

打完属性，文件在每个人的工作副本里都是只读的，编辑器改不动。要用先 svn lock，锁到手文件自动变可写；改完提交，锁自动释放，文件又变回只读。

抢锁和破锁用 svn unlock --force 与 svn lock --force，两个都要权限，而且会给人添麻烦。正确做法是先问一句「这个锁还要吗」。锁不会自动过期，人一旦休假，锁就永远挂在那儿。团队里该有个规矩：抢锁前在群里说一声。

8.4 这是 SVN 相对 Git 的一个实际优势 #

Git 没有锁。Git LFS 后来补了 git lfs lock，思路一样，但要额外部署 LFS 服务端。原生 Git 面对「两个人同时改同一个 PSD」，只能事后发现冲突，然后让一个人把改动重做一遍。

判据很直接：

场景 更适合
代码为主，文本文件，改动频繁合并 Git
美术资源、设计稿、Office 文档占比高 SVN（靠 svn:needs-lock）
需要按目录精确授权 SVN
大量并行分支、频繁 rebase Git

九、忽略规则 #

9.1 svn:ignore 是目录属性 #

Git 用一个 .gitignore 管全仓库。SVN 没有这个文件，它用目录属性 svn:ignore：

bash
cd MyProject
svn propedit svn:ignore .        # 用编辑器打开当前目录的忽略列表
svn propset svn:ignore "*.log" .
svn propget svn:ignore .

编辑器里一行一个模式，写 *.log、*.tmp、bin、obj、.DS_Store 这类。

9.2 三个坑 #

第一，只对当前目录的直接子项生效，不递归。 你在项目根写了 bin，src/bin 不会被忽略，每个目录都要单独设。这是它最反直觉的地方。

第二，属性要提交才生效。 svn propset 只改了本地属性，svn status 会把目录标成 M（第二列）。不提交，别人那儿没有这条规则。

第三，已经版本化的文件加不进忽略。 文件一旦 svn add 过，写进 svn:ignore 也没用，照样出现在 status 里、照样被提交。要忽略必须先 svn delete 并提交。

9.3 全局忽略与对照 #

客户端配置文件里有一段 global-ignores，对本机所有工作副本生效，不进仓库：

text
[ miscellany ]
global-ignores = *.o *.pyc __pycache__ *~ .*.swp .DS_Store Thumbs.db

它放在 %APPDATA%\Subversion\config（Windows）或 ~/.subversion/config（Linux）里。

维度 svn:ignore .gitignore
载体 目录属性 仓库里的一个文件
作用范围 只对该目录的直接子项 该目录及其所有子目录
是否递归 否 是
全局规则 客户端 config 的 global-ignores core.excludesFile

svn status --no-ignore 能看到被忽略的东西，排查「为什么这个文件没进库」时用它。

十、TortoiseSVN 的图形操作 #

10.1 右键菜单 #

在受版本控制的目录上右键，能看到 Update、Commit、Show log、Check for modifications、Revert、Repo Browser、Merge...、Branch/tag...、Switch...、Resolve、Settings。文件图标上有角标：绿色钩是无改动，红色叹号是有本地修改，黄色感叹号是冲突，蓝色加号是待添加。扫一眼目录就知道状态。

10.2 建分支 #

在 trunk 上右键 → Branch/tag...，弹窗三项：To URL 填 ^/branches/feature-x；Create copy in the repository from 默认 HEAD revision in the repository，也可选某个 revision 或工作副本；Log message 必填。勾上 Switch working copy to new branch/tag，建完自动切过去，省一次 svn switch。

10.3 合并：完整步骤 #

这是素材讲的那条路。第一步，在 /trunk/MyProject 上右键——注意是在主线的目录上右键，不是随便哪个目录。右键位置决定了合并结果落在哪里。依次选 TortoiseSVN → Merge...。

第二步，选合并类型。弹出窗口里三个选项，选第一项 Merge a range of revisions：

选项 用在哪
Merge a range of revisions 把某个分支或主线上若干 revision 的改动合到另一条线
Merge two different trees 两棵树的差异整体搬过来，适合没有血缘关系的分支
Reintegrate a branch 功能分支收尾，整条分支一次性合回父线

它适用于把某个分支或主线上提交的多个 revision 之间的变化，合并到另外一个分支上。

第三步，填来源和版本范围。 点 next 进入第二页。素材里这一页的截图已经丢失，这里用文字说清它长什么样：上方一个输入框 URL to merge from，下方 Revision range to merge 输入框加一个 Show log 按钮，再往下是 all revisions 和 specific range 两个单选。

因为是从 branch 合到 trunk，配置如下：

  • URL to merge from 填 branch 的路径，比如 https://svn.example.com/repo/branches/feature-x，或者简写 ^/branches/feature-x。
  • Revision range to merge 填你要把 branch 的哪些 revision 对应的变化合进 trunk。可以是一连串（4-7、15-HEAD），也可以是单个 revision 号，点 Show log 能在日志列表里勾选，不用手敲。
  • 也可以选 all revisions 表示所有修订。把分支合并到主干，多数情况选 all revisions；只想合一部分到主干，就选 specific revisions 指定版本号。

范围写法：

写法 含义
4-7 第 4 到第 7 次提交的改动
15-HEAD 从 15 一直到最新
1235 只有 1235 这一次
4-7,15,20-HEAD 混着写，逗号分隔

第四步，合并选项页。 再点 next 进入第三页，一页复选框，管合并深度、忽略祖先关系、Force the merge 之类的行为，保留默认设置即可。

点 Merge 之前先点一次 Test merge。它只试跑不落盘，把将要发生的改动列给你看：哪些文件会新增、哪些会更新、有没有冲突。结果不对就回去改版本范围；显示「已经合并过、没有新内容」，说明上一次合过了。

如果 Test merge 报错，而你又确认范围没问题，可以勾上 Force the merge 强制合并——它跳过「本地有未提交改动就别合」这类保护性检查。这是一根保险丝，拔了要自己承担后果：强制合并会把本地未提交的改动冲掉。

确认无误后点 Merge，branch 上那些 revision 的改动就同步到 trunk 的工作副本里了。

第五步，处理冲突。 有冲突的文件会标红，用 Edit conflicts 打开三方对比窗口，逐处选「用我的」「用他的」或手工改，改完在 Resolve 里点 Mark as resolved。命令行等价物在第七章。

第六步，提交。 合并只发生在本地 working copy，不提交就不影响 repository。先在本地跑一遍构建和测试，通过之后再 SVN Commit。这一步才真正把改动写进中央仓库，产生一个新的 revision。

第七步，失败了怎么办。 先 svn revert -R . 退回合并前，再从仓库拉一次最新的 trunk，重新合。素材里那句「如果合并失败，可以尝试从仓库拉取最新的 trunk 代码，再次尝试合并」说的就是这个顺序——旧基线上合并，冲突只会更多。

10.4 图形与命令行的对应 #

Check for modifications 窗口能勾 Show unversioned files（对应 status 的 ?）和 Show ignored files，提交前扫一眼比读命令行输出直观。TortoiseSVN 在 Settings → Dialogs 里能勾上显示命令行，执行时把等价的 svn 命令打出来，想学命令行的可以拿它当翻译器用一段时间。

十一、SVN 与 Git 的对照速查 #

想做什么 SVN Git
拿到代码 svn checkout URL git clone URL
拉取更新 svn update git pull
看状态 / 改动 svn status / svn diff git status / git diff
添加 / 删除 / 改名 svn add / delete / move git add / rm / mv
提交 svn commit git commit
提交并上网 没有这一步，提交即上网 git push
撤销本地改动 svn revert git restore
看历史 / 逐行作者 svn log / svn blame git log / git blame
建分支 svn copy ^/trunk ^/branches/x git branch x
切分支 svn switch ^/branches/x git switch x
合并 svn merge ^/branches/x git merge x
打标签 svn copy ^/trunk ^/tags/v1.0 git tag v1.0
撤销已提交的改动 svn merge -c -1235 . git revert 1235
忽略文件 svn:ignore 目录属性 .gitignore
锁文件 svn lock 无（LFS 才有）
导出干净副本 svn export git archive

四条不能混的：

  1. r1234 和提交哈希不是一回事。前者是仓库内的提交序号，后者是内容指纹。
  2. svn merge 不是 git merge。Git 按提交图的祖先关系判断该合什么；SVN 按你给的 URL 和版本范围算差异，再把结果记进 mergeinfo。
  3. svn switch 不是 git switch。前者改文件并下载差异，后者只挪指针。
  4. SVN 提交没有中间态。没有暂存区、没有本地历史、没有 --amend。

十二、易错点速查 #

现象 原因 处理
提交成功但别人拿不到文件 新文件忘了 svn add，status 里还是 ? 补 svn add 再提交
报 E155004 locked 上次操作被中断 svn cleanup
提交被拒 out of date 别人先提交了 先 svn update
svn revert dir 没生效 目录撤销要递归 svn revert -R dir
忽略规则不管用 只对当前目录生效、属性没提交、或文件已版本化 逐目录设属性并提交
合并后代码重复一段 mergeinfo 没记上，同样的改动合了两次 查 --show-revs merged，必要时清属性重合
合并漏掉一部分改动 mergeinfo 记多了，SVN 以为合过 用 -c 显式指定版本号强制合
提交里混进不该有的文件 没有暂存区，全部改动一起进 提交前 svn diff + svn status，用路径参数挑文件
改名后历史断了 用资源管理器改名，没走 svn move 一律 svn move
E160013 URL not found 分支被改名或删除 svn switch 到新地址或重新 checkout
二进制文件被覆盖 没锁就改 加 svn:needs-lock，改前 svn lock
在错误的分支上提交 提交前没确认 URL 养成 svn info 看一眼
合并后忘了提交 合并只在本地 svn status 会显示一堆 M，提交它
tags 里的版本被人改了 tag 是目录，没有只读属性 配 pre-commit hook 拒绝对 /tags/ 的写

最后一条经验：SVN 的麻烦都来自「目录」这一个抽象。分支是目录、标签是目录、合并是两个目录之间的关系、权限也按目录发。你把它当成一台「有版本的共享文件服务器」来用，就不会期待它具备 Git 那样的本地能力，也就不会在「为什么不能离线提交」「为什么不能改提交说明」这类问题上卡住。
