Git 命令与工作流 #

版本控制的所有复杂度，都来自三件事：提交是一张有向无环图、分支只是贴在某个提交上的可移动标签、同一份仓库可以同时存在于多台机器上。把这三件事想通，「暂存」「合并」「回退」「拉取上游更新」就都只是"移动标签"和"搬运对象"的不同组合，而不是一堆要背的命令。

本文合并了原先的「Git 介绍和基本命令」「Git 常用操作」「Git 分支」「Git 撤销或回退」「Git 标签」「git 介绍及操作记录」「合并远端分支的更新」「Git 命令表」「在 Git 中忽略文件和文件夹」「GitHub 加速访问」「Git 同步时报错」「版本控制方案」共十二篇。

零、全景：我要做什么，敲什么 #

任务 命令 关键点
拿到一份代码 git clone 只克隆默认分支；大仓库加 --depth 1
把本地目录变成仓库 git init + git remote add 先 init 再关联 origin
我今天改了什么 git status -s / git diff status 看"哪些文件"，diff 看"哪些行"
提交 git add → git commit -m 两步分离是 Git 的核心设计，不是多此一举
同步 git pull --rebase / git push 拉用 rebase 保持线性，推用 --set-upstream 绑定
开新功能 git switch -c feat 等价于老写法 git checkout -b feat
提交碎了想整理 git rebase -i / git commit --amend 改写历史，只能在未 push 的提交上做
后悔了 git reset / git revert / git reflog 本地用 reset，已推送用 revert，救命用 reflog
临时走开 git stash 现场打包，git stash pop 还原
打版本 git tag -a v1.0 -m "..." 附注标签才带作者/日期/说明
合并别人的上游更新 git remote add + git fetch + git merge 见第七章完整流程

一、四个区域与五种状态 #

Git 把"文件"分成了四个物理位置，这是所有困惑的源头，也是所有能力的来源：

text
+-----------+   git add   +----------+   git commit   +-------------+   git push   +---------+
| 工作区    | ----------> | 暂存区   | -------------> | 本地仓库    | ----------> | 远程仓库 |
| Workspace |             | Index    |                | Repository  |             | Remote  |
+-----------+             +----------+                +-------------+             +---------+
     ^                         |                            |
     |       git checkout --   |        git reset           |
     +-------------------------+----------------------------+
  • Workspace（工作区）：你在资源管理器 / 编辑器里看到的那份文件。
  • Index / Stage（暂存区）：存放在 .git/index，是一份"下次提交的快照草案"。git add 就是把工作区的改动写进这里。
  • Repository（本地仓库）：.git/objects 里的对象库 + 一堆指针。git commit 把暂存区的内容固化成一次提交。
  • Remote（远程仓库）：另一台机器上的同一个仓库。git clone 把它复制过来，git push / git fetch 在两者之间搬对象。

文件状态 #

状态 含义 怎么进来 怎么出去
Untracked 库里没有这个文件 新建文件 git add → Staged
Modified 已跟踪，但工作区与库中快照不同 编辑已跟踪文件 git add → Staged
Staged 改动已进暂存区，等待提交 git add git commit → Unmodified
Unmodified 工作区与最近一次快照一致 commit 之后 编辑 → Modified
Ignored 被 .gitignore 排除，Git 假装看不见 写进忽略规则 删规则

正向工作流 #

text
git pull            # 1. 先取远端，别在过期代码上开发
    ↓  改代码……
git status / git diff    # 2. 看看自己动了什么
git add <file>      # 3. 挑出这次要提交的改动
git commit -m "..." # 4. 固化为一次提交
git push            # 5. 推上去

顺序里最容易被跳过的是第 1 步和第 2 步。跳过 pull 会制造无谓的分叉与冲突；跳过 diff 会提交进调试代码和密钥。

二、原理：提交链表、分支、HEAD、References #

提交是一张图 #

每一次 git commit 都在库里写入一个提交对象，内容包含：

  1. 一棵目录树（本次快照的文件名与内容哈希）；
  2. 父提交的 SHA-1（可能有两个，那就是合并提交）；
  3. 作者、提交者、时间、提交说明。

Git 对这个对象算一个 40 字节的 SHA-1（现在也有 SHA-256 仓库），所以提交是内容寻址的：同样的内容 + 同样的父提交，算出的 ID 一定相同。这也是为什么"同一个提交"可以在多台机器、多个仓库里被识别为同一个东西。

沿父指针往回走，就得到一条（或一张）提交链：

text
c1 <-- c2 <-- c3 <-- c4        (master)
                \
                 <-- c5 <-- c6  (feature)

分支 = 指针 #

所谓 master 分支，本质上只是文件 .git/refs/heads/master 里存的一行 SHA-1，指向 c4。「新提交」不过是：写一个新对象 → 把它设为当前分支的新值。

所以：

  • 创建分支 = 新建一个指针文件（开销近乎为零，这就是 Git 分支比 SVN 便宜的原因）；
  • 切换分支 = 把 HEAD 指到另一个分支，再把工作区改成那个提交的快照；
  • 删除分支 = 删一个指针文件；
  • 合并分支 = 建一个双亲提交；
  • rebase = 把一串提交复制到新基底上，然后移动指针。

HEAD #

HEAD 是"我现在站在哪个分支上"的指针，通常内容是一行 ref: refs/heads/master。切到某个具体提交上（detached HEAD）时，它退化为直接存一个 SHA-1——这时你的新提交不属于任何分支，切走就会"丢"，这也是新手最容易踩的坑。

References 的四种全名 #

全名 平时写法 含义
refs/heads/master master 本地分支
refs/remotes/origin/master origin/master 远端分支在本地的只读镜像
refs/tags/v1.0 v1.0 标签
HEAD HEAD 当前分支（或其指向的提交）

记住 origin/master 是远端分支的本地副本这一点非常重要：git fetch 只更新它，不碰你的工作区；git merge origin/master 才是真正把改动并进来。git pull = fetch + merge，所以"pull 之前想先看看"是完全可以做到的。

三、首次配置 #

身份（决定 commit 里的作者信息） #

bash
git config --global user.name  "Your Name"
git config --global user.email "you@example.com"

配置有三个层级，后写的覆盖先写的：系统级 /etc/gitconfig < 用户级 ~/.gitconfig（Windows 是 C:\Users\<用户名>\.gitconfig）< 仓库级 .git/config。只想给某个仓库单独换身份时，去掉 --global 即可。

SSH 密钥 #

bash
ssh-keygen -t ed25519 -C "you@example.com"   # 一路回车，公钥在 ~/.ssh/id_ed25519.pub
eval $(ssh-agent -s)
ssh-add ~/.ssh/id_ed25519
ssh -T git@github.com                        # 验证

公钥整行贴到平台的 Settings → SSH keys。之后 clone 要用 SSH 地址（git@host:owner/repo.git），HTTPS 地址仍然会问密码。

换行符（跨平台必配） #

bash
git config --global core.autocrlf true    # Windows：检出转 CRLF，提交转 LF
git config --global core.autocrlf input   # Linux/macOS：提交时把 CRLF 归一为 LF

不配这一项的后果是：在 Windows 上改了 3 行代码，diff 里却显示整个文件都变了。

默认编辑器 #

bash
git config --global core.editor "vim"
# Windows 下指向具体程序时路径要带引号，参数用单引号包一层
git config --unset --global core.editor   # 撤销

一组「建议一开始就打开」的开关 #

bash
git config --global status.showUntrackedFiles all   # 新建文件也出现在 status 里
git config --global push.default simple             # 只推当前分支到同名上游
git config --global pull.rebase true                # pull 默认用 rebase，保持线性历史
git config --global rebase.stat true                # rebase 时也显示改动统计
git config --global rerere.enabled true             # 记住冲突解法，重复冲突自动套用
git config --global rerere.autoupdate true          # 自动 git add 已解决的冲突
git config --global color.ui auto
git config --global core.pager "less -FRSX"         # 短输出不占满屏，退出不清屏
git config --global core.longpaths true             # Windows 长路径问题
git config --global init.defaultBranch main         # 新仓库默认 main

代理 #

bash
# HTTP 代理
git config --global http.proxy http://127.0.0.1:7890
git config --global https.proxy http://127.0.0.1:7890
# SOCKS5 代理（注意 http.proxy 也能塞 socks5://）
git config --global http.proxy socks5://127.0.0.1:7890
# 取消
git config --global --unset http.proxy
git config --global --unset https.proxy
# 可以按域名只给某站设代理，避免内网仓库也走代理
git config --global http.https://github.com.proxy http://127.0.0.1:7890

不带 --global 就只对当前仓库生效——这是"公司仓库不走代理、GitHub 走代理"的标准做法。

四、命令速查（按场景，不按字母表） #

4.1 获取代码 #

命令 说明
git clone <url> [dir] 克隆到 dir（省略则用仓库名）
git clone -b dev --single-branch <url> 只取 dev 一个分支，省带宽
git clone --depth 1 <url> 只取最新一次提交（浅克隆），日志不可查
git clone --recursive <url> 连同子模块一起克隆（默认不递归）
git init 把现有目录变成仓库
git init --bare x.git 建裸仓库，只有对象库没有工作区（服务器用）

4.2 提交 #

命令 说明
git add <file/dir> 加入暂存区；. 表示全部
git add -p 逐块挑选要暂存的内容（把一个文件拆成多次提交的利器）
git commit -m "msg" 提交暂存区
git commit -a -m "msg" 跳过 add，自动暂存已跟踪文件的改动（新文件仍要 add）
git commit --amend 修改上一次提交（内容 + 说明）
git commit --amend --author="Name <mail>" 连作者一起改
git commit -s 追加 Signed-off-by（内核 / 开源项目要求）
git rm <path> 删除文件并从索引移除
git rm --cached <path> 只从索引移除，本地文件保留（"别追踪它了"）
git mv <src> <dst> 移动/改名并同步索引

4.3 看状态与历史 #

命令 说明
git status -s 精简状态（?? 未跟踪，M 已改，A 已暂存）
git diff 工作区 vs 暂存区
git diff --staged 暂存区 vs 最近提交（即将提交的内容）
git diff HEAD -- <file> 工作区 vs 最近提交
git diff <branch> -- <file> / git diff <c1> <c2> 跨分支 / 跨提交比较
git log --oneline --graph --all 最常用的一条历史视图
git log -p -- <file> 带补丁看某文件历史
git log -S "keyword" 搜索"哪个提交引入了这段代码"（排障神器）
git blame <file> 逐行显示最后修改者与提交
git show <rev> 看某次提交的完整内容
git shortlog -sn 按人统计提交数

4.4 分支 #

命令 说明
git branch 列本地分支（带 * 的是当前分支）
git branch -a / -r 连同远端 / 只看远端
git branch <name> 新建分支但不切换
git switch -c <name> 新建并切换（旧写法 git checkout -b）
git switch <name> 切换（旧写法 git checkout <name>）
git branch -d <name> / -D 删除已合并 / 强制删除未合并
git branch -m <old> <new> 重命名
git branch -u origin/<name> 绑定上游（等价 --set-upstream-to）

4.5 远端 #

命令 说明
git remote -v 列出远端名与地址
git remote add <name> <url> 添加远端（可以是第二个、第三个上游）
git remote show <name> 远端详情（默认分支、跟踪状态）
git remote set-url <name> <url> 改地址
git remote remove <name> 删除远端
git remote prune origin 清掉远端已删除分支的本地镜像
git fetch --all 取所有远端更新（不动工作区）
git pull --rebase 取回并把本地提交重放到最新之上
git push -u origin <branch> 首次推送并绑定上游
git push origin <local>:<remote> 推到不同名的远端分支
git push origin --delete <branch> 真正删除远端分支

git branch -dr origin/xxx 只删本地那份"远端分支的镜像"，远端还在，下次 fetch 又回来。要真删必须 git push origin -d。

4.6 撤销与回退 #

命令 影响范围 历史
git restore <file>（旧 git checkout -- <file>） 丢弃工作区改动 不变
git restore --staged <file>（旧 git reset HEAD -- <file>） 撤销 git add 不变
git reset --soft <rev> 指针回退，改动留在暂存区 改写
git reset --mixed <rev>（默认） 指针回退，改动留在工作区 改写
git reset --hard <rev> 指针 + 工作区 + 暂存区全部回退 改写，未提交改动丢失
git revert <rev> 生成一个新提交来抵消旧提交 追加，不改写
git reflog 查看 HEAD 的移动轨迹 ——

4.7 标签 #

命令 说明
git tag 列出标签
git tag v1.0 轻量标签（只是一个指针）
git tag -a v1.0 -m "release 1.0" 附注标签（带作者、日期、说明，发布应该用这个）
git tag -a v1.0 <commit> 给历史提交补打标签
git show v1.0 查看标签内容
git push origin v1.0 / git push --tags 推单个 / 全部标签
git tag -d v1.0 + git push origin :refs/tags/v1.0 删本地 + 删远端
git checkout -b hotfix v1.0 从标签拉修复分支

git push 默认不推标签，这是标签"推不上去"的最常见原因。

4.8 暂存现场与拣选提交 #

bash
git stash                     # 打包当前改动，工作区回到干净状态
git stash -u                  # 连未跟踪文件一起打包（常用）
git stash list                # 查看栈
git stash show -p stash@{0}   # 看具体改了什么
git stash pop                 # 恢复并出栈
git stash apply               # 恢复但保留在栈里
git stash drop / clear        # 删一条 / 全清

git cherry-pick <commit>      # 把某个提交"复制"到当前分支
git cherry-pick <c1>..<c2>    # 复制一段（左开右闭）
git cherry-pick --continue / --abort

4.9 补丁 #

bash
git format-patch -1                 # 最近一次提交做成补丁
git format-patch -3                 # 最近三次，每个提交一个文件
git format-patch origin/master      # 当前分支领先上游的所有提交
git format-patch <c1>..<c2> -o out/ # 区间补丁并指定输出目录
git am < 0001-xxx.patch             # 应用 format-patch 生成的补丁（保留作者和说明）
git am -s *.patch                   # 批量应用并加 Signed-off-by

git diff > old.patch                # 老式补丁（无提交元信息）
git apply old.patch                 # 应用老式补丁

format-patch 生成的补丁用 git am 应用，git diff 生成的老式补丁用 git apply 应用，两者不能混。这是补丁类问题里最高频的错误。

4.10 子模块 #

bash
git submodule add <url> <path>       # 添加
git submodule update --init          # 初始化并检出到父仓库记录的提交
git submodule update --init --recursive   # 递归（子模块里还有子模块）
git submodule update --remote        # 更新到子模块远端的最新提交（维护者用）
git config submodule.<name>.url <new-url>          # 改子模块地址
git config -f .gitmodules submodule.<name>.branch <branch>  # 改跟踪分支
git mv <old> <new>                   # 移动子模块位置
git submodule deinit <path> && git rm <path>        # 删除子模块

两个关键点：--init 会把 dirty 状态的子模块恢复原状（没有它会更新失败）；不带 --remote 时 update 只把子模块定位到父仓库记录的提交，不是最新提交。

4.11 清理 #

bash
git clean -n            # 先干跑，看会删什么
git clean -fd           # 删除未跟踪文件与目录
git clean -fdx          # 连 .gitignore 里的文件一起删（构建产物清理）

git clean 删除的东西不进回收站，先用 -n 干跑一次。

五、分支与合并 #

合并的两种形态 #

text
fast-forward（快进）              三方合并（--no-ff）
c1--c2--c3 (master)              c1--c2--c3------M (master)
         \                                \      /
          c4--c5 (feat)                    c4---c5 (feat)
master 指针直接前移到 c5          M 有两个父提交，分支拓扑被保留
  • 当当前分支没有任何新提交时，默认就是快进，历史是一条直线，看不出"这里曾经有过一个分支"。
  • git merge --no-ff <branch> 强制生成合并提交，能在 git log --graph 里看到功能分支的完整轮廓——团队协作、需要"一个功能一次合并"的项目应该默认用它。

标准合并流程 #

bash
git switch master
git pull --rebase            # 先对齐远端
git merge --no-ff feat       # 合并
# 有冲突：
git status                   # 列出 both modified 的文件
#   打开文件，处理 <<<<<<< ======= >>>>>>> 之间的人工抉择
git add <resolved-file>      # 逐个标记已解决（这一步不能忘）
git commit                   # 完成合并提交（说明可保留默认）
# 反悔：
git merge --abort            # 回到合并前
git merge --continue         # 冲突解决后继续被中断的合并

冲突的本质是"同一个文件的同一处，两条历史给出了不同内容"，Git 不会替你选。解决完必须 git add，因为 Git 靠"索引里是否还有未合并条目"判断能不能提交。

推一个新分支 #

bash
git push --set-upstream origin feat:feat   # 本地名:远端名，同名也要写两遍
# 忘了 -u 的补救：
git branch --set-upstream-to=origin/feat

绑定上游只需做一次；不绑定的话以后每次 push/pull 都得把分支名写全。

六、撤销与回退：按"改动到了哪一步"来选命令 #

这是所有 Git 操作里最容易搞坏东西的一块。判断依据只有一个：这次改动走到哪一步了？

情况 1：改了文件，还没 add #

bash
git restore <file>        # 丢弃单个文件的改动
git restore .             # 丢弃全部（危险，不可恢复）
git diff <file>           # 先看清楚再说

情况 2：add 了，还没 commit #

bash
git restore --staged <file>   # 只撤销"加入暂存区"这一步，工作区改动仍在

情况 3：commit 了，还没 push #

bash
git reset --soft HEAD~1   # 撤销提交，改动回暂存区（想"重新组织这次提交"时用）
git reset HEAD~1          # 撤销提交，改动回工作区
git reset --hard HEAD~1   # 连改动一起删掉（不可恢复，靠 reflog 才有救）
git commit --amend        # 只是说明写错了 / 漏了一个文件

情况 4：已经 push 了 #

bash
git revert <commit>       # 生成一个反向提交，历史保留，这是协作场景下的正确做法
git revert -m 1 <merge-commit>   # 撤销一个合并提交，-m 1 表示保留第一父提交那一侧

reset 与 revert 的区别 #

git reset git revert
做了什么 移动分支指针 新增一个"反向补丁"提交
历史 被改写（提交"消失"） 只追加，不改写
已推送的仓库 需要 push -f 且会破坏他人历史 直接 push 即可
适用场景 本地、私有分支 公共分支、发布后回滚

判断口诀：只要别人可能已经拉过这段历史，就用 revert；只在本地，随便折腾。

reflog：误操作的最后一道保险 #

bash
git reflog                     # 最近所有 HEAD 移动记录（含 reset、rebase、checkout）
git reset --hard HEAD@{3}      # 回到 reflog 里的某个位置

reset --hard 之后提交对象并没有立刻被删除，只是没有指针指过去了，默认还能在 .git 里存活两周（gc.reflogExpire）。所以"刚 reset 错了"几乎总是可救的——前提是你没有紧接着跑 git gc --prune=now。

七、多远端：合并上游仓库的更新 #

这是"二次开发 / 从官方仓库 fork 出来做了定制"的场景，也是最实用的一个完整案例。

仓库拓扑 #

text
denx（官方上游） ----clone----> origin（自己的服务器） ----clone----> 本地仓库
                                                                    |
                                                              日常工作在这里

本地仓库 clone 自 origin 时，Git 自动把 origin 记成远端别名；要拿官方更新，需要把 denx 也加成远端。

步骤 1：确认现状并添加上游 #

bash
git remote -v                 # 看当前有哪些远端
git remote add denx http://git.denx.de/u-boot.git
git remote show denx          # 确认地址和上游分支列表
git fetch denx                # 取回 denx 的所有分支和标签（不动工作区）
git branch -r                 # 现在能看到 denx/master、origin/master 两套镜像

步骤 2：在自己的分支上合并上游 #

bash
git switch -c xdev_merge origin/master   # 基于 origin/master 开一个临时合并分支
git merge denx/master                    # 若本地无定制，此处是快进；有定制则可能冲突
git log --oneline -5                     # 确认合并结果
git push origin xdev_merge:master        # 推回去（本地名:远端名）

步骤 3：合并到有定制内容的分支会遇到冲突 #

bash
git switch -c xdev_merge2 origin/x_integration
git merge denx/master
# 输出里会列出 CONFLICT 的文件，git status 里显示 both modified:
#   both modified:   arch/arm/dts/Makefile
#   both modified:   drivers/gpio/s5p_gpio.c
# 逐个手工合并后：
git add arch/arm/dts/Makefile drivers/gpio/s5p_gpio.c
git commit                       # 默认合并说明即可
git push origin xdev_merge2:x_integration

合并完一定要编译一遍再推。上游改了 API、改了 Kconfig 默认值这类问题，Git 是看不出来的，只有编译器和板子能看出来。

顺手会把默认分支改对 #

如果这个仓库的日常开发都在 x_integration 上，把远端仓库的默认分支改成它（GitHub：Settings → Branches；Gitea：仓库设置 → 分支），之后所有人的 git clone 直接落在正确的分支上，省掉一次手工切换。

八、团队分支模型 #

小团队里比"用哪条命令"更重要的是"用哪条分支"。一套能落地的四层模型：

分支 内容 谁能推 用途
主分支 main / master 代码 + 文档 管理员（只接受合并） 发布版本，每次提交都应可交付
开发分支 develop 完整源码 管理员 集成各人成果，仅管理员可见
运行分支 release 头文件 + 库文件 管理员 只暴露稳定接口，所有人可见
人员分支 dev/name 个人源码 本人 基于运行分支创建，日常提交都在这里

流程：

  1. 每个人只往自己的 dev/<name> 提交；
  2. 提 PR/MR 或直接告知管理员，由管理员评审；
  3. 管理员把通过的改动合入开发分支，构建验证后再合入主分支 / 更新运行分支的库文件。

配套建议：

  • 主分支与开发分支开启分支保护（禁止强推、禁止直接 push、要求评审）；
  • .gitignore 全局化（见第九章），避免 node_modules、构建产物、编辑器配置被提交；
  • 提交说明统一前缀（feat: / fix: / docs:），历史可读性收益极大。

九、.gitignore：让 Git 假装看不见 #

三类文件状态 #

状态 含义
tracked 已被 Git 记录的文件
untracked 工作区里有、但没被记录的
ignored 被忽略规则排除，git status 不显示，git add 也不收

规则语法 #

写法 含义
/text.txt 只忽略根目录下的 text.txt
text.txt 忽略任意层级的 text.txt
/test/text.txt 或 test/text.txt 忽略根下 test 目录里的它
test/ 忽略整个 test 目录及其内容（末尾斜杠表示"是目录"）
*.md 忽略所有 .md
img* 忽略所有以 img 开头的文件/目录
!keep.md 取反：把之前被排除的重新纳入
**/logs 任意深度的 logs 目录
.env* 所有 .env 变体（含 .env.local）

对应到仓库里的实例（本站点自己的规则就是这么一个典型）

text
# 依赖与构建产物
1.site/node_modules/
1.site/dist/
1.site/.pagefind-cache/
# 缓存与临时脚本
.npm-cache/  .tmp/  __pycache__/  *.pyc  .cache/
# 系统与编辑器
.DS_Store  Thumbs.db  *.log

把"已经提交过"的文件变成被忽略 #

忽略规则只对未跟踪文件生效。已经进了库的文件，要先从索引里摘掉：

bash
echo ".env" >> .gitignore
git rm --cached .env        # 从索引移除，本地文件保留
git add .gitignore
git commit -m "chore: stop tracking .env"

如果这个文件已经在历史里待了很多次提交，rm --cached 只解决"以后"，历史里的副本仍然在。要彻底清理得用 git filter-repo（见《Git 服务器搭建与运维》维护一节）。

强烈建议的全局忽略 #

bash
git config --global core.excludesFile ~/.gitignore_global

在 ~/.gitignore_global 里写 .DS_Store、Thumbs.db、.idea/、.vscode/、~$*（Office 临时文件）、*.swp，这样每个新仓库都不用再抄一遍。

十、网络问题与大文件 #

典型症状 #

text
error: RPC failed; curl 92 HTTP/2 stream 7 was not closed cleanly: CANCEL (err 8)
error: RPC failed; curl 56 Failure when receiving data from the peer
error: 6920 bytes of body are still expected
fetch-pack: unexpected disconnect while reading sideband packet
fatal: early EOF
fatal: fetch-pack: invalid index-pack output

这组报错的共同点是传输被中途掐断，原因通常是网络不稳、代理设置错、HTTP/2 实现不兼容，或者单个 pack 太大。

按命中率排查 #

1）关掉或换对代理（最常见）

bash
git config --global --unset http.proxy
git config --global --unset https.proxy
# 或者确认代理真的可达
git config --global http.proxy http://127.0.0.1:7890

代理开着但代理本身不通，报错就是上面这一串。

2）降级到 HTTP/1.1

bash
git config --global http.version HTTP/1.1

HTTP/2 的多路复用在弱网下容易触发 stream ... CANCEL，退回 1.1 通常立刻好转。

3）调大缓冲区、关压缩

bash
git config --global http.postBuffer 524288000     # 500 MB
git config --global http.maxRequestBuffer 524288000
git config --global core.compression 0

4）限制并发

bash
git config --global http.maxRequests 10

5）只取需要的分支 / 浅克隆

bash
git clone --single-branch --branch <branch> <url>
git clone --depth 1 <url>

先拿到能用的代码，之后 git fetch --unshallow 补全历史。

6）确认远端地址没错

bash
git remote -v
git remote set-url origin <correct-url>

7）升级 git 与 curl

bash
git --version && curl --version
sudo apt update && sudo apt install -y git curl

对应的 .gitconfig 片段 #

ini
[user]
    name = Your Name
    email = you@example.com
[http]
    postBuffer = 524288000
    maxRequests = 10
    version = HTTP/1.1
[core]
    editor = vim
    autocrlf = true

直接编辑 ~/.gitconfig 与 git config 完全等价，前者适合一次性抄一大段。

GitHub 访问加速 #

这类镜像站的可用性变化很快，能直连时优先直连，把镜像当兜底。

场景 做法
克隆 镜像前缀：git clone https://gitclone.com/github.com/owner/repo
克隆 换域名的镜像站（如 github.hscsec.cn、mirror.ghproxy.com）
Release / 归档下载 gh-proxy 类加速：https://ghproxy.net/https://github.com/owner/repo/releases/download/...
raw 文件 raw.githubusercontent.com 换成 raw.gitmirror.com 或 raw.staticdn.net
前端 CDN jsDelivr：https://cdn.jsdelivr.net/gh/owner/repo@version/path（不支持 Release 附件）
自建 用 Cloudflare Workers 部署 gh-proxy，自带 CDN 且不占自己服务器

大文件不是 Git 的活 #

单文件超过 50 MB、仓库超过 1~2 GB 之后，clone 会明显变慢，因为 Git 存的是每个版本的完整对象（压缩后），二进制文件几乎压不动。正确做法是 Git LFS 或不放进 Git——具体配置见《Git 服务器搭建与运维》。

十一、坑位速查 #

现象 原因 解法
改了 3 行，diff 显示整个文件都变了 换行符 配 core.autocrlf；必要时 --ignore-cr-at-eol 看图
detached HEAD 后提交"消失" 提交不在任何分支上 当时就 git switch -c newbranch，事后用 reflog 找
分支删了想找回来 指针没了但对象还在 git reflog 找到 SHA 再 git branch xx <sha>
git push 被拒 non-fast-forward 远端有你没有的提交 先 git pull --rebase，不要无脑 push -f
标签推不上去 push 默认不推标签 git push origin --tags
git branch -dr 删了远端分支还在 只删了本地镜像 git push origin -d <branch>
冲突解决后提交不了 忘了 git add git status 里还有 both modified 就说明没解决完
子模块更新失败（dirty） 缺 --init git submodule update --init --recursive
补丁应用失败 "patch does not apply" 补丁类型与命令不匹配 format-patch→am，diff→apply
Windows 上路径过长报错 MAX_PATH git config --global core.longpaths true
一直要求输入密码 用了 HTTPS 地址 / 公钥没生效 改用 SSH 地址，ssh -T 验证
误 git clean -fdx 未跟踪文件不可恢复 只能从编辑器/系统备份找回，先 -n 干跑

小结 #

  1. 提交是图，分支是标签，HEAD 是指向标签的标签。 想通这一点，"回退"就是移指针，"rebase"就是复制节点。
  2. 暂存区是为了让你挑拣改动，而不是流程负担；git add -p 是把一堆乱改拆成若干干净提交的地方。
  3. 改写历史（reset / amend / rebase）只对没推出去的提交做；一旦推出去，改用 revert。
  4. 多远端是常态：origin 是自己的，denx / upstream 是上游的，fetch 只搬对象，合不合、怎么合由你决定。
  5. 网络问题先查代理和 HTTP/2，大文件交给 LFS——这两类占了"Git 用不起来"的大半。
