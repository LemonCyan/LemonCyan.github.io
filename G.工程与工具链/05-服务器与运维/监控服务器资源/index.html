服务器卡顿、告警响起、业务假死，很多人的第一反应是重启，但重启只会掩盖问题。排查服务器性能瓶颈，核心就是搞清楚 CPU、内存、磁盘 I/O 和网络这四大件到底哪个在排队。

本文按四大核心资源梳理排查链路与工具，命令和诊断阈值全部可以直接落地。

1. 全景工具：USE 方法论与 top / htop #

排查系统性能遵循 Brendan Gregg 提出的 USE 方法论：

  • U (Utilization)：使用率，资源有多忙（如 CPU 占用 90%）；
  • S (Saturation)：饱和度，有多少任务在排队等候（如 Load Average 高于核数、Swap 持续换入换出）；
  • E (Errors)：错误数，网卡丢包、磁盘坏块等异常指标。

1.1 top：自带的基础看板 #

任何一台 Linux 机器都有 top。敲下 top 后，记住以下几个按键：

按键 行为 作用场景
1 展开所有 CPU 逻辑核心 查看是否有单核被单线程程序跑满
M 按内存占用（%MEM）降序排列 快速找内存泄漏或大内存进程
P 按 CPU 使用率（%CPU）降序排列 默认排序，抓高耗 CPU 进程
c 切换显示进程完整启动命令与参数 区分同名的一堆 java/node 到底跑的哪个服务
k 输入 PID 发送信号（默认 15 TERM，加 9 为 KILL） 直接在面板里杀掉失控进程
q 退出 —

第一行头部字段先看三样：

text
top - 14:20:00 up 120 days,  2:10,  2 users,  load average: 3.12, 1.85, 0.90
Tasks: 180 total,   2 running, 178 sleeping,   0 stopped,   0 zombie
%Cpu(s): 75.2 us, 12.1 sy,  0.0 ni, 10.5 id,  2.0 wa,  0.0 hi,  0.2 si,  0.0 st
  • load average：过去 1 分钟、5 分钟、15 分钟的系统平均负载；
  • Tasks zombie：僵尸进程数量，大于 0 说明有父进程死掉未回收子进程；
  • %Cpu(s)：
    • us（user）：用户态进程消耗，业务代码、数据库算力集中在这里；
    • sy（system）：内核态消耗，系统调用频繁或中断过多时偏高；
    • wa（iowait）：等待 I/O 完成的时间百分比。若 wa > 20% 且 load 很高，瓶颈在磁盘或网络存储，不在 CPU 算力；
    • st（steal）：云服务器宿主机超卖被其他 VPS 抢走的 CPU 时间，大于 5% 说明云主机遭邻居争抢。

1.2 htop：更直观的交互式排查 #

htop 比 top 多了色彩显示、鼠标点击、树状进程关系以及直接看 Swap 进度条：

bash
sudo apt install -y htop   # Debian / Ubuntu
sudo dnf install -y htop   # RHEL / Rocky
htop

核心操作：

  • F3：搜索进程名；
  • F4：过滤进程；
  • F5：树状视图（Tree），查看父子进程派生关系（例如看 Nginx worker 是哪个 master 起的）；
  • F6：选择排序列（按 CPU%、MEM%、TIME+ 等排序）；
  • F9：发送信号杀进程（列出全部信号，选 SIGKILL 或 SIGTERM）。

2. CPU 负载诊断：算力耗尽还是 I/O 阻塞 #

2.1 Load Average 到底怎么算 #

Load Average 是处于 R 状态（可运行/运行中） 与 D 状态（不可中断睡眠，通常在等磁盘 I/O） 的平均进程数。

对比基准是系统的逻辑 CPU 核心总数：

bash
# 查看 CPU 逻辑核心数
nproc
# 或者
grep -c ^processor /proc/cpuinfo

健康判定：

  • Load < 逻辑核数：资源充裕，随到随处理；
  • Load ≈ 逻辑核数：满载，没有浪费但也无缓冲余量；
  • Load > 逻辑核数 × 2：明显排队，开始堆积请求；
  • Load 长期 > 逻辑核数 × 5：严重拥堵，响应超时、连接堆积。

2.2 区分 CPU 密集还是 I/O 假高 #

现象 %us / %sy %wa 根因
CPU 密集型 极高（>80%） 极低（<2%） 死循环、密集加密/解压、未建索引的大 SQL、编译代码
I/O 等待型 偏低（<20%） 极高（>30%） 磁盘吞吐打满、NFS 挂载点卡死、慢查询读盘

查看每个核心是否均衡：

bash
# 需安装 sysstat
sudo apt install -y sysstat

# 每秒刷新一次各核心状态，共采集 3 次
mpstat -P ALL 1 3

若发现只有某个核心 CPU 0 占用 100%，其余都是 0%，说明有单线程程序（如 Node.js 单实例、Redis 单线程执行了大 key 操作）跑死，需做多实例部署。

定位具体吃 CPU 的进程和线程：

bash
# 查看每个进程的 CPU 细分消耗
pidstat -u 1 3

# 找出进程内部哪个线程（TID）最耗 CPU
pidstat -p <PID> -t 1 3

3. 内存诊断：为什么内存占用 80% 往往不用慌 #

3.1 free -h 的正确阅读方式 #

bash
free -h

典型输出：

text
               total        used        free      shared  buff/cache   available
Mem:            15Gi       4.2Gi       1.1Gi       210Mi        10Gi        11Gi
Swap:          4.0Gi       120Mi       3.9Gi

误区提醒：

  • 不要看 free：很多初学者看到 free 1.1Gi 就以为内存快满了。
  • 看 available：当前可用内存是 available（这里有 11Gi）。

Linux 的内存设计哲学是「空闲内存就是浪费」。内核会把闲置的物理内存全部借用来做文件系统的页缓存（buff/cache），提升磁盘读写命中率。当有应用程序需要新分配内存时，内核会在毫秒级丢弃这部分缓存腾给应用。

真正危险的信号是：available 接近 0，且 Swap 出现高频的进出。

3.2 Swap 抖动与 vm.swappiness #

Swap 是在磁盘上划出的一块虚拟内存空间。物理内存吃紧时，内核把不常用的内存页挪到 Swap 里。

通过 vmstat 观察 Swap 活跃度：

bash
# 每 1 秒刷新一行
vmstat 1

重点看 swap 列下的两项：

  • si（swap in）：每秒从 Swap 换入到物理内存的大小（KB/s）；
  • so（swap out）：每秒从物理内存写入 Swap 的大小（KB/s）。

判断标准：

  • 如果 Swap 用了几百兆，但 si 和 so 长期是 0，这是健康状态（冷数据呆在 Swap 里，物理内存留给活跃业务）；
  • 一旦 si 和 so 持续大于几兆（例如几十 MB/s），说明内存彻底耗尽，系统正疯狂在磁盘和内存间倒腾数据，由于磁盘比内存慢千倍，整机会瞬间进入卡死假死状态。

生产参数建议：

bash
# 查看当前 swappiness（默认常为 60，偏激进）
cat /proc/sys/vm/swappiness

# 调到 10：尽量使用物理内存，只有在真正撑不住时才换出
sudo sysctl -w vm.swappiness=10

# 永久写入
echo 'vm.swappiness = 10' | sudo tee -a /etc/sysctl.d/99-swappiness.conf

3.3 别乱跑 drop_caches #

网上大量教程教人在内存高时跑这行命令：

bash
# 生产慎用！
sync && echo 3 | sudo tee /proc/sys/vm/drop_caches

为什么不要盲目跑： 它强行丢弃了所有 Clean Page Cache。跑完的一瞬间，free 确实变大了，但随后的全部数据库查询、文件读取都必须重新去打真实磁盘。如果此时有生产高并发流量，磁盘 IOPS 会瞬间被打爆，导致数据库查询耗时从 2ms 飙升至几秒。除非在做基准测试需要控制初始变量，否则不要跑。

3.4 OOM Killer 追查 #

当物理内存与 Swap 完全耗尽，内核为了保住系统不崩溃，会根据算法给各进程打分并杀死最占内存的进程。

排查是否发生过 OOM：

bash
# 查内核环形缓冲区
sudo dmesg -T | grep -i oom

# 或从 systemd 日志查
sudo journalctl -k -g "Out of Memory" --no-pager

如果看到 Killed process 12345 (mysqld)，说明 MariaDB/MySQL 被内核 OOM 杀死了，必须按我们在 WordPress.md 里讲的调整 innodb_buffer_pool_size 和 PHP-FPM 的 pm.max_children，留足缓冲。

4. 磁盘空间与 I/O 瓶颈 #

4.1 磁盘写满的两种死法：块存储满与 Inode 耗尽 #

死法一：容量满了（100%） #

bash
df -h

如果挂载点 / 的 Use% 到了 100%，排查大文件：

bash
# 在根目录查找最大的 10 个目录/文件（排除了其他挂载盘）
sudo du -ahx / | sort -rh | head -n 10

# 交互式工具推荐：ncdu（需 apt install ncdu）
sudo ncdu /

死法二：Inode 用光了（Inode 100%） #

容量明明还有几十 GB，但新建文件、解压甚至 touch a 都报错 No space left on device：

bash
df -i

如果 IUse% 是 100%，说明磁盘上产生了数百万个极小的碎文件（最常见于 PHP session 目录没配置定时清理、或是邮件队列 spool/mqueue、未轮转的小日志）：

bash
# 统计哪个目录下的小文件最多
sudo find / -xdev -printf '%h\n' | sort | uniq -c | sort -k 1 -n | tail -n 10

删了文件但空间没降？ #

把几个 G 的日志 rm -f app.log 删除了，但 df -h 空间纹丝不动。原因是某个后台进程依然开着这个文件的句柄，内核只删了目录索引，数据块并未释放：

bash
# 查看所有已删除但被进程占用的文件
sudo lsof +L1
# 或
sudo lsof | grep deleted

输出中会列出占用的进程 PID。给该进程发 systemctl reload 或平滑重启，句柄关闭后空间瞬间恢复。

4.2 磁盘 I/O 饱和排查 #

磁盘读写成了瓶颈，CPU 和内存就会全卡在 I/O 等待上。

使用 iostat 观察磁盘物理表现：

bash
# 需 sysstat 包，每秒采集一次扩展统计
iostat -xz 1 5

重点关注以下四列：

  • r/s 与 w/s：每秒读/写完成的次数（IOPS）；
  • rkB/s 与 wkB/s：每秒读/写的吞吐量（KB/s）；
  • await：读写请求的平均响应时间（毫秒）。SSD 正常在 1ms~5ms；机械盘在 10ms~20ms。如果 await 超过 50ms 甚至数百毫秒，说明 I/O 已经严重拥堵；
  • %util：设备利用率。长期超过 80%~90% 说明磁盘已打满，写入已经出现排队。

定位疯狂刷盘的罪魁祸首：

bash
sudo apt install -y iotop
sudo iotop -oP

参数 -o 表示只显示有实际 I/O 读写的进程，一秒抓出正在高频刷盘的进程 PID 和速度。

5. 网络流量与 TCP 连接状态 #

5.1 网卡吞吐与丢包 #

bash
# 查看网卡实时上下行速率
sar -n DEV 1 3
  • rxkB/s：每秒接收的数据（KB/s）；
  • txkB/s：每秒发送的数据（KB/s）；
  • rxpck/s / txpck/s：包速率（PPS）；
  • 如果 rxdrop/s 大于 0，说明内核接收队列溢出，在丢包。

终端简易带宽看板：

bash
sudo apt install -y nload
nload

5.2 TCP 连接状态分析 #

bash
# 快速统计当前系统的 TCP 连接概况
ss -s

输出示例：

text
Total: 185
TCP:   32 (estab 14, closed 2, orphaned 0, timewait 2)

细分排查所有连接：

bash
# 统计各状态连接数分布
ss -ant | awk '{print $1}' | sort | uniq -c | sort -rn

常见状态异常处理：

  • CLOSE_WAIT 堆积：说明被动关闭方（本机应用）收到了远端 FIN，但本机的应用程序代码迟迟没有调用 close() 关闭 Socket。这是典型的应用层连接池或代码 Bug，必须重启对应服务并修复代码；
  • TIME_WAIT 堆积：高并发短连接服务的正常现象。若堆积上万导致本地端口号耗尽，在 /etc/sysctl.d/99-nginx.conf 中开启端口复用：
    ini
    net.ipv4.tcp_tw_reuse = 1
net.ipv4.ip_local_port_range = 1024 65535

查看某个端口当前与哪些外部 IP 建立了连接：

bash
# 查看连在 80/443 上的外部 IP 统计排行 Top 10
ss -ant '( sport = :80 or sport = :443 )' | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn | head -10

症状 首选用工具 关键指征 处理动作
全站响应变慢，Load 居高不下 top / htop %us 很高 找出高占用 PID，看是否死循环；应用加缓存或扩容
Load 极高但 CPU 使用率很低 top + iostat -xz 1 %wa > 20%，%util 接近 100% 磁盘 I/O 饱和；用 iotop -oP 抓进程；换 SSD 或优化慢查询
系统突发假死，服务被莫名杀掉 dmesg -T 出现 Out of Memory 日志 内存被打满，调小 FPM max_children 或数据库缓冲池
磁盘报空间已满但找不到大文件 df -i + lsof +L1 IUse% 100% 或有大量 deleted 句柄 清理 session 碎文件；重启持有 deleted 文件的进程
