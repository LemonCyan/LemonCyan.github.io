本篇讲什么：把 Portainer CE 部署起来，然后用它管容器、镜像、网络、卷，用 Stacks 管 Compose 编排，最后落到多主机、用户权限、备份和安全边界。

本篇不讲什么：Docker 命令本身怎么用、Compose 的 YAML 语法细节、Dockerfile 怎么写。这些在同一个目录的其余两篇里——《Docker：命令、网络、存储与镜像构建》和《Docker Compose：编排语法与实战》。

一句话定位：Portainer 不替代命令行。它把 Docker API 包了一层 Web 界面，你在界面上点的每个按钮，底层都是一条 Docker API 调用。命令行能做的它大部分能做，命令行做不到的它也做不到。

一、Portainer 是什么 #

Portainer 是一个用 Go 写的 Web 应用。整个产品就是一个容器镜像，跑起来之后对外提供 HTTP（9000）和 HTTPS（9443）两个端口，浏览器打开就是一套管理界面。

它管的范围就是 Docker 那几样东西，没有额外发明概念：

对象 对应 Docker 概念 Portainer 里的位置
容器 container Containers
镜像 image Images
网络 network Networks
卷 volume Volumes
编排项目 compose project Stacks

关键一点：Portainer 自己也是一个容器。它要管宿主机的 Docker，就必须能跟宿主机的 dockerd 说话。两种接法——挂 docker.sock，或者连 dockerd 的 TCP 端口。前者最省事，也是下面部署时用的方式。

text
浏览器
  │  HTTP / HTTPS（9000 / 9443）
  ▼
Portainer 容器
  │  Docker API（/var/run/docker.sock 或 tcp://host:2375）
  ▼
dockerd（宿主机）
  │
  ▼
容器 / 镜像 / 网络 / 卷

这条链条很长。浏览器到 Portainer 是一段，Portainer 到 dockerd 是一段，dockerd 到真实资源又是一段。中间任何一环断了，界面上就是转圈或者一片红。排错顺序也从这里来：先看 Portainer 容器活没活，再看 docker.sock 通不通，最后才看那个目标容器自己出了什么问题。

1.1 CE 与 BE 的分界线 #

CE 是 Community Edition，免费。BE 是 Business Edition，订阅收费。两者共用同一套代码基线，差在能力包和管理功能上。

能力 CE（社区版） BE（商业版）
费用 免费 按节点订阅
容器 / 镜像 / 网络 / 卷管理 有 有
Stacks（Compose 编排） 有 有
多环境（Environment）接入 有 有
多用户 / 团队 有 有
按环境赋权 有 有
细粒度 RBAC（到命名空间、到资源） 无 有
外部认证（LDAP / AD / OAuth 等） 无 有
审计日志、配额、合规报表 无 有
官方支持 社区论坛 商业 SLA

本篇只讲 CE。BE 的功能在界面上能看到入口，但没有授权就用不了——别照着 BE 的文档在 CE 里找按钮，找不到是正常的。

1.2 它不改变 Docker 的工作方式 #

第一次用的人容易误会，以为 Portainer 是某种「更高级的 Docker」。不是。它没有自己的运行时，也不接管 dockerd，更不会替你把容器跑起来。删掉 Portainer 容器，宿主机上的业务容器照样跑——因为那些容器本来就是 dockerd 在管。

界面上每个动作，底下都是一条具体的命令。对照表值得记一下：

你在界面上做的事 底层对应的命令
点 Start docker start <id>
点 Stop docker stop <id>
点 Remove docker rm <id>
打开 Logs docker logs -f <id>
打开 Console docker exec -it <id> sh
点 Pull image docker pull <image>
Stacks 里点 Deploy docker compose up -d
点 Prune unused docker image prune

记住这张表有两个好处。

一是界面上缺的功能，去命令行补，别指望 Portainer 有隐藏能力。它做的事就是把 API 画成按钮，API 没有的能力它变不出来。

二是界面上出现怪现象，用命令行复现一遍，能立刻分清是 Portainer 的问题还是 Docker 的问题。同一个容器在界面上起不来、命令行 docker run 也起不来，那问题在镜像和宿主机，不在面板。

Docker 自身的限制它也绕不过：容器没挂的目录，Console 里照样看不到；镜像没有的 tag，点多少次 Pull 都拉不下来；容器网络不通，界面上换个端口映射也不会自动修好。

二、部署 Portainer CE #

前提两条：宿主机装好 Docker Engine，装好 Compose 插件。确认一下：

bash
docker version
docker compose version

两条都有版本号再往下走。

2.1 先建数据卷 #

Portainer 自己的数据（管理员账号、环境配置、Stacks 定义、加密后的凭据）全在容器的 /data 下。先给它一个命名卷：

bash
docker volume create portainer_data

用 docker volume ls 确认：

bash
docker volume ls | grep portainer

text
local     portainer_data

2.2 写 docker-compose.yml #

新建一个目录放配置，把文件写进去：

bash
mkdir -p ~/portainer && cd ~/portainer

yaml
services:
  portainer:
    image: portainer/portainer-ce:latest
    container_name: portainer
    ports:
      - 9094:9000
    volumes:
      - portainer_data:/data
      - /var/run/docker.sock:/var/run/docker.sock
    restart: unless-stopped

volumes:
  portainer_data:

这份文件的信息量集中在四处。

portainer/portainer-ce:latest 是社区版镜像。生产上把 latest 换成具体 tag，免得哪天重启顺手拉了个新版本上来，界面变了都找不到按钮。

9094:9000 把宿主机 9094 映射到容器内 9000。9000 是 Portainer 的 HTTP 端口。宿主机的 9000 早被别的东西占了，所以换成 9094，换成别的空闲端口也行。

portainer_data:/data 挂命名卷。容器删了重建，账号和 Stacks 都还在。

/var/run/docker.sock:/var/run/docker.sock 是它能干活的前提。宿主机 Docker 的 Unix socket 被原样挂进容器，Portainer 才有权限去调 dockerd。这一行也是最大的风险点，第三章展开。

顶层的 volumes: 那两行别省。省了 Docker 会报卷未定义。而卷已经用 docker volume create 建好了，Compose 会直接复用同名卷，不会重建。

2.3 启动 #

bash
docker compose up -d

看到 Container portainer Started 就行。再确认一下：

bash
docker ps --filter name=portainer

text
CONTAINER ID   IMAGE                           STATUS          PORTS
a1b2c3d4e5f6   portainer/portainer-ce:latest   Up 5 seconds    8000/tcp, 9443/tcp, 0.0.0.0:9094->9000/tcp

状态是 Up 就通了。起不来看日志：

bash
docker logs portainer

常见的是端口被占（bind: address already in use）和 socket 权限不对（permission denied）。

2.4 第一次访问 #

浏览器打开：

text
http://localhost:9094

注意是 http://，不是 https://。9094 映射到的是容器内的 9000，那是明文 HTTP 端口。

第一次访问会要求设置 admin 密码，密码有长度下限（当前要求 12 位）。这个初始化页面有时限——默认 5 分钟内不设置，Portainer 会锁掉初始化入口，之后只能删卷重来。所以别开着页面去泡咖啡。

设完密码登录，下一步是选环境。本机部署就是 Local，它对应挂进来的 docker.sock。点进去就是主界面。

2.5 不用 Compose 的等价写法 #

只有一台机器、不想留 yml 的话，一条命令等价：

bash
docker run -d \
  --name portainer \
  --restart=unless-stopped \
  -p 9094:9000 \
  -v portainer_data:/data \
  -v /var/run/docker.sock:/var/run/docker.sock \
  portainer/portainer-ce:latest

两条路选一条。用 Compose 的好处是配置留在文件里，换机器复制粘贴就能重来，改端口改镜像都在文本里，不用翻命令历史。

三、部署时的四个注意点 #

这四条是踩出来的，跟版本没关系，换个环境照样成立。

3.1 端口：9094 后面是 9000，也就是 HTTP #

9094:9000 把宿主机 9094 映射到容器内的 HTTP 端口 9000，所以访问地址是 http://，不是 https://。照着 https 敲，浏览器会给你一个 ERR_SSL_PROTOCOL_ERROR。

Portainer 另有 HTTPS 端口 9443。要用它，把映射改成 9094:9443：

yaml
services:
  portainer:
    ports:
      - 9094:9443

重启容器后访问 https://localhost:9094，浏览器会提示自签证书，点继续就行。自签证书只适合内网和调试；对外提供服务就让反向代理去管证书，别指望容器里那张自签的。

容器端口 协议 访问写法 说明
9000 HTTP http://host:9094 素材里的映射方式
9443 HTTPS https://host:9094 需把映射改成 9094:9443，自签证书

端口号以所用版本的文档为准。版本升级后端口有调整的话，先看 docker ps 里暴露了哪几个端口，比翻文档快。

3.2 /var/run/docker.sock 交出去的是宿主机的控制权 #

/var/run/docker.sock 挂进容器，等于把宿主机 Docker 的权限交给了 Portainer。别把 9094 端口对公网开放。

这句话在素材里只有一行，但它的分量最重，第十一章铺开讲。这里先记住结论：能登录 Portainer 的人，等于能在这台机器上以 root 起容器、挂载宿主机任意目录。

3.3 卷是复用的，不是覆盖的 #

手工建过 portainer_data 后，Compose 里的 volumes: 声明会复用它，不会覆盖已有数据。docker compose down 也不删这个卷。

这条行为很关键：意味着改 yml、重启、升级镜像，账号和 Stacks 都还在。也意味着另一个方向——想清空重来时，光 down 没用。要连卷一起删：

bash
docker compose down -v

或者显式删卷：

bash
docker volume rm portainer_data

删卷 = 丢管理员账号、丢所有 Stacks 定义、丢所有环境配置。下手之前先想三秒。

3.4 version: "3" 已经废弃 #

老文章里的 Compose 文件开头都有一行 version: "3"。新版 Compose 里这个字段已废弃，docker compose up 时会打一条 the attribute version is obsolete 的 warning。warning 不影响启动，但会一直刷。删掉即可，Compose 现在按文件内容自动识别格式版本。

注意点 现象 处理
端口映射 用 https 打开 9094 报 SSL 错误 9094 后面是 9000，用 http://；要 HTTPS 改成 9443
socket 权限 面板能进，一操作就 500 挂载对了加上别对公网开放
卷复用 改配置不生效、旧账号还在 卷在复用；要清空用 down -v 或 volume rm
version 字段 启动刷 obsolete warning 删掉 version: 那行

四、界面四个板块 #

登录之后左边导航栏那几个入口，对应 Docker 的四类资源。先看全景：

板块 主要能力 等价命令 容易踩的点
Containers 列举、启停、删除、日志、终端、Inspect、Stats docker ps / logs / exec Console 进不去多是镜像里没有 shell
Images 拉取、构建、查看分层、删除、清理 docker pull / build / rmi 删镜像前要先删依赖它的容器
Networks 创建、查看、看已连接容器 docker network 容器网络归属基本在创建时定
Volumes 创建、删除、浏览内容 docker volume 浏览要起辅助容器，慢且容易失败

4.1 Containers #

最常用的板块。默认列出当前环境所有容器，带状态、镜像、端口映射、创建时间。顶部能按名称搜、按状态筛（running / stopped / unhealthy）。进单个容器能看到九个左右的标签页：Logs、Inspect、Stats、Console、Attach、Container details、Image details 等等，日常 90% 的时间花在 Logs 和 Console 两页上。

4.2 Images #

列出本机镜像、大小、标签数。右上角 Build a new image 可以从 Dockerfile 构建，Import 可以导入 docker save 出来的 tar。点进单个镜像能看到分层（layers）和每层对应的构建指令。查镜像为什么两个 G 的时候，这页比 docker history 直观——至少不用眯着眼对齐列。

4.3 Networks #

列出 bridge / host / none 和自建网络的子网、网关、已连接的容器数。建自定义网络时能指定 driver、子网、网关、可分配 IP 范围。容器的网络归属在创建时确定，事后要换，回 Compose 改 yml 重新部署更靠谱。

4.4 Volumes #

列出命名卷、driver、挂载点、大小。Browse 能看卷里的文件——注意它是靠临时起一个辅助容器把卷挂上再列目录，所以卷正被容器占用时容易挂不上，目录里文件多的时候转圈很慢。图形界面读不到宿主机文件系统，只能借一个容器去看。

五、容器的日常操作 #

界面上的操作路径和命令行不是一一对应，但心智模型可以对齐。下面按「你每天会做的事」排。

5.1 列表与筛选 #

顶部搜索框按容器名过滤，右侧下拉按状态筛。容器多的时候用 Stacks 分组看更清楚——同一个 stack 起的容器名字都带同一个前缀。

5.2 启动、停止、重启、删除 #

列表行尾的图标就是开关。删除时有个勾选项 Automatically remove non-persistent volumes，勾上会顺手删掉匿名卷——也就是 Dockerfile 里 VOLUME 声明出来的那种。命名卷不会被这个勾删掉。

批量操作在列表左上角：全选或勾几个，右上出现 Start / Stop / Remove / Restart 的批量条。

5.3 看日志 #

进容器点 Logs。能设显示行数、开时间戳、开自动滚动，右上角可以下载整份日志。

几个实际经验：

  • 默认只显示最后若干行。滚动到顶就到底了，要看更早的调大行数或者直接 docker logs --since。
  • 容器重启过，旧日志还在，但日志面板不会标出重启边界，时间戳跳一下就是重启点。
  • 日志驱动不是 json-file 或 local 的时候，面板里读不到内容，只会显示空——这不是 Portainer 的 bug，是驱动本身不落本地文件。

5.4 进终端 #

点 Console，选 sh 或 bash，点 Connect。本质就是 docker exec -it <id> sh。

进不去的情况几乎都是同一个原因：镜像里没有 shell。distroless、scratch 基础镜像、部分精简版镜像都不带 shell，这时候界面和命令行的结果一样——都进不去，只能靠日志和外部调试工具。

5.5 Inspect 与 Stats #

Inspect 是完整 JSON，等同 docker inspect。查挂载点、环境变量、网络 IP、重启次数都在这。Stats 是实时的 CPU、内存、网络、磁盘 IO 曲线，看某个容器是不是在偷偷吃内存，这一页比 docker stats 舒服。

5.6 改配置 #

容器的端口、环境变量、重启策略、资源限制，界面上能改一部分。改完点 Deploy the container，Portainer 会重建容器——旧容器删掉，按新参数起一个同名的。

所以两件事要注意：容器里的临时改动会丢；重建期间服务有短暂中断。生产上改配置的正当路径是改 Compose 文件、重新部署，而不是在界面上点。

六、镜像与网络、卷 #

容器之外的三类资源，用法比 Containers 简单，坑却各有各的。

6.1 镜像 #

拉取：Images 页右上 Pull image，填 nginx:1.27-alpine 这种完整名。不写 tag 默认 latest，生产上别省。

构建：Build a new image 支持三种来源——上传 Dockerfile 和构建上下文、编辑器里直接写、从 Git 仓库拉。构建完自动出现在列表里。

查看分层：点进镜像能看到每层的大小和来源指令，镜像膨胀的时候先在这里定位是哪一层大。删除：镜像被容器引用时删不掉，报 image is being used by running container，先删容器再删镜像，或者用 Prune unused——它只清理没被任何容器引用的悬空镜像。

6.2 网络 #

创建时选 driver。单机就 bridge，给了子网的话 Docker 会按你写的网段分配 IP。overlay 只在 Swarm 里用得上，CE 单机环境用不到。

网络页能看到每个网络连了哪些容器，但改连接关系的手段有限。正经做法还是 Compose：把服务写进同一个 networks:，服务之间用服务名互访。排查时先看容器有没有连上正确的网络，再看 IP 是不是同一网段，这两条在界面上一眼能看出来，比敲 docker network inspect 快。

6.3 卷 #

三个动作：建、看、删。

动作 界面操作 等价命令
建 Volumes → Add volume，填名称和 driver docker volume create
看 点进卷 → Browse docker run -v vol:/x alpine ls /x
删 行尾垃圾桶 docker volume rm

卷被容器占用时删不掉，界面会提示仍然在使用。要先停并删掉那个容器。

Browse 失败很常见，原因就那几类：卷被占用、辅助容器镜像拉不下来（离线环境）、卷里文件极多导致超时。离线环境下 Browse 基本用不了，因为它需要 alpine 之类的镜像起容器。

删卷之前一定确认它里面是不是还有数据。命名卷不会随容器删除而消失，这是它的价值，也是它容易变成「一堆不知道能不能删的卷」的原因。定期用 docker volume ls -f dangling=true 清一下没挂载的卷，比在界面上一个个点快。

七、Stacks：用 Compose 编排 #

如果只留一个功能，留 Stacks。它是 Portainer 对 Docker Compose 的封装，也是这个面板真正比命令行省事的地方。

7.1 Stack 到底是什么 #

一个 Stack 就是一份 docker-compose.yml 对应的一组资源。Stack 名等于 Compose 的项目名，起的容器名是 栈名-服务名-序号。

text
Stack: blog
  ├─ blog-web-1      （服务 web）
  ├─ blog-api-1      （服务 api）
  └─ blog-redis-1    （服务 redis）
  + 网络 blog_default
  + 卷   blog_uploads

删 Stack 时，这一整套会一起清掉。手工 docker run 一串命令起三个容器，事后你记得自己要删哪几个；Stack 帮你记住了。它的价值在一句话里：把一份 YAML 变成可版本化、可重复部署的单元。改一行 YAML，点重新部署，整个栈按新定义重来。比手工敲命令、比逐个容器改配置都可靠。

7.2 三种创建方式 #

方式 输入 适合 缺点
Web editor 直接粘 yml 文本 试用、小栈、临时验证 改动不落版本库
Upload 上传本地 yml 文件 从已有项目迁移 每次改动要重传
Repository Git 仓库 + 分支 + 文件路径 长期维护的栈 要配仓库访问权限

Repository 那一种就是 GitOps 的路子：栈定义活在 git 里，改配置走 commit，Portainer 负责把它拉下来部署。

7.3 用 Web editor 粘一份 yml #

导航到 Stacks → Add stack → 命名（比如 blog）→ 选 Web editor，把内容粘进去：

yaml
services:
  web:
    image: nginx:1.27-alpine
    ports:
      - 8088:80
    volumes:
      - ./conf/nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - uploads:/var/www/uploads
    depends_on:
      - api

  api:
    image: ghcr.io/example/blog-api:1.4.2
    environment:
      REDIS_URL: redis://redis:6379/0
      TZ: Asia/Shanghai
    depends_on:
      - redis

  redis:
    image: redis:7-alpine
    volumes:
      - redis_data:/data

volumes:
  redis_data:
  uploads:

下面还有一个环境变量区，可以填 key/value 覆盖 yml 里的变量，写法跟 .env 一个道理。填 TAG=1.4.3 这种，在 yml 里用 ${TAG} 引用。

点 Deploy the stack。部署完回 Containers 页，三个容器名字都带 blog- 前缀。

注意 ./conf/nginx.conf 这种相对路径——它相对的是宿主机上 Portainer 的工作目录，不是你的浏览器。用 Web editor 时宿主机上并没有这个文件，容器会起不来或者挂个空目录。要么改绝对路径，要么把配置塞进镜像，要么用 Repository 方式让文件跟着仓库一起过去。

7.4 更新、停止、删除 #

Stacks 列表点进某个栈，能看到 Editor 标签。改 yml → Update the stack → 勾上 Re-pull image and redeploy，才会重新拉镜像。不勾的话只按新定义重建容器，镜像还是本地那份旧的。

这是最容易犯的错：改了 tag、点了更新、页面显示成功，容器跑的还是旧镜像。原因就是没勾那个选项，或者本地镜像的 tag 没变。

Stop 只是停容器，Stack 定义还在。Delete 连定义一起删，勾上 Remove volumes 会连卷清除。

7.5 Git 仓库方式 #

Add stack 里选 Repository，填四项：

字段 填什么
Repository URL https://github.com/you/repo.git
Repository reference 分支名，比如 refs/heads/main
Compose path 仓库里的相对路径，比如 deploy/docker-compose.yml
Authentication 私有仓库才需要，填用户名 + token

下面有个 GitOps updates 选项，可以开自动轮询：Portainer 每隔一段时间去仓库拉一次，文件变了就自动重新部署。间隔能设，也能设成只在手动触发时更新。

私有仓库的 token 存在 Portainer 的数据库里。备份卷的时候注意这一点，备份文件等于带着这些凭据，按敏感文件处理。

7.6 它做不到的事 #

Stacks 好用，但有边界，别把它当成万能的部署系统：

  • Web editor 里写 build: 没用，没有构建上下文。要自己构建镜像，用 Repository 方式把整个仓库拉下来，或者先在 Images 页构建好再引用。
  • 它不做多机调度。一个 Stack 只能部署在选定的那一个环境上，跨机器编排是 Swarm / Kubernetes 的活。
  • 它不管发布流程。没有灰度、没有回滚按钮、没有健康检查门禁。这些要么在 CI 里做，要么在 Compose 里用 healthcheck 自己兜。
  • 敏感信息还是明文。环境变量存在 Portainer 的数据库里，界面上能看。真要保密，用 Docker secrets 或者外部密钥管理。

八、多主机管理 #

一台机器用面板，价值有限；十台机器用一个面板，价值就出来了。这就是 Environment（环境）的意义。

8.1 环境是什么 #

一个 Environment 就是一个 Docker 端点——可以是本机 dockerd，可以是另一台机器，也可以是 Swarm 集群或 Kubernetes。

界面左上角有环境切换器。切过去之后，Containers、Images、Stacks 全都指向那台机器的资源。你在一台机器上管十台，不用挨个 SSH。

8.2 三种接法 #

接法 目标机要做什么 传什么 风险
本地 socket 无，挂 /var/run/docker.sock Unix socket 高，等于宿主机 root
Portainer Agent 跑一个 portainer/agent 容器，开 9001 HTTP 到 agent 中，权限仍然大但走 agent
直连 TCP dockerd 开 -H tcp://0.0.0.0:2375 明文 HTTP，无认证 极高，谁连上谁能控制

第三种是最不该用的。2375 端口裸奔在公网上，几分钟就会被扫到，然后你的机器就变成别人的矿机。要用 TCP，至少是 2376 + TLS 双向认证，而且只在内网。

8.3 用 Agent 接一台远程机 #

在目标机上跑：

bash
docker run -d \
  --name portainer_agent \
  --restart=always \
  -p 9001:9001 \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v /var/lib/docker/volumes:/var/lib/docker/volumes \
  portainer/agent:latest

两个挂载各有用途：socket 让 agent 能调 dockerd，/var/lib/docker/volumes 让面板能看到卷里的实际内容（卷浏览靠它）。

然后在主 Portainer 里：Environments → Add environment → Docker Standalone → Agent，填 name 和 Environment address，形如 10.0.0.12:9001。点 Connect，能连上就进了列表。

8.4 环境连不上怎么查 #

现象 查什么
环境列表里显示 offline 目标机 agent 容器在不在跑；9001 端口通不通
连接超时 安全组/防火墙；地址填错（别填 localhost）
连上但操作报错 agent 的 socket 挂载是否正确
卷浏览一片空白 agent 少了 /var/lib/docker/volumes 挂载

排查从目标机本地开始：curl http://10.0.0.12:9001/ping 有回应，说明 agent 活着，问题在网络或地址；没回应，就先看容器日志。

多环境有个实用场景：测试机和生产机接进同一个 Portainer，用两个环境分开。切换靠左上角的下拉，别在错误的机器上删东西——这个事故在给环境起名的时候就能预防，名字里带 prod 的，操作前多看一眼顶部。

九、用户与权限 #

CE 版支持多用户，这是它比「一个人用的面板」多出来的能力，但别把它当成完整的权限系统。

9.1 CE 能配什么 #

对象 能力
Users 建用户、改密码、设管理员标记、禁用账号
Teams 把用户分组，按组授权
Environment access 给用户或团队指定能访问哪些环境
访问级别 只读 / 可读写（按环境）

流程是三步：Users 里建人 → Teams 里分组 → 环境详情页里加授权。

只读权限适合给测试、运维观察用。他们能看容器状态、看日志、看配置，不能启停删除——出事的时候能看清现场，不会误操作。

9.2 CE 与 BE 的权限差别 #

能力 CE BE
建用户、建团队 有 有
按环境授权（只读/读写） 有 有
按资源细粒度 RBAC 无 有
LDAP / AD / OAuth 登录 无 有
审计谁做了什么 无 有

CE 的授权粒度停在环境这一层。你要么能管这台机器上所有容器，要么只能看。想做到「张三只能动 stack A 的容器，李四只能动 stack B」，CE 做不到。

具体角色名称和界面选项随版本有调整，以你实际装的版本为准，别照老文章抄。

9.3 几条实操建议 #

一人一号。别几个人共用一个 admin——出问题的时候查不到是谁操作的，等于没有审计。

admin 只留一两个。日常运维用普通账号，需要动环境配置的时候再切。

密码别设成 admin123。这玩意儿挂着 docker.sock，一个弱密码等于把宿主机交出去。

API 访问用 token。My account 里能建 access token，给 CI 调 Portainer API 用。token 权限等同账号本身，泄露了要立刻删。用 token 别用密码，token 能单独吊销。

要外部认证就得上 BE。CE 只能本地账号，公司里几十号人都要建一遍，人走了还得手工删——这也是很多人从 CE 换到 BE 的原因。

十、备份与恢复 #

Portainer 的数据全在 portainer_data 卷里：用户、环境配置、Stacks 定义、加密后的凭据。备份这个卷就够了，镜像不用管。

10.1 备份 #

用临时容器打包，不必在宿主机装工具：

bash
cd ~/portainer
docker run --rm -v portainer_data:/data -v $(pwd):/backup alpine \
  tar czf /backup/portainer_data_$(date +%Y%m%d).tar.gz -C /data .

--rm 用完即删，-C /data . 让包内是相对路径，恢复时不用管挂载点。

10.2 恢复 #

先停掉 Portainer，避免它一边写一边被覆盖：

bash
docker compose down
docker run --rm -v portainer_data:/data -v $(pwd):/backup alpine \
  sh -c "rm -rf /data/* && tar xzf /backup/portainer_data_20261118.tar.gz -C /data"
docker compose up -d

rm -rf /data/* 不能漏。不清理直接解包，新旧文件混在一起，数据库层面对不上。

10.3 三点提醒 #

备份文件里有账号哈希和仓库凭据，按敏感文件处理，别扔在公开目录。换机器恢复时 admin 密码沿用旧的，不用重新初始化。

down 时加过 -v 的话卷已经没了，恢复前先 docker volume create portainer_data。界面里的备份导出属于 BE 能力，CE 直接备卷，路径短还可靠。

十一、安全边界 #

11.1 挂 docker.sock 意味着什么 #

Docker 的 Unix socket 就是 dockerd 的控制入口，它自己不做鉴权——能读写这个 socket 的进程，等同于宿主机的 root。

把它挂进 Portainer 容器，等于把这份控制权交给了那个容器，以及任何能用浏览器登录它的人。

严重到什么程度？登录进来的人在 Stacks 里贴一份 yml 就够了：

yaml
services:
  demo:
    image: alpine
    privileged: true
    command: chroot /host sh -c 'cat /etc/shadow'
    volumes:
      - /:/host

宿主机整个文件系统挂进容器的 /host，读写随便。不需要什么漏洞利用，全是 Docker 的正常功能。

所以只有一句话：Portainer 的访问控制，就是宿主机的访问控制。这不是危言耸听，是挂载方式决定的。

11.2 风险与对策 #

风险 后果 对策
挂了 docker.sock 面板用户 = 宿主机 root 严格控访问；只给需要的人
9000/9443 对公网开放 扫描器几小时就能找到 只绑 127.0.0.1，走反代
HTTP 明文传输 密码和 token 可被嗅探 用 9443，或者反代终止 TLS
admin 弱密码 等同于交出整台机器 长随机密码 + 不共用账号
长期不升级 已知问题没有补丁 定期升级镜像，升级前备份
Stacks 里明文密钥 有面板权限就能看 用 Docker secrets 或外部密钥管理

11.3 只监听本机，前面挂反代 #

把映射限死在回环地址：

yaml
    ports:
      - 127.0.0.1:9094:9000

外面用反向代理加认证和证书。Caddy 的两行就够，WebSocket 它自己转发：

text
portainer.example.com {
    basic_auth {
        ops $2a$14$替换成你自己的哈希
    }
    reverse_proxy 127.0.0.1:9094
}

哈希用 caddy hash-password 生成。Nginx 也行，记得补 Upgrade 和 Connection 两个头——少了它们页面能打开，但 Console 和实时日志连不上。

11.4 其余三条 #

定期升级镜像。Portainer 历史上有过安全问题的修复版本，具体编号去官方 release notes 核对，别听二手转述。升级前先备份卷。最小授权——能只读的给只读，只用一个环境的别给全部环境；CE 的粒度只到环境，那就把环境拆细。

别在 Stacks 里写明文密码。存在数据库里的东西，谁能开面板谁就能看。

十二、易错点速查 #

现象 原因 处理
用 https 打 9094 报 SSL 错误 9094 映射的是 HTTP 的 9000 改用 http://，或把映射改成 9443
首次访问进不去，提示已初始化 5 分钟内没设密码，初始化入口被锁 删卷重建，或按官方方式重置 admin 密码
忘记 admin 密码 密码只存在卷里的数据库中 用镜像的 --admin-password 参数重置，或删卷重建
启动刷 obsolete warning yml 里有 version: "3" 删掉那一行
改了 Stacks 不生效 没勾 Re-pull image，或镜像 tag 没变 勾上重跑，或先把本地旧镜像删掉
容器里看不到日志 日志驱动不是 json-file / local 换回 json-file 并配 max-size
Console 连不上 镜像里没有 shell 用 distroless 就别指望终端，靠日志排查
卷 Browse 转圈或失败 辅助容器起不来 / 卷被占用 停掉占用容器；离线环境别用 Browse
环境显示 offline agent 没跑 / 9001 不通 / 地址填错 目标机上 curl http://IP:9001/ping
容器名带一长串前缀 Stack 部署的容器按 栈名-服务名-序号 命名 正常现象，不是 bug

这张表覆盖了大部分人的第一次卡壳。真卡住了，回命令行跑一遍对应命令，把问题从「面板不好用」缩小到具体的 Docker 报错——这条路永远管用。
