本篇讲 GitHub Actions 这个平台本身：事件怎么触发 workflow，workflow 里怎么写 job 和 step，参数怎么在 job 之间传，最后怎么把产物推出去。读完你应该能独立写出一个能跑的 .github/workflows/*.yml。

不讲 CI/CD 的概念、流水线该怎么分层、缓存策略怎么设计，那部分在《CI/CD 概念与流水线设计》里。

全文用「事件 → workflow → job → step」这条主线组织。第十章起是实战与实例。

一、GitHub Actions 的组成 #

执行模型是四层，从上到下依次收窄：

层 是什么 在哪里定义 数量关系
事件 event 仓库上发生了一件事：push、PR、tag、release、定时 由外部行为产生 一个事件可触发多个 workflow
workflow 一个 .yml 文件，一次完整的流水线定义 .github/workflows/*.yml 一个 workflow 含多个 job
job 一个任务，跑在一台独立的 runner 上 jobs.<job_id> 一个 job 含多个 step
step 一步操作，跑命令或用现成 action jobs.<job_id>.steps[] 顺序执行

反过来看也一样：step 组成 job，job 组成 workflow，workflow 由事件唤醒。

事件决定「什么时候跑」，没有事件 workflow 就是个躺着不动的文件。workflow 决定「跑哪些 job」，一个仓库可以放任意多个文件。job 决定「分成几块跑」，每个 job 分配到一台干净 runner，默认并行。step 决定「具体做什么」，在同一个 job 内顺序执行，共享同一台 runner、同一个工作目录。

step 只有两种形态 #

yaml
steps:
  # 形态一：跑命令
  - name: 装依赖
    run: npm ci

  # 形态二：用别人写好的 action
  - name: 检出代码
    uses: actions/checkout@v4

run 是「自己写命令」，uses 是「复用别人打包好的动作」。run 适合项目自己的业务，uses 适合检出、装环境、传文件、发版这类通用活。

runner 是临时的 #

runner 是一台临时虚拟机或容器。作业跑完，机器销毁，上面装的软件、写的临时文件全部消失。

这一点决定了后面的很多设计：为什么每次都要 actions/checkout，为什么 job 之间传文件得用 artifact，为什么缓存要单独做一层。

一个能跑的最小 workflow #

yaml
name: GitHub Actions Demo
on:
  push:
    branches:
      - main

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20

      - run: npm ci

      - run: npm run build

四层齐全：on.push 是事件，整个文件是 workflow，build 是 job，四个 - 开头的是 step。

文件放在哪 #

路径固定：仓库根目录下的 .github/workflows/，文件名随便取，后缀必须是 .yml。ci.yml、deploy.yml、release.yml 三个文件就是三个独立 workflow，各有各的 on，互不影响。

一句必须记住的话 #

job 之间不共享文件系统。 哪怕用 needs 把它们串成一条线，它们也跑在不同 runner 上，前一个 job 写出的文件，后一个看不到。第五章讲这件事，第九章讲怎么用 artifact 绕过去。

二、workflow 文件的结构 #

字段 必填 作用
name 否 workflow 显示名，不写就用文件路径
on 是 触发事件
env 否 全局环境变量，对所有 job 生效
jobs 是 任务集合，核心内容都在这里
permissions 否 GITHUB_TOKEN 的权限范围
concurrency 否 并发控制，同组同时只跑一个
defaults 否 默认值，如默认 shell、工作目录

最少可用只需 on 和 jobs。

yaml
name: CI

on:
  push:
    branches:
      - main

env:
  NODE_VERSION: 20

permissions:
  contents: write

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: npm test

jobs 下面的字段 #

jobs 是字典，键是 job_id，值是这个 job 的配置。job_id 自己起名，只能用字母、数字、-、_，不能数字开头。

字段 作用
name job 显示名，不写就显示 job_id
runs-on 跑在什么环境上，必填
needs 依赖哪些 job，决定顺序
if 条件，不满足就跳过
steps 步骤数组
env 这个 job 的环境变量
outputs 这个 job 对外输出的值
strategy 矩阵配置，一个 job 跑多份
timeout-minutes 超时，默认 360 分钟
continue-on-error 失败也继续
environment 绑定部署环境，走审批

两个 job 没有 needs 关系，默认并行：

yaml
jobs:
  my_first_job:
    name: My first job
    runs-on: ubuntu-latest
    steps:
      - run: echo first

  my_second_job:
    name: My second job
    runs-on: ubuntu-latest
    steps:
      - run: echo second

steps 下面的字段 #

text
jobs.<job_id>.steps.name   步骤名称，显示在日志里
jobs.<job_id>.steps.run    这一步要跑的命令
jobs.<job_id>.steps.uses   这一步要调用的 action
jobs.<job_id>.steps.env    这一步的环境变量
jobs.<job_id>.steps.with   传给 action 的参数
jobs.<job_id>.steps.id     给这一步起 id，方便引用输出

name、env 是修饰，run 和 uses 二选一，必有一个。with 是喂给 action 的入参，键名由 action 作者定，得看它的 README。下面这个 job 四种都有，setup-node 的 with 传版本号和 registry：

yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 16
          registry-url: 'https://registry.npmjs.org'

      - run: npm install

      - run: npm run build

runs-on 选什么环境 #

runs-on 决定 runner 的操作系统，必填，不写直接报错。

环境 YAML 标签 备注
Windows Server 2022 windows-latest 或 windows-2022 windows-latest 当前指向 2022
Windows Server 2019 windows-2019
Ubuntu 22.04 ubuntu-22.04
Ubuntu 20.04 ubuntu-latest 或 ubuntu-20.04 ubuntu-latest 当前指向 20.04
Ubuntu 18.04 ubuntu-18.04
macOS Monterey 12 macos-12
macOS Big Sur 11 macos-latest 或 macos-11 macos-latest 当前指向 11
macOS Catalina 10.15 macos-10.15 
yaml
jobs:
  build:
    runs-on: ubuntu-18.04

latest 是浮动标签，指向上游当前主推版本。上游一升级，构建环境跟着变。要稳住结果就把版本号钉死。

一个 workflow 触发另一个 workflow #

yaml
# ci.yml
name: Node.js CI
on: push

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 16

      - name: Install dependencies
        run: npm install

  trigger_tests:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - name: Trigger tests
        uses: actions/github-script@v6
        with:
          script: |
            const res = await github.rest.repos.createDispatchEvent({
              owner: 'jaywcjlove',
              repo: 'typenexus',
              event_type: 'run-deploy'
            });
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

ci.yml 跑完后往仓库扔一个自定义事件，事件名 run-deploy。接收方：

yaml
# main.yml
name: deploy
on:
  repository_dispatch:
    types: [run-deploy]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

两边 run-deploy 必须一字不差。改一边不改另一边，链路断掉，而且没有报错提示，只能等下游一直不跑才发现。注意 github-script 这个 step 的 env 写在 with 同级，不是塞进 with 里。

三、触发条件 #

on 决定 workflow 什么时候被唤醒。三种写法，从简到繁。

yaml
# 写法一：单个事件
on: push

# 写法二：事件数组
on: [push, pull_request]

# 写法三：带筛选条件的对象
on:
  push:
    branches:
      - main

第三种最常用。事件名做键，值里写筛选条件。

事件 什么时候触发 典型用途
push 推送提交或 tag 构建、部署
pull_request PR 打开、同步、重开 跑测试、检查
schedule 定时，cron 语法 夜间构建、定期同步
workflow_dispatch 手动点按钮 手动发布、补跑
repository_dispatch 外部 API 打进来 跨 workflow 联动
release 发布 release 发版、上传产物
workflow_run 另一个 workflow 跑完 串接流水线
issues issue 开、关、打标签 自动回复、分流
create 创建分支或 tag 新 tag 触发发版

push 的筛选 #

yaml
# 只有 main 分支的 push 才触发
on:
  push:
    branches:
      - main

# 只在 v 开头的 tag 推送时触发
on:
  push:
    tags:
      - 'v*'

分支和 tag 可以并列，是「或」的关系——推 main 触发，推 v1.2.3 也触发：

yaml
on:
  push:
    branches:
      - main
    tags:
      - 'v*'

pull_request 的筛选 #

yaml
on:
  pull_request:
    branches:
      - main
    types: [opened, synchronize, reopened]

types 限定 PR 动作类型。不写时默认覆盖 opened、synchronize、reopened，不含 closed。

branches 在 pull_request 里指目标分支，也就是 PR 要合入的那个分支，不是源分支。跟直觉相反，配错了会以为规则没生效。

paths-ignore：改文档不跑构建 #

yaml
# push 事件触发 workflow，但是 docs 目录下的更改不触发
on:
  push:
    paths-ignore:
      - 'docs/**'

列出的路径变了不触发，之外变了照常触发。

paths：只关心特定目录 #

yaml
# 包括 sub-project 目录或其子目录中的文件，触发 workflow
# 除非该文件在 sub-project/docs 目录中，不触发 workflow
on:
  push:
    paths:
      - 'sub-project/**'
      - '!sub-project/docs/**'

! 开头是排除。先包含再排除，! 写在后面才生效。

release 事件 #

yaml
on:
  release:
    types: [published]

release 从草稿变成正式发布时触发。types 可选 published、created、edited、deleted、prereleased、released。发版流水线用 published，草稿状态不该触发部署。

schedule 定时 #

yaml
on:
  schedule:
    - cron: '0 18 * * *'

cron 用 UTC，0 18 * * * 对应北京时间次日凌晨 2 点。定时任务只跑默认分支上的 workflow。仓库长期无提交时 GitHub 会自动停用定时任务，隔几个月提交点东西能续上。

workflow_dispatch：手动触发 #

yaml
on:
  workflow_dispatch:
    inputs:
      version:
        description: '要发布的版本号'
        required: true
        default: '1.0.0'

配了它，Actions 页面出现「Run workflow」按钮。inputs 定义表单字段，跑起来用 ${{ inputs.version }} 或 ${{ github.event.inputs.version }} 取值。调试时不用为空跑一次而提交个无意义的 commit。

workflow_run：串接两个 workflow #

yaml
on:
  workflow_run:
    workflows: ["CI"]
    types:
      - completed

workflows 填的是上游 workflow 的 name，不是文件名。填错永远不触发。

多个事件混配 #

yaml
on:
  push:
    branches:
      - main
    tags:
      - 'v*'
  pull_request:
    branches:
      - main
  workflow_dispatch:

一个人维护的项目，push 走正常构建，PR 走检查，手动留个口子，一个文件就够。

分支名支持通配 #

yaml
on:
  push:
    branches:
      - main
      - 'releases/**'
      - 'feature/*'
写法 匹配
main 精确匹配 main
feature/* 匹配 feature/a，不匹配 feature/a/b
releases/** 匹配 releases/a、releases/a/b
!main 排除 main

* 不跨斜杠，** 跨斜杠。

yaml
on:
  push:
    branches:
      - '**'
      - '!gh-pages'
      - '!docs'

先 ** 全包含，再逐个排除。顺序敏感，! 必须在包含规则之后。

paths 与 paths-ignore 不能同时用 #

这是硬规则。下面这样写是错的：

yaml
# 错误写法
on:
  push:
    paths:
      - 'src/**'
    paths-ignore:
      - 'src/docs/**'

GitHub 不报错，但两个字段只有一个生效，实际行为取决于内部实现顺序，你没法预期。正确做法是用 paths 加 !：

yaml
on:
  push:
    paths:
      - 'src/**'
      - '!src/docs/**'

paths-ignore 只在「排除少数目录、其余全要」时单独用：

yaml
on:
  push:
    paths-ignore:
      - '**.md'
      - 'docs/**'

paths 和 tags 的坑 #

配了 paths 之后，tag 推送也会被过滤掉。

原因：tag 推送事件本身不带文件变更列表，paths 无从判断，于是判定为「不匹配」，整个事件被丢掉。

yaml
# 错误写法：以为 tag 会触发，实际不会
on:
  push:
    paths:
      - 'src/**'
    tags:
      - 'v*'

paths 的过滤会作用到 tags 上，结果 tag 推送不触发。两种改法：

yaml
# 改法一：不要 paths，只按分支和 tag 过滤
on:
  push:
    branches:
      - main
    tags:
      - 'v*'

yaml
# 改法二：拆成两个 workflow 文件
# ci.yml
on:
  push:
    branches:
      - main
    paths:
      - 'src/**'

yaml
# release.yml
on:
  push:
    tags:
      - 'v*'

改法二更干净。构建走路径过滤，发版走 tag，职责分开。

pull_request 的 paths 语义 #

yaml
on:
  pull_request:
    paths:
      - 'src/**'

在 pull_request 里，paths 判断的是这个 PR 的改动文件列表。动了 src 下文件就触发，只动 README 就不触发。文档 PR 不跑测试，靠的就是它。

过滤规则速查 #

需求 写法
只看 main 分支 branches: [main]
排除 gh-pages branches: ['**', '!gh-pages']
只看 v 开头 tag tags: ['v*']
只看 src 目录 paths: ['src/**']
src 里但排除测试 paths: ['src/**', '!src/**/*.test.js']
忽略 markdown paths-ignore: ['**.md']
分支和 tag 都要 branches: [main] 与 tags: ['v*'] 并列
PR 只看目标 main pull_request.branches: [main]

博客项目常见的一套：

yaml
name: CI

on:
  push:
    branches:
      - master
    paths-ignore:
      - '**.md'
      - '.gitignore'
  pull_request:
    branches:
      - master
  workflow_dispatch:

push 到 master 且不是纯文档改动时构建；PR 目标 master 时跑检查；留手动入口。

四、job 与 step #

job 默认并行 #

yaml
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - run: npm run lint

  test:
    runs-on: ubuntu-latest
    steps:
      - run: npm test

  build:
    runs-on: ubuntu-latest
    steps:
      - run: npm run build

三个 job 之间没有 needs，GitHub 同时起三台 runner，三条线并行。总耗时约等于最慢的那个。代价是三台机器各自要装一遍依赖，依赖装得慢的项目并行反而更慢，得实测。

同一个 job 里的 step 严格按顺序走，前一个成功后跑下一个。任何一个失败，后面的全部跳过，job 标记失败。

step 的 shell 与多行 #

run 默认用 bash（Linux/macOS）和 pwsh（Windows）。可选 bash、pwsh、python、sh、cmd、powershell：

yaml
- name: 用 bash 跑
  shell: bash
  run: |
    echo "hello"

- name: 用 python 跑
  shell: python
  run: |
    print("hello")

多行用 |，保留换行，每行是独立命令：

yaml
- name: 构建并检查
  run: |
    npm ci
    npm run build
    ls -la dist/

用 > 会把换行折叠成空格，命令拼成一行跑，一般不是你要的。

失败后继续与超时 #

yaml
- name: 会失败的步骤
  continue-on-error: true
  run: ./maybe-fail.sh

写在 step 上，这一步失败了 job 继续，但这一步标记为失败。写在 job 上则整个 job 失败也不影响 workflow 判定。

超时默认 360 分钟。卡死的任务会占着 runner 六小时，吃额度还不出结果。

yaml
jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - run: npm run build

条件执行 #

yaml
- name: 只在 main 分支跑
  if: github.ref == 'refs/heads/main'
  run: ./deploy.sh

- name: 只在 tag 上跑
  if: startsWith(github.ref, 'refs/tags/')
  run: ./release.sh

清理、上报这类收尾工作，希望不管前面成没成功都跑：

yaml
- name: 上传测试报告
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: test-report
    path: reports/
函数 什么时候为真
success() 之前所有步骤都成功，默认行为
failure() 之前有步骤失败
always() 无论如何
cancelled() workflow 被取消

收尾步骤忘了写 always()，失败场景下永远跑不到，这是常见坑。

用 commit 跳过任务 #

yaml
jobs:
  build:
    if: "!contains(github.event.head_commit.message, 'skip ci')"
    runs-on: ubuntu-latest
    steps:
      - run: npm run build

提交时写 docs: 补一段说明 [skip ci]，CI 就跳过。[skip ci]、[ci skip]、[no ci]、[skip actions]、[actions skip] 都是 GitHub 认的关键词。

这个判断只对 push 成立。github.event.head_commit 在 PR 事件里不存在，取到空值，条件恒为真——PR 不会被跳过。

job 输出 #

yaml
jobs:
  job1:
    runs-on: ubuntu-latest
    outputs:
      output1: ${{ steps.step1.outputs.test }}
      output2: ${{ steps.step2.outputs.test }}
    steps:
      - id: step1
        run: echo "test=hello" >> $GITHUB_OUTPUT

      - id: step2
        run: echo "test=world" >> $GITHUB_OUTPUT

  job2:
    runs-on: ubuntu-latest
    needs: job1
    steps:
      - run: echo ${{ needs.job1.outputs.output1 }} ${{ needs.job1.outputs.output2 }}

链路是四段：step 写 $GITHUB_OUTPUT → step 有 id → job 的 outputs 映射出去 → 下游用 needs.<job_id>.outputs.<key> 取。老写法 echo "::set-output name=test::hello" 已废弃。

四个环节缺一不可，id 忘了写、outputs 忘了映射、下游 needs 忘了加，都会取到空字符串，而且不报错。

一个 job 写多个 step 的实战 #

yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - name: 装依赖
        run: npm ci

      - name: 类型检查
        run: npm run typecheck

      - name: 构建
        run: npm run build

      - name: 上传产物
        uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/

检出、装环境、装依赖、检查、构建、上传，六步。工具都在同一台机器上，node_modules 装一次够用，dist/ 原地产生。

五、job 之间的依赖与传值 #

这一章是全篇最容易出错的地方。依赖关系和文件共享是两件事，混在一起理解就会写出「明明串行了却读不到文件」的配置。

needs 只管顺序，不管文件 #

yaml
jobs:
  job1:
  job2:
    needs: job1
  job3:
    needs: [job1, job2]

job1 必须先于 job2 完成，job3 等 job1 和 job2 都完成才跑。执行顺序是 job1 → job2 → job3。

关键在这里：这三个 job 跑在三台不同的 runner 上。 needs 只是让第二台机器等第一台机器结束，第二台启动时是一台全新的空机器，它不会挂载第一台的磁盘。

text
runner A:  [job1]  ← 写出的文件在这里，然后 A 被销毁
                ↓ needs 只是等待信号
runner B:                          [job2]  ← 全新机器，看不到 A 的任何文件

依赖是「成功才继续」 #

needs 的语义不只是「等它结束」，而是「等它成功结束」。上游失败，下游直接被跳过。想让它失败也继续：

yaml
jobs:
  job1:
  job2:
    needs: job1
  job3:
    if: ${{ always() }}
    needs: [job1, job2]

job3 加了 always()，不管 job1、job2 成没成功，只要跑完了，job3 就跑。这个写法适合收尾任务：汇总结果、发通知、清理资源。

依赖多个上游与依赖成链 #

needs: [job1, job2] 里每个都必须成功，任何一个失败就跳过。

yaml
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - run: npm run lint

  test:
    needs: lint
    runs-on: ubuntu-latest
    steps:
      - run: npm test

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - run: npm run build

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh

四级串行，前一个失败后面全部跳过，deploy 永远不会在测试失败时误触发。

传值的完整链路 #

job 之间传值靠 outputs，不靠文件。

yaml
jobs:
  prepare:
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.getver.outputs.version }}
    steps:
      - id: getver
        run: echo "version=${GITHUB_REF#refs/tags/v}" >> $GITHUB_OUTPUT

  build:
    needs: prepare
    runs-on: ubuntu-latest
    steps:
      - name: 用上游传来的版本号
        run: echo "版本是 ${{ needs.prepare.outputs.version }}"

prepare 算出版本号，写进 step output，映射成 job output，build 用 needs.prepare.outputs.version 拿出来。整条链不经过文件系统，是 GitHub 在 job 之间传的字符串。

传文件的正确做法：artifact #

要传的是目录、一批文件，塞不进字符串，只能用 artifact。

yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: mkdir -p path/to/artifact
      - run: echo hello > path/to/artifact/world.txt

      - uses: actions/upload-artifact@v4
        with:
          name: my-artifact
          path: path/to/artifact/world.txt

  consume:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: my-artifact

download-artifact 按 name 找回同名 artifact，解到当前工作目录。name 是两边对接的唯一凭据，写错就是找不到，报错信息也不指向根因。

path: dist/ 上传的是目录内容，下载后 dist 里直接是文件。| 多行可以一次传多个路径，打进同一个 artifact：

yaml
- uses: actions/upload-artifact@v4
  with:
    name: dist
    path: |
      dist/
      package.json

- uses: actions/download-artifact@v4
  with:
    name: dist
    path: ./dist

artifact 与 cache 的区别 #

产物用 artifact，依赖用 cache，别混。两者的完整对照在第九章。

一个完整的跨 job 构建：

yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: dist
          path: dist
      - name: 部署
        run: ./deploy.sh dist

build 在一台机器上构建并上传，deploy 在另一台机器上下载再部署，中间没有任何文件共享。如果 deploy 还要跑 git 命令，别忘了它自己也需要 actions/checkout——下载 artifact 不等于有了仓库副本。

六、环境变量与 secrets #

环境变量分三种作用域，写在同一份文件里互相覆盖，理解覆盖顺序比背字段名重要。

层级 写在哪 作用范围 优先级
workflow 级 顶层 env 所有 job、所有 step 最低
job 级 jobs.<job_id>.env 该 job 的所有 step 中
step 级 steps[].env 该 step 最高 
yaml
env:
  APP_ENV: production
  NODE_VERSION: 20

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      BUILD_TARGET: web
    steps:
      - name: 覆盖全局值
        env:
          APP_ENV: staging
        run: echo "$APP_ENV $BUILD_TARGET $NODE_VERSION"

这个 step 里 APP_ENV 是 staging，BUILD_TARGET 是 web，NODE_VERSION 是 20。

默认环境变量 #

GitHub 在每个 runner 上预置了一批环境变量。强烈建议用它们访问文件系统，别硬编码路径——runner 上的目录结构不由你控制。

变量 含义
CI 始终为 true
HOME 用户数据的主目录，如 /github/home
GITHUB_WORKFLOW workflow 的名称
GITHUB_RUN_ID 仓库内每次运行的唯一编号，重跑不变
GITHUB_RUN_NUMBER 特定 workflow 的运行序号，从 1 递增，重跑不变
GITHUB_ACTION 当前 action 的唯一标识
GITHUB_ACTIONS 在 Actions 里运行时始终为 true，可区分本地和 CI
GITHUB_ACTOR 触发者的用户名或应用名
GITHUB_REPOSITORY 所有者和仓库名，如 octocat/Hello-World
GITHUB_EVENT_NAME 触发事件的名称
GITHUB_EVENT_PATH 事件完整 payload 的文件路径
GITHUB_WORKSPACE 工作空间目录路径，用了 checkout 才有内容
GITHUB_SHA 触发运行的提交 SHA
GITHUB_REF 触发的分支或 tag 引用，如 refs/heads/feature-branch-1
GITHUB_HEAD_REF PR 的源分支，仅 fork 仓库设置
GITHUB_BASE_REF PR 的目标分支，仅 fork 仓库设置 
bash
# 从 tag 引用里剥出纯版本号
VERSION="${GITHUB_REF#refs/tags/v}"

# 拿到当前分支名
BRANCH="${GITHUB_REF#refs/heads/}"

# 判断是不是在 CI 里
if [ "$CI" = "true" ]; then echo "in CI"; fi

GITHUB_REF 的字符串替换是最常用的技巧。refs/tags/v1.2.3 去掉前缀 refs/tags/v 就剩 1.2.3。写 shell 时用环境变量省事，写 YAML 表达式时用 github.ref，两者是同一个值。

往环境里写值：GITHUB_ENV #

一个 step 算出的值要让后面 step 也看到，写 $GITHUB_ENV：

yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@master

      # 向 ENV 写入 CURRENT_VERSION 环境变量，赋值版本号
      - run: |
          echo "CURRENT_VERSION=${GITHUB_REF#refs/tags/v}" >> $GITHUB_ENV

      # 后面的步骤可以拿到 CURRENT_VERSION
      - run: echo "${{env.CURRENT_VERSION}}"

$GITHUB_ENV 是个文件，往里 >> 追加 KEY=VALUE 行，GitHub 在下一步之前注入环境。

注意写入之后当前 step 内还读不到，只有后续 step 能拿到。同一个 step 里要用，得用普通 shell 变量。老写法 echo "::set-env name=X::value" 已废弃。

$GITHUB_OUTPUT 是另一条通道，给 step output 用：

yaml
- id: gen
  run: echo "version=1.2.3" >> $GITHUB_OUTPUT

- run: echo "${{ steps.gen.outputs.version }}"

区别在引用方式：环境变量是 ${{ env.KEY }}，output 是 ${{ steps.<id>.outputs.KEY }}。

secrets 从哪来 #

仓库的 Settings → Secrets and variables → Actions → New repository secret。

yaml
- name: 测试 nodejs 获取环境变量
  env:
    NODE_API_TOKEN: ${{ secrets.NODE_API_TOKEN }}
  run: npm run env

secret 存好之后再也看不到，只能覆盖重写。写错了没有「编辑」入口，只能重建一个。

secrets 会被打码 #

日志里出现的 secret 值自动替换成 ***，不需要你做任何事。

但打码只对完整精确匹配生效。把 secret 拼进 URL、base64 编码、截取前四位，都能绕过打码把内容漏出来。不要在 run 里随意 echo 含 secret 的变量。

secrets 不能传给 fork 的 PR #

这是安全设计，改不了。

从 fork 仓库发起的 PR，pull_request 事件里所有 secrets 都是空的。GitHub 不会把主仓库的密钥交给陌生人写的代码——那段代码能在 CI 里执行任意命令，拿到 secret 就直接偷走。

由此带来一个实际的坑：fork PR 上需要 token 的那一步会失败，或者取到空字符串继续跑出奇怪结果。

yaml
- name: 需要 token 的步骤
  if: github.event.pull_request.head.repo.full_name == github.repository
  env:
    TOKEN: ${{ secrets.MY_TOKEN }}
  run: ./upload.sh

用 if 判断 PR 来源是不是本仓库，不是就跳过。本仓库分支的 PR 正常工作，fork PR 直接跳过而不是失败。

敏感信息传外部服务 #

pattern 是 env 引入加命令消费，别把 secret 拼进命令行参数。

yaml
- name: Docker login
  run: echo "${{ secrets.DOCKER_PASSWORD }}" | docker login -u "${{ secrets.DOCKER_USER }}" --password-stdin

--password-stdin 比 -p 好，密码不进程参数列表，不会出现在 ps 输出里。

yaml
- run: npm publish --access public
  env:
    NODE_AUTH_TOKEN: ${{secrets.NPM_TOKEN}}

npm publish 从 NODE_AUTH_TOKEN 读 token，用 env 喂进去。这种「工具从固定环境变量读凭据」的模式最稳，日志里也不会打印。

env secrets
存明文 是，写在文件里 否，存在仓库设置里
日志显示 原样显示 自动打码
fork PR 可用 是 否
典型内容 版本号、路径、开关 token、私钥、密码
引用方式 ${{ env.X }} / $X ${{ secrets.X }}

判据很简单：能公开的写 env，不能公开的写 secrets。

GITHUB_TOKEN #

每个 workflow 自带一个 secrets.GITHUB_TOKEN，不用创建，自动注入，运行结束失效。能做什么由 permissions 控制：

yaml
permissions:
  contents: write
  pull-requests: write
  issues: read

不写就按仓库默认设置来，会给得过宽或过窄。显式声明最小权限是稳妥做法。contents: write 是推代码需要的权限，gh-pages 部署、提交版本号都得有它，否则报 403。

GITHUB_ 前缀是保留的，定义带这个前缀的环境变量或 secret 会直接报错。改用 GH_、APP_、MY_ 这类前缀。

上下文是 GitHub 运行时注入的结构化数据，用 ${{ }} 取值。环境变量是扁平的字符串集合，上下文是带层级的对象。

属性 类型 描述

github.event object 完整的事件 payload
github.event_path string runner 上事件 payload 的文件路径
github.workflow string workflow 的名称，没写 name 则是文件完整路径

github.actor string 触发运行的用户的登录名
github.repository string 所有者和仓库名，如 Codertocat/Hello-World
github.repository_owner string 仓库所有者的名称
github.event_name string 触发运行的事件名称
github.sha string 触发运行的提交 SHA
github.ref string 触发运行的分支或 tag 引用

github.base_ref string PR 的目标分支，仅 pull_request 事件可用

github.action 有个细节：GitHub 会删掉名称里的特殊字符，纯脚本步骤用 run。同一个 job 里多次用同一个 action 时带序号后缀——第一个脚本叫 run1，第二个叫 run2；actions/checkout 第二次调用变成 actionscheckout2。

github.event 里有什么 #

github.event 是整个 webhook payload，内容随事件类型变化。

yaml
# push 事件
- run: echo "${{ github.event.head_commit.message }}"
- run: echo "${{ github.event.pusher.name }}"
- run: echo "${{ toJSON(github.event.commits) }}"

# pull_request 事件
- run: echo "${{ github.event.pull_request.number }}"
- run: echo "${{ github.event.pull_request.title }}"

调试时最省事的做法是把整个 payload 打出来：

yaml
- run: echo '${{ toJSON(github.event) }}'

想知道某个字段叫什么，跑一次看输出，比翻文档快。

常用表达式函数 #

函数 作用 例子
contains(a, b) 包含 contains(github.ref, 'main')
startsWith(a, b) 前缀 startsWith(github.ref, 'refs/tags/')
endsWith(a, b) 后缀 endsWith(github.ref, '/main')
format(f, ...) 格式化 format('{0}-{1}', a, b)
join(a, sep) 拼接数组 join(github.event.labels, ',')

fromJSON(x) 转对象 fromJSON('["a","b"]')
success() 前面都成功 if: success()
failure() 前面有失败 if: failure()

yaml
# 是不是 main 分支
if: github.ref == 'refs/heads/main'

# 是不是 tag
if: startsWith(github.ref, 'refs/tags/')

# 提交信息里有没有 skip
if: "!contains(github.event.head_commit.message, 'skip ci')"

# 是不是 PR
if: github.event_name == 'pull_request'

# 是不是从本仓库发的 PR
if: github.event.pull_request.head.repo.full_name == github.repository

取版本号的实战 #

bash
# 从 tag 引用里剥版本号
VERSION="${GITHUB_REF#refs/tags/v}"
echo "CURRENT_VERSION=$VERSION" >> $GITHUB_ENV

从任意 ref 剥出最后一段的通用做法：

bash
VERSION=$(echo "${{ github.ref }}" | sed -e 's,.*/\(.*\),\1,')

sed 把最后一个斜杠之前的部分全删掉，剩下 v1.2.3 或 main。再剥 v 前缀：

bash
[[ "${{ github.ref }}" == "refs/tags/"* ]] && VERSION=$(echo $VERSION | sed -e 's/^v//')

这两段在后面的实例里反复出现，是发版脚本的地基。

runner.os 取值 Linux、Windows、macOS，多平台矩阵里按系统分支处理时用它：

yaml
- name: 当前系统
  run: echo "${{ runner.os }} ${{ runner.arch }}"

- if: runner.os == 'Windows'
  run: echo "Windows 上的处理"

八、矩阵构建与多环境 #

矩阵让一个 job 跑出多份，是「同一套步骤跑不同参数」的标准做法。

yaml
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [16.x, 18.x, 20.x]

    steps:
      - uses: actions/checkout@v4

      - name: Use Node.js ${{ matrix.node-version }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}

      - run: npm ci
      - run: npm run build --if-present
      - run: npm test

三个版本，这个 job 跑三遍，${{ matrix.node-version }} 分别是 16.x、18.x、20.x。三遍并行，各自在独立 runner 上，总耗时约等于最慢的一份。

多维度做笛卡尔积，3 × 2 = 6 个 job：

yaml
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        node-version: [18, 20]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm test

维度一多组合数涨得很快，会吃掉大量额度。

include 与 exclude #

yaml
strategy:
  matrix:
    node-version: [18, 20]
    include:
      - node-version: 20
        experimental: true

include 可以往某个组合里加字段，也可以加全新组合：

yaml
strategy:
  matrix:
    os: [ubuntu-latest]
    include:
      - os: windows-latest
        node-version: 20

多出一个只跑 Windows + Node 20 的组合。

yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest]
    node-version: [18, 20]
    exclude:
      - os: windows-latest
        node-version: 18

四减一，跑三个组合。

fail-fast 与 max-parallel #

yaml
strategy:
  fail-fast: false
  max-parallel: 2
  matrix:
    node-version: [16.x, 18.x, 20.x]

默认一个组合失败其余全部取消。fail-fast: false 让它跑完所有组合再判定，「想知道到底哪些版本挂了」时用。max-parallel 限制同时跑几个，下游服务扛不住或额度吃紧时用。

矩阵的值来自 JSON #

yaml
jobs:
  setup:
    runs-on: ubuntu-latest
    outputs:
      versions: ${{ steps.gen.outputs.versions }}
    steps:
      - id: gen
        run: echo 'versions=["18","20"]' >> $GITHUB_OUTPUT

  test:
    needs: setup
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: ${{ fromJSON(needs.setup.outputs.versions) }}
    steps:
      - run: echo "${{ matrix.node }}"

fromJSON 把字符串还原成数组，矩阵就能动态生成。多仓库、多目标平台同步构建时常用。

矩阵变量在 if 里能正常比较，可以做「只有一个组合跑额外步骤」：

yaml
- name: 只在 Node 20 上跑
  if: matrix.node-version == 20
  run: ./only-on-20.sh

不写 name，列表里显示 build (16.x, ubuntu-latest) 这种自动拼的。写了 name 可以定制展示：

yaml
jobs:
  build:
    name: Build on node ${{ matrix.node_version }} and ${{ matrix.os }}
    runs-on: ubuntu-latest
    strategy:
      matrix:
        os: [ubuntu-latest]
        node_version: [16.x]

排查时更容易定位是哪个组合。

九、缓存与产物 #

每次 job 都从空机器开始，依赖得重新装。装一次 Node 依赖三分钟，一天跑二十次就是一小时。缓存解决这件事。

yaml
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-npm-

三个参数各有分工：path 缓存哪些目录，可以写多行；key 缓存的精确标识，命中就跳过后面的步骤；restore-keys 兜底的模糊匹配，精确 key 没中时按前缀找最近的缓存。

为什么 key 要带 hashFiles #

package-lock.json 变一次，哈希变一次，key 变一次，旧缓存自然失效，新缓存重新建。写成固定值就麻烦了：

yaml
# 错误：依赖升级后仍在用旧缓存
key: npm-cache

依赖升级了还拿旧缓存，构建结果跟本地不一致，排查很费时间。

一个 key 一旦写入就不能被覆盖，第二次用同一个 key 上传会报 cache already exists，但不影响使用。所以 key 必须能区分内容。

setup-node 自带的缓存 #

yaml
- uses: actions/setup-node@v4
  with:
    node-version: 20
    cache: npm

cache 可选 npm、yarn、pnpm，自动按 lock 文件算 key，省掉手写那一段。其他语言的 setup action 同理：setup-python 有 cache: pip，setup-java 有 cache: maven。

缓存只按 key 匹配，不跟踪内容。分支之间共享缓存（只要 key 一样），这既是优点也是风险：从 main 恢复的缓存跑到 feature 分支上，偶发的不一致得靠人判断。跨操作系统不能共享，${{ runner.os }} 放在 key 最前面就是这个原因——Linux 的 node_modules 拿到 Windows runner 上用不了。

产物的保留期与重名 #

yaml
- uses: actions/upload-artifact@v4
  with:
    name: dist
    path: dist/
    retention-days: 7

默认保留 90 天，retention-days 可缩到 1 到 90。构建产物没必要留三个月。

同一个 workflow 里两次上传同名 artifact，v4 直接报错，不像 v2 那样合并或覆盖。矩阵场景下让名字带上维度：

yaml
- uses: actions/upload-artifact@v4
  with:
    name: dist-${{ matrix.node-version }}
    path: dist/

下载时不写 name，会取回全部 artifact：

yaml
- uses: actions/download-artifact@v4
  with:
    path: all-dists

每个 artifact 解到独立子目录，子目录名就是 artifact 名。

artifact cache

十、部署实战：GitHub Pages 与 Hexo #

把前面所有零件拼成一条真实可用的部署流水线：写完文章 push 到仓库，Actions 自动构建 Hexo 并发布到 GitHub Pages。

以前写完文章得在本地跑 hexo generate --deploy，文章多了要等很久。更麻烦的是本地 Node.js 版本一旦跟 Hexo 不兼容，部署就卡住——比如升到 v14 之后 Hexo 跑不起来。交给 runner，本地环境怎么样都无所谓，装什么版本由 workflow 决定。

前提一：准备两个仓库 #

  • blog：放 Hexo 源码，文章、主题配置、workflow 都在这里
  • your.github.io：放生成的静态页面，Hexo 编译产物推到这儿

分开的理由是源码仓库可以被别人看，Pages 仓库只装静态文件。混在一起会把依赖和源码也发布出去。

前提二：生成部署密钥 #

bash
ssh-keygen -f github-deploy-key

一路回车到生成成功，当前目录出现两个文件：

text
github-deploy-key      私钥
github-deploy-key.pub  公钥

不用设密码。设了就得在 workflow 里再处理一次解密，多一层麻烦。

前提三：配置两个 secret #

私钥放进 blog 仓库，路径 Settings → Secrets and variables → Actions → New repository secret（2024-01 之后的位置；旧版本叫 Settings → Secrets）：

  • Name 填 HEXO_DEPLOY_PRI
  • Value 填 github-deploy-key 的完整内容

公钥放进 your.github.io 仓库，路径 Settings → Deploy keys → Add deploy key：

  • Title 填 HEXO_DEPLOY_PUB
  • Key 填 github-deploy-key.pub 的完整内容
  • 勾上 Allow write access

勾 Allow write access 不能漏。不勾，公钥只能读，部署时 git push 报 403。

编写 deploy.yml #

在 blog 仓库根目录建文件：

text
blog (repository)
└── .github
    └── workflows
        └── deploy.yml

yaml
name: CI

on:
  push:
    branches:
      - master

env:
  GIT_USER: Sanonz
  GIT_EMAIL: sanonz@126.com
  THEME_REPO: sanonz/hexo-theme-concise
  THEME_BRANCH: master
  DEPLOY_REPO: sanonz/sanonz.github.io
  DEPLOY_BRANCH: master

jobs:
  build:
    name: Build on node ${{ matrix.node_version }} and ${{ matrix.os }}
    runs-on: ubuntu-latest
    strategy:
      matrix:
        os: [ubuntu-latest]
        node_version: [16.x]

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Checkout theme repo
        uses: actions/checkout@v4
        with:
          repository: ${{ env.THEME_REPO }}
          ref: ${{ env.THEME_BRANCH }}
          path: themes/concise

      - name: Checkout deploy repo
        uses: actions/checkout@v4
        with:
          repository: ${{ env.DEPLOY_REPO }}
          ref: ${{ env.DEPLOY_BRANCH }}
          path: .deploy_git

      - name: Use Node.js ${{ matrix.node_version }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node_version }}

      - name: Configuration environment
        env:
          HEXO_DEPLOY_PRI: ${{secrets.HEXO_DEPLOY_PRI}}
        run: |
          sudo timedatectl set-timezone "Asia/Shanghai"
          mkdir -p ~/.ssh/
          echo "$HEXO_DEPLOY_PRI" > ~/.ssh/id_rsa
          chmod 600 ~/.ssh/id_rsa
          ssh-keyscan github.com >> ~/.ssh/known_hosts
          git config --global user.name $GIT_USER
          git config --global user.email $GIT_EMAIL
          cp _config.theme.yml themes/concise/_config.yml

      - name: Install dependencies
        run: |
          npm install

      - name: Deploy hexo
        run: |
          npm run deploy

流程是：检出源码 → 主题仓库检出到 themes/concise → Pages 仓库检出到 .deploy_git → 装 Node → 配 ssh 和 git → 装依赖 → 跑部署脚本。

三段检出是关键 #

普通项目一次 actions/checkout 就够，Hexo 需要三次，各自落到不同目录：

检出 落到哪 干什么
源码 工作目录根 拿文章和配置
主题仓库 themes/concise 主题不在源码里，单独拉
Pages 仓库 .deploy_git Hexo 部署时往这里写并 push

with.path 决定检出到哪个子目录。不写就到根目录，三次都写根目录会互相覆盖。

.deploy_git 是 Hexo 约定的目录名，不要改。改了 hexo deploy 会重新 clone 一份，你检出的内容白费。

私钥怎么进 runner #

四步缺一不可，全在 Configuration environment 这个 step 里：

  1. mkdir -p ~/.ssh/ 建目录
  2. echo "$HEXO_DEPLOY_PRI" > ~/.ssh/id_rsa 把私钥写进 id_rsa
  3. chmod 600 改权限，ssh 不接受过宽权限，会直接拒绝使用
  4. ssh-keyscan github.com >> ~/.ssh/known_hosts 把 GitHub 的主机指纹加进去

ssh-keyscan 容易漏。本地用 ssh 第一次会问 yes/no，CI 里没人回答，就一直等到超时。

私钥先写进 env 再落盘，就是第六章讲的「env 引入加命令消费」。直接内联展开也能跑，但脚本里更容易出转义问题。

模版参数逐条说明 #

参数 含义
name 这个 Action 的名字
on 触发条件，on.push.branches.master 指 master 收到 push 后执行
env 环境变量对象
env.GIT_USER Hexo 编译后用这个 git 用户名部署
env.GIT_EMAIL Hexo 编译后用这个 git 邮箱部署
env.THEME_REPO 主题仓库，如 sanonz/hexo-theme-concise

获取是否存在 Tag #

有上一个 tag 才生成 changelog：

yaml
- run: echo "previous_tag=$(git describe --tags --abbrev=0 2>/dev/null || echo '')" >> $GITHUB_ENV

- name: Generate changelog
  id: changelog
  uses: jaywcjlove/changelog-generator@main
  if: env.previous_tag

git describe --tags --abbrev=0 找最近的 tag。没有 tag 时命令失败，|| echo '' 兜底成空串，if: env.previous_tag 判空后跳过。第一个版本发布时靠这个逻辑不出错。

修改 package.json #

按日期生成版本号，用 Node 直接改文件：

yaml
- name: Modify Version
  shell: bash
  run: |
    node -e 'var pkg = require("./package.json"); pkg.version= (new Date().getFullYear().toString().substr(2)) + "." + (new Date().getMonth() + 1) + "." + (new Date().getDate()); require("fs").writeFileSync("./package.json", JSON.stringify(pkg, null, 2))'

生成形如 25.3.14 的版本号：年份后两位 + 月 + 日。JSON.stringify(pkg, null, 2) 保留两空格缩进，跟 npm 的默认格式一致，diff 不会因为格式变化而变脏。

shell: bash 必须写。不写默认走 Windows 上是 pwsh，单引号里的内容会被当成不同语法解析。

克隆带有 Submodule 的仓库 #

yaml
- name: Checkout
  uses: actions/checkout@v3
  with:
    path: main
    submodules: true

submodules 取 true 检出直接子模块，取 recursive 递归检出。要拉子模块的最新提交而不是锁定的 SHA：

yaml
- name: Clone sub repository
  shell: bash
  run: |
    auth_header="$(git config --local --get http.https://github.com/.extraheader)"
    git submodule sync --recursive
    git -c "http.extraheader=$auth_header" -c protocol.version=2 submodule update --init --remote --force --recursive --checkout ant.design

--remote 是关键，不加就只检出主仓库记录的那个 commit。auth_header 从 checkout 留下的配置里取凭据，私有子模块靠它过认证。

提交 commit 到 master 分支 #

yaml
- name: 生成一个文件，并将它提交到 master 分支
  run: |
    # Strip git ref prefix from version
    VERSION=$(echo "${{ github.ref }}" | sed -e 's,.*/\(.*\),\1,')
    COMMIT=released-${VERSION}
    # Strip "v" prefix from tag name
    [[ "${{ github.ref }}" == "refs/tags/"* ]] && VERSION=$(echo $VERSION | sed -e 's/^v//')
    echo "输出版本号：$VERSION"
    # 将版本输出到当前 VERSION 文件中
    echo "$VERSION" > VERSION
    echo "1. 输出Commit：$COMMIT"
    echo "2. Released $VERSION"
    git fetch
    git config --local user.email "action@github.com"
    git config --local user.name "GitHub Action"
    git add .
    git commit -am $COMMIT
    git branch -av
    git pull origin master

- name: 将上面的提交 push 到 master 分支
  uses: ad-m/github-push-action@master
  with:
    github_token: ${{ secrets.GITHUB_TOKEN }}

git config 那两行不能省。runner 上没有全局身份，不配就 commit 失败。邮箱和用户名随便填，但必须是合法格式。git pull origin master 在 push 之前拉一次，减少跟远端撞车的概率。

同步 Gitee #

yaml
- name: Sync to Gitee
  run: |
    mirror() {
      git clone "https://github.com/$1/$2"
      cd "$2"
      git remote add gitee "https://jaywcjlove:${{ secrets.GITEE_TOKEN }}@gitee.com/uiw/$2.git"
      git remote set-head origin -d
      git push gitee --prune +refs/remotes/origin/*:refs/heads/* +refs/tags/*:refs/tags/*
      cd ..
    }
    mirror uiwjs uiw

git push gitee 的 refspec 把远端所有分支和 tag 全量推过去，--prune 删掉 Gitee 上多出来的分支。git remote set-head origin -d 清掉默认分支的引用，避免 push 时带上 HEAD。

GITEE_TOKEN 建在仓库 secret 里。把它塞进 URL 是唯一能免交互认证的方式，代价是 token 会出现在 git 的 remote 配置里——但那个配置在 runner 上，跑完就销毁。

拼发版流水线时别忘了 fetch-depth: 0。默认只拉一个提交的浅克隆，git describe 找不到历史 tag，切片版本号那一步永远是空。

十二、易错点速查 #

现象 原因 改法
后面 job 拿不到前面 job 的文件 以为 needs 会共享文件系统 用 upload-artifact 加 download-artifact
needs 下游 job 一直不跑 上游失败，默认跳过下游 加 if: ${{ always() }}
paths 配了之后 tag 不触发 paths 过滤把 tag 事件也筛掉了 拆成独立 workflow，或去掉 paths
paths 和 paths-ignore 同时写了 两个不能共存 只用 paths 加 ! 排除
$GITHUB_ENV 写完当前 step 读不到 注入发生在下一步之前 当前 step 用普通 shell 变量
下游拿到空 outputs 缺 id 或缺 outputs 映射或缺 needs 三处补齐
fork PR 上 token 为空 secrets 不传给 fork PR，安全设计 用 if 判断 PR 来源后跳过
日志里 secret 没打码 只对完整精确匹配打码 别拼接、别 base64、别截断
推送报 403 GITHUB_TOKEN 权限不足 顶层加 permissions
上传同名 artifact 报错 v4 不允许重名 名字带 matrix 维度
git describe 找不到 tag 浅克隆没有历史 checkout 加 fetch-depth: 0
Windows runner 上脚本语法错 默认 shell 是 pwsh 显式写 shell: bash
ssh 卡住等确认 首次连接问 yes/no ssh-keyscan 写进 known_hosts
ssh 拒绝使用私钥 权限过宽 chmod 600 ~/.ssh/id_rsa
部署报 403 公钥没勾 Allow write access 提权后重建 deploy key
环境突然挂了 latest 是浮动标签，跟着上游升级 钉死版本号
矩阵跑爆额度 多维度笛卡尔积 用 exclude、max-parallel
定时任务不跑了 仓库长期无提交被自动停用 手动跑一次或提交点东西
workflow_run 不触发 workflows 填了文件名 填上游的 name
repository_dispatch 不触发 两边事件名不一致 对齐 event_type

排查顺序 #

第一次配置跑不通，按这个顺序看：

  1. Actions 页面有没有这个 workflow。没有说明文件路径或后缀不对，或者 on 没匹配上。
  2. workflow 出现了但一直是灰的。说明 on 配对了但触发条件没满足，检查分支名和路径。
  3. job 起来了但卡在某一步。看日志，多半是环境或凭据问题。
  4. 全部步骤都绿但结果不对。检查 artifact 名、outputs 链路、版本号提取。

三句话记住核心 #

job 之间不共享文件系统，要传文件用 artifact。 needs 只保证顺序，不保证文件。

secrets 不进 fork 的 PR。 安全设计，改不了，用 if 判断来源绕过。

paths 和 paths-ignore 不能共存，paths 会吃掉 tag 推送。 发版单独拆一个文件最省心。
