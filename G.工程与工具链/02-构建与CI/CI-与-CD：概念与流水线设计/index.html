这篇讲 CI（Continuous Integration，持续集成）与 CD（Continuous Delivery 持续交付、Continuous Deployment 持续部署）的概念与流水线设计，不展开平台语法。

同目录另一篇《GitHub Actions：从触发到部署》已经写完了实操部分：workflow 的结构、触发条件怎么写、job 与 step 怎么排、needs 怎么连、secrets 怎么配、十几个能直接抄的例子，以及把 Hexo 推上 GitHub Pages 的全过程。要抄配置，去那一篇。

这篇只回答设计层的问题：CI 与 CD 的分界线画在哪，一条流水线该有哪些阶段，什么交给机器、什么留给人，job 拆到多细合适，拆完怎么串起来，哪些地方最容易翻车。

下面的代码块只用来示意形状，不绑定具体平台。

一、CI 与 CD 的分界线 #

CI 是 Continuous Integration，持续集成。定义很短：每次把代码合进主干，都触发一次自动构建加自动测试。它防的不是手滑写错一行，而是「我本地是好的」和「这个分支三周没人跑过」。没有 CI 的团队靠人记得跑测试，而人记不住。

CD 有两个意思，英文只差一个词：Continuous Delivery 是持续交付，Continuous Deployment 是持续部署。中文常把两个都叫「持续交付」，一混就说不清了。差别只有一处：产物准备好之后，最后那一步是等人点，还是自己走。

维度 CI 持续集成 CD 持续交付 CD 持续部署
自动化到哪一步 构建加测试，出结论 一直接到「可发布产物」 一直接到生产环境
最后一道动作 无 人点确认 机器执行
谁承担发布风险 提交者 提交者加发布负责人 提交者
出问题的暴露时机 提交后几分钟 点确认之前 上线之后
适合谁 任何有代码的仓库 多数业务系统 发布频繁、回滚成熟、监控到位
失败后怎么办 红灯，没人受影响 卡在门外，可以不发 只能回滚

判断一个仓库处在哪一档，不用看名字，看有没有那道门。

那道门在哪 #

门的物理形态是「环境」加「保护规则」：部署动作引用一个叫生产的受保护环境，环境上挂了人工审批，于是流水线跑到这一步会停住，等人点。没挂环境、或者挂了环境但没配审批，代码合并后机器一路推到线上，这是持续部署。

text
代码合并 ──> 自动构建 ──> 自动测试 ──> 可发布产物 ──> 部署
                                              │
                                   ┌──────────┴──────────┐
                                   │ 有人点确认：持续交付   │
                                   │ 无人点确认：持续部署   │
                                   └─────────────────────┘

两道门的成本差别不在技术，在责任。有门的时候，「今天要不要发」是人做的决定，出了事有人认；无门的时候，决定权交给了「谁最后合的那一行」。

名字对不上现实 #

最常见的错位：仓库名叫 ci-cd，点进去一看是一条测试 workflow 加一段部署脚本，两个 job 并行跑。看着很自动化，实际测试红了站点照样更新，因为部署根本没等构建结果。这不叫持续部署，叫「碰巧也能跑」。

链没串起来的症状很统一：

  • 测试失败的那次提交，线上代码还是变了。
  • 部署日志里的 commit 和构建日志里的 commit 不是同一个。
  • 有人手动 rerun 了部署，但没 rerun 构建，两边产物对不上。

把依赖关系写进流水线，这些症状一起消失。写法在另一篇，这里只记住一条：部署必须挂在构建的下游。

价值不是自动化 #

这句要写清楚：CI/CD 的价值不在「自动」，在「缩短反馈回路」。让问题在提交后几分钟内被发现，而不是在发布前夜。

自动化只是手段。一个跑到 40 分钟的流水线，自动化程度再高也没人等，大家改成先合并、明天再看结果，反馈回路就断了。一条测试十个里错一个的流水线，团队学会「红了先重跑」，红灯就不再是信号。这两件事都会让回路失效，等于没做。

反过来，一个只有 lint 加单元测试、3 分钟出结果的小流水线，价值比一条全自动但没人看的流水线高。

为什么多数团队该停在持续交付 #

全自动部署的风险不在构建失败，构建失败是最容易拦的。真麻烦的失败长这样：

  • 代码没错，配置错了，上线后某个功能的开关没打开。
  • 压测数据正常，真实流量一进来数据库连接数打满。
  • 依赖的下游服务在发版窗口期做维护。
  • 本次改动只有运维知道要提前扩容。

这些检查跑不出来。测试验证的是「代码行为符合断言」，发布验证的是「这一刻发出去会不会出事」。后者要人的判断，还有人的在场。门的意义不是拦机器，是留一个「现在发合适吗」的判断点。

结论：多数团队做到持续交付就够。把构建、测试、打包、发布前准备全自动化，最后一步留人点。等发布频率高到「人点不过来」，或者回滚已经做到一键、监控能兜住，再谈持续部署。

工具怎么选，给结论 #

  • 公开仓库用 GitHub Actions：标准 runner 免费且不限量，不用自己养机器；私有仓库按分钟计费。
  • Jenkins：插件多，但 runner 和插件升级得有人盯，团队里没有专人维护就别碰。
  • Argo CD：只在 Kubernetes 那套部署形态里值，拿它推静态站点是自找麻烦。
  • GitLab CI、CircleCI：适合代码本来就在对应平台的仓库，为了 CI 换个地方托管不划算。

工具是耗材，流水线设计才是资产。下面所有讨论都跟具体平台无关，换工具时能整体搬走。

二、一条流水线的典型阶段 #

一条完整的流水线从提交事件开始，到生产环境结束。中间的阶段不一定要全有，但每个阶段解决一个独立的问题，砍掉哪个就等于放弃哪类信号。

阶段 机器在做什么 价值 失败后果
提交触发 监听合并、打标签、定时器等事件 让检查不依赖人记得 不跑，等于回到手工时代
静态检查 语法、格式、类型、明显 bug 模式 最便宜的一层过滤 脏代码进入后面的所有阶段
构建 装依赖、编译、生成产物 证明「从干净环境能装出来」 本地能跑、服务器装不起来
单元测试 跑函数级断言 快速定位到具体函数 回归无声无息
集成测试 连数据库、连外部服务跑流程 证明组件之间的契约没断 单测全绿、上线全挂
打包 生成镜像、压缩包、静态文件 产出唯一可部署的物件 部署的是临时拼装的东西
部署到测试环境 把产物装进一套隔离环境 给验收一个真实靶子 验收只能靠想象
验收 人点、或用自动化冒烟脚本 最后一道业务判断 功能坏了但没人知道
部署到生产 替换线上版本 交付 出事，只能回滚

越往后失败越贵 #

同一行错误，在不同阶段被发现的代价差一个量级：

  • 静态检查拦下：改一行，重跑一次。
  • 单元测试拦下：看断言，改逻辑。
  • 集成测试拦下：起环境、看日志、查是哪个服务的问题。
  • 验收拦下：涉及两个团队的时间对齐。
  • 生产环境出事：回滚、通报、查数据有没有脏写。

这个顺序决定了流水线该怎么排。不是因为后面的检查不重要，是因为前面的检查便宜，能先把明显的问题清掉，让后面昂贵的检查只在真需要时才跑。

text
提交
  └─> 静态检查 ──> 构建 ──> 单元测试 ──> 集成测试 ──> 打包
                                                      │
                                                    部署测试环境
                                                      │
                                                    验收（人）
                                                      │
                                                    部署生产

阶段可以合并，不能跳 #

小仓库完全可以合并：构建和单元测试放一个 job，集成测试和部署测试环境放一个 job。合并省的是等待时间，不是检查项。

不能跳的是这两类：

  • 静态检查。它便宜到没理由跳过，也是唯一能在「代码还没构建成功」时就给结论的一层。
  • 打包。本地能跑，不等于从仓库干净检出、装完依赖、用产物路径能跑。打包就是验证这一点的动作。

最容易被省掉的是「部署到测试环境」：要么测试环境长期挂着旧版本，要么干脆没有。结果验收变成「在我机器上点点看」。

触发粒度也是设计 #

流水线什么时候跑，本身是设计决定，不是配置细节。

  • 每个分支都跑全量：反馈齐全，代价是机器时间。
  • 只对主干和 PR 跑：够用，但没人跑过的分支会烂掉。
  • 按路径过滤：只改了文档就别构建，省时间。

路径过滤有个坑要提前知道：被过滤规则跳过的 workflow，它在 PR 上关联的检查会一直停在「等待中」。仓库把这项检查设成合并必需时，PR 就卡住，永远等一个不会来的结果。所以给 PR 用的那些必需检查不加路径过滤，只改文档的提交也照样跑一遍。

定时触发（cron）适合夜间全量回归、依赖漏洞巡检这类任务。用的时候注意两点：时刻按 UTC 算，不是本地时间；最短间隔是 5 分钟，别把全量构建挂到 5 分钟一次，私有仓库的计费分钟数烧得很快。

环境阶梯 #

阶段表里的三段环境不是摆设，各自负责一类问题：

环境 装的是 用来回答 数据
开发 最新代码，随时变 这个改法通不通 假数据
测试 每次构建出来的产物 这个版本对不对 构造数据
生产 人确认过的产物 真实流量扛不扛得住 真数据

一条铁律：产物逐级往上升，环境之间不重新构建。测试环境验的和生产上的是同一个物件，才叫「验过了」。每个环境各构建一次，等于验了三个不同的东西。

验收站在测试环境之后、生产之前。它是阶段表里唯一必须由人参与的环节，也是持续交付那道门的位置。

三、快速失败原则 #

流水线设计只有一个核心原则：把最便宜、最容易失败的检查放最前面。行业里叫 fail fast，快速失败。

理由跟成本有关。一条流水线的总耗时由所有阶段累加，但人实际感受到的是「从提交到拿到第一个结论」的等待。把秒级的格式检查放在几十分钟的集成测试后面，等于让最便宜的信号排在最后。

四条排序规则：

  1. 快的排前面。格式化、语法、类型检查都是秒级，构建和测试是分钟级。
  2. 确定性高的排前面。静态检查的结论没有随机性，跑一次就是一次结论。
  3. 失败率高的排前面。日常提交里最常犯的错先被拦下，后面的阶段就不用白跑。
  4. 无依赖的排前面。需要起数据库、拉镜像、连外部服务的检查放在后面。

按这四条排出来的顺序几乎是固定的：

text
格式检查  ──>  语法/类型检查  ──>  构建  ──>  单元测试  ──>  集成测试  ──>  端到端
  秒级           秒级               分钟级      分钟级        最慢          更慢

便宜的先跑，不只是省时间 #

假设一次提交有格式错误。如果格式检查在最前面，几秒后红灯，改一行，重跑。如果它在最后面，前面几十分钟全跑完才告诉你结尾多了一个空格——你会开始怀疑这个检查的价值。

人对流水线的信任就是这么一点点被磨掉的。连续三次「等了十分钟，报一个空格」，第四次就会有人提议把格式检查关掉。

快失败也保护后面的阶段 #

构建失败的产物，跑单元测试没有意义；单元测试大红的代码，起集成环境只是浪费机器时间。前置阶段失败后立刻终止，后面的阶段一个都不启动，这是快速失败的第二个作用：不做无用功。

但有一种情况要反着来：诊断性任务需要「即使前面失败也跑」。比如「即使测试红了也要把失败截图和覆盖率报告传上来」。这类步骤要显式声明「不管上一步成功与否都执行」，否则默认行为是失败即终止，报告永远传不上来。

红灯意味着什么 #

快速失败能成立的前提是：红灯真的意味着代码有问题。下面三件事会让红灯失去含义：

  • 同一个测试今天过明天不过，没人去修，团队学会「重跑一次」。
  • 流水线偶尔因为基础设施抖动失败（拉不到镜像、runner 磁盘满），和真失败混在一起。
  • 有已知的失败用例挂着不管，红灯变成常态。

一旦红灯不再是信号，前面所有排序工作全部作废。这是流水线的头号杀手，比慢更要命。慢只是让人等，假红灯让人不看。

时间预算 #

给一条流水线定个目标时长，是设计的一部分。

  • 静态检查加单元测试：控制在 5 分钟以内。超过这个数，PR 上没人等结果，都先合再说。
  • 到「可发布产物」为止：10 分钟以内。
  • 总时长（含集成测试和部署测试环境）：20 分钟到 30 分钟。

这些数字来自工程实践的经验区间，不是测量结论。真正的判据是这条：超过 10 分钟，等的人就开始干别的，反馈回路实际中断。这时候要么拆并行，要么把慢的检查挪到夜间。

超过预算怎么办，按性价比依次试：

  1. 并行。互不依赖的测试拆成多个 job 同时跑。
  2. 缓存。依赖装一次存起来，下次直接取。
  3. 只跑受影响的测试。用改动路径判断哪些测试需要跑。
  4. 分级。PR 上跑快速子集，完整套件放合并后或夜间。

四、什么该自动化 #

判据只有一条：重复的、确定性的、有明确通过/失败判据的，交给机器。

三个条件同时成立才值得自动化。拆开看：

条件 含义 反例
重复 每次提交都要做一遍，或者每天都要做 一年发一次版才用的发版脚本
确定性 同样输入必然同样输出，没有「看情况」 「这个改动影响面大不大」
有判据 能写出一句「通过」或「失败」的判定 「这个接口设计合不合理」

按这条判据过一遍，该自动化的东西很集中：

  • 格式与风格检查。行宽、缩进、引号、import 顺序。
  • 语法与类型检查。编译得过吗，类型对得上吗。
  • 单元测试。函数行为是否符合断言。
  • 构建。从干净环境能不能装出产物。
  • 集成测试与冒烟测试。组件之间的契约有没有断。
  • 打包与产物归档。产物是不是唯一、可复现。
  • 部署到测试环境。这一步的判据是「装成功了，健康检查过了」。
  • 依赖漏洞扫描、许可证检查。判据是「有没有已知高危漏洞」。
  • 夜间全量回归。判据是「有没有新的失败」。

观察到的三条经验 #

第一，凡是「人做的时候老是忘」的事，都该自动化。忘了跑测试、忘了升版本号、忘了同步文档分支——这类遗漏是自动化的最佳目标，因为判据清楚，只是人不可靠。

第二，凡是「人做的时候每次都要查文档」的事，都值得自动化。查一次是学习，查一百次是浪费。

第三，凡是「做完之后没人看结果」的事，不该自动化。一条没人读的报告，和没跑是一样的，还多消耗机器时间。要么让它失败时能找到人，要么砍掉。

自动化的边界要写下来 #

流水线一旦跑起来，它会慢慢被塞进越来越多东西。半年后回头看，一条 workflow 里混着构建、测试、发通知、同步镜像、清理缓存、更新文档、发版本号——没人敢改。

给流水线划个边界，写进文档：它负责「从提交到可部署产物」，不负责「部署之后的事」。监控、告警、日志聚合是另一套系统。

五、什么不该自动化 #

这一节比上一节重要。多自动化一样东西，成本不只是写配置那点时间。

需要人判断的 #

代码可读性评审是典型。一个函数能不能看懂、命名是否准确、抽象层次对不对——这些没有通过/失败的判据。工具能给的是「圈复杂度 12」，但那不是结论。

设计评审同理。「这个方案在这个业务规模下合不合适」只有人答得出。

这类事放进流水线的后果是可预期的：机器给出一个粗糙的分数，人照着分数改，改到分数达标，代码照样难读。指标变成了目标，就不再是好指标。

一次性的任务 #

迁移脚本、历史数据清洗、仓库结构调整、把某个服务从 A 平台搬到 B 平台——这些做一次就完，写进流水线的维护成本高于收益。

判断方法：如果这个脚本明年还会跑第二遍吗。不会，就写个一次性脚本，跑完留着记录。

例外是一种：需要「每次都能重复跑」的一次性任务，比如「重建测试数据」。这属于重复任务，归上一节。

成本高于收益的 #

自动化的收益 = 省下的人工时间 × 次数。成本 = 写配置的时间 + 以后维护的时间 + 出错排查的时间。

会落在成本侧的典型：

  • 只有一个项目用的特殊检查。写配置文件花两小时，每次省三十秒。
  • 界面外观的像素级比对。环境字体差一点就红，天天修。
  • 需要复杂前置条件的端到端测试。为了跑它要维护三套 mock 服务，而那三套 mock 本身就是 bug 来源。
  • 把部署凭据塞进 CI 里做「一键上线」。省的那一下点击，换来凭据扩散的风险。

不该做不等于不做 #

注意区分「不该自动化」和「不该做」。代码可读性该有人评审，只是不该由一个自动步骤判定；一次性任务该有人做，只是不该进流水线。

不做自动化的那些事，要落到别的地方：评审清单、发布检查表、人工操作手册。它们不是流水线的失败，是分工。

一个判断工具 #

拿不准的时候问三个问题：

  1. 这件事做错的后果是什么，能被别的检查拦住吗。
  2. 判定标准能写成一句话吗，这句话机器能读懂吗。
  3. 这件事一年会做几次。

第一个问题的答案如果是「后果很严重但拦不住」，那更该补监控和回滚，而不是硬塞进 CI。第三个问题的答案如果小于十次，先别写。

六、流水线的常见反模式 #

下面七条按「见过多少次」排序。每条都给出症状、为什么错、怎么改。

反模式 症状 根因 改法
一个巨型 job 干所有事 红了不知道哪步错，要翻完整日志 图省事，把所有步骤塞一处 按「失败原因类别」拆 job
流水线跑太久 没人等结果，合了再看 串行到底，不做并行与缓存 并行、缓存、只跑受影响的部分
测试不稳定没人修 红灯先重跑，重跑成习惯 拿「偶发」当解释 不稳定测试当场标出来隔离
只跑测试不跑静态检查 提交记录里全是格式修正 认为格式是小事 静态检查放最前面，几秒钟的事
凭据遍地都是 每个 job 都能读生产密钥 权限没分级，图方便 按环境分级，最小权限
流水线是唯一的手册 只有一个人会改这条 workflow 知识没有沉淀 配置进仓库，写清为什么这么排
什么都塞进 CI 发通知、清缓存、更新文档全在里面 边界没划 只负责到「可部署产物」

巨型 job #

症状很具体：一条 workflow 里只有一个 job，二十几个步骤从上跑到下。某次失败，日志滚了三千行，你在找是哪一步红的。

为什么错：失败原因被压平了。跑测试失败和装依赖失败是两个完全不同的问题，前者改代码，后者改配置或查网络，混在一个 job 里就得靠人肉区分。

为什么有人这么写：拆 job 意味着每个 job 都要重新拉代码、装环境，总时长会涨。这个顾虑是真的，见第八节。

怎么改：按「失败后你要去找谁」来拆。静态检查失败找写代码的人，依赖安装失败找维护依赖的人，部署失败找运维。同一类原因放一起，不同类分开。

流水线跑太久 #

症状：PR 提上去，去倒杯水，回来还没完，于是先干别的，两小时后想起来看，绿了，合了。整个过程里流水线没有起到任何拦截作用。

为什么错：反馈的价值随时间衰减。3 分钟的结果有人看，30 分钟的结果等于事后审计。

怎么改：先量出各阶段耗时，找最长的那个。常见做法是并行拆 job、给依赖装缓存、只跑受影响的测试、把全量回归挪到夜间。

一个细节：优化之前先量化。凭感觉拆 job 经常拆完更慢，因为每个 job 都要重新准备环境。

测试不稳定 #

症状：同一个 commit 重跑一次就绿了。团队里流传一句话「这个测试偶尔会挂，重跑就行」。

为什么错：这是所有反模式里破坏力最大的。红灯一旦不代表「代码坏了」，「看红灯」这个行为就消失了。三个月后没人知道主干是不是好的。

不稳定的来源集中在这几类：依赖真实时间的测试、依赖执行顺序的测试、共享外部服务的测试、并发下互相干扰的测试、没有隔离的临时文件。

怎么改：

  1. 一发现不稳定就标出来，单独隔离跑，不阻塞主流水线，但要有人跟进。
  2. 记录重跑次数。同一个测试一周内重跑超过两次，当成必修缺陷。
  3. 别用「再跑一次」当解决方案。重跑是排查手段，不是修复手段。

只跑测试不跑静态检查 #

症状：提交历史里有一堆「fix lint」「格式修正」。

为什么错：把最便宜的检查留给了人。格式问题是机器一眼能看出来的，让人来回改是浪费。

怎么改：静态检查放在流水线第一位，几秒钟出结果。同时给本地配好自动格式化，让人在提交前就不产生这类问题。

凭据遍地都是 #

症状：所有 job 都能读到生产环境的密钥；测试代码里能看到真实的 token。

为什么错：一处泄露全身失守。流水线是攻击面，第三方 action、被污染的依赖、日志泄露都从这里进来。

怎么改：见下一节。

流水线是唯一的手册 #

症状：只有一个人会改这条配置；问他为什么这么排，答案是「之前这么写的」。

为什么错：配置进仓库了，但决策理由没进仓库。下一个人只能猜。

怎么改：把配置和理由放在一起，用注释写「这一步为什么在这里」。改动时一起改。

什么都塞进 CI #

症状：一条 workflow 里混着构建、部署、发钉钉通知、清理云缓存、更新文档站、自动发版本号。

为什么错：职责混在一起后，任何一处小改动都要碰这条流水线；改坏的风险和改动量不成比例。

怎么改：划边界。CI 负责到「可部署产物」，之后的事情各有各的系统。

逃生门 #

流水线得留一个「这次不跑」的口子，否则改一个错别字也要等十分钟，人就会开始想办法绕。

常见的口子有三个：按路径过滤、在提交信息里带跳过标记、手动触发。

口子本身没问题，问题是它会被滥用。第一周用来跳文档改动，第二周用来跳「只改了一行配置」，第三周用来跳「这次赶时间」。三个月后流水线形同虚设。

给口子定规则，规则要写进文档：

  • 只允许跳「不改变产物」的改动。文档、注释、README 属于这类；任何会进产物的文件都不算。
  • 跳过之后要有替代检查。文档改动至少过一遍格式检查。
  • 跳过要在提交信息里留痕，事后能查。别用「本地跑过了」当理由——本地跑过的是你的机器，不是干净环境。

手动触发是另一类口子，它不跳过检查，只是让检查不在每次提交时跑。适合发布、巡检、全量回归这类不该跟着每次提交走的事。

写法上的细节去另一篇查，这里只强调设计：口子越少越好，每个口子都要说清什么情况下能用。

七、环境与凭据管理 #

流水线的安全模型只有两条：凭据不落在代码里，权限只给到需要的地方。

三套环境，三套凭据 #

环境 凭据用途 谁能读 保护级别
开发 连开发库、调测试接口 全体开发者 低，泄露影响有限
测试 部署测试环境、跑集成测试 流水线自动读 中，不对公网暴露
生产 上线、改配置、动数据 只有受保护环境里的 job 高，要审批

关键设计：三套环境的凭据互不相同。用一套凭据通吃三套环境，等于测试环境的任何一次泄露都直接威胁生产。

同理，测试环境的所有东西都该是「能随便删」的。测试库里的数据是构造的，测试桶里的文件是临时的。反过来，生产环境的一切操作都该有痕迹。

凭据不硬编码 #

这条没有例外。不在代码里写密码，不在配置里写密钥，不把 token 拼进命令行。

具体到流水线，三件事值得做：

  1. 密钥存在平台的密钥存储里，用变量引用，不在配置文件里出现明文。
  2. 用环境变量传给脚本，不要拼进命令字符串。拼进命令行的密钥会出现在进程列表和日志里。
  3. 日志里要能屏蔽敏感值。多数平台会自动遮蔽已注册的密钥，但自己打印的中间值不一定被识别。

关于拼接的风险，值得单独说一句：把外部输入（分支名、PR 标题、commit message）直接拼进 shell 命令，是命令注入的常见入口。这类输入的来源不可控，来自 fork 的 PR 尤其如此。用环境变量传，让 shell 别去解析它。

最小权限 #

权限不是「有没有」的问题，是「多少」的问题。两种权限要分开管：

  • 流水线自身的 token。默认给读写全部，改成一律只读，需要写的 job 单独放开。不收窄权限，任何一次依赖被投毒都有机会顺手改仓库内容。
  • 部署用的密钥。分开测试环境和生产环境的密钥，分开只读和可写的密钥，能只读就只读。

具体到部署密钥，一条实践是：部署密钥只对目标仓库有写权限，不给别的仓库。一把密钥能推所有仓库，等于没有隔离。

fork 与外部贡献 #

从 fork 提上来的 PR 默认拿不到密钥，这是设计如此，不是配置漏了。

背后的道理：PR 里的代码是不可信的，任何能执行仓库代码的流水线都会被它利用。所以权限被收紧是安全边界，不是 bug。

想验证外部 PR 的构建结果，做法是「先跑无密钥的检查，人工审查后再跑完整流程」。别为了让它跑通就打开不安全的检出选项——那两个特殊触发器带着基础仓库的 token 和密钥。

凭据的轮换 #

密钥用了两年没换过，是常见的状态。轮换的成本主要不在换，在「换的时候有多少地方要同步改」。

把密钥集中到一处引用（一个变量名），轮换就变成改一个值。散落在十个地方，就没人愿意轮换了。

轮换的触发条件可以写清楚：有人离职、有依赖被曝漏洞、定期（比如每季度）。不写清楚，就是永远不换。

环境是审批点，也是隔离点 #

受保护环境承担两个职责，容易被混为一谈：

  • 审批：引用这个环境的 job 会停下来等人点。
  • 隔离：只有这个 job 能读到这个环境的密钥，其它 job 读不到。

一个常见的错：以为配了审批就有了隔离，结果密钥配在仓库级，全仓库可读。审批形同虚设，因为绕过审批的路还在。

八、把流水线拆成多个 job #

第四节和第六节都在说「拆」，这一节说拆的代价，以及拆到哪儿停。

一个 job 就是一台上新开的机器：拉代码、装环境、跑步骤、销毁。job 之间默认不共享任何东西，不共享内存，不共享装好的依赖，不共享文件系统。

所以拆分是一笔交易：

拆得细 拆得粗
失败定位快，红的是哪个 job 一目了然 失败后要翻日志找是哪一步
可以并行，总耗时下降 只能串行，总耗时累加
每个 job 能看到自己的用时和日志 时间混在一起
每个 job 重新拉代码、装环境 环境准备只做一次
中间结果要靠产物传递，多一层出错点 中间结果就在本地目录里
job 数量多，配置变长，改一次碰多处 一条配置读完就懂

结论：拆到什么程度，取决于「定位问题的成本」与「等待的成本」哪个更高。定位一次失败要花 20 分钟找人问，那就值得为它拆一个 job；团队只有三个人、看一眼日志就知道哪步错，拆太细反而增加维护。

按失败原因拆，不按技术栈拆 #

一个常犯的错误是按目录或语言拆：「前端 job」「后端 job」「脚本 job」。这样的 job 红了，你还是不知道是装依赖失败、编译失败还是测试失败。

更合适的切法按失败原因归类：

text
job: check    静态检查 —— 红了：改代码格式或类型
job: build    构建     —— 红了：改依赖或构建配置
job: test     单元测试 —— 红了：改逻辑
job: e2e      集成测试 —— 红了：查环境、查服务、查数据
job: deploy   部署     —— 红了：查凭据、查目标环境

每个 job 的红色都指向一个明确的下一步动作。这比按目录拆有用得多。

依赖关系 #

job 之间默认并行。要让后面的 job 等前面的，就得声明依赖。

默认行为要说清楚，免得踩坑：

  • 没有声明依赖的 job 全部并行启动。
  • 声明了依赖，等上游全部成功后才跑。
  • 上游失败，下游直接跳过，不执行。
  • 上游被跳过，下游也跳过。
  • 想打破「上游失败就跳过」的规则，要显式声明「无论上一步结果如何都执行」。

最后这条的用途是诊断：即使测试红了，也要把失败截图、覆盖率报告传上来。默认不会传，因为默认行为是失败即终止。

值怎么从上一个 job 传到下一个 #

job 之间不共享文件系统，所以有两种传法，用途不同：

  • 小的字符串（版本号、构建标识、产物的目录名）：用输出值。上游在一个步骤里声明「这个步骤产出什么」，下游通过依赖关系取到。
  • 大的文件（构建产物、测试报告、日志包）：用产物上传下载。

两种传法的选择很直接：能用字符串就别传文件；传文件就别指望它在下一个 job 的本地目录里等着你。

一个历史教训值得记一笔：早期写输出值的语法是打印一行特殊格式的字符串，这个写法在 2022 年被宣布废弃。现在的做法是往一个由环境给出的临时文件里写。照抄三年前的博客，会拿到一个已经不生效的语法——命令没报错，值就是传不过去。这个坑排查起来很费时间，因为流水线是绿的。

中间产物 #

产物是 job 之间唯一的桥。设计上有四点要定：

  1. 产物要有名字。名字是下游取用的钥匙。
  2. 产物要能区分。多套并行构建（比如多个运行环境版本）往同一个名字写，会撞车。做法是在名字里带上区分的后缀。
  3. 产物要做完整性校验。构建没产出目录时，如果上传步骤不报错，下游会拿到一个空目录继续跑，然后在更远的地方以更奇怪的方式失败。最好的做法是让「没产出」当场报错。
  4. 产物会过期。默认保存天数有限，别指望一个月后还能从流水线里翻出当时的东西。

还有一个细节：产物打包会丢文件权限。压缩之后下载解压，可执行位没了，chmod +x 过的脚本变成不可执行文件。要保留权限，就先打成 tar 再上传，或者上传时关掉压缩，下载后自己解开。

产物不可变 #

较新的产物实现是不可变的：同名产物一旦创建，不能再往里写。这条规则会让老写法直接失败——多个并行 job 写同名产物以前是「后写的覆盖」，现在是「直接报错」。

正确做法是每个 job 写自己的名字。这条规则本身是好事：产物和某次构建一一对应，不会出现「一半来自这次构建、一半来自上次」的混合物。

并行构建 #

同一个 job 需要验证多种组合时（多个语言版本、多个操作系统、多个依赖版本），用矩阵展开：声明一个维度，平台会为每个取值各开一个 job。

矩阵的代价是 job 数按维度相乘增长。三个取值乘三个操作系统就是九个 job，九个 job 各拉一次代码。所以矩阵的维度要克制，别把所有能想到的组合都列上。取「最低支持版本」和「最高版本」两端，就够发现兼容性问题。

矩阵里的产物命名尤其要带后缀，否则多个 job 抢同一个名字。

九、跨 workflow 的协作 #

一条 workflow 跑完要触发另一条，是真实需求：CI 完成后触发部署、发版后触发文档更新、夜间任务完成后触发报告。

但先问一句：为什么不在同一条 workflow 里。多数时候拆成两条是因为历史遗留，不是因为需要。同一条里能做完的事，拆成两条会多出「怎么把结果传过去」这个新问题。

真正需要分开的场景只有这几个：

  • 触发条件不同。PR 上跑快速检查，合并后跑完整套件，夜间跑全量回归。
  • 权限不同。构建只需要读，部署需要写，分开才能各自收窄。
  • 生命周期不同。一条是每次提交都跑，一条是发版时跑一次。

两种串接方式 #

第一种是自定义事件：上游主动发一个带事件名的事件，下游监听这个事件名。好处是能带自定义参数，事件名自己定；代价是要写代码去发。

第二种是「某条 workflow 完成后触发」。不用发事件，声明「监听这条 workflow 的完成」即可。代价是它只告诉你「跑完了」，参数要从上游的运行记录里自己取。

text
代码合并
   └─> workflow: CI   (构建 + 测试)
          └─> workflow: Deploy  (监听 CI 完成)

一个必写的判断 #

「完成后触发」只表示结束，不表示成功。构建失败了，也照样算「完成了」。

所以下游必须显式判断上游的结论是不是成功，把这一条写成条件。省掉它的后果可以想象：CI 红着，部署照样执行。

这条也是第六节「链没串起来」的另一个入口——依赖写在了 workflow 之间，但没写条件，等于没写。

权限与代码来源 #

这两个触发器有一个共同点：它们运行在基础仓库的上下文里，能拿到基础仓库的凭据和密钥。

于是有一类危险的组合：这类 workflow 里检出 fork 的代码并执行。上游代码来自不受信任的人，一执行就能读到密钥。

较新的检出动作对这种情况有默认防护：在这两类触发器里，默认拒绝检出 fork PR 的代码，要显式打开一个名字里就带「不安全」的选项才放行。别为了让流水线跑通就随手打开，先想清楚这段代码为什么需要在这里跑。

串接的另一种做法 #

需要「复用一段逻辑」而不是「触发另一条流程」时，用可复用的工作流：把公共部分定义成带参数的模板，多条 workflow 引用同一个模板。

两者的区别值得分清：

  • 触发：上游结束之后，另一条流程从头开始跑。两条是独立运行，各自有独立的记录。
  • 复用：把一段步骤嵌进当前运行里，共用这台机器和这次上下文。

多数人想要的是复用，写成了触发。症状是配置重复、参数靠猜、日志要跳着看。

十、可观测性：日志、产物与通知 #

流水线的输出是给人看的。看不到就没法修，太吵就没人看。

失败要能一眼定位 #

三个层次，从粗到细：

层次 看什么 解决什么
概览 哪个 job 红了 去哪里找
步骤 哪个步骤红了 哪一类问题
日志 具体哪一行报了什么 怎么改

设计上能做的是让这三层不要断。断的典型：

  • 一个 job 里塞了二十个步骤，概览层只告诉你「job 红了」。
  • 关键信息打在循环里，一次几百行，滚动日志淹掉了错误行。
  • 错误信息只在最后一行，而日志被截断。

几条实操建议：给每个步骤起个能读懂的名字，别叫「Run script」；让脚本在出错时输出上下文而不是只输出退出码；把长循环的日志压缩成摘要。

日志里的敏感信息 #

日志是公开的——至少在团队内部是。写日志时默认它会被人看到，还会被贴进工单。

  • 不要把密钥、token、完整的连接串打进日志。
  • 平台对已注册的密钥会自动遮蔽，自己拼出来的中间值不一定会。
  • 调试时临时打印的变量，删掉再提交。

产物要留，但别留成垃圾场 #

产物有两个用途：给下游用，给事后查。

给下游用的产物要求是可靠的、能校验的；给事后查的产物要求是可追溯的。两者都指向一条：产物要带够元信息——哪次运行产生的、什么代码版本、什么时候。

保留策略上要定天数。永久保留的产物会占满配额，也会让人放弃整理。常见做法：日常构建的产物留几天到两周，发布产物的留更久。

通知 #

通知的设计目标是「该看的人看到，不该看的人不被打扰」。落地就一句话：只在需要人动作的时候通知。

事件 要不要通知 通知谁
主干的构建失败 要 提交者，加一个团队频道
分支的构建失败 不要 存着，谁看谁知道
部署成功 不要（除非是生产） 生产部署要留记录
生产部署失败 要 值班的人
夜间回归出现新失败 要 负责这块的人
流水线跑过了 不要 没有

最后一行是最常违反的：每条流水线结束都往群里发一条「构建成功」。这种消息一周之后就被无视，一个月之后被人屏蔽，连带把真正重要的告警一起屏蔽。

实现的细节不用展开，原则是：通知里要带上「谁的问题」和「点哪里看」。一条只说「构建失败」的通知，收到的人还得自己去找是哪条。

别把流水线日志当唯一证据 #

流水线日志会过期、会被清理、会在配额满时丢失。真正需要长期留的证据（发布记录、合规审计）要落到独立的地方。

这一条要区分清楚：日志是排障工具，不是审计系统。

十一、从零开始建流水线的顺序 #

顺序错了，三个月后会得到一条没人敢改的流水线。正确顺序只有一条：

text
1. 静态检查  ──>  2. 单元测试  ──>  3. 构建产物  ──>  4. 部署测试环境  ──>  5. 部署生产

每一步都要跑通、有人用、稳定一周，再进下一步。加部署之前先有几个月的绿灯记录，这是判断「前面的检查可信」的唯一依据。

反过来做——先上部署再补测试——会发生什么很容易预测：部署已经自动化，测试成了摆设，因为部署不需要它；等哪天真出事，才会发现测试从来没拦住过东西，而这时没人愿意回头补。

先把四个词分清 #

抄配置之前先对齐层级，不然改的时候不知道该动哪一层。这四个词递进包含：

text
workflow   一次运行的完整定义
  └─ job       一次运行里的一组任务，跑在一台机器上
       └─ step      任务里的一个步骤，顺序执行
            └─ action    步骤调用的现成动作

三个设计上的含义：

  • workflow 可以有很多个。一条路一条线，别把不相关的流程塞进同一个文件。
  • job 是资源边界。一个 job 一开一台机器，跨 job 的东西都得显式传。
  • step 是失败边界。某个 step 退出码不是 0，这个 job 判失败，后面同 job 的 step 不再跑。

第一步：先让机制跑通 #

先把最小的一条链建起来：一个触发条件、一个 job、一个步骤。步骤内容随便，打印一行字就行。

这一步验证的不是技术，是四件事：

  • 提交后流水线真的会启动。
  • 结果能在某处看到（提交记录旁、页面上）。
  • 失败时能看到日志。
  • 你知道去哪里改配置。

跑通之后再谈检查项。很多人一上来直接抄一份三十行的完整配置，跑不通时不知道是触发没生效、还是环境不对、还是脚本错了。

第二步：静态检查 #

第一项真正的内容检查，选它有三个理由：快、确定性高、不会误报。

  • 快。秒级出结果。
  • 确定。同样的代码永远同样的结论，没有「这次过了下次挂」。
  • 好改。报错信息直接指向行号。

静态检查的范围按顺序加：格式、语法、类型。别一开始就上全套规则，先上「团队会真的去改」的那几条。规则开了没人改，等于没有规则。

第三步：单元测试 #

加这一步的时候同步设一个时长目标。超过十分钟的单元测试套件，要么拆并行，要么把慢的部分挪走。

验收标准是：每次失败都有人看。做不到这一点就先别加，加了也是白加。

第四步：构建 #

「能构建」和「能跑测试」是两件不同的事。测试往往直接在源码目录跑，构建则是从干净检出开始装依赖、编译、产出。

这一步的价值是证明「别人拿到这份代码能装起来」。本地能跑、服务器装不起来，是最常见的一类问题，只有清空环境的构建能发现它。

到这一步，产物要存档。存档的意义是后面所有部署都从同一份产物出发。

第五步：部署到测试环境 #

这一步的判据很明确：装成功了，健康检查过了。

先部署到测试环境，不要直接上生产。测试环境的作用是给「验」一个真实靶子。没有测试环境的时候，验收会退化成「在我机器上点点看」，而机器和你不一样。

第六步：部署到生产，先手动触发 #

生产部署的第一版不要接在自动链上。做成「手动点一下才跑」，跑上十几次，确认没有意外。

手动触发阶段做的事情其实是收集信息：部署要多久、失败时哪些地方会报错、失败之后怎么退回去。这些信息在自动触发下同样需要，只是没有在低风险的时候收集过。

第七步：决定要不要关门 #

两种做法：

  • 关上门：生产部署加人工审批，谁点谁负责。多数团队的最优解。
  • 不关门：确认后就把审批去掉，代码合并即上线。前提是回滚已经一键完成、监控覆盖到关键路径、发布频率高到人工确认成为瓶颈。

做了几个月的持续交付之后，再判断要不要往持续部署走。判断依据不是「能不能做到」，是「出事时能不能快速退回去」。

变量该放哪 #

这一节说设计，写法去另一篇查。

变量有三个层级，从外到内：整条流水线、单个 job、单个步骤。越靠内的优先级越高。这条规则决定了两件事：

  • 所有 job 都要用的配置（比如日志级别、统一的超时值）写在最外层，改一处全生效。
  • 只有某个 job 需要的（比如部署目标）写在该 job 上，别的 job 看不到，也就无从误用。

反过来写——把生产的部署目标写在最外层——等于每个 job 都能往生产推。这是第七节说的权限扩散的一种形态。

两类取值要分清 #

运行时的信息有两套读法，混用是最常见的一类空值事故：

  • 表达式求值：在配置交给运行器之前就算好了。
  • 环境变量：运行器上真实存在的变量。

两者的边界要记住：默认环境变量不在表达式的变量上下文里。所以拿表达式去读一个默认变量，得到的是空值，而不是报错。空值造成的问题会一路传到很远的地方才爆。

常用的默认变量就那么几个：commit 的完整哈希、分支或标签的引用、工作目录、两个用于写输出值和生产环境变量的临时文件路径、以及一个恒为真的标记（很多工具靠它判断「我在 CI 里」）。

另一个坑：自定义变量名不能以平台保留的前缀开头。用了这个前缀，赋值会被静默忽略——不报错，就是不生效。查半天发现变量没生效，先看名字。

密钥该放哪 #

密钥和普通变量的分界线很简单：一旦泄露会有后果的，都是密钥。

存的规则：

  • 存在平台的密钥存储里。不在配置文件里，不在代码注释里，不在仓库的配置文件里。
  • 引用的时候用变量语法，让运行器去注入。
  • 传给脚本时走环境变量，不要拼进命令字符串。

最后这条不是洁癖。拼进命令行的东西会出现在进程列表里，也会出现在日志里；而且如果拼的是外部输入（分支名、PR 标题），还多一层命令注入的风险。

还有一条必须知道的默认行为：从 fork 提上来的 PR 拿不到密钥。这是安全设计，不是配置问题。想让外部 PR 的代码跑通还能读密钥，那不是配置能解决的，那是在自找麻烦。

为什么顺序不能反 #

把整个顺序倒过来看一遍，每一步都被前一步保护：

  • 有静态检查，单元测试的失败才更容易是真逻辑问题，而不是拼写错。
  • 有单元测试，构建失败才更容易是环境问题，而不是代码没写完。
  • 有构建，部署失败才更容易是凭据或目标环境问题，而不是产物不对。
  • 有测试环境的部署经验，生产部署的手动操作才有依据。

跳过某一步，后面所有失败的归因都会变模糊：你不知道这次红是代码问题还是环境问题，于是开始习惯性重跑。

落到一个具体的例子 #

写博客这件事很适合当样本，因为它的痛点非常典型。

本地的场景：改一篇文章，本地跑一次生成，推上去。问题有三个——本地环境和构建工具版本绑定，升级本地运行环境会连带把构建搞坏；文章一多，生成加部署要等很久；构建这一步依赖「记得在自己机器上跑」。

把这件事搬进流水线的动机不是「想自动化」，是这三个痛点都指向同一件事：构建不该依赖某台特定的机器。

搬进去之后，本地只管推，机器版本跟自己的电脑脱钩。顺带得到一个副作用：每次发布都有记录，知道哪篇文章是在哪次构建里上线的。

至于它算交付还是部署，取决于有没有那道门。把发布接在构建下游、不加人工审批，是持续部署；单独拆出一个引用受保护环境的步骤、配了审批人，是持续交付。同一件事，加不加一个配置项，性质完全不同。

这也是为什么第一节说「别看名字，看有没有那道门」。

十二、易错点速查 #

下面按「踩到的频率」排。每条都是能查证的现象，不是猜测。

易错点 现象 处理
用滚动的镜像标签 今天能构建，下个月突然挂 钉死具体版本，接受跟进退役的代价
用可变的主版本号引用第三方动作 上游改动把流水线改坏 钉到具体版本或完整提交哈希
输出值用了已废弃的语法 命令不报错，值就是传不过去 改用官方当前写法，写环境提供的临时文件
跨步骤传变量用错机制 上一步设的变量下一步读不到 输出值走输出文件，环境变量走环境文件
产物重名 并行 job 互相覆盖或直接报错 产物名带区分后缀；较新实现下产物不可变
构建没产出也不报错 下游拿到空目录继续跑，在更远处失败 上传时要求「找不到文件就报错」
产物丢文件权限 可执行脚本下来后不可执行 打成 tar 再传，或关掉压缩自己解
路径过滤卡住必需检查 PR 一直显示「等待中」，合并不了 合并必需的检查不加路径过滤
「完成后触发」当「成功后触发」 上游红了，下游照样跑 下游显式判断上游结论
表达式读默认环境变量 拿到空值，不报错 默认变量用运行器环境变量读
变量名撞平台前缀 赋值静默失效 换名字，保留前缀不能用
密钥拼进命令行 日志留痕，外部输入还能注入 走环境变量传给脚本
部署仓库被强制推送覆盖 网页上手工改的内容消失 挪进源码仓库，别在部署仓库手改
自定义域名配置放错位置 部署后域名配置丢了 放进源码目录一起生成
时区之类的无关步骤 步骤跑成功，但没有任何作用 删掉，流水线只留有用的步骤
脚本名对不上 报找不到命令 按项目里实际定义的脚本来调
自建镜像推送照抄 凭据策略未必还是原来那样 照抄前自己验一遍
远程复制式部署 报权限拒绝、主机不可信 补齐私钥、主机指纹、目录属主三件事

三条容易被忽略的 #

第一，滚动标签的风险是双向的。钉死版本解决了「下个月突然挂」，但带来了「镜像退役要跟进」。两个成本都要接受，只是选哪一个。

第二，被强制推送覆盖这件事，多数人是在丢了数据之后才知道。部署动作如果用了强制推送，部署目标仓库里的任何手工修改都会被下一次部署冲掉。解决办法不是记住别手改，是把要保留的东西挪进源码。

第三，也是最重要的一条：所有「配置已经写好」的东西都会过期。第三方动作的主版本号会往前走，平台会停用旧接口，镜像会退役。这份表里的每一条都值得在照抄之前去对应的地方看一眼现状。

最后一句 #

流水线是给人用的工具，判据只有一条：它有没有让问题更早被发现。

一条三分钟的流水线，只要红灯可信、结论可靠，价值就大于一条全自动但没人看的流水线。反过来，一条跑四十分钟、测试还偶尔挂的流水线，不管里面塞了多少阶段，反馈回路已经断了。

先让回路转起来，再让它变快。
