CI 和 CD：从一次 push 到自动上线 #

把 .github/workflows/ci.yml 推进仓库，之后每次 push，GitHub 都会开一台临时虚拟机，拉代码、装依赖、跑测试，失败就在那个 commit 上标红。这条链就是 CI。它跟 CD 的区别只在最后一步：构建出来的东西，是等人点一下才上线，还是自己就上线了。

我把原来的三份笔记拼成一篇，顺手按 2026-11 的官方文档核了一遍。旧稿里 ubuntu-18.04、::set-output、upload-artifact@v2、checkout@v3 这些写法，现在要么跑不通，要么早该换了。下面把能直接用的部分留下，把过期的地方标出来。

分界线在最后那道门 #

一次 push 之后发生的事是有固定顺序的：仓库发出事件，GitHub 拿 on 去匹配所有 workflow 文件，命中就建一次 run；每个 job 分到一台全新 runner，按 steps 顺序执行；某一步退出码不是 0，这个 job 标失败，后面的 step 不再跑；needs 依赖它的 job 全部跳过。

text
push ──> 事件 ──> 匹配 .github/workflows/*.yml ──> 一次 workflow run
                                                   │
                          ┌────────────────────────┴──────────────────────┐
                          │ job: build (ubuntu-latest)                    │
                          │  checkout → setup-node → npm ci → npm test    │
                          │  任一步失败：job 红，后续 step 不执行           │
                          └────────────────────────┬──────────────────────┘
                                                   │ needs: build
                                                   v
                                          job: deploy  (build 失败就整条跳过)

CI（持续集成）负责把代码验到「产物可信」；Continuous Delivery（持续交付）把产物备到「随时能发」，最后那下由人确认；Continuous Deployment（持续部署）连这下也自动了。别背定义，看 workflow 里有没有那道门就行：挂了 environment: production 并配了审批人，是 Delivery；needs: build 后面直接跟部署命令，是 Deployment。

这里有个旧稿没说透的坑：不少仓库挂着 CI/CD 的名字，实际只有 CI 加一个部署脚本。部署 job 没写 needs: build，两个 job 并行跑，测试红了站点照样更新。加一行 needs 才算把链串起来。

工具怎么选，给结论：公开仓库直接用 GitHub Actions，标准 runner 免费且不限量，不用自己养机器；私有仓库按分钟计费。Jenkins 插件多，但要自己维护 runner 和插件升级，团队里没有专人盯就别碰。Argo CD 只在 Kubernetes 那套部署形态里值，静态站点用它纯属自找麻烦。GitLab CI、CircleCI 适合代码本来就在对应平台的仓库，没必要为了 CI 搬家。

一份能跑的最小配置 #

四个词先对齐：workflow 是一次运行的定义，job 是里面的一组任务，step 是任务里的一个步骤，action 是 step 调用的现成动作。文件必须放在 .github/workflows，后缀 .yml 或 .yaml，一个仓库可以放多个。

yaml
name: CI

on:
  push:
    branches: [main]
    paths-ignore:
      - 'docs/**'
  pull_request:

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 22
          package-manager-cache: false
      - run: npm ci
      - run: npm test

逐条说容易写错的地方。

on 定触发事件。paths-ignore 只写在 push 下，让只改文档的 push 不跑构建。官方文档专门提醒过一件事：被分支或路径过滤跳过的 workflow，关联的 check 会一直停在 Pending，配了 required checks 的 PR 就卡住合并不了。所以 PR 必需的那些检查别加路径过滤，pull_request 这里保持全量触发。

runs-on 必填，写 runner 标签。当前官方表里 Linux 是 ubuntu-latest、ubuntu-24.04、ubuntu-22.04、ubuntu-26.04，另有 windows-latest、macos-latest 和 ARM 标签。旧稿列的那张表里 ubuntu-18.04 还在，这个镜像 2023 年 4 月就彻底不支持了；ubuntu-20.04 也不在当前标签表里。照抄会直接报找不到 runner。

permissions 收窄 GITHUB_TOKEN 的权限，actions/checkout 的 README 推荐 contents: read。不写这行，token 拿的是仓库默认权限，部署类 workflow 里风险更大。

npm ci 替换了旧稿的 npm install：它按 lockfile 装，版本可复现，代价是仓库里必须有 package-lock.json，没有就当场报错。npm test 同理，package.json 里没定义 test script 也会失败。package-manager-cache: false 是 setup-node v6 之后才要关心的：v6 起看到 packageManager 字段就自动开 npm 缓存。这份示例只跑一次测试，不值得引入缓存状态；真要提速就显式写 cache: 'npm'。

旧稿那份部署示例写的是 npm build。构建脚本名得按 package.json 里 scripts 的实际名字来，比如 npm run build；Hexo 那节我们直接用 npx hexo generate，不依赖自定义 script。

触发条件换几种写法，字段都是官方的：

yaml
on:
  push:
    tags: ['v*']
  release:
    types: [published]
  schedule:
    - cron: '30 5 * * 1-5'
  workflow_dispatch:

workflow_dispatch 让 Actions 页面出现手动运行按钮；schedule 用 POSIX cron，默认 UTC，最短间隔 5 分钟。别把全量构建挂到 5 分钟一次上，私有仓库的分钟数烧得很快。

多 job、传值、跨 workflow #

needs 管依赖。默认并行，写了 needs: [job1, job2] 就等这两个都成功；上游失败或跳过，下游一起跳过，除非给下游加 if: ${{ always() }}。

job 之间传值走 outputs，写法在 2022 年变过一次：

yaml
jobs:
  prepare:
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.ver.outputs.version }}
    steps:
      - id: ver
        run: echo "version=${GITHUB_REF#refs/tags/v}" >> "$GITHUB_OUTPUT"
  deploy:
    needs: prepare
    runs-on: ubuntu-latest
    steps:
      - env:
          VERSION: ${{ needs.prepare.outputs.version }}
        run: echo "deploy $VERSION"

旧稿里的 echo "::set-output name=test::hello" 别再抄。GitHub 在 2022-10-11 的 changelog 里宣布废弃 set-output 和 save-state，2023-07-24 又更新说因为用量太大推迟移除；官方 workflow 语法文档现在的示例一律写 $GITHUB_OUTPUT。同理，跨 step 传环境变量写 $GITHUB_ENV。

产物共享用 artifact，注意上传和下载两个 action 的主版本并不同步：

yaml
      - uses: actions/upload-artifact@v7
        with:
          name: dist
          path: dist/
          if-no-files-found: error
      # 另一个 job 里
      - uses: actions/download-artifact@v8
        with:
          name: dist

if-no-files-found: error 是故意的：构建没生成 dist/ 时不报错，部署 job 会拿一个空目录继续跑，排查起来更费劲。旧稿的 upload-artifact@v2 / download-artifact@v2 在 2024-06-30 停用，v3 在 2024-11-30 停用。v4 之后 artifact 不可变，多个 job 往同名写会失败，matrix 里要带上后缀，比如 name: dist-${{ matrix.os }}。

一条 workflow 跑完触发另一条，旧稿用 repository_dispatch：CI 里调 github.rest.repos.createDispatchEvent 发一个自定义 event_type，接收方写 on.repository_dispatch.types。少写代码的办法是 workflow_run：

yaml
on:
  workflow_run:
    workflows: ["CI"]
    types: [completed]

jobs:
  deploy:
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
    runs-on: ubuntu-latest
    steps:
      - run: echo "CI 过了，开始部署"

那个 if 不能省，completed 只表示跑完了，不表示成功。

变量和 secrets 放哪 #

env 可以写在 workflow、job、step 三层，越靠里优先级越高。读运行信息有两套写法：${{ github.ref }} 是上下文表达式，在 YAML 交给 runner 之前就求值；$GITHUB_REF 是 runner 上的环境变量。官方 Variables reference 明确写了，默认环境变量不进 env 上下文，所以 ${{ env.GITHUB_REF }} 取不到东西。

自定义变量名不能以 GITHUB_ 开头。旧稿说这样「会导致错误」，按现在的文档更准确的说法是：覆盖 GITHUB_* 和 RUNNER_* 这些默认变量的赋值会被直接忽略，配置变量名也不许用这个前缀。查半天发现变量没生效，多半是撞了这个。常用的默认变量就那几个：GITHUB_REF、GITHUB_SHA、GITHUB_WORKSPACE、GITHUB_OUTPUT、GITHUB_ENV、CI（恒为 true）。旧稿那张二十行的表格不用背，完整表在官方 Variables reference。

密钥写在仓库 Settings → Secrets and variables → Actions → New repository secret，用 ${{ secrets.HEXO_DEPLOY_PRI }} 取。别把值直接拼进 run 命令：日志会留痕，pull_request 里拼进来的字符串还有注入风险，用 env 传给脚本更安全。fork 提的 PR 默认拿不到 secrets，这是设计如此，别当成配置漏了。

实战：把 Hexo 推上 GitHub Pages #

旧稿记了个很实在的动机：本地 Node.js 升到 v14 后跟 Hexo 不兼容，部署不了；文章一多，hexo generate --deploy 还得等很久。把构建搬进 runner，本地只管 push，机器版本就跟自己电脑脱钩了。

前提有五项，少一项都跑不通：

  1. 两个仓库：放 Hexo 源码的 blog，放静态页面的 <username>.github.io。

  2. 本地跑 ssh-keygen -f github-deploy-key 生成一对密钥。私钥内容存进 blog 仓库的 secret HEXO_DEPLOY_PRI；公钥加到静态站点仓库的 Settings → Deploy keys，勾上 Allow write access。

  3. 装部署插件 npm install hexo-deployer-git --save，并在 _config.yml 里写 deploy 段。旧稿漏了这一步，直接跑 npm run deploy 会什么也推不出去：

    yaml
    deploy:
  type: git
  repo: git@github.com:<username>/<username>.github.io.git
  branch: master

    配了 SSH 密钥就用 git@github.com: 开头的地址，插件 README 说写 HTTPS 会要密码或被拒。

  4. 仓库里有 package-lock.json，hexo 和 hexo-cli 都在 devDependencies 里，npm ci 和 npx hexo 才跑得动。

  5. 把主题配置另存为 blog 根目录的 _config.theme.yml。主题目录是单独 checkout 出来的，配置不能预置在里面；下面的 workflow 会把它拷回主题目录。

完整的 .github/workflows/deploy.yml：

yaml
name: Deploy Hexo

on:
  push:
    branches: [master]

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      GIT_USER: github-actions[bot]
      GIT_EMAIL: 41898282+github-actions[bot]@users.noreply.github.com
      THEME_REPO: <owner>/<theme-repo>
      THEME_BRANCH: master
      DEPLOY_REPO: <username>/<username>.github.io
      DEPLOY_BRANCH: master
    steps:
      - uses: actions/checkout@v7
        with:
          # 部署走 SSH 私钥，不需要 checkout 写进 .git/config 的 token
          persist-credentials: false

      - name: 拉主题
        uses: actions/checkout@v7
        with:
          repository: ${{ env.THEME_REPO }}
          ref: ${{ env.THEME_BRANCH }}
          path: themes/concise

      - name: 保留部署仓库的提交历史
        uses: actions/checkout@v7
        with:
          repository: ${{ env.DEPLOY_REPO }}
          ref: ${{ env.DEPLOY_BRANCH }}
          path: .deploy_git

      - uses: actions/setup-node@v7
        with:
          node-version: 22
          package-manager-cache: false

      - name: 装 SSH 私钥
        env:
          HEXO_DEPLOY_PRI: ${{ secrets.HEXO_DEPLOY_PRI }}
        run: |
          mkdir -p ~/.ssh
          echo "$HEXO_DEPLOY_PRI" > ~/.ssh/id_rsa
          chmod 600 ~/.ssh/id_rsa
          ssh-keyscan github.com >> ~/.ssh/known_hosts
          git config --global user.name "$GIT_USER"
          git config --global user.email "$GIT_EMAIL"
          cp _config.theme.yml themes/concise/_config.yml

      - run: npm ci
      - run: npx hexo generate --deploy

几处注释解释为什么这么写。主题和静态站点仓库是单独 checkout 的，主题配置不能塞进主题目录，所以单独留一份 _config.theme.yml 再拷过去；主题若是 submodule，把第二次 checkout 换成主仓库那步的 with: submodules: recursive 就行。hexo-deployer-git 在 .deploy_git 里生成页面再 push，目录不存在就自己 git init，提前 clone 一次是为了不丢提交历史。chmod 600 不能省，权限太松 SSH 直接拒收私钥。旧稿里还有一行 sudo timedatectl set-timezone，改时区对部署没有任何作用，删了。

主题仓库和部署仓库如果是私有的，得给 checkout 传 token: ${{ secrets.GH_PAT }}。GITHUB_TOKEN 的作用域只有当前仓库，拉不动别的私有库。

npm run deploy 是旧稿里的 script 名，仓库里没定义就直接调 npx hexo generate --deploy，前提是 hexo-cli 和 hexo-deployer-git 都在 package.json 里。

不想维护部署密钥和双仓库，还有条更短的路：只生成，然后交给第三方 action 发到 gh-pages 分支。把上面的部署步骤换成下面两步，并把 job 权限改成 contents: write：

yaml
      - run: npx hexo generate
      - uses: peaceiris/actions-gh-pages@v4
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./public
          publish_branch: gh-pages

这条路有两个 README 里写明的卡点：第一次用 GITHUB_TOKEN 部署会撞上 403（Write access to repository not granted），除了加 permissions: contents: write，还得去仓库设置里手动选一次 Pages 分支，再跑一遍才过；GITHUB_TOKEN 推不到别的仓库，跨仓库发布要换成 deploy_key 或 personal_token。

验证方式很直接：写篇文章 push 到 master，去 Actions 页看这次 run，绿了之后打开 https://<username>.github.io。

上面这份是 Continuous Deployment，push 完没人拦。想改成 Delivery，把部署单独拆成第二个 job 并挂上环境：

yaml
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production

在 Settings → Environments → production 里配 required reviewers，job 会停在那等人点。官方 workflow 语法文档写得很清楚，环境上的保护规则全部通过之后，引用这个环境的 job 才会被派发给 runner。

旧稿里的片段，哪些还能用 #

取版本号配 tag 触发，旧稿这段还能用，写成完整的一份是这样。第二个 step 直接读 $CURRENT_VERSION，说明 $GITHUB_ENV 写进去的变量在后续 step 里生效：

yaml
name: Show version

on:
  push:
    tags: ['v*']

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - run: echo "CURRENT_VERSION=${GITHUB_REF#refs/tags/v}" >> "$GITHUB_ENV"
      - run: echo "$CURRENT_VERSION"

按 commit message 跳过：if: "!contains(github.event.head_commit.message, 'skip ci')"。外层双引号不是多余，官方 if 文档说表达式以 ! 开头时必须写成 ${{ }} 或加引号，! 在 YAML 里是保留符号。

测多个 Node 版本用 matrix，setup-node 官方示例给的是 [20, 22, 24]：

yaml
    strategy:
      matrix:
        node: [20, 22, 24]
    steps:
      - uses: actions/setup-node@v7
        with:
          node-version: ${{ matrix.node }}
          package-manager-cache: false

发 npm 包时配 registry-url，NODE_AUTH_TOKEN 必须真的给值。setup-node v7 的 breaking change 里删掉了那个 dummy fallback，以前靠占位 token 混过去的旧 Yarn 和老 npm 会报错。

推 Docker 镜像、同步 Gitee、把生成的文件 commit 回 master，本质都是同一套：checkout → 配凭据 → 跑命令 → push。旧稿贴了十几段，这里不逐条搬。Gitee 镜像那段把 token 拼进 remote URL，我没跑过现在 Gitee 的凭据策略，照抄前自己验一遍。

会翻车的地方 #

ubuntu-latest 是滚动标签，runner 镜像里的预装软件每周更新。今天能构建，下个月镜像换掉某个系统库就挂。要可复现就钉死 ubuntu-24.04，代价是以后得自己跟进镜像退役。

@v7 也是可变 tag。peaceiris 的 README 说得很直白：major tag 里不会有 breaking change，但推荐钉到具体版本 tag 或完整 commit SHA，因为分支和 tag 能被上游改动。第三方 action 尤其值得这么做。

hexo-deployer-git 用的是 git push --force。在 <username>.github.io 仓库网页上手工改过的东西，下次部署会被整个覆盖；自定义域名的 CNAME 不放进 source/ 也会在部署时丢掉，这两条是插件 README 专门列出来的。

artifact 打包成 zip 会丢文件权限，下载后目录是 755、文件是 644，chmod +x 过的脚本不再是可执行文件。要保权限就先 tar 成一个文件，上传时带 archive: false，下载后自己解开。

旧稿那份自动部署示例最后一行是 scp -r ./dist user@your-server:/var/www/html，这份配置跑不通。临时 runner 上没有目标服务器的 SSH 私钥，也没有 known_hosts，目标目录的写权限更没配。要补齐：私钥存 secret、ssh-keyscan 写 known_hosts、服务器上的目录属主，跟上面 Hexo 那步是同一套活。

actions/checkout@v7 还有个默认行为变了：在 pull_request_target 或 workflow_run 触发的 workflow 里，它默认拒绝检出 fork PR 的代码，要显式开 allow-unsafe-pr-checkout: true。别为了让它跑通就随手打开，这两个触发器带着基础仓库的 token 和 secrets。

这篇不讲自建 runner、Kubernetes + Argo CD、蓝绿与金丝雀、自动回滚和监控接入。旧稿把这些名词列了一遍，展开都要单独一篇。

从哪儿开始 #

  1. 把「一份能跑的最小配置」存成 .github/workflows/ci.yml，push 一次，去 Actions 页确认四个 step 全绿。
  2. 加第二个 deploy job，写 needs: build，把部署凭据放进 secrets。先部署到测试分支或测试仓库。
  3. 决定要不要人工确认。要，就挂 environment: production 配审批人；不要，就把 environment 去掉，让 push 直接上线。

核对过的来源（2026-11）：GitHub Docs 的 Workflow syntax、Variables reference、GitHub-hosted runners；GitHub Changelog 2022-10-11 关于 set-output 废弃的公告；actions/checkout、actions/setup-node、actions/upload-artifact、actions/download-artifact 的仓库 README；peaceiris/actions-gh-pages 与 hexojs/hexo-deployer-git 的 README。这些主版本号还会往前走，隔一阵子照抄之前去对应仓库看一眼 tag。
