本篇讲 QEMU 命令行虚拟化与系统仿真：虚拟机怎么起、磁盘怎么造、加速怎么开、和 KVM 到底是什么关系。

不讲什么：不展开桌面图形化虚拟机的安装向导与排障，那属于同目录《VMware：日常使用与常见故障》；不展开 WSL 的发行版安装与图形界面，那属于同目录《WSL：安装、图形界面与外设》。

怎么选：要在笔记本上装一个日常工作用的系统、点几下就完事，看 VMware 那篇。要在服务器上没有图形界面的前提下批量起机器，要用命令行脚本编排、要跑 ARM 或 RISC-V 这种异地架构、要通过串口盯内核启动日志，看这篇。

一、QEMU 是什么 #

QEMU 全名 Quick EMUlator。2003 年由 Fabrice Bellard 发起，开源、跨平台。

它干的事可以一句话说完：在用户态把一台机器的硬件模拟出来。CPU、内存、磁盘控制器、网卡、串口、显示设备，全都由 QEMU 这个普通进程当作数据来生成和处理。虚拟机里跑的操作系统看到的是一套完整硬件，宿主机的物理硬件长什么样，跟它没关系。

核心价值就在这：软件模拟一切硬件。你有多少台机器、什么架构的 CPU、插了什么卡，QEMU 都能在进程里现造一套。代价是仿真模式下每条指令都要翻译一遍，慢得能让你重新理解「一秒」有多长，所以同架构时要开 KVM 把 CPU 执行这条路交还给硬件。

一句话对照：VMware 让你在图形界面里跑一个同架构的系统，QEMU 让你在命令行里造一台任意架构的机器。

QEMU 有两个可执行程序家族，别搞混：

程序名 干什么 典型命令
qemu-system-* 模拟一整台机器，启动操作系统 qemu-system-x86_64、qemu-system-arm
qemu-user-* 只模拟一个进程，直接跑异地架构的单文件 qemu-arm、qemu-riscv64
qemu-img 造盘、改盘、转换格式、看信息 qemu-img create
qemu-nbd 把镜像挂成块设备给宿主机用 qemu-nbd -c /dev/nbd0 disk.qcow2

系统模式对应 -system，用户模式对应 -user，这是两套东西。玩嵌入式、调内核、做跨架构兼容测试，用的是系统模式；在 x86 主机上直接跑一个 ARM 的编译产物、不用起整机，用的是用户模式。

素材里的特性清单 #

多架构支持。x86、ARM、PowerPC、MIPS、RISC-V 都能跑，同一台宿主机上换一个可执行文件就换一种架构。要给一堆平台测兼容性，这比凑齐一堆真机省事得多。

与 KVM 结合。KVM 提供硬件虚拟化的执行通道，QEMU 提供设备模型，两者拼起来，同架构虚拟机的速度能贴近原生。

用户空间仿真。qemu-arm ./program 这种用法不起整机，直接在宿主机上把单个程序跑起来，软件测试和调试大型项目时省掉一层编排。

应用场景。嵌入式开发、操作系统测试、系统镜像调试是主战场。模拟一套硬件环境，在主机上验证嵌入式系统或新内核。开源，源码透明，可以按需要改。

二、虚拟化与仿真两副面孔 #

QEMU 装完之后你会看到一堆可执行文件，它们其实分属两条路线。这两条路线的分界，是虚拟机里的指令和宿主机的指令是不是同一套。

路线一：仿真 #

qemu-system-arm 在 x86 服务器上启动 ARM 内核，走的就是仿真。QEMU 取一条客户机指令，翻译成宿主机能执行的指令，执行，再取下一条。CPU 是「翻译出来」的，不是「借过来」的，所以客户机架构和宿主机架构没有任何关系。

代价很直接：指令要逐条翻译，还要维护一套指令集状态的映射，速度比原生慢几个数量级。用来跑一个完整桌面系统不现实，用来验证内核启动流程、跑驱动、跑单测，完全够用。好处也很直接：你不需要那块板子。交叉编译出来的内核有 bug，先在 QEMU 里把启动流程走一遍，比烧写到板子上再看串口快得多。

路线二：虚拟化 #

宿主机和客户机架构相同的时候，CPU 执行这条路可以交给硬件，QEMU 只负责那些硬件不虚拟的设备。加一个 -enable-kvm，客户机代码就在真实 CPU 上跑特权级切换，速度接近原生。此时 QEMU 的角色从「CPU 模拟器」退成「设备模拟器 + 控制器」。

一张表分清 #

维度 仿真 虚拟化（KVM）
代表程序 qemu-system-arm、qemu-system-riscv64 qemu-system-x86_64 -enable-kvm
客户机架构 任意，可以和宿主机不同 必须和宿主机一致
指令怎么执行 逐条翻译后执行 交给 CPU 直接执行
速度 慢，跨架构时差几个数量级 接近原生
靠什么 QEMU 自己的软件实现 VT-x / AMD-V 硬件虚拟化
典型用途 嵌入式驱动验证、跨架构兼容测试、内核调试 服务器上跑生产虚拟机、批量测试环境

两条路线不冲突。同一台宿主机上，x86 的虚拟机开 KVM，ARM 的虚拟机走仿真，各跑各的。

用户模式：不起整机的第三种用法 #

系统模式之外还有用户模式，只模拟一个进程，连内核都不用起：

bash
qemu-arm -L /usr/arm-linux-gnueabihf ./hello
qemu-arm -L /usr/arm-linux-gnueabihf -g 1234 ./app

-L 指定交叉环境里的动态库位置，否则加载器找不到 ld-linux。想在 x86 上快速验证一个 ARM 可执行文件能不能跑通，这比在 QEMU 里装一个完整系统快得多。-g 1234 在 1234 端口等 gdb 连过来，宿主机上用交叉工具链的 gdb 去 target remote。

三、QEMU 与 KVM 的关系 #

这两个名字经常被连着说，其实是两层东西。

KVM 是 Linux 内核里的一个模块。它把 CPU 的硬件虚拟化能力（Intel VT-x、AMD-V）包装成一组内核接口，自身不做设备模拟，也不管你从哪启动、磁盘是什么格式。加载之后多出 /dev/kvm 这个字符设备。

QEMU 是一个用户态程序。它负责造主板、造网卡、造磁盘控制器、造串口，负责加载引导扇区、处理 I/O 端口访问，负责那些硬件不替你干的事。

两者接上的方式：QEMU 打开 /dev/kvm，通过一组 ioctl 调用 KVM。客户机的 vCPU 线程创建、寄存器读写、内存区域映射、每次退出（exit）的原因和处置，全走这套接口。

一句话概括：设备模拟器 + 硬件加速器。

分成三层看更清楚：

text
客户机操作系统（以为自己在一台真机上）
        |
   QEMU 用户态进程  —— 模拟磁盘、网卡、串口、显示
        |  ioctl
   /dev/kvm —— 内核模块 KVM —— VT-x / AMD-V
        |
   物理 CPU

这个分层解释了为什么 -enable-kvm 只是「一个开关」。QEMU 本身就有完整的纯软件实现，KVM 只是把其中「执行客户机指令」这一段换成了硬件通道，其余部分照旧由 QEMU 完成。

它还解释了另一个现象：KVM 只对同架构有意义。ARM 指令没法交给 x86 的 VT-x 去执行，所以 ARM 虚拟机开 -enable-kvm 会直接报错退出。

libvirt 又是什么 #

再往外还有一层管理层。libvirtd 加 virsh、virt-manager 负责虚拟机定义、生命周期、存储池、网络定义，最后落实到启动一个 QEMU 进程。

层 组件 职责
管理层 libvirt、virsh、virt-manager 生命周期、存储池、网络定义
用户态模拟 QEMU 设备模型、引导、I/O
内核加速 KVM 指令执行、内存虚拟化

用 virsh 起一台机器，ps 里能看到一个 qemu-system-x86_64 进程，参数一长串，就是这套关系的实证。

四、安装与依赖 #

Linux #

bash
sudo apt update
sudo apt install qemu qemu-system qemu-user-static
sudo yum install qemu-kvm qemu-img
sudo dnf install @virtualization

qemu 是元包，qemu-system 带各种架构的系统模拟器，qemu-user-static 是静态链接的用户模式模拟器，最后这个在容器里做跨架构构建时经常要用，因为它不依赖宿主机库。要图形化管理再装 virt-manager，要命令行管理装 libvirt-daemon-system libvirt-clients。

qemu-kvm qemu-img 装的就是带 KVM 支持的 QEMU，较新发行版把 yum 换成 dnf，包名一致。Fedora 的 @virtualization 是组包，把 QEMU、libvirt、virt-manager 一起带上。

Windows 与 macOS #

bash
brew install qemu

Windows 到 QEMU 官方页面 https://www.qemu.org 下载安装包，勾选把安装目录加入 PATH，否则每次都要敲完整路径。Windows 版没有 KVM，硬件加速走 WHPX（Windows Hypervisor Platform），装了 Hyper-V 或 WSL2 的机器可以启用。跨架构仿真照样能用，qemu-system-arm.exe 一样在。

macOS 用上面的 brew 命令安装，加速依赖 Hypervisor.framework，命令里用 -accel hvf。命令行的组织方式和 Linux 一样。

依赖与权限 #

安装完还要处理两件事，否则 -enable-kvm 用不了：把当前用户加进 kvm 组，确认 /dev/kvm 的设备节点存在。

bash
groups
sudo usermod -aG kvm $USER
newgrp kvm
ls -l /dev/kvm
sudo apt install cpu-checker
kvm-ok

改完必须重新登录才生效，newgrp kvm 只能在当前 shell 里临时生效。ls -l /dev/kvm 报 No such file or directory，说明 KVM 模块没加载或者硬件不支持，不是权限问题，加组没用。kvm-ok 输出 KVM acceleration can be used 就是就绪；输出里带 KVM will not be enabled 时会同时说明原因，比如 VT-x 在 BIOS 里被禁用。

验证安装 #

bash
qemu-system-x86_64 --version
qemu-img --version
qemu-system-x86_64 -accel help
qemu-system-x86_64 -M help

第三条列出当前构建支持的加速后端，常见的有 kvm、tcg、hvf、whpx。列表里没有 kvm 说明这个 QEMU 构建没编进 KVM 支持。第四条列出支持的主板型号，换成 -device help 就是列出可热插的设备，排查「参数写了但报 unknown device」时很有用。

一个可用的启动脚本 #

把常用参数固化成脚本，比每次敲一长串可靠。放到 ~/bin/startvm.sh：

bash
#!/usr/bin/env bash
set -euo pipefail

NAME="${1:?usage: startvm.sh <name>}"
DIR="$HOME/vms/$NAME"
DISK="$DIR/disk.qcow2"

if [ ! -f "$DISK" ]; then
  qemu-img create -f qcow2 "$DISK" 20G
fi

exec qemu-system-x86_64 \
  -enable-kvm -machine q35 -cpu host -smp 2 -m 2G \
  -drive file="$DISK",format=qcow2,if=virtio \
  -netdev user,id=net0 -device virtio-net-pci,netdev=net0 \
  -display none -serial mon:stdio

set -euo pipefail 让脚本在任一步出错时停下，避免带着半截状态继续。exec 用 QEMU 进程替换 shell，Ctrl-C 直接发给 QEMU 而不是外层。按名字给不同的机器建目录，磁盘和配置各归各的，比把所有镜像堆在一个目录里好管。

五、一条完整的启动命令 #

下面这条命令启动一台 x86_64 虚拟机，开硬件加速、给 2G 内存和两个 CPU、挂一块 qcow2 磁盘、插一张 ISO、配一块能上网的网卡，控制台接管到当前终端：

bash
qemu-system-x86_64 \
  -enable-kvm -m 2G -smp 2 \
  -drive file=disk.qcow2,format=qcow2 \
  -cdrom ubuntu.iso \
  -netdev user,id=net0 -device e1000,netdev=net0 \
  -nographic

反斜杠是换行续行，写成一行完全等价，只是为了看清参数分组。

这条命令跑起来会发生这些事：QEMU 进程启动，打开 /dev/kvm，向内核申请一块内存建立客户机物理地址空间，创建 vCPU 线程，从 BIOS/UEFI 固件开始执行，固件读到第一个可引导设备。这里是 -cdrom 指定的 ISO，于是引导安装器。你看到的输出通过 -nographic 落到终端里。

素材里最简单的版本是 qemu-system-x86_64 -boot d -cdrom /path/to/your.iso -m 1024。区别只在取舍，-boot d 显式指定从光盘启动，-m 1024 是 1024 MiB 内存。没有任何磁盘，所以装了东西也留不下。

把参数按作用分组，记起来容易得多：

组 参数 作用
加速 -enable-kvm、-accel 决定客户机指令怎么执行
资源 -m、-smp、-cpu、-machine 内存、CPU 数量、CPU 型号、主板
存储 -drive、-cdrom、-hda、-blockdev 磁盘与光盘
网络 -netdev、-device、-nic 后端与网卡型号
显示 -nographic、-display、-vnc 输出到哪里
生命周期 -boot、-snapshot、-daemonize 引导顺序、临时运行、后台运行
调试 -serial、-monitor、-d、-s -S 串口、监视器、日志、gdb 挂起

第一次用建议逐组加上去。先只给资源参数看能不能进固件界面，再加磁盘，再加网络。出问题的时候分组排查比对着一条长命令猜快。

参数是「后写覆盖前写」的语义，同一个 -m 出现两次后面那个生效，写脚本拼参数时要注意顺序。长短写也通用，-m 和 -memory 是一回事，-cdrom 等价于 -drive media=cdrom，选一种风格保持到底。

六、参数逐个解释 #

-enable-kvm #

打开 KVM 硬件加速，客户机的指令交给真实 CPU 执行，而不是由 QEMU 逐条翻译。这一项到位与否，速度是数量级的差距。

它的前提就是前面那三条：CPU 支持、模块加载、/dev/kvm 可访问。三条不满足，QEMU 会在启动时直接报错退出，不会悄悄降级成软件模拟。

对应的替代写法是 -accel kvm，或者 -machine accel=kvm。想让它「能开就开、开不了就退回软件模拟」，用 -accel kvm:tcg，冒号后面是候选顺序。

交叉架构的机器上不要加这个参数。ARM 客户机配 -enable-kvm 会报 KVM does not support this CPU 一类错误。

-m 2G #

给客户机分配的内存大小。2G 是 2 GiB，也可以写 2048（单位 MiB）或 2048M。这块内存由 QEMU 进程从宿主机要来，宿主机内存不够时把虚拟机内存调小比调 swap 更实际，因为客户机内存被换出会让它卡到没法用。不带 -m 时默认值偏小，跑现代发行版不够用，2G 是稳妥的起点。

-smp 2 #

客户机的 CPU 数量为 2。-smp 4 就是 4 个 vCPU。vCPU 是宿主机的线程，客户机 CPU 数不该超过宿主机物理核心数太多，4 核超线程的宿主机配 -smp 4，线程互相抢占反而更慢。要指定拓扑结构可以用 -smp 2,sockets=1,cores=2,threads=1。

-drive file=disk.qcow2,format=qcow2 #

挂一块磁盘。file= 指定镜像文件，format=qcow2 指定格式。format 建议永远显式写出来，不写的话 QEMU 会去探测文件头，一个被改过后缀名或内容异常的镜像会被误判，导致写坏。写明确是零成本的保险。

-drive 还有几个常用子选项：

子选项 含义 常用值
if= 接口类型 virtio、ide、scsi、none
media= 介质类型 disk、cdrom
readonly=on 只读挂载 写保护，适合挂种子镜像
cache= 缓存策略 none、writeback、writethrough
snapshot=on 本次运行不落盘 临时试东西时用

if=virtio 走虚拟化专用接口，比模拟 IDE 快，但客户机里要有 virtio 驱动，装 Windows 客户机时这一步最容易卡住，需要额外挂一个 virtio 驱动 ISO。新写法是 -blockdev 加 -device，把后端和前端彻底分开，支持的东西更多，日常用 -drive 就够。-hda mydisk.qcow2 是 -drive 的老式简写，等价于挂成第一个 IDE 硬盘。

-cdrom ubuntu.iso #

挂一个 ISO 到光驱，等价于 -drive file=ubuntu.iso,media=cdrom,readonly=on。配 -boot d 才是从光盘启动。

-netdev user,id=net0 #

创建一个网络后端，类型是 user，也就是用户模式网络。id=net0 是这个后端的标识符，后面 -device 要用它来接线。

用户模式网络是 QEMU 自己实现的一个小栈：客户机发出的包由 QEMU 进程代为转发、做 NAT、发到宿主机网络。客户机被分到 10.0.2.0/24 这个网段，网关 10.0.2.2，DNS 10.0.2.3。它不需要宿主机做任何额外配置，代价是外部主动连不进来。

-device e1000,netdev=net0 #

创建一块虚拟网卡，型号 e1000，把它接到 net0 这个后端上。这条命令体现的是 QEMU 网络的两段式结构：后端（-netdev）负责包怎么出去，前端（-device）负责卡长什么样，两个 id 对上网络就通了。

e1000 是模拟 Intel 千兆网卡，兼容性好，几乎所有系统都自带驱动。追求性能可以换 virtio-net-pci，但同样需要客户机驱动。

型号 场景
e1000 通用，兼容优先，Windows 和 Linux 都有驱动
virtio-net-pci 性能优先，配 if=virtio 一起用
rtl8139 老系统兼容，比如很旧的 Windows
vmxnet3 移植自 VMware 的虚拟网卡

不确定客户机有没有 virtio 驱动的时候，先用 e1000 跑通，再换成 virtio-net-pci。

-nographic #

完全关闭图形输出，把串口和控制台重定向到当前终端。具体做了三件事：关掉图形窗口，把客户机的串口映射到标准输入输出，把 QEMU 监视器也挂到标准输入输出上，用 Ctrl-A C 在两者之间切换。

这是服务器和嵌入式场景的默认选择，因为那些环境根本没有显示器。客户机内核要能在串口上输出，需要配 console=ttyS0 之类的内核参数，否则终端上是一片死寂。退出用 Ctrl-A X，直接关终端窗口会来不及让客户机正常落盘。

-nographic 不等于 -display none。前者连监视器一起重定向，后者只是不显示图形，串口还得靠 -serial 单独指定。

上面这些串起来就是一条能用的命令，-machine q35 选较新的主板模型，配合 -cpu host 把宿主机 CPU 特性透传给客户机；-serial mon:stdio 把串口接终端并把监视器复用上去，效果和 -nographic 接近但更显式。

bash
qemu-system-x86_64 -enable-kvm -machine q35 -cpu host \
  -m 2G -smp 2 \
  -drive file=disk.qcow2,format=qcow2,if=virtio \
  -cdrom ubuntu.iso -boot d \
  -netdev user,id=net0 -device virtio-net-pci,netdev=net0 \
  -display none -serial mon:stdio

七、磁盘镜像：raw 与 qcow2 #

虚拟机的硬盘是一个文件。QEMU 支持多种格式，日常要用明白的就是两种。

raw #

原始格式，把镜像当作一块裸块设备，字节按顺序摆着。优点是简单和快，读写不维护元数据结构，也没有分配表的开销。要追求磁盘 I/O 的极限，raw 是终点。

缺点是它不省空间。造一个 20G 的 raw 盘，宿主机上就多出 20G 的占用（稀疏文件在某些文件系统上可以延迟分配，但依赖文件系统和写模式，不能当保证）。功能也少，快照、压缩、加密都没有。

qcow2 #

QEMU Copy On Write 第 2 版，也是 QEMU 的默认格式。镜像里只存真正被写过的数据块，配套一张映射表记录每个客户机块落在文件里的哪个位置。没写过的块不占任何空间。

bash
qemu-img create -f qcow2 disk.qcow2 20G

-f qcow2 指定格式，disk.qcow2 是文件名，20G 是虚拟磁盘容量上限。

这条命令执行完，ls -lh 看到的文件大小只有几百 KB。20G 是客户机看到的最大容量，不是宿主机上占用的空间。上限不是占用，这是新手最容易误解的地方。往客户机里装系统、写日志、下载东西，文件才一点点长大，长到 20G 封顶。

一张表对比 #

维度 raw qcow2
空间占用 按容量算，造出来就大 按写入增长，初始几百 KB
镜像结构 裸块，无元数据 有分配表和元数据头
读写性能 略好 有轻微开销，日常感知不到
快照 不支持 支持内部快照
后备镜像 不支持 支持 backing file
压缩 不支持 支持 qemu-img convert -c
加密 不支持 支持 LUKS 加密
适合 追求极限 I/O、导入导出 日常开发、测试、批量实例

qcow2 不会自动缩小 #

写进去再删掉，文件不会变小。客户机里 rm 掉 5G 数据，disk.qcow2 还是那么大，因为 QEMU 只知道那些块被写过了，不知道客户机里已经不需要了。

要真正把空间收回来，得重建：

bash
qemu-img convert -O qcow2 disk.qcow2 disk-compact.qcow2

convert 读一遍源镜像，只把实际用到的块写进目标，出来是一个新的紧凑文件，确认无误后再替换掉原文件。

常用的 qemu-img 操作 #

bash
qemu-img info disk.qcow2
qemu-img resize disk.qcow2 +10G
qemu-img check disk.qcow2
qemu-img convert -f raw -O qcow2 disk.raw disk.qcow2
qemu-img create -f qcow2 -b base.qcow2 -F qcow2 overlay.qcow2

info 看虚拟容量、实际占用、格式、簇大小、后备文件，是排查「盘怎么满了」的第一步。resize 扩容，改的是虚拟磁盘容量，客户机里还要再操作一遍分区和文件系统才能真正用上，而且不能对着正在写的盘做。check 检查一致性，宿主机异常断电之后值得跑一次。convert 做格式互转，从云厂商下载的 raw 镜像转成 qcow2 能省下不少空间。-b base.qcow2 -F qcow2 基于基础镜像造一个后备链上的差分盘，基础镜像保持只读，每个实例只存自己的增量。

快照 #

bash
qemu-img snapshot -c snap1 disk.qcow2
qemu-img snapshot -l disk.qcow2
qemu-img snapshot -a snap1 disk.qcow2

创建、列表、回滚。这是 qcow2 的内部快照，回滚必须在关机状态做。运行中要做快照，走 QEMU 监视器里的 savevm snap1 和 loadvm snap1。或者在启动时加 -snapshot，所有写入进临时层，退出即丢弃，原始镜像一个字节都不变，试危险操作时先这么起。

从零造一个能用的盘 #

bash
qemu-img create -f qcow2 -o preallocation=metadata disk.qcow2 20G
qemu-system-x86_64 -enable-kvm -m 2G -smp 2 \
  -drive file=disk.qcow2,format=qcow2,if=virtio \
  -cdrom ubuntu.iso -boot d \
  -netdev user,id=net0 -device e1000,netdev=net0

preallocation=metadata 预先分配元数据，减少运行时的碎片，代价是创建时慢一点、占用大一点。默认的动态分配对多数场景够用。装完系统后，把 -cdrom 和 -boot d 去掉，就能从硬盘直接启动了。

八、网络四种模式 #

-netdev 的 type= 决定网络怎么跟外界打交道。四种模式，从简单到复杂排。

user（NAT） #

bash
-netdev user,id=net0 -device e1000,netdev=net0

QEMU 在进程内实现了一套用户态的 TCP/IP 栈。客户机的包被 QEMU 截住，转成宿主机上的系统调用发出去，回来的包再转回去。

客户机拿到的地址是固定的：10.0.2.15 是客户机，10.0.2.2 是网关（同时是宿主机的入口），10.0.2.3 是 DNS。客户机 ping 不到宿主机在局域网里的真实 IP。

这台机器的网络是单向的。客户机可以主动访问外部，外部不能访问客户机。想在宿主机上连客户机的 SSH，得先做端口转发：

bash
-netdev user,id=net0,hostfwd=tcp::2222-:22 -device e1000,netdev=net0

hostfwd=tcp::2222-:22 把宿主机 2222 端口的连接转到客户机的 22 端口，之后 ssh -p 2222 user@localhost 就能进去。老写法是 -redir tcp:2222::22。用户模式不需要 root，不需要配置宿主机网络，这是它作为默认选项的理由。

bridge（桥接） #

bash
sudo ip link add br0 type bridge
sudo ip link set br0 up
sudo ip link set eth0 master br0

客户机像宿主机局域网里的另一台独立机器，有自己从 DHCP 拿到的 IP，能被局域网内其他机器直接访问。配置在宿主机侧完成：建网桥，把物理网卡挂进去，再让 QEMU 用 tap 后端接到桥上。这一步要 root，配错了会把宿主机网络弄断，远程操作时留一条后路。

tap（自定义） #

bash
sudo ip tuntap add dev tap0 mode tap
sudo ip link set tap0 up
sudo ip addr add 192.168.100.1/24 dev tap0

tap 是宿主机的虚拟二层网卡，客户机的包直接进出这个设备。要做精细化网络控制就用它：自定义网段、加 iptables 规则、做流量整形、接到 Open vSwitch 上。配置繁琐，换来的是完全的控制权。

none #

bash
-nic none

不给网络，完全隔离。拿到不信任的镜像、分析可疑样本、做纯离线测试时，这个模式应该主动选。QEMU 不会因为你不写 -netdev 就完全不配网络，某些版本会带一个默认网卡。

模式 客户机能不能上网 外部能不能连进来 要不要 root 场景
user 可以 不能，要 hostfwd 转发 不用 默认、日常、装系统
bridge 可以 可以 要 局域网暴露服务
tap 看你怎么配 看你怎么配 要 精细控制、抓包
none 不能 不能 不用 隔离样本、离线测试

排查网络不通，与抓包 #

顺序固定，从下往上查。客户机里 ip addr，user 模式下应该是 10.0.2.15，没有地址说明网卡没被认出来或者 DHCP 没跑起来。客户机里 lspci 或 ip link 看不到设备，说明型号选错了，换 e1000 试。启动时打印 Warning: netdev net0 has no peer，说明 -device 里的 netdev=net0 和 -netdev 的 id=net0 拼写对不上，这是最容易犯的错。客户机解析失败但 IP 直连能通，查 DNS，用户模式里它固定是 10.0.2.3。

抓包这件事要提前想清楚。user 模式下流量在 QEMU 进程内部，宿主机上 tcpdump 抓不到；要抓就用 tap 或 bridge 模式，客户机流量会真正经过宿主机的网卡设备：

bash
sudo tcpdump -i tap0 -n -vv

用 user 模式开发网络程序，出问题时会比较被动。

九、开启硬件加速 #

-enable-kvm 是这条命令里最容易失败的一项。失败原因基本就三个，按从常见到不常见排。

原因一：当前用户不在 kvm 组 #

这是三者里最常见的那个。

bash
ls -l /dev/kvm
groups
sudo usermod -aG kvm $USER
newgrp kvm

看到 crw-rw---- 1 root kvm，说明只有属主 root 和属组 kvm 能读写。当前用户不在 kvm 组里，QEMU 打开设备失败，报 Could not access KVM kernel module: Permission denied。

加完必须重新登录。最容易出现的误判是：组加了、命令也执行成功了，但当前 shell 的组凭据还是旧的，于是以为加组没用。开一个新终端或者 newgrp kvm 再跑一次。

-aG 里的 a 不能省。写成 usermod -G kvm $USER 会把用户从其他所有附加组里踢出去，包括 sudo 组。

原因二：内核模块没加载 #

bash
lsmod | grep kvm
sudo modprobe kvm
sudo modprobe kvm_intel

没有输出说明 kvm 模块没在。Intel 平台用 kvm_intel，AMD 平台用 kvm_amd。加载失败时看 dmesg | tail，会说明原因。报 Operation not permitted 八成是虚拟机套虚拟机，宿主机的嵌套虚拟化没打开。要开机自动加载，写进 /etc/modules-load.d/kvm.conf，两行 kvm 和 kvm_intel。

原因三：CPU 不支持虚拟化 #

bash
grep -E -o 'vmx|svm' /proc/cpuinfo | sort -u

没有任何输出，说明 CPU 标志位里就没有虚拟化扩展，或者 BIOS/UEFI 里被关了。vmx 是 Intel，svm 是 AMD。

如果是被关的，重启进固件设置，Intel 平台找 Intel Virtualization Technology、VT-x，AMD 平台找 SVM Mode。有些品牌机把这些选项藏在 Advanced 或 Security 下面，或者要先设管理员密码才显示。改完保存重启，再跑一次 grep 确认标志位出现。

如果 CPU 确实不支持，或者固件里根本没这个选项，那就只能退回软件模拟：去掉 -enable-kvm，QEMU 用 TCG（Tiny Code Generator）自己翻译指令。功能不缩水，速度差很多。

一次查完，然后验证 #

bash
sudo apt install cpu-checker
kvm-ok
qemu-system-x86_64 -accel kvm ...

kvm-ok 输出 INFO: /dev/kvm exists 和 KVM acceleration can be used 就绪，不满足时它会指明是哪一条没过，把上面三步打包了。

继续用 -accel kvm 而不是 -enable-kvm 起机器，KVM 不可用时会直接报错退出，不会静默降级。想确认，就看 QEMU 监视器里的 info kvm，输出 kvm support: enabled 才是真的开了。客户机里 dmesg 出现 kvm-clock 相关的行，也是同一件事的旁证。

其他平台的加速后端 #

平台 参数 依赖
Linux -enable-kvm 或 -accel kvm KVM 内核模块、/dev/kvm
macOS -accel hvf Hypervisor.framework
Windows -accel whpx Windows Hypervisor Platform
任意 -accel tcg 无，纯软件，慢

-accel help 列出当前构建支持的全部后端，跨平台脚本里先查一次再决定用哪个比较稳。

关掉加速的场合 #

有些时候要主动走 TCG。调内核启动、复现时序相关的 bug、验证客户机在不同 CPU 特性下的行为，可复现性比速度重要。TCG 的执行是确定的，KVM 会把宿主机 CPU 的微架构细节暴露给客户机，同一份镜像在不同机器上表现会不同。

bash
qemu-system-x86_64 -accel tcg,thread=multi -m 2G

thread=multi 让 TCG 用多线程翻译，比单线程快，代价是确定性下降。要严格复现就用单线程。

十、嵌入式仿真实战 #

前面九章讲的是「怎么起一台同架构的虚拟机」。这一章换一条路线：起一台根本不存在的 ARM 开发板。

素材里那句「不用买板子就能验证驱动」，落在命令上就是这么一条：

bash
qemu-system-arm -M vexpress-a9 \
  -kernel zImage \
  -dtb vexpress-v2p-ca9.dtb \
  -drive file=rootfs.ext4,format=raw,if=sd \
  -append "root=/dev/mmcblk0 console=ttyAMA0" \
  -nographic

一条条拆开。

qemu-system-arm 是 ARM 的系统模拟器。注意这里没有 -enable-kvm，也不该有：x86 宿主机上跑 ARM 客户机，只能走逐条翻译的仿真，加 KVM 参数会直接报错。

-M vexpress-a9 指定虚拟开发板型号。-M 是 -machine 的短写，它决定 QEMU 模拟哪一块板子：CPU 核数、内存布局、外设地址、中断控制器，全都跟着这个型号走。vexpress-a9 是 ARM 官方的 Versatile Express 开发板，双核 Cortex-A9，文档多、内核支持完整，拿来练手合适。

-kernel zImage 直接加载内核镜像，跳过引导加载程序。真板子上这一步由 U-Boot 做，QEMU 里可以直接给内核，省掉一层。

-dtb vexpress-v2p-ca9.dtb 提供设备树。ARM 平台没有 x86 那套 ACPI 自动枚举，硬件长什么样全靠这份二进制描述。vexpress-v2p-ca9.dtb 要和 -M vexpress-a9 配对上，名字对不上就会在启动早期卡住，串口上什么都看不到。

-drive file=rootfs.ext4,format=raw,if=sd 挂根文件系统。if=sd 让 QEMU 把它当作 SD 卡设备，所以内核里看到的块设备是 /dev/mmcblk0 而不是 /dev/sda。format=raw 是因为这个 rootfs 本身就是个 ext4 文件系统镜像，不是 qcow2。

-append 把内核命令行传进去。root= 告诉内核根文件系统在哪，console=ttyAMA0 让它把日志送到第一个串口。这两个参数少一个，你面对的都是一片安静的黑屏。

-nographic 把串口接到当前终端，见下一节。

-nographic 与串口 #

嵌入式开发板没有显示器，也没有键盘。你能看到的一切都来自串口，-nographic 就是把这个串口搬到你的终端上：不创建图形窗口，把客户机串口映射到标准输入输出，把 QEMU 监视器也挂上去，用 Ctrl-A C 在串口和监视器之间切换。

内核侧要配合。console=ttyAMA0 是 ARM 平台第一个 PL011 串口的名字，x86 上对应的是 ttyS0。写错名字，内核照样启动，但输出全丢在虚空里。退出方式是 Ctrl-A X，直接关终端窗口，客户机来不及把缓存刷到磁盘，下次起来是一个损坏的文件系统。

-nographic 和 -display none 不是一回事。前者连监视器一起重定向，后者只是不显示图形，串口还得靠 -serial 单独指定。下面这条和上面那条效果接近，写法更显式，也更容易再挂第二个串口：

bash
qemu-system-arm -M vexpress-a9 -kernel zImage \
  -append "console=ttyAMA0" \
  -display none -serial mon:stdio

为什么要用仿真做驱动开发 #

三个理由。快：交叉编译出内核，-kernel 一给，几秒内就能看到启动日志，真板子要烧写、接串口线、按复位键，一轮下来几分钟。可复现：虚拟硬件的寄存器行为是固定的，同样的镜像每次跑结果都一样。可观测：QEMU 能打印设备访问日志，能把 gdb 挂到客户机内核上单步，真板子上要么靠 JTAG，要么靠 printf。

把 gdb 挂上去调内核 #

bash
qemu-system-arm -M vexpress-a9 -kernel zImage \
  -append "console=ttyAMA0" \
  -nographic -s -S

-s 是 -gdb tcp::1234 的简写，-S 让 CPU 在启动时暂停，等调试器发话。然后另一个终端里：

bash
arm-linux-gnueabihf-gdb vmlinux
(gdb) target remote :1234
(gdb) b start_kernel
(gdb) c

vmlinux 是带符号的内核镜像，zImage 是压缩过的，gdb 认不出符号。两个都要有：QEMU 加载 zImage 负责跑，gdb 读 vmlinux 负责查符号。

常用开发板型号 #

型号 CPU 场景
vexpress-a9 双核 Cortex-A9 通用 ARM 练手，文档齐全
virt 可配，ARM 或 RISC-V 半虚拟化平台，没有对应真板子
raspi3b 四核 Cortex-A53 树莓派 3B 行为
xilinx-zynq-a9 单核 Cortex-A9 Zynq 开发

virt 值得单独说。它不是任何一块真板子的模拟，而是专为虚拟化设计的平台，设备都是 virtio 的，启动快、依赖少。学习内核启动流程、跑测试，用 virt 比用 vexpress-a9 更省事。

bash
qemu-system-aarch64 -M virt -cpu cortex-a57 -m 1G \
  -kernel Image -append "console=ttyAMA0" -nographic

qemu-system-aarch64 和 qemu-system-arm 是两个程序。前者跑 AArch64，后者跑 32 位 ARM，用错一个内核会在最早期挂掉，串口上什么都不输出。交叉工具链也要对上：32 位用 arm-linux-gnueabihf-，64 位用 aarch64-linux-gnu-，混用的现象一样，都是静默失败。

挂载根文件系统，与最小完整流程 #

最简单的是 ext4 镜像。想省掉制作镜像这一步，可以用 initramfs：

bash
qemu-system-arm -M vexpress-a9 -kernel zImage \
  -initrd initramfs.cpio.gz \
  -append "console=ttyAMA0 rdinit=/bin/sh" -nographic

-initrd 给一个 cpio 包，rdinit=/bin/sh 直接进 shell。没有根文件系统，没有 systemd，一个最简调试环境。NFS root 也能用，但那要求宿主机配好 NFS 服务和 tap 网络，环节多，先跑通前两条再考虑。

从头跑一遍完整流程是这样：

bash
export ARCH=arm
export CROSS_COMPILE=arm-linux-gnueabihf-
make vexpress_defconfig
make zImage dtbs -j$(nproc)

qemu-system-arm -M vexpress-a9 \
  -kernel arch/arm/boot/zImage \
  -dtb arch/arm/boot/dts/vexpress-v2p-ca9.dtb \
  -append "console=ttyAMA0" -nographic

没有根文件系统，内核会在挂载根的时候 panic，但启动日志会完整打出来。调启动流程、验证驱动 probe，到这一步就够了。要真的进用户态，再补一个 rootfs：

bash
dd if=/dev/zero of=rootfs.ext4 bs=1M count=256
mkfs.ext4 rootfs.ext4
sudo mount -o loop rootfs.ext4 /mnt
sudo cp -r rootfs-content/* /mnt
sudo umount /mnt

mkfs.ext4 造的是 raw 格式的块设备镜像，不是 qcow2。这也是前面那条命令里写 format=raw 的原因。

这套流程的价值在于：改一行驱动代码，重新编译内核，把它塞进启动命令，几十秒就能看到结果。不用烧写 SD 卡、不用等板子重启、不用接串口线。交叉开发里最耗时间的「验证」环节，被压到了最短。

代价要说清楚：QEMU 仿的是一块虚拟开发板，它的外设行为和真芯片有出入。时序敏感的代码（中断延迟、DMA 与缓存的竞争、时钟精度）在仿真里跑通，不代表上板就对。仿真是用来验证「逻辑对不对」，不是验证「时序准不准」。

十一、QEMU 与 VMware 的对比 #

两个都叫虚拟机，解决的问题不一样。

维度 QEMU VMware
交互方式 命令行、参数式 图形界面、点选式
架构支持 同架构（KVM 加速）与跨架构（纯仿真） 只跑宿主机同架构
加速方式 -enable-kvm 调内核 KVM 自家的 hypervisor 驱动
设备模拟 软件模拟，可选几十种网卡/显卡/芯片 模拟一套固定的 PC 硬件
快照与克隆 qemu-img 做后备镜像与快照 图形界面里点几下
典型场景 嵌入式开发、内核调试、跨架构测试、CI 里跑测试 桌面工作环境、偶尔装个 Windows 试试
上手成本 要背参数 装完就能用
开源 是（GPL） 否（免费版功能受限）

一句话区分：VMware 是给「想用一台虚拟机工作」的人做的，QEMU 是给「想控制一台机器内部怎么跑」的人做的。

选哪个的判断很清楚：

  • 要装个 Linux 做日常开发、要图形界面、不想记参数，VMware（或者 VirtualBox、Hyper-V）
  • 要在 x86 上验证 ARM 驱动、要给内核打补丁、要在 CI 里无图形化跑测试，QEMU
  • 两台机器上都要跑同一个系统做对比实验，两个都用，各有各的顺手

QEMU 在 CI 里有一个特别的位置：-nographic 加 -serial mon:stdio 之后，整个虚拟机的行为就是一个标准输入输出流，可以完全脚本化。这是图形化虚拟机做不到的。

十二、易错点速查 #

现象 原因 处理
Could not access KVM kernel module /dev/kvm 权限不够或模块没加载 用户加进 kvm 组，modprobe kvm_intel，用 kvm-ok 查
-enable-kvm 报了不支持 BIOS 里没开 VT-x/AMD-V 进 BIOS 打开虚拟化，egrep -c '(vmx|svm)' /proc/cpuinfo 应该有非零输出
启动后黑屏、无任何输出 缺 -nographic 或没指对串口 加 -nographic 与 -append "console=ttyS0"，确认 console= 与机器类型匹配
qemu-img create ... 20G 后文件就几 K 这是 qcow2 的正常行为 20G 是上限，实际占用随写入增长
虚拟机里删了文件，宿主机上 .qcow2 不变小 qcow2 不会自动回收 qemu-img convert -O qcow2 in out 重建
装机时报找不到磁盘 -drive 没配或 if= 类型不对 显式写 if=virtio 或 if=ide，并确认内核里有对应驱动
网络不通（user 模式） 外部访问不进来是设计如此 要入站用 -netdev user,hostfwd=tcp::2222-:22 转发端口
装了系统后启动不了，提示找不到引导 没有可引导磁盘或启动顺序不对 加 -boot order=c，或用 -boot menu=on 手动选
硬盘镜像被虚拟机占了，另一个进程打不开 QEMU 默认独占锁 多实例共享只读盘时加 -drive ...,readonly=on
仿真跑得极慢 忘记 -enable-kvm，走的是纯仿真 同架构一定要开 KVM；跨架构慢是必然的
qemu-system-arm 找不到机器类型 该架构的机器名不同 qemu-system-arm -M help 列出所有可用机器
嵌套在 KVM 虚拟机里跑 QEMU 起不来 没开嵌套虚拟化 宿主机加 kvm-intel.nested=1，或直接改用 TCG

最后压一句：QEMU 的门槛全在那条命令行上。参数记错一个，现象就是从「起不来」到「起来了但没网」的各种花样。碰到问题时，先用最小可用命令跑通，再一个参数一个参数往上加，比对着长命令调快得多。
