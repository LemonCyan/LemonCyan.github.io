这篇只讲 WSL 本身：怎么装、怎么管多个发行版、文件和网络怎么通、图形界面怎么出、USB 设备怎么接进来、资源怎么限、开发环境（拿 Qt 举例）怎么配。不展开讲 VMware、QEMU 这类完整虚拟机，那是同目录另外两篇的事；也不讲 Windows 上跑 Linux 容器（Docker Desktop 那条线）。文中出现的命令，PS 标记的在 Windows PowerShell 里跑，bash 标记的在 WSL 发行版终端里跑，别搞反。

一、WSL 是什么 #

WSL 是 Windows Subsystem for Linux 的缩写，微软在 Windows 内核这一侧加的一层兼容设施，让你不重装系统、不开传统虚拟机软件，就能在 Windows 里跑一个 Linux 用户态。

它不是模拟器，也不是 Cygwin 那种「把 Unix 调用翻译成 Win32 调用」的库。第一代 WSL 是翻译层，第二代直接换成了一台轻量虚拟机。

这篇讲的日常操作，九成以上建立在第二代上。第一代现在基本只有考古价值，但两者的差别值得单独开一章，因为后面所有「为什么访问不到」「为什么这么慢」的答案都埋在那里。

先把后面反复用到的一句结论放这里：

WSL2 是一台跑在 Hyper-V 上的真 Linux 虚拟机，只是集成得极深。

它有自己编译的 Linux 内核、自己的 ext4 文件系统镜像、自己的网络栈、自己的 init 进程。微软把它的终端、文件系统、网络、图形、音频都接到了 Windows 上，接得太顺，以至于很多人忘了它本质是一台虚拟机。

记住这句话，后面这些现象就都不奇怪了：

  • 它的 IP 跟 Windows 不是同一个，所以 Windows 直接 localhost 连它里面的服务有时通有时不通。
  • 它的根文件系统不在 C:\ 里某个普通文件夹，而是一个 .vhdx 虚拟磁盘。
  • 它的 USB 口默认是空的，因为虚拟机默认不接管宿主机的 USB 控制器。
  • 它的内存是动态从 Windows 借的，借了不一定马上还。

二、WSL1 与 WSL2 #

WSL1 和 WSL2 不是版本号升级，是两套完全不同的实现。名字里的 1 和 2 容易让人以为是「新版本修了 bug」，其实架构上根本不是一条路。

WSL1 干的事是翻译：Linux 程序发出的系统调用，被 WSL1 的驱动实时翻译成 Windows 内核能懂的调用。文件系统是同一个，你在 Linux 里看的 /mnt/c/Users/... 和 Windows 里看的 C:\Users\... 就是同一批文件，同一个 NTFS 卷，没有跨系统边界这回事。

这套做法有它的好处：文件是同一份，不存在同步问题，启动快，占内存少。代价是每个系统调用都要翻译一次，fork() 这类调用翻起来更是费劲，于是 Git 操大仓库、npm install、编译大项目这些重 I/O 重进程的场景就明显拖不动。兼容性也只能做到「常用调用能翻，冷门调用凑合」。

WSL2 换了思路：不翻译了，直接给你一台虚拟机，里面跑真内核。系统调用在 Linux 内核里原生执行，没有翻译损耗，于是 Docker 能跑、systemd 能上、性能贴近日志里的原生 Linux。代价是它成了一台真正的机器，跟 Windows 之间有了一道边界。

维度 WSL1 WSL2
实现方式 系统调用翻译层 轻量虚拟机（Hyper-V）
Linux 内核 没有，用 Windows 内核翻译 微软编译的真 Linux 内核
文件系统 与 Windows 同一套 NTFS 自己的 ext4 虚拟磁盘
Linux 侧 I/O 慢，重进程操作尤其明显 快，接近原生
访问 /mnt/c 原生速度 走 9P 协议，大量小文件慢一个数量级
完整系统调用 部分支持，兼容性有缺口 完整支持
Docker 跑不动 能跑
systemd 不支持 支持
图形界面 需要外挂 X Server 自带 WSLg
内存占用 低 动态分配，可设上限
网络 与宿主共用 独立网络栈（NAT）或镜像模式
USB 设备 直接可用 要用 usbipd 转发
启动速度 快 稍慢（要起虚拟机）

选哪个：除非你有明确理由必须用 WSL1（比如老项目依赖某个 WSL2 下没跑通的调用，或者机器上连 Hyper-V 都开不了），否则一律 WSL2。现在新装的系统默认就是 WSL2。

确认当前某个发行版跑的是哪代：

bash
wsl --list --verbose

输出里的 VERSION 列就是答案。要改：

bash
wsl --set-version Ubuntu-22.04 2

转换是单向的坑比较多的事：从 1 升到 2 会重建文件系统，发行版里的东西会丢，动手前先 wsl --export 备份一份。

三、安装与发行版管理 #

3.1 从零装一套 #

如果你从来没在这台机器上装过 WSL 相关组件，下面几步都要走。只是想加一个新发行版，跳到 3.2。

第一步，用管理员权限打开 PowerShell，启用 Windows 的 Linux 子系统功能：

ps
dism.exe /online /enable-feature /featurename:Microsoft-Windows-Subsystem-Linux /all /norestart

第二步，等上面跑完，启用虚拟机平台功能：

ps
dism.exe /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart

第三步，开启 Hyper-V：

ps
dism.exe /online /enable-feature /featurename:Microsoft-Hyper-V /all /norestart

第四步，让引导管理器默认加载 Hyper-V：

ps
bcdedit /set hypervisorlaunchtype Auto

第五步，重启电脑。重启过程中会显示正在安装系统更新，这是正常的，耐心等着。

第六步，下载并安装 Linux 内核更新包：https://wslstorestorage.blob.core.windows.net/wslblob/wsl_update_x64.msi

第七步，回到 PowerShell，这一步开始不需要管理员权限了。把默认版本设成 2：

ps
wsl --set-default-version 2

第八步，装发行版：

ps
wsl --install -d ubuntu22.04

这个命令从 Microsoft Store 拉发行版，所以本机的 UWP 商店客户端得能连上微软的网络。网络环境不行会直接报错，那就去微软官网手动下安装包：

发行版 链接
Ubuntu 22.04 https://aka.ms/wslubuntu2204
Ubuntu 20.04 https://aka.ms/wslubuntu2004
Ubuntu 18.04 https://aka.ms/wsl-ubuntu-1804

下完用 Add-AppxPackage .\app_name.appx 手动装。

第九步，更新 WSL 自身组件：

ps
wsl --update

较新的 Windows 上，wsl --install 一条命令就能把上面大部分步骤包掉，装完重启即可。老系统沿用上面这套 dism 流程更稳，因为 --install 依赖的组件在旧版里还没到位。

3.2 查看已安装的发行版 #

ps
wsl --list

常用变体：

ps
wsl --list --verbose
wsl --list --running
wsl --list --online
  • --verbose 带状态、版本号和内核版本，最常用。
  • --running 只看正在跑的。
  • --online 列出商店里能装的发行版清单。

如果某个发行版的列表项显示成乱码方块，那是老版本 WSL 的编码问题，wsl --update 之后一般就好了。

3.3 删除发行版 #

ps
wsl --unregister ubuntu22.04

--unregister 是不可逆的：发行版的整个文件系统连同里面的数据一起消失，磁盘空间回收。敲之前先 wsl --export 导出备份。改名、迁移也走导出加导入这条路，见 3.5。

3.4 更新 #

ps
wsl --update

更新完如果没生效：

ps
wsl --shutdown

--shutdown 会把所有发行版和 WSL2 的轻量虚拟机整个停掉，再打开终端会重新起。改完 .wslconfig、改完 wsl.conf、装完显卡驱动，都建议来一下。

想回滚到旧版 WSL：

ps
wsl --update --rollback

3.5 停掉、设默认、迁移 #

停某个发行版而不动其他的，用 wsl --terminate Ubuntu-22.04；设默认发行版用 wsl --set-default Ubuntu-22.04。

C 盘紧张时可以把发行版挪到别的盘，走导出加导入：

ps
wsl --export Ubuntu-22.04 D:\wsl-backup\ubuntu2204.tar
mkdir D:\wsl\ubuntu2204
wsl --import Ubuntu-22.04 D:\wsl\ubuntu2204 D:\wsl-backup\ubuntu2204.tar --version 2

导入之后默认用户会变回 root，改回来：

bash
ubuntu2204 config --default-user yourname

发行版一旦多起来，记住三件事就够了：--list 看有什么，--unregister 删，export + import 搬家。

四、文件系统的互通 #

WSL2 的存储结构是两层，这两层性能差别很大，理解这个差别的收益比背命令大得多。

4.1 两个世界 #

Windows 侧的文件，在 Linux 里挂在 /mnt/c、/mnt/d 这些路径下，由 WSL 驱动自动挂载。你 cd /mnt/c/Users/liuluhua/Desktop 就能直接看到桌面。

Linux 侧的文件，在 WSL2 里是一个 .vhdx 虚拟磁盘，里面是 ext4 文件系统。默认位置在 %LOCALAPPDATA%\Packages\<发行版包名>\LocalState\ext4.vhdx，从 Windows 的文件管理器看，它就是一个几百 MB 到几十 GB 的磁盘镜像文件。

4.2 性能差在哪 #

跨过 /mnt/c 的每一次读写，都要经过一层网络文件协议（9P，较新版本里做了改进），由 Windows 侧的服务器进程代理。单次访问的额外开销不算夸张，但小文件一多就顶不住。

具体感受是这样的：

操作位置 文件系统 大量小文件（npm install、git clone、编译） 大文件顺序读写
~/project（Linux 侧） ext4，在 vhdx 里 快 快
/mnt/c/project（Windows 侧） NTFS，走 9P 慢一个数量级 尚可

一个真实量级：同一个 Node 项目，放在 ~/ 下装依赖两三分钟，放在 /mnt/c/ 下能跑十几分钟，还会因为文件锁问题直接失败。

结论很直白：代码放 Linux 侧，工具链放 Linux 侧。

4.3 项目代码应该放哪 #

放进 Linux 的家目录：

bash
mkdir -p ~/projects && cd ~/projects
git clone <repo>

在 Windows 上编辑这些文件有两种办法：

一是用 VS Code 的 WSL 远程模式。在 WSL 终端里 cd ~/projects/myrepo，然后 code .，VS Code 会在 Windows 侧打开窗口，文件读写走 WSL 内部通道，不经过 9P，编辑体验和本地没差别。

二是直接把 Windows 侧编辑器指向 \\wsl$\ 路径。这可行，但编辑器扫描目录、建索引会慢，大项目不推荐。

4.4 从 Windows 访问 Linux 文件 #

打开文件管理器，地址栏输入：

text
\\wsl$

回车。会看到当前装的所有发行版，点进去就是各自的根目录，可以直接拖文件进出。往里面复制文件后 WSL 里会自动刷新，不用重启也不用敲命令。

也可以直接定位到某个发行版：

text
\\wsl$\Ubuntu-22.04\home\yourname

一个坑：地址栏输入回车后半天没反应，那是因为内容还没加载出来。别关窗口，耐心等。有些机器上要等好几分钟，尤其是发行版里文件多的时候。

4.5 从 Linux 打开 Windows 资源管理器 #

在 WSL 终端里：

bash
explorer.exe .

资源管理器会弹出来，停在当前目录。这是在 Windows 里看 Linux 文件最顺手的方式，比记 \\wsl$ 路径方便。

同理，Windows 的 exe 只要在 PATH 里就能直接调，比如 notepad.exe README.md、code .。.exe 后缀不能省，Linux 侧不会帮你补。

4.6 挂载选项 #

/mnt/c 的默认挂载行为可以调，元数据支持、权限位这些由 /etc/wsl.conf 里的 [automount] 段控制，详见第十章。想看当前挂载情况，跑 mount | grep drvfs：drvfs 是 WSL 挂 Windows 盘用的文件系统类型，看到 /mnt/c 是 drvfs、/ 是 ext4，就对上了。

五、网络模型与端口访问 #

这一章解决最高频的一个疑问：在 WSL 里起了个服务，Windows 上用浏览器打不开。

5.1 两种网络模式 #

WSL2 有两种网络模式，默认是 NAT。

NAT 模式：WSL2 这台虚拟机从 Hyper-V 拿到一个独立的私有 IP（一般是 172.x.x.x 网段），通过宿主机的 NAT 出网。它和 Windows 是两个网络节点，各有各的地址。Windows 侧配了个 localhost 转发机制，把 Windows 上的 localhost:端口 转到 WSL 的对应端口，所以多数情况下 localhost 是通的——但只对能监听的转发生效，绑在特定地址上的服务就不一定。

镜像模式：较新版本 Windows 提供。配 networkingMode=mirrored 之后，WSL 跟 Windows 共用网络接口和 IP，127.0.0.1 在两边指向同一个地方，网络行为接近「同一个系统里的两个进程」。

维度 NAT 模式（默认） 镜像模式
IP 地址 WSL 有独立私有 IP 与 Windows 共用
localhost 访问 靠 Windows 侧转发，有条件 天然互通
从 WSL 访问 Windows 服务 要查宿主机 IP 直接 127.0.0.1
从局域网其他机器访问 WSL 服务 要在 Windows 上做端口转发 一般可直接访问
代理配置 要手动指宿主 IP 可直接用 127.0.0.1
配置位置 .wslconfig 的 [wsl2] 段 .wslconfig 的 [wsl2] 段
适用 Windows 版本 都支持 较新版本

镜像是较新版本才有的，具体从哪个版本号开始提供，不同渠道说法不一致，动手前先 wsl --version 看一下，再用 wsl --update 升到最新，然后试配置能不能生效。

5.2 NAT 模式下为什么访问不到 #

三个常见原因。

一是服务只绑了 127.0.0.1。 在 NAT 模式下，WSL 里的 127.0.0.1 是它自己的回环，跟 Windows 无关。Windows 的 localhost 转发能不能碰到它，取决于 WSL 的转发实现和服务的绑定行为。稳妥做法是让服务绑 0.0.0.0：

bash
python3 -m http.server 8000 --bind 0.0.0.0

二是宿主 IP 变了。 WSL 每次重启会重新分配 IP，写死在脚本里的老地址自然失效。要现查：

bash
ip addr show eth0 | grep 'inet '
hostname -I

三是 Windows 防火墙拦了。 从局域网另一台机器访问 WSL 服务时，Windows 侧的入站规则会把连接挡了。这类规则要按需加，别一把关掉防火墙。

5.3 端口转发 #

想从局域网访问 WSL 里的服务，NAT 模式下要在 Windows 上做端口转发。管理员 PowerShell：

ps
netsh interface portproxy add v4tov4 listenport=8000 listenaddress=0.0.0.0 connectport=8000 connectaddress=172.20.10.5

connectaddress 换成 hostname -I 查到的 WSL IP。看现有规则：

ps
netsh interface portproxy show all

删掉：

ps
netsh interface portproxy delete v4tov4 listenport=8000 listenaddress=0.0.0.0

这套东西的毛病是 WSL IP 一变规则就废，所以更适合临时调试。长期跑服务，镜像模式省事得多。

5.4 从 WSL 访问 Windows 上的服务 #

反过来也要注意。NAT 模式下 WSL 里的 127.0.0.1 不是 Windows，要拿宿主机 IP：

bash
cat /etc/resolv.conf | grep nameserver

那个 nameserver 行的地址就是宿主侧 NAT 网关，同时也是 Windows 在 WSL 眼里的地址。较新版本的 WSL 还提供了 mirrored 和主机名解析，用主机名有时也能通。

一个细节：Windows 上的服务默认绑 127.0.0.1 时，WSL 从外面连不进去，因为它只监听自己的回环。要让 WSL 连上，服务得绑 0.0.0.0，或者用端口转发。

5.5 DNS 出问题怎么办 #

偶尔会遇到 WSL 里域名解析不了，ping IP 通、ping 域名不通。先 cat /etc/resolv.conf 看配置。较新 WSL 在 .wslconfig 里提供了 DNS 隧道相关选项，保持默认即可。手动改 /etc/resolv.conf 只能当排查手段，因为每次重启都会被重新生成。

较新版本支持在 /etc/wsl.conf 里写 [network] 段的 generateResolvConf = false，关掉自动生成之后自己维护 /etc/resolv.conf，改完 wsl --shutdown 重启生效。这只在自动生成的配置确实不对时用。

六、代理配置 #

WSL 里的终端默认不继承 Windows 的代理设置。你在 Windows 上开了代理软件，WSL 里 curl 一样连不上外网，得手动告诉它。

6.1 先拿到代理端口 #

打开你在 Windows 上用的代理软件，找到 HTTP 代理的监听端口。本文统一以 7890 举例，你的端口多半不是这个，照抄会失败。

6.2 NAT 模式：指向宿主机 IP #

NAT 模式下，WSL 要连的是 Windows 的代理端口，所以地址得写宿主侧 IP，不能写 127.0.0.1：

bash
#!/bin/bash
host_ip=$(cat /etc/resolv.conf | grep "nameserver" | cut -f 2 -d " ")
export HTTP_PROXY="http://$host_ip:7890"
export HTTPS_PROXY="http://$host_ip:7890"
export ALL_PROXY="http://$host_ip:7890"

两个细节必须注意：地址里的 http:// 前缀不能丢；端口号必须换成你自己的。

另外，代理软件本身要允许来自局域网的连接（也就是监听 0.0.0.0 而不是只绑 127.0.0.1），否则 WSL 发出的请求会被它自己拒掉。这个开关在多数代理软件的设置里叫「允许局域网连接」之类。

6.3 镜像模式：可以直接用回环 #

配了 networkingMode=mirrored 之后，WSL 和 Windows 共用网络，代理地址直接写 127.0.0.1 就行：

bash
export HTTP_PROXY="http://127.0.0.1:7890"
export HTTPS_PROXY="http://127.0.0.1:7890"
export ALL_PROXY="http://127.0.0.1:7890"

这比每次去 resolv.conf 里抠 IP 省事，也是镜像模式比较实用的一个理由。

6.4 让它一直生效 #

写进 ~/.bashrc 是最省事的做法：

bash
echo 'export HTTP_PROXY="http://127.0.0.1:7890"' >> ~/.bashrc
echo 'export HTTPS_PROXY="http://127.0.0.1:7890"' >> ~/.bashrc
source ~/.bashrc

但要注意 $host_ip 是动态的。如果 .bashrc 里写的是变量引用，得保证那个变量在同一次 shell 里先被算出来：

bash
host_ip=$(cat /etc/resolv.conf | grep "nameserver" | cut -f 2 -d " ")
export HTTP_PROXY="http://$host_ip:7890"
export HTTPS_PROXY="http://$host_ip:7890"
export ALL_PROXY="http://$host_ip:7890"

把这段整体放进 ~/.bashrc 末尾，每次开终端自动算一遍。

6.5 只给特定命令用 #

不希望全局设代理，可以只在单条命令前加：

bash
http_proxy=http://127.0.0.1:7890 https_proxy=http://127.0.0.1:7890 git clone <repo>

6.6 别忘了这些工具的代理 #

环境变量对一部分工具无效，它们读自己的配置：

bash
git config --global http.proxy http://127.0.0.1:7890
git config --global https.proxy http://127.0.0.1:7890

取消：

bash
git config --global --unset http.proxy
git config --global --unset https.proxy

apt 走的是自己的配置文件：

bash
sudo tee /etc/apt/apt.conf.d/95proxy <<'EOF'
Acquire::http::Proxy "http://127.0.0.1:7890";
Acquire::https::Proxy "http://127.0.0.1:7890";
EOF

sudo 默认不继承你 shell 里的环境变量，所以 sudo apt update 即使你设了 HTTP_PROXY 也不一定生效，按上面配一次更保险。要让 sudo 保留代理变量，可以用 sudo -E，前提是 sudoers 里允许。

6.7 验证通不通 #

bash
curl -I https://www.google.com
env | grep -i proxy

env 那行应该有输出，说明变量确实设上了。设了还是不通，八成是代理软件没开「允许局域网」，或者端口写错了。

七、图形界面：WSLg #

7.1 老办法已经过时 #

早年的教程会让你在 Windows 上装一个 X Server（VcXsrv、Xming、X410 之类），手动画配置、勾选「Disable access control」，然后在 WSL 里 export DISPLAY=<宿主IP>:0，把图形程序投到那个 X Server 上。

这套流程今天基本不需要了。较新的 Windows 自带 WSLg（Windows Subsystem for Linux GUI），WSL2 装完就能直接跑图形程序，不用额外装任何东西。

方案 要不要装东西 配置 现状
WSLg 不用，系统自带 零配置 较新 Windows 的默认路径
VcXsrv / Xming 要装 X Server 手动配 Display number、关访问控制、设 DISPLAY 老教程方案，能用但没必要

如果你的系统确实没有 WSLg（老 Windows），才考虑退回 X Server 方案，配置方式见 7.6。判断标准很简单，先跑 wsl --version 看输出里带不带 WSLg 版本。

7.2 WSLg 是什么 #

WSLg 让 WSL2 里的 Linux 图形程序直接显示在 Windows 桌面上，X11 和 Wayland 两种协议都支持。

项目地址：https://github.com/microsoft/wslg

集成到 Windows 上的表现：

  • Linux 应用的图标会出现在「开始」菜单和任务栏，跟 Windows 应用一起用 Alt+Tab 切换。
  • 两边共用剪贴板，Windows 里复制的文本能直接粘进 Linux 应用。
  • 音频和 GPU 加速走同一套通道。

它跑的是单个应用窗口，不是一整套 Linux 桌面。要完整桌面环境（比如 GNOME、KDE），还是得开完整虚拟机，那是同目录另一篇的事。

7.3 确认能用 #

在 PowerShell 里：

powershell
wsl --version
wsl --status

wsl --version 的输出里带 WSLg 版本号，就说明装上了。较新的 Windows 上 WSLg 随 WSL2 一起提供，不用单独下载。没有的话先更新：

powershell
wsl --update
wsl --shutdown

--shutdown 之后要重新打开 WSL 终端才生效。

7.4 跑一个试试 #

在 WSL 终端里装个小工具再启动：

bash
sudo apt update
sudo apt install x11-apps
xeyes

弹出窗口就说明链路通了。WSLg 自己接好了显示通道，不用手动设 DISPLAY。

再试一个更实用的：

bash
sudo apt install firefox
firefox

浏览器窗口会直接出现在 Windows 桌面上。

7.5 WSLg 卡住怎么办 #

  • 窗口起不来：先确认是 WSL2 不是 WSL1，wsl --list --verbose 看 VERSION 列。WSL1 没有 WSLg。
  • 中文显示成方框：WSL 里没装中文字体，处理办法见第十一章。
  • 图形卡顿或黑屏：更新 WSL 和显卡驱动，然后 wsl --shutdown 重开。
  • 要接 USB 设备（比如 3D 打印机）：走 usbipd，见第八章。
  • 报 cannot open display：先 echo $DISPLAY 看有没有值，正常情况 WSLg 会给一个类似 :0 的值。空的话检查是不是在纯 SSH 会话里，或者是不是 wsl --shutdown 之后没重开终端。

7.6 老方案：外挂 X Server #

只有系统确实没有 WSLg 才需要这一段。

先装一个 X Server，以 VcXsrv 为例。从 https://sourceforge.net/projects/vcxsrv/files/vcxsrv/ 下最新版安装包，装好。

运行它，默认会进配置窗口。在 Display number 里填一个数字并记住，这里以 0 为例。一路下一步，到出现几个复选框那页时，勾上 Disable access control。继续下一步到完成，VcXsrv 就设好并启动了。

回到 WSL2，运行：

bash
#!/bin/bash
host_ip=$(cat /etc/resolv.conf | grep "nameserver" | cut -f 2 -d " ")
export DISPLAY=$host_ip:0

那个 :0 就是上一步填的 Display number，要对应上，冒号也不能丢。然后直接跑你的图形软件。

如果启动的是 Qt 程序还是起不来，多半缺少 X11 相关环境：

bash
sudo apt install -y libxcb* libxkbcommon-x11-0

这一整套的唯一优势是可控性——你能看到 X Server 的日志，排查某些老旧程序时反而方便。新系统上没必要走这条路。

八、USB 设备转发 #

8.1 为什么 U 盘插上没反应 #

WSL2 是虚拟机。虚拟机的默认行为是：宿主机的 USB 口不归它管。你在 Windows 上插一个 U 盘、一个 3D 打印机、一个调试器，WSL 里 lsusb 什么都看不到。这不是驱动没装，是设备压根没进虚拟机。

WSL1 时代没这个问题，因为那时候没有虚拟机边界。换成 WSL2 之后，USB 就得显式转发。

转发靠两个组件：Windows 侧的 usbipd-win，Linux 侧的 usbip 客户端。USB/IP 本来是 Linux 内核里一套把 USB 请求封装成 IP 报文传输的协议，usbipd 把它搬到了 Windows 上当服务端。

项目地址：https://github.com/dorssel/usbipd-win

8.2 转发的本质是「解绑」 #

这里有个很多人没料到的语义，先讲清楚：

usbipd 做的事是把 USB 设备从 Windows 解绑，通过 IP 网络转发给 WSL。

不是「共享」，是「移交」。bind 之后设备 exclusivity 归了 USB/IP 服务，Windows 自己就不能再用它了；attach 到 WSL 之后，设备节点出现在 Linux 里，Windows 的资源管理器看不到它。直到你 detach，设备才还给 Windows。

所以会碰到这些情况：

  • 挂上去之后，Windows 上那个打印机软件突然找不到设备了——正常，它被 WSL 拿走了。
  • 想 Windows 和 WSL 同时用一个 U 盘——做不到，得二选一。
  • 不 detach 就拔线——建议先 detach 再拔，直接拔不会烧坏东西，但下次插上状态会不干净。

8.3 Windows 侧装 usbipd #

用管理员权限打开 PowerShell：

powershell
winget search usbipd
winget install --exact --id <ID>

把 <ID> 换成 winget search 输出里 ID 那一列的值，别照抄。也可以直接从仓库 Releases 下载 .msi 安装。

装完重开一个终端确认：

powershell
usbipd --version

重开终端是因为 PATH 更新了对已开的会话不生效。

8.4 版本差异的坑 #

usbipd 的子命令形式随版本变过。老版本写 usbipd wsl list，较新版本里 wsl 这个中间层被去掉了，直接 usbipd list。

动手前先跑一次：

powershell
usbipd --help

按实际装到的版本对一下命令，下面的写法以 --help 输出为准。本文两套写法都会给出。

8.5 WSL 侧装 usbip 客户端 #

在 WSL 终端里：

bash
sudo apt update
sudo apt install linux-tools-virtual hwdata
sudo update-alternatives --install /usr/local/bin/usbip usbip $(ls /usr/lib/linux-tools/*/usbip | tail -n1) 20

第一条装工具包，第二条把对应内核版本的 usbip 链到 /usr/local/bin。少了第二步，Windows 侧 attach 时会报：

text
usbipd: error: WSL 'usbip' client not correctly installed

报这个错就回头核对 update-alternatives 有没有执行成功，用 usbip version 试一下。

WSL2 内核本身还得带 USB/IP 支持。老内核没有，wsl --update 升级一下再试。

8.6 找到设备并挂进去 #

插上设备，在 Windows 终端列出：

powershell
usbipd wsl list

较新版本：

powershell
usbipd list

输出里会列出所有本地 USB 设备。记下目标设备的 busid，形如 4-1。

第一步，绑定（要管理员权限）：

powershell
usbipd bind --busid 4-1

这一步把设备从 Windows 解绑给 USB/IP 服务，是后面 attach 的前提。绑定状态在重启后会保留。

第二步，挂到 WSL：

powershell
usbipd attach --wsl --busid 4-1

老版本写法：

powershell
usbipd wsl attach --busid 4-1

设备此刻被 WSL2 占用，Windows 里就看不到了。

8.7 在 Linux 里确认 #

回到 WSL 终端：

bash
lsusb
ls /dev/ttyUSB* /dev/ttyACM*

lsusb 里能看到那个设备，说明转发成功。

3D 打印机是串口设备，出现 /dev/ttyACM0 这类节点，切片软件就能连了。用之前确认当前用户有权限读写这个节点，不然会报权限错：

bash
sudo usermod -aG dialout $USER

加组之后要重新登录 WSL 才生效，或者临时用 sudo chmod 666 /dev/ttyACM0 应急。

8.8 用完归还 #

在 Windows 终端：

powershell
usbipd detach --busid 4-1

老版本：

powershell
usbipd wsl detach --busid 4-1

归还之后 Windows 重新接管这个设备，资源管理器里又能看到了。

不归还的话，拔线之前 Windows 那边一直看不到它。整个流程走一遍其实就五步，连起来看：

步骤 在哪执行 命令
1. 装服务端 Windows（管理员） winget install --exact --id <ID>
2. 装客户端 WSL apt install linux-tools-virtual hwdata
3. 列设备 Windows（管理员） usbipd list
4. 绑定 Windows（管理员） usbipd bind --busid 4-1
5. 挂载 Windows usbipd attach --wsl --busid 4-1
6. 验证 WSL lsusb
7. 归还 Windows usbipd detach --busid 4-1

8.9 常见故障 #

usbipd 找不到命令，是装完没重开终端。attach 报客户端没装好，回 8.5 重做 update-alternatives。lsusb 里没有设备，多半只 attach 没 bind，或者 bind 不是管理员身份跑的。设备节点有但打不开，加 dialout 组。插拔一次后挂不上，detach 之后重新 bind 再 attach。

九、硬件资源限制 #

9.1 默认行为 #

WSL2 是一台虚拟机，内存、CPU 都从 Windows 那边拿。默认配置下，它能用到宿主机的很大一部分资源，而且是动态借：启动时不多占，用多少拿多少。

麻烦在「还不还」。早期 WSL2 会用满一部分内存之后长期不释放，Windows 侧看起来就是可用内存莫名其妙少了好几个 G。较新版本加了 pageReporting 之类的机制，会往回还一些，但不是立刻全还。

机器内存大的话，直接给个上限最省心。

9.2 配置文件 #

创建一个叫 .wslconfig 的文件，放在 C:\Users\<UserName> 下，例如 C:\Users\wangwenx190\.wslconfig。

注意文件名以点开头，Windows 资源管理器默认不让你建这种名字。用记事本另存为时文件名写成 ".wslconfig"（带引号），或者用 PowerShell：

powershell
New-Item -Path "$env:USERPROFILE\.wslconfig" -ItemType File

下面是一个配置示例，出自官方文档：

ini
# Settings apply across all Linux distros running on WSL 2
[wsl2]

# Limits VM memory to use no more than 4 GB, this can be set as whole numbers using GB or MB
memory=4GB

# Sets the VM to use two virtual processors
processors=2

# Specify a custom Linux kernel to use with your installed distros. The default kernel used can be found at https://github.com/microsoft/WSL2-Linux-Kernel
kernel=C:\\temp\\myCustomKernel

# Sets additional kernel parameters, in this case enabling older Linux base images such as Centos 6
kernelCommandLine = vsyscall=emulate

# Sets amount of swap storage space to 8GB, default is 25% of available RAM
swap=8GB

# Sets swapfile path location, default is %USERPROFILE%\AppData\Local\Temp\swap.vhdx
swapfile=C:\\temp\\wsl-swap.vhdx

# Disable page reporting so WSL retains all allocated memory claimed from Windows and releases none back when free
pageReporting=false

# Turn on default connection to bind WSL 2 localhost to Windows localhost
localhostforwarding=true

# Disables nested virtualization
nestedVirtualization=false

# Turns on output console showing contents of dmesg when opening a WSL 2 distro for debugging
debugConsole=true

# Enable experimental features
[experimental]
sparseVhd=true

9.3 各字段什么意思 #

键 作用 默认
memory 虚拟机内存上限，GB / MB 为单位 宿主内存的一定比例
processors 虚拟机可见的 CPU 核数 宿主核数
swap 交换空间大小 可用内存的 25%
swapfile 交换文件路径 %USERPROFILE%\AppData\Local\Temp\swap.vhdx
kernel 自定义内核路径 微软自带内核
kernelCommandLine 追加内核启动参数 空
pageReporting 空闲内存是否归还 Windows true
localhostforwarding WSL 端口是否绑到 Windows 的 localhost true
nestedVirtualization 是否允许嵌套虚拟化 false
debugConsole 打开发行版时是否显示 dmesg false
sparseVhd（实验性） vhdx 用稀疏文件，删文件后磁盘能缩 关

memory=4GB 这种写法很实用，但别设太小。编译大项目时内存不够会 OOM，比慢更难受。留出余量，机器 16G 给 8G 是个常见选择。

sparseVhd 解决的是另一个经典问题：WSL 里删了文件，Windows 上那个 ext4.vhdx 却不会变小。开了稀疏之后删掉的块能真正释放。

9.4 改完要重启 #

.wslconfig 不是实时读的，改完必须：

powershell
wsl --shutdown

然后重新打开终端。不重启等于没改。

9.5 在 Linux 里看实际用量 #

free -h 看内存和 swap，nproc 看核数，df -h / 看根文件系统。设了 memory=4GB 之后 free -h 显示的总量应该在 4G 附近（内核和固件会占掉一点点）。WSL 内部不要再自己调 sysctl 改内存参数，那些改动重启就没了，也绕不过虚拟机的资源上限。要限就在 .wslconfig 里限。

十、wsl.conf 与 .wslconfig #

这两个文件名字像、作用完全不同，混起来用的次数比想象中多。先把区别钉死。

维度 .wslconfig wsl.conf
位置 Windows 用户目录 C:\Users\<你>\ Linux 里的 /etc/wsl.conf
谁读它 WSL 的 Windows 侧组件 发行版内部的 init
管什么 整个 WSL2 虚拟机 单个发行版
写什么 内存、CPU、swap、内核、网络模式 默认用户、挂载、systemd、主机名
格式 [wsl2]、[experimental] [user]、[automount]、[boot]、[network]
改完怎么生效 wsl --shutdown wsl --shutdown，或重启该发行版
多发行版 一份配置管全部 每个发行版各有一份

一句话记法：.wslconfig 管机器，wsl.conf 管系统。

10.1 wsl.conf 长什么样 #

在某个发行版里创建 /etc/wsl.conf：

ini
[user]
default=yourname

[automount]
enabled=true
root=/mnt/
options="metadata,umask=22,fmask=11"

[boot]
systemd=true
command="service docker start"

[network]
hostname=devbox
generateResolvConf=true

[interop]
enabled=true
appendWindowsPath=true

各段作用：

段 键 作用
[user] default 打开终端时的默认用户，不用写 --user
[automount] enabled 是否自动挂 Windows 盘到 /mnt
root 挂载根路径，默认 /mnt/
options 挂载参数，metadata 让 Linux 能改 Windows 文件权限位
[boot] systemd 是否用 systemd 作为 init，较新版本支持
command 启动时执行的命令，systemd 已接管时不生效
[network] hostname 发行版自己的主机名
generateResolvConf 是否自动生成 /etc/resolv.conf
[interop] enabled 能否在 Linux 里调 Windows 的 exe
appendWindowsPath 是否把 Windows 的 PATH 拼进来

appendWindowsPath=true 用起来方便（可以直接敲 code、explorer.exe），代价是 PATH 变长，同名命令会撞车。如果 Linux 里也有个 code，那就看谁排在前面了。嫌乱就设成 false，需要时写全路径 /mnt/c/.../code.exe。

10.2 两个文件同时改了 #

两边改完一起 wsl --shutdown 就行，重启后用 wsl -d Ubuntu-22.04 直接进指定发行版，比先 wsl 再切省事。

10.3 排错时先看哪个 #

现象对照着看：

现象 先查
内存占用下不去 .wslconfig 的 memory
打开终端变成 root wsl.conf 的 [user] default
局域网访问不到 WSL 里的服务 .wslconfig 的网络模式，和第五章的转发
/mnt/c 里改权限报错 wsl.conf 的 [automount] options 里有没有 metadata
systemctl 用不了 wsl.conf 的 [boot] systemd
代理连不上 网络模式是 NAT 还是 mirrored，见第六章

改配置之前先把原文件复制一份，出问题好退回。配置文件写错格式会导致发行版启动异常，wsl --shutdown 之后连不上就得改回来。

十一、开发环境：以 Qt 为例 #

前面讲的是通用设施。这一章拿 Qt 走一遍完整流程，能踩的坑基本都踩到了。

11.1 先确定显示通道 #

在动手装 Qt 之前先确认 WSLg 是好的，见第七章。装完 Qt 跑不起来，你要花时间分辨是 Qt 的问题还是显示的问题，不如先把 xeyes 跑通。

11.2 安装器起不来：缺 libxkbcommon-x11.so.0 #

跑 Qt 在线安装器：

bash
./qt-opensource-linux-x64-5.12.12.run

会直接报：

text
./qt-opensource-linux-x64-5.12.12.run: error while loading shared libraries: libxkbcommon-x11.so.0: cannot open shared object file: No such file or directory

缺的是 XKB 的 X11 支持库。WSL 默认不装图形依赖，直接装：

bash
sudo apt update
sudo apt install libxkbcommon-x11-0

装完重跑安装器。

11.3 库在但名字对不上 #

先看系统里实际有什么：

bash
ldconfig -p | grep libxkbcommon-x11

如果只有 libxkbcommon-x11.so.1，别急着软链成 .so.0。soname 变了意味着 ABI 不兼容，硬链过去轻则启动崩，重则运行到一半出错。先确认安装包要求的发行版和当前系统是不是一致。

实在要试，只在临时目录做，别写进 /usr/lib：

bash
mkdir -p /tmp/qt-libs
ln -s /path/to/libxkbcommon-x11.so.1 /tmp/qt-libs/libxkbcommon-x11.so.0
LD_LIBRARY_PATH=/tmp/qt-libs ./qt-opensource-linux-x64-5.12.12.run

/path/to/ 换成 ldconfig -p 查到的真实路径。库不在默认搜索路径时，用 LD_LIBRARY_PATH 指过去，比全盘 find / 快得多。要永久生效再写进 ~/.bashrc。

11.4 Qt 应用起不来：xcb 插件 #

text
qt.qpa.plugin: Could not load the Qt platform plugin "xcb" in "" even though it was found.
This application failed to start because no Qt platform plugin could be initialized. Reinstalling the application may fix this problem.

Available platform plugins are: eglfs, linuxfb, minimal, minimalegl, offscreen, vnc, xcb.

Aborted (core dumped)

「even though it was found」说明插件文件在，是它依赖的某个库加载不上。别猜，让 Qt 把依赖链打出来：

bash
QT_DEBUG_PLUGINS=1 ./your_qt_application 2>&1 | grep -i 'cannot load\|not found'

输出点名哪个 .so 找不到，就装哪个包。Ubuntu 和 WSL 上常见的一批：

bash
sudo apt install libxcb-xinerama0 libxcb-xkb1 libxcb-render-util0 libxcb-icccm4 \
  libxcb-image0 libxcb-keysyms1 libxcb-shape0 libxcb-xfixes0 \
  libxkbcommon-x11-0

安装 Qt 程序运行依赖时，这一串基本可以一次装完，省得一个一个试。老教程里那个 sudo apt install -y libxcb* libxkbcommon-x11-0 用的是通配符，装得更全但会拉进来一堆用不上的包，按需选一种。

11.5 插件路径没找对 #

Qt 装在非标准目录时，手动指一下：

bash
export QT_QPA_PLATFORM_PLUGIN_PATH=/opt/Qt5.12.12/plugins/platforms

路径换成实际安装位置。要每次生效就写进 ~/.bashrc：

bash
echo 'export QT_QPA_PLATFORM_PLUGIN_PATH=/opt/Qt5.12.12/plugins/platforms' >> ~/.bashrc
source ~/.bashrc

顺手确认插件本身可读：

bash
ls -l /opt/Qt5.12.12/plugins/platforms/libqxcb.so

11.6 实在没有 X 显示 #

只要程序能跑起来、不需要窗口，可以换 offscreen 后端：

bash
QT_QPA_PLATFORM=offscreen ./your_qt_application

offscreen 不弹窗口，别拿它判断图形界面是否正常。要真窗口，回到 WSLg。

清 ~/.cache/Qt*、检查 Qt 版本和权限这些放最后试，多数情况 QT_DEBUG_PLUGINS=1 已经把原因指出来了。

11.7 中文显示成方框 #

WSL 里没装中文字体，把 Windows 的字体目录挂进来：

bash
sudo mkdir -p /usr/share/fonts/windows
sudo ln -s /mnt/c/Windows/Fonts /usr/share/fonts/windows/fonts
fc-cache -fv

/usr/share/fonts/windows 这类目录默认不存在，软链之前要先建好父目录，否则 ln -s 会报错或链到意外位置。

验证字体能被识别：

bash
fc-list :lang=zh | head

有输出就能用。Qt 应用要重启才会重新读字体缓存。

11.8 几个容易忽略的点 #

OpenGL 后端。 WSLg 下跑 Qt 程序，如果画面花屏、黑屏、卡住，可以试试换渲染后端：

bash
export QT_QUICK_BACKEND=software
export LIBGL_ALWAYS_SOFTWARE=1

软件渲染不掉帧才怪，但能用来判断问题在驱动还是代码。显卡驱动和 wsl --update 都升到最新之后，硬件加速一般能正常工作。

和 Windows 侧 Qt 工具链的区别。 Windows 上装的 Qt 是 mingw 或 msvc 工具链，编出来的是 .exe；WSL 里的 Qt 是 Linux 工具链，编出来的是 ELF 可执行文件。两边不能混用，qmake 不能跨着调，PATH 里混着两个 qmake 是最常见的编译事故。要交叉编译就上交叉编译工具链，别指望直接调 Windows 那个。

CMake 工程。 在 Linux 侧建 build 目录，别在 /mnt/c 下建：

bash
mkdir -p ~/projects/myqt/build && cd ~/projects/myqt/build
cmake .. -DCMAKE_PREFIX_PATH=/opt/Qt5.12.12/gcc_64

理由在第四章讲过：构建过程会生成海量小文件，放在 9P 上会慢到怀疑人生。

11.9 用 VS Code 远程开发 #

最省事的组合是 VS Code + WSL 扩展，在 WSL 终端里 cd ~/projects/myqt 之后跑 code .。窗口开在 Windows 侧，后端跑在 WSL 里，终端、调试器、CMake 插件都在 Linux 侧执行，文件不经过 9P。

十二、易错点速查 #

把全文容易翻车的地方压缩成一张表，出问题先来这扫一眼。

现象 根因 处理
Windows 上 localhost 打不开 WSL 里的服务 NAT 模式，服务绑了 127.0.0.1，或转发没生效 服务绑 0.0.0.0；局域网访问走端口转发；长期方案用镜像模式
局域网别的机器访问不到 NAT 模式下 WSL 有独立 IP，且 Windows 防火墙挡着 netsh interface portproxy 加转发，按需放行
端口转发第二天失效 WSL 重启后 IP 变了 别写死 IP，或改用镜像模式
npm install / git clone 慢得离谱 项目放在 /mnt/c，走 9P 挪到 ~/ 下
Windows 上那个 ext4.vhdx 只涨不缩 默认 vhdx 不回收已删块 .wslconfig 里开 [experimental] sparseVhd=true
内存被 WSL 吃掉不还 默认动态分配且回收不积极 .wslconfig 设 memory=8GB，wsl --shutdown
改了 .wslconfig 没反应 配置只在虚拟机启动时读 wsl --shutdown 后重开终端
打开终端变成 root 导入发行版后默认用户回退 wsl.conf 里设 [user] default，或跑发行版自己的 config --default-user
中文全是方框 没装中文字体 软链 Windows 字体目录，fc-cache -fv
图形程序起不来 是 WSL1，或者在 SSH 会话里 wsl --list --verbose 确认版本；在本地终端里跑
按老教程装了 VcXsrv 还是不行 较新系统自带 WSLg，不需要外挂 X Server 删掉 DISPLAY 手工设置，直接用 WSLg
usbipd 命令找不到 装完没重开终端 重开 PowerShell
attach 报 usbip 客户端没装好 少了 update-alternatives 那步 回第八章 8.5 重做
Windows 里设备突然消失 被 WSL 独占，这是设计行为 用完 usbipd detach 还回去
串口设备节点打不开 当前用户不在 dialout 组 usermod -aG dialout $USER 后重登
sudo apt 不走代理 sudo 不继承环境变量 写 /etc/apt/apt.conf.d/95proxy
代理软件明明开了还是不通 只绑了 127.0.0.1，没允许局域网 打开代理软件的「允许局域网连接」
镜像模式配了不生效 Windows 版本偏老 wsl --version 确认，wsl --update 升级后重试
两个 qmake 打架 WSL 的 PATH 里拼进了 Windows 路径 wsl.conf 里设 appendWindowsPath=false

最后强调一次那个贯穿全文的判断：WSL2 是一台跑在 Hyper-V 上的真 Linux 虚拟机，有自己的内核、文件系统、网络栈。把它当虚拟机看，跨边界的地方就都是可预期的——文件跨边界慢，网络跨边界要转发，USB 跨边界要显式接，资源跨边界要设上限。反过来，凡是你觉得「怎么跟本机不一样」的地方，十有八九是你在跨那条边界。
