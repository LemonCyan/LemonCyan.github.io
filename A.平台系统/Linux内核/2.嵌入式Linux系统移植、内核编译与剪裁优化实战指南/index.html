嵌入式 Linux 系统移植、内核编译与剪裁优化实战指南 #

在嵌入式 Linux 产品开发中，系统移植与裁剪优化是连接底层硬件与上层应用的桥梁。一个未经裁剪的通用内核不仅体积庞大（数兆甚至数十兆字节），在有限的嵌入式 Flash 中极难容纳，而且启动速度迟缓，无法满足工业控制或消费电子对“瞬间开机”的严苛要求。

本指南将基于三星 S3C2410/2440 (ARM9) 平台，带你走过一条完整的嵌入式 Linux 系统构建全链路：从交叉编译环境搭建，到 U-Boot 板级支持包的深度修改，再到内核驱动移植、Busybox 根文件系统制作、Qt 与 tslib 触摸库移植，最后深入探讨如何通过内核裁剪与启动图调优，实现系统秒级自举启动的极限优化。

第一部分：交叉编译链环境搭建 #

在宿主机（通常为 x86 PC）上开发嵌入式代码，必须搭建一套能生成 ARM 目标机可执行程序的交叉编译链（Cross-Compilation Toolchain）。

1.1 安装交叉编译器 #

我们以经典的 arm-linux-gcc-3.4.6-glibc-2.3.6 编译器为例进行演示：

  1. 拷贝与解压：将交叉编译器源码包拷贝至宿主机，并解压安装到系统的 /usr/local/arm 目录下：
    bash
    mkdir -p /usr/local/arm
tar -jxvf arm-linux-gcc-3.4.6-glibc-2.3.6.tar.bz2 -C /usr/local/arm/
  2. 配置环境变量：为了让终端能直接识别 arm-linux- 前缀指令，必须将编译器二进制目录追加到系统的 PATH 变量中。编辑 /etc/profile 文件，在末尾添加：
    bash
    export PATH=/usr/local/arm/gcc-3.4.6-glibc-2.3.6/bin:$PATH
  3. 使能与校验：执行命令使配置立即生效，并运行编译器版本查询命令：
    bash
    source /etc/profile
arm-linux-gcc -v
    若成功安装，终端会输出编译器的具体配置选项、Target 架构为 arm-linux 及其对应的 Glibc 版本号。

第二部分：U-Boot 引导程序移植实战 #

U-Boot 负责初始化基本的 CPU 时钟、外部 SDRAM、并从 Flash 中将 Linux 内核搬运至物理内存运行。本部分以 U-Boot 1.3.2 为基础，为我们的 gdut2410 开发板建立板级支持包。

2.1 建立板级支持目录与配置文件 #

由于我们的开发板硬件布局与三星官方的 smdk2410 极度相似，我们直接以其为模板进行派生：

bash
cd u-boot-1.3.2/
# 1. 建立开发板特定目录
cp -rf board/smdk2410 board/gdut2410
# 2. 建立开发板专用的全局头文件
cp include/configs/smdk2410.h include/configs/gdut2410.h

修改顶层 Makefile，在 smdk2410_config 规则下方，添加我们自己的开发板编译规则：

makefile
gdut2410_config :       unconfig
	@$(MKCONFIG) $(@:_config=) arm arm920t gdut2410 NULL s24x0
  • arm：CPU 架构体系。
  • arm920t：CPU 核心型号。
  • gdut2410：开发板名称（对应 board/gdut2410）。
  • s24x0：三星 SoC 芯片系列。

同时，指定交叉编译器前缀：

makefile
CROSS_COMPILE = arm-linux-

2.2 修改 start.S 与 nand.c 实现 Nand Flash 引导启动 #

原厂的 smdk2410 配置默认只支持从 Nor Flash 启动。由于 Nor Flash 价格昂贵，现代嵌入式系统大多采用 Nand Flash 启动。 当开发板上电且选择 Nand 启动时，CPU 内部硬件会自动将 Nand Flash 前 4KB 的引导代码（即 U-Boot 的前半部分）硬拷贝到 SoC 内部极速 SRAM（称为 Steppingstone）中运行。这段代码必须在 4KB 的物理限制内完成 SDRAM 的初始化，并将 U-Boot 的完整映像（约 150KB）从 Nand 拷贝到外部 SDRAM 中运行。

  1. 修改 board/gdut2410/start.S 汇编引导段： 在汇编阶段关看门狗，屏蔽中断，并跳入物理时钟初始化。在进入 C 语言入口前，添加 Nand 拷贝跳转指令：

    # 💡 屏蔽看门狗与中断保护
ldr     r0, =WTCON
mov     r1, #0x0
str     r1, [r0]

# 💡 初始化时钟比 (FCLK:HCLK:PCLK = 1:2:4, 主频约 202MHz)
ldr     r0, =CLKDIVN
mov     r1, #0x3
str     r1, [r0]

# 💡 执行 SDRAM 内存控制器初始化
bl      cpu_init_crit

# 💡 增加 Nand Boot 拷贝代码段
ldr     sp, =0x33f00000        ; 设置临时栈
mov     r0, #0x0               ; 参数1: Nand 源地址 (0x0)
ldr     r1, =0x33f00000        ; 参数2: SDRAM 目的地址 (U-Boot装载地址)
mov     r2, #0x30000           ; 参数3: 拷贝长度 (192KB)
bl      nand_read_ll           ; 调用底层 C 语言 Nand 读函数

# 跳转到真正装载完毕的 SDRAM U-Boot 代码入口处继续运行
ldr     pc, =stack_setup

  2. 编写 board/gdut2410/nand.c 核心驱动： 为了在没有加载复杂 OS 的情况下直接读取 Nand 芯片，我们手写底层的 Nand Flash 控制器读写 C 代码：

    c
    #define NFCONF (*(volatile unsigned int *)0x4E000000)
#define NFCMD  (*(volatile unsigned char *)0x4E000004)
#define NFADDR (*(volatile unsigned char *)0x4E000008)
#define NFDATA (*(volatile unsigned char *)0x4E00000C)
#define NFSTAT (*(volatile unsigned char *)0x4E000010)

// 💡 简单的 Nand 等待就绪函数
static void nand_wait(void) {
    int i;
    while (!(NFSTAT & 0x1));
    for (i = 0; i < 10; i++);
}

// 💡 低级 Nand 读取主函数：将 Nand 指定偏移拷贝到 RAM
int nand_read_ll(unsigned char *buf, unsigned long start_addr, int size) {
    int i, j;
    if ((start_addr & 511) != 0 || (size & 511) != 0) {
        return -1; // 💡 必须以 512 字节（扇区大小）对齐
    }
    
    // 开启 Nand 控制器，进行片选
    NFCONF &= ~0x800; // 选通芯片
    
    for (i = start_addr; i < (start_addr + size); i += 512) {
        // 发送读取命令 0x00
        NFCMD = 0x00;
        
        // 发送列地址 (页内偏移) 与行地址 (页号)
        NFADDR = 0;
        NFADDR = (i >> 9) & 0xFF;
        NFADDR = (i >> 17) & 0xFF;
        NFADDR = (i >> 25) & 0xFF;
        
        nand_wait(); // 💡 等待 Nand 物理层数据加载就绪
        
        // 循环读取一页（512 字节）数据至 SDRAM
        for (j = 0; j < 512; j++, buf++) {
            *buf = NFDATA;
        }
    }
    NFCONF |= 0x800; // 💡 撤销片选，关闭控制器以节能
    return 0;
}

2.3 修改配置头文件与编译 #

打开 include/configs/gdut2410.h，更改环境变量在 Flash 中的存储地址。因为我们要从 Nand 启动，必须废弃原有的 Nor Flash 存储配置，改为：

c
#define CFG_ENV_IS_IN_NAND      1
#define CFG_ENV_OFFSET          0x30000   /* 💡 在 Nand 中的存储地址 */
#define CFG_ENV_SIZE            0x10000   /* 64KB */

配置完成后，在控制台执行：

bash
make gdut2410_config
make

编译成功后，将在根目录下生成 u-boot.bin 文件。我们通过 JTAG 仿真器或通过已有的 Bootloader 将其烧写到开发板 Nand Flash 的 0x00000000 起始地址处。

第三部分：Linux 内核移植与设备驱动集成 #

我们选用经典的 Linux 2.6.24.4 内核，对其进行适配移植，使其能够支持 Nand 分区、LCD 显示屏、触摸屏和网卡。

3.1 修改内核架构编译配置 #

解压内核源码包后，打开顶层 Makefile，修改体系结构及交叉编译器路径：

makefile
# 💡 改为 arm 架构和 arm-linux- 交叉编译器
ARCH            ?= arm
CROSS_COMPILE   ?= arm-linux-

3.2 移植 Nand Flash 驱动并更改分区信息 #

为了让内核能够正确读取 Flash 中的文件系统，必须在板级初始代码中声明 Nand Flash 的分区情况。编辑 arch/arm/mach-s3c2410/mach-smdk2410.c，添加分区结构体描述：

c
#include <linux/mtd/partitions.h>
#include <asm/arch/nand.h>

// 💡 声明 Nand Flash 分区表，必须与 Bootloader 的烧写分区严格一致！
static struct mtd_partition smdk_default_nand_part[] = {
    [0] = {
        .name   = "bootloader",
        .size   = 0x00040000,      // 256KB 用于 U-Boot
        .offset = 0,
    },
    [1] = {
        .name   = "param",
        .size   = 0x00020000,      // 128KB 存放 U-Boot 环境变量
        .offset = 0x00040000,
    },
    [2] = {
        .name   = "kernel",
        .size   = 0x00200000,      // 2MB 存放内核镜像 (uImage)
        .offset = 0x00060000,
    },
    [3] = {
        .name   = "rootfs",
        .size   = MTDPART_SIZ_FULL, // 💡 剩余的所有空间划归文件系统
        .offset = 0x00260000,
    },
};

// 💡 注册 Nand 平台设备控制器信息
static struct s3c2410_platform_nand smdk_nand_info = {
    .tacls      = 20,
    .twrph0     = 60,
    .twrph1     = 20,
    .nr_sets    = 1,
    .sets       = & (struct s3c2410_nand_set) {
        .nr_partitions  = ARRAY_SIZE(smdk_default_nand_part),
        .partitions     = smdk_default_nand_part,
    },
};

在底层 smdk2410_devices 指针数组中，将 Nand 控制器设备挂载进去，保证内核启动阶段能够通过平台设备总线匹配并装载 s3c2410-nand 核心驱动。

3.3 移植 LCD 液晶屏与 CS8900 网卡驱动 #

  1. LCD 驱动适配： 为了使开发板的液晶屏（分辨率 320x240）正常显示，编辑 mach-smdk2410.c 中的 s3c2410fb_mach_info 控制器配置：
    c
    #include <asm/arch/fb.h>

static struct s3c2410fb_mach_info smdk2410_lcd_platdata __initdata = {
    .regs   = {
        .lcdcon1 = S3C2410_LCDCON1_TFT16BPP | S3C2410_LCDCON1_TFT | S3C2410_LCDCON1_CLKVAL(4),
        .lcdcon2 = S3C2410_LCDCON2_VBPD(1) | S3C2410_LCDCON2_LINEVAL(239) | S3C2410_LCDCON2_VFPD(5),
        .lcdcon3 = S3C2410_LCDCON3_HBPD(36) | S3C2410_LCDCON3_HOZVAL(319) | S3C2410_LCDCON3_HFPD(19),
        .lcdcon4 = S3C2410_LCDCON4_HSPW(5),
    },
    .width  = 320,
    .height = 240,
    .xres   = {320, 320, 1},
    .yres   = {240, 240, 1},
    .bpp    = {16, 16, 1},
};
  2. CS8900 网卡驱动移植： CS8900 挂载在 S3C2410 的 Bank3 内存片选总线上。我们需要在驱动初始化阶段通过 ioremap 映射对应的 IO 端口，并在 drivers/net/cs8900.c（或相应网卡驱动）中配置物理片选基地址 0x18000300 以及对应的外部中断号 IRQ_EINT9。

3.4 深入设备驱动开发：手写触摸屏 ADC 中断服务程序 #

为了保证物理触摸屏能精准将硬件电压转换为输入坐标并提交给用户空间（tslib），我们在内核中实现一个经典的 S3C2410 触摸屏中断服务程序（ISR）处理逻辑：

c
#include <linux/input.h>
#include <linux/adc.h>
#include <asm/io.h>
#include <asm/arch/regs-adc.h>

static struct input_dev *ts_input_dev; // 输入子系统设备指针
static void __iomem *adc_base;         // 寄存器映射基地址

// 💡 触摸屏中断顶半部 (ISR)：当屏幕被按下或抬起时触发
static irqreturn_t s3c2410_ts_irq(int irq, void *dev_id) {
    unsigned long adccon, adcdat0, adcdat1;
    
    // 💡 1. 读取当前的坐标物理数据寄存器
    adcdat0 = readl(adc_base + S3C2410_ADCDAT0);
    adcdat1 = readl(adc_base + S3C2410_ADCDAT1);
    
    // 💡 2. 判定是按下还是抬起
    if (adcdat0 & S3C2410_ADCDAT0_UPDOWN) {
        // 笔尖抬起 (Pen Up)
        input_report_key(ts_input_dev, BTN_TOUCH, 0); // 报告按键状态为 0
        input_report_abs(ts_input_dev, ABS_PRESSURE, 0);
        input_sync(ts_input_dev);                     // 发送同步帧
        
        // 重新配置控制器进入“等待按下中断”模式
        writel(WAIT_FOR_PENDOWN_INT, adc_base + S3C2410_ADCTSC);
    } else {
        // 笔尖按下 (Pen Down)，启动 ADC 转换获取高精度 XY 坐标
        adccon = readl(adc_base + S3C2410_ADCCON);
        writel(adccon | S3C2410_ADCCON_ENABLE_START, adc_base + S3C2410_ADCCON); // 启动转换
        
        // 启动 ADC 后，内核会等待 ADC 转换结束中断 (ADC_IRQ) 触发后，在底半部报告具体的 X/Y 轴绝对值坐标：
        // input_report_abs(ts_input_dev, ABS_X, x_value);
        // input_report_abs(ts_input_dev, ABS_Y, y_value);
        // input_report_key(ts_input_dev, BTN_TOUCH, 1);
        // input_sync(ts_input_dev);
    }
    return IRQ_HANDLED;
}

通过输入子系统接口，驱动程序可以将底层的模拟电信号转变为标准的 Linux Input Event 帧，供应用层直接无缝使用。

3.5 内核图形裁剪与编译 #

执行默认开发板模板配置，然后进入图形界面进行深度微调裁剪：

bash
make s3c2410_defconfig
make menuconfig

在图形菜单中：

  • System Type ---> 确认勾选 SMDK2410 / SMDK2440 支持。
  • Device Drivers ---> Graphics support ---> 选中 Support for frame buffer devices 并勾选 S3C2410 LCD Driver 以及 Bootup logo (可在开机时在 LCD 上显示可爱的 Linux 企鹅 logo)。
  • File systems ---> 勾选支持 YAFFS2 (Nand 专用文件系统) 以及 NFS。

退出保存后，执行：

bash
make zImage

为了让 U-Boot 能正常引导 Linux 内核，必须使用 U-Boot 源码编译生成的 mkimage 工具为 zImage 添加一个 64 字节的特定引导头部：

bash
mkimage -A arm -O linux -T kernel -C none -a 0x30008000 -e 0x30008000 -n "Linux Kernel" -d arch/arm/boot/zImage uImage
  • -a 0x30008000 : 指定内核的加载地址。
  • -e 0x30008000 : 指定内核的入口执行地址。 生成的 uImage 即可通过 TFTP 或 NFS 直接下载并烧写。

第四部分：根文件系统制作与 Qt / Tslib 界面移植 #

根文件系统（Rootfs）是 Linux 系统赖以运行的用户空间目录大本营。我们使用 Busybox 来精简生成各种核心命令工具。

4.1 使用 Busybox 构造核心文件系统目录 #

  1. 编译 Busybox： 解压 busybox-1.9.2.tar.bz2，在 Makefile 中指定架构和编译器：

    makefile
    ARCH ?= arm
CROSS_COMPILE ?= arm-linux-

    执行配置并编译：

    bash
    make menuconfig  # 💡 建议勾选 "Build BusyBox as a static binary" (静态链接，避免由于缺少依赖库导致开机 panic)
make
make install     # 默认会在当前目录生成 _install 文件夹
    ✦提示

    如果为了节省空间而选择动态链接编译 BusyBox，则必须将交叉编译器工具链中的动态链接器和核心共享库手动拷贝至开发板的 /lib 目录中。拷贝命令示例：

    bash
    cp -d /usr/local/arm/gcc-3.4.6-glibc-2.3.6/arm-linux/lib/ld*.so* /rootfs/lib/
cp -d /usr/local/arm/gcc-3.4.6-glibc-2.3.6/arm-linux/lib/libc*.so* /rootfs/lib/
cp -d /usr/local/arm/gcc-3.4.6-glibc-2.3.6/arm-linux/lib/libm*.so* /rootfs/lib/
cp -d /usr/local/arm/gcc-3.4.6-glibc-2.3.6/arm-linux/lib/libdl*.so* /rootfs/lib/

    -d 参数极为关键，它能够保留动态链接库的软链接属性，避免拷贝后软链接失效转为实体文件，导致文件系统体积极速膨胀。 2. 创建系统基础骨架： 将 _install 目录下的所有文件拷贝到我们的根文件系统目标区（假设为 /rootfs），并手动补齐缺少的虚拟目录和设备节点：

    bash
    cd /rootfs
mkdir -p dev etc/init.d lib proc sys usr tmp var root

    💡 必须手动创建控制台和空设备节点，否则系统启动会崩溃！ #

    sudo mknod dev/console c 5 1 sudo mknod dev/null c 1 3

4.2 编写系统启动配置文件 #

当内核引导 Rootfs 后，会执行第一个用户进程 /sbin/init，它根据 /etc/inittab 配置文件来调用启动脚本：

  1. /etc/inittab (环境初始化配置)：
    ::sysinit:/etc/init.d/rcS
console::askfirst:-/bin/sh
::ctrlaltdel:/sbin/reboot
::shutdown:/bin/umount -a -r
  2. /etc/init.d/rcS (启动初始化脚本)：
    bash
    #!/bin/sh
# 💡 挂载虚拟文件系统
mount -a
mkdir -p /dev/pts
mount -t devpts devpts /dev/pts

# 💡 动态热插拔处理：借助 mdev 实现设备节点自动生成
echo /sbin/mdev > /proc/sys/kernel/hotplug
mdev -s

# 配置回环网络与网卡 IP
ifconfig lo 127.0.0.1
ifconfig eth0 192.168.2.17 up
  3. /etc/fstab (文件系统挂载表)：
    #device     mount-point    type      options    dump  fsck-order
proc        /proc          proc      defaults   0     0
sysfs       /sys           sysfs     defaults   0     0
tmpfs       /tmp           tmpfs     defaults   0     0

4.3 移植 Tslib 触摸校准库与 Qt 4 动态运行库 #

为了让开发板的触摸屏能够准确操作 Qt 的图形按钮，必须移植 tslib 进行五点电阻校准：

  1. 编译与安装 tslib：
    bash
    tar -jxvf tslib-1.4.tar.bz2
cd tslib-1.4/
./autogen.sh
# 配置交叉编译安装路径
./configure --host=arm-linux --prefix=/rootfs/usr/local/tslib
make
make install
  2. 编译 QT/E 库并拷贝： 在开发机上交叉编译 qt-embedded-linux-opensource-src-4.5.0，将其输出的 lib 目录下的动态库（例如 libQtGui.so, libQtCore.so）全部拷贝至开发板的 /rootfs/usr/local/qt/lib 目录下。
  3. 在开发板 /etc/profile 中配置触摸与 Qt 环境变量：
    bash
    export TSLIB_ROOT=/usr/local/tslib
export TSLIB_TSDEVICE=/dev/input/event0      # 💡 触摸屏物理输入节点
export TSLIB_CALIBFILE=$TSLIB_ROOT/etc/pointercal
export TSLIB_CONFFILE=$TSLIB_ROOT/etc/ts.conf
export TSLIB_PLUGINDIR=$TSLIB_ROOT/lib/ts
export LD_LIBRARY_PATH=$TSLIB_ROOT/lib:/usr/local/qt/lib:$LD_LIBRARY_PATH

export QWS_MOUSE_PROTO="Tslib:/dev/input/event0" # 💡 让 Qt 鼠标指针绑定 tslib
export QWS_KEYBOARD="TTY:/dev/tty1"

运行 /usr/local/tslib/bin/ts_calibrate，LCD 屏幕上会显示五个十字靶心，用触摸笔依次点击校准后，系统会在 pointercal 文件中写入矩阵转换系数，此后 Qt 程序的触摸操作即可达到像素级精准度！

4.4 常见文件系统挂载故障排除 (NFS 与 YAFFS2 实战) #

在开发板自举的最后一阶段，挂载 Rootfs 经常遇到各种崩溃，以下是两类经典崩溃的深层原因及排查方案：

  1. 崩溃提示：Kernel Panic: VFS: Unable to mount root fs on unknown-block(2,0)
    • 根源分析：
      1. 内核没有编入对应的物理文件系统驱动（例如 YAFFS2 驱动未被勾选，却指定以 rootfstype=yaffs2 挂载）。
      2. U-Boot 环境变量指定的挂载分区编号错误（例如 Rootfs 在 Nand 第 3 分区，但 bootargs 里错写成 root=/dev/mtdblock2，导致内核去挂载只存有 uImage 的 kernel 分区）。
  2. 崩溃提示：NFS Boot error: DHCP/bootp failed, or Permission Denied
    • 根源分析：
      1. 宿主机中 NFS 服务器配置文件 /etc/exports 路径或 IP 网段配置不匹配。
      2. /etc/exports 中未加 no_root_squash 选项。如果缺此选项，嵌入式端以 root 用户身份建立虚拟节点时，主机会将其降权压制为 nobody 用户，导致权限不足直接挂载失败崩溃。

第五部分：内核启动时间与体积极致裁剪优化 #

当开发板的功能全部跑通后，最终的产品化开发必须要对内核进行极致的“瘦身”与“加速”。

5.1 initcall_debug 启动时间分析 #

为了揪出到底是哪个内核初始化函数拖慢了开机速度，我们在内核启动命令行中添加：

bash
initcall_debug loglevel=9
  1. 获取时间戳日志：内核会在控制台输出每一个初始化函数（initcall）开始和结束的时间戳（微秒级）。
  2. 生成启动分析图： 拷贝板端串口输出的启动日志并保存为 boot.log。在宿主机上，进入 Linux 内核源码目录，运行编译脚本自带的 Perl 工具：
    bash
    scripts/bootgraph.pl boot.log > boot.svg
    用矢量图浏览器（如 Inkscape 或 Chrome）打开生成的 boot.svg，整个内核初始化阶段的时间占比、探测（probe）阻塞热点一目了然。

5.2 极致裁剪技巧与配置优化 #

根据启动图和产品实际需求，我们进行深度的功能阉割：

  1. 精简驱动与硬件检测：
    • 通过查阅相关子目录的 Makefile 和 Kconfig，在 make menuconfig 中剔除所有开发板未焊接的驱动（例如：无用的 PCIE 驱动、USB 网卡驱动、多余的显示芯片支持）。
    • SMP 初始化：即使开发板只有一个 CPU 核心，内核默认可能也会启用对称多处理器支持（CONFIG_SMP）。关闭它！这不仅能直接让编译出的内核大小减少约 180KB，还能省去多核初始化握手的等待时间。
  2. 选用微型替代算法：
    • 将内核通用的伙伴系统/SLAB 物理页分配算法，替换为专门为嵌入式低内存设计的 CONFIG_SLOB 机制，可进一步优化页表常驻大小。
    • 使能 CONFIG_EMBEDDED，允许对内核的底层细节（如内核日志缓冲区大小 CONFIG_LOG_BUF_SHIFT）进行极限微调。

5.3 优化延时与控制台 #

  1. 预置 lpj（loops_per_jiffy）参数： 内核每次引导启动时，为了校准 udelay() 精确延迟，都会执行一段耗时较长（约 200ms）的延迟循环校准（Calibrating delay loop）。
    • 实战做法：我们在第一次开机时，在内核串口终端中找到如下日志： Calibrating delay loop... 996.14 BogoMIPS (lpj=4980736)
    • 记录下这个 lpj 数值。随后在 U-Boot 中，将此参数固化到内核启动命令行（bootargs）中： setenv bootargs 'console=ttySAC0,115200 root=/dev/mtdblock3 lpj=4980736'
    • 效果：再次开机时，内核会直接跳过耗时的物理校准（显示 Calibrating delay loop (skipped) preset value），直接开机，瞬间节省近五分之一的开机耗时！
  2. 静默控制台： 控制台串口输出（十分低速且会发生总线阻塞）在量产产品中并无用处。在内核命令行中添加 quiet 参数可以静音输出；或者在 menuconfig 中直接设置 CONFIG_PRINTK=n。这虽然会丢失 dmesg 功能，但能瞬间将引导时间再次缩短约 0.5 秒 以上。

5.4 各种压缩算法在嵌入式 ARM 平台上的性能测试 #

内核被搬运到 SDRAM 前，必须在 Flash 中以压缩包形式存放。不同的压缩算法在“解压速度（依赖 CPU 主频）”与“读取速度（依赖 Nand 接口速率）”之间各执一词。 以下是在基于 TI AM335x (ARM Cortex-A8, 主频 1 GHz) 平台下运行 Linux 5.1 的内核镜像实测数据：

压缩算法类型 生成内核镜像体积 (Bytes) Nand Flash 拷贝耗时 (s) 内核 CPU 解压启动耗时 (s) 综合启动耗时 (s)
Gzip (默认) 2,350,336 0.208 1.243 1.451
LZMA 1,777,000 0.158 2.009 2.167
XZ 1,720,120 0.154 1.845 1.999
LZO 2,533,872 0.224 1.192 1.416
LZ4 2,716,752 0.241 1.221 1.462
  • 结论分析：
    • XZ / LZMA 算法拥有极高的压缩比，内核体积最小（节省 Flash 空间），但解压阶段需要进行复杂的浮点和字典树计算，对于低主频 ARM 来说，CPU 解压时间反而大大拉长，得不偿失。
    • LZO / Gzip 在压缩体积和解压算法开销上取得了最佳平衡。在 1GHz CPU 下，LZO 凭借极速的解密算法，综合启动用时最短（1.416s）。
    • 在产品优化收尾阶段，建议根据自己开发板的 CPU 性能与 Flash 读取带宽，对各算法进行交叉对比，选出最契合自身硬件的解压缩算法。
