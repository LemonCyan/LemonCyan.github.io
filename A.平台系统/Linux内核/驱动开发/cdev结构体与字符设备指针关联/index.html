cdev结构体与字符设备指针关联

Linux字符设备驱动深度解析：struct inode、struct file与struct cdev三位一体指针关联机制 #

在编写 Linux 字符设备驱动时，我们常说“注册一个 cdev，并实现它的 file_operations 接口”。然而，当应用层执行 fd = open("/dev/my_cdev", O_RDWR) 时，内核是如何在庞大的虚拟文件系统（VFS）中，精准寻找到我们注册的这个 cdev，又是如何把我们定义的各种 read/write 接口和该文件关联起来的呢？

这涉及到内核中三个至关重要的数据结构：struct inode（文件节点描述）、struct file（打开的文件实例）与 struct cdev（设备结构体）的指针绑定过程。

一、 内核三者关联模型 (三位一体指针图) #

当进程打开一个字符设备文件时，内核在底层建立了如下的指针指向与替换机制：

 用户空间进程                     内核 VFS 空间
  +----------+                   struct file (由 fd 索引)
  |  fd = 0  |------------------> [ *f_op       ] ------------+
  |  fd = 1  |                    [ private_data ]             |
  +----------+                          |                      |
                                        v (通常在 open 中指向)  | (调用替换)
                                  [ struct cdev ]              |
                                        ^                      |
                                        | i_cdev               v
                                 struct inode            struct file_operations
                                  [ *i_cdev ]-----------> [ .open  = hello_open  ]
                                  [ i_rdev  ] (设备号)    [ .read  = hello_read  ]
                                                          [ .write = hello_write ]

各结构体职责分工： #

  1. struct inode：代表磁盘或 VFS 中的物理节点，在系统中是唯一的。一旦设备节点被创建（mknod），该 inode 在内核中就拥有一个固定的物理设备号 i_rdev，以及一个指向字符设备控制块的指针 i_cdev。
  2. struct file：代表一个被打开的文件实例。每次调用 open()，内核都会在主存中新建一个 struct file。所以一个 inode 可以对应多个 struct file。它里面包含重要的读写位置偏移 f_pos 以及关联的操作函数指针 f_op。
  3. struct cdev：代表我们编写的字符设备驱动实体，它包含了设备的主次设备号和关联的 struct file_operations 动作集合。

二、 💡 核心关联步骤：字符设备是如何被“打开”的？ #

当应用层发起 open() 系统调用，内核的执行链路如下：

1. 设备号匹配与 inode 定位 #

  1. 用户打开 /dev/my_cdev，VFS 根据路径找到对应的磁盘节点，并在内存中建立一个描述该文件的 struct inode。
  2. 内核识别出该 inode 的 i_mode 是字符设备（S_IFCHR）。
  3. 内核利用 inode->i_rdev（设备号），在全局字符设备哈希表 cdev_map 中检索。
  4. 一旦检索到驱动先前通过 cdev_add() 注册的 struct cdev 实例，内核就将 inode->i_cdev 指针指向这个驱动实体：
    c
    // 内核底层绑定
inode->i_cdev = cdev_p;

2. 操作方法集的“偷天换日” (chrdev_open) #

  1. 在 VFS 刚新建 struct file 时，其 file->f_op 指向的是通用字符设备空壳操作集 def_chr_fops，其唯一的动作就是 .open = chrdev_open。
  2. 当调用执行 chrdev_open 时，内核开始执行“指针替换”：
    c
    static int chrdev_open(struct inode *inode, struct file *filp)
{
    struct cdev *p;
    // 💡 通过 inode 获取之前绑定的 cdev 实体
    p = inode->i_cdev; 
    
    // 💡 将 file 的操作指针偷天换日，替换为我们驱动中编写的 file_operations!
    filp->f_op = fops_get(p->ops); 
    
    // 💡 调用驱动中具体的真正 open 函数
    if (filp->f_op->open) {
        return filp->f_op->open(inode, filp);
    }
    return 0;
}
  3. 替换完成后，应用层后续调用 read(fd, ...)，就会直接穿透到 filp->f_op->read，即我们驱动实现的具体的 hello_read，完成了驱动绑定的完整闭环。

三、 驱动编写中的黄金法则：private_data #

在驱动开发的 open 和 read/write 接口中，我们经常能看到这样的指针传递操作：

c
// 1. 在 open 接口中：利用 container_of 得到设备结构体，并存放在 file 中
static int hello_open(struct inode *inode, struct file *file)
{
    struct my_char_dev *dev;
    
    // 通过 inode 中的 i_cdev 指针，反向计算出包含它的自定义设备大结构体指针
    dev = container_of(inode->i_cdev, struct my_char_dev, cdev);
    
    // 🔑 存入 file 的 private_data 中
    file->private_data = dev; 
    return 0;
}

// 2. 在 read 接口中：直接取出使用，无需再次计算
static ssize_t hello_read(struct file *file, char __user *user_buf, size_t size, loff_t *pos)
{
    // 🔑 轻松取出设备对象
    struct my_char_dev *dev = file->private_data; 
    
    // 接下来可以直接操作 dev->buf, dev->sem 等私有字段了...
    return size;
}

通过 file->private_data 承载设备指针，使得驱动中的不同操作接口能够安全、跨函数地共享当前操作设备的上下文环境，是编写高质量多设备并发字符驱动的核心黄金法则。
