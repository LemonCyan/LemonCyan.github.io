Linux 驱动开发核心技术笔记：中断、内存、设备模型与动态节点 #

在 Linux 驱动开发里，中断、内存管理和设备模型是绕不过去的三座大山。咱们今天就把这些底层机制理一遍，看看怎么手搓驱动代码、避开那些恶心的坑点。

一、 中断处理机制与程序编写 #

中断机制提供了硬件和软件之间异步传递信息的方式。当硬件设备发生某些事件时，会通过中断通知 CPU，让内核停下手中的活去优先处理设备请求。

1. 注册与释放中断处理程序 #

在驱动中，咱们通常在设备初始化或者在用户 open 打开设备时安装中断处理程序，在 close 释放设备时将其卸载。

c
// 申请 IRQ（注册中断）
int request_irq(unsigned int irq,
                irqreturn_t (*handler)(int, void *),
                unsigned long irqflags,
                const char *devname,
                void *dev_id);
  • 参数说明：
    • irq：申请的硬件中断号。
    • handler：中断处理函数指针。
    • irqflags：中断标志，如共享中断的 IRQF_SHARED（老版本中为 SA_SHIRQ）。
    • devname：设备名称，会显示在 /proc/interrupts 中。
    • dev_id：传递给中断处理程序的私有数据指针，在共享中断时也是区分不同设备的唯一标识。
  • 释放 IRQ：
    c
    void free_irq(unsigned int irq, void *dev_id);

2. 使能与屏蔽中断源 #

对于单根中断线的控制，内核提供了以下三个函数：

c
void disable_irq(int irq);
void disable_irq_nosync(int irq);
void enable_irq(int irq);
  • disable_irq()：屏蔽指定中断并等待当前已触发的中断处理程序执行完毕再返回。在中断上下文调用它容易引起死锁，千万注意。
  • disable_irq_nosync()：屏蔽中断后立即返回，不等待当前处理程序执行完。
  • 这三个函数是作用于可编程中断控制器（PIC）的，因此对系统内的所有 CPU 都生效。
  • 全局中断控制：虽然 cli()（禁中断）和 sti()（使能中断）在老内核中被用来控制全局中断，但现代驱动开发中，咱们基本不需要用禁用/启用全局中断这种简单粗暴的形式来处理竞态，而是使用自旋锁等更爽的并发控制手段。

3. 中断共享机制 #

多个物理设备共享一根中断线时，申请中断必须带上共享标志：

c
// 申请共享中断
result = request_irq(sh_irq, xxx_interrupt, IRQF_SHARED, "xxx", xxx_dev);

在共享中断的处理函数中，第一步必须通过读取设备内部的状态寄存器判断这个中断是不是本设备产生的。如果不是，必须识相地返回 IRQ_NONE 让内核去问下一个设备；如果是，处理完后返回 IRQ_HANDLED。

c
irqreturn_t xxx_interrupt(int irq, void *dev_id)
{
    int status = read_int_status(); /* 获取中断源状态 */
    if (!is_myint(dev_id, status)) { /* 判断是否是本设备中断 */
        return IRQ_NONE;             /* 立即返回，不是我的不管 */
    }
    /* 处理本设备中断业务... */
    return IRQ_HANDLED;
}

4. Linux 中断处理子系统原理 #

内核处理中断的流水线大致如下：

  1. 检测与转换：系统检测到中断后，首先读取可编程中断控制器的状态寄存器确定中断源，并将其转换为 irq_desc 向量表（老版本中为 irq_action 向量表）的偏移。
  2. 遍历执行：通过该偏移找到对应的中断处理描述结构，依次调用挂在该中断线上的所有设备注册的中断处理例程。
  3. 分层处理：由于中断处理程序（ISR）运行在中断上下文，不能睡眠、不能与用户空间交换数据、不能调用 schedule() 放弃调度，所以处理原则是越快越好。冗长耗时的计算必须交由底半部（Tasklet 或工作队列）延迟执行。

二、 驱动程序的上/下半部与延缓执行机制 #

为了解决“既要中断处理快，又要处理大量数据”的矛盾，Linux 将中断分为上半部（Top Half）和下半部（Bottom Half）。

  • 上半部：也就是实际的 ISR。只做最紧急的事，比如把设备数据拷贝到缓冲区、清除中断标志，然后快速返回。
  • 下半部：被上半部调度，在稍后更安全、CPU 空闲的时间被调用，执行剩余的耗时工作（如数据处理、唤醒进程）。

1. Tasklet 延时机制 #

Tasklet 运行于中断上下文，其处理函数中绝不能睡眠。

c
// 1. 定义处理函数
void my_tasklet_func(unsigned long data);

// 2. 定义并静态初始化 tasklet 结构，与函数绑定
DECLARE_TASKLET(my_tasklet, my_tasklet_func, data);

// 3. 在上半部中调度 tasklet 执行
tasklet_schedule(&my_tasklet);

2. 工作队列（Workqueue）机制 #

工作队列运行于进程上下文。因此，它的处理函数中允许睡眠、阻塞、申请大内存，用起来非常爽。

c
// 1. 定义工作结构体
struct work_struct my_wq;

// 2. 定义处理函数
void my_wq_func(struct work_struct *work);

// 3. 初始化工作队列并绑定函数
INIT_WORK(&my_wq, my_wq_func);

// 4. 调度工作队列
schedule_work(&my_wq);

三、 内核定时器与时间延迟机制 #

1. 系统时间流与获取 #

  • jiffies：内核时间计算的基石。每隔一个固定的时间（定时器中断）jiffies 就会加 1。
  • HZ：一秒内产生定时器中断的次数，在 <linux/param.h> 中定义。jiffies 增加 1 代表过了 1/HZ 秒。
  • 获取当前时间：
    • 一般通过读取全局变量 jiffies 测量时间间隔。
    • 获取更精确的绝对时间可使用 do_gettimeofday()（微秒级精度，填充 struct timeval）或 current_kernel_time()。

2. 长延迟与短延迟 #

  • 长延迟（大于若干个 jiffies）：
    • 忙等待：使用 time_before(jiffies, timeout) 或 time_after(jiffies, timeout)。
    • 睡眠等待：schedule_timeout(delay_jiffies) 或 sleep_on_timeout()。
  • 短延迟（短于一个 jiffies，微秒/毫秒级）：
    • 忙等待函数，非常消耗 CPU 资源：
      c
      void udelay(unsigned long usecs); // 微秒延迟
void mdelay(unsigned long msecs); // 毫秒延迟（通过嵌套udelay实现）

3. 内核定时器 #

内核定时器只执行一次，超时后被内核调用。其超时值是一个绝对的 jiffies 值。

c
// 1. 定义定时器
struct timer_list my_timer;

// 2. 初始化定时器（通常使用 setup_timer）
setup_timer(&my_timer, my_timer_function, data);

// 3. 设置过期时间并添加到内核
my_timer.expires = jiffies + HZ; // 延迟 1 秒
add_timer(&my_timer);

// 4. 修改定时器（如果需要重新定时）
mod_timer(&my_timer, jiffies + new_delay);

// 5. 删除定时器
del_timer(&my_timer);

四、 内核地址空间与内存使用 #

1. ARM 处理器内存管理（MMU） #

ARM 系统中的内存管理单元（MMU）主要负责：

  1. 实现虚拟地址到物理地址的页式映射。
  2. 存储器访问权限的控制。
  3. 设置虚拟存储空间的缓冲特性。

2. 内核空间内存分配方式 #

不同于用户空间的 malloc()，内核分配内存有以下几种硬核武器：

分配方式 物理连续性 适用大小 允许睡眠/阻塞 典型场景
kmalloc 连续 小于 128KB 可配置（取决于 FLAG） 频繁申请的小型控制结构体
__get_free_pages 连续 整页（2order 页） 可配置 大缓冲区申请
vmalloc 不连续（仅虚拟连续） 很大 必须能睡眠，中断中禁用 装载内核模块、超大缓冲区
(1) 分配标志（GFP Flags）
  • GFP_KERNEL：最常用的分配标志，可能会阻塞和睡眠，直到有空闲物理内存。
  • GFP_ATOMIC：绝对不会睡眠和阻塞。用于中断处理程序等不能睡眠的上下文中。如果内存不足，会直接返回失败。
  • __GFP_DMA：指定在 DMA 区域分配内存。
(2) 伙伴系统按页分配
c
unsigned long __get_free_pages(gfp_t gfp_mask, unsigned int order);
// 释放函数
void free_pages(unsigned long addr, unsigned long order);
  • 分配的页数为 2order。在 4KB 页的系统上，最大 order 限制通常是 10 或 11。
  • 模块卸载时必须手动调用 free_pages 释放，内核不会帮你擦屁股。
(3) 后备高速缓存（Slab/Slob/Slub Allocation）

如果驱动程序频繁分配和释放相同大小的内存块，应该自己创建一个专属内存池（Kmem Cache），这比直接用 kmalloc 效率高得多。可通过 /proc/slabinfo 跟踪其状态。

(4) 引导时内存分配（Boot-time Allocation）

在系统引导阶段（内存管理系统还没初始化完），如果需要极大的物理连续内存，可以通过 alloc_bootmem() 族函数直接强行保留物理内存，这能直接绕过 __get_free_pages 的大小限制。

五、 设备 I/O、内存映射（mmap）与 DMA #

在对吞吐量要求极高的设备驱动中（如网卡、显卡、视频采集卡），频繁在用户空间和内核空间拷贝数据是恶魔级别的性能杀手。

1. 应用层 mmap 映射 #

mmap() 允许用户进程直接将设备内存映射到自己的虚拟地址空间，读写这片内存就相当于直接读写设备，实现零拷贝。

c
void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);
  • 映射的内存大小必须是页面大小的整数倍。
  • 只有字符设备、块设备等随机访问设备支持映射，面向流的设备（如串口、管道）无法进行映射。

2. 驱动中 mmap 的实现 #

驱动的核心工作是为用户进程的映射请求构造页表，主要调用 remap_pfn_range()：

c
int remap_pfn_range(struct vm_area_struct *vma, 
                    unsigned long addr,
                    unsigned long pfn, 
                    unsigned long size, 
                    pgprot_t prot);
  • vma：用户空间虚存区结构体指针。
  • addr：映射的起始虚拟地址。
  • pfn：物理内存对应的页帧号（Page Frame Number），即将物理地址右移 PAGE_SHIFT 位。
  • size：映射的长度。

六、 Linux 设备驱动模型与 sysfs #

为了统一管理系统中的所有总线、设备和驱动，Linux 2.6 引入了设备模型。而 sysfs 就是这个模型在用户空间的投影。

1. sysfs 与 Kobject 树 #

  • sysfs：一个挂载在 /sys 的特殊文件系统，展现了内核的设备拓扑。
  • Kobject：设备模型的基本基石，相当于 C++ 中的基类。Bus、Device、Driver 结构体内部都嵌入了 struct kobject。
  • 通过 Kobject 之间的父子关系（parent），在内核中形成了一棵设备树，直接映射为 /sys 下层层嵌套的目录结构。
  • Kref：Kobject 内部的引用计数器，用于管理对象的生命周期，防止对象在被使用时被意外释放。

2. Kobj_type 与属性文件（attribute） #

Kobject 导出的目录中包含的各类属性文件（例如控制 LED 亮灭的属性），在内核中用 attribute 描述。

c
struct attribute {
    char *name;          // 属性名（显示在 sysfs 中的文件名）
    struct module *owner;
    mode_t mode;         // 文件读写权限
};

当用户态读取或写入这个文件时，系统会调用绑定在该 kobj_type 上的 sysfs_ops 操作集：

  • show()：读取属性值并返回给用户。
  • store()：接收用户写入的属性值并做出响应。

3. 总线、设备与驱动（Bus, Device, Driver） #

在设备模型中，这三者的关系是：设备挂载在总线上，驱动注册到总线上；总线负责将设备与驱动进行匹配（match）。

                    +-------------------+
                    |     总线 (Bus)     |
                    +---------+---------+
                              |
            +-----------------+-----------------+
            |                                   |
  +---------v---------+               +---------v---------+
  |    设备 (Device)  | <== match ==> |    驱动 (Driver)  |
  +-------------------+               +-------------------+
  • Bus (总线)：由 struct bus_type 描述（如 USB、PCI、Platform）。它维护了两个链表：设备链表和驱动链表。当有新设备或新驱动加入时，调用 match() 进行匹配。
  • Device (设备)：由 struct device 描述。代表硬件实体。
  • Driver (驱动)：由 struct device_driver 描述。实现对硬件控制的具体逻辑，提供 probe()（匹配成功时调用）和 remove() 函数。

七、 动态创建设备节点：devfs 与 udev #

手写字符设备驱动时，如果还要手动用 mknod 创建设备文件，未免显得太不专业。现代 Linux 使用 udev 在用户空间动态管理设备节点。

1. devfs 与 udev 的对比 #

  • devfs：老版本 2.4 内核引入，在内核空间创建设备节点。但存在主次设备号分配混乱、命名不规范等严重缺陷，现已被废弃。
  • udev：完全在用户空间运行。当内核发现新设备（如插拔 USB）时，通过 netlink 发出 uevent 广播，用户空间的 udevd 守护进程收到后，根据 /etc/udev/rules.d/ 下的规则文件，动态创建或删除 /dev/ 下的设备节点。

2. 在驱动中利用 udev 自动创建节点 #

要在驱动加载时让 udev 自动在 /dev/ 下建立节点，咱们只需在驱动初始化函数中调两步 API：

c
#include <linux/device.h>

struct class *my_class;

// 1. 创建一个类（会对应生成 /sys/class/farsight_class 目录）
my_class = class_create(THIS_MODULE, "farsight_class");
if (IS_ERR(my_class)) {
    printk("Err: failed in creating class.\n");
    return PTR_ERR(my_class);
}

// 2. 注册设备（会触发 uevent，让 udevd 自动创建 /dev/farsight_dev 节点）
device_create(my_class, NULL, devno, NULL, "farsight_dev"); // 注：老版本内核为 class_device_create

在驱动卸载时，逆向注销即可：

c
device_destroy(my_class, devno);
class_destroy(my_class);
