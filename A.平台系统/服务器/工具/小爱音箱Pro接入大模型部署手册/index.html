小爱音箱 Pro（LX06）接入大模型全流程部署手册 #

本文性质：一份在真实服务器上从零跑通并逐条验证过的操作手册，不是照抄上游 README 的翻译稿。 实测环境：Debian 12.9 (bookworm) / x86_64 / 1.9 GB 内存 / 洛杉矶 VPS / 音箱型号 LX06（小爱音箱 Pro）。 实测日期：2026-11-09。所有版本号、日志、耗时、内存占用均为当场采集。 适用读者：会 SSH 登录、能复制粘贴命令，但没部署过这套东西的人。

0. 先看结论 #

你可能担心的问题 真实答案
要不要 Docker？ 不要。手动部署业务进程只占 约 70 MB 内存；Docker 光是 dockerd + containerd 常驻就要多 50–150 MB，还要几 GB 镜像盘
要不要公网 IP / 开端口 / 内网穿透？ 都不要。程序是纯出站轮询小米云，全程没有任何监听端口（实测部署后 ss -ltnp 无新增）
要不要刷机 / root 音箱 / 同局域网？ 都不要，完全不碰音箱固件
LX06 要手填 MIoT 指令吗？ 不要。config.yaml 里 hardware: LX06 之后，ttsCommand/wakeupCommand 由程序内置查表得到
小米账号能不能用「账号 + 密码」直接登录？ 不能（本文实测）。境外 IP 会触发风控，只能扫码。详见 3.3
扫一次码之后要一直重扫吗？ 不用。拿到 passToken 后可免扫码自动续期，这是本文能把方案写成「可长期维护」的关键
服务器要多大内存？ 实测可用内存只要 400 MB 左右就够跑，整套 venv 占 407 MB 磁盘

唯一的硬约束：这个中转程序必须一直在跑。用 systemd 托管即可，开机自启。

1. 它是怎么工作的 #

你说「小爱同学，请问 讲个笑话」
        │
        ▼
   小爱音箱 ──录音──▶ 小米云（语音识别 + 存下这条对话记录）
                            │
                            │  ← 这边一直在「出站轮询」查有没有新记录
                            ▼
                    xiaogpt（你的服务器）
                            │
                            │  发现提问以「请问」开头
                            ▼
                    大模型 API（OpenRouter / DeepSeek / OpenAI ...）
                            │
                            ▼
                    xiaogpt 拿到回答文字
                            │
                            ▼
              调用小米的 TTS 接口 ──▶ 小米云 ──▶ 音箱把答案念出来

三个要点：

  1. 不带「请问」的话不会被接管。闹钟、天气、控制家电仍然走小爱原生通道，两者互不干扰。
  2. 全流程是你的服务器主动去问小米云「有没有新问题」，所以服务器不需要公网 IP、不需要端口映射。
  3. 登录态存在一个 token 文件里，重启后复用，不需要每次重新登录。

2. 动手前的确认（这步做错后面全白费） #

2.1 Python 版本是硬门槛 #

xiaogpt 最新版（3.24）在 pyproject.toml 里写死：

toml
requires-python = ">=3.12,<3.15"

而 Debian 自带的 Python 版本：

系统 自带 python3 能否直接用 本文怎么处理
Debian 13 (trixie) 3.13.x 可以 仍建议按本文用 uv，省事
Debian 12 (bookworm) 3.11.2 不行 用 uv 装一个独立的 3.13，不动系统 Python
Ubuntu 22.04 3.10 不行 同上

先确认自己的系统：

bash
cat /etc/debian_version
python3 --version
uname -m          # 应为 x86_64
free -m           # 看 available 那一列
df -h /

实测这台机器：Debian 12.9、Python 3.11.2、x86_64、内存 1967 MB（可用 906 MB）、磁盘 30 G 用了 8.6 G。

2.2 网络：这台机器的地理位置会决定你能不能登录 #

这是本文最重要的一个认知，很多人卡在这里却不知道原因。

小米的登录接口对非中国大陆的 IP 有很强的风控。实测（洛杉矶 IP）：

  • 用「账号 + 密码」登录 → 一律返回 87001 验证码输入错误，即使密码完全正确
  • 连根本不存在的账号 19999999999 也返回同样的 87001（说明这是 IP 级拦截，跟账号密码无关）
  • 试了 4 种 User-Agent × 2 种 sid（共 8 组）→ 全部 87001
  • 图形验证码接口能取到图，但提交后永远失败（因为拦的是 IP，不是验证码内容）
登录方式 实测结果
账号 + 密码 ❌ 87001 验证码输入错误
账号 + 密码 + 图形验证码 ❌ 同样 87001
扫码登录 ✅ 成功

结论：只走扫码登录（3.3 节）。 如果你的服务器在香港/新加坡/日本/美国，这条路径同样可用。

先测一下出站通不通：

bash
curl -s -o /dev/null -w "%{http_code}\n" https://account.xiaomi.com   # 期望 200 或 302
curl -s -o /dev/null -w "%{http_code}\n" https://openrouter.ai        # 期望 200 或 301

3. 从零部署（7 步） #

全部命令默认以 root 执行。如果你用普通用户，请在命令前加 sudo，并把 /opt/xiaogpt 的属主改成自己。

3.1 装 uv，拿到合格的 Python #

uv 是 Rust 写的 Python 包管理器，不编译、不污染系统 Python，几秒装好一个独立的 3.13。

bash
apt update
apt install -y curl ca-certificates

curl -LsSf https://astral.sh/uv/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"

uv --version                 # 实测输出：uv 0.11.12
uv python install 3.13       # 实测 4.1 秒下完，108 MB

装完后检查一下版本号：

bash
uv python list | grep 3.13   # 应能看到 cpython-3.13.13-linux-x86_64-gnu

为什么不用 apt 装 Python 3.13：Debian 12 的官方源里没有 3.13，要加第三方源；uv 直接从 python-build-standalone 下载预编译版本，干净且可随时删。

3.2 建目录、建虚拟环境、装 xiaogpt #

bash
mkdir -p /opt/xiaogpt

uv venv --python 3.13 /opt/xiaogpt/venv
uv pip install --python /opt/xiaogpt/venv/bin/python -U --force-reinstall "xiaogpt[locked]"

实测：xiaogpt[locked] 一共装 60 多个包，13.1 秒装完，venv 体积 407 MB。

[locked] 是什么？它会把所有依赖钉死到一组经过上游测试的版本组合（openai==3.42.1、miservice==3.0.1、edge-tts==7.3.1 等）。建议保留，避免某天某个依赖升级后炸掉。

验证：

bash
/opt/xiaogpt/venv/bin/python -V        # 必须落在 3.12–3.14，实测 3.13.13
/opt/xiaogpt/venv/bin/xiaogpt --help   # 能打出帮助即可

注意：uv 建的 venv 里面没有 pip，这是正常的。以后升级/装包都用 uv pip install --python /opt/xiaogpt/venv/bin/python ...，不要用 venv/bin/pip。

此时目录形态：

/opt/xiaogpt/
└── venv/                 # 407 MB，别惊讶

3.3 扫码登录小米账号（本文最关键的一步） #

为什么要单独做这一步 #

  • 上游文档说「跑一次 miservice list，它会提示你输入验证码」—— 在境外 IP 上这条路是死的（见 2.2 节实测）。
  • 而且 xiaogpt 在 systemd 下运行时没有交互终端，如果它卡在「请输入验证码」，就会无限重启。

所以正确做法是：先用一个独立脚本把登录做完、把 token 落盘，再启动服务。

下载登录脚本 #

把下面这个文件存到服务器 /opt/xiaogpt/mi_qr_login.py（也可以用 scp 传上去）：

python
#!/usr/bin/env python3
"""
小米账号扫码登录助手（一次性使用）

原理：
  1. 向 account.xiaomi.com 申请一个扫码登录会话（longPolling/loginUrl）
  2. 把二维码存成文件，用手机米家 App 扫码确认
  3. 长轮询拿到 location/nonce/ssecurity/passToken
  4. 用 passToken 自动为 xiaomiio / micoapi 两个服务换取 serviceToken
  5. 合并写入 token 文件（600 权限）

后续到期自动续期不需要再扫码：passToken 有效期很长，程序会用 passToken
重新走 serviceLogin 换新的 serviceToken。

用法：
  python3 mi_qr_login.py                 # 默认写 /opt/xiaogpt/.mi.token
  python3 mi_qr_login.py /root/.mi.token # 指定输出路径
"""
import base64
import hashlib
import json
import os
import random
import string
import sys
import time
import urllib.parse

try:
    import requests
except ImportError:
    sys.exit("缺少 requests：/opt/xiaogpt/venv/bin/python 里已自带，请用它运行")

ACCOUNT_BASE = "https://account.xiaomi.com"
UA_LOGIN = (
    "APP/com.xiaomi.mihome APPV/11.3.203 iosPassportSDK/4.2.50 iOS/26.3.1 "
    "MK/aVBob25lMTcsMg== DEVT/aVBob25l DEVS/aU9T BRA/QXBsbGU= L/zh_CN"
)
SIDS = ("xiaomiio", "micoapi")


def log(*args):
    print(*args, file=sys.stderr, flush=True)


def parse_start(text: str) -> dict:
    """小米接口会在 JSON 前加 '&&&START&&&'，这里剥掉。"""
    i = text.find("{")
    return json.loads(text[i:]) if i >= 0 else {}


def new_device_id() -> str:
    return "".join(random.choice(string.ascii_uppercase + string.digits) for _ in range(16))


def get_qr(sid: str):
    s = requests.Session()
    s.headers.update({"User-Agent": UA_LOGIN})
    r = s.get(
        f"{ACCOUNT_BASE}/longPolling/loginUrl",
        params={"_json": "true", "sid": sid, "_locale": "zh_CN"},
        timeout=20,
    )
    j = parse_start(r.text)
    if not j.get("qr"):
        raise RuntimeError(f"申请二维码失败：{r.text[:200]}")
    img = s.get(j["qr"], timeout=20).content
    return s, j["lp"], img, j.get("timeout", 300)


def wait_scan(s, lp: str, timeout: int) -> dict:
    t0 = time.time()
    while time.time() - t0 < timeout - 5:
        try:
            r = s.get(lp, timeout=45)
        except requests.exceptions.ReadTimeout:
            continue
        j = parse_start(r.text)
        if j.get("code") == 0 and j.get("location"):
            return j
        time.sleep(1)
    raise TimeoutError("扫码超时，请重新运行")


def exchange(location: str, nonce: str, ssecurity: str) -> str:
    sign = base64.b64encode(
        hashlib.sha1(f"nonce={nonce}&{ssecurity}".encode()).digest()
    ).decode()
    s = requests.Session()
    s.headers.update({"User-Agent": UA_LOGIN})
    r = s.get(location + "&clientSign=" + urllib.parse.quote(sign), timeout=20)
    st = r.cookies.get("serviceToken")
    if not st:
        raise RuntimeError(f"换取 serviceToken 失败（HTTP {r.status_code}）")
    return st


def relogin_with_passtoken(user_id, pass_token, sid) -> tuple:
    """用 passToken 免扫码换取某个 sid 的 serviceToken。"""
    s = requests.Session()
    s.headers.update({"User-Agent": UA_LOGIN})
    for k, v in (("userId", str(user_id)), ("passToken", pass_token), ("sdkVersion", "3.9")):
        s.cookies.set(k, v, domain="account.xiaomi.com")
    r = s.get(
        f"{ACCOUNT_BASE}/pass/serviceLogin",
        params={"sid": sid, "_json": "true"},
        timeout=20,
    )
    j = parse_start(r.text)
    if j.get("code") != 0 or not j.get("location"):
        raise RuntimeError(f"[{sid}] 续期失败 code={j.get('code')} {j.get('description')}")
    st = exchange(j["location"], j["nonce"], j["ssecurity"])
    return j["ssecurity"], st, j.get("passToken") or pass_token


def main():
    out = sys.argv[1] if len(sys.argv) > 1 else "/opt/xiaogpt/.mi.token"

    log("== 第 1 步：申请二维码 ==")
    s, lp, img, timeout = get_qr("xiaomiio")
    qr_path = os.path.join(os.path.dirname(out), "qr.png")
    with open(qr_path, "wb") as f:
        f.write(img)
    os.chmod(qr_path, 0o644)
    log(f"二维码已保存：{qr_path}（{len(img)} 字节）")
    log(f"有效期约 {timeout} 秒")
    log("")
    log("== 第 2 步：用手机米家 App 扫码并确认 ==")
    log("   打开米家 App → 我的 → 右上角扫码（或任何登录了同一小米账号的 App）")

    resp = wait_scan(s, lp, timeout)
    user_id = resp.get("userId")
    pass_token = resp.get("passToken")
    log(f"扫码成功，userId={user_id}")

    token: dict = {}
    if os.path.isfile(out):
        try:
            token = json.load(open(out))
        except Exception:
            token = {}
    token["deviceId"] = new_device_id()
    token["userId"] = user_id
    token["passToken"] = pass_token

    log("== 第 3 步：换取两个服务的 serviceToken ==")
    for sid in SIDS:
        if sid == "xiaomiio":
            ssec, st = resp.get("ssecurity"), exchange(
                resp["location"], resp["nonce"], resp["ssecurity"]
            )
        else:
            ssec, st, pass_token = relogin_with_passtoken(user_id, pass_token, sid)
        token[sid] = [ssec, st]
        token["passToken"] = pass_token
        log(f"   {sid}: OK")

    os.makedirs(os.path.dirname(out) or ".", exist_ok=True)
    with open(out, "w") as f:
        json.dump(token, f, indent=2)
    os.chmod(out, 0o600)
    log("")
    log(f"完成：{out}（权限 600）")
    log(f"包含 sid：{[k for k, v in token.items() if isinstance(v, list)]}")
    log("之后到期会自动续期，不需要再扫码。")


if __name__ == "__main__":
    try:
        main()
    except Exception as e:
        log(f"失败：{e}")
        sys.exit(1)

3.4 取小爱音箱的 did #

did 是设备号，纯数字。config.yaml 里写上它，程序就不会再去查设备列表接口（那个接口另有坑）。

为什么不用上游说的 miservice list #

实测直接跑会失败：

Error https://api.io.mi.com/app/home/device_list:
{"code":-127, "message":"client withdraw",
 "result":{"wait_second":30, ...}}
HTTP 429

原因：miservice 3.0.1 里写死的 UA_MIIO 是 2021 年的米家 6.0.103，小米早已下线这个客户端版本，请求被判定为「客户端已撤回」。等 35 秒重试也没用。

解决办法：把 UA 换成现在在用的版本。下面是独立脚本，在运行时替换 UA，不改动已安装的文件。

保存脚本为 /opt/xiaogpt/get_did.py #

python
#!/usr/bin/env python3
"""
列出小米账号下的设备，用于找小爱音箱的 did（MIoT DID）。
用法：/opt/xiaogpt/venv/bin/python get_did.py

为什么要这个脚本？
  miservice 自带的 `miservice list` 使用了 2021 年的旧客户端 UA
  （MiHome 6.0.103），小米已下线该版本，会返回
  -127 client withdraw。本脚本在运行时替换成在用的新 UA，
  不需要修改 site-packages。
"""
import asyncio
import json
import os
import sys

import aiohttp

# 新版客户端 UA（iOS 米家 9.0），当前可用
UA_MIIO_NEW = (
    "iOS-17.0-9.0.0-iPhone15,2--"
    "D7744744F7AF32F0544445285880DD63E47D9BE9-8816080-84A3F44E137B71AE-iPhone"
)

TOKEN = os.environ.get("XIAOGPT_MI_TOKEN_PATH", "/opt/xiaogpt/.mi.token")


async def main() -> int:
    import miservice.miaccount as mac
    import miservice.miioservice as mis
    from miservice import MiAccount, MiIOService

    # 运行时替换 UA（不改动已安装的文件）
    mac.UA_MIIO = UA_MIIO_NEW
    mis.UA_MIIO = UA_MIIO_NEW

    if not os.path.isfile(TOKEN):
        print(f"找不到 token 文件：{TOKEN}", file=sys.stderr)
        print("请先运行 mi_qr_login.py 扫码登录。", file=sys.stderr)
        return 1

    token = json.load(open(TOKEN))
    async with aiohttp.ClientSession() as session:
        account = MiAccount(session, "", "", TOKEN)
        account.token = token
        devices = await MiIOService(account).device_list()

    if not devices:
        print("没有查到设备。", file=sys.stderr)
        return 1

    speakers = []
    for d in devices:
        name = d.get("name", "")

关于耗时：从提问到出答案约 21 秒，到「回答完毕」约 3 分 48 秒。拆解一下：

阶段 耗时 来源
提问 → 识别出问题 约 11 秒 mute_xiaoai: false 时有固定的 asyncio.sleep(8)，加轮询间隔

python
# xiaogpt/tts/base.py

    if not await self.get_if_xiaoai_is_playing():

  • prompt 限制回答字数 —— 直接缩短播报等待（收益最大）
  • 让音箱别在放歌 —— 避免播放状态卡住

4.1 触发词怎么定（建议只留 请问） #

上游默认 ["帮我", "请"]，实测这两个词都会带来麻烦：

  • 帮我 太像小爱原生指令的口气（「帮我放首歌」「帮我关灯」），容易和小爱自己的能力打架；
  • 请 是前缀匹配，会把「请问…」「请帮我…」全部吃掉，触发范围失控。

所以本文统一改成 ["请问"]：语义明确（就是在发问），而且不会误伤原生指令。

判定逻辑（读源码确认，xiaogpt.py 第 224 / 419 行）是大小写无关的前缀匹配：

python
query.lower().startswith(tuple(w.lower() for w in self.config.keyword))
...
query = re.sub(rf"^({'|'.join(self.config.keyword)})", "", query)   # 只剥掉前缀本身

实测（keyword: ["请问"]）：

你对音箱说的话 是否被接管 实际送进大模型的内容
「请问 你好」 ✅ 接管 你好
「请问你好」（连读不空格） ✅ 接管 你好
「请问一下明天天气」 ✅ 接管 一下明天天气
「帮我 讲个笑话」 ❌ 不接管，走小爱原生 —
「放首歌」 ❌ 不接管 —
「明天七点叫我起床」 ❌ 不接管 —

两个要注意的点：

  1. 只剥前缀，不剥语气词。说「请问一下明天天气」，送进模型的是「一下明天天气」—— 不影响理解，但你如果在意，就别说「一下」。
  2. 连读和空格都可以。小米云识别出来是「请问 你好」还是「请问你好」，都能命中，空格会被前后 strip() 掉。

改完 systemctl restart xiaogpt，日志第一行会变成 Running xiaogpt now, 用 请问 开头来提问，看到这行就说明配置生效了。

5.4 【重点】音箱在放音乐时，程序会一直卡住 #

这是本文实测发现、上游文档完全没提的一个行为，也是最容易被误判成「服务挂了」的问题。

现象：日志里大模型回答已经出来了，但「回答完毕」这一行几分钟都不出现，服务 active 正常、没有任何报错。

原因在 xiaogpt/tts/base.py 的 wait_for_duration()：

python
async def wait_for_duration(self, duration: float) -> None:
    await asyncio.sleep(duration)                       # 先按字数睡一会儿
    while True:                                         # 再等音箱停止播放
        if not await self.get_if_xiaoai_is_playing():   # status != 1 才退出
            break
        await asyncio.sleep(1)

而 get_if_xiaoai_is_playing() 判断的只是 player_get_status() 返回的 status == 1。音箱在放音乐时 status 恒为 1，于是这个 while 循环永远不会 break。

实测复现（让音箱放歌后下发 TTS）：

calculate_tts_elapse('测试一句话。') = 1.3s
放歌中 status = 1
已下发 TTS，开始复现 wait_for_duration 循环：
  loop#1 +  2.0s status=1 playing=True
  loop#2 +  3.6s status=1 playing=True
  ...
  loop#12 + 19.5s status=1 playing=True
  -> 12 次后仍 playing=True，证实会被音乐阻塞

19.5 秒里 status 一次都没变过。

处理办法：

bash
# 先让音箱停下来
/opt/xiaogpt/venv/bin/python - <<'PY'
import asyncio, aiohttp, json
from miservice import MiAccount, MiNAService
DEV = "换成你自己上一步输出的 deviceID"
async def m():
    t = json.load(open('/opt/xiaogpt/.mi.token'))
    async with aiohttp.ClientSession() as s:
        a = MiAccount(s, 'x', 'y', '/opt/xiaogpt/.mi.token'); a.token = t
        print(await MiNAService(a).player_pause(DEV))
asyncio.run(m())
PY

systemctl restart xiaogpt      # 让卡住的循环重新开始

注意：这个循环卡住时不影响下一次提问吗？会影响 —— 因为 run_forever 是串行的，卡在等待里就没法去轮询下一个问题。所以表现为「问了一次之后就没反应了」。

A.4 端到端耗时 #

阶段 耗时
提问 → 小爱回答被识别 约 11 秒（含固定 8 秒等待）
识别 → 大模型出答案 约 10 秒

总计 约 3.8 分钟（回答较长时）

播报等待时间是 len(文字) / 4.5 秒估算 + 轮询播放状态，文字越长等越久。这是上游设计，不是 bug。 例外：如果音箱在放音乐，最后那段轮询会因为 status 恒为 1 而永远不退出，见 5.4。

A.5 关于「耗时」的实测参考值 #

文本 字数 calculate_tts_elapse
「你好！我是Nemotron…请问有什么我可以为您做的吗？」（一次真实回答） 101 22.4 秒
「这是一次语音播报测试，如果你听到这句话，说明整条链路已经打通。」 31 6.9 秒
「测试一句话。」 6 1.3 秒

公式是 len(去掉标点后的文字) / 4.5。所以控制回答长度是控制延迟最有效的手段：把 prompt 里的「300 字以内」改成「100 字以内」，播报等待直接少三分之二。

附录 B. 上游文档里过时或错误的说法（重要） #

实测发现上游 README 和实际代码有几处对不上，照着做会卡住。列在这里省得你再踩一遍：

上游说法 实际情况 本文怎么处理
跑 miservice list 会提示输入验证码 境外 IP 上直接返回 87001，根本没有输验证码的机会；且 notificationUrl 为空，没有短信通道 改用扫码（3.3）
miservice mina 用来查设备 miservice --help 不列出 mina 子命令（虽然代码里有） 用 get_did.py 更直接
pip install -U --force-reinstall xiaogpt[locked] Debian 12 自带 Python 3.11 装不上（要求 ≥3.12） 用 uv 装 3.13（3.1）
miservice list 能取 did 必定 -127 client withdraw（旧 UA 被下线） 用 get_did.py 运行时换 UA（3.4）
miservice 尊重 XIAOGPT_MI_TOKEN_PATH CLI 硬编码读 ~/.mi.token，完全忽略这个环境变量 用脚本时不需要；非要用 CLI 就先 cp 到 ~/.mi.token
--tts 支持 minimax CLI 的 choices 里没有，只有 config.py 的类型注解有 按 8 个值来，详见第 4 节
tts: mi 不需要额外配置 对，但 do_tts() 会静默吞掉 TTS 异常，出错没日志 单独验证 TTS（3.4 最后）
回答完就结束了 音箱在放音乐时程序会卡在播放状态轮询里出不来，且上游完全没提 见 5.4
首次登录在 systemd 里跑就行 systemd 无交互终端，遇到验证码会无限重启 先在终端把 token 做完（3.3）

附：一句话总结 #

装 uv → 装 xiaogpt → 扫码拿 token（别用密码）→ 用小脚本拿 did（别用 miservice list）→ 写 config 指向 OpenRouter 免费模型 → systemd 托管。 全流程约 15 分钟，跑起来只占约 70 MB 内存、不开任何端口。
