Caddy 入门与实战：自动 HTTPS、反向代理与 Caddyfile 一本通 #

Nginx 用着挺好，但只要牵涉证书，事情就开始变得烦人：certbot 装一遍、cron 续期配一遍、ssl_certificate 路径改三遍、忘了 reload 一遍。Caddy 就是来干掉这一整套流程的。

一句话：你把域名写进配置文件，它自己去申请证书、自动续期、自动把 80 跳 443。这活儿以前要写一个定时任务加一个 ACME 客户端才能干完。

本文按"装、配、跑、调、避坑"的顺序把 Caddy 走一遍，配置全部可以直接抄。想先补 Nginx 那一套的，可以看 Nginx 核心实战；没有公网 IP 想对外发布服务的，看 Cloudflare Tunnel 内网穿透。

1. Caddy 到底是个什么东西 #

Go 写的 Web 服务器与反向代理，单个静态二进制，没有运行时要装。它的特性清单里最显眼的那一条就是 Automatic HTTPS，其余都是常规能力：静态文件、反向代理、负载均衡、FastCGI、模板渲染、HTTP/2 与 HTTP/3、Prometheus 指标、访问日志。

截至写文，最新版本是 v2.11.9（2026-11-05）。这个补丁主要是收 2.11.8 带进来的回归问题，外加几个 FastCGI 相关的安全修复，跑 PHP 的建议直接跳上来。

跟 Nginx 摆在一起比一下：

对比项 Caddy Nginx
配置形态 Caddyfile（人类可读）+ JSON（机器可读） nginx.conf 自有指令集
HTTPS 证书 内置 ACME 客户端，自动签发 + 自动续期 需要 certbot / acme.sh 外部配合
80 跳 443 默认开启 手写 server 块 + return 301
配置变更生效 caddy reload，走 admin API，零停机 nginx -s reload，发信号
单机静态性能 略低于 Nginx 业界基准线
上手成本 一个文件搞定 需要理解 location、upstream、context 层级
插件扩展 自己用 xcaddy 重新编译（无运行时动态加载） 大部分功能内置，第三方模块同样要重编译

结论不复杂：如果你维护的站点在 10 个以内、主要诉求是"给我把 HTTPS 搞定"，Caddy 是省事的那一边。 如果你在跑 CDN 回源、几十万 QPS 的静态分发、或者需要极其精细的 buffer 与超时控制，Nginx 依然是正确选择。

爽点在于配置量。Nginx 上一个完整的 HTTPS 反代站点大概 40 行，Caddy 上是 4 行。

坑点在于心智模型不同。Nginx 的人习惯 location 匹配加 proxy_pass，而 Caddy 是"指令 + 匹配器 + 处理器链"，很多东西没有直接对应物，第一次写容易摸不着头绪。

2. 安装：五种姿势，按环境挑 #

2.1 Linux 官方包（生产首选） #

Debian / Ubuntu 系装完就自带 systemd 服务并自动启动：

bash
# 加官方源（Cloudsmith 维护）
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo chmod o+r /usr/share/keyrings/caddy-stable-archive-keyring.gpg
sudo chmod o+r /etc/apt/sources.list.d/caddy-stable.list
sudo apt update && sudo apt install caddy

caddy version          # 确认装上了
systemctl status caddy # 已经跑起来了

Fedora / CentOS 走 COPR：

bash
dnf install dnf-plugins-core
dnf copr enable @caddy/caddy
dnf install caddy
systemctl enable --now caddy   # 这两个源不会自动 enable，得手动来

Arch 用户 pacman -Syu caddy 就完事，但要注意 Arch 的 service 文件加了沙箱限制，某些宿主机目录可能对进程不可见。

2.2 静态二进制（想自己控制版本） #

bash
# 从 GitHub Releases 下对应架构的包，解压后得到一个 caddy 可执行文件
sudo mv caddy /usr/bin/
caddy version

二进制方式的缺点是服务文件要自己写，第 9.3 节给了完整的 systemd 配置。另外提一句，caddy upgrade 这个命令可以自动替换当前二进制到最新版，属于实验性功能，测试环境玩玩可以，生产上我更愿意手动下载 + 校验签名。

2.3 Windows #

powershell
choco install caddy   # 或者 scoop install caddy

本地写前端、调 API 的时候，Windows 上装一个 Caddy 比折腾 IIS 舒服太多，caddy file-server --browse 就能起一个带目录列表的静态服务器。

2.4 Docker #

bash
docker pull caddy

正式的 compose 编排见第 7.3 节。

2.5 需要插件时：xcaddy #

Caddy 没有运行时加载的插件机制，所谓"装插件"就是把插件编译进二进制。想用 DNS-01 挑战（通配符证书必备）就得走这条路：

bash
# 装 xcaddy
go install github.com/caddyserver/xcaddy/cmd/xcaddy@latest

# 把 DNS 插件编译进去（这里以 Cloudflare 为例）
xcaddy build --with github.com/caddy-dns/cloudflare

官方下载页其实也提供在线定制编译，勾选插件直接下载二进制，省得本地装 Go 环境。

3. Caddyfile：语法就那几样 #

Caddy 接受两种配置：JSON（原生格式，字段巨多但能表达一切）和 Caddyfile（人类友好格式，启动时自动 adapt 成 JSON）。99% 的场景写 Caddyfile 就够了。

写来写去就这几个东西：

{                              # 全局配置块，整个文件最多一个，必须放最前面
    email admin@example.com    # 注册 ACME 账号用的邮箱，别乱填
    debug                      # 打开调试日志，排障时临时开
}

example.com {                  # 站点块：第一行是站点地址，后面大括号里是指令
    root * /var/www/html       # * 是匹配器，表示匹配所有请求
    file_server                # 起一个文件服务器
}

api.example.com {              # 一个文件里可以写任意多个站点块
    reverse_proxy localhost:9005
}

指令之间有默认执行顺序，这个必须记住，否则会踩"为什么我的 header 没生效"这种坑。顺序大致是这样（只列常用的）：

header → request_body → redir → method → rewrite → uri → try_files
→ basic_auth → forward_auth → request_header → encode → templates
→ handle / handle_path / route → abort → error → respond
→ reverse_proxy → php_fastcgi → file_server

header 排在最前面，reverse_proxy 排在很后面。所以你在一个站点块里写 redir 和 reverse_proxy，Caddy 会先判断重定向，不会被反代吃掉。真有自己的顺序需求，用 route 包一层，里面就按字面顺序执行。

graph TD
    A[请求进来] --> B[匹配站点块<br/>按 Host / 端口]
    B --> C[按默认顺序排序指令]
    C --> D{命中 handle 块?}
    D -->|是| E[该块内部独占执行]
    D -->|否| F[继续走后续指令]
    F --> G[reverse_proxy / file_server / respond]
    G --> H[响应写出]
    H --> I[header 与 encode 收尾]

想看你的 Caddyfile 到底被翻译成了什么 JSON，adapt 一下：

bash
caddy adapt --config /etc/caddy/Caddyfile --pretty

改配置前跑一遍 caddy validate --config /etc/caddy/Caddyfile，能把语法错误挡在 reload 之前。

4. 自动 HTTPS 是怎么跑起来的 #

这块是 Caddy 的核心卖点，值得单独拆开看。

sequenceDiagram
    participant U as 浏览器
    participant C as Caddy
    participant A as Let's Encrypt / ZeroSSL
    U->>C: 访问 http://example.com (80)
    C-->>U: 301 跳转到 https://
    U->>C: TLS 握手 (443)
    Note over C: 本地无证书，触发签发流程
    C->>A: ACME 下单 (HTTP-01 或 TLS-ALPN-01)
    A->>C: 挑战验证
    C-->>A: 验证通过
    A->>C: 下发证书
    C->>C: 落盘到 data 目录
    C-->>U: 完成握手，返回页面
    Note over C: 到期前 30 天自动续期

关键行为有几条：

证书来源：公网域名走 Let's Encrypt，失败自动降级到 ZeroSSL。两个 issuer 都不需要你申请 API key，只要有个邮箱（可选）。签发失败后按指数退避重试，最长持续 30 天，单次间隔上限 1 天。内部还有限流，同一个 ACME 账号 10 秒内最多 10 次尝试，防止你把 CA 的速率限制撞爆。

挑战方式：默认同时开 HTTP-01（走 80 端口）和 TLS-ALPN-01（走 443 端口）。这意味着 80 和 443 必须是公网可达的，云厂商安全组记得放行。通配符证书拿不到这条路，因为 ACME 不允许用 HTTP 挑战验证通配符，只能用 DNS-01，也就是前面说的必须编译 DNS 插件。

*.example.com, example.com {
    tls {
        dns cloudflare {env.CF_API_TOKEN}   # token 从环境变量读，别写死在配置里
    }
}

本地域名：localhost、*.localhost 和纯 IP 地址走内置的 local CA，签发"Caddy Local Authority"根证书再签站点证书。浏览器第一次访问会红，装上根证书就绿了：

bash
caddy trust          # 把根证书装进系统信任库（Linux 上要 sudo）
caddy untrust        # 玩完了想撤掉

根证书文件在 data 目录的 pki/authorities/local/root.crt，其他设备要信任就拷这个文件过去装。现在很多浏览器有自己的信任库，不走系统那一套，那就得在浏览器设置里手动导入一遍。

证书存储：默认放 $HOME/.local/share/caddy。容器里是 /data，systemd 服务里是 /var/lib/caddy/.local/share/caddy。这个目录必须可写并且要持久化，删了就得重新签发，容易撞 CA 的速率限制。

按需签发（On-Demand TLS）：给多租户 SaaS 用，域名不写死在配置里，第一次握手时拿着 SNI 去申请。默认关着，开了必须配 ask 端点做拦截，否则任何指向你服务器的域名都能让 Caddy 去签发，几小时就能把速率限制刷爆。

{
    on_demand_tls {
        ask http://localhost:9000/check   # 你自己的鉴权接口，返回 2xx 才签
    }
}

https:// {
    tls {
        on_demand
    }
    reverse_proxy localhost:8080
}

还有一点容易忽略：Caddy 2.10 之后，通配符证书会自动覆盖配置里出现的单个子域。也就是说你既配了 *.example.com 又配了 blog.example.com，它不会傻乎乎地给子域单独签一张。

5. 静态站点：三行搞定 #

最简形态：

example.com {
    root * /var/www/blog          # 站点根目录
    encode zstd gzip              # 顺带开压缩，zstd 优先，不支持就退到 gzip
    file_server                   # 静态文件服务
}

目录列表、预压缩文件这些也有：

example.com {
    root * /var/www/blog
    file_server {
        browse                    # 允许列目录，内网文件站很实用
        precompressed br gzip     # 优先返回 .br / .gz 预压缩文件
    }
}

前端的单页应用（Vue Router、React Router 那种 history 模式）必须加一条兜底，否则刷新二级路由直接 404：

app.example.com {
    root * /var/www/app
    encode zstd gzip
    try_files {path} /index.html      # 找不到文件就吐 index.html 交给前端路由
    file_server
}

try_files 走的是内部重写，浏览器地址栏不变，跟前端路由能对上。

写到这儿顺手提个 Caddy 的隐藏技能：caddy file-server 可以直接从命令行起一个静态服务，不用写配置文件。给人传文件、临时看个构建产物，比 python -m http.server 靠谱得多，至少支持 Range 请求和目录浏览。

bash
caddy file-server --root ./dist --browse --listen :8080

6. 反向代理：Caddy 最强的地方 #

反代的最小写法短得离谱：

api.example.com {
    reverse_proxy localhost:9005
}

就这一行，HTTPS、证书、跳转全齐了。对比 Nginx 那一长串 proxy_set_header，确实省事。Host 头、X-Forwarded-For、X-Forwarded-Proto 这些 Caddy 都自动补，不用手写。

6.1 上游地址的几种写法 #

example.com {
    # 普通 host:port
    reverse_proxy 127.0.0.1:8080

    # 端口段，自动在 8001~8006 之间做负载均衡
    reverse_proxy localhost:8001-8006

    # Unix socket，跑在同一台机器上的应用常用
    reverse_proxy unix//run/app.sock

    # 上游本身是 HTTPS，v2.11.0 起 Host 头会自动设成上游主机名
    reverse_proxy https://backend.internal:8443

    # 上游支持 h2c（明文 HTTP/2）
    reverse_proxy h2c://127.0.0.1:8081
}

v2.11.0 那个改动值得单独说：以前反代到 https:// 上游，还得手写 header_up Host {upstream_hostport}，现在不用了。旧配置里的那行留着也不报错，但已经多余。

6.2 负载均衡 #

app.example.com {
    reverse_proxy 10.0.0.11:8080 10.0.0.12:8080 10.0.0.13:8080 {
        lb_policy least_conn          # 按最少连接数分发，默认是 random
        lb_try_duration 5s            # 5 秒内持续重试其他上游
        lb_try_interval 250ms         # 重试间隔
        lb_retries 3                  # 最多换 3 个上游
        health_uri /healthz           # 主动健康检查路径
        health_interval 10s
        health_timeout 3s
        health_status 200
    }
}

lb_policy 可选的值挺多，常用的几个：

策略 适用场景
random 默认值，上游数量少且能力相当时够用
least_conn 后端处理时长差异大，避免堆在慢节点上
round_robin 无状态、想严格控制分发比例
ip_hash 需要会话粘滞但不能改应用（老系统救急）
uri_hash 想让同一路径固定落在一个节点，提高缓存命中
first 主备模式，第一个活了就不用后面的

lb_try_duration 和 lb_retries 的区别容易搞混：前者是时间窗口，在窗口内不断换上游重试，配合 dial_timeout（默认 3s）一起理解；后者是次数上限。默认情况下这套重试只对 GET 生效，因为 POST 重放可能重复扣款。要放宽就写 lb_retry_match，但得自己想清楚幂等性。

健康检查分主动和被动两套，两个都能开：

reverse_proxy localhost:8001-8003 {
    # 主动探测
    health_uri /healthz
    health_interval 30s
    health_passes 2        # 连续成功 2 次才恢复
    health_fails 3         # 连续失败 3 次才摘除

    # 被动探测（靠真实流量判断）
    fail_duration 30s      # 大于 0 才启用，被判定失败后摘除 30 秒
    max_fails 1            # 30 秒内失败 1 次就开始摘
    unhealthy_status 500 502 503 504
    unhealthy_latency 2s   # 超过 2 秒也算失败，防慢节点拖死整体
}

被动检查对 PHP、Python 这类会被慢查询拖住的应用特别有用，比主动探测更贴近真实体感。

6.3 大文件上传与下载 #

默认反代对大 body 没有硬限制，但有个 10MB 的内存缓冲阈值，超出部分写临时文件。要压住磁盘 IO 或者干脆流式转发：

upload.example.com {
    request_body {
        max_size 2GB              # 超过直接 413，别让请求打满磁盘
    }
    reverse_proxy 10.0.0.11:8080 {
        flush_interval -1         # 流式传输，响应立刻下发不缓冲
        transport http {
            read_timeout 300s
            write_timeout 300s
        }
    }
}

flush_interval -1 是 SSE（Server-Sent Events）和 LLM 流式输出的救命配置。不设这个，客户端会看到"卡半天然后一次性吐出来"。

6.4 WebSocket #

不用额外配置。Caddy 会自动识别 Upgrade 头并透传，不像 Nginx 那样必须手写：

nginx
# Nginx 那边得这么写，忘了就 400
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";

Caddy 这边：

ws.example.com {
    reverse_proxy localhost:8080     # WebSocket 自动支持，什么都不用加
}

唯一要注意的是 HTTP/3 与 WebSocket 的关系。Caddy 默认开 HTTP/3，走 QUIC，而 WebSocket 跑在 HTTP/1.1 上，两者是协商出来的，不会互相干扰。反向代理链路上如果前面还挂了一层 CDN，那就得看 CDN 脸色了。

6.5 自定义错误页与状态码改写 #

后端挂了想吐一张自己的维护页：

app.example.com {
    reverse_proxy 10.0.0.11:8080 {
        @backend_down status 502 503 504
        handle_response @backend_down {
            root * /var/www/errors
            rewrite * /maintenance.html
            file_server
        }
    }
}

handle_response 里还能用 {rp.status_code}、{rp.header.*} 这些占位符拿到原始响应信息，做条件判断和日志。

6.6 内网鉴权与访问控制 #

内网服务不想裸奔，最省事的是 Basic Auth：

bash
# 生成 bcrypt 哈希，默认 cost 14，第一次生成要等半秒
caddy hash-password --plaintext 'your-strong-pass'

admin.example.com {
    basic_auth {
        admin $2a$14$xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
        # 用户名 哈希，一行一个账号
    }
    reverse_proxy localhost:9090
}

要接外部认证（OAuth2 Proxy、Authelia 那类），用 forward_auth：

private.example.com {
    forward_auth localhost:4181 {
        uri /api/authz/forward-auth
        copy_headers Remote-User Remote-Groups Remote-Email
    }
    reverse_proxy localhost:3000
}

7. 实战配置组：抄就完事 #

7.1 一个文件托管多个站点 + API #

{
    email ops@example.com
}

# 博客：纯静态
blog.example.com {
    root * /var/www/blog
    encode zstd gzip
    header {
        Strict-Transport-Security "max-age=31536000; includeSubDomains; preload"
        X-Content-Type-Options "nosniff"
        Referrer-Policy "strict-origin-when-cross-origin"
    }
    try_files {path} /index.html
    file_server
}

# 前端静态 + 后端 API 同域，省掉 CORS 那一堆破事
app.example.com {
    handle /api/* {
        reverse_proxy localhost:9005
    }
    handle {
        root * /var/www/app
        encode zstd gzip
        try_files {path} /index.html
        file_server
    }
}

# 纯反代
api.example.com {
    reverse_proxy localhost:9005 {
        health_uri /health
        health_interval 15s
    }
}

handle 块之间是互斥的，进了 /api/* 就不会再走后面那个，比 Nginx 的 location 优先级规则好理解。注意 handle 不剥前缀，/api/users 到后端还是 /api/users。想剥掉前缀用 handle_path：

app.example.com {
    handle_path /api/* {
        reverse_proxy localhost:9005   # 后端收到的是 /users 而不是 /api/users
    }
}

这里有个经典坑：剥了前缀之后，后端生成的相对路径、重定向 Location、Set-Cookie 的 Path 全都对不上，前端一片空白。这叫 subfolder problem。除非后端明确支持配置 base path，否则别用 handle_path，老老实实用 handle 保留前缀。

7.2 WordPress / PHP 站点 #

Caddy 有个 php_fastcgi 简写，它其实展开成了一串指令（root + try_files + reverse_proxy 的 FastCGI 传输 + 静态文件兜底），比手写 transport fastcgi 省事得多：

blog.example.com {
    root * /var/www/wordpress
    encode zstd gzip
    php_fastcgi unix//run/php/php8.3-fpm.sock {
        resolve_root_symlink    # 站点目录是软链接时必须开这个
    }
    file_server
}

resolve_root_symlink 这个选项是给别人挖坑挖出来的：root 指向一个 symlink（宝塔、Runcloud 那类面板很爱用 current -> releases/20261110 这种结构），PHP-FPM 的 DOCUMENT_ROOT 传的是链接路径而不是真实路径，WordPress 会各种报 "Could not open input file"。开了它就老实解析到真实路径。

WordPress 的永久链接不用像 Nginx 那样手写 try_files $uri $uri/ /index.php?$args。php_fastcgi 展开的时候已经带了一段 try_files {path} {path}/index.php index.php，/2026/11/hello-world/ 这类不存在的路径会自动落到 index.php 上，由 WordPress 自己路由。所以配置到上面那一段就够了，别多写。

另外两种情况要额外动手：

  • WordPress 装在子目录 /blog，得配合 handle_path 或者在后端把 WP_HOME / WP_SITEURL 改成带子目录的完整地址
  • 用静态缓存插件（WP Super Cache 之类）导出了纯 HTML 文件，那就得把 try_files 的候选列表加上 {path}/index.html {path}/，让静态文件优先命中

顺带说一个反例：网上有些教程抄了 SPA 的写法，给 WordPress 加一条 rewrite @not_static /index.html。那是给前端路由用的，WordPress 上根本没有 index.html，加上之后后台和文章页全白屏。看到这段直接删掉。

7.3 Docker Compose 里的 Caddy #

yaml
services:
  caddy:
    image: caddy:2.11.9
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"        # HTTP/3 走 QUIC，UDP 不放通就等于没开
    volumes:
      - ./conf:/etc/caddy    # Caddyfile 放这里
      - ./site:/srv          # 静态文件
      - caddy_data:/data     # 证书和状态，必须持久化
      - caddy_config:/config
    environment:
      - CF_API_TOKEN=${CF_API_TOKEN}
    networks:
      - web

  app:
    image: myapp:latest
    restart: unless-stopped
    networks:
      - web
    # 不需要 ports，同网络里 caddy 直接访问 app:3000

networks:
  web:

volumes:
  caddy_data:
  caddy_config:

对应 Caddyfile 里上游写容器名，不能写 localhost：

app.example.com {
    reverse_proxy app:3000    # 容器网络里 localhost 指容器自己
}

容器里改完配置重载：

bash
docker compose exec -w /etc/caddy caddy caddy reload --config /etc/caddy/Caddyfile

v2.11.0 之后也可以发信号，只要容器是用 caddy run 起的：

bash
docker compose kill -sUSR1 caddy

看日志：

bash
docker compose logs caddy -n=1000 -f

本地开发想让浏览器信任容器里的 local CA，把根证书拷出来装：

bash
docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt ./root.crt
# Windows
certutil -addstore -f "ROOT" .\root.crt
# Linux
sudo cp root.crt /usr/local/share/ca-certificates/ && sudo update-ca-certificates

8. 日志、指标与可观测性 #

Caddy 的日志分两种：运行日志（生命周期、错误）和访问日志（请求记录）。

{
    # 全局日志配置：把错误日志写到文件并按大小切割
    log {
        output file /var/log/caddy/caddy.log {
            roll_size 100MiB
            roll_keep 5
            roll_keep_for 720h
        }
        level INFO
    }
}

blog.example.com {
    log {
        output file /var/log/caddy/access-blog.log {
            roll_size 50MiB
            roll_keep 3
        }
        format json                # 默认就是 JSON，写 ES/Loki 直接吃
    }
    root * /var/www/blog
    file_server
}

要拦掉健康检查这类噪音请求：

example.com {
    @health {
        path /healthz /readyz
    }
    log_skip @health
    reverse_proxy localhost:8080
}

Prometheus 指标开一个端点就行，不用额外装 exporter：

{
    metrics {
        per_host        # 指标里带上 Host 维度，多站点才有意义
    }
}

指标默认挂在 admin 监听器的 localhost:2019/metrics 上，抓取端填这个地址就行，不用再装 node_exporter 之类的东西。反过来说，如果 admin 端口被你换到公网地址了，指标也跟着一起露出去，这就又绕回下面那条坑了。

日志里的字段已经够用了，request.headers、duration、size、status、remote_ip 全在里面。想加自定义字段，log_append 补一条：

example.com {
    log_append app_name "myapp"
    reverse_proxy localhost:8080
}

9. 命令行与进程管理 #

9.1 常用命令速查 #

bash
caddy run                       # 前台跑，排障就用它，日志全在眼前
caddy run --config /etc/caddy/Caddyfile --adapter caddyfile
caddy start                     # 后台跑，官方不建议在 systemd 或 Windows 下用
caddy stop                      # 停
caddy reload                    # 零停机重载，走 admin API，改配置后应该用这个
caddy reload --force            # 配置有问题时强制重载（会跳过校验，慎用）
caddy adapt --pretty            # 看 Caddyfile 翻译出的 JSON
caddy validate --config Caddyfile
caddy fmt --overwrite           # 格式化，团队协作时当 gofmt 用
caddy fmt --diff                # 只看格式差异，不改文件
caddy environ                   # 打印进程环境变量，排查 env 占位符取值为空很好用
caddy list-modules              # 列出编译进来的模块，确认 DNS 插件在不在
caddy version

caddy respond 和 caddy reverse-proxy 是开发期的两个小工具，前者起一个硬编码响应的服务（caddy respond --listen :2000 "hello"），后者一条命令起反代（caddy reverse-proxy --from :8080 --to localhost:9005）。调前端联调时挺省事。

9.2 信号与退出码 #

信号 行为
SIGINT / SIGTERM 优雅退出，等在处理的请求完成；再发一次强制退出
SIGQUIT 立即退出，但会清理锁文件
SIGUSR1 重新读取配置文件（仅在 caddy run 且没通过 API 改过配置时有效，v2.11.0 起）
SIGHUP / SIGUSR2 忽略

退出码：0 正常、1 启动失败、2 强制退出、3 清理出错。

退出码 1 特别值得说。它表示配置或端口有问题，这时候不要让 systemd 自动重启，因为配置错误重启一万次也起不来，只会把日志刷满。这在第 9.3 节的 systemd 配置里用 RestartPreventExitStatus=1 处理掉了。

9.3 systemd 服务（二进制安装时手写） #

bash
sudo mv caddy /usr/bin/
sudo groupadd --system caddy
sudo useradd --system \
    --gid caddy \
    --create-home \
    --home-dir /var/lib/caddy \
    --shell /usr/sbin/nologin \
    --comment "Caddy web server" \
    caddy

服务文件 /etc/systemd/system/caddy.service：

ini
[Unit]
Description=Caddy
Documentation=https://caddyserver.com/docs/
After=network.target network-online.target
Requires=network-online.target

[Service]
Type=notify
User=caddy
Group=caddy
ExecStart=/usr/bin/caddy run --environ --config /etc/caddy/Caddyfile
ExecReload=/usr/bin/caddy reload --config /etc/caddy/Caddyfile --force
TimeoutStopSec=5s
LimitNOFILE=1048576
PrivateTmp=true
ProtectSystem=full
AmbientCapabilities=CAP_NET_BIND_SERVICE

[Install]
WantedBy=multi-user.target

bash
sudo systemctl daemon-reload
sudo systemctl enable --now caddy
systemctl status caddy

改配置后用 sudo systemctl reload caddy，别用 stop/restart，停服务是有停机时间的。

跑起来之后，进程身份是 caddy 用户，$HOME=/var/lib/caddy：

  • 证书和状态：/var/lib/caddy/.local/share/caddy
  • 自动保存的 JSON 配置：/var/lib/caddy/.config/caddy

数据目录归 caddy 用户所有，别用 root 手动去改里面的东西。要在服务里注入环境变量（比如 DNS 插件的 token），用 drop-in 而不是改主服务文件：

bash
sudo systemctl edit caddy

ini
[Service]
EnvironmentFile=/etc/caddy/.env
Restart=on-failure
RestartPreventExitStatus=1
RestartSec=5s

/etc/caddy/.env 里写 CF_API_TOKEN=xxx，注意不要加引号，systemd 的 EnvironmentFile 不接受引号包裹的值。

SELinux 的系统上二进制会被拦，得打标签：

bash
sudo semanage fcontext -a -t bin_t /usr/bin/caddy
sudo restorecon -Rv /usr/bin/caddy

10. 踩坑清单 #

坑点 1：证书签不下来，日志里反复 challenge failed #

先按顺序查三件事。80 和 443 端口云厂商安全组放了吗；域名 A 记录真的指到这台机器了吗（dig +short example.com）；有没有别的进程占着 80 端口（ss -lntp | grep :80）。

还有一个高频原因是 IPv6。域名同时有 AAAA 记录但机器没有 IPv6 出网能力，Let's Encrypt 会优先走 IPv6 验证，然后超时。要么把 AAAA 记录删掉，要么把 IPv6 修好。

坑点 2：caddy reload 报 connection refused #

reload 走的是 admin API，默认监听 localhost:2019。如果 Caddy 没跑、或者 admin 被你关了、或者改了 admin 端口，reload 就摸不到。查一下：

bash
curl -s localhost:2019/config/ | head    # 能拿到 JSON 说明 API 活着

如果确实关了 admin API，那就只能 systemctl restart caddy，会有几秒停机。

顺便提醒：admin API 千万不能暴露到公网。它没有认证，任何人 POST /load 都能把你的配置换掉。要么绑在 localhost:2019 上，要么前面挂鉴权。Caddy 默认就是绑 localhost 的，别手贱改成 :2019。

坑点 3：反代 502，但 curl 后端是通的 #

九成是地址写错了。如果 Caddy 跑在 Docker 里，localhost 指的是容器自己，不是宿主机。要访问宿主机上的服务，得用 host.docker.internal（Mac/Windows）或者宿主机的网桥 IP（Linux 上需要 --add-host=host.docker.internal:host-gateway）。

反过来也一样：反代到另一个容器，用容器名，不要用宿主机映射出来的端口。

坑点 4：header 配了不生效 #

八成顺序问题。header 在默认顺序里排得很靠前，如果你在 reverse_proxy 后面才想起来加，或者被 handle 块隔开了，它就不会按你想象的层次生效。要么把 header 放到站点块顶层，要么用 route 包起来按字面顺序执行。另一个可能是后端自己也在写同名 header，那就得用 header_down 在反代内部改：

reverse_proxy localhost:8080 {
    header_down -Server                # 删掉后端吐的 Server 头
    header_down +X-Custom "value"      # 加一个
}

坑点 5：中文站点访问变成乱码或 404 #

root 后面的路径包含中文时，Caddy 是按字面路径处理的，没问题。真正容易出事的是 Caddyfile 本身不是 UTF-8 编码（Windows 上用记事本另存过），或者文件名在实际文件系统里是 GBK。用 file_server 的 browse 看一眼列表就能确认。

坑点 6：容器重启后重新申请证书，撞上速率限制 #

/data 卷没挂或者用了匿名卷。每次重建容器都是空的数据目录，Caddy 只能重新签。Let's Encrypt 对同一组域名有每周 5 张的限制，撞上就得等七天。把 caddy_data 挂成命名卷或者宿主目录，这个问题就消失了。

11. 什么场景选 Caddy #

场景 建议 理由
个人博客、小团队官网 Caddy 配置量少一个数量级，证书零维护
前后端分离 + 本地开发内网 HTTPS Caddy local CA 直接给 .localhost 发证书，不用自签
多副本后端 + 健康检查 Caddy lb_policy 和主被动健康检查开箱可用
内网服务加一层 Basic Auth / SSO 网关 Caddy basic_auth、forward_auth 都是一行
高并发静态资源分发 Nginx 单机极限吞吐与内存占用更优，调优手段更多
需要大量第三方模块（WAF、缓存、特殊协议） Nginx Caddy 装插件要重编译二进制，运维成本高
需要在运行时动态改路由 Caddy admin API 直接 POST JSON 就能改，不用碰文件

最后一行的 admin API 是个被低估的能力。整个配置就是一个 JSON 文档，改某一棵子树可以直接 PATCH，Caddy 会做增量更新，只动受影响的部分。做多租户平台、动态路由下发这类需求时，这个接口比"生成配置文件然后 reload"干净得多。

12. 运维 Checklist #

  • caddy version
  • 数据目录（/data 或 /var/lib/caddy
  • caddy validate
  • 用 systemctl reload caddy
  • systemd 里配了 RestartPreventExitStatus=1
  • admin API 只绑在 localhost:2019
  • 访问日志按大小切割，roll_keep 和 roll_keep_for
  • 有通配符需求的话，确认 DNS 插件已编译进来（caddy list-modules | grep dns
  • 敏感配置（DNS token 等）走环境变量或 EnvironmentFile
  • 本地开发证书用完 caddy untrust
  • 定期 caddy fmt --diff
