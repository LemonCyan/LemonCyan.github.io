Cloudflare Tunnel 内网穿透与零信任访问实战指南

Cloudflare Tunnel 终极实战指南：从零打通内网服务公网访问与零信任安全架构 #

把内网服务（如家庭 NAS、开发环境、Wiki、个人博客、SSH 终端）暴露到公网，是每个搞 homelab 和后端开发哥们的刚需。但传统的方案总有一堆让人抓狂的痛点：

  1. 没有公网 IP：找运营商要公网 IPv4 难如登天，绝大多数宽带都被扔在大内网 NAT 里；
  2. 端口转发风险极大：即使有公网 IP，在路由器上大开端口，分分钟被公网全网扫描器肉鸡爆破，NAS 里的个人照片和重要代码随时可能中招勒索病毒；
  3. 自建 FRP 中继机带宽太贵：买台带公网 IP 的云服务器做 FRP/NPS 转发，小水管带宽贵得肉疼，多几个人访问直接卡死。

Cloudflare Tunnel（也就是大家熟知的 cloudflared，早年叫 Argo Tunnel）正是为了彻底终结这套恶心流程而生。它的核心逻辑是：内网服务器只主动向 Cloudflare 边缘节点发起加密的出站连接（Outbound Connection），完全不需要公网 IP、不需要在路由器上做端口映射、不需要放行入站防火墙，即可通过 Cloudflare 的全球 Anycast CDN 网络把内网 HTTP、WebSocket、TCP、SSH 等服务安全发布到你的独立域名上，同时白嫖 Cloudflare 的免费 DDoS 防护、自动 HTTPS 证书与 Zero Trust 零信任安全策略。

本文将以一线极客实战视角，全盘梳理从域名接入、多平台安装、生产级 YAML Ingress 配置、Systemd 守护进程、SSH 零信任免密穿透、性能调优到避坑排错的完整实战闭环。

1. 核心架构与工作原理解析 #

为什么说这种架构极其安全？ #

  • 零入站开放（Zero Inbound Ports）：内网防火墙可以把所有入站端口（Inbound）全部封死，cloudflared 只需要能够访问公网的 443 端口即可建立出站隧道；
  • 隐藏真实源站 IP：外部任何访客只能解析到 Cloudflare 的 Anycast 节点 IP，完全探测不到你的真实家庭宽带或局域网 IP；
  • 原生内置安全防护：自带全球顶级 DDoS 防护、Web 应用程序防火墙（WAF）、自动更新的 SSL/TLS 证书，以及基于身份验证的 Zero Trust Access 策略。

2. 前置准备与域名接入 Cloudflare #

2.1 准备清单 #

  • 已注册的独立域名：可在阿里云、腾讯云、Namecheap、GoDaddy 或 Cloudflare Registrar 购买（推荐 .com、.net、.top、.xyz 等标准国际域名）；
  • 内网主机：任意一台能够 24 小时开机的机器（Linux 服务器、树莓派、群晖 NAS、Windows PC 或 Mac mini）；
  • Cloudflare 免费账号：注册即可，完全不需要绑定信用卡。

2.2 域名接入与 NS 记录切换 #

  1. 登录 Cloudflare Dashboard；
  2. 点击右上角 Add a Site，输入你的根域名（例如 example.com）；
  3. 计划选择 Free（免费版）；
  4. Cloudflare 会自动扫描你原有的 DNS 记录，确认无误后点击继续；
  5. 系统会分配两个 Nameserver（NS）地址，例如：
    text
    alice.ns.cloudflare.com
bob.ns.cloudflare.com
  6. 登录你的域名注册商控制台（例如阿里云万网或腾讯云 DNSPod），将域名的 DNS 服务器修改为 Cloudflare 分配的上述两个 NS 地址。
❢重要

NS 修改注意事项：

  • 格式必须纯净，不要带 https://，末尾切勿加点号；
  • 国内注册商的 .cn 域名必须完成实名认证才允许修改境外 NS；
  • 修改后全球 DNS 传播通常需要 5 分钟到 48 小时不等。

2.3 验证 NS 是否生效 #

在终端通过 dig 或 nslookup 查询：

bash
# Linux / macOS / Windows PowerShell
nslookup -type=ns example.com
# 或者
dig ns example.com +short

当输出显示为 *.ns.cloudflare.com，且 Cloudflare 控制台对应站点状态变为 Active 时，准备工作即告完成。

3. 开通 Zero Trust 与创建 Tunnel #

Cloudflare Tunnel 的管理中枢位于 Zero Trust 控制台。

3.1 初始化 Zero Trust 团队 #

  1. 在 Cloudflare Dashboard 左侧边栏点击 Zero Trust；
  2. 首次进入会提示创建 Organization 团队名称（例如输入 my-homelab），系统将生成对应的团队域 my-homelab.cloudflareaccess.com；
  3. 选择免费计划（Free Plan，支持最多 50 个免费用户席位，对个人和团队极其充裕）。

3.2 创建隧道（Create Tunnel） #

  1. 在 Zero Trust 面板左侧导航栏依次点击：Networks -> Tunnels；
  2. 点击 Create a tunnel 按钮；
  3. 选择 Connector 类型为 Cloudflared，点击 Next；
  4. 给你的隧道起个好认的名字（如 homelab-gateway），点击 Save tunnel；
  5. 此时控制台会展示针对不同操作系统的安装命令和专属 Token 令牌。

4. 全平台安装 Cloudflared 客户端 #

根据你内网宿主机的操作系统，选择对应的安装方式：

4.1 Linux（Debian / Ubuntu / PVE / 树莓派） #

bash
# 1. 下载官方 AMD64 或 ARM64 安装包
# AMD64 架构：
curl -L --output cloudflared.deb https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64.deb

# ARM64 / 树莓派 64位架构：
# curl -L --output cloudflared.deb https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-arm64.deb

# 2. 安装软件包
sudo dpkg -i cloudflared.deb

# 3. 验证安装版本
cloudflared --version

4.2 Linux（CentOS / RHEL / Rocky Linux） #

bash
# 下载二进制文件
wget https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64
chmod +x cloudflared-linux-amd64
sudo mv cloudflared-linux-amd64 /usr/local/bin/cloudflared

# 验证安装
cloudflared --version

4.3 macOS #

bash
# 使用 Homebrew 安装
brew install cloudflare/cloudflare/cloudflared

# 验证安装
cloudflared --version

4.4 Windows #

  1. 下载 Windows 64 位可执行文件： https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-windows-amd64.exe
  2. 将其重命名为 cloudflared.exe；
  3. 移动到 C:\Windows\System32\，或自定义目录并加入系统 PATH 环境变量；
  4. 在 PowerShell 中验证：
    powershell
    cloudflared.exe --version

4.5 Docker / Docker Compose 容器化部署 #

如果你喜欢用 Docker 统一管理，可以直接启动官方镜像：

yaml
# docker-compose.yml

services:
  cloudflared:
    image: cloudflare/cloudflared:latest
    container_name: cloudflared

    command: tunnel run --token YOUR_TUNNEL_TOKEN_HERE

5. 双配置模式深度对比：Dashboard 模式 vs 本地 YAML 模式 #

在配置路由规则时，Cloudflare 提供了两种模式：

对比维度 方案 A：Web Dashboard 远程托管模式 方案 B：本地 config.yml 文件模式 (推荐)
配置位置 Cloudflare 网页后台 (Public Hostnames) 内网机器本地文件 /etc/cloudflared/config.yml
操作体验 图形化点击，上手最快 代码化、可纳入 Git 版本控制、便于备份
高级能力 支持基础 HTTP/HTTPS、SSH 支持精细化路径路由、正则重写、连接池微调、自签名证书忽略、WebSocket 深度调优
多环境协作 依赖网页登录 支持本地脚本自动化批量部署
✦提示

极客最佳实践：初学者可以直接在 Dashboard 上添加 Public Hostname；而追求可维护性与复杂微服务架构的开发者，强烈推荐采用本地 config.yml 模式。

6. 本地 YAML 模式生产级 Ingress 路由配置 #

这是整个 Tunnel 部署中最具含金量的部分。通过单个配置文件，即可统一代理内网所有 Web、NAS、Wiki、自签名 HTTPS、WebSocket 及 SSH 服务。

6.1 初始化凭证与配置文件 #

如果你使用命令行创建隧道，可以通过以下命令登录并生成证书：

bash
# 1. 登录并拉取账户凭证 cert.pem
cloudflared tunnel login

# 2. 创建一个名为 homelab 的隧道
cloudflared tunnel create homelab

命令执行后，终端会输出生成的 Tunnel UUID，并在 ~/.cloudflared/ 目录下生成 <Tunnel-UUID>.json 凭证文件。

bash
# 创建系统配置主目录
sudo mkdir -p /etc/cloudflared

# 将凭证文件移动到系统目录
sudo cp ~/.cloudflared/*.json /etc/cloudflared/

6.2 编写全功能 /etc/cloudflared/config.yml #

创建并编辑配置文件：

bash
sudo nano /etc/cloudflared/config.yml

写入以下经过生产验证的完整配置模板：

yaml
# ==========================================
# Cloudflare Tunnel 生产级 Ingress 配置文件
# ==========================================

# 1. 隧道标识 (填写隧道名称或 Tunnel UUID)
tunnel: homelab

# 2. 凭证文件绝对路径 (替换为你实际的 UUID)
credentials-file: /etc/cloudflared/a1b2c3d4-e5f6-7890-abcd-ef1234567890.json

# 3. 全局运行参数与连接池微调
loglevel: info
logfile: /var/log/cloudflared.log
transport-loglevel: warn

# 4. 入站流量路由规则列表 (从上到下按顺序匹配)
ingress:
  # ----------------------------------------------------
  # 规则 1：标准本地 Web 前端 (Node.js / React / Vue / Hexo)
  # ----------------------------------------------------
  - hostname: app.example.com
    service: http://127.0.0.1:3000
    originRequest:
      connectTimeout: 30s
      noChunkedEncoding: false

  # ----------------------------------------------------
  # 规则 2：路径分流规则 (将特定 API 路由转给后端微服务)
  # ----------------------------------------------------
  - hostname: api.example.com
    path: ^/v1/.*
    service: http://127.0.0.1:8000

  - hostname: api.example.com
    service: http://127.0.0.1:8080

  # ----------------------------------------------------
  # 规则 3：局域网私有 Wiki 知识库
  # ----------------------------------------------------
  - hostname: wiki.example.com
    service: http://192.168.1.55:8080

  # ----------------------------------------------------
  # 规则 4：群晖 NAS / PVE 宿主机 (自签名 HTTPS 证书服务)
  # 必须开启 noTLSVerify: true，否则握手会报 502
  # ----------------------------------------------------
  - hostname: nas.example.com
    service: https://192.168.1.100:5000
    originRequest:
      noTLSVerify: true
      httpHostHeader: nas.example.com

  # ----------------------------------------------------
  # 规则 5：实时 WebSocket 服务
  # ----------------------------------------------------
  - hostname: ws.example.com
    service: http://127.0.0.1:9000
    originRequest:
      httpHostHeader: ws.example.com
      noTLSVerify: true

  # ----------------------------------------------------
  # 规则 6：SSH 远程终端连接 (配合 Cloudflare Access 使用)
  # ----------------------------------------------------
  - hostname: ssh.example.com
    service: ssh://127.0.0.1:22

  # ----------------------------------------------------
  # 规则 7：原生 TCP 端口代理 (如 MySQL 数据库)
  # ----------------------------------------------------
  - hostname: db.example.com
    service: tcp://127.0.0.1:3306

  # ----------------------------------------------------
  # 规则 8：兜底匹配规则 (CRITICAL: 必须放在最后一行!)
  # 所有未命中的未知域名一律返回 404，防止流量悬空
  # ----------------------------------------------------
  - service: http_status:404

6.3 配置语法自检 #

在启动服务前，务必运行校验命令，避免因 YAML 缩进错误导致启动崩溃：

bash
sudo cloudflared tunnel --config /etc/cloudflared/config.yml ingress validate

若返回：

text
Validating rules from /etc/cloudflared/config.yml
OK

说明配置语法完全正确！

7. 绑定 DNS 记录与公共主机名 #

配置文件写好了，还需要让域名解析指向这个隧道。

方式 A：通过 Dashboard 自动关联 #

在 Zero Trust 控制台 -> Networks -> Tunnels -> 点击你的隧道 -> Public Hostname -> Add a public hostname：

  • Subdomain：app
  • Domain：example.com
  • Type：HTTP
  • URL：127.0.0.1:3000 保存后，Cloudflare 会在你的 DNS 表里自动添加一条指向该隧道的 CNAME 记录。

方式 B：通过 CLI 快速绑定 DNS #

bash
# 自动在 Cloudflare DNS 中添加对应的 CNAME 记录
cloudflared tunnel route dns homelab app.example.com
cloudflared tunnel route dns homelab wiki.example.com
cloudflared tunnel route dns homelab nas.example.com
cloudflared tunnel route dns homelab ssh.example.com

方式 C：在 DNS 管理面板手动添加 CNAME #

  • 记录类型：CNAME
  • 名称（Host）：app（代表 app.example.com）
  • 目标内容（Target）：<Tunnel-UUID>.cfargotunnel.com
  • 代理状态：必须开启（橙色小云朵，Proxied）

8. 配置 Systemd 守护进程与开机自启 #

为了保证服务器重启后隧道能够自动拉起，必须配置为操作系统原生服务。

8.1 方案一：使用 cloudflared 自带的服务安装命令（推荐） #

bash
# 卸载旧服务（如果之前装过）
sudo cloudflared service uninstall

# 基于指定的 YAML 配置文件安装系统服务
sudo cloudflared --config /etc/cloudflared/config.yml service install

# 启动服务并设置开机自启
sudo systemctl enable --now cloudflared

8.2 方案二：手动手搓 Systemd 服务单元 #

创建 /etc/systemd/system/cloudflared.service：

ini
[Unit]
Description=Cloudflare Tunnel Agent
After=network-online.target
Wants=network-online.target

[Service]
Type=notify
User=root
ExecStart=/usr/local/bin/cloudflared tunnel --config /etc/cloudflared/config.yml --no-autoupdate run
Restart=on-failure
RestartSec=5s
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target

执行生效命令：

bash
sudo systemctl daemon-reload
sudo systemctl enable --now cloudflared

8.3 状态检查与实时日志排查 #

bash
# 查看服务运行状态 (应该看到 active (running))
sudo systemctl status cloudflared

# 查看实时滚动日志
sudo journalctl -u cloudflared -f -n 50

9. SSH 远程访问全场景攻防实战 #

通过 Cloudflare Tunnel 暴露 SSH 具有极高安全性，公网端口完全封闭，防止任何爆破脚本扫描。

sequenceDiagram
    autonumber
    actor Admin as 👨‍💻 开发者终端
    participant CF_Auth as 🔐 Cloudflare Access SSO
    participant CF_Edge as ☁️ Cloudflare Edge
    participant Local_Agent as 🖥️ 内网 cloudflared
    participant SSHD as 🔒 本地 sshd (Port 22)

    Admin->>CF_Edge: 发起 SSH 握手 (ssh user@ssh.example.com)
    CF_Edge-->>CF_Auth: 拦截未认证请求
    CF_Auth-->>Admin: 弹出浏览器单点登录与 MFA 认证
    Admin->>CF_Auth: 提交身份凭据通过验证
    CF_Auth->>CF_Edge: 下发短期加密访问 Token
    CF_Edge->>Local_Agent: 建立双向 WebSocket / TCP 隧道
    Local_Agent->>SSHD: 转发原始流量到 127.0.0.1:22
    SSHD-->>Admin: 成功建立终端会话！

9.1 姿势一：客户端 ProxyCommand 代理（极客最爽姿势） #

1. 客户端电脑安装 cloudflared #

  • macOS：brew install cloudflare/cloudflare/cloudflared
  • Windows：下载 cloudflared.exe 并配置到环境变量 PATH 中；
  • Linux：按前文方式下载安装对应二进制。

2. 配置本地 ~/.ssh/config #

在你的个人电脑（客户端）上编辑 ~/.ssh/config 文件，追加以下内容：

text
# Cloudflare Tunnel 穿透 SSH 专用配置
Host ssh.example.com
    ProxyCommand cloudflared access ssh --hostname %h
    User root
    IdentityFile ~/.ssh/id_rsa

3. 直接敲 SSH 连接 #

bash
ssh root@ssh.example.com

神奇的体验发生了：终端会自动唤起默认浏览器，打开 Cloudflare 登录页面完成身份认证；认证通过后，终端瞬间直通内网服务器控制台！

9.2 姿势二：Cloudflare Access 零信任安全策略加固 #

为了防止任何未授权人员访问你的 SSH 和内部系统，必须在 Cloudflare Zero Trust 后台配置拦截策略：

  1. 进入 Zero Trust -> Access -> Applications -> 点击 Add an application；
  2. 选择 Self-hosted；
  3. Application configuration：
    • Application name: Homelab SSH
    • Application domain: ssh.example.com
  4. Add policies（定义访问权限）：
    • Policy name: Allow Dev Team
    • Action: Allow
    • Configure rules（按需组合）：
      • Include -> Emails -> 输入你的专属邮箱（例如 yourname@gmail.com）；
      • 或者 Email domains ending in -> @yourcompany.com；
      • 或者 Country -> 仅允许特定国家/地区 IP 访问。
  5. 保存应用。现在任何人直接用 IP 或未认证的浏览器访问 ssh.example.com，都会被 Cloudflare 的零信任防火墙死死拦在门外。

10. 性能调优与高可用进阶 #

10.1 连接池与传输优化 #

在 /etc/cloudflared/config.yml 的 originRequest 中增加连接池配置，能显著降低反复建连导致的握手延迟：

yaml
originRequest:
  # 开启长连接复用
  keepAliveConnections: 100
  keepAliveTimeout: 90s
  
  # 握手超时与响应超时
  connectTimeout: 10s
  tlsTimeout: 10s
  
  # 禁用分块编码 (对某些遗留后端有奇效)
  disableChunkedEncoding: true

10.2 多节点冗余负载均衡（High Availability） #

如果你在内网有多台服务器（例如一台在 PVE、一台在物理机），可以让它们运行相同的 Tunnel Token：

  1. 在两台机器上均安装 cloudflared 并启动相同隧道；
  2. Cloudflare Anycast 会自动在两个 Connector 之间做心跳检测与负载均衡；
  3. 当其中一台服务器断电或宕机时，流量在几秒内自动无缝漂移到另一台健康节点，实现真正的双机热备。

11. 踩坑避坑指南（常见报错一网打尽） #

坑点 1：浏览器访问报 502 Bad Gateway #

  • 排查步骤：
    1. 确认内网本地服务是否正常运行：curl http://127.0.0.1:3000；
    2. 确认服务监听的是 0.0.0.0 还是 127.0.0.1。若服务运行在 Docker 容器内且未使用 host 网络模式，localhost 会指向 cloudflared 容器自身，应填写容器 IP 或网桥 IP（如 172.17.0.1:3000）；
    3. 代理群晖、PVE 等 HTTPS 管理后台时，必须在 YAML 中添加 noTLSVerify: true，否则 Cloudflared 校验自签名证书失败会直接抛出 502。

坑点 2：提示 Unauthorized 或 SSH 握手反复重定向 #

  • 排查步骤：
    1. 检查客户端 cloudflared 与服务端版本是否脱节过大，建议执行 cloudflared update 保持最新；
    2. 检查 Cloudflare Access 策略中的邮箱白名单是否输入有误；
    3. 清理浏览器中的 Cookie 缓存，或在命令行运行 cloudflared access login ssh.example.com 重新生成凭证。

坑点 3：免费版文件上传大小限制（HTTP 413 Payload Too Large） #

  • 现象：通过 Cloudflare Tunnel 上传超过 100MB 的大文件（如向 NAS 上传镜像）时报错。
  • 原因：Cloudflare 免费版对经过 CDN 代理的 HTTP POST Body 默认限制为 100MB。
  • 应对方案：
    1. 纯私有大文件传输与全内网互通，建议搭配 Tailscale 内网穿透与异地虚拟组网实战指南 走 P2P 直连，完全不受任何流量和文件大小限制；
    2. 或者使用分片上传机制（Chunked Upload）将大文件切片为 50MB 分块分批提交。

坑点 4：国内访问延迟波动与线路优化 #

  • 原因：Cloudflare 免费 Anycast 节点对国内三大运营商的路由策略可能会绕道美西或欧洲，导致首包延迟在 150ms~300ms 左右。
  • 优化：在 Cloudflare Dashboard 开启 HTTP/3 (QUIC) 支持与 0-RTT 连接恢复；对于高频交互的静态资源，开启 Cloudflare Page Rules 页面缓存规则，让大部分静态文件直接命中边缘节点。
