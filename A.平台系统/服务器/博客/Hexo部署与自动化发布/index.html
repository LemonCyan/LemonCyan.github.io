Hexo 部署与自动化发布全栈实战 #

构建现代个人技术博客与知识库的核心设计思想是 「源码与静态产物解耦」。通过将 Hexo Markdown 源文件、主题配置及私有脚本保存在私有仓库中，利用云端 CI/CD（如 GitHub Actions）在容器中自动编译构建，再将生成的静态 HTML/CSS/JS 文件分发到全球托管平台（如 GitHub Pages、Cloudflare Pages 或自建 VPS），实现 “本地专注写作，Git 推送即刻全球发布” 的极致工作流。

2. 仓库架构设计与安全隔离机制 #

为了确保核心私密数据、Obsidian 草稿及图床资源井井有条，推荐采用 多仓库/分支分离架构：

2.1 各仓库与分支职责划分 #

  1. 源码仓库（私有，如 BlogDeploy）：
    • 存放全站的核心源文件、Markdown 笔记、站点与主题配置文件。
    • 私有化保障：未公开发布的草稿（_drafts/）与敏感私有配置不会泄露到公网。
  2. 发布仓库（公有，如 username.github.io）：
    • 仅存放 Hexo 编译输出的 public/ 静态网页。
    • 在该仓库的 Settings > Pages 中将构建源设为 main 分支根目录 /，即可对外服务。
  3. 图床仓库 / 分支（如 username.github.io@ImageBed）：
    • 集中存储博客引用的高清插图与动图。
    • 访问链接采用 CDN 加速：https://cdn.jsdelivr.net/gh/username/username.github.io@ImageBed/2026/image.png。

4. 本地环境初始化与核心命令大全 #

4.1 Hexo CLI 核心指令全景速查 #

bash
# 1. 全局安装 Hexo 脚手架工具
npm install -g hexo-cli

# 2. 清理本地缓存与旧构建输出 (删除 db.json 与 public 文件夹)
hexo clean

# 3. 编译生成静态 HTML 文件 (输出至 public/ 目录)
hexo generate               # 简写: hexo g

# 4. 开启本地预览调试服务器 (支持热重载，默认端口 4000)
hexo server                 # 简写: hexo s

# 5. 常用参数扩展
hexo s -p 9050              # 指定端口为 9050
hexo s -i 192.168.1.100     # 绑定特定 IP 供局域网移动端设备访问
hexo s -s                   # 静态模式 (仅提供静态文件服务，不监听变动)

# 6. 新建文章或独立页面
hexo new "文章标题"          # 简写: hexo n "文章标题"
hexo new page tags          # 创建标签单页

# 7. 一键构建并推送到部署远端
hexo deploy                 # 简写: hexo d

5. GitHub Actions 自动化 CI/CD 全流程实战 #

利用 GitHub Actions，可以在每次 git push 到源码仓库 main 分支时，自动启动 Ubuntu 容器完成依赖拉取、时间戳恢复、主题配置注入、静态网页生成并安全推送到 username.github.io。

sequenceDiagram
    autonumber
    actor Dev as 本地博主 (Obsidian / Git)
    participant SourceRepo as 源码私有仓 BlogDeploy
    participant Runner as GitHub Actions Runner (Ubuntu)
    participant TargetRepo as 发布公有仓 username.github.io

    Dev->>SourceRepo: 1. git push origin main (提交新文章)
    SourceRepo->>Runner: 2. 触发 push 事件，启动容器作业
    Runner->>Runner: 3. Checkout 全量提交历史 (fetch-depth: 0)
    Runner->>Runner: 4. 执行 git log 恢复各文件真实修改时间戳
    Runner->>Runner: 5. 安装 Node.js 20 与 npm 依赖缓存
    Runner->>Runner: 6. 注入 _config.theme.yml 并执行 hexo generate
    Runner->>TargetRepo: 7. 利用 Deploy Key 推送 public/ 至 main 分支
    TargetRepo-->>Dev: 8. GitHub Pages 自动上线，发送完成通知

5.1 配置 SSH Deploy Key 跨仓库免密授权 #

由于 CI/CD 流水线运行在源码仓库中，需要向独立的发布仓库推送代码，必须配置专用的 SSH Deploy Key 密钥对：

  1. 在本地生成专用部署密钥对：
    bash
    ssh-keygen -t rsa -b 4096 -C "deploy@github.com" -f ./github-deploy-key -N ""
    得到两个文件：github-deploy-key（私钥）与 github-deploy-key.pub（公钥）。
  2. 发布仓库添加公钥（Public Key）：
    • 打开 username.github.io 仓库 -> Settings > Deploy keys > Add deploy key。
    • 粘贴 github-deploy-key.pub 内容，务必勾选 Allow write access（允许写入权限），保存。
  3. 源码仓库添加私钥（Private Key Secret）：
    • 打开 BlogDeploy 仓库 -> Settings > Secrets and variables > Actions > New repository secret。
    • Secret 名称填 ACTIONS_DEPLOY_KEY，值粘贴 github-deploy-key（私钥完整内容）。

5.2 生产级自动化工作流配置（.github/workflows/blogPublish.yml） #

在源码仓库创建 .github/workflows/blogPublish.yml：

yaml
name: Deploy Hexo Site

on:
  push:
    branches:
      - main  # 监听 main 分支推送

# 允许并发时自动取消旧任务，避免资源竞争
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout source code
        uses: actions/checkout@v4
        with:
          persist-credentials: true
          # 必须设为 0（拉取全量 Git 历史），以便恢复真实时间戳
          fetch-depth: 0
          token: ${{ secrets.ACTIONS_DEPLOY_KEY }}

      - name: Setup Node.js Environment
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'  # 开启 npm 依赖缓存，大幅加快构建速度

      - name: Restore File Modification Timestamp
        run: |
          echo "正在根据 Git 提交历史恢复文章真实修改时间戳..."
          git ls-files -z | while read -d '' path; do 
            touch -d "$(git log -1 --format="@%ct" "$path")" "$path"
          done
          echo "时间戳恢复完成！"

      - name: Install Dependencies
        run: |
          npm ci || npm install
          npm install -g hexo-cli
          npm install hexo-theme-stellar

      - name: Inject Theme Configurations
        run: |
          # 自动将源码根目录下的主题配置复制到 node_modules 主题目录下
          if [ -f "_config.theme.stellar.yml" ]; then
            cp _config.theme.stellar.yml node_modules/hexo-theme-stellar/_config.yml
          fi
          if [ -f "_config.theme.stellar.widgets.yml" ]; then
            cp _config.theme.stellar.widgets.yml node_modules/hexo-theme-stellar/_data/widgets.yml
          fi

      - name: Generate Static Files
        run: |
          hexo clean
          hexo generate

      - name: Deploy to GitHub Pages
        uses: peaceiris/actions-gh-pages@v3
        with:
          external_repository: your-username/your-username.github.io
          publish_branch: main
          publish_dir: ./public
          personal_token: ${{ secrets.ACTIONS_DEPLOY_KEY }}
          user_name: 'github-actions[bot]'
          user_email: 'github-actions[bot]@users.noreply.github.com'
          commit_message: "Automated Deploy by GitHub Actions: ${{ github.sha }}"

      - name: Send Notification Webhook (Optional)
        if: always()
        run: |
          echo "部署作业完成，状态: ${{ job.status }}"
          # 可选：向钉钉/企业微信/飞书群机器人发送构建卡片通知

6. 核心技术陷阱：解决 CI 构建导致的「文章更新时间全部重置」 #

6.1 问题根本原因 #

Git 在分布式传输与检出时，默认不保留文件的物理系统修改时间（mtime）。在 GitHub Actions 虚拟机中运行 git clone 后，所有 .md 文件的系统修改时间都会变成当次 CI 运行的当前时间戳。 由于 Hexo 默认在 Front-matter 未显式声明 updated 时，会回退读取文件的系统 mtime 作为文章的「最后更新时间」，导致每次哪怕只改了一个错别字推送，全站数百篇文章的更新时间全部被刷新成今天。

6.2 解决方案与原理剖析 #

通过在 hexo generate 之前执行 Git 历史回溯脚本：

bash
git ls-files -z | while read -d '' path; do 
  touch -d "$(git log -1 --format="@%ct" "$path")" "$path"
done
  • git log -1 --format="@%ct" "$path"：提取该文件在 Git 历史中最近一次实际被 commit 修改的 Unix 时间戳。
  • touch -d：将文件的系统修改时间强制修正为该提交时间戳。
  • 配合 actions/checkout@v4 中的 fetch-depth: 0，完美恢复每篇文章真实无误的修改历史。

7. Cloudflare Pages 边缘双轨加速部署方案 #

如果你希望同时部署在 Cloudflare Pages，享受全球 Anycast CDN 边缘网络毫秒级首屏加载：

7.1 方案 A：Cloudflare 控制台与 GitHub 源码仓原生集成（最推荐） #

  1. 登录 Cloudflare Dashboard，进入 Workers & Pages > Create application > Pages > Connect to Git。
  2. 授权并选择私有源码仓库 BlogDeploy。
  3. 配置构建设置：
    • Framework preset：选择 None。
    • Build command：npm install && npm install -g hexo-cli && hexo generate。
    • Build output directory：public。
    • Environment variables：添加 NODE_VERSION = 20。
  4. 点击「Save and Deploy」，此后每次向 GitHub 推送代码，Cloudflare 会在数十秒内自动完成全球边缘分发。

7.2 方案 B：使用 Wrangler CLI 命令行直接推送编译产物 #

bash
# 1. 安装 Wrangler CLI 工具
npm install -g wrangler

# 2. 本地编译静态文件
hexo clean && hexo generate

# 3. 部署到 Cloudflare Pages
wrangler pages deploy ./public --project-name=my-hexo-blog

如果你拥有一台独立云服务器，希望实现本地推送到自建服务器直接自动上线：

graph LR

8.1 编写 /srv/git/blog.git/hooks/post-receive 部署钩子 #

bash
#!/usr/bin/env bash
DEPLOY_DIR="/var/www/blog"
GIT_DIR="/srv/git/blog.git"

echo "=========================================="
echo "🚀 收到推送，正在自动部署静态博客至 $DEPLOY_DIR"
echo "=========================================="

mkdir -p $DEPLOY_DIR
git --work-tree=$DEPLOY_DIR --git-dir=$GIT_DIR checkout -f main

# 修正权限
chown -R www-data:www-data $DEPLOY_DIR
chmod -R 755 $DEPLOY_DIR

echo "✅ 博客自动部署完成！"

bash

9. 自定义域名与 DNS 全局智能解析配置 #

将个人专属域名绑定至托管平台并实现全网 HTTPS 加速：

9.1 GitHub Pages 自定义域名配置 #

  1. 在 source/ 根目录下创建 CNAME 文件（注意无扩展名），写入你的自定义域名：
    text
    blog.example.com
  2. 在 DNS 控制台添加解析记录：
    • 主机记录：blog
    • 记录类型：CNAME
    • 记录值：your-username.github.io.
  3. 进入发布仓库 Settings > Pages > Custom domain，勾选 Enforce HTTPS。

9.2 Cloudflare 根域名（Apex Domain）CNAME 扁平化 #

如果想用不带 www 的顶级域名（如 example.com）直接访问博客，由于传统 DNS 规范中根域名不能配置 CNAME：

  • 推荐使用 Cloudflare 作为 DNS 解析商，开启 CNAME Flattening（CNAME 扁平化） 功能，即可将顶级域名直接指向 your-username.github.io，由 Cloudflare 自动解析为 A 记录并开启 HTTPS 加速。

14. 自动化百度与 Bing 搜索引擎收录提交（SEO API 推送） #

为使新发布的博客文章在数分钟内被百度和 Bing 索引收录，可以在 GitHub Actions 构建成功后，自动提取 public/sitemap.xml 或新文章 URL 并调用搜索引擎 API 推送：

yaml
      - name: Auto Push URLs to Baidu & Bing Webmaster
        if: success()
        run: |
          echo "正在向百度与 Bing 提交最新文章链接..."
          # 提取 sitemap 中的所有 URL
          grep -Eo 'https://[a-zA-Z0-9./?=_-]+' public/sitemap.xml | sort -u > urls.txt
          
          # 1. 提交至百度站长平台 API
          curl -H 'Content-Type:text/plain' --data-binary @urls.txt             "http://data.zz.baidu.com/urls?site=https://your-domain.com&token=${{ secrets.BAIDU_PUSH_TOKEN }}"
          
          # 2. 提交至 Bing IndexNow API
          curl -X POST -H 'Content-Type: application/json'             -d "{"host":"your-domain.com","key":"${{ secrets.INDEXNOW_KEY }}","urlList":$(jq -R -s -c 'split("\n")[:-1]' urls.txt)}"             "https://api.indexnow.org/indexnow"
          
          echo "SEO API 提交完成！"

故障现象 根因剖析 快速解决对策
部署后页面白屏 / CSS JS 404 _config.yml 中的 url 或 root 路径配置不正确（例如二级域名缺少子路径前缀） 检查 _config.yml，若部署在根目录，确保 root: /；若在 username.github.io/blog，需设置 root: /blog/
GitHub Actions 报错 Host key verification failed 工作流未正确配置 ACTIONS_DEPLOY_KEY 或公钥未赋予写入权限 重新核对私钥内容，并确保发布仓库 Deploy Keys 中勾选了 Allow write access
CI 构建报错 JavaScript heap out of memory 博客文章数量过多（上千篇）导致 Node.js 内存溢出 在 CI 环境变量中添加 NODE_OPTIONS: "--max-old-space-size=4096" 调大内存上限
推送后 GitHub Pages 未更新 浏览器强缓存或 GitHub Pages 处于编译排队中 按 Ctrl + F5 强制刷新，或在 GitHub Pages 设置中重新切换一次部署分支触发重构
自定义域名访问显示 404 CNAME reset 每次 hexo g 重新生成时覆盖了 public/CNAME 务必确保 CNAME 文件放置在 source/CNAME 下，而非手动放到 public/ 目录下
