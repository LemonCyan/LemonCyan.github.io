I2C 控制器驱动在 Linux 里叫 adapter driver，也叫 bus driver、controller driver。它要干的事只有一件：把一颗 SoC 的 I2C 寄存器操作，翻译成 core 认识的 struct i2c_algorithm 回调，然后挂到 i2c_bus_type 上。这篇就讲怎么把它填满。

边界先说清。本篇是 provider 侧，回答「怎么写一个控制器驱动」。core 层怎么组织、总线怎么匹配、i2c_client 怎么来，看同目录的《I2C 驱动框架与核心结构》；本篇只在需要衔接时点一句。具体平台从寄存器到能通信的完整推演，看《Exynos4412 I2C 驱动开发实战》。挂在一根总线下面的 OLED、AT24C08 这类设备的驱动，看《I2C 设备驱动实战：OLED 与 AT24C08》。本篇不讲 consumer 侧怎么写 i2c_driver，也不逐个寄存器讲时序图——那是裸机手册的活。

内核版本基线：素材主体来自 3.x 内核（drivers/i2c/i2c-core.c 还是独立文件，i2c_adapter 里还是 struct rt_mutex bus_lock），移植实录部分来自 4.x 的 i2c-s3c2410.c。凡是 4.x/5.x 才变动的地方，逐处标注。标「未验证」的，我没在对应版本源码里核对过。

一、controller driver 要做什么 #

先把职责列清，别一上来就啃寄存器。

职责 落到哪 说明
提供一个 struct i2c_algorithm adap->algo 至少 master_xfer + functionality
分配并初始化 struct i2c_adapter driver 私有结构体内嵌 名字、owner、retries、class、dev.parent
拿到寄存器基址并映射 devm_ioremap_resource() 资源来自 DT 的 reg 或 platform 资源
拿时钟并管理开关 devm_clk_get() / clk_prepare_enable() 传输前后反复开关
配置引脚复用 pinctrl 或 cfg_gpio 回调 SCL/SDA 两个脚，开漏
申请中断（如果控制器走中断） devm_request_irq() 轮询模式可跳过
算出分频写进控制器 clk_get_rate() 反推 目标是 100k/400k
注册适配器 i2c_add_adapter() 或 i2c_add_numbered_adapter() 注册后 core 会去解析子节点
注销并释放 i2c_del_adapter() 托管 API 下自动做

struct i2c_adapter 抽象一根物理 I2C 总线，连同访问它上面 slave 的那套算法。3.x 的定义长这样：

c
/* include/linux/i2c.h */
/*
 * i2c_adapter is the structure used to identify a physical i2c bus along
 * with the access algorithms necessary to access it.
 */
struct i2c_adapter {
        struct module *owner;
        unsigned int class;               /* classes to allow probing for */
        const struct i2c_algorithm *algo; /* the algorithm to access the bus */
        void *algo_data;

        /* data fields that are valid for all devices   */
        struct rt_mutex bus_lock;

        int timeout;                    /* in jiffies */
        int retries;
        struct device dev;              /* the adapter device */

        int nr;
        char name[48];
        struct completion dev_released;

        struct mutex userspace_clients_lock;
        struct list_head userspace_clients;

        struct i2c_bus_recovery_info *bus_recovery_info;
};

逐字段过一遍，重点在你要填哪几个：

  • owner：填 THIS_MODULE。core 会用它做引用计数。
  • class：这条总线上允许探测哪些类型的 slave。只有类型匹配的设备才能绑上来。取值（include/linux/i2c.h）：I2C_CLASS_HWMON 硬件监控（lm-sensors 那类）、I2C_CLASS_DDC 显示通道，用来读显示器信息、I2C_CLASS_SPD 存储类模组、I2C_CLASS_DEPRECATED 已弃用的 class。用 DT 描述设备的驱动一般填 I2C_CLASS_DEPRECATED，等于关掉自动探测。
  • algo：指向你的 i2c_algorithm。这是驱动的主体。
  • algo_data：私有指针。惯例是回指你自己的控制器结构体，master_xfer 里从 adap->algo_data 取回来用。
  • bus_lock：core 内部锁，别动。5.x 里这行换成了 const struct i2c_lock_operations *lock_ops;（5.0 引入，用来支持锁定总线的实现差异；精确引入版本未验证），驱动仍然不应直接操作。
  • timeout：单位 jiffies。传输失败要不要重试、能重试多久，看它和 retries。
  • retries：重试次数。重试逻辑由 core 做，你只给数字。consumer 对返回时间有要求的，靠 timeout 兜住。
  • dev：适配器在设备模型里的体现。dev.parent 一般指回你的 platform device。
  • nr：总线号。体现在 /sys/bus/i2c/devices/i2c-n 里的 n。可以由 driver 直接赋值、从 DT 的 aliases 解析，或让 core 自动分配。
  • name：字符串，出现在 sysfs 和 log 里，长度上限 48。
  • dev_released：卸载时等设备真正释放用的 completion。
  • userspace_clients_lock / userspace_clients：给 i2c-dev 的用户态 client 用的链表和锁。
  • bus_recovery_info：总线卡死后的恢复钩子。要写的话看 Documentation/i2c/gpio-fault-injection 和 i2c_recover_bus()。

一句话记：必填的是 owner、algo、dev.parent、name，可选但有实际影响的是 class、retries、timeout、nr、algo_data、bus_recovery_info。

二、i2c_adapter 的分配与初始化 #

适配器内存谁分配，取决于你打算怎么管生命周期。三种写法，按项目内核版本挑。

写法一：直接内嵌在控制器结构体里。 这是最老的写法，i2c-s3c2410.c 就是这么干的：

c
struct s3c24xx_i2c {              /* 表示 SoC 的一个 I2C 控制器 */
        wait_queue_head_t       wait;
        kernel_ulong_t          quirks;

        struct i2c_msg          *msg;     /* 待发送的 I2C 数据包 */
        unsigned int            msg_num;  /* 数据包个数，实际只有 1 个 */
        unsigned int            msg_idx;
        unsigned int            msg_ptr;

        unsigned int            tx_setup; /* 延时，等 SCL 被释放 */
        unsigned int            irq;

        enum s3c24xx_i2c_state  state;    /* STATE_START/IDLE/STOP/WRITE/READ */
        unsigned long           clkrate;

        void __iomem            *regs;
        struct clk              *clk;
        struct device           *dev;     /* 存 platform 设备的 dev */
        struct i2c_adapter      adap;     /* 内嵌适配器 */

        struct s3c2410_platform_i2c     *pdata;
        int                     gpios[2];
        struct pinctrl          *pctrl;
#if defined(CONFIG_ARM_S3C24XX_CPUFREQ)
        struct notifier_block   freq_transition;
#endif
        struct regmap           *sysreg;
        unsigned int            sys_i2c_cfg;
};

整个结构体用一次 devm_kzalloc() 申请，adap 跟着走，不用单独 free，也不用单独写 release 回调。container_of(adap, struct s3c24xx_i2c, adap) 就能从适配器拿回控制器。

写法二：i2c_alloc_adapter() 单独分配。 3.x 有 i2c_alloc_adapter(sizeof_priv, THIS_MODULE)，分配 sizeof(struct i2c_adapter) + sizeof_priv 一块内存，返回的 adap 后面跟着私有区，用 i2c_get_adapdata()/i2c_set_adapdata() 存取。要用就得自己写 adap->dev.release 把它 kfree() 掉。这个接口在后续版本被移除，具体移除版本未验证，新代码别用。

写法三：托管注册，5.13+。 devm_i2c_add_adapter(dev, adap)，卸载时自动 i2c_del_adapter()，省掉 remove 里那一行。5.13 引入，用之前确认内核版本（未在更早版本上验证回移情况）。它管的是注册，不管 adap 本身的内存。

初始化顺序按依赖排，别乱：

c
static int foo_i2c_probe(struct platform_device *pdev)
{
        struct foo_i2c *priv;
        int ret;

        priv = devm_kzalloc(&pdev->dev, sizeof(*priv), GFP_KERNEL);
        if (!priv)
                return -ENOMEM;

        strscpy(priv->adap.name, "foo-i2c", sizeof(priv->adap.name));
        priv->adap.owner   = THIS_MODULE;
        priv->adap.algo    = &foo_i2c_algorithm;
        priv->adap.algo_data = priv;
        priv->adap.dev.parent = &pdev->dev;
        priv->adap.dev.of_node = pdev->dev.of_node;
        priv->adap.retries = 3;
        priv->adap.class   = I2C_CLASS_DEPRECATED;

        platform_set_drvdata(pdev, priv);
        /* ... 资源获取，见第九章 ... */

        ret = devm_i2c_add_adapter(&pdev->dev, &priv->adap);
        if (ret)
                return ret;

        return 0;
}

strlcpy 是老写法，5.x 起内核推 strscpy，两者语义有差别：strlcpy 返回源串长度，strscpy 返回实际拷贝长度或 -E2BIG。现代内核用 strscpy。

两个容易漏的点。adap.dev.of_node 一定要指过去，否则 i2c_add_adapter() 拿不到 of_alias_get_id，也拿不到 of_i2c_register_devices() 要解析的子节点。adap.dev.parent 不填，适配器目录会挂到 /sys/devices/ 根下，也丢了运行时 PM 的父子关系。

三、i2c_algorithm 必须实现什么 #

i2c_algorithm 就是「通过这根总线收发数据」的抽象。3.x 定义：

c
/* include/linux/i2c.h */
/**
 * struct i2c_algorithm - represent I2C transfer method
 * @master_xfer: Issue a set of i2c transactions to the given I2C adapter
 *   defined by the msgs array, with num messages available to transfer via
 *   the adapter specified by adap.
 * @smbus_xfer: Issue smbus transactions to the given I2C adapter. If this
 *   is not present, then the bus layer will try and convert the SMBus calls
 *   into I2C transfers instead.
 * @functionality: Return the flags that this algorithm/adapter pair supports
 *   from the I2C_FUNC_* flags.
 *
 * The following structs are for those who like to implement new bus drivers:
 * i2c_algorithm is the interface to a class of hardware solutions which can
 * be addressed using the same bus algorithms - i.e. bit-banging or the PCF85
 * to name two of the most common.
 *
 * The return codes from the @master_xfer field should indicate the type of
 * error code that occured during the transfer, as documented in the kernel
 * Documentation file Documentation/i2c/fault-codes.
 */
struct i2c_algorithm {
        /* If an adapter algorithm can't do I2C-level access, set master_xfer
           to NULL. If an adapter algorithm can do SMBus access, set
           smbus_xfer. If set to NULL, the SMBus protocol is simulated
           using common I2C messages */
        /* master_xfer should return the number of messages successfully
           processed, or a negative value on error */
        int (*master_xfer)(struct i2c_adapter *adap, struct i2c_msg *msgs,
                           int num);
        int (*smbus_xfer) (struct i2c_adapter *adap, u16 addr,
                           unsigned short flags, char read_write,
                           u8 command, int size, union i2c_smbus_data *data);

        /* To determine what the adapter supports */
        u32 (*functionality) (struct i2c_adapter *);
};
成员 必须？ 签名要点 语义
master_xfer 两者取一 (adap, struct i2c_msg *msgs, int num) 处理 num 条 i2c_msg，返回成功处理的条数，出错返回负值
smbus_xfer 两者取一（与上面） (adap, u16 addr, flags, read_write, u8 command, int size, union i2c_smbus_data *data) 直接做 SMBus 事务；为 NULL 时 core 用 master_xfer 模拟
functionality 必须 (adap) 返回 u32 位图 告诉上层这套 algo/adapter 支持哪些 I2C_FUNC_*

三个要点。

一，master_xfer 和 smbus_xfer 的取舍。注释写得很明确：算法做不了 I2C 级访问就把 master_xfer 设 NULL；能做 SMBus 就填 smbus_xfer；smbus_xfer 为 NULL 时 SMBus 协议由普通 I2C 报文模拟。绝大多数 SoC 控制器属于「我只会发标准 I2C」，所以填 master_xfer、不填 smbus_xfer。

二，返回值语义。master_xfer 返回的是成功处理的 msg 条数，不是字节数。core 的 i2c_transfer() 那层会拿它和 num 比，不等就返回 -EIO（具体映射逻辑见 drivers/i2c/i2c-core-base.c 的 __i2c_transfer，5.x）。所以中途第 2 条失败时，返回 1 而不是错误码，反而会让上层以为全成功——正确做法是失败即返回负值，别返回半截计数。

三，错误码要按 Documentation/i2c/fault-codes 来。常用几个：-ENXIO（地址无应答）、-EAGAIN（仲裁丢失，可重试）、-ETIMEDOUT（等不到控制器完成）、-EOPNOTSUPP（不支持这种传输）。

i2c_msg 是传输单位，你自己也得懂它：

c
/* include/uapi/linux/i2c.h */
struct i2c_msg {
        __u16 addr;     /* slave address                        */
        __u16 flags;
#define I2C_M_TEN               0x0010  /* this is a ten bit chip address */
#define I2C_M_RD                0x0001  /* read data, from slave to master */
#define I2C_M_STOP              0x8000  /* if I2C_FUNC_PROTOCOL_MANGLING */
#define I2C_M_NOSTART           0x4000  /* if I2C_FUNC_NOSTART */
#define I2C_M_REV_DIR_ADDR      0x2000  /* if I2C_FUNC_PROTOCOL_MANGLING */
#define I2C_M_IGNORE_NAK        0x1000  /* if I2C_FUNC_PROTOCOL_MANGLING */
#define I2C_M_NO_RD_ACK         0x0800  /* if I2C_FUNC_PROTOCOL_MANGLING */
#define I2C_M_RECV_LEN          0x0400  /* length will be first received byte */
        __u16 len;              /* msg length                           */
        __u8 *buf;              /* pointer to msg data                  */
};

flags 为 0 时走标准协议（Documentation/i2c/i2c-protocol）：

text
写：S Addr Wr [A] Data [A] Data [A] ... [A] Data [A] P
读：S Addr Rd [A] [Data] A [Data] A ... A [Data] NA P
读后写（组合）：S Addr Rd [A] [Data] NA S Addr Wr [A] Data [A] P

读操作里 master 收到 NACK 表示 slave 没数据了，该停。非 0 flags 就是非标行为，前提是你的 functionality 声明了支持：

  • I2C_M_IGNORE_NAK：把 NACK 当 ACK 接着读。读 EDID 时某些电视就这么恶心。
  • I2C_M_NO_RD_ACK：读的时候完全不管 ACK/NACK。少见。
  • I2C_M_NOSTART：多条 msg 连续传输时，后续 msg 不再发 S Addr Wr/Rd [A]，直接续上数据。组合传输拆成一条时序用。
  • I2C_M_REV_DIR_ADDR：读写方向位翻转，读发 Wr、写发 Rd。极少数器件需要。
  • I2C_M_STOP：这条 msg 完成后强制发 STOP。
  • I2C_M_RECV_LEN：SMBus 的长度字段在数据首字节。只在 I2C_FUNC_SMBUS_* 场景出现。

写控制器驱动时的现实做法：master_xfer 里对这些 flag 逐一 if 处理，不认识的直接 return -EOPNOTSUPP，别硬跑。同时 functionality 里别声明你没实现的那几位。

四、master_xfer 的完整实现 #

master_xfer 是整篇的核心。它拿到一串 msg，要做的事固定：加锁 → 逐条拆包 → 按读写分别发时序 → 等完成 → 解锁 → 返回条数。

先给一个不依赖具体寄存器的骨架，结构对了，往里填控制器操作就行。

c
static int foo_i2c_xfer(struct i2c_adapter *adap, struct i2c_msg *msgs, int num)
{
        struct foo_i2c *priv = i2c_get_adapdata(adap);
        int i, ret;

        if (!msgs || num <= 0)
                return -EINVAL;

        for (i = 0; i < num; i++) {
                struct i2c_msg *msg = &msgs[i];

                ret = foo_i2c_wait_idle(priv);      /* 等控制器空闲 */
                if (ret)
                        return ret;

                if (!(msg->flags & I2C_M_NOSTART))
                        foo_i2c_start(priv, msg);
                else if (i == 0)
                        return -EINVAL;             /* 首条不能 NOSTART */

                if (msg->flags & I2C_M_RD)
                        ret = foo_i2c_read(priv, msg);
                else
                        ret = foo_i2c_write(priv, msg);
                if (ret)
                        return ret;                 /* 失败即返回负值 */

                if (msg->flags & I2C_M_STOP || i == num - 1)
                        foo_i2c_stop(priv);
        }

        return num;                                 /* 成功处理的条数 */
}

拆开讲几处必须想明白的。

锁。 一根总线同一时刻只能有一个传输在跑。core 在 i2c_transfer() 里已经对 adap->bus_lock 加锁了，所以你的 master_xfer 里不用再加互斥锁。但如果驱动自己还有别的路径会碰寄存器（比如中断里在推进状态机、或者有个 sysfs 调试接口），那要自己的 mutex 或 completion 保护。老式 rt_mutex 的 bus_lock 语义是「内核态传输互斥、用户态可打断恢复」，我没在 3.x 之外逐版本核过，标未验证。

逐条处理而不是一次全发。 因为每条 msg 带的 flag 不同、方向不同，组合传输还要求两条之间不发 STOP——你不能在第一条后面无条件补 STOP。

等完成。 中断模式下是 wait_event_timeout(priv->wait, priv->done, adap->timeout)；轮询模式下是循环读状态位直到 bit 或超时。两种都必须在失败时把控制器状态复位，否则下一次传输直接卡死。超时后返回 -ETIMEDOUT。

读的最后字节前发 NACK。 这是最容易写错的地方。标准读时序要求 master 在收到最后一个字节之后回 NACK，让 slave 释放 SDA。多数控制器用「还剩几个字节」的寄存器位或「是否最后一字节」标志来处理，部分控制器要手动置位。照着手册写，别抄别人的 msg->len。

返回 num 而不是 0。 全成功就 return num。失败返回负值。

再看一个更贴近硬件的实现形态，i2c-s3c2410.c 的 xfer 走的是「填状态机 + 等完成」：

c
static int s3c24xx_i2c_xfer(struct i2c_adapter *adap,
                            struct i2c_msg *msgs, int num)
{
        struct s3c24xx_i2c *i2c = (struct s3c24xx_i2c *)adap->algo_data;
        int ret;

        ret = clk_enable(i2c->clk);
        if (ret)
                return ret;

        ret = s3c24xx_i2c_doxfer(i2c, msgs, num);
        clk_disable(i2c->clk);

        return ret;
}

s3c24xx_i2c_doxfer() 内部做的事：把 msgs/num 存进 i2c->msg/msg_num，msg_idx、msg_ptr 归零，state = STATE_START，写 IICSTAT 产生 START，然后 wait_event_timeout(i2c->wait, ..., HZ) 等中断处理函数推进到 IDLE。等不到就 s3c24xx_i2c_stop() 并返回错误。这就是典型的「中断驱动 + 等待队列」形态，其余控制器换个寄存器名字而已。

注意它把 clk_enable()/clk_disable() 放在 xfer 里，是因为 S3C 的 I2C 模块空闲时关时钟省电。你的控制器如果没这个需求，时钟在 probe 里开一次就行。

五、smbus_xfer 与它的可选项 #

上一章说了 master_xfer 和 smbus_xfer 二选一。这一章讲另一半：什么时候你该填它，填的时候怎么填。

SMBus 是 I2C 的子集加扩展，时序上比 I2C 严格得多，有 QUICK、BYTE、BYTE_DATA、WORD_DATA、BLOCK 几种事务类型。很多 SoC 的 I2C 控制器其实能直接产生 SMBus 时序（尤其是带 PEC 校验支持的），那就填 smbus_xfer，省掉 core 模拟的报文转换开销。反过来，如果你的控制器只会发标准 I2C，smbus_xfer 留 NULL 就对了：

c
static const struct i2c_algorithm s3c24xx_i2c_algorithm = {
        .master_xfer            = s3c24xx_i2c_xfer,
        .functionality          = s3c24xx_i2c_func,
};

这是 i2c-s3c2410.c 的真实写法。没有 smbus_xfer，SMBus 请求由 core 转成 I2C 报文，功能上没问题，只是慢一点。绝大多数移植场景到这就够了。

真要实现，签名要一字不差：参数是 (adap, u16 addr, unsigned short flags, char read_write, u8 command, int size, union i2c_smbus_data *data)，返回 s32。函数体按 size 分派：I2C_SMBUS_QUICK 只发地址无数据；I2C_SMBUS_BYTE 看 read_write 决定是收还是发 command；I2C_SMBUS_BYTE_DATA 是 command 加 1 字节 data->byte；I2C_SMBUS_WORD_DATA 是 2 字节；I2C_SMBUS_BLOCK_DATA 是长度加数据；不认识的一律返回 -EOPNOTSUPP。

几个坑说在前面。

I2C_SMBUS_WORD_DATA 是小端先发低字节，这是 SMBus 规范定的，不是主机的字节序。别直接 memcpy 一个字出去。I2C_SMBUS_BLOCK_DATA 的最大长度是 32（I2C_SMBUS_BLOCK_MAX），包里第一字节是长度，要单独处理，不能当成 data->block[0] 个数据字节直接发。

PEC。 SMBus 有可选的包错误校验，CRC-8，多项式 x^8 + x^2 + x + 1，core 里有现成的 i2c_smbus_data 校验辅助，但发不发取决于 flags & I2C_CLIENT_PEC 和你的 functionality 里有没有 I2C_FUNC_SMBUS_PEC。硬件能算就让硬件算，硬件不能算就在 driver 里算，然后声明支持。声明了 I2C_FUNC_SMBUS_PEC 却不真正校验，属于撒谎，会出事。

functionality 里 SMBus 的位要和你 switch 里支持的 size 一一对应，别多声明。第五章和第六章要交叉检查。

最后提醒一句版本：i2c_algorithm 结构体从 3.x 到 6.x 成员没变过，但 smbus_xfer 的返回类型在某个版本从 int 改成了 s32（精确版本未验证，5.x 已是 s32）。写新驱动用 s32，老的 int 也能编。

六、functionality：告诉 core 你支持什么 #

functionality 返回一个 u32 位图，描述「这套 algo/adapter 组合」能干什么。consumer 侧用 i2c_check_functionality(adap, I2C_FUNC_SMBUS_BYTE_DATA) 之类的调用先问一句再干活，所以这里必须诚实。

位定义来自 include/uapi/linux/i2c.h：

两点必须自己核对：I2C_FUNC_SLAVE 与 I2C_FUNC_SMBUS_WRITE_BYTE_DATA 的数值在这些头文件里是重名的（从机模式复用了一个 SMBus 位），以你实际内核的 include/uapi/linux/i2c.h 为准，我上面这张表是按常见版本整理的，个别值标未验证。写代码时不要手写数字，一律用宏。

一个最小可用的实现就一行：return I2C_FUNC_I2C | I2C_FUNC_SMBUS_EMUL;。

I2C_FUNC_SMBUS_EMUL 是个组合宏，意思是「SMBus 我用 I2C 报文模拟，这些事务都能做」，它覆盖了 byte/byte_data/word_data/block 的模拟能力。用 I2C_FUNC_SMBUS_EMUL 有个前提：你的 master_xfer 至少能处理单条写、单条读、读后写组合这三种形态，因为模拟全靠这三种拼出来。

i2c-s3c2410.c 的 functionality 稍复杂，因为它要看传入的 quirks：轮询模式（QUIRK_POLL）返回 I2C_FUNC_I2C | I2C_FUNC_SMBUS_EMUL，中断模式只返回 I2C_FUNC_I2C。逻辑是：中断模式下这个老控制器在某些边角时序上靠不住，只报纯 I2C；轮询模式反而是给 HDMIPHY 这类要读 EDID 的场合用的，报上 SMBus 模拟。这段是我按素材里 quirks 的用法重写的示意，具体返回值未在原始内核中逐行核对。

一个判断准则：你 master_xfer 里没实现的 flag，functionality 里就别报。 报了 I2C_FUNC_PROTOCOL_MANGLING 却不处理 I2C_M_IGNORE_NAK，上层传下来就是一堆莫名其妙的时序错误。

七、适配器的注册：i2c_add_adapter #

适配器填好了，注册到内核。相关 API 在 include/linux/i2c.h：i2c_add_adapter()、i2c_del_adapter()、i2c_add_numbered_adapter() 三个实函数，加上 i2c_get_functionality()、i2c_check_functionality()、i2c_adapter_id() 三个内联；消费侧另有 i2c_get_adapter()/i2c_put_adapter() 和 of_find_i2c_adapter_by_node()（后者注释写明「用完必须 put_device()」）。

API 作用 注意
i2c_add_adapter() 注册，总线号自动分配 走 aliases 或 idr
i2c_add_numbered_adapter() 注册，用 adap->nr 指定号 nr 无效时退回自动分配
i2c_del_adapter() 注销 会解绑并销毁子 client
i2c_get_functionality() 取功能位图 转调 algo->functionality
i2c_check_functionality() 查某位 返回 bool
i2c_adapter_id() 取 adap->nr 内联
i2c_get_adapter(nr) 按号拿适配器 会 try_module_get，必须配对 i2c_put_adapter()
of_find_i2c_adapter_by_node() 按 DT 节点拿适配器 用完要 put_device()

i2c_add_adapter() 内部流程，3.x 的源码：

c
/* drivers/i2c/i2c-core.c */
int i2c_add_adapter(struct i2c_adapter *adapter)
{
        struct device *dev = &adapter->dev;
        int id;

        if (dev->of_node) {
                id = of_alias_get_id(dev->of_node, "i2c");
                if (id >= 0) {
                        adapter->nr = id;
                        return __i2c_add_numbered_adapter(adapter);
                }
        }

        mutex_lock(&core_lock);
        id = idr_alloc(&i2c_adapter_idr, adapter,
                       __i2c_first_dynamic_bus_num, 0, GFP_KERNEL);
        mutex_unlock(&core_lock);
        if (id < 0)
                return id;

        adapter->nr = id;

        return i2c_register_adapter(adapter);
}

三步走。有 of_node 就先试 aliases：DT 里写了 aliases { i2c0 = &i2c0; }; 就拿到固定号，走 __i2c_add_numbered_adapter()，这一步解释了为什么很多板子上 i2c 编号是跳的。没有 aliases 就 idr_alloc() 从 __i2c_first_dynamic_bus_num 往后找个空号，core_lock 保护这个 idr，别自己碰。拿到号后进 i2c_register_adapter()。

i2c_add_numbered_adapter() 的链路是 i2c_add_numbered_adapter ---> __i2c_add_numbered_adapter ---> i2c_register_adapter。它要求 adap->nr >= 0 且号段没被占，否则失败；nr 为负会转回 i2c_add_adapter()。

i2c_register_adapter() 里做三件事，对应你关心的三个副作用：

其一，建设备模型。 设 dev_set_name(&adap->dev, "i2c-%d", adap->nr)，把 adap->dev.bus 指向 i2c_bus_type、adap->dev.type 指向 i2c_adapter_type，然后 device_register(&adap->dev)。这一路走 device_add() ---> bus_add_device() ---> sysfs_create_link()，于是 /sys/bus/i2c/devices/ 下出现 i2c-n 符号链接，指向适配器真正的设备目录。父设备（adap->dev.parent = &pdev->dev; 指向 platform device）决定目录落在哪，目录在 /sys/devices/xxxxxxxx.i2c/i2c-n，i2c-n 只是链接别名，不设 parent 就挂到根下。

其二，完成设备模型之后就轮到子设备。 DT 场景下的调用链是 i2c_register_adapter ---> of_i2c_register_devices ---> i2c_new_device。适配器一注册，它 of_node 下所有子节点都会被建成 struct i2c_client 并挂到 i2c_bus_type。这就是「控制器驱动写对了，设备驱动什么都不用注册」的原因。

i2c_add_adapter() 在 3.x 之后有几处调整：4.x 后期 I2C core 被拆成 i2c-core-base.c / i2c-core-smbus.c / i2c-core-of.c，i2c_add_adapter() 挪到了 i2c-core-base.c，代码骨架基本一致（精确的拆分版本是 4.10 前后，未逐字核对）。5.16 起增加了 i2c_add_adapter() 里对 adap->dev.of_node 缺失时更严格的检查，具体行为以源码为准。注册失败时不用你释放任何东西，清理路径只管撤自己申请的资源，别在失败路径里调 i2c_del_adapter()。

八、设备树里的 I2C 控制器节点 #

控制器节点写对了，驱动才能 probe 到，编号和中断线才对。SoC 级 dtsi 里这么写（arch/arm/boot/dts/am33xx.dtsi）：

dts
i2c0: i2c@44e0b000 {
        compatible = "ti,omap4-i2c";
        #address-cells = <1>;
        #size-cells = <0>;
        ti,hwmods = "i2c1";
        reg = <0x44e0b000 0x1000>;
        interrupts = <70>;
        status = "disabled";
};

字段逐个说：

  • compatible：必须和驱动 of_match_table 里的字符串完全一致，一个字符都不能差。
  • reg：寄存器基址和长度。devm_ioremap_resource() 取的就是它。
  • interrupts：中断号。用 platform_get_irq(pdev, 0) 取。
  • #address-cells = <1> 和 #size-cells = <0>：这两个是必须的。子节点是 I2C 从设备，地址只有 1 个 cell，没有地址空间长度，所以 size-cells 必须是 0。写错了子节点的 reg 解析不出来，i2c_new_device 会失败，表现为「适配器注册了但下面一个设备都没有」。
  • status = "disabled"：SoC 级的 dtsi 里默认关，板级 dts 里打开。
  • ti,hwmods：TI 平台特有的，别的 SoC 没有，别照抄。

板级 dts 里打开并加从设备：

dts
&i2c0 {
        status = "okay";
        clock-frequency = <100000>;

        eeprom@50 {
                compatible = "atmel,24c08";
                reg = <0x50>;
        };
};

clock-frequency 是给控制器驱动读的标准属性，单位 Hz，不写时驱动取自己的默认值（多为 100000）。

别名控制编号：在根节点写 aliases { i2c0 = &i2c0; };。有了这行，of_alias_get_id(dev->of_node, "i2c") 返回 0，总线号固定成 0，板子上电后 /dev/i2c-0 永远是那根线，不会因为 probe 顺序变化。产品里强烈建议写，调试脚本和用户态工具都依赖这个稳定性。

同一个 SoC 上的多个控制器，#address-cells/#size-cells 每个节点都要写，不能靠继承——这是 DT 规范的要求，虽然有些解析器容忍。

九、probe 里的资源获取顺序 #

顺序错了就是随机 panic。这一章给一张表，照着排。

序号 动作 API 失败后果 / 注意
1 分配私有结构 devm_kzalloc() 下面所有步骤的基础
2 填 adap 静态字段 直接赋值 只填字符串和指针，不碰硬件
3 拿平台数据或解析 DT dev_get_platdata() / 私有 parse 函数 决定 bus_num、frequency
4 拿时钟 devm_clk_get() 拿不到先别开
5 映射寄存器 devm_ioremap_resource() 依赖第 1 步的资源，reg 缺失直接 -EBUSY/-ENOMEM
6 拿 pinctrl / 配引脚 devm_pinctrl_get_select_default() 引脚没复用时访问总线就是死
7 开时钟 clk_prepare_enable() 不开时钟访问寄存器会挂总线
8 初始化控制器寄存器 私有 xxx_init() 必须在时钟开后
9 申请中断 devm_request_irq() 轮询模式跳过
10 设置 nr / of_node 直接赋值 顺序在第 11 步之前
11 注册适配器 i2c_add_numbered_adapter() / devm_i2c_add_adapter() 放最后
12 运行时 PM 使能 pm_runtime_enable() 视平台需要

把 4.x 的 s3c24xx_i2c_probe() 按骨架重排（返回值判断和回滚代码省略），对号入座：

c
static int s3c24xx_i2c_probe(struct platform_device *pdev)
{
        if (!pdev->dev.of_node)                                 /* 3 平台数据 */
                pdata = dev_get_platdata(&pdev->dev);

        i2c = devm_kzalloc(&pdev->dev, sizeof(*i2c), GFP_KERNEL);   /* 1 */
        i2c->pdata = devm_kzalloc(&pdev->dev, sizeof(*pdata), GFP_KERNEL);
        ...
        if (pdata)
                memcpy(i2c->pdata, pdata, sizeof(*pdata));
        else
                s3c24xx_i2c_parse_dt(pdev->dev.of_node, i2c);

        strlcpy(i2c->adap.name, "s3c2410-i2c", sizeof(i2c->adap.name));  /* 2 */
        i2c->adap.owner   = THIS_MODULE;
        i2c->adap.algo    = &s3c24xx_i2c_algorithm;
        i2c->adap.retries = 2;
        i2c->adap.class   = I2C_CLASS_DEPRECATED;
        init_waitqueue_head(&i2c->wait);

        i2c->clk = devm_clk_get(&pdev->dev, "i2c");              /* 4 时钟 */

        res = platform_get_resource(pdev, IORESOURCE_MEM, 0);    /* 5 寄存器 */
        i2c->regs = devm_ioremap_resource(&pdev->dev, res);

        i2c->adap.algo_data   = i2c;                             /* 2 补字段 */
        i2c->adap.dev.parent  = &pdev->dev;
        i2c->pctrl = devm_pinctrl_get_select_default(i2c->dev);  /* 6 引脚 */

        if (i2c->pdata->cfg_gpio)
                i2c->pdata->cfg_gpio(to_platform_device(i2c->dev));
        else if (IS_ERR(i2c->pctrl) && s3c24xx_i2c_parse_dt_gpio(i2c))
                return -EINVAL;

        clk_prepare_enable(i2c->clk);                            /* 7 开时钟 */
        ret = s3c24xx_i2c_init(i2c);                             /* 8 初始化 */
        clk_disable(i2c->clk);

        if (!(i2c->quirks & QUIRK_POLL)) {                       /* 9 中断 */
                i2c->irq = platform_get_irq(pdev, 0);
                devm_request_irq(&pdev->dev, i2c->irq, s3c24xx_i2c_irq,
                                 0, dev_name(&pdev->dev), i2c);
        }

        s3c24xx_i2c_register_cpufreq(i2c);                       /* 见第十章 */

        i2c->adap.nr = i2c->pdata->bus_num;                      /* 10 编号 */
        i2c->adap.dev.of_node = pdev->dev.of_node;
        platform_set_drvdata(pdev, i2c);

        pm_runtime_enable(&pdev->dev);                           /* 12 */
        return i2c_add_numbered_adapter(&i2c->adap);             /* 11 注册 */
}

读这段要抓的几件事。骨架就是「填结构体 → 拿时钟 → 映射寄存器 → 配引脚 → 开时钟初始化 → 拿中断 → 注册」，原版每一步失败都在原地回滚已经做过的部分，这就是为什么它到处 clk_unprepare()。

i2c->pdata->cfg_gpio 和 pinctrl 是两条互斥的引脚配置路径。老平台走 platform data 里的回调（s3c_i2c0_cfg_gpio，定义在 arch/arm/mach-s3c24xx/setup-i2c.c，作用是把 GPE15 设成 SDA、GPE14 设成 SCL），DT 平台走 pinctrl。两种都支持的时候，顺序是先试 pinctrl，失败了再退回回调。

clk_prepare_enable() 之后紧跟 clk_disable() 不是写错，是「临时开一下把寄存器初始化完，然后关掉省电」，真正的开关在每次 xfer 里。这种写法要求你的 xxx_init() 不依赖中断，只写寄存器。

platform_get_irq() 返回值判断用 <= 0，因为老内核里 0 也不算合法中断号。现代内核返回负值错误码，写 if (ret < 0) 更清楚。

i2c->adap.nr = i2c->pdata->bus_num; 配上 i2c_add_numbered_adapter()，等价于「我指定编号」。如果 bus_num 是 0 且被占了，注册会失败，这时要么改数，要么换 i2c_add_adapter() 自动分配。

platform_set_drvdata(pdev, i2c) 要在注册前做完，因为一旦注册成功，下面子设备的 probe 会立刻跑起来，它们反过来找父控制器（dev_get_drvdata(adap->dev.parent)）时得能拿到东西。

十、时钟与复位 #

时钟和复位是移植时最容易「看起来对但其实不对」的两块。

时钟。 devm_clk_get(&pdev->dev, "i2c") 里那个字符串对应 DT 的 clock-names，必须一字不差：clocks = <&i2c_clkctrl 0>; 配 clock-names = "i2c";。写 NULL 表示取第一个时钟，只在控制器只有一个时钟源时可靠。多时钟控制器（总线时钟 + 功能时钟）必须按名字取，一个个来。

clk_prepare_enable() 在原子上下文里不能调 prepare 部分，clk_enable()/clk_disable() 是可以的。所以中断里别随便 clk_prepare_enable()。S3C 的驱动在 xfer 里只用 clk_enable()/clk_disable()、在 probe 里 clk_prepare_enable() 配一次，就是这个道理。

clk_prepare_enable() 的返回值要检查。开了没成功就访问寄存器，结果是总线挂死，而且挂死是「整个 SoC 的 I2C 都没了」，不只是一个驱动。

时钟频率漂移会让波特率不对。SoC 有 CPUFreq 调节主频时，I2C 模块时钟如果挂在会变的源上，分频系数就得跟着改。i2c-s3c2410.c 为此注册了一个 notifier_block freq_transition（CONFIG_ARM_S3C24XX_CPUFREQ 打开时），主频变化时重算分频。你的 SoC 如果有这个特性，别漏。

复位。 4.x 之后用 devm_reset_control_get_exclusive() 拿复位控制，reset_control_assert() / reset_control_deassert() 成对，位置在「时钟开之后、寄存器初始化之前」。-EPROBE_DEFER 一定要透传，别吞：复位控制器有时比你的 I2C 驱动后加载，这时该 defer 就 defer。没有复位线（驱动返回 -ENOENT）就把句柄置 NULL 跳过。老平台没有 reset framework，靠 arch/.../clock.c 里的门控位手工开关，或者干脆不复位，移植到新内核时这块要重写。

传输超时后的软复位也一样重要。控制器卡在「等 ACK」状态时，s3c24xx_i2c_stop() 要写 IICSTAT 的 STOP 位并清中断 pend，否则下一次 xfer 直接超时。有些控制器还得在超时后整块复位。这块建议在 xxx_stop() 里做干净，别留到下一步。

十一、中断与传输完成判定 #

传输怎么算「完成」，有两种模型，选哪一种由你的控制器决定。

模型一：中断 + 等待队列。 S3C 是这个模型的典型：

c
/* top level IRQ servicing routine */
static irqreturn_t s3c24xx_i2c_irq(int irqno, void *dev_id)
{
        struct s3c24xx_i2c *i2c = dev_id;
        unsigned long status;
        unsigned long tmp;

        status = readl(i2c->regs + S3C2410_IICSTAT);

        if (status & S3C2410_IICSTAT_ARBITR)
                dev_err(i2c->dev, "deal with arbitration loss\n");   /* 仲裁丢失 */

        if (i2c->state == STATE_IDLE) {
                dev_dbg(i2c->dev, "IRQ: error i2c->state == IDLE\n");

                tmp = readl(i2c->regs + S3C2410_IICCON);
                tmp &= ~S3C2410_IICCON_IRQPEND;
                writel(tmp, i2c->regs + S3C2410_IICCON);   /* 清中断 pend */
                goto out;
        }

        i2c_s3c_irq_nextbyte(i2c, status);   /* 上一字节已收发完，推进状态机 */

out:
        return IRQ_HANDLED;
}

要点：

  • 中断处理只做「读状态 → 清 pend → 推进一个字节」。别在中断里做长循环，也别在这里 clk_prepare_enable()。
  • 清 pend 的顺序：先读状态、再清标志、再判断。写反了会丢中断。
  • 仲裁丢失（IICSTAT_ARBITR）要单独处理。多主总线上这是正常事件，返回值应该让上层知道可以重试（-EAGAIN）。只打 log 不处理是耍赖。
  • i2c->state 是驱动自己的状态机：STATE_IDLE、STATE_START、STATE_WRITE、STATE_READ、STATE_STOP。中断里根据当前 state 决定下一步是发地址、发数据字节还是发 STOP。
  • 完成判定：i2c_s3c_irq_nextbyte() 在数据发完、STOP 发出之后把 state 置 STATE_IDLE，然后 wake_up(&i2c->wait)。xfer 那边 wait_event_timeout() 醒来检查 state。

模型二：轮询。 控制器有 QUIRK_POLL 或者根本没有中断线时用。本质是个带超时的忙等循环：读状态位，命中完成位返回 0，命中错误位返回 -EIO，time_before(jiffies, end) 耗尽返回 -ETIMEDOUT。中间用 cpu_relax() 松弛 CPU。微秒级等待用 udelay()，毫秒级用 usleep_range() 或 wait_event_timeout()。

中断模式下 devm_request_irq() 的标志位：共享中断用 IRQF_SHARED，绝大多数 SoC 的 I2C 中断是独占的，传 0。名字用 dev_name(&pdev->dev)，dev_id 传你的控制器指针，中断处理函数里靠它取状态。IRQF_NO_SUSPEND 只在确实需要在系统挂起期间收中断时才加，加错了会破坏电源管理。

devm_request_irq() 申请到的中断由 devm 自动释放，但 remove 里如果早就把设备注销了、中断却还在跑，就会踩到已释放内存。正确顺序在第十四章。

十二、速率配置与总线频率 #

总线频率不是写死一个常数就完事，得从模块时钟反算分频，再验证实际频率没超过目标值。

S3C 的做法值得抄：

c
static int s3c24xx_i2c_init(struct s3c24xx_i2c *i2c)
{
        struct s3c2410_platform_i2c *pdata;
        unsigned int freq;

        pdata = i2c->pdata;

        writeb(pdata->slave_addr, i2c->regs + S3C2410_IICADD);   /* 从设备地址 */

        dev_info(i2c->dev, "slave address 0x%02x\n", pdata->slave_addr);

        writel(0, i2c->regs + S3C2410_IICCON);                  /* IICCON = 0 */
        writel(0, i2c->regs + S3C2410_IICSTAT);                 /* IICSTAT = 0 */

        if (s3c24xx_i2c_clockrate(i2c, &freq) != 0) {           /* 算分频 */
                dev_err(i2c->dev, "cannot meet bus frequency required\n");
                return -EINVAL;
        }

        dev_info(i2c->dev, "bus frequency set to %d KHz\n", freq);
        dev_dbg(i2c->dev, "S3C2410_IICCON=0x%02x\n",
                readl(i2c->regs + S3C2410_IICCON));

        return 0;
}

writeb(pdata->slave_addr, ...S3C2410_IICADD) 这个容易看懵：我们写的是控制器驱动，为什么配置了从设备地址。原因是这颗控制器自己也能当从机（slave 模式），IICADD 是它作为从机时的应答地址。S3C 的 s3c2410_platform_i2c 里 slave_addr 默认 0x10。主机模式下这个值不起作用，但寄存器得初始化。

writel(0, ...IICCON) 和 writel(0, ...IICSTAT) 在算分频之前，是为了清掉上一次运行的残留状态。IICSTAT 里的模式位一旦处于非 IDLE，后面写的分频不生效。

关键是 s3c24xx_i2c_clockrate() 的逻辑，伪码讲清：目标是 pdata->frequency（Hz，未设取默认 100000），输入是 clk_get_rate(i2c->clk)；按控制器手册的公式反推分频系数，写进 IICCON 低位字段；再按「实际频率 = 输入时钟 / 分频」复核，超过目标值就返回 -EINVAL（不允许超），否则把实际值回填给调用者打印。QUIRK_S3C2440 分支的除法方式与 S3C2410 不同。要精确到寄存器位就看 drivers/i2c/busses/i2c-s3c2410.c 本体，这里给的是逻辑骨架（逐位实现未验证）。

自己写驱动时，这一段要照手册的公式来，并做两件事：

一，向上取整还是向下取整。 总线频率不能超过目标值。NXP 的 I2C 规范里 100 kHz 是上限，400 kHz 是 Fast-mode 上限。取整要多除一点，宁慢不超。S3C 的实现是超了就报错，这是保守做法，也最安全。

二，算出实际值后打印出来。 dev_info(i2c->dev, "bus frequency set to %d KHz\n", freq); 这一行看着啰嗦，调试时救命。i2cdetect 扫不到设备的第一件事就是看这个值对不对。

驱动里用 device_property_read_u32(dev, "clock-frequency", &freq) 读，失败就取 100000。这个接口是 4.4 之后统一的属性读取方式，比直接用 of_property_read_u32() 更通用（也支持 ACPI）。老代码里是 of_property_read_u32(np, "clock-frequency", &freq)。

还有一条：i2c_adapter 自己没有「频率」字段。频率是私有结构体的事，i2c_algorithm 也管不着。上层想知道频率只能看你打印的 log 或者读控制器。有的 SoC 提供 bus_clk_rate 之类的 sysfs 属性，那是驱动自己加的非标准接口。

十三、i2c_parse_fw_timings：从设备树读时序 #

严格的 I2C 时序不只是频率，还涉及 SCL 高低电平时间、SDA 建立保持时间、START/STOP 建立时间这些。这些参数在 DT 里有标准属性名，core 提供了一个统一解析函数。

i2c_parse_fw_timings()，4.15+ 引入（精确引入版本记作 4.15，未在更早版本核对）。原型：

c
void i2c_parse_fw_timings(struct device *dev, struct i2c_timings *t, bool use_defaults);

struct i2c_timings 的字段与对应 DT 属性：

字段 单位 DT 属性 说明
bus_freq_hz Hz clock-frequency 总线频率，必读项
scl_rise_ns ns i2c-scl-rising-time-ns SCL 上升时间
scl_fall_ns ns i2c-scl-falling-time-ns SCL 下降时间
scl_int_delay_ns ns i2c-scl-internal-delay-ns SCL 内部附加延时
sda_fall_ns ns i2c-sda-falling-time-ns SDA 下降时间
sda_hold_ns ns i2c-sda-hold-time-ns SDA 保持时间
digital_filter_width_ns ns i2c-digital-filter-width-ns 数字滤波宽度
analog_filter_width_ns ns i2c-analog-filter-width-ns 模拟滤波宽度

第三个参数 use_defaults 决定缺属性时给不给默认值：

  • use_defaults = true：缺的项用一套保守默认值填（升/降时间按 100 kHz 和 400 kHz 各有一组），适合不严格要求时序的控制器。
  • use_defaults = false：缺的项填 0，调用者自己判断。适合必须精确时序的控制器，缺参数就该报错。

用法：

c
struct i2c_timings timings;

i2c_parse_fw_timings(dev, &timings, true);
dev_dbg(dev, "bus freq %u Hz, scl rise %u ns\n",
        timings.bus_freq_hz, timings.scl_rise_ns);

怎么用这些值算寄存器，取决于控制器。一类是直接把高低电平时间写进寄存器：新 SoC 的 I2C 控制器寄存器就是「SCL 高电平计数」和「SCL 低电平计数」，输入 ns 除以时钟周期就是计数值。二类是只有分频系数、时序靠频率保证，老控制器属于这类，此时升/降时间只用来校验频率能否达成：周期减去 scl_rise_ns、scl_fall_ns 再减余量，可用低电平时间小于等于 0 就说明这个频率在这块板上做不到。这就是为什么很多驱动里能看到「算出分频后拿 scl_rise_ns 再核一遍」的代码。三类是滤波配置：digital_filter_width_ns 对应数字毛刺滤波器，宽度小于它的脉冲被吃掉；analog_filter_width_ns 对应模拟滤波器。板上干扰大、长线走线、或者有热插拔连接器的时候，这两个参数决定通信稳不稳。

拿不到 i2c_parse_fw_timings() 的老内核（4.15 之前），只能自己 of_property_read_u32() 一个个读，属性名一样，函数不一样。新驱动尽量用它：省掉重复代码，DT 属性名也跟同目录各驱动保持一致。注意它在 linux/i2c.h 里，不在 i2c-core.h。

十四、适配器的注销与资源释放 #

注销顺序和注册顺序严格相反。这是「设备还在用、资源已经没了」唯一可靠的避免方式。

c
static int s3c24xx_i2c_remove(struct platform_device *pdev)
{
        struct s3c24xx_i2c *i2c = platform_get_drvdata(pdev);

        pm_runtime_disable(&pdev->dev);
        i2c_del_adapter(&i2c->adap);            /* 先注销适配器 */
        s3c24xx_i2c_deregister_cpufreq(i2c);
        clk_unprepare(i2c->clk);                /* 再关时钟 */

        return 0;
}

顺序的道理：i2c_del_adapter() 会先解绑所有子 i2c_client，也就是把挂在这根总线上的设备驱动 remove() 掉，让它们停止发 I2C 传输。之后你才能安全地关时钟、放引脚。反过来的话，设备驱动还在 xfer，时钟被你关了，就是总线挂死。

i2c_del_adapter() 内部做：

  1. 把适配器从 i2c_adapter_idr 里删掉。
  2. 注销所有子设备（of_i2c_unregister_devices() 或逐个 i2c_unregister_device()）。
  3. device_unregister(&adap->dev)，等 dev_released completion。
  4. 清 algo、algo_data。

注意第 3 步：i2c_del_adapter() 会等设备引用计数归零。如果此时还有个用户态进程 open("/dev/i2c-0") 没关，它会一直等。调试时遇到 rmmod 卡住，多半是这个。

devm 托管能省掉什么。 用 devm_i2c_add_adapter()（5.13+）时，remove 里那行 i2c_del_adapter() 不用写，devm 框架在设备 detach 时按逆序自动调。但顺序问题它管不了：devm 的释放顺序是「后注册的先释放」，devm_i2c_add_adapter() 在 probe 末尾调用，所以它会比前面的 devm_clk_get()、devm_ioremap_resource() 先释放。这个顺序恰好是对的——适配器先撤，资源后撤。

用 devm_* 注册中断、时钟、ioremap 时，remove 里对应的清理都不用写。但 pm_runtime_disable()、你自己注册的 notifier、手动 pinctrl_put() 这些不属于 devm 的，还得手工做。

一个真实的坑。 有些驱动在 remove 里先 i2c_del_adapter() 再 clk_disable_unprepare()，但忘了解除注册的中断。中断处理函数此时仍在跑，读一个还没关时钟的寄存器，如果这块内存已经 devm 释放了就是 use-after-free。devm_request_irq() 会在这个设备的所有 devm 资源释放过程中按序撤销，顺序上在你 remove 返回之后，所以只要别在 remove 里手动 free 内存就没事。

十五、移植实录：从零到能通信 #

这一章把前面的东西串成一条线，讲清「拿到一块新板子，I2C 控制器驱动从零到能读到设备」的完整路径。以 S3C2440 为主线，因为它的每一步都能看到寄存器。

第 0 步：确认硬件。 S3C2440 内部只有一个 I2C 控制器，SCL 接 GPE14，SDA 接 GPE15，寄存器基址 0x54000000，长度 4 KB，中断号 IRQ_IIC（27）。

第 1 步：platform 设备。 老内核没有 DT，设备是代码里写死的。arch/arm/plat-samsung/devs.c：

c
/* arch/arm/plat-samsung/devs.c */
static struct resource s3c_i2c0_resource[] = {
        [0] = DEFINE_RES_MEM(S3C_PA_IIC, SZ_4K),
        [1] = DEFINE_RES_IRQ(IRQ_IIC),
};

struct platform_device s3c_device_i2c0 = {
        .name           = "s3c2410-i2c",
        .id             = 0,
        .num_resources  = ARRAY_SIZE(s3c_i2c0_resource),
        .resource       = s3c_i2c0_resource,
};

struct s3c2410_platform_i2c default_i2c_data __initdata = {
        .flags          = 0,
        .slave_addr     = 0x10,
        .frequency      = 100*1000,      /* 100 KB */
        .sda_delay      = 100,
};

void __init s3c_i2c0_set_platdata(struct s3c2410_platform_i2c *pd)
{
        struct s3c2410_platform_i2c *npd;

        if (!pd) {
                pd = &default_i2c_data;
                pd->bus_num = 0;
        }

        npd = s3c_set_platdata(pd, sizeof(*npd), &s3c_device_i2c0);

        if (!npd->cfg_gpio)
                npd->cfg_gpio = s3c_i2c0_cfg_gpio;
}

两个资源：IO 内存（基址即 I2C 寄存器基地址 0x54000000，4 KB）、中断（IRQ_IIC）。s3c_set_platdata() 把 default_i2c_data 挂到 s3c_device_i2c0.dev.platform_data 上，同时补一个 cfg_gpio 回调。

第 2 步：设备什么时候注册。 内核启动时按 U-Boot 传的机器 id 走对应 MACHINE_START（arch/arm/mach-s3c24xx/mach-smdk2440.c），里面的 .init_machine = smdk2440_machine_init。这个函数里 s3c_i2c0_set_platdata(NULL) 先把 platform_data 挂好，再 platform_add_devices(smdk2440_devices, ...) 批量注册设备；后者内部就是循环 platform_device_register()。smdk2440_devices[] 里 &s3c_device_i2c0 跟 ohci、lcd、wdt 一起走这条路。

第 3 步：驱动侧。 drivers/i2c/busses/i2c-s3c2410.c：

c
static const struct platform_device_id s3c24xx_driver_ids[] = {
        { .name = "s3c2410-i2c", .driver_data = 0 },
        { .name = "s3c2440-i2c", .driver_data = QUIRK_S3C2440 },
        { .name = "s3c2440-hdmiphy-i2c",
          .driver_data = QUIRK_S3C2440 | QUIRK_HDMIPHY | QUIRK_NO_GPIO },
        { },
};

static const struct of_device_id s3c24xx_i2c_match[] = {
        { .compatible = "samsung,s3c2410-i2c", .data = (void *)0 },
        { .compatible = "samsung,s3c2440-i2c", .data = (void *)QUIRK_S3C2440 },
        { .compatible = "samsung,s3c2440-hdmiphy-i2c",
          .data = (void *)(QUIRK_S3C2440 | QUIRK_HDMIPHY | QUIRK_NO_GPIO) },
        { .compatible = "samsung,exynos5-sata-phy-i2c",
          .data = (void *)(QUIRK_S3C2440 | QUIRK_POLL | QUIRK_NO_GPIO) },
        {},
};

static struct platform_driver s3c24xx_i2c_driver = {
        .probe          = s3c24xx_i2c_probe,
        .remove         = s3c24xx_i2c_remove,
        .id_table       = s3c24xx_driver_ids,
        .driver         = {
                .name   = "s3c-i2c",
                .pm     = S3C24XX_DEV_PM_OPS,
                .of_match_table = of_match_ptr(s3c24xx_i2c_match),
        },
};

static int __init i2c_adap_s3c_init(void)
{
        return platform_driver_register(&s3c24xx_i2c_driver);
}
subsys_initcall(i2c_adap_s3c_init);

static void __exit i2c_adap_s3c_exit(void)
{
        platform_driver_unregister(&s3c24xx_i2c_driver);
}
module_exit(i2c_adap_s3c_exit);

id_table 走非 DT 匹配（name 对 platform_device.name），of_match_table 走 DT 匹配。两个都留着，是为了同一份代码同时支持老板子的板级文件和新的 DT 板子。

subsys_initcall 而不是 module_init：I2C 总线驱动要比下面挂的设备驱动先就位。用 module_init 会出现「设备驱动先 probe、找不到适配器、-EPROBE_DEFER、再来一轮」的情况，能用但慢。

QUIRK_* 这个东西值得学：同一份代码服务多个 SoC 变体，差异用 driver_data 打标志位埋进 i2c->quirks，后面所有分支都查这个标志。比复制一份驱动好得多。

.pm = S3C24XX_DEV_PM_OPS 是电源管理回调集合（suspend/resume/运行时 PM），控制器挂起时要保存恢复寄存器，这块不能省。

第 4 步：probe 跑起来。 见第九章的骨架。跑通之后 dmesg 里应该出现三行：

text
s3c-i2c s3c2410-i2c: slave address 0x10
s3c-i2c s3c2410-i2c: bus frequency set to 97 KHz
s3c-i2c s3c2410-i2c: i2c-0: S3C I2C adapter

分别对应：从机地址写进去了、分频算出来 97 kHz（没超 100 kHz，正常）、适配器注册成功且总线号是 0。

第 5 步：验证通信。 用 i2c-tools 走一遍 i2cdetect -l（列适配器）、i2cdetect -y 0（扫总线 0）、i2cget -y 0 0x50 0x00（读 EEPROM 首字节）。i2cdetect -y 0 能把地址打出来，说明 master_xfer 的「发地址 + 等 ACK」这条最短路径是通的。这一步过了，剩下的都是数据搬移。

移植到 DT 平台要改的。 第 1、2 步整体删掉，换成第八章的 dts 节点；dev_get_platdata() 改成 of_property_read_* 或 i2c_parse_fw_timings()；cfg_gpio 回调改成 pinctrl；platform_get_resource + devm_ioremap_resource 保留（DT 的 reg 会被 platform 层转成 IORESOURCE_MEM）。i2c_add_numbered_adapter() 可以留着，因为 of_alias_get_id 会给你编号。

第一次 xfer 成功，之后全失败 STOP 没发或状态没复位 查 xxx_stop() 和超时清理
挂起唤醒后 I2C 挂了 寄存器没保存恢复 查 .pm 回调
rmmod 卡住 有用户态进程占着 /dev/i2c-0 lsof /dev/i2c-0
CPUFreq 变频后通信失败 分频没跟着主频重算 查有没有注册 freq notifier
只在某些板子上失败 从设备地址冲突或地址不匹配 对板子原理图的地址跳线

调试顺序建议固定：i2cdetect -l → dmesg → i2cdetect -y N → 量波形。别一上来看波形，先确认软件这条链是通的。
