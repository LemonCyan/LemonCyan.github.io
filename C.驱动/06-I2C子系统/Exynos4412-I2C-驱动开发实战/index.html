一、Exynos4412 的 I2C 控制器家底 #

Exynos4412 内部有多个 I2C 通道。这条板子上，MPU6050 挂的是通道 5，控制器寄存器基址 0x138B0000。

控制器叫什么名字，看内核里的字符串更直接。drivers/i2c/busses/i2c-s3c2410.c 里注册的 platform 驱动 id 与设备树兼容串：

c
static const struct platform_device_id s3c24xx_driver_ids[] = {
        {
                .name           = "s3c2410-i2c",
                .driver_data    = 0,
        }, {
                .name           = "s3c2440-i2c",
                .driver_data    = QUIRK_S3C2440,
        }, {
                .name           = "s3c2440-hdmiphy-i2c",
                .driver_data    = QUIRK_S3C2440 | QUIRK_HDMIPHY | QUIRK_NO_GPIO,
        }, { },
};

static const struct of_device_id s3c24xx_i2c_match[] = {
        { .compatible = "samsung,s3c2410-i2c", .data = (void *)0 },
        { .compatible = "samsung,s3c2440-i2c", .data = (void *)QUIRK_S3C2440 },
        { .compatible = "samsung,s3c2440-hdmiphy-i2c",
          .data = (void *)(QUIRK_S3C2440 | QUIRK_HDMIPHY | QUIRK_NO_GPIO) },
        { .compatible = "samsung,exynos5-sata-phy-i2c",
          .data = (void *)(QUIRK_S3C2440 | QUIRK_POLL | QUIRK_NO_GPIO) },
        {},
};

看懂两件事就够了。

第一，Exynos4412 的 I2C 用的是 S3C2440 那一套控制器，所以设备树里兼容串写 samsung,s3c2440-i2c，对应 QUIRK_S3C2440 这一档。素材里出现过 compatible = "samsung,s3c2440-i2c" 配 reg = <0x13870000 0x100> 的片段，那是另一路通道的写法，寄存器窗口给的是 0x100；MPU6050 这一路是 0x138B0000。两处地址不冲突，是不同的 I2C 实例。

第二，QUIRK_POLL 的出现说明这个驱动支持轮询模式。轮询模式下面会反复出现在 master_xfer 的代码里——凡是 if (i2c->quirks & QUIRK_POLL) 的分支，Exynos4412 都不进去，走的是中断。

控制器对外只有四个寄存器。名字是历史遗留，一直叫 S3C2410_IIC*：

寄存器 宏名 宽度 作用
控制寄存器 S3C2410_IICCON writel/readl 应答使能、中断使能、中断挂起清除、发送时钟预分频
状态寄存器 S3C2410_IICSTAT writel/readl 收发使能、主/从模式、START/STOP 触发、仲裁失败、ACK 状态
地址寄存器 S3C2410_IICADD writeb 本控制器作为从机时的自身地址
数据寄存器 S3C2410_IICDS writeb/readb 发送/接收的那个字节

四位一体，一个字节的收发就是往 IICDS 写一次、从 IICDS 读一次。剩下的全是状态位的开关。

按素材与代码注释整理，这几个寄存器的关键位如下（位定义来自 i2c-s3c2410.c 里的宏名与代码注释，具体位号标注见「备注」列）：

寄存器 位 宏 含义
IICCON [7] 应答使能 代码注释「使能应答 IICCON 位[7]」
IICCON [5] 中断使能 代码注释「i2c 中断使能 IICCON 位[5] 设置为 1」
IICCON [4] S3C2410_IICCON_IRQPEND 中断挂起标志，写 0 清除
IICCON [3:0] 发送时钟预分频 分频值，算法见第十二章
IICSTAT [7:6] MASTER_TX / MASTER_RX 主发送 / 主接收模式
IICSTAT [5] S3C2410_IICSTAT_TXRXEN 收发使能
IICSTAT [4] S3C2410_IICSTAT_START 置 1 发出 START，清 0 发出 STOP
IICSTAT [0] S3C2410_IICSTAT_LASTBIT 最近一位的 ACK 状态
IICSTAT — S3C2410_IICSTAT_ARBITR 仲裁失败

上表的位号不是猜的：IICCON 的 [7][5][4] 三个位在素材代码注释里被明确写过，IICSTAT 的 [7:6]、[4]、[0] 是代码里 stat |= S3C2410_IICSTAT_START; /* 位[4]设置为1 */、stat |= S3C2410_IICSTAT_MASTER_TX;、iicstat & S3C2410_IICSTAT_LASTBIT 三处反推出来的。IICCON 的 [3:0] 预分频位号、IICSTAT 中 ARBITR 的确切位号，素材里没有给出，标注为「未验证」——写代码时用宏，别手写位运算。

二、硬件连接与引脚配置 #

先看原理图。这不是客套话，是从零开始时唯一能确定「挂在哪」的动作。素材给的三条结论，直接决定了后面所有代码：

从图上看出来的 结论 落到代码哪里
MPU6050 接在哪根 I2C 上 IIC 通道 5 设备树节点 i2c@138b0000
中断脚接在哪 EINT27，父节点 GPX3，index 3 节点属性 interrupt-parent = <&gpx3>; interrupts = <3 2>;
AD0 引脚电平 AD0 接地 → 从设备 7 位地址 0x68 reg = <0x68>; 与 client->addr
控制器寄存器基址 0x138B0000 节点名与 reg

三条里最容易被跳过的是第三条。AD0 是 MPU6050 的地址选择脚：接 GND 时 7 位地址是 0x68，接 VCC 时是 0x69。这个 0x68 与 MPU6050 内部 WHO_AM_I 寄存器的默认值 0x68 是巧合的一对，别混。WHO_AM_I 是「我是谁」的自报家门寄存器，地址是 0x75；0x68 是它在总线上的门牌号。

引脚这一侧，Exynos4412 用的是 pinctrl。I2C5 的两根线在设备树里由 pinctrl-0 = <&i2c5_bus>; 一次性配好复用功能，不用像老平台那样在板级 C 文件里手写 cfg_gpio 回调。素材里那个 S3C2440 版本的写法是：

c
if (i2c->pdata->cfg_gpio)   // 配置 gpio，初始化为 I2C 功能
        i2c->pdata->cfg_gpio(to_platform_device(i2c->dev));
else if (IS_ERR(i2c->pctrl) && s3c24xx_i2c_parse_dt_gpio(i2c))
        return -EINVAL;

两类平台走两条路，最终效果一样：把 SDA/SCL 两根脚从普通 GPIO 切成 I2C 复用功能，并且打开内部/外部上拉。Exynos4412 走的是 devm_pinctrl_get_select_default() 这条，pinctrl-0 里的 i2c5_bus 节点负责具体的引脚号与上拉配置。i2c5_bus 里到底配了哪两个 pin、上拉强度多少，素材原文未给出，需要查 arch/arm/boot/dts/exynos4412-pinctrl.dtsi 一类文件确认，本文标注「未验证」。

SDA 上的边沿延时由设备树属性 samsung,i2c-sda-delay 控制，素材给的是 <100>，单位 ns。它落到驱动里是：

c
/* s3c24xx_i2c_parse_dt() 中 */
i2c->pdata->sda_delay = ...

这个值最终喂给 i2c->tx_setup，在每次写完数据字节后 ndelay(i2c->tx_setup) 用。100 ns 是个保守值，意思是「数据摆到 SDA 上之后，等 100 ns 再让时钟动」，防止从机采样窗口踩到边沿。

三、驱动的分层：控制器驱动与设备驱动 #

I2C 驱动开发的工作量，按层切是四份。素材原文列得很清楚，直接照录并补上「这一层在哪、谁写」：

# 工作内容 归属 实现在哪 谁写
1 提供 I2C 适配器的硬件驱动，探测、初始化适配器（申请 I/O 地址与中断号），让 CPU 控制的 I2C 适配器从硬件上产生 总线驱动 drivers/i2c/busses/i2c-s3c2410.c 芯片厂商 / 内核
2 提供 I2C 控制的 algorithm，用具体适配器的 xxx_xfer() 填充 i2c_algorithm 的 master_xfer 指针，再把 i2c_algorithm 指针赋给 i2c_adapter 的 algo 指针 总线驱动 同上 芯片厂商 / 内核
3 实现 I2C 设备驱动中的 i2c_driver 接口，用具体 yyy 的 yyy_probe()、yyy_remove()、yyy_suspend()、yyy_resume() 函数指针和 i2c_device_id 设备 ID 表，赋给 i2c_driver 的 probe、remove、suspend、resume 与 id_table 指针 设备驱动 你的 mpu6050.c 你
4 实现 I2C 设备所对应类型的具体驱动，i2c_driver 只是完成设备与总线的挂接 设备驱动 你的 mpu6050.c 你

前两条是总线驱动，后两条是设备驱动。

这句话值得停一下。素材原文还有一段话说得比教材直白：内核和芯片提供商已经把 I2C 驱动的框架、以及框架底层与硬件相关的代码实现都给你了；剩下的只是针对挂在 I2C 两根线上的设备（device）去写具体设备驱动。这里的「设备」指的是硬件接口外面挂的芯片，不是硬件接口本身。SoC 的 I2C 接口本身的驱动，才是总线驱动。

所以整条链是：

text
应用层 open/ioctl/write/read
      │
      ▼
设备驱动 mpu6050.c（i2c_driver + 字符设备）
      │  i2c_transfer(adapter, msgs, num)
      ▼
I2C 核心 drivers/i2c/i2c-core-base.c
      │  adap->algo->master_xfer(adap, msgs, num)
      ▼
适配器驱动 i2c-s3c2410.c（i2c_algorithm）
      │  writel/readl 到 IICCON / IICSTAT / IICDS
      ▼
Exynos4412 I2C 控制器 → SDA/SCL → MPU6050

这条链上你只负责右上角那一段（设备驱动），下面三段是现成的。本章后面所有代码，都是围绕「怎么正确调用第三层」和「第三层往下是怎么动的」展开。

四、平台相关代码在哪个文件 #

从零开始时，第一个问题不是「怎么写」，而是「读哪个文件」。素材给的答案：

想看的 文件 备注
适配器驱动主体 drivers/i2c/busses/i2c-s3c2410.c 素材原路径为 e:\linux-3.14-fs4412\drivers\i2c\busses，文件时间戳 2016/10/28
I2C 核心 drivers/i2c/i2c-core-base.c 注册、匹配、探测都在这
设备树解析注册从设备 drivers/i2c/i2c-core-of.c 4.x 之后拆出来的文件
用户态直接操作 I2C drivers/i2c/i2c-dev.c 提供 /dev/i2c-N
老平台的板级从设备表 arch/arm/mach-s5pc100/mach-smdkc100.c Cortex-A8 时代的写法
Exynos4412 的设备树 arch/arm/boot/dts/exynos4412-*.dts 控制器叶子节点与 pinmux 在这

i2c-s3c2410.c 是接下来要反复翻的那个。它的模块入口是：

c
static struct platform_driver s3c24xx_i2c_driver = {
        .probe          = s3c24xx_i2c_probe,
        .remove         = s3c24xx_i2c_remove,
        .id_table       = s3c24xx_driver_ids,
        .driver         = {
                .name   = "s3c-i2c",
                .pm     = S3C24XX_DEV_PM_OPS,
                .of_match_table = of_match_ptr(s3c24xx_i2c_match),
        },
};

static int __init i2c_adap_s3c_init(void)
{
        return platform_driver_register(&s3c24xx_i2c_driver);
}
subsys_initcall(i2c_adap_s3c_init);

static void __exit i2c_adap_s3c_exit(void)
{
        platform_driver_unregister(&s3c24xx_i2c_driver);
}
module_exit(i2c_adap_s3c_exit);

注意 subsys_initcall，不是 module_init。适配器驱动必须在设备驱动之前就绪，所以它挂在比 module_init 更早的初始化段上。这也解释了一个常见困惑：为什么你的 i2c_driver 模块一 insmod 就 probe 了——因为适配器早就在那儿等着了。

五、board 文件里怎么注册 I2C 设备 #

这一章讲的是老写法，但它必须讲，因为「从零到跑通」在很多板子上仍然是从这里开始的，而且它能解释清楚设备树那套到底替代了什么。

没有设备树的年代，从设备信息写在板级 C 文件里，像这样：

c
/* arch/arm/mach-s5pc100/mach-smdkc100.c */
static struct i2c_board_info i2c_des0[] = {
        {
                I2C_BOARD_INFO("mpu6050", 0x68),
                .irq = IRQ_EINT(27),
        },
        /* 填下更多从设备 */
};

然后注册进核心：

c
static int __init smdkc100_i2c_init(void)
{
        return i2c_register_board_info(0, i2c_des0, ARRAY_SIZE(i2c_des0));
}
arch_initcall(smdkc100_i2c_init);

i2c_register_board_info() 的第一个参数是适配器编号，也就是这个从设备挂在哪一路 I2C 上。函数体只做一件事：把每个 i2c_board_info 包成一个 i2c_devinfo，追加到全局链表 __i2c_board_list 上。

c
int i2c_register_board_info(int busnum, struct i2c_board_info const *info, unsigned len)
{
        int status;

        down_write(&__i2c_board_lock);

        /* dynamic bus numbers will be assigned after the last static one */
        if (busnum >= __i2c_first_dynamic_bus_num)
                __i2c_first_dynamic_bus_num = busnum + 1;

        for (status = 0; len; len--, info++) {
                struct i2c_devinfo      *devinfo;

                devinfo = kzalloc(sizeof(*devinfo), GFP_KERNEL);
                if (!devinfo) {
                        pr_debug("i2c-core: can't register boardinfo!\n");
                        status = -ENOMEM;
                        break;
                }

                devinfo->busnum = busnum;        // 设置 I2C 适配器编号
                devinfo->board_info = *info;     // 保存 I2C 从设备信息
                /* 中间还有 properties / resources 的深拷贝，略 */

                list_add_tail(&devinfo->list, &__i2c_board_list);   // 挂到总链表
        }

        up_write(&__i2c_board_lock);

        return status;
}

真正生成设备是后来的事。等适配器注册时，核心调 i2c_scan_static_board_info() 扫这张链表：

c
static void i2c_scan_static_board_info(struct i2c_adapter *adapter)
{
        struct i2c_devinfo      *devinfo;

        down_read(&__i2c_board_lock);
        list_for_each_entry(devinfo, &__i2c_board_list, list) {
                if (devinfo->busnum == adapter->nr              // 属于这个适配器
                                && !i2c_new_device(adapter,     // 注册 I2C 从设备
                                                &devinfo->board_info))
                        dev_err(&adapter->dev,
                                "Can't create device at 0x%02x\n",
                                devinfo->board_info.addr);
        }
        up_read(&__i2c_board_lock);
}

调用点在 i2c_register_adapter() 里：

text
i2c_add_numbered_adapter()
  |
  +--> i2c_register_adapter(adap)
         |
         +--> i2c_scan_static_board_info()   // 扫 __i2c_board_list
                |
                +--> i2c_new_device()
                       |
                       +--> 1. 产生 i2c_client（填入了从设备信息）
                            2. 注册 client->dev

这就推出一个硬约束：i2c_register_board_info() 必须早于 i2c_register_adapter()。所以板级代码里用的是 arch_initcall，而适配器驱动用的是 subsys_initcall。顺序错了，链表扫的时候还是空的，设备就永远出不来，/sys/bus/i2c/devices/ 下一个条目都没有。

i2c_devinfo 本身很薄，就是链表节点加 busnum 加 board_info：

c
struct i2c_devinfo {
        struct list_head        list;   // 用于构建双向链表
        int                     busnum;  // I2C 控制器编号
        struct i2c_board_info   board_info;
};

设备树普及之后，这条路基本没人走了。核心改成扫节点：i2c_register_adapter() 在扫完静态链表之后，会调 of_i2c_register_devices()，由它遍历控制器节点下的所有子节点，每个子节点调 of_i2c_get_board_info() 解析出一个 i2c_board_info，再喂给 i2c_new_device()。

c
void of_i2c_register_devices(struct i2c_adapter *adap)
{
        struct device_node *bus, *node;
        struct i2c_client *client;

        /* Only register child devices if the adapter has a node pointer set */
        if (!adap->dev.of_node)   // 没有设备树，直接返回
                return;

        bus = of_get_child_by_name(adap->dev.of_node, "i2c-bus");
        if (!bus)                        // 没有 i2c-bus 中间层，就直接用控制器节点
                bus = of_node_get(adap->dev.of_node);

        for_each_available_child_of_node(bus, node) {
                if (of_node_test_and_set_flag(node, OF_POPULATED))
                        continue;

                client = of_i2c_register_device(adap, node);
                if (IS_ERR(client)) {
                        dev_err(&adap->dev,
                                "Failed to create I2C device for %pOF\n", node);
                        of_node_clear_flag(node, OF_POPULATED);
                }
        }

        of_node_put(bus);
}

三条路殊途同归，终点都是 i2c_new_device()。区别只在 i2c_board_info 从哪来：

来源 触发时机 谁来填 i2c_board_info 现在的地位
板级 C 文件 + i2c_register_board_info() arch_initcall 阶段 人手工写死在 .c 里 老平台遗留，新板不用
设备树子节点 适配器注册时扫节点 of_i2c_get_board_info() 解析 compatible、reg 等属性 Exynos4412 走这条
运行时 i2c_new_device() / 用户态实例化 任何时候 驱动自己或应用层 动态设备、调试用

这就是 i2c_board_info 在设备树普及后的地位变化：它从一个「你手写的板级配置结构体」，退化成一个「核心内部的中转结构」。对你来说，写设备树就等价于填 i2c_board_info 的 type、addr、irq、of_node 四个字段。你在代码里再手填一份，属于重复劳动，还会出现两份信息打架。

六、i2c_board_info 的填写 #

i2c_board_info 是个纯数据描述结构，不含函数指针。它的字段不多，但每个字段流向哪里非常明确。Linux 3.14 时期的形态：

c
struct i2c_board_info {
        char            type[I2C_NAME_SIZE];
        unsigned short  flags;
        unsigned short  addr;
        void            *platform_data;
        struct dev_archdata *archdata;
        struct device_node  *of_node;
        struct acpi_dev_node acpi_node;
        int             irq;
};

4.x 之后重构过一轮，archdata 与 acpi_node 被拿掉，换上了 dev_name、fwnode、properties、resources、num_resources：

c
struct i2c_board_info {
        char            type[I2C_NAME_SIZE];
        unsigned short  flags;
        unsigned short  addr;
        const char      *dev_name;
        void            *platform_data;
        struct device_node *of_node;
        struct fwnode_handle *fwnode;
        const struct property_entry *properties;
        const struct resource *resources;
        unsigned int    num_resources;
        int             irq;
};

填哪些字段，看下面的对照表。这张表是本篇最该抄下来的东西之一：

字段 填什么 流向 i2c_client 的哪里 你需不需要填
type 从设备名字，如 "mpu6050" client->name 必须。它决定驱动能不能匹配上
addr 7 位从地址，不含读写位，如 0x68 client->addr 必须
flags I2C_CLIENT_TEN / I2C_CLIENT_PEC / I2C_CLIENT_SLAVE / I2C_CLIENT_WAKE / I2C_CLIENT_SCCB / I2C_CLIENT_HOST_NOTIFY client->flags 十位地址、SMBus PEC 才填
irq 从设备的中断号 client->init_irq、client->irq 该设备要报警才填
platform_data 私有数据指针 client->dev.platform_data 驱动要靠板级传参才填
of_node 从设备的设备树节点 client->dev.of_node 设备树路径下由核心填
dev_name 设备名（4.x 起） client->dev.kobj.name 想自定义 /sys 目录名才填
resources / num_resources 资源数组及其长度 用于找不到 irq 时反查 一般不需要

type 这一格要加重。它直接决定 client->name，而 i2c_device_match() 拿 client->name 去和 i2c_driver.id_table 里的名字比。名字差一个字母，probe 就不会被调用，并且在 /sys 下看起来一切正常——设备在、驱动在，就是不绑。这是本篇排障问答里问得最多的一条。

addr 这一格的坑在于读写位。总线上实际传输的第一个字节是 (addr << 1) | rw，但你填 addr 时只填 7 位本体，0x68 就是 0x68，不是 0xD0。代码里移位这一步是适配器驱动替你做的：

c
unsigned int addr = (msg->addr & 0x7f) << 1;

设备树里，这个结构体由 of_i2c_get_board_info() 从节点解析出来：

c
int of_i2c_get_board_info(struct device *dev, struct device_node *node,
                          struct i2c_board_info *info)
{
        u32 addr;
        int ret;

        memset(info, 0, sizeof(*info));

        /* 取 compatible 中逗号后面的部分作为 type，如 "invensense,mpu6050" -> "mpu6050" */
        if (of_modalias_node(node, info->type, sizeof(info->type)) < 0) {
                dev_err(dev, "of_i2c: modalias failure on %pOF\n", node);
                return -EINVAL;
        }

        ret = of_property_read_u32(node, "reg", &addr);   // reg 属性即 7 位从地址
        if (ret) {
                dev_err(dev, "of_i2c: invalid reg on %pOF\n", node);
                return ret;
        }

        if (addr & I2C_TEN_BIT_ADDRESS) {           // 1<<31，十位地址标志
                addr &= ~I2C_TEN_BIT_ADDRESS;
                info->flags |= I2C_CLIENT_TEN;
        }

        if (addr & I2C_OWN_SLAVE_ADDRESS) {         // 1<<30，本机作从机标志
                addr &= ~I2C_OWN_SLAVE_ADDRESS;
                info->flags |= I2C_CLIENT_SLAVE;
        }

        info->addr = addr;
        info->of_node = node;

        if (of_property_read_bool(node, "host-notify"))
                info->flags |= I2C_CLIENT_HOST_NOTIFY;

        if (of_get_property(node, "wakeup-source", NULL))
                info->flags |= I2C_CLIENT_WAKE;

        return 0;
}

of_modalias_node() 那条注释是关键：compatible 里逗号前半段是厂商前缀，后半段才落到 info->type。所以我们写 compatible = "invensense,mpu6050"，最终 client->name 是 "mpu6050"，正好对上 i2c_device_id mpu6050_id[] = {{"mpu6050", 0}, {}}。

顺带纠一个素材里的拼写。素材设备树写的是 compatible = "invense,mpu6050"，少了个 ns；驱动里的 mpu6050_dt_match 也跟着写 {.compatible = "invense,mpu6050"}。设备树与驱动两处必须逐字一致才能匹配，所以素材那套代码「自洽但拼错」。上游内核里 MPU6050 的 compatible 是 invensense,mpu6050。你照素材抄不会出错（两边都错就是一致），但别和别的代码混用。

再看 i2c_client 到底被填成了什么样：

c
static struct i2c_client *
i2c_new_client_device(struct i2c_adapter *adap, struct i2c_board_info const *info)
{
        struct i2c_client       *client;
        int                     status;

        client = kzalloc(sizeof *client, GFP_KERNEL);
        if (!client)
                return ERR_PTR(-ENOMEM);

        client->adapter = adap;
        client->dev.platform_data = info->platform_data;
        client->flags = info->flags;
        client->addr = info->addr;

        client->init_irq = info->irq;
        if (!client->init_irq)   // 没设中断号就从 resources 里找
                client->init_irq = i2c_dev_irq_from_resources(info->resources,
                                                         info->num_resources);
        client->irq = client->init_irq;

        strlcpy(client->name, info->type, sizeof(client->name));   // type -> name

        status = i2c_check_addr_validity(client->addr, client->flags);
        if (status) {
                dev_err(&adap->dev, "Invalid %d-bit I2C address 0x%02hx\n",
                        client->flags & I2C_CLIENT_TEN ? 10 : 7, client->addr);
                goto out_err_silent;
        }

        status = i2c_check_addr_busy(adap, i2c_encode_flags_to_addr(client));
        if (status)
                goto out_err;

        client->dev.parent = &client->adapter->dev;
        client->dev.bus = &i2c_bus_type;
        client->dev.type = &i2c_client_type;
        client->dev.of_node = of_node_get(info->of_node);
        client->dev.fwnode = info->fwnode;

        i2c_dev_set_name(adap, client, info);

        status = device_register(&client->dev);
        if (status)
                goto out_free_props;

        dev_dbg(&adap->dev, "client [%s] registered with bus id %s\n",
                client->name, dev_name(&client->dev));

i2c_check_addr_validity() 那道检查卡在 0x08 ~ 0x77。0x00 是广播地址，留给它的是保留区；0x78 以上被十位地址前缀占掉。MPU6050 的 0x68 落在这个区间内，没问题。

i2c_dev_set_name() 决定了 /sys/bus/i2c/devices/ 下的目录名格式是 %d-%04x：前面是适配器编号，后面是从地址。.68 这种名字就来自这里。

七、适配器驱动的 probe 流程 #

probe 是适配器驱动从「平台设备出现」到「/dev/i2c-5 可用」的全部工作。函数长，但骨架只有八步。

c
static int s3c24xx_i2c_probe(struct platform_device *pdev)
{
        struct s3c24xx_i2c *i2c;
        struct s3c2410_platform_i2c *pdata = NULL;
        struct resource *res;
        int ret;

        if (!pdev->dev.of_node) {
                pdata = dev_get_platdata(&pdev->dev);     // 非设备树平台：取板级 platform_data
                if (!pdata) {
                        dev_err(&pdev->dev, "no platform data\n");
                        return -EINVAL;
                }
        }

        i2c = devm_kzalloc(&pdev->dev, sizeof(struct s3c24xx_i2c), GFP_KERNEL);
        if (!i2c)
                return -ENOMEM;

        i2c->pdata = devm_kzalloc(&pdev->dev, sizeof(*pdata), GFP_KERNEL);
        if (!i2c->pdata)
                return -ENOMEM;

        i2c->quirks = s3c24xx_get_device_quirks(pdev);
        i2c->sysreg = ERR_PTR(-ENOENT);
        if (pdata)
                memcpy(i2c->pdata, pdata, sizeof(*pdata));
        else
                s3c24xx_i2c_parse_dt(pdev->dev.of_node, i2c);      // 设备树平台：解析属性

        strlcpy(i2c->adap.name, "s3c2410-i2c", sizeof(i2c->adap.name));
        i2c->adap.owner = THIS_MODULE;
        i2c->adap.algo = &s3c24xx_i2c_algorithm;                   // 关键：挂上算法
        i2c->adap.retries = 2;
        i2c->adap.class = I2C_CLASS_DEPRECATED;                    // 不支持按 class 自动探测从设备
        i2c->tx_setup = 50;

        init_waitqueue_head(&i2c->wait);

        i2c->dev = &pdev->dev;
        i2c->clk = devm_clk_get(&pdev->dev, "i2c");                // 取 i2c 时钟
        if (IS_ERR(i2c->clk)) {
                dev_err(&pdev->dev, "cannot get clock\n");
                return -ENOENT;
        }

        res = platform_get_resource(pdev, IORESOURCE_MEM, 0);      // 第 0 个内存资源
        i2c->regs = devm_ioremap_resource(&pdev->dev, res);       // 物理地址 -> 虚拟地址
        if (IS_ERR(i2c->regs))
                return PTR_ERR(i2c->regs);

        i2c->adap.algo_data = i2c;                                 // algo_data 指向自己
        i2c->adap.dev.parent = &pdev->dev;
        i2c->pctrl = devm_pinctrl_get_select_default(i2c->dev);

        /* 初始化 I2C 两根线 */
        if (i2c->pdata->cfg_gpio)
                i2c->pdata->cfg_gpio(to_platform_device(i2c->dev));
        else if (IS_ERR(i2c->pctrl) && s3c24xx_i2c_parse_dt_gpio(i2c))
                return -EINVAL;

        ret = clk_prepare_enable(i2c->clk);
        if (ret) {
                dev_err(&pdev->dev, "I2C clock enable failed\n");
                return ret;
        }

        ret = s3c24xx_i2c_init(i2c);                               // 初始化控制器寄存器
        clk_disable(i2c->clk);
        if (ret != 0) {
                dev_err(&pdev->dev, "I2C controller init failed\n");
                clk_unprepare(i2c->clk);
                return ret;
        }

        if (!(i2c->quirks & QUIRK_POLL)) {                         // 中断方式
                i2c->irq = ret = platform_get_irq(pdev, 0);
                if (ret <= 0) {
                        dev_err(&pdev->dev, "cannot find IRQ\n");
                        clk_unprepare(i2c->clk);
                        return ret;
                }

                ret = devm_request_irq(&pdev->dev, i2c->irq, s3c24xx_i2c_irq,
                                       0, dev_name(&pdev->dev), i2c);
                if (ret != 0) {
                        dev_err(&pdev->dev, "cannot claim IRQ %d\n", i2c->irq);
                        clk_unprepare(i2c->clk);
                        return ret;
                }
        }

        ret = s3c24xx_i2c_register_cpufreq(i2c);
        if (ret < 0) {
                dev_err(&pdev->dev, "failed to register cpufreq notifier\n");
                clk_unprepare(i2c->clk);
                return ret;
        }

        i2c->adap.nr = i2c->pdata->bus_num;
        i2c->adap.dev.of_node = pdev->dev.of_node;

        platform_set_drvdata(pdev, i2c);

        pm_runtime_enable(&pdev->dev);

        ret = i2c_add_numbered_adapter(&i2c->adap);                // 注册适配器
        if (ret < 0) {
                pm_runtime_disable(&pdev->dev);
                s3c24xx_i2c_deregister_cpufreq(i2c);
                clk_unprepare(i2c->clk);
                return ret;
        }

        dev_info(&pdev->dev, "%s: S3C I2C adapter\n", dev_name(&i2c->adap.dev));
        return 0;
}

八步拆开：

  1. 拿板级数据。设备树平台跳过这步，改由 s3c24xx_i2c_parse_dt() 从属性解析。
  2. 申请 struct s3c24xx_i2c，把 pdata 拷贝进去。
  3. 填 i2c_adapter：name、owner、algo、retries、class。algo 是整个驱动的中枢，指向 s3c24xx_i2c_algorithm。
  4. 取时钟 devm_clk_get()，此时先不使能。
  5. 映射寄存器：platform_get_resource(IORESOURCE_MEM, 0) 拿到物理地址，devm_ioremap_resource() 映射成虚拟地址存在 i2c->regs。
  6. 配引脚：devm_pinctrl_get_select_default() 或 cfg_gpio() 回调。
  7. 使能时钟 → s3c24xx_i2c_init() 初始化寄存器 → 关时钟。这一步做完，控制器已经能按正确速度产生时钟了。
  8. 拿中断号、devm_request_irq() 注册 s3c24xx_i2c_irq、i2c_add_numbered_adapter() 注册适配器。

私有结构体 s3c24xx_i2c 是这一切的载体：

c
struct s3c24xx_i2c {  // 用来表示 SoC 的一个 I2C 控制器
        wait_queue_head_t       wait;     // 等待队列
        kernel_ulong_t          quirks;   // 控制器的一些特殊行为

        struct i2c_msg          *msg;     // 当前要发的数据包
        unsigned int            msg_num;  // 数据包个数
        unsigned int            msg_idx;  // 当前数据包索引
        unsigned int            msg_ptr;  // 当前字节在数据包内的索引

        unsigned int            tx_setup; // 延时，等 SCL 释放
        unsigned int            irq;      // 中断号

        enum s3c24xx_i2c_state  state;    // STATE_START / STATE_IDLE / STATE_STOP / STATE_WRITE / STATE_READ
        unsigned long           clkrate;

        void __iomem            *regs;
        struct clk              *clk;
        struct device           *dev;
        struct i2c_adapter      adap;     // 该控制器的适配器

        struct s3c2410_platform_i2c     *pdata;
        int                     gpios[2];
        struct pinctrl          *pctrl;
#if defined(CONFIG_ARM_S3C24XX_CPUFREQ)
        struct notifier_block   freq_transition;
#endif
        struct regmap           *sysreg;
        unsigned int            sys_i2c_cfg;
};

四个游标要分清：msg 是当前数据包指针，msg_num 是剩余包数（传完一包减到 0 就唤醒等待队列），msg_idx 是已完成的包数，msg_ptr 是当前包内的字节偏移。state 是中断处理器的工作状态机，五态流转构成整条传输。

pdata 对应的是 s3c2410_platform_i2c，非设备树平台的参数入口：

c
struct s3c2410_platform_i2c {
        int             bus_num;    // I2C 控制器编号
        unsigned int    flags;
        unsigned int    slave_addr;  // 从设备地址（本控制器当从机时用）
        unsigned long   frequency;   // 时钟频率
        unsigned int    sda_delay;

        void    (*cfg_gpio)(struct platform_device *dev);  // 把引脚复用成 I2C
};

cfg_gpio 这个回调在设备树平台是废弃的，靠 pinctrl 替代。bus_num 却是关键：它就是 /dev/i2c-N 里的那个 N，也是 i2c_board_info 里 busnum 匹配的键。素材里 MPU6050 挂通道 5，所以 bus_num 是 5，设备节点是 i2c@138b0000。

八、寄存器映射与初始化 #

i2c->regs 到手之后，s3c24xx_i2c_init() 负责让控制器进入可工作的初始状态。就三件事：

c
static int s3c24xx_i2c_init(struct s3c24xx_i2c *i2c)
{
        struct s3c2410_platform_i2c *pdata;
        unsigned int freq;

        pdata = i2c->pdata;

        /* 写从设备地址 */
        writeb(pdata->slave_addr, i2c->regs + S3C2410_IICADD);
        dev_info(i2c->dev, "slave address 0x%02x\n", pdata->slave_addr);

        writel(0, i2c->regs + S3C2410_IICCON);                  // IICCON 清零
        writel(0, i2c->regs + S3C2410_IICSTAT);                 // IICSTAT 清零

        /* 算时钟分频 */
        if (s3c24xx_i2c_clockrate(i2c, &freq) != 0) {
                dev_err(i2c->dev, "cannot meet bus frequency required\n");
                return -EINVAL;
        }

        dev_info(i2c->dev, "bus frequency set to %d KHz\n", freq);
        dev_dbg(i2c->dev, "S3C2410_IICCON=0x%02x\n",
                readl(i2c->regs + S3C2410_IICCON));

        return 0;
}

三件事按顺序：

步骤 操作 为什么
1 writeb(pdata->slave_addr, regs + IICADD) 万一这根总线被别的控制器当从机访问，得有个门牌号
2 writel(0, regs + IICCON)、writel(0, regs + IICSTAT) 清掉上电残留的应答使能、模式位、START 位、中断挂起
3 s3c24xx_i2c_clockrate(i2c, &freq) 算分频，把结果写进 IICCON 低四位

第 2 步不能省。IICCON 的 bit[4] 是中断挂起标志，如果上电时它是脏的，你 devm_request_irq() 注册完中断会立刻进一次处理函数，而那时 i2c->state 还是 STATE_IDLE，中断处理函数会走 dev_dbg(i2c->dev, "IRQ: error i2c->state == IDLE\n") 然后清标志退出。这一次多余的进入不致命，但会让人以为「中断在乱跳」。

第 3 步函数体素材未给出，本文按 IICCON 低四位分频的常见实现写公式，见第十二章。s3c24xx_i2c_clockrate() 的内部代码本文未取得原文，标「未验证」。

还有一处容易忽略：i2c->adap.retries = 2。这个值是重试次数，出现在 master_xfer 的循环上限里。传输遇到 -EAGAIN（总线被占用拿不到）时会重试两次，每次之间 udelay(100)。两次都拿不到就返回 -EREMOTEIO。

九、i2c_algorithm 的实现：master_xfer #

i2c_algorithm 有三个函数指针，Adaptor 侧只实现两个：

c
static const struct i2c_algorithm s3c24xx_i2c_algorithm = {
        .master_xfer            = s3c24xx_i2c_xfer,      /* 数据传输 */
        .functionality          = s3c24xx_i2c_func,      /* 报告本适配器支持哪些 I2C 功能 */
};

smbus_xfer 留空。这意思是本适配器不支持 SMBus 专用传输，内核核心会用 master_xfer 拼出等价操作。

master_xfer 是整个适配器驱动的出口。设备驱动调 i2c_transfer()，核心层转一手，最终落到这里。Exynos4412 上的实现分四层，一层调一层：

text
i2c_transfer()
  └── __i2c_transfer()                      内核核心，带重试与 trace
        └── adap->algo->master_xfer(...)    ← s3c24xx_i2c_xfer
              └── s3c24xx_i2c_doxfer()
                    ├── s3c24xx_i2c_set_master()        拿总线
                    ├── s3c24xx_i2c_enable_irq()        开 IICCON[5]
                    ├── s3c24xx_i2c_message_start()     发地址，触发 START
                    ├── wait_event_timeout(..., HZ*5)   睡到传输完成
                    ├── s3c24xx_i2c_wait_idle()
                    └── s3c24xx_i2c_disable_bus()

第一层，s3c24xx_i2c_xfer()：

c
static int s3c24xx_i2c_xfer(struct i2c_adapter *adap,
                        struct i2c_msg *msgs, int num)
{
        struct s3c24xx_i2c *i2c = (struct s3c24xx_i2c *)adap->algo_data;  // 取私有数据
        int retry;
        int ret;

        ret = clk_enable(i2c->clk);
        if (ret)
                return ret;

        for (retry = 0; retry < adap->retries; retry++) {    // 失败重试

                ret = s3c24xx_i2c_doxfer(i2c, msgs, num);

                if (ret != -EAGAIN) {
                        clk_disable(i2c->clk);
                        return ret;
                }

                dev_dbg(i2c->dev, "Retrying transmission (%d)\n", retry);

                udelay(100);
        }

        clk_disable(i2c->clk);
        return -EREMOTEIO;
}

adap->algo_data 就是 probe 里那句 i2c->adap.algo_data = i2c; 存进去的。这是从通用类型拿回私有类型的标准手法，不用 container_of。

第二层，s3c24xx_i2c_doxfer()：

c
static int s3c24xx_i2c_doxfer(struct s3c24xx_i2c *i2c,
                              struct i2c_msg *msgs, int num)
{
        unsigned long timeout;
        int ret;

        ret = s3c24xx_i2c_set_master(i2c);
        if (ret != 0) {
                dev_err(i2c->dev, "cannot get bus (error %d)\n", ret);
                ret = -EAGAIN;
                goto out;
        }

        i2c->msg     = msgs;         // 数据包
        i2c->msg_num = num;          // 一般只有一个
        i2c->msg_ptr = 0;
        i2c->msg_idx = 0;
        i2c->state   = STATE_START;

        s3c24xx_i2c_enable_irq(i2c);             // IICCON 位[5] 置 1
        s3c24xx_i2c_message_start(i2c, msgs);    // 真正发地址 + START

        if (i2c->quirks & QUIRK_POLL) {          // 轮询模式，Exynos4412 不进
                ret = i2c->msg_idx;
                if (ret != num)
                        dev_dbg(i2c->dev, "incomplete xfer (%d)\n", ret);
                goto out;
        }

        timeout = wait_event_timeout(i2c->wait, i2c->msg_num == 0, HZ * 5);

        ret = i2c->msg_idx;

        if (timeout == 0)
                dev_dbg(i2c->dev, "timeout\n");
        else if (ret != num)
                dev_dbg(i2c->dev, "incomplete xfer (%d)\n", ret);

        if (i2c->quirks & QUIRK_HDMIPHY)
                goto out;

        s3c24xx_i2c_wait_idle(i2c);      // 等总线空闲

        s3c24xx_i2c_disable_bus(i2c);

 out:
        i2c->state = STATE_IDLE;

        return ret;
}

wait_event_timeout(i2c->wait, i2c->msg_num == 0, HZ * 5) 这一行是理解整个驱动的钥匙。它就是素材里那句「i2c_transfer() 只发送第一个 msg 的第一个字节，然后就阻塞」的落点。内核版本里 HZ * 5 是按 jiffies 计的 5 秒超时；素材原文只写了 wait_event_timeout 进入阻塞状态，没给超时值。

把它讲透：

  • 调用方（你的 mpu6050_read_byte()）线程在这里睡下去。
  • 控制器此时已经把从地址 + 读写位推出去了，正在等从机回 ACK。
  • 从机回 ACK（或回数据）触发中断，中断处理函数进 i2c_s3c_irq_nextbyte()，一个字节一个字节把剩下的全推完。
  • 全部推完时调 s3c24xx_i2c_stop() → s3c24xx_i2c_master_complete() → wake_up。
  • wake_up 让 msg_num 归零，条件成立，wait_event_timeout 返回，调用方线程被唤醒。

所以一次 i2c_transfer() 是「前台一个字节 + 中断推完剩下的 + 睡到中断叫醒」的模式。这是本控制器驱动的核心设计，不是缺陷。

第三层，s3c24xx_i2c_message_start()。这个函数只做传输的起手式：设模式、发地址、拉 START。

c
static void s3c24xx_i2c_message_start(struct s3c24xx_i2c *i2c,
                                      struct i2c_msg *msg)
{
        unsigned int addr = (msg->addr & 0x7f) << 1;   // 7 位地址左移，腾出读写位
        unsigned long stat;
        unsigned long iiccon;

        stat = 0;
        stat |=  S3C2410_IICSTAT_TXRXEN;               // 收发使能

        if (msg->flags & I2C_M_RD) {                   // 读：主接收
                stat |= S3C2410_IICSTAT_MASTER_RX;
                addr |= 1;                             // 读写位置 1
        } else                                          // 写：主发送
                stat |= S3C2410_IICSTAT_MASTER_TX;

        if (msg->flags & I2C_M_REV_DIR_ADDR)            // 协议畸形场景：翻转读写位
                addr ^= 1;

        s3c24xx_i2c_enable_ack(i2c);                   // 1. IICCON 位[7] 使能应答

        iiccon = readl(i2c->regs + S3C2410_IICCON);
        writel(stat, i2c->regs + S3C2410_IICSTAT);     // 2. 写工作模式

        dev_dbg(i2c->dev, "START: %08lx to IICSTAT, %02x to DS\n", stat, addr);
        writeb(addr, i2c->regs + S3C2410_IICDS);       // 3. 把地址塞进数据寄存器

        ndelay(i2c->tx_setup);                         // 等数据摆稳到总线上

        dev_dbg(i2c->dev, "iiccon, %08lx\n", iiccon);
        writel(iiccon, i2c->regs + S3C2410_IICCON);

        stat |= S3C2410_IICSTAT_START;                 // 4. 位[4] 置 1
        writel(stat, i2c->regs + S3C2410_IICSTAT);     //    使能串行输出，发出 START

        if (i2c->quirks & QUIRK_POLL) {                // 轮询模式才会进，Exynos4412 不进
                while ((i2c->msg_num != 0) && is_ack(i2c)) {
                        i2c_s3c_irq_nextbyte(i2c, stat);
                        stat = readl(i2c->regs + S3C2410_IICSTAT);

                        if (stat & S3C2410_IICSTAT_ARBITR)
                                dev_err(i2c->dev, "deal with arbitration loss\n");
                }
        }
}

三个细节别漏。

ndelay(i2c->tx_setup) 的位置在写 IICDS 之后、写 IICSTAT 之前。注释说明得很清楚：写数据寄存器会让第一个 bit 出现在 SDA 上，而中断一应答 SCL 就会变化，所以要等一下，保证数据建立时间。tx_setup 初值是 50（ns），可由 samsung,i2c-sda-delay 覆盖。

iiccon 是先读后写的。读出当前值（含分频、应答使能等），暂存，写 IICSTAT，再原样写回 IICCON。原因在硬件：写 IICCON 的动作会清除中断挂起标志，如果不小心把其它位写坏，分频就乱了。素材原文用 iiccon, %08lx 的调试打印点出了这一读一写。

I2C_M_REV_DIR_ADDR 这个分支是给协议畸形场景用的——极少数器件要求读写位反着来。正常情况下 addr 就按常规拼。

十、一次传输的寄存器操作序列 #

把前两层的代码串成时序，一次「写一个字节然后读一个字节」的完整动作是这样。以 MPU6050 的 who_am_i 读为例（先写寄存器地址 0x75，再读回 1 字节）：

# 谁 动作 具体到寄存器
1 i2c_transfer() 加锁、取 adapter —
2 s3c24xx_i2c_xfer() clk_enable() —
3 s3c24xx_i2c_doxfer() set_master() 抢总线 读 IICSTAT 判忙
4 同上 记 msg/msg_num/state = STATE_START 软件状态
5 同上 enable_irq() IICCON bit[5] = 1
6 message_start() enable_ack() IICCON bit[7] = 1
7 同上 写模式（主发送） IICSTAT = `TXRXEN
8 同上 写从地址 + 写方向 IICDS = `(0x68 << 1)
9 同上 延时 tx_setup —
10 同上 置 START IICSTAT
11 硬件 发 START + 8 位地址 + 等 ACK SDA/SCL
12 硬件 ACK 回来，拉中断 —
13 s3c24xx_i2c_irq() 读状态 IICSTAT
14 i2c_s3c_irq_nextbyte() STATE_START → STATE_WRITE，写第一个数据字节 IICDS = 0x75
15 硬件 发数据 + 等 ACK，拉中断 —
16 中断 STATE_WRITE，本包已到末字节、非末包 → msg++，重新 message_start() 回第 6 步，方向改为读
17 中断 第二个包为读，`addr = 1→0xD1`
18 硬件 重发 START + 地址（读），从机回数据 —
19 中断 STATE_READ：readb(IICDS) 取回字节 写入 msg->buf[0]
20 中断 是末包末字节 → disable_ack() IICCON bit[7] = 0
21 中断 s3c24xx_i2c_stop() → 写 STOP IICSTAT 清 START
22 中断 master_complete() → wake_up() msg_num = 0
23 调用方 wait_event_timeout() 返回，xfer() 关时钟返回 —

第 8 步那个 0xD0 是整张表里最容易翻车的数字。0x68 << 1 = 0xD0，写方向时最低位是 0；读方向时 0xD1。而 msg->addr 里存的始终是 0x68。你在 i2c_msg 里写 0xD0，适配器会再左移一次变成 0x1A0，& 0x7f 之后变 0x20，于是总线上去找一个不存在的 0x20，回 NAK，i2c_transfer() 返回 -ENXIO。这个错误在排障问答里排第二常见。

第 23 步之后还有两件事，在 doxfer() 的尾部：s3c24xx_i2c_wait_idle() 等总线真正空下来，s3c24xx_i2c_disable_bus() 关收发使能。不关的话，控制器会一直占着 SDA/SCL 不放，下次传输 set_master() 拿不到总线，返回 -EAGAIN，重试两次后 -EREMOTEIO。

十一、中断处理与传输完成判定 #

中断处理器是这套驱动的发动机。两个函数：入口 s3c24xx_i2c_irq()，干活的 i2c_s3c_irq_nextbyte()。

入口先做异常兜底：

c
static irqreturn_t s3c24xx_i2c_irq(int irqno, void *dev_id)
{
        struct s3c24xx_i2c *i2c = dev_id;
        unsigned long status;
        unsigned long tmp;

        status = readl(i2c->regs + S3C2410_IICSTAT);

        if (status & S3C2410_IICSTAT_ARBITR) {      // 仲裁失败
                dev_err(i2c->dev, "deal with arbitration loss\n");
        }

        if (i2c->state == STATE_IDLE) {             // 空闲态进来，属异常
                dev_dbg(i2c->dev, "IRQ: error i2c->state == IDLE\n");

                tmp = readl(i2c->regs + S3C2410_IICCON);
                tmp &= ~S3C2410_IICCON_IRQPEND;
                writel(tmp, i2c->regs + S3C2410_IICCON);   // 清 IICCON 位[4]
                goto out;
        }

        /*
         * pretty much this leaves us with the fact that we've
         * transmitted or received whatever byte we last sent
         */
        i2c_s3c_irq_nextbyte(i2c, status);          // 继续推进

 out:
        return IRQ_HANDLED;
}

state == STATE_IDLE 时那次「清标志退出」是必须的。中断挂起位如果不清，中断会立刻再进一次，变成死循环把 CPU 钉死。

dev_err 打印仲裁失败但没做恢复动作。单主机总线上仲裁失败基本不会发生；真发生了，说明有多主机在抢，本驱动只报告不仲裁，这次传输会靠超时收场。

干活的函数是一个以 state 为主轴的状态机：

c
static int i2c_s3c_irq_nextbyte(struct s3c24xx_i2c *i2c, unsigned long iicstat)
{
        unsigned long tmp;
        unsigned char byte;
        int ret = 0;

        switch (i2c->state) {

        case STATE_IDLE:
                dev_err(i2c->dev, "%s: called in STATE_IDLE\n", __func__);
                goto out;

        case STATE_STOP:
                dev_err(i2c->dev, "%s: called in STATE_STOP\n", __func__);
                s3c24xx_i2c_disable_irq(i2c);
                goto out_ack;

        case STATE_START:
                if (iicstat & S3C2410_IICSTAT_LASTBIT &&
                    !(i2c->msg->flags & I2C_M_IGNORE_NAK)) {
                        /* 上一次发地址没收到 ACK */
                        dev_dbg(i2c->dev, "ack was not received\n");
                        s3c24xx_i2c_stop(i2c, -ENXIO);
                        goto out_ack;
                }

                if (i2c->msg->flags & I2C_M_RD)
                        i2c->state = STATE_READ;
                else
                        i2c->state = STATE_WRITE;

                /* 长度为 0 的传输，用来探测设备在不在 */
                if (is_lastmsg(i2c) && i2c->msg->len == 0) {
                        s3c24xx_i2c_stop(i2c, 0);
                        goto out_ack;
                }

                if (i2c->state == STATE_READ)
                        goto prepare_read;

                /* 写态直接穿下去，还要发一个字节 */
        case STATE_WRITE:
                if (!(i2c->msg->flags & I2C_M_IGNORE_NAK)) {
                        if (iicstat & S3C2410_IICSTAT_LASTBIT) {   // 没收到 ACK
                                dev_dbg(i2c->dev, "WRITE: No Ack\n");
                                s3c24xx_i2c_stop(i2c, -ECONNREFUSED);
                                goto out_ack;
                        }
                }

 retry_write:
                if (!is_msgend(i2c)) {          // 本包还有字节
                        byte = i2c->msg->buf[i2c->msg_ptr++];
                        writeb(byte, i2c->regs + S3C2410_IICDS);
                        ndelay(i2c->tx_setup);
                } else if (!is_lastmsg(i2c)) {  // 本包写完，还有下一包
                        dev_dbg(i2c->dev, "WRITE: Next Message\n");

                        i2c->msg_ptr = 0;
                        i2c->msg_idx++;
                        i2c->msg++;

                        if (i2c->msg->flags & I2C_M_NOSTART) {
                                if (i2c->msg->flags & I2C_M_RD) {
                                        /*
                                         * 不行：控制器换方向时会强制重发 START
                                         */
                                        s3c24xx_i2c_stop(i2c, -EINVAL);
                                }
                                goto retry_write;
                        } else {
                                /* 发一个新的 START */
                                s3c24xx_i2c_message_start(i2c, i2c->msg);
                                i2c->state = STATE_START;
                        }
                } else {
                        /* 最后一包也写完了 */
                        s3c24xx_i2c_stop(i2c, 0);
                }
                break;

        case STATE_READ:
                byte = readb(i2c->regs + S3C2410_IICDS);
                i2c->msg->buf[i2c->msg_ptr++] = byte;

                /* SMBus block read：首字节是实际长度 */
                if (i2c->msg->flags & I2C_M_RECV_LEN && i2c->msg->len == 1)
                        i2c->msg->len += byte;
 prepare_read:
                if (is_msglast(i2c)) {
                        /* 已经是缓冲区最后一字节 */
                        if (is_lastmsg(i2c))
                                s3c24xx_i2c_disable_ack(i2c);
                } else if (is_msgend(i2c)) {
                        if (is_lastmsg(i2c)) {
                                dev_dbg(i2c->dev, "READ: Send Stop\n");
                                s3c24xx_i2c_stop(i2c, 0);
                        } else {
                                dev_dbg(i2c->dev, "READ: Next Transfer\n");
                                i2c->msg_ptr = 0;
                                i2c->msg_idx++;
                                i2c->msg++;
                        }
                }
                break;
        }

 out_ack:
        tmp = readl(i2c->regs + S3C2410_IICCON);
        tmp &= ~S3C2410_IICCON_IRQPEND;
        writel(tmp, i2c->regs + S3C2410_IICCON);   // 清中断挂起
 out:
        return ret;
}

状态切换表：

进入时的 state 条件 去向 做了什么
STATE_IDLE — 退出 打错误日志，不干活
STATE_STOP — out_ack 关中断，清挂起
STATE_START LASTBIT 置位且非 IGNORE_NAK out_ack 地址无人应答，stop(-ENXIO)
STATE_START 本包为读 STATE_READ 跳 prepare_read
STATE_START len == 0 out_ack 起停探测设备，stop(0)
STATE_START 本包为写 STATE_WRITE（穿透） 继续发数据字节
STATE_WRITE LASTBIT 置位（无 ACK） out_ack stop(-ECONNREFUSED)
STATE_WRITE 本包还有字节 STATE_WRITE 写下一个字节到 IICDS
STATE_WRITE 本包完，非末包 STATE_START msg++，重新 message_start()
STATE_WRITE 末包完 out_ack stop(0)
STATE_READ 非末字节 STATE_READ 收下字节
STATE_READ 末字节且末包 out_ack disable_ack() + stop(0)
STATE_READ 末字节非末包 STATE_READ msg++ 继续收

LASTBIT 这一位是传输完成判定的失败分支。它不是「传完了」，是「最后一位是高电平，说明从机没拉低 ACK」。所以 STATE_START 里看到它，含义是「地址没人理」，返回 -ENXIO；STATE_WRITE 里看到它，含义是「数据被拒收」，返回 -ECONNREFUSED。两个返回值都不是超时，说明帧结构本身没错，只是对端没应答。

成功分支不带 LASTBIT：末包末字节正常推进到 stop(0)，stop() 内部走 master_complete() → wake_up()，睡在 wait_event_timeout 上的线程被叫醒，msg_num == 0 条件成立，doxfer() 返回 i2c->msg_idx。上层 i2c_transfer() 返回的就是「成功执行了几个 msg」。

还有个坑在 STATE_WRITE 的 I2C_M_NOSTART 分支。如果下一包既要求不重发 START，又是读方向，驱动会直接 stop(-EINVAL)，注释写得很直白：「控制器换方向时会强制我们发新的 START，做不到」。所以在 s3c2410 系列控制器上，I2C_M_NOSTART 只能用于「连写」，不能用于「写转读」。

十二、时钟与速率的配置 #

SCL 频率由 IICCON 低四位分频决定。设备树里给的是目标值，驱动算出来的实际值和它有出入，原因是整数除法要取整。

素材给的属性与取值：

位置 属性 取值 换算
MPU6050 所在的 i2c@138b0000 samsung,i2c-max-bus-freq <20000> 20 kHz
另一路 i2c@13870000 片段 samsung,i2c-max-bus-freq <100000> 100 kHz
S3C2440 板级默认数据 .frequency 100*1000 100 kHz
S3C2440 板级默认数据 .sda_delay 100 100 ns

MPU6050 那一档的 20 kHz 值得注意：标准模式是 100 kHz，快速模式是 400 kHz，20 kHz 远低于标准模式。为什么这么慢，素材没解释（原文未标注原因）。工程上的考虑无非几种：排线长、上拉电阻配大了导致边沿太缓、或者调试阶段先求稳再提速。跑通之后你可以试着提到 100000，如果不稳再退回。

分频怎么算。S3C2410 系列控制器的公式形态是：

text
IICCON[3:0] = (PCLK / (目标频率 × 16)) - 1
实际频率    = PCLK / ((IICCON[3:0] + 1) × 16)

-1 不能省，+1 也不能省：那四位存的是分频系数减一。

举个算例，假设 PCLK 是 66 MHz，目标 100 kHz：

text
分频系数 = 66,000,000 / (100,000 × 16) = 41.25 → 取 41
IICCON[3:0] = 41 - 1 = 40 = 0x28
实际频率 = 66,000,000 / ((40 + 1) × 16) = 66,000,000 / 656 = 100,610 Hz ≈ 100 kHz

再算 20 kHz：

text
分频系数 = 66,000,000 / (20,000 × 16) = 206.25 → 取 206
IICCON[3:0] = 206 - 1 = 205 = 0xCD
实际频率 = 66,000,000 / ((205 + 1) × 16) = 66,000,000 / 3296 = 20,024 Hz ≈ 20 kHz

这两个算例里的 PCLK = 66 MHz 是我假设的，不是素材给的，标注「未验证」。 Exynos4412 的 PCLK 具体值要去查时钟树或跑 cat /sys/kernel/debug/clk/clk_summary。你把实际 PCLK 代进去重算，公式与 -1 的写法是对的。

IICCON[3:0] 只有 4 位，最大 15，也就是分频系数最大 16。如果 PCLK 太高、目标频率太低，算出来会超过 15，这时 s3c24xx_i2c_clockrate() 会返回错误，probe 里报 "cannot meet bus frequency required"，初始化失败，/dev/i2c-N 干脆不出现。这条错误日志指的就是「你要求的频率低到分频器做不到」。

还有 samsung,i2c-sda-delay = <100>。这个不是时钟分频，是 SDA 边沿延时，落到 i2c->tx_setup，在写数据字节后 ndelay() 用。它影响的是数据建立时间，不是频率。频率不对会整体变慢或通信失败，这个值不对则是偶发误码——波形上看得出数据翻转贴着时钟边沿。

设备侧的骨架就三块：i2c_device_id 表、of_device_id 表、i2c_driver 结构体。MPU6050 的完整版：

素材原文这里有两处笔误，直接抄会编译不过：

c
/* 素材原文 */
static init _init mpu6050_init(void)     /* 应为 static int __init */

i2c_add_driver() 是一个宏，包了 THIS_MODULE：

c
#define i2c_add_driver(driver) \
    i2c_register_driver(THIS_MODULE, driver)

展开之后是 i2c_register_driver()，函数体：

c
int i2c_register_driver(struct module *owner, struct i2c_driver *driver)
{
        int res;

        /* Can't register until after driver model init */
        if (WARN_ON(!is_registered))
                return -EAGAIN;

        driver->driver.owner = owner;
        driver->driver.bus = &i2c_bus_type;    // 挂到 I2C 总线
        INIT_LIST_HEAD(&driver->clients);

        /* 返回时，driver core 已对所有「匹配但未绑定」的设备调过 probe() */
        res = driver_register(&driver->driver);
        if (res)
                return res;

        pr_debug("driver [%s] registered\n", driver->driver.name);

        /* 遍历已经在的总线 */
        i2c_for_each_dev(driver, __process_new_driver);

        return 0;
}

三个动作按顺序：设 owner 和 bus、driver_register() 真正进驱动模型、i2c_for_each_dev() 反向遍历已有适配器。

第二步的注释值得读两遍：driver_register() 返回时，所有「匹配但未绑定」的设备已经调过 probe 了。这解释了为什么有时 insmod 一敲下去，printk("match OK!\n") 立刻就打出来了，而你的 module_init 还没返回。

第三步是给「驱动后注册」的情况补课。适配器往往早就存在了，需要通知每个 address_list 里登记的地址去探测。

匹配靠什么。i2c_bus_type 的 match 是 i2c_device_match，走两条路：

路径 比什么 用在
of_driver_match_device() 设备节点 compatible ↔ 驱动 of_match_table[].compatible 设备树平台
i2c_match_id() client->name ↔ i2c_driver.id_table[].name 所有平台，含无设备树的老板

两条路是「或」关系，任一条命中就绑定。 设备树平台下主路是 compatible，但 id_table 依然要留，因为 probe(struct i2c_client *client, const struct i2c_device_id *id) 的第二个参数就是从 id_table 里取出来的。id_table 写空了，id 会是 NULL，很多驱动里 id->driver_data 会直接崩。

素材的排障问答里对这条有个很干脆的对照：

平台 匹配依据
Cortex-A8 driver 提供 id_table，与 client->name 匹配
Cortex-A9（含 Exynos4412） 走设备树，compatible 匹配

这个划分是简化说法。实际在 A9 上，i2c_match_id() 这条也在，只是设备树已经生成了正确的 client->name（等于 compatible 逗号后半段），两条路同时命中。

十四、probe 里怎么和芯片通信 #

probe 一进来，说明匹配成功、i2c_client 已经就位。你要做三件事：拿 client、装字符设备、把芯片配到能工作的状态。

c
struct mpu6050_device {
        struct cdev cdev;
        struct i2c_client *client;
};
struct mpu6050_device *mpu6050;

static int mpu6050_probe(struct i2c_client *client, const struct i2c_device_id *id)
{
        int ret;
        dev_t devno = MKDEV(MPU6050_MAJOR, MPU6050_MINOR);
        printk("match OK!\n");

        mpu6050 = kzalloc(sizeof(*mpu6050), GFP_KERNEL);
        if (mpu6050 == NULL) {
                return -ENOMEM;
        }

        mpu6050->client = client;                     // ① 存下 client

        ret = register_chrdev_region(devno, 1, "mpu6050");
        if (ret < 0) {
                printk("failed to register char device region!\n");
                goto err1;
        }

        cdev_init(&mpu6050->cdev, &mpu6050_fops);     // ② 装字符设备
        mpu6050->cdev.owner = THIS_MODULE;
        ret = cdev_add(&mpu6050->cdev, devno, 1);
        if (ret < 0) {
                printk("failed to add device\n");
                goto err2;
        }

        mpu6050_write_byte(client, PWR_MGMT_1, 0x00);   // ③ 配芯片
        mpu6050_write_byte(client, SMPLRT_DIV, 0x07);
        mpu6050_write_byte(client, CONFIG, 0x06);
        mpu6050_write_byte(client, GYRO_CONFIG, 0xF8);
        mpu6050_write_byte(client, ACCEL_CONFIG, 0x19);

        return 0;
err2:
        unregister_chrdev_region(devno, 1);
err1:
        kfree(mpu6050);
        return ret;
}

client 里有哪些东西可用，是你写 probe 时最需要知道的：

字段 内容 你在 probe 里怎么用
client->addr 7 位从地址，来自设备树 reg 填 i2c_msg.addr
client->adapter 所属适配器 i2c_transfer() 的第一个参数
client->name 设备名，来自 compatible 后半段 一般只打日志
client->irq 中断号，来自设备树 interrupts request_irq() 用
client->dev 设备模型里的 device dev_info()、devm_*() 用

第三块那五行写序列，每一行都有具体目的，不是随便凑的：

寄存器 地址 写入值 作用
PWR_MGMT_1 0x6B 0x00 退出睡眠，选内部 8 MHz 振荡器，器件开始工作
SMPLRT_DIV 0x19 0x07 采样率分频，典型值 0x07 对应 125 Hz
CONFIG 0x1A 0x06 低通滤波频率，典型值 0x06 对应 5 Hz
GYRO_CONFIG 0x1B 0xF8 陀螺仪自检位 + 量程。0xF8 的 bit[4:3] 是满量程选择，与注释「典型值 0x18」不同，见勘误
ACCEL_CONFIG 0x1C 0x19 加速度计量程与高通滤波。与注释「典型值 0x01」不同，见勘误

PWR_MGMT_1 = 0x00 必须是第一笔。芯片上电默认在睡眠态，寄存器还读得到，但转换不跑，数据寄存器一直是 0。你的 cat 出来全是 0x0000，第一反应是 I2C 没通，其实是芯片在睡。

后四条与素材注释的「典型值」不一致，我照代码原样写，并在文末勘误里列出差异。哪个是对的，需要拿 MPU6050 寄存器手册核对，本文不做判断，标「未验证」。

一个必须指出的设计问题：mpu6050_write_byte() 的返回值被完全忽略。五行里任何一行失败，probe 都照样 return 0，系统认为设备初始化成功。这在调试期很危险——总线断了你也不知道。第 3 节那五行应该写成：

c
ret = mpu6050_write_byte(client, PWR_MGMT_1, 0x00);
if (ret < 0) {
        dev_err(&client->dev, "PWR_MGMT_1 write failed\n");
        goto err3;
}

另外 struct mpu6050_device *mpu6050 是全局单指针，probe 里 kzalloc 覆盖、remove 里 kfree 置空。一块板一根总线一个 MPU6050 时能用，一旦同型号器件挂两路（比如两块板类比的场景），第二个 probe 会把第一个的指针冲掉，ioctl 全走错设备。正规写法是 i2c_set_clientdata(client, mpu6050)，在 ioctl 里用 i2c_get_clientdata(client) 取回；或者把 struct mpu6050_device * 塞进 file->private_data。Exynos4412 上 MPU6050 只有一个，素材这套能跑通，知道它只能撑到单器件就够了。

十五、完整的数据读写实例 #

设备侧的两个底层函数，一个读字节、一个写字节。全部 I2C 逻辑都收在这两个函数里，上面 ioctl 之类只是包装。

读一个字节：先写寄存器地址，再读数据。两个 i2c_msg，两次传输，中间不插 STOP（控制器会自动重发 START）。

c
static int mpu6050_read_byte(struct i2c_client *client, unsigned char reg)
{
        int ret;

        char txbuf[1] = { reg };
        char rxbuf[1];

        struct i2c_msg msg[2] = {
                { client->addr, 0,        1, txbuf },   /* 写：把寄存器地址送出去 */
                { client->addr, I2C_M_RD, 1, rxbuf }    /* 读：把数据收回来 */
        };

        ret = i2c_transfer(client->adapter, msg, ARRAY_SIZE(msg));
        if (ret < 0) {
                printk("ret = %d\n", ret);
                return ret;
        }

        return rxbuf[0];
}

写一个字节：寄存器地址和数据拼成一个 2 字节缓冲区，一个 i2c_msg 就够。

c
static int mpu6050_write_byte(struct i2c_client *client, unsigned char reg, unsigned char val)
{
        char txbuf[2] = { reg, val };

        struct i2c_msg msg[2] = {                /* 声明 2 个，实际只用 1 个 */
                { client->addr, 0, 2, txbuf },
        };

        i2c_transfer(client->adapter, msg, ARRAY_SIZE(msg));   /* 传了 2！ */

        return 0;
}

这段代码里有三个问题，逐个说清楚，因为它们直接决定你读出来的数据对不对。

问题一：ARRAY_SIZE(msg) 是 2，但只有一个 msg 被初始化。

struct i2c_msg msg[2] = { {...} }; 这种写法会把 msg[1] 的四个字段全部零初始化：addr = 0、flags = 0、len = 0、buf = NULL。然后 ARRAY_SIZE(msg) 得到 2，你把这两个都传给了 i2c_transfer()。

后果是：第二笔传输的从地址是 0，长度 0。地址 0 是广播地址，i2c_check_addr_validity() 会拦，但拦截发生在 i2c_new_device() 阶段，不在传输阶段；传输阶段 i2c_s3c_irq_nextbyte() 的 STATE_START 分支会尝试往 0x00 发地址，收不到 ACK，stop(-ENXIO)。也就是说每一次写寄存器，第二次 i2c_msg 都会失败。

MPU6050 写寄存器这条路上，第一笔已经写成功了（地址 + 寄存器 + 数据都推出去了），所以功能上看不出异常——这正是它一直没被发现的原因。

正确写法是数组只开一个，或者数传对的个数：

c
struct i2c_msg msg[1] = {
        { client->addr, 0, 2, txbuf },
};
i2c_transfer(client->adapter, msg, 1);

素材的定位里那句「有几个 i2c_msg 就有几个，i2c_msg->num 每个命令除了从设备之外，有几个 BYTE 就是几」——说的是 msg[i].len 该填字节数，跟 num 该填 msg 个数。这两件事被这段代码揉在一起了。

问题二：i2c_transfer() 的返回值没检查。

读函数检查了 ret < 0，写函数完全没看。失败时静默返回 0，上层以为成功。第五章讲 probe 时提过同一个问题，这里是第二次。

问题三：char 的符号性。

txbuf / rxbuf 是 char 而不是 unsigned char。读过 0x80 以上的数据后，rxbuf[0] 是负数，return rxbuf[0] 会把一个 -128 ~ -1 的负值返回出去。mpu6050_read_byte() 的返回类型是 int，调用处 data.accel.x = mpu6050_read_byte(...) 装进 unsigned short 时靠符号扩展会填出 0xFF80 这类值。

素材这段代码里 ioctl 的拼法还另外有一坑：

c
data.accel.x = mpu6050_read_byte(client, ACCEL_XOUT_L);        /* 低字节 */
data.accel.x |= mpu6050_read_byte(client, ACCEL_XOUT_H) << 8;  /* 高字节 */

先读 L 再读 H。MPU6050 的 ACCEL_XOUT_H 地址是 0x3B，ACCEL_XOUT_L 是 0x3C，两个字节是一起 latch 的，先后顺序不影响正确性。但如果读的过程中芯片更新了一帧，L 和 H 就来自不同帧，结果是跳变的脏数据。芯片手册建议先读 H 再读 L 以启用内部锁存（此说法需要对照寄存器手册确认，本文标「未验证」）。更稳的做法是一次读 6 个字节，用一个 i2c_msg 连续读：

c
static int mpu6050_read_bytes(struct i2c_client *client, unsigned char reg,
                              unsigned char *buf, int len)
{
        struct i2c_msg msg[2] = {
                { client->addr, 0,        1,   &reg },
                { client->addr, I2C_M_RD, len, buf  }
        };

        return i2c_transfer(client->adapter, msg, 2);
}

一次传输 6 字节，比 6 次单字节读快得多，也不会跨帧撕裂。这个函数没在素材里出现，是我按同一套接口补的，接口与语义与素材一致。

上层 ioctl 完整版：

c
static long mpu6050_ioctl(struct file *file, unsigned int cmd, unsigned long arg)
{
        union mpu6050_data data;
        struct i2c_client *client = mpu6050->client;

        switch (cmd) {
        case GET_ACCEL:
                data.accel.x = mpu6050_read_byte(client, ACCEL_XOUT_L);
                data.accel.x |= mpu6050_read_byte(client, ACCEL_XOUT_H) << 8;

                data.accel.y = mpu6050_read_byte(client, ACCEL_YOUT_L);
                data.accel.y |= mpu6050_read_byte(client, ACCEL_YOUT_H) << 8;

                data.accel.z = mpu6050_read_byte(client, ACCEL_ZOUT_L);
                data.accel.z |= mpu6050_read_byte(client, ACCEL_ZOUT_H) << 8;
                break;

        case GET_GYRO:
                data.gyro.x = mpu6050_read_byte(client, GYRO_XOUT_L);
                data.gyro.x |= mpu6050_read_byte(client, GYRO_XOUT_H) << 8;

                data.gyro.y = mpu6050_read_byte(client, GYRO_YOUT_L);
                data.gyro.y |= mpu6050_read_byte(client, GYRO_YOUT_H) << 8;

                data.gyro.z = mpu6050_read_byte(client, GYRO_ZOUT_L);
                data.gyro.z |= mpu6050_read_byte(client, GYRO_ZOUT_H) << 8;
                break;

        case GET_TEMP:
                data.temp = mpu6050_read_byte(client, TEMP_OUT_L);
                data.temp |= mpu6050_read_byte(client, TEMP_OUT_H) << 8;
                break;

        default:
                printk("invalid argument\n");
                return -EINVAL;
        }

        if (copy_to_user((void *)arg, &data, sizeof(data)))
                return -EFAULT;

        return sizeof(data);
}

十六、调试过程：从不通到通 #

这一章按「症状 → 查什么 → 结论」排。素材里这些断点都是实际踩过的，顺序就是你敲命令的顺序。

第 0 步：先确认适配器活着。

bash
ls /sys/bus/i2c/devices/
i2cdetect -l

i2cdetect -l 应该列出 i2c-5。没有，问题在适配器侧，不在你的驱动侧。回第七章看 probe 的八步，重点查三处：

bash
dmesg | grep -i "s3c-i2c\|i2c.*adapter\|clock source"

正常会看到：

text
s3c-i2c 138b0000.i2c: slave address 0x00
s3c-i2c 138b0000.i2c: bus frequency set to 20 KHz
s3c-i2c 138b0000.i2c: 138b0000.i2c: S3C I2C adapter

这三行分别对应 s3c24xx_i2c_init() 里写 IICADD、clockrate() 算分频、probe 末尾打 adapter 名。缺哪行就是哪步挂了。如果看到 cannot get clock，是 devm_clk_get() 失败，设备树里 clock-names = "i2c" 或 clocks 属性写错。看到 cannot meet bus frequency required，是分频算不出来，频率定太低，见第十二章。

第 1 步：从设备有没有被识别。

bash
ls /sys/bus/i2c/devices/i2c-5/
i2cdetect -y -r 5

目录里应该出现 5-0068 这种名字。没有，问题在 i2c_board_info 的生成，查三处：

  • 设备树节点写在哪。必须写在 i2c@138b0000 的花括号里面，是它的子节点。写在外层，of_i2c_register_devices() 遍历子节点时看不见它。
  • status 是不是 "okay"。控制器节点和从设备节点都要 okay，写成 "disabled" 就整段跳过。
  • reg 是不是 7 位地址。写 0xD0 会被当成 8 位值，i2c_check_addr_validity() 判 0xD0 > 0x77，报 Invalid 7-bit I2C address 0xd0。

i2cdetect 的地址表里 68 位置如果显示 68（而不是 --），说明总线能通到这个地址；显示 UU 表示该地址已被内核驱动占用，也是好事。

第 2 步：驱动有没有绑上。

bash
ls /sys/bus/i2c/devices/5-0068/
ls -l /sys/bus/i2c/devices/5-0068/driver

driver 这个符号链接存在，说明已经绑定；不存在就是没匹配。没匹配时看 compatible 与 of_match_table 是否逐字相同——素材那套是 invense,mpu6050（少个 ns），你两边写一致就行，但千万别一边抄素材一边抄上游。

也可以强制绑一下，看驱动本身有没有问题：

bash
echo 5-0068 > /sys/bus/i2c/drivers/mpu6050/bind

第 3 步：probe 被调用了没有。

bash
dmesg | grep "match OK"

match OK! 是素材 probe 第一行那个 printk。它打出来了，说明协议栈一路走通到了你的 probe。打不出来但第 2 步的 driver 链接在，说明绑定发生在更早的时间点，dmesg 缓冲区被冲掉了，去 /var/log/ 或把日志级别提上去。

素材原来设了一个「打断点用」的观察点，就是 Probe 里的 printk("match OK!\n")。这类 printk 在开发期一直留着很实用，比 dev_dbg 稳，不受 dynamic_debug 开关影响。

第 4 步：传输能不能成。

最简单的一笔传输是读 WHO_AM_I，期望值 0x68。这个数字和器件地址是巧合，两个都等于 0x68，做健全性检查很适合：

c
int who = mpu6050_read_byte(client, WHO_AM_I);
printk("WHO_AM_I = 0x%02x\n", who);

三种结果三种结论：

读回 说明 下一步
0x68 通了 继续读加速度
0xff 总线上没人拉低，SDA 悬空 查 SCL 和 SDA 的连线、上拉电阻、引脚复用
其他值 通了但读到脏数据 查速率、查 sda_delay、检查是否读到了别的器件的地址

第 5 步：i2c_transfer() 返回值是多少。

mpu6050_read_byte() 里有 printk("ret = %d\n", ret)。这个负数直接给答案：

返回值 含义 常见原因
2 成功，两个 i2c_msg 都执行了 正常
-ENXIO（-6） 地址发了没人 ACK 地址错、器件没上电、引脚复用没配、上拉缺失
-ECONNREFUSED（-111） 数据字节被 NAK 寄存器地址错、器件在睡眠态不接受写、写序列违规
-EREMOTEIO（-121） 抢总线失败，重试 2 次都不行 上一次传输没收尾，IICSTAT 的 START 位没清
-EINVAL 参数非法，或换方向的 I2C_M_NOSTART msg 结构填错
负数但不认识 时钟使能失败 probe 后时钟被关

-EREMOTEIO 这条尤其值得记。它出现的原因是 s3c24xx_i2c_disable_bus() 没跑到——比如上一次传输超时退出，doxfer() 里 wait_event_timeout 返回 0，代码走到 s3c24xx_i2c_wait_idle() 之前就 goto out 了（超时情况下实际上是继续往下的，取决于具体分支），总线没释放。再来一次 set_master() 就抢不到。处理方法：rmmod 再 insmod，或者复位板子。

第 6 步：数据对不对。

读回来的加速度值应该随板子姿态变化。一直是 0x0000，查 PWR_MGMT_1 有没有写成 0x00。数值在跳但明显不对，查量程配置——GYRO_CONFIG 和 ACCEL_CONFIG 里的满量程位决定了原始值到物理量的换算系数，配成 ±2g 和 ±16g，同一个加速度下的原始值差 8 倍。

一个用示波器才能看出来的问题。

如果第 5 步返回 2（传输成功），但第 6 步数据不对，逻辑分析仪或者双通道示波器是唯一能定案的工具。接 SDA 和 SCL，触发在 SDA 下降沿（START），看这几项：

看什么 正常 异常说明
START SCL 高时 SDA 由高变低 START 没有，IICSTAT 的 START 位没写进去
地址字节 8 位，最后一位是读写位 移位错了，见第十章第 8 步
ACK 第 9 个时钟 SDA 被从机拉低 没拉低就是 -ENXIO
数据位 SCL 低电平期间翻转 SCL 高电平期间翻转，sda_delay 太小
STOP SCL 高时 SDA 由低变高 没有 STOP，总线一直占用

SCL 频率也在这时量。量出来跟你算的分频值差很多，说明 IICCON[3:0] 写的时候被别的位带坏了——回第十章看 message_start() 里那个 iiccon 先读后写的操作。

十七、排障问答：常见问题与答案 #

以下问答保留原始素材的问法，答案按本章前面章节的代码补全。

Q1：I2C 总线上的设备是怎么描述的？

用 struct i2c_client 描述，它的核心是内嵌的一个 struct device dev：

c
struct i2c_client {
        unsigned short flags;
        unsigned short addr;          /* 7 位地址存在低 7 位 */
        char name[I2C_NAME_SIZE];
        struct i2c_adapter *adapter;  /* 挂在哪根总线上 */
        struct device dev;            /* 设备模型节点 */
        int init_irq;
        int irq;
        struct list_head detected;
};

i2c_client 由 i2c_new_device() 生成，数据来自 i2c_board_info（设备树平台由 of_i2c_get_board_info() 填充）。

Q2：I2C 总线上的驱动是怎么描述的？

用 struct i2c_driver，核心是内嵌的 struct device_driver driver：

c
struct i2c_driver {
        int (*probe)(struct i2c_client *, const struct i2c_device_id *);
        int (*remove)(struct i2c_client *);
        void (*shutdown)(struct i2c_client *);
        struct device_driver driver;
        const struct i2c_device_id *id_table;
        int (*detect)(struct i2c_client *, struct i2c_board_info *);
        const unsigned short *address_list;
        struct list_head clients;
};

attach_adapter 这个老回调在 3.14 里已经标了 __deprecated，别用。

Q3：设备和驱动是怎么匹配的？

i2c_bus_type 的 .match 指向 i2c_device_match()，两条路「或」：

  • Cortex-A8 这类没有设备树的平台：驱动提供 id_table，与 client->name 比对。
  • Cortex-A9（Exynos4412）这类有设备树的平台：比对设备树 compatible 与驱动的 of_match_table，同时 id_table 那条也仍然生效。

i2c_bus_type 的定义：

c
struct bus_type i2c_bus_type = {
        .name     = "i2c",
        .match    = i2c_device_match,   /* 匹配规则与 platform 总线设备树节点匹配规则一致 */
        .probe    = i2c_device_probe,
        .remove   = i2c_device_remove,
        .shutdown = i2c_device_shutdown,
        .pm       = &i2c_device_pm_ops,
};

Q4：怎么告诉系统我们的从设备信息？

两种方式，看内核有没有设备树：

  • Cortex-A8：在板级文件里写一张 struct i2c_board_info 数组，比如 arch/arm/mach-s5pc100/mach-smdkc100.c，然后 i2c_register_board_info() 注册。
  • Cortex-A9（Exynos4412）：写设备树节点，内核解析时由 of_i2c_get_board_info() 转换成 i2c_board_info。素材原文说「通过设备树，内核转换」，就是这个意思。

Q5：系统怎么找到从设备信息，找到之后做了什么？

Cortex-A8 这条路是一条完整的链：

text
i2c_add_numbered_adapter()
  |
  +--> i2c_register_adapter(adap)
         |
         +--> i2c_scan_static_board_info()   /* 扫 __i2c_board_list */
                |
                +--> i2c_new_device()
                       |
                       +--> 1. 产生 i2c_client（填入从设备信息）
                            2. 注册 client->dev

设备树那条路把 i2c_scan_static_board_info() 换成 of_i2c_register_devices()，终点同样是 i2c_new_device()。

Q6：驱动怎么拿到从设备的信息？

i2c_driver 的 probe 被调用时，i2c_client 指针直接传进来，设备信息全在里面：

c
int xxx_probe(struct i2c_client *client, const struct i2c_device_id *id)
{
        /* client->addr / client->adapter / client->irq / client->name 都可用 */
}

Q7：数据怎么接收？

靠中断。适配器驱动发完地址或写下一个字节后，从机动作完成会拉中断，s3c24xx_i2c_irq() → i2c_s3c_irq_nextbyte() 把字节从 IICDS 读出来塞进 msg->buf[]。整个接收过程都是中断推的，只有最开始那一笔是前台代码发的。

Q8：数据怎么发送？

走 adap->algo->master_xfer：

c
static const struct i2c_algorithm s3c24xx_i2c_algorithm = {
        .master_xfer            = s3c24xx_i2c_xfer,
        .functionality          = s3c24xx_i2c_func,
};

你在设备驱动里不直接调它，调 i2c_transfer()，核心层转一手。

Q9：i2c_msg 到底怎么发送出去的？

i2c_transfer() 只发第一个 msg 的第一个字节——确切说是从地址字节，然后调 wait_event_timeout() 进入阻塞。从设备回 ACK 或回数据都会触发中断处理函数，中断里把剩下的 data 和 msg 全部推完。推完之后调 s3c24xx_i2c_stop() → s3c24xx_i2c_master_complete() → wake_up()，唤醒阻塞的线程，一次 i2c_msg 传输结束。

Q10：i2c_msg 的数量怎么算？

一个 i2c_msg 对应一次 START 到 STOP 之间的一段（或者说，对应一次「地址 + 方向 + 一段数据」）。一条完整的 I2C 命令有几个这样的段，就有几个 i2c_msg。单个 i2c_msg 的 len 是这个段里除了从设备地址之外的字节数。

以 MPU6050 为例：

操作 i2c_msg 个数 各 msg 的 len
写一个寄存器 1 2（寄存器地址 + 数据）
读一个寄存器 2 1（寄存器地址）+ 1（数据）
连续读 6 字节 2 1 + 6

Q11：i2c_adapter 是怎么注册加载的？

i2c-s3c2410.c 里，probe 设置 i2c->adap.algo = &s3c24xx_i2c_algorithm;，注册中断：

c
ret = devm_request_irq(&pdev->dev, i2c->irq, s3c24xx_i2c_irq, 0,
                dev_name(&pdev->dev), i2c);

最后 i2c_add_numbered_adapter(&i2c->adap) 完成注册。

Q12：i2c_client 到底什么时候生成的？

在 i2c_add_numbered_adapter() 里。具体是在 i2c_register_adapter() 中，扫静态链表（i2c_scan_static_board_info()）或扫设备树（of_i2c_register_devices()），再调 i2c_new_device()。关键结论：i2c_client 生成于适配器注册的那一刻，不是模块加载时。所以驱动模块先 insmod、适配器后来才出现，设备照样能生成，只是 probe 会晚一点。

Q13：3.14 内核的 adapter 驱动比起 s3c2410 那套有什么不同？

大部分兼容，不一样的地方在 i2c_client 的生成方式：老平台靠 i2c_register_board_info() 静态声明，3.14 之后（Exynos4412 这类有设备树的）靠设备树节点生成。

Q14：从设备地址怎么确定？

看原理图上 AD0 引脚接哪：接 GND 是 0x68，接 VCC 是 0x69。WHO_AM_I 寄存器（地址 0x75）的默认内容也是 0x68，可以拿来交叉验证，但这两个值相等纯属巧合，别混。

Q15：设备树节点写成什么样？

MPU6050 挂 I2C5，寄存器基址 0x138b0000，中断接 EIF27（gpx3 的第 3 号），地址 0x68：

dts
i2c@138b0000 {
        #address-cells = <1>;
        #size-cells = <0>;

        samsung,i2c-sda-delay = <100>;
        samsung,i2c-max-bus-freq = <20000>;
        pinctrl-0 = <&i2c5_bus>;
        pinctrl-names = "default";
        status = "okay";

        mpu6050-3-asix@68 {
                compatible = "invense,mpu6050";   /* 缺 ns，与驱动端保持一致 */
                reg = <0x68>;
                interrupt-parent = <&gpx3>;
                interrupts = <3 2>;
        };
};

几个属性逐个对：

属性 值 作用
reg <0x138b0000> 由父节点名体现，reg 用 <0x100> 一类窗口大小 控制器寄存器物理地址
#address-cells / #size-cells <1> / <0> 子节点的 reg 只有地址，无长度
samsung,i2c-sda-delay <100> SDA 边沿延时，单位 ns
samsung,i2c-max-bus-freq <20000> 目标 SCL 频率，单位 Hz
pinctrl-0 <&i2c5_bus> 引脚复用配置
pinctrl-names "default" 对应 devm_pinctrl_get_select_default()
status "okay" 使能该节点
子节点 mpu6050-3-asix@68 节点名后缀 @68 与 reg 一致 从设备
compatible "invense,mpu6050" 与驱动 of_match_table 匹配
reg <0x68> 7 位从地址
interrupt-parent <&gpx3> 中断所在引脚组
interrupts <3 2> gpx3 第 3 号，类型 2

interrupts = <3 2> 这个组合在素材两个版本里写法不同：一版是 <3 2>，另一版是 <32>。<32> 是把「引脚号 + 触发类型」压成了单个十进制 32，语义完全不同。哪个对要看 gpx3 节点在 SoC dtsi 里定义的 #interrupt-cells 是几个，素材没给，本文标「未验证」。素材原文另有一处写 interrupt_parent=<&gpx3>; interrupts=<3 2>;，用的是单下划线 interrupt_parent，设备树标准属性是双下划线 interrupt-parent，单下划线版本内核不认，这一处已修正。
