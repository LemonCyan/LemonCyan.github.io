I2C 子系统是 Linux 里最容易「用错」的框架之一：i2c_transfer() 一行就能把数据发出去，背后却是 core、adapter、client、driver 四个角色加一套总线匹配机制。这篇把它拆开，讲清楚每个角色归谁写、数据结构长什么样、注册和匹配各走哪条路、一次传输从驱动层到寄存器到底经过几个函数。

划界：讲什么，不讲什么 #

本篇只讲框架和结构，不深挖任意一侧的驱动实现。

你想解决的问题 去哪一篇

一、I2C 驱动框架的四个角色 #

先给结论：Linux 的 I2C 子系统拆成四个角色，各管一段，边界比 SPI、USB 都清楚。

角色 数据结构 抽象的是谁 谁负责写
core（核心层） 无独立结构，i2c-core-*.c 一组文件 内核公共逻辑 内核，不用碰
adapter（适配器） struct i2c_adapter SoC 里的一个 I2C 控制器 SoC 厂商写在 drivers/i2c/busses/
algorithm（算法） struct i2c_algorithm 控制器产生波形的方法 同上，挂到 adapter->algo
client（从设备） struct i2c_client 挂在总线上的一个芯片 由 core 实例化，也可以用户态创建
driver（设备驱动） struct i2c_driver 一套针对某型号芯片的驱动逻辑 驱动工程师

client 和 driver 是配对的：client 描述「板上装着什么」，driver 描述「这类芯片怎么操作」。adapter 和 algorithm 也是配对的：adapter 描述「哪条总线」，algorithm 描述「怎么在这条总线上发波形」。

用户态还会碰到两个附赠角色：i2c-dev 给每个 adapter 建一个 /dev/i2c-%d 字符设备，让你不解内核也能读写总线；i2c-mux 在一个 adapter 后面挂多路复用器（如 PCA954x），再分出若干虚拟总线。

两条关系最容易记错：i2c_driver 对 i2c_client 是一对多，一个驱动同时服务同型号的多个实例；i2c_adapter 对 i2c_client 也是一对多，adapter 内部维护链表把挂在它下面的 client 串起来。两条物理线接上的芯片都算 I2C 设备，一个 SoC 里可以有好几个控制器，也就是好几个 adapter。

二、三层结构：core、adapter、client/driver #

「四层划分」和「三部分划分」说的是同一套东西，只是切法不同。老文档里常写的四层：

层 内容 对应代码
第一层 adapter 硬件驱动，探测/初始化控制器，申请 IO 和中断，处理 I2C 中断 drivers/i2c/busses/i2c-*.c
第二层 adapter 的 algorithm，用 xxx_xfer() 填 master_xfer 再赋给 adapter->algo 同上，同一文件里
第三层 设备驱动侧 i2c_driver 接口实现 drivers/i2c/chips/ 或各子系统目录
第四层 具体设备的 write()/read()/ioctl()，填 file_operations 注册字符设备 同上

第一层加第二层叫 I2C 总线驱动（bus），第三层加第四层叫 I2C 设备驱动（device driver）。按 drivers/i2c/ 目录的实际组织，分成三部分更贴合代码：

部分 职责 文件
I2C core 注册/注销 API、通信封装、探测框架 i2c-core-base.c、i2c-core-smbus.c、i2c-core-of.c
I2C 总线驱动 i2c_adapter + i2c_algorithm，控制控制器出波形 drivers/i2c/busses/、drivers/i2c/algos/
I2C 设备驱动 i2c_driver + i2c_client drivers/i2c/chips/ 及各驱动目录

目录下有 algos/、busses/、chips/、muxes/，加上 i2c-core*.c 和 i2c-dev.c。busses 这拼写双 s 一路沿用，别照着「buses」去找。老教程说的三件套在 4.x 之后已经拆散：core 拆成 i2c-core-base.c、i2c-core-smbus.c、i2c-core-acpi.c、i2c-core-of.c、i2c-core-slave.c 几块，5.x 源码里找不到单个 i2c-core.c。

你要动手的地方只有两处：写 controller 就填 i2c_adapter + i2c_algorithm；写芯片驱动就填 i2c_driver，在 probe() 里用 i2c_transfer() 收发。bus 本身不用加，硬件相关的部分芯片厂写好了，早年三星 s3c2440 的控制器驱动就是 drivers/i2c/busses/i2c-s3c2410.c，这个文件到 5.x 还在。

三、为什么要有 core 这一层 #

假如没有 core：每个芯片驱动都要自己去拿控制器句柄、自己加锁、自己处理重试超时、自己解析设备树、自己算从设备地址。N 个芯片 × M 个控制器 = N×M 份重复代码。core 层把这几个维度收拢了：

core 提供的 谁来用 省掉了什么
i2c_add_adapter() / i2c_del_adapter() adapter 驱动 总线编号分配、/sys 节点创建、client 实例化
i2c_register_driver() / i2c_del_driver() 设备驱动 挂到 i2c_bus_type、触发匹配和 probe
i2c_transfer() / __i2c_transfer() 设备驱动 加锁、超时、重试、trace
i2c_smbus_* 系列 设备驱动 SMBus 协议到 I2C 消息的翻译
i2c_new_client_device() 设备驱动、设备树 构造 i2c_client、地址合法性检查、sysfs 命名
探测框架 i2c_detect() 老式驱动 遍历地址表、发 START 试探

由此「控制器差异」和「设备差异」这两个维度彻底解耦：设备驱动只面对 i2c_adapter，不关心后面是 S3C 还是 STM32 控制器；控制器驱动只面对 i2c_algorithm，不关心上面挂的是 EEPROM 还是 OLED。

i2c_master_send() 是这种解耦的直接证据——它只把地址、数据、长度填进 i2c_msg 再调 i2c_transfer()，完全不碰寄存器，换平台这行代码不用动：

c
int i2c_master_send(const struct i2c_client *client, const char *buf, int count)
{
        struct i2c_adapter *adap = client->adapter;
        struct i2c_msg msg;
        int ret;

        msg.addr  = client->addr;
        msg.flags = client->flags & I2C_M_TEN;
        msg.len   = count;
        msg.buf   = (char *)buf;

        ret = i2c_transfer(adap, &msg, 1);
        return (ret == 1) ? count : ret;
}

四、i2c_adapter：一个控制器的抽象 #

struct i2c_adapter 定义在 include/linux/i2c.h。5.2.8 版本全字段：

c
struct i2c_adapter {
        struct module *owner;
        unsigned int class;               /* classes to allow probing for */
        const struct i2c_algorithm *algo; /* the algorithm to access the bus */
        void *algo_data;

        /* data fields that are valid for all devices   */
        const struct i2c_lock_operations *lock_ops;
        struct rt_mutex bus_lock;
        struct rt_mutex mux_lock;

        int timeout;                    /* in jiffies */
        int retries;
        struct device dev;              /* the adapter device */
        unsigned long locked_flags;     /* owned by the I2C core */
#define I2C_ALF_IS_SUSPENDED            0
#define I2C_ALF_SUSPEND_REPORTED        1

        int nr;
        char name[48];
        struct completion dev_released;

        struct mutex userspace_clients_lock;
        struct list_head userspace_clients;

        struct i2c_bus_recovery_info *bus_recovery_info;
        const struct i2c_adapter_quirks *quirks;

        struct irq_domain *host_notify_domain;
};

逐字段过一遍：

字段 含义 你要不要填
owner 模块引用计数，写 THIS_MODULE 要
class 允许自动探测的设备类，I2C_CLASS_* 位图 自动探测才填
algo 指向 i2c_algorithm，核心中的核心 必填
algo_data 私有数据，控制器驱动常用它回拿自己的 struct xxx_i2c * 建议填
lock_ops 总线加锁/解锁操作集 core 补默认值
bus_lock / mux_lock 总线互斥锁 / mux 场景的锁 由 core 初始化
timeout 一次消息发送的最长时间，单位 jiffies 不填则 core 设 HZ
retries 失败重试次数上限 可选
dev 设备模型实体，把 adapter 当 device 子类用 由 core 初始化
locked_flags 挂起状态标志位 由 core 管理
nr 总线编号，决定 /dev/i2c-N 和 i2c-N 目录 由 core 分配
name 适配器名字，48 字节 必填
dev_released 注销同步用的完成量 由 core 管理
userspace_clients_lock / userspace_clients 用户态通过 sysfs 新建的 client 链表及其锁 由 core 管理
bus_recovery_info / quirks / host_notify_domain 总线恢复信息 / 硬件限制 / Host Notify 的 irq domain 可选，core 管理

版本差异要逐个标清：

  • lock_ops 是 5.x 才有的（4.x 后期引入，确切版本未验证）。3.x 的 i2c_adapter 里只有 struct mutex bus_lock、struct mutex clist_lock，没有 lock_ops。老代码那种写法在 3.x 是对的，直接抄进 5.x 编译不过。
  • bus_lock 从 struct mutex 变成了 struct rt_mutex，还要写 base 级加锁的场景得跟着改。
  • 3.x 的 id、client_register / client_unregister、level 在 5.x 全部删除：id 改由 class 和运行时判断接管，client 注册统一交给设备模型。

class 常见取值：I2C_CLASS_HWMON（硬件监控，温度电压风扇）、I2C_CLASS_DDC（数字显示通道，显示器 EDID 那条线）、I2C_CLASS_SPD（内存 SPD）、I2C_CLASS_DEPRECATED（已废弃，设了它等于明说不支持 i2c_detect() 自动探测）。

adapter->dev 的初始化是理解 sysfs 的关键。四个赋值决定节点位置：dev.bus = &i2c_bus_type、dev.type = &i2c_adapter_type、dev.parent = &pdev->dev、dev_set_name(&adap->dev, "i2c-%d", adap->nr)。注册完成后看到这棵树：

text
/sys/devices/platform/s3c2440-i2c.0/i2c-0/          <- adapter，kobj.name = "i2c-%d"
/sys/devices/platform/s3c2440-i2c.0/i2c-0/0-0050/   <- client，kobj.name = "%d-%04x"
/sys/bus/i2c/devices/i2c-0                          -> 指向前者
/sys/bus/i2c/drivers/<driver-name>/                 <- 驱动目录
/sys/class/i2c-adapter/i2c-0                        -> 指向前者（CONFIG_I2C_COMPAT）
/sys/class/i2c-dev/i2c-0                            <- 字符设备类
/dev/i2c-0                                          <- 主设备号 89，次设备号 = adapter->nr

i2c_adapter_type 挂的是 adapter 专有属性文件，这就是你能在 sysfs 读到 name、new_device、delete_device 的原因。/sys/devices/platform/s3c2440-i2c.0 自己的 subsystem 指向 /sys/bus/platform，而它下面的 i2c-0 指向 /sys/bus/i2c，父子不同总线是正常的。

五、i2c_algorithm：传输算法的接口 #

i2c_algorithm 是 adapter 的「能力实现」，定义在 include/linux/i2c.h：

c
struct i2c_algorithm {
        int (*master_xfer)(struct i2c_adapter *adap, struct i2c_msg *msgs,
                           int num);
        int (*master_xfer_atomic)(struct i2c_adapter *adap,
                                   struct i2c_msg *msgs, int num);
        int (*smbus_xfer)(struct i2c_adapter *adap, u16 addr,
                          unsigned short flags, char read_write,
                          u8 command, int size, union i2c_smbus_data *data);
        int (*smbus_xfer_atomic)(struct i2c_adapter *adap, u16 addr,
                                 unsigned short flags, char read_write,
                                 u8 command, int size, union i2c_smbus_data *data);

        /* To determine what the adapter supports */
        u32 (*functionality)(struct i2c_adapter *adap);

#if IS_ENABLED(CONFIG_I2C_SLAVE)
        int (*reg_slave)(struct i2c_client *client);
        int (*unreg_slave)(struct i2c_client *client);
#endif
};
成员 作用 返回值约定
master_xfer 发一组 I2C 消息，产生 START/STOP/ACK 成功处理的消息条数，出错返回负 errno
master_xfer_atomic 同 master_xfer，但只用原子上下文，给关机前访问 PMIC 用 同上
smbus_xfer 直接走 SMBus 协议 0 成功，负 errno 失败
smbus_xfer_atomic 原子上下文版 SMBus 同上
functionality 返回 I2C_FUNC_* 能力位图 位图
reg_slave / unreg_slave 把本控制器切成从机模式 0 或负 errno

master_xfer 和 smbus_xfer 的关系只有一句话：两个实现其中一个就够，core 会自动兜底。只实现 master_xfer 时，SMBus 调用由 i2c_smbus_xfer_emulated() 翻译成若干条 I2C 消息再走 master_xfer，绝大多数控制器走这条路；只实现 smbus_xfer 时，i2c_transfer() 直接返回 -EOPNOTSUPP，因为它只认 master_xfer——老资料里「smbus_xfer 一般都赋值为 NULL」说的就是这个现实；两个都实现时，SMBus 调用优先走 smbus_xfer。

functionality 的返回位图决定上层还能玩什么花活：I2C_FUNC_I2C（传统 I2C 传输）、I2C_FUNC_10BIT_ADDR（10 位地址）、I2C_FUNC_PROTOCOL_MANGLING（非标准协议行为）、I2C_FUNC_NOSTART（不发 START 的接续传输）、I2C_FUNC_SMBUS_*（各类 SMBus 协议支持情况）。设备驱动拿 i2c_check_functionality(adap, I2C_FUNC_SMBUS_BYTE_DATA) 先查再调，查不过就别硬来。

master_xfer_atomic、smbus_xfer_atomic 是 4.x 后期才加的（首次引入版本未验证），3.x 的 i2c_algorithm 只有三个成员：master_xfer、smbus_xfer、functionality。

S3C2440 的实际配置就两个成员，smbus_xfer 压根没实现，SMBus 走模拟路径：

c
static const struct i2c_algorithm s3c24xx_i2c_algorithm = {
        .master_xfer            = s3c24xx_i2c_xfer,
        .functionality          = s3c24xx_i2c_func,
};

所以 S3C 平台上 i2c_smbus_* 能跑，只是底层被翻译成 I2C 消息。

六、i2c_client：一个挂载在总线上的设备 #

struct i2c_client 描述「总线上真实存在的一颗芯片」，定义在 include/linux/i2c.h，5.2.8 全字段：

c
struct i2c_client {
        unsigned short flags;           /* div., see below              */
        unsigned short addr;            /* chip address - NOTE: 7bit    */
                                        /* addresses are stored in the  */
                                        /* _LOWER_ 7 bits               */
        char name[I2C_NAME_SIZE];
        struct i2c_adapter *adapter;    /* the adapter we sit on        */
        struct device dev;              /* the device structure         */
        int init_irq;                   /* irq set at initialization    */
        int irq;                        /* irq issued by device         */
        struct list_head detected;
#if IS_ENABLED(CONFIG_I2C_SLAVE)
        i2c_slave_cb_t slave_cb;        /* callback for slave mode      */
#endif
};
字段 含义
flags I2C_CLIENT_* 位图：10 位地址、PEC、从机模式、host-notify 等
addr 从设备地址，7 位地址存在低 7 位，不含读写位
name 芯片名，I2C_NAME_SIZE 为 20 字节，匹配时与 i2c_device_id.name 比
adapter / dev 所属控制器 / 设备模型实体（parent = &adapter->dev，bus = &i2c_bus_type）
init_irq / irq 初始化时记录的 IRQ（来自 i2c_board_info.irq 或 resources）/ 实际使用的 IRQ
detected 挂到 i2c_driver.clients 或 core 的 userspace_devices 链表用
slave_cb 从机模式回调，CONFIG_I2C_SLAVE 打开才有

flags 常见取值：I2C_CLIENT_TEN（10 位芯片地址）、I2C_CLIENT_PEC（SMBus 包错误校验）、I2C_CLIENT_SLAVE（本设备被配置为从机）、I2C_CLIENT_WAKE（需要它唤醒系统）、I2C_CLIENT_HOST_NOTIFY（支持 SMBus Host Notify）、I2C_CLIENT_SCCB（SCCB 兼容，摄像头那条线）。

老资料在这里有两处笔误要纠正：宏名写成 I2C_CLIENT_SLAVA、I2C_CLIENT_WAK，正确的是 I2C_CLIENT_SLAVE 和 I2C_CLIENT_WAKE；另外「addr 的低 8 位表示地址，第 7 位是 R/W 位，0 表示写、2 表示读」这整段都错了——addr 存的是 7 位地址不含读写位（AT24C08 就是 0x50），方向位在 flags 的 I2C_M_RD 里，取值只能是 0 或 1。

内核里对得上：i2c_new_client_device() 用 i2c_check_addr_validity(client->addr, client->flags) 校验，7 位上限 0x7f，10 位上限 0x3ff。client->dev 的名字由 i2c_dev_set_name() 定，优先级是 info->dev_name 指定了就用它，否则 %d-%04x（适配器编号 + 地址），所以 0 号总线上的 0x50 设备目录名是 0-0050。

detected 成员容易被忽略：从设备树和 i2c_board_info 来的 client 不挂这条链，只有 i2c_detect() 探测出来的 client 才挂到 driver->clients。

七、i2c_driver：设备驱动的注册 #

struct i2c_driver 描述「一套驱动逻辑」，5.2.8 全字段：

c
struct i2c_driver {
        unsigned int class;

        /* Standard driver model interfaces */
        int (*probe)(struct i2c_client *, const struct i2c_device_id *);
        int (*remove)(struct i2c_client *);

        /* New driver model interface to aid the seamless removal of the
         * current probe()'s, more commonly unused than used second parameter.
         */
        int (*probe_new)(struct i2c_client *);

        /* driver model interfaces that don't relate to enumeration  */
        void (*shutdown)(struct i2c_client *);

        void (*alert)(struct i2c_client *, enum i2c_alert_protocol protocol,
                      unsigned int data);

        int (*command)(struct i2c_client *client, unsigned int cmd, void *arg);

        struct device_driver driver;
        const struct i2c_device_id *id_table;

        /* Device detection callback for automatic device creation */
        int (*detect)(struct i2c_client *, struct i2c_board_info *);
        const unsigned short *address_list;
        struct list_head clients;

        bool disable_i2c_core_irq_mapping;
};
成员 作用
class 驱动想探测的设备类，与 adapter->class 位与匹配
probe 匹配成功后调用，所有资源注册、初始化都放这里
remove 设备移除或驱动卸载时调用，释放资源
probe_new 只收 i2c_client * 的 probe 新形态，probe 的第二参数没人用
shutdown 关机时静默设备
alert SMBus Alert 协议回调
command 类似 ioctl 的旁路命令通道，现代驱动基本不用
driver struct device_driver 基类，bus 必须是 i2c_bus_type
id_table 支持的设备 ID 表
detect 自动探测回调，探测到设备后至少要填 i2c_board_info.type
address_list 自动探测时挨个试的地址表，以 I2C_CLIENT_END 结尾
clients 本驱动通过探测创建出来的 client 链表
disable_i2c_core_irq_mapping 告诉 core 不要做 IRQ 映射

probe_new 的生命周期要注意：5.2.8 里它已经存在，但在 6.x 又被移除，统一回 probe。写代码时看清手上内核的版本（6.x 的移除未核对源码，未验证）。

老资料里这个结构体还被写成带 attach_adapter() / detach_adapter() / detach_client() 的形态，这是 2.6 时代的老 API，5.x 已经彻底删掉：

老成员 现状
attach_adapter 已删除，被 i2c_detect() + 设备模型匹配取代
detach_adapter 已删除
detach_client 已删除（3.x 就有 __deprecated 标记）
int id 已删除
suspend / resume 已删除，改由 dev_pm_ops 走 driver.pm
struct device_driver driver 保留（老资料拼成 devcie_driver 是抓取时断词）

老资料那句「要么实现上面 3 个，要么实现下面 5 个，不能同时定义」在 5.x 已无意义，上面的 3 个已经不存在了。

class 和 address_list 共同服务于自动探测，i2c_detect() 的判断顺序是：!driver->detect || !address_list 返回、adapter->class == I2C_CLASS_DEPRECATED 返回、!(adapter->class & driver->class) 返回。三条全过才继续——detect 和 address_list 缺一个探测就不工作，adapter 没置对应 class 位也不工作。

为什么要自动探测：一个 SoC 挂着多个控制器、一堆从设备，装机时不确定某颗芯片接在哪条总线上。给驱动一个地址表，注册 adapter 或 driver 时内核挨个发 START 试探，有 ACK 就当场实例化 client。代价是要在总线上产生真实波形，所以新代码一律推荐设备树或显式 i2c_new_client_device()。

八、i2c_board_info 与设备实例化 #

struct i2c_board_info 是「设备模板」，i2c_client 由它长出来：

c
struct i2c_board_info {
        char            type[I2C_NAME_SIZE];
        unsigned short  flags;
        unsigned short  addr;
        const char      *dev_name;
        void            *platform_data;
        struct device_node *of_node;
        struct fwnode_handle *fwnode;
        const struct property_entry *properties;
        const struct resource *resources;
        unsigned int    num_resources;
        int             irq;
};

字段继承关系（i2c_new_client_device() 里逐字段拷贝）：

i2c_board_info 去向
type client->name，最终与 i2c_device_id.name 比
addr client->addr
flags client->flags
platform_data client->dev.platform_data
of_node client->dev.of_node
fwnode client->dev.fwnode
irq client->init_irq 和 client->irq
properties device_add_properties() 挂到 dev 上
resources 用于从中找 IRQ（i2c_dev_irq_from_resources）
dev_name 覆盖默认的 %d-%04x 名字

写设备驱动时 type 和 addr 是必须想明白的两个：type 决定能不能匹配上驱动进 probe，addr 决定能不能对上硬件。

还有一层 struct i2c_devinfo，定义在 drivers/i2c/i2c-core.h，就三个字段：list 用于串链表、busnum 记控制器编号、board_info 内嵌模板。它是板级静态声明时代的产物，只在无设备树的内核里有存在感：定义 i2c_board_info 数组，用 i2c_register_board_info() 灌进全局链表 __i2c_board_list，注册 adapter 时再遍历这张表转成 i2c_client。

i2c_register_board_info() 的实现就是往链表尾部追，同时把 __i2c_first_dynamic_bus_num 推高：

c
int i2c_register_board_info(int busnum, struct i2c_board_info const *info,
                            unsigned len)
{
        int status;

        down_write(&__i2c_board_lock);

        /* dynamic bus numbers will be assigned after the last static one */
        if (busnum >= __i2c_first_dynamic_bus_num)
                __i2c_first_dynamic_bus_num = busnum + 1;

        for (status = 0; len; len--, info++) {
                struct i2c_devinfo *devinfo;

                devinfo = kzalloc(sizeof(*devinfo), GFP_KERNEL);
                if (!devinfo) {
                        status = -ENOMEM;
                        break;
                }
                devinfo->busnum = busnum;
                devinfo->board_info = *info;
                /* properties 和 resources 需要深拷贝，略 */
                list_add_tail(&devinfo->list, &__i2c_board_list);
        }

        up_write(&__i2c_board_lock);
        return status;
}

副作用值得记住：静态声明的总线号不能被动态分配占用，写大了会挤掉后面的动态编号。

转换发生在 i2c_scan_static_board_info()，由 i2c_register_adapter() 调用，逻辑就是遍历链表、busnum 对上当前 adapter 就造 client：

c
list_for_each_entry(devinfo, &__i2c_board_list, list) {
        if (devinfo->busnum == adapter->nr
                        && !i2c_new_device(adapter, &devinfo->board_info))
                dev_err(&adapter->dev, "Can't create device at 0x%02x\n",
                        devinfo->board_info.addr);
}

由此得到一个硬性时序约束：i2c_register_board_info() 必须在 i2c_add_adapter() 之前调用，否则扫不到，设备永远实例化不出来。

这套机制现在基本退场，设备树内核里的流程变成 of_i2c_register_devices() → of_i2c_get_board_info() → i2c_new_client_device()。5.2.8 里 i2c_new_device() 已只剩一层壳：ret = i2c_new_client_device(adap, info); return IS_ERR(ret) ? NULL : ret;。

i2c_new_client_device() 在 5.2 引入（未验证确切 commit），i2c_new_device() 当场降级成兼容包装：前者返回 ERR_PTR，后者把错误吞成 NULL。新代码用 i2c_new_client_device() + IS_ERR()；老代码的 if (!client) 切过去之后必须改成 if (IS_ERR(client))，否则 ERR_PTR(-ENOMEM) 被当成非空指针用下去，宕机。

i2c_new_client_device() 的关键步骤，顺序有讲究：

c
client = kzalloc(sizeof *client, GFP_KERNEL);
client->adapter = adap;
client->dev.platform_data = info->platform_data;
client->flags = info->flags;
client->addr  = info->addr;

client->init_irq = info->irq;
if (!client->init_irq)
        client->init_irq = i2c_dev_irq_from_resources(info->resources,
                                                 info->num_resources);
client->irq = client->init_irq;

strlcpy(client->name, info->type, sizeof(client->name));

status = i2c_check_addr_validity(client->addr, client->flags);
status = i2c_check_addr_busy(adap, i2c_encode_flags_to_addr(client));

client->dev.parent  = &client->adapter->dev;
client->dev.bus     = &i2c_bus_type;
client->dev.type    = &i2c_client_type;
client->dev.of_node = of_node_get(info->of_node);

i2c_dev_set_name(adap, client, info);
status = device_register(&client->dev);

两个检查点决定失败模式：地址非法在 i2c_check_addr_validity() 被挡，地址已被占用在 i2c_check_addr_busy() 被挡。报「Failed to register i2c client ... at 0x50 (-16)」，-16 就是 -EBUSY，板上已经有别的 client 占了 0x50。

九、注册流程：adapter 怎么注册 #

i2c_init() 定义在 drivers/i2c/i2c-core-base.c，主干三句：先把设备树里 i2c 别名的最大编号算进 __i2c_first_dynamic_bus_num，再 bus_register(&i2c_bus_type) 建出 /sys/bus/i2c，最后 is_registered = true 打开门禁，之后才允许注册 adapter 和 driver。

c
static int __init i2c_init(void)
{
        int retval;

        retval = of_alias_get_highest_id("i2c");

        down_write(&__i2c_board_lock);
        if (retval >= __i2c_first_dynamic_bus_num)
                __i2c_first_dynamic_bus_num = retval + 1;
        up_write(&__i2c_board_lock);

        retval = bus_register(&i2c_bus_type);
        if (retval)
                return retval;
        is_registered = true;

        /* 此处省略 CONFIG_I2C_COMPAT 的 class_compat_register("i2c-adapter") */

        retval = i2c_add_driver(&dummy_driver);
        if (retval)
                goto class_err;

        if (IS_ENABLED(CONFIG_OF_DYNAMIC))
                WARN_ON(of_reconfig_notifier_register(&i2c_of_notifier));
        if (IS_ENABLED(CONFIG_ACPI))
                WARN_ON(acpi_reconfig_notifier_register(&i2c_acpi_notifier));

        return 0;
        /* 省略 class_err / bus_err 回滚路径 */
}

i2c_bus_type 本身定义得很薄：

c
struct bus_type i2c_bus_type = {
        .name           = "i2c",
        .match          = i2c_device_match,
        .probe          = i2c_device_probe,
        .remove         = i2c_device_remove,
        .shutdown       = i2c_device_shutdown,
};

/sys/bus/i2c/devices/ 里存的不只是从设备，adapter 自己也挂在这条总线上，这是很多人第一次看错的地方。

i2c_register_adapter() 是真正的注册主体。先做门禁与自检（is_registered、name、algo），补默认值（lock_ops、timeout = HZ），初始化三把锁和 userspace_clients 链表，再 dev_set_name(&adap->dev, "i2c-%d", adap->nr) 后 device_register() 把 adapter 挂上总线。接下来依次建 SMBus alert、开运行时 PM、建 compat class 链接、初始化总线恢复，然后两条实例化 client 的路径（of_i2c_register_devices() 走设备树，i2c_scan_static_board_info() 走老式板级表），最后 bus_for_each_drv() 通知所有已注册驱动，落到 i2c_detect()。

of_i2c_register_devices() 是设备树实例化 client 的入口，定义在 drivers/i2c/i2c-core-of.c，逻辑就是遍历控制器节点下每个可用子节点、打上 OF_POPULATED 防重复、逐个调 of_i2c_register_device()：

c

        bus = of_node_get(adap->dev.of_node);

        if (of_node_test_and_set_flag(node, OF_POPULATED))
                continue;

        client = of_i2c_register_device(adap, node);
        if (IS_ERR(client)) {
                dev_err(&adap->dev,
                         "Failed to create I2C device for %pOF\n", node);
                of_node_clear_flag(node, OF_POPULATED);
        }
}
of_node_put(bus);

OF_POPULATED 标志防重复实例化：同一节点被转成 client 后打上标记，第二个 adapter 再扫到会跳过。

of_i2c_register_device() 实体只有三行：of_i2c_get_board_info() 填 info、i2c_new_device() 造 client、出错返回 ERR_PTR。映射规则全在 of_i2c_get_board_info() 里：

设备树属性 去向 说明
compatible info->type 经 of_modalias_node() 取逗号后面那段，"24c02" 就是这样得来的
reg info->addr 位 [0-6] 为 7 位地址
reg 高位 1<<31 I2C_CLIENT_TEN I2C_TEN_BIT_ADDRESS，10 位地址
reg 高位 1<<30 I2C_CLIENT_SLAVE I2C_OWN_SLAVE_ADDRESS，本机作从机
host-notify I2C_CLIENT_HOST_NOTIFY 布尔属性
wakeup-source I2C_CLIENT_WAKE 布尔属性

compatible = "24c02" 没有厂商前缀时会整体作为 type；compatible = "atmel,24c02" 则取 24c02。匹配 of_match_table 用的是完整 compatible，匹配 i2c_device_id 用的是 type，两者不是一回事。

十、注册流程：driver 怎么注册与匹配 #

设备驱动的入口是 i2c_register_driver()，被 i2c_add_driver() 宏包了一层（i2c_add_driver(driver) 展开成 i2c_register_driver(THIS_MODULE, driver)）。本体流程拆成两段：

c
int i2c_register_driver(struct module *owner, struct i2c_driver *driver)
{
        int res;

        /* Can't register until after driver model init */
        if (WARN_ON(!is_registered))
                return -EAGAIN;

        driver->driver.owner = owner;
        driver->driver.bus   = &i2c_bus_type;
        INIT_LIST_HEAD(&driver->clients);

        res = driver_register(&driver->driver);
        if (res)
                return res;

        /* Walk the adapters that are already present */
        i2c_for_each_dev(driver, __process_new_driver);

        return 0;
}

第一段：driver_register()。 把驱动挂到 i2c_bus_type 的驱动链表，设备模型立刻拿它跟总线上已有的每个 device 跑一遍 i2c_device_match()，能匹配就调 probe。「先注册驱动后插设备」这条最常见的路径，匹配就完成在这一步。

第二段：i2c_for_each_dev(driver, __process_new_driver)。 遍历总线上所有 device，用 dev->type != &i2c_adapter_type 滤出 adapter（i2c_bus_type 上同时挂着 adapter 和 client，只有 adapter 才需要探测），给每个 adapter 跑一遍自动探测，落到 i2c_do_add_adapter() → i2c_detect()。

反向路径在 adapter 注册那一侧：bus_for_each_drv(&i2c_bus_type, NULL, adap, __process_new_adapter)，对每个已注册驱动调一次 i2c_do_add_adapter()。两条路殊途同归：

谁后注册 遍历什么 回调 最终
driver 后注册 所有 device，滤出 adapter __process_new_driver i2c_detect()
adapter 后注册 所有 driver __process_new_adapter i2c_detect()

i2c_detect() 的判断链和探测主干：

c
static int i2c_detect(struct i2c_adapter *adapter, struct i2c_driver *driver)
{
        address_list = driver->address_list;               /* 驱动给的地址表 */
        if (!driver->detect || !address_list)              /* 缺一个就不探测 */
                return 0;
        if (adapter->class == I2C_CLASS_DEPRECATED)        /* 老适配器退出探测 */
                return 0;
        if (!(adapter->class & driver->class))             /* class 不匹配 */
                return 0;

        temp_client = kzalloc(sizeof(struct i2c_client), GFP_KERNEL);
        temp_client->adapter = adapter;

        for (i = 0; address_list[i] != I2C_CLIENT_END; i += 1) {
                temp_client->addr = address_list[i];      /* 逐个地址试 */
                err = i2c_detect_address(temp_client, driver);
                if (unlikely(err))
                        break;
        }
        kfree(temp_client);
        return err;
}

temp_client 是个「假 client」，只用来给 i2c_detect_address() 传地址，它本身永远不会注册进设备模型，用完就 kfree。这点很关键，别以为探测阶段已经生成了真实的 i2c_client。

i2c_detect_address() 才是真正对总线动手的地方：先 i2c_check_7bit_addr_validity_strict() 确认地址在 0x08~0x77，再 i2c_check_addr_busy() 跳过已占用的，然后 i2c_default_probe() 发 START+地址看有没有 ACK，通过了就 memset 出 i2c_board_info、填 info.addr，回调 driver->detect()。info.type[0] 还是空就报「no name」，非空则 i2c_new_device() 实例化，并 list_add_tail(&client->detected, &driver->clients)。

驱动作者的义务就一条：detect() 回调里必须给 info->type 填名字，否则造出来的 client 名字是空串，永远匹配不上驱动。

最后无论哪条路走通，client 和 driver 都交给设备模型，由 i2c_device_probe() 收口，它再去调 driver->probe() 或 driver->probe_new()。probe() 里做的事就是一套完整的字符设备驱动逻辑：申请设备号、建类、建节点、初始化硬件。

顺便回答一个常见疑问：能不能只注册 client 和 driver，不注册 adapter？不行。i2c_new_device() 的第一个参数就是 struct i2c_adapter *adap，没有 adapter，client 无处安放，更没法通过它收发数据。

十一、匹配机制：i2c_device_id 与 of_match_table #

i2c_device_match() 是匹配的唯一入口，定义在 drivers/i2c/i2c-core-base.c：

c
static int i2c_device_match(struct device *dev, struct device_driver *drv)
{
        struct i2c_client       *client = i2c_verify_client(dev);
        struct i2c_driver       *driver;

        /* Attempt an OF style match */
        if (i2c_of_match_device(drv->of_match_table, client))
                return 1;

        /* Then ACPI style match */
        if (acpi_driver_match_device(dev, drv))
                return 1;

        driver = to_i2c_driver(drv);

        /* Finally an I2C match */
        if (i2c_match_id(driver->id_table, client))
                return 1;

        return 0;
}

三条路按顺序试，命中即返回：

顺序 匹配方式 比较对象 用在什么场景
1 OF 匹配 of_match_table[].compatible vs client->dev.of_node 设备树平台，首选
2 ACPI 匹配 ACPI _HID / _CID x86 平台
3 ID 表匹配 id_table[].name vs client->name 无设备树、静态 board info、用户态 new_device

第三路的具体实现是字符串比较：

c
const struct i2c_device_id *i2c_match_id(const struct i2c_device_id *id,
                                                const struct i2c_client *client)
{
        if (!(id && client))
                return NULL;

        while (id->name[0]) {
                if (strcmp(client->name, id->name) == 0)
                        return id;
                id++;
        }
        return NULL;
}

while (id->name[0]) 是终止条件：末项 name 为空即停，不需要显式写结尾标记。三条实战结论：有设备树就写 of_match_table，compatible 必须和 dts 一字不差；没有设备树，id_table 的名字必须和 i2c_board_info.type 或用户态 new_device 传入的名字一致；两个表都写最稳，设备既会从设备树来，也会被用户态手动创建。

i2c_device_id 只有两个字段：name[I2C_NAME_SIZE] 和 kernel_ulong_t driver_data。driver_data 是给驱动自己用的标记，同一份代码服务多个变体芯片时靠它区分，和 of_device_id.data 用途一样，两个表都写时别给成不同的值。

一个典型的匹配表配置：

c
static const struct i2c_device_id at24_ids[] = {
        { "24c02", 0 },
        { }
};
MODULE_DEVICE_TABLE(i2c, at24_ids);

static const struct of_device_id at24_of_match[] = {
        { .compatible = "atmel,24c02" },
        { }
};
MODULE_DEVICE_TABLE(of, at24_of_match);

static struct i2c_driver at24_driver = {
        .driver = {
                .name           = "at24",
                .of_match_table = at24_of_match,
        },
        .probe  = at24_probe,
        .remove = at24_remove,
        .id_table = at24_ids,
};

driver.name 和 id_table[].name 是两回事，前一个决定 /sys/bus/i2c/drivers/ 下目录叫什么，后一个参与匹配。

十二、i2c_transfer：一次传输的完整链路 #

i2c_transfer() 是设备驱动唯一需要直接调用的传输接口，定义在 drivers/i2c/i2c-core-base.c：

c
int i2c_transfer(struct i2c_adapter *adap, struct i2c_msg *msgs, int num)
{
        int ret;

        if (!adap->algo->master_xfer) {
                dev_dbg(&adap->dev, "I2C level transfers not supported\n");
                return -EOPNOTSUPP;
        }

        ret = __i2c_lock_bus_helper(adap);
        if (ret)
                return ret;

        ret = __i2c_transfer(adap, msgs, num);
        i2c_unlock_bus(adap, I2C_LOCK_SEGMENT);

        return ret;
}

它只做三件事：查 master_xfer 在不在、加总线锁、交给 __i2c_transfer()。源码里那段长注释（「fault reporting model here is weak」）在讲错误上报的固有缺陷——传到一半出错时没法告诉调用方「成功了几条」，注释保留着，不影响逻辑。

__i2c_transfer() 是「不加锁版」，主干就是重试循环：

c
int __i2c_transfer(struct i2c_adapter *adap, struct i2c_msg *msgs, int num)
{
        unsigned long orig_jiffies;
        int ret, try;

        if (WARN_ON(!msgs || num < 1))
                return -EINVAL;

        ret = __i2c_check_suspended(adap);
        if (ret)
                return ret;

        if (adap->quirks && i2c_check_for_quirks(adap, msgs, num))
                return -EOPNOTSUPP;

        /* 此处省略 trace_i2c_read / trace_i2c_write 的 static_branch 分支 */

        /* Retry automatically on arbitration loss */
        orig_jiffies = jiffies;
        for (ret = 0, try = 0; try <= adap->retries; try++) {
                if (i2c_in_atomic_xfer_mode() && adap->algo->master_xfer_atomic)
                        ret = adap->algo->master_xfer_atomic(adap, msgs, num);
                else
                        ret = adap->algo->master_xfer(adap, msgs, num);

                if (ret != -EAGAIN)
                        break;
                if (time_after(jiffies, orig_jiffies + adap->timeout))
                        break;
        }

        return ret;
}

几个关键设计点：只有返回 -EAGAIN 才重试，-ENXIO（地址无 ACK）、-EIO 直接往外抛；重试上限是 adap->retries，同时受 adap->timeout 兜底，满足其一就停；原子上下文里 master_xfer_atomic 存在就优先用它；adap->quirks 不通过直接 -EOPNOTSUPP，给「一次最多传 32 字节」这类硬件限制兜底。

整条链路：

text
设备驱动
  |  i2c_master_send() / i2c_master_recv() / i2c_smbus_*()
  v
i2c_transfer(adap, msgs, num)                     查 master_xfer，拿总线锁
  |  __i2c_transfer(adap, msgs, num)               检查挂起、quirks、重试循环
  v
adap->algo->master_xfer(adap, msgs, num)          纯软件层到此为止
  |
  |  xxx_i2c_xfer() -> xxx_i2c_doxfer()            控制器驱动：开时钟、填地址
  |  -> xxx_i2c_message_start()                    起 START
  |  中断 -> xxx_i2c_irq_nextbyte()                逐字节收发，判 ACK
  v
xxx_i2c_stop() + wake_up()                        唤醒等待中的进程

master_xfer 往下就是寄存器活了。S3C2440 的 s3c24xx_i2c_message_start() 里能看到全部要素：(msg->addr & 0x7f) << 1 拼地址，I2C_M_RD 置位时 addr |= 1 并切主接收模式，随后 writeb(addr, regs + S3C2410_IICDS) 出地址、置 IICSTAT 的 START 位起波形。这段归 controller 篇，本篇只需知道：core 到 master_xfer 就交棒了。

两条路径的差别拉一张表，很多人把这两个搞混：

项 走 master_xfer 走 smbus_xfer
触发条件 设备驱动调 i2c_transfer() / i2c_master_send/recv() 设备驱动调 i2c_smbus_*()，且 adapter 实现了 smbus_xfer
中间层 i2c_transfer → __i2c_transfer i2c_smbus_xfer → __i2c_smbus_xfer
消息形态 直接下发 struct i2c_msg[] 打散成 addr/read_write/command/size/data 参数
依赖 master_xfer 必须存在，否则 -EOPNOTSUPP smbus_xfer 或 master_xfer 有一个就行
典型场景 所有控制器的基本路径 硬件原生支持 SMBus 的控制器

举个完整的设备侧写法，一次「写寄存器地址再读一个字节」用两个 msg 串起来：

c
static int mydev_read_reg(struct i2c_client *client, u8 reg, u8 *val)
{
        struct i2c_msg msgs[2];
        int ret;

        msgs[0].addr  = client->addr;
        msgs[0].flags = 0;
        msgs[0].len   = 1;
        msgs[0].buf   = &reg;

        msgs[1].addr  = client->addr;
        msgs[1].flags = I2C_M_RD;
        msgs[1].len   = 1;
        msgs[1].buf   = val;

        ret = i2c_transfer(client->adapter, msgs, 2);
        return (ret == 2) ? 0 : (ret < 0 ? ret : -EIO);
}

两条 msg 之间只有重复 START，没有 STOP，这是读寄存器能成功的物理前提。返回 2 表示两条都成功；返回 1 说明写成功读失败，这种情况要当错误处理。

i2c_transfer() 返回的是「处理成功的消息条数」，不是字节数。所以 i2c_master_send/recv() 才要自己判断 ret == 1 再把结果换成 count。这个语义差异是「函数返回 1 但我传了 16 字节」这类困惑的根源。

十三、i2c_msg 结构：消息的描述 #

struct i2c_msg 定义在 include/uapi/linux/i2c.h，因为用户态 I2C_RDWR ioctl 也要用它：

c
struct i2c_msg {
        __u16 addr;     /* slave address                        */
        __u16 flags;
#define I2C_M_RD                0x0001  /* read data, from slave to master */
                                        /* I2C_M_RD is guaranteed to be 0x0001! */
#define I2C_M_TEN               0x0010  /* this is a ten bit chip address */
#define I2C_M_DMA_SAFE          0x0200  /* the buffer of this message is DMA safe */
#define I2C_M_RECV_LEN          0x0400  /* length will be first received byte */
#define I2C_M_NO_RD_ACK         0x0800  /* if I2C_FUNC_PROTOCOL_MANGLING */
#define I2C_M_IGNORE_NAK        0x1000  /* if I2C_FUNC_PROTOCOL_MANGLING */
#define I2C_M_REV_DIR_ADDR      0x2000  /* if I2C_FUNC_PROTOCOL_MANGLING */
#define I2C_M_NOSTART           0x4000  /* if I2C_FUNC_NOSTART */
#define I2C_M_STOP              0x8000  /* if I2C_FUNC_PROTOCOL_MANGLING */
        __u16 len;              /* msg length                           */
        __u8 *buf;              /* pointer to msg data                  */
};
字段 含义 陷阱
addr 从设备地址，7 位或 10 位 7 位地址不含读写位
flags 方向与协议修饰位 I2C_M_RD 固定 0x0001，硬件依赖这个值
len 本段字节数 I2C_M_RECV_LEN 时会被硬件回填
buf 数据缓冲 不含从设备地址，只放纯数据

各 flags 位的用途见上面的宏注释，几个容易踩坑的点单独说：

  • I2C_M_RD 被硬编码为 0x0001，注释专门强调「guaranteed」。写 controller 驱动时若按位解析方向，认准这一位。
  • 除 I2C_M_RD 外的修饰位，都要求 functionality() 先报出对应的 I2C_FUNC_*，否则协议行为没保证。
  • I2C_M_NOSTART 常被误当成「省一次 START 提速」，真实用途是某些强制要求地址只发一次的老芯片。
  • I2C_M_RECV_LEN 时 len 只是初值 1，硬件收完后要加上实际字节数；S3C 驱动里就是 i2c->msg->len += byte。
  • I2C_M_IGNORE_NAK 不是「容错开关」，开了之后从机不应答也不报错，容易把接线问题吞掉。

len 为 0 的消息是合法且有用的：它就是「只发地址不发数据」，用来探测某地址上有没有设备。i2c_default_probe() 走的就是这条路，S3C 驱动里也有对应分支——is_lastmsg(i2c) && i2c->msg->len == 0 时直接发 STOP。

十四、SMBus 与 I2C 的关系 #

SMBus（System Management Bus）是 Intel 在 I2C 基础上定的一套更严格的子集。两者物理层几乎一样，协议层差别不小：

维度 I2C SMBus
速率 100k / 400k / 1M / 3.4M 10k ~ 100k，强制规范
超时 无强制超时 有明确超时（约 25~35ms）
最小电压/电流 无统一规定 有电气规范约束
包格式 自由，由芯片定义 固定命令集，command + data
错误校验 可选 支持 PEC（CRC-8）
地址仲裁 支持 复用 I2C 机制
重复起始 支持 部分协议禁用

对驱动工程师的实际影响只有一条：SMBus 定义了固定的传输类型，I2C 没有。所以你会看到 i2c_smbus_read_byte_data() 这种按协议命名的函数，而不是按芯片命名的函数。

SMBus 协议族一览：

协议 典型调用 线上形态
Quick Command i2c_smbus_write_quick() 只有地址 + 读写位，无数据
Send Byte i2c_smbus_write_byte() 地址 + 1 字节
Receive Byte i2c_smbus_read_byte() 地址 + 读 1 字节
Write Byte i2c_smbus_write_byte_data() 地址 + command + data
Read Byte i2c_smbus_read_byte_data() 地址 + command，重复START，读 1 字节
Write Word i2c_smbus_write_word_data() 地址 + command + data(2B, 小端)
Read Word i2c_smbus_read_word_data() 地址 + command，重复START，读 2 字节
Process Call i2c_smbus_process_call() 写 2 字节后读 2 字节
Block Write i2c_smbus_write_block_data() 地址 + command + 长度 + 最多 32 字节
Block Read i2c_smbus_read_block_data() 地址 + command，长度由从机给，最多 32 字节
Block Write-Read i2c_smbus_block_process_call() 写块后读块
I2C Block Read i2c_smbus_read_i2c_block_data() SMBus 索引下读任意长度

「Block」类协议上限 32 字节是 SMBus 规定的硬限制，和 I2C 本身无关。EEPROM 页写是 64 字节时，用 i2c_smbus_* 会被截断，得改用 i2c_transfer() 直接发 msg。

i2c_smbus_xfer_emulated() 就是那个兜底翻译器：把上表每一种协议翻译成 1~2 条 i2c_msg，再走 master_xfer。它的存在解释了一个现象：明明 i2c_algorithm 里 smbus_xfer 是 NULL，i2c_smbus_read_byte_data() 还是能用。

十五、i2c_smbus_read/write 系列接口 #

i2c_smbus_* 系列定义在 include/linux/i2c.h，实现在 drivers/i2c/i2c-core-smbus.c（4.x 之前这些函数在 i2c-core.c 里）。

底层参数结构是 union i2c_smbus_data：

c
union i2c_smbus_data {
        __u8 byte;
        __u16 word;
        __u8 block[I2C_SMBUS_BLOCK_MAX + 2]; /* block[0] is used for length */
                                             /* and one more for PEC */
};

block[0] 是长度，block[1] 开始是数据，末尾留 1 字节给 PEC。

SMBus 读写函数按功能分成几组：

函数 参数 返回
i2c_smbus_read_byte(client) client 读到的字节，负为错误
i2c_smbus_write_byte(client, value) value 0 或负 errno
i2c_smbus_read_byte_data(client, command) command 读到的字节
i2c_smbus_write_byte_data(client, command, value) command, value 0 或负 errno
i2c_smbus_read_word_data(client, command) command 读到的 16 位（小端）
i2c_smbus_write_word_data(client, command, value) command, value 0 或负 errno
i2c_smbus_read_i2c_block_data(client, command, length, values) command, length, buf 读到的字节数
i2c_smbus_write_i2c_block_data(client, command, length, values) command, length, buf 0 或负 errno
i2c_smbus_read_block_data(client, command, values) command, buf 读到的字节数
i2c_smbus_xfer(adapter, addr, flags, read_write, command, protocol, data) 全套参数 0 或负 errno

统一约定：读类函数返回读到的数据或字节数，写类函数返回 0；负数一律是 errno。所以判断失败用 ret < 0，不是 ret == 0。

另外两个入口值得记住：i2c_smbus_xfer() 是最底层入口，直接指定协议枚举 I2C_SMBUS_BYTE_DATA 之类；i2c_check_functionality(adap, func) 查能力位图，返回 bool，配套的 i2c_get_functionality(adap) 取原始位图。

i2c_check_functionality() 必须在调用前做，尤其是 SMBus 专有协议：

c
if (!i2c_check_functionality(client->adapter, I2C_FUNC_SMBUS_BYTE_DATA))
        return -EOPNOTSUPP;
val = i2c_smbus_read_byte_data(client, reg);
if (val < 0)
        return val;

I2C_FUNC_SMBUS_* 的能力位与上表一一对应：I2C_FUNC_SMBUS_BYTE、I2C_FUNC_SMBUS_BYTE_DATA、I2C_FUNC_SMBUS_WORD_DATA、I2C_FUNC_SMBUS_PROC_CALL、I2C_FUNC_SMBUS_BLOCK_DATA、I2C_FUNC_SMBUS_I2C_BLOCK，加上 I2C_FUNC_SMBUS_EMUL。EMUL 是合成位，只实现 master_xfer 的控制器应当报 I2C_FUNC_I2C | I2C_FUNC_SMBUS_EMUL，这样上层调 SMBus 才不会一律失败。

十六、从设备树实例化 I2C 设备 #

设备树里 I2C 从设备是控制器节点的子节点。一个能跑的 s3c2440 例子：

dts
i2c@54000000 {
    compatible = "samsung,s3c2440-i2c";
    clocks = <&clocks PCLK_I2C>;
    clock-names = "i2c";
    pinctrl-names = "default";
    pinctrl-0 = <&i2c0_bus>;
    status = "okay";
    samsung,i2c-max-bus-freq = <200000>;

    eeprom@50 {
        compatible = "24c02";
        reg = <0x50>;
        pagesize = <32>;
        status = "okay";
    };
};

几个约束：

  • 子节点名建议 <型号>@<地址>，@ 后面的地址必须和 reg 一致，dts 检查器会校验。
  • reg 写 7 位地址，0x50 不是 0xa0。写 0xa0 会在 i2c_check_addr_validity() 那里被挡下。
  • 10 位地址要在 reg 里加 I2C_TEN_BIT_ADDRESS 标志位（1<<31），本机作从机加 I2C_OWN_SLAVE_ADDRESS（1<<30），解析器会剥掉高位再存地址。
  • compatible 决定走 OF 匹配，reg 决定 client->addr。

驱动侧 of_match_table 必须匹配完整字符串。compatible = "24c02" 配 .compatible = "atmel,24c02" 匹配不上，这是最常见的排查点。

sysfs 手动实例化这条路适合调试，不需要重新编译 dts：

bash
# 在 1 号总线上创建一颗地址 0x50、型号 24c02 的设备
echo "24c02 0x50" > /sys/bus/i2c/devices/i2c-1/new_device

# 删掉它
echo 0x50 > /sys/bus/i2c/devices/i2c-1/delete_device

new_device 收的格式是 <name> <addr>，name 会直接成为 client->name，走 i2c_device_match() 的第三条路——id_table 匹配。驱动必须写了 id_table，只有 of_match_table 这条路走不通。delete_device 只接受地址，地址写错返回 -ENODEV。

内核配置项也要对：CONFIG_I2C 是基础，CONFIG_I2C_CHARDEV 才有 /dev/i2c-*，CONFIG_I2C_SLAVE 才有从机模式，设备树平台还得有 CONFIG_OF。

十七、i2c_add_numbered_adapter 与动态分配 #

adapter 的编号有两个入口，区别就一句话：编号是你指的还是内核给的。

函数 编号来源 适合场景
i2c_add_adapter() 动态分配，或设备树 alias 指定 USB、PCI 热插拔控制器
i2c_add_numbered_adapter() 调用者指定 adapter->nr 板级固定编号、已知总线号
i2c_add_numbered_adapter() 内部 __i2c_add_numbered_adapter() 真正干活的那个

i2c_add_numbered_adapter() 的实现要点：

c
int i2c_add_numbered_adapter(struct i2c_adapter *adap)
{
        if (adap->nr == -1) /* -1 means dynamically assign bus id */
                return i2c_add_adapter(adap);
        return __i2c_add_numbered_adapter(adap);
}

nr = -1 交给动态分配，指定了 nr 就走静态注册。__i2c_add_numbered_adapter() 里用 idr_alloc(&i2c_adapter_idr, adap, adap->nr, adap->nr + 1, GFP_KERNEL) 精确占坑，目标编号已被占用就直接失败，不会自动挪位。

i2c_add_adapter() 的那条设备树捷径值得单独看：

c
if (dev->of_node) {
        id = of_alias_get_id(dev->of_node, "i2c");
        if (id >= 0) {
                adapter->nr = id;
                return __i2c_add_numbered_adapter(adapter);
        }
}

只要 dts 里写了 aliases { i2c0 = &i2c_0; }，i2c_add_adapter() 就自动走静态编号路径。这解释了为什么有些板子上 /dev/i2c-0 一定是某个控制器——是 alias 定的，不是注册顺序定的。

编号分配三条规则：静态范围是 __i2c_first_dynamic_bus_num 以下，由 i2c_register_board_info() 的 busnum 和 of_alias_get_highest_id("i2c") 共同推高；动态范围从 __i2c_first_dynamic_bus_num 往上找空位；alias 优先，有 alias 就用 alias 的号跳过 IDR 分配。两个实战结论：板级静态声明的总线号别随意加大，会挤占动态编号空间；想固定 /dev/i2c-N，写 alias 比指定 nr 更规范。

成功之后 adap->nr 就是总线号，/dev/i2c-N 的次设备号也是它。i2c-dev 靠 i2c_get_adapter(minor) 反查适配器，这个调用给 dev 引用计数加一，配对的是 i2c_put_adapter()。漏掉 put 会让 adapter 永远卸不掉，rmmod 卡住。

i2c-dev.c 的初始化流程：register_chrdev_region(MKDEV(I2C_MAJOR, 0), I2C_MINORS, "i2c") 占主设备号 89 和 256 个次设备，class_create 建 /sys/class/i2c-dev/，再用 bus_register_notifier 监听 adapter 增删、用 i2c_for_each_dev(NULL, i2cdev_attach_adapter) 给已有 adapter 补建节点。i2cdev_attach_adapter() 为每个 adapter 建字符设备，次设备号 = adap->nr，device_create 出 /dev/i2c-%d。之后应用层 open("/dev/i2c-0") → ioctl(I2C_SLAVE, 0x50) 设地址 → read()/write() 收发，底层分别落到 i2c_master_recv() / i2c_master_send()；i2cdev_read() 里 count 上限 8192。

十八、上电时序与 adapter 的 probe #

平台驱动从 probe() 到 adapter 可用，中间有几个必须按顺序来的步骤，乱了就失败。

text
platform_driver->probe()
  |
  +-- 1. devm_kzalloc 私有结构
  +-- 2. platform_get_resource / devm_ioremap_resource 映射寄存器
  +-- 3. platform_get_irq + devm_request_irq 申请中断
  +-- 4. clk_get + clk_prepare_enable 开时钟
  +-- 5. 填 adapter->owner / name / algo / algo_data / nr / class
  +-- 6. devm_i2c_add_adapter() 或 i2c_add_adapter() 注册
  +-- 7. 失败则逆序回滚

几个时序坑：

时钟必须在注册前开好。 i2c_register_adapter() 里不碰时钟，它只做软件层初始化。时钟没开就注册成功，第一次 i2c_transfer() 会卡死或读回全 0。

中断要在 adapter 注册前申请。 s3c24xx_i2c_doxfer() 里 enable_irq 之后立刻发 START，中断没准备好就等于丢事件，进程在 wait_event_timeout() 里睡到超时。

adapter->algo 必须指向静态常量。 别用栈上或临时分配的 i2c_algorithm，bus_for_each_drv 遍历时还会用到。

失败回滚是申请的逆序。 用 devm_* 系列能省掉大半，devm_i2c_add_adapter() 连 adapter 都帮你注销（4.x 后期加的设备管理版本，确切版本未验证；3.x 只有 i2c_add_adapter()）。

pinmux 交给设备模型。 多数平台靠 pinctrl-names / pinctrl-0 自动配好，不用驱动代码手动 mux。SDA/SCL 的上拉是硬件的事，但总线修不起来时先量这两根线的电平。

挂起恢复要自己接管。 i2c_register_adapter() 里的 pm_runtime_no_callbacks() 和 pm_suspend_ignore_children(&adap->dev, true) 意思就是 core 不会替控制器做运行时电源管理。真要在 suspend 里省电，控制器驱动自己实现 dev_pm_ops，并确保挂起前没有传输在飞——__i2c_check_suspended() 会挡住挂起期间的传输。

复位和总线恢复是两件事。 bus_recovery_info 给 SDA 被从机拉死时用：靠 GPIO 模拟时钟脉冲把从机踢出，填了它 i2c_recover_bus() 才有办法。

一个典型 probe 的骨架：

c
static int my_i2c_probe(struct platform_device *pdev)
{
        struct my_i2c *i2c;

        i2c = devm_kzalloc(&pdev->dev, sizeof(*i2c), GFP_KERNEL);
        if (!i2c)
                return -ENOMEM;

        i2c->regs = devm_platform_ioremap_resource(pdev, 0);
        if (IS_ERR(i2c->regs))
                return PTR_ERR(i2c->regs);

        i2c->irq = platform_get_irq(pdev, 0);
        if (i2c->irq < 0)
                return i2c->irq;
        ret = devm_request_irq(&pdev->dev, i2c->irq, my_i2c_irq, 0,
                               dev_name(&pdev->dev), i2c);

        i2c->clk = devm_clk_get(&pdev->dev, "i2c");
        ret = clk_prepare_enable(i2c->clk);

        i2c->adap.owner      = THIS_MODULE;
        i2c->adap.algo       = &my_i2c_algorithm;
        i2c->adap.algo_data  = i2c;
        i2c->adap.dev.parent = &pdev->dev;
        i2c->adap.nr         = pdev->id;
        strscpy(i2c->adap.name, "my-i2c", sizeof(i2c->adap.name));

        return devm_i2c_add_adapter(&pdev->dev, &i2c->adap);
}

十九、调试手段：i2cdetect / i2cdump / debugfs #

i2cdetect 回答「这条总线上挂着谁」。前提是内核开了 CONFIG_I2C_CHARDEV，且用户有 /dev/i2c-* 权限。

bash
i2cdetect -l                    # 列出所有 I2C 适配器
i2cdetect -y 1                  # 扫描 1 号总线的 0x03~0x77
i2cdetect -y -a 1               # 强制扫描全地址段（有风险，会碰保留地址）

输出里 -- 是无设备，UU 是地址已被驱动占用（i2c_check_addr_busy() 判出），十六进制数字表示该地址有 ACK 应答但没驱动接管。UU 不代表探测成功，只代表内核里已有 client 占着这个地址。 三种探测模式决定结果准不准：

模式 参数 手法 风险
Quick Write 默认 只发地址+写位，看 ACK 最低，但有些芯片不应答
Read Byte -r 发地址+读位再读 1 字节 会真的把数据读走，会打乱从机状态机
Write Byte -q 发地址+写位再写 1 字节 会写坏配置寄存器，慎用

i2cdump 回答「这个地址里是什么」。

bash
i2cdump -y 1 0x50                    # 以字节模式读 0x50 的 0x00~0xff
i2cdump -y -r 0x00-0x0f 1 0x50       # 只读 0x00~0x0f
i2cget -y 1 0x50 0x00                # 单点读 0x50 的 0x00 寄存器
i2cset -y 1 0x50 0x00 0x5a           # 单点写
i2cget -y 1 0x68 0x75 w              # 读 16 位（w = word）

读出来全是 XX 表示探测不到；全 ff 说明没有应答、总线被拉死；读出来有规律的数据才是真读到了。

sysfs 侧也是重要调试面，bind / unbind 手动绑定解绑是验证匹配逻辑最直接的手段：

bash
ls /sys/bus/i2c/devices/                     # 所有 adapter + client
cat /sys/bus/i2c/devices/1-0050/name         # 从设备名字
echo 1-0050 > /sys/bus/i2c/drivers/at24/unbind
echo 1-0050 > /sys/bus/i2c/drivers/at24/bind

debugfs / tracing 看的是内核内部状态，比 printk 精准：

bash
echo 1 > /sys/kernel/debug/tracing/events/i2c/enable   # 打开 I2C 消息 trace
cat /sys/kernel/debug/tracing/trace
echo -n 'file i2c-core-base.c +p' > /sys/kernel/debug/dynamic_debug/control

__i2c_transfer() 里那些 trace_i2c_read / trace_i2c_write 就是 tracepoint 的落点，用 static_branch_unlikely(&i2c_trace_msg_key) 判断有没有开，没开时几乎零开销。

dmesg 关键词别只 grep i2c，几条真正有用的报错：

打印 含义 方向
adapter 'xxx': no algo supplied! adapter->algo 没填 查 adapter 初始化
i2c adapter has no name name 空 补 strscpy
Invalid 7-bit I2C address 0x%02hx 地址越界 查 dts 的 reg
Failed to register i2c client ... (-16) 地址已被占用 -EBUSY，查 board info 冲突
Failed to create I2C device for %pOF 设备树节点解析失败 查 compatible、reg
ack was not received 从机不响应 查接线、上拉、供电
timeout 传输超时 查时钟、中断、从机死锁

总线被拉死的判断方法：断开设备只接 i2cdetect，还是全 XX 就量 SDA/SCL 静态电平；SDA 一直被拉低说明某个从机在等时钟，需要 clock stretching 或 GPIO 恢复，这时 bus_recovery_info 就有用了。

二十、易错点速查 #

按「踩了会怎样 / 怎么改」的形式列，都是会浪费半天的那种：

易错点 现象 正确做法
i2c_board_info 的 type 没填 detect() 后 client 名字为空，驱动匹配不上 detect 回调里必须给 info->type 赋值
i2c_register_board_info() 在 i2c_add_adapter() 之后调 设备永不实例化 顺序反过来，放 board 初始化早期
用 i2c_new_device() 的返回值判 !client 换成 i2c_new_client_device() 后 ERR_PTR 非空，直奔宕机 新代码用 IS_ERR()
i2c_transfer() 返回值当字节数 传 16 字节却只判断 ret > 0 它返回的是消息条数，ret == num 才算全成
地址里带了读写位 0xa0 写进 reg，探测全失败 7 位地址只写 0x50，方向位在 flags 的 I2C_M_RD
I2C_M_NOSTART 滥用 从机不收数据，读操作直接 -EINVAL 只在芯片明确要求时用，且不能跨方向改变
设备树 compatible 带厂商前缀但驱动表里没带 OF 匹配失败，只剩 id_table 兜底 两个表都写，字符串逐字对比
只写 of_match_table 没写 id_table new_device 手动实例化后匹配不上 补 i2c_device_id[] 表
probe() 里不能睡眠的地方睡眠 报 scheduling while atomic probe 本身可睡眠，别在中断上下文里调 i2c_transfer
在中断上下文里调 i2c_transfer() 死锁或长时间关中断 用 workqueue / threaded irq 挪到进程上下文
SMBus 协议传超 32 字节 数据被截断，无报错 超 32 字节改用 i2c_transfer() 自组 msg
不查 i2c_check_functionality() 就调 SMBus 返回 -EOPNOTSUPP，原因难定位 调用前先查，查不过就走模拟路径
两次 i2c_get_adapter() 只 put 一次 rmmod 卡住，adapter 引用计数泄漏 每次 get 都配一次 put
adapter->timeout 留 0 5.2.8 里 core 会补 HZ，但老内核行为不同 显式赋值，别靠默认
adapter->name 空 WARN 后注册失败 strscpy 一定填
adapter->algo 用临时变量 注册后随时被解引用，悬空 指向 static const 常量
在 probe() 里同步等长延时 拖慢开机，probe 会被并发调用 用 devm_* 减负，异步部分挪出去
多个 client 抢同一地址 后注册的报 -EBUSY 查 board info / dts 是否重复声明
忘记开 CONFIG_I2C_CHARDEV 没有 /dev/i2c-0 内核 config 里补上
把 3.x 的 attach_adapter() 抄进 5.x 编译不过 老 API 已删，改走设备模型匹配
把 3.x i2c_adapter 字段照抄 clist_lock、client_register、id、level 都不存在 按 5.x 字段表重写
struct i2c_msg 的 buf 里塞地址 从机收到两个地址字节，行为异常 buf 只放纯数据
i2c_smbus_read_* 返回值判断写 == 0 读到数据 0 被误判为失败 失败判断用 ret < 0

再加三条不写进上表但值得单独记的：i2c_transfer() 的 num 上限不是 1，一次传多条 msg 是常态，多字节寄存器读靠的就是两条 msg 加重复 START；adap->retries 只在 -EAGAIN 时触发，-ENXIO 表示从机不存在，重试 100 次也没用；i2c_msg.len 为 0 是合法用法，用于「只发地址」探测，别把它当错误拦截掉。
