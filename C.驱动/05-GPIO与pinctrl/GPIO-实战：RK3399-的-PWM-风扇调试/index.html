一、要做一个什么东西：温控风扇 #

目标很朴素：板子热了风扇转，板子凉了风扇停，中间按温度分档调速，全程不碰用户态脚本。

拆开看是三个动作，落在三个子系统上：

动作 落到哪个子系统 内核里对应的东西
风扇能不能转（总开关） GPIO GPIO4_C6 的高低电平，或 pwm-fan 的 cooling-levels[0] = 0
风扇转多快（调速） PWM pwm1 输出占空比，20KHz 载波
什么时候转、转到几档 Thermal cpu_thermal 的 trip point + cooling-maps

第四个子系统是 pinctrl，它不产生任何行为，但决定前三个能不能生效——GPIO4_C6 这一根脚，要么当 GPIO 用，要么当 PWM 用，二选一，选错了就是「节点都在、就是不动」。

RK3399 的 PWM 有个容易踩的点：pwm1 挂在 PMUCRU 下（基地址 0xff420010，时钟 PCLK_RKPWM_PMU），而它复用的引脚 GPIO4_C6 属于 APIO4 电源域，供电由 gpio1830-supply 描述。也就是说，PWM 控制器在 PMU 域，引脚在主域。这两边任何一边没配好，风扇都是静止的。

二、电路原理图：GPIO、PWM、电源三者怎么接 #

NanoPC-T4 板载一个 3Pin 风扇座，连接器是 JST GH 系列、3Pin、型号 BM03B-GHS-TBT。它的 2 号脚不是直接接 12V，中间串了两级开关管。

链路是这样的：

text
VCC_12V0_SYS (12V)
      |
      +--- Q1 (N-MOS) 漏极
              |
              +--- BM03B-GHS-TBT pin2  → 风扇正极
                                         风扇负极 → GND
控制侧：
GPIO4_C6/PWM1 ──> Q41 (三极管) ──> Q1 栅极
风扇测速：
GPIO2_A6_FAN_TACH ──< 风扇转速信号

行为对应关系：

  • GPIO4_C6/PWM1 输出高电平 → Q41 导通 → Q1 栅极被拉起 → Q1 导通 → 连接器 2 号脚拿到 12V → 风扇转。
  • GPIO4_C6/PWM1 输出低电平 → Q41 截止 → Q1 截止 → 2 号脚没有电压 → 风扇停。

所以这是一个「正逻辑」的开关链路：高电平 = 通电。后面讲极性的时候，这条就是判断依据。

三个针脚的分工：

连接器引脚 板上接到哪 作用 内核里怎么用
pin1 VCC_12V0_SYS 经 Q1 开关 风扇电源 fan-supply = <&vcc12v0_sys>
pin2 Q1 漏极（开关后 12V） 风扇正极 同上，由 pwm-fan 做 regulator 使能
pin3 GND 地 无
测速针 GPIO2_A6_FAN_TACH 转速反馈 素材给了引脚名，没做驱动接入

这里要澄清一处常见误会：fan-supply 指的是风扇供电的那一路 regulator，不是 PWM 信号。PWM 走的是 pwms 属性。两者在节点里是分开的两个属性。

GPIO2_A6_FAN_TACH 是测速脚。素材只给了引脚名，没有给接线细节，也没有写接入方案。本篇不展开测速，这部分「未验证」。

⚠️ 图丢失注记：原始抓取稿此处应有散热风扇接线图与 3Pin 连接器实物图各一张，抓取时图片未随正文保存，正文里只剩下「下图是……」「硬件引脚接线如下：」这类引导句。上面的 ASCII 接线图是按正文描述重画的，位置和引脚编号以原理图 PDF 为准。

三、引脚分配与复用配置 #

先把引脚账算清楚。RK3399 的 GPIO 编号规则是「bank × 32 + 组内序号」，组内序号按 A0~A7、B0~B7、C0~C7、D0~D7 排。

信号 引脚 bank 组内序号 内核 GPIO 号 复用功能
风扇 PWM／开关 GPIO4_C6 4 C6 = 2×8+6 = 22 4×32+22 = 150 func1 = PWM1
风扇测速 GPIO2_A6 2 A6 = 6 2×32+6 = 70 未验证（素材未给）
tsadc 过温输出 GPIO1_A6 1 A6 = 6 1×32+6 = 38 func1 = tsadc_int

GPIO4_C6 = 150 这个数在板上能直接对上：/sys/kernel/debug/gpio 里 gpiochip4 是 GPIOs 128-159，gpiochip128 的 base 是 128、label 是 gpio4、ngpio 是 32。

bash
root@rk3399:~# cat /sys/class/gpio/gpiochip128/base
128
root@rk3399:~# cat /sys/class/gpio/gpiochip128/label
gpio4
root@rk3399:~# cat /sys/class/gpio/gpiochip128/ngpio
32

复用配置在 rk3399.dtsi 里已经写好了两组 pinctrl 状态，我们只需要在板级 dts 里引用：

dts
pwm1 {
		pwm1_pin: pwm1-pin {
				rockchip,pins =
						<4 RK_PC6 1 &pcfg_pull_none>;
		};

		pwm1_pin_pull_down: pwm1-pin-pull-down {
				rockchip,pins =
						<4 RK_PC6 1 &pcfg_pull_down>;
		};
};

rockchip,pins 的四元组含义是 <bank 引脚 复用功能 电气属性>：bank 4、引脚 RK_PC6、func 1（PWM1）、无上下拉。

这里有个必须记牢的选择题：GPIO4_C6 这一根脚，选了 func1 就是 PWM1 输出，选了 func0（RK_FUNC_GPIO）才是普通 GPIO。两者不能同时成立。本篇第九章讲 GPIO 开关，用的是另一条思路（把占空比打到 0），不抢这根脚的复用。真要纯 GPIO 控制，就得把 pinctrl-0 换成 GPIO 复用，此时 PWM 输出自然消失。

关于 IO 电源域：GPIO4_C6 属于 APIO4_VDD 域，对应 io_domains 的 gpio1830-supply。这一项没配，引脚输出不生效——素材在 GPIO 那节专门留了一句提醒，我在第十六章再展开。

四、设备树里的节点怎么写 #

板级文件是 arch/arm64/boot/dts/rockchip/rk3399-evb.dts（素材就是在它上面追加的）。风扇节点如下，两个节点一起看：

dts
fan: pwm-fan {
		compatible = "pwm-fan";
		/*
		 * With 20KHz PWM and an EVERCOOL EC4007H12SA fan
		 */
		cooling-levels = <0 12 30 100 200 255>;
		#cooling-cells = <2>;
		fan-supply = <&vcc12v0_sys>;
		pwms = <&pwm1 0 50000 0>;
};

vcc12v0_sys: vcc12v0-sys {
		compatible = "regulator-fixed";
		regulator-always-on;
		regulator-boot-on;
		regulator-max-microvolt = <12000000>;
		regulator-min-microvolt = <12000000>;
		regulator-name = "vcc12v0_sys";
};

逐项说：

属性 取值 含义
compatible "pwm-fan" 匹配 drivers/hwmon/pwm-fan.c，绑定的文档是 Documentation/devicetree/bindings/hwmon/pwm-fan.txt（素材所引路径）
pwms <&pwm1 0 50000 0> PWM 说明符：phandle、通道号、周期、极性
cooling-levels <0 12 30 100 200 255> 6 个档位，取值 0~255，不是 0~100
#cooling-cells <2> 作为 cooling device 被引用时的单元数，min 与 max 各一个
fan-supply <&vcc12v0_sys> 风扇供电 regulator

pwms 那四个数要拆开看：

  • 第 1 个：phandle，指向 PWM 控制器。这里填的是 &pwm1。
  • 第 2 个：通道号，per-chip index。Rockchip 每个 PWM chip 只有一个通道，所以填 0。
  • 第 3 个：PWM 输出波形周期，单位纳秒。50000 ns = 50 µs = 20KHz。
  • 第 4 个：极性，可选。0 表示正常极性。

这里要补一句素材没写透的话：pwm1 在 rk3399.dtsi 里写的是 #pwm-cells = <3>，三个 cell 是「channel、period、flags」，phandle 本身由引用语法 &pwm1 提供。所以 pwms 里一共出现 4 项，实际是「1 个 phandle + 3 个 cell」。#pwm-cells 是控制器声明的，不是消费者随便填的，改错了解析直接越界。

cooling-levels 的 6 个值是 6 个降温档位，档位号就是数组下标 0~5：下标 0 对应 0/255 占空比（停），下标 5 对应 255/255（全速）。后面 Thermal 章节里的 cooling state 指的就是这个下标，max_state 会是 5。

regulator-fixed 这一路是给 fan-supply 用的。regulator-always-on 与 regulator-boot-on 两个属性让它常开，12V 电源始终在，开关动作交给 PWM 那条通路。

pwm1 节点本体在 rk3399.dtsi，板级 dts 只负责打开：

dts
&pwm1 {
	status = "okay";
};

dts
pwm1: pwm@ff420010 {
		compatible = "rockchip,rk3399-pwm", "rockchip,rk3288-pwm";
		reg = <0x0 0xff420010 0x0 0x10>;
		#pwm-cells = <3>;
		pinctrl-names = "default";
		pinctrl-0 = <&pwm1_pin>;
		clocks = <&pmucru PCLK_RKPWM_PMU>;
		status = "disabled";
};

pinctrl-0 = <&pwm1_pin> 决定了引脚走 PWM 复用。这一行在 dtsi 里已经写好，我们别动它，动了就等于把引脚从 PWM 上摘下来。

五、PWM 子系统的 consumer 接口 #

站在写驱动的人的角度，PWM 只有一句话：拿一个 struct pwm_device 句柄，对它设周期和占空比，然后使能。框架把芯片差异全吃掉了，drivers/pwm/pwm-rockchip.c 里怎么算分频、怎么配 PWM_CNT 寄存器，我们不用管。

consumer 侧要 #include <linux/pwm.h>。核心对象的层级是这样的：

text
pwm_chip（控制器，Rockchip 一个 chip 一个通道）
  └── pwm_device（通道句柄，consumer 拿到的就是它）
        └── pwm_state（当前状态：period / duty_cycle / polarity / enabled）

pwm_state 是 4.x 之后 PWM 框架的中心数据结构。字段如下：

字段 类型 单位 含义
period u64 ns 一个完整 PWM 周期的长度
duty_cycle u64 ns 一个周期内有效电平持续的时间
polarity enum pwm_polarity — PWM_POLARITY_NORMAL 或 PWM_POLARITY_INVERTED
enabled bool — 输出是否使能

三个约束必须挂在心上：

  • duty_cycle 的单位是纳秒，不是千分比，不是百分比。pwm-fan 拿 cooling-levels 的 0~255 去换算，换算公式在驱动里，见下一节。
  • duty_cycle 必须小于等于 period。大于的话老接口直接返回 -EINVAL，新接口由驱动决定怎么钳。
  • 改了 polarity 却不动 duty_cycle 的数值，实际引脚上的有效电平宽度会翻转——逻辑上的「占空比」没变，物理上的高电平宽度变成了 period - duty_cycle。

旧版内核里还有一个 enum pwm_polarity pwm_polarity[] 的全局表，以及 pwm_set_polarity()。这套东西在 4.x 到 5.x 期间被逐步废弃，polarity 收进 pwm_state 统一管理。素材用的 6.3 里 pwm_set_polarity() 已经不存在，只剩 pwm_apply_state()。具体删除版本我没查到确切的 commit，写「未验证」。

六、申请 PWM：pwm_get 与 devm_pwm_get #

申请有两个入口：

c
struct pwm_device *pwm_get(struct device *dev, const char *con_id);
struct pwm_device *devm_pwm_get(struct device *dev, const char *con_id);

两者的区别只有一个：谁负责释放。

  • pwm_get() 拿到的句柄要自己 pwm_put()，漏了就泄漏。
  • devm_pwm_get() 走 devres 托管，设备 detach 时框架自动 pwm_put()，驱动里不用写清理代码。

devres 的托管点是 devres_release_all()，在驱动 unbind 或 probe 失败回退时被调。所以 devm_pwm_get() 拿到的句柄，生命周期严格绑在 struct device 上，比手写 pwm_put() 少一个出错面。代价是：在 remove() 里拿不到「还没释放」的句柄再做一次 pwm_disable()，要关 PWM 得在 remove() 前面自己关。

con_id 是什么？它就是 pwms 里对应的名字。设备树里如果写的是 pwms = <&pwm1 0 50000 0>;，没有 pwm-names，那 con_id 传 NULL，框架按序号 0 取第一个。写了 pwm-names = "fan"; 就传 "fan"。pwm-fan 驱动自己用的是 devm_pwm_get(dev, NULL)，因为一个风扇只有一个 PWM。

按 id 取的变体是 pwm_request(int pwm, const char *label)，这是给没有设备树的场景用的全局编号接口，新代码不该再用。

一个最小骨架，把本篇会用到的 API 串起来：

c
#include <linux/pwm.h>

static int fan_probe(struct platform_device *pdev)
{
	struct pwm_device *pwm;
	struct pwm_state state;
	int ret;

	pwm = devm_pwm_get(&pdev->dev, NULL);
	if (IS_ERR(pwm))
		return PTR_ERR(pwm);

	/* 老接口：直接设周期与占空比 */
	ret = pwm_config(pwm, 5000, 50000);	/* duty=5us, period=50us，即 10% */
	if (ret)
		return ret;

	ret = pwm_enable(pwm);
	if (ret)
		return ret;

	/* 新接口：一次性提交完整状态 */
	pwm_init_state(pwm, &state);
	state.period = 50000;
	state.duty_cycle = 25000;
	state.polarity = PWM_POLARITY_NORMAL;
	state.enabled = true;

	return pwm_apply_state(pwm, &state);
}

pwm_init_state() 用当前硬件状态填初值，之后再改想改的字段，不要自己 memset 一个 pwm_state 出来——未初始化的 polarity 会让极性随机。

七、设置周期与占空比 #

老接口三件套，签名如下（include/linux/pwm.h）：

c
int pwm_config(struct pwm_device *pwm, int duty_ns, int period_ns);
int pwm_enable(struct pwm_device *pwm);
void pwm_disable(struct pwm_device *pwm);

注意 pwm_config() 的参数顺序是「先占空比、后周期」，跟直觉相反，写反了现象是「周期变成 5µs、占空比 50µs」，驱动会返回 -EINVAL。

新接口是 pwm_apply_state()：

c
int pwm_apply_state(struct pwm_device *pwm, const struct pwm_state *state);

一次提交 period、duty_cycle、polarity、enabled 四个字段。对比一下：

需求 老接口写法 6.3 的写法
设周期 + 占空比 pwm_config(pwm, duty_ns, period_ns) 填 state 后 pwm_apply_state()
启动输出 pwm_enable(pwm) state.enabled = true 后 pwm_apply_state()
停止输出 pwm_disable(pwm) state.enabled = false 后 pwm_apply_state()
改极性 pwm_set_polarity()（4.x 旧 API） 填 state.polarity 后 pwm_apply_state()
读当前状态 无统一接口 pwm_get_state(pwm, &state)

版本标注：pwm_config() 在 4.x 之后就被建议换用 pwm_apply_state()，但它一直没被删，6.3 里还在，内部实现对已使能的 PWM 会先 disable、改参数、再 enable。上面那份 API 对照以 6.3 为准；5.x 早期是否已有 pwm_get_state() 统一出口，我写「未验证」。

还有一个更新版本才有的接口：pwm_set_relative_rate()，用整数分子分母表达占空比，避免 ns 换算精度损失。它在 6.3 里没有，出现在更晚的内核上（我看到它时才注意到这个变化，确切引入版本未验证）。本篇的 pwm-fan 场景不需要它，但你在新内核上翻 PWM 文档看到这个函数时，别在 6.3 的代码里找。

pwm-fan 驱动内部把 cooling-levels 换算成 duty_cycle 的逻辑是：

text
duty_cycle = period × cooling_level / 255

255 是分母，不是 100。素材在 dts 注释里写了 20KHz 和风扇型号（EVERCOOL EC4007H12SA），cooling-levels = <0 12 30 100 200 255> 的 6 档就按这个公式摊到 50µs 上。取 12 时对应 50000 × 12 / 255 ≈ 2353 ns。这个数是我按公式算的，不是实测读数。

八、PWM 的极性：正逻辑与反逻辑 #

极性这件事，一句话：PWM_POLARITY_NORMAL 下 duty_cycle 说的是高电平宽度；PWM_POLARITY_INVERTED 下说的是低电平宽度。

回到第二章的电路。GPIO4_C6 高电平 → Q41 通 → Q1 通 → 风扇通电。所以「高电平 = 转」，正逻辑，极性填 0（即 PWM_POLARITY_NORMAL）。

pwm-fan 的 dts 注释里把这条写得很直白：

  • 极性配 0，cooling-levels 描述的是高电平的占空比。
  • 极性配 PWM_POLARITY_INVERTED，cooling-levels 描述的是低电平的占空比。

如果极性填反了，现象是「反着来」：cooling-levels 下标 5（255）本该全速，实际变成完全不通电，风扇停；下标 0 本该停，实际满速。这个现象很有辨识度，第十七章会列进对照表。

/sys 里对应的文件是 /sys/class/pwm/pwmchipX/pwmN/polarity，写 normal 或 inversed：

bash
root@rk3399:/sys/class/pwm/pwmchip0/pwm0# echo normal > polarity

注意两点：

  • polarity 要在 period 与 duty_cycle 都设好之后再确认一遍，因为某些驱动在改极性时会把 duty_cycle 按 period - duty_cycle 重算。素材的日志顺序是 period → duty_cycle → polarity → enable，就是这个道理。
  • 设备树里的 flags 也吃常量名。pwm.yaml 绑定里定义的是 PWM_POLARITY_INVERTED，dts 里写常量名而不是数字，可读性差很多的时候才写 0／1。

还有一层容易混的：GPIO 子系统里也有个 active_low，/sys/class/gpio/gpioN/active_low。它翻的是 GPIO 的逻辑电平，跟 PWM 的 polarity 不是一回事。风扇链路上我们用的是 PWM 极性，别把两个概念混着调，否则调一处、错一处。

九、用 GPIO 做风扇开关 #

在还没接 Thermal 之前，最直接的验证手段就是用 GPIO 直接开关风扇。这条路不依赖 pwm-fan，也不依赖 governor。

前提是内核开了 sysfs 接口：

text
General setup  --->
	[*] Configure standard kernel features (expert users)   // CONFIG_EXPERT
Device Drivers  --->
	 -*- GPIO Support  --->                                  // CONFIG_GPIOLIB
		[*]   /sys/class/gpio/... (sysfs interface)         // CONFIG_GPIO_SYSFS

CONFIG_GPIOLIB 一般都得是 y，别的驱动也要用。CONFIG_GPIO_SYSFS 看需求开，不需要从 /sys/class/gpio 操作就不开。

操作四步：查编号 → export → 读写文件 → unexport。

bash
root@rk3399:/sys/class/gpio# echo 150 > export
root@rk3399:/sys/class/gpio# ls
export   gpio156    gpiochip128  gpiochip64  unexport
gpio150  gpiochip0  gpiochip32   gpiochip96
root@rk3399:/sys/class/gpio# cd gpio150
root@rk3399:/sys/class/gpio/gpio150# echo out > direction
root@rk3399:/sys/class/gpio/gpio150# echo 1 > value
root@rk3399:/sys/class/gpio/gpio150# echo 0 > value
root@rk3399:/sys/class/gpio/gpio150# cat value
0
root@rk3399:/# echo 150 > /sys/class/gpio/unexport

direction 接受 in、out、high、low。后两个在设方向为输出的同时把 value 一起写成 1／0。

这条路能跑通的前提有两个，缺一个都不动：

  • io_domains 里的 gpio1830-supply 配了，否则 GPIO4_C6 输出不生效。素材这里专门留了提醒。
  • 引脚没被 pinctrl 抢成 PWM 功能。GPIO4_C6 在 pwm1 的 pinctrl-0 里是 func1，只要 pwm1 是 okay 状态，这根脚就是 PWM 输出而不是 GPIO，echo 150 > export 直接失败，或者导出了也控制不了物理电平。

所以实际工程里我不建议用 GPIO 硬开关风扇。更稳的做法是让 pwm-fan 一直持有这根脚，停机就把 cooling-levels[0] 对应的占空比打到 0——输出恒定低电平，Q41 截止，风扇停。效果一样，还不会跟 pinctrl 打架。

对比一下两条路：

方式 占用引脚复用 调速能力 依赖子系统 适用场景
sysfs GPIO 拉高／拉低 func0（GPIO） 无，只有全速／停 GPIO 快速验证、临时调试
pwm-fan 占空比 0 func1（PWM1） 有，6 档 PWM + hwmon 正式方案
cooling-levels[0] = 0 func1（PWM1） 有，档位可关停 PWM + Thermal 温控方案

十、转速与占空比的实测关系 #

先说清楚：素材只有配置值和一个用户态写入值，没有转速计读数，也没有占空比-转速曲线。本文没有实测数据。

能确认的是配置和理论换算。素材给的风扇型号是 EVERCOOL EC4007H12SA，载波 20KHz。

cooling state（下标） cooling-levels 值 占空比 = 值/255 对应 duty_cycle（ns，period = 50000） 描述
0 0 0 0 全周期低电平，风扇停
1 12 4.71% 2353 素材描述为「开始转动，转速较慢」
2 30 11.76% 5882 素材未描述
3 100 39.22% 19608 素材未描述
4 200 78.43% 39216 素材未描述
5 255 100% 50000 全速

表的第 4 列是按 50000 × 值 / 255 算出来的，不是抄的读数。前两列和最后一列来自素材。

素材里另有两个用过的值，都是往 hwmon 的 pwm1 文件里写的，属于用户态输入而不是实测结果：

bash
root@rk3399:/#  echo 100 > /sys/devices/platform/pwm-fan/hwmon/hwmon1/pwm1

/sys/devices/platform/pwm-fan/hwmon/hwmon1/pwm1 这个节点是 pwm-fan 作为 hwmon 设备暴露的：

文件 权限 作用
pwm1 可写 0~255，直接改占空比，值越大转得越快
pwm1_enable 可写 手动／自动模式切换（6.3 的 pwm-fan 提供，具体取值未验证）

hwmon1 的编号不是固定的，板子上有几个 hwmon 设备它排第几就变，脚本里别硬编码。

想要真实曲线，只能自己测：风扇供电并一个示波器看 GPIO4_C6 波形确认占空比，再用测速脚或光电转速计量转速，逐档记录。这个动作需要硬件，素材没做，我也不编。

十一、Thermal 子系统的接入 #

Thermal 是内核里负责「按温度做点什么」的框架。它由四块组成：

组成 职责
thermal sensor driver 采温度。RK3399 上是 tsadc，驱动在 drivers/thermal/rockchip_thermal.c
thermal core 把 governor 和 driver 封起来，统一接口
thermal governor 温控策略，决定 cooling device 该不该降、降到几档
thermal cooling device 执行冷却的东西。CPU、GPU 是，风扇也是

governor 有几个常见选择：

governor 策略
step_wise 每个轮询周期逐级调档，动作温和
power_allocator 引入 PID，按温度动态分配 power 再折算成频率
fair_share 档位多的 cooling device 优先降
userspace 内核不干预，由用户态写

cooling device 只认一个东西：state，档位。它不问「现在多少度」，只执行「现在要第 3 档」。温度到档位的换算全在 governor 里。这个分工是理解后面所有配置的关键。

传感器侧是 tsadc。两种模式：

  • 用户定义模式：所有控制信号由软件写寄存器直接控。
  • 自动模式：模块自己轮询，温度过高就发中断；持续超阈值就拉 TSHUT 给 CRU 复位整芯片，或者通过 GPIO 通知 PMIC。走 GPIO 复位这条路，硬件上必须把 tsadc_int 连到 PMIC 的复位脚，否则只能走 CRU。

NanoPC-T4 上是有过温保护电路的。tsadc 节点在板级 dts 里这样打开：

dts
&tsadc {
	/* tshut mode 0:CRU 1:GPIO */
	rockchip,hw-tshut-mode = <1>;
	/* tshut polarity 0:LOW 1:HIGH */
	rockchip,hw-tshut-polarity = <1>;
	status = "okay";
};

rk3399.dtsi 里的本体，几个关键字段：

dts
tsadc: tsadc@ff260000 {
		compatible = "rockchip,rk3399-tsadc";
		reg = <0x0 0xff260000 0x0 0x100>;
		interrupts = <GIC_SPI 97 IRQ_TYPE_LEVEL_HIGH 0>;
		assigned-clocks = <&cru SCLK_TSADC>;
		assigned-clock-rates = <750000>;
		clocks = <&cru SCLK_TSADC>, <&cru PCLK_TSADC>;
		clock-names = "tsadc", "apb_pclk";
		resets = <&cru SRST_TSADC>;
		reset-names = "tsadc-apb";
		rockchip,grf = <&grf>;
		rockchip,hw-tshut-temp = <95000>;
		pinctrl-names = "init", "default", "sleep";
		pinctrl-0 = <&otp_pin>;
		pinctrl-1 = <&otp_out>;
		pinctrl-2 = <&otp_pin>;
		#thermal-sensor-cells = <1>;
		status = "disabled";
};
字段 含义
reg tsadc 寄存器基地址与长度
interrupts 中断号与触发方式
resets 复位信号
rockchip,hw-tshut-temp 硬件关机温度，95000 = 95℃
rockchip,hw-tshut-mode 硬件关机走哪条路，0 = CRU，1 = GPIO
rockchip,hw-tshut-polarity 硬件关机的有效极性，0 = LOW，1 = HIGH
#thermal-sensor-cells 作为 sensor 被引用时的单元数，<1> 是 channel 号

pinctrl-0/1/2 对应 init、default、sleep 三个状态，otp_pin 把 GPIO1_A6 配成 GPIO，otp_out 把它配成 func1（tsadc_int）：

dts
tsadc {
		otp_pin: otp-pin {
				rockchip,pins = <1 RK_PA6 RK_FUNC_GPIO &pcfg_pull_none>;
		};

		otp_out: otp-out {
				rockchip,pins = <1 RK_PA6 1 &pcfg_pull_none>;
		};
};

#thermal-sensor-cells = <1> 意味着引用时要带 channel 号：thermal-sensors = <&tsadc 0>; 是 CPU 温度，<&tsadc 1> 是 GPU 温度。

⚠️ 图丢失注记：原始素材在这里配了一张过温保护电路的硬件接线图，抓取时丢失，只剩「硬件引脚接线如下：」的引导句。

十二、thermal zone 与 trip point #

thermal zone 是一个温控管理区间，可以理解成一个「虚拟温度传感器 + 一套规则」。规则靠 trip point 描述。

一个 zone 关联一个 sensor，可以挂多个 trip point。trip point 三个字段：

字段 单位 含义
temperature 毫摄氏度 触发温度，到点就触发
hysteresis 毫摄氏度 迟滞量。触发后一直保持，直到温度降到 temperature - hysteresis 以下才解除，用来防抖
type 字符串 类型，见下表

type 分四类：

类型 含义 典型动作
active 主动冷却 控制风扇这类主动器件
passive 被动冷却 限 CPU 频率／进 idle，牺牲性能
hot 热通知 通知驱动，动作由驱动自定
critical 临界 通知驱动并关机；阈值之上硬件已经不稳，固件会复位

zone 本体在 rk3399.dtsi 的 thermal_zones 下：

dts
thermal_zones: thermal-zones {
		cpu_thermal: cpu-thermal {
				/* 温度超过阀值时，每隔100ms查询温度 */
				polling-delay-passive = <100>;
				/* 温度未超过阀值时，每隔1000ms查询温度 */
				polling-delay = <1000>;
				/* 当前thermal zone通过tsadc0获取温度 */
				thermal-sensors = <&tsadc 0>;

				trips {
						cpu_alert0: cpu_alert0 {
								temperature = <70000>;
								hysteresis = <2000>;
								type = "passive";
						};
						cpu_alert1: cpu_alert1 {
								temperature = <75000>;
								hysteresis = <2000>;
								type = "passive";
						};
						cpu_crit: cpu_crit {
								temperature = <95000>;
								hysteresis = <2000>;
								type = "critical";
						};
				};
		};
};

polling-delay 与 polling-delay-passive 都是毫秒，设为 0 表示关掉框架定时器，假设 sensor 自己能出中断。cpu_alert0 是 70℃ 起走被动冷却，降到 68℃ 解除；cpu_crit 是 95℃，跟上文的 rockchip,hw-tshut-temp 对齐。

GPU 那个 zone 结构一样，thermal-sensors = <&tsadc 1>，gpu_alert0 75℃ passive，gpu_crit 95℃ critical。

这一部分解析在 of_thermal 里做（drivers/thermal/of-thermal.c）：它遍历 zone 节点的 trips 子节点，逐个读 temperature、hysteresis、type，把每个 trip 填成 struct thermal_trip 挂到 thermal_zone_device 的 trip 数组上；再遍历 cooling-maps 建 cooling mapping。映射通过 thermal_zone_device_register_with_trips() 注册 zone 时一起交给核心。如果 type 写了个不认识的字符串，of_thermal 会把这一条 trip 丢掉，而不是报错——所以 trip_point_x_type 文件的数量对不上时，先回去检查字符串拼写。

十三、cooling device：把风扇注册成降温设备 #

一个设备要能当 cooling device 用，必须在设备树里声明 #cooling-cells = <2>，并且驱动里调用 thermal_cooling_device_register()（或 devm 版本）把自己注册进 thermal 核。

CPU 侧，rk3399.dtsi 里每个 core 都带 #cooling-cells = <2>; /* min followed by max */，还有 dynamic-power-coefficient，后者是 power_allocator 要用到的功耗常数（Pdyn = C * V^2 * F）：

dts
cpu_b0: cpu@100 {
		device_type = "cpu";
		compatible = "arm,cortex-a72";
		reg = <0x0 0x100>;
		enable-method = "psci";
		capacity-dmips-mhz = <1024>;
		clocks = <&cru ARMCLKB>;
		#cooling-cells = <2>; /* min followed by max */
		dynamic-power-coefficient = <436>;
		cpu-idle-states = <&CPU_SLEEP &CLUSTER_SLEEP>;

		thermal-idle {
				#cooling-cells = <2>;
				duration-us = <10000>;
				exit-latency-us = <500>;
		};
};

cpu_l0 到 cpu_l3 是四核 Cortex-A53（最高 1.5GHz），cpu_b0、cpu_b1 是双核 Cortex-A72（最高 2.0GHz）。A53 的 dynamic-power-coefficient 是 100，A72 是 436。GPU 节点也带 #cooling-cells = <2>。

风扇侧，#cooling-cells = <2> 在第四节的 pwm-fan 节点里已经写了。pwm-fan 驱动注册 cooling device 的逻辑：

  • 从 cooling-levels 数出档位个数，作为 max_state。
  • 实现 get_max_state() / get_cur_state() / set_cur_state() 三个回调。
  • set_cur_state(n) 就是取 cooling-levels[n]，按 255 换算成 duty_cycle，提交给 PWM。

绑定关系写在 zone 的 cooling-maps 里。每个 map 三个字段：

字段 含义
trip 指向本 zone 内某个 trip point 的 phandle
cooling-device phandle 数组，每项带 min 与 max 两个档位限定符
contribution （power_allocator 用）该设备在本 zone 冷却贡献里的占比

thermal-cooling-devices.yaml 是这部分绑定的文档。THERMAL_NO_LIMIT（-1UL）是「不设限」，让框架用设备的最小／最大档位。

十四、温控策略：什么时候开、什么时候关 #

板级 dts 里我们给 CPU zone 加两条 active 规则，把风扇挂上去：

dts
&cpu_thermal {
        trips {
                cpu_warm: cpu_warm {
                        temperature = <55000>;
                        hysteresis = <2000>;
                        type = "active";
                };

                cpu_hot: cpu_hot {
                        temperature = <65000>;
                        hysteresis = <2000>;
                        type = "active";
                };
        };

        cooling-maps {
                map2 {
                        trip = <&cpu_warm>;
                        cooling-device = <&fan THERMAL_NO_LIMIT 1>;
                };

                map3 {
                        trip = <&cpu_hot>;
                        cooling-device = <&fan 2 THERMAL_NO_LIMIT>;
                };
        };
};

读法：

  • 55℃ 触发 cpu_warm，风扇档位范围是 [THERMAL_NO_LIMIT, 1]，也就是 0~1 档。到 53℃（55 - 2）解除。
  • 65℃ 触发 cpu_hot，风扇档位范围是 [2, THERMAL_NO_LIMIT]，也就是 2~5 档。到 63℃ 解除。
  • 两段不重叠，55~65℃ 之间风扇在第 1 档，65℃ 以上才允许上到 2 档以上。

THERMAL_NO_LIMIT 当 min 用时表示从 0 开始，当 max 用时表示到顶。写法上 <&fan THERMAL_NO_LIMIT 1> 与 <&fan 0 1> 等价。

step_wise 具体怎么在区间里挑档位，四条规则：

throttle 状态 温度趋势 动作
发生 上升 升一级 cooling state
发生 下降 保持
解除 下降 保持
解除 上升 降一级 cooling state

其中 throttle = 当前温度 > trip point 的触发温度／滞后温度。step_wise 每个轮询周期最多动一级，所以从 0 冲到 5 需要几个周期，急不来。

内核配置（这一块素材给的是 make menuconfig 路径）：

text
Device Drivers  --->
	-*- Thermal drivers  --->
	    [*]   Expose thermal sensors as hwmon device
	    [*]   APIs to parse thermal data out of device tree
	    [*]   Enable writable trip points
		Default Thermal governor (step_wise)  --->
		[ ]   Fair-share thermal governor
		[*]   Step_wise thermal governor
		[ ]   Bang Bang thermal governor
		[ ]   User_space thermal governor
		[*]   Power allocator thermal governor
		[*]   Generic cpu cooling support
		[*]     CPU frequency cooling device
		[*]   Generic device cooling support
		[*]   Thermal emulation mode support
		<*>   Rockchip thermal driver

Default Thermal governor (step_wise) 决定默认策略。Enable writable trip points 决定 /sys/class/thermal/thermal_zoneN/trip_point_x_temp 能不能写，调试时要开。Thermal emulation mode support 决定 emul_temp 节点在不在，这个后面用得上。

CPU 各核的 cpu-supply 也要绑上，否则调频降温那条通路走不通：

dts
&cpu_b0 {
        cpu-supply = <&vdd_cpu_b>;
};

&cpu_b1 {
        cpu-supply = <&vdd_cpu_b>;
};

&cpu_l0 {
        cpu-supply = <&vdd_cpu_l>;
};

vdd_cpu_b 与 vdd_cpu_l 定义在 i2c0 下的 regulator@40（silergy,syr827）与 regulator@41（silergy,syr828）里，电压范围 712500~1500000 µV，regulator-ramp-delay = <1000>。

十五、设备树里 pq 与 pwm 的绑定 #

这一节把前面散落的绑定关系收成一张图。素材原稿的小节标题写作「pq 与 pwm 的绑定」，从上下文看，pq 是 pwm 的笔误——全篇没有出现任何 pq 相关节点或属性，所有绑定都在 pwms 与 cooling-maps 上。下面按实际内容还原。

text
tsadc@ff260000 (sensor, #thermal-sensor-cells=<1>)
        │
        │ thermal-sensors = <&tsadc 0>
        ▼
cpu_thermal (thermal zone)
        │
        ├── trips:  cpu_warm(55℃,active)  cpu_hot(65℃,active)  cpu_crit(95℃,critical)
        │
        └── cooling-maps:
                map2: trip=<&cpu_warm> → cooling-device=<&fan THERMAL_NO_LIMIT 1>
                map3: trip=<&cpu_hot>  → cooling-device=<&fan 2 THERMAL_NO_LIMIT>

pwm-fan (cooling device + hwmon)
        │
        ├── cooling-levels = <0 12 30 100 200 255>   → state 0..5
        ├── fan-supply = <&vcc12v0_sys>              → regulator-fixed 12V
        └── pwms = <&pwm1 0 50000 0>
                        │
                        ▼
                pwm@ff420010 (pwm1, #pwm-cells=<3>)
                        │
                        └── pinctrl-0 = <&pwm1_pin>
                                        │
                                        ▼
                                GPIO4_C6 func1 (GPIO 150)
                                        │
                                        ▼
                                Q41 → Q1 → 风扇 12V

四个子系统在这一张图里各占一段：pinctrl 在最底下决定引脚归属，PWM 在中间产生波形，Thermal 在最上面决定该给什么档位，GPIO 只在调试时插一脚。

几个绑定上的硬约束：

  • pwms 的 cell 数必须等于 PWM 控制器的 #pwm-cells，pwm1 是 3，写多写少都解析失败。
  • cooling-device 里每组限定符的个数必须等于目标设备的 #cooling-cells，都是 2（min、max）。
  • thermal-sensors 后面带的 channel 数必须等于 #thermal-sensor-cells，tsadc 是 1。
  • cooling-maps 的 trip 只能在同一个 zone 的 trips 里找，跨 zone 引用不通。

十六、调试过程：从不动到转起来 #

这是本篇最值钱的一段。素材记录的现场过程，我按时间顺序重排。

第一步，配好 io_domains。rk3399-io-domain.yaml 里 RK3399 需要配的 supply 有 bt656、audio、sdmmc、gpio1830，PMUGRF 下面还有 pmu1830。查 APIO4_VDD 在原理图上的来源，是 rk808 的 15 号引脚 VLDO8，输出 VCC_3V0，对应设备树里的 vcc_3v0。

dts
&io_domains {
        bt656-supply = <&vcc_1v8>;
        audio-supply = <&vcca1v8_codec>;
        sdmmc-supply = <&vcc_sdio>;
        gpio1830-supply = <&vcc_3v0>;
        status = "okay";
};

&pmu_io_domains {
        pmu1830-supply = <&vcc_3v0>;
        status = "okay";
};

素材的做法是「把所有要用到的电源域一次配齐」，图省事。工程上只要保证用到的那一路（这里是 gpio1830-supply）对就行。

GRF_IO_VSEL 这个寄存器在 GRF 偏移 0x0e640。写 1 对应 1.62~1.98V（典型 1.8V），写 0 对应 3.00~3.60V（典型 3.3V）。这一位配错，引脚要么输出不到位，要么直接被保护。寄存器位的具体字段名我没读到原文，写「未验证」。

第四步，上 PWM 和 pwm-fan，风扇不转。

素材这一阶段的记录只有一句原话：

text
开发板重新上电后，我们发现散热风扇并没有转动

素材里所有 root@rk3399 开头的输出，都是最终配置生效后重新上电抓的。中间几次失败的迭代没有留下串口日志，本篇不补。

原因在素材里写得很直接：缺 Thermal 相关的配置。pwm-fan 起来时 cur_state 是 0，cooling-levels[0] 是 0，占空比 0，引脚恒低，Q41 截止，风扇当然不转。这是设计行为，不是 bug——没有 governor 下指令，风扇就该待在 0 档。

第五步，不接 Thermal，先用用户态接口验证 PWM 通路本身通不通：

bash
root@rk3399:/#  echo 100 > /sys/devices/platform/pwm-fan/hwmon/hwmon1/pwm1

这一步很关键。它绕开 governor，直接给 pwm-fan 灌一个 0~255 的值。如果这里风扇转了，说明 PWM 输出、引脚复用、12V 供电全链路 OK，问题只在 Thermal 的绑定或配置上；如果这里也不转，就往回查硬件链路和 pinctrl。这次调试就是靠它把「PWM 问题」和「Thermal 问题」切开，省了很多时间。

第六步，单独验证 PWM 波形。用一个不接风扇的 pwmchip 来看 sysfs 接口怎么用：

bash
root@rk3399:/sys/class/pwm# ll /sys/class/pwm/
lrwxrwxrwx  1 root root 0 Mar 15  2023 pwmchip0 -> ../../devices/platform/ff420000.pwm/pwm/pwmchip0/
lrwxrwxrwx  1 root root 0 Mar 15  2023 pwmchip1 -> ../../devices/platform/ff420010.pwm/pwm/pwmchip1/
lrwxrwxrwx  1 root root 0 Mar 15  2023 pwmchip2 -> ../../devices/platform/ff420020.pwm/pwm/pwmchip2/
lrwxrwxrwx  1 root root 0 Mar 15  2023 pwmchip3 -> ../../devices/platform/ff420030.pwm/pwm/pwmchip3/

pwmchip1 就是风扇用的 ff420010.pwm。pwmchip0 是 ff420000.pwm，拿它做实验：

bash
root@rk3399:/sys/class/pwm/pwmchip0# echo 0 > export
root@rk3399:/sys/class/pwm/pwmchip0/pwm0# echo 100000 > period
root@rk3399:/sys/class/pwm/pwmchip0/pwm0# echo 50000 > duty_cycle
root@rk3399:/sys/class/pwm/pwmchip0/pwm0# echo normal > polarity
root@rk3399:/sys/class/pwm/pwmchip0/pwm0# echo 1 > enable

这一段是 100KHz、50% 占空比、正极性。四步顺序不能乱：先 period，再 duty_cycle（必须 ≤ period），再 polarity，最后 enable。

第七步，接 Thermal。tsadc 打开，cpu_thermal 加 cpu_warm、cpu_hot 两条 active trip 和对应 cooling-maps，cpu-supply 绑好，重新编译烧录。

起来后看 thermal 用户态接口：

bash
root@rk3399:~$ ll /sys/class/thermal/
lrwxrwxrwx  1 root root 0 Mar 15  2023 cooling_device0 -> ../../devices/virtual/thermal/cooling_device0/
lrwxrwxrwx  1 root root 0 Mar 15  2023 thermal_zone0 -> ../../devices/virtual/thermal/thermal_zone0/
lrwxrwxrwx  1 root root 0 Mar 15  2023 thermal_zone1 -> ../../devices/virtual/thermal/thermal_zone1/

风扇这个 cooling device 的档位：

bash
root@rk3399:~# cat /sys/class/thermal/cooling_device0/cur_state
0
root@rk3399:~# cat /sys/class/thermal/cooling_device0/max_state
5

max_state = 5 对上了 cooling-levels 的 6 个元素，说明 pwm-fan 注册成 cooling device 成功了。

第八步，用 emul_temp 灌一个假温度，验证 governor 有没有把档位下发给风扇：

bash
root@rk3399:/sys/class/thermal/thermal_zone0# cat temp
48750
root@rk3399:/sys/class/thermal/thermal_zone0# cat policy
step_wise
root@rk3399:/sys/class/thermal/thermal_zone0# cat available_policies
power_allocator step_wise
root@rk3399:/sys/class/thermal/thermal_zone0# cat cdev0/type
pwm-fan
root@rk3399:/sys/class/thermal/thermal_zone0# cat cdev0/max_state
5

当前 48.75℃，没到 55℃，cdev0/cur_state 是 0，风扇停。灌 55℃：

bash
root@rk3399:/sys/class/thermal/thermal_zone0# echo 55000 > emul_temp
root@rk3399:/sys/class/thermal/thermal_zone0# cat cdev0/cur_state
1

档位从 0 跳到 1，风扇上到第 1 档。到这一步，整条链路通了：tsadc 采温度 → zone 判断 trip → step_wise 选档 → pwm-fan 设占空比 → PWM 出波形 → 三极管 → 风扇转。

第九步，验证临界保护。灌 120℃：

bash
root@rk3399:/sys/class/thermal/thermal_zone0# echo 120000 > emul_temp

超过 cpu_crit 的 95℃，按设计会走 critical 关机。素材只给了命令，没记执行后的日志，这里也不替它补。

/sys/class/thermal/thermal_zone0 下的文件含义，挑常用的列：

文件 含义
temp 当前温度（毫摄氏度）。写 emul_temp 后读到的也是模拟值
emul_temp 模拟温度。非 0 时框架用这个值代替真实温度；写 0 恢复真实读数
mode enabled 表示按定时器取温；disabled 关掉
policy 当前 governor
available_policies 本 zone 可选的 governor
trip_point_N_temp / _hyst / _type 第 N 个 trip point 的三个字段，来自 dts
cdevN 第 N 个绑定的 cooling device
cdevN_trip_point 该 cdev 关联的 trip 在 trips 里的索引
cdevN_weight power_allocator 算 power 时的放大倍数
k_d k_i k_po k_pu integral_cutoff sustainable_power power_allocator 的 PID 参数，step_wise 下不用管

十七、常见故障与现象对照 #

现象 首要怀疑 怎么确认 怎么改
风扇完全不动，pwm-fan 已 probe 没接 Thermal，cur_state 一直是 0 cat cooling_device0/cur_state 接 trip + cooling-maps，或直接写 hwmon 的 pwm1
风扇完全不动，/sys/class/pwm 里没有对应 chip CONFIG_PWM_ROCKCHIP 没开，或 &pwm1 还是 disabled ls /sys/class/pwm/ 开配置，dts 里 status = "okay"
风扇完全不动，GPIO4_C6 无输出 io_domains 没配，gpio1830-supply 缺失 导 GPIO 写 1 看不看得到电平 补 io_domains 与 pmu_io_domains
echo 150 > export 失败 引脚被 pwm1 的 pinctrl-0 占成 func1 cat /sys/kernel/debug/pinctrl/*/pinmux-pins 要么关 pwm1，要么改用占空比 0 停风扇
档位往上调，转速反而下降 PWM 极性填反 看 pwms 第 4 项与 dts 极性注释 改成 0（PWM_POLARITY_NORMAL）
emul_temp 写了，cur_state 不动 trip 的 type 不是 active，或 cooling-maps 没绑 &fan cat trip_point_N_type、ls cdev0/ 补 active trip 与 map
max_state 不是 5 cooling-levels 元素个数不对 cat cooling_device0/max_state 对齐 cooling-levels
trip_point_2_type 这类文件缺失 type 字符串拼错，of_thermal 静默丢弃 数 trip 文件个数对不对 改成合法的四个类型之一
temp 一直是 0 或不变 tsadc 没开，或 thermal-sensors 的 channel 号错 cat thermal_zone0/temp 开 &tsadc，核对 <&tsadc 0> / <&tsadc 1>
温度一到 95℃ 直接重启 rockchip,hw-tshut-mode = <1> 但硬件没把 tsadc_int 接到 PMIC 复位脚 查原理图与 PMIC 复位脚连通性 改 0 走 CRU，或补硬件连线
风扇转了但一直全速 polarity 反了，低电平被算成有效 把风扇档位打到 0 看停不停 修极性
/sys/devices/platform/pwm-fan/hwmon/hwmon1 路径不存在 hwmon 编号变了 ls /sys/class/hwmon/ 别硬编码编号，用 hwmon* 通配

十八、易错点速查 #

易错点 正确做法
pwm_config() 参数顺序记成「周期、占空比」 是 pwm_config(pwm, duty_ns, period_ns)，占空比在前
duty_cycle 单位当百分比 是纳秒，且必须 ≤ period
cooling-levels 当 0~100 用 是 0~255，duty_cycle = period × level / 255
pwms 的周期填频率 填的是 ns 周期，20KHz 要填 50000
#pwm-cells 手改 控制器声明的是 3，消费者按 3 个 cell 写
pwm_get() 拿的句柄忘了 pwm_put() 用 devm_pwm_get() 走 devres 托管
用 memset 造 pwm_state 用 pwm_init_state() 拿初值再改字段
6.3 里找 pwm_set_polarity() 已废弃，极性走 pwm_state.polarity + pwm_apply_state()
6.3 里找 pwm_set_relative_rate() 6.3 没有，更晚的内核才有（确切版本未验证）
PWM 极性和 GPIO 的 active_low 混着调 是两个概念，风扇链路上只调 PWM 极性
fan-supply 当成 PWM 信号 是风扇供电 regulator，PWM 走 pwms
thermal-sensors 漏 channel 号 #thermal-sensor-cells = <1>，要写 <&tsadc 0>
cooling-device 限定符个数随手写 个数要等于目标设备 #cooling-cells，pwm-fan 是 2
trip 的 type 写 "Active" 大小写敏感，写 "active"
THERMAL_NO_LIMIT 当成 0 是 -1UL，表示不设限，min 位与 max 位含义不同
认为 pwm-fan probe 成功风扇就该转 没 governor 下指令时它就该待在 0 档
hwmon 编号硬编码成 hwmon1 用 ls /sys/class/hwmon/ 按 name 找
改了 pwm1 的 pinctrl-0 还想用 PWM pinctrl-0 决定引脚归属，改了就没 PWM 了
只配 gpio1830-supply 就以为 IO 域全好了 还有 pmu1830-supply，库里两套 power domain
以为 emul_temp 只在调试内核里存在 依赖 Thermal emulation mode support 配置项
