一、pinctrl 要解决什么：引脚只有一组，用途有十种 #

先看一块 S3C2440 的引脚表。GPB0 一根线，SoC 内部至少挂了三个消费者：GPIO、TOUT0（定时器 PWM 输出）、其他复用功能。GPB5~GPB8 四根线，既能当普通 IO，也能当 SPI 的一组信号。你把它配成 SPI，它就不是 GPIO；你把它配成 GPIO，SPI 那侧就没线可用。

硬件不会替你做仲裁。同一时刻，一根引脚的复用寄存器里只有一个功能号。谁最后写，谁说了算。没有统一框架的年代，这件事是这么烂掉的：

症状 根因
换一块板子就要重新编一份内核 引脚配置硬编码在板级 C 代码里
某个驱动突然不工作，查一天 另一个驱动 probe 时把引脚复用改走了
bootloader 里有一张巨表，内核里又抄一遍 配置没有唯一权威来源
同一 SoC 的两个产品不能共用一个 image 差异是引脚，不是芯片

pinctrl 子系统就是把这些收拢成一个框架：pin controller 驱动独占引脚寄存器，其他所有人只声明需求。消费者不写 GPBCON、不写 GPBUP，只在设备树里说「我要 gpb-5 到 gpb-8 这四根，功能号 1，上拉」，然后由内核在 probe 之前替你应用。

功能规格三条，来自内核文档 Documentation/pinctrl.txt（5.x 以后迁到 driver-api 目录，文件名有改动，具体路径未逐版核对）：

  1. 枚举系统中所有可控 pin；
  2. 管理 pin 复用（若干 pin 组成 pin group，共同构成某个功能）；
  3. 配置 pin 的电气特性（上下拉、驱动强度、转换速率等）。

三条之外还有一条隐含要求：冲突要能被发现。同一根 pin 被两个功能同时申请时，框架要报错，而不是让两个驱动互相踩。

二、GPIO 与 pinctrl 的分工边界 #

初学者最常见的误解：以为配了 GPIO 就是配了引脚。「配 GPIO」其实是两步，两步属于两个子系统。

维度 GPIO 子系统（gpiolib） pinctrl 子系统
回答的问题 这根线现在是高还是低 这根线归谁用、长什么样
操作对象 逻辑编号（gpio 19、gpiod） 物理引脚（pin 52、gpb-5）
核心数据结构 struct gpio_chip、struct gpio_desc struct pinctrl_desc、struct pinctrl_dev
典型寄存器 GPxDAT、方向位 GPxCON（复用）、GPxPUD（上下拉）、GPxDRV
典型 API gpiod_get、gpiod_set_value devm_pinctrl_get、pinctrl_select_state
设备树属性 gpios = <&gpb 5 GPIO_ACTIVE_HIGH> pinctrl-0 = <&myled_on>
冲突语义 同一根线只能被一个 consumer 申请 同一根线只能属于一个 function（视 strict）

正确的使用顺序是：先用 pin controller 把引脚复用成 GPIO 功能，再用 GPIO controller 把它配成输入/输出。顺序反了，你往 GPxDAT 写值不会生效，因为那根线的复用寄存器还指着别的外设。

S3C2440 上把 GPF7 配成上升沿中断，要动三处东西：

text
GPFCON   -> 复用为 EINT7      （pinctrl 的地盘）
EINTMASK -> 使能 EINT7 通道   （中断子系统的地盘）
INTMSK   -> 使能主中断 EINT4~7（中断子系统的地盘）

pinctrl 只负责第一步。后面两步没做，中断就是进不来——这是新手最常见的「配了 pinctrl 还是没中断」的原因。

S3C2440 的外部中断映射：

外部中断 引脚
EINT0 ~ EINT7 GPF0 ~ GPF7
EINT8 ~ EINT23 GPG0 ~ GPG15

三、pin、group、function 三个概念 #

这三个词是所有 pinctrl 文档的地基，混了后面全看不懂。

概念 是什么 由谁定义 数量级 设备树里的形态
pin 一根可复用的物理引脚 驱动用 pinctrl_pin_desc 数组描述 几十到几百 samsung,pins = "gpb-5" 里的最小单位
group 要一起切换的一组 pin 驱动通过 pctlops 枚举 多于 bank 数 &pinctrl_0 下一个子节点
function 一个硬件功能块（UART0 / I2C1 / PWM1） 驱动通过 pmxops 枚举 与 SoC 型号相关 子节点里的 samsung,pin-function = <2>

pin。core 只关心「有多少个 pin」，用自然数编号，后续所有操作都以编号为对象。编号怎么对应到物理引脚，完全是驱动自己的事：

c
struct pinctrl_pin_desc {
        unsigned int number;    /* 全局 pin 编号空间中唯一，给机器用 */
        const char *name;       /* 给人看；为 NULL 时 core 生成 "PIN<n>" */
        void *drv_data;         /* 每 pin 私有数据，core 完全不碰 */
};

取值原则两条：有利于写代码，有利于读懂。Samsung 取「bank 名-组内序号」（gpb-5），编号从本控制器的 pin_base 起连续分配；S3C2440 有 GPA~GPJ 十个 bank，拼成一张连续编号表。

group。SPI、I2C 这类功能必须同时控制多根 pin，所以 pin controller 以 group 为单位访问。子系统要能回答三个问题：有多少个 group、每个叫什么、每个包含哪些 pin。答案全在 struct pinctrl_ops 里（下一节展开）。

Samsung 的做法：设备树里每个 pin configuration 子节点 = 一个 group，group 名取「节点名 + -grp」，节点里的 samsung,pins 就是 group 成员。

group 与 bank 是两个层次。bank 是硬件寄存器分块（共用一套寄存器，特性相同），group 是功能上的一组引脚（可以跨 bank）。S3C2440 有 10 个 bank，group 数量远多于 10。

另一处容易读错的地方：素材里截图说「myled_on（4 个 pin）解析后每个 pin 各一条 group、group 名是 gpb-5」。这与上游 samsung_dt_node_to_map() 不符——一个设备树子节点生成一个 map 条目（mux 一条 + configs 一条），group 名带 -grp 后缀。见第十四章与附录勘误。

function。function 表示一个功能，对应一个硬件逻辑块。core 不关心 function 的形态，只要求驱动把全部候选 function 枚举出来（有编号、有名字）注册给它。

关键点：同一个 function 会映射到不同的 pin group。UART0 可以从 gph-0/gph-1 引出，也可以从 gph-8/gph-9 引出，这两组不能同时 active——芯片里 UART0 的逻辑电路只有一个。所以做 mux 设定时必须同时给出 func_selector 和 group_selector，这两个数就是 set_mux() 的两个入参。

分组的物理意义：SPI 用四根线，你不能只把其中一根切过去。group 就是「要么全切，要么不切」的最小单位。

四、struct pinctrl_desc：控制器怎么描述自己 #

pinctrl 的入口结构体。你把这三个 ops 填满、把 pin 数组填满，框架就认得你：

c
/* include/linux/pinctrl/pinctrl.h */
struct pinctrl_desc {
        const char *name;
        const struct pinctrl_pin_desc *pins;
        unsigned int npins;
        const struct pinctrl_ops *pctlops;
        const struct pinmux_ops *pmxops;
        const struct pinconf_ops *confops;
        struct module *owner;
#ifdef CONFIG_GENERIC_PINCONF
        unsigned int num_custom_params;
        const struct pinconf_generic_params *custom_params;
        const struct pin_config_item *custom_conf_items;
#endif
        bool link_consumers;
};
字段 必须？ 作用 填错的后果
name 是 控制器名，出现在 debugfs、pinctrl-devices 里 为空 → pinctrl_init_controller 直接 -EINVAL
pins 是 所有引脚描述符数组 编号重复 → pin %d already registered
npins 是 数组长度，一般 ARRAY_SIZE() 小于实际 → 后面的 pin 全部查不到
pctlops 是 group 枚举 + 设备树解析 缺 get_groups_count/get_group_name → pinctrl ops lacks necessary functions
pmxops 否 复用操作 为空 → 本控制器只能配电气属性，不能切功能
confops 否 电气属性操作 为空 → 所有 CONFIGS_* 类型 setting 无人处理
owner 一般 THIS_MODULE 模块引用计数 卸载模块时缺少引用保护
num_custom_params / custom_params / custom_conf_items 否 驱动私有电气参数，让 generic pinconf 认识它们 只能用在 confops->is_generic = true 的控制器
link_consumers 否 为 true 时在 controller 与 consumer 之间建 device link，约束 suspend/resume 顺序 漏掉它，睡眠时序会反

三个 ops 指针就是 core 与驱动之间的全部契约：core 负责流程，驱动负责填表。

pinctrl_dev 是 core 侧的实例，provider 注册后拿到的就是它：node 挂进全局 pinctrl_devices 链表，desc 指回你自己填的那份描述，pin_desc_tree 是「pin 编号 → 描述符」的 radix tree，gpio_ranges 是第二套编号空间的映射区段，driver_data 是你注册时传进去的私有指针。同一个控制器维护两套编号，这就是第十五章那个「后门」的代价。

五、struct pinctrl_ops 与 pinmux_ops #

5.1 pinctrl_ops：group 枚举 + 设备树解析 #

c
/* include/linux/pinctrl/pinctrl.h */
struct pinctrl_ops {
        int (*get_groups_count) (struct pinctrl_dev *pctldev);
        const char *(*get_group_name) (struct pinctrl_dev *pctldev,
                                       unsigned int selector);
        int (*get_group_pins) (struct pinctrl_dev *pctldev,
                               unsigned int selector,
                               const unsigned int **pins,
                               unsigned int *num_pins);
        void (*pin_dbg_show) (struct pinctrl_dev *pctldev, struct seq_file *s,
                              unsigned int offset);
        int (*dt_node_to_map) (struct pinctrl_dev *pctldev,
                               struct device_node *np_config,
                               struct pinctrl_map **map, unsigned int *num_maps);
        void (*dt_free_map) (struct pinctrl_dev *pctldev,
                             struct pinctrl_map *map, unsigned int num_maps);
};
成员 必须？ 作用 备注
get_groups_count 是 返回 group 总数，相当于数组长度 缺这个 → 注册失败
get_group_name 是 返回指定 selector 的 group 名 缺这个 → 注册失败
get_group_pins 否 返回 group 内的 pin 编号数组与个数 缺它，pingroups 里会出现 [ERROR GETTING PINS]
pin_dbg_show 否 给 debugfs 的 pins 文件追加每 pin 的私有信息 只影响调试体验
dt_node_to_map 否 把设备树上的 pin configuration 节点翻成 pinctrl_map 数组 不支持设备树时可以没有，但 DT 平台必须有
dt_free_map 否 释放上面生成的 map 有 dt_node_to_map 就得配对实现

dt_node_to_map 是这一层里唯一有「解释权」的回调。设备树子节点的格式完全由你的驱动定义，因为解析也是你写的。Samsung 的格式是 samsung,pins + samsung,pin-function + 几个 samsung,pin-*；Rockchip 的格式是 rockchip,pins = <bank pin func &phandle>；NXP 又是另一套。看别人芯片的 dts 时，不要套 Samsung 的结构。

三个查询回调几乎是纯 getter，只是把驱动私有数组按 selector 下标取出来。Samsung 的 samsung_get_group_count() 就是 pinctrl_dev_get_drvdata(pctldev)->nr_groups，samsung_get_group_name() 就是 ...->pin_groups[selector].name。pinctrl_dev_get_drvdata() 是它们的共同起点：从 core 的实例里把注册时传进去的私有数据拿回来。这就是「core 完全不知道 pins 数组内容」的具体形态——core 只存指针，解释权归驱动。

5.2 pinmux_ops：有哪些功能，怎么切 #

c
/* include/linux/pinctrl/pinmux.h */

        const char *(*get_function_name) (struct pinctrl_dev *pctldev,
                                          unsigned int selector);
        int (*get_function_groups) (struct pinctrl_dev *pctldev,
                                    unsigned int selector,
                                    const char * const **groups,
                                    unsigned int *num_groups);
        bool (*function_is_gpio) (struct pinctrl_dev *pctldev,
                                  unsigned int selector);
        int (*set_mux) (struct pinctrl_dev *pctldev, unsigned int func_selector,
                        unsigned int group_selector);
        int (*gpio_request_enable) (struct pinctrl_dev *pctldev,
                                    struct pinctrl_gpio_range *range,
                                    unsigned int offset);
        void (*gpio_disable_free) (struct pinctrl_dev *pctldev,
                                   struct pinctrl_gpio_range *range,
                                   unsigned int offset);
        int (*gpio_set_direction) (struct pinctrl_dev *pctldev,
                                   struct pinctrl_gpio_range *range,
                                   unsigned int offset, bool input);

};
成员 必须？ 作用
get_functions_count 是 function 总数
get_function_name 是 指定 function 的名字
get_function_groups 是 指定 function 占用的 group 名列表（可以多个）
set_mux 是 真正写复用寄存器：把 group_selector 那组线切到 func_selector
request / free 否 申请/释放单根 pin 的使用权，做互斥检查
function_is_gpio 否 告诉框架某个 function 就是 GPIO 功能；配合 strict 使用
gpio_request_enable / gpio_disable_free / gpio_set_direction 否 给 gpiolib 开的加速通道，第十五章展开
strict 否 为 true 时禁止同一 pin 同时当 GPIO 和其他功能用

strict 值得单独说。默认 false，core 允许一根 pin 既被某个功能占着、又作为 GPIO 申请（有些 SoC 硬件真支持「外设在用但我还想读一下电平」）；置 true 就强制互斥，冲突直接返回错误，而不是等出现莫名其妙的现象。

Samsung 的 set_mux 落到底层就是一个 for 循环：从 pin_groups[group].pins 取 group 成员，用 pin_to_reg_bank() 定位 bank 与组内偏移，按 bank->func_width（S3C2440 的 GPB/GPF 是每 pin 2 bit，某些 bank 4 bit）算出 mask 与 shift，readl 后先清位再或入 pin_groups[group].func，最后 writel。宽度写错，一个 pin 的复用会把隔壁 pin 一起改掉；功能域超过 32 位时还要 reg += 4 跳到第二个 CON。

六、struct pinconf_ops：电气属性怎么配 #

pinmux 管「这根线归谁」，pinconf 管「这根线电气上长什么样」。上拉、下拉、高阻、驱动强度、转换速率（slew rate）都在这里：

c
/* include/linux/pinctrl/pinconf.h */
struct pinconf_ops {
#ifdef CONFIG_GENERIC_PINCONF
        bool is_generic;
#endif
        int (*pin_config_get) (struct pinctrl_dev *pctldev,
                               unsigned int pin, unsigned long *config);
        int (*pin_config_set) (struct pinctrl_dev *pctldev,
                               unsigned int pin, unsigned long *configs,
                               unsigned int num_configs);
        int (*pin_config_group_get) (struct pinctrl_dev *pctldev,
                                     unsigned int selector, unsigned long *config);
        int (*pin_config_group_set) (struct pinctrl_dev *pctldev,
                                     unsigned int selector, unsigned long *configs,
                                     unsigned int num_configs);
        void (*pin_config_dbg_show) (struct pinctrl_dev *pctldev,
                                     struct seq_file *s, unsigned int offset);
        void (*pin_config_group_dbg_show) (struct pinctrl_dev *pctldev,
                                           struct seq_file *s, unsigned int selector);
        void (*pin_config_config_dbg_show) (struct pinctrl_dev *pctldev,
                                            struct seq_file *s, unsigned long config);
};
成员 必须？ 作用
is_generic 否 为 true 表示控制器吃 generic pinconf 那套标准参数（PIN_CONFIG_BIAS_PULL_UP 等），由 core 帮你解析设备树
pin_config_get 是 读单根 pin 的配置。参数不支持返回 -ENOTSUPP，支持但当前禁用返回 -EINVAL
pin_config_set 是 配单根 pin，一次可以给多个 config
pin_config_group_get 是 读整组配置，返回值约定同上
pin_config_group_set 是 配整组，Samsung 的实现就是遍历组内 pin 逐个调 samsung_pinconf_set
pin_config_dbg_show 否 debugfs pins 文件里每 pin 的附加信息
pin_config_group_dbg_show 否 debugfs pingroups 文件里每组的附加信息
pin_config_config_dbg_show 否 把一个 config 数值翻译成人话（比如 bias-pull-up），调试时很有用

pinctrl core 完全不关心配置项的内容是什么。它只提供 get/set 的通用机制；那个整数代表什么、寄存器位怎么摆，是驱动自己的事。整个子系统贯彻「参数是不透明整数」这个原则。

这不是偷懒。电气参数的厂商编码方式千差万别：有的直接是位域值，有的是查表索引。core 若想统一解释，就得给每家写一套翻译，那才是真的灾难。

Samsung 的编码很直白，类型塞低 8 位、值塞高 8 位，PINCFG_PACK(type, value) 就是 ((value) << 8) | type。反查打包动作：pin-pud = <1> 被打成 (1 << 8) | PINCFG_TYPE_PUD，而 PINCFG_TYPE_PUD 在 enum pincfg_type 里排第 2（FUNC=0、DAT=1、PUD=2），所以正确值是 258 = 0x102。素材截图写「configs = [770, 1]」是错的：770 = 0x302 = (3 << 8) | 2，类型对但值是 3，而 pin-pud 取 3 并不是上拉。见附录。

两个 ops 的分界线整理成一张表：

维度 pinmux pinconf
管什么 这根线归谁 这根线电气上长什么样
操作单位 function + group pin 或 group
参数形态 两个 selector（func、group） 不透明整数数组
冲突语义 有，一根 pin 同时只能给一个 function 无冲突概念，后写覆盖前写
典型寄存器 GPxCON GPxPUD、GPxDRV、GPxSR
先后关系 必须先定功能 相对独立，但顺序有讲究

最后一行在实战里很重要：先把驱动强度配好，再把功能从 GPIO 切到 I2C，某些 SoC 会在切换瞬间把电气配置寄存器复位。所以 map 数组里的顺序习惯写成「先 mux，后 conf」——而 6.1 以后的 pinctrl_commit_state() 直接把这件事写进了代码：第一轮只做 MUX，第二轮才做 CONFIGS（第十一章）。

七、pin controller 的注册 #

Samsung 的 samsung_pinctrl_register() 是教科书式的最小实现，五步：

c
static int samsung_pinctrl_register(struct platform_device *pdev,
                                    struct samsung_pinctrl_drv_data *drvdata)
{
        struct pinctrl_desc *ctrldesc = &drvdata->pctl;

        /* 1. 填 pinctrl_desc：三个 ops 是 core 唯一的入口 */
        ctrldesc->name    = "samsung-pinctrl";
        ctrldesc->owner   = THIS_MODULE;
        ctrldesc->pctlops = &samsung_pctrl_ops;
        ctrldesc->pmxops  = &samsung_pinmux_ops;
        ctrldesc->confops = &samsung_pinconf_ops;

        /* 2. 分配并填满 pin 描述符：number = pin + ctrl->base，
         *    name = "<bank>-<pin>"，与 dts 里 samsung,pins 的写法对应 */
        ctrldesc->pins  = pindesc = devm_kzalloc(&pdev->dev,
                                sizeof(*pindesc) * drvdata->ctrl->nr_pins, GFP_KERNEL);
        ctrldesc->npins = drvdata->ctrl->nr_pins;
        for (pin = 0; pin < ctrldesc->npins; pin++)
                pindesc[pin].number = pin + drvdata->ctrl->base;
        /* ... 按 bank 逐 pin sprintf(pin_names, "%s-%d", bank->name, pin) ... */

        /* 3. 注册 —— 核心动作就这一行 */
        drvdata->pctl_dev = pinctrl_register(ctrldesc, &pdev->dev, drvdata);
        if (!drvdata->pctl_dev)
                return -EINVAL;

        /* 4. 建 gpio range 供 gpiolib 反查 pin（老写法，见第十五章） */
        drvdata->grange.base  = drvdata->ctrl->base;
        drvdata->grange.npins = drvdata->ctrl->nr_pins;
        drvdata->grange.gc    = drvdata->gc;
        pinctrl_add_gpio_range(drvdata->pctl_dev, &drvdata->grange);

        /* 5. 解析设备树，把子节点变成 group 与 function */
        return samsung_pinctrl_parse_dt(pdev, drvdata);
}

base 解决全局编号问题：系统里有多个 pin controller 时，A 管 32 个 pin、B 管 64 个，统一编号后 A 占 0~31、B 占 32~95，B 的 pin_base 就是 32。

pinctrl_register() 本身只是两段：先 pinctrl_init_controller()，再 pinctrl_enable()；后者失败时返回 ERR_PTR。

pinctrl_init_controller() 里依次做：校验 name 非空 → 分配 pinctrl_dev → 初始化 radix tree 与 gpio_ranges → pinctrl_check_ops() 查 pctlops → pinmux_check_ops() / pinconf_check_ops() 查另外两张表 → pinctrl_register_pins() 逐个注册 pin（每个 pin 分配 struct pin_desc 并 radix_tree_insert() 进 pin_desc_tree）。任一步失败整个注册回滚。pinctrl_enable() 则负责 claim hogs（pin controller 也可以给自己节点下的 pinctrl-0 定义状态）、挂进全局 pinctrl_devices 链表、建 debugfs。

几点实战经验：

  • pinctrl_register() 的注释明确写了它「已知有问题」：驱动回调会在驱动还没拿到 pinctrl_dev 句柄时就被调用。新代码用 devm_pinctrl_register_and_init() + pinctrl_enable() 两段式更稳。
  • 第 4 步手工 pinctrl_add_gpio_range() 是老写法。新驱动在 GPIO 节点上写 gpio-ranges，让 gpiolib 自己建（第十五章）。
  • 注册必须早于任何 consumer probe。Samsung 用 postcore_initcall() 注册 platform driver，就是为了抢在其他外设前面。
  • pinctrl_register() 返回值不同版本不一致：3.7 的老代码判断 !pctl_dev，5.x 以后要判断 IS_ERR()。迁移代码时这里容易漏。

八、pinctrl 状态的申请：default、idle、sleep #

「引脚状态」是这个子系统的核心抽象：一组 pin（或 group）+ 一个 function + 一组电气配置，合起来构成设备的一个状态。consumer 只说「帮我切到 sleep 那个状态」，怎么切是 pin controller 的事。

状态之上还有个持有者，一个设备一份：

c
/* drivers/pinctrl/core.h（节选） */
struct pinctrl {
        struct list_head node;        /* 挂进全局 pinctrl_list */
        struct device *dev;
        struct list_head states;      /* 本设备的全部 state */
        struct pinctrl_state *state;  /* 当前生效的 state */
        struct list_head dt_maps;     /* 从设备树解析出的 map 集合 */
        struct kref users;            /* 引用计数，get/put 配对增减 */
};

struct pinctrl_state {
        struct list_head node;        /* 挂进 holder 的 states 链表 */
        const char *name;             /* default / idle / sleep / 自定义 */
        struct list_head settings;    /* 本状态由若干 setting 组成 */
};

内核预定义四个标准状态名（include/linux/pinctrl/pinctrl-state.h）：PINCTRL_STATE_DEFAULT = "default"、PINCTRL_STATE_INIT = "init"、PINCTRL_STATE_IDLE = "idle"、PINCTRL_STATE_SLEEP = "sleep"。

状态 宏 谁在什么时刻应用 典型用途
default PINCTRL_STATE_DEFAULT pinctrl_bind_pins() 在 probe 之前；pinctrl_init_done() 在 probe 之后兜底 引脚处于「设备可用」状态：复用正确、上拉正确
init PINCTRL_STATE_INIT pinctrl_bind_pins() 优先于 default 防止 probe 期间引脚毛刺。probe 结束后如果还停在 init，自动切到 default
idle PINCTRL_STATE_IDLE pinctrl_pm_select_idle_state()，一般在 pm_runtime_suspend 系统松弛但没睡死，时钟已门控
sleep PINCTRL_STATE_SLEEP pinctrl_pm_select_sleep_state()，一般在 .suspend() 最低功耗态：把引脚切成 GPIO 并钉住电平

init 的设计意图写在头文件注释里：有些设备在 probe 之前就被切到工作功能会产生毛刺（比如 LCD 背光、音频功放），那就先给它一个「安静」的 init 状态，等 probe 完成再切 default。这两个状态的切换时机是 5.x 才补齐的（3.x 只有 default 生效、init 直接顶替，见第十三章对照表）。

consumer 侧的四个 API 全在 include/linux/pinctrl/consumer.h：pinctrl_get() / devm_pinctrl_get() 拿 holder，pinctrl_put() 还回去，pinctrl_lookup_state(p, name) 按名字找状态，pinctrl_select_state(p, state) 应用状态。

三个必须记住的细节：

  1. 第一次 pinctrl_get() 很贵。它要读设备树、逐条解析 phandle、建 map、再把每条 map 变成 setting。所以别在热路径里反复 get。
  2. 多次 get 不会重复分配。pinctrl_get() 内部先用 find_pinctrl() 按 dev 查已有 holder，找到就把 users 引用计数加一。pinctrl_put() 减一，减到 0 才释放全部资源。get/put 必须配对。
  3. pinctrl_select_state() 是唯一真正碰硬件的接口。它遍历 settings，按类型分派到 set_mux 或 pin_config_set。

状态名可以自定义。pinctrl_lookup_state() 就是拿字符串在 p->states 链表里 find_state() 比对，找不到就返回 ERR_PTR(-ENODEV)——除非 pinctrl_provide_dummies() 开过口子，那会现场造一个空状态，给「没有 pinctrl 驱动却调了 pinctrl API」的老平台兜底。新平台用不到。

九、设备树里的 pinctrl 绑定 #

9.1 pin bank：一个 GPIO 端口一个节点 #

pin controller 节点的子节点分两类。第一类是 bank 描述，它同时是一个 GPIO 控制器：

dts
gpa: gpa {
    gpio-controller;          /* 我是 GPIO 控制器 */
    #gpio-cells = <2>;        /* 引用我时用 2 个数：引脚号 + 极性 */
};
gpf: gpf {
    gpio-controller;
    #gpio-cells = <2>;
    interrupt-controller;     /* 我还能当中断控制器 */
    #interrupt-cells = <2>;
};

S3C2440 只有 GPA~GPJ 十组，外部中断只有 GPF、GPG 两组。设备树里多写了 GPL/GPK，probe 时就会去访问不存在的寄存器。

9.2 pin group：一组引脚的复用与电气配置 #

第二类子节点是 pin configuration，格式由驱动的 dt_node_to_map 决定。Samsung 的写法：

dts
&pinctrl_0 {
    uart0_data: uart0-data {
        samsung,pins = "gph-2", "gph-3";   /* 组名-组内编号，全小写 */
        samsung,pin-function = <2>;         /* 复用功能号 2 = UART */
    };
    myled_on: myled-on {
        samsung,pins = "gpb-5", "gpb-6", "gpb-7", "gpb-8";
        samsung,pin-function = <1>;         /* 1 = 输出 */
        samsung,pin-val = <0>;              /* 初始电平 0 */
        samsung,pin-pud = <1>;              /* 上拉 */
    };
};

Samsung 平台认的属性一共就这五个（来自 pinctrl-samsung.c 的 cfg_params[] 表）：

属性 含义 映射到 pincfg_type 取值范围
samsung,pins 引脚列表，格式 "组名-组内编号"，必须小写 不适用（只用来找 group） 形如 "gpb-5"
samsung,pin-function 复用功能号，对应手册的 function 列 不打包，走 MUX 按 SoC 手册
samsung,pin-val 输出初始值 PINCFG_TYPE_DAT 0 / 1
samsung,pin-pud 上下拉 PINCFG_TYPE_PUD 0 无、1 上拉、2 下拉、3 保留
samsung,pin-drv 驱动强度 PINCFG_TYPE_DRV 按 SoC
samsung,pin-con-pdn 掉电（power down）时的引脚功能 PINCFG_TYPE_CON_PDN 按 SoC
samsung,pin-pud-pdn 掉电时的上下拉 PINCFG_TYPE_PUD_PDN 按 SoC

素材里把 samsung,pin-drv-pdn 写成独立属性，与上游 cfg_params[] 表不符——掉电相关的只有 pin-con-pdn 和 pin-pud-pdn 两个。见附录勘误。

一个子节点能配几条 map，是驱动 dt_node_to_map 说了算。Samsung 的逻辑是「所有 config 合一条，function 单独一条」：先数出子节点上有几个 samsung,pin-* 属性，有几个就把它们打包成一条 CONFIGS_GROUP；如果还有 samsung,pin-function，再单独加一条 MUX_GROUP；两条都没有就直接 -EINVAL 报 node %s does not have either config or function configurations。

这条「一个子节点最多两条 map」的规则很实用：翻 pinctrl-maps 时看到同一个 group 名出现两次，一次 MUX_GROUP 一次 CONFIGS_GROUP，不是重复配置。

9.3 client 侧：pinctrl-names + pinctrl-N #

dts
&uart_0 {
    status = "okay";
    pinctrl-names = "default";          /* 状态名数组 */
    pinctrl-0 = <&uart0_data>;          /* 第 0 个状态引用哪些 group */
};

&myled {
    pinctrl-names = "default", "myled_off";
    pinctrl-0 = <&myled_on>;            /* 默认态：点亮 */
    pinctrl-1 = <&myled_off>;           /* 状态 1：熄灭 */
};

规则只有一条：pinctrl-N 的下标 N 就是 pinctrl-names 数组的下标。一个状态可以引用多个 group（pinctrl-1 = <&a &b>），这些 group 会被 pinctrl_dt_to_map() 循环展开成多条 map。

真实板子上能看到三个状态一起写的例子。RK3399 的 tsadc 用 pinctrl-names = "init", "default", "sleep"，pinctrl-0/1/2 分别指向 &otp_pin、&otp_out、&otp_pin——init 先让引脚安静，default 切成工作功能，sleep 回到安全态。RK3399 的 pwm1 则只有一个状态，而且引脚配置是 <bank pin func &phandle> 四元组：

dts
pwm1 {
    pwm1_pin: pwm1-pin {
        rockchip,pins = <4 RK_PC6 1 &pcfg_pull_none>;
    };
    pwm1_pin_pull_down: pwm1-pin-pull-down {
        rockchip,pins = <4 RK_PC6 1 &pcfg_pull_down>;
    };
};

同一个 GPIO4_C6，一个子节点配成无上下拉，一个配成下拉。格式完全不同，但 consumer 侧写法一模一样——pinctrl-names + pinctrl-N，因为 consumer 侧的解析是 core 做的（pinctrl_dt_to_map），只有子节点内部格式归驱动。

十、pinctrl-0、pinctrl-names 的语义 #

这一节把「名字、下标、phandle」三者的关系钉死，因为报错十次有八次错在这儿。

pinctrl_dt_to_map() 的循环就是全部真相：

c
int pinctrl_dt_to_map(struct pinctrl *p, struct pinctrl_dev *pctldev)
{
        struct device_node *np = p->dev->of_node;

        if (!np) {
                if (of_have_populated_dt())
                        dev_dbg(p->dev, "no of_node; not parsing pinctrl DT\n");
                return 0;
        }
        of_node_get(np);

        /* 从 pinctrl-0 开始，一直往后找，找不到就断 */
        for (state = 0; ; state++) {
                propname = kasprintf(GFP_KERNEL, "pinctrl-%d", state);
                prop = of_find_property(np, propname, &size);
                kfree(propname);
                if (!prop) {
                        if (state == 0) {
                                ret = -ENODEV;      /* 连 pinctrl-0 都没有 */
                                goto err;
                        }
                        break;
                }
                list = prop->value;
                size /= sizeof(*list);              /* size = 本状态的 phandle 个数 */

                /* 从 pinctrl-names 取第 state 个名字，取不到就用属性名后缀 */
                if (of_property_read_string_index(np, "pinctrl-names",
                                                  state, &statename) < 0)
                        statename = prop->name + strlen("pinctrl-");

                for (config = 0; config < size; config++) {
                        phandle = be32_to_cpup(list++);
                        np_config = of_find_node_by_phandle(phandle);
                        if (!np_config) {
                                dev_err(p->dev, "prop %s index %i invalid phandle\n",
                                        prop->name, config);
                                ret = -EINVAL;
                                goto err;
                        }
                        ret = dt_to_map_one_config(p, pctldev, statename, np_config);
                        of_node_put(np_config);
                        if (ret == 1)           /* phandle 指的是自己，跳过 */
                                continue;
                        if (ret < 0)
                                goto err;
                }

                /* 属性存在但一个 phandle 都没写，也要造个 dummy state */
                if (!size && dt_remember_dummy_state(p, statename) < 0)
                        goto err;
        }
        return 0;
err:
        pinctrl_dt_free_maps(p);
        return ret;
}

从这段代码能抽出六条硬规则：

规则 代码依据 违反后的现象
下标从 0 连续写，中间断一个，后面的全丢 循环遇到不存在的 pinctrl-N 直接 break 写了 pinctrl-0、pinctrl-2 却漏 pinctrl-1，2 号状态静默失效
没有 pinctrl-0 就没有任何状态 state == 0 时 ret = -ENODEV 驱动里 devm_pinctrl_get() 拿到 -ENODEV，日志 no pinctrl handle
pinctrl-names 缺了也能跑 名字回退成属性名后缀 状态名变成 "0"、"1"，pinctrl_lookup_state(p, "default") 找不到
名字和下标必须同步改 of_property_read_string_index(np, "pinctrl-names", state, ...) 报 -EINVAL
phandle 必须是 pin controller 子节点 dt_to_map_one_config() 顺着 parent 往上找 controller -EPROBE_DEFER（controller 还没注册）或 -ENODEV
一个状态可以有多个 phandle for (config = 0; config < size; config++) 不违反规则，但两组互相冲突时会由 pinmux 报占用

dt_to_map_one_config() 往上找 controller 的循环有三个结局：-EPROBE_DEFER（模块化内核里 controller 还没加载，稍后重试）、-ENODEV（到根节点仍没找到，硬错误）、1（这个 phandle 指的是设备自己，调用方 continue 跳过——否则 hogs 场景下设备等自己，永远探不完）。

顺带一个不太常见的属性：节点上写 pinctrl-use-default 后，reparent 到根的搜索不会改成 defer，而直接报 -ENODEV。给「控制器驱动永远不会有」的叶子节点用。

十一、pinctrl_select_state 的调用链 #

前面所有准备（设备树解析、map、setting）都只是为了这一刻：把状态真正写进寄存器。

c
int pinctrl_select_state(struct pinctrl *p, struct pinctrl_state *state)
{
        if (p->state == state)
                return 0;

        return pinctrl_commit_state(p, state);
}

pinctrl_commit_state() 在 6.1 到 6.8 的实现：先卸旧状态的 mux，再用两轮遍历应用新状态——第一轮只做 mux，第二轮才做 conf。

c
static int pinctrl_commit_state(struct pinctrl *p, struct pinctrl_state *state)
{
        struct pinctrl_setting *setting, *setting2;
        struct pinctrl_state *old_state = READ_ONCE(p->state);

        /* 1. 撤掉旧状态的 mux，把 group 所有权交还 */
        if (old_state)
                list_for_each_entry(setting, &old_state->settings, node)
                        if (setting->type == PIN_MAP_TYPE_MUX_GROUP)
                                pinmux_disable_setting(setting);
        p->state = NULL;

        /* 2. 第一轮：只应用 MUX_GROUP，先把「这根线归谁」定下来 */
        list_for_each_entry(setting, &state->settings, node) {
                switch (setting->type) {
                case PIN_MAP_TYPE_MUX_GROUP:
                        ret = pinmux_enable_setting(setting);
                        break;
                case PIN_MAP_TYPE_CONFIGS_PIN:
                case PIN_MAP_TYPE_CONFIGS_GROUP:
                        ret = 0;                /* 留到第二轮 */
                        break;
                default:
                        ret = -EINVAL;
                        break;
                }
                if (ret < 0)
                        goto unapply_new_state;
                if (p != setting->pctldev->p)   /* hogs 不建自环 link */
                        pinctrl_link_add(setting->pctldev, p->dev);
        }

        /* 3. 第二轮：再应用电气属性，避免切功能时把配置冲掉 */
        list_for_each_entry(setting, &state->settings, node) {
                ret = (setting->type == PIN_MAP_TYPE_MUX_GROUP) ? 0
                    : (setting->type == PIN_MAP_TYPE_CONFIGS_PIN ||
                       setting->type == PIN_MAP_TYPE_CONFIGS_GROUP)
                              ? pinconf_apply_setting(setting) : -EINVAL;
                if (ret < 0)
                        goto unapply_new_state;
                if (p != setting->pctldev->p)
                        pinctrl_link_add(setting->pctldev, p->dev);
        }

        p->state = state;
        return 0;

unapply_new_state:
        dev_err(p->dev, "Error applying setting, reverse things back\n");
        list_for_each_entry(setting2, &state->settings, node) {
                if (&setting2->node == &setting->node)
                        break;
                if (setting2->type == PIN_MAP_TYPE_MUX_GROUP)
                        pinmux_disable_setting(setting2);
        }
        if (old_state)
                pinctrl_select_state(p, old_state);   /* 回滚到旧状态 */
        return ret;
}

这段代码有三层含义：

  1. 两轮遍历就是第六章那句「先 mux 后 conf」的代码化。3.x / 4.x 是一轮遍历、按链表顺序执行，能不能保证顺序取决于 dt_node_to_map 造 map 的顺序；6.x 把顺序写死了。
  2. 失败会回滚。回滚粒度只到 pinmux_disable_setting()——注释也承认「我们没法真的 un-mux 一根 pin」，但会把 p->state 清空再重新 select 一遍旧状态。
  3. pinctrl_link_add() 建立 device link。条件是 pctldev->desc->link_consumers == true，作用是让 PM 框架知道 consumer 依赖 controller，挂起顺序不会反。

setting 类型与最终回调的对应关系，就是设备树属性和驱动的映射表：

dts 属性 map 类型 最终调用
samsung,pin-function PIN_MAP_TYPE_MUX_GROUP pinmux_ops->set_mux
samsung,pin-val / pin-pud / pin-drv PIN_MAP_TYPE_CONFIGS_GROUP pinconf_ops->pin_config_group_set
兼容老平台静态表的单 pin 配置 PIN_MAP_TYPE_CONFIGS_PIN pinconf_ops->pin_config_set
子节点存在但没有 phandle PIN_MAP_TYPE_DUMMY_STATE 无

pinctrl_select_state 还有几个兄弟函数，做 PM 时天天见：

API 作用 典型调用点
pinctrl_select_default_state(dev) 切回 default 手动恢复
pinctrl_pm_select_default_state(dev) 同上，PM 专用入口 .resume() / pm_runtime_resume
pinctrl_pm_select_idle_state(dev) 切到 idle pm_runtime_suspend
pinctrl_pm_select_sleep_state(dev) 切到 sleep .suspend()

这四个函数全部先看 dev->pins 是否为空，再看对应的 state 是不是 ERR_PTR，都齐了才 select。所以驱动里没写一句 pinctrl 代码，PM 状态也会跟着自动切换——这就是第十二章要讲的绑定机制。

十二、设备和 pinctrl 的绑定时机 #

先问一个问题：驱动里一行 pinctrl 代码都没写，为什么引脚还是配好了？

因为绑定发生在 probe 之前，由设备模型代劳。完整调用链（6.x 路径，3.x 的差异点在下一章标出）：

    device_add

          __device_attach

三个节点值得盯住：

  • platform_match：先尝试 OF 匹配（compatible），再 ACPI，再 id_table，最后 fallback 比名字。pin controller 驱动也是普通 platform driver，走同一条路。
  • pinctrl_bind_pins：在 drv->probe 之前。这就是「驱动里没有 pinctrl 代码，引脚却是对的」的全部原因。
  • pinctrl_init_done：在 probe 返回之后，负责把「probe 期间被 init 状态占着」的引脚切到 default。

十三、pinctrl_bind_pins：设备 probe 前发生了什么 #

c
/* drivers/base/pinctrl.c */
int pinctrl_bind_pins(struct device *dev)
{
        int ret;

        if (dev->of_node_reused)
                return 0;

        /* 1. 为 consumer 分配 dev_pin_info，挂到 dev->pins */
        dev->pins = devm_kzalloc(dev, sizeof(*(dev->pins)), GFP_KERNEL);
        if (!dev->pins)
                return -ENOMEM;

        /* 2. 拿 holder（第一次会解析设备树、建 map） */
        dev->pins->p = devm_pinctrl_get(dev);
        if (IS_ERR(dev->pins->p)) {
                dev_dbg(dev, "no pinctrl handle\n");
                ret = PTR_ERR(dev->pins->p);
                goto cleanup_alloc;
        }

        /* 3. 找 default 状态；没有 default 不算错 */
        dev->pins->default_state = pinctrl_lookup_state(dev->pins->p,
                                                        PINCTRL_STATE_DEFAULT);
        if (IS_ERR(dev->pins->default_state)) {
                dev_dbg(dev, "no default pinctrl state\n");
                ret = 0;
                goto cleanup_get;
        }

        /* 4. 有 init 就用 init，否则用 default */
        dev->pins->init_state = pinctrl_lookup_state(dev->pins->p,
                                                     PINCTRL_STATE_INIT);
        if (IS_ERR(dev->pins->init_state)) {
                dev_dbg(dev, "no init pinctrl state\n");
                ret = pinctrl_select_state(dev->pins->p, dev->pins->default_state);
        } else {
                ret = pinctrl_select_state(dev->pins->p, dev->pins->init_state);
        }
        if (ret) {
                dev_dbg(dev, "failed to activate initial pinctrl state\n");
                goto cleanup_get;
        }

#ifdef CONFIG_PM
        /* 5. 睡眠态与空闲态，可选；缺了不算错 */
        dev->pins->sleep_state = pinctrl_lookup_state(dev->pins->p, PINCTRL_STATE_SLEEP);
        if (IS_ERR(dev->pins->sleep_state))
                dev_dbg(dev, "no sleep pinctrl state\n");
        dev->pins->idle_state = pinctrl_lookup_state(dev->pins->p, PINCTRL_STATE_IDLE);
        if (IS_ERR(dev->pins->idle_state))
                dev_dbg(dev, "no idle pinctrl state\n");
#endif
        return 0;

cleanup_get:
        devm_pinctrl_put(dev->pins->p);
cleanup_alloc:
        devm_kfree(dev, dev->pins);
        dev->pins = NULL;

        if (ret == -EPROBE_DEFER)       /* controller 未就绪：重试 */
                return ret;
        if (ret == -EINVAL)             /* phandle 无效 / 应用失败：硬错误 */
                return ret;
        return 0;                       /* -ENOENT 之类：当作没配 pinctrl */
}

dev->pins 指向的 struct dev_pin_info（include/linux/pinctrl/devinfo.h）只有五个成员：struct pinctrl *p（state holder）、default_state、init_state（5.x 起加入）、sleep_state、idle_state，后两个只在 CONFIG_PM 下有。

错误处理是这个函数最容易被忽略的部分，但实战里最值钱：

返回码来源 含义 最终行为
-ENOMEM devm_kzalloc 失败 直接返回，probe 不会跑
-EPROBE_DEFER pin controller 还没注册 往上抛，设备进 deferred 队列等重试
-ENOENT 设备树里没有 pinctrl-0 吞掉，当作「这设备不用 pinctrl」
-ENODEV 有 pinctrl-0 但解析不到 controller 吞掉，dev->pins = NULL
-EINVAL phandle 无效、状态应用失败、名字与下标错位 往上抛，设备探不起来

所以「日志里只有 no pinctrl handle」不是错误，是提示。

十四、引脚复用冲突怎么排查 #

冲突的表现五花八门，但根因就三类。先把三类分清，再谈手段。

类型 机理 典型现象
两个 consumer 抢同一 group 后 select 的把前一个的 mux 改掉 A 驱动工作几分钟后失效，B 驱动完全正常
忘改复用就操作 GPIO 引脚还挂在别的外设上 往 GPxDAT 写值，万用表量不到任何变化
大小写/名字写错 samsung,pins 匹配不到 pin 日志里 does not have pin group 或整条 map 为空

14.1 先看有没有冲突 #

pinctrl_select_state() 的 unapply_new_state 分支会打印 Error applying setting, reverse things back，但这只在同一次 select 内失败时出现。跨驱动的抢占不会报错——后一个 select 直接 pinmux_disable_setting() 掉前一个的 group，谁也没吭声。

要发现这类问题，靠 debugfs 的三个文件组合看：

text
/sys/kernel/debug/pinctrl/pinctrl-handles   <-- 谁持有哪个状态
/sys/kernel/debug/pinctrl/pinctrl-maps      <-- 系统里所有 map 条目
/sys/kernel/debug/pinctrl/<dev>/pins        <-- 每个 pin 当前落到哪个 gpio chip

第一步在 pinctrl-maps 里 grep 你怀疑的 group 名。它出现在两个不同的 device 名下，就是冲突。

第二步在 pinctrl-handles 里看这两个设备的 current state。谁的 state 是 none，说明它从没 select 成功过；都是具体状态名，那就是先后执行顺序问题。

14.2 Samsung 的 group 命名，是排查时的定位依据 #

Samsung 的 dt_node_to_map() 与 samsung_pinctrl_parse_dt() 都按同一个规则命名：

text
group 名   = 设备树子节点名 + "-grp"
function 名 = 设备树子节点名 + "-mux"

所以 myled_on: myled-on { ... } 这个子节点，在 debugfs 里会以 myled-on-grp 和 myled-on-mux 两个身份出现。素材里「转换链」那张图（name = "/pinctrl/myled-on"、groups = {"gpb-5", "gpb-6", ...}、num_groups = 4、以及「每个 pin 各一条 group」）与上游实现不符：

  • 一个子节点只生成一个 group，group 名带 -grp，成员是 samsung,pins 里列的全部 pin；
  • 一个子节点生成一个 function（前提是写了 samsung,pin-function），num_groups 恒为 1，指向上面那个 group；
  • 那个子节点最终只产生两条 map：一条 MUX_GROUP、一条 CONFIGS_GROUP。

所以 myled_on 这 4 个 pin 对应的 group selector 是同一个值，不是 30/31/32/33。

14.3 三种定位手段 #

text
① 数一下 group 数对不对
   cat /sys/kernel/debug/pinctrl/<dev>/pingroups | grep -c '^group:'
   dts 里有几个带 samsung,pins 的子节点，这里就该有几行（减去 interrupt-controller 那些）

② 看复用到没到硬件
   cat /sys/kernel/debug/pinctrl/<dev>/pinmux-pins
   显示 (MUX UNCLAIMED) 或某个 function 名，而不是 GPIO 状态
   再对照手册的 CON 寄存器 dump（devmem 或 /dev/mem 读）

③ 确认 map 真的建起来了
   cat /sys/kernel/debug/pinctrl/pinctrl-maps
   搜你的设备名。没有条目 = pinctrl-N 没写或 phandle 指错

第三条尤其重要：pinctrl-maps 里没有你的设备，就说明根本没走到驱动，后面所有寄存器操作都无从谈起，不用去看 CON。

14.4 一个真实约束：pin controller 必须先 probe #

dt_to_map_one_config() 顺着父节点往上找 pinctrl_dev。找不到时，模块化配置下返回 -EPROBE_DEFER，设备模型会把 consumer 放进 deferred 队列，等 controller 就绪后重试。所以「pin controller 的 probe 比 consumer 晚」不算致命问题，最终会重排。

真正的致命场景有两个：

  • dt_node_to_map 返回 num_maps == 0。日志是 there is not valid maps for state %s，比如 samsung,pins 里全是拼错的名字。这不会 defer，也不会报错，只是静默没有配置。
  • phandle 指向的不是 pin controller 的子节点。日志是 prop pinctrl-0 index 0 invalid phandle，返回 -EINVAL，设备直接探不起来。

十五、pinctrl 与 GPIO 的协作：gpio 申请时怎么被 pinctrl 接管 #

逻辑上这层关系很清楚：GPIO 是 pinctrl 管的一根根引脚的一种用途，所以 gpiolib 应该是 pinctrl 的 consumer。gpio 申请一根线时，应该向 pinctrl 申请 pin 并把它配成 GPIO 功能。

实际实现打了个洞，原因是粒度。

假设一个 gpio chip 里有两根线，都能单独在 GPIO 与 UART 之间切换。按 pinctrl 的正统模型抽象 function：

  • 如果两根线必须一起切：gpio 和 uart 两个 function，够用；
  • 如果两根能各自独立切：就得有 gpio1、gpio2、uart 三个 function；
  • 一个 bank 32 根线都能独立切：32 个 function。

一个 SoC 几十个 bank，设备树里会塞满几百个 function 节点。抽象纯度与可用性冲突，于是 pinctrl 留了后门：gpio 子系统申请资源时，绕过 function/group 模型，直接用 gpio 编号申请。

后门的入口只有四个函数，声明在 include/linux/pinctrl/consumer.h：

c
int pinctrl_gpio_request(struct gpio_chip *gc, unsigned int offset);
void pinctrl_gpio_free(struct gpio_chip *gc, unsigned int offset);
int pinctrl_gpio_direction_input(struct gpio_chip *gc, unsigned int offset);
int pinctrl_gpio_direction_output(struct gpio_chip *gc, unsigned int offset);

注意签名。老内核（3.x / 4.x）是 pinctrl_request_gpio(unsigned gpio)，传全局 gpio 编号；5.x 起改成传 (struct gpio_chip *gc, unsigned int offset)，因为全局 gpio 编号空间正在被废弃。素材里贴的是老签名，移植新内核时要改。

c
int pinctrl_gpio_request(struct gpio_chip *gc, unsigned int offset)
{
        struct pinctrl_gpio_range *range;
        struct pinctrl_dev *pctldev;
        int ret, pin;

        /* A. 按 gpio chip + offset 找到 pin controller 和 range */
        ret = pinctrl_get_device_gpio_range(gc, offset, &pctldev, &range);
        if (ret) {
                if (pinctrl_ready_for_gpio_range(gc, offset))
                        ret = 0;
                return ret;
        }
        mutex_lock(&pctldev->mutex);
        /* B. gpio 编号空间 -> pin 编号空间 */
        pin = gpio_to_pin(range, gc, offset);
        /* C. 标记占用 + 回调驱动切功能 */
        ret = pinmux_request_gpio(pctldev, range, pin, gc->base + offset);
        mutex_unlock(&pctldev->mutex);
        return ret;
}

三步各有含义。A 在全局 pinctrldev_list 里遍历每个 controller 的 gpio_ranges 链表，看哪个 range 覆盖了 gc->base + offset；找不到返回 -EPROBE_DEFER，但如果这个 chip 其他 gpio 已经在某个 range 里（pinctrl_ready_for_gpio_range() 为真），说明只是这根线没有 pinctrl 后端，返回 0 放行。B gpio_to_pin() 做编号转换。C pinmux_request_gpio() 在 core 里给这根 pin 记上 gpio_owner（之后别人再申请会被拒），再调驱动的 gpio_request_enable() 写寄存器。

15.1 gpio range：那个 map #

c
/* include/linux/pinctrl/pinctrl.h */
struct pinctrl_gpio_range {
        struct list_head node;
        const char *name;       /* 本 range 对应的 chip 名 */
        unsigned int id;        /* 本 range 的编号 */
        unsigned int base;      /* gpio 编号空间的起始 */
        unsigned int pin_base;  /* pin 编号空间的起始（pins 为 NULL 时使用） */
        unsigned int npins;     /* 覆盖的引脚数（含 base） */
        unsigned const *pins;   /* 非线性映射查找表，NULL 表示线性 */
        struct gpio_chip *gc;   /* 对应的 gpio chip，可选 */
};

一句话概括：gpio chip 的 [base, base + npins - 1] 与 pin controller 的 [pin_base, pin_base + npins - 1] 一一对应。

映射方式 判据 转换规则
线性映射 pins == NULL，pin_base 起作用 gpio_to_pin(range, gc, offset) 返回 pin_base + (gc->base + offset - base)
非线性映射 pins 非 NULL 以 offset 为下标查 pins[] 表

两套编号空间同时存在，这就是第十一章说的「代价」。

15.2 gpio-ranges：设备树里的写法 #

手工 pinctrl_add_gpio_range() 已经过时。现代写法在 GPIO 节点上写 gpio-ranges：

dts
gpio-controller@1460 {
    #gpio-cells = <2>;
    compatible = "fsl,qe-pario-bank-e", "fsl,qe-pario-bank";
    reg = <0x1460 0x18>;
    gpio-controller;
    gpio-ranges = <&pinctrl1 0 20 10>, <&pinctrl2 10 50 20>;
};

每个四元组是 <&pin控制器 gpio起始 pin起始 个数>。上面这个例子把同一个 chip 的编号空间切给两个 pin controller：gpio0~9 对应 pinctrl1 的 pin20~29，gpio10~29 对应 pinctrl2 的 pin50~69。仓库里 Actions S900（Bubblegum-96）的真实写法是 gpio-ranges = <&pinctrl1 19 52 1>，含义「gpioa 的 19 号 gpio 对应 pinctrl1 的 52 号 pin，共 1 个」；写成 <&pinctrl1 52 19 1> 一样能编译，但运行时会去操作一根不存在的 gpio，症状是 export 报错或者写到了别的引脚上。

解析走 gpiolib：devm_gpiochip_add_data() → gpiochip_add_data() → of_gpiochip_add()（gpiolib-of.c）→ of_gpiochip_add_pin_range() → gpiochip_add_pin_range() → pinctrl_find_and_add_gpio_range()（pinctrl/core.c）→ pinctrl_add_gpio_range()。结果是 pin controller 的 pinctrl_dev->gpio_ranges 链表上长出一个节点。

15.3 驱动侧要实现的三个回调 #

gpio-ranges 建好之后，gpio 侧的请求会落到 pinmux_ops 的三个回调上，签名都是 (pctldev, range, offset)：

c
int (*gpio_request_enable) (struct pinctrl_dev *pctldev,
                            struct pinctrl_gpio_range *range, unsigned int offset);
void (*gpio_disable_free) (struct pinctrl_dev *pctldev,
                           struct pinctrl_gpio_range *range, unsigned int offset);
int (*gpio_set_direction) (struct pinctrl_dev *pctldev,
                           struct pinctrl_gpio_range *range,
                           unsigned int offset, bool input);

对应的 gpio_chip 回调转调关系：.request → pinctrl_gpio_request(gc, offset)、.free → pinctrl_gpio_free(gc, offset)、.direction_input → pinctrl_gpio_direction_input(gc, offset)、.direction_output → pinctrl_gpio_direction_output(gc, offset)；老内核则统一是单参数形态 pinctrl_request_gpio(gpio) / pinctrl_free_gpio(gpio)。

素材里把 .request 写成转调 pinctrl_gpio_request(gpio)、把 .free 写成 pinctrl_free_gpio(gpio)，都是老内核的单参数形态，且那张消费表把 pinctrl_gpio_request 的语义写成「向 gpiolib 申请 GPIO，同时通知 pin controller」，方向反了——是 gpiolib 调 pinctrl。见附录。

Samsung 的实现没走这条路（它在 samsung_gpio_direction_input() 里直接写 PINCFG_TYPE_FUNC 位），所以两种风格并存：硬件配置自己干、pinctrl 只做互斥仲裁，或者全部交给 pinctrl。前者要 gpio 驱动懂寄存器，后者要 pinctrl 驱动懂 gpio。

15.4 一次 gpio_request 的完整路径 #

text
consumer: gpiod_get() / gpio_request()
  gpiolib: gpiod_request()
    gc->request() 或 gpiolib 默认实现
      pinctrl_gpio_request(gc, offset)
        pinctrl_get_device_gpio_range()   找 range
        gpio_to_pin()                     gpio 编号 -> pin 编号
        pinmux_request_gpio()
          标记 pin->gpio_owner
          pinmux_ops->gpio_request_enable()
            写寄存器，把这根 pin 切成 GPIO 功能

后面方向设置走 pinctrl_gpio_direction_input/output()，释放走 pinctrl_gpio_free()。至此两条路径汇合：标准路径是 consumer 告诉 pinctrl「我要某个 state」；后门路径是 gpiolib 告诉 pinctrl「我要某根 pin」。两者共用同一套底层回调，差别只在谁发起、粒度多细。

十六、一个 pin controller 驱动的骨架 #

这一章是补写的模板。拿一块假想 SoC 走一遍，你可以直接照骨架填自己的寄存器。

第一步，静态表——pin、group、function 三张：

c
/* 骨架示意，寄存器按你的 SoC 手册改；未在任何真实 SoC 上编译验证 */
static const struct pinctrl_pin_desc fake_pins[] = {
        PINCTRL_PIN(0, "pa0"), PINCTRL_PIN(1, "pa1"),
        PINCTRL_PIN(4, "pa4"), PINCTRL_PIN(5, "pa5"),

第二步，三张 ops 表。查询类的回调都是纯 getter，只有 set_mux 和 pin_config_set 真正写寄存器：

c
static const struct pinctrl_ops fake_pctlops = {
        .get_groups_count = fake_get_groups_count,   /* ARRAY_SIZE(fake_groups) */
        .get_group_name   = fake_get_group_name,     /* fake_groups[s].name */
        .get_group_pins   = fake_get_group_pins,     /* 回填 pins / num_pins */
        .dt_node_to_map   = fake_dt_node_to_map,     /* 见下方说明 */
        .dt_free_map      = fake_dt_free_map,
};

static int fake_set_mux(struct pinctrl_dev *pctldev, unsigned int func_selector,
                        unsigned int group_selector)
{
        struct fake_pinctrl *priv = pinctrl_dev_get_drvdata(pctldev);
        const struct fake_group *g = &fake_groups[group_selector];

        for (i = 0; i < g->npins; i++) {
                unsigned int pin = g->pins[i];
                unsigned int shift = (pin % 16) * 2;    /* 每 pin 2 bit 功能域 */

                val = readl(priv->base + (pin / 16) * 4);
                val &= ~(0x3 << shift);
                val |= (g->func & 0x3) << shift;
                writel(val, priv->base + (pin / 16) * 4);
        }
        return 0;
}

static const struct pinmux_ops fake_pmxops = {
        .get_functions_count = fake_get_functions_count,   /* ARRAY_SIZE(fake_functions) */
        .get_function_name   = fake_get_function_name,     /* fake_functions[s].name */
        .get_function_groups = fake_get_function_groups,   /* 回填 groups / ngroups */
        .set_mux             = fake_set_mux,
        .strict              = true,   /* 拒绝同一 pin 既当 gpio 又当外设 */
};

static const struct pinconf_ops fake_confops = {
        .is_generic     = false,
        .pin_config_get = fake_pin_config_get,   /* 骨架里直接 return -ENOTSUPP */
        .pin_config_set = fake_pin_config_set,   /* switch 到 PUD/DRV 分支写寄存器 */
};

第三步，probe 里把描述符填满并注册：

c
static int fake_probe(struct platform_device *pdev)

        desc->name    = "fake-pinctrl";

        desc->npins   = ARRAY_SIZE(fake_pins);

        desc->pmxops  = &fake_pmxops;
        desc->confops = &fake_confops;

                return PTR_ERR(priv->pctldev);
        return 0;
}

dt_node_to_map 只写了一半，正是为了让规则显形：kcalloc(2, sizeof(*new_map), GFP_KERNEL) 分配两条，写 fake,pin-function 就填一条 PIN_MAP_TYPE_MUX_GROUP（data.mux.group / data.mux.function），有几个 fake,pin-* 电气属性就再填一条 PIN_MAP_TYPE_CONFIGS_GROUP，dt_free_map 里把 configs 数组和 map 一起 kfree()。一个子节点最多两条 map，这个规则和 Samsung 完全一致。

骨架里为了讲清楚结构做了三处简化，正式写驱动都要补：confops 只填了单 pin 版，而 Samsung 的 map 走的是 CONFIGS_GROUP 的 group 版，所以真驱动要么两个都实现、要么像 Samsung 那样把 group 版实现成「遍历组内 pin 调单 pin 版」；dt_node_to_map 里的 CONFIGS 那条要按你的格式打包；dt_free_map 必须释放 configs，否则泄漏。

注册顺序两条纪律：必须早于任何 consumer，用 postcore_initcall() 而不是 module_platform_driver 默认的 device_initcall；devm_pinctrl_register() 只做初始化和入链表，不做 hogs claim，要 hogs 就用 devm_pinctrl_register_and_init() 再显式 pinctrl_enable()。

17.1 全局三个文件 #

文件 头一行 关键信息
pinctrl-devices name [pinmux] [pinconf] 每控制器一行；第二列 no 说明根本没有 pmxops，别指望它能切复用
pinctrl-maps Pinctrl maps: 每条 map 一段：device / state / type <名字> (<数值>) / controlling device / mux 的 group+function 或 configs 的 group+config
pinctrl-handles Requested pin control handlers their pinmux maps: 每设备一行 device: <名字> current state: <状态>，下面按 state 列出每条 setting

pinctrl-maps 里 type 后面的数值就是 enum pinctrl_map_type：0 INVALID、1 DUMMY_STATE、2 MUX_GROUP、3 CONFIGS_PIN、4 CONFIGS_GROUP。config 258 (0x102) 就是第六章那个 PINCFG_PACK 的结果——0x102 = (1 << 8) | 2，类型 2 是 PINCFG_TYPE_PUD，值 1 是上拉。

pinctrl-handles 的 current state: 是整个 debugfs 里最有用的一个字段。它显示 none 或压根没有这个设备，就说明 holder 建了但从没 select 成功过。

十九、易错点速查 #

# 易错点 正确做法
1 以为配了 GPIO 就是配了引脚 两步走：pinctrl 定功能，gpiolib 定方向与电平
2 dts 里 group 名大写 samsung,pins = "gpb-5"，全小写，横线不许改成下划线
3 pinctrl-names 写了，pinctrl-0 忘了 两个都得写，否则解析不到任何状态
4 下标跳着写（0、2） 必须从 0 连续，断一个后面全丢
5 状态名和下标错位 名字数组与 pinctrl-N 一一对应，改一个就得改另一个
6 在 probe 里又配了一遍 GPIO 方向 default 已在 pinctrl_bind_pins() 里应用过，重复无害但多余
7 在 probe 里重复 devm_pinctrl_get() 引用计数会加一，但 holder 复用，不会重新解析；不必为了省开销而缓存
8 pinctrl_get() 不配对 pinctrl_put() 用 devm_ 版本，随设备 detach 自动释放
9 把 -ENOENT / -ENODEV 当硬错误 pinctrl_bind_pins() 会吞掉它们；只有 -EPROBE_DEFER 和 -EINVAL 往上抛
10 以为 init 状态在 3.x 也生效 3.x 没有 init 的专门语义，5.x 才补齐（3.7 具体行为未验证）
11 pinmux_ops->strict 默认开着 默认是 false，要互斥得显式设 true
12 手工 pinctrl_add_gpio_range() 现代写法是设备树 gpio-ranges，让 gpiolib 建
13 gpio-ranges 四元组顺序写反 <&ctrl gpio起始 pin起始 个数>，写反能编译，运行时写到别的 pin
14 以为 pinctrl_gpio_request() 是给普通驱动调的 只给 gpiolib 用，其他驱动走 gpiod API
15 新内核照抄 pinctrl_request_gpio(gpio) 5.x 起签名换成 (gc, offset)
16 npins 写成 bank 数量 是本控制器可控 pin 的总数
17 多个 controller 的 base 重叠 全局编号必须唯一，后注册的会撞 pin already registered
18 pinctrl_register() 返回值用 !ptr 判断 6.x 返回 ERR_PTR，用 IS_ERR()
19 一个子节点既想当 group 又想当 function 一个子节点 = 一个 group + 一个 function（后者可选），别指望拆成多个 group
20 以为 pinctrl-maps 里出现两次就是重复配置 Samsung 一个子节点固定生成 MUX + CONFIGS 两条
21 调试时忘了 CONFIG_DEBUG_FS 没有 debugfs 就只能靠 dmesg 和寄存器 dump
22 以为 pinctrl-devices 第二列 no 也能切复用 没 pmxops 就是不能切，别浪费时间
23 睡眠态 sleep 配了却不生效 要 CONFIG_PM，并且驱动得调 pinctrl_pm_select_sleep_state() 或由 PM 框架代劳
24 同一个 group 被两个 consumer 抢 pinmux-pins 只会显示后一个设备名，冲突静默发生，必须人工核对
