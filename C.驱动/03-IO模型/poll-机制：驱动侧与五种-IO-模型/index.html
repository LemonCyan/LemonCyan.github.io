上一篇解决了"一个设备怎么阻塞地等"，这一篇解决"一个进程怎么同时等多个设备"。

一、问题的由来：一个只能阻塞的 read #

前面用中断方式获取按键值时，应用程序是这样写的：

c
#include <sys/stat.h>
#include <fcntl.h>
#include <stdio.h>

int main(int argc, char **argv)
{
    int fd, ret;
    unsigned int key_val = 0;

    fd = open("/dev/buttons", O_RDWR);
    if (fd < 0) {
        printf("can't open!\n");
        return -1;
    }

    while (1) {
        /* 读取一个字节值。在等待队列中本进程会进入休眠状态，
           只有按键按下或者松开才会返回 */
        ret = read(fd, &key_val, 1);
        if (ret < 0) {
            printf("read error\n");
            continue;
        }
        printf("key_val = 0x%x\n", key_val);
    }

    return 0;
}

这实际上是同步 I/O 操作——一个 read 就阻塞了当前线程，导致其他代码无法执行。解决这个问题有若干种办法：

  • 异步 I/O：需要执行耗时的 IO 操作时，只发出 IO 指令，不等待结果，转去执行其他代码；一段时间后 IO 返回结果再通知调用者。
  • 多线程：用并发解决，但系统不能无上限地增加线程。线程切换开销也很大，线程数量过多时 CPU 时间全花在切换上，真正运行代码的时间少了，性能严重下降。

要真正解决，得先理解 IO 模型的分类。

二、五种 I/O 模型 #

Linux 下有五种 IO 模型：

# 模型 机制 同步/异步
1 阻塞 IO read 睡眠直到有数据 同步
2 非阻塞 IO read 立即返回，应用轮询 同步
3 多路复用 IO select/poll/epoll 等，就绪再 read 同步
4 信号驱动 IO 内核发 SIGIO 通知 同步
5 异步 IO aio_read，内核全程代办 异步

前四种都是同步 IO，只有最后一种是异步 IO。

2.1 判据：看第二阶段 #

进程无法直接操作 IO 设备，必须通过系统调用请求内核协助，内核为每个 IO 设备维护一个 buffer。一次设备 IO（以 read 为例）涉及两个系统对象——调用 IO 的进程/线程，以及系统内核——并经历两个阶段：

  • 阶段 1 · 等待设备数据就绪：用户进程发起请求，内核接收到请求后从 IO 设备中获取数据到 buffer（Waiting for the data to be ready）；
  • 阶段 2 · 将数据从内核空间拷贝到用户空间：把 buffer 中的数据 copy 到用户进程的地址空间（Copying the data from the kernel to the process）。

在异步 IO 模型中，用户进程发起系统调用后立刻可以去做别的事，直到 IO 执行的两个阶段都完成之后，内核才给用户进程发送通知说操作已完成。异步 IO 的读操作通过 aio_read 实现。

2.2 两条关键判据 #

  • 异步 IO 和同步 IO 的主要区别在于 IO 操作的第二阶段：同步 IO 用户进程会发生堵塞，而异步 IO 用户进程不会。
  • 阻塞 IO 和非阻塞 IO 主要就在于当设备没有数据时，我们调用 read 是立即返回还是处于睡眠状态。

2.3 四种同步模型的递进 #

以按键测试程序调用 read 为例：

（1）阻塞 IO 模型 #

也就是第一章那个例子。调用 read 的线程一直处于阻塞状态，一直等到有按键变化，才会将数据从内核拷贝到用户空间。

应用:   read ──────────等待数据──────────▶ 拷贝 ─▶ 返回
内核:         ░░░░░░░░░ 睡眠 ░░░░░░░░░       ██

（2）非阻塞 IO 模型 #

如果在 open 打开 /dev/buttons 时指定了 O_NONBLOCK 标志，read 函数就不会阻塞。如果没有按键发生改变，就会立即返回 -1。

采用轮询方式反复调用 read：

c
while (1)
{
    ret1 = read(设备1);
    if (ret1 > 0)
        处理数据;

    ret2 = read(设备2);
    if (ret2 > 0)
        处理数据;

    /* ...... */
}

调用者只是查询一下，不会阻塞在这里，这样可以同时监控多个设备。

但上面的代码有问题：线程会不停轮询，导致 CPU 使用率急剧升高。

因此可以在循环最后加入一定时长的睡眠，但这又带来另一个问题——如果设备有数据到达，睡眠可能导致数据处理不及时。于是衍生了 IO 多路复用模型。

（3）IO 多路复用模型 #

IO 多路复用通过一种机制，让一个进程/线程可以监视多个设备，一旦某个设备就绪（一般是读就绪或写就绪），能够通知程序进行相应的读写操作。

Linux 下目前支持 IO 多路复用的系统调用有 select、pselect、poll、epoll。

在调用 read 之前先调用 select/poll/epoll，它们可以阻塞地同时监视多个设备，还可以设定阻塞等待的超时时间，并且当内核准备好数据时会通知调用者，这时候再去调用 read 读取数据。

应用:   select/poll ──等待任一就绪──▶ read ─▶ 返回
内核:   同时监视 fd1, fd2, fd3 ...      ██

（4）信号驱动 IO 模型 #

应用注册 SIGIO 处理函数后立即返回，内核在数据就绪时发信号通知，应用在信号处理函数里 read。省掉了主动轮询，但阶段 2 仍然是同步的，见《信号驱动 IO 与异步通知》。

2.4 四者对照 #

阻塞 IO 非阻塞 IO 多路复用 信号驱动
阶段 1 谁在等 进程睡眠 进程反复问 进程睡在 select/poll 进程干别的事
CPU 占用 低 高 低 低
能否同时等多个 fd 否 是（要自己轮询） 是 是（每个 fd 信号）
数据就绪通知方式 无（阻塞自然返回） 无（自己问） 返回后自己 read 信号回调
驱动侧依赖 等待队列 O_NONBLOCK 检查 .poll 方法 .fasync

三、poll 系统调用 #

3.1 两种系统调用形式 #

select 与 poll 做的事一样，接口形式不同：

select（BSD 引入，用得较广）：

c
#include <sys/select.h>

int select(int maxfdp1, fd_set *readset, fd_set *writeset,
           fd_set *exceptset, const struct timeval *timeout);

poll（System V 引入）：

c
#include <poll.h>

int poll(struct pollfd *fds, unsigned int nfds, int timeout);

poll 的优势是不用受 FD_SETSIZE（通常 1024）限制，而且把"关注什么事件"和"发生了什么事件"分开表达：

c
struct pollfd {
    int   fd;       /* 要监视的文件描述符 */
    short events;   /* 请求监视的事件（输入） */
    short revents;  /* 实际发生的事件（输出） */
};

3.2 为什么要用 poll 而不是轮询 read #

轮询 read select/poll
CPU 占用 高（不停调用） 低（无事件时睡眠）
空闲时行为 一直跑 阻塞在 schedule()
多设备 挨个试 一次监视一批
超时控制 要自己算 内核原生支持

四、驱动侧：poll 方法 #

4.1 原型 #

c
unsigned int (*poll)(struct file *filp, struct poll_table_struct *wait);

第一个参数是 file 结构体指针，第二个是轮询表指针（poll_table）。

4.2 poll 方法只做两件事 #

a — 注册等待队列

对可能引起设备文件状态变化的等待队列调用 poll_wait()，把对应的等待队列头添加到 poll_table。如果没有文件描述符可用来执行 I/O，内核使进程在传递到该系统调用的所有文件描述符对应的等待队列上等待。

b — 返回掩码

返回表示是否能对设备进行无阻塞读、写访问的掩码。

4.3 状态掩码 #

掩码 含义
POLLIN 设备有数据可读，读操作不会阻塞
POLLRDNORM 常规数据可读（常与 POLLIN 并用）
POLLOUT 设备缓冲区有空间，写操作不会阻塞
POLLWRNORM 常规数据可写（常与 POLLOUT 并用）
POLLERR 设备发生错误
POLLHUP 设备挂起（对端已关闭）
POLLNVAL 文件描述符未打开

惯例写法：

c
设备可读，通常返回：(POLLIN | POLLRDNORM)
设备可写，通常返回：(POLLOUT | POLLWRNORM)

4.4 poll_wait 的语义（关键） #

c
void poll_wait(struct file *filp, wait_queue_head_t *queue, poll_table *wait);

poll_wait() 不会引起阻塞。 它所做的工作是把当前进程添加到 wait 参数指定的等待列表（poll_table）中。

真正的阻塞动作是上层的 select/poll 函数中完成的：select/poll 会在一个循环中对每个需要监听的设备调用它们自己的 poll 支持函数，以使得当前进程被加入各个设备的等待列表。若当前没有任何被监听的设备就绪，则内核进行调度（调用 schedule）让出 CPU 进入阻塞状态；schedule 返回时再次循环检测是否有操作可以进行，如此反复；若任意一个设备就绪，select/poll 都立即返回。

这是最容易误解的一点：poll_wait 只是"挂个号"，不是"等在这儿"。

4.5 典型实现 #

c
static unsigned int XXX_poll(struct file *filp, poll_table *wait)
{
    unsigned int mask = 0;
    struct XXX_dev *dev = filp->private_data;   /* 获得设备结构指针 */

    poll_wait(filp, &dev->r_wait, wait);        /* 加读等待队列头 */
    poll_wait(filp, &dev->w_wait, wait);        /* 加写等待队列头 */

    if (/* 可读 */) {
        mask |= POLLIN | POLLRDNORM;            /* 标识数据可获得 */
    }
    if (/* 可写 */) {
        mask |= POLLOUT | POLLWRNORM;           /* 标识数据可写入 */
    }

    return mask;
}

五、完整调用过程 #

5.1 两轮循环 #

第一轮：用户程序第一次调用 select 或 poll，驱动调用 poll_wait 使两条队列都加入 poll_table 结构中，作为下次调用驱动 poll 的条件。一个 mask 返回值指示设备是否可操作，0 为未准备状态。如果文件描述符未准备好可读或可写，用户进程会被加入到写或读等待队列中进入睡眠状态。

第二轮：当驱动执行了某些操作（例如写缓冲或读缓冲——写缓冲使读队列被唤醒，读缓冲使写队列被唤醒），select 或 poll 系统调用在将要返回给用户进程时再次调用驱动 poll。驱动依然调用 poll_wait 使两条队列都加入 poll_table，并判断可写或可读条件是否满足：

  • 如果 mask 返回 POLLIN | POLLRDNORM 或 POLLOUT | POLLWRNORM，指示可读或可写，这时 select/poll 真正返回给用户进程；
  • 如果 mask 还是返回 0，则 select/poll 继续不返回。

5.2 内核侧的调用顺序 #

Linux 下 select 调用的过程：

  1. 用户层应用调用 select()，底层调用 poll()；
  2. 核心层调用 sys_select() → do_select()，最终调用文件描述符 fd 对应 struct file 的 struct file_operations *f_op 的 poll 函数：
    • 如果当前可读写，返回读写信息；
    • 如果当前不可读写，则阻塞进程，并等待驱动程序唤醒，重新调用 poll 函数，或超时返回；
  3. 驱动需要实现 poll 函数。当驱动发现有数据可以读写时，通知核心层，核心层重新调用 poll 指向的函数查询信息。
c
poll_wait(filp, &wait_q, wait);   /* 此处将当前进程加入等待队列，但并不阻塞 */
/* 中断中 */
wake_up_interruptible(&wait_q);   /* 唤醒等待队列 */

5.3 驱动侧要做的事 #

位置 动作
.poll 方法里 poll_wait() 注册每个相关等待队列；按当前状态返回 mask
中断 / 写函数里 改变状态后 wake_up_interruptible(&wq)
read/write 里 检查 O_NONBLOCK，非阻塞时返回 -EAGAIN

三者缺一，select 就会永远不返回或者立即返回错误值。

六、驱动侧实现示例 #

c
#include <linux/poll.h>
#include <linux/fs.h>

extern wait_queue_head_t wq;    /* 读等待队列 */
extern wait_queue_head_t wwq;   /* 写等待队列 */
extern int havedata;            /* 数据就绪标志：0 无数据，1 有数据 */

unsigned int hello_poll(struct file *file, struct poll_table_struct *ptbl)
{
    unsigned int mask = 0;

    /* 1. 把当前进程的轮询表项挂载到对应的读/写等待队列中
          poll_wait 并不会使进程休眠，它只是把进程"注册"到队列中，
          这样一旦设备就绪，驱动才能唤醒它 */
    poll_wait(file, &wq, ptbl);
    poll_wait(file, &wwq, ptbl);

    /* 2. 根据当前的硬件数据状态，计算并返回掩码 */
    if (havedata == 0)
        mask |= POLLOUT | POLLWRNORM;   /* 当前无数据可读，可以写入 */

    if (havedata == 1)
        mask |= POLLIN | POLLRDNORM;    /* 当前有数据未读，可以读取 */

    return mask;
}

6.1 数据就绪后的唤醒 #

当驱动从外部硬件中断或其他写入途径接收到数据、并将 havedata 置为 1 时，必须显式调用：

c
havedata = 1;
wake_up_interruptible(&wq);    /* 唤醒挂在 wq 上的读轮询进程 */

此时处于 poll() 等待状态的用户进程被唤醒，重新调用 hello_poll，返回的 mask 包含 POLLIN，应用层随之退出阻塞并执行 read。

七、按键驱动 poll 改造 #

把前面 read 只能阻塞等按键的驱动，改造成支持多路复用的版本。目标：当有按键改变时，我们再去调用 read 函数，否则进程就阻塞（通过 poll 函数设置等待超时时间）。

7.1 驱动侧改动 #

c
/* 1. 在设备结构体里加一个等待队列头 */
struct button_dev {
    struct cdev cdev;
    /* ... */
    wait_queue_head_t r_wait;   /* 读等待队列 */
    int key_pressed;            /* 按键状态标志 */
};

/* 2. 在 probe / init 里初始化 */
init_waitqueue_head(&btn->r_wait);

/* 3. 新增 poll 方法 */
static unsigned int button_poll(struct file *filp, poll_table *wait)
{
    unsigned int mask = 0;
    struct button_dev *dev = filp->private_data;

    poll_wait(filp, &dev->r_wait, wait);

    if (dev->key_pressed)
        mask |= POLLIN | POLLRDNORM;

    return mask;
}

/* 4. 中断处理里置位并唤醒 */
static irqreturn_t button_irq(int irq, void *dev_id)
{
    struct button_dev *dev = dev_id;

    dev->key_pressed = 1;
    wake_up_interruptible(&dev->r_wait);

    return IRQ_HANDLED;
}

/* 5. 注册 poll 方法 */
static struct file_operations button_fops = {
    .owner = THIS_MODULE,
    .open  = button_open,
    .read  = button_read,
    .poll  = button_poll,
};

7.2 应用侧改动 #

c
#include <stdio.h>
#include <poll.h>
#include <fcntl.h>
#include <unistd.h>

int main(void)
{
    struct pollfd fds[1];
    unsigned int key_val;
    int ret;

    fds[0].fd = open("/dev/buttons", O_RDWR);
    if (fds[0].fd < 0) {
        printf("can't open!\n");
        return -1;
    }
    fds[0].events = POLLIN;      /* 关心"可读" */

    while (1) {
        ret = poll(fds, 1, 3000);   /* 超时 3000ms */
        if (ret < 0) {
            perror("poll");
            break;
        }
        if (ret == 0) {
            printf("time out\n");
            continue;
        }

        if (fds[0].revents & POLLIN) {
            read(fds[0].fd, &key_val, 1);
            printf("key_val = 0x%x\n", key_val);
        }
    }

    return 0;
}

改造后，应用不再需要一个线程死等在 read 上——poll 返回 0 时可以去做超时处理，返回 POLLIN 时才去 read，同一个循环里还能同时监视多个设备。

八、速查 #

角色 该做什么
驱动 · .poll 先 poll_wait 注册每个相关队列，再按状态返回 mask
驱动 · 中断/写 状态变化后 wake_up_interruptible()
驱动 · read 非阻塞且无数据时返回 -EAGAIN
应用 · select 注意 nfds 是最大 fd + 1，且每次返回后 fd_set 会被修改，需重新 FD_SET
应用 · poll 每次调用前重设 events，检查返回后的 revents
常见错误 poll_wait 写进 if 里导致某些状态下没注册 → select 永远不醒
