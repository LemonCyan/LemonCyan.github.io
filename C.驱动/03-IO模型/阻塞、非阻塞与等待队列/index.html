应用层调用 read() 时，如果设备当前没有数据，驱动的行为取决于两件事：调用者是不是希望阻塞、驱动有没有实现相应的等待机制。本篇讲清这条链路。

一、五种 I/O 模型 #

回顾 Unix/Linux 共有五种 I/O 模型：

# 模型 谁在等 驱动侧依赖
a 阻塞 I/O 进程睡眠等 等待队列
b 非阻塞 I/O 进程轮询 O_NONBLOCK 检查
c I/O 复用（select / poll） 进程睡眠等多个 fd poll 方法
d 信号驱动 I/O（SIGIO） 进程干别的事，等信号 fasync / kill_fasync
e 异步 I/O（Posix.1 的 aio_*） 内核全程代办 aio_read / aio_write

本篇讲 a 和 b，c 与 d 各有专篇。

前四种都是同步 I/O，只有最后一种是异步 I/O。 区别在于第二阶段：同步 I/O 在"把数据从内核拷到用户空间"时用户进程会堵塞，异步 I/O 不会。

1.1 一次 read 的两个阶段 #

进程无法直接操作 I/O 设备，必须通过系统调用请求内核协助，而内核会为每个 I/O 设备维护一个 buffer。一次 read 涉及两个系统对象——调用它的进程/线程，以及系统内核：

阶段 1  等待设备数据就绪
        用户进程发起请求 → 内核从 IO 设备获取数据到 buffer
        （Waiting for the data to be ready）

阶段 2  将数据从内核空间拷贝到用户空间
        buffer 中的数据 copy 到用户进程地址空间
        （Copying the data from the kernel to the process）

阻塞与非阻塞的差别只在阶段 1 怎么等；两者的阶段 2 都是同步的。

二、阻塞与非阻塞的本质 #

2.1 定义 #

阻塞操作：在执行设备操作时，若不能获得资源，则挂起进程直到满足可操作的条件后再进行操作。被挂起的进程进入休眠状态（放弃 CPU），被从调度器的运行队列移走，直到等待的条件被满足。

非阻塞：进程在不能进行设备操作时并不挂起（继续占用 CPU），它或者放弃，或者不停地查询，直到可以操作为止。

二者的区别可以看应用程序的调用是否立即返回。

2.2 驱动应该怎么做 #

驱动程序通常需要提供这样的能力：

  • 当应用进行 read()、write() 等系统调用时，若设备资源不能获取，而用户又希望以阻塞方式访问设备，驱动应在 xxx_read()、xxx_write() 中将进程阻塞直到资源可以获取，此后应用的 read()、write() 才返回。整个过程仍完成了正确的设备访问，用户没有感知。
  • 若用户以非阻塞方式访问设备文件，则当设备资源不可获取时，驱动的 xxx_read()、xxx_write() 立刻返回，read()、write() 等系统调用也随即返回。

2.3 谁来唤醒 #

因为阻塞的进程会进入休眠状态，必须确保有一个地方能够唤醒休眠的进程，否则进程就真的挂了。

唤醒进程的地方最大可能发生在中断里面——因为硬件资源获得的同时往往伴随着一个中断。

阻塞 I/O 通常由等待队列来实现，而非阻塞 I/O 由轮询来实现。

三、阻塞 I/O 的实现：等待队列 #

3.1 基本思想 #

在 Linux 驱动程序中，可以使用等待队列（wait queue）来实现阻塞进程的唤醒。wait queue 很早就作为一个基本的功能单位出现在内核里了，它以队列为基础，与进程调度机制紧密结合，能够实现内核中的异步事件通知机制。等待队列可以用来同步对系统资源的访问——上一篇讲的信号量在内核中也依赖等待队列来实现。

使用过程很简单：先定义一个 wait_queue_head，然后如果一个 task 想等待某种事件，调用 wait_event(等待队列, 事件) 就可以了。

3.2 两个核心数据结构 #

等待队列的内核实现十分简单，涉及两个重要结构。

__wait_queue_head — 描述等待队列的链头，包含一个链表和一个原子锁：

c
struct __wait_queue_head {
    spinlock_t lock;            /* 保护等待队列的原子锁 */
    struct list_head task_list; /* 等待队列 */
};
typedef struct __wait_queue_head wait_queue_head_t;

__wait_queue — 对一个等待任务的抽象。每个等待任务都会抽象成一个 wait_queue 并挂载到 wait_queue_head 上：

c
struct __wait_queue {
    unsigned int flags;
    void *private;              /* 通常指向当前任务控制块 */
    wait_queue_func_t func;     /* 任务唤醒操作方法，内核通常提供 autoremove_wake_function */
    struct list_head task_list; /* 挂入 wait_queue_head 的挂载点 */
};

3.3 实现思想 #

当一个任务需要在某个 wait_queue_head 上睡眠时，把自己的进程控制块信息封装到 wait_queue 中，然后挂载到 wait_queue 的链表中，执行调度睡眠。

当某些事件发生后，另一个任务（进程）会唤醒 wait_queue_head 上的某个或者所有任务——唤醒工作也就是将等待队列中的任务设置为可调度的状态，并且从队列中删除。

         wait_queue_head_t
        +-----------------+
        |  lock           |
        |  task_list ----+|----> [wait_queue A] -> [wait_queue B] -> ...
        +-----------------+          (private: PCB)    (private: PCB)

3.4 wait_event 的五步流程 #

一个任务需要等待某一事件时，通常调用 wait_event。该函数会定义一个 wait_queue 描述等待任务，用当前进程描述块初始化它，然后把它加入 wait_queue_head。流程如下：

  • a — 用当前的进程描述块（PCB）初始化一个 wait_queue 描述的等待任务；
  • b — 在等待队列锁资源的保护下，将等待任务加入等待队列；
  • c — 判断等待条件是否满足，如果满足，那么将等待任务从队列中移出，退出函数；
  • d — 如果条件不满足，那么任务调度，将 CPU 资源交与其它任务；
  • e — 当睡眠任务被唤醒之后，需要重复 b、c 步骤，如果确认条件满足，退出等待事件函数。

注意 c 在 d 之前——先判断再睡，这个顺序避免了"条件已经成立却还是睡下去"的丢唤醒。

四、等待队列 API #

4.1 定义并初始化 #

c
/* 定义"等待队列头" */
wait_queue_head_t my_queue;

/* 初始化"等待队列头" */
init_waitqueue_head(&my_queue);

init_waitqueue_head() 会将自旋锁初始化为未锁，等待队列初始化为空的双向循环链表。

c
/* 定义并初始化一步到位的快捷方式 */
DECLARE_WAIT_QUEUE_HEAD(my_queue);

4.2 定义等待队列 #

c
DECLARE_WAITQUEUE(name, tsk);   /* 定义并初始化一个名为 name 的等待队列 */

4.3 添加／移出等待队列 #

c
/* 设置等待的进程为非互斥进程，并将其添加进等待队列头 q 的队头 */
void add_wait_queue(wait_queue_head_t *q, wait_queue_t *wait);

/* 功能基本一样，只不过它把等待的进程 wait 设置为互斥进程 */
void add_wait_queue_exclusive(wait_queue_head_t *q, wait_queue_t *wait);

4.4 等待事件：五个变体 #

宏 进程状态 被信号打断时 返回值
wait_event(wq, condition) TASK_UNINTERRUPTIBLE 不可打断 无
wait_event_interruptible(wq, condition) TASK_INTERRUPTIBLE 返回 -ERESTARTSYS 或 0
wait_event_timeout(wq, condition, timeout) TASK_UNINTERRUPTIBLE 不可打断 剩余 jiffies 或 0
wait_event_interruptible_timeout(wq, condition, timeout) TASK_INTERRUPTIBLE 返回 -ERESTARTSYS 或剩余时间
wait_event_interruptible_exclusive(wq, condition) TASK_INTERRUPTIBLE 返回 同上，但为互斥进程

逐个说明：

  • wait_event()：在等待队列中睡眠直到 condition 为真。等待期间进程被置为 TASK_UNINTERRUPTIBLE。每次被唤醒都会检查 condition。
  • wait_event_interruptible()：与上者的区别是进程被置为 TASK_INTERRUPTIBLE。每次被唤醒先检查 condition，为真则返回；否则如果进程是被信号唤醒，返回 -ERESTARTSYS。condition 为真时返回 0。
  • wait_event_timeout()：与 wait_event() 类似。如果所给的睡眠时间为负数则立即返回；如果在睡眠期间被唤醒且 condition 为真，返回剩余的睡眠时间，否则继续睡眠直到到达或超过给定睡眠时间，然后返回 0。
  • wait_event_interruptible_timeout()：与 wait_event_timeout() 类似，不过如果在睡眠期间被信号打断则返回 ERESTARTSYS。
  • wait_event_interruptible_exclusive()：同样和 wait_event_interruptible() 一样，不过该睡眠的进程是一个互斥进程——见第五章的独占等待。

4.5 唤醒队列 #

c
void wake_up(wait_queue_head_t *q);
void wake_up_interruptible(wait_queue_head_t *q);

wake_up 会唤醒队列上的任务，其核心实现是：

c
#define wake_up(x)  __wake_up(x, TASK_NORMAL, 1, NULL)

void __wake_up(wait_queue_head_t *q, unsigned int mode, int nr_exclusive, void *key)
{
    unsigned long flags;

    spin_lock_irqsave(&q->lock, flags);
    __wake_up_common(q, mode, nr_exclusive, 0, key);
    spin_unlock_irqrestore(&q->lock, flags);
}
EXPORT_SYMBOL(__wake_up);

注意 nr_exclusive 参数（wake_up 传的是 1）——它和下面的"独占等待"直接相关。

4.6 疯狂兽群 与 独占等待 #

这两个概念是使用等待队列时绕不开的：

a — 疯狂兽群（thundering herd）

wake_up 的时候，所有阻塞在队列的进程都会被唤醒，但因为 condition 的限制，只有一个进程能得到资源，其他进程又会再次休眠。数量很大时，这种现象称为疯狂兽群——一次硬件事件唤起几十上百个进程，绝大部分立刻又睡回去，白白消耗调度开销。

b — 独占等待（exclusive wait）

等待队列的入口设置一个 WQ_FLAG_EXCLUSIVE 标志，该等待项就会被添加到等待队列的尾部；没有设置该标志的添加到头部。wake_up 时遇到第一个具有 WQ_FLAG_EXCLUSIVE 标志的进程，就停止唤醒其他进程。

        队头                                        队尾
   [普通] -> [普通] -> [独占 A] -> [独占 B] -> ...
     ↑ 全部唤醒（共 nr_exclusive 次后停）
                        ↑ 只唤醒这一个就停

这就是 wake_up(x) 里 nr_exclusive = 1 的含义：最多唤醒 1 个互斥进程，之后就不再往下叫了。驱动里如果知道"一次事件只够喂饱一个读者"，就用 wait_event_interruptible_exclusive()，避免疯狂兽群。

五、非阻塞 I/O 的实现 #

5.1 方式一：立即返回 -EAGAIN #

这是最直接的做法——在 read/write 里检查 filp->f_flags 的 O_NONBLOCK 位：

c
if (havedata == 0) {
    if (filp->f_flags & O_NONBLOCK)
        return -EAGAIN;                  /* 立即返回，告诉应用层稍后再试 */
    wait_event_interruptible(wq, havedata == 1);
}

-EAGAIN 是约定的"现在没有，等会儿再来"，应用层收到它通常重试或去做别的事。

5.2 方式二：多路复用（select / poll） #

应用层反复调用 read() 轮询的代价是 CPU 占用率急剧升高：

c
while (1) {
    ret1 = read(设备1);
    if (ret1 > 0) 处理数据;

    ret2 = read(设备2);
    if (ret2 > 0) 处理数据;
    /* ... */
}

在循环末尾加睡眠能降 CPU，但会带来新问题：设备有数据到达时可能因睡眠而处理不及时。于是有了 I/O 多路复用——用一个机制同时监视多个设备，任一就绪就通知程序。

select() / poll() 与阻塞和非阻塞访问息息相关：使用非阻塞 I/O 的应用程序通常会用它查询是否可对设备进行无阻塞访问。这两个系统调用最终会引发设备驱动中的 poll() 函数被执行。

select 是在 BSD UNIX 中引入的，poll 是在 System V 中引入的，两者本质一样。驱动侧实现见《poll 机制：驱动侧与五种 IO 模型》。

5.3 应用层的 select 速查 #

c
int select(int numfds, fd_set *readfds, fd_set *writefds,
           fd_set *exceptfds, struct timeval *timeout);
参数 含义
readfds / writefds / exceptfds 监视的读、写、异常处理的文件描述符集合
numfds 需要检查的号码最高的文件描述符 + 1
timeout 时间上限，超过该值后即使仍没有描述符准备好也会返回 
c
struct timeval {
    int tv_sec;    /* 秒 */
    int tv_usec;   /* 微秒 */
};

timeout 的三种取值对应三种行为：

取值 行为
NULL 一直阻塞
时间全 0 非阻塞，立即返回
非 0 超过设定时间就立刻返回

描述符集合的四个操作宏：

c

void FD_SET(int fd, fd_set *set);   /* 将一个文件描述符加入集合 */
void FD_CLR(int fd, fd_set *set);   /* 将一个文件描述符从集合中清除 */

六、驱动侧模板 #

6.1 阻塞读 + 阻塞写 #

c
static ssize_t hello_read(struct file *filep, char __user *buf, size_t len, loff_t *pos)
{
    if (len > 64)
        len = 64;

    /* 没有数据就阻塞，直到 have_data 为 1 */
    wait_event_interruptible(wq, have_data == 1);

    if (copy_to_user(buf, temp, len))
        return -EFAULT;

    have_data = 0;
    return len;
}

static ssize_t hello_write(struct file *filep, const char __user *buf, size_t len, loff_t *pos)
{
    if (len > 64)
        len = 64;

    if (copy_from_user(temp, buf, len))
        return -EFAULT;

    printk("write %s\n", temp);
    have_data = 1;
    wake_up_interruptible(&wq);     /* 唤醒阻塞在 read 里的进程 */
    return len;
}

这段代码的骨架值得记住：写者负责置位标志并唤醒读者；读者在无数据时睡，有数据时被唤醒。

七、完整实例：memdev #

7.1 memdev.h #

c
struct mem_dev {
    char *data;
    unsigned long size;
    wait_queue_head_t inq;      /* 读等待队列 */
};

7.2 驱动部分 #

c
static mem_major = MEMDEV_MAJOR;
bool have_data = false;         /* 标明设备有足够数据可供读 */

module_param(mem_major, int, S_IRUGO);

struct mem_dev *mem_devp;
struct cdev cdev;

static ssize_t mem_read(struct file *filp, char __user *buf, size_t size, loff_t *ppos)
{
    unsigned long p = *ppos;
    unsigned int count = size;
    int ret = 0;
    struct mem_dev *dev = filp->private_data;

    /* 判断读位置是否有效 */
    if (p >= MEMDEV_SIZE)
        return 0;
    if (count > MEMDEV_SIZE - p)
        count = MEMDEV_SIZE - p;

    while (!have_data) {                    /* 没有数据可读，考虑为什么用 while 而不是 if */
        if (filp->f_flags & O_NONBLOCK)
            return -EAGAIN;

        wait_event_interruptible(dev->inq, have_data);
    }

    if (copy_to_user(buf, (void *)(dev->data + p), count)) {
        ret = -EFAULT;
    } else {
        *ppos += count;
        ret = count;
        printk(KERN_INFO "read %d bytes(s) from %d\n", count, p);
    }

    have_data = false;      /* 表明不再有数据可读 */
    return ret;
}

static ssize_t mem_write(struct file *filp, const char __user *buf, size_t size, loff_t *ppos)
{
    unsigned long p = *ppos;
    unsigned int count = size;
    int ret = 0;
    struct mem_dev *dev = filp->private_data;

    if (p >= MEMDEV_SIZE)
        return 0;
    if (count > MEMDEV_SIZE - p)
        count = MEMDEV_SIZE - p;

    if (copy_from_user(dev->data + p, buf, count)) {
        ret = -EFAULT;
    } else {
        *ppos += count;
        ret = count;
        printk(KERN_INFO "written %d bytes(s) from %d\n", count, p);
    }

    have_data = true;               /* 有新的数据可读 */
    wake_up(&(dev->inq));           /* 唤醒读进程 */
    return ret;
}

为什么用 while 而不是 if——注释里专门留了这个思考题。答案是：wait_event_interruptible 返回后重新检查条件（第 3.4 节流程的 e 步），但如果用 if，条件可能在"被唤醒"与"真正执行到拷贝"之间被别的线程二次消耗掉。while 保证条件为真才往下走。这也是"疯狂兽群"场景下必须的写法——多个进程被同时唤醒，只有一个能拿到数据，其余的必须重新判断并睡回去。

7.3 初始化等待队列 #

c
for (i = 0; i < MEMDEV_NR_DEVS; i++) {
    mem_devp[i].size = MEMDEV_SIZE;
    mem_devp[i].data = kmalloc(MEMDEV_SIZE, GFP_KERNEL);
    memset(mem_devp[i].data, 0, MEMDEV_SIZE);

    /* 初始化等待队列 */
    init_waitqueue_head(&(mem_devp[i].inq));
}

等待队列必须在设备结构体分配之后、任何 open 之前初始化。忘了这一步，wait_event 会操作一个全零的链表头，直接崩。

7.4 配套的 poll 方法 #

c
unsigned int mem_poll(struct file *filp, poll_table *wait)
{
    struct mem_dev *dev = filp->private_data;
    unsigned int mask = 0;

    poll_wait(filp, &dev->inq, wait);   /* 将等待队列添加到 poll_table */

    if (have_data)
        mask |= POLLIN | POLLRDNORM;    /* readable */

    return mask;
}

有了它，应用层就能用 select 等待，而不必自己轮询。

7.5 应用层验证 #

写端（app-write.c）——写一次，睡 5 秒：

c
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(void)
{
    FILE *fp = NULL;
    char Buf[128];

    fp = fopen("/dev/memdev0", "r+");
    if (fp == NULL) {
        printf("Open Dev memdev Error!\n");
        return -1;
    }

    strcpy(Buf, "memdev is char dev!");
    printf("Write BUF: %s\n", Buf);
    fwrite(Buf, sizeof(Buf), 1, fp);

    sleep(5);
    fclose(fp);
    return 0;
}

读端（app-read.c）——用 select 等数据就绪：

c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <sys/select.h>
#include <sys/time.h>
#include <errno.h>

int main(void)
{
    int fd, ret;
    fd_set rds;
    char Buf[128];

    strcpy(Buf, "memdev is char dev!");
    printf("BUF: %s\n", Buf);

    fd = open("/dev/memdev0", O_RDWR);
    if (fd < 0) {
        perror("open");
        return -1;
    }

    FD_ZERO(&rds);
    FD_SET(fd, &rds);

    strcpy(Buf, "Buf is NULL!");
    printf("Read BUF1: %s\n", Buf);

    ret = select(fd + 1, &rds, NULL, NULL, NULL);   /* 一直阻塞到可读 */
    if (ret < 0) {
        printf("select error!\n");
        exit(1);
    }

    if (FD_ISSET(fd, &rds))
        read(fd, Buf, sizeof(Buf));

    printf("Read BUF2: %s\n", Buf);

    close(fd);
    return 0;
}

先跑读端（它会在 select 上睡着），再跑写端，读端就立即被唤醒并打印出数据。

八、整条链路串起来 #

应用 read(fd, buf, n)
   │
   ▼
驱动 xxx_read()
   │
   ├── 有数据？── 是 ──→ copy_to_user → 返回 n
   │
   └── 否
        ├── f_flags & O_NONBLOCK？── 是 ──→ return -EAGAIN （应用自己重试或改走 select）
        │
        └── 否
             └── wait_event_interruptible(wq, cond)
                   │ 进程置 TASK_INTERRUPTIBLE，挂到 wq，schedule()
                   ▼  ... 睡 ...
     中断 / 另一个进程 write()
        └── cond = 1; wake_up_interruptible(&wq)
                   │
                   ▼
             被唤醒 → 重新检查 cond → 成立则继续 copy_to_user
