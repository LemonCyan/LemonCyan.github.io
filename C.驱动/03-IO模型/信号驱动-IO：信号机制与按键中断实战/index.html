写驱动时绕不开一个尴尬：read 阻塞在那儿等数据，进程就什么都干不了；改用非阻塞轮询，又把 CPU 浪费在无意义的 read 上。信号驱动 IO 是第三条路：进程正常干自己的事，设备就绪时由内核发一个信号通知它。

一、信号驱动 IO 是第几种模型 #

钓鱼的类比最直白。盯着鱼漂不放，看到下沉才敢动作，这就是阻塞 IO；给鱼竿装个报警器，平时可以走开，铃响了再回来收竿，这就是信号驱动 IO。

五种 IO 模型的位置：

模型 进程状态 谁在等
阻塞 IO 睡眠 内核等下数据，进程陪着睡
非阻塞 IO 运行，反复问 进程自己轮询
IO 多路复用（select/poll/epoll） 睡眠 内核等多个 fd 中的任意一个
信号驱动 IO 运行 内核，就绪后主动通知
异步 IO（io_uring/aio） 运行 内核，连数据搬运都替你做完了

和 IO 多路复用的区别要分清：poll 虽然也能同时等多个 fd，但进程仍然阻塞在 poll() 上；信号驱动 IO 里进程连 poll 都不调，通知以信号的形式直接送上门。

代价是信号这套机制本身不好用：异步、不可重入、处理函数里能干的活极少。所以实际工程里 epoll 用得远比它多。但设备驱动这一侧必须支持它，因为 FASYNC 是 POSIX 要求的能力。

二、信号怎么送到进程：内核做代理 #

一个容易产生误解的地方：进程收信号时，并不是进程自己"发现"了信号。

实际情况是内核代理：

text
P2 调用 kill(P1, SIGUSR1)
  ↓
内核把该信号挂进 P1 的待处理信号队列（task_struct->pending）
  ↓
P1 继续跑，内核什么都不做
  ↓
P1 因系统调用 / 中断 / 异常进入内核态
  ↓
内核在处理完毕、返回用户态的前夕检查信号队列
  ↓
发现有未屏蔽信号 → 把用户态栈指针挪一挪，塞进信号处理函数的地址
  ↓
P1 「返回」用户态，实际跳进了信号处理函数
  ↓
处理函数返回 → 走 sigreturn 系统调用 → 恢复原上下文

关键在「返回用户态的前夕」这个时机。这也解释了为什么纯用户态死循环（不含任何系统调用）的进程收不到信号，它永远不进内核态，内核就没机会安排跳转。

两个检查点：

  • 从内核态返回用户态之前；
  • 在内核里睡眠被唤醒时（如果存在不可忽略的信号，会提前返回用户态）。

信号是内核里唯一真正异步的 IPC 机制。POSIX 实时扩展之后，信号还能携带附加信息（sigqueue / sigaction 的 SA_SIGINFO）。

信号的来源：

来源 例子
硬件 按 Ctrl+C 产生 SIGINT，按 Ctrl+\ 产生 SIGQUIT，按 Ctrl+Z 产生 SIGTSTP
硬件异常 除零产生 SIGFPE，非法内存访问产生 SIGSEGV
软件条件 alarm() 计时到点产生 SIGALRM，向已关闭管道写产生 SIGPIPE
显式发送 kill / raise / sigqueue / shell 的 kill 命令

发送权限有一个约束：发送方和接收方的 real UID 必须相同，或者发送方是 root。

三、信号一览与三种处理方式 #

kill -l 能列出全部信号，注意 32 和 33 是空缺的（内核内部保留给 SIGCANCEL/SIGSETXID，用户态不可用）：

bash
$ kill -l
 1) SIGHUP       2) SIGINT       3) SIGQUIT      4) SIGILL       5) SIGTRAP
 6) SIGABRT      7) SIGBUS       8) SIGFPE       9) SIGKILL     10) SIGUSR1
11) SIGSEGV     12) SIGUSR2     13) SIGPIPE     14) SIGALRM     15) SIGTERM
16) SIGSTKFLT   17) SIGCHLD     18) SIGCONT     19) SIGSTOP     20) SIGTSTP
21) SIGTTIN     22) SIGTTOU     23) SIGURG      24) SIGXCPU     25) SIGXFSZ
26) SIGVTALRM   27) SIGPROF     28) SIGWINCH    29) SIGIO       30) SIGPWR
31) SIGSYS      34) SIGRTMIN    …              64) SIGRTMAX

本篇关心的是 SIGIO（编号 29），它是异步 IO 通知的默认信号。

进程收到信号后有三种选择：

方式 做法 注意
忽略 signal(sig, SIG_IGN) SIGKILL 和 SIGSTOP 不能被忽略，否则进程无法被杀死/暂停
默认动作 signal(sig, SIG_DFL) 多数信号的默认动作是终止进程
捕获 传入自定义处理函数 只能捕获除 SIGKILL/SIGSTOP 之外的信号

关于「不可忽略」，准确说法是：SIGKILL 和 SIGSTOP 的处置方式由内核强制，signal() 传入的 handler 会被静默忽略。这是个安全阀，保证总有手段能停掉失控进程。

四、安装信号处理函数 #

signal() 的原型以可读性差著称：

c
void (*signal(int signum, void (*handler)(int)))(int);

拆开看就清楚了，它接收一个 handler、返回旧的 handler：

c
typedef void (*sighandler_t)(int);
sighandler_t signal(int signum, sighandler_t handler);

signal() 有两个历史包袱：不同 UNIX 实现语义不一致（BSD 会重置为默认动作，System V 不会），且无法传递附加信息。新代码应该用 sigaction()：

c
#include <signal.h>

struct sigaction sa;

memset(&sa, 0, sizeof(sa));
sa.sa_handler = my_handler;
sigemptyset(&sa.sa_mask);      /* 处理期间不额外屏蔽其他信号 */
sa.sa_flags = SA_RESTART;      /* 被信号打断的系统调用自动重启 */

if (sigaction(SIGIO, &sa, NULL) < 0) {
    perror("sigaction");
    return -1;
}

sa_flags 里两个常用的：

标志 作用
SA_RESTART 处理函数返回后，被该信号打断的系统调用自动重新执行，而不是返回 EINTR
SA_SIGINFO 使用 sa_sigaction 而不是 sa_handler，能拿到 siginfo_t（发送者 pid、附加数据等）

SA_RESTART 值得展开。不加它，信号到来时正在 read() 的进程会收到 EINTR，read 返回 -1。很多代码不检查 EINTR，于是偶发「读失败」的怪问题。加了 SA_RESTART，内核自动帮你重试。

但 SA_RESTART 不是万能的，有一批系统调用无论加不加都会返回 EINTR：poll、select、epoll_wait、nanosleep、sigsuspend，以及带超时的 recv 系列。这恰好是信号驱动 IO 最常用的那几个。

五、进程间主动发信号 #

驱动向进程发信号之前，先看清进程之间是怎么发的，SIGIO 走的也是同一套机制。

函数 作用 能否带数据
kill(pid, sig) 向指定进程发信号 否
raise(sig) 向自己发信号，等价于 kill(getpid(), sig) 否
alarm(sec) 定时到点向自己发 SIGALRM 否
setitimer() 更精细的定时器，可周期性触发 否
sigqueue(pid, sig, value) 带附加数据发送，需要 SA_SIGINFO 是 
c
#include <signal.h>
#include <sys/types.h>

/* 向 pid 发 SIGUSR1 */
if (kill(pid, SIGUSR1) < 0) {
    perror("kill");
}

/* 向自己发 */
raise(SIGUSR1);

/* 5 秒后收到 SIGALRM */
alarm(5);

/* 带一个整数过去 */
union sigval val;
val.sival_int = 42;
sigqueue(pid, SIGRTMIN, val);

kill 这个命名有历史误导性，它并不专用于「杀死」，而是通用的信号发送接口。kill -0 pid 不发送任何信号，只做权限和存在性检查，是探测进程是否存活的常用手法。

六、应用端：三项准备 #

要用上信号驱动 IO，应用端必须做三件事，顺序不能乱：

c
#include <fcntl.h>
#include <signal.h>
#include <unistd.h>

int fd = open("/dev/buttons", O_RDWR);
int oflags;

/* ① 安装信号处理函数 */
signal(SIGIO, sigio_handler);

/* ② 告诉内核：这个 fd 的信号发给哪个进程 */
fcntl(fd, F_SETOWN, getpid());

/* ③ 打开 FASYNC，让驱动知道「这个文件要异步通知」 */
oflags = fcntl(fd, F_GETFL);
fcntl(fd, F_SETFL, oflags | O_ASYNC);

三步各自的含义：

步骤 做什么 不做会怎样
① signal(SIGIO, h) 让进程能处理 SIGIO 信号到达后按默认动作处理，SIGIO 默认是终止进程
② F_SETOWN 设置 filp->f_owner 为目标进程 内核不知道该把信号发给谁，信号被丢弃
③ F_SETFL | O_ASYNC 触发驱动的 .fasync()，mode=1 驱动侧的 fasync_queue 一直是空的，永远不发信号

FASYNC 和 O_ASYNC 是同一个值的两个名字，头文件里 #define FASYNC O_ASYNC。用 O_ASYNC 更现代，但内核代码和多数教材写 FASYNC。

第 ③ 步必须放在 ② 之后。反过来的话，F_SETFL 触发 fasync_helper 时 f_owner 还是空的，这一次注册的记录里没有有效目标进程。

6.1 完整应用示例 #

c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>
#include <signal.h>
#include <errno.h>

static int sig_count = 0;
static int fd = -1;

static void sigio_handler(int signo)
{
    unsigned char key_val;
    int ret;

    sig_count++;

    /* 信号处理函数里只能调 async-signal-safe 的函数，
       read 和 printf 严格说都不在名单里，调试阶段凑合用 */
    ret = read(fd, &key_val, 1);
    if (ret == 1)
        printf("[%d] SIGIO=%d, key=0x%02x\n", sig_count, signo, key_val);
    else if (ret < 0 && errno != EINTR)
        perror("read");
}

int main(void)
{
    struct sigaction sa;
    int oflags;

    fd = open("/dev/buttons", O_RDWR);
    if (fd < 0) {
        perror("open /dev/buttons");
        return 1;
    }

    memset(&sa, 0, sizeof(sa));
    sa.sa_handler = sigio_handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    if (sigaction(SIGIO, &sa, NULL) < 0) {
        perror("sigaction");
        close(fd);
        return 1;
    }

    if (fcntl(fd, F_SETOWN, getpid()) < 0) {
        perror("F_SETOWN");
        close(fd);
        return 1;
    }

    oflags = fcntl(fd, F_GETFL);
    if (fcntl(fd, F_SETFL, oflags | O_ASYNC) < 0) {
        perror("F_SETFL");
        close(fd);
        return 1;
    }

    for (;;)
        sleep(10);

    close(fd);
    return 0;
}

主循环用 sleep(10)，这一点有讲究，第九章展开。

七、驱动端：三件套 #

POSIX 规定了 FASYNC 的语义，驱动侧要实现三件事：

# 工作 谁负责
1 处理 F_SETOWN，把目标 pid 存进 filp->f_owner 内核已完成，驱动不管
2 处理 F_SETFL，FASYNC 变化时调用驱动的 .fasync() 驱动必须实现
3 设备就绪时调 kill_fasync() 发信号 驱动必须调用

所以驱动实际只做第 2、3 项。用到的就一个结构体加两个函数：

c
struct fasync_struct;

int  fasync_helper(int fd, struct file *filp, int mode,
                   struct fasync_struct **fa);
void kill_fasync(struct fasync_struct **fa, int sig, int band);

7.1 把指针挂进设备结构体 #

c
struct button_dev {
    struct cdev cdev;
    struct fasync_struct *async_queue;    /* 异步通知队列 */
    /* ... 其他私有数据 ... */
};

这一行是必须的。fasync_helper 需要的是一个「能长期存活的 struct fasync_struct * 的地址」，它把链表头存在这里。

7.2 fasync 方法 #

c
static int button_fasync(int fd, struct file *filp, int mode)
{
    struct button_dev *dev = filp->private_data;

    return fasync_helper(fd, filp, mode, &dev->async_queue);
}

fasync_helper 内部维护一个双向链表：

  • mode 非 0（FASYNC 被设置）：分配一个 fasync_struct，记录 fd 和 filp，插入链表；
  • mode 为 0（FASYNC 被清除，或文件关闭）：从链表中摘除对应记录并释放。

驱动不需要自己 allocate、不需要 free、不需要加锁，这些全在 helper 里做完了。

7.3 就绪时发信号 #

c
if (dev->async_queue)                              /* 有进程在等才发 */
    kill_fasync(&dev->async_queue, SIGIO, POLL_IN);

band 参数的含义跟着 poll 的语义走：

事件 用哪个 band
可读 POLL_IN
可写 POLL_OUT
异常条件 POLL_ERR / POLL_HUP

这个值会被放进 siginfo_t.si_band（需要 SA_SIGINFO），进程据此判断是哪种事件。

kill_fasync 可以在中断上下文里调用。 这一点很多人不确定，但内核源码的注释写得很明确，fa_lock 也专门配成了 IRQ-safe 的自旋锁。所以按键这类「中断里产生数据」的场景可以直接在中断处理函数里发信号，不用绕到工作队列。

7.4 release 里必须注销 #

c
static int button_close(struct inode *inode, struct file *file)
{
    button_fasync(-1, file, 0);    /* mode=0，从链表摘除 */

    /* ... 其他清理 ... */
    return 0;
}

这是最容易漏的一步。漏了会怎样：进程退出后，async_queue 里还挂着一条指向已释放 struct file 的记录。下次 kill_fasync 遍历链表时会去访问那块已释放内存，典型的 use-after-free。

这类 bug 的恶劣之处在于不立刻复现。要等进程退出、内存被复用、再有一次设备事件，三个条件凑齐才崩，而且崩的位置跟真凶毫无关系。

八、完整实例：S3C2440 按键驱动 #

以 S3C2440 的 6 个按键为例。硬件上按键接在 GPG 口，按下时产生下降沿，松开时产生上升沿，两边都要捕获。

8.1 按键描述表 #

c
#include <linux/module.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/device.h>
#include <linux/interrupt.h>
#include <linux/gpio.h>
#include <linux/uaccess.h>

struct pin_desc {
    unsigned int pin;
    unsigned int key_val;
};

/* 6 个按键，注意数组大小必须和初始化项数一致 */
static struct pin_desc pins_desc[] = {
    { S3C2410_GPG(0),  0x01 },
    { S3C2410_GPG(3),  0x02 },
    { S3C2410_GPG(5),  0x03 },
    { S3C2410_GPG(6),  0x04 },
    { S3C2410_GPG(7),  0x05 },
    { S3C2410_GPG(11), 0x06 },
};

这里有个必须说的坑。 常见的老代码会写成：

c
static struct pin_desc pins_desc[4] = {
    {S3C2410_GPG(0),  0x01},
    {S3C2410_GPG(3),  0x02},
    {S3C2410_GPG(5),  0x03},
    {S3C2410_GPG(6),  0x04},
    {S3C2410_GPG(7),  0x05},    /* 超出！被丢弃 */
    {S3C2410_GPG(11), 0x06},    /* 超出！被丢弃 */
};

C 允许初始化项多于数组容量，多出来的被静默丢弃（只有 -Wexcess-initializers 会警告）。结果 pins_desc[4] 和 pins_desc[5] 全 0，而 request_irq 照样拿它们当 dev_id 传进去。中断来了 pindesc->pin 是 0，gpio_get_value(0) 读到的东西跟按键毫无关系。

现象是「前 4 个按键正常，后 2 个按键值永远是 0x01」。不写 [] 让编译器自己数，就不会有这个问题。

8.2 中断处理：读电平、发信号 #

c
static struct fasync_struct *button_async;
static unsigned char key_val;

static irqreturn_t button_irq(int irq, void *dev_id)
{
    struct pin_desc *pindesc = dev_id;
    unsigned int pinval;

    pinval = gpio_get_value(pindesc->pin);

    if (pinval) {
        key_val = 0x80 | pindesc->key_val;    /* 松开：高字节置位 */
    } else {
        key_val = pindesc->key_val;           /* 按下 */
    }

    /* 中断上下文可以直接调，内部锁是 IRQ-safe 的 */
    kill_fasync(&button_async, SIGIO, POLL_IN);

    return IRQ_HANDLED;
}

键值的编码规则：低 7 位是键号（0x01~0x06），最高位表示松手（0x81~0x86）。这样应用层一个 unsigned char 就能区分按下和松开。

按 GPIO 当前电平判断按下还是松开，比靠「第几次中断」推断可靠，中断从来不能假设成对出现。

8.3 open / read / close #

c
static int button_open(struct inode *inode, struct file *file)
{
    int i, ret;
    static const int irqs[] = {
        IRQ_EINT8, IRQ_EINT11, IRQ_EINT13,
        IRQ_EINT14, IRQ_EINT15, IRQ_EINT19,
    };

    for (i = 0; i < ARRAY_SIZE(pins_desc); i++) {
        ret = request_irq(irqs[i], button_irq, IRQF_TRIGGER_FALLING |
                          IRQF_TRIGGER_RISING, "button", &pins_desc[i]);
        if (ret) {
            pr_err("request_irq %d failed: %d\n", irqs[i], ret);
            while (i--)                              /* 回滚已申请的 */
                free_irq(irqs[i], &pins_desc[i]);
            return ret;
        }
    }

    file->private_data = &button_async;
    return 0;
}

static ssize_t button_read(struct file *file, char __user *buf,
                           size_t size, loff_t *ppos)
{
    if (size != 1)
        return -EINVAL;

    if (copy_to_user(buf, &key_val, 1))
        return -EFAULT;

    return 1;                    /* 返回实际读到的字节数，不是 copy_to_user 的返回值 */
}

static int button_close(struct inode *inode, struct file *file)
{
    int i;
    static const int irqs[] = {
        IRQ_EINT8, IRQ_EINT11, IRQ_EINT13,
        IRQ_EINT14, IRQ_EINT15, IRQ_EINT19,
    };

    button_fasync(-1, file, 0);                  /* 先注销异步队列 */

    for (i = 0; i < ARRAY_SIZE(pins_desc); i++)
        free_irq(irqs[i], &pins_desc[i]);

    return 0;
}

button_read 里那个 return 1 是个高频 bug 点。copy_to_user() 返回的是未拷贝成功的字节数，成功时返回 0。所以写 return copy_to_user(...) 的结果是：读成功却返回 0，应用层看到的是 EOF。

正确的约定是：成功返回拷贝的字节数，失败返回负的错误码。

8.4 fasync 与操作表 #

c
static int button_fasync(int fd, struct file *file, int mode)
{
    return fasync_helper(fd, file, mode, &button_async);
}

static const struct file_operations button_fops = {
    .owner   = THIS_MODULE,
    .open    = button_open,
    .read    = button_read,
    .release = button_close,
    .fasync  = button_fasync,
};

button_async 用全局静态变量而不是放进设备结构体，是因为这个例子里只有一个设备实例。多个实例时要放进各自的结构体，否则所有设备共用一个队列，A 设备的信号会发给 B 设备的进程。

8.5 注册与注销 #

c
static dev_t devid;
static struct cdev button_cdev;
static struct class *button_cls;

static int __init button_init(void)
{
    int ret;

    ret = alloc_chrdev_region(&devid, 0, 1, "button");
    if (ret)
        return ret;

    cdev_init(&button_cdev, &button_fops);
    button_cdev.owner = THIS_MODULE;
    ret = cdev_add(&button_cdev, devid, 1);
    if (ret) {
        unregister_chrdev_region(devid, 1);
        return ret;
    }

    button_cls = class_create("button");
    if (IS_ERR(button_cls)) {
        cdev_del(&button_cdev);
        unregister_chrdev_region(devid, 1);
        return PTR_ERR(button_cls);
    }

    if (IS_ERR(device_create(button_cls, NULL, devid, NULL, "buttons"))) {
        class_destroy(button_cls);
        cdev_del(&button_cdev);
        unregister_chrdev_region(devid, 1);
        return -ENODEV;
    }

    return 0;
}

static void __exit button_exit(void)
{
    device_destroy(button_cls, devid);
    class_destroy(button_cls);
    cdev_del(&button_cdev);
    unregister_chrdev_region(devid, 1);
}

module_init(button_init);
module_exit(button_exit);
MODULE_LICENSE("GPL");

注意 class_create("button") 只有一个参数，这是 6.4 之后的签名。老内核要写 class_create(THIS_MODULE, "button")，按你的版本二选一。

九、为什么 sleep 能被信号唤醒 #

应用端主循环写的是 sleep(10) 而不是 while(1);，这不是随手写的。

如果主循环是纯用户态空转：

c
while (1)
    ;                    /* 永远不进内核态 */

进程永远不进入内核态，内核就没有机会在「返回用户态的前夕」检查信号队列，信号会一直挂在 pending 队列里，直到进程下次因别的原因进内核。实际现象是按键按下去毫无反应，或者要等好几十次之后突然一次性爆发。

sleep() 底层是 nanosleep()，进程会进入内核并睡眠在 TASK_INTERRUPTIBLE 状态：

进程状态 收到信号时
TASK_INTERRUPTIBLE 被唤醒，处理完信号后 nanosleep 返回 EINTR
TASK_UNINTERRUPTIBLE 忽略信号，继续睡到自然醒

所以两个要点：

一、主循环里必须有能让进程进内核的操作，sleep、pause、poll、read 都行。pause() 是语义最贴合的选择，它专门就是「停下来等一个信号」。

二、sleep 被打断是正常行为，不是错误。 收到信号后 sleep(10) 会提前返回剩余秒数，而非睡满 10 秒。要循环等下一次，得自己处理：

c
while (1) {
    unsigned int left = sleep(10);
    /* left 是没睡完的秒数，非 0 说明被信号打断了 */
    (void)left;
}

十、常见故障与现象 #

现象 原因 检查
信号完全不来 ③ 步 O_ASYNC 没设 cat /proc/<pid>/fdinfo/<fd> 看 flags 里有没有 O_ASYNC
信号不来，但 fasync 被调用过 ② 步 F_SETOWN 在 O_ASYNC 之后 调换顺序
进程直接被杀死 SIGIO 默认动作就是终止，handler 没装上 确认 sigaction 返回 0
只收到一次信号就静默 SIGIO 是普通信号，不排队 用 SIGRTMIN+1 之类的实时信号代替
偶发 read 返回 -1 信号打断系统调用，errno == EINTR 加 SA_RESTART 或显式处理 EINTR
前几个按键正常，后面的读出来是 0x01 pins_desc 数组声明小了，多出的初始化被丢弃 用 [] 让编译器数
read 成功但应用读不到数据 return copy_to_user(...) 返回 0 改成 return 1
主循环空转时无反应 进程不进内核态，没机会检查信号队列 换成 sleep / pause
卸载模块时崩溃 release 里没注销 fasync 队列 加 xxx_fasync(-1, filp, 0)
第二个进程 open 失败 request_irq 在 open 里重复注册 把中断注册挪到 module_init

最后一条值得多说。request_irq 放在 open 里，单进程使用时完全正常，一旦两个进程同时打开设备，第二次 request_irq 会返回 -EBUSY（除非带 IRQF_SHARED 且 dev_id 唯一）。中断是设备资源，不是「每次打开一份」的资源，正确位置是 module_init，open 只做引用计数。

「SIGIO 不排队」那条也是常见困惑来源。标准信号只有「有/无」两种状态，连续来 5 个 SIGIO，进程处理期间来的都被丢弃，只留一个 pending。要保证每次事件都不丢，要么用实时信号（SIGRTMIN 起，它们排队），要么在 handler 里一次性把所有数据读干净。

十一、信号驱动、poll 与 epoll 怎么选 #

最后给一张选型表，避免用错：

场景 选什么 理由
只等一个设备，且事件稀疏（按键、传感器中断） 信号驱动 IO 无需轮询，CPU 占用接近 0
等多个设备 epoll 信号只有一个队列，多 fd 会互相干扰
事件高频（网卡、块设备） epoll 信号开销大，且不排队会丢事件
需要精确控制超时 poll / epoll_wait 信号没有超时概念
老代码兼容、驱动已经实现了 fasync 信号驱动 IO 不用改驱动

信号驱动 IO 的真实定位是「极低事件率 + 单设备」。按键、GPIO 中断、串口的 SIGIO，这些场景下它比 epoll 更省资源，进程压根不需要维护一个等待队列。

一旦事件率上来了，或者设备数超过一个，就该换 epoll。信号这套机制的硬伤（不排队、处理函数里限制多、无法设超时）在高频场景下会全部暴露。
