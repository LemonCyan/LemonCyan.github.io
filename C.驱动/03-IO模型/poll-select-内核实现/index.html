上一篇讲了驱动侧怎么写 .poll，这一篇钻进内核，看 select() / poll() 从系统调用到驱动回调之间发生了什么。

源码主要分布在 fs/select.c。

一、三个核心问题 #

select() 和 poll() 是最经典的多路复用机制，允许一个线程监控成百上千个文件描述符的可读、可写状态。要把它的内核实现讲清，需要回答三个问题：

  1. 用户空间的数据怎么组织并传进内核？—— pollfd 数组与 poll_list 分页链表
  2. 内核用什么结构管理这些监测事件？—— poll_wqueues 三层结构
  3. 驱动底层的等待队列是怎么被挂上去、又怎么唤醒回来的？—— __pollwait 与 pollwake

二、数据结构 #

poll 机制在内核中通过多级链表和页面指针来管理监测事件。

2.1 用户空间数据传入：struct pollfd #

应用层传递一组 pollfd 数组给内核，由 unsigned int nfds 指定数组长度。

c
struct pollfd {
    int   fd;       /* 被监控的文件描述符 */
    short events;   /* 期望监听的事件掩码（输入项，如 POLLIN / POLLOUT） */
    short revents;  /* 实际发生并返回的就绪事件掩码（输出项） */
};

fd 与 events 是输入，revents 是输出——内核不会改动前两个，只回填第三个。这个设计让应用层不必在每次调用前重建整个数组。

2.2 内部分段：struct poll_list #

当描述符数量较大时，内核将用户空间数据分段存放在由 poll_list 链接的单向链表中：

c
struct poll_list {
    struct poll_list *next;     /* 链表指针 */
    int len;                    /* 本页中保存的 pollfd 数量 */
    struct pollfd entries[0];   /* 指向存放 pollfd 数据的弹性数组 */
};

entries[0] 是零长度数组（C99 弹性数组成员的前身），它不占结构体空间，实际数据紧跟在 struct poll_list 之后。这样一块分配就能同时装下链表头和一批 pollfd。

内核对每个物理页保存的最大数量做了优化限制，通常为 POLLFD_PER_PAGE。

为什么要分页？ 因为 nfds 可能非常大（成千上万），一次性 kmalloc 一大块连续内存容易失败。按页分配合成链表，既避免了连续内存压力，又不需要限制 nfds——这正是 poll 相比 select 的 FD_SETSIZE 限制的优势所在。

poll_list ──▶ [next | len=N | fd0 fd1 ... fdN-1] ──▶ [next | len=M | ...] ──▶ NULL
              (第 1 页)                              (第 2 页)

2.3 等待队列容器：struct poll_wqueues #

这是内核管理并挂接驱动等待队列的核心容器，负责把当前轮询任务绑定到具体驱动设备的等待队列中：

成员 作用
poll_table pt 向驱动提供的接口函数指针（驱动拿到的 poll_table_struct * 就是它）
struct poll_table_page *table 指向物理内存页分配链表，每页包含多个轮询表项 poll_table_entry
struct task_struct *polling_task 指向发起 poll 调用的当前进程控制块

2.4 三层结构的挂靠关系 #

  struct poll_wqueues
  +------------------+
  | poll_table pt    |-------> 指向 poll_queue_proc 回调函数（即 __pollwait）
  | polling_task     |-------> 指向当前线程进程结构体 (task_struct)
  | table (链表指针)  |
  +--------|---------+
           |
           v   struct poll_table_page
         [ next | struct poll_table_entry entries[N] ]
                  |
                  v   struct poll_table_entry（单个轮询表项）
                [ file         ] ------> 指向被轮询的特定设备文件
                [ key          ] ------> 期望监控的事件掩码
                [ wait_address ] ------> 指向驱动中定义的 wait_queue_head_t
                [ wait         ] (wait_queue_t)
                  |
                  +-------------------> 挂靠并注册到驱动底层的 wq 链表中！

关键是最后一跳：poll_table_entry.wait 这个 wait_queue_t 最终被 add_wait_queue() 挂进了驱动自己的 wait_queue_head_t。这就是"内核的 poll 机制"与"驱动的等待队列"之间的接缝。

应用 poll()  ─┐
              ├─ poll_wqueues ─ poll_table_entry ─ add_wait_queue() ─┐
驱动 .poll ───┘                                                      │
                                                                     ▼
                                             驱动里的 wait_queue_head_t (wq)
                                                                     ▲
驱动中断 ── wake_up_interruptible(&wq) ──────────────────────────────┘

三、执行流程 #

从用户调用 poll() 直至就绪返回，内核的运转顺序如下：

sequenceDiagram
    autonumber
    participant U as 用户空间 (app)
    participant G as Glibc 库 (sys_poll)
    participant K as 通用内核层 (do_sys_poll)
    participant DP as 循环处理核心 (do_poll)
    participant D as 设备驱动层 (f_op->poll)

    U->>G: 调用 poll(fds, nfds, timeout)
    G->>K: 陷入内核，触发 do_sys_poll
    K->>K: 从用户空间拷贝 fds 数组并初始化 poll_wqueues
    K->>DP: 执行核心处理环路 do_poll()

    loop 循环轮询每一个文件描述符
        DP->>D: 调用驱动的 poll() 方法并传入 poll_table
        activate D
        D->>D: 调用 poll_wait()
        D->>DP: 注册当前等待队列项 (wait_queue_t)，返回状态掩码 mask
        deactivate D
    end

    alt 是否有至少一个就绪事件，或者已超时？
        DP->>K: 是（获取所有 mask），跳出循环
    else 否（所有设备都未就绪）
        DP->>DP: 调用 poll_schedule_timeout() 挂起当前进程，让出 CPU 进入休眠
        Note over DP: 进程处于浅度睡眠状态，等待被唤醒...
    end

    Note over D: 驱动接收到硬件数据/中断
    D->>DP: 调用 wake_up() 唤醒队列上的挂起进程

    Note over DP: 唤醒或超时时间到
    DP->>DP: 再次循环遍历各个驱动检测就绪状态
    DP->>K: 返回实际的就绪 revents 掩码
    K->>G: 释放并回收 poll_wqueues，数据拷贝回用户空间
    G->>U: 返回就绪数量，应用层恢复执行

四、内核源码关键函数 #

4.1 do_poll：轮询休眠核心环路 #

在 fs/select.c 中，do_poll 利用一个无限的 for(;;) 循环检查所有被监测描述符的就绪状态：

c
static int do_poll(unsigned int nfds, struct poll_list *list,
                   struct poll_wqueues *wait, struct timespec *end_time)
{
    int count = 0;
    struct poll_list *walk;

    for (;;) {
        /* 1. 遍历链表中的所有描述符 */
        for (walk = list; walk; walk = walk->next) {
            struct pollfd *pfd, *pfd_end;

            pfd = walk->entries;
            pfd_end = pfd + walk->len;

            for (; pfd != pfd_end; pfd++) {
                /* 2. 调用具体的驱动事件检测函数 */
                if (do_pollfd(pfd, &wait->pt)) {
                    count++;                /* 有就绪事件，计数器加 1 */
                    wait->pt._qproc = NULL; /* 挂载成功后，之后无需重复挂载 */
                }
            }
        }

        /* 3. 判断是否满足退出条件 */
        if (count || !*timeout || signal_pending(current))
            break;

        /* 4. 让出 CPU，进程休眠，等待被驱动唤醒或超时 */
        if (!poll_schedule_timeout(wait, TASK_INTERRUPTIBLE, to, slack))
            *timeout = 0;                   /* 超时时间到 */

        count = 0;                          /* 清空计数，重新轮询 */
    }
    return count;
}

四个要点：

行 作用 注意
2 do_pollfd() 最终调用驱动的 .poll 每轮都调，所以驱动的 .poll 必须无副作用
2 wait->pt._qproc = NULL 只要有一个 fd 就绪，后续不再重复挂队列
3 三个退出条件 有就绪 / 超时 / 收到信号
4 poll_schedule_timeout 睡眠期间进程可被信号打断

_qproc = NULL 这一行很关键——它解释了为什么 poll_wait() 内部要判断 if (p && p->_qproc)：一旦已经确定要返回，就没必要再往驱动队列里挂新表项了。

4.2 __pollwait：挂靠驱动回调 #

当驱动程序在 hello_poll 中调用 poll_wait(file, &wq, ptbl) 时，如果 ptbl 仍然生效，它实质上调用了内核预设的回调函数 __pollwait：

c
static void __pollwait(struct file *filp, wait_queue_head_t *wait_address,
                       poll_table *p)
{
    struct poll_wqueues *pwq = container_of(p, struct poll_wqueues, pt);
    struct poll_table_entry *entry = poll_get_entry(pwq);   /* 得到一个轮询表项 */

    if (!entry)
        return;

    /* 绑定目标文件 */
    entry->filp = get_file(filp);
    entry->wait_address = wait_address;
    entry->key = p->_key;

    /* 初始化等待队列项，设置自定义唤醒回调函数为 pollwake */
    init_waitqueue_func_entry(&entry->wait, pollwake);
    entry->wait.private = pwq;      /* 私有指针指回 poll_wqueues */

    /* 挂靠：将等待项挂载到驱动的等待队列头 wait_address 中 */
    add_wait_queue(wait_address, &entry->wait);
}

两个技术点：

  1. container_of(p, struct poll_wqueues, pt) —— 驱动传回来的 poll_table * 其实是 poll_wqueues 的第一个成员，所以反向就能拿回整个容器。这和 container_of(inode->i_cdev, ...) 是同一个套路。
  2. init_waitqueue_func_entry(&entry->wait, pollwake) —— 这里给等待项指定了自定义唤醒函数 pollwake，而不是默认的 autoremove_wake_function。这是 poll 能工作的关键：唤醒时走的不是普通路径。

4.3 pollwake：驱动唤醒的回填 #

当数据就绪时，驱动调用 wake_up(wait_address)。系统会调用之前注册的唤醒函数 pollwake：

  1. pollwake 读取 entry->wait.private，定位到对应的 poll_wqueues 结构体；
  2. 更改 polling_task（发起 poll 的那个休眠进程）的状态为 TASK_WAKING；
  3. 调用 try_to_wake_up(polling_task)，告诉 CPU 调度器将此进程重新排入就绪运行队列，从而触发 do_poll 环路的下一次遍历并正常退出。
驱动 wake_up(&wq)
   │
   ▼
__wake_up_common 遍历队列 → 遇到 entry->wait
   │
   ▼  func = pollwake（不是普通的 autoremove_wake_function）
pollwake(entry->wait, mode, flags, key)
   │
   ▼  private 指向 poll_wqueues
   pwq->polling_task → try_to_wake_up()
   │
   ▼
do_poll 从 poll_schedule_timeout 返回 → 重新遍历 → 拿到 POLLIN → 返回用户态

五、为什么驱动侧不加锁也能工作 #

一个常见疑问：驱动在 .poll 里读 havedata，中断里改 havedata，中间没有任何锁，为什么不会丢唤醒？

答案藏在 add_wait_queue() 里。它内部会获取 wait_queue_head 的自旋锁：

c
void add_wait_queue(wait_queue_head_t *q, wait_queue_t *wait)
{
    unsigned long flags;

    wait->flags &= ~WQ_FLAG_EXCLUSIVE;
    spin_lock_irqsave(&q->lock, flags);
    __add_wait_queue(q, wait);
    spin_unlock_irqrestore(&q->lock, flags);
}

而驱动的 wake_up 同样要拿这把锁。于是：

CPU0 (驱动 .poll)                    CPU1 (中断)
poll_wait → add_wait_queue
  拿 q->lock ─┐
  挂 entry    │   ← 中断在此刻到，wake_up 想拿 q->lock，被挡住
  放 q->lock ─┘
              之后 wake_up 拿到锁 → 看到队列里已有 entry → 唤醒它

"挂队列"与"检查条件"都在同一把锁保护下进行，所以要么中断在挂队列之前发生（此时 .poll 里读到的 havedata 已是新值，直接返回就绪），要么在之后发生（唤醒能命中已挂上的项）。这就是无锁写法的正确性依据。

前提是你先 poll_wait 再读条件——顺序反了就会丢唤醒。这是个非常隐蔽的 bug 来源。
