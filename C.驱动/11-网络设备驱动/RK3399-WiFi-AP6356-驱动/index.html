一个必须先说清的前提：AP6356 的芯片是 BCM4356，它在 Linux 下有两条驱动路线。一条是内核主线的 brcmfmac（树内，drivers/net/wireless/broadcom/brcm80211/brcmfmac/）；另一条是博通自己发布的 dhd（bcmdhd，wlan.ko），只出现在 Rockchip/Vendor/Android BSP 里，由 drivers/net/wireless/rockchip_wlan/rkwifi/ 这类目录包着，永远不进内核主线。本文记录的是第一条路线，原因和第 9 章会讲的取舍有关；第二条路线在文末单独交代它为什么存在。

一、AP6356 模块的硬件组成 #

先把「模组」和「芯片」分开。芯片是一颗裸 die 加上必要的模拟电路；模组把晶振、匹配网络、天线接口、屏蔽罩、批量的射频校准数据一起封进一个 15 × 13 × 1.5 mm 的壳里。板厂拿到模组就能上板，不用自己调 PA 的偏置和滤波。

AP6356 是正基（AMPAK）做的模组，里面的主芯片是博通 BCM4356。规格书（AP6356 Datasheet，REV 1.0，2014/07/25）写得很直白：

  • WLAN 标准：IEEE 802.11a/b/g/n/ac，2×2 MIMO；
  • 2.4 GHz 频段 2.400 ~ 2.497 GHz，Ch1 ~ Ch14；5 GHz 频段 4.900 ~ 5.845 GHz；
  • 蓝牙：Bluetooth V4.1，1/2/3 Mbps，主机接口 UART，频段 2402 ~ 2480 MHz，79 信道；
  • WiFi 接口：SDIO 或 PCIe（二选一，由 GPIO8_9 决定）；
  • BT 接口：UART / PCM；
  • 工作温度 −10 ~ 65 ℃，存储温度 −40 ~ 85 ℃。

802.11n 双流下理论速率 867 Mbps，这是模组的射频能力上限，能不能跑到看板子的 SDIO 时序和天线。

模组自带射频校准。这一点决定了后面第 13 章的所有讨论：pa2ga0、pa5ga1、mcsbw205glpo 这类参数不是驱动算出来的，是产线逐颗校准后写进 NVRAM 文件的。驱动做的事只是把文件喂进去。

二、WiFi 与 BT 二合一的结构 #

二合一省的是成本和板面积，代价是两套完全不同的总线挤在一个 50 pin 的封装里。

三类接口各管一摊：

接口 归属 传什么
SDIO（4 bit） WiFi 802.11 数据帧、控制命令、固件下载
UART 蓝牙 HCI 命令/事件/A2DP 音频数据
PCM 蓝牙 通话用的同步语音（SCO）

放音乐走 UART，蓝牙通话走 PCM——数据是异步的、语音是实时的，两者不能共用一条链路。

于是这个模组上会同时出现 wlan0 和 hci0 两个完全独立的设备节点，它们共享 VBAT 和 VDDIO 两路电源，各有一套 *_REG_ON 使能脚。第 14 章讲蓝牙时要把这条边界守住。

3.2 电源 #

模组需要两路电源（规格书 4.2.2）：

符号 描述 引脚 Min Typ Max
VBAT Main power voltage source input 36 3.0 V 3.6 V 4.8 V
VDDIO I/O Voltage supply input 34 1.7 V — 3.6 V

绝对最大额定值：VBAT −0.5 ~ 5.5 V，VDDIO −0.5 ~ 3.8 V。

两路电在 NanoPC-T4 上的来源不同：

  • VBAT 来源：板级 VCC3V3_SYS，由 12 V 输入经稳压管 NB680GD 降压得到，落在 3.0 ~ 4.8 V 窗口内；
  • VDDIO 来源：rk808 电源管理芯片第 61 号引脚输出，1.8 V；
  • LPO 来源：rk808 第 67 号引脚 CLK32KOUT2 输出的 RTC_CLKO_WIFI，32.768 kHz。

LPO 这条容易被忽略。规格书第 9 章给了外部低功耗时钟的电气要求：标称 32.768 kHz、精度 30 ppm、占空比 30 ~ 70 %、幅度 1600 ~ 3300 mV p-p、输入阻抗 > 100 kΩ（< 5 pF）、抖动（300 Hz ~ 15 kHz 积分）< 1 Hz。这条路断了，蓝牙待机和 WiFi 低功耗模式都会出怪事，但设备照样枚举，最难查。

3.3 供电一致性这条死规矩 #

WiFi 的 IO 是两段拼起来的：一段是主控 RK3399 侧的 SDIO 引脚（CLK/CMD/D0~D3）的供电，另一段是模组 VDDIO 引脚的供电。两边必须一致，否则轻则枚举不到卡，重则信号电平打架。

这也是为什么 SDIO 工作模式按 VDDIO 分家：

VDDIO 模式 速率档
1.8 V 超高速（UHS-I） SDR50（100 Mbps，100 MHz）、SDR104（208 MHz）、DDR50（50 MHz 双沿）
3.3 V 高速 / 默认 默认 25 MHz、高速 50 MHz

NanoPC-T4 走的是 1.8 V，所以设备树里能放心写 sd-uhs-sdr104。换一块 VDDIO 供 3.3 V 的板子，这一行必须删掉，否则 SDIO 会直接降级或枚举失败。

这张表能直接推出两件事。第一，SDIO0 的六根信号全部落在 GPIO2 的 C/D 段，所以设备树里 sdio0_bus4、sdio0_cmd、sdio0_clk 全是 bank 2。第二，WL_REG_ON 是 GPIO0_B2，也就是 gpio0 控制器的第 10 号（B 段第 3 个，8 + 2 = 10），这解释了后面 reset-gpios = <&gpio0 10 GPIO_ACTIVE_LOW> 里那个 10 是怎么来的。

四、设备树里的 AP6356 节点 #

linux 6.3 的主线 arch/arm64/boot/dts/rockchip/ 下没有现成的 AP6356 支持，rk3399-evb.dts 得自己补。补的东西分四块：sdio_pwrseq、wifi_enable_h pinctrl、&sdio0 属性、以及两个 *-platdata 平台节点。

4.1 sdio_pwrseq：控制 WiFi 上下电 #

arch/arm64/boot/dts/rockchip/rk3399-evb.dts 根节点下新增：

dts
sdio_pwrseq: sdio-pwrseq {
    compatible = "mmc-pwrseq-simple";
    clocks = <&rk808 1>;
    clock-names = "ext_clock";
    pinctrl-names = "default";
    pinctrl-0 = <&wifi_enable_h>;

    /*
     * On the module itself this is one of these (depending
     * on the actual card populated):
     * - SDIO_RESET_L_WL_REG_ON
     * - PDN (power down when low)
     */
    reset-gpios = <&gpio0 10 GPIO_ACTIVE_LOW>; /* GPIO0_B2 */
};

逐条拆：

属性 含义 关键点
compatible "mmc-pwrseq-simple" 对应驱动 drivers/mmc/core/pwrseq_simple.c，MMC 核心自带
clocks <&rk808 1> 取 rk808 这个 clock provider 的 1 号时钟，即 rtc_clko_wifi
clock-names "ext_clock" pwrseq 驱动按这个名字 clk_get，名字错了就拿不到 clock
pinctrl-names / pinctrl-0 default → wifi_enable_h 上电前先把 GPIO0_B2 复用成普通 GPIO
reset-gpios <&gpio0 10 GPIO_ACTIVE_LOW> 低电平进复位，即低电平时 WiFi 关闭

三个属性缺一不可。clocks 那条最隐蔽：mmc-pwrseq-simple 会在上电时打开 ext_clock 并保持，LPO 没有它，模组就没有 32.768 kHz 参考。设备树里漏了 clock-names = "ext_clock"，日志里不报错，后面蓝牙休眠会莫名失败。

4.2 wifi_enable_h：引脚复用节点 #

RK3399 有 5 组 GPIO（GPIO0 ~ GPIO4），每组用 A0~A7 / B0~B7 / C0~C7 / D0~D7 编号。sdio_pwrseq 引用了 wifi_enable_h，就得在 &pinctrl 下把它定义出来：

dts
sdio-pwrseq {
    wifi_enable_h: wifi-enable-h {
        rockchip,pins =
            <0 RK_PB2 RK_FUNC_GPIO &pcfg_pull_none>;
    };
};

rockchip,pins 的四个字段是固定的：

字段 含义 本例
PIN_BANK 引脚所在 bank 0（GPIO0 ~ GPIO3 对应 0 ~ 3）
PIN_BANK_IDX bank 内引脚号，0 ~ 31 RK_PB2，即 B 段第 2 个 = 10
MUX 复用功能，0 = 普通 GPIO，1~N = 特殊功能 RK_FUNC_GPIO
phandle 电气特性 pcfg_pull_none，不上拉不下拉

所以这一行读作：把 GPIO0_B2 配成普通 GPIO，电气特性为无上下拉。规格书把 WL_REG_ON 定义为「Low asserting reset」，主动驱动、不需要外部偏置，pcfg_pull_none 是对的。

绑定文档在 Documentation/devicetree/bindings/pinctrl/rockchip,pinctrl.txt 和 pinctrl-bindings.txt。

4.3 sdio0：控制器本体 #

sdio0 节点在 arch/arm64/boot/dts/rockchip/rk3399.dtsi 里已经定义好，rk3399-evb.dts 只是补属性：

dts
sdio0: dwmmc@fe310000 {
    compatible = "rockchip,rk3399-dw-mshc",
                 "rockchip,rk3288-dw-mshc";
    reg = <0x0 0xfe310000 0x0 0x4000>;
    interrupts = <GIC_SPI 64 IRQ_TYPE_LEVEL_HIGH 0>;
    max-frequency = <150000000>;
    clocks = <&cru HCLK_SDIO>, <&cru SCLK_SDIO>,
             <&cru SCLK_SDIO_DRV>, <&cru SCLK_SDIO_SAMPLE>;
    clock-names = "biu", "ciu", "ciu-drive", "ciu-sample";
    fifo-depth = <0x100>;
    power-domains = <&power RK3399_PD_SDIOAUDIO>;
    resets = <&cru SRST_SDIO0>;
    reset-names = "reset";
    status = "disabled";
};

dtsi 里 status = "disabled"，板级 dts 负责打开。四个时钟名字要对上 Designware MMC 驱动的预期：biu 是总线接口单元时钟，ciu 是卡接口单元时钟，ciu-drive 和 ciu-sample 是输出/采样相位用的分频时钟——SDR104 的调相位（tuning）全靠后两个。

fifo-depth = <0x100> 对应 256 深度 FIFO，启动日志里有一行印证：

text
dwmmc_rockchip fe310000.mmc: DW MMC controller at irq 64,32 bit host data width,256 deep fifo

power-domains = <&power RK3399_PD_SDIOAUDIO> 说明 SDIO 控制器和音频共享一个电源域，休眠策略会互相影响。

4.4 sdio0 的 pinctrl 分组 #

dtsi 的 &pinctrl 下已有一整套 sdio0 引脚组：

dts
sdio0 {
    sdio0_bus1: sdio0-bus1 {
        rockchip,pins = <2 RK_PC4 1 &pcfg_pull_up>;
    };

    sdio0_bus4: sdio0-bus4 {
        rockchip,pins =
            <2 RK_PC4 1 &pcfg_pull_up>,
            <2 RK_PC5 1 &pcfg_pull_up>,
            <2 RK_PC6 1 &pcfg_pull_up>,
            <2 RK_PC7 1 &pcfg_pull_up>;
    };

    sdio0_cmd: sdio0-cmd {
        rockchip,pins = <2 RK_PD0 1 &pcfg_pull_up>;
    };

    sdio0_clk: sdio0-clk {
        rockchip,pins = <2 RK_PD1 1 &pcfg_pull_none>;
    };

    sdio0_cd: sdio0-cd {
        rockchip,pins = <2 RK_PD2 1 &pcfg_pull_up>;
    };

    sdio0_pwr: sdio0-pwr {
        rockchip,pins = <2 RK_PD3 1 &pcfg_pull_up>;
    };

    sdio0_bkpwr: sdio0-bkpwr {
        rockchip,pins = <2 RK_PD4 1 &pcfg_pull_up>;
    };

    sdio0_wp: sdio0-wp {
        rockchip,pins = <0 RK_PA3 1 &pcfg_pull_up>;
    };

    sdio0_int: sdio0-int {
        rockchip,pins = <0 RK_PA4 1 &pcfg_pull_up>;
    };
};

注意 sdio0_clk 用的是 pcfg_pull_none，其余数据/命令线是 pcfg_pull_up。时钟不加上下拉是对的——加了会拖慢上升沿，208 MHz 下直接崩。数据线必须有上拉，不然总线浮空时会读到假数据。

sdio0_wp 是 GPIO0_A3、sdio0_int 是 GPIO0_A4。GPIO0_A3 和 WL_HOST_WAKE 是同一个脚，接线复用了它——所以 WiFi 中断不用 SDIO 带内中断，而是走 GPIO 带外（out-of-band）中断。这一点第 12 章会展开。

4.5 板级 dts 里给 &sdio0 补的属性 #

dts
&sdio0 {
    clock-frequency = <150000000>;
    clock-freq-min-max = <200000 150000000>;
    supports-sdio;
    bus-width = <4>;
    disable-wp;
    cap-sd-highspeed;
    cap-sdio-irq;
    keep-power-in-suspend;
    mmc-pwrseq = <&sdio_pwrseq>;
    non-removable;
    num-slots = <1>;
    pinctrl-names = "default";
    pinctrl-0 = <&sdio0_bus4 &sdio0_cmd &sdio0_clk>;
    sd-uhs-sdr104;
    status = "okay";
};
属性 作用 写错的后果
clock-frequency 上限 150 MHz 超范围调相位失败
clock-freq-min-max 最低 200 kHz、最高 150 MHz 枚举阶段需要低频
supports-sdio 声明这是 SDIO 而非 SD 卡槽 不写则不加载 SDIO 功能驱动
bus-width = <4> 4 位数据 写 1 位带宽掉一半
disable-wp 关写保护检测 不关会去读一个不存在的 WP 脚
cap-sd-highspeed 允许 50 MHz 高速 只能跑 25 MHz
cap-sdio-irq 允许 SDIO 带内中断 退化到轮询，延迟上去
keep-power-in-suspend 挂起时保电 休眠后唤醒要重新上电
mmc-pwrseq = <&sdio_pwrseq> 绑定上电时序控制器 不写则 WL_REG_ON 永不拉高，卡枚举不到
non-removable 不可插拔，不检测 CD 会等一个永远不来的插卡事件
pinctrl-0 只用 bus4 + cmd + clk 多挂 cd/wp/int 会抢 GPIO
sd-uhs-sdr104 开 SDR104（需 1.8 V IO） 掉到 SDR50 或更慢

mmc-pwrseq 这一行是整份设备树里最关键的一行。MMC 核心在 mmc_host 扫描卡之前会调 pwrseq->post_power_on，把 WL_REG_ON 从低拉高并保持至少 1 ms，然后才发 CMD52 去读 CIS。没有这个绑定，卡根本不会出现在 mmc1 上。启动日志里的对应行是：

text
dwmmc_rockchip fe310000.mmc: allocated mmc-pwrseq

看到这行，说明 pwrseq 已经挂上了。

五、SDIO 接口的配置 #

5.1 三条路径的分工 #

SDIO 本身是 Host-Device 结构：所有通信都由 Host 发命令发起，Device 只负责解析。驱动分三层：

层 是什么 在本文里对应
主机控制器驱动 RK3399 的 Designware MMC 控制器 dwmmc_rockchip，控制 fe310000.mmc
SDIO 设备驱动 认卡、读 CIS、绑功能号 MMC 核心 + brcmfmac 的 SDIO 层
WiFi 协议/芯片驱动 802.11 与厂商固件通道 brcmfmac + 固件

再往上还有一个和平台强相关但不属于 WiFi 协议栈的东西：rfkill。Rockchip 自己加了一份 rfkill-wlan.c / rfkill-bt.c，负责管住 WL_REG_ON、BT_REG_ON、WL_HOST_WAKE、BT_WAKE 这几根脚，以及模组级的 VBAT 开关。这部分代码不在主线，第 10 章会讲怎么从 Rockchip BSP 里搬过来。

5.2 AP6356 的 SDIO 能力 #

规格书 9.1 节：模组支持 SDIO 3.0，向下兼容 SDIO 2.0，4 位数据宽度。

模式 电压 时钟 数据速率
默认（Default） 3.3 V 25 MHz 12.5 MB/s 量级
高速（High Speed） 3.3 V 50 MHz 25 MB/s 量级
SDR50 1.8 V 100 MHz 100 Mbps
SDR104 1.8 V 208 MHz 208 MHz 单沿
DDR50 1.8 V 50 MHz 双沿

三个 SDIO 功能号的块大小上限：

功能号 用途 Max BlockSize / ByteCount
Function 0 标准 SDIO（CIS、CCCR、FBR） 32 B
Function 1 Backplane，访问芯片内部 SoC 地址空间 64 B
Function 2 WLAN，走 DMA 做数据包搬运 512 B

Function 2 的 512 B 是 WiFi 吞吐的硬门槛——每次 DMA 最多搬 512 字节，吞吐靠并发流水堆上去。

5.3 带内中断与带外中断 #

规格书明确写了模组「有能力停掉 SDIO 时钟并把中断信号映射到一个 GPIO 引脚」，这个 out-of-band 中断用来通知主机 WLAN 设备想打开 SDIO 接口。同时模组内部也能强制控制门控时钟。

实际工程上有两种走法：

  • 带内中断：用 DAT1 复用作中断线，靠 SDIO 协议里的 interrupt 机制，对应 cap-sdio-irq；
  • 带外中断：单独占一根 GPIO，对应 WL_HOST_WAKE。

NanoPC-T4 板子上这两个都做了：设备树既写了 cap-sdio-irq，又把 WL_HOST_WAKE 接到 GPIO0_A3 并通过 WIFI,host_wake_irq 交给 rfkill-wlan。带外中断的意义是能进 suspend 当唤醒源——DAT1 在控制器挂起后就不工作了，而 GPIO 中断可以配成 wakeup source。

5.4 板级实测的 SDIO 时序 #

启动日志里能看到 RK3399 侧实际跑出来的时钟：

5.5 SDIO 时序参数 #

规格书 10.2 ~ 10.5 节给了四组时序图：Default Mode、High Speed Mode、SDR Mode 时钟/输入/输出时序、DDR50 数据时序。这些图在原始抓取稿里全部丢失，只有标题。

我们能确定的是模式与频率的对应（5.2 节那张表），以及具体数值必须回规格书查。想调 RK3399 侧的 ciu-drive / ciu-sample 相位延迟时，需要的是 SDR104（208 MHz）下的 tISU（输入建立）和 tIH（输入保持）——这两项在 10.4 节的「Card Input timing (SDR Modes)」表里。数值本文不复述，避免抄错，标注为未验证。

工程上的经验值：DTS 里不显式配相位延迟时，Designware MMC 驱动会走自动 scan，日志里那句 Successfully tuned phase to 208 就是 scan 的结果。板子换了、线长了，这个数会变；如果调试时固定死一个相位，反而在温度变化下更容易出错。

6.1 三路电各自的角色 #

VDDIO 一般常开；VBAT 才是有条件关断的那一路，用来做真正的低功耗。rfkill-wlan 里 rfkill_set_wifi_bt_power() 就是操作这一路：

c
int rfkill_set_wifi_bt_power(int on)
{
    struct rfkill_wlan_data *mrfkill = g_rfkill;
    struct rksdmmc_gpio *vbat;

    if (!mrfkill) {
        LOG("%s: rfkill-wlan driver has not Successful initialized\n", __func__);
        return -1;
    }

    vbat = &mrfkill->pdata->vbat_n;
    if (on) {
        if (gpio_is_valid(vbat->io))
            gpio_direction_output(vbat->io, vbat->enable);
    } else {
        if (gpio_is_valid(vbat->io))
            gpio_direction_output(vbat->io, !(vbat->enable));
    }
    wifi_bt_vbat_state = on;
    return 0;
}

注意函数名里的 wifi_bt：这一路电是 WiFi 和 BT 共用的。所以关 WiFi 之前要先问蓝牙还在不在——rockchip_wifi_power(0) 里的这段就是干这个的：

c
if (toggle) {
    if (!bt_power) {
        LOG("%s: wifi will set vbat to low\n", __func__);
        rfkill_set_wifi_bt_power(0);
    } else {
        LOG("%s: wifi shouldn't control the vbat\n", __func__);
    }
}

toggle 来自设备树属性 wifi-bt-power-toggle。写了它，WiFi 和 BT 才协同管理 VBAT；不写就各管各的。

6.2 rfkill-wlan 的两条上电路径 #

rockchip_wifi_power() 有分支：走 PMU 还是走 GPIO。

走 PMU（设备树有 power_ctrl_by_pmu）：用 regulator 框架拉 LDO。

c
if (on == level) {
    regulator_set_voltage(ldo, 3000000, 3000000);
    LOG("%s: %s enabled\n", __func__, ldostr);
    ret = regulator_enable(ldo);
    if (ret)
        LOG("ldo enable failed\n");
    wifi_power_state = 1;
    LOG("wifi turn on power.\n");
} else {
    LOG("%s: %s disabled\n", __func__, ldostr);
    while (regulator_is_enabled(ldo) > 0) {
        ret = regulator_disable(ldo);
        if (ret)
            LOG("ldo disable failed\n");
    }
    wifi_power_state = 0;
    LOG("wifi shut off power.\n");
}

对应设备树属性是 power_ctrl_by_pmu、power_pmu_regulator、power_pmu_enable_level；代码里用 regulator_set_voltage(ldo, 3000000, 3000000) 把电压钉在 3.0 V。

走 GPIO（默认路径，NanoPC-T4 用的就是这条）：直接拉 WIFI,poweren_gpio 和 WIFI,reset_gpio。

c
poweron = &mrfkill->pdata->power_n;
reset = &mrfkill->pdata->reset_n;

if (on) {
    if (toggle) {
        rfkill_set_wifi_bt_power(1);
        msleep(100);
    }

    if (gpio_is_valid(poweron->io)) {
        gpio_direction_output(poweron->io, poweron->enable);
        msleep(100);
    }

    if (gpio_is_valid(reset->io)) {
        gpio_direction_output(reset->io, reset->enable);
        msleep(100);
    }

    wifi_power_state = 1;
    LOG("wifi turn on power [GPIO%d-%d]\n", poweron->io, poweron->enable);
}

这里有三个 msleep(100)：VBAT 上电后等 100 ms、poweren 拉高后等 100 ms、reset 拉高后等 100 ms。加起来 300 ms，比规格书要求的最小值宽得多，属于保守写法。

6.3 时钟树 #

SDIO0 的四个时钟（biu / ciu / ciu-drive / ciu-sample）来自 CRU。max-frequency = <150000000> 是驱动允许的上限，实际分频器能给出的是 148.5 MHz——slot req 150000000Hz, actual 148500000HZ div = 0 这行日志把差值写死了。

模组参考时钟有两条路：

  • XTAL_IN / XTAL_OUT 外挂 37.4 MHz 晶振（NanoPC-T4 的接法，也是 NVRAM 里 xtalfreq=37400 对应的值）；
  • LPO 32.768 kHz，用于低功耗时钟域。

37.4 MHz 这个数字不能改。它同时写在硬件（晶振）和 NVRAM（xtalfreq=37400）里，两边必须一致，否则射频频率会整体偏移，表现为「能连上但速率极低 / 频繁掉线」。

七、WL_REG_ON 与上电时序 #

7.1 规格书怎么定义这两根使能脚 #

规格书 10.1 节原文的两段定义，翻译过来：

  • WL_REG_ON：PMU 用它开启/关闭 WLAN 部分的内部稳压器。引脚为高时，内部稳压器使能，WLAN 部分退出复位；引脚为低时，WLAN 部分处于复位。
  • BT_REG_ON：同样用于开/关 BT 部分的内部稳压器，低电平复位。这个引脚对 WLAN 没有任何影响，也不控制任何 PMU 功能。它必须被驱动到确定的高或低电平，不能悬空。

「不能悬空」这句话是硬要求。悬空的 BT_REG_ON 会让 BT 内核随机进出复位，表现为蓝牙时而能扫到、时而扫不到。

规格书同时给了四种状态组合的时序图：

组合 对应图
WLAN=ON，Bluetooth=ON 10.1 节第一张
WLAN=OFF，Bluetooth=OFF 10.1 节第二张
WLAN=ON，Bluetooth=OFF 10.1 节第三张
WLAN=OFF，Bluetooth=ON 10.1 节第四张

图示的数值区间在原始抓取稿里丢失（原稿只有图片，图片未随文保存）。规格书原文明说「所示的时序值是最小要求值：更长的延迟也是可以接受的」。所以工程做法是：不抠最小值，直接按下面的流程给足余量。

7.3 三个必须守住的先后关系 #

  1. VBAT 先于 WL_REG_ON。WL_REG_ON 拉高时如果 VBAT 还没稳，内部稳压器上电会出毛刺，模组会卡在 1.2 V 内核不稳的状态。rfkill-wlan 里 rfkill_set_wifi_bt_power(1) 之后的 msleep(100) 就是为这个留的。
  2. WL_REG_ON 早于 CMD52。这是 pwrseq 的职责，mmc-pwrseq-simple 保证在 mmc_rescan 之前拉高。手写裸机代码时最容易漏这条——先发命令、后上电，读回来全是 0xff。
  3. BT_REG_ON 不能悬空。设备树里 BT,reset_gpio = <&gpio0 9 GPIO_ACTIVE_HIGH> 把它钉在 GPIO0_B1 上，probe 时驱动会主动拉低：
c
// bt turn off power
if (gpio_is_valid(pdata->poweron_gpio.io)) {
    gpio_direction_output(pdata->poweron_gpio.io, !pdata->poweron_gpio.enable);
}
if (gpio_is_valid(pdata->reset_gpio.io)) {
    gpio_direction_output(pdata->reset_gpio.io, !pdata->reset_gpio.enable);
}

日志证据是那行 [BT_RFKILL]: bt shut off power。

7.4 下电顺序 #

rfkill_wlan_shutdown() 走的是反方向：

c
static void rfkill_wlan_shutdown(struct platform_device *pdev)
{
    LOG("Enter %s\n", __func__);
    rockchip_wifi_power(0);
    rfkill_set_wifi_bt_power(0);
}

先关 WiFi（拉低 WL_REG_ON），再关 VBAT。反了的话 WL_REG_ON 还高时电源先掉，模组内部会有一段电流倒灌。

关于 sdio_mmc 这个键：它在安卓 dhd 驱动的 dhd_conf 体系里是一个合法参数（用来声明走 SDIO 总线、指定 SDIO 功能号），但在 brcmfmac 读的 brcmfmac4356-sdio.txt 里没有这个键，写了也不生效。brcmfmac 是 SDIO 版还是 PCIe 版，由它匹配到哪个总线驱动决定，不看 NVRAM。这条边界不清的话，从安卓 BSP 抄 NVRAM 过来的第一件事就是踩这个坑。

关于 macaddr：原始抓取稿里没有讨论过 macaddr、boardtype。上表的这些参数是我按 AP6356S 官方 NVRAM 补的，与原文无关。原文没写的键，本文一律不编。

MAC 地址的真源不是 NVRAM。NanoPC-T4 上 wlan0 的 MAC 走的是 Rockchip vendor storage，见 13.3 节。NVRAM 里的 macaddr 只是固件的兜底。

9.4 linux 5.2.8 的差异 #

9.5 为什么不走 rockchip_wlan 那条路 #

Rockchip 官方 linux 4.4 / 4.19 / 5.10 在 drivers/net/wireless/rockchip_wlan/ 下有一整套自适应框架，把瑞昱、博通各家芯片编成不同的 *.ko。linux 6.3 主线里没有这个目录。

要把它搬过来，就得连 bcmdhd 那一大坨一起搬，还要对着 6.3 的 cfg80211 / mac80211 API 大改。改完之后你手上就有了一份私有 WiFi 驱动，内核一升级就再来一遍。这条路在 BSP 里是合理的（厂商只维护一个内核版本），在跟着主线走的板子上不划算。

所以本文选 brcmfmac：代码在主线，升级内核基本不用管，代价是要自己补 rfkill 这一小层平台黏合剂。

同一个 dts 里还要把 &i2c0 下的 PMIC 组补全，因为 VDDIO 和 LPO 都由 rk808 出：

关键两行：

  • #clock-cells = <1> —— 没有它，<&rk808 1> 这种写法不成立。

LDO 侧和 WiFi 相关的是 vcc_sdio（LDO_REG4）：

LDO_REG8 vcc_3v0 3.0 V regulator-on-in-suspend

vcc_3v0 又是 rk808 的 vddio-supply。这条链路决定了 VDDIO 最终是 1.8 V 还是 3.0 V，和 3.3 节那条「供电必须一致」的规矩直接相关。

原文还提到要移除根节点下的 vdd_center（pwm-regulator）节点，改由 rk808 的 DCDC_REG1 提供——这一处和 WiFi 没有直接关系，属于同一次板级带全的必要改动。

11.2 rfkill-bt 的 init 顺序很怪 #

rfkill_rk_init() 里第一件事不是注册自己，而是先起 WiFi：

c
static int __init rfkill_rk_init(void)
{
    int err;

    LOG("Enter %s\n", __func__);
    err = rfkill_wlan_init();
    if (err)
        return err;
    return platform_driver_register(&rfkill_rk_driver);
}

反过来 rfkill_rk_exit() 先注销自己，再收 WiFi。这么写是因为 Bluetooth 侧要调 rfkill_get_wifi_power_state() 和 rfkill_set_wifi_bt_power()——这两个函数都在 rfkill-wlan.c 里，WiFi 侧没初始化就会出现空指针。日志顺理成章：rfkill_rk_init 先打，rfkill_wlan_init 后打。

11.3 rfkill-wlan 的 probe 做了什么 #

十二、SDIO 扫描与设备识别 #

12.1 扫描三阶段 #

MMC 核心认一张不可插拔 SDIO 卡，走三段：

阶段 总线状态 干什么
上电 400 kHz，CMD 线复位 发 CMD0/CMD5，进 SPI/SD 识别模式
识别 400 kHz CMD5 读 OCR，确认是 SDIO 而非 SD 卡；CMD52/CMD53 读 CIS
传输 148.5 MHz + 调相位 升速到 SDR104，读写数据

日志里能看到第一和第三段，第二段不打日志：

text
[    2.982147] mmc_host mmc1: Bus speed (slot 0) = 400000Hz (slot req 400000Hz, actual 400000HZ div = 0)
[    3.106521] mmc_host mmc1: Bus speed (slot 0) = 148500000Hz (slot req 150000000Hz, actual 148500000HZ div = 0)
[    3.416285] mmc1: new ultra high speed SDR104 SDIO card at address 0001

at address 0001 是卡的 RCA（Relative Card Address）。SDIO 卡一般固定为 0001，所以设备名是 mmc1:0001:1——mmc1 是主机，0001 是 RCA，:1 是 SDIO 功能号 1（backplane）。固件加载失败日志里的 mmc1:0001:1 就是这个命名：

text
brcmfmac mmc1:0001:1: Direct firmware load for brcm/brcmfmac4356-sdio.rockchip,rk3399-evb.bin failed with error -2

12.2 CIS 与三个功能号 #

SDIO 卡在 Function 0 的 CIS 区里自报家门：厂商 ID、设备 ID、各功能号的能力。brcmfmac 的 SDIO 层会读这些找 Function 2 的块大小：

功能号 本模块用途 块大小 驱动怎么用
0 CIS / CCCR / FBR 32 B MMC 核心读 CIS，识别厂商
1 Backplane 64 B 访问芯片内部寄存器（含 F1 签名）
2 WLAN 512 B brcmf_sdio_bus_sleep、数据收发

brcmfmac 只认 Function 2 做数据通路，Function 1 用来下固件、读芯片 ID。这就是为什么第 8 章那行 F1 signature read 这么关键——它是 Function 1 通道可用的唯一证明。

12.3 中断绑定 #

带外中断在 rfkill-wlan 里拿到号，交给 brcmfmac。rockchip_wifi_get_oob_irq() 做的事是：

c

if (gpio_is_valid(wifi_int_irq->io)) {
    return gpio_to_irq(wifi_int_irq->io);
} else {
    LOG("%s: wifi OOB pin isn't defined.\n", __func__);
}
return -1;

WIFI,host_wake_irq = <&gpio0 3 ...> → gpio 3 → gpio_to_irq(3) → 某个 GIC 中断号。日志里 WIFI,host_wake_irq = 3, flags = 0 就是这个 gpio 号。

rockchip_wifi_get_oob_irq_flag() 返回 wifi_int_b.enable，brcmfmac 拿它决定 request_irq 的触发类型（IRQF_TRIGGER_HIGH / LOW）。前面 10.5 节提到 enable = !flags 的语义可疑，这里就是它实际起作用的地方。

12.4 休眠与唤醒 #

休眠时 WL_HOST_WAKE 要能叫醒系统。设备树的 keep-power-in-suspend 保住了 VBAT，WL_HOST_WAKE 的 GPIO 中断则是唤醒源。rfkill-wlan 的 suspend/resume 是空壳：

{

AP6356 的 MAC 不走 NVRAM 的 macaddr。rfkill-wlan.c 从 Rockchip 的 vendor storage 分区读：

        LOG("%s: rk_vendor_read wifi mac address failed (%d)\n", __func__, ret);
#ifdef CONFIG_WIFI_GENERATE_RANDOM_MAC_ADDR
        random_ether_addr(addr);
        ...

这段有两个工程细节：

14.1 WiFi 与蓝牙的边界 #

同一颗模组，两条独立的数据通路，但共享 VBAT 和 LPO。这张表是排查「WiFi 好了蓝牙不好」时的分界线：

14.2 rfkill-bt 的 probe #

日志里蓝牙侧的四个关键行：

text
[    3.503936] [BT_RFKILL]: bluetooth_platdata_parse_dt: get property: uart_rts_gpios = 83.
[    3.513055] [BT_RFKILL]: bluetooth_platdata_parse_dt: get property: BT,reset_gpio = 9.
[    3.521946] [BT_RFKILL]: bluetooth_platdata_parse_dt: get property: BT,wake_gpio = 90.
[    3.530847] [BT_RFKILL]: bluetooth_platdata_parse_dt: get property: BT,wake_host_irq = 4.

83、9、90、4 这四个数对应设备树：

属性 设备树 gpio 号
uart_rts_gpios <&gpio2 19 ...> bank2 第 19 个 = 64 + 19 = 83
BT,reset_gpio <&gpio0 9 ...> 9
BT,wake_gpio <&gpio2 26 ...> 64 + 26 = 90

RK3399 每个 GPIO bank 有 32 个脚，bank N 的基址是 N × 32。所以 &gpio2 19 换算成全局号是 64 + 19 = 83，和设备树里的 GPIO2_C3 对得上（C 段第 3 个 → 2×8+3 = 19）。

14.3 蓝牙上电流程 #

rfkill_rk_set_power() 是 rfkill 的 set_block 回调，blocked = false 时走开电：

c
if (!blocked) {
    if (toggle) {
        rfkill_set_wifi_bt_power(1);
        msleep(100);
    }

    rfkill_rk_sleep_bt(BT_WAKEUP); // ensure bt is wakeup

    if (gpio_is_valid(wake_host->io)) {
        LOG("%s: set bt wake_host high!\n", __func__);
        gpio_direction_output(wake_host->io, 1);
        msleep(20);
    }

    if (gpio_is_valid(poweron->io)) {
        if (gpio_get_value(poweron->io) == !poweron->enable) {
            gpio_direction_output(poweron->io, !poweron->enable);
            msleep(20);
            gpio_direction_output(poweron->io, poweron->enable);
            msleep(20);
            if (gpio_is_valid(wake_host->io))
                gpio_direction_input(wake_host->io);
        }
    }

    if (gpio_is_valid(reset->io)) {
        if (gpio_get_value(reset->io) == !reset->enable) {
            gpio_direction_output(reset->io, !reset->enable);
            msleep(20);
            gpio_direction_output(reset->io, reset->enable);
        }
    }

    if (pinctrl && gpio_is_valid(rts->io)) {
        pinctrl_select_state(pinctrl, rts->gpio_state);
        LOG("ENABLE UART_RTS\n");
        gpio_direction_output(rts->io, rts->enable);
        msleep(100);
        LOG("DISABLE UART_RTS\n");
        gpio_direction_output(rts->io, !rts->enable);
        pinctrl_select_state(pinctrl, rts->default_state);
    }

    bt_power_state = 1;
    LOG("bt turn on power\n");
    rfkill_rk_setup_wake_irq(rfkill, 1);
}

顺序拆开看：

步骤 动作 等待 目的
1 拉 VBAT（若 toggle） 100 ms 与 WiFi 共享电源
2 BT_WAKE 拉高 — 叫醒蓝牙内核
3 BT_HOST_WAKE 输出高 20 ms 松开被前一次操作挂住的中断线
4 BT_REG_ON 先低后高 20 + 20 ms 产生一个复位脉冲
5 BT_HOST_WAKE 切回输入 — 释放，准备当唤醒源
6 UART_RTS 切 GPIO 拉高 100 ms 再拉低 100 ms 清掉 UART 上的残留数据
7 申请唤醒中断 — 让蓝牙能叫醒主机

第 6 步是 Rockchip 特有的偏方：切到 rts_gpio 状态、把 RTS 当普通 GPIO 拉高 100 ms 再拉低，相当于手工在 UART 上打一个握手信号，把模组里残留的数据冲掉。ENABLE UART_RTS / DISABLE UART_RTS 两行就是这两次操作。

关电走 blocked = true 分支：先拉低 BT_REG_ON，再看 toggle 决定要不要连 VBAT 一起关（要问 WiFi 还在不在）。

14.4 蓝牙的 proc 接口 #

rfkill-bt.c 建了两个 proc 节点：

text
/proc/bluetooth/sleep/lpm
/proc/bluetooth/sleep/btwrite

btwrite 是给 BlueZ 的 bluesleep 兼容层用的，写 0 让蓝牙睡，写非 0 唤醒：

c
/* HCI_DEV_WRITE */
if (b != '0')
    rfkill_rk_sleep_bt(BT_WAKEUP);
else
    rfkill_rk_sleep_bt(BT_SLEEP);

这条路径对现代 BlueZ 意义不大，但 Android 时代的 HAL 依赖它。

14.5 蓝牙固件 #

BCM4356A2.hcd 是博通格式的 HCD（HCI Command Data）固件，由 BlueZ 的 btattach 或 hciattach 下载到模组。流程是：

  1. UART 挂上（hci_uart 内核模块）；
  2. 拉高 BT_REG_ON 让模组进入可通信状态；
  3. 往 UART 写 HCI 命令，把 .hcd 里的补丁逐条发下去；
  4. 模组返回成功后，内核出 hci0。

/lib/firmware/brcm/ 里几个相关文件：

text
BCM4356A2.hcd
BCM4345C0.hcd
BCM4345C5.hcd

BCM4356A2 对应 BCM4356 A2 版本，正是 AP6356 的芯片。版本号选错，蓝牙能起来但连不上设备——这是 hcd 文件一个典型的软故障。

14.6 UART 侧的设备树 #

wireless-bluetooth 节点只描述了控制脚，UART 本身要另外配。原文在 5.2.8 版的内核上跑通了蓝牙，6.3 版需要额外确认 &uart0 的 status、波特率、流控（pinctrl-0 里要有 uart0_rts 和 uart0_cts）。这一块原文未给出完整的 &uart0 节点，本文不编，标注为未验证。

14.7 那个 GPIO 中断失败的坑 #

启动日志里 13.45 秒处有一段报错：

text
[   13.454115] gpio gpiochip0: (gpio0): gpiochip_lock_as_irq: tried to flag a GPIO set as output for IRQ
[   13.470190] gpio gpiochip0: (gpio0): unable to lock HW IRQ 4 for IRQ
[   13.481030] genirq: Failed to request resources for bt_default_wake_host_irq (irq 66) on irqchip rockchip_gpio_irq

发生了什么：rfkill_rk_set_power() 的第 3 步把 BT_HOST_WAKE（GPIO0_A4）设成了输出高，然后第 7 步调 rfkill_rk_setup_wake_irq() 去申请中断。GPIO 还处于输出方向，gpiochip_lock_as_irq() 就拒绝了。

rfkill_rk_setup_wake_irq() 的实现：

c
if (!flag) {
    rfkill->irq_req = 0;
    ret = rfkill_rk_setup_gpio(rfkill->pdev, &irq->gpio,
                   rfkill->pdata->name, "wake_host");
    if (ret)
        goto fail1;
}
if (gpio_is_valid(irq->gpio.io)) {
    ...
    irq->irq = gpio_to_irq(irq->gpio.io);
    ...
    ret = request_irq(irq->irq, rfkill_rk_wake_host_irq, ...);
    if (ret)
        goto fail2;
    rfkill->irq_req = 1;
    LOG("** disable irq\n");
    disable_irq(irq->irq);
}

它没有把 GPIO 方向改回输入就申请中断。正确写法是在 request_irq 前加一句 gpio_direction_input(irq->gpio.io)。

后果：蓝牙无法把主机从深睡叫醒。日常使用不受影响（wlan0 和 hci0 都正常），配了 wakeup-source 的休眠场景会失效。日志里连 ** disable irq 都没打出来，说明确实没申请成功。

这个坑在原文里没有单独解释，属于我按代码和日志对应出来的结论，标注为分析结论，非原文陈述。

15.3 iw 与 nmcli #

iw 是 nl80211 的直接接口，比 nmcli 更底层：

bash
root@rk3399:~# iw dev                          # 看 wlan0 在不在、是什么类型
root@rk3399:~# iw phy                          # 看频段、信道、支持的速率和加密
root@rk3399:~# iw reg get                      # 当前管制域
root@rk3399:~# iw dev wlan0 scan | grep -E 'SSID|freq|signal'
root@rk3399:~# iw dev wlan0 link               # 看当前关联的 AP 和速率

iw phy 的输出能直接验证 13.4 节的管制域和 8.2 节的 CLM blob 是否正常——如果 5 GHz 段只有寥寥几个信道，多半是 clm_blob 没加载。

原文的验证走的是 NetworkManager 这条路：

bash
root@rk3399:~# nmcli device wifi list
IN-USE  BSSID              SSID  MODE   CHAN  RATE        SIGNAL  BARS  SECURITY

        8C:A6:DF:6F:E4:41  2202  Infra  6     405 Mbit/s  59      ▂▄▆_  WPA1 WPA2

RATE 405 Mbit/s 是协商速率，CHAN 6 是 2.4 GHz。要注意 BARS 那列是乱码方块，属于终端字体问题，不是驱动问题。

15.4 wpa_supplicant #

NetworkManager 底层还是 wpa_supplicant。手工调试时绕过 NM 直接用它：

bash
root@rk3399:~# wpa_passphrase "你的SSID" "你的密码" > /etc/wpa_supplicant.conf
root@rk3399:~# wpa_supplicant -i wlan0 -c /etc/wpa_supplicant.conf -B
root@rk3399:~# wpa_cli -i wlan0 status
root@rk3399:~# udhcpc -i wlan0

启动日志里能看到 systemd 拉起了它：

text
[  OK  ] Started WPA supplicant.

wpa_supplicant 的连接失败码很有用：4-Way Handshake failed 是密码或加密方式不对，Association rejected 是 AP 侧拒绝（多半 MAC 过滤），CTRL-EVENT-SCAN-FAILED 是射频侧没起来。

16.2 三条分诊路线 #

A. 卡都认不到（停在 15.1 节门 1~2）：万用表量三处——VBAT 是否 3.3 V，WL_REG_ON（GPIO0_B2）是否为高，SDIO CLK 是否有 400 kHz 波形。三个都对了还认不到，看 pinctrl-0 有没有多挂 sdio0_cd/sdio0_wp 抢脚。

B. 卡认到但固件起不来（停在门 4~6）：先确认 /lib/firmware/brcm/ 下三个文件齐全（bin、clm_blob、txt），再确认 6.3 需要的板型后缀名，最后 lsmod 看是否六个模块都在。

C. wlan0 有了但连不上 / 速率低：iw phy 看能力，iw dev wlan0 scan 看能不能收到 AP，iw dev wlan0 link 看协商速率和信号。收不到 AP 但射频正常，查天线（WL/BT_ANT0 / WL_ANT1 两路都要接）；能连但只跑单流，查 NVRAM 的 rxchain/txchain/aa2g/aa5g。

16.3 一个具体的排查实例：6.3 升级后 WiFi 整个消失 #

这是从 5.2.8 升 6.3 最常见的场景。按时间线复盘：

  1. dmesg | grep brcmfmac 只看到 brcmf_fw_alloc_request: using brcm/brcmfmac4356-sdio for chip BCM4356/2；
  2. 紧接着是 Direct firmware load for brcm/brcmfmac4356-sdio.rockchip,rk3399-evb.bin failed with error -2；
  3. 然后 mod=wcc: failed 256；
  4. 最后 brcmf_attach failed。

三条错都在，但只有第 2 条是根因。第 3 条是 brcmfmac-wcc.ko 没拷进 /lib/modules/6.3.0/，第 4 条是前两条的连锁。

修法：拷三个新模块 + 复制带后缀的固件 + depmod -a + 重启。重启后会看到 brcmf_wcc_attach: executing 和固件版本行，wlan0 出现。

17.1 先把「没跑满」的原因分清 #

层次 上限 怎么看
宽带出口 16 Mbps（本环境实测） speedtest-cli
AP 与协商速率 405 Mbps（nmcli 显示） iw dev wlan0 link

17.2 SDIO 侧 #

项 现状 可调空间
总线模式 SDR104 已是最快，不能再高
时钟 148.5 MHz（请求 150 MHz） 受分频器限制，调不到 150
位宽 4 bit 已是上限
相位 tuned phase to 208 自动调优，不要手改
中断 带外 GPIO + 带内 cap-sdio-irq 两者都开着

sdio0 的 max-frequency 写 150 MHz 而实际拿 148.5 MHz，这 1% 的差值不值得动。真正有收益的是 bus width 必须是 4，以及 cap-sdio-irq 必须开——关掉它会退化到轮询，小包延迟直接翻倍。

17.3 射频侧 #

项 对应 NVRAM 说明
双流 rxchain=3、txchain=3 3 = 二进制 11，两条链都开。改成 1 就掉成单流
5G 子带功率 maxp5ga0/1 调高能扩覆盖，但要受 ccode 法规限制
2.4G 功率 maxp2ga0/1 同上
共存 btc_params33=5 蓝牙和 WiFi 同开时的 2.4G 抢先策略
温度补偿 tempthresh=255、tempoffset=255 255 表示关闭温度补偿（原厂默认）

温度补偿那两项设成 255 意味着关掉。RK3399 满载时模组会热，如果发现「跑久了掉速」，可以把 tempthresh 调低启用温度补偿——但这属于改原厂校准策略，改之前先备份原 NVRAM。这一条未验证，属于推测方向。
