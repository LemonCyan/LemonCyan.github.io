一、Linux 网络子系统的分层 #

Linux 内核对网络部分按四层设计：网络协议层、网络设备层、设备驱动功能层、网络媒介层。这四层跟 TCP/IP 模型的对应关系不是一一对齐的，得分开看。

1.1 四层划分 #

先把驱动视角的四层摆出来，这是后面所有内容的地基。

层次 职责 承载者 驱动要不要写
网络协议接口层 给网络层协议提供统一收发接口，屏蔽具体设备 dev_queue_xmit()、netif_rx() 不写，只调用
网络设备接口层 用统一结构描述设备属性和操作 struct net_device 填充、注册
设备驱动功能层 真正驱使硬件收发数据 xxx_open、xxx_stop、xxx_xmit、中断处理 全部自己写
网络设备与媒介层 物理实体，适配器加传输媒介 网卡芯片、PHY、双绞线/光纤/无线 不写

这个划分的好处很直接：网络协议接口层往上，协议层不需要知道下面是 DM9000 还是 RTL8211F，甚至不需要知道是不是一块真网卡；往下，驱动也不需要知道上面跑的是 ARP、IP 还是别的什么，它只认 sk_buff。net_device 处在中间，是协议层和硬件之间的桥——硬件千变万化，软件层次上只暴露一个结构体。所以写网卡驱动这件事可以浓缩成一句：实现设备驱动功能层的数据收发函数，填满一个 net_device，注册进内核。

1.2 从 TCP/IP 模型往下看 #

text
用户空间应用程序
   |  socket() / sendto() / recv()
   v
系统调用接口层              sys_socketcall、文件操作兼容
协议无关层（socket 层）      struct sock、struct proto、struct proto_ops
网络协议层                  TCP / UDP / IP / ARP / ICMP

设备驱动程序                你的 xxx_xmit / 中断处理
物理设备                    网卡芯片 + 媒介

socket 层是一层协议无关接口，不只服务 TCP/UDP，IP、裸以太网、SCTP 都从这儿走。内核里 socket 用 struct sock 表示，定义在 include/net/sock.h，装着某个 socket 需要的全部状态。每个协议自己维护一个 struct proto（建 socket、连接、关闭的函数指针），通过 proto_register() 注册到全局链表，TCP 的内嵌实现就在 net/ipv4/tcp.c 的 tcp_prot。

TCP 和 UDP 都属于 inet 簇，一起在 net/ipv4/af_inet.c 的 inet_init() 里初始化：调 proto_register() 注册每个内嵌协议，调 inet_register_protosw() 把 inetsw_array[] 里的每项挂到 inetsw 上，顺带初始化 ARP、ICMP、IP 各模块。socket(AF_INET, SOCK_STREAM, 0) 里 AF_INET 定地址簇、SOCK_STREAM 定类型，内核拿这两个值去 inetsw 查表找到对应的 proto_ops。注意 proto 和 proto_ops 不是一回事：前者定义传输层特有的方法，后者定义通用的 socket 方法（release、bind、connect、sendmsg 等）。

1.3 设备无关层做了什么 #

设备无关层（代码在 net/core/dev.c）是这一篇的主角，给驱动提供的通用函数就三组：注册/注销走 register_netdevice() / unregister_netdevice()；往设备发数据走 dev_queue_xmit()；往上层交数据走 netif_rx() 或 NAPI 的 napi_gro_receive()。协议层只管把 sk_buff 往 dev_queue_xmit() 里一塞，dev 层负责查 skb->dev 找到目标设备，再调它的发送方法。

二、从应用层到网卡驱动的完整路径 #

这一章把发送和接收两条路各走一遍。走着走着你会发现，sk_buff 是唯一贯穿始终的东西。

几个易混的旧名字：早期文档里出现 ip_build_xmit()、output_maybe_reroute()、ip_queue_xmit() 这类调用，那是 2.6 及更早的路径。2.6.24 之后 IP 输出路径重构成 ip_local_out -> ip_output -> ip_finish_output 这一串，到了 4.x/5.x 基本稳定。素材里的 out_maybe_reroute() 是抓取时截断的 output_maybe_reroute()，已经不存在了。

ip_output() 出来之后并不直接调驱动。中间还有一层：邻居子系统。以太网要根据目的 IP 查 ARP 缓存拿到 MAC，没命中就发 ARP 请求并把这个包缓冲起来。所以调 sendto() 之后发不出去，抓包却只看到 ARP 请求，问题不在你的驱动上。

ip_local_deliver() 和 ip_local_deliver_finish() 为什么分两步？因为中间要插 netfilter。NF_HOOK 在这里过一道 INPUT 链，iptables 加的规则就在这个点上被调用。没装 netfilter 时这个钩子直接返回 1，等于空过。

ip_rcv() 和 ipv4_rcv() 的关系值得一提：5.x 里 ip_rcv 实际是个薄壳，主体逻辑在 ip_rcv_core，而注册给 ptype 的是 ipv4_rcv（一个 INDIRECT_CALLABLE 包装）。看源码找不到 ip_rcv 的实现细节时，别以为看错了版本。

2.3 两条路径的交汇点 #

发送和接收在 sk_buff 上汇合。发送方向每往下一层，skb_push() 加一个头；接收方向每往上一层，skb_pull() 剥一个头。整包数据在内存里从头到尾只搬一次——从应用缓冲区到内核（或者 DMA 直接搬），之后全靠指针挪动。这就是 sk_buff 存在的理由：避免各层来回复制。

三、net_device：一个网络设备的抽象 #

struct net_device 定义在 include/linux/netdevice.h。它是网络设备接口层最重要的结构，接口信息在里面，硬件信息也在里面。内核源码注释自己都吐槽，开头一句就是「Actually, this whole structure is a big mistake」——它把 I/O 数据和纯高层数据混在了一起，还得知道 INET 模块里几乎所有数据结构。这话是写注释的人说的，不是骂人，是提醒你：这个结构不是按漂亮的分层切的。

3.3 高频字段与两条坑 #

写驱动时真正高频用到的其实就十来个字段：name、irq、base_addr、dev_addr、flags、mtu、type、hard_header_len、netdev_ops、stats、dev、watchdog_timeo。剩下的等真遇到需求再翻。有两条容易踩：

  • dev->dev_addr 在 2.6 是 unsigned char dev_addr[MAX_ADDR_LEN] 数组，5.x 变成了 unsigned char *dev_addr 指针，指向 dev_addrs 链表里的一块。所以老代码里 memcpy(dev->dev_addr, mac, 6) 还能用，但 &dev->dev_addr 的语义彻底变了。设置 MAC 统一走 eth_hw_addr_set()（5.17 起）或 memcpy(dev->dev_addr, ...) 加 dev_addr_check（未验证具体引入版本）。
  • rx_dropped、tx_dropped、rx_nohandler 归核心层管，注释写得很直白：do not use this in drivers。驱动丢包要记在 dev->stats.rx_dropped 或通过 ndo_get_stats64 自己算。

3.4 reg_state 状态机 #

reg_state 是个 8 位枚举，注册和注销的整个过程就靠它往前推：

值 含义
NETREG_UNINITIALIZED = 0 刚分配，未注册
NETREG_REGISTERED register_netdevice() 已完成
NETREG_UNREGISTERING / NETREG_UNREGISTERED 正在执行 unregister_netdevice() / 注销的延迟工作已完成
NETREG_RELEASED / NETREG_DUMMY 已调 free_netdev() / NAPI poll 用的哑设备

状态不能倒退。注册失败的设备停在 NETREG_UNINITIALIZED，注销完的设备不能再注册第二次——第二次 register_netdev() 会直接返回 -EEXIST 或类似错误，具体错误码随版本有差异（未验证）。

四、net_device_ops：驱动要实现的回调 #

struct net_device_ops 也在 include/linux/netdevice.h，注释第一句写着：除非特别注明，这些钩子都是可选的，可以填 NULL。但有一条例外，注释里明写 Required; cannot be NULL——ndo_start_xmit。

4.2 ndo_start_xmit 的返回值 #

这里有个跨版本的坑。2.6 时代函数叫 hard_start_xmit，返回 int，约定是「成功返回 0，硬件忙返回 1」。素材 3 里写「如果设备暂时无法处理，比如硬件忙，则返回 1」，说的就是这套。

2.6.31 引入 netdev_tx_t 枚举与 NETDEV_TX_OK / NETDEV_TX_BUSY，函数指针从 net_device 的直接成员挪进 net_device_ops 并改名 ndo_start_xmit。5.x 原型是 netdev_tx_t (*ndo_start_xmit)(struct sk_buff *skb, struct net_device *dev);。

返回值语义看内核注释原文更准：

  • NETDEV_TX_OK：正常。skb 的处置权已转给驱动，驱动必须自己释放或交还给硬件；
  • NETDEV_TX_BUSY：给老旧设备和怪角落用的，返回前必须先停队列，否则协议栈会做一堆无用功；
  • NETDEV_TX_LOCKED：早期给驱动处理队列锁用，已移除。看到老教程提它，忽略。

0 / 1 的写法在新内核里数值上等于 NETDEV_TX_OK / NETDEV_TX_BUSY，但别再这么写。

4.3 ndo_open / ndo_stop 的分工 #

ifconfig eth0 up 走的其实是两步：先 ioctl(SIOCSIFADDR) 设地址，再 ioctl(SIOCSIFFLAGS) 置 IFF_UP，这一步才触发 ndo_open。down 反过来：清 IFF_UP，触发 ndo_stop。

open 里该干什么：申请硬件资源、使能硬件；注册中断、申请 DMA；配置寄存器、启动收发；唤醒发送队列。中断注册放 init 还是放 open？绝大多数放 open，理由是网卡会被反复 up/down，放 open 就跟着申请释放，不留悬空的中断号。只有 probe 阶段就必须响应中断的场景才提前，用 devm_request_irq() 交给设备模型回收。open 返回非 0，硬件状态还是 down，所以任何一步失败都要回滚前面拿到的资源，否则第二次 up 会重复申请、报 -EBUSY。

4.4 中断处理不是 ndo_ 回调 #

接收数据的中断处理函数不在 net_device_ops 里。它通过 request_irq() / devm_request_irq() 单独注册，dev_id 传 net_device *，处理函数里用 struct net_device *ndev = dev_id; struct my_priv *priv = netdev_priv(ndev); 拿回来，最后返回 IRQ_HANDLED。

中断里要把三种情况分开：新报文到达、发送完成、出错。分不清就去读网卡的中断状态寄存器。发送完成中断里常见动作是重启发送队列，接收中断里是收数据交给协议栈。

5.2 注册：register_netdev #

register_netdev() 是 register_netdevice() 的包装。它多做的只有一件：dev->name 里有 %d 就找空闲编号填进去，其余交给后者。register_netdevice() 内部顺序：

text
1. 检查 reg_state，必须是 NETREG_UNINITIALIZED
2. dev_get_valid_name()        校验/分配名字
3. dev->ndo_init(dev)          如果定义了，失败则返回错误
4. netdev_register_kobject()   建 /sys/class/net/<name> 条目

8. reg_state = NETREG_REGISTERED
9. rtmsg_ifinfo()              发 netlink 通知

六、sk_buff：网络数据的载体 #

struct sk_buff 定义在 include/linux/skbuff.h，中文叫「套接字缓冲区」。内核网络栈各层处理数据包都在操作它。用它的根本原因是避免拷贝：协议栈从上到下四五层，每层都要在包前面加自己的头，每层都申请新内存再拷贝，一个 1500 字节的包在发送路径上要拷四五次。sk_buff 的做法是一次分配一块足够大的缓冲区，数据放中间，每层加头就是让 data 指针往前挪 14 字节直接写进去，完全不动已有数据。

6.1 结构和数据区 #

sk_buff 本身很小，只是一组指针和管理信息；真正放数据的是它指向的另一块缓冲区。

text
struct sk_buff（几百字节，走 skbuff_head_cache）
   | head/data/tail/end ──→  数据缓冲区（kmalloc，大小随包而定）

  head          data              tail          end
   |             |                 |             |
   v             v                 v             v
   +-------------+-----------------+-------------+
   |  headroom   |   包数据 payload |  tailroom   |
   +-------------+-----------------+-------------+
                 |<---- skb->len --->|

6.2 四指针 #

指针 类型 指向 会不会变
head unsigned char * 分配到的数据缓冲区首地址 不会变
end sk_buff_data_t 缓冲区的尾地址 不会变
data unsigned char * 当前包有效数据的起始地址 随 skb_push/skb_pull/skb_reserve 变
tail sk_buff_data_t 当前包有效数据的结束地址 随 skb_put/skb_trim 变

head/end 定的是权限边界，data/tail 定的是内容边界。包上下走，动的永远是后两个。

类型上的坑：5.x 里 tail/end 是 sk_buff_data_t，配置成 offset 模式时是 unsigned int 偏移量而不是指针；head/data 始终是真正的指针。2.6 时代四个都是 unsigned char *。所以 skb->tail - skb->data 在新内核里编译不过，算长度用 skb->len，算尾部空间用 skb_tailroom()。

6.5 它是个双向链表 #

next/prev 的存在有实际用途：一个 socket 的接收队列、一个 NAPI 实例一次 poll 收上来的一批包、一个 qdisc 里排着的待发包，都是 sk_buff 链。链表头是 struct sk_buff_head：

struct sk_buff_head {
	struct sk_buff	*next;
	struct sk_buff	*prev;
	__u32		qlen;      /* 链表里 skb 的个数 */
	spinlock_t	lock;      /* 保护链表的自旋锁 */
};

两点容易搞混：2.6 时代 sk_buff 里还有个 list 域直接指向 sk_buff_head，后来删了，素材 3 那句「在老的内核中会有一个 list 域……但是在我研究的 linux2.6.30.4 内核中已经不存在了」说的就是这个。5.x 里 list 又回来了，但它是和 next/prev、rbnode 共用内存的联合体成员，含义完全不同，看到 skb->list 先确认版本。链表操作宏是 skb_queue_head、skb_queue_tail、skb_dequeue、__skb_dequeue 这套，不是 list_add/list_del，因为 sk_buff_head 不是标准 list_head。

struct sk_buff *netdev_alloc_skb(struct net_device *dev, unsigned int length);
struct sk_buff *build_skb(void *data, unsigned int frag_size);

alloc_skb() 一次做两件事：从 skbuff_head_cache 拿一个结构体，再从 slab 分配 len 字节数据区。2.6 时代要求 len 按 L1_CACHE_BYTES 对齐（32 位 ARM 是 32 字节），5.x 内部用 SKB_DATA_ALIGN 处理了。刚分配完的指针状态是 head == data == tail、end = head + SKB_DATA_ALIGN(len)、len = 0，整块缓冲区都是空余空间，一个字节有效数据都没有。

dev_alloc_skb(len) 就是 alloc_skb(len + NET_SKB_PAD, GFP_ATOMIC) 再加 skb_reserve(NET_SKB_PAD)。用 GFP_ATOMIC 的理由很直接：它主要在接收中断里被调用，中断上下文不能睡眠。netdev_alloc_skb(dev, len) 是给网络设备用的版本，会按设备配置对齐数据，并对 dev->needed_headroom 有额外处理。build_skb(data, frag_size) 走另一条路：数据已经在某块内存里了（比如 DMA 收到的页），不用拷贝，直接包成 skb，高性能驱动的收包路径常用它。

7.3 变更：四个经典函数 #

skb_reserve() 的源码极简单，正因为它只挪两个指针才叫「免费」：skb->data += len; skb->tail += len;。以分配 100 字节为例：alloc_skb(100) 之后 head=data=tail=0, end=100, len=0；skb_reserve(skb, 2) 之后 data=tail=2，腾出 2 字节头空间；skb_put(skb, 14) 灌入 14 字节以太网头后 tail=16, len=14；skb_pull(skb, 14) 剥掉头后 data=tail=16, len=0。

八、数据发送路径：从 xmit 到硬件 #

8.1 dev_queue_xmit 入口 #

c
int dev_queue_xmit(struct sk_buff *skb);

在 net/core/dev.c。上层（IP 层、ARP、或 AF_PACKET 原始套接字）调它，参数是已经准备好完整链路层头的 sk_buff。

text
dev_queue_xmit(skb)
  -> __dev_queue_xmit(skb, sb_dev)
       +-- dev = skb->dev                    从 skb 上拿目标设备
       +-- if (!(dev->flags & IFF_UP))       设备没 up，丢弃，返回 -ENETDOWN
       +-- txq = netdev_pick_tx(dev, skb, sb_dev)
       |      -> 有 ndo_select_queue 就调它，否则按 hash / queue_mapping / XPS 选
       +-- q = rcu_dereference(txq->qdisc)
       |      -> 默认 noqueue（mq 设备）直接 dev_hard_start_xmit，否则走 qdisc 分支
       +-- __dev_xmit_skb(skb, q, dev, txq)
              -> 有锁竞争或 qdisc 忙：qdisc_enqueue 入队，等软中断
              -> 否则：q->enqueue 入队，然后 sch_direct_xmit 直接试着发

dev_queue_xmit() 必须在进程上下文调用且持 BH（bottom half）禁用，不是从任意上下文都能调。返回值是错误码：0 表示被 qdisc 接受了（不代表已经发出去），负数是错误。丢 skb 时返回 -ENETDOWN、-ENOMEM 之类。

8.2 sch_direct_xmit 与 dev_hard_start_xmit #

sch_direct_xmit() 从 qdisc 里取包，逐个调 dev_hard_start_xmit()。这里有两件事必须知道。

第一，GSO 分段。如果 skb->gso_size 非 0 且设备不支持 TSO，会先调 skb_gso_segment() 把大包切成小包再逐个发。所以你写 ndo_start_xmit 时收到的 skb，在 NETIF_F_TSO 没开的情况下，已经是常规尺寸了。

第二，xmit_one() 是每个包的最后一跳：

c
static int xmit_one(struct sk_buff *skb, struct net_device *dev,
		    struct netdev_queue *txq, bool more)
{
	unsigned int len;
	int rc;

	if (dev_nit_active(dev))
		dev_queue_xmit_nit(skb, dev);	/* AF_PACKET 抓包点 */

	len = skb->len;
	rc = netdev_start_xmit(skb, dev, txq, more);
	trace_net_dev_xmit(skb, rc, dev, len, txq);
	return rc;
}

netdev_start_xmit() 就是真正调 dev->netdev_ops->ndo_start_xmit(skb, dev) 的地方。dev_queue_xmit_nit() 那个抓包点单独记一下：tcpdump 抓到的是发出去之前的包，位置就在这里。所以 tcpdump 看到包不代表网卡发出去了，后面还有 ndo_start_xmit 和硬件这一关。

8.3 ndo_start_xmit 的实现要点 #

第一，进来先占住队列。 硬件描述符环就那么多槽位，没有空闲就 netif_stop_queue(dev); return NETDEV_TX_BUSY;。netif_stop_queue() 必须在 return NETDEV_TX_BUSY 之前调用，不停队列就返回 BUSY，协议栈会做一堆无用功还会反复重试。它置的是 txq->state 里的 __QUEUE_STATE_DRV_XOFF 位，上层看到这个位就不再送来。

第二，skb 交出去就忘掉它。 NETDEV_TX_OK 的含义是处置权已转给驱动，驱动必须在将来某个时刻释放它（发送完成中断里，或 DMA unmap 后立刻 dev_kfree_skb_irq）。忘掉就泄漏，多释放一次就崩。

第三，不要在这里睡眠。 ndo_start_xmit 会在任何上下文被调用，包括软中断里。kmalloc(GFP_KERNEL)、msleep()、mutex_lock() 都是错的。

第四，DMA 缓冲区要映射。 硬件是 DMA 的话，skb->data 是内核虚拟地址，得先 dma_map_single() 拿物理地址写进描述符，发送完成中断里再 dma_unmap_single()。

第五，返回之后别再碰 skb。 这是最常见的 use-after-free 来源：硬件已经发出去，驱动还在读 skb->len 更新统计。统计应该在交给硬件之前取好。

c
static netdev_tx_t my_start_xmit(struct sk_buff *skb, struct net_device *dev)
{
	struct my_priv *priv = netdev_priv(dev);
	dma_addr_t dma;

	if (unlikely(my_tx_ring_full(priv))) {
		netif_stop_queue(dev);
		return NETDEV_TX_BUSY;
	}

	dma = dma_map_single(&dev->dev, skb->data, skb->len, DMA_TO_DEVICE);
	if (unlikely(dma_mapping_error(&dev->dev, dma))) {
		dev->stats.tx_dropped++;
		dev_kfree_skb(skb);
		return NETDEV_TX_OK;	/* 包已丢弃，但队列没满 */
	}

	priv->tx_buf[priv->tx_head].skb = skb;
	priv->tx_buf[priv->tx_head].dma = dma;
	my_write_tx_desc(priv, dma, skb->len);

	dev->stats.tx_packets++;
	dev->stats.tx_bytes += skb->len;
	/* 从这里开始不能再访问 skb */
	return NETDEV_TX_OK;
}

8.4 发送完成与队列重启 #

c
static irqreturn_t my_interrupt(int irq, void *dev_id)
{
	struct net_device *dev = dev_id;
	struct my_priv *priv = netdev_priv(dev);

	while ((txd = my_get_completed_txd(priv)) != NULL) {
		dma_unmap_single(&dev->dev, txd->dma, txd->skb->len, DMA_TO_DEVICE);
		dev_kfree_skb_irq(txd->skb);
		txd->skb = NULL;
		priv->tx_tail++;
	}

	if (my_tx_ring_has_space(priv) && netif_queue_stopped(dev))
		netif_wake_queue(dev);	/* 唤醒上层 */

	return IRQ_HANDLED;
}

netif_wake_queue() 和 netif_start_queue() 的区别要记住：start_queue 是「设备刚 open，从头开始收包」，只清 XOFF 位；wake_queue 是「我之前说过我满了，现在有空间了」，除了清位还会主动触发一次 qdisc 调度，把积压的包发出去。发送完成中断里必须用 wake_queue，用错了会出现「队列里有包但没人来发」，表现为发送速率莫名降到 0，然后看门狗超时。

8.5 看门狗 #

ndo_tx_timeout 在 dev_watchdog() 判定发射器超时时被调用，任务是把硬件从卡死状态捞回来：dev_warn() 记一笔、netif_stop_queue()、my_reset_hardware() 复位 MAC 并重初始化描述符环、把环里没有完成的 skb 全部释放、dev->stats.tx_errors++、最后 netif_wake_queue()。dev->watchdog_timeo 没设的话，看门狗根本不会启动。以太网驱动常设成 msecs_to_jiffies(5000) 或 5 * HZ。

九、数据接收路径：从硬件到协议栈 #

9.1 中断里的第一次搬运 #

老式（非 NAPI）接收路径全在中断里完成：

c
static void my_rx(struct net_device *dev)
{
	struct sk_buff *skb;
	int pkt_len = my_rx_packet_len(priv);

	skb = dev_alloc_skb(pkt_len + 2);
	if (!skb) {
		dev->stats.rx_dropped++;
		return;
	}

	skb_reserve(skb, 2);
	my_read_fifo(priv, skb_put(skb, pkt_len), pkt_len);

	skb->dev = dev;
	skb->protocol = eth_type_trans(skb, dev);
	skb->ip_summed = CHECKSUM_UNNECESSARY;	/* 硬件已经校验过 */

	dev->stats.rx_packets++;
	dev->stats.rx_bytes += pkt_len;

	netif_rx(skb);		/* 交给协议栈 */
}

中断处理函数里按中断状态位分派：if (status & RX_READY) my_rx(dev); 和 if (status & TX_DONE) my_tx_complete(dev);，最后 my_write_isr(priv, status) 写回清中断。上面 my_rx 那十行基本是模板，dev_alloc_skb(pkt_len + 2) 那个 +2 就是给 skb_reserve(skb, 2) 腾的地方。

9.2 netif_rx 做了什么 #

5.x 里 int netif_rx(struct sk_buff *skb) 是个薄层，核心是 netif_rx_internal()：

text
netif_rx(skb) -> netif_rx_internal(skb)
  +-- trace_netif_rx_entry
  +-- if (static_key_false(&rps_needed)) 走 RPS 路径
  +-- enqueue_to_backlog(skb, cpu, &rflow)
  |      -> 挂到 per-CPU 的 sd->input_pkt_queue（或处理流缓存 rflow）
  +-- 成功入队：____napi_schedule(sd, &sd->backlog)
  |      -> 挂进当前 CPU 的 poll_list，__raise_softirq_irqoff(NET_RX_SOFTIRQ)
  +-- 队列满：kfree_skb(skb)，返回 NET_RX_DROP

两个关键点：netif_rx() 只负责「放进队列 + 触发软中断」，不做协议解析，解析在软中断里做；per-CPU 队列有上限，由 netdev_max_backlog 控制，满了直接丢包，/proc/net/softnet_stat 的第二列会涨。netif_rx_ni(skb) 在 2.6 时代存在，作用是「在进程上下文调 netif_rx 并顺带 local_bh_enable 把软中断跑起来」，它在 5.18 前后被移除，新代码里看到它就是抄了旧教程。具体删除的版本号未验证。

9.3 硬中断到软中断 #

中断处理返回前（irq_exit），如果有待处理软中断且不在中断上下文，就 invoke_softirq()：ksoftirqd 已唤醒就交给它，否则 __do_softirq() 直接跑，最多 2ms / 10 次。跑超预算就唤醒 ksoftirqd，剩下的活交给内核线程在进程上下文慢慢做。高负载时 /proc/softirqs 的 NET_RX 列数字会非常大，ksoftirqd/N 的 CPU 占用也上去。

9.4 net_rx_action 与协议分派 #

net_rx_action() 拿 budget = netdev_budget（默认 300）和 time_limit = 2 * HZ，遍历 sd->poll_list：取一个 NAPI 实例 → napi_poll(...)（poll 返回 0 表示收完了，从链表摘掉）→ budget -= work，budget <= 0 或超时就 break → 还有没跑完的重挂 NET_RX_SOFTIRQ。非 NAPI 路径下，per-CPU backlog 的 poll 是 process_backlog()，它把 input_pkt_queue 里的包一个个取出来调 __netif_receive_skb()。

__netif_receive_skb_core() 是协议分派总入口，主线顺序：

text
1. 处理 VLAN tag（skb_vlan_untag）
2. tap 层的 ptype_all 链：tcpdump / AF_PACKET 从这里拿到包的副本
3. 调 rx_handler（bridge、macvlan 挂在设备的这个钩子上）
4. 处理 bonding、team 的归档
5. 按 skb->protocol 在 ptype_specific 里找匹配的 packet_type
6. 交给 ->func()：IP 走 ip_rcv / ipv4_rcv，ARP 走 arp_rcv
7. 找不到就 kfree_skb，rx_nohandler++

第 5 步是关键：skb->protocol 设错了，包会在这里被静默丢掉，ifconfig 的 dropped 不涨，只有 /proc/net/snmp 或 ethtool 的 rx_nohandler 能看出来。

十、NAPI：中断与轮询的结合 #

10.1 为什么要 NAPI #

千兆线速下，最小以太网帧 64 字节，加上前导码和帧间隙是 84 字节，理论上一秒能来约 148 万个小包。每包一次中断，CPU 光进出中断就忙不过来，协议栈没机会处理数据。这叫中断活锁（receive livelock）：系统看起来 100% 忙，实际吞吐接近 0。NAPI 的想法很朴素：第一个包来的时候中断，然后把接收中断关掉，改成轮询，一批一批收，收完了再把中断打开，中断次数从「每包一次」降到「每批一次」。素材 5 里提过「用 NAPI 的驱动和非 NAPI 驱动是 6:1」，那是 2000 年代中期的统计，跟今天没关系，别引用。

10.3 四条核心 API #

函数 放在哪 干什么
netif_napi_add(dev, napi, poll, weight) probe 里，register_netdev() 之前 初始化 poll/weight/dev，把 napi_id 加进 napi_hash，挂到 dev->napi_list
napi_enable(n) ndo_open() 里 清 NAPI_STATE_SCHED、NAPI_STATE_DISABLE，允许被调度
napi_disable(n) ndo_stop() 里 置 NAPI_STATE_DISABLE，然后自旋等待 SCHED 位被清（当前 poll 已退出）
netif_napi_del(napi) remove 里 从 dev->napi_list 和 napi_hash 摘掉

napi_disable() 会自旋等，所以不能在中断上下文调，而且调用前必须先把硬中断关掉，否则中断里刚调度上的 poll 永远退不出去，就死等。标准顺序：open 走 napi_enable() → enable_irq() → netif_start_queue()；stop 走 netif_stop_queue() → disable_irq()（先掐中断源）→ napi_disable()（再等 poll 退出）。顺序反了就是死锁，这是驱动卸载挂住的第一名原因，14.4 节展开。napi_schedule(n) 的实质是 napi_schedule_prep(n) 成功则 __napi_schedule(n) → ____napi_schedule()，也就是 list_add_tail(&napi->poll_list, &sd->poll_list) 加 __raise_softirq_irqoff(NET_RX_SOFTIRQ)——挂链表 + 触发软中断，就这两句。

10.4 NAPI 驱动的硬中断该多短 #

c
static irqreturn_t my_interrupt(int irq, void *dev_id)
{
	struct net_device *dev = dev_id;
	struct my_priv *priv = netdev_priv(dev);

	if (likely(napi_schedule_prep(&priv->napi))) {
		my_disable_rx_interrupts(priv);	/* 关中断，改用轮询 */
		__napi_schedule(&priv->napi);
	}

	my_write_isr(priv, my_read_isr(priv));	/* 清中断状态 */
	return IRQ_HANDLED;
}

my_disable_rx_interrupts() 是 NAPI 的完整形态：中断里关掉接收中断，poll 收完了在 napi_complete_done() 里再打开。只挂链表不关中断，等于没省下中断开销，还会疯狂重入。

10.5 poll 函数 #

int (*poll)(struct napi_struct *napi, int budget)，budget 是本次最多处理多少个包，返回值是实际处理的数量。核心层靠这两个数字判断收完没有：work_done < budget 说明收完了，把这个 NAPI 从 poll_list 摘掉；work_done >= budget 说明还有积压，留着继续下一轮。

c
static int my_poll(struct napi_struct *napi, int budget)
{
	struct my_priv *priv = container_of(napi, struct my_priv, napi);
	struct net_device *dev = napi->dev;
	int work_done = 0;

	while (work_done < budget) {
		struct sk_buff *skb = my_rx_skb(priv);

		if (!skb)
			break;			/* 环空了 */

		skb->dev = dev;
		skb->protocol = eth_type_trans(skb, dev);
		napi_gro_receive(napi, skb);	/* 不是 netif_rx */
		work_done++;
	}

	if (work_done < budget) {
		if (napi_complete_done(napi, work_done))
			my_enable_rx_interrupts(priv);	/* 重新开中断 */
	}
	return work_done;
}

四个必须记住的点：

  1. 返回 work_done，不是 0 或 budget。 返回错的数字会让核心层误判「收完了」，之后新包只在中断里挂着却不被 poll，链路看起来通但完全收不到数据。
  2. poll 里不能调 netif_rx()。 要走 napi_gro_receive() 或 napi_gro_frags()。netif_rx 会再挂一次 per-CPU backlog，一次收包变两次调度。
  3. napi_complete_done() 返回真才开中断。 它还有别的实例在同一条中断线上时，返回假表示「先别开」。
  4. work_done >= budget 时不要调 napi_complete_done()，让它留在 poll_list 里继续被 net_rx_action 调。

10.6 napi_gro_receive 与 NAPI vs 中断 #

GRO（Generic Receive Offload）把多个同一条流、首尾相接的小包在协议栈之前合并成一个大包，上层只处理一次。100 个 1500 字节的 TCP 段合成一个 150KB 的包，IP 层和 TCP 层的每包开销摊薄 100 倍。napi_gro_receive(napi, skb) 先把它和 napi->gro_list 里的同类包尝试合并，合得上就丢掉新包（数据已并进去），合不上就挂进 gro_list 等下一次；gro_list 满了或超时（gro_flush_timeout / napi->timer）就一次性刷给上游。

函数 用途
napi_gro_receive(napi, skb) / napi_gro_frags(napi) NAPI 路径正常的收包入口，带 GRO / 零拷贝路径，数据在 page frag 里
napi_alloc_skb(napi, len) NAPI 路径上分配 skb，比 netdev_alloc_skb 更省
napi_complete(napi) 老的完成函数，5.x 基本被 napi_complete_done 取代
netif_receive_skb(skb) / netif_receive_skb_list(list) 非 NAPI 路径用，直接进协议栈，无 GRO 状态 / 一次提交一串包
维度 纯中断（netif_rx） NAPI
中断频率 每包一次，高负载下爆炸 每批一次，可控
延迟 最低，来了就处理 略高，要等软中断调度
per-CPU 队列 input_pkt_queue（有长度限制） 驱动自己的环形缓冲
丢包风险 队列满时丢 预算跑完留待下轮，不丢
适合场景 低速设备、包率极低 千兆及以上、包率高
代码复杂度 低 中高，poll 难写对
和 GRO 的关系 不支持 支持

今天写以太网驱动就用 NAPI。netif_rx 留着的主要是虚拟设备（loopback、ifb）从进程上下文注入包，以及没改完的老驱动。一次完整时序：硬件收包 → 硬中断 → my_interrupt() 里 napi_schedule_prep() 成功、关接收中断、__napi_schedule() 挂 poll_list 并触发 NET_RX_SOFTIRQ → irq_exit → invoke_softirq → net_rx_action → napi_poll(n, budget=n->weight) → my_poll() 循环到 budget 或环空 → work_done < budget 时 napi_complete_done() 返回真、重新开中断 → napi_gro_receive → netif_receive_skb_internal → __netif_receive_skb_core → ip_rcv → ip_local_deliver → udp_rcv。

十一、中断处理与 netif_rx #

11.1 三种中断与上下半部 #

中断类型 触发时机 处理动作

出错中断 溢出、总线错误、链路断开、校验错 统计、复位、必要时 netif_carrier_off

中断处理函数第一件事永远是读中断状态寄存器，再按位判断。DM9000 那类老芯片是单寄存器多位；现代网卡是多队列、每个中断向量对应一组队列，MSI-X 下每条向量只服务一个队列。

上半部（hardirq） 下半部（softirq/tasklet/threaded）

收包数据放哪一边取决于体量和延迟要求：老式全在上半部；NAPI 上半部只调 __napi_schedule()；threaded NAPI 的 poll 跑在独立内核线程里，可以睡眠，适合需要走 I2C/SPI 总线访问网卡芯片的平台（SDIO WiFi 就是典型）。

request_threaded_irq(irq, handler, thread_fn, flags, name, dev_id) 的用法：handler 返回 IRQ_WAKE_THREAD 表示「唤醒线程处理」；handler 传 NULL 加 IRQF_ONESHOT 表示「直接唤醒线程，上半部什么都不做」；共享中断线时必须传非 NULL 的 dev_id。

上半部的硬规矩：不用 kmalloc(GFP_KERNEL)，只能用 GFP_ATOMIC / GFP_NOWAIT；不用 mutex（会睡眠），只用 spin_lock_irqsave；不调任何内部会睡眠的函数（msleep、copy_to_user、wait_event、down）；current 不可靠（指向被中断的那个进程）；时间统计用 ktime_get() 或 local_clock()，jiffies 精度不够。

返回值 含义

11.5 中断共享 #

共享中断线的处理函数必须先判断「这个中断是不是我的」：

c
static irqreturn_t shared_handler(int irq, void *dev_id)
{
	struct net_device *dev = dev_id;
	u32 status = read_isr(dev);

	if (!(status & MY_DEVICE_BITS))
		return IRQ_NONE;	/* 不是我的 */
	...
	return IRQ_HANDLED;
}

返回 IRQ_NONE 时内核会统计。某条中断线在没人声明处理的次数过多，会打印 nobody cared 并把这条线屏蔽掉——这是排查「网卡突然没流量」的经典线索。原因多半是驱动忘了清中断状态位，或者 dev_id 传错导致判断永远为假。

十二、流量控制与队列规则 #

12.1 为什么需要 qdisc #

ndo_start_xmit 是「尽力而为」的：硬件有环、环有容量、容量会用完。用完之后直接丢包会让 TCP 一直重传，吞吐崩掉。内核的做法是在驱动之上垫一层队列，把包先攒起来，按策略决定什么时候发、发哪个、丢哪个。这就是 qdisc（队列规则）。

概念 数据结构 说明
发送队列 struct netdev_queue 一个硬件发送通道对应一个，有独立锁和状态
qdisc struct Qdisc 队列规则实例，dev->qdisc 是根 qdisc
队列长度上限 dev->tx_queue_len 每个队列最多排多少帧，以太网默认 1000
队列状态 txq->state __QUEUE_STATE_DRV_XOFF 等位
分类 skb->priority 决定进哪个子队列

dev->tx_queue_len 影响很大。调小对延迟敏感（交互式 SSH），调大对吞吐有好处但 bufferbloat 更严重。ifconfig 里的 txqueuelen:1000 就是它。

12.3 多队列与丢包策略 #

alloc_netdev_mqs(..., txqs, rxqs) 分配的就是多个 qdisc 对应的发送队列：

text
    上层协议栈 → ndo_select_queue / netdev_pick_tx
        +------+------+------+
        v      v      v      v
      txq0   txq1   txq2   txq3
        |      |      |      |
      qdisc  qdisc  qdisc  qdisc
        |      |      |      |
        v      v      v      v
      硬件发送队列（各自独立）

队列选择逻辑：驱动实现了 ndo_select_queue 就用它的返回值；没实现的话，内核按 skb_get_hash() 算流哈希，再用 XPS 映射把流绑到 CPU/队列；也可以由用户态通过 SO_PRIORITY 或 tc 分类指定。real_num_tx_queues 可以在运行期改小（比如为了限速），但 num_tx_queues 在 alloc_netdev_mqs() 时就定了，改不了。

队列满时的策略是吞吐和延迟之间最直接的取舍。尾部丢包（tail drop）最简单，但大流量会把队列填满、所有流一起丢；RED / CoDel 在队列真正满之前主动丢一点，让发送方早点减速；ECN 不丢包，在包头打 CE 标记让 TCP 自己减速，需要两端都开。驱动层能做的很少：netif_stop_queue() 是背压，让上层不再送包；返回 NETDEV_TX_BUSY 是退包，上层会重试。真正的丢包发生在 qdisc 里，dev->stats.tx_dropped 涨了说明 qdisc 丢的。

14.1 临界区的四类 #

spin_lock_bh 的语义是「关掉本 CPU 的软中断并拿锁」。之所以需要它，是因为 ndo_start_xmit 会在软中断（qdisc 调度）里被调用，而另一条路径会在进程上下文改同一份数据。

14.3 netif_tx_lock 与发送路径的锁 #

单队列设备的核心层用 txq->_xmit_lock 保护发送。dev_hard_start_xmit 会被进程上下文、软中断、watchdog 几处调用，核心层在 sch_direct_xmit 里拿 HARD_TX_LOCK(dev, txq)，它实际是 spin_lock(&txq->_xmit_lock) 的宏。5.x 对 ndo_start_xmit 的并发要求是：同一个设备不会有两个 CPU 同时在里面，除非驱动显式开了 NETIF_F_LLTX。老代码里自己玩 NETDEV_TX_LOCKED 的那套机制已经删了。多队列设备能并发，因为不同队列有不同的 _xmit_lock。

14.4 一处典型死锁：napi_disable 与 disable_irq #

错误顺序是 napi_disable() 在前、disable_irq() 在后。前者自旋等 SCHED 位被清（即等当前 poll 返回），后者等当前中断处理返回。中断若正好在跑并调了 __napi_schedule()，中断处理函数很快完成，但 napi_disable 一直自旋等 softirq 里的 poll 退出；这期间 disable_irq 还没执行、中断一直开着，中断又调度上 NAPI，napi_disable 继续等，于是活锁。正确顺序是 disable_irq() 先掐中断源，再 napi_disable() 等 poll 退出。

14.5 RCU 与 per-CPU 统计 #

设备注销和协议栈遍历之间靠 RCU 保证安全：dev_hold(dev) / dev_put(dev) 管引用计数；rcu_read_lock() 包住的遍历路径里设备不会被释放；unregister_netdevice() 会等一个 RCU grace period，确保没有读者还在用它。驱动里直接碰 RCU 的地方不多，主要是动态替换的指针要用 rcu_assign_pointer() 和 rcu_dereference()。

5.x 推荐用 dev->tstats 这套 per-CPU 统计，而不是往全局 dev->stats 上做加法：struct pcpu_sw_netstats *tstats = this_cpu_ptr(dev->tstats); 然后在 u64_stats_update_begin(&tstats->syncp) 和 u64_stats_update_end(&tstats->syncp) 之间累加 tx_packets / tx_bytes。dev->stats 在多核高包率下会成为争用点，它现在标着 legacy，新驱动用 pcpu_sw_netstats 加 ndo_get_stats64 汇总更对。读的时候要用 u64_stats_read() 那套带同步的宏，直接 tstats->tx_packets 会读到撕裂的值。

十五、常见故障与现象 #

按「现象 → 病因 → 怎么确认」组织。

15.1 驱动加载了，/sys/class/net 里没有设备 #

先看 dmesg 最后 20 行，再 ls /sys/class/net。

检查点 确认方法
register_netdev() 返回值没检查 / alloc_netdev() 返回 NULL 加打印或看 dmesg / dmesg | grep -i alloc
name 格式不对 %d 只支持这一种，写 %02d 会失败
ndo_init 里返回了错误 / 设备名和已有设备冲突 注册失败的路径只有驱动自己打印才知道 / dmesg 里有 rename 相关提示

15.2 接口能看到，ifconfig up 失败 #

顺序查：ndo_open 返回非 0 但错误被 ifconfig 吞了（看 dmesg）；request_irq() 失败（中断号错，或被占用且不能共享）；clk_prepare_enable() 失败；regulator_enable() 失败；MAC 没设（dev_addr 全 0），注册时的校验会报。ndo_open 里任何一步失败都必须回滚前面申请的资源，常见 bug 是 open 失败后第二次 up，request_irq 报 -EBUSY，因为第一次成功的那半截没释放。

15.3 链路 up 了，但完全没有收发 #

text
1. /proc/interrupts 里网卡中断计数涨不涨？
     不涨 → 中断没注册上，或中断线被别的设备占了
     涨   → 进第 2 步
2. /sys/class/net/eth0/statistics/ 的计数变化吗？
     tx_packets 涨、rx_packets 不涨 → 发出去没人接（MAC 地址、环配置、PHY）
     tx_packets 不涨                 → ndo_start_xmit 没被调用，看路由和 qdisc
     两个都不涨                      → 上层根本没发包，ip addr 配了没有？
3. ethtool eth0 的 Link detected 是什么？
     no   → PHY 没协商上，或者 netif_carrier_on 没调
     yes  → 进第 4 步
4. ethtool -S eth0 里有没有错误计数？
     tx_errors / rx_errors 持续涨 → 描述符环或 DMA 配置错了

「tx_packets 涨但对方收不到」最典型的原因是 MAC 地址全 0：源地址全 0，交换机不转发，对端也丢弃。

15.4 ping 不通但同网段其他机器能通 #

驱动层面多半没问题，但有两个点会造出来：IFF_NOARP 被设上，或者 ndo_set_rx_mode 把组播关了，收到的 ARP 请求被丢；dev->broadcast 是空的——ether_setup() 会填 broadcast，自己手写 setup 就漏了，导致 ARP 广播发不出去。确认方法：cat /sys/class/net/eth0/broadcast 应该是 ff:ff:ff:ff:ff:ff。IFF_MULTICAST 同理：flags 里没有它，收到组播帧时 eth_type_trans 会标成 PACKET_OTHERHOST 然后丢弃。

15.5 能 ping 通，但大包不通 #

MTU 和分片问题。驱动侧检查点：dev->mtu 是 1500 但硬件 FIFO 只支持 256 字节一帧，ndo_start_xmit 里没做分片；ndo_change_mtu 没校验 min_mtu / max_mtu；hard_header_len 没设成 ETH_HLEN，上层算出来的可用载荷比实际大 14 字节。ping -s 1472 通、-s 1473 不通是正常分片行为；但 ping -s 1000 就不通，那是 MTU 设错了。

15.6 一开大流量就卡死、系统 100% CPU #

中断活锁的典型症状。确认：

bash
cat /proc/softirqs          # NET_RX 列是不是一直在暴涨
cat /proc/interrupts        # 网卡中断次数是不是暴涨
top                         # ksoftirqd 是不是占满一个核

用纯中断路径的话改成 NAPI。已经是 NAPI 就查三件事：napi_schedule_prep 之后有没有关接收中断（没关等于还是每包一次中断）；poll 的返回值对不对；weight 是不是设得太小（比如 16）。netstat -s 里 receive buffer errors 和 /proc/net/softnet_stat 第 2 列持续涨，都指向同一个问题：收包速度跟不上。

15.7 看门狗超时：NETDEV WATCHDOG #

dmesg 里出现 NETDEV WATCHDOG: eth0 (my_driver): transmit queue 0 timed out，含义是 dev_watchdog() 发现队列里有包，但 ndo_start_xmit 连续 watchdog_timeo 时间没进展，或者调用了但硬件没动。病因：队列被 netif_stop_queue() 停了之后忘了 netif_wake_queue()；发送完成中断没来（中断状态位没清，或中断是 level 触发）；ndo_start_xmit 里 dma_map_single 失败却返回了成功，硬件拿到脏地址；硬件真的挂了。ndo_tx_timeout 里复位硬件后必须把环里所有未完成的 skb 释放掉，否则泄漏，下次 up 时环里还有脏数据。

15.8 卸载模块时卡住 #

现象 原因
rmmod 卡住，进程是 D 状态 napi_disable 自旋等不完，或 disable_irq 等不到中断处理返回
rmmod 报 Device or resource busy 有 socket 还在用这个接口，或者 dev_hold() 引用没释放
卸载后 oops，use-after-free 注销了 net_device，但定时器/工作队列还在跑
卸载后中断还报 nobody cared 中断没释放
卸载后 skbuff 缓存一直涨 队列里的 skb 没清空

正确顺序：

text
1. netif_stop_queue(dev)              停上层送包
2. disable_irq(priv->irq)             掐中断源
3. napi_disable(&priv->napi)          等 poll 退出
4. del_timer_sync / cancel_work_sync  等异步工作退出
5. unregister_netdev(dev)             注销
6. 释放 clk、regulator、ioremap、reset
7. free_netdev(dev)                   释放结构体

第 4 步必须在 unregister_netdev 之前，因为注销路径本身会触发回调，定时器还在跑就会碰到已释放的内存。

15.9 统计数字对不上 #

ifconfig 的字节数和实际流量差很多，常见原因：收包统计用 skb->len，但 eth_type_trans 已经剥了 14 字节帧头，少了 14 × 包数；tx_bytes 在 dev_kfree_skb() 之后才累加（UAF 的早期表现，不一定立刻崩）；用了 per-CPU 统计但 ndo_get_stats64 汇总时没走同步读；硬件统计和软件统计各记一份。

15.10 用虚拟网卡验证框架 #

不知道驱动哪里不对时，先写一个什么都不干的虚拟网卡，验证框架是通的，再往里加硬件逻辑：

c
static struct net_device *vnet_dev;

static netdev_tx_t vnet_send_packet(struct sk_buff *skb, struct net_device *dev)
{
	netif_stop_queue(dev);
	dev_kfree_skb(skb);
	dev->stats.tx_packets++;
	dev->stats.tx_bytes += skb->len;
	netif_wake_queue(dev);
	return NETDEV_TX_OK;
}

static const struct net_device_ops vnet_ops = {
	.ndo_start_xmit = vnet_send_packet,
};

static int vnet_init(void)
{
	vnet_dev = alloc_netdev(0, "vnet%d", NET_NAME_ENUM, ether_setup);
	if (!vnet_dev)
		return -ENOMEM;

	vnet_dev->netdev_ops = &vnet_ops;
	eth_hw_addr_random(vnet_dev);		/* MAC 随机，别全 0 */
	vnet_dev->flags |= IFF_NOARP;

	return register_netdev(vnet_dev);
}

static void vnet_exit(void)
{
	unregister_netdev(vnet_dev);
	free_netdev(vnet_dev);
}

module_init(vnet_init);
module_exit(vnet_exit);
MODULE_LICENSE("GPL");

验证顺序：insmod vnet_dev.ko → ls /sys/class/net 出现 vnet0 → ifconfig -a 里有 MAC 和 MTU 1500 → ifconfig vnet0 3.3.3.3 up 成功 → ping 3.3.3.4 走驱动发包。最后一步有个坑：ping 3.3.3.3（ping 自己）走回环，根本不会调 ndo_start_xmit，必须 ping 一个同网段的别的地址。

原始素材里那个 vnet 还把发出去的包改造成 ICMP 应答再从 netif_rx 送回协议栈，用来在没有硬件的情况下验证完整收发链路——做法是交换源/目的 MAC 和 IP、把 ICMP 类型从 0x08 改成 0x00、用 ip_fast_csum() 重算校验和、dev_alloc_skb + skb_reserve(2) + skb_put 造新包、eth_type_trans() 取协议、最后 netif_rx()。结果是 ping 3.3.3.4 真的能通。这条路的每个调用点第七章都讲过，可以照着复现。
