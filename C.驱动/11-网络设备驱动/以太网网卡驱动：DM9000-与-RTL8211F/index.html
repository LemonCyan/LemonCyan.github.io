本篇讲两颗具体的以太网芯片：DM9000（DaviCOM 的老式 10/100M 独立网卡控制器，把 MAC、PHY、SRAM 全塞进一颗芯片）和 RTL8211F（Realtek 的千兆 PHY，只做物理层，挂在 RK3588 的 GMAC 后面）。两条线各走一遍：从芯片特性、寄存器，到 probe、收发、设备树、链路检测、调试。

不讲什么：net_device、sk_buff、NAPI、napi_struct、netif_rx 的内核实现、register_netdev 往下那套设备模型，都在同目录的《网络设备驱动框架：从 net_device 到 NAPI》里；本篇只在你需要衔接时点一句。无线侧（cfg80211、mac80211、SDIO/USB 网卡）看《WiFi 驱动：从协议到 SDIO 与 USB 实现》与《RK3399 WiFi AP6356 驱动》。

DTS 的语法本身、compatible 的匹配机制看 C.驱动/04-platform与总线模型 的《platform 总线：设备、驱动与匹配》；本篇只讲以太网节点里那些以太网特有的属性。

内核版本基线：DM9000 部分是 linux 5.2.8（Mini2440/S3C2440，arch/arm/mach-s3c24xx/），drivers/net/ethernet/davicom/dm9000.c。这颗芯片的驱动比 netdev_tx_t 这个返回类型还老，2.6 时代的 ndo_start_xmit 返回 int，5.x 早已是 netdev_tx_t，逐处标。RTL8211F 部分是 Rockchip 5.10 内核（RK3588，drivers/net/phy/ 与 drivers/net/ethernet/stmicro/stmmac/，drivers/net/ethernet/stmicro/stmmac/dwmac-rk.c）。RK3588 的 PHY 框架在 5.10 已经是 phy_device 的老框架，不是 6.9 之后那套 phy_attach_direct 重构过的形态。

素材没写死的地方一律标「未验证」。

一、两个芯片的定位差异：MAC 与 PHY #

先把两颗芯片摆在坐标上，不然后面的寄存器表看起来会很分裂。

以太网接口从硬件的角度拆，就是 MAC 控制器加 PHY 两大部分，中间用 MII 这一族接口连起来。DMA 控制器在中间插一手，负责替 CPU 搬报文，它不是必须的，有它 CPU 才不用一字节一字节地喂 FIFO。

DM9000（DM9000E/A/B） RTL8211F
是什么 完整的以太网控制器：MAC + 10/100M PHY + 16KB SRAM + EEPROM 接口，一颗搞定 纯 PHY：只做物理层，MAC 在外面的 SoC 里
速率 10/100 Mbps，半双工/全双工 10/100/1000 Mbps
与主控的接口 类 SRAM 的并行总线（8/16/32 位）+ CMD 地址线 + 中断脚 RGMII（也支持 SGMII，型号而定）
寄存器访问 地址寄存器 + 数据寄存器两个端口，两拍完成一次访问 MDIO/MDC 串行总线，IEEE 802.3 Clause 22
典型用法 没有 MAC 的老 SoC（S3C2440）外挂 有 GMAC 的新 SoC（RK3588）外挂
驱动位置 drivers/net/ethernet/davicom/dm9000.c drivers/net/phy/realtek.c，MAC 侧在 dwmac-rk.c
驱动形态 platform_driver + 自己填 net_device_ops phy_driver，由 PHY 框架调度，不碰 net_device

一句话记住差别：DM9000 的驱动是自己管收发和 net_device 的完整网卡驱动；RTL8211F 的驱动只回答「链路起没起来、跑多快、双工是什么」，报文怎么搬它一律不管。 RK3588 上真正搬报文的是 GMAC 控制器（DesignWare stmmac），PHY 只是它链路上的一个从设备。

RK3588 芯片有 2 个 GMAC 控制器，每个提供 RMII 或 RGMII 接外置 PHY，平台默认配的就是 RTL8211F。S3C2440 什么 MAC 都没有，只能外挂 DM9000 这种「全包」芯片。

所以两种驱动在 Linux 里的分层位置完全不同：

text
DM9000:        应用 → 协议栈 → net_device(ndo_start_xmit) → dm9000.c → 并行总线 → 芯片
RK3588+RTL8211F: 应用 → 协议栈 → net_device(stmmac) → dwmac-rk.c / stmmac → RGMII → RTL8211F → 双绞线
                                                        ↑
                                               phy_device (realtek.c 只管这一层)

二、以太网帧与 MAC 层 #

MAC 有两个意思，别混：一个是硬件控制器，一个是那套协议。

MAC 协议位于 OSI 七层里数据链路层的下半部分，负责控制对物理介质的访问。发送时先判断能不能发（半双工下要听信道空不空），能发就给数据加控制信息，按规定的格式送到物理层；接收时先判断有没有传输错误，没错再去掉控制信息交给 LLC 子层。这套规矩由 IEEE 802.3 定义。

数据链路层其实分两层：MAC（介质访问控制）子层和 LLC（逻辑链路控制）子层。一块以太网卡 MAC 芯片要把这两层都实现，还要提供符合规范的总线界面和主机交换数据。

一帧以太网报文长这样（我们看的是最常见的 802.3/Ethernet II 帧）：

字段 长度 说明
前导码 + SFD 7 + 1 字节 前导码 7 个 0xAA，SFD 是 0xAB，不参与 CRC，不往上层递
目的 MAC 6 字节 全 F 是广播，第一个字节的 bit0 为 1 是组播
源 MAC 6 字节 由此得到 MAC 地址表
类型/长度 2 字节 大于 0x0600 是 EtherType，小于 0x0600 是 802.3 的长度
数据 46~1500 字节 不够 46 要补齐，否则是 runt 帧
FCS 4 字节 CRC32，由 PHY 或 MAC 校验

DM9000 驱动里那几条边界判断就是对这张表的逆运算：RxLen < 0x40（64）判 runt，RxLen > DM9000_PKT_MAX 拒收，状态位里的 RSR_CE（CRC 错）、RSR_RF（长度错）逐位翻译成 stats 计数。

驱动交给协议栈之前调用 eth_type_trans(skb, dev)，它干三件事：剥掉以太网头、按类型字段填 skb->protocol、把 skb->pkt_type 定成 PACKET_HOST/PACKET_OTHERHOST/PACKET_BROADCAST/PACKET_MULTICAST 之一。这一步做错的典型症状是「抓包有、协议栈不认」，tcpdump 能看到帧但 ping 不回。

物理层那一半由 PHY 负责，它的活儿是四件：

  1. 信号转换：MAC 输出数字信号，驱动物理介质得是另一套电平。双绞线要差分曼彻斯特编码的 ±2.5V 电平，光纤要光脉冲调制。
  2. 介质适配：不同介质电气特性不同，只有 MAC 就得为每种介质单独设计硬件。
  3. 信号完整性：长距离传输衰减加噪声，PHY 用均衡器（EQ）和时钟恢复电路补偿，千兆 PHY 用自适应均衡消 ISI。
  4. 协议标准化：10BASE-T、100BASE-TX、1000BASE-T 的电气特性都写死在 802.3 里，PHY 保证符合。

PHY 是 IEEE 802.3 定义的标准模块，STA（管理实体，一般是 MAC 或 CPU）通过 SMI 总线读写 PHY 内部寄存器来管它。PHY 内部由 MII/GMII 子层、PCS（物理编码子层）、PMA（物理介质附加）、PMD（物理介质相关）、MDI 子层堆起来，对应 802.3 里 10BaseT 的第 14 条和 100BaseTX 的第 24、25 条。

PHY 寄存器的权威出处是 802.3 标准 22.2.4 节 Management functions，但那一节列不全，个别寄存器要去其它章节找。

三、MII、RMII 与 RGMII 接口 #

MII（Media Independent Interface）是 MAC 和 PHY 之间的标准接口，「媒体无关」的意思是：只要换 PHY 不动 MAC 硬件，任何类型的 PHY 都能干活。802.3 最多支持 32 个 PHY 挂一条 MII。

MII 接口由四部分组成：MAC 到 PHY 的发送数据接口、PHY 到 MAC 的接收数据接口、PHY 到 MAC 的状态指示信号、MAC 与 PHY 之间传控制状态的 MDIO 接口。

标准 MII 一共 18 个主要信号引脚，按用途分三组。数据通道（发送方向 4 位宽、接收方向 4 位宽）：

信号 方向 说明
TX_CLK PHY → MAC 时钟频率随速率变：10M 是 2.5MHz，100M 是 25MHz，上升沿有效
TXD[3:0] MAC → PHY 每拍 4 位，组一个字节要两拍；TX_EN=1 时有效，高位 TXD[3] 在前
TX_EN MAC → PHY 高表示数据有效；低时 PHY 发空闲码 IDLE
TX_ER MAC → PHY 可选。指示本拍数据有错，须在 TX_EN=1 期间拉高
RX_CLK PHY → MAC 与 TX_CLK 同步，由 PHY 给
RXD[3:0] PHY → MAC RX_DV=1 时是有效帧内容；RX_DV=0 时是前导码或空闲码
RX_DV PHY → MAC 标识 RXD 上是不是有效帧
RX_ER PHY → MAC PHY 检出接收错误（帧校验错或冲突）

控制信号两个：CRS（载波侦听，高表示介质上有数据传输，信道忙）和 COL（冲突检测，只有半双工有效，高表示检测到冲突，MAC 要重发）。

速率和时钟的对应关系可以直接算：10Mbps 模式 TX_CLK/RX_CLK 是 2.5MHz，4 位 × 2.5MHz = 10Mbps，两拍出一个字节；100Mbps 模式时钟 25MHz，4 位 × 25MHz = 100Mbps，同样是两拍一个字节。

为了跑更高速度，MII 后面衍生出一串变体：

接口 位宽 时钟 最高速率 引脚数（数据+控制） 用在哪
MII 4 位 25MHz（100M） 100 Mbps 约 16~18 S3C2440 外挂 DM9000 那个年代
RMII 2 位 50MHz 100 Mbps 约 7 个核心信号 RK3588 GMAC 的低速档、引脚吃紧的方案
GMII 8 位 125MHz 1000 Mbps 约 24 千兆早期方案，引脚多
RGMII 4 位 DDR 125MHz 1000 Mbps 12 RK3588 + RTL8211F 的主力
SGMII 串行 625MHz 1000 Mbps 少 RTL8211FS 这类支持 SGMII 的型号

还有 10GMII、25GMII、200GMII、500GMII，嵌入式用不到，知道有这回事就行。

RS（Reconciliation sublayer）也顺带说一句：它的职能是提供 MII 与 MAC/PLS 之间的信号映射机制，是个纯逻辑的中间层，没有引脚。

RGMII 是 RK3588 这条线上真正在用的接口，它的关键点是把 4 位数据线当时钟的双沿用：TX_CLK 125MHz，上升沿发 TXD[3:0] = D[3:0]（低 4 位），下降沿发 TXD[3:0] = D[7:4]（高 4 位）；接收端同理，RX_CLK 上升沿采低 4 位，下降沿采高 4 位。一个时钟周期出 8 位，125MHz × 8 = 1Gbps。RK3588 原理图里 RGMII 的收发两个方向加起来一共 12 个引脚，多出来的 TX_EN、REFCLKO_25M、RXDV_CRS 是 RMII 模式复用的。

RGMII 还有一根 MCLKINOUT，是 SoC 与 PHY 交互参考时钟的核心引脚，双向设计：外部 PHY 没内置振荡器时 RK3588 从这里往外输出参考时钟，PHY 自带振荡器时 RK3588 从这里收 PHY 给的时钟。这根线的方向配反了，网口直接不起。

四、DM9000 的硬件特性 #

DM9000 是 DaviCOM 的 10/100M 自适应以太网控制器，把 MAC、PHY、16KB SRAM（收发共用，TX 与 RX 各占一段）和 EEPROM 接口做在一颗芯片里。它有三个常见型号，驱动里用 enum dm9000_type 区分：

c
/* The driver supports the original DM9000E, and now the two newer
 * devices, DM9000A and DM9000B.
 */
enum dm9000_type {
        TYPE_DM9000E,   /* original DM9000 */
        TYPE_DM9000A,
        TYPE_DM9000B
};

型号差别直接影响功能：DM9000A 和 DM9000B 支持硬件校验和卸载（NETIF_F_RXCSUM、NETIF_F_IP_CSUM），DM9000E 不支持；DM9000B 还需要额外的 PHY 复位和 DSP 初始化参数；只有非 E 型号才会用 IMR_LNKCHNG 链路变化中断，E 型只能靠定时轮询。

Mini2440 这块板子上，DM9000 的接法是这样的：

  • DM9000 只有一根地址线 CMD，接在 S3C2440 的 ADDR2 上；
  • 数据线 SD0~SD15 接 S3C2440 的 LDATA0~LDATA15；
  • 片选线 nLAN_CS（AEN）低电平有效，接 S3C2440 的 nGCS4；
  • 中断脚 IRQ_LAN（INT）接 S3C2440 的 EINT7（GPF7），这路中断用于接收数据时触发，高电平有效。

nGCS4 这个片选对应的物理地址段是 0x20000000~0x28000000，CPU 一访问这段地址，DM9000 就被选中。关键在 CMD 那根线：DM9000 读写地址和读写数据走的是同一组 16 根 I/O 引脚，靠 CMD 区分这一拍到底在传寄存器地址还是寄存器数据。而 CMD 接在 ADDR2 上，意味着 CPU 地址的最低位（bit2）就是 CMD：

  • 访问 0x20000000 时，CMD=0，这一拍传的是 DM9000 的寄存器地址；
  • 访问 0x20000004 时，CMD=1，这一拍传的是 DM9000 的寄存器数据。

于是「往 0x20000004 写 0x12」这件事，对 DM9000 来说只是「数据端口收到 0x12」，它不知道这 0x12 要进哪个寄存器——必须先往 0x20000000 写一次寄存器号。这就是 driver 里 ior()/iow() 必须两拍完成的原因，也是 dm9000_reset() 为什么长成那样：

c
static void dm9000_reset(board_info_t * db)
{
    dev_dbg(db->dev, "resetting device\n");

    /* RESET device */
    writeb(DM9000_NCR, db->io_addr);  /* 地址寄存器写入 DM9000_NCR */
    udelay(200);
    writeb(NCR_RST, db->io_data);     /* 数据寄存器写入 NCR_RST: 1 << 0 */
    udelay(200);
}

Mini2440 上的 DM9000 没有外挂 EEPROM，MAC 地址由 bootloader 在启动内核前写好，platform data 里用 DM9000_PLATF_NO_EEPROM 标明这件事。驱动里那段「从 EEPROM 读 MAC」的循环跑起来是读不到东西的，最终走随机 MAC 分支。

五、DM9000 的寄存器与操作 #

DM9000 的寄存器空间是 8 位地址、8 位数据。因为地址和数据共用数据线，所有访问都是两拍。驱动把这件事包成两个函数，ior/iow 读/写一个字节的寄存器，ior 内部先写地址再读数据：

c
/* 逻辑形态，非逐字源码 */
static u8 ior(struct board_info *db, int reg)
{
    writeb(reg, db->io_addr);   /* 先出地址 */
    return readb(db->io_data);  /* 再取数据 */
}

static void iow(struct board_info *db, int reg, u8 value)
{
    writeb(reg, db->io_addr);
    writeb(value, db->io_data);
}

这两个函数有个前提：io_addr 里存的寄存器号必须保证在这次访问期间不被别人改掉。DM9000 的地址寄存器是芯片级唯一的一份，进程上下文正在读 PHY，中断里插进来读 ISR，中断返回后进程那一拍就打到错误的寄存器上去了。驱动用两把锁解决：中断里用 spin_lock_irqsave(&db->lock)，允许睡眠的路径用 mutex addr_lock，addr_lock 同时串行化 EEPROM 和 PHY 这两组共享寄存器的访问。中断处理里还额外保存了进入前的地址寄存器值 reg_save = readb(db->io_addr)，退出时写回。

常用寄存器表（DM9000 datasheet 的编号，也是驱动里 #define 的值）：

寄存器 地址 名字 关键位与用法
NCR 0x00 Network Control bit0 NCR_RST 软复位；bit6 NCR_EXT_PHY 用外部 PHY；bit7 NCR_WAKEEN 唤醒使能
NSR 0x01 Network Status NSR_TX1END(bit2) 第 1 包发完；NSR_TX2END(bit3) 第 2 包发完；NSR_WAKEST(bit5) 唤醒事件
TCR 0x02 TX Control bit0 TCR_TXREQ 启动一次发送，发完自动清零
TSR1 0x03 TX Status 1 发送完成状态，dm9000_tx_done() 读的是 NSR 不是它
TSR2 0x04 TX Status 2 第二个包的发送状态
RCR 0x05 RX Control bit0 RCR_RXEN 收包使能；dm9000_rx() 出错时写 0 直接关掉接收
RSR 0x06 RX Status RSR_FOE FIFO 溢出、RSR_CE CRC 错、RSR_AE 对齐错、RSR_PLE 物理层错、RSR_RWTO 收超时、RSR_LCS 冲突、RSR_RF 长度错
ISR 0x0E Interrupt Status ISR_PRS(bit0) 收包完成；ISR_PTS(bit1) 发包完成；ISR_LNKCHNG；ISR_CLR_STATUS 全 1 清标志；bit7:6 存 I/O 位宽模式
IMR 0x0F Interrupt Mask IMR_PAR 使能；IMR_PTM 发中断；IMR_PRM 收中断；IMR_LNKCHNG 链路变化
RCSR 0x05(页内) RX Checksum RCSR_CSUM 开硬件校验和
TCCR 0x06(页内) TX Checksum TCCR_IP/TCCR_UDP/TCCR_TCP
TXPLL/TXPLH 0x0D/0x0C TX Packet Length 待发报文长度低/高字节，写这两拍不是启动发送
BPTR 0x22 Back Pressure 驱动写 0x3f，注释是「Less 3Kb, 200us」
FCR 0x23 Flow Control 驱动写 0xff
SMCR 0x2F Special Mode 驱动写 0，正常模式
PAR 0x10~0x15 Physical Address 6 字节 MAC，dm9000_probe() 里从这读
VIDL/VIDH 0x28/0x29 Vendor ID 低/高字节
PIDL/PIDH 0x2A/0x2B Product ID 低/高字节
CHIPR 0x2C Chip Revision 区分 DM9000A/B/E
GPCR 0x1E GPIO Control GPCR_GEP_CNTL 让 GPIO0 作输出
GPR 0x1F GPIO Register 写 0 给内部 PHY 供电
MWCMD 0xF8 Memory Write Command 写地址后 outblk 连续写 TX SRAM，地址自动递增
MRCMD 0xF2 Memory Read Command 读写 RX SRAM 数据 + 状态头，地址自动递增
MRCMDX 0xF0 Memory Read Command (no addr inc) 空读一次，地址不动，用来探「有没有新包」
TRPA 0x09 TX SRAM Read Pointer 两个包并发发送时用

两张表里各出现一次 0x05 和 0x06，那是因为 DM9000 的寄存器分页，RCSR/TCCR 在页内而 RCR/RSR 在基础页，中间靠 SMCR 切页。驱动里这两组不冲突，因为访问路径分开。

识别芯片 ID 只用三个寄存器拼 32 位：

c
/* try multiple times, DM9000 sometimes gets the read wrong */
for (i = 0; i < 8; i++) {
        id_val  = ior(db, DM9000_VIDL);                /* 厂家 ID 低 8 位 */
        id_val |= (u32)ior(db, DM9000_VIDH) << 8;      /* 厂家 ID 高 8 位 */
        id_val |= (u32)ior(db, DM9000_PIDL) << 16;     /* 产品 ID 低 8 位 */
        id_val |= (u32)ior(db, DM9000_PIDH) << 24;     /* 产品 ID 高 8 位 */

        if (id_val == DM9000_ID)                       /* 0x90000A46 */
                break;
        dev_err(db->dev, "read wrong id 0x%08x\n", id_val);
}

读 8 次是官方注释写的「DM9000 有时会读错」，不是兜底客套。上电复位后第一次读经常读到全 0 或全 F，读到一次对的就 breakout。

复位只有一件事：往 NCR 写 NCR_RST。地址拍数据拍各 200us 延时。复位后 NCR 会自动清零。

5.1 EEPROM 读取 #

DM9000 的 MAC 地址来源有三条路：挂在芯片上的 EEPROM（如果焊了）、bootloader 通过 PAR 寄存器写进去的值、platform data 里指定的值。驱动按顺序试。

EEPROM 的访问地址在 0x0A（DM9000_EPAR）、命令在 0x0B（DM9000_EPCR）、数据在 0x0C（DM9000_EPDRL）和 0x0D（DM9000_EPDRH），读写靠 EPCR 里的 ER/EW/EPR 位（地址值未验证，按 datasheet 的 EEPROM 章节核对）。

驱动包成一个函数，取一个字（两个字节）：

text
dm9000_read_eeprom(db, offset, to)
  ├─ 上 addr_lock（EEPROM 与 PHY 共用这一把）
  ├─ 往 EPAR 写 offset
  ├─ 往 EPCR 写 ER | EPR（选寄存器区 + 读命令）
  ├─ 轮询 EPCR 的 ER 位，等硬件清掉（超时保护）
  ├─ 从 EPDRL 读低字节、EPDRH 读高字节
  └─ 放锁，拼成 16 位返回

dm9000_probe() 里那段调用是每 2 个字节读一次，凑 6 字节 MAC：

c
/* try reading the node address from the attached EEPROM */
for (i = 0; i < 6; i += 2)
        dm9000_read_eeprom(db, i / 2, ndev->dev_addr + i);

Mini2440 上 DM9000_PLATF_NO_EEPROM 置了位，这段读出来是 0x99 0x99 0x99 0x99 0x99 0x99（原文注释这么写的），is_valid_ether_addr() 判为无效，接着走 platform data 和 PAR 寄存器。三跳都失败才 eth_hw_addr_random()。

is_valid_ether_addr() 排除两种情况：全 0 地址、组播地址（第一个字节 bit0 为 1）。它不排除「本地管理地址」，所以随机 MAC 是这个函数生成的那种 02:xx:xx:xx:xx:xx 形态，从设备名 eth0 的输出里就能认出来。

5.2 软件复位与 IO 位宽选择 #

驱动先按数据资源的大小猜总线位宽，再让 platform data 覆盖：

c
static void dm9000_set_io(struct board_info *db, int byte_width)
{
    switch (byte_width) {
    case 1:
        db->dumpblk = dm9000_dumpblk_8bit;
        db->outblk  = dm9000_outblk_8bit;
        db->inblk   = dm9000_inblk_8bit;
        break;

    case 3:
        dev_dbg(db->dev, ": 3 byte IO, falling back to 16bit\n");
    case 2:
        db->dumpblk = dm9000_dumpblk_16bit;
        db->outblk  = dm9000_outblk_16bit;
        db->inblk   = dm9000_inblk_16bit;
        break;

    case 4:
    default:
        db->dumpblk = dm9000_dumpblk_32bit;
        db->outblk  = dm9000_outblk_32bit;
        db->inblk   = dm9000_inblk_32bit;
        break;
    }
}

case 3 故意不带 break，穿透到 16 位——3 字节位宽物理上不存在，只能退回 16 位。三组函数分别是逐字节、逐半字、逐字从 io_data 上 readb/writeb 循环，dumpblk 只读不写（丢弃用）。选中哪一组不仅影响速度，还决定 iow() 一次写几个字节，位宽配错的表现是寄存器读出来值对不上但地址没错。

六、DM9000 驱动的 probe 流程 #

DM9000 走的是 platform 总线。内核配置这样打开：

text
Device Drivers --->
   [*] Network device support -->
       [*] Ethernet driver support -->
            [*] DM9000 support

.config 里落成 CONFIG_DM9000=y，drivers/net/ethernet/davicom/Makefile 里是 obj-$(CONFIG_DM9000) += dm9000.o，编出来直接进内核镜像。驱动模块入口是 module_platform_driver(dm9000_driver)，展开后等价于：

c
module_init(dm9000_driver_init);
module_exit(dm9000_driver_exit);

static int __init dm9000_driver_init(void)
{
     platform_driver_register(dm9000_driver);
}

{

}

匹配方式有两条：老的板级描述靠 .name = "dm9000" 与 platform_device 同名；新一点的靠 of_match_table 里的 compatible = "davicom,dm9000"，由 dm9000_parse_dt() 把 DT 节点翻译成 dm9000_plat_data。

S3C2440 这类老 ARM 平台没有 DT，设备在 arch/arm/mach-s3c24xx/mach-smdk2440.c 里手写。参考同目录的 mach-mini2440.c，照抄改成自己的板子：

        .name           = "dm9000",
        .id             = -1,

三个资源的位置是死规矩，顺序错了驱动拿到的就是错东西：

索引 类型 内容 错位的后果

dm9000_plat_data 除了 flags 还有三个可选项：dev_addr 直接指定 MAC，inblk/outblk/dumpblk 覆盖默认的读写函数（有些板子的总线时序需要特殊拼法）。flags 的定义在 include/linux/dm9000.h：

标志 含义

DM9000_PLATF_16BITONLY 只用 16 位总线（Mini2440 用这个）
DM9000_PLATF_32BITONLY 只用 32 位总线
DM9000_PLATF_NO_EEPROM 板上没焊 EEPROM，跳过读 MAC
DM9000_PLATF_SIMPLE_PHY 简化 PHY 轮询（CONFIG_DM9000_FORCE_SIMPLE_PHY_POLL 会强制打开）
DM9000_PLATF_EXT_PHY 用外部 PHY，init_dm9000 里会置 NCR_EXT_PHY

设备注册的时机在机器初始化里。MACHINE_START 里 .init_machine = smdk2440_machine_init，这个函数里调 platform_add_devices(smdk2440_devices, ARRAY_SIZE(smdk2440_devices))，逐个调 platform_device_register()。把 &smdk2440_device_eth 加进那个数组，网卡设备才会被创建。

6.2 dm9000_probe 全流程 #

dm9000_probe() 四百多行，我们按顺序拆成七段。整段代码的关键私有结构是 struct board_info，贯穿全程，定义在 dm9000.c 开头：

c
struct board_info {
        void __iomem    *io_addr;       /* Register I/O base address */
        void __iomem    *io_data;       /* Data I/O address */
        u16              irq;           /* IRQ */

        u16             tx_pkt_cnt;
        u16             queue_pkt_len;
        u16             queue_start_addr;
        u16             queue_ip_summed;
        u16             dbug_cnt;
        u8              io_mode;                /* 0:word, 2:byte */
        u8              phy_addr;
        u8              imr_all;

        unsigned int    flags;
        unsigned int    in_timeout:1;
        unsigned int    in_suspend:1;
        unsigned int    wake_supported:1;

        enum dm9000_type type;

        void (*inblk)(void __iomem *port, void *data, int length);
        void (*outblk)(void __iomem *port, void *data, int length);
        void (*dumpblk)(void __iomem *port, int length);

        struct device   *dev;        /* parent device */

        struct resource *addr_res;   /* resources found */
        struct resource *data_res;
        struct resource *addr_req;   /* resources requested */
        struct resource *data_req;

        struct mutex     addr_lock;     /* phy and eeprom access lock */

        struct net_device  *ndev;

        spinlock_t      lock;

        struct mii_if_info mii;
        u32             msg_enable;
        u32             wake_state;

        int             ip_summed;
};

几个字段值得单独记：io_mode 是从 ISR 的 bit7:6 读回来的 I/O 位宽（0 是 16 位，2 是 8 位，注释里写「1 为 32 位」，这个映射与寄存器手册的编码是否一致未验证）；tx_pkt_cnt 是「已写进 TX SRAM 但还没发完」的包数，值域 0~2；addr_res/data_res 是 platform_get_resource() 拿到的原始资源，addr_req/data_req 是 request_mem_region() 抢下来的保留区，两套都要留，释放时前一套不用管，后一套要 release_mem_region()。

第一段，取电、复位、拿 platform data：

c
        power = devm_regulator_get(dev, "vcc");
        if (IS_ERR(power)) {
                if (PTR_ERR(power) == -EPROBE_DEFER)
                        return -EPROBE_DEFER;
                dev_dbg(dev, "no regulator provided\n");
        } else {
                ret = regulator_enable(power);
                if (ret != 0) {
                        dev_err(dev, "Failed to enable power regulator: %d\n", ret);
                        return ret;
                }
        }

        reset_gpios = of_get_named_gpio_flags(dev->of_node, "reset-gpios", 0, &flags);
        if (gpio_is_valid(reset_gpios)) {
                ret = devm_gpio_request_one(dev, reset_gpios, flags, "dm9000_reset");
                if (ret) {
                        dev_err(dev, "failed to request reset gpio %d: %d\n",
                                reset_gpios, ret);
                        return -ENODEV;
                }

                /* According to manual PWRST# Low Period Min 1ms */
                msleep(2);
                gpio_set_value(reset_gpios, 1);
                /* Needs 3ms to read eeprom when PWRST is deasserted */
                msleep(4);
        }

那两个 msleep 的数字来自手册：PWRST# 低电平最短 1ms，取 2ms 富余量；复位撤销后 EEPROM 要 3ms 才能读，取 4ms。这两个值不要随手改小。

第二段，分配 net_device 并初始化锁与私有数据：

c
        ndev = alloc_etherdev(sizeof(struct board_info));
        if (!ndev)
                return -ENOMEM;

        SET_NETDEV_DEV(ndev, &pdev->dev);
        db = netdev_priv(ndev);        /* 拿 alloc_etherdev 附带的私有区 */

        db->dev = &pdev->dev;
        db->ndev = ndev;

        spin_lock_init(&db->lock);
        mutex_init(&db->addr_lock);

        INIT_DELAYED_WORK(&db->phy_poll, dm9000_poll_work);

alloc_etherdev(size) 一次分出 net_device 加 size 字节私有区，netdev_priv() 拿到的就是后面那截。这是网卡驱动的标准套路，比分开两次分配省一次 kfree，也让 free_netdev() 一步回收干净。

第三段，资源获取与地址映射：

c
        db->addr_res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
        db->data_res = platform_get_resource(pdev, IORESOURCE_MEM, 1);

        if (!db->addr_res || !db->data_res) {
                dev_err(db->dev, "insufficient resources addr=%p data=%p\n",
                        db->addr_res, db->data_res);
                ret = -ENOENT;
                goto out;
        }

        ndev->irq = platform_get_irq(pdev, 0);
        if (ndev->irq < 0) {
                dev_err(db->dev, "interrupt resource unavailable: %d\n", ndev->irq);
                ret = ndev->irq;
                goto out;
        }

platform_get_irq(pdev, 0) 是 5.x 的写法，早期版本叫 platform_get_irq() 或者直接读 pdev->resource[2].start。db->irq_wake = platform_get_irq(pdev, 1) 是第二个中断资源，Mini2440 上没配，值是负数，request_irq 那段不会进。

接下来 request_mem_region() + ioremap() 对两组资源各做一次。request_mem_region() 不做任何映射，只是告诉内核「这段物理地址我要用」，防止别的驱动也来抢；ioremap() 才把物理地址映射成能 readb/writeb 的虚拟地址。两个返回值都要查，一个 NULL 一个 -EIO/-EINVAL。

第四段，确定 IO 位宽并复位：

c
        ndev->base_addr = (unsigned long)db->io_addr;

        /* ensure at least we have a default set of IO routines */
        dm9000_set_io(db, iosize);      /* 按数据资源大小先猜一次 */

        if (pdata != NULL) {
                if (pdata->flags & DM9000_PLATF_8BITONLY)
                        dm9000_set_io(db, 1);

                if (pdata->flags & DM9000_PLATF_16BITONLY)
                        dm9000_set_io(db, 2);

                if (pdata->flags & DM9000_PLATF_32BITONLY)
                        dm9000_set_io(db, 4);

                if (pdata->inblk != NULL)
                        db->inblk = pdata->inblk;

                if (pdata->outblk != NULL)
                        db->outblk = pdata->outblk;

                if (pdata->dumpblk != NULL)
                        db->dumpblk = pdata->dumpblk;

                db->flags = pdata->flags;
        }

        dm9000_reset(db);

第一次 dm9000_set_io(db, iosize) 传的是数据资源的大小（一般是 4），结果一定是选 32 位那组，紧接着被 platform data 覆盖。原文注释「下面也会这行一次，所以这里设置无效」说的就是这个。

第五段，读 ID 认芯片（代码见第五章），然后按 CHIPR 分型号，给 A/B 型打开校验和卸载：

c
        if (db->type == TYPE_DM9000A || db->type == TYPE_DM9000B) {
                ndev->hw_features = NETIF_F_RXCSUM | NETIF_F_IP_CSUM;
                ndev->features |= ndev->hw_features;
        }

第六段，填 net_device 的功能表：

c
        ndev->netdev_ops        = &dm9000_netdev_ops;
        ndev->watchdog_timeo    = msecs_to_jiffies(watchdog);
        ndev->ethtool_ops       = &dm9000_ethtool_ops;

        db->msg_enable       = NETIF_MSG_LINK;
        db->mii.phy_id_mask  = 0x1f;
        db->mii.reg_num_mask = 0x1f;
        db->mii.force_media  = 0;
        db->mii.full_duplex  = 0;
        db->mii.dev          = ndev;
        db->mii.mdio_read    = dm9000_phy_read;
        db->mii.mdio_write   = dm9000_phy_write;

struct mii_if_info 是老的 MII 兼容层，让 mii_check_media()、mii_ethtool_gset() 这类通用函数能把 DM9000 当成一个普通的 MII 设备。phy_id_mask = 0x1f 和 reg_num_mask = 0x1f 是 802.3 的硬规定：一条 MDIO 总线最多 32 个 PHY，每个 PHY 32 个寄存器。mdio_read/mdio_write 把 MII 的读写翻译成 DM9000 内部的 PHY 通路（DM9000_EPAR/EPCR 那套，选第几个 PHY、读写哪个寄存器）。

第七段，定 MAC 并注册：

c
        mac_src = "eeprom";

        for (i = 0; i < 6; i += 2)              /* 先试 EEPROM */
                dm9000_read_eeprom(db, i / 2, ndev->dev_addr + i);

        if (!is_valid_ether_addr(ndev->dev_addr) && pdata != NULL) {
                mac_src = "platform data";      /* 再试 platform data */
                memcpy(ndev->dev_addr, pdata->dev_addr, ETH_ALEN);
        }

        if (!is_valid_ether_addr(ndev->dev_addr)) {
                mac_src = "chip";               /* 再试芯片 PAR 寄存器 */
                for (i = 0; i < 6; i++)
                        ndev->dev_addr[i] = ior(db, i + DM9000_PAR);
        }

        if (!is_valid_ether_addr(ndev->dev_addr)) {
                inv_mac_addr = true;
                eth_hw_addr_random(ndev);       /* 最后随机 */
                mac_src = "random";
        }

        platform_set_drvdata(pdev, ndev);
        ret = register_netdev(ndev);

三条来路加一条兜底，打印里那个 (%s) 就是 mac_src，dmesg 里一眼看出 MAC 从哪来：

text
eth0: dm9000e at c2802300,c2802304 IRQ 55 MAC: 86:51:42:d9:d0:cc (chip)

86: 这个首字节是组播地址（bit0=1），正是「从 PAR 读到一个没写好的值」的死证据。bootloader 里 set ethaddr 那句没执行，或者 PAR 寄存器被写坏，都会这样。这种 MAC 能勉强通信但在交换机侧行为不对，一定要修。

out: 标签那段收尾：dm9000_release_board() 释放两块 request_mem_region 和一个中断，然后 free_netdev(ndev)。dm9000_release_board() 内部是按「已经申请到哪一步」逐层判断的，所以不用担心只做了一半。

七、DM9000 的收发实现 #

probe 只负责把设备和驱动对上。真正的数据搬运从 ifconfig eth0 up 开始。

7.1 net_device_ops 与 open #

c
static const struct net_device_ops dm9000_netdev_ops = {

ndo_open 的活儿：打开收发送中断、初始化芯片、激活发送队列。

c
static int dm9000_open(struct net_device *dev)
{
        struct board_info *db = netdev_priv(dev);
        unsigned int irq_flags = irq_get_trigger_type(dev->irq);

        if (netif_msg_ifup(db))
                dev_dbg(db->dev, "enabling %s\n", dev->name);

        /* If there is no IRQ type specified, tell the user that this is a problem */
        if (irq_flags == IRQF_TRIGGER_NONE)
                dev_warn(db->dev, "WARNING: no IRQ resource flags set.\n");

        irq_flags |= IRQF_SHARED;

        /* GPIO0 on pre-activate PHY, Reg 1F is not set by reset */
        iow(db, DM9000_GPR, 0);   /* 写 0 为内部 PHY 供电 */
        mdelay(1);                /* delay needs by DM9000B */

        dm9000_init_dm9000(dev);

        if (request_irq(dev->irq, dm9000_interrupt, irq_flags, dev->name, dev))
                return -EAGAIN;

        dm9000_unmask_interrupts(db);

        db->dbug_cnt = 0;

        mii_check_media(&db->mii, netif_msg_link(db), 1);
        netif_start_queue(dev);

        /* Poll initial link status */
        schedule_delayed_work(&db->phy_poll, 1);

        return 0;
}

三个细节别漏。第一，irq_flags 来自资源描述里的 IORESOURCE_IRQ | IORESOURCE_IRQ_HIGHEDGE，也就是上升沿触发；资源里没写触发方式的话 irq_get_trigger_type() 返回 IRQF_TRIGGER_NONE，驱动只打一句警告就继续，结果就是中断要么一直进要么一直不进，ifconfig 里 interrupt 计数不动。第二，IRQF_SHARED 是硬加的，因为 EINT7 这根线有被别的设备共用的风险；共享中断要求最后一个参数不能为空，这里传的是 dev，中断处理函数靠它反查出 board_info。第三，iow(db, DM9000_GPR, 0) 这个「给内部 PHY 供电」的动作必须在初始化之前做，DM9000 复位不会自动置这个位。

dm9000_init_dm9000() 全是寄存器操作，按顺序下料：

c
static void dm9000_init_dm9000(struct net_device *dev)
{
        struct board_info *db = netdev_priv(dev);
        unsigned int imr;
        unsigned int ncr;

        dm9000_reset(db);             /* 复位 */
        dm9000_mask_interrupts(db);   /* IMR 写 IMR_PAR，只留使能位 */

        /* I/O mode */
        db->io_mode = ior(db, DM9000_ISR) >> 6; /* ISR bit7:6 keeps I/O mode */

        /* Checksum mode */
        if (dev->hw_features & NETIF_F_RXCSUM)
                iow(db, DM9000_RCSR,
                        (dev->features & NETIF_F_RXCSUM) ? RCSR_CSUM : 0);

        iow(db, DM9000_GPCR, GPCR_GEP_CNTL);    /* Let GPIO0 output */
        iow(db, DM9000_GPR, 0);                 /* 再写一次，上电 PHY */

        /* If we are dealing with DM9000B, some extra steps are required */
        if (db->type == TYPE_DM9000B) {
                dm9000_phy_write(dev, 0, MII_BMCR, BMCR_RESET);
                dm9000_phy_write(dev, 0, MII_DM_DSPCR, DSPCR_INIT_PARAM);
        }

        ncr = (db->flags & DM9000_PLATF_EXT_PHY) ? NCR_EXT_PHY : 0;
        if (db->wake_supported)
                ncr |= NCR_WAKEEN;
        iow(db, DM9000_NCR, ncr);

        /* Program operating register */
        iow(db, DM9000_TCR, 0);         /* TX Polling clear */
        iow(db, DM9000_BPTR, 0x3f);     /* Less 3Kb, 200us */
        iow(db, DM9000_FCR, 0xff);      /* Flow Control */
        iow(db, DM9000_SMCR, 0);        /* Special Mode */
        /* clear TX status */
        iow(db, DM9000_NSR, NSR_WAKEST | NSR_TX2END | NSR_TX1END);
        iow(db, DM9000_ISR, ISR_CLR_STATUS); /* Clear interrupt status */

        /* Set address filter table */
        dm9000_hash_table_unlocked(dev);

        imr = IMR_PAR | IMR_PTM | IMR_PRM;
        if (db->type != TYPE_DM9000E)
                imr |= IMR_LNKCHNG;

        db->imr_all = imr;

        db->tx_pkt_cnt = 0;
        db->queue_pkt_len = 0;
        netif_trans_update(dev);
}

RCR 不在这里写，它在 dm9000_mask_interrupts() 之前那次复位里由驱动按需开——更准确地说，收包使能 RCR_RXEN 是在 dm9000_rx() 出错分支里被关掉、下一次中断 dm9000_tx_done() 之后才重开的。原文这一段没有 RCR_RXEN 的赋值语句（未验证是否为素材截断），实战中以实际源码为准。

netif_trans_update(dev) 是 4.7 之后的名字，之前叫 dev->trans_start = jiffies。它把「上次发包时刻」推到当前，ndo_tx_timeout 的计时从这里起算。初始化里重置它是为了让第一次超时从 open 开始算，不吃上一次的旧值。

dm9000_stop() 是反操作：

c
static int dm9000_stop(struct net_device *ndev)
{
        struct board_info *db = netdev_priv(ndev);

        if (netif_msg_ifdown(db))
                dev_dbg(db->dev, "shutting down %s\n", ndev->name);

        cancel_delayed_work_sync(&db->phy_poll);

        netif_stop_queue(ndev);
        netif_carrier_off(ndev);

        /* free interrupt */
        free_irq(ndev->irq, ndev);

        dm9000_shutdown(ndev);

        return 0;
}

顺序有讲究：先 cancel_delayed_work_sync() 把链路轮询停掉（否则轮询里还在读寄存器，而 free_irq 之后 io_data 的映射已经要被拆），再关队列和 carrier，再放中断，最后关芯片。

7.2 ndo_start_xmit：两包流水线 #

先把这个函数的签名说清。5.x 里 ndo_start_xmit 的返回类型是 netdev_tx_t，返回值只有两个要认的：NETDEV_TX_OK（这个 skb 我接管了，协议栈别再管）和 NETDEV_TX_BUSY（现在发不了，skb 还给你，等下再试）。2.6 时代它返回 int，0 相当于 OK、1 相当于 BUSY；从 netdev_tx_t 引入（2.6.31 前后）到 3.x 之间那个双轨期，返回 NETDEV_TX_BUSY 就会被协议栈当成 1。这颗老驱动跨了这条线，写移植补丁时要按目标内核的 ndo_start_xmit 原型改。

DM9000 的 TX SRAM 只够塞两个包，所以驱动自己搭了一条两级流水线：第一个包立刻启动发送，第二个包先写进 SRAM 排队。

c
static int dm9000_start_xmit(struct sk_buff *skb, struct net_device *dev)
{
        unsigned long flags;
        struct board_info *db = netdev_priv(dev);

        dm9000_dbg(db, 3, "%s:\n", __func__);

        if (db->tx_pkt_cnt > 1)               /* 已经有两个包在流水线上 */
                return NETDEV_TX_BUSY;

        spin_lock_irqsave(&db->lock, flags);  /* 进程和中断都要动地址寄存器 */

        /* Move data to DM9000 TX RAM */
        writeb(DM9000_MWCMD, db->io_addr);

        (db->outblk)(db->io_data, skb->data, skb->len);
        dev->stats.tx_bytes += skb->len;

        db->tx_pkt_cnt++;
        /* TX control: First packet immediately send, second packet queue */
        if (db->tx_pkt_cnt == 1) {            /* 第一个：立刻发 */
                dm9000_send_packet(dev, skb->ip_summed, skb->len);
        } else {                              /* 第二个：只进 SRAM，排队 */
                db->queue_pkt_len = skb->len;
                db->queue_ip_summed = skb->ip_summed;
                netif_stop_queue(dev);        /* 拦住上层，别再给了 */
        }

        spin_unlock_irqrestore(&db->lock, flags);

        /* free this SKB */
        dev_consume_skb_any(skb);

        return NETDEV_TX_OK;
}

一次完整发包的动作序列：

  1. 往地址寄存器写 DM9000_MWCMD，接下来的写数据拍都送往 TX SRAM，每写一个单位地址自动递增；
  2. outblk() 把 skb->data 的 skb->len 字节一单位一单位搬进 SRAM；
  3. dm9000_send_packet() 往 TXPLL/TXPLH 写长度，再往 TCR 写 TCR_TXREQ 启动；
  4. 硬件发完置 NSR_TX1END（或 NSR_TX2END）、拉中断；
  5. 中断处理里 dm9000_tx_done() 读完 NSR 把 tx_pkt_cnt 减一，如果还有排队的包就启动它，然后 netif_wake_queue() 唤醒被堵住的上层。

第三到第五步就是 dm9000_send_packet()：

c
static void dm9000_send_packet(struct net_device *dev, int ip_summed, u16 pkt_len)
{
        struct board_info *dm = to_dm9000_board(dev);

        /* The DM9000 is not smart enough to leave fragmented packets alone. */
        if (dm->ip_summed != ip_summed) {
                if (ip_summed == CHECKSUM_NONE)
                        iow(dm, DM9000_TCCR, 0);
                else
                        iow(dm, DM9000_TCCR, TCCR_IP | TCCR_UDP | TCCR_TCP);
                dm->ip_summed = ip_summed;
        }

        /* Set TX length to DM9000 */
        iow(dm, DM9000_TXPLL, pkt_len);
        iow(dm, DM9000_TXPLH, pkt_len >> 8);

        /* Issue TX polling command */
        iow(dm, DM9000_TCR, TCR_TXREQ); /* Cleared after TX complete */
}

ip_summed 那段是给分片报文补的：DM9000 的硬件校验和只对完整包成立，遇到 CHECKSUM_PARTIAL（分片需要软件分段）时它不会自己识别，所以每次 ip_summed 变化都要重新写 TCCR。这个变量缓存在 db->ip_summed 里，省掉每包一次寄存器写。

这里能看出 NETDEV_TX_BUSY 那条早退的道理：tx_pkt_cnt > 1 时 SRAM 满了，再写就会覆盖掉正在发的包。早退之后协议栈会把 skb 放回队列，等 netif_wake_queue() 之后再调一次。

7.3 中断处理 #

c
static irqreturn_t dm9000_interrupt(int irq, void *dev_id)
{
        struct net_device *dev = dev_id;
        struct board_info *db = netdev_priv(dev);
        int int_status;
        unsigned long flags;
        u8 reg_save;

        dm9000_dbg(db, 3, "entering %s\n", __func__);

        /* holders of db->lock must always block IRQs */
        spin_lock_irqsave(&db->lock, flags);

        /* Save previous register address */
        reg_save = readb(db->io_addr);

        dm9000_mask_interrupts(db);
        /* Got DM9000 interrupt status */
        int_status = ior(db, DM9000_ISR);       /* Got ISR */
        iow(db, DM9000_ISR, int_status);        /* Clear ISR status，写 1 清 */

        if (netif_msg_intr(db))
                dev_dbg(db->dev, "interrupt status %02x\n", int_status);

        /* Received the coming packet */
        if (int_status & ISR_PRS)
                dm9000_rx(dev);

        /* Transmit Interrupt check */
        if (int_status & ISR_PTS)
                dm9000_tx_done(dev, db);

        if (db->type != TYPE_DM9000E) {
                if (int_status & ISR_LNKCHNG) {
                        /* fire a link-change request */
                        schedule_delayed_work(&db->phy_poll, 1);
                }
        }

        dm9000_unmask_interrupts(db);
        /* Restore previous register address */
        writeb(reg_save, db->io_addr);

        spin_unlock_irqrestore(&db->lock, flags);

        return IRQ_HANDLED;
}

五个动作：存地址寄存器、屏蔽中断防嵌套、读 ISR 并写回清标志、按 ISR_PRS/ISR_PTS 分别调 rx 和 tx_done、恢复屏蔽与地址。

reg_save 那两行是这个驱动最容易被误删的代码。DM9000 的地址寄存器只有一份，中断插在某次 ior() 的「写地址」和「读数据」两拍之间时，中断里改掉的寄存器号会让中断返回后那次读数据读到错误的寄存器。存下来再写回，把两拍还原成原子。

ISR 是写 1 清零，不是写 0 清零，也不是读清零。这里 iow(db, DM9000_ISR, int_status) 是把刚读到的位原样写回去，等于清掉所有立起来的位。

7.4 发送完成：dm9000_tx_done #

c
static void dm9000_tx_done(struct net_device *dev, struct board_info *db)
{
        int tx_status = ior(db, DM9000_NSR);    /* Got TX status */

        if (tx_status & (NSR_TX2END | NSR_TX1END)) {
                /* One packet sent complete */
                db->tx_pkt_cnt--;
                dev->stats.tx_packets++;

                if (netif_msg_tx_done(db))
                        dev_dbg(db->dev, "tx done, NSR %02x\n", tx_status);

                /* Queue packet check & send */
                if (db->tx_pkt_cnt > 0)
                        dm9000_send_packet(dev, db->queue_ip_summed, db->queue_pkt_len);
                netif_wake_queue(dev);
        }
}

NSR_TX1END 是第 1 个包发完，NSR_TX2END 是第 2 个。中断里不管哪个立起来都只减一次 tx_pkt_cnt——因为一次中断只代表「有一个包完成了」。如果排队里还有包就立刻启动它，然后无条件 netif_wake_queue()：wake_queue 对已经处于 running 状态的队列是幂等的，多调一次没副作用，所以这里不需要判断。

7.5 接收：RX 头与 dm9000_rx #

RX SRAM 里每个包前面有 4 字节头：

偏移 字段 值
0 RxPktReady 固定 0x01，表示这个位置有包
1 RxStatus 与 RSR 寄存器同构的状态位
2~3 RxLen 有效数据长度，小端 
c
struct dm9000_rxhdr {
        u8      RxPktReady;
        u8      RxStatus;
        __le16  RxLen;
} __packed;

__packed 必须有：结构体自然对齐下 __le16 会被排到偏移 2，这里恰好也是 2，但去掉 __packed 之后编译器不保证，换 64 位或者换编译器就错位。

c
static void dm9000_rx(struct net_device *dev)
{
        struct board_info *db = netdev_priv(dev);
        struct dm9000_rxhdr rxhdr;
        struct sk_buff *skb;
        u8 rxbyte, *rdptr;
        bool GoodPacket;
        int RxLen;

        /* Check packet ready or not */
        do {
                ior(db, DM9000_MRCMDX);      /* Dummy read，地址不变 */

                rxbyte = readb(db->io_data); /* 读 RX SRAM 第一字节，固定 0x01 */

                /* Status check: this byte must be 0 or 1 */
                if (rxbyte & DM9000_PKT_ERR) {
                        dev_warn(db->dev, "status check fail: %d\n", rxbyte);
                        iow(db, DM9000_RCR, 0x00);      /* Stop Device */
                        return;
                }

                if (!(rxbyte & DM9000_PKT_RDY))
                        return;

                /* A packet ready now  & Get status/length */
                GoodPacket = true;
                writeb(DM9000_MRCMD, db->io_addr);

                (db->inblk)(db->io_data, &rxhdr, sizeof(rxhdr));

                RxLen = le16_to_cpu(rxhdr.RxLen);

                if (netif_msg_rx_status(db))
                        dev_dbg(db->dev, "RX: status %02x, length %04x\n",
                                rxhdr.RxStatus, RxLen);

                /* Packet Status check，以太帧长度 (64, 1536] */
                if (RxLen < 0x40) {
                        GoodPacket = false;
                        if (netif_msg_rx_err(db))
                                dev_dbg(db->dev, "RX: Bad Packet (runt)\n");
                }

                if (RxLen > DM9000_PKT_MAX) {
                        dev_dbg(db->dev, "RST: RX Len:%x\n", RxLen);
                }

                /* rxhdr.RxStatus is identical to RSR register */
                if (rxhdr.RxStatus & (RSR_FOE | RSR_CE | RSR_AE |
                                      RSR_PLE | RSR_RWTO |
                                      RSR_LCS | RSR_RF)) {
                        GoodPacket = false;
                        if (rxhdr.RxStatus & RSR_FOE) {
                                if (netif_msg_rx_err(db))
                                        dev_dbg(db->dev, "fifo error\n");
                                dev->stats.rx_fifo_errors++;
                        }
                        if (rxhdr.RxStatus & RSR_CE) {
                                if (netif_msg_rx_err(db))
                                        dev_dbg(db->dev, "crc error\n");
                                dev->stats.rx_crc_errors++;
                        }
                        if (rxhdr.RxStatus & RSR_RF) {
                                if (netif_msg_rx_err(db))
                                        dev_dbg(db->dev, "length error\n");
                                dev->stats.rx_length_errors++;
                        }
                }

                /* Move data from DM9000 */
                if (GoodPacket &&
                    ((skb = netdev_alloc_skb(dev, RxLen + 4)) != NULL)) {
                        skb_reserve(skb, 2);
                        rdptr = skb_put(skb, RxLen - 4);

                        (db->inblk)(db->io_data, rdptr, RxLen);
                        dev->stats.rx_bytes += RxLen;

                        /* Pass to upper layer */
                        skb->protocol = eth_type_trans(skb, dev);
                        if (dev->features & NETIF_F_RXCSUM) {
                                if ((((rxbyte & 0x1c) << 3) & rxbyte) == 0)
                                        skb->ip_summed = CHECKSUM_UNNECESSARY;
                                else
                                        skb_checksum_none_assert(skb);
                        }
                        netif_rx(skb);
                        dev->stats.rx_packets++;
                } else {
                        /* need to dump the packet's data */
                        (db->dumpblk)(db->io_data, RxLen);
                }
        } while (rxbyte & DM9000_PKT_RDY);
}

逐段看：

  • ior(db, DM9000_MRCMDX) 是空读。MRCMDX 的特点是读它不改 SRAM 指针，专门用来探「下一个位置有没有包」，探完再 readb 取那个 0x01。
  • DM9000_PKT_ERR 那个分支是致命的：读了半个包或者状态乱掉，驱动直接把 RCR 写 0 关掉接收，然后返回。芯片这时是聋的，下次 ifconfig down/up 才能恢复。这条分支只在硬件出问题时走到。
  • writeb(DM9000_MRCMD, db->io_addr) 之后地址指针就锁在 RX SRAM 上了，后面的 inblk 连续读。注意这里只用 writeb 写地址，不再 ior——ior 会额外读一次数据，把 SRAM 指针多推一格。
  • RxLen 包含 4 字节头，所以 skb_put(skb, RxLen - 4) 拿的是纯数据长度，但 inblk 读的是 RxLen 字节，也就是把头也读进了 rdptr。这是原样代码（头 4 字节被读进数据区开头，后面又被 eth_type_trans 按以太头处理），效果是把 4 字节垃圾当成以太头的一部分——这一段是素材原样，行为上是读 RxLen 字节到只留了 RxLen-4 的空间之外，属于「照抄历史代码但别学它」的典型，我们只作为反面材料记录，不改写它的语义。
  • 校验和判断那一行 (((rxbyte & 0x1c) << 3) & rxbyte) == 0 是查 RxPktReady 字节里那几位状态，不是查 RxStatus。这个位运算的含义原文没讲，未验证。
  • netif_rx() 是老的收包接口，把 skb 丢进 per-CPU 的 backlog 队列，等软中断慢慢处理，不走 NAPI。这颗芯片的驱动就是非 NAPI 的，这也是它吞吐上不去的原因之一。

dm9000_timeout() 是协议栈发现「包发出去没回执」时调的回调：

c
static void dm9000_timeout(struct net_device *dev)
{
        struct board_info *db = netdev_priv(dev);
        u8 reg_save;
        unsigned long flags;

        spin_lock_irqsave(&db->lock, flags);
        db->in_timeout = 1;
        reg_save = readb(db->io_addr);

        netif_stop_queue(dev);
        dm9000_init_dm9000(dev);
        dm9000_unmask_interrupts(db);
        /* We can accept TX packets again */
        netif_trans_update(dev); /* prevent tx timeout */
        netif_wake_queue(dev);

        writeb(reg_save, db->io_addr);
        db->in_timeout = 0;
        spin_unlock_irqrestore(&db->lock, flags);
}

超时处理就是「整个重来」：关队列、重新初始化芯片、开中断、推 trans_start、开队列。db->in_timeout 标志位会在 dm9000_init_dm9000() 里被用上（那条路径会跳过 netif_trans_update，避免超时重入时又推一次时钟），具体用法未在正文展开。

7.6 收发的内存视角 #

整条路径上没有 DMA——DM9000 没有 DMA，全靠 CPU 一个单位一个单位地读写 I/O 口。吞吐上限由总线和 CPU 决定：16 位总线上搬一帧 1500 字节要写 750 次，这颗芯片配 S3C2440 跑 100M 已经把 CPU 吃满了。

          [*] Root file system on NFS

NFS client support for NFS version 4 勾上之后 v2、v3 的支持自动带上（v4 依赖它们）。真正决定「能不能拿 NFS 当根」的是第二项 CONFIG_ROOT_NFS，素材原文漏了这个（它只写了 NFS 客户端），少了它内核启动到最后会卡在 VFS: Unable to mount root fs。改完存盘并把 defconfig 存回去：

bash
make menuconfig
mv .config arch/arm/configs/s3c2440_defconfig

然后重新编内核。

8.4 搭共享目录与启动参数 #

宿主机侧，把根文件系统复制到 NFS 共享路径：

bash
cp -a /work/sambashare/rootfs /work/nfs_root/

/etc/exports 里加 /work/nfs_root/rootfs *(rw,sync,no_root_squash)，exportfs -ra 生效。no_root_squash 不能少，否则板上以 root 身份创建的文件在服务器上会变成 nobody，/etc 写不进去。

板子侧，u-boot 里设 bootargs：

text
set bootargs "noinitrd console=ttySAC0,115200 root=/dev/nfs rw nfsroot=192.168.0.200:/work/nfs_root/rootfs ip=192.168.0.105:192.168.0.200:192.168.0.1:255.255.255.0::eth0:off"
save

ip= 是内核 ipconfig 的自动配置语法，冒号分段，这里用到前八段：

位置 值 含义
1 192.168.0.105 板子自己的 IP
2 192.168.0.200 NFS 服务器，也是默认服务器地址
3 192.168.0.1 网关地址
4 255.255.255.0 子网掩码
5 空 板子主机名，不填
6 eth0 使用的网络设备
7 off 关闭动态获取（DHCP/BOOTP/RARP 全关）

::eth0:off 前面是两个冒号——第 5 段留空也要占位。root=/dev/nfs 是「用 NFS 当根」的固定写法，不是真有个叫 nfs 的设备。rw 让根可写，调试期必须开。这串参数很长，从文本直接粘到串口终端容易错位（串口没流控时尤其），错位的表现就是启动到一半 VFS: Unable to mount root fs。

启动：

text
nand read 0x30000000 kernel
bootm 0x30000000

0x30000000 是 NAND 读的目的地址，也是 bootm 的入参。启动成功后内核会先打 IP-Config: 那几行（配置到的 IP、网关、DNS），然后是 VFS: Mounted root (nfs filesystem) 和 Freeing unused kernel memory。这两行之后没有别的东西，就该看到 shell 提示符了。

8.5 NFS 根起来之后的收益 #

改一个驱动，make uImage，拷到 /work/nfs_root/rootfs/lib/modules/... 或者直接替换内核，板子重启就生效。「先移植 DM9000、再谈其它驱动」的顺序就是这么来的：网通了，后面每个驱动都省掉一次烧写。代价是 NFS 断网就完蛋，生产环境要换回块设备或 flash 上的 rootfs。

九、RTL8211F 的硬件特性 #

换到 RK3588 这条线。这里的 MAC 是 SoC 里的 GMAC，PHY 是外挂的 RTL8211F，中间走 RGMII。

RTL8211F 是 Realtek 的 10/100/1000Mbps PHY，广泛用于机顶盒、瘦客户机、路由器和工业产品。它是一个系列，子型号决定接口：

型号 RGMII SGMII 备注
RTL8211F-CG 支持 不支持 RK3588 常见选项
RTL8211FS-CG 支持 支持 同一块板可切 SGMII

RK3588 的两个 GMAC 提供 RGMII 或 RMII 接外置 PHY：RGMII 支持 10/100/1000 Mbps，RMII 支持 10/100 Mbps；GMAC0 的 RGMII/RMII 引脚复用在 VCCIO3 电源域，这个电源域的电压和引脚驱动强度直接决定时序能不能对上。

一条完整的千兆链路是这么串起来的：

text
RK3588 MAC → RGMII 接口 → RTL8211F PHY → H5007 网络变压器 → RJ45 插座 → 外部网络

发送路径：RTL8211F 把 RGMII 的 4 位 DDR 信号转成串行差分信号（TXP/TXN），H5007 把这 1.1V 的低压差分升到 ±2.5V，再用阻抗匹配网络驱动双绞线。

接收路径：H5007 从双绞线收 ±2.5V，降压到 1.1V 送进 RTL8211F 的 RXP/RXN，PHY 内部均衡器补偿衰减，恢复成干净的数字信号。

网络变压器 H5007 在这里不是可选件。它做三件事：电气隔离（几百伏的共模电压挡在板子外面）、共模抑制、阻抗匹配。省掉它，短距离能通，长线或者有雷击时芯片直接烧。

PHY 芯片本身的电路很简单——一颗芯片、一颗 25MHz 晶振（或者从 SoC 的 MCLKINOUT 拿时钟）、几颗去耦电容、几个配置用的上下拉电阻。配置电阻（strap pin）决定上电默认值：PHY 地址、是否开自动协商、PHYAD 几位。这几个引脚的电阻焊错，Probe 阶段就找不到 PHY。

9.1 PHY 的必要性，四句话说清 #

  1. 信号转换：MAC 输出数字信号，双绞线要差分曼彻斯特编码的 ±2.5V 电平；
  2. 介质适配：同一颗 MAC 接双绞线、光纤、同轴，靠换 PHY 就行；
  3. 信号完整性：均衡器、时钟恢复、自适应均衡消 ISI，这些全是模拟电路，MAC 这个纯数字器件干不了；
  4. 协议标准化：802.3 对每种介质的电气特性有硬规范，PHY 保证符合，否则各家设备互通不了。

一句话：「MAC 管数据怎么组织，PHY 管数据怎么在现实介质里可靠地跑」，两者缺一不可。

十、PHY 的寄存器与自协商 #

PHY 的寄存器按 IEEE 802.3 Clause 22 编址：一条 MDIO 总线最多 32 个 PHY（地址 0~31），每个 PHY 前 16 个寄存器（0~15）是标准化的，16~31 留给厂商自定义。

10.1 三个标准寄存器 #

寄存器 地址 名字 关键位
MII_BMCR 0x00 Basic Mode Control bit15 BMCR_RESET 复位；bit13 BMCR_SPEED100；bit12 BMCR_ANENABLE 自动协商使能；bit11 BMCR_PDOWN 掉电；bit9 BMCR_FULLDPLX；bit8 BMCR_CTST
MII_BMSR 0x01 Basic Mode Status bit2 BMSR_LSTATUS 链路状态（1 = up）；bit3 BMSR_ANEGCAPABLE；bit5 BMSR_ANEGCOMPLETE；bit8 BMSR_ESTATEN 扩展状态可用；bit15 BMSR_100FULL2 等能力位
MII_PHYSID1/MII_PHYSID2 0x02/0x03 PHY ID 高 16 位 / 低 16 位；Realtek 的 OUI 段在 0x001cc8xx
MII_ADVERTISE 0x04 Auto-Neg Advertisement 我支持什么：10/100、半/全双工、ADVERTISE_PAUSE_CAP
MII_LPA 0x05 Link Partner Ability 对端支持什么：从对端发来的 FLP 里读出来的
MII_EXPANSION 0x06 Expansion bit5 EXPANSION_MFAULTS 等
MII_CTRL1000 0x09 1000BASE-T Control bit9 ADVERTISE_1000FULL，bit8 ADVERTISE_1000HALF
MII_STAT1000 0x0A 1000BASE-T Status bit11 LPA_1000FULL 对端千兆全双工；bit10 LPA_1000HALF
MII_ESTATUS 0x0F Extended Status 能读到 1000BASE-T 的能力位，前面 BMSR_ESTATEN 置位才读得到
MII_LBRERROR 0x10 扩展寄存器指针 Realtek 用它做「页选择 + 数据」两段式访问

RK3588 上的 RTL8211F，PHY 地址由硬件 strap 决定，DTS 里 mdio 节点下 reg = <0> 就表示地址 0，对应 sysfs 里的 stmmac-0:00 这个目录名（前面是 MAC 控制器名，冒号后面是 PHY 地址）。

10.2 自协商流程 #

自动协商是两颗 PHY 之间的握手：双方各发一串 FLP（Fast Link Pulse）把自己支持的能力告诉对方，然后各自取交集，选最高档的工作模式。

text
1. 上电/复位后 BMCR_ANENABLE=1，TXD 线上开始发 FLP
2. A 端把 ADVERTISE(0x04) 的内容编码进 FLP 发给 B 端
3. B 端同样发；两端各自把对方的 FLP 解出来存进 LPA(0x05)
4. 千兆能力不在 FLP 里，走 CTLR1000(0x09)/STAT1000(0x0A) 的扩展协商
5. 两侧按 1000F > 1000H > 100F > 100H > 10F > 10H 的优先级取交集
6. BMSR_ANEGCOMPLETE(bit5) 置 1，协商结束
7. 链路训练（千兆要 echo canceller / 均衡器收敛），BMSR_LSTATUS(bit2) 置 1
8. 内核 phylib 读 BMSR_LSTATUS，调 netif_carrier_on()

状态判读用哪几个位：

现象 要看哪个位 含义
链路没起 BMSR.LSTATUS=0 物理层没建立连接，查线、查对端、查变压器
协商完了但没链路 BMSR.ANEGCOMPLETE=1 而 LSTATUS=0 参数谈好了但物理链路握不上，多半在 PMA/PMD 一侧
只跑到 100M STAT1000.LPA_1000FULL=0 对端不支持千兆，或者只有两对线通
跑百兆但丢包 BMSR 能力位正常，LPA 与实际能力不符 线序错（只通 1-2、3-6），千兆要四对全通
半双工 BMCR.FULLDPLX=0 对端强制半双工，或者自协商失败落到并行检测

自协商失败之后 PHY 会退到并行检测（Parallel Detection）：只能识别出速率不能识别双工，于是默认半双工。这就是「百兆半双工、大量冲突、速度慢得离谱」的根源，ethtool eth0 的 Duplex: Half 一眼能看出来。

10.3 强制模式 #

把 BMCR.ANENABLE 清 0 就进了强制模式，此时 BMCR.SPEED100 和 BMCR.FULLDPLX 决定速率和双工，自协商寄存器全部作废。强制模式最大的坑是两端必须同时强制成一样的：一端强制百兆全双工，另一端自协商，自协商那端读不到 FLP 就会退到并行检测→半双工，于是「一端全双工一端半双工」，冲突计数飙升，表现为「能 ping 通但传大文件就断」。

正确做法是两端都自协商，或者两端都强制成同参数。

十一、RTL8211F 驱动的实现 #

RTL8211F 在 5.10 上有两种用法：通用 PHY 驱动，或者 Realtek 专用驱动。

11.1 phy_device 与 phy_driver #

PHY 在 Linux 里是一个挂在 MDIO 总线上的设备，对应 struct phy_device；驱动是 struct phy_driver，两者用 PHY ID 匹配。

c
/* 5.10 的形态，字段裁剪过 */
struct phy_device {
        struct mdio_device mdio;      /* 内嵌，含 bus、addr、dev */
        u32 phy_id;
        u32 phy_id_mask;
        ...
        struct phy_driver *drv;
        struct device_link *devlink;
        struct mutex lock;
        ...
        int speed;
        int duplex;
        int pause;
        ...
};

关键点：phy_device 内嵌 struct mdio_device，mdio_device 里才有 struct device dev。所以 &phydev->mdio.dev 才是设备模型意义上那个 device，写驱动时别直接拿 phydev 当 device 用。

5.10 系列的 PHY 注册走 phy_driver_register()，注册的是一张 phy_driver 数组。6.x 之后重构过一次：phy_driver 里塞了 probe 回调、phy_device_create 之后要 phy_attach_direct()，struct phy_driver 的名字也被统一成「driver」。本篇的代码形态按 5.10，看到 phy_attach_direct() 的字样要按那个版本理解。

c
/* 形态示意，5.10 */
static struct phy_driver realtek_drvs[] = {
        {
                .phy_id         = 0x001cc916,
                .name           = "RTL8211F Gigabit Ethernet",
                .phy_id_mask    = 0x001fffff,
                .features       = PHY_GBIT_FEATURES,
                .config_init    = rtl8211f_config_init,
                .config_aneg    = genphy_config_aneg,
                .read_status    = rtl8211f_read_status,
                .suspend        = genphy_suspend,
                .resume         = genphy_resume,
        },
};

module_phy_driver(realtek_drvs);

phy_id 配 phy_id_mask 是匹配规则：(phydev->phy_id & phy_driver->phy_id_mask) == phy_driver->phy_id。Realtek 的 ID 是 0x001cc8xx 这一段，rtl8211f 具体是 0x001cc916（未在素材中给出，按 Realtek 公开的 PHY ID 记录，实际以 phy 实测值为准）。

回调各管一段：

回调 何时被调 该做什么
config_init phy_attach 之后、起链之前一次 写厂商私有寄存器：RGMII 延时、LED、TX 幅度、EEE
config_aneg 自协商参数变化时 写 ADVERTISE/CTRL1000，genphy_config_aneg 已经把标准部分做完了
read_status 每次 phy_start_machine 轮询 读 BMSR/STAT1000，更新 phydev->speed/duplex，返回链路状态
suspend/resume 系统电源状态切换 读写 BMCR.PDOWN
ack_interrupt 中断模式 清 PHY 的中断源

11.2 通用驱动与专用驱动的分工 #

Rockchip 官方的说法很直接：PHY 驱动一般用通用 PHY 驱动，需要改特殊寄存器时才上对应的 PHY 驱动，代码都在 drivers/net/phy。

通用驱动 drivers/net/phy/phy_device.c 里的 genphy_* 系列能干这些：读 BMSR 判链路、genphy_config_aneg 按 phydev->advertising 填 ADVERTISE、genphy_read_status 解析速度双工。RTL8211F 的绝大多数板子用通用驱动就够。

需要专用驱动的场景就四个字：改私有寄存器。RTL8211F 私有的那几处：

  1. RGMII 收发延时（RGMII delay），不配只能靠 PCB 走线碰运气；
  2. TX 幅度/驱动强度（长线要调）；
  3. EEE（Energy Efficient Ethernet）开关，EEE 在这个平台上跟 delayline 打架，经常要关掉；
  4. LED 行为（链路灯、速率灯、收发闪）。

这些都在 realtek.c 里用 MDIO 扩展寄存器访问（写 0x1f 选页，再读写目标页内的偏移）完成。具体寄存器编号素材未给出，本篇不臆造。

11.3 注册与匹配的时序 #

5.10 上的顺序：

text
MAC 驱动 probe
  └─ devm_mdiobus_alloc + of_mdiobus_register()
       └─ MDIO 扫地址 0~31，逐个读 PHYSID1/PHYSID2
            └─ 读到的 ID 建 phy_device（PHY 就此成为一个设备）
                 └─ phy_device 与 phy_driver 按 ID 匹配 → drv->probe / config_init
MAC 驱动拿 phydev
  └─ phy_connect()（老接口）或 phy_attach_direct()（新接口）
       └─ phy_start() 起状态机，每 1 秒轮询一次 read_status
            └─ 状态变化 → phydev->adjust_link 回调 → netif_carrier_on/off
  └─ phy_start_aneg() 触发自协商

phy_connect() 和 phy_attach_direct() 的差别：前者是 MAC 侧用的老接口，接受 net_device 和 adjust_link 回调，内部转调 phy_attach_direct()；后者更底层，接受 struct device *。5.10 的 stmmac 走 phy_connect_direct() / phy_connect() 那一套。6.9 之后 phy_attach_direct() 的签名变了（去掉了 if_link_update 参数），这篇不涉及。

十二、设备树里的以太网节点 #

DM9000 用板级描述，RK3588 用设备树。两套东西的语义是一样的：把资源（地址、中断、时钟、复位脚）告诉驱动。

12.1 RK3588 的 GMAC 节点结构 #

DTS 的官方参考是 Documentation/devicetree/bindings/net/rockchip-dwmac.yaml。一个典型的板级覆盖长这样（注意这段来自 rk3288 的示例配置，字段名与 RK3588 一致，但地址、时钟名不同）：

dts
gmac: ethernet@ff290000 {
	compatible = "rockchip,rk3288-gmac";
	reg = <0xff290000 0x10000>;
	interrupts = <GIC_SPI 27 IRQ_TYPE_LEVEL_HIGH>;
	interrupt-names = "macirq";
	rockchip,grf = <&grf>;
	clocks = <&cru SCLK_MAC>,
        <&cru SCLK_MAC_RX>, <&cru SCLK_MAC_TX>,
        <&cru SCLK_MACREF>, <&cru SCLK_MACREF_OUT>,
        <&cru ACLK_GMAC>, <&cru PCLK_GMAC>;
	clock-names = "stmmaceth",
        "mac_clk_rx", "mac_clk_tx",
        "clk_mac_ref", "clk_mac_refout",
        "aclk_mac", "pclk_mac";
	phy-mode = "rgmii";
	pinctrl-names = "default";
	pinctrl-0 = <&rgmii_pins /*&rmii_pins*/>;

	clock_in_out = "input";
	snps,reset-gpio = <&gpio4 7 0>;
	snps,reset-active-low;
	snps,reset-delays-us = <0 10000 1000000>;

	assigned-clocks = <&cru SCLK_MAC>;
	assigned-clock-parents = <&ext_gmac>;
	tx_delay = <0x30>;
	rx_delay = <0x10>;

	status = "ok";
};

逐字段过一遍：

属性 作用 坑
compatible 匹配驱动 取值随平台变：rockchip,rk3288-gmac、rockchip,rk3528-gmac、rockchip,rk3562-gmac、rockchip,rk3568-gmac、rockchip,rk3588-gmac。RK3588 上是 "rockchip,rk3588-gmac", "snps,dwmac-4.20a" 两级
reg 寄存器起始地址与长度 0xff290000 起点、0x10000（64KB）长度。RK3588 上是 64 位地址，写成 <0x0 0xfe1b0000 0x0 0x10000>
interrupts 中断号与触发方式 GIC_SPI 是共享外设中断，由 GIC 管；IRQ_TYPE_LEVEL_HIGH 是电平高有效
interrupt-names 给每个中断起名 MAC 主体中断必须叫 macirq，驱动按名字取；第二个是 eth_wake_irq
rockchip,grf 引用 GRF 寄存器文件 控制信号在外设寄存器之外，得通过 GRF 中转
clocks/clock-names 时钟源与名字 至少 5 个，最多 8 个；clock-names 顺序必须与 clocks 一一对应
phy-mode 接口类型 只有两个值：rmii 和 rgmii
pinctrl-0 引脚复用 RGMII 和 RMII 的 pinctrl 组不同，二选一。输出时钟的脚驱动强度要单独配（RMII 的 ref_clock 输出时驱动强度要更大）
clock_in_out 时钟方向 RGMII 的 125MHz 主时钟由 PHY 提供，不是 SoC 的 PLL，所以填 "input"；RMII 看具体方案
snps,reset-gpio PHY 硬件复位脚 接错或者漏接，PHY 起不来
snps,reset-active-low 复位有效电平 低有效写这个；高有效写 snps,reset-active-high
snps,reset-delays-us 复位三段时序 低有效时三个值分别是「拉高时间、拉低时间、再拉高后的等待时间」，单位 us。<0 10000 1000000> = 拉低 10ms、释放后等 1s
tx_delay/rx_delay RGMII 时序补偿 取值 0~0x7F（0~127），默认 0x30/0x10，单位是 0.1ns 级的 delayline 刻度（具体刻度与 PHY/SoC 相关，未验证）
phy-supply PHY 电源 PHY 常供电可以不配；否则指一个 regulator

compatible、clocks、clock-names 三个属性是必填的，少一个 probe 就失败。

		snps,mtl-tx-config = <&gmac0_mtl_tx_setup>;
		status = "disabled";

		mdio0: mdio {
				compatible = "snps,dwmac-mdio";
				#address-cells = <0x1>;
				#size-cells = <0x0>;
		};

		gmac0_stmmac_axi_setup: stmmac-axi-config {
				snps,wr_osr_lmt = <4>;
				snps,rd_osr_lmt = <8>;
				snps,blen = <0 0 0 0 16 8 4>;
		};

		gmac0_mtl_rx_setup: rx-queues-config {
				snps,rx-queues-to-use = <1>;
				queue0 {};
		};

		gmac0_mtl_tx_setup: tx-queues-config {
				snps,tx-queues-to-use = <1>;
				queue0 {};
		};
};

gmac1 只在地址和中断号上不同：ethernet@fe1c0000、GIC_SPI 234 与 GIC_SPI 233、SRST_A_GMAC1、CLK_GMAC1_PTP_REF。其余字段逐字相同。

几个字段值单独提：

  • dmaw-4.20a 这个版本号说明 RK3588 的 GMAC 是 Synopsys DesignWare MAC 4.20a 版本。4.20a 与 dwxgmac（XGMAC，万兆）不是一回事，stmmac 驱动里用两套代码路径。
  • snps,axi-config 里的 snps,blen = <0 0 0 0 16 8 4> 是 AXI burst 长度，依次对应 4/8/16/32/64/128/256 拍的使能位，0 表示不使能。这一串填错不影响功能但影响峰值带宽。
  • snps,wr_osr_lmt = <4>/snps,rd_osr_lmt = <8> 是 AXI outstanding 请求上限，太小跑不满千兆。
  • mdio0: mdio 子节点是 PHY 的容器，#address-cells = <0x1>、#size-cells = <0x0> 是规定值——子节点只写 reg = <地址> 不带长度。

12.3 PHY 子节点与 LED #

PHY 本身在 mdio 下面挂一个节点：

dts
phy: phy@0 {
	compatible = "ethernet-phy-id1234.d400", "ethernet-phy-ieee802.3-c22";
	reg = <0>;
	clocks = <&cru SCLK_MAC2PHY_OUT>;
	resets = <&cru SRST_MACPHY>;
	pinctrl-names = "default";
	pinctrl-0 = <&fephyled_rxm1 &fephyled_linkm1>;
	phy-is-integrated;
};

这段是 RK3228/RK3328 内置 macphy 的写法，外挂 RTL8211F 要照 Realtek 的 datasheet 改。值得学的是 compatible 的两种写法：

写法 含义
ethernet-phy-ieee802.3-c22 通用，靠运行时读 PHYSID1/2 匹配驱动
ethernet-phy-idXXXX.YYYY 硬指定 ID，XXXX 是 PHYSID1，YYYY 是 PHYSID2

ethernet-phy-id1234.d400 里的 1234 和 d400 就是 ID 高 16 位和低 16 位。硬指定 ID 的用途是：某些 PHY 的 ID 读不出来（MDIO 时序不对、上电顺序不对），先靠 DT 把驱动绑上，再看具体问题。

phy-is-integrated 是个非标准的 Rockchip 私有属性，表示这颗 PHY 是 SoC 内置的，不需要外部复位脚。外挂 PHY 不写这个。

pinctrl-0 里那两个 fephyled_* 是 LED 脚的复用，PHY 的 LED 引脚接到 SoC 上做软件控制时才需要。

十三、链路状态检测 #

两条线的链路检测机制完全不同。

13.1 DM9000：轮询加中断两条腿 #

DM9000E 没有链路变化中断，只能靠定时轮询。驱动在 probe 里就 INIT_DELAYED_WORK(&db->phy_poll, dm9000_poll_work)，dm9000_open() 里 schedule_delayed_work(&db->phy_poll, 1) 起第一轮，之后由 dm9000_poll_work() 自己反复重排。

DM9000A/B 有 IMR_LNKCHNG，链路一变就进中断，中断里 schedule_delayed_work(&db->phy_poll, 1) 立刻触发一次轮询。所以：

text
DM9000E:  纯定时轮询（间隔由驱动常量决定） → 链路变化最慢一个轮询周期才被发现
DM9000A/B: 链路中断 + 轮询兜底           → 变化几乎立刻上报

轮询的活儿是读 NSR 里的链路状态位（NSR_LINKST，未在素材中给出确切位号，按 datasheet 的 NSR 章节核对），再调 netif_carrier_on() / netif_carrier_off()。carrier 状态是协议栈判断「这根线能不能发」的依据，iproute2 的 ip link 里 NO-CARRIER 就是从这个状态来的。

CONFIG_DM9000_FORCE_SIMPLE_PHY_POLL 这个编译选项会把 DM9000_PLATF_SIMPLE_PHY 强推进 db->flags，作用是把轮询简化成「只读链路位」，不去碰 mii_check_media() 那一套完整的 MII 状态机。板子的 PHY 是外部的、行为不规范时用这个绕开。

13.2 RTL8211F：phylib 状态机 #

RK3588 这条线的链路检测是 PHY 框架统一做的，MAC 驱动一行不用写：

text
phy_start()
  └─ phy_start_machine(phydev)
       └─ 定时器每 1 秒跑一次 phy_state_machine()
            ├─ phy_read_status() → drv->read_status()（RTL8211F 就是读 BMSR/STAT1000）
            ├─ 状态从 PHY_UP 变 PHY_RUNNING → netif_carrier_on()
            ├─ 状态从 PHY_RUNNING 变 PHY_NOLINK → netif_carrier_off()
            └─ 状态变化时调 phydev->adjust_link(ndev)

phy_state_machine() 的状态有好几个：PHY_DOWN、PHY_READY、PHY_HALTED、PHY_UP、PHY_RUNNING、PHY_NOLINK、PHY_CHANGELINK、PHY_RESUMING。运行中主要在 PHY_UP、PHY_RUNNING、PHY_NOLINK 之间跳。

adjust_link 是 MAC 侧的回调，拿到新的 phydev->speed/duplex 之后要配 MAC 自己的寄存器（比如 stmmac 里改 MAC_10_100_CTRL 的速率位）。这是最容易漏的一步：PHY 自己知道跑 100M 了，MAC 还以为在 1000M，结果就是「link 起来了但一个包都不通」。RTL8211F 的报告没错，错的是 MAC 没跟上。

调试时看这两个地方：

bash
cat /sys/class/net/eth0/carrier      # 1 = up，0 = down
cat /sys/class/net/eth0/speed        # 当前速率，单位 Mbps
cat /sys/class/net/eth0/duplex       # full / half
cat /sys/class/net/eth0/operstate    # up / down / unknown

13.3 两种检测思路的对照 #

维度 DM9000 RTL8211F
谁管链路 驱动自己 PHY 框架（phylib）
检测手段 定时轮询 NSR，A/B 型加中断 1 秒一次状态机读 BMSR
上报路径 直接调 netif_carrier_on() adjust_link → MAC 驱动 → netif_carrier_on()
驱动要写的代码 dm9000_poll_work() + 中断分支 read_status 一个回调
漏了会怎样 carrier 不动，NO-CARRIER MAC 速率没更新，link 通但发不出包

十四、ethtool 与调试手段 #

14.1 ethtool 命令 #

bash
ethtool eth0                    # 速率/双工/链路/协商状态一览
ethtool -i eth0                 # 驱动名、版本、固件、总线信息
ethtool -S eth0                 # 驱动私有统计（有用时才有输出）
ethtool -d eth0                 # dump 寄存器（需要驱动实现 get_regs）
ethtool -s eth0 speed 100 duplex full autoneg off    # 强制模式
ethtool -A eth0 autoneg off rx off tx off            # 关流控

ethtool eth0 的输出里最该看三行：Link detected: yes|no、Speed: 1000Mb/s|100Mb/s|10Mb/s、Duplex: Full|Half。这三个值和你的预期不符，先怀疑自协商，不要怀疑驱动。

DM9000 的 dm9000_ethtool_ops 提供 get_drvinfo、get_settings/set_settings、get_link，ndo_do_ioctl 里的 dm9000_ioctl() 处理 SIOCGMIIPHY/SIOCGMIIREG/SIOCSMIIREG 三个老命令——那是 mii-tool 走的路径，ethtool 走的是另一个。

14.2 DM9000 侧的调试观察点 #

bash
cat /proc/interrupts | grep eth0      # 中断计数，发包/收包都在涨
cat /proc/net/dev                     # 收发计数与错误计数
cat /sys/class/net/eth0/statistics/tx_errors
cat /sys/class/net/eth0/statistics/rx_crc_errors
dmesg | grep -i dm9000                # probe 那行 MAC 与 ID

/proc/interrupts 里中断号是 0 或者不涨，说明 request_irq 没成功、或者中断触发方式配错（IORESOURCE_IRQ_HIGHEDGE 和高电平触发作对比）。tx_errors 涨而 tx_packets 也涨，说明包发出去但超时过，回去看 dB->tx_pkt_cnt 有没有卡在 2。

dm9000_dbg() 的调试分级由 db->msg_enable 控制，默认 NETIF_MSG_LINK。要看更细的收发日志，在 probe 之后手工把 msg_enable 调到 NETIF_MSG_RX_STATUS | NETIF_MSG_TX_DONE | NETIF_MSG_INTR（需要加 sysfs 接口或改代码）。

14.3 RK3588 侧：phy_registers 直接读写 #

Rockchip 补丁给 MDIO 设备加了 phy_registers 属性文件，5.10 上可以直接读写 PHY 寄存器：

bash
# 往 Reg0 写 0xabcd
echo 0x00 0xabcd > /sys/bus/mdio_bus/devices/stmmac-0:00/phy_registers

# 读 0~31 全部寄存器
cat /sys/bus/mdio_bus/devices/stmmac-0:00/phy_registers

stmmac-0:00 这个目录名拆开看：stmmac-0 是 MAC 控制器（mdio_bus 的名字），00 是 PHY 地址。这个接口比 ethtool -d 可靠，因为不依赖驱动实现 get_regs。注意它是 Rockchip 私有补丁，主线内核没有这个文件。

14.4 时钟与引脚的前置检查 #

GMAC 起不来，先看时钟。开机 log 里出现 DMA engine initialization failed，基本可以确定是 GMAC 的工作时钟出了问题：

  1. IOMUX 错：时钟脚的寄存器值不对，先用 io -4 读一下 pinctrl 映射后的复用值；
  2. 时钟方向与硬件不匹配：clock_in_out 写了 "input" 但硬件上是 SoC 往 PHY 输出时钟，两层都在等对方，永远等不到；
  3. clock tree 与 CRU 寄存器：cat /sys/kernel/debug/clk/clk_summary 看 CLK_GMAC_125M 的频率和 enable 计数，为 0 就是没开。

用示波器量时钟脚：有没有波形、频率对不对（RGMII 是 125MHz）、幅度够不够（VCCIO3 域的电压决定摆幅）。

14.5 RGMII delayline #

tx_delay/rx_delay 这两个值不是随便填的。RGMII 的时序余量很窄：125MHz 下 8ns 一个周期，建立/保持窗口只有几百 ps，PCB 走线长度差、PHY 内部延时、SoC 内部延时叠加起来很容易吃掉全部余量。

Rockchip 给的做法是扫：把 tx_delay 从 0 到 0x7F 逐个试，每换一个值跑一次 ping -f 或者 iperf3，记下能跑满的和丢包的，取能跑满的那一段的中间值。rx_delay 同理。官方文档是《Rockchip_Developer_Guide_Linux_GMAC_RGMII_Delayline_CN.pdf》。

tx_delay 和 rx_delay 都给不了足够的窗口时，说明硬件有问题：PCB 等长没做、变压器型号不对、PHY 的 strap 配错。软件扫不出来的硬件问题，别在 dts 里瞎调。

14.6 回环测试 #

回环分两种：MAC 回环和 PHY 回环。MAC 回环把 MAC 的 TX 直接接回 RX，不走 PHY，测的是 MAC 与 DMA；PHY 回环在 PHY 内部把 TX 接回 RX，测的是 PHY 与变压器与线。两个回环都通而外网不通，问题在变压器或 RJ45 那一侧。具体节点名与使能方法在《Rockchip_Developer_Guide_Linux_GMAC_RGMII_Delayline_CN.pdf》的 mac_lb/phy_lb 节点说明里。

14.7 硬件测量的分工 #

链路不通时，先分清是 TX 还是 RX，别一头乱撞：

测什么 在哪一端 说明
GMAC 的 TXC/TXD SoC 侧 有波形说明 MAC 在发，没波形说明 MAC 卡住了
PHY 的 TXP/TXN 变压器前 有波形说明 PHY 收到 MAC 的数据并转出来了
双绞线上的差分 RJ45 侧 有波形说明变压器和匹配网络没问题
PHY 的 RXP/RXN 变压器后 对端在发、这里没有，问题在变压器或 RJ45
GMAC 的 RXC/RXD SoC 侧 有波形说明 PHY 收进来并转给 MAC 了
MDC/MDIO PHY 侧 探 PHY 的时候必须有，MDC 频率要小于 2.5MHz

那个「if (ret == 0)」的判断值得单独说：素材原文写的是

c

        if (inv_mac_addr)
                dev_warn(...);
        ...
}

register_netdev 返回 0 是成功。if (ret == 0) 进去打印的是「设备已经注册好了」的信息，注释「失败」是错的。更严重的是函数末尾无条件 return 0，注册失败也返回成功——这是素材原样，真实内核源码里这一段是 if (ret) goto out; 的形态。移植老代码时这一处必须核对。

No PHY found 的五条排查顺序：

  1. MDC/MDIO IOMUX：检查复用寄存器值是否正确，这两个脚是不是配成了 MDIO 功能；
  2. PHY 供电：量 PHY 的 VDDIO 和 VDDA，phy-supply 配了但没有 regulator 拿不到电是常见的；
  3. Reset IO 配置：snps,reset-gpio 写的那个脚，是不是真的接在 PHY 的复位脚上；
  4. Reset 时序：snps,reset-delays-us 三个值不满足 PHY datasheet 的要求。不同 PHY 要求不同，RTL8211F 的具体最小复位宽度以 datasheet 为准；
  5. MDIO/MDC 波形：MDC 是类似 I2C 的开漏输出，频率要小于 2.5MHz，测量波形看有没有下拉不足导致的高电平塌陷。

有一个排除法的技巧很好用：把 MDC/MDIO 从主控上断开，让 PHY 直接和一台 PC 的网口连，看 PC 端有没有同样的症状。PC 端正常，问题在软件/驱动；PC 端也不正常，问题在硬件（PHY、变压器、RJ45、供电）。

RX 不通的排查顺序，反过来：

  • 看 GMAC 的 RXC/RXD 有没有波形，有波形说明 PHY 转出来了；
  • 没有波形就看 PHY 的 RXP/RXN，有波形说明变压器没问题；
  • 再看 RXD 的 iomux、RXC 时钟、RGMII 的 rx_delay。

TX packets 在涨但通信不正常，另外两个原因值得先查：RMII 模式下 MAC 和 PHY 的参考时钟不是同一个源；PHY 的 phy-mode 配错（硬件按 RGMII 连的，dts 写了 rmii，或者硬件按 MII 连的，dts 写了 rgmii）。
