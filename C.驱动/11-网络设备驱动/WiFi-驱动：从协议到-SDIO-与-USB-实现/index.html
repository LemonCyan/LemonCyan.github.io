一、WiFi 与以太网的差别 #

先把名字理清。WiFi 英文全称 WIreless-FIdelity，中文叫无线保真，是 Wi-Fi 联盟持有的一个商标，用来保证基于 IEEE 802.11 的产品之间能互通。WLAN 是 Wireless Local Area Networks，无线局域网。两者经常被人混着用，其实 WiFi 只是实现 WLAN 的技术之一，蓝牙、WiMax 也都算 WLAN 的实现路线。

对写驱动的人来说，有意义的是这句话：以太网卡跑 802.3，无线网卡跑 802.11，网络层以上的部分基本一样，网络层以下的整段不一样。

1.1 六个硬差别 #

维度 有线（802.3） 无线（802.11）
建链 插上线就能发帧 必须先扫描、认证、关联，才有资格发数据帧
双工 可以全双工 半双工，同一时刻只能收或发
差错率 极低，链路层几乎不重传 高，必须在 LLC 之下自己加确认与重传
抓包 要接线或端口镜像 空口谁都能收，天然不安全
功耗 小 大，射频收发是电池的敌人
吞吐 高 低，802.11n 标称可以到 600Mbps

半双工这一条直接决定了 802.11 不能照抄以太网的 CSMA/CD。CSMA/CD 要求发送方一边发一边听，靠检测冲突来退避。无线做不到：自己发出去的信号比远处站点传来的信号强几个数量级，本地根本听不出冲突，这就是所谓的 Near/Far 现象。802.11 的答案是 CSMA/CA——用避免代替检测，靠 ACK 帧和随机退避来间接判断有没有撞上。

差错率高带来的后果是驱动侧多出一整套机制：聚合、块确认、速率自适应、重传计数。这些不是「优化项」，是无线链路能用的前提。

1.2 802.11 里四个必须认识的实体 #

  • 工作站 STA（Station）：带无线接入能力的设备，笔记本、手机、模组都算。
  • 接入点 AP（Access Point）：做无线到有线的桥接，帧必须经过它转换才能进别的网络。
  • 无线介质 WM（Wireless Medium）：帧在空口上传输的物理途径，802.11 定义的物理层不止一种。
  • 传输系统 DS（Distribution System）：AP 之间转发帧的骨干网，也叫 backbone。它是个逻辑元件，实际产品里由桥接引擎加传输介质组成。

802.11 的数据链路层分 LLC 和 MAC 两层。LLC 与 802.2 完全相同，MAC 用 48 位地址，这套设计让无线和有线之间的桥接变得方便——驱动里那份「802.3 头 ↔ 802.11 头」的转换之所以成立，根子在这里。

1.3 协议族速览 #

802.11 基本规格覆盖 MAC 加两种物理层：跳频展频 FHSS、直接序列展频 DSSS。802.11a 的物理层建立于 OFDM（正交频分多工）之上。802.11 把 PHY 又切成两块：PLCP（物理层收敛程序）负责把 MAC 帧映射到传输介质，PMD（物理介质相关子层）负责真正把帧发出去。

标准 频段 标称速率 物理层要点
802.11 原始 2.4GHz 1 / 2Mbit/s FHSS 与 DSSS
802.11b 2.4GHz 11Mbit/s DSSS，14 个 22MHz 宽信道
802.11a 5GHz 54Mbit/s OFDM
802.11g 2.4GHz 54Mbit/s OFDM，向下兼容 b
802.11n 2.4 / 5GHz 600Mbit/s（4 流） MIMO、信道绑定、帧聚合

这里有个常见的误解要拆掉：802.11b 常被人直接叫「Wi-Fi」，其实 Wi-Fi 是 WLANA 的商标，只保证贴了这个标的商品之间能互通，跟标准本身没关系。

1.4 三个名字的三层 #

WLAN、WiFi、802.11 这三个词天天混着用，其实分属三层。

名字 是什么 谁定的 层级
WLAN Wireless Local Area Networks，无线局域网的统称 业界通称，不是某家的标准 网络形态
WiFi Wi-Fi 联盟持有的商标，一种互通性认证 Wi-Fi Alliance 认证商标
802.11 IEEE 的无线局域网技术标准，定 PHY 与 MAC IEEE 技术规范

Wi-Fi 联盟 1999 年成立，原名 Wireless Ethernet Compatibility Alliance（WECA），2002 年 10 月改成现在的名字。它做的事很简单：拿厂商的设备来测，通过了就准你贴这个标。贴了标的设备之间能互通，这是商标的全部含义，和标准本身的细节无关。

覆盖范围上的差别常被拿来当「谁更强」的证据，其实跟协议无关：WiFi 的覆盖在 90 米量级（300 英尺），WLAN 加上定向天线能拉到公里级（5km）。差的是功率和天线，不是 CSMA/CA。

还有一个历史包袱：WiFi 早期主要落在 802.11b 上，于是「WiFi 就是 802.11b」的说法传了下来，到今天还有人这么用。你写驱动时对上的是 802.11 标准，商标管不到寄存器。

1.5 无线网卡与它的接口形态 #

无线网卡就是不做有线连接、靠无线电波收发数据的网络设备。它本身只是个信号收发器，能不能上互联网取决于它连上的那个无线网络有没有出口。

接口 形态 现状
PCMCIA 早期笔记本扩展卡 已退场
PCI 台式机内置卡 少见
MiniPCI / MiniPCIe 笔记本内置 老设备上还能见到
USB 外置网卡、模组 主流
CF / SD / SDIO 嵌入式与手持设备 主流，后面几章讲的就是它

手机里的 WiFi 是焊在板上的模块，不是插卡。开热点的时候它扮演 AP，把蜂窝网转成 WiFi 信号发出去；关掉热点它扮 STA，去连别的 AP。同一颗射频干不了两件事，单射频并发做不到，所以手机上开了热点，WiFi 上网那一栏多半会灰掉。

二、802.11 的频段与信道 #

2.4G 这一段（802.11b/g）的账很干净：频率范围 2.400 到 2.4835GHz，共 83.5MHz 带宽，切 14 个子信道，每个子信道宽 22MHz，相邻信道中心频点间隔 5MHz。

22MHz 宽、5MHz 间隔，这两个数字一摆，重叠就不可避免：信道 1 和 2、3、4、5 都有频率交叠。真正互不干扰的只有 1、6、11 三组（美国区）。这也是为什么你翻开任何一个拥挤小区的扫描列表，2.4G 上永远是一片红。

信道 中心频率 备注
1 2.412GHz 2.4G 三个不重叠信道之一
6 2.437GHz 同上
11 2.462GHz 同上
14 2.484GHz 仅日本允许，与 13 之外的区域法规相关

中心频率这块只列到原文给得出的四个点，其余信道的具体频点在原文没有逐条给出，此处不补。

驱动里频段表现为两个概念：band（IEEE80211_BAND_2GHZ / IEEE80211_BAND_5GHZ）和 channel。厂商驱动（WEXT 时代）用 CHANNEL_WIDTH_20、CENTER_CH_* 描述带宽与中心频点；mac80211 驱动则在 ieee80211_supported_band 里挂一张 ieee80211_channel 表，表里每一项的 hw_value 是写给硬件看的信道号。

寄存器层面要记住一件事：很多 SDIO/USB WiFi 芯片的信道号不是 1 到 14，而是内部映射过的枚举值。你在 ieee80211_channel.hw_value 里填错一位，表现就是「能扫描到 AP，却怎么都关联不上」。这类问题在《RK3399 WiFi AP6356 驱动》里出现过一次，排查花的时间比改代码多得多。

三、802.11 的帧类型与结构 #

所有 802.11 帧共用 24 字节的 MAC 头（带 QoS 的加 2 字节，带 HT Control 再加 4 字节）。控制在 Frame Control 字段里：2 字节，按位切。

3.1 Frame Control 字段 #

位域 名称 作用
bit 0-1 Protocol Version 恒为 0，留着以后改
bit 2-3 Type 00 管理帧 / 01 控制帧 / 10 数据帧 / 11 扩展
bit 4-7 Subtype 细分类别，见下表
bit 8 ToDS 发给 DS
bit 9 FromDS 从 DS 来
bit 10 More Frag 后面还有分片
bit 11 Retry 这是重传帧
bit 12 Pwr Mgmt 发完这帧进省电
bit 13 More Data 还有数据要给你
bit 14 Protected Frame 帧体已加密
bit 15 Order 严格顺序

ToDS / FromDS 这两个位是整张地址解释表的钥匙。四地址字段的语义完全由这两位决定，这也是驱动里 ieee80211_hdr 的 addr1 到 addr4 为什么不能想当然地当源/目的地址用的原因。

3.2 三大类帧 #

类别 Type 典型子类型 干什么
管理帧 00 Beacon、Probe Request/Response、Authentication、Association Request/Response、Deauthentication、Disassociation 建链、维持、拆链
控制帧 01 RTS、CTS、ACK、PS-Poll、BlockAck Request/BlockAck 抢信道、确认、块确认
数据帧 10 Data、Data+CF-Ack、Null、QoS Data、QoS Null 真正运数据

管理帧管「我们能不能连上」，控制帧管「现在谁能说话」，数据帧管「把包送过去」。驱动工程师的大部分调试都在第一类上——连不上，八成是管理帧交互出了问题。

3.3 三种帧头 #

管理帧头（24 字节）

字段 长度 说明
Frame Control 2 见上
Duration 2 占信道时长，微秒
DA 6 目的地址
SA 6 源地址
BSSID 6 所属 BSS 的标识
Sequence Control 2 4 位分片号 + 12 位序列号
Frame Body 变长 一组 Information Element
FCS 4 CRC32

Beacon 的 Frame Body 就是一串 IE：SSID(0)、Supported Rates(1)、DS Parameter Set(3)、TIM(5)、RSN(48)、HT Capabilities(45) 等。mac80211 驱动只负责上报 IE 原始字节，解析在 cfg80211 和用户态做——这条分工线值得记住。

控制帧头（10 字节）

字段 长度 说明
Frame Control 2 只有类型和子类型有意义
Duration 2 预约的信道时长
RA 6 接收方地址
FCS 4 —

RTS 和 PS-Poll 还多带一个 TA 字段（6 字节）。控制帧没有 Frame Body，所以它是最短的一类。数据帧头 24 字节起步：Frame Control、Duration、Address 1/2/3、Sequence Control；存在 Address 4（仅 WDS，ToDS=1 且 FromDS=1）时到 30 字节；QoS Control 再加 2 字节，Order 位置 1 的 HT 帧再加 4 字节 HT Control。

地址解释规则一句话记法：ToDS=0/FromDS=0 是 IBSS，Addr1=DA、Addr2=SA、Addr3=BSSID；ToDS=1/FromDS=0 是 STA 发给 AP，Addr1=BSSID、Addr2=SA、Addr3=DA；ToDS=0/FromDS=1 是 AP 发给 STA，Addr1=DA、Addr2=BSSID、Addr3=SA；ToDS=1/FromDS=1 是 WDS，四个地址全用上。

这套地址映射在驱动里的具体体现是发送路径上的 pkt_attrib 填充：ra、ta、bssid、seq_ctrl 一项项算好，再拷进硬件描述符。填错哪一项，症状都是「抓包有帧、对面不回」——DA 不对，AP 直接丢。

3.4 单播必有 ACK，广播没有 #

这条规则贯穿整个 802.11，抓包先认它。

帧的地址性质 要不要 ACK 例子
单播 要，收到后立刻回 ACK Data、Authentication、Association、Probe Response
组播 不要 组播数据帧
广播 不要 Beacon、Probe Request
ACK 本身 不要再被确认 ACK

判断一个地址是单播还是广播，看第一个字节的最低位，不是看整个地址大小：首位为 0 是单播，为 1 是组播，前两位都为 1 是广播。a8:27:26:...:b7 的第一个字节 a8 是 10101000，最低位 0，所以是单播地址。

ACK 帧只有接收地址（RA），没有源地址，也没有序列号。发出去的单播帧和收回来的 ACK 在协议上是一个原子动作，算一次成功的通信。抓包看到「单播帧后面没有紧跟 ACK」，就是这一帧没送达，重传计数会加一。

建立关联的过程最能说明这套规则，每一步都配着 ACK：

text
AP  --> Beacon (broadcast)          /* 不要 ACK */
STA --> Probe Request (broadcast)   /* 不要 ACK */
AP  --> Probe Response              /* 单播 */
STA --> ACK
STA --> Authentication Request      /* 单播 */
AP  --> ACK
AP  --> Authentication Response     /* 单播 */
STA --> ACK
STA --> Association Request
AP  --> ACK
AP  --> Association Response
STA --> ACK

3.5 Duration 与 NAV：一次通信的原子性 #

Duration 是 802.11 帧头里的一个 2 字节字段，单位微秒。它说的是「这个信道我还要占用多久」。

收到这一帧的站点都会把 Duration 的值装进自己的 NAV（Network Allocation Vector，网络分配向量）。NAV 是个倒计时器，倒计时没到零之前，这些站点认为自己不是空闲的，不去抢信道。于是从第一帧到最后那个 ACK，中间没人插嘴，整段通信成了原子的。

后续每一帧都会视情况把 Duration 续上，因为后面还剩多少时间要传，发送方算得出来。这就是为什么一个数据帧后面跟着的 ACK，是 SIFS 那样的极短间隔就发出来了——中间的竞争窗口被 Duration 提前抹平了。

驱动侧这一项落在发送描述符的 duration 字段里。填 0 或者填错，现象是同一 BSS 里别人总在你传大包时插进来，吞吐上不去，丢包率上升。

四、SSID、BSSID 与连接过程 #

4.1 从 BSS 到 ESS #

BSS（Basic Service Set）是 802.11 LAN 的基本组成模块，一组能互相通信的 STA 构成一个 BSS。站移出覆盖范围，就不能再和 BSS 内其他成员通信。多个 BSS 拼起来是 ESS（Extended Service Set），一个 ESS 内部的 STA 可以互通，连接各 BSS 的组件就是 DS。

概念 作用域 本质
SSID ESS 网络名，如 TP_Link_1201
BSSID BSS 实际上就是 AP 的 MAC 地址
ESSID ESS 与 SSID 同义，WEXT 时代习惯用这个词

同一个 AP 内 BSSID 与 SSID 一一映射。一个 AP 支持多个 SSID（多 SSID 虚拟 AP）时，会给每个 SSID 分配不同的 BSSID。这条特性在驱动里对应多个 netdev 或多个 ieee80211_vif，取决于 mac80211 的接口组合能力。

4.2 三个阶段 #

STA 从上电到能发数据帧，要过三道关：

  1. 扫描 SCAN：主动扫描，往每个信道发 Probe Request 等 Probe Response；被动扫描，逐个信道蹲 Beacon，慢但省电。
  2. 认证 Authentication：发 Authentication 帧，AP 回 Authentication 帧。这是 802.11 层的链路级认证，跟 WPA2 的密码认证不是一回事。
  3. 关联 Association：STA 发 Association Request，带上支持的速率、能力信息和（加密网络的）RSN IE，AP 回 Association Response 并分配 AID。

三步走完才能发数据帧。关联之后还有一个可选的 4 次握手，那是加密层的事。

4.3 一次完整连接用到的帧序 #

text
STA                                  AP
 |------ Probe Request (broadcast) -->|
 |<----- Probe Response --------------|
 |------ Authentication Request ----->|
 |<----- Authentication Response -----|
 |------ Association Request -------->|
 |<----- Association Response --------|   ← 此处拿到 AID
 |====== 4-Way Handshake (EAPOL) =====|   ← 见第五章
 |<----- Data -------------------------|

被动扫描时第一步换成蹲 Beacon。mac80211 里这一整套由 hw_scan（或 sw_scan_start/sw_scan_complete）、auth、assoc、deauth、disassoc 分散承包。ieee80211_ops 这一族回调名字在 2.6.35 到 3.x 基本没变，但 hw_scan 的完成通知在 3.x 后期从 ieee80211_scan_completed 的 aborted 参数改成了 struct cfg80211_scan_info，未验证是哪个版本切的，动老驱动时对着自己树里的 include/net/mac80211.h 查。

4.4 漫游与 BSSID 绑定 #

漫游是为了扩覆盖：多个 AP 拉同一个 SSID/ESSID，各自覆盖一块，STA 按信号强弱换 AP。这个动作在 mac80211 里是 ieee80211_ops 的事，在厂商 fullmac 驱动里是一段厂商自己写的「重连」逻辑。

BSSID 绑定是另一种需求：802.11 允许不同网络用同一个 SSID，但 BSSID 必须唯一。有人会架一台假 AP 广播同样的 SSID，把 STA 骗过去。驱动里记下目标 BSSID、关联时只接受这一个 BSSID 的响应，就能挡掉这类钓鱼。这条在嵌入式模组的 AT/私有命令里是常见选项。

五、加密与认证：WEP、WPA、WPA2 #

名称 标准 加密算法 完整性校验 密钥管理 现状
WEP 802.11 原始 RC4，静态密钥 CRC-32（ICV） 无 已破，不要再上
WPA 802.11i 草案 TKIP（RC4 + 每包换密钥） Michael MIC 4 次握手 + PSK/802.1X 兼容老硬件用
WPA2 802.11i CCMP（AES-CTR + CBC-MAC） AES CBC-MAC 4 次握手 + PSK/802.1X 主流
WPA3 802.11w/SAE CCMP / GCMP — SAE 原文未涉及，此处不展开

WEP 的问题在于 IV 太短、静态密钥人人一样，抓够包就能算出密钥。TKIP 是对 WEP 硬件的补救：把静态密钥升级成「每包一个密钥」，再加 Michael 做完整性。CCMP 才是干净的做法，直接改用 AES。

5.1 WPA2 四次握手 #

PSK 模式下，双方用 PMK = PBKDF2(口令, SSID, 4096, 32) 先各自算出 PMK，不传空口。之后：

text
STA                                        AP
 |<--------- EAPOL-Key 1 (ANonce) ----------|
 |   算 PTK = PRF(PMK, ANonce, SNonce, ...)  |
 |---------- EAPOL-Key 2 (SNonce + MIC) ---->|
 |<--------- EAPOL-Key 3 (GTK + MIC) --------|
 |---------- EAPOL-Key 4 (ACK) ------------->|

四步结束，双方各持 PTK。PTK 再切成三把：KCK 算 MIC、KEK 加密 GTK、TK 加密数据帧。空口上能抓到的只有 ANonce/SNonce 和 MIC，PMK 从不上线，这就是 PSK 能挡抓包的原因。

对驱动来说，握手过程基本是「透传」：EAPOL 帧原样交给 mac80211（ieee80211_rx 里的 ieee80211_rx_h_eapol 路径），用户态 wpa_supplicant 负责计算，再把密钥经 nl80211 的 NL80211_CMD_SET_KEY / NEW_KEY 下发到驱动。厂商 fullmac 驱动会把整套 EAPOL 塞进固件，主机侧只剩一条私有命令——这条路调试起来最痛，因为空口行为你完全看不见。

5.2 加密在驱动里的落点 #

  • 密钥表：硬件限量的 key slot（常见 4 组组密钥 + 若干 pairwise），驱动要管分配与回收。
  • set_key：mac80211 驱动实现 ieee80211_ops.set_key；fullmac 驱动实现 cfg80211_ops.add_key / del_key。
  • 硬件加解密标志：发送路径要按帧类型决定是否让硬件加 MIC/加密，接收路径要读硬件给的解密状态位。这一步做错，现象是「能连上、能 ping、传大包掉线」。

前面提到的那批模组普遍支持 WEP64/WEP128/TKIP/CCMP(AES)，以及 WEP / WPA-PSK / WPA2-PSK 三种模式。老模组的安全能力表就这么宽，别指望它支持 WPA3。

5.3 PSK 与 802.1X/EAP：谁在管认证 #

路由器配置页上那些 WPA-Personal / WPA-Enterprise 的字眼，讲的是同一套加密、不同的密钥来源。

叫法 正式名 密钥从哪来 要不要服务器 场景
WPA-Personal / WPA-PSK WPA-PSK 所有人共用一个口令，用它算 PMK 不要 家里、SOHO
WPA2-Personal / WPA2-PSK WPA2-PSK 同上，只是加密换成 CCMP 不要 主流家用
WPA-Enterprise WPA-802.1X/EAP 每人在服务器上单独认证，得各自的密钥 要，典型是 RADIUS 企业、校园
WPA2-Enterprise WPA2-802.1X/EAP 同上 要 企业主流

PSK 模式不碰认证服务器，口令就是全部凭据。这也是它省事的原因，也是它没法按人撤销权限的原因——有人离职，口令得全换。

Enterprise 模式里 802.1X 和 EAP 是两件事：802.1X 是「先认证再放行」的框架，EAP 是认证时对话的内容格式。RADIUS 服务器（也叫认证服务器）跑的就是这套：AP 当中间人，把 STA 的 EAP 报文原样往服务器上转，服务器决定放不放行，顺带下发密钥材料。

对驱动的影响就一点：EAP 报文是封装在 EAPOL 帧里过的，走数据帧通道，驱动只要保证 EAPOL 帧能收发、能过硬件加密旁路。剩下的全在用户态 supplicant 和服务器之间。你能抓到的只有空口那一段的 EAPOL 交换，服务器那一段是无线的盲区。

Wi-Fi 联盟定的商业化标准和 IEEE 定的技术标准是两层：WEP 是 1999 年 9 月 IEEE 802.11 标准的一部分，WPA 是联盟为了在中途补 WEP 的洞而先推的商业标准，指向的是 IEEE 802.11i；WPA2 就是 802.11i 正式落地后的版本。这也解释了为什么有些设备配置页写的是 AES 而不是 CCMP——同一件事，厂商按用户听得懂的词写。

一个细节容易踩：WEP 只工作在 802.11b/g 模式下，802.11n 草案不支持它。设备上只要选 WEP，射频就掉回 b/g，N 的性能一点吃不到。老设备图兼容选 WEP，代价是整个网络降级。

六、CSMA/CA：无线为什么不能冲突检测 #

前面提过一句 CSMA/CA，这里补全。先把两个容易混的概念分开：介质访问控制里说的「冲突」，是多个节点抢同一段空口；驱动里说的「冲突」，是多个执行单元抢同一个变量。两件事，别搅在一起。

6.1 从 CSMA 说起 #

有线以太网和无线 802.11 在底层都是广播式的：一个节点发出去，覆盖范围内所有人都收得到。所有人都能发，又只有一个介质，同时开口就是碰撞，碰撞了就得重来，速度掉下去。

协议给的解法是 CSMA，Carrier Sense Multiple Access，载波监听多路访问。拆开看：多路访问，大家都往这一个介质上发；载波监听，发之前先听一听有没有人在发。有线网在这个基础上加冲突检测，无线网加冲突避免。

名称 全称 介质 核心手段
CSMA/CD Carrier Sense Multiple Access / Collision Detection 有线（802.3） 边发边听，听到冲突就停
CSMA/CA Carrier Sense Multiple Access / Collision Avoidance 无线（802.11） 先听后发，发完等确认

两个词只差一个字母，区别却决定了整条链路的行为。名字像，机制不一样。

6.2 CSMA/CD：边发边听 #

以太网撞了怎么办？撞了能立刻知道，因为它在发的时候一直在听。

流程是这样：发之前先听，信道空闲就发；发的时候继续听，一旦监听到冲突，立刻停止发送，同时向线路上发一段阻塞信号，告诉其他节点「这里刚撞了」，然后自己随机等一段时间重发。如果监听的时候信道就是忙的，也随机等一段时间再听。试若干次都失败，就放弃，把失败报给上层。

撞了能立刻知道，靠的是电缆里的电压。发出去的信号是 3.3V 量级，如果同时收到别人的信号，电压叠加到 6V 左右，这个跳变非常明显，电路一测就出来。这是 CSMA/CD 成立的物理前提。

「随机等一段时间」不是真的随机，是二进制指数退避（BEB，Binary Exponential Backoff）：

  1. 定一个基本退避时间单位 2T，以太网上是 51.2us；
  2. 重传次数 N 换算成参数 K = min(N, 10)；
  3. 从 [0, 1, 2, ..., 2^K - 1] 这个整数集合里随机取一个数；
  4. 取出来的数乘以 2T，就是这次要等的时间。

重传次数越多，K 越大，可选的等待区间越宽，撞第二次的概率越低。10 次封顶，再往上区间不涨了——防止退避时间无限拉长。

6.3 无线为什么做不到边发边听 #

把上面那套搬到无线，第一处就卡住：发的时候听不到。

射频是半双工的，同一时刻只能干一件事。你在发，天线就在输出功率；自己发出去的信号在本地的强度，比远处站点传过来的信号高出几个数量级。远处的信号落在你耳朵里，早被自己这团噪声淹没了。想在发送时检测冲突，等于想在一台开着的音箱旁边听清隔壁的耳语。

这就是 Near/Far 现象：近端的强信号把远端的弱信号盖掉。有线网没有这个问题，因为电缆里的电压叠加是可测的物理量；空口没有这条线，只有一根共享的、随距离剧烈衰减的电磁场。

还有第二处问题：就算你检测到了冲突，也没有回退的机会。CSMA/CD 的「边发边听、撞了立刻停」要求在传输过程中实时判断。空口上等你察觉撞了，一帧早就发完了，暂停没有任何意义。

所以 802.11 换了个方向：不检测，只避免。先把会撞的情况尽量掐掉，撞了也没关系，用确认机制事后发现并重传。

对比项 CSMA/CD CSMA/CA
冲突处理 撞了才发现，发现就停 发射前先避开，撞了靠 ACK 事后发现
检测手段 电缆电压叠加 空口能量/载波检测（CCA）
发送中监听 要，边发边听 做不到，半双工且自身信号淹没对方
撞了之后 立刻停发，发阻塞信号 没 ACK，到超时后重传
退避算法 二进制指数退避（2T 为单位） 竞争窗口 + 随机 slot 退避（重传时窗口翻倍）
开销 低，无额外帧 高，ACK/RTS/CTS 都是额外帧

一句话记：有线是「撞了才知道」，无线是「知道会撞，那就别撞」。

6.4 「听」是怎么实现的：CCA #

无线不能边发边听，但可以「发之前听」。这个听的动作叫 CCA，Clear Channel Assessment，空闲信道评估。三种做法：

方式 全称 判断依据
ED Energy Detection，能量检测 收到的信号功率超过某个阈值，就当信道被占用
CS Carrier Sense，载波检测 收到的信号和本地 PN 码做运算，相关性超过阈值就当被占用
ED & CS 混合检测 两样一起用，判断更稳

为什么无线要这么麻烦？还是衰减。有线里干扰信号叠加出的电压跳变很明显；空口上干扰信号随距离衰减得很快，到了接收端只剩一点点波动，光看幅度不够，还得靠载波相关性帮忙确认「这确实是一个 802.11 信号，不是环境噪声」。

驱动侧这件事基本是芯片的事，你在驱动里接触不到 CCA 算法本身。但你会碰到它的结果：CCA 阈值配得保守，芯片整天报「信道忙」，吞吐上不去；配得太激进，别人在发它也当空闲，撞了就丢包。厂商驱动里那些 cca_threshold、ed_threshold 之类的私有参数，调的就是这个。

6.5 隐藏终端：最典型的撞法 #

CSMA/CA 靠「先听」能避开大部分碰撞，但有一类撞法它看不见。

A 和 C 都能和 B 通，但 A 与 C 之间互相听不到——中间隔得远，或者有堵墙。A 要发数据给 B，先听，信道空闲，发。同一时刻 C 也要发给 B，也先听，也没听到 A（因为听不到），也发。两路信号在 B 那里撞成一团。B 什么都收不到，A 和 C 都以为自己在正常传输，直到 ACK 超时才知道出事。

这叫隐藏终端问题（Hidden Terminal）。问题不在 A 也不在 C，在于它们的信息不完整：只听到了自己那一半的世界。

解决靠 RTS/CTS 握手，让 B 来当裁判：

text
A ---- RTS ------------> B
C                    （C 听不到 A 的 RTS，但能听到 B 的 CTS）
B ---- CTS (广播) -----> A 和 C
A ==== Data ===========> B       ← C 已经静默
B ---- ACK ------------> A
  1. A 先发 RTS（Request To Send），告诉 B「我想占用信道一段时间」；
  2. B 回 CTS（Clear To Send），而且这个 CTS 是广播出去的，A 和 C 都能收到；
  3. C 收到 CTS 就知道「接下来这段时间有人要用信道」，自己压下不发；
  4. A 收到 CTS，确认 B 已经清场，开始传数据。

关键在于 CTS 是 B 发的，而 B 对 A、C 都可见。用 B 这个「双方都能听见的中间人」把隐藏关系打通。CTS 的 Duration 字段还会把需要静默的时长写清楚，其他站点据此设置 NAV。

RTS/CTS 不是免费的，两个小包也是开销。所以它有个阈值：帧大于阈值才走 RTS/CTS，小帧直接发。这个阈值就是驱动里的 RTS Threshold，iw phy 里的 RTS threshold，mac80211 里通过 ieee80211_ops.set_rts_threshold 或 config 回调下发给硬件。设成 2347 等于关掉握手，设得小会让小包也走握手，开销立刻上去。

顺带说一个边界情况：RTS/CTS 只在发送方和接收方之间建立保护，如果 A 和 C 连 B 的 CTS 也听不到（三个方向全互相隐藏），这套机制救不了，只能靠上层重传。

七、帧间间隔、退避与 RTS/CTS #

上一章讲了「为什么不能检测」，这一章讲「避开」的具体节奏。核心是一件事：每次通信都要有一段只有一个人在说话的时间窗，把这段时间切出来靠的是帧间间隔和退避。

7.1 帧间间隔：谁先说，谁后说 #

信道从忙变闲之后，不是谁想发就立刻发。所有想发的站点都要等一段固定时长，这个时长叫帧间间隔（IFS，Interframe Space）。间隔越长，优先级越低。

间隔 全称 长度（量级） 谁用 作用
SIFS Short IFS 10us 级（2.4G） ACK、CTS、分片后续帧 最短，保证一次通信的原子性
PIFS PCF IFS SIFS + 一个 slot PCF 模式下 AP 轮询 无竞争期用，实际部署少见
DIFS DCF IFS SIFS + 两个 slot 普通数据帧和 RTS 常规竞争的门槛

SIFS 短到别人根本来不及抢：数据帧发完，接收方等 SIFS 就回 ACK，其他站点还在等 DIFS，插不进来。这就是「原子性」的实现方式——不给别人留窗口。

具体的微秒数值依赖物理层（802.11b/g/n 各不相同），协议标准里按 PHY 分别规定。这里只记量级：SIFS 最短，DIFS 是 SIFS 加两个时隙。

7.2 退避：DIFS 之后还要抽签 #

等完 DIFS 还没完。所有同时等完 DIFS 的站点会一起进入竞争窗口，把窗口切成若干 slot，各自随机挑一个 slot 数，作为自己还要再等几个 slot。

text
信道空闲
   |
   |<-- DIFS -->|<-- 退避窗口（随机挑 slot）-->|
   |            | slot0 | slot1 | slot2 | ... |
   |            |       |       |       |     |
   |            站点挑中 slot2，等到 slot2 结尾才发

挑的 slot 越小，越早发。挑中同一个 slot 的两个站点会同时发，真的撞上——这就回到上一章的 ACK 机制：收不到 ACK 就重传，重传时把竞争窗口翻倍，随机区间变大，第二次撞的概率下降。这套和有线网的 BEB 是同一个思路。

退避计数还有个细节：站点在倒计时过程中如果听到别人开始发，就暂停自己的计数，等对方传完、再等一个 DIFS，从刚才停下的地方继续倒数。这样先到的人不会被后来者反复打断，公平性靠这条规则维持。

QoS 就架在这套机制上：不同优先级的帧用不同的竞争参数（CWmin、AIFSN），语音和视频拿更小的窗口，先抽中先发。mac80211 里这些参数挂在每个 AC（接入类别）队列上，驱动侧看到的是 ieee80211_tx_queue_params。

7.3 ACK：撞没撞，靠这个判定 #

CSMA/CA 没有冲突检测，它怎么知道刚才那一帧有没有送达？靠 ACK。

单播数据帧发出去之后，发送方启动一个定时器，等接收方在 SIFS 之后回来的 ACK。收到 ACK，这一帧算完；定时器超时还没收到，就判定失败，重传，同时把重传计数加一。

这就是「CA = Collision Avoidance」的完整回合：发射前尽量避开，发射后靠确认兜底。ACK 帧本身极短（10 字节控制帧），不带 Frame Body，不会引入明显开销，但它把「可靠传输」这件事从上层 TCP 拉到了链路层。无线链路误码率高，没有这一层兜底，TCP 会以为网络拥塞，把窗口越压越小，吞吐彻底塌掉。

重传次数有上限，mac80211 里对应 IEEE80211_TX_MAX_RATES 那套速率重试表，硬件里则是每帧的重试计数（retry_limit）。超上限就丢包，统计里计入 tx_errors。你 iw dev wlan0 station dump 看到的 tx retries、tx failed 就是这两项。

7.4 一次完整的信道竞争 #

把上面几块拼起来，一帧数据从「想发」到「发成功」的完整顺序：

text
1. 听信道。忙 -> 等
2. 信道空闲，等 DIFS
3. 随机挑一个退避 slot，倒数
4. 倒数到 0，信道仍空闲 -> 发
5. 帧超过 RTS 阈值 -> 先发 RTS，等 CTS
6. 发数据帧（Duration 设置 NAV）
7. 等 SIFS，接收方回 ACK
8. 收到 ACK -> 完成；超时 -> 窗口翻倍，重传

第 5 步是可选的，第 7、8 步是必须的。这两步删掉任何一步，无线链路都不能用。

7.5 分片：把长帧切短 #

无线链路误码率高，一帧越长，全帧全对的概率越低。802.11 的应对是分片：帧体超过分片阈值就切开，一片一片发。

项 说明
判定依据 帧体长度超过 Fragmentation Threshold
每片怎么发 一片一个数据帧，各自带序号与分片号
片间间隔 SIFS，比其他站点等 DIFS 短，插不进来
确认粒度 每片单独 ACK，不用等整帧
出错代价 只重传出错的那一片

代价是开销变大：每片都要一个帧头、一个 ACK、一个 SIFS 间隔，频谱效率下降。所以阈值要按环境调：干扰重的现场往小调，干净的室内往大调或者干脆关掉（设成 2346 以上）。

分片号和序列号挤在同一个 Sequence Control 字段里：高 12 位是序列号，低 4 位是分片号。重传时序列号不变，只把 Frame Control 里的 Retry 位置 1，接收端据此去重。这也是为什么抓包里看到序列号重复不要急着当丢包，先看 Retry 位。

八、802.11 帧的字节序与地址字段 #

写驱动绕不开两件事：字节序和地址。前者决定你从 buffer 里读出来的数字对不对，后者决定帧该往哪送。

8.1 传输用小端，描述用大端 #

802.11 和以太网在传输时都按小端走：一个字节一个字节地发，低位字节先上线。协议标准描述一个帧的整体结构时，也是小端的画法：

text
|b0|b1|b2|b3|b4|b5|b6|b7|b8|...

最低位 b0 排在最前面，按这个顺序往物理层送，先 b0 到 b7，再 b8 往后。

但标准在解释某个具体字段的值时，用的是大端写法。假设 b3=0、b2=1、b1=0、b0=0 组成一个叫 FLAG 的域，标准会写 FLAG=4，也就是 b3b2b1b0 = 0100。同一个域，整体描述里是 b0b1b2b3 = 0010，字段值里是 4。两个数看着不一样，说的是同一件事。

场景 字节序 例子
空口传输 小端，低位字节先发 帧按 b0 到 b7 依次送
标准描述帧整体 小端 按 b0 到 b7 的顺序画
标准描述字段值 大端 FLAG=4 即 0100
TCP/IP 网络字节序 大端 htonl / htons
Wireshark 显示 一律大端 位序按 b7 到 b0 展示

内存地址是按字节编的，不是按位，所以内存里的大端小端也是以字节为单位。32 位小端机器上存 int 1，内存里从低地址到高地址是 01 00 00 00；说「位序大小端」的时候讲的是位，说「内存大小端」的时候讲的是字节，两件事别混。

落到代码上就一条准则：header 里的多字节字段（Duration、Sequence Control、Frame Body 里的 IE 长度）从 buffer 里取出来必须过 le16_to_cpu / cpu_to_le16。直接强转在当前机器上跑得通，换个架构就错位。这类 bug 在 x86 上测不出来，一到 ARM 上就现形。

MAC 地址是个例外，它不是数值，是一串 pattern，没有端序可言，也没有「哪个 MAC 更大」这种说法。但传输时仍然是逐字节走，字节内部低位先传——所以 01-80-C2-00-00-00 上线之后的比特流顺序和它写出来的样子并不一致。判断单播还是组播，看第一个字节的最低位，别看整个地址。

8.2 为什么无线要四个地址 #

以太网帧头只有两个地址：源和目的。802.11 最多四个。原因在于无线帧要跨两段：空口那一段，和分布式系统那一段。中间那个 AP 既是无线侧的端点，又是有线侧的端点，两段各有各的「谁发的、谁收的」。

四个地址的定义：

字段 名称 含义
Address 1 RA / DA 当前这一段实际接收者
Address 2 TA / SA 当前这一段实际发送者
Address 3 DA 或 SA 或 BSSID 跨段之后的另一端
Address 4 仅 WDS 用 第四段地址

换成中文说：SA 是帧最初从谁那儿发出的，DA 是帧最终要送到谁那儿；TA 是这一段空口上实际在发的人（往往是转发中的 AP），RA 是这一段空口上实际在收的人（往往是接收后还要转发的 AP）。SA/DA 管端到端，TA/RA 管一跳。

8.3 ToDS / FromDS 决定怎么填 #

哪几个地址生效、各填什么，全由 Frame Control 里的 ToDS、FromDS 两位定。这两位只在数据帧里有意义，管理帧和控制帧里恒为 0。

ToDS FromDS 场景 Address 1 Address 2 Address 3 Address 4
0 0 IBSS / Adhoc，或管理帧、控制帧 DA SA BSSID 不用
0 1 AP 发给 STA（下行） DA BSSID SA 不用
1 0 STA 发给 AP（上行） BSSID SA DA 不用
1 1 WDS，AP 之间桥接 RA TA DA SA

把 DS 大致当成 AP 来理解最省事：To DS 是从 STA 往 AP 送（也叫 Upload），From DS 是从 AP 往 STA 送（也叫 Download）。To/From 是站在 AP 的角度说的。

同一份内容在两种介质里的地址变化，看一个例子就清楚。Station 和以太网上的 Host 通信：

text
Station <--- 空口 ---> AP <--- 以太网 ---> Host
  • Station 到 Host：空口那一段 Src=Station, Dst=Host, Tx=Station, Rx=AP；AP 转到以太网上，以太网帧只有 Src=Station, Dst=Host，没有 Tx/Rx 的位置。
  • Host 到 Station：以太网那一段 Src=Host, Dst=Station；AP 转到空口上，Src=Host, Dst=Station, Tx=AP, Rx=Station。

两个无线 Station 经同一个 AP 通信也一样：空口上始终有 Tx 和 Rx，而跨段的只有三个地址。只有当两端都是无线、且中间过两个 AP 做无线桥接时，四个地址才真的各不相干，这就是 WDS 的场合。

8.4 落到驱动里的位置 #

发送路径上，这些地址要在 pkt_attrib 里一项项填好再拷进硬件描述符：ra、ta、bssid、seq_ctrl。填错哪一项，症状都一样——抓包能看到帧出去了，对面不回。

现象 填错的位置
AP 完全不响应 ra 不对
能收到 ACK 但上层收不到数据 Address 3 里的 DA/SA 填反
AP 模式下对端关联不上 bssid 没填或填错
抓包看序列号跳变 seq_ctrl 没按帧递增

接收路径反过来：ieee80211_rx 拿到帧之后按 ToDS/FromDS 重新解析地址，把该剥的剥掉，转成 802.3 头往上送。这一段 mac80211 替你做了，fullmac 芯片在固件里做，厂商私有驱动自己写——三条路里最容易被写错的是最后一条，因为没人给你兜底。

九、Power Save：节电模式与 TIM/DTIM #

电池是无线设备的命门。射频一直开着收，电很快就没了，所以 802.11 专门设计了一套节电机制。

9.1 睡的只是接收 #

先纠正一个常见误解：802.11 的 Power Save 不是把整台设备睡过去，睡的是 WiFi 的接收部分。

状态 接收器 发射器 说明
活跃（Active） 开 开 正常收发，最费电
节电（PS） 关 开 收不了，但随时能发
发射中 — 开 比接收更费电，射频功放是耗电大头

关键点在第 2 行：睡眠期间 STA 仍然可以主动发。发的时候它会等回复，所以那一刻接收器是开着的。真正收不到的是「别人主动发给它」的帧——这正是需要 AP 配合的地方。

状态切换前，STA 会给 AP 发一个 Frame Control 里 Pwr Mgmt 位置 1 的帧，告诉 AP「我要睡了」。AP 记下这个 STA 进入节电状态，之后不再直接给它送帧。

这几位状态和功耗的关系，画成图更直观：

text
功耗
 ^
 |                    +----------------+
 |                    |    发射（TX）  |
 |        +-----------+                |
 |        |  接收（RX）                 |
 +--------+                            +------------------> 时间
   睡眠

发射比接收更耗电，这是射频功放的物理特性，跟软件优化无关。

9.2 AP 帮忙缓存：TIM 与 DTIM #

STA 睡了，发给它的帧怎么办？AP 替它存着。

缓存分两类，机制不一样：

帧类型 AP 怎么处理 通知方式
单播 缓存起来，等 STA 来取 Beacon 的 TIM 位图
广播/组播 缓存起来，按 DTIM 周期统一发 Beacon 的 DTIM 计数

Beacon 是 AP 定时广播的帧，里面有个 TIM（Traffic Indication Map）字段，实际是一张位图，每个和这个 AP 关联的 STA 占一位。某位被置 1，表示「这个 STA 有缓存数据等着」。睡着的 STA 会按约定周期醒来，读一下 Beacon 里的 TIM，发现自己的位是 1，就发一个 PS-Poll 帧去取数据，取完继续睡。

text
AP  ---- Beacon (TIM[STA]=1) ----> STA（醒来读一眼）
STA ---- PS-Poll ----------------> AP
AP  ---- Data (More Data=1) ------> STA
STA ---- ACK ---------------------> AP
AP  ---- Data (More Data=0) ------> STA
STA（取完继续睡）

More Data 位告诉 STA「还有没有下一帧」，省得它为每一帧都发一次 PS-Poll。

广播和组播不能这么办——那是所有 STA 都要的，一个个问太浪费。所以用 DTIM：AP 每发一个 Beacon 就把 DTIM 计数减 1，减到 0 的那个 Beacon（DTIM Beacon）之后，AP 把缓存的广播帧一次性发出去。所有 STA 只要在 DTIM 时刻醒着就能收到。

这就解释了为什么给一个睡着的设备 ping 延迟那么高：echo request 到了 AP，AP 得等 STA 醒来读 TIM，STA 再发 PS-Poll 来取，一个来回要跨好几个 Beacon 周期。默认 Beacon 间隔 100ms 上下，DTIM 周期常见 1 到 3，加起来就是几百毫秒的延迟。

9.3 驱动里的落点 #

落点 mac80211 fullmac / 厂商驱动
开关节电 NL80211_CMD_SET_POWER_SAVE → ieee80211_ops.set_power_mgmt 或 cfg80211_ops.set_power_mgmt 私有命令下发到固件
Pwr Mgmt 位 mac80211 自动置位 固件自己写
PS-Poll 帧 mac80211 生成 固件生成
TIM/DTIM 解析 mac80211 处理 固件处理
唤醒源 — wol_gpio、wol_criteria

节电开关在 iw dev wlan0 set power_save on 与 iw dev wlan0 set power_save off 之间切。mac80211 的 IEEE80211_CONF_PS 标志一开，硬件就按节电时序工作。

厂商驱动多出来的那一坨是深度睡眠（deep sleep）：整颗芯片掉电，只留一根 GPIO 和极少数逻辑，靠 WOL（Wake on LAN）事件唤醒。libertas 的 if_sdio_probe 里那几个字段就是干这个的：priv->wol_gpio 指定唤醒脚，priv->wol_gap 是唤醒后的等待间隔，priv->wol_criteria 是唤醒条件。这套东西配错的表现很典型——suspend 之后设备再也唤不醒，只能拔电重启。

节电和吞吐是一对矛盾。开着 PS，接收要等 Beacon 周期，延迟和突发吞吐都受影响；关掉 PS，功耗立刻上去。可穿戴设备选前者，插电设备选后者。这也是笔记本一插电 WiFi 就变快的原因之一。

9.4 有节电与无节电的差别 #

把两种模式摆在一起看，差别全在「什么时候能收到帧」。

维度 无节电（Active） 有节电（PS）
接收器 常开 周期性关闭
收帧时机 随时 只在醒来的窗口
单播怎么到手 AP 直接发 AP 缓存，等 STA 发 PS-Poll
广播怎么到手 AP 直接发 攒到 DTIM Beacon 之后统一发
延迟 一个帧间隔 跨几个 Beacon 周期，几百毫秒
功耗 高 低，与唤醒周期强相关
适用 插电、要吞吐 电池供电、要续航

决定功耗的是唤醒频率，不是「开不开节电」。Beacon 间隔 100ms、DTIM 周期 3，意味着 STA 每 300ms 至少醒一次，其余时间在睡。把 DTIM 周期调大能更省电，代价是广播帧到手更慢、组播业务（比如 mDNS 发现）延迟明显。

这里有个常被忽略的联动：STA 睡着的时候，AP 那边还留着一份「这个 STA 在省电」的状态。STA 异常掉线没来得及通知 AP，AP 会一直替它缓存，缓存满了就丢新来的帧。表现是设备重新连上之后一段时间内收不到包，得等 AP 的超时机制把它清掉。

十、抓包看 802.11 #

前面所有机制，最终都要在抓包里验证。这一章讲怎么抓、抓到了看什么。

10.1 网卡默认抓不到别人的帧 #

第一个要接受的事实：普通网卡抓不到不属于自己的帧。驱动收包时先按目的地址过滤，不是发给本机的直接扔掉，抓包工具连影子都看不到。

要看到整个空口，网卡得进监听模式（monitor mode）。监听模式关掉地址过滤，把收到的每一个 802.11 帧原样交给上层。

bash
iw dev wlan0 interface add mon0 type monitor
ip link set mon0 up
tcpdump -i mon0 -e -s 0 -w cap.pcap

两句前提：驱动得支持 monitor。厂商驱动经常把 add_interface 里的 NL80211_IFTYPE_MONITOR 分支砍掉，那这条路就走不通。监听和上网也不能同时干——同一颗射频切到监听，就没法正常关联了。

专门的硬件嗅探器也有一类，比如 AirPcap，插上就能收全空口，代价是几百到上千美金。它只有 Windows 驱动，配 Wireshark 用。还有一类是芯片厂自带的调试口，能看到固件内部的收发路径，比空口抓包更细，但不通用。

10.2 抓包前先确认三件事 #

抓到的帧不一定可信，看之前先做三项检查。

检查项 怎么判断 处理
校验和 FCS 字段算不对 直接忽略，这类帧没有分析价值
信道 在 1 信道抓到了 6 信道的帧 说明存在邻频泄漏，别把它当成同信道干扰
加密 Protected Frame 位为 1 载荷看不到，只有头和长度可用

FCS 是 CRC32，抓包工具一般会标出 bad FCS。开着监听模式在干扰重的地方抓，坏帧比例能到两三成，这部分不能当真实流量统计。

加密这一条得说清：Protected Frame 位为 1 只表示载荷被加密，不代表这个网络要密码才能接入。两种情况是分开的——网络可以开放认证但启用加密，也可以有认证但某类帧没有加密（比如管理帧）。

10.3 看什么：帧类型与过滤 #

抓下来一屏幕帧，先按三种类型分开看。

类型 抓包过滤表达式 关注点
管理帧 wlan.fc.type == 0 Beacon 的 SSID/RSN IE、关联交互的 Status Code
控制帧 wlan.fc.type == 1 RTS/CTS 的 Duration、ACK 有没有回
数据帧 wlan.fc.type == 2 ToDS/FromDS、三个地址、序列号

再细一层，按子类型过滤更省事：wlan.fc.type_subtype == 0x08 是 Beacon，0x0b 是 Authentication，0x00 是 Association Request。

Wireshark 的显示过滤器和抓包过滤器是两套。抓包时用的是 BPF 语法（Berkeley Packet Filter），是通用的，不是 Wireshark 专有；显示时用的是 Wireshark 自己的语法，功能更强，能引用任意字段。实践上的做法是抓的时候不过滤，全抓下来，再用显示过滤器筛——抓包期的过滤有时候不准，漏掉的帧再也找不回来。

显示过滤器可以存成按钮复用，常用的几条：wlan.addr == xx:xx:... 只看某个设备，wlan.fc.retry == 1 只看重传帧，eapol 只看四次握手。

10.4 关联阶段的帧序 #

抓关联过程最能验证协议理解对不对。开放认证的完整帧序：

text
AP  -> Beacon (周期广播)
STA -> Probe Request (广播)
AP  -> Probe Response
STA -> ACK
STA -> Authentication Request
AP  -> ACK
AP  -> Authentication Response
STA -> ACK
STA -> Association Request
AP  -> ACK
AP  -> Association Response   ← 看 Status Code，0 才是成功
STA -> ACK

两个容易看错的地方。

第一个：802.11 层的认证（Authentication）在抓包里看着是「直接通过」的。开放认证就是空认证，谁来都过。真正的安全认证在后面——如果网络用了 WPA2，关联成功之后紧跟一段 EAPOL 四次握手，那一段过不了，已经建立的关联会被立刻拆掉。这套设计的根源是 802.11 最初没考虑安全，为了兼容老设备只能后补。

第二个：广播帧没有 ACK，单播帧有。Probe Request 是广播，抓包里它后面不会跟 ACK；Probe Response 是单播，后面必须有 ACK。看到「单播帧后面缺 ACK」，就是丢了。

10.5 地址与序列号怎么读 #

抓包里最容易看晕的是地址。记住上一章那张 ToDS/FromDS 表，逐帧套就行。几个经验：

  • BSSID 和 AP 标注的 MAC 经常不一样，一般只差最后几位。看见几个只差几位的地址，多半是同一台设备虚拟出来的多个接口。
  • 一个地址上的序列号是连续的。看到跳号或者重复，要么丢包，要么是重传（wlan.fc.retry == 1）。
  • 如果一台设备虚拟了两个地址，两串序列号会各自连续，也会混在一起连续，取决于实现。

抓 40MHz 信道要留个心：老的嗅探硬件对 40MHz 支持不好，容易抓不全。要在 36 或 40 号信道上抓，并且把 Wireshark 的 offset 设成 +1。这是嗅探器芯片固件的限制，跟 802.11 无关。

10.6 命令行侧的几个入口 #

不想开图形界面的时候，几个命令够用：

bash
wpa_cli status            # 当前连的 SSID、BSSID、本机 MAC、IP
iw dev wlan0 link         # 链路状态与信号强度
iw dev wlan0 station dump # 对端统计，含 tx retries / tx failed
iw phy | grep -A5 "RTS"   # 看 RTS 阈值

wc 和 wl 这两个命令是博通那套工具链的，wc 偏上层配置，wl 直接怼芯片。换到别的芯片厂就没有了，别把它当成通用命令。

11.2 wiphy 与 ieee80211_hw #

struct wiphy 描述一块无线硬件的静态能力：支持哪些频段、哪些加密套件、哪些接口模式、哪些 nl80211 命令。驱动先填它，再 wiphy_register。struct ieee80211_hw 是 mac80211 的视图，里面套着一个 wiphy，外加队列数、最大聚合长度、硬件加密能力这些给协议栈看的参数。

c
/* mac80211 驱动的注册骨架，名字对照 2.6.35~3.x */
hw = ieee80211_alloc_hw(sizeof(struct my_priv), &my_ieee80211_ops);
/* 填 hw->wiphy->bands[IEEE80211_BAND_2GHZ]，填 hw->queues 等 */
ieee80211_register_hw(hw);

ieee80211_alloc_hw 的第二个参数是 struct ieee80211_ops *。从 3.x 起 ieee80211_ops 成员只增不减，老驱动拿新头文件编译，问题不在报错，在「老代码给它赋 NULL 的成员被新内核当空指针调用」。对着 include/net/mac80211.h 逐个成员核，别靠猜。

11.5 两条注册路径 #

c
/* fullmac：libertas 走这条 */
wdev->wiphy = wiphy_new(&lbs_cfg80211_ops, sizeof(struct lbs_private));
wiphy_register(wdev->wiphy);

/* softmac：走 ieee80211_alloc_hw，内部替你 wiphy_new */
hw = ieee80211_alloc_hw(priv_size, &my_ieee80211_ops);
ieee80211_register_hw(hw);

这两行的差别就是「802.11 协议栈跑在哪」。跑固件里，主机侧只剩搬运；跑内核里，主机侧要处理大量帧级逻辑。

十二、无线驱动的整体架构 #

分层的写法跟 SDIO/USB 都一样，只是每层叫法不同。

text
        用户态：wpa_supplicant / hostapd / iw
                    |  nl80211（netlink）
        --------------------------------------------
        cfg80211   （配置核心，注册 wiphy）
                    |
        mac80211   （802.11 软协议栈，可选）
                    |
        ieee80211_ops / cfg80211_ops
                    |
        厂商私有核心层：lbs_* / rtw_* / hal_*
                    |
        接口驱动层：sdio_driver / usb_driver
                    |
        主机控制器驱动：mmc_host_ops / usb_hcd
                    |
        硬件：SDIO 控制器 / USB 控制器 → WiFi 芯片

再往下看就是固件。固件干两件主机不愿意干的事：一是帧格式转换，空口上是 802.11 帧，主机和上层要的是 802.3 帧，fullmac 里由固件转、softmac 里由 mac80211 转、厂商私有驱动里由驱动自己写函数转；二是数据缓存与中断上报，天线收到数据、固件处理完塞进 buffer，再抬一根中断线告诉主机「有东西了」。

这就是全文反复出现的同一个模式：中断 → 读 buffer → 剥封装 → 交给协议栈。SDIO 和 USB 的差别，只在于「读 buffer」用的是 sdio_readsb 还是 URB。

12.1 三种设备身份 #

以 USB 接口的 WiFi 模组为例，同一个东西在 Linux 里有三重身份：

视角 它是什么 落点
USB 总线视角 USB 设备 usb_driver + usb_interface
Linux 设备分类视角 网络设备 net_device（wlan0）
WiFi 协议视角 私有设备 厂商私有结构 + wireless_handlers 或 wiphy

抓这三条线索读源码，框架就能自己浮出来。SDIO 接口换成 sdio_driver + sdio_func，其余两条不变。

12.2 模块分类：先搞清你在给谁写驱动 #

类别 协议栈跑在哪 接口 代表
通用 WiFi 模块 主机 OS 里（Android / Windows / iOS） USB、SDIO RTL81xx、BCM、Marvell、高通 Atheros
路由器方案模块 带 Flash/RAM 的芯片 + Linux 内部总线 家用路由器方案
嵌入式 WiFi 模块 模块自带的 MCU 里 UART、SPI、I2C、SDIO TI CC3200、MXCHIP、ASIX、HF-LPA

这个分类直接决定「要不要写内核驱动」。嵌入式模块把 RF 收发器、MAC、WiFi 驱动、全部 WiFi 协议、无线安全协议、一键连接全塞进模块，对外只露一个 UART/SPI 口。从软件层面看，它压根不是网络设备，你往串口读写字节就行。通用模块反过来，驱动与协议栈都在主机，从软件层面看就是个网络设备，必须遵循网络协议。

维度 嵌入式 WiFi 模块 普通 WiFi 模块
适用范围 无线家电、仪表、智能灯泡 笔记本、手机、平板
主控 模块上的 MCU x86 / ARM 高速处理器
接口 UART、SPI、I2C、SDIO USB、SDIO
功耗 低 高

家电、仪表、LED 灯的主控常是成本极低的 MCU，跑不动整套 802.11 协议栈，功耗也扛不住。嵌入式模块就是为这类场景造的。本系列讲的驱动，全部属于「普通 WiFi 模块」那一栏。

12.3 拓扑与工作模式 #

拓扑 谁创建网络 有无 AP 典型场景
Infra（基础网） AP 创建，STA 加入 有 家里、办公室
Adhoc / IBSS（自组网） STA 自己组成 无 临时对等网、传感器网

Infra 里所有通信都经 AP 转发，AP 是中心节点，没有它网就不存在。Adhoc 是松散结构，网内 STA 可以直接互通，但缺中心节点意味着没有认证与转发的管理者，实际部署少。

很多模组的模式配置就是这两档：AP 模式把它当路由器（手机电脑直接连模组），Infra 模式把它当终端（去连别的路由器）。虚拟 AP 是第三种，允许一个射频同时扮演 AP 和 STA。

串口模组还有两种联网方式，跟驱动无关但常被一起问：主动型，设备主动连后台服务器当 TCP Client（无线 POS 机是典型）；被动型，设备当 TCP Server 等服务器来连（传感器网是典型）。

12.4 模组的常见能力清单 #

以原文那款模组的规格为例，看清它给驱动的边界：2.4GHz，IEEE 802.11b/g，内置 PCB 天线、可选外置；支持 Infra / Adhoc(IBSS) / 虚拟 AP；加密支持 WEP-64/128、TKIP(WPA-PSK)、AES(WPA2-PSK)；MCU 内置 TCP/IP 栈；3 路 UART（其中 1 路支持 DMA、全功能串口，最高 921.6Kbps）、SPI、I2S/PCM、Digital Video 口、最多 24 个 GPIO（部分与上述接口复用）；TCP/IP 传输带宽 10Mbps 以上；支持三种带定时自动唤醒的 WiFi 节能模式。

这份清单里有两项跟本章主题直接相关：其一是指定信道快速联网，正常联网要逐信道扫一遍，预先知道目标信道就能省掉这一轮，驱动里表现为跳过 hw_scan 直连；其二是 BSSID 绑定，作用见 4.4。

十三、SDIO 接口基础 #

SDIO 就是 SD 的 I/O 接口。SD 本来是存储卡标准，把 SD 的 I/O 脚拿去接外设，就是 SDIO。SD 协会提供了一整套 SDIO stack 驱动，SDIO 外设（SDIO 卡）的开发因此变得常见。

SDIO 外设 用途
Wi-Fi card 无线网卡，本章主角
CMOS sensor card 摄像模块
GPS card 定位
GSM/GPRS modem card 蜂窝模组
Bluetooth card 蓝牙

SD 标准本来就是冲着移动设备定的，所以手机、手持装置支持 SDIO 是常态。这也是绝大多数移动 WiFi 芯片走 SDIO 而不是 USB 的原因——省电、省口。

13.1 信号线 #

SDIO 总线跟 USB 类似，两端：HOST 端和 device 端。所有通信由 HOST 发命令开始，device 能解析命令就能通信。

信号 方向 作用
CLK HOST → DEVICE 时钟，每个时钟周期传一条命令
CMD 双向 传命令与响应
DAT0-DAT3 双向 四条数据线
VDD — 电源
VSS1 / VSS2 — 电源地

DAT 线可以只用 DAT0（1 线模式），也可以四条全用（4 线模式）。4 线模式是吞吐的关键，SDIO WiFi 挂到 1 线模式上，速率直接腰斩。

13.2 命令与数据 #

SDIO 上永远是 HOST 发起、DEVICE 回应。命令由 6 个字节组成。

组成 方向 走哪条线
Command HOST → DEVICE CMD
Response DEVICE → HOST CMD
Data 双向 DAT0-DAT3，可 1 线或 4 线，跟 CRC

不是每条 CMD 都要 Response。读写流程：

阶段 步骤
读 HOST 发命令 → DEVICE 回握手 → HOST 从 4 位数据线取数据（带 CRC）→ HOST 发结束命令 → DEVICE 回响应
写 HOST 发命令 → DEVICE 回握手 → HOST 把数据放上 4 位数据线（带 CRC）→ HOST 发结束命令 → DEVICE 回响应

注意数据传送期间那颗 CRC。SDIO 总线上没有 TCP 那样的重传，坏一块数据要么硬件重试、要么协议栈往上丢包重发。SDIO WiFi 在干扰重的地方丢包，根子常在这里。

13.3 CCCR 与 FBR #

SDIO 卡把功能拆成 function，每个 function 一块 64KB 地址窗：0x00000-0x0FFFF 是 function 0，其余按 CIA 里的指针分给 function 1..7。WiFi 卡基本只用 function 1。

CCCR（Card Common Control Registers）是功能 0 里的寄存器组，管整张卡：I/O 使能、I/O 中断使能、中断挂起标志、总线位宽、块大小。写 WiFi 驱动时天天打交道的几个：

寄存器 偏移 作用
SDIO_CCCR_IOEx 0x02 各 function 的 I/O 使能位
SDIO_CCCR_IENx 0x04 各 function 的中断使能位
SDIO_CCCR_INTx 0x05 中断挂起标志，中断处理里先读它
SDIO_CCCR_ABORT 0x06 复位/中止
SDIO_CCCR_BRCTL 0x10 块大小写控制
SDIO_CCCR_BLKSIZE_0/1 0x10 / 0x11 传输块长度，SDIO WiFi 常设成 512

FBR（Function Basic Registers）在每个 function 内部的 256 字节功能区，管这个 function 自己：标准 SDIO 接口代码（CIS）、块大小、CIS/CSA 指针、scratch 寄存器。

寄存器 偏移 作用
SDIO_FBR_BASE(f) 0x100 * f 每个 function 的基址
SDIO_FBR_STD_IF +0x00 标准 I/O 接口码，WiFi 是 0x0
SDIO_FBR_CIS_PTR +0x09 CIS 指针，从 CIS 里读厂商 ID、设备 ID
SDIO_FBR_CSA_PTR +0x0C CSA 指针
SDIO_FBR_BLKSIZE_0/1 +0x10 / +0x11 该 function 的块大小

libertas 的 if_sdio_probe 里有一段：

c
for (i = 0; i < func->card->num_info; i++) {
    if (sscanf(func->card->info[i], "802.11 SDIO ID: %x", &model) == 1)
        break;
}
switch (model) {
case MODEL_8686:
    card->scratch_reg = IF_SDIO_SCRATCH;
    break;
}

func->card->info[] 里存的就是从 CIS 解析出的字符串。厂商在 CIS 里写一条 "802.11 SDIO ID: 0x..."，驱动拿来认卡。支持一颗新卡，往往不是改 ID 表，而是加一条型号识别分支。

13.4 热插拔 #

两种做法：定时器轮询，或者插拔中断。

板子上拿一根 GPIO 做卡检测，比如 GPG10 复用成 EINT18：

电平 含义
高 没插卡
低 插了卡

软件侧就是给这根 GPIO 注册中断，在中断里调 mmc_detect_change()。具体见第十五章。

十四、SDIO 上的 WiFi 驱动结构 #

SDIO 接口的 WiFi，本质上是「一张 SDIO 卡，碰巧具备 WiFi 功能」。所以注册顺序是先作为 SDIO 卡注册，卡检测到之后再去驱动它的 WiFi 功能。整个驱动就是在 WiFi 驱动外面套了一层 SDIO 壳。

text
    设备驱动层（WiFi 设备：net_device / wiphy）
                    |
    核心层（MMC core / SDIO bus，向上向下提供接口）
                    |
    主机驱动层（mmc_host：具体 SDIO 控制器驱动，如 s3cmci）

这套「分层 + 分离」跟平台总线那套一模一样：核心层隔离主机控制器与设备驱动，两侧各自注册。

14.1 关键数据结构 #

include/linux/mmc/host.h 与 include/linux/mmc/card.h 里：

结构体 描述什么
mmc_host 卡控制器
mmc_card 卡
mmc_driver MMC 卡驱动
sdio_func 功能设备（WiFi 就是 function 1）
mmc_host_ops 卡控制器操作接口，主机控制器层向 core 注册

mmc_host_ops 的意义在于隔离：core 要操作主机控制器，只能走这组函数指针，不许直接调具体控制器的函数。换一颗 SoC，只换 mmc_host_ops 的实现，上层不用动。

    .name      = "sdio",
    .dev_attrs = sdio_dev_attrs,
    .match     = sdio_bus_match,
    .uevent    = sdio_bus_uevent,

static int sdio_bus_match(struct device *dev, struct device_driver *drv)
{
    struct sdio_func   *func = dev_to_sdio_func(dev);
    struct sdio_driver *sdrv = to_sdio_driver(drv);
    if (sdio_match_device(func, sdrv))
        return 1;
    return 0;
}

static const struct sdio_device_id *sdio_match_device(struct sdio_func *func,
                                                      struct sdio_driver *sdrv)
{
    const struct sdio_device_id *ids = sdrv->id_table;
    if (sdio_match_one(func, ids))
        return ids;
    return NULL;
}

设备和驱动注册到系统时，总线上的 match 会被调用。匹配靠 id_table 里的厂商号与设备号，匹配成功后调 .probe。

15.1 主机层：控制器注册 #

15.3 mmc_rescan：卡的识别 #

c
void mmc_rescan(struct work_struct *work)
{
    /* 卡从 bus 上移除时释放它占用的总线空间 */
    /* mmc_claim_host 判断控制器是否被占用：occupied -> host->claimed = 1 */
    mmc_claim_host(host);
    mmc_rescan_try_freq(host, max(freqs[i], host->f_min));
}

static int mmc_rescan_try_freq(struct mmc_host *host, unsigned freq)
{
    /* Order's important: probe SDIO, then SD, then MMC */
    if (!mmc_attach_sdio(host))
        return 0;
    if (!mmc_attach_sd(host))
        return 0;
    if (!mmc_attach_mmc(host))
        return 0;
    return -EIO;
}

mmc_claim_host 那一套是互斥。控制器同一时刻只许一个操作者，占用时 host->claimed = 1，后来的在 while(1) 里 schedule() 出去等；占用方 mmc_release_host() 时唤醒 &host->wq 上排队的人。这是老 MMC core 的写法，新内核改成了带上下文判断的版本。

探测顺序必须是 SDIO → SD → MMC。三种卡的识别命令有交集，先试错的那个会吃掉后面的。SDIO 卡被当成 SD 存储卡去识别，后面的一切都不会发生。

15.4 mmc_attach_sdio：建卡建功能 #

c
static int mmc_attach_sdio(struct mmc_host *host)
{
    mmc_attach_bus(host, &mmc_sdio_ops);
    /* 卡与总线上的驱动匹配时才初始化卡 */
    mmc_sdio_init_card(host, host->ocr, NULL, 0);
      -> card = mmc_alloc_card(host, NULL);            /* 分配 mmc_card */
         mmc_set_bus_mode(host, MMC_BUSMODE_PUSHPULL); /* 总线工作模式 */
         for (i = 0; i < card->sdio_funcs; i++)
             sdio_init_func(host->card, i + 1);
               -> func = sdio_alloc_func(card);        /* 分配 sdio_func */
                  mmc_io_rw_direct();                  /* 读 CIS */
                  card->sdio_func[fn - 1] = func;
    mmc_add_card(host->card);                          /* 卡挂到 mmc_bus_type */
    sdio_add_func(host->card->sdio_func[i]);           /* 功能挂到 sdio_bus_type */
    return 0;
}

struct sdio_func *sdio_func[SDIO_MAX_FUNCS] 是 mmc_card 里的功能数组，SDIO 最多 8 个功能（0 到 7），0 是卡本身，WiFi 卡一般只实现 function 1。mmc_io_rw_direct() 读的正是 CIS，里面就有前面说的 "802.11 SDIO ID: 0x..." 字符串。

整个链条收尾在 sdio_add_func → sdio_bus_type 上的 match → if_sdio_probe。

text
卡插入 → GPIO 中断 → mmc_detect_change
      → 延时工作 mmc_rescan
      → mmc_rescan_try_freq → mmc_attach_sdio
      → mmc_alloc_card → sdio_init_func → 读 CIS
      → mmc_add_card + sdio_add_func
      → sdio_bus_match → if_sdio_probe
      → wiphy_new + alloc_netdev + register_netdev
      → wlan0

15.5 if_sdio_probe 里真正的初始化动作 #

14.3 讲的是「造对象」，这里补「点硬件」：

c
static int if_sdio_probe(struct sdio_func *func, const struct sdio_device_id *id)
{
    struct if_sdio_card *card;
    struct if_sdio_packet *packet;
    struct mmc_host *host = func->card->host;

    /* 1. 认卡：从 CIS 里解析型号 */
    /* 2. 挑固件：fw_table[model] */
    /* 3. 建工作队列 */
    card->workqueue = create_workqueue("libertas_sdio");
    INIT_WORK(&card->packet_worker, if_sdio_host_to_card_worker);

    /* 4. 占有 host，开 function，要中断 */
    sdio_claim_host(func);
    ret = sdio_enable_func(func);
    if (ret)
        goto release;
    ret = sdio_claim_irq(func, if_sdio_interrupt);
    /* 5. 造网络设备（见 14.3） */
    /* 6. 启动卡、注册 cfg80211、注册 netdev */
    sdio_claim_host(func);
    ret = lbs_start_card(priv);
    if (lbs_cfg_register(priv))
        goto err;
    ret = register_netdev(priv->dev);
release:
    sdio_release_host(func);
    return ret;
}

四处顺序不能换：

步骤 调错会怎样
sdio_enable_func 先于一切寄存器访问 没使能 I/O 就访问，读回全 0xFF 或直接超时
sdio_claim_irq 先于数据收发 中断没挂上，数据到了没人接
sdio_claim_host 包住所有寄存器操作 并发读写互相踩，症状是随机 EIO
register_netdev 最后 netdev 一注册就会被 up，此时硬件栈还没齐

固件表：

c
static const struct if_sdio_model fw_table[] = {
    { MODEL_8686, "libertas/sd8686_helper.bin", "libertas/sd8686.bin" },
    { MODEL_8688, "libertas/sd8688_helper.bin", "libertas/sd8688.bin" },
};

两段固件：helper 负责把主固件搬进芯片 RAM（芯片上电时只有一小块 SRAM 可用），主固件负责后面所有事。老内核用 request_firmware，从 /lib/firmware/ 取。取不到就是那句最常见的报错：

text
libertas_sdio: failed to load firmware "libertas/sd8686.bin"

固件没在 rootfs 里，或者 CONFIG_EXTRA_FIRMWARE 没编进去，卡能认出来，网卡起不来。

十六、SDIO 的数据收发 #

16.1 接收：中断驱动 #

网络设备收数据的主路径是「中断 → 中断处理函数 → 判断类型 → 读数据 → 分配 sk_buff → 拷数据 → netif_rx() 交给上层」。

if_sdio_interrupt 挂在哪？在 if_sdio_probe 的 sdio_claim_irq(func, if_sdio_interrupt)，落到 func->irq_handler = if_sdio_interrupt。当主机控制器中断里的 S3C2410_SDIIMSK_SDIOIRQ 位被触发，MMC core 就调它。

c
static void if_sdio_interrupt(struct sdio_func *func)
{
    struct if_sdio_card *card = sdio_get_drvdata(func);
    int ret = if_sdio_card_to_host(card);   /* 从卡读数据上来 */
}

static int if_sdio_card_to_host(struct if_sdio_card *card)
{
    /* 先读 4 字节头，知道这一包有多长、什么类型 */
    ret = sdio_readsb(card->func, card->buffer, card->ioport, chunk);

    switch (type) {
    case MVMS_CMD:
        ret = if_sdio_handle_cmd(card, card->buffer + 4, chunk - 4);
        break;
    case MVMS_DAT:
        ret = if_sdio_handle_data(card, card->buffer + 4, chunk - 4);
        break;
    case MVMS_EVENT:
        ret = if_sdio_handle_event(card, card->buffer + 4, chunk - 4);
        break;
    }
}

buffer + 4 这个偏移是固定协议：前 4 字节是 Marvell 的私有头（含类型和长度），后面才是负载。这种「头部 + 载荷」的私有封装在 SDIO WiFi 里到处都是，各家字段不同，思路相同。

类型 含义 处理函数
MVMS_CMD 命令响应 if_sdio_handle_cmd
MVMS_DAT 数据帧 if_sdio_handle_data
MVMS_EVENT 异步事件（扫描完成、断开、睡眠） if_sdio_handle_event

数据包拿到之后交协议栈：

c
lbs_process_rxed_packet(card->priv, skb);

/* 中断上下文用 netif_rx，进程上下文可以用 netif_receive_skb */
if (in_interrupt())
    netif_rx(skb);

netif_rx 把 skb 丢进每 CPU 的 backlog 队列，软中断再处理。中断处理函数能很快返回，不阻塞 SDIO 控制器。这是 SDIO WiFi 吞吐能做上去的前提：中断里只搬数据，不解析。

16.2 sdio_readsb 到底做了什么 #

c
int sdio_readsb(struct sdio_func *func, void *dst, unsigned int addr, int count)
{
    return sdio_io_rw_ext_helper(func, 0, addr, 0, dst, count);
}

/* 往上追： */
static int sdio_io_rw_ext_helper(..., int write, unsigned fn,
                                 unsigned addr, int incr_addr,
                                 u8 *buf, unsigned size)
{
    ...
    ret = mmc_io_rw_extended(func->card, write, func->num,
                             addr, incr_addr, buf, blocks, func->cur_blksize);
}

int mmc_io_rw_extended(struct mmc_card *card, int write, unsigned fn,
                       unsigned addr, int incr_addr, u8 *buf,
                       unsigned blocks, unsigned blksz)
{
    struct mmc_request mrq = {0};
    struct mmc_command cmd = {0};
    ...
    cmd.arg = write ? 0x80000000 : 0x00000000;  /* bit31 是读写方向 */
    ...
    mmc_wait_for_req(card->host, &mrq);
}

这条链子从「读一串字节」一路降到「往 CMD53 的 arg 里拼读写位」。cmd.arg 的 bit31 是方向位，fn 是功能号，addr 是寄存器地址。写代码时传错 fn，读到的永远是 0xFF。

mmc_wait_for_req 内部：

c
mmc_start_request(host, mrq);
  -> host->ops->request(host, mrq);   /* 控制器驱动真正去操作寄存器 */
mrq->done_data = &complete;
mrq->done      = mmc_wait_done;
wait_for_completion(&complete);       /* 睡等完成 */

wait_for_completion 说明这条路径是同步阻塞的。所以 sdio_readsb 不能在中断上下文乱用——if_sdio_interrupt 里调它，靠的是 SDIO 的「中断里读数据」这个特例，MMC core 保证中断线程化之后能睡。这也是 SDIO WiFi 延迟偏高的原因：每个包都要等一次控制器往返。

16.3 发送：从 xmit 到 SDIO 写 #

c
/* IP 层 → dev_queue_xmit → 网络设备层的发送函数 */
int dev_queue_xmit(struct sk_buff *skb)
{
    ...
    if (!netif_tx_queue_stopped(txq)) {
        __this_cpu_inc(xmit_recursion);
        rc = dev_hard_start_xmit(skb, dev, txq);
        /* 内部：rc = ops->ndo_start_xmit(skb, dev); */
    }
}

落到 lbs_hard_start_xmit，再落到驱动挂的私有出口：

c
int ret = priv->hw_host_to_card(priv, MVMS_DAT,
                                priv->tx_pending_buf, priv->tx_pending_len);

hw_host_to_card 就是 14.3 里 probe 中赋值的 if_sdio_host_to_card。这里为什么要绕一层间接？因为核心层不知道接口类型。USB 版本赋成 usb_write_port，SDIO 版本赋成 if_sdio_host_to_card，核心层只认函数指针。这一层间接就是「同一套 WiFi 核心，两个物理接口」的实现方式。

c
static int if_sdio_host_to_card(struct lbs_private *priv, u8 type, u8 *buf, u16 nb)
{
    struct if_sdio_card *card = priv->card;
    struct if_sdio_packet *packet;

    /* 把 buf 拷进 sdio 包，前 4 字节留给私有头 */
    packet = kzalloc(sizeof(*packet) + nb + 4, GFP_ATOMIC);
    packet->nb = nb + 4;
    memcpy(packet->buffer + 4, buf, nb);
    packet->buffer[0] = 0; /* ... 私有头字段 ... */

    queue_work(card->workqueue, &card->packet_worker);
    return 0;
}

static void if_sdio_host_to_card_worker(struct work_struct *work)
{
    ...
    ret = sdio_writesb(card->func, card->ioport, packet->buffer, packet->nb);
    ...
}

为什么要 queue_work？ndo_start_xmit 会在软中断里被调用，而 sdio_writesb 要睡（前面那条 wait_for_completion）。睡眠的函数不能在中断上下文调，所以必须扔进工作队列。「xmit 只入队，真正发由 worker 干」是几乎所有无线驱动的标准做法，USB 那边换成 usb_submit_urb 异步提交，不需要额外 worker。

sdio_writesb 往下走的路和读完全对称：

c
int sdio_writesb(struct sdio_func *func, unsigned addr, void *src, int count)
{
    return sdio_io_rw_ext_helper(func, 1, addr, 0, src, count);
}
/* 再到 mmc_io_rw_extended(..., write=1, ...) → mmc_wait_for_req → wait_for_completion */

读写只差 write 参数和 cmd.arg 的 bit31。

16.4 发送队列的流控 #

dev_queue_xmit 里那句 if (!netif_tx_queue_stopped(txq)) 是流控入口。队列满了就 netif_stop_queue()，等驱动有空了再 netif_wake_queue()。这个阈值调得不对，典型症状是「小包正常、大流量直接卡死」——队列满了没被唤醒，上层一直丢包。

16.5 移除路径 #

卡拔掉时走 if_sdio_remove。顺序必须是「先停业务，再拆对象，最后放 host」：

c
if_sdio_remove(struct sdio_func *func)
  -> lbs_stop_card(card->priv);
     lbs_remove_card(card->priv);
       -> kthread_stop(priv->main_thread);   /* 停内核线程 */
          lbs_free_adapter(priv);
          lbs_cfg_free(priv);
          free_netdev(dev);
  -> flush_workqueue(card->workqueue);       /* 排空工作队列 */
     destroy_workqueue(card->workqueue);
  -> sdio_claim_host(func);
     sdio_release_irq(func);                 /* 先放中断 */
     sdio_disable_func(func);                /* 再关功能 */
     sdio_release_host(func);

flush_workqueue 必须在 destroy_workqueue 之前，否则工作项还在跑，结构体已经被释放。sdio_release_irq 必须在 sdio_disable_func 之前，否则中断还会来。这两个顺序错一个就是随机 oops，而且是插拔几次才崩一次的那种，最难查。

十七、USB 接口 WiFi 驱动结构 #

USB 版跟 SDIO 版只差接口，其余框架同源。作为参照：USB 摄像头驱动、USB 鼠标驱动都符合同一套 USB 驱动结构，区别只是摄像头是字符设备、WiFi 是网络设备。你要写的部分永远是「USB 设备驱动」那一层。

text
    USB 设备驱动（字符设备 / 块设备 / 网络设备）
                    |
              USB 核心
                    |
        USB 主机控制器驱动（HCD）

硬件层面，WiFi 芯片跟 CPU 说话走 USB，跟别的 WiFi 芯片说话走 RF。软件层面，Linux 要管它就得挂到 USB 总线上（由 USB 子系统管），同时又得对接网络（封装成网络设备）。

c

usb_register 这一步只解决「让 Linux 在 USB 总线上看到这个设备」。最大最复杂的工作全在填 usb_driver 成员。

.id_table 与 SDIO 的 sdio_device_id 一样是匹配依据，只是字段换成 idVendor/idProduct。

17.3 私有功能层与 USB 四层描述符 #

第三块归 WiFi 自己：芯片配置与初始化、与用户空间的交互接口、私有功能实现。

c

xxx_hal_init();

外加功耗管理。WiFi 在移动设备里是耗电大户，suspend/resume 里要能真正关射频、保寄存器、按需唤醒。这部分在同一颗芯片上常比数据路径还长。

USB 设备的四层：设备、配置、接口、端点。不是每层都要初始化，按设备功能挑。

c
static struct dvobj_priv *usb_dvobj_init(struct usb_interface *usb_intf)
{
    struct dvobj_priv *pdvobjpriv;
    struct usb_device *pusbd;
    struct usb_device_descriptor *pdev_desc;
    struct usb_host_config *phost_conf;
    struct usb_config_descriptor *pconf_desc;
    struct usb_host_interface *phost_iface;
    struct usb_interface_descriptor *piface_desc;
    struct usb_host_endpoint *phost_endp;
    struct usb_endpoint_descriptor *pendp_desc;
    int i, status = _FAIL;
    u8 val8;

    /* 设备 */
    pdvobjpriv->pusbintf = usb_intf;
    pusbd = pdvobjpriv->pusbdev = interface_to_usbdev(usb_intf);
    usb_set_intfdata(usb_intf, pdvobjpriv);
    pdev_desc = &pusbd->descriptor;

    /* 配置 */
    phost_conf  = pusbd->actconfig;
    pconf_desc  = &phost_conf->desc;

    /* 接口 */
    phost_iface = &usb_intf->altsetting[0];
    piface_desc = &phost_iface->desc;

    /* 端点：网络设备传批量数据，所以要找批量端点，并分输入/输出 */
    for (i = 0; i < phost_iface->desc.bNumEndpoints; i++) {
        phost_endp = phost_iface->endpoint + i;
        if (phost_endp) {
            pendp_desc = &phost_endp->desc;
            if (usb_endpoint_is_bulk_in(pendp_desc))
                /* 记下 bulk IN 端点 */;
            if (usb_endpoint_is_bulk_out(pendp_desc))

原文这一段的 for 条件被截断成 for (i = 0;i nr_endpoint; i++)，按上下文还原成 bNumEndpoints。原文的 usb_get_dev() 也没有对应释放点，实际驱动会在 disconnect 里 usb_put_dev，原文未体现。

端点配置是 USB WiFi 的核心元数据：

端点类型 用途 判断宏
Bulk IN 接收数据帧 usb_endpoint_is_bulk_in
Bulk OUT 发送数据帧 usb_endpoint_is_bulk_out
Interrupt IN 芯片事件上报（C2H） usb_endpoint_is_int_in
控制端点 EP0 寄存器读写 内核自带，驱动不用找

WiFi 驱动功能多，一般要配好几个输入输出端点：一个 bulk IN 收数据、一个 bulk OUT 发数据、一个 interrupt IN 收异步事件、EP0 读寄存器。

寄存器读写（_read8/16/32）走控制传输，批量数据（_read_port/_write_port）走 bulk 传输。这两条路在 USB 上的根本区别是延迟：控制传输要经过 setup 阶段，一次几十微秒；bulk 传输一旦流水起来就是线速。

17.7 固件与 HTC：厂商私有的那一层 #

ath9k_htc 是 SoftMAC，但 MAC 以下的大半还在固件里。没有固件，probe 走不下去。

芯片 固件文件 说明
AR9271 htc_9271.fw 最常见的 USB 802.11n 模块方案
AR7010 + AR9280 htc_7010.fw USB 桥 + MAC/BB/RF 双芯片

文件放 /lib/firmware/，驱动用 request_firmware 取。加载分两段：先把固件整块推给设备（走 bulk OUT），再轮询寄存器等它回一句「起好了」，然后做 HTC 握手。哪一步超时，probe 就返回负值，dmesg 里是 ath9k_htc: Failed to initialize the device 一类的话。

固件缺一个文件就整块不能用。这不是降级运行，是直接不工作。调这类驱动的第一步永远是 ls /lib/firmware/htc_*.fw。

HTC 是 Host Target Communication，主机与目标固件之间的通信。Atheros 自己定的一层协议，把「发一帧」「收一帧」「配个参数」统一切成消息，再塞进 USB 的批量端点传出去。

关键在这一句：HTC 是厂商私有的，既不是 802.11 标准的一部分，也不是 USB 标准的一部分。 换一颗芯片，这套协议整套换掉，能复用的只有「分帧加端点分发」这个思路。

HTC 之上还有一层 WMI（Wireless Module Interface），负责「说什么」：改信道、加 BSS、配密钥、设聚合，都是 WMI 命令。HTC 只负责「怎么搬」。两层加起来，主机侧对固件的控制才完整。

HTC 帧头四个字节，贴在每个载荷前面：

c
struct htc_frame_hdr {
    u8     endpoint_id;   /* 逻辑端点号，决定这包给谁 */
    u8     flags;         /* 方向与选项位 */
    __be16 payload_len;   /* 载荷长度，大端 */
} __packed;

endpoint_id 是分发的钥匙。0 号端点留给 HTC 自身消息与命令控制，其余按帧类别分。payload_len 用大端，跟 802.11 帧里那些描述字段一个规矩，取值前过 be16_to_cpu。这一位填错，表现是「能扫到 AP、能关联，一打流就挂」——载荷被截断，帧校验永远过不了。

18.1 URB 是什么 #

USB 设备通信不用 I/O 内存和 I/O 端口，用 URB（USB Request Block）。URB 在整个 USB 子系统里相当于无线设备里的「电波」——主机与设备之间的每一次通信都由 URB 承载。

一次完整 URB 流程五步：

  1. usb_alloc_urb() 创建并分配 URB。
  2. 创建并分配 DMA 缓冲区。
  3. 按传输量选择类型初始化，批量数据用 usb_fill_bulk_urb()。
  4. 提交到 USB 核心 usb_submit_urb()。
  5. 提交成功后，完成函数被 USB 核心调用。

第 5 步是 USB 驱动的灵魂：提交是异步的，结果回调。这跟 SDIO 的 wait_for_completion 同步等完全是两种心智模型。

十九、USB 的数据收发 #

19.1 接收初始化 #

c
int xxxwifi_init_recv(_adapter *padapter)
{
    struct recv_priv *precvpriv = &padapter->recvpriv;
    struct recv_buf *precvbuf;
    int i, res = _SUCCESS;

    tasklet_init(&precvpriv->recv_tasklet,
                 (void (*)(unsigned long))rtl8188eu_recv_tasklet,
                 (unsigned long)padapter);

    /* 1. 一个中断 URB，用来收芯片的异步事件 */
    precvpriv->int_in_urb = usb_alloc_urb(0, GFP_KERNEL);
    precvpriv->int_in_buf = rtw_zmalloc(INTERRUPT_MSG_FORMAT_LEN);

    _rtw_init_queue(&precvpriv->free_recv_buf_queue);
    _rtw_init_queue(&precvpriv->recv_buf_pending_queue);

    /* 2. 预分配一批 recv_buf（NR_RECVBUFF 个） */
    precvpriv->pallocated_recv_buf =
        rtw_zmalloc(NR_RECVBUFF * sizeof(struct recv_buf) + 4);
    precvbuf = (struct recv_buf *)precvpriv->precv_buf;
    for (i = 0; i < NR_RECVBUFF; i++) {
        _rtw_init_listhead(&precvbuf->list);
        _rtw_spinlock_init(&precvbuf->recvbuf_lock);
        precvbuf->alloc_sz = MAX_RECVBUF_SZ;
        res = rtw_os_recvbuf_resource_alloc(padapter, precvbuf);
        precvbuf->ref_cnt = 0;
        precvbuf->adapter = padapter;
        precvbuf++;
    }
    precvpriv->free_recv_buf_queue_cnt = NR_RECVBUFF;
    skb_queue_head_init(&precvpriv->rx_skb_queue);
    return res;
}

NR_RECVBUFF 个缓冲区一次性备好，插到 free_recv_buf_queue 里。这是 USB WiFi 的常见做法：URB 是异步的，你必须在有空 URB 可用时立刻提交，不能等数据到了才分配内存。

给每个 recv_buf 配 URB 与 DMA 缓冲：

c
int rtw_os_recvbuf_resource_alloc(_adapter *padapter, struct recv_buf *precvbuf)
{
    struct dvobj_priv *pdvobjpriv = adapter_to_dvobj(padapter);
    struct usb_device *pusbd = pdvobjpriv->pusbdev;
    int res = _SUCCESS;

    precvbuf->irp_pending = _FALSE;
    precvbuf->purb = usb_alloc_urb(0, GFP_KERNEL);   /* 一个批量 URB */
    precvbuf->pskb = NULL;
    precvbuf->reuse = _FALSE;
    precvbuf->pallocated_buf = precvbuf->pbuf = NULL;
    precvbuf->pdata = precvbuf->phead = precvbuf->ptail = precvbuf->pend = NULL;
    precvbuf->transfer_len = 0;
    precvbuf->len = 0;

#ifdef CONFIG_USE_USB_BUFFER_ALLOC_RX
    precvbuf->pallocated_buf = rtw_usb_buffer_alloc(pusbd,
                                (size_t)precvbuf->alloc_sz,
                                &precvbuf->dma_transfer_addr);
    precvbuf->pbuf = precvbuf->pallocated_buf;
    if (precvbuf->pallocated_buf == NULL)
        return _FAIL;
#endif
    return res;
}

rtw_usb_buffer_alloc 拿的是 USB 核心的 DMA 一致性缓冲（usb_buffer_alloc/usb_alloc_coherent 一系）。URB 的 transfer_buffer 必须指向这种内存，普通 kmalloc 在没开 DMA 一致性的平台上会出缓存一致性问题。

到这里 URB 和 DMA 缓冲都建好了，但还没提交。真正提交在 usb_read_port。

19.2 读端口：提交 URB #

c
static u32 usb_read_port(struct intf_hdl *pintfhdl, u32 addr, u32 cnt, u8 *rmem)
{
    struct recv_buf *precvbuf = (struct recv_buf *)rmem;
    _adapter *adapter = pintfhdl->padapter;
    struct dvobj_priv *pdvobj = adapter_to_dvobj(adapter);
    struct usb_device *pusbd = pdvobj->pusbdev;
    PURB purb;
    unsigned int pipe;
    int err;

    rtl8188eu_init_recvbuf(adapter, precvbuf);
    precvpriv->rx_pending_cnt++;

    purb = precvbuf->purb;
    /* 把 DMA FIFO 地址翻译成 pipe handle：不同队列用不同管道 */
    pipe = ffaddr2pipehdl(pdvobj, addr);

    usb_fill_bulk_urb(purb, pusbd, pipe,
                      precvbuf->pbuf,
                      MAX_RECVBUF_SZ,
                      usb_read_port_complete,   /* 完成回调 */
                      precvbuf);                /* context 是 precvbuf */

    err = usb_submit_urb(purb, GFP_ATOMIC);
    return err ? _FAIL : _SUCCESS;
}

三处值得盯：

  1. ffaddr2pipehdl —— 芯片有多个接收队列（普通数据、管理帧、高优先级），每个队列在 USB 上映射成一条独立 pipe。填错队列地址，表现是「管理帧能收到、数据帧收不到」，或者反过来。
  2. usb_submit_urb 的 GFP_ATOMIC —— 说明这段在软中断/原子上下文里跑，不许睡。这也是前面要预分配缓冲、不能在这里 kmalloc(GFP_KERNEL) 的原因。
  3. precvbuf 当上下文一路传 —— 完成回调里就靠它找回归属的缓冲。

19.3 完成回调：把 skb 交上去 #

c
static void usb_read_port_complete(struct urb *purb, struct pt_regs *regs)
{
    struct recv_buf *precvbuf = (struct recv_buf *)purb->context;

    switch (purb->status) {
    case 0:            /* 成功 */
        break;
    case -ESHUTDOWN:   /* 设备已断开，直接退出 */
        return;
    default:           /* 其他错误：重提交 */
        goto handle_out;
    }

    if (purb->actual_length) {
        /* 剥 USB 私有头，转成 skb，交给网络栈 */
    }
handle_out:
    /* 重新提交，保持 pipe 上始终有 URB 在飞 */

}

这个「收完就立刻重提交」的循环是 USB WiFi 吞吐的根本。断了一个 URB，对应的 queue 就停了，表现是收着收着不动了。

19.4 发送路径 #

c
u32 usb_write_port(struct intf_hdl *pintfhdl, u32 addr, u32 cnt, u8 *wmem)
{
    struct xmit_buf *pxmitbuf = (struct xmit_buf *)wmem;
    struct xmit_frame *pxmitframe = (struct xmit_frame *)pxmitbuf->priv_data;
    struct usb_device *pusbd = pdvobj->pusbdev;
    struct pkt_attrib *pattrib = &pxmitframe->attrib;
    PURB purb;
    unsigned int pipe;
    int status;

    purb = pxmitbuf->pxmit_urb[0];
    pipe = ffaddr2pipehdl(pdvobj, addr);

    usb_fill_bulk_urb(purb, pusbd, pipe,
                      pxmitframe->buf_addr,      /* = pxmitbuf->pbuf */
                      cnt,

发送侧的 ffaddr2pipehdl 同样按「目标队列」选 pipe。芯片一般有 AC（高优先级）、MG（管理）、BK/BE/VI/VO 几档，QoS 映射做错，重传率会飙。发送侧的 URB 也是预分配的：pxmitbuf->pxmit_urb[0] 在 xmit_buf 建立时已经 usb_alloc_urb 过，因为发送频率高，每次分配太贵。

19.6 ath9k_htc 的收发路径 #

回到真实驱动。ath9k_htc 的收发会绕开「一根 pipe 收所有东西」的简化，改成按 HTC 端点分流。

USB 接口层先声明自己认识哪些端点。做法是按 HTC 端点个数各分配一条接收 URB（hif_dev->htc_handle.rx_urb[]），另加一根独立的 interrupt URB 走事件通道。下面三段代码是按源码框架整理的结构示意，函数体细节以你手上的驱动树为准。

四条路各干各的：

通路 端点类型 承载什么 谁提交
RX bulk bulk IN 从固件下来的 802.11 帧，HTC 头 + 载荷 ath9k_hif_usb_rx_cb 完成后立刻重提交
TX bulk bulk OUT 打给固件的帧，HTC 头 + 载荷 ath9k_htc_tx → ath9k_hif_usb_tx
事件 interrupt IN 固件主动上报的事件与 WMI 回复 ath9k_hif_usb_regout_cb
控制 EP0 控制传输 寄存器读写、固件下载 内核 USB 核心

发送从 mac80211 的 .tx 回调进来：

c
static void ath9k_htc_tx(struct ieee80211_hw *hw,
                         struct ieee80211_tx_control *control,
                         struct sk_buff *skb)
{
    struct ath9k_htc_priv *priv = hw->priv;
    u8 endpoint;

    /* 1. 按帧类型选 HTC 端点：管理帧走 mgmt 端点，数据帧按 AC 分 */
    endpoint = ath9k_htc_get_endpoint(priv, skb);

    /* 2. 在载荷前面补 struct htc_frame_hdr，这一步在 HIF 层做 */
    /* 3. 交给 HIF 层做实际 USB 传输 */
    ath9k_hif_usb_tx(priv->hif_dev, endpoint, skb);
}

ath9k_hif_usb_tx 里做的是「拼 URB + 提交」：

c
static int ath9k_hif_usb_tx(struct hif_device_usb *hif_dev,
                            u8 endpoint, struct sk_buff *skb)
{
    struct urb *urb = usb_alloc_urb(0, GFP_ATOMIC);
    void *transfer = kmalloc(skb->len + sizeof(struct htc_frame_hdr),
                             GFP_ATOMIC);

    /* HTC 头贴在真实载荷前面，两段一起发 */
    hdr = (struct htc_frame_hdr *)transfer;
    hdr->endpoint_id = endpoint;
    hdr->flags       = 0;
    hdr->payload_len = cpu_to_be16(skb->len);
    memcpy(transfer + sizeof(*hdr), skb->data, skb->len);

    usb_fill_bulk_urb(urb, hif_dev->udev,
                      hif_dev->tx_pipe,
                      transfer, skb->len + sizeof(*hdr),
                      ath9k_hif_usb_tx_cb, hif_dev);
    usb_submit_urb(urb, GFP_ATOMIC);
    return 0;
}

这段要看出三件事。HTC 头是主机侧自己加的，固件那头靠它认端点。endpoint_id 决定固件把包交给谁：管理帧和数据的处理路径不同，端点填串，表现是「能发 Beacon 但发不出数据」。GFP_ATOMIC 说明 .tx 回调不许睡，URB 和缓冲得当场分配。

接收由完成回调驱动：

c
static void ath9k_hif_usb_rx_cb(struct urb *urb)
{
    struct sk_buff *skb = (struct sk_buff *)urb->context;
    struct hif_device_usb *hif_dev = (struct hif_device_usb *)skb->dev;
    struct htc_frame_hdr *htc_hdr;
    u16 payload_len;

    switch (urb->status) {
    case 0:
        break;
    case -ESHUTDOWN:
        return;                 /* 设备走了，别再提交 */
    default:
        goto resubmit;
    }

    /* 剥 HTC 头，按 endpoint_id 分派 */
    htc_hdr     = (struct htc_frame_hdr *)skb->data;
    payload_len = be16_to_cpu(htc_hdr->payload_len);
    skb_pull(skb, sizeof(*htc_hdr));

    if (htc_hdr->endpoint_id == 0)
        ath9k_htc_rx_msg(hif_dev, skb, payload_len);  /* HTC/WMI，控制路径 */
    else
        ieee80211_rx(hif_dev->hw, skb);  /* 数据帧，直接交给 mac80211 */

resubmit:
    usb_submit_urb(urb, GFP_ATOMIC);
}

注意 ieee80211_rx 这一句。SoftMAC 驱动收到的已经是剥干净的 802.11 帧，往里丢就完事；分片重组、重复检测、解密、转 802.3、送给网络栈，全在 mac80211 里。fullmac 驱动就做不到这么省事——帧在固件里已经是 802.3 了。

跟 rtl8188eu 那条路对比一下：

发送入口 ndo_start_xmit → usb_write_port ieee80211_ops.tx → ath9k_hif_usb_tx

19.7 断开 #

c
static void xxx_disconnect(struct usb_interface *intf)
{
    /* 1. stop 网络设备：unregister_netdev / netif_carrier_off */
    /* 2. kill 所有在飞的 URB：usb_kill_urb */
    /* 3. 释放 recv_buf / xmit_buf 里的 URB 与 DMA 缓冲 */

    /* 5. usb_put_dev */

顺序和 SDIO 的 if_sdio_remove 一致：先停业务、再杀传输、最后放资源。usb_kill_urb 会等到完成回调或错误返回才返回，所以它必须在释放 precvbuf 之前。反过来的顺序是 USB 驱动最经典的 use-after-free。

原文这份 USB 稿件写到 usb_read_port 收尾就断了，xxx_disconnect 只是按框架补全，具体实现未验证，以你手上的驱动树为准。

二十一、SPI 接口的 WiFi 驱动 #

前面十几章讲的都是 SDIO 和 USB。SPI 是第三种接口，也是嵌入式里最容易被低估的一种：几乎每颗 SoC 都有 SPI 控制器，接一颗 WiFi 模组只多占 5 根线，代价是速率和中断要自己想办法。

这一章的样本是 drivers/net/wireless/libertas/if_spi.c，Marvell Libertas 系列的 SPI 版，内核 2.6.35.6 时代。它跟第十三到十六章那个 if_sdio.c 是同一族芯片的两个接口版本，正好拿来对照。

21.1 SPI 与 SDIO 差在哪 #

先看物理层。SPI 是同步串行，四根信号线加一根片选：

信号 方向 作用
SCLK 主机 → 从机 时钟，由主机产生，速率固定
MOSI 主机 → 从机 主机发、从机收
MISO 从机 → 主机 从机发、主机收
CS 主机 → 从机 片选，低电平选中，一根 CS 挂一个设备

关键一点：SPI 是全双工的。每个时钟周期，主机移出一位到 MOSI，同时从 MISO 移入一位。所以一次 spi_transfer 天然是「发 N 字节、同时收 N 字节」，收发长度必须相等。想只读不写，得发 N 个哑字节；想只写不读，收到的数据丢掉。

SDIO 不是这样。它有独立的 CMD 线和 DAT0-3 数据线，命令和数据分两条路走，数据宽度可以从 1 线切到 4 线，还规定了一条中断通路（复用 DAT1）。速度能上到几十 MB/s，中断是协议的一部分。SPI 那四根线里，一根专管「从机有事找你」的都没有。

物理层的差别直接推出协议层的差别：

维度 SDIO SPI
命令与数据 分开，CMD 线专管命令 不分，命令也是往 MOSI 写字节
寄存器访问 CMD52 单字节读写 先写地址再读写数据，靠芯片的私有时序
批量数据 CMD53 块/字节模式 连续读写字，长度自己数
中断 协议内建（DAT1） 协议里没有
多设备 一条总线可挂多个 function 一根 CS 挂一个，多设备多根 CS
速率 高，4 线高速到 50MB/s 级 低，SCLK 常见 20~50MHz
硬件复杂度 需要 SD 控制器 任意 SPI 控制器

表格最后两行的组合很残酷：SPI 硬件便宜，但速率上不去，还得自己解决中断。

21.2 「数据来了」这件事，SPI 得自己解决 #

这是 SPI WiFi 和 SDIO WiFi 最本质的差别，值得单独一节。

SDIO 卡有数据要上报，拉中断线，主机侧 sdio_claim_irq 注册的回调被调用。USB 设备有事件要上报，往 interrupt IN 端点塞数据，主机的 URB 完成回调被调用。两条路都是「协议规定好的异步通知」，驱动只管收。

SPI 什么都没有。它四根线里没有一根是给从机主动发信号用的。从机（WiFi 芯片）想把「我有数据」告诉主机，只有两个办法：

  1. 额外拉一根 GPIO，芯片的 INT 引脚接到 SoC 的一个 GPIO 上，配成下降沿触发中断。
  2. 主机轮询，定时读芯片的状态寄存器，看有没有数据位被置起来。

第一种是主流做法，libertas 的 SPI 版走的就是这条：

c
err = request_irq(spi->irq, if_spi_host_interrupt,
                  IRQF_TRIGGER_FALLING, "libertas_spi", card);

spi->irq 这个字段不是 SPI 协议给的，是板级代码在注册 spi_board_info 时填的：

c
static struct spi_board_info cm_x270_spi_devices[] = {
    {
        .modalias     = "libertas_spi",
        .irq          = PXA_GPIO_TO_IRQ(GPIO_LIBERTAS_INT),
        .max_speed_hz = 20000000,
        .mode         = SPI_MODE_0,
        .bus_num      = 2,
        .chip_select  = 0,
    },
};

也就是说，这根中断线在 SPI 协议之外，属于板级设计。同一颗芯片换一块板子，接的 GPIO 号就变了，驱动树里的 spi_board_info 跟着改。写这类驱动第一件事是问硬件要原理图，确认 INT 引脚接哪个 GPIO、极性是高还是低。

第二种轮询方案在低速率、低功耗场景还有位置，但延迟和 CPU 占用都难看。真要在 SPI 上做 WiFi，别省那根线。

中断回调能干什么，也很受限：

c
static irqreturn_t if_spi_host_interrupt(int irq, void *dev_id)
{
    struct if_spi_card *card = dev_id;

    /* 中断上下文不能睡，SPI 传输会睡，所以只做唤醒 */
    up(&card->spi_ready);
    return IRQ_HANDLED;
}

一个 up()，没了。为什么？SPI 传输要睡（spi_sync 内部要等完成量），中断上下文不许睡。所以中断里只能把等待的线程叫醒，真正的读寄存器、判断事件类型、搬数据，全在那个线程里干。

这条约束跟十六章里 SDIO 那个「中断里不能 sdio_readsb」是同一条。区别是 SDIO 至少有中断可注册，SPI 得先求硬件给你一根线。

21.3 SPI 控制器与 SPI 设备的注册 #

看 WiFi 驱动之前先把 SPI 那套注册流程走一遍，不然后面全是黑箱。

板级初始化里向平台总线注册 SPI 控制器，再登记挂在上面的设备：

c
static void __init cmx270_init_spi(void)
{
    pxa2xx_set_spi_info(2, &cm_x270_spi_info);
    spi_register_board_info(ARRAY_AND_SIZE(cm_x270_spi_devices));
}

pxa2xx_set_spi_info 把控制器的描述信息挂到平台设备上，spi_register_board_info 把设备清单塞进一个全局链表 board_list。两边都只是登记，还没动硬件。

控制器驱动匹配上之后跑 probe：

c
static int __init pxa2xx_spi_init(void)
{
    return platform_driver_probe(&driver, pxa2xx_spi_probe);
}

pxa2xx_spi_probe 里按 cm_x270_spi_info 实例化一个 spi_master，申请资源，初始化队列，然后 spi_register_master 把它挂到设备模型上。最后一步是扫设备：

c
/* drivers/spi/spi.c 一侧 */
scan_boardinfo(master);

scan_boardinfo 遍历 board_list，把总线号和 master 对得上的设备挑出来，逐个 spi_new_device 注册成 spi_device。到这一步，控制器和设备都在 SPI 总线上了，就等驱动来认。

这个顺序有个坑：控制器 probe 的时候才扫 board_list，所以 spi_register_board_info 必须在控制器 probe 之前调用，也就是板级 __init 里，不能放到模块加载里。放晚了，设备不在总线上，驱动再注册也匹配不到。

21.4 spi_driver 与 if_spi_probe #

WiFi 驱动那一侧：

c
static int __init if_spi_init_module(void)
{
    int ret;

    lbs_deb_enter(LBS_DEB_SPI);
    printk(KERN_INFO "libertas_spi: Libertas SPI driver\n");
    ret = spi_register_driver(&libertas_spi_driver);
    lbs_deb_leave_args(LBS_DEB_SPI, "ret %d", ret);
    return ret;
}

libertas_spi_driver 是标准的 spi_driver：

c
static struct spi_driver libertas_spi_driver = {
    .probe   = if_spi_probe,
    .remove  = __devexit_p(if_spi_remove),
    .suspend = if_spi_suspend,
    .resume  = if_spi_resume,
    .driver  = {
        .name  = "libertas_spi",
        .owner = THIS_MODULE,
    },
};

注意它没有 .id_table。SPI 的匹配靠 driver.name 跟 spi_board_info.modalias 做字符串比较，跟 USB/SDIO 那种 VID/PID 表是两套机制。modalias 写错一个字符，设备就永远匹配不上，而且不报错，/sys/bus/spi/devices/ 下有设备、/sys/bus/spi/drivers/ 下有驱动，就是不见绑定。

probe 里按顺序走六步：

c
static int if_spi_probe(struct spi_device *spi)
{
    struct if_spi_card *card;
    struct lbs_private *priv;
    int err;

    /* 1. 建立私有对象，描述这颗卡 */
    card = kzalloc(sizeof(struct if_spi_card), GFP_KERNEL);
    card->spi = spi;
    spi_set_drvdata(spi, card);

    /* 2. 下固件：先 helper 再主固件 */
    err = if_spi_prog_helper_firmware(card, helper_fw_name);
    err = if_spi_prog_main_firmware(card, main_fw_name);

    /* 3. 挂进 libertas 公共层，拿到 net_device */
    priv = lbs_add_card(card, &spi->dev);
    card->priv = priv;

    /* 4. 把接口相关的回调告诉 libertas 层 */
    priv->hw_host_to_card = if_spi_host_to_card;
    priv->hw_wakeup_firmware = if_spi_wakeup_firmware;

    /* 5. 接收线程 + 中断 */
    card->spi_thread = kthread_run(lbs_spi_thread, card, "lbs_spi_thread");
    err = request_irq(spi->irq, if_spi_host_interrupt,
                      IRQF_TRIGGER_FALLING, "libertas_spi", card);

    /* 6. 启动：注册 wiphy、注册 netdev */
    err = lbs_start_card(priv);
    return 0;
}

拆开看。

第一步建 struct if_spi_card，它是「SPI 接口私有」的那一半，跟 lbs_private（libertas 公共层）分开。这个分法跟 SDIO 版一模一样，理由也一样：libertas 要能同时支持 SPI、SDIO、USB 三种接口，公共层不能知道下面接的是哪个。

第二步下固件，if_spi_prog_helper_firmware 和 if_spi_prog_main_firmware 两段。这跟 SDIO 版要 helper.bin + 主 bin 是同一件事。

固件在 WiFi 设备里干什么，值得说清楚：它是一段跑在 WiFi 芯片上的程序，系统上电后由 WLAN 驱动下载进去。它负责硬件接口控制、数据缓冲、802.11 与 802.3 帧类型转换、MAC 层管理、MAC 中断管理。发数据时，主机把 802.3 帧交给固件，固件转成 802.11 帧发出去；收数据时，固件把 802.11 帧转回 802.3 交给主机。

这个分工解释了一个常见困惑：为什么 fullmac 驱动里看不到 802.11 帧的处理代码？因为转换在固件里。内核眼里这颗 WiFi 就是个以太网口，net_device 收到的一直是 802.3 帧。也正因为这样，fullmac 驱动才能短到几百行——802.11 那一整套它根本不管。

第三步调 lbs_add_card。它内部 alloc_netdev 申请网络设备，挂上 lbs_netdev_ops：

c
static const struct net_device_ops lbs_netdev_ops = {
    .ndo_open            = lbs_dev_open,
    .ndo_stop            = lbs_eth_stop,
    .ndo_start_xmit      = lbs_hard_start_xmit,
    .ndo_set_mac_address = lbs_set_mac_address,
    .ndo_tx_timeout      = lbs_tx_timeout,
    .ndo_set_multicast_list = lbs_set_multicast_list,
    .ndo_change_mtu      = eth_change_mtu,
    .ndo_validate_addr   = eth_validate_addr,
};

同一个函数里还建了两个执行体，后面全靠它们：

c
init_waitqueue_head(&priv->waitq);
priv->main_thread = kthread_run(lbs_thread, dev, "lbs_main");
priv->work_thread = create_singlethread_workqueue("lbs_worker");
INIT_DELAYED_WORK(&priv->assoc_work, lbs_association_worker);
INIT_DELAYED_WORK(&priv->scan_work, lbs_scan_worker);
INIT_WORK(&priv->mcast_work, lbs_set_mcast_worker);

lbs_thread 是命令与事件的主线程，work_thread 干关联、扫描、多播这些可以延后的活。「一类事件统一到一个线程处理」是这类驱动的常见结构，不是为了好看，是因为底层 SPI 传输会睡，不能在软中断里直接干。

第四步把 if_spi_host_to_card 这个函数指针交给 libertas 层。这一行是整个分层的关键：libertas 层要发数据时，只管调 priv->hw_host_to_card，完全不关心下面是 SPI 还是 SDIO。

第五步开线程、注册中断。lbs_spi_thread 负责收包和命令响应，中断只负责叫醒它。

第六步 lbs_start_card，调用链：

text
lbs_start_card
  -> lbs_cfg_register
       -> wiphy_register        /* 无线能力对 cfg80211 可见 */
       -> register_netdev       /* 网络设备对网络栈可见 */

到这一步，wlan0 才真正出现在 ip link 里。

21.5 三个情景：把调用链走一遍 #

光看注册不够，得看数据怎么动。分三个情景。

情景一：上层要发数据

网络栈调 lbs_hard_start_xmit，它属于 lbs_netdev_ops。这个函数不做传输，只做三件事：把 skb 拷进自己的缓冲、wake_up(&priv->waitq) 叫醒 lbs_thread、返回。

真正的发送在 lbs_thread 里：

text
lbs_hard_start_xmit
  -> 拷包 + wake_up(&priv->waitq)
       -> lbs_thread 被唤醒
            -> lbs_execute_next_command
                 -> lbs_submit_command
                      -> priv->hw_host_to_card      /* = if_spi_host_to_card */
                           -> master->transfer      /* SPI 控制器 */
                                -> queue_work(pump_messages)
                                     -> pump_transfers  /* 真正摸硬件 */

if_spi_host_to_card 最终落到 SPI 控制器实例的 master->transfer，这个指针在 pxa2xx_spi_probe 里注册。transfer 本身也是异步的——它把活排进控制器自己的工作队列：

c
if (drv_data->run == QUEUE_RUNNING && !drv_data->busy)
    queue_work(drv_data->workqueue, &drv_data->pump_messages);

那个工作队列也在 pxa2xx_spi_probe 里建：

c
INIT_WORK(&drv_data->pump_messages, pump_messages);
drv_data->workqueue = create_singlethread_workqueue(
                          dev_name(drv_data->master->dev.parent));

pump_messages 再调 pump_transfers 完成硬件搬运。

这条链绕得很，绕的原因值得说：

  • lbs_thread 的存在，是为了把「发包」「收事件」「命令响应」统一到一个上下文。网络栈催得急，ndo_start_xmit 要尽快返回，剩下的交给线程。
  • hw_host_to_card 用回调，是为了让 libertas 层跟接口解耦。不这么写，libertas 里就到处是 if (是 SPI) ... else if (是 SDIO) ...。
  • 控制器里再套一层 worker，是为了让「上层线程」和「硬件搬运」异步。SPI 总线上一次只能有一个传输，谁的包都得排队，队列在控制器里统一管更顺。

一句话：三层 worker 不是设计过度，是「SPI 传输会睡」这一个约束逐层推出来的。

情景二：设备收到数据

WiFi 芯片有数据上来，拉 INT 引脚，触发 if_spi_host_interrupt。这个函数只做一件事：up(&card->spi_ready)。

睡在这个信号量上的是 lbs_spi_thread，probe 里建的。它醒了之后读状态寄存器：

c
err = spu_read_u16(card, IF_SPI_HOST_INT_STATUS_REG, &hiStatus);

hiStatus 是位图，每一位对应一种事件。看到 IF_SPI_HIST_RX_UPLOAD_RDY，说明有数据包等着：

c
if (hiStatus & IF_SPI_HIST_RX_UPLOAD_RDY)
    err = if_spi_c2h_data(card);

if_spi_c2h_data 干的是所有网卡接收都干的事：dev_alloc_skb 申请缓冲、从 SPI 读数据填进去（可以直接读，也可以用 DMA）、剥掉接口私有头、lbs_process_rxed_packet 处理一下、最后 netif_rx 交给网络栈。

情景三：命令响应

同一个线程，另一个分支：

c
if (hiStatus & IF_SPI_HIST_CMD_UPLOAD_RDY)
    err = if_spi_c2h_cmd(card);

命令响应不能让网络栈处理——网络栈眼里这只是一块网卡，不懂「改信道」「查统计」这些厂商命令。所以 if_spi_c2h_cmd 把响应塞回 priv->resp_buf，然后由 lbs_thread 收尾：

c
if (priv->resp_len[resp_idx]) {
    spin_unlock_irq(&priv->driver_lock);
    lbs_process_command_response(priv, priv->resp_buf[resp_idx],
                                 priv->resp_len[resp_idx]);
    spin_lock_irq(&priv->driver_lock);
    priv->resp_len[resp_idx] = 0;
}

数据走网络栈，命令走 libertas 控制层。两条路在 lbs_spi_thread 里分开，靠的就是状态寄存器那一位。

21.6 SPI WiFi 的芯片与限制 #

真正量产过的 SPI 接口 WiFi 芯片不多，这不是巧合。

芯片/系列 驱动 备注
Marvell 88W8686（SPI 模式） libertas/if_spi.c 本章样本，fullmac
Marvell 88W8385 libertas/if_spi.c 更早一代
TI CC3000 厂商树 / wilink 一系 简易模组，SPI 接口
Espressif ESP8089 厂商树 少见

限制集中在三处：

速率。 SPI 的 SCLK 常见 20~50MHz，一个时钟一位，算下来几 MB/s 到十几 MB/s 的量级。这还是理论峰值，实际有命令开销、状态轮询、时序间隙，能跑出 2~3MB/s 就算好。对比 SDIO 4 线高速和 USB2.0，SPI 天生不在一个量级。所以 SPI WiFi 只出现在「带宽不重要、成本敏感」的场景：传感器节点、老旧工控板、给 MCU 加个无线口。

中断。 前面说过，协议里没有。板子忘了把 INT 引脚接上，驱动就只能轮询，延迟和功耗一起上去。有些模组干脆把 INT 和某个 GPIO 复用，软件要额外配一遍引脚功能。

时序。 SPI 有四种模式（CPOL/CPHA 组合），WiFi 芯片常常只支持其中一种，配错就是读回来全是 0xFF 或 0x00。spi_board_info 里的 mode 字段、max_speed_hz 都要跟芯片手册对上。这一条在调试时最费时间，因为「配错了」和「芯片没响应」的现象完全一样。

一句话总结 SPI WiFi 的定位：能用，但只在「引脚数比带宽重要」的地方用。 真要做高吞吐的无线，SDIO 或 USB 才是答案。

21.7 三种接口选型：先问六个问题 #

你关心什么 先选 理由
要吞吐、引脚也够 SDIO 4 线 + 协议内建中断，几十 MB/s
引脚紧张、可热插拔 USB 2 根线，枚举原生支持
引脚极紧、带宽无所谓 SPI 5 根线，任意 SoC 都有控制器
要低功耗 SDIO 省电模式成熟，能配合 DTIM 睡
没有 SD 控制器 USB 或 SPI SDIO 必须占一路 MMC
板子已经焊死、不换芯片 看芯片支持哪个 三者不能互转，芯片定了接口就定了

最后一条最硬。三种接口之间没有软件层的兼容，一颗芯片支持哪种就是哪种，spi_board_info、sdio_device_id、usb_device_id 是三套完全不同的匹配机制。选型在硬件阶段就定死了，驱动只是把既定事实实现出来。

二十二、调试手段与常见故障 #

22.1 先看设备有没有被认出来 #

bash
## SDIO
ls /sys/bus/sdio/devices/
cat /sys/bus/sdio/devices/*/modalias

## USB
lsusb -t
ls /sys/bus/usb/devices/

## SPI
ls /sys/bus/spi/devices/
ls /sys/bus/spi/drivers/
cat /sys/bus/spi/devices/*/modalias

## 网络设备
ip link show
iw dev            ## 需要 nl80211 支持

SPI 那三行要连着看。设备目录下有条目、驱动目录下有 libertas_spi、但两边就是没绑定，八成是 modalias 跟 driver.name 不一致——SPI 靠字符串匹配，不匹配也不报错。

/sys/bus/sdio/devices/ 下没有条目，说明卡根本没被识别，问题在 MMC 层（时钟、供电、卡检测 GPIO），不是 WiFi 驱动的事。

bash
dmesg | grep -i firmware        ## 固件加载
ls /lib/firmware/libertas/
cat /proc/interrupts | grep -i "sdio\|mmc"   ## 中断有没有来
cat /proc/net/dev
ethtool -S wlan0                ## 厂商驱动常带私有统计

SDIO fullmac 的固件分两段（*_helper.bin + 主 bin），少一段都起不来。中断计数不涨，说明数据根本没到主机；涨了但包数不涨，说明读上来的东西没被认成合格帧——去看私有头的长度字段。

抓包：SDIO/USB 侧你只能抓到 802.3 帧。要看 802.11 帧，得用 monitor 模式的另一张网卡，或者芯片自带的调试口。

bash
iw dev wlan0 interface add mon0 type monitor
ip link set mon0 up

不是所有驱动都支持 monitor，厂商驱动经常把 add_interface 里的 monitor 分支砍掉。

22.2 故障速查 #

现象 先查什么 根因高频项
卡识别不出来 /sys/bus/sdio/devices/ 供电时序、卡检测 GPIO 极性反了、时钟超频
认到卡但没 wlan0 dmesg 里 probe 的返回值 wiphy_new 失败、register_netdev 之前就 return
没 wlan0 但 probe 报固件错 /lib/firmware/ helper 或主 bin 缺失、路径与 fw_table 不匹配
能扫描到但关联不上 关联帧的 RSN IE 加密套件、hw_value 信道号映射错
关联上但 DHCP 拿不到地址 netif_carrier 状态 netif_carrier_on 没在关联成功后调
小包正常大流量卡死 tx_pending、队列停位 netif_stop_queue 后没 wake_queue
跑一会儿丢包 /proc/interrupts 增速 URB 没重提交、SDIO 中断丢失
插拔几次后 oops remove/disconnect 顺序 先 free 后杀传输
传输速率只有一半 SDIO 位宽 1 线模式没切到 4 线
suspend 后唤不醒 wol_gpio、wol_criteria 唤醒源没配对，SDIO 时钟停了

SPI 有包但收不上来 INT 引脚的 /proc/interrupts 板级没接 INT 或极性配反，中断根本没来

22.3 几条准则 #

  • 先分清层。卡没认出来是 MMC 的事、没网卡是 netdev 的事、连不上是 802.11 的事。混着查必然绕圈。
  • printk 打在边界上。probe 入口、hw_host_to_card 入口、中断入口，三个点各一行，路径立刻清楚。
  • 一次只改一处。信道号、块大小、队列阈值三样一起调，你永远不知道是哪一样生效的。
  • 拿示波器看 SDIO 时钟和 CMD 线。供电跌落、时钟抖动、CMD 线被拉低，软件层查不出来的问题硬件一测就现原形。

二十三、易错点速查 #

# 易错点 正确做法
1 Wi-Fi 与 IEEE 802.11 当同义词 Wi-Fi 是商标，802.11 是标准，驱动写的是 802.11
2 照抄 CSMA/CD 理解无线 无线用 CSMA/CA，靠 ACK 和退避，不是冲突检测
3 把 ToDS/FromDS 两位忽略 这两位的组合决定 Address 1/2/3/4 的语义
4 把 802.11 认证当 WPA2 认证 802.11 认证在关联前，WPA2 是关联后的 4 次握手
5 认为 SSID 唯一 SSID 只在 ESS 内共用，BSSID 才是唯一标识
6 2.4G 14 个信道随便挑 只有 1/6/11 互不重叠，其他信道必然邻频干扰
7 cfg80211_ops 与 ieee80211_ops 混用 fullmac 填前者、softmac 填后者，两套不能同时挂
8 拿新内核头文件编老驱动 ieee80211_ops 成员逐版本增长，先核成员再编
9 mmc_rescan_try_freq 里换探测顺序 必须 SDIO → SD → MMC，顺序错了卡认成存储卡
10 sdio_enable_func 之前访问寄存器 先使能 I/O 再读写，否则读回 0xFF
11 不在 sdio_claim_host 保护下读写 所有 function 寄存器操作都要 claim，否则随机 EIO
12 在中断上下文调 sdio_writesb 它会睡，必须丢工作队列
13 remove 里先 destroy_workqueue 后 flush 先 flush 再 destroy，否则释放后仍有 worker
14 sdio_disable_func 在 sdio_release_irq 之前 先放中断再关功能
15 私有头偏移算错 buffer + 4 那个 4 是 type+len，别少别多
16 usb_read_port_complete 里不重提交 URB 必须重提交，否则管道停摆

18 ffaddr2pipehdl 传错队列地址 管理帧与数据帧是不同 pipe，传错就单向不通
19 disconnect 里先释放 recv_buf 后 usb_kill_urb 先杀 URB，否则 use-after-free
20 ndo_set_multicast_list 搬到新内核不改名 3.x 后改叫 ndo_set_rx_mode
21 还在填 wireless_handlers 写新驱动 WEXT 已退场（4.5 合入），新驱动走 nl80211
22 关联成功不调 netif_carrier_on 不调上层认为链路 down，DHCP 不启动
23 SDIO 1 线模式当 4 线用 位宽要显式切，速率差一半以上
24 忽略 .id_table 结尾的全零项 sdio_device_id 数组必须有全零结尾，否则越界匹配
25 想在无线里做冲突检测 半双工加上自身信号淹没，边发边听做不到，只能避免加确认
26 隐藏终端当成丢包查 A、C 互不可见时 RTS/CTS 才是解，先看 RTS 阈值是不是关了握手
27 把 Address 2 当源地址用 它是这一跳的发送者（TA），端到端的源地址在 Address 3
28 跳过 Frame Control 的多字节字段端序 空口是小端，从 buffer 取值必须过 le16_to_cpu
29 发送描述符里 Duration 不填 NAV 靠它生效，填 0 会让别人在你传大包时插进来
30 节电模式下按常开算延迟 收帧要等 Beacon 的 TIM，延迟是几百毫秒量级
31 抓包不加监听模式就看空口 普通网卡按目的地址过滤，别人的帧进不来
32 拿坏 FCS 的帧当流量统计 干扰重的环境坏帧占比很高，先剔掉再算
33 把 802.11 认证过了当成安全 开放认证谁都能过，真正的门在关联之后的 EAPOL
34 PSK 网络当企业网调 口令算 PMK，没有 RADIUS，抓空口拿不到 PMK
35 以为 HTC 是标准协议 HTC 是 Atheros 私有层，换芯片就整套换，能复用的只有分层思路

37 htc_frame_hdr.endpoint_id 随手填 端点号决定固件把包交给谁，管理帧与数据帧不同端点
38 ath9k_htc 缺固件还在查代码 先 ls /lib/firmware/htc_*.fw，缺文件 probe 直接失败，不降级
39 把 ath9k_hif_usb_driver 的 soft_unbind 删掉 去掉它，disconnect 被 USB 核心从中间抽走，就是 use-after-free
40 在 ieee80211_ops.tx 里睡 .tx 在原子上下文跑，URB 与缓冲必须 GFP_ATOMIC 当场分配
41 把 ieee80211_dataif_ops.ndo_start_xmit 当驱动函数 它指向 ieee80211_subif_start_xmit，是 mac80211 的，不是你的
42 SoftMAC 驱动里自己转 802.3 交给 ieee80211_rx，转换在 mac80211 里，别重写一遍
43 认为 SPI 有中断线可以注册 SPI 协议里没有，中断来自板级的额外 GPIO，spi->irq 是板级填的

47 spi_register_board_info 放到模块加载里 控制器 probe 时才扫 board_list，放晚了设备根本不在总线上
48 想在 SPI 上跑高吞吐 SPI 在几 MB/s 量级，要高吞吐换 SDIO 或 USB

50 拿 SPI 版驱动去套 SDIO 芯片 芯片定了接口就定了，三种接口之间没有软件层兼容
