本文讲什么：DRM/KMS 里四类核心对象——CRTC、plane、encoder、connector，外加 backing store 层的 GEM。逐个拆解数据结构的全字段、funcs/helper_funcs 两套 vtable、初始化函数的逐行流程，最后串成一条从设备树到点亮的完整通路。

本文不讲什么：DRM 子系统整体分层与图形栈（DRM/KMS 之上还有 libdrm、Mesa、Wayland）见《DRM 子系统：架构与图形栈全景》；HDMI 与 eDP 这两条具体接口的 PHY、PHY 时钟、HPD 电路见《DRM 显示接口：HDMI 与 eDP》；VOP 这颗显示处理器的寄存器级驱动见同目录 vop 驱动篇；fbdev 模拟层与 /dev/fb0 见《LCD 与 framebuffer》。

版本基线：素材对应 Linux 6.3 + RK3399（NanoPC-T4）。DRM 的 struct 字段随版本漂移很快，凡是有变化的地方我们逐个标注；未能核对上游源码的点直接写「未验证」，不猜。

一、四类对象的分工 #

先把一张图刻进脑子：一条显示通路上，数据流是 GEM/ framebuffer → plane → CRTC → encoder → (bridge) → connector → 显示器。控制流的反方向则是用户空间通过 atomic ioctl 把属性推给这四个对象。

用一句话概括各自职责：

  • plane：一块扫描源。它拿着一个 framebuffer，说明「显存的哪一块、以什么格式、多大范围」被取出来。对应显示处理器里的 layer。
  • CRTC：一个扫描输出单元。它把挂在自己身上的若干 plane 合成，再按一个 drm_display_mode（时序）把像素按 Pixel Clock 吐出去。对应显示处理器里「图层合成 + 时序生成」那一坨。
  • encoder：格式/电平转换。把 CRTC 输出的并行像素流转成某种串行接口信号（TMDS、LVDS、DSI、eDP）。RK3399 上多数 encoder 是「虚」的，真正的活交给了 bridge。
  • connector：物理插座。它代表「显示器插在哪个口上」，负责状态检测（插没插）、读 EDID、枚举这个口能跑哪些分辨率。
  • GEM：显存对象。它是 framebuffer 的后备存储，负责内存分配、handle 管理、mmap、dma-buf 共享。

四类对象对照表（字段名全部取自 6.3 头文件）：

对象 struct 头文件 关键字段 初始化函数 从属关系

plane drm_plane include/drm/drm_plane.h possible_crtcs / format_types / type / fb drm_universal_plane_init() 挂 mode_config.plane_list，指向 drm_framebuffer 与 drm_crtc

有三个容易混的点先摆清楚。

第一，plane 和 CRTC 的绑定是两个方向的位掩码。plane 用 possible_crtcs 说明自己能接哪几个 CRTC，CRTC 用 primary/cursor 指针记录 legacy 路径默认用哪个 plane。位掩码的位号就是 drm_crtc_index()。

第二，encoder 可以选择不实现任何硬件动作。drm_encoder 的所有 helper_funcs 全是可选的，RK3399 上 encoder 往往只做「挂 bridge」这一件事，真正的 PHY 配置在 bridge 里。这点后面第十、十一章展开。

第三，GEM 不是 KMS 对象。它没有 drm_mode_object，没有 ID 空间里的 modeset ID，用户空间看到的是 handle 和 dma-buf fd。framebuffer 才是两者之间的桥：drm_framebuffer.obj[] 里存 GEM 指针，drm_framebuffer.base 才是 KMS 对象。

二、CRTC：一个扫描输出单元 #

「CRTC」这个名字纯属历史包袱——Cathode Ray Tube Controller。现在它已经不控制任何阴极射线管了，但内核改名成本太高，就这么留下了。drm_crtc_funcs 的注释原话是：the name CRTC is simply historical, a CRTC may control LVDS, VGA, DVI, TV out, etc. connectors, not just CRTs。

CRTC 干三件事：

  • 配置显示模式（分辨率、刷新率、时序参数），输出对应的 Pixel Clock / HSYNC / VSYNC；
  • 从 plane 拿像素做合成，扫描出去；
  • 帧切换（page flip）、电源控制（ACTIVE 属性）、色彩调整（gamma LUT、CTM）。

时序参数是理解 CRTC 的入口。RGB 接口上至少三根信号线：Pixel Clock 每来一个时钟沿推进一个像素；HSYNC 一个脉冲换一行；VSYNC 一个脉冲换一帧。参数名字对照：

缩写 全称 含义 单位
HOZVAL / hdisplay horizontal display 行有效像素 pixel
HFPD / hfront porch horizontal front porch 行同步前沿肩 pixel clock
HSPW / hsync pulse horizontal sync pulse width 行同步脉宽 pixel clock
HBPD / hback porch horizontal back porch 行同步后沿肩 pixel clock
LINEVAL / vdisplay vertical display 帧有效行 line
VFPD vertical front porch 帧同步前沿肩 HSYNC
VSPW vertical sync pulse 帧同步脉宽 HSYNC
VBPD vertical back porch 帧同步后沿肩 HSYNC

把这些填进 struct drm_display_mode，CRTC 就有活干了。字段与上面的缩写一一对应：hdisplay、hsync_start（= hdisplay + HFPD）、hsync_end（= hsync_start + HSPW）、htotal（= hsync_end + HBPD），垂直方向同理。clock 是像素时钟，单位 kHz。

struct drm_display_mode 里存了两套时序。一套是逻辑时序（hdisplay / vdisplay 这套），就是用户空间看到的分辨率；另一套是 crtc_* 前缀的硬件时序，已经被 drm_mode_set_crtcinfo() 按隔行、双时钟、立体模式矫正过。clock 与 crtc_clock 的关系同理：8b/10b 编码的接口上两者差 10 倍是常态，别拿 clock 直接去配 PHY。

struct drm_display_mode {
        int clock;              /* Pixel clock in kHz */
        u16 hdisplay, hsync_start, hsync_end, htotal, hskew;
        u16 vdisplay, vsync_start, vsync_end, vtotal, vscan;
        u32 flags;              /* PHSYNC/NHSYNC/PVSYNC/NVSYNC/DBLCLK ... */
        int crtc_clock;
        u16 crtc_hdisplay, crtc_hblank_start, crtc_hblank_end;
        u16 crtc_hsync_start, crtc_hsync_end, crtc_htotal, crtc_hskew;
        u16 crtc_vdisplay, crtc_vblank_start, crtc_vblank_end;
        u16 crtc_vsync_start, crtc_vsync_end, crtc_vtotal;
        u16 width_mm, height_mm;
        u8 type;                /* DRM_MODE_TYPE_PREFERRED / DRIVER / USERDEF */
        bool expose_to_userspace;
        struct list_head head;
        char name[DRM_DISPLAY_MODE_LEN];
        enum drm_mode_status status;
        enum hdmi_picture_aspect picture_aspect_ratio;

flags 里最常踩的是极性：DRM_MODE_FLAG_PHSYNC 是高有效、NHSYNC 是低有效，垂直方向是 PVSYNC/NVSYNC。极性填反在模拟接口上表现为画面偏移，在数字接口上表现为直接无信号。

三、struct drm_crtc 的字段 #

全字段，来自 6.3 的 include/drm/drm_crtc.h。按用途分组看更清楚。

第一组是身份：dev、port、head、name、base、index。base 是 struct drm_mode_object，里面装着 id（基数树分配的唯一 ID，用户空间 GETCRTC 拿到的就是它）和对象类型。port 是 OF 设备节点，专门给 drm_of_find_possible_crtcs() 用——从设备树里 ports 子节点反查这个 CRTC 能接哪些输出。index 是它在 mode_config.crtc_list 里的位置，一旦分配终生不变，因为 possible_crtcs 位掩码就是拿它当位号的。不要把 index 和 base.id 搞混：index 是紧凑的数组下标，base.id 是给用户空间的 ID，两者数值不等。

第二组是 plane 关联：primary、cursor。注释写得很直白：this is only relevant for legacy IOCTL。SETCRTC / PAGE_FLIP 隐式用 primary，SETCURSOR 隐式用 cursor。走 atomic uAPI 的用户空间完全不看这两个指针，直接拿 plane ID 操作。

第三组是 legacy 状态镜像：cursor_x、cursor_y、enabled、mode、hwmode、x、y、gamma_size、gamma_store。这些字段 atomic 驱动一个都不该读——enabled 对应 drm_crtc_state.enable/active，mode 对应 drm_crtc_state.mode，x/y 对应 primary plane 的 crtc_x/crtc_y。内核用 drm_atomic_helper_update_legacy_modeset_state() 把这些镜像刷一遍，纯粹是让还在用 legacy ioctl 的老用户空间不至于瞎掉。

第四组是锁与提交：mutex（struct drm_modeset_lock）、commit_list、commit_lock。mutex 对 atomic 驱动而言保护的是 state；commit_list 跟踪挂起的 drm_crtc_commit，用来在 fb 清理时正确 stall。

第五组是调试与事件：debugfs_entry、crc、fence_context、fence_lock、fence_seqno、timeline_name、self_refresh_data。fence_context 由 dma_fence_context_alloc(1) 分配，CRTC 自己是一条 fence 时间线，timeline_name 格式化为 CRTC:%d-%s。

三个跨组要点。funcs 是 core 调用驱动 的 vtable，helper_private 是 helper 库调用驱动 的 vtable，同一个驱动两个都要填，位置分别是 drm_crtc_init_with_planes() 和 drm_crtc_helper_add()。scaling_filter_property 是 6.x 才有的成员，5.x 不存在。primary 即使走 atomic 也要传，因为 CRTC init 拿它兜底填 possible_crtcs。

c
struct drm_crtc {

        struct device_node *port;          /* drm_of_find_possible_crtcs() 用 */
        struct list_head head;             /* 挂 mode_config.crtc_list */

        struct drm_modeset_lock mutex;     /* atomic 驱动里保护 state */
        struct drm_mode_object base;
        struct drm_plane *primary;         /* 仅 legacy ioctl 有意义 */
        struct drm_plane *cursor;          /* 仅 legacy ioctl 有意义 */
        unsigned index;                    /* possible_crtcs 的位号 */
        int cursor_x, cursor_y;            /* legacy 镜像 */
        bool enabled;                      /* legacy 镜像 */
        struct drm_display_mode mode;      /* legacy 镜像 */
        struct drm_display_mode hwmode;    /* legacy 镜像 */
        int x, y;                          /* legacy 镜像 */
        const struct drm_crtc_funcs *funcs;
        uint32_t gamma_size;
        uint16_t *gamma_store;
        const struct drm_crtc_helper_funcs *helper_private;
        struct drm_object_properties properties;
        struct drm_property *scaling_filter_property;   /* 6.x 新增，未验证具体引入版本 */
        struct drm_crtc_state *state;
        struct list_head commit_list;
        spinlock_t commit_lock;
        struct dentry *debugfs_entry;
        struct drm_crtc_crc crc;

四个最容易踩的字段单独点一下：index 不要自己算，用 drm_crtc_index()；state 必须持 mutex 才能看；mode / enabled 是 legacy 镜像，atomic 驱动读了就是 bug；funcs->destroy 为 NULL 会在 init 时 WARN。

四、CRTC 的创建与注册 #

入口是 drm_crtc_init_with_planes()，定义在 drivers/gpu/drm/drm_crtc.c。它是个薄壳，只做参数转发 + 一个 WARN_ON(!funcs->destroy)，实体在 __drm_crtc_init_with_planes()。

c
int drm_crtc_init_with_planes(struct drm_device *dev, struct drm_crtc *crtc,
                              struct drm_plane *primary,   /* 可为 NULL */
                              struct drm_plane *cursor,    /* 可为 NULL */
                              const struct drm_crtc_funcs *funcs,
                              const char *name, ...)
{
        va_list ap;
        int ret;

        WARN_ON(!funcs->destroy);

        va_start(ap, name);
        ret = __drm_crtc_init_with_planes(dev, crtc, primary, cursor, funcs,
                                          name, ap);
        va_end(ap);

        return ret;
}

__drm_crtc_init_with_planes() 按顺序做完这些事：

  1. 校验 plane 类型。primary 非空则必须是 DRM_PLANE_TYPE_PRIMARY，cursor 非空则必须是 DRM_PLANE_TYPE_CURSOR，不符直接 WARN。
  2. 位掩码上限检查。config->num_crtc >= 32 直接 -EINVAL，注释写得很明白：crtc index is used with 32bit bitmasks。
  3. atomic 一致性检查。驱动声明了 DRIVER_ATOMIC，却漏了 atomic_destroy_state 或 atomic_duplicate_state，WARN。
  4. 存 dev、funcs，INIT_LIST_HEAD(&crtc->commit_list)，spin_lock_init(&crtc->commit_lock)，drm_modeset_lock_init(&crtc->mutex)。
  5. drm_mode_object_add(dev, &crtc->base, DRM_MODE_OBJECT_CRTC)——基于 IDR 基数树分配唯一 ID。
  6. 起名字。传了 name 就 kvasprintf，没传就 kasprintf("crtc-%d", drm_num_crtcs(dev))。
  7. crtc->fence_context = dma_fence_context_alloc(1)，snprintf(crtc->timeline_name, ..., "CRTC:%d-%s", crtc->base.id, crtc->name)。
  8. crtc->base.properties = &crtc->properties。
  9. list_add_tail(&crtc->head, &config->crtc_list)，然后 crtc->index = config->num_crtc++。
  10. 记住 primary/cursor，并在 plane 侧 possible_crtcs 还是 0 时兜底填成 drm_crtc_mask(crtc)。
  11. drm_crtc_crc_init()。
  12. atomic 驱动额外挂属性：prop_active、prop_mode_id、prop_out_fence_ptr、prop_vrr_enabled。

第 10 步的兜底逻辑值得单独拎出来。它意味着「如果你在 plane init 时没写 possible_crtcs，CRTC init 会替你写成本 CRTC 自己」。听起来体贴，实际上是个陷阱：如果一块 plane 本来能接两个 CRTC，而你在 plane init 时漏填，兜底只会填上一个，另一个永远绑不上，而且没有任何报错。

c
        /* crtc index is used with 32bit bitmasks */
        if (WARN_ON(config->num_crtc >= 32))
                return -EINVAL;

        crtc->dev = dev;
        crtc->funcs = funcs;
        INIT_LIST_HEAD(&crtc->commit_list);
        spin_lock_init(&crtc->commit_lock);
        drm_modeset_lock_init(&crtc->mutex);

        ret = drm_mode_object_add(dev, &crtc->base, DRM_MODE_OBJECT_CRTC);
        ...
        crtc->fence_context = dma_fence_context_alloc(1);
        spin_lock_init(&crtc->fence_lock);
        snprintf(crtc->timeline_name, sizeof(crtc->timeline_name),
                 "CRTC:%d-%s", crtc->base.id, crtc->name);

        crtc->base.properties = &crtc->properties;
        list_add_tail(&crtc->head, &config->crtc_list);
        crtc->index = config->num_crtc++;

drm_crtc_crc_init() 只在 CONFIG_DEBUG_FS 下有效，做的事就是初始化 CRC 的锁、等待队列，把 crc.source 默认设成 "auto"：

c
static int drm_crtc_crc_init(struct drm_crtc *crtc)
{
#ifdef CONFIG_DEBUG_FS
        spin_lock_init(&crtc->crc.lock);
        init_waitqueue_head(&crtc->crc.wq);
        crtc->crc.source = kstrdup("auto", GFP_KERNEL);
        if (!crtc->crc.source)
                return -ENOMEM;
#endif
        return 0;
}

helper vtable 是单独挂的，drm_crtc_helper_add() 就是个内联一行赋值：

c
static inline void drm_crtc_helper_add(struct drm_crtc *crtc,
                                       const struct drm_crtc_helper_funcs *funcs)
{
        crtc->helper_private = funcs;
}

注册动作不在这里。CRTC 真正的「对用户空间可见」发生在 drm_dev_register() 里：drm_crtc_register_all() 遍历 mode_config.crtc_list，依次调 crtc->funcs->late_register。注册路径反过来是 drm_dev_unregister() → drm_crtc_unregister_all() → early_unregister。所以驱动里所有「建 debugfs 文件」的活都该放 late_register，所有「拆 debugfs 文件」的活放 early_unregister，别在 probe/remove 里自己干。

RK3399 上的实际调用形态（VOP 驱动里每个 VP 一个 CRTC）：

text
rockchip_drm_bind()
  -> rockchip_drm_vop_probe()           /* 每颗 VOP 一个 */
     -> vop_plane_atomic_*()             /* 先建 plane */
     -> drm_crtc_init_with_planes(drm, &vop->crtc, &vop->plane...
                                  primary, cursor, &vop_crtc_funcs, NULL)
     -> drm_crtc_helper_add(&vop->crtc, &vop_crtc_helper_funcs)
     -> drm_mode_crtc_set_gamma_size()   /* 视需要 */
  -> drm_dev_register()
     -> drm_crtc_register_all()
        -> vop_crtc_funcs.late_register()

RK3399 有两颗 VOP（big VOP 与 little VOP），每颗有若干 VP（Video Port），每个 VP 对应一个 CRTC、至少一个 primary plane。/sys/kernel/debug/dri/0/crtc-0、crtc-1 这些目录就是 late_register 建出来的。

五、CRTC 的状态与 atomic 属性 #

struct drm_crtc_state 存在的意义：把「这个 CRTC 现在长什么样」从硬件和对象本体里剥出来，做成一个可以复制、可以试算、可以整体丢弃的值对象。atomic 提交的整个前提就是「先造一个候选 state，检查通过再一次性刷进硬件」。

先记一个语义区分，enable 和 active 不是一回事：

  • enable 表示资源分配。设了它，驱动可以占用共享时钟、预留带宽。
  • active 表示硬件真实状态，纯 DPMS 用。active 为真隐含 enable 为真。

关键约束：用户空间把 active 从 0 翻到 1，其余属性不动，这个 atomic 测试必须永远成功。所以驱动绝不能在 atomic_check 里看 active 来拒绝提交，也绝不能在 active=0 但 enable=1 时释放共享资源。这是 DPMS 语义的硬要求，踩了会被用户空间判定为驱动 bug。

三个 *_changed 位构成是否需要 full modeset 的判据，逻辑在 drm_atomic_crtc_needs_modeset() 里：mode_changed || active_changed || connectors_changed 任一为真就要走完整 modeset 路径。

全字段，按「状态位 → 位掩码 → 对象引用」三档看：

字段 类型 含义
crtc drm_crtc * 反指回 CRTC
enable / active bool 资源分配闸门 / 硬件真在显示
planes_changed / mode_changed / active_changed / connectors_changed bool : 1 是否需要 full modeset 的判据
zpos_changed / color_mgmt_changed / no_vblank bool : 1 zpos 变了 / 色彩管理变了 / 无 vblank 中断
plane_mask / connector_mask / encoder_mask u32 挂在本 CRTC 上的三类对象位掩码
adjusted_mode / mode drm_display_mode 实际烧进硬件的时序 / 用户空间请求的时序
mode_blob / degamma_lut / ctm / gamma_lut drm_property_blob * 暴露给用户空间的 mode blob 与三段色彩 LUT
target_vblank / async_flip / vrr_enabled / self_refresh_active u32 / bool flip 目标帧 / 异步 flip / 可变刷新率 / PSR

event / commit / state 三种指针 flip 完成事件 / 本次提交追踪 / 反指全局 atomic state

adjusted_mode 与 mode 的差异是 DRM 里最难绷的一处语义。mode 是用户空间要的；adjusted_mode 是 CRTC 实际吐给下游的。链路里有 bridge 做缩放，或者接口要做像素重复、YCbCr 420 降采样，两者就不一样。对 bridge 驱动而言，adjusted_mode 表示「CRTC 到第一颗 bridge 之间」的时序。

drm_crtc_funcs 是给 core 调的，五组：

  • 生命周期：reset、destroy、late_register、early_unregister。destroy 只由 drm_mode_config_cleanup() 调，CRTC 不能热插拔。
  • legacy 显示路径：set_config、page_flip、page_flip_target、set_property、cursor_set、cursor_set2、cursor_move、gamma_set。cursor_* 三个全标了 deprecated，改成 universal plane + drm_crtc_init_with_planes()；atomic 驱动用 drm_atomic_helper_set_config() / drm_atomic_helper_page_flip() 顶掉。
  • atomic 状态机：atomic_duplicate_state、atomic_destroy_state、atomic_set_property、atomic_get_property、atomic_print_state。前两个对 atomic 驱动强制，漏了 init 时 WARN。
  • CRC：set_crc_source、verify_crc_source、get_crc_sources，配合 drm_crtc_add_crc_entry() 报每帧校验值。
  • vblank：get_vblank_counter、enable_vblank、disable_vblank、get_vblank_timestamp。这几个是从 drm_driver 搬到 CRTC 上的，新驱动别再用旧的。

drm_crtc_helper_funcs 是给 helper 库调的，套路是「legacy 一组、atomic 一组」，新驱动只填 atomic 那组：

阶段 atomic 回调 legacy 对应 注
校验 atomic_check mode_valid / mode_fixup mode_valid 只做配置无关的硬约束；atomic_check 从 drm_atomic_helper_check_planes() 调
使能 atomic_enable dpms / commit / prepare atomic_enable 在所有 encoder enable 之前调
关断 atomic_disable disable / dpms atomic_disable 在所有 encoder disable 之后调
提交 atomic_begin / atomic_flush mode_set / mode_set_base 两者夹着 plane 的 atomic_update
时序查询 get_scanout_position — 只有走 drm_crtc_vblank_helper_get_vblank_timestamp() 才用

atomic_begin / atomic_flush 这一对是 RK3399 VOP 的关键。VOP 的寄存器写入不是立即生效的，要等一个「standby/GO」时机，atomic_begin 里置 pending 标志、atomic_flush 里触发配置装载，正好对应这两个钩子。

标准 atomic 属性有四个，__drm_crtc_init_with_planes() 里挂的那批：

  • ACTIVE：1 表示正在显示，0 表示断电。设 0 时不得释放内部资源（预留带宽、时钟发生器），因为用户空间期望 ACTIVE 回 1 永不失败。
  • MODE_ID：blob 属性，值是一个装着 drm_mode_modeinfo 的 blob ID。设 0 表示关掉 CRTC 并释放预留资源。
  • SCALING_FILTER：Default 或 Nearest Neighbor。
  • OUT_FENCE_PTR、VRR_ENABLED：与出帧 fence、可变刷新率相关。

六、plane：图层与扫描 #

plane 是显示处理器里 layer 的内核抽象。硬件上一块 layer 需要配什么，plane 就要能表达什么：图像格式、宽高、stride、显存地址，支持缩放的话还要原图和目标尺寸。

RK3399 的 VOP 一颗支持 4 个 layer，RK3568 的 VOP 支持 6 个。layer 之间靠合成次序（zpos）和合成方式（porter-duff 混合方程）叠起来，位置由一个 (x, y) 决定，最终画布尺寸由 CRTC 的分辨率定。

一个 CRTC 可以吃多个 plane 的输入。三种 plane 在同一块屏幕上层的分工很直观：

text
  ┌──────────────────────────────────────┐
  │  Cursor Framerbuffer   (CURSOR)      │  ← 鼠标光标，小，常带 alpha
  │  ┌──────────────────────────────┐    │
  │  │ Overlay Framebuffer (OVERLAY)│    │  ← 视频窗口，动态内容，硬件合成
  │  │      ┌────────────────┐      │    │
  │  └──────│ 小窗           │──────┘    │
  │  ┌──────┴────────────────┴──────┐    │
  │  │ Background Framebuffer       │    │  ← 桌面背景，整屏
  │  │        (PRIMARY)             │    │
  │  └──────────────────────────────┘    │
  └──────────────────────────────────────┘

plane 自己不存像素。它持有一个 drm_framebuffer 引用，说明「这块显存的哪一部分被扫」，再持有一个 drm_crtc 引用，说明「扫到哪个显示单元的坐标系里」。真正的像素格式、stride、offset 全在 framebuffer 里，plane 只声明「我支持哪些格式」。

struct drm_framebuffer 与 GEM 的关系要单独说清，因为它是整个 DRM 内存模型的交汇点：

  • obj[] 数组（长度 DRM_FORMAT_MAX_PLANES = 4）指向后备的 drm_gem_object，每个 color plane 一个。RGB 打包格式只填 obj[0]，NV12 这类半平面格式要填 obj[0] 和 obj[1]。
  • pitches[] 是每个 color plane 的行跨度（字节）。
  • offsets[] 是每个 color plane 的实际像素数据相对 buffer 起点的线性偏移。注意它不是 x/y 像素偏移，x/y 走 plane state 的 src_x/src_y。
  • modifier 描述 tiling 或压缩布局（AFBC、tile 格式）。
  • format 指向 drm_format_info，里面才有 num_planes、hsub、vsub。

drm_format_info 是格式元数据的唯一来源。看 num_planes 和 hsub/vsub 就能推出 buffer 大小，drm_gem_fb_init_with_funcs() 就是靠这几个字段做尺寸校验的。

七、struct drm_plane 的字段 #

全字段。分组方式和 CRTC 那节一致，便于对照。

身份组：dev、head、name、mutex、base、index、type。index 在 mode_config.plane_list 里的位置，终生不变。

能力组：possible_crtcs、format_types、format_count、format_default、modifiers、modifier_count。possible_crtcs 是用 drm_crtc_mask() 拼出来的位掩码。format_types 是一段 uint32_t 数组，长度 format_count，内容就是 DRM_FORMAT_* 常量。modifiers 同理，元素是 uint64_t。format_default 只在非 atomic 兼容包装层里有意义。

绑定组：crtc、fb、old_fb。这三个全是 legacy 字段，atomic 驱动下被强制成 NULL。atomic 驱动要看绑定关系就读 drm_plane_state.crtc / drm_plane_state.fb。

vtable 与属性组：funcs、helper_private、properties、state，以及一大排可选属性指针 alpha_property、zpos_property、rotation_property、blend_mode_property、color_encoding_property、color_range_property、scaling_filter_property。每个都有对应的 drm_plane_create_*_property() 建属性函数。

struct drm_plane_state 才是 atomic 路径真正读的地方。最关键的八个坐标字段，两两成对：

text
framebuffer (源)                          crtc (目标)
src_x, src_y, src_w, src_h      ──────▶   crtc_x, crtc_y, crtc_w, crtc_h
     16.16 定点，单位像素                       整数，单位像素
        │                                          ▲
        └──────── 硬件 scaler 拉伸 ────────────────┘

src_* 是 framebuffer 里的可见区域，用 16.16 定点数表示，因为亚像素裁剪确实存在。crtc_* 是 CRTC 坐标系里的目标矩形，用整数表示。两者尺寸不等就触发缩放，硬件不支持缩放时驱动必须返回 -EINVAL。

源码注释明确要求：驱动要先把原始坐标交给 drm_atomic_helper_check_plane_state()，然后只用它算出来的 src/dst 两个 drm_rect 去配硬件。自己手算裁剪很容易在「部分出屏」的窗口上翻车。

其余状态字段：plane、crtc、fb、fence（显式 fence，扫描前要等）、alpha（0 全透明 ~ 0xffff 全不透明）、pixel_blend_mode、rotation、zpos、normalized_zpos（0~N-1 归一化后的值，前提是 mode_config.normalize_zpos 为真或调用过 drm_atomic_normalize_zpos()）、color_encoding、color_range、fb_damage_clips（脏区 blob，注意它不是 16.16 定点）、src/dst（drm_rect）、visible（fb 和 crtc 都非空、却被裁到不可见时为假）、scaling_filter、commit、state。

zpos 相同是个用户空间 bug，但驱动不能崩——内核的处理办法是比较 plane 对象 ID，ID 大的叠在上面。

drm_plane_funcs 给你的回调：

回调 强制? 说明
destroy 是（否则 WARN） 卸载时走 drm_mode_config_cleanup()
reset 建议 只由 drm_mode_config_reset() 调；atomic 驱动用 drm_atomic_helper_plane_reset()
update_plane / disable_plane 否 legacy，atomic 下换成 drm_atomic_helper_update_plane() / drm_atomic_helper_disable_plane()
set_property 否 legacy，atomic 下 core 全包

drm_plane_helper_funcs 里最要紧的是 prepare_fb / cleanup_fb 这一对。prepare_fb 干的是「扫描前把 buffer 钉住」：pin 住物理页、搬进连续 VRAM、刷 cache。注意它不能阻塞等渲染完成，因为它跑在 atomic ioctl 上下文里；正确做法是把 fence 填进 drm_plane_state.fence。GEM 驱动如果两个钩子都不给，helper 会自动调 drm_gem_plane_helper_prepare_fb()。

6.x 里这一组多出 begin_fb_access / end_fb_access，用来区分「提交期间要用的资源」和「要一直持有到下一次 flip 的资源」。pin 放 prepare_fb，vmap 放 begin_fb_access。

commit 阶段的四个钩子有严格次序：

text
CRTC.atomic_begin
  └─ plane.atomic_check（在 check 阶段，更早）
  └─ plane.atomic_update  / plane.atomic_disable
CRTC.atomic_flush

atomic_async_check / atomic_async_update 是给光标这类「不等 vblank」的路径用的，限制是只支持单 plane 更新，异步 flip 不支持。

八、plane 的三种类型 #

类型是 UABI——enum drm_plane_type 的值直接暴露在 plane 的 type 属性里，改不了。

类型 枚举值 必需性 每 CRTC 数量 用途 硬件要求
PRIMARY 1 必须 至少 1 桌面背景 / 主体图形内容，整屏 要能覆盖整个 CRTC，无缩放裁剪
CURSOR 2 可选 0 或 1 鼠标光标 尺寸受 mode_config.cursor_width/height 限制，无 modifier 时要求线性布局
OVERLAY 0 可选 0~N 视频窗口、动态内容，吃硬件合成 常可在多 CRTC 间动态分配

枚举顺序反直觉：OVERLAY 是 0，PRIMARY 是 1，CURSOR 是 2，写 switch 别按语义顺序猜。另外，兼容非 universal plane 感知的老用户空间时，默认只暴露 overlay plane，用户空间要设 DRM_CLIENT_CAP_UNIVERSAL_PLANES 才看得到全部三类。

RK3399 的实际配置：每个 VP 一个 primary plane，窗口层作为 overlay plane 注册，possible_crtcs 填本 VOP 所有 VP 的掩码，窗口就能在 VP 之间迁移。

入口 drm_universal_plane_init()，同样是个转发壳，实体在 __drm_universal_plane_init()。

__drm_universal_plane_init() 的流程：

  1. 上限检查两连。config->num_total_plane >= 32 拒（plane 索引进 32 位掩码），format_count > 64 也拒（每个格式占一位，现有实现只支持 u64）。
  2. atomic 一致性 WARN，与 CRTC 那处完全对称。
  3. drm_mode_object_add(dev, &plane->base, DRM_MODE_OBJECT_PLANE) 分配 ID。
  4. drm_modeset_lock_init(&plane->mutex)。
  5. 存 base.properties、dev、funcs。
  6. kmalloc_array 分配 format_types，失败就 drm_mode_object_unregister 回滚。
  7. 处理 modifier。传了 format_modifiers 就数到 DRM_FORMAT_MOD_INVALID 终止符为止；没传且 fb_modifiers_not_supported 为假，就退化成只支持 DRM_FORMAT_MOD_LINEAR。随后 drm_WARN_ON 检查「声明不支持 modifier 却又数出了 modifier」这种自相矛盾的配置。
  8. 分配 modifiers 数组。
  9. 起名字，不传就是 plane-%d + drm_num_planes(dev)。
  10. memcpy 格式表和 modifier 表，填 format_count、possible_crtcs、type。
  11. list_add_tail(&plane->head, &config->plane_list)，plane->index = config->num_total_plane++。
  12. 挂 plane_type_property（值就是 type）；atomic 驱动再挂 prop_fb_id、prop_in_fence_fd、prop_crtc_id、prop_crtc_x/y/w/h、prop_src_x/y/w/h。
  13. 有 modifier 就 create_in_format_blob()，生成 IN_FORMATS blob——用户空间靠这个才知道「哪些 modifier 配哪些格式」。

第 13 步值得展开。IN_FORMATS blob 的内容是「格式 → 该格式允许的 modifier 位掩码」的映射。如果驱动实现了 format_mod_supported，core 会逐个格式 × 逐个 modifier 询问，生成精确位图；没实现就按笛卡尔积全允许。RK3399 的 AFBC 支持必须靠这个回调正确声明，否则用户空间会挑到硬件不支持的组合。

drm_mode_object_add() 是四类对象共用的 ID 分配器，值得单独看一眼。它最终落到 __drm_mode_object_add()：拿 mode_config.idr_mutex，在 mode_config.object_idr 这棵基数树上 idr_alloc 一个从 1 开始的位置，把对象指针存进去，然后回填 obj->id 和 obj->type。register_obj 参数决定是否立即把对象挂进 IDR——plane/CRTC/encoder 传 true，framebuffer 传 false（它要等 drm_framebuffer_init() 尾部再 drm_mode_object_register() 用 idr_replace 补上）。

c
int __drm_mode_object_add(struct drm_device *dev, struct drm_mode_object *obj,
                          uint32_t obj_type, bool register_obj,
                          void (*obj_free_cb)(struct kref *kref))
{
        int ret;

        WARN_ON(!dev->driver->load && dev->registered && !obj_free_cb);

        mutex_lock(&dev->mode_config.idr_mutex);
        ret = idr_alloc(&dev->mode_config.object_idr, register_obj ? obj : NULL,
                        1, 0, GFP_KERNEL);
        if (ret >= 0) {
                obj->id = ret;
                obj->type = obj_type;
                if (obj_free_cb) {
                        obj->free_cb = obj_free_cb;
                        kref_init(&obj->refcount);
                }
        }
        mutex_unlock(&dev->mode_config.idr_mutex);

        return ret < 0 ? ret : 0;
}

drm_object_attach_property() 是四类对象共用的属性挂载器。属性存在一个定长数组里（DRM_OBJECT_MAX_PROPERTY 个槽），满了只 WARN 然后直接 return，不报错——这是最坑的一处静默失败：属性挂不上，用户空间拿不到，你查半天以为自己忘了写。

c
void drm_object_attach_property(struct drm_mode_object *obj,
                                struct drm_property *property,
                                uint64_t init_val)
{
        int count = obj->properties->count;
        struct drm_device *dev = property->dev;

        if (count == DRM_OBJECT_MAX_PROPERTY) {
                WARN(1, "Failed to attach object property (type: 0x%x). Please "
                        "increase DRM_OBJECT_MAX_PROPERTY by 1 for each time "
                        "you see this message on the same object type.\n",
                        obj->type);
                return;
        }

        obj->properties->properties[count] = property;
        obj->properties->values[count] = init_val;
        obj->properties->count++;
}

framebuffer 的初始化在 drm_framebuffer_init()：

c
int drm_framebuffer_init(struct drm_device *dev, struct drm_framebuffer *fb,
                         const struct drm_framebuffer_funcs *funcs)
{
        int ret;

        if (WARN_ON_ONCE(fb->dev != dev || !fb->format))
                return -EINVAL;

        INIT_LIST_HEAD(&fb->filp_head);
        fb->funcs = funcs;
        strcpy(fb->comm, current->comm);

        /* 注意第四个参数是 false：先不挂进 IDR */
        ret = __drm_mode_object_add(dev, &fb->base, DRM_MODE_OBJECT_FB,
                                    false, drm_framebuffer_free);
        if (ret)
                goto out;

        mutex_lock(&dev->mode_config.fb_lock);
        dev->mode_config.num_fb++;
        list_add(&fb->head, &dev->mode_config.fb_list);
        mutex_unlock(&dev->mode_config.fb_lock);

        drm_mode_object_register(dev, &fb->base);
out:
        return ret;
}

fb->format 必须由调用者在进来之前填好，函数只 WARN_ON_ONCE(!fb->format) 不做补救。drm_mode_object_register() 用 idr_replace 把之前留空的位置换成真实对象指针：

c
void drm_mode_object_register(struct drm_device *dev,
                              struct drm_mode_object *base)
{
        mutex_lock(&dev->mode_config.idr_mutex);
        idr_replace(&dev->mode_config.object_idr, base, base->id);
        mutex_unlock(&dev->mode_config.idr_mutex);
}

plane 的 format 支持在 RK3399 上的落地方式：VOP 驱动维护一张格式表（vop_plane_formats），AFBC 再叠一张 modifier 表，注册时把两张表传进 drm_universal_plane_init()，并实现 format_mod_supported 说明某格式配某 modifier 是否合法。窗口层的格式支持比 primary 宽，因为 primary 要保证能整屏扫描。

十、encoder：编码与转换 #

encoder 夹在 CRTC 和 connector 中间，职责是把 CRTC 输出的并行像素流转换成某种具体接口格式的数字信号：HDMI 走 TMDS，DisplayPort 走 8b/10b 编码的差分对，MIPI DSI 走 D-PHY 或 C-PHY 的包协议，LVDS 走 7:1 串行。

encoder_type 决定它是哪一类，也决定默认命名：

枚举值 含义
DRM_MODE_ENCODER_NONE 未指定
DRM_MODE_ENCODER_DAC VGA 与 DVI-I / DVI-A 上的模拟通道
DRM_MODE_ENCODER_TMDS DVI、HDMI、（内嵌）DisplayPort
DRM_MODE_ENCODER_LVDS 显示面板，或任何自定义并行接口的面板
DRM_MODE_ENCODER_TVDAC 电视输出（Composite、S-Video、Component、SCART）
DRM_MODE_ENCODER_VIRTUAL 虚拟机显示
DRM_MODE_ENCODER_DSI DSI 串行总线上的面板
DRM_MODE_ENCODER_DPI DPI 并行总线上的面板
DRM_MODE_ENCODER_DPMST DP MST 用的假 encoder，让多路流共享一个物理 encoder

encoder_type 只影响默认命名和用户空间展示，不影响行为。真正决定行为的是 funcs 和 helper_private。

RK3399 上很多 encoder 是「空壳」。VOP 输出的并行 RGB 直接进 HDMI TX 控制器或 eDP 控制器，那颗控制器在内核里以 drm_bridge 存在，encoder 只负责挂链。你会看到 drm_encoder 的 helper_private 里 atomic_enable 之类全是空函数，实际配置都在 bridge 的 atomic_enable 里。

possible_crtcs 的版本变化要标清楚：6.3 里它是 uint32_t，位号取 drm_crtc_index()，驱动必须在 drm_dev_register() 之前把所有能接的 CRTC 位设上，设错会 WARN。CRTC 不能热插拔，索引稳定且注册前已知。6.3 之后上游有没有改成动态分配，未验证。possible_clones 的规则稍绕：它是克隆（一个 CRTC 同时驱动多个 encoder）的允许集合，位号取 drm_encoder_index()，能一起克隆的 encoder 必须互相设位（含自己）；不实现克隆的留 0，core 会自动补上自己那一位。

struct drm_encoder 全字段，7 个：

crtc 成员有个和 plane 一样的陷阱：注释写 only really meaningful for non-atomic drivers，atomic 驱动要看 drm_connector_state.crtc。bridge_chain 注释更直接：Drivers shall not access this field directly，你只该通过 drm_bridge_attach() 往里塞。

drm_encoder_funcs 只有四个回调，全部可选（destroy 实际必需，否则 init 时 WARN）：reset 只由 drm_mode_config_reset() 调；destroy 只在驱动卸载时通过 drm_mode_config_cleanup() 调；late_register / early_unregister 是 debugfs 这类接口的挂载/卸载点，分别在 drm_dev_register() 和 drm_dev_unregister() 里调。

drm_encoder_helper_funcs 按「legacy 一组 / atomic 一组」分：

回调 组 说明
dpms legacy 控件电源电平，不支持的模式要用次低一级。也被用来关 encoder
mode_valid 共用 只按传入 mode 判断硬件能否支持，不许看别的状态
mode_fixup legacy 校验并调整 mode；atomic 驱动改用 atomic_check 后此钩子不再被调
prepare / commit legacy modeset 前后的关/开，实际就是调 dpms

detect 历史遗留 在 encoder 上做检测，只有 radeon/amdgpu/nouveau 用

atomic_check atomic 同时拿到 crtc_state 和 conn_state，能做跨对象校验

atomic_enable 与 atomic_disable 的次序是硬约定，写在注释里：atomic_disable 在本 encoder 的 CRTC 被 drm_crtc_helper_funcs.atomic_disable 关掉之前调用；atomic_enable 在本 encoder 的 CRTC 被 drm_crtc_helper_funcs.atomic_enable 打开之后调用。这条次序保证了「关的时候从下游往上游关，开的时候从上游往下游开」，避免中间态出现无时钟数据。

drm_bridge_funcs 的回调分四组，其中「legacy / atomic」的配对最要紧：

atomic_check 的调用次序是反的——从链尾的 bridge 往链头调。原因是下游先确定自己要什么格式，上游再据此决定输出什么。

pre_enable_prev_first 是给 DSI 这类「必须先初始化 host 再初始化 peripheral」的器件准备的开关。置位后，pre_enable 要等前一级 bridge 的 pre_enable 先跑完，post_disable 反之。

drm_bridge_attach() 是唯一的挂链入口，实现在 drivers/gpu/drm/drm_bridge.c。它的参数语义：previous 为 NULL 表示直接挂在 encoder 输出端，非 NULL 表示挂在前一颗 bridge 的输出端，而且那颗必须已经 attach 过。

c
int drm_bridge_attach(struct drm_encoder *encoder, struct drm_bridge *bridge,
                      struct drm_bridge *previous,
                      enum drm_bridge_attach_flags flags)
{
        int ret;

        if (!encoder || !bridge)
                return -EINVAL;

        if (previous && (!previous->dev || previous->encoder != encoder))
                return -EINVAL;

        if (bridge->dev)
                return -EBUSY;

        bridge->dev = encoder->dev;
        bridge->encoder = encoder;

        if (previous)
                list_add(&bridge->chain_node, &previous->chain_node);
        else
                list_add(&bridge->chain_node, &encoder->bridge_chain);

        if (bridge->funcs->attach) {
                ret = bridge->funcs->attach(bridge, flags);
                if (ret < 0)
                        goto err_reset_bridge;
        }

        if (bridge->funcs->atomic_reset) {
                struct drm_bridge_state *state;

                state = bridge->funcs->atomic_reset(bridge);
                if (IS_ERR(state)) {
                        ret = PTR_ERR(state);
                        goto err_detach_bridge;
                }

                drm_atomic_private_obj_init(bridge->dev, &bridge->base,
                                            &state->base,
                                            &drm_bridge_priv_state_funcs);
        }

        return 0;

err_detach_bridge:
        if (bridge->funcs->detach)
                bridge->funcs->detach(bridge);

err_reset_bridge:
        bridge->dev = NULL;
        bridge->encoder = NULL;
        list_del(&bridge->chain_node);

        DRM_ERROR("failed to attach bridge %pOF to encoder %s: %d\n",
                  bridge->of_node, encoder->name, ret);
        return ret;
}

三个动作值得记住：bridge->dev 非空直接 -EBUSY，所以一颗 bridge 只能挂到一个 encoder 上；list_add（不是 list_add_tail）意味着后 attach 的 bridge 排在链头，遍历时要注意方向；挂链成功后立刻调 atomic_reset 并把 state 交给 drm_atomic_private_obj_init() 托管。

最后一个细节：bridge 的自动解挂发生在 drm_encoder_cleanup() 里，所以驱动代码里不要给 drm_bridge_attach() 配一个 drm_bridge_detach() 去配对，会 double free。

bridge 与 encoder 的对比，这是最容易混的一对：

维度 drm_encoder drm_bridge

用户空间可见 可见（GETENCODER） 不可见
数量关系 一个 CRTC 可接多个 encoder（克隆） 一个 encoder 串一条 bridge 链
链式结构 无 chain_node 串成双向链
典型职责 声明「本 CRTC 能接哪类接口」 真正干 PHY/协议转换的活
设备树绑定 无独立节点 有 of_node，走 DT 匹配
状态对象 无独立 state，用 connector state 有 drm_bridge_state（私有 state）
RK3399 实例 VOP 里每类输出一个空壳 encoder dw-hdmi、analogix-dp、dw-mipi-dsi 等

十二、connector：连接到显示器 #

connector 是「物理插座」的抽象。它管三件事：这个口插没插东西（状态检测）、这口能跑哪些分辨率（读 EDID 并解析）、这口当前用哪个 encoder。

connector_type 是 DRM_MODE_CONNECTOR_* 一系列枚举，HDMI-A、DisplayPort、eDP、LVDS、DSI、VGA、DVI-D 等。connector_type_id 是同类型内的序号。这两个拼起来就是名字：kasprintf("%s-%d", drm_connector_enum_list[connector_type].name, connector_type_id)，HDMI 第一个口就叫 HDMI-A-1。/sys/class/drm/card0-HDMI-A-1 那个目录名就是这么来的。

connector 的四个布尔能力位决定模式过滤行为：interlace_allowed、doublescan_allowed、stereo_allowed、ycbcr_420_allowed。前三个只被 drm_helper_probe_single_connector_modes() 拿去过滤；第四个影响 EDID 解析时能否接受 YCbCr 420 的 VIC 表。

十三、struct drm_connector 与 EDID #

struct drm_connector 是四类 KMS 对象里字段最多的一个，6.3 版本接近 100 个成员。按用途分五组。

EDID 解析这块原文只有零星提及，这里按 6.3 的实际结构补齐。EDID 以 128 字节为一块，第一块叫基础块（base block），可以再接扩展块（extension block）。cea_rev 来自 CEA-861 扩展块。解析的调用链：

text
connector 探测（drm_helper_probe_single_connector_modes）
  -> 驱动 get_modes / detect_ctx
     -> 通过 connector->ddc（i2c_adapter）读 0x50 偏移 0 起 128 字节
     -> drm_do_get_edid() 校验头 00 FF FF FF FF FF FF 00 与块校验和

        -> drm_parse_hdmi_vsdb() 填 drm_hdmi_info

EDID 基础块的关键字段：头 8 字节魔数、厂商 ID（2 字节 5bit 压缩的 PNP ID）、产品码、序列号、制造周/年、EDID version/revision、基本显示参数（含物理尺寸、gamma、电源管理）、色度坐标、已建立时序位图、标准时序位图、4 个详细时序描述符、扩展块数量、校验和。

128 字节的详细时序描述符里，前两块（像素时钟、水平/垂直有效与消隐）就是 struct drm_display_mode 的原生字段。解析出来的 mode 会带 DRM_MODE_TYPE_DRIVER 位，第一个详细描述符带 DRM_MODE_TYPE_PREFERRED。

四个详细描述符如果像素时钟为 0，就说明它是「显示器描述符」而不是时序：类型 0xFC 是显示器名，0xFD 是频率范围（填进 monitor_range），0xFE 是 ASCII 字符串，0xFB 是附加白点，0xFF 是序列号。这些不产生 mode，只填 display_info。

quirks 字段就是为了对付「EDID 内容能读但信息是错的」的显示器，用 EDID_QUIRK_* 位标记，在解析时逐条打补丁。

fill_modes 否 输出检测 + 模式校验总入口，用 probe helper 的话给 drm_helper_probe_single_connector_modes
set_property legacy atomic 下 core 全包
late_register / early_unregister 否 背光、i2c、DP aux 这类接口挂在 drm_connector_register() → late_register
destroy 必需 drm_mode_config_cleanup() 或热拔时调
atomic_duplicate_state / atomic_destroy_state atomic 必需 不 subclass state 就用 drm_atomic_helper_connector_duplicate_state()
atomic_set_property / atomic_get_property 否 仅驱动私有属性
atomic_print_state 否 走 drm_atomic_connector_print_state()
oob_hotplug_event 否 来自显示驱动之外的 HPD 源（如 USB-C 控制器）
debugfs_init 否 建 connector 专属 debugfs

drm_connector_helper_funcs 是 helper 库调的回调，重点是三个：

  • get_modes：往 probed_modes 里填模式，同时调 drm_connector_update_edid_property() 更新 EDID 属性。标准做法是在 detect 里把 EDID 缓存到驱动私有结构，这里解析后用 drm_add_edid_modes() 加进去。固定面板可以直接 drm_mode_probed_add() 手加。这个回调返回 0 而状态是 connected/unknown 时，调用者会自动补一组 VESA DMT 模式（到 1024x768），不用手动调 drm_add_modes_noedid()。
  • detect_ctx：detect 的 atomic 版本，带 drm_modeset_acquire_ctx，允许在里面加锁。
  • best_encoder：挑本 connector 该用哪个 encoder。只挂一个 encoder 时可以留 NULL，core 会调 drm_connector_get_single_encoder()。atomic 驱动若需按配置动态选，用 atomic_best_encoder。

还有一个容易忽略的语义差异：drm_connector_helper_funcs.mode_valid 只过滤送给用户空间的模式表（GETCONNECTOR ioctl），不参与 atomic check。真正的源端硬约束要写在 drm_encoder_helper_funcs.mode_valid、drm_crtc_helper_funcs.mode_valid 或 drm_bridge_funcs.mode_valid 里，那三个才会从 drm_atomic_helper_check_modeset() 被调。这意味着用户空间可以绕过 connector 的 mode_valid 强行用超范围模式——这是设计上留给测试和对付坏 EDID 的口子。

十四、connector 的状态检测 #

enum drm_connector_status 三个值：connector_status_connected、connector_status_disconnected、connector_status_unknown。

检测有两条路：

第一条是中断驱动。polled 里置了 DRM_CONNECTOR_POLL_HPD，HPD 中断来了之后驱动调 drm_helper_hpd_irq_event()，core 再逐个 connector 探一遍。

第二条是轮询驱动。polled 里置了 POLL_CONNECT / POLL_DISCONNECT，drm_kms_helper_poll_enable() 起一个延迟工作队列，按固定间隔（默认 10 秒，可由模块参数调整）调 drm_helper_probe_single_connector_modes()。RK3399 的 HDMI 走中断，MIPI DSI 面板是固定连接的，polled 填 0。

无论哪条路，最后都落到同一个函数：drm_helper_probe_single_connector_modes()。它的流程：

  1. 拿 mode_config.mutex。
  2. 若 connector 处于 force 状态，跳过 detect，直接按强制的状态走；否则调驱动提供的 detect_ctx 或 detect。
  3. 状态变了就发 sysfs uevent，并递增 epoch_counter。
  4. 清空 probed_modes 和 modes。
  5. 状态是 connected（或 unknown）时调 fill_modes，后者落到驱动的 get_modes。
  6. 逐个模式过一遍所有 mode_valid 回调（connector、encoder、CRTC、bridge 各自的），再按 max_width/max_height 裁掉超尺寸的。
  7. 合并去重，把 probed_modes 里剩下的搬到 modes。

sysfs 上能直接看到结果：

bash
root@rk3399:~# cat /sys/class/drm/card0-HDMI-A-1/status
connected
root@rk3399:~# cat /sys/class/drm/card0-HDMI-A-1/modes
1920x1080
1280x720
1024x768

force 是调试时的救命开关。/sys/class/drm/card0-HDMI-A-1/force 可以写 on / off / detect，强制认或不认显示器，也能通过内核命令行 video=HDMI-A-1:1920x1080@60e 指定。cmdline_mode 字段就是存这条命令行解析结果的。

drm_connector_funcs.detect 的 force 参数要注意：轮询时传 false，用户主动查询时传 true。驱动可以据此在自动轮询时跳过破坏性操作（比如 DDC 读取超时较长的情况）。

drm_display_info.is_hdmi 这个字段的存在是为了避免每次都调 drm_detect_hdmi_monitor() 重读 EDID。填好之后后续判断直接读字段。

十五、GEM：图形内存管理 #

GEM 负责显示 buffer 的分配、释放、共享。它不管 GPU 渲染调度（那是 drm_sched），也不管 GPU 页表（那是 VM_BIND / GPUVM），只管 buffer 对象本身。

struct drm_gem_object 是基类，驱动必须把它嵌进自己的私有结构里：GEM 的语义要求「基类指针能从私有结构推出私有结构」，而内核没有 container_of 之外的机制，所以必须内嵌而不是指针引用。

一个 GEM 对象的完整生命周期：

text
1. 驱动 kzalloc 私有 GEM 结构（内含 drm_gem_object base）
2. 填 obj->funcs（drm_gem_object_funcs）
3. drm_gem_object_init() 或 drm_gem_private_object_init()
4. 分配物理后备存储（dma_alloc_attrs / shmem 缺页）
5. drm_gem_handle_create() 拿 handle，暴露给某一个 drm_file
6. userspace 用 handle 做 mmap / PRIME export / fb_create
7. drm_gem_handle_delete()（GEM_CLOSE 或关 fd）
8. 最后一个引用 drop → refcount 归零 → funcs->free() → drm_gem_object_release()

全字段：

c
struct drm_gem_object {
        struct kref refcount;
        unsigned handle_count;              /* 本对象的 fd 句柄计数 */
        struct drm_device *dev;
        struct file *filp;                  /* shmem 后备；私有对象为 NULL */
        struct drm_vma_offset_node vma_node;/* mmap 偏移管理 */
        size_t size;                        /* 字节，终生不变 */
        int name;                           /* flink 全局名，1 起，0 = 无名 */
        struct dma_buf *dma_buf;            /* PRIME 关联的 dma-buf */
        struct dma_buf_attachment *import_attach;  /* 导入来的对象才有 */
        struct dma_resv *resv;              /* 指向 _resv，导入对象指向别人的 */
        struct dma_resv _resv;              /* 自带的 reservation object */
        const struct drm_gem_object_funcs *funcs;
        struct list_head lru_node;
        struct drm_gem_lru *lru;
};

几个字段的语义要掰开：

  • refcount：对象生命周期。所有引用都走 drm_gem_object_get() / drm_gem_object_put()。
  • handle_count：句柄计数，不是引用计数。每个 handle 另外持有一个普通引用。归零时 flink 全局名会被清掉。受 drm_device.object_name_lock 保护。
  • filp：只有 shmem 后备的对象才有。私有对象（连续 DMA 内存、保留显存）这里是 NULL。
  • vma_node：mmap 偏移的分配器节点。偏移用 drm_gem_create_mmap_offset() 分配，取回用 drm_vma_node_offset_addr()。
  • resv / _resv：dma_resv 是 fence 容器，管 GPU 渲染完成、DMA 搬完这类时序依赖。resv 平时指向自己的 _resv，导入的 dma-buf 指向对方的。
  • lru_node / lru：回收管理器用，6.x 引入。

struct drm_gem_object_funcs 是对象级 vtable。这个指针是 funcs 字段在 6.x 演进的产物——早期 GEM 驱动把 gem_free_object、gem_vm_ops、gem_prime_export 这些回调全塞在 struct drm_driver 里，全局一份；后来引入 drm_gem_object_funcs，做成「每对象一份」，允许同一个 DRM 设备里的不同 GEM 对象有不同行为（比如 AFBC 压缩 buffer 和普通 buffer 的 mmap 就不一样）。新驱动必须用 funcs，struct drm_driver 里那批老回调是给老驱动留的兼容路径。

6.3 的 drm_gem_object_funcs 里需要注意两处签名变化：vmap/vunmap 用的是 struct iosys_map *（不是裸 void *），这是 6.1 之后为了统一 I/O 内存抽象改的；evict 和 status 也是较新加入的（6.x 才有，具体引入版本未验证）。老代码里 void *vaddr 的写法在 6.3 编不过。

c
struct drm_gem_object_funcs {
        void (*free)(struct drm_gem_object *obj);       /* 必需 */
        int (*open)(struct drm_gem_object *obj, struct drm_file *file);
        void (*close)(struct drm_gem_object *obj, struct drm_file *file);
        void (*print_info)(struct drm_printer *p, unsigned int indent,
                           const struct drm_gem_object *obj);
        struct dma_buf *(*export)(struct drm_gem_object *obj, int flags);
        int (*pin)(struct drm_gem_object *obj);
        void (*unpin)(struct drm_gem_object *obj);
        struct sg_table *(*get_sg_table)(struct drm_gem_object *obj);
        int (*vmap)(struct drm_gem_object *obj, struct iosys_map *map);
        void (*vunmap)(struct drm_gem_object *obj, struct iosys_map *map);
        int (*mmap)(struct drm_gem_object *obj, struct vm_area_struct *vma);
        int (*evict)(struct drm_gem_object *obj);
        enum drm_gem_object_status (*status)(struct drm_gem_object *obj);
        const struct vm_operations_struct *vm_ops;
};

回调说明：

回调 何时调 备注
free 最后一个引用释放 必需。释放对象和全部相关资源
open drm_gem_handle_create() 内 可选，创建句柄时通知驱动
close drm_gem_handle_delete() 内 可选
get_sg_table PRIME export 时 返回 scatter-gather 表
vmap / vunmap drm_gem_dmabuf_vmap/vunmap 给 dma-buf 映射内核虚拟地址
mmap drm_gem_mmap_obj() / drm_gem_prime_mmap() 有它就不看 vm_ops，必须自己设 vma->vm_ops

status 打印/统计 6.x 新增，未验证

mmap 和 vm_ops 二选一的规则很关键：给了 mmap 回调，内核的 drm_gem_mmap() 就把控制权全交给你，你必须自己实现 vma->vm_ops->fault。不给 mmap 就退回 vm_ops 路径。

十六、struct drm_gem_object 与 handle #

用户空间和内核之间用三种东西引用 GEM 对象，全是 32 位数：本进程 handle、全局 flink 名称、dma-buf fd。

handle 只在特定 drm_file 内有效。一个进程打开 /dev/dri/card0 得到一个 drm_file，在这个 fd 上创建的 handle 只有这个 fd 能用。关掉 fd，所有 handle 全没。

两种初始化函数，用途完全不同：

c
int drm_gem_object_init(struct drm_device *dev,
                        struct drm_gem_object *obj, size_t size)
{
        struct file *filp;

        drm_gem_private_object_init(dev, obj, size);

        filp = shmem_file_setup("drm mm object", size, VM_NORESERVE);
        if (IS_ERR(filp))
                return PTR_ERR(filp);

        obj->filp = filp;

        return 0;
}

void drm_gem_private_object_init(struct drm_device *dev,
                                 struct drm_gem_object *obj, size_t size)
{
        BUG_ON((size & (PAGE_SIZE - 1)) != 0);

        obj->dev = dev;
        obj->filp = NULL;

        kref_init(&obj->refcount);
        obj->handle_count = 0;
        obj->size = size;
        dma_resv_init(&obj->_resv);
        if (!obj->resv)
                obj->resv = &obj->_resv;

        drm_vma_node_reset(&obj->vma_node);
        INIT_LIST_HEAD(&obj->lru_node);
}

drm_gem_object_init() 用 shmem 做后备：物理页按需分配，可以换出到 swap。这是桌面 GPU 的常规做法，显存不够时把不用的 buffer 挪到内存也不心疼。

drm_gem_private_object_init() 不建 shmem，完全由驱动自己管物理存储。嵌入式场景常常必须走这条路——硬件要求物理连续内存，匿名可分页内存满足不了。RK3399 的 rockchip_gem_alloc_object() 调的正是 drm_gem_object_init()，但随后在 rockchip_gem_alloc_dma() 里用 dma_alloc_attrs() 另外拿了一块物理连续的 DMA buffer，等于 shmem 那份只是占位。

size 必须页对齐，BUG_ON 硬性检查，别踩。

handle 创建，drm_gem_handle_create() → drm_gem_handle_create_tail()：

c
int drm_gem_handle_create_tail(struct drm_file *file_priv,
                               struct drm_gem_object *obj,
                               u32 *handlep)
{
        struct drm_device *dev = obj->dev;
        u32 handle;
        int ret;

        WARN_ON(!mutex_is_locked(&dev->object_name_lock));
        if (obj->handle_count++ == 0)
                drm_gem_object_get(obj);

        idr_preload(GFP_KERNEL);
        spin_lock(&file_priv->table_lock);
        ret = idr_alloc(&file_priv->object_idr, obj, 1, 0, GFP_NOWAIT);
        spin_unlock(&file_priv->table_lock);
        idr_preload_end();

        mutex_unlock(&dev->object_name_lock);
        if (ret < 0)
                goto err_unref;

        handle = ret;

        ret = drm_vma_node_allow(&obj->vma_node, file_priv);
        if (ret)
                goto err_remove;

        if (obj->funcs->open) {
                ret = obj->funcs->open(obj, file_priv);
                if (ret)
                        goto err_revoke;
        }

        *handlep = handle;
        return 0;

err_revoke:
        drm_vma_node_revoke(&obj->vma_node, file_priv);
err_remove:
        spin_lock(&file_priv->table_lock);
        idr_remove(&file_priv->object_idr, handle);
        spin_unlock(&file_priv->table_lock);
err_unref:
        drm_gem_object_handle_put_unlocked(obj);
        return ret;
}

int drm_gem_handle_create(struct drm_file *file_priv,
                          struct drm_gem_object *obj,
                          u32 *handlep)
{
        mutex_lock(&obj->dev->object_name_lock);

        return drm_gem_handle_create_tail(file_priv, obj, handlep);
}

六个动作按序：句柄计数自增（从 0 到 1 时额外抓一个引用）；idr_preload + 自旋锁下在 file_priv->object_idr 里分配 handle 号（从 1 开始）；放开 vma_node 让本 drm_file 可以 mmap；回调 funcs->open；写回 handle；任何一步失败就沿原路回滚。

注意 handle_count 与 refcount 的耦合点：if (obj->handle_count++ == 0) drm_gem_object_get(obj)。也就是「第一个句柄额外持一个引用」，之后每个句柄只增计数不增引用。所以对象的真实引用数是 1 + handle_count + 其他。

drm_gem_object_lookup() 是 handle → 对象的反向查找，在各驱动的 ioctl 入口都是第一行。它同时会 drm_gem_object_get() 一个引用，用完必须 drm_gem_object_put()。

drm_gem_handle_delete() 删句柄，但不销毁对象——它只解绑。要真正释放，最后一个引用 drop 时才走 funcs->free。

这条规则引出一个必踩的坑：驱动在 dumb_create 里创建对象后，创建时那个初始引用必须自己 drop，否则 handle 关掉了对象还在，泄漏。代码模板固定长这样：

c
        ret = drm_gem_handle_create(file_priv, obj, &handle);
        if (ret)
                goto err_handle_create;

        /* drop reference from allocate - handle holds it now. */
        drm_gem_object_put(obj);

flink 全局名：GEM_FLINK ioctl 把 handle 换成 obj->name（全局名），GEM_OPEN 反向。转换全在 core 里做，驱动不用管。问题在于名称是可猜测的小整数，任何进程猜到就能拿到你的 buffer，安全模型形同虚设。新代码别用。

PRIME dma-buf fd：drm_gem_prime_handle_to_fd() 把对象导出成 dma-buf fd，drm_gem_prime_fd_to_handle() 反向导入。这条路既能跨进程也能跨设备，是首选共享机制。跨驱动共享时，导入方拿到的对象 import_attach 非空，resv 指向导出方的 reservation object。

mmap 的两种建映射方式，原文的总结很到位：

  • 一次性映射：在 mmap 回调里 remap_pfn_range() 把整块物理内存直接铺给用户。
  • 缺页映射：mmap 只登记 vma 和 vm_ops，等用户访问触发缺页异常时在 fault 里 vm_insert_page() 一页一页补。

drm_gem_mmap() 属于第二种——它不真的映射内存，只按 mmap 的 offset 参数找到对应 GEM 对象，把 vma->vm_ops 设成 drm_driver.gem_vm_ops，靠驱动的 fault handler 逐页映射。所以「drm_gem_mmap 返回 0」不等于「内存已经映射好了」。

十七、dumb buffer 与 CMA helper #

dumb buffer 是 DRM 给「只想拿块内存画点东西」的客户端准备的最简路径：DRM_IOCTL_MODE_CREATE_DUMB 一条 ioctl 拿到 handle 和 pitch，MAP_DUMB 拿到 mmap 偏移。驱动侧只实现一个回调 dumb_create。

RK3399 的实现分三层。

第一层，rockchip_gem_dumb_create()，负责对齐和尺寸计算：

c
int rockchip_gem_dumb_create(struct drm_file *file_priv,
                             struct drm_device *dev,
                             struct drm_mode_create_dumb *args)
{
        struct rockchip_gem_object *rk_obj;

        /* 宽度 * 每像素位数 / 8 */
        int min_pitch = DIV_ROUND_UP(args->width * args->bpp, 8);

        /* align to 64 bytes since Mali requires it. */
        args->pitch = ALIGN(min_pitch, 64);

        args->size = args->pitch * args->height;

        rk_obj = rockchip_gem_create_with_handle(file_priv, dev, args->size,
                                                 &args->handle);

        return PTR_ERR_OR_ZERO(rk_obj);
}

64 字节对齐是给 Mali GPU 用的——GPU 的 tile 写回要求 stride 对齐，不对齐会撕裂或直接算错。这个约束所有窗口系统都遵守，所以 dumb buffer 也照做。

第二层，rockchip_gem_create_with_handle()：

c
static struct rockchip_gem_object *
rockchip_gem_create_with_handle(struct drm_file *file_priv,
                                struct drm_device *drm, unsigned int size,
                                unsigned int *handle)
{
        struct rockchip_gem_object *rk_obj;
        struct drm_gem_object *obj;
        bool is_framebuffer;
        int ret;

        is_framebuffer = drm->fb_helper && file_priv == drm->fb_helper->client.file;

        rk_obj = rockchip_gem_create_object(drm, size, is_framebuffer);
        if (IS_ERR(rk_obj))
                return ERR_CAST(rk_obj);

        obj = &rk_obj->base;

        ret = drm_gem_handle_create(file_priv, obj, handle);
        if (ret)
                goto err_handle_create;

        /* drop reference from allocate - handle holds it now. */
        drm_gem_object_put(obj);

        return rk_obj;

err_handle_create:
        rockchip_gem_free_object(obj);

        return ERR_PTR(ret);
}

is_framebuffer 的判断值得注意：如果这个 drm_file 是 fbdev 模拟层的，那它要的 buffer 会一直扫描出去，所以走另一条分配策略（drm_gem_cma_create 系列里会考虑 CMA 的连续性要求）。

第三层，rockchip_gem_alloc_object() 建对象，rockchip_gem_alloc_buf() 分配物理内存：

c
static const struct drm_gem_object_funcs rockchip_gem_object_funcs = {
        .free = rockchip_gem_free_object,
        .get_sg_table = rockchip_gem_prime_get_sg_table,
        .vmap = rockchip_gem_prime_vmap,
        .vunmap = rockchip_gem_prime_vunmap,
        .mmap = rockchip_drm_gem_object_mmap,
        .vm_ops = &drm_gem_dma_vm_ops,
};

static struct rockchip_gem_object *
        rockchip_gem_alloc_object(struct drm_device *drm, unsigned int size)
{
        struct rockchip_gem_object *rk_obj;
        struct drm_gem_object *obj;

        size = round_up(size, PAGE_SIZE);

        rk_obj = kzalloc(sizeof(*rk_obj), GFP_KERNEL);
        if (!rk_obj)
                return ERR_PTR(-ENOMEM);

        obj = &rk_obj->base;
        obj->funcs = &rockchip_gem_object_funcs;

        drm_gem_object_init(drm, obj, size);

        return rk_obj;
}

注意 funcs 必须在 drm_gem_object_init() 之前填——后者会走到 drm_gem_private_object_init()，而那条路径不碰 funcs，但顺序上先填没坏处，反过来忘了填就会在后面 drm_gem_handle_create_tail() 里解引用空指针。

物理内存分配的分叉在 rockchip_gem_alloc_buf()：

c
static int rockchip_gem_alloc_buf(struct rockchip_gem_object *rk_obj,
                                  bool alloc_kmap)
{
        struct drm_gem_object *obj = &rk_obj->base;
        struct drm_device *drm = obj->dev;
        struct rockchip_drm_private *private = drm->dev_private;

        if (private->domain)
                return rockchip_gem_alloc_iommu(rk_obj, alloc_kmap);
        else
                return rockchip_gem_alloc_dma(rk_obj, alloc_kmap);
}

private->domain 是 IOMMU 域。设备树里 VOP / GPU 节点挂了 iommus 属性，probe 时就会设上 private->domain，此时走 IOMMU 路径：rockchip_gem_get_pages() 拿页面 → rockchip_gem_iommu_map() 建 IOMMU 映射 → 需要内核虚拟地址时 vmap() 一下。

没 IOMMU 时走 rockchip_gem_alloc_dma()，直接 dma_alloc_attrs() 要一块物理连续的 DMA buffer，属性 DMA_ATTR_WRITE_COMBINE（写合并，适合帧缓冲）；不需要内核侧映射时再叠一个 DMA_ATTR_NO_KERNEL_MAPPING 省掉 vmalloc 区。

c
static int rockchip_gem_alloc_dma(struct rockchip_gem_object *rk_obj,
                                  bool alloc_kmap)
{
        struct drm_gem_object *obj = &rk_obj->base;
        struct drm_device *drm = obj->dev;

        rk_obj->dma_attrs = DMA_ATTR_WRITE_COMBINE;

        if (!alloc_kmap)
                rk_obj->dma_attrs |= DMA_ATTR_NO_KERNEL_MAPPING;

        rk_obj->kvaddr = dma_alloc_attrs(drm->dev, obj->size,
                                         &rk_obj->dma_addr, GFP_KERNEL,
                                         rk_obj->dma_attrs);
        if (!rk_obj->kvaddr) {
                DRM_ERROR("failed to allocate %zu byte dma buffer", obj->size);
                return -ENOMEM;
        }

        return 0;
}

rockchip_fb_create() 的活是「把用户空间传来的一组 GEM handle 变成一个 framebuffer」：

c
static const struct drm_framebuffer_funcs rockchip_drm_fb_funcs = {
        .destroy       = drm_gem_fb_destroy,
        .create_handle = drm_gem_fb_create_handle,
        .dirty         = drm_atomic_helper_dirtyfb,
};

static struct drm_framebuffer *
rockchip_fb_create(struct drm_device *dev, struct drm_file *file,
                   const struct drm_mode_fb_cmd2 *mode_cmd)
{
        struct drm_afbc_framebuffer *afbc_fb;
        const struct drm_format_info *info;
        int ret;

        info = drm_get_format_info(dev, mode_cmd);
        if (!info)
                return ERR_PTR(-ENOMEM);

        afbc_fb = kzalloc(sizeof(*afbc_fb), GFP_KERNEL);
        if (!afbc_fb)
                return ERR_PTR(-ENOMEM);

        ret = drm_gem_fb_init_with_funcs(dev, &afbc_fb->base, file, mode_cmd,
                                         &rockchip_drm_fb_funcs);
        if (ret) {
                kfree(afbc_fb);
                return ERR_PTR(ret);
        }

        if (drm_is_afbc(mode_cmd->modifier[0])) {
                int ret, i;

                ret = drm_gem_fb_afbc_init(dev, mode_cmd, afbc_fb);
                if (ret) {
                        struct drm_gem_object **obj = afbc_fb->base.obj;

                        for (i = 0; i < info->num_planes; ++i)
                                drm_gem_object_put(obj[i]);

                        kfree(afbc_fb);
                        return ERR_PTR(ret);
                }
        }

        return &afbc_fb->base;
}

为什么用 drm_afbc_framebuffer 而不是裸 drm_framebuffer？因为 AFBC（ARM Frame Buffer Compression）除了普通平面参数，还要记 header 大小、tile 布局等额外信息，所以套了一层。不用 AFBC 时这层壳的额外字段是零，白占几十字节，但不影响正确性。

drm_gem_fb_init_with_funcs() 是 core 提供的辅助，干的活：

  1. drm_get_format_info() 拿格式元数据。
  2. 遍历每个 color plane，按 hsub/vsub 算该 plane 的宽高。
  3. drm_gem_object_lookup(file, mode_cmd->handles[i]) 找到对应 GEM 对象。
  4. 算最小尺寸 (height - 1) * pitch + min_pitch + offset，和 obj->size 比对，小了就 -EINVAL。
  5. 调 drm_gem_fb_init() 填好 fb->obj[] 并 drm_framebuffer_init()。

第 4 步的尺寸校验经常被用户空间踩：传了个 stride 没对齐的 fb，算出最小尺寸比对象大，直接 EINVAL，而错误信息只在 drm_dbg_kms 里，默认看不到。查这类问题要打开 dynamic debug。

c
static int
drm_gem_fb_init(struct drm_device *dev,
                 struct drm_framebuffer *fb,
                 const struct drm_mode_fb_cmd2 *mode_cmd,
                 struct drm_gem_object **obj, unsigned int num_planes,
                 const struct drm_framebuffer_funcs *funcs)
{
        unsigned int i;
        int ret;

        drm_helper_mode_fill_fb_struct(dev, fb, mode_cmd);

        for (i = 0; i < num_planes; i++)
                fb->obj[i] = obj[i];

        ret = drm_framebuffer_init(dev, fb, funcs);
        if (ret)
                drm_err(dev, "Failed to init framebuffer: %d\n", ret);

        return ret;
}

  • crtc_state->plane_mask / connector_mask / encoder_mask：运行时实际挂载关系，全部 32 位。

十九、从设备树到完整显示通路的建立 #

possible_crtcs 从哪来？设备树的 ports / port / endpoint 结构。

RK3399 的 VOP 节点在 DT 里长这样（简化）：

dts
vopb: vop@ff900000 {
        compatible = "rockchip,rk3399-vop-big";
        reg = <0x0 0xff900000 0x0 0x2000>, <0x0 0xff901000 0x0 0x1000>;
        interrupts = <GIC_SPI 118 IRQ_TYPE_LEVEL_HIGH 0>;
        clocks = <&cru ACLK_VOP0>, <&cru HCLK_VOP0>;
        clock-names = "aclk_vop", "hclk_vop";
        iommus = <&vopb_mmu>;
        power-domains = <&power RK3399_PD_VOPB>;

        vopb_out: port {
                #address-cells = <1>;
                #size-cells = <0>;

                vopb_out_edp: endpoint@0 {
                        reg = <0>;
                        remote-endpoint = <&edp_in_vopb>;
                };
                vopb_out_hdmi: endpoint@1 {
                        reg = <1>;
                        remote-endpoint = <&hdmi_in_vopb>;
                };
                vopb_out_dsi: endpoint@2 {
                        reg = <2>;
                        remote-endpoint = <&dsi_in_vopb>;
                };
        };
};

关键点：一个 VOP 有一个 port，下面若干 endpoint，每个 endpoint 通过 remote-endpoint 指到下游（HDMI TX、eDP、DSI）的输入 endpoint。下游节点再反向指回来。这就构成一张图。

内核从这张图推导 possible_crtcs：drm_of_find_possible_crtcs() 走一遍 port 的所有 endpoint，看每个 remote 属于哪个 CRTC 的 port，拼成位掩码。CRTC 的 port 字段（struct drm_crtc.port）就是这里的入口——注释写 OF node used by drm_of_find_possible_crtcs()。

驱动 probe 时填 possible_crtcs 的典型写法：

c
        vop->crtc.port = of_graph_get_port_by_id(dev->of_node, 0);
        ...
        encoder->possible_crtcs = drm_of_find_possible_crtcs(drm, np);
        if (!encoder->possible_crtcs)
                encoder->possible_crtcs = drm_crtc_mask(crtc);

注意这里有个必须显式兜底的写法（历史上很多驱动踩过）：如果 DT 图里某个输出端没被引用，drm_of_find_possible_crtcs() 会返回 0，此时驱动得自己设上 drm_crtc_mask(crtc)。不兜底的话 encoder 谁也接不上，用户空间看到的就是「这个口没输出」。

依赖顺序也必须对：of_graph_get_port_by_id() 要在 drm_crtc_init_with_planes() 之前，因为后者只看 plane 的 possible_crtcs，不看 CRTC 的 port；而 encoder 的 possible_crtcs 必须在 drm_dev_register() 之前设好，否则 core 会 WARN。

      -> component_match_add() 注册所有子组件
      -> component_master_add_with_match()

[2] 各子组件 probe（VOP / HDMI TX / eDP / DSI / 各 bridge）

text
drm_atomic_helper_check_modeset()
  ├─ connector_helper.mode_valid / mode_valid_ctx
  ├─ encoder_helper.atomic_check
  ├─ crtc_helper.mode_valid / mode_fixup
  └─ bridge_funcs.atomic_check（反序：链尾 → 链头）

drm_atomic_helper_check_planes()
  ├─ plane_helper.atomic_check（先）
  └─ crtc_helper.atomic_check（后，可分配共享资源）

drm_atomic_helper_commit_modeset_disables()   CRTC 关断路径
  ├─ encoder_helper.atomic_disable
  ├─ bridge.atomic_disable / atomic_post_disable（下游 → 上游）
  └─ crtc_helper.atomic_disable

drm_atomic_helper_commit_planes()
  ├─ crtc_helper.atomic_begin
  ├─ plane_helper.atomic_update / atomic_disable
  └─ crtc_helper.atomic_flush

  ├─ crtc_helper.atomic_enable
  ├─ bridge.atomic_pre_enable / atomic_enable（上游 → 下游）

这个次序的物理含义：关的时候先让下游停止接收（避免收到残缺帧），再关上游时钟；开的时候先让上游时钟稳住，再放开下游。反了就会在示波器上看到半帧或抖动。

probe 失败最常见的原因排序（实机经验）：时钟没拿到、电源域没上电、DT 的 endpoint 连错了导致 possible_crtcs 为 0、iommus 属性缺失导致 GEM 分配走了 DMA 路径但 buffer 地址 VOP 访问不到。

验证手段，用 sysfs 和 debugfs 直接看：

bash
# 1. 看 connector 状态和模式
cat /sys/class/drm/card0-HDMI-A-1/status
cat /sys/class/drm/card0-HDMI-A-1/modes

# 2. 读原始 EDID，前 8 字节应为 00 ff ff ff ff ff ff 00
cat /sys/class/drm/card0-HDMI-A-1/edid | hexdump -C | head -4

# 3. 看原子状态快照（最关键的一份）
cat /sys/kernel/debug/dri/0/state

# 4. 看 crtc 帧计数
cat /sys/kernel/debug/dri/0/crtc-0/summary

# 5. 看当前挂在 drm 上的进程
cat /sys/kernel/debug/dri/0/clients

/sys/kernel/debug/dri/0/state 是排查「画面不对」的第一站：它会列出每个 CRTC、plane、connector 的当前属性值，包括 MODE_ID、ACTIVE、FB_ID、SRC_*、CRTC_*。如果这里显示的一切正常但屏幕仍黑，问题一定在 encoder 之后。

/sys/kernel/debug/dri/0/crtc-0/summary 里的 frame 计数一直在涨说明扫描在跑，停在某个值说明 CRTC 被关掉了或者卡在 vblank 里。

真机上屏幕不亮，按这个顺序查，一路缩小范围：

2. cat /sys/class/drm/card0-*/status
     connected 才往下走；unknown 说明 detect 没实现或 DDC 不通

     空说明 EDID 没读到或解析失败；看 /sys/class/drm/card0-*/edid 是否全 0

     MODE_ID 非 0、ACTIVE=1、FB_ID 非 0 才说明用户空间真的提了模式

     frame 计数上涨 = 扫描在跑；停了 = CRTC 被关或 vblank 卡死

6. 到这一步还黑，问题在 encoder/bridge/PHY
     量时钟、看 PHY 寄存器、示波器看 TMDS 差分对

第 5 步和第 6 步的分界线很重要：frame 在涨说明 KMS 层已经把该做的都做了，剩下的责任在 bridge 和 PHY；frame 不涨说明问题还在 KMS 层的属性提交或者 CRTC 的寄存器配置上。
