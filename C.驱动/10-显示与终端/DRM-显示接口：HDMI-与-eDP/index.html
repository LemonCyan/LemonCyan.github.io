一、两种显示接口：HDMI 与 eDP 的定位 #

RK3399 有两个 VOP。VOPB 是 big，最大 4096x2160@60Hz；VOPL 是 lite，最大 2560x1600@60Hz。两个 VOP 都能接 HDMI、eDP、DP、MIPI DSI0、MIPI DSI1。同一时刻一个显示接口只能绑一个 VOP，绑哪个由设备树里 endpoint 的 status 决定，这层关系由 GRF 里的 lcdc_sel 位最终落地。

HDMI 是外接接口，线缆可插拔、线长可达数米，靠 HPD 热插拔检测，靠 DDC 读 EDID。eDP 是嵌入式接口，走 FPC 排线，面板焊死在机器里，设计上默认不需要 HPD，靠 force-hpd 骗过驱动。

二、HDMI 协议基础 #

HDMI 全称 High Definition Multimedia Interface，高清多媒体接口，在一根线缆上同时传全数字高清视频和多声道音频。它基于 TMDS 协议，用在 DVD、机顶盒这类 source 到 TV、显示器这类 sink 之间。

HDMI 向下兼容 DVI。差别只有一条：DVI 只能传视频，不能同时传音频。

先把术语列清楚，后面代码里到处都是缩写：

  • HDCP（High-bandwidth Digital Content Protection）：内容保护，通过 I2C 读取密钥。
  • EDID（Extended Display Identification Data）：显示器能力描述，含供应商、尺寸、色域、时序、名称、序列号。
  • DDC（Display Data Channel）：本质就是 I2C，用来读 EDID 与 HDCP 密钥。
  • HPD（Hot Plug Detect）：热插拔检测。
  • CEC（Consumer Electronics Control）：用户电气控制，遥控器那条线。
  • TMDS（Transition Minimized Differential Signaling）：最小化传输差分信号。
  • HEAC（HDMI Ethernet and Audio Return Channel）：以太网与音频回传，需要额外 PHY。
  • Source / Sink：输出侧 / 输入侧。
  • CTS（Compliance Test Specification）：一致性测试规范。

HDMI 系统由 source 和 sink 两端组成。一条 HDMI 线里有五样东西：

  • 四路差分信号：三路 TMDS Data（蓝色通道 Channel0、绿色 Channel1、红色 Channel2）加一路 TMDS Clock。TMDS 不只传视频，音频和辅助信息也在里面。
  • 一个 DDC 通道：source 和 sink 交换状态，告诉 source 对面能收什么。
  • HPD：线插好后 sink 把该信号拉高，source 收到后开始发数据。
  • CEC：遥控用途，可选。
  • HEAC：以太网与音频回传，可选。

由此可以直接推出四件事：要传音视频，有 TMDS 就够；要用遥控器，得有 CEC；要做到分辨率自适应屏幕，得有 DDC；要支持热插拔，得实现 HPD。

HDMI 有 A、B、C、D、E 五种接口类型，常用的是 Type A：

  • A：19 pin，宽 13.9 毫米，厚 4.45 毫米。
  • B：29 pin，宽 21 毫米。
  • C：常称 Mini HDMI，为小型设备设计。
  • D：尺寸更小，用于手机、平板。
  • E：车载娱乐系统用，具备抗震、防潮、耐高强度、大温差等特性。

Type A 的 19 个引脚分工如下：

引脚 用途
1~9 TMDS Data，共三组差分
10~12 TMDS Clock，一组差分
13 CEC
14 保留
15、16 DDC 的 SCL 与 SDA（基于 I2C）
17 DDC/CEC 地
18 +5V 电源
19 HPD，热插拔检测

RK3399 板级接线只需记住三根关键信号：DDC_SCL 接 GPIO2_B0（复用为 I2C7_SCL），DDC_SDA 接 GPIO2_A7（I2C7_SDA），PORT_CEC 接 GPIO4_C7（HDMI_CECINOUT）。注意 GPIO4_C7 这颗引脚被 HDMI 的 CEC 和 eDP 的 HPD 共用，后面双屏会踩坑。

RK3399 的 HDMI TX 能力：支持 HDMI 2.0a、4K@60Hz、HDCP 1.4/2.2。供电上 HDMI_AVDD_0V9 由 VCCA0V9_S3 提供、HDMI_AVDD_1V8 由 VCC1V8_S3 提供，两者都可视作常供电，所以驱动里即使拿不到 regulator 也不会影响出图。

三、HDMI 的版本演进与带宽 #

版本迭代的主线就一条：把带宽一路堆上去，顺手补齐音频与 HDR。素材里有价值的是各代的带宽数值与对应的分辨率上限，逐个列出来：

版本 发布时间 带宽 / 像素时钟 关键能力
HDMI 1.0 2002 最高 5Gbps 首版，基于 TMDS
HDMI 1.1 2004 年 5 月 同上 新增 DVD Audio 支持
HDMI 1.2 2005 年 8 月 像素时钟 165MHz，约 4.95Gbps 解决 1080P 与 PC 点对点问题，改善与电脑设备兼容性
HDMI 1.3 2006 年 6 月 单链接带宽频率提到 340MHz，数据量 10.2Gbps 色深从 24 位扩到 30/36/48 位（RGB 或 YCbCr）
HDMI 1.4 2009 受制于 10.2Gbps 支持 4K，但只能到 3840x2160@30Hz，并引入太网与音频回传
HDMI 2.0 2013 18Gbps 3840x2160@50/60Hz，32 声道，1536kHz 采样率
HDMI 2.0a 2015 18Gbps 只加了一项：HDR 格式传输
HDMI 2.0b 2016 18Gbps 与 2.0a 差别很小，兼容此前全部规格
HDMI 2.1 2017 理论 48Gbps 8K、VRR、更高色深

1.3 这一代的算术要单独拆一下，里面有个容易绕进去的地方。1.3 版的线由 4 对传输通道组成：1 对时钟通道，另 3 对是 TMDS 数据通道，每对速率 3.4Gbps，三对合计 3 x 3.4 = 10.2Gbps。这 10.2Gbps 是链路层聚合带宽，落到每通道的数字是 3.4Gbps。

几个必须记住的换算关系：像素时钟与 TMDS Clock 是 1:1，两者频率相同；每个 TMDS 通道串行率是像素时钟的 10 倍，因为 8bit 编码成 10bit；24bpp 下总串行率 = 像素时钟 x 10 x 3 = 像素时钟 x 30；单通道串行率 = 像素时钟 x 10，超过 TMDS 单通道上限时要拆成双链接（dual-link），即同样的 3 组数据线再来一组，这就是 DVI 的 dual-link 方案。

拿 1920x1080@60Hz 验一遍：htotal 2200，vtotal 1125，像素时钟 = 2200 x 1125 x 60 = 148.5MHz。单通道串行率 1.485Gbps，三通道合计 4.455Gbps，24bpp 的有效数据率 148.5MHz x 24 = 3.564Gbps。这就是 1.2 版本 4.95Gbps 带宽刚好够 1080P 的原因。

再看 2.0 的 18Gbps：4K@60Hz 10bit 4:4:4 需要的像素时钟约 594MHz，单通道串行率 5.94Gbps，三通道 17.82Gbps，加上编码开销正好顶到 18Gbps 这条线。这也是 6.3 内核里 rockchip_phy_config 最后一项 594000000 的来源。

RK3399 落在 2.0a 这一档。驱动里检测到的控制器版本字符串是 Detected HDMI TX controller v2.11a with HDCP (DWC HDMI 2.0 TX PHY)，v2.11a 是 DesignWare IP 的版本号，不是 HDMI 规范版本号，两者别混。

四、TMDS 与差分信号 #

TMDS（Transition Minimized Differential Signaling）最小化传输差分信号，是 Silicon Image 开发的高速数据传输技术。差分传输用两个引脚传一路信号，靠两脚间电压差的正负与大小决定数值 0 或 1。

TMDS 链路分发送端 source 和接收端 sink，链路包含 3 个数据通道和 1 个时钟通道：

  • 发送端对数据编码、并串转换，分配到独立通道发出去。
  • 接收端收串行信号，解码、串并转换，送到显示器控制端。

发送端左边是源，右边是接收，可以看作发送与接收两端。源侧有蓝、绿、红三个数据通道，加一个时钟通道：

  • 时钟通道：让收发两端同步在同一时钟网络下，避免累积误差。
  • 数据通道：
    • 每个通道有 8 位像素位，传颜色数据。
    • 每个通道另有 2 位控制位：蓝色通道传 HSYNC、VSYNC；绿色通道传 CTL0、CTL1；红色通道传 CTL2、CTL3。
    • 每个通道还有 4 位在 Data Island 周期传音频。

编码阶段是关键：Encoder 把 8bit 并行视频数据变成 10bit 串行数据，所以串行数据率必须是像素时钟的 10 倍。接收端反向做串并转换与解码。TMDS 不只编码 video，还编码 audio 和控制信号。

TMDS 链路把传输分成三个阶段：

阶段 内容
Control Period 既没有视频也没有音频、辅助数据时处于此阶段，传 HSYNC/VSYNC 与 Preamble
Data Island Period 传音频与辅助信息（InfoFrame 等），以 2 字符前导保护边界开始，2 字符末尾保护边界结束
Video Data Period 传实际有效视频像素，以报文头为前导，之后以两个字符作视频前导保护边界，没有末尾保护边界

TMDS 传四类数据：

类型 承载通道与位宽
Control 经 Channel1、Channel2 的 D[1:0] 传输，共 4bit，决定接下来是 Data Island 还是 Video Data
Data Island 音频经 3 个 Channel 的 D[3:0] 传，共 12bit；辅助数据包同通道
Video Data RGB 或 YUV 像素，R/G/B 分别走 Channel2/1/0，每色 8bit，共 24bit
HSYNC/VSYNC 走 Channel0 的 D[1:0]，共 2bit

以 720x480p 一帧为例：蓝色部分是 Data Island Period，深灰是有效图像 Video Data Period，浅灰是 Control Period。有效图像部分宽度正好是 720；不传 Data Island 的时候都在传 Control。

三段再拆细一点：Control Period 里，Channel0 传 HSYNC/VSYNC，Channel1[1:0] 与 Channel2[1:0] 传 Preamble，在 Control Period 的最后阶段，CTL0~CTL3 组成的文件头说明下一个周期是 Data Island 还是 Video Data；Data Island Period 里，Channel0[3:2] 传 Data Island Header（包头），Channel1[3:0] 与 Channel2[3:0] 传 Data Island Content（包内数据）；Video Data Period 里，24 位像素信号经编码生成三路 TMDS 数据通道，每通道 8 位转 10 位，每个 10 位像素周期送出一个最小化跳变的序列。

控制数据一共 6 位（每通道 2 位），采用 2bit 到 10bit 的编码方式，两端的码表是固定的，这也是接收端能无歧义恢复 D[1:0] 的原因。这就是「为什么像素时钟跑 148.5MHz、线上却要跑 1.485Gbps」的完整解释：10 倍冗余换编码增益与直流平衡。

五、HDMI 的音频传输 #

HDMI 的音频不是独立线缆，而是塞进 TMDS 的 Data Island 周期里传。每个通道 4bit，三通道合计 12bit，这就是音频在物理层上的全部预算——只有视频位宽的一半。

音频包走 Data Island，因此音频带宽被 Video Data 挤在中间。这也是为什么改分辨率会顺带影响音频流重新配置。

Linux 侧的实现在 dw_hdmi_probe 里，按控制器能力注册三种音频 platform device 之一：

config0 & HDMI_CONFIG0_I2S dw-hdmi-i2s-audio dw_hdmi_i2s_audio_enable / dw_hdmi_i2s_audio_disable
config3 & HDMI_CONFIG3_GPAUD dw-hdmi-gp-audio dw_hdmi_gp_audio_enable / dw_hdmi_gp_audio_disable

sample_rate、channels 在 probe 里给了默认值：

        hdmi->channels = 2;

还有一个坑写在 dw_hdmi_probe 的注释里：必须在使能 PHY 之前调用 hdmi_init_clk_regenerator，把 clk regenerator 的 N 与 cts 写好，否则 HDMI_IH_FC_STAT2 会溢出：

c
        /*
         * To prevent overflows in HDMI_IH_FC_STAT2, set the clk regenerator
         * N and cts values before enabling phy
         */
        hdmi_init_clk_regenerator(hdmi);

CTS/N 是音频时钟与视频时钟之间的桥，视频时序一变，这两个值就得跟着重算。这解释了另一个现象：改分辨率后音频卡顿或爆音，往往是 regenerator 重配时序问题，不是 I2S 时钟本身。

六、EDID：显示器的能力描述 #

EDID 全称 Extended Display Identification Data，外部显示设备标识数据。VGA、DVI 的 EDID 由主块 128 字节组成，HDMI 的 EDID 再加扩展块（每块 128 字节），扩展块内容主要是音频属性相关，定义在 CEA-861x 标准里。理论上可以继续扩到 512 字节或 256 的整数倍。

它包含显示器及其性能的全部参数：供应商信息、最大图像尺寸、颜色设置、厂商预置、频率范围限制、显示名与序列号。形象说法：EDID 就是显示器的身份证、户口本、技能证书的集合，目的是告诉别人我是谁、从哪来、能干什么。

CRT 时代没有 EDID。显示器种类越来越多，模拟的、数字的、普屏的、宽屏的、17 寸、19 寸、22 寸，PC 就傻眼了：分辨率与时序种类太多，每种显示器又无法全支持，怎么知道该给什么分辨率？随便输出一个还有损坏硬件的风险。于是 EDID 出场当传话筒：显示器告诉 PC「我能显示 N 种分辨率，最佳是 XXX」，PC 回一句「收到，按最佳输出」。

两个关键约束：EDID 通过 DDC 通道（I2C）传输；一台显示器会带多份 EDID。现在显示器常带多个视频接口，DVI、VGA、HDMI、DP 各接口特性与带宽不同，EDID 也不同。用哪个接口，PC 读到的就是哪个接口的 EDID。

制造商名用 3 个字母，基于压缩 ASCII：00001=A、00010=B，一直到 11010=Z。两个字节合起来 16 位，去掉最高位的保留位后正好 15 位，够放 3 个 5 位字母。

0x14 的视频信号定义按 bit7 分两种解释。bit7=0 是模拟信号：bit[6:5] 是信号电平（00 = 0.700/0.300，1.000Vp-p；01 = 0.714/0.286；10 = 1.000/0.400，1.400Vp-p；11 = 0.700/0.000），bit[4:3] 是 setup，bit[3:0] 是同步输入支持（bit3 同步分离、bit2 同步复合、bit1 SOG、bit0 场同步扫描起点）。bit7=1 是数字信号：bit[6:1] 保留，bit0 表示 DFP 1.x 兼容（1 pixel / clock, up to 8 bits / color MSB aligned, DE active high）。

0x18 的特性位：bit7 Standby、bit6 Suspend、bit5 Active Off/Very Low Power、bit[4:3] 显示类型（00 黑白/灰度、01 RGB 彩色、10 非 RGB 多彩如 RGY、11 未定义）、bit2 标准默认颜色空间 sRGB、bit1 推荐分辨率模式（置 1 表示第一个 Detailed Timing 是推荐分辨率）、bit0 支持 GTF。

举一组实测字节 0x2F 0xCF 0x00：解析出来是 640x480@60Hz、640x480@72Hz、640x480@75Hz、800x600@56Hz、800x600@60Hz、800x600@72Hz、800x600@75Hz、1024x768@60Hz、1024x768@70Hz、1024x768@75Hz、1280x1024@75Hz，共 11 项。

Standard Timings 是对内建时序的扩充，最多描述 8 个时序，每 2 字节一个，这些时序都不在 Established Timings 里。第一个字节是 (行有效像素 / 8) - 31；第二个字节 bit[7:6] 是宽高比（00 = 1:1、01 = 4:3、10 = 5:4、11 = 16:9），bit[5:0] 是 刷新率 - 60（范围 60~123Hz）。宽高比等于行像素/列像素。

举例 0x71 0x40：行有效像素 = (0x71 + 31) x 8 = 1152；宽高比 4:3，列有效像素 = 1152 x 3 / 4 = 864；刷新率 = 0 + 60 = 60Hz。得到 1152x864@60Hz。

Detailed Timings 是整个 EDID 里跟驱动关系最密切、改动最频繁的区域。4 个块，每块 18 字节，共 72 字节。每块既可以是时序说明（Timing Descriptor）也可以是显示器描述符（Monitor Descriptor）。

约束两条：

  • Block 1 必须是时序说明。
  • EDID 1.4 及以上，第一个详细时序就是最佳时序；EDID 1.4 以下，要看 0x18 的 bit1（推荐分辨率位）是否为 1。

Monitor Descriptor 的第 1 个字节为 0、第 2 个字节是类型码：ff 序列号、fe 字符串、fd 显示器频率范围、fc 显示器名、fb 色度点、fa 标准时序、f9 未定义、f8 厂商保留。

CEA-861 扩展块（第二块 EDID，字节 128~255）的头三个字节是 tag、revision、DTD 起始偏移；第 131 字节是 Display Support 位（DTV Underscan、Basic Audio、YCbCr 4:4:4、YCbCr 4:2:2 以及 Native Formats 数量）；之后是一串 Data Block，每个块 1 字节 tag/长度加 payload，最常见的是 Video Data Block（VDB，里面装着 CEA 的 VIC 短码）。VIC 短码对应的分辨率与时序由内核的 cea_mode_alternate_clock、cea_mode_for_vic 查表得到，不属于 EDID 数据本身。

七、EDID 的解析与使用 #

内核用 struct edid 描述 EDID 主块，定义在 include/drm/drm_edid.h，字段与上一章的字节布局一一对应，都是纯字节映射、无额外语义（serial 那项在源码里标了 FIXME: byte order）。

三个子结构都是纯字节映射，没有额外语义：struct est_timings 是三个 u8（t1、t2、mfg_rsvd）；struct std_timing 是两个 u8（hsize、vfreq_aspect），配套两个宏 EDID_TIMING_ASPECT_SHIFT（6，掩码 0x3）与 EDID_TIMING_VFREQ_SHIFT（0，掩码 0x3f，取值后要加 60）；struct detailed_timing 用一个 union 兼容两种块：__le16 pixel_clock 后面接 detailed_pixel_timing（Timing Descriptor）或 detailed_non_pixel（Monitor Descriptor）。

pixel_clock 的单位是 10kHz，这一条必须记住，否则时序推导会差两个数量级。EDID 里存 0xBCD3 = 48339，drm_mode_detailed 里算出 mode->clock = 48339 * 10 = 483390（单位 kHz），实际像素时钟 483.39MHz，对应 TMDS 串行率 4.8339Gbps。原文有一句"TMDS 时钟频率为 483390000Hz*10"，方向是对的，但数值写成 4833900KHz 与像素时钟混淆了，以「像素时钟 483.39MHz、串行率 = 像素时钟 x10」为准。

Timing Descriptor 的 16 字节载荷是 struct detailed_pixel_timing，按字节顺序为 hactive_lo、hblank_lo、hactive_hblank_hi、vactive_lo、vblank_lo、vactive_vblank_hi、hsync_offset_lo、hsync_pulse_width_lo、vsync_offset_pulse_width_lo、hsync_vsync_offset_pulse_width_hi、width_mm_lo、height_mm_lo、width_height_mm_hi、hborder、vborder、misc。取位规则见下面的手算表。

Monitor Descriptor 的载荷是 struct detailed_non_pixel：pad1（值为 0，标识该 block 被使用）、type、pad2，然后是 union（str 字符串 / range 频率范围 / color 色度点 / timings[6] 六个标准时序 / cvt[4] 四个 CVT 码）。timings[6] 只在 type = EDID_DETAIL_STD_MODES（0xfa）时生效，cvt[4] 只在 type = EDID_DETAIL_CVT_3BYTE（0xf8）时生效。

内核拿到 EDID 后的入口是 dw_hdmi_get_edid：没有 hdmi->ddc 直接返回 NULL；否则 drm_get_edid(connector, hdmi->ddc) 通过 DDC 的 I2C 从地址 0x50 读数据；读完后记两个 sink 能力位——drm_detect_hdmi_monitor → sink_is_hdmi，drm_detect_monitor_audio → sink_has_audio。

drm_get_edid 里有一个前置判断值得注意：connector->force == DRM_FORCE_OFF 直接返回 NULL；DRM_FORCE_UNSPECIFIED 时先 drm_probe_ddc 探一下有没有设备应答。这两个分支就是 force 属性为什么能"屏蔽不听话的显示器"的原因。

拿到 EDID 之后走 drm_add_edid_modes：先 drm_edid_is_valid 校验（不合法就 drm_warn 并置 NULL），再 drm_edid_legacy_init 初始化 drm_edid 壳子（drm_edid->size = edid_size(edid)），然后 update_display_info 填 connector->display_info，最后 _drm_edid_connector_add_modes 把时序转成模式。

update_display_info 是我们关心的部分。它先复位 display_info、清 ELD，然后按 EDID 版本逐段推进：edid_get_quirks 用面板 ID 到 edid_quirk_list 查 quirk（手上这块屏查不到，为 0）；width_mm/height_mm 由 cm x10 转来；drm_get_monitor_range 解析 0xfd 类型的频率范围；revision < 3 或非数字信号直接 out；否则置 DRM_COLOR_FORMAT_RGB444 并 drm_parse_cea_ext；EDID 1.3 带 DRM_EDID_DIGITAL_DFP_1_X 位时若 bpc 为 0 按 8bpc；revision < 4 到此为止；1.4 及以上按 DRM_EDID_DIGITAL_DEPTH_MASK 取 bpc（6/8/10/12/14/16）；按 features 位补 YCbCr444/422；drm_update_mso 处理多流；最后 drm_edid_to_eld 把音频 ELD 交给音频侧。

drm_parse_cea_ext 遍历扩展块时干两件事：把 CEA revision 记到 info->cea_rev；按第 131 字节（edid_ext[3]）的 EDID_CEA_YCRCB444、EDID_CEA_YCRCB422 位补颜色格式。之后 cea_db_iter_for_each 逐个 Data Block 分派：HDMI VSDB 走 drm_parse_hdmi_vsdb_video，HDMI Forum VSDB 与 SCDB 走 drm_parse_hdmi_forum_scds，Microsoft VSDB 走 drm_parse_microsoft_vsdb，Y420CMDB、Y420VDB 各有解析函数，VCDB 走 drm_parse_vcdb，HDR metadata block 走 drm_parse_hdr_metadata_block，普通 VDB 走 parse_cta_vdb。

_drm_edid_connector_add_modes 按 EDID 规范定义的优先级顺序添加模式。注释里列的规范顺序是：首选详细时序 → 主块的其他详细时序 → 扩展块的详细时序 → CVT 3 字节码 → 标准时序 → 内建时序 → 由 GTF/CVT 频率范围推断的模式。代码里的调用顺序是 add_detailed_modes、add_cvt_modes、add_standard_modes、add_established_modes、add_cea_modes、add_alternate_cea_modes、add_displayid_detailed_modes，最后若 EDID 特性位 DRM_EDID_FEATURE_CONTINUOUS_FREQ 置位再调 add_inferred_modes；结束前若 quirks 命中 EDID_QUIRK_PREFER_LARGE_60 或 _75，还会 edid_fixup_preferred。

注意代码顺序与注释顺序不完全一致：注释把 detailed modes from extension blocks 排在 CVT 之前，代码里 add_cea_modes 在 add_established_modes 之后才跑。这是历史实现与规范文档之间的偏差，实际效果对大多数屏没影响。

接下来逐个看解析器。

add_detailed_modes 处理 4 个 18 字节块。首要标志取决于 EDID 版本：revision >= 4 时第一个详细时序一定是最佳（closure.preferred = true）；否则看 0x18 的 DRM_EDID_FEATURE_PREFERRED_TIMING（bit1）。之后 drm_for_each_detailed_block(drm_edid, do_detailed_mode, &closure) 遍历，返回 closure.modes。

do_detailed_mode 先判块类型，非 Timing Descriptor 直接跳过；然后调 drm_mode_detailed 造模式；若 closure->preferred 为真就打上 DRM_MODE_TYPE_PREFERRED 并把标志清掉；再做一次 fixup_detailed_cea_mode_clock 修正 10kHz 精度带来的时钟偏差；最后 drm_mode_probed_add 入链表并计数。

drm_mode_detailed 的取位方式与我们手算的表格完全一致：hactive = (hi & 0xf0) << 4 | lo、vactive 同理；hblank = (hi & 0x0f) << 8 | lo、vblank 同理；hsync_offset 取 hi & 0xc0 左移 2 位，hsync_pulse_width 取 hi & 0x30 左移 4 位；vsync_offset 取 hi & 0xc 左移 2 位再并上 lo >> 4，vsync_pulse_width 取 hi & 0x3 左移 4 位再并上 lo & 0xf。

后面依次是若干否决条件：hactive 或 vactive 小于 64 直接丢掉；DRM_EDID_PT_STEREO 置位的立体模式不支持；hsync 或 vsync 脉宽为 0 视为错误时序丢掉；带 EDID_QUIRK_135_CLOCK_TOO_HIGH 的把时钟改成 1088x10 强行修；hsync_end > htotal、vsync_end > vtotal 时把 total 撑大 1。极性从 misc 的 DRM_EDID_PT_HSYNC_POSITIVE、DRM_EDID_PT_VSYNC_POSITIVE 取。

add_cvt_modes 找 EDID_DETAIL_CVT_3BYTE 类型的 Monitor Descriptor，即 type=0xf8 的 CVT 3 字节码块。drm_cvt_modes 对 4 个 CVT 码逐个解码：高度 = (code[0] + ((code[1] & 0xf0) << 4) + 1) * 2，宽度按 code[1] & 0x0c 的宽高比算出（4:3、16:9、16:10、15:9），刷新率从 code[2] 的支持位取，码表是 {60, 85, 75, 60, 50}。我们这块屏的第四个块是 Monitor Name（type=0xfc），所以这条路径空跑。

add_standard_modes 循环 8 次，每次把 standard_timings[i] 交给 drm_mode_std，成功就 drm_mode_probed_add 入链表。drm_mode_std 是把「宽 × 8 + 248」和「宽高比 + 刷新率」还原成真实模式的地方，逻辑顺序是：取 aspect_ratio 与 vfreq 两个字段 → standard_timing_level 判断用 DMT/GTF/GTF2/CVT 哪套算法 → 按宽高比算 vsize → 查 drm_dmt_modes（先试 reduced blanking 版本再试普通版本）→ 查不到就按 timing_level 现场生成。

以 0x71 0x40 为例走一遍：aspect_ratio = (0x40 & 0xc0) >> 6 = 1（4:3）；vfreq = 0x40 & 0x3f = 0，刷新率 60Hz；hsize = 0x71 x 8 + 248 = 1152；vsize = 1152 x 3 / 4 = 864；drm_monitor_supports_rb 为真，先按 RB 查 DMT 不中；再按非 RB 查，drm_dmt_modes 里只有 1152x864@75Hz，刷新率不匹配，仍不中；于是按 timing_level = LEVEL_GTF 现场用 drm_gtf_mode 生成一个 1152x864@60Hz。

八、eDP 协议基础 #

eDP 全称 Embedded DisplayPort，嵌入式显示接口，是基于 DisplayPort 架构与协议的一种内部数字接口。它用较简单的连接器、较少的引脚传递高分辨率信号，能实现多数据同时传输。

eDP 是 DP 面向嵌入式方向的架构与协议拓展，所以完全兼容 DP 协议。相对 DVI/HDMI，eDP 带宽高、整合性好、产品设计简单，已广泛用于笔记本、平板、手机等集成显示面板与图像处理器的领域。

eDP 的设计目标是取代较旧的数字视频传送接口，比如 LVDS，尤其在全高清 FHD（1920x1080 或 1920x1200）或超过 FHD 的面板上。

eDP 系统同样由 source 端与 sink 端组成。一条 eDP 链路分三块：

Main Link 是主通道，传视频与音频：

  • 由 1~4 对 lane 组成，每条 lane 是一对差分线，单向，从 source 指向 sink。
  • 每对差分线采用交流耦合，收发两端可以有不同的共模电压，接口因此能做得更小。
  • 数据采用 8B/10B 编码，eDP 1.4 中每条 lane 速率最大 5.4Gbps，最小 1.62Gbps。
  • 每条线都传数据，没有独立时钟线，EMI 因此更小。

AUX 是辅助通道：

  • 传小带宽数据、链路管理与设备控制。
  • 交流耦合差分传输，双向半双工。
  • 采用 Manchester II 编码。
  • 提供 1Mbps 传输速率与 15m 传输距离。
  • 低延时，每个传输任务要求小于 500us。
  • 提供 Link Services 与 Device Services，具体是连到 EDID 与 DPCD 存储器，通过总线方式读写。EDID 存显示器参数，DPCD 存链路层配置。

HPD 在 eDP 里是可选的。与 DP 一样，eDP 支持与该信号相关的全部功能，包括中断与链路故障通知。不用 HPD 时，source 可以轮询 sink 来检查链路完整性，但会增加 source 功耗，所以仍推荐用 HPD。

1.2 及以上版本的 Backlight control 是可选功能。

eDP 接口常用 FPC 排线，连接器主要是 20PIN、30PIN、40PIN 三种。NanoPC-T4 用的是 I-PEX-20455-030E，30PIN。

以标准时序 1920x1080@60Hz 为例：htotal 2200，vtotal 1125，field rate 60Hz，像素时钟 = 2200 x 1125 x 60 = 148.5MHz。24bpp 下需要的传输带宽 = 148.5MHz x 24 = 3.564Gbps。

eDP 1.4 单 lane 5.4Gbps，扣除 8B/10B 编码开销后有效数据带宽 = 5.4Gbps x 0.8 = 4.32Gbps。结论：单 lane 5.4Gbps 即可满足 1080p@60 24bpp 的传输需求。

为避免 link 带宽过载，数据打包速率只能等于或小于 link symbol 速率；小于时要插空闲字符，空闲字符放在 FS 与 FE 之间。一个基本传输单元（TU）包含 32~64 个 link symbol，传输过程中不能改变。举例：1920x1080@60Hz、24bpp、strm_clk = 148.5MHz、采用 2.7Gbps、4 lane 传输，TU 固定为 64，则每个 TU 只有 27 个 active symbol，其余用空闲字符填充。

NanoPC-T4 的 eDP 30PIN 接口除 lane 与 AUX 外还引出这些引脚：

GPIO1_C4_TP_INT 触摸面板中断，默认高电平，触摸时发低电平脉冲

这块屏是友善的 HD702E，1280x800、7 寸、电容触摸、背光可调（一线通讯），触摸走 I2C，触摸 IC 是 GT9271。GT9271 本质是 I2C 设备：一端接触摸屏模拟信号做采样与 AD 转换，另一端通过 I2C 把数据发给 SoC；触摸驱动就是 I2C 设备驱动，中断里读触摸坐标与按下状态。鼠标、键盘、触摸屏都属于 HID 设备，所以触摸数据必须按 HID 报告描述符规定的格式上报（HID 细节见《输入子系统》）。

上电之后 source 与 sink 的握手流程，按顺序共 11 步：

  1. sink 通过 HPD 向 source 发一个脉冲，告诉 source 有设备接入。
  2. source 通过 AUX 读 sink 的 DPCD 接收能力字段。
  3. sink 用 DPCD 接收能力字段应答。
  4. source 通过 AUX 读 sink 的 EDID，得知 sink 能显示的能力与参数。
  5. sink 通过 AUX 应答 EDID。
  6. source 写入 DPCD 链路配置字段。
  7. source 启动 Link Training，sink 做时钟恢复与均衡化。
  8. source 读取 DPCD 链路与 sink 状态。
  9. sink 回应链路与 sink 状态；如果 Main Link 不稳，回到第 7 步。
  10. source 发送 MSA（主流属性）数据。
  11. source 发送视频数据。

第 7 到第 9 步是一个可以反复的循环，这就是链路训练在整个协议里的位置——它不是一个可选步骤，而是上电必经的协商。

九、eDP 与 DP 的关系 #

一句话：eDP 是 DP 的一个 profile，不是另一套协议。凡是 DP 规定的电气层、编码、AUX、DPCD、链路训练，eDP 全部继承；eDP 只做减法与约束。

维度 DP eDP
定位 外部接口，机箱外走线 内部接口，机箱内 FPC 排线
兼容 — 完全兼容 DP 协议
lane 速率 1.62 / 2.7 / 5.4 / 8.1Gbps（按版本） 1.62 / 2.7 / 5.4Gbps（eDP 1.4）
HPD 是标配 可选，可用轮询替代
背光控制 无 1.2 及以上可选
PSR DP 1.2 后引入 eDP 重点特性，psr_supported 标志

四处在驱动里能直接看到的 eDP 专属项：struct analogix_dp_device 里的 force_hpd（嵌入式面板没有 HPD 线，靠设备树属性 force-hpd 让驱动假装已经插上）；fast_train_enable（允许跳过完整链路训练，直接用已知参数起链路，缩短点亮时间）；psr_supported（Panel Self Refresh，sink 侧带显存，画面静止时 source 可以停发，省电）；背光（eDP 面板的背光在 Linux 侧是独立子系统 pwm_bl + pwm-rockchip，不在 eDP 驱动里）。

所以调试 eDP 和调试 HDMI 的心态不同。HDMI 出问题先怀疑 EDID 与 TMDS 时钟；eDP 出问题先怀疑链路训练、AUX 通信和背光。

RK3399 的两个 VOP 与两个接口的映射关系是交叉的：

接口 可绑 VOP 设备树对应 endpoint
HDMI VOPB（支持 4K）、VOPL（只支持 2K） hdmi_in_vopb（endpoint@0）、hdmi_in_vopl（endpoint@1）
eDP VOPB、VOPL edp_in_vopb（port@0 的 endpoint@0）、edp_in_vopl（endpoint@1）

一个显示接口在同一时刻只能和一个 VOP 连接，所以在板级配置里要把使用的那条通路打开，不用的置 disabled。双屏时的典型组合是 HDMI 走 VOPB、eDP 走 VOPL，因为 eDP 面板 800x1280 用不着 4K 带宽。

十、eDP 的链路训练 #

链路训练是 source 与 sink 协商「用几条 lane、每条 lane 跑多快、发射端预加重多少、接收端均衡多少」的过程。DP 规范把它分成两个阶段：clock recovery 与 channel equalization。eDP 继承同一套流程。

阶段一：clock recovery #

目的：让 sink 从数据流里恢复出与 source 同频的时钟。

做法：source 按 Link Configuration 字段选定 rate 与 lane 数，向每条 lane 发固定图案（TPS1 = 1100001010，10bit 8B/10B 编码序列）。sink 用自己的 CR 电路尝试锁定。每条 lane 训练完成后，sink 在 DPCD 的 LANE0_1_CR_DONE / LANE2_3_CR_DONE 位上报。source 读回，全部 CR_DONE 才进入下一阶段。

CR 失败时 source 调整参数重试：先提高 drive current（发射电流，DPCD 的 TRAINING_LANEx_SET 的 drive current 位），到顶之后再调 pre-emphasis。每一项都有上限，参数表在 DPCD 的 MAX_ 前缀寄存器里，sink 事先声明了它支持到什么程度。

阶段二：channel equalization #

目的：补偿线缆与连接器在中高频段的衰减，让符号眼图张开。

做法：source 发 TPS2、TPS3、TPS4 图案（具体取决于电压摆幅与预加重组合的符号表），sink 在其中选择使采样误差最小的发端设置，通过 DPCD 的 LANE0_1_EQ_DONE / SYMBOL_LOCKED / INTERLANE_ALIGN_DONE 回报。全部 lane EQ_DONE 后，训练结束。

三个阶段的状态位汇总：

阶段 sink 回报的 DPCD 位 失败时的现象
Clock Recovery LANE0_1_CR_DONE、LANE2_3_CR_DONE 无图、屏幕全黑或闪一下又灭
Channel Equalization LANE0_1_EQ_DONE、LANE2_3_EQ_DONE、SYMBOL_LOCKED 出图但花屏、雪花、偏色、随机横线
Interlane Align INTERLANE_ALIGN_DONE 图像错位、左右撕裂

速率与 lane 数的选择 #

source 从两边取交集：DPCD 的 MAX_LINK_RATE、MAX_LANE_COUNT 给出 sink 上限，source 自己的控制器给出下限，中间按需要的带宽往上选。eDP 1.4 的四档速率：

速率档 单 lane 4 lane 有效带宽（x0.8）
RBR 1.62Gbps 5.184Gbps
HBR 2.7Gbps 8.64Gbps
HBR2 5.4Gbps 17.28Gbps
HBR3（eDP 1.4b 起） 8.1Gbps 25.92Gbps

快速训练 #

fast_train_enable 为真时，驱动跳过完整的 CR/EQ 试探，直接把上次成功的电压摆幅与预加重写进 DPCD 并只做符号锁定检查。前提是 sink 在 DPCD 里声明支持 No AUX Training（无 AUX 训练）。嵌入式面板出厂参数固定，这条路能省下几十毫秒的点亮时间。

训练失败后驱动做什么 #

analogix_dp_core.c 里训练的返回值会一路传回 analogix_dp_bridge_atomic_enable。失败时的典型日志是 AUX CH error happened（见第十八章实测日志）。注意 AUX 错误和链路训练失败是两码事：AUX 错在训练之前，链路是连 DPCD 都读不通；训练失败是 DPCD 读得到但状态位不置位。

十一、RK3399 的 HDMI 控制器 #

RK3399 的 HDMI 是 Synopsys DesignWare HDMI TX IP，Rockchip 只做封装。控制器与 PHY 的分工：

  • HDMI 控制器负责视频与音频数据的处理、编码，以及按 HDMI 协议传输。
  • HDMI PHY 负责把控制器的数字信号转成符合 HDMI 规范的电气信号。
  • 6.3 内核里 DesignWare HDMI PHY 驱动集成在 drivers/gpu/drm/bridge/synopsys/dw-hdmi.c，drivers/phy/rockchip/ 下没有单独的 DesignWare HDMI PHY 驱动。这也是为啥 menuconfig 里的 Rockchip INNO HDMI PHY Driver 不需要选——RK3399 没用 Innosilicon 的 PHY。

设备树节点定义在 arch/arm64/boot/dts/rockchip/rk3399.dtsi：

dts
hdmi: hdmi@ff940000 {
		compatible = "rockchip,rk3399-dw-hdmi";
		reg = <0x0 0xff940000 0x0 0x20000>;
		interrupts = <GIC_SPI 23 IRQ_TYPE_LEVEL_HIGH 0>;
		clocks = <&cru PCLK_HDMI_CTRL>, <&cru SCLK_HDMI_SFR>,
				 <&cru SCLK_HDMI_CEC>, <&cru PCLK_VIO_GRF>, <&cru PLL_VPLL>;
		clock-names = "iahb", "isfr", "cec", "grf", "ref";
		power-domains = <&power RK3399_PD_HDCP>;
		reg-io-width = <4>;
		rockchip,grf = <&grf>;
		#sound-dai-cells = <0>;
		status = "disabled";

		ports {
				hdmi_in: port {
						hdmi_in_vopb: endpoint@0 { reg = <0>; remote-endpoint = <&vopb_out_hdmi>; };
						hdmi_in_vopl: endpoint@1 { reg = <1>; remote-endpoint = <&vopl_out_hdmi>; };
				};
		};
};

逐项说明：reg 是寄存器基址 0xFF940000、长 128KB；interrupts 用 GIC_SPI 中断号 23、高电平触发；五路时钟分别是 iahb（PCLK_HDMI_CTRL，AHB 总线）、isfr（SCLK_HDMI_SFR，SFR 寄存器）、cec（SCLK_HDMI_CEC）、grf（PCLK_VIO_GRF）、ref（PLL_VPLL，PHY 参考时钟）；reg-io-width = <4> 表示寄存器 32 位宽，驱动据此把 reg_shift 设成 2；#sound-dai-cells = <0> 表示作为 DAI 被音频侧引用；两个 input endpoint 分别是 hdmi_in_vopb 接 vopb_out_hdmi、hdmi_in_vopl 接 vopl_out_hdmi。

板级使能写在 arch/arm64/boot/dts/rockchip/rk3399-evb.dts，四步：&i2c7 置 okay（DDC 总线）；&display_subsystem、&vopb、&vopb_mmu 置 okay；&hdmi 里加 ddc-i2c-bus = <&i2c7>、pinctrl-names = "default"、pinctrl-0 = <&hdmi_cec> 并置 okay；&hdmi_in_vopb 置 okay、&hdmi_in_vopl 置 disabled。

ddc-i2c-bus = <&i2c7> 就是那条 DDC 通道，接的是 GPIO2_B0/GPIO2_A7 复用出来的 I2C7。

十二、HDMI 驱动的整体结构 #

HDMI 驱动分两层：Rockchip 层在 drivers/gpu/drm/rockchip/dw_hdmi-rockchip.c，只做设备树解析、时钟电源、VOP 选择；DesignWare 层在 drivers/gpu/drm/bridge/synopsys/，承担真正的控制器操作、PHY 配置、connector 与 bridge。

先用一个类比把三者的分工钉死：纸 = HDMI 显示器（LCD 驱动器把收到的数据在屏上显示出来）；画布 = framebuffer（一块驱动和应用层都能访问的内存，描述分辨率、色彩格式如 RGB24/I420/YUYV，以及真正要显示的内容所在的虚拟地址，物理内存通过 GEM 分配）；画笔 = crtc（从 framebuffer 读图，按配置的时序输出给 encoder）；落笔动作 = encoder（对 HDMI 就是 TMDS 编码，编完通过线缆送到显示器，过程与绘画一样从左到右、从上到下）。

对架构本身的展开（对象关系、原子提交、四类对象的属性）看《DRM 核心对象：crtc、encoder、plane 与 gem》，这里只讲 HDMI 这条链是怎么接起来的。

省掉的都是错误处理：err_bind 清 encoder 并关 ref_clk，err_clk 关 1.8V，err_avdd_1v8 关 0.9V。中间那段 chip_data == &rk3568_chip_data 分支只对 RK3568 生效，RK3399 跳过。

两个细节值得单独说。第一，hdmi->chip_data = plat_data->phy_data; plat_data->phy_data = hdmi; 这两行把 phy_data 的值换了个位置：原本它是芯片数据指针，现在改成指向 rockchip_hdmi。这样 DesignWare 层回调 mode_valid 时拿到的 data 参数就是 rockchip_hdmi 而不是芯片表——这也是 dw_hdmi_rockchip_mode_valid 实际没用 data 参数的原因。第二，drm_encoder_helper_add 在 drm_simple_encoder_init 之前调用，标准顺序应该反过来，这里反着也能工作，因为 drm_encoder_init 不会清空 helper_private。这种写法在 Rockchip 多家平台驱动里都有，读代码时别被误导。

possible_crtcs 的来历 #

drm_of_find_possible_crtcs 遍历 hdmi 节点的所有 endpoint（for_each_endpoint_of_node），对每个 endpoint 用 of_graph_get_remote_port 拿到对端 port 节点（vopb_out 或 vopl_out），再交给 drm_of_crtc_port_mask 算位并或进掩码；后者在 crtc 链表里找 tmp->port == port 的那一项，返回 1 << index。eDP 与 HDMI 都会调这个函数，所以 modetest -e 里两个 encoder 的 possible crtcs 都是 0x00000003——两个 VOP 都声明可接。真正决定绑哪一个的是设备树 endpoint 的 status，以及运行时 GRF 的 lcdc_sel 写入。

crtc_endpoint_id 的来历 #

rockchip_drm_encoder_set_crtc_endpoint_id(rkencoder, np, port, reg) 拿 (np, 0, 0) 调 of_graph_get_endpoint_by_regs，命中 hdmi_in_vopb；再取它的 remote-endpoint（vopb_out_hdmi），把对端的 ep.id 赋给 crtc_endpoint_id。在 rk3399.dtsi 里 vopb_out_hdmi 的 reg = <2>，所以 RK3399 上 HDMI 的 crtc_endpoint_id 是 2。这个值在 VOP2 驱动里用来反查是哪个 encoder，老 VOP 不用。

rockchip_hdmi_parse_dt #

四件事，每件对应设备树一个属性：regmap 用 syscon_regmap_lookup_by_phandle(np, "rockchip,grf") 取，失败报错返回；ref_clk 用 devm_clk_get_optional(dev, "ref")，为空再试 "vpll"，两者皆空返回 NULL 不报错；grf_clk 用 devm_clk_get(dev, "grf")，-ENOENT 置 NULL、-EPROBE_DEFER 透传；avdd_0v9 与 avdd_1v8 用 devm_regulator_get，拿不到返回 dummy regulator。

ref 用 devm_clk_get_optional，所以 RK3399 上 PLL_VPLL 命名为 ref 完全够用，vpll 只是给老设备树留的退路；两者皆空返回 NULL，不报错。

devm_regulator_get 拿不到 regulator 时不会失败，而是返回一个 dummy regulator 并在日志里警告：

text
[    1.475048] dwhdmi-rockchip ff940000.hdmi: supply avdd-0v9 not found, using dummy regulator
[    1.484573] dwhdmi-rockchip ff940000.hdmi: supply avdd-1v8 not found, using dummy regulator

这两行是 NanoPC-T4 启动日志里的固定内容，不是错误。设备树里既没有 avdd-0v9-supply 属性，也没有 regulator-name = "avdd-0v9" 的 regulator，所以必然走 dummy 分支。dummy regulator 的 enable/disable 是空操作，电源实际由板级常供电提供。

dw_hdmi_bind 到 dw_hdmi_probe #

dw_hdmi_bind(pdev, encoder, plat_data) 本体很短：先 dw_hdmi_probe(pdev, plat_data)，失败直接返回 ERR_PTR；成功则 drm_bridge_attach(encoder, &hdmi->bridge, NULL, 0)，失败则 dw_hdmi_remove(hdmi) 回滚并返回 ERR_PTR。

dw_hdmi_probe 是 DesignWare 层的入口，15 步按顺序：(1) devm_kzalloc 分配 dw_hdmi，初值 sample_rate=48000、channels=2、disabled=true、rxsense=true、phy_mask=~(HDMI_PHY_HPD|HDMI_PHY_RX_SENSE)、mc_clkdis=0x7f、last_connector_result=disconnected，并初始化三 mutex 一 spinlock；(2) dw_hdmi_parse_dt，Rockchip 没设 output_port 直接返回 0，next_bridge 保持 NULL；(3) 解析 ddc-i2c-bus，I2C adapter 存进 hdmi->ddc；(4) 读 reg-io-width，为 4 用 hdmi_regmap_32bit_config 且 reg_shift=2，为 1 用 8bit 配置，devm_ioremap_resource 映射 0xff940000 起的 0x20000 再 devm_regmap_init_mmio；(5) 取并使能 isfr、iahb、cec 三路时钟，cec 允许不存在；(6) 读 HDMI_DESIGN_ID、HDMI_REVISION_ID 拼版本，读 HDMI_PRODUCT_ID0/1 验产品 ID，不匹配 -ENODEV；(7) dw_hdmi_detect_phy；(8) dw_hdmi_init_hw，含 initialize_hdmi_ih_mutes、dw_hdmi_i2c_init，有 phy.ops->setup_hpd 就调；(9) platform_get_irq + devm_request_threaded_irq（硬中断 dw_hdmi_hardirq，线程 dw_hdmi_irq）；(10) hdmi_init_clk_regenerator 先设音频 CTS/N；(11) 没有 DDC 时退回内建 dw_hdmi_i2c_adapter；(12) 初始化 bridge，设 driver_private、funcs、ops = DETECT|EDID|HPD、interlace_allowed、of_node；(13) 按 HDMI_CONFIG0_ID、HDMI_CONFIG3_ID 注册音频 platform device；(14) disable_cec 未置且控制器支持 CEC 时注册 dw-hdmi-cec；(15) drm_bridge_add(&hdmi->bridge)。

版本识别日志就是第 6 步打印的：dev_info 用 %x.%03x 格式拼 hdmi->version >> 12 与 hdmi->version & 0xfff，再拼 prod_id1 & HDMI_PRODUCT_ID1_HDCP ? "with" : "without" 与 hdmi->phy.name。对应输出 Detected HDMI TX controller v2.11a with HDCP (DWC HDMI 2.0 TX PHY)，即版本 2、修订 0x11a。

中断与寄存器访问 #

硬中断 dw_hdmi_hardirq 只做两件事：内建 I2C 时先 dw_hdmi_i2c_irq；然后读 HDMI_IH_PHY_STAT0（HPD 与 RXSENSE 两类事件），非零就向 HDMI_IH_MUTE_PHY_STAT0 写 ~0 屏蔽并返回 IRQ_WAKE_THREAD。

真正的处理在 dw_hdmi_irq 里，负责判断插拔、触发 drm_helper_hpd_irq_event。

hdmi_readb/hdmi_writeb 只是 regmap_read/regmap_write 的薄包装，地址要用 offset << hdmi->reg_shift 换算。reg-io-width = <4> 时 reg_shift = 2，代码里的 HDMI_IH_PHY_STAT0 这类逻辑偏移要左移 2 位才是寄存器总线上的实际地址。

dw_hdmi_connector_create 里有四项判断值得注意：

  • hdmi->version >= 0x200a 才允许 YCbCr 4:2:0，否则 ycbcr_420_allowed = false。
  • connector->polled = DRM_CONNECTOR_POLL_HPD，插拔靠 HPD 中断而不是轮询。
  • drm_connector_attach_max_bpc_property(connector, 8, 16)，属性范围 8~16，实际能力受 EDID 与 PHY 限制。
  • hdmi->version >= 0x200a && use_drm_infoframe 才挂 HDR metadata 属性，后者是 rk3399_hdmi_drv_data 里显式置 true 的。

connector 初调用的是 drm_connector_init_with_ddc(..., &dw_hdmi_connector_funcs, DRM_MODE_CONNECTOR_HDMIA, hdmi->ddc)，之后 drm_atomic_helper_connector_reset 建出初始 state，drm_connector_attach_encoder 把它挂到 hdmi->bridge.encoder。

drm_connector_funcs 与 drm_connector_helper_funcs 的区别要讲清楚，这是 DRM 里最容易搞混的一对：drm_xxx_funcs 是应用层 ioctl 的最终入口，各 SoC 的流程基本相同，只在寄存器配置上有差别；于是通用流程被抽成 helper，厂商差异放进 drm_xxx_helper_funcs。fill_modes、reset、atomic_duplicate_state 都用通用 helper，helper 内部再回调厂商的 get_modes。

HDMI 这边 helper 只有两项：get_modes = dw_hdmi_connector_get_modes、atomic_check = dw_hdmi_connector_atomic_check。funcs 里有七项：fill_modes = drm_helper_probe_single_connector_modes、detect = dw_hdmi_connector_detect、destroy = drm_connector_cleanup、force = dw_hdmi_connector_force，以及三个 drm_atomic_helper_connector_*。

drm_helper_probe_single_connector_modes 的完整流程决定了 sysfs 里 modes 最终长什么样：

  1. 把 connector 现有 modes 全标记为 stale。
  2. 调 drm_helper_probe_get_modes（内部走到 get_modes → drm_add_edid_modes），新探测到的模式以 OK 状态进 probed_modes。
  3. 若 connector 为 connected 但 get_modes 没拿到模式，drm_add_modes_noedid 补一批 VESA DMT 标准模式，最高 1024x768。
  4. 加入内核命令行指定的模式（drm_helper_probe_add_cmdline_mode），这类模式由 VESA GTF/CVT 算法生成。
  5. drm_connector_list_update 把 probed_modes 搬进 modes，重复项合并。
  6. 逐个验证：drm_mode_validate_basic 做基本合法性检查；drm_mode_validate_size 过滤超出 maxX/maxY 的模式；drm_mode_validate_flag 按 interlace/doublescan/stereo 能力检查；可选的 mode_valid 回调做驱动与显示器特定检查——这里会依次走到 drm_crtc_helper_funcs.mode_valid、drm_bridge_funcs.mode_valid（即 dw_hdmi_bridge_mode_valid）、drm_encoder_helper_funcs.mode_valid。
  7. drm_mode_prune_invalid 去掉状态不为 OK 的模式，并按 drm.debug 输出拒绝原因。

这条流程解释了 cat /sys/class/drm/card0-HDMI-A-1/modes 为什么比 EDID 里列出的模式少：EDID 里有 3 个 2560x1440 时序（120/60/144Hz），但 rockchip_mpll_cfg 里没有对应像素时钟，全被 mode_valid 拒了。

EDID 的两条入口殊途同归：bridge 的 .get_edid（dw_hdmi_bridge_get_edid）与 connector 的 .get_modes（dw_hdmi_connector_get_modes）最后都落到 dw_hdmi_get_edid。

新增分辨率必须同步三处 #

要让 2560x1440@60Hz 出图，需要同时改三个地方，缺一不可：

  1. drivers/gpu/drm/drm_edid.c 的 drm_dmt_modes：新增时序表项，否则 EDID 里的 Standard Timing 查不到、get_modes 不产出这个模式。
  2. rockchip_mpll_cfg：新增 241500000 条目，否则 mode_valid 直接返回 MODE_BAD。
  3. rockchip_cur_ctr：新增 241500000 条目，否则电流配置落到 ~0UL 兜底项，配置全 0。

rockchip_phy_config 因为最大已到 297MHz，241.5MHz 落在 148.5 与 297 之间，命中 297 项，可以不改。

历史上试过的做法是把 linux-4.19 的三张表整表拷进来，再手插 241.5MHz 条目（DRM_MODE("2560x1600", DRM_MODE_TYPE_DRIVER, 241500, 2560, 2608, 2640, 2720, 0, 1440, 1443, 1448, 1481, 0, DRM_MODE_FLAG_NHSYNC | DRM_MODE_FLAG_PVSYNC)）。

这段代码里模式名写成了 2560x1600 而分辨率是 2560x1440，是从别的条目复制时忘了改名。功能不致命（名字只影响 sysfs 里的显示文本），但会让人误判。

结果是：cat modes 里确实出现了 2560x1440，但显示器无法正常出图，说明 mpll_cfg 或 cur_ctr 的取值不对。PHY 参数必须按 datasheet 里对应像素时钟的推荐值填，或向 FAE 索取；猜出来的值组合即使能过 mode_valid 也驱动不了。这块最终回退了这些改动。

十五、eDP 驱动的整体结构 #

eDP 驱动同样两层：Rockchip 层 drivers/gpu/drm/rockchip/analogix_dp-rockchip.c，Analogix 通用层 drivers/gpu/drm/bridge/analogix/analogix_dp_core.c 与 analogix_dp_reg.c，PHY 在 drivers/phy/rockchip/phy-rockchip-dp.c。

设备树 #

arch/arm64/boot/dts/rockchip/rk3399.dtsi：

与 HDMI 节点的三个差异：reg 只有 0x8000（HDMI 是 0x20000）；interrupts 是 GIC_SPI 10（HDMI 是 23）；时钟名字是 dp/pclk/grf（HDMI 是 iahb/isfr/cec/grf/ref）。

edp_hpd 的 pinmux 把 GPIO4_C7 配成功能 2（<4 RK_PC7 2 &pcfg_pull_none>）。但 NanoPC-T4 的 eDP 接线里并没有引出 HPD，所以实际靠 force-hpd 属性绕过。

双屏时有一个必须处理的问题：GPIO4_C7 同时被 HDMI 的 CEC 与 eDP 的 HPD 引用，两个 pinctrl 组会打架。解法是删掉 HDMI 节点里的 pinctrl-names = "default"; 与 pinctrl-0 = <&hdmi_cec>; 两行，代价是 CEC 遥控功能失效。对一个把 HDMI 当副屏、用键盘鼠标的开发场景，这个代价可以接受。

板级节点启用写在 rk3399-evb.dts：&display_subsystem、&vopl、&vopl_mmu 置 okay；&edp 置 okay 并加 force-hpd，同时在 ports 里新增 edp_out: port@1 与 edp_out_panel: endpoint@0，remote-endpoint = <&panel_in_edp>；&edp_in_vopl 置 okay、&edp_in_vopb 置 disabled。

force-hpd 是嵌入式连接的关键属性：没有这根线时驱动会一直认为没插屏。

panel 节点用 panel-simple 驱动，compatible = "chunghwa,claa070wp03xg"，带 backlight = <&backlight>、power-supply = <&vcc3v3_s0>、prepare-delay-ms = <20>、enable-delay-ms = <20>，port 里的 panel_in_edp 通过 remote-endpoint = <&edp_out_panel> 接回 eDP。

compatible 用的是 chunghwa,claa070wp03xg 而不是 panel-simple：6.3 的 panel-simple.c 已经不再接受纯 simple-panel 作为 compatible，必须用具体型号。对应的时序与描述：

probe 与 bind #

rockchip_dp_probe 按顺序做六件事：

  1. of_device_get_match_data 取 rk3399_edp。
  2. drm_of_find_panel_or_bridge(dev->of_node, 1, 0, &panel, NULL) 找 panel。
  3. devm_kzalloc 分配 rockchip_dp_device，填 dev、adp = ERR_PTR(-ENODEV)、data、plat_data.panel、plat_data.dev_type = chip_type，并把 power_on_start/power_off/get_modes 三个回调分别指向 rockchip_dp_poweron_start、rockchip_dp_powerdown、rockchip_dp_get_modes。
  4. rockchip_dp_of_probe(dp) 拿 GRF、grf 时钟、pclk、复位控制。
  5. platform_set_drvdata 存私有数据，然后 analogix_dp_probe(dev, &dp->plat_data) 进 Analogix 层。
  6. component_add(dev, &rockchip_dp_component_ops)；失败时 analogix_dp_remove 回滚。

drm_of_find_panel_or_bridge(dev->of_node, 1, 0, &panel, NULL) 的 1, 0 就是找 port@1 的 endpoint@0，即 edp_out_panel，再沿 remote-endpoint 找到 panel_in_edp 所属的 edp_panel 节点。函数注释里明确标了已废弃（Use devm_drm_of_get_bridge() instead）。内部逻辑：先 of_graph_is_present(np) 判断节点有没有 ports；再 of_graph_get_remote_node(np, port, endpoint) 拿到远端节点；然后 of_drm_find_panel(remote) 在全局 panel 链表 panel_list 里按 of_node 找。

of_drm_find_panel(np) 先判 of_device_is_available(np)，不可用直接返回 -ENODEV（永久失败）；可用则持 panel_lock 遍历 panel_list，按 panel->dev->of_node == np 匹配，匹配不上返回 -EPROBE_DEFER（panel 驱动还没 probe，等下一轮）。

of_graph_get_endpoint_by_regs 的规则只有两条：端点的父节点是 port，port 的 reg 赋值给 endpoint->port，端点自己的 reg 赋值给 endpoint->id，然后按传入的 port_reg、reg 逐项比对。对 eDP 节点，port@1 的 reg = <1>、endpoint@0 的 reg = <0>，所以 of_graph_get_endpoint_by_regs(np, 1, 0) 精确命中 edp_out_panel。HDMI 侧调的是 (np, 0, 0)，命中的是 hdmi_in_vopb。

rockchip_dp_bind 只有三步：dp->drm_dev = drm_dev；rockchip_dp_drm_create_encoder(dp) 建 encoder 并赋给 plat_data.encoder；analogix_dp_bind(dp->adp, drm_dev) 进 Analogix 层。失败时 dp->encoder.encoder.funcs->destroy 清 encoder。

encoder 初始化与 HDMI 几乎一样，possible_crtcs 都是 drm_of_find_possible_crtcs，encoder type 都是 DRM_MODE_ENCODER_TMDS（eDP 虽然在电气上不是 TMDS，但 DRM 里这个枚举表示「像素流编码器」，不特指 TMDS 协议）。rockchip_dp_encoder_helper_funcs 五项：mode_fixup、mode_set、atomic_enable、atomic_disable、atomic_check，分别指向同名的 rockchip_dp_drm_encoder_* 函数。

analogix_dp_bind 负责四件事：把 dp->encoder 指向 plat_data->encoder；配好 dp->aux（名字 "DP-AUX"、transfer = analogix_dpaux_transfer、dev、drm_dev）并 drm_dp_aux_register；开运行时电源管理（pm_runtime_use_autosuspend、set_autosuspend_delay(100)、pm_runtime_enable）；最后 analogix_dp_create_bridge。

bridge 部分：analogix_dp_create_bridge 分配 drm_bridge，设 driver_private = dp、funcs = &analogix_dp_bridge_funcs，然后 drm_bridge_attach(dp->encoder, bridge, NULL, 0)。

analogix_dp_bridge_funcs 与 HDMI 的区别很明显：eDP 的 bridge 挂在 panel 前面，attach = analogix_dp_bridge_attach 里把 panel 接到 bridge 链上；HDMI 的 bridge 自己建 connector。从原子提交顺序看，eDP 多出 atomic_pre_enable 与 atomic_post_disable 两级（对应 analogix_dp_bridge_atomic_pre_enable / _post_disable），因为面板上电时序（prepare/enable/disable/unprepare）必须在链路训练前后分两段完成。其余项是 atomic_enable、atomic_disable、mode_set，加上三个 drm_atomic_helper_bridge_*。

与 HDMI 的区别很明显：eDP 的 bridge 挂在 panel 前面，attach 回调里把 panel 接到 bridge 链上；HDMI 的 bridge 自己建 connector。从原子提交顺序看，eDP 多出 atomic_pre_enable 与 atomic_post_disable 两级，因为面板上电时序（prepare/enable/disable/unprepare）必须在链路训练前后分两段完成。

eDP 的 rockchip_dp_get_modes 只有一个职责——把 YUV 格式抹掉：

rockchip_dp_get_modes 只有一个职责——把 YUV 格式抹掉：取 connector->display_info，若 color_formats 里带 DRM_COLOR_FORMAT_YCBCR444 或 DRM_COLOR_FORMAT_YCBCR422，就清掉这两位、置 DRM_COLOR_FORMAT_RGB444，并把 bpc 强制成 8。注释写明了原因：VOP couldn't output YUV video format for eDP rightly。

原因是 VOP 无法给 eDP 正确输出 YUV，所以 EDID 里即使声明了 YCbCr 也一律降级为 RGB444、8bpc。这段代码是"驱动能力覆盖 EDID 声明"的典型例子——EDID 说支持，不代表这条链路能跑。eDP 面板的显示模式不来自 EDID，而来自 panel 的 chunghwa_claa070wp03xg_mode，所以 get_modes 不需要去解析 EDID。

十六、eDP 驱动的初始化 #

rockchip_dp_of_probe #

只做四件事：拿 GRF regmap、拿 grf 时钟、拿 pclk 时钟、拿复位控制。

四件事：grf（regmap）用 syscon_regmap_lookup_by_phandle(np, "rockchip,grf") 取，失败报错返回；grfclk 用 devm_clk_get(dev, "grf")，-ENOENT 置 NULL、-EPROBE_DEFER 透传；pclk 用 devm_clk_get(dev, "pclk")，必须成功，它是 eDP 控制器的寄存器时钟；rst 用 devm_reset_control_get(dev, "dp")，失败报错返回。

电源管理与上电时序 #

rockchip_dp_pre_init 就是 assert、usleep_range(10, 20)、deassert 三步。rockchip_dp_poweron_start 先 clk_prepare_enable(dp->pclk)，失败报错返回；成功则调 rockchip_dp_pre_init，预初始化失败时把 pclk clk_disable_unprepare 回滚。rockchip_dp_powerdown 反向操作，只做 clk_disable_unprepare(dp->pclk)。那 10~20us 不能省：eDP 控制器的复位释放需要一个稳定窗口，太短会读到未初始化的寄存器值。

NanoPC-T4 上 eDP 面板点亮是四段串起来的：power_on_start 使能 pclk 并复位控制器；Analogix 层读 DPCD、读 EDID、写链路配置、跑链路训练（第十章）；panel 的 prepare 按 prepare-delay-ms = <20> 延时 20ms 给供电与逻辑建立时间；panel 的 enable 按 enable-delay-ms = <20> 再延时 20ms，然后开背光。

背光由 pwm-backlight 单独控制。enable-gpios（GPIO4_D5）拉高使能背光电源，PWM 占空比决定亮度。

十七、背光与电源控制 #

背光在 Linux 上是独立子系统，链路四层：用户态 /sys/class/backlight/backlight/brightness → pwm_bl（drivers/video/backlight/pwm_bl.c）→ 分两路，一路到 pwm-rockchip（drivers/pwm/pwm-rockchip.c）出 PWM 波形，一路到 enable-gpios（GPIO4_D5）使能背光电源。

pwm_bl 的属性在第十五章已按节点列过，这里只强调一点：pwms 的周期 25000ns 等于 40kHz，既高于人眼可感知的闪烁频率，又能保证占空比调节的线性度。

调亮度直接读写 sysfs：cat /sys/class/backlight/backlight/max_brightness（本例输出 255），echo 100 > /sys/class/backlight/backlight/brightness。

eDP 面板的电源树要理清三路：

电源 来源 用途 是否常供
VCC12V0_SYS 板级输入 背光电源、VCC3V3_SYS 的输入 是
VCC3V3_SYS VCC12V0_SYS 经 NB680GD 降压 LCD 逻辑电路、触摸 IC 的 AVDD28 与 VDDIO 是
VCC0V9_S3 VCC1V8_S3 经使能控制（PMIC_SLEEP_H → Q16） 面板内部 否，随 PMIC 状态

对应设备树三个 regulator-fixed 节点：vcc12v0_sys（12V，always-on、boot-on）、vcc3v3_sys（3.3V，vin-supply = <&vcc12v0_sys>，always-on、boot-on）、vcca0v9_s3（0.9V，vin-supply = <&vcc1v8_s3>，无 always-on）。

第三段的注释说得很清楚：vcca0v9_s3 实际由 vcc_1v8 供电，vcc1v8_s3 只驱动使能脚，但设备树模型表达不了这种关系，所以 vin-supply 只能写成 vcc1v8_s3。

这一路电源的硬件链路：PMIC_SLEEP_H 接 RK3399 的 GPIO1_A5/AP_PWROFF。拉低时 Q16 N-MOS 导通、VCC0V9_S3 输出 0.9V；拉高时 Q16 截止、输出 0V。

HDMI 侧的电源简单得多：HDMI_AVDD_0V9 由 VCCA0V9_S3 提供，HDMI_AVDD_1V8 由 VCC1V8_S3 提供，都是常供电。VCCA0V9_S3 本身由 RT9041B-10GE 稳压器从 VCC3V3_S5 得到，由 VCC1V8_S3 驱动 EN 脚。这就是驱动里 devm_regulator_get 拿不到 regulator、只能用 dummy 的原因——电源硬件上不需要软件控制。

三个 show 函数都短到一眼看完：enabled_show 读 READ_ONCE(connector->encoder)，非空输出 enabled；status_show 读 READ_ONCE(connector->status)，用 drm_get_connector_status_name 转字符串；modes_show 持 mode_config.mutex 遍历 connector->modes，逐个 scnprintf 打印 mode->name。

这些文件由 drm_sysfs_connector_add 创建：分配 device，设 class = drm_class、type = &drm_sysfs_device_connector、parent = dev->primary->kdev、groups = connector_dev_groups、release = drm_sysfs_release，dev_set_name(kdev, "card%d-%s", dev->primary->index, connector->name) 后 device_add；若 connector->ddc 存在，再建一个 ddc 符号链接。card%d-%s 就是 card0-HDMI-A-1、card1-eDP-1 这种命名的来源。

mode->name 的规则是 %dx%d%s：hdisplay、vdisplay、以及 i 或空（取决于 DRM_MODE_FLAG_INTERLACE）。所以 cat modes 里会出现多个同名的 1920x1080 与 1920x1080i——名字相同但刷新率与时钟不同，不是 bug。

导出 EDID：

bash
root@rk3399:/# cat /sys/class/drm/card0-HDMI-A-1/edid > /data/edid.bin
root@rk3399:/# hexdump -C /data/edid.bin
00000000  00 ff ff ff ff ff ff 00  35 34 00 00 01 01 01 01  |........54......|
00000010  00 20 01 03 81 00 00 78  ee 8c 75 a9 54 45 98 22  |. .....x..u.TE."|
000000f0  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 c4  |................|

256 字节，两个块。第 0x80 字节 02 是 CEA 扩展块 tag，第 0xFE 字节 01 是扩展块数量，第 0xFF 字节 c4 是主块校验和。拿去 EDID Manager 之类工具解析，能得到第七章那份可读报告。

eDP 侧同样 cat /sys/class/drm/card1-eDP-1/edid > /data/edid.bin，但如果 force-hpd 生效而实际没有 EDID 通路，读出来是 0 字节——此时显示模式完全来自 panel 描述表。

第三层：debugfs #

/sys/kernel/debug/dri/ 下三个目录：0/ 是 panfrost（GPU，minor 0），1/ 是 rockchip（display-subsystem，minor 1），128/ 是 renderD128。进 1/ 能看到 eDP-1/、HDMI-A-1/ 两个 connector 子目录，以及 clients、crtc-0/、crtc-1/、framebuffer、gem_names、internal_clients、name、state 八个文件。

cat /sys/kernel/debug/dri/1/name 输出 rockchip dev=display-subsystem unique=display-subsystem。

framebuffer 列出每个 framebuffer 的分配者、格式、尺寸、像素步长、GEM 对象：

text
framebuffer[57]:
        allocated by = gnome-shell
        format=XR24 little-endian (0x34325258)
        size=800x1280   pitch[0]=3200
framebuffer[65]:
        allocated by = gnome-shell
        modifier=0x800000000000051
        size=1920x1080  pitch[0]=7680
framebuffer[56]:
        allocated by = [fbcon]
        size=1920x1280  pitch[0]=7680

pitch 是每行字节数：800 x 4 = 3200，1920 x 4 = 7680，说明用的是 32bpp XR24。modifier=0x800000000000051 是 AFBC 压缩修饰符，普通线性缓冲区是 0。allocated by = [fbcon] 那条是内核帧缓冲控制台占的，尺寸 1920x1280 是两块屏横向拼接的结果。

第四层：modetest #

装 modetest：取 drm-libdrm-2.4.105.tar.gz 解开，apt-get install meson，meson builddir/、ninja -C builddir install，最后把 builddir/tests/modetest/modetest 拷进 /usr/bin/。

直接 modetest -c 报 no device found，是 /dev/dri/card0 被桌面占用了：先 ps -A | grep Xorg 找到显示进程（输出里 4828 tty2 ... Xorg），然后 killall Xorg & modetest -M rockchip -c。一次没杀掉就多试几次。

root@rk3399:~# modetest -M rockchip -s 52@37:1280x800-57   # 52=eDP connector, 37=VOPL crtc

正常屏幕上出现彩色条纹（modetest 的测试图案）。报 failed to set mode: Permission denied 几乎一定是桌面进程占着 DRM master：ps -ef | grep display 找到那个 Xwayland 进程，kill -9 <pid> 后再试。

HDMI 侧逐个试下来，1920x1080@60、1600x900、1280x1024、1280x720、1024x768 都正常，只有 800x600 无法显示。

HDMI 插上但 status 一直是 disconnected #

先看 ddc 符号链接指向哪个 I2C。如果指向的是 i2c-7，说明 DDC 走外部 I2C；如果是内建控制器，符号链接会是别的名字。然后：

bash
root@rk3399:~# ls /sys/bus/i2c/devices/i2c-7/7-0050/
root@rk3399:~# i2cdetect -y 7

7-0050 应该存在（EDID 的 I2C 从地址 0x50）。i2cdetect 在 0x50 位置有应答，说明 DDC 链路通，问题在 HPD 或驱动侧。

EDID 里有的分辨率 cat modes 里没有 #

这是最常见的问题，链路是：EDID 里有 → drm_add_edid_modes 添到 probed_modes → drm_helper_probe_single_connector_modes 逐个校验 → 校验通过才进 modes。任何一步失败都会消失。

验证方法：把 modes 和 EDID 解析结果并排列出来。2560x1440 三个时序全部缺失的情况，就是卡在 dw_hdmi_rockchip_mode_valid 这一步——它只认 rockchip_mpll_cfg 里列出的像素时钟。

eDP 背光不亮与显存不足 #

背光问题先排除 PWM 与背光子系统：读 /sys/class/backlight/backlight/brightness 与 max_brightness，再 echo 255 > brightness 看有没有反应。写入有效但屏还黑，就量 GPIO4_D5 电平；电平被拉住，检查设备树里 enable-gpios 有没有和其他节点冲突。

显存不足的表现是花屏或 fb 分配失败。fb0: rockchipdrmfb 单屏 1920x1080 XR24 需要 8.3MB，双屏 2720x1280 约 13.9MB，加上 4 个 plane 与 GNOME 的三缓冲，128MB 预留内存不够时会出问题。查法：cat /sys/kernel/debug/dri/1/framebuffer | grep -E "size=|pitch"，看 size 总和有没有接近启动参数里 CMA 的大小。

易错点 错误做法 正确做法
