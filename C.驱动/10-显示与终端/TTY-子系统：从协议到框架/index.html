本篇讲终端抽象层：内核怎么把「终端」抽成一套字符设备框架。讲什么：TTY 四层结构、tty_driver/tty_operations/tty_struct/tty_port 全字段、line discipline 机制、termios 全字段、注册与注销链、从驱动到用户态的完整路径，外加串口协议与电气底子。

不讲什么：串口控制器寄存器、uart_driver/uart_port/uart_ops、中断、DMA、console、serial console，全在 UART 驱动：serial_core 与具体实现。VT 图形化实现、pty 内核实现细节也不提，tty buffer / flip 只到接口层。串口一侧的实现细节看那篇，显示见 Linux 图形栈与 DRM 架构、LCD 与 framebuffer：两代显示框架的交接，键盘输入见 Linux input 框架：input_dev 与 handler。

素材基线：Linux 5.2.8（S3C2440 / Mini2440）+ 4.6-rc5（Bubblegum-96）。版本差异逐处标注，标不上的写「未验证」。

一、TTY 是什么：终端设备的抽象 #

先看一条最朴素的证据。u-boot 启动内核时传的启动参数是 root=/dev/mtdblock3 console=ttySAC0,115200 init=/linuxrc，三个字段各管一件事：root 指定根文件系统在 NAND 三号分区；init 指定内核起来后跑的第一个用户态程序；console 指定控制台落在哪个终端上。ttySAC0 就是三星 SoC 的第 0 个串口。终端是处理计算机输入输出的那套设备，它显示主机的输出，接收主机要求的输入。典型的终端是电传打印机、显示器加键盘。tty 是 Teletype / Teletypewriter 的缩写，原本指电传打字机，这种设备后来被键盘加显示器取代，但「计算机的终端设备」这个角色没变。不指定 console= 时默认落到 /dev/tty0，tty0 是当前使用的虚拟终端的一个别名。早期终端通过电缆和计算机连接，一端是终端设备，一端是用户进程。为了把不同型号的电传打字机接进计算机，内核里要装驱动，为上层屏蔽底层细节。于是有了三个组件：

组件 职责
uart 驱动 管理字节的物理传输，对应硬件 UART（通用异步收发器）
line discipline（行规范） 提供编辑缓冲区和基本编辑命令（退格、清词、清行、重打印），支持用户输入行为
tty 驱动 会话管理，处理各类终端设备

今天的终端已经不是物理设备。电传打字机进了博物馆，内核保留了 tty 驱动和 line discipline 的设计。终端成了内核的一个模块，可以直接向 tty 驱动发字符，并从 tty 驱动读响应打印到屏幕上。用内核模块模拟物理终端设备，这就是终端模拟器，也就是虚拟终端（virtual console，有时也叫本地终端）。它监听键盘事件发给 tty 驱动，再从 tty 驱动读响应，通过显卡驱动渲染到显示器。tty 驱动和 line discipline 的行为和原来一样，但不再有 UART 和物理终端参与。装无图形界面的 Linux，启动完成后屏幕上会有一个文本模式的登录提示，那就是虚拟终端界面。CTRL+ALT+[F1~F6] 在 tty1~tty6 之间切换，切到哪个哪个就是焦点终端。焦点终端被内核记在全局变量里，只要有键盘输入，字符就交给焦点终端。往 /dev/console 里写东西总会出现在当前焦点终端上；往 /dev/tty 里写，无论你在哪个终端下工作，都会出现在你眼前。伪终端（pty）是终端的发展，为满足网络登录、X window 窗口管理等需求。它是成对出现的逻辑终端设备：master 和 slave，对 master 的操作会反映到 slave 上。pty 运行在用户态，仍保留 tty 驱动和 line discipline 的能力，常用形态是 xterm、gnome-terminal、ssh 远程终端。pty 通过打开 /dev/ptmx 创建：pty slave 对应 /dev/pts/ 目录下的一个文件，pty master 在内存里以一个文件描述符（fd）标识。每个 fd 都是独立的 master，有自己关联的 slave，ptmx 内部维护 fd 与 slave 的对应关系，对该 fd 的读写都被转发到对应 slave 上。验证一下当前终端：

/dev/pts/6
$ ps -l

从内核视角看，TTY 设备是「虚拟的数据通道」。串口控制器是实实在在的硬件，一个控制器支持多个串口，软件在串口上收发数据就等于在驱动「串口终端」；网络终端那里只有以太网/WLAN 控制器是硬件，sshd 基于 socket 虚拟出一个通道。这也是为什么内核不认为 TTY device 是一个「设备」——TTY driver 在 Linux 内核里出现得比设备模型早得多。为了方便，内核从两个角度对它做了抽象：设备模型角度是 /sys/class/tty/tty、/sys/class/tty/console、/sys/class/tty/ttyS0，字符设备角度是 /dev/tty、/dev/console、/dev/ttyS0。串口只是 TTY 的一类。串口控制器的驱动怎么写、寄存器怎么动，全在 UART 驱动：serial_core 与具体实现。

二、串口、UART、RS232 的关系 #

这几个词天天挂在嘴边，细节却容易被模糊。一句话记住分工：

  • 串行通信（serial communication）泛指 bit 流的通信方式，RS232、USB、I2C、SPI、1-Wire、Ethernet 都算，串行是相对于并行说的。
  • 串口（serial port）特指用异步串行方式通信的接口，从硬件角度描述。
  • RS-232 定义两个串口之间通信行为的规范，偏电平、连接器、电缆这类硬件特性。
  • UART（Universal Asynchronous Receiver/Transmitter）一个硬件模块，按串口规定的编码格式和 bit rate 产生通信所需的 bit 流。

接收方收到一长串 0/1 电平跳变，怎么还原有用的信息？两条路：一是发送端同时提供时钟信号，按约定（比如时钟上升沿）送数据，接收端照时钟和约定收，这是同步串行通信，I2C、SPI 这种带时钟线的都属于它；二是发送端在数据前后用 START / STOP 信号告诉接收端何时开始停止，双方事先约定好波特率，发完 START 就按固定节奏发，收到 START 就按固定节奏收，这是异步串行通信，本篇的主角串口就是这种。严格讲后者应叫 asynchronous start-stop communication，但它在这个领域用得太多，两者早已混用不分。串口本身也分异步串口和同步串口，本篇只讲异步串口。RS-232 规定「硬件相关」的特性：电气信号特性（-3V~-15V 表示逻辑 1，+3V~+15V 表示逻辑 0）、接口特性（9-pin DE-9、25-pin DB-25 的连接器定义与管脚信号定义）、电缆特性（没有显式限制长度，但限制了电容，效果一样）。「软件相关」的特性——数据编码格式（起始位、数据位、校验位、停止位）和数据传输的 bit rate——反而由具体串口硬件定义，原文给的猜测是硬件差异太大，规范无法完全覆盖。它倒是要求「不能超过 20Kbps」，这条和后来的实际能力差得远。RS-232 定义了 DE-9、DB-25 等各种形态，大多和上古通信场景相关，嵌入式里反而更多见简化的 4 线形态（VCC/RX/TX/GND）。至于 UART 为什么存在：早期产品大多用软件按 bit rate 产生 bit 流，后来为了性能，很多产品（如 IBM 的 PC）改用专门的硬件模块，这就是 UART。一个容易被忽略的事实：串口和 TTY 的关系是「所有串口设备都是 TTY 设备」，反过来不成立。虚拟终端、伪终端都是 TTY 设备但不是串口。所以 Linux 的目录布局是 drivers/tty/ 下挂 serial/ 和 vt/，串口子系统是 TTY 框架的一个子集。

三、串口的电气标准与信号线 #

PC 串口按 RS-232 走负逻辑，电平在 ±3V~±15V 之间；大多数嵌入式产品用 TTL 电平（0V / 3.3V）。两者无法直接连接，中间加一个电平转换电路：

text
PC(串口) <--> 电平转换电路 <--> 嵌入式产品(串口)
PC(USB接口) <--> USB转串口 <--> 嵌入式产品(串口)

这条链路值得记住，因为调试现场十次有八次是它出问题：USB 转串口的芯片型号决定它能支持的最高波特率和流控能力，不是所有 USB 转串口都能稳跑 3Mbps 以上，也不是所有都能做硬件流控。RS-232 的信号线按功能分三组，下面的命名以 DE-9（9 针）为准，DB-25（25 针）是另一套引脚编号：

信号 方向 作用 备注
TXD DTE 发 → DCE 收 发送数据 必须
RXD DCE 发 → DTE 收 接收数据 必须
GND — 信号地 必须
RTS DTE 发 → DCE 收 请求发送 硬件流控时用；软件流控时可作他用
CTS DCE 发 → DTE 收 清除发送 对 RTS 的应答
DTR DTE 发 → DCE 收 数据终端就绪 常被用来做「设备已连接」指示
DSR DCE 发 → DTE 收 数据装置就绪 对 DTR 的应答
DCD DCE 发 → DTE 收 载波检测 modem 场景为主
RI DCE 发 → DTE 收 振铃指示 modem 场景为主

超过三根线的场景里，最常见的是四线（VCC/RX/TX/GND）和带流控的六线（加 RTS/CTS）。三线（TX/RX/GND）能通就不用管其余信号，但一旦开了 crtscts，DTS 里没接 RTS/CTS 就会卡住不发货——这是现场最常见的「串口能收不能发」。流控分两种：软件流控用 XON/XOFF（Ctrl+Q / Ctrl+S，0x11 / 0x13）走数据通道本身，问题是二进制数据里出现 0x11/0x13 会被误判；硬件流控走 RTS/CTS 独立线，需要额外两根线。uart_port 里这两者各有对应标志 UPF_AUTO_CTS、UPF_AUTO_RTS、UPF_SOFT_FLOW，标志全表见 UART 驱动：serial_core 与具体实现；termios 侧怎么开这两类流控，看本篇第九章。

四、波特率与比特率 #

比特率（bit rate）好理解：一定时间内能传多少 bit，bps 就是 bit per second。波特率（baud rate）也叫符号速率（symbol rate），指的是「数据变化」的速率。原文举例：考试时小杨拿黑白两支笔，按两支笔的出现组合表示 A/B/C/D 四个答案，约定每分钟换一次，这个「每分钟换一次」就是 baud rate，1 bd per minute；但每次变化传递了两个 bit（00/01/10/11），所以 bit rate 是 2 bits per minute，两者不等。串口通信里两者相等，因为一次只传一个 bit——说 115200 的波特率，比特率也是 115200。帧格式决定了每字节约占多少个 bit：

字段 位数 说明
start bit 固定 1 bit 起始位
data bits 5、6、7、8、9 bit 常用 8 bit
parity bit 非必须，一般 0 bit 校验位
stop bit 1 或 2 bit 一般为 1 bit

所以 8N1（8 数据位、无校验、1 停止位）一帧是 10 bit。波特率定义了帧里每一个 bit 的持续时间，即 1 / baud rate；一帧传完需要 (1 / baud rate) * 10。比如 115200 8N1：一个 bit 约 8.68μs，一帧约 86.8μs，理论最大约 11520 字节/秒。很多人算串口吞吐直接用 115200/8，忘了起始位和停止位，误差 20%。误差受系统时钟精度、分频系数影响，而且在一帧传输过程中会累积；误差累积不多时，start/stop 信号的矫正作用会让下一帧把累积误差清零。信号在中间点采样，所以一帧内误差累积超过 1 / baud rate / 2 就会采错。设理想波特率 BDi、实际 BDr：每个 bit 的误差时间是 1 / BDi - 1 / BDr，10 个 bit 就是 10 * (1 / BDi - 1 / BDr)，安全条件是 abs(10 * (1 / BDi - 1 / BDr)) < 1 / BDi / 2。代入 115200：

text
abs(10 * (1/115200 - 1/BDr)) < 1/115200/2
(20/21) * 115200 < BDr < (20/19) * 115200

容许的误差范围是 20/21 ~ 20/19，约 ±5%，其它波特率同理代入，双方都有误差就再除 2。这条 5% 的结论在移植时很有用：算分频系数时向下取整导致的偏差如果超过 2.5%（双方各占一半预算），就要换成更接近的时钟源或者支持小数分频的控制器。三星 S3C2440 的 UBRDIV 只有整数分频，所以它的 set_termios 里必须挑一个能让误差落在范围内的 PCLK 分频组合。分频系数具体怎么算见 UART 驱动：serial_core 与具体实现。

五、TTY 子系统的四层结构 #

TTY framework 位于内核 drivers/tty 目录，通过 TTY core 屏蔽技术细节：对上以字符设备的形式向应用提供统一接口，对下以 TTY device / TTY driver 的形式提供驱动编写框架。

层 目录 核心结构体 职责
用户接口层 drivers/tty/tty_io.c file_operations tty_fops 把 /dev/ttySn 的 read/write/ioctl/open 接到内核
line discipline 层 drivers/tty/n_tty.c 等 tty_ldisc_ops 行编辑、回显、特殊字符转换、规范/非规范模式
tty driver 层 各驱动 tty_driver + tty_operations 会话管理、字符设备注册、为下层提供 tty->ops
uart 驱动层 drivers/tty/serial/ uart_driver + uart_port + uart_ops 操作真实硬件寄存器、收字节、发字节

严格说 serial framework 在 tty driver 和硬件之间插了一层 serial_core，它不是第五个抽象层，而是 tty driver 层的「现成实现」——serial_core 把 struct tty_operations uart_ops 注册成 tty driver 的操作集，把 tty 层的一切翻译成 uart_ops 调用。所以你在写 SoC 串口驱动时，只面对 uart_driver / uart_port / uart_ops 三个结构，tty_driver 由 uart_register_driver 内部帮你搞定。这个归属划分是理解两篇分工的钥匙：本篇管上面三层，最底层的实现细节全在 UART 驱动：serial_core 与具体实现。这个「翻译层」的设计还有一个直接收益：uart_driver.cons 字段让 console 也走同一条硬件路径，三种访问方式（tty 字符设备、console、early console）落到同一份寄存器操作上；console 部分不在本篇。参考素材里有一张图展示了四种注册 UART 设备驱动的方式（case A 到 case D），图在抓取时丢了，但它的四个组成部分是清楚的：

  • character device：tty 字符设备节点，比如 /dev/ttyN；
  • tty_register_device：注册 tty 字符设备；
  • tty_driver：tty 驱动的核心结构体，关联 tty_struct、tty_port、tty_operations、tty_ldisc、tty_ldisc_ops，通过 tty_register_driver 注册；
  • uart_driver：uart 驱动的核心结构体，也是 UART 驱动要自己实现的部分，关联 uart_state、uart_port、uart_ops，通过 uart_register_driver 注册。

TTY core 以字符设备形式提供的节点，设备号有一张固定的表：

设备号（主，次） 字符设备 备注
(5, 0) /dev/tty 控制终端（Controlling Terminal）
(5, 1) /dev/console 控制台终端（Console Terminal）
(4, 0) /dev/vc/0 或 /dev/tty0 虚拟终端（Virtual Terminal）
(4, 1) /dev/vc/1 或 /dev/tty1 同上
… … …
(x, x) /dev/ttyS0 串口终端，名称与设备号由驱动自行决定
(x, x) /dev/ttyUSB0 USB 转串口终端

六、tty_driver 与 tty_operations #

6.1 struct tty_driver #

struct tty_driver 描述一个 tty 驱动，定义在 include/linux/tty_driver.h（5.2.8 全字段）：

c
struct tty_driver {
        int     magic;          /* magic number for this structure */
        struct kref kref;       /* Reference management */
        struct cdev **cdevs; struct module   *owner;
        const char      *driver_name; const char      *name;
        int     name_base;      /* offset of printed name */
        int     major;          /* major device number */
        int     minor_start;    /* start of minor device number */
        unsigned int    num;    /* number of devices allocated */
        short   type;           /* type of tty driver */
        short   subtype;        /* subtype of tty driver */
        struct ktermios init_termios; /* Initial termios */
        unsigned long   flags;          /* tty driver flags */
        struct proc_dir_entry *proc_entry; /* /proc fs entry */
        struct tty_driver *other; /* only used for the PTY driver */
        /*
         * Pointer to the tty data structures
         */
        struct tty_struct **ttys; struct tty_port **ports;
        struct ktermios **termios; void *driver_state;
        /*
         * Driver methods
         */
        const struct tty_operations *ops; struct list_head tty_drivers;

既然有了 tty_struct，为什么还要 tty_port？内核注释的原话：

c
/* include/linux/tty.h */
/*
 * Port level information. Each device keeps its own port level information
 * so provide a common structure for those ports wanting to use common support
 * routines.
 *
 * The tty port has a different lifetime to the tty so must be kept apart.
 * In addition be careful as tty -> port mappings are valid for the life
 * of the tty object but in many cases port -> tty mappings are valid only
 * until a hangup so don't use the wrong path.
 */

拆开看：tty_struct 是 TTY 设备的动态抽象，保存访问过程中的临时信息，生命周期从 open 到 close 结束；tty_port 是 TTY 设备固有属性的静态抽象，保存固定不变的属性（是否是 console、开关是否需要 delay 等），生命周期比 tty 长。TTY core 负责逻辑抽象，不关心这些固有属性，所以这些属性完全可以由具体 tty driver 自己维护；不同 tty 设备的属性有共性，每个 driver 都维护一份私有结构会冗余，于是框架把共性抽出来放进 tty_port，同时提供通用操作接口。一句话记：tty_struct 是 TTY core 的数据结构，框架提供框架使用，必要时借给 driver 用；tty_port 是 tty driver 的数据结构，框架提供，driver 使用，框架不关心。

tty_port 的两个回调集：

c
struct tty_port_operations {
        /* Return 1 if the carrier is raised */
        int (*carrier_raised)(struct tty_port *port);
        /* Control the DTR line */
        void (*dtr_rts)(struct tty_port *port, int raise);
        /* Called when the last close completes or a hangup happens */
        void (*shutdown)(struct tty_port *port);
        /* Called on first open */
        int (*activate)(struct tty_port *port, struct tty_struct *tty);
        /* Called on last close */
        void (*destruct)(struct tty_port *port);
};

struct tty_port_client_operations {
        int (*receive_buf)(struct tty_port *port, const unsigned char *cp,
                        const unsigned char *fp, size_t count);
        void (*write_wakeup)(struct tty_port *port);
};

这一段最需要标版本。tty_port_operations 在 4.x 期间的形态是「直接挂 activate/shutdown 等」，到 5.x 收敛成上面这五个回调。本篇素材覆盖的 4.6-rc5 与 5.2.8 之间，tty_port_operations 还经历过一次「不再通过 port->ops 暴露 activate，改由 tty_port_client_operations 分工」的重构（client_ops 里的 receive_buf/write_wakeup），具体提交和精确版本节点未验证。写驱动时以你手上的内核头文件为准。对串口驱动来说，tty_port_operations 由 serial_core 填成 uart_port_ops，所以你在 uart_register_driver 里看到这一行：

c
port->ops = &uart_port_ops;

port->ops->activate 最终落到 uart_port_activate → uport->ops->startup(uport)。那一侧的实现见 UART 驱动：serial_core 与具体实现。

八、line discipline：TTY 的中间层 #

8.1 它解决什么问题 #

line discipline 在 TTY framework 里是一个「适配层」，位于设备驱动和应用接口之间。字面意思是辅助 tty driver，把通过 TTY 设备键入的字符转换成一行一行的数据。实际远比这复杂：它要处理退格、删词、删行、Ctrl+C 转信号、回显、\n 转 \r\n（onlcr）、\r 转 \n（icrnl）等等。对串口驱动作者来说，好消息是你基本不用碰它。需要知道的是三件事：它在哪、什么时候被调、怎么切。

8.2 两种模式：规范与非规范 #

termios.c_lflag 的 ICANON 位决定行为：

模式 条件 读取行为
规范（canonical / cooked） ICANON 置位 缓冲到行结束符（\n 或 EOF 字符）才唤醒读者，n_tty_read 走 canon_copy_from_read_buf
非规范（non-canonical / raw） ICANON 清零 按 VMIN/VTIME 决定读多少、等多久，n_tty_read 走 copy_from_read_buf
VMIN VTIME 行为
> 0 0 阻塞到读满 VMIN 个字节
0 > 0 读到至少 1 字节或超时（VTIME × 100ms）
> 0 > 0 读到 VMIN 字节，或字节间超时（VTIME × 100ms）
0 0 有数据就立即返回

这就是 n_tty_read 里这段代码的含义：

c
        minimum = time = 0;
        timeout = MAX_SCHEDULE_TIMEOUT;
        if (!ldata->icanon) {
                minimum = MIN_CHAR(tty);
                if (minimum) {
                        time = (HZ / 10) * TIME_CHAR(tty);
                } else {
                        timeout = (HZ / 10) * TIME_CHAR(tty);
                        minimum = 1;
                }
        }

HZ/10 就是 100ms，正好对应 VTIME 的单位。调试场景最常用的组合是 raw（cfmakeraw 或 stty raw -echo），因为你要收发二进制。用 minicom/picocom 抓数据时如果发现 0x0d 被吃掉了、0x11 被当成 XOFF 了，先查 termios。

8.3 ldisc 的切换 #

  -> tty_set_ldisc(tty, disc)
     -> tty_ldisc_lock(tty, 2 * HZ)
     -> tty_ldisc_hangup(tty, 1)        /* 先关旧的 */
     -> ld = tty_ldisc_get(tty, disc)   /* 申请新的 */
     -> tty_ldisc_close(tty, tty->ldisc)
     -> tty->ldisc = ld
     -> tty_ldisc_open(tty, tty->ldisc)
     -> tty->ops->set_ldisc(tty)        /* 通知 tty driver */

tty->ops->set_ldisc 对串口驱动就是 uart_set_ldisc → port->ops->set_ldisc（uart_ops.set_ldisc），你那层一般只需要处理 N_PPS 这类特殊 ldisc。tty_ldisc_get 是这套机制的核心：

c
static struct tty_ldisc *tty_ldisc_get(struct tty_struct *tty, int disc)
{
        struct tty_ldisc *ld; struct tty_ldisc_ops *ldops;

        if (disc < N_TTY || disc >= NR_LDISCS)
                return ERR_PTR(-EINVAL);
        ldops = get_ldops(disc);
        if (IS_ERR(ldops)) {
                if (!capable(CAP_SYS_MODULE) && !tty_ldisc_autoload)
                        return ERR_PTR(-EPERM);
                request_module("tty-ldisc-%d", disc);
                ldops = get_ldops(disc);
                if (IS_ERR(ldops))
                        return ERR_CAST(ldops);
        }
        ld = kmalloc(sizeof(struct tty_ldisc), GFP_KERNEL | __GFP_NOFAIL);
        ld->ops = ldops; ld->tty = tty;
        return ld;
}

它先查 tty_ldiscs[disc]，没有就尝试 request_module("tty-ldisc-%d", disc) 动态加载模块，再查一次。CONFIG_LDISC_AUTOLOAD 控制默认是否允许自动加载：

c
#if defined(CONFIG_LDISC_AUTOLOAD)
        #define INITIAL_AUTOLOAD_STATE  1
#else
        #define INITIAL_AUTOLOAD_STATE  0
#endif
static int tty_ldisc_autoload = INITIAL_AUTOLOAD_STATE;

CONFIG_LDISC_AUTOLOAD 从 5.1 起才有（未验证精确版本），之前是无条件尝试。这条对嵌入式裁剪有用：关掉它能省掉一堆 tty-ldisc-N 的模块探测，也能避免非特权用户触发模块加载。

8.4 do_tty_write 的分片 #

tty_write 到 ldisc 之间有一层 do_tty_write，它把用户数据分片，原因是低层驱动不该处理用户态地址，也不该处理长写：

c
        chunk = 2048;
        if (test_bit(TTY_NO_WRITE_SPLIT, &tty->flags))
                chunk = 65536;
        if (count < chunk)
                chunk = count;

2048 这个数的原因写在注释里：NTTY 层对更大的块有问题，它会声称能处理比实际能处理更多的字符。如果驱动设了 TTY_NO_WRITE_SPLIT，就用 64K。这个 flag 串口驱动不设——28 字节的 FIFO 也吃不下 64K。

九、termios：终端属性 #

9.1 struct ktermios 全字段 #

用户空间叫 struct termios，内核空间叫 struct ktermios，都在 include/uapi/asm-generic/termbits.h：

c
struct ktermios {
        tcflag_t c_iflag;               /* input mode flags */
        tcflag_t c_oflag;               /* output mode flags */
        tcflag_t c_cflag;               /* control mode flags */
        tcflag_t c_lflag;               /* local mode flags */
        cc_t c_line;                    /* line discipline */
        cc_t c_cc[NCCS];                /* control characters */
        speed_t c_ispeed;               /* input speed */
        speed_t c_ospeed;               /* output speed */
};
字段 含义
c_iflag 输入模式标志：字符怎么从硬件进 ldisc
c_oflag 输出模式标志：字符怎么从 ldisc 出到硬件
c_cflag 控制模式标志：数据位、校验、停止位、流控（8N1 就写在这）
c_lflag 本地模式标志：规范模式、回显、信号生成
c_line line discipline 编号（N_TTY = 0）
c_cc[NCCS] 控制字符数组，NCCS = 19；索引 VINTR/VQUIT/VERASE/VKILL/VEOF/VMIN/VTIME 等
c_ispeed / c_ospeed 输入/输出速率（波特率）

c_cflag 的常用位：

位 含义
CS5~CS8 数据位长度（CS8 是 8 位）
CSTOPB 两位停止位（置位），否则一位
PARENB 启用校验
PARODD 奇校验（配合 PARENB），否则偶校验
CREAD 启用接收
CLOCAL 忽略 modem 控制线（不等待 DCD）
HUPCL 最后关闭时挂断（拉低 DTR）
CRTSCTS 硬件流控

c_lflag 的常用位：ISIG（Ctrl+C 产生信号）、ICANON（规范模式）、ECHO/ECHOE/ECHOK/ECHONL（回显细分）、IEXTEN（扩展处理如 Ctrl+V）。c_iflag：IGNBRK/BRKINT（break 处理）、IGNPAR/PARMRK（校验错误/标记奇偶错）、ISTRIP（剥掉第 8 位）、INLCR/IGNCR/ICRNL（回车换行转换）、IXON/IXOFF/IXANY（软件流控）、IUTF8。c_oflag：OPOST（启用输出处理）、ONLCR（\n 转 \r\n）、OCRNL（\r 转 \n）、ONOCR/ONLRET。还有 termios_locked——tty_struct 里和 termios 并排的那个字段，用来实现 TIOCGLCKTRMIOS/TIOCSLCKTRMIOS 的锁定语义（普通用户不能改被锁的位）。

9.2 默认值和 8N1 怎么来的 #

serial_core 在 uart_register_driver 里设的初始值：

c
        normal->init_termios    = tty_std_termios;
        normal->init_termios.c_cflag = B9600 | CS8 | CREAD | HUPCL | CLOCAL;
        normal->init_termios.c_ispeed = normal->init_termios.c_ospeed = 9600;

也就是说，内核串口驱动的默认不是 115200 也不是裸 8N1，而是 9600 8N1 + CREAD|HUPCL|CLOCAL。tty_std_termios 里还带了 ICRNL|IXON（c_iflag）和 OPOST|ONLCR（c_oflag）。要 115200 8N1 裸模式，用户态得自己 tcsetattr。B9600 这种宏是「编码过的波特率」，不是数值 9600，tty_termios_baud_rate() 负责把 c_cflag 里的码解回数值，tty_termios_encode_baud_rate() 反过来。这一对函数在 uart_set_termios 里必用。

9.3 波特率改动的落地点 #

stty 115200 或 tcsetattr 触发的路径：

{

        dev_t dev;

{
        spin_lock_irq(&port->lock);
        ++port->count;
        spin_unlock_irq(&port->lock);
        tty_port_tty_set(port, tty);
        mutex_lock(&port->mutex);
        if (!tty_port_initialized(port)) {
                clear_bit(TTY_IO_ERROR, &tty->flags);

                        int retval = port->ops->activate(port, tty);  /* -> startup */
                        if (retval) {
                                mutex_unlock(&port->mutex);
                                return retval;
                        }
                }
                tty_port_set_initialized(port, 1);
        }
        mutex_unlock(&port->mutex);
        return tty_port_block_til_ready(port, tty, filp);
}

                                                size_t count, loff_t *ppos)
{
        struct tty_struct *tty = file_tty(file);
        struct tty_ldisc *ld; ssize_t ret;

        if (tty_paranoia_check(tty, file_inode(file), "tty_write"))
                return -EIO;
        if (!tty || !tty->ops->write || tty_io_error(tty))
                return -EIO;
        if (tty->ops->write_room == NULL)
                tty_err(tty, "missing write_room method\n");
        ld = tty_ldisc_ref_wait(tty);
        if (!ld)
                return hung_up_tty_write(file, buf, count, ppos);
        if (!ld->ops->write)
                ret = -EIO;
        else
                ret = do_tty_write(ld->ops->write, tty, file, buf, count);
        tty_ldisc_deref(ld);
        return ret;
}

do_tty_write 的分片循环（5KB 的写被切成 2KB、2KB、1KB 三次下传）：

n_tty_write 两条分支，OPOST 走 process_output_block/process_output 做 \n → \r\n 转换、末尾 tty->ops->flush_chars 一次性刷；非 OPOST 直接 tty->ops->write 循环、用 output_lock 串行化。串口驱动必须实现 write，最好实现 flush_chars——只实现 write 时靠里面的 __uart_start 推数据，功能没问题，但「攒一批再发」的优化会失效。uart_write 为什么返回 -EL3HLT、__uart_start 怎么判断 uart_tx_stopped、start_tx 怎么搬 FIFO，全在 UART 驱动：serial_core 与具体实现 的收发路径一节。本篇记住一句话就够：tty->ops->write 那层只负责把数据放进 state->xmit 环形缓冲，真正的硬件动作是另一层。

11.3 接收路径 #

text
UART 收到数据 -> RX 中断
  -> s3c24xx_serial_rx_chars(irq, dev_id)
     -> s3c24xx_serial_rx_chars_pio / _dma
        -> 读 UART 数据寄存器
        -> uart_insert_char(port, status, overrun, ch, flag)
           -> tty_insert_flip_char(&port->state->port, ch, flag)

中断入口那一段是 UART 篇的，见 UART 驱动：serial_core 与具体实现；从 tty_insert_flip_char 往后是本篇的。用 uart_insert_char 而不是直接 tty_insert_flip_char，是因为前者能处理 overrun：

c
extern void uart_insert_char(struct uart_port *port, unsigned int status,
                 unsigned int overrun, unsigned int ch, unsigned int flag);

status 来自控制器状态寄存器（帧错、校验错、溢出、break），overrun 是这一位对应的控制器掩码。serial core 按 port->ignore_status_mask 决定丢弃还是上报，按 port->read_status_mask 决定带什么 flag 交给 ldisc。这两个 mask 就是 set_termios 里要更新的东西。

11.4 读路径与规范模式 #

c
static ssize_t tty_read(struct file *file, char __user *buf, size_t count,
                        loff_t *ppos)
{
        int i;
        struct inode *inode = file_inode(file);
        struct tty_struct *tty = file_tty(file);
        struct tty_ldisc *ld;

        if (tty_paranoia_check(tty, inode, "tty_read"))
                return -EIO;
        if (!tty || tty_io_error(tty))
                return -EIO;
        ld = tty_ldisc_ref_wait(tty);
        if (!ld)
                return hung_up_tty_read(file, buf, count, ppos);

                i = ld->ops->read(tty, file, buf, count);   /* n_tty_read */

                i = -EIO;

}

n_tty_read 的三点：没数据时，非阻塞直接 -EAGAIN，阻塞则把进程设 TASK_INTERRUPTIBLE 并 schedule_timeout，由接收中断里的 wake_up_interruptible(&tty->read_wait) 唤醒；规范模式（ldata->icanon && !L_EXTPROC(tty)）走 canon_copy_from_read_buf，按行拷贝；非规范模式走 copy_from_read_buf 两次——环形缓冲会跨越结尾，一次拷贝会被切成两段。它的等待循环骨架：

canon_copy_from_read_buf 的核心是 read_flags 位图：

c
        n = min(*nr + 1, smp_load_acquire(&ldata->canon_head) - ldata->read_tail);
        tail = ldata->read_tail & (N_TTY_BUF_SIZE - 1);
        size = min_t(size_t, tail + n, N_TTY_BUF_SIZE);
        eol = find_next_bit(ldata->read_flags, size, tail);
        more = n - (size - tail);
        if (eol == N_TTY_BUF_SIZE && more) {
                /* scan wrapped without finding set bit */
                eol = find_next_bit(ldata->read_flags, more, 0);
                found = eol != more;
        } else
                found = eol != size;
        /* ... 计算 n / c ... */
        ret = tty_copy_to_user(tty, *b, tail, n);
        if (ret)
                return -EFAULT;
        *b += n;
        *nr -= n;
        if (found)
                clear_bit(eol, ldata->read_flags);
        smp_store_release(&ldata->read_tail, ldata->read_tail + c);

行结束符位置在 read_flags 里置 1，find_next_bit 找到这一行结尾，tty_copy_to_user 拷走，clear_bit 清标记，read_tail 前移。两种模式都从 ldata->read_buf[] 取数据，往里填的是接收中断路径上的 n_tty_receive_buf。整条链路完整：

十二、易错点速查 #

# 易错点 正确做法
1 把 struct tty_operations uart_ops（serial_core 里的）和 struct uart_ops xxx_ops（驱动要实现的那个）搞混 串口驱动只填 struct uart_ops；struct tty_operations 由 serial_core 提供
2 以为 tty_set_operations 会逐字段拷贝函数指针 它只赋一个 ops 指针；tty_driver 里没有那些函数指针成员
3 串口吞吐按 baud/8 估 8N1 是 10 bit 一帧，按 baud/10 算，见第四章
4 以为 tty 设备是 tty_register_driver 建的 串口设了 TTY_DRIVER_DYNAMIC_DEV，节点由 uart_add_one_port 建
5 tty->port 忘了设 open 时 WARN 且会崩，见 tty_init_dev
6 开了 crtscts 但 DTS 没接 RTS/CTS 发送会卡死
7 发二进制数据不关 IXON 0x11/0x13 被当流控吃掉，用 stty raw
8 以为 /proc/tty/driver/<name> 一定有 tty_operations 没实现 proc_show 时这个节点根本不创建
9 往 tty_operations 里塞 uart_ops 的回调名 两个结构体不同，tty_operations 没有 startup/tx_empty 这些成员
10 自己的 tty driver 只填 open/write，没填 install 不填就走 tty_standard_install 兜底，能跑；填了要自己把 tty 装进 driver->ttys[index]
11 以为 do_tty_write 一次把整块数据交给驱动 默认 2048 字节一片，长写会被切成多次调用
12 改 termios 后只更新了波特率，忘了同步 ldisc tty->ops->set_termios 之后 ldisc 的 set_termios 也要跟着走，否则 ONLCR/ICRNL 行为对不上
13 以为 tty_ldiscs[] 里没编号就是坏 先看 CONFIG_LDISC_AUTOLOAD 有没有开，再确认 tty-ldisc-N 模块是否存在
14 把 tty_unregister_device 的 index 和 driver->num 弄混 索引来自 line/minor_start 偏移，不是数组长度
