一、输入子系统要解决什么 #

先看一个已经写好的按键驱动摆在面前的问题。中断、poll、异步通知、互斥都加上了，read/write 也实现了，应用打开 /dev/button 能读到一串字节。然后应用作者问你：这几个字节是什么意思？

没有答案。这个格式只有你的驱动懂，换一个按键驱动，应用就得重写。设备一多更麻烦：鼠标、键盘、触摸屏、手柄、平板笔同时插着，原理不同、上报方式不同、字节布局不同。每个驱动自带一套私有 ABI，用户态就只能给每个设备写一套适配。

input 子系统把这件事收掉：设备驱动只负责把硬件状态翻译成标准事件，翻译完往上一交，剩下的谁要谁拿。标准就是 (type, code, value) 三元组加一套全局统一的编码表。三层结构：

层 内核位置 职责 关键接口
设备驱动层 drivers/input/{keyboard,mouse,touchscreen,joystick,misc,…} 把硬件输入翻译成统一事件，向 core 上报 input_allocate_device、input_register_device、input_report_*
输入核心层 input core drivers/input/input.c 给下层注册 input_dev 的接口，给上层注册 handler 的接口，负责事件分发与匹配 input_event、input_register_handler、input_register_handle
事件驱动层 handlers drivers/input/{evdev,joydev,mousedev,…}.c 把事件接到用户态，负责 file_operations 与 /dev 下的设备节点 evdev_fops 等

没有第四层。input.c 就是 core 的全部，evdev.c、joydev.c、mousedev.c 是三个平行 handler，彼此不依赖。不同 handler 留给用户态的接口名不一样：Event 类走 /dev/input/eventX，X 从 0 起；Mouse 类走 /dev/input/mouseX，专指 PS/2 那一路；Joystick 类走 /dev/input/jsX。一个设备可以同时被多个 handler 接住，所以同一个物理鼠标同时出现 event2 和 mouse0 不是 bug，是设计。

这个子系统要满足三条需求，也是判断一个驱动写得对不对的标准：每接入一个输入设备，/dev/input 下要有对应节点；设备驱动只管「取事件」，事件怎么到设备文件不归它管；不同类型的设备拿到不同形态的设备文件接口，这套接口由 handler 层实现。第三条是 handler 分家的理由——键盘要「按键字符流」，手柄要「轴和按钮的结构化状态」，触摸屏要「带时间戳的原始事件序列」，三种需求写不进同一个 file_operations。

二、input 设备的分类 #

内核不给「设备类型」建枚举。它用能力位描述设备，再让 handler 按能力位去匹配。落成表格：

分类 典型硬件 主要事件类型 命中的 handler 用户态节点
事件类 USB 鼠标、USB 键盘、触摸屏、板载按键 EV_KEY / EV_REL / EV_ABS evdev /dev/input/eventX
MOUSE 类 PS/2 接口鼠标 EV_REL + BTN_LEFT 等 mousedev /dev/input/mouseX
游戏杆类 手柄、摇杆 EV_ABS + EV_KEY joydev /dev/input/jsX
力反馈类 震动方向盘、震动手柄 EV_FF、EV_FF_STATUS evdev + ff-core /dev/input/eventX
开关/传感器类 盖子开关、耳机插入、旋转锁 EV_SW 无专门 handler，evdev 透传 /dev/input/eventX
无线开关类 无线电开关按键 EV_KEY + SW_RFKILL_ALL rfkill 过滤 无独立节点

rfkill 靠 filter 回调先过一道，把该吞掉的事件在到达普通 handler 之前拦下；sysrq 也是 filter，在 /proc/bus/input/handlers 里带 (filter) 标记。设备身份用 struct input_id 标，四个 __u16：bustype、vendor、product、version。

bustype 取 BUS_* 系列：BUS_PCI=0x01、BUS_USB=0x03、BUS_VIRTUAL=0x06、BUS_ISA=0x10、BUS_I8042=0x11、BUS_I2C=0x18、BUS_HOST=0x19、BUS_SPI=0x1c。板载按键那种没有物理总线的填 BUS_HOST，纯软件虚拟的填 BUS_VIRTUAL。填错的后果不严重，但 libinput、udev 规则会按这个字段归类，填 BUS_VIRTUAL 的手柄会被当成不可信设备。

propbit 描述「这类设备的怪异属性」，取 INPUT_PROP_*：INPUT_PROP_POINTER、INPUT_PROP_DIRECT、INPUT_PROP_BUTTONPAD、INPUT_PROP_SEMI_MT、INPUT_PROP_TOPBUTTONPAD、INPUT_PROP_POINTING_STICK、INPUT_PROP_ACCELEROMETER，最大到 INPUT_PROP_MAX=0x1f。

INPUT_PROP_DIRECT 是触摸屏与触摸板的分水岭：直接坐标（手指落在哪就是哪）标 DIRECT，间接坐标（触摸板，手指挪的是光标）标 POINTER。libinput 这类库第一眼看的就是这一位，标错方向，触摸板会被当成绝对定位屏，光标瞬移到手指按下那个点的屏幕坐标上。分类在代码里的落点只有 input_set_capability() 和 input_set_abs_params() 两次调用，没有 input_set_device_type() 这种函数，因为「类型」是能力位算出来的副产物。

三、input_dev：一个输入设备的抽象 #

输入设备在核心里就是一个 struct input_dev，定义在 include/linux/input.h。下面是 4.19 的完整定义，字段一个没删：

c
struct input_dev {
        const char *name;
        const char *phys;
        const char *uniq;
        struct input_id id;

        unsigned long propbit[BITS_TO_LONGS(INPUT_PROP_CNT)];

        unsigned long evbit[BITS_TO_LONGS(EV_CNT)];
        unsigned long keybit[BITS_TO_LONGS(KEY_CNT)];
        unsigned long relbit[BITS_TO_LONGS(REL_CNT)];
        unsigned long absbit[BITS_TO_LONGS(ABS_CNT)];
        unsigned long mscbit[BITS_TO_LONGS(MSC_CNT)];
        unsigned long ledbit[BITS_TO_LONGS(LED_CNT)];
        unsigned long sndbit[BITS_TO_LONGS(SND_CNT)];
        unsigned long ffbit[BITS_TO_LONGS(FF_CNT)];
        unsigned long swbit[BITS_TO_LONGS(SW_CNT)];

        unsigned int hint_events_per_packet;

        unsigned int keycodemax;
        unsigned int keycodesize;
        void *keycode;

        int (*setkeycode)(struct input_dev *dev,
                          const struct input_keymap_entry *ke,
                          unsigned int *old_keycode);
        int (*getkeycode)(struct input_dev *dev,
                          struct input_keymap_entry *ke);

        struct ff_device *ff;

        unsigned int repeat_key;
        struct timer_list timer;
        int rep[REP_CNT];
        struct input_mt *mt;
        struct input_absinfo *absinfo;
        unsigned long key[BITS_TO_LONGS(KEY_CNT)];
        unsigned long led[BITS_TO_LONGS(LED_CNT)];
        unsigned long snd[BITS_TO_LONGS(SND_CNT)];
        unsigned long sw[BITS_TO_LONGS(SW_CNT)];

        int (*open)(struct input_dev *dev);
        void (*close)(struct input_dev *dev);
        int (*flush)(struct input_dev *dev, struct file *file);
        int (*event)(struct input_dev *dev, unsigned int type, unsigned int code, int value);

        struct input_handle __rcu *grab;

        spinlock_t event_lock;
        struct mutex mutex;
        unsigned int users;
        bool going_away;
        struct device dev;
        struct list_head        h_list;
        struct list_head        node;

        unsigned int num_vals;
        unsigned int max_vals;
        struct input_value *vals;

        bool devres_managed;
};

四十一行字段（含函数指针），分四组看，别一口气背：

组 字段 说明
身份 name / phys / uniq / id 名字、系统层次里的物理路径、唯一识别码、input_id。/proc/bus/input/devices 的 N/P/U/I 四行就是这四个
能力位图 propbit、evbit、keybit、relbit、absbit、mscbit、ledbit、sndbit、ffbit、swbit 每种事件一张位图。evbit 是总开关，其他位图必须和 evbit 对得上，否则注册时会被清零
状态与参数 absinfo、mt、key、led、snd、sw、rep、repeat_key、timer absinfo 存绝对轴的 value/minimum/maximum/fuzz/flat/resolution；mt 指向多点触控状态；key/led/snd/sw 是「当前状态」而非「能力」
生命周期与分发 open / close / flush / event、grab、event_lock、mutex、users、going_away、dev、h_list、node、vals 系列、devres_managed open 在第一个用户 input_open_device 时调用，close 在最后一个用户关闭时调用；h_list 挂该设备上的所有 handle；node 把设备挂到 input_dev_list

几个容易看漏的。hint_events_per_packet 给 handler 估算缓冲区大小，语义是「一个包（两次 SYN_REPORT 之间）平均多少事件」；num_vals/max_vals/vals 是 core 自己的一帧累积区，input_register_device 里按 hint + 2 分配，驱动不该碰。keycodemax/keycodesize/keycode 加 getkeycode/setkeycode 是键码映射表，带扫描码的设备（矩阵键盘、PS/2 键盘）在这里放「硬件扫描码 → KEY_*」的表，用户态通过 EVIOCGKEYCODE/EVIOCSKEYCODE 读写；板载 GPIO 按键每个引脚在驱动里就写死了 KEY_A 之类，这两个回调留空。ff 是力反馈设备指针，repeat_key/timer/rep[] 是软重复状态，led/snd/sw 是当前状态位图——跟 ledbit/sndbit/swbit 的「能力」位图区分：前者记「现在灯是亮的吗」，后者记「这设备有灯吗」。grab 是被独占时指向抢占者的 handle，going_away 是「正在注销」的标志，devres_managed 是「生命周期交给 devres 托管」，三个字段都为同一件事：确保设备在拔线、grab、模块卸载三种并发场景下不打穿。

BITS_TO_LONGS 决定每张位图占几个 unsigned long，4.19 是 #define BITS_TO_LONGS(nr) DIV_ROUND_UP(nr, BITS_PER_BYTE * sizeof(long))。素材里写的是 ((nr) + (32 - 1) / (32))，那是把宏拍扁成 32 位版本，而且括号位置也错了，展开等于 nr + 0。按 32 位 long 正确写法应是 ((nr) + 31) / 32。用宏的意图没错：EV_CNT = EV_MAX + 1 = 0x20，正好 32，evbit 一个 long 装得下；KEY_CNT = 0x300 就要 24 个 long。所以「1~32 用 1 个，33~64 用 2 个」这个理解是对的，别被公式带偏。

设能力位在 3.x 时代是手写 set_bit(EV_KEY, dev->evbit)；4.x 起统一走 input_set_capability(dev, type, code)，它会顺手把 evbit 置上，并给 EV_ABS 分配 absinfo。手写 set_bit 在 4.x 仍能编过，但 EV_ABS 那条路会漏掉 absinfo 分配，注册时直接 -EINVAL。这个坑在第六章和第十一章各出现一次，值得记牢。

struct input_dev 里没有一块是「设备类型」，也没有一块是「坐标范围」。设备能力全部散在那十张位图加一张 absinfo 数组里，input_register_device 之后这些位图就冻结了——注册后再改位图，用户态 EVIOCGBIT 缓存的还是旧值。

四、input 事件的类型与编码 #

事件是 (type, code, value) 三元组。type 取 EV_*，code 取该类型下的具体编码，value 的含义随类型变。完整事件类型表（include/uapi/linux/input-event-codes.h）：

宏 值 含义 value 语义
EV_SYN 0x00 同步 0
EV_KEY 0x01 按键/按钮 0 松开，1 按下，2 自动重复
EV_REL 0x02 相对位移 增量
EV_ABS 0x03 绝对坐标 绝对位置
EV_MSC 0x04 杂项 视 code
EV_SW 0x05 开关 0/1
EV_LED 0x11 设备 LED 0/1
EV_SND 0x12 声音/报警 视 code
EV_REP 0x14 自动重复参数 延时/周期
EV_FF 0x15 力反馈 效果参数
EV_PWR 0x16 电源 —
EV_FF_STATUS 0x17 力反馈状态 状态值
EV_MAX 0x1f 类型最大编号 位图上限

EV_CNT = EV_MAX + 1 = 32。注意 0x06~0x10 是空档，从 EV_SW=0x05 直接跳到 EV_LED=0x11，这是历史遗留，中间原本留给早期编号，后来重新排过。

同步子编码有四个：SYN_REPORT=0（一帧结束）、SYN_CONFIG=1、SYN_MT_REPORT=2（旧式 MT 协议用）、SYN_DROPPED=3（core 丢事件时补发，告诉用户态状态已断）。SYN_DROPPED 值得展开一句：它出现意味着 client 环形缓冲溢出、中间一堆事件被丢。用户态收到它不能当普通事件推进，要丢掉自己的状态缓存，用 EVIOCGKEY/EVIOCGMTSLOTS 重新拉一份全量快照。libinput 就这么处理，自己写 evdev 客户端也得这么处理，否则丢包之后按键状态会永远错位。

按键编码分两段。普通键 KEY_* 从 0 到 KEY_MAX=0x2ff：KEY_RESERVED=0（保留，不发给用户态）、KEY_ESC=1、KEY_LEFTCTRL=29、KEY_A=30（之后 B~Z 连续排）。按钮 BTN_* 从 0x100 起，跟 KEY_* 共用同一个 0x300 编号空间，只是段位不同：BTN_MISC=0x100、BTN_MOUSE=0x110（BTN_LEFT 同值）、BTN_JOYSTICK=0x120、BTN_GAMEPAD=0x130、BTN_DIGI=0x140、BTN_TOOL_FINGER=0x145、BTN_TOUCH=0x14a、BTN_STYLUS=0x14b。KEY_CNT = KEY_MAX + 1 = 0x300，24 个 long 的位图，EVIOCGKEY 一次要拷 96 字节（64 位机）。

绝对轴 ABS_*，ABS_MAX=0x3f。本篇关心这几个：ABS_X/ABS_Y 是 0x00/0x01，ABS_PRESSURE 是 0x18，ABS_DISTANCE 是 0x19，ABS_TOOL_WIDTH 是 0x1c，ABS_MT_SLOT 是 0x2f，ABS_MT_TOUCH_MAJOR 是 0x30（即 ABS_MT_FIRST），ABS_MT_POSITION_X/ABS_MT_POSITION_Y 是 0x35/0x36，ABS_MT_TOOL_TYPE 是 0x37，ABS_MT_TRACKING_ID 是 0x39，ABS_MT_PRESSURE 是 0x3a，ABS_MT_TOOL_Y 是 0x3d（即 ABS_MT_LAST）。

ABS_MT_FIRST 就是 ABS_MT_TOUCH_MAJOR，ABS_MT_LAST 是 ABS_MT_TOOL_Y，两者之间全是多点触控专用轴，0x3d - 0x30 + 1 = 14，正好 14 根。ABS_X/ABS_Y 和 ABS_MT_POSITION_X/ABS_MT_POSITION_Y 是两套轴：前者是单点遗留，后者是 MT 专用。一个多点驱动同时报这两套，老应用读前者、新应用读后者，这叫 pointer emulation，细节在《触摸屏与按键驱动实战》第五章。

相对轴 REL_X=0x00、REL_Y=0x01、REL_WHEEL=0x08。开关 SW_LID=0x00、SW_TABLET_MODE=0x01、SW_JACK_PHYSICAL_INSERT=0x07、SW_ROTATE_LOCK=0x0c。杂项 MSC_SERIAL=0x00、MSC_SCAN=0x04、MSC_TIMESTAMP=0x05。自动重复 REP_DELAY=0x00、REP_PERIOD=0x01。MSC_SCAN 是调试时最有用的那个：键盘驱动把硬件扫描码单独报一条 EV_MSC/MSC_SCAN，evtest 一开就能看到「物理上按下的是哪个键」，跟 KEY_* 映射表分开看，键码映射错了一眼就能定位。

事件传到用户态长这样，struct input_event：

c
struct input_event {
#if (__BITS_PER_LONG != 32 || !defined(__USE_TIME_BITS64)) && !defined(__KERNEL)
        struct timeval time;
#define input_event_sec time.tv_sec
#define input_event_usec time.tv_usec
#else
        __kernel_ulong_t __sec;
        __kernel_ulong_t __usec;
#define input_event_sec  __sec
#define input_event_usec __usec
#endif
        __u16 type;
        __u16 code;
        __s32 value;
};

时间戳形态按 __BITS_PER_LONG 和 __USE_TIME_BITS64 分叉：64 位用户态默认走 __sec/__usec 两个 __kernel_ulong_t，32 位或未开 64 位 time 的 libc 走 struct timeval，两边都靠 input_event_sec/input_event_usec 宏抹平。交叉编译、32/64 位混跑时读出来的时间戳一塌糊涂，原因就在这。结构体大小：64 位下 8+8+2+2+4 = 24 字节（有 4 字节尾填充），32 位下 16 字节。写跨平台 evdev 客户端按 24 字节算缓冲区，32 位机上会浪费但不会错。

时间戳的时钟源可以选，EVIOCSCLOCKID 三个选项：CLOCK_REALTIME（墙钟，会被 NTP 跳）、CLOCK_MONOTONIC（开机以来单调增）、CLOCK_BOOTTIME（含休眠时间）。做手势识别、录像同步选后两个，看日志对时间选第一个。默认是 CLOCK_REALTIME。

五、input_report_xxx 系列接口 #

驱动上报事件用 input_event() 和它的一圈 inline 包装，全部在 include/linux/input.h：

c
void input_event(struct input_dev *dev, unsigned int type,
                 unsigned int code, int value);
void input_inject_event(struct input_handle *handle, unsigned int type,
                        unsigned int code, int value);

static inline void input_report_key(struct input_dev *dev, unsigned int code, int value)
{
        input_event(dev, EV_KEY, code, !!value);
}
static inline void input_report_rel(struct input_dev *dev, unsigned int code, int value)
{
        input_event(dev, EV_REL, code, value);
}
static inline void input_report_abs(struct input_dev *dev, unsigned int code, int value)
{
        input_event(dev, EV_ABS, code, value);
}
static inline void input_report_ff_status(struct input_dev *dev, unsigned int code, int value)
{
        input_event(dev, EV_FF_STATUS, code, value);
}
static inline void input_report_switch(struct input_dev *dev, unsigned int code, int value)
{
        input_event(dev, EV_SW, code, !!value);
}
static inline void input_sync(struct input_dev *dev)
{
        input_event(dev, EV_SYN, SYN_REPORT, 0);
}
static inline void input_mt_sync(struct input_dev *dev)
{
        input_event(dev, EV_SYN, SYN_MT_REPORT, 0);
}

包装层有两处细节。input_report_key 和 input_report_switch 都把 value 过了一遍 !!，你传 3 进去会被压成 1；要发自动重复的「2」只能直接调 input_event(dev, EV_KEY, code, 2)。input_report_rel 和 input_report_abs 不过 !!，因为相对位移和绝对坐标本来就要原值。input_mt_sync 只发 SYN_MT_REPORT，是给旧式协议 A 用的分隔符，协议 B 不用它、改用 input_mt_sync_frame；B 协议驱动里插一句 input_mt_sync，内核会当成「一个触点结束」处理，槽位编号错乱。

input_sync 不能省。它是一帧的收尾：core 在收到 SYN_REPORT 之前把本帧所有事件攒在 dev->vals 里，收到之后一次性推给所有 handler。少一次 sync，事件就卡在 half-full 的缓冲区里，直到攒满 max_vals - 2 才被强制 flush 一次并补一个 SYN_REPORT，表现就是用户态反应一顿一顿的。一个「按下」要这样报：input_report_key(dev, BTN_TOUCH, 1)、input_report_abs(dev, ABS_X, x)、input_report_abs(dev, ABS_Y, y)、input_report_abs(dev, ABS_PRESSURE, p)，最后 input_sync(dev)（等价 input_event(dev, EV_SYN, SYN_REPORT, 0)）。四条事件加一条同步，缺最后一条前四条就白报。顺序也有讲究：BTN_TOUCH 在坐标之前，用户态收包时先知道「有接触」再填坐标，逻辑上不会出现「坐标有了但还没按」的中间态。反过来也能跑，但协议不保证。

input_set_abs_params(dev, axis, min, max, fuzz, flat) 的签名是 void input_set_abs_params(struct input_dev *dev, unsigned int axis, int min, int max, int fuzz, int flat);。五个参数的含义按 struct input_absinfo 的注释：minimum/maximum 是轴的范围；fuzz 是噪声过滤半径，core 在 input_defuzz_abs_event() 里按它做平滑；flat 是「这个范围内一律按 0 报」的死区，主要给 joydev 用；resolution 不在这五个参数里，要单独写 absinfo[axis].resolution，那是每单位的物理量（典型单位「每毫米多少个单位」），libinput 用它把触摸板手势距离换算成毫米。触摸板驱动要填，触摸屏不填也不影响。这个函数会置 EV_ABS 和对应 absbit，所以调它之前不必先 set_bit(EV_ABS, evbit)。[3.x] 签名相同，input_defuzz_abs_event 的行为也是 3.x 引入的，更早的 2.6 时代 fuzz 处理更简单——具体分界点未验证。

fuzz 的三种处理（4.19 input.c）：

c
static int input_defuzz_abs_event(int value, int old_val, int fuzz)
{
        if (fuzz) {
                if (value > old_val - fuzz / 2 && value < old_val + fuzz / 2)
                        return old_val;
                if (value > old_val - fuzz && value < old_val + fuzz)
                        return (old_val * 3 + value) / 4;
                if (value > old_val - fuzz * 2 && value < old_val + fuzz * 2)
                        return (old_val + value) / 2;
        }
        return value;
}

小于半个 fuzz 直接吞、半个到一个 fuzz 走 3:1 加权、一到两个 fuzz 走平均、超过两个 fuzz 原样放行。所以 fuzz 设得对不对，直接决定坐标抖不抖。ADC 噪声在 ±3 个 LSB 的量级，fuzz = 4 是个合理起点；设成 0 就是把所有噪声原样交给用户态。注意 fuzz 的过滤只对「上一条成功上报的值」生效，被吞掉的值不更新 absinfo[axis].value，所以下一次比较还是拿原来那个基准——这个设计对噪声是正好，对真实快速移动就很糟，位移一下子超过两个 fuzz 才被放行，中间的小幅移动全丢。

input_event() 本身很薄，4.19：

c
void input_event(struct input_dev *dev, unsigned int type,
                 unsigned int code, int value)
{
        unsigned long flags;

        if (is_event_supported(type, dev->evbit, EV_MAX)) {
                spin_lock_irqsave(&dev->event_lock, flags);
                input_handle_event(dev, type, code, value);
                spin_unlock_irqrestore(&dev->event_lock, flags);
        }
}

evbit 里没这一位，事件直接被吞，一声不响。这是新手最常见的「代码全对但事件没出来」的头号原因：没有告警、没有返回值，is_event_supported 不通过就静默返回。input_report_abs 前没调 input_set_abs_params，EV_ABS 位没置上，所有坐标事件都进不来。

input_handle_event() 按类型分派处置（input_get_disposition）：

type 处置逻辑
EV_SYN SYN_REPORT 走 INPUT_PASS_TO_HANDLERS | INPUT_FLUSH；SYN_CONFIG 走 INPUT_PASS_TO_ALL；SYN_MT_REPORT 走 INPUT_PASS_TO_HANDLERS
EV_KEY keybit 里该位没置就丢弃；value == 2 绕过状态更新直接传；状态确实变化才传
EV_ABS 走 input_handle_abs_event，做 fuzz、做 MT 槽位暂存、值没变就丢
EV_REL value 为 0 直接丢，值相同不丢（相对轴的语义就是增量，报两次 1 就是滚两格）
EV_MSC 支持即 INPUT_PASS_TO_ALL，同时 add_input_randomness 熵池加熵
EV_SW 状态变化才传
EV_LED / EV_SND / EV_REP / EV_FF / EV_PWR 下发到设备的 dev->event 回调

这张表解释了三种「报了没反应」：EV_KEY 报了但 keybit 没这位，丢弃，连 dev->key 状态都不更新；EV_ABS 报相同的值，丢弃，因为值没变化（想强制重发同一个坐标得先报一个别的值）；EV_REL 报 0，丢弃，这是合理设计。

EV_KEY 的 value 语义对应键盘的按键重复：1 按下、0 松开、2 自动重复。驱动只报 0/1，2 由 core 定时器 input_repeat_key() 按 REP_DELAY/REP_PERIOD 自己生成。前提是设备位图里有 EV_REP，且 rep[] 有值。input_register_device 里如果发现 rep[REP_DELAY] 和 rep[REP_PERIOD] 都是 0，会调 input_enable_softrepeat(dev, 250, 33) 兜底，即 250ms 后开始重复、33ms 一次。这条软重复只对 keybit 里有对应位且按住不放的键生效。

input_inject_event() 是给 handler 反向往设备塞事件用的（evdev 的 write 就走它）。和 input_event() 的差别只有一条：设备被别人 grab 了，且塞事件的 handle 不是 grab 者，事件被忽略。这条规则防的是「A 进程 grab 了设备，B 进程还能通过 write 往里塞假事件」的越权。用户态 write 到 /dev/input/eventX 的典型用途是送 EV_LED（点键盘灯）和 EV_FF（触发震动），方向和上报是反的。

六、input_register_device 的流程 #

分配、注册、卸载几个函数要分清楚，用错一个就是 bug：

函数 用在什么时候 说明
input_allocate_device() 注册前 kzalloc 一个 input_dev，填 dev.type/dev.class，device_initialize，初始化 mutex/event_lock/timer/两个链表，起名 input%lu
input_free_device() 注册前失败，或注册失败 只释放未注册的设备
input_register_device() 能力位配齐之后 注册；成功后由 core 接管生命周期
input_unregister_device() 已注册设备要拔 会自动调 input_free_device 那一侧

input_allocate_device() 源码（4.19）：

c
struct input_dev *input_allocate_device(void)
{
        static atomic_t input_no = ATOMIC_INIT(-1);
        struct input_dev *dev;

        dev = kzalloc(sizeof(*dev), GFP_KERNEL);
        if (dev) {
                dev->dev.type = &input_dev_type;
                dev->dev.class = &input_class;
                device_initialize(&dev->dev);
                mutex_init(&dev->mutex);
                spin_lock_init(&dev->event_lock);
                timer_setup(&dev->timer, NULL, 0);
                INIT_LIST_HEAD(&dev->h_list);
                INIT_LIST_HEAD(&dev->node);
                dev_set_name(&dev->dev, "input%lu",
                             (unsigned long)atomic_inc_return(&input_no));
                __module_get(THIS_MODULE);
        }
        return dev;
}

static atomic_t input_no = ATOMIC_INIT(-1) 加 atomic_inc_return 等于从 0 开始编号，dev_set_name 拿到的就是 input0、input1……这个序号在分配时就定了，注册失败也不回滚，所以 /sys/class/input 里出现 input2 缺号是常态。__module_get(THIS_MODULE) 是给「模块卸载时设备还挂着」保命，input_put_device 里减回去。timer_setup(&dev->timer, NULL, 0) 这行暴露了版本：timer_setup 是 4.15 引进的，[3.x] 里对应的是 setup_timer(&dev->timer, NULL, 0) 或更早的 init_timer() 加手工赋值 .function；素材驱动的 timer_setup(&button_timer, button_timer_timeout, 0) 走的是 4.15+ 路径，回调签名也必须是 void (*)(struct timer_list *)，用老版的 unsigned long 传参会在编译期就崩。

device_initialize 只做初始化，真正挂进设备模型是在 input_register_device 里调 device_add。三个容易混的函数：device_register = device_initialize + device_add；device_create() 是包了一层的便利函数，先按参数构造一个 struct device（填好 devt、class、parent、release），再走 device_register。这个拆分让 input core 能把「分配」和「进系统」两步分开——input_allocate_device 之后驱动还要填一堆能力位，这段时间设备不能出现在 /sys 里，否则 udev 会立刻收到 add 事件去建节点，而那时能力位还没配好。

input_put_device 是 put_device(&dev->dev) 的包装，把引用计数减一，计数归零才真释放。所以「注册成功后调 input_free_device」不是立刻 double free，而是把计数减到不匹配，等 input_unregister_device 再减一次时触发 refcount 告警或提前释放——两种表现都难看。正确用法只有一条：注册成功过就只调 input_unregister_device。

input_set_capability() 一次只设一个 (type, code)，多个能力就多调几次。EV_ABS 这个分支会先 input_alloc_absinfo，其余分支规模一样、只换位图：

c
void input_set_capability(struct input_dev *dev, unsigned int type, unsigned int code)
{
        switch (type) {
        case EV_KEY:
                __set_bit(code, dev->keybit);
                break;
        case EV_REL:
                __set_bit(code, dev->relbit);
                break;
        case EV_ABS:
                input_alloc_absinfo(dev);
                if (!dev->absinfo)
                        return;
                __set_bit(code, dev->absbit);
                break;
        case EV_MSC:
                __set_bit(code, dev->mscbit);
                break;
        /* EV_SW/EV_LED/EV_SND/EV_FF 分别写 swbit/ledbit/sndbit/ffbit，略 */
        case EV_PWR:
                /* do nothing */
                break;
        default:
                pr_err("%s: unknown type %u (code %u)\n", __func__, type, code);
                dump_stack();
                return;
        }

        __set_bit(type, dev->evbit);
}

三点。case EV_ABS 里 input_alloc_absinfo(dev) 分配 ABS_CNT 个 struct input_absinfo，失败就 return，连 absbit 都不置，这是唯一会分配内存的分支。case EV_PWR 什么都不做，但末尾那句 __set_bit(type, dev->evbit) 还是执行，所以 EV_PWR 只有类型位、没有子码位，跟 EV_REP 一样。default 分支 pr_err 加 dump_stack() 是故意让它在 dmesg 里炸出来。device_initialize 之后分配器已经把 dev_set_name 设成 input%lu，所以 /sys/class/input/input0 这些名字在注册前就定了。

input_register_device() 完整流程，按顺序看：

c
int input_register_device(struct input_dev *dev)
{
        struct input_devres *devres = NULL;
        struct input_handler *handler;
        unsigned int packet_size;
        const char *path;
        int error;

        if (test_bit(EV_ABS, dev->evbit) && !dev->absinfo)
                return -EINVAL;                 /* 1 */
        if (dev->devres_managed) {              /* 2 */
                devres = devres_alloc(devm_input_device_unregister,
                                      sizeof(*devres), GFP_KERNEL);
                if (!devres)
                        return -ENOMEM;
                devres->input = dev;
        }

        __set_bit(EV_SYN, dev->evbit);          /* 3 */
        __clear_bit(KEY_RESERVED, dev->keybit); /* 4 */
        input_cleanse_bitmasks(dev);            /* 5 */

        packet_size = input_estimate_events_per_packet(dev);  /* 6 */
        if (dev->hint_events_per_packet < packet_size)
                dev->hint_events_per_packet = packet_size;

        dev->max_vals = dev->hint_events_per_packet + 2;      /* 7 */
        dev->vals = kcalloc(dev->max_vals, sizeof(*dev->vals), GFP_KERNEL);
        if (!dev->vals) {
                error = -ENOMEM;
                goto err_devres_free;
        }

        /* 8：驱动自己设了 rep[] 就不用 core 的软重复 */
        if (!dev->rep[REP_DELAY] && !dev->rep[REP_PERIOD])
                input_enable_softrepeat(dev, 250, 33);

        if (!dev->getkeycode)                   /* 9 */
                dev->getkeycode = input_default_getkeycode;
        if (!dev->setkeycode)
                dev->setkeycode = input_default_setkeycode;

        error = device_add(&dev->dev);          /* 10 */
        if (error)
                goto err_free_vals;

        path = kobject_get_path(&dev->dev.kobj, GFP_KERNEL);  /* 11 */
        pr_info("%s as %s\n", dev->name ? dev->name : "Unspecified device",
                path ? path : "N/A");
        kfree(path);

        error = mutex_lock_interruptible(&input_mutex);       /* 12 */
        if (error)
                goto err_device_del;

        list_add_tail(&dev->node, &input_dev_list);
        list_for_each_entry(handler, &input_handler_list, node)
                input_attach_handler(dev, handler);

        input_wakeup_procfs_readers();                        /* 13 */
        mutex_unlock(&input_mutex);

        if (dev->devres_managed)
                devres_add(dev->dev.parent, devres);
        return 0;

err_device_del:
        device_del(&dev->dev);
err_free_vals:
        kfree(dev->vals);
        dev->vals = NULL;
err_devres_free:
        devres_free(devres);
        return error;
}

代码里 1~6 的编号对应下面七条（第 4 条里把估算与分配合成了一步）：

  1. EV_ABS 有、absinfo 没有，直接 -EINVAL。这是 input_set_abs_params 存在的真正理由，手写 set_bit(EV_ABS, evbit) 会踩到这条；devres 托管设备在此之前先登记回收器。
  2. 无条件置 EV_SYN，再清 KEY_RESERVED（0 号键不往用户态发）。所以任何设备都有 EV_SYN，/proc/bus/input/devices 里 EV= 的第一位永远是 1 或 3、5、7 这种奇数。
  3. input_cleanse_bitmasks：evbit 里没开的类型，对应位图整块清零。这一步会把你「顺手设了但忘了开类型」的能力位静默吃掉。
  4. input_estimate_events_per_packet 估算包大小：MT 设备按 num_slots 算，无槽位但带 ABS_MT_TRACKING_ID 的按 maximum - minimum + 1 再钳到 2~32，只有 ABS_MT_POSITION_X 的按 2，其余按 0；每根轴算 1 个事件，MT 轴按槽位数算；REL 全部计入；再加 7 个给 KEY 和 MSC 留位。然后 max_vals = hint + 2，kcalloc 一帧缓冲。
  5. 没设重复参数就上 input_enable_softrepeat(dev, 250, 33)；没提供 getkeycode/setkeycode 就塞默认实现。
  6. device_add(&dev->dev)——这一步会在 /sys/class/input/inputN 建出链接。注意此时 dev->dev.devt 是 0，所以不会在 /dev/input 下建节点，真正的 /dev/input/eventX 是后面 handler 的 connect 里建的。随后 pr_info 打出 名字 as /sys/devices/.../input/inputN，就是 insmod 之后看到的那行。
  7. 上 input_mutex，list_add_tail(&dev->node, &input_dev_list)，然后遍历 input_handler_list 逐个 input_attach_handler。最后 input_wakeup_procfs_readers() 叫醒正在 poll /proc/bus/input/devices 的进程，再解锁。失败路径反向拆，vals 单独 kfree 掉。

第 3 步值得单独说。input_cleanse_bitmasks 遍历所有位图，把 evbit 没开的类型整个清零。写驱动时「我先 set_bit(KEY_A, keybit) 再设 EV_KEY」，顺序反了也没事，注册时会救回来；但「set_bit(KEY_A, keybit) 却忘了 EV_KEY」，注册时这块被清零，input_report_key 报出去的事件在 input_get_disposition 里被 is_event_supported 挡掉，全程无告警。

匹配是双向的、不管先后：注册设备时先挂 input_dev_list（LIST_HEAD 静态初始化）再遍历 input_handler_list；注册 handler 时反过来先挂 handler 表再遍历设备表。谁先谁后都能配上——evdev 编译进内核时先于大多数设备驱动初始化，做成模块时先加载哪个都行。

input_attach_handler 这一小段是匹配的总闸门，注册设备、注册 handler 两条路都会进：

c
static int input_attach_handler(struct input_dev *dev, struct input_handler *handler)
{
        const struct input_device_id *id;
        int error;

        id = input_match_device(handler, dev);
        if (!id)
                return -ENODEV;

        error = handler->connect(handler, dev, id);
        if (error && error != -ENODEV)
                pr_err("failed to attach handler %s to device %s, error: %d\n",
                       handler->name, kobject_name(&dev->dev.kobj), error);

        return error;
}

-ENODEV 是「没配上」的正常返回值，不打印；其他错误才 pr_err。所以 dmesg 里出现 failed to attach handler 就是真有问题——多半是 connect 里分配失败或者 input_register_handle 出错。input_match_device 遍历 handler 的 id_table：for (id = handler->id_table; id->flags || id->driver_info; id++) 里，input_match_device_id(dev, id) 过一遍，再让 handler->match 做细筛（没定义就跳过），第一个都过的项返回。所以表尾那个 { } 全零项自动终止；反过来，如果一项 flags 和 driver_info 都是 0 但你本意是「这一项匹配全部设备」，那就等于提前结束了整张表。

input_match_device_id 比对 input_id 的四个字段，再对十张能力位图逐个 bitmap_subset：

c
bool input_match_device_id(const struct input_dev *dev,
                           const struct input_device_id *id)
{
        if (id->flags & INPUT_DEVICE_ID_MATCH_BUS)
                if (id->bustype != dev->id.bustype)
                        return false;
        if (id->flags & INPUT_DEVICE_ID_MATCH_VENDOR)
                if (id->vendor != dev->id.vendor)
                        return false;
        if (id->flags & INPUT_DEVICE_ID_MATCH_PRODUCT)
                if (id->product != dev->id.product)
                        return false;
        if (id->flags & INPUT_DEVICE_ID_MATCH_VERSION)
                if (id->version != dev->id.version)
                        return false;

        if (!bitmap_subset(id->evbit, dev->evbit, EV_MAX) ||
            !bitmap_subset(id->keybit, dev->keybit, KEY_MAX) ||
            !bitmap_subset(id->relbit, dev->relbit, REL_MAX) ||
            !bitmap_subset(id->absbit, dev->absbit, ABS_MAX) ||
            !bitmap_subset(id->mscbit, dev->mscbit, MSC_MAX) ||
            !bitmap_subset(id->ledbit, dev->ledbit, LED_MAX) ||
            !bitmap_subset(id->sndbit, dev->sndbit, SND_MAX) ||
            !bitmap_subset(id->ffbit, dev->ffbit, FF_MAX) ||
            !bitmap_subset(id->swbit, dev->swbit, SW_MAX) ||
            !bitmap_subset(id->propbit, dev->propbit, INPUT_PROP_MAX))
                return false;

        return true;
}

bitmap_subset(a, b, n) 判断 a ⊆ b。id 表里没写的位图是全 0，0 ⊆ anything 恒真，所以「不给能力位要求」等价于「所有设备都符合」。input_device_id 的 flags 与 INPUT_DEVICE_ID_MATCH_* 一一对应：1 匹配总线、2 匹配供应商、4 匹配产品、8 匹配版本，能力位图那几张是 0x0010 起的独立开关。这四个 MATCH_* 位只控制「要不要比 input_id 那四个字段」，能力位图是无条件比的——你写了 absbit 就一定要求子集关系，没有开关能关掉它。

匹配成功后进 handler->connect。一个 input_dev 可以同时被多个 handler 接住，evdev、mousedev、joydev 各建一个 handle，各建一个字符设备，次设备号不同。于是同一个鼠标既有 /dev/input/event2（major 13，minor 66）又有 /dev/input/mouse0（major 13，minor 32）。

七、handler 层：evdev 与其它 #

drivers/input/ 下 ls 一眼能看出哪些是 core、哪些是 handler：input.c 是 core，input-mt.c 是多点触控槽位库，input-compat.c 是 32 位兼容层，sparse-keymap.c/matrix-keymap.c 是键码表实现；evdev.c、mousedev.c、joydev.c、evbug.c、input-leds.c 是 handler，都调用 input_register_handler，都能被 /proc/bus/input/handlers 列出来。evbug.c 是调试用 handler，什么都不做，只把每条事件 printk 出来，意义是「不改驱动、不装 evtest，直接看 dmesg」；生产内核里别开它，一条鼠标移动就能把 dmesg 刷满。

handler 与 core 的接口结构是 struct input_handler：

c
struct input_handler {

        void *private;

        void (*event)(struct input_handle *handle, unsigned int type, unsigned int code, int value);
        void (*events)(struct input_handle *handle,
                       const struct input_value *vals, unsigned int count);
        bool (*filter)(struct input_handle *handle, unsigned int type, unsigned int code, int value);
        bool (*match)(struct input_handler *handler, struct input_dev *dev);
        int (*connect)(struct input_handler *handler, struct input_dev *dev, const struct input_device_id *id);
        void (*disconnect)(struct input_handle *handle);
        void (*start)(struct input_handle *handle);

        bool legacy_minors;
        int minor;
        const char *name;

        const struct input_device_id *id_table;

        struct list_head        h_list;
        struct list_head        node;
};

七个回调、三个标量字段、id_table 加两张 list_head，结构就是一个 private 加这些。下面逐回调说清楚。

回调 何时调 约束
event 单个事件分发 中断上下文，持 dev->event_lock，不能睡
events 一帧多个事件批量分发；有它就不再逐条调 event 同上
filter 在普通 handler 之前跑；返回 true 表示吞掉 同上；filter 的 handle 会被 list_add_rcu 插到 h_list 头部
match id_table 粗筛之后做细筛 —
connect 匹配成功、建立 handle 被 input_mutex 串行化
disconnect 断开 同上
start connect 之后立即调；设备从 grab 释放时再调一次 用于让 handler 与设备状态重新同步

七个回调里 event 和 events 是二选一的关系。core 在 input_to_handler 里先看 handler->events 有没有，有就批量调一次，没有才循环调 event。批量接口是为了摊薄锁开销：一帧 20 条事件，逐条进 evdev_event 就要拿 20 次 client->buffer_lock，批量接口一次拿完。filter 返回 true 是「吞掉」。rfkill 用它在事件到达 evdev 之前拦下 SW_RFKILL_ALL，sysrq 用它识别魔术键组合。filter 的优先级靠「插到 h_list 头部」实现，所以遍历 dev->h_list 时它自然排在最前。

legacy_minors + minor 是「老式次设备号段」：evdev 起 64、mousedev 起 32、joydev 起 0，各占 32 个号。这三段是 2.6 时代定死的，用户态脚本里写死了 13:64 这种设备号，动了就全崩。新 handler 不要再用这个机制，走动态分配（INPUT_FIRST_DYNAMIC_DEV=256 起）。name 就是 /proc/bus/input/handlers 里打出来的名字。

三者的连接物是 struct input_handle：void *private、int open、const char *name、struct input_dev *dev、struct input_handler *handler、struct list_head d_node、struct list_head h_node。dev 指向被接的设备，handler 指向接它的 handler，这就是一对多、多对多的那条边；d_node 挂进 dev->h_list，h_node 挂进 handler->h_list；open 是引用计数，只有非 0 的 handle 才收事件；private 是 handler 自己的上下文，evdev 里存的就是 struct evdev *。

本质上是三张表、两条边：input_dev_list 和 input_handler_list 是两张全局表，dev->h_list 与 handler->h_list 是 handle 的两端。一个 handle 等于「一对匹配成功的 dev + handler」，从任一端都能摸到另一端：[input_dev A] 的 h_list 上挂 [handle 1] 和 [handle 2]，分别指向 [input_handler evdev] 和 [input_handler kbd]。一个 input_dev 的 h_list 上挂几个 handle，就说明它被几个 handler 接住。/proc/bus/input/devices 里 H: Handlers=kbd event0 那一行就是这个链表的 name 拼接。

evdev 是用了最多的那个，drivers/input/evdev.c 末尾两个宏说明它也是个模块，evdev_init 里只有一句 return input_register_handler(&evdev_handler);，evdev_exit 里是对应的 input_unregister_handler。evdev_handler 定义成 { .event = evdev_event, .events = evdev_events, .connect = evdev_connect, .disconnect = evdev_disconnect, .legacy_minors = true, .minor = EVDEV_MINOR_BASE, .name = "evdev", .id_table = evdev_ids }——没有 filter、没有 match、没有 start。evdev 不做过滤也做不了细筛，它要接住所有设备。

EVDEV_MINOR_BASE 是 64，EVDEV_MINORS 是 32，EVDEV_MIN_BUFFER_SIZE 是 64，EVDEV_BUF_PACKETS 是 8，四个都在文件头部 #define。id_table 只有 { .driver_info = 1 } 加一个全零表尾。.driver_info = 1 让 flags 保持 0 但 input_match_device 的循环条件 id->flags || id->driver_info 成立，于是这一项被检查，input_match_device_id 里所有位图都是空集、0 ⊆ anything 恒真，结果「全匹配」。这就是为什么每个 input 设备注册完都会有 eventX。如果这里写成两个空 { }，整个 evdev 就一个设备也接不住，/dev/input 下空一片。

evdev_connect 是连接动作的全貌：

c
static int evdev_connect(struct input_handler *handler, struct input_dev *dev,
                         const struct input_device_id *id)
{
        struct evdev *evdev;
        int minor;
        int dev_no;
        int error;

        minor = input_get_new_minor(EVDEV_MINOR_BASE, EVDEV_MINORS, true);   /* 1 */
        if (minor < 0) {
                error = minor;
                pr_err("failed to reserve new minor: %d\n", error);
                return error;
        }

        evdev = kzalloc(sizeof(struct evdev), GFP_KERNEL);
        if (!evdev) {
                error = -ENOMEM;
                goto err_free_minor;
        }

        INIT_LIST_HEAD(&evdev->client_list);
        spin_lock_init(&evdev->client_lock);
        mutex_init(&evdev->mutex);
        init_waitqueue_head(&evdev->wait);
        evdev->exist = true;

        dev_no = minor;                                                     /* 2 */
        /* Normalize device number if it falls into legacy range */
        if (dev_no < EVDEV_MINOR_BASE + EVDEV_MINORS)
                dev_no -= EVDEV_MINOR_BASE;
        dev_set_name(&evdev->dev, "event%d", dev_no);

        evdev->handle.dev = input_get_device(dev);                          /* 3 */
        evdev->handle.name = dev_name(&evdev->dev);
        evdev->handle.handler = handler;
        evdev->handle.private = evdev;

        evdev->dev.devt = MKDEV(INPUT_MAJOR, minor);                        /* 4 */
        evdev->dev.class = &input_class;
        evdev->dev.parent = &dev->dev;
        evdev->dev.release = evdev_free;
        device_initialize(&evdev->dev);

        error = input_register_handle(&evdev->handle);                      /* 5 */
        if (error)
                goto err_free_evdev;

        cdev_init(&evdev->cdev, &evdev_fops);                               /* 6 */
        error = cdev_device_add(&evdev->cdev, &evdev->dev);
        if (error)
                goto err_cleanup_evdev;

        return 0;

 err_cleanup_evdev:
        evdev_cleanup(evdev);
        input_unregister_handle(&evdev->handle);
 err_free_evdev:
        put_device(&evdev->dev);
 err_free_minor:
        input_free_minor(minor);
        return error;
}

对着看六件事：input_get_new_minor(64, 32, true) 抢次设备号，范围 [64, 96)，抢不到从动态区（INPUT_FIRST_DYNAMIC_DEV=256 起）拿，第三个参数 true 表示允许动态回退。dev_no = minor - 64，于是 64 对应 event0、65 对应 event1；越过 96 的动态号不减，动态分配的设备会拿到 event300 这种名字。handle 填四个字段：dev（带引用）、name、handler、private，input_get_device 增加 input_dev 的引用计数，防止设备先于 handle 释放。evdev->dev.devt = MKDEV(INPUT_MAJOR, minor)，INPUT_MAJOR 是 13——这才让 /dev/input/eventX 真能建出来。input_register_handle 把 handle 挂进设备与 handler 两张 h_list，并调 handler->start。cdev_init 加 cdev_device_add 等价于 cdev_add 加 device_add，字符设备与设备模型一起挂上。失败路径的三层清理是倒序的：cdev_device_add 失败就先 evdev_cleanup 再注销 handle；input_register_handle 失败就只 put_device；最外层连次设备号都退。

[3.x] 这段末尾用的是 device_add(&evdev->dev) 加 cdev_add；cdev_device_add() 是 4.9 前后才出现的封装，[4.9+] 才有。老内核里是 cdev_add(&evdev->cdev, evdev->dev.devt, 1) 再 device_add(&evdev->dev) 两步，各自判错跳 err_cleanup_evdev。这个封装的动机是「字符设备与 sysfs 节点必须同生同死」——分两步写，中间那次 device_add 失败时要记得 cdev_del，忘了就留一个孤儿字符设备。

input_register_handle 这一段顺带把 filter 的位置讲清楚了：

c
int input_register_handle(struct input_handle *handle)
{
        struct input_handler *handler = handle->handler;
        struct input_dev *dev = handle->dev;
        int error;

        error = mutex_lock_interruptible(&dev->mutex);
        if (error)
                return error;

        /*
         * Filters go to the head of the list, normal handlers
         * to the tail.
         */
        if (handler->filter)
                list_add_rcu(&handle->d_node, &dev->h_list);
        else
                list_add_tail_rcu(&handle->d_node, &dev->h_list);

        mutex_unlock(&dev->mutex);
        list_add_tail_rcu(&handle->h_node, &handler->h_list);

        if (handler->start)
                handler->start(handle);

        return 0;
}

拿 dev->mutex 是为了不和 input_release_device() 撞车；filter 插头、普通 handler 插尾，直接决定了第九章「谁先看到事件」的顺序。

evdev_fops 是给用户态用的那一面：.owner = THIS_MODULE、.read = evdev_read、.write = evdev_write、.poll = evdev_poll、.open = evdev_open、.release = evdev_release、.unlocked_ioctl = evdev_ioctl、#ifdef CONFIG_COMPAT 包着的 .compat_ioctl = evdev_ioctl_compat、.fasync = evdev_fasync、.flush = evdev_flush、.llseek = no_llseek。

九个回调，缺一个就有一类用户态用法失灵：

回调 缺了的后果
read 读不出事件，整个设备废了
write 不能回灌事件，键盘点灯、手柄震动写不进去
poll 不能 epoll/select，只能阻塞 read，多设备场景被拖死
open 打不开，设备建不出来
release close 时 client 泄漏，环形缓冲永不释放
unlocked_ioctl EVIOCGNAME/EVIOCGRAB/EVIOCGBIT 全失效
compat_ioctl 32 位程序跑 64 位内核时 ioctl 全返回 -ENOTTY
fasync 不能 SIGIO 异步通知
flush 进程退出时不能清力反馈，震动会一直抖到断电

llseek = no_llseek 是显式声明「不能 seek」——字符设备的 read 流不能倒回，填 no_llseek 让 lseek 直接返回 -ESPIPE，比留 NULL 更明确。compat_ioctl 外面套了 #ifdef CONFIG_COMPAT，所以「九个回调」在具体内核里是 9 个还是 10 个，看 CONFIG_COMPAT。

每个打开 /dev/input/eventX 的文件描述符对应一个 struct evdev_client，自带环形缓冲：

c
struct evdev_client {
        unsigned int head;
        unsigned int tail;
        unsigned int packet_head;
        spinlock_t buffer_lock;
        struct fasync_struct *fasync;
        struct evdev *evdev;
        struct list_head node;
        unsigned int clk_type;
        bool revoked;
        unsigned long *evmasks[EV_CNT];
        unsigned int bufsize;
        struct input_event buffer[];
};

buffer[] 是柔性数组，跟在结构体后面一次分配。head 是写指针，tail 是读指针，packet_head 是「最后一个完整包的结束位置」：evdev_pass_values 往 head 写；遇到 SYN_REPORT 时把 packet_head = head；读的时候只读到 packet_head，tail != packet_head 才算有完整包可取。这就是 evdev_read 和 evdev_poll 里都用 packet_head != tail 判断可读的原因——半包不给。一个包写到一半（BTN_TOUCH 已写、坐标没写完），head 在动但 packet_head 没动，读者看不到半包。

evmasks[EV_CNT] 是 4.x 的客户端侧事件过滤（EVIOCSMASK），每个事件类型一张掩码，NULL 表示不过滤。clk_type 是 EVIOCSCLOCKID 设的时钟源。revoked 是 EVIOCREVOKE 的标记，置位后该 client 的所有操作都返回 -ENODEV。

bufsize 由 evdev_compute_buffer_size() 定：max(hint_events_per_packet * EVDEV_BUF_PACKETS, 64)，向上取到 2 的幂。所以第六章第 6 步里那个 hint_events_per_packet 估算最终变成了用户态缓冲区的大小。算一遍：双指触摸屏 num_slots=2、MT 轴 5 根，估算 15 个事件/包，乘 8 得 120，向上取 2 的幂得 128，一个 client 就是 128 × 24 = 3KB。20 个 client 就 60KB，所以 evdev_open 里 kzalloc 带 __GFP_NOWARN，失败退 vzalloc——一次要连续 3KB 以上的物理页，内存紧的机器上 kzalloc 会 warn。evdev 自身那个结构体则是 open 计数、内嵌 handle、wait 等待队列、grab 指针、client_list 加保护它的 client_lock、mutex、dev、cdev、exist；其中 grab 是 evdev 层的独占，一个 client 调 EVIOCGRAB 成功，evdev_pass_values 就只喂它，这跟 input_dev 上的 grab（handle 级独占）是两层，粒度不同。

八、input handler 的注册与匹配 #

handler 侧向 core 注册的两个函数是 input_register_handler / input_unregister_handler，handle 侧是 input_register_handle / input_unregister_handle。四个函数对称排开。

c
int input_register_handler(struct input_handler *handler)
{
        struct input_dev *dev;
        int error;

        error = mutex_lock_interruptible(&input_mutex);
        if (error)
                return error;

        INIT_LIST_HEAD(&handler->h_list);
        list_add_tail(&handler->node, &input_handler_list);
        list_for_each_entry(dev, &input_dev_list, node)
                input_attach_handler(dev, handler);
        input_wakeup_procfs_readers();
        mutex_unlock(&input_mutex);
        return 0;
}

和 input_register_device 是镜像的：一个先挂 dev 表再遍历 handler 表，一个先挂 handler 表再遍历 dev 表。input_mutex 就是这把对称锁，它同时保护两张表，顺带让 input_[un]register_device 和 input_[un]register_handler 互斥。没有这把锁，设备注册遍历到一半 handler 表被改，两边各遍历一次，同一个 (dev, handler) 对被 attach 两次、两次 connect、两个 /dev/input/eventX 抢同一个次设备号。锁的存在让「匹配」成为一个原子事件。

c
void input_unregister_handler(struct input_handler *handler)
{
        struct input_handle *handle, *next;

        mutex_lock(&input_mutex);

        list_for_each_entry_safe(handle, next, &handler->h_list, h_node)
                handler->disconnect(handle);
        WARN_ON(!list_empty(&handler->h_list));

        list_del_init(&handler->node);

        input_wakeup_procfs_readers();
        mutex_unlock(&input_mutex);
}

void input_unregister_handle(struct input_handle *handle)
{
        struct input_dev *dev = handle->dev;

        list_del_rcu(&handle->h_node);

        mutex_lock(&dev->mutex);
        list_del_rcu(&handle->d_node);
        mutex_unlock(&dev->mutex);

        synchronize_rcu();
}

卸载 handler 是「把这条边上的 handle 全 disconnect」，然后 WARN_ON 断言表真的空了。如果你在 disconnect 里忘了 input_unregister_handle，这行 WARN 就会在 dmesg 里骂你。list_for_each_entry_safe 那个 next 是为了在遍历中删除当前项不失效——disconnect 会调 input_unregister_handle，那里面 list_del_rcu(&handle->h_node) 正好删的就是 handler->h_list 上的这个节点。两条边分两步删，中间用 dev->mutex 保护 d_node；最后那句 synchronize_rcu() 是等所有正在遍历 h_list 的读者退出 RCU 临界区——input_pass_values 是 RCU 读侧，不等它就会拿已摘链的 handle 指针做判断。[3.x] 的 input_register_handle 没有 filter 分支，统一 list_add_tail；filter 优先入表是后加的优化，具体哪个版本引入未验证。

设备侧卸载走 __input_unregister_device，顺序是：先 input_disconnect_device（置 going_away、给所有按下的键补发松开事件、把所有 handle 的 open 清零），再上 input_mutex 逐个 handler->disconnect，再 del_timer_sync 删自动重复定时器，最后 device_del。input_disconnect_device 的动作是：拿 dev->mutex 把 going_away 置真，再拿 dev->event_lock 依次调 input_dev_release_keys(dev) 和把所有 handle 的 open 清 0。

补发松键这件事很关键：拔掉一个正按着的键盘，INPUT_PASS_TO_HANDLERS 已经走不通了，必须在断开前把 key 位图里所有置位逐个报 0 再补一个 SYN_REPORT，否则用户态会永远以为那个键按着，X 里就是「粘键」。注意顺序不能反：input_dev_release_keys 要靠 handle->open 非零才能把松键事件推出去，推完才清零。going_away 置位之后 input_open_device 会返回 -ENODEV，所以「拔设备的同时有人正 open」这个竞态，结果是 open 失败而不是拿到一个已死的设备。

/proc/bus/input/handlers 是这一步的观察窗口。input_proc_init() 在 input_init 里建两个文件：先 proc_mkdir("bus/input", NULL)，再 proc_create 出 devices 和 handlers，任一失败按逆序 remove_proc_entry 回滚。handlers 的读侧是 input_handlers_seq_show：seq_printf(seq, "N: Number=%u Name=%s", state->pos, handler->name)，handler->filter 非空补 " (filter)"，handler->legacy_minors 为真补 " Minor=%d"。

text

N: Number=1 Name=kbd

七行把三层结构摊平了：rfkill、kbd、sysrq、leds 是功能型 handler，mousedev/evdev/joydev 是设备文件型。带 (filter) 标记的只有一个 sysrq。Minor= 只在 legacy_minors 为 true 时打，所以 rfkill、kbd、leds 没有。Number= 是 input_handler_list 上的下标，顺序由初始化先后决定——编译进内核的 handler 按 subsys_initcall 之类的时间点排，模块按加载顺序追加，同一台机器两次开机就不一样，别拿这个号做判断。

顺带一处纠偏：素材正文说「rfkill 是 filter」，实测输出里 (filter) 标在 sysrq 上、rfkill 上没有。两者都带 filter 回调整理事件，但在这个内核版本上只有 sysrq 被标记成 filter handler。判断依据是 handler->filter 指针是否非空，不看你心里怎么想。

九、事件从驱动到用户态的完整路径 #

把前面几节串成一条线。驱动那边一句 input_report_key(dev, KEY_A, 1) 之后发生了什么：

  1. input_event() 检查 evbit 有没有 EV_KEY，没有就返回。
  2. 上 dev->event_lock，进 input_handle_event()。
  3. input_get_disposition() 判断处置：EV_KEY 要 keybit 支持，且 dev->key 状态真的变了才继续。
  4. 处置里带 PASS_TO_DEVICE 且 dev->event 非空时，回调设备的 event（比如让键盘点灯）。
  5. 处置里带 PASS_TO_HANDLERS 时，把 (type, code, value) 追加进 dev->vals，num_vals++。
  6. 处置里带 INPUT_FLUSH（也就是这一条是 SYN_REPORT）时，调 input_pass_values(dev, vals, num_vals) 推出去，num_vals 归零。
  7. input_pass_values 里 RCU 保护下看 dev->grab：被 grab 就只发给 grab 者；否则遍历 dev->h_list，handle->open 非 0 的才进。
  8. 对每个 handle，input_to_handler() 先过 filter（filter 返回 true 的事件被剔掉），再调 handler->events（evdev 有）或逐条 handler->event。
  9. evdev 的 evdev_events 取三个时钟源（mono / real / boot），遍历 client：被某个 client grab 就只给它，否则给 client_list 上所有 client。
  10. evdev_pass_values 把每个值拷成 struct input_event 塞进该 client 的环形缓冲，遇 SYN_REPORT 时更新 packet_head 并 kill_fasync 发 SIGIO，然后唤醒 evdev->wait。
  11. 用户态的 read() 被唤醒，evdev_read 从环形缓冲取事件，input_event_to_user 拷到用户缓冲区。

第 1 步到第 6 步全在 dev->event_lock 自旋锁里，且在第 9 步之前都处在中断上下文。这个上下文约束决定了三件事：驱动上报时不能睡，不能 msleep，不能 mutex_lock；handler->event/events 也不能睡，evdev 里只能用 spin_lock；一帧的事件越少，锁持有时间越短——这就是 input_sync 存在的性能理由。

第 6 步有个兜底：如果 num_vals >= max_vals - 2，core 会强制补一个 input_value_sync = { EV_SYN, SYN_REPORT, 1 } 并 flush。所以漏调 input_sync 不会丢事件，只会把节奏搞乱。注意这个兜底的 sync 的 value 是 1 而不是 0——这是个隐藏信号，evdev 客户端看到 EV_SYN/SYN_REPORT/value=1，就该知道中间少了一次正常 sync、帧边界不对。绝大多数应用忽略它，所以漏 input_sync 的驱动能在生产里活很久不被发现。

事件链路上的三个计数点：

计数 位置 作用
handle->open input_register_handle 注册，input_open_device 递增 非 0 才收事件
dev->users input_open_device / input_close_device 第一个用户时调 dev->open()，最后一个时调 dev->close()
evdev->open evdev_open_device / evdev_close_device 同一设备多个 fd 时的去重

三层计数对应三层对象：handle 属于「设备↔handler 这一对」，dev->users 属于设备全局，evdev->open 属于 evdev 实例。一个 /dev/input/event2 被 open 两次，evdev->open 是 2，handle->open 是 1，dev->users 是 1。input_open_device 是「上层第一次打开」的那一道：

c
int input_open_device(struct input_handle *handle)
{
        struct input_dev *dev = handle->dev;
        int retval;

        retval = mutex_lock_interruptible(&dev->mutex);
        if (retval)
                return retval;

        if (dev->going_away) {
                retval = -ENODEV;
                goto out;
        }

        handle->open++;
        if (!dev->users++ && dev->open)
                retval = dev->open(dev);

        if (retval) {
                dev->users--;
                if (!--handle->open)
                        synchronize_rcu();
        }

 out:
        mutex_unlock(&dev->mutex);
        return retval;
}

!dev->users++ 决定了 dev->open() 只在第一个用户时调一次。按键驱动把 request_irq 塞进 dev->open 里，意义就是「没人用的时候别占中断」。失败回滚那段为什么要 synchronize_rcu？因为 input_pass_values 正在 RCU 读侧遍历 h_list 并检查 handle->open，刚把计数减到 0 得等所有在途读者退出，才能保证不会有人在下一拍读到「open 为 0 却已经被判定为收事件」的中间态。

input_close_device 是镜像的，最后一个用户时调 dev->close()。如果你在 dev->open 里 request_irq 而在 dev->close 里忘了 free_irq，一次 rmmod 之后中断还在，下一次 insmod 会 request_irq 失败（-EBUSY）。

十、/dev/input/eventX 与读取方式 #

设备节点长这样：主设备号全是 13，次设备号从 64 起连续排——13, 64 是 event0，13, 65 是 event1，依此到 13, 68 的 event4。权限 crw-rw---- root input：普通用户要读得进 input 组，这是 X、Wayland、libinput 能工作的前提。容器里跑图形应用读不到 /dev/input，多半是没加 --device 或没进组。

/sys/class/input/eventX 那侧是对应的符号链接，event2 -> ../../devices/.../input/input3/event2/，event0 -> .../input/input0/event0/。注意 input1 对应 event1 而 input3 对应 event2：inputN 是设备序号，eventN 是 evdev 的次设备号序号，两者只在设备按序接入时碰巧对齐。要看准对应关系，走 /sys/class/input/eventX 这条符号链接，别猜数字。

用户态读取分三条路：阻塞 read、O_NONBLOCK 加 poll/epoll、SIGIO 异步通知。evdev_read 覆盖了前两条：count < input_event_size() 返回 -EINVAL；!evdev->exist || client->revoked 返回 -ENODEV；非阻塞且 packet_head == tail 返回 -EAGAIN；count == 0 只检查错误不读数据；然后一个内层 while 按 input_event_size() 步长从 evdev_fetch_next_event 取事件、input_event_to_user 拷出去；没取到且是阻塞模式就 wait_event_interruptible(evdev->wait, ...) 睡下。骨架如下：

c
for (;;) {
        if (!evdev->exist || client->revoked)
                return -ENODEV;
        if (client->packet_head == client->tail && (file->f_flags & O_NONBLOCK))
                return -EAGAIN;
        if (count == 0)
                break;                  /* 只探测错误，不做 IO */
        while (read + input_event_size() <= count &&
               evdev_fetch_next_event(client, &event)) {
                if (input_event_to_user(buffer + read, &event))
                        return -EFAULT;
                read += input_event_size();
        }
        if (read)
                break;
        if (!(file->f_flags & O_NONBLOCK)) {
                error = wait_event_interruptible(evdev->wait,
                                client->packet_head != client->tail ||
                                !evdev->exist || client->revoked);
                if (error)
                        return error;
        }
}
return read;

四件事：count < sizeof(struct input_event) 直接 -EINVAL；非阻塞且没数据返回 -EAGAIN；packet_head != tail 才算有完整包（半包不给你）；阻塞模式在 evdev->wait 上睡，evdev_pass_values 里 wake_up_interruptible 唤醒。还有两个隐藏契约：count == 0 的语义是「只检查错误不读数据」，用于探测设备是否还在；input_event_to_user 失败返回 -EFAULT，但已经读出来的事件已经从环形缓冲里摘走了，用户态会丢这一批，所以传正确的缓冲区地址是必需条件，不能靠重试救。

evdev_poll 决定 epoll 行为：mask 默认 EPOLLOUT | EPOLLWRNORM（evdev->exist 且未 revoke 时），否则 EPOLLHUP | EPOLLERR；packet_head != tail 时再 |= EPOLLIN | EPOLLRDNORM。默认就绪可写，有完整包才可读。这是个容易踩的点：epoll 里监听 EPOLLOUT 的代码会一直忙等，因为 evdev 永远可写，只监听 EPOLLIN。设备拔掉时 mask 变成 EPOLLHUP | EPOLLERR，epoll_wait 立刻返回，用户态据此知道设备没了——这是热插拔的正确发现方式之一（另一个是 EV_SYN/SYN_DROPPED）。

evdev_open 给每个 fd 分配 client 并挂进 client_list，evdev_open_device 是往下打通到 dev->open 的那一跳：

c
static int evdev_open(struct inode *inode, struct file *file)
{
        struct evdev *evdev = container_of(inode->i_cdev, struct evdev, cdev);
        unsigned int bufsize = evdev_compute_buffer_size(evdev->handle.dev);
        unsigned int size = sizeof(struct evdev_client) +
                                        bufsize * sizeof(struct input_event);
        struct evdev_client *client;
        int error;

        client = kzalloc(size, GFP_KERNEL | __GFP_NOWARN);
        if (!client)
                client = vzalloc(size);
        if (!client)
                return -ENOMEM;

        client->bufsize = bufsize;
        spin_lock_init(&client->buffer_lock);
        client->evdev = evdev;
        evdev_attach_client(evdev, client);

        error = evdev_open_device(evdev);
        if (error)
                goto err_free_client;

        file->private_data = client;
        nonseekable_open(inode, file);

        return 0;

 err_free_client:
        evdev_detach_client(evdev, client);
        kvfree(client);
        return error;
}

static int evdev_open_device(struct evdev *evdev)
{
        int retval;

        retval = mutex_lock_interruptible(&evdev->mutex);
        if (retval)
                return retval;

        if (!evdev->exist)
                retval = -ENODEV;
        else if (!evdev->open++) {
                retval = input_open_device(&evdev->handle);
                if (retval)
                        evdev->open--;
        }

        mutex_unlock(&evdev->mutex);
        return retval;
}

container_of(inode->i_cdev, struct evdev, cdev) 从字符设备反推 evdev 实例，这是 cdev 内嵌在 evdev 里的标准用法。nonseekable_open 配合 no_llseek，两个一起才算完整声明。!evdev->open++ 保证同一设备打开多次只往 core 递一次，最终落到 input_open_device 的 !dev->users++。所以三层计数是「与」的关系：只有第一个 fd 才真正把中断打开。

ioctl 侧对调试最有用的是这几个：

ioctl 用途
EVIOCGVERSION 协议版本 EV_VERSION = 0x010001
EVIOCGID 取 struct input_id
EVIOCGNAME(len) / EVIOCGPHYS / EVIOCGUNIQ 取名字/物理路径/唯一码
EVIOCGBIT(ev, len) 取能力位图，ev=0 取事件类型位图
EVIOCGABS(abs) 取某个绝对轴的 struct input_absinfo
EVIOCGKEY(len) 取当前按键状态位图
EVIOCGMTSLOTS(len) 取所有槽位上某个 ABS_MT_* 的当前值
EVIOCGRAB 独占设备，参数非 0 抓、0 放
EVIOCREVOKE 让设备对本 fd 失效
EVIOCSCLOCKID 选时间戳时钟（real/mono/boot）
EVIOCGMASK / EVIOCSMASK 读写该 client 的事件掩码

EVIOCSCLOCKID 是 4.x 才有的（evdev_set_clk_type），[3.x] 没有，时间戳固定用 getnstimeofday 那一路。EVIOCGMASK/EVIOCSMASK 同样 4.x 引入，用于客户端侧过滤——evdev_pass_values 里 __evdev_is_filtered 就是靠它。EVIOCGRAB 是把双刃剑：抓住了，其他所有 client 一个事件都收不到，input_pass_values 直接走 grab 分支。Android 的 EVIOCREVOKE 就是靠「先 grab 再 revoke」把老进程踢开。EVIOCGBIT 的取法有个常见错误：len 要按「返回多少位图字节」算，不是「多少位」——EVIOCGBIT(0, KEY_CNT/8) 取事件类型位图，传小了内核返回 -EINVAL。

命令行上最直白的验证方式是 hexdump /dev/input/event0。每个事件 8 字节（32 位）或 16/24 字节（64 位含两个 8 字节时间戳加 4 字节 type/code/value），一行一组。input_event_to_user 是 32/64 位兼容层，input-compat.h 里做了 layout 换算，所以 32 位程序读 64 位内核不会读出乱码；它的换算方向是「内核的 struct input_event → 用户的 struct input_event」，传的缓冲区是用户态地址，所以内部要 copy_to_user，不能直接赋值。

/proc/bus/input/devices 是设备侧的窗口，input_devices_seq_show 打 I:/N:/P:/S:/U:/H:/B: 七类行。以一块电源按钮为例：I: Bus=0019 Vendor=0000 Product=0001 Version=0000、N: Name="Power Button"、P: Phys=LNXPWRBN/button/input0、S: Sysfs=/devices/LNXSYSTM:00/LNXPWRBN:00/input/input0、U: Uniq=、H: Handlers=kbd event0、B: PROP=0、B: EV=3、B: KEY=10000000000000 0。

逐行读：I: 是 struct input_id 四个字段（十六进制），N: 是 dev->name 带引号，P: 是 dev->phys 系统层次里的物理路径，S: 是 dev->dev 的 sysfs 路径，U: 是 dev->uniq 唯一识别码（蓝牙设备的 MAC 之类），H: 是 dev->h_list 上所有 handle 的名字，B: 是位图（PROP/EV/KEY/REL/ABS/MSC/LED/SND/FF/SW 每类一行）。

H: Handlers=kbd event0 这一行就是 dev->h_list 上所有 handle 的名字，一个设备被几个 handler 接住一目了然。B: EV=3 表示 EV_SYN | EV_KEY，3 = 0b11。B: KEY=10000000000000 0 是按 long 粒度打印的位图：64 位机上每个 long 打 16 个十六进制字符，最右边是最低位；第一个 10000000000000 有一个 bit 置位，后面那个 0 是第二个 long（全 0）。这一段按位解析需要写脚本，肉眼看不出名堂。

十一、易错点速查 #

按「一句话 + 后果」排，只收框架层的错，设备层的（GPIO、ADC、去抖、校准）在对篇：

易错点 后果
用了 set_bit(EV_ABS, evbit) 没调 input_set_abs_params 注册返回 -EINVAL，dmesg 报 Absolute device without dev->absinfo
调 input_report_* 后忘记 input_sync 事件卡在 dev->vals 里，攒满才吐，用户态卡顿
注册后还调 input_free_device refcount 下溢 / double free；注册后只能 input_unregister_device
注册前用 input_unregister_device 攻击未初始化的 handle 链，崩
input_set_capability 只调一次就想支持多个键 一次只能设一个 code，要逐个调
EV_KEY 报 value 3 想发自动重复 input_report_key 里 !!value 压成 1；重复值 2 只能 input_event 直发
设了 EV_KEY 位但没设 keybit 对应位 事件被 input_get_disposition 静默丢弃
设了 keybit 但 evbit 没 EV_KEY 注册时 input_cleanse_bitmasks 把 keybit 整块清零

write 到 evdev 想伪造上报事件 只能塞 EV_LED/EV_FF 这类下发类事件，EV_KEY 会被 disposition 反复处理，行为不可预期

补两条跟框架强相关的：

input_dev 的位图在 input_register_device 之后改，用户态看到的是旧值。EVIOCGBIT 在 open 时读一次缓存，注册后再 input_set_capability 加的能力，用户态拿不到。所以能力位必须在注册前全部配置完。

input_register_device 失败后不要再 input_unregister_device。失败路径里 device_add 已经走过、vals 已经释放，再走注销会访问已释放的 vals。正确做法是失败时只 input_free_device。
