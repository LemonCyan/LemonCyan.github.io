一、Linux 图形栈全景：从 GUI 到硬件 #

图形子系统的本职是提供图形化的人机交互界面。往下它要管住形态各异、性能各异的显示器件，往上它要给应用程序一套能用的 GUI 接口。所以它是内核里少有的、跟最终用户直接打交道的子系统之一。

1.1 一次人机交互的完整回路 #

以 VR 游戏这个最吃带宽的场景为例：

text
人脑（动作/声音）→ 键盘/鼠标/手柄/麦克风（输入设备）
  → kernel Input subsystem → 手势/语音中间件 → 应用程序
    ├─ 3D rendering：OpenGL / OpenGL|ES + 用户态驱动
    └─ 输出：kernel Video subsystem（DRM/KMS）、ALSA → 显示器 / 扬声器 / 力反馈

原稿算过一笔账：1280×800@95fps 的 VR 场景，要求 10.5ms 内生成并输出一帧；按 RGBA 算，每秒要搬 1280×800×95×4×8 ≈ 3.11Gb。换到 1080p 只会更紧。

1.2 窗口系统与 display server #

窗口系统是 GUI 的一种实现形态，用 WIMP（windows、icons、menus、pointer）跟人交互。Linux 上的实现有 X Window System、Wayland、Android SurfaceFlinger，形态不同，骨架一致：

  • client-server 架构。server 叫 display server，也叫 window server、compositor，它管住所有输入设备和输出显示设备；
  • 应用是 server 的 client，在自己的窗口里画自己的界面；
  • client 的绘图请求全部提交给 server，server 按规则混合叠加，最终落在有限的屏幕上；
  • 两端靠 display server protocol 通信。协议可以做成网络透明的，X 就是典型，server 和 client 能分处两台机器。

1.3 X 的自我定位 #

X 由 MIT 在 1984 年发布，1987 年演进到第 11 版，此后所有 X 都基于 X11 发展。名字里的 X 是因为它排在 W 之后，而 W 是 MIT 在 X 之前用的 GUI 系统。

维护者换过几轮：最早由 X.Org 维护，后来基于 X11R6 分出专给 Intel x86 PC 用的 XFree86，XFree86 一度成了 X 的代名词。2004 年 XFree86 不再遵从 GPL 发行，发行版集体转向 X.Org，现在 X.Org 才是 X 的代名词。

X 设计之初立过一条规矩：It is as important to decide what a system is not as to decide what it is。翻译成人话：X 只提供实现 GUI 环境的基本框架——定义 protocol、在显示设备上画点线面这类基本图形单元、跟键鼠交互。button、menu、window title-bar style 一概不管，交给第三方。Unix 的「提供机制，而非策略」在这里体现得最彻底：好处是 X 几十年保持稳定，代价是桌面环境五花八门、体验不统一。

架构上 X 分 X server 和 X client，两者走 X protocol。X server 常驻为 daemon，收 client 的绘图请求输出到屏幕，同时把输入事件转回给对应 client。protocol 被封装成命令原语，以 xlib 或 xcb 的形式给 client 用；2D 请求走这些 API，3D 走 GLX 扩展。远端登录时角色会反过来：管理输入输出设备的是 user computer，所以它当 server，远端跑 client。

1.5 渲染与 OpenGL #

渲染指用软件从模型生成图像，模型是对三维物体的严格描述，含几何、视点、纹理、照明信息。GUI 里常见的点、线、矩形绘制同样属于渲染，只是 2D 渲染，算力压力远小于 3D，所以不加限定时「渲染」默认指 3D。

2D 渲染一般由 CPU 完成，也可以交给专用硬件。3D 渲染让 CPU 硬扛会崩，主流平台都上 GPU。用特定功能的硬件模块替 CPU 干它不擅长的活，这叫硬件加速。硬件五花八门，应用层就需要一个稳定的、跨平台的 API 来定义渲染行为，OpenGL 是其中最被广泛接受的一种。它归根到底只做两件事：对上屏蔽硬件细节，给应用一个平台无关的 3D（也可 2D）图像处理 API；对下指引硬件相关驱动，实现 3D 图像处理功能。它还独立于操作系统和窗口系统存在。

二、DRI 框架：为什么需要它 #

2.1 一个应用要显示，只有两步 #

  • 把 UI 画出来，以某种格式存进 buffer。这一步叫 Rendering，形态有四种：2D 点线面绘图（比如用 for 循环生成一个 640×480、RGB888、纯红的矩形）、3D 渲染、图片与视频解码、字体渲染（从字库里抽字形）；
  • 把 buffer 里的数据放到显示设备上。这一步叫送显。

问题出在「谁来干这两步」。

2.2 应用不该直接碰硬件 #

操作系统有一条底线：应用不直接访问硬件，路径是 Application <-> Service <-> Driver <-> Hardware。理由两条：安全，以及硬件资源共享（屏幕只有一个，想显示的进程有一堆）。

X server + 3D 出现后这条底线被顶开了。基于 OpenGL 的 3D 程序要渲染，得通过 X server 的 GLX 扩展请它代劳；X server 再走用户态驱动、过内核、摸到 GPU。普通 2D 绘图、字体渲染也一律先请求 X server。这套完全符合「应用不碰硬件」，但游戏厂商和图形硬件厂商不认：高性能图形设备必须让应用直接访问硬件，性能才上得去。

两边都有理，妥协的结果是给 3D 渲染另起一套直连硬件的路径，DRI 就是这么来的。送显这一步没让步，仍由 display server 统一处理——屏幕资源有限，多应用的界面要靠 server 统一管理、叠加，这个叠加过程叫合成（Compositor）。

2.2.1 DRI 之后设备权限模型跟着变了 #

DRI 这条直连路径不是画个箭头就完了，它逼着内核引入一套新的设备权限模型。老的 2D 路径下应用只有一条路——跟 X server 说话，X server 是唯一需要权限的进程；DRI 之后应用自己握着文件描述符跟内核 DRM 驱动打交道，于是出现了三个新问题：

  • 谁能打开 /dev/dri/card0？答案是不受限制，因为是 udev 按 class 给的 crw-rw---- root video，问题变成「谁在 video 组里」；
  • 打开之后谁说了算？答案是拿到 master 的那个。这一步由 drm_master_open() 在 open 时做，先到先得，后面的进程只能当普通客户端——它不能改显示模式，但可以提交渲染任务；
  • 渲染任务和显示控制怎么分离？答案是拆节点。card0 留给需要 KMS 的进程，renderD128 只做渲染、不碰显示，多进程共享不需要 master，也不需要 video 组的特权。

这套模型是 DRI 的必然产物，不是设计之初就规划好的，它在十几年的演进里才补齐。第一次接触 DRM 时最容易混的正是这里：以为「打开 card0 就能画东西」，实际能画东西但改不了模式；以为 render 节点也能 modetest -s，实际连 -s 要的 master 权限都拿不到。

2.3 DRI 是什么 #

DRI 因 3D 而生，意义不止 3D。它背后是一次设计思路的整体转向：

旧思路 DRI 之后的思路
中心 X server 是宇宙中心，所有接口都要跟它对话 Linux kernel 及其组件是中心
X server 地位 不可绕过 只是角落里的一员，可有可无
渲染路径 应用 → X server → 驱动 → 硬件 应用 → Mesa → libdrm → DRM → GPU
送显路径 X server 统一处理 compositor → KMS

转向后用两条独立路径分别覆盖渲染和送显：DRM 管渲染，KMS 管送显。

2.4 How：从应用到屏幕的四步 #

  • 应用（比如 3D 游戏）要重绘，通过 OpenGL|ES、EGL 把一批绘图请求交给 GPU。这些接口的实现有多种，以 Mesa 3D 为例，所有 3D 渲染请求都过它，它按实际情况选硬件或软件方式响应；
  • 系统有基于 DRI 的硬件渲染机制时，Mesa 3D 走 libGL-mesa-DRI，调用 DRI 提供的渲染功能；
  • libGL-mesa-DRI 调 libdrm，libdrm 通过 ioctl 打到内核态的 DRI 驱动，也就是 DRM（Direct Rendering Module）；
  • 内核 DRM 模块通过 GPU 完成渲染，结果以 image buffer 形式返回给应用。

应用拿到画好的 buffer（不止一个），交给 Wayland compositor。compositor 收齐各应用的 buffer，算好屏幕坐标和叠加方式，直接 ioctl 给 kernel KMS，KMS 控制显示控制器把图像送出去。

2.5 DRM 与 KMS 的分工 #

DRM 是 DRI 框架在内核里的实现，管 GPU（显卡）和对应的 graphics memory，两个职能：

  • 统一管理和调度多个应用发往显卡的命令请求，可以类比进程管理对 CPU 资源做的那件事；
  • 统一管理显示相关的 memory。可以在 GPU 专用显存里，也可以从 system RAM 里划，嵌入式多用后者。这块由 GEM（Graphics Execution Manager）实现，具体做四件事：允许用户态创建、管理、销毁 video memory 对象（GEM object，以 handle 为句柄）；允许不同进程共享同一个 GEM object，做法是把不唯一的 handle 转成每个 driver 唯一的 GEM name，后续则用 dma-buf；处理 CPU 与 GPU 之间的内存一致性；video memory 都在内核里管着，方便交给 display controller 送显——应用只要把句柄经 compositor 递给内核，内核自己去拿内存和内容。

KMS 是 Kernel Mode Setting，也叫 Atomic KMS，做的事听上去很简单：设置显示模式，含分辨率、色深、刷新率，手段是控制 display controller。它跟 DRI 的逻辑关系其实不大，KMS 的代码落在 DRM 里纯属历史原因。4.2 之后的版本里，两者除了共用目录、共用设备节点提供 ioctl 之外，基本没有逻辑耦合，可以当独立模块看。

三、从 fbdev 到 DRM：两代显示框架 #

内核里并行着两套图形显示设备驱动框架：FB 设备（Framebuffer）与 DRM。Framebuffer 驱动的特征是：直接控制显卡的帧缓冲区，提供最基本的显卡输出能力；用一组内核数据结构和 API 管图形界面，并向上暴露接口给用户态；实现相对简单，适合嵌入式系统或不需要高性能图形的场景。

维度 fbdev DRM
抽象层次 一块帧缓冲，一个平面 完整显示流水线：crtc/encoder/connector/plane/framebuffer
多应用并发 不擅长，主流做法是独占 支持多应用同时访问，用 master 机制仲裁
显示参数设置 基本不管 KMS 专职，含分辨率、刷新率、电源状态
硬件加速 / 3D 无 有，GEM + 渲染节点
多显示器 / 多 GPU 弱 支持
显存管理 由驱动自理 GEM / TTM 统一抽象，PRIME 跨设备共享
热插拔 无统一机制 HPD 事件 + connector 轮询
典型场景 简单嵌入式屏、启动早期输出 PC、移动、机顶盒，几乎所有现代平台

一句话：DRM 更适应现在这批显示硬件。fbdev 退出主舞台，但没有被扔掉——它以 fbdev emulation 的形式并入了 DRM，供部分嵌入式设备（以及启动早期的控制台）使用。

实际系统里两套是叠着的。DRM 驱动的 probe 末尾调用 drm_fbdev_generic_setup() 建一层兼容层，于是你会同时看到 /dev/fb0 和 /dev/dri/card0：fbcon 走前者，图形栈走后者。debugfs 的 framebuffer 输出里同时挂着 [fbcon] 和 Xorg 分配的 fb，就是这个原因。

四、DRM 子系统的整体架构 #

4.1 四层结构 #

text
应用程序 --ioctl(DRM_IOCTL_*)--> libdrm --ioctl 封装--> DRM core
                                                          ├─ KMS：更新画面 + 设置显示参数
                                                          └─ GEM：显存管理
                        DRM core --> DRM driver（如 drivers/gpu/drm/rockchip/）--> HW

应用程序可以直接操 DRM 的 ioctl，后来这些调用被封装进 libdrm；libdrm 是 DRM 框架提供的用户态库，本质是对各种 ioctl 的封装；DRM core 是核心层，由 GEM 和 KMS 组成；DRM driver 是具体硬件的驱动，填 core 留出来的坑；最后一层是硬件。

4.2 KMS 干什么 #

KMS 拆开只有两件事：更新画面（显示 buffer 的切换、多图层的合成方式、每个图层的显示位置）、设置显示参数（分辨率、刷新率、电源状态即休眠唤醒）。对应到 DRM 的抽象，就是 CRTC、ENCODER、CONNECTOR、PLANE、Framebuffer、VBLANK、Property。

以 HDMI 输出为例对号入座：SoC 内部的 Display 模块 → CRTC；HDMI 接口 → Connector；显存 → Framebuffer；描述 Framebuffer 的图层 → Plane；把像素转成 HDMI 所需信号的模块 → Encoder（Encoder 和 Connector 一般在同一处初始化）。

4.3 GEM 干什么 #

GEM 管显示 buffer 的分配和释放，对应的抽象是 DUMB、PRIME、fence。DRM 里其实有两个内存管理器：TTM 和 GEM。TTM 是先做出来的那个，GEM 是后来更通用、更轻量的方案。RK3399 这条线走 GEM（具体是 CMA helper 路线），TTM 不展开。

4.5 硬件抽象落到对象上的难点 #

初学者卡住的地方往往不是对象概念本身，而是对象跟硬件的对应关系。不是所有 Display 硬件都能规规矩矩映射到 plane/crtc/encoder/connector 上。拿三种常见屏幕接口看：

接口 数据线 控制线 屏是否需要 GRAM 对象映射特点
MIPI DSI DSI 差分，1~4 lane DSI 命令通道 否 crtc → DSI 控制器（encoder）→ panel（connector）
MIPI DPI（即 RGB 并行） RGB 并行总线 SPI / I2C 否 crtc → RGB 接口 → panel（connector）
MIPI DBI（MCU / SPI 屏） SPI 或 I80 与数据同一条总线 是，必须内置 走精简路径，plane 与 crtc 大幅合并

MIPI 联盟 2003 年由 ARM、Nokia、ST、TI 等成立，目的是把手机内部接口标准化，降低设计复杂度、增加灵活性。旗下工作组分别定义了 CSI（摄像头）、DSI（显示）、DigRF（射频）、SLIMbus（麦克风/喇叭）等标准。

第三种（DBI）在 kernel 4.19 里走 tinydrm 架构，参考驱动 drivers/gpu/drm/tinydrm/ili9341.c。这套路径在后续内核里被重新整理成 drm_mipi_dbi，6.3 的目录里已经没有 tinydrm/ 了，只有 drm_mipi_dbi.c。素材里的路径是 4.19 的，照抄到 6.3 编译不起来。前两种的 panel 驱动可参考 panel-ilitek-ili9881c.c（DSI）和 panel-sitronix-st7789v.c（DPI），都在 drivers/gpu/drm/panel/。

五、DRM 设备节点与 ioctl #

5.1 主设备号与 stub 字符设备 #

DRM 的模块入口是 drm_core_init，在 drivers/gpu/drm/drm_drv.c：

c
static int __init drm_core_init(void)
{
        int ret;

        drm_connector_ida_init();
        idr_init(&drm_minors_idr);          /* minor 编号表 */
        drm_memcpy_init_early();

        ret = drm_sysfs_init();             /* 建 drm_class → /sys/class/drm */
        if (ret < 0) {
                DRM_ERROR("Cannot create DRM class: %d\n", ret);
                goto error;
        }

        drm_debugfs_root = debugfs_create_dir("dri", NULL);   /* /sys/kernel/debug/dri */

        /* 主设备号 226，一次注册 256 个次设备，ops 全绑 drm_stub_fops */
        ret = register_chrdev(DRM_MAJOR, "drm", &drm_stub_fops);
        if (ret < 0)
                goto error;
        ret = accel_core_init();
        if (ret < 0)
                goto error;

        drm_privacy_screen_lookup_init();
        drm_core_init_complete = true;
        DRM_DEBUG("Initialized\n");
        return 0;
error:
        drm_core_exit();
        return ret;
}
module_init(drm_core_init);

三件事：建 drm_class（落点 /sys/class/drm）、在 /sys/kernel/debug 下建 dri 目录、申请主设备号 DRM_MAJOR（值 226）并一次注册 256 个字符设备。drm_sysfs_init 建 class 并指定节点命名回调 drm_class->devnode = drm_devnode；drm_devnode 返回 kasprintf(GFP_KERNEL, "dri/%s", dev_name(dev))，udev 据此在 /dev/dri/ 下建节点。所以 /dev/dri/card0 的 crw-rw---- root video 不是驱动设的，是 udev 按 class 规则设的。

5.2 stub open：一次转接 #

c
static int drm_stub_open(struct inode *inode, struct file *filp)
{
        const struct file_operations *new_fops;
        struct drm_minor *minor;
        int err;

        minor = drm_minor_acquire(iminor(inode));    /* 按节点拿 minor */
        if (IS_ERR(minor))
                return PTR_ERR(minor);

        new_fops = fops_get(minor->dev->driver->fops);
        if (!new_fops) {
                err = -ENODEV;
                goto out;
        }

        replace_fops(filp, new_fops);                /* filp->f_op 换成驱动的 */
        if (filp->f_op->open)
                err = filp->f_op->open(inode, filp);
        else
                err = 0;
out:
        drm_minor_release(minor);
        return err;
}

core 占住主设备号，具体操作集由每个驱动通过 drm_driver.fops 提供；stub 只是接住 open 再换手，此后 read/write/ioctl/mmap 全走驱动的 fops。

5.3 三种 minor #

drm_device 的 primary、render、accel 都是 struct drm_minor，core 按 driver_features 决定给哪几个注册字符设备。

enum drm_minor_type {
        DRM_MINOR_PRIMARY,
        DRM_MINOR_CONTROL,
        DRM_MINOR_RENDER,
        DRM_MINOR_ACCEL = 32,
};

struct drm_minor {
        int index;                      /* 次设备号 */
        int type;                       /* Control / render / accel */
        struct device *kdev;            /* 设备模型里的 device */
        struct drm_device *dev;
        struct dentry *debugfs_root;
        struct list_head debugfs_list;  /* 存 drm_debugfs_entry */
        struct mutex debugfs_lock;      /* 保护 debugfs_list */

minor 类型 节点名 次设备号区间 典型用途 创建条件
PRIMARY /dev/dri/card0 0~63 显示控制 + 渲染，KMS 只认这个 总是创建
CONTROL 无独立节点 — 历史上用于渲染控制（DRI1 遗留） 6.3 已不再注册，见下
RENDER /dev/dri/renderD128 128~191 纯渲染，不碰 KMS，多进程共享无需 master DRIVER_RENDER
ACCEL /dev/dri/accel0 由 accel_minor_alloc 自己管 纯计算加速 DRIVER_COMPUTE_ACCEL

DRM_MINOR_ACCEL = 32 是给未来留空间，32 之前的编号都留给 minor。素材把 RENDER 的区间写成「64×type ~ 64×(type+1)」，按 DRM_MINOR_RENDER = 2 算出来是 128~129；实际区间是 128~191，到 192 才归 accel。idr_alloc 的结束参数排他，代码不错，是文字描述写窄了。DRM_MINOR_CONTROL 在 6.3 的 enum 里还留着，但已没有代码用它注册节点，合入时间点未验证。

5.4 ioctl 走哪 #

应用打开 /dev/dri/card0 后所有请求走 drm_ioctl，分两路：core 实现的通用 ioctl（DRM_IOCTL_MODE_*、DRM_IOCTL_GEM_* 一类）由 core 直接处理；驱动私有 ioctl 查 drm_driver.ioctls 数组（struct drm_ioctl_desc），匹配到再调对应 handler。KMS 与 GEM 共用同一个节点，靠的就是这一点：按 ioctl 号分流，不按节点分。

六、DRM 的四类对象总览 #

6.1 一句话关系 #

原话说得最准：plane 是连接 framebuffer 和 crtc 的纽带，encoder 是连接 crtc 和 connector 的纽带。跟物理 buffer 直接打交道的是 gem，不是 framebuffer。

text
drm_gem_object      缓冲区的真实载体，GEM 管分配释放
  └─ drm_framebuffer    描述显存布局：format / pitch / size / modifier
       └─ drm_plane         一个图层：源窗口、目标窗口、格式、缩放、alpha、zpos
            └─ drm_crtc         一路显示时序：分辨率、刷新率、扫描输出
                 └─ drm_encoder     把内部并行像素信号转成接口需要的信号
                      └─ drm_connector  对外物理接口：读 EDID、探 HPD、下发 DPMS
                           └─ 真实显示器

6.2 四类对象对照 #

对象 抽象什么 关键职责 RK3399 上的实例 核心回调结构
crtc 一路显示时序 + 扫描输出 产生时序信号、把 framebuffer 搬到输出、上报 vblank VOP_BIG、VOP_LIT 各一个 drm_crtc_funcs + drm_crtc_helper_funcs
plane 一个硬件图层 把 framebuffer 的某窗口缩放/贴到 crtc 的某位置 每个 VOP 4 个 win（1 primary + 1 cursor + 2 overlay） drm_plane_funcs + drm_plane_helper_funcs
encoder 信号格式转换 把 crtc 输出转成 HDMI/DP/DSI 等接口信号，附带休眠唤醒通知 dw-hdmi、analogix-dp、dw-mipi-dsi 各自的 encoder drm_encoder_funcs + drm_encoder_helper_funcs
connector 对外物理接口 读 EDID、探 HPD、决定可用 mode 列表、下发 DPMS HDMI-A-1、eDP-1、DP-1、DSI-1 drm_connector_funcs + drm_connector_helper_funcs

几条直白的理解：buffer 是硬件存储，由 GEM 分配释放；framebuffer 描述这块显存的信息（format、pitch、size）；plane 描述图层信息，同一个 crtc 可以由多个 plane 组成；crtc 控制显卡输出图像信号；encoder 把 crtc 的输出转成一定格式的数字信号（HDMI、DP、MIPI）；connector 把 encoder 输出传给显示器并建立连接。

要点：上表里某些对象即使没有实际硬件与之对应，软件驱动里也照样得建出来，否则 DRM 子系统跑不起来。典型例子是没有独立 encoder 硬件的接口，驱动里要挂一个只有样板实现的 encoder。

6.3 drm_panel：为了解耦 #

encoder 和 connector 常常分属两个驱动，于是必然产生耦合：connector 的主要作用是拿显示参数，所以它往往在 LCD/panel 驱动里构造，可初始化时要 attach 一个长在别的硬件驱动里的 encoder；encoder 除了转换信号还负责通知显示设备休眠唤醒，通知 LCD 驱动执行 enable/disable 时必然要调它导出的全局函数。

DRM 给的解法是 drm_panel，把这个结构体做成 connector 与 encoder 访问 LCD 的常用接口集合，原来的「encoder 驱动 ↔ LCD 驱动」耦合就变成「encoder 驱动 ↔ drm_panel」和「drm_panel ↔ LCD 驱动」两段。它不属于 objects 的范畴，只是一堆回调的集合，作用只有一个：降低 LCD 驱动与 encoder 驱动之间的耦合度。

6.4 公共基类 drm_mode_object #

plane、crtc、encoder、connector 共用一个基类 struct drm_mode_object（include/drm/drm_mode_object.h），作为成员嵌在这四个结构体里。

c
struct drm_mode_object {
        uint32_t id;                            /* 用户可见唯一标识，idr 分配 */
        uint32_t type;                          /* DRM_MODE_OBJECT_* 之一 */
        struct drm_object_properties *properties; /* 挂在本对象上的属性 */
        struct kref refcount;                   /* 动态生命周期对象的引用计数 */
        void (*free_cb)(struct kref *kref);     /* 释放回调，仅动态对象设置 */
};

它提供两个服务（注释原文要点）：跟踪挂在对象上的属性及其值，供 drm_crtc、drm_plane、drm_connector 使用，属性须在对象对用户可见之前调 drm_object_attach_property() 挂上；对动态生命周期的对象（free_cb 非空），通过 drm_mode_object_get() / drm_mode_object_put() 提供引用计数，用于 drm_framebuffer、drm_connector、drm_property_blob。有了它，drm_mode_object_find() 就能按 id + type 查任意 modeset 对象。

refcount 的规则很标准：对象创建时计为 1，每多一个引用加 1，每释放一个减 1，归零内核自动释放。这样保证不会留下没人用又回收不掉的对象。

type 的取值在 include/uapi/drm/drm_mode.h：

c
#define DRM_MODE_OBJECT_CRTC 0xcccccccc
#define DRM_MODE_OBJECT_CONNECTOR 0xc0c0c0c0
#define DRM_MODE_OBJECT_ENCODER 0xe0e0e0e0
#define DRM_MODE_OBJECT_MODE 0xdededede
#define DRM_MODE_OBJECT_PROPERTY 0xb0b0b0b0
#define DRM_MODE_OBJECT_FB 0xfbfbfbfb
#define DRM_MODE_OBJECT_BLOB 0xbbbbbbbb
#define DRM_MODE_OBJECT_PLANE 0xeeeeeeee
#define DRM_MODE_OBJECT_ANY 0

这些魔数不是随便挑的，每个都呈「字节重复」形态（0xcc、0xc0、0xfb……），在内存 dump 里一眼能认出来。

属性相关的两个结构体：

c
struct drm_object_properties {
        int count;                                              /* ≤ 24 */
        struct drm_property *properties[DRM_OBJECT_MAX_PROPERTY];
        uint64_t values[DRM_OBJECT_MAX_PROPERTY];
};

struct drm_property {
        struct list_head head;              /* 每设备属性链表，用于清理 */
        struct drm_mode_object base;
        uint32_t flags;                     /* 类型 + 标志，见下表 */
        char name[DRM_PROP_NAME_LEN];
        uint32_t num_values;
        uint64_t *values;                   /* 取值范围/取值，解释方式由 flags 决定 */
        struct drm_device *dev;
        struct list_head enum_list;         /* enum / bitmask 的名字列表 */
};

count 的上限 DRM_OBJECT_MAX_PROPERTY 值为 24。values[] 那条注释值得抄下来：atomic 驱动不把可变属性存这个数组，只存解码后的值在对应的 state 结构里——crtc 用 drm_crtc_funcs.atomic_get_property/atomic_set_property，plane 用 drm_plane_funcs 的同名钩子，connector 用 drm_connector_funcs 的同名钩子。所以 atomic 驱动不该对可变属性（即没打 DRM_MODE_PROP_IMMUTABLE 标记的那些）调 drm_object_property_set_value() / drm_object_property_get_value()，那个数组对它们只用来存默认值。

flags 必须是下列类型之一：

类型 含义 创建函数
DRM_MODE_PROP_RANGE 无符号范围，core 校验取值落在区间内 drm_property_create_range()
DRM_MODE_PROP_SIGNED_RANGE 有符号范围 drm_property_create_signed_range()
DRM_MODE_PROP_ENUM 枚举，0 到 N-1，每值配一个自由字符串名 drm_property_create_enum()
DRM_MODE_PROP_BITMASK 位掩码，枚举值额外限制在 0~63 drm_property_create_bitmask()
DRM_MODE_PROP_OBJECT 对象引用，用来串起显示流水线 drm_property_create_object()
DRM_MODE_PROP_BLOB 二进制 blob，无格式限制 drm_property_create() 传 BLOB

可叠加的标志：DRM_MODE_PROP_ATOMIC（编码 atomic 状态，不暴露给 legacy 用户态）、DRM_MODE_PROP_IMMUTABLE（用户态不能改，只有内核能更新，用于把 EDID、DP MST path 这类探测结果吐给用户态）。OBJECT 那条是 atomic 流水线的关键：framebuffer 挂到 plane、plane 挂到 crtc、connector 挂到 crtc 全靠它，它只能指向特定类型的 mode object，这条限制由 core 兜住。

DRIVER_ATOMIC 支持完整 atomic 用户态 API；只内部用 atomic 的不要置
DRIVER_SYNCOBJ / DRIVER_SYNCOBJ_TIMELINE 支持 drm_syncobj 显式同步 / 其 timeline 变体
DRIVER_COMPUTE_ACCEL 支持计算加速设备；与 DRIVER_RENDER、DRIVER_MODESET 互斥
DRIVER_USE_AGP / DRIVER_PCI_DMA / DRIVER_SG / DRIVER_HAVE_DMA / DRIVER_HAVE_IRQ / DRIVER_LEGACY 旧世界的东西，新驱动一律不碰

DRIVER_COMPUTE_ACCEL 与图形驱动互斥这条在 drm_dev_init() 里有硬检查，同时置位直接 -EINVAL 退出。既做图形又做计算加速的设备，得拆成两个驱动，用 auxiliary bus 连起来。

dumb_create 值得单说。dumb buffer 指所有绘图操作都由 CPU 完成的 framebuffer，参数里给了 width、height、bpp，回调要回填 handle、pitch、size。它做三件事：建 GEM object、建 GEM handle、分配物理内存（可选）。前两步所有实现都必须做，第三步看情况——需要一次性映射的场景要提前把物理内存分配好，分配完成后就能用 mmap 映射到用户空间。

6.8 驱动私有 ioctl 的描述表 #

前面 5.4 提到驱动私有 ioctl 查 drm_driver.ioctls 数组。这张表就是 struct drm_ioctl_desc 的数组，每一项描述一个 ioctl 号、它的处理函数和权限标志：

c
struct drm_ioctl_desc {
        unsigned int cmd;
        int flags;
        drm_ioctl_t *func;
        const char *name;
};

#define DRM_IOCTL_DEF_DRV(ioctl, _func, _flags)                         \
        [DRM_##ioctl] = {                                               \
                .cmd = DRM_IOCTL_##ioctl,                               \
                .func = _func,                                          \
                .flags = _flags,                                        \
                .name = #ioctl                                          \
        }

数组的下标是 DRM_COMMAND_BASE 之后相对编号，所以驱动私有的命令号从 DRM_COMMAND_BASE + 0 起排。flags 里最常用的三个：DRM_AUTH 要求客户端已认证，DRM_MASTER 要求调用者是当前 master，DRM_RENDER_ALLOW 表示这个 ioctl 在 render 节点上也放行——没置这个位的命令只能从 card0 走。drm_ioctl 查到条目后会逐项检查，不满足就返回 -EACCES，认定失败返回 -EINVAL。

拿 KMS 之外的路径说一遍完整分流：应用发 DRM_IOCTL_GEM_CLOSE，它落在 core 的 drm_ioctl_desc 表里，drm_ioctl 走 drm_gem_close_ioctl；应用发厂商私有的性能计数命令，drm_ioctl 先用 drm_ioctl_permit() 做权限判断，再查 dev->driver->ioctls，命中就调这一项 func，没命中返回 -EINVAL 并打一行 no ioctl 日志。日志级别是 DRM_DEBUG，默认看不到，排查「某个 ioctl 报 EINVAL」时要把 drm.debug 打开。

七、mode setting 与 atomic 提交 #

7.1 从「设个分辨率」到「一次提交」 #

legacy 的 KMS 接口是零碎的：设 crtc、设 encoder、设 connector，一步一步来，中间任何一步失败都会留下半截状态。atomic 把这套改成「攒一个完整状态 → 一次性校验 → 一次性提交」。drm_mode_config_funcs 是这条路的中枢：

c
struct drm_mode_config_funcs {
        struct drm_framebuffer *(*fb_create)(struct drm_device *dev,
                                             struct drm_file *file_priv,
                                             const struct drm_mode_fb_cmd2 *mode_cmd);
        const struct drm_format_info *(*get_format_info)(const struct drm_mode_fb_cmd2 *mode_cmd);
        void (*output_poll_changed)(struct drm_device *dev);   /* 已废弃 */
        enum drm_mode_status (*mode_valid)(struct drm_device *dev,
                                           const struct drm_display_mode *mode);
        int (*atomic_check)(struct drm_device *dev, struct drm_atomic_state *state);
        int (*atomic_commit)(struct drm_device *dev, struct drm_atomic_state *state,
                             bool nonblock);
        /* 以下三个用于子类化 drm_atomic_state，已废弃，改用 drm_private_state */
        struct drm_atomic_state *(*atomic_state_alloc)(struct drm_device *dev);
        void (*atomic_state_clear)(struct drm_atomic_state *state);
        void (*atomic_state_free)(struct drm_atomic_state *state);
};

三个最常打交道的：fb_create 按给定参数建 framebuffer object 并返回句柄，注意它不分配内存，内存归 GEM 管，framebuffer 只描述显存布局；get_format_info 取格式信息，返回 struct drm_format_info；atomic_check / atomic_commit 是 atomic 提交的两道闸门。

7.2 一次 modeset 里四类对象各自被改了什么 #

atomic 提交的输入是一批「对象 + 该对象的新状态」的配对。四类对象各有自己的 state 结构，名字都是 drm_<对象>_state，它们共同包在 drm_atomic_state 里。理解提交行为，先得知道谁改了谁的什么字段：

对象 state 结构 modeset 时被改的关键字段
crtc struct drm_crtc_state mode、enable、active、adjusted_mode、mode_changed、connectors_changed、color_mgmt_changed、event
plane struct drm_plane_state fb、crtc、src_*、dst_*、rotation、alpha、zpos、visible、fence
connector struct drm_connector_state crtc、best_encoder、link_status、content_protection
私有 struct drm_private_state 驱动自己定义的全局资源状态，比如整颗 SoC 的 PLL 分配表

drm_crtc_state 里那几个 *_changed 布尔量是提交路径的分叉开关，它们跟 drm_atomic_crtc_needs_modeset() 的关系是：

c
static inline bool
drm_atomic_crtc_needs_modeset(const struct drm_crtc_state *state)
{
        return state->mode_changed || state->active_changed ||
               state->connectors_changed;
}

换成直白的话：只要模式换了、crtc 从灭到亮或从亮到灭、或者挂在这个 crtc 上的 connector 集合变了，就得整套 modeset；只换 framebuffer（page flip）不碰这三个位，走快速路径。驱动的 atomic_check 要负责把这三个位填对，填错的结果是 core 用错路径：该全套重配的只翻了页，屏幕花；不该全套重配的走了全套，中间黑一下。

planes 那一侧还有一条容易忽略的约束：drm_plane_state.fb 为 NULL 表示这个 plane 要关掉，此时 crtc 也必须为 NULL。core 在 drm_atomic_plane_check() 里做这条校验，违反了返回 -EINVAL。同理 visible 为假时 dst_* 的宽高必须为 0。

drm_atomic_state 本身是引用计数对象，drm_atomic_state_get() / put() 管生命周期。它内部维护三个数组，分别存 crtc、connector、plane 的「旧指针 → 新指针」映射，加一个 drm_private_obj 状态数组。drm_atomic_get_crtc_state() 这类 getter 第一次调用时把旧状态复制一份出来（drm_atomic_helper_duplicate_state 或对象自己的 atomic_duplicate_state 回调），所以「状态是复制出来的」这句话在代码上就落在这里。

7.3 atomic_check 查什么 #

atomic_check 是校验 atomic 更新的唯一钩子，必须拒掉硬件或驱动不支持的任何 modeset 与状态变更。查的东西包括但不限于：

  • mode、framebuffer、缩放、位置是否在硬件能力内；
  • 隐藏的共享资源有没有超卖：共享 PLL、共享 lane、总内存带宽、显示 FIFO 空间；
  • 暴露给用户态的虚拟资源有没有超卖。典型例子是双 pipe 操作：硬件 lockstep 时该对用户隐藏，不 lockstep 时暴露出来，同样一个 plane 要 1 个硬件 plane（只在一个 pipe 上）、2 个（跨两个 pipe），甚至跟第二个 plane 共用；
  • 过渡状态是否可达，请求的更新能否在 vblank 内完成而不临时关掉某些功能。

它还得正确填 drm_crtc_state，好让 drm_atomic_crtc_needs_modeset() 如实反映这次更新的性质：当且仅当这次更新无法在该 CRTC 的一个 vblank 内无撕裂地应用时返回 true，core 靠这个信息拒掉需要整套 modeset（blank 掉屏幕或长时间暂停更新）而用户态又明确不允许的请求。基础输入校验不用重复做，core 在调这个钩子之前已经做过一遍。

返回值：0 成功；-EINVAL 违反约束；-EDEADLK 拿 drm_modeset_lock() 失败；-ENOMEM 分配 state 子结构失败；-EINTR / -EAGAIN / -ERESTARTSYS 需要重启 ioctl。用 atomic helper 的驱动直接挂 drm_atomic_helper_check 或它的子函数即可。

7.4 atomic_commit 的承诺 #

atomic_commit 是提交 atomic 更新的唯一钩子，core 保证调它之前 atomic_check 已经成功过，且期间没被别的东西改过。

非阻塞提交（nonblock 为真）有一条硬约束：所有会引起提交失败的准备工作都必须在本次回调上下文里做完。唯一例外是硬件错误导致的 -EIO，而且即便 -EIO，驱动也得保证显示 pipe 至少还在跑——否则 compositor 会因为 page flip 突然失败而崩。其余的事，特别是真正写硬件的动作，不能阻塞调用者；不需要 modeset 的更新必须做到这一点。驱动在 flip 之前必须等新 framebuffer 上的渲染完成；如果底层 buffer 是共享 dma-buf，还得等别的驱动的渲染完成。

应用可以申请提交完成的通知，这类事件按 CRTC 区分，靠 drm_event 里的 CRTC index 辨识，core 会把 struct drm_event 放进每个 CRTC 的 drm_crtc_state.event。一条禁止项：驱动不许自行关掉一个已经通过 atomic 提交成功启用的显示 pipe，那会让 compositor 在 page flip 被突然拒绝时崩。

错误码 含义
-EBUSY 请求非阻塞更新但前面还有未完成的更新
-ENOMEM 分配内存失败，典型在 pin framebuffer 时
-ENOSPC -ENOMEM 的细化，表示 VRAM / IOMMU 空间耗尽
-EIO 硬件彻底挂了
-EINTR / -EAGAIN / -ERESTARTSYS ioctl 需要重启

明确不许返回 -EINVAL（无效请求该在 atomic_check 拦掉）和 -EDEADLK（这个函数不许再拿 modeset 锁）。

7.5 helper 与 RK3399 的选择 #

Rockchip 走 helper 路线，rockchip_drm_fb.c 里只有两组：

c
static const struct drm_mode_config_funcs rockchip_drm_mode_config_funcs = {
        .fb_create = rockchip_fb_create,
        .atomic_check = drm_atomic_helper_check,
        .atomic_commit = drm_atomic_helper_commit,
};

static const struct drm_mode_config_helper_funcs rockchip_mode_config_helpers = {
        .atomic_commit_tail = drm_atomic_helper_commit_tail_rpm,
};

fb_create 的实现在 GEM 那一章讲。drm_atomic_helper_commit_tail_rpm 是给用 runtime PM 的驱动准备的 commit tail：它接管「disabled → begin → 写硬件 → flush → enabled」这段收尾顺序，RK3399 的 VOP 用 pm_runtime_enable() 管时钟，所以用它而不是默认的 drm_atomic_helper_commit_tail。版本上留个心眼：drm_atomic_helper_commit_tail_rpm 在 5.x 期间有过行为调整（涉及 plane 的 disable 时机），6.3 的实现在 drm_atomic_helper.c，细节未逐行验证。

7.6 一次提交的状态流转 #

text
用户 ioctl(ATOMIC_IOCTL)
  → 分配 drm_atomic_state，把涉及的 crtc/plane/connector 状态 duplicate 一份
  → drm_atomic_check_only()
       ├─ 逐对象调 helper 的 atomic_check
       ├─ 查 possible_crtcs / possible_clones
       ├─ 查格式、缩放、位置是否合法
       └─ normalize_zpos（mode_config.normalize_zpos 为真时）
       任一失败 → 丢弃 state，返回 -EINVAL
  → drm_atomic_commit()
       ├─ 阻塞路径：commit_tail 同步跑完
       └─ 非阻塞路径：丢进 commit work 队列
            → commit_tail（RK3399 为 _rpm 版）
                 ├─ disable 不再使用的输出
                 ├─ atomic_begin（crtc helper）
                 ├─ atomic_update / atomic_disable（plane helper）
                 ├─ atomic_flush（crtc helper）
                 ├─ wait_for_vblanks
                 └─ atomic_enable（新启用的 crtc）
            → 旧 state / 旧 framebuffer 引用释放（drm_flip_work 延后排队）

三个要记住的点：状态是复制出来的，不是原地改；校验是全套一次性做；提交分阻塞与非阻塞两条路，非阻塞必须能立刻返回。

八、DRM 的驱动注册 #

写一个 DRM 驱动，骨架就五步：定义 struct drm_driver，初始化 name、desc、date、major、minor、driver_features、fops、dumb_create 等成员；分配并初始化 struct drm_device；初始化 mode_config；创建 framebuffer、plane、crtc、encoder、connector 五类对象；注册 drm_device，得到 /dev/dri/card%d，四类 KMS 对象一并注册。

第三、四步在 RK3399 上被拆到了 component 框架里：CRTC 驱动（VOP）负责 plane 与 crtc 的初始化，HDMI / eDP 驱动负责 encoder 与 connector。所有组件都 bind 成功，整个 DRM 系统才算启动完成。component 的装配细节在《RK3399 VOP 驱动：从 probe 到显示通路》第十节。

8.1 drm_dev_init：初始化设备 #

c
static int drm_dev_init(struct drm_device *dev, const struct drm_driver *driver,
                        struct device *parent)
{
        struct inode *inode;
        int ret;

        if (!drm_core_init_complete) { DRM_ERROR("DRM core is not initialized\n"); return -ENODEV; }
        if (WARN_ON(!parent))
                return -EINVAL;

        kref_init(&dev->ref);                       /* 引用计数 = 1 */
        dev->dev = get_device(parent);
        dev->driver = driver;

        INIT_LIST_HEAD(&dev->managed.resources);
        spin_lock_init(&dev->managed.lock);
        dev->driver_features = ~0u;                 /* 默认不做每设备限制 */

        /* 计算加速与图形驱动互斥，同时置位直接失败 */
        if (drm_core_check_feature(dev, DRIVER_COMPUTE_ACCEL) &&
            (drm_core_check_feature(dev, DRIVER_RENDER) ||
             drm_core_check_feature(dev, DRIVER_MODESET)))
                return -EINVAL;

        drm_legacy_init_members(dev);
        drm_dev_init_lists_and_locks(dev);          /* 原稿逐个 INIT_LIST_HEAD / mutex_init，见下表 */

        ret = drmm_add_action_or_reset(dev, drm_dev_init_release, NULL);
        inode = drm_fs_inode_new();                 /* 所有 minor 共享的 address_space */
        if (IS_ERR(inode))
                goto err;
        dev->anon_inode = inode;

        if (drm_core_check_feature(dev, DRIVER_COMPUTE_ACCEL)) {
                ret = drm_minor_alloc(dev, DRM_MINOR_ACCEL);
        } else {
                if (drm_core_check_feature(dev, DRIVER_RENDER))
                        ret = drm_minor_alloc(dev, DRM_MINOR_RENDER);
                ret = drm_minor_alloc(dev, DRM_MINOR_PRIMARY);   /* 普通图形驱动走这里 */
        }

        ret = drm_legacy_create_map_hash(dev);
        drm_legacy_ctxbitmap_init(dev);

        if (drm_core_check_feature(dev, DRIVER_GEM))
                ret = drm_gem_init(dev);

        ret = drm_dev_set_unique(dev, dev_name(parent));   /* dev->unique */
        return 0;
err:
        drm_managed_release(dev);
        return ret;
}

（每一步后的 if (ret) goto err; 为省版面省略，语义不变。）被折叠成一行的全部初始化成员：

类别 成员
链表 filelist（用户态客户端）、filelist_internal（内核内客户端）、clientlist（内核内客户端按 client 记）、vblank_event_list、debugfs_list
锁 event_lock（spinlock_t）、struct_mutex、master_mutex、filelist_mutex、clientlist_mutex、debugfs_mutex（struct mutex）

Rockchip 的声明是 .driver_features = DRIVER_MODESET | DRIVER_GEM | DRIVER_ATOMIC，没设 DRIVER_COMPUTE_ACCEL 也没设 DRIVER_RENDER，所以 DRM_MINOR_ACCEL 和 DRM_MINOR_RENDER 两行 drm_minor_alloc 都走不到，accel 成员始终为空。render 也不为空——但那是另一个驱动的事：Rockchip 的 GPU（Mali-T860）由独立的 panfrost 驱动管，card1 与 renderD128 是它报出来的，跟 VOP 那个 card0 不是一个驱动。

drm_dev_init 里最关键的两步是 drm_minor_alloc(dev, DRM_MINOR_PRIMARY) 和 drm_gem_init(dev)。

8.2 drm_minor_alloc 与 drm_sysfs_minor_alloc #

c
static int drm_minor_alloc(struct drm_device *dev, unsigned int type) /* PRIMARY = 0 */
{
        struct drm_minor *minor = drmm_kzalloc(dev, sizeof(*minor), GFP_KERNEL);
        unsigned long flags;
        int r;

        minor->type = type;
        minor->dev = dev;

        idr_preload(GFP_KERNEL);
        if (type == DRM_MINOR_ACCEL) {
                r = accel_minor_alloc();
        } else {
                spin_lock_irqsave(&drm_minor_lock, flags);
                /* 按 64 一段分配唯一 id：64*type ~ 64*(type+1)，结束值排他 */
                r = idr_alloc(&drm_minors_idr, NULL,
                        64 * type, 64 * (type + 1), GFP_NOWAIT);
                spin_unlock_irqrestore(&drm_minor_lock, flags);
        }
        idr_preload_end();
        if (r < 0)
                return r;
        minor->index = r;

        r = drmm_add_action_or_reset(dev, drm_minor_alloc_release, minor);
        minor->kdev = drm_sysfs_minor_alloc(minor);   /* 配 struct device */
        *drm_minor_get_slot(dev, type) = minor;       /* 写到 primary / render / accel */
        return 0;
}

drm_minor_get_slot 按 type 返回对应成员的地址（DRM_MINOR_PRIMARY → &dev->primary，RENDER → &dev->render，ACCEL → &dev->accel，其余 BUG()）。

drm_sysfs_minor_alloc 给 minor 配一个 struct device，四步：

步骤 动作 说明
1 kzalloc + device_initialize() 这是 device_register 的前半段，只初始化不注册
2 定名字 ACCEL 用 accel%d，RENDER 用 renderD%d，其它用 card%d
3 填设备模型字段 devt = MKDEV(DRM_MAJOR, index) 即 226:index、class = drm_class、type = &drm_sysfs_device_minor、parent = minor->dev->dev、release = drm_sysfs_release，再 dev_set_drvdata(kdev, minor)
4 dev_set_name() 失败则 put_device() 并返回 ERR_PTR

device_add 不在这里，它推迟到 drm_minor_register 里做。drm_class 也是 drm_core_init 建的。

8.3 drm_gem_init：GEM 的设备级初始化 #

c

8.4 drm_dev_register：注册设备 #

c
int drm_dev_register(struct drm_device *dev, unsigned long flags)
{
        const struct drm_driver *driver = dev->driver;
        int ret;

        if (!driver->load)
                drm_mode_config_validate(dev);          /* 注册前体检，见 8.5 */
        WARN_ON(!dev->managed.final_kfree);

        if (drm_dev_needs_global_mutex(dev))
                mutex_lock(&drm_global_mutex);

        ret = drm_minor_register(dev, DRM_MINOR_RENDER);   /* 没建 render，返回 0 */
        ret = drm_minor_register(dev, DRM_MINOR_PRIMARY);  /* 重点 */
        ret = drm_minor_register(dev, DRM_MINOR_ACCEL);    /* 没建 accel，返回 0 */
        ret = create_compat_control_link(dev);             /* 以上各有 if (ret) goto err_minors */

        dev->registered = true;

        if (driver->load) {                                 /* 已废弃的路径 */
                ret = driver->load(dev, flags);
                if (ret)
                        goto err_minors;
        }

        if (drm_core_check_feature(dev, DRIVER_MODESET))    /* 注册四类 KMS 对象 */
                drm_modeset_register_all(dev);

        DRM_INFO("Initialized %s %d.%d.%d %s for %s on minor %d\n",
                 driver->name, driver->major, driver->minor,
                 driver->patchlevel, driver->date,
                 dev->dev ? dev_name(dev->dev) : "virtual device",
                 dev->primary ? dev->primary->index : dev->accel->index);
        goto out_unlock;
err_minors:
        remove_compat_control_link(dev);
        drm_minor_unregister(dev, DRM_MINOR_ACCEL);
        drm_minor_unregister(dev, DRM_MINOR_PRIMARY);
        drm_minor_unregister(dev, DRM_MINOR_RENDER);
out_unlock:
        if (drm_dev_needs_global_mutex(dev))
                mutex_unlock(&drm_global_mutex);
        return ret;
}

顺序是有讲究的：先建节点（drm_minor_register 里 device_add，udev 立刻建 /dev/dri/card0），再 load，再注册四类对象。这就是注释里说的「为向后兼容在注册节点后才调 load，因此产生竞态」——所以新驱动别用 load，所有初始化都应该在 drm_dev_register 之前做完。

8.5 drm_mode_config_validate：注册前的体检 #

c
void drm_mode_config_validate(struct drm_device *dev)
{
        struct drm_encoder *encoder;
        struct drm_crtc *crtc;
        struct drm_plane *plane;
        u32 primary_with_crtc = 0, cursor_with_crtc = 0;
        unsigned int num_primary = 0;

        if (!drm_core_check_feature(dev, DRIVER_MODESET))
                return;

        drm_for_each_encoder(encoder, dev)
                fixup_encoder_possible_clones(encoder);
        drm_for_each_encoder(encoder, dev) {
                validate_encoder_possible_clones(encoder);
                validate_encoder_possible_crtcs(encoder);
        }

        drm_for_each_crtc(crtc, dev) {
                WARN(!crtc->primary, "Missing primary plane on [CRTC:%d:%s]\n",
                     crtc->base.id, crtc->name);
                /* 下面三条：crtc 不能既挂 cursor plane 又实现旧的 cursor 回调 */
                WARN(crtc->cursor && crtc->funcs->cursor_set,  "... cursor_set ...");
                WARN(crtc->cursor && crtc->funcs->cursor_set2, "... cursor_set2 ...");
                WARN(crtc->cursor && crtc->funcs->cursor_move, "... cursor_move ...");

                if (crtc->primary) {
                        WARN(!(crtc->primary->possible_crtcs & drm_crtc_mask(crtc)),
                             "Bogus primary plane possible_crtcs ...");
                        WARN(primary_with_crtc & drm_plane_mask(crtc->primary),
                             "Primary plane [PLANE:%d:%s] used for multiple CRTCs");
                        primary_with_crtc |= drm_plane_mask(crtc->primary);
                }
                if (crtc->cursor) {
                        WARN(!(crtc->cursor->possible_crtcs & drm_crtc_mask(crtc)),
                             "Bogus cursor plane possible_crtcs ...");
                        WARN(cursor_with_crtc & drm_plane_mask(crtc->cursor),
                             "Cursor plane [PLANE:%d:%s] used for multiple CRTCs");
                        cursor_with_crtc |= drm_plane_mask(crtc->cursor);
                }
        }

        drm_for_each_plane(plane, dev)
                if (plane->type == DRM_PLANE_TYPE_PRIMARY)
                        num_primary++;

        WARN(num_primary != dev->mode_config.num_crtc,
             "Must have as many primary planes as there are CRTCs, but have %u primary planes and %u CRTCs",
             num_primary, dev->mode_config.num_crtc);
}

它在注册前把四类对象的内部一致性扫一遍，全是 WARN，不会让注册失败，但 dmesg 里出现任何一条都说明驱动写错了。要查的六条：每个 crtc 必须有 primary plane；crtc 不能既挂 cursor plane 又实现 cursor_set / cursor_set2 / cursor_move；plane 的 possible_crtcs 必须包含它挂的 crtc；一个 primary plane 不能被多个 crtc 共用；encoder 的 possible_clones / possible_crtcs 必须自洽；primary plane 数量必须等于 crtc 数量。

最后一条最容易踩：RK3399 两个 VOP = 两个 crtc，那就必须有两个 primary plane。

8.6 drm_minor_register 与 drm_debugfs_init #

c
static int drm_minor_register(struct drm_device *dev, unsigned int type)
{
        struct drm_minor *minor = *drm_minor_get_slot(dev, type);
        unsigned long flags;
        int ret;

        if (!minor)                     /* render / accel 没建就是 NULL，直接返回 0 */
                return 0;

        if (minor->type == DRM_MINOR_ACCEL)
                accel_debugfs_init(minor, minor->index);
        else if ((ret = drm_debugfs_init(minor, minor->index, drm_debugfs_root))) {
                DRM_ERROR("DRM: Failed to initialize /sys/kernel/debug/dri.\n");
                goto err_debugfs;
        }

        if ((ret = device_add(minor->kdev)))    /* udev 据此建 /dev/dri/card%d */
                goto err_debugfs;

        if (minor->type == DRM_MINOR_ACCEL) {
                accel_minor_replace(minor, minor->index);
        } else {
                spin_lock_irqsave(&drm_minor_lock, flags);
                idr_replace(&drm_minors_idr, minor, minor->index);  /* NULL → minor */
                spin_unlock_irqrestore(&drm_minor_lock, flags);
        }
        return 0;
err_debugfs:
        drm_debugfs_cleanup(minor);
        return ret;
}

8.7 drm_debugfs_init 的内部顺序 #

九、DRM 与内存管理 #

9.1 GEM 的分工边界 #

层 谁管 管什么
显存对象 drm_gem_object 一块 buffer 的载体，引用计数，handle 与 name
显存布局 drm_framebuffer format、pitch、offset、modifier、层数
显存来源 CMA / SHMEM / VRAM helper 物理页从哪来
显存映射 drm_vma_offset_manager 用户态 mmap 的 offset 空间
跨设备共享 dma-buf / PRIME 导出 fd、导入 handle

drm_framebuffer 只是「描述」，不持有内存；真正持有内存的是 GEM object。这就是为什么 drm_mode_config_funcs.fb_create 的注释特意写着「不是分配内存，只是创建 framebuffer object」。

9.2 dumb buffer 与 mmap #

text
ioctl DRM_IOCTL_MODE_CREATE_DUMB
  → drm_mode_create_dumb_ioctl
       → drm_driver.dumb_create（RK3399 = rockchip_gem_dumb_create）
            ├─ 建 gem object      ├─ 建 gem handle（对当前 drm_file 生效）
            └─ 分配物理内存（可选）
  ← 回填 handle / pitch / size
ioctl DRM_IOCTL_MODE_MAP_DUMB
  → drm_driver.dumb_map_offset（默认 drm_gem_create_mmap_offset）
       → 在 vma_offset_manager 里找一个 offset
mmap(fd, offset, ...)
  → drm_gem_mmap
       ├─ drm_dev_is_unplugged() 检查
       ├─ drm_vma_offset_exact_lookup_locked()  按 offset 找 node
       ├─ container_of 反推 gem object → kref_get_unless_zero()
       ├─ drm_vma_node_is_allowed()             权限检查
       └─ drm_gem_mmap_obj()                    挂 vm_ops

Rockchip 的 rockchip_gem_dumb_create 走 CMA 分配路线，显存是物理连续的 system RAM。这也是为什么 rockchip_drm_dma_init_device() 要判断 IOMMU：有 IOMMU 时 buffer 可以不连续，没有 IOMMU 就必须连续。

drm_gem_mmap 里有一句最容易看漏的并发保护：查到 node 后 container_of 反推出 gem object，必须再 kref_get_unless_zero(&obj->refcount) ——查找时对象刚好被释放到一半，refcount 已经 0，这种时候不能拿，拿了就是 use-after-free。拿不到就 obj = NULL，随后返回 -EINVAL；drm_vma_node_is_allowed() 失败则返回 -EACCES；最后 drm_gem_mmap_obj(obj, drm_vma_node_size(node) << PAGE_SHIFT, vma) 挂上 vm_ops，再 drm_gem_object_put(obj) 放掉临时引用。

9.4 fops 与 open 路径 #

c

强制要求实现的是 drm_open、drm_read、drm_ioctl、drm_compat_ioctl（开了 CONFIG_COMPAT 才有）。drm_read 与 drm_poll 提供 DRM 事件支持——通过文件描述符往用户态发异步事件，vblank 和 page flip 完成事件都走这条路，驱动也可以拿它报渲染完成。

drm_open 的流程：drm_minor_acquire(iminor(inode)) 拿 minor；dev = minor->dev；需要全局互斥时 mutex_lock(&drm_global_mutex)；atomic_fetch_inc(&dev->open_count) 为 0 则置 need_setup；filp->f_mapping = dev->anon_inode->i_mapping 让同一设备所有节点共享 address_space；调 drm_open_helper()；首次打开时再 drm_legacy_setup()；出错就 atomic_dec(&dev->open_count) + 解锁 + drm_minor_release(minor)。

drm_open_helper 的流程：O_EXCL 直接 -EBUSY（不支持独占打开）；drm_cpu_valid() 与 switch_power_state 检查；drm_file_alloc(minor) 分配 struct drm_file；primary 客户端要先 drm_master_open()；filp->private_data = priv、filp->f_mode |= FMODE_UNSIGNED_OFFSET、priv->filp = filp；最后 list_add(&priv->lhead, &dev->filelist)。

FMODE_UNSIGNED_OFFSET 这句别小看：mmap 的 offset 是「伪造」的 vma offset，会落在有符号 64 位范围之外，不开这个标志内核会直接拒掉。drm_master_open() 是 KMS 独占的入口——/dev/dri/card0 上同时只能有一个 master，Xorg、systemd-logind 谁抢到谁说话，这解释了为什么跑 modetest 前必须 killall Xorg。

十、易错点速查 #

编号 易错点 正确做法 / 判据
1 以为 drm_framebuffer 持有内存 内存归 drm_gem_object；framebuffer 只描述 format / pitch / offset / modifier
2 以为 drm_crtc 就是屏幕 crtc 是「一路时序」，屏幕是 connector；一个 crtc 可以换接到不同 connector
3 用 drm_dev_alloc 写新驱动 用 devm_drm_dev_alloc 把 drm_device 嵌进私有结构；dev_private 已废弃

5 忘记置 DRIVER_ATOMIC 用户态用不了 ATOMIC_IOCTL，modetest 的 -a 会失败
6 同时置 DRIVER_COMPUTE_ACCEL 和 DRIVER_MODESET drm_dev_init() 直接 -EINVAL 返回
7 把 drm_mode_config_validate() 的 WARN 当无害 它只 WARN 不 fail，但每条都意味着驱动写错，上线前必须清干净
8 以为 6.3 还有 drivers/gpu/drm/tinydrm/ 已改成 drm_mipi_dbi.c；tinydrm/ili9341.c 是 4.19 的路径
9 用 dumb_create 回填的 size 直接当显存大小 size 是整块 buffer 字节数，含 padding；对齐与 pitch 有关
10 atomic 驱动里对可变属性调 drm_object_property_set_value() atomic 驱动只把可变属性存在 state 里，values[] 只存默认值
11 忘了 FMODE_UNSIGNED_OFFSET GEM 的伪造 offset 超出有符号范围，mmap 会被内核拒
