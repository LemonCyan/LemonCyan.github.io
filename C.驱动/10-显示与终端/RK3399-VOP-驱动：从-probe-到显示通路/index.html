一、RK3399 的显示硬件：两个 VOP #

1.1 显示子系统的构成 #

Rockchip 平台把显示输出相关软硬件统称显示子系统，内核用 component 框架把它搭起来。一个显示子系统由这些独立模块组成：显示处理器（vop）、接口控制器（mipi、lvds、hdmi、edp、dp、rgb、BT1120、BT656、I8080 即 MCU 显示接口）、液晶背光、电源。

先分清两个概念：把内存里的图像数据转成电信号送到显示设备，这个部件叫显示控制器，早期叫 LCDC；在显示控制器基础上继续扩展、能做一些简单图像处理（缩放、旋转、合成）的，叫显示处理器，瑞芯的 vop、高通的 sde 都属于这一类。显示处理器在没有 CPU 参与时能干：缩放、旋转；多层合成，支持 porter-duff；支持多种显存格式（ARGB888、RGB565，包括 GPU 输出的 tile 格式和 fbdc 压缩格式）；生成时序信号如 tcon 送给 mipi、lvds 等接口；支持多种分辨率。

text
GPU / RGA / VPU（渲染、2D 缩放旋转合成、视频解码）→ DDR
   → VOP（Alpha 叠加、颜色空间转换、gamma 矫正、HDR 转换）
        ├─ HDMI          └─ eDP / DP
        ├─ MIPI DSI（双通道）   └─ LVDS / RGB / BT1120 / BT656 / I8080
              → 接口模块转成各自协议 → 显示器

1.2 VOP 1.0 与 VOP 2.0 #

VOP 1.0 VOP 2.0
多屏实现 多个 VOP，一个 VOP 同一时刻只出一路独立时序 一个 VOP，后端挂多路独立 Video Port（VP）
双屏条件 需要两个物理 VOP 一个 VOP 的多个 VP 同时独立工作
典型平台 RK3288、RK3399、PX30 RK3568、RK3588 一代（版本号以 TRM 为准）
驱动文件 rockchip_drm_vop.c + rockchip_vop_reg.c rockchip_drm_vop2.c + rockchip_vop2_reg.c
一个 crtc 的图层上限 每个 VOP 4 个 win，双屏时总图层数翻倍 所有 VP 共享一套 win 池，按 VP 分配
双屏时序约束 两个 VOP 各有独立 dclk，互不牵连 多 VP 常常共用一个 PLL，时序互相约束

两条路线在 rockchip_drm_init() 里用两个 Kconfig 开关互斥二选一：CONFIG_ROCKCHIP_VOP 与 CONFIG_ROCKCHIP_VOP2。RK3399 是前者。

为什么 VOP2 要另起一套驱动文件，不是因为寄存器变了，而是因为「多屏」这件事的抽象变了。VOP1.0 时代两个物理 VOP 就是两个 struct vop 实例，各自嵌一个 drm_crtc，天然对应两个 crtc。VOP2.0 只有一个实例，多个 VP 才是最上层的显示通道，驱动里就得引入 struct vop2_video_port 这一层，把 crtc 建在 VP 上，win 变成可跨 VP 分配的共享资源。这套抽象差异太大，没法在一个文件里用 if 兼容，所以内核直接分家。

1.3 RK3399 的两个 VOP #

  • VOP_BIG：支持 4096×2160，带 AFBC；
  • VOP_LIT：支持 2560×1600。

两者的差别不只是分辨率上限。VOP_LIT 不需要 AFBC，寄存器表里 afbc 一组是空的；LUT 尺寸也不同，rk3399_vop_big.lut_size = 1024，rk3399_vop_lit 的取值素材没给，modetest -p 在 crtc 44 上读到的 GAMMA_LUT_SIZE 是 1024，但那是运行时值，不能反推 vop_data 里的配置，这条列在附录未验证项里。

支持的显示接口：双通道 MIPI DSI（4 线/通道）、1 个 eDP、1 个 DP、1 个 HDMI。NanoPC-T4 这块板子的输出能力：eDP 1.3（4 线，10.8Gbps）+ 1~2 路 4 线 MIPI DSI；Type-C 上的 DisplayPort 1.2 Alt Mode；HDMI 2.0a，支持 4K@60Hz，支持 HDCP 1.4/2.2。

1.4 设备树里 VOP 长什么样 #

dts
vopb: vop@ff900000 {
        compatible = "rockchip,rk3399-vop-big";
        reg = <0x0 0xff900000 0x0 0x2000>, <0x0 0xff902000 0x0 0x1000>;
        interrupts = <GIC_SPI 118 IRQ_TYPE_LEVEL_HIGH 0>;
        assigned-clocks = <&cru ACLK_VOP0>, <&cru HCLK_VOP0>;
        assigned-clock-rates = <400000000>, <100000000>;
        clocks = <&cru ACLK_VOP0>, <&cru DCLK_VOP0>, <&cru HCLK_VOP0>;
        clock-names = "aclk_vop", "dclk_vop", "hclk_vop";
        iommus = <&vopb_mmu>;
        power-domains = <&power RK3399_PD_VOPB>;
        resets = <&cru SRST_A_VOP0>, <&cru SRST_H_VOP0>, <&cru SRST_D_VOP0>;
        reset-names = "axi", "ahb", "dclk";
        status = "disabled";

        vopb_out: port {
                #address-cells = <1>;
                #size-cells = <0>;
                vopb_out_edp:   endpoint@0 { reg = <0>; remote-endpoint = <&edp_in_vopb>;   };
                vopb_out_mipi:  endpoint@1 { reg = <1>; remote-endpoint = <&mipi_in_vopb>;  };
                vopb_out_hdmi:  endpoint@2 { reg = <2>; remote-endpoint = <&hdmi_in_vopb>;  };
                vopb_out_mipi1: endpoint@3 { reg = <3>; remote-endpoint = <&mipi1_in_vopb>; };
                vopb_out_dp:    endpoint@4 { reg = <4>; remote-endpoint = <&dp_in_vopb>;    };
        };
};

（endpoint 节点在原稿里多行写开，这里压成单行，内容一字未改。）要点：reg 两段，0xff900000 是 VOP 寄存器窗口（8KB），0xff902000 是 gamma LUT 窗口（4KB），驱动分别用 IORESOURCE_MEM 的 0 号和 1 号资源取；clock-names 三项对应 aclk_vop（共享内存频率）、dclk_vop（像素时钟）、hclk_vop（AHB 时钟）；iommus = <&vopb_mmu> 意味着 VOP 走 IOMMU；reset-names 三项 axi、ahb、dclk，驱动只显式用了后两个；port 下五个 endpoint 说明 VOP_BIG 能接 eDP、MIPI DSI0、HDMI、MIPI DSI1、DP 五个接口。

vopl 节点结构同理，compatible = "rockchip,rk3399-vop-lit"，基址 0xff8f0000（未验证，素材未给出）。

要在板级 dts 里启用 VOP_BIG，补三段：

dts
&vopb { status = "okay"; };
&vopb_mmu { status = "okay"; };
&display_subsystem { status = "okay"; };

dtsi 里 vopb 默认 disabled，板级文件不覆盖它，整个 DRM 就起不来。而且 VOP 和它的 MMU 必须一起启用，只开 VOP 不开 MMU，rockchip_drm_init_iommu() 会失败。

Rockchip VOP driver 与 Rockchip VOP2 driver 只能勾一个。两个都勾上不是二选一失效，而是两个 platform driver 都注册进去、各自匹配各自的 compatible，RK3399 只有 VOP1 的 compatible，VOP2 那套驱动等于白写进来占内存。选错的表现是编译能过、启动后 vop_probe 根本不进——of_match_table 里没有 rockchip,rk3399-vop-big。

二、struct vop 与 vop_data #

2.1 vop_win：一个图层 #

c
struct vop_win {                            /* 一个图层 */
        struct drm_plane base;              /* 对应的 drm_plane */
        const struct vop_win_data *data;    /* win 的寄存器描述 */
        const struct vop_win_yuv2yuv_data *yuv2yuv_data;
        struct vop *vop;
};

四个成员各管一摊：base 是给 DRM core 看的通用 plane 对象，data 指向 SoC 寄存器描述表里这一层的那一条，yuv2yuv_data 只在需要 YUV 转 YUV 的 SoC 上有意义，vop 反指回自己的 VOP 实例，为的是在 plane 回调里 container_of 之后能直接拿到寄存器基址和锁。

2.2 vop_data：一颗 SoC 的 VOP 长什么样 #

c
struct vop_data {                           /* 一颗 SoC 的 VOP 长什么样 */
        uint32_t version;
        const struct vop_intr *intr;
        const struct vop_common *common;
        const struct vop_misc *misc;
        const struct vop_modeset *modeset;  /* 模式配置相关寄存器 */
        const struct vop_output *output;    /* 输出配置相关寄存器 */
        const struct vop_afbc *afbc;
        const struct vop_win_yuv2yuv_data *win_yuv2yuv;
        const struct vop_win_data *win;
        unsigned int win_size;
        unsigned int lut_size;

#define VOP_FEATURE_OUTPUT_RGB10        BIT(0)
#define VOP_FEATURE_INTERNAL_RGB        BIT(1)
        u64 feature;
};

七组寄存器描述指针，一组一个功能域：intr 管中断的 status/enable/clear 三套位；common 管 DSP 输出通用配置；misc 管零碎的全局开关（比如 global_regdone_en）；modeset 管时序参数的写入寄存器；output 管各接口的使能、dclk 极性、pin 极性；afbc 管压缩帧缓冲那块；win 是图层数组。win_size 是数组长度，lut_size 只在 1024 与 256 两个值里取，feature 是能力位。

version 是驱动自己编的版本号，跟 SoC 编号无关，用 VOP_VERSION(major, minor) 拼出来，只在打印和分支判断里用。

struct vop 的完整字段（crtc 直接内嵌，&vop->crtc 就是 DRM crtc 对象；win[] 是柔性数组，RK3399 为 4 个）：

三个字段需要单独解释，因为它们最容易在改代码时被误用：

regsbak 是整段寄存器窗口的影子副本，长度等于 len，在 vop_initial 里复位之后整体备份一次，此后每次 vop_reg_set 读改写都先读影子、算完再写回影子、最后写硬件。它让读改写不需要回读硬件，也不需要持锁，代价是硬件被外部（比如 uboot 残留配置、另一个 agent 写同一段地址）改过之后影子会失真。所以复位之后必须重新整体备份一遍，这条在易错点表里单列。

pending 是挂起标志位，is_enabled 与它配合描述「硬件开着、但某次提交还没走完」这种中间态。win_enabled 是另一个维度：crtc 亮着不代表 4 个 win 都开着，哪些 win 有内容要送要用位掩码记着，vop_crtc_atomic_disable 里要靠它逐个关。

vop_lock 与 reg_lock/irq_lock 的分工是三条不同粒度的锁：vop_lock 是 mutex，保护 crtc 级的 enable/disable 这类慢路径；reg_lock 是 spinlock，保护每一次寄存器读改写；irq_lock 专门保护中断的 status/enable/clear 三组位，因为中断上下文和提交路径会同时碰这三组寄存器，只用一把 reg_lock 会让中断里持锁时间过长。

2.4 RK3399 VOP_BIG 的实例 #

RK3399 VOP_BIG 的实例与四个图层的配置：

c
static const struct vop_data rk3399_vop_big = {
        .version = VOP_VERSION(3, 5),
        .feature = VOP_FEATURE_OUTPUT_RGB10,
        .intr = &rk3366_vop_intr,
        .common = &rk3399_common,
        .modeset = &rk3288_modeset,
        .output = &rk3399_output,
        .afbc = &rk3399_vop_afbc,
        .misc = &rk3368_misc,
        .win = rk3399_vop_win_data,
        .win_size = ARRAY_SIZE(rk3399_vop_win_data),
        .win_yuv2yuv = rk3399_vop_big_win_yuv2yuv_data,
        .lut_size = 1024,
};

static const struct vop_win_data rk3399_vop_win_data[] = {
        { .base = 0x00,  .phy = &rk3399_win01_data, .type = DRM_PLANE_TYPE_PRIMARY },
        { .base = 0x40,  .phy = &rk3368_win01_data, .type = DRM_PLANE_TYPE_OVERLAY },
        { .base = 0x00,  .phy = &rk3368_win23_data, .type = DRM_PLANE_TYPE_OVERLAY },
        { .base = 0x50,  .phy = &rk3368_win23_data, .type = DRM_PLANE_TYPE_CURSOR  },
};

static const struct vop_win_yuv2yuv_data rk3399_vop_big_win_yuv2yuv_data[] = {
        { .base = 0x00,  .phy = &rk3399_yuv2yuv_win01_data,
          .y2r_en = VOP_REG(RK3399_YUV2YUV_WIN, 0x1, 1) },
        { .base = 0x60,  .phy = &rk3399_yuv2yuv_win01_data,
          .y2r_en = VOP_REG(RK3399_YUV2YUV_WIN, 0x1, 9) },
        { .base = 0xC0,  .phy = &rk3399_yuv2yuv_win23_data },
        { .base = 0x120, .phy = &rk3399_yuv2yuv_win23_data },
};

两个细节：feature 只有 VOP_FEATURE_OUTPUT_RGB10，没有 VOP_FEATURE_INTERNAL_RGB，所以 vop_bind 里初始化内置 rgb encoder 那段走不到；lut_size = 1024，与 vop_bind 里 lut_size != 1024 && lut_size != 256 的检查一致。

win_data 那张表有个坑：四条的 .base 是 0x00、0x40、0x00、0x50，其中 WIN0 和 WIN2 都是 0x00。base 不是相对 VOP 寄存器窗口的绝对偏移，而是这一层自己的那套图层寄存器组相对 phy 里那些偏移的起点。WIN0 和 WIN1 每层占 0x40 字节，共用 rk3368_win01_data 或 rk3399_win01_data 那套偏移；WIN2 和 WIN3 每层占 0x50 字节（多出 4 组 YUV 平面地址），共用 rk3368_win23_data。所以 base 的实际含义是「在这套偏移之上再加多少」，WIN0 加 0、WIN1 加 0x40、WIN2 加 0、WIN3 加 0x50，加起来正好落在 RK3399_WIN0_CTRL0 = 0x0030、0x0070、0x00b0、0x0100 上。

win_yuv2yuv 四条对应四个 win，base 分别是 0x00、0x60、0xC0、0x120，y2r_en 只有前两个给了，后两个是空的——这跟硬件上只有 WIN0/WIN1 支持 YUV 到 YUV 转换对得上。这个字段为空的图层，vop_win_init 里 yuv2yuv_data 就不指过去，plane 的 atomic_check 里也不会走 YUV 变换那条分支。

VOP_REG(offset, mask, shift) 三个参数的读法，拿 HDMI 使能这一项拆：RK3288_SYS_CTRL 的偏移是 0x0008，掩码 0x1，移位 13。合起来：物理地址 0xff900000 + 0x0008 = 0xff900008 这个寄存器的 bit13 控制 HDMI 接口输出使能。

mask 写成 0x1fff1fff 的几项是高半字和低半字各放一个 13 位计数值，比如 DSP_HTOTAL_HS_END 低 13 位是 HTOTAL、高 13 位是 HS_END。这类寄存器不能用 VOP_REG(off, 0x1fff, 0) 那种单值写法，一次写进去要同时算好两个值再左移拼起来。

每个 win 内部还有一整套窗体寄存器（以 WIN0 为例）：CTRL0/CTRL1/COLOR_KEY/VIR/YRGB_MST/CBR_MST/ACT_INFO/DSP_INFO/DSP_ST/SCL_FACTOR_YRGB/SCL_FACTOR_CBR/SCL_OFFSET/SRC_ALPHA_CTRL/DST_ALPHA_CTRL/FADING_CTRL/CTRL2，步长 0x40。完整宏表见原文件。

REG_CFG_DONE 那个 0x0000 值得单独记：它是「让配置生效」的触发寄存器，写 1 之后硬件才把前面配的一堆影子值真正加载，然后报 DSP_HOLD_VALID 中断。vop_cfg_done() 就是往这个偏移写一下，它在 vop_initial 末尾、vop_crtc_atomic_enable 末尾、vop_crtc_atomic_flush 里都要调。忘了调的后果是寄存器全配好了但屏幕毫无反应，这种 bug 查起来极耗时。

VERSION_INFO 那个偏移可以读硬件版本号，调试时用 devmem 0xff900004 读一下能确认这一段地址确实映射到了 VOP，而不是映射错到了别的模块。

三、VOP 驱动怎么组织 #

3.2 vop_win_init：把数据表铺到实例上 #

c
static void vop_win_init(struct vop *vop)
{
        const struct vop_data *vop_data = vop->data;
        unsigned int i;

        for (i = 0; i < vop_data->win_size; i++) {
                struct vop_win *vop_win = &vop->win[i];
                const struct vop_win_data *win_data = &vop_data->win[i];

                vop_win->data = win_data;
                vop_win->vop = vop;

                        vop_win->yuv2yuv_data = &vop_data->win_yuv2yuv[i];
        }
}

vop win 就是 VOP 的图层，RK3399 的 VOP 有 4 个图层。这个函数只做指针赋值，没有硬件操作，但它是 vop_create_crtc 的前提——vop_create_crtc 里 win_data = vop_win->data 拿的正是这里铺好的指针。顺序反了会拿到 NULL 直接崩。

3.3 vop_reg：一个寄存器字段的描述 #

c
struct vop_reg {
        uint32_t mask;
        uint32_t shift;
        uint32_t offset;
        bool relaxed;
        bool write_mask;
};

五个字段：offset 是相对寄存器窗口的字节偏移，mask 是这一段在 32 位寄存器里占几位，shift 是起始位，relaxed 决定写用 writel_relaxed 还是 writel，write_mask 决定写的方式走哪条分支。VOP_REG(off, m, s) 宏就是把这几个填进去。

relaxed 这个标志的存在是因为 VOP 有一部分寄存器必须在时序敏感的时刻写（比如 atomic_flush 里最后几个），正常的 writel 带内存屏障，代价是几个周期的等待；relaxed 版去掉屏障，换取时序紧凑。用错的地方表现是偶发的时序抖动，不会稳定复现。

write_mask 是另一条分支：置了这个位的字段，写硬件时走的是「值 + 掩码」双 16 位打包（v = ((v << shift) & 0xffff) | (mask << (shift + 16));），一次写就把「改哪几位、改成什么」都告诉硬件，硬件自己完成读改写。这种方式不能走影子寄存器，因为写入的值不是目标寄存器的完整内容。RK3399 上置这个位的字段不多，主要是几个需要免竞争更新的中断位。

四、vop_probe 与 vop_bind 九步 #

4.1 vop_bind 逐步看 #

c
static int vop_bind(struct device *dev, struct device *master, void *data)
{
        struct platform_device *pdev = to_platform_device(dev);
        const struct vop_data *vop_data;
        struct drm_device *drm_dev = data;
        struct vop *vop;
        struct resource *res;
        int ret, irq;

        vop_data = of_device_get_match_data(dev);      /* 1. 得到 rk3399_vop_big */
        vop = devm_kzalloc(dev, struct_size(vop, win, vop_data->win_size), GFP_KERNEL);
        vop->dev = dev;
        vop->data = vop_data;
        vop->drm_dev = drm_dev;
        dev_set_drvdata(dev, vop);

        vop_win_init(vop);                             /* 2. 初始化 win 数组 */

        res = platform_get_resource(pdev, IORESOURCE_MEM, 0);   /* 3. VOP 寄存器窗口 */
        vop->regs = devm_ioremap_resource(dev, res);
        vop->len = resource_size(res);

        res = platform_get_resource(pdev, IORESOURCE_MEM, 1);   /* 4. LUT 窗口 */
        if (res && (vop_data->lut_size == 1024 || vop_data->lut_size == 256))
                vop->lut_regs = devm_ioremap_resource(dev, res);

        vop->regsbak = devm_kzalloc(dev, vop->len, GFP_KERNEL);

        irq = platform_get_irq(pdev, 0);                        /* 5. GIC_SPI 118 */
        vop->irq = (unsigned int)irq;

        spin_lock_init(&vop->reg_lock);
        spin_lock_init(&vop->irq_lock);
        mutex_init(&vop->vop_lock);

        ret = vop_create_crtc(vop);                    /* 6. 建 crtc 并关联 plane */
        pm_runtime_enable(&pdev->dev);

        ret = vop_initial(vop);                        /* 7. vop 初始化 */

        ret = devm_request_irq(dev, vop->irq, vop_isr, /* 8. 申请中断 */
                               IRQF_SHARED, dev_name(dev), vop);

        if (vop->data->feature & VOP_FEATURE_INTERNAL_RGB)     /* RK3399 走不到 */
                vop->rgb = rockchip_rgb_init(dev, &vop->crtc, vop->drm_dev);

        rockchip_drm_dma_init_device(drm_dev, dev);    /* 9. dma / iommu */
        return 0;
err_disable_pm_runtime:
        pm_runtime_disable(&pdev->dev);
        vop_destroy_crtc(vop);
        return ret;
}

（为压版面省略了 if (!vop) return -ENOMEM;、各处 IS_ERR() 检查与 goto err_disable_pm_runtime。）

步 调用 取到什么 / 为什么这么做
1 of_device_get_match_data() 从 vop_driver_dt_match 拿到 rk3399_vop_big（VOP_LIT 是 rk3399_vop_lit）
2 vop_win_init() 填 vop->win[] 的 data、vop、yuv2yuv_data 三个成员
3 IORESOURCE_MEM 第 0 段 <0x0 0xff900000 0x0 0x2000>，VOP 寄存器窗口，vop->len 由 resource_size() 得到
4 IORESOURCE_MEM 第 1 段 <0x0 0xff902000 0x0 0x1000>，gamma LUT 窗口；lut_size 只允许 1024 或 256
5 platform_get_irq(pdev, 0) dts 里 interrupts = <GIC_SPI 118 IRQ_TYPE_LEVEL_HIGH 0>
6 vop_create_crtc() 建 4 个 plane，再建 crtc，详见第五节
7 vop_initial() 取三个时钟 + 写寄存器初值，详见第六节
8 devm_request_irq(..., vop_isr, IRQF_SHARED, ...) 与 IOMMU 共享中断线，所以是 IRQF_SHARED
9 rockchip_drm_dma_init_device() 记录 private->iommu_dev，决定后续 GEM 走不走 IOMMU

九步里有两处必须按顺序：vop_create_crtc() 在 pm_runtime_enable() 之前；vop_initial() 在 devm_request_irq() 之前——初始化阶段要清中断状态位，中断还没注册就开中断会收到一堆假中断。

第 1 步还有一个隐含约束：devm_kzalloc 的长度是 struct_size(vop, win, vop_data->win_size)，柔性数组按本 SoC 的 win 数量算。RK3399 是 4，RK3036 是 2，如果代码里把 win 数量写死成 4，换一颗 SoC 就会踩到越界或者浪费。

第 6 步与第 7 步之间的 pm_runtime_enable 位置很讲究：vop_create_crtc 里会建 plane 和 crtc 对象并调 drm_crtc_init_with_planes，这些动作不碰硬件；vop_initial 第一件事是 pm_runtime_resume_and_get，它要求 runtime PM 已经 enable。所以 enable 必须卡在两者中间，早一步没有坏处但晚了就直接返回 -EACCES。

4.2 vop_bind 干完的事 #

  • 解析 vopb 设备节点；
  • 取 aclk_vop、dclk_vop、hclk_vop 三个时钟，做 prepare / enable；
  • 取并申请 vop 中断；
  • 取 vopb 寄存器窗口的虚拟地址（两段：主窗口 + LUT）；
  • 取 ahb、dclk 复位句柄并执行复位；
  • 建 drm_crtc，funcs 为 vop_crtc_funcs，helper_private 为 vop_crtc_helper_funcs；
  • RK3399 有 4 个 vop win，每个 win 内嵌一个 drm_plane，一律初始化，funcs 为 vop_plane_funcs，helper_private 为 plane_helper_funcs；
  • 配 vop 寄存器，比如 rk3399_vop_big.intr.clear、.intr.enable。

一条边界要划死：vop_bind 里没有显示模式（时序参数）的配置。时序要等 connector 读回 EDID、用户态决定用哪个 mode 之后，在 atomic 提交里的 vop_crtc_atomic_enable / vop_crtc_mode_fixup 中才落下去。bind 阶段硬件只是「备好了，但没开机」。

4.3 vop_unbind 与回收顺序 #

c
static void vop_unbind(struct device *dev, struct device *master, void *data)
{
        struct vop *vop = dev_get_drvdata(dev);

        if (!vop)
                return;

        pm_runtime_disable(dev);
        vop_destroy_crtc(vop);
        /* devm_* 申请的资源由设备模型统一回收 */
}

顺序跟 bind 严格相反：bind 里 pm_runtime_enable 之后才 vop_initial，unbind 里就先 pm_runtime_disable 再拆 crtc。devm_request_irq 申请的中断、devm_ioremap_resource 映射的寄存器、devm_kzalloc 分的内存都由 devres 在设备 detach 时按申请顺序逆序释放，不用手写。

vop_destroy_crtc 里要做三件事：drm_flip_work_cleanup(&vop->fb_unref_work) 收掉延迟释放队列、of_node_put(crtc->port) 放掉 OF 节点引用、drm_crtc_cleanup(crtc) 让对象从 core 的链表里摘掉。漏掉 of_node_put 的表现是 unbind/bind 反复做几次之后 of_node 引用计数泄漏，/proc/device-tree 相关的 probe 开始异常。

五、窗口初始化与 crtc 创建 #

5.1 vop_create_crtc：plane 与 crtc 的搭建 #

c
static int vop_create_crtc(struct vop *vop)
{
        const struct vop_data *vop_data = vop->data;
        struct device *dev = vop->dev;
        struct drm_device *drm_dev = vop->drm_dev;
        struct drm_plane *primary = NULL, *cursor = NULL, *plane, *tmp;
        struct drm_crtc *crtc = &vop->crtc;
        struct device_node *port;
        int ret, i;

        /* 1. 先建 primary 和 cursor —— drm_crtc_init_with_planes 要用它们
         *    来设置新 crtc 的 possible_crtcs */
        for (i = 0; i < vop_data->win_size; i++) {
                struct vop_win *vop_win = &vop->win[i];
                const struct vop_win_data *win_data = vop_win->data;

                if (win_data->type != DRM_PLANE_TYPE_PRIMARY &&
                    win_data->type != DRM_PLANE_TYPE_CURSOR)
                        continue;
                ret = drm_universal_plane_init(vop->drm_dev, &vop_win->base, 0,
                                               &vop_plane_funcs,
                                               win_data->phy->data_formats,
                                               win_data->phy->nformats,
                                               win_data->phy->format_modifiers,
                                               win_data->type, NULL);
                if (ret)
                        goto err_cleanup_planes;

                plane = &vop_win->base;
                drm_plane_helper_add(plane, &plane_helper_funcs);
                vop_plane_add_properties(plane, win_data);
                if (plane->type == DRM_PLANE_TYPE_PRIMARY)
                        primary = plane;
                else
                        cursor = plane;
        }

        /* 2. 用 primary + cursor 建 crtc */
        ret = drm_crtc_init_with_planes(drm_dev, crtc, primary, cursor,
                                        &vop_crtc_funcs, NULL);
        if (ret)
                goto err_cleanup_planes;
        drm_crtc_helper_add(crtc, &vop_crtc_helper_funcs);

        if (vop->lut_regs) {                            /* gamma LUT */
                drm_mode_crtc_set_gamma_size(crtc, vop_data->lut_size);
                drm_crtc_enable_color_mgmt(crtc, 0, false, vop_data->lut_size);
        }

        /* 3. 建 overlay plane，possible_crtcs 限定到刚建好的 crtc */
        for (i = 0; i < vop_data->win_size; i++) {
                struct vop_win *vop_win = &vop->win[i];
                const struct vop_win_data *win_data = vop_win->data;
                unsigned long possible_crtcs = drm_crtc_mask(crtc);

                if (win_data->type != DRM_PLANE_TYPE_OVERLAY)
                        continue;
                ret = drm_universal_plane_init(vop->drm_dev, &vop_win->base,
                                               possible_crtcs, &vop_plane_funcs,
                                               win_data->phy->data_formats,
                                               win_data->phy->nformats,
                                               win_data->phy->format_modifiers,
                                               win_data->type, NULL);
                if (ret)
                        goto err_cleanup_crtc;
                drm_plane_helper_add(&vop_win->base, &plane_helper_funcs);
                vop_plane_add_properties(&vop_win->base, win_data);
        }

        port = of_get_child_by_name(dev->of_node, "port");   /* 4. 即 vopb_out */
        if (!port) {
                ret = -ENOENT;
                goto err_cleanup_crtc;
        }

        /* 5. fb 引用释放的工作队列 + 完成量 */
        drm_flip_work_init(&vop->fb_unref_work, "fb_unref", vop_fb_unref_worker);
        init_completion(&vop->dsp_hold_completion);
        init_completion(&vop->line_flag_completion);
        crtc->port = port;

        /* 6. 自刷新 helper，失败只打日志不算错 */
        ret = drm_self_refresh_helper_init(crtc);
        if (ret)
                DRM_DEV_DEBUG_KMS(vop->dev, "Failed to init %s with SR helpers %d, ignoring\n",
                                  crtc->name, ret);
        return 0;
err_cleanup_crtc:
        drm_crtc_cleanup(crtc);
err_cleanup_planes:
        list_for_each_entry_safe(plane, tmp, &drm_dev->mode_config.plane_list, head)
                drm_plane_cleanup(plane);
        return ret;
}

顺序不能换的原因在注释里写明了：drm_crtc_init_with_planes() 会把新 crtc 的 mask 写进 primary/cursor plane 的 possible_crtcs，所以它们必须先建；overlay plane 反过来，必须等 crtc 建好，才能用 drm_crtc_mask(crtc) 算出自己只能在哪个 crtc 上用。

第 1 步给 primary/cursor 传的 possible_crtcs 是 0，这不是笔误。0 表示「先不限定」，真正的 mask 由 drm_crtc_init_with_planes() 在建 crtc 时回填。overlay 那一批传的 possible_crtcs 非 0，是因为它们不参与 crtc 初始化，得自己算。

第 4 步的 port 与下一节要讲的 possible_crtcs 是两个方向的线索：crtc 这头把 OF port 记下来，encoder 那头从 OF graph 反推能挂到哪些 crtc，两边在 drm_mode_config_validate() 里交叉检查。

四组回调里只有 8 个函数是真正写硬件的：vop_plane_atomic_update、vop_plane_atomic_disable、vop_crtc_atomic_enable、vop_crtc_atomic_disable、vop_crtc_atomic_begin、vop_crtc_atomic_flush、vop_plane_atomic_async_update、vop_crtc_mode_fixup（改 mode 里的 clock，不碰寄存器）。其余全是把请求转给 helper 或做对象生命周期管理。改 VOP 驱动出问题时，先分清是这 8 个里的哪一个，比读整个文件快。

5.3 plane 的属性 #

vop_plane_add_properties() 在每个 plane 初始化后给它挂属性。RK3399 上挂的几项：

属性 类型 作用
alpha / pixel blend mode range / enum 全局 alpha 值与混合模式（Porter-Duff）
SRC_X / SRC_Y / SRC_W / SRC_H range 源区域，走 VOP_WIN_SET(..., act_info)
zpos range 叠放顺序，由 core 在 normalize_zpos 打开时统一分配
EOTF / color space enum 只在支持 HDR 的 SoC 上挂

属性挂上去的时机有硬要求：必须在对象对用户态可见之前，也就是 drm_dev_register 之前。vop_plane_add_properties 在 vop_create_crtc 里紧接着 drm_universal_plane_init 调，这个位置是对的。

5.5 vop_crtc_atomic_enable：时序真正落下去的地方 #

vop_bind 只把对象建好、寄存器写成初值，屏幕还是黑的。真正把模式写进硬件的是 vop_crtc_atomic_enable，它在 atomic 提交里被调用，顺序上排在 atomic_begin 之后。骨架：

c
static void vop_crtc_atomic_enable(struct drm_crtc *crtc,
                                   struct drm_atomic_state *state)
{
        struct vop *vop = to_vop(crtc);
        const struct vop_data *vop_data = vop->data;
        struct drm_display_mode *mode = &crtc->state->adjusted_mode;
        unsigned long clock = mode->clock * 1000;
        u16 hsync_len = mode->hsync_end - mode->hsync_start;
        u16 hdisplay = mode->hdisplay, htotal = mode->htotal;
        u16 vsync_len = mode->vsync_end - mode->vsync_start;
        u16 vdisplay = mode->vdisplay, vtotal = mode->vtotal;
        u32 val;

        vop_core_clks_enable(vop);           /* hclk/aclk 开 */
        vop_set_dclk(vop, clock);            /* clk_set_rate + clk_prepare_enable */

        if (vop->is_enabled) {
                vop->is_enabled = true;
                goto out;
        }

        VOP_REG_SET(vop, common, dsp_blank, 0);
        VOP_REG_SET(vop, common, overlay_mode, ...);

        if (vop_data->output.hdmi_en)
                VOP_REG_SET(vop, output, hdmi_pin_pol, ...);
        /* ...... 各接口的 dclk_pol / pin_pol 按 connector 类型逐组配 ...... */

        VOP_REG_SET(vop, modeset, vtotal_pw, (vtotal - 1) | ((vtotal - 1 + vsync_len) << 16));
        VOP_REG_SET(vop, modeset, vact_st_end, (vdisplay - 1) | ((vdisplay - 1 + vsync_len) << 16));
        VOP_REG_SET(vop, modeset, htotal_pw, ...);
        VOP_REG_SET(vop, modeset, hact_st_end, ...);

        vop_cfg_done(vop);
        vop->is_enabled = true;
out:
        drm_crtc_vblank_on(crtc);
        vop_core_clks_disable(vop);
}

（各接口的极性配置与 vop_data 里的字段名随 SoC 不同，这里用省略号代替，只保留结构。原稿此处也是分段描述、未给完整函数体。）

这段代码里有四条判断顺序要记牢：

vop_set_dclk 必须在 vop_cfg_done 之前。dclk 是像素时钟，没有它写进时序寄存器也没人来搬数据，硬件会停在等待状态，DSP_HOLD_VALID 永远不来。

if (vop->is_enabled) 那个提前返回是给「模式没变、只是重新提交一次」这种情况用的：时钟已经配好、寄存器已经写好，跳过整段重配，直接 drm_crtc_vblank_on() 收尾。少了这个判断，每次提交都会重配一遍时序，屏幕会闪一下。

drm_crtc_vblank_on(crtc) 要放在硬件真正开起来之后。它在 vop_crtc_enable_vblank 之前调，把这个 crtc 的 vblank 计数从关闭状态恢复；放早了会让用户在硬件还没开始扫描时就收到 vblank 事件。

末尾的 vop_core_clks_disable 不是关掉输出，而是把「临时打开给配置用」的 core 时钟关掉——跟 vop_isr 里那对 vop_core_clks_enable / disable 是同一套动作。dclk 保持开着，因为它由 runtime PM 管，不是这对函数管的。

HACT/HTOTAL 那两个寄存器用 0x1fff1fff 的掩码，低 16 位放起始值、高 16 位放结束值，所以代码里是 (vtotal - 1) | ((vtotal - 1 + vsync_len) << 16) 这种拼法。写反了（把结束值放低位）的表现是画面高度只剩几行、剩下全是黑。

5.6 vop_crtc_atomic_flush：页翻转的收尾 #

atomic_flush 是 commit tail 里对每个被改动的 crtc 调的最后一站，作用是「把这一批 plane 更新一次性推给硬件」：

c
static void vop_crtc_atomic_flush(struct drm_crtc *crtc,
                                  struct drm_atomic_state *state)
{
        struct vop *vop = to_vop(crtc);
        unsigned long flags;

        spin_lock_irqsave(&vop->irq_lock, flags);
        vop->event = crtc->state->event;          /* 挂起 page flip 完成事件 */
        if (vop->event)
                crtc->state->event = NULL;
        spin_unlock_irqrestore(&vop->irq_lock, flags);

        vop_cfg_done(vop);                        /* 让这一批配置生效 */
        vop->is_enabled = true;
}

这里有三件事。第一，crtc->state->event 是用户态申请 page flip 完成通知时带的那个 drm_pending_vblank_event，它从 state 里被「取走」挂到 vop->event 上，等下一次 FS_INTR 时由 vop_handle_vblank 发出去。spin_lock_irqsave(&vop->irq_lock) 是因为中断里也要碰 vop->event，两边必须用同一把锁。

第二，crtc->state->event = NULL 这一句不能漏。它把事件从 state 上摘掉，避免 state 释放时把还没发出去的事件一起回收。

第三，vop_cfg_done(vop) 又一次出现。整个提交路径里它会调两次：atomic_enable 一次（模式重配）、atomic_flush 一次（plane 更新）。两次都是必须的，前一次让时序生效，后一次让图层生效。中间的 atomic_update 只写图层寄存器，不单独提交。

5.7 vop_crtc_atomic_disable：关输出 #

c
static void vop_crtc_atomic_disable(struct drm_crtc *crtc,
                                    struct drm_atomic_state *state)
{
        struct vop *vop = to_vop(crtc);
        int i;

        drm_crtc_vblank_off(crtc);              /* 先停 vblank 事件 */

        for (i = 0; i < vop->data->win_size; i++) {
                struct vop_win *vop_win = &vop->win[i];

                if (!(vop->win_enabled & BIT(i)))
                        continue;
                vop_win_disable(vop, vop_win);
        }
        vop->win_enabled = 0;

        VOP_REG_SET(vop, common, dsp_blank, 1);  /* 输出空白 */
        vop_cfg_done(vop);

        vop->is_enabled = false;
        vop_core_clks_disable(vop);
}

顺序同样是刻意的：先 drm_crtc_vblank_off() 停掉 vblank 事件，否则关的过程中还会有一批 FS 中断进来，drm_crtc_handle_vblank() 在 crtc 已关的情况下被调用会触发 core 里的警告。

win_enabled 位掩码在这里派上用场：只关真正开着的 win，不是无脑关四个。vop_win_disable 会把这一层的 gate 位清掉、dsp_blank 之外的相关位复位，具体字段取决于 vop_data 里 win 那组描述填了什么。

dsp_blank 置 1 是硬件层的空白，不是关时钟。dclk 还开着，只是输出全黑。最终时钟由 runtime PM 在 commit tail 走完之后收。

5.8 vop_plane_atomic_update：图层寄存器怎么写 #

c
static void vop_plane_atomic_update(struct drm_plane *plane,
                                    struct drm_atomic_state *state)
{
        struct drm_plane_state *new_state = plane->state;
        struct vop_win *vop_win = to_vop_win(plane);
        const struct vop_win_data *win = vop_win->data;
        struct vop *vop = to_vop(plane->state->crtc);
        struct drm_framebuffer *fb = new_state->fb;
        struct rockchip_gem_object *rk_obj;
        dma_addr_t yrgb_mst;
        unsigned int actual_w, actual_h;
        unsigned int dsp_stx, dsp_sty;
        uint32_t act_info, dsp_info, dsp_st;
        struct drm_rect *src = &new_state->src;
        struct drm_rect *dst = &new_state->dst;
        uint32_t xdiv, ydiv;
        bool rb_swap;
        int format;

        if (!fb)
                return;

        rk_obj = to_rockchip_obj(fb->obj[0]);
        yrgb_mst = rk_obj->dma_addr + fb->offsets[0];   /* IOMMU 后的地址 */

        actual_w = drm_rect_width(src) >> 16;
        actual_h = drm_rect_height(src) >> 16;
        dsp_stx = dst->x1;
        dsp_sty = dst->y1;

        spin_lock(&vop->reg_lock);

        VOP_WIN_SET(vop, win, yrgb_mst, yrgb_mst);
        VOP_WIN_SET(vop, win, format, format);
        VOP_WIN_SET(vop, win, act_info, act_info);
        VOP_WIN_SET(vop, win, dsp_info, dsp_info);
        VOP_WIN_SET(vop, win, dsp_st, dsp_st);
        /* SCL_FACTOR、ALPHA、COLOR_KEY 等按需设置 ...... */
        VOP_WIN_SET(vop, win, enable, 1);

        spin_unlock(&vop->reg_lock);
}

（act_info / dsp_info / dsp_st 的拼装、xdiv / ydiv 缩放因子、rb_swap 红蓝交换、YUV 格式的 CBR_MST 与 SRC_ALPHA_CTRL 等分支，原稿是按字段逐条描述的，这里压成骨架，只保留寄存器写入的顺序。）

四件事值得看清：

sentinel 判断在第一行：!fb 直接返回，表示这一层没内容。plane 没内容时 atomic_disable 才是该走的路径，atomic_update 里遇到 NULL 说明 core 判定错了，直接返回是最安全的处理。

地址那一句：yrgb_mst = rk_obj->dma_addr + fb->offsets[0]。dma_addr 是 GEM 对象在 IOMMU 地址空间里的首地址（对应 debugfs 里那个 start=00000000），fb->offsets[0] 是这一层（0 号平面）从对象起点算的偏移。多平面格式（NV12 之类）的第二、三平面用 fb->offsets[1]、fb->offsets[2]，走 CBR_MST 那组寄存器。

drm_rect_width(src) >> 16 那个右移：DRM 的 drm_rect 里 source 坐标是 16.16 定点数，整数部分在高 16 位，所以要右移。dst 用的是整数像素坐标，不右移。

spin_lock(&vop->reg_lock) 保护的是这一串 VOP_WIN_SET。它们改的是同一段图层寄存器，跟中断里的 irq_lock 不是一把，跟慢路径的 vop_lock 也不是一把。用错锁的表现是偶发的图层闪烁，不会稳定复现。

5.9 vop_plane_atomic_check：能画什么 #

vop_plane_atomic_check 是整条提交路径上第一个能拒绝请求的地方。它查的东西：

  • 格式是否在 win_data->phy->data_formats 那张表里，不在就 -EINVAL；
  • 源区域是否超出 framebuffer 边界；
  • 缩放比例是否超出硬件能力（VOP1.0 的缩放因子寄存器有精度上限）；
  • 目标区域是否落在这层支持的显示窗口内；
  • YUV 格式时是否走到了不支持 YUV2YUV 的那个窗（RK3399 上 WIN2/WIN3 的 yuv2yuv_data 是空的）。

这四条里最常踩的是第一条和第五条。格式表在 rockchip_vop_reg.c 的 data_formats 数组里，modetest -p 输出那一行 formats: 就是它的运行时投影。第五条的失败表现是「NV12 格式的 video 层能设上去但颜色全绿」，因为 YUV 当 RGB 解了。

6.1 vop_initial：寄存器初值 #

c
static int vop_initial(struct vop *vop)
{
        struct reset_control *ahb_rst;
        int i, ret;

        vop->hclk = devm_clk_get(vop->dev, "hclk_vop");     /* <&cru HCLK_VOP0> */
        vop->aclk = devm_clk_get(vop->dev, "aclk_vop");     /* <&cru ACLK_VOP0> */
        vop->dclk = devm_clk_get(vop->dev, "dclk_vop");     /* <&cru DCLK_VOP0> */

        ret = pm_runtime_resume_and_get(vop->dev);
        ret = clk_prepare(vop->dclk);                  /* dclk 只 prepare，先不开 */
        ret = clk_prepare_enable(vop->hclk);           /* 配寄存器前必须先开 hclk */
        ret = clk_prepare_enable(vop->aclk);           /* 和 aclk */

        ahb_rst = devm_reset_control_get(vop->dev, "ahb");  /* 复位 AHB */
        reset_control_assert(ahb_rst);
        usleep_range(10, 20);
        reset_control_deassert(ahb_rst);

        VOP_INTR_SET_TYPE(vop, clear, INTR_MASK, 1);   /* 清全部中断状态位 */
        VOP_INTR_SET_TYPE(vop, enable, INTR_MASK, 0);  /* 关全部中断使能 */

        for (i = 0; i < vop->len; i += sizeof(u32))    /* 备份整段寄存器 */
                vop->regsbak[i / 4] = readl_relaxed(vop->regs + i);

        VOP_REG_SET(vop, misc, global_regdone_en, 1);
        VOP_REG_SET(vop, common, dsp_blank, 0);

        for (i = 0; i < vop->data->win_size; i++) {    /* 逐 win 配通道、关窗、开 gate */
                struct vop_win *vop_win = &vop->win[i];
                const struct vop_win_data *win = vop_win->data;
                int channel = i * 2 + 1;

                VOP_WIN_SET(vop, win, channel, (channel + 1) << 4 | channel);
                vop_win_disable(vop, vop_win);
                VOP_WIN_SET(vop, win, gate, 1);
        }

        vop_cfg_done(vop);                             /* 让配置生效 */

        vop->dclk_rst = devm_reset_control_get(vop->dev, "dclk");   /* 复位 dclk */
        reset_control_assert(vop->dclk_rst);
        usleep_range(10, 20);
        reset_control_deassert(vop->dclk_rst);

        clk_disable(vop->hclk);                        /* 配完就关，等 enable 时再开 */
        clk_disable(vop->aclk);
        vop->is_enabled = false;
        pm_runtime_put_sync(vop->dev);
        return 0;

err_disable_aclk:      clk_disable_unprepare(vop->aclk);
err_disable_hclk:      clk_disable_unprepare(vop->hclk);
err_unprepare_dclk:    clk_unprepare(vop->dclk);
err_put_pm_runtime:    pm_runtime_put_sync(vop->dev);
        return ret;
}

（每个 devm_clk_get / clk_prepare* / devm_reset_control_get 后面原稿都有 IS_ERR 判断与 goto，目标就是末尾那四个错误标签，顺序与资源申请顺序严格相反。）

两件事：时钟初始化（aclk_vop、dclk_vop、hclk_vop），寄存器配置（底层全是 vop_reg_set）。三处值得记住：

要点 细节
时钟开关时机 配寄存器时 hclk、aclk 必须开着，dclk 只 clk_prepare，像素时钟真正开是在 crtc atomic_enable 时
两次复位 ahb 与 dclk 都是 assert → usleep_range(10, 20) → deassert，必须给硬件留时间
is_enabled 置 false 表示寄存器配好了但输出没开

时钟那份分工要拆开看。hclk_vop 是 AHB 总线时钟，负责让 CPU 的寄存器读写能到达 VOP；aclk_vop 是 AXI 时钟，负责 VOP 去 DDR 取像素数据那一路；dclk_vop 是像素时钟，直接决定出多少像素每秒，它由显示模式算出来，vop_crtc_mode_fixup 里调 clk_set_rate() 设，atomic_enable 里才 enable。三个时钟必须按「hclk 先开、aclk 跟上、dclk 最后」的次序，反了会在配寄存器时总线超时。

两次复位的位置也有讲究：ahb 复位在配寄存器之前，把 VOP 的 AHB 侧逻辑清干净；dclk 复位在 vop_cfg_done 之后，把像素时钟域的逻辑清一遍。usleep_range(10, 20) 这个范围是硬件手册要求的复位保持时间，写成 udelay(10) 也能过，但 usleep_range 在系统负载低时能让出 CPU，是规范写法。

6.2 vop_reg_set：所有寄存器写的唯一出口 #

c
static void vop_reg_set(struct vop *vop, const struct vop_reg *reg, uint32_t _offset,
                        uint32_t _mask, uint32_t v, const char *reg_name)
{
        int offset, mask, shift;

        if (!reg || !reg->mask) {
                DRM_DEV_DEBUG(vop->dev, "Warning: not support %s\n", reg_name);
                return;
        }

        offset = reg->offset + _offset;
        mask = reg->mask & _mask;
        shift = reg->shift;

        if (reg->write_mask) {
                v = ((v << shift) & 0xffff) | (mask << (shift + 16));
        } else {
                uint32_t cached_val = vop->regsbak[offset >> 2];   /* 从影子读 */
                v = (cached_val & ~(mask << shift)) | ((v & mask) << shift);
                vop->regsbak[offset >> 2] = v;                     /* 写回影子 */
        }

        if (reg->relaxed)
                writel_relaxed(v, vop->regs + offset);
        else
                writel(v, vop->regs + offset);
}

#define VOP_REG_SET(vop, group, name, v) \
                    vop_reg_set(vop, &vop->data->group->name, 0, ~0, v, #name)
#define VOP_WIN_SET(vop, win, name, v) \
                    vop_reg_set(vop, &win->phy->name, win->base, ~0, v, #name)
#define VOP_INTR_SET_MASK(vop, name, mask, v) \
                    vop_reg_set(vop, &vop->data->intr->name, 0, mask, v, #name)
#define VOP_INTR_SET_TYPE(vop, name, type, v) \
        do { \
                int i, reg = 0, mask = 0; \
                for (i = 0; i < vop->data->intr->nintrs; i++) { \
                        if (vop->data->intr->intrs[i] & type) { \
                                reg |= (v) << i; \
                                mask |= 1 << i; \
                        } \
                } \
                VOP_INTR_SET_MASK(vop, name, mask, reg); \
        } while (0)

VOP_REG_SET(vop, common, dsp_blank, 0) 展开后就是配 RK3399_DSP_CTRL0 的 bit[19:18] 为 0，因为 rk3399_vop_big.common.dsp_blank 的定义是 VOP_REG(RK3399_DSP_CTRL0, 0x3, 18)。影子寄存器的意义：读改写不用每次回读硬件，也不需要持锁，写出去的永远是一个完整 32 位值。代价是硬件被别的东西改过之后影子会失真——所以 vop_initial 里复位完立刻整体备份一次。

四个宏的分工值得记清：

  • VOP_REG_SET 走 vop->data->group->name，用于那些不在 win 里的全局寄存器组，offset 不加偏移；
  • VOP_WIN_SET 走 win->phy->name，offset 要加 win->base，这是唯一带偏移的一个；
  • VOP_INTR_SET_MASK 走 vop->data->intr->name，额外传一个 mask 收窄；
  • VOP_INTR_SET_TYPE 是最绕的一个：它把「中断类型集合」翻译成「中断位掩码」，遍历 nintrs 个中断位，凡这一位属于 type 集合的，就在 reg 和 mask 里都置上，最后调一次 VOP_INTR_SET_MASK。所以 VOP_INTR_SET_TYPE(vop, clear, INTR_MASK, 1) 的意思是「把所有中断类型的 clear 位置 1」，一次清全部中断状态。

!reg || !reg->mask 那个早退分支是这套表的容错：某颗 SoC 的寄存器表里这一项没填（mask 为 0），写操作直接跳过，只在 debug 日志里提一句。这让同一份 vop_crtc_atomic_enable 代码能跑在寄存器表残缺的老 SoC 上，代价是「这个字段没配」这种问题不会在编译期报出来，只能靠打开 drm.debug 看日志发现。

6.3 vop_cfg_done 与 dsp_hold_completion #

c
static void vop_cfg_done(struct vop *vop)
{
        VOP_REG_SET(vop, common, cfg_done, 1);
}

cfg_done 在 RK3399 的描述表里指向 RK3399_REG_CFG_DONE（偏移 0x0000）。写这一位是「提交配置」的动作，硬件收到之后才把前面写进影子寄存器的整套值加载生效，然后报 DSP_HOLD_VALID 中断。

dsp_hold_completion 这个完成量就是等这个中断的。vop_crtc_atomic_enable 里配好时序之后：

七、中断处理 #

7.1 vop_isr #

c
static irqreturn_t vop_isr(int irq, void *data)
{
        struct vop *vop = data;
        struct drm_crtc *crtc = &vop->crtc;
        uint32_t active_irqs;
        int ret = IRQ_NONE;

        /* 中断和 iommu 共享；vop 不在 runtime-pm 活跃状态说明这次是 iommu 的 */
        if (!pm_runtime_get_if_in_use(vop->dev))
                return IRQ_NONE;

        if (vop_core_clks_enable(vop))
                goto out;

        spin_lock(&vop->irq_lock);      /* 保护 status/enable/clear 三组位 */
        active_irqs = VOP_INTR_GET_TYPE(vop, status, INTR_MASK);
        if (active_irqs)
                VOP_INTR_SET_TYPE(vop, clear, active_irqs, 1);
        spin_unlock(&vop->irq_lock);

        if (!active_irqs)
                goto out_disable;

        if (active_irqs & DSP_HOLD_VALID_INTR) {    /* 配置已生效 */
                complete(&vop->dsp_hold_completion);
                active_irqs &= ~DSP_HOLD_VALID_INTR;
                ret = IRQ_HANDLED;
        }
        if (active_irqs & LINE_FLAG_INTR) {         /* 行标志，用于精确时间戳 */
                complete(&vop->line_flag_completion);
                active_irqs &= ~LINE_FLAG_INTR;
                ret = IRQ_HANDLED;
        }
        if (active_irqs & FS_INTR) {                /* 帧起始，即 vblank */
                drm_crtc_handle_vblank(crtc);
                vop_handle_vblank(vop);
                active_irqs &= ~FS_INTR;
                ret = IRQ_HANDLED;
        }

        if (active_irqs)                            /* 剩下的都是假中断 */
                DRM_DEV_ERROR(vop->dev, "Unknown VOP IRQs: %#02x\n", active_irqs);
out_disable:
        vop_core_clks_disable(vop);
out:
        pm_runtime_put(vop->dev);
        return ret;
}

pm_runtime_get_if_in_use 那个判断是 iommu 共享中断的必要处理：VOP 没开机时这条中断线上只有 iommu 在报事。它返回 0 表示 VOP 当前不在 runtime PM 活跃态，直接 IRQ_NONE 交还给共享线上的另一个 handler，不耗时、不碰寄存器。

vop_core_clks_enable 那一句是中断里临时把 core 时钟打开的兜底：正常情况下 VOP 中断只在 is_enabled 为真时有意义，但某些竞态下（比如刚 disable 完还剩一个 pending 中断）时钟已经关了，这时直接读写寄存器会让总线挂死。这个函数里调 clk_prepare_enable，失败就 goto out，成功则在末尾 out_disable 里关掉。

irq_lock 持锁区间只包住了「读 status + 写 clear」两步，因为这两步必须原子：如果中间被另一个上下文插进来读了 status，第二次读会拿到空的，因为第一次已经清掉了。三组中断位（status、enable、clear）在硬件上是同一批位的三个映射，共用一把锁。

三类中断的处理方式不同：DSP_HOLD_VALID_INTR 和 LINE_FLAG_INTR 都是 complete() 一次完成量，前者用于 atomic_enable 等配置生效，后者用于需要行精度时间戳的场合；FS_INTR 是 vblank，要调 drm_crtc_handle_vblank(crtc) 让 core 更新 vblank 计数并唤醒等待者，再调 vop_handle_vblank(vop) 把挂起的 vblank 事件（page flip 完成通知）发出去。三个 if 是并列的、不是 else if，一次中断里会同时报多个位，所以每个分支都要把自己的位从 active_irqs 里清掉。

最后 if (active_irqs) 那行打 Unknown VOP IRQs，剩下没被认领的位就是「寄存器表里声明了但代码没处理」的中断。这条日志出现本身不致命，但它意味着 vop_data.intr.intrs[] 表跟代码不同步，有中断被白白清掉了。

7.2 vop_crtc_enable_vblank / disable_vblank #

c
static int vop_crtc_enable_vblank(struct drm_crtc *crtc)
{
        struct vop *vop = to_vop(crtc);

        spin_lock(&vop->irq_lock);
        VOP_INTR_SET_TYPE(vop, enable, FS_INTR, 1);
        spin_unlock(&vop->irq_lock);

        return 0;
}

static void vop_crtc_disable_vblank(struct drm_crtc *crtc)
{
        struct vop *vop = to_vop(crtc);

        spin_lock(&vop->irq_lock);
        VOP_INTR_SET_TYPE(vop, enable, FS_INTR, 0);
        spin_unlock(&vop->irq_lock);
}

这两个函数是 core 调过来的，时机是第一个客户端开始等 vblank 时打开、最后一个客户端不再等时关掉。vop_initial 里 VOP_INTR_SET_TYPE(vop, enable, INTR_MASK, 0) 已经把全部中断关了，所以 bind 阶段不会有 vblank 中断冒出来。

complete() 与 drm_crtc_handle_vblank() 的区别要分清：前者是驱动内部等硬件动作，后者是给用户态的 vblank 计数与事件。dsp_hold_completion 只会被 vop_crtc_atomic_enable 里的 wait_for_completion_timeout 消费，line_flag_completion 在需要行级同步的场合消费，这两个都不牵扯用户态。FS_INTR 才跟用户态有关。

7.3 rockchip_drm_dma_init_device 与 IOMMU #

c
void rockchip_drm_dma_init_device(struct drm_device *drm_dev, struct device *dev)
{
        struct rockchip_drm_private *private = drm_dev->dev_private;

        if (!device_iommu_mapped(dev))
                private->iommu_dev = ERR_PTR(-ENODEV);
        else if (!private->iommu_dev)
                private->iommu_dev = dev;
}

只有两句，作用是决定后续 GEM 分配 buffer 时走不走 IOMMU：设备挂了 IOMMU 就把 dev 记下来，否则记一个 -ENODEV 让上层走 CMA 连续内存。

这段被放在 vop_bind 的第九步，看起来跟中断无关，但它是中断与内存之间的纽带：IOMMU 挂在 VOP 的同一条中断线上，所以 vop_isr 才需要 IRQF_SHARED 和 pm_runtime_get_if_in_use 那套判断。设备树里 iommus = <&vopb_mmu> 那一行就是这里判断的依据，少了它 device_iommu_mapped() 返回假，所有 buffer 都退回连续内存分配。

/* 校验 display-subsystem 的 ports 属性是否可用 */
static int rockchip_drm_platform_of_probe(struct device *dev)
{
        struct device_node *np = dev->of_node;
        struct device_node *port;
        bool found = false;
        int i;

        if (!np)
                return -ENODEV;

        for (i = 0;; i++) {
                /* ports = <&vopl_out>, <&vopb_out>，取第 i 个 phandle 的目标节点 */
                port = of_parse_phandle(np, "ports", i);
                if (!port)
                        break;
                if (!of_device_is_available(port->parent)) {   /* 父节点不可用就跳过 */
                        of_node_put(port);
                        continue;
                }
                found = true;
                of_node_put(port);
        }

        if (i == 0) {
                DRM_DEV_ERROR(dev, "missing 'ports' property\n");
                return -ENODEV;
        }
        if (!found) {
                DRM_DEV_ERROR(dev, "No available vop found for display-subsystem.\n");
                return -ENODEV;
        }
        return 0;
}

static int rockchip_drm_platform_probe(struct platform_device *pdev)
{
        struct device *dev = &pdev->dev;
        struct component_match *match = NULL;
        int ret;

        ret = rockchip_drm_platform_of_probe(dev);
        if (ret)
                return ret;

        match = rockchip_drm_match_add(dev);          /* 构建 component_match */
        if (IS_ERR(match))
                return PTR_ERR(match);

        /* 注册 aggregate device，触发 rockchip_drm_ops.bind */
        ret = component_master_add_with_match(dev, &rockchip_drm_ops, match);
        if (ret < 0) {
                rockchip_drm_match_remove(dev);
                return ret;
        }
        return 0;
}

static const struct component_master_ops rockchip_drm_ops = {
        .bind = rockchip_drm_bind,
        .unbind = rockchip_drm_unbind,
};

rockchip_drm_match_add 遍历 rockchip_sub_drivers[]，对每个驱动用 platform_find_device_by_driver() 找出所有实例，对每个实例先 device_link_add(dev, d, DL_FLAG_STATELESS) 再 component_match_add(dev, &match, component_compare_dev, d)。device_link_add() 这一句容易被忽略：它给 master 和每个 component 之间拉了条设备链接，让 PM 顺序有保证——子设备不会在 master 之前被挂起。

rockchip_drm_platform_of_probe 的两条失败路径对应两种配置错误：i == 0 是 ports 属性完全没写，!found 是写了但指向的 VOP 节点全都 status = "disabled"。两者的 dmesg 完全不一样，看日志能直接定位到设备树哪一行。

component_compare_dev 是匹配函数，比较 struct device 指针相等。用它而不是 component_compare_of，是因为这里已经用 platform_find_device_by_driver() 找到了具体实例，按指针比最直接。

8.3 component 框架的三段式 #

component 框架把「一个虚拟设备由多个物理设备拼成」这件事拆成三段：

阶段 谁做 做什么
登记 每个子驱动 probe component_add(dev, &ops)，把 ops（含 bind/unbind）挂到自己设备上
聚合 master probe component_master_add_with_match()，用一个 match 列表声明「我要哪些 component」
触发 内核 每次有 component 登记或 master 登记，检查 match 是否已全部满足，满足就按 match 顺序逐个调 bind

VOP 的 vop_probe 是第一步，rockchip_drm_platform_probe 是第二步，第三步由 component 核心在 try_to_bring_up_aggregate_device() 里自动做。全部 component 到齐前，谁都不做事，所以 VOP 的 bind 比 vop_probe 晚几百毫秒甚至几秒，取决于 HDMI PHY 什么时候就绪。

component_bind_all(parent, data) 的路径是 parent → __aggregate_find() 找到 aggregate_device → adev->match->compare[i].component，然后对每个非 duplicate 的 component 调 component_bind(c, adev, data)，也就是它的 bind 回调。失败时反序 component_unbind 已 bind 的部分，不留半截状态。

顺序由 match 的构造顺序决定，也就是 rockchip_sub_drivers[] 的数组顺序——VOP 在最前面，所以 VOP 的 crtc 先建，接口驱动的 encoder/connector 后建。这个顺序是刻意的：connector 的 best_encoder 回调要靠 crtc mask 算。如果反过来让 HDMI 先 bind，它调 drm_of_find_possible_crtcs() 时 crtc->port 还没设好，拿到的是空 mask，结果是 encoder 挂不到任何 crtc，屏幕永远亮不了。

8.4 rockchip_drm_bind：十二步 #

c
static int rockchip_drm_bind(struct device *dev)
{
        struct drm_device *drm_dev;
        struct rockchip_drm_private *private;
        int ret;

        /* 1. 踢掉占着 framebuffer 内存的旧驱动 */
        ret = drm_aperture_remove_framebuffers(false, &rockchip_drm_driver);
        if (ret)
                return ret;

        /* 2. 分配并初始化 drm_device */
        drm_dev = drm_dev_alloc(&rockchip_drm_driver, dev);
        if (IS_ERR(drm_dev))
                return PTR_ERR(drm_dev);

        dev_set_drvdata(dev, drm_dev);                 /* 3. 设备私有数据指向 drm_dev */

        /* 4. 分配 rockchip_drm_private */
        private = devm_kzalloc(drm_dev->dev, sizeof(*private), GFP_KERNEL);
        if (!private) {
                ret = -ENOMEM;
                goto err_free;
        }
        drm_dev->dev_private = private;

        /* 5. 初始化 mode_config */
        ret = drmm_mode_config_init(drm_dev);
        if (ret)
                goto err_free;
        rockchip_drm_mode_config_init(drm_dev);

        /* 6. 按顺序 bind 所有显示子系统组件 */
        ret = component_bind_all(dev, drm_dev);
        if (ret)
                goto err_free;

        ret = rockchip_drm_init_iommu(drm_dev);        /* 7. IOMMU */
        if (ret)
                goto err_unbind_all;

        ret = drm_vblank_init(drm_dev, drm_dev->mode_config.num_crtc);   /* 8. vblank */
        if (ret)
                goto err_iommu_cleanup;

        drm_mode_config_reset(drm_dev);                /* 9. 重置模式配置 */
        drm_kms_helper_poll_init(drm_dev);             /* 10. HPD 轮询 */

        ret = drm_dev_register(drm_dev, 0);            /* 11. 注册 DRM 设备 */
        if (ret)
                goto err_kms_helper_poll_fini;

        drm_fbdev_generic_setup(drm_dev, 0);           /* 12. fbdev 兼容层 */
        return 0;

err_kms_helper_poll_fini:
        drm_kms_helper_poll_fini(drm_dev);
err_iommu_cleanup:
        rockchip_iommu_cleanup(drm_dev);
err_unbind_all:
        component_unbind_all(dev, drm_dev);
err_free:
        drm_dev_put(drm_dev);
        return ret;
}

第一步为什么要踢人：一块图形设备上不止一个驱动能跑，但同一时刻只能有一个活着。很多系统在启动早期加载通用图形驱动（EFI-GOP 或 VESA），到后面引导阶段要用专用驱动替换，专用驱动要接管设备，第一步就得把通用的那个踹下去。DRM aperture 这套 API 就是管「谁拥有 framebuffer 内存、什么时候交接」的。

8.4.1 十二步之间的依赖 #

十二步不是随便排的，每一对相邻步骤都有依赖：

步 依赖前一步的原因
1 → 2 旧的 framebuffer 驱动必须先让出内存区域，drm_dev_alloc 才能安全建 GEM 结构
2 → 4 private 用 drm_dev->dev 做父设备分配，没有 drm_dev 就没有父设备
4 → 6 vop_bind 里 rockchip_drm_dma_init_device 要写 private->iommu_dev
5 → 6 vop_create_crtc 调的 drm_crtc_init_with_planes 依赖 mode_config 已初始化
6 → 7 rockchip_drm_init_iommu 要等所有 component 都拿到自己的 IOMMU
6 → 8 drm_vblank_init 要 num_crtc，这个数由 component bind 时建出几个 crtc 决定
8 → 11 drm_dev_register 前的 mode_config_validate 会数 crtc 和 primary plane
11 → 12 drm_fbdev_generic_setup 要求设备已注册，否则 fbdev 客户端没法挂上去

第 9 步的 drm_mode_config_reset 值得单说：它遍历四类对象，逐个调各自的 reset 回调。VOP 的 vop_crtc_reset 和 drm_atomic_helper_plane_reset 在这里把每个对象的状态恢复到初始值。漏了这一句的表现是 bootloader 留下的 fb 在 framebuffer 列表里找不到对应的 state，第一次 atomic 提交直接崩。

8.5 deferred probe #

这条链路依赖很重：VOP 需要时钟、复位、电源域、IOMMU 全部就绪；HDMI 需要 PHY、DDC、桥接芯片就绪。任何一环没好，整个 bind 就失败。

DRM 驱动借的是内核的 deferred probe 机制：发现依赖资源没就绪就返回 -EPROBE_DEFER（数值 -517），退出，内核过一阵再试，直到依赖齐了、驱动加载成功。所以调试时 dmesg 里出现 -517 不是错误，是排队。真正要盯的是同一行反复出现几百次——那说明某个依赖永远不会就绪，比如某个 status = "disabled" 的节点。

deferred probe 还有一个副作用要知道：它给每个驱动的重试次数是无限的，但每次重试都会在 dmesg 里留一行 probe of xxx deferred。系统里几十个驱动都 defer 的时候，这几十行会把真正的错误淹掉。查的时候用 dmesg | grep -c deferred 比一行行翻快，再看哪个 probe 的 defer 次数最多。

九、显示通路的建立：从 VOP 到接口 #

9.1 从设备树到 DRM 连接 #

vopb_out_hdmi 和 hdmi_in_vopb 通过 remote-endpoint 互相指向，OF graph 解析会从 crtc 的 port 出发一路走到 connector。内核里走的是 drm_of.c 那套接口：vop_create_crtc() 里 crtc->port = port，把 crtc 和 OF port 绑上；encoder 的 bind 里调 encoder->possible_crtcs = drm_of_find_possible_crtcs(drm, dev->of_node)，反过来算出自己能被哪些 crtc 驱动。possible_crtcs 是位掩码，一位对应一个 crtc，RK3399 两个 VOP 时无脑接全部就是 0x3。

9.2 从板级数据看连接 #

bash
root@rk3399:/# killall Xorg & modetest -M rockchip -e
Encoders:
id      crtc    type    possible crtcs  possible clones
51      37      TMDS    0x00000003      0x00000001

possible_crtcs = 0x3 表示这个 encoder 能挂到 id 37 和 44 两个 crtc 的任意一个上，也就是 VOP_BIG 或 VOP_LIT，当前接的是 37。这个值是 dw_hdmi_rockchip_bind() 里用 drm_of_find_possible_crtcs(drm, dev->of_node) 直接算出来设的。

possible clones = 0x1 表示这个 encoder 只有自己一个克隆体，没有第二个 encoder 能跟它同时输出同一画面。RK3399 上 VOP 不支持 clone 输出，这个值就是固定的。

9.3 显示通路三段的建立时机 #

text
设备树就绪
  ├─ VOP probe → component 登记
  ├─ HDMI probe → component 登记
  └─ display-subsystem probe → component_match 构造
       → component_bind_all
            ├─ vop_bind
            │    ├─ vop_create_crtc
            │    │    ├─ drm_universal_plane_init × 4      plane

关键点：crtc->port 在 crtc 层设，possible_crtcs 在 encoder 层算，这两条线在 drm_mode_config_validate() 里被交叉检查——plane 的 possible_crtcs 必须包含它挂的 crtc，encoder 的 possible_crtcs 不能是空的。任何一条对不上，注册前就会 WARN。

三段建立完之后，显示通路只是「结构上通了」，硬件还是灭的。真正出图要等用户态发 atomic 提交，走 vop_crtc_mode_fixup（算 dclk）→ vop_crtc_atomic_check（查能力）→ vop_crtc_atomic_enable（开时钟、写时序、vop_cfg_done）→ vop_plane_atomic_update（配 win）这一串。

9.4 display_subsystem 节点 #

dts
display_subsystem: display-subsystem {
        compatible = "rockchip,display-subsystem";
        ports = <&vopl_out>, <&vopb_out>;
};

这个节点就是 Rockchip DRM 主设备，也就是 component 框架里的 aggregate device，一个虚拟设备，唯一作用是列出组成图形子系统的所有 vop 与显示接口节点。ports 列出指向各 vop 的 phandle，vopl_out 对应 VOP_LITE，vopb_out 对应 VOP_BIG。

为什么是「虚拟设备」：它没有 reg、没有寄存器窗口、没有中断，platform_driver 的 probe 里也不碰硬件。它的存在价值就两个：给 component_master_add_with_match 提供一个 host 设备，给 drm_dev_set_unique() 提供一个名字来源。debugfs 里 dri/0/name 那一行的 unique=display-subsystem 就是从这个节点的 dev_name 来的。

ports 属性的顺序不影响 bind 顺序——bind 顺序由 rockchip_sub_drivers[] 决定。但它的顺序影响 rockchip_drm_platform_of_probe 的遍历，只影响「找不找得到可用的 VOP」，不影响结果。

板级 dts 要启用整条链路，四个节点一起开：

dts
&vopb { status = "okay"; };
&vopb_mmu { status = "okay"; };
&vopl { status = "okay"; };
&vopl_mmu { status = "okay"; };
&display_subsystem { status = "okay"; };

只开 display_subsystem 不开 VOP，rockchip_drm_platform_of_probe 会走到 !found 那条分支打 No available vop found for display-subsystem.，整条 DRM 不加载。
