一、framebuffer 是什么：一块可以直接写的显存 #

一句话：framebuffer 就是内核划出来的一块内存，用户进程往里面写像素，显示控制器自己把它扫到屏上。

拆开看这块内存里装什么。LCD 屏是一堆像素点，S3C2440 的 LCD 控制器外接屏幕，每来一个 VCLK，就从左到右送一个像素的颜色出去；HSYNC 每来一个脉冲，跳到下一行；VSYNC 每来一个脉冲，回到左上角原点。像素的颜色从内存里取，这块内存就是 framebuffer。嵌入式板子上没有独立显存，从 SDRAM 里切一块充当。

R、G、B 三组数据线决定颜色，位宽由屏和控制器共同约定。T35 屏是 240×320 像素、RGB565，即 R 占 5 位、G 占 6 位、B 占 5 位，一个像素 2 字节。

framebuffer 被注册成一个标准字符设备，主设备号 29（FB_MAJOR），次设备号按缓冲区编号分配，设备文件是 /dev/fb0、/dev/fb1……用户侧拿到的是 read、write、mmap、ioctl 这几个入口。

这带来一个很实际的结论：有了 framebuffer，图形界面（GUI/X/fbcon）就不用关心底层是哪个 LCD 控制器。同一份 mmap 加写显存的代码，换一块屏、换一个 SoC 也能跑。

如果你觉得「framebuffer 设备」这个叫法别扭，把它当 LCD 设备理解就行，它们的差别只在抽象层级。

单纯按字符设备手写一套也能做出来：申请设备号、填 file_operations、创建设备节点、实现 open/write。问题在多个显示设备共存的时候，几个设备只有分辨率、时序参数不同，操作函数基本一样。C 没有继承，内核用的是结构体加函数指针这层抽象：每个显示设备用一个 fb_info 描述，共性逻辑全在 fbmem.c，差异全在驱动里填的 fb_info 和 fb_ops。

二、fbdev 框架的历史地位 #

fbdev 能活二十年，靠的是简单。它只有两个文件在支撑整条通路：

  • drivers/video/fbdev/core/fbmem.c：向上给应用提供系统调用入口（fb_fops），向下给硬件提供注册接口（register_framebuffer）。
  • xxxfb.c：具体驱动，干的活就是填 fb_info 然后注册。

架构图在原始抓取稿里丢了，文字描述是这样的：应用层 open/write/mmap 走到 fb_fops，fb_fops 再按次设备号从 registered_fb[] 里捞出对应的 fb_info，最后转给 fb_info->fbops 里的回调。硬件相关的部分与字符设备操作彻底分离，内核代码稳定性因此好很多。

fbmem_init() 干的事就三件：

c
static int __init
fbmem_init(void)
{
        int ret;

        if (!proc_create_seq("fb", 0, NULL, &proc_fb_seq_ops))
                return -ENOMEM;

        ret = register_chrdev(FB_MAJOR, "fb", &fb_fops);
        if (ret) {
                printk("unable to get major %d for fb devs\n", FB_MAJOR);
                goto err_chrdev;
        }

        fb_class = class_create(THIS_MODULE, "graphics");
        if (IS_ERR(fb_class)) {
                ret = PTR_ERR(fb_class);
                pr_warn("Unable to create fb class; errno = %d\n", ret);
                fb_class = NULL;
                goto err_class;
        }

        fb_console_init();

        return 0;

err_class:
        unregister_chrdev(FB_MAJOR, "fb");
err_chrdev:
        remove_proc_entry("fb", NULL);
        return ret;
}

顺序是：建 /proc/fb，注册主设备号 29 的 fb 字符设备并挂上 fb_fops，建 /sys/class/graphics 类，初始化 fbcon。注意这里只建了类，没有建设备节点，/dev/fb0 是后面 register_framebuffer() 里建的。

fbdev 的能力边界很清楚：它只管「一块显存 + 一套固定格式 + 几个 2D 绘制回调」。没有显存管理器，没有多平面合成，没有原子提交，没有通用对象模型。X11 时代够用，Wayland 和 GPU 渲染管线起来以后就不够了。

内核版本现状：CONFIG_DRM_FBDEV_EMULATION 让 DRM 驱动同时导出一个 /dev/fb0 给老应用用，这是旧接口延续生命的唯一方式。上游对 fbdev 的定位是「不再接受新用户」，已有驱动沿用。本篇的代码可以编译、可以跑，拿来理解「显存是怎么被写进屏幕的」有价值，拿来给新板子写驱动没有价值。

三、fbdev 与 DRM 的关系 #

两者不是替换与被替换那么简单，是两代抽象模型。

维度 fbdev DRM/KMS
引入年代 2.0 前后，1990 年代 2000 年代中期起，4.x 后成为主路径
设备节点 /dev/fb0（主 29） /dev/dri/card0、/dev/dri/renderD128
核心对象 只有一个 fb_info crtc、encoder、connector、plane、framebuffer、gem 对象
显存管理 驱动自己 dma_alloc_wc 一块 GEM/TTM，支持共享、导入导出
多平面 不支持 plane 原生支持叠加层
模式设置 ioctl(FBIOPUT_VSCREENINFO) 直接改 atomic commit，整帧一起生效
双缓冲 FBIOPAN_DISPLAY 硬切 offset 翻页由 DRM 提交序列完成
缓冲共享 无，只能自己 mmap 自己 dma-buf 跨设备共享
与 GPU 的关系 无 渲染与显示在同一套对象模型里
现在的分工 仅兼容层（fbdev-emulation） 新硬件的唯一路径

演进原因不复杂，三条：

一、fbdev 把「显存」和「显示控制器」焊死在一起。要换分辨率就得改显存布局，要双缓冲就得改 yoffset，应用和驱动之间靠约定，不靠接口。

二、没有对象模型就没法描述现代显示管线。一颗 SoC 里 VOP 有多个图层、HDMI 和 eDP 是两个独立 connector、每个 connector 有自己的 EDID 和模式列表。这些在 fbdev 里没有落脚点，只能塞进驱动的私有结构。

三、没有 buffer 共享就没有零拷贝。GPU 渲染完的画面要直接上屏，得让 GPU 和显示控制器看到同一块物理内存，fbdev 没有语言描述这件事，FBINFO_HIDE_SMEM_START 这个标志就是给 DRM 驱动用的，用来阻止用户程序绕过内核去共享缓冲区。

交接点在哪：同一个物理 framebuffer，老应用通过 /dev/fb0 写，DRM 驱动通过 drm_fbdev 把这块缓冲区包成 DRM framebuffer 对象。两套接口指向同一块显存，这就是 emulation 层的做法。第十八章会展开迁移。

四、fb_info：framebuffer 的核心结构 #

struct fb_info 定义在 include/linux/fb.h，一个显示设备对应一个实例。

c
struct fb_info {
        atomic_t count;
        int node;
        int flags;
        /*
         * -1 by default, set to a FB_ROTATE_* value by the driver, if it knows
         * a lcd is not mounted upright and fbcon should rotate to compensate.
         */
        int fbcon_rotate_hint;

        struct mutex mm_lock;           /* Lock for fb_mmap and smem_* fields */

        struct work_struct queue;       /* Framebuffer event queue */
        struct fb_pixmap pixmap;        /* Image hardware mapper */
        struct fb_pixmap sprite;        /* Cursor hardware mapper */
        struct fb_cmap cmap;            /* Current cmap */
        struct list_head modelist;      /* mode list */
        struct fb_videomode *mode;      /* current mode */

#if IS_ENABLED(CONFIG_FB_BACKLIGHT)
        struct backlight_device *bl_dev;

#endif

        struct device *dev;             /* This is this fb device */
        int class_flag;                    /* private sysfs flags */
#ifdef CONFIG_FB_TILEBLITTING
        struct fb_tile_ops *tileops;    /* Tile Blitting */
#endif
        union {
                char __iomem *screen_base;      /* Virtual address */
                char *screen_buffer;
        };
        unsigned long screen_size;      /* Amount of ioremapped VRAM or 0 */
        void *pseudo_palette;           /* Fake palette of 16 colors */

                unsigned int count;
                struct aperture {

关键字段逐个过一遍：

字段 含义 谁填
count 引用计数，fb_open 加一、fb_release 减一，归零才销毁 内核在 do_register_framebuffer 里置 1
node 在全局数组 registered_fb[] 里的下标，即次设备号 注册时分配
flags FBINFO_* 位标志，管硬件加速、大小端、显存位置 驱动
lock / mm_lock 分别保护 open/release/ioctl 与 mmap/smem 字段 注册时 mutex_init
var 可变参数：分辨率、BPP、时序、调色板位域 驱动填初值，应用可 FBIOPUT_VSCREENINFO 改
fix 不可变参数：显存物理地址、长度、行宽、视觉类型 驱动填，用户层不能改
monspecs 显示器参数，来自 EDID 解析 一般驱动不填
queue 事件队列工作项 内核
pixmap / sprite 像素图与光标图的影子缓冲，注册时默认申请 注册时按需分配
cmap 设备无关调色板，走 FBIOGETCMAP/FBIOPUTCMAP 应用 ioctl
modelist / mode 由 var 转换出的 video mode 链表与当前 mode 注册时 fb_var_to_videomode
bl_dev / bl_curve 背光设备与背光曲线，要求注册前就初始化好 驱动
fbops 操作回调表，见第五章 驱动
device 父设备，sysfs 里体现为 /sys/devices/.../fb0 framebuffer_alloc 的第二个参数
dev fb 自己的设备对象，注册时创建 内核
screen_base 显存虚拟地址，物理地址在 fix.smem_start 驱动分配后填
screen_size 显存大小，为 0 时回退用 fix.smem_len 驱动
pseudo_palette 伪调色板，16 色 驱动
state 硬件状态，FBINFO_STATE_RUNNING 或 SUSPENDED 内核在 suspend/resume 时改
fbcon_par fbcon 专用私有区 内核
par 驱动私有数据起始地址，由 framebuffer_alloc 的 size 参数决定大小 驱动
apertures 显存对应的 PCI 或类似地址窗口，用于抢占冲突检查 驱动
skip_vt_switch 唤醒时不切 VT 驱动

par 这个字段值得单独说。framebuffer_alloc(sizeof(struct s3c2410fb_info), &pdev->dev) 一次性分配 fb_info 加上指定大小的私有区，私有区紧跟在结构体后面，info->par 指向它。驱动把自己的状态全塞进去，不用第二次分配。

flags 的位定义：

c
/* FBINFO_* = fb_info.flags bit flags */
#define FBINFO_DEFAULT          0
#define FBINFO_HWACCEL_DISABLED 0x0002
#define FBINFO_VIRTFB           0x0004 /* FB is System RAM, not device. */
#define FBINFO_PARTIAL_PAN_OK   0x0040 /* otw use pan only for double-buffering */
#define FBINFO_READS_FAST       0x0080 /* soft-copy faster than rendering */

#define FBINFO_HWACCEL_NONE             0x0000
#define FBINFO_HWACCEL_COPYAREA         0x0100 /* required */
#define FBINFO_HWACCEL_FILLRECT         0x0200 /* required */
#define FBINFO_HWACCEL_IMAGEBLIT        0x0400 /* required */
#define FBINFO_HWACCEL_ROTATE           0x0800 /* optional */
#define FBINFO_HWACCEL_XPAN             0x1000 /* optional */
#define FBINFO_HWACCEL_YPAN             0x2000 /* optional */
#define FBINFO_HWACCEL_YWRAP            0x4000 /* optional */

#define FBINFO_MISC_USEREVENT          0x10000 /* event request from userspace */
#define FBINFO_MISC_TILEBLITTING       0x20000 /* use tile blitting */
#define FBINFO_MISC_ALWAYS_SETPAR      0x40000
#define FBINFO_MISC_FIRMWARE           0x80000
#define FBINFO_FOREIGN_ENDIAN         0x100000
#define FBINFO_BE_MATH                0x100000
#define FBINFO_HIDE_SMEM_START        0x200000

语义是：置了加速位就等于声明「这个操作我硬件能做」，没置也能工作，走软件实现。FBINFO_HWACCEL_DISABLED 反过来，强制关掉硬件加速，让 copyarea/fillrect/imageblit 全部退回软件。

FBINFO_MISC_ALWAYS_SETPAR 是个调试用开关，置上之后每次 fbcon 切换都调一次 fb_check_var/set_par，代价是切换变慢，好处是能排除「X 和 fbcon 抢硬件状态」类问题。注释里写得很直白，就是给这种事准备的工具。

S3C2440 板上老驱动常用 FBINFO_FLAG_DEFAULT。这个宏定义在 include/uapi/linux/fb.h 里，旧内核里是 0 的别名，跟 FBINFO_DEFAULT 等价。

fb_info 里最容易被误用的两个字段：

  • screen_base 是 char __iomem *，意味着 CPU 写它不经过 cache（dma_alloc_wc 拿到的映射本身就带这种属性）。写成普通指针不会立刻出错，但在某些平台会因为 cache 未刷回导致屏幕出现残影。
  • screen_size 为 0 时，fb_read/fb_write 会退回 fix.smem_len。驱动只填一个的话别填错，两个字段语义不同。

五、fb_ops：驱动要实现的回调 #

struct fb_ops 是驱动真正要写的东西。所有函数都必须在持有 console semaphore 的情况下调用（这是 2.6 时代的注释，现在实际锁语义在 fbmem.c 里按 info->lock 组织），但 fb_debug_enter/fb_debug_leave 例外，这两个要在无锁状态下直接写硬件。

c

                            size_t count, loff_t *ppos);

        int (*fb_setcmap)(struct fb_cmap *cmap, struct fb_info *info);

        int (*fb_blank)(int blank, struct fb_info *info);
        int (*fb_pan_display)(struct fb_var_screeninfo *var, struct fb_info *info);

        void (*fb_fillrect) (struct fb_info *info, const struct fb_fillrect *rect);
        void (*fb_copyarea) (struct fb_info *info, const struct fb_copyarea *region);
        void (*fb_imageblit) (struct fb_info *info, const struct fb_image *image);

        int (*fb_cursor) (struct fb_info *info, struct fb_cursor *cursor);

        int (*fb_sync)(struct fb_info *info);

        int (*fb_ioctl)(struct fb_info *info, unsigned int cmd,

                        unsigned long arg);

        int (*fb_mmap)(struct fb_info *info, struct vm_area_struct *vma);

        void (*fb_get_caps)(struct fb_info *info, struct fb_blit_caps *caps,
                            struct fb_var_screeninfo *var);

哪些必须实现，哪些可以不写，放张表：

回调 必要性 作用 S3C2440 里怎么填
owner 必填 模块引用，try_module_get 用 THIS_MODULE
fb_check_var 强烈建议 校验并修正 var，不改 par 自己写，或缺省也行
fb_set_par 建议 按 info->var 重新编程硬件 s3c2410fb_set_par
fb_setcolreg 16 色以下必填 设置调色板单色 手写 chan_to_field 版
fb_setcmap 可选 批量设调色板 不填，走默认
fb_blank 可选 关屏/省电 可挂背光控制
fb_pan_display 双缓冲要填 换显存起始偏移 写 LCDSADDR 或改 yoffset
fb_fillrect 必填 填充矩形 cfb_fillrect
fb_copyarea 必填 区域拷贝 cfb_copyarea
fb_imageblit 必填 贴图/画字 cfb_imageblit
fb_cursor 可选 硬件光标 不填
fb_sync 可选 等 blit 空闲 不填
fb_ioctl 可选 私有 ioctl 不填
fb_mmap 可选 自定义 mmap 不填，走 fbmem 默认
fb_open / fb_release 可选 使用计数、上下电 不填
fb_read / fb_write 可选 非正常布局的访问 不填，走默认拷贝
fb_destroy 可选 释放资源 不填，framebuffer_release 处理
fb_debug_enter / leave 可选 KDB 进出时准备控制台 不填

三个绘制回调是核心。cfb_* 系列是内核提供的通用软件实现，在 drivers/video/fbdev/core/ 下：

  • cfbfillrect.c → cfb_fillrect
  • cfbcopyarea.c → cfb_copyarea
  • cfbimgblt.c → cfb_imageblit

它们靠 var 里的 red/green/blue 三个 fb_bitfield 做像素格式换算，所以你只要把 var 的位域填对，这三个函数对 RGB565、RGB888、灰度都能正确工作。S3C2440 的驱动一律直接挂这三个，不写硬件加速版本，一是这颗芯片没有 2D 加速器，二是软件实现够快。

不填 fb_fillrect/fb_copyarea/fb_imageblit 会怎样？fbmem 不做兜底，fbcon 画字的地方会直接解引用空指针。这三个是必填项，别省。

六、fbdev 的注册流程 #

注册一个 framebuffer 设备，主轴只有一个函数：register_framebuffer()。它加锁后调 do_register_framebuffer()：

c
int
register_framebuffer(struct fb_info *fb_info)
{
        int ret;

        mutex_lock(&registration_lock);
        ret = do_register_framebuffer(fb_info);
        mutex_unlock(&registration_lock);

        return ret;
}

registration_lock 是个全局互斥锁，说明这个操作全局串行。真正干活在 do_register_framebuffer：

c
static int do_register_framebuffer(struct fb_info *fb_info)
{
        int i, ret;
        struct fb_event event;
        struct fb_videomode mode;

        if (fb_check_foreignness(fb_info))
                return -ENOSYS;

        ret = do_remove_conflicting_framebuffers(fb_info->apertures,
                                                 fb_info->fix.id,
                                                 fb_is_primary_device(fb_info));
        if (ret)
                return ret;

        if (num_registered_fb == FB_MAX)   /* 已达到最大注册设备数 */
                return -ENXIO;

        num_registered_fb++;               /* 已注册设备计数+1 */
        for (i = 0 ; i < FB_MAX; i++)      /* 查找空的数组项 */
                if (!registered_fb[i])
                        break;
        fb_info->node = i;               /* fb_info 在 registered_fb 数组中的索引 */
        atomic_set(&fb_info->count, 1);  /* 引用计数设置为1 */
        mutex_init(&fb_info->lock);      /* 初始化互斥锁 */
        mutex_init(&fb_info->mm_lock);   /* 初始化互斥锁 */

        fb_info->dev = device_create(fb_class, fb_info->device,  /* 设备节点在这里创建 */
                                     MKDEV(FB_MAJOR, i), NULL, "fb%d", i);
        if (IS_ERR(fb_info->dev)) {
                /* Not fatal */
                printk(KERN_WARNING "Unable to create device for framebuffer %d; errno = %ld\n", i, PTR_ERR(fb_info->dev));
                fb_info->dev = NULL;
        } else
                fb_init_device(fb_info);  /* 初始化fb_info部分参数 */

        if (fb_info->pixmap.addr == NULL) {
                fb_info->pixmap.addr = kmalloc(FBPIXMAPSIZE, GFP_KERNEL);
                if (fb_info->pixmap.addr) {
                        fb_info->pixmap.size = FBPIXMAPSIZE;
                        fb_info->pixmap.buf_align = 1;
                        fb_info->pixmap.scan_align = 1;
                        fb_info->pixmap.access_align = 32;
                        fb_info->pixmap.flags = FB_PIXMAP_DEFAULT;
                }
        }
        fb_info->pixmap.offset = 0;

        if (!fb_info->pixmap.blit_x)
                fb_info->pixmap.blit_x = ~(u32)0;

        if (!fb_info->pixmap.blit_y)
                fb_info->pixmap.blit_y = ~(u32)0;

        if (!fb_info->modelist.prev || !fb_info->modelist.next)
                INIT_LIST_HEAD(&fb_info->modelist);

        if (fb_info->skip_vt_switch)
                pm_vt_switch_required(fb_info->dev, false);
        else
                pm_vt_switch_required(fb_info->dev, true);

        fb_var_to_videomode(&mode, &fb_info->var);
        fb_add_videomode(&mode, &fb_info->modelist);
        registered_fb[i] = fb_info;                            /* 设置数组第i个元素 */

        event.info = fb_info;
        if (!lockless_register_fb)
                console_lock();
        else
                atomic_inc(&ignore_console_lock_warning);
        if (!lock_fb_info(fb_info)) {
                ret = -ENODEV;
                goto unlock_console;
        }
        ret = 0;

        fb_notifier_call_chain(FB_EVENT_FB_REGISTERED, &event);
        unlock_fb_info(fb_info);
unlock_console:
        if (!lockless_register_fb)
                console_unlock();
        else
                atomic_dec(&ignore_console_lock_warning);
        return ret;
}

按执行顺序拆成七步：

  1. fb_check_foreignness 校验大小端，不一致直接 -ENOSYS。
  2. do_remove_conflicting_framebuffers 按 apertures 地址范围踢掉冲突的旧 framebuffer。这一层是为了让 DRM 驱动能顶掉 firmware 留下的 simplefb。
  3. 在 registered_fb[FB_MAX] 里找空位，把下标写进 node。这个下标就是 /dev/fb%d 的 %d。
  4. device_create 建 /dev/fb%d 节点，走 fb_class；失败只是警告，不算致命。
  5. 给 pixmap 分配影子缓冲（FBPIXMAPSIZE），把 blit_x/blit_y 置全 1 表示「任意尺寸都支持」。
  6. fb_var_to_videomode 把当前 var 转成一条 mode 存进 modelist，供 fbcon 和 fbset 查询。
  7. 拿 console 锁，发 FB_EVENT_FB_REGISTERED 通知链，fbcon 就在这条链上接管这块屏。

用户态操作的完整通路，从 fb_fops 看最清楚：

        .owner =        THIS_MODULE,

fb_open 的动作：取次设备号 → get_fb_info 从 registered_fb[] 取出 fb_info 并 atomic_inc 引用计数 → try_module_get(fbops->owner) → file->private_data = info → 调驱动的 fb_open（如果填了）。get_fb_info 失败时会先 request_module("fb%d", fbidx) 再取一次，/dev/fb0 在但模块没加载时内核会自动 modprobe 一遍。

fb_read/fb_write 给驱动留了覆盖点，驱动没填就走通用的按页拷贝。核心逻辑就是「按 PAGE_SIZE 分块，fb_memcpy_fromfb/fb_memcpy_tofb 在显存和临时缓冲之间搬，再用 copy_to_user/copy_from_user 过用户态这一层」：

                return info->fbops->fb_read(info, buf, count, ppos);

        total_size = info->screen_size;
        if (total_size == 0)
                total_size = info->fix.smem_len;
        ...
        src = (u8 __iomem *) (info->screen_base + p);

别指望用 write 写整屏会快，动画路径一律走 mmap。

fb_mmap 是实际应用最常用的入口。驱动填了 fb_mmap 就转给驱动，没填就拿 fix.smem_start 加 fix.smem_len 直接 vm_iomap_memory：

c
        start = info->fix.smem_start;
        len = info->fix.smem_len;
        mmio_pgoff = PAGE_ALIGN((start & ~PAGE_MASK) + len) >> PAGE_SHIFT;
        if (vma->vm_pgoff >= mmio_pgoff) {
                vma->vm_pgoff -= mmio_pgoff;
                start = info->fix.mmio_start;
                len = info->fix.mmio_len;
        }
        vma->vm_page_prot = vm_get_page_prot(vma->vm_flags);
        fb_pgprotect(file, vma, start);
        return vm_iomap_memory(vma, start, len);

这里的 mmio_pgoff 是个技巧：vm_pgoff 落在显存范围之外的往后一页开始，映射到的是 mmio_start 指向的寄存器区。应用可以用同一次 mmap 拿到显存和寄存器两段地址。

内核版本差异：这段代码里的 pgprot_decrypted 在 5.x 才出现，fb_pgprotect 的签名在不同版本里也有变化。老 2.6/3.x 内核里 fb_mmap 直接操作 vma->vm_page_prot 和 remap_pfn_range，没有 decrypted 那一层。移植时以手头内核的源码为准。

七、S3C2440 的 LCD 控制器 #

S3C2440 把 LCD 控制器集成在芯片内部，寄存器块基址 0x4D000000，大小按资源描述给 1MB（S3C24XX_SZ_LCD）。控制器负责三件事：

  • 产生 VCLK、HSYNC、VSYNC、VD[23:0] 这些时序信号；
  • 按配置从显存里读像素数据（自己走 DMA，不占 CPU）；
  • 提供 16 级灰度/彩色 STN、TFT 面板接口，支持 1/2/4/8/16/24 bpp。

在板级支持代码里，LCD 被描述成一个 platform 设备，名字 s3c2410-lcd：

        [0] = DEFINE_RES_MEM(S3C24XX_PA_LCD, S3C24XX_SZ_LCD),  /* 0x4D000000，1MB */
        [1] = DEFINE_RES_IRQ(IRQ_LCD),
};

struct platform_device s3c_device_lcd = {
        .name           = "s3c2410-lcd",
        .id             = -1,
        .num_resources  = ARRAY_SIZE(s3c_lcd_resource),
        .resource       = s3c_lcd_resource,
        .dev            = {
                .dma_mask               = &samsung_device_dma_mask,
                .coherent_dma_mask      = DMA_BIT_MASK(32),
        }
};

配套的平台数据由 arch/arm/plat-samsung/include/plat/fb-s3c2410.h 里三个结构体描述：

时序寄存器的计算落在 s3c2410fb_calculate_tft_lcd_regs：

c
static void s3c2410fb_calculate_tft_lcd_regs(const struct fb_info *info,
                                             struct s3c2410fb_hw *regs)
{
        const struct s3c2410fb_info *fbi = info->par;
        const struct fb_var_screeninfo *var = &info->var;

        switch (var->bits_per_pixel) {
        case 1:  regs->lcdcon1 |= S3C2410_LCDCON1_TFT1BPP;  break;
        case 2:  regs->lcdcon1 |= S3C2410_LCDCON1_TFT2BPP;  break;
        case 4:  regs->lcdcon1 |= S3C2410_LCDCON1_TFT4BPP;  break;
        case 8:
                regs->lcdcon1 |= S3C2410_LCDCON1_TFT8BPP;
                regs->lcdcon5 |= S3C2410_LCDCON5_BSWP |
                                 S3C2410_LCDCON5_FRM565;
                regs->lcdcon5 &= ~S3C2410_LCDCON5_HWSWP;
                break;
        case 16:
                regs->lcdcon1 |= S3C2410_LCDCON1_TFT16BPP;
                regs->lcdcon5 &= ~S3C2410_LCDCON5_BSWP;
                regs->lcdcon5 |= S3C2410_LCDCON5_HWSWP;
                break;
        case 32:
                regs->lcdcon1 |= S3C2410_LCDCON1_TFT24BPP;
                regs->lcdcon5 &= ~(S3C2410_LCDCON5_BSWP |
                                   S3C2410_LCDCON5_HWSWP |
                                   S3C2410_LCDCON5_BPP24BL);
                break;
        default:
                dev_err(fbi->dev, "invalid bpp %d\n", var->bits_per_pixel);
        }

        regs->lcdcon2 = S3C2410_LCDCON2_LINEVAL(var->yres - 1) |
                        S3C2410_LCDCON2_VBPD(var->upper_margin - 1) |
                        S3C2410_LCDCON2_VFPD(var->lower_margin - 1) |
                        S3C2410_LCDCON2_VSPW(var->vsync_len - 1);

        regs->lcdcon3 = S3C2410_LCDCON3_HBPD(var->right_margin - 1) |
                        S3C2410_LCDCON3_HFPD(var->left_margin - 1) |
                        S3C2410_LCDCON3_HOZVAL(var->xres - 1);

        regs->lcdcon4 = S3C2410_LCDCON4_HSPW(var->hsync_len - 1);
}

这里有两个对照关系必须记住，后面第十一章还要用到：

  • left_margin → HFPD，right_margin → HBPD。内核 var 的命名是从「图像」视角出发的，left_margin 是图像左边到同步信号的距离，也就是 LCD 手册说的前肩（front porch）。
  • upper_margin → VFPD，lower_margin → VBPD。同理。
  • 所有寄存器字段都要减 1 再写。var 里存的是「周期数」，寄存器存的是「周期数减一」。

写完寄存器后靠 cpufreq 通知链重算。CPU 主频一变，HCLK 跟着变，VCLK 就飘了，必须重算 CLKVAL：

c
static int s3c2410fb_cpufreq_transition(struct notifier_block *nb,
                                        unsigned long val, void *data)
{
        struct s3c2410fb_info *info;
        struct fb_info *fbinfo;
        long delta_f;

        info = container_of(nb, struct s3c2410fb_info, freq_transition);
        fbinfo = dev_get_drvdata(info->dev);

        delta_f = info->clk_rate - clk_get_rate(info->clk);

        if ((val == CPUFREQ_POSTCHANGE && delta_f > 0) ||
            (val == CPUFREQ_PRECHANGE && delta_f < 0)) {
                info->clk_rate = clk_get_rate(info->clk);
                s3c2410fb_activate_var(fbinfo);
        }

        return 0;
}

delta_f 的符号判断有点绕：POSTCHANGE 时若新频率更低（delta_f > 0），说明时钟已经降下来了，立刻重算；PRECHANGE 时若新频率更高，也要提前重算。目的是保证任何时刻写入硬件的 CLKVAL 都与当前 HCLK 匹配。

八、LCD 控制器的寄存器 #

寄存器按 32 位偏移排列，手工驱动的结构体定义：

c
struct lcd_regs {
        unsigned long   lcdcon1;
        unsigned long   lcdcon2;
        unsigned long   lcdcon3;
        unsigned long   lcdcon4;
        unsigned long   lcdcon5;
        unsigned long   lcdsaddr1;
        unsigned long   lcdsaddr2;
        unsigned long   lcdsaddr3;
        unsigned long   redlut;
        unsigned long   greenlut;
        unsigned long   bluelut;
        unsigned long   reserved[9];
        unsigned long   dithmode;
        unsigned long   tpal;
        unsigned long   lcdintpnd;
        unsigned long   lcdsrcpnd;
        unsigned long   lcdintmsk;
        unsigned long   lpcsel;
};

sizeof(struct lcd_regs) 在 32 位 ARM 上是 104 字节，ioremap(0x4D000000, 104) 就够，素材日志里的 lcd_regs=c48a4000 map_size 104 印证了这一点。

LCDCON1 管时钟分频、面板类型、bpp 和总开关：

位 名称 含义
[17:8] CLKVAL VCLK = HCLK / [(CLKVAL+1) × 2]，STN 时是 HCLK/(CLKVAL+1)
[7] — 保留
[6:5] PNRMODE 00 4 位双扫描，01 4 位单扫描（STN），10 8 位单扫描，11 TFT 面板
[4:1] BPPMODE 1bpp=0000，2bpp=0001，4bpp=0010，8bpp=0011，16bpp=1100，24bpp=1101
[0] ENVID 0 禁止视频输出与控制信号，1 允许

手工驱动里的写法是 (CLKVAL<<8) | (3<<5) | (0xC<<1)，注意这里没置 ENVID，开关屏单独控制。

LCDCON2 管垂直方向：

位 名称 含义
[31:24] VBPD 帧同步信号的后肩（vertical back porch），单位是行
[23:14] LINEVAL 垂直可见行数减一，即 yres - 1
[13:6] VFPD 帧同步信号的前肩
[5:0] VSPW VSYNC 脉宽减一

LCDCON3 管水平方向：

位 名称 含义
[25:19] HBPD 行同步信号的后肩，单位是 VCLK
[18:8] HOZVAL 水平可见像素数减一，即 xres - 1
[7:0] HFPD 行同步信号的前肩

LCDCON4 只有低 8 位有用，HSPW[7:0]，HSYNC 脉宽减一。

LCDCON5 管数据格式和信号极性：

位 名称 含义
[11] FRM565 16bpp 输出格式，0 = 5:5:5:1，1 = 5:6:5
[10] INVVCLK VCLK 采样沿极性，0 下降沿取数，1 上升沿取数
[9] INVVLINE VLINE/HSYNC 脉冲极性，0 正常 1 反转
[8] INVVFRAME VFRAME/VSYNC 脉冲极性，0 正常 1 反转
[7] INVVD VD 数据极性，0 正常 1 反转
[6] INVVDEN VDEN 极性
[5] INVPWREN PWREN 极性
[4] INVLEND LEND 极性
[3] PWREN 0 禁止 PWREN 信号，1 允许
[2] ENLEND LEND 使能
[1] BSWP 字节交换，0 禁止 1 使能
[0] HWSWP 半字交换，0 禁止 1 使能

素材里那份手写驱动只置了 [11] [10] [9] [8] [0]：

c
lcd_regs->lcdcon5 = ((1<<11) | (1<<10) | (1 << 9) | (1 << 8) | (1 << 0));

即 FRM565 开、VCLK 上升沿采样、HSYNC/VSYNC 极性反转、半字交换开。原注释把 [10] 写成「STN/TFT」，正确的名称是 INVVCLK，这是抓取稿的笔误，以数据手册为准。

LCDSADDR1/2/3 三个寄存器决定显存在哪、多长、行宽多少：

寄存器 位 名称 含义
LCDSADDR1 [29:21] LCDBANK 帧缓冲起始物理地址的 [30:22]
LCDSADDR1 [20:0] LCDBASEU 帧缓冲起始物理地址的 [21:1]
LCDSADDR2 [20:0] LCDBASEL 帧结束物理地址的 [21:1]
LCDSADDR3 [21:11] OFFSIZE 虚拟屏偏移，上一行末像素到下一行首像素间隔多少半字
LCDSADDR3 [10:0] PAGEWIDTH 行宽，半字为单位

手工驱动的写法：

c
/* [29:21] LCDBANK:[30:22]  [20:0] LCDBASEU:[21:1] */
lcd_regs->lcdsaddr1 = (s3c_lcd->fix.smem_start >> 1) & ~(3<<30);

/* 存放帧结束地址[21:1] */
lcd_regs->lcdsaddr2 = ((s3c_lcd->fix.smem_start + s3c_lcd->fix.smem_len) >> 1) & 0x1fffff;

/* [21:11] OFFSIZE  [10:0] PAGEWIDTH（半字为单位 16bit） */
lcd_regs->lcdsaddr3 = LCD_WIDTH & 0x3ff;

第 2 行有个问题：& 0x1fffff 只保留低 21 位，把 [30:22] 那段地址高位丢了，高位应由 LCDBANK 承担。这段代码本身有瑕疵，正确的做法是先把地址按 0x400000 对齐再取位段，或者至少保证显存落在同一个 4MB bank 内。素材里跑出来的 lcdsaddr[1]=0x19ce0000、lcdsaddr[2]=0x000f2c00（后面第十九章会讲这个值是怎么错的）。

lpcsel 不是 LCD 控制器时序寄存器，它是 LPC3600 那一片的电源/扫描方向控制。素材注释写「第一位设置为1 选择输出分片率类型 0:320×240 1:240×320」，这个位含义来自 LPC3600 的文档，本机未验证。素材里出现过 1<<4 和 1<<1 两种写法，跑通的是 | 1<<1 那一版，对应 240×320 竖屏。

九、时序参数的计算 #

LCD 手册给的是一张表，内核要的是六个数字，两者之间的换算就三步。

第一步，认参数。 一帧图像的时间轴长这样：

text
VSYNC ┌──┐                          ┌──┐
      │  │                          │  │
      ┘  └──────────────────────────┘  └───
       VSPW   VBPD      图像           VFPD
      ├────┤├──────┤├──────────────┤├──────┤
                  VLINE
HSYNC ──┐   ┌───────────────────────────┐   ┌──
        │   │                           │   │
        └───┘                           └───┘
        HSPW  HBPD       图像            HFPD
手册名 fb_var_screeninfo 字段 寄存器字段 含义
HSPW hsync_len LCDCON4 HSPW HSYNC 脉冲宽度，单位 VCLK
HBP right_margin LCDCON3 HBPD 行同步后肩：HSYNC 下降沿到可见数据开始
HFP left_margin LCDCON3 HFPD 行同步前肩：可见数据结束到 HSYNC 上升沿
VSPW vsync_len LCDCON2 VSPW VSYNC 脉冲宽度，单位行
VBP lower_margin LCDCON2 VBPD 帧同步后肩：VSYNC 之后到第一行可见行的无效行数
VFP upper_margin LCDCON2 VFPD 帧同步前肩：最后一行可见行到 VSYNC 的无效行数
— xres LCDCON3 HOZVAL 水平像素数
— yres LCDCON2 LINEVAL 垂直行数

「前肩/后肩」和 left/right、upper/lower 的对应关系容易搞反，按「图像先出现，后肩在图像前」来记：right_margin 是后肩，left_margin 是前肩。这个映射在 s3c2410fb_calculate_tft_lcd_regs 里写死了。

第二步，代入寄存器。 寄存器值一律减一：

text
LINEVAL = yres - 1        HOZVAL = xres - 1
VSPW    = vsync_len - 1   VFPD   = upper_margin - 1   VBPD = lower_margin - 1
HSPW    = hsync_len - 1   HFPD   = left_margin - 1    HBPD = right_margin - 1

第三步，算 CLKVAL。 VCLK 的频率决定一个像素的时间：

text
VCLK = 10^12 / pixclock          （pixclock 单位皮秒）
VCLK = HCLK / [(CLKVAL + 1) × 2]
CLKVAL = HCLK × pixclock / (2 × 10^12) - 1

拿 T35 屏走一遍。手册给的参数是：240×320、16bpp，水平同步脉宽/前肩/后肩取 10/10/20，垂直三个值取 2/2/2，像素时钟 6.4MHz。VCLK = 6.4MHz 对应 pixclock = 1/(6.4×10^6)×10^12 = 156250 ps。

text
HOZVAL = 240 - 1 = 239         LINEVAL = 320 - 1 = 319
HSPW   = 10 - 1  = 9           HFPD    = 10 - 1  = 9      HBPD = 20 - 1 = 19
VSPW   = 2 - 1   = 1           VFPD    = 2 - 1   = 1      VBPD = 2 - 1  = 1

HCLK = 100MHz
CLKVAL = 100 / 6.4 / 2 - 1 = 6.8   →  取整 7

取整 7 之后 VCLK 就不再是 6.4MHz 了，回代一下：

text
VCLK = 100MHz / [(7 + 1) × 2] = 6.25MHz

6.25MHz 与 6.4MHz 差 2.3%，屏能接受，因为 LCD 的 VCLK 容差一般有 ±10%。要更准就得调 HCLK 或者换晶振，CLKVAL 只能取整数，这是硬约束。

驱动里算这一步的代码：

c
static void s3c2410fb_activate_var(struct fb_info *info)
{
        struct s3c2410fb_info *fbi = info->par;
        void __iomem *regs = fbi->io;
        int type = fbi->regs.lcdcon1 & S3C2410_LCDCON1_TFT;
        struct fb_var_screeninfo *var = &info->var;
        int clkdiv;

        clkdiv = DIV_ROUND_UP(s3c2410fb_calc_pixclk(fbi, var->pixclock), 2);

        if (type == S3C2410_LCDCON1_TFT) {          /* TFT 真彩走这里 */
                s3c2410fb_calculate_tft_lcd_regs(info, &fbi->regs);
                --clkdiv;
                if (clkdiv < 0)
                        clkdiv = 0;
        } else {
                s3c2410fb_calculate_stn_lcd_regs(info, &fbi->regs);
                if (clkdiv < 2)
                        clkdiv = 2;
        }

        fbi->regs.lcdcon1 |=  S3C2410_LCDCON1_CLKVAL(clkdiv);

        /* 先关输出再改参数 */
        writel(fbi->regs.lcdcon1 & ~S3C2410_LCDCON1_ENVID,
                regs + S3C2410_LCDCON1);
        writel(fbi->regs.lcdcon2, regs + S3C2410_LCDCON2);
        writel(fbi->regs.lcdcon3, regs + S3C2410_LCDCON3);
        writel(fbi->regs.lcdcon4, regs + S3C2410_LCDCON4);
        writel(fbi->regs.lcdcon5, regs + S3C2410_LCDCON5);

        /* set lcd address pointers */
        s3c2410fb_set_lcdaddr(info);

        fbi->regs.lcdcon1 |= S3C2410_LCDCON1_ENVID;  /* 使能LCD */
        writel(fbi->regs.lcdcon1, regs + S3C2410_LCDCON1);
}

DIV_ROUND_UP(x, 2) - 1 和上面那个公式是同一件事，s3c2410fb_calc_pixclk 内部做的正是 clk_rate × pixclock / 10^12。

改寄存器的顺序有讲究：先清 ENVID，改完五个寄存器，再置 ENVID。中途不能让屏上出现半套时序，否则会看到抖动或者直接花屏。

对应到板级配置，T35 屏最终填成这样（pixclock 用上面算出的 156250）：

c
static struct s3c2410fb_display smdk2440_lcd_cfg __initdata = {
        .lcdcon5        = S3C2410_LCDCON5_FRM565 |
                          S3C2410_LCDCON5_INVVLINE |
                          S3C2410_LCDCON5_INVVFRAME |
                          S3C2410_LCDCON5_PWREN |
                          S3C2410_LCDCON5_HWSWP,
        .type           = S3C2410_LCDCON1_TFT,
        .width          = LCD_WIDTH,   /* 240 */
        .height         = LCD_HEIGHT,  /* 320 */
        .pixclock       = 156250,      /* 10^12 / 6.4MHz */
        .xres           = LCD_WIDTH,
        .yres           = LCD_HEIGHT,
        .bpp            = 16,
        .left_margin    = HFPD,   /* 9  */
        .right_margin   = HBPD,   /* 19 */
        .hsync_len      = HSPW,   /* 9  */

有个坑要说清楚：.upper_margin = VBPD，.lower_margin = VFPD。这是按内核 var 的语义填的，与寄存器字段同名不同侧。想省事就照抄 s3c2410fb_calculate_tft_lcd_regs 里的反向映射推一遍。

手册给的行时序数字（HSPW/HBP/HFP），S3C2440 数据手册里以 VCLK 周期为单位，直接减一填进去。T35 手册的单位是以 ns 还是以 VCLK 给，取决于具体版本手册，本篇按素材给的「10/10/20」直接使用，数值来源未验证，自己动手时按手头手册重算。

十、显存的组织与分配 #

显存就是一块普通的 DMA 内存，但它必须是非 cache、连续物理的，因为 LCD 控制器靠 DMA 读它，CPU 这边写进去的画面要立刻能被控制器看见。

分配函数是 dma_alloc_wc（write-combine，写合并）：

c
static int s3c2440fb_map_video_memory(struct fb_info *fbinfo)
{
        dma_addr_t map_dma;
        unsigned long map_size = PAGE_ALIGN(fbinfo->fix.smem_len);

        fbinfo->screen_base = dma_alloc_wc(&s3c_device_lcd.dev, map_size,
                                           &map_dma, GFP_KERNEL);
        if (fbinfo->screen_base) {
                /* prevent initial garbage on screen */
                memset(fbinfo->screen_base, 0x00, map_size);
                fbinfo->fix.smem_start = map_dma;
        }

        return fbinfo->screen_base ? 0 : -ENOMEM;
}

三个要点：

  • map_size 必须经过 PAGE_ALIGN，DMA 分配器只接受整页。
  • 第一个参数 dev 不能是 NULL，否则 dma_alloc_wc 内部取 dev->dma_mask 时直接崩。
  • 清屏这一步不能省，否则上电那一瞬间屏上是上一次的内存残留。

释放用 dma_free_wc(&s3c_device_lcd.dev, s3c_lcd->fix.smem_len, s3c_lcd->screen_base, s3c_lcd->fix.smem_start)。传给释放函数的大小要和分配时一致，这里传的是没对齐的 smem_len，与分配时的 PAGE_ALIGN(smem_len) 不一致。位置无关的分配器一般能容忍，但严格讲应该 PAGE_ALIGN 后再释放，素材原稿这里不规范。

主线路由 s3c2410fb_map_video_memory 走，逻辑多了设备管理：

c
static int s3c2410fb_map_video_memory(struct fb_info *fbinfo)
{
        ...
        fbinfo->screen_base = dma_alloc_wc(fbinfo->device,
                                           PAGE_ALIGN(fbinfo->fix.smem_len),
                                           &map_dma, GFP_KERNEL);
        ...
}

显存大小怎么算：

text
smem_len = xres × yres × bpp / 8

240 × 320 × 16 / 8 = 153600 字节 = 150KB。对齐到 4KB 页之后是 155648 = 0x26000。素材里的日志 map_size 155648、size=00026000 对得上。

单缓冲要这么多，双缓冲翻倍，见第十五章。

显存和 fb_info 的对应关系，三处地址必须一致：

位置 内容 谁写
fix.smem_start 显存物理地址 dma_alloc_wc 的输出参数
screen_base 显存虚拟地址 dma_alloc_wc 的返回值
LCDSADDR1/2 显存物理地址的位段 驱动按 smem_start 换算

fbmem.c 的 fb_mmap 用 fix.smem_start 给用户空间做映射，所以 smem_start 填错，用户态 mmap 出来的地址就指向别处。这是调试显存相关问题时第一个要核对的字段。

行宽 line_length 是另一处容易出错的地方：

c
s3c_lcd->fix.line_length = LCD_WIDTH * 2;   /* 240 * 2 = 480 字节 */

line_length 是一行在显存里占多少字节，不是一行有多少像素。cfb_* 系列函数全靠这个值算跨行偏移。RGB565 下它等于 xres × 2，RGB888 下等于 xres × 3（或 4，取决于对齐要求）。

LCDSADDR3 的 PAGEWIDTH 用半字为单位，所以是 xres（240）而不是 480。OFFSIZE 在单缓冲时填 0；虚拟屏比可见区域宽的时候，填「每行多出来的半字数」。

驱动入口里显存和寄存器地址最终这样对上：

text
root@smdk2440 # 内核启动日志
map_video_memory: clear (ptrval):00026000
map_video_memory: dma=339c0000 cpu=(ptrval) size=00026000
got video memory

dma=339c0000 是物理地址，最终写进 LCDSADDR1。

显存分配失败最常见的原因是 DMA 掩码没设。s3c_device_lcd.dev.dma_mask 和 coherent_dma_mask 都要设成 DMA_BIT_MASK(32)，漏设时 dma_alloc_wc 返回 NULL，日志里只有一句 failed to allocate video RAM。

十一、调色板与色彩格式 #

fb_info 里跟颜色相关的字段分三层：fix.visual 说这块屏是哪种色彩模型，var.red/green/blue 说每个通道占几位、偏多少，cmap/pseudo_palette 说具体 16 个颜色值怎么查。

fix.visual 值 含义
FB_VISUAL_MONO01 0 单色，1 黑 0 白
FB_VISUAL_MONO10 1 单色，1 白 0 黑
FB_VISUAL_TRUECOLOR 2 真彩，每像素直接存 RGB
FB_VISUAL_PSEUDOCOLOR 3 伪彩，每像素存索引
FB_VISUAL_DIRECTCOLOR 4 直彩，每像素存索引但走三个独立 LUT
FB_VISUAL_STATIC_PSEUDOCOLOR 5 只读伪彩
FB_VISUAL_FOURCC 6 由 V4L2 FOURCC 描述

S3C2440 跑 RGB565 就填 FB_VISUAL_TRUECOLOR。位域结构是 struct fb_bitfield { __u32 offset; __u32 length; __u32 msb_right; }，offset 指从最低位起偏移多少位，length 指占几位。

RGB565 的填法：

通道 offset length 说明
red 11 5 从最低位起偏移 11 位，占 5 位
green 5 6 偏移 5 位，占 6 位
blue 0 5 偏移 0 位，占 5 位
transp 0 0 无 Alpha

换成 24 位色时三组 offset/length 一起改成 16/8、8/8、0/8，cfb_* 会自动适配，代码不用动。

常见格式的对照表：

格式 bpp R offset/len G offset/len B offset/len S3C2440 侧 视觉类型
RGB565 16 11/5 5/6 0/5 TFT16BPP + FRM565=1 TRUECOLOR
RGB555 16 10/5 5/5 0/5 TFT16BPP + FRM565=0 TRUECOLOR
RGB888 24 16/8 8/8 0/8 TFT24BPP TRUECOLOR
ARGB8888 32 16/8 8/8 0/8 TFT24BPP，高 8 位丢弃 TRUECOLOR
调色板 8 — — — TFT8BPP + BSWP PSEUDOCOLOR，查 cmap
灰度 8 — — — TFT8BPP grayscale = 1

S3C2440 有个硬限制：bits_per_pixel 不支持 18 位。手册里的 18bpp 模式在 s3c2410fb_calculate_tft_lcd_regs 的 switch 里没有分支，填 18 走到 default 打印 invalid bpp 18，屏上就是一帧不刷新。

BPP 到 LCDCON1 BPPMODE 的映射：

var.bits_per_pixel BPPMODE 编码 LCDCON1 位[4:1] LCDCON5 相关位
1 TFT1BPP 0000 无
2 TFT2BPP 0001 无
4 TFT4BPP 0010 无
8 TFT8BPP 0011 BSWP=1、FRM565=1、HWSWP=0
16 TFT16BPP 1100 BSWP=0、HWSWP=1
24 TFT24BPP 1101 BSWP=0、HWSWP=0、BPP24BL=0
32 TFT24BPP 1101 同上，内存里每像素占 4 字节但只有低 24 位参与显示

8bpp 那行反直觉：HWSWP 清掉、BSWP 置上，这是 8 位调色板数据在内存里的字节序要求，照抄驱动即可，不要自己推。

调色板这块，16bpp 及以上其实用不到 cmap，但内核仍然要求填 pseudo_palette，因为 fbcon 画光标和边框时会走 16 色路径：

c
static u32 pseudo_palette[16];

static inline unsigned int chan_to_field(unsigned int chan,
                                         struct fb_bitfield *bf)
{
    chan &= 0xffff;
    chan >>= 16 - bf->length;
    return chan << bf->offset;
}

static int s3c2440fb_setcolreg(unsigned regno,
                               unsigned red, unsigned green, unsigned blue,
                               unsigned transp, struct fb_info *info)
{
    unsigned int val;

    if (regno >= 16)
         return 1;

    val  = chan_to_field(red,   &info->var.red);
    val |= chan_to_field(green, &info->var.green);
    val |= chan_to_field(blue,  &info->var.blue);

    pseudo_palette[regno] = val;
    return 0;
}

chan_to_field 干的事：内核传进来的 red/green/blue 都是 16 位（0~65535），先取高 bf->length 位，再左移到 bf->offset。RGB565 下红色就是 (red >> 11) << 11，正好落在 [15:11]。

素材原稿这里有个 bug：函数里声明了 u32 *pal = info->pseudo_palette; 却没用，写回时用的是全局 pseudo_palette。两个数组其实是同一个对象（info->pseudo_palette 指向它），能跑，但这个变量是死代码。正确写法是通过 pal[regno] 写回，这样一份驱动能支持多个 fb_info。另一个 bug 是边界判断的两种写法：一处 if (regno > 16)，一处 if (regno >= 16)。数组大小是 16，合法下标 0~15，> 16 会让 pseudo_palette[16] 写到数组外面，以 >= 16 为准。

十二、图像数据的格式转换 #

屏要的是 RGB565，图片素材往往是 24 位 BMP、JPEG，或者带 Alpha 的 PNG。写显存之前得把格式统一到 var 描述的那一种。

最直接的转换是 24 位转 16 位：

c
static inline unsigned short rgb888_to_rgb565(unsigned char r,
                                              unsigned char g,
                                              unsigned char b)
{
        return ((r >> 3) << 11) | ((g >> 2) << 5) | (b >> 3);
}

规则是每个通道取高位丢低位：R 从 8 位砍到 5 位，右移 3；G 从 8 位砍到 6 位，右移 2；B 从 8 位砍到 5 位，右移 3。再用前面那个 chan_to_field 的同一套逻辑拼进 16 位字。这两个函数本质上做的是同一件事，区别只在输入宽度。

BMP 文件读进来不能直接拷，原因有三条：

  • BMP 的每行按 4 字节对齐。240 像素的 24 位 BMP，一行 720 字节正好整除，不用补；320×240 的 16 位图一行 640 字节也整除。非整除的宽度要按 ((width * bpp + 31) / 32) * 4 算行距。
  • 像素顺序是 B、G、R，不是 R、G、B。
  • 位图数据在文件里是倒序存的，最后一行在最前。

一段能用的转换循环：

c
static int bmp_to_fb(const unsigned char *src, unsigned short *dst,
                     int width, int height, int bytes_per_pixel)
{
        int line_bytes = (width * bytes_per_pixel + 3) & ~3;
        int padded = (4 - (width * bytes_per_pixel) % 4) % 4;
        int x, y;

        for (y = 0; y < height; y++) {
                const unsigned char *row = src + (height - 1 - y) * line_bytes;

                for (x = 0; x < width; x++) {
                        unsigned char b = row[x * bytes_per_pixel + 0];
                        unsigned char g = row[x * bytes_per_pixel + 1];
                        unsigned char r = row[x * bytes_per_pixel + 2];

                        dst[y * width + x] = rgb888_to_rgb565(r, g, b);
                }
        }
        return 0;
}

bytes_per_pixel 传 3 是 24 位 BMP，传 4 是带 Alpha 的 32 位 BMP（Alpha 直接丢）。

字节交换是另一个高频问题。S3C2440 的 LCDCON5 里有 BSWP（字节交换）和 HWSWP（半字交换）两个位，用来适配不同字节序的显存数据。RGB565 的 16bpp 模式，驱动填的是 HWSWP=1、BSWP=0。这意味着内存里 0xF800 这个红色像素按小端存成 00 F8，控制器按半字高位在前的预期取数。人为手动往显存里写字节时如果按大端写，红色会变成蓝色。

调过去调不回来的解决办法是反过来验一遍：在显存第一像素写 0xF800，屏上应该出一个红点；出蓝点就把 BSWP/HWSWP 换一下组合。这个实验比查手册快得多。

行对齐还有一层坑。fix.line_length 是显存里的真实行宽，var.xres 是可见像素数，两者在 fbdev 里可以不等。S3C2440 不支持行宽任意对齐，PAGEWIDTH 只能填半字数，所以 line_length 必须是 2 的倍数。填 240 × 3 这种奇数在 RGB888 下会出问题，得补齐到 4 字节对齐，然后 PAGEWIDTH 填补齐后的半字数。

转换完的像素写显存时，最佳方式是按行 memcpy 而不是逐像素赋值：

c
        for (y = 0; y < height; y++)
                memcpy(fb + y * line_length, dst + y * width,
                       width * sizeof(unsigned short));

按行拷能开 memcpy 的向量化，逐像素赋值在高 BPP 下经常是几倍的性能差。

十三、画点、画线与填充 #

fbdev 给应用层留下的接口只有 mmap 出来的那块内存，所有图形操作都得自己算偏移。

画点是最小单元：

c
static inline void put_pixel(unsigned short *fb, int x, int y,
                             unsigned short color)
{
        fb[y * LCD_WIDTH + x] = color;
}

偏移是 y × 每行像素数 + x。这里的「每行像素数」必须是显存里的行宽，不是可见宽度。单缓冲下两者相等；一旦上了双缓冲或者 xres_virtual 大于 xres，就得换成虚拟宽度。这个下标算错，屏幕会出现斜着的撕裂条纹。

画线用 Bresenham：

c
static void draw_line(unsigned short *fb, int x0, int y0, int x1, int y1,
                      unsigned short color)
{
        int dx =  abs(x1 - x0), sx = x0 < x1 ? 1 : -1;
        int dy = -abs(y1 - y0), sy = y0 < y1 ? 1 : -1;
        int err = dx + dy, e2;

        for (;;) {
                put_pixel(fb, x0, y0, color);
                if (x0 == x1 && y0 == y1)
                        break;
                e2 = 2 * err;
                if (e2 >= dy) { err += dy; x0 += sx; }
                if (e2 <= dx) { err += dx; y0 += sy; }
        }
}

只做整数加减和比较，没有浮点，也没有除法。ARM9 上跑一条 240 像素的对角线是微秒级。

画矩形框和实心填充：

c
static void fill_rect(unsigned short *fb, int x, int y, int w, int h,
                      unsigned short color)
{
        int i, j;

        for (j = 0; j < h; j++) {
                unsigned short *row = fb + (y + j) * LCD_WIDTH + x;

                for (i = 0; i < w; i++)
                        row[i] = color;
        }
}

static void draw_rect(unsigned short *fb, int x, int y, int w, int h,
                      unsigned short color)
{
        int i;

        for (i = 0; i < w; i++) {
                put_pixel(fb, x + i, y, color);
                put_pixel(fb, x + i, y + h - 1, color);
        }
        for (i = 0; i < h; i++) {
                put_pixel(fb, x, y + i, color);
                put_pixel(fb, x + w - 1, y + i, color);
        }
}

填充可以再快一档，用 memset 的思路一次写多个像素：颜色只有 16 位，把它扩成 32 位再按 unsigned int 写，速度翻倍。宽度是偶数时好办，奇数时尾部单独补一个。

内核侧的等价物是 cfb_fillrect/cfb_copyarea/cfb_imageblit，它们接受 struct fb_fillrect/fb_copyarea/fb_image，内部按 var 的位域做像素打包。驱动的 fb_fillrect 接了 cfb_fillrect 之后，fbcon 滚屏、清屏、画光标全部自动走这条路径，我们在应用层写的 fill_rect 只用在纯用户态程序里。

一个常见的误判：很多人以为挂了 cfb_fillrect 就是硬件加速。不是，那是软件实现，只是比逐像素循环写得紧凑。真加速需要驱动声明 FBINFO_HWACCEL_FILLRECT 并且自己写一个能操作硬件引擎的 fb_fillrect。S3C2440 没有 2D 引擎，这条路上限就是软件速度。

十四、字库与字符显示 #

在屏上显示一个字符，本质是把「字模」这组位图贴上去。字模的来源是点阵字库。

8×16 点阵的 ASCII 字库，一个字符 16 字节，每字节 8 个位对应一列像素的 8 个像素。以 A（0x41）为例，字模数据大致长这样：

text
0x00,0x00,0x00,0x00,0x00,0x00,0x00,0x00,
0x00,0x00,0x00,0x00,0x00,0x00,0x00,0x00,  /* 实际数据从第 3 字节起 */

真实数据从字库文件的 0x41 × 16 偏移处取。取模软件（PCtoLCD2002 一类）生成的数组，索引就是字符的 ASCII 码。

绘制函数逐行逐位展开：

c
static void draw_char(unsigned short *fb, int x, int y, char ch,
                      const unsigned char *font, unsigned short color)
{
        const unsigned char *glyph = font + (unsigned char)ch * 16;
        int row, col;

        for (row = 0; row < 16; row++) {
                unsigned char bits = glyph[row];

                for (col = 0; col < 8; col++) {
                        if (bits & (0x80 >> col))
                                put_pixel(fb, x + col, y + row, color);
                }
        }
}

要点：0x80 >> col 是从左往右扫，也就是「高位在左」。取模软件里选的「高位在前」就是这个意思，选错了字符会左右镜像。

这套逻辑有两层优化。第一层加描边和背色，让它能盖住底下的内容：

c
static void draw_char_bg(unsigned short *fb, int x, int y, char ch,
                         const unsigned char *font,
                         unsigned short fg, unsigned short bg)
{
        const unsigned char *glyph = font + (unsigned char)ch * 16;
        int row, col;

        for (row = 0; row < 16; row++) {
                unsigned char bits = glyph[row];

                for (col = 0; col < 7; col += 1) {
                        put_pixel(fb, x + col, y + row,
                                  (bits & (0x80 >> col)) ? fg : bg);
                }
        }
}

第二层是整行写。8 像素正好半个字，可以先生成一个 unsigned short，再一次性写进去。

汉字是 16×16 点阵，一个字符 32 字节，前 16 字节上半部、后 16 字节下半部。字库要用 GB2312 区位码查：

c
static const unsigned char *get_gb2312_glyph(const unsigned char *font,
                                             unsigned char hi,
                                             unsigned char lo)
{
        int qh = hi - 0xA1;
        int ql = lo - 0xA1;

        return font + (qh * 94 + ql) * 32;
}

GB2312 一级字库从 0xB0A1（「啊」）开始，区号和位号都从 1 起算，所以减 0xA1。乘 94 是因为每区 94 个汉字位。这个公式只对一级、二级汉字成立，符号区（0xA1~0xA9）的排布不同，用之前先确认字库文件的组织方式。

画一个汉字：

c
static void draw_hanzi(unsigned short *fb, int x, int y,
                       unsigned char hi, unsigned char lo,
                       const unsigned char *font, unsigned short color)
{
        const unsigned char *glyph = get_gb2312_glyph(font, hi, lo);
        int row, col, half;

        for (half = 0; half < 2; half++) {
                for (row = 0; row < 16; row++) {
                        unsigned char bits = glyph[half * 16 + row];

                        for (col = 0; col < 8; col++) {
                                if (bits & (0x80 >> col))
                                        put_pixel(fb, x + half * 8 + col,
                                                  y + row, color);
                        }
                }
        }
}

内核里对应的是 fbcon 加 font_8x16。include/linux/font.h 定义了 struct font_desc，lib/fonts/ 下有 font_8x16.c、font_10x18.c 等。cfb_imageblit 拿到 struct fb_image 之后按同样的逐位逻辑贴图，字符集和字形由 fbcon 管。用户态程序显示文字，最省事的做法是直接在 /dev/fb0 上贴字模，不去碰 fbcon；要做带光标的终端，才需要动 tty1 那一侧。

十五、双缓冲与硬件加速 #

单缓冲的问题一眼能看出：正在写显存的时候，LCD 控制器也在读它，于是屏幕上出现「上半截新画面、下半截旧画面」的撕裂。

fbdev 时代的标准解法是把显存开大，用 yoffset 翻页。

text
显存布局（yres_virtual = 2 × yres）：

  +-------------------+  smem_start
  |   缓冲区 0        |  yoffset = 0
  |  240 × 320 × 2B   |  可见
  +-------------------+
  |   缓冲区 1        |  yoffset = 320
  |  240 × 320 × 2B   |  可见
  +-------------------+  smem_start + smem_len（单块 150KB，合计 300KB）

smem_len 要按两倍申请，var.yres_virtual = 640，var.yoffset 在 0 和 320 之间切。

c
s3c_lcd->fix.smem_len         = LCD_WIDTH * LCD_HEIGHT * 2 * 2;  /* 双缓冲 */
s3c_lcd->var.yres_virtual     = LCD_HEIGHT * 2;
s3c_lcd->var.yoffset          = 0;
s3c_lcd->screen_size          = LCD_WIDTH * LCD_HEIGHT * 2 * 2;

背缓冲的起始地址是 screen_base + smem_len / 2，或者用 yoffset 算：

c
        unsigned short *back = (unsigned short *)(s3c_lcd->screen_base +
                                 LCD_WIDTH * LCD_HEIGHT * 2);

翻页要驱动实现 fb_pan_display。S3C2440 的做法是重新算 LCDSADDR1/2，把 LCDBASEU 指到新缓冲区的起始地址，LCDBASEL 指到它的末尾：

c
static int s3c2440fb_pan_display(struct fb_var_screeninfo *var,
                                 struct fb_info *info)
{
        unsigned long buffer_size = info->fix.line_length * info->var.yres;
        unsigned long base = info->fix.smem_start + var->yoffset
                             * info->fix.line_length;

        lcd_regs->lcdsaddr1 = base >> 1;
        lcd_regs->lcdsaddr2 = (base + buffer_size) >> 1;
        info->var.yoffset = var->yoffset;
        return 0;
}

缓冲区大小用 line_length × yres，不是 fix.smem_len。双缓冲下 smem_len 是两块之和，拿它算 LCDBASEL 会让结束地址落到第二块末尾，控制器读越界。

lcdsaddr1/lcdsaddr2 也不该再套 & 0x1fffff 那种掩码，那是第八章那个出错写法的延续。LCDBASEU 只取 [20:0]，交给硬件自然截断即可；人为掩码会连带把 LCDBANK 该承担的高位砍掉。

用户态触发翻页：

c
        struct fb_var_screeninfo var;

        ioctl(fd, FBIOGET_VSCREENINFO, &var);
        var.yoffset = (var.yoffset == 0) ? LCD_HEIGHT : 0;
        ioctl(fd, FBIOPUT_VSCREENINFO, &var);   /* 驱动走 fb_set_par */

FBIOPUT_VSCREENINFO 会调 fb_set_par，fb_set_par 一般就是调 fb_pan_display 加重新编程控制器。S3C2440 这条路上要注意：一次 FBIOPUT_VSCREENINFO 会连带重算全部时序寄存器，比只改地址慢。更轻的写法是驱动提供一个私有 ioctl，只改 LCDSADDR1。

翻页本身是瞬间生效的：控制器下一次扫描帧时就从新地址取数，中间不需要等 VSYNC。这是 fbdev 比裸寄存器方便的地方，也是它的隐患，真要做到完全无撕裂，得等 VSYNC 中断（IRQ_LCD）再翻。s3c2410fb 注册了 s3c2410fb_irq，但标准路径里没有把它用于翻页同步，需要自己加。

硬件加速在 fbdev 里是 fb_info->flags 加 fb_ops 两处配合：

  • FBINFO_HWACCEL_FILLRECT + 自己写的 fb_fillrect：矩形填充走硬件。
  • FBINFO_HWACCEL_COPYAREA + 自己写的 fb_copyarea：区域拷贝走硬件。
  • FBINFO_HWACCEL_IMAGEBLIT + 自己写的 fb_imageblit：图像贴图走硬件。
  • FBINFO_HWACCEL_XPAN/YPAN/YWRAP + xpanstep/ypanstep/ywrapstep：硬件支持的平移粒度。

S3C2440 没有任何一个 2D 加速位可以置。fix.accel = FB_ACCEL_NONE，三个回调全部挂 cfb_*，flags 里不置任何 HWACCEL_*。这不是省事，是硬件只提供了 DMA 送像素的能力，没有填充、拷贝、混合引擎。

如果硬件真有加速引擎，模式是这样的：

c
static struct fb_ops accel_ops = {
        .owner          = THIS_MODULE,
        .fb_fillrect    = hw_fillrect,     /* 操作硬件引擎 */
        .fb_copyarea    = hw_copyarea,
        .fb_imageblit   = hw_imageblit,
        .fb_sync        = hw_wait_idle,    /* 等引擎空闲，可选 */
};

/* 初始化时 */
info->flags |= FBINFO_HWACCEL_FILLRECT | FBINFO_HWACCEL_COPYAREA;
info->fix.xpanstep = 8;   /* 水平平移必须 8 像素对齐 */

十六、驱动实例：完整的 LCD 驱动 #

这一节把前面的零件拼成一个能编译加载的模块驱动。目标板 Mini2440，屏 T35（240×320，RGB565），内核 5.2.8。

头文件与参数宏：

c
#include <linux/module.h>
#include <linux/fs.h>
#include <linux/platform_device.h>
#include <linux/fb.h>
#include <linux/dma-mapping.h>
#include <linux/clk.h>
#include <linux/io.h>

/*  LCD T35参数设定 */
#define     LCD_WIDTH   240             /* LCD面板的行宽 */
#define     LCD_HEIGHT  320             /* LCD面板的列宽 */

#define     VSPW        1               /* VSYNC 脉冲宽度 - 1 */
#define     VBPD        1               /* 垂直同步周期后的无效行数 */
#define     LINEVAL     (LCD_HEIGHT-1)  /* LCD的垂直宽度-1 */
#define     VFPD        1               /* 垂直同步周期前的无效行数 */

#define     CLKVAL      7               /* VCLK = HCLK / [(CLKVAL + 1) × 2] */

#define     HSPW        9               /* HSYNC 脉冲宽度 - 1 */
#define     HBPD        19              /* HSYNC 下降沿到可见数据开始的 VCLK 数 */
#define     HOZVAL      (LCD_WIDTH-1)   /* LCD的水平宽度-1 */
#define     HFPD        9               /* 可见数据结束到 HSYNC 上升沿的 VCLK 数 */

static struct fb_info *s3c_lcd;
static u32 pseudo_palette[16];
static struct clk *lcd_clk;
static volatile struct lcd_regs *lcd_regs;

lcd_regs 用第八章那个结构体。GPIO 三个端口用 ioremap 直接映射，gpgdat 存成静态变量，模块出口和背光控制都要用：

c
static volatile unsigned long *gpgdat;

static void s3c2440fb_config_gpio(void)
{
        volatile unsigned long *gpcup  = ioremap(0x56000028, 4);
        volatile unsigned long *gpccon = ioremap(0x56000020, 4);
        volatile unsigned long *gpdup  = ioremap(0x56000038, 4);
        volatile unsigned long *gpdcon = ioremap(0x56000030, 4);
        volatile unsigned long *gpgcon = ioremap(0x56000060, 12);
        volatile unsigned long *gpgup;

        gpgdat = gpgcon + 1;
        gpgup  = gpgdat + 1;

        /* GPCCON/GPCUP：VD[7:0], LCDVF[2:0], VM, VFRAME, VLINE, VCLK, LEND */
        *gpcup  = 0xffffffff;
        *gpccon = 0xaaaaaaaa;
        /* GPDCON/GPDUP：VD[23:8] */
        *gpdup  = 0xffffffff;
        *gpdcon = 0xaaaaaaaa;

        /* GPG4 = LCD_PWREN，GPGUP 对应位置 1 拉低上拉 */
        *gpgup  |= (1 << 4);
        *gpgcon |= (3 << 8);
}

0xaaaaaaaa 的含义是每个引脚占 2 位、全填 10 即第二功能（LCD 信号）。GPIO 三类寄存器在 S3C2440 上的排布是 CON 在前、DAT 居中、UP 在后，gpgcon + 1 拿到的是 gpgdat，+2 是 gpgup，指针算术加一等于加一个 unsigned long。

s3c2440fb_map_video_memory 就是第十章那段：PAGE_ALIGN(smem_len) → dma_alloc_wc(&s3c_device_lcd.dev, map_size, &map_dma, GFP_KERNEL) → memset 清零 → 回填 fix.smem_start = map_dma。

模块入口：

c
static int lcd_init(void)
{
        int ret;

        /* 1. 分配 fb_info */
        s3c_lcd = framebuffer_alloc(0, NULL);
        if (!s3c_lcd)
                return -ENOMEM;

        /* 2.1 固定参数 */
        strcpy(s3c_lcd->fix.id, "mylcd");
        s3c_lcd->fix.smem_len    = LCD_WIDTH * LCD_HEIGHT * 2;
        s3c_lcd->fix.type        = FB_TYPE_PACKED_PIXELS;
        s3c_lcd->fix.type_aux    = 0;
        s3c_lcd->fix.xpanstep    = 0;
        s3c_lcd->fix.ypanstep    = 0;
        s3c_lcd->fix.ywrapstep   = 0;
        s3c_lcd->fix.accel       = FB_ACCEL_NONE;
        s3c_lcd->fix.visual      = FB_VISUAL_TRUECOLOR;
        s3c_lcd->fix.line_length = LCD_WIDTH * 2;

        /* 2.2 可变参数 */
        s3c_lcd->var.xres            = LCD_WIDTH;
        s3c_lcd->var.yres            = LCD_HEIGHT;
        s3c_lcd->var.xres_virtual    = LCD_WIDTH;
        s3c_lcd->var.yres_virtual    = LCD_HEIGHT;
        s3c_lcd->var.bits_per_pixel  = 16;
        s3c_lcd->var.red.offset      = 11;
        s3c_lcd->var.red.length      = 5;
        s3c_lcd->var.green.offset    = 5;
        s3c_lcd->var.green.length    = 6;
        s3c_lcd->var.blue.offset     = 0;
        s3c_lcd->var.blue.length     = 5;
        s3c_lcd->var.activate        = FB_ACTIVATE_NOW;
        s3c_lcd->var.vmode           = FB_VMODE_NONINTERLACED;

        /* 2.3 操作函数 */
        s3c_lcd->fbops = &s3c2440fb_ops;

        /* 2.4 其他 */
        s3c_lcd->flags          = FBINFO_FLAG_DEFAULT;
        s3c_lcd->pseudo_palette = pseudo_palette;
        s3c_lcd->screen_size    = LCD_WIDTH * LCD_HEIGHT * 2;

        lcd_clk = clk_get(NULL, "lcd");
        if (IS_ERR(lcd_clk))
                return PTR_ERR(lcd_clk);
        clk_prepare_enable(lcd_clk);

        /* 3.1 GPIO */
        s3c2440fb_config_gpio();

        /* 3.2 LCD 控制器 */
        lcd_regs = ioremap(0x4D000000, sizeof(struct lcd_regs));

        lcd_regs->lcdcon1 = (CLKVAL<<8) | (3<<5) | (0xC<<1);   /* TFT, 16bpp */
        lcd_regs->lcdcon2 = (VBPD<<24)|(LINEVAL<<14)|(VFPD<<6)|(VSPW);
        lcd_regs->lcdcon3 = (HBPD<<19)|(HOZVAL<<8)|(HFPD);
        lcd_regs->lcdcon4 = (HSPW);
        lcd_regs->lcdcon5 = (1<<11) | (1<<10) | (1<<9) | (1<<8) | (1<<0);
        lcd_regs->lpcsel  = ((0xCE6) & ~7) | 1<<1;             /* 240×320 */

        /* 3.3 显存 */
        ret = s3c2440fb_map_video_memory(s3c_lcd);
        if (ret) {
                printk("failed to allocate video RAM: %d\n", ret);
                return -ENOMEM;
        }

        lcd_regs->lcdsaddr1 = s3c_lcd->fix.smem_start >> 1;
        lcd_regs->lcdsaddr2 = (s3c_lcd->fix.smem_start +
                               s3c_lcd->fix.smem_len) >> 1;
        lcd_regs->lcdsaddr3 = LCD_WIDTH & 0x3ff;

        /* 4.1 开屏：先允许 PWREN，再开 ENVID，最后拉背光 */
        lcd_regs->lcdcon5 |= (1 << 3);
        lcd_regs->lcdcon1 |= (1 << 0);

        /* 4.2 注册 */
        register_framebuffer(s3c_lcd);

        return 0;
}

八个宏到寄存器的落点：CLKVAL→LCDCON1，LINEVAL/VBPD/VFPD/VSPW→LCDCON2，HOZVAL/HBPD/HFPD→LCDCON3，HSPW→LCDCON4。开屏顺序是 PWREN → ENVID → 背光，背光那一步写 GPGDAT 的 bit4：

c
        *gpgdat |= (1 << 4);

模块出口严格按申请的逆序释放：

c
static void __exit lcd_exit(void)
{
        unregister_framebuffer(s3c_lcd);

        lcd_regs->lcdcon1 &= ~(1 << 0);         /* 关 ENVID */
        lcd_regs->lcdcon5 &= ~(1 << 3);         /* 关 PWREN */
        iounmap(lcd_regs);

        dma_free_wc(&s3c_device_lcd.dev,
                    PAGE_ALIGN(s3c_lcd->fix.smem_len),
                    s3c_lcd->screen_base, s3c_lcd->fix.smem_start);

        clk_disable_unprepare(lcd_clk);
        clk_put(lcd_clk);

        framebuffer_release(s3c_lcd);
}

module_init(lcd_init);
module_exit(lcd_exit);
MODULE_LICENSE("GPL");

素材原稿在这一版上有几个问题，逐条列出，我们写的时候已经改掉：

  • 素材写 if (regno > 16) 越界，改成 >= 16。
  • 素材在 chan_to_field 那一版里声明 pal 却不用，改成直接写 pseudo_palette[regno]。
  • 素材用 return 直接从 lcd_init 里退出，cls_get 成功之后 framebuffer_alloc 失败会漏掉时钟，改成统一走错误路径（上面为了紧凑只保留了主路径，工程里每一处 return -ENOMEM 都该配一次 clk_disable_unprepare）。
  • 素材的 dma_free_wc 传的是未对齐的 smem_len，改成 PAGE_ALIGN 后的值。
  • 素材把 clk_put 漏了，模块卸载后时钟引用计数不减，反复加载会失败。

一个更靠得住的做法是不要自己 ioremap GPIO，改用 devm_* 和 platform driver 那套框架。S3C2440 的寄存器基址在 BSP 里已经有 S3C24XX_PA_GPIO 这类宏，硬编码 0x56000020 换到别的板子上就废了。

十七、测试程序怎么写 #

驱动加载起来，/dev/fb0 就出现了。先确认：

text
[root@zy:/]# ls -l /dev/fb*
crw-rw----    1 root     root       29,   0 Jan  1 00:00 /dev/fb0

主设备号 29、次设备号 0 对上就说明 register_framebuffer 走通了。

三个最常用的 ioctl：FBIOGET_VSCREENINFO 取可变参数、FBIOGET_FSCREENINFO 取固定参数、FBIOPUT_VSCREENINFO 写可变参数（改分辨率、翻页）。

一个程序同时做查询和画屏，最省事：

c
#include <stdio.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <linux/fb.h>

int main(int argc, char **argv)
{
        int fd = open("/dev/fb0", O_RDWR);
        struct fb_var_screeninfo var;
        struct fb_fix_screeninfo fix;
        unsigned short *fb;
        unsigned long i, n;
        unsigned short color;

        if (fd < 0) {
                perror("open /dev/fb0");
                return 1;
        }
        ioctl(fd, FBIOGET_VSCREENINFO, &var);
        ioctl(fd, FBIOGET_FSCREENINFO, &fix);

        printf("id       = %s\n", fix.id);
        printf("resolution = %u x %u (virtual %u x %u)\n",
               var.xres, var.yres, var.xres_virtual, var.yres_virtual);
        printf("bpp      = %u\n", var.bits_per_pixel);
        printf("line_len = %u bytes\n", fix.line_length);
        printf("smem     = 0x%lx len %u\n", fix.smem_start, fix.smem_len);

        if (argc < 2)
                return 0;

        /* 颜色由命令行给：red / green / blue / off */
        if (!strcmp(argv[1], "red"))        color = 0xF800;
        else if (!strcmp(argv[1], "green")) color = 0x07E0;
        else if (!strcmp(argv[1], "blue"))  color = 0x001F;
        else                                color = 0x0000;

        fb = mmap(NULL, fix.smem_len, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
        if (fb == MAP_FAILED) {
                perror("mmap");
                return 1;
        }

        n = fix.line_length * var.yres / sizeof(unsigned short);
        for (i = 0; i < n; i++)
                fb[i] = color;

        munmap(fb, fix.smem_len);
        close(fd);
        return 0;
}

十八、从 fbdev 迁移到 DRM #

先说结论：S3C2440 这类老平台没有上游 DRM 驱动。samsung 的 DRM 驱动从 Exynos 4210 起步，2440 不在支持列表里。所以迁移对 2440 本身不是「换个驱动」，而是「换芯片或自己写一个 DRM 驱动」。

对其它平台，迁移的路径是明确的。按工作量和收益排：

场景 推荐做法 说明
应用只需要一块可写的屏 继续用 /dev/fb0 DRM 驱动的 fbdev emulation 会提供这个节点
要做多图层、硬件叠加 改 DRM plane API fbdev 没有对应能力
要做零拷贝 GPU 渲染上屏 GEM + dma-buf + atomic commit fbdev 无 buffer 共享模型
新写一颗 SoC 的显示驱动 直接写 DRM/KMS 不要再新写 fbdev 驱动
老驱动想被上游接受 改造成 DRM 上游不接受新 fbdev 驱动

概念对照表，改代码时按这张表翻：

fbdev DRM/KMS 差异要点
fb_info drm_device + drm_crtc 等对象 一个变六个
fix.smem_start / smem_len drm_gem_object / drm_framebuffer 显存由 GEM 管，不再是一块固定地址
var.xres / yres drm_display_mode / mode_config 模式列表从 connector 的 EDID 来
var.pixclock + 六个 margin drm_display_mode 的 clock/hdisplay/htotal 等 换成「总量」表述，不再拆前后肩
fb_set_par atomic_commit / crtc_helper_set_mode 整帧原子生效
fb_pan_display atomic commit 里改 plane->fb 双缓冲由提交序列管理
fb_fillrect / fb_copyarea plane 硬件合成 真实硬件加速
register_framebuffer drm_dev_register —
/dev/fb0 /dev/dri/card0 + /dev/fb0（emulation） 两者可同时存在
FBIOGET_VSCREENINFO DRM_IOCTL_MODE_GETCRTC 信息更细

模式参数换算最别扭的一处：fbdev 用「可见区 + 前后肩 + 同步宽」，DRM 用「总量」。两者互换：

text
htotal = xres + right_margin + left_margin + hsync_len
hdisplay = xres
hsync_start = xres + right_margin
hsync_end = hsync_start + hsync_len

vtotal = yres + lower_margin + upper_margin + vsync_len
vdisplay = yres
vsync_start = yres + lower_margin
vsync_end = vsync_start + vsync_len

时钟也一样：fbdev 的 pixclock 是皮秒，DRM 的 mode->clock 是 kHz，clock = 10^9 / pixclock。T35 的 pixclock = 156250 对应 clock = 6400，即 6.4MHz。这个换算关系是上限，实际写进 DRM 的时钟要按屏手册给的总线带宽乘一个系数，各驱动不同，具体系数未验证。

最小的迁移步骤：

  1. 保留应用侧的 /dev/fb0 使用方式，先让 DRM 驱动的 CONFIG_DRM_FBDEV_EMULATION=y 把兼容节点打开。这一步不做任何应用改动。
  2. 应用逐步改到 DRM：先替换查询部分（FBIOGET_VSCREENINFO → DRM_IOCTL_MODE_GETRESOURCES），再替换显存获取（mmap /dev/fb0 → GEM dumb buffer + mmap）。
  3. 最后替换提交路径（FBIOPUT_VSCREENINFO → DRM_IOCTL_MODE_ATOMIC）。
  4. 驱动侧：如果手头有正在维护的 fbdev 驱动，评估是否直接对接 drm_simple_display_pipe（drivers/gpu/drm/tiny/ 下有参考实现），它给的是最简单的单 CRTC 单 plane 模型，工作量比完整 KMS 小得多。

同一块显存被两套接口同时操作的坑：fbcon 还在 /dev/fb0 上画，DRM 应用往 GEM 缓冲里渲染，两边互不知道，屏上就会出现闪烁。解决办法是从内核命令行去掉 console=tty1 的 framebuffer 输出，或者用 fbcon=map:1 把 fbcon 挪到别的 fb 上。

这篇的定位再强调一次：fbdev 是上一代框架，理解它的价值在于看懂「一块显存怎么变成屏幕上的像素」这条最短路径，以及读懂大量遗留代码。新驱动从 DRM 起步。

LCDSADDR2 那一行值得单独讲，因为素材里有两版不同的值：

s3c2410fb.c（内核驱动） 0x19ce0000 0x19cf2c00 0x000000f0

最后一行对应素材里那个真实故障：手写的模块驱动 insmod 之后，打印出来的 lcdcon[1..5] 全是 0x00。原稿的诊断是「排查了很久也没找到原因」。从代码看，最可疑的两处是：ioremap 返回的指针被声明成 volatile struct lcd_regs *（丢掉了 __iomem 属性），以及 lpcsel 的偏移在结构体里算错导致写越界。这两条都是「读回全 0」的典型成因，属于推断，未在板子上验证。

另一个素材里没解决的问题：「LCD 上能看到企鹅 logo，过一会屏幕就什么都没了」。这类现象在 fbcon 接管之后出现，多半是 fbcon 里的某个绘制回调把整屏清成了黑色，或者 cfb_fillrect 读到的 var 位域不对把黑当成了背景色。排查办法是把 console=tty1 去掉再看是否还闪，去掉后正常就锁定在 fbcon 配置上。

二十、易错点速查 #

挑最容易踩的，一条一行。

# 易错点 后果 正确做法
1 寄存器字段忘了减一 分辨率差 1 像素，边界出杂色 所有 *PWS/*OZVAL/*INEVAL 都 -1
2 left_margin 当成 HBPD 填 图像左右偏移 left_margin→HFPD，right_margin→HBPD
3 CLKVAL 直接填不取整 编译告警或截断 整数除法，向下取整
4 改时序前没关 ENVID 屏上瞬间花屏 先清 [0]，改完再置
5 smem_len 没按 PAGE_ALIGN 分配失败或释放错乱 分配和释放都用对齐值
6 dma_alloc_wc 首参传 NULL 取 dev->dma_mask 时出错 传 &pdev->dev 或 &s3c_device_lcd.dev
7 line_length 填成行像素数 cfb_* 跨行错位 填字节数 xres × bpp / 8
8 regno > 16 的调色板判断 数组越界写 regno >= 16
9 fb_fillrect 等三个回调不填 fbcon 画字解引用空指针 挂 cfb_*
10 16bpp 下 HWSWP 没开 颜色错乱 16bpp 固定 BSWP=0、HWSWP=1
11 FRM565 没开 颜色发暗、绿色不准 16bpp 显式置 [11]
12 LCDSADDR2 用 & 0x1fffff 高地址被截断，刷新异常 先算完整地址再取位段
13 bits_per_pixel 填 18 走 default，屏不刷 只用 1/2/4/8/16/24/32
14 引脚复用没配 屏无输出 GPCCON/GPDCON 填 0xaaaaaaaa
15 背光 GPIO 没拉高 有图像但看不见 GPGDAT 相应位置 1
16 卸载时漏 clk_put 反复加载失败 申请和释放成对
17 双缓冲只改 yoffset 不改 LCDSADDR1 翻页无效 fb_pan_display 里重写地址寄存器
18 应用层用可见宽度算下标 双缓冲下斜向撕裂 用 line_length / 2 或 xres_virtual
19 用 write() 做动画 帧率低到不可用 走 mmap，或者直接写显存
20 以为挂 cfb_* 就是硬件加速 性能预期落空 cfb_* 是软件实现，加速要置 FBINFO_HWACCEL_*
21 新项目还在用 fbdev 上游不收，将来断维护 新驱动写 DRM
