这是整个驱动模块的入口篇。读完它，你应该能回答五个问题：驱动程序到底在系统里占什么位置、驱动框架为什么要分「层」和「主机/外设」两刀、Linux 把设备分成哪几类、一个字符设备驱动从零到能跑分几步、驱动是怎么被内核加载进去的。

一、驱动程序是什么 #

1.1 从裸机到操作系统 #

我们在 Mini2440 上写裸机程序时，点亮 LED、在 LCD 上显示图片，都是直接操作寄存器。但开发板移植了 Linux 内核之后，"点亮 LED"这件事就变了：应用程序无法和硬件直接打交道。

于是驱动程序登场，它充当硬件和应用程序之间的枢纽：

应用程序（用户空间）  open/read/write/ioctl/mmap 系统调用
        ↓  ↑  ────────── 系统调用边界 ──────────
驱动程序（内核空间）  把系统调用翻译成对寄存器的读写
        ↓  ↑
硬件                  寄存器 / 中断 / DMA

正因为驱动程序的表现形式就是"一些标准的、事先协定好的 API 函数"，写一个驱动本质上就是去完成相应函数的填充。这也是为什么学驱动最难的往往不是硬件本身，而是摸清现有框架、找到该填的那几个坑。

1.2 设备驱动程序的四项职责 #

设备驱动程序作为操作系统内核和机器硬件之间的接口，为应用程序屏蔽硬件细节，使硬件设备在应用程序中表现为设备文件，可以像操作普通文件一样操作硬件。例如应用程序通过设备驱动程序向打印机发送打印指令，而无需了解打印机的硬件实现细节。它承担四件事：

  1. 设备初始化和释放：在系统启动或模块加载时初始化设备，在设备停止使用时释放相关资源。
  2. 数据传输：实现内核与硬件之间的数据交互，包括把数据从内核传送到硬件，以及从硬件读取数据。
  3. 数据处理：读取应用程序传给设备文件的数据，并回送应用程序请求的数据。
  4. 错误检测与处理：及时检测设备出现的错误并进行相应处理，确保系统的稳定性。

1.3 驱动程序是"被动"的 #

这是新手最容易误解的一点。驱动程序从不主动运行：

  • 驱动程序加载进内核时，只是告诉内核"我在这里、我能做这些工作"，至于这些工作何时开始，取决于应用程序；
  • 它根据应用程序的要求进行初始化，根据应用程序的要求进行读写。

当然也有例外，比如完全可以写一个由系统时钟触发的驱动，让它自动点亮 LED。

与之配套的是权限差异：应用程序运行于用户空间，拥有 MMU 的系统能限制其权限（比如把它限制在某个内存块中），这可以避免应用程序的 bug 使整个系统崩溃；而驱动程序运行于内核空间，是系统信任的一部分，它的一个错误有可能导致整个系统崩溃。这也是驱动开发者必须比应用开发者更谨慎的根本原因。

1.4 驱动程序能用到的内核服务 #

驱动不是从零造轮子，内核提供了大量标准服务供其调用：

  • 内存分配：kmalloc、kzalloc、vmalloc 等动态分配内存，配合内存池等机制提高效率。
  • 中断发送与处理：硬件通过中断请求（IRQ）向内核报告事件，驱动在处理这些中断时能够响应设备状态的变化。
  • 等待队列：没有数据可读时，驱动可以让应用程序进入等待状态，直到有数据可用，从而提高系统整体效率。
  • 并发控制：自旋锁、信号量等，应对"驱动可能同时被多个进程使用"的场景。
  • 性能手段：例如硬盘驱动中，既可以用 DMA 也可以不用——用 DMA 时程序更复杂，但能显著提高效率。

动态加载是另一个关键机制：多数 Linux 设备驱动支持动态加载，驱动可以在需要时被加载至内核（用户插入新设备时自动加载），设备拔出后可被卸载，从而减少启动时所需的资源占用、提高资源利用率与灵活性。此外，用户还能按需配置驱动——开关特定功能、修改工作模式、调整带宽限制或其他参数，以适配具体应用场景。

1.5 驱动开发的难点不在硬件 #

Linux 内核本身就由各种驱动组成，源码中大约 85% 是各类驱动程序的代码。内核里驱动种类齐全，可以在同类驱动的基础上修改以符合具体单板。

编写驱动程序的难点并不是硬件的具体操作，而是弄清楚现有驱动程序的框架，在这个框架中加入这个硬件。

举个具体的例子：x86 架构的内核对 IDE 硬盘的支持非常完善——先通过 BIOS 得到硬盘信息，或使用默认 I/O 地址去枚举硬盘，然后识别分区、挂载文件系统。对于其他架构的内核，只要指定了硬盘的访问地址和中断号，后面的枚举、识别和挂接过程完全一样。也许修改的代码不超过 10 行，花费精力的地方在于：了解硬盘驱动的框架，找到修改的位置。

这也是为什么本模块后面每一篇芯片驱动移植，都遵循同一个套路：先分析框架，再找位置，最后才写代码。

二、驱动框架的两个设计思想：分层与分离 #

学完 I2C、USB、SD 驱动之后回头看，会发现一个共性：每个驱动都分三层。

text
1、XXX 设备驱动
2、XXX 核心层
3、XXX 主机控制器驱动

需要我们编写的主要是设备驱动部分，主机控制器驱动部分也有少量编写，二者交互主要通过核心层提供的接口实现。这背后是 Linux 设备驱动开发中的两个思想：分层与分离。

这一章是后面所有子系统的阅读方法：先问「分了几层、每层管什么」，再问「主机侧与外设侧的边界在哪」，框架就立住了。

分层：核心层做默认实现，底层按需重载 #

2.1 从面向对象说起 #

面向对象程序设计中，可以为某一类相似的事物定义一个基类，具体事物继承基类的函数。如果某函数的实现与基类一致，就可以直接继承；不一致则可以重载。这种设计极大提高了代码可复用能力，是对现实世界事物间关系的一种良好呈现。

Linux 内核完全由 C 语言和汇编写成，却频繁用到了面向对象的设计思想。在设备驱动方面，往往为同类的设备设计一个框架，框架中的核心层实现该类设备的通用功能；如果具体设备不想用核心层的实现，它可以重载之。

2.2 核心层如何决定用谁的实现 #

核心层函数先检查底层设备是否重载了某个操作，重载了就走底层代码，否则走通用实现：

c
return_type core_funca(xxx_device *bottom_dev, param1_type param1, param1_type param2)
{
    if (bottom_dev->funca)
        return bottom_dev->funca(param1, param2);

    /* 核心层通用的 funca 代码 */
    ...
}

这样做的好处是：核心层代码可以处理绝大多数该类设备的 funca() 功能，只有少数特殊设备需要重新实现。

2.3 更典型的分层形态：通用流程 + 底层 ops #

再看一个更常见的例子。假设为了实现 funca()，同类设备的操作流程完全一致，都要经过：

通用代码A → 底层 ops1 → 通用代码B → 底层 ops2 → 通用代码C → 底层 ops3

那么核心层就长成这样：

c
return_type core_funca(xxx_device *bottom_dev, param1_type param1, param1_type param2)
{
    /* 通用的步骤代码 A */
    ...
    bottom_dev->funca_ops1();

    /* 通用的步骤代码 B */
    ...
    bottom_dev->funca_ops2();

    /* 通用的步骤代码 C */
    ...
    bottom_dev->funca_ops3();
}

分层设计带来的好处很明显：通用代码 A、B、C 具体底层驱动不需要再实现，只需关心自己的底层操作 ops1、ops2、ops3。

分层的层数并不固定，可能只有 2 层，也可能是多层。

2.4 哪些子系统用了分层 #

这种分层化设计在 Linux 的 input、RTC、MTD、I2C、SPI、TTY、USB 等诸多设备驱动类型中屡见不鲜。

分离：主机控制器与外设解耦 #

2.5 不分离会怎样 #

除了分层，Linux 设备驱动框架还用了分离的思想。

假设要通过 SPI 总线访问某外设。这个访问过程中，要通过操作 CPU 上的 SPI 控制器寄存器来达到访问 SPI 外设的目的。最简单的方法是：

c
return_type xxx_write_spi_yyy(...)
{
    xxx_write_spi_host_ctrl_reg(ctrl);
    xxx_write_spi_host_data_reg(buf);
    while (!(xxx_spi_host_status_reg() & SPI_DATA_TRANSFER_DONE))
        ;
    ...
}

按这种方式设计，结果是对于任何一个 SPI 外设，它的驱动代码都是 CPU 相关的。用在 CPU XXX 上时访问 XXX 的 SPI 主机控制寄存器，用在 CPU XXX1 上时就要访问 XXX1 的寄存器：

c
return_type xxx1_write_spi_yyy(...)
{
    xxx1_write_spi_host_ctrl_reg(ctrl);
    xxx1_write_spi_host_data_reg(buf);
    while (!(xxx1_spi_host_status_reg() & SPI_DATA_TRANSFER_DONE))
        ;
    ...
}

这显然不能接受——这意味着外设 YYY 用在不同 CPU 上时需要不同的驱动。

2.6 分离之后 #

把主机控制器驱动和外设驱动分开：

   外设 a     外设 b     外设 c          ← 只调核心层通用 API
      \        |        /
       +-------+-------+
       |   XXX 核心层    |              ← 统一的数据传输接口
       +-------+-------+
      /        |        \
  主机控制器A 主机控制器B 主机控制器C     ← 只关心自己的寄存器

这样的结构是：外设 a、b、c 的驱动与主机控制器 A、B、C 的驱动互不相关——主机控制器驱动不关心外设，外设驱动也不关心主机，外设只访问核心层的通用 API 进行数据传输，主机和外设之间可以任意组合。

2.7 m + n 与 m × n #

把成本算清楚就明白这个设计值多少：

方案 需要的驱动数 m = 3 主机、n = 3 外设时
不分离 m × n 9 个
分离 m + n 6 个

主机控制器和外设越多，差距越大。这就是分离思想的价值。

2.8 哪些子系统用了分离 #

Linux 的 SPI、I2C、USB、ASoC（ALSA SoC）等子系统都典型地利用了这种分离的设计思想。

两者关系：一纵一横 #

分层 分离
切的方向 纵向：同一类设备，从上到下分核心层与具体驱动 横向：主机控制器与外设，左边和右边解耦
解决的问题 通用流程写一次，底层只填差异 m 个主机 + n 个外设只需写 m + n 个驱动
典型子系统 input、RTC、MTD、TTY SPI、I2C、USB、ASoC
关键机制 核心层做默认实现，底层按需重载 核心层提供统一 API，两侧互不感知

实际子系统往往两者同时使用：SPI 子系统既是分层的（核心层 + 具体设备驱动），又是分离的（主机控制器驱动 vs SPI 外设驱动）。

后面读任何一个子系统的源码，先问这两个问题——"分了几层、每层管什么"和"主机侧与外设侧各自的边界在哪"——框架就立住了。

三、Linux 设备分类 #

Linux 将所有的外设分为三类。理解这个分类是理解字符设备位置的前提。

3.1 三类设备对照 #

维度 字符设备 块设备 网络设备
访问单位 字节 块 报文 / 包 / 帧
缓冲 通常不使用缓存，每字节直达硬件 使用 buffer 与 cache 内核协议栈统一管理
随机访问 不支持，顺序进行 支持，可直接访问任意位置 不适用
设备文件 有，如 /dev/ttyS0 有，如 /dev/sda1 没有 /dev 节点，用 eth0 这类名字
典型设备 串口、键盘、鼠标、传感器、LED IDE 硬盘、NAND FLASH、SD 卡 以太网卡、Wi-Fi
用户接口 open/close/read/write/ioctl 同字符设备 BSD 套接字接口

3.2 字符设备 #

字符设备是能够像字节流（比如文件）一样被访问的设备，即对它的读写以字节为单位。串口收发数据时就是一个字节一个字节进行的；我们可以在驱动内部使用缓冲区存放数据以提高效率，但串口本身对此没有要求。

字符设备的驱动程序中实现了 open、close、read、write 等系统调用，应用程序通过设备文件（如 /dev/ttySAC0）来访问字符设备。

本模块 02–03 章讲的就是这一类，因为它最贴近"驱动就是一组函数填充"的直观模型，也是理解 file_operations 的最佳入口。

3.3 块设备 #

块设备上的数据以块的形式存放，比如 NAND FLASH 上的数据以页为单位存放。块设备驱动程序向用户层提供的接口与字符设备一样，应用程序同样可以通过设备文件（如 /dev/mtdblock0、/dev/hda1）调用 open、close、read、write，与块设备传送任意字节的数据。对用户而言，字符设备和块设备的访问方式没有差别。

块设备的特别之处有两点：

  1. 操作硬件的接口实现方式不一样。块设备驱动先将用户发来的数据组织成块再写入设备；或从设备中读出若干块数据，再从中挑出用户需要的。
  2. 数据块上可以有格式。通常在块设备中按一定格式存放数据，不同的文件系统类型就是用来定义这些格式的。内核中，文件系统层次位于块设备驱动之上，这意味着块设备驱动除了向用户层提供与字符设备一样的接口外，还要向内核其他部件提供一些接口，这些接口用户看不到，它们使得可以在块设备上存放文件系统、挂载块设备。

详见《C.驱动/09-存储与块设备》。

3.4 网络设备 #

网络设备同时具有字符设备、块设备的部分特点，无法归入这两类：说它是字符设备，它的输入/输出却是有结构的、成块的（报文、包、帧）；说它是块设备，它的"块"又不是固定大小的，大到数百甚至数千字节，小到几字节。

UNIX 式操作系统访问网络接口的方法是给它们分配一个唯一的名字（如 eth0），但这个名字在文件系统中（比如 /dev 目录下）不存在对应的节点项。应用程序、内核和网络驱动程序间的通信完全不同于字符块设备——库和内核提供的是一套与数据包传输相关的函数（dev_queue_xmit、netif_rx 等），而不是 open、read、write。

详见《C.驱动/11-网络设备驱动》。

四、Linux 驱动开发流程 #

4.1 七步流程 #

一般来说，编写一个 Linux 设备驱动程序的大致流程如下：

  1. 查看原理图、数据手册，了解设备的工作原理与操作方法；
  2. 在内核中找到相近的驱动程序，以它为模板进行开发，有时候需要从零开始；
  3. 实现驱动程序的初始化：向内核注册这个驱动程序，这样应用程序传入文件名时，内核才能找到相应的驱动；
  4. 设计所要实现的操作：如 open、close、read、write 等函数；
  5. 实现中断服务（中断并不是每个设备驱动所必须的）；
  6. 编译该驱动程序到内核中，或者用 insmod 命令加载；
  7. 测试驱动程序。

第 2 步和上一节"难点不在硬件"是同一件事的两面说法：找模板比读手册更省时间。

4.2 编写驱动时要额外留意的三件事 #

  • 并发：驱动程序可能同时被多个进程使用，必须考虑并发问题（见《Linux 驱动并发控制》）；
  • 性能：尽可能发挥硬件作用以提高性能，例如在硬盘驱动中既可以使用 DMA 也可以不用，用 DMA 时程序复杂但效率更高；
  • 异常处理：必须处理硬件的各种异常情况，否则出错时可能导致整个系统崩溃。

4.3 一次 open 调用穿过了哪些层 #

假设我们已经写好 LED 的字符驱动并加载进内核，那么应用程序点亮 LED 的流程是这样的：

应用程序    open("/dev/led", O_RDWR)
   ↓
库(glibc)   根据参数执行 "swi" 指令，引发 CPU 异常，进入内核
   ↓
内核异常处理函数  根据参数找到对应的驱动程序，返回文件句柄给库，再返回给应用程序
   ↓
应用程序    得到句柄后，用 write / ioctl 发出控制命令
   ↓
库          再次执行 "swi" 指令进入内核
   ↓
内核异常处理函数  调用驱动程序中对应的函数

库（比如 glibc）提供给应用程序的 open、read、write、ioctl、mmap 等接口函数被称为系统调用，它们本质上都是设置好相关寄存器后，执行某条指令引发异常进入内核。除系统调用外，库还提供字符串处理（strcpy、strcmp）、输入输出（scanf、printf）、数学库，以及应用程序的启动代码等。

在异常处理函数中，内核会根据传入参数执行各种操作——比如根据设备文件名找到对应的驱动程序，再调用驱动程序里的相关函数。这条链路里"根据设备文件名找驱动"的那一步，靠的就是设备号，见第五章。

五、驱动程序如何进入内核 #

驱动写完后有两个去处：编译进内核随内核启动，或编译成模块按需加载。

5.1 两种加载方式对比 #

维度 静态编译进内核 动态加载模块（.ko）
时机 内核启动时随同加载 系统启动后按需 insmod
形态 内核镜像的一部分 独立的 .ko 文件
编译 改 Kconfig + Makefile，重编内核 模块依赖特定内核版本，单独编译
调试友好度 低（每次改动要重编内核 + 重启） 高（可反复 insmod / rmmod）
资源占用 常驻，即使不用也占内存 不用时可卸载
适用场景 根文件系统 / 存储 / 串口等启动必需驱动 外设、调试期驱动

模块的扩展名为 .ko，用 insmod 加载、rmmod 卸载。

5.2 三条常用命令 #

bash
insmod hello_dev.ko    # 加载模块
lsmod                  # 查看已加载模块（或 lsmod | grep hello）
rmmod hello_dev        # 卸载模块
cat /proc/devices      # 查看当前系统已注册的字符/块设备号
dmesg                  # 查看 printk 打印信息

dmesg -C 清空缓冲区，dmesg -c 先打印再清除。

5.3 静态编译进内核的完整步骤 #

以 hello_dev.c 为例，假设内核源码在 /work/sambashare/linux-5.2.8：

第一步，把源文件复制到对应目录：

bash
cp /work/sambashare/drivers/1.hello_dev/hello_dev.c /work/sambashare/linux-5.2.8/drivers/char/

第二步，在该目录的 Kconfig 中新增配置项：

text
config HELLO
        bool "hello_dev"
        default y
        help
          hello driver

第三步，在该目录的 Makefile 中新增编译规则：

makefile
obj-$(CONFIG_HELLO)             += hello_dev.o

第四步，在源码顶层配置并使能该选项：

bash
make menuconfig      # Device Drivers -> Character devices -> 勾选 hello_dev
make s3c2440_defconfig

六、字符设备驱动框架：hello_dev 实例 #

这一章是本文的核心，也是整个驱动开发的骨架。按顺序走完六步，一个字符设备驱动就立起来了。

6.1 框架全貌：三步走 #

字符设备框架可以概括为三件事，后面所有细节都是围绕它们展开：

  1. 注册一个设备号（静态 register_chrdev_region 或动态 alloc_chrdev_region）；
  2. 初始化并注册 cdev（cdev_init + cdev_add）；
  3. 实现文件操作集合（填充 struct file_operations）。

6.2 第一步：申请设备号 #

设备号 dev_t 是 32 位无符号整型：高 12 位是主设备号，低 20 位是次设备号。主设备号标识设备种类及对应的驱动，次设备号区分同一驱动下的不同硬件设备。

c
#define MINORBITS    20
#define MINORMASK    ((1U << MINORBITS) - 1)

#define MAJOR(dev)   ((unsigned int) ((dev) >> MINORBITS))
#define MINOR(dev)   ((unsigned int) ((dev) & MINORMASK))
#define MKDEV(ma,mi) (((ma) << MINORBITS) | (mi))

例如 /dev/tty1 是字符设备，其主设备号指向字符终端设备的驱动，次设备号用于区分它和 /dev/tty2、/dev/tty3。

方式一：静态注册一组设备号

c
int register_chrdev_region(dev_t from, unsigned count, const char *name);
  • from：起始设备号；
  • count：要注册的设备数量；
  • name：设备描述，会出现在 /proc/devices 中；
  • 返回值：成功 0，失败负值。

使用静态注册前，必须先确认哪些主设备号没被占用：

text
[root@zy:/]# cat /proc/devices
Character devices:
  1 mem
  4 ttyS
 10 misc
 13 input
 29 fb
 90 mtd
180 usb
188 ttyUSB
204 ttySAC
232 hello

方式二：动态分配（推荐，避免主设备号冲突）

c
int alloc_chrdev_region(dev_t *dev, unsigned baseminor, unsigned count, const char *name);
  • dev：存放起始设备编号的指针，之后可用 MAJOR/MINOR 宏提取主次设备号；
  • baseminor：次设备号的基准，即从第几个次设备号开始分配；
  • count：需要连续注册的次设备编号个数；
  • name：字符设备的名字。

对应的注销函数：

c
void unregister_chrdev_region(dev_t from, unsigned count);

6.3 第二步：初始化并注册 cdev #

c
struct cdev *gDev;

// 1. 申请内存
gDev = kzalloc(sizeof(struct cdev), GFP_KERNEL);

// 2. 用 file_operations 初始化 cdev
cdev_init(gDev, gFile);
gDev->owner = THIS_MODULE;

// 3. 把 cdev 注册进内核，与设备号绑定
cdev_add(gDev, devNum, subDevNum);

// 4. 卸载时移除
cdev_del(gDev);

cdev_add 成功后，设备即处于活动状态，内核可以调用其操作函数。但此时用户空间还无法访问——/dev 下还没有节点，见 5.6。

6.4 第三步：实现 file_operations #

字符设备驱动由七个主要函数和一个结构体组成：

函数 职责
open 打开设备文件时调用，负责设备初始化。例如打开串口时配置波特率、数据位、停止位
release 关闭设备文件时调用，释放资源，例如关闭串口连接并保存配置
write 把用户空间数据写入设备，通常需先复制到内核空间，再发送到硬件
read 从设备读取数据并传回用户空间，可能实现缓冲机制以保证高效读取
ioctl 实现设备特定的控制命令，如获取设备信息或更改参数
init 驱动加载时调用，初始化设备并注册到内核，通常调用设备号注册函数
exit 驱动卸载时调用，执行反注册操作，确保资源正确释放

七者通过 struct file_operations 交给内核——这个结构体是与内核交互的桥梁：

c
struct file_operations my_fops = {
    .owner          = THIS_MODULE,
    .open           = my_open,
    .release        = my_release,
    .write          = my_write,
    .read           = my_read,
    .unlocked_ioctl = my_ioctl,
};

内核在相应用户操作发生时调用对应函数指针。通过实现这些函数，驱动就为设备提供了具体操作功能，使得应用程序能方便地与硬件通信。这个框架为各种字符设备提供了统一接口，大大简化了驱动开发。

每个成员的逐字段解析见《file、inode 与 file_operations》；read/write 的 __user 语义与 copy_to_user 见《read()、write() 与用户空间数据拷贝》。

6.5 hello_dev 的完整骨架 #

把前面三步串起来，hello_init 的完整流程如下：

c
static int hello_init(void)
{
    int ret = 0;

    printk("%s enter.\n", __func__);

    devNum = MKDEV(reg_major, reg_minor);

    /* 1. 静态注册一组字符设备编号 */
    ret = register_chrdev_region(devNum, subDevNum, "hello_dev");
    if (ret < 0) {
        printk("register char dev region error\n");
        goto fail_devid;
    }

    /* 2. 申请 cdev 与 file_operations 内存 */
    gDev = kzalloc(sizeof(struct cdev), GFP_KERNEL);
    if (!gDev) {
        printk("kzalloc for cdev error\n");
        goto fail_gdev;
    }

    gFile = kzalloc(sizeof(struct file_operations), GFP_KERNEL);
    if (!gFile) {
        printk("kzalloc for file_operations error\n");
        goto fail_gfile;
    }

    /* 3. 填充操作集合 */
    gFile->owner = THIS_MODULE;
    gFile->open  = hello_open;
    gFile->read  = hello_read;
    gFile->write = hello_write;

    /* 4. 初始化并注册 cdev */
    cdev_init(gDev, gFile);
    gDev->owner = THIS_MODULE;
    cdev_add(gDev, devNum, subDevNum);

    /* 5. 创建设备类与设备节点，交给 udev/mdev 自动生成 /dev 节点 */
    hello_class = class_create(THIS_MODULE, "hello_dev");
    device_create(hello_class, NULL, devNum, NULL, "hello_dev");

    return 0;

fail_gfile:
    kfree(gDev);
fail_gdev:
    unregister_chrdev_region(devNum, subDevNum);
fail_devid:
    return ret;
}

注意 goto 的逆序回滚写法：每个失败标签只回滚它之前已经成功的那一步，这是内核里最标准的错误处理风格。对应的退出函数按相反顺序拆解：

c
static void hello_exit(void)
{
    device_destroy(hello_class, devNum);
    class_destroy(hello_class);
    cdev_del(gDev);
    kfree(gFile);
    kfree(gDev);
    unregister_chrdev_region(devNum, subDevNum);
}

6.6 设备节点的两种创建方式 #

前面提到 cdev_add 成功后用户空间仍不能访问，因为必须先在 /dev 下创建设备节点。设备文件的作用是：应用程序 open 一个设备时，内核先从文件属性中取得设备类型（c / b）、主设备号、次设备号，再据此找到对应的 file_operations，从而找到驱动里的读写方法。

手工创建：

bash
mknod /dev/hello c 主设备号 次设备号

例如主设备号 232、次设备号 0：

bash
mknod /dev/hello c 232 0

自动创建（推荐）：驱动里调用 class_create + device_create，由 udev/mdev 在 /dev 下自动生成节点。

c
hello_class = class_create(THIS_MODULE, "hello_dev");            // 生成 /sys/class/hello_dev
device_create(hello_class, NULL, devNum, NULL, "hello_dev");     // 触发 uevent，udev 建 /dev/hello_dev

c
device_destroy(hello_class, devNum);   // 卸载时删除节点
class_destroy(hello_class);

class_device_create 是 2.6 早期版本的函数名，现已改为 device_create。

class_create / device_create 的内部机制见《struct_class设备类架构详解》；udev 与 mdev 的原理与配置见《udev 与 mdev：设备节点的自动创建》。

6.7 一个容易混的点：cdev_add 与 device_create 各管什么 #

函数 管什么 不管什么
cdev_init + cdev_add 把字符设备注册进内核，cdev_add 成功后设备处于活动状态，内核可调用其操作 不会创建 /dev 下的节点
class_create + device_create 在 /sys/class/<name> 下建立条目，并触发 uevent 让 udev/mdev 创建 /dev/<name> 不负责设备注册本身

缺了前者，用户态 open 找不到驱动；缺了后者，/dev 下没有节点可打开。两者都要有。

6.8 测试驱动 #

以文件读写方式做最小验证（不写测试程序也能确认驱动在跑）：

bash
insmod hello_dev.ko          # 加载
ls /dev/hello_dev            # 确认节点已生成
echo "hello" > /dev/hello_dev   # 触发 write
cat /dev/hello_dev           # 触发 read
dmesg | tail                 # 查看 printk 输出
rmmod hello_dev              # 卸载

真实项目的测试程序一般以 C 文件编写，交叉编译后拷到开发板运行：

bash
arm-linux-gcc -o flowled flowled.c

应用程序侧固定三件事：open 打开设备文件 → 用 write/ioctl/read 发起操作 → close 释放。这套流程在任何一个字符设备驱动上都是通用的。
