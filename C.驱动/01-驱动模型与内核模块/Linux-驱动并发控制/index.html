设备驱动必须要解决的一个问题是多个执行单元对共享资源的并发访问，并发访问会导致竞态。即使是经验丰富的驱动工程师，也常常设计出包含并发问题 bug 的驱动程序。

一、基础概念 #

1.1 四个概念 #

概念 定义
并发（concurrency） 多个执行单元同时、并发被执行。宏观上看多个任务并行执行，微观上仍是串行的（受"时间片"调度）
竞态（race condition） 并发执行单元对共享资源（硬件资源、软件上的全局变量、静态变量等）的访问导致的资源错误状态
临界区（Critical Section） 每个进程中访问临界资源的那段代码
临界资源 一次仅允许一个进程使用的资源。多道程序中很多资源一次只能供一个进程使用

打个比方：类似两条十字交叉的道路上运行的车，当它们同一时刻要经过共同的资源（交叉点）时，如果没有交通信号灯，就可能出现混乱。

1.2 并发产生的四种场合 #

# 场合 说明
1 SMP 的多个 CPU 对称多处理器是共享存储的系统模型，多个 CPU 使用共同系统总线，可访问共同的外设和存储器，实现真正的并行
2 单 CPU 内进程与抢占它的进程 一个进程在内核执行时，有可能被另一个高优先级进程打断
3 中断和进程之间 中断可以打断正在执行的进程。如果中断处理程序访问了进程正在访问的资源，竞态就会发生
4 单 CPU，中断与中断之间 高优先级中断打断低优先级中断

1.3 解决竞态的核心原则 #

保证对共享资源的互斥访问——所谓互斥访问，是指一个执行单元在访问共享资源的时候，其他执行单元被禁止访问。

Linux 提供了多种互斥途径。搞清它们"相同在哪、区别在哪、该用在哪、有什么副作用"，要从所处环境细化分类：是 UP（单 CPU）还是 SMP（多 CPU）；是抢占式内核还是非抢占式内核；是在中断上下文还是进程上下文。

三个常用机制的定位：

机制 一句话 保护对象
原子操作 不可能被其他任务打断，一切（包括中断） 针对单个变量
自旋锁 忙等待锁，确保互斥 针对临界区
信号量 一个变量 + 两个原语操作 针对临界区，可睡眠

解决竞态问题的途径，本质上都是在共享资源周围放一盏"交通信号灯"。

二、途径一：中断屏蔽 #

在单 CPU 范围内避免静态竞态的一种简单省事的办法，是在进入临界区之前屏蔽系统的中断。

这项功能可以保证正在执行的内核路径不被中断处理程序抢占，从而防止某些竞争条件。具体而言：

  • a — 中断屏蔽将使得中断和进程之间的并发不再发生；
  • b — 由于 Linux 内核的进程调度等操作都依赖中断来实现，内核抢占进程之间的并发也得以避免。

2.1 API #

c
local_irq_disable();
local_irq_enable();

只能禁止/使能本地 CPU 的中断，不能解决多 CPU 引发的竞态。

c
local_irq_save(flags);
local_irq_restore(flags);

除了禁止/使能中断，还保存和还原当前 CPU 的中断位信息。这才是正确的用法——只 disable 不恢复，会把进入临界区之前已经关中断的状态错误地打开。

c
local_bh_disable();
local_bh_enable();

如果只是想禁止中断的底半部（softirq/tasklet），这是个不错的选择。

2.2 两条注意事项 #

  1. 中断对系统正常运行很重要，长时间屏蔽很危险，可能造成数据丢失乃至系统崩溃，所以中断屏蔽后应尽可能快地执行完毕。
  2. 宜与自旋锁联合使用。

结论：不建议单独使用中断屏蔽。 它是自旋锁的底层组成部分，但它本身粒度太粗——一旦屏蔽中断，很多事情都做不了。

三、途径二：原子操作 #

原子操作就是绝不会在执行完毕前被任何其他任务和中断打断、不会执行一半又去执行其他代码的操作。原子操作需要硬件的支持，因此与架构相关，其 API 和类型定义在 include/asm/atomic.h 中，用汇编语言实现。

3.1 atomic_t 的定义 #

c
typedef struct { volatile int counter; } atomic_t;

volatile 关键字用来暗示 GCC 不要对该类型做数据优化，所以对这个变量 counter 的访问都基于内存，不要将其缓冲到寄存器中。若缓冲到寄存器，可能导致内存中的数据已经改变，而寄存器中的数据没变。

3.2 原子整型操作 #

1）定义原子变量：

c
#define ATOMIC_INIT(i)  ( (atomic_t) { (i) } )

atomic_t v = ATOMIC_INIT(0);    /* 定义原子变量 v 并初始化为 0 */

2）设置原子变量的值：

c
#define atomic_set(v, i)  ((v)->counter = (i))
void atomic_set(atomic_t *v, int i);       /* 设置原子变量的值为 i */

3）获取原子变量的值：

c
#define atomic_read(v)  ((v)->counter + 0)
int atomic_read(atomic_t *v);              /* 返回原子变量的值 */

4）原子变量加/减：

c
static __inline__ void atomic_add(int i, atomic_t *v);   /* 原子变量增加 i */
static __inline__ void atomic_sub(int i, atomic_t *v);   /* 原子变量减少 i */

5）原子变量自增/自减：

c
#define atomic_inc(v)  atomic_add(1, v);   /* 原子变量加 1 */
#define atomic_dec(v)  atomic_sub(1, v);   /* 原子变量减 1 */

6）操作并测试：

c
/* 对原子变量执行自增、自减后测试是否为 0，是则返回 true，否则返回 false */
#define atomic_inc_and_test(v)  (atomic_add_return(1, (v)) == 0)
static inline int atomic_add_return(int i, atomic_t *v);

3.3 实例：用原子操作实现"设备只能被一个进程打开" #

c
static atomic_t v = ATOMIC_INIT(1);

static int hello_open(struct inode *inode, struct file *filep)
{
    printk("hello_open()\n");

    if (!atomic_dec_and_test(&v)) {
        atomic_inc(&v);          /* 恢复计数，别把坑留给自己 */
        return -EBUSY;
    }
    return 0;
}

static int hello_release(struct inode *inode, struct file *filep)
{
    printk("hello_release()\n");
    atomic_inc(&v);
    return 0;
}

这段代码的逻辑值得细看：初值 1，第一个 open 减到 0、atomic_dec_and_test 返回真，允许打开；第二个进程再减就变成负数，返回假，此时要把计数加回来（否则计数会一路往下掉，最后连"是否被占用"都判断不了），并返回 -EBUSY。

3.4 对照：一个经典的错误写法 #

很多教材先给出这段"错误示范"，然后问你问题在哪：

c
static int flage = 1;

int hello_open(struct inode *inode, struct file *file)
{
    if (flage != 1)
        return -EBUSY;

    flage = 0;

    return 0;
}

int hello_release(struct inode *inode, struct file *file)
{
    flage++;
    return 0;
}

问题在于"判断"与"修改"是两条独立指令，中间可以被抢占：

进程 A: 读 flage → 1，判断通过
        ← 此刻被抢占（或来了中断）
进程 B: 读 flage → 仍然是 1，判断通过
进程 B: 写 flage = 0，打开成功
进程 A: 恢复执行，写 flage = 0，也打开成功
        ✗ 两个进程同时持有设备

正是这种"读-判-写"的不可分割需求，催生了原子操作。

3.5 优缺点 #

  • 优点：编写简单。
  • 缺点：功能太简单，只能做计数操作，保护的东西太少。

四、途径三：自旋锁 #

自旋锁是专为防止多处理器并发而引入的一种锁，应用于中断处理等部分。对于单处理器来说，防止中断处理中的并发可简单采用关闭中断的方式，不需要自旋锁。

4.1 自旋的语义 #

自旋锁最多只能被一个内核任务持有。如果一个内核任务试图请求一个已被争用的自旋锁，那么这个任务就会一直忙循环——"旋转"——等待锁重新可用。要是锁未被争用，请求它的内核任务便立刻得到它并继续执行。

自旋锁在任何时刻防止多于一个内核任务同时进入临界区，因此可有效避免多处理器上并发运行的内核任务竞争共享资源。

4.2 API #

c
spinlock_t spin;             /* 定义自旋锁 */
spin_lock_init(lock);        /* 初始化自旋锁 */
spin_lock(lock);             /* 成功获得立即返回，否则自旋直到持有者释放 */
spin_trylock(lock);          /* 成功获得立即返回真，否则返回假，不在原地打转 */
spin_unlock(lock);           /* 释放自旋锁 */

4.3 实例 #

c
static spinlock_t lock;
static int flag = 1;

static int hello_open(struct inode *inode, struct file *filep)
{
    spin_lock(&lock);

    if (flag != 1) {
        spin_unlock(&lock);
        return -EBUSY;
    }

    flag = 0;
    spin_unlock(&lock);
    return 0;
}

static int hello_release(struct inode *inode, struct file *filep)
{
    flag = 1;
    return 0;
}

注意 release 里没有加锁——这是不严谨的。同一把锁保护同一份数据，读和写都要加，否则 release 的 flag = 1 仍可能与另一个 CPU 上的 open 交错。正确写法是 release 也 spin_lock/spin_unlock 包起来。

4.4 适用场合 #

自旋锁主要针对 SMP 或单 CPU 但内核可抢占的情况。对于单 CPU 且内核不支持抢占的系统，自旋锁退化为空操作。

在单 CPU 和内核可抢占的系统中，自旋锁持有期间内核的抢占将被禁止。由于内核可抢占的单 CPU 系统的行为实际很类似于 SMP 系统，因此在这样的单 CPU 系统中使用自旋锁仍十分重要。

4.5 自旋锁的四个特性 #

被自旋锁保护的临界区代码执行时：

  • a — 不能进入休眠；
  • b — 不能被其他中断打断（需配合 spin_lock_irqsave 等衍生形式）；
  • c — 内核不能被抢占；
  • d — 结论：它不能因为任何原因放弃处理器。

4.6 两种典型的死锁 #

死锁 1：持锁睡眠

进程 A 拥有自旋锁后在内核态阻塞了（比如调用了会睡眠的函数），内核调度进程 B，B 也要获得同一把自旋锁，只能自旋；而此时抢占已经关闭，A 不会被调度回来，B 永远自旋。

死锁 2：中断取锁

进程 A 拥有自旋锁，中断来了，CPU 执行中断处理函数，中断处理函数也需要获得同一把锁访问共享资源，此时无法获得，只能自旋，产生死锁。

这正是"自旋锁必须配合关中断"的原因——在可能被中断打断的位置，要用 spin_lock_irqsave() 而不是裸 spin_lock()。

4.7 两条注意事项 #

  • a — 自旋锁是一种忙等待，适合短时间锁定的轻量级加锁机制。
  • b — 自旋锁不能递归使用。自旋锁被设计成在不同线程或函数之间同步。如果一个线程在已经持有自旋锁时再次请求同一把锁，它处于忙等待状态，就没有机会释放自己持有的锁，造成死锁。

4.8 内核抢占 #

不管当前进程处于内核态还是用户态，内核都会去调度优先级更高的进程运行、停止当前进程——这就是内核抢占。

当我们使用自旋锁的时候，抢占是关闭的：自旋锁自旋的时候内核抢占关闭，内核就不会去调度其他进程运行。

五、途径四：信号量 #

Linux 提供了两种信号量：一种用于内核程序，一种用于应用程序。这里只讲前者。

5.1 与自旋锁的根本区别 #

信号量和自旋锁的使用方法基本一样，但最大区别在于：当一个进程试图获得一个已经锁定的信号量时，进程不会像自旋锁一样在远处忙等待。

信号量是一种睡眠锁。如果有一个任务试图获得一个已被持有的信号量，信号量会将其推入等待队列，然后让其睡眠——这时处理器获得自由去执行其他代码。当持有信号量的进程释放信号量后，等待队列中的一个任务将被唤醒，从而获得这个信号量。

5.2 结构体 #

c
struct semaphore {
    spinlock_t lock;              /* 用来对 count 变量起保护作用 */
    unsigned int count;           /* > 0：资源空闲
                                      = 0：资源忙，但没有进程等待
                                      < 0：资源不可用，并至少有一个进程等待 */
    struct list_head wait_list;   /* 等待队列链表，所有等待资源的睡眠进程都挂在这里 */
};

count 的三态语义是整个信号量的核心：它同时表达了"资源剩几个"和"有多少人在等"。

5.3 API #

初始化：

c
static inline void sema_init(struct semaphore *sem, int val);

#define init_MUTEX(sem)          sema_init(sem, 1)   /* 互斥用的信号量，值设 1 */
#define init_MUTEX_LOCKED(sem)   sema_init(sem, 0)   /* 值设 0 */

/* 定义和初始化一步完成 */
DECLARE_MUTEX(name);          /* 定义信号量 name 并初始化为 1 */
DECLARE_MUTEX_LOCKED(name);   /* 定义信号量 name 并初始化为 0 */

获取（P 操作）：

c
void down(struct semaphore *sem);              /* 不可被信号打断 */
int down_interruptible(struct semaphore *sem); /* 可被信号打断，推荐 */
int down_killable(struct semaphore *sem);

释放（V 操作）：

c
void up(struct semaphore *sem);

5.4 为什么优先用 down_interruptible #

down() 会让进程进入 TASK_UNINTERRUPTIBLE 状态，连 Ctrl+C 都杀不掉它。如果锁被永久持有（因为持有者出了 bug），这个进程就只能等重启。

down_interruptible() 让进程进入 TASK_INTERRUPTIBLE，可被信号唤醒，返回非 0 表示被打断，驱动应当把这个返回值返回给用户（通常转成 -ERESTARTSYS）。

c
if (down_interruptible(&sem))
    return -ERESTARTSYS;

5.5 实例 #

c
static struct semaphore sem;

static int hello_open(struct inode *inode, struct file *filep)
{
    /* P 操作：获得信号量，保护临界区 */
    if (down_interruptible(&sem)) {
        /* 没有获得信号量，被信号打断 */
        return -ERESTARTSYS;
    }
    return 0;
}

static int hello_release(struct inode *inode, struct file *filep)
{
    /* V 操作：释放信号量 */
    up(&sem);
    return 0;
}

注意这里 open 里获得却没有在 open 内释放——这是有意的：它把"持有"跨越到了 release，从而实现"设备只能被一个进程打开"。这也是信号量常用于此场景的典型写法。

5.6 互斥体（mutex） #

当信号量用于互斥时（避免多个进程同时在同一个临界区运行），其值应初始化为 1。这种信号量在任何给定时刻只能由单个进程或线程拥有，在这种使用模式下它有时也被称为互斥体（mutex）——mutual exclusion 的简称。

Linux 内核中几乎所有的信号量都用于互斥。

新代码建议直接用 struct mutex + mutex_lock_interruptible() / mutex_unlock()，它比用计数为 1 的信号量表达力更强，且内核可做更严格的调试检查（如检测重复加锁）。

5.7 头文件 #

使用信号量，内核代码必须包含 <asm/semaphore.h>（现代内核为 <linux/semaphore.h>）。

六、自旋锁与信号量的对照 #

只考虑内核态，两者的差别可以整理成下面这张表：

信号量 自旋锁
开销成本 进程上下文切换时间 忙等待获得自旋锁的时间
特性 a 会导致阻塞，产生睡眠 忙等待，内核抢占关闭
特性 b 进程级的（内核代表进程来争夺资源） 主要是用于 CPU 同步的
应用场合 只能运行于进程上下文 还可以出现于中断上下文
其他 还可以出现在用户进程中 只能在内核线程中使用

6.1 怎么选 #

判断标准只有一条：临界区里会不会睡眠 / 这段代码可能在哪运行。

这个临界区可能在中断上下文执行吗？
 ├─ 会  → 只能用自旋锁（信号量会睡眠，中断里不能睡眠）
 └─ 不会
      └─ 临界区里会睡眠、或可能等很久吗？
           ├─ 会  → 用信号量 / mutex
           └─ 不会 → 临界区很短？→ 自旋锁（更轻）
                     临界区长？  → 信号量（别让别人空转烧 CPU）

七、其他几种机制 #

除了上面四种广泛使用的并发控制机制外，内核还提供：

机制 适用场景 一句话
顺序锁（seqlock） 读者多、写者少 读者无锁读，读完校验序号；写者优先
RCU（Read-Copy-Update） 读极多、写极少（如链表遍历） 读者零开销，写者延迟释放旧数据
完成量（completion） 一方向另一方通知"事情做完了" 比信号量更轻的"等一次事件"
位锁（bit_spinlock） 与标志位复用同一个字 省内存

seqlock 与 RCU 的实现细节与选用建议见 B.内核/06-内核同步。

八、速查 #

机制 定义/初始化 加锁 解锁 能睡眠 可用于中断
中断屏蔽 — local_irq_save(flags) local_irq_restore(flags) — 是
原子操作 atomic_t v = ATOMIC_INIT(1) atomic_dec_and_test atomic_inc 否 是
自旋锁 spin_lock_init(&l) spin_lock(&l) spin_unlock(&l) 否 是
自旋锁+关中断 spin_lock_init(&l) spin_lock_irqsave(&l, fl) spin_unlock_irqrestore(&l, fl) 否 是
信号量 sema_init(&s, 1) down_interruptible(&s) up(&s) 是 否
互斥体 mutex_init(&m) mutex_lock_interruptible(&m) mutex_unlock(&m) 是 否

三条铁律：

  1. 自旋锁保护的临界区里不能有任何可能引起调度的操作（不能睡眠、不能 copy_to_user、不能 kmalloc(GFP_KERNEL)）。
  2. 加锁时间不能太长，尤其自旋锁。
  3. 同一把锁的粒度要对齐——读也加、写也加，漏一边等于没加。
