往开发板上移植好文件系统、各种设备驱动也移植好了，启动开发板、用串口工具进去看 /dev 目录，往往会发现里面空荡荡——顶多只有 null、console 等几个系统必需的设备文件，其余什么都没有。

那我们移植好的那些设备驱动，设备文件去哪了？难道每用一个设备就要手动 mknod 建一次节点？设备文件系统就是为了解决这个问题：它能在系统初始化时动态在 /dev 下创建好各种设备文件节点，也能在设备卸载后自动删除对应节点（这对热插拔设备极有用——插上自动创建、拔掉自动删除）。它还带来一个附带好处：写驱动时不必再为设备指定主设备号，注册时用 0 让内核动态分配即可。

本文覆盖：udev 是什么、与 devfs 的区别、udev 借助 sysfs 建节点的流程、嵌入式侧用 mdev 的完整配置（busybox、fstab、rcS、驱动侧 class/device、mdev.conf）、符号链接与固定设备名的做法、class_create/device_create 的内核源码实现。

本文不覆盖：struct class 结构体的完整字段与设备类架构见《struct_class设备类架构详解》；内核侧的 uevent 与 kobject 机制见《Linux 字符设备与驱动模型总览》第六章与 B.内核/08-总线与设备模型；字符设备注册本身见《cdev 与设备号》。

一、udev 是什么 #

1.1 2.4 时代的 devfs 及其缺陷 #

2.4 内核使用 devfs（设备文件系统）在设备初始化时创建设备文件，设备驱动程序可以指定设备号、所有者、用户空间等信息。devfs 运行在内核环境中，有不少缺点：

  • 可能出现主/辅设备号不够；
  • 命名不灵活，不能指定设备名称；
  • 不确定的设备映射——同一设备映射出的设备文件可能不同，比如你的 U 盘这次是 sda，下次变成 sdb。

1.2 2.6 起的 sysfs + udev #

自 2.6 内核开始引入了 sysfs 文件系统。sysfs 把连接在系统上的设备和总线组织成一个分级的文件，并提供给用户空间存取使用。

udev 运行在用户模式，而非内核中。udev 的初始化脚本在系统启动时创建设备节点；并且当插入新设备、加入驱动模块、在 sysfs 上注册新数据后，udev 会创建新的设备节点。

udev 是一个工作在用户空间的工具，它能根据系统中硬件设备的状态动态更新设备文件——包括设备文件的创建、删除、权限等。这些文件通常定义在 /dev 下，但也可以在配置文件中指定。

udev 必须得到内核中 sysfs 和 tmpfs 的支持：sysfs 为 udev 提供设备入口和 uevent 通道，tmpfs 为 udev 的设备文件提供存放空间。

1.3 关键认识：udev 不改变内核行为 #

注意，udev 是通过对内核产生的设备文件修改或增加别名来达到自定义设备文件的目的。但 udev 是用户模式程序，它不会更改内核行为。

也就是说：内核仍然会创建 sda、sdb 这些设备文件；udev 则根据设备的唯一信息区分不同设备，并产生新的设备文件（或链接）。在用户的应用程序中，只要使用新产生的设备文件即可。

二、udev 与 devfs 的区别 #

# udev devfs
1 能实现 devfs 的全部功能 功能被 udev 完全覆盖
2 运行在用户模式 运行在内核中
3 在设备被发现时加载模块 打开一个并不存在的 /dev 节点时自动加载驱动
4 内核行为不变，只增别名/链接 直接在内核里创建设备文件

第 3 条值得展开。devfs 的"打开即加载"听起来很方便，但对一台配置正确的计算机是多余的：系统中所有设备都应该产生 hotplug 事件、加载恰当的驱动，udev 会注意到这点并为它创建对应节点。如果你不想让所有设备驱动常驻内存，应该用别的东西管理模块（脚本、modules.conf 等）。而 devfs 那套方法导致了大量无用的 modprobe 尝试——每个试探性探测都新建一个运行 modprobe 的进程，而几乎全是白费。

2.1 用符号链接固定设备名 #

由于 udev 只加别名不改内核行为，内核依然会我行我素地产生 sda、sdb 这类设备名。udev 可以根据设备的其他信息（总线 bus、生产商 vendor 等）区分不同设备，并产生设备文件——只要为这个设备文件取一个固定的文件名就能解决命名漂移问题。

为了保证最大限度的兼容，新设备名一般作为对内核自动产生的设备名的符号链接使用。

举例：内核产生了 sda，而根据信息判断这是内置硬盘，就可以制定 udev 规则，让 udev 除了产生 /dev/sda 外，再创建一个符号链接 /dev/internalHD。这样在 fstab 里就可以用 /dev/internalHD 代替 /dev/sda。下次由于某些原因，这块硬盘在内核里变成 sdb 了也不用慌——udev 会照样自动产生 /dev/internalHD 并指向正确的 /dev/sdb，fstab 之类的文件一概不用改。

bash
# /etc/udev/rules.d/ 下的一条规则示意
SUBSYSTEM=="block", ATTRS{serial}=="XXXX", SYMLINK+="internalHD"

三、udev 如何建立设备文件 #

设备文件系统 udev 的工作过程依赖于 sysfs。udev 在用户空间工作，根据 sysfs 导出的信息（设备号 dev 等）动态建立和删除设备文件。sysfs 把这些设备和总线组织成分级目录与文件，可以由用户空间存取，向用户空间导出内核数据结构及它们的属性——其中包括设备的主次设备号。

3.1 对于已编译进内核的驱动 #

当设备被内核检测到时，驱动会直接在 sysfs 中注册其对象；对于编译成模块的驱动，则在模块载入时这样做。一旦挂载了 sysfs（挂到 /sys），内建驱动在 sysfs 注册的数据就可以被用户空间进程使用，并提供给 udev 创建设备节点。

udev 初始化脚本负责在 Linux 启动时创建设备节点。该脚本首先把 /sbin/udevsend 注册为热插拔事件处理程序——热插拔事件本不该在这个阶段发生，注册只是为了以防万一。

然后 udevstart 遍历 /sys 文件系统（其属性文件 dev 中记录着主设备号与次设备号），在 /dev 下创建符合描述的设备文件。

例如 /sys/class/tty/vcs/dev 里含有 "7:0" 字符串，udevstart 就据此创建主设备号 7、次设备号 0 的 /dev/vcs。每个设备的名字和权限由 /etc/udev/rules.d/ 下的规则文件指定；如果 udev 找不到对应的权限规则文件，就把权限设为缺省的 660，所有者为 root:root。

3.2 对于编译成模块的驱动 #

内核检测到新设备连接时会产生热插拔事件，并在 /proc/sys/kernel/hotplug 文件里查找处理设备连接的用户空间程序。udev 初始化脚本把 udevsend 注册为该处理程序。产生热插拔事件时，内核让 udev 到 /sys 里检测新设备的相关信息，并为新设备在 /dev 里创建项目。

这里有个坑：大多数 Linux 发行版通过 /etc/modules.conf 处理模块加载，即"对某个设备节点的访问导致相应内核模块被加载"。对 udev 这条路行不通，因为模块加载前设备节点根本不存在。

解决办法是在 LFS-Bootscripts 软件包里加入 modules 启动脚本以及 /etc/sysconfig/modules 文件：在 modules 文件里添加模块名，系统启动时就加载这些模块，这样 udev 才能检测到设备并创建节点。如果插入的设备有驱动模块但尚未加载，Hotplug 软件包就有用了——它响应内核总线驱动热插拔事件并加载相应模块、为其创建设备节点，设备就可以用了。

四、嵌入式侧：创建和配置 mdev #

mdev 是 udev 的简化版本，是 busybox 自带的程序，最适合嵌入式系统；udev 一般用在 PC 上的 Linux，相对复杂些。

4.1 基本认识 #

不管是 udev 还是 mdev，它们就是一个应用程序，跟其他应用程序（比如 Boa 服务）一样，配置了就能用。为方便起见，就直接用 busybox 自带的 mdev：配置编译 busybox 时把 mdev 的支持选项选上，编译后就包含了 mdev 设备文件系统的应用（当然也可以下载 udev 源码自行编译移植）。

bash
cd busybox-1.13.0/
make menuconfig
# Linux System Utilities --->
#     [*] mdev
#     [*]   Support /etc/mdev.conf
#     [*]     Support subdirs/symlinks
#     [*]       Support regular expressions substitutions when renaming device
#     [*]     Support command execution at device addition/removal

4.2 挂载 sysfs 与 tmpfs #

udev 或 mdev 都需要内核 sysfs 和 tmpfs 虚拟文件系统的支持。在 /etc/fstab 中添加：

text
# device        mount-point     type      options    dump    fsck order
#-----------------------------------------------------------------------
procfs          /proc           proc      defaults   0       0
sysfs           /sys            sysfs     defaults   0       0
tmpfs           /dev/shm        tmpfs     defaults   0       0
usbfs           /proc/bus/usb   usbfs     defaults   0       0
ramfs           /dev            ramfs     defaults   0       0
none            /dev/pts        devpts    mode=0622  0       0

嵌入式设备上 /dev 常用 tmpfs 而非 ramfs（ramfs 不限制大小，易被写爆内存）。上面沿用的是素材原文的 ramfs 写法，实际项目建议改成 tmpfs /dev tmpfs defaults 0 0。

4.3 在 rcS 中启动 mdev #

在系统初始化配置文件 /etc/init.d/rcS 中挂载 sysfs 与 tmpfs，然后启动 /sbin/mdev 对系统设备进行搜索：

bash
#!/bin/sh

## Mount virtual filesystem
/bin/mount -t proc       procfs  /proc
/bin/mount -n -t sysfs   sysfs   /sys
/bin/mount -n -t usbfs   usbfs   /proc/bus/usb
/bin/mount -t ramfs      ramfs   /dev
/bin/mount -n -t tmpfs   tmpfs   /dev/shm

## Make dir
/bin/mkdir -p /dev/pts
/bin/mkdir -p /dev/shm
/bin/mkdir -p /var/log
/bin/mount -n -t devpts none  /dev/pts -o mode=0622

## Make device node
echo /sbin/mdev > /proc/sys/kernel/hotplug
/sbin/mdev -s

这两条命令是整个机制的核心，值得逐字理解：

命令 含义
mdev -s 扫描 /sys 中所有的类设备目录，如果目录中有名为 dev 的文件且其中包含设备号，就据此在 /dev 下创建设备节点
echo /sbin/mdev > /proc/sys/kernel/hotplug 注册热插拔处理程序。产生热插拔事件时内核调用 /sbin/mdev，mdev 通过环境变量 ACTION 与 DEVPATH 确定事件动作以及影响了 /sys 中哪个目录，再看该目录下是否有 dev 属性文件，有就据此建节点

4.4 驱动侧要做什么 #

驱动的加载和卸载函数里要实现设备文件的创建与销毁。以按键驱动为例：

c
#include <linux/device.h>

static int device_major = DEVICE_MAJOR;   // 保存系统动态生成的主设备号
static struct class *button_class;        // 定义一个类

static int __init button_init(void)
{
    /* 注册字符设备：DEVICE_MAJOR 传 0，让系统动态分配主设备号 */
    device_major = register_chrdev(DEVICE_MAJOR, DEVICE_NAME, &buttons_fops);
    if (device_major < 0) {
        printk(DEVICE_NAME " register failed!\n");
        return device_major;
    }

    /* 注册一个设备类，使 mdev 可以在 /dev/ 下建立设备节点 */
    button_class = class_create(THIS_MODULE, DEVICE_NAME);
    if (IS_ERR(button_class)) {
        printk(DEVICE_NAME " create class failed!\n");
        return -1;
    }

    /* 创建设备节点，取名为 DEVICE_NAME（即 my2440_buttons）
       注意：2.6 内核较早版本的函数名是 class_device_create，现改为 device_create */
    device_create(button_class, NULL, MKDEV(device_major, 0), NULL, DEVICE_NAME);
    return 0;
}

static void __exit button_exit(void)
{
    /* 注销字符设备 */
    unregister_chrdev(device_major, DEVICE_NAME);
    /* 删除设备节点：老版本为 class_device_destroy */
    device_destroy(button_class, MKDEV(device_major, 0));
    /* 注销类 */
    class_destroy(button_class);
}

4.5 mdev 的配置文件 #

/etc/mdev.conf 可有可无，只是设定设备文件的一些规则，留空也能正常工作。

text
# /etc/mdev.conf 语法：<设备名正则> <属主>:<属组> <权限> [@|$|* 命令]
# 例：把 my2440_buttons 的属主属组设为 root，权限 660
my2440_buttons   root:root  660

五、udev、mdev 与 devfs 三者对照 #

devfs udev mdev
位置 内核 用户空间 用户空间
依赖 无（自带） sysfs + tmpfs sysfs + tmpfs

六、class_create 与 device_create 的内核实现 #

4.4 节用了这两个函数，这里看看它们内部到底做了什么。

6.1 class_create #

现代内核里 class_create 只是个薄包装：

c
#define class_create(owner, name)       \
({                                      \
    static struct lock_class_key __key; \
    __class_create(owner, name, &__key); \
})

它真正干活的是 __class_create：

c
struct class *__class_create(struct module *owner, const char *name,
                             struct lock_class_key *key)
{
    struct class *cls;
    int retval;

    cls = kzalloc(sizeof(*cls), GFP_KERNEL);
    if (!cls) {
        retval = -ENOMEM;
        goto error;
    }

    cls->name = name;
    cls->owner = owner;
    cls->class_release = class_create_release;

    retval = __class_register(cls, key);
    if (retval)
        goto error;

    return cls;

error:
    kfree(cls);
    return ERR_PTR(retval);
}
EXPORT_SYMBOL_GPL(__class_create);

四步：分配 struct class → 记录名字与所属模块 → 指定释放回调 → __class_register() 把它挂进 sysfs。这就是 /sys/class/<name> 目录的由来。

参数 含义
owner 一般为 THIS_MODULE
name 类名，即 /sys/class/ 下的目录名

配套销毁函数：

c
void class_destroy(struct class *cls)
{
    if ((cls == NULL) || (IS_ERR(cls)))
        return;
    class_unregister(cls);
}

注意它做了空指针与错误指针保护，所以 class_destroy(NULL) 是安全的；但它只做 class_unregister，真正的内存释放要等引用计数归零后由 class_release 回调完成。

现代内核（5.x 起）的 class_create 已简化为单参数 class_create(const char *name)，owner 由框架自己填。

6.2 device_create #

c
struct device *device_create(struct class *class, struct device *parent,
                             dev_t devt, void *drvdata, const char *fmt, ...)
{
    va_list vargs;
    struct device *dev;

    va_start(vargs, fmt);
    dev = device_create_vargs(class, parent, devt, drvdata, fmt, vargs);
    va_end(vargs);
    return dev;
}

它用可变参数解析出设备名，然后转给 device_create_vargs，后者再转到 device_create_groups_vargs——属性组版本，再往下就不在本篇展开了。

参数 含义 常见取值
class 类 上一步 class_create 的返回值
parent 父设备 NULL
devt 设备号 MKDEV(major, minor)
drvdata 驱动私有数据 NULL
fmt 设备名格式（支持 %d 等） "hello"

返回值：struct device *，失败时是 ERR_PTR() 编码的错误指针，必须用 IS_ERR() 判断，不能直接 == NULL。

配套销毁函数：

c
void device_destroy(struct class *class, dev_t devt);

6.3 三个名字的对应关系 #

驱动加载后，三个名字分别落在三个位置，容易搞混：

class_create(THIS_MODULE, "myclass")        →  /sys/class/myclass/
device_create(cls, NULL, devno, NULL, "hello") →  /dev/hello
                                                 └─ 同时生成 /sys/class/myclass/hello → (符号链接，指回 /sys/devices/virtual/myclass/hello)

设备号 MKDEV(major, minor)                   →  cat /proc/devices 里可见
名字 出现在哪 由谁决定
类名 "myclass" /sys/class/myclass/ class_create 的第二参数
设备名 "hello" /dev/hello device_create 的 fmt
设备名 "hello" /proc/devices 注册设备号时传给 register_chrdev_region 的 name

类名与设备名可以不同，/dev 下生成的是设备名，类名只决定 /sys/class/<类名>/ 这层目录。很多人误以为 /dev 下会是类名，这是常见困惑点。
