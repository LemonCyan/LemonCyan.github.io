一、ALC5651 芯片概览 #

ALC5651 是 Realtek 的一颗低功耗音频 codec，NanoPC-T4 开发板用它负责模拟侧的采集和回放。RK3399 内部的 I2S 控制器只出数字信号，模拟信号这一端由它来做。

按素材转录的 datasheet 特性：

  • 一路 24 位、8kHz ~ 192kHz 的 I2S/PCM/TDM 接口，可以接立体声 DAC 和 ADC；
  • 一路 24 位、8kHz ~ 192kHz 的 I2S/PCM 接口，同样接立体声 DAC 和 ADC；
  • 控制接口走 I2C；
  • 1 路数字麦克风接口（DMIC）加 3 路模拟麦克风（IN1P、IN2P/IN2N、IN3P）；
  • 每个接口都带异步采样率转换器（ASRC）；
  • DAC 和 ADC 路径上各有 7 段可调的均衡器（EQ）；
  • DAC/ADC 路径带增强型动态范围控制器（DRC）/自动增益控制器（AGC），以及防风噪降噪滤波器。

引脚总数 40。按功能分四组：数字 I/O（I2S1、I2S2、I2C、DMIC、PDM）、模拟输入（麦克风、Line in）、模拟输出（耳机、Line out）、电源与地。

从驱动视角，你只需要记住下面这张「能力—寄存器—驱动结构体」对照：

芯片能力 落到的寄存器 驱动里对应的东西
I2S1 数字接口 0x70（I2S1 SDP） rt5651_dai[0]，name = rt5651-aif1
I2S2 数字接口 0x71（I2S2 SDP） rt5651_dai[1]，name = rt5651-aif2
I2C 控制口 从地址 0x1a rt5651_i2c_driver，rt5651_regmap
内部时钟树 0x80（GLB_CLK）、0x81/0x82（PLL） rt5651_set_dai_sysclk、rt5651_set_dai_pll
模拟通路开关 0x29、0x2a、0x45、0x4f、0x52、0x02 DAPM widget + route + SOC_DAPM_SINGLE
增益/音量 0x02、0x1f、0x20、0x1b…… rt5651_snd_controls[] 里的 SOC_DOUBLE_TLV
耳机插拔检测 0xBB（JD_CTRL1）、0xBC（JD_CTRL2） rt5651_set_jack → rt5651_enable_jack_detect

驱动源码位于 sound/soc/codecs/rt5651.c。注意文件名和芯片名不一样：芯片叫 ALC5651，内核里的驱动、结构体、宏前缀全是 rt5651。设备树的 compatible 也是 realtek,rt5651。

一颗 codec 驱动在内核里必须交代清楚六件事，缺一件这套 ASoC 就转不起来：

  1. DAI 和 PCM 的能力：struct snd_soc_dai_driver，描述声道数、采样率、位深，以及操作接口；
  2. 控制接口：对 ALC5651 就是 I2C，用于读写寄存器，落在 struct snd_soc_component_driver 的读写回调上；
  3. Mixer 和其它音频控件：struct snd_kcontrol_new 数组；
  4. 音频操作：struct snd_soc_dai_ops；
  5. DAPM 描述：widget 数组加 route 数组；
  6. DAPM 事件处理程序：SND_SOC_DAPM_PRE_PMU/POST_PMD 这类事件回调。

版本分水岭：snd_soc_codec 与 snd_soc_component #

这一点必须先说清楚，否则你拿 4.x 的资料对着 6.3 的源码看会全程对不上号。

内核版本 codec 注册接口 代表结构体
≤ 4.19 snd_soc_register_codec() / devm_snd_soc_register_codec() struct snd_soc_codec_driver
≥ 4.20 devm_snd_soc_register_component() struct snd_soc_component_driver

snd_soc_codec 在 4.20 的 ASoC 重构里被合并进了 snd_soc_component。改动之后，codec、platform、没有 DAI 的辅助驱动统一用同一套 component 框架。也就是说：

  • 你在 6.3 的 rt5651.c 里搜不到 snd_soc_codec_driver，只有 snd_soc_component_driver；
  • 老文章里的 .read、.write、.volatile_register、.reg_cache_size 这些字段，现在都搬到了 snd_soc_component_driver 的同名字段上；
  • 老的 codec->dev 变成 component->dev，老的 snd_soc_codec_get_drvdata() 变成 snd_soc_component_get_drvdata()。

本篇所有代码都按 6.3 的 component 写法。如果你的内核是 4.19 及更早，把 snd_soc_component 按 snd_soc_codec 读一遍，字段名基本能对上；具体哪些字段被删改，未验证，得看你手上那棵树的头文件。

二、I2S 接口协议基础 #

数字音频接口全是硬件接口，是实实在在的物理连线，说的是同一块 PCB 上两颗 IC 之间的时序协议。它和音频编码格式是两码事：编码格式（PCM、PDM）说的是数据长什么样，接口（I2S、PCM/TDM、AC97、PDM）说的是数据怎么在线路上跑。

两者有对应关系：

  • I2S 和 PCM（TDM）接口传输的是 PCM 编码格式的音频数据；
  • PDM 接口传输的是 PDM 编码格式的音频数据。

采样、量化、编码 #

模拟声音进计算机之前要过三道工序。

采样是把时间上连续的模拟信号在时间轴上离散化。采样周期是相邻两个采样点的时间间隔，采样频率是它的倒数。采样率越高，点越密，数据量越大，音质越好。

奈奎斯特说采样频率不低于信号最高频率的两倍就能无失真还原。人耳范围大约 20Hz ~ 20kHz，所以采样率得在 40kHz 以上。

常见采样率的用途，抄录素材：

采样率 典型用途
8kHz 电话，人声够用
11.025kHz AM 调幅广播
22.05kHz / 24kHz FM 调频广播
32kHz miniDV 数码视频、DAT
44.1kHz 音频 CD、MPEG-1 音频（VCD、SVCD、MP3）
47.25kHz 商用 PCM 录音机
48kHz miniDV、数字电视、DVD、DAT、电影专业音频
50kHz 商用数字录音机
96kHz / 192kHz DVD-Audio、LPCM DVD 音轨、BD-ROM 音轨、HD-DVD 音轨

量化（位深、位宽、量化精度）决定每个采样点用几个 bit 表示。4bit、8bit、16bit、32bit 都能用，位数越多越精细，数据量成倍涨。常见是 8bit 和 16bit。

编码是最后一步。模拟信号经采样、量化之后已经是数字形式了，编码是为了压缩数据量方便存储处理。

数据传输率和数据量可以算：

text
数据传输率（bps） = 采样频率 × 量化位数 × 声道数
数据量（byte）    = 数据传输率 × 持续时间 / 8

拿 CD 举例：44.1kHz、16 位、双声道、一小时。44100 × 16 × 2 × 3600 / 8 = 6350400B ≈ 605.6MB。这个数字不小，所以编码阶段经常上压缩。

PCM 和 PDM 的区别：

  • PCM（Pulse Code Modulation）以等时间间隔采样，每次采样的模拟幅度量化成 N 位数字分量，所以每个采样结果是 N bit 长的数据；
  • PDM（Pulse Density Modulation）用远高于 PCM 采样率的时钟去调制模拟分量，只有 1 位输出，非 0 即 1。所以 PDM 数字音频也叫 Oversampled 1-bit Audio。

相比 PDM 那串 0/1 的密度变化，PCM 的量化结果直观得多。

I2S 的三根线 #

I2S 总线是飞利浦半导体发明的数字音频串行连接，现在被大量半导体厂商采用。用它的设备包括 ADC、DAC、DSP、CPU。把音频设备和嵌入式 SoC 接起来，I2S 是最省事的一条路。

最少三根线（要收也要发就是四根）：

信号线 别名 作用 频率关系
SCLK BCLK，位时钟 每一位音频数据对应一个 SCLK 脉冲 SCLK = 2 × 采样率 × 采样位数（立体声）
WS LRCK，帧时钟 切左右声道，1 表示传左声道，0 表示传右声道（I2S 标准模式） 等于采样率
SD 数据线 实际音频数据，收发分开时要两根 跟位宽走

拿 44.1kHz、16 位立体声算一遍：SCLK = 2 × 44100 × 16 = 1411200Hz = 1.4112MHz，WS = 44.1kHz。

收发分开时的命名，在 codec 侧叫 ADCDAT 和 DACDAT——前者是 codec 往 SoC 送录音数据，后者是 codec 从 SoC 收播放数据。方向别搞反，这是移植时最常见的接线错误。

除 BCLK 和 LRCK，还可能要 MCLK（Master/System clock input）。原因在 codec 内部的 Delta-Sigma（ΔΣ）架构：这类 codec 没有自己的工作时钟晶振电路，只能靠外部喂。MCLK 频率一般是采样频率的 256 倍或 384 倍，具体看器件手册。

MCLK 不是必须的。ALC5651 就可以拿 BCLK1/2 当内部 PLL 的参考时钟，从而给芯片提供时钟——RK3399 这颗芯片的板子上，MCLK 是接的，但驱动默认走的是 MCLK 直通，PLL 全程没上电（后面第十三节会用寄存器值证明这一点）。

主从关系：I2S 总线上同时只能有一个主设备。提供 SCLK 和 WS 的那个就是主设备，它可以是发送方，也可以是接收方，还可以是另外一颗专门管时钟的芯片。

PCM / TDM 与 PDM #

PCM 总线四根线：

信号线 作用
PCM_CLK 数据时钟
PCM_SYNC 帧同步时钟
PCM_IN 接收数据
PCM_OUT 发送数据

PCM 接口常用于 AP 处理器和通信 MODEM 之间传语音（打电话的双向数据）。AP 和蓝牙之间传语音也走 PCM；但蓝牙放音乐不走 PCM，走串口。

I2S 只能传 2 个声道，PCM 靠时分复用（TDM）能传多路，素材里给的上限是 16 路。

PDM 总线只有两根：PDM_CLK 和 PDM_DATA。线少，多用于麦克风录音，传的是 PDM 编码数据。数字麦克风领域 PDM 用得最广，其次是 I2S。

三种对齐模式 #

按 SDATA 相对 SCLK 和 LRCK 的位置分三种模式。

模式 LRCK 电平与声道 数据起始位置 备注
标准 I2S 低 = 左声道，高 = 右声道 LRCK 变化后的第一个 SCLK 周期 MSB 先出，可为 LSB 先出
左对齐 高 = 左声道，低 = 右声道 LRCK 变化后的第一个 SCLK 周期 数据靠左，LSB 位置随位宽浮动
右对齐 高 = 左声道，低 = 右声道 最后一个位对齐到 LRCK 边沿 数据靠右，帧头空出若干位

三种模式的共同点：SD 位宽可在 16 ~ 32 位之间设，MSB/LSB 先出可选，每个 SCLK 周期传一位。

右对齐的细节值得展开：每个数据帧的起始边沿处，数据的位数与 SD 信号位宽相等；而标准 I2S 和左对齐在起始边沿处分别是第一位和最后一位数据。换句话说，右对齐是「贴着 LRCK 边沿收尾」，左对齐和标准 I2S 是「贴着 LRCK 边沿开头」。这一点直接决定了 DAI 格式怎么配，我们留到第十二节。

RK3399 侧还有个 RCNT 位（right justified counter），只在右对齐加从机发送模式下有效，作用是让数据在左声道有效后延 RCNT 个 SCLK 周期再发。这个位在 I2S_TXCR 里，具体位域未验证。

三、I2S 的时序与时钟 #

RK3399 的三个 I2S 控制器 #

RK3399 datasheet 第 22 章讲 I2S/PCM 控制器。这颗 SoC 嵌了三个：I2S0、I2S1、I2S2。

差异如下：

控制器 FIFO（32 位宽 × 32 位深） I2S 模式通道 最高采样率 对外
I2S0 8 个，4 发 4 收 10 收 + 10 发 192kHz 暴露到外设
I2S1 2 个，1 发 1 收 2 收 + 2 发 192kHz 暴露到外设
I2S2 4 个，4 发 8 发 768kHz 内部接 HDMI 和 DP

三者共同特性（素材转录）：

  • AHB 总线接口；
  • 16 ~ 32 位音频数据传输；
  • 主从模式都支持；
  • PCM 模式下支持 2 通道音频接收；
  • Support DMA handshake interface and configurable DMA water level；
  • 发送 FIFO 空、下溢，接收 FIFO 满、上溢都产生中断，全部可屏蔽；
  • 发送 FIFO 空和接收 FIFO 满的中断水位可配；
  • 支持合并中断输出；
  • 支持 I2S 正常、左对齐、右对齐三种串行格式；
  • 支持 PCM 无延迟、延 1、延 2、延 3 四种模式；
  • 支持 16 ~ 31 位音频数据在 32 位宽 FIFO 里左对齐或右对齐存放；
  • 支持两个 16 位音频数据塞进一个 32 位宽位置；
  • 支持两条独立 LRCK，收发各一条；采样率相同时可共用一条；
  • SCLK 和 LRCK 极性可配。

控制器内部六个模块：

模块 职责
系统接口 AHB 从属操作，含控制寄存器、中断、DMA 握手
时钟发生器 输入源时钟 MCLK_I2S，经分频器生成 SCLK 和 LRCK
发送器 可主可从，I2S/PCM 模式下提供环绕立体声接口
接收器 可主可从，提供立体声串行接口
传输 FIFO 32 位 × 32 位置
接收 FIFO 32 位 × 32 位置

四种工作组合：发送主 + 接收主、发送主 + 接收从、发送从 + 接收主、发送从 + 接收从。

  • 发送方做主设备时，它向接收方（从设备）发全部信号，CPU 控制何时发时钟和数据；
  • 发送方做从设备时，SD 仍从发送方到接收方，但 SCLK 和 LRCK 由接收方（主设备）发过来。所以 CPU 必须提前知道接收方何时初始化事务，数据传输才能对上；
  • 接收方做主设备时，它向发送方（从设备）发 SCLK 和 LRCK，同时收串行数据。CPU 得先告诉发送方何时开始事务，让它把数据准备好；
  • 接收方做从设备时，CPU 做完初始化设置就等着收数据。

开始传数据之前，CPU 必须先把 I2S 寄存器配好。这包括 CPU 侧设置、I2S 接口寄存器设置，以及可能的 SoC 平台设置。

TXCR / RXCR 的位定义 #

I2S_TXCR 是发送控制寄存器。注意大部分位域都有一个前置条件：XFER[0] 为 0 时才能写。

位域 名称 含义
RCNT right justified counter 仅 I2S 右对齐 + 从机发送模式有效。左声道有效后延 RCNT 个 SCLK 周期开始发数据
TCSR TX Channel Select 2'b00 双声道，2'b01 四声道，2'b10 六声道，2'b11 八声道
HWT Halfword word transform 仅 VDW 选 16bit 时有效。0：从 AHB/APB 总线来的是 32 位数据，低 16 位左声道、高 16 位右声道；1：只有低 16 位有效，高 16 位无效
SJM Store justified mode 16 ~ 31 位数据存进 32 位宽 FIFO 时的对齐方式。0 右对齐，1 左对齐。当 VDW 选 16bit 且 HWT 为 0 时此位无效，因为每个 FIFO 单元已经塞了两个 16 位数据，32 位空间占满，选不了对齐方式
FBM First Bit Mode 0：MSB 先出，1：LSB 先出
IBM I2S bus mode 0：I2S normal，1：I2S Left justified，2：I2S Right justified，3：reserved
PBM PCM bus mode 0：PCM no delay，1：PCM delay 1，2：PCM delay 2，3：PCM delay 3
TFS Transfer format select 0：I2S 格式，1：PCM 格式
VDW Valid Data width 0 ~ 14 预留，15 为 16bit，16 为 17bit，……，n 为 (n+1)bit，……，31 为 32bit

I2S_RXCR 是接收控制寄存器，位定义跟 TXCR 一一对应，只是把前置条件从 XFER[0] 换成 XFER[1]：

  • RCSR：RX Channel Select，编码同 TCSR；
  • HWT：方向反过来，0 表示 32 位数据有效送到 AHB/APB 总线，低 16 位左声道、高 16 位右声道；1 表示只有低 16 位有效；
  • SJM：与 TXCR 语义相同，但在 VDW 选 16bit 时只有 HWT 为 0 才有效，理由同上；
  • FBM、IBM、PBM、TFS、VDW：与 TXCR 完全一致。

CKR 的时钟位 #

I2S_CKR 管时钟发生，是整个 I2S 里最需要看懂的一个寄存器。

位域 名称 含义
TRCM Tx and Rx Common Use 2'b00/2'b11：tx_lrck 和 rx_lrck 各作各的同步信号；2'b01：只用 tx_lrck 作收发同步；2'b10：只用 rx_lrck
MSS Master/slave mode select 0：主模式（输出 sclk），1：从模式（输入 sclk）
CKP Sclk polarity 0：sclk 上升沿采样、下降沿驱动；1：下降沿采样、上升沿驱动
RLP Receive lrck polarity 0：正常极性；1：反相极性
TLP Transmit lrck polarity 0：正常极性；1：反相极性
MDIV mclk divider Serial Clock Divider = Fmclk / Ftxsclk - 1
RSD Receive sclk divider Receive sclk divider = Fsclk / Frxlrck，0~30 预留，31 起表示 32fs，n 表示 (n+1)fs，255 表示 256fs
TSD Transmit sclk divider Transmit sclk divider = Ftxsclk / Ftxlrck，编码同 RSD

正常/反相极性的具体含义，以 LRCK 为例：

  • 正常极性，I2S 标准模式：低为左声道，高为右声道；I2S 左右对齐：高为左，低为右；PCM 起始信号高触发；
  • 反相极性，I2S 标准模式：高为左声道，低为右声道；I2S 左右对齐：低为左，高为右；PCM 起始信号低触发。

MDIV 的分配表有个规律，实际上就是偶数分频：

text
MDIV = 0        → Fmclk = Ftxsclk
MDIV = 1        → Fmclk = 2 × Ftxsclk
MDIV = 2, 3     → Fmclk = 4 × Ftxsclk
MDIV = 4, 5     → Fmclk = 6 × Ftxsclk
......
MDIV = 2n, 2n+1 → Fmclk = (2n+2) × Ftxsclk
......
MDIV = 254, 255 → Fmclk = 256 × Ftxsclk

发送启动的完整时序 #

官方给的传输操作流程，八步，顺序不能乱：

text
(1) 向 I2S_XFER 第 0 位写 0x0，禁止 I2S 发送器
(2) 向 I2S_CLR  第 0 位写 0x1，清除 I2S 控制逻辑
(3) 读 I2S_CLR  第 0 位，直到读回 0x0
(4) 设置 I2S_TXCR 和 I2S_CKR，配置 I2S 操作模式
(5) 为发送器配置 DMA 通道，通过 I2S_TXDR 寄存器给出目标地址
(6) 写 I2S_DMACR，确定何时发 DMA 请求
(7) 向 I2S_XFER 第 0 位写 0x01，使能 I2S 发送器
(8) 数据传输完成之前，I2S_XFER 第 0 位不能再被禁止

第 (3) 步这个轮询很关键。清逻辑是跨 SCLK 域的异步操作，写完就配下一颗寄存器，清逻辑还在路上，配置就被冲掉了。

素材里第 (1) 步写的是「I2C_XFER」，这是原文笔误，应为 I2S_XFER。第 (5) 步「通过 I2S_TXDR 寄存器传输目标地址」这个措辞也含糊，实际是 DMA 把源数据搬到 TXDR，不是写目标地址。这两处一并在附录记下。

引脚与通道数 #

I2S0 有 1 路 SDI、4 路 SDO，可以支持 2 个输入通道和 8 路输出声道。 I2S1 有 1 路 SDI、1 路 SDO，可以支持 2 个输入通道和 2 路输出声道。 I2S2 接 HDMI 和 DP 的音频接口，支持 8 通道发送。它的引脚没对外暴露，原理图上看不到。

RK3399 的引脚大多复用多路功能，用哪路 I2S 就得先把引脚 mux 过去。NanoPC-T4 上 ALC5651 挂在 I2S1 上，I2S0 的 LRCK 引脚（GPIO3_D2 / I2S0_LRCK_TX、GPIO3_D1 / I2S0_LRCK_RX）在原理图里也出现过——这是原理图抓取时把多个网络的标注混在一起了，实际连线以板子原理图为准，本篇不臆测。

数字 I/O 组 #

接口 引脚

  • 播放：数字信号送进 DACDAT1，ALC5651 解码后产生模拟信号到喇叭或耳机；

耳机插拔检测电路 #

JD1、JD2 是检测引脚。ALC5651 支持对 sta_gpio_jd、sta_jd1_1、sta_jd1_2、sta_jd2、sta_micbias1_ovcd 五种状态做检测。JD 是 jack detection 的缩写。

一般用 IRQ 配合 JD：JD 被触发时，IRQ 往主机送一个标志，软件驱动据此执行相应动作。Jack detection 还能用来开/关相关输出端口，比如 HP（耳机）和 LOUT（喇叭）的自动切换。

配置分三步。

第一步，选 JD 触发源，写 MX-BC[11:9]：

编码 来源
000'b From sta_gpio_jd
001'b From sta_jd1_1
010'b From sta_jd1_2
011'b From sta_jd2
其它 Reserved

MX-BC 就是寄存器 0xBC，即 RT5651_JD_CTRL2。

第二步，按 JD 激活状态设置目标行为，做 HP 和 LOUT 自动切换：MX-BB[11:10] = 11'b 且 MX-BB[3:2] = 10'b。

第三步，看 MX-BB（寄存器 0xBB，RT5651_JD_CTRL1）的位定义：

位 名称 含义
11 Enable Jack Detect Trigger HPOUT 0 禁止，1 使能
10 Select Jack Detect Polarity Trigger HPOUT 0 低电平触发，1 高电平触发
3 Enable Jack Detect Trigger LOUT 0 禁止，1 使能
2 Select Jack Detect Polarity Trigger LOUT 0 低电平触发，1 高电平触发

行为：JD 状态为低时，HP_OUT（耳机）静音，LOUT（喇叭）正常出声。JD 由低变高时，HP 恢复，LOUT 静音。

有一条限制必须记住：HP 和 SPK 插孔切换这个功能，驱动程序得先把 DAC 到 HP 的通路、DAC 到 LOUT 的通路都打开。MX-BB 的寄存器控制只负责 HP 和 SPK 的静音/取消静音，不负责建通路。通路没建，切了也是静音。

实测：在移植完声卡驱动、用板子 Ubuntu 放音时读这两个寄存器，0xBB 是 0x00，0xBC 也是 0x00。也就是说这条自动切换路径没被启用，切换逻辑全交给了上层（Machine 驱动的 jack 事件）。

五、Codec 的寄存器空间 #

ALC5651 的寄存器分两页。0x00 ~ 0xFF 是主页面（MX 页），0x00 直接寻址；内部寄存器组（private base）通过 RT5651_PR_BASE 基址加偏移访问，驱动里的 RT5651_PR_BASE + 0x3d 就属于这一类。

复位与 ID #

出厂上电后第一件事是读 ID：向 0xFF 写读命令，读回 0x6281 才算芯片在线。ID 不对就直接 -ENODEV。

第二件事是写 0x00 = 0x0000，软件复位，把全部寄存器打回默认值。这一步放在 devm_regmap_init_i2c 之后、regmap_register_patch 之前。

第三件事是打补丁。init_list 只有一条：

c
static const struct reg_sequence init_list[] = {
        {RT5651_PR_BASE + 0x3d, 0x3e00},
};

这条补丁写的是厂商私有页的 0x3d，datasheet 里没有对应说明，属于 Realtek 给的「校正值」。regmap_register_patch 会把它登记进 map->patch，并且在之后每次 regcache_sync() 时重放。这是它的关键价值——不是「初始化一次」，而是「每次从 suspend 恢复同步缓存时都补上」。

regmap_register_patch 的实现要点：

c
int regmap_register_patch(struct regmap *map, const struct reg_sequence *regs,
                          int num_regs)
{
        struct reg_sequence *p;
        int ret;
        bool bypass;

        if (WARN_ONCE(num_regs <= 0, "invalid registers number (%d)\n",
            num_regs))
                return 0;

        p = krealloc(map->patch,
                     sizeof(struct reg_sequence) * (map->patch_regs + num_regs),
                     GFP_KERNEL);
        if (p) {
                memcpy(p + map->patch_regs, regs, num_regs * sizeof(*regs));
                map->patch = p;
                map->patch_regs += num_regs;
        } else {
                return -ENOMEM;
        }

        map->lock(map->lock_arg);

        bypass = map->cache_bypass;

        map->cache_bypass = true;
        map->async = true;

        ret = _regmap_multi_reg_write(map, regs, num_regs);

        map->async = false;
        map->cache_bypass = bypass;

        map->unlock(map->lock_arg);

        regmap_async_complete(map);

        return ret;
}

注意它先 krealloc 把补丁追加到 map->patch，然后立刻用 _regmap_multi_reg_write 写一遍硬件，写的时候 cache_bypass 和 async 都置位。所以补丁是「存一份 + 立刻生效」，缺一不可。

调用方 rt5651_i2c_probe 对返回值只 dev_warn：

c
ret = regmap_register_patch(rt5651->regmap, init_list,
                            ARRAY_SIZE(init_list));
if (ret != 0)
        dev_warn(&i2c->dev, "Failed to apply regmap patch: %d\n", ret);

打补丁失败不阻断 probe。这是个取舍：私有寄存器写不进去，芯片在多数场景下还能出声，只是音质可能偏。换成某些 codec，这一步失败就得直接退出。

六、regmap 与寄存器访问 #

为什么 codec 驱动离不开 regmap #

codec 的寄存器有三个特点：位宽不统一（8 位、16 位、24 位都有）、地址空间分页、很多寄存器是 volatile（读出来跟写进去不一样，比如状态位）。regmap 把这三件事统一了，还顺手给了缓存、批量写、调试接口。

初始化只要一行：

c
rt5651->regmap = devm_regmap_init_i2c(i2c, &rt5651_regmap);
if (IS_ERR(rt5651->regmap)) {
        ret = PTR_ERR(rt5651->regmap);
        dev_err(&i2c->dev, "Failed to allocate register map: %d\n",
                ret);
        return ret;
}

devm_ 前缀意味着卸载时自动释放，不用写 regmap_exit。

regmap_config #

rt5651_regmap 的定义在 rt5651.c 顶部，素材没完整转录，只能按字段用途说明：

c
static const struct regmap_config rt5651_regmap = {
        /* 实际数值请对照 sound/soc/codecs/rt5651.c */
};

几个字段的作用，你改驱动时一定会碰到：

字段 作用 配错的后果
reg_bits 寄存器地址位宽 地址只发出去 8 位，高位页面丢
val_bits 寄存器值位宽 写 16 位值只到 8 位，后半截被截断
max_register 最大合法地址 访问越界直接报 EIO
volatile_reg 声明哪些寄存器不被缓存 状态寄存器被缓存，读出来永远是旧值
readable_reg / writeable_reg 读写权限表 误写只读寄存器，I2C 上返回 NAK
reg_defaults 寄存器默认值表 上电时缓存是空的，regcache_sync 什么都没同步
cache_type 缓存策略 ALC5651 这类寄存器多的芯片要用 REGCACHE_RBTREE

reg_bits 和 val_bits 具体是 8 和 16 还是别的组合，未验证——这颗芯片是 16 位值宽、8 位地址宽，这是从 regmap_read(rt5651->regmap, RT5651_DEVICE_ID, &ret) 把结果读进 int 且值域到 0x6281 推出来的，但没有原文直接确认。

codec 组件层怎么调到 regmap #

驱动的 snd_soc_component_driver 没有显式给 .read/.write，因为 6.3 的 ASoC 会自动从 component->regmap 走。snd_soc_component_update_bits 就是分叉点：

c
int snd_soc_component_update_bits(struct snd_soc_component *component,
                                  unsigned int reg, unsigned int mask, unsigned int val)
{
        bool change;
        int ret;

        if (component->regmap)
                ret = regmap_update_bits_check(component->regmap, reg, mask,
                                               val, &change);
        else
                ret = snd_soc_component_update_bits_legacy(component, reg,
                                                           mask, val, &change);

        if (ret < 0)
                return soc_component_ret_reg_rw(component, ret, reg);
        return change;
}

有 regmap 就走 regmap_update_bits_check，没有就走老路径。老路径自己实现了「读—改—写」，并在前后加 component->io_mutex 保护：

c
static int snd_soc_component_update_bits_legacy(
        struct snd_soc_component *component, unsigned int reg,
        unsigned int mask, unsigned int val, bool *change)
{
        unsigned int old, new;
        int ret = 0;

        mutex_lock(&component->io_mutex);

        old = soc_component_read_no_lock(component, reg);

        new = (old & ~mask) | (val & mask);
        *change = old != new;
        if (*change)
                ret = soc_component_write_no_lock(component, reg, new);

        mutex_unlock(&component->io_mutex);

        return soc_component_ret_reg_rw(component, ret, reg);
}

返回值语义值得单独记：snd_soc_component_update_bits 成功且值真的变了返回 1，成功但值没变返回 0，失败返回负数。所以判断成败不能写 if (ret)——那会把「值没变」当成错误。

调试视角 #

注册路径 #

成员 作用

probe_new 是 pre-6.3 的写法，回调只收 struct i2c_client *。老的 probe 回调签名是 (struct i2c_client *client, const struct i2c_device_id *id)，多一个 id 参数。linux 6.3 已经把 probe 和 probe_new 合并回单一的 probe，probe_new 在 6.4 前后被移除——具体哪一个小版本移除，未验证，看你手上的 include/linux/i2c.h 里还有没有这个成员。

两套匹配机制 #

设备树匹配：

c
#if defined(CONFIG_OF)
static const struct of_device_id rt5651_of_match[] = {
        { .compatible = "realtek,rt5651", },
        {},  /* 最后一个必须为空，表示结束 */
};
MODULE_DEVICE_TABLE(of, rt5651_of_match);
#endif

ID 表匹配：

c
static const struct i2c_device_id rt5651_i2c_id[] = {
        { "rt5651", 0 },
        { }
};

这里有一个特别容易踩的坑，原文专门点出来了：设备树里 compatible = "rockchip,rt5651"，但 rt5651_of_match 里写的是 "realtek,rt5651"，两者对不上。所以设备树匹配这条路走不通。

真正让 probe 被调用的是 id_table。I2C 控制器注册从设备时，of_i2c_get_board_info 会解析设备节点，把 compatible 属性值里逗号之后的部分作为 type：

text
struct i2c_board_info info = {
     .type      = "rt5651",   /* 取自 compatible = "rockchip,rt5651" 逗号后部分 */
     .addr      = 0x1a,
     .of_node   = rt5651 设备节点,
};

type 会赋给 i2c_client->name，于是 i2c_client->name（而不是 of_node->compatible 的名字）跟 rt5651_i2c_id[0].name 都是 "rt5651"，匹配成功。

这条链路解释了一个常见困惑：明明是设备树平台，为什么实际走的是 id_table 匹配？因为 SoC 厂商给的 dts 写了 rockchip,rt5651，而驱动 of_match 表只认 realtek,rt5651。要修可以两选一——把 dts 的 compatible 改成 "realtek,rt5651"，或者在 rt5651_of_match 里加一条 "rockchip,rt5651"。前者更正规，后者更省事且不动驱动。

I2C 控制器侧 #

RK3399 有 9 个 I2C 控制器。I2C1 的 SCL 接 GPIO4_A2，SDA 接 GPIO4_A1。控制器驱动在 drivers/i2c/busses/i2c-rk3x.c，走 platform 模型，核心产出是 algorithm 层的收发函数。

platform probe 里干这几件事：

  1. 动态分配 i2c_adapter 并初始化，包括设 algo；
  2. 把用到的 GPIO 复用成 I2C 功能；
  3. 初始化 I2C 控制器寄存器；
  4. 取资源、注册 I2C 中断处理函数；
  5. 调 i2c_add_adapter 把 adapter 注册到 i2c_bus_type 总线。

第 5 步注册时会触发从设备的扫描：

  • of_i2c_register_devices：解析控制器节点的子节点，逐个调 of_i2c_register_device 完成从设备注册；
  • i2c_scan_board_info：扫描并用 i2c_new_device 注册静态从设备。

ALC5651 走的是第一条，因为它在 dts 里是 i2c1 节点的子节点。

注意顺序：adapter 先注册，client 才出现，驱动 probe 才可能被调用。dts 里 rt5651@1a 节点写了但 &i2c1 的 status 是 "disabled"，整条链路从一开始就断了，probe 不会被调用，dmesg 里连失败日志都没有。排查「驱动没加载」时，先确认 status。

soc_probe_component 干了什么 #

Machine 驱动注册声卡时会执行 soc_probe_component(card, component)，顺序如下：

  1. 把 component->driver->dapm_widgets 注册到声卡 card 的 widgets 链表；
  2. 执行 component->driver->probe(component)；
  3. 按 component->driver->controls 数组创建并添加多个 kcontrol 到 card 的 controls 链表；
  4. 遍历 component->driver->dapm_routes，调 snd_soc_dapm_add_routes 把每条 snd_soc_dapm_route 展开成需要的 snd_soc_dapm_path，注册到 card 的 paths 链表；
  5. 把 component 加到声卡的 component_dev_list 链表。

第 2 步的位置很关键：probe 在 routes 展开之前执行。所以 rt5651_probe 里不能依赖 DAPM 通路已经建好，只能做纯寄存器级初始化。

第 3、4 步的顺序也不能换：先有 kcontrol，才有 route 引用的 control 名字可以被解析。route 里写了 {"DAC MIXR", "INF1 Switch", "IF1 DAC1 R"}，如果 rt5651_dac_r_mix[] 里没有叫 INF1 Switch 的控件，snd_soc_dapm_add_routes 会报错，最后你在 dmesg 里看到的是 ASoC: no dapm match for INF1 Switch。

DAPM 在这里扮演的角色 #

两句话把 DAPM 的行为说清：

  1. 音频路径发生改变时（上层用 tinymix 改通路），或者有数据流事件时（开始/停止播放），DAPM 会遍历所有邻近 widget，检查是否存在完整通路。通路完整，路径上所有 widget 上电，其余下电；
  2. widget 的上下电由 DAPM 按策略自主控制，外部干预不了。DAPM 是专门给音频系统做的电源管理模块，独立于 Linux 那套 PM 之外。

第 2 点有一个很实际的好处：SoC 睡了，codec 还能正常工作。语音通话场景就是这样——modem 的 DAI 直接连到 codec 的 DAI，语音数据不经过 SoC，于是 SoC 可以进低功耗，只要 codec 醒着。这也是 DAPM 非要做成「自成体系」的原因。

DAPM 的遍历算法、snd_soc_dapm_path 的生成规则、PRE_PMU/POST_PMD 的执行时机，在《DAPM：Widget、Route 与 Path》里，本篇不重复。

一个要留意的现象 #

你翻上面这张表会发现一件事：播放主通路上的 widget 基本都没设电源控制寄存器。

从 AIF1RX → IF1 DAC → IF1 DAC1 R → DAC MIXR → Audio DSP → Stereo DAC MIXR → DAC R1 → OUT MIXR → HPOVOL R → HPOR MIX → HP Amp → HPO R Playback → HPOR，这一整条链上，SND_SOC_NOPM 占了大半。

这不是驱动写漏了。ALC5651 的电源是按「域」管理的，一个 PWR_DIG1 里塞了 I2S1、I2S2、ADC L/R、DAC L1/R1 六路电源位，一个 PWR_VOL 塞了输入、输出、耳机四组音量级电源位。所以驱动选择的做法是：主通路用虚拟 widget 表达拓扑，真实的上下电交给 Power 后缀的 SUPPLY widget 和 route 里那些 NULL control 的连线来触发。

理解这一点，你排查「某段通路不通」时才知道去哪看寄存器：不要盯着 DAC MIXR 找寄存器，要找它 route 里连到的 Stero1 DAC Power，去看 PWR_DIG2 的对应位。

三参数的语义 #

struct snd_soc_dapm_route 三个成员依次是 sink、control、source。写成一行就是：

text
{sink, control, source}

拿 {"DAC MIXL", "INF1 Switch", "IF1 DAC1 L"} 举例：

  • 输入端（source）是 IF1 DAC1 L；
  • 输出端（sink）是 DAC MIXL；
  • 名为 INF1 Switch 的 kcontrol 控制这两个 widget 之间连线的通断。

关键点：这个 kcontrol 定义在 sink 端的控件数组里，也就是 rt5651_dac_l_mix[]。所以 route 里写的名字必须在 sink 的 mixer 控件里能找到。名字对不上就报 no dapm match。

control 写 NULL 表示这条连线常通，没有开关。这类连线通常用来表达「电源依赖」——{"ADC L", NULL, "ADC L Power"} 的意思就是 ADC L 要工作必须 ADC L Power 在。

写 route 的规则 #

总结成五条，写自己的 codec 驱动时照着做：

  1. sink 和 source 必须是在 dapm_widgets 里出现过的名字，一字不差；
  2. control 非空时，名字必须在 sink 的 widget 控件的 name 字段里出现，同样一字不差；
  3. 电源依赖用 control = NULL 表达，从 sink 连到 SUPPLY widget；
  4. mixer 的每个输入都要一条 route，漏一条就有一个输入永远用不上；
  5. 顺序无所谓，snd_soc_dapm_add_routes 会自己建图，但同类放一起以后好维护。

宏的语义 #

宏 控制量 用途
SOC_SINGLE 一个 最简单的开关或数值
SOC_SINGLE_TLV 一个 + TLV 增益控制，如音量、EQ
SOC_DOUBLE 两个（同一个寄存器） 立体声开关
SOC_DOUBLE_TLV 两个 + TLV 立体声音量
SOC_ENUM 一个枚举 Mux 控件
SOC_DAPM_SINGLE 一个 对应普通 SOC_SINGLE，但 get/put 换成了 DAPM 版本
SOC_DAPM_SINGLE_AUTODISABLE 一个 DAPM 版本，且断电时自动置为关闭
SOC_DAPM_ENUM 一个枚举 DAPM 版本的 Mux

DAPM 版的控件和普通控件只差 info/get/put 三个回调——普通版直接读写寄存器，DAPM 版会通知 DAPM 重新走一遍路径检查。所以 mixer 的输入开关必须用 SOC_DAPM_SINGLE，用 SOC_SINGLE 的话寄存器写进去了但 DAPM 不知道，通路不会真的建立。

mux 与 route 的字符串必须严格对齐 #

Stereo1 ADC L1 Mux 的枚举选项是 {"DD MIX", "ADC"}，route 里对应写：

text
{"Stereo1 ADC L1 Mux", "ADC", "ADC L"},
{"Stereo1 ADC L1 Mux", "DD MIX", "DD MIXL"},

Stereo2 ADC L1 Mux 的枚举是 {"DD MIXL", "ADCL"}（注意多了 L 后缀），route 里也必须是：

text
{"Stereo2 ADC L1 Mux", "DD MIXL", "DD MIXL"},
{"Stereo2 ADC L1 Mux", "ADCL", "ADC L"},

DD MIX 和 DD MIXL 差一个字母，ADC 和 ADCL 也差一个字母。这两组对不上就是通路上那个 mux 永远选不到你要的输入，表现为「录音只有底噪」或者「录音走的是另一条路」。这是改 route 时最容易犯的错。

DAI 与 widget 的对应 #

注册声卡时会调 soc_probe_link_components，为每个 DAI 创建两个流 widget。以 rt5651-aif1 为例：

DAI widget 类型 widget name widget sname
rt5651-aif1 snd_soc_dapm_dai_in AIF1 Playback AIF1 Playback
rt5651-aif1 snd_soc_dapm_dai_out AIF1 Capture AIF1 Capture

同时构造两条路径：

  • 以播放流 widget 为输入端，连接到 sname == "AIF1 Playback" 的 widget。在 rt5651_dapm_widgets 里就是：
c
SND_SOC_DAPM_AIF_IN("AIF1RX", "AIF1 Playback", 0, SND_SOC_NOPM, 0, 0)
  • 以录音流 widget 为输出端，输入端连 sname == "AIF1 Capture" 的 widget。也就是：
c
SND_SOC_DAPM_AIF_OUT("AIF1TX", "AIF1 Capture", 0, SND_SOC_NOPM, 0, 0)

于是得到一条从 DAI 出发的完整播放链路：

text
AIF1 Playback --> AIF1RX --> IF1 DAC --> IF1 DAC1 L --> ... --> HPO L Playback --> HPOL --> Headphones

这里的 AIF1 Playback 是流 widget 的 name 与 sname 同名，AIF1RX 的 sname 也是 AIF1 Playback，靠 sname 匹配。如果哪天你把 DAI 的 stream_name 从 "AIF1 Playback" 改成别的，AIF1RX 的 sname 也得跟着改，否则链路在第一步就断了——现象是播放时 DAPM 报 AIF1RX 没有 source，通路建不起来，无声。

set_sysclk：选系统时钟源 #

c
static int rt5651_set_dai_sysclk(struct snd_soc_dai *dai,
                int clk_id, unsigned int freq, int dir)
{
        struct snd_soc_component *component = dai->component;
        struct rt5651_priv *rt5651 = snd_soc_component_get_drvdata(component);
        unsigned int reg_val = 0;
        unsigned int pll_bit = 0;

        if (freq == rt5651->sysclk && clk_id == rt5651->sysclk_src)
                return 0;

        switch (clk_id) {
        case RT5651_SCLK_S_MCLK:
                reg_val |= RT5651_SCLK_SRC_MCLK;
                break;
        case RT5651_SCLK_S_PLL1:
                reg_val |= RT5651_SCLK_SRC_PLL1;
                pll_bit |= RT5651_PWR_PLL;
                break;
        case RT5651_SCLK_S_RCCLK:
                reg_val |= RT5651_SCLK_SRC_RCCLK;
                break;
        default:
                dev_err(component->dev, "Invalid clock id (%d)\n", clk_id);
                return -EINVAL;
        }

        snd_soc_component_update_bits(component, RT5651_PWR_ANLG2,
                RT5651_PWR_PLL, pll_bit);

        snd_soc_component_update_bits(component, RT5651_GLB_CLK,
                RT5651_SCLK_SRC_MASK, reg_val);
        rt5651->sysclk = freq;
        rt5651->sysclk_src = clk_id;

        dev_dbg(dai->dev, "Sysclk is %dHz and clock id is %d\n", freq, clk_id);

        return 0;
}

三个时钟源：

clk_id 值 GLB_CLK[15:14] PLL 电源
RT5651_SCLK_S_MCLK 0 00'b 下电
RT5651_SCLK_S_PLL1 1 01'b 上电（PWR_ANLG2[9] = 1）
RT5651_SCLK_S_RCCLK 2 10'b 不动

两个寄存器的分工：

  • RT5651_PWR_ANLG2（0x64），位[9] 是 PLL Power Control，0 下电、1 上电；
  • RT5651_GLB_CLK（0x80），位[15:14] 是 System Clock Source MUX，00 MCLK、01 PLL1、10 RCCLK、11 保留。

结论很直接：

  • 选 MCLK 就顺手把 PLL 下电。此时系统时钟频率 = 外部 MCLK 频率；
  • 选 PLL1 就给 PLL 上电。此时系统时钟由 PLL 产生，分频系数由 set_pll 动态算。

素材原文把 RT5651_GLB_CLK 的地址写成过「0x84」，正文另一处写 0x80。0x80 才是全局时钟控制，0x84 是另一个寄存器。以 0x80 为准。

set_pll：算分频系数 #

c
static int rt5651_set_dai_pll(struct snd_soc_dai *dai, int pll_id, int source,
                        unsigned int freq_in, unsigned int freq_out)
{
        struct snd_soc_component *component = dai->component;
        struct rt5651_priv *rt5651 = snd_soc_component_get_drvdata(component);
        struct rl6231_pll_code pll_code;
        int ret;

        if (source == rt5651->pll_src && freq_in == rt5651->pll_in &&
            freq_out == rt5651->pll_out)
                return 0;

        if (!freq_in || !freq_out) {
                dev_dbg(component->dev, "PLL disabled\n");

                rt5651->pll_in = 0;
                rt5651->pll_out = 0;
                snd_soc_component_update_bits(component, RT5651_GLB_CLK,
                        RT5651_SCLK_SRC_MASK, RT5651_SCLK_SRC_MCLK);
                return 0;
        }

        switch (source) {
        case RT5651_PLL1_S_MCLK:
                snd_soc_component_update_bits(component, RT5651_GLB_CLK,
                        RT5651_PLL1_SRC_MASK, RT5651_PLL1_SRC_MCLK);
                break;
        case RT5651_PLL1_S_BCLK1:
                snd_soc_component_update_bits(component, RT5651_GLB_CLK,
                                RT5651_PLL1_SRC_MASK, RT5651_PLL1_SRC_BCLK1);
                break;
        case RT5651_PLL1_S_BCLK2:
                        snd_soc_component_update_bits(component, RT5651_GLB_CLK,
                                RT5651_PLL1_SRC_MASK, RT5651_PLL1_SRC_BCLK2);
                break;
        default:
                dev_err(component->dev, "Unknown PLL source %d\n", source);
                return -EINVAL;
        }

        ret = rl6231_pll_calc(freq_in, freq_out, &pll_code);
        if (ret < 0) {
                dev_err(component->dev, "Unsupported input clock %d\n", freq_in);
                return ret;
        }

        dev_dbg(component->dev, "bypass=%d m=%d n=%d k=%d\n",
                pll_code.m_bp, (pll_code.m_bp ? 0 : pll_code.m_code),
                pll_code.n_code, pll_code.k_code);

        snd_soc_component_write(component, RT5651_PLL_CTRL1,
                pll_code.n_code << RT5651_PLL_N_SFT | pll_code.k_code);
        snd_soc_component_write(component, RT5651_PLL_CTRL2,
                ((pll_code.m_bp ? 0 : pll_code.m_code) << RT5651_PLL_M_SFT) |
                (pll_code.m_bp << RT5651_PLL_M_BP_SFT));

        rt5651->pll_in = freq_in;
        rt5651->pll_out = freq_out;
        rt5651->pll_src = source;

        return 0;
}

参数含义：

参数 含义
pll_id PLL 编号，ALC5651 只有 1 个
source PLL 参考时钟源：MCLK、BCLK1、BCLK2 三选一
freq_in 参考时钟频率
freq_out 期望输出频率

参考源的编码在 RT5651_GLB_CLK（0x80）位[13:12]：

编码 参考源 宏
00'b MCLK RT5651_PLL1_SRC_MCLK，对应 RT5651_PLL1_S_MCLK = 0
01'b BCLK1 RT5651_PLL1_SRC_BCLK1，对应 RT5651_PLL1_S_BCLK1 = 1
10'b BCLK2 RT5651_PLL1_SRC_BCLK2，对应 RT5651_PLL1_S_BCLK2 = 2

（素材注释里把 RT5651_PLL1_S_BCLK2 那一行注释成「位[13:12] 配置为 10'b，PLL 时钟源选择为 MCLK2」，这是笔误，应为 BCLK2。）

freq_in 或 freq_out 为 0 时，函数把 GLB_CLK 的时钟源拨回 MCLK，这就是「关 PLL」的标准做法。这个分支很有用：想省电或者嫌 PLL 锁定时长影响启动，就传 0 进来。

PLL 输出频率公式与分频 #

ALC5651 的 PLL 有两个控制寄存器：MX81（RT5651_PLL_CTRL1）和 MX82（RT5651_PLL_CTRL2）。

输出频率：

text
             MCLK × (N + 2)
F_OUT  =  ────────────────────
          (M + 2) × (K + 2)

典型值 K = 2（K + 2 = 4），于是公式简化成 F_OUT = MCLK × (N+2) / (4 × (M+2))。

位域：

寄存器 位域 宏 偏移
PLL_CTRL1 (0x81) N PLL_N_SFT 7
PLL_CTRL1 (0x81) K — 低位
PLL_CTRL2 (0x82) M PLL_M_SFT 12
PLL_CTRL2 (0x82) M bypass PLL_M_BP_SFT 11

m_bp（M bypass）为 1 时，M 分频被旁路，m_code 不写进寄存器。所以代码里写的是：

c
snd_soc_component_write(component, RT5651_PLL_CTRL2,
        ((pll_code.m_bp ? 0 : pll_code.m_code) << RT5651_PLL_M_SFT) |
        (pll_code.m_bp << RT5651_PLL_M_BP_SFT));

N 和 K 挤在同一个寄存器里，n_code << 7 | k_code。

具体 N/M/K 的数值由 rl6231_pll_calc() 算，函数在 sound/soc/codecs/rl6231.c。计算过程素材没展开（原文说「比较复杂，咱们就不研究了」），这里也不编。

一个能验证公式的量级：MCLK = 12.288MHz、K = 2、M = 0（M+2 = 2）时，要得到 12.288MHz 的输出，则 N + 2 = 4 × 2 × 1 = 8，N = 6。这组数只是说明公式怎么用，实际取值以 rl6231_pll_calc 的输出为准。

实测值（播放时读寄存器）：

寄存器 值 含义
0x64（PWR_ANLG2） 0x0000 位[9] = 0，PLL 下电
0x80（GLB_CLK） 0x0000 位[15:14] = 00，时钟源为 MCLK
0x81（PLL_CTRL1） 0x0000 PLL 禁用，写这些位没意义
0x82（PLL_CTRL2） 0x0000 同上

四个值全是 0，是一致的——这条板子的默认路径就是 MCLK 直通，全程没有 PLL 参与。这也是为什么 rt5651_set_dai_pll 在默认配置下根本没被调到。

hw_params：按参数配寄存器 #

c
static int rt5651_hw_params(struct snd_pcm_substream *substream,
        struct snd_pcm_hw_params *params, struct snd_soc_dai *dai)
{
        struct snd_soc_component *component = dai->component;
        struct rt5651_priv *rt5651 = snd_soc_component_get_drvdata(component);
        unsigned int val_len = 0, val_clk, mask_clk;
        int pre_div, bclk_ms, frame_size;

        rt5651->lrck[dai->id] = params_rate(params);
        pre_div = rl6231_get_clk_info(rt5651->sysclk, rt5651->lrck[dai->id]);

        if (pre_div < 0) {
                dev_err(component->dev, "Unsupported clock setting\n");
                return -EINVAL;
        }
        frame_size = snd_soc_params_to_frame_size(params);
        if (frame_size < 0) {
                dev_err(component->dev, "Unsupported frame size: %d\n", frame_size);
                return -EINVAL;
        }
        bclk_ms = frame_size > 32 ? 1 : 0;
        rt5651->bclk[dai->id] = rt5651->lrck[dai->id] * (32 << bclk_ms);

        dev_dbg(dai->dev, "bclk is %dHz and lrck is %dHz\n",
                rt5651->bclk[dai->id], rt5651->lrck[dai->id]);
        dev_dbg(dai->dev, "bclk_ms is %d and pre_div is %d for iis %d\n",
                                bclk_ms, pre_div, dai->id);

        switch (params_width(params)) {
        case 16:
                break;
        case 20:
                val_len |= RT5651_I2S_DL_20;
                break;
        case 24:
                val_len |= RT5651_I2S_DL_24;
                break;
        case 8:
                val_len |= RT5651_I2S_DL_8;
                break;
        default:
                return -EINVAL;
        }

        switch (dai->id) {
        case RT5651_AIF1:
                mask_clk = RT5651_I2S_PD1_MASK;
                val_clk = pre_div << RT5651_I2S_PD1_SFT;
                snd_soc_component_update_bits(component, RT5651_I2S1_SDP,
                        RT5651_I2S_DL_MASK, val_len);
                snd_soc_component_update_bits(component, RT5651_ADDA_CLK1, mask_clk, val_clk);
                break;
        case RT5651_AIF2:
                mask_clk = RT5651_I2S_BCLK_MS2_MASK | RT5651_I2S_PD2_MASK;
                val_clk = pre_div << RT5651_I2S_PD2_SFT;
                snd_soc_component_update_bits(component, RT5651_I2S2_SDP,
                        RT5651_I2S_DL_MASK, val_len);
                snd_soc_component_update_bits(component, RT5651_ADDA_CLK1, mask_clk, val_clk);
                break;
        default:
                dev_err(component->dev, "Wrong dai->id: %d\n", dai->id);
                return -EINVAL;
        }
        return 0;
}

流程拆开：

  1. 从 params 取采样率，存进 rt5651->lrck[dai->id]。LRCK 频率 = 采样率；
  2. rl6231_get_clk_info(sysclk, lrck) 算预分频值 pre_div。这个函数的输入是系统时钟和 LRCK，输出是分频档位。算不出来（比如 MCLK 不是 LRCK 的整数倍且超出表范围）返回负数；
  3. snd_soc_params_to_frame_size(params) 算帧大小。帧是「左右两个采样点」这个单位，等于声道数 × 采样位数；
  4. bclk_ms 取 0 或 1：帧大小超过 32 就置 1；
  5. bclk = lrck × (32 << bclk_ms)，也就是 lrck × 32 或 lrck × 64；
  6. 按 params_width(params) 选位深编码；
  7. 按 DAI 编号写 I2S_SDP[3:2] 和 ADDA_CLK1 的预分频位。

ADDA_CLK1（0x73）位[14:12] 是 I2S Clock Pre-Divider 1：

编码 分频
000'b +1
001'b +2
010'b +3
011'b +4
100'b +6
101'b +8
110'b +12
111'b +16

注意这不是连续的 2 的幂，+1/+2/+3/+4/+6/+8/+12/+16 是常见的音频分频档位表，用来在多种采样率下凑出整数比。

实测：播放时 0x73 读回 0x0104。位[14:12] = 0 表示预分频为 +1，于是 Clk_sys_i2s1 = MCLK = 256 × FS。同时 0x70 读回 0x8000，位[3:2] = 0 表示 16 位。

播放时 hw_params 的真实值 #

bash
root@rk3399:/proc/asound/card0/pcm0p/sub0# cat hw_params
access: RW_INTERLEAVED
format: S16_LE
subformat: STD
channels: 2
rate: 44100 (44100/1)

对着看：format: S16_LE → 位深 16 → 0x70[3:2] = 00'b；channels: 2 → 帧大小 32 → bclk_ms = 0 → bclk = 44100 × 32 = 1.4112MHz；rate: 44100 → LRCK = 44.1kHz。

period_size 5513 和 buffer_size 22052 的关系是 22052 / 5513 = 4，即 4 个 period。这两个值由 ALSA 的 period/buffer 协商决定，跟 codec 无关，但排查 xrun 时用得着。

三个参数解析函数 #

c
static inline unsigned int params_rate(const struct snd_pcm_hw_params *p)
{
        return hw_param_interval_c(p, SNDRV_PCM_HW_PARAM_RATE)->min;
}

SNDRV_PCM_HW_PARAM_RATE 的枚举值是 11。再往下：

c
static inline const struct snd_interval *hw_param_interval_c(const struct snd_pcm_hw_params *params,
                                                     snd_pcm_hw_param_t var)
{
        return &params->intervals[var - SNDRV_PCM_HW_PARAM_FIRST_INTERVAL];
}

SNDRV_PCM_HW_PARAM_FIRST_INTERVAL 的值是 8，所以 11 - 8 = 3。取的是 params->intervals[3]->min，也就是采样率区间的最小值。

c
int snd_soc_params_to_frame_size(struct snd_pcm_hw_params *params)
{
        int sample_size;

        sample_size = snd_pcm_format_width(params_format(params));
        if (sample_size < 0)
                return sample_size;

        return snd_soc_calc_frame_size(sample_size, params_channels(params), 1);
}

sample_size 是单个采样的位宽，snd_soc_calc_frame_size(sample_bits, channels, slots) 的结果是 bits × channels × slots，这里 slots = 1。16 位 × 2 声道 = 32。

c
static inline int params_width(const struct snd_pcm_hw_params *p)
{
        return snd_pcm_format_width(params_format(p));
}

params_format 从 SNDRV_PCM_HW_PARAM_FORMAT 的掩码里取最小值，snd_pcm_format_width 再把它映射成位宽。S16_LE → 16。

这一串调用链本身没什么坑，但有个点值得知道：params_rate 取的是区间 min，不是唯一值。hw_params 里的区间在协商完成后已经收敛成单点，所以 min 就等于实际值。

rl6231_get_clk_info() 的具体实现素材没给，它的分频表未验证。只知道输入 (sysclk, lrck)、输出分频档位，负值表示不支持。

时钟树全景 #

        ┌─────▼─────┐               ┌─────▼─────┐

        └───────────┘               └───────────┘

上电顺序 #

时钟相关寄存器的上电顺序有讲究，set_sysclk 里的写法是：先动 PWR_ANLG2 的 PLL 电源位，再动 GLB_CLK 的时钟源选择。

text
(1) 写 PWR_ANLG2[9]：0 关 PLL / 1 开 PLL
(2) 写 GLB_CLK[15:14]：选 MCLK / PLL1 / RCCLK
(3) （若选 PLL）写 GLB_CLK[13:12] 选参考源
(4) （若选 PLL）写 PLL_CTRL1 / PLL_CTRL2 设 N/M/K

顺序反了会怎样：先切时钟源到 PLL、再给 PLL 上电，中间那段时间系统时钟源指向一个还没上电的 PLL，输出是垃圾。虽然绝大多数情况下这段窗口很短、不会真的出问题，但按正确顺序写不费事。

PLL 什么时候用得着 #

看三个实际场景。

场景一，MCLK 频率和采样率不配套。板子给 12.288MHz 的 MCLK，采样率 44.1kHz，12.288MHz / 44.1kHz = 278.6，不是整数，rl6231_get_clk_info 算不出合适的分频档位，返回负数，hw_params 直接 -EINVAL。这时候要么换 MCLK（24.576MHz 或者 22.5792MHz），要么开 PLL 把非整数比转成整数比。

场景二，只有 BCLK 没有 MCLK。某些板子为了省一根线，MCLK 不接，让 codec 从 BCLK 恢复时钟。这时 GLB_CLK[13:12] 选 01（BCLK1）或 10（BCLK2），PLL 参考源用 BCLK。

场景三，48kHz 和 44.1kHz 两个系列都要。44.1k 系列要 11.2896MHz 的整数倍，48k 系列要 12.288MHz 的整数倍，一颗固定晶振喂不满两头。PLL 就是干这个的。

关掉 PLL 的正确姿势 #

rt5651_set_dai_pll 里有一句话值得记住：

c
if (!freq_in || !freq_out) {
        dev_dbg(component->dev, "PLL disabled\n");
        rt5651->pll_in = 0;
        rt5651->pll_out = 0;
        snd_soc_component_update_bits(component, RT5651_GLB_CLK,
                RT5651_SCLK_SRC_MASK, RT5651_SCLK_SRC_MCLK);
        return 0;
}

传 0 进 freq_in 或者 freq_out，函数把时钟源拨回 MCLK 就走了。注意它没有去动 PWR_ANLG2[9] 的 PLL 电源位——那是 set_sysclk 的活儿。两个函数各管一半，调用的先后顺序由 Machine 驱动决定。想彻底关 PLL，得两个都走到。

MCLK 的频率 #

素材给的典型值是 MCLK = 256 × FS。44.1kHz 时是 11.2896MHz，48kHz 时是 12.288MHz。

实测印证了这一点：0x73 读回 0x0104，位[14:12] = 0 表示预分频 +1，即 Clk_sys_i2s1 = MCLK = 256 × FS。也就是说 MCLK 直通，一级分频都没过。

RK3399 侧的 MCLK 源在 clk_i2sout。这条时钟链后面第十七节讲设备树时再展开。

位时钟和帧时钟的关系 #

三个频率，一条公式把关系锁死：

text
LRCK = FS                              （帧时钟 = 采样率）
BCLK = FS × 声道数 × 采样位数/声道       （位时钟）
     = FS × 32   （16 位 × 2 声道）
     = FS × 64   （32 位 × 2 声道）
MCLK = 256 × FS 或 384 × FS            （典型值）

44.1kHz / 16 位 / 双声道这一组具体数值：LRCK = 44100Hz，BCLK = 1411200Hz = 1.4112MHz，MCLK = 11289600Hz = 11.2896MHz。

BCLK 和 MCLK 的比值是 11.2896M / 1.4112M = 8。这个 8 就是 SoC 侧 I2S_CKR 的 MDIV 要配的值减去 1，即 MDIV = 7（Fmclk = (2×3+2) × Ftxsclk = 8 × Ftxsclk，取 MDIV = 6 或 7）。RK3399 侧的分频由 rockchip-i2s 的 hclk/mclk 驱动算，不用 codec 驱动操心，但两边必须对得上，对不上的现象是「播放速度不对」或者「噪声」。

十四、耳机与喇叭的输出路径 #

耳机通路 #

从数字接口到耳机插孔，右声道：

text
AIF1RX ──► IF1 DAC ──► IF1 DAC1 R ──► DAC MIXR ──► Audio DSP ──► Stereo DAC MIXR
   ──► DAC R1 ──► OUT MIXR ──► HPOVOL R ──► HPOR MIX ──► HP Amp ──► HPO R Playback ──► HPOR

逐段对应的 kcontrol 和寄存器：

段 kcontrol 名 寄存器 位 语义
IF1 DAC1 R → DAC MIXR INF1 Switch AD_DA_MIXER（0x29） 6 0 非静音，1 静音
DAC MIXR → Stereo DAC MIXR DAC R1 Switch STO_DAC_MIXER（0x2A） 6 0 非静音，1 静音
DAC R1 → OUT MIXR DAC R1 Switch OUT_R3_MIXER（0x52） 0 0 非静音，1 静音
OUT MIXR → HPOVOL R Switch HP_VOL（0x02） 6 0 非静音，1 静音
HPOVOL R → HPOR MIX HPO MIX HPVOL Switch HPO_MIXER（0x45） 13 0 非静音，1 静音
HP Amp → HPO R Playback Switch HP_VOL（0x02） 7 0 非静音，1 静音

左声道完全对称：

段 kcontrol 名 寄存器 位
IF1 DAC1 L → DAC MIXL INF1 Switch AD_DA_MIXER（0x29） 14
DAC MIXL → Stereo DAC MIXL DAC L1 Switch STO_DAC_MIXER（0x2A） 14
DAC L1 → OUT MIXL DAC L1 Switch OUT_L3_MIXER（0x4F） 0
OUT MIXL → HPOVOL L Switch HP_VOL（0x02） 14
HPOVOL L → HPOL MIX HPO MIX HPVOL Switch HPO_MIXER（0x45） 13
HP Amp → HPO L Playback Switch HP_VOL（0x02） 15

注意 HPO MIX HPVOL Switch 这一位（HPO_MIXER 的 bit13）左右声道共用，因为 rt5651_hpo_mix[] 是同一个数组，HPOL MIX 和 HPOR MIX 两个 widget 都挂它。

一条旁路 #

HPOR MIX 有第二个输入，直接从 DAC R1 来：

text
{"HPOR MIX", "HPO MIX DAC1 Switch", "DAC R1"},

对应 HPO_MIXER 的 bit14。这条路绕开 OUT MIXR 和 HPOVOL R，所以走这条路时，OUT MIXR 上的 5 个开关和 HPOVOL R 的音量控制全部不起作用。音量只剩 HP_VOL 那一级。

什么时候会走这条？你在 tinymix 里把 HPO MIX DAC1 Switch 打开就知道了。它是「跳过输出混合器」的直通路径，调试时用来排除 OUT MIXR 那一级的问题很好使。

喇叭（Line out）通路 #

ALC5651 的 LOUTL/P 和 LOUTR/N 是线路输出，不能直接推耳机，板子上要外接功放。通路：

text
DAC L1 ──► LOUT MIX ──► LOUT L Playback ──► LOUTL ──► Amp Power
DAC R1 ──► LOUT MIX ──► LOUT R Playback ──► LOUTR ──► Amp Power
段 kcontrol 名 寄存器 位
DAC L1 → LOUT MIX DAC L1 Switch LOUT_MIXER M_DAC_L1_LM_SFT
DAC R1 → LOUT MIX DAC R1 Switch LOUT_MIXER M_DAC_R1_LM_SFT
OUTVOL L → LOUT MIX OUTVOL L Switch LOUT_MIXER M_OV_L_LM_SFT
OUTVOL R → LOUT MIX OUTVOL R Switch LOUT_MIXER M_OV_R_LM_SFT
LOUT MIX → LOUT L Playback Switch LOUT_CTRL1 L_MUTE_SFT
LOUT MIX → LOUT R Playback Switch LOUT_CTRL1 R_MUTE_SFT

LOUT 还有一条替代输入：{"LOUT MIX", "DAC L1 Switch", "DAC L1"} 和 {"LOUT MIX", "DAC R1 Switch", "DAC R1"} 这两条是直通 DAC 的，绕过 OUTVOL。所以喇叭有两级音量可调：OUT Playback Volume（LOUT_CTRL1）和 DAC1 Playback Volume（DAC1_DIG_VOL），前者是模拟的，后者是数字的。数字音量开太大会在 DAC1_DIG_VOL 那一级削顶，模拟音量开太大则在功放输入削顶。实践上数字音量留在 0dB 附近，模拟音量拿来调。

Amp Power 这个 widget 连着 LOUTL 和 LOUTR 两个输出，还连着 HP Amp。它挂在 PWR_ANLG1 的 PWR_HA_BIT，POST_PMU 时调 rt5651_amp_power_event。这个事件的作用是控制外接功放的电源/使能——具体做什么素材没给，未验证。

耳机/喇叭的自动切换 #

第 4 节讲过硬件层面的 MX-BB / MX-BC 切换。软件层面 ASoC 提供了一套 snd_soc_jack 机制，实现在 Machine 驱动里：

  • 耳机插拔事件由 codec 的 set_jack 回调配置的中断源产生；
  • Machine 驱动在 jack 事件回调里改 DAPM 通路（打开耳机通路、关闭喇叭通路，或者反过来）。

实测 0xBB 和 0xBC 都是 0x00，说明 NanoPC-T4 这条板子没用 codec 自带的自动切换，靠软件做。所以你在 dmesg 里能看到 rt5651 1-001a: Failed to reguest IRQ 0: -22 这条报错也照样能放音——因为整条 jack 检测链路都没启用。

（reguest 是内核源码里的拼写错误，不是本篇的错别字。）

十五、录音输入路径 #

模拟麦克风通路 #

板子用的是麦克风 2，差分接 IN2P / IN2N。到 ADCDAT1 的完整链路：

text
MIC2 ──► IN2P ──► BST2 ──► RECMIXL ──► ADC L ──► ADC L Power
     └─► IN2N ──┘                ▲
                                  │
IN2P ──► INL1 VOL ──► "INL1 Switch" ┘

从 route 表逐条抽出来：

text
{"IN2P", NULL, "LDO"},
{"IN2P", NULL, "MIC2"},
{"IN2N", NULL, "MIC2"},
{"BST2", NULL, "IN2P"},
{"BST2", NULL, "IN2N"},
{"INL1 VOL", NULL, "IN2P"},
{"INR1 VOL", NULL, "IN2N"},
{"RECMIXL", "INL1 Switch", "INL1 VOL"},
{"RECMIXL", "BST2 Switch", "BST2"},
{"ADC L", NULL, "RECMIXL"},
{"ADC L", NULL, "ADC L Power"},
{"Stereo1 ADC L1 Mux", "ADC", "ADC L"},
{"Stereo1 ADC MIXL", "ADC1 Switch", "Stereo1 ADC L1 Mux"},
{"Stereo1 ADC MIXL", NULL, "Stereo1 Filter"},
{"Stereo1 Filter", NULL, "ADC ASRC"},
{"IF1 ADC1", NULL, "Stereo1 ADC MIXL"},
{"IF1 ADC1", NULL, "I2S1"},
{"AIF1TX", NULL, "IF1 ADC1"},

三件事值得说清。

第一，RECMIXL 有四个输入：INL1 VOL、BST1、BST2、BST3。板子走的是 BST2（差分麦克风 2）和 INL1 VOL（单端参考）两支。选哪支决定录音增益：BST2 走 IN2 Boost（0 ~ +52dB），INL1 VOL 走 IN Capture Volume（-34.5 ~ 0dB）。

第二，ADC L Power 是一条 NULL control 的 route，纯电源依赖。ADC L 这个 widget 本身是 SND_SOC_DAPM_ADC 且寄存器是 SND_SOC_NOPM，它上不上电只看有没有连到 ADC L Power。

第三，ADC ASRC 和 I2S1 也都挂在链上。Stereo1 Filter 要 ADC ASRC 才工作，IF1 ADC1 要 I2S1 才工作。所以录音不出声时，除了麦克风本身，还要确认 PWR_DIG1 的 PWR_I2S1_BIT 和 PWR_DIG2 的 PWR_ADC_STO1_F_BIT 有没有被拉起来。

数字麦克风通路 #

板子没用 DMIC，但通路是完整的：

text
DMIC L1 ──► Stereo1 ADC L2 Mux ─(DMIC)─► Stereo1 ADC MIXL ──► "..."
DMIC R1 ──► Stereo1 ADC R2 Mux ─(DMIC)─► Stereo1 ADC MIXR ──► "..."
DMIC CLK ──► DMIC L1 / DMIC R1          （时钟依赖）

DMIC CLK 是个 SUPPLY widget，挂在 RT5651_DMIC 的 DMIC_1_EN_SFT 位上，带 PRE_PMU 事件回调 set_dmic_clk。这个回调在 widget 上电之前把 DMIC 时钟频率配好。

DMIC L1 和 DMIC R1 的名字里带空格，这是 DAPM widget 命名里少数带空格的，写 route 时别忘了。

麦克风偏置 #

micbias1 是个 SUPPLY widget，挂在 PWR_ANLG2 的 PWR_MB1_BIT。电容麦克风需要直流偏置电压才能工作，MICBIAS1 引脚提供这个电压。偏置电压有三个实际作用：

  • 稳定工作点。没有偏置时，温湿度变化会让输出信号偏移，偏置把工作点钉住；
  • 提高灵敏度，增强声音捕获能力；
  • 降低噪声水平，输出更干净。

set_bias_level 里 SND_SOC_BIAS_STANDBY 分支做的事情就是把 PWR_ANLG1 的 PWR_MB（bit13，MBIAS 电源）拉起来，同时拉 PWR_VREF1、PWR_BG、PWR_VREF2 三个参考电压/带隙电源。四路一起上，等 10~15ms 让电压稳下来（usleep_range(10000, 15000)），再把 PWR_FV1、PWR_FV2 置上切到慢速 VREF 模式（datasheet 注释：For good analog performance）。

这段代码的关键就是那个 usleep_range。少了它，参考电压没稳，录音里会有「咔」声或者低频噪声。

录音增益链 #

从麦克风到 ADC 数字输出，要过的增益级：

级 控件 范围 说明
1 IN2 Boost 0 ~ +52dB，9 档 差分前置放大，BST2 上
2 IN Capture Volume -34.5 ~ 0dB，1.5dB 步进 INL1 VOL / INR1 VOL
3 ADC Boost Gain 0 / 12 / 24 / 36dB ADC 前级，2 位
4 ADC Capture Volume -17.62 ~ +30dB ADC 数字增益，7 位
5 ADC Capture Switch on/off ADC 静音

五级串起来，理论增益上限是 52 + 0 + 36 + 30 = 118dB。实际用不满这个数——IN2 Boost 开到 +50dB 时底噪也会被放大 50dB。录音调音量的常见做法：麦克风离得近就把 boost 压到 0 ~ +20dB，靠 ADC 数字增益补；离得远才开高 boost。

ADC Boost Gain 的 TLV 是 adc_bst_tlv（DECLARE_TLV_DB_SCALE(adc_bst_tlv, 0, 1200, 0)），起点 0dB、步进 12dB、共 4 档，所以是 0/12/24/36dB。

录音不出声的排查顺序 #

按链路顺序查，一步一个脚印：

  1. 看 /proc/asound/card0/pcm0c/sub0/hw_params，确认 capture 流的采样率和格式对不对；
  2. 看 cat /sys/kernel/debug/asoc/<card>/dapm/ 下面各个 widget 的状态，IN2P、BST2、RECMIXL、ADC L、Stereo1 ADC L1 Mux、IF1 ADC1、AIF1TX 这一串应该都是 On；
  3. 用 tinymix 确认 RECMIXL BST2 Switch、Stereo1 ADC L1 source、Stereo1 ADC MIXL ADC1 Switch 三个都是开的；
  4. 读 PWR_ANLG2 和 PWR_ANLG1，确认 micbias1 和 LDO 的位是 1；
  5. 都对了还不行，就回到硬件：麦克风是不是真的接在 IN2P/IN2N 上，MICBIAS1 上有没有电压。

第 2 步的 debugfs 路径在《音频调试实战》里有完整用法，这里只点到为止。

十六、probe 的完整流程 #

rt5651_i2c_probe 逐行 #

c
static int rt5651_i2c_probe(struct i2c_client *i2c)
{
        struct rt5651_priv *rt5651;
        int ret;
        int err;

        rt5651 = devm_kzalloc(&i2c->dev, sizeof(*rt5651),
                                GFP_KERNEL);
        if (NULL == rt5651)
                return -ENOMEM;

        i2c_set_clientdata(i2c, rt5651);

        rt5651->regmap = devm_regmap_init_i2c(i2c, &rt5651_regmap);
        if (IS_ERR(rt5651->regmap)) {
                ret = PTR_ERR(rt5651->regmap);
                dev_err(&i2c->dev, "Failed to allocate register map: %d\n",
                        ret);
                return ret;
        }

        err = regmap_read(rt5651->regmap, RT5651_DEVICE_ID, &ret);
        if (err)
                return err;

        if (ret != RT5651_DEVICE_ID_VALUE) {    /* 0x6281 */
                dev_err(&i2c->dev,
                        "Device with ID register %#x is not rt5651\n", ret);
                return -ENODEV;
        }

        regmap_write(rt5651->regmap, RT5651_RESET, 0);

        ret = regmap_register_patch(rt5651->regmap, init_list,
                                    ARRAY_SIZE(init_list));
        if (ret != 0)
                dev_warn(&i2c->dev, "Failed to apply regmap patch: %d\n", ret);

        rt5651->irq = i2c->irq;
        rt5651->hp_mute = true;

        INIT_DELAYED_WORK(&rt5651->bp_work, rt5651_button_press_work);
        INIT_WORK(&rt5651->jack_detect_work, rt5651_jack_detect_work);

        /* Make sure work is stopped on probe-error / remove */
        ret = devm_add_action_or_reset(&i2c->dev, rt5651_cancel_work, rt5651);
        if (ret)
                return ret;

        ret = devm_request_irq(&i2c->dev, rt5651->irq, rt5651_irq,
                               IRQF_TRIGGER_RISING | IRQF_TRIGGER_FALLING
                               | IRQF_ONESHOT | IRQF_NO_AUTOEN, "rt5651", rt5651);
        if (ret) {
                dev_warn(&i2c->dev, "Failed to reguest IRQ %d: %d\n",
                         rt5651->irq, ret);
                rt5651->irq = -ENXIO;
        }

        ret = devm_snd_soc_register_component(&i2c->dev,
                                &soc_component_dev_rt5651,
                                rt5651_dai, ARRAY_SIZE(rt5651_dai));

        return ret;
}

九步，按顺序：

第 1 步，申请私有数据。 devm_kzalloc 申请 struct rt5651_priv，devm_ 意味着跟着设备生命周期自动释放。然后 i2c_set_clientdata(i2c, rt5651) 把它挂到 i2c->dev.driver_data。之后 snd_soc_component_get_drvdata(component) 拿到的就是这个指针——因为 component 的 dev 就是 i2c->dev。

第 2 步，注册 regmap。 devm_regmap_init_i2c 之后就能 regmap_read/regmap_write 了。失败直接返回，因为后面每一步都依赖寄存器访问。

第 3 步，读设备 ID。 RT5651_DEVICE_ID = 0xFF，读回值必须等于 RT5651_DEVICE_ID_VALUE = 0x6281。这一步是「I2C 通不通 + 芯片在不在」的双重确认。ID 不对返回 -ENODEV，probe 失败。

素材原文在 regmap_read(rt5651->regmap, RT5651_DEVICE_ID, &ret); 后面紧贴着写了 if (err)，两行连在了一起。这是抓取时换行丢了，实际是两句。

第 4 步，软件复位。 向 0x00 写 0，全部寄存器回默认值。

第 5 步，打补丁。 regmap_register_patch 写 RT5651_PR_BASE + 0x3d = 0x3e00。失败只 dev_warn，不阻断。

第 6 步，初始化私有状态。 rt5651->irq = i2c->irq——设备树没配中断时 i2c->irq 是 0。hp_mute = true 是安全默认，开机先静音。然后初始化两个 work：

c
INIT_DELAYED_WORK(&rt5651->bp_work, rt5651_button_press_work);
INIT_WORK(&rt5651->jack_detect_work, rt5651_jack_detect_work);

bp_work 是延迟工作队列，处理耳机按键（按钮按下的检测）；jack_detect_work 是普通工作队列，处理插拔事件。

第 7 步，注册清理动作。 devm_add_action_or_reset 在 probe 失败或设备卸载时调 rt5651_cancel_work：

c
static void rt5651_cancel_work(void *data)
{
        struct rt5651_priv *rt5651 = data;

        cancel_work_sync(&rt5651->jack_detect_work);
        cancel_delayed_work_sync(&rt5651->bp_work);
}

两个 cancel_*_sync 都是同步等待，保证 work 真的停了才返回。这一步必须在申请中断之前——先有清理动作，再有中断源，否则中断进来了但 work 还没初始化完。

第 8 步，申请中断。 devm_request_irq 配 IRQF_TRIGGER_RISING | IRQF_TRIGGER_FALLING | IRQF_ONESHOT | IRQF_NO_AUTOEN。

  • 双边沿触发：插拔两个方向都要响应；
  • IRQF_ONESHOT：中断线程化，handler 跑完才放开中断线，配合下面那个「快速返回」的 handler；
  • IRQF_NO_AUTOEN：申请成功但不自动使能。真正 enable_irq 是在 rt5651_enable_jack_detect 的最后。这防止申请到使能之间的事件把 handler 提前叫起来。

handler 极简：

c
static irqreturn_t rt5651_irq(int irq, void *data)
{
        struct rt5651_priv *rt5651 = data;

        queue_work(system_power_efficient_wq, &rt5651->jack_detect_work);

        return IRQ_HANDLED;
}

只把 work 排进队列就返回。真正的寄存器读写全在 rt5651_jack_detect_work 里。这是中断上下文的常规做法：I2C 读寄存器会睡眠，不能在硬中断里做。

设备树没配中断时 i2c->irq = 0，这次申请必然失败，于是：

text
[    3.465917] rt5651 1-001a: Failed to reguest IRQ 0: -22

rt5651_probe（component 层） #

rt5651_i2c_probe 注册完 component 就结束了。真正操作 DAPM 相关寄存器的初始化在 rt5651_probe，由 soc_probe_component 在注册声卡时调用：

c
static int rt5651_probe(struct snd_soc_component *component)
{
        struct rt5651_priv *rt5651 = snd_soc_component_get_drvdata(component);

        rt5651->component = component;

        snd_soc_component_update_bits(component, RT5651_PWR_ANLG1,
                RT5651_PWR_LDO_DVO_MASK, RT5651_PWR_LDO_DVO_1_2V);
        snd_soc_component_force_bias_level(component, SND_SOC_BIAS_OFF);

        rt5651_apply_properties(component);

        return 0;
}

三件事：

  1. 配内部 LDO 输出 1.2V。 RT5651_PWR_ANLG1（0x63）的 PWR_LDO_DVO_MASK = 0x03（位[1:0]），PWR_LDO_DVO_1_2V = 2，也就是写 10'b 到这两位上，得到 1.2V 输出。这个 LDO 供数字核用，LDO1_EN 拉高时才启用；
  2. 强制 bias 等级到 OFF。 snd_soc_component_force_bias_level(component, SND_SOC_BIAS_OFF) 把 dapm->bias_level 置 0，等于告诉 DAPM「当前是关闭态」。这样后续第一次上电时会走完整的 OFF → STANDBY 路径，四路参考电压能正常拉起；
  3. 应用设备树属性。 rt5651_apply_properties 从 of_node 里读 realtek,jd-src、realtek,ovcd-threshold 等私有属性。具体支持哪些属性，看 Documentation/devicetree/bindings/sound/rt5651.txt，本篇不列。

第 2 步那个 force_bias_level 容易看漏。没有它，dapm->bias_level 的初值是 0（SND_SOC_BIAS_OFF 的枚举值也是 0），看起来一样——但 force 版本会把 bias_level 的变化通知出去，确保状态机从干净状态开始。

set_bias_level 详解 #

c
static int rt5651_set_bias_level(struct snd_soc_component *component,
                        enum snd_soc_bias_level level)
{
        switch (level) {
        case SND_SOC_BIAS_PREPARE:
                if (SND_SOC_BIAS_STANDBY == snd_soc_component_get_bias_level(component)) {
                        if (snd_soc_component_read(component, RT5651_PLL_MODE_1) & 0x9200)
                                snd_soc_component_update_bits(component, RT5651_D_MISC,
                                                    0xc00, 0xc00);
                }
                break;
        case SND_SOC_BIAS_STANDBY:
                if (SND_SOC_BIAS_OFF == snd_soc_component_get_bias_level(component)) {
                        snd_soc_component_update_bits(component, RT5651_PWR_ANLG1,
                                RT5651_PWR_VREF1 | RT5651_PWR_MB |
                                RT5651_PWR_BG | RT5651_PWR_VREF2,
                                RT5651_PWR_VREF1 | RT5651_PWR_MB |
                                RT5651_PWR_BG | RT5651_PWR_VREF2);
                        usleep_range(10000, 15000);
                        snd_soc_component_update_bits(component, RT5651_PWR_ANLG1,
                                RT5651_PWR_FV1 | RT5651_PWR_FV2,
                                RT5651_PWR_FV1 | RT5651_PWR_FV2);
                        snd_soc_component_update_bits(component, RT5651_D_MISC, 0x1, 0x1);
                }
                break;

        case SND_SOC_BIAS_OFF:
                snd_soc_component_write(component, RT5651_D_MISC, 0x0010);
                snd_soc_component_write(component, RT5651_PWR_DIG1, 0x0000);
                snd_soc_component_write(component, RT5651_PWR_DIG2, 0x0000);
                snd_soc_component_write(component, RT5651_PWR_VOL, 0x0000);
                snd_soc_component_write(component, RT5651_PWR_MIXER, 0x0000);
                /* Do not touch the LDO voltage select bits on bias-off */
                snd_soc_component_update_bits(component, RT5651_PWR_ANLG1,
                        ~RT5651_PWR_LDO_DVO_MASK, 0);
                /* Leave PLL1 and jack-detect power as is, all others off */
                snd_soc_component_update_bits(component, RT5651_PWR_ANLG2,
                                    ~(RT5651_PWR_PLL | RT5651_PWR_JD_M), 0);
                break;

        default:
                break;
        }

        return 0;
}

三个分支对应三个方向的迁移：

分支 触发条件 条件检查 动作
PREPARE 进准备态 当前是 STANDBY 若 ASRC 开着，写 D_MISC[11:10] = 11'b
STANDBY 进待机态 当前是 OFF 拉 4 路参考电压、延时、切慢速 VREF、写 D_MISC[0] = 1
OFF 进关闭态 无 清 5 个电源寄存器，保留 LDO 电压位和 PLL/JD 电源位

PREPARE 分支的判断条件是 PLL_MODE_1 & 0x9200。0x9200 展开成二进制：

text
0x9200 = 1001 0010 0000 0000
              bit15  bit12  bit9
              I2S1   I2S2   DMIC1
              ASRC   ASRC   ASRC

任一路 ASRC 开着，就往 D_MISC 的位[11:10] 写 11'b。datasheet 没描述这两位的作用，驱动注释也直说「芯片手册中并没有描述这两位有什么作用」。这是典型的厂商私有配置，只能照抄，别自作聪明改。

STANDBY 分支的寄存器位：

位 宏 名称 含义
15 PWR_VREF1 VREF1 Power Control 0 下电，1 上电
14 PWR_FV1 VREF1 Fast Mode Control 0 Fast VREF，1 Slow VREF
13 PWR_MB MBIAS Power Control 0 下电，1 上电
11 PWR_BG MBIAS Bandgap Power Control 0 下电，1 上电
4 PWR_VREF2 VREF2 Power Control 0 下电，1 上电
0 PWR_FV2 VREF2 Fast Mode Control 0 Fast VREF，1 Slow VREF

先上电（bit15/13/11/4），延时，再切慢速模式（bit14/0）。顺序不能反——VREF 还没稳就切慢速，环路会振荡。datasheet 注释写了 For good analog performance，意思是慢速模式模拟性能更好，代价是建立时间长，所以必须等电压稳。

OFF 分支的两条「保留」注释值得单独记：

  • Do not touch the LDO voltage select bits on bias-off——写的是 ~RT5651_PWR_LDO_DVO_MASK 作为 mask，把 LDO 电压位排除在外。因为 LDO 电压是 rt5651_probe 里配好的，清了就得重配；
  • Leave PLL1 and jack-detect power as is——~（PWR_PLL | PWR_JD_M），PLL 电源和 jack 检测电源不清。因为这两路在 bias off 期间还要工作（插拔检测必须在「关机」状态下也响应）。

D_MISC（0xFA）上电时写 0x0010，待机时写位[0]。同样，datasheet 没描述这两处，照抄。

素材原文说「这里寄存器配置有点看不懂……有兴趣自行研究吧」，这个态度是对的。看不懂就不要动。

rt5651_enable_jack_detect 的骨架：

c
static void rt5651_enable_jack_detect(struct snd_soc_component *component,
                                      struct snd_soc_jack *hp_jack,
                                      struct gpio_desc *gpiod_hp_det)
{
        struct rt5651_priv *rt5651 = snd_soc_component_get_drvdata(component);
        bool using_internal_jack_detect = true;

        /* Select jack detect source */
        switch (rt5651->jd_src) {
        case RT5651_JD_NULL:
                rt5651->gpiod_hp_det = gpiod_hp_det;
                if (!rt5651->gpiod_hp_det)
                        return; /* No jack detect */
                using_internal_jack_detect = false;
                break;
        case RT5651_JD1_1:
                snd_soc_component_update_bits(component, RT5651_JD_CTRL2,
                        RT5651_JD_TRG_SEL_MASK, RT5651_JD_TRG_SEL_JD1_1);
                /* active-low is normal, set inv flag for active-high */
                if (rt5651->jd_active_high)
                        snd_soc_component_update_bits(component,
                                RT5651_IRQ_CTRL1,
                                RT5651_JD1_1_IRQ_EN | RT5651_JD1_1_INV,
                                RT5651_JD1_1_IRQ_EN | RT5651_JD1_1_INV);
                else
                        snd_soc_component_update_bits(component,
                                RT5651_IRQ_CTRL1,
                                RT5651_JD1_1_IRQ_EN | RT5651_JD1_1_INV,
                                RT5651_JD1_1_IRQ_EN);
                break;
        case RT5651_JD1_2:
                snd_soc_component_update_bits(component, RT5651_JD_CTRL2,
                        RT5651_JD_TRG_SEL_MASK, RT5651_JD_TRG_SEL_JD1_2);
                /* active-low is normal, set inv flag for active-high */
                if (rt5651->jd_active_high)
                        snd_soc_component_update_bits(component,
                                RT5651_IRQ_CTRL1,
                                RT5651_JD1_2_IRQ_EN | RT5651_JD1_2_INV,
                                RT5651_JD1_2_IRQ_EN | RT5651_JD1_2_INV);
                else
                        snd_soc_component_update_bits(component,
                                RT5651_IRQ_CTRL1,
                                RT5651_JD1_2_IRQ_EN | RT5651_JD1_2_INV,
                                RT5651_JD1_2_IRQ_EN);
                break;
        case RT5651_JD2:
                snd_soc_component_update_bits(component, RT5651_JD_CTRL2,
                        RT5651_JD_TRG_SEL_MASK, RT5651_JD_TRG_SEL_JD2);
                /* active-low is normal, set inv flag for active-high */
                if (rt5651->jd_active_high)
                        snd_soc_component_update_bits(component,
                                RT5651_IRQ_CTRL1,
                                RT5651_JD2_IRQ_EN | RT5651_JD2_INV,
                                RT5651_JD2_IRQ_EN | RT5651_JD2_INV);
                else
                        snd_soc_component_update_bits(component,
                                RT5651_IRQ_CTRL1,
                                RT5651_JD2_IRQ_EN | RT5651_JD2_INV,
                                RT5651_JD2_IRQ_EN);
                break;
        default:
                dev_err(component->dev, "Currently only JD1_1 / JD1_2 / JD2 are supported\n");
                return;
        }

        if (using_internal_jack_detect) {
                /* IRQ output on GPIO1 */
                snd_soc_component_update_bits(component, RT5651_GPIO_CTRL1,
                        RT5651_GP1_PIN_MASK, RT5651_GP1_PIN_IRQ);

                /* Enable jack detect power */
                snd_soc_component_update_bits(component, RT5651_PWR_ANLG2,
                        RT5651_PWR_JD_M, RT5651_PWR_JD_M);
        }

        /* Set OVCD threshold current and scale-factor */
        snd_soc_component_write(component, RT5651_PR_BASE + RT5651_BIAS_CUR4,
                                0xa800 | rt5651->ovcd_sf);

        snd_soc_component_update_bits(component, RT5651_MICBIAS,
                                      RT5651_MIC1_OVCD_MASK |
                                      RT5651_MIC1_OVTH_MASK |
                                      RT5651_PWR_CLK12M_MASK |
                                      RT5651_PWR_MB_MASK,
                                      RT5651_MIC1_OVCD_EN |
                                      rt5651->ovcd_th |
                                      RT5651_PWR_MB_PU |
                                      RT5651_PWR_CLK12M_PU);

        /*
         * The over-current-detect is only reliable in detecting the absence
         * of over-current, when the mic-contact in the jack is short-circuited,
         * the hardware periodically retries if it can apply the bias-current
         * leading to the ovcd status flip-flopping 1-0-1 with it being 0 about
         * 10% of the time, as we poll the ovcd status bit we might hit that
         * 10%, so we enable sticky mode and when checking OVCD we clear the
         * status, msleep() a bit and then check to get a reliable reading.
         */
        snd_soc_component_update_bits(component, RT5651_IRQ_CTRL2,
                RT5651_MB1_OC_STKY_MASK, RT5651_MB1_OC_STKY_EN);

        rt5651->hp_jack = hp_jack;
        if (rt5651_support_button_press(rt5651)) {
                rt5651_enable_micbias1_for_ovcd(component);
                rt5651_enable_micbias1_ovcd_irq(component);
        }

        enable_irq(rt5651->irq);
        /* sync initial jack state */
        queue_work(system_power_efficient_wq, &rt5651->jack_detect_work);
}

四种 JD 源：

jd_src 值 用 JD_CTRL2 的哪个 备注
RT5651_JD_NULL — 不用 走外部 GPIO，需 gpiod_hp_det
RT5651_JD1_1 — JD_TRG_SEL_JD1_1 接 JD1 引脚
RT5651_JD1_2 — JD_TRG_SEL_JD1_2 接 JD1 引脚的另一种检测模式
RT5651_JD2 — JD_TRG_SEL_JD2 接 JD2 引脚

jd_active_high 为真时，除了使能 IRQ，还要置 INV 位把极性反过来。注释写得很直白：active-low is normal——芯片默认低电平触发，板子接成高电平触发才需要置 INV。

using_internal_jack_detect 为真时做两件事：

  1. 把 GPIO1 复用成 IRQ 输出（GPIO_CTRL1 的 GP1_PIN_MASK 写成 GP1_PIN_IRQ）。这一步是把 GPIO1/IRQ1 这颗引脚从「通用 GPIO」切成「中断输出」；
  2. 打开 jack 检测电源（PWR_ANLG2 的 PWR_JD_M）。

ovcd 相关是麦克风按键检测用的。RT5651_BIAS_CUR4 写 0xa800 | ovcd_sf，前 16 位是固定的偏置电流配置，低 16 位是缩放因子。MICBIAS 寄存器配的是过流检测（over-current detect）阈值和使能。

那段长注释讲了一个硬件行为：过流检测只在「没有过流」这个方向上可靠。插孔里的麦克风触点被短路时，硬件会周期性地重试加偏置电流，导致 OVCD 状态在 1-0-1 之间翻转，其中约有 10% 的时间是 0。软件轮询这个状态位有概率正好撞上那 10%。所以驱动开了 sticky 模式（MB1_OC_STKY_EN），检查 OVCD 的时候先清状态、msleep() 一下、再读，才能拿到可靠值。

最后两句：enable_irq(rt5651->irq) 把中断真正打开（probe 里用了 IRQF_NO_AUTOEN，所以必须在这里显式开），然后排一个 jack_detect_work 同步初始插孔状态。

在 NanoPC-T4 上，这一步会因为 rt5651->irq = -ENXIO（probe 里 IRQ 申请失败被置成这个值）而无效——具体 enable_irq(-ENXIO) 会不会触发 warning，未验证。实测没有相关报错，说明要么设备树没走 set_jack，要么这条路径被 Machine 驱动的判断绕过了。

十七、设备树节点 #

codec 节点 #

在 arch/arm64/boot/dts/rockchip/rk3399-evb.dts 里，&i2c1 下面挂 rt5651：

dts
&i2c1 {
    status = "okay";
    i2c-scl-rising-time-ns = <300>;
    i2c-scl-falling-time-ns = <15>;

    rt5651: rt5651@1a {
        #sound-dai-cells = <0>;
        compatible = "rockchip,rt5651";
        reg = <0x1a>;
        clocks = <&cru SCLK_I2S_8CH_OUT>;
        clock-names = "mclk";
        status = "okay";
    };
};

逐项：

属性 值 含义
status（i2c1 上） "okay" 打开 I2C1 控制器。这项不 ok，codec 节点写了也没用
i2c-scl-rising-time-ns <300> SCL 上升时间，单位 ns。用于算 I2C 时序
i2c-scl-falling-time-ns <15> SCL 下降时间，单位 ns
#sound-dai-cells <0> 作为 DAI 被引用时不带参数，sound-dai = <&rt5651>
compatible "rockchip,rt5651" 匹配用的字符串。注意和驱动的 of_match 不一致
reg <0x1a> I2C 从设备 7 位地址
clocks <&cru SCLK_I2S_8CH_OUT> MCLK 时钟源
clock-names "mclk" 时钟名，驱动按这个名字 devm_clk_get
status "okay" 该设备启用

reg = <0x1a> 是 ALC5651 的固定 I2C 地址，由硬件引脚决定，改不了。板子上如果同时有别的 0x1a 设备，会冲突，表现为 probe 读到错的 ID。

i2c-scl-rising-time-ns = <300> 和 i2c-scl-falling-time-ns = <15> 这两个值来自板子的信号完整性测量。填大了会拉低 SCL 频率，填小了会超时。

#sound-dai-cells = <0> 决定 Machine 驱动里怎么写引用。为 0 时写 sound-dai = <&rt5651>；为 1 时得写 sound-dai = <&rt5651 0>，那个 0 是 DAI 编号。ALC5651 有两个 DAI，但如果只有一路被用，0 就够了。

I2C 控制器节点 #

i2c1 的定义在 arch/arm64/boot/dts/rockchip/rk3399.dtsi：

dts
i2c1: i2c@ff110000 {
        compatible = "rockchip,rk3399-i2c";
        reg = <0x0 0xff110000 0x0 0x1000>;
        assigned-clocks = <&cru SCLK_I2C1>;
        assigned-clock-rates = <200000000>;
        clocks = <&cru SCLK_I2C1>, <&cru PCLK_I2C1>;
        clock-names = "i2c", "pclk";
        interrupts = <GIC_SPI 59 IRQ_TYPE_LEVEL_HIGH 0>;
        pinctrl-names = "default";
        pinctrl-0 = <&i2c1_xfer>;
        #address-cells = <1>;
        #size-cells = <0>;
        status = "disabled";
};

要点：

  • reg 是 64 位地址写法，<0x0 0xff110000 0x0 0x1000> 表示基址 0xFF110000、长度 0x1000；
  • assigned-clock-rates = <200000000> 把 SCLK_I2C1 设成 200MHz。这是控制器的输入时钟，实际 SCL 频率由分频器从它算出来；
  • clocks 两路：SCLK_I2C1（功能时钟）和 PCLK_I2C1（总线时钟），名字分别是 i2c 和 pclk；
  • pinctrl-0 = <&i2c1_xfer> 是引脚复用，对应 GPIO4_A1/A2；
  • #address-cells = <1> 和 #size-cells = <0> 决定了子节点 reg 只写一个数（从地址），不带长度；
  • status = "disabled" 是 SoC 级默认值，板级 dts 里改成 okay。

status 从 disabled 变成 okay 是「板子级覆盖 SoC 级」的标准做法。dtsi 里全部关掉，dts 里按板子需要打开，这样同一颗 SoC 的不同板子不会互相干扰。

MCLK 的来源 #

clock-names = "mclk";

SCLK_I2S_8CH_OUT 是 RK3399 CRU 里的一颗 composite 时钟，定义在 drivers/clk/rockchip/clk-rk3399.c：

text
COMPOSITE_NODIV(SCLK_I2S_8CH_OUT, "clk_i2sout", mux_i2sout_p, CLK_SET_RATE_PARENT,
                RK3399_CLKSEL_CON(31), 2, 1, MFLAGS,
                RK3399_CLKGATE_CON(8), 12, GFLAGS)

COMPOSITE_NODIV 定义在 drivers/clk/rockchip/clk.h：

c
#define COMPOSITE_NODIV(_id, cname, pnames, f, mo, ms, mw, mf,  \
                        go, gs, gf)                             \
        {                                                       \

                .branch_type    = branch_composite,             \
                .name           = cname,                        \

                .mux_shift      = ms,                           \
                .mux_width      = mw,                           \

参数展开：

宏参数 实际值 含义
_id SCLK_I2S_8CH_OUT 时钟 ID
cname "clk_i2sout" 时钟名
pnames mux_i2sout_p 父时钟名单
f CLK_SET_RATE_PARENT 设频率时往父时钟传

两个地址宏：

c
#define RK3399_CLKGATE_CON(x)           ((x) * 0x4 + 0x300)
#define RK3399_CLKSEL_CON(x)            ((x) * 0x4 + 0x100)

算一下：

  • RK3399_CLKGATE_CON(8) = 8 × 0x4 + 0x300 = 0x320，即 CRU_CLKGATE_CON8；
  • RK3399_CLKSEL_CON(31) = 31 × 0x4 + 0x100 = 0x17C，即 CRU_CLKSEL_CON31。

CRU_CLKGATE_CON8 的位[12] 是 clk_i2sout 的时钟使能，低电平使能、高电平禁用（Rockchip CRU 的门控是反相的）。

CRU_CLKSEL_CON31 的位[2] 用于 clk_i2sout 的时钟源选择。mux 位偏移是 2、位宽 1，和这个对得上。clk_i2sout 需要配成 clk_i2s。

clk_i2sout 到底是什么？RK3399 有三路 I2S，其中 I2S2 内部接 HDMI/DP，真正能对外的是 I2S0 和 I2S1。而 MCLK 只有一路，所以 I2S0 和 I2S1 只有一个能占用。clk_i2sout 就是这条 MCLK 信号线的时钟——这是素材作者的推断，标注为推断而非 datasheet 明确结论。

父时钟链 #

mux_i2sout_p 有两个父时钟：

text
PNAME(mux_i2sout_p)  = { "clk_i2sout_src", "xin12m" };
  • clk_i2sout_src：ID 62，多路选择时钟；
  • xin12m：ID 64，12MHz 固定时钟（有源或无源晶振）。

clk_i2sout_src 的定义：

text
MUX(0, "clk_i2sout_src", mux_i2sch_p, CLK_SET_RATE_PARENT,
RK3399_CLKSEL_CON(31), 0, 2, MFLAGS),

MUX 类型，父时钟是 mux_i2sch_p，mux 位偏移 0、位宽 2（4 选 1，实际用了 3 个）：

text
PNAME(mux_i2sch_p)  = { "clk_i2s0", "clk_i2s1","clk_i2s2" };

所以完整的时钟链是：

text
clk_i2s0 / clk_i2s1 / clk_i2s2          （三选一，CRU_CLKSEL_CON31[1:0]）
    └─► clk_i2sout_src
            └─► clk_i2sout              （二选一，CRU_CLKSEL_CON31[2]；另一路是 xin12m）
                    └─► SCLK_I2S_8CH_OUT
                            └─► MCLK（ALC5651 引脚）

clk_i2s0 及其上游在 Platform 驱动那一篇讲，本篇不展开。

一个 dts 写法上的坑 #

compatible = "rockchip,rt5651" 和驱动 of_match 里的 "realtek,rt5651" 不一致，理由在第七节讲过。这带来一个副作用：如果你把 i2c_device_id 那张表删掉、只留 of_match，probe 就永远不会被调用。

反过来，如果你按正规做法把 dts 改成 compatible = "realtek,rt5651"，type 就变成 "rt5651"，id_table 依然能匹配上。两条路都能通，但含义不同：

dts compatible 匹配路径 需要动驱动吗
"rockchip,rt5651" 仅 id_table 不用
"realtek,rt5651" of_match + id_table 都能命中 不用

推荐第二种。理由：走 of_match 才有 of_node 关联，驱动的 of_property_read_* 才能正常工作。rt5651_apply_properties 读的那些私有属性依赖 of_node，虽然 i2c_client 的 of_node 是在 of_i2c_get_board_info 里一起设的、跟匹配走哪条路无关，但走 of_match 语义上更干净。

DAI 在 Machine 侧怎么引 #

codec 节点只定义了 codec 自己。Machine 节点（sound 节点）里通过 sound-dai 引用：

dts
/* 示例，具体内容以 Machine 驱动文档为准 */
sound {
    compatible = "simple-audio-card";
    simple-audio-card,cpu {
        sound-dai = <&i2s1>;
    };
    simple-audio-card,codec {
        sound-dai = <&rt5651>;
    };
};

simple-audio-card 的完整写法和 Machine 驱动的三种实现方式，在《ASoC 架构：Machine、Platform 与 Codec》和《Machine 驱动 simple-audio-card》里。这里只说一句：sound-dai = <&rt5651> 里没有 DAI 编号，因为 #sound-dai-cells = <0>。要指定用哪个 DAI，得把 #sound-dai-cells 改成 <1> 然后写 <&rt5651 0>。

一个通用的定位思路 #

遇到问题按「电 → 时钟 → 数据 → 通路 → 混音」五层往下走：

  1. 电：0x63 的 PWR_VREF1/PWR_MB/PWR_BG/PWR_VREF2 是否都为 1。为 0 说明 bias 没上去，什么都不会有声；
  2. 时钟：0x80 的时钟源、0x73 的分频档位，和 /proc/asound/card0/pcm0p/sub0/hw_params 里的 rate 对得上吗；
  3. 数据：0x70 的位[15]（主从）、位[1:0]（格式）和 SoC 侧 I2S_CKR 配的是不是一致；
  4. 通路：DAPM 里从 AIF1RX 到 HPOR 是不是一串 On；
  5. 混音：OUT MIXR 的 5 个开关、HPOVOL R 的开关，逐个确认。

五层都过了还没声，问题就在硬件——接线、焊接、电源。软件层能查的到此为止。
