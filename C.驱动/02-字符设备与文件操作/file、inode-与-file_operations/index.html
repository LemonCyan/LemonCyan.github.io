用户在 /dev 下 open 一个字符设备，内核是如何找到你注册的那个 cdev，又是如何把 read/write 接到你写的函数上的？

这条链路上有三个关键数据结构：struct inode（文件节点）、struct file（打开的文件实例）、struct cdev（字符设备实体），而 struct file_operations 则是挂在这个链条末端的操作表。理解它们之间的指针关系，就等于理解了字符设备的工作原理。

本文覆盖：struct file 的五个重要成员、struct inode 与 file 的区别与 i_rdev/i_cdev、file_operations 成员的逐字段解析、chrdev_open 的六步、private_data + container_of 的黄金法则。

本文不覆盖：cdev 结构体本身与设备号申请见《cdev 与设备号》；read/write 的数据拷贝见《read()、write() 与用户空间数据拷贝》；ioctl 见《ioctl()：命令码、实现与实例》；VFS 层的文件系统抽象（super_block/dentry/sys_open 调用链）见 B.内核/04-文件系统 的《VFS 虚拟文件系统：抽象层与三大操作表》。

一、三个结构体与一条打开链 #

1.1 定位 #

在设备驱动程序的设计中，一般而言只会关心 file 和 inode 这两个结构体。用户空间 fd = open("/dev/hello", O_RDWR) 这一调用，最终会带出 struct inode 与 struct file 两个数据结构，二者都在虚拟文件系统（VFS）处。

1.2 三者关系图 #

 用户空间进程                     内核 VFS 空间
  +----------+                   struct file (由 fd 索引)
  |  fd = 3  |------------------> [ *f_op        ] ------------+
  |          |                    [ private_data ]              |
  +----------+                          |                       |
                                        v (通常在 open 中指向)   | (chrdev_open 时替换)
                                  [ struct cdev ]               |
                                        ^                       |
                                        | i_cdev                v
                                 struct inode          struct file_operations
                                  [ *i_cdev ]---------> [ .open  = hello_open  ]
                                  [ i_rdev  ] (设备号)  [ .read  = hello_read  ]
                                                        [ .write = hello_write ]

1.3 职责分工 #

结构体 代表什么 数量关系 关键成员
struct inode 磁盘或 VFS 中的物理节点 一个设备节点唯一一个 i_rdev、i_cdev
struct file 一次打开的文件实例 一个 inode 可对应多个 f_op、f_pos、private_data
struct cdev 你编写的字符设备驱动实体 通常一个驱动一个 ops、dev、count

一句话记住区别：inode 是"文件本身"，file 是"打开这个文件这件事"。同一个设备被三个进程打开，就有三个 struct file，但只有一个 struct inode。

二、struct file #

2.1 与 C 库 FILE 的区别 #

这是必须先分清的一点：这里的 file 与用户空间程序里的 FILE 指针是不同的。用户空间的 FILE 定义在 C 库中，从来不会出现在内核中；而 struct file 是内核当中的数据结构，因此它也不会出现在用户层程序中。

file 结构体指示一个已经打开的文件（设备对应于设备文件）。系统中的每个打开的文件在内核空间都有一个相应的 struct file，它由内核在打开文件时创建，并传递给在文件上进行操作的任何函数，直至文件被关闭；文件关闭后内核就释放相应的数据结构。

在内核源码中，struct file 要么写作 file，要么写作 filp（意指 "file pointer"）。注意区分：file 指的是 struct file 本身，而 filp 是指向这个结构体的指针。

2.2 五个重要成员 #

a — fmode_t f_mode; #

此文件模式通过 FMODE_READ、FMODE_WRITE 标识了文件是可读、可写或二者兼有。在 open 或 ioctl 函数中可能需要检查此域以确认文件的读/写权限。你不必直接去检测读或写权限，因为在进行 ioctl 等操作时内核本身就需要对其权限进行检测。

b — loff_t f_pos; #

当前读写文件的位置，64 位。如果想知道当前文件位置在哪，驱动可以读取这个值而不会改变其位置。

对 read、write 来说，当它们接收到一个 loff_t * 型指针作为最后一个参数时，读写操作便会更新文件的位置，而不需要直接执行 filp->f_pos 操作。llseek 方法的目的就是用于改变文件的位置。

c — unsigned int f_flags; #

文件标志，如 O_RDONLY、O_NONBLOCK、O_SYNC。驱动中可以检查 O_NONBLOCK 标志查看是否有非阻塞请求；其它标志较少使用。

特别注意：读写权限的检查是使用 f_mode 而不是 f_flags。所有标志定义在 <linux/fcntl.h> 与 <linux/fs.h> 中。

d — struct file_operations *f_op; #

与文件相关的各种操作。当文件需要快速进行各种操作时，内核分配这个指针作为实现文件打开、读、写等功能的一部分。

filp->f_op 的值从未被内核保存作为下次的引用——也就是说你可以随时改变与文件相关的各种操作，这种方式效率非常高。chrdev_open 正是利用这一点完成了 f_op 的替换（见第四章）。

e — void *private_data; #

在驱动调用 open 方法之前，open 系统调用设置此指针为 NULL。你可以很自由地将它作为自己的数据域，或者干脆不管它。

例如，你可以让它指向一块分配好的数据，但是必须记得在 file 结构被内核销毁之前，在 release 方法中释放这些数据的内存空间。private_data 用于在系统调用期间保存各种状态信息是非常有用的。

三、struct inode #

3.1 它代表什么 #

VFS inode 包含文件的访问权限、属主、组、大小、生成时间、访问时间、最后修改时间等信息。它是 Linux 管理文件系统的最基本单位，也是文件系统连接任何子目录、文件的桥梁。

内核使用 inode 结构体在内核内部表示一个文件。因此，它与表示一个已经打开的文件描述符的 struct file 是不同的：

  • 我们可以使用多个 file 表示同一个文件的多个文件描述符；
  • 但此时所有这些 file 结构全部都必须指向同一个 inode。

3.2 驱动只关心两个域 #

inode 结构体包含了一大堆文件相关的信息，但就驱动代码而言，只要关心其中两个域：

(1) dev_t i_rdev; #

表示设备文件的结点，这个域实际上包含了设备号。

(2) struct cdev *i_cdev; #

struct cdev 是内核的一个内部结构，用来表示字符设备。当 inode 结点指向一个字符设备文件时，此域为一个指向 cdev 的指针。

3.3 源码节选 #

c
struct inode {
    struct hlist_node   i_hash;
    struct list_head    i_list;
    struct list_head    i_sb_list;
    struct list_head    i_dentry;
    unsigned long       i_ino;
    atomic_t            i_count;

    unsigned int        i_nlink;
    uid_t               i_uid;      /* inode 拥有者 id */
    gid_t               i_gid;      /* inode 所属群组 id */
    dev_t               i_rdev;     /* 若是设备文件，记录设备的设备号 */
    u64                 i_version;
    loff_t              i_size;     /* inode 所代表的大小 */

    struct timespec     i_atime;    /* inode 最近一次的存取时间 */
    struct timespec     i_mtime;    /* inode 最近一次修改时间 */
    struct timespec     i_ctime;    /* inode 的生成时间 */

    unsigned int        i_blkbits;
    blkcnt_t            i_blocks;
    unsigned short      i_bytes;
    umode_t             i_mode;     /* 文件类型 + 权限位 */
    spinlock_t          i_lock;

    const struct inode_operations *i_op;
    const struct file_operations  *i_fop;
    struct super_block  *i_sb;
    struct address_space *i_mapping;
    struct list_head    i_devices;

    union {
        struct pipe_inode_info *i_pipe;

这是较老内核的结构体定义，字段数量随版本变化很大（现代内核的 i_atime/i_mtime/i_ctime 已合并为 struct timespec64 i_atime 等并移入 i_* 子结构）。记住 i_rdev 和 i_cdev 两个成员即可，其余不必背。

四、file_operations 逐字段解析 #

4.1 定义 #

struct file_operations 在 Fs.h 中定义，结构内是访问驱动程序的函数指针，这个结构的每一个成员的名字都对应着一个调用。

c
struct file_operations {
    struct module *owner;                                                    /* 拥有该结构的模块指针，一般为 THIS_MODULE */
    loff_t (*llseek)(struct file *, loff_t, int);                            /* 修改文件当前的读写位置 */
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);         /* 从设备中同步读取数据 */
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);  /* 向设备发送数据 */
    ssize_t (*aio_read)(struct kiocb *, const struct iovec *, unsigned long, loff_t);  /* 初始化一个异步读取 */
    ssize_t (*aio_write)(struct kiocb *, const struct iovec *, unsigned long, loff_t); /* 初始化一个异步写入 */
    int (*readdir)(struct file *, void *, filldir_t);                        /* 仅用于读取目录，设备文件为 NULL */
    unsigned int (*poll)(struct file *, struct poll_table_struct *);         /* 轮询：判断目前是否可非阻塞读写 */
    long (*unlocked_ioctl)(struct file *, unsigned int, unsigned long);      /* I/O 控制命令 */
    long (*compat_ioctl)(struct file *, unsigned int, unsigned long);        /* 64 位系统上代替 ioctl 处理 32 位调用 */
    int (*mmap)(struct file *, struct vm_area_struct *);                     /* 将设备内存映射到进程地址空间 */
    int (*open)(struct inode *, struct file *);                              /* 打开 */
    int (*flush)(struct file *, fl_owner_t id);                              /* flush 操作 */
    int (*release)(struct inode *, struct file *);                           /* 关闭 */
    int (*fsync)(struct file *, struct dentry *, int datasync);              /* 刷新待处理的数据 */
    int (*aio_fsync)(struct kiocb *, int datasync);                          /* 异步刷新待处理数据 */
    int (*fasync)(int, struct file *, int);                                  /* 通知设备 FASYNC 标志发生变化 */
    int (*lock)(struct file *, int, struct file_lock *);                     /* 文件加锁 */
    ssize_t (*sendpage)(struct file *, struct page *, int, size_t, loff_t *, int);
    unsigned long (*get_unmapped_area)(struct file *, unsigned long, unsigned long,
                                       unsigned long, unsigned long);
    int (*check_flags)(int);
    int (*flock)(struct file *, int, struct file_lock *);
};

4.2 工作原理 #

Linux 使用 file_operations 结构访问驱动程序的函数，这个结构的每一个成员的名字都对应着一个调用。

用户进程对设备文件进行诸如 read/write 操作时，系统调用通过设备文件的主设备号找到相应的设备驱动程序，然后读取这个数据结构相应的函数指针，接着把控制权交给该函数。这就是 Linux 设备驱动程序工作的基本原理。

用户态 read(fd, buf, n)
   │  系统调用
   ▼
VFS: filp->f_op->read(filp, buf, n, &filp->f_pos)
   │  查表：f_op 指向你注册的 file_operations
   ▼
你的 hello_read()

4.3 重点成员详解 #

owner #

第一个成员根本不是一个操作，它是一个指向拥有这个结构的模块的指针。它用来在操作还在被使用时阻止模块被卸载。几乎所有情况下它被初始化为 THIS_MODULE（一个在 <linux/module.h> 中定义的宏）。

llseek #

c
loff_t (*llseek)(struct file *filp, loff_t p, int orig);
  • filp：目标文件结构体指针；
  • p：文件定位的目标偏移量；
  • orig：定位的起始地址，可取 SEEK_SET(0，文件开头)、SEEK_CUR(1，当前位置)、SEEK_END(2，文件末尾)。

llseek 方法用作改变文件中的当前读/写位置，并且新位置作为（正的）返回值。

loff_t 是一个 "long offset"，就算在 32 位平台上也至少 64 位宽。错误由负返回值指示。如果这个函数指针是 NULL，seek 调用会以潜在地无法预知的方式修改 file 结构中的位置计数器。

read / write #

详见《read()、write() 与用户空间数据拷贝》。

poll #

判断目前是否可以进行非阻塞的读写。配合应用层的 select/poll 使用，详见 C.驱动/03-IO模型。

mmap #

用于请求将设备内存映射到进程地址空间。为什么需要它、驱动侧怎么实现 remap_pfn_range，见 B.内核/03-内存管理 的《Linux的mmap内存映射机制解析》。

fasync #

通知设备其 FASYNC 标志发生变化——这是异步通知（SIGIO）的驱动侧入口，详见 C.驱动/03-IO模型。

unlocked_ioctl / compat_ioctl #

不使用 BLK 文件系统时，将用 unlocked_ioctl 代替旧的 ioctl；在 64 位系统上，32 位的 ioctl 调用将使用 compat_ioctl 代替。细节见《ioctl()：命令码、实现与实例》。

五、chrdev_open：指针如何被"偷天换日" #

5.1 先看 cdev 当初怎么来的 #

从 struct inode 的 i_cdev 成员可以找到 cdev，而所有已注册的字符设备都挂在全局 chrdevs 数组中。

c
#define CHRDEV_MAJOR_HASH_SIZE 255

static DEFINE_MUTEX(chrdevs_lock);

static struct char_device_struct {
    struct char_device_struct *next;   /* 结构体指针 */
    unsigned int major;                /* 主设备号 */
    unsigned int baseminor;            /* 次设备起始号 */
    int minorct;                       /* 次设备号个数 */
    char name[64];
    struct cdev *cdev;                 /* will die */
} *chrdevs[CHRDEV_MAJOR_HASH_SIZE];    /* 只能挂 255 个字符主设备 */

全局数组 chrdevs 包含 255 个（CHRDEV_MAJOR_HASH_SIZE 的值）struct char_device_struct 元素，每一个对应一个相应的主设备号。

如果分配了一个设备号，就会创建一个 struct char_device_struct 对象并将其添加到 chrdevs 中；这样通过 chrdevs 数组就能知道分配了哪些设备号。

各注册函数的关系：

函数 做的事
register_chrdev_region() 分配指定范围的设备号
alloc_chrdev_region() 动态分配设备号
以上二者 都通过 __register_chrdev_region() 实现；仅仅注册设备号，要与 cdev 关联还得再调 cdev_add()
register_chrdev() 设备号 + cdev + 关联，一步到位（老接口）

register_chrdev() 具体做了四步：

  • a — 注册设备号，通过 __register_chrdev_region() 实现；
  • b — 分配一个 cdev，通过 cdev_alloc() 实现；
  • c — 将 cdev 添加到驱动模型中，这一步将设备号和驱动关联了起来，通过 cdev_add() 实现；
  • d — 将第一步创建的 struct char_device_struct 对象的 cdev 指向第二步分配的 cdev。由于 register_chrdev() 是老接口，这一步在新的接口中并不需要。

5.2 打开时的六步 #

对于一个字符设备文件，其 inode->i_cdev 指向字符驱动对象 cdev；如果 i_cdev 为 NULL，则说明该设备文件还没有被打开。

由于多个设备可以共用同一个驱动程序，因此通过字符设备 inode 中的 i_devices 和 cdev 中的 list 组成一个链表。

系统调用 open 打开一个字符设备时，通过一系列调用最终会执行到 chrdev_open——最终是通过调用 def_chr_fops 中的 .open，而 def_chr_fops.open = chrdev_open。

c
int chrdev_open(struct inode *inode, struct file *filp);

chrdev_open() 所做的事情可以概括为六步：

  1. 根据设备号（inode->i_rdev），在字符设备驱动模型中查找对应的驱动程序，这通过 kobj_lookup() 来实现，它会返回对应驱动程序 cdev 的 kobject；
  2. 设置 inode->i_cdev，指向找到的 cdev；
  3. 将 inode 添加到 cdev->list 的链表中；
  4. 使用 cdev 的 ops 设置 file 对象的 f_op；
  5. 如果 ops 中定义了 open 方法，则调用该 open 方法；
  6. 返回。

执行完 chrdev_open() 之后，file 对象的 f_op 指向 cdev 的 ops，因而之后对设备进行的 read、write 等操作，就会执行 cdev 的相应操作。

c
static int chrdev_open(struct inode *inode, struct file *filp)
{
    struct cdev *p;

    /* 通过 inode 获取之前绑定的 cdev 实体 */
    p = inode->i_cdev;

    /* 把 file 的操作指针替换为我们驱动中编写的 file_operations */
    filp->f_op = fops_get(p->ops);

    /* 调用驱动中真正的 open 函数 */
    if (filp->f_op->open)
        return filp->f_op->open(inode, filp);

    return 0;
}

这段是教学简化版。真实内核的 chrdev_open 还要处理 kobj_lookup、并发保护、i_cdev 为 NULL 时回填、模块引用计数等，逻辑比这复杂得多，但**"把 f_op 换成驱动自己的 ops"这一核心动作是准确的**。

这就是为什么 filp->f_op 的值"从未被内核保存作为下次的引用"——它本来就是要被替换的。

六、黄金法则：private_data + container_of #

6.1 问题 #

前面的链条解到 file 就断了：read/write 拿到的只有 struct file *，怎么找到"这是哪个设备的上下文"？

答案就在 struct file 的 private_data 成员——它专门用来承载驱动的私有上下文。

6.2 container_of 反向定位设备结构体 #

实际驱动里通常定义一个大结构体，把 cdev 嵌在里面：

c
struct my_char_dev {
    struct cdev cdev;       /* 嵌在内核要的 cdev */
    char *buf;              /* 自己的数据 */
    int size;
    struct semaphore sem;
    /* ... */
};

open 拿到的是 inode->i_cdev，即那个内嵌的 cdev 子对象的地址，而不是整个 my_char_dev 的地址。container_of 干的就是"从成员地址反推出包含它的结构体地址"：

c
static int hello_open(struct inode *inode, struct file *file)
{
    struct my_char_dev *dev;

    /* 通过 inode 中的 i_cdev 指针，反向计算出包含它的自定义设备大结构体指针 */
    dev = container_of(inode->i_cdev, struct my_char_dev, cdev);

    /* 存入 file 的 private_data 中 */
    file->private_data = dev;
    return 0;
}

static ssize_t hello_read(struct file *file, char __user *user_buf, size_t size, loff_t *pos)
{
    /* 轻松取出设备对象，无需再次计算 */
    struct my_char_dev *dev = file->private_data;

    /* 接下来可以直接操作 dev->buf, dev->sem 等私有字段了... */
    return size;
}

6.3 为什么是黄金法则 #

通过 file->private_data 承载设备指针，使得驱动中的不同操作接口能够安全、跨函数地共享当前操作设备的上下文环境，是编写高质量多设备并发字符驱动的核心法则。

它一次解决了三个问题：

问题 解法
read/write 只拿到 file，怎么找到设备？ file->private_data
同时支持多个次设备，怎么区分？ 每个 open 各自填自己的 dev 指针
怎么从内嵌的 cdev 找回外层结构体？ container_of

⚠️ 配套纪律：private_data 在 open 前是 NULL；若你在 open 里 kmalloc 了资源挂上去，必须在 release 里释放，否则每次 open/close 循环都泄漏一次。

勘误与整理说明：

  1. file_operations 结构体代码严重粘连：素材里是 structfile_operations、structmodule、constchar、unsignedint、loff_t 与函数名之间无空格，这种代码贴进编辑器连语法高亮都过不去。已逐行重建。
  2. struct inode 源码同样粘连：structinode、unsignedlong、structtimespec、hlist_nodei_hash 等。已重建为规范写法。
  3. 行号噪声：长稿(三) 51 处、长稿(四) 34 处。已清除。
  4. 交叉引用指向已失效的篇名：素材中多次出现"前面我们学习了字符设备结构体 cdev"、"在 有解析。"（后面空白）、"Linux 字符设备驱动开发 （一）—— 字符设备驱动结构（上）"这类章节标题被当作正文插进来的情况——这是抓取时把目录/面包屑混进了正文。已删除这些孤立标题行，改为正常指路。
  5. 原文"四、cdev 结构体"一节正文只有一句"在 有解析。"，内容完全缺失（指向的正是同目录另一篇）。本篇未保留该死节，改为一句话指路到《cdev 与设备号》。
  6. file_operations 成员数与版本差异：素材列的 23 个成员是 2.6.x 时代的样子，其中 ioctl 已被 unlocked_ioctl 取代、flock 后被移除、readdir 改为 iterate。本篇在代码中统一按现代主线内核的成员集合呈现，并保留素材原有的中文注释。
  7. file 与 inode 的差异被重复讲了两遍（两份素材各自讲一遍），本篇合并为 3.1 一节。
  8. 新增内容：1.2 关系图（cdev结构体与字符设备指针关联.md 原有 + 本篇补充）、1.3 职责分工表、4.2 的调用链示意、4.3 对 poll/mmap/fasync 三者的跨目录指路、6.2 的 my_char_dev 大结构体示例、6.3 的三问题表和生命周期纪律、第七章速查表。
  9. 素材 kobj_lookup() 一句原文写"kobj_lookup() 会返回对应驱动程序 cdev 的 kobject"，而 kobj_lookup() 实际返回的是 kobject *，本篇保留了原意但补注说明现代内核 chrdev_open 的实现更复杂。
