file_operations 是一个函数指针的集合，放着我们定义的用于操作设备的函数的指针；不定义则保留为 NULL。其中最重要的几个是 open()、read()、write()、ioctl()。

本篇讲 open/release/read/write 四个，重点在后两个——因为它们牵出驱动开发里最核心的一道坎：用户空间与内核空间不能直接互访。

本文覆盖：open/release/read/write 四个方法的原型与参数、copy_to_user/copy_from_user 为什么必须存在、volatile_memcpy 与返回值语义、驱动的读写实现与配套测试程序。

本文不覆盖：ioctl() 见《ioctl()：命令码、实现与实例》；file/inode 结构体与 file_operations 全部成员见《file、inode 与 file_operations》；阻塞/非阻塞与 poll 见 C.驱动/03-IO模型。

一、打开和关闭设备 #

1.1 open #

c
int (*open)(struct inode *, struct file *);

在操作设备前必须先调用 open 打开文件，可以做一些需要的初始化操作。如果不实现这个函数，驱动会默认设备的打开永远成功。打开成功时 open 返回 0。

1.2 release #

c
int (*release)(struct inode *, struct file *);

当设备文件被关闭时内核会调用这个操作。这也可以不实现，函数默认为 NULL。关闭设备永远成功。

方法 可否不实现 默认行为
open 可以 打开永远成功
release 可以 关闭永远成功

二、read 与 write #

这两个函数放在一起讲，因为它们是密不可分的一对——一个把设备数据交给用户，一个把用户数据送给设备。

2.1 原型 #

c
ssize_t (*read)(struct file *filp, char __user *buffer, size_t size, loff_t *p);
ssize_t (*write)(struct file *filp, const char __user *buffer, size_t count, loff_t *ppos);

2.2 read 的参数 #

参数 含义
filp 进行读取信息的目标文件
buffer 对应放置信息的缓冲区，即用户空间内存地址
size 要读取的信息长度
p 读的位置相对于文件开头的偏移。读取信息后这个指针一般都会移动，移动的值为要读取信息的长度值

2.3 write 的参数 #

参数 含义
filp 目标文件结构体指针
buffer 要写入文件的信息缓冲区，同样在用户空间
count 要写入信息的长度
ppos 当前的偏移位置，通常用来判断写文件是否越界

2.4 关键：__user 标注 #

两个 buffer 参数都有 __user 修饰符，意思是"这个指针指向用户空间"。这不是装饰，是编译器/sparse 的强制检查：

c
       用户空间                      内核空间
    ┌─────────────┐              ┌─────────────┐
    │ buffer 指向的 │   ✗ 不能直接  │   驱动代码    │
    │   用户内存    │  ◀── 解引用 ──▶│              │
    └─────────────┘              └─────────────┘
           ▲                            │
           └──────── copy_to_user ──────┘
                     copy_from_user

驱动绝不能直接 *buffer = x 或 x = *buffer。一是因为用户地址可能根本没映射（非法指针），直接解引用会 Oops；二是因为现代内核在部分架构上用户页不可由内核直接访问。必须走拷贝函数，它们内部会做地址合法性检查。

两个函数的作用分别是从设备中获取数据和发送数据给设备，应用程序中与之对应的也有 write() 和 read() 函数：

c
/* 应用层 */
len = read(fd, buf, len);     // 触发驱动的 hello_read
len = write(fd, buf, size);   // 触发驱动的 hello_write

/* 驱动层 */
static ssize_t hello_read(struct file *filep, char __user *buf, size_t len, loff_t *pos);
static ssize_t hello_write(struct file *filep, const char __user *buf, size_t len, loff_t *pos);

注意应用层与驱动层的方向是反的：应用 read 时驱动在做"把数据送出去"，应用 write 时驱动在做"把数据收进来"。

三、内核空间与用户空间的数据拷贝 #

应用程序工作在用户空间，驱动工作在内核空间，两者不能直接通信。内核里虽然有 memcpy（用法跟 C 库的一样），但不能直接用它拷用户内存。

3.1 两个拷贝函数 #

c
static inline unsigned long __must_check
copy_from_user(void *to, const void __user *from, unsigned long n);

static inline unsigned long __must_check
copy_to_user(void __user *to, const void *from, unsigned long n);

它们的核心实现都落在 volatile_memcpy 上：

c
static inline int copy_from_user(void *to, const void __user volatile *from,
                                 unsigned long n)
{
    __chk_user_ptr(from, n);
    volatile_memcpy(to, from, n);
    return 0;
}

static inline int copy_to_user(void __user volatile *to, const void *from,
                               unsigned long n)
{
    __chk_user_ptr(to, n);
    volatile_memcpy(to, from, n);
    return 0;
}

static void volatile_memcpy(volatile char *to, const volatile char *from,
                            unsigned long n)
{
    while (n--)
        *(to++) = *(from++);
}

3.2 为什么不直接用 memcpy #

既然 volatile_memcpy 就能完成拷贝功能，为什么还要封装成 copy_to_user() 和 copy_from_user()？

因为裸 memcpy 有缺陷：如果在用户层调用函数时传入的不是合法地址，而是一个不能访问或修改的地址，那样就会造成系统崩溃。

所以内核与用户态之间交互数据时必须先对数据做检测，确认数据安全才进行交互。上面两个函数就是 memcpy 的改进版——在 memcpy 功能的基础上加上了检查传入参数的功能，防止有意或无意地传入无效参数。

3.3 用法 #

参数和 memcpy 一样，但根据传参方向的不同分成了两个函数：

  • to 是相对于内核态来说的。所以 to 的意思是：从 from 指针指向的数据，将 n 个字节的数据传到 to 指针指向的数据。
  • from 也是相对于内核来说的。同理，从 from 指向的数据传 n 个字节到 to 指向的数据。

返回值：指定要读取的 n 个字节中，还剩下多少字节没有被拷贝。

注意：一般的，如果返回值不为 0，调用 copy_to_user 的函数应返回错误号 -EFAULT 表示操作出错。当然也可以自己决定。

这个返回值语义是经典易错点：成功时返回 0，失败时返回"没拷完的字节数"（正数），所以判断要写 if (copy_to_user(...)) 而不是 if (copy_to_user(...) < 0)——后者永远为假，错误会被吞掉。

四、读写实现示例 #

4.1 驱动侧 #

c
#define MAX_LEN 64
static char temp[MAX_LEN];      /* 驱动内部缓冲区 */

static ssize_t hello_read(struct file *filep, char __user *buf, size_t len, loff_t *pos)
{
    if (len > MAX_LEN)
        len = MAX_LEN;

    if (copy_to_user(buf, temp, len))
        return -EFAULT;

    return len;
}

static ssize_t hello_write(struct file *filep, const char __user *buf, size_t len, loff_t *pos)
{
    if (len > MAX_LEN)
        len = MAX_LEN;

    if (copy_from_user(temp, buf, len))
        return -EFAULT;

    printk("write %s\n", temp);
    return len;
}

两个要点：

  1. 长度必须截断。len 是用户传来的，可能远大于驱动缓冲区 temp 的容量，不截断就是缓冲区溢出。
  2. 成功时返回实际传输的字节数，不是 0。应用层的 read/write 返回值就是这个值；返回 0 会被应用层理解为 EOF。

上面示例直接用 printk("%s", temp) 打印用户送进来的字符串，这在生产驱动里是危险写法——temp 末尾没有保证 '\0'，属于格式化字符串越界读。正确做法是 temp[len] = '\0'（预留一位）或改 printk("%.*s", (int)len, temp)。

4.2 测试程序 #

c
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

char buf[] = "111232342342342";
char temp[64] = {0};

int main(void)
{
    int fd, len;

    fd = open("/dev/hello", O_RDWR);
    if (fd < 0) {
        perror("open fail \n");
        return -1;
    }

    write(fd, buf, strlen(buf));        /* → hello_write → copy_from_user */

    len = read(fd, temp, sizeof(temp)); /* → hello_read  → copy_to_user   */

    printf("len=%d,%s \n", len, temp);

    close(fd);
    return 0;
}

4.3 完整调用链 #

到这里 open、close、read、write 四个函数已经学完。把它们串起来，一次应用调用在内核里的路径是这样的（箭头方向从调用方指向被作用方）：

应用   open("/dev/hello")  ──▶  VFS  ──▶  chrdev_open  ──▶  hello_open
应用   write(fd, buf, n)   ──▶  VFS  ──▶  vfs_write    ──▶  hello_write ──▶ copy_from_user
应用   read(fd, temp, n)   ──▶  VFS  ──▶  vfs_read     ──▶  hello_read  ──▶ copy_to_user
应用   close(fd)           ──▶  VFS  ──▶  __fput       ──▶  hello_release

其中 chrdev_open 如何根据设备号找到你的 cdev 并把 f_op 换成你的 file_operations，见《cdev 与设备号》第五章。

五、四个方法速查 #

方法 原型 返回值语义 常见错误
open int (*)(struct inode *, struct file *) 0 成功，负错误码 忘记赋值 filp->private_data
release int (*)(struct inode *, struct file *) 0 成功 与 open 里申请的资源不对称释放
read ssize_t (*)(struct file *, char __user *, size_t, loff_t *) 实际读到的字节数 返回 0 被当成 EOF；未截断长度
write ssize_t (*)(struct file *, const char __user *, size_t, loff_t *) 实际写入的字节数 用 < 0 判断 copy_from_user 返回值
