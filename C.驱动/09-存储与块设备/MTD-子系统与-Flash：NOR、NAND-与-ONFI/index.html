边界一句话：磁盘是「覆盖写」，Flash 是「擦除后才能写，写只能把 1 变 0」。整篇的技术分歧都从这句长出来。

内核版本：素材实测环境为 linux 5.2.8 + busybox 1.25.0 + u-boot 2016.05（Mini2440 / S3C2440，NAND 为 K9F2G08U0C 与 K9F1G089U0B，NOR 为 SST39VF1601）。涉及 3.x/4.x/5.x 差异的地方会单独标出，拿不准的写「未验证」。

一、Flash 与磁盘的本质差别 #

先把三件事分清，后面所有代码都是它们的推论。

  • 写只能是 1→0。编程（Program）操作只能把比特从 1 变 0，想从 0 变 1 只能整块擦除。所以你在 Flash 上改一个字节，背后是「读整块 → 改内存 → 擦块 → 写回」。
  • 擦除的最小单位是块，不是字节。NOR 常见 4KB/64KB 扇区，NAND 是几十到几百 KB 的擦除块。块内的数据要么一起活，要么一起死。
  • 出厂就带坏块。NAND 出厂允许有坏块，且使用中还会新增。磁盘的坏道是故障，NAND 的坏块是规格的一部分。

由此推出驱动必须处理的三件事，也正好是本篇的三条主线：

Flash 特性 驱动层的应对 本篇章节
写前必须擦 把「擦-写」两段命令序列封装成 _erase / _write 六、七、十一、十六
位翻转 ECC 计算 + 纠错 + 阈值上报 十三
坏块与寿命 坏块表、坏块标记、磨损均衡、UBI 十四、十五、十七

再看一层：磁盘控制器把「扇区」这个抽象做完了，文件系统只管提交 bio。Flash 没有控制器帮你做这层抽象，它裸露的是命令、地址周期、状态位。所以 Linux 在块层之下又插了一层 MTD，专门管这些裸露的东西。

二、NOR 与 NAND 的物理特性对比 #

这两种器件不是同一类东西的两种封装，连访问模型都不一样。NOR 可以像内存一样随机读（XIP 的基础），NAND 必须整页读出再在页内寻址。

维度 NOR Flash NAND Flash
访问模型 地址线直接寻址，可随机读单字节，支持 XIP 命令 + 地址周期，按页读，页内串行输出
读最小单位 1 字节 1 页（512B~16KB）
写最小单位 1 字节（NOR 可单字节编程） 1 页
擦除最小单位 扇区 4KB / 块 64KB（SST39VF1601：2Kword=4KB 扇区、32Kword=64KB 块） 128KB（K9F1G089U0B）
接口信号 地址线 + 数据线 + 控制线，并行 8/16 位复用 IO + CLE/ALE/CE/RE/WE/RB，共 15 根（必需 13 根）
识别方式 CFI 查询表 / JEDEC ID 表 读 ID（命令 0x90）查表，或 ONFI 参数页
坏块 一般没有坏块概念，按整片可靠 出厂即有坏块，需坏块表管理
常见容量 1~64Mb，2MB/4MB 常见 1Gb~1Tb，128MB 起
典型文件系统 jffs2（可直接跑在 mtdblock 上） YAFFS2 / UBI + UBIFS

容量上的直觉：Mini2440 板载 NOR 只有 2MB，而要装整个根文件系统的是 128MB 的 NAND。这不是巧合，是同价位下 NAND 密度高一个数量级的结果。

再补一层 NAND 的单元工艺，它直接决定 ECC 强度要求：

类型 每单元位数 擦写寿命（原文数据） 备注
SLC 1 bit 约 9 万~10 万次 最耐用，成本高
MLC 2 bit 约 3000~10000 次 需要更强 ECC
TLC 3 bit 约 500~1000 次 速度与寿命都弱
QLC 4 bit 约 1000 次 密度更高，成本更低

原文的结论是 SLC > MLC > TLC。这个排序只在「寿命」这一维成立，选型时要按容量/成本/温度一起算。上面这些寿命数字来自二手资料汇总，不是实测，按「量级参考」用，不要写进规格书。

三、MTD 子系统是什么：为什么不用块设备层 #

先回想块设备驱动的流程：register_blkdev 注册主设备号 → alloc_disk 申请 gendisk → blk_mq_init_sq_queue 初始化请求队列 → 填 gendisk 成员 → add_disk 注册。

这套流程对每种 Flash 都要重抄一遍，而不同 Flash 之间真正不同的只有内存模型（页大小、块大小、每块页数、OOB 大小）和时序参数。那能不能把「相同的部分」抽出来复用、只让驱动填「不同的部分」？MTD 干的就是这件事。

MTD 全称 Memory Technology Drivers（原文标题这么写，实际内核里常写作 Memory Technology Device），是访问 ROM、Flash 这类存储器的子系统，在硬件和上层之间提供抽象接口。

它解决的问题清单：

  • 统一暴露 read / write / erase 三个语义，屏蔽「写前必须擦」的差异。
  • 把擦除块、OOB、坏块、ECC 这些概念收进 mtd_info，上层不用各自实现。
  • 同时提供字符设备（/dev/mtd0，支持 ioctl 擦除）和块设备（/dev/mtdblock0，给只认块设备的文件系统用）。
  • 分区在 MTD 内部做，mtd_part 让每个分区看起来都是一个独立的 MTD 设备。

代价是 mtdblock 这层「块设备外壳」并不真正理解 Flash 的擦除语义（第七节会讲 mtdblock 的读改写缓冲），所以 NAND 上跑 FAT/ext4 这类文件系统会面临严重的写放大。这也是后来 UBI 出现的原因（第十七节）。

四、MTD 的分层结构 #

MTD 框架从上到下分四层。

层 文件 职责
设备节点 /dev/mtdN、/dev/mtdNro（字符，主设备号 90）、/dev/mtdblockN（块，主设备号 31） 用户态入口，由 mdev/udev 根据 /sys/class/mtd 自动创建
MTD 设备层 mtdchar.c、mtdblock.c、mtd_blkdevs.c 把原始设备包装成字符设备与块设备；块设备的 gendisk、请求队列都由内核代劳
MTD 原始设备层 mtdcore.c、mtdpart.c mtd_info 的注册/注销、mtd_idr 管理、分区切分、notifier 机制
Flash 驱动层 drivers/mtd/nand/raw/、drivers/mtd/chips/、drivers/mtd/maps/ 真正和硬件说话：发命令、等就绪、搬数据、算 ECC

Flash 驱动层的两种形态差别很大：

  • NAND：drivers/mtd/nand/raw/nand_base.c 提供通用实现，芯片级驱动只填 nand_chip 里的硬件钩子。
  • NOR：内核已实现 CFI、JEDEC 等接口标准的通用驱动，芯片级驱动更薄——填一个 map_info，然后 do_map_probe 让内核自己去认。

注册链路上还有个 notifier 机制值得记住：add_mtd_device() 里遍历 mtd_notifiers 链表逐个 not->add(mtd)，mtdblock 和 mtdchar 就是挂在这个链表上的「用户」。这意味着 MTD 原始设备的注册和块设备节点的创建是解耦的，谁先加载都能对上。

五、mtd_info 与 mtd_info 的操作 #

mtd_info 定义在 include/linux/mtd/mtd.h，代表一个原始的 MTD 设备，或者多分区设备里的一个分区。所有 mtd_info 都挂在 mtd_idr 这棵 radix 树上（老内核用 mtd_table[] 数组，4.x 后统一改成 IDR）。

完整定义有四十多个字段，直接整段抄进博客没有阅读价值。这里按「字段分类」给结构，完整清单查头文件：

分组 代表性字段 作用
设备属性 type、flags、orig_flags、size、name、index 类型、标志、容量、名字、IDR 索引
几何参数 erasesize、writesize、writebufsize、oobsize、oobavail 擦除/写的最小单位与 OOB 容量
位偏移与掩码 erasesize_shift/_mask、writesize_shift/_mask 注册时由 ffs() 算出，省掉运行时除法
ECC 信息 ecc_step_size、ecc_strength、bitflip_threshold、ecc_stats、subpage_sft 纠错能力与统计
布局描述 ooblayout、pairing、numeraseregions、eraseregions OOB 摆放、MLC 配对、变长擦除区
操作集 _erase、_read、_write、_read_oob、_write_oob 等 驱动要实现的钩子
生命周期与引用 priv、owner、dev、usecount、_get_device/_put_device、reboot_notifier 设备模型挂载点与引用计数

单看「你该关心的点」这一列：

字段 含义 你该关心的点

操作函数指针全部带下划线前缀（_read、_write、_erase……），注释写得很明白：不要直接调用这些指针，走 mtd_read() / mtd_write() / mtd_erase() 这层包装。包装函数负责加锁、统计 ECC 错误、检查 MTD_WRITEABLE、把 -EUCLEAN 转成上层的位翻转计数。

核心操作集：

c
int (*_erase)(struct mtd_info *mtd, struct erase_info *instr);
int (*_read)(struct mtd_info *mtd, loff_t from, size_t len,
             size_t *retlen, u_char *buf);
int (*_write)(struct mtd_info *mtd, loff_t to, size_t len,
              size_t *retlen, const u_char *buf);
int (*_read_oob)(struct mtd_info *mtd, loff_t from, struct mtd_oob_ops *ops);
int (*_write_oob)(struct mtd_info *mtd, loff_t to, struct mtd_oob_ops *ops);
int (*_block_isbad)(struct mtd_info *mtd, loff_t ofs);
int (*_block_markbad)(struct mtd_info *mtd, loff_t ofs);
int (*_max_bad_blocks)(struct mtd_info *mtd, loff_t ofs, size_t len);
int (*_is_locked)(struct mtd_info *mtd, loff_t ofs, uint64_t len);
int (*_lock)(struct mtd_info *mtd, loff_t ofs, uint64_t len);
int (*_unlock)(struct mtd_info *mtd, loff_t ofs, uint64_t len);

除了这几个，结构体里还有一组 OTP（一次性可编程区）相关指针：_get_fact_prot_info、_read_fact_prot_reg、_get_user_prot_info、_read_user_prot_reg、_write_user_prot_reg、_lock_user_prot_reg，分别对应出厂保护区与用户保护区的信息查询和读写。_get_device / _put_device 是给 UBI 这类「聪明驱动」自己做引用计数用的。

还要记住一个硬性约束，add_mtd_device() 里做了校验：_read/_write 与 _read_oob/_write_oob 只能实现其中一对，两对同时给直接返回 -EINVAL。

分区的结构体是 mtd_part，它把 mtd_info 嵌在第一个成员：

c
struct mtd_part {
        struct mtd_info mtd;     /* 分区自己的 mtd_info */
        struct mtd_info *parent; /* 主分区（整片 Flash 或上一级分区） */
        uint64_t offset;         /* 相对主分区的偏移 */
        struct list_head list;   /* 挂到 mtd_partitions 链表 */
};

分区自己的读写函数并不是另写一套，而是包装：part_read → 把 offset 加到地址上 → 调 parent->_read。所以分区在 MTD 里是「偏移的视图」，不是独立设备。

描述分区表的是 mtd_partition：

c
struct mtd_partition {
        const char *name;          /* 分区名 */
        const char *const *types;  /* 子分区解析器名称数组 */
        uint64_t size;             /* MTDPART_SIZ_FULL 表示到结尾 */
        uint64_t offset;           /* MTDPART_OFS_APPEND / NXTBLK / RETAIN */
        uint32_t mask_flags;       /* 从主设备 flags 里屏蔽掉的位 */
        struct device_node *of_node;
};

mask_flags 加 MTD_WRITEABLE 就是把分区强制只读，这比在文件系统层做 ACL 靠谱得多。

六、MTD 设备的注册 #

三组 API，按分区分化程度选：

场景 注册 注销
整片一个设备 add_mtd_device(mtd) del_mtd_device(mtd)
有显式分区表 add_mtd_partitions(master, parts, nbparts) del_mtd_partitions(master)
驱动常规入口 mtd_device_register(master, parts, nr_parts) mtd_device_unregister(mtd)

mtd_device_register 是个宏：

c
#define mtd_device_register(master, parts, nr_parts)    \
        mtd_device_parse_register(master, NULL, NULL, parts, nr_parts)

真正干活的是 mtd_device_parse_register()（drivers/mtd/mtdcore.c），逻辑就三步：

  1. 若开了 CONFIG_MTD_PARTITIONED_MASTER，先把整片注册成一个 MTD 设备。
  2. parse_mtd_partitions() 让各分区解析器去探（cmdlinepart、RedBoot、ofpart 等）。
  3. 解析不出就用传进来的 parts/nr_parts 调 add_mtd_partitions()；再不行就整片注册。

add_mtd_device() 里的关键动作，按执行顺序：

  • 校验：mtd->dev.type 已设置说明重复注册，返回 -EEXIST；writesize == 0 直接 BUG_ON；读写与 OOB 读写成对冲突返回 -EINVAL；没有 erasesize 或 _erase 又没标 MTD_NO_ERASE 返回 -EINVAL。
  • idr_alloc(&mtd_idr, mtd, 0, 0, GFP_KERNEL) 分配索引 mtd->index。
  • 算 erasesize_shift / writesize_shift（ffs(x) - 1，非 2 的幂置 0）以及对应的 mask。
  • 对上电即锁的芯片（MTD_WRITEABLE | MTD_POWERUP_LOCK）调 mtd_unlock() 解锁。
  • 填 mtd->dev.type = &mtd_devtype、class = &mtd_class、devt = MTD_DEVT(i)、dev_set_name("mtd%d")，然后 device_register()。
  • mtd_nvmem_add() 挂 nvmem 提供者；debugfs 目录。
  • device_create(..., MTD_DEVT(i) + 1, ..., "mtd%dro", i) 创建只读节点。
  • 遍历 mtd_notifiers，not->add(mtd) —— 块设备节点在这一步被造出来。

设备号宏说明了「为什么每个分区占两个次设备号」：

c
#define MTD_DEVT(index)  MKDEV(MTD_CHAR_MAJOR, (index) * 2)

主设备号 90，mtd0 是次设备号 0，mtd0ro 是 1，mtd1 是 2，依此类推。

add_mtd_partitions() 遍历分区表，对每一项调 allocate_partition() 分配 mtd_part，再 add_mtd_device(&slave->mtd)，最后 parse_mtd_partitions() 找子分区。allocate_partition() 里有几处容易踩：

  • 分区起止地址不按擦除块对齐时，静默清掉 MTD_WRITEABLE 并打印警告 —— 分区别随手写小数。
  • MTDPART_OFS_NXTBLK 会把 offset 向上取整到 wr_alignment（有 MTD_NO_ERASE 时是 writesize，否则是 erasesize）。
  • MTDPART_OFS_RETAIN 表示「尽量占满，给后面留出 size 那么长」。
  • 分区越界会被截断并警告，完全越界则 offset/size 清零但仍注册以保持编号顺序。
  • 有 _block_isbad 时会遍历分区内的块统计 ecc_stats.badblocks / bbtblocks。

七、NOR Flash 的读写时序 #

NOR 的「时序」不是 NAND 那种命令-地址周期，而是三件事：解锁序列、状态轮询、总线位宽错接。

以 SST39VF1601（2MB，16 位模式）为例。读软件 ID 的序列：向 0x5555 写 0xAA，向 0x2AAA 写 0x55，向 0x5555 写 0x90，然后从 0x0000 读到厂家 ID 0x00BF，从 0x0001 读到设备 ID 0x234B。

板级上真正要发出去的地址是左移一位的：

text
解锁：写 0xAAAA ← 0xAA，写 0x5554 ← 0x55
命令：写 0xAAAA ← 0x90
读  ：读 0x0000 → 厂家 ID，读 0x0001 → 设备 ID

原因在接线：S3C2440 的 A1~A20 接 SST39VF1601 的 A0~A19。S3C2440 每个地址对应 1 字节，而 16 位模式下 Flash 每个地址对应 1 个 half-word，必须错一位才对齐。这样处理器发地址的最低位 A0 就被屏蔽掉了。ARM 处理器一般有内部寄存器声明外部 Flash 位宽，支持软件错位的芯片在硬件上可以不错线，等效效果一致。

其余三种操作的状态语义：

  • 读：上电即 Reading Array Data 状态，正常读与读 SRAM 无异。进了软件 ID 模式必须发退出命令才回到读状态。
  • 擦除：支持扇区擦除（4KB）、块擦除（64KB）、整片擦除三种，命令序列发送后自动回到读状态。
  • 编程：必须先擦除。编程只能把 1 写成 0，擦除把整块写成 1。

16 位模式下写命令要用 writew 而不是 writeb，用错字节写会把命令拆成两半发出去，芯片不认。这是 NOR 驱动最常见的第一个坑。

内核对 NOR 的「时序」控制体现在两层：

第一层是轮询。编程与擦除发出命令后不会立刻完成，必须先查状态。CFI 器件先发 Read Status Register 命令（AMD 命令集是往任意地址写 0x70），再读同一地址得到状态字：bit7 是 data# polling，命令完成后与写入数据的 bit7 一致；bit5 是 timeout 位，置位表示内部操作超时。内核各 cfi_cmdset_000X.c 里的 chip->mutex + xip_udelay() 循环（Intel 系列用 wait_for_completion 等中断）就是在等这两位。

第二层是虚拟地址与物理地址的映射。map_info 里 virt 是 ioremap 后的内核虚拟地址，phys 是芯片在 CPU 地址空间里的物理起点，size 是映射窗口长度。size 必须不小于芯片实际容量，否则超出的那一段读不到（mtd_do_chip_probe() 里有 mtd->size > map->size 时把可见容量缩小的告警）。

还有一条约束在 map_info 里：#define NO_XIP (-1UL)。phys 设成真实物理地址才谈得上 XIP；设成 NO_XIP 就表示这片映射不提供 XIP，_point/_unpoint 会返回 -EOPNOTSUPP。

八、CFI 与 JEDEC：NOR 的识别 #

NOR 的识别有两条路，内核两条都实现了。

标准 做法 优点 缺点
JEDEC 读厂家 ID + 设备 ID，去 jedec_table[] 里查表 老芯片都支持 表里没有就得手改内核，容量/位宽全靠表里的静态数据
CFI 发 CFI Query Entry 命令进入查询模式，从固定地址读结构体 阵列结构、电气与时序参数、支持的功能全都能读到 老芯片不支持

CFI 的价值在于换料不改软件：新型号擦除时间减半，软件从 CFI 读到新参数即可。

JEDEC 表项长这样（drivers/mtd/chips/jedec_probe.c）：

c
{
        .mfr_id     = CFI_MFR_SST,          /* 0xBF */
        .dev_id     = SST39VF1601,          /* 0x234B */
        .name       = "SST 39VF1601",
        .devtypes   = CFI_DEVICETYPE_X16,
        .uaddr      = MTD_UADDR_0xAAAA_0x5555,
        .dev_size   = SIZE_2MiB,
        .cmd_set    = P_ID_AMD_STD,         /* 0x0002 */
        .nr_regions = 2,
        .regions    = {
                ERASEINFO(0x1000, 256),
                ERASEINFO(0x1000, 256)
        }
}

uaddr 是解锁地址对，regions 是擦除块分布（从低地址到高地址），nr_regions 是分布种类数而不是块总数。表里没有你的芯片，就得自己加一项 —— 这也是 u-boot 时代常见的手工活。

CFI 侧靠的是 genprobe 拿到 cfi_private 和 cfi_ident 结构体，里面 P_ID（主命令集 ID）决定用哪套命令时序实现：

P_ID 值 命令集 内核实现
P_ID_INTEL_EXT / P_ID_INTEL_STD / P_ID_INTEL_PERFORMANCE Intel/Sharp cfi_cmdset_0001.c
P_ID_AMD_STD / P_ID_SST_OLD / P_ID_WINBOND AMD/Fujitsu/Spansion cfi_cmdset_0002.c
P_ID_ST_ADV ST Advanced cfi_cmdset_0020.c
其它 未知 cfi_cmdset_unknown.c

SST39VF1601 走的是 P_ID_AMD_STD 分支，对应 CONFIG_MTD_CFI_AMDSTD。这个宏没开，CFI 探测就会掉到最后打印「No supported Vendor Command Set found」。

识别流程的入口是 do_map_probe(name, map)（drivers/mtd/chips/chipreg.c）：按名字在 chip_drvs_list 链表里找 mtd_chip_driver，找不到就 request_module() 试着加载模块，找到就调 drv->probe(map)。

physmap 的探测顺序由这个数组决定：

c
static const char * const rom_probe_types[] = {
        "cfi_probe", "jedec_probe", "qinfo_probe", "map_rom",
};

CFI 优先。因为 CFI 能成功，就不会再走 JEDEC 那条查表的路。实测日志里 CFI 探测成功时只打印 Found 1 x16 devices ... number of CFI chips: 1；如果 CFI 驱动没编进去，才会看到 JEDEC PROBE: ID bf 234b 这样的输出。

cfi_probe() 只是个转发，实活由 mtd_do_chip_probe() 干：先 genprobe_ident_chips() 发命令进 CFI 模式拿芯片结构，再 check_cmd_set(map, 1) 按主命令集建 mtd_info，失败再试次命令集。genprobe_ident_chips() 里还对 chipshift 做了 interleave 修正——cfi_interleave_is_2() 加 1 位、is_4() 加 2 位、is_8() 加 3 位，BUG() 兜底其它情况。

九、NOR 驱动实例 #

内核自带的 physmap 是最短路径。项目在 drivers/mtd/maps/physmap-core.c，CONFIG_MTD_PHYSMAP_COMPAT 打开时会自己注册一个 platform 设备：

c
static struct resource physmap_flash_resource = {
        .start  = CONFIG_MTD_PHYSMAP_START,   /* Flash 物理基址 */
        .end    = CONFIG_MTD_PHYSMAP_START + CONFIG_MTD_PHYSMAP_LEN - 1,
        .flags  = IORESOURCE_MEM,
};

三个宏对应物理基址、映射长度、位宽（CONFIG_MTD_PHYSMAP_BANKWIDTH，16 位写 2）。

physmap_flash_probe() 的骨架，按执行顺序：

  1. devm_kzalloc 分配 physmap_flash_info。
  2. 数 IORESOURCE_MEM 资源个数得到 info->nmaps，据此分配 info->maps[] 与 info->mtds[]。
  3. 逐个数：devm_ioremap_resource() 填 maps[i].virt，填 name、phys、size（由 get_bitmask_order() 算窗口大小），map_priv_1 存 platform 设备指针。
  4. 调 simple_map_init(&info->maps[i])。这个宏只做一件事——BUG_ON(!map_bankwidth_supported((map)->bankwidth))，即校验位宽是否落在编译期允许的集合（CONFIG_MTD_MAP_BANK_WIDTH_{1,2,4,8,16,32}）里。physmap 的写法是：开了 CONFIG_MTD_COMPLEX_MAPPINGS 时只在 maps[i].read 为空时才调它（有自定义 map 钩子就不覆盖），否则无条件调。真正的 read/write/copy_from/copy_to 默认实现来自 map.h 里的内联版本，不需要你写。
  5. 用 probe_type 或遍历 rom_probe_types[] 调 do_map_probe()，成功的存进 mtds[i]。
  6. nmaps == 1 时 cmtd = mtds[0]；多个芯片用 mtd_concat_create() 拼成一个连续 MTD。
  7. mtd_device_parse_register(cmtd, part_types, NULL, parts, nparts) 完成注册。

do_map_probe() 本身只有十几行，但它决定了整条识别链：

c
struct mtd_info *do_map_probe(const char *name, struct map_info *map)
{
        struct mtd_chip_driver *drv;
        struct mtd_info *ret;

        drv = get_mtd_chip_driver(name);
        if (!drv && !request_module("%s", name))
                drv = get_mtd_chip_driver(name);
        if (!drv)
                return NULL;

        ret = drv->probe(map);
        module_put(drv->module);
        return ret;
}

get_mtd_chip_driver() 遍历 chip_drvs_list，比较 name，找到后 try_module_get() 加引用。往链表里加成员的是 register_mtd_chip_driver()，cfi_probe.c、jedec_probe.c、map_ram.c、map_rom.c 的入口函数都调它。

自己写一个 NOR 驱动时，比 NAND 简单得多：不需要实现读写函数，因为 NOR 可像内存一样访问，内核 simple_map_init 给的默认实现就够用。步骤就五步：

c
/* 1. 分配 */
s3c_map = kzalloc(sizeof(struct map_info), GFP_KERNEL);

/* 2. 填 map_info 并映射 */
s3c_map->name      = "nor_flash";
s3c_map->phys      = 0x0;
s3c_map->size      = 0x1000000;   /* 必须 >= 芯片容量 */
s3c_map->bankwidth = 2;           /* 16 位 */
s3c_map->virt      = ioremap(s3c_map->phys, s3c_map->size);
simple_map_init(s3c_map);

/* 3. 探测 */
for (; s3c_mtd == NULL && *probe_type != NULL; probe_type++)
        s3c_mtd = do_map_probe(*probe_type, s3c_map);
if (!s3c_mtd)
        goto err_out;
s3c_mtd->owner = THIS_MODULE;

/* 4. 注册 */
mtd_device_parse_register(s3c_mtd, part_types, NULL,
                          s3c_nor_part, ARRAY_SIZE(s3c_nor_part));

rom_probe_types[] 写 {"cfi_probe", "jedec_probe", NULL} 就能覆盖两种识别路径。分区表随便切，实测切成 bootloader(0x40000) + root(剩余) 两个分区，得到 mtd0/mtd0ro/mtd1/mtd1ro 四个字符节点和 mtdblock0/mtdblock1 两个块节点。

挂 jffs2 前必须先格式化，且格式化走字符设备：

bash
flash_eraseall -j /dev/mtd1
mount -t jffs2 /dev/mtdblock1 /mnt

-j 表示写入 jffs2 cleanmarker。用字符设备的原因很实在：擦除靠 ioctl 实现，块设备不支持 ioctl，只有字符设备支持。

配套的内核配置别忘：File systems → Miscellaneous filesystems → Journaling Flash File System v2 (JFFS2) support 要打开，busybox 里的 flash_eraseall 要编进去。最终验证一条就够 —— 往挂载点写个文件，重新挂载后能读回来：

text
[root@zy:/mnt]# touch test && echo "111" > test && cat test
111

ls -l 里显示的 -rw-r--r-- 1 0 0 4 ... test 是 4 字节，与 111 加换行对上，说明数据真的落到了 mtdblock1 上。

十、NAND Flash 的组织：页、块、plane #

ONFI 把 NAND 的层级定死为：Device → LUN(Die/Target) → Plane → Block → Page → Cell。

层级 定义 是否必有
Device 一颗封装好的芯片，含 1 个或多个 LUN 必有
LUN / Die / Target 接收并执行 Flash 命令的基本单元，含 1 个或多个 plane 大容量（8Gb 以上）才有，否则视为 1
Plane 含多个 Block，部分支持 plane 内并行操作 同上，否则视为 1
Block 擦除的最小单元 必有
Page 编程与读的最小单元 必有
Cell 浮栅晶体管，存 1 bit 或多 bit —

三个术语是一回事：LUN、Die、Target 在 ONFI 和内核对口代码里是同义词。原文还有一处提醒：口语里的「chip」有时指整颗封装，有时指内部的 LUN，读手册时看清上下文 —— 三星 K9WAG08U1A（2GB）内部装了 2 颗 K9K8G08U0A（各 1GB），而 K9K8G08U0A 内部又含 4 个 2Gb 的 plane。

读 ID 是认识一颗 NAND 的第一步。发 0x90，再发地址 0x00，连读 5 个字节。K9F2G08U0C 的 5 个字节是 0xEC 0xDA 0x10 0x15 0x44：第 1 字节厂家 ID（0xEC = Samsung），第 2 字节设备 ID，后三字节是内部几何参数。逐字节解码：

字节 值 字段 含义
3 0x10 = 0001 0000b Internal Chip Number 1，内部 1 个 chip
3 同上 bit1:0 = 00 Cell Type 2 Level Cell，即 SLC，1 bit/cell
3 同上 bit3:2 = 00 Simultaneously Programmed Pages 1
3 同上 bit4 Interleave Program Between multiple chips 不支持
3 同上 bit5 Cache Program 不支持
4 0x15 = 0001 0101b Page Size（bit1:0 = 01） 2KB
4 同上 bit3:2 = 01 Block Size 128KB
4 同上 bit5 = 0 Redundant Area Size 16 字节 / 512 字节
4 同上 bit6 = 1 Organization x8（8 位数据线）
4 同上 bit7 = 0 Serial Access Minimum 50ns/30ns
5 0x44 = 0100 0100b Plane Number（bit1:0 = 00） 2
5 同上 bit3:2 = 01、bit5:3 = 000（合成 3 位值 001） Plane Size 1Gb = 128MB

合起来：2 个 plane × 1Gb = 每 chip 256MB。

冗余区按 512 字节粒度算：每页 2KB 就有 2KB/512 × 16 = 64 字节 OOB。这个 64 字节决定了 ECC 能放多强、坏块标记放哪、YAFFS2 的 tag 怎么摆——后面几节反复用到它。

手边的板子换过一颗，实测 ID 是 0xEC 0xF1 0x00 0x95 0x40，即 K9F1G089U0B：1 chip、1 plane、128MB、页 2KB、块 128KB。位宽没变、页大小没变，只是 plane 数和容量不同 —— 这正好说明为什么内核要靠 ID 查表而不是写死。

在 u-boot 里手工读 ID 的办法（直接戳寄存器）：

text
SMDK2440 # mw.l 0x4e000004 1        /* NFCONT：使能 + 片选 */
SMDK2440 # mw.b 0x4e000008 0x90     /* NFCMMD：发 0x90 */
SMDK2440 # mw.b 0x4e00000c 0x00     /* NFADDR：发 0x00 */
SMDK2440 # md.b 0x4e000010 1        /* NFDATA：读 1 字节 */

mw/md 的 .b/.w/.l 后缀就是 1/2/4 字节，别写反成 mw.l 0x4e000008 0x90，那样会往命令寄存器写一个 32 位值。

十一、NAND 的命令序列 #

NAND 是「命令 + 地址 + 数据」三段式，命令走 CLE 拉高时的那一拍，地址走 ALE 拉高时的那一拍，数据走两者都低的拍。内核里这个动作的落点是 chip->legacy.cmd_ctrl(chip, cmd, ctrl)，ctrl 上的 NAND_CLE / NAND_ALE 位区分当前是命令还是地址。S3C2440 的实现就两行：

c
static void s3c2440_nand_hwcontrol(struct nand_chip *chip, int cmd,
                                   unsigned int ctrl)
{
        struct s3c2410_nand_info *info = ...;

        if (cmd == NAND_CMD_NONE)
                return;

        if (ctrl & NAND_CLE)
                writeb(cmd, info->regs + S3C2440_NFCMD);   /* 写命令寄存器 */
        else
                writeb(cmd, info->regs + S3C2440_NFADDR);  /* 写地址寄存器 */
}

常用命令码（include/linux/mtd/rawnand.h）：

命令码 宏 作用
0x00 NAND_CMD_READ0 读页（页内起始列地址 0）
0x01 NAND_CMD_READ1 读页后半（小页器件用）
0x50 NAND_CMD_READOOB 读 spare area
0x30 NAND_CMD_READSTART 大页读的第二段命令
0x80 NAND_CMD_SEQIN 页编程序列输入
0x10 NAND_CMD_PAGEPROG 页编程执行
0x85 NAND_CMD_CACHEDPROG 缓存编程
0x60 NAND_CMD_ERASE1 块擦除第一段
0xD0 NAND_CMD_ERASE2 块擦除执行
0x70 NAND_CMD_STATUS 读状态
0x90 NAND_CMD_READID 读 ID
0xE0 NAND_CMD_PARAM 读 ONFI 参数页
0xFF NAND_CMD_RESET 复位
0xEC NAND_CMD_READONFI_PARAM 读 ONFI 参数页（部分器件用）

擦除一整块的命令流：

text
0x60 → A12~A19 → A20~A27 → A28~…（行地址，3 周期或 5 周期视容量）
     → 0xD0
     → 轮询 RB 或 0x70 读状态直到 bit6（RDY）=1、bit0（FAIL）=0

页编程的命令流：

text
0x80 → 列地址 A0~A7 → A8~A11 → 行地址 A12~A19 → A20~A27
     → 数据（writesize + oobsize 字节）
     → 0x10 → 等 RB 就绪 → 0x70 读状态

页读的命令流（大页）：

text
0x00 → 列地址 → 行地址 → 0x30 → 等 RB 就绪 → 连续读出页数据与 OOB

三个「等就绪」的实现方式：chip->legacy.dev_ready() 读硬件 RB 引脚（S3C2440 是读 NFSTAT bit0，0 忙 1 就绪），或者没有 RB 线时发 0x70 读状态字节。dev_ready 为 NULL 时内核回退到 0x70 轮询。

状态字节的三位要记清：bit6 = RDY（1 就绪/0 忙）、bit0 = FAIL（1 失败）、bit5 = READY（部分器件复用作 Cache Program 的忙标志）。判失败必须同时看 bit6 与 bit0，只看 bit0 会在擦写进行中误判。

页地址宽度决定命令流分几段发：

芯片容量 行地址（页号）周期 内核对口
小页、≤ 32MB 2 周期（A12~A27） chip->options & NAND_ROW_ADDR_3 未置位
大页、> 32MB 3 周期（A12~A28，A28 通过 0x00 命令的 bit0 复用） nand_detect() 里 chip->chip_shift - chip->page_shift > 16 时置 NAND_ROW_ADDR_3

这条判断就写在 nand_detect() 里：

c
if (chip->chip_shift - chip->page_shift > 16)
        chip->options |= NAND_ROW_ADDR_3;

128MB 的 K9F1G089U0B：chip_shift = 27、page_shift = 11，差值 16，不置位 → 2 周期行地址。256MB 的 K9F2G08U0C：chip_shift = 28，差值 17 → 置位，走 3 周期。换大容量芯片时驱动忘了这条，表现是「地址高位被截断，写到后半片就乱」。

小页器件读 OOB 用 0x50 命令而不是 0x00；大页器件读 OOB 是 0x00 + 列地址越过 data 区（writesize 开始处）再 0x30。两者别混。

十二、ONFI 标准：参数页与扩展 #

Raw NAND 早期各厂商自由设计，尺寸不统一、结构差异大、命令不通用，客户很难受。2006 年 Hynix、Intel、Micron、Phison、Sony、ST 联合制定 Open NAND Flash Interface，2006 年 12 月 ONFI 1.0 发布，此后绝大多数 Raw NAND 按它做，至少在驱动代码层面统一了。

先分两大类：Serial NAND（SPI 接口，单独一套子系统）和 Raw NAND（并行接口，本篇讲这个）。ONFI 只管 Raw NAND。

ONFI 定义的可选维度：数据线宽度 x8 / x16；数据采集模式 SDR / DDR；接口命令标准（非标 / ONFI）。封装从 TSOP48、LGA52 到 BGA63/100/132/152/272/316，嵌入式最常用 TSOP-48 —— 容量 1~32Gb 够用，PCB 也好画。

x8 器件必需信号线 13 根，CE# 与 RB# 可以省。板级设计时 RB 省掉就得靠 0x70 读状态轮询，慢一点但省一根线。

ONFI 1.0 的命令集分强制（M）与可选（O）：强制项里最常用的是 Read（读页）、Page Program、Block Erase、Read Status 四条。另有两条值得单独记：

  • Read Status：拿命令执行结果。
  • Read Parameter Page：读芯片出厂信息（内存结构、特性、时序、行为参数），结构由 ONFI 规定。驱动拿这张表就能通用，不用为每颗芯片改代码。

三个要点：

  1. 参数页有 3 份。器件内部有 3 份冗余副本，每份 256 字节，任一份校验通过即可用；三份都坏说明参数页损坏，只能靠 ID 表兜底。
  2. 要校验。crc16 覆盖范围是前 254 字节（不含自身 2 字节）。内核 nand_onfi_params 的字段注释写得比这张表细，以上按公开 ONFI 规格整理，个别偏移在 3.x/4.x 头文件里因版本合并有过调整，落地时以手上的 include/linux/mtd/onfi.h 为准。
  3. 厂商 fixup。nand_manufacturer_ops::fixup_onfi_param_page() 是给「参数页填错但芯片能跑」的器件留的后门，在 CRC 校验通过之后调用。

内核读参数页的动作序列（nand_onfi_detect()）：nand_read_param_page_op(chip, 0, NULL, 0) 发 0xE0 命令 → 读 256 字节 → 检查 signature 是否等于 "ONFI" → onfi_crc16() 校验 → 填 chip->parameters.onfi。失败则把偏移加 256 重试另外两份，三份都失败返回 0（表示「不是 ONFI 器件」，交给 JEDEC 那条路），而不是返回错误。

bitflips 与 model 这两个字段在实战里最有用：前者是主控建议的 ECC 强度，后者是型号字符串，mtd->name 在没有显式命名时就取它（nand_detect() 里 if (!mtd->name) mtd->name = chip->parameters.model;）。

内核读参数页的路径：nand_detect() 里 ID 表没填 pagesize 时，先 nand_onfi_detect()，再 nand_jedec_detect()。前者成功就直接 goto ident_done，后者成功同理。两条都不成，才去走厂商 ID 解码（nand_manufacturer_ops::detect，三星是 samsung_nand_decode_id() → nand_decode_ext_id() 解析 id.data[2] / id.data[3] 得到 cell type、pagesize、oobsize、blocksize）。

注意一个反直觉的点：K9F2G08U0C 这颗芯片不支持 ONFI。把它的命令表和 ONFI 1.0 强制项一比就能看出来。所以老芯片靠 ID 表 + 扩展 ID 解码，新芯片靠参数页，两条路内核都得留着。

ONFI 的扩展还有一层——时序模式（Timing Mode）。ONFI 2.x 定义了 mode 0~5 六个时序档，越高的档位数据率越高（NV-DDR 下最高到 mode 5）。chip->onfi_timing_mode_default 记录「复位后默认进入哪一档」，由 nand_detect() 里 onfi_fill_data_interface(chip, NAND_SDR_IFACE, 0) 初始化为 mode 0。控制器驱动想跑到高档位，要在 nand_controller_ops::setup_data_interface() 里按参数页的 timing_mode_support 位图协商，协商成功才真正提速。S3C2440 这种老控制器只有固定时序寄存器（NFCONF 的 TACLS/TWRPH0/TWRPH1），压根没有 setup_data_interface 这个钩子 —— 所以它在 5.2.8 里必须置 NAND_KEEP_TIMINGS，让内核别去自动探测时序（见第十六节）。

十三、NAND 的 ECC #

SLC 每单元只判两种电平，读错概率低；MLC/TLC 要在多档电平之间分辨，对读干扰、保持时间极敏感。ECC 不是可选项，是能不能用的问题。

ECC 的粒度由 ecc.size（每步覆盖的数据字节）和 ecc.bytes（每步占用的 OOB 字节）定义，ecc.strength 是每步能纠的位数：

c
struct nand_ecc_ctrl {
        nand_ecc_modes_t mode;      /* NONE / SOFT / HW / HW_SYNDROME ... */
        enum nand_ecc_algo algo;    /* HAMMING / BCH ... */
        int steps;                  /* 每页 ECC 步数 */
        int size;                   /* 每步数据字节数 */
        int bytes;                  /* 每步 ECC 字节数 */
        int strength;               /* 每步可纠位数 */
        int total;                  /* 每页 ECC 总字节数 */
        int prepad, postpad;
        u8 *calc_buf;               /* 计算出的 ECC，大小 oobsize */
        u8 *code_buf;               /* 从 Flash 读回的 ECC，大小 oobsize */
        void (*hwctl)(struct nand_chip *chip, int mode);
        int (*calculate)(struct nand_chip *chip, const uint8_t *dat,
                         uint8_t *ecc_code);
        int (*correct)(struct nand_chip *chip, uint8_t *dat, uint8_t *read_ecc,
                       uint8_t *calc_ecc);
        int (*read_page_raw)(struct nand_chip *chip, uint8_t *buf,
                             int oob_required, int page);
        int (*write_page_raw)(struct nand_chip *chip, const uint8_t *buf,
                              int oob_required, int page);
        int (*read_page)(struct nand_chip *chip, uint8_t *buf,
                         int oob_required, int page);
        int (*write_page)(struct nand_chip *chip, const uint8_t *buf,
                          int oob_required, int page);
        int (*read_subpage)(struct nand_chip *chip, uint32_t offs,
                            uint32_t len, uint8_t *buf, int page);
        int (*write_subpage)(struct nand_chip *chip, uint32_t offset,
                             uint32_t data_len, const uint8_t *buf,
                             int oob_required, int page);
        int (*read_oob_raw)(struct nand_chip *chip, int page);
        int (*write_oob_raw)(struct nand_chip *chip, int page);
        int (*read_oob)(struct nand_chip *chip, int page);
        int (*write_oob)(struct nand_chip *chip, int page);
};

correct() 的返回值语义要记死：正数 = 纠过来的位数；-EBADMSG = 超出纠错能力（此时输入缓冲不能被改动）；其它负值 = 与纠错无关的错误。这个语义直接决定上层看到的是「悄悄纠好了」还是「数据坏了」。

read_page_raw / write_page_raw 是绕开 ECC 的裸读裸写，做硬件 ECC 时它就是「不干预」的对照组，也是 nanddump 这类工具看原始位的入口。

S3C2440 硬件 ECC 的用法：控制器内置 ECC 引擎，enable_hwecc 清一次 NFCONT.INITECC（0x01 << 13），之后每读写一个字节引擎自动累加，读完一步后从 NFMECC0 取出校验值：

c
static void s3c2440_nand_enable_hwecc(struct nand_chip *chip, int mode)
{
        unsigned long ctrl = readl(info->regs + S3C2440_NFCONT);
        writel(ctrl | S3C2440_NFCONT_INITECC, info->regs + S3C2440_NFCONT);
}

static int s3c2440_nand_calculate_ecc(struct nand_chip *chip,
                                      const u_char *dat, u_char *ecc_code)
{
        unsigned long ecc = readl(info->regs + S3C2440_NFMECC0);

        ecc_code[0] = ecc;
        ecc_code[1] = ecc >> 8;
        ecc_code[2] = ecc >> 16;
        return 0;
}

3 字节 = 24 bit 的汉明码，对应 chip->ecc.bytes = 3、strength = 1。

步长随页大小切换，这是 s3c2410_nand_attach_chip() 里的关键分支：

c
if (chip->page_shift > 10) {      /* 页 > 1KB，大页 */
        chip->ecc.size  = 256;
        chip->ecc.bytes = 3;
} else {                          /* 小页 */
        chip->ecc.size  = 512;
        chip->ecc.bytes = 3;
        mtd_set_ooblayout(nand_to_mtd(chip), &s3c2410_ooblayout_ops);
}

2KB 页按 256 字节一步，算下来 8 步 × 3 字节 = 24 字节 ECC，塞进 64 字节 OOB 里留 40 字节自由。页越大每步越细，是因为控制器一次算一步，步长不能超过硬件缓冲。

校验怎么算、怎么检错。汉明码的直觉：对每个 ECC 步的数据按位做奇偶校验，把校验位拼成 syndromes。nand_calculate_ecc() 算出「应有的校验值」，nand_correct_data() 拿它跟从 OOB 读回的 read_ecc 比对：

  • 两个 syndrome 全 0 → 数据正确，返回 0。
  • 非 0 且落在可纠正的 syndrome 表里 → 翻转对应位，返回 1（纠正位数）。
  • 落不进表 → 返回 -EBADMSG，数据不可信。

ecc_strength 越高，BCH 需要越多冗余字节。ONFI 参数页里的 ecc_bits_per_512 / ecc_bits_per_1024 就是厂家给的建议值；OOB 装不下这个强度，就只能缩小步长或提高密度。

两种模式的取舍：

模式 实现 优点 缺点
NAND_ECC_NONE 不校验 教程里方便看裸数据 上板就是数据灾难，内核会打印 not recommended
NAND_ECC_SOFT CPU 算汉明/BCH（nand_ecc.c） 不依赖控制器 占 CPU；S3C2440 这条路径强制 NAND_ECC_HAMMING
NAND_ECC_HW 控制器引擎 快、零 CPU 强度受硬件限制（S3C2440 只有 1 bit/步）
NAND_ECC_HW_SYNDROME 控制器做 syndrome，软件纠错 强度可以做高 数据与 OOB 在器件上交织存放，read_page_raw 要负责还原

NAND_ECC_HW_SYNDROME 的交织布局是踩坑重灾区：器件上的 in-band 与 out-of-band 数据是交错的，而 read_page_raw 的契约要求「隐藏布局，始终返回连续的 in-band + 连续的 OOB」。自己实现控制器驱动时，这一步不做就会读出乱码。

ECC 失败怎么报给上层：读页返回纠正位数，mtd_read() 里如果某步的位翻转数 ≥ bitflip_threshold（默认为 ecc_strength），整次读返回 -EUCLEAN 但数据是好用的。上层（UBIFS、jffs2）看到 -EUCLEAN 就知道「该块快不行了」，可以触发搬运。完全不纠错的 -EBADMSG 才是真坏。-EUCLEAN 语义在 3.x→4.x 之间改过，老代码里对它的处理要重新看一遍（见附录勘误）。

十四、坏块管理 #

NAND 出厂允许存在坏块，使用中坏块还会增加。坏块的位置信息和识别规则要用一张表管起来，这就是 BBT（Bad Block Table）。

坏块标记的物理位置：OOB（spare area）里的第 1 或第 2 字节。1 个具体的块记为坏，就是把该块第 1 页 OOB 对应字节从 0xFF 擦成非 0xFF（一般写 0x00）。因为「编程只能 1→0」，出厂标记写完擦不掉，也不会被误清除。

关键字段：chip->badblockpos（标记在 OOB 内的字节偏移）、chip->badblockbits（判定阈值）。

badblockbits 的语义在 nand_chip 注释里写得最清楚：好块的标记位置「至少要有这么多位为 1」，例如 badblockbits == 7 时，BBM = 11110111b 不算坏。这个宽松判定的原因是：某些器件在擦写扰动后会有个别位从 1 掉到 0，严格判等会把好块误杀。

位置并不固定，取决于器件：

情形 badblockpos 说明
小页（512B）器件 5 第 1 页 OOB 第 5 字节
大页（2KB 及以上）器件 0 第 1 页 OOB 第 0 字节
最后一页 视 NAND_BBT_SCANLASTPAGE 部分器件在块内最后一页也放标记
厂商特殊约定 NAND_BBT_SCAN2NDPAGE 等 需要看手册

nand_detect() 末尾有一行 chip->badblockbits = 8;，这是默认严格判定；nand_decode_bbm_options() 会按器件特性调整它。

厂商预标记的坏块表（nand_bbt_descr 的配套宏）：

宏 作用
NAND_BBT_USE_FLASH 坏块表存在 Flash 里，不再每次全扫
NAND_BBT_NO_OOB 坏块表本身不占 OOB，只占一整块的数据区
NAND_BBT_CREATE 首次找不到表时自动创建
NAND_BBT_VERSION 带版本号，取版本高的那份
NAND_BBT_SCAN2NDPAGE 第 2 页也参与坏块判定
NAND_BBT_SCANLASTPAGE 块内最后一页也参与
NAND_BBT_SCANEMPTY 扫描时跳过全 0xFF 的空页（未写过）
NAND_BBT_SAVECONTENT 建表时保留块内原有数据

NAND_BBT_SCANEMPTY 值得多说一句：出厂标记只看 OOB 的 badblockpos 字节，但某些老器件在「从未写过的块」里 OOB 整片都是 0xFF，此时按「非 0xFF 即坏」判定会把所有空块判成坏块。这个宏就是给这种器件兜底的。

扫描与建表：nand_scan_tail() 在函数指针补齐之后扫描坏块。两种存法：

方式 位置 开销 适用
每次扫描 逐块读 OOB 标记 启动慢（128MB 全扫要几秒） 无 BBT 的裸板
BBT 存在 Flash 里 用一整个块存表，首尾各一份（TD 与 MD） 启动快 量产设备

BBT 落盘用 chip->bbt_options |= NAND_BBT_USE_FLASH，nand_chip 里的三个指针负责这件事：bbt_td（主表描述符）、bbt_md（镜像表描述符）、badblock_pattern（初始扫描时用的匹配模式）。另外 NAND_SKIP_BBTSCAN 表示跳过全量扫描、直接信任已存在的 BBT —— 这依赖 u-boot 侧先把 BBT 建好（s3c2410_nand_set::flash_bbt 就是这条路的开关，对应 u-boot 的 BBT 创建代码）。

s3c2410_nand_attach_chip() 里有一处联动：

c
if (chip->bbt_options & NAND_BBT_USE_FLASH)
        chip->options |= NAND_SKIP_BBTSCAN;

用了 Flash 里的 BBT 就不再全量扫。这个组合在量产里正常，在首板调试时是陷阱：u-boot 没建 BBT 而内核又跳过扫描，坏块就会被当成好块用。

访问坏块的操作集在下三层各有对应：

层 接口
mtd_info _block_isbad / _block_markbad / _block_isreserved / _max_bad_blocks
用户态 mtd_ioctl 的 MEMGETBADBLOCK / MEMSETBADBLOCK，flash_erase 的 -N 跳过坏块检查
分区层 allocate_partition() 统计 mtd->ecc_stats.badblocks 与 bbtblocks

十五、磨损均衡 #

磨损均衡要解决的是「擦写寿命是有限的，而热数据集中在少数块上」。

按擦除次数分布的均衡策略分三档：

策略 做法 典型实现 代价
无 原地擦写 裸 mtdblock + FAT（早期方案） 热块先死
块内静态均衡 只在同一块内换页写 YAFFS2 的 chunk 分配 只能缓解，跨块不均
全局动态 + 静态均衡 空闲块轮换 + 冷数据定期搬迁 UBI（ubi_wl_get_peb / 磨损层 wl.c） 需要整层映射表

「动态均衡」只保证每个块的擦除次数不落后太多；「静态均衡」会把长期不写的冷数据块也搬一次，让它的擦除次数跟上。UBI 做的是后者，代价是擦写总量上升。

原文素材没有给出 UBI 磨损层的代码细节，本篇按内核 drivers/mtd/ubi/wl.c 的公开架构描述，具体阈值（WL_RESERVED_PEBS、UBI_WL_THRESHOLD 与 max_ec 的关系）未验证，以你手上树里的宏为准。

还有一层容易忽略的预算：预留块。UBI 建卷时会按 MTD 的 _max_bad_blocks() 预留坏块替换空间，可用容量比标称小一截。128MB 的 NAND 分完 UBI 卷，实际可用常常只有 115MB 上下 —— 这不是 bug，是给寿命和坏块留的余量。

十六、NAND 驱动实例 #

内核自带的 s3c2410.c 是最完整的参考。它的 probe 骨架和所有 NAND 驱动一样：

text
分配 s3c2410_nand_info
  → nand_controller_init(&info->controller)，ops = &s3c24xx_nand_controller_ops
  → devm_clk_get("nand") + 使能时钟
  → devm_ioremap_resource() 映射控制器寄存器（0x4E000000，1MB）
  → 逐 nand_set: s3c2410_nand_init_chip() → nand_scan() → s3c2410_nand_add_partition()
  → s3c2410_nand_inithw() 写 TACLS/TWRPH0/TWRPH1

nand_scan() 是三个阶段，每个阶段负责不同的事：

阶段 做的事
nand_scan_ident() 读 ID → 查表 → 解析内存模型 → 填 mtd 的 writesize/oobsize/erasesize、memorg、options、eccreq；顺带探测多 chip
nand_attach() 调 chip->controller->ops->attach_chip()，即 s3c2410_nand_attach_chip()，配 ECC
nand_scan_tail() 给所有未初始化的函数指针填默认实现，扫坏块表

nand_scan_ident() 收尾时做了件容易被忽略的事：memorg->ntargets = i; mtd->size = i * nanddev_target_size(&chip->base);。它在循环里逐个片选、读 ID、比对，把连续同 ID 的 die 合并成一颗大器件。

s3c2410_nand_init_chip() 是「硬件钩子」的唯一落点，也是最值得抄的一段：

c
chip->legacy.write_buf    = s3c2410_nand_write_buf;
chip->legacy.read_buf     = s3c2410_nand_read_buf;
chip->legacy.select_chip  = s3c2410_nand_select_chip;
chip->legacy.chip_delay   = 50;
nand_set_controller_data(chip, nmtd);   /* chip->priv = nmtd */
chip->controller = &info->controller;

switch (info->cpu_type) {
case TYPE_S3C2440:
        chip->legacy.IO_ADDR_W = regs + S3C2440_NFDATA;
        info->sel_reg   = regs + S3C2440_NFCONT;
        info->sel_bit   = S3C2440_NFCONT_nFCE;   /* bit1 */
        chip->legacy.cmd_ctrl  = s3c2440_nand_hwcontrol;
        chip->legacy.dev_ready = s3c2440_nand_devready;
        break;
        /* TYPE_S3C2410 / 2412 分支略，差异在寄存器基址与片选位 */
}
chip->ecc.mode = info->platform->ecc_mode;

四个钩子的实现都很短，值得逐个看清：

c
/* 片选：chip == -1 拉高 nFCE（失能），否则拉低 */
cur = readl(info->sel_reg);
if (chip == -1)
        cur |= info->sel_bit;
else
        cur &= ~info->sel_bit;
writel(cur, info->sel_reg);

/* 就绪：读 NFSTAT，bit0 为 1 表示 ready */
return readb(info->regs + S3C2440_NFSTAT) & S3C2440_NFSTAT_READY;

/* 读数据：按字读，尾部不足 4 字节的按字节补 */
readsl(info->regs + S3C2440_NFDATA, buf, len >> 2);
if (len & 3) {
        buf += len & ~3;
        for (; len & 3; len--)
                *buf++ = readb(info->regs + S3C2440_NFDATA);
}

write_buf 是镜像写法。len >> 2 之后再补尾的处理看起来啰嗦，但少了它，2KB+64B 的页尾就会错位。

板级数据在 arch/arm/mach-s3c24xx/common-smdk.c，四个分区 u-boot / params / kernel / rootfs，时序 tacls=20、twrph0=60、twrph1=20（单位 ns）。

这也解释了 NAND_KEEP_TIMINGS 这行：

c
if (!np)                       /* 走 pdata 的老板子 */
        chip->options |= NAND_KEEP_TIMINGS;

走设备树时内核会尝试用 ONFI 时序模式自动配置数据接口；走 pdata 的老板子没这信息，就显式告诉内核「别动时序，用板级写死的值」。S3C2440 的寄存器换算在 s3c2410_nand_inithw() 里：

text
NFCONF = (TACLS << 12) | (TWRPH0 << 8) | (TWRPH1 << 4)
        | (S3C2440_NFCONF_TACLS(tacls - 1) | ...)

实测打印 Tacls=2, 20ns Twrph0=6 60ns, Twrph1=2 20ns，就是板级 tacls=20ns 换算成寄存器值 2 的结果。时序算错的表现是 ID 读出来对、数据读出来错，或者干脆读不到 ID —— 前者容易被误判成 ECC 问题。

自己写一个最小驱动时，把 s3c2410.c 的骨架压到 init/exit 两个函数里就够：

c
s3c_nand_chip = kzalloc(sizeof(struct nand_chip), GFP_KERNEL);
s3c_mtd       = &s3c_nand_chip->base.mtd;
s3c_regs      = ioremap(0x4E000000, sizeof(struct nand_regs));

s3c_mtd->owner = THIS_MODULE;
s3c_mtd->priv  = s3c_nand_chip;

s3c_nand_chip->legacy.IO_ADDR_R   = &s3c_regs->nfdata;
s3c_nand_chip->legacy.IO_ADDR_W   = &s3c_regs->nfdata;
s3c_nand_chip->legacy.select_chip = s3c_nand_select_chip;
s3c_nand_chip->legacy.cmd_ctrl    = s3c_nand_cmd_ctrl;
s3c_nand_chip->legacy.dev_ready   = s3c_nand_devready;
s3c_nand_chip->legacy.read_buf    = s3c_nand_read_buf;
s3c_nand_chip->legacy.write_buf   = s3c_nand_write_buf;
s3c_nand_chip->ecc.mode           = NAND_ECC_NONE;
s3c_nand_chip->legacy.chip_delay  = 50;

s3c_regs->nfconf = (TACLS << 12) | (TWRPH0 << 8) | (TWRPH1 << 4);
s3c_regs->nfcont = (1 << 1) | (1 << 0);   /* 关闭片选 + 开启控制器 */

if (nand_scan(s3c_nand_chip, 1))
        goto out;

mtd_device_register(s3c_mtd, s3c_nand_part, 4);

erasesize 全为 00020000（128KB），与驱动打印的 erase size 128KiB 一致。四段大小相加正好是 0x8000000 = 128MB，说明分区表把整片吃满了。

写驱动的经验总结成清单：

  1. kzalloc 分配 nand_chip，mtd = &chip->base.mtd。
  2. ioremap 控制器寄存器。
  3. 填 mtd 的 owner / priv。
  4. 填 chip->legacy 的七个钩子 + chip->controller。
  5. 使能时钟、写时序寄存器。
  6. nand_scan(chip, 1)。
  7. mtd_device_register(mtd, parts, nparts)。
  8. 卸载顺序反过来：mtd_device_unregister → iounmap → kfree。

第 8 步的顺序别乱，先注销 MTD 再释放内存，否则并发访问会踩空。

十七、UBI 与文件系统层 #

在 mtdblock 之上放文件系统，问题在于 mtdblock 得假装自己是个「可覆盖写」的块设备。它的做法是内置一层读写缓冲（struct mtdblk_dev 里的 cache_data 与 STATE_EMPTY/CLEAN/DIRTY 三态）：写一个字节时先把整块读进缓冲、改、擦块、再写回。一个 4 字节的文件改动，背后是一整块擦写。写放大就是这样来的，寿命也是这样烧掉的。

所以 NAND 上的正确用法是分层：

text
应用
  └─ UBIFS                ← 日志结构化、无固定位置、支持原子提交
      └─ UBI 卷层         ← 逻辑卷（UBI_VID_HDR）与物理块（PEB）的映射
          └─ UBI 磨损层   ← 擦除计数均衡、坏块替换、scrub
              └─ MTD / NAND

四层各自解决一个问题：

层 解决的问题 关键机制
mtdchar / mtdblock 给用户态和块文件系统一个入口 ioctl 擦除（字符）、读写缓冲（块）
UBI 把坏的、会老的 NAND 变成「看起来好的块设备」 LEB↔PEB 映射、坏块替换、磨损均衡、scrub
UBIFS 掉电原子性、压缩、写放大控制 日志、wandering tree、索引树

jffs2 是 NOR 时代的经典选择：日志结构化，跑在 mtdblock 上即可，实测 flash_eraseall -j /dev/mtd1 后 mount -t jffs2 /dev/mtdblock1 /mnt 一步到位。但 jffs2 挂载时要扫描全片，容量越大越慢，128MB 以上就不合适了。

YAFFS2 是 NAND 专用的，直接把 OOB 当成标签区用（yaffs_Spare 结构），不走通用块层。实测 mount /dev/mtdblock3 /mnt 后内核打印 yaffs: dev is 32505859 name is "mtdblock3" rw —— 设备号 32505859 = 0x1F000003，主设备号 31、次设备号 3，对上了 mtdblock3。

选型速查：

介质 推荐 别用
NOR（几 MB） jffs2；只读场景直接 map_rom + XIP ext2/ext4（写放大 + 无坏块处理）
NAND（几十 MB 以上） UBI + UBIFS jffs2（挂载太慢）、裸 mtdblock + FAT
NOR + 只读固件 直接用 MTD 字符设备读 —

在 NOR 上跑 jffs2 时还有个内核配置项值得开：CONFIG_JFFS2_SUMMARY。它把擦除块的内容摘要单独存一份，挂载时只读摘要不用扫全块，4MB 的 NOR 上挂载时间能从秒级降到几百毫秒。素材里的配置清单没提这一项，实测也未验证，需要时翻 fs/jffs2/Kconfig。

十八、调试手段与常见故障 #

排 Flash 问题，从「物理层能不能通」往上查，别一上来就看文件系统。

手段 命令 看什么
分区表 cat /proc/mtd size / erasesize / name，核对几何参数是否与手册一致
块设备容量 cat /proc/partitions 主设备号 31 的设备是否齐全，#blocks（单位 KB）是否对
节点 ls -l /dev/mtd* 字符 90,x 与块 31,x 是否都生成
原始读写 flash_erase、nanddump、nandwrite 一定走字符设备 mtdN，块设备没有擦除 ioctl
ECC 统计 cat /sys/class/mtd/mtd0/ecc_failures 等 位翻转是否在增长
坏块 flash_erase -N 跳过检查；MEMGETBADBLOCK ioctl 坏块数量是否异常
识别过程 dmesg 里的 device found, Manufacturer ID / number of CFI chips ID 是否被认出来、走的哪个 probe
时序 dmesg 里 Tacls=2, 20ns Twrph0=6 60ns, Twrph1=2 20ns 时序寄存器换算是否符合手册要求

故障对照表：

现象 高概率原因 怎么确认
No NAND device found ID 读不出（片选/时序/接线），或 ID 表没有这颗芯片 用 u-boot 手工读 ID 五点数据；对比 nand_flash_ids[]
识别成错误型号 两次 ID 读取不一致（总线保持导致），或 ID 表项匹配到 dev_id 而非完整 ID dmesg 里 second ID read did not match
bus width 16 instead of 8 bits chip->options 的 NAND_BUSWIDTH_16 与实测不符 检查板级 options 与器件实际位宽
No supported Vendor Command Set found CONFIG_MTD_CFI_AMDSTD 没开 看 .config，缺了就打开重编
NOR 写入无效 用了 writeb 写 16 位命令 改成 writew；确认 bankwidth = 2
分区挂不上 分区起止没按擦除块对齐，被强制只读 dmesg 里 doesn't start on an erase/write block boundary
jffs2 挂载为空目录 没先 flash_eraseall -j 写 cleanmarker 擦除后重新挂载
读返回 -EUCLEAN 位翻转超过阈值但数据已纠好 ecc_failures 增长，考虑 scrub 或搬块
读返回 -EBADMSG 超出 ECC 纠错能力 数据真坏，从备份恢复
BBT 里没有已知坏块 u-boot 没建 BBT，内核又 NAND_SKIP_BBTSCAN 打印 flash_bbt 配置，先做一次全量扫描
掉电后文件系统损坏 跑的是 mtdblock + 非日志文件系统 换 UBI + UBIFS

调试 NAND 时用 nanddump 与 nandwrite 有两条注意事项：

bash
# 只读页数据区，不要 OOB（-o 才会带 OOB）
nanddump -l 0x800 /dev/mtd2

# 带 OOB 一起 dump，用来看坏块标记与 ECC 字节
nanddump -o -l 0x800 /dev/mtd2

# 写入前务必先擦，且跳过坏块
flash_erase -N /dev/mtd2 0 1
nandwrite -p /dev/mtd2 image.bin

-o 输出的 OOB 是器件上的原始布局。如果你的控制器用 NAND_ECC_HW_SYNDROME，这里看到的 in-band 与 OOB 是交织的，肉眼对不上页边界，别拿它当「数据错位」的证据。

排故障的顺序建议是：先 cat /proc/mtd 确认几何参数对不对（erasesize 与手册不一致说明 ID 识别或时序有问题），再 dmesg 看 ID 与分区创建，再 nanddump 看具体页。顺序错了会在文件系统层浪费大量时间。

十九、易错点速查 #

易错点 正确做法
直接调 mtd->_read / mtd->_write 走 mtd_read() / mtd_write() / mtd_erase() 包装
同时实现 _read 和 _read_oob 二者只能取其一，否则 add_mtd_device() 返回 -EINVAL
writesize 留 0 add_mtd_device() 直接 BUG_ON
分区大小不按 erasesize 对齐 会被清掉 MTD_WRITEABLE 强制只读，MTDPART_OFS_NXTBLK 可自动取整
用 mtdblockN 做擦除 块设备没有擦除 ioctl，擦除必须走 mtdN
NOR 16 位模式用 writeb 发命令 用 writew，且 map->bankwidth 必须是 2
把 0xAAAA 当解锁地址写进 8 位总线 解锁地址要按总线位宽换算（0x5555 << 1）
NAND_ECC_NONE 上量产 至少 NAND_ECC_HW + 1 bit/步，MLC 要上 BCH
硬件 ECC 忘了 INITECC 每次读写前清一次引擎，否则校验值叠加
大页器件 ecc.size 照抄 512 页 > 1KB 时 S3C2440 走 256；其它控制器看手册
badblockpos 写死 0 小页器件是 5，大页是 0，看器件手册
badblockbits 用严格判等 默认 8，宽松场景按器件调成 7 之类
NAND_BBT_USE_FLASH + 无 BBT 首板调试先做一次全量扫描，别直接 NAND_SKIP_BBTSCAN
卸载顺序写成 kfree → mtd_device_unregister 先注销再释放
擦除后立刻写 某些器件擦除后需要延时或先读一次
把 -EUCLEAN 当错误处理 它是「数据已纠正但该块快坏」的信号，应触发搬块
用 jffs2 挂 128MB 以上 NAND 挂载全片扫描太慢，换 UBIFS
mtd_concat_create 拼多片 NOR 后按单片容量算分区 拼接后是连续地址空间，分区要按总和算
