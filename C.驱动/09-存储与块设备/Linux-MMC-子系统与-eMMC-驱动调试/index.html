一、MMC framework 的软件架构 #

Linux kernel 的驱动框架有两个要点，值得反复强调：

  1. 抽象硬件——硬件架构长什么样，驱动框架就应该长什么样；
  2. 向"客户"提供 API——客户不只用户态 Application，还包括内核空间的其它 driver、其它 framework。

MMC 协议是一个总线协议，硬件上包含 Host controller、Bus、Card 三类实体。因此 framework 抽象出 host、bus、card 三个软件实体与之对应（"从左到右"）；同时按职责分成 core / host driver / card driver 三层（"从下到上"）。

1.1 从左到右：host / bus / card #

实体 职责
host 驱动 Host controller，提供访问 card 寄存器、检测插拔、读写 card 等操作方法。从设备模型看，host 检测到卡插入后向 bus 注册 MMC card 设备
bus MMC bus 的虚拟抽象，以标准设备模型的方式收纳 MMC card（device）与对应的 MMC driver（driver）
card 抽象具体的 MMC 卡，由对应的 MMC driver 驱动。从这个角度可以忽略技术细节，只关心它是存储卡、WiFi 卡还是 GPS 卡

1.2 从下到上：core / host driver / card driver #

层次 位置 职责
MMC core 中间 framework 的核心实现，抽象 host/bus/card 实体，向底层提供统一、便利的 host controller driver 编写 API
MMC host controller driver 底层 基于 core 提供的框架驱动具体硬件（drivers/mmc/host）
MMC card driver 上层 驱动 core 抽象出的虚拟 card 设备，对接块设备、TTY、wireless 等其它 framework

二、struct mmc_host #

MMC core 用 struct mmc_host 抽象具体的 Host controller，定义在 include/linux/mmc/host.h。它既描述控制器具有的特性与能力（host driver 关心的），也保存运行期的状态与参数（core 关心的）。host driver 需要关注的字段：

字段 说明
parent struct device *，指向父设备，一般是注册该 host 的 platform 设备
class_dev struct device，该 host 在设备模型中的"设备"体现，从属于 mmc_host_class
ops struct mmc_host_ops *，操作函数集
pwrseq struct mmc_pwrseq *，电源管理操作函数集
f_min / f_max / f_init 支持的时钟频率范围与初始频率
ocr_avail 支持的操作电压范围（见 MMC_VDD_ 开头的宏）
ocr_avail_sdio / _sd / _mmc 针对不同类型卡分别指定电压范围；不需要时留 0
pm_notify struct notifier_block，支持 power management 的 notify
max_current_330 / _300 / _180 对应工作电压下的最大操作电流（无特别限制可不赋值）
caps / caps2 功能特性位图
pm_caps mmc_pm_flag_t，支持的电源管理特性
max_seg_size / max_segs / max_req_size / max_blk_size / max_blk_count / max_busy_timeout 块设备参数。磁盘时代很重要，基于 MMC 的块设备硬件性能大幅提升后意义不大
lock spin lock，host driver 的私有变量，保护临界资源
ios struct mmc_ios，MMC bus 的当前配置
supply struct mmc_supply，供电信息
private 0 长度数组，长度在 mmc_alloc_host 时指定，由 host driver 自行支配

OCR（Operating Conditions Register） 是 MMC/SD/SDIO 卡上的一个 32-bit 寄存器，其中某些 bit 指明该卡的操作电压。Host 驱动卡时必须让自身支持的电压范围与之匹配，这正是 ocr_avail 存在的意义。

三、struct mmc_host_ops 与 pwrseq #

struct mmc_host_ops 集合了 host controller 的全部操作函数。

3.1 数据传输 #

c
/*
 * It is optional for the host to implement pre_req and post_req in
 * order to support double buffering of requests (prepare one request
 * while another request is active).
 * pre_req() must always be followed by a post_req().
 * To undo a call made to pre_req(), call post_req() with a
 * nonzero err condition.
 */
void    (*post_req)(struct mmc_host *host, struct mmc_request *req,
                    int err);
void    (*pre_req)(struct mmc_host *host, struct mmc_request *req,
                   bool is_first_req);
void    (*request)(struct mmc_host *host, struct mmc_request *req);

request 是必需的；pre_req / post_req 可选，host driver 可用它们实现双 buffer 之类的高级功能。传输的主体是 struct mmc_request。

3.2 总线参数配置与卡状态获取 #

c
/*
 * Avoid calling these three functions too often or in a "fast path",
 * since underlaying controller might implement them in an expensive
 * and/or slow way.
 *
 * Also note that these functions might sleep, so don't call them
 * in the atomic contexts!
 */
void    (*set_ios)(struct mmc_host *host, struct mmc_ios *ios);
int     (*get_ro)(struct mmc_host *host);
int     (*get_cd)(struct mmc_host *host);
  • set_ios：设置 bus 参数；
  • get_ro：返回卡是否只读——0 读写卡、1 只读卡、-ENOSYS 不支持、其它负 errno 表示出错；
  • get_cd：检测卡存在——0 无卡、1 有卡、-ENOSYS 不支持、其它负 errno 表示出错。

这三个函数可能 sleep、耗时较长，千万别在 atomic 上下文里调用。

其余函数都是 optional。

3.3 pwrseq #

MMC framework 的 power sequence 是个有意思的设计：struct mmc_pwrseq_ops 集合了 power on / power off 等操作：

c
struct mmc_pwrseq_ops {
        void (*pre_power_on)(struct mmc_host *host);
        void (*post_power_on)(struct mmc_host *host);
        void (*power_off)(struct mmc_host *host);
        void (*free)(struct mmc_host *host);
};

struct mmc_pwrseq {
        const struct mmc_pwrseq_ops *ops;
};

core 提供了通用管理模块 drivers/mmc/core/pwrseq.c 和几个简单策略（pwrseq_simple.c、pwrseq_emmc.c），目的就是只靠 dts 配置就能把 MMC 供电配对：

dts
/* arch/arm/boot/dts/omap3-igep0020.dts */
mmc2_pwrseq: mmc2_pwrseq {
        compatible = "mmc-pwrseq-simple";
        reset-gpios = <&gpio5 11 GPIO_ACTIVE_LOW>,      /* gpio_139 - RESET_N_W */
                      <&gpio5 10 GPIO_ACTIVE_LOW>;      /* gpio_138 - WIFI_PDN */
};

/* arch/arm/boot/dts/rk3288-veyron.dtsi  */
emmc_pwrseq: emmc-pwrseq {
        compatible = "mmc-pwrseq-emmc";
        pinctrl-0 = <&emmc_reset>;
        pinctrl-names = "default";
        reset-gpios = <&gpio2 9 GPIO_ACTIVE_HIGH>;
};

五、struct mmc_ios #

struct mmc_ios 保存 MMC 总线当前的配置：

字段 取值
clock 时钟频率
vdd 卡的供电电压，通过 1 << vdd 得到 MMC_VDD_x_x 宏
bus_mode MMC_BUSMODE_OPENDRAIN / MMC_BUSMODE_PUSHPULL
chip_select 仅 SPI 模式：MMC_CS_DONTCARE / MMC_CS_HIGH / MMC_CS_LOW
power_mode MMC_POWER_OFF / UP / ON / UNDEFINED
bus_width MMC_BUS_WIDTH_1 / _4 / _8
timing 见下
signal_voltage MMC_SIGNAL_VOLTAGE_330 / _180 / _120
drv_type MMC_SET_DRIVER_TYPE_B/A/C/D

timing 的取值覆盖全部速率规范：MMC_TIMING_LEGACY、MMC_TIMING_MMC_HS、MMC_TIMING_SD_HS、MMC_TIMING_UHS_SDR12/25/50/104、MMC_TIMING_UHS_DDR50、MMC_TIMING_MMC_DDR52、MMC_TIMING_MMC_HS200、MMC_TIMING_MMC_HS400。

六、struct mmc_supply：vmmc 与 vqmmc #

c
struct mmc_supply {
        struct regulator *vmmc;         /* Card power supply */
        struct regulator *vqmmc;        /* Optional Vccq supply */
};
  • vmmc 是卡的供电，一般接卡的 VDD 引脚；
  • vqmmc 用于给信号线（CMD、CLK、DATA）上拉供电。

通常两者用同一个 regulator 即可。但一些高速卡（如 UHS SD）要求高速模式下 vmmc 为 3.3V、vqmmc 为 1.8V，这时就必须用两个独立的 regulator。

七、struct mmc_request / command / data #

c
/* include/linux/mmc/core.h */
struct mmc_request {
        struct mmc_command      *sbc;           /* SET_BLOCK_COUNT for multiblock */
        struct mmc_command      *cmd;
        struct mmc_data         *data;
        struct mmc_command      *stop;

        struct completion       completion;
        void                    (*done)(struct mmc_request *);/* completion function */
        struct mmc_host         *host;
};

要理解它，得先回看总线协议（详见《eMMC 原理与协议》第四章）：一次传输由 Command / Response / Data 三种 token 组成，其中 Response 与 Data 都不是必需的。

Command token 只有一种格式，48 bit：Start bit(0)、Transmitter bit(1, host command)、Content(38bit)、CRC(7bit)、Stop bit(1)。

Response token 有 R1/R3/R4/R5/R2 五种，前者均为 48 bit，R2 为 136 bit。

带 Data 的 Command 有两类：

  • Sequential commands：发 Start 后数据以 stream 形式传输，直到 Stop 为止。仅支持 1-bit 总线，主要为兼容旧技术，一般不用；
  • Block-oriented commands：数据以 block 形式传输，每块大小固定且都有 CRC 保护。

block 传输又可分：

  • Open-ended：Start 时不指定块数，直到发 Stop Command；
  • pre-defined block count：Start 时指定块数，达到后卡自动停止，可省掉 Stop。

对照来看 struct mmc_request 的字段：

字段 说明
cmd Start command，必需
data 传输的数据，可选
stop / sbc Open-ended 需要 stop；pre-defined block count 需要 sbc（发 SET_BLOCK_COUNT / CMD23）
completion 等待传输完成，host driver 按需使用
done 传输完成回调
host 对应的 mmc host controller

struct mmc_command：

字段 说明
opcode 操作码
arg 命令参数
resp[4] 应答结果，32-bit 数组，最多存 128 bit
flags 期望的应答类型位图：MMC_RSP_PRESENT（是否需应答）、MMC_RSP_136（需 136bit 应答）、MMC_RSP_CRC（需 CRC 校验）等
retries 出错时最多重发次数
error 最终错误原因，如 ETIMEDOUT、EILSEQ、EINVAL、ENOMEDIUM
busy_timeout 等待卡返回 busy 的超时时间（ms）
data / mrq 对应的 data / request 指针

struct mmc_data：

字段 说明
timeout_ns / timeout_clks 传输超时（ns / clocks）
blksz / blocks 块大小与块数，不会超过 host 上报的 max_blk_size / max_blk_count
error 传输错误值
flags 方向：MMC_DATA_WRITE / MMC_DATA_READ
sg / sg_len struct scatterlist 数组与其长度，保存待传输数据
sg_count sg map 出来的实际 entry 数，可能因物理连续或 IOMMU 干涉而小于 sg_len
host_cookie host driver 私有数据

八、MMC core 提供的操作函数 #

围绕 struct mmc_host，core 提供以下几类接口：

生命周期：

  • mmc_alloc_host：动态分配一个 struct mmc_host，extra 是私有数据大小，可通过 host->private 或 mmc_priv 访问；mmc_free_host 相反；
  • mmc_add_host：把初始化好的 host 注册进 kernel；mmc_remove_host 相反。

配置解析：

  • mmc_of_parse：方便 host driver 在 dts 中定义 host 特性，由它解析并填充到 struct mmc_host。dts 属性关键字参考 drivers/mmc/core/host.c。

运行时：

  • power save 的进入 / 退出；
  • 当检测到总线设备变动（卡插入/拔出）时调用，让 core 做后续处理；delay 参数（jiffies）可用于卡插拔去抖；
  • 处理完一个 mmc request 后调用，通知 core 做善后——校验结果、调用 .done 回调等；
  • SDIO IRQ 相关的两个函数。

regulator 辅助：

c
int mmc_regulator_get_ocrmask(struct regulator *supply);
int mmc_regulator_set_ocr(struct mmc_host *mmc,
                          struct regulator *supply,
                          unsigned short vdd_bit);
int mmc_regulator_set_vqmmc(struct mmc_host *mmc, struct mmc_ios *ios);
int mmc_regulator_get_supply(struct mmc_host *mmc);
  • mmc_regulator_get_ocrmask：由 regulator 支持的电压推导 ocr mask；
  • mmc_regulator_set_ocr：把 host 切到某个操作电压，内部调用 regulator framework；
  • mmc_regulator_set_vqmmc：按 mmc_ios 设置 vqmmc 电压；
  • mmc_regulator_get_supply：从 dts 的 vmmc / vqmmc 属性解析出 regulator 指针。

九、怎么写一个 MMC host driver #

所有工作都围绕 struct mmc_host 展开，大流程只有三步：

  1. 调用 mmc_alloc_host 分配 struct mmc_host，描述某一块具体的 MMC host 控制器；
  2. 按控制器的硬件特性填充各字段——MMC 类型、电压范围、操作函数集等；
  3. 调用 mmc_add_host 把填好的 host 注册到 MMC core。

看着简单，一牵涉实现细节就很麻烦。kernel 里有大把现成例子（如 drivers/mmc/host/pxamci.c），是学习 Linux 驱动的最佳材料。

大部分和控制器能力有关的字段都可以通过 dts 配置，再 mmc_of_parse 自动解析填充：

dts
/* arch/arm/boot/dts/exynos5420-peach-pit.dts */
&mmc_1 {
        status = "okay";
        num-slots = <1>;
        non-removable;
        cap-sdio-irq;
        keep-power-in-suspend;
        clock-frequency = <400000000>;
        samsung,dw-mshc-ciu-div = <1>;
        samsung,dw-mshc-sdr-timing = <0 1>;
        samsung,dw-mshc-ddr-timing = <0 2>;
        pinctrl-names = "default";
        pinctrl-0 = <&sd1_clk>, <&sd1_cmd>, <&sd1_int>,
                    <&sd1_bus1>, <&sd1_bus4>, <&sd1_bus8>, <&wifi_en>;
        bus-width = <4>;
        cap-sd-highspeed;
        mmc-pwrseq = <&mmc1_pwrseq>;
        vqmmc-supply = <&buck10_reg>;
};

工作量最大的永远是 struct mmc_host_ops 的实现——所有 MMC host 的操作逻辑都封在这里。

9.1 Sectors / Blocks / Segments #

理解 max_seg_size、max_segs、max_req_size、max_blk_size、max_blk_count 这几个参数，需要先分清三个概念：

Sectors（扇区）：存储设备访问的基本单位。磁盘、NAND 的 sector 大小固定（512、2048 等）。对存储类 MMC 设备，因为有协议封装，host 驱动和块设备驱动不需要关注物理 size，只关注总线上的数据传输单位；非存储类 MMC 设备则完全没有 sector 概念。

Blocks（块）：数据传输的基本单位，是 VFS 抽象出来的纯软件概念，与硬件无关。必须是 2 的整数倍、不大于 sector 单位、不大于 page 长度，一般为 512B / 2048B / 4096B。

对 MMC 设备来说，由于协议封装，sector 概念被淡化，设备可以支持一定范围内的任意 block size，范围由两个因素决定：

  • host controller 的能力（max_blk_size）；
  • 卡的能力（可通过 MMC command 从 CSD 寄存器读出）。

Segments（段）：块设备传输本质上是"设备上相邻扇区 ↔ 内存"之间的传输。为提升性能通常走 DMA。早期磁盘控制器的 DMA 要求内存连续；现代 SoC 多支持分散/聚合（scatter-gather）DMA，可以在多块不连续内存区域间传输。

一次 SG DMA，块设备驱动需要给控制器两样东西：

  1. 初始扇区号与总扇区数；
  2. 内存区域描述链表，每项包含地址与长度，项之间可以物理连续也可以不连续。

这里的每个内存区域描述（一段物理连续内存，可以是一个 page 或 page 的一部分）就是一个 Segment，一个 Segment 包含多个相邻扇区。一次传输可能涉及多个 Segment。

于是：

  • max_seg_size：单个 Segment 的最大长度；
  • max_segs：最多支持的 Segment 个数。

9.2 mmc_data 里的 sg #

MMC core 提交给 host driver 的传输请求是一个 struct scatterlist 链表，也就是一个个 Segment（个数在 sg_len 中）。

host driver 收到后需要调用 dma_map_sg 把这些 Segment 映射出物理地址交给控制器传输。映射时，相邻两个 Segment 的物理地址可能本来就连续，因而被合并，所以可供控制器传输的内存片可能少于 sg_len——实际数量看 dma_map_sg 的返回值，存进 sg_count。

具体怎么传，取决于 MMC controller 的硬件实现。

十、实战一：RK3399 的 SD 卡配置 #

板卡：NanoPC-T4，eMMC 16GB / LPDDR3 4GB / 15.6 英寸 HDMI 屏，u-boot 2023.04，linux 6.3。

NanoPC-T4 带一个 microSD 卡槽。注意一个容易误解的点：并没有"SDMMC 卡"或"SDMMC 接口"，这里的 SDMMC 就是 SD 卡。

RK3399 的电源域包含 sdmmc，要使用 SDMMC0 必须先配置电源域。SDMMC0_VDD 引脚所接的 VCC_SDIO 来自 rk808 的 12 号引脚 VLDO4。

设备节点配置参考 Documentation/devicetree/bindings/mmc/rockchip-dw-mshc.yaml，在 arch/arm64/boot/dts/rockchip/rk3399-evb.dts 中追加：

dts
&sdmmc {
	bus-width = <4>;
	cap-sd-highspeed;
	cap-mmc-highspeed;
	cd-gpios = <&gpio0 RK_PA7 GPIO_ACTIVE_LOW>;
	disable-wp;
	pinctrl-names = "default";
	pinctrl-0 = <&sdmmc_bus4 &sdmmc_clk &sdmmc_cmd &sdmmc0_det_l>;
	sd-uhs-sdr104;
	vmmc-supply = <&vcc3v0_sd>;

十一、实战二：RK3568 的 eMMC 配置与调试 #

11.1 控制器 #

RK3568 eMMC 主机控制器特性：

  1. 支持 eMMC 5.1 协议；
  2. 支持自动 tuning；
  3. 支持 4/8-bit 接口；
  4. 支持 legacy、High Speed SDR、High Speed DDR、HS200/HS400 速度模式；
  5. AHB 从接口：32bit 数据和地址宽度；
  6. AXI 主接口：32bit 地址宽度、64bit 数据宽度；
  7. 时钟调整：支持 transmit clock、sample clock 与 data strobe 相位自动调整。

先看原理图再调驱动。两点注意：

  • eMMC 的 D0~D8 / CMD 电压必须一致，同为 3.3V 或 1.8V；
  • Data Strobe 由 eMMC 发给 RK3568，频率同 CLK，用于接收同步；只能在 HS400 模式下启用，启用后提高稳定性、省去 tuning。

11.3 驱动 #

RK3568 eMMC 控制器使用 Synopsys IP，驱动文件 drivers/mmc/host/sdhci-of-dwcmshc.c，核心是两组 ops：

c
static const struct sdhci_ops sdhci_dwcmshc_ops = {
        .set_clock              = sdhci_set_clock,
        .set_bus_width          = sdhci_set_bus_width,
        .set_uhs_signaling      = dwcmshc_set_uhs_signaling,
        .get_max_clock          = sdhci_pltfm_clk_get_max_clock,
        .reset                  = sdhci_reset,
        .adma_write_desc        = dwcmshc_adma_write_desc,
};

static const struct sdhci_ops sdhci_dwcmshc_rk_ops = {
        .set_clock              = dwcmshc_rk_set_clock,
        .set_bus_width          = sdhci_set_bus_width,
        .set_uhs_signaling      = dwcmshc_set_uhs_signaling,
        .get_max_clock          = sdhci_pltfm_clk_get_max_clock,
        .reset                  = sdhci_reset,
        .adma_write_desc        = dwcmshc_adma_write_desc,
};

差别只在 .set_clock：RK 版本多了自定义的时钟设置（因为 Rockchip 把 transmit / sample clock 的相位调整做进了时钟树）。

十二、小结 #

  1. framework 的形状来自硬件：host / bus / card 三个实体对应总线上的三类角色，core / host driver / card driver 三层对应职责划分；
  2. 写 host driver 就是填两个结构体：struct mmc_host 填能力（电压、频率、caps、supply），struct mmc_host_ops 填行为（request 是必须的，set_ios/get_ro/get_cd 别在 atomic 上下文调）；
  3. 大部分板级差异都可以只写设备树：bus-width、non-removable、cap-*-highspeed、sd-uhs-*、vmmc/vqmmc-supply、mmc-pwrseq——剩下真正要写代码的地方，往往是时钟与相位；
  4. 调试路径是 U-Boot → 内核 devicetree → sysfs/debugfs：mmc info 看卡与模式，cat ios 看当前总线配置，/sys/kernel/debug/clk 看时钟树与 tuning 相位；
  5. HS200/HS400 的所有稳定性问题，八成落在 clock phase 与 signal voltage 上——这也是 ios 里 timing spec 与 signal voltage 两个字段值得先看一眼的原因。
