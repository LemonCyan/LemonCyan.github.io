一、块设备与字符设备的本质差别 #

Linux 把外设分成三类：字符设备、块设备、网络设备。块设备管的是机械硬盘、SSD、SD/TF 卡、eMMC、U 盘、RamDisk 这类存储介质。

从用户态看，块设备和字符设备没什么区别：都是 /dev/sda1、/dev/mtdblock0 这样的设备文件，都能 open/close/read/write。差别全在驱动内部。

字符设备像字节流。串口收数据就是一个字节一个字节来，驱动内部爱用多大的环形缓冲区都行，串口本身不管。你在驱动里实现 open、release、read、write，应用顺着设备文件调进去，链路就到头了。

块设备不一样，它多了一层内核里的消费者：文件系统。

维度 字符设备 块设备
读写基本单位 字节（Byte） 块（Block），典型 512B / 1KB / 4KB
访问模式 顺序访问，不能前后跳跃 随机访问，可任意寻址
典型设备 LED、按键、串口、USB 鼠标键盘 HDD、SSD、SD/TF、eMMC、NAND/NOR Flash
驱动操作集 struct file_operations struct block_device_operations
有没有 read/write 回调 有 没有
往上层提供的接口 只面向用户态 用户态接口 + 内核接口（可挂文件系统）
缓存机制 驱动自己决定 页缓存 + 缓冲区 + 请求队列统一处理
设备号 最多 2^20 个从设备号（12:20 拆分） 主设备号用于块类，次设备号按 minors 划给磁盘/分区
数据组织 无固定格式要求 由文件系统定义格式（ext4、FAT、yaffs…）

这张表里最关键的一行是「没有 read/write 回调」。块设备的操作函数集只有 open、release、ioctl、getgeo、check_events 这些，数据实际怎么搬，走的是另一条路：上层攒出 bio，通用块层拼成 request，驱动实现 queue_rq 或 submit_bio 把数据搬到介质上。第九章会把这条路走一遍。

两类设备的分类也不是绝对的。网络设备就两头都不像：说它是字符设备，它的 I/O 却是成块的（报文、包、帧）；说它是块设备，它的块又不固定大小，几字节到几千字节都有。UNIX 给网络接口分配 eth0 这种名字，但 /dev 下没有对应节点，内核和网卡驱动之间传的是 sk_buff，不是 open/read/write。

再就是介质本身的物理差异，它直接决定了要不要 I/O 调度：

  • SD 卡、eMMC、NAND Flash 没有机械部件，任意扇区都能直接读写，寻道开销为 0；
  • 机械硬盘要动磁头，换盘面、换磁道都要等磁头挪过去。把杂乱的访问按位置重排，一次寻道能多带几百 KB，性能差距就在这。

前一类设备上跑电梯算法纯属浪费 CPU；后一类设备上不排序，吞吐直接掉一半。第十节讲合并与调度时会回到这个分界。

二、扇区、块与段的层级关系 #

三个概念经常被混用，它们的单位和归属是分开的。

概念 单位 由谁定义 谁在用它 数据结构
扇区 Sector 硬件最小传输单位，经典值 512 字节 硬件接口 块层与驱动之间的地址单位 sector_t
块 Block 文件系统最小分配单位，2^n 字节 文件系统 VFS 与页缓存的映射粒度 bd_block_size、i_blkbits
段 Segment 页内一段连续内存（可以是一整页） 内存管理 DMA 描述一次传输的物理缓冲 struct bio_vec

往下拆：

  • 扇区是硬件的单位。驱动向上层暴露的地址一律以扇区计数，所以你会到处看到 >> 9、<< 9 这类移位。
  • 块是文件系统的单位。它必须是 2 的 n 次方，必须是扇区的整数倍，常见值 512B / 1KB / 4KB，不能大于一个内存页。内核里块的换算靠 set_blocksize() 和 i_blkbits。
  • 段是内存侧的单位，由若干个相邻的块组成，落在同一个内存页里。一个 bio 由若干个 bio_vec 组成，每个 bio_vec 描述一页里的一段。

为什么需要一个「段」的概念？因为磁盘上一段连续的扇区，在内存里往往散落在好几个不连续的页上。一次 I/O 的磁盘侧是连续的，内存侧不连续，那就得用数组把每页中那一段记下来，这个数组就是 bio_vec[]。段的数量取决于这段连续磁盘空间映射了多少块不连续内存，上层构 bio 时一般只有一段。

那么为什么写一个 txt 文件里的几十字节，会引发一整个扇区的读改写？因为硬件只认扇区。内核的做法是引入缓冲区：把包含目标位置的整块读进内存，改内存，再整块写回。写多次小数据就会反复读扇区、写扇区。请求队列存在的意义就在这里——一个进程在跑，它的写请求可以先攒着，合并、排序之后一次性下发。

三、Linux 块子系统的层次架构 #

一次 write() 在内核里的落点，按层往下是这样：

text
用户态 write()/read()
   |
   v
VFS 虚拟文件系统        统一 file 接口，屏蔽具体文件系统
   |
   v
磁盘页缓存 Page Cache   预读 + 回写，命中就直接返回
   |
   v
映射层 Mapping Layer    查 inode，算出数据落在哪些逻辑块（LBA）
   |
   v
通用块层 Generic Block  把请求封装成 bio，submit_bio 入口
   |
   v
I/O 调度层 Scheduler    合并、排序，把 bio 变成 request
   |
   v
块设备驱动               queue_rq / submit_bio，向控制器发指令
   |
   v
硬件磁盘控制器

逐层交代职责：

  1. VFS：抽象文件系统差异，向上给应用统一接口，sys_write、sys_read 都从这里进。
  2. 页缓存：读写先看内存里有没有，命中不进块层。同时负责预读，检测到顺序访问就提前把后续数据读进来。
  3. 映射层：具体文件系统查 inode，把文件内的偏移换算成磁盘上的逻辑块地址。
  4. 通用块层：定义统一的数据模型。上层不管下面挂的是 SATA 盘还是 eMMC，都只负责发出 bio。
  5. I/O 调度层：接收通用块层的请求，按算法合并相邻、重排顺序，再把请求交给驱动。
  6. 块设备驱动：从队列取请求，向控制器发物理指令。

页缓存和写回这两层看着和驱动无关，排查性能问题时绕不开：写操作先进脏页，内核按负载决定什么时候刷出去，所以你看到的不一定是驱动慢，而是回写线程还没轮到。

历史分岔点必须在这里说清楚。

内核版本 块层形态 驱动要实现的回调
2.6 ~ 4.x 单队列 blk-sq 与 blk-mq 并存 request_fn（队列调度）或 make_request_fn（自行处理 bio）
3.13 / 3.16 blk-mq 合入主线 / 成为完整特性 开始出现 mrq、blk_mq_init_queue
5.0 blk-sq 代码及其调度器被完整移除，blk-mq 成为唯一路径 blk_mq_ops.queue_rq
5.9 make_request_fn 从 request_queue 移到 block_device_operations，改名 submit_bio；generic_make_request 改名 submit_bio_noacct bdev_ops.submit_bio（仅 bio 型驱动用）
5.11 新增 blk_mq_alloc_disk / blk_cleanup_disk，磁盘与队列一起分配 blk_mq_alloc_disk + add_disk
5.16 alloc_disk/alloc_disk_node 宏移除；blk_mq_init_sq_queue 移除 只剩 blk_mq_alloc_disk / blk_alloc_disk
5.18 起（提交日期 2022-03） REQ_OP_SECURE_ERASE 与 BLKSECDISCARD 被移除 不用再处理 secure erase

按这张表，5.x 之后写块设备驱动，只有一条路：填 blk_mq_ops，用 blk_mq_alloc_disk 拿 gendisk，add_disk 注册。素材里那些 blk_init_queue(my_request_fn, &lock) + blk_queue_make_request() 的写法，在 5.0 以后编译不过，在 4.x 上还能跑。

四、四大核心数据结构总览 #

通用块层和驱动之间靠四个结构承载数据：gendisk、block_device_operations、request_queue、bio，外加两个配角 request 和 bio_vec。

结构 一句话职责 生命周期 谁分配 谁释放
struct gendisk 一块磁盘的整体抽象 驱动 probe 到 remove blk_mq_alloc_disk / blk_alloc_disk del_gendisk + put_disk
struct block_device_operations 驱动回调表 静态常量 驱动定义 不用释放
struct request_queue 挂在这块盘上的请求队列 跟 disk 一起 blk_mq_alloc_disk（内含） blk_cleanup_disk / blk_cleanup_queue
struct bio 一次块 I/O 的基本单位 每次 I/O 一份 上层的 bio_alloc 完成后 bio_endio 回收
struct request 调度后的一个任务单元，装一个或多个 bio 队列固定预分配 blk-mq 初始化时按深度分好 队列销毁时才释放
struct bio_vec 一页内的一段连续内存 随 bio 随 bio 随 bio

完整的包含关系：

text
gendisk  ──1:1──>  request_queue
                       │ 存放
                       v
                   request  ──1:N──>  bio  ──1:N──>  bio_vec
                                                            │
                                                            v
                                                          struct page

一条 request_queue 由若干 request 组成；一个 request 装多个被合并的 bio；一个 bio 在内存侧由若干 bio_vec 描述。

为什么中间要插一个 request？光有 bio 也能下发，但 bio 是上层视角的「我要读这段」，没法排序。request 是「调度视角的一个任务单元」，它在队列里可以被移动、合并、重排。多绕这一层，换来的是调度能力。

五、gendisk：一个磁盘的抽象 #

struct gendisk 描述一块磁盘，地位类似字符设备的 struct cdev。定义位置随版本漂移：5.2.8 在 include/linux/genhd.h，5.11 之后磁盘结构逐步搬进 include/linux/blk_types.h（未验证具体搬移版本）。

struct gendisk 的完整字段（5.2.8，include/linux/genhd.h）分四组：设备号与名字（major / first_minor / minors / disk_name / devnode）、分区（part_tbl / part0）、驱动挂载点（fops / queue / private_data）、状态与杂项（flags / lookup_sem / slave_dir / random / sync_io / ev / integrity_kobj / node_id / bb / lockdep_map）。真正要写的只有前三个组里那几个：

字段 含义 注意事项
major 主设备号，由 register_blkdev 申请 注释写明「仅作输入参数，别直接读」，读要用 disk_devt()
first_minor 本盘第一个次设备号，一般 0 分区从 first_minor + 1 开始
minors 次设备号总数 = 分区数 + 1 最小 1，表示不分区；大于 1 时可分区数为 minors - 1
disk_name 磁盘名，注册后出现在 /dev 和 /sys/block 长度 DISK_NAME_LEN（32）
devnode 自定义设备节点名 不用就给 NULL
part_tbl 指向分区表 disk_part_tbl RCU 保护，通过 helper 访问
part0 内嵌的 0 号分区，代表整块盘 没有单独分配，就长在 gendisk 里
fops 回调表 block_device_operations 必须填 owner
queue 绑定的请求队列 5.11 起不手工赋值，由 alloc 时传入
private_data 驱动私有数据 随便用，典型放设备结构体
flags GENHD_FL_* 位 GENHD_FL_UP 由 add_disk 置位
lookup_sem 读写信号量，保护磁盘查找 由 __alloc_disk_node 初始化
node_id NUMA 节点 alloc_disk 宏固定传 NUMA_NO_NODE

queue 这一条要展开。5.2.8 时代是两步：先 alloc_disk(1) 拿 gendisk，再 blk_mq_init_sq_queue() 拿队列，最后 disk->queue = q 手工挂上。5.11 的提交「block: pass a request_queue to __blk_alloc_disk」把 disk->queue = q 挪进了 __alloc_disk_node() 内部，目的就是保证 gendisk 的 ->queue 始终指向一个活着的队列；同期把 scsi/sd.c、scsi/sr.c 里的 gd->queue = ... 全删了。所以 5.11 之后的驱动代码里再写 disk->queue = q，会编译报错或者根本不生效（未验证具体报错形态，取决于那个版本的字段可见性）。

再往下的分区对象，5.2.8 是这样：

c

        struct rcu_head rcu_head;
        int len;

c

六、block_device_operations：驱动要实现的回调 #

块设备的回调表和字符设备的 file_operations 是一对，但内容完全不同。5.2.8 的完整定义在 include/linux/blkdev.h：

c
struct block_device_operations {
        int (*open) (struct block_device *, fmode_t);
        void (*release) (struct gendisk *, fmode_t);
        int (*rw_page)(struct block_device *, sector_t, struct page *, unsigned int);
        int (*ioctl) (struct block_device *, fmode_t, unsigned, unsigned long);
        int (*compat_ioctl) (struct block_device *, fmode_t, unsigned, unsigned long);
        unsigned int (*check_events) (struct gendisk *disk,
                                      unsigned int clearing);
        /* ->media_changed() is DEPRECATED, use ->check_events() instead */
        int (*media_changed) (struct gendisk *);
        void (*unlock_native_capacity) (struct gendisk *);
        int (*revalidate_disk) (struct gendisk *);
        int (*getgeo)(struct block_device *, struct hd_geometry *);
        /* this callback is with swap_lock and sometimes page table lock held */
        void (*swap_slot_free_notify) (struct block_device *, unsigned long);
        int (*report_zones)(struct gendisk *, sector_t sector,
                            struct blk_zone *zones, unsigned int *nr_zones,
                            gfp_t gfp_mask);
        struct module *owner;
        const struct pr_ops *pr_ops;
};

逐个回调交代什么时候被调、要不要实现：

回调 触发时机 必须实现 说明
owner — 是 填 THIS_MODULE，否则模块计数不对，卸载会崩
open 打开设备节点时 否 返回 -ERESTARTSYS 会让块层重试（磁盘正在删除的竞态）
release 关闭设备节点时 否 只在最后一次 close 时调
ioctl ioctl(2) 否 私有命令走这里
compat_ioctl 32 位应用跑在 64 位内核 否 不填时 32 位应用调 ioctl 直接失败
getgeo HDIO_GETGEO 否 填 hd_geometry，老工具和 fdisk 会看
check_events 轮询介质变化 否 可移动设备要填，用来上报插拔
media_changed 同上 否 已废弃，用 check_events
revalidate_disk 重扫分区之前 否 容量变了在这里更新
rw_page 直接读写单个页 否 极少数驱动用
unlock_native_capacity 分区表超出 EOD 否 破解 HPA 隐藏容量
report_zones 主机管理型 zoned 设备 否 普通设备不用管
swap_slot_free_notify swap 释放槽位 否 掉电内存类设备用

最小可用版本就两行：

c
static const struct block_device_operations my_fops = {
        .owner = THIS_MODULE,
};

注意到没有：没有 read，没有 write。数据搬运走 blk_mq_ops（或 5.9 之前的 make_request_fn），不在这个表里。读到这里的第一个反应应该是：那 open 里的 bdev 和 release 里的 disk 参数为什么不统一？历史包袱。open 拿的是具体的块设备（分区或整盘），release 给的是整块盘。

getgeo 是老接口，但在 RamDisk 这类没有真实几何的设备上仍然有用，因为 fdisk 分区要靠它算柱面。第十三章会给一个具体例子，heads=2, cylinders=32 直接决定 fdisk 里只能建 2 个主分区。

七、request_queue 与请求队列 #

struct request_queue 是挂在一块盘上的请求队列。5.2.8 的完整定义在 include/linux/blkdev.h，字段近 100 个，下面按「你实际会碰到的」分组交代：

分组 字段 含义
请求链与合并 queue_head、last_merge 请求链头；第一个有机会被合并的请求
调度 elevator 当前 I/O 调度器，没开调度就是 NULL
提交入口 make_request_fn bio 提交回调，blk-mq 下是 blk_mq_make_request；5.9 移到 block_device_operations.submit_bio
驱动回调 mq_ops blk_mq_ops，驱动实现 queue_rq 的地方
软件队列 queue_ctx、nr_queues per-CPU 的 blk_mq_ctx，数量等于 CPU 数
硬件队列 queue_hw_ctx、nr_hw_queues 对应设备真实队列数，多数设备是 1
深度 queue_depth、nr_requests 队列能挂起的请求上限
排队 requeue_list、requeue_lock、requeue_work 驱动忙时把请求挂回这里
限制 limits queue_limits，最大扇区数、对齐、粒度都在这
统计与节流 stats、rq_qos、td IO 记账与限速
生命周期 q_usage_counter、mq_freeze_depth、kobj 引用计数、冻结、sysfs

版本提示：make_request_fn 这个字段 5.9 就不在 request_queue 里了，被移进 block_device_operations 并改名 submit_bio（Christoph Hellwig 的 20 篇系列，[PATCH 16/20] 就是这步）。同一系列还砍掉了 direct_make_request 这条旁路。看到某份资料写 blk_queue_make_request(q, my_fn)，先确认它是 5.9 之前的。

request_queue 不是驱动自己乱造的，5.x 的分配方式三选一：

c
/* 5.11+：一步拿到 gendisk 和内部的 request_queue，推荐 */
struct gendisk *disk = blk_mq_alloc_disk(&tag_set, queuedata);

/* 5.11+：bio 全程自定义处理的驱动 */
struct gendisk *disk = blk_alloc_disk(NUMA_NO_NODE);

/* 5.2.8 的写法：先队列后磁盘，两步走 */
struct request_queue *q = blk_mq_init_sq_queue(&tag_set, &mq_ops, 16,
                                                BLK_MQ_F_SHOULD_MERGE);
struct gendisk *disk = alloc_disk(1);
disk->queue = q;

blk_mq_init_sq_queue 在 5.16 被删除（提交说明：All users are gone now），alloc_disk 宏也在 5.16 消失。所以第三行那种写法只适用于 5.11 ~ 5.15。

request 就是队列里的节点，5.2.8 定义在 include/linux/blkdev.h。几个字段是排查问题的切入口：__sector 是起始扇区，__data_len 是字节数，tag 是硬件队列槽位号（没分配时是 -1），nr_phys_segments 是物理段数（合并后的真实 DMA 段数），end_io 是完成回调。

request 是队列初始化时预先分配的，不是每次 I/O 现要现给。深度由 queue_depth 决定，这些 request 早就躺在硬件队列的 static_rqs[] 数组里，用哪个由 tag 决定。为什么这么设计？因为 I/O 路径上不能 kmalloc(GFP_KERNEL)，也不能在里面等锁。

八、bio：I/O 的基本单位 #

struct bio 描述一次进行中的块 I/O，记录这次 I/O 需要的一切：数据在内存哪里、磁盘起始扇区在哪、读还是写、完成了叫谁。字段在 include/linux/blk_types.h，要盯的只有这几个：

字段 含义
bi_next 链到下一个 bio，合并时用
bi_disk 这次 I/O 发往哪块盘（5.11 前是 bi_bdev，指向 block_device）
bi_opf 低 8 位是操作码 REQ_OP_*，高 24 位是标志 REQ_*
bi_partno 分区号，0 表示整块盘
bi_iter 当前遍历到的位置（扇区、剩余字节、第几个段）
bi_phys_segments 物理合并后的段数
bi_end_io I/O 完成回调，驱动/堆叠层都要调
bi_private 完成回调的私有数据
bi_vcnt 当前 bio_vec 个数
bi_max_vecs 容量上限
bi_io_vec 段数组，指向实际内存页
bi_inline_vecs 内联的小数组，省一次额外分配，必须是最后一个成员

bi_disk 这一项要留意版本：5.2.8 里是 struct gendisk *bi_disk；更早（4.x）是 struct block_device *bi_bdev；后续又有变化。写跨版本驱动时这行是要加宏的（未验证具体在哪一版切回）。

bio_vec 描述一页里的一段：

c
/*
 * was unsigned short, but we might as well be ready for > 64kB I/O pages
 */
struct bio_vec {
        struct page     *bv_page;
        unsigned int    bv_len;
        unsigned int    bv_offset;
};
  • bv_page：数据所在页的页描述符；
  • bv_len：这一段多少字节；
  • bv_offset：页内起始偏移。

遍历它靠 bvec_iter：

c
struct bvec_iter {
        sector_t                bi_sector;      /* device address in 512 byte sectors */
        unsigned int            bi_size;        /* residual I/O count */
        unsigned int            bi_idx;         /* current index into bvl_vec */
        unsigned int            bi_bvec_done;   /* number of bytes completed in current bvec */
};
  • bi_sector：本次 I/O 的起始扇区（512 字节为单位）；
  • bi_size：还差多少字节没传完；
  • bi_idx：当前处理到第几个 bio_vec；
  • bi_bvec_done：当前 bio_vec 里已经处理掉多少字节。

这四个字段合起来就是「数据源 + 数据长度 + 数据目的地」里的磁盘侧地址和数据长度；bi_io_vec[] 给出内存侧地址。驱动遍历 bio 的标准姿势是 bio_for_each_segment(bvec, bio, iter)，它在遍历过程中自动维护 iter，你只管按 bv_len 搬。

操作码在 enum req_opf 里（include/linux/blk_types.h），8 位编码：REQ_OP_BITS 8、REQ_FLAG_BITS 24，bi_opf / cmd_flags 的低 8 位是 op、高 24 位是 flag。要认的只有这几个：REQ_OP_READ = 0、REQ_OP_WRITE = 1、REQ_OP_FLUSH = 2（刷易失写缓存）、REQ_OP_DISCARD = 3、REQ_OP_ZONE_RESET = 6、REQ_OP_WRITE_SAME = 7、REQ_OP_WRITE_ZEROES = 9；32 以上留给透传（REQ_OP_SCSI_IN/OUT、REQ_OP_DRV_IN/OUT）。最省事的是直接用 bio_op(bio) / req_op(rq) 取 op、op_is_write() / op_is_flush() 判方向，别自己移位。 常用标志：

标志 含义
REQ_FAILFAST_DEV 设备错误不重试
REQ_FAILFAST_TRANSPORT 传输错误不重试
REQ_FAILFAST_DRIVER 驱动错误不重试
REQ_SYNC 同步 I/O
REQ_META 元数据 I/O
REQ_PRIO 提高优先级
REQ_NOMERGE 这个请求不许合并
REQ_INTEGRITY 带完整性负载
REQ_FUA 写完必须落盘
REQ_PREFLUSH I/O 前先刷盘
REQ_RAHEAD 预读，失败无所谓
REQ_BACKGROUND 后台 I/O
REQ_NOWAIT 不等待，拿不到就返回
REQ_HIPRI 高优先级，走 poll 队列

REQ_OP_SECURE_ERASE 已经被移除（2022 年 3 月 Christoph Hellwig 的补丁，理由是 blk-lib 按 discard 粒度对齐会漏掉区间，且只有 eMMC 一种硬件真支持），对应的 BLKSECDISCARD ioctl 和 QUEUE_FLAG_SECERASE 一并删掉。素材里出现 REQ_OP_SECURE_ERASE 的代码，直接删掉分支。

改方向的老接口在 5.2.8 还能用，但已废弃：早期 bio_rw(bio) 返回 READ/WRITE/READA，现在用 bio_data_dir(bio) 返回 READ/WRITE，或者用 op_is_write(bio_op(bio))。要素材里那段 switch (bio_rw(bio)) 的代码原封不动贴到 5.x，编译不过。

九、从文件系统到驱动的完整路径 #

把前面的结构串起来，一次读写的落点是这样：

text
write()/read()
  -> VFS -> 具体文件系统（ext4 等）决定要读写哪个块
  -> submit_bio(bio)                       block/blk-core.c
  -> submit_bio_noacct / generic_make_request   （5.9 前叫 generic_make_request）
  -> q->make_request_fn(q, bio)             = blk_mq_make_request()
        |
        +-- 尝试合并进当前进程 plug list
        +-- 尝试合并进 I/O 调度器队列 / 软件队列
        +-- 拿不到就分配 tag，把 bio 变成 request
        +-- 按场景派发：直接下发 / 挂 plug / 进调度器队列
        |
  -> blk_mq_ops.queue_rq(hctx, bd)           ← 驱动在这里干活
  -> 驱动搬数据，完成后 blk_mq_end_request() 或 bio_endio()

submit_bio() 只做两件事：记账（bio_has_data() 为真时按读写分别打 PGPGOUT / PGPGIN，task_io_account_read() 记读量，block_dump 非零时打一行调试日志），然后 return generic_make_request(bio); 原样转手。它不返回 I/O 结果，只给一个 blk_qc_t cookie。

generic_make_request()（5.9 起改名 submit_bio_noacct()）的目标是给堆叠设备留一条递归通路：先 generic_make_request_checks() 校验，然后判断 current->bio_list 是否为 NULL——非 NULL 说明当前进程已经在一个 make_request_fn 里，新 bio 直接挂到 current->bio_list[0] 尾部返回，避免递归加深栈；为 NULL 则初始化 bio_list_on_stack，进 do {} while 循环，blk_queue_enter() 成功后调 q->make_request_fn(q, bio)，再把回调过程中新产生的 bio 按「下层优先」排序，最后 blk_queue_exit()。普通单层设备这一轮循环只跑一次。

看这段有两个要点：

  1. 它不返回 I/O 结果，只返回一个 blk_qc_t cookie。成功/失败通过 bio->bi_end_io 异步通知。
  2. 真正干活的是 q->make_request_fn(q, bio)。blk-mq 下这个指针在 blk_mq_init_allocated_queue 里被设成 blk_mq_make_request。5.9 之后这个回调搬到 block_device_operations.submit_bio。

blk_mq_make_request() 的三段骨架（5.2.8，block/blk-mq.c）：

c
static blk_qc_t blk_mq_make_request(struct request_queue *q, struct bio *bio)
{
        const int is_sync = op_is_sync(bio->bi_opf);
        const int is_flush_fua = op_is_flush(bio->bi_opf);
        struct blk_mq_alloc_data data = { .flags = 0 };
        struct request *rq;
        struct request *same_queue_rq = NULL;
        blk_qc_t cookie;

        blk_queue_bounce(q, &bio);
        blk_queue_split(q, &bio);
        if (!bio_integrity_prep(bio))
                return BLK_QC_T_NONE;

        /* 1. 先试着合并 */
        if (!is_flush_fua && !blk_queue_nomerges(q) &&
            blk_attempt_plug_merge(q, bio, &same_queue_rq))
                return BLK_QC_T_NONE;
        if (blk_mq_sched_bio_merge(q, bio))
                return BLK_QC_T_NONE;

        /* 2. 合并不了就分配一个 request */
        rq_qos_throttle(q, bio);
        data.cmd_flags = bio->bi_opf;
        rq = blk_mq_get_request(q, bio, &data);
        if (unlikely(!rq))
                return BLK_QC_T_NONE;
        cookie = request_to_qc_t(data.hctx, rq);

        /* 3. 按场景派发 */
        if (unlikely(is_flush_fua)) {
                blk_mq_put_ctx(data.ctx);
                blk_mq_bio_to_request(rq, bio);
                blk_insert_flush(rq);
                blk_mq_run_hw_queue(data.hctx, true);
        } else if (current->plug) {
                blk_mq_bio_to_request(rq, bio);
                blk_add_rq_to_plug(current->plug, rq);
        } else if ((q->nr_hw_queues > 1 && is_sync) ||
                   (!q->elevator && !data.hctx->dispatch_busy)) {
                blk_mq_put_ctx(data.ctx);
                blk_mq_bio_to_request(rq, bio);
                blk_mq_try_issue_directly(data.hctx, rq, &cookie);
        } else {
                blk_mq_put_ctx(data.ctx);
                blk_mq_bio_to_request(rq, bio);
                blk_mq_sched_insert_request(rq, false, true, true);
        }

        return cookie;
}

驱动在整条链路的末端做两件事：从 bd->rq 拿到请求，搬数据，然后 blk_mq_end_request(rq, status) 或者对 bio 型驱动调 bio_endio(bio)。

另外，bio 是「上层视角」，request 是「调度视角」，bio 到 request 的转换动作叫 blk_mq_bio_to_request()：

c
void blk_mq_bio_to_request(struct request *rq, struct bio *bio)
{
        blk_rq_bio_prep(rq, bio);

        /* This can't fail, since GFP_NOIO includes __GFP_DIRECT_RECLAIM. */
        blk_rq_prep_clone(rq, bio);
}

转换时干了什么：rq->__sector = bio->bi_iter.bi_sector、rq->__data_len = bio->bi_iter.bi_size、rq->bio = rq->biotail = bio、rq->nr_phys_segments 从 bio 继承。合并进来的 bio 挂到 biotail->bi_next，biotail 往后挪。所以一个 request 的 __sector 永远是最靠前的那个 bio 的起点。

十、请求的合并与调度 #

合并是整个块层最省钱的优化。两个 bio 描述的磁盘空间正好首尾相接，打给硬件就是一次请求，而不是两次。

合并分两个位置：

位置 函数 特点
进程 plug list blk_attempt_plug_merge 不加锁，只有本进程能碰
I/O 调度器队列 elevator 的 bio_merge 需要 q->elevator 存在
软件队列 blk_mq_bio_list_merge 无调度器时用，有 ctx->lock

plug 机制是「攒一攒再一起发」：进程提交一个 bio 后，紧接着往往还有下一个，这些 request 先挂在 plug->mq_list 里，等攒够量或者进程主动 unplug 时统一推给块层。好处是不用每次去抢 request_queue 的锁。要注意 struct blk_plug 从 5.x 起合并了原来单队列和多队列两套（list 与 mq_list 合并为 mq_list），素材里两种叫法都出现过，是版本差异，不是笔误。

blk_attempt_plug_merge 的实现很短，值得看：

c
bool blk_attempt_plug_merge(struct request_queue *q, struct bio *bio,
                            struct request **same_queue_rq)
{
        struct blk_plug *plug;
        struct request *rq;
        struct list_head *plug_list;

        plug = current->plug;
        if (!plug)
                return false;

        plug_list = &plug->mq_list;

        list_for_each_entry_reverse(rq, plug_list, queuelist) {
                bool merged = false;

                if (rq->q == q && same_queue_rq) {
                        *same_queue_rq = rq;
                }

                if (rq->q != q || !blk_rq_merge_ok(rq, bio))
                        continue;

                switch (blk_try_merge(rq, bio)) {
                case ELEVATOR_BACK_MERGE:
                        merged = bio_attempt_back_merge(q, rq, bio);
                        break;
                case ELEVATOR_FRONT_MERGE:
                        merged = bio_attempt_front_merge(q, rq, bio);
                        break;
                case ELEVATOR_DISCARD_MERGE:
                        merged = bio_attempt_discard_merge(q, rq, bio);
                        break;
                default:
                        break;
                }

                if (merged)
                        return true;
        }

        return false;
}

三种合并方向：

c
bool bio_attempt_back_merge(struct request_queue *q, struct request *req,
                            struct bio *bio)
{
        const int ff = bio->bi_opf & REQ_FAILFAST_MASK;

        if (!ll_back_merge_fn(q, req, bio))
                return false;

        trace_block_bio_backmerge(q, req, bio);

        if ((req->cmd_flags & REQ_FAILFAST_MASK) != ff)
                blk_rq_set_mixed_merge(req);

        req->biotail->bi_next = bio;             /* 接到尾部 */
        req->biotail = bio;
        req->__data_len += bio->bi_iter.bi_size;

        blk_account_io_start(req, false);
        return true;
}

c
bool bio_attempt_front_merge(struct request_queue *q, struct request *req,
                             struct bio *bio)
{
        const int ff = bio->bi_opf & REQ_FAILFAST_MASK;

        if (!ll_front_merge_fn(q, req, bio))
                return false;

        trace_block_bio_frontmerge(q, req, bio);

        if ((req->cmd_flags & REQ_FAILFAST_MASK) != ff)
                blk_rq_set_mixed_merge(req);

        bio->bi_next = req->bio;              /* 插到头部 */
        req->bio = bio;

        req->__sector = bio->bi_iter.bi_sector;
        req->__data_len += bio->bi_iter.bi_size;

        blk_account_io_start(req, false);
        return true;
}

前合并和后合并的区别不只是挂头挂尾：前合并要改 __sector，因为请求的起点往前挪了；后合并只改 biotail 和长度。

不是所有 bio 都能合。合并前要过 blk_rq_merge_ok()：设备得是同一个、操作码得一致、REQ_NOMERGE 得没有、FLUSH/FUA 不能混、物理段数不能超 max_segments。无调度器路径上还限制只往回看 8 个请求，避免在合并上耗太多时间：

c
bool blk_mq_bio_list_merge(struct request_queue *q, struct list_head *list,
                           struct bio *bio)
{
        struct request *rq;
        int checked = 8;

        list_for_each_entry_reverse(rq, list, queuelist) {
                bool merged = false;

                if (!checked--)
                        break;

                if (!blk_rq_merge_ok(rq, bio))
                        continue;

                switch (blk_try_merge(rq, bio)) {
                ...
                }

                return merged;
        }

        return false;

调度器这边用 blk_mq_sched_bio_merge，它先看有没有 e->type->ops.bio_merge，有就交给调度器；没有就退化成往当前 CPU 的软件队列里试合并（要求 hctx->flags & BLK_MQ_F_SHOULD_MERGE，这也是 blk_mq_init_sq_queue 那个参数的作用）。

调度算法的世代更替：

版本 可用调度器 备注

十一、扇区与偏移的换算 #

这一节全是坑，单独拎出来。

基本单位：块层内部地址一律用 sector_t，单位 512 字节，和硬件的物理扇区大小无关。一个 4Kn 盘（物理扇区 4096），在块层眼里仍然是 8 个 512 字节的「扇区」。所以换算常量永远是 9：

c
#define SECTOR_SHIFT            9
#define SECTOR_SIZE             (1 << SECTOR_SHIFT)     /* 512 */

常用换算：

从 到 写法 说明
扇区 字节 sector << 9 等价 sector * 512
字节 扇区 bytes >> 9 必须保证是 512 的整数倍，否则丢余数
容量（字节） 容量（扇区） set_capacity(disk, bytes >> 9) set_capacity 收的是扇区数
磁盘偏移 扇区 (offset >> 9) + part->start_sect 分区必须加起始扇区
页数 扇区 pages << (PAGE_SHIFT - 9) 4K 页 = 8 个扇区

三个必须记住的细节：

  1. >> 9 只能用于 512 对齐的数。用户态 dd bs=1000 这种非对齐偏移，块层会先做 splice，塞进缓冲区再对齐下发。驱动里如果自己算偏移，务必校验 % 512 == 0。
  2. 分区要加偏移。bio 里的 bi_sector 是相对分区的，但很多驱动拿到的是整盘视角的 request —— 具体是哪一种取决于 request->part 和驱动写法。稳妥做法是统一用整盘偏移，把 hd_struct->start_sect 加进去。
  3. loff_t 别用 int。容量超过 2GB 之后 int << 9 直接溢出。bd_set_size(bdev, (loff_t)get_capacity(disk) << 9) 里那个强制转换不是装饰。

一个常见写法，来自 RamDisk 驱动，检查越界：

c
if ((bio->bi_sector << 9) + bio->bi_size > DISK_BYTES) {
        printk(KERN_ERR "bad request: block=%llu, count=%u\n",
               (unsigned long long)bio->bi_sector, bio->bi_size);
        bio_endio(bio, -EIO);
        return 0;
}

/* 转成设备内存里的指针 */
dsk_mem = disk_buf + (bio->bi_sector << 9);

注意 bio->bi_sector 是 sector_t，64 位，打印要用 %llu 加 (unsigned long long) 强转，否则在 32 位平台上是未定义行为。

请求视角的写法，来自 z2_queue_rq 那一类驱动，逐段推进：

c
unsigned long start = blk_rq_pos(req) << 9;   /* 起始扇区 -> 字节地址 */
unsigned long len = blk_rq_cur_bytes(req);    /* 当前段要传的字节数 */

while (len) {
        unsigned long addr = start & CHUNKMASK;       /* 切片内偏移 */
        unsigned long size = CHUNKSIZE - addr;        /* 本切片还能放多少 */
        void *buffer = bio_data(req->bio);

        if (len < size)
                size = len;

        addr += map[start >> CHUNKSHIFT];             /* 切片基址 + 偏移 */
        if (rq_data_dir(req) == READ)
                memcpy(buffer, (char *)addr, size);
        else
                memcpy((char *)addr, buffer, size);

        start += size;
        len -= size;
}

三个移位各管一件事：<< 9 是扇区到字节，>> CHUNKSHIFT（16）是字节到 64KB 切片序号，& CHUNKMASK 是切片内偏移。任何一处写错，表现都是「数据能读出来，但整体错位一个固定量」。

十二、驱动的注册：add_disk 与 del_gendisk #

注册一块盘要做的事，按顺序排开是这么一张表：

步骤 函数 作用 5.x 变化
1 register_blkdev(major, name) 申请块主设备号，major=0 让内核分配 仍然可用，但对有固定 major 的驱动可省
2 blk_mq_alloc_disk(&tag_set, queuedata) 一次拿到 gendisk + request_queue 5.11 才有；之前是 alloc_disk + blk_mq_init_sq_queue
3 填 major / first_minor / disk_name / fops 描述这块盘 queue 不再手工赋值
4 set_capacity(disk, sectors) 设容量，单位扇区 不变
5 add_disk(disk) 注册到 device model、sysfs、/dev、扫分区 不变
6 del_gendisk(disk) 反向操作 不变
7 put_disk(disk) / blk_cleanup_disk(disk) 释放引用 5.11 起用 blk_cleanup_disk
8 unregister_blkdev(major, name) 注销主设备号 不变

register_blkdev 本质上只是分配一个主设备号，不碰任何设备状态。register_blkdev() 的逻辑很短：拿 block_class_lock 互斥锁；major == 0 时从 major_names[] 尾部往前找第一个空槽，找到就把它当返回的主设备号，找不到返回 -EBUSY；major >= BLKDEV_MAJOR_MAX 返回 -EINVAL；否则 kmalloc 一个 struct blk_major_name，strlcpy 名字，链进 major_names[major % 255] 的链表，撞号返回 -EBUSY。全程只在维护一张哈希表：

c
#define BLKDEV_MAJOR_HASH_SIZE 255
static struct blk_major_name {
        struct blk_major_name *next;
        int major;
        char name[16];
} *major_names[BLKDEV_MAJOR_HASH_SIZE];

要点：

  • major=0 时从高位往低位找空槽，返回分配到的号；指定主设备号时成功返回 0，失败返回负值；
  • 注册成功后在 /proc/devices 的 Block devices 段能看到这个名字；
  • 名字字段是 char name[16]，超过会被 strlcpy 截断；
  • 素材里写「块设备主设备号理论上有 2^32 个，不必小于 255」不够准确：register_blkdev 的入参上限是 BLKDEV_MAJOR_MAX，而被索引的哈希表只有 255 个槽位。具体上限以那个版本的 include/linux/kdev_t.h 为准（未验证 5.2.8 的确切数值）。

注销是反操作：

注销是反操作：按 major % 255 找到链表，比对 major 和 name，都匹配才摘链并 kfree，名字对不上就 WARN_ON(1)（照样返回，属于「调用者写错了」的防御）。 名字对不上会 WARN_ON(1) 但照样返回，这属于「调用者写错了」的防御。

add_disk 做了什么，这是整章最值得看清的一段。5.2.8 里 add_disk 是 device_add_disk(parent, disk, groups) 的包装，实际逻辑在 __device_add_disk()。按顺序拆成八步：

  1. GENHD_FL_UP 置位——之后 __blkdev_get 会检查这个标志，没置位就打不开；
  2. blk_alloc_devt() 给 0 号分区分配设备号，回填 major 和 first_minor。所以驱动里不一定非要自己算设备号，major 填 0、first_minor 填 0 让它分配也是可行写法；
  3. 隐藏盘（GENHD_FL_HIDDEN）跳过 sysfs 与扫描，同时打上 GENHD_FL_NO_PART_SCAN；
  4. blk_register_region() 建立「设备号 → gendisk」的映射，落在 bdev_map 里；
  5. register_disk() 把 0 号分区的 device 加进 sysfs，然后首次打开整盘块设备并扫描分区表；
  6. blk_register_queue() 建 /sys/block/<name>/queue/ 子目录；
  7. 补一次 blk_get_queue() 引用，保证队列活得和 disk 一样久；
  8. 注册磁盘事件（disk_add_events）与完整性信息（blk_integrity_add）。

device_add_disk() 只是带着 register_queue = true 调它一次，没有别的逻辑。

register_disk() 里最关键的两步：bdev->bd_invalidated = 1 强制标脏，然后 blkdev_get(bdev, FMODE_READ, NULL) 首次打开触发 rescan_partitions()，最后 dev_set_uevent_suppress(ddev, 0) 才放开 uevent 上报。分区扫描是被「打开」这个动作触发的，不是 add_disk 直接去读扇区。这也是为什么 set_capacity() 必须放在 add_disk() 前面——扫分区要发真实 I/O，容量为 0 时 register_disk() 直接 goto exit 跳过扫描。

这里有个容易忽略的前提：register_disk() 在 device_add(ddev) 之后才建 holders / slaves 两个 kobject 目录，分区节点的父设备就是 disk_to_dev(disk)。所以 add_disk 之后 /sys/block/<name>/ 下的目录结构已经全了，udev 拿到 KOBJ_ADD 就能直接用。

del_gendisk 做反向拆除：

del_gendisk() 倒着拆：先删所有分区（disk_part_iter 反向遍历 + invalidate_partition + bdev_unhash_inode + delete_partition），再处理 0 号分区，set_capacity(disk, 0)，清掉 GENHD_FL_UP（此后打开返回 -ENXIO）；接着注销 bdi、blk_unregister_queue()、blk_unregister_region() 撤设备号映射、blk_invalidate_devt()，最后 device_del(disk_to_dev(disk))。整段在 disk->lookup_sem 写锁里完成，为的是等在途的磁盘查找退出，所以它不能在 I/O 上下文里调。

del_gendisk 不释放 gendisk 本身，它只是「下线」。内存回收靠 put_disk()（减引用）或 5.11 起的 blk_cleanup_disk()（减引用 + 清队列）。只调 del_gendisk 不调 put_disk 就是泄漏，这是卸载后 rmmod 卡住、重装报 -EBUSY 的头号原因。

设备号到 gendisk 的映射靠 bdev_map：

c
struct kobj_map {
        struct probe {
                struct probe *next;
                dev_t dev;
                unsigned long range;
                struct module *owner;
                kobj_probe_t *get;
                int (*lock)(dev_t, void *);
                void *data;
        } *probes[255];
        struct mutex *lock;
};

每个 probe 记一个设备号区间（dev + range）和对应数据（data，指向 gendisk），链在 probes[major % 255] 上，按 range 升序排列，这样子区间可以覆盖父区间。查表就是 bdev_map → probes[] → 链 → 找到 gendisk。

十三、分区与磁盘几何 #

分区的数据结构在第五章给过（disk_part_tbl / hd_struct）。这里说流程和几何。

扫描流程走 rescan_partitions()：

rescan_partitions() 的顺序：删旧分区（drop_partitions）→ 调 revalidate_disk 给驱动一次更新容量的机会 → check_disk_size_change 校正 i_size → 清 bd_invalidated → check_partition() 读分区表 → 越界检查（from >= get_capacity、from + size > get_capacity、zoned 对齐）→ add_partition() 逐个建 → 发 KOBJ_CHANGE uevent。越界本身不致命，size 会被裁到 get_capacity(disk) - from，分区表写坏的盘也能挂上一部分；但起始扇区越界（from >= get_capacity）那一项直接 continue 跳过。

check_partition() 遍历 check_part[] 数组（check_part_dos()、check_part_gpt() 等），每个 check 函数都去读第 0 扇区或 LBA1 验证魔数。所以分区表识别失败的根因多数在第 0 扇区读不到：驱动有 bug、容量设 0、或者 minors=1 根本不允许扫。

add_partition() 给每个分区建 hd_struct、device_initialize、device_add，设备名按规则生成：

c
dname = dev_name(ddev);
if (isdigit(dname[strlen(dname) - 1]))
        dev_set_name(pdev, "%sp%d", dname, partno);   /* mmcblk0 -> mmcblk0p1 */
else
        dev_set_name(pdev, "%s%d", dname, partno);    /* sda -> sda1 */

这条规则解释了为什么 eMMC 分区叫 mmcblk0p1 而 SATA 盘叫 sda1。

磁盘几何只在实现了 getgeo 的设备上才有意义。RamDisk 的例子：

c
static int ramdisk_getgeo(struct block_device *bdev, struct hd_geometry *geo)
{
        geo->heads = 2;
        geo->cylinders = 32;
        geo->sectors = RAMDISK_SIZE / (2 * 32 * SECTOR_SIZE);
        return 0;
}

heads=2、cylinders=32，2MB 的盘算出来每柱面 64 个扇区。这个几何直接决定 fdisk 的行为：柱面只有 1~32，最多只能划 2 个主分区，第 3 个直接失败；分区边界也不落在物理柱面边界上，fdisk 会打 Partition 1 does not end on cylinder boundary 警告。这不是驱动写错了，是几何填得不合理。真实磁盘驱动从硬盘的 identify 信息里取几何，不用自己编。

分区数的硬限制是 minors：

alloc_disk(n) 的 minors 效果
1 只有 0 号分区，不能分区，可分区数为 0
2 只能有 1 个分区
16 最多 15 个分区，MBR 的经典配置
0 交给内核用 GENHD_FL_EXT_DEVT 动态分配设备号

素材里那个 fdisk w 保存失败的案例，根因就是 alloc_disk(1)，改成大于 2 的值立刻恢复。

2）核心处理函数

c
static int sbull_make_request(struct request_queue *q, struct bio *bio)
{
        struct bio_vec *bvec;
        int i;
        void *dsk_mem;

        /* 越界检查：起始偏移 + 长度 不能超过设备容量 */
        if ((bio->bi_sector << 9) + bio->bi_size > SBULL_BYTES) {
                printk(KERN_ERR SBULL_DISKNAME
                        ": bad request: block=%llu, count=%u\n",
                        (unsigned long long)bio->bi_sector, bio->bi_size);
                bio_endio(bio, -EIO);
                return 0;
        }

        dsk_mem = sbull_data + (bio->bi_sector << 9);

        bio_for_each_segment(bvec, bio, i) {
                void *iovec_mem
                        = kmap(bvec->bv_page) + bvec->bv_offset;

                if (bio_rw(bio) == WRITE)
                        memcpy(dsk_mem, iovec_mem, bvec->bv_len);
                else
                        memcpy(iovec_mem, dsk_mem, bvec->bv_len);

                kunmap(bvec->bv_page);
                dsk_mem += bvec->bv_len;
        }

        bio_endio(bio, 0);
        return 0;
}

这段是全文最值得逐行读的代码。它做了一个块设备驱动的最小数据通路：

  • bio->bi_sector << 9 得到字节偏移，直接当 RAM 数组下标；
  • bio_for_each_segment 遍历内存段，逐段 memcpy；
  • 读完/写完调 bio_endio(bio, 0)，块层收到通知继续往上走。

kmap / kunmap 这对操作在 32 位时代是必须的（高端内存需要临时映射），64 位内核上 page_address() 就够，但为了兼容低端/高端内存混用，用 kmap 不会错。bio_for_each_segment 的第三个参数在 2.6 是 int i，3.x 之后要传 struct bvec_iter iter。

一个 5.15+ 能编译的骨架（未在真机验证，只保证接口对齐）：

c
#include <linux/module.h>
#include <linux/blk-mq.h>
#include <linux/blkdev.h>

#define RAM_BYTES   (16 * 1024 * 1024)
#define RAM_NAME    "sbull"

static unsigned char *ram_data;
static struct blk_mq_tag_set tag_set;
static struct gendisk *ram_disk;

static blk_status_t ram_queue_rq(struct blk_mq_hw_ctx *hctx,
                                 const struct blk_mq_queue_data *bd)
{
        struct request *rq = bd->rq;
        struct req_iterator iter;
        struct bio_vec bvec;
        unsigned long pos = blk_rq_pos(rq) << 9;
        int dir = rq_data_dir(rq);

        blk_mq_start_request(rq);

        rq_for_each_segment(bvec, rq, iter) {
                unsigned char *buf = kmap_local_page(bvec.bv_page) + bvec.bv_offset;

                if (pos + bvec.bv_len > RAM_BYTES) {
                        kunmap_local(buf);
                        blk_mq_end_request(rq, BLK_STS_IOERR);
                        return BLK_STS_OK;
                }

                if (dir == WRITE)
                        memcpy(ram_data + pos, buf, bvec.bv_len);
                else
                        memcpy(buf, ram_data + pos, bvec.bv_len);

                kunmap_local(buf);
                pos += bvec.bv_len;
        }

        blk_mq_end_request(rq, BLK_STS_OK);
        return BLK_STS_OK;
}

static const struct blk_mq_ops ram_mq_ops = {
        .queue_rq = ram_queue_rq,
};

static const struct block_device_operations ram_fops = {
        .owner = THIS_MODULE,
};

初始化路径：

c
static int __init ram_init(void)
{
        int ret;

        ram_data = vzalloc(RAM_BYTES);
        if (!ram_data)
                return -ENOMEM;

        tag_set.ops = &ram_mq_ops;
        tag_set.nr_hw_queues = 1;
        tag_set.queue_depth = 128;
        tag_set.numa_node = NUMA_NO_NODE;
        tag_set.flags = BLK_MQ_F_SHOULD_MERGE;

        ret = blk_mq_alloc_tag_set(&tag_set);
        if (ret)
                goto err_free;

        ram_disk = blk_mq_alloc_disk(&tag_set, NULL);
        if (IS_ERR(ram_disk)) {
                ret = PTR_ERR(ram_disk);
                goto err_tag;
        }

        ram_disk->fops = &ram_fops;
        strscpy(ram_disk->disk_name, RAM_NAME, DISK_NAME_LEN);
        set_capacity(ram_disk, RAM_BYTES >> 9);   /* 必须在 add_disk 之前 */

        ret = add_disk(ram_disk);
        if (ret)
                goto err_disk;

        return 0;

err_disk:
        put_disk(ram_disk);
err_tag:
        blk_mq_free_tag_set(&tag_set);
err_free:
        vfree(ram_data);
        return ret;
}

差异清单，注意这几处：

  • 用 rq_for_each_segment 遍历请求的段，而不是 bio_for_each_segment 遍历 bio 的段。因为一个 request 里能装好几个 bio，后者只覆盖第一个；
  • set_capacity 必须在 add_disk 之前，否则扫分区时容量是 0，直接跳过；
  • blk_mq_alloc_disk 之后不再有 disk->queue = q 这一行；
  • add_disk 在 5.11 之后有返回值（int），旧版本是 void，所以 ret = add_disk(...) 这行跨版本要加判断。

十五、错误处理与热插拔 #

错误从哪一层返回，要分清三处：

位置 表达方式 含义
queue_rq 返回 BLK_STS_RESOURCE / BLK_STS_DEV_RESOURCE 状态码 资源忙，块层把请求挂回 hctx->dispatch 或软队列重试
queue_rq 返回 BLK_STS_IOERR 状态码 硬错误，直接失败
blk_mq_end_request(rq, status) 状态码 完成并上报结果
bio_endio(bio) / bio_endio(bio, -EIO) errno bio 型驱动专用，4.3 前要额外传 bio->bi_size
fops->open() 返回 -ENXIO errno 设备不在（介质被拔）
fops->open() 返回 -ERESTARTSYS errno 告诉块层重试打开

最常踩的是返回码用错。queue_rq 不能返回 -EIO（那是 errno），必须返回 blk_status_t。返回 -EIO 会被当成一个无意义的状态值，块层行为不确定。

越界检查是所有 RamDisk/自定义驱动的必修课，两种位置各有讲究：

c
/* bio 型 */
if ((bio->bi_sector << 9) + bio->bi_size > DISK_BYTES)
        bio_endio(bio, -EIO);

/* request 型 */
if ((blk_rq_pos(rq) << 9) + blk_rq_bytes(rq) > DISK_BYTES)
        blk_mq_end_request(rq, BLK_STS_IOERR);

第二个用的是 blk_rq_bytes(rq)（整个请求），有驱动用 blk_rq_cur_bytes(rq)（当前段），后者只检查一段，请求尾部越界查不出来。

错误注入：内核自带 CONFIG_FAIL_MAKE_REQUEST，可以按比例让下发直接失败，用来验证上层文件系统和应用有没有正确处理 I/O 错误。这是测错误路径最省事的办法，比拔盘强（未验证 该配置在 5.9 之后的 debugfs 路径名）。

热插拔分两种场景：

介质可换（U 盘、SD 卡、光驱）。设备本身在，介质换了：

  1. 驱动在 check_events() 里检测到介质变化，调 bdev_disk_changed(disk, false)；
  2. 内核去调 revalidate_disk() 让驱动更新容量；
  3. 触发 rescan_partitions()；
  4. 老的分区 device 全部删掉、新的加进来，uevent 上报。

设备消失（USB 拔掉、SD 控制器移除）：

  1. 停止队列，让新请求快速失败；
  2. del_gendisk(disk) 下线；
  3. put_disk() 减引用。

add_disk 之后有 I/O 在跑的时候不能直接 put_disk，del_gendisk 会先拿 lookup_sem 写锁，这就是它要持写锁的原因。

udev 与分区自动挂载：add_disk 里 dev_set_uevent_suppress(ddev, 1) 把 uevent 压到分区扫完再发，这样 uevent 处理器拿到 /dev/sdX 的时候分区节点已经齐了。如果驱动自己提前 kobject_uevent(KOBJ_ADD)，用户态就会拿到一个还没有分区的设备，自动挂载工具白跑一次。

/sys/block/<dev>/size 是最快的容量核对手段：值等于 bytes >> 9。如果它是 0，set_capacity 那一行没生效或者放错了位置。

十七、易错点速查 #

# 坑 正确做法
1 拿 5.0 之前的教程照抄 blk_init_queue / make_request_fn 5.0 起只用 blk-mq：填 blk_mq_ops.queue_rq
2 bio_endio(bio, 0) 两参数写法 4.3 起是 bio_endio(bio)
3 bio->bi_sector / bio->bi_size 4.14 起重构成 bio->bi_iter.bi_sector / .bi_size
4 bio_rw(bio) 返回 READ/WRITE/READA 用 bio_data_dir(bio) 或 op_is_write(bio_op(bio))
5 disk->queue = q（5.11+） 队列在 blk_mq_alloc_disk 内部挂好，别再赋
6 set_capacity 放在 add_disk 之后 必须在之前，否则扫分区时容量是 0
7 容量按字节传 set_capacity 收扇区数：bytes >> 9
8 用 int 装 bytes << 9 用 loff_t / sector_t，超过 2GB 必溢出
9 alloc_disk(1) 之后去 fdisk 分区 minors 至少 2 才能有 1 个分区，16 是常规配置
10 只调 del_gendisk 不调 put_disk 两个都要调，否则 rmmod 卡死
11 queue_rq 返回 errno（-EIO） 返回 blk_status_t（BLK_STS_IOERR）
12 错误分支里直接 return 不调完成 每条路径都要 blk_mq_end_request / bio_endio
13 用 bio_for_each_segment 遍历 request request 型驱动用 rq_for_each_segment
14 bio_for_each_segment(bv, bio, int i) 第三个参数是 struct bvec_iter，不是 int
15 越界检查用 blk_rq_cur_bytes 用 blk_rq_bytes 检查整个请求
16 分区访问忘了加 start_sect 分区偏移要加上分区起始扇区
17 REQ_OP_SECURE_ERASE 分支照抄 2022 年 3 月后的内核已删掉这个操作码
18 register_blkdev 返回值当成功判断 指定 major 时返回 0 是成功，major=0 时返回分配到的号
19 在驱动里期待自己扫分区 分区由 register_disk 打开设备时触发扫描
20 unsigned char data[16MB] 定义成静态数组 模块 data 段太大，用 vmalloc / vzalloc
21 用 %d 打印 sector_t 用 %llu 加 (unsigned long long)
22 fops 忘了 .owner = THIS_MODULE 必填，否则模块引用计数错乱
