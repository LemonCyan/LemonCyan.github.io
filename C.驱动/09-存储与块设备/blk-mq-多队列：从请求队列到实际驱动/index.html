一、为什么要 blk-mq：单队列的瓶颈 #

传统块层是为机械盘设计的。HDD 随机 IO 性能很差，吞吐几百 IOPS，延迟毫秒级 —— 瓶颈在硬件，内核那点软件开销根本不算事。

所以当时的设计很朴素：每个块设备一个请求队列 request_queue，一把 q->queue_lock 管住整个队列。这就是 blk-sq（block simple queue）单队列架构。

局面被 SSD 和 NVMe 改掉了。这类器件没有机械部件，能高并发随机访问，百万级甚至千万级 IOPS 起步。软件开销一上来就顶不住，瓶颈从硬件挪到内核。多核体系下 blk-sq 的开销来自三个地方：

开销来源 具体表现 多核下为什么更糟
请求队列锁竞争 每次往调度器队列插入/删除 request 都要抢 q->queue_lock；排序、调度也要抢 高 IOPS 场景多线程同时提交，锁竞争剧烈
硬件中断 高 IOPS 等于高中断数。完成一次 I/O 常需要两次中断：存储器件一次，IPI 核间中断一次 中断在多核间乱飞，软中断排队
远端内存访问 提交 I/O 的 CPU 与收中断的 CPU 不是同一个、且不共享缓存时，抢锁过程要跨节点访问内存 NUMA 机器上代价被放大

blk-mq 的思路就是把一把大锁拆成每个 CPU 一把小锁，再把提交路径和完成路径钉在同一个 CPU 上，顺带把硬件队列这层抽象让给驱动。两层队列一分摊，锁竞争和远端内存访问同时缓解，Block Layer 的 IOPS 吞吐量才跟得上器件。

一句话总结拆锁逻辑：blk-sq 里 N 个 CPU 抢 1 把锁，blk-mq 里 N 个 CPU 各用各的 ctx 锁，只在向硬件队列派发的那一刻才碰 hctx 锁。

二、从 request_fn 到 MQ：架构的改变 #

先把两种架构并排放。

维度 单队列 blk-sq 多队列 blk-mq
队列结构 1 个 request_queue，1 个 request_fn 每 CPU 1 个 sw queue（ctx）+ N 个 hw queue（hctx）
驱动接口 q->request_fn，驱动自己从队列取 request blk_mq_ops->queue_rq，块层把 request 推给驱动
同步手段 全局 q->queue_lock ctx->lock + hctx->lock + sbitmap 原子位图
bio 入口 make_request_fn（驱动可自定义） 固定为 blk_mq_make_request
request 分配 运行时申请，走 slab 初始化时预分配，靠 tag 索引取用
IO 调度 单一调度器队列 每 hctx 一个调度器实例，elevator 挂在 queue 上
生命周期终点 blk_cleanup_queue() blk_cleanup_queue() + blk_mq_free_tag_set()

历史上这条迁移走了六年多：

  • 内核 3.13（2014）blk-mq 代码合入主线；
  • 内核 3.16 成为完整特性；
  • 内核 5.0 blk-sq 代码（含基于 blk-sq 的 I/O 调度器）被完全移除，MQ 成为 Block Layer 的默认也是唯一路径。

两个直接影响驱动的变化：

  1. make_request_fn 接口删除。5.0 之后 request_queue 上不再有 make_request_fn 字段给你塞自定义函数，blk_queue_make_request() 的语义也变了，不再是「注册你自己的 make_request」，而是内部设置 blk_mq_make_request。想绕开块层做 bio 直通，得用 blk_mq 提供的其他钩子，不要指望复刻 4.x 的老写法。
  2. q->request_fn 彻底没了。所有块设备驱动，包括 RAM 盘、loop、NVMe、virtio-blk，统一用 blk_mq_ops。

本篇下面所有结构体、函数都取自 Linux 5.2.8，见 include/linux/blk-mq.h、block/blk-mq.c、block/blk-mq-tag.c、block/blk-mq-sched.c。

版本注记：5.2.8 的 request_queue 里还留着 make_request_fn 字段和 const struct blk_mq_ops *mq_ops，但真正用的是 q->mq_ops，make_request_fn 由 blk_queue_make_request(q, blk_mq_make_request) 内部改写。6.x 里这一组字段被重整为 q->tag_set、q->mq_ops + q->limits 分离，具体字段名各版本有出入，字段级差异本篇不逐个断言，标「未验证」。

三、软件队列与硬件队列 #

blk-mq 用两层队列把锁竞争分散开，分层职责很清晰。

层 内核结构体 数量 谁锁它 存放什么
软件队列（sw queue / ctx） struct blk_mq_ctx 等于 CPU 数，per-CPU ctx->lock，只被本 CPU 抢 本 CPU 提交的 request 链表 rq_lists[]
硬件派发队列（hw queue / hctx） struct blk_mq_hw_ctx set->nr_hw_queues，多数器件为 1，NVMe 可 >1 hctx->lock hctx->dispatch 派发链表 + hctx->tags

软件队列是 per-CPU 变量，blk_mq_ctx 用 per_cpu_ptr(q->queue_ctx, cpu) 取。每个 CPU 提交的 I/O 只进自己的链表，所以提交路径上根本不存在跨 CPU 竞争 —— 同一个 CPU 上的多个进程之间仍然会抢 ctx->lock，这一点别忽略。

硬件队列对应器件真正的提交通路。blk_mq_hw_ctx 的 __percpu 之外的字段都住在这一个结构里，最要紧的几个：dispatch（已派发但驱动没收下的 request 链表）、tags（无调度器时的 tag 集合）、sched_tags（有调度器时的 tag 集合）、queue_num（硬件队列号）、ctxs/nr_ctx（挂在这个 hctx 上的 ctx 数组）。

派发方向是单向的：sw queue → hw queue → 器件。软件队列往硬件队列派发的动作由 blk_mq_run_hw_queue() 驱动，映射关系在驱动初始化时一次性建好，之后不再变（nr_hw_queues 跑着改属于热插拔/超配场景，走 blk_mq_update_nr_hw_queues()，本篇不展开）。

两种队列之外还有第三种位置容易被漏：plug list。它是进程私有的，current->plug，不加锁就能做 bio merge。plug 不是必须的 —— 5.2.8 里 sys_read 用了 plug，sys_write 已经不用，具体看调用方有没有 blk_start_plug() / blk_finish_plug() 配对。

四、tag 与请求的生命周期 #

tag 是 blk-mq 的身份证号。一个 request 只有拿到 tag 才能做真正的 I/O 传输，没有 tag 就只能躺在链表里等着。

tag 不是动态分配的堆对象，而是预先撒好的 request 池的数组下标。这个池子在硬件队列初始化时一次性建好，之后整台机器跑多久就用多久。

c
/* block/blk-mq-tag.h，Linux 5.2.8 */
struct blk_mq_tags {
        unsigned int nr_tags;              /* 每个硬件队列的深度，含 reserved */
        unsigned int nr_reserved_tags;     /* 预留 tag 个数 */
        atomic_t active_queues;
        struct sbitmap_queue bitmap_tags;  /* 普通 tag 位图 */
        struct sbitmap_queue breserved_tags; /* 预留 tag 位图 */
        struct request **rqs;              /* 已分配出去的 request，长度 nr_tags */
        struct request **static_rqs;       /* 预分配的 request 池，长度 nr_tags */
        struct list_head page_list;        /* 用来串 alloc_pages 出来的页 */
};

几个字段的含义和分工：

字段 含义 容易搞错的地方
nr_tags 该硬件队列的总深度，等于 set->queue_depth 含预留，不是「可用普通 tag 数」
nr_reserved_tags 预留 tag 数，给内存回收等关键路径用 为 0 时走 BLK_MQ_REQ_RESERVED 会 WARN_ON_ONCE 并失败
bitmap_tags 管理 static_rqs[nr_reserved_tags .. nr_tags) 这一段 下标偏移是 nr_reserved_tags，不是 0
breserved_tags 管理 static_rqs[0 .. nr_reserved_tags) 这一段 只在 BLK_MQ_REQ_RESERVED 时用
rqs 当前 tag 上挂着的 request 指针 派发失败释放 tag 后这里也要清
static_rqs 真正的 request 池，物理内存连续分配 数组长度是 nr_tags，不是 queue_depth - reserved
page_list 记录 alloc_pages_node 拿到的页，释放时要一页页还 忘了它还就等于漏内存

一次「bio 变成能做 I/O 的 request」要走四步：从 bitmap_tags 或 breserved_tags 抢一个 tag；以 static_rqs[tag] 取出预分配的 request；用 blk_mq_rq_ctx_init() 把 q / mq_ctx / mq_hctx / cmd_flags / 起始时间填好；最后 rqs[tag] = rq，把 tag 和 request 双向绑定。

中间有个坑要记：blk_mq_get_tag() 返回的是相对位图的下标，found_tag: return tag + tag_offset;，tag_offset 在普通路径上是 nr_reserved_tags。所以 static_rqs[tag_offset + tag] 才是那个 request。驱动不该碰这一层，但调试 rqs[] / static_rqs[] 对不上号时，先回头查有没有漏掉这个偏移。

tag 的生命周期跟 request 不完全一样，是三条互相独立的线：

阶段 谁动的 标志
申请内部 tag blk_mq_get_request()，有调度器时 rq->tag = -1，rq->internal_tag = tag
申请驱动 tag blk_mq_get_driver_tag()，派发前 rq->tag = tag；若驱动繁忙失败则回退到 -1
释放 tag 完成或 requeue 时 rq->tag 复位；rqs[tag] 清空

internal_tag 和 tag 并存是 blk-mq 一个反直觉的设计：有 I/O 调度器时，request 先进调度器，此时只占「内部名额」（internal tag，位图来自 sched_tags），真正要发给硬件时再从 hctx->tags 里要一个 driver tag。两套 tag 分开，调度器才能持有超过硬件深度的 request。没有调度器时，rq->tag 直接就是 driver tag，internal_tag = -1。

版本注记：6.x 里 internal_tag 仍在，但 tag 分配路径（blk_mq_get_tag()、sbitmap 换 sbitmap_queue 的细节、BLK_MQ_F_TAG_SHARED 改为 BLK_MQ_F_TAG_HCTX_SHARED）有变化，跨版本读代码要对齐字段名。本篇所有断言都只覆盖 5.2.8。

五、struct blk_mq_tag_set：驱动要填什么 #

blk_mq_tag_set 是驱动递给块层的「器件 I/O 特征说明书」。一个物理设备注册时，所有块层需要知道的东西都在这一个结构里。

c
/* include/linux/blk-mq.h，Linux 5.2.8 */
struct blk_mq_tag_set {
        struct blk_mq_queue_map map[HCTX_MAX_TYPES];
        unsigned int            nr_maps;        /* nr entries in map[] */
        const struct blk_mq_ops *ops;
        unsigned int            nr_hw_queues;   /* nr hw queues across maps */
        unsigned int            queue_depth;    /* max hw supported */
        unsigned int            reserved_tags;
        unsigned int            cmd_size;       /* per-request extra data */
        int                     numa_node;
        unsigned int            timeout;
        unsigned int            flags;          /* BLK_MQ_F_* */
        void                    *driver_data;
        struct blk_mq_tags      **tags;
        struct mutex            tag_list_lock;
        struct list_head        tag_list;
};

全字段逐个说明：

字段 含义 驱动要填吗 注意点
map[HCTX_MAX_TYPES] 每种 hctx 类型一份的 ctx→hctx 映射表 由 blk_mq_alloc_tag_set() 填 mq_map 指针 数组下标是 HCTX_TYPE_*
nr_maps map[] 里有几份生效的映射，取值 [1, HCTX_MAX_TYPES] 要（0 会被当成 1） 只用 default 类型就填 1
ops 驱动回调集合 blk_mq_ops 必须 ops->queue_rq 为空直接被拒
nr_hw_queues 硬件队列数 必须，且非 0 多数器件 1；单 map 且大于 CPU 数会被压到 nr_cpu_ids
queue_depth 每个硬件队列深度，含 reserved 必须，且非 0 > BLK_MQ_MAX_DEPTH（10240）会被截断并打印提示
reserved_tags 每队列的预留 tag 数 要（常用 0，或留 2~8 个） 必须满足 queue_depth >= reserved_tags + BLK_MQ_TAG_MIN
cmd_size 每个 request 额外分配的驱动私有区大小 要（不需要就 0） 拿法见下面的 blk_mq_rq_to_pdu()
numa_node 设备所在的 NUMA 节点 要（不知道填 NUMA_NO_NODE 即 -1） 分配 request 和 queue 内存都按它走，避免远端访问
timeout 请求超时，单位 jiffies 要（0 则块层默认 30s） blk_mq_init_allocated_queue() 里 set->timeout ? set->timeout : 30 * HZ
flags BLK_MQ_F_* 组合 要 BLK_MQ_F_SHOULD_MERGE 决定支不支持 merge；BLK_MQ_F_BLOCKING 允许 queue_rq 睡眠
driver_data 驱动私有数据指针 可选 块层不碰
tags nr_hw_queues 个 blk_mq_tags * 不要填 blk_mq_alloc_tag_set() 内部 kcalloc_node 分配
tag_list_lock 保护 tag_list 的互斥锁 不要填 同上函数里 mutex_init
tag_list 挂到全局 tag set 链表 不要填 同上函数里 INIT_LIST_HEAD

cmd_size 是实战里最常用的一个字段。给 NVMe 提交队列条目、给自研卡留 DMA 描述符，都靠它：块层在分配 request 时多分配 cmd_size 字节，紧跟在 struct request 后面，驱动用 blk_mq_rq_to_pdu(rq) 取。

queue_depth 的含义要用准：它是单个硬件队列的深度。nr_hw_queues = 8 且 queue_depth = 64 时一共预分配 512 个 request。这个数字决定内存占用，也决定硬件能压多少在飞。填大了 blk_mq_alloc_rq_maps() 会逐次减半重试（见第八章），最后拿到的深度未必是你写的那个数。

numa_node 的影响面比看起来大：它决定 blk_alloc_queue_node() 从哪个节点拿 request_queue，也决定 blk_mq_alloc_rq_map() / blk_mq_alloc_rqs() 在哪个节点上分配 rqs / static_rqs / 页。填错就是全程远端内存访问，跑分能差出一截。

六、struct blk_mq_ops：驱动要实现的回调 #

blk_mq_ops 是驱动行为的抽象层。字段不算多，但真正必填的只有一个。

c
/* include/linux/blk-mq.h，Linux 5.2.8 */
struct blk_mq_ops {
        queue_rq_fn             *queue_rq;
        commit_rqs_fn           *commit_rqs;
        get_budget_fn           *get_budget;
        put_budget_fn           *put_budget;
        timeout_fn              *timeout;
        poll_fn                 *poll;
        complete_fn             *complete;
        init_hctx_fn            *init_hctx;
        exit_hctx_fn            *exit_hctx;
        init_request_fn         *init_request;
        exit_request_fn         *exit_request;
        void (*initialize_rq_fn)(struct request *rq);
        busy_fn                 *busy;
        map_queues_fn           *map_queues;
#ifdef CONFIG_BLK_DEBUG_FS
        void (*show_rq)(struct seq_file *m, struct request *rq);
#endif
};

逐个回调的作用、是否必填、什么时候被调：

回调 作用 必填 调用时机
queue_rq 把块层给的 request 交给硬件 必填 每次派发，__blk_mq_issue_directly() / blk_mq_dispatch_rq_list() 调用
commit_rqs 驱动用 bd->last 判断何时提交时，出错了靠它踢一脚硬件 条件必填 有 bd->last 语义时；没实现则块层一条条发
get_budget 派发前预留配额 与 put_budget 成对 __blk_mq_try_issue_directly() 里先调
put_budget 释放配额 与 get_budget 成对 派发失败、或完成时
timeout 超时处理 选了 超时工作时；返回 BLK_EH_DONE / BLK_EH_RESET_TIMER
poll 轮询指定 tag 的完成状态 选了 QUEUE_FLAG_POLL 且用户走轮询 I/O 时
complete 标记 request 完成（驱动有自己的完成队列时用） 选了 块层准备结束一个 request 时
init_hctx hctx 建立后让驱动分配配套结构 选了 blk_mq_alloc_and_init_hctx() 里
exit_hctx 对应的拆除 选了 blk_mq_exit_hctx()
init_request 每个预分配 request 的驱动侧初始化 选了 blk_mq_alloc_rqs() 里逐个调；tag ≥ queue_depth 的那批是给 flush request 用的
exit_request 对应拆除 选了 释放 request 池前
initialize_rq_fn blk_get_request() 内部初始化 选了 走 blk_get_request 的路径
busy 返回队列当前是否繁忙 选了 块层判断要不要继续往这里塞
map_queues 覆写默认的 ctx→hctx 映射算法 选了 blk_mq_update_queue_map() 里
show_rq debugfs 里打印请求细节 可选 只在 CONFIG_BLK_DEBUG_FS 下编译进来

两个成对约束会直接 -EINVAL 拒绝注册：

c
/* block/blk-mq.c，Linux 5.2.8，节选 */
if (!set->ops->queue_rq)
        return -EINVAL;
if (!set->ops->get_budget ^ !set->ops->put_budget)
        return -EINVAL;

第二句是异或：只填一个就报错，两个都不填可以，两个都填也行。别只填 get_budget 忘了 put_budget，报错信息很难定位到这里。

只填 queue_rq 的最小实例如下，z2ram 就是这么干的：

c
static const struct blk_mq_ops z2_mq_ops = {
        .queue_rq       = z2_queue_rq,
};

这已经足够让驱动跑起来。nr_hw_queues = 1 + BLK_MQ_F_SHOULD_MERGE + 单一 queue_rq，就是 RAM 盘、loop 这类设备的全部配置。

七、队列映射：CPU 到硬件队列 #

映射表 blk_mq_queue_map 只有三个字段，却决定整台机器的 I/O 走向。

c
/* include/linux/blk-mq.h，Linux 5.2.8 */
struct blk_mq_queue_map {
        unsigned int *mq_map;      /* 长度 nr_cpu_ids，下标 CPU 号，元素 hctx 号 */
        unsigned int nr_queues;    /* 本类型可用的硬件队列数 */
        unsigned int queue_offset; /* 本类型在全局 hctx 编号里的起始偏移 */
};

blk_mq_tag_set.map[] 是它的数组，每种 hctx 类型一份。三种类型的语义完全不同：

类型 编号 派发什么 谁来触发
HCTX_TYPE_DEFAULT 0 普通写、flush、绝大多数请求 blk_mq_make_request() 常规路径
HCTX_TYPE_READ 1 只读请求（NVMe 读写共用队列时写会堵读，所以要分开） blk_mq_map_queue() 按 REQ_OP_READ 判断
HCTX_TYPE_POLL 2 REQ_HIPRI 的轮询请求 同上，按 REQ_HIPRI 判断

类型怎么选出来，逻辑就这几行：

c
/* include/linux/blk-mq.h，Linux 5.2.8 */
static inline struct blk_mq_hw_ctx *blk_mq_map_queue(struct request_queue *q,
                                                     unsigned int flags,
                                                     struct blk_mq_ctx *ctx)
{
        enum hctx_type type = HCTX_TYPE_DEFAULT;
        if (flags & REQ_HIPRI)
                type = HCTX_TYPE_POLL;
        else if ((flags & REQ_OP_MASK) == REQ_OP_READ)
                type = HCTX_TYPE_READ;
        return ctx->hctxs[type];
}

所以 ctx->hctxs[3] 各指向一个 blk_mq_hw_ctx，ctx->index_hw[3] 各存一个 hctx 编号。只有 default 类型时，hctxs[READ] / hctxs[POLL] 和 hctxs[DEFAULT] 指向同一个硬件队列。

默认映射算法有两套，由驱动有没有实现 map_queues 决定：

c
/* block/blk-mq.c，Linux 5.2.8 */
static int blk_mq_update_queue_map(struct blk_mq_tag_set *set)
{
        if (set->ops->map_queues && !is_kdump_kernel()) {
                int i;
                for (i = 0; i < set->nr_maps; i++)
                        blk_mq_clear_mq_map(&set->map[i]);
                return set->ops->map_queues(set);
        } else {
                BUG_ON(set->nr_maps > 1);
                return blk_mq_map_queues(&set->map[HCTX_TYPE_DEFAULT]);
        }
}

注意 BUG_ON(set->nr_maps > 1)：没实现 map_queues 却又声明了多份 map，内核直接 BUG。想用 READ / POLL 分队列，必须自己实现 map_queues。

自己实现时的标准写法，源码注释里就给了模板：外层 for (queue = 0; queue < set->nr_hw_queues; queue++) 取 mask = get_cpu_mask(queue)，内层 for_each_cpu(cpu, mask) 写 set->map[x].mq_map[cpu] = queue。重映射前必须 blk_mq_clear_mq_map() 清表，否则某个 CPU 会挂在已经不存在的 hctx 上。

两套映射容易混：

名字 位置 内容 什么时候建
map[i].mq_map[cpu] struct blk_mq_queue_map CPU → hctx 编号的数字表 blk_mq_update_queue_map()
blk_mq_map_swqueue() block/blk-mq.c 按上表把 ctx->hctxs[] / ctx->index_hw[] 指针与编号落实，并填充 hctx->ctxs[] / hctx->nr_ctx blk_mq_init_allocated_queue() 末尾

一句话区分：前者是「编号表」，后者是「运行时真正的双向指针绑定」。

八、blk_mq_init_queue 的完整流程 #

从驱动的 z2_init() 到拿到一个能用的 request_queue，中间这一串调用链是 blk-mq 初始化期的全貌。

8.1 tag_set 的分配：blk_mq_alloc_tag_set #

c
/* block/blk-mq.c，Linux 5.2.8，校验段 + 会改写 set 的几处 */
int blk_mq_alloc_tag_set(struct blk_mq_tag_set *set)
{
        BUILD_BUG_ON(BLK_MQ_MAX_DEPTH > 1 << BLK_MQ_UNIQUE_TAG_BITS);

        if (!set->ops->get_budget ^ !set->ops->put_budget) return -EINVAL;  /* 成对约束 */

                set->queue_depth = BLK_MQ_MAX_DEPTH;
        }
        if (!set->nr_maps)
                set->nr_maps = 1;
        else if (set->nr_maps > HCTX_MAX_TYPES)
                return -EINVAL;
        if (is_kdump_kernel()) {                           /* kdump 下极限缩水 */
                set->nr_hw_queues = 1;
                set->nr_maps = 1;
                set->queue_depth = min(64U, set->queue_depth);
        }

                set->nr_hw_queues = nr_cpu_ids;            /* 单 map 不需要比 CPU 多 */
        /* 之后依次：tags 指针数组 -> 每份 map 的 mq_map -> blk_mq_update_queue_map()

        return 0;
}

校验 !nr_maps 补成 1

8.2 tags 与 request 池的分配 #

blk_mq_alloc_rq_maps() 会带重试：分配失败就把深度砍一半再试。三个函数的分工是：__blk_mq_alloc_rq_maps() 遍历每个 hctx 调 __blk_mq_alloc_rq_map()，后者先 blk_mq_alloc_rq_map() 建 tags 骨架、再 blk_mq_alloc_rqs() 撒真 request。下面是后两个的节选：

c
/* block/blk-mq.c，Linux 5.2.8，节选 */
static int blk_mq_alloc_rq_maps(struct blk_mq_tag_set *set)
{
        unsigned int depth = set->queue_depth;
        int err;
        do {
                err = __blk_mq_alloc_rq_maps(set);   /* 逐个 hctx 调下面两个函数 */
                if (!err)
                        break;
                set->queue_depth >>= 1;              /* 失败就把深度砍一半再试 */
                if (set->queue_depth < set->reserved_tags + BLK_MQ_TAG_MIN) {
                        err = -ENOMEM;
                        break;
                }
        } while (set->queue_depth);
        if (!set->queue_depth || err) {
                pr_err("blk-mq: failed to allocate request map\n");
                return -ENOMEM;
        }
        if (depth != set->queue_depth)
                pr_info("blk-mq: reduced tag depth (%u -> %u)\n", depth, set->queue_depth);
        return 0;
}
/* 只分配 blk_mq_tags 和两个指针数组，不碰 request 本体 */
struct blk_mq_tags *blk_mq_alloc_rq_map(struct blk_mq_tag_set *set,
                                        unsigned int hctx_idx,
                                        unsigned int nr_tags,
                                        unsigned int reserved_tags)
{
        int node = blk_mq_hw_queue_to_node(&set->map[HCTX_TYPE_DEFAULT], hctx_idx);
        if (node == NUMA_NO_NODE)                 /* 节点从 DEFAULT map 反查 */
                node = set->numa_node;
        tags = blk_mq_init_tags(nr_tags, reserved_tags, node,
                                BLK_MQ_FLAG_TO_ALLOC_POLICY(set->flags));
        if (!tags)
                return NULL;
        tags->rqs = kcalloc_node(nr_tags, sizeof(struct request *),
                                 GFP_NOIO | __GFP_NOWARN | __GFP_NORETRY, node);
        tags->static_rqs = kcalloc_node(nr_tags, sizeof(struct request *),
                                        GFP_NOIO | __GFP_NOWARN | __GFP_NORETRY, node);
        /* 任一失败：先 kfree(rqs) 再 blk_mq_free_tags(tags)，然后返回 NULL */
        return tags;
}
/* 真正把 request 撒出来：按页批量切，rq_size 里含 cmd_size */
int blk_mq_alloc_rqs(struct blk_mq_tag_set *set, struct blk_mq_tags *tags,
                     unsigned int hctx_idx, unsigned int depth)
{
        unsigned int i, j, entries_per_page, max_order = 4;
        size_t rq_size, left;
        int node = blk_mq_hw_queue_to_node(&set->map[HCTX_TYPE_DEFAULT], hctx_idx);
        if (node == NUMA_NO_NODE)
                node = set->numa_node;
        INIT_LIST_HEAD(&tags->page_list);
        /* 请求本体 + 驱动 payload，按 cacheline 向上取整 */
        rq_size = round_up(sizeof(struct request) + set->cmd_size, cache_line_size());
        left = rq_size * depth;
        for (i = 0; i < depth; ) {
                int this_order = max_order;
                struct page *page;
                int to_do;
                void *p;
                while (this_order && left < order_to_size(this_order - 1))
                        this_order--;
                /* order 不够就降阶再试，GFP_ZERO 保证槽位干净 */
                page = alloc_pages_node(node,
                        GFP_NOIO | __GFP_NOWARN | __GFP_NORETRY | __GFP_ZERO, this_order);
                if (!page)
                        goto fail;
                page->private = this_order;
                list_add_tail(&page->lru, &tags->page_list);   /* 记帐，释放要还 */
                p = page_address(page);
                kmemleak_alloc(p, order_to_size(this_order), 1, GFP_NOIO);
                entries_per_page = order_to_size(this_order) / rq_size;
                to_do = min(entries_per_page, depth - i);
                left -= to_do * rq_size;
                for (j = 0; j < to_do; j++) {
                        struct request *rq = p;
                        tags->static_rqs[i] = rq;
                        if (blk_mq_init_request(set, rq, hctx_idx, node)) {
                                tags->static_rqs[i] = NULL;   /* 内部会调 ops->init_request */
                                goto fail;
                        }
                        p += rq_size;
                        i++;
                }
        }
        return 0;
fail:
        blk_mq_free_rqs(set, tags, hctx_idx);
        return -ENOMEM;
}

cmd_size 就是在这里生效的：rq_size 把驱动私有区一起算进每个槽位，blk_mq_init_request() 内部调 ops->init_request() 让你初始化它。所以 cmd_size 定的值一经初始化就不能变，改它必须重建整个 tag set。

8.3 request_queue 的初始化：blk_mq_init_allocated_queue #

c
/* block/blk-mq.c，Linux 5.2.8，节选 */
struct request_queue *blk_mq_init_allocated_queue(struct blk_mq_tag_set *set,
                                                  struct request_queue *q)
{
        q->mq_ops = set->ops;                             /* 第一件事：标记为 MQ */
        q->poll_cb = blk_stat_alloc_callback(blk_mq_poll_stats_fn,
                                             blk_mq_poll_stats_bkt,
                                             BLK_MQ_POLL_STATS_BKTS, q);
        if (!q->poll_cb)
                goto err_exit;
        if (blk_mq_alloc_ctxs(q))                         /* per-CPU ctx 数组 */
                goto err_poll;
        blk_mq_sysfs_init(q);                             /* q->mq_kobj + sw queue kobj */
        q->nr_queues = nr_hw_queues(set);
        q->queue_hw_ctx = kcalloc_node(q->nr_queues, sizeof(*(q->queue_hw_ctx)),
                                                GFP_KERNEL, set->numa_node);
        if (!q->queue_hw_ctx)
                goto err_sys_init;
        INIT_LIST_HEAD(&q->unused_hctx_list);
        spin_lock_init(&q->unused_hctx_lock);
        blk_mq_realloc_hw_ctxs(set, q);                   /* 建每个 hctx */
        if (!q->nr_hw_queues)
                goto err_hctxs;
        INIT_WORK(&q->timeout_work, blk_mq_timeout_work);
        blk_queue_rq_timeout(q, set->timeout ? set->timeout : 30 * HZ);
        q->tag_set = set;
        q->queue_flags |= QUEUE_FLAG_MQ_DEFAULT;
        if (set->nr_maps > HCTX_TYPE_POLL &&
            set->map[HCTX_TYPE_POLL].nr_queues)
                blk_queue_flag_set(QUEUE_FLAG_POLL, q);
        q->sg_reserved_size = INT_MAX;
        INIT_DELAYED_WORK(&q->requeue_work, blk_mq_requeue_work);
        INIT_LIST_HEAD(&q->requeue_list);
        spin_lock_init(&q->requeue_lock);
        blk_queue_make_request(q, blk_mq_make_request);   /* bio 入口从此固定 */
        /* Do this after blk_queue_make_request() overrides it... */
        q->nr_requests = set->queue_depth;
        q->poll_nsec = BLK_MQ_POLL_CLASSIC;
        blk_mq_init_cpu_queues(q, set->nr_hw_queues);     /* 初始化每个 ctx */
        blk_mq_add_queue_tag_set(set, q);                 /* 挂进 set->tag_list */
        blk_mq_map_swqueue(q);                            /* ctx <-> hctx 双向绑定 */
        if (!(set->flags & BLK_MQ_F_NO_SCHED)) {          /* 除非显式禁用调度器 */
                int ret = elevator_init_mq(q);
                if (ret)
                        return ERR_PTR(ret);
        }
        return q;
        /* err_hctxs / err_sys_init / err_poll / err_exit 四级回滚，略 */
}

上面每一步的作用就写在注释里，按序号读一遍即可。重点看三步：第 5 步建 hctx、第 8 步固定 bio 入口、第 10 步建调度器。

第 5 步的 blk_mq_realloc_hw_ctxs() 对每个 hctx 的顺序，就是一份「hctx 初始化清单」：

text
hctx->nr_active = 0;
hctx->run_work  -> blk_mq_run_work_fn;
hctx->ctxs      = kmalloc_array_node(nr_cpu_ids, sizeof(void *), gfp, node);
hctx->nr_ctx    = 0;
hctx->queue     = q;
spin_lock_init(&hctx->dispatch_wait_lock);
spin_lock_init(&hctx->lock);
INIT_LIST_HEAD(&hctx->hctx_list);
INIT_LIST_HEAD(&hctx->dispatch);

它还有个 NUMA 早退分支：if (hctxs[i] && (hctxs[i]->numa_node == node)) continue; —— hctx 已存在且节点没变就跳过重建，热更新 nr_hw_queues 时靠这个避免全量拆建。

第 9 步的 blk_mq_init_cpu_queues() 末尾那段值得抄：

for (j = 0; j < set->nr_maps; j++) {
        hctx = blk_mq_map_queue_type(q, j, i);
        if (nr_hw_queues > 1 && hctx->numa_node == NUMA_NO_NODE)
                hctx->numa_node = local_memory_node(cpu_to_node(i));

只有 nr_hw_queues > 1 才把 hctx 的 NUMA 节点落到本地内存节点；单硬件队列时保持设备本节点，这是有意的取舍。前面那套逐个字段初始化的动作则是 __ctx->cpu = i、spin_lock_init(&__ctx->lock)、把 rq_lists[HCTX_MAX_TYPES] 逐个 INIT_LIST_HEAD。

8.4 便捷封装：blk_mq_init_sq_queue #

多数单队列设备不愿意手写上面这一串，所以块层给了封装：

c
/* block/blk-mq.c，Linux 5.2.8，节选 */
struct request_queue *blk_mq_init_sq_queue(struct blk_mq_tag_set *set,
                                           const struct blk_mq_ops *ops,
                                           unsigned int queue_depth,
                                           unsigned int set_flags)
{
        struct request_queue *q;
        int ret;
        memset(set, 0, sizeof(*set));   /* 注意：cmd_size / timeout 等一并清 0 */
        set->ops = ops;
        set->nr_hw_queues = 1;          /* 强制单硬件队列 */
        set->nr_maps = 1;               /* 强制单 map */
        set->queue_depth = queue_depth;
        set->numa_node = NUMA_NO_NODE;  /* 强制不指定节点 */
        set->flags = set_flags;
        ret = blk_mq_alloc_tag_set(set);
        if (ret)
                return ERR_PTR(ret);
        q = blk_mq_init_queue(set);
        if (IS_ERR(q)) {
                blk_mq_free_tag_set(set);
                return q;
        }
        return q;
}

四个参数：set（调用方提供的 blk_mq_tag_set 存储）、ops、queue_depth、set_flags。它的隐含设定要记牢，因为这几项你没法通过它传：

  • nr_hw_queues 强制 1，nr_maps 强制 1；
  • numa_node 强制 NUMA_NO_NODE；
  • reserved_tags、cmd_size、timeout、driver_data 全被 memset 清 0；
  • 出错时帮你调 blk_mq_free_tag_set()，分配 q 失败时也一并退了 tag set。

所以只要你的设备有多个硬件队列、需要 cmd_size、需要预留 tag 或要指定 NUMA 节点，就得走 blk_mq_alloc_tag_set() + blk_mq_init_queue() 两条调用，不能用 sq 封装。z2ram 什么特殊需求都没有，一行 blk_mq_init_sq_queue(&tag_set, &z2_mq_ops, 16, BLK_MQ_F_SHOULD_MERGE) 就够。

版本注记：blk_mq_init_sq_queue() 在较新内核（6.x）里已被删除。现在等价的路径是 blk_mq_alloc_tag_set() + blk_mq_alloc_disk()。后者一次返回 gendisk 和 request_queue（通过出参），省掉 alloc_disk() + blk_mq_init_queue() + 手工赋 disk->queue 三步，配套释放是 del_gendisk() + put_disk()，queue 的生命周期跟着 gendisk 走。5.x 里 alloc_disk() + blk_mq_init_queue() 还是标准写法，两种写法不要混用。

九、请求的分发：queue_rq #

queue_rq 是块层唯一强制的驱动回调，签名固定：

c
blk_status_t (*queue_rq)(struct blk_mq_hw_ctx *hctx,
                         const struct blk_mq_queue_data *bd);

bd 里就两个东西：bd->rq 是这次的 request，bd->last 表示「这是本批次的最后一条」。要不要用 last 做批量提交由驱动自己定，用了就得实现 commit_rqs。

从 submit_bio() 到 queue_rq() 只隔一层：generic_make_request() 调 q->make_request_fn，也就是 blk_mq_make_request()。函数前半段是固定动作，按顺序背下来即可：blk_queue_bounce()（DMA 地址限制）→ blk_queue_split()（超限 bio 拆分，拆出的部分重新走 generic_make_request）→ bio_integrity_prep()（完整性校验）→ blk_attempt_plug_merge()（试合并到 plug）→ blk_mq_sched_bio_merge()（试合并到调度器或 sw queue）→ rq_qos_throttle()（限流）→ blk_mq_get_request()（拿 request + tag）。任一步合并成功就直接 return BLK_QC_T_NONE，根本不产生新 request。后半段是五条分支：

c
/* block/blk-mq.c，Linux 5.2.8，节选：四条派发分支 */
        plug = current->plug;
        if (unlikely(is_flush_fua)) {                     /* 分支一：flush/FUA 绕过调度器 */
                blk_mq_put_ctx(data.ctx);
                blk_mq_bio_to_request(rq, bio);
                blk_insert_flush(rq);
                blk_mq_run_hw_queue(data.hctx, true);
        } else if (plug && (q->nr_hw_queues == 1 || q->mq_ops->commit_rqs)) {
                /* 分支二：单队列或驱动支持 bd->last，攒进 plug->mq_list */
                unsigned int request_count = plug->rq_count;
                struct request *last = NULL;
                blk_mq_put_ctx(data.ctx);
                blk_mq_bio_to_request(rq, bio);
                if (request_count)
                        last = list_entry_rq(plug->mq_list.prev);
                if (request_count >= BLK_MAX_REQUEST_COUNT || (last &&
                    blk_rq_bytes(last) >= BLK_PLUG_FLUSH_SIZE))
                        blk_flush_plug_list(plug, false);  /* 攒够了，一次下发 */
                blk_add_rq_to_plug(plug, rq);
        } else if (plug && !blk_queue_nomerges(q)) {      /* 分支三：plug 里只留一条 */
                blk_mq_bio_to_request(rq, bio);
                if (list_empty(&plug->mq_list))
                        same_queue_rq = NULL;
                if (same_queue_rq) {
                        list_del_init(&same_queue_rq->queuelist);
                        plug->rq_count--;
                }
                blk_add_rq_to_plug(plug, rq);
                blk_mq_put_ctx(data.ctx);
                if (same_queue_rq) {                      /* 旧的同队列请求直发 */
                        data.hctx = same_queue_rq->mq_hctx;
                        blk_mq_try_issue_directly(data.hctx, same_queue_rq, &cookie);
                }
        } else if ((q->nr_hw_queues > 1 && is_sync) || (!q->elevator &&
                        !data.hctx->dispatch_busy)) {     /* 分支四：直发 */
                blk_mq_put_ctx(data.ctx);
                blk_mq_bio_to_request(rq, bio);
                blk_mq_try_issue_directly(data.hctx, rq, &cookie);
        } else {                                          /* 分支五：进调度器 */
                blk_mq_put_ctx(data.ctx);
                blk_mq_bio_to_request(rq, bio);
                blk_mq_sched_insert_request(rq, false, true, true);
        }
        return cookie;

一句话对照五条分支：flush/FUA 绕过调度器进 flush 队列；有 plug 且单队列或驱动实现了 commit_rqs 就攒进 plug->mq_list，到阈值一次下发；有 plug 且允许 merge 时 plug 里最多留一条，旧的同队列请求直发；多队列同步 I/O 或无调度器且 hctx 不忙走 blk_mq_try_issue_directly，省一次入队出队；其余进调度器排队。

同步判定的规则很干脆：

c
/* include/linux/blk_types.h，Linux 5.2.8 */
static inline bool op_is_sync(unsigned int op)
{
        return (op & REQ_OP_MASK) == REQ_OP_READ ||
                (op & (REQ_SYNC | REQ_FUA | REQ_PREFLUSH));
}

所有读都算同步，加上带 REQ_SYNC / REQ_FUA / REQ_PREFLUSH 的写。读多写少的负载更容易走直发路径，原因就在这里。

真正落到 queue_rq 的三个入口，最要紧的是返回值处理：

c
/* block/blk-mq.c，Linux 5.2.8，节选 */
        ret = q->mq_ops->queue_rq(hctx, &bd);     /* 驱动在这里被调用 */
        switch (ret) {
        case BLK_STS_OK:
                blk_mq_update_dispatch_busy(hctx, false);
                *cookie = new_cookie;
                break;
        case BLK_STS_RESOURCE:
        case BLK_STS_DEV_RESOURCE:
                blk_mq_update_dispatch_busy(hctx, true);
                __blk_mq_requeue_request(rq);     /* 释放 tag，挂回 dispatch */
                break;
        default:
                blk_mq_update_dispatch_busy(hctx, false);
                *cookie = BLK_QC_T_NONE;
                break;
        }
        return ret;

返回值语义必须背下来，这是驱动和块层之间唯一的握手协议：

返回 含义 块层动作
BLK_STS_OK 已受理（不代表已完成） 标记 hctx 不忙，继续
BLK_STS_RESOURCE 缺内核资源，暂时发不出去 标记 hctx 忙，释放 tag，request 挂回 hctx->dispatch
BLK_STS_DEV_RESOURCE 设备侧资源耗尽 同上
其他（如 BLK_STS_IOERR） 这条已经失败了 视为派发结束，由块层走完成路径

直发路径的前置检查，__blk_mq_try_issue_directly()：

c
/* block/blk-mq.c，Linux 5.2.8 */
static blk_status_t __blk_mq_try_issue_directly(struct blk_mq_hw_ctx *hctx,
                                                struct request *rq,
                                                blk_qc_t *cookie,
                                                bool bypass_insert, bool last)
{
        struct request_queue *q = rq->q;
        bool run_queue = true;
        if (blk_mq_hctx_stopped(hctx) || blk_queue_quiesced(q)) {
                run_queue = false;
                bypass_insert = false;
                goto insert;
        }
        if (q->elevator && !bypass_insert)
                goto insert;
        if (!blk_mq_get_dispatch_budget(hctx))
                goto insert;
        if (!blk_mq_get_driver_tag(rq)) {
                blk_mq_put_dispatch_budget(hctx);
                goto insert;
        }
        return __blk_mq_issue_directly(hctx, rq, cookie, last);
insert:
        if (bypass_insert)
                return BLK_STS_RESOURCE;
        blk_mq_request_bypass_insert(rq, run_queue);
        return BLK_STS_OK;
}

这里出现了第二个「拿 tag」的动作，很多人会疑惑为什么前面 blk_mq_get_request() 已经拿过还要再拿：

c
/* block/blk-mq.c，Linux 5.2.8，节选 */
bool blk_mq_get_driver_tag(struct request *rq)
{
        struct blk_mq_alloc_data data = {
                .q = rq->q,
                .hctx = rq->mq_hctx,
                .flags = BLK_MQ_REQ_NOWAIT,
                .cmd_flags = rq->cmd_flags,
        };
        bool shared;
        if (rq->tag != -1)                /* 已经拿到 driver tag，直接返回 */
                goto done;
        if (blk_mq_tag_is_reserved(data.hctx->sched_tags, rq->internal_tag))
                data.flags |= BLK_MQ_REQ_RESERVED;
        shared = blk_mq_tag_busy(data.hctx);
        rq->tag = blk_mq_get_tag(&data);  /* 重新申请 */
        if (rq->tag >= 0) {
                if (shared) {
                        rq->rq_flags |= RQF_MQ_INFLIGHT;
                        atomic_inc(&data.hctx->nr_active);
                }
                data.hctx->tags->rqs[rq->tag] = rq;
        }
done:
        return rq->tag != -1;
}

答案是：派发失败会把 tag 还回去。request 被塞进 hctx->dispatch 等待时，rq->tag 已经是 -1，真正要发的时候得重新要一个。这解释了为什么 request 里 tag 和 internal_tag 两个字段必须分开存 —— 前者是可以反复申请、反复释放的，后者在整个生命周期里稳定。

blk_mq_run_hw_queue() 是另一条派发入口，粒度是整个硬件队列：

c
/* block/blk-mq.c，Linux 5.2.8 */
bool blk_mq_run_hw_queue(struct blk_mq_hw_ctx *hctx, bool async)
{
        int srcu_idx;
        bool need_run;
        hctx_lock(hctx, &srcu_idx);
        need_run = !blk_queue_quiesced(hctx->queue) &&
                blk_mq_hctx_has_pending(hctx);
        hctx_unlock(hctx, srcu_idx);
        if (need_run) {
                __blk_mq_delay_run_hw_queue(hctx, async, 0);
                return true;
        }
        return false;
}

async 是这里的核心分岔：

c
/* block/blk-mq.c，Linux 5.2.8 */
static void __blk_mq_delay_run_hw_queue(struct blk_mq_hw_ctx *hctx, bool async,
                                        unsigned long msecs)
{
        if (unlikely(blk_mq_hctx_stopped(hctx)))
                return;
        if (!async && !(hctx->flags & BLK_MQ_F_BLOCKING)) {  int cpu = get_cpu();
                if (cpumask_test_cpu(cpu, hctx->cpumask)) {
                        __blk_mq_run_hw_queue(hctx);
                        put_cpu();
                        return;
                }
                put_cpu();
        }
        kblockd_mod_delayed_work_on(blk_mq_hctx_next_cpu(hctx), &hctx->run_work,
                                    msecs_to_jiffies(msecs));
}

同步走：当前 CPU 在这个 hctx 的 cpumask 里、且驱动没标 BLK_MQ_F_BLOCKING，就在原地直接跑 __blk_mq_run_hw_queue()。否则一律丢给 kblockd 内核线程异步跑。这就是「CPU 亲和」在派发路径上的第一个体现。

__blk_mq_run_hw_queue() 里还有一道 DEBUG 级检查：run queue from wrong CPU %d, hctx %s，并附 dump_stack()。看到它说明驱动在错误的 CPU 上同步调用了派发，或者 hctx 的 cpumask 配得跟中断亲和不一致。

最后是真正的派发总调度，blk_mq_sched_dispatch_requests()：

c
/* block/blk-mq-sched.c，Linux 5.2.8 */
void blk_mq_sched_dispatch_requests(struct blk_mq_hw_ctx *hctx)
{
        struct request_queue *q = hctx->queue;
        struct elevator_queue *e = q->elevator;
        const bool has_sched_dispatch = e && e->type->ops.dispatch_request;
        LIST_HEAD(rq_list);
        if (unlikely(blk_mq_hctx_stopped(hctx) || blk_queue_quiesced(q)))
                return;
        hctx->run++;
        /* 先把 hctx->dispatch 上的残留搬到 rq_list */
        if (!list_empty_careful(&hctx->dispatch)) {
                spin_lock(&hctx->lock);
                if (!list_empty(&hctx->dispatch))
                        list_splice_init(&hctx->dispatch, &rq_list);
                spin_unlock(&hctx->lock);
        }
        if (!list_empty(&rq_list)) {
                blk_mq_sched_mark_restart_hctx(hctx);
                if (blk_mq_dispatch_rq_list(q, &rq_list, false)) {
                        if (has_sched_dispatch)
                                blk_mq_do_dispatch_sched(hctx);
                        else
                                blk_mq_do_dispatch_ctx(hctx);
                }
        } else if (has_sched_dispatch) {
                blk_mq_do_dispatch_sched(hctx);      /* 有调度器：从调度器队列取 */
        } else if (hctx->dispatch_busy) {
                blk_mq_do_dispatch_ctx(hctx);        /* 设备忙：一条条从 sw queue 取 */
        } else {
                blk_mq_flush_busy_ctxs(hctx, &rq_list);   /* sw queue 一次扫空 */
                blk_mq_dispatch_rq_list(q, &rq_list, false);
        }
}

四种情况一目了然：

优先顺序 情况 派发来源
1 hctx->dispatch 非空 先把残留的派发队列清干净，再考虑调度器
2 有调度器 dispatch_request blk_mq_do_dispatch_sched()，从调度器队列取
3 hctx 忙 blk_mq_do_dispatch_ctx()，一条条从软件队列取
4 都不忙 blk_mq_flush_busy_ctxs() 把各 sw queue 一次扫空，再批量派发

为什么非得先清 dispatch？注释说得明白：从调度器里取出来的 request 就不能再 merge 或排序了，所以能留在调度器里就尽量留着。但当 dispatch 队列里还有货时，得先发完，否则低队列深度的设备就永远只发出一小部分。

最终都要落到 blk_mq_dispatch_rq_list()，它才是调 queue_rq() 的地方。派发失败时把剩余 request 挪回 hctx->dispatch 并启异步传输。

plug 的收尾也是同一条路：blk_flush_plug_list() 检查 plug->mq_list 非空就转给 blk_mq_flush_plug_list()；后者先按 plug->rq_count > 2 && plug->multiple_queues 决定要不要 list_sort（按磁盘位置排，让下发前还能合并），再按 (q, ctx, hctx) 三元组分组，每组交给 blk_mq_sched_insert_requests()。blk_mq_sched_insert_requests() 对无调度器的快速路径是：hctx 不忙、没调度器、不要求异步，就 blk_mq_try_issue_list_directly() 直接下发，省掉一次 sw queue 的入队出队；否则 blk_mq_insert_requests() 进软件队列，末尾 blk_mq_run_hw_queue(hctx, run_queue_async) 顶一脚。

十、完成路径：blk_mq_complete_request #

派发出去只是开始，request 怎么结束才是驱动最容易写错的地方。

z2ram 的做法简单粗暴 —— memcpy 是同步的，硬件没有真正意义上的异步完成，所以它在 queue_rq 里搬完数据就直接调 blk_mq_end_request()：

c
        spin_unlock_irq(&z2ram_lock);
        blk_mq_end_request(req, BLK_STS_OK);
        return BLK_STS_OK;

这段代码能跑，但有两个必须说清的边界。

第一，blk_mq_start_request() 已经在前面调过。它会启动 request 的超时计时；如果你在 queue_rq 里同步完成，最好让块层走「快速完成」的判定，否则每个请求都要等超时工作来收尾。z2ram 用 BLK_MQ_F_SHOULD_MERGE 单队列 + 同步完成，实测跑得通（见第十四章日志）。

第二，blk_mq_end_request() 是「块层侧结束」，适合在 request 真正完成后、且处在可以安全回调的上下文时调用。真实的异步设备（NVMe、virtio-blk、自研卡）走的是一条更长的链：完成中断里从自己的完成队列取出 tag / status → 用 tags->rqs[tag] 找回 request → 走 rq->end_io 或块层默认完成 → 最后落到 blk_mq_end_request()，或者抬软中断走 blk_mq_complete_softirq()。

三个函数的职责边界：

函数 干什么 你在哪用
blk_mq_start_request(rq) 记起点、启动超时计时 queue_rq 里，接受 request 后第一件事
blk_mq_end_request(rq, status) 结束 request、统计、返 tag、唤醒 queue_rq 同步完成时，或完成中断里
blk_mq_complete_request(rq) 请求远程 CPU 完成（需要时会发 IPI 到提交的 CPU） 完成发生在别的 CPU、想让完成回到提交 CPU 时

blk_mq_complete_request() 的存在意义是让完成也亲和提交 CPU。派发出去的 CPU 和收中断的 CPU 常常不是同一个，如果完成时直接处理，就把 request 的数据结构和 bio 的 bi_end_io 都拉到远端节点上了。complete 回调（blk_mq_ops.complete）就是给驱动在这一步插手用的：块层准备「标记完成」的时候先问你一句。

版本注记：5.2.8 里 blk_mq_complete_request() 内部走 __blk_mq_complete_request() → 判断 rq->mq_ctx->cpu 是否等于当前 CPU → 不等就 blk_mq_complete_remote_or_requeue() 发 IPI，相等就走软中断 blk_mq_complete_softirq()。6.x 里这段被重写为 blk_mq_complete_request_remote() 加 rq->mq_hctx->cpumask 的判定，函数名和内部结构有变化，具体分支标「未验证」。驱动侧只依赖 blk_mq_end_request() / blk_mq_complete_request() 两个入口，这两个的语义在各版本间保持一致。

十一、超时与错误处理 #

超时时间来自 set->timeout，单位 jiffies。填 0 不等于关超时，是走默认值：

c
/* block/blk-mq.c，Linux 5.2.8，blk_mq_init_allocated_queue() 里 */
INIT_WORK(&q->timeout_work, blk_mq_timeout_work);
blk_queue_rq_timeout(q, set->timeout ? set->timeout : 30 * HZ);

不填 timeout 拿到的是 30 秒。要改就用 blk_queue_rq_timeout()，想彻底不超时做不到 —— 块层不允许。

blk_mq_timeout_work() 扫 hctx->tags 上所有 tag 的 deadline，把过期的交给驱动的 timeout 回调。回调返回值只有两种有意义的取法：

返回 含义 块层接着做什么
BLK_EH_DONE 已处理（自己复位了硬件） 不再重试，等驱动完成
BLK_EH_RESET_TIMER 还没到放弃的时候 重置 deadline，继续等

不实现 timeout 的设备，超时后由块层按错误终止，bi_status 置 BLK_STS_TIMEOUT，数据不可重试。自研卡至少要实现一个「标记失败并触发控制器复位」的 timeout。

queue_rq 的返回状态别混，「设备忙」返回成 BLK_STS_IOERR 是最常见的错，结果是大批 I/O 被误判成介质错误，文件系统上抛 EIO。四种语义见第九章的表。

z2ram 只有一处错误处理，写法基本标准：越界立即拒绝，返回 BLK_STS_IOERR。它先 blk_mq_start_request() 再判断越界、越界直接 return，少了一次 blk_mq_end_request(req, BLK_STS_IOERR)。5.2.8 的 blk_mq_dispatch_rq_list() 对错误返回值有兜底，功能上不卡死，但这是可改进之处，见第十八章。

十二、调度器与 elevator #

blk-mq 时代的调度器和 blk-sq 时代是两套东西，老的只有一部分被改造过来：

调度器 blk-sq 时代 blk-mq 时代 备注
noop 有 none 5.x 里 none 表示不装调度器
deadline 有 mq-deadline 每 hctx 一份实例
cfq 有 无对应物，已删除 5.0 移除 blk-sq 时一起走
bfq 有 bfq（mq 版） CONFIG_IOSCHED_BFQ
kyber 无 kyber 只有 mq 版

机制上，调度器挂在 request_queue 的一个 elevator_queue 上，但每个 hctx 各有自己的调度器数据结构（hctx->sched_data）和一套 sched_tags。所以 nr_hw_queues = 8 时调度器在内存里有 8 份独立实例。

驱动的唯一开关是 BLK_MQ_F_NO_SCHED：

c
/* block/blk-mq.c，Linux 5.2.8，blk_mq_init_allocated_queue() 末尾 */
if (!(set->flags & BLK_MQ_F_NO_SCHED)) {
        int ret = elevator_init_mq(q);
        if (ret)
                return ERR_PTR(ret);
}

设了它，q->elevator 恒为 NULL，所有 request 走软件队列直发路径。RAM 盘、纯内存设备该设它 —— 调度只增加延迟。z2ram 没设，所以它跑的是带 mq-deadline 的路径。

调度器对驱动的影响有三点：tag 分两套（internal tag 来自 sched_tags，driver tag 来自 hctx->tags，总数可超过 queue_depth）；merge 由调度器的 bio_merge / allow_merge 决定，驱动设的 BLK_MQ_F_SHOULD_MERGE 只在无调度器时管用；has_sched_dispatch 为真时派发来源就是调度器，不再扫软件队列。

版本注记：5.x 切调度器靠往 /sys/block/<dev>/queue/scheduler 写字符串，elevator_switch_mq() 走 quiesce → 冻结 → 换 → 解冻。6.x 里 elevator 一层的内部结构有变动，none 的行为也调整过（不再等同于无调度器）。本篇只断言 5.2.8。

十三、多队列与中断亲和 #

多队列要真跑出并发，光有软件分层不够 —— 中断得跟着队列走。

cpumask 谁设 含义 设错会怎样
hctx->cpumask blk_mq_map_swqueue() 哪些 CPU 的 I/O 走这个 hctx 派发落到不该跑的 CPU，打 run queue from wrong CPU
中断亲和性 驱动 request_irq() 前后自己设 该 hw queue 的完成中断落在哪些 CPU 完成与派发错位，远端内存访问回来了
map[i].mq_map[cpu] map_queues 或默认算法 CPU → hctx 编号 映射不均，某个 hctx 被压满

理想状态是一条直线：CPU N 提交 → hctx N 派发 → hctx N 中断回到 CPU N → 在 CPU N 完成，全程不出 CPU，ctx、tags、bio 数据都留在本地缓存。

中断数不够时，nr_hw_queues 只能开到中断数，靠加大 queue_depth 补吞吐。NVMe 那种一队列一中断的硬件，nr_hw_queues 直接等于 CPU 数，numa_node 再按 CPU 所在节点配，才算把多队列用满。

z2ram 完全不走中断（memcpy 同步完成），nr_hw_queues = 1 就够，没有亲和可谈。这个反差本身就是好材料：只有异步硬件才需要多队列。

    int device;
    int max_z2_map = ( Z2RAM_SIZE / Z2RAM_CHUNKSIZE ) * sizeof( z2ram_map[0] );
    int max_chip_map = ( amiga_chip_size / Z2RAM_CHUNKSIZE ) * sizeof( z2ram_map[0] );
    int rc = -ENOMEM;
    device = MINOR(bdev->bd_dev);
    mutex_lock(&z2ram_mutex);
    if ( current_device != -1 && current_device != device )
    {
        rc = -EBUSY;
        goto err_out;
    }
    if ( current_device == -1 )                 /* 首次打开才真正分配 */
    {
        z2_count = 0; chip_count = 0; list_count = 0; z2ram_size = 0;
        if (device >= Z2MINOR_MEMLIST1 && device <= Z2MINOR_MEMLIST4) {
                /* 次设备号 4~7：从 m68k_memory[] 取一段，先用 z_remap_nocache_nonser()
                   映射成虚拟地址，再按 64KB 切片填进 z2ram_map，同时算 list_count */
        } else switch ( device )
        {
            case Z2MINOR_COMBINED:              /* 0，正常走这里 */
                /* kmalloc(max_z2_map + max_chip_map) 后依次 get_z2ram()
                   + get_chipram()，再按 z2_count / chip_count 打印两段用量 */
            case Z2MINOR_Z2ONLY:                /* 1，只 Zorro II，只调 get_z2ram() */
            case Z2MINOR_CHIPONLY:              /* 2，只 Chip RAM，只调 get_chipram() */
            default:
                rc = -ENODEV;
                goto err_out;
        }
        if ( z2ram_size == 0 ) {
            printk( KERN_NOTICE DEVICE_NAME ": no unused ZII/Chip RAM found\n" );
            goto err_out_kfree;
        }
        current_device = device;
        z2ram_size <<= Z2RAM_CHUNKSHIFT;                 /* 切片数 -> 字节数 */
        set_capacity(z2ram_gendisk, z2ram_size >> 9);    /* 字节 -> 扇区 */
    }
    mutex_unlock(&z2ram_mutex);
    return 0;
err_out_kfree:
    kfree(z2ram_map);
err_out:
    mutex_unlock(&z2ram_mutex);
    return rc;
}

四个要点：current_device == -1 时才真分配，之后重复 open 直接返回 0，用一个次设备号变量当「内存已就绪」的锁；set_capacity() 单位是 512 字节扇区，>> 9 漏了就是容量为 0 的盘；z2ram_size 在同一个变量里先当切片数再当字节数，<<= Z2RAM_CHUNKSHIFT 之后语义就换了；err_out_kfree 之后 z2ram_map 没置 NULL，重复 open 会二次 free（见勘误）。

14.4 queue_rq：真正干活的地方 #

c
static blk_status_t z2_queue_rq(struct blk_mq_hw_ctx *hctx,
                                const struct blk_mq_queue_data *bd)
{
        struct request *req = bd->rq;
        unsigned long start = blk_rq_pos(req) << 9;   /* 起始扇区 -> 字节偏移 */
        unsigned long len  = blk_rq_cur_bytes(req);   /* 当前 bio 段字节数 */
        blk_mq_start_request(req);                    /* 启动超时计时 */
        if (start + len > z2ram_size) {
                pr_err(DEVICE_NAME ": bad access: block=%llu, count=%u\n",
                       (unsigned long long)blk_rq_pos(req),
                       blk_rq_cur_sectors(req));
                return BLK_STS_IOERR;
        }
        spin_lock_irq(&z2ram_lock);
        while (len) {
                unsigned long addr = start & Z2RAM_CHUNKMASK;   /* 切片内偏移 */
                unsigned long size = Z2RAM_CHUNKSIZE - addr;    /* 本切片还能用多少 */
                void *buffer = bio_data(req->bio);              /* 内存侧地址 */
                if (len < size)
                        size = len;
                addr += z2ram_map[ start >> Z2RAM_CHUNKSHIFT ]; /* 加上切片基地址 */
                if (rq_data_dir(req) == READ)
                        memcpy(buffer, (char *)addr, size);
                else
                        memcpy((char *)addr, buffer, size);
                start += size;
                len -= size;
        }
        spin_unlock_irq(&z2ram_lock);
        blk_mq_end_request(req, BLK_STS_OK);
        return BLK_STS_OK;
}

逐条拆，这就是「RAM 模拟块设备」的全部秘密：blk_rq_pos(req) 拿起始扇区（512 字节）左移 9 位换成字节偏移；blk_rq_cur_bytes(req) 拿当前 bio 段的字节数，是 cur 不是整条 request 的总长，一条 request 挂多个 bio 时这里只处理当前那段；blk_mq_start_request() 必须受理后立刻调，它置 deadline、启超时；while (len) 跨切片搬运，每次只搬「当前切片剩余的部分」，一条跨 3 个切片的 200KB 请求循环 4 次；z2ram_map[start >> 16] 是切片基地址、start & 0xffff 是切片内偏移，相加就是真实地址；rq_data_dir(req) == READ 判方向，读是「器件 → 内存」，写反过来，别搞反；最后 blk_mq_end_request() 同步完成，返回 BLK_STS_OK 告诉块层「已受理」。

bio_data() 取当前 bio 段的内核地址，对无数据请求返回 NULL：

c
static inline bool bio_has_data(struct bio *bio)
{
        if (bio &&
            bio->bi_iter.bi_size &&
            bio_op(bio) != REQ_OP_DISCARD &&
            bio_op(bio) != REQ_OP_SECURE_ERASE &&
            bio_op(bio) != REQ_OP_WRITE_ZEROES)
                return true;
        return false;
}
static inline void *bio_data(struct bio *bio)
{
        if (bio_has_data(bio))
                return page_address(bio_page(bio)) + bio_offset(bio);
        return NULL;
}

bio_page() / bio_offset() 从 bi_io_vec[bi_iter.bi_idx] 里取页和页内偏移。所以 DISCARD / WRITE_ZEROES 这类请求拿到的是 NULL，用之前先确认 bio_has_data()。

出口步骤 对应入口步骤

十五、z2ram 的数据组织 #

z2ram 没有一个字节是「磁盘」，全是 z2ram_map 这一层间接。8MB 切成 128 个 64KB 切片，z2ram_map[i] 存第 i 个切片的虚拟起始地址。地址换算只三条式子：

要什么 式子
request 的字节偏移 blk_rq_pos(req) << 9
落在哪个切片 start >> Z2RAM_CHUNKSHIFT（即 >> 16）
切片内偏移 start & Z2RAM_CHUNKMASK（即 & 0xffff）
真实地址 z2ram_map[start >> 16] + (start & 0xffff)

切片从哪儿来，由两个函数决定。

c
static void get_z2ram( void )
{
    int i;
    for ( i = 0; i < Z2RAM_SIZE / Z2RAM_CHUNKSIZE; i++ )   /* 128 次 */
    {
        if ( test_bit( i, zorro_unused_z2ram ) )           /* 这个 64KB 块没人用 */
        {
            z2_count++;
            z2ram_map[z2ram_size++] = (unsigned long)ZTWO_VADDR(Z2RAM_START) +
                                      (i << Z2RAM_CHUNKSHIFT);
            clear_bit( i, zorro_unused_z2ram );            /* 占住 */
        }
    }
}
static void get_chipram( void )
{
    while ( amiga_chip_avail() > ( Z2RAM_CHUNKSIZE * 4 ) )
    {
        chip_count++;
        z2ram_map[ z2ram_size ] = (u_long)amiga_chip_alloc( Z2RAM_CHUNKSIZE, "z2ram" );
        if ( z2ram_map[ z2ram_size ] == 0 )
                break;
        z2ram_size++;
    }
}

zorro_unused_z2ram 是 128 位位图，由 amiga_zorro_probe() 里的 mark_region() 填：先把所有 Zorro II 内存按 64KB 全置 1，再把系统已用区间清 0。get_z2ram() 顺着扫，test_bit 为 1 的就归自己。

两者来源不同，语义就分叉了：z2ram_map[0 .. z2_count) 是借来的物理 RAM 的虚拟地址，只能 set_bit 归还标记；z2ram_map[z2_count .. z2ram_size) 是 amiga_chip_alloc() 新分配的内存地址，必须 amiga_chip_free()。这就是 z2_exit() 要分两段循环的原因。

好处是零拷贝：读数据时 memcpy 直接从 Zorro II RAM 搬到页缓存，没有中间缓冲区，也不用建 DMA 描述符。代价是只能在 m68k Amiga 上跑，ZTWO_VADDR 离开那个平台没意义。

m68k_memory[] 是另一种切片来源，次设备号为 4~7 时从内核内存描述表里拿一整段。struct m68k_mem_info 只有 addr 和 size 两个字段，m68k_memory[NUM_MEMINFO]（NUM_MEMINFO = 4）配 m68k_realnum_memory 使用。这条路径代码里有，但 alloc_disk(1) 只暴露了 1 个次设备（0 号），实际走不到。

第 2 步：写 queue_rq

c
static blk_status_t ramdisk_queue_rq(struct blk_mq_hw_ctx *hctx,
                                     const struct blk_mq_queue_data *bd)
{
        struct request *req = bd->rq;
        unsigned long start = blk_rq_pos(req) << SECTOR_SHIFT;
        unsigned long len = blk_rq_cur_bytes(req);
        blk_mq_start_request(req);
        if (start + len > RAMDISK_SIZE) {
                pr_err(DEVICE_NAME ": bad access: block=%llu, count=%u\n",
                       (unsigned long long)blk_rq_pos(req),
                       blk_rq_cur_sectors(req));
                blk_mq_end_request(req, BLK_STS_IOERR);
                return BLK_STS_IOERR;
        }
        spin_lock_irq(&ramdisk_lock);
        while (len) {
                unsigned long off = start & RAMDISK_CHUNKMASK;
                unsigned long size = RAMDISK_CHUNKSIZE - off;
                void *buffer = bio_data(req->bio);
                char *addr;
                if (len < size)
                        size = len;
                addr = (char *)ramdisk_map[start >> RAMDISK_CHUNKSHIFT] + off;
                if (rq_data_dir(req) == READ)
                        memcpy(buffer, addr, size);
                else
                        memcpy(addr, buffer, size);
                start += size;
                len -= size;
        }
        spin_unlock_irq(&ramdisk_lock);
        blk_mq_end_request(req, BLK_STS_OK);
        return BLK_STS_OK;
}

比 z2ram 改进两处：越界分支补了 blk_mq_end_request()；off 提出来单独算，避免「先算 size 再算 addr」那个容易看错顺序的写法。配套的 blk_mq_ops 只有一行：static struct blk_mq_ops ramdisk_mq_ops = { .queue_rq = ramdisk_queue_rq, };。

I/O 全部 EIO queue_rq 把「设备忙」返回成 BLK_STS_IOERR 设备忙返回 BLK_STS_DEV_RESOURCE 或 BLK_STS_RESOURCE
卸载时 oops / use-after-free 先 blk_mq_free_tag_set() 后 blk_cleanup_queue() 顺序反过来，队列先拆
每个请求都等 30 秒 queue_rq 里漏了 blk_mq_start_request()，或同步完成后没 blk_mq_end_request() 两头都必须调
超时时间改了没生效 改的是 q->rq_timeout 旧字段 用 blk_queue_rq_timeout()
日志刷 run queue from wrong CPU 在不在 hctx->cpumask 里的 CPU 上同步派发 查 map_queues 结果和中断亲和
cmd_size 改了没用 tag set 已建，rq_size 在 blk_mq_alloc_rqs() 里定死 拆掉整个 tag set 重建
queue_depth 跟你填的不一样 超 BLK_MQ_MAX_DEPTH 被截断，或内存不足被减半 看 dmesg 的 reduced tag depth
多队列没提速 中断全落在 CPU0 irq_set_affinity_hint() 按 hctx 绑
numa_node 填了却全场远端访问 设备在别的节点，或用 blk_mq_init_sq_queue() 被强制成 NUMA_NO_NODE 手工走 blk_mq_alloc_tag_set() 路径
崩溃在 memcpy DISCARD / WRITE_ZEROES 这类无数据请求，bio_data() 返回 NULL 先判 bio_has_data()
只处理了第一个 bio 段 用了 blk_rq_bytes() 而不是 blk_rq_cur_bytes() 用 cur 版本，并循环处理
z2_open() 重复打开二次 free err_out_kfree 之后 z2ram_map 没置 NULL 释放后 z2ram_map = NULL
卸载后 /dev/xxx 还在 只 del_gendisk() 没 unregister_blkdev() 两个都要，顺序见 14.5

几条不属于 bug 但得心里有数：

  • 5.0 之后没有回头路。request_fn 和老的 make_request 都没了。网上大量 3.x/4.x 的块设备驱动贴过来编不过，不要以为是头文件问题，是接口整体换了。
  • blk_mq_init_sq_queue() 在 6.x 里没有了。迁移到 blk_mq_alloc_tag_set() + blk_mq_alloc_disk()，后者把 gendisk 和 queue 一起给你。
  • BLK_MQ_F_SHOULD_MERGE 只影响无调度器路径。装了 mq-deadline 之后 merge 由调度器说了算。
  • reserved_tags 不是保险。预留 tag 只给带 BLK_MQ_REQ_RESERVED 的关键路径（内存回收等）用，普通 I/O 抢不到。设太小没意义，太大浪费深度。
