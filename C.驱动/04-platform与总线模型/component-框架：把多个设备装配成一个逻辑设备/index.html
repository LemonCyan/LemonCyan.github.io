本篇只讲一件事：当一个逻辑设备要靠多个驱动拼起来时，内核用什么机制等齐它们、排序它们、最后一次性 bind。

讲什么：component 的存在理由、两个角色（master / component）、struct component_master_ops 与 struct component_ops 全字段、注册与匹配流程、try_to_bring_up_* 的完整判定、RK3399 DRM 的实际组装、常见错误与调试。

不讲什么：platform 总线自身的 probe 匹配细节、device/driver/bus/class 的内核模型全景、DRM 内部的 KMS 对象与原子提交。

跨篇指路：总线匹配看同目录《platform 总线：设备、驱动与匹配》；device/driver/bus/class 的内核视角看 B.内核/08-总线与设备模型。

版本说明：代码以 linux 5.x（RK3399 / NanoPC-T4 实际跑的那套）为准。4.x 与 5.x 之间 component 内部实现改动不小，凡是会踩到版本差异的地方逐处标出；拿不准的写「未验证」。

一、component 要解决什么：一个设备由多个驱动拼起来 #

一个屏幕要亮，需要的东西不止一个驱动。以 RK3399 为例：VOP 负责扫帧，eDP 和 MIPI DSI 把像素送出去，HDMI 还有自己的 PHY 和音频通道，再加背光与电源域。这些在内核里是各自独立的 platform 驱动，各自占一个设备树节点，各自被 platform 总线 probe。但它们对外只能表现为一个设备：display-subsystem。用户态只看到一个 DRM card、一堆 framebuffer、一套 connector。中间那个「把 N 个驱动拼成一个逻辑设备」的动作，就是 component 框架干的活。

它保证两件事：所有该到的都到了，少一个 VOP 就不许开显示；到齐之后按固定顺序初始化，乱序会炸。两句话记住定位：component 不是总线，不负责发现设备；它是一个装配协调器，负责在设备都已 probe 之后决定「什么时候可以开始组装」。代码在 drivers/base/component.c，头文件 include/linux/component.h，两个文件加起来不到两千行，值得通读。

二、为什么 platform 总线不够用 #

platform 总线解决「一个 device 配一个 driver」，配对成功就 probe，一对一，互不干涉。这套模型在多设备协作面前有三个硬伤。

第一，probe 时机无法协调。设备树节点注册顺序、驱动注册顺序、-EPROBE_DEFER 返回时机共同决定 probe 顺序。VOP 的 probe 要访问 eDP 提供的资源而 eDP 还没 probe，只能返 -EPROBE_DEFER 重试。两个设备互相等还能靠 deferred probe 兜住；五个设备互相等，重试次数和顺序就变成玄学。

第二，初始化需要全局视角。显示子系统要创建一张 DRM card，而建 card 需要所有 CRTC、encoder、connector 的拓扑信息，这个动作必须在所有子设备就绪后由某一个驱动统一执行，platform 总线没有「等齐了叫我」这个语义。第三，生命周期要绑在一起：任一子设备被卸载，整个逻辑设备必须拆掉，而 platform 总线只保证自己的 device 和 driver 解绑，不保证兄弟设备跟着走。

component 的思路和 platform 总线同构：注册 → 配对 → 回调。区别只在基数，platform 是「一对一」，component 是「多对一」。

维度 platform 总线 component 框架
配对基数 一个 device 对一个 driver 一个 master 对 N 个 component
谁发起 设备或驱动任一侧注册都触发匹配 master 与 component 任一侧注册都触发装配尝试
匹配依据 id_table / of_match_table / name 调用方提供的 compare 回调 + 任意数据
回调 probe / remove component_ops.bind/unbind + component_master_ops.bind/unbind
顺序 无法控制 由 match 数组顺序决定
卸载联动 无 component 走掉会拆掉整个 master
代码位置 drivers/base/platform.c drivers/base/component.c

看最后两行。顺序控制和卸载联动，是 component 相对 platform 总线唯一的实质性增值。

三、component 的两个角色：master 与 component #

框架里只有两个角色。

master：也叫 aggregate driver，代表「拼出来的整体」。对应 struct aggregate_device（内部结构）和 struct component_master_ops（回调集）。RK3399 里 master 是 VOP 驱动，被称作 rockchip_drm_driver 的装配者。component：代表一个零件。对应 struct component（内部结构）和 struct component_ops（回调集）。RK3399 里 eDP、MIPI DSI、HDMI 都是 component。

流程一句话：零件先报到，master 后点名；或者 master 先点名，零件陆续报到。谁先谁后都行，框架两头都会尝试装配。

维度 master（aggregate driver） component
代表结构 struct aggregate_device struct component
回调结构 struct component_master_ops struct component_ops
注册函数 component_master_add_with_match() component_add()
注销函数 component_master_del() component_del()
全局链表 aggregate_devices component_list
匹配依据 自己持有的 struct component_match 无，被别人匹配
典型实例 VOP / display-subsystem 节点 eDP、MIPI DSI、HDMI
数量关系 一个 match 对应一组 component 一个 component 可被多个 master 看到，但只归属一个
谁调 bind 框架调 master 的 bind，你在里面调 component_bind_all() 框架调你的 bind，参数带 master 的 struct device *

容易忽略的一点：struct aggregate_device 这个名字是 5.x 才改的。4.x 里它叫 struct master，全局链表叫 masters，函数叫 try_to_bring_up_master。遇到 4.x 代码时把 aggregate_device 换成 master、adev 换成 master 就能对上。

struct component 的定义（drivers/base/component.c，5.x）：

c
struct component {
	struct list_head node;
	struct aggregate_device *adev;
	bool bound;
	const struct component_ops *ops;
	int subcomponent;
	struct device *dev;
};

逐字段：node 挂进全局链表 component_list（保存系统里所有已注册 component，是匹配的搜索空间）；adev 是反向指针，指向匹配上自己的 aggregate_device，没被认领时是 NULL，find_component 靠它避免同一个零件被两个 master 抢；bound 在 component_ops.bind 成功后被置 true，debugfs 里的 bound / not bound 就是它；ops 是零件自己的回调集；subcomponent 是一个物理 device 注册多个逻辑 component 时的编号，component_add() 传 0，component_add_typed() 传具体值；dev 是零件对应的 struct device，多数时候就是 platform_device 的 dev。

struct aggregate_device 的定义：

c
struct aggregate_device {
	struct list_head node;
	bool bound;
	const struct component_master_ops *ops;
	struct device *parent;
	struct component_match *match;
};

逐字段：node 挂进 aggregate_devices 链表；bound 在 master 的 bind 成功后置 true，try_to_bring_up_masters 靠它跳过已装配完成的 master；ops 是 master 的回调集；parent 是 master 所属的 struct device，注意它才是传给 component_master_ops.bind() 的参数，不是 adev 本身；match 是这个 master 的采购清单。

struct component_match 定义：

c
struct component_match {
	size_t alloc;
	size_t num;
	struct component_match_array *compare;
};

alloc 是 compare 数组已分配的槽位数，按 16 个一档增长；num 是实际条目数，master 注册时会按它缩容一次；compare 是数组本体，每个条目描述「我要找什么样的零件」。

struct component_match_array 定义：

c
struct component_match_array {
	void *data;
	int (*compare)(struct device *, void *);
	int (*compare_typed)(struct device *, int, void *);
	void (*release)(struct device *, void *);
	struct component *component;
	bool duplicate;
};

data 是喂给 compare / compare_typed 的匹配数据，RK3399 里多数是一个 struct device_node *；compare 是匹配规则，返回非 0 表示这个 struct device 就是我要的；compare_typed 是带 subcomponent 编号的匹配规则，供 component_match_add_typed() 用；release 是匹配数据用完后的释放函数，比如 of_node_put；component 在匹配成功后回填；duplicate 表示这个零件同时被别的 master 认领过，置位时 component_bind_all() 会跳过它。

用拼乐高打比方：struct component 是积木，struct aggregate_device 是要拼出的东西，struct component_match 是你手里的图纸。图纸每一行说明「我要一块什么形状的积木」，即 component_match_array，但此时还没指定具体是哪一块。

四、struct component_master_ops #

master 侧唯一要实现的回调集，在 include/linux/component.h，只有两个成员。

c
/**
 * struct component_master_ops - callback for the aggregate driver
 *
 * Aggregate drivers are registered with component_master_add_with_match() and
 * unregistered with component_master_del().
 */
struct component_master_ops {
	int (*bind)(struct device *master);
	void (*unbind)(struct device *master);
};
成员 原型 何时被调 你要做的事
bind int (*)(struct device *master) 所有 component 到齐，且 master 首次尝试装配时 分配上下文，调 component_bind_all()，注册到子系统
unbind void (*)(struct device *master) master 自己注销，或任一 component 注销时 撤销 bind 里做的一切，调 component_unbind_all()

内核源码对这俩回调的注释里有两条硬规矩：master 的 bind 走三步——给 aggregate driver 分配结构体、以它为 opaque 指针调 component_bind_all()、把 aggregate driver 注册进子系统对外发布接口；master 的生命周期和任何一个底层 struct device 都不对齐，所以 devm 在这里用不了，bind 里申请的资源必须在 unbind 里显式释放。

第二条最容易翻车。你写惯了 platform driver，什么都想 devm_kzalloc。这里不行：bind 传进来的 struct device *master 是 master 设备的，它的销毁时机和装配体的销毁时机不是一回事。unbind 的触发条件也来自注释：要么用 component_master_del() 注销 master，要么某个 component 用 component_del() 把自己摘掉。

五、struct component_ops #

component 侧的回调集，同样两个成员。

c
/**
 * struct component_ops - callbacks for component drivers
 *
 * Components are registered with component_add() and unregistered with
 * component_del().
 */
struct component_ops {
	int (*bind)(struct device *comp, struct device *master,
		    void *master_data);
	void (*unbind)(struct device *comp, struct device *master,
		       void *master_data);
};
成员 原型 何时被调 参数含义
bind int (*)(struct device *comp, struct device *master, void *master_data) component_bind_all() 遍历到它时，按 match 数组顺序 comp 自己的 device；master 是 master 的 device；master_data 是 component_bind_all() 的第二个参数
unbind void (*)(struct device *comp, struct device *master, void *master_data) component_unbind_all() 或 bind 半途失败回滚时 同上，保证成对

bind 的返回值有意义：返回 0，零件绑好了，component->bound 置 true，component_bind_all() 继续下一个；返回负数，component_bind_all() 立即停下，把已经绑好的那些反向 unbind 掉，再把错误码一路经 master 的 bind 传回装配流程；返回 -EPROBE_DEFER，装配被推迟，第十六节细说。

master_data 的类型完全由你定，RK3399 DRM 传的是 struct rockchip_drm_private *。两个 ops 的对比：

对比项 component_master_ops component_ops
调用方 component 核心，在装配判定通过后 component_bind_all() / component_unbind_all()
参数里的 device master，即 adev->parent comp 自己的 device + master device
数量 一个 master 一份 每个零件一份
能否用 devm 不建议，生命周期不匹配（源码明确说明不能用） 可以用在 comp 设备上，核心实现里就开了 devres group 保护

六、注册流程：component_master_add 与 component_add #

两侧各有入口，先看名字。

| 函数 | 作用 | 所属 | | --- | --- | --- || --- | --- | --- | | component_add(dev, ops) | 注册一个 component | component 侧 | | component_add_typed(dev, ops, subcomponent) | 同一 device 注册多个 component | component 侧 | | component_del(dev, ops) | 注销 component | component 侧 | | component_master_add_with_match(parent, ops, match) | 注册一个 master | master 侧 | | component_master_del(dev, ops) | 注销 master | master 侧 | | component_master_add(parent, ops) | 老的简化版入口 | master 侧 |

component_add() 极薄，只是给 __component_add() 补个 0；真正干活的是 __component_add()：

c
static int __component_add(struct device *dev, const struct component_ops *ops,
	int subcomponent)
{
	struct component *component;
	int ret;

	component = kzalloc(sizeof(*component), GFP_KERNEL);
	if (!component)
		return -ENOMEM;
	component->ops = ops;
	component->dev = dev;
	component->subcomponent = subcomponent;
	mutex_lock(&component_mutex);
	list_add_tail(&component->node, &component_list);
	ret = try_to_bring_up_masters(component);
	if (ret < 0) {
		if (component->adev)
			remove_component(component->adev, component);
		list_del(&component->node);
		kfree(component);
	}
	mutex_unlock(&component_mutex);
	return ret < 0 ? ret : 0;
}

四步走：分配 struct component、填 ops / dev / subcomponent、挂到 component_list 尾部、调 try_to_bring_up_masters() 试着唤醒正等着它的 master。只有 ret < 0 才算失败并回滚；try_to_bring_up_masters 返回 0（还没齐）或 1（装好了）都当成功，component_add() 返回 0。零件报到成功，不代表装配完成。

component_del() 是反过程，遍历 component_list 找 c->dev == dev && c->ops == ops 的那一项，list_del(&c->node) 摘下、调 remove_component(component->adev, component)、再 kfree。它同时匹配 dev 和 ops 两项，所以同一个设备用两套 ops 注册两次时能精确摘掉其中一个。remove_component() 会连带处理 master 的解绑，第十三节展开。

master 侧入口，5.x 主用带 match 的版本：

c
int component_master_add_with_match(struct device *parent,
	const struct component_master_ops *ops,
	struct component_match *match)
{
	struct aggregate_device *adev;
	int ret;

	/* Reallocate the match array for its true size */
	ret = component_match_realloc(match, match->num);
	if (ret)
		return ret;
	adev = kzalloc(sizeof(*adev), GFP_KERNEL);
	if (!adev)
		return -ENOMEM;
	adev->parent = parent;
	adev->ops = ops;
	adev->match = match;
	component_debugfs_add(adev);
	mutex_lock(&component_mutex);
	list_add(&adev->node, &aggregate_devices);
	ret = try_to_bring_up_aggregate_device(adev, NULL);
	if (ret < 0)
		free_aggregate_device(adev);
	mutex_unlock(&component_mutex);
	return ret < 0 ? ret : 0;
}

步骤读一遍就懂：按真实条目数缩容 match 数组（前面按 16 一档扩过，实际没准只用了 3 个槽）；分配 aggregate_device；填 parent / ops / match；在 debugfs 建一个可读文件；挂到 aggregate_devices；立刻尝试一次装配。最后一步是关键：master 注册时 component 没准早就到齐了，所以 component 参数传 NULL，表示「不是某个特定零件把我叫醒的，我来看看现在能不能装」。素材在这里有个笔误要纠——这里调的是 try_to_bring_up_aggregate_device(adev, NULL)，不是 try_to_bring_up_masters()，后者只在 __component_add() 里被调，两个函数别混。

关于 component_master_add()：它是不带 match 的入口，match 传 NULL，最后调 component_master_add_with_match(parent, ops, NULL)，只能用于「我全都要」的简单场景，实际没人用。4.x 时代 component_master_add() 是主入口，component_master_add_with_match() 是后来加的扩展；5.x 反过来，带 match 的成为唯一正经入口，老的只是兼容壳子。演进方向很明确：匹配必须由 master 显式描述，不能靠猜。

component_match_realloc() 是 match 数组的分配器：

c
static int component_match_realloc(struct component_match *match, size_t num)
{
	struct component_match_array *new;

	if (match->alloc == num)
		return 0;
	new = kmalloc_array(num, sizeof(*new), GFP_KERNEL);
	if (!new)
		return -ENOMEM;
	if (match->compare) {
		memcpy(new, match->compare, sizeof(*new) *
				    min(match->num, num));
		kfree(match->compare);
	}
	match->compare = new;
	match->alloc = num;
	return 0;
}

缩容和扩容共用一个函数。拷贝长度取 min(match->num, num)，保证缩容时不越界。

七、匹配机制：devicetree 里的 compatible 怎么配对 #

先纠正一个常见误解：component 框架本身完全不看设备树的 compatible 字符串。框架只认 component_match_array 里的 compare 函数指针，把全局链表里每个 struct component 的 dev 依次喂给你的 compare 函数，返回非 0 就算匹配上。

那 compatible 怎么参与进来？靠 master 侧先把设备树节点找出来做成 compare 的匹配数据。常见做法是 master 遍历自己的子节点，逐个调 component_match_add()，把 device_node 作为 data 塞进 match 数组，用 compare_of（语义等于 device->of_node == data）做比较函数。equal 判断的对象于是从 compatible 字符串变成「设备树节点指针相等」。

整条链是：DTS 节点 → of_node → compare_of 比较指针 → 命中对应 platform_device 的 dev → 命中对应的 struct component。RK3399 的 DTS 里，统筹节点长这样（结构示意，非完整节点）：

dts
display-subsystem {
	compatible = "rockchip,display-subsystem";
	ports = <&vopb_out>, <&vopl_out>;
	status = "okay";
	route {
		route_hdmi: route-hdmi {
			status = "okay";
			logo,uboot = "logo.bmp";
			connect = <&vopb_out_hdmi>;
		};
	};
};

注意 ports = <&vopb_out>, <&vopl_out> 这一行。它不是 component 框架的语法，而是 Rockchip DRM 自己的私有属性，master 驱动读它来决定 match 哪些 VOP 端口节点。component 框架对 ports 一无所知。

这就解释了 component 为什么比 platform 总线灵活：匹配规则是任意 C 函数，数据是任意 void *。你可以按 compatible 匹配、按节点指针匹配、按设备名匹配、按 syscon 寄存器值匹配，甚至自己编一套规则。代价是两边都得写对——master 写的 match 描述和 component 实际注册的 dev 必须能对上，框架帮不了你。

八、bind 与 unbind：装配的时机 #

装配时机由三个入口共同触发，谁先到都不影响结果：

text
component_add()                     -> try_to_bring_up_masters(component)
component_master_add_with_match()   -> try_to_bring_up_aggregate_device(adev, NULL)
component_del() / 某 component 掉线 -> remove_component() -> unbind 链

前两个是「装配尝试」，第三个是「拆解」。try_to_bring_up_masters() 是 5.x 的写法，遍历所有还没 bound 的 master，对每个调一次 try_to_bring_up_aggregate_device(adev, component)，ret != 0 就停：

c
static int try_to_bring_up_masters(struct component *component)
{
	struct aggregate_device *adev;
	int ret = 0;

	list_for_each_entry(adev, &aggregate_devices, node) {
		if (!adev->bound) {
			ret = try_to_bring_up_aggregate_device(adev, component);
			if (ret != 0)
				break;
		}
	}
	return ret;
}

有个细节值得盯：if (ret != 0) break;。返回 1 表示这次装配成功，要 break；返回 0 表示这个 master 还没齐，继续看下一个；返回负数表示出错，同样 break。

try_to_bring_up_aggregate_device() 是整个框架的判定核心。版本提示：4.x 里这一族函数叫 try_to_bring_up_master(master, component)，结构体叫 struct master；5.x 把 master 改名成 aggregate_device，函数名相应变成 try_to_bring_up_aggregate_device()。逻辑没变，名字变了，翻 4.19 源码时对不上是正常的。

c
static int try_to_bring_up_aggregate_device(struct aggregate_device *adev,
	struct component *component)
{
	int ret;

	if (find_components(adev)) {
		dev_dbg(adev->parent, "master has incomplete components\n");
		return 0;
	}
	if (component && component->adev != adev) {
		dev_dbg(adev->parent, "master is not for this component (%s)\n",
			dev_name(component->dev));
		return 0;
	}
	if (!devres_open_group(adev->parent, adev, GFP_KERNEL))
		return -ENOMEM;
	ret = adev->ops->bind(adev->parent);
	if (ret < 0) {
		devres_release_group(adev->parent, NULL);
		if (ret != -EPROBE_DEFER)
			dev_info(adev->parent, "adev bind failed: %d\n", ret);
		return ret;
	}
	devres_close_group(adev->parent, NULL);
	adev->bound = true;
	return 1;
}

按顺序拆五步：find_components(adev) 返回非 0，说明零件没齐，返回 0，这是「还没准备好」，不是错误；如果是 component_add() 进来的（component 非 NULL），检查这个零件的归属是不是当前 adev，不是就返回 0，说明这个 master 不关心它；开一个 devres 资源组，用 adev 当 ID；调 master 的 bind，返回值小于 0 就释放资源组并返回错误；成功后关资源组（devres_close_group 保留，devres_release_group 是丢弃），置 adev->bound = true，返回 1。

返回值三种含义写死在源码注释里：1 装配成功，0 还没准备好，负数是 errno。混淆 0 和负数会让 component_add() 把「还没齐」当成失败去回滚，这是自己写调试打桩时常见的错。find_components() 负责把 match 数组里的「图纸行」和实际的零件对上号：

c
static int find_components(struct aggregate_device *adev)
{
	struct component_match *match = adev->match;
	size_t i;
	int ret = 0;

	for (i = 0; i < match->num; i++) {
		struct component_match_array *mc = &match->compare[i];
		struct component *c;
		if (match->compare[i].component)
			continue;
		c = find_component(adev, mc);
		if (!c) {
			ret = -ENXIO;
			break;
		}
		match->compare[i].duplicate = !!c->adev;
		match->compare[i].component = c;
		c->adev = adev;
	}
	return ret;
}

三个字段在这里一次写全：duplicate 记录这个零件是不是被别处认领过；component 回填找到的零件；c->adev 反向指回来。find_component() 遍历 component_list，把第一个匹配的捞出来：

c
static struct component *find_component(struct aggregate_device *adev,
	struct component_match_array *mc)
{
	struct component *c;

	list_for_each_entry(c, &component_list, node) {
		if (c->adev && c->adev != adev)
			continue;
		if (mc->compare && mc->compare(c->dev, mc->data))
			return c;
		if (mc->compare_typed &&
		    mc->compare_typed(c->dev, c->subcomponent, mc->data))
			return c;
	}
	return NULL;
}

两处判定值得记：第一行 continue，已经归属别的 master 的零件直接跳过，一个零件只能有一个家；compare 和 compare_typed 是「或」的关系，任一命中即可返回。

九、component 的添加顺序与依赖 #

框架不强制你按什么顺序注册，但绑定顺序是强制的，而且只由一处决定：component_match 数组的下标顺序。component_bind_all() 里那行注释写得很直白 —— /* Bind components in match order */。

也就是说，你在 master 的 probe 里第几个调 component_match_add()，component_ops.bind 就第几个被调。顺序由你掌握，跟注册时间、DTS 节点顺序、驱动加载顺序都无关。

三个实践结论。第一，master 驱动里 match 的添加次序要写清楚：RK3399 DRM 里 VOP 先 match、接口控制器后 match，因为 VOP 的 bind 创建 CRTC，接口控制器的 bind 创建 encoder，后者依赖前者。第二，一个零件的 bind 依赖另一个零件 bind 的产物，它就必须排在后面，这个依赖框架检查不出来，写错了就是空指针。第三，unbind 严格逆序，框架帮你保证，你不要自己去调整。

DTS 节点的书写顺序、status = "okay" 的位置、驱动 module_init 的先后，只影响「零件什么时候报到」，不影响「装配时谁先谁后」。报到顺序只决定装配尝试被触发多少次，最终结果一样。

顺序来源 影响什么 是否影响 bind 顺序
DTS 节点顺序 platform_device 注册顺序 否
驱动链接 / module_init 顺序 probe 尝试顺序 否
-EPROBE_DEFER 重试 probe 成功时刻 否
component_match 数组下标 component_ops.bind 调用顺序 是，唯一决定因素

十、component_match：怎么描述「我等的是谁」 #

component_match 是 master 的采购清单。构建它的 API 有三个常用变体，加一个内部实现：

API 用途 是否带 release 是否带 typed
component_match_add(dev, matchptr, compare, data) 最常用 否 否
component_match_add_release(dev, matchptr, release, compare, data) 需要释放匹配数据时 是 否
component_match_add_typed(dev, matchptr, compare_typed, data) 一个 device 多 component 否 是

它们最终都落到 __component_match_add()：

c
static void __component_match_add(struct device *parent,
	struct component_match **matchptr,
	void (*release)(struct device *, void *),
	int (*compare)(struct device *, void *),
	int (*compare_typed)(struct device *, int, void *),
	void *compare_data)
{
	struct component_match *match = *matchptr;

	if (IS_ERR(match))
		return;
	if (!match) {
		match = devres_alloc(devm_component_match_release,
				     sizeof(*match), GFP_KERNEL);
		if (!match) {
			*matchptr = ERR_PTR(-ENOMEM);
			return;
		}
		devres_add(parent, match);
		*matchptr = match;
	}
	if (match->num == match->alloc) {
		size_t new_size = match->alloc + 16;
		int ret;
		ret = component_match_realloc(match, new_size);
		if (ret) {
			*matchptr = ERR_PTR(ret);
			return;
		}
	}
	match->compare[match->num].compare = compare;
	match->compare[match->num].compare_typed = compare_typed;
	match->compare[match->num].release = release;
	match->compare[match->num].data = compare_data;
	match->compare[match->num].component = NULL;
	match->num++;
}

四个要点。其一，matchptr 第一次传进来必须是 NULL 的地址，函数自己用 devres_alloc() 分配 struct component_match 并挂到 parent 上，match 的生命周期跟着 master 的 device 走，不用手动释放。其二，容量按 16 一档增长：match->num == match->alloc 时 alloc 直接加 16，这也是为什么 component_master_add_with_match() 开头要按 match->num 缩一次容，把浪费的槽位还回去。其三，条目只填 compare / compare_typed / release / data，component 清成 NULL，此时还没找到任何零件，真正的匹配发生在 find_components()。其四，duplicate 在这里没初始化，它在 find_components() 里被赋值；component_match_realloc() 用 kmalloc_array 不是 kzalloc，那段内存的内容全靠后面覆盖，读代码时别以为它一开始就是 0。

devres_alloc() 带的释放函数是 devm_component_match_release：遍历 match->compare[0..num)，对每个非空 entry->release 调一次 entry->release(dev, entry->data)，然后释放 compare 数组和 struct component_match 本身。这个函数体的确切写法未逐行核对，流程按 devres 惯例推导，未验证。

典型用法，master 在 probe 里收集子节点：

c
struct component_match *match = NULL;
struct device_node *np;
for_each_child_of_node(dev->of_node, np)
	component_match_add(dev, &match, compare_of, np);
ret = component_master_add_with_match(dev, &my_master_ops, match);
if (ret)
	return ret;

这段是骨架示意，非 RK3399 原文。RK3399 走的是另一条路，见第十四节。

component 框架不校验你在 match 里加了多少条。加少了，零件齐了但没被绑，行为是「装配成功但少了功能」；加多了，match 永远凑不齐，master 永远不 bind，表现为「驱动不 probe，也无报错」。

十一、比较函数 compare_of 与 compare_dev_name #

比较函数是一个 int (*)(struct device *, void *)，返回非 0 表示命中。

函数 语义 可用性 典型场景
compare_of(dev, data) dev->of_node == (struct device_node *)data 通用，指向设备树节点 最常见，master 遍历 DTS 子节点
compare_dev_name(dev, data) 比较 dev_name(dev) 与 (const char *)data 通用，按设备名字符串匹配 无设备树环境或名字稳定的场景
compare_dev(dev, data) dev == (struct device *)data 通用，直接比 device 指针 已知 device 指针的窄场景
compare_dev_null(dev, data) data 为 NULL 时命中 通用 兜底占位
component_compare_of 4.x 时代的旧名 5.x 已改名 / 未验证 老代码里能见到
component_compare_dev_name 4.x 时代的旧名 5.x 已改名 / 未验证 老代码里能见到

compare_of 的实现短得可以背下来：

c
static int compare_of(struct device *dev, void *data)
{
	return dev->of_node == data;
}

它比的是节点指针，不是 compatible 字符串。同一颗 DTS 节点只有一个 of_node，只能命中一个 device，天然不歧义。

compare_dev_name 同理，取 data 当 const char *，与 dev_name(dev) 做 strcmp：

c
static int compare_dev_name(struct device *dev, void *data)
{
	const char *name = data;
	return !strcmp(dev_name(dev), name);
}

这一行的写法是按语义还原的，未与源码逐字比对。用名字匹配的坑在于，dev_name() 对 platform_device 是 地址.名字 形式，比如 ff8f0000.vop，地址一变就匹配不上；内核里存在同名设备时，匹配就不可控。RK3399 的 DRM 驱动走 compare_of 路线，因为它要给 ports 属性里列出的每个端口节点配一个 parts 结构。这种「按节点精确锁定」是主流做法。

自己写比较函数也很常见，比如按 compatible 匹配：

c
static int my_compare_compat(struct device *dev, void *data)
{
	return of_device_is_compatible(dev->of_node, data);
}

数据是字符串，规则是 compatible 包含关系。注意它仍然是你自己写的，框架只是借你一个回调。

十二、装配完成的判定：所有 component 到齐才 bind #

判定只有一处，在 try_to_bring_up_aggregate_device() 里：find_components(adev) == 0，即每个 component_match_array 都有 component。

find_components() 的严格读法：返回 0 表示「match->num 个条目全部有归属」。若 match->num == 0，循环一次不跑，直接返回 0，也判为「齐了」。所以空 match 的 master 会因为「全部到齐（一条都没有）」而直接 bind —— 忘加 match 就是这个效果。

装配通过的完整条件清单：

条件 检查位置 不满足时
match 数组每一项都找到了 component find_components() 返回 0 返回 0，继续等
若是被某个 component 唤醒，它的 adev 必须是自己 component->adev != adev 返回 0，不处理
devres 组能开起来 devres_open_group() 返回 -ENOMEM
master 的 bind 返回 0 adev->ops->bind() 返回该错误码，bound 保持 false
以上全过 —— adev->bound = true，返回 1

find_components() 里的 ret = -ENXIO 是个迷惑点。它表示「找到了图纸行，但没找到对应零件」，也就是「还没齐」。但 try_to_bring_up_aggregate_device() 把它当非 0 处理，统一 return 0，并不把 -ENXIO 传出去，它只用于函数内部表达。component_bind_all() 遍历时不需要再判空，find_components() 已保证每个槽位都有 component：

c
for (i = 0; i < adev->match->num; i++)
	if (!adev->match->compare[i].duplicate) {
		c = adev->match->compare[i].component;
		ret = component_bind(c, adev, data);
		if (ret)
			break;
	}

duplicate 为真的槽位会被跳过。这个状态出现在「同一个零件被两个 master 的 match 都匹配到」时：先到的 master 把它认走，后到的看到 c->adev 已非空，就把 duplicate 记为真，但 c->adev 不改。后来的 master 装配时这个槽位形同虚设。

十三、反装配：unbind 的顺序 #

拆卸的入口有两条，终点是一个函数：

text
component_master_del(dev, ops)      -> 找 master，卸掉
任一 component 调 component_del()   -> remove_component() -> 若曾归属某 master，把 master 也拆掉

remove_component() 是拆解核心，它会：如果该 component 归属某个 adev 且那个 adev 已 bound，调 master 的 unbind；把 adev 的 bound 清掉，让它下次能重新装配；清理 match 数组里对应槽位的 component 指针。这个函数在 4.x 与 5.x 之间也随命名改过，5.x 里断言了 mutex_is_locked(&component_mutex)，即必须在锁内调用。具体函数体未逐行引用，未验证。

master 的 unbind 里，标准做法是调 component_unbind_all()：

c
void component_unbind_all(struct device *parent, void *data)
{
	struct aggregate_device *adev;
	struct component *c;
	size_t i;

	WARN_ON(!mutex_is_locked(&component_mutex));
	adev = __aggregate_find(parent, NULL);
	if (!adev)
		return;
	/* Unbind components in reverse order */
	for (i = adev->match->num; i-- > 0; )
		if (!adev->match->compare[i].duplicate) {
			c = adev->match->compare[i].component;
			component_unbind(c, adev, data);
		}
}

注释同样直白：/* Unbind components in reverse order */。for (i = num; i-- > 0; ) 是先自减再判断，i 从 num-1 走到 0，严格倒序。component_unbind() 会依次做：置 component->bound = false，调 component->ops->unbind(comp, master, data)，然后 devres_release_group(component->dev, component) 回收这个零件在 bind 期间申请的资源。

阶段 顺序 依据
component_ops.bind match 数组正序 /* Bind components in match order */
component_ops.unbind match 数组逆序 /* Unbind components in reverse order */
component_master_ops.bind 在第一个 component 的 bind 之前 component_bind_all() 由 master bind 调用
component_master_ops.unbind 在最后一个 component 的 unbind 之后 master unbind 里才调 component_unbind_all()

兜底场景：component_bind_all() 中途某个零件 bind 失败，它会自己回滚：

c
if (ret != 0) {
	for (; i > 0; i--)
		if (!adev->match->compare[i - 1].duplicate) {
			c = adev->match->compare[i - 1].component;
			component_unbind(c, adev, data);
		}
}

拆解起点是 i，即失败槽位的前一个。失败者自己不用 unbind，它的 bind 失败时已经走过 devres_release_group 了。

十四、RK3399 DRM 里的实际用法 #

RK3399 的显示子系统是 component 在 mainline 里最典型的用例之一。master 是 rockchip,display-subsystem 节点对应的驱动，代码在 drivers/gpu/drm/rockchip/rockchip_drm_drv.c，probe 里给每个 VOP 端口建 match，然后 component_master_add_with_match()。

component 侧是几类驱动，各自在 probe 里调 component_add()：

  • rockchip_drm_vop.c：VOP，compatible = "rockchip,rk3399-vop-big" / "rockchip,rk3399-vop-lit"。
  • analogix_dp-rockchip.c 一类：eDP 输出。
  • dw_hdmi-rockchip.c：HDMI 输出。
  • dw-mipi-dsi.c：MIPI DSI 输出。

共同点：probe 里除了硬件初始化（拿 clock、要 regulator、写 regmap），最后都调 component_add(&pdev->dev, &xxx_ops)；remove 里调 component_del()。装配顺序由 master 侧的 match 数组顺序决定：VOP 一定排最前，因为 DRM 的 crtc 由它在 component_ops.bind 里创建，而 encoder 要挂在 crtc 上。各零件的 component_ops.bind 都会拿到 master_data，即 struct rockchip_drm_private *：VOP 用它 drm_crtc_init_with_planes()，接口控制器用它 drm_encoder_init() 和 drm_connector_init()。

调试入口是 debugfs：

text
root@rk3399:~# ll /sys/kernel/debug/device_component/
-r--r--r--  1 root root 0 Jan  1  1970 display-subsystem
root@rk3399:~# cat /sys/kernel/debug/device_component/display-subsystem
aggregate_device name                                  status
-------------------------------------------------------------
display-subsystem                                       bound
device name                                            status
-------------------------------------------------------------
ff8f0000.vop                                            bound
ff900000.vop                                            bound
ff940000.hdmi                                           bound

这个文件由 component_debugfs_add() 在 master 注册时创建，文件名是 dev_name(adev->parent)，权限 0444，内容由 component_devices_show() 生成。核心逻辑：先打印 master 自己的 dev_name(m->parent) 和 m->bound ? "bound" : "not bound"，再按 match 数组顺序对 match->compare[i].component 逐行打印。整段在 component_mutex 锁内完成：

c
seq_printf(s, "%-40s %20s\n",
	   component ? dev_name(component->dev) : "(unknown)",
	   component ? (component->bound ? "bound" : "not bound") : "not registered");

看到 (unknown) / not registered 就是这一项没匹配上，master 永远不会 bind。挂着 debugfs 的板子上，/sys/kernel/debug/device_component/ 目录名和单个文件都能 cat，比加 printk 快得多。顺带说一句 duplicate：debugfs 输出里看不出来，要看有没有抢零件得自己加打印。

十五、VOP、eDP、HDMI 怎么组装成一个设备 #

把视角落到「一颗像素怎么从内存走到屏幕」。第一步，VOP 拿到帧缓冲：它的 bind 创建 drm_crtc 和 plane，注册到 rockchip_drm_private->drm_dev，必须在任何人之前，否则 CRTC 指针是空的。第二步，接口控制器挂上 CRTC：eDP 和 HDMI 的 bind 创建 drm_encoder 和 drm_connector，并通过 drm_encoder_init() 的 possible_crtcs 声明自己只能接哪些 CRTC。第三步，master 发布设备：所有 component 的 bind 都返回 0 之后，master 的 bind 才执行 drm_dev_register()，这时 /dev/dri/card0 才出现。

三步的编排全部落在这几个函数调用的位置上：

环节 代码位置 由谁写
描述要哪些零件 master probe 里 component_match_add() master 驱动
零件的初始化逻辑 component_ops.bind 各零件驱动
触发装配 master probe 里 component_master_add_with_match() master 驱动
统一发布 component_master_ops.bind 末尾 master 驱动

关系示意：

text
rockchip-drm (master, display-subsystem)
  |
  +-- component_bind_all(&pdev->dev, drm)
        |
        +-- [0] ff8f0000.vop   component_ops.bind  -> drm_crtc / plane
        +-- [1] ff900000.vop   component_ops.bind  -> drm_crtc / plane
        +-- [2] ff940000.hdmi  component_ops.bind  -> encoder / connector
        |
  +-- drm_dev_register()   <- 全部 bind 成功后

HDMI 的 bind 在 VOP 之后，这不是巧合，是 match 数组钉死的。想换顺序，只能改 master probe 里加 match 的先后。eDP 和 HDMI 物理上互不依赖，它们的相对顺序在 RK3399 里其实无所谓，但 VOP 必须在前。这就是「顺序只对真有依赖的地方重要」的实际情况。

十六、component 与 deferred probe 的关系 #

两者是两个独立机制，但会互相影响。deferred probe 解决「资源还没准备好，等会儿再来」，component 解决「等齐了再一起开工」。前者是时间问题，后者是集合问题。交界点在返回值上：

  • component_ops.bind 返回 -EPROBE_DEFER：component_bind_all() 停下并回滚已绑的零件，把错误码传给 master 的 bind，再传给 try_to_bring_up_aggregate_device()。后者看到 ret < 0，devres_release_group()，并且因为它等于 -EPROBE_DEFER，不打那条 adev bind failed 的 info 日志。装配失败，adev->bound 保持 false。
  • 接着 component_master_add_with_match() 把这个错误码返回给 master 驱动的 probe，probe 返回 -EPROBE_DEFER，platform 总线把 master 排进 deferred 队列，稍后重试。
  • 重试时 master 重新建 match、重新注册 aggregate_device，重走一遍装配。所以 master 的 probe 必须可重复执行。

这个「重来一遍」是关键理解。component 框架不保存中间态，失败就退干净。因此：master 的 probe 里不要做不可重入的全局副作用；component_match 每次重新建，matchptr 每次进 probe 都是 NULL，靠 devres 自动回收上一次的；不要在 component_master_ops.bind 里依赖「我只会被调一次」这个假设。

另一条路径：零件自己还没 probe，master 已注册完，find_components() 找不到某个零件，返回 0（未齐），component_master_add_with_match() 返回 0，master probe 成功，此时 master 处于「注册了但没 bind」的状态。等零件后来 probe 并调 component_add()，try_to_bring_up_masters() 再走一遍，这次齐了，装配成功。这就是为什么 component_master_add_with_match() 返回 0 有两种含义：装配成功，或者干等着。光看返回值分不出来，得看 adev->bound 或 debugfs 的 status 栏。

场景 master 返回值 adev->bound 后续谁触发
零件已齐，bind 成功 0 true 无
零件未齐 0 false 后到的 component 的 component_add()
bind 返回 -EPROBE_DEFER -EPROBE_DEFER false platform deferred probe 重试
bind 返回其他负数 该错误码 false 无自动重试，驱动 probe 失败

第四种最麻烦：bind 返回 -ENOMEM 之类的错误，platform 总线不会重试，显示子系统就永久不能用了。try_to_bring_up_aggregate_device() 里那句 dev_info(adev->parent, "adev bind failed: %d\n", ret) 是唯一的线索。

十七、写一个 component master 的完整骨架 #

下面是可直接抄的骨架，覆盖 master 侧该有的全部动作。命名随意，结构固定。

c
struct my_drm {
	struct device *dev;
	struct drm_device *drm;
};
static int my_component_bind(struct device *comp, struct device *master,
			     void *data)
{
	struct my_drm *priv = data;

	return 0;
}
static void my_component_unbind(struct device *comp, struct device *master,
				void *data)
{
	/* 严格对应 my_component_bind 做的每一件事 */
}
static const struct component_ops my_component_ops = {
	.bind = my_component_bind,
	.unbind = my_component_unbind,
};
static int my_master_bind(struct device *master)
{
	struct my_drm *priv = dev_get_drvdata(master);
	int ret;

	/* 1. 分配装配体自己的结构 */
	priv->drm = drm_dev_alloc(&my_drm_driver, master);
	if (IS_ERR(priv->drm))
		return PTR_ERR(priv->drm);
	/* 2. 以 priv 为 opaque 指针，绑定所有零件 */
	ret = component_bind_all(master, priv);
	if (ret)
		goto err_put;
	/* 3. 注册到子系统，对外发布 */
	ret = drm_dev_register(priv->drm, 0);
	if (ret) {
		component_unbind_all(master, priv);
		goto err_put;
	}
	return 0;
err_put:
	drm_dev_put(priv->drm);
	return ret;
}
static void my_master_unbind(struct device *master)
{
	struct my_drm *priv = dev_get_drvdata(master);

	drm_dev_unregister(priv->drm);
	component_unbind_all(master, priv);
	drm_dev_put(priv->drm);
}
static const struct component_master_ops my_master_ops = {
	.bind = my_master_bind,
	.unbind = my_master_unbind,
};
static int my_probe(struct platform_device *pdev)
{
	struct device *dev = &pdev->dev;
	struct component_match *match = NULL;
	struct device_node *np;
	struct my_drm *priv;

	priv = devm_kzalloc(dev, sizeof(*priv), GFP_KERNEL);
	if (!priv)
		return -ENOMEM;
	priv->dev = dev;
	platform_set_drvdata(pdev, priv);

	for_each_child_of_node(dev->of_node, np)
		component_match_add(dev, &match, compare_of, np);

	return component_master_add_with_match(dev, &my_master_ops, match);
}

static int my_remove(struct platform_device *pdev)
{
	component_master_del(&pdev->dev, &my_master_ops);
	return 0;
}

几个纪律点。my_master_bind 里的资源全部手工管，不用 devm：drm_dev_alloc 出来的东西在 my_master_unbind 里 drm_dev_put，一环漏了就泄漏。失败路径要对称，component_bind_all() 失败时已经自己回滚了零件，你只需要收拾 my_master_bind 里在它之前分配的东西。component_master_del() 的第二个参数必须和注册时传给 component_master_add_with_match() 的 ops 是同一个指针，内核用 dev + ops 两项定位。for_each_child_of_node 遍历子节点只是最简写法，真实驱动多数按 ports 属性挑节点；抄的时候注意 of_node_put(np) 的引用计数，component_match_add 不接管你的引用。

十八、常见错误与调试 #

症状：master 驱动 probe 了，但 debugfs 里没有条目。 说明 component_master_add_with_match() 没走到，或者走进去就返回了负数。先看 probe 里有没有提前 return，再看 match 是不是 ERR_PTR。__component_match_add() 在分配失败时会把 *matchptr 写成 ERR_PTR，此时继续往下调注册，component_match_realloc() 会拿到野指针。

症状：debugfs 里列出了条目，但状态是 not registered。 这一条 match 没找到零件，原因只有三类：零件的 dev 和 compare 判断对不上、零件根本没注册、零件被别的 master 抢走了。把 compare 的入参打一遍，dev_name(dev) 和 dev->of_node 都对一下。

症状：debugfs 里 master 是 bound，但某个零件是 not bound。 这个零件在 match 里是 duplicate，已被另一个 master 认领。find_components() 把 c->adev 留给先来的，后到的只能标 duplicate。查一下是不是有两个 master 的 match 都命中了同一个节点。

症状：一切正常，但屏幕不亮。 component 只管装配，不管硬件寄存器。该查的是各零件 component_ops.bind 里的硬件初始化，以及 master bind 末尾的 drm_dev_register() 有没有被调。debugfs 显示 bound 只说明回调成功返回了。

症状：unbind 后重装失败。 component_master_ops.unbind 里漏了 component_unbind_all()，或者 component_ops.unbind 没清干净零件状态。下次装配时 component->bound 之类的残留会让流程走到奇怪的地方。

调试手段按性价比排：

手段 打开方式 能看到什么

十九、易错点速查 #

# 易错点 后果 正确做法
1 用 devm_ 管 master bind 里的资源 资源释放时机错，泄漏或提前释放 bind 里手工分配，unbind 里手工释放
2 以为 component_master_add_with_match() 返回 0 就是装好了 后续逻辑等不到设备 看 adev->bound 或 debugfs 的 status
3 match 少加一条 装配成功但功能缺失，难察觉 对着 DTS 的 ports 逐项核对
4 match 多加一条 master 永不 bind，无报错 在 compare 里打日志确认命中情况
5 漏掉 component_del() 模块卸载后 component_list 留悬垂节点 remove 里与 add 对称调用
6 component_master_del() 传的 ops 与注册时不同 WARN_ON 触发，master 卸不掉 用同一个 static const 指针
7 把 compatible 字符串当匹配依据 框架根本不看它 匹配靠 compare 函数，compatible 要自己写进去
8 依赖 DTS 节点顺序控制 bind 顺序 顺序不受控，偶发失败 顺序只由 component_match 下标决定
9 component_match_add 的 matchptr 传非 NULL 初值 野指针或提前 ERR_PTR 每次进 probe 都从 NULL 开始
10 compare 里做重操作或打日志 每次装配尝试都跑，性能与噪声 compare 保持 O(1) 纯判断
11 component_ops.bind 返回 -EPROBE_DEFER 却没清理已分配资源 重试时泄漏 走 devres 或手工回滚
12 master 的 probe 不幂等 deferred probe 重试时状态错乱 每次重试都当第一次
13 用 4.x 函数名读 5.x 代码 找不到 try_to_bring_up_master 5.x 叫 try_to_bring_up_aggregate_device
14 忘了 compare 和 compare_typed 是「或」关系 以为两者同时生效 任一命中即返回
15 空 match 的 master 立刻 bind，什么都没绑 加之前先判 match->num

修正的错误

  1. 原文说 component_master_add_with_match() 最后「调用 try_to_bring_up_masters 函数尝试启动 aggregate_device」。错，那里调的是 try_to_bring_up_aggregate_device(adev, NULL)；try_to_bring_up_masters() 只在 __component_add() 里被调。

  3. 原文说 struct component_match_array 的 data 字段「保存了 compare、compare_typed 用到的匹配数据」，但字段列表漏了 release 和 duplicate 两项说明。本篇补全全字段。
