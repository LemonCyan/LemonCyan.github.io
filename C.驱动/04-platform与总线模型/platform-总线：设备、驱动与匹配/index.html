本篇讲什么：platform 这条「假总线」怎么把设备和驱动配对上。三个核心结构体的全字段、platform_bus_type 的全部回调、platform_match 的完整判定顺序、设备与驱动各自的注册路径、really_probe 的逐步流程、resource 与 platform_get_resource/platform_get_irq 系列，最后落到一个从 insmod 到 probe 跑通的完整实例。

本篇不讲什么：完整的 device/driver/bus/class 通用模型（device 的引用计数、kobject、sysfs 属性创建那套）在 B.内核/08-总线与设备模型 的《device、driver、bus、class：四个注册表》里，本篇只讲 platform 特有的那一层。设备树语法本身在 A.硬件与固件/06-设备树，本篇只讲 of_match_table 怎么参与匹配。struct class 与 device_create 见《struct_class设备类架构详解》。

同目录的其他篇：多个 platform 设备要装配成一个逻辑设备（DRM、V4L2 那类），看《component 框架：把多个设备装配成一个》。PCIe 控制器本身也是个 platform 设备，那部分链路看《Rockchip RK3399 - PCIe》。

素材版本范围：本篇素材横跨 3.x ~ 5.2.8。写到的内核源码行为，凡是能在 6.10 / 6.11 / 6.12 上游源码里核对过的，标注具体版本；核对不到的直接写「未验证」。

一、platform 总线为什么存在：SoC 内部那些探测不到的设备 #

1.1 先看真实总线怎么工作 #

一条真实总线，比如 PCI 或 USB，它至少干三件事：

  1. 物理上存在，有电气规范和时序；
  2. 能枚举——PCI 扫配置空间、USB 读描述符，主机控制器主动去问「你是什么设备、你的厂商 ID 是多少」；
  3. 设备可以随时插拔，热插拔事件走总线回调通知内核。

枚举这一步决定了「设备信息从哪来」。PCI 设备的信息不是人写的，是硬件自己吐出来的。所以 PCI 的设备节点是内核扫描时动态创建的，谁写驱动谁不需要知道总线上有几个显卡。

1.2 SoC 内部的这些控制器没有这个待遇 #

嵌入式 SoC 里有一大批外设控制器：GPIO 控制器、I2C 控制器、SPI 控制器、UART 控制器、PWM、看门狗、DMA、定时器、RTC……它们集成在芯片内部，通过片内互连（AXI/AHB/APB）挂在 CPU 的内存地址空间上。

它们有几个共同点：

  • 不能枚举。没有「读一个寄存器就知道这里有什么控制器」的机制。你在地址 0x114000a0 上读一下，读到的是未定义值，不是设备 ID。
  • 地址固定。第几个 UART 在哪个物理地址，写死在 SoC 的数据手册里。
  • 不可插拔。芯片焊上去就那些外设，不会多一个少一个。

所以，「设备信息」这个活没人替你做，必须由人写出来：这块板子有 4 个 UART，分别在哪几个地址、用哪几个中断号。

1.3 于是内核造了一条假总线 #

Linux 从 2.6 起引入 platform 总线，专门用来承载这类设备。说它「假」，是因为：

text
真实总线（PCI / USB / I2C / SPI）
  硬件存在 ──▶ 内核枚举 ──▶ 自动生成 device ──▶ 匹配 driver ──▶ probe
  ▲ 可以热插拔，设备随时来随时走

platform 总线
  硬件存在（但只在内存空间里）──▶ 没人枚举 ──▶ 人写 device ──▶ 匹配 driver ──▶ probe
  ▲ 不能热插拔，device 从开机到关机就那么几个

内核的注释自己说得挺直白：drivers/base/platform.c 文件头写的是 platform 'pseudo' bus for legacy devices——给历史遗留设备用的假总线。

1.4 它解决的真问题：驱动与 BSP 分离 #

早期内核里，每个 SoC 的每个控制器驱动都是自己的代码。S3C2440 的 I2C 驱动和 S3C6410 的 I2C 驱动是两份文件，内容 90% 相同，因为寄存器基址不一样。

platform 总线把这件事拆成两半：

谁 负责什么 写在哪
platform_device 这块板子有什么外设、地址是多少、中断号是多少 BSP（板级代码）或设备树
platform_driver 这个外设怎么操作、寄存器怎么读怎么写 SoC 厂商或通用驱动代码

驱动里从此不再出现 #define UART_BASE 0x11400000，改成 platform_get_resource(pdev, IORESOURCE_MEM, 0)。换一块板子，只改 BSP，驱动一行不动。

这就是「设备驱动分离」。它带来三个直接好处：

  • 一份驱动能同时支持多个同系列 SoC；
  • 换板子不改驱动；
  • 地址冲突在设备注册阶段就能被内核发现（insert_resource 会失败），不必等到运行时莫名其妙写坏别的外设。

1.5 必须澄清的概念：platform 是分类维度 B，不是 A #

这条最容易被讲混。platform_device 不是与字符设备、块设备、网络设备并列的东西。

        分类维度 A：用户怎么访问         分类维度 B：怎么被找到并绑定驱动
        ─────────────────────          ──────────────────────────────
        字符设备  ┐                     PCI 设备
        块设备    ├─ 并列关系            USB 设备
        网络设备  ┘                     I2C 设备
                                        SPI 设备
                                        platform 设备 ← 虚拟总线，收纳「没有总线」的

S3C6410 内部集成的 I2C、RTC、SPI、LCD、看门狗控制器，同时是 platform 设备和字符设备。platform 这一层只决定「怎么被找到、怎么被绑定驱动、资源从哪取」，完全不改变「用户怎么 open/read」。

所以写一个 platform 字符驱动的实际工作量是：字符设备那一套原样保留（cdev、file_operations、dev_t、device_create），只是把原来 module_init 里干的事搬进 probe，module_exit 里的搬进 remove，然后 module_init 只留一行 platform_driver_register。

二、platform_device 与 platform_driver 的结构 #

2.1 名词铺垫：BSP #

BSP 即 Board Support Package（板级支持包）。操作系统被设计成运行在虚拟硬件平台上，具体硬件相关的代码全被封装在 BSP 里，由 BSP 向上提供一个虚拟硬件平台。BSP 是所有与硬件相关代码的集合。

在设备树出现之前，platform_device 就定义在 BSP 的板文件里（arch/arm/mach-xxx/board-xxx.c）。设备树之后，这部分搬到了 .dts，由内核启动时遍历设备树、自动生成 platform_device——但结构体还是同一个。

2.2 struct platform_device 全字段 #

先给一个最小版本（3.x 时代的样子，老教材基本都是这个）：

c
struct platform_device {
    const char      *name;          /* 设备名 */
    int             id;             /* 设备 id */
    struct device   dev;            /* 内嵌的通用设备结构 */
    u32             num_resources;  /* 资源数量 */
    struct resource *resource;      /* 资源数组 */
};

内核实现在的完整定义（6.11 / 6.12 一致，见 include/linux/platform_device.h）：

c
struct platform_device {
    const char      *name;
    int             id;
    bool            id_auto;
    struct device   dev;
    u64             platform_dma_mask;
    struct device_dma_parameters dma_parms;
    u32             num_resources;
    struct resource *resource;

    const struct platform_device_id *id_entry;
    /*
     * Driver name to force a match.  Do not set directly, because core
     * frees it.  Use driver_set_override() to set or clear it.
     */
    const char      *driver_override;

    /* MFD cell pointer */
    struct mfd_cell *mfd_cell;

    /* arch specific additions */
    struct pdev_archdata archdata;
};

逐字段说明：

字段 作用 备注
name 设备名，name 匹配的比对对象 与 drv->name 或 id_table[].name 比
id 实例编号 -1/0/1…，见下一张表
id_auto 标记 id 是内核自动分配的 由 PLATFORM_DEVID_AUTO 触发，注销时要还回去
dev 内嵌的 struct device 必须有，container_of 靠它反推
platform_dma_mask DMA 掩码的存放处 5.x 后加的默认 32 位掩码存储位置
dma_parms DMA 参数 platform_device_alloc 里挂到 dev.dma_parms
num_resources resource[] 的元素个数 与数组长度必须一致
resource 资源数组指针 全篇重点，见第十二章
id_entry id_table 命中项的指针 由 platform_match_id 回填，驱动在 probe 里读它
driver_override 强制指定只匹配哪个驱动 通过 sysfs driver_override 写，别手动赋值
mfd_cell MFD 框架的 cell 指针 MFD 拆分多设备时用
archdata 架构私有数据 各架构自己定义

id 的取值规则要记牢：

id 语义 /sys/devices/platform/ 下的名字
PLATFORM_DEVID_NONE（-1） 只有一个该类设备 foo
0、1、2… 多个同类设备，按编号区分 foo.0、foo.1…
PLATFORM_DEVID_AUTO（-2） 让内核自动分配 foo.0.auto、foo.1.auto…

后两种是两个宏，值固定：

c
#define PLATFORM_DEVID_NONE  (-1)
#define PLATFORM_DEVID_AUTO  (-2)

注意 AUTO 分配出来的名字带 .auto 后缀，这是故意的——避免和显式写的 foo.0 撞名字。

2.3 struct platform_driver 全字段 #

老版本（3.x，素材里的样子）：

c
struct platform_driver {
    int  (*probe)(struct platform_device *);
    int  (*remove)(struct platform_device *);
    void (*shutdown)(struct platform_device *);
    int  (*suspend)(struct platform_device *, pm_message_t state);
    int  (*suspend_late)(struct platform_device *, pm_message_t state);
    int  (*resume_early)(struct platform_device *);
    int  (*resume)(struct platform_device *);
    struct pm_ext_ops *pm;
    struct device_driver driver;
};

这个版本有两个现在已经不存在的成员：suspend_late / resume_early（早期平台电源管理的遗留），以及 pm_ext_ops。在 5.x 时代它们已经不在了，pm_ext_ops 类型在主干里早就删了（具体删于哪个版本未验证）。

当前的定义（6.9/6.10 是 int (*remove) 加 remove_new，6.11/6.12 已经合回一个 void 的 remove）：

c
struct platform_driver {
    int (*probe)(struct platform_device *);
    /*
     * .remove_new() is a relic from a prototype conversion of .remove().
     * New drivers are supposed to implement .remove(). Once all drivers are
     * converted to not use .remove_new any more, it will be dropped.
     */
    union {
        void (*remove)(struct platform_device *);
        void (*remove_new)(struct platform_device *);
    };
    void (*shutdown)(struct platform_device *);
    int (*suspend)(struct platform_device *, pm_message_t state);
    int (*resume)(struct platform_device *);
    struct device_driver driver;
    const struct platform_device_id *id_table;
    bool prevent_deferred_probe;
    bool driver_managed_dma;
};

remove 的返回值变化是这一段最值得记住的版本坑：

内核版本 签名 说明
3.x ~ 6.9 int (*remove)(struct platform_device *) 返回 int，但驱动核心一直忽略返回值
6.9 ~ 6.10 int (*remove) 与 void (*remove_new) 并存 remove_new 是过渡期产物，新驱动先写它
6.11 / 6.12 void (*remove) 与 remove_new 组成 union 收敛成一个 void 回调

依据：6.9 与 6.10 的 platform_device.h 里 remove 仍是 int、旁边有 remove_new 且带那段注释；6.11 与 6.12 里两者已经是 union，都是 void。改成 void 的理由就写在注释里：返回 int 会让写驱动的人误以为返回错误码能起到错误处理的作用，而驱动核心根本不看它。

remove_new 是哪个版本引入的、哪个版本彻底消失，未验证——我只核对了 6.9 / 6.10 / 6.11 / 6.12 四个点。

其余字段：

成员 何时被调用 该干什么
probe() 匹配成功、really_probe 走到最后一步 申请资源、注册字符设备、初始化硬件（原来的 module_init 内容搬过来）
remove() 设备注销、驱动卸载、unbind 反向释放（原来的 module_exit 内容搬过来），必须与 probe 严格对称
shutdown() 系统关机 让硬件进入安全态（关蜂鸣器、停 DMA）
suspend() / resume() 早期电源管理 与现代 dev_pm_ops 并存，新驱动建议走 driver.pm
driver — struct device_driver，内核里所有驱动都必须有
id_table 匹配阶段 「驱动名 ≠ 设备名」或者一个驱动支持多款芯片时用
prevent_deferred_probe 匹配/探测阶段 置位后 -EPROBE_DEFER 会被改成 -ENXIO
driver_managed_dma DMA 配置阶段 驱动自己管 DMA 时置位，绕开 IOMMU 默认域

platform_driver → device_driver 的强转靠宏：

c
#define to_platform_driver(drv) (container_of((drv), struct platform_driver, driver))

driver 的完整定义在 6.11 的 include/linux/device/driver.h：

c
struct device_driver {
    const char          *name;
    const struct bus_type *bus;

    struct module       *owner;
    const char          *mod_name;      /* used for built-in modules */

    bool suppress_bind_attrs;           /* disables bind/unbind via sysfs */

2.4 platform_device_id #

id_table 的元素类型，定义在 include/linux/mod_devicetable.h：

c
struct platform_device_id {
    char name[PLATFORM_NAME_SIZE];
    kernel_ulong_t driver_data;
};

PLATFORM_NAME_SIZE 的值是 20（素材未给，按内核头文件为准；未在 6.11 源码中实读确认，标未验证）。driver_data 是给驱动塞型号标记用的，probe 里通过 platform_get_device_id(pdev)->driver_data 取。

c
#define platform_get_device_id(pdev) ((pdev)->id_entry)

2.5 of_device_id #

of_match_table 的元素类型，同样在 include/linux/mod_devicetable.h：

c
struct of_device_id {
    char name[32];
    char type[32];
    char compatible[128];
    const void *data;
};

匹配时比对的是 compatible 字段（具体规则见第八章）。name 和 type 主要是老 PowerPC 时代用的，现代 ARM 基本只填 compatible。

三、platform_bus_type：一个几乎不做匹配的总线 #

3.1 bus_type 长什么样 #

所有总线（I2C、SPI、USB、platform）都用 struct bus_type 描述，定义在 include/linux/device.h：

c
struct bus_type {
    const char              *name;
    const char              *dev_name;
    struct device           *dev_root;
    const struct attribute_group **bus_groups;
    const struct attribute_group **dev_groups;
    const struct attribute_group **drv_groups;

    int  (*match)(struct device *dev, struct device_driver *drv);
    int  (*uevent)(struct device *dev, struct kobj_uevent_env *env);
    int  (*probe)(struct device *dev);
    void (*remove)(struct device *dev);
    void (*shutdown)(struct device *dev);

    int  (*online)(struct device *dev);
    int  (*offline)(struct device *dev);

    int  (*suspend)(struct device *dev, pm_message_t state);
    int  (*resume)(struct device *dev);

    int  (*num_vf)(struct device *dev);
    int  (*dma_configure)(struct device *dev);
    void (*dma_cleanup)(struct device *dev);

    const struct dev_pm_ops *pm;
    const struct iommu_ops *iommu_ops;

    struct subsys_private *p;
    struct lock_class_key lock_key;
    bool need_parent_lock;
};

关键几个：

  • match：有新设备或新驱动挂到这条总线上时被调用，会调不止一次。返回正数表示能处理，0 表示不匹配，返回 -EPROBE_DEFER 会把设备排进延迟探测队列。
  • probe / remove / shutdown：总线级的兜底回调。驱动核心优先走总线的，没有才走 device_driver 的。really_probe 里就是这么写的：if (dev->bus->probe) ret = dev->bus->probe(dev); else if (drv->probe) ret = drv->probe(dev);
  • uevent：添加/删除设备时往环境变量里塞东西（MODALIAS 就是这里加的）。
  • pm：总线的电源管理 ops。

.match 有 有 有 platform_match
.uevent 有 有 有 platform_uevent，填 MODALIAS
.probe 无 无 有 platform_probe，做 OF 时钟/PM domain 准备后再回调驱动
.remove 无 无 有 platform_remove，回调驱动 remove 后拆 PM domain
.shutdown 无 无 有 platform_shutdown
.dma_configure 无 有 有 配 DMA / IOMMU 默认域
.dma_cleanup 无 无 有 拆 IOMMU 默认域
.pm PLATFORM_PM_OPS_PTR platform_dev_pm_ops platform_dev_pm_ops 电源管理

这张表纠正了素材里一句很常见的话：「默认 platform_bus_type 中没有定义 probe 函数」。这句话只在 5.x 及以前成立。 6.x 主干里 .probe / .remove / .shutdown 三个回调都有了，而且 platform_probe 不是空的，它在回调你的 probe 之前还要干两件事：

c
static int platform_probe(struct device *_dev)
{
    struct platform_driver *drv = to_platform_driver(_dev->driver);
    struct platform_device *dev = to_platform_device(_dev);
    int ret;

    /*
     * A driver registered using platform_driver_probe() cannot be bound
     * again later because the probe function usually lives in __init code
     * and so is gone. For these drivers .probe is set to
     * platform_probe_fail in __platform_driver_probe(). Don't even prepare
     * clocks and PM domains for these to match the traditional behaviour.
     */
    if (unlikely(drv->probe == platform_probe_fail))
        return -ENXIO;

    ret = of_clk_set_defaults(_dev->of_node, false);
    if (ret < 0)
        return ret;

    ret = dev_pm_domain_attach(_dev, true);
    if (ret)
        goto out;

    if (drv->probe) {
        ret = drv->probe(dev);
        if (ret)
            dev_pm_domain_detach(_dev, true);
    }
out:
    if (drv->prevent_deferred_probe && ret == -EPROBE_DEFER) {
        dev_warn(_dev, "probe deferral not supported\n");
        ret = -ENXIO;
    }
    return ret;
}

也就是说 6.x 里 probe 这一层的调用链是三层，不是两层：

really_probe()
  └─ call_driver_probe()
       └─ dev->bus->probe()  ==  platform_probe()
            ├─ of_clk_set_defaults(of_node, false)     /* 按 dts 配时钟 */
            ├─ dev_pm_domain_attach(dev, true)         /* 挂 PM domain */
            └─ drv->probe(dev)  ==  你写的 probe()

素材三那份 5.2.8 时代的论述「过程中的驱动基类 driver 的 probe 函数和 platform_drv_probe 函数都是达到这个目的的中转函数而已」，在 5.2.8 上成立（那时是 drv->driver.probe = platform_drv_probe）。6.x 里过渡函数换了名字和位置，从 drv->driver.probe 挪到了 bus->probe，名字叫 platform_probe。这是查老资料对不上 6.x 源码的常见原因之一。

3.3 为什么说它「几乎不做匹配」 #

platform 的 match 回调里没有一次硬件访问。它做的事就是：

比字符串：
  pdev->driver_override 和 drv->name      ─ 强制绑定
  of_match_device / acpi_match_device     ─ 比 compatible
  id_table[] 里的 name 和 pdev->name      ─ 比名字表
  pdev->name 和 drv->name                 ─ 比名字

没有读寄存器，没有发命令，没有超时等待。原因是 platform 没有物理总线可读——它要匹配的那个「设备」根本不是硬件探测出来的对象，是另一个软件结构体。

这个反直觉的性质推出一条重要结论：platform 的匹配是「两个结构体之间比名字」，而不是「驱动问硬件你是谁」。 所以：

  • 名字写错一个字符，就永远匹配不上，而且不会报错——设备静静挂在 /sys/bus/platform/devices/ 下面，drivers/ 里对应目录是空的。
  • 没有任何热插拔的余地。设备注册时驱动不在，就等；驱动注册时设备不在，也等。只有第二个来的一方才触发匹配。
  • 一个设备只能绑定一个驱动，一个驱动可以绑定多个设备，靠 id 区分。

3.4 platform_uevent：假总线也有热插拔事件 #

虽然 platform 不能热插拔硬件，设备注册时仍然要产生 uevent，让用户空间有机会自动 modprobe 驱动模块。

3.x 的版本很简单：

c
static int platform_uevent(struct device *dev, struct kobj_uevent_env *env)
{
    struct platform_device *pdev = to_platform_device(dev);

    add_uevent_var(env, "MODALIAS=%s%s",
                   PLATFORM_MODULE_PREFIX,
                   (pdev->id_entry) ? pdev->id_entry->name : pdev->name);
    return 0;
}

5.2.8 / 6.11 的版本多了 OF 和 ACPI 两条分支：

c
static int platform_uevent(const struct device *dev, struct kobj_uevent_env *env)
{
    const struct platform_device *pdev = to_platform_device(dev);
    int rc;

    /* Some devices have extra OF data and an OF-style MODALIAS */
    rc = of_device_uevent_modalias(dev, env);
    if (rc != -ENODEV)
        return rc;
    rc = acpi_device_uevent_modalias(dev, env);
    if (rc != -ENODEV)
        return rc;
    add_uevent_var(env, "MODALIAS=%s%s", PLATFORM_MODULE_PREFIX, pdev->name);
    return 0;
}

PLATFORM_MODULE_PREFIX 是 "platform:"。所以从设备树生成的设备，modalias 是 of:NxxxTnullCvendor,chip 这种格式；手工声明的设备是 platform:bigbang。

sysfs 里也直接暴露了它，同一个值可以从 modalias 文件读：

c
static ssize_t modalias_show(struct device *dev, struct device_attribute *attr, char *buf)
{
    struct platform_device *pdev = to_platform_device(dev);
    int len;

    len = of_device_modalias(dev, buf, PAGE_SIZE);
    if (len != -ENODEV)
        return len;
    len = acpi_device_modalias(dev, buf, PAGE_SIZE - 1);
    if (len != -ENODEV)
        return len;
    return sysfs_emit(buf, "platform:%s\n", pdev->name);
}

从 device_add() 到 uevent 的链路：

text
platform_device_add()
  └─ device_add()
       └─ kobject_uevent(&dev->kobj, KOBJ_ADD)
            └─ kset->uevent_ops->uevent  ==  dev_uevent()
                 └─ dev->bus->uevent  ==  platform_uevent()
                      └─ env 里塞 MODALIAS
                           └─ 用户态 udev/mdev 读到 MODALIAS → modprobe

/sys/bus/platform/devices/<name>/modalias 是排查「设备在但驱动没加载」的第一站。

四、platform_device 的注册流程 #

4.1 总线自己先注册 #

设备要注册到总线上，总线得先在。platform 总线的初始化发生在内核启动的早期：

text
start_kernel()
  └─ rest_init()
       └─ kernel_init()
            └─ do_basic_setup()
                 └─ driver_init()
                      └─ platform_bus_init()

platform_bus_init 在 drivers/base/platform.c（6.11 原文）：

c
int __init platform_bus_init(void)
{
    int error;

    early_platform_cleanup();

    error = device_register(&platform_bus);
    if (error) {
        put_device(&platform_bus);
        return error;
    }
    error = bus_register(&platform_bus_type);
    if (error)
        device_unregister(&platform_bus);
    return error;
}

这里有两个名字极像的东西，必须分清：

c
struct device platform_bus = {
    .init_name = "platform",
};
EXPORT_SYMBOL_GPL(platform_bus);

const struct bus_type platform_bus_type = { ... };
EXPORT_SYMBOL_GPL(platform_bus_type);
名字 类型 注册函数 在 sysfs 里
platform_bus struct device device_register(&platform_bus) /sys/devices/platform/
platform_bus_type struct bus_type bus_register(&platform_bus_type) /sys/bus/platform/

platform_bus 是「所有 platform 设备的父设备」，platform_bus_type 才是「总线」。 新手最容易把这两个当成同一个东西，然后在读 pdev->dev.parent = &platform_bus 时想不通「为什么 parent 是个 device 而不是 bus」。

5.2.8 的 platform_bus_init 多一行，末尾调了 of_platform_register_reconfig_notifier()（素材三原文有）；6.11 里这一行已经不在这个函数里了。

bus_register 执行完之后，用户空间就能看到 platform 总线的完整骨架：

bash
root@zhengyang:/work/sambashare/linux-5.2.8# ls /sys/bus/platform/
devices  drivers  drivers_autoprobe  drivers_probe  uevent

其中 devices 是已注册的 platform 设备（都是符号链接，指向 /sys/devices/platform/ 下的真实节点），drivers 是已注册的 platform 驱动目录。

bash

ACPI0003:00  Fixed MDIO bus.0  pcspkr                  PNP0001:00  reg-dummy
alarmtimer   i8042             platform-framebuffer.0  PNP0800:00  serial8250

4.2 设备的注册有两条路径 #

方式 做法 适用
静态 提供一个初始化好的全局 platform_device，调 platform_device_register() 传统 BSP，设备数量与资源固定
动态 platform_device_alloc() → platform_device_add_resources() / _add_data() → platform_device_add() 运行时才知道有几个设备、资源要复用

两条路径最终都汇到 platform_device_add()。所有其他注册函数都基于它：platform_device_register()、platform_device_register_simple()、platform_device_register_data()、platform_device_register_full()、platform_add_devices() 全是包一层的便捷接口。

4.3 platform_device_register() 与 device_register() 的区别 #

device_register() platform_device_register()
参数 struct device * struct platform_device *（内嵌 struct device，另加 resource[]）
资源 无 有，会调用 insert_resource 占住地址区间
总线 由调用者自己设 dev->bus 强制设成 platform_bus_type
父设备 由调用者自己设 没设就填成 platform_bus
适用 任意设备 有独立资源描述、无物理总线的设备

一句话：platform_device–platform_driver 机制与 device–driver 机制的主要区别就在 resource。前者适合有独立资源描述的设备，后者不是。Linux 各种其他驱动机制的基础都是 device–driver，platform 只是在它上面加了资源管理。

4.4 platform_device_register() #

c
/**
 * platform_device_register - add a platform-level device
 * @pdev: platform device we're adding
 *
 * NOTE: _Never_ directly free @pdev after calling this function, even if it
 * returned an error! Always use platform_device_put() to give up the
 * reference initialised in this function instead.
 */
int platform_device_register(struct platform_device *pdev)
{
    device_initialize(&pdev->dev);
    setup_pdev_dma_masks(pdev);
    return platform_device_add(pdev);
}

5.2.8 里中间那行是 arch_setup_pdev_archdata(pdev)（素材三原文），6.x 里换成了 setup_pdev_dma_masks——给没设过 DMA 掩码的设备配默认 32 位掩码。这个改名说明 5.x 之后 platform 设备默认带 DMA 能力，不需要架构代码特殊处理。

那行文档注释值得看一眼：函数返回错误时不要直接 kfree(pdev)，因为 device_initialize 已经给 dev 初始化了引用计数，得走 platform_device_put()。

4.5 platform_device_add()（核心，6.11 原文） #

c
int platform_device_add(struct platform_device *pdev)
{
    struct device *dev = &pdev->dev;
    u32 i;
    int ret;

    if (!dev->parent)
        dev->parent = &platform_bus;
    dev->bus = &platform_bus_type;

    switch (pdev->id) {
    default:
        dev_set_name(dev, "%s.%d", pdev->name, pdev->id);
        break;
    case PLATFORM_DEVID_NONE:
        dev_set_name(dev, "%s", pdev->name);
        break;
    case PLATFORM_DEVID_AUTO:
        /*
         * Automatically allocated device ID. We mark it as such so
         * that we remember it must be freed, and we append a suffix
         * to avoid namespace collision with explicit IDs.
         */
        ret = ida_alloc(&platform_devid_ida, GFP_KERNEL);
        if (ret < 0)
            return ret;
        pdev->id = ret;
        pdev->id_auto = true;
        dev_set_name(dev, "%s.%d.auto", pdev->name, pdev->id);
        break;
    }

    for (i = 0; i < pdev->num_resources; i++) {
        struct resource *p, *r = &pdev->resource[i];

        if (r->name == NULL)
            r->name = dev_name(dev);

        p = r->parent;
        if (!p) {
            if (resource_type(r) == IORESOURCE_MEM)
                p = &iomem_resource;
            else if (resource_type(r) == IORESOURCE_IO)
                p = &ioport_resource;
        }
        if (p) {
            ret = insert_resource(p, r);
            if (ret) {
                dev_err(dev, "failed to claim resource %d: %pR\n", i, r);
                goto failed;
            }
        }
    }
    pr_debug("Registering platform device '%s'. Parent at %s\n",
             dev_name(dev), dev_name(dev->parent));

    ret = device_add(dev);
    if (ret)
        goto failed;
    return 0;

failed:
    if (pdev->id_auto) {
        ida_free(&platform_devid_ida, pdev->id);
        pdev->id = PLATFORM_DEVID_AUTO;
    }
    while (i--) {
        struct resource *r = &pdev->resource[i];
        if (r->parent)
            release_resource(r);
    }
    return ret;
}

按执行顺序拆成五个动作：

  1. 定 parent：dev->parent 为空就填 &platform_bus。效果是在 /sys/devices/platform/ 下出现这个设备。
  2. 定总线：dev->bus = &platform_bus_type。这是匹配的开关——device_add() 会检查 dev->bus，总线不为空才去遍历驱动链表。
  3. 定名字：id 三个分支，-1 不加后缀，-2 走 IDA 拿号再加 .auto。
  4. 占资源：resource[] 逐项 insert_resource 到 iomem_resource / ioport_resource 这棵资源树里，这一步顺手就检测了地址冲突——两个设备抢同一段寄存器地址，这里直接 -EBUSY 掉。
  5. 挂设备：device_add()。

失败回滚：

  • id_auto 为真时先还 IDA 号，并把 id 恢复成 PLATFORM_DEVID_AUTO；
  • 然后 while (i--) 逆序释放已经插进资源树的资源。注意判断条件从素材早期的 if (type == IORESOURCE_MEM || type == IORESOURCE_IO) 变成了 if (r->parent)：谁进过树谁才需要出来，靠 parent 指针判断比靠 flags 判断更准（IORESOURCE_IRQ 若被显式挂在别的资源下面是会有 parent 的）。

超时素材里那段老代码用的是 ida_simple_get(&platform_devid_ida, 0, 0, GFP_KERNEL) / ida_simple_remove，这两个接口在 5.x 之后被 ida_alloc / ida_free 取代（具体替换于哪个版本未验证，但 6.11 已是 ida_alloc）。

4.6 动态申请：platform_device_alloc() #

c
struct platform_object {
    struct platform_device pdev;
    char name[];
};

struct platform_device *platform_device_alloc(const char *name, int id)
{
    struct platform_object *pa;

    pa = kzalloc(sizeof(*pa) + strlen(name) + 1, GFP_KERNEL);
    if (pa) {
        strcpy(pa->name, name);
        pa->pdev.name = pa->name;
        pa->pdev.id = id;
        device_initialize(&pa->pdev.dev);
        pa->pdev.dev.release = platform_device_release;
        setup_pdev_dma_masks(&pa->pdev);
    }
    return pa ? &pa->pdev : NULL;
}

这里有个柔性数组技巧：struct platform_object 末尾的 char name[] 没有长度，kzalloc 时一次性多给 strlen(name) + 1 字节，名字就紧贴在结构体后面。一次分配、一次释放，不用单独 kfree 名字。

（3.x 里写的是 char name[1]，kzalloc 时只加 strlen(name)；6.x 改成了真正的柔性数组并 +1 给 \0。老代码照抄会少一个字节。）

配的释放函数：

c
static void platform_device_release(struct device *dev)
{
    struct platform_object *pa = container_of(dev, struct platform_object, pdev.dev);

    of_node_put(pa->pdev.dev.of_node);
    kfree(pa->pdev.dev.platform_data);
    kfree(pa->pdev.mfd_cell);
    kfree(pa->pdev.resource);
    kfree(pa->pdev.driver_override);
    kfree(pa);
}

注意它按顺序放了 of_node、platform_data、mfd_cell、resource、driver_override，最后才放 pa 本身。

4.7 platform_device_add_resources() #

c
int platform_device_add_resources(struct platform_device *pdev,
                                  const struct resource *res, unsigned int num)
{
    struct resource *r = NULL;

    if (res) {
        r = kmemdup_array(res, num, sizeof(*r), GFP_KERNEL);
        if (!r)
            return -ENOMEM;
    }
    kfree(pdev->resource);
    pdev->resource = r;
    pdev->num_resources = num;
    return 0;
}

这是深拷贝。 pdev->resource 指向新分配的内存，不再引用调用者的数组。所以调用方把 res 定义成栈上的局部变量是安全的——但只有配合 platform_device_alloc() 时才成立，静态设备直接 .resource = res，栈退出就悬空了。

（3.x 里是 kmalloc + memcpy 两步，且没有 kfree(pdev->resource)，重复调用会泄漏；6.x 换 kmemdup_array 并先释放旧数组。）

配套的 platform_device_add_data() 同理，只是拷的是 dev.platform_data：

c
int platform_device_add_data(struct platform_device *pdev,
                             const void *data, size_t size)
{
    void *d = NULL;

    if (data) {
        d = kmemdup(data, size, GFP_KERNEL);
        if (!d)
            return -ENOMEM;
    }
    kfree(pdev->dev.platform_data);
    pdev->dev.platform_data = d;
    return 0;
}

platform_data 就是驱动拿板级私有数据的老路子——比如一个 GPIO 编号、一个引脚极性。设备树时代它被 of_property_read_*() 取代了，但很多老驱动还在用。

4.8 一步到位：platform_device_register_simple() #

5.2.8 里的实现（素材三原文，函数体在 .c 里）：

c
struct platform_device *platform_device_register_simple(const char *name, int id,
                                                        struct resource *res,
                                                        unsigned int num)
{
    struct platform_device *pdev;
    int retval;

    pdev = platform_device_alloc(name, id);
    if (!pdev) {
        retval = -ENOMEM;
        goto error;
    }
    if (num) {
        retval = platform_device_add_resources(pdev, res, num);
        if (retval)
            goto error;
    }
    retval = platform_device_add(pdev);
    if (retval)
        goto error;

    return pdev;

error:
    platform_device_put(pdev);
    return ERR_PTR(retval);
}

6.x 里它被改写成了头文件里的内联函数，走一个统一的 platform_device_register_full()：

c
#define platform_device_register_simple(name, id, res, num) \
    platform_device_register_resndata(NULL, name, id, res, num, NULL, 0)

c
static inline struct platform_device *platform_device_register_resndata(
        struct device *parent, const char *name, int id,
        const struct resource *res, unsigned int num,
        const void *data, size_t size)
{
    struct platform_device_info pdevinfo = {
        .parent = parent,
        .name   = name,
        .id     = id,
        .res    = res,
        .num_res   = num,
        .data   = data,
        .size_data = size,
        .dma_mask  = 0,
    };
    return platform_device_register_full(&pdevinfo);
}

platform_device_register_full() 是现在真正的落地实现，它比老的 _simple 多管了三件事：fwnode / of_node、dma_mask、properties（软件节点）。

返回值语义要看清：成功返回 struct platform_device *，失败返回 ERR_PTR()。 用 IS_ERR() 判断，别直接判 NULL。

4.9 批量注册：platform_add_devices() #

c
int platform_add_devices(struct platform_device **devs, int num)
{
    int i, ret = 0;

    for (i = 0; i < num; i++) {
        ret = platform_device_register(devs[i]);
        if (ret) {
            while (--i >= 0)
                platform_device_unregister(devs[i]);
            break;
        }
    }
    return ret;
}

典型用法就是 BSP 里一个数组把所有板级设备列出来：

c
static struct platform_device *fs4412_devices[] __initdata = {
    &s3c_device_uart0,
    &s3c_device_uart1,
    &s3c_device_i2c0,
    &s3c_device_wdt,
};

static void __init fs4412_machine_init(void)
{
    platform_add_devices(fs4412_devices, ARRAY_SIZE(fs4412_devices));

4.10 设备注册的完整调用链 #

text
platform_device_register()
  ├─ device_initialize(&pdev->dev)      /* 引用计数 = 1，kobject 初始化 */
  ├─ setup_pdev_dma_masks(pdev)         /* 默认 32 位 DMA 掩码 */
  └─ platform_device_add()
       ├─ dev->parent ?: &platform_bus
       ├─ dev->bus = &platform_bus_type
       ├─ dev_set_name(...)              /* foo / foo.0 / foo.0.auto */
       ├─ insert_resource() × num_resources
       └─ device_add()
            ├─ 在 sysfs 建目录 + dev_groups 属性
            ├─ kobject_uevent(KOBJ_ADD)  → platform_uevent → MODALIAS
            └─ bus_probe_device()
                 └─ device_initial_probe()
                      └─ __device_attach(dev, true)
                           └─ bus_for_each_drv(&platform_bus_type, ...)
                                └─ __device_attach_driver()
                                     ├─ driver_match_device() == platform_match()
                                     └─ driver_probe_device()
                                          └─ really_probe()      ← 第九章

注意 device_add() 内部就会回去遍历驱动链表。 所以「先注册设备、后注册驱动」之所以能匹配上，是靠后面驱动注册时走另一条对称的遍历；「先注册驱动、后注册设备」则是靠这里。两条路径都通到 really_probe()，见第十章。

五、platform_driver 的注册流程 #

5.1 platform_driver_register() 是个宏 #

先纠正一个几乎人人都会踩的坑：platform_driver_register 不是函数，是宏。

c
/*
 * use a macro to avoid include chaining to get THIS_MODULE
 */
#define platform_driver_register(drv) \
    __platform_driver_register(drv, THIS_MODULE)
extern int __platform_driver_register(struct platform_driver *, struct module *);

之所以绕一层宏，是因为头文件里拿不到 THIS_MODULE（那是 module.h 的东西），用宏才能把当前模块的 THIS_MODULE 塞进去。所以你搜 platform_driver_register 的实现时会搜不到函数体——要找 __platform_driver_register。

5.2 __platform_driver_register() #

6.11 原文，只有三行：

c
int __platform_driver_register(struct platform_driver *drv, struct module *owner)
{
    drv->driver.owner = owner;
    drv->driver.bus = &platform_bus_type;
    return driver_register(&drv->driver);
}

5.2.8 同样是这三行（素材三原文）。6.x 里那个「把 platform 的 probe 包成过渡函数」的动作已经搬走了：

3.x 的样子（素材一原文，platform_drv_probe 那套）：

c
int platform_driver_register(struct platform_driver *drv)
{
    drv->driver.bus = &platform_bus_type;
    if (drv->probe)
        drv->driver.probe = platform_drv_probe;
    if (drv->remove)
        drv->driver.remove = platform_drv_remove;
    if (drv->shutdown)
        drv->driver.shutdown = platform_drv_shutdown;
    return driver_register(&drv->driver);
}

对照成表：

动作 3.x 5.2.8 6.11 / 6.12
设 driver.owner 在 platform_driver_register 里没写（由 platform_driver_register 宏或调用方传） 有 有
设 driver.bus 有 有 有
driver.probe = 过渡函数 有（platform_drv_probe） 无 无
driver.remove = 过渡函数 有（platform_drv_remove） 无 无
driver.shutdown = 过渡函数 有（platform_drv_shutdown） 无 无
bus->probe 无 无 有（platform_probe）
bus->remove 无 无 有（platform_remove）

为什么能这么改：really_probe() 里的逻辑一直是「总线有 probe 就走总线的，没有才走驱动的」。所以把过渡函数从 driver.probe 挪到 bus->probe 是等价的，还省掉了每个驱动都要被改一次指针的开销，同时顺手把 of_clk_set_defaults / dev_pm_domain_attach 塞了进去。

5.3 三个过渡函数的完整代码（3.x） #

读老资料一定会遇到这三个函数，给出完整实现：

c
static int platform_drv_probe(struct device *_dev)
{
    struct platform_driver *drv = to_platform_driver(_dev->driver);
    struct platform_device *dev = to_platform_device(_dev);

    return drv->probe(dev);
}

static int platform_drv_remove(struct device *_dev)
{
    struct platform_driver *drv = to_platform_driver(_dev->driver);
    struct platform_device *dev = to_platform_device(_dev);

    return drv->remove(dev);
}

static void platform_drv_shutdown(struct device *_dev)
{
    struct platform_driver *drv = to_platform_driver(_dev->driver);
    struct platform_device *dev = to_platform_device(_dev);

    drv->shutdown(dev);
}

它们存在的唯一理由是类型不兼容：

  • 通用框架要的是 int (*)(struct device *)；
  • platform 驱动写的是 int (*)(struct platform_device *)。

两个签名里的结构体不是同一种，函数指针不能直接赋值。过渡函数用 container_of（to_platform_driver / to_platform_device）把内嵌的 device / device_driver 反推回外层的 platform 结构体，再回调用户真正写的函数。

调用者              框架                       过渡层                     你的代码
really_probe ──▶ bus->probe(dev) / drv->probe(dev)
                        │
                        ▼
                  platform_drv_probe(_dev)   [3.x]    /  platform_probe(_dev)  [6.x]
                        │ to_platform_device(_dev)
                        │ to_platform_driver(_dev->driver)
                        ▼
                   drv->probe(pdev) ─────────────▶ my_probe(pdev)

三个 to_* 宏都是 container_of 的糖：

c
#define to_platform_device(x) container_of((x), struct platform_device, dev)
#define to_platform_driver(drv) (container_of((drv), struct platform_driver, driver))

container_of 的算法是「已知成员地址，减去成员在结构体里的偏移，得到结构体首地址」。所以 struct platform_device 里 dev 的位置必须是固定的，这也是为什么它不能是柔性数组成员、不能在 dev 前面放变长字段。

5.4 6.x 的 platform_probe / platform_remove / platform_shutdown #

c
static int platform_probe(struct device *_dev)
{
    struct platform_driver *drv = to_platform_driver(_dev->driver);
    struct platform_device *dev = to_platform_device(_dev);
    int ret;

    if (unlikely(drv->probe == platform_probe_fail))
        return -ENXIO;

    ret = of_clk_set_defaults(_dev->of_node, false);
    if (ret < 0)
        return ret;

    ret = dev_pm_domain_attach(_dev, true);
    if (ret)
        goto out;

    if (drv->probe) {
        ret = drv->probe(dev);
        if (ret)
            dev_pm_domain_detach(_dev, true);
    }
out:
    if (drv->prevent_deferred_probe && ret == -EPROBE_DEFER) {
        dev_warn(_dev, "probe deferral not supported\n");
        ret = -ENXIO;
    }
    return ret;
}

static void platform_remove(struct device *_dev)
{
    struct platform_driver *drv = to_platform_driver(_dev->driver);
    struct platform_device *dev = to_platform_device(_dev);

    if (drv->remove)
        drv->remove(dev);
    dev_pm_domain_detach(_dev, true);
}

static void platform_shutdown(struct device *_dev)
{
    struct platform_device *dev = to_platform_device(_dev);
    struct platform_driver *drv;

    if (!_dev->driver)
        return;
    drv = to_platform_driver(_dev->driver);
    if (drv->shutdown)
        drv->shutdown(dev);
}

三处细节：

  • platform_probe_fail 是 __platform_driver_probe() 用的哨兵函数（return -ENXIO;）。用 platform_driver_probe 注册的驱动，probe 函数放在 __init 段，绑过一次之后代码就被回收了，所以之后不许再绑定。
  • platform_remove 是 void，回调和拆 PM domain 都是无条件做完，不判错误。
  • prevent_deferred_probe 为真时，-EPROBE_DEFER 被改写成 -ENXIO，同时打一条 probe deferral not supported。这是给「明确不支持延迟探测」的驱动用的。

5.5 driver_register() 往下干了什么 #

text
platform_driver_register(drv)                  /* 宏 */
  └─ __platform_driver_register(drv, THIS_MODULE)
       ├─ drv->driver.owner = THIS_MODULE
       ├─ drv->driver.bus = &platform_bus_type
       └─ driver_register(&drv->driver)
            └─ bus_add_driver()
                 ├─ 在 /sys/bus/platform/drivers/ 建目录
                 └─ driver_attach()
                      └─ bus_for_each_dev(&platform_bus_type, ...)   ← 遍历设备
                           └─ __driver_attach()
                                ├─ driver_match_device() == platform_match()
                                └─ driver_probe_device()
                                     └─ really_probe()

driver_attach() 会遍历总线上已有的每一个设备。 这就是「驱动后注册也能匹配上已注册设备」的实现方式。反过来，设备后注册时 device_add() 内部反向遍历驱动链表，两条路对称。

5.6 注销：platform_driver_unregister() #

c
void platform_driver_unregister(struct platform_driver *drv)
{
    driver_unregister(&drv->driver);
}

就这一行。真正干活的是 driver_unregister() → driver_detach() → 对每个已绑定设备调 device_release_driver()，进而走到 device_remove()：

c
static void device_remove(struct device *dev)
{
    device_remove_file(dev, &dev_attr_state_synced);
    device_remove_groups(dev, dev->driver->dev_groups);
    if (dev->bus && dev->bus->remove)
        dev->bus->remove(dev);
    else if (dev->driver->remove)
        dev->driver->remove(dev);
}

又是同一个优先级：总线 remove 优先。6.x 走 platform_remove()，3.x 走 driver_remove（当时是 platform_drv_remove）。

六、匹配的核心：platform_match 的三级判定 #

6.1 完整实现（5.2.8 起，含 ACPI） #

素材三逐字给的是 5.2.8 的版本，6.11 只差一个 const：

c
/**
 * platform_match - bind platform device to platform driver.
 * @dev: device.
 * @drv: driver.
 *
 * Platform device IDs are assumed to be encoded like this:
 * "<name><instance>", where <name> is a short description of the type of
 * device, like "pci" or "floppy", and <instance> is the enumerated
 * instance of the device, like '0' or '42'.  Driver IDs are simply
 * "<name>".  So, extract the <name> from the platform_device structure,
 * and compare it against the name of the driver. Return whether they match
 * or not.
 */
static int platform_match(struct device *dev, const struct device_driver *drv)
{
    struct platform_device *pdev = to_platform_device(dev);
    struct platform_driver *pdrv = to_platform_driver(drv);

    /* When driver_override is set, only bind to the matching driver */
    if (pdev->driver_override)
        return !strcmp(pdev->driver_override, drv->name);

    /* Attempt an OF style match first */
    if (of_driver_match_device(dev, drv))
        return 1;

    /* Then try ACPI style match */
    if (acpi_driver_match_device(dev, drv))
        return 1;

    /* Then try to match against the id table */
    if (pdrv->id_table)
        return platform_match_id(pdrv->id_table, pdev) != NULL;

    /* fall-back to driver name match */
    return (strcmp(pdev->name, drv->name) == 0);
}

6.2 逐句读 #

c
struct platform_device *pdev = to_platform_device(dev);
struct platform_driver *pdrv = to_platform_driver(drv);

参数是通用的 device / device_driver，第一步反推回 platform 的具体类型。这两行一旦写错（比如用 drv 去反推 platform_device），后面全是野指针。

c
if (pdev->driver_override)
    return !strcmp(pdev->driver_override, drv->name);

driver_override 是最高优先级，而且是「独占」语义：一旦设了，其他三种匹配全都不走，只比 driver_override 和驱动名。它通过 sysfs 写：

bash
echo "s3c2410-ohci" > /sys/bus/platform/devices/usb0/driver_override

用途是抢绑——一个设备能被多个驱动匹配时（比如 driver 有 id_table 且名字也不同），强制绑到你指定的那个。代码注释写了别手动赋 pdev->driver_override，因为驱动核心会在设备释放时 kfree 它，得走 driver_set_override()。

c
if (of_driver_match_device(dev, drv))
    return 1;

设备树匹配，最高优先级。只看设备的 of_node 和驱动的 of_match_table，见第八章。

c
if (acpi_driver_match_device(dev, drv))
    return 1;

ACPI 匹配。x86 服务器和部分 ARM 服务器用 ACPI 描述硬件，规则和 OF 类似但走 drv->acpi_match_table。素材三是 5.2.8 的原文，3.x 素材里没有这一段——ACPI 匹配是后来才加的（具体引入版本未验证）。

c
if (pdrv->id_table)
    return platform_match_id(pdrv->id_table, pdev) != NULL;

注意这里是 return 而不是「匹配失败继续往下走」。也就是说，驱动一旦定义了 id_table，name 匹配就彻底不参与。这是新手最容易读错的一行。

c
return (strcmp(pdev->name, drv->name) == 0);

最后的兜底：纯字符串比对。

6.3 三级（其实是四级）判定表 #

优先级 判据 比对对象 典型场合 备注
0 driver_override pdev->driver_override vs drv->name 强制绑定时 设了就独占，其余全跳过
1 of_driver_match_device() dts compatible vs of_match_table 现代 ARM，设备由 dts 描述 需要 pdev->dev.of_node 非空
2 acpi_driver_match_device() ACPI _HID vs acpi_match_table x86 / ARM 服务器 3.x 版本里没有
3 platform_match_id() pdev->name vs id_table[].name 一个驱动支持多款芯片 命中与否都 return，不再往下
4 strcmp(name, name) pdev->name vs drv->name 传统板级 BSP 唯一无条件参与的兜底

一句话记忆：override 独占 → OF → ACPI → id_table → name，其中 id_table 是「有则终局」，name 是「没有 id_table 时才轮到」。

6.4 三个时代的 platform_match 对照 #

素材里正好出现了三个版本，差异值得单独列出来：

版本 代码特征 出处
2.6 早期 strncmp(pdev->name, drv->name, BUS_ID_SIZE)，无 id_table 素材一勘误里提到
3.x of_driver_match_device + id_table + strcmp 素材二
5.2.8 / 6.x 上面再加 driver_override 和 acpi_driver_match_device 素材三、6.11 源码

BUS_ID_SIZE 那个名字早就不存在了，看到就说明是十五年前的资料。

6.5 platform_match 的返回值语义 #

match 回调的返回值不是简单的 bool：

返回值 含义 后续动作
> 0 匹配 走 driver_probe_device()
0 不匹配 换下一个驱动/设备
< 0（尤其 -EPROBE_DEFER） 匹配过程本身要求延后 设备进延迟探测队列，不再尝试这条总线上的其他驱动

__device_attach_driver() 里就是这个逻辑：

c
ret = driver_match_device(drv, dev);
if (ret == 0) {
    /* no match */
    return 0;
} else if (ret == -EPROBE_DEFER) {
    dev_dbg(dev, "Device match requests probe deferral\n");
    dev->can_match = true;
    driver_deferred_probe_add(dev);
    /*
     * Device can't match with a driver right now, so don't attempt
     * to match or bind with other drivers on the bus.
     */
    return ret;
} else if (ret < 0) {
    dev_dbg(dev, "Bus failed to match device: %d\n", ret);
    return ret;
}

platform_match 自己永远返回 0 或 1，不返回负值。但 driver_match_device() 外面还套了一层 device_links_check_suppliers 检查（在 really_probe 里），那才是 -EPROBE_DEFER 的主要来源。

七、id_table 与 name 匹配 #

7.1 platform_match_id() 的完整实现 #

c
static const struct platform_device_id *platform_match_id(
        const struct platform_device_id *id, struct platform_device *pdev)
{
    while (id->name[0]) {
        if (strcmp(pdev->name, id->name) == 0) {
            pdev->id_entry = id;
            return id;
        }
        id++;
    }
    return NULL;
}

三个细节：

  1. 循环终止靠 id->name[0] 为空。这就是为什么 id_table 数组末尾必须有一个全零的哨兵项 { }——struct platform_device_id 全是零时 name[0] == '\0'，循环停。
  2. pdev->id_entry = id 是副作用。匹配成功时把命中的那一项记到设备上，驱动后面能取。
  3. 返回的是指针，不是 bool。platform_match 里用 != NULL 转成 0/1。

如果忘了末尾哨兵，循环会一直往后读，读到内存边界才撞上恰好为 0 的字节，或者直接 oops。这是 id_table 最常见的 bug。

7.2 靠 id_entry 区分型号 #

id_entry 最大的用处是把型号信息带进 probe：

c
/* 一个驱动支持三款芯片 */
enum {
    TYPE_S3C2440 = 0,
    TYPE_S3C6410,
    TYPE_S5PV210,
};

static const struct platform_device_id my_uart_ids[] = {
    { .name = "s3c2440-uart", .driver_data = TYPE_S3C2440 },
    { .name = "s3c6410-uart", .driver_data = TYPE_S3C6410 },
    { .name = "s5pv210-uart", .driver_data = TYPE_S5PV210 },
    { }   /* 哨兵，绝对不能省 */
};

static int my_uart_probe(struct platform_device *pdev)
{
    const struct platform_device_id *id = platform_get_device_id(pdev);
    unsigned long type = id ? id->driver_data : TYPE_S3C2440;

    switch (type) {
    case TYPE_S3C2440:
        /* 2440 的寄存器布局 */
        break;
    case TYPE_S3C6410:
        /* 6410 的寄存器布局 */
        break;
    default:
        return -ENODEV;
    }
    return 0;
}

static struct platform_driver my_uart_driver = {
    .probe    = my_uart_probe,
    .id_table = my_uart_ids,
    .driver   = { .name = "my-uart", .owner = THIS_MODULE },
};

设备侧声明 "s3c6410-uart"，驱动注册名是 "my-uart"——纯 name 匹配必然失败，但 id_table 能对上。

7.3 id_table 与 name 到底该选谁 #

场景 用什么 理由
驱动名与设备名完全一样，只支持一款硬件 driver.name 最省事
一个驱动支持多款芯片，行为有差异 id_table + driver_data 型号信息能从 id_entry 取出来
设备名由 BSP 决定，驱动名想取个好听的 id_table 名字解耦
设备树描述设备 of_match_table id_table 和 name 都不参与
一个设备要能被多个驱动匹配，需要抢绑 driver_override 优先级最高

注意第一条的陷阱：一旦加了 id_table，name 匹配就失效了。有人给一个已经能工作的驱动补了 id_table（想支持新型号），结果老设备反而匹配不上——因为老设备的名字不在 id_table 里，而代码已经 return 了。补 id_table 时记得把老名字也列进去。

7.4 名字长度限制 #

struct platform_device_id.name 是 char name[PLATFORM_NAME_SIZE]，定长数组。写超长的名字在编译期就会被截断或报错（取决于初始化方式）。实在要长的名字，用 driver.name（const char *）走 name 匹配，或者用设备树。

实际经验：设备名控制在 20 字符以内足够，超过基本说明命名方式该换了。

7.5 多个驱动都能匹配时谁赢 #

bus_for_each_drv() 按驱动链表顺序遍历，第一个返回正值的就赢。所以多条 id_table 项重叠、或者两个驱动名字相同的极端情况下，结果是「谁先注册谁赢」，不确定但可复现。

driver_override 就是为这种场景准备的。调试这类问题时：

bash
ls -l /sys/bus/platform/drivers/           # 看驱动目录顺序
cat /sys/bus/platform/devices/foo/driver   # 看当前绑的是谁（符号链接）
echo "my-driver" > /sys/bus/platform/devices/foo/driver_override
echo "foo" > /sys/bus/platform/drivers/my-driver/bind

八、设备树路径：of_device_id 与 of_match_device #

8.1 设备树时代设备从哪来 #

前面说「platform 设备必须人写」，这句话在设备树之后就变了。有 dts 的平台上：

text
内核启动 → unflatten_device_tree() 建出 device_node 树
       → of_platform_default_populate() 遍历树
            → 对每个 status == "okay" 且有 compatible 的节点
                 → of_platform_device_create()
                      → platform_device_alloc() + of_node 挂上
                           → platform_device_add()

结果是：你只写 dts，platform_device 由内核自动生成。 设备名取自节点名（serial@11400000 这类），of_node 指向对应的 device_node。

这就是「支持设备树的版本一上来做设备树匹配就完事」的意思——names 匹配和 id_table 都退成历史兼容手段。

8.2 dts 侧怎么写 #

dts
/ {
    beep: beep@114000a0 {
        compatible = "fs4412,beep";
        reg = <0x114000a0 0x4>, <0x139D0000 0x14>;
        reg-names = "gpd0con", "timer";
        interrupts = <0 40 0>;
        clocks = <&clock CLK_PWM>;
        clock-names = "pwm";
        status = "okay";
    };
};
  • compatible 是匹配键，格式约定 "vendor,device"，可以写多个，从左到右优先级递减。
  • reg 会被翻译成 IORESOURCE_MEM 类型的 resource[]，按出现顺序排。
  • interrupts 会被翻译成 IORESOURCE_IRQ，中断号由 interrupt controller 的 interrupt-map 换算。
  • status = "okay" 才会生成设备；"disabled" 就跳过。

8.3 驱动侧怎么写 #

c
static const struct of_device_id beep_of_match[] = {
    { .compatible = "fs4412,beep" },
    { /* sentinel */ }
};
MODULE_DEVICE_TABLE(of, beep_of_match);

static struct platform_driver beep_driver = {
    .probe  = beep_probe,
    .remove = beep_remove,
    .driver = {
        .name           = "fs4412-beep",
        .of_match_table = beep_of_match,
        .owner          = THIS_MODULE,
    },
};

MODULE_DEVICE_TABLE(of, ...) 不是可有可无的。它把匹配表导出到模块的 __mod_of__*_device_table 段里，depmod 才能生成 modules.alias，udev 才能根据 MODALIAS 自动 modprobe。不写它，模块能手动 insmod，但不会自动加载。

8.4 of_driver_match_device() 里面是什么 #

c
static inline int of_driver_match_device(struct device *dev,
                                         const struct device_driver *drv)
{
    return of_match_device(drv->of_match_table, dev) != NULL;
}

核心是 of_match_device()：

c
const struct of_device_id *of_match_device(const struct of_device_id *matches,
                                           const struct device *dev)
{
    if ((!matches) || (!dev->of_node))
        return NULL;
    return of_match_node(matches, dev->of_node);
}

两个前置条件缺一不可：

  1. drv->of_match_table 非空——驱动没写就谈不上 OF 匹配；
  2. dev->of_node 非空——设备必须是设备树生成的，手工 platform_device_register() 出来的设备没有 of_node。

of_match_node() 的匹配规则（drivers/of/base.c）逐项看 of_device_id 的三个字段：

字段 匹配规则
name 与节点 name 完全相等
type 与节点 device_type 属性相等
compatible 与节点 compatible 属性里任意一项相等

三个字段都为空时表示通配（匹配一切），这在实际驱动里几乎不用。常见写法只填 compatible。

复合匹配最有用的一点：节点可以写多个兼容字符串，取第一个能匹配上的驱动。

dts
mydev@1000 {
    compatible = "rockchip,rk3399-i2c", "rockchip,rk3399-i2c-v2", "snps,designware-i2c";
};

厂商专用驱动匹配第一个，通用 DesignWare 驱动匹配最后一个。同一个设备能匹配多个驱动，谁先注册谁绑上——又是 driver_override 的场景。

8.5 of_match_device() 在驱动里的用法 #

拿到匹配项的 data（用来区分配置）：

c
static const struct of_device_id my_i2c_of_match[] = {
    { .compatible = "rockchip,rk3399-i2c", .data = &rk3399_data },
    { .compatible = "rockchip,rk3288-i2c", .data = &rk3288_data },
    { }
};

static int my_i2c_probe(struct platform_device *pdev)
{
    const struct of_device_id *match;
    const struct my_i2c_config *cfg;

    match = of_match_device(my_i2c_of_match, &pdev->dev);
    if (!match)
        return -ENODEV;
    cfg = match->data;

    /* cfg->something 用起来 */
    return 0;
}

6.x 更省事的写法是 device_get_match_data(&pdev->dev)，它内部会先试 OF 再试 ACPI，把 data 直接给你。

8.6 设备树路径下的资源怎么来 #

reg / interrupts 在生成 platform_device 时就已经被翻译成 resource[] 了。所以驱动侧取资源不用区分是不是设备树，都用同一套 platform_get_resource() / platform_get_irq()。

唯一的区别是 IORESOURCE_MEM 的 start 会是总线地址而不是 CPU 物理地址（有 ranges 转换时）。ioremap 直接传总线地址会出错，正确做法是用 of_iomap() 或者 devm_platform_ioremap_resource()——后者内部会处理。

九、probe 的调用时机与上下文 #

9.1 调用时机：只有两个入口 #

probe 被调用的路径只有两条，其它任何地方都不会凭空调它：

触发者 调用链起点 遍历方向
设备注册 device_add() → bus_probe_device() → device_initial_probe() 遍历驱动链表
驱动注册 driver_register() → bus_add_driver() → driver_attach() 遍历设备链表
延迟探测重试 deferred_probe_work 工作队列 → bus_probe_device() 单个设备
用户态手动绑 echo dev > /sys/bus/platform/drivers/drv/bind 指定设备

四条入口最后都汇到 driver_probe_device() → really_probe()。没有第五个入口。 所以 probe 里出错就别指望「重试一下」——除了 -EPROBE_DEFER，没有机制帮你重来。

9.2 注册顺序对结果的影响 #

顺序 发生了什么 probe 何时跑
设备先注册，驱动后注册 设备注册时驱动链表里没有能匹配的，静静挂在总线上；驱动注册时 driver_attach() 遍历到它 驱动注册时
驱动先注册，设备后注册 驱动注册时设备链表为空，probe 不跑；设备注册时 device_add() 反向遍历到它 设备注册时
两者已存在，只是换绑 driver_override + bind 写 sysfs 时
两者都存在，且已绑定 不会再跑第二次 —

关键结论：probe 一定在「设备与驱动都已就绪」之后才被调用，先装哪个都不影响最终结果。 这正是 platform 相对「在 module_init 里手工找设备」的优势。

9.3 上下文细节 #

probe 运行时：

  • 进程上下文，可以睡眠。kmalloc(GFP_KERNEL)、mutex_lock、msleep 都可以。
  • 持有设备锁。__device_attach() 里先 device_lock(dev) 再遍历，一路持到 probe 返回。所以 probe 里绝对不能再对同一个 dev 调 device_lock()，也不要在里面长时间阻塞——会让整个设备模型的锁等待。
  • 父设备的 runtime PM 已被临时拉起。__driver_probe_device() 里 pm_runtime_get_sync(dev->parent)，返回后再 pm_runtime_put。
  • devres 池必须干净。really_probe() 里有这一段：
c
if (!list_empty(&dev->devres_head)) {
    dev_crit(dev, "Resources present before probing\n");
    ret = -EBUSY;
    goto done;
}

意思是进入 probe 之前，这个设备的 devres 链表必须是空的。如果你在 probe 外面（比如设备注册前）给 pdev->dev 挂过 devm_* 资源，这里直接 -EBUSY，probe 永远跑不起来。这条报错 Resources present before probing 出现时基本只能是这个原因。

9.4 probe 返回值语义 #

call_driver_probe() 里按返回值分四类打印：

返回值 含义 日志
0 成功，完成绑定 无
-EPROBE_DEFER 依赖的东西还没好，排队等重试 dev_dbg，静默
-ENODEV / -ENXIO 这个设备我不认，拒绝匹配 dev_dbg，静默
其它负值 真出错了 dev_err: probe with driver %s failed with error %d

-EPROBE_DEFER 和 -ENODEV 都是静默的（只有 dev_dbg，默认看不到）。所以「probe 没跑」有两种完全不同的原因，日志表现却一样安静，必须靠 dmesg -w 或 debugfs 才能分。

返回值还有一个坑：really_probe() 把驱动返回的错误取负再往上传（ret = -ret;），是为了和驱动核心自己的错误码区分开。所以 driver_probe_device() 返回正值表示「probe 失败」，负值表示「驱动核心失败」。自己写代码调这个函数时别搞反。

十、匹配成功的完整时序 #

10.1 really_probe() 逐步拆（6.11 原文节选） #

c
static int really_probe(struct device *dev, const struct device_driver *drv)
{
    bool test_remove = IS_ENABLED(CONFIG_DEBUG_TEST_DRIVER_REMOVE) && !drv->suppress_bind_attrs;
    int ret, link_ret;

    if (defer_all_probes) {
        dev_dbg(dev, "Driver %s force probe deferral\n", drv->name);
        return -EPROBE_DEFER;
    }

    link_ret = device_links_check_suppliers(dev);
    if (link_ret == -EPROBE_DEFER)
        return link_ret;

    if (!list_empty(&dev->devres_head)) {
        dev_crit(dev, "Resources present before probing\n");
        ret = -EBUSY;
        goto done;
    }

re_probe:
    dev->driver = (struct device_driver *)drv;

    /* If using pinctrl, bind pins now before probing */
    ret = pinctrl_bind_pins(dev);
    if (ret)
        goto pinctrl_bind_failed;

    if (dev->bus->dma_configure) {
        ret = dev->bus->dma_configure(dev);
        if (ret)
            goto pinctrl_bind_failed;
    }

    ret = driver_sysfs_add(dev);
    if (ret) {
        dev_err(dev, "%s: driver_sysfs_add failed\n", __func__);
        goto sysfs_failed;
    }

    if (dev->pm_domain && dev->pm_domain->activate) {
        ret = dev->pm_domain->activate(dev);
        if (ret)
            goto probe_failed;
    }

    ret = call_driver_probe(dev, drv);
    if (ret) {
        if (link_ret == -EAGAIN)
            ret = -EPROBE_DEFER;
        ret = -ret;
        goto probe_failed;
    }

    ret = device_add_groups(dev, drv->dev_groups);
    if (ret) {
        dev_err(dev, "device_add_groups() failed\n");
        goto dev_groups_failed;
    }

    pinctrl_init_done(dev);
    if (dev->pm_domain && dev->pm_domain->sync)
        dev->pm_domain->sync(dev);

    driver_bound(dev);
    goto done;

dev_groups_failed:
    device_remove(dev);
probe_failed:
    driver_sysfs_remove(dev);
sysfs_failed:
    bus_notify(dev, BUS_NOTIFY_DRIVER_NOT_BOUND);
    if (dev->bus && dev->bus->dma_cleanup)
        dev->bus->dma_cleanup(dev);
pinctrl_bind_failed:
    device_links_no_driver(dev);
    device_unbind_cleanup(dev);
done:
    return ret;
}

按顺序翻译成中文动作：

步 动作 失败回滚到
1 defer_all_probes 检查（系统挂起/休眠期间禁止探测） 直接返回 -EPROBE_DEFER
2 device_links_check_suppliers() 查供方设备是否就绪 返回 -EPROBE_DEFER
3 检查 devres 池为空 done
4 dev->driver = drv 先挂上（此时还没 probe） —
5 pinctrl_bind_pins() 按 dts 绑引脚 pinctrl_bind_failed
6 bus->dma_configure() 配 IOMMU / DMA pinctrl_bind_failed
7 driver_sysfs_add() 建 /sys/devices/.../driver 符号链接 sysfs_failed
8 pm_domain->activate() probe_failed
9 call_driver_probe() → bus->probe → 你的 probe() probe_failed
10 device_add_groups() 加 dev_groups 属性 dev_groups_failed
11 pinctrl_init_done() + pm_domain->sync() —
12 driver_bound() ：加 klist、触发延迟探测、发 KOBJ_BIND 成功

driver_bound() 里还会做一件重要的事：

c
static void driver_bound(struct device *dev)
{
    ...
    klist_add_tail(&dev->p->knode_driver, &dev->driver->p->klist_devices);
    device_links_driver_bound(dev);
    device_pm_check_callbacks(dev);
    /* Make sure the device is no longer in one of the deferred lists */

十一、不匹配时会发生什么：deferred probe #

11.1 三种「没成功」要分清 #

现象 原因 /sys/bus/platform/devices/ 下有设备吗 drivers/ 下有驱动吗 设备目录下有 driver 链接吗
完全没匹配上 名字/id_table/compatible 都对不上 有 有 无
匹配上了，probe 失败 probe 返回了负值（非 DAT 非 DEFER） 有 有 无
匹配上了，probe 延期 probe 返回 -EPROBE_DEFER 有 有 无，但在延迟队列里

三种情况下 sysfs 表现一模一样，所以光看 sysfs 分不出来。要分得看日志和 /sys/kernel/debug/devices_deferred。

11.2 为什么需要 deferred probe #

典型场景：一个 I2C 从设备驱动要拿一个 GPIO，而那个 GPIO 由另一个 platform 设备（I2C GPIO 扩展芯片）提供。两个驱动都是 module_init 阶段注册，谁先跑不确定。如果 I2C 从设备的 probe 先跑，gpiod_get() 会返回 -ENOENT，驱动没法初始化。

早期内核的解法是调 initcall 顺序（subsys_initcall 之类），非常脆弱。5.x 前后引入的 device_links + deferred probe 换了个思路：probe 返回 -EPROBE_DEFER 表示「我还没准备好，等会儿再试」，驱动核心把设备放进队列，等别的设备绑定成功时批量重试。

device_links 是 5.x 引入的机制（素材范围里没有，具体版本未验证）。6.11 的 really_probe() 里第 2 步 device_links_check_suppliers() 就是它的入口——如果这个设备的供方（supplier）还没 probe 完，直接 -EPROBE_DEFER，连驱动代码都不进。

11.3 延迟探测的机制 #

drivers/base/dd.c 里维护两个链表：

c
static LIST_HEAD(deferred_probe_pending_list);   /* 等着重试 */
static LIST_HEAD(deferred_probe_active_list);    /* 正在重试 */

流程：

text
probe 返回 -EPROBE_DEFER
  └ driver_probe_device()
       └ driver_deferred_probe_add(dev)        → 挂进 pending 链表
            （前提 dev->can_match 为真）

任何设备绑定成功
  └ driver_bound()
       └ driver_deferred_probe_trigger()
            ├ pending 全部 splice 到 active
            └ queue_work(system_unbound_wq, &deferred_probe_work)

deferred_probe_work_func()
  └ while (active 非空)
       ├ 取出一个设备，从链表摘掉
       ├ device_pm_move_to_tail(dev)     /* PM 顺序要重排 */
       └ bus_probe_device(dev)           /* 重试 */

这里面有一个竞态，注释写得很老实：

c
/*
 * Note, there is a race condition in multi-threaded probe. In the case where
 * more than one device is probing at the same time, it is possible for one
 * probe to complete successfully while another is about to defer. If the second
 * depends on the first, then it will get put on the pending list after the
 * trigger event has already occurred and will be stuck there.
 */

一个人成功绑定时另一个人正准备延期，延期的那次就会错过触发事件、永远卡在 pending 里。内核用 deferred_trigger_count 原子计数来兜：driver_probe_device() 在跑 probe 前后各读一次计数，变了就再触发一次。

11.4 排查延迟探测 #

bash

cat /sys/kernel/debug/devices_deferred
# 每行是设备名 + TAB + 延期原因（5.x 后期起会带原因）

# 2. 打开 debug 日志看具体哪个依赖
dmesg | grep -i "defer"
# Driver foo requests probe deferral

# 3. 自己设延长超时（单位秒，默认 10）

超时到了会怎样？deferred_probe_timeout_work_func() 会把 driver_deferred_probe_timeout 置 0、再触发一轮，然后对剩下还在 pending 里的设备逐个 dev_warn("deferred probe pending: %s")。这时如果驱动里调的是 driver_deferred_probe_check_state()，它会返回 -ETIMEDOUT（配了 CONFIG_MODULES 时）或 -ENODEV（没配），让驱动放弃。

11.5 该不该用 -EPROBE_DEFER #

该用：

  • 依赖另一个设备（clock、regulator、GPIO、phy、IOMMU）的，且那个设备会比自己晚 probe；
  • 依赖的子系统还没注册完（比如 i2c_adapter 还没 i2c_add_adapter）。

不该用：

  • 驱动自己写错了（比如寄存器读不到），这时该返回 -EIO 之类，别用 DEFER 掩盖；
  • 依赖的东西永远不来——会一直卡到超时，还拖着启动时间。

-EPROBE_DEFER 不是无限重试的魔法。 它只能解决「顺序问题」，解决不了「依赖根本不存在」。真实项目里 devices_deferred 常年躺着一堆条目，基本都是依赖写错了。

11.6 反过来的问题：没有 physical bus 就没有真正的热插拔 #

platform 设备不能热插拔。这一点和 deferred probe 是两件事：

  • deferred probe 解决的是启动阶段的顺序问题，是一次性的重试；
  • 热插拔要解决的是运行阶段的动态增删，platform 没有这个能力。

想在运行时加一个 platform 设备，只能手动：

bash
# 内核里没有通用的「运行时创建 platform device」的 sysfs 接口
# 只能写一个模块去 platform_device_register()，或者用 configfs（少数子系统有）

这也是为什么 platform 只适合 SoC 内部那些「开机就在、关机才走」的设备。真需要热插拔的（USB、SD 卡、PCIe），得挂在真正的总线上。

十二、platform_get_resource：资源是怎么描述的 #

12.1 struct resource 全字段 #

定义在 include/linux/ioport.h：

c
/*
 * Resources are tree-like, allowing
 * nesting etc..
 */
struct resource {
    resource_size_t start;      /* 起始，地址的话必须是物理地址 */
    resource_size_t end;        /* 结束，地址的话必须是物理地址 */
    const char      *name;      /* 资源名 */
    unsigned long   flags;      /* 类型 + 属性 */
    unsigned long   desc;
    struct resource *parent, *sibling, *child;   /* 资源树的父、兄、子 */
};

两点说明：

  1. desc 在 5.x 之前的版本里没有（素材三那份 5.2.8 的代码里有，素材一素材二那份没有，说明它们在 3.x/4.x）。它是给资源树做的内部标记。
  2. parent/sibling/child 让所有资源构成一棵树。iomem_resource 是根，ioport_resource 是 I/O 端口的根，每个设备的 resource[] 插进去成为子树的一个节点。树结构就是地址冲突检测的实现方式——插入时逐层查有没有重叠。

flags 同时装两样东西：

text
flags
 ├─ 低 8 位左右：类型（IORESOURCE_MEM / IO / IRQ / DMA / BUS …）
 └─ 高位：属性（IORESOURCE_READONLY / CACHEABLE / PREFETCHABLE …）

#define IORESOURCE_MEM     0x00000200
#define IORESOURCE_IRQ     0x00000400
#define IORESOURCE_DMA     0x00000800
#define IORESOURCE_BUS     0x00001000

取值方式：

c
#define IORESOURCE_TYPE_BITS  0x00001f00
#define resource_type(res)    ((res)->flags & IORESOURCE_TYPE_BITS)

所以 resource_type(r) == IORESOURCE_MEM 判断的是「这个资源的类型是不是 MEM」。

12.2 platform_get_resource() 的实现 #

c
/**
 * platform_get_resource - get a resource for a device
 * @dev: platform device
 * @type: resource type
 * @num: resource index
 *
 * Return: a pointer to the resource or NULL on failure.
 */
struct resource *platform_get_resource(struct platform_device *dev,
                                       unsigned int type, unsigned int num)
{
    u32 i;

    for (i = 0; i < dev->num_resources; i++) {
        struct resource *r = &dev->resource[i];

        if (type == resource_type(r) && num-- == 0)
            return r;
    }
    return NULL;
}
EXPORT_SYMBOL_GPL(platform_get_resource);

十行代码，三个要点：

  1. 线性扫描。num_resources 项的数组从头到尾，没有索引表。
  2. type 用 == 而不是 &。所以给 type 传 IORESOURCE_MEM 可以，传 IORESOURCE_MEM | IORESOURCE_READONLY 永远匹配不上——resource_type() 只取 TYPE_BITS 那几位。要同时接受 MEM 和 IO，用 platform_get_mem_or_io()。
  3. num 是「第几个这种类型的资源」，不是数组下标。platform_get_resource(pdev, IORESOURCE_MEM, 1) 意思是「第二段内存」，它的 resource[] 下标会是 3。

参数含义：

参数 含义
dev 目标 platform 设备
type 资源类型：IORESOURCE_MEM / IORESOURCE_IRQ / IORESOURCE_IO / IORESOURCE_DMA
num 该类型下的第几个，从 0 开始

返回 NULL 表示没找到。必须判空，否则 res->start 直接 oops。

12.3 配套的几个取资源函数 #

c
/* 按名字取，要求 resource[i].name 与之相等 */
struct resource *platform_get_resource_byname(struct platform_device *dev,
                                              unsigned int type, const char *name);

/* 不区分 MEM 和 IO，取第一个内存映射型资源 */
struct resource *platform_get_mem_or_io(struct platform_device *dev, unsigned int num);

platform_get_resource_byname() 的实现多一步 strcmp：

c
struct resource *platform_get_resource_byname(struct platform_device *dev,
                                              unsigned int type, const char *name)
{
    u32 i;

    for (i = 0; i < dev->num_resources; i++) {
        struct resource *r = &dev->resource[i];

        if (unlikely(!r->name))
            continue;
        if (type == resource_type(r) && !strcmp(r->name, name))
            return r;
    }
    return NULL;
}

注意它跳过无名资源：r->name == NULL 的直接 continue。而 platform_device_add() 会把无名资源的 name 填成设备名，所以实际上只有 num_resources 之外的项才是无名。

设备树侧对应的是 reg-names：

dts
mydev@1000 {
    reg = <0x1000 0x100>, <0x2000 0x40>;
    reg-names = "ctrl", "fifo";
};

驱动里就能 platform_get_resource_byname(pdev, IORESOURCE_MEM, "fifo")。reg 的项数和 reg-names 的项数必须一致，不一致时内核会忽略 reg-names。

12.4 映射的现代写法 #

素材里的老写法：

c
res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
gpd0con = ioremap(res->start, res->end - res->start + 1);

对的三步：取资源、算长度、ioremap。但也有三道坑：没判 res 为 NULL、没判 ioremap 返回 NULL、remove 里要记得 iounmap。

现在推荐两条路：

c
/* 路线 A：devm 版，自动 iounmap，probe 失败时自动回滚 */
void __iomem *base = devm_platform_ioremap_resource(pdev, 0);
if (IS_ERR(base))
    return PTR_ERR(base);

/* 路线 B：要同时拿到 struct resource 的时候 */
struct resource *res;
void __iomem *base = devm_platform_get_and_ioremap_resource(pdev, 0, &res);
if (IS_ERR(base))
    return PTR_ERR(base);

devm_platform_ioremap_resource() 的实现就三行：

c
void __iomem *devm_platform_ioremap_resource(struct platform_device *pdev,
                                             unsigned int index)
{
    return devm_platform_get_and_ioremap_resource(pdev, index, NULL);
}

void __iomem *devm_platform_get_and_ioremap_resource(struct platform_device *pdev,
                                                     unsigned int index,
                                                     struct resource **res)
{
    struct resource *r;

    r = platform_get_resource(pdev, IORESOURCE_MEM, index);
    if (res)
        *res = r;
    return devm_ioremap_resource(&pdev->dev, r);
}

devm_ioremap_resource() 内部会帮你判 r 为 NULL、检查资源是否已被别人申请、按 end - start + 1 算长度。自己写 ioremap 能出的错它都替你堵上了。

长度语义必须记清：end 是闭区间的最后一个字节地址，长度是 end - start + 1。素材实例里写 .end = 0x114000a0 + 0x4，然后 end - start 得 4——这其实是把长度写进了 end，+1 少算了最后一个字节。寄存器窗口访问时多算一个字节无所谓，但用 request_mem_region() 申报范围时就会漏一个字节。规范写法是 .end = start + size - 1。

十三、IORESOURCE_MEM / IRQ / DMA 三类资源 #

13.1 三类资源对照 #

类型 flags start end 内存树归属 典型来源
IORESOURCE_MEM 起始物理地址 末字节物理地址 iomem_resource dts reg
IORESOURCE_IO 起始 I/O 端口 末 I/O 端口 ioport_resource x86 老 ISA 设备

}
if (p) {

}

14.2 platform_get_irq() 的实现 #

c
int platform_get_irq(struct platform_device *dev, unsigned int num)
{
    int ret;

    ret = platform_get_irq_optional(dev, num);
    if (ret < 0)
        return dev_err_probe(&dev->dev, ret, "IRQ index %u not found\n", num);
    return ret;
}
EXPORT_SYMBOL_GPL(platform_get_irq);

它只是 _optional 的包装，加一行错误打印。真正的逻辑在 platform_get_irq_optional() 里，按优先级分五步：

c
int platform_get_irq_optional(struct platform_device *dev, unsigned int num)
{
    int ret;

    struct fwnode_handle *fwnode = dev_fwnode(&dev->dev);
    struct resource *r;

    /* ① 设备树路径 */
    if (is_of_node(fwnode)) {
        ret = of_irq_get(to_of_node(fwnode), num);
        if (ret > 0 || ret == -EPROBE_DEFER)
            goto out;
    }

    /* ② 传统 resource[] 路径 */
    r = platform_get_resource(dev, IORESOURCE_IRQ, num);

    /* ③ ACPI 路径 */
    if (is_acpi_device_node(fwnode)) {
        if (r && r->flags & IORESOURCE_DISABLED) {
            ret = acpi_irq_get(ACPI_HANDLE_FWNODE(fwnode), num, r);
            if (ret)
                goto out;
        }
    }

    /* ④ 传递触发方式 */
    if (r && r->flags & IORESOURCE_BITS) {
        struct irq_data *irqd;

        irqd = irq_get_irq_data(r->start);
        if (!irqd)
            goto out_not_found;
        irqd_set_trigger_type(irqd, r->flags & IORESOURCE_BITS);
    }

    if (r) {
        ret = r->start;
        goto out;
    }

    /* ⑤ ACPI GpioInt 兜底 */
    if (num == 0 && is_acpi_device_node(fwnode)) {
        ret = acpi_dev_gpio_irq_get(to_acpi_device_node(fwnode), num);
        if (ret >= 0 || ret == -EPROBE_DEFER)
            goto out;
    }

out_not_found:
    ret = -ENXIO;
out:
    if (WARN(!ret, "0 is an invalid IRQ number\n"))
        return -EINVAL;
    return ret;
}

三条路径的优先级是：设备树 of_irq_get() → IORESOURCE_IRQ → ACPI。

第 4 步容易被忽略：IORESOURCE_BITS 里装的触发方式（上升沿/下降沿/高电平/低电平）会被直接写进 irq 描述符。这就是为什么手工声明的 resource 里，flags = IORESOURCE_IRQ | IORESOURCE_IRQ_HIGHEDGE 能起作用。

14.3 返回值语义的版本变化 #

内核版本 找不中断时返回 是否有 _optional
3.x 老的 platform_get_irq 返回 -ENXIO（素材里 3.x 驱动直接 if (irq < 0)） 没有
4.x _optional 引入，platform_get_irq 变成「_optional + 打日志」 有
5.x / 6.x 同上；WARN(!ret) 把 0 号中断视作非法，返回 -EINVAL 有

三个必须记住的点：

  1. 返回值是 int，不是 unsigned int。以前有驱动写成 unsigned int irq = platform_get_irq(...)，负数被转成巨大正数，request_irq 时报一个看不懂的错。
  2. 成功返回值一定是正数。中断号 0 被视为非法（WARN(!ret) + -EINVAL），因为 0 在 Linux 里历史上是「无中断」的哨兵值。
  3. -EPROBE_DEFER 会原样透出。如果中断控制器还没 probe，of_irq_get() 返回 -EPROBE_DEFER，你应该原样返回它，让设备进延迟队列——别把它当成「没有中断」处理。

_optional 具体在哪个版本引入（我记得是 4.19 前后），未验证。

14.4 platform_irq_count() #

c
int platform_irq_count(struct platform_device *dev)
{
    int ret, nr = 0;

    while ((ret = platform_get_irq_optional(dev, nr)) >= 0)
        nr++;
    if (ret == -EPROBE_DEFER)
        return ret;
    return nr;
}

一直试下去直到拿到负数。注意它只在 -EPROBE_DEFER 时透传错误，其它负值都当成「到头了」，返回已经数出来的个数。所以如果设备一个中断都没有，它返回 0，你没法区分「真的没有」和「资源配错了」。

14.5 platform_get_irq_byname() #

c
static int __platform_get_irq_byname(struct platform_device *dev, const char *name)
{
    struct resource *r;
    int ret;

    ret = fwnode_irq_get_byname(dev_fwnode(&dev->dev), name);
    if (ret > 0 || ret == -EPROBE_DEFER)
        return ret;

    r = platform_get_resource_byname(dev, IORESOURCE_IRQ, name);
    if (r) {
        if (WARN(!r->start, "0 is an invalid IRQ number\n"))
            return -EINVAL;
        return r->start;
    }
    return -ENXIO;
}

设备树侧对应 interrupt-names：

dts

    interrupts = <0 40 0>, <0 41 0>;
    interrupt-names = "tx", "rx";

c

int irq_rx = platform_get_irq_byname(pdev, "rx");

多中断设备必须用 byname，因为 interrupts 的顺序一旦变了，索引就全错。

14.6 用 devm_request_irq() 把申请和释放一起托管 #

c
ret = devm_request_irq(&pdev->dev, irq, my_isr, IRQF_SHARED, "mydev", pdev);
if (ret)
    return ret;

remove() 里不用 free_irq()，设备 detach 时 devres 自动释放。素材里的老代码用的是 request_irq() + remove 里手写 free_irq()，两者都行，但 devm 版少一次「忘了释放」的机会。

15.3 led_drv.c —— 驱动侧 #

c
#include <linux/module.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/io.h>
#include <linux/uaccess.h>
#include <linux/platform_device.h>
#include <linux/device.h>

/* GPB 寄存器 */
static void __iomem *gpbcon;
static void __iomem *gpbdata;

/* 保存操作结构体的字符设备 */
static struct cdev led_cdev;
static struct class *led_cls;
static dev_t devid;
static int start_pin;
static int end_pin;

/* GPB5~GPB8 配置为输出 */
static int led_open(struct inode *inode, struct file *file)
{
    int i;

    for (i = start_pin; i < end_pin; i++) {
        u32 v = readl(gpbcon);
        v &= ~(0x03 << (i * 2));
        v |=  (0x01 << (i * 2));
        writel(v, gpbcon);
    }
    return 0;
}

/* 点亮/熄灭 LED1~LED4 */
static ssize_t led_write(struct file *file, const char __user *buf,
                         size_t count, loff_t *ppos)
{
    int val, i;

    if (copy_from_user(&val, buf, sizeof(val)))
        return -EFAULT;

    printk("value %d\n", val);

    for (i = start_pin; i < end_pin; i++) {
        u32 v = readl(gpbdata);
        if (val)
            v &= ~(0x01 << i);      /* 点亮：输出低电平 */
        else
            v |=  (0x01 << i);      /* 熄灭：输出高电平 */
        writel(v, gpbdata);
    }
    return count;
}

static struct file_operations led_fops = {
    .owner = THIS_MODULE,
    .open  = led_open,
    .write = led_write,
};

/*
 * 驱动所有资源的注册和初始化全部放在 probe 中
 */
static int led_probe(struct platform_device *pdev)
{
    struct resource *res;
    struct device *dev;
    int err;

    printk("led_probe, found led\n");

    /* 取第一段内存资源并映射，失败自动回滚 */
    gpbcon = devm_platform_ioremap_resource(pdev, 0);
    if (IS_ERR(gpbcon))
        return PTR_ERR(gpbcon);

    /* GPBDAT 紧跟在 GPBCON 后面 4 字节 */
    gpbdata = gpbcon + 1;

    /* 取「第二类」资源：这里借用 IORESOURCE_IRQ 传引脚范围 */
    res = platform_get_resource(pdev, IORESOURCE_IRQ, 0);
    if (!res)
        return -ENODEV;
    start_pin = res->start;
    end_pin   = res->end;

    /* 动态分配字符设备编号 */
    err = alloc_chrdev_region(&devid, 0, 1, "led");
    if (err) {
        printk("alloc_chrdev_region error\n");
        return err;
    }

    cdev_init(&led_cdev, &led_fops);
    led_cdev.owner = THIS_MODULE;
    err = cdev_add(&led_cdev, devid, 1);
    if (err) {
        unregister_chrdev_region(devid, 1);
        return err;
    }

    led_cls = class_create("led");
    if (IS_ERR(led_cls)) {
        cdev_del(&led_cdev);
        unregister_chrdev_region(devid, 1);
        return PTR_ERR(led_cls);
    }

    dev = device_create(led_cls, NULL, devid, NULL, "led");
    if (IS_ERR(dev)) {
        class_destroy(led_cls);
        cdev_del(&led_cdev);
        unregister_chrdev_region(devid, 1);
        return PTR_ERR(dev);
    }

    printk("led_probe ok\n");
    return 0;
}

static int led_remove(struct platform_device *pdev)
{
    printk("led_remove, remove led\n");

    /* gpbcon 由 devm 托管，不需要 iounmap */
    device_destroy(led_cls, devid);
    class_destroy(led_cls);
    cdev_del(&led_cdev);
    unregister_chrdev_region(devid, 1);

    return 0;
}

static struct platform_driver led_driver = {
    .probe  = led_probe,
    .remove = led_remove,
    .driver = {
        .name = "led_test",     /* 必须和 platform 设备的 .name 相同 */
    }
};

MODULE_LICENSE("GPL");

这份代码和素材原文的四处差别都值得说清楚（原文在 附录 里统一列），最关键的三处：

  • *gpbcon &= ... 改成 readl/writel。素材用 volatile unsigned long * 直接解指针，在 64 位平台上一个 unsigned long 是 8 字节，一次写会覆盖相邻寄存器。
  • ioremap 换 devm_platform_ioremap_resource，省掉手写 iounmap 和长度计算。
  • class_create 在 6.4 起只有一个参数（去掉了 THIS_MODULE），素材是两参数的老写法。这个改动同样是对着源码定的：现代签名是 class_create(const char *name)，返回值仍然是 ERR_PTR。

16.3 platform_driver_probe() 是什么 #

它是 __platform_driver_probe() 的宏：

c
#define platform_driver_probe(drv, probe) \
    __platform_driver_probe(drv, probe, THIS_MODULE)

c
int __init_or_module __platform_driver_probe(struct platform_driver *drv,
        int (*probe)(struct platform_device *), struct module *module)
{
    int retval;

    if (drv->driver.probe_type == PROBE_PREFER_ASYNCHRONOUS) {
        pr_err("%s: drivers registered with %s can not be probed asynchronously\n",
               drv->driver.name, __func__);
        return -EINVAL;
    }

    drv->driver.probe_type = PROBE_FORCE_SYNCHRONOUS;
    drv->prevent_deferred_probe = true;
    drv->driver.suppress_bind_attrs = true;

    drv->probe = probe;
    retval = __platform_driver_register(drv, module);
    if (retval)
        return retval;

    /* Force all new probes of this driver to fail */
    drv->probe = platform_probe_fail;

    if (!bus_for_each_dev(&platform_bus_type, NULL, &drv->driver, is_bound_to_driver)) {
        retval = -ENODEV;
        platform_driver_unregister(drv);
    }
    return retval;
}

它干了四件特别的事：

  1. 强制同步探测（不许异步）。
  2. prevent_deferred_probe = true——-EPROBE_DEFER 会被改写成 -ENXIO。
  3. suppress_bind_attrs = true——sysfs 里没有 bind/unbind，因为 probe 函数在 __init 段里，模块加载完那段内存已经回收了。
  4. 注册完立刻把 drv->probe 换成 platform_probe_fail，然后再检查有没有绑到任何设备。一个都没绑到就 -ENODEV 并自动注销驱动。

用途很明确：SoC 片上控制器这种「开机一定在、永不热插拔」的设备，probe 只用一次，扔进 __init 段省内存。代价是失去延迟探测能力，所以对依赖别的设备的驱动不能用它。

16.4 什么时候别用 module_platform_driver #

场景 原因
init 里要做别的检查 宏只帮你注册，别的干不了
需要按条件注册多个驱动 一个模块只能用一次宏
需要读模块参数决定注册哪个驱动 同上
驱动注册失败要打印额外信息 宏只有一行 return，没日志

素材里的写法是手写 module_init / module_exit 并带 printk——调试阶段这么做有价值，正式代码换成 module_platform_driver 少五行。

十七、平台的注销与资源释放 #

17.1 设备注销：platform_device_unregister() #

c
/**
 * platform_device_unregister - unregister a platform-level device
 * @pdev: platform device we're unregistering
 *
 * Unregistration is done in 2 steps. First we release all resources
 * and remove it from the subsystem, then we drop reference count by
 * calling platform_device_put().
 */
void platform_device_unregister(struct platform_device *pdev)
{
    platform_device_del(pdev);
    platform_device_put(pdev);
}

两步：_del 拆台，_put 减引用计数。

c
void platform_device_del(struct platform_device *pdev)
{
    u32 i;

    if (!IS_ERR_OR_NULL(pdev)) {
        device_del(&pdev->dev);

        if (pdev->id_auto) {
            ida_free(&platform_devid_ida, pdev->id);
            pdev->id = PLATFORM_DEVID_AUTO;
        }

        for (i = 0; i < pdev->num_resources; i++) {
            struct resource *r = &pdev->resource[i];
            if (r->parent)
                release_resource(r);
        }
    }
}

顺序值得注意：先 device_del()（这会触发 unbind，调你的 remove），然后才还 IDA 号、才释放资源树节点。所以 remove 执行时，pdev->resource[] 里的地址范围还是活的，可以继续访问。反过来就不行。

c
void platform_device_put(struct platform_device *pdev)
{
    if (!IS_ERR_OR_NULL(pdev))
        put_device(&pdev->dev);
}

put_device 减到 0 时才调 dev.release。静态设备（.dev.release = led_release）走用户的回调，动态设备（platform_device_alloc 出来的）走 platform_device_release 释放整块内存。

引用计数不归零就不会释放。 有人调完 platform_device_unregister() 发现 /sys/devices/platform/foo 还在，就是因为还有别处持着引用。

17.2 驱动注销：platform_driver_unregister() #

c
void platform_driver_unregister(struct platform_driver *drv)
{
    driver_unregister(&drv->driver);
}

driver_unregister() → driver_detach()：对驱动绑定的每个设备调 device_release_driver()，这条路会：

text
device_release_driver()
  └ __device_release_driver()
       ├ driver_sysfs_remove(dev)
       ├ device_remove(dev)           ← bus->remove() / drv->remove()
       │    └ platform_remove() → drv->remove(pdev)   ← 你的 remove
       ├ bus->dma_cleanup(dev)
       ├ device_unbind_cleanup(dev)   ← devres_release_all()
       ├ device_links_driver_cleanup(dev)
       └ kobject_uevent(KOBJ_UNBIND)

device_unbind_cleanup() 里那句 devres_release_all(dev) 是 devm 机制的核心。 所有 devm_* 申请的资源（devm_ioremap、devm_request_irq、devm_kzalloc、devm_clk_get）都在这里按申请的逆序自动释放。这就是为什么用 devm 的驱动 remove 里可以什么都不写。

注意顺序：device_remove() 在前，devres_release_all() 在后。所以 remove 里还能正常使用 devm 申请的资源，用完才统一回收。

17.3 谁先卸，结果不同 #

操作 走的路 remove 被调用吗
rmmod led_drv driver_unregister → driver_detach 会，每个绑定设备一次
rmmod led_dev platform_device_unregister → device_del → 解绑 会，如果此时绑着驱动
先 led_drv 后 led_dev 上面两条各走一次 只调一次，第二次已解绑
只 led_dev 不卸驱动 device_del 时解绑 会

17.4 remove 必须与 probe 严格对称 #

probe 里做了 remove 里必须做 devm 版还需要吗
devm_platform_ioremap_resource — 不需要
ioremap iounmap —
devm_request_irq — 不需要
request_irq free_irq —
alloc_chrdev_region unregister_chrdev_region 不需要（可用 devm）
cdev_add cdev_del 不需要（cdev_device_add 更省事）
class_create class_destroy 不需要（devm 版有）
device_create device_destroy 不需要
clk_get clk_put 不需要（devm_clk_get）
gpiod_get gpiod_put 不需要（devm_gpiod_get）
让硬件进工作态（开时钟、开 PWM） 让硬件进安全态（关 PWM、关时钟） 需要，devm 管不了硬件状态

最后一行是 devm 管不到的地方。devm 只负责「内核资源」，不管「硬件副作用」。probe 里点亮了蜂鸣器，remove 里必须熄灭，否则卸载模块后板子一直叫。

17.5 remove 返回值的坑 #

回到第二章那个版本表：6.11 起 platform_driver.remove 是 void。但 5.x/6.0~6.10 的驱动写的是 int：

c
/* 5.x / 6.0 ~ 6.10 */
static int led_remove(struct platform_device *pdev)
{
    ...
    return 0;       /* 这个返回值从来没人看 */
}

这段代码在 6.11+ 上编译会报 incompatible pointer types。迁移到 6.11+ 只需要把 int 改成 void、删掉 return 0。行为没变——驱动核心本来就一直忽略返回值。
