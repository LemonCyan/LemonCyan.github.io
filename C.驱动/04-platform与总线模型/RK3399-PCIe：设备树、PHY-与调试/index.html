一、RK3399 的 PCIe 家底 #

先把硬件能力摆清楚，后面看 dts 才知道每个数字为什么是那个值。

项 RK3399 PCIe 控制器 依据
dts 里的节点名 pcie0: pcie@f8000000，只有一路 rk3399.dtsi
compatible rockchip,rk3399-pcie 同上
AXI 寄存器窗口 0xf8000000，长 0x2000000（32MB） reg 第一段
APB 寄存器窗口 0xfd000000，长 0x1000000（16MB） reg 第二段
中断线 3 路 SPI：GIC_SPI 49/50/51 interrupts
时钟 4 路：aclk aclk-perf hclk pm clocks / clock-names
复位 7 路：core mgmt mgmt-sticky pipe pm pclk aclk resets / reset-names
PHY 独立 PHY 节点 pcie_phy，最多 4 个 lane phys / phy-names
总线号范围 bus-range = <0x0 0x1f>，即 0~31 bus-range
默认链路速率 max-link-speed = <1>，Gen1 max-link-speed
MSI 走 GICv3 ITS，DeviceID 范围 0x0~0xfff msi-map
dtsi 默认状态 disabled status

一句话总结：RK3399 只有一路 PCIe，4 lane 的 PHY 硬 IP，控制器挂在 AXI 上，MSI 通过 ITS 走 LPI，legacy INTx 走一根专用 SPI。

注意 RK3399 是 GICv3 平台，它的 MSI 没有走 GICv2m 那种方式，而是走 ITS（Interrupt Translation Service）。这一点在第六章展开。

pcie0 这个名字带一个冒号前缀，是 dts 里的 label。设备树编译后 label 会变成 phandle，其它节点用 &pcie0 就能引用到这个节点。你在板级 dts 里看到的 &pcie0 { ... } 就是在给这个 label 打补丁。

二、pcie0 设备树节点全貌 #

完整抄一遍，后面逐段拆。

dts
pcie0: pcie@f8000000 {
		compatible = "rockchip,rk3399-pcie";
		reg = <0x0 0xf8000000 0x0 0x2000000>,
			  <0x0 0xfd000000 0x0 0x1000000>;
		reg-names = "axi-base", "apb-base";
		device_type = "pci";
		#address-cells = <3>;
		#size-cells = <2>;
		#interrupt-cells = <1>;
		aspm-no-l0s;
		bus-range = <0x0 0x1f>;
		clocks = <&cru ACLK_PCIE>, <&cru ACLK_PERF_PCIE>,
				 <&cru PCLK_PCIE>, <&cru SCLK_PCIE_PM>;
		clock-names = "aclk", "aclk-perf",
					  "hclk", "pm";
		interrupts = <GIC_SPI 49 IRQ_TYPE_LEVEL_HIGH 0>,
					 <GIC_SPI 50 IRQ_TYPE_LEVEL_HIGH 0>,

		interrupt-map-mask = <0 0 0 7>;
		interrupt-map = <0 0 0 1 &pcie0_intc 0>,
						<0 0 0 2 &pcie0_intc 1>,
						<0 0 0 3 &pcie0_intc 2>,
						<0 0 0 4 &pcie0_intc 3>;

		msi-map = <0x0 &its 0x0 0x1000>;
		phys = <&pcie_phy 0>, <&pcie_phy 1>,
			   <&pcie_phy 2>, <&pcie_phy 3>;
		phy-names = "pcie-phy-0", "pcie-phy-1",
					"pcie-phy-2", "pcie-phy-3";
		ranges = <0x82000000 0x0 0xfa000000 0x0 0xfa000000 0x0 0x1e00000>,
				 <0x81000000 0x0 0xfbe00000 0x0 0xfbe00000 0x0 0x100000>;
		resets = <&cru SRST_PCIE_CORE>, <&cru SRST_PCIE_MGMT>,
				 <&cru SRST_PCIE_MGMT_STICKY>, <&cru SRST_PCIE_PIPE>,
				 <&cru SRST_PCIE_PM>, <&cru SRST_P_PCIE>,
				 <&cru SRST_A_PCIE>;
		reset-names = "core", "mgmt", "mgmt-sticky", "pipe",
					  "pm", "pclk", "aclk";
		status = "disabled";

		pcie0_intc: interrupt-controller {
				interrupt-controller;
				#address-cells = <0>;
				#interrupt-cells = <1>;
		};
};

字段一览表：

属性 值 作用 谁消费
compatible rockchip,rk3399-pcie 绑定驱动 rk3399-pcie.c
reg 两段：AXI 32MB、APB 16MB 寄存器基址 驱动 platform_get_resource
reg-names axi-base、apb-base 给两段命名 驱动按名字取
device_type pci 声明这是个 PCI 主机桥 OF 核心，of_pci 相关代码
#address-cells <3> 子节点地址三格（PCI 地址格式） OF 核心
#size-cells <2> 子节点长度两格（64 位） OF 核心
#interrupt-cells <1> 本节点作为中断控制器时中断描述 1 格 of_irq_parse_map
aspm-no-l0s 布尔 告诉驱动 RC 不支持 ASPM L0s 驱动
bus-range 0x0 0x1f 根总线 0，最大 31 pci_host_probe 相关
clocks/clock-names 4 路 时钟句柄 devm_clk_get 按名取
interrupts/interrupt-names 3 路 SPI 控制器自身中断 驱动 platform_get_irq_byname
interrupt-map-mask <0 0 0 7> INTx 映射的行选择掩码 OF 中断映射核心
interrupt-map 4 条 INTx A/B/C/D 映射 同上
max-link-speed <1> 默认只跑 Gen1 驱动
msi-map 0x0 &its 0x0 0x1000 RID → ITS DeviceID of_msi_map_get
phys/phy-names 4 个 lane PHY 句柄 devm_phy_get 按名取
ranges 2 条 CPU 地址 ↔ PCI 地址 pci_parse_ranges 等
resets/reset-names 7 路 复位线 devm_reset_control_get 按名取
status disabled 默认不启用 OF 核心，不 probe
子节点 pcie0_intc 中断控制器 承接 4 根 INTx interrupt-map 的 target

有三处容易看错，先点出来。

第一，#address-cells = <3> 和 #size-cells = <2> 不是给 reg 用的，是给子节点用的。reg 自己的格数由父节点（这里是 /，或者 soc 节点）的 #address-cells/#size-cells 决定。pcie0 是 / 的直接子节点，RK3399 的根节点是 #address-cells = <2>、#size-cells = <2>，所以你看到 reg 每段是 4 格。

第二，#interrupt-cells = <1> 同理，是给用 interrupts 引用这个节点作为中断控制器的人用的。这个节点既是中断消费者（interrupts 属性引用 GIC），又是中断控制器（pcie0_intc 是它的子节点，但 map 里用的是 &pcie0_intc）。两种身份并存，这在 PCI 主机桥里是常态。

第三，aspm-no-l0s 是个布尔属性，没有值。它存在的历史原因写在绑定文档里：如果 RC 的 PHY 用 24MHz 晶振而不是 100MHz，就不支持 ASPM L0s，需要置这一位。

text
Documentation/devicetree/bindings/pci/rockchip-pcie.txt:
- aspm-no-l0s: RC won't support ASPM L0s. This property is needed
  if using 24MHz OSC for RC's PHY.

RK3399 的 dtsi 里直接写了 aspm-no-l0s，意思是这一路默认按「PHY 参考时钟不是 100MHz 出 L0s」来对待。板级 dts 把 assigned-clock-rates 改成 100000000 之后，这一位理论上可以去掉，但没人会去改，留着不出错。

三、reg 与 reg-names：两段地址空间 #

reg 两段，对应控制器里两块完全独立的寄存器区域。

text
reg = <0x0 0xf8000000 0x0 0x2000000>,      /* axi-base: 0xf8000000, 32MB */
      <0x0 0xfd000000 0x0 0x1000000>;      /* apb-base: 0xfd000000, 16MB */

每段 4 格：地址高 32 位、地址低 32 位、长度高 32 位、长度低 32 位。高 32 位都是 0，因为 RK3399 是 32 位物理地址空间（ARMv8 的 32 位 PA 模式）。

名字 基址 长度 装什么
axi-base 0xf8000000 32MB 控制器主寄存器组，DMA/数据通路相关、中断状态，以及配置空间访问用的 ATU 窗口
apb-base 0xfd000000 16MB APB 侧的寄存器组，控制/状态类访问

为什么叫 AXI 和 APB？因为 RK3399 的 PCIe 控制器在 SoC 内部接两条总线：一条高带宽的 AXI 主口，一条低速的 APB 从口。驱动要同时 ioremap 两块，用不同的辅助函数读写。

c
/* 伪代码，示意两段的取法，非逐行原文 */
res = platform_get_resource_byname(pdev, IORESOURCE_MEM, "axi-base");
pci->axi_base = devm_ioremap_resource(dev, res);

res = platform_get_resource_byname(pdev, IORESOURCE_MEM, "apb-base");
pci->apb_base = devm_ioremap_resource(dev, res);

绑定文档把这两段写成必填：

text
- reg: Two register ranges as listed in the reg-names property
- reg-names: Must include the following names
  - "axi-base"
  - "apb-base"

地址别记死。 0xfa000000 这块是 ranges 里的 PCI 内存窗口，和 reg 的 axi-base 是两回事，两个地址挨着，非常容易搞混。前者是「PCI 设备在这颗 SoC 上被 CPU 看到的地址」，后者是「控制器自己的寄存器」。第七章会把这张表列清楚。

ATU 窗口 #

axi-base 那 32MB 里有一块是给 ATU（Address Translation Unit）用的。ATU 是 PCIe 控制器里的地址翻译硬件，负责把 CPU 侧地址翻译成 PCI 总线地址，反过来也是一样。RK3399 的控制器里，ATU 按 region 组织，每个 region 配三个东西：基地址、目标地址、大小。

Linux 侧的对应代码是 drivers/pci/controller/pcie-cadence.c 里的 ATU 配置逻辑（PCI_ATU_REGION_INDEX0 系列寄存器偏移），Rockchip 的控制器复用了 Cadence 的这套 ATU 布局。这一段我没有在 RK3399 手册里逐寄存器核对过，标为未验证；可以确认的是 dts 里没有 ATU 相关的属性，窗口配置全部在内核里按 ranges 自动算出来。

实际含义：ranges 里写的那两条窗口，内核会拿去做 ATU region 的编程。也就是说，改 ranges 就是改 ATU 窗口，不是改什么软映射表。

四、interrupts 与 interrupt-names：三路中断 #

dts
interrupts = <GIC_SPI 49 IRQ_TYPE_LEVEL_HIGH 0>,
             <GIC_SPI 50 IRQ_TYPE_LEVEL_HIGH 0>,
             <GIC_SPI 51 IRQ_TYPE_LEVEL_HIGH 0>;
interrupt-names = "sys", "legacy", "client";

RK3399 是 GICv3，interrupts 每项 4 格。按 arm,gic-v3.txt 的定义：

格 含义 这里的值
第 1 格 中断类型，0 = SPI，1 = PPI GIC_SPI，即 0
第 2 格 中断号，SPI 范围 0~987 49/50/51
第 3 格 触发类型标志，bits[3:0]，1 = 上升沿，4 = 电平 IRQ_TYPE_LEVEL_HIGH
第 4 格 PPI 亲和性 phandle，SPI 必须写 0 0

三路中断分工：

名字 SPI 号 用途 驱动里怎么取
sys 49 系统级事件：链路训练、错误、热插拔这类控制器自身状态 platform_get_irq_byname(pdev, "sys")
legacy 50 INTx 中断汇聚，4 根 INTx 经 interrupt-map 编成一根 platform_get_irq_byname(pdev, "legacy")
client 51 客户端消息类中断 platform_get_irq_byname(pdev, "client")

绑定文档对三路的措辞是「Three interrupt entries must be specified」，名字必须包含 sys、legacy、client 三个。写漏一个，驱动 devm_request_irq 那步会直接报错，probe 失败。

注意 interrupt-names 的顺序必须和 interrupts 严格对齐。第 2 个 interrupts 项配第 2 个名字，错位会让驱动把 legacy 的中断挂到 client 的处理函数上，症状是「能进中断但不知道进了哪个」，极难查。

三根 SPI 在 GIC 里都是电平触发（IRQ_TYPE_LEVEL_HIGH）。电平触发的好处是不会丢边沿，代价是处理函数必须把中断状态清干净，否则一退出中断就会立刻再进一次，表现为中断风暴、CPU 100%。这是第十四章调试时最常见的现象之一。

五、interrupt-map 与内嵌中断控制器 #

这一段是 PCI 设备树里最绕的地方。先看原样：

dts
interrupt-map-mask = <0 0 0 7>;
interrupt-map = <0 0 0 1 &pcie0_intc 0>,
                <0 0 0 2 &pcie0_intc 1>,
                <0 0 0 3 &pcie0_intc 2>,
                <0 0 0 4 &pcie0_intc 3>;

pcie0_intc: interrupt-controller {
		interrupt-controller;
		#address-cells = <0>;
		#interrupt-cells = <1>;
};

为什么需要 interrupt-map #

PCI 设备没有 dts 节点。你插上一块 NVMe，内核对它一无所知，只能靠总线枚举发现它。它要报中断，报的方式是 INTx（传统引脚中断 A/B/C/D），而 INTx 在 SoC 侧必须落到某个真实的中断号上。

interrupt-map 就是这张翻译表：输入是「哪个 PCI 设备的哪根 INTx」，输出是「哪个中断控制器的第几号中断」。

interrupt-map 的四元组输入 #

每个条目前 4 格是子节点地址，格式由本节点的 #address-cells = <3> 加 1 格中断号构成：

位置 含义 这里的值
第 1 格 phys.hi，高 8 位固定 0，中间 8 位是总线号，接下来 5 位是设备号，低 3 位是功能号 0（全 0，表示通配匹配）
第 2 格 phys.mid，地址中段 0
第 3 格 phys.lo，地址低段 0
第 4 格 中断号，PCI 场景下就是 INTx 编号：1 = INTA，2 = INTB，3 = INTC，4 = INTD 1/2/3/4

所以 <0 0 0 1 &pcie0_intc 0> 读作：任何 PCI 设备的 INTA，翻译成 pcie0_intc 的第 0 号中断。四条一起覆盖 INTA~INTD。

interrupt-map-mask 的四元组语义 #

text
interrupt-map-mask = <0 0 0 7>;

掩码长度和输入四元组一一对应，逐格做按位与，结果再拿去 interrupt-map 里匹配。

掩码格 值 作用
phys.hi 0 把总线号/设备号/功能号全部抹掉，任何设备都匹配
phys.mid 0 抹掉
phys.lo 0 抹掉
中断号 7 保留低 3 位，即 0~7，足够区分 INTx 1~4

掩码写 0 0 0 7 的实际效果：所有 PCI 设备，按 INTx 编号分四组，各自落到 pcie0_intc 的 0/1/2/3 号。这就是 RK3399 只有一根 legacy SPI 却要承接 4 根 INTx 的做法。

那为啥不是 0 0 0 3？因为 INTx 编号从 1 开始，1~4 需要 3 个 bit 才装得下，低 2 位取 0x3 只能覆盖 0~3。7 是够用的最小值，也是几乎所有 PCI 主机桥的统一写法（host-generic-pci.txt 的示例用的是 <0xf800 0x0 0x0 0x7>，那里多保留了 phys.hi 的高位用于选设备）。

pcie0_intc 的角色 #

pcie0_intc 是个内嵌的虚拟中断控制器，没有 reg，不占地址空间。它的三个属性：

属性 值 说明
interrupt-controller 布尔 声明我是中断控制器
#address-cells <0> 我这个域里没有地址概念，只有中断号
#interrupt-cells <1> 一条中断描述只占 1 格

绑定文档的原话：

text
*Interrupt controller child node*
The core controller provides a single interrupt for legacy INTx. The PCIe
node should contain an interrupt controller node as a target for the PCI
'interrupt-map' property. This node represents the domain at which the four
INTx interrupts are decoded and routed.

也就是说，INTx 的两级翻译是这样的：

text
PCI 设备的 INTA
   ↓  interrupt-map（本章）
pcie0_intc 的 irq 0
   ↓  pcie0 节点自身的 interrupts（第四章）
GIC 的 SPI 50（"legacy"）

pcie0_intc 自己没有 interrupts 属性，它的父节点是 pcie0，所以中断会继续往上冒泡到 pcie0 的 interrupts。这就是「一根 legacy SPI 承接四根 INTx」的完整链路。

一个反直觉点 #

#address-cells = <3> 是 pcie0 的值，但子节点 pcie0_intc 写的是 #address-cells = <0>。两个不冲突：前者管 PCI 子设备的地址长度，后者管中断域里的地址长度。中断域没有地址，所以是 0。

interrupt-map 里的目标部分 &pcie0_intc 0，0 后面只有 1 格，因为 pcie0_intc 的 #interrupt-cells = <1>。如果写成 &pcie0_intc 0 0，dtc 会报 cell 数不匹配。

六、msi-map：MSI 中断怎么路由到 ITS #

dts
msi-map = <0x0 &its 0x0 0x1000>;

这行只有 4 个 32 位数，但它是整个 MSI 通路的入口。

三元组还是四元组 #

按 pci-msi.txt（Documentation/devicetree/bindings/pci/pci-msi.txt）的定义，msi-map 是若干「四元组」：

text
- msi-map: Maps a Requester ID to an MSI controller and associated
  msi-specifier data. The property is an arbitrary number of tuples of
  (rid-base, msi-controller, msi-base, length)
位置 名字 这里的值 含义
第 1 格 rid-base 0x0 起始 Requester ID
第 2 格 msi-controller &its MSI 控制器句柄（GICv3 的 ITS 节点）
第 3 格 msi-base 0x0 映射后的起始 msi-specifier（这里就是 DeviceID）
第 4 格 length 0x1000 连续匹配多少个 RID

数值上看是「三个数字加一个 phandle」，说成三元组也对，差别只是把 phandle 算不算一格。真正要记住的是：它是一条 RID 区间到 DeviceID 区间的线性映射。

映射规则（文档原文语义）：

text
Any RID r in the interval [rid-base, rid-base + length) is associated with
the listed msi-controller, with the msi-specifier
(r - rid-base + msi-base).

代进 RK3399 的值：RID 在 [0, 0x1000) 区间的设备，全部走 its，DeviceID = RID。因为 rid-base 和 msi-base 都是 0，这就是个恒等映射。

RID 是什么 #

RID（Requester ID）就是 PCI 设备的 BDF 三元组压成一个 16 位数：

位域 含义
bits[15:8] 总线号
bits[7:3] 设备号
bits[2:0] 功能号

bus-range = <0x0 0x1f> 意味着总线号最大 31，所以 RID 最大也就 0x1fff 左右。length = 0x1000 刚好覆盖 16 条总线（0x1000 >> 8 = 16），够用但不富余。这是一处容易踩的点：如果板子上挂了 PCIe switch 把总线号撑到 16 以上，超出 0x1000 的 RID 就没有 MSI 映射，那些设备的 MSI 会直接失败。

ITS 与 DeviceID #

RK3399 是 GICv3 平台，&its 指向 GIC 节点下的 arm,gic-v3-its 子节点。arm,gic-v3.txt 对 ITS 的定义：

text
GICv3 has one or more Interrupt Translation Services (ITS) that are used to
route Message Signalled Interrupts (MSI) to the CPUs. These nodes must have
the following properties:
- compatible : Should at least contain "arm,gic-v3-its"
- msi-controller : Boolean property. Identifies the node as an MSI controller
- #msi-cells: Must be <1>. The single msi-cell is the DeviceID of the device
  which will generate the MSI.
- reg: Specifies the base physical address and size of the ITS registers.

#msi-cells = <1> 里的那 1 格就是 DeviceID。RK3399 的 msi-map 把 DeviceID 设成等于 RID，是因为 ITS 的 DeviceID 来自写 MSI 时随消息带过去的 sideband 数据，控制器能直接给出 RID。

完整链路 #

text
PCI 设备写 MSI（地址 = ITS 的 GITS_TRANSLATER，数据 = EventID）
   ↓  sideband DeviceID = RID
ITS 查自己的设备表（DevID → ITT）
   ↓  做成 LPI
GICv3 投递 LPI 到目标 CPU
   ↓
Linux 的 ITS 驱动（drivers/irqchip/irq-gic-v3-its.c）分发
   ↓
nvme 等设备驱动注册的中断处理函数

和 INTx 走的是两条完全独立的路：INTx 走 SPI 50，MSI 走 LPI。所以你会看到 lspci -v 里 NVMe 报「MSI-X: Enable+ Count=9」，而 PCI 桥报「MSI: Enable+」。

of_msi_map 怎么用这张表 #

内核在枚举时会对每个 PCI 设备调 of_msi_map_get()，拿设备的 RID 查 msi-map，得到 msi-specifier（DeviceID）。这套逻辑在 drivers/pci/of.c 和 drivers/pci/msi.c 里，属于通用代码，不会因为换 SoC 而改。

RK3399 还留了一个坑：msi-map 只有一条，length 是 0x1000。如果板级 dts 里改了 bus-range 却没同步改 msi-map，且实际总线数超过 16，就会出现「设备能被枚举、BAR 能分配、但中断一句都进不来」的现象。第十五章把这条列进故障对照表。

七、ranges：CPU 地址到 PCI 地址的映射 #

dts
ranges = <0x82000000 0x0 0xfa000000 0x0 0xfa000000 0x0 0x1e00000>,
         <0x81000000 0x0 0xfbe00000 0x0 0xfbe00000 0x0 0x100000>;

ranges 是设备树里最标准的地址转换属性，格式是 子地址 + 父地址 + 长度。这里子节点是 PCI 空间（#address-cells = <3>、#size-cells = <2>），父节点是 CPU 空间（RK3399 根节点 #address-cells = <2>、#size-cells = <2>）。

所以每条 7 格：

格位 归属 第 1 条的值 第 2 条的值
1 子地址 phys.hi 0x82000000 0x81000000
2 子地址 phys.mid 0x0 0x0
3 子地址 phys.lo 0xfa000000 0xfbe00000
4 父地址高 32 位 0x0 0x0
5 父地址低 32 位 0xfa000000 0xfbe00000
6 长度高 32 位 0x0 0x0
7 长度低 32 位 0x1e00000（30MB） 0x100000（1MB）

phys.hi 的位域 #

ranges 第 1 格那三个 0x8xxxxxxx 不是随便编的，它按 IEEE 1275 的 PCI 地址编码：

位域 含义
bits[31:24] 地址类型：0x01 = I/O 空间，0x02 = 32 位内存，0x03 = 64 位内存
bits[23:16] 类型相关标志，内存空间里 bit 30（0x40000000）表示可预取，这里都没置
bits[15:8] 总线号，0 表示从根总线开始
bits[7:3] 设备号
bits[2:0] 功能号

按这个规则拆：

写法 类型字节 空间类型 可预取
0x82000000 0x02 32 位内存空间 否
0x81000000 0x01 I/O 空间 不适用
0x83000000 0x03 64 位内存空间 否
0xC2000000 0x02 + 可预取位 32 位内存，可预取 是

RK3399 这里用的是 0x82000000 和 0x81000000，即「32 位非预取内存窗口」加「I/O 空间窗口」两条。注意：没有 64 位内存窗口。这不代表 64 位设备挂不上，设备如果要 64 位 BAR，内核会把它压缩到这条 32 位窗口里，前提是窗口装得下。

两条窗口的实际值 #

窗口 CPU 侧地址 大小 说明
32 位内存 0xfa000000 ~ 0xfbdfffff 30MB PCI 设备的内存 BAR 都落在这里
I/O 空间 0xfbe00000 ~ 0xfbefffff 1MB 老式 I/O BAR，现代设备基本不用

两块窗口紧挨着，0xfa000000 + 0x1e00000 = 0xfbe00000，正好接上 I/O 窗口的起点。这种排布是故意的，方便在 lspci -v 的输出里核对。

前面说的实际表现，在这份真实日志里能看到：

text
00:00.0 PCI bridge: Fuzhou Rockchip Electronics Co., Ltd RK3399 PCI Express Root Port
        I/O behind bridge: 00000000-00000fff [size=4K]
        Memory behind bridge: fa000000-fa0fffff [size=1M]
        Prefetchable memory behind bridge: 00000000-000fffff [size=1M]

01:00.0 Non-Volatile memory controller: ... Device 0021 (rev 01)
        Memory at fa000000 (64-bit, non-prefetchable) [size=16K]

桥的「Memory behind bridge」从 fa000000 开始，NVMe 的 BAR 也落在 fa000000，两者对得上。桥的「Prefetchable memory」显示 00000000-000fffff，这是因为 RK3399 的 ranges 里根本没有可预取窗口，内核给了一个占位值。

ranges 与 ATU 的对应 #

第三章提过，ranges 里的窗口最终会被编程进 ATU。对应关系：

text
dts ranges 第 1 条  →  ATU region 0（32 位内存窗口）
dts ranges 第 2 条  →  ATU region 1（I/O 窗口）

具体 region 索引是内核按 ranges 顺序分配的，我给不出严格的一一证据，这一点标为未验证。能确认的是：dts 里写的 CPU 侧地址和 PCI 侧地址如果不一样（比如实现带偏移的映射），ATU 就会按这个偏移去翻译；RK3399 这里 CPU 侧和 PCI 侧写的是同一个地址（0xfa000000 → 0xfa000000），所以是恒等映射，ATU 的偏移为 0。

改 ranges 的后果 #

板级 dts 里改 ranges 多数是为了躲开别的外设占用的地址段。改的时候两条都要动，且长度不能超：

  • 内存窗口超过 30MB，会和 I/O 窗口重叠，内核在解析 ranges 时会报冲突。
  • CPU 侧地址落进控制器 reg 区间（0xf8000000 起）也不行，两套地址语义会打架。

八、clocks 与 clock-names：四路时钟 #

dts
clocks = <&cru ACLK_PCIE>, <&cru ACLK_PERF_PCIE>,
         <&cru PCLK_PCIE>, <&cru SCLK_PCIE_PM>;
clock-names = "aclk", "aclk-perf", "hclk", "pm";

&cru 是 RK3399 的时钟复位单元，节点在 0xff760000，#clock-cells = <1>，#reset-cells = <1>。rk3399-cru.h 里给每路时钟定义了宏 ID。

clock-names 时钟宏 名字里的含义 谁管它
aclk ACLK_PCIE AXI 总线时钟，主数据通路 驱动 devm_clk_get(dev, "aclk")
aclk-perf ACLK_PERF_PCIE AXI 高性能通路时钟，与上一路配合 驱动按名取
hclk PCLK_PCIE 寄存器访问时钟，对应 APB 侧 驱动按名取
pm SCLK_PCIE_PM 电源管理模块时钟 驱动按名取

注意一个反直觉的地方：名字叫 hclk，实际绑的宏是 PCLK_PCIE。这是 Rockchip 驱动沿用的老名字，clock-names 里的字符串只是给驱动查表用的键，和宏名的前缀没关系。你在 rk3399-cru.h 里搜 HCLK_PCIE 是搜不到的，别怀疑自己。

绑定文档把四个名字写成硬性要求：

text
- clock-names: Must include the following entries:
  - "aclk"
  - "aclk-perf"
  - "hclk"
  - "pm"

顺序也必须对齐。驱动里是按名字取时钟的（devm_clk_get(dev, "aclk") 这种），名字对了顺序无所谓；但如果驱动里改成按下标取，就会错位。

时钟树的三层 #

RK3399 的 PCIe 时钟有三层，容易混淆：

层级 时钟 归属节点 说明
CRU 层 ACLK_PCIE 等 4 路 pcie0.clocks 控制器总线时钟
CRU 层 SCLK_PCIEPHY_REF pcie_phy.clocks PHY 参考时钟的父时钟
PHY 内部 100MHz / 24MHz 参考 由 assigned-clock-* 决定 影响链路速率和 ASPM

SCLK_PCIEPHY_REF 不在 pcie0 的 clocks 列表里，它在 PHY 节点里。第十三章改板级 dts 时会看到 &pcie_phy 里设 assigned-clock-rates = <100000000>，改的就是这一路。

九、resets 与 reset-names：七路复位 #

dts
resets = <&cru SRST_PCIE_CORE>, <&cru SRST_PCIE_MGMT>,
         <&cru SRST_PCIE_MGMT_STICKY>, <&cru SRST_PCIE_PIPE>,
         <&cru SRST_PCIE_PM>, <&cru SRST_P_PCIE>,
         <&cru SRST_A_PCIE>;
reset-names = "core", "mgmt", "mgmt-sticky", "pipe",
              "pm", "pclk", "aclk";

七路复位一一对应，顺序必须严格一致。reset-names 里的名字是驱动 devm_reset_control_get(dev, "core") 的键。

reset-names 复位宏 复的是什么 顺序 漏掉的后果
core SRST_PCIE_CORE 控制器核心逻辑 1 核心寄存器状态残留，probe 后读写异常
mgmt SRST_PCIE_MGMT 管理/配置模块 2 配置空间访问失败，枚举不到设备
mgmt-sticky SRST_PCIE_MGMT_STICKY 管理模块的粘滞寄存器组 3 上一次运行留下的错误标志清不掉
pipe SRST_PCIE_PIPE PIPE 接口，控制器与 PHY 之间的并行接口 4 链路训练起不来
pm SRST_PCIE_PM 电源管理模块 5 低功耗状态切换卡死
pclk SRST_P_PCIE APB 侧逻辑（P 前缀表示 APB） 6 APB 寄存器读写异常
aclk SRST_A_PCIE AXI 侧逻辑（A 前缀表示 AXI） 7 DMA/数据通路不通

命名规律值得记一下：宏里 SRST_P_ 和 SRST_A_ 用的是单字母前缀，对应 APB 和 AXI；而 reset-names 写成 pclk 和 aclk。这两路在列表末尾，很容易漏抄。

绑定文档的措辞：

text
- resets: Must contain seven entries for each entry in reset-names.
- reset-names: Must include the following names
  - "core" - "mgmt" - "mgmt-sticky" - "pipe" - "pm" - "aclk" - "pclk"

文档里列出的顺序是 aclk 在 pclk 之前，而 dtsi 里是 pclk 在 aclk 之前。以 dtsi 为准，因为驱动是按名字查的，顺序不影响功能；但抄的时候别只抄文档那行，会和 resets 的 7 个句柄错位。

复位拉起的时序由驱动控制，dts 里只需要列全。这意味着你在板级 dts 里不要覆盖 resets，除非确实要改复位行为，否则会漏掉 mgmt-sticky 这种一看就不该动的项。

十、phys 与 phy-names：四个 lane 的 PHY #

dts
phys = <&pcie_phy 0>, <&pcie_phy 1>,
       <&pcie_phy 2>, <&pcie_phy 3>;
phy-names = "pcie-phy-0", "pcie-phy-1",
            "pcie-phy-2", "pcie-phy-3";

phys 里的每个 phandle 后面跟 1 格，这 1 格是 lane 编号，因为 PHY 节点的 #phy-cells = <1>。

lane phandle + cell 名字 说明
0 <&pcie_phy 0> pcie-phy-0 第 0 条通道
1 <&pcie_phy 1> pcie-phy-1 第 1 条通道
2 <&pcie_phy 2> pcie-phy-2 第 2 条通道
3 <&pcie_phy 3> pcie-phy-3 第 3 条通道

绑定文档对这套写法的说明：

text
Required properties for per-lane PHY model (preferred):
- phys: Must contain an phandle to a PHY for each entry in phy-names.
- phy-names: Must include 4 entries for all 4 lanes even if some of them
  won't be used for your cases. Entries are of the form "pcie-phy-N":
  where N ranges from 0 to 3.

四个都要写全，哪怕你只用一个 lane。这条容易踩：板上实际走 2 lane 时，num-lanes = <2>，但 phys 和 phy-names 仍然要 4 项。驱动按名取 PHY，取不到会报错。

两种 PHY 模型的区别 #

RK3399 的 PHY 绑定支持两套写法，rockchip-pcie-phy.yaml 里写得很清楚：

模型 #phy-cells phys 写法 状态
传统单 PHY <0> phys = <&pcie_phy>; phy-names = "pcie-phy"; 已废弃（deprecated）
多 lane PHY <1> 每 lane 一项，带 lane 编号 推荐

yaml 原文：

text
'#phy-cells':
  oneOf:
    - const: 0
      deprecated: true
    - const: 1
      description: One lane per phy mode

RK3399 的 dtsi 用的是 #phy-cells = <1>，即多 lane 模型。如果你照着一份老教程写成 #phy-cells = <0>，那 phys 里带的 lane 编号就成了多余的 cell，dtc 会告警。

PHY 驱动侧 #

phys 里的 lane 编号传进 PHY 驱动后，用来算 GRF 里那个 lane 对应的寄存器偏移。RK3399 的 PHY 没有自己的独立寄存器块，它是挂在 GRF 下的虚拟节点（第十二章展开），所有配置都通过 GRF 的 syscon 写。

&pcie_phy 这个 label 不是 pcie0 的子节点，而是 grf 的子节点。dts 里跨节点引用，靠的就是 label。

十一、max-link-speed 与链路速率 #

dtsi 里写的是：

dts
max-link-speed = <1>;

板级 dts 里改成：

dts
max-link-speed = <2>;

这个属性是通用 PCI 主机桥属性，pci.txt 的定义：

text
- max-link-speed: If present this property specifies PCI gen for link capability.
  Host drivers could add this as a strategy to avoid unnecessary operation for
  unsupported link speed, for instance, trying to do training for unsupported
  link speed, etc. Must be '4' for gen4, '3' for gen3, '2' for gen2, and '1' for gen1.
  Any other values are invalid.

合法的只有 1、2、3、4 四个值。

值 代际 单 lane 速率 RK3399 是否支持
1 Gen1 2.5 GT/s 支持
2 Gen2 5.0 GT/s 支持
3 Gen3 8.0 GT/s 不支持
4 Gen4 16.0 GT/s 不支持

RK3399 是 PCIe 2.1 的控制器，最高 Gen2。dtsi 里默认写 1 是「最保守的可用值」，板子确定能跑 Gen2 才改成 2。

三个数别搞混 #

属性 管什么 典型值
max-link-speed 链路可以协商到的最高代际 1（默认）/ 2
num-lanes 实际用几条 lane 1 / 2 / 4
bus-range 总线号范围，和速率无关 0x0 0x1f

num-lanes 不在 dtsi 里，是板级 dts 补的（绑定文档标为可选属性）。它和 phys 的 4 个 lane 是两回事：phys 列的是硬件上存在哪些 lane，num-lanes 说的是这次用几个。

速率受什么限制 #

协商出来的速率取两者较小值：控制器上限（max-link-speed）和设备能力。以下三条都会把速率压下来：

  • max-link-speed 写 1，永远只能 Gen1，即使设备是 Gen4。
  • num-lanes 配错了，比如硬件走 4 lane 但写成 2，链路会先训练失败再降到 2 lane 重新协商，或者干脆起不来。
  • PHY 参考时钟不对。第十三章会看到 assigned-clock-rates = <100000000>，如果这一项缺失，PHY 参考时钟拿不到 100MHz，速率上不去。

怎么看实际协商结果：

bash
# 看链路的当前速率和宽度
cat /sys/bus/pci/slots/*/cur_bus_speed 2>/dev/null
lspci -vv -s 00:00.0 | grep -E 'LnkCap|LnkSta'

LnkSta 那一行给的就是实际速率：

text
LnkSta:	Speed 5GT/s (ok), Width x2 (ok)

LnkCap 是能力上限。两者对比就知道是被 dts 限制了还是被设备限制了。

十二、pcie_phy 节点与 GRF syscon #

PHY 不是独立节点，它挂在 GRF（General Register Files）下面。

dts
grf: syscon@ff770000 {
		compatible = "rockchip,rk3399-grf", "syscon", "simple-mfd";
		reg = <0x0 0xff770000 0x0 0x10000>;
		#address-cells = <1>;
		#size-cells = <1>;

		......

		pcie_phy: pcie-phy {
				compatible = "rockchip,rk3399-pcie-phy";
				clocks = <&cru SCLK_PCIEPHY_REF>;
				clock-names = "refclk";
				#phy-cells = <1>;
				resets = <&cru SRST_PCIEPHY>;
				reset-names = "phy";
				status = "disabled";
		};
};

为什么没有 reg #

pcie_phy 没有 reg 属性，因为它不占独立地址。RK3399 的 PCIe PHY 的配置寄存器被塞在 GRF 的某一批偏移里，PHY 驱动要先拿到 GRF 的 syscon 句柄，再用偏移去读写。

GRF 节点上那串 compatible 是关键：

compatible 项 作用
rockchip,rk3399-grf SoC 专用标识
syscon 声明这是一组杂项寄存器，可以被别人通过 syscon 框架拿到
simple-mfd 声明这是个简单多功能设备，子节点各自当独立 platform device 注册

simple-mfd 让 pcie_phy 这个子节点能被单独实例化成 platform device，才会有自己的驱动去 probe。没有它，pcie_phy 只是个死节点。

PHY 节点里的两个 phandle：&cru 是时钟复位单元（PHY 的 refclk 和 phy 复位都从那儿来），GRF 本身则通过 syscon 查找。PHY 驱动里怎么拿到 GRF，源码我没有逐行核对，按 Rockchip 同类 PHY 驱动的惯例是查 rockchip,rk3399-grf 这个 compatible，标为未验证。

GRF 地址 #

syscon@ff770000，长 0x10000（64KB）。#address-cells = <1>、#size-cells = <1>，所以它的子节点如果有 reg，是 1 格地址 1 格长度。

pcie_phy 没有 reg，也就没有偏移。这意味着 PHY 驱动必须自己知道「PCIe PHY 那批寄存器在 GRF 的第几页」，这个知识硬编码在驱动里。

PHY 节点的字段表 #

属性 值 说明
compatible rockchip,rk3399-pcie-phy 绑定 PHY 驱动
clocks <&cru SCLK_PCIEPHY_REF> 参考时钟
clock-names refclk 必须是这个名字
#phy-cells <1> 每个 phandle 带 1 格 lane 编号
resets <&cru SRST_PCIEPHY> PHY 专用复位
reset-names phy 必须是这个名字
status disabled 默认不启用

rockchip,rk3399-pcie-phy.yaml 把 clock-names 和 reset-names 写成了 const，也就是只能填 refclk 和 phy，别自己起名。

CLKREQ# 的 pinctrl 定义 #

CLKREQ# 这类边带信号在 dtsi 里另有一组 pinctrl 定义：

dts
pinctrl: pinctrl {
		compatible = "rockchip,rk3399-pinctrl";
		rockchip,grf = <&grf>;
		rockchip,pmu = <&pmugrf>;
		#address-cells = <2>;
		#size-cells = <2>;
		ranges;
		......
		pcie {
				pcie_clkreqn_cpm: pci-clkreqn-cpm {
						rockchip,pins =
								<2 RK_PD2 RK_FUNC_GPIO &pcfg_pull_none>;
				};

				pcie_clkreqnb_cpm: pci-clkreqnb-cpm {
						rockchip,pins =
								<4 RK_PD0 RK_FUNC_GPIO &pcfg_pull_none>;
				};
		};
};
引脚名 排布 含义
pcie_clkreqn_cpm bank 2、RK_PD2 CLKREQ#，GPIO 功能，无上下拉
pcie_clkreqnb_cpm bank 4、RK_PD0 CLKREQ#B（第二路），GPIO 功能，无上下拉

RK_FUNC_GPIO 表示把引脚切到 GPIO 功能，&pcfg_pull_none 表示不加上下拉。CLKREQ# 是开漏信号，上下拉由板上电阻决定，SoC 侧不能抢。

这两个 pin group 要不要用，取决于板子有没有引出 CLKREQ#。dtsi 里 pcie0 的 pinctrl 相关属性没写，需要时由板级 dts 补 pinctrl-names = "default"; pinctrl-0 = <&pcie_clkreqn_cpm>;。

GRF 的另一个身份 #

pinctrl 节点自己的 rockchip,grf = <&grf> 和 PHY 用 GRF 的路径是两条独立的线：pinctrl 用它改引脚复用，PHY 用它配模拟参数。同一个 GRF，两个消费者，互不干扰。

十三、从 disabled 到 enabled：怎么打开 #

dtsi 里两个节点都是 status = "disabled"，板级 dts 里要同时打补丁。素材给的是 rk3399-evb.dts 的写法。

pcie_phy 的补丁 #

dts
&pcie_phy {
	assigned-clock-parents = <&cru SCLK_PCIEPHY_REF100M>;
	assigned-clock-rates = <100000000>;
	assigned-clocks = <&cru SCLK_PCIEPHY_REF>;
	status = "okay";
};

四个属性各管一件事：

属性 值 作用
assigned-clocks SCLK_PCIEPHY_REF 指定要配置哪一路时钟
assigned-clock-parents SCLK_PCIEPHY_REF100M 指定它的父时钟源
assigned-clock-rates 100000000 指定频率 100MHz
status okay 启用

这三个 assigned-* 是标准时钟绑定属性，由 of_clk_set_defaults() 在设备 probe 前统一处理，顺序是先设父、再设频率。少了 assigned-clock-parents，切频率这一步会失败，因为父时钟源跑不到 100MHz。

SCLK_PCIEPHY_REF100M 是个 100MHz 的固定时钟源（PLL 分频出来的），和 dtsi 里 aspm-no-l0s 那条「PHY 参考时钟不是 100MHz 就不支持 L0s」正好对上：把参考时钟切到 100MHz，L0s 的限制就不再成立。

pcie0 的补丁 #

dts
&pcie0 {
	ep-gpios = <&gpio2 RK_PA4 GPIO_ACTIVE_HIGH>;
	max-link-speed = <2>;
	num-lanes = <2>;
	vpcie0v9-supply = <&vcca0v9_s3>;
	vpcie1v8-supply = <&vcca1v8_s3>;
	status = "okay";
};
属性 值 作用 是否必填
ep-gpios gpio2 的 RK_PA4，高电平触发 PERST#，复位下游设备 有 EP 就该写
max-link-speed <2> 覆盖 dtsi 的 1，跑 Gen2 可选
num-lanes <2> 用 2 条 lane 可选
vpcie0v9-supply vcca0v9_s3 0.9V 供电 板上有就写
vpcie1v8-supply vcca1v8_s3 1.8V 供电 板上有就写
status okay 启用 必填

ep-gpios 对应绑定文档的「pre-reset GPIO」，作用是给下游设备一个确定的复位时序：先拉低复位、释放、再等链路训练。没有它，链路训练时序取决于上电顺序，冷启动能起来、热重启起不来这类怪现象就从这儿来。

vpcie12v-supply 和 vpcie3v3-supply 也是可用选项，绑定文档里列了。板上没有这两路电源就不写。

供电节点 #

板级 dts 根节点下要有对应的 regulator 节点，否则 vpcie*-supply 的 phandle 无处可指：

dts
/ {
	vcca0v9_s3: vcca0v9-s3 {
		compatible = "regulator-fixed";
		regulator-min-microvolt = <900000>;
		regulator-max-microvolt = <900000>;
		regulator-name = "vcca0v9_s3";
		vin-supply = <&vcc1v8_s3>;
	};

	/* As above, actually supplied by vcc3v3_sys */
	vcca1v8_s3: vcca1v8-s3 {
		compatible = "regulator-fixed";
		regulator-min-microvolt = <1800000>;
		regulator-max-microvolt = <1800000>;
		regulator-name = "vcca1v8_s3";
		vin-supply = <&vcc1v8_s3>;
	};
};

两点值得看：

compatible = "regulator-fixed" 表示固定电压，regulator-min-microvolt 和 regulator-max-microvolt 相等就是这个意思。vin-supply 指定上级电源，形成供电树。

注意 vcca1v8_s3 那个节点的注释「actually supplied by vcc3v3_sys」和 vin-supply = <&vcc1v8_s3> 对不上。注释说的是实际上由 3.3V 系统电源供出来，代码写的是挂到 vcc1v8_s3 下面。素材里就是这样，我原样保留，这是一处文档与代码不一致，改板时按原理图核对，别照抄注释。

十四、调试手段：lspci 与 sysfs #

板上跑起来之后，按下面的顺序看。

第一步：设备有没有被枚举 #

bash
lspci

素材里的真实输出：

text
00:00.0 PCI bridge: Fuzhou Rockchip Electronics Co., Ltd RK3399 PCI Express Root Port
01:00.0 Non-Volatile memory controller: Yangtze Memory Technologies Co.,Ltd Device 0021 (rev 01)

两行说明两件事：00:00.0 是控制器自身（根端口，0 号总线），01:00.0 是挂在总线 1 上的 NVMe。素材这块盘是长江存储致钛 TiPlus5000（NVMe M.2）。

01 这个总线号来自 bus-range = <0x0 0x1f>，根总线 0 用了，下游分配 1。

第二步：看细节 #

bash
lspci -v

素材输出的关键几行：

text

        Flags: bus master, fast devsel, latency 0, IRQ 80

逐行读：

行 读法
IRQ 80 / IRQ 79 Linux 虚拟中断号，不是 GIC 的 SPI 号，也不是 MSI 的 vector
Memory behind bridge: fa000000-... 桥后面能用的内存窗口，和 ranges 对得上
Memory at fa000000 (64-bit, non-prefetchable) [size=16K] NVMe 的 BAR0，映射到 CPU 地址 0xfa000000
MSI: Enable+（桥） 桥自身用 MSI，1 个向量
MSI: Enable-（设备） Enable- 表示 NVMe 这一路没走传统 MSI
MSI-X: Enable+ Count=9 NVMe 用了 9 个 MSI-X 向量，走 ITS
Kernel driver in use: nvme 绑定到了 nvme 驱动
Unable to load libkmod resources: error -12 板子上缺 libkmod 数据，只是 lspci 的显示告警，不影响设备

lspci -v 输出的能力项（Capabilities）是设备配置空间里 CAP 链表的直读结果。看到 MSI-X: Enable+ 就说明 ITS 那条链路是通的。

第三步：看 sysfs #

bash
# 所有 PCI 设备的属性
ls /sys/bus/pci/devices/

# 看某个设备的资源分配
cat /sys/bus/pci/devices/0000:01:00.0/resource

# 看链路速率和宽度
cat /sys/bus/pci/devices/0000:00:00.0/current_link_speed
cat /sys/bus/pci/devices/0000:00:00.0/current_link_width
cat /sys/bus/pci/devices/0000:00:00.0/max_link_speed
cat /sys/bus/pci/devices/0000:00:00.0/max_link_width

# 看中断向量
cat /sys/bus/pci/devices/0000:01:00.0/irq

0000:01:00.0 里的 0000 是 PCI domain，没有 linux,pci-domain 属性时由内核分配。

resource 文件每一行是一对 start end 地址区间，全 0 表示这个 BAR 没分配。

第四步：看中断有没有真的来 #

bash
cat /proc/interrupts | grep -E 'pcie|its|nvme'

这个文件里的行按中断控制器分组。ITSP 开头的那些是 ITS 的 LPI 行，pcie0 三根 SPI 也会单独出现。nvme0q0、nvme0q1 这类名字出现，说明 MSI 向量确实分配到了。

中断计数一直不涨，但 lspci 能看到设备，问题就在中断路由上，回去看第五、六章的属性。

第五步：看内核日志 #

十五、常见故障与现象对照 #

按「现象 → 先查哪 → 根因」排。

现象 先看什么 常见根因 对应章节
lspci 一行都没有 /sys/bus/pci/devices/ 是否为空；dmesg 有没有 PCI host bridge status 没改 okay；CONFIG_PCI_ROCKCHIP 没开 十三
只有 00:00.0，没有下游设备 dmesg 里 Link up 有没有 链路训练失败：PERST# GPIO 错、供电缺失、num-lanes 与实际不符 十、十一、十三
probe 报 failed to get pcie-phy phys、phy-names 是否 4 项齐全 phy-names 写了 pcie-phy（老写法）而 #phy-cells = <1> 十
probe 报取不到时钟 clocks 四路是否齐全、名字对不对 clock-names 里把 hclk 改成了 pclk 八
probe 报取不到复位 resets 是不是 7 项 只抄了 5 项，漏 pclk/aclk 九
设备能枚举，BAR 全 0 cat resource ranges 窗口被别处占用导致解析失败 七
设备能枚举，中断不进来 /proc/interrupts 计数不动 msi-map 覆盖的 RID 范围不够；interrupt-map 被改坏 五、六
中断风暴，CPU 100% /proc/interrupts 某一根疯涨 电平触发中断没清状态位；legacy 和 client 挂反 四
冷启动正常、热重启起不来 ep-gpios 有没有写 缺 PERST#，复位时序依赖上电顺序 十三
链路只跑 Gen1 current_link_speed、max_link_speed max-link-speed 还是 dtsi 的 1 十一
链路宽度只有 x1 current_link_width num-lanes 配错，或 lane 走线有问题 十、十一
nvme 设备在，/dev/nvme0n1 不在 CONFIG_BLK_DEV_NVME 内核配置缺驱动 十三
AER 刷屏 Corrected error lspci -vv 的 LnkSta 信号质量差、参考时钟抖动、走线过长 十一
改了 dts 没生效 反编译 dtb 看 status 板级 dts 没被编进去，或用的是旧 dtb 十三

排查顺序建议固定成：dmesg → lspci → /sys 资源 → /proc/interrupts。从前往后走，能在哪一步断掉就说明问题在哪一层，不用一上来就翻寄存器。

十六、易错点速查 #

易错点 错误写法 正确写法 后果
reg-names 顺序 把 apb-base 写前面 axi-base 在前，apb-base 在后 两段寄存器映射反了，读写全乱
#address-cells 以为是给 reg 用的 是给子节点的 PCI 地址格式 理解错就连 ranges 都看不明白
interrupt-map-mask 写 <0 0 0 3> 写 <0 0 0 7> INTx 4（编号 4）匹配不上，D 根丢失
interrupt-names 顺序 和 interrupts 错位 严格一一对应 中断挂到错的处理函数
pcie0_intc 的 #address-cells 抄父节点的 <3> 必须 <0> dtc 报 cell 数不匹配
msi-map 第 4 格 以为是通道数 是 RID 区间长度 总线数超过覆盖范围时 MSI 静默失效
ranges 的 phys.hi 以为 0x82000000 是随便编的地址 高字节是空间类型：0x02 内存、0x01 I/O 写错类型，设备 BAR 分配失败
ranges 长度 两条窗口重叠 内存 30MB + I/O 1MB，首尾相接 内核报地址冲突
clock-names 的 hclk 去 rk3399-cru.h 搜 HCLK_PCIE 宏名是 PCLK_PCIE，名字只是键 搜不到以为 dts 写错了
resets 项数 只写 5 项 7 项，含 pclk、aclk probe 失败
phys 项数 只用 2 lane 就写 2 项 必须 4 项全写 PHY 取不到，probe 失败
phy-names 写法 "pcie-phy" "pcie-phy-0" 到 "pcie-phy-3" 与 #phy-cells = <1> 不配套
#phy-cells <0> <1> lane 编号无处安放
max-link-speed 写 5 只能 1 到 4 属性非法，驱动忽略或用默认
status 只改 pcie0 不改 pcie_phy 两个都要 okay PHY 没起，链路训练失败
SCLK_PCIEPHY_REF 的父时钟 只设 assigned-clock-rates 三个 assigned-* 一起写 频率设不上去
ep-gpios 省略 有下游设备就写 热复位异常
aspm-no-l0s 当成有值属性写成 aspm-no-l0s = <1> 它是布尔属性，不写值 dtc 告警

还有一条不属于字段层面但更常踩：改完 dts 一定要反编译确认。&pcie0 { ... } 这种补丁写错 label 名字时，dtc 不一定报错，生成的 dtb 里节点还是 disabled，你在板上怎么查都查不出原因。
