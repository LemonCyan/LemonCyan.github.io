一、总线、设备、驱动三者怎么配 #

一条真实总线，PCI 也好 USB 也好，至少干三件事：有电气规范和时序；能枚举，主机主动去问「你是什么设备」；支持热插拔，插拔都有事件通知内核。

嵌入式的 SoC 内部设备三件都不占。GPIO 控制器、I2C 控制器、UART、PWM、看门狗、DMA、RTC 全焊在芯片里，挂在片内 AXI/AHB/APB 上，寄存器直接映射进 CPU 地址空间。它们没法枚举——在 0x114000a0 上读一下，读到的是未定义值，不是设备 ID；地址写死在 SoC 手册里；也不能插拔，芯片焊上去就那些外设。

枚举这一环没人替你干，设备信息就只能由人写出来。这就是 platform 总线的来历，内核源码 drivers/base/platform.c 的文件头写得很直白：platform 'pseudo' bus for legacy devices。

两条路的差别，一句话：

text
真实总线
  硬件存在 ──▶ 内核枚举 ──▶ device 自动生成 ──▶ 匹配 driver ──▶ probe

platform
  硬件存在（只在地址空间里）──▶ 没人枚举 ──▶ 人写 device ──▶ 匹配 driver ──▶ probe

三个角色各管什么：

角色 抽象的是什么 谁负责写 在总线里的位置
bus（总线类型） 一套匹配规则加一组回调 内核 持有 devices 与 drivers 两个链表
device（设备） 这块板有什么外设、地址多少、中断号多少 BSP 代码或设备树 挂进 bus->devices
driver（驱动） 这类外设怎么操作，寄存器怎么读写 SoC 厂商或驱动工程师 挂进 bus->drivers

这个拆法的收益很直接：驱动里不再出现 #define UART_BASE 0x11400000，改成 platform_get_resource(pdev, IORESOURCE_MEM, 0)；换一块板只改 BSP，驱动一行不动。BSP 在 2.6.35 时代的落点是 linux/arch/arm/mach-s5pc100/mach-smdkc100.c，板子上所有 platform_device 都塞在那种文件里。到了 3.14 之后，这个角色交给设备树。

platform 总线内部的两个链表 #

总线内部挂两个链表：一个串 device，一个串 driver。注册 device 时扫 driver 链表，注册 driver 时扫 device 链表，两个方向都收敛到同一个回调——bus->match。

所以「先 insmod 驱动还是先 insmod 设备」这个问题没有意义。晚到的那一方注册时会主动去扫另一侧。

每个结构体里「参与匹配」的字段 #

这一列最容易记混，单独拎出来：

结构体 字段 作用
platform_device .name 参与匹配，比对驱动名
platform_device .id 不参与匹配，只拼 bus_id（name.id），-1 表示只有一个实例
platform_driver .driver.name 与 pdev->name 字符串比对，兜底规则
platform_driver .id_table 一个驱动对多个型号；一旦写了，name 匹配直接出局
platform_driver .driver.of_match_table 与设备树 compatible 比对，优先级最高

platform_device 里还有一个 struct device dev 成员，描述硬件设备必须有它——没有这个成员，设备根本进不了设备模型，总线也看不到你。这是「设备树信息怎么变成 platform_device」这条链的落脚点。

二、platform 是条什么总线 #

bus_type 抽象的是「一类设备和一类驱动的共同规则」。platform 的那一份，3.x 原文：

c
struct bus_type platform_bus_type = {
    .name       = "platform",
    .dev_groups = platform_dev_groups,
    .match      = platform_match,
    .uevent     = platform_uevent,
    .pm         = &platform_dev_pm_ops,
};

三个回调，逐个说清楚：

回调 什么时候被调 干什么 要不要自己写
.match 设备或驱动任一侧注册时 判断这个 dev 和这个 drv 配不配对 这是核心，读它
.uevent 设备注册、状态变化 往用户态发 uevent，udev / mdev 收到后建设备节点 内核提供，不碰
.pm 系统挂起与恢复 遍历总线上的设备做 suspend / resume 内核提供，驱动只在 dev_pm_ops 里填自己的

.dev_groups 不算回调，是 sysfs 属性组，把设备的属性文件挂到 /sys/bus/platform/devices/*/ 下面。

总线这一层是并列的：spi、i2c、usb、can、pci、platform。前五条都有电气规范和硬件协议；platform 是唯一没有电气的那条，纯靠人填结构体，所以叫假总线。这几条总线共用同一套设备模型，区别只在 .match 怎么写、两侧结构体长什么样。学会 platform 的读法，换成 i2c、spi 只是换名字。

三、platform 的注册与匹配 #

先看两条注册链。驱动侧：

text
platform_driver_register(&pdrv)
  └─ __platform_driver_register()
       └─ driver_register(&pdrv->driver)
            └─ bus_add_driver()
                 └─ driver_attach()
                      └─ bus_for_each_dev(drv->bus, NULL, drv, __driver_attach)
                           └─ __driver_attach(dev, drv)      /* 对每个 device 来一遍 */
                                └─ driver_match_device(drv, dev)
                                     └─ drv->bus->match(dev, drv)   ← 落到 platform_match

设备侧：

text
platform_device_register(&pdev)
  └─ platform_device_add()
       └─ device_add()
            └─ bus_probe_device()
                 └─ device_attach()  →  __device_attach_driver()
                      └─ driver_match_device()  →  bus->match()

两条链在 driver_match_device() 汇合。它的实现短到可以背下来：

c
static inline int driver_match_device(struct device_driver *drv,
                                      struct device *dev)
{
    return drv->bus->match ? drv->bus->match(dev, drv) : 1;
}

注意那个三元运算的右半边：match 为空的 bus，一律返回 1，也就是「无条件匹配成功」。这就是为什么有些极简的总线不写 match 也能跑起来。

platform_match 是 3.x 的版本：

c
static int platform_match(struct device *dev, struct device_driver *drv)
{
    struct platform_device *pdev = to_platform_device(dev);
    struct platform_driver *pdrv = to_platform_driver(drv);

    /* 第一级：设备树匹配 */
    if (of_driver_match_device(dev, drv))
        return 1;

    /* 第二级：id_table 匹配 */
    if (pdrv->id_table)
        return platform_match_id(pdrv->id_table, pdev) != NULL;

    /* 兜底：名字比对 */
    return (strcmp(pdev->name, drv->name) == 0);
}

两个参数是通用的 device / device_driver，头两行先反推回 platform 的具体类型。做 device 和 driver 的强转，别搞反，否则后面全是野指针。

platform_match 的判定按代际分成两张表。3.x 是三级：

优先级 判据 比对对象 典型场合 坑
1 of_driver_match_device() dts compatible 对 of_match_table 现代 ARM，设备由设备树描述 要求 pdev->dev.of_node 非空
2 platform_match_id() pdev->name 对 id_table[].name 一个驱动支持多款芯片 命中与不命中都直接 return
3 strcmp(pdev->name, drv->name) 纯字符串比对 传统板级 BSP 只在上面都没走到时才生效

5.x 起变成五级，前面插了两级、后面没动：

优先级 判据 引入 说明
0 pdev->driver_override 具体版本未验证 设了就是独占，其余四级全跳过
1 of_driver_match_device() 3.x 已有 同 3.x 第一级
2 acpi_driver_match_device() 具体版本未验证 比 ACPI _HID 与 acpi_match_table，3.x 里没有
3 platform_match_id() 3.x 已有 同 3.x 第二级
4 strcmp(pdev->name, drv->name) 3.x 已有 同 3.x 第三级

第三级那一行（按 5.x 的编号）最容易读错：它是 return 而不是「不匹配就继续往下走」。驱动一旦定义了 id_table，name 匹配就再也不参与。很多人写了 id_table 又纳闷名字明明一样为什么不 probe，就是撞在这行上。

driver_override 通过 sysfs 设置，不是直接赋结构体字段——驱动核心会在设备释放时 kfree 它，走 driver_set_override() 才安全。用途是抢绑：一个设备能被多个驱动匹配时，强制绑到你指定的那个。

of_driver_match_device 往下是什么 #

设备树匹配这一级不是一步到位的，调用链一层套一层：

text
of_driver_match_device(dev, drv)
  └─ of_match_device(drv->of_match_table, dev)
       └─ of_match_node(drv->of_match_table, dev->of_node)
            └─ __of_match_node(drv->of_match_table, dev->of_node)
                 └─ 逐个 compatible 项比对

四层看着多，实际就干一件事：拿设备的 compatible 字符串，去 of_match_table 里一行一行比。命中就返回那个 of_device_id 项，驱动后面能用 .data 取到型号相关的数据。

id_table 的哨兵 #

platform_match_id() 的循环靠 id->name[0] 为空来终止。struct platform_device_id 全零时 name[0] 正好是 '\0'，循环停。

c
static const struct platform_device_id my_ids[] = {
    { .name = "s3c2440-uart", .driver_data = 0 },
    { .name = "s5pv210-uart", .driver_data = 1 },
    { }            /* 哨兵，少这一行就等着 oops */
};

忘了最后那个空项，循环会一直往后读，读到内存边界才撞上一个恰好为 0 的字节，或者直接崩溃。这是 id_table 最经典的 bug。

循环命中时还有个副作用：pdev->id_entry = id。所以驱动可以在 probe() 里读 pdev->id_entry->driver_data 区分型号。

platform_driver 的回调与 remove 的返回值 #

3.x 时代的结构体，回调只有五个：

c
struct platform_driver {
    int (*probe)(struct platform_device *);      /* 匹配成功就调它 */
    int (*remove)(struct platform_device *);     /* 卸载/解绑时调 */
    void (*shutdown)(struct platform_device *);
    int (*suspend)(struct platform_device *, pm_message_t state);
    int (*resume)(struct platform_device *);
    struct device_driver driver;                 /* 内嵌的通用驱动结构 */
    const struct platform_device_id *id_table;   /* 一个驱动对多个型号 */
    bool prevent_deferred_probe;
};

内嵌的那个 struct device_driver driver 是必须的成员，跟 platform_device 里内嵌 struct device dev 是一个道理：总线只认通用类型，你的私有结构必须把它包在里面。id_table 在老内核上就是给「一个驱动支持多个硬件」用的。

probe 的返回值是有意义的：0 表示绑定成功，负 errno 表示失败，核心会把这个设备留给下一个驱动。remove 的返回值没有意义：核心拿到之后只看一眼是不是 0，非 0 就打印一条警告然后照样继续卸载。

这件事在 6.11 被彻底改掉。platform_driver.remove 的返回类型从 int 改成 void（commit 0edb555a65d1，作者 Uwe Kleine-König），中间还经历过一个 remove_new 的过渡期——新驱动先写返回 void 的 remove_new，等所有驱动都改完了，两者合并成一个返回 void 的 remove。

落到写法上：

内核版本 .remove 的签名 你是不是要 return
3.x（本篇素材） int (*remove)(struct platform_device *) 要，return 0
过渡期（含 remove_new） int 与 void 两套并存 老字段要 return，新字段不要
6.11 之后 void (*remove)(struct platform_device *) 不要，写 return; 会编译告警

拿 3.x 的代码往 6.x 上搬，remove 里那个 return 0 就是第一个编译错误。

设备树怎么变成 platform_device #

素材里只留了两个符号：start_kernel 和 setup_arch()。链路大意的说法是：setup_arch() 阶段解析 dtb、展开成 device_node 树，之后 of_platform_populate() 遍历根节点下的子节点，命中 compatible 的节点按 reg 属性填出 resource 数组，再生成 platform_device 并注册。

每一步的准确函数名和版本差异，没有逐个核对，标「未验证」。面试被追问到这一层，能说出「在 setup_arch 之后由 of 平台代码批量生成」就够了，再往下就进正式篇目。

四、子系统框架的共同骨架 #

把 platform、I2C、SPI、ADC 这几套东西摊开看，骨架是同一个。五个固定位置：

位置 platform 里的实例 说明
总线类型 platform_bus_type 定匹配规则，串两个链表
设备侧结构体 platform_device 描述板上有啥
驱动侧结构体 platform_driver 描述怎么操作
数据与资源 struct resource 地址、中断号
用户接口 无，驱动自建 靠 cdev 和 file_operations

第五个位置是 platform 与字符设备最容易混的地方。platform_device 不是与字符设备并列的另一种设备分类，它是「挂在哪条总线上」的维度；字符设备是「用户态怎么访问」的维度。一个 LED 驱动可以同时是 platform 驱动和字符设备驱动——前半段靠 platform 拿到寄存器地址，后半段靠 cdev 让应用层 open。

于是每个外设驱动都有两条链，分头走：

text
内核态这条（注册与匹配）
  driver_register → bus 匹配 → probe(pdev) → 取资源 → ioremap → 干活

用户态这条（字符设备）
  register_chrdev_region → cdev_init → cdev_add → class_create
  → device_create → /dev/xxx → open/read/write/ioctl 落到 file_operations

probe() 就是把两条链接上的那个交点。这也是为什么 platform 版的 LED 驱动，看着像字符设备驱动多套了一层壳——壳里多出来的东西，全是为了把寄存器地址从「写死」改成「从 pdev 里问」。

五、I2C 子系统的四层 #

I2C 自己也是条真实总线，但它的框架比 platform 多一层核心代码，所以拆成四层：

层 内容 谁写 代码位置
第一层 adapter 硬件驱动：探测控制器、申请 IO 与中断、处理 I2C 中断 SoC 厂商 drivers/i2c/busses/i2c-*.c
第二层 adapter 的 algorithm：xxx_xfer() 填进 master_xfer，赋给 adapter->algo SoC 厂商，与第一层同一文件 同上
第三层 设备驱动侧：i2c_driver 的 probe/remove 与收发逻辑 驱动工程师 drivers/i2c/chips/ 或各子系统目录
第四层 具体设备的 read/write/ioctl，填 file_operations 注册字符设备 驱动工程师 同上

第一层加第二层合称 I2C 总线驱动，第三层加第四层合称 I2C 设备驱动。你要写的永远只有一半：写控制器就填 adapter + algorithm，写芯片就填 driver，bus 本身芯片厂已经给了。3.14 上三星的控制器驱动是 drivers/i2c/busses/i2c-s3c2410.c。

三个角色怎么对上 #

除了四层，还要记住三个结构体的三角关系：

结构体 抽象的是谁 由谁创建 关键字段
i2c_adapter SoC 里的一个 I2C 控制器，也就是一条总线 adapter 驱动注册时 algo、nr、dev
i2c_client 挂在这条总线上的一个芯片 内核按设备树或 board_info 生成 addr、adapter、irq
i2c_driver 一套针对某型号芯片的操作逻辑 驱动工程师填，i2c_add_driver 注册 id_table、probe、driver

配对关系是两根线：client 与 driver 配对，一个驱动服务同型号的多个实例；adapter 与 client 也是一对多，adapter 内部用链表串起挂在它下面的所有 client。一个 SoC 有几个 I2C 控制器，就有几个 adapter。

还有一个不在四层里但绕不开的角色：core。i2c_transfer()、i2c_register_driver()、client 的实例化全在 core 里，设备驱动只面对 i2c_adapter，不关心后面是 S3C 还是 STM32 的控制器。

3.14 上几个结构体的关键字段 #

i2c_client，匹配靠 addr，一个 client 只代表一个地址上的芯片：

c
struct i2c_client {
    unsigned short flags;
    unsigned short addr;            /* 7 位地址，存在低 7 位 */
    char name[I2C_NAME_SIZE];
    struct i2c_adapter *adapter;    /* 挂在哪条总线上 */
    struct device dev;
    int irq;                        /* 这个设备自己的中断 */
    struct list_head detected;
};

上面这份是 3.14 的字段集。5.3 的文档里多了 init_irq 和 slave_cb（开了 CONFIG_I2C_SLAVE 才有），detected 的含义也扩了。

i2c_driver 侧，3.14 上还留着已经废弃的 attach_adapter：

c
struct i2c_driver {
    unsigned int class;
    int (*attach_adapter)(struct i2c_adapter *) __deprecated;
    int (*probe)(struct i2c_client *, const struct i2c_device_id *);
    int (*remove)(struct i2c_client *);
    void (*shutdown)(struct i2c_client *);
    void (*alert)(struct i2c_client *, unsigned int data);
    int (*command)(struct i2c_client *, unsigned int cmd, void *arg);
    struct device_driver driver;
    const struct i2c_device_id *id_table;
    int (*detect)(struct i2c_client *, struct i2c_board_info *);
    const unsigned short *address_list;
    struct list_head clients;
};

四处版本变化要记：

字段 3.x 之后
attach_adapter 已标 __deprecated 后续删除，具体版本未验证
probe int (*probe)(client, id) 5.x 增加 probe_new(client) 双份并存，文档里写老 probe 将被废弃
remove int (*remove)(client) 6.1 起改成返回 void（commit ed5c2f5fd10d）
detect / address_list 老式地址探测用 新驱动不写，靠设备树枚举

i2c_algorithm 只有三个函数指针，第二个是给 SMBus 用的，没有就走 I2C 消息模拟：

c
struct i2c_algorithm {
    int (*master_xfer)(struct i2c_adapter *adap, struct i2c_msg *msgs, int num);
    int (*smbus_xfer)(struct i2c_adapter *adap, u16 addr,
                      unsigned short flags, char read_write,
                      u8 command, int size, union i2c_smbus_data *data);
    u32 (*functionality)(struct i2c_adapter *adap);
};

master_xfer 是核心：拿到一组 i2c_msg 和个数，负责真的把波形打出去。

i2c_msg 是设备驱动唯一要亲手填的东西：

c
struct i2c_msg {
    __u16 addr;     /* 从设备地址 */
    __u16 flags;    /* I2C_M_RD 表示读，0 表示写 */
    __u16 len;      /* 本段消息的字节数 */
    __u8  *buf;     /* 数据缓冲区 */
};

flags 里只有 I2C_M_RD 和 I2C_M_TEN 是日常要用的，剩下几个是协议变形开关，多数控制器不支持。

i2c_board_info 是 client 的原料。3.14 版本里还带着 archdata、acpi_node 这种老字段，5.x 之后换成了 fwnode、properties、resources。转述一句关键的：老内核要自己填这个结构体并调 i2c_register_board_info()；基于设备树的内核里，它是 of 代码从节点里解析出来的，人不写。

i2c_bus_type #

I2C 也有一条 bus_type，形状跟 platform 那条一模一样：

c
struct bus_type i2c_bus_type = {
    .name    = "i2c",
    .match   = i2c_device_match,
    .probe   = i2c_device_probe,
    .remove  = i2c_device_remove,
    .shutdown = i2c_device_shutdown,
    .pm      = &i2c_device_pm_ops,
};

跟 platform 的差别在于：platform 的 bus_type 只填了 match，probe 由驱动核心统一调；i2c 这里还填了 .probe 和 .remove，属于总线层自己接管一部分绑定动作。

.match 的判定规则与 platform 的设备树匹配规则一致——先比 of_match_table，再比 id_table，最后比名字。素材原话是「匹配规则和 platform 设备树节点匹配规则一致」。

六、I2C 的注册与匹配 #

两件事分开走：adapter 注册，driver 注册。设备（client）夹在中间，由 adapter 注册过程中生成。

adapter 注册链 #

3.14 上的链路，素材逐层点过名字：

text
i2c_add_numbered_adapter(&i2c->adap)
  └─ __i2c_add_numbered_adapter()
       └─ i2c_register_adapter()
            ├─ device_register()            把 adapter 挂上 i2c_bus_type
            └─ of_i2c_register_devices()     ← 设备树内核的关键一步
                 └─ i2c_new_device()         为每个子节点造 client

i2c_add_numbered_adapter() 与 i2c_add_adapter() 的区别只有一个：前者用你指定的总线号（adap->nr 预先填好），后者让内核动态分配。SoC 内部的控制器用前者，因为设备树里的总线号是写死的，得对上。

client 什么时候生成 #

素材把这个问题标了三个问号，答案就在上面那条链的最后一跳：client 不是驱动建的，是 adapter 注册时由 of 代码从设备树子节点里批量生成的。

text
i2c@13870000 {                      ← adapter 节点
    compatible = "samsung,s3c2440-i2c";
    reg = <0x13870000 0x100>;
    #address-cells = <1>;
    #size-cells = <0>;
    ...
    mpu6050-3-asix@68 {             ← client 节点
        compatible = "invensense,mpu6050";
        reg = <0x68>;
        interrupt-parent = <&gpx3>;
        interrupts = <3 2>;
    };
};

节点名里 @68 的 68 就是 I2C 从地址，reg = <0x68> 是同一个值的十六进制写法。#address-cells = <1> 与 #size-cells = <0> 这两行是硬要求，少一行 of 代码就解析不出子节点。

版本变化：i2c_new_device 已经过时 #

i2c_new_device() 在 5.x 里被标成 deprecated，替代者是 i2c_new_client_device()。两者的功能一样，差别在错误返回：

函数 出错时返回 状态
i2c_new_device() NULL 5.3 文档里写明 deprecated，将被删除
i2c_new_client_device() ERR_PTR 5.3 起是推荐接口

引入 i2c_new_client_device() 的确切版本未验证。可以确认的是它已经出现在 5.3 的文档里，而 5.1 的文档里只有 i2c_new_device()。所以「3.14 上还是 i2c_new_device、5.4 前后换成 i2c_new_client_device」这个说法方向没错，中间的具体版本点没有核对到。

改接口带来的实际差别只有一个：拿到返回值之后要判 IS_ERR(client) 而不是判 NULL。判错了，一个错误指针直接进 i2c_transfer()，等着 oops。

driver 注册 #

c
#define i2c_add_driver(driver) \
    i2c_register_driver(THIS_MODULE, driver)

一个宏，把模块 owner 塞进去。往下走 i2c_register_driver()，它做三件事：填 driver->driver.bus = &i2c_bus_type、调 driver_register()、扫描已有的 client 试着绑定。

模块里只写一个驱动，用 module_i2c_driver(my_drv) 就够，省掉 init 与 exit 两个函数。

匹配靠什么 #

i2c 的匹配不看 name，看 id_table 和 of_match_table，与 platform 的设备树那一级同构：

c
static const struct i2c_device_id mpu6050_id[] = {
    { "mpu6050", 0 },
    { }
};

static const struct of_device_id mpu6050_of_match[] = {
    { .compatible = "invensense,mpu6050" },
    { }
};

static struct i2c_driver mpu6050_drv = {
    .probe  = mpu6050_probe,
    .remove = mpu6050_remove,
    .driver = {
        .name           = "mpu6050",
        .of_match_table = mpu6050_of_match,
    },
    .id_table = mpu6050_id,
};

注意这里 driver.name 不参与匹配，它只是 sysfs 里的目录名。跟 platform 那条 strcmp(pdev->name, drv->name) 完全不同——别把两边记串。

怎么填 i2c_msg #

素材里反复强调的那条规则，值得单独记：

有几个 STOP 就有几个 i2c_msg；每个 i2c_msg 的 len 是这个命令除从设备地址之外还有几个字节。

拆开说。一次「写寄存器地址再读数据」的读操作，中间有个重复起始位（Sr），没有 STOP，所以是两条 msg：

c
/* 读 mpu6050 的 WHO_AM_I 寄存器 */
u8 reg = 0x75;
u8 val;
struct i2c_msg msgs[2] = {
    { .addr = client->addr, .flags = 0,       .len = 1, .buf = &reg },
    { .addr = client->addr, .flags = I2C_M_RD, .len = 1, .buf = &val },
};

ret = i2c_transfer(client->adapter, msgs, 2);
if (ret != 2)
    return ret < 0 ? ret : -EIO;

第一条发寄存器地址（1 字节），第二条读回值（1 字节）。len 都不含从设备地址本身——地址在 .addr 字段里，单独发。

i2c_transfer() 的返回值是「成功传输了几条 msg」，不是字节数。所以判 ret != 2 而不是判 ret < 0。判成字节数是常见错误，两条 msg 各 1 字节时恰好都是 2，一旦长度变了就错得莫名其妙。

它自己的三个参数：

参数 含义 从哪来
adap 从设备挂载的那条总线 client->adapter
msgs 你填好的消息数组 自己填
num 消息条数 ARRAY_SIZE(msgs)

函数做的事是把 msg 数组解析成寄存器操作序列，交给 adap->algo->master_xfer()。

一次传输的完整时序 #

3.14 的 s3c2410 控制器上，i2c_transfer() 不是自始至终占着 CPU 的：

text
i2c_transfer()
  ├─ 取 adap->bus_lock，加锁
  ├─ 发第一条 msg 的第一个字节（从地址 + 写标志）
  ├─ wait_event_timeout()  ← 进入阻塞，让出 CPU
  │
  │  …… 从设备回 ACK 或吐数据，产生中断 ……
  │
  ├─ 中断处理函数 s3c24xx_i2c_irq()
  │    ├─ 继续发剩下的字节
  │    ├─ 发完了就 s3c24xx_i2c_stop()
  │    └─ → s3c24xx_i2c_master_complete() → wake_up()
  │
  └─ 任务被唤醒，返回已完成的 msg 条数

要点有三条。第一，起始字节发出去之后主动权就交给中断了，主循环在睡眠。第二，从设备每回一个 ACK、每送一个字节都会触发中断，中断里接着往下推。第三，唤醒点在 s3c24xx_i2c_master_complete() 里，i2c_transfer() 从这里恢复执行。

所以 I2C 传输耗时基本由中断次数和总线频率决定，占用的是睡眠时间而不是 CPU 时间。

adapter 驱动里那两行 #

i2c-s3c2410.c 里必看的两处：algorithm 的挂接，和中断的申请。

c
i2c->adap.algo = &s3c24xx_i2c_algorithm;

ret = devm_request_irq(&pdev->dev, i2c->irq, s3c24xx_i2c_irq, 0,
                       dev_name(&pdev->dev), i2c);

devm_request_irq() 是带资源管理版的申请，设备 detach 时自动释放，省掉一个 remove 里的 free_irq()。写新驱动优先用 devm 系列。

七、ADC 子系统与字符设备的结合 #

ADC 在 3.x 的课上没有统一子系统可讲，走的是最朴素的一条路：一个 platform 设备加一个字符设备。这正是它值得单列的原因——它把前六章的东西全用了一遍。

硬件与寄存器 #

Exynos4412 的 ADC 基址 0x126C0000，寄存器偏移：

寄存器 偏移 作用 操作方式
ADCCON 0x0000 控制寄存器，启动转换 写 1<<16 | 1<<14 | 0xff<<6 | 1<<0
ADCDLY 0x0008 转换延时 课上未用到
ADCDAT 0x000C 转换结果 读，& 0xfff 取 12 位
CLRINTADC 0x0018 清中断 中断处理里写
ADCMUX 0x001C 通道选择 写 3 选通道 3

ADCCON 的那个写入值里每一位的含义要按 SoC 手册核对，本篇不逐个解释（未验证）。要记的是它同时干了三件事：开预分频、设分频系数、启动一次转换。

ADCDAT 读完必须 & 0xfff。高 4 位是标志位，不掩掉会读出一个远超 4095 的数，接到应用层就是「电压爆表」。

设备树节点与 resources #

text
fs4412-adc {
    compatible = "fs4412,adc";
    interrupt-parent = <&combiner>;
    reg = <0x126C0000 0x20>;
    interrupts = <10 3>;
};

interrupt-parent 指向 combiner（中断复合器）而不是 GIC 本身，因为这颗 SoC 的外设中断先汇到 combiner 再上报。interrupts = <10 3> 里第一个数是中断号，第二个是触发类型，具体编码由 interrupt-parent 那个节点的 #interrupt-cells 决定。

节点解析成 platform_device 之后，reg 变成 IORESOURCE_MEM 类型的 resource，interrupts 变成 IORESOURCE_IRQ 类型的 resource，两类分开排。

platform_get_resource 的序号规则 #

这是 ADC 这一章唯一真正容易错的点。第三个参数是「同类型资源里的第几个」，不是整个 resource 数组的下标：

c
res_mem = platform_get_resource(pdev, IORESOURCE_MEM, 0);
res_irq = platform_get_resource(pdev, IORESOURCE_IRQ, 0);

素材里画过一个把两类资源混在一个数组里的反例：

c
static struct resource adc_res[] = {
    [0] = { .start = ..., .end = ..., .flags = IORESOURCE_IRQ  },
    [1] = { .start = 0x126C0000, .end = 0x126C0000 + 0x20, .flags = IORESOURCE_MEM },
    [2] = { .start = ..., .end = ..., .flags = IORESOURCE_MEM },
    [3] = { .start = ..., .end = ..., .flags = IORESOURCE_MEM },
};

数组里 IRQ 排第 0 位、MEM 排第 1 位，但取的时候照样是 platform_get_resource(pdev, IORESOURCE_MEM, 0) —— 取的是「MEM 类型的第 0 个」，也就是数组下标 1 那一项。

一句话记住：只关心同种资源的相对顺序，不同种之间的相对位置不用管。 这条规则由 platform_get_resource() 内部按 flags 过滤实现，你自己排数组时怎么插都行。想省掉这一步就用封装接口：platform_get_irq(pdev, 0) 只找 IRQ，devm_platform_ioremap_resource(pdev, 0) 只找 MEM 并顺手 ioremap（后者 5.x 才有，3.14 上手写两步）。

顺带说清 resource 的边界：start 是起始地址，end 是最后一个可用地址，不是长度；只有一个寄存器时 start 与 end 填同一个值。

从 probe 到 read 的完整链路 #

ADC 驱动把两件事缝在一起：platform 拿到基址，字符设备提供用户接口。

text
module_init
  └─ platform_driver_register(&adc_drv)
       └─ adc_probe(pdev)
            ├─ platform_get_resource(pdev, IORESOURCE_MEM, 0)   取物理地址
            ├─ ioremap()                                         映射成虚拟地址
            ├─ platform_get_resource(pdev, IORESOURCE_IRQ, 0)    取中断号
            ├─ request_irq(irq, adc_handler, ...)                注册中断
            ├─ register_chrdev_region() / alloc_chrdev_region()  申请设备号
            ├─ cdev_init() + cdev_add()                          挂 file_operations
            ├─ class_create() + device_create()                  出 /dev/adc
            └─ init_waitqueue_head(&wq)                          初始化等待队列

用户态 read() 进来之后：

c
static ssize_t adc_read(struct file *filep, char __user *buf,
                        size_t len, loff_t *pos)
{
    writel(0x3, adc_base + ADCMUX);                        /* 选通道 3 */
    writel(1<<0 | 1<<14 | 0xff<<6 | 1<<16, adc_base + ADCCON);  /* 启动转换 */

    wait_event_interruptible(wq, have_data == 1);          /* 睡到中断来 */

    adc = readl(adc_base + ADCDAT) & 0xfff;                /* 取 12 位结果 */

    if (copy_to_user(buf, &adc, sizeof(int)))
        return -EFAULT;

    have_data = 0;
    return sizeof(int);
}

中断侧只做三件事：

c
static irqreturn_t adc_handler(int irqno, void *dev)
{
    have_data = 1;
    writel(0x12, adc_base + CLRINTADC);   /* 清中断，不清就一直进 */
    wake_up_interruptible(&wq);
    return IRQ_HANDLED;
}

这个结构就是「启动硬件 → 睡眠 → 中断唤醒 → 读结果 → 拷给用户」的标准模板。温湿度传感器、按键、触摸屏，形状都一样。

与 cdev 的结合点 #

四个位置对上：

platform 侧 字符设备侧 结合在哪
probe(pdev) 无 probe 里完成全部注册
resource 里的 MEM ioremap 的返回值 adc_base 全局变量
resource 里的 IRQ request_irq 中断处理函数
remove(pdev) cdev_del / unregister_chrdev_region 逆序释放

顺序在 remove() 里必须反过来：先 device_destroy + class_destroy，再 cdev_del，再 unregister_chrdev_region，再 free_irq，最后 iounmap。反过来释放会在 /dev 下留一个悬空节点，应用层一 open 就崩溃。另一个隐患是 have_data 这个全局标志位：多个进程同时 open 同一个 /dev/adc 会抢同一个标志和同一份 adc 数据。要正经做，得把它挪进 per-open 的私有结构体里，open() 时分配、release() 时释放，再配一个 mutex 保护硬件访问。课上没做，实战必须做。

八、几种子系统的框架对照 #

把前面几章的骨架并排摊开，横向对照一遍。这张表是整篇的收敛点：

维度 platform I2C ADC（字符设备路线）
总线类型 platform_bus_type i2c_bus_type 无自己的 bus，借用 platform
设备侧结构体 platform_device i2c_client platform_device
驱动侧结构体 platform_driver i2c_driver platform_driver
设备谁创建 BSP 代码或设备树 adapter 注册时由 of 代码生成 设备树
匹配依据 OF → ACPI → id_table → name OF → id_table 同 platform
probe 入参 struct platform_device * struct i2c_client * 加 i2c_device_id * struct platform_device *
资源从哪取 platform_get_resource() 不用取，client 里已有 addr 与 irq platform_get_resource()
寄存器访问 ioremap 加 readl/writel 不直接碰，走 i2c_transfer() ioremap 加 readl/writel

传输模型 无传输概念 消息队列加中断推进 启动转换加中断唤醒
谁的活最重 设备树与匹配规则 三个结构体的三角关系 资源类型索引

三条规律从表里直接读出来：

  1. 总线决定匹配规则。platform 和 ADC 共用同一套四级判定，I2C 只看 OF 与 id_table。
  2. probe 的入参决定了你能拿到什么。拿到 platform_device 就能取 resource；拿到 i2c_client 就只有地址和 irq，数据必须发消息去要。
  3. 用户接口与总线无关。不管前面挂哪条总线，要让应用层 open 就得自己上 cdev。platform 和 I2C 都不提供字符设备，ADC 这一章自己补上了这一段。

再加一条 SPI 做对照：SPI 的结构是 spi_bus_type + spi_device + spi_driver，匹配靠 modalias，传输靠 spi_message 与 spi_transfer 两层结构。形状跟 I2C 一样，只是消息结构多套了一层。
