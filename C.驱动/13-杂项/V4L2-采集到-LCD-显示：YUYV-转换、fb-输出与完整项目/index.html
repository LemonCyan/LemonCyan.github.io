摄像头采回来的第一帧数据，直接往屏幕上扔是花的。原因很简单：几乎所有的 UVC 摄像头默认输出 YUYV（YUV 4:2:2 打包格式），而绝大多数的 LCD framebuffer 只认 RGB565（或 RGB32）。中间必须做一次格式转换。

这篇从「为什么两种格式不能直接对接」讲到「一帧图像真的出现在屏幕上」，最后给一个能编译运行的完整项目。

一、为什么要转换 #

两个数字先摆出来。320×240 的 YUYV 一帧是：

text
320 × 240 × 2 = 153 600 字节

同样的画面，RGB565 一帧也是 153 600 字节。大小一样，但排布完全不同：

YUYV 4:2:2 RGB565
每个像素占 平均 2 字节 固定 2 字节
分量组织 4 字节描述 2 个像素，共享 U/V 每 2 字节独立描述 1 个像素
通道 Y（亮度）+ U/V（色度） R / G / B
谁在用 摄像头、视频编码 LCD framebuffer、多数 GUI

不能直接拷过去的原因：YUYV 的字节流里没有「红色」「绿色」「蓝色」，只有亮度和色差。LCD 控制器收到 0x56 0x59 会当成一个像素的 RGB565 值（R=10, G=45, B=25），得到的是灰紫色噪点，跟原图毫无关系。

所以转换是必须的一步。而且这一步是纯 CPU 运算，嵌入式上开销不小。320×240 一帧 76 800 个像素，每个像素十几次乘加，在 400MHz 的 ARM9 上要几毫秒。这也是为什么很多方案宁可用硬件 IP（如 SoC 的 CSC 模块）或让摄像头直接输出 RGB。

二、YUV 采样：4:4:4 / 4:2:2 / 4:2:0 #

人眼对亮度的敏感度远高于颜色。这个生理事实是 YUV 全部设计的出发点：亮度（Y）全采样，色度（U/V）可以少采，肉眼几乎看不出差别，而数据量能省下一大半。

写成 J:a:b 的形式，含义是「J 个像素宽的参考块里，第一行有 a 个色度采样，第二行有 b 个」。

2.1 4:4:4：不压缩 #

每个像素都有独立的 Y、U、V：

text
像素：  [Y0 U0 V0] [Y1 U1 V1] [Y2 U2 V2] [Y3 U3 V3]
码流：   Y0 U0 V0   Y1 U1 V1   Y2 U2 V2   Y3 U3 V3

每像素 3 字节。完全无损，但也就没有压缩的意义了。用于专业后期和色彩关键场景。

2.2 4:2:2：水平方向减半 #

每两个相邻像素共享一组 U/V：

text
像素：  [Y0 U0 V0] [Y1 U1 V1] [Y2 U2 V2] [Y3 U3 V3]
              └────┬────┘          └────┬────┘
              共享U0V0               共享U2V2
码流：   Y0 U0 Y1 V0   Y2 U2 Y3 V2

还原回去：

text
[Y0 U0 V0] [Y1 U0 V0] [Y2 U2 V2] [Y3 U2 V2]

每像素平均 2 字节（省 1/3）。这就是 YUYV。 摄像头最常用的格式，因为不跨行，硬件实现简单。

2.3 4:2:0：水平垂直都减半 #

两行两列共四个像素共享一组 U/V：

text
第0行：  [Y0 U0 V0] [Y1 U0 V0] [Y2 U2 V2] [Y3 U2 V2]
第1行：  [Y4 U0 V0] [Y5 U0 V0] [Y6 U2 V2] [Y7 U2 V2]
                  └──────┬──────┘
                    共享U0V0

每像素平均 1.5 字节（省一半）。H.264 / JPEG 用的就是 4:2:0，也是 NV12、NV21、I420 这几种格式的基础。

代价是不能按行独立解码，一行数据需要两行的色度信息，这也是 4:2:0 在硬件管线里比 4:2:2 麻烦的地方。

2.4 有一处常见的说法错误 #

老资料里常写「4:2:0 是水平方向每 4 个像素取 1 个 U、1 个 V」。这个说法把 4:2:0 和已经淘汰的 4:1:1 搞混了。

准确的描述是：4:2:0 在水平方向每 2 像素取 1 个色度采样，但垂直方向也每 2 行取 1 次，所以 4 个像素（2×2）共享一组 U/V。总采样数是 4:4:4 的 1/4，但两个方向各减半，而不是一个方向减到 1/4。

三、存储格式：planar 与 packed #

采样决定「采多少」，存储决定「怎么摆」。这是两个独立维度，混起来是理解 YUV 最大的障碍。

3.1 两种排布 #

类型 含义 例子
planar（平面） 先存完所有 Y，再存完所有 U，再存完所有 V I420、YV12、YUV420P
packed（打包） 每个像素（或像素对）的 Y/U/V 交错在一起 YUYV、UYVY、YVYU
semi-planar（半平面） Y 是独立平面，UV 交错成第二个平面 NV12、NV21

3.2 具体格式对比 #

以 4×2 的小图为例，Y 分量是 Y0..Y7，色度是 U0 V0（第 0 组）和 U1 V1（第 1 组）：

text
YUYV（packed 4:2:2），每 4 字节两个像素
  Y0 U0 Y1 V0  Y2 U1 Y3 V1  Y4 U2 Y5 V2  Y6 U3 Y7 V3
  └─ 像素0,1 ─┘ └─ 像素2,3 ─┘

I420 / YU12（planar 4:2:0）：Y 平面 + U 平面 + V 平面
  Y 平面: Y0 Y1 Y2 Y3 Y4 Y5 Y6 Y7
  U 平面: U0 U1 U2 U3
  V 平面: V0 V1 V2 V3

YV12（planar 4:2:0）：同 I420，但 V 在 U 前面
  Y 平面: Y0 Y1 Y2 Y3 Y4 Y5 Y6 Y7
  V 平面: V0 V1 V2 V3
  U 平面: U0 U1 U2 U3

NV12（semi-planar 4:2:0）：Y 平面 + UV 交织平面
  Y 平面:  Y0 Y1 Y2 Y3 Y4 Y5 Y6 Y7
  UV 平面: U0 V0 U1 V1 U2 V2 U3 V3

NV21（semi-planar 4:2:0）：同 NV12，但 VU 交织
  Y 平面:  Y0 Y1 Y2 Y3 Y4 Y5 Y6 Y7
  VU 平面: V0 U0 V1 U1 V2 U2 V3 U3

记忆口诀：

  • I 开头的是 I420，Y 开头的是 YV12，两者只差 U/V 平面顺序；
  • NV12 是 UV 交织，NV21 是 VU 交织（Android Camera 默认输出 NV21）；
  • V4L2 里 V4L2_PIX_FMT_YUV420 对应 I420，V4L2_PIX_FMT_YVU420 对应 YV12。

搞错 U/V 顺序不会崩，但画面颜色会「红蓝互换」，人脸变青、天空变橙。这是 YUV 处理最常见的 bug，出现时先怀疑 U/V 顺序。

四、RGB 的几种位宽 #

LCD 侧要的是 RGB。RGB 的变体按每个像素占多少字节分：

格式 位宽 通道分配 每像素字节
RGB555 16 1 位空 + R5 + G5 + B5 2
RGB565 16 R5 + G6 + B5 2
RGB444 16 A4 + R4 + G4 + B4 2
RGB888 24 R8 + G8 + B8 3
ARGB8888 32 A8 + R8 + G8 + B8 4

RGB565 是嵌入式 LCD 的默认选择：16 位刚好对齐总线宽度，G 多给 1 位是因为人眼对绿色最敏感。代价是颜色有断层，渐变天空会出现色带。

RGB565 的位布局（小端，即内存里低字节在前）：

text
16 位值:  R R R R R  G G G G G G  B B B B B
bit:      15..11     10..5         4..0

举例：纯红 = 0xF800，纯绿 = 0x07E0，纯蓝 = 0x001F，白 = 0xFFFF

构造宏：

c
#define RGB565(r, g, b)  ( (((r) >> 3) << 11) | \
                           (((g) >> 2) << 5)  | \
                            ((b) >> 3) )

用 | 而不是 +。两者在字段不重叠时结果一样，但 | 明确表达了「拼位域」的意图，也不怕将来调整位宽时出错。

RGB888 转 RGB565：

c
/* 0xRRGGBB -> RGB565 */
#define RGB888_TO_RGB565(x)  RGB565(((x) >> 16) & 0xFF, \
                                    ((x) >> 8)  & 0xFF, \
                                     (x)        & 0xFF)

注意蓝色是 (x) & 0xFF，右移 0 位。写成 (x >> 3) & 0xFF 是错的。RGB565 宏内部已经会对 B 做 >> 3，再移一次等于丢了 3 位精度，蓝色会整体偏暗。

五、YUYV → RGB565 转换 #

原理用 BT.601 的换算公式：

text
R = Y + 1.402 × (V - 128)
G = Y - 0.344 × (U - 128) - 0.715 × (V - 128)
B = Y + 1.772 × (U - 128)

浮点太慢，改整数近似（除以 256）：

系数 256 倍 整数写法
1.402 359 V + (V*103 >> 8)（把 1.402 拆成 1 + 0.402）
0.344 88 (U*88 >> 8)
0.715 183 (V*183 >> 8)
1.772 454 U + (U*198 >> 8)（1 + 0.773）

实现：

c
static inline int clamp255(int v)
{
    return v < 0 ? 0 : (v > 255 ? 255 : v);
}

/*
 * YUYV (YUV 4:2:2 packed) -> RGB565
 * 输入 yuyv: 每 4 字节 2 像素，布局 Y0 U0 Y1 V0
 * 输入 rgb : 输出缓冲，宽 × 高 × 2 字节
 */
int yuyv_to_rgb565(const unsigned char *yuyv, unsigned short *rgb,
                   int width, int height)
{
    int x, y;

    for (y = 0; y < height; y++) {
        const unsigned char *line = yuyv + (size_t)y * width * 2;
        unsigned short *out = rgb + (size_t)y * width;
        int r, g, b;

        for (x = 0; x + 1 < width; x += 2) {
            /* 四个字节一次取完，两个像素共享 U/V */
            int Y0 = line[0];
            int U  = line[1] - 128;
            int Y1 = line[2];
            int V  = line[3] - 128;

            /* 像素 0 */
            r = Y0 + V + ((V * 103) >> 8);
            g = Y0 - ((U * 88) >> 8) - ((V * 183) >> 8);
            b = Y0 + U + ((U * 198) >> 8);
            out[x] = (unsigned short)(((clamp255(r) >> 3) << 11) |
                                      ((clamp255(g) >> 2) << 5)  |
                                       (clamp255(b) >> 3));

            /* 像素 1：Y 换成 Y1，U/V 不变 */
            r = Y1 + V + ((V * 103) >> 8);
            g = Y1 - ((U * 88) >> 8) - ((V * 183) >> 8);
            b = Y1 + U + ((U * 198) >> 8);
            out[x + 1] = (unsigned short)(((clamp255(r) >> 3) << 11) |
                                          ((clamp255(g) >> 2) << 5)  |
                                           (clamp255(b) >> 3));

            line += 4;
        }
    }
    return 0;
}

5.1 三个必须说清的点 #

一、clamp255 不能省。 YUV→RGB 的换算结果可能超出 [0,255]（高饱和区域的 R 或 B 会超过 255）。不截断直接右移，溢出位会污染相邻字段，在高光或纯色区域会出现彩色噪点。

二、U/V 是「共享」的，不是「每像素一个」。 上面代码里两个像素用同一组 U/V，这正是 4:2:2 的定义。很多实现写错就错在这里：按像素推进指针（每像素 +2 字节），结果 U/V 读到的是下一个像素的 Y。现象是画面整体偏色，并且颜色呈周期性条纹。

三、行宽用 width × 2，但真实帧可能带填充。 摄像头驱动可能让 bytesperline > width × 2（行尾补齐到 16 或 32 字节对齐）。此时必须用 v4l2_pix_format.bytesperline 推进行指针，否则每行会越错越多，画面呈斜条纹。上面函数为了通用性假设无填充，实际项目里应把 bytesperline 作为参数传进来。

5.2 性能：能优化在哪 #

一帧 320×240 要转 76 800 次，每次约 15 次整数运算，总共约 115 万次操作。在 400MHz 的 ARM920T 上这是 5～10 毫秒，25fps 时 CPU 占用 12%～25%。

能做的优化，按性价比排序：

手段 收益 代价
编译器开 -O2 2～3 倍 无
查表法（预计算 RGB565 分量） 1.5～2 倍 3 × 256 项表，占用 1.5KB
NEON / MMX SIMD 4～8 倍 需要架构支持，代码可读性差
让摄像头直接输出 RGB565 完全省掉 多数 UVC 不支持，或帧率受限
用 GPU（OpenGL ES 纹理 + 着色器） 硬件加速 需要 GPU 驱动栈，复杂度高

嵌入式上最实际的是前两条。真要跑 30fps 高分辨率，就别在 CPU 上转，查 SoC 有没有 CSC/DE 硬件模块。

六、存一帧 YUV，用 ffplay 验证 #

转换代码写对没有，最快的确诊方式是先把原始 YUV 存下来，用桌面上的 ffplay 打开看。ffplay 认识 YUYV，能正确显示；如果 ffplay 里正常而你的 LCD 上是花的，问题就在转换或 fb 那一侧。

存盘：

c
int save_yuv_image(const unsigned char *start, int length)
{
    FILE *fp = fopen("pic.yuv", "wb");    /* 必须是 "wb"，不是 "w" */

    if (!fp) {
        perror("fopen pic.yuv");
        return -1;
    }
    fwrite(start, 1, length, fp);
    fclose(fp);
    return 0;
}

那个 "wb" 很关键。文本模式在某些平台上会做换行符转换，把二进制数据写坏。Windows 上必翻车，Linux 上虽然无差别，但习惯要养成。

在采集循环里每 N 帧存一张：

c
if (count % 200 == 0)
    save_yuv_image(frame, frame_len);

6.1 装 ffplay #

ffplay 依赖 SDL2。从源码装（2016 年的做法，现在多数发行版直接 apt install ffmpeg 就行）：

bash
# 先装 SDL2
git clone https://github.com/libsdl-org/SDL.git
cd SDL
./configure && make && make install

# 再编 ffmpeg（需要 yasm）
sudo apt-get install yasm
wget http://www.ffmpeg.org/releases/ffmpeg-3.1.tar.gz
tar -zxvf ffmpeg-3.1.tar.gz
cd ffmpeg-3.1

export PKG_CONFIG_PATH=/usr/local/lib/pkgconfig:$PKG_CONFIG_PATH
./configure --enable-shared \
            --extra-cflags=-I/usr/local/include \
            --extra-ldflags=-L/usr/local/lib \
            --enable-gpl
make && make install

老资料里写的 ./configure make & make install 是错的。./configure 不带参数会把 make 和 & 当成自己的参数，实际什么都没配。三个步骤之间要用 &&。

装完让动态链接器找到 /usr/local/lib：

sudo ldconfig

# 把 /usr/local/bin 加进 PATH
echo 'export PATH=$PATH:/usr/local/bin' >> /etc/profile
source /etc/profile          # 注意是 /etc，不是 /ect

bash

6.2 播放 #

bash
ffplay -f rawvideo -video_size 320x240 -pixel_format yuyv422 pic.yuv

四个参数：

参数 作用
-f rawvideo 输入是裸数据，没有容器头
-video_size 320x240 必须和采集分辨率完全一致
-pixel_format yuyv422 必须和采集格式一致
结尾 文件路径

尺寸写错会报：

text
Invalid buffer size, packet size 1646280 < expected frame_size 3098880

两个数字的含义：第一个是文件实际大小，第二个是按 -video_size 算出来的期望大小。对不上就说明尺寸或格式参数错了。这个报错其实是个很好的自检工具。

正常运行时 ffplay 会打印：

text
Input #0, rawvideo, from 'pic.yuv':
  Duration: 00:00:00.04, start: 0.000000, bitrate: 30720 kb/s
    Stream #0:0: Video: rawvideo (YUY2 / 0x32595559), yuyv422, 320x240, 30720 kb/s

看到 yuyv422 和正确的分辨率，就证明采集这一侧完全没问题。

七、fb 设备：查询参数与映射 #

LCD 在 Linux 下是 framebuffer 设备 /dev/fb0。写它就是在屏幕上画。

用之前要问它三件事：分辨率多少、位深多少、一行多少字节。

c
#include <linux/fb.h>

struct fb_fix_screeninfo finfo;    /* 不可变参数 */
struct fb_var_screeninfo vinfo;    /* 可变参数（分辨率、位深可改） */

ioctl(fb_fd, FBIOGET_FSCREENINFO, &finfo);
ioctl(fb_fd, FBIOGET_VSCREENINFO, &vinfo);

两套参数的分工：

结构体 关键字段 用途
fb_fix_screeninfo smem_start（物理地址）、line_length（每行字节）、smem_len 算偏移、算大小
fb_var_screeninfo xres / yres（可见分辨率）、xres_virtual / yres_virtual（显存分辨率）、bits_per_pixel、red / green / blue 位域 画点、算像素格式

两个分辨率要分清：xres 是屏幕实际显示的像素，xres_virtual 是显存里一行有多少像素。双缓冲时 xres_virtual = 2 × xres，一屏显示一屏绘制。单缓冲时两者相等。

line_length 是显存里一行的真实字节数，可能大于 xres × bits_per_pixel / 8（存在行尾 padding）。算地址偏移必须用 line_length，不能用 xres × bpp。 这是 fb 编程最常见的错误来源，现象是画面斜移。

完整打开流程：

c
#include <stdio.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/mman.h>
#include <linux/fb.h>

static unsigned short *fb_addr;   /* 映射后的显存基址 */
static unsigned int   fb_width;   /* 可见宽度 */
static unsigned int   fb_height;  /* 可见高度 */
static unsigned int   fb_line;    /* 每行字节数 */

int fb_open(const char *name)
{
    struct fb_fix_screeninfo finfo;
    struct fb_var_screeninfo vinfo;
    unsigned long len;
    void *p;
    int fd;

    fd = open(name, O_RDWR);
    if (fd < 0) {
        perror(name);
        return -1;
    }

    if (ioctl(fd, FBIOGET_FSCREENINFO, &finfo) < 0) {
        perror("FBIOGET_FSCREENINFO");
        goto fail;
    }
    if (ioctl(fd, FBIOGET_VSCREENINFO, &vinfo) < 0) {
        perror("FBIOGET_VSCREENINFO");
        goto fail;
    }

    fb_width  = vinfo.xres;
    fb_height = vinfo.yres;
    fb_line   = finfo.line_length;

    printf("fb: %ux%u, %u bpp, line_length=%u, smem_len=%u\n",
           fb_width, fb_height, vinfo.bits_per_pixel,
           finfo.line_length, finfo.smem_len);

    /* 显存总大小：用 smem_len，不要自己拿 w*h*bpp/8 算，
       虚拟分辨率大于可见分辨率时会算小 */
    len = finfo.smem_len;
    p = mmap(NULL, len, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (p == MAP_FAILED) {          /* 不是 NULL */
        perror("mmap fb");
        goto fail;
    }
    fb_addr = p;

    return fd;

fail:
    close(fd);
    return -1;
}

fb_width / fb_height / fb_line / fb_addr 用全局静态变量，是因为画点函数要被高频调用，传一串参数既慢又难读。这个写法在多屏场景下要改成上下文结构体。

7.1 画一个像素 #

c
void fb_put_pixel(unsigned int x, unsigned int y, unsigned short color)
{
    /* 偏移按「行」算，用 fb_line 而不是 fb_width * 2 */
    ((unsigned short *)((char *)fb_addr + y * fb_line))[x] = color;
}

等价但更常见的写法（要求 fb_line == fb_width × 2，无 padding 时才成立）：

c
fb_addr[y * fb_width + x] = color;

第二种写法在带 padding 的 fb 上是错的。 先确认 fb_line == fb_width * 2，不等就必须用第一种。

八、把一帧画到 LCD #

8.1 先看一个尺寸巧合 #

例子里有个很幸运的条件：

宽 高
摄像头采集 320 240
LCD 屏幕（竖屏） 240 320

摄像头是横向 4:3，LCD 是竖向 3:4。两者正好是转 90° 的关系，而且转完之后尺寸刚好嵌满，一个像素都不浪费。

所以显示的时候不是缩小或裁剪，而是旋转 90°：把采集图的第 y 行第 x 列，画到屏幕的第 x 行第 y 列。

text
采集图 (320宽 × 240高)          屏幕 (240宽 × 320高)
  (0,0) ──────────► (319,0)       (0,0)
   │                              │            ▲
   │                              │  旋转 90° │
   ▼                              ▼            │
  (0,239)                (0,319)  └────────────┘

8.2 实现 #

c
/*
 * 把 rgb565 缓冲显示到 LCD，同时做 90° 旋转
 * src_w/src_h 是源图（采集图）的宽高
 */
void fb_show_img(const unsigned short *rgb, unsigned int src_w,
                 unsigned int src_h)
{
    unsigned int x, y;
    unsigned int max_x, max_y;

    /* 旋转后，源图的宽对应屏幕的高，源图的高对应屏幕的宽 */
    max_x = src_w < fb_height ? src_w : fb_height;
    max_y = src_h < fb_width  ? src_h : fb_width;

    for (y = 0; y < max_y; y++) {
        const unsigned short *src_line = rgb + y * src_w;

        for (x = 0; x < max_x; x++) {
            /* 关键：坐标互换 (x,y) -> (y,x) */
            fb_put_pixel(y, x, src_line[x]);
        }
    }
}

坐标互换那行是全部要点。fb_put_pixel(y, x, ...) 里第一个参数是屏幕的 X（来自源图的 y），第二个是屏幕的 Y（来自源图的 x）。

用 min() 裁剪是为了防止源图比屏幕大时越界写显存。越界写在 fb 上不会立刻崩，它只是往显存的邻居区域写数据，结果可能是花屏、可能是闪一下、也可能是把别的图层覆盖掉。

8.3 翻转方向 #

旋转有四个方向，改坐标映射就行：

需求 写法
顺时针 90° fb_put_pixel(y, x, c)
逆时针 90° fb_put_pixel(fb_width - 1 - y, fb_height - 1 - x, c)
180° fb_put_pixel(src_w - 1 - x, src_h - 1 - y, c)
不旋转（裁剪） fb_put_pixel(x, y, c)

摄像头装反了（很多模块的排线朝下就算倒装）就是靠这个改的，不用拆机器。

8.4 直接内存拷贝会更快 #

上面是逐点写，76 800 次函数调用加偏移计算。如果能不旋转，一次 memcpy 整帧更快：

c
/* 无旋转、且 fb_line == src_w * 2 时，整帧一次拷贝 */
memcpy(fb_addr, rgb, src_w * src_h * 2);

要旋转就没这个便宜可占了，只能逐点或逐行搬。逐行版本：

c
/* 旋转 90° 的逐行优化：源图一行 -> 屏幕一列，仍需逐点，但省掉重复的行基址计算 */
for (y = 0; y < max_y; y++) {
    const unsigned short *src_line = rgb + y * src_w;
    unsigned short *dst = (unsigned short *)((char *)fb_addr + y * 2);
    for (x = 0; x < max_x; x++)
        dst[x * fb_width] = src_line[x];   /* 屏幕上一列 = 步长 fb_width */
}

九、完整项目 #

9.1 文件构成 #

text
usb_camera/
├── Makefile
├── video2lcd.c             主程序：采集 + 转换 + 显示
└── libv4l2/
    ├── libv4l2.c            V4L2 ioctl 封装（对每个命令的薄封装）
    ├── libv4l2.h
    ├── color.c              YUYV -> RGB565
    ├── color.h
    ├── fb.c                 framebuffer 打开/映射/画点
    └── fb.h

这个分层值得说一句：把 V4L2 的十几个 ioctl 各包一个函数，主程序里就只剩业务逻辑（采集→转换→显示），读起来清爽。代价是多了一层函数调用，但相对于 ioctl 本身的系统调用开销，这层几乎可以忽略。

libv4l2.c 里那二十来个函数（v4l2_open / v4l2_querycap / v4l2_s_fmt / v4l2_reqbufs / v4l2_dqbuf / v4l2_qbuf 等）就是前一篇文章里各个 ioctl 的薄封装，每个只有 10～20 行，内容不再重复。

9.2 主程序 #

c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <sys/mman.h>
#include <linux/videodev2.h>

#include "libv4l2/libv4l2.h"
#include "libv4l2/color.h"
#include "libv4l2/fb.h"

#define FB_NAME   "/dev/fb0"
#define NR_BUFS   4

int main(int argc, char **argv)
{
    int fd_video = -1;
    int fd_fb = -1;
    int ret = -1;
    int width = 320, height = 240;
    int count = 0;

    struct v4l2_capability cap;
    struct v4l2_buf *v4l2_buf = NULL;
    struct v4l2_buf_unit *unit = NULL;
    unsigned char *rgb565 = NULL;
    unsigned int caps;

    if (argc != 2) {
        fprintf(stderr, "usage: %s </dev/videox>\n", argv[0]);
        return -1;
    }

    /* 打开 LCD */
    fd_fb = fb_open(FB_NAME);
    if (fd_fb < 0)
        goto err;

    /* 打开摄像头 */
    fd_video = v4l2_open(argv[1], O_RDWR);
    if (fd_video < 0)
        goto err;

    /* 查能力，注意用 device_caps */
    memset(&cap, 0, sizeof(cap));
    if (v4l2_querycap(fd_video, &cap) < 0)
        goto err;

    caps = (cap.capabilities & V4L2_CAP_DEVICE_CAPS)
           ? cap.device_caps : cap.capabilities;
    printf("driver=%s card=%s bus=%s\n", cap.driver, cap.card, cap.bus_info);

    if (!(caps & V4L2_CAP_VIDEO_CAPTURE) || !(caps & V4L2_CAP_STREAMING)) {
        fprintf(stderr, "not a streaming capture device\n");
        goto err;
    }

    /* 枚举输入并选 0 */
    if (v4l2_enuminput(fd_video, 0) < 0)
        goto err;
    if (v4l2_s_input(fd_video, 0) < 0)
        goto err;

    /* 确认支持 YUYV，然后设置 */
    if (v4l2_enum_fmt(fd_video, V4L2_PIX_FMT_YUYV,
                      V4L2_BUF_TYPE_VIDEO_CAPTURE) < 0)
        goto err;
    if (v4l2_s_fmt(fd_video, &width, &height, V4L2_PIX_FMT_YUYV,
                   V4L2_BUF_TYPE_VIDEO_CAPTURE) < 0)
        goto err;
    printf("capture: %dx%d YUYV\n", width, height);

    /* RGB565 缓冲：每像素 2 字节 */
    rgb565 = malloc((size_t)width * height * 2);
    if (!rgb565) {
        fprintf(stderr, "out of memory\n");
        goto err;
    }

    /* 申请缓冲并映射 */
    v4l2_buf = v4l2_reqbufs(fd_video, V4L2_BUF_TYPE_VIDEO_CAPTURE, NR_BUFS);
    if (!v4l2_buf)
        goto err;
    if (v4l2_querybuf(fd_video, v4l2_buf) < 0)
        goto err;
    if (v4l2_mmap(fd_video, v4l2_buf) < 0)
        goto err;

    /* 全部入队并启动 */
    if (v4l2_qbuf_all(fd_video, v4l2_buf) < 0)
        goto err;
    if (v4l2_streamon(fd_video) < 0)
        goto err;

    /* 采集循环 */
    while (1) {
        if (v4l2_poll(fd_video) < 0)
            break;

        unit = v4l2_dqbuf(fd_video, v4l2_buf);
        if (!unit)
            break;

        /* 每 200 帧存一张原始 YUV，方便回去用 ffplay 核对 */
        if (count % 200 == 0)
            save_yuv_image(unit->start, unit->length);
        count++;

        /* 转换并显示 */
        yuyv_to_rgb565(unit->start, (unsigned short *)rgb565, width, height);
        fb_show_img((unsigned short *)rgb565, width, height);

        /* 这一行漏了，采集会在 NR_BUFS 帧之后停住 */
        if (v4l2_qbuf(fd_video, unit) < 0)
            break;
    }

    ret = 0;

err:
    if (fd_video >= 0) {
        enum v4l2_buf_type t = V4L2_BUF_TYPE_VIDEO_CAPTURE;
        ioctl(fd_video, VIDIOC_STREAMOFF, &t);   /* 先停采集 */
    }
    if (v4l2_buf) {
        v4l2_munmap(fd_video, v4l2_buf);         /* 再解映射 */
        v4l2_relbufs(v4l2_buf);
    }
    if (fd_video >= 0)
        v4l2_close(fd_video);
    if (fd_fb >= 0)
        fb_close(fd_fb);
    free(rgb565);
    return ret;
}

清理顺序是有讲究的：先 STREAMOFF，再 munmap，最后 close。顺序反了，内核可能正在往已经解映射的地址 DMA，轻则花屏，重则访问非法页崩溃。

十、运行与排错 #

10.1 正常运行的样子 #

text
[root@zy:/]# ./video2lcd /dev/video0
fb: 240x320, 16 bpp, line_length=480, smem_len=153600
driver=uvcvideo card=USB 2.0 Camera: USB Camera bus=usb-s3c24xx-1
input 0: Camera 1, std: 0x00000000
pixelformat = YUYV, description = YUYV 4:2:2
capture: 320x240 YUYV

逐行解读：

输出 说明
fb: 240x320, 16 bpp, line_length=480 LCD 竖屏 240×320，16 位色。line_length=480 = 240×2，说明没有行填充，可以用 fb_addr[y*240+x] 简化写法
driver=uvcvideo 标准 UVC 驱动，说明摄像头是免驱的
bus=usb-s3c24xx-1 挂在三星 SoC 的 USB host 上，-1 表示第 1 个端口
input 0: Camera 1 只有一路输入，名字是 Camera 1
pixelformat = YUYV 确认支持目标格式，转换代码按 YUYV 写没问题
capture: 320x240 S_FMT 回读的实际值，与请求一致

line_length=480 这一行值得单独高兴一下：它等于 240 × 2，意味着没有行 padding，画点可以用最简形式。如果打印出来是 512 或 496，说明有对齐填充，必须改用 fb_line 计算偏移。

10.2 排错表 #

现象 原因 定位
LCD 上全是彩色噪点 把 YUYV 当 RGB565 直接写了 确认调用了 yuyv_to_rgb565
画面是灰的但轮廓可辨 只取到了 Y 分量，U/V 没参与 检查转换函数的 U/V 索引
颜色反了（人脸发青、天空发橙） U/V 顺序反了 交换 U 和 V 的读取位置
画面斜向撕裂 行宽用了 width×2 而实际有 padding 改用 bytesperline
画面呈周期性条纹 转换时按像素推进指针，U/V 错位 U/V 应每 2 像素取一次
采几帧后卡住 DQBUF 后忘了 QBUF 循环里补上
上下或左右颠倒 摄像头倒装 改 8.3 节坐标映射
只显示左上角一块 旋转后尺寸算错，或屏幕分辨率读错 打印 fb_width/fb_height
花屏一闪一闪 munmap 在 STREAMOFF 之前 调换清理顺序
帧率很低、CPU 100% 转换没开 -O2，或在 ARM9 上跑高分辨率 开优化或降分辨率
偶发段错误 mmap 用 !ptr 判断，MAP_FAILED 没接住 判 == MAP_FAILED

最后一条是本篇最实用的排查策略：凡是「画面不对」，先存一帧 YUV 用 ffplay 看。ffplay 显示正常说明采集和格式都对了，问题一定在转换或 fb；ffplay 也花说明采集侧就错了，去看格式协商。

10.3 一个已知的性能限制 #

例子用的是 Mini2440（S3C2440），USB 只支持 1.1，12Mbps 理论上限 1.5MB/s。而 320×240 YUYV@25fps 需要：

text
320 × 240 × 2 × 25 = 3.84 MB/s

远超 USB 1.1 的带宽，所以实际帧率会被压到 7～8fps，画面明显卡顿。这不是代码问题，是硬件上限。

要提升，只有三条路：

  • 换 MJPEG 格式（压缩比 5～10 倍，带宽够了，但要加解码）；
  • 降分辨率到 160×120；
  • 换支持 USB 2.0 的板子（480Mbps，完全够）。

这也解释了为什么同期的开发板教程都停在 320×240：不是不想上高分辨率，是 USB 1.1 搬不动。
