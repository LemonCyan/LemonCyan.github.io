一、内核工程目录怎么搭 #

搭建内核工程有两条路。一条是纯命令行：把内核源码树解压到某处，模块源码另放一个目录，编译时用 -C 指过去。另一条是 IDE 路线：把整棵源码树导进工程，靠索引跳转读代码。两条路共用同一份源码，不冲突。

1.1 源码树先落地 #

课堂发的是 linux-3.14-fs4412.tar。落地顺序是：先在 Windows 上解压到某个盘的根目录（避免路径过长和中文目录名），再传进虚拟机。虚拟机里放在用户主目录下，比如 /home/peng/linux-3.14-fs4412，这个路径后面要写进 Makefile 的 KDIR。

源码树里真正要认识的目录不多：

text
linux-3.14-fs4412/
├── arch/arm/          体系结构相关，mach-exynos/ 是芯片初始化，boot/ 出 zImage
├── drivers/           各子系统驱动，字符设备多在 char/
├── include/linux/     module.h、init.h、fs.h、device.h 都在这里
├── scripts/           编译脚本，Makefile 靠它生成 .mod.c
├── Makefile           顶层 Makefile，KERNELRELEASE 在这里定义
└── .config            当前配置，缺了会先问你要 defconfig

外部模块编译只依赖两样东西：include/ 下的头文件，和 scripts/ 下的工具脚本。源码树不用整个编译过也能编模块——但前提是 .config 和 include/generated/ 里的自动生成头文件已经存在，这来自跑过一次 make modules_prepare。

1.2 IDE 工程的建法 #

课堂用的是 Source Insight 一类带全局索引的工具。步骤记下来是这样：

  1. 新建工程，工程文件放源码树外面，别污染源码目录；
  2. 源码目录选内核根目录，让它把顶层文件收进来；
  3. 再把 arch/arm 下的文件全部加入工程——只加这一个子目录，不要整棵树，否则索引建到一半就卡住；
  4. 确认后关闭对话框，触发一次「同步」（Rebuild Project），等索引跑完。

同步这一步不能跳过。不做同步，跳转和全局搜索都只能命中已打开的文件。

1.3 板子上的模块目录 #

板子端有一个容易忽略的前提：/lib/modules/ 下必须有以内核版本命名的目录。素材里记的现象是开发板上 rmmod 失败，处理办法是建出这个目录并给足权限：

bash
mkdir -p /rootfs/lib/modules/3.14.0

3.14.0 要和 uname -r 的输出严格一致。insmod 只吃一个 .ko 文件，不需要这个目录；但 modprobe、rmmod（部分发行版会查依赖）、depmod 都要靠它。目录缺失时 rmmod 报的错误信息各版本不一致，这条按 3.14 记录，未验证其他版本。

1.4 两种编译方式的分界 #

方式 适用场景 产物位置
内部编译 驱动代码已经在源码树里 跟随内核编译一起进 zImage 或 .ko
外部编译 驱动源码独立于源码树 源码所在目录，make -C 借树编译

课堂练的都是外部编译。内部编译要改 drivers/char/Makefile 和 Kconfig，走一遍全量编译，改一次等十几分钟，不适合调试。

二、Makefile 的写法 #

外部模块的 Makefile 有一个固定骨架，所有内容都围绕它长。

2.1 完整骨架 #

makefile
ifneq ($(KERNELRELEASE),)
$(info "1st")
obj-m := hello.o
else
KDIR := /lib/modules/$(shell uname -r)/build/
#KDIR := /home/peng/linux-3.14-fs4412
PWD  := $(shell pwd)
all:
	make -C $(KDIR) M=$(PWD) modules
clean:
	rm -f *.o *.ko *.mod.c *.order Module.symvers
endif

注意 all: 和 clean: 下面的命令行必须以 Tab 开头，不能用空格。素材原件里这几行是空格缩进，直接抄会报 *** missing separator. Stop.，这是抄这份骨架时第一号坑。

两行 KDIR 是二选一。走本机内核时用 /lib/modules/$(shell uname -r)/build/，那是个符号链接，指向当前运行内核对应的源码或头文件目录，uname -r 替换成实际版本号。交叉编译时这个链接指向的是主机内核，必须换成目标板源码树的绝对路径，也就是注释掉的那一行 /home/peng/linux-3.14-fs4412。

$(info "1st") 不是必需项，作用是编译时打印一句话，用来观察这段分支被执行了几次。

2.2 为什么会有 ifneq #

KERNELRELEASE 是内核顶层 Makefile 定义的变量。第一次敲 make，它没有值，条件不成立，走 else 分支，只做一件事：记录内核目录和当前目录，然后执行 all。

all 里的 make -C $(KDIR) M=$(PWD) modules 有三个关键参数：

参数 作用
-C $(KDIR) 先切到内核源码树目录，再执行那里的 Makefile
M=$(PWD) 告诉内核源码树，外部模块在哪个目录
modules 目标是编译模块，不是编 zImage

进到内核源码树之后，顶层 Makefile 会定义 KERNELRELEASE，然后回头再次读取我们的这份 Makefile。这一次条件成立，走 ifneq 分支，只留下 obj-m := hello.o。内核的编译框架靠这一行知道要生成什么。

整个过程里 Makefile 被读了三遍：

  1. 第一遍，KERNELRELEASE 为空，进 else，确定 KDIR 和 PWD；
  2. 第二遍，由内核源码树触发，KERNELRELEASE 有值，读出 obj-m，把 hello.c 编成 hello.o；
  3. 第三遍，回到源码目录，把 hello.o 加上 .mod.c、Module.symvers 等材料链接成 hello.ko。

理解这三遍，才能在报错时判断错在哪一步：缺头文件错在第一遍之后，Unknown symbol 错在第三遍，missing separator 错在第一遍之前。

2.3 多个 .c 合成一个 .ko #

模块名和源文件名不一致时，要用「模块名-y」把对象文件挂上去：

makefile
ifneq ($(KERNELRELEASE),)
obj-m := helloshow.o
helloshow-y += hello.o
helloshow-y += show.o
else
KDIR := /lib/modules/$(shell uname -r)/build/
PWD  := $(shell pwd)
all:
	make -C $(KDIR) M=$(PWD) modules
clean:
	rm -f *.o *.ko *.mod.c *.order Module.symvers
endif

产物只有一个 helloshow.ko。helloshow-y 是较新的写法，老一些的代码写 helloshow-objs，两者语义相同。每条 += 也可以写成一行，把两个 .o 并列。

2.4 多个 .c 各生成一个 .ko #

不合并的话，obj-m 里直接列多个目标文件，一次 make 出多个 .ko：

makefile
obj-m := hello.o show.o

show.c 里被 hello.c 调用的函数必须用 EXPORT_SYMBOL 导出，否则加载时解析不到符号。

clean 目标里的四类中间文件不能漏：.mod.c 是内核框架生成的内核态包装代码，.order 记录符号依赖顺序，Module.symvers 记录导出的符号与 CRC。少删一个，下次编译会沿用旧记录，改过函数签名后照样链接通过，运行时才出问题。

三、编译与加载的完整流程 #

从零到看见 printk 输出，动作序列是固定的。按顺序走，出问题时能定位到具体一步。

3.1 编译 #

bash
cd ~/driver/hello
make

成功时目录里出现 hello.ko，还有 hello.o、hello.mod.c、hello.mod.o、Module.symvers、modules.order。没有 .ko 就是某一步失败，往上翻日志找第一处 error，不要看最后一行。

make 前先确认 KDIR 路径存在。指向不存在的目录时报的是 make: *** /lib/modules/xxx/build/: No such file or directory，很容易误判成源码写错。

内核模块编译时和特定内核版本绑定。源码树版本、头文件版本、运行内核版本三者不一致，编出来的 .ko 加载会被拒。这是 .ko 与普通可执行文件的根本区别，也是为什么交叉编译必须显式指定 KDIR。

3.2 传到板子 #

bash
scp hello.ko root@192.168.1.100:/root/

也能用 NFS 挂载、U 盘或 tftp 传。.ko 是二进制文件，传输时别用文本模式。

3.3 加载 #

bash
insmod hello.ko

insmod 把模块的代码段和数据段搬进内核空间的某块内存，再调用入口函数。它需要 root 权限，普通用户执行报 Operation not permitted。带参数加载时参数直接跟在后面：

bash
insmod hello.ko myint=10
insmod hello.ko howmany=15 whom="aaaaaa"
insmod hello.ko myint=10 mystring="farsight" myarr=2,12,34

数组参数用逗号分隔，中间不能有空格。字符串参数不加引号也能过，参数里有空格时必须加。

3.4 看输出 #

printk 的输出进内核环形缓冲区，不进终端，dmesg 是唯一入口。缓冲区有上限，刷得太快会覆盖前面的内容，调试前先清空：

bash
dmesg -C
dmesg

-C 是清空，-c 是先打印再清空。两者只差大小写，结果完全不同：用 -c 会顺手把内容丢掉，第二次执行看不到东西。

3.5 查状态与卸载 #

bash
lsmod | grep hello
rmmod hello

lsmod 输出三列：模块名、占用内存大小、被引用计数。第三列非零说明还有别的模块依赖它，此时 rmmod 会失败。卸载写模块名，不带 .ko 后缀。

3.6 双模块的编译与加载顺序 #

模块 A 要调用模块 B 的函数时，顺序不能乱。编译阶段：

  1. 先编 B，产物里有 Module.symvers；
  2. 把 B 的 Module.symvers 拷到 A 的源码目录；
  3. 再编 A。

少了第二步，A 编译能过（只是警告），加载时报 Unknown symbol。Module.symvers 记录的是符号名与 CRC 校验值，A 靠它确认调用的是同一份 B。

加载阶段：先 insmod b.ko，再 insmod a.ko。卸载是反序：先 rmmod a，再 rmmod b。顺序颠倒时 rmmod b 会因引用计数非零而失败。这条链在《内核模块：传参与符号导出》里有完整展开。

3.7 一个辅助观察手段 #

课堂还记了一个和驱动无关但很好用的手法：用 strace ./a.out 看应用程序到底调了哪些系统调用。一个 printf 背后是 write，一次 open 失败能在 strace 里直接看到返回 -1 和 ENOENT。写驱动时对上层的调用路径没把握，先用 strace 把用户态这一半摸清。

四、常用命令速查 #

按使用频率排。全部在板子或虚拟机上以 root 执行。

命令 作用 备注
insmod hello.ko 装载模块 需要 root；参数直接跟在后面
rmmod hello 卸载模块 写模块名，不带 .ko
lsmod 列出已加载模块 三列：名字、大小、引用计数
lsmod | grep hello 过滤某个模块 确认是否加载成功最快的方式
modinfo hello.ko 查看模块信息 显示 license、author、description、vermagic、参数
dmesg 查看内核打印 printk 的唯一出口
dmesg -C 清空缓冲区 调试前先清，避免旧日志干扰
dmesg -c 打印后清空 内容会被丢掉
cat /proc/devices 查看已分配的设备号 分 Character devices 和 Block devices 两段
mknod /dev/hello c 250 0 手动创建设备节点 c 字符设备，b 块设备
mdev -s 扫描 /sys/class 补建节点 板子上没有 udev 时用它
ls /sys/class/ 看已注册的类 class_create 成功后在这里出现
ls /sys/module/hello/parameters/ 看模块参数节点 module_param 的 perm 非 0 才有
uname -r 当前内核版本 KDIR 里的版本号由它决定
strace ./a.out 跟踪系统调用 定位应用层调用路径

几个容易记混的点：

lsmod 和 cat /proc/modules 是同一份数据，前者格式化过。modinfo 的对象是文件（hello.ko），lsmod 的对象是已加载的模块（hello），参数形式不同。

mknod 的三个数字分别是设备类型、主设备号、次设备号，顺序不能错，写成 sudo mknod /dev/hello c 250 0。设备号写错时，open 报 No such device or address，而不是 No such file——这个区别能帮你判断是节点没建还是设备号没注册。

mdev -s 会遍历 /sys/class，发现一个设备就在 /dev 下按同名建节点。所以自动建节点的前提是 class_create + device_create 已经成功，/sys/class/<类名>/ 下能看到东西。原理与配置见《udev 与 mdev：设备节点的自动创建》。

五、Vim 与编辑器快捷键 #

读内核源码的时间远多于写代码。源码树里一个符号在几十个文件里出现，靠手动打开文件找不现实，得靠索引和跳转。课堂用的是 Source Insight 一类带全局索引的编辑器，快捷键记在下面这张表里。

Ctrl + / 查标识符的引用点 想知道某个函数在内核里被哪些地方调用
Shift + F8 高亮当前标识符 在一个文件里快速数清某变量出现几次

5.3 查内核源码的固定套路 #

碰到不认识的函数名，路径是固定的：先在 include/linux/ 下找声明，再在 kernel/、fs/、drivers/ 下找定义。声明和定义之间的差别很重要——声明只告诉你签名，宏展开后的实际形态要去看定义。

module_init 就是典型。它在 include/linux/init.h 里是一个宏，展开结果和它字面意思差别很大，光看调用处看不出来。这类宏必须在头文件里读原始定义，见第六章。

六、模块的入口与出口 #

模块和应用程序的第一处结构差异就在入口。应用程序从 main 开始，模块没有 main，只有加载函数和卸载函数。

6.1 三要素 #

一个能被正常加载的模块，必须凑齐三样：

要素 声明方式 缺了会怎样
许可证 MODULE_LICENSE("GPL") 加载时内核被标记为污染，EXPORT_SYMBOL_GPL 导出的符号不可用
加载函数 module_init(hello_init) 无法加载，insmod 直接报错
卸载函数 module_exit(hello_exit) 无法卸载，rmmod 拒绝

许可证不是形式主义。内核在加载时读 .modinfo 段里的 license 字段，读到 GPL 才认，否则打一条 tainted 警告并永久标记这个内核。功能上不影响模块运行，但会让后续排查问题时无法区分是内核自己的 bug 还是第三方模块引入的。

6.2 两种写法 #

缺省的写法是直接用固定名字：

c
int init_module(void)
{
    /* 初始化工作 */
    return 0;
}

void cleanup_module(void)
{
    /* 与 init_module 相反的工作 */
}

init_module 和 cleanup_module 是加载器按名字查找的符号，名字对了就能用。这种写法在现代内核里不推荐——一旦同一个文件里用了 module_init，宏会生成同名的 init_module，两处冲突，编译报重复定义。

自定义写法是主流：

c
static int hello_init(void)
{
    printk("hello_init()\n");
    return 0;
}

static void hello_exit(void)
{
    printk("hello_exit()\n");
}

module_init(hello_init);
module_exit(hello_exit);

6.3 module_init 做了什么 #

它不是函数调用，是宏。在 MODULE 宏已定义（编译模块时必然如此）的前提下，include/linux/init.h 里的展开大致是：声明一个内联函数做类型检查，再用 alias 属性把 init_module 指向你写的函数。

结果就是：你写 hello_init，编译器产出的符号仍叫 init_module，加载器按这个名字找到它。module_exit 同理，映射到 cleanup_module。

这解释了为什么自定义函数必须签名匹配 int (void) 和 void (void)——类型检查在编译期做，签名不对会报 __inittest 相关的错误。展开细节按 3.x 的 init.h 记录，6.x 是否完全一致未逐版核对。

6.4 返回值决定加载成败 #

加载函数返回 0 表示成功，返回负值表示失败：

c
static int hello_init(void)
{
    int ret;

    ret = register_chrdev_region(devno, 1, "hello");
    if (ret < 0) {
        printk(KERN_ERR "register region failed: %d\n", ret);
        return ret;
    }

    return 0;
}

返回负值时，insmod 报错退出，内核自动回滚——已经 cdev_add 的会被框架清掉。但不能指望回滚，中间步骤失败的清理要自己写，从失败点往前逐个释放。

6.5 printk 与优先级 #

printk 是内核里的 printf，输出进环形缓冲区，用 dmesg 看。它的第一个参数可以是优先级宏，定义在 include/linux/kern_levels.h：

宏 数值 含义
KERN_EMERG 0 系统不可用
KERN_ALERT 1 必须立即处理
KERN_CRIT 2 严重错误
KERN_ERR 3 错误
KERN_WARNING 4 警告
KERN_NOTICE 5 正常但值得注意
KERN_INFO 6 信息
KERN_DEBUG 7 调试

用法上有个细节容易忽略：优先级宏和格式串之间不加逗号，靠字符串字面量拼接，写成 printk(KERN_EMERG "hello_exit()\n");。中间必须有空格。<linux/kern_levels.h> 定义的是 "\001" "0" 这类相邻字面量，所以 KERN_EMERG"hello" 也能过编译，风格上不推荐。

不写优先级的 printk("...") 按默认级别处理，能否显示取决于控制台的 loglevel。调试时输出不出现，先查 dmesg -n 8 之类的设置，别急着怀疑代码。

七、cdev 结构体的关键点 #

设备号申请下来之后，要把它和一套操作函数绑在一起，这个绑定关系的载体就是 struct cdev。

7.1 结构体成员 #

c
struct cdev {
    struct kobject kobj;                  /* 内嵌的 kobject，sysfs 的基类 */
    struct module *owner;                 /* 指向所属模块，一般填 THIS_MODULE */
    const struct file_operations *ops;    /* 操作函数集合，驱动的主要工作 */
    struct list_head list;                /* 内核链表节点 */
    dev_t dev;                            /* 起始设备号 */
    unsigned int count;                   /* 管理的设备个数 */
};

六个成员里，驱动开发者真正要碰的只有 owner 和 ops。ops 指向的那张表就是驱动本体，第六章之后的所有工作都落在它上面。

7.2 四个操作接口 #

函数 原型 调用位置
cdev_init void cdev_init(struct cdev *, const struct file_operations *) 加载函数中，建立 cdev 与 fops 的连接
cdev_add int cdev_add(struct cdev *, dev_t, unsigned) 加载函数中，设备号与 cdev 绑定并注册到内核
cdev_del void cdev_del(struct cdev *) 卸载函数中，注销
cdev_alloc struct cdev *cdev_alloc(void) 需要动态分配 cdev 时用，配套 kfree

cdev_init 会把 ops 指针写进结构体，同时初始化内部链表和 kobj。它不负责注册，注册靠 cdev_add。两件事分开做，顺序不能颠倒。

cdev_add 的第二个参数是起始设备号，第三个是数量。数量为 1 表示只管一个设备，这也是练习里最常见的用法。

7.3 内嵌还是动态分配 #

两种写法：

c
/* 写法一：内嵌，静态分配 */
static struct cdev mycdev;
cdev_init(&mycdev, &hello_fops);
mycdev.owner = THIS_MODULE;
cdev_add(&mycdev, devno, 1);

/* 写法二：动态分配 */
struct cdev *pcdev = cdev_alloc();
pcdev->ops = &hello_fops;
pcdev->owner = THIS_MODULE;
cdev_add(pcdev, devno, 1);

写法一简单，但 mycdev 是模块的全局变量，模块卸载后内存跟着消失，必须先 cdev_del。写法二里 cdev_alloc 已经填好 ops 之外的初始化，卸载时要 cdev_del 再 kfree。

cdev_init 之后还要单独赋一次 owner，这是很多人漏掉的一行。漏了不会立刻出错，直到引用计数出问题。

7.4 三步框架 #

字符设备驱动的注册链拆开就是三步：

text
1. 申请设备号     register_chrdev_region / alloc_chrdev_region
2. 初始化 cdev    cdev_init + cdev_add
3. 实现 fops      struct file_operations 的各个回调

三步的顺序不能换。设备号没有就 cdev_add，内核直接返回 -EINVAL。cdev_add 没有就 open 设备节点，VFS 找不到任何驱动，报 No such device or address。

7.5 register_chrdev 与两个 region 接口 #

这三个接口常被混淆，区别必须分清：

接口 申请设备号 创建并注册 cdev 适用场景
register_chrdev_region 是，静态指定起始设备号 否 设备号固定，自己控 cdev
alloc_chrdev_region 是，内核动态分配 否 主设备号不固定，避免冲突
register_chrdev 是，major 传 0 时动态分配并返回主设备号 是，内部完成 cdev_init 与 cdev_add 一个主设备号只对应一套 fops 的简单场景

register_chrdev 是三合一，用起来最省事：

c
static inline int register_chrdev(unsigned int major, const char *name,
                                  const struct file_operations *fops);

返回值语义分两种：major 传 0 时返回分配到的正主设备号，major 传非 0 时成功返回 0，失败返回负的错误码。这两种返回值混在一个 int 里，判断时要分开处理：

c
int major = 250;
int ret = register_chrdev(major, "hello", &hello_fops);
if (ret < 0) {
    printk(KERN_ERR "register_chrdev failed\n");
    return ret;
}

register_chrdev 在 2.6 时代被拆出 __register_chrdev 内部实现，3.14 与 6.x 都还保留着这个对外接口，但已被归入遗留接口。新代码推荐用 region + cdev 的两步写法，理由是可精确控制设备号范围，也能一个主设备号管多个次设备。这条归入遗留的具体时间点未验证。

7.6 设备节点：手动与自动 #

手动建节点写成 sudo mknod /dev/hello c 250 0。c 是字符设备，250 主设备号，0 次设备号。三个参数错一个，open 的报错都不一样，排查时先 ls -l /dev/hello 核对主次设备号。

自动建节点要两步。先建类：

c
my_class = class_create(THIS_MODULE, "farsight_class");
if (IS_ERR(my_class)) {
    printk(KERN_ERR "failed in creating class\n");
    return PTR_ERR(my_class);
}

再建设备：

c
device = device_create(my_class, NULL, devno, NULL, "farsight_dev");
if (IS_ERR(device)) {
    class_destroy(my_class);
    return PTR_ERR(device);
}

版本标注：素材里的 class_create 是双参数形式 class_create(owner, name)，宏定义在 include/linux/device.h，内部拼一个 lock_class_key 再调 __class_create。这个双参数形式在 6.4 内核起改为单参数 class_create(name)，owner 参数被去掉。写代码前先确认目标内核版本，照抄 3.x 的写法在 6.4 以上会报参数过多。

配套的销毁顺序是反的：先 device_destroy，再 class_destroy。反过来会留下悬空的设备指针。

素材里还出现了 class_device_create，这是更早的设备模型接口，已被 device_create 取代（退场版本未验证）。3.14 里用的是 device_create(class, parent, devt, drvdata, fmt, ...)，成功返回 struct device *。

节点自动创建成功的判据有两条：/sys/class/farsight_class/ 下有对应目录，/dev/ 下有对应节点。后者要靠 udev 或 mdev -s 配合，光是 device_create 成功不一定立刻有 /dev 节点，原因见《udev 与 mdev：设备节点的自动创建》。

八、file_operations 的实现要点 #

file_operations 是驱动交给 VFS 的函数表。用户态每一次 open、read、write、ioctl，最终都落到表里的某个函数指针上。

8.1 常用回调 #

成员 原型 实现要点
owner struct module * 固定填 THIS_MODULE，防止使用中模块被卸载
open int (*)(struct inode *, struct file *) 可省；省了则打开永远成功。返回 0 成功，负值失败
release int (*)(struct inode *, struct file *) 可省；省了则关闭永远成功。用于释放 open 里申请的资源
read ssize_t (*)(struct file *, char __user *, size_t, loff_t *) 必须用 copy_to_user 把数据送到用户空间
write ssize_t (*)(struct file *, const char __user *, size_t, loff_t *) 必须用 copy_from_user 从用户空间取数据
llseek loff_t (*)(struct file *, loff_t, int) 设备不支持定位时可省
unlocked_ioctl long (*)(struct file *, unsigned int, unsigned long) 命令与参数一起传，见 8.4
compat_ioctl long (*)(struct file *, unsigned int, unsigned long) 32 位应用跑在 64 位内核上时要实现
mmap int (*)(struct file *, struct vm_area_struct *) 把设备内存映射到用户空间
poll unsigned int (*)(struct file *, struct poll_table_struct *) 支撑 select/poll，见《并发与 IO 模型速记》
fasync int (*)(int, struct file *, int) 异步通知
flush int (*)(struct file *, fl_owner_t) 每次 close 都调，注意与 release 区分

表里的 __user 不是装饰。它是给编译器和静态检查工具看的标记，表明这个指针指向用户空间地址，不能直接解引用。漏写 __user 编译器不报错，但语义就丢了。

8.2 初始化的写法 #

只填用得到的成员，用指定初始化器：

c
static struct file_operations hello_fops = {
    .owner   = THIS_MODULE,
    .open    = hello_open,
    .release = hello_release,
    .read    = hello_read,
    .write   = hello_write,
};

素材原稿这里是 struct file_operations hello_fops{ .owner = THIS_MODULE, };，缺 = 和结尾分号，直接抄编译不过。正确形式要有 = { ... };。

没填的成员自动为 NULL。VFS 对 NULL 的处理不一致：open 为 NULL 时打开永远成功，read 为 NULL 时 read() 系统调用直接失败（3.x 返回 -EINVAL，其他版本未验证），release 为 NULL 时关闭永远成功。所以「不实现也能跑」这句话只对 open/release 成立。

8.3 回调为什么用 static #

几乎所有驱动的 fops 回调和 fops 结构体本身都写成 static。原因不是风格，是这个符号不需要导出到模块外——写成非 static 会进符号表，和其他模块重名时链接冲突。

8.4 ioctl 的命令码 #

ioctl 一次传一个命令加一个参数，命令码不是随手写的整数，要用内核提供的宏拼：

c
#define _IO(type, nr)          _IOC(_IOC_NONE, (type), (nr), 0)
#define _IOR(type, nr, size)   _IOC(_IOC_READ, (type), (nr), sizeof(size))
#define _IOW(type, nr, size)   _IOC(_IOC_WRITE, (type), (nr), sizeof(size))
#define _IOWR(type, nr, size)  _IOC(_IOC_READ | _IOC_WRITE, (type), (nr), sizeof(size))

命令码的位域分成四段：8 位幻数（type）、8 位序号（nr）、2 位读写方向、14 位数据大小。幻数用来区分不同驱动，避免命令码撞车。内核已经占用的幻数清单在 Documentation/ioctl/ioctl-number.txt 里，自己选之前先查一遍。

应用层用 ioctl(fd, 命令, 参数)，参数可以传值也可以传地址，驱动侧从 unsigned long arg 里按约定还原。完整实现与实例见《ioctl()：命令码、实现与实例》。

九、read 与 write 的数据拷贝 #

用户态调 read 和 write 是三个参数起步，驱动侧看到的却是四个，多出来的是 file 和偏移。

9.1 两侧的签名对照 #

c
/* 应用层 */
ssize_t read(int fd, void *buf, size_t count);
ssize_t write(int fd, const void *buf, size_t count);

/* 驱动侧 */
ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);

四个参数一一对应：

驱动侧参数 对应应用层 含义
struct file * fd 背后的对象 打开的文件描述，私有数据挂在 private_data 上
char __user * buf 用户空间缓冲区地址
size_t count 用户缓冲区大小，即可传的最大字节数
loff_t * 隐含的文件偏移 读或写之后要把偏移推进，否则 cat 会死循环

__user 标记在 read 里加在 char * 上，在 write 里加在 const char * 上。write 多一个 const，因为数据是从用户流向内核，源地址驱动不该改。

9.2 返回值语义 #

两个函数的返回值含义相同：

返回值 含义
大于 0 实际读/写的字节数，可以小于请求的 count
0 read 时表示读到文件尾，write 时表示没写进去
小于 0 出错，返回负的错误码，如 -EFAULT、-EINVAL、-ENOMEM

返回值的正负是硬规矩。返回正数就得是真实字节数，返回 -1 这种裸值是错的——内核要求错误码取负，用 -EFAULT 而不是 EFAULT，也不是 -1。

9.3 内核态不能直接解引用用户指针 #

用户传进来的 buf 是用户空间地址。内核态代码直接 memcpy(dst, buf, count) 访问它，在 3.x 上未必立刻崩（内核页表里用户页也映射着），在开了 CONFIG_DEBUG_ATOMIC_SLEEP 或 SMAP 的机器上直接出错。

所以内核提供了专门的拷贝函数，见第十章。

9.4 fd 与 file 的共享 #

一个容易踩的坑：fork 之后，子进程拷贝父进程的文件描述符表，父子指向同一个 struct file。文件偏移存在 file 里，所以：

c
/* 父进程 */
lseek(fd, 100, SEEK_SET);   /* 只改父进程的偏移 */

父进程读了 100 字节，子进程接着读，看到的位置也是 100 之后。父子共用同一个偏移，互相影响。

想让两边互不干扰，只能关掉重新打开，各自拿到独立的 file 对象。这一点在写阻塞 IO 驱动时会影响设计——private_data 里放的状态到底是每进程一份还是每 file 一份，得想清楚。

十、copy_to_user 与 copy_from_user #

这两个函数是用户态与内核态之间的唯一合法通道。

10.1 签名与参数 #

c
static inline unsigned long __must_check
copy_to_user(void __user *to, const void *from, unsigned long n);

static inline unsigned long __must_check
copy_from_user(void *to, const void __user *from, unsigned long n);
参数 copy_to_user copy_from_user
第一个 to：用户空间目的地址 to：内核空间目的地址
第二个 from：内核空间源地址 from：用户空间源地址
第三个 n：要拷贝的字节数 同左

方向记忆法：函数名里的 to/from 都是相对用户空间说的。copy_to_user 是往用户送,copy_from_user 是从用户取。

三个修饰词各有含义：

修饰 含义
static 静态函数，作用域限于当前编译单元，库里不导出
inline 内联，建议编译器展开，避免函数调用开销
__must_check 返回值必须被使用，不检查编译器会给警告

__must_check 这条不是摆设。写了 copy_to_user(...) 却不接返回值，编译时出 warning: ignoring return value。这个警告必须当真，它指向的是数据没拷全的 bug。

10.2 返回值是「未拷贝字节数」 #

这是最容易搞反的地方：返回值不是拷了多少，是还剩多少没拷。0 是全部拷完，大于 0 是有这么多字节没拷成功（源地址非法是主因），等于 n 是一个字节都没拷成功。

所以判断成功要写 if (ret == 0)，不能写 if (ret > 0) 然后当成成功。反过来，非 0 就是失败，返回 -EFAULT。

10.3 正确的 read 实现 #

c
static ssize_t hello_read(struct file *filp, char __user *buf,
                          size_t count, loff_t *off)
{
    unsigned long ret;

    if (count > sizeof(kbuf))
        count = sizeof(kbuf);

    ret = copy_to_user(buf, kbuf, count);
    if (ret) {
        printk(KERN_ERR "copy_to_user failed, %lu bytes left\n", ret);
        return -EFAULT;
    }

    return count;
}

10.4 正确的 write 实现 #

c
static ssize_t hello_write(struct file *filp, const char __user *buf,
                           size_t count, loff_t *off)
{
    unsigned long ret;

    if (count > sizeof(kbuf))
        count = sizeof(kbuf);

    ret = copy_from_user(kbuf, buf, count);
    if (ret) {
        printk(KERN_ERR "copy_from_user failed, %lu bytes left\n", ret);
        return -EFAULT;
    }

    return count;
}

10.5 三个细节 #

长度先截断再拷。count 由用户说了算，能塞进比内核 buffer 大得多的值。不判断就拷，缓冲区溢出，后果是内核崩溃而不是段错误。

返回实际字节数。上面两段代码返回 count（已经截断过的值），不是 sizeof(kbuf)，也不是 0。

偏移要自己推进。*off 是 loff_t *，读完之后加上实际字节数。不推进的话，应用层反复读到同一段数据，cat 一个设备文件会停不下来。

10.6 顺带说清 const 的位置 #

素材里留了一个老问题：char * const p 和 char const *p 有什么区别。答案在 * 和 const 的左右关系上：

写法 含义
char * const p 指针本身不能改，指向的内容可以改
const char *p 指向的内容不能改，指针本身可以改
const char * const p 两者都不能改

copy_from_user 的第一个参数是 void *to，因为内核这一段要被写；第二个参数是 const void __user *from，因为用户那一段只读。签名本身就是这个规则的体现。

十一、常见编译错误的排查 #

按出错阶段排。看到报错先定位属于哪一阶段，别从头读日志。

11.1 Makefile 阶段 #

报错 原因 处理
*** missing separator. Stop. 命令行用了空格缩进 改成 Tab；编辑器里开「显示不可见字符」核对
/lib/modules/xxx/build/: No such file or directory KDIR 指向的路径不存在 用 uname -r 核对版本号，交叉编译时填源码树绝对路径
Nothing to be done for 'all' 目标名写错或没有 all 分支 核对 all: 是否存在，冒号后不能有空格
No rule to make target 'modules' 进了错的目录执行 make -C KDIR 指向的目录里必须有顶层 Makefile
obj-m 写了 .ko 后缀 语法错误 obj-m := hello.o，只写 .o

missing separator 出现时，先用 cat -A Makefile 看缩进字符。Tab 显示成 ^I，空格显示成普通空白，一眼能分辨。

11.2 编译阶段 #

报错 原因 处理
unknown field 'ioctl' specified in initializer 用了老字段名 3.x 起改用 unlocked_ioctl，ioctl 早在 2.6.36 前后被移除
implicit declaration of function 'printk' 缺头文件 补 #include <linux/module.h>
implicit declaration of function 'copy_to_user' 缺头文件 补 #include <linux/uaccess.h>
assignment from incompatible pointer type 回调签名不对 常见是把 ssize_t 写成 int，或漏了 __user
initializer element is not constant fops 初始化用了变量 fops 必须是静态初始化，函数名是常量

11.3 加载阶段 #

报错 原因 处理
Unknown symbol in module 依赖的符号没导出来 依赖模块要 EXPORT_SYMBOL，且先加载
invalid module format vermagic 不匹配 编模块的内核和运行内核不是同一个，重编
disagrees about version of symbol 符号 CRC 不一致 依赖模块改了没重编，清掉 Module.symvers 全量重编
Operation not permitted 不是 root 换 root 或用 sudo
File exists 模块已加载 先 rmmod 再 insmod
Resource temporarily unavailable 设备号被占用 cat /proc/devices 查冲突，换号
module license 'unspecified' taints kernel 缺 MODULE_LICENSE 补上，这个警告会让内核永久带 taint 标记
module verification failed 内核开了签名校验 关掉 CONFIG_MODULE_SIG_FORCE 或给模块签名

invalid module format 是最常见的一条，本质是版本绑定。modinfo hello.ko 输出里的 vermagic 一行，和 uname -r 对不上就是它。交叉编译忘了改 KDIR 也会撞上这条——编出来的是主机内核的模块。

11.4 运行阶段 #

程序能加载但行为不对，看这几处：

现象 排查方向
open 报 No such file or directory /dev 下节点没建，用 mknod 或 mdev -s
open 报 No such device or address 节点存在但设备号没注册，查 cat /proc/devices
open 报 Permission denied 节点权限不对，chmod 或改 fops 里的行为
cat 设备文件停不下来 read 没推进 *off，或没在结尾返回 0
读完数据全是乱码 用了 memcpy 而不是 copy_to_user，或 count 越界
dmesg 看不到输出 缓冲区被后来的日志覆盖，或 loglevel 过滤掉了
rmmod 报 Device or resource busy 引用计数非零，还有进程持有 fd，或别的模块依赖它

rmmod 失败时先 lsof /dev/hello 看有没有进程占着，再 lsmod 看引用计数。

十二、易错点速查 #

把前面各章散落的坑集中列一遍，写完代码对着过一遍。

易错点 正确做法
Makefile 命令行用空格缩进 用 Tab，cat -A 核对
obj-m := hello.ko 写 obj-m := hello.o
交叉编译没改 KDIR 注释掉 uname -r 那行，填源码树绝对路径
module_param 权限写 600 写 0600 或 0644，600 是十进制，含义完全不同
module_param 权限写 0666 内核不允许，会拒绝加载或告警
忘记 MODULE_LICENSE MODULE_LICENSE("GPL")，否则内核被 taint
同时写 init_module 和 module_init 只用 module_init
加载函数返回 -1 返回真实负错误码，如 -ENOMEM
cdev_init 后忘赋 owner 补 mycdev.owner = THIS_MODULE
cdev_add 之前没申请设备号 先 region 再 cdev_add
卸载时只 cdev_del 不 unregister_chrdev_region 两个都要，顺序是先 del cdev 再放设备号
mknod 参数顺序写反 mknod 路径 c 主设备号 次设备号
主次设备号记反 高 12 位是主，低 20 位是次；MAJOR/MINOR 宏拆
手算 major << 20 | minor 不加括号 用 MKDEV(major, minor)
copy_to_user 返回非 0 当成功 0 才是成功，非 0 是剩余字节数
直接 memcpy 用户指针 用 copy_to_user/copy_from_user
read 不推进 *off 读完 *off += 实际字节数
read 结尾不返回 0 数据读完返回 0，告诉应用层到结尾
返回裸 -1 表示错误 返回 -EFAULT 这类负错误码
内核 6.4 以上照抄双参数 class_create 改成单参数 class_create(name)
dmesg -c 当清空用 清空用 -C，-c 是打印后清空
板子上没有 /lib/modules/$(uname -r) 建目录 3.14.0 并给权限，否则 rmmod 失败
设备号写死导致冲突 用 alloc_chrdev_region 动态分配
依赖模块的 Module.symvers 没拷 先编依赖，拷 Module.symvers，再编本模块
先卸载被依赖的模块 卸载顺序与加载顺序相反
以为 fork 后偏移各自独立 共用同一个 file，偏移互相影响，需要独立就重新 open
