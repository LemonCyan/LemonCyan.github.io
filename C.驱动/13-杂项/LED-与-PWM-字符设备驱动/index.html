本篇只做一件事：用 LED 和 PWM 蜂鸣器这两台最简陋的外设，把字符设备驱动从设备号一路走到 write 回调。

平台与内核：S3C2440（Mini2440）+ linux-5.2.8；Exynos4412（FS4412）+ linux-3.14-fs4412。两块板子的设备号申请各走一条路，本篇对照着写。

跨篇指路：同目录的《ADC 与 DS18B20 传感器驱动》《RTC 驱动》接着往下走。

一、为什么用 LED 做第一个驱动 #

第一个驱动挑 LED，不是图它简单，是它把字符设备该有的环节全占了，又把干扰项剔干净了：没有时序、没有中断、没有协议，灯亮没亮肉眼就能判。

写字符设备驱动的骨架固定为七步：看原理图和数据手册定位寄存器和引脚；在内核源码里找同类驱动当模板，找不到就从零写；注册驱动，让内核在应用打开某个文件名时能找到你的代码；实现 open、release、read、write、ioctl；需要中断的设备才写中断服务，LED 不需要；编译成模块 insmod 或编进内核；写应用验证现象。

LED 走完这七步只碰两个寄存器，注意力能全放在框架上。等 PWM 蜂鸣器上来，多出来的只是「寄存器变多、要算频率」，框架还是同一套。

二、硬件连接与原理图 #

两套板子接线完全不同，代码不能直接搬。

平台 板子 引脚 控制寄存器 数据寄存器 点亮电平
S3C2440 Mini2440 GPB5~GPB8（LED1~LED4） GPBCON 0x56000010 GPBDAT 0x56000014 低电平
Exynos4412 FS4412 GPX2_7 GPX2CON 0x11000C40 GPX2DAT 0x11000C44 高电平
Exynos4412 FS4412 GPX1_0 GPX1CON 0x11000C20 GPX1DAT 0x11000C24 高电平
Exynos4412 FS4412 GPF3_4 GPF3CON 0x114001E0 GPF3DAT 0x114001E4 高电平
Exynos4412 FS4412 GPF3_5 GPF3CON 0x114001E0 GPF3DAT 0x114001E4 高电平

S3C2440 这一路：每根引脚在 GPBCON 里占 2 位，[11:10] 对 GPB5，[13:12] 对 GPB6，[15:14] 对 GPB7，[17:16] 对 GPB8，写 0b01 是输出。GPBDAT 的 bit5~bit8 对应电平，写 0 输出低、灯亮，写 1 输出高、灯灭，所以「四盏全亮」= 把 bit5~bit8 全清 0。

Exynos4412 这一路：每根引脚在 CON 里占 4 位，写 0x1 是输出。GPX2_7 占 GPX2CON 的 [31:28]，GPX1_0 占 GPX1CON 的 [3:0]，GPF3_4 与 GPF3_5 占 GPF3CON 的 [19:16] 和 [23:20]，一次 0x11 << 16 把两根配完。数据位在 GPX2DAT 的 bit7、GPX1DAT 的 bit0、GPF3DAT 的 bit4 和 bit5，写 1 输出高、灯亮。

两块板子的点亮电平是反的。同一份点灯逻辑从 S3C2440 搬到 FS4412，现象会完全反过来，第一次移植踩的坑多半在这里。

原文此处各配有一张原理图和一张接线图，抓取过程中丢失。位号已按寄存器位定义还原到具体引脚。

三、LED 驱动的整体结构 #

字符设备模块从头到尾就是「申请资源 → 挂上操作集合 → 卸载时按相反顺序释放」。

text
module_init
   +-- alloc_chrdev_region()   拿设备号 (major, 0)
   +-- cdev_init()             把 fops 绑到 cdev 上
   +-- cdev_add()              把 cdev 挂进内核
   +-- class_create()          建 /sys/class/led
   +-- device_create()         建 /sys/class/led/led0，mdev 据此生成 /dev/led0
   +-- ioremap()               物理寄存器地址 -> 内核虚拟地址

应用 open("/dev/led0") --> 内核按设备号找到 cdev --> fops->open
应用 write(fd, &val, 4) --> fops->write --> copy_from_user --> 写寄存器

module_exit
   +-- iounmap() -> device_destroy() -> class_destroy()
   +-- cdev_del() -> unregister_chrdev_region()
对象 类型 职责 少了会怎样
设备号 dev_t 应用层靠它从 /dev 节点找到驱动 open 报错，设备不存在
cdev struct cdev 把设备号和 file_operations 绑在一起 内核知道号，不知道调谁
class struct class 在 /sys/class 下建目录，给 mdev 看 不会自动生成 /dev 节点
device struct device class 下的具体设备，携带 dev_t mdev 不知道设备号，节点建不出来

顺序不能乱。设备号没拿到就 cdev_add，等于往内核挂一个没有身份的 cdev。卸载要反着来，否则 device_destroy 里传的 dev_t 已经被释放了。

四、设备号与 cdev 的申请 #

4.1 dev_t 与主次设备号 #

dev_t 是 32 位，高 12 位主设备号，低 20 位次设备号（2.6 以后的内核如此）。主设备号对应「哪一类驱动」，次设备号对应「这一类里的第几个设备」。

c
dev_t devid;
devid = MKDEV(major, minor);   /* 主次拼成 dev_t */
major = MAJOR(devid);          /* 拆出主设备号 */
minor = MINOR(devid);          /* 拆出次设备号 */

4.2 三种申请方式，register_chrdev 与 region 的区别 #

函数 语义 占用范围 返回值
register_chrdev(major, name, fops) 设备号 + cdev 一次搞定 major 下全部 256 个次设备号 major=0 返回主设备号；major>0 成功返 0
register_chrdev_region(from, count, name) 静态指定设备号 count 个 成功 0，失败负数
alloc_chrdev_region(&dev, baseminor, count, name) 动态分配设备号 count 个 成功 0，失败负数

核心区别一条：register_chrdev 是「老接口」，把申请设备号、cdev_init、cdev_add 三件事一次做完，代价是占满那个主设备号下全部 256 个次设备号；register_chrdev_region / alloc_chrdev_region 只申请设备号，cdev 要自己建，想占几个就占几个。

返回值也容易看错：register_chrdev 在 major == 0 时返回内核给的主设备号，major > 0 时成功返回 0、失败返回负错误码。两个 region 函数统一是成功 0、失败负数。

4.3 FS4412 的走法：register_chrdev #

c
static int major = 250;
static int minor = 0;
static dev_t devno;

devno = MKDEV(major, minor);
ret = register_chrdev(major, "led", &hello_ops);

主设备号写死 250，换个环境就撞车。2.6 之后主设备号都是动态分配的，写死一个数字只在你那块板子上成立。

4.4 S3C2440 的走法：region + cdev #

拆开走，每步失败都能单独回滚：

c
/* 动态分配，只 1 个：ls /proc/devices 里看到的名字就是这里的 "led" */
ret = alloc_chrdev_region(&devid, 0, 1, "led");
if (ret < 0) {
    printk("alloc char dev region error\n");
    goto fail_devid;
}

cdev_init(&led_cdev, &led_fops);
ret = cdev_add(&led_cdev, devid, 1);
if (ret < 0) {
    printk("char device add failed\n");
    goto fail_cdev;
}

alloc_chrdev_region 第二个参数是起始次设备号，第三个是要几个。静态指定时换成 register_chrdev_region(MKDEV(250, 0), 1, "led")。

4.5 cdev 结构与三个函数 #

c
struct cdev {
    struct kobject kobj;                  /* sysfs 基类 */
    struct module *owner;                 /* this 指针 */
    const struct file_operations *ops;    /* 硬件操作函数集合，主要工作在这里 */
    struct list_head list;                /* 内核链表 */
    dev_t dev;                            /* 起始设备号 */
    unsigned int count;                   /* 设备个数 */
};

void cdev_init(struct cdev *cdev, const struct file_operations *fops);  /* 初始化 */
int  cdev_add(struct cdev *cdev, dev_t dev, unsigned count);            /* 注册 */
void cdev_del(struct cdev *cdev);                                       /* 注销 */

cdev_init 顺手把 cdev->ops 指过去，所以 file_operations 必须在 cdev_init 之前定义好，生命周期要覆盖整个模块存活期。

cdev 自己 cdev_init + cdev_add register_chrdev 内部完成
节点名 "led0" "led"
卸载 cdev_del + unregister_chrdev_region unregister_chrdev

五、file_operations 的实现 #

file_operations 是驱动对应用层的全部接口。没实现的回调留 NULL，应用调过去会拿到错误码。

c
struct file_operations {
    struct module *owner;
    loff_t (*llseek) (struct file *, loff_t, int);
    ssize_t (*read) (struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write) (struct file *, const char __user *, size_t, loff_t *);
    unsigned int (*poll) (struct file *, struct poll_table_struct *);
    long (*unlocked_ioctl) (struct file *, unsigned int, unsigned long);
    long (*compat_ioctl) (struct file *, unsigned int, unsigned long);
    int (*mmap) (struct file *, struct vm_area_struct *);
    int (*open) (struct inode *, struct file *);
    int (*release) (struct inode *, struct file *);
    /* ... 还有 splice/setlease/fallocate 等，本例用不到 */
};
回调 触发时机 LED 驱动 PWM 驱动 说明
.owner — THIS_MODULE THIS_MODULE 必填，管模块引用计数
.open open() 引脚配输出，先全灭 空实现 硬件初始化放这里
.release close() 全灭 关蜂鸣器 与 open 成对
.read read() return 0 不填 本例没有状态要读
.write write() copy_from_user 后点灯 不填 一次传 4 字节
.unlocked_ioctl ioctl() 不填 BEEP_ON/OFF/FREQ 命令 + 参数
.compat_ioctl 32 位应用跑 64 位内核 不填 不填 两块板都是 32 位，可不填
.llseek / .poll / .mmap — 不填 不填 无位置、无事件、寄存器映射留在内核里

两种初始化写法，效果一样：

c
/* 指定初始化器，推荐 */
static const struct file_operations led_fops = {
    .owner = THIS_MODULE,
    .open  = led_open,
    .write = led_write,
};

/* 顺序初始化：成员顺序一变就错位，别用 */
static struct file_operations led_fops = {
    led_open, NULL, NULL, led_write,
};

.owner 要留着。它是 THIS_MODULE，作用是 open 期间给模块加引用计数，防止设备还开着就被 rmmod 把代码抽走。忘了填，卸载那一刻就是踩空。

3.14 和 5.2.8 的 struct cdev 里 ops 已是 const struct file_operations *，把 fops 定义成 static const 能编过，还多一层编译期保护。原文写的是非 const，能跑，但白丢一层检查。

六、open 与 write 的实现 #

6.1 open 里做引脚配置 #

int (*open) (struct inode *inode, struct file *file); 的 inode 带设备号，file 是这次打开的实例，LED 驱动不区分谁打开，两个参数都用不上。S3C2440 版「先清两位再置一位」：

c
static int led_open(struct inode *inode, struct file *file)
{
    /* GPB5~GPB8 配置为输出：先把 [17:10] 清 0，再写入 01 */
    *gpbcon &= ~((0x01 << 10) | (0x01 << 12) | (0x01 << 14) | (0x01 << 16));
    *gpbcon |= ((0x01 << 10) | (0x01 << 12) | (0x01 << 14) | (0x01 << 16));
    return 0;
}

读-改-写的意义：GPBCON 一根引脚占 2 位，直接 *gpbcon = 0x01 << 10 会把其他引脚配置一起冲掉。别的驱动正用着 GPB0 做串口，你一写它就不工作了。

FS4412 版把配置挪到 fs4412_led_init()，open 只负责把四盏灯关掉。放哪儿都行，保证「配置先于操作」即可：放在 open 里每次打开重配一遍，放在 module_init 里只配一次，后者更快、前者更抗外部干扰。

6.2 write 的两个坑 #

原型是 ssize_t (*write) (struct file *file, const char __user *buf, size_t count, loff_t *ppos);。buf 前面的 __user 不是装饰，它告诉 sparse 检查工具「这是用户空间地址」，意味着不能直接解引用。用户指针在内核态解引用，轻则 EFAULT，重则把别的进程地址空间当自己的写。唯一正确路径是 copy_from_user。原文是这样的：

c
static ssize_t led_write(struct file *file, const char __user *buf,
                         size_t count, loff_t *ppos)
{
    int val;

    copy_from_user(&val, buf, count);   /* 返回值被丢了 */
    printk("value %d", val);

    if (val == 1)
        *gpbdata &= ~((0x01 << 5) | (0x01 << 6) | (0x01 << 7) | (0x01 << 8));
    else
        *gpbdata |= ((0x01 << 5) | (0x01 << 6) | (0x01 << 7) | (0x01 << 8));

    return 0;
}

两个问题。第一，copy_from_user 的返回值被丢了。它返回未拷贝成功的字节数，0 表示全成功；非 0 必须返回 -EFAULT，否则用户传野指针进来，val 是未初始化的栈垃圾，驱动照样点灯。第二，count 直接当拷贝长度用，用户传 8 字节，val 只有 4 字节，栈上多写 4 字节，就是栈溢出。修好的版本：

c
static ssize_t led_write(struct file *file, const char __user *buf,
                         size_t count, loff_t *ppos)
{
    int val;

    if (count != sizeof(int))
        return -EINVAL;

    if (copy_from_user(&val, buf, count))
        return -EFAULT;

    if (val == 1)
        *gpbdata &= ~((0x01 << 5) | (0x01 << 6) | (0x01 << 7) | (0x01 << 8));
    else
        *gpbdata |= ((0x01 << 5) | (0x01 << 6) | (0x01 << 7) | (0x01 << 8));

    printk("value %d\n", val);
    return count;      /* 成功返回实际写入的字节数 */
}

返回值也要改。return 0 在应用层看来是「一个字节都没写进去」，write() 返回 0，循环调用就死循环。内核惯例是成功返回 count。

6.3 FS4412 的 write：传灯号 #

FS4412 那份把 write 的数据含义改了：传 0 全灭，传 1~4 点亮对应 LED，传其他全灭。这比只传 0/1 有用，一颗芯片就能做跑马灯。校验写的是 if (len != 4) return -EINVAL;，说明作者知道要校验长度，只是拿 4 当魔数，用 sizeof(int) 更稳妥。

6.4 copy_from_user 与 copy_to_user #

函数 方向 参数序 返回值
copy_from_user(to, from, n) 用户 -> 内核 内核地址在前 未拷贝字节数
copy_to_user(to, from, n) 内核 -> 用户 用户地址在前 未拷贝字节数 
c
static inline unsigned long __must_check
copy_from_user(void *to, const void __user *from, unsigned long n);

static inline unsigned long __must_check
copy_to_user(void __user *to, const void *from, unsigned long n);

三个修饰词各有含义：static inline 让每个编译单元各自展开，不生成外部符号；__must_check 让编译器对丢弃返回值的调用告警，原文那两处没检查，开 -Wunused-result 就报；__user 是地址空间标记，sparse 靠它抓直接解引用用户指针。

两个方向参数序反着来，名字也反着：from_user 的 to 是内核地址，to_user 的 to 是用户地址。写反了不会立刻崩，会在别处出诡异现象。

6.5 release 与 read #

release 里把四盏灯关掉是习惯做法，避免应用异常退出后灯一直亮着耗电。read 直接 return 0 表示「读到末尾」，应用侧 read() 拿到 0。本例没有状态要上报，这样写够了。

七、硬件寄存器操作 #

7.1 为什么必须 ioremap #

CPU 访问外设有两种编址：x86 那套是 I/O 映射，外设占独立地址空间，用 IN/OUT 指令；ARM、PowerPC 这套 RISC 是内存映射，外设寄存器就是内存的一部分，用普通访存指令。

ARM 走内存映射，但物理地址不能直接用：MMU 开着，CPU 发出的地址要过页表翻译，你给物理地址它当虚拟地址翻，结果不可控；内核虚拟地址空间里外设物理地址没有被预映射；同一片物理地址要由内核统一管映射。流程固定为：ioremap 把物理地址映射进内核虚拟地址空间（3G~4G 那段），拿返回的虚拟地址做读写，卸载时 iounmap 释放。

c
#define ioremap(cookie, size)   __ioremap(cookie, size, 0)

void __iomem *__ioremap(unsigned long phys_addr, size_t size, unsigned long flags);

phys_addr 是要映射的起始物理地址，size 是长度（按字节算），flags 是映射属性，走宏时传 0。返回值是内核虚拟地址，失败返回 NULL，严格做法要判空。

7.2 readl / writel 与它们的兄弟 #

原型是 unsigned int readl(const volatile void __iomem *addr); 和 void writel(unsigned int value, volatile void __iomem *addr);。按宽度还有一组兄弟：readb/writeb 是 8 位，readw/writew 是 16 位，readl/writel 是 32 位，本例全部寄存器都用最后这组。

用它们而不是 *(volatile unsigned int *)addr = v，差别在：带内存屏障，编译器和 CPU 都不会把访问重排到屏障之外；处理字节序，ARM 小端板上两者等价，大端板上直接指针访问就错；有些架构上还带额外的总线同步周期。

寄存器地址相邻时用基址加偏移更清楚：

c
#define TIMER_BASE  0x139D0000
#define TCFG0       0x0000
#define TCFG1       0x0004
#define TCON        0x0008
#define TCNTB0      0x000C
#define TCMPB0      0x0010

static void __iomem *timer_base;

timer_base = ioremap(TIMER_BASE, 0x14);   /* 覆盖 0x00~0x13 五个寄存器 */
writel(500, timer_base + TCNTB0);

timer_base 声明成 void *，做指针加法时按 1 字节步进，timer_base + TCNTB0 就是基址加 0xC。原文注释写了「偏移量为 4 时只移动 4 个字节，方便理解」，就是这个意思。声明成 unsigned int * 的话 +1 移动 4 字节，偏移量就得写成寄存器序号。偏移量的单位是字节，不是寄存器个数。

7.3 位操作的标准姿势 #

配置一个位域，三步不能省：读整个寄存器、清目标位域（保留其他位）、写入新值。写成一行就是原文那种 writel((readl(gpd0con) & ~(0xf << 0)) | (0x2 << 0), gpd0con);：读 GPD0CON，把 [3:0] 清 0，写入 0x2 表示配成 Timer0 输出模式，写回。

目标 掩码 写入值
GPX2CON [31:28] 配输出 ~(0xf << 28) 0x1 << 28
GPX1CON [3:0] 配输出 ~(0xf << 0) 0x1 << 0
GPF3CON [23:16] 两根配输出 ~(0xff << 16) 0x11 << 16
GPD0CON [3:0] 配 Timer0 ~(0xf << 0) 0x2 << 0
TCFG0 [7:0] 预分频 255 ~(0xff << 0) 0xff << 0
TCFG1 [3:0] 分频 1/4 ~(0xf << 0) 0x2 << 0

7.4 数据寄存器可以直接位操作 #

GPBDAT 这类数据寄存器每一位独立控制一根引脚，可以直接 &= 或 |=：*gpbdata &= ~(0x01 << 5) 让 GPB5 输出低，*gpbdata |= (0x01 << 5) 输出高。四盏灯一起操作时先算好掩码一次写，比逐位写少三次读-改-写。要更严格就走 writel(readl(gpbdata) & ~(0x1 << 5), gpbdata)。

7.5 iounmap 与卸载顺序 #

「谁申请谁释放、后申请先释放」没错就行。S3C2440 版在 init 最后一步做 ioremap，卸载就先 iounmap，再 device_destroy、class_destroy、cdev_del、unregister_chrdev_region。映射没释放就 rmmod，那段虚拟地址一直占着，反复加载卸载几十次 vmalloc 区就漏光，insmod 开始报 ENOMEM。

十、PWM 与 LED 的差别 #

LED 是纯 GPIO，写一个位就出结果。PWM 蜂鸣器挂了定时器，写进去的是计数值，硬件按自己的节拍翻转引脚。框架没变，变的是「写什么」。

维度 LED（S3C2440/FS4412） PWM 蜂鸣器（FS4412）
控制器 GPIO Timer0 + GPIO 复用
关键寄存器 GPBCON/GPBDAT 或 GPXnCON/GPXnDAT GPD0CON + TCFG0/TCFG1/TCON/TCNTB0/TCMPB0
输出方式 静态电平，写一次保持 连续方波，靠硬件翻转
参数 亮 / 灭 频率 + 占空比
所需时钟 无 PCLK 经预分频和分频后供给
接口 write 传 0/1 或灯号 ioctl 传命令 + 频率参数
关断 清数据位 清 TCON 的启动位
框架 设备号 + cdev + fops 同左，一行不改

LED 让你理解「寄存器怎么写」，PWM 让你理解「寄存器写的值之间有什么关系」。后者才是驱动里真正花时间的那部分。

十一、PWM 的工作原理 #

PWM 就是方波。一个周期里高电平占的比例叫占空比，一秒内周期重复的次数叫频率。

text
         ____      ____      ____
        |    |    |    |    |    |
  ______|    |____|    |____|    |____
        <----> 高电平（TCMPB0）  <----> 一个周期（TCNTB0）

占空比 = TCMPB0 / TCNTB0

PCLK --> [预分频 TCFG0] --> [分频 TCFG1] --> 计数时钟
                                                |
                                     [TCNTB0 递减计数]
                                                |
                              计数值 > TCMPB0  --> 引脚输出一种电平
                              计数值 <= TCMPB0 --> 引脚翻转
                                                |
                                          [减到 0 自动重装]

FS4412 上蜂鸣器接 GPD0_0。查手册可知这根脚复用为 Timer0 的输出 TOUT0，所以 GPD0CON 的 [3:0] 要配成 0x2。配好之后，引脚电平不再由 GPD0DAT 决定，改由 Timer0 的比较结果决定。

TCON 控制 Timer0 的启停：

位 名称 作用
bit0 Timer0 start/stop 1 启动，0 停止
bit1 Timer0 manual update 1 把 TCNTB0/TCMPB0 装入内部寄存器
bit2 Timer0 inverter 1 反相输出
bit3 Timer0 auto reload 1 计数到 0 后自动重装 TCNTB0

对本例有用的三个值：0x2 手动更新，把刚写进去的 500 和 250 装进内部计数器，必须写这一下，否则 TCNTB0 里的值不生效；0x9 自动重装 + 启动，方波开始输出；0x0 停。0x2 和 0x9 都会整体改写 [3:0]，所以代码里用 (readl(TCON) & ~(0xf << 0)) | 值 这种形式，只动低 4 位。

十二、PWM 的寄存器配置 #

基址 TIMER_BASE = 0x139D0000，五个寄存器连续排列，用偏移量访问：

寄存器名 偏移量 位域 配置值 作用
TCFG0 0x0000 [7:0] 0xFF 预分频值 255
TCFG1 0x0004 [3:0] 0x2 MUX 分频（见第十三章）
TCON 0x0008 [3:0] 0x2 → 0x9 → 0x0 手动更新 / 启动 / 停止
TCNTB0 0x000C [31:0] 500 计数初值，定周期
TCMPB0 0x0010 [31:0] 250 比较值，定占空比
GPD0CON 独立地址 0x114000a0 [3:0] 0x2 GPD0_0 复用为 TOUT0

映射长度取 0x14，正好覆盖 0x00 到 0x13 这五个寄存器。少映射一个字节，写 TCMPB0 就越界。

c
static void fs4412_beep_init(void)
{
    gpd0con    = ioremap(GPD0CON, 4);
    timer_base = ioremap(TIMER_BASE, 0x14);

    /* 1. 引脚复用为 TOUT0 */
    writel((readl(gpd0con) & ~(0xf << 0)) | (0x2 << 0), gpd0con);

    /* 2. 预分频 255，分频见 TCFG1 */
    writel((readl(timer_base + TCFG0) & ~(0xff << 0)) | (0xff << 0), timer_base + TCFG0);
    writel((readl(timer_base + TCFG1) & ~(0xf << 0)) | (0x2 << 0), timer_base + TCFG1);

    /* 3. 装周期和占空比 */
    writel(500, timer_base + TCNTB0);
    writel(250, timer_base + TCMPB0);

    /* 4. 手动更新，把上面的值装进内部寄存器 */
    writel((readl(timer_base + TCON) & ~(0xf << 0)) | (0x2 << 0), timer_base + TCON);
}

static void fs4412_beep_on(void)
{
    /* bit3 自动重装 + bit0 启动，bit1 手动更新顺带被清掉 */
    writel((readl(timer_base + TCON) & ~(0xf << 0)) | (0x9 << 0), timer_base + TCON);
}

static void fs4412_beep_off(void)
{
    writel((readl(timer_base + TCON) & ~(0xf << 0)) | (0x0 << 0), timer_base + TCON);
}

先配时钟再装计数值，因为计数值是按配置好的时钟节拍跑的，顺序反了第一声的频率是错的。0x9 这一写顺手把 bit1 清了，所以 init 里置上的 manual update 不会一直挂着，这是原码能跑起来的原因，不是巧合。

十三、频率与占空比的计算 #

三个参数决定最终频率：计数时钟 = PCLK / (prescaler + 1) / divider，PWM 频率 = 计数时钟 / TCNTB0，占空比 = TCMPB0 / TCNTB0。

代入本例的数字。PCLK 在素材的 pwm_music.h 里定义为 (202800000/4)，即 50 700 000；prescaler 写 0xFF，实际分频 0xFF + 1 = 256；TCNTB0 = 500，TCMPB0 = 250，于是计数时钟 = 50700000 / 256 / 4 = 49512 Hz，PWM 频率 = 49512 / 500 = 99.0 Hz，占空比 = 250 / 500 = 50%。99 Hz 落在人耳可听范围内，所以蜂鸣器响。

要改频率、保持占空比 50%，只动两个寄存器：writel(49512 / f, timer_base + TCNTB0); 和 writel(49512 / f / 2, timer_base + TCMPB0);。

原码里的 BEPP_IN_FREQ（拼写应为 BEEP_IN_FREQ）取的是整数 100000，是同一思路的简化版：

c
#define BEPP_IN_FREQ 100000

static void beep_freq(unsigned long arg)
{
    writel(BEPP_IN_FREQ / arg,       timer_base + TCNTB0);
    writel(BEPP_IN_FREQ / (2 * arg), timer_base + TCMPB0);
}

arg 直接当频率用，arg = 262（中央 C）时 TCNTB0 = 381、TCMPB0 = 190。用 100000 代替真实计数时钟 49512，算出来的音高整体偏高，但相邻音的相对关系没变，放歌还是能听出调子。要准就得换成真实值。

两个边界要留意：TCNTB0 最小不能到 0，arg 大到超过 BEPP_IN_FREQ 时整数除法得 0，定时器就停了，TCMPB0 同理，加范围判断。上电之后改 TCNTB0/TCMPB0 还要重新走一遍 manual update，否则新值只在下一个周期被部分采用，原码没有重装这一步，改频率时会有短暂杂音。

        return -EBUSY;

        class_destroy(cls);
        unregister_chrdev(major, "beep");
        return -EBUSY;
    }

    fs4412_beep_init();
    return 0;
}

    iounmap(timer_base);

十五、用 ioctl 控制 LED 与 BEEP #

write 只能传一段数据。open 关灯、write 点灯这套在 LED 上还凑合，到蜂鸣器就不够用了：既要「开」、又要「关」、还要「设频率」，三种意图混在一个 write 的缓冲区里靠约定字节含义区分，越写越乱。ioctl 就是为这件事生的：一个命令号 + 一个参数。

c
int ioctl(int d, int request, ...);           /* 应用侧，需 <sys/ioctl.h> */
long (*unlocked_ioctl) (struct file *, unsigned int cmd, unsigned long arg);

应用侧 request 是命令号，第三个参数可以是值也可以是地址。驱动侧 arg 类型是 unsigned long，传整数直接强转，传指针要再 (void __user *) 转回去。内核不像应用那样有可变参数，值还是地址全靠你在驱动里约定。

LED 也能加 ioctl。素材只留了「练习：1. led」这一行，这里补一份可用的设计：

c
#define LED_MAGIC    'L'
#define LED_ON       _IOW(LED_MAGIC, 0, int)    /* 参数：灯号 1~4 */
#define LED_OFF      _IOW(LED_MAGIC, 1, int)
#define LED_ALL_ON   _IO(LED_MAGIC, 2)
#define LED_ALL_OFF  _IO(LED_MAGIC, 3)

static long led_ioctl(struct file *filep, unsigned int cmd, unsigned long arg)
{
    int num;

    switch (cmd) {
    case LED_ALL_ON:
        fs4412_led_on(0);      /* 传非法值，走 default 全亮 */
        break;
    case LED_ALL_OFF:
        fs4412_led_off(1); fs4412_led_off(2);
        fs4412_led_off(3); fs4412_led_off(4);
        break;
    case LED_ON:
    case LED_OFF:
        if (copy_from_user(&num, (void __user *)arg, sizeof(int)))
            return -EFAULT;
        if (num < 1 || num > 4)
            return -EINVAL;
        if (cmd == LED_ON)
            fs4412_led_on(num);
        else
            fs4412_led_off(num);
        break;
    default:
        return -EINVAL;
    }
    return 0;
}

应用侧传地址：int num = 2; ioctl(fd, LED_ON, &num);。蜂鸣器那套原码已写好三档命令，完整的响 6 秒测试程序：

c
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>
#include <sys/ioctl.h>

#define MAGIC_NUMBER  'k'
#define BEEP_ON       _IO(MAGIC_NUMBER, 0)
#define BEEP_OFF      _IO(MAGIC_NUMBER, 1)
#define BEEP_FREQ     _IO(MAGIC_NUMBER, 2)

int main(void)
{
    int fd;

    fd = open("/dev/beep", O_RDWR);
    if (fd < 0) {
        perror("open fail");
        return -1;
    }

    ioctl(fd, BEEP_ON);
    sleep(6);
    ioctl(fd, BEEP_OFF);

    close(fd);
    return 0;
}

_IO 宏在应用侧和驱动侧必须展开成同一个值，所以两边的 MAGIC_NUMBER 和序号必须完全一致。放一个公共头文件里最稳妥，两边各自抄一遍迟早抄错。

十六、ioctl 命令码的设计 #

c
#define _IO(type, nr)            _IOC(_IOC_NONE,  (type), (nr), 0)
#define _IOR(type, nr, size)     _IOC(_IOC_READ,  (type), (nr), sizeof(size))
#define _IOW(type, nr, size)     _IOC(_IOC_WRITE, (type), (nr), sizeof(size))
#define _IOWR(type, nr, size)    _IOC(_IOC_READ | _IOC_WRITE, (type), (nr), sizeof(size))

一个 32 位命令码被切成四段：

位域 宽度 名称 含义
[31:30] 2 位 方向 00 无数据，01 读（内核->用户），10 写（用户->内核），11 双向
[29:16] 14 位 size 参数类型的大小
[15:8] 8 位 type 幻数，区分不同驱动
[7:0] 8 位 nr 序号，同一驱动内的命令编号

8 8 2 14 这四个数字就是四个字段的位宽，顺序是 type、nr、方向、size。

四个宏怎么选：_IO 无数据只有命令；_IOW 用户传给内核；_IOR 内核传给用户；_IOWR 双向。原码把 BEEP_FREQ 写成 _IO，实际却要用 arg 传频率。能用，但方向字段是空的、size 也是 0，别的工具拿命令码去解析就看不出这个命令要带参数，改成 _IOW(MAGIC_NUMBER, 2, int) 更准确。

幻数取一个字符，'k'、'L' 都行，但要保证和已占用的不冲突。内核源码树里有分配表 Documentation/ioctl/ioctl-number.txt，素材记的路径是 E:\linux-3.14-fs4412\Documentation\ioctl\ioctl-number.txt，位置对，盘符按你本机改。撞了别人的幻数，同一个进程里两个驱动的命令码会互相误判。

宏 定义 参数 驱动侧动作
BEEP_ON _IO('k', 0) 无 TCON 写 0x9，启动 Timer0
BEEP_OFF _IO('k', 1) 无 TCON 写 0x0，停止 Timer0
BEEP_FREQ _IO('k', 2)，建议 _IOW('k', 2, int) 频率 Hz 重算 TCNTB0 / TCMPB0
LED_ON _IOW('L', 0, int) 灯号 1~4 对应数据位置 1
LED_OFF _IOW('L', 1, int) 灯号 1~4 对应数据位清 0
LED_ALL_ON _IO('L', 2) 无 四盏全亮
LED_ALL_OFF _IO('L', 3) 无 四盏全灭

调试时可以用 _IOC_DIR、_IOC_TYPE、_IOC_NR、_IOC_SIZE 把命令码拆回来打印，比对着十六进制猜快得多。

十九、易错点速查 #

# 易错点 后果 正确做法
1 把用户指针直接解引用 内核 oops 或数据错乱 一律走 copy_from_user
2 丢掉 copy_from_user 返回值 野指针也能「成功」 非 0 返回 -EFAULT
3 不校验 count 就拷贝 栈溢出 先判 count != sizeof(int)
4 write 返回 0 应用侧视为没写进去 成功返回 count
5 不填 .owner 模块被抽走后踩空 = THIS_MODULE
6 fops 用顺序初始化 成员顺序变动即错位 用指定初始化器 .xxx =
7 主设备号写死 250 换环境就冲突 alloc_chrdev_region
8 设备号申请失败仍继续 cdev_add 挂空壳 每步判返回值并 goto 回滚
9 卸载顺序和申请顺序一致 释放已失效的对象 后申请的先释放
10 忘记 iounmap vmalloc 泄漏 每个 ioremap 都有对应 iounmap
11 直接给寄存器赋值 冲掉相邻引脚的配置 读-改-写，先清位再置位
12 ioremap 长度算少 写越界，踩到别的映射 按最高偏移加寄存器宽度算
13 ioremap 返回值不判空 空指针写，直接崩 判空并回滚
14 用 int * 存 timer_base 指针加法步进 4 字节，偏移全错 用 void *，偏移按字节写
15 TCON 忘了 manual update TCNTB0 的值不生效 先写 0x2 再写 0x9
16 ioctl 命令码两边不一致 全部返回 -EINVAL 抽公共头文件，别各抄一遍
17 ioctl 函数 switch 后没 return 返回值是栈垃圾 末尾补 return 0
18 _IO 当 _IOW 用 命令码里没 size，工具解析不出 带参数就用 _IOW(type, nr, 类型)
19 幻数和已有驱动撞车 命令互相误判 查 ioctl-number.txt
20 占空比参数不判上下限 除零或定时器停摆 加范围检查
21 改频率后不重装计数值 有杂音、频率跳变 重走一遍 manual update
22 -march 和目标板不匹配 一跑就非法指令 S3C2440 用 armv4t
23 obj-m 和源文件名不符 make 报 No rule to make target 两者对齐
