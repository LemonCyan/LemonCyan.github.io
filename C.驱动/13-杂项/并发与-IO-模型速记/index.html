一、并发与竞态：课堂上的第一个错误示范 #

课上给并发的定义是从两个视角切开的：宏观上看，操作系统里多个任务在并行执行；微观上看，任何一个瞬间 CPU 只跑一条指令，多个任务是被切碎了串行跑的。这两句话不矛盾，它们是同一件事的两面——并发是宏观的并行，微观的串行加上切换。

竞态就从这个「切碎了串行跑」里长出来。当多个执行单元访问同一份共享资源（硬件寄存器、全局变量、链表、静态变量），访问顺序不同、结果就不同，这就是竞态。资源本身没毛病，毛病在于访问没被约束。

第一个贯穿全课的引子是个很朴素的需求：让一个驱动在同一时刻只能被一个进程打开。课上先用一个 flag 变量去实现它，代码写出来是这样的：

c
static int flag = 1;          /* 1 表示空闲，0 表示已被占用 */

static int hello_open(struct inode *inode, struct file *file)
{
    if (flag != 1) {
        return -EBUSY;
    }

    flag = 0;                 /* 占住 */

    return 0;
}

static int hello_release(struct inode *inode, struct file *file)
{
    flag++;
    return 0;
}

这段代码写完，问题留在了黑板上：它错在哪？

问题不在语法，也不在逻辑顺序。问题在于 if (flag != 1) 和 flag = 0; 是两条彼此独立的指令，中间那个缝可以插进任何东西。课堂上把这条时间线当场摊开：

text
进程 A：读 flag    → 1，判断通过
        ← 时间片用完，或被更高优先级的进程抢占，CPU 切走
进程 B：读 flag    → 还是 1，判断通过
进程 B：写 flag=0  → open 成功，拿到设备
进程 A：被调度回来，写 flag=0 → open 也成功
        ✗ 两个进程同时持有 /dev/hello

这段示范的价值在于它把「临界区」这个词从定义变成了画面。flag 是临界资源，读写它的那几行代码是临界区，而临界区一旦被拆开执行，互斥就失效了。hello_release 里的 flag++ 同理——读、加、写三步，同样能被拆。

课堂板书还有另一个版本，写的是结构体成员：

c
if (hello_dev.flag == 1) {
    hello_dev.flag = 0;
}

这两版是同一节课的两块板书，判断方向并不冲突（都是 1 表示空闲），差别只在于第二版只记了 if 分支，else 分支在抄写时掉了。看速记时别被这个坑住。

判断和修改必须是一个不可分割的整体，这个需求直接催生了后面所有机制。课上把它归成一句话：访问共享资源的那几条指令不能被打断，打断它的东西一共有三类——别的进程（抢占）、中断、别的 CPU。

二、临界区与临界资源 #

课上的定义给得很直接，四个词两两成对：

概念 课堂定义 落到代码上
并发 多个执行单元同时执行；或多执行单元微观串行、宏观并行 两个 open 同时进来
竞态 并发执行单元对共享资源访问导致的状态错乱 flag 被读了两遍、写了两遍
临界资源 同一时刻只允许一个执行单元使用的资源 flag、环形缓冲区、硬件寄存器
临界区 访问临界资源的那段代码 if (flag != 1) ... flag = 0;

关键点在于临界区是代码，不是资源。判断一段代码是不是临界区，只看它碰不碰临界资源，不看它写在哪个函数里。open 里碰了，open 里那两行就是；release 里碰了，release 里那行也是。同一份资源的所有临界区必须用同一把锁保护，漏掉任何一处，锁就白加了。

课上强调过一个容易被忽略的推论：临界区的粒度决定了锁的代价。围得太大，把 printk、copy_to_user 这种慢操作包进去，锁的持有时间被拉长，别的执行单元全在门外排队；围得太小，漏掉几行，互斥直接破功。三种粒度当场对比过：

写法 效果
只锁 flag = 0; 一行 判断在锁外，还是两个进程都能通过判断，等于没锁
锁住判断到赋值两行 正确，这是最小可用临界区
锁住整个 hello_open 正确但浪费，printk 之类不该进临界区

那个「只锁一行」的写法是课上专门写出来反着讲的，它比完全不锁更有欺骗性——代码里明明有 spin_lock，跑起来照样两个进程进得去。

三、四种并发场合 #

并发场合这条是考试重点，课上要求背下来并且能对上每种场合该用什么机制。四种场合按「谁打断谁」排列：

# 场合 打断关系 单/多核 课上给的对应机制
1 单 CPU，进程与进程之间 抢占，高优先级进程打断低优先级 单核 自旋锁、信号量
2 单 CPU，进程与中断之间 中断打断正在执行的进程 单核 加锁 + 关中断
3 多 CPU 之间 真正并行，各自跑各自的 多核 原子操作、自旋锁
4 单 CPU，中断与中断之间 高优先级中断打断低优先级中断 单核 关中断 + 锁

课上对着这张表的讲法是：场合 1 是「进程打进程」，场合 2 是「中断打进程」，场合 3 是「CPU 打 CPU」，场合 4 是「中断打中断」。四种里只有场合 3 是物理上的同时发生，其余三种都是靠切换制造出来的假并行——但对代码来说没区别，一样会烂。

这里有个课堂反复纠正的误解：单 CPU 就不用上锁。错。单 CPU 上如果内核是可抢占的，进程跑到临界区中间被切走，另一个进程进来照样踩。只有当「单 CPU + 内核不可抢占 + 不涉及中断」三个条件同时成立时，竞态才不存在——而这三个条件在真实系统里凑不齐。

场合 2 和场合 4 为什么必须关中断，课上是用反证讲的：如果只加锁不关中断，进程 A 拿到锁以后中断来了，中断处理函数也要这把锁，它在中断上下文里自旋等——可 A 已经被中断挂起了，永远回不来交出锁，于是死锁。这个场景后面第六节还会展开。

四、中断屏蔽 #

最原始的一招。进临界区前把本地 CPU 的中断全关掉，出来再打开：

c
local_irq_disable();          /* 屏蔽本 CPU 中断 */
/* ... 临界区 ... */
local_irq_enable();           /* 开中断 */

课上给的结论很干脆：单 CPU 下没问题，多 CPU 下照样有竞态。原因是 local_irq_disable() 只动本地 CPU 的中断标志位，另一个 CPU 上的进程该跑还是跑，它进临界区不需要经过你的中断开关。所以中断屏蔽从来不是一把完整的锁，它只是把「中断」这一路竞争者挡在门外。

结论很直接：这东西不单独使用。原因两条，第一条是关中断以后很多事都做不了——时钟中断进不来，调度器停摆，系统的时间感消失；第二条是临界区必须尽量短，赶紧干完赶紧开中断，关久了整个系统跟着卡。

正因为它这么粗暴，实际代码里更常见的是保存恢复版本：

c
unsigned long flags;

local_irq_save(flags);        /* 关中断，同时把原中断状态存进 flags */
/* ... 临界区 ... */
local_irq_restore(flags);     /* 恢复成原来的状态，不是无脑开中断 */

区别在 local_irq_restore 恢复的是「进来之前的样子」。如果这段代码本身已经运行在关中断上下文里，用 local_irq_enable() 出去就直接把中断打开了，等于把外层关的中断给拆了——这类嵌套场景正是 save/restore 存在的理由。

维度 说明
作用范围 只影响本地 CPU
能挡住 中断、以及依赖中断的进程抢占
挡不住 其他 CPU 上的进程
代价 系统失去时间感，临界区必须极短
课堂结论 一般不单独使用，作为自旋锁的配套手段出现

（local_irq_save / local_irq_restore 在 3.x 已有；具体宏展开随架构不同，未验证。）

五、原子操作：那个经典的单例判断 #

原子操作的定义课上只讲了一句：不可分割的操作。执行期间不会被任何东西打断，连中断也不行。它能保护的范围很小，只针对单个变量，但正好卡在第一节那个 flag 的判断上。

一个原子变量用 atomic_t 定义，初值靠 ATOMIC_INIT 给：

c
static atomic_t v = ATOMIC_INIT(1);     /* 1 表示没有被占用 */

配套的几个操作里，关键是 atomic_dec_and_test()：把变量减 1，然后测试结果是不是 0，是 0 返回真，否则返回假。注意它把「减」和「测」合成了一步，这两步之间没有缝可插——难点正在这里，拆成 atomic_dec() 再读值又回到竞态了。

课上给的正确版是这样：

c
static atomic_t v = ATOMIC_INIT(1);

static int hello_open(struct inode *inode, struct file *file)
{
    printk("hello_open()\n");

    if (!atomic_dec_and_test(&v)) {      /* 减到 0 才算抢到 */
        atomic_inc(&v);                  /* 没抢到，把计数加回来 */
        return -EBUSY;
    }

    return 0;
}

static int hello_release(struct inode *inode, struct file *file)
{
    printk("hello_release()\n");
    atomic_inc(&v);
    return 0;
}

两个细节必须抠清楚。第一，初值为什么是 1 而不是 0：atomic_dec_and_test 是「减完看是不是 0」，初值 1 减一次到 0 返回真，表示第一个进程拿到了；第二个进程再减就变成 -1，返回假。如果初值给 0，第一个进程一减就成 -1，永远拿不到。第二，失败分支里的 atomic_inc(&v) 不是可选的客气话：不加回来，计数会一路往下掉，掉到很负以后，即便所有进程都关了设备，atomic_dec_and_test 也再也回不到 0，这把「是否被占用」的判断彻底废掉。

课上把原子操作的常用项列成一张表：

函数 语义 返回值
atomic_set(v, i) 设为 i 无
atomic_read(v) 读当前值 当前值
atomic_inc(v) 加 1 无
atomic_dec(v) 减 1 无
atomic_inc_and_test(v) 加 1 后测是否等于 0 等于 0 返回真
atomic_dec_and_test(v) 减 1 后测是否等于 0 等于 0 返回真
atomic_add(i, v) / atomic_sub(i, v) 加减 i 无

（atomic_t、ATOMIC_INIT、atomic_dec_and_test 在 3.x 与 2.6 后期都可用；atomic_inc_and_test 同期的存在性未逐版本验证。）

课上还专门澄清过一次板书里的表述错误。速记里写的是「上述操作对原子变量执行自增、自减和减操作后（注意没有加）测试其是否为 0」，这句话读不通——atomic_inc_and_test 就是「加 1 后测试」，atomic_dec_and_test 是「减 1 后测试」，两个都有，没有「没有加」这回事。

原子操作的局限也要说清：它只能做计数类的事，保护的是一两个整数，说不上保护一段逻辑。要保护多行代码、多个变量，就得往上走，用锁。它的优点是简单、不进睡眠、中断上下文里也能用。

六、自旋锁：什么时候必须关中断 #

自旋锁的语义课上用两个词拆开讲：锁，是拿到就能访问临界资源；自旋，是拿不到就在原地忙等，不睡、不放手、占着 CPU 转圈。

先讲它跟 CPU 核数的关系，这块是课堂上的一个小表：

场景 自旋锁的实际行为
单核、内核不可抢占 空操作，退化成什么都不做
单核、内核可抢占 关掉内核抢占
多核 关抢占 + 真的自旋等锁

单核非抢占下为什么能退化成空操作：只有一个执行流在跑，不存在「另一个人正拿着锁」这种情况，加锁解锁自然没意义。单核抢占下要关抢占，是因为抢占会让另一个进程进来抢同一把锁。多核下两者都要。

API 只有四个，课上要求默写：

c
spinlock_t lock;              /* 定义 */
spin_lock_init(&lock);        /* 初始化 */

spin_lock(&lock);             /* 拿到立即返回，拿不到原地自旋 */
/* ... 临界区 ... */
spin_unlock(&lock);           /* 释放 */

spin_trylock() 课上提了一句：拿到返回真，拿不到立刻返回假，不在原地打转——用在不值得等或者不能等的场合。

内核抢占这件事课上单独讲了一段，因为它是自旋锁一切限制的根源：不管当前进程在内核态还是用户态，内核都会去调度优先级更高的进程运行、把当前进程停下。而自旋锁自旋期间内核抢占是关闭的，内核不会去调度别的进程。好处是持锁的进程一定能拿到 CPU 把活干完、把锁放掉；坏处是持锁的进程一旦不放手，全系统陪着等。

两种死锁是课堂重点，都是从这个「抢占关闭」推出来的。

死锁一，持锁睡眠：进程 A 拿到自旋锁以后在内核态阻塞了（比如调了个会睡的接口），内核调度进程 B，B 也要同一把锁，B 只能自旋；而此时抢占是关闭的，A 不会被调度回来，B 永远自旋下去。

死锁二，中断取锁：进程 A 拿着自旋锁，中断来了，CPU 转去执行中断处理函数，该函数也要这把锁，拿不到只能自旋；可锁在 A 手里，A 被这个中断挂起了，永远回不来。两边互等，卡死。

死锁二正好回答了「什么时候必须关中断」这个标题：只要临界区会跟中断处理函数抢同一把锁，进临界区就必须把中断一起关上，用 spin_lock_irqsave() 系列：

c
unsigned long flags;

spin_lock_irqsave(&lock, flags);     /* 关中断 + 拿锁 */
/* ... 临界区 ... */
spin_unlock_irqrestore(&lock, flags);/* 放锁 + 恢复中断 */

注意是 save/restore 而不是 spin_lock_irq / spin_unlock_irq。后者出去时无条件开中断，遇到嵌套调用会把外层的关中断状态搞坏。课上把这个当成纪律要求，不是风格偏好。

注意事项课上列了四条：

# 注意事项 原因
1 能解决多 CPU 之间的并发 这是它被设计出来的主因
2 单 CPU 进程之间可直接加锁；进程与中断、中断与中断必须加锁 + 关中断 中断不受锁约束，只受中断开关约束
3 加锁时间一定不能太长 忙等烧 CPU，不睡不放手
4 持锁期间不能调用会引起调度的函数 一调度就撞上死锁一

第 4 条的具体清单课上点过几个：copy_to_user、copy_from_user、kmalloc(GFP_KERNEL)、msleep、schedule。判据只有一条：这个函数会不会睡。

还有一条课上顺带说的：自旋锁不能递归。已经拿着锁的代码再去 spin_lock 同一把锁，它自己就在原地自旋，而唯一能解锁的人是它自己——自己等自己，锁死。

（spin_lock_init、spin_lock、spin_unlock、spin_lock_irqsave、spin_unlock_irqrestore 在 3.x 可用。3.x 里 spinlock_t 是 struct spinlock 的 typedef，其内部成员随 CONFIG_DEBUG_SPINLOCK 等配置变化，未验证。）

七、信号量：什么时候可以睡 #

自旋锁的毛病是「拿不到就占着 CPU 转」。信号量换个思路：拿不到就把当前任务挂起、让出 CPU、睡觉去，等别人放锁时把它叫醒。

课上把根本区别压成一句：信号量是睡眠锁。它内部是一个计数加一张等待队列，计数表达「还剩几个资源」，队列放着「谁在等」。

P/V 那套术语课上提了一次，落到 Linux 就是 down/up：P 是申请（计数减一），V 是释放（计数加一）。课上顺带把用户态的分法点了一下——线程之间用无名信号量，进程之间用信号灯（System V 信号量），内核里用 struct semaphore，这三者名字像、机制不是一回事，别混。

结构体三个成员，课上画了图：

c
struct semaphore {
    spinlock_t lock;              /* 保护 count 的小锁 */
    unsigned int count;           /* >0 空闲；=0 忙但没人等；<0 忙且有 |count| 个在等 */
    struct list_head wait_list;   /* 等待队列链表 */
};

count 的三态语义是这块的核心：一个变量同时表达了「剩几个」和「几个人在等」，负数表示有人在等，绝对值就是人数。

驱动的用法四步：

c
struct semaphore sem;                 /* 定义 */
sema_init(&sem, 1);                   /* 初始化，1 就是二值信号量 */

down(&sem);                           /* 申请，拿不到就睡，且睡得不可被打断 */
/* ... 临界区 ... */
up(&sem);                             /* 释放，唤醒等待队列里的一个 */

申请有两个版本，区别只在「睡下去以后能不能被信号叫醒」：

函数 拿不到时 返回值 适用
down(&sem) 进入不可中断睡眠 无 确定不会有人 Ctrl-C 的场合
down_interruptible(&sem) 进入可中断睡眠，收到信号就醒 0 成功；-EINTR 被信号打断 驱动里优先用这个

down_interruptible 优先的原因课上讲得实在：用 down() 睡下去，用户按下 Ctrl-C，进程处在不可中断睡眠里，信号挂在那里不处理，ps 里显示成 D 状态，谁也杀不掉。用户以为程序死了，其实它只是不肯被叫醒。

但优先用它有个代价必须配套处理——返回 -EINTR 说明你根本没拿到信号量，不能往下走，也不能 up：

c
if (down_interruptible(&sem)) {
    return -ERESTARTSYS;      /* 让上层决定是否重新发起系统调用 */
}
/* 到这里才是真的拿到了 */

-ERESTARTSYS 这个返回值的语义是「被信号打断，请回到系统调用入口重来」，由内核的信号处理逻辑按 SA_RESTART 决定要不要重启。直接返回 -EINTR 也能编译通过，但语义是「这个系统调用失败了」，跟「被打断、可以重试」不是一回事。

sema_init(&sem, 2) 这种写法课上单独提了一句：初值给 2 就是计数信号量，允许两个执行单元同时进临界区。它不再是互斥锁，而是限流器——比如限制同时打开的会话数。

信号量的使用限制跟自旋锁正好互补：它可以睡，所以能保护耗时的、会阻塞的临界区；也正因为会睡，它不能用在中断上下文里——中断处理函数没有进程上下文可睡，睡了没人来叫醒。这是考试里的高频错点。

（sema_init、down、down_interruptible、up 在 3.x 可用；struct semaphore 的成员布局在 3.x 与 4.x 早期一致，新版本的细节未验证。down_interruptible 返回 -EINTR 是 3.x 的语义，2.6 早期版本返回值的具体取值未验证。）

八、自旋锁与信号量的选择 #

五种互斥机制的关系课上用一句话概括：中断屏蔽管的是「中断」这一路，原子操作管的是「一条指令」，剩下三种才管「一段代码」，区别只在于拿不到锁时干什么。

机制 拿不到时 能保护的粒度 能睡吗 中断上下文可用 课堂定位
中断屏蔽 不存在「拿不到」 一段代码 不能 就是给中断用的 保底手段，少单用
原子操作 不存在「拿不到」 单个整型变量 不能 可以 只能计数
自旋锁 忙等、不放手 一段代码 不能 可以（配 irqsave） 短临界区
信号量 睡眠、让出 CPU 一段代码 可以 不可以 长临界区
互斥锁（mutex） 睡眠 一段代码 可以 不可以 二值信号量的专用版

课上把自旋锁和信号量单独拎出来对照，这是考试必答的一道题：

对比项 自旋锁 信号量
等待方式 忙等待（busy-wait），占着 CPU 自旋 睡眠等待，让出 CPU
适用临界区 极短，几条指令 可以较长，允许调用会睡的函数
开销 无调度开销，烧 CPU 有调度开销，但不烧 CPU
内核抢占 持锁期间关闭 不关
中断上下文 可用 不可用
能否递归 不可（自己等自己） 可（计数 >1 时同名函数可再进，但同一把二值信号量仍会死锁）
本质 一把锁 一个计数器 + 一张等待队列
典型用途 保护寄存器、链表指针、标志位 保护需要 copy_from_user、kmalloc 的长流程

选择的判据课上按优先级排了顺序，照着问下来就能定：

  1. 临界区里会不会睡？会睡，就只能选信号量或互斥锁，自旋锁直接出局。
  2. 代码跑在中断上下文里？是中断上下文，就只能选自旋锁或原子操作，会睡的全出局。
  3. 只保护一个整型计数？用原子操作，别上锁。
  4. 临界区是几条指令、竞争激烈？用自旋锁。
  5. 其余情况用信号量或互斥锁。

最后一条注意事项课上重复过两遍：同一份资源只能有一种保护方式。有人既加自旋锁又加信号量，还关中断，三重保险看着稳，实际是把锁的顺序搞复杂了，嵌套一深就容易互相等死。

（mutex 在 3.x 提供的接口是 mutex_init / mutex_lock / mutex_unlock，与信号量不共用 API；素材只写了「互斥锁」三个字，没有展开，具体接口未在素材中验证。）

九、阻塞与非阻塞：从 read 说起 #

read 进到驱动里，做的事很少：有数据就 copy_to_user 拷过去、返回拷贝长度；没数据怎么办？这里是分水岭。

两条路。一条是立刻返回一个错误码，告诉应用「现在没东西，你自己待会儿再来」——这是非阻塞。另一条是把当前进程挂起、让出 CPU、等有数据了再被叫醒——这是阻塞。

阻塞读的两个阶段值得摊开看，五种 IO 模型的差别全在这两个阶段上：

阶段 干什么 谁在等
第一阶段 等数据就绪（硬件收完、缓冲区非空） 内核 / 驱动
第二阶段 把数据从内核缓冲拷到用户空间 进程

阻塞读在两个阶段都让进程睡；非阻塞读第一阶段立刻返回，第二阶段根本不会进入。

非阻塞的驱动侧写法短得没什么可讲，就一个 -EAGAIN：

c
if (0 == hello_dev.len) {
    printk("no resource\n");
    return -EAGAIN;          /* 告诉应用：现在没数据，别等了 */
}

-EAGAIN 的语义是「暂时不可用，稍后重试」，不是错误。应用层拿到它要自己决定是马上再 read 一次（这就是轮询），还是干别的去。用户侧打开设备时带上标志位：

c
fd = open("/dev/hello", O_RDWR | O_NONBLOCK);

驱动里判断这个标志，靠的是 file->f_flags & O_NONBLOCK。课上把这个判断放进了阻塞/非阻塞二合一的 read 里，因为它必须在同一个函数里分流：

c
if (file->f_flags & O_NONBLOCK) {
    return -EAGAIN;                       /* 非阻塞：立刻回去 */
}
wait_event_interruptible(wq, havedata == 1);   /* 阻塞：睡下等 */

课上还提了一个测试小技巧，用 shell 一条命令就能验证非阻塞路径：

text
echo xxx > /dev/hello

这条命令等价于一次 open + write + close。设备没资源时 write 返回 -EAGAIN，echo 会打印一句写失败的提示。所以课上先用它确认驱动到底是「没数据」还是「真坏了」——这条命令不区分阻塞非阻塞，因为 echo 只写不读。

阻塞的依赖关系也定死了：阻塞一定靠等待队列实现，没有第二种办法。非阻塞不需要任何基础设施，加个 if 返回错误码就完事。所以「实现阻塞」这件事的成本，全在等待队列上。

十、等待队列的五个步骤 #

等待队列是这一节的全部内容，课上要求按五步默写。

第一步，定义等待队列头：

c
wait_queue_head_t my_queue;

第二步，初始化它：

c
init_waitqueue_head(&my_queue);

这两步有个一步到位的写法，定义和初始化合在一起：

c
static DECLARE_WAIT_QUEUE_HEAD(my_queue);

DECLARE_WAIT_QUEUE_HEAD 在素材里没有出现，是补进来的；它在 3.x 的 include/linux/wait.h 中是静态定义并初始化的宏，静态全局队列用它更省事。（该宏在 2.6 后期到 3.x 的形态一致，更早版本未验证。）

第三步，等待事件。没资源就让进程睡，条件满足才往下走：

c
wait_event(queue, condition);
wait_event_interruptible(queue, condition);

condition 的判定时机是这块最容易记错的地方，课上专门拆成睡前睡后两行：

时机 condition 为真 condition 为假
睡前检查 不睡，直接往下走 进入睡眠
睡后检查（被唤醒时） 醒了，返回，继续执行 继续睡回去

关键理解是：唤醒不等于条件成立。wake_up 只是把进程从睡眠队列里拎出来，它醒来第一件事是重新检查 condition，不成立就继续睡。这个「唤醒后重查」的循环是整个等待队列不丢事件的根本，也是为什么 condition 必须能反映真实状态、不能用一次性标志糊弄。

返回值语义也要标清楚，素材里完全没写：

调用 返回值 说明
wait_event 无（宏，不返回状态） 不可中断睡眠，只能被 wake_up 叫醒
wait_event_interruptible 0：条件成立后醒来；-ERESTARTSYS：被信号打断 调用方必须判断返回值，非 0 说明条件没满足

（返回值取值来自 3.x include/linux/wait.h 的惯例；本机无 3.x 源码可核对，未验证。4.x 之后的 wait_event_interruptible 仍是同一套返回值。）

第四步，有资源时唤醒：

c
void wake_up(wait_queue_head_t *queue);
void wake_up_interruptible(wait_queue_head_t *queue);

配对规则课上强调过：wait_event 配 wake_up，wait_event_interruptible 配 wake_up_interruptible。混着用不会编译报错，但会漏唤醒——不可中断睡眠的进程只能被 wake_up 叫醒，用 wake_up_interruptible 叫它等于没叫。

第五步，处理「一次唤醒几个」的问题。这就是惊群。

课上在这里追问了一句：一次唤醒几个？这个概念有个名字叫疯狂兽群（thundering herd，惊群），现象是：缓冲区里只来了一份数据，wake_up 把队列上所有睡着的进程全叫醒，它们冲进来抢这一份数据，抢到的只有一个，其余全部白醒一趟、再睡回去——一次唤醒换来 N 次无效调度。

解药是独占等待，靠标志位 WQ_FLAG_EXCLUSIVE。内核侧对应的唤醒接口是 wake_up_interruptible 的限定版，醒来时只叫醒队列头部的若干个独占等待者，而不是把所有人掀起来。素材对这部分只有「标记，WQ_FLAG_EXCLUSIVE」一句，没有代码；prepare_to_wait_exclusive 等接口出自 3.x 的 wait.h，素材里没出现，未验证。

课上还留了一句带实验色彩的话：「通过实验得出结论，唤醒所有的」。意思是先别背结论，自己在设备上加打印，把 wake_up 前后每个进程的状态打出来看——看到几个进程被叫醒、几个又睡回去，惊群就不是概念了。

把这些拼起来，就是课上那个完整的阻塞 read，它同时处理了三件事：数据长度裁剪、非阻塞分流、阻塞等待：

c
ssize_t hello_read(struct file *file, char __user *user, size_t size, loff_t *pos)
{
    if (size > strlen(buf)) {
        size = strlen(buf);              /* 别让应用要的比我们有的还多 */
    }

    if (havedata == 0) {                 /* 没数据 */
        if (file->f_flags & O_NONBLOCK) {
            return -EAGAIN;              /* 非阻塞：立刻回去 */
        }
        wait_event_interruptible(wq, havedata == 1);   /* 阻塞：睡下等 */
    }

    if (copy_to_user(user, buf, size)) {
        return -EFAULT;                  /* 拷贝失败，用户地址有问题 */
    }

    havedata = 0;                        /* 数据被取走了 */
    return size;
}

havedata 是配套的软件标志，写侧写进数据后把它置 1、再 wake_up_interruptible(&wq)；读侧取走后清 0。它和 condition 是同一个东西的两个身份：既是状态位，又是 wait_event 的判据。

这段代码还有一处课堂没展开但必须知道的缺口：wait_event_interruptible 的返回值被直接忽略了。被信号打断时它返回 -ERESTARTSYS，此时 havedata 仍是 0，代码却继续往下走 copy_to_user，把空缓冲区拷给应用。严谨写法是先判返回值：

c
if (wait_event_interruptible(wq, havedata == 1)) {
    return -ERESTARTSYS;
}

十一、poll 与多路复用 #

一个进程要同时盯好几个设备，阻塞读做不到——它一睡就只等一个 fd。多路复用解决的就是这件事：让一个进程同时监听多路输入输出。应用层用 select，驱动层靠 poll 方法配合。

select 的原型和参数在课上抄了完整一遍：

c
int select(int nfds, fd_set *readfds, fd_set *writefds,
           fd_set *exceptfds, struct timeval *timeout);

参数逐个抠：

参数 含义 课堂备注
nfds 所监控的描述符最大值 + 1 不是个数，是最大值加一
readfds 读集合，关心「有数据可读」的 fd 放这里 传入传出双向使用
writefds 写集合，关心「可以写」的 fd 放这里 同上
exceptfds 异常集合 课上没细讲
timeout 超时时间 三种取值见下

timeout 的三态是考点：

取值 行为
NULL 一直阻塞，直到有 fd 就绪
指向 {0, 0} 的时间结构 非阻塞，立刻返回当前就绪情况
指向一个大于 0 的时间 等到有 fd 就绪，或超过这个时间就立刻返回

配套四个宏，操作 fd_set：

c
void FD_CLR(int fd, fd_set *set);     /* 从集合里清掉一个 fd */
int  FD_ISSET(int fd, fd_set *set);   /* 判断某个 fd 是否就绪 */
void FD_SET(int fd, fd_set *set);     /* 把一个 fd 加进集合 */
void FD_ZERO(fd_set *set);            /* 清空整个集合 */

select 的返回值素材里空着，这里补齐：返回就绪的 fd 总数，返回 0 表示超时、一个都没就绪，返回 -1 表示出错（错误码在 errno）。（这是 POSIX 语义，与内核版本无关。）

驱动侧要提供的是 poll 方法，它在 file_operations 里的原型是：

c
unsigned int (*poll)(struct file *, struct poll_table_struct *);

课上给的实现只有十几行，但每一行都有讲究：

c
static unsigned int hello_poll(struct file *filep, struct poll_table_struct *wait)
{
    poll_wait(filep, &hello_dev.queue, wait);   /* 把本驱动的等待队列挂到 poll 表上 */

    if (hello_dev.len != 0) {
        return POLLIN | POLLRDNORM;             /* 有数据可读 */
    } else {
        return POLLOUT | POLLWRNORM;            /* 原注释写「可写」 */
    }
}

poll_wait 是这件事的核心，课上给它的注释是「添加一个等待队列到 poll_table 结构体里面」。它不睡、不阻塞，只做登记：把你的等待队列挂到这次 select 的监听表上，等 select 那边睡下去，你的 wake_up 才能把它叫醒。

状态掩码的含义：

掩码 含义
POLLIN 有普通数据可读
POLLRDNORM 有普通数据可读（POLLIN 的细分）
POLLOUT 可以写
POLLWRNORM 可以写（POLLOUT 的细分）
POLLERR / POLLHUP 设备出错 / 挂断，驱动不主动返回，由内核补

（POLLIN、POLLRDNORM、POLLOUT、POLLWRNORM 在 3.x 的 include/uapi/asm-generic/poll.h 中定义；具体数值未验证。）

这段代码课上有两处当场被指出来的毛病，抄速记时容易一起抄错：

第一，else 分支的注释写「可写」，但它判断的是 len == 0，意思是没数据可读。这两件事不是一回事——没数据可读，不代表设备可写；只有在设备同时具备读写能力、且缓冲区空着可写时，这个 else 才成立。严谨的写法是把可读和可写分别判断，可写条件单独写一个 if，而不是拿「不可读」当「可写」。

第二，两个分支互斥的写法意味着 poll 一次只返回一种能力。真实设备常常同时可读可写，返回值应当按位或累加，而不是二选一。

十二、五种 IO 模型的对照 #

素材里只列了四种：阻塞、非阻塞、多路复用、异步。少的那一种是信号驱动 IO，它正好在异步通知那一节讲到了实现，属于漏列，这里按五种补齐：

# 模型 第一阶段（等数据） 第二阶段（拷贝） 同步/异步
1 阻塞 IO 进程睡，等数据就绪 进程睡，等拷贝完成 同步
2 非阻塞 IO 立刻返回 -EAGAIN，应用自己轮询 拷贝时进程参与 同步
3 IO 多路复用（select/poll） 进程睡在 select 上，等任一 fd 就绪 拷贝时进程参与 同步
4 信号驱动 IO（SIGIO） 不睡，注册信号后干别的，数据就绪时收信号 拷贝时进程参与 同步
5 异步 IO（AIO） 不睡 拷贝也由内核完成，完成后通知 异步

判据只有一条，课上重复过：第二阶段要不要进程自己动手拷。要，就是同步；不要，才是异步。所以前四种全归同步，只有第五种是真异步——这个结论反直觉，但卡在判据上就清楚了。

第 4 种在驱动侧叫异步通知，课上给的实现分应用层和驱动层两块。

应用层三步，顺序不能乱：

c
/* 1. 捕捉 SIGIO 信号 */
void sig_handler(int signo)
{
    /* 有数据了，在这儿读 */
}

signal(SIGIO, sig_handler);        /* 注册处理函数 */

/* 2. 指定进程为文件的属主，让设备知道该给谁发信号 */
fcntl(fd, F_SETOWN, getpid());

/* 3. 在设备上打开 FASYNC 标志 */
oflags = fcntl(fd, F_GETFL);
oflags = oflags | FASYNC;
fcntl(fd, F_SETFL, oflags);

第一步的名字在素材里是错的：声明的是 sig_handler，注册时写的是 handler，两个名字对不上，编译就过不去。这类错在速记里很常见，抄的时候顺手改了就行。

信号的处置方式课上点过三种：默认、忽略、捕获。默认处置对 SIGIO 是「忽略」，所以不做第一步就永远收不到通知——这是「为什么我的驱动不发信号」最常见的原因之一。捕获既可以用 signal()，也可以用 sigaction()；sigaction 能带 SA_RESTART 之类的标志，signal 的可移植性和语义在不同标准里不一样。素材只留了 sigaction 一个词，没展开。

还有一层联系：进程如果正阻塞在 read 里（wait_event_interruptible 的那条路），收到被捕获的信号会被打断，wait_event_interruptible 返回 -ERESTARTSYS。这跟第七节信号量那段的返回值处理是同一套机制。

驱动层要提供 fasync 方法：

c
int (*fasync)(int, struct file *, int);

实现只有一行，把活交给 fasync_helper：

c
static int hello_fasync(int fd, struct file *filp, int mode)
{
    return fasync_helper(fd, filp, mode, &async_queue);   /* 处理标志的变更 */
}

fasync_helper 干的事是把「谁要收信号」这个信息维护进 async_queue。应用层那三步里的 F_SETFL 触发的就是这个回调，mode 带进来的就是 FASYNC 开关的变化。

有数据的时候发信号：

c
kill_fasync(&async_queue, SIGIO, POLL_IN);

POLL_IN 表示「可读」这个事件，跟 poll 里的 POLLIN 是同一套语义，一个给信号用，一个给多路复用用。

（fasync_helper、kill_fasync、struct fasync_struct 在 3.x 可用；file_operations 中 fasync 的位置随版本变化，3.x 里在 .fasync 字段，未逐版本验证。）

十三、课堂踩坑记录 #

这一节收的是课上真正踩出来的东西，按现象归拢：

# 现象 根因 处理
1 两个进程同时打开成功 if (flag != 1) 与 flag = 0 之间被抢占 换原子操作或锁
2 flag 计数一路变负，设备再也打不开 失败分支只减不加，忘了 atomic_inc 回补 失败路径必须还原计数
3 加锁后仍然两个进程进得去 只锁了赋值那一行，判断在锁外 判断和赋值一起进临界区
4 release 里改了 flag 却不加锁 同一份资源写了两套代码，只有一处加锁 release 也加同一把锁
5 系统整个卡死，ps 看到进程 D 状态杀不掉 用了 down() 不可中断睡眠 换 down_interruptible
6 加锁以后系统整体卡住不动 持自旋锁调了会睡的函数（copy_to_user、kmalloc(GFP_KERNEL)） 移出临界区
7 中断一来就死锁 中断处理函数抢了进程手里的自旋锁 spin_lock_irqsave
8 一份数据来了，N 个进程全醒 惊群，wake_up 叫醒全部 独占等待 WQ_FLAG_EXCLUSIVE
9 驱动写完了不报错，应用收不到信号 没做 F_SETOWN，或没做 F_SETFL 打 FASYNC 补应用层三步
10 编不过，报在全角分号上 速记把 ; 抄成 ； 手敲，别粘贴
11 select 永远不返回 nfds 填成了 fd 个数而不是最大值加一 改成 maxfd + 1
12 poll 报告可读但 read 返回 -EAGAIN poll 判断条件与 read 的判断条件不一致 两处共用同一个状态位

第 6 条值得单独说。自旋锁的临界区里有一份「禁止调用清单」，课上点名过：copy_to_user、copy_from_user、kmalloc 带 GFP_KERNEL 的版本、msleep、schedule。判据就一个：这个函数会不会睡。会睡的，一律搬出临界区。搬不出去的，说明临界区划错了，得重新划。

第 10 条是速记里真实存在的破损。素材里那句 oflags = oflags | FASYNC； 用了个全角分号，粘贴进编辑器后，编译器报的错和分号本身看不出关系。同类破损还有一处：atomic_dec_and_test() 后面跟着的说明里混进了「（注意没有加）」，读不通，实际是抄写时把 atomic_inc_and_test 那行漏了。清理碎片时顺手改掉，但要知道原文长什么样，不然下次还认不出来。

课上留过一个综合练习，把并发和 IO 两条线并到一起：

一个应用程序同时控制三个驱动。一个驱动控制灯，一个驱动控制蜂鸣器鸣叫，一个驱动用于接收字符（write /dev/hello）。收到字符 1，灯亮；收到字符 p，蜂鸣器叫。

这个题的用意是把本节的东西串起来：三个设备要同时盯，靠 poll 或 select；字符从应用层 write 进驱动，读侧要用等待队列把「有字符可读」这件事告诉应用；不走多路复用就只能用信号驱动，三个设备都要做 fasync、三个 SIGIO 处理函数，还得区分信号是谁发的——这一点比 poll 麻烦得多，这类场景 poll 更顺手。

十四、易错点速查 #

# 易错点 正确做法
1 用普通变量做「只能开一次」的判断 判断和修改必须原子，用 atomic_dec_and_test 或锁
2 原子操作失败分支不回补计数 atomic_inc 还回去
3 认为单 CPU 不会并发 内核可抢占时照样会
4 用 local_irq_disable 解决多核竞态 它只关本地 CPU，多核要自旋锁
5 进临界区用 local_irq_disable、出来用 local_irq_enable 用 local_irq_save / local_irq_restore，恢复而非打开
6 自旋锁里调 copy_to_user 搬出临界区，或改用信号量
7 自旋锁递归加同一把锁 不允许，会自己等自己
8 进程与中断共享资源时只 spin_lock 用 spin_lock_irqsave 系列
9 wait_event 与 wake_up_interruptible 混配 可中断配可中断，不可中断配 wake_up
10 忽略 wait_event_interruptible 的返回值 非 0 说明被信号打断，要返回 -ERESTARTSYS
11 把「唤醒」当成「条件成立」 唤醒后要重查 condition
12 以为 wake_up 只叫醒一个 它叫醒全部，独占等待才限量
13 select 的 nfds 填成 fd 个数 最大值 + 1
14 在中断上下文里用信号量或 mutex 会睡的机制一律不能在中断里用
15 信号驱动只写 signal() 不做 F_SETOWN 三步齐全，缺一步收不到信号
16 poll 的返回值和 read 的判断不一致 两处共用同一个状态位
