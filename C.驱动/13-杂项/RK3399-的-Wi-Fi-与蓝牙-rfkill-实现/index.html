上一篇讲了 rfkill 框架本身。这一篇看 Rockchip 在 RK3399 上怎么用它，对象是 NanoPC-T4 板子上的 AP6356（博通 BCM4356，Wi-Fi + 蓝牙二合一）。

先把结论摆出来，因为这是读这两个驱动时最反直觉的一点：

rfkill-wlan.c 里没有任何 rfkill 代码。 它一个 struct rfkill 都没分配，纯粹是个"给 Wi-Fi 芯片上电"的 platform 驱动，名字里的 rfkill 是历史遗留。

rfkill-bt.c 才是真的 rfkill 驱动。 它走完了 rfkill_alloc + rfkill_register + set_block 全套。

两个文件还互相调彼此的初始化函数，所以代码分布更加反直觉。这一篇按这个真实结构讲。

一、两个文件怎么互相挂钩 #

先看目录。这两个文件在 5.2.8 官方内核里并不存在，是从 Rockchip 的 4.19 SDK 里搬过来的：

text
net/rfkill/
├── core.c            内核自带的框架
├── input.c           内核自带（弃用）
├── rfkill-gpio.c     内核自带的通用 GPIO 驱动
├── rfkill-wlan.c     ← Rockchip 加的
└── rfkill-bt.c       ← Rockchip 加的

打开 rfkill-wlan.c 会发现一个奇怪之处：没有 module_init / module_exit。文件末尾只有：

c
int __init rfkill_wlan_init(void)
{
	LOG("Enter %s\n", __func__);
	return platform_driver_register(&rfkill_wlan_driver);
}

void __exit rfkill_wlan_exit(void)
{
	LOG("Enter %s\n", __func__);
	platform_driver_unregister(&rfkill_wlan_driver);
}

没有模块入口，这两个函数谁来调？

答案是 rfkill-bt.c 的模块入口和出口：

c
static int __init rfkill_rk_init(void)
{
	int ret;

	LOG("Enter %s\n", __func__);

	ret = rfkill_wlan_init();       /* 先注册 Wi-Fi 驱动 */
	if (ret)
		return ret;

	ret = platform_driver_register(&rfkill_rk_driver);
	if (ret)
		rfkill_wlan_exit();

	return ret;
}

static void __exit rfkill_rk_exit(void)
{
	platform_driver_unregister(&rfkill_rk_driver);
	rfkill_wlan_exit();
}

/* 只有这一个模块入口，注册两个 platform 驱动 */
module_init(rfkill_rk_init);
module_exit(rfkill_rk_exit);

所以 rfkill-bt.c 是主模块，rfkill-wlan.c 是被它带进来的。编译时两个文件编进同一个 .ko。

这个设计的坏处很直接：想让 Wi-Fi 单独工作，得把蓝牙驱动一起加载。好处也有一个：Wi-Fi 和蓝牙共用 AP6356 的电源域，上电时序得协同，放在一个模块里省了跨模块同步。

名字和实际情况的错位值得记一笔：rfkill-bt.c 编出来的模块叫 rfkill_bt，但它实际管着 Wi-Fi 和蓝牙两个平台的初始化。

二、硬件：AP6356 在 NanoPC-T4 上怎么接 #

分析驱动之前先把接线搞清楚，否则看不懂设备树里的那些 GPIO。

2.1 电源 #

电源 电压 来源
VBAT 3.0 ~ 4.8V VCC3V3_SYS，由 12V 主电源经 NB680GD 稳压得到
VDDIO 1.8V RK808 PMIC 第 61 脚

VBAT 是给射频功放供的，VDDIO 是 IO 电平参考。两个都要在，缺一个芯片就不工作。

2.2 时钟 #

AP6356 需要一个外部低功耗时钟（LPO），接的是 RTC_CLKO_WIFI，来自 RK808 第 67 脚 CLK32KOUT2。32.768kHz，用于蓝牙低功耗模式下的休眠唤醒计时。

设备树里 clocks = <&rk808 1> 就是这个。

2.3 控制引脚 #

RK3399 与 AP6356 之间能动的 GPIO 就这几个：

信号 RK3399 引脚 方向 作用
WL_REG_ON GPIO0_B2 SoC → 模块 Wi-Fi 上电/复位
BT_REG_ON GPIO0_B1 SoC → 模块 蓝牙上电/复位
BT_WAKE GPIO2_D2 SoC → 模块 主机告诉蓝牙"别睡"
BT_HOST_WAKE GPIO0_A4 模块 → SoC 蓝牙告诉主机"有事找你"
WIFI,host_wake_irq GPIO0_A3 模块 → SoC Wi-Fi 告诉主机"有事找你"
UART_CTS_N GPIO2_C3 模块 → SoC 蓝牙串口流控（可复用成 GPIO）

注意 WL_REG_ON 和 BT_REG_ON 都在 GPIO0 上，紧挨着（B2 / B1）。

有一件事在这张表里看不出来但很关键：WL_REG_ON（GPIO0_B2）在两个驱动里都没出现。它不在 rfkill-wlan.c 里，被 sdio_pwrseq 框架接管了。第五节展开。

三、设备树：两个 platdata 节点 #

3.1 Wi-Fi 节点 #

dts
wireless-wlan {
	compatible = "wlan-platdata";
	rockchip,grf = <&grf>;
	wifi_chip_type = "ap6356";
	sdio_vref = <1800>;
	WIFI,host_wake_irq = <&gpio0 3 GPIO_ACTIVE_HIGH>; /* GPIO0_A3 */
	status = "okay";
};

驱动侧的匹配表：

c
static struct of_device_id wlan_platdata_of_match[] = {
	{ .compatible = "wlan-platdata" },
	{}
};
MODULE_DEVICE_TABLE(of, wlan_platdata_of_match);

static struct platform_driver rfkill_wlan_driver = {
	.probe  = rfkill_wlan_probe,
	.remove = rfkill_wlan_remove,
	.driver = {
		.name = "wlan-platdata",
		.of_match_table = of_match_ptr(wlan_platdata_of_match),
	},
};

节点名 wireless-wlan 和 compatible wlan-platdata 不是一回事。 匹配只看 compatible，节点名随便叫什么都行。老资料里写"只有 wireless-wlan 节点的 compatible 与驱动匹配表一致"，容易让人以为节点名也参与匹配，其实不参与。

wifi_chip_type = "ap6356" 只是个标识串，驱动用它决定加载哪套参数（不同芯片的 SDIO 时序、天线配置不同）。

WIFI,host_wake_irq 是 Wi-Fi 唤醒主机的引脚。这个中断不在 rfkill-wlan.c 里申请，而是由 SDIO/brcmfmac 驱动处理。

3.2 蓝牙节点 #

dts
wireless-bluetooth {
	compatible = "bluetooth-platdata";
	clocks = <&rk808 1>;
	clock-names = "ext_clock";
	uart_rts_gpios = <&gpio2 19 GPIO_ACTIVE_LOW>; /* GPIO2_C3 */
	pinctrl-names = "default", "rts_gpio";
	pinctrl-0 = <&uart0_rts>;
	pinctrl-1 = <&uart0_gpios>;
	BT,reset_gpio    = <&gpio0 9 GPIO_ACTIVE_HIGH>;  /* GPIO0_B1 */
	BT,wake_gpio     = <&gpio2 26 GPIO_ACTIVE_HIGH>; /* GPIO2_D2 */
	BT,wake_host_irq = <&gpio0 4 GPIO_ACTIVE_HIGH>;  /* GPIO0_A4 */
	status = "okay";
};

属性逐个说：

属性 含义
clocks / clock-names 外部时钟源，指向 rk808 的 1 号时钟，名字 ext_clock
uart_rts_gpios 把 UART_CTS_N（GPIO2_C3）当 GPIO 用时的描述，低有效
pinctrl-names 两套引脚状态：default 和 rts_gpio
pinctrl-0 default 状态把 GPIO2_C3 复用成 UART RTS 功能
pinctrl-1 rts_gpio 状态把 GPIO2_C3 复用成普通 GPIO
BT,reset_gpio BT_REG_ON，高有效。高电平开蓝牙，低电平关
BT,wake_gpio BT_WAKE，高有效。主机 → 蓝牙的唤醒线
BT,wake_host_irq BT_HOST_WAKE，高有效。蓝牙 → 主机，配成中断

pinctrl 两套状态是为了流控切换：正常跑数据时 GPIO2_C3 是 UART 的 RTS 引脚，需要用 GPIO 手动控制时切到 rts_gpio 状态。

3.3 BT_WAKE 的语义 #

这根线的逻辑容易反着记，按设备树注释原文：

BT_WAKE 电平 含义
高 蓝牙不能睡，或者必须醒来
低 蓝牙可以睡（睡不睡它自己决定）

关键一条：主机每次发数据前都要拉高 BT_WAKE。低电平只是"允许睡"，不是"命令睡"，所以蓝牙可能还醒着。但反过来，一直保持低电平，蓝牙迟早会自主进入低功耗。

四、Wi-Fi 驱动：一个名不副实的文件 #

rfkill_wlan_probe() 全文看完，会发现它和 rfkill 框架完全无关：

c
static int rfkill_wlan_probe(struct platform_device *pdev)
{
	struct rfkill_wlan_data *rfkill;
	struct rksdmmc_gpio_wifi_moudle *pdata = pdev->dev.platform_data;
	int ret = -1;

	/* 1. 注册一个 class，名字 rkwifi */
	class_register(&rkwifi_power);

	/* 2. 没有平台数据就从设备树解析 */
	if (!pdata) {
		pdata = kzalloc(sizeof(*pdata), GFP_KERNEL);
		if (!pdata)
			return -ENOMEM;

		ret = wlan_platdata_parse_dt(&pdev->dev, pdata);
		if (ret < 0) {
			LOG("%s: No platform data specified\n", __func__);
			return ret;
		}
	}

	/* 3. 分配驱动私有数据 */
	rfkill = kzalloc(sizeof(*rfkill), GFP_KERNEL);
	if (!rfkill)
		goto rfkill_alloc_fail;

	rfkill->pdata = pdata;
	g_rfkill = rfkill;

	/* 4. 如果配了 VBAT / RESET 引脚，申请它们 */
	if (!pdata->mregulator.power_ctrl_by_pmu) {
		ret = rfkill_rk_setup_gpio(&pdata->vbat_n, wlan_name, "wlan_vbat");
		if (ret)
			goto fail_alloc;

		ret = rfkill_rk_setup_gpio(&pdata->reset_n, wlan_name, "wlan_reset");
		if (ret)
			goto fail_alloc;
	}

	/* 5. 初始化唤醒锁 */
	wake_lock_init(&rfkill->wlan_irq_wl, WAKE_LOCK_SUSPEND, "rfkill_wlan_wake");

	/* 6. 给 Wi-Fi 芯片上电 */
	rfkill_set_wifi_bt_power(1);

	if (pdata->wifi_power_remain)
		rockchip_wifi_power(1);

	fb_register_client(&rfkill_wlan_fb_notifier);

	return 0;

fail_alloc:
	kfree(rfkill);
rfkill_alloc_fail:
	kfree(pdata);
	g_rfkill = NULL;
	return ret;
}

整段没有 rfkill_alloc、没有 struct rfkill、没有 set_block。

它做的唯一有价值的事是：如果 Wi-Fi 芯片的电源和复位引脚接在 SoC 的 GPIO 上，就在 probe 时把芯片拉起来。仅此而已。

所以"Wi-Fi 的 rfkill"这个说法在这个平台上是不准确的。真正管 Wi-Fi 开关的是 cfg80211 / brcmfmac，它们通过自己的机制响应 rfkill 框架的全局状态。

4.1 私有数据结构 #

c
struct rfkill_wlan_data {
	struct rksdmmc_gpio_wifi_moudle *pdata;
	struct wake_lock wlan_irq_wl;
};

只有两个成员：

  • pdata：指向平台数据，下一节展开；
  • wlan_irq_wl：Wi-Fi 中断唤醒锁。Wi-Fi 模块有中断要处理时，防止系统进入休眠。

wake_lock 这套 API 从来没进过主线内核（一直待 android-3.x 分支），PC 上的发行版内核里没有。用 Rockchip SDK 才有。

4.2 平台数据：struct rksdmmc_gpio_wifi_moudle #

c
struct rksdmmc_gpio_wifi_moudle {
	int  sdio_vol;              /* SDIO 参考电压 */
	bool vref_ctrl_enble;
	bool wifi_power_remain;     /* 是否保持 Wi-Fi 供电 */
	struct rksdmmc_pmu  mregulator;   /* 主电源，走 PMIC */
	struct rksdmmc_pmu  ioregulator;  /* IO 电源，走 PMIC */
	struct rksdmmc_gpio vbat_n;       /* 模块电源控制 */
	struct rksdmmc_gpio power_n;      /* 电源使能 */
	struct rksdmmc_gpio reset_n;      /* 复位 */
	struct rksdmmc_gpio vddio;        /* IO 电压控制 */
	struct rksdmmc_gpio bgf_int_b;
	struct rksdmmc_gpio wifi_int_b;   /* Wi-Fi 中断 */
	struct rksdmmc_gpio gps_sync;
	struct rksdmmc_gpio ANTSEL2;      /* 天线选择 2 */
	struct rksdmmc_gpio ANTSEL3;      /* 天线选择 3 */
	struct rksdmmc_gpio GPS_LAN;
	struct regmap *grf;               /* 控制寄存器的 regmap */
	struct clk    *ext_clk;           /* 外部时钟源 */
};

（moudle 是 Rockchip 自己的拼写错误，保留原样，搜代码时要注意。）

字段虽多，实际用得上的只有 vbat_n、reset_n、wifi_int_b。在 NanoPC-T4 上：

  • reset_n 和 vbat_n 都没配，所以 rfkill_rk_setup_gpio 直接返回 0 什么都不做；
  • mregulator.power_ctrl_by_pmu 是 false，走的是上面的 GPIO 分支。

也就是说这块板子的 Wi-Fi 上电完全靠 WL_REG_ON，而已知 WL_REG_ON 不在这里。

4.3 WL_REG_ON 去哪了：sdio_pwrseq #

设备树里没配 WL_REG_ON，是因为它在 sdio_pwrseq 那个节点里：

dts
sdio-pwrseq {
	compatible = "mmc-pwrseq-simple";
	clocks = <&rk808 1>;
	clock-names = "ext_clock";
	pinctrl-names = "default";
	pinctrl-0 = <&wifi_enable_h>;
	reset-gpios = <&gpio0 10 GPIO_ACTIVE_LOW>;  /* GPIO0_B2 = WL_REG_ON */
};

mmc-pwrseq-simple 是 MMC 子系统的通用上电时序驱动。它的做法是：在 SDIO 控制器 probe 之前，按 reset-gpios 和 clocks 的配置把芯片拉起来，等时钟稳定，再交给 SDIO 去枚举。

为什么放这儿而不放 rfkill-wlan.c？ 因为 Wi-Fi 芯片挂在 SDIO 上，必须先上电才能被 SDIO 枚举到。而 rfkill-wlan 这个 platform 驱动的 probe 时机不保证在 SDIO 枚举之前。放进 pwrseq 就由 MMC 核心保证了顺序。

所以这块板子上的上电链路是：

text
sdio-pwrseq (GPIO0_B2 拉高) → 芯片上电
       ↓
SDIO 控制器枚举 → 发现 Wi-Fi 芯片 → brcmfmac 加载固件
       ↓
rfkill-wlan probe → 检查 vbat/reset（都没配，什么都不做）
       ↓
bluetooth probe → 拉 BT_REG_ON 给蓝牙上电

Wi-Fi 的上电由 pwrseq 负责，蓝牙的上电由 rfkill-bt.c 负责。两个芯片在同一个封装里，但上电是分开管的两条路。

五、蓝牙驱动：这次真的用了 rfkill #

rfkill_rk_probe() 是完整实现。九步：

# 动作
1 分配 rfkill_rk_platform_data，调 bluetooth_platdata_parse_dt() 从设备树填
2 在 /proc/bluetooth/sleep/ 下建 lpm、btwrite 两个文件
3 为电源、复位、RTS 引脚申请 GPIO
4 初始化 wake_lock
5 为 BT_HOST_WAKE 申请 GPIO 并申请中断
6 rfkill_alloc() 分配 rfkill 设备，操作集设为 rfkill_rk_ops
7 rfkill_register() 注册
8 初始化延时工作 bt_sleep_delay_work
9 拉 BT_REG_ON 给蓝牙上电

代码骨架：

c
static int rfkill_rk_probe(struct platform_device *pdev)
{
	struct rfkill_rk_data *rfkill;
	struct rfkill_rk_platform_data *pdata = pdev->dev.platform_data;
	int ret = -1;

	/* 1. 从设备树解析平台数据 */
	if (!pdata) {
		pdata = kzalloc(sizeof(*pdata), GFP_KERNEL);
		if (!pdata)
			return -ENOMEM;
		ret = bluetooth_platdata_parse_dt(&pdev->dev, pdata);
		if (ret < 0) {
			kfree(pdata);
			return ret;
		}
	}

	rfkill = kzalloc(sizeof(*rfkill), GFP_KERNEL);
	if (!rfkill)
		goto fail;

	rfkill->pdev   = pdev;
	rfkill->pdata  = pdata;
	g_rfkill       = rfkill;

	/* 2. 建 /proc 节点 */
	bluesleep_init();   /* 内部 proc_mkdir + create_proc_entry */

	/* 3. 申请 GPIO */
	ret = rfkill_rk_setup_gpio(pdev, &pdata->poweron_gpio, pdata->name, "poweron");
	if (ret)
		goto fail;

	ret = rfkill_rk_setup_gpio(pdev, &pdata->reset_gpio, pdata->name, "reset");
	if (ret)
		goto fail;

	rfkill_rk_setup_gpio(pdev, &pdata->rts_gpio, pdata->name, "rts");

	/* 4. 唤醒锁 */
	wake_lock_init(&rfkill->bt_irq_wl, WAKE_LOCK_SUSPEND, "rfkill_bt_wake");

	/* 5. 中断 */
	rfkill_rk_setup_wake_irq(rfkill);

	/* 6. 分配 rfkill 设备 */
	rfkill->rfkill_dev = rfkill_alloc(pdata->name, &pdev->dev,
					  pdata->type, &rfkill_rk_ops, rfkill);
	if (!rfkill->rfkill_dev) {
		ret = -ENOMEM;
		goto fail;
	}

	/* 7. 注册 */
	ret = rfkill_register(rfkill->rfkill_dev);
	if (ret < 0)
		goto fail;

	/* 8. 延时工作：用于自动睡眠 */
	INIT_DELAYED_WORK(&rfkill->bt_sleep_delay_work, rfkill_rk_delay_sleep_bt);

#ifdef CONFIG_BT_AUTOSLEEP
	rfkill->bt_sleep_delay_work.timeout = ...;
#endif

	/* 9. 上电 */
	if (gpio_is_valid(pdata->poweron_gpio.io))
		gpio_direction_output(pdata->poweron_gpio.io,
				      pdata->poweron_gpio.enable);

	if (gpio_is_valid(pdata->reset_gpio.io))
		gpio_direction_output(pdata->reset_gpio.io,
				      pdata->reset_gpio.enable);

	platform_set_drvdata(pdev, rfkill);
	return 0;

fail:
	/* 逐级回滚 */
	return ret;
}

5.1 平台数据结构 #

c
struct rfkill_rk_platform_data {
	char *name;                       /* 设备名，显示在 rfkill list 里 */
	enum rfkill_type type;            /* RFKILL_TYPE_BLUETOOTH */
	bool power_toggle;                /* 上电前是否要先给整个模块上电 */
	struct pinctrl *pinctrl;
	struct rfkill_rk_gpio  poweron_gpio;   /* VDDIO */
	struct rfkill_rk_gpio  reset_gpio;     /* BT_REG_ON */
	struct rfkill_rk_gpio  wake_gpio;      /* BT_WAKE */
	struct rfkill_rk_irq   wake_host_irq;  /* BT_HOST_WAKE */
	struct rfkill_rk_gpio  rts_gpio;       /* UART_CTS_N */
	struct clk *ext_clk;
};

power_toggle 是个开关：如果 Wi-Fi 和蓝牙共用一路电源（AP6356 就是这样），蓝牙上电前得先把整个模块的电给了。看 set_block 的实现能确认这一点。

5.2 驱动私有数据 #

c
struct rfkill_rk_data {
	struct rfkill_rk_platform_data *pdata;
	struct platform_device *pdev;
	struct rfkill *rfkill_dev;        /* 内核的 rfkill 设备 */
	struct wake_lock bt_irq_wl;       /* 中断唤醒锁 */
	struct delayed_work bt_sleep_delay_work;
	int irq_req;                      /* 中断是否已申请 */
};

rfkill_dev 是框架那边的对象，rfkill 这个名字被这个结构体占了，读代码时容易混。

六、set_block：唯一真正干活的回调 #

操作集只实现一个回调：

c
static const struct rfkill_ops rfkill_rk_ops = {
	.set_block = rfkill_rk_set_power,
};

c
static int rfkill_rk_set_power(void *data, bool blocked)
{
	struct rfkill_rk_data *rfkill = data;
	struct rfkill_rk_gpio *wake_host = &rfkill->pdata->wake_host_irq.gpio;
	struct rfkill_rk_gpio *poweron   = &rfkill->pdata->poweron_gpio;
	struct rfkill_rk_gpio *reset     = &rfkill->pdata->reset_gpio;
	bool toggle = rfkill->pdata->power_toggle;

	if (!blocked) {                    /* blocked=false → 开启蓝牙 */
		if (toggle) {
			rfkill_set_wifi_bt_power(1);   /* 先把整个模块的电给了 */
			msleep(100);
		}

		rfkill_rk_sleep_bt(BT_WAKEUP);     /* 先唤醒，避免它睡着不理人 */

		if (gpio_is_valid(wake_host->io)) {
			gpio_direction_output(wake_host->io, 1);
			msleep(20);
		}

		if (gpio_is_valid(reset->io)) {
			gpio_direction_output(reset->io, !reset->enable);
			msleep(100);
			gpio_direction_output(reset->io, reset->enable);
		}

		if (gpio_is_valid(poweron->io))
			gpio_direction_output(poweron->io, poweron->enable);

	} else {                           /* blocked=true → 关闭蓝牙 */
		if (gpio_is_valid(reset->io))
			gpio_direction_output(reset->io, !reset->enable);

		if (gpio_is_valid(poweron->io))
			gpio_direction_output(poweron->io, !poweron->enable);
	}

	return 0;
}

开蓝牙的顺序值得记：先上电 → 再唤醒 → 再复位 → 最后拉电源使能。

复位那一段是标准的低脉冲：先拉低 100ms，再拉高。低脉冲期间芯片处于复位态，拉高后开始跑内部固件。100ms 不是随便给的，BCM 芯片的固件启动时间在数据手册里有标，短了会初始化失败。

关蓝牙只做了两件事：拉低 BT_REG_ON、拉低电源使能。没有握手协商，rfkill 的语义就是直接切断。

七、BT_HOST_WAKE：蓝牙怎么叫醒主机 #

BT_HOST_WAKE（GPIO0_A4）配成中断，处理函数很短：

c
static irqreturn_t rfkill_rk_wake_host_irq(int irq, void *dev_id)
{
	struct rfkill_rk_data *rfkill = dev_id;

	/* 保持系统 10 秒内不进入休眠，避免蓝牙数据丢失 */
	wake_lock_timeout(&rfkill->bt_irq_wl,
			  msecs_to_jiffies(BT_IRQ_WAKELOCK_TIMEOUT));
	return IRQ_HANDLED;
}

BT_IRQ_WAKELOCK_TIMEOUT 是 10000ms。

逻辑是：蓝牙有数据要给主机，拉高 BT_HOST_WAKE → 触发中断 → 驱动持锁 10 秒 → 系统在这 10 秒内不会进 suspend → 上层有时间把数据取走 → 锁超时自动释放。

这是 Android 时代典型的 wake_lock 用法。主线内核的等价物是 pm_wakeup_event() / pm_stay_awake()，语义更细（能区分 wakeup source 和事件计数），但没有 wake_lock 那么简单直接。

八、/proc/bluetooth/sleep：一个半死的接口 #

probe 里创建了 /proc/bluetooth/sleep/ 目录，下面两个文件：lpm 和 btwrite。

8.1 lpm：完全没实现 #

c
static ssize_t bluesleep_read_proc_lpm(struct file *file, char __user *buffer,
				       size_t count, loff_t *data)
{
	return sprintf(buffer, "unsupported to read\n");
}

static ssize_t bluesleep_write_proc_lpm(struct file *file,
					const char __user *buffer,
					size_t count, loff_t *data)
{
	return count;    /* 什么都不做 */
}

读只会告诉你"不支持读"，写直接返回成功但什么也不做。这个接口是留给"蓝牙低功耗模式"的，注释说没支持。

顺带一个真实 bug：sprintf(buffer, ...) 里的 buffer 是 char __user *，用户态指针。在核心里直接 sprintf 到用户地址是错的，正确做法是 copy_to_user()。在 ARM 上因为内核能直接访问用户空间（set_fs 还没删的时代）它"能工作"，但这是把两个地址空间混用，换个架构或开了 HARDENED_USERCOPY 就会出事。

8.2 btwrite：语义绕了三个弯 #

c
static ssize_t bluesleep_write_proc_btwrite(struct file *file,
					    const char __user *buffer,
					    size_t count, loff_t *data)
{
	char b;

	if (count < 1)
		return -EINVAL;

	if (copy_from_user(&b, buffer, 1))
		return -EFAULT;

	if (b != '0')
		rfkill_rk_sleep_bt(BT_WAKEUP);
	else
		rfkill_rk_sleep_bt(BT_SLEEP);

	return count;
}

看起来正常：写非 0 就唤醒，写 0 就睡眠。但配合宏定义一看就出问题：

c
#define BT_SLEEP   true
#define BT_WAKEUP  false

BT_WAKEUP 是 false，BT_SLEEP 是 true。 名字和值反着。

再往下：

c
static inline void rfkill_rk_sleep_bt_internal(struct rfkill_rk_data *rfkill,
					       bool sleep)
{
	struct rfkill_rk_gpio *wake = &rfkill->pdata->wake_gpio;

	if (!sleep) {          /* 只有 sleep == false 才做事 */
		if (rfkill_rk_setup_gpio(rfkill->pdev, wake,
					 rfkill->pdata->name, "wake") != 0)
			return;

		gpio_direction_output(wake->io, wake->enable);    /* 拉高 */
		usleep_range(10, 20);
		gpio_direction_output(wake->io, !wake->enable);   /* 拉低 */

		gpio_free(wake->io);
	}
}

连起来看，实际行为是：

写入 传入 sleep 值 实际动作
1（非 '0'） BT_WAKEUP false 拉高 10~20μs 再拉低，一个唤醒脉冲
0 BT_SLEEP true if (!sleep) 不成立，什么都不做

所以这个接口的真实行为是：

  • 写非 0 = 给 BT_WAKE 一个高电平脉冲（高 10~20μs，然后回低）。脉冲结束后引脚是低电平，蓝牙被通知"有事"，之后可以继续睡。
  • 写 0 = 完全没反应。

这解释了测试章节里那句"echo 1 > btwrite 会将 AP6536 的 BT_WAKE 引脚拉低"。观察到的确实是最终的低电平，但那是一次脉冲的尾巴，不是直接拉低。

而且 bt_sleep_delay_work（延时工作）最终调的也是 rfkill_rk_sleep_bt_internal(rfkill, BT_SLEEP)，也就是永远不做事。所以 CONFIG_BT_AUTOSLEEP 那条自动休眠路径是死的。

读这段代码的教训：看到 #define XXX_SLEEP true 这种"名字是动作、值是布尔"的组合，必须一路跟到 if 条件里，否则会把语义完全搞反。这个驱动里至少有三层嵌套的反转（宏名 → 函数参数名 → if (!sleep)）。

8.3 gpio_free 在热路径里 #

rfkill_rk_sleep_bt_internal 每次调用都 rfkill_rk_setup_gpio() 申请 + gpio_free() 释放同一个 GPIO。

这个写法效率很低（申请/释放要走 gpiolib 的链表和锁），但它有个副作用是"安全的"：如果这个 GPIO 已经被别的驱动申请了，setup 失败就直接返回，不会误操作。

更好的做法是 probe 时申请一次，之后只改方向。但厂商代码这么写也说明他们吃过"重复申请"的亏。

九、验证 #

9.1 设备注册情况 #

bash
$ ls /sys/class/rfkill/
rfkill0  rfkill1

$ cat /sys/class/rfkill/rfkill0/name
bt_default

$ cat /sys/class/rfkill/rfkill0/type
bluetooth

rfkill0 就是 rfkill-bt.c 注册的蓝牙设备。

rfkill1（phy0，Wireless LAN）和 rfkill-wlan.c 完全无关，它是 brcmfmac 或 cfg80211 自己注册的。这一点在测试章节里也印证了：

bash
$ ls -l /sys/class/rfkill/rfkill1
rfkill1 -> ../../devices/platform/fe310000.sdhci/mmc_host/mmc0/mmc0:0001/...

路径落在 SDIO 主机控制器下面，说明它属于 SDIO 上的 Wi-Fi 芯片，不是 platform 设备的产物。

9.2 平台设备与驱动的链接关系 #

bash
$ ls -l /sys/devices/platform/wireless-bluetooth/
drivers  driver  subsystem  uevent  of_node  ...

$ ls -l /sys/bus/platform/drivers/rfkill_bt

按前一篇文章里的思路，这些链接合起来就是"目录是结构体、文件是成员、链接是指针"：

链接 指向 说明
of_node /sys/firmware/devicetree/base/wireless-bluetooth/ 设备树节点，属性和值都在这里
subsystem /sys/bus/platform 挂在 platform 总线下
driver /sys/bus/platform/drivers/rfkill_bt 匹配到的驱动
rfkill/rfkill0 同级的 rfkill 设备 rfkill_register() 建的子系统链接

9.3 开关测试 #

bash
$ rfkill block 0
$ rfkill list
0: bt_default: Bluetooth
	Soft blocked: yes
	Hard blocked: no

$ rfkill unblock 0

block 0 会走到 rfkill_rk_set_power(data, true)，拉低 BT_REG_ON，蓝牙断电。

也可以直接写 sysfs：

bash
echo 1 > /sys/class/rfkill/rfkill0/soft   # 等价于 block
echo 0 > /sys/class/rfkill/rfkill0/soft   # 等价于 unblock

注意 soft = 1 是"关"。老资料里写的 /sys/class/rfkill/rfkill0/state 接口已被内核删除，别再照着写。

9.4 用万用表验证 btwrite #

bash
$ echo 1 > /proc/bluetooth/sleep/btwrite
$ echo 0 > /proc/bluetooth/sleep/btwrite   # 无反应

量 GPIO2_D2：

  • 写 1 时能抓到一次短暂的高电平（10~20μs，普通万用表可能抓不到，得用示波器或逻辑分析仪），之后稳定在低电平；
  • 写 0 时电平不变。

这就是第八节分析出来的结论：只有"唤醒脉冲"，没有"睡眠"。

十、排错 #

现象 原因 排查
rfkill list 里没有蓝牙设备 bluetooth-platdata 节点没匹配上 dmesg | grep rfkill；ls /sys/bus/platform/drivers/rfkill_bt
有 rfkill0 但开关无反应 poweron_gpio / reset_gpio 都没配 看设备树；cat /sys/kernel/debug/gpio
Wi-Fi 起不来但蓝牙正常 sdio-pwrseq 的 reset-gpios 没配或引脚错 dmesg | grep mmc；查 GPIO0_B2
蓝牙上电了但枚举不到 UART_CTS_N 流控没配 检查 uart_rts_gpios 与 pinctrl-1
关闭后重新打开失败 复位低脉冲时间不够 确认 msleep(100) 存在
系统睡下去后蓝牙断连 BT_HOST_WAKE 中断没申请 cat /proc/interrupts | grep -i wake
写 btwrite 写 0 没反应 设计如此 见第八节，只有写非 0 才动作
/dev/rfkill 不存在 CONFIG_RFKILL 没开 zcat /proc/config.gz | grep RFKILL
加载模块报 Unknown symbol CONFIG_RFKILL 没开，或 wake_lock 缺失 主线内核没有 wake_lock，只能用 SDK

最后一条值得单说：wake_lock 从未进入主线内核。如果你的板子跑的是主线 Linux 而不是 Rockchip SDK，这两个文件根本编译不过，得把 wake_lock_* 换成 pm_wakeup_event() 一族。
