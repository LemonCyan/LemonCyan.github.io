笔记本上那个"飞行模式"按钮按下之后，Wi-Fi、蓝牙、WWAN 会一起断掉，而且有些机器上软件怎么都打不开。这套开关逻辑在内核里由 rfkill 子系统统一管，代码在 net/rfkill/。

驱动作者要做的只有一件事：把芯片的上电和断电动作挂到 rfkill 的回调上。剩下的状态记账、用户态通知、/dev/rfkill 事件流，框架全包了。

一、soft block 与 hard block #

rfkill 把"发射器关闭"分成两种，区别在于谁能解除。

hard block soft block
谁触发 物理开关、机身拨杆、固件 软件：rfkill block、sysfs 写属性
谁能否解除 只有硬件 软件随时可以
典型场景 笔记本侧面的无线开关、SIM 卡槽检测 飞行模式、用户主动关 Wi-Fi
硬件电源状态 可能仍上电 可能仍上电，也可能被驱动断掉

关键规则：hard block 优先。设备处于 hard block 时，软件层写任何东西都不会让发射器工作起来，set_block 回调也不会被调用（框架拦住了）。要让设备重新工作，只能去动那个物理开关。

两者是独立的两条线，最终状态是逻辑或：

text
发射器被阻塞  ⟺  hard blocked  ‖  soft blocked

所以一个设备可以同时处于两种 block，也可以只处于其中一种。

1.1 分清"阻塞状态"和"硬件电源" #

这里有个容易混的点：rfkill 的 blocked 不等于芯片断电。

soft block 的语义是"发射器不许工作"，具体怎么做由驱动决定：

  • 有的驱动真的去拉低电源使能引脚，芯片彻底断电；
  • 有的驱动只把射频前端关掉，数字部分仍在上电；
  • 有的驱动什么硬件都不动，只在软件层记账（比如 Wi-Fi 的 rfkill 通过通知 cfg80211 让协议栈停止发射）。

这也解释了一个常见困惑：rfkill block 1 之后 ifconfig 里 wlan0 消失了，但模块还在、设备节点还在。消失的是网络接口的注册，不是物理设备。

二、三个组成部分 #

组件 位置 职责
rfkill core net/rfkill/core.c 注册/注销、状态记账、sysfs、/dev/rfkill 事件、LED
rfkill input net/rfkill/input.c 把 input 子系统里的按键事件映射成全局开关。已弃用，由用户态策略取代
rfkill 驱动 net/rfkill/rfkill-gpio.c 或厂商自定义 实现 set_block，真正去操作硬件

core.c 底下还有 rfkill-gpio.c，一个通用驱动：只要设备树里给它一组 GPIO 和复位时序，它就能直接工作，不用自己写驱动。

text
net/rfkill/
├── core.c          核心：注册、状态、sysfs、/dev/rfkill
├── input.c         input 按键映射（弃用）
├── rfkill-gpio.c   通用 GPIO 驱动
├── Kconfig
└── Makefile

设备树里 compatible = "rfkill-gpio" 就能直接挂上这个通用驱动。厂商（比如 Rockchip）会自己写一份，因为需要处理时钟、regulator、SDIO 上电时序这些 rfkill-gpio 覆盖不了的东西。

三、用户态看到的两个入口 #

3.1 命令行工具 #

bash
$ rfkill list
0: bt_default: Bluetooth
	Soft blocked: yes
	Hard blocked: no
1: phy0: Wireless LAN
	Soft blocked: no
	Hard blocked: no

$ rfkill
ID TYPE      DEVICE      SOFT      HARD
 0 bluetooth bt_default blocked unblocked
 1 wlan      phy0       unblocked unblocked

ID 就是内核分配的 idx，后续 rfkill block <ID> / rfkill unblock <ID> 都用它。

有两个设备：蓝牙默认被软阻塞，Wi-Fi 正常。

bash
# 打开蓝牙
$ rfkill unblock 0

# 关掉 Wi-Fi
$ rfkill block 1

# 此时想手动启用会被内核拒绝
$ ifconfig wlan0 up
SIOCSIFFLAGS: Operation not possible due to RF-kill

最后那条报错很有辨识度：Operation not possible due to RF-kill。看到它就别去查驱动 probe 了，先 rfkill list 看是不是被阻塞。

bash
# 全部打开 / 全部关掉
rfkill unblock all
rfkill block all

3.2 sysfs 属性 #

每个已注册的 rfkill 设备在 /sys/class/rfkill/rfkillN/ 下有一组属性：

属性 权限 含义
name 只读 驱动给的名字
type 只读 wlan / bluetooth / wwan …
index 只读 就是 idx
hard 只读 1 表示被硬件阻塞
soft 可读写（0644） 1 表示被软件阻塞
persistent 只读 soft 状态是否有持久化初值

只有 soft 可写。 写它需要 CAP_NET_ADMIN：

bash
echo 1 > /sys/class/rfkill/rfkill0/soft   # 软阻塞（关）
echo 0 > /sys/class/rfkill/rfkill0/soft   # 解除（开）

注意语义方向：soft = 1 才是"关"，跟很多人的直觉相反。

3.3 老接口 state 已经删了 #

老资料里常写：

bash
echo 0 > /sys/class/rfkill/rfkill0/state   # 关
echo 1 > /sys/class/rfkill/rfkill0/state   # 开

这个 state 接口是 v2.6.22 时代的产物，ABI 文档里明确写着「计划 2014 年移除，因为它无法表达 soft 和 hard 同时阻塞的状态，但用户太多先留着」。现在内核里它已经不存在，只剩 soft 和 hard。

两套接口的语义是相反的：

关 开
老 state 0 1
新 soft 1 0

state 的三个取值来自 RFKILL_STATE_*：0 = 软阻塞，1 = 未阻塞，2 = 硬阻塞。而 soft 只有 0/1 二值。所以要判断"到底能不能用"，soft 和 hard 两个都得看。

在过渡期的内核（比如 5.2）上，先 ls /sys/class/rfkill/rfkill0/ 确认存在哪个，别照抄老脚本。

3.4 /dev/rfkill 是单个 misc 设备 #

/dev/rfkill 只有一个，由 rfkill core 在模块初始化时用 misc_register() 注册，不是每个 rfkillN 一个。

用户态（udev、NetworkManager、bluetoothd）打开它，读到的是一串 struct rfkill_event：

c
struct rfkill_event {
	__u32 idx;      /* rfkillN 的 N */
	__u8  type;     /* RFKILL_TYPE_* */
	__u8  op;       /* ADD / DEL / CHANGE / CHANGE_ALL */
	__u8  soft;
	__u8  hard;
} __attribute__((packed));

写这个文件可以改 soft 状态，和写 sysfs 的 soft 等价。现代用户态都走这条路，因为一次 read() 就能拿到全部事件的流，比轮询一堆 sysfs 文件高效。

rfkill_register() 内部只做 device_add()，不碰设备号，所以确实不会为每个设备创建 /dev/rfkillN。这两件事（单 misc 设备 + per-device sysfs 目录）要分开看。

四、struct rfkill #

c
struct rfkill {
	spinlock_t              lock;

	enum rfkill_type        type;

	unsigned long           state;
	unsigned long           hard_block_reasons;

	u32                     idx;

	bool                    registered;
	bool                    persistent;
	bool                    polling_paused;
	bool                    suspended;
	bool                    need_sync;

	const struct rfkill_ops *ops;
	void                    *data;

#ifdef CONFIG_RFKILL_LEDS
	struct led_trigger      led_trigger;
	const char              *ledtrigname;
#endif

	struct device           dev;
	struct list_head        node;

	struct delayed_work     poll_work;
	struct work_struct      uevent_work;
	struct work_struct      sync_work;
	char                    name[];
};

重点字段：

字段 作用
state 阻塞状态位图，见下
hard_block_reasons 硬阻塞的多个来源计数（不同来源各占一位）
idx 就是 rfkillN 里的 N，注册时分配
registered 是否已注册，防止重复注册
persistent soft 状态是否有初值，影响恢复时的行为
ops / data 回调表和驱动私有数据
dev 内嵌的 device，sysfs 目录靠它
name[] 柔性数组，名字直接跟在结构体后面

4.1 state 是位图，不是枚举 #

老资料里写「state 表示 rfkill 设备的状态，取值与 type 相关」，这是错的。state 和 type 没有关系，它是一组独立的位标志：

c
#define RFKILL_BLOCK_HW        BIT(0)   /* 硬阻塞 */
#define RFKILL_BLOCK_SW        BIT(1)   /* 软阻塞 */
#define RFKILL_BLOCK_SW_PREV   BIT(2)   /* 上一次的软状态，用于 uevent 通知 */
#define RFKILL_BLOCK_ANY       (HW | SW | SW_PREV)
#define RFKILL_BLOCK_SW_SETCALL BIT(31) /* 标记 set_block 已被调用过 */

所以一个设备的状态可以同时有 HW 和 SW 两位。判断"能不能用"要看 state & RFKILL_BLOCK_ANY 是否为 0。

SW_PREV 的存在是为了 uevent：驱动改状态时，框架需要知道"变了没有"，才能决定要不要通知用户态。

hard_block_reasons 是后来加的，支持多个独立的硬阻塞源各自占一位。比如一个开关加一个固件标志，任意一个生效就算阻塞，但想知道具体是哪个就得看这个字段。

4.2 enum rfkill_type #

c
enum rfkill_type {
	RFKILL_TYPE_ALL = 0,
	RFKILL_TYPE_WLAN,
	RFKILL_TYPE_BLUETOOTH,
	RFKILL_TYPE_UWB,
	RFKILL_TYPE_WIMAX,
	RFKILL_TYPE_WWAN,
	RFKILL_TYPE_GPS,
	RFKILL_TYPE_FM,
	RFKILL_TYPE_NFC,
	NUM_RFKILL_TYPES,
};

九种类型。RFKILL_TYPE_ALL 只用于"请求作用于全部设备"，不能用它注册单个设备，rfkill_alloc() 会检查这一点，传 ALL 或超过 NUM_RFKILL_TYPES 的值直接返回 NULL。

五、struct rfkill_ops：三个回调 #

c
struct rfkill_ops {
	void	(*poll)(struct rfkill *rfkill, void *data);
	void	(*query)(struct rfkill *rfkill, void *data);
	int	(*set_block)(void *data, bool blocked);
};
回调 什么时候实现 做什么
set_block 必须 按 blocked 开关发射器
poll 需要轮询时 定期查硬件状态，然后调 rfkill_set_*_state() 上报
query 硬件状态可能被 input 事件改变时 同上，但在框架设置 block 之前被调用

5.1 set_block 的两条纪律 #

c
static int my_set_block(void *data, bool blocked)
{
	struct my_dev *dev = data;

	if (blocked)
		disable_transmitter(dev);
	else
		enable_transmitter(dev);

	return 0;
}

一、blocked == true 表示"关"。 参数名是"被阻塞"，不是"被启用"。这个方向搞反，设备的行为就是反的。

二、硬阻塞时应当忽略并返回 0。 框架在硬阻塞生效期间根本不会调 set_block，但驱动如果自己维护了一份状态，要保证硬阻塞解除后能恢复到正确的软件状态。返回非 0 表示"这个操作失败了"，框架会把它记进日志，但不能回滚，因为硬件已经动过了。

5.2 poll 与 query 的区别 #

poll 是定时的：框架每隔 POLL_INTERVAL（5 秒）调一次，用来发现"硬件状态被外部改了"。

query 是按需的：用户在写 soft 之前，框架先问一次驱动"现在硬件是什么状态"，避免基于过期的信息做决定。

两者都不能直接改 state，必须通过 rfkill_set_hw_state() / rfkill_set_sw_state() 上报，让框架统一处理锁和通知。

六、注册链路 #

6.1 四步走 #

text
rfkill_alloc()       分配并初始化 struct rfkill
   ↓
rfkill_init_sw_state()  （可选）设置 soft 初值
   ↓
rfkill_register()    注册到设备模型，分配 idx，创建 sysfs
   ↓
rfkill_unregister()  注销
   ↓
rfkill_destroy()     释放

顺序不能乱：rfkill_init_sw_state() 必须在 rfkill_register() 之前调用，否则无效（注册时已经确定初值了）。rfkill_set_led_trigger_name() 同理。

6.2 rfkill_alloc #

c
struct rfkill *rfkill_alloc(const char *name,
                            struct device *parent,
                            const enum rfkill_type type,
                            const struct rfkill_ops *ops,
                            void *ops_data);

参数：

参数 填什么
name 设备名，会出现在 rfkill list 里。内核不拷贝这个字符串，所以不能传栈上的临时缓冲
parent 父设备，一般是平台设备的 &pdev->dev，决定 sysfs 里的层级
type 九种类型之一，不能是 RFKILL_TYPE_ALL
ops 回调表，set_block 必须非空
ops_data 驱动私有数据，会原样传给每个回调

内部做了三件事：

c
/* 省略参数检查 */
rfkill = kzalloc(sizeof(*rfkill) + strlen(name) + 1, GFP_KERNEL);

spin_lock_init(&rfkill->lock);
INIT_LIST_HEAD(&rfkill->node);
rfkill->type = type;
strcpy(rfkill->name, name);
rfkill->ops  = ops;
rfkill->data = ops_data;

dev = &rfkill->dev;
dev->class  = &rfkill_class;
dev->parent = parent;
device_initialize(dev);

return rfkill;

名字是内联分配在结构体尾部的（sizeof(*rfkill) + strlen(name) + 1），这就是 char name[] 柔性数组的用法，一次 kzalloc 搞定，省一次分配也省一个指针。

四处参数检查用 WARN_ON 实现，任一条命中就返回 NULL：ops 为空、ops->set_block 为空、name 为空、type 非法。

dev->class = &rfkill_class 决定了 sysfs 目录位置：

c
static struct class rfkill_class = {
	.name        = "rfkill",
	.dev_release = rfkill_release,
	.dev_groups  = rfkill_dev_groups,
	.dev_uevent  = rfkill_dev_uevent,
	.pm          = RFKILL_PM_OPS,
};

所以注册后设备出现在 /sys/class/rfkill/rfkillN/。

6.3 rfkill_register #

c
int rfkill_register(struct rfkill *rfkill)
{
	static unsigned long rfkill_no;    /* 静态，跨调用累加 */
	struct device *dev = &rfkill->dev;
	int error;

	BUG_ON(!rfkill);

	mutex_lock(&rfkill_global_mutex);

	if (rfkill->registered) {
		error = -EALREADY;
		goto unlock;
	}

	rfkill->idx = rfkill_no;
	dev_set_name(dev, "rfkill%lu", rfkill_no);
	rfkill_no++;

	list_add_tail(&rfkill->node, &rfkill_list);

	error = device_add(dev);           /* 建 sysfs 目录 */
	if (error)
		goto remove;

	error = rfkill_led_trigger_register(rfkill);
	if (error)
		goto devdel;

	rfkill->registered = true;

	INIT_DELAYED_WORK(&rfkill->poll_work, rfkill_poll);
	INIT_WORK(&rfkill->uevent_work, rfkill_uevent_work);
	INIT_WORK(&rfkill->sync_work, rfkill_sync_work);

	/* 驱动实现了 poll 才启用轮询 */
	if (rfkill->ops->poll)
		queue_delayed_work(system_power_efficient_wq,
				   &rfkill->poll_work,
				   round_jiffies_relative(POLL_INTERVAL));

	if (!rfkill->persistent || rfkill_epo_lock_active)
		schedule_work(&rfkill->sync_work);
	/* ... CONFIG_RFKILL_INPUT 的全局同步 ... */

	rfkill_global_led_trigger_event();
	rfkill_send_events(rfkill, RFKILL_OP_ADD);

	mutex_unlock(&rfkill_global_mutex);
	return 0;

devdel:
	device_del(&rfkill->dev);
remove:
	list_del_init(&rfkill->node);
unlock:
	mutex_unlock(&rfkill_global_mutex);
	return error;
}

几个细节：

rfkill_no 是 static，只增不减。 卸载再加载驱动，新设备的 idx 会比上次大。所以 rfkill0 这个编号不保证稳定，脚本里别写死。

idx 分配在所有检查通过之后、device_add 之前。 如果 device_add 失败，idx 已经消耗掉了。这就是为什么重试注册可能拿到不连续的编号。

round_jiffies_relative() 把定时器对齐到整秒。 多个 rfkill 设备的轮询会聚在同一时刻醒，减少 CPU 唤醒次数。嵌入式省电场景下这个优化有实际意义。

rfkill_send_events(RFKILL_OP_ADD) 是通知用户态的最后一环，写进 /dev/rfkill 的事件队列。

6.4 rfkill_unregister #

清理顺序与注册严格相反：

c
void rfkill_unregister(struct rfkill *rfkill)
{
	BUG_ON(!rfkill);

	if (rfkill->ops->poll)
		cancel_delayed_work_sync(&rfkill->poll_work);

	cancel_work_sync(&rfkill->uevent_work);
	cancel_work_sync(&rfkill->sync_work);

	rfkill->registered = false;

	device_del(&rfkill->dev);

	mutex_lock(&rfkill_global_mutex);
	rfkill_send_events(rfkill, RFKILL_OP_DEL);
	list_del_init(&rfkill->node);
	rfkill_global_led_trigger_event();
	mutex_unlock(&rfkill_global_mutex);

	rfkill_led_trigger_unregister(rfkill);
}

先 cancel_*_work_sync 再 device_del。 反过来的话，已排队的工作可能在设备结构已经半销毁时执行，典型的 use-after-free。_sync 后缀表示"等到确实取消了才返回"。

rfkill_unregister 不释放内存，只做注销。释放靠 rfkill_destroy()。这是标准的两段式，允许驱动在注销后还读一下状态。

七、状态设置 API #

这一族是驱动上报信息的唯一正确途径，都返回"组合后的阻塞状态"（true = 应该被阻塞）。

函数 用途
rfkill_set_hw_state(rfkill, blocked) 硬件状态变了（物理开关拨动、固件上报）
rfkill_set_sw_state(rfkill, blocked) 软件状态变了（某些平台直接响应输入）
rfkill_set_states(rfkill, sw, hw) 两者一起设，省一次加锁
rfkill_init_sw_state(rfkill, blocked) 注册前设初值，同时置 persistent
rfkill_blocked(rfkill) 查询当前是否被阻塞

7.1 为什么返回组合状态 #

看这个典型用法：

c
/* 硬件刚被解除阻塞 */
bool blocked = rfkill_set_hw_state(rfkill, false);

/*
 * blocked 为 true 说明软件层还阻塞着。
 * 驱动不需要自己记 soft 状态，直接用返回值决定要不要真的开硬件。
 */
if (!blocked)
	enable_transmitter(dev);

如果让驱动自己维护一份 soft 状态，就得处理"用户态在另一个 CPU 上同时改状态"的竞态。返回值把这件事收进了框架的锁里。

7.2 可以在任何上下文调用 #

这几个函数的文档都明确写着「can be called in any context, even from within rfkill callbacks」。内部用 spin_lock_irqsave(&rfkill->lock) 保护，所以从中断处理函数里调是安全的。

这是硬件开关驱动最需要的性质：GPIO 中断里直接上报状态，不用绕到工作队列。

7.3 轮询的暂停与恢复 #

c
void rfkill_pause_polling(struct rfkill *rfkill);
void rfkill_resume_polling(struct rfkill *rfkill);

用于"发射器因为其他原因关闭了，别浪费 CPU 轮询"的场景。

注意：挂起/恢复时不需要调这两个。 框架在 suspend 时会自动暂停轮询，resume 时自动恢复，并且能正确处理"挂起前就已经手动暂停"的情况。多此一举地调反而可能打乱状态。

八、写一个最小 rfkill 驱动 #

c
#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/rfkill.h>
#include <linux/gpio/consumer.h>

struct my_rfkill {
	struct rfkill *rfkill;
	struct gpio_desc *en_gpio;
};

static int my_set_block(void *data, bool blocked)
{
	struct my_rfkill *priv = data;

	/* blocked == true 表示关闭发射器 */
	gpiod_set_value_cansleep(priv->en_gpio, blocked ? 0 : 1);

	dev_info(&priv->rfkill_parent->dev,
		 "transmitter %s\n", blocked ? "off" : "on");
	return 0;
}

static const struct rfkill_ops my_rfkill_ops = {
	.set_block = my_set_block,
};

static int my_probe(struct platform_device *pdev)
{
	struct my_rfkill *priv;
	int ret;

	priv = devm_kzalloc(&pdev->dev, sizeof(*priv), GFP_KERNEL);
	if (!priv)
		return -ENOMEM;

	priv->en_gpio = devm_gpiod_get(&pdev->dev, "enable", GPIOD_OUT_LOW);
	if (IS_ERR(priv->en_gpio))
		return PTR_ERR(priv->en_gpio);

	priv->rfkill = rfkill_alloc("my-wifi", &pdev->dev,
				    RFKILL_TYPE_WLAN,
				    &my_rfkill_ops, priv);
	if (!priv->rfkill)
		return -ENOMEM;

	/* 初值：默认不阻塞。必须在 register 之前设 */
	rfkill_init_sw_state(priv->rfkill, false);

	ret = rfkill_register(priv->rfkill);
	if (ret) {
		rfkill_destroy(priv->rfkill);
		return ret;
	}

	platform_set_drvdata(pdev, priv);
	return 0;
}

static int my_remove(struct platform_device *pdev)
{
	struct my_rfkill *priv = platform_get_drvdata(pdev);

	rfkill_unregister(priv->rfkill);
	rfkill_destroy(priv->rfkill);
	return 0;
}

rfkill_destroy() 必须调。rfkill_unregister() 只注销，不释放；漏了 destroy 就是内存泄漏，而且是那种 insmod/rmmod 循环几百次才被发现的那种。

九、易错点 #

现象 原因 排查
rfkill list 里看不到自建设备 没调 rfkill_register，或 rfkill_alloc 返回了 NULL dmesg 看 WARN_ON 的栈
软件控制不了设备 set_block 没实现 rfkill_alloc 会直接返回 NULL
开关方向反了 blocked 的语义搞反 true 是"关"
ifconfig up 报 RF-kill 设备被 block 了 rfkill list
写 soft 报权限不足 需要 CAP_NET_ADMIN 用 root
写 state 报文件不存在 state 老接口已删除 改用 soft，注意语义相反
设备名是乱的 name 传了栈上临时缓冲 内核不拷贝字符串
rmmod 后内存泄漏 漏了 rfkill_destroy kmemleak
物理开关拨了软件不知道 没实现 poll 或 query 补上回调并上报
挂起后状态错乱 自己调了 pause_polling 挂起恢复由框架管，别插手
