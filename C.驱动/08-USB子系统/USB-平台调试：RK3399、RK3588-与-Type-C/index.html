这是 C.驱动/08-USB子系统 的平台篇。只讲 Rockchip 这两颗 SoC 上怎么把 USB 跑起来、跑不通时怎么查。设备树节点、PHY、Type-C 控制器、DWC3、调试接口，一个不落。

不讲什么：USB 协议栈的通用框架（host/device 核心、urb、usb_device/urb/endpoint 结构体那条线）在《USB 驱动框架与核心结构》里；EHCI/OHCI/xHCI 主控制器驱动的寄存器级实现和 urb 调度在《USB 主机控制器驱动》里；UVC、HID、串口这类具体设备驱动在《USB 设备驱动实战》里。本篇只把它们的结论拿来当背景。

跨篇指路：struct usb_hcd、struct dwc3 的初始化流程 →《USB 主机控制器驱动》；usb_gadget、usb_composite_driver、configfs 的通用机制 →《USB 设备驱动实战》；extcon 的框架实现 →《USB 驱动框架与核心结构》里的「extcon 与角色通知」小节。

版本前提：RK3399 部分来自 NanoPC-T4，u-boot 2023.04 + linux 6.3（部分段落是 4.19 的写法，文中单独标注）；RK3588 部分来自 NanoPC-T6，u-boot 2017.09 + linux 6.1。凡是没在这两个版本上实际跑过的，写「未验证」。

一、Rockchip 平台的 USB 子系统全景 #

一句话概括这个子系统：控制器负责协议和搬运，PHY 负责并串转换，Type-C 控制器负责「谁来当主机」，extcon 或 usb-role-switch 负责把「谁来当主机」这个结论通知给控制器。

先看软件分层，从用户态往下：

三个角色分清楚：

  • 主机侧：EHCI/OHCI(EHCI 管 USB2.0，OHCI 管 USB1.0/1.1)、xHCI(USB3.0)。Rockchip 全用内核的 generic 驱动，compatible 写 generic-ehci/generic-ohci，几乎不用自己写代码。
  • 设备侧：dwc3 的 gadget 部分，加上 configfs 或 legacy gadget。
  • 角色控制：OTG ID 电平、Type-C 的 CC 检测、或者强制写 debugfs 的 mode 文件。三条路殊途同归，最后都是改变 dwc3 的 role。

Type-C 在两个平台上的分量不一样，这点从素材里就能量出来：RK3399 那篇 141 处提到 Type-C，RK3588 那篇 261 处。数字差异背后是硬件设计差异——RK3399 的 OTG1 被友善直接设计成了 Type-A（VBUS 常供，只能做 host），真正带 Type-C 的只有一个口；RK3588 是两个口都在 Type-C 的逻辑里打转，OTG0 走完整的 cc/tcpm/altmode 链路，OTG1 虽然是 Type-A 但同样接在 usbdp_phy 上，所以设备树里 Type-C 相关的节点、属性、调试路径都要多写一倍。

二、RK3399 的 USB 控制器布局 #

RK3399 支持 4 个独立的 USB 控制器，彼此不共享资源：

  • 两个 USB2.0 HOST（EHCI&OHCI）；
  • 两个 USB3.0 OTG（DWC3/xHCI）。

命名里那个「&」和「/」是有含义的：EHCI&OHCI 表示一个控制器 IP 里集成两个 HCD；DWC3/xHCI 表示 DWC3 这个 IP 内含一个 xHCI 主机控制器，Host 功能走 xHCI 框架，Device 功能由 DWC3 扩展部分实现。

USB2.0 HOST 控制器支持高速 480Mbps、全速 12Mbps、低速 1.5Mbps。内部除 EHCI 和 OHCI 两个 Host Controller 外，还有一个 Port Routing Control，负责决定某个端口上的设备交给 EHCI 还是 OHCI 管——低速/全速设备走 OHCI，高速设备走 EHCI。这一段逻辑是硬件自动做的，设备树里不用配。

USB2.0 Host 控制器接 USB2.0 PHY，通过 UTMI+ 连接。

RK3399 没有独立的 USB2.0 OTG 控制器，但 USB3.0 OTG 控制器向下兼容 USB2.0 OTG 的完整功能。它具备这些特性（来自 Rockchip 手册）：

  • 支持 Host 模式和 Device 模式；
  • 支持 OTG ID 检测，并通过 ID 电平自动切换 Host 和 Device；
  • 不支持 ADP/SRP/HNP 协议；
  • Host 模式支持高速、全速、低速；Device 模式只支持高速和全速；
  • Host 模式支持 9 个通道；
  • Device 模式支持 9 个端点（不含端点 0），其中 4 个 IN、3 个 OUT、2 个 IN/OUT 双向；
  • 支持 1024x35 bits 内部 FIFO；
  • 支持内部 DMA，支持 scatter/gather；
  • 支持动态配置每个端点的 FIFO 大小；
  • Device 模式支持 BCD（Battery Charging Detect）；
  • 支持 UART Bypass 模式。

DWC3 部分（USB3.0 OTG）的特性：

  • 支持 Control / Bulk（含 stream）/ Interrupt / Isochronous 四种传输；
  • USB3.0 支持同时执行 IN 和 OUT，带宽 8Gbps；
  • 支持描述符缓存（Descriptor Caching）和数据预取（Data Pre-fetching）；
  • Device 模式的 IN/OUT 端点数量看芯片手册；
  • 硬件自动处理 ERDY 和 burst；
  • 支持 bulk stream；
  • 支持 USB3.0 DRD（Dual-Role Device）；
  • 支持按 OTG ID 状态切换 Device 和 Host；
  • 对于支持 Type-C 的芯片，支持 UFP/DFP 角色交换；
  • 不支持 SRP、HNP、RSP。

xHCI 那一半：

  • 最多连 64 个外设；
  • 一个中断器；
  • 一个 USB2.0 端口 + 一个 USB3.0 端口；
  • USB3.0/USB2.0 并发传输，带宽 8Gbps；
  • 用标准和开源的 xHCI 驱动；
  • 部分芯片支持 xHCI Debug Capability。

OTG 控制器对外最大传输速率 5Gbps。因为 USB3.0 HOST 就是 DWC3 里那个 xHCI，所以不用单独给它建设备树节点——配好 DWC3、把 dr_mode 设成 otg 或 host，xHCI 就起来了。

四个控制器的寄存器基址（整理自 rk3399.dtsi 的 reg 属性）：

控制器 设备节点 基址 长度 中断 类型
USB2.0 HOST0 usb_host0_ehci 0xfe380000 0x20000 GIC_SPI 26 EHCI
USB2.0 HOST0 usb_host0_ohci 0xfe3a0000 0x20000 GIC_SPI 28 OHCI
USB2.0 HOST1 usb_host1_ehci 0xfe3c0000 0x20000 GIC_SPI 30 EHCI

PHY 侧的地址：u2phy0 在 0xe450（reg 长度 0x10，syscon 风格），u2phy1 在 0xe460；tcphy0 在 0xff7c0000，tcphy1 在 0xff800000，长度都是 0x40000。

注意 EHCI 和 OHCI 成对出现但基址错开 0x20000，中断也各自独立——不是共享中断，这也是为什么启动日志里能看到 8 个 root hub（4 个控制器 × 每控制器 2 个总线，OTG 控制器上线时会同时注册 USB2.0 和 USB3.0 两条总线）。

RK3399 支持 4 个独立的 USB PHY：

  • 2 个 USB2.0 PHY：设备树里叫 u2phy0、u2phy1；
  • 2 个 USB3.0 Type-C PHY：设备树里叫 tcphy0、tcphy1（素材原文把第二个写成了「tcphy0」两次，笔误）。

以 RK3399 为例，每个 USB2.0 PHY 都有两个 port：

  • u2phy0：包含 u2phy0_host 和 u2phy0_otg；
  • u2phy1：包含 u2phy1_host 和 u2phy1_otg。

Type-C PHY 同理拆两个子 port：

  • tcphy0：包含 tcphy0_dp 和 tcphy0_usb3；
  • tcphy1：包含 tcphy1_dp 和 tcphy1_usb3（素材原文写成「tcphy1 包含 u2phy1_host 和 u2phy1_otg」，是把两个 PHY 的子节点抄混了，勘误见附）。

硬件连接关系：DP 控制器和 USB3.0 OTG 共用那个 Type-C PHY。一个完整的 Type-C 功能，由 USB3.0 SuperSpeed PHY 和 USB2.0 OTG PHY 两部分拼出来，两部分 PHY 在芯片内部是独立的硬件模块，供电也各自独立。所以 USB3.0 起不来的时候，USB2.0 那半截照样能枚举——这也是现场排查时判断「是只有 SS 挂了还是整口都挂了」的关键依据。

三、RK3588 的 USB 控制器布局 #

RK3588 的控制器清单，素材原文列了五项，开头却写「支持 4 个独立的 USB 控制器」。按项数和原文后文的解释（「USB3.0 HOST 控制器只支持 USB3.0 功能，无法支持 USB2.0，因为没有带 USB2.0 PHY」），应理解为 5 组控制器实例，数字 4 视为笔误。

  • 两个 USB2.0 HOST（EHCI&OHCI）；
  • 两个 USB3.0 OTG（DWC3/xHCI）；
  • 一个 USB3.0 HOST（xHCI），只支持 USB3.0，不向下兼容 USB2.0。

纯 USB3.0 HOST 存在的理由：它没有 USB2.0 PHY，只有一个 SS 端口，接不了鼠标键盘这类 FS/LS 设备。要用它，得让 USB2.0 HOST0 或 HOST1 与它并排放在同一个 Type-A 口上，两个控制器拼一个完整接口。这就是「HOST2 必须和 HOST0/1 二选一组合」的由来。

RK3588 支持 7 个独立的 USB PHY：

  • 4 个 USB2.0 PHY：u2phy0、u2phy1、u2phy2、u2phy3；
  • 2 个 USB3.0/DP Combo PHY：usbdp_phy0、usbdp_phy1；
  • 1 个 USB3.0/SATA/PCIe Combo PHY：combphy2_psu。

USB3.0/DP Combo PHY 支持 4 lanes，能同时跑 USB3.0 + DP 2 lanes。USB3.0/SATA/PCIe Combo PHY 同一时刻只能一种模式，USB3.0 与 SATA/PCIe 互斥——板子上接了 SATA 或 M.2 之后会直接影响那个 USB3.0 口，排查容易漏。

四颗 USB2.0 PHY 都是 Innosilicon IP，每颗只有 1 个 port（和 RK3399 的双 port 不同）：

  • u2phy0：只含 u2phy0_otg；
  • u2phy1：只含 u2phy1_otg；
  • u2phy2：只含 u2phy2_host；
  • u2phy3：只含 u2phy3_host。

绑定关系硬连线，不能改：USB3.0/DP Combo PHY0 固定配 USB2 PHY0，PHY1 固定配 USB2 PHY1。naneng 那颗 Combo PHY 只能支持 USB3.0，芯片内部压根没和 USB2.0 PHY 组合，所以 HOST2 必须和 USB2.0 HOST0/1 组合才能做出完整 Type-A 口。

由这套连接关系推出 RK3588 的接口上限：最多同时 2 个全功能 USB3.0 Type-C、2 个 USB2.0 Type-A、1 个 USB3.0 Type-A（不兼容 USB2.0）。USB3.0 OTG 与 DP 复用 Combo PHY，可以做成完整 Type-C，也可以拆开独立用（USB3.0 Type-A + DP 2 lanes）。

五、设备树里的 USB 节点 #

5.1 先看哪份文档 #

RK3399（6.3）要翻：Documentation/devicetree/bindings/usb/ 下的 generic-ehci.yaml、generic-ohci.yaml、generic-xhci.yaml、usb-xhci.yaml、usb-uhci.txt、fcs,fusb302.yaml、rockchip,rk3399-dwc3.yaml，加上 connector/usb-connector.yaml，以及 phy/phy-rockchip-typec.txt、rockchip,inno-usb2phy.yaml、rockchip-usb-phy.yaml。

RK3588（6.1）再加：snps,dwc3.yaml、phy-rockchip-usbdp.yaml、phy-rockchip-naneng-combphy.txt。

5.2 节点层级 #

text
RK3399：
usb2phy@e450 (u2phy0)            ← PHY 控制器，管时钟和 grf
├── host-port  (u2phy0_host)     ← 给 USB2.0 HOST 用
└── otg-port   (u2phy0_otg)      ← 给 USB3.0 OTG 的 USB2.0 部分用

RK3588：
syscon@fd5d0000 (usb2phy0_grf)   ← simple-mfd 容器，含 GRF 寄存器
└── usb2-phy@0 (u2phy0)
    └── otg-port (u2phy0_otg)    ← 只有一个 port

控制器侧：
usbdrd3_0 {                      ← wrapper，compatible = rockchip,rk3399-dwc3
    usbdrd_dwc3_0 {              ← DWC3 核，compatible = snps,dwc3
        phys = <&u2phy0_otg>, <&tcphy0_usb3>;
    };
};

wrapper 拿 bus 时钟和 usb3-otg 复位，core 拿 ref/bus_early/suspend 三个时钟，两层分开管。跑不通先分清卡在哪层。

六、USB2.0 HOST：EHCI 与 OHCI #

6.1 为什么两个都要开 #

OHCI 管 USB1.0/1.1（低速 1.5Mbps、全速 12Mbps），EHCI 管 USB2.0（高速 480Mbps）。要让一个 Type-A 口既能吃老键盘又能吃新 U 盘，两个 HCD 都得在线，插进来之后由硬件的 Port Routing Control 分派。

最小配置就是四个 status = "okay"（见 5.4）。Rockchip 用内核 generic 驱动，compatible 里带 generic-ehci/generic-ohci，驱动代码一行不用改——这就是「只调设备树就能跑」的原因。

七、USB3.0 OTG：DWC3 与 xHCI #

7.1 一个 IP 两种身份 #

DWC3 是 Synopsys 的 DesignWare USB3 DRD。Host 那一半是标准 xHCI，直接用 xhci-hcd；Device 那一半是 DWC3 私有寄存器 + gadget 框架。

dr_mode Host 能力 Device 能力 切换方式
host xHCI 在线 无 不需要
peripheral 无 gadget 在线 不需要
otg xHCI 在线 gadget 在线 ID 电平 / extcon / role-switch / debugfs

otg 下两条总线同时存在，同一时间只有一条能对外工作，所以 OTG 控制器总占两个总线编号。

内核配置：

text
Device Drivers --->
	[*] USB support --->
		<*> DesignWare USB2 DRD Core Support
			DWC2 Mode Selection (Dual Role mode)
		<*> DesignWare USB3 DRD Core Support
			DWC3 Mode Selection (Dual Role mode)

两颗芯片都走 DWC3，关键是第二项。

7.2 角色切换的四条路 #

按优先级排：

  1. OTG ID 电平（RK3399）：ID 接地进 host，悬空进 device，由 u2phyX_otg 的 otg-id 中断触发。
  2. extcon（RK3399 + 4.19）：drivers/mfd/fusb302.c 注册 extcon 设备，DWC3 和 PHY 用 extcon = <&fusb0> 收 EXTCON_USB / EXTCON_USB_HOST / EXTCON_DISP_DP。
  3. usb-role-switch + graph（RK3588）：tcpm 通过 connector 的 remote-endpoint 把 role 直接送进 DWC3。
  4. debugfs 强制写（两平台通用）：echo host > /sys/kernel/debug/usb/<reg>.usb/mode，只对当次启动起作用。

第 4 条是最省事的定位手段：怀疑角色判断有问题，先强制成 host，插设备看能不能枚举。能枚举，问题就不在角色上。

7.3 DWC3 的 quirk 清单 #

RK3399 五个：snps,dis_enblslpm_quirk、snps,dis-u2-freeclk-exists-quirk、snps,dis_u2_susphy_quirk、snps,dis-del-phy-power-chg-quirk、snps,dis-tx-ipgap-linecheck-quirk。

RK3588 的 OTG0/OTG1 七个，其中两条 RK3399 没有：snps,dis_enblslpm_quirk、snps,dis-u1-entry-quirk（禁 U1 进入）、snps,dis-u2-entry-quirk（禁 U2 进入）、snps,dis-u2-freeclk-exists-quirk、snps,dis-del-phy-power-chg-quirk、snps,dis-tx-ipgap-linecheck-quirk、snps,parkmode-disable-ss-quirk，OTG0 另加 quirk-skip-phy-init。

HOST2 用的是 snps,dis_rxdet_inp3_quirk，不是 U1/U2 那两条。这些 quirk 别删，删了轻则 SS 链路训练失败，重则枚举到一半掉。

quirk-skip-phy-init 单独说：它表示 PHY 由 PHY 驱动自己初始化，DWC3 不要插手。RK3588 的 usbdp_phy 需要自己跟 DP 那半协商 lane，DWC3 抢先初始化 PHY，DP altmode 就起不来。所以 OTG0（可切 DP）要它，OTG1（纯 USB）不要。

7.4 RK3399 上 extcon 的坑 #

linux 6.3 没有 drivers/mfd/fusb302.c，FUSB302 走 drivers/usb/typec/tcpm/fusb302.c，走 tcpm 框架，不注册 extcon。所以 6.3 的设备树里不能在 usbdrd3_0 上写 extcon = <&fusb0>，否则整个控制器挂住：

text
[   24.692156] platform ff7c0000.phy: deferred probe pending
[   24.692188] platform fe800000.usb: deferred probe pending

这两行几乎是「extcon 配错」的专属签名——PHY 和控制器一起卡住，谁也不往下走。反过来，4.19 必须写：

dts
&usbdrd3_0 {
		status = "okay";
		extcon = <&fusb0>;
};

tcphy0、u2phy0 上也要配。

7.5 Host 与 Device 两个方向 #

Host：dr_mode = "host"，xHCI 起来，U 盘、键鼠、HUB 都能用，代价是没法当 device。RK3399 的 OTG1（CON5）就是这么用的。

Device：dr_mode = "peripheral" 或 otg，再加载 gadget。RK3399 模拟 U 盘、声卡、键鼠的完整步骤在第十六章。

7.6 DWC3 的 tracepoint #

RK3588 的 DWC3 驱动额外实现了基于 trace 框架的 tracepoint，能动态使能并保存关键事件。事件目录路径与内核版本相关，6.1 上的具体事件名未逐条验证：

bash
root@NanoPC-T6:~# ls /sys/kernel/tracing/events/dwc3/ 2>/dev/null
root@NanoPC-T6:~# ls /sys/kernel/debug/tracing/events/dwc3/

RK3399 那篇素材没提 tracepoint，6.3 上有没有同名事件，未验证。

7.7 两个 OTG 同时配成 otg？ #

Rockchip 手册说：USB Gadget 的内核架构（原文称只针对低版本内核，比如 4.19）只支持一个 USB 控制器配成 otg。所以理论上 OTG0 和 OTG1 不能同时当 otg。

RK3399 上的试法：usbdrd_dwc3_1 的 dr_mode 改成 otg，给 u2phy1_otg 加 rockchip,vbus-always-on，重编重烧，然后看：

bash
root@rk3399:~# cat /sys/kernel/debug/usb/fe800000.usb/mode
otg
root@rk3399:~# cat /sys/kernel/debug/usb/fe900000.usb/mode
otg

素材做到了两个都显示 otg，但没验证两个口同时当 device 会不会打架。这一项标未验证。

8.6 中断、复位与 VBUSDET 的硬件差异 #

RK3399 的 u2phyX_otg 有三个中断（otg-bvalid、otg-id、linestate），u2phyX_host 只有 linestate。otg-bvalid 和 otg-id 就是 OTG 角色判断的物理来源，这两个中断没拿到，/sys/kernel/debug/usb/<reg>.usb/mode 永远停在 otg 不动。

RK3588 的 u2phy0~3 每颗只有一个中断（393/394/391/392），复位拆成 phy 和 apb 两条（reset-names = "phy", "apb"）。少给 apb 复位，寄存器写入会静默失败。

VBUSDET 脚的处理是最容易背锅的地方：

板子 引脚 处理 结果
NanoPC-T4（RK3399） TYPEC1_U2VBUSDET 悬空 OTG1 只能当 host
NanoPC-T4（RK3399） TYPEC0_U2VBUSDET 接 TYPE-C/DP 的 VBUS Type-C 口可检测
NanoPC-T6（RK3588） TYPEC0_USB20_VBUSDET 固定上拉 VCCA_3V3_S0，不能悬空 支持 PD，VBUS 检测交给 FUSB302 的 CC

RK3588 官方给的理由：为了支持高压充电同时降低硬件风险，TYPEC0_USB20_VBUSDET 不要接 Type-C 的 VBUS，固定上拉到 3.3V 即可，但不能悬空；当 Type-C0 设计成支持 PD（外置 FUSB302/HUSB311）时，软件通过 Type-C 控制器的 CC 检测 USB Device 的连接和断开。

官方对 Type-A 口的建议是「如果 USB OTG 有作 Device/HOST 的应用场景，建议 TYPEC0_OTG_VBUSDET 通过 30KΩ 电阻串联到 USB Type-A 接口的 VBUS」，友善这里悬空，所以那个口只能当 HOST。

九、Type-C 规范基础 #

9.1 它为什么能独立成一本规范 #

USB Type-C 有自己的规范文件（USB Type-C Specification，2014 年 8 月发布 1.0，2017 年 7 月发布 1.3），而 Type-A/Type-B/Mini/Micro 都依附在 USB 1.0/1.1/2.0 各自的规范里。

原因：老接口规范只定义「硬」的东西——信号个数、接口形态、电气特性。定完就不用改，没必要单独成文。Type-C 在「硬」之外加了「软」的内容，也就是 Configuration Process，于是它和 USB 规范平起平坐。

Configuration Process 解决两个问题：

  1. 插头可以正反随便插，需要一套检测插入方向的机制，并能按方向动态 map 管脚信号；
  2. 线缆两端一模一样，物理上无法区分谁是 Host 谁是 Device，需要一套协商机制。

这套机制只用了两根脚：CC1 和 CC2，靠不同电压传递简单信息。后来 USB PD 又在这两根脚上做了半双工通信协议，把供电协商也塞进去。有了这条通道，Type-C 就能承载扩展功能（配件、音频、视频、debug），变成一个能变成任意其他协议物理接口的壳子。

9.2 形态清单 #

管脚层面，Type-C 是 24 脚。插座两种：全功能 Type-C 插座、USB 2.0 Type-C 插座。插头三种：全功能、USB 2.0、Power-Only（只供电）。

标准线缆三种：两端全功能插头、两端 USB 2.0 插头、只有一端是 Type-C 插头。

为兼容旧设备还定义了一堆转接件：Type-C 转 USB3.1 Type-A、Type-C 转 USB2.0 Type-A、Type-C 转 USB3.1 Type-B、Type-C 转 USB2.0 Type-B、Type-C 转 USB2.0 Mini-B、Type-C 转 USB3.1 Micro-B、Type-C 转 USB2.0 Micro-B，以及两种适配器（全功能 Type-C 转 USB3.1 Type-A 插座、USB2.0 Type-C 转 USB2.0 Micro-B 插座）。

9.3 24 脚按功能分五类 #

类别 信号 说明
电源 VBUS、VCONN、GND VCONN 只在插头上，用于给插头供电（说明有些插头里带电路）
USB2.0 数据 D+、D- 插头端一对，和旧 USB2.0 一致；插座端两组，按方向 mapping
USB3.1 数据 TX+/TX-、RX+/RX- 插头和插座都两组，支持正反插

一个关键观察：电源类（VBUS/GND）和数据类（D+/D-/TX/RX）完全对称——VBUS 怎么插都一样，数据线简单路由一下就行。真正需要判断的只有 CC、SBU 和 VCONN，它们承载方向、线缆类型等信息。不是所有形态都会把 24 脚全用上，具体看规范对应章节。

9.4 数据角色与电源角色 #

数据角色 对应旧概念 含义

DRD（Dual-Role-Data） OTG 既能 DFP 也能 UFP，初始角色由 Power Role 决定，之后可通过 data role switch 改

记住这两张表，看 tcpm 日志就顺了：pd header := Source, Host 是「供电方 + 主机」，pd header := Sink, Device 是「受电方 + 设备」。

十、Type-C 的 CC 逻辑与角色切换 #

10.1 连接检测的三件事 #

CC 脚上做三件事：连接检测、方向检测、Power Role 检测。

插座有两个 CC，线缆侧有两种情况：正常线缆只有一根 CC，两个 Type-C 端口连起来只存在一个 CC 连接，检测哪个 CC 有连接就知道方向；可供电线缆（Powered cable）一根当 CC，另一根当 VCONN。

10.2 Rp / Rd / Ra #

角色 在 CC1/CC2 上接什么 规范出处
Source 上拉电阻 Rp（也可用电流源代替） USB Type-C Spec Table 4-20 Source CC Termination (Rp) Requirements
Sink 下拉电阻 Rd Table 4-21 Sink CC Termination (Rd) Requirements
可供电线缆（Powered cable） CC 脚接 Rd，Vconn 串一个 Ra 代表 Vconn 负载 —

Rp 分档：素材里的 fusb302 日志出现过 Rp-def、Rp-1.5，对应 default 档和 1.5A 档。规范里还有其他档位，数值查 Table 4-20，本文不展开。

10.3 Source 侧怎么判断 #

判定时要把自己的 Rp（或电流源）排除掉算：

CC1 CC2 结论
Open Open 没有 Sink 连接
Rd Open 有 Sink 连接，方向由 CC1
Open Rd 有 Sink 连接，方向由 CC2
Ra Open 有不带 Sink 的 Powered cable，方向由哪个 CC 为 Ra 决定
Open Ra 同上
Ra Rd 有带 Sink 的 Powered cable，方向由哪个 CC 为 Ra（Rd）决定

之后的行为：

  1. Source 检测到 Sink 连接（及方向）→ 给 VBUS 和 VCONN 供电；Sink 通过检测 VBUS 判断 Source 已连接，再用 CC 判断方向。
  2. Source 检测到不带 Sink 的 Powered cable → VBUS 和 VCONN 都不供。
  3. Source 检测到带 Sink 的 Powered cable → 供电，Sink 行为同第 1 条。

10.4 DRP 怎么在两个角色间跳 #

DRP 端口在 Source 和 Sink 两个状态之间来回切，每个状态下检测逻辑一样：在 Source 状态检测到 Sink 连接就当 Source，在 Sink 状态检测到 Source 连接就当 Sink。切换有周期，日志里 start drp toggling 就是这件事。

规范还留了个后悔药：虽然我是 DRP，但更想当 Source（或 Sink），可以走 Try.SRC 或 Try.SNK 尝试变成喜欢的角色。RK3588 的 connector 里 try-power-role = "sink" 就是配这个，日志里的 SNK_TRY、SRC_TRYWAIT 是这个过程。

10.5 没有 PD 时 data role 必须跟着 power role #

没有 USB PD 参与时，Type-C port 的 data role 必须和 power role 保持一致，因为规范没提供多余机制单独协商 data role。

所以看到 pd header := Source, Host，它就是主机；要让它变设备，得像 RK3588 那样走 PD 的 data role swap，或者像 RK3399 那样用 debugfs 硬掰。

10.6 有 PD 之后还能干什么 #

正确连接后，双方通过 CC 脚用 USB PD 做后续配置：Data Role 切换（类似 OTG）、Power Role 切换、Vconn Role 切换（谁给 Powered cable 供电）、供电调整（电压、电流）。这些都在 tcpm-<bus>-0022/log 里，SRC_SEND_CAPABILITIES、AMS POWER_NEGOTIATION、PD TX, header: 0x11a1 就是 PD 协商的开始。

11.4 4.19 版驱动的 probe 流程 #

fusb30x_probe() 是 extcon 那条链的源头，骨架：

c
static int fusb30x_probe(struct i2c_client *client,
                         const struct i2c_device_id *id)
{
        chip = devm_kzalloc(&client->dev, sizeof(*chip), GFP_KERNEL);
        chip->dev = &client->dev;
        chip->regmap = devm_regmap_init_i2c(client, &fusb302_regmap_config);

        ret = fusb_initialize_gpio(chip);
        fusb_initialize_timer(chip);
        chip->fusb30x_wq = create_workqueue("fusb302_wq");
        INIT_WORK(&chip->work, fusb302_work_func);

        /* 从设备树读角色：ROLE_MODE_DRP / ROLE_MODE_DFP / ROLE_MODE_UFP */
        chip->role = ROLE_MODE_NONE;
        if (!of_property_read_string(chip->dev->of_node, "fusb302,role",
                                     (const char **)&string[0])) {
                if (!strcmp(string[0], "ROLE_MODE_DRP"))
                        chip->role = ROLE_MODE_DRP;
                else if (!strcmp(string[0], "ROLE_MODE_DFP"))
                        chip->role = ROLE_MODE_DFP;
                else if (!strcmp(string[0], "ROLE_MODE_UFP"))
                        chip->role = ROLE_MODE_UFP;
        }
        if (chip->role == ROLE_MODE_NONE) {
                dev_warn(chip->dev,
                         "Can't get property of role, set role to default DRP\n");
                chip->role = ROLE_MODE_DRP;
        }

        chip->vconn_supported = true;
        tcpm_init(chip);
        tcpm_set_rx_enable(chip, 0);
        chip->conn_state = unattached;
        tcpm_set_cc(chip, chip->role);

        /* 注册 extcon 设备 */
        chip->extcon = devm_extcon_dev_allocate(&client->dev, fusb302_cable);
        ret = devm_extcon_dev_register(&client->dev, chip->extcon);

        /* 逐个声明能力，每个 cable 两组 property */
        ret = extcon_set_property_capability(chip->extcon, EXTCON_USB,
                                             EXTCON_PROP_USB_TYPEC_POLARITY);
        /* EXTCON_USB_HOST / EXTCON_DISP_DP / EXTCON_CHG_USB_FAST 同样调用 */

        i2c_set_clientdata(client, chip);
        spin_lock_init(&chip->irq_lock);
        chip->enable_irq = 1;

        chip->gpio_int_irq = gpiod_to_irq(chip->gpio_int);
        if (chip->gpio_int_irq < 0)
                goto IRQ_ERR;

        ret = devm_request_threaded_irq(&client->dev,
                                        chip->gpio_int_irq,
                                        NULL,
                                        cc_interrupt_handler,
                                        IRQF_ONESHOT | IRQF_TRIGGER_LOW,
                                        client->name,
                                        chip);
        if (ret)
                goto IRQ_ERR;

        dev_info(chip->dev,
                 "port %d probe success with role %s, try_role %s\n",
                 chip->port_num, string[0], string[1]);
        return 0;
IRQ_ERR:
        destroy_workqueue(chip->fusb30x_wq);
        return ret;
}

（原函数还包含 fusb302,try_role 的字符串解析、pd_cap_info 的十来个能力位赋值、以及一个 input 设备注册——那部分把 Type-C 当成耳机插孔上报 SW_HEADPHONE_INSERT，和 USB 角色无关，本文略去。）

四个关键点：

  1. fusb302,role 属性决定初始 CC 配置，没有就默认 DRP 并打 warning；
  2. tcpm_set_cc() 之后才真正开始 CC 状态机；
  3. devm_extcon_dev_register() 注册出 extcon 设备，DWC3 和 PHY 才拿得到；
  4. 中断用 IRQF_ONESHOT | IRQF_TRIGGER_LOW，设备树里配的 IRQ_TYPE_LEVEL_LOW 必须和它对上，配成高电平永远进不了中断。

11.5 为什么 6.3 上没有 extcon #

6.3 的 drivers/usb/typec/tcpm/fusb302.c 走标准 tcpm 框架，角色上报路径是 tcpm → usb_role_switch 或 connector 的 typec_switch/typec_mux，不再是 extcon。所以：

  • 设备树写 extcon = <&fusb0> → 找不到 provider → -EPROBE_DEFER → deferred probe pending；
  • 想让角色生效，得给 DWC3 配 usb-role-switch，再用 port/endpoint 连到 tcpm。

RK3399 6.3 的素材里这两步都没做，所以自动识别没工作。要在 RK3399 + 6.3 上做完整的 Type-C 角色切换，需要照 5.6 的结构补一套 graph，或者给 fusb302 加 role-switch 相关属性。这条只是推断，未验证。

十二、extcon 与角色通知 #

12.1 通知链的两端 #

物理层判断完角色之后要通知三个消费者。extcon 时代用一条广播链把它们串起来：

text
FUSB302 (mfd 驱动) → tcpm 状态机 (tcpm-4-0022) → extcon 广播
                                                    ├──▶ dwc3->role    切 Host/Device
                                                    ├──▶ u2phy0_otg    切 USB2.0 通路
                                                    └──▶ tcphy0        切 USB3.0/DP 通路

广播源就是 fusb30x_probe() 注册的那个 extcon 设备：

c
chip->extcon = devm_extcon_dev_allocate(&client->dev, fusb302_cable);
if (IS_ERR(chip->extcon)) {
        dev_err(&client->dev, "allocat extcon failed\n");
        return PTR_ERR(chip->extcon);
}

ret = devm_extcon_dev_register(&client->dev, chip->extcon);
if (ret) {
        dev_err(&client->dev, "failed to register extcon: %d\n", ret);
        return ret;
}

消费者申请了 provider 没声明的 capability，extcon_get_property() 返回 -EPERM，表现就是 role 变了但 PHY 没跟着切，插设备不认。

12.3 PHY 侧怎么消费 #

4.19 的 u2phyX_otg 和 tcphyX 节点上都要写 extcon，PHY 驱动 probe 时 extcon_get_edev_by_phandle() 拿到设备，再 devm_extcon_register_notifier() 注册回调，按 EXTCON_USB / EXTCON_USB_HOST 的 state 决定开关哪条通路。少配一个属性，DWC3 拿到了角色、PHY 没拿到，插设备毫无反应，dmesg 也不报错。

12.4 RK3588 换成了 usb-role-switch #

维度 extcon（4.19） usb-role-switch + graph（6.1）
绑定方式 phandle：extcon = <&fusb0> graph：remote-endpoint
传输内容 cable state + property（含极性、SS） role（host/device/none）+ 独立的 orientation switch
消费端数量 多个（dwc3、u2phy、tcphy 各配一次） 一个 role-switch + 一个 orientation-switch

otg_mode 是这条路在 RK3588 上的可观测点：

12.5 extcon 的排查顺序 #

  1. I2C 上有没有设备：i2cdetect -y 4（RK3399）或 -y 6（RK3588），0x22 必须在。
  2. 驱动有没有 probe：ls /sys/kernel/debug/usb/ 下有没有 fusb302-4-0022 和 tcpm-4-0022。
  3. extcon 设备有没有注册：ls /sys/class/extcon/（4.19 上才有内容；6.1/6.3 走 role-switch，这个目录是空的，别误判成故障）。
  4. 通知有没有到消费者：cat /sys/kernel/debug/usb/<reg>.usb/mode，插拔线看它变不变。

13.2 VBUS 什么时候开、什么时候关 #

RK3588 的规则：USB3.0 OTG 控制器在 Device mode 关闭 VBUS，在 Host mode 打开 VBUS。RK3399 那边靠 FUSB302 + tcpm 完成同样的事：

text
[392786.758666] pd header := Source, Host
[392786.761069] vbus := On
[392786.762226] IRQ: VBUS_OK, vbus=On
[393000.158623] vbus := Off
[393000.160018] IRQ: VBUS_OK, vbus=Off

VBUS 不输出时，先看这行 vbus := On/Off，再看 vbus-supply/phy-supply 指对没有，最后才怀疑硬件。

13.3 PD 能力表 #

dts
data-role = "dual";
power-role = "dual";
try-power-role = "sink";
op-sink-microwatt = <1000000>;
sink-pdos = <PDO_FIXED(5000, 3000, PDO_FIXED_USB_COMM)>;
source-pdos = <PDO_FIXED(5000, 2000, PDO_FIXED_USB_COMM)>;

含义：作为 Sink 接受 5V/3A 固定 PDO；作为 Source 对外提供 5V/2A；作为 Sink 最大功耗 1000mW。PDO_FIXED_USB_COMM 表示这档供电同时支持 USB 通信，不是纯充电档。

这和芯片能力是两件事：fusb302 支持 PD 2.0、最高 100W 协商，但板子实际能供多少由 source-pdos 和 SY6280AAC 的限流共同决定。把 source-pdos 写成 5V/3A 而硬件限流 1A，接大功率设备就掉电重启。

13.4 PD 协商的日志特征 #

text
[394482.705888] AMS POWER_NEGOTIATION start
[394482.708707] state change AMS_START -> SRC_SEND_CAPABILITIES [rev3 POWER_NEGOTIATION]

13.5 供电的三个坑 #

  1. phy-supply 控不了动态开关。RK3588 的 OTG1 用它，就是为了「一直供 5V，反正这个口只当 host」。
  2. VBUS 常供的口不能配 phy-supply，要配 rockchip,vbus-always-on。RK3399 的 OTG1 就是这情况。
  3. VBUSDET 脚悬空的口只能当 host。RK3588 的 TYPEC1 就是这样，官方建议串 30KΩ 到 Type-A 的 VBUS 才能做双角色。

14.6 fusb302 与 tcpm 的日志怎么读 #

fusb302-<bus>-<addr>/log 关心三件事：IRQ: 0x.., a: 0x.., b: 0x.. 是中断（status、a、b 三个寄存器）；detected cc1=Rd, cc2=Open 是 CC 判定结果；cc := Rp-1.5 / cc := Rd 是自己当前挂的端接。

text
[392786.091216] IRQ: TOGDONE
[392786.096222] detected cc1=Rd, cc2=Open
[392786.296268] cc := Rd
[392786.398930] cc := Rp-1.5
[392786.558168] detected cc1=Rd, cc2=Open
[392786.758666] pd header := Source, Host
[392786.761069] vbus := On
[392786.762226] IRQ: VBUS_OK, vbus=On

读法：detected cc1=Rd 说明对端在 CC1 挂了 Rd（它是 Sink），于是自己切 cc := Rp-1.5（挂 1.5A 档上拉当 Source），然后 Source, Host 打开 VBUS。接 PC 正好反过来：detected cc1=Rp-def → pd header := Sink, Device → vbus is already Off。

tcpm-<bus>-<addr>/log 关心状态迁移：

text
[394482.036799] state change TOGGLING -> SRC_ATTACH_WAIT [rev3 NONE_AMS]
[394482.236822] state change SRC_ATTACH_WAIT -> SNK_TRY [delayed 200 ms]
[394482.339483] state change SNK_TRY_WAIT -> SRC_TRYWAIT [rev3 NONE_AMS]
[394482.701864] state change SRC_ATTACH_WAIT -> SRC_ATTACHED [delayed 200 ms]
[394482.701866] polarity 1
[394482.701868] Requesting mux state 1, usb-role 1, orientation 2
[394482.705850] VBUS on

polarity 1 是正反插结论，Requesting mux state 1, usb-role 1, orientation 2 是往 role-switch 和 orientation-switch 下发结果——这一行不出现，说明通知没出去。

14.7 三种强制改模式的方法 #

方法 路径 适用 生效范围

16.1 四个口怎么接 #

NanoPC-T4 的 USB 资源：2 个原生 USB2.0 Host Type-A（丝印 USBH2、USBH3），1 个原生 USB3.0 Host Type-A（CON5），1 个 USB3.0 Type-C（TYPE-C/DP，支持 DP 1.2 Alt Mode）。

板上接口 控制器 PHY 说明
USBH2 USB2.0 HOST0（EHCI&OHCI） u2phy0_host 电源 VCC5V0_HOST0，RT9724GQW
USBH3 USB2.0 HOST1（EHCI&OHCI） u2phy1_host 电源同 VCC5V0_HOST0
CON5 USB3.0 OTG1（DWC3/xHCI） u2phy1_otg + tcphy1_usb3 电源 VCC5V0_HOST2；dr_mode = "host"
TYPE-C/DP USB3.0 OTG0（DWC3/xHCI） u2phy0_otg + tcphy0_usb3 电源 VBUS_TYPEC，GPIO4_D2 使能；配 FUSB302

CON5 那个口三个注意点：fusb 节点不要配（Type-A 不需要 fusb302）；usbdrd_dwc3_1 和 PHY 节点都要删 extcon；dr_mode 必须 host。TYPE-C/DP 反过来：fusb 必须配，usbdrd_dwc3_0 和 PHY 都要配 extcon（仅 4.19），dr_mode 配 otg。

16.8 configfs 模拟复合键鼠与触摸屏 #

脚本 /shell/hid/hid_keyboard_mouse.sh 一个 gadget 两个 hid 接口，差异只在两处：

接口 subclass protocol report_length 含义
hid.0 1 1 8 键盘（Boot 设备、键盘协议、8 字节报告）
hid.1 1 2 4 鼠标（Boot 设备、鼠标协议、4 字节报告）

触摸屏脚本 hid_touch.sh 再用另一组：subclass 0（No Subclass）、protocol 0、report_length 5。差在坐标类型——鼠标是相对坐标 8 bit，触摸屏是绝对坐标 16 bit，所以 xy 各占两字节。bInterfaceProtocol 只有在 bInterfaceSubClass 支持启动接口时才有意义，否则填 0。

5 字节报告的布局：

 * 触摸屏每次发送5字节报告
 * report[0]的D0就是左键，D1就是右键，D2就是中键
 * report[1]为X轴低字节
 * report[2]为X轴高字节
 * report[3]为Y轴低字节
 * report[4]为Y轴高字节，
*/

gadget=g1
do_start(){
    mount -t configfs none /sys/kernel/config 2>/dev/null
    cd /sys/kernel/config/usb_gadget
    [ -d ${gadget} ] || mkdir ${gadget}
    cd ${gadget}

    cd /lib/modules/6.3.0
    depmod -a
    modprobe libcomposite
    modprobe usb_f_hid
    cd /sys/kernel/config/usb_gadget/${gadget}

    echo 0x0200 > bcdUSB
    echo "0x0525"  > idVendor
    echo "0xa4ac" > idProduct

    mkdir strings/0x409
    echo "76543210" > strings/0x409/serialnumber
    echo "mkelehk"  > strings/0x409/manufacturer
    echo "keyboard_mouse"  > strings/0x409/product

    mkdir configs/c.1
    mkdir configs/c.1/strings/0x409
    echo "hid" > configs/c.1/strings/0x409/configuration

    mkdir functions/hid.0
    mkdir functions/hid.1
    echo 1 > functions/hid.0/subclass
    echo 1 > functions/hid.0/protocol
    echo 8 > functions/hid.0/report_length
    echo -ne \\x05\\x01\\x09\\x06\\xa1\\x01\\x05\\x07\\x19\\xe0\\x29\\xe7 > functions/hid.0/report_desc
    echo 1 > functions/hid.1/subclass
    echo 2 > functions/hid.1/protocol
    echo 4 > functions/hid.1/report_length
    echo -ne \\x05\\x01\\x09\\x02\\xa1\\x01\\x09\\x01\\xa1\\x00 > functions/hid.1/report_desc

    ln -s functions/hid.0 configs/c.1
    ln -s functions/hid.1 configs/c.1

do_stop() {
    cd /sys/kernel/config/usb_gadget/${gadget}

}
case $1 in

    {.opt = "--left-ctrl",  .val = 0x01},  {.opt = "--right-ctrl", .val = 0x10},

    {.opt = "--left-meta",  .val = 0x08},  {.opt = "--right-meta", .val = 0x80},
    {.opt = NULL}
};

// 描述普通按键，存储在BYTE2~BYTE7字节
static struct options kval[] = {
    {.opt = "--return", .val = 0x28},  {.opt = "--esc", .val = 0x29},

16.13 RK3399 侧的结论 #

四个口全部跑通：两个 USB2.0 Type-A 能带键鼠 HUB，USB3.0 Type-A 能带摄像头和 1TB 移动硬盘（达到 SuperSpeed），Type-C 口能带触摸屏。device 方向能模拟 U 盘、声卡、复合键鼠、触摸屏。

没跑通的：Type-C 的自动角色识别（6.3 + tcpm 没配对），以及 Type-C 连 PC 时的键鼠回灌。

17.1 两个口的接线 #

NanoPC-T6：一个全功能 USB3.0 Type-C（USB-C/DP，USB3.0 数据 + DP 显示，4Kp60），一个 USB3.0 Type-A。

17.6 强制模式的两条路 #

方式 1（otg_mode）在 Type-C 口上无效，tcpm 会自己接管。方式 2（debugfs）：

bash
root@NanoPC-T6:~# echo host > /sys/kernel/debug/usb/fc000000.usb/mode    # USB3.0 Type-C 口
root@NanoPC-T6:~# echo host > /sys/kernel/debug/usb/fc400000.usb/mode    # USB3.0 Type-A 口

原话是「比如 USB3.0 Type-C 接口当前连接着鼠标设备并且工作为主机模式，如果将其设置为设备模式，鼠标将无法工作」。两个口强制 host 之后插鼠标都能正常工作，验证了控制器和 PHY 都是好的。

17.7 官方脚本 usbdevice 要先挪走 #

系统默认通过 /etc/profile.d/usbdevice.sh 自动执行 /bin/usbdevice，把开发板模拟成 adb 终端。

bash
root@NanoPC-T6:/# mkdir /opt/hid
root@NanoPC-T6:/opt/hid# mv /bin/usbdevice /opt/hid

不挪走的话，配 g2 时官方脚本会抢先占住 UDC，echo fc000000.usb > UDC 会失败。

17.10 RK3588 侧的结论 #

Type-C 口的自动角色切换通了（接 U 盘进 host、接 PC 进 device），USB3.0 Type-A 口只能当 host，与 VBUSDET 悬空的设计一致。device 方向能用 configfs 模拟触摸屏，UDC 名 fc000000.usb。

没做的：OTG0 的 DP altmode 实拍验证、HOST2 的实际使用、Type-C 口的高速 PD 协商（只看到 5V 固定档）。三项标未验证。

十八、易错点速查 #

# 坑 后果 正确做法
1 6.x 内核照 4.19 写 extcon = <&fusb0> deferred probe pending，整个控制器挂住 6.x 删 extcon，改用 usb-role-switch + graph
2 compatible 用了对方版本的字符串 probe 不上 6.x 用 fcs,fusb302，4.19 用 fairchild,fusb302
3 RK3588 的 EHCI 抄 RK3399 的 phy-names = "usb" PHY 拿不到 RK3588 是 "usb2-phy"
4 RK3588 的 HOST0 配 &u2phy0_host 没有这个节点 HOST0 配 u2phy2_host，HOST1 配 u2phy3_host
5 phys 和 phy-names 顺序不一致 绑错 PHY usb2-phy 在前，usb3-phy 在后
6 VBUS 常供的口仍配 phy-supply 无法连接 去掉 phy-supply，加 rockchip,vbus-always-on
7 需要动态开关 VBUS 却配了 phy-supply 切 device 时 VBUS 不掉 用 vbus-supply（要求 OTG 独占 GPIO）
8 dr_mode = "host" 却想当 device 插 PC 不枚举 改 peripheral 或 otg
9 IRQ_TYPE_LEVEL_LOW 与驱动的 IRQF_TRIGGER_LOW 不一致 永远进不了中断 两处保持一致
10 少声明 EXTCON_PROP_USB_TYPEC_POLARITY capability 反插不认 provider 端要 extcon_set_property_capability()
11 删掉 snps,dis-*-quirk SS 链路训练失败 全保留，尤其别删 u1/u2 entry 两条
12 reset-names 抄错（usb3-otg vs usb3-host） 拿不到复位 HOST2 用 usb3-host
13 没跑 depmod -a 就 modprobe 模块加载失败 先 depmod -a
