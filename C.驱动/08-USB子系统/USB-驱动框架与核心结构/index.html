一、USB 是什么：四根线连接主从 #

通用串行总线（Universal Serial Bus，USB）是连接计算机系统与外部设备的一种串口总线标准，也是一套输入输出接口的技术规范。它在个人电脑、移动设备上普及，也扩到摄影器材、数字电视机顶盒、游戏机这些领域。

在 USB 之前，键盘、鼠标、扫描仪、打印机各用专用接口，不能互用，扩展性差，插拔设备得关机，速率还低。USB 把这些一次解决：一条管道，只要流过的数据符合 USB 协议，里面装的是什么，总线不管。USB 键盘、鼠标、摄像头、音箱都能插同一类口，支持热插拔。

USB 是主从模式的总线。主机叫 Host，从机叫 Device。从机与从机之间、主机与主机之间（USB4 除外）不能互联。每一次通信都由主机发起，从机只能被动应答，不能主动开口。

USB 3.0 以后的协议里，主机也能直接和集线器（Hub）通信。为了灵活性又出现了 USB OTG（On The Go），支持主从切换，同一个设备在不同场合可以在主机和从机之间换角色。OTG 线里多一根 USB ID 线：ID 线上拉是从机模式，ID 线接地是主机模式。

四根线，以及插上去怎么被发现 #

USB 2.0 接口只有 4 条线：VBUS（5V）、GND、D-、D+。VBUS 由主机向设备供电，GND 是地线。

插上去之后主机怎么知道来了设备？靠上拉电阻。

  • PC 机侧 USB 插孔的 D-、D+ 都接 15 kΩ 下拉电阻。
  • 设备侧在 D- 或 D+ 上接 1.5 kΩ 上拉电阻。
  • 设备插入，把 PC 机 D- 或 D+ 的电压拉高；主机在总线上检测到高电平，就知道有设备接入。

拉高的是哪根线，直接把速度档位暴露出来：

  • PC 机 D- 被拉高，接入的是 USB 低速设备。
  • PC 机 D+ 被拉高，接入的是全速设备或高速设备。具体是全速还是高速，由主机和设备发包握手确定。

差分线与双工 #

USB 用差分信号传数据。USB 3.2 线缆示意里，D+/D- 是一对差分线，SSTX+/SSTX- 是一对，SSRX+/SSRX- 是一对：

  • USB 2.0 只有一对差分线（D+/D-），半双工，不能同时收发。
  • USB 3.2 有两对差分线（SSTX± 与 SSRX±），全双工，可同时收发。

USB 3.2 和 USB 2.0 用不同差分线跑，互不干扰，能同时工作。3.2 线缆保留了 2.0 的数据通道，向下兼容 2.0。供电方面，主机通过 VBUS 给设备供电，最大输出 20V/5A。

二、USB 的版本与速率 #

从 USB 协议诞生至今出现了多个版本：USB 1.0、1.1、2.0、3.0、3.1、3.2。最新的 USB4 可直连 CPU 的 PCIe 总线，最大 40 Gbps，使用 Type-C 接口，兼容 DP 视频协议、PD 快充协议，最高支持 100W 供电。

命名规范折腾过一次。USB 3.2 推出时，USB-IF 公布新命名：USB 3.0 改名 USB 3.2 Gen 1，USB 3.1 改名 USB 3.2 Gen 2，能用两个 Type-C Rx/Tx 针脚的那版改名 USB 3.2 Gen 2×2。老文章里写「USB 3.1」，今天看多半指 Gen 2。

各版本速率汇总：

USB 1.0 低速 / 全速 1.5 Mbps / 12 Mbps 1 对 半双工 Type-A
USB 1.1 全速 12 Mbps 1 对 半双工 Type-A
USB 2.0 高速 480 Mbps 1 对 半双工 Type-A / Type-B
USB 3.0 USB 3.2 Gen 1 5 Gbps 2 对 全双工 Type-A / Type-C
USB 3.1 USB 3.2 Gen 2 10 Gbps 2 对 全双工 Type-C

帧与微帧 #

USB 2.0 主机控制器把时间切成帧：低速和全速模式下 1 ms 一帧，高速模式下 125 µs 一个微帧（microframe），主机控制器把每个帧或微帧的一部分分给各个传输。每帧（微帧）以帧起始包（Start-of-Frame，SOF）开始，带时序参考。超高速总线不使用 SOF，但主机控制器仍能在 125 µs 的总线时间内安排超高速传输。

一个传输（transfer）可以安排在 1 个或多个帧/微帧里，每个传输包含若干事务（transaction），每个事务又含若干信息包（packet）。信息包必须在一个帧/微帧内传完，不能跨帧。包分四类：

  • 令牌类：确认事务类型。
  • 数据类：携带数据和状态代码。
  • 握手类：携带状态代码。
  • 特殊类。

USB 2.0 的事务开始于主机在总线上发出的令牌信息包，令牌里带目标端点号和方向。IN 令牌表示向端点请求数据包，OUT 令牌是主机派发数据包的先行包。除数据外，每个数据包还带错误检查位和带数据顺序值的包 ID（PID）。很多事务还有握手包，接收端借它报告事务成功或失败。超高速事务的包类型和协议不同，但同样含地址、错误检查和与数据配合的顺序值。

三、USB 的拓扑：主机、集线器与设备 #

USB 总线拓扑是分层的星型结构。根节点是 USB Host 控制器（图里常省掉），挂在 Host 控制器上的是根集线器（Root Hub）。Hub 把一个 USB 口扩展成多个口，扩展出来的口还能再接 Hub，每个口都能接设备。

几个必须记住的边界：

  • Hub 只扩接口，不扩带宽。所有 USB 设备共享 Host 控制器的带宽。多个大带宽设备要么分散到不同 Host 控制器的根集线器上，要么认命。
  • 级联最多 5 层 Hub，加上根这一层，最大 7 层星型结构。
  • 一个分层星型结构代表一条 USB 总线，一条总线有且仅有一个 USB 主机控制器。一台计算机内部可以有多个 USB 总线（我的机器上就是 1 个主控制器 + Root Hub，Windows 设备管理器里能看到好几条）。
  • USB 3.x 起，主机也可以直接和 Hub 通信，不再只是转发。

对应到内核的字符串表示，就是 usb_device.devpath：1-0:1.0 表示 1 号总线、根 Hub 的 0 号口、配置 1、接口 0。/sys/bus/usb/devices 下的名字就是这套规则。

四、端点与管道 #

USB 通信最基本的形式是经由端点。端点只能往一个方向送数据：从主机到设备叫输出端点（OUT），从设备到主机叫输入端点（IN）。端点就是单向管道。

设备地址是设备级的，插上主机时由 USB 主机控制器分配，根 Hub 地址固定为 1，主机靠这个地址访问设备。设备内部再把地址分细：设备分出若干端点，端点号由厂商指定，一个 USB 设备最多 16 个端点，端点地址 0~15。

每个端点地址绑定一个方向。端点 3-IN 和端点 3-OUT 是两个不同的东西。有一个例外：端点 0。

  • 每个 USB 设备必须有端点 0，用于枚举和对设备做基本控制，又叫控制端点。
  • 端点 0 是双向的，既能发也能收。其它端点都是单向。

16 个端点里，实际很少全用。典型配置只用 3 个：

  • EP0：传输配置和控制信息。
  • EP1：数据输入，IN_EP。
  • EP2：数据输出，OUT_EP。

除端点 0，其余端点在设备被配置之前不能和主机通信，必须先向主机报告特性并确认，才能激活。

内核怎么描述端点 #

struct usb_host_endpoint 描述主机侧的端点，定义在 include/linux/usb.h：

c
struct usb_host_endpoint {
        struct usb_endpoint_descriptor          desc;
        struct usb_ss_ep_comp_descriptor        ss_ep_comp;
        struct usb_ssp_isoc_ep_comp_descriptor  ssp_isoc_ep_comp;
        struct list_head                urb_list;
        void                            *hcpriv;
        struct ep_device                *ep_dev;        /* For sysfs info */

        unsigned char *extra;   /* Extra descriptors */
        int extralen;
        int enabled;
        int streams;
};

字段含义：

字段 含义
desc 端点描述符，wMaxPacketSize 已是本机字节序
ss_ep_comp SuperSpeed 端点配套描述符
ssp_isoc_ep_comp SuperSpeedPlus 等时端点配套描述符
urb_list 本端点上排队的 URB 链表，由 usbcore 维护
hcpriv HCD 私有数据，放硬件 DMA 队列头（QH）和 TD
ep_dev sysfs 用的 ep_device
extra / extralen 该端点之后跟着的额外描述符及字节数
enabled 置位后才允许向本端点提交 URB
streams 该端点分配的 USB 3 streams 数量

真正的端点信息在 struct usb_endpoint_descriptor 里，定义在 include/uapi/linux/usb/ch9.h：

c
/* USB_DT_ENDPOINT: Endpoint descriptor */
struct usb_endpoint_descriptor {
        __u8  bLength;
        __u8  bDescriptorType;

        __u8  bEndpointAddress;
        __u8  bmAttributes;
        __le16 wMaxPacketSize;
        __u8  bInterval;

        /* NOTE:  these two are _only_ in audio endpoints. */
        /* use USB_DT_ENDPOINT*_SIZE in bLength, not sizeof. */
        __u8  bRefresh;
        __u8  bSynchAddress;
} __attribute__ ((packed));

关键字段：

字段 含义
bLength 描述符长度
bDescriptorType 描述符类型，端点描述符为 5
bEndpointAddress 位 [3:0] 是端点号，第 7 位是方向：0 输出、1 输入
bmAttributes 位 [1:0]：00 控制、01 等时、10 批量、11 中断
wMaxPacketSize 本端点一次可收发的最大包长
bInterval 轮询间隔，中断传输用，比如多久查一次鼠标数据

bEndpointAddress 的方向位用 USB_ENDPOINT_DIR_MASK 取，bmAttributes 的类型位用 USB_ENDPOINT_XFERTYPE_MASK 取，这两个掩码在写探测端点时会反复出现。

五、四种传输类型：控制、中断、批量、等时 #

USB 端点的四种类型，对应四种基本数据传输。它们的取舍就是「可靠性」和「时间保证」之间选边。

传输类型 可靠性 时间保证 数据量 典型用途 端点 bmAttributes
控制 可靠 协议保证有足够带宽 小 枚举、取描述符、发命令、读状态 00
中断 可靠 固定轮询间隔，实时性高 小 鼠标、键盘 11
批量 可靠 不保证完成时间 大 U 盘、打印机 10
等时 不保证 恒定速率 大 摄像头、音频 01

逐个说清楚。

控制传输用来配置设备、获取设备信息、发命令、读设备状态。每个 USB 设备都有端点 0 这个控制端点，设备插入拓扑后，主机先通过端点 0 与它通信完成配置，之后才有别的传输。协议保证控制传输有足够带宽，可靠、有时间保证，但数据量不大。枚举走的就是控制传输。

中断传输在主机请求数据时以固定速率传送少量数据。中断端点的传输方式就是中断传输，可靠、实时性高。这里的「中断」不是设备真的发中断给主机——是主机每隔固定时间主动查询设备有没有数据要传，靠轮询换实时性。鼠标用的就是中断传输。

批量传输用于大量数据。协议不保证这些数据在特定时间内传完，但保证准确性。总线上带宽不够发整个批量包，就拆成多个包分别传。可靠，实时性差。U 盘、打印机是批量传输。

等时传输也能传大量数据，但可靠性无法保证。用等时传输的设备更看重恒定的传输速率，对可靠性的要求低，丢一两帧可以接受。摄像头用的就是等时传输。

四种传输在不同速度下支持的最大包长不一样，具体值查 USB 协议第 5 章的表，这里不抄——抄了容易抄错，写驱动时用 wMaxPacketSize 现场读，别硬编码。

六、描述符体系 #

USB 设备用描述符描述自己的架构，标准四件套：设备描述符、配置描述符、接口描述符、端点描述符。四者层层嵌套：

text
设备描述符 (Device, type=1)
  bNumConfigurations 个
  └── 配置描述符 (Configuration, type=2)   wTotalLength 覆盖本配置下全部描述符
        bNumInterfaces 个
        └── 接口描述符 (Interface, type=4)
              bAlternateSetting 个
              └── 端点描述符 (Endpoint, type=5)   bNumEndpoints 个
        └── 类描述符（HID, type=0x21 / CDC, type=0x24 …）
                   └── 类专用描述符（HID Report, type=0x22 …）
描述符 类型值 内核结构体 头文件
设备 1 usb_device_descriptor uapi/linux/usb/ch9.h
配置 2 usb_config_descriptor uapi/linux/usb/ch9.h
字符串 3 无独立结构，usb_string() 读 —
接口 4 usb_interface_descriptor uapi/linux/usb/ch9.h
端点 5 usb_endpoint_descriptor uapi/linux/usb/ch9.h
设备限定符 6 usb_qualifier_descriptor uapi/linux/usb/ch9.h
其它速度配置 7 复用 usb_config_descriptor uapi/linux/usb/ch9.h
接口关联（IAD） 11 usb_interface_assoc_descriptor uapi/linux/usb/ch9.h
BOS 15 usb_bos_descriptor uapi/linux/usb/ch9.h

「配置 → 接口 → 端点」这层抽象的含义：配置和接口是对设备功能的抽象，真正搬数据的是端点。

设备描述符 #

设备描述符说明设备树形，固化在设备内部。主机检测到设备插入后，用控制传输把它读出来，这步在枚举时完成。

c
/* USB_DT_DEVICE: Device descriptor */
struct usb_device_descriptor {
        __u8  bLength;
        __u8  bDescriptorType;

        __le16 bcdUSB;
        __u8  bDeviceClass;
        __u8  bDeviceSubClass;
        __u8  bDeviceProtocol;
        __u8  bMaxPacketSize0;
        __le16 idVendor;
        __le16 idProduct;
        __le16 bcdDevice;
        __u8  iManufacturer;
        __u8  iProduct;
        __u8  iSerialNumber;
        __u8  bNumConfigurations;
} __attribute__ ((packed));
字段 含义
bLength 描述符长度
bDescriptorType 类型，设备描述符为 1
bcdUSB USB 版本号，BCD 编码，比如 0x0200 表示 2.0
bDeviceClass USB-IF 分配的设备类 code
bDeviceSubClass 设备子类 code
bDeviceProtocol 协议 code
bMaxPacketSize0 端点 0 最大包长
idVendor 厂商编号，USB-IF 分配
idProduct 产品编号，厂商自定
bcdDevice 设备出厂编号
iManufacturer 厂商字符串索引
iProduct 产品字符串索引
iSerialNumber 序列号字符串索引
bNumConfigurations 配置描述符个数

bcdUSB 决定主机按哪版协议跟设备讲话，bMaxPacketSize0 决定枚举时控制传输能一次搬多少字节——8 字节起步，枚举早期读设备描述符只用 8 字节，就是这个原因。

配置描述符 #

接口被捆绑为配置。一个设备可以有多个配置，同一时刻只能激活一个。有些允许下载固件的设备用多个配置完成这件事（一个配置跑正常功能，另一个配置专供下载固件）。

c
struct usb_config_descriptor {
        __u8  bLength;
        __u8  bDescriptorType;

        __le16 wTotalLength;
        __u8  bNumInterfaces;
        __u8  bConfigurationValue;
        __u8  iConfiguration;
        __u8  bmAttributes;
        __u8  bMaxPower;
} __attribute__ ((packed));
字段 含义
bLength 描述符长度
bDescriptorType 类型，配置描述符为 2
wTotalLength 本配置下所有描述符的总长度，含本配置描述符
bNumInterfaces 本配置支持的接口数
bConfigurationValue 配置值，实际就是该配置在 usb_device->config 数组里的索引
iConfiguration 配置字符串索引
bmAttributes 供电模式选择（总线供电/自供电、是否支持远程唤醒）
bMaxPower 设备从总线取的最大电流

wTotalLength 是枚举的关键数字：读配置描述符时，先读 9 字节拿到它，再按它的长度把整棵描述符树一次读回来。读少了，端点描述符就丢了。

接口描述符 #

USB 端口被捆绑为接口。一个接口只处理一种 USB 逻辑，代表一个逻辑上的设备。声卡驱动就常见两个接口：录音接口和播放接口。

c
/* USB_DT_INTERFACE: Interface descriptor */
struct usb_interface_descriptor {
        __u8  bLength;
        __u8  bDescriptorType;

        __u8  bInterfaceNumber;
        __u8  bAlternateSetting;
        __u8  bNumEndpoints;
        __u8  bInterfaceClass;
        __u8  bInterfaceSubClass;
        __u8  bInterfaceProtocol;
        __u8  iInterface;
} __attribute__ ((packed));
字段 含义
bLength 描述符长度
bDescriptorType 类型，接口描述符为 4
bInterfaceNumber 接口编号，编号相同代表同一功能接口
bAlternateSetting 接口设置编号，同一接口可有多个设置代表不同参数
bNumEndpoints 本设置使用的端点数，不含端点 0
bInterfaceClass 接口类型
bInterfaceSubClass 接口子类型
bInterfaceProtocol 接口遵循的协议
iInterface 接口字符串索引

bAlternateSetting 是很多人第一次踩坑的地方。UVC 摄像头、USB 音频这类周期传输设备，带宽需求在运行中会变，靠切换 altsetting 重新分配预留带宽。altsetting 0 常常是「零带宽待机」配置，只有零星控制端点；真正出图的 altsetting 才带等时端点。协议规定 altsetting 编号从 0 连续排到 n-1，但确实有设备搞错，内核对数组顺序也不保证有序，所以查 altsetting 要用 usb_altnum_to_altsetting()，别自己按下标猜。

HID 与字符串描述符 #

HID 类设备（键盘、鼠标、触摸屏）在接口描述符后面跟两个类描述符：

  • HID 描述符，bDescriptorType = 0x21，由 struct hid_descriptor 描述，内含 HID 版本号、国家码、报告描述符长度等。
  • 报告描述符（Report Descriptor），bDescriptorType = 0x22，是一段用 HID 项目（item）编码的脚本，描述每个「报告」里哪些位是按键、哪些位是轴、取值范围多少。这一段不是 C 结构体，得用 hid_parse_report() 或直接搬到用户态解析。

字符串描述符（bDescriptorType = 3）没有独立结构体，内容是一串 UTF-16LE 编码的字符串。设备描述符和配置、接口描述符里的 iManufacturer、iProduct、iSerialNumber、iConfiguration、iInterface 都是索引，0 表示「无此字符串」。读字符串要先读语言 ID（索引 0），拿到 wLANGID 数组，再按语言 ID 去读具体字符串，内核用 usb_string() 封好了这套流程，usb_cache_string() 会把结果缓存在 usb_device 的 product、manufacturer、serial 字段里。usb_device.have_langid 和 string_langid 就是给这套缓存记状态的。

内核里描述符怎么存 #

四个描述符结构体内核各有一份「host 侧包装」，多带了额外描述符和端点数组：

协议描述符 内核包装结构 主要增量
配置 usb_host_config 接口数组、intf_cache、IAD、extra
接口 usb_host_interface 端点数组 endpoint、extra、string
端点 usb_host_endpoint urb_list、hcpriv、enabled、streams

struct usb_host_interface 的定义：

c
/* host-side wrapper for one interface setting's parsed descriptors */
struct usb_host_interface {
        struct usb_interface_descriptor desc;

        int extralen;
        unsigned char *extra;   /* Extra descriptors */

        /* array of desc.bNumEndpoints endpoints associated with this
         * interface setting.  these will be in no particular order.
         */
        struct usb_host_endpoint *endpoint;

        char *string;           /* iInterface string, if present */
};

字段：desc 是接口描述符；endpoint 是本接口设置下所有端点；extra 是额外描述符。

struct usb_host_config 的定义：

c
struct usb_host_config {
        struct usb_config_descriptor    desc;

        char *string;           /* iConfiguration string, if present */

        /* List of any Interface Association Descriptors in this
         * configuration. */
        struct usb_interface_assoc_descriptor *intf_assoc[USB_MAXIADS];

        /* the interfaces associated with this configuration,
         * stored in no particular order */
        struct usb_interface *interface[USB_MAXINTERFACES];

        /* Interface information available even when this is not the
         * active configuration */
        struct usb_interface_cache *intf_cache[USB_MAXINTERFACES];

        unsigned char *extra;   /* Extra descriptors */
        int extralen;
};

字段：desc 是配置描述符；interface 是本配置包含的所有接口（只在该配置激活时可用）；intf_cache 是接口缓存，在设备整个生命周期内都在，所以不激活配置也能看接口信息；extra 是额外描述符。

usb_ifnum_to_if() 按编号查接口，usb_altnum_to_altsetting() 按编号查 altsetting——用这两个，别依赖数组顺序。

七、枚举过程：设备怎么被识别 #

USB 总线上的所有通信都由主机发起，本质上 USB 全是轮询：

  1. 主机轮询检测总线上有没有设备接入，有设备接入，对应的 D+ 或 D- 就有电平变化。
  2. USB 总线按协议与设备通信，设备把存在自己身上的设备信息依次交给主机。
  3. 主机把这些信息组织起来上报内核，内核的 USB 子系统再去匹配对应的设备驱动。

这里说的「主机」指 USB 主机控制器。

一次完整枚举走这些步：

步骤 动作 用的传输
1 Hub 检测到端口电平变化，上报根 Hub / 上层 Hub 硬件中断 + Hub 类请求
2 主机给设备复位（至少 10 ms），设备进入 Default 状态 复位信号
3 主机读设备描述符前 8 字节，拿到 bMaxPacketSize0 控制传输，地址 0，EP0
4 主机分配设备地址，SET_ADDRESS 下发给设备 控制传输，地址 0，EP0
5 用新地址重读完整 18 字节设备描述符 控制传输，EP0
6 读配置描述符 9 字节，取 wTotalLength 控制传输，EP0
7 按 wTotalLength 读回整棵描述符树 控制传输，EP0
8 读字符串描述符（语言 ID → 厂商 / 产品 / 序列号） 控制传输，EP0
9 SET_CONFIGURATION 下发 bConfigurationValue，设备进入 Configured 状态 控制传输，EP0
10 内核创建 usb_interface 设备，注册到 usb_bus_type，匹配接口驱动 —

几个细节值得记。

为什么要先读 8 字节。 枚举开始时不知道设备的 bMaxPacketSize0，只能按最小值 8 字节去要。读完前半段拿到真实包长（8/16/32/64），后面才能一次搬更多。

地址 0 是共享的。 刚插上的设备都用地址 0，所以枚举必须串行——主机不会同时枚举两个设备，否则地址 0 上两个设备会撞。

配置从哪来。 内核的设备驱动不应该自己去激活配置。「装哪个配置」是策略决定，取决于可用供电、功能需求、用户意愿（用户态工具表达）。驱动可以调 usb_reset_configuration() 重新初始化当前配置和它的全部接口，但不要自己挑配置。 枚举收尾后。 设备进入 Configured 状态，所有 usb_interface 被创建并挂到 usb_bus_type 上，从这一刻开始接口驱动才有机会 probe。开篇那句 usb 1-1: new low-speed USB device number 2 using s3c2410-ohci 就是这一串流程走完时打的日志。

枚举失败的常见表现和原因：

日志 含义
device descriptor read/64, error -71 EP0 通信出错，-71 是 -EPROTO，多半是信号质量或供电
device not accepting address N, error -71 SET_ADDRESS 没生效，设备固件或 D+ 上拉不稳
device descriptor read/8, error -32 -EPIPE，EP0 被 stall，设备固件拒绝
unable to enumerate USB device 上面任一步反复重试后放弃

-EPROTO 在板子上出现，先量 VBUS 和地，再看差分线有没有串阻、ESD 器件是否漏电。这条排查线在《USB 平台调试：RK3399、RK3588 与 Type-C》里有更细的做法。

八、Linux USB 驱动框架的四层结构 #

USB 驱动分三类（按职责，gadget 单列）：

  • USB 主机控制器驱动：创建 HCD、创建并注册根 Hub 设备。
  • 主机端 USB 设备驱动，准确说是 usb 接口驱动——这是驱动工程师的主要战场。
  • 设备端 USB Gadget 驱动，即把本机当从设备时跑的驱动。

标准 USB 设备的控制器驱动内核已经写好了，gadget 驱动大多跑在固件里而不是 Linux 上。所以驱动工程师的活儿集中在主机端设备驱动。

框架分四层：

层次 代码位置 职责 你碰不碰
USB 设备驱动（usb_driver） drivers/usb/*（class、storage、serial、hid…） 按 ID 表匹配接口，实现业务 主要工作区
USB 核心（usbcore） drivers/usb/core/ 枚举、描述符解析、设备/接口注册、ID 匹配、URB 排队 读它，不改它
主机控制器驱动（HCD） drivers/usb/host/ 把 URB 翻译成控制器寄存器操作，管 DMA 与调度 平台适配时碰
主机控制器硬件 SoC 内 EHCI / OHCI / UHCI / xHCI 不看

usbcore：纯软件的协议栈 #

USB Core 是纯软件模块，不代表任何设备，独立于硬件的协议栈，是所有 USB 设备赖以生存的部分，即 USB 子系统的核心。代码在 drivers/usb/core。

它的职责：

  • 识别 USB 设备：分配地址、把地址告诉设备、发命令获取描述符。
  • 查找并安装对应的 USB 设备驱动（准确说是 usb 接口驱动）。
  • 提供 USB 读写函数：usb_submit_urb、usb_bulk_msg、usb_control_msg 都在这一层。

向上，它为 USB 设备驱动提供编程接口；向下，它为 USB 主机控制器驱动提供编程接口。它维护整个系统的 USB 设备信息，完成热插拔控制、总线数据传输控制。用户请求由核心层映射到对应的 HCD，用户不能直接访问 HCD——核心层就是 HCD 与 USB 设备之间的桥。

HCD：主机控制器的抽象 #

硬件主机控制器（Host Controller）之上跑的是 USB HCD，它是主机控制器的抽象，实现核心层与主机控制器之间的对话接口。代码在 drivers/usb/host。

主机控制器有几种类型，OHCI、UHCI、EHCI、xHCI，区别与联系这里不展开，看《USB 主机控制器驱动》。你只需要记住：接口驱动永远不碰寄存器，只提交 URB。

一个设备怎么变成一棵设备树 #

USB 设备的逻辑划分是「配置 → 接口 → 端点」，内核把它映射成两层 device：

  • 每个 USB 设备是一个 device，具体是 struct usb_device。
  • 每个接口也是一个 device，具体是 struct usb_interface，代表一个逻辑设备。

两类 device 都注册到同一条总线 usb_bus_type 上，靠 match 函数区分，再各自绑不同的 driver。

具体的绑定路径：

  1. 所有 USB 设备都会先和 usb_generic_driver 匹配。这个设备驱动在 USB 子系统初始化时注册。
  2. 设备插入后，usb_generic_driver 与设备交互，读出全部描述符。
  3. 核心层为每个接口创建一个 device，挂到 usb 总线上。
  4. 接口 device 再去匹配对应的接口驱动（usb_driver）。

这就是为什么你写的 probe 拿到的第一个参数是 usb_interface * 而不是 usb_device *——你绑的是接口，不是设备。

struct usb_interface #

struct usb_interface 描述 USB 接口。USB 核心把这个结构体传给 USB 设备驱动，之后由驱动负责控制它。定义在 include/linux/usb.h：

c
struct usb_interface {
        /* array of alternate settings for this interface,
         * stored in no particular order */
        struct usb_host_interface *altsetting;

        struct usb_host_interface *cur_altsetting;      /* the currently
                                         * active alternate setting */
        unsigned num_altsetting;        /* number of alternate settings */

        /* If there is an interface association descriptor then it will list
         * the associated interfaces */
        struct usb_interface_assoc_descriptor *intf_assoc;

        int minor;                      /* minor number this interface is
                                         * bound to */
        enum usb_interface_condition condition;         /* state of binding */
        unsigned sysfs_files_created:1; /* the sysfs attributes exist */
        unsigned ep_devs_created:1;     /* endpoint "devices" exist */
        unsigned unregistering:1;       /* unregistration is in progress */
        unsigned needs_remote_wakeup:1; /* driver requires remote wakeup */
        unsigned needs_altsetting0:1;   /* switch to altsetting 0 is pending */
        unsigned needs_binding:1;       /* needs delayed unbind/rebind */
        unsigned resetting_device:1;    /* true: bandwidth alloc after reset */
        unsigned authorized:1;          /* used for interface authorization */

        struct device dev;              /* interface specific device info */
        struct device *usb_dev;
        struct work_struct reset_ws;    /* for resets in atomic context */
};

字段速查：

字段 含义
altsetting 该接口所有可选设置的数组。每个 usb_host_interface 含一套 usb_host_endpoint 端点配置。数组没有固定顺序
cur_altsetting 指向 altsetting 内部，当前激活的那一个
num_altsetting 可选设置的数量
intf_assoc 接口关联描述符（IAD），列出关联的接口
minor 若绑定到使用 USB 主设备号的驱动，这里是核心分配的次设备号。只在 usb_register_dev() 成功后有意义
condition 绑定状态：未绑定、绑定中（在 probe 里）、已绑定、解绑中（在 disconnect 里）
sysfs_files_created sysfs 属性已创建
ep_devs_created 端点伪设备已创建
unregistering 正在注销
needs_remote_wakeup 自动挂起期间驱动需要远程唤醒能力
needs_altsetting0 切到 altsetting 0 的 set-interface 请求被推迟了
needs_binding 复位/挂起后需要延迟重新 probe 或解绑
resetting_device 核心复位了设备，用 altsetting 0，复位后要重新分配带宽
authorized 单接口级别的授权，区别于整设备的授权
dev 设备模型视角的 device
usb_dev 若接口绑到 USB 主设备号，指向该设备的 sysfs 表示
reset_ws 原子上下文里调度复位用的 work

usb_interface 的设计意图在内核注释里写得很清楚：

  • USB 设备驱动绑在物理设备的接口上。每个接口封装一个高层功能，比如给音箱送音频流，或者报告音量控件变化。
  • 很多 USB 设备只有一个接口。
  • 与接口端点通信的协议由 USB class 规范定义，或由厂商定义。
  • 默认控制端点属于每个接口，但不列在接口描述符里。
  • 每个接口可以有 altsetting。初始配置设定 altsetting 0，驱动可用 usb_set_interface() 切换。altsetting 常用于控制周期端点的使用，比如让不同端点预留不同带宽。
  • 用等时端点的合规设备一定在非默认设置里使用它们。
  • 接口编号应为 0 到 n-1，不少设备搞错，数组也不保证有序，所以用 usb_ifnum_to_if() 查。

驱动拿到 usb_interface 后，可以对 dev 成员用标准驱动模型调用，比如 dev_get_drvdata()、usb_get_intfdata()、usb_set_intfdata()。

两个 device 类型怎么区分 #

usb_device 和 usb_interface 都是 struct device，靠 dev->type 区分：

结构体 dev.type 判断宏 转换宏
usb_device usb_device_type is_usb_device(dev) to_usb_device(dev)
usb_interface usb_if_device_type is_usb_interface(dev) to_usb_interface(dev)

从接口反查设备：interface_to_usbdev(interface)。这个宏走 dev.parent，不涉及引用计数——要用得久，得配 usb_get_dev()。

十、usb_driver：设备驱动的注册 #

usb_driver 结构体 #

在 Linux 设备模型里，USB 接口驱动由 usb_driver 表示，定义在 include/linux/usb.h：

                        void *buf);

        int (*resume) (struct usb_interface *intf);
        int (*reset_resume)(struct usb_interface *intf);

        int (*pre_reset)(struct usb_interface *intf);
        int (*post_reset)(struct usb_interface *intf);

        const struct usb_device_id *id_table;

        struct usbdrv_wrap drvwrap;

        unsigned int supports_autosuspend:1;

成员 含义
name 驱动名，在 USB 驱动中必须唯一，与模块名一致是好习惯
probe 判断驱动是否愿意接管某个接口。愿意则返回 0，并用 usb_set_intfdata() 把私有数据和接口绑定，可用 usb_set_interface() 选合适的 altsetting。不愿接管返回 -ENODEV，真出错返回对应的负 errno
disconnect 接口不可访问时调用，原因多半是设备被拔或模块被卸载
unlocked_ioctl 驱动想通过 usbfs 与用户态对话时用
suspend / resume 系统睡眠或 runtime suspend 时调用。系统睡眠上下文里返回值被忽略，suspend 失败也别继续用设备，交给 resume/reset_resume 恢复
reset_resume 挂起的设备是被复位而不是被唤醒时调用
pre_reset usb_reset_device() 复位之前调用。必须等到驱动没有活动 URB 才能返回，且在 post_reset 之前不许再提交 URB
post_reset 复位之后调用
id_table ID 表，热插拔靠它。必须设置，否则 probe 永远不会被调用。要用 MODULE_DEVICE_TABLE(usb, ...) 导出
dynids 内部用，存动态添加的设备 ID
drvwrap 驱动模型核心结构的包装
no_dynamic_id 置 1 时内核不让通过 sysfs 动态加 ID
supports_autosuspend 置 0 时内核不允许绑定到此驱动的接口自动挂起
disable_hub_initiated_lpm 置 1 时不允许 Hub 在空闲超时后发起低功耗链路状态切换。设备发起的 USB 3.0 链路电源管理仍然允许
soft_unbind 置 1 时内核在调 disconnect 前不杀 URB、不禁用端点

接口驱动必须提供 name、probe、disconnect、id_table，其余可选。probe 和 disconnect 在可以睡眠的上下文里调用，但也别滥用这特权——连设备的活放到 open 里做，close 里撤，disconnect 要处理与 open/close 的并发，并且强制所有在途 IO 完成（该 unlink 的 unlink，并阻塞到 unlink 完成）。

usb_register：注册流程 #

usb_register 是个宏，定义在 include/linux/usb.h：

c
/* use a define to avoid include chaining to get THIS_MODULE & friends */
#define usb_register(driver) \
        usb_register_driver(driver, THIS_MODULE, KBUILD_MODNAME)

真正干活的是 usb_register_driver，在 drivers/usb/core/driver.c：

c
int usb_register_driver(struct usb_driver *new_driver, struct module *owner,
                        const char *mod_name)
{
        int retval = 0;

        if (usb_disabled())
                return -ENODEV;

        new_driver->drvwrap.for_devices = 0;
        new_driver->drvwrap.driver.name = new_driver->name;
        new_driver->drvwrap.driver.bus = &usb_bus_type;
        new_driver->drvwrap.driver.probe = usb_probe_interface;
        new_driver->drvwrap.driver.remove = usb_unbind_interface;
        new_driver->drvwrap.driver.owner = owner;
        new_driver->drvwrap.driver.mod_name = mod_name;
        spin_lock_init(&new_driver->dynids.lock);
        INIT_LIST_HEAD(&new_driver->dynids.list);

        retval = driver_register(&new_driver->drvwrap.driver);
        if (retval)
                goto out;

        retval = usb_create_newid_files(new_driver);
        if (retval)
                goto out_newid;

        pr_info("%s: registered new interface driver %s\n",
                        usbcore_name, new_driver->name);

out:
        return retval;

out_newid:
        driver_unregister(&new_driver->drvwrap.driver);

        printk(KERN_ERR "%s: error %d registering interface "
                        "       driver %s\n",
                        usbcore_name, retval, new_driver->name);
        goto out;
}

按顺序看它做了什么：

  1. usb_disabled() 检查，内核启动带了 nousb 就直接 -ENODEV 回绝。
  2. drvwrap.for_devices = 0，把自己标记成接口驱动而不是设备驱动。
  3. 填驱动基类：name、bus = &usb_bus_type、probe、remove、owner、mod_name。注意这里挂的 probe 是 usb_probe_interface，不是你的 probe——它是个中转函数。
  4. 初始化动态 ID 链表与自旋锁。
  5. driver_register(&new_driver->drvwrap.driver)，把驱动挂到总线上。
  6. usb_create_newid_files() 建 sysfs 的 new_id 文件，之后可以 echo 1234 5678 > new_id 动态加 ID。
  7. 打一行 registered new interface driver 日志。

driver_register 往下做的事：

  • 把接口驱动加到 usb 总线（usb_bus_type）的驱动链表上。
  • 遍历总线上的所有接口，调 usb_device_match 做匹配。
  • 匹配上，最终执行接口驱动的 probe。中间的 driver.probe（即 usb_probe_interface）只是中转。

所以注册顺序无所谓：先有接口后注册驱动，驱动注册时会扫一遍现存接口；先有驱动后插设备，usb_device_match 会在新接口加入时命中。

usbdrv_wrap：一个包装解决两种驱动 #

usb_device_driver 和 usb_driver 都包含一项 struct usbdrv_wrap：

c
struct usbdrv_wrap {
    struct device_driver driver;
    int for_devices;
}

for_devices 标记这个驱动是设备驱动还是接口驱动。usb_register_device_driver 注册时置 1，usb_register_driver 注册时置 0。usb_device_match 里的 is_usb_device_driver() 判断的就是这个位。

这个包装存在的理由很实际：设备驱动和接口驱动都要变成 device_driver 挂到 usb_bus_type 上，但内核要知道它是哪一种，才能在 match 时把两类 driver 分成两条路。历史原因，for_devices 是 int 而不是 bool，占位浪费了一点，但接口稳定（5.2 内核仍是这个定义）。

usb_deregister：注销 #

usb_deregister 在 drivers/usb/core/driver.c：

c
void usb_deregister(struct usb_driver *driver)
{
        pr_info("%s: deregistering interface driver %s\n",
                        usbcore_name, driver->name);

        usb_remove_newid_files(driver);

删 new_id 文件、driver_unregister、释放动态 ID。注意 usb_register_dev() 申请的次设备号不在这里回收——你在 disconnect 里自己调过 usb_deregister_dev() 才干净。

对比：usb_device_driver #

设备驱动用 usb_device_driver 表示，同样在 include/linux/usb.h：

struct usb_device_driver {
        const char *name;

        int (*probe) (struct usb_device *udev);
        void (*disconnect) (struct usb_device *udev);

        int (*suspend) (struct usb_device *udev, pm_message_t message);

区别一眼可见：参数是 usb_device *，不是 usb_interface *。

        new_udriver->drvwrap.driver.probe = usb_probe_device;
        new_udriver->drvwrap.driver.remove = usb_unbind_device;

注册后，总线上的所有 USB 设备都会和它匹配——因为 usb_device_match 对设备的处理是「只要对方是设备驱动就返回 1」，匹配逻辑在那个位置写死为总是成立。

        .probe = generic_probe,
        .disconnect = generic_disconnect,

        .resume = generic_resume,

所有 USB 设备注册到总线后都会和它匹配成功，都会走 generic_probe。你在 sysfs 的 /sys/bus/usb/drivers/usb/ 下看到的那个 usb 驱动就是它。

usb_deregister_device_driver() 是它的注销路径，只调 driver_unregister。

usb_device_match #

c
static int usb_device_match(struct device *dev, struct device_driver *drv)
{
        /* devices and interfaces are handled separately */
        if (is_usb_device(dev)) {

                /* interface drivers never match devices */
                if (!is_usb_device_driver(drv))
                        return 0;

                /* TODO: Add real matching code */
                return 1;

        } else if (is_usb_interface(dev)) {
                struct usb_interface *intf;
                struct usb_driver *usb_drv;
                const struct usb_device_id *id;

                /* device drivers never match interfaces */
                if (is_usb_device_driver(drv))
                        return 0;

                intf = to_usb_interface(dev);
                usb_drv = to_usb_driver(drv);

                id = usb_match_id(intf, usb_drv->id_table);
                if (id)
                        return 1;

                id = usb_match_dynamic_id(intf, usb_drv);
                if (id)
                        return 1;
        }

        return 0;
}

两个参数是新设备与驱动，函数分两条路：

  • 设备侧：只接受设备驱动，返回 1。那句 TODO: Add real matching code 说明这条路的匹配是写死的，所有 USB 设备都归 usb_generic_driver 管。注意这个函数在这里返回 1 表示「匹配」，0 表示不匹配，跟 bus_type.match 注释里「返回正值表示可以处理」的约定略有出入，看代码时按实现走。
  • 接口侧：先排除设备驱动，再用 usb_match_id() 对比 id_table，然后用 usb_match_dynamic_id() 查动态 ID。任一命中即返回 1。

驱动工程师的工作集中在接口驱动上，所以我们平时用 usb_register 注册，不是 usb_register_device_driver。

usb_match_id 与三级匹配 #

usb_match_id() 在 drivers/usb/core/driver.c：

c
const struct usb_device_id *usb_match_id(struct usb_interface *interface,
                                         const struct usb_device_id *id)
{
        /* proc_connectinfo in devio.c may call us with id == NULL. */
        if (id == NULL)
                return NULL;

        /* It is important to check that id->driver_info is nonzero,
           since an entry that is all zeroes except for a nonzero
           id->driver_info is the way to create an entry that
           indicates that the driver want to examine every
           device and interface. */
        for (; id->idVendor || id->idProduct || id->bDeviceClass ||
               id->bInterfaceClass || id->driver_info; id++) {
                if (usb_match_one_id(interface, id))
                        return id;
        }

        return NULL;
}

遍历 id_table 的每一项，只要 idVendor、idProduct、bDeviceClass、bInterfaceClass、driver_info 中任一项非零就去做比对。五项全零就是终止项。

这条规则给了一个通用匹配技巧：只填 driver_info、其它全零的项，等于「匹配一切」，驱动在 probe 里自己拿主意要不要接管。usbhid 之类的驱动就这么干过。

usb_match_one_id() 分两段——先比设备描述符，再比接口描述符：

c
int usb_match_one_id(struct usb_interface *interface,
                     const struct usb_device_id *id)
{
        struct usb_host_interface *intf;
        struct usb_device *dev;

        /* proc_connectinfo in devio.c may call us with id == NULL. */
        if (id == NULL)
                return 0;

        intf = interface->cur_altsetting;
        dev = interface_to_usbdev(interface);

        if (!usb_match_device(dev, id))
                return 0;

        return usb_match_one_id_intf(dev, intf, id);
}

设备段 usb_match_device()：

c
/* returns 0 if no match, 1 if match */
int usb_match_device(struct usb_device *dev, const struct usb_device_id *id)
{
        if ((id->match_flags & USB_DEVICE_ID_MATCH_VENDOR) &&
            id->idVendor != le16_to_cpu(dev->descriptor.idVendor))
                return 0;

        if ((id->match_flags & USB_DEVICE_ID_MATCH_PRODUCT) &&
            id->idProduct != le16_to_cpu(dev->descriptor.idProduct))
                return 0;

        /* No need to test id->bcdDevice_lo != 0, since 0 is never
           greater than any unsigned number. */
        if ((id->match_flags & USB_DEVICE_ID_MATCH_DEV_LO) &&
            (id->bcdDevice_lo > le16_to_cpu(dev->descriptor.bcdDevice)))
                return 0;

        if ((id->match_flags & USB_DEVICE_ID_MATCH_DEV_HI) &&
            (id->bcdDevice_hi < le16_to_cpu(dev->descriptor.bcdDevice)))
                return 0;

        if ((id->match_flags & USB_DEVICE_ID_MATCH_DEV_CLASS) &&
            (id->bDeviceClass != dev->descriptor.bDeviceClass))
                return 0;

        if ((id->match_flags & USB_DEVICE_ID_MATCH_DEV_SUBCLASS) &&
            (id->bDeviceSubClass != dev->descriptor.bDeviceSubClass))
                return 0;

        if ((id->match_flags & USB_DEVICE_ID_MATCH_DEV_PROTOCOL) &&
            (id->bDeviceProtocol != dev->descriptor.bDeviceProtocol))
                return 0;

        return 1;
}

接口段 usb_match_one_id_intf()：

c
/* returns 0 if no match, 1 if match */
int usb_match_one_id_intf(struct usb_device *dev,
                          struct usb_host_interface *intf,
                          const struct usb_device_id *id)
{
        /* The interface class, subclass, protocol and number should never be
         * checked for a match if the device class is Vendor Specific,
         * unless the match record specifies the Vendor ID. */
        if (dev->descriptor.bDeviceClass == USB_CLASS_VENDOR_SPEC &&
                        !(id->match_flags & USB_DEVICE_ID_MATCH_VENDOR) &&
                        (id->match_flags & (USB_DEVICE_ID_MATCH_INT_CLASS |
                                USB_DEVICE_ID_MATCH_INT_SUBCLASS |
                                USB_DEVICE_ID_MATCH_INT_PROTOCOL |
                                USB_DEVICE_ID_MATCH_INT_NUMBER)))
                return 0;

        if ((id->match_flags & USB_DEVICE_ID_MATCH_INT_CLASS) &&
            (id->bInterfaceClass != intf->desc.bInterfaceClass))
                return 0;

        if ((id->match_flags & USB_DEVICE_ID_MATCH_INT_SUBCLASS) &&
            (id->bInterfaceSubClass != intf->desc.bInterfaceSubClass))
                return 0;

        if ((id->match_flags & USB_DEVICE_ID_MATCH_INT_PROTOCOL) &&
            (id->bInterfaceProtocol != intf->desc.bInterfaceProtocol))
                return 0;

        if ((id->match_flags & USB_DEVICE_ID_MATCH_INT_NUMBER) &&
            (id->bInterfaceNumber != intf->desc.bInterfaceNumber))
                return 0;

        return 1;
}

match_flags 的每一位管一个字段，位没置就跳过对应比较。合起来就是三级匹配的优先级：

匹配方式 用的宏 比对的字段 粒度
产品级 USB_DEVICE(v, p) idVendor + idProduct 最具体，可加版本区间
设备类级 USB_DEVICE_INFO(cls, sub, proto) bDeviceClass/SubClass/Protocol 稍泛，单功能设备用
接口类级 USB_INTERFACE_INFO(cls, sub, proto) bInterfaceClass/SubClass/Protocol 最泛，多功能设备用

有两条坑写在注释里：

  1. 设备类为 Vendor-Specific 时，接口类匹配直接失效，除非 ID 项里同时指定了厂商 ID。协议规定这类设备的接口 class/subclass/protocol 也是厂商自定义的，拿标准类去比没有意义。真要用接口匹配，就得造一条同时带 idVendor 的记录——标准宏里没有现成的。
  2. ID 表要从具体到泛排列。匹配算法很简单，谁先命中算谁的，所以最具体的匹配放最前面，driver_info 才能记下具体产品的 quirk。usb_match_id 返回第一个命中的项，probe 的第二个参数就是它。

还有一条组合约束：别只给版本区间不给厂商/产品 ID，也别只给 protocol 不给 class 和 subclass——这种组合没有意义，只会让表更难读。

usb_device_id 结构体 #

定义在 include/linux/mod_devicetable.h：

c
struct usb_device_id {
        /* which fields to match against? */
        __u16           match_flags;

        /* Used for product specific matches; range is inclusive */
        __u16           idVendor;
        __u16           idProduct;
        __u16           bcdDevice_lo;
        __u16           bcdDevice_hi;

        /* Used for device class matches */
        __u8            bDeviceClass;
        __u8            bDeviceSubClass;
        __u8            bDeviceProtocol;

        /* Used for interface class matches */
        __u8            bInterfaceClass;
        __u8            bInterfaceSubClass;
        __u8            bInterfaceProtocol;

        /* Used for vendor-specific interface matches */
        __u8            bInterfaceNumber;

        /* not matched against */
        kernel_ulong_t  driver_info
                __attribute__((aligned(sizeof(kernel_ulong_t))));
};
字段 说明
match_flags 位掩码，控制哪些字段参与比较。除 driver_info 外任何字段都能用，有些字段只能跟别的字段搭配。由 USB_DEVICE_*() 宏自动填好
idVendor 设备厂商 ID
idProduct 厂商分配的产品 ID
bcdDevice_lo / bcdDevice_hi 产品版本号区间，闭区间。区间只含一个值时也能标识单个版本
bDeviceClass / bDeviceSubClass / bDeviceProtocol 设备类/子类/协议，描述设备上所有接口的行为
bInterfaceClass / bInterfaceSubClass / bInterfaceProtocol 接口类/子类/协议，只描述该接口的行为，其它接口可属别的类
bInterfaceNumber 接口号，复合设备可用固定接口号区分厂商自定义接口
driver_info 驱动自己的信息，不参与匹配，放 quirk 或指向驱动理解的描述结构

driver_info 那个 __aligned(sizeof(kernel_ulong_t)) 不是装饰——它是保证在 64 位平台上结构体对齐正确，顺便让 driver_info 能安全存指针。

RTL8152 的 ID 表长这样 #

真实驱动里，ID 表加宏的写法：

c
static const struct usb_device_id rtl8152_table[] = {
        { USB_DEVICE(VENDOR_ID_REALTEK, 0x8153) },
        { USB_DEVICE(VENDOR_ID_MICROSOFT, 0x07ab) },
        { USB_DEVICE(VENDOR_ID_SAMSUNG, 0xa101) },
        {},

MODULE_DEVICE_TABLE(usb, rtl8152_table);

MODULE_DEVICE_TABLE 的第一个参数是设备类型：USB 设备写 usb，PCI 设备写 pci，两个子系统用同一个宏注册各自支持的设备表。第二个参数是表名，最后那个空元素是终止项。这张表还会被抽出来写进模块的 modules.usbmap，用户态工具靠它决定插入设备时该 insmod 哪个模块。

十二、URB：USB 请求块 #

内核通过 URB（USB Request Block）和所有 USB 设备通信。URB 是 USB 设备驱动描述「与 USB 设备通信」的基本载体和核心数据结构，struct urb 定义在 include/linux/usb.h。

打个比方：USB 总线是高速公路，数据是货，URB 是卡车。端点有四种类型，卡车上能装的货就有四种，你只是得先告诉司机装什么、去哪。

URB 的分配与释放：

c
struct urb *usb_alloc_urb(int isoc_packets, gfp_t mem_flags);
void usb_free_urb(struct urb *urb);

isoc_packets 是等时包数量，非等时传 0。mem_flags 与 kmalloc 标志相同，GFP_ATOMIC 用于原子上下文。

完整结构体（5.x，字段顺序与注释照抄内核）：

        struct list_head anchor_list;   /* the URB may be anchored */

        struct usb_host_endpoint *ep;   /* (internal) pointer to endpoint */
        unsigned int pipe;              /* (in) pipe information */
        unsigned int stream_id;         /* (in) stream ID */
        int status;                     /* (return) non-ISO status */
        unsigned int transfer_flags;    /* (in) URB_SHORT_NOT_OK | ...*/
        void *transfer_buffer;          /* (in) associated data buffer */
        dma_addr_t transfer_dma;        /* (in) dma addr for transfer_buffer */
        struct scatterlist *sg;         /* (in) scatter gather buffer list */
        int num_mapped_sgs;             /* (internal) mapped sg entries */
        int num_sgs;                    /* (in) number of entries in the sg list */

十三、URB 的生命周期与回调 #

URB 的一生：

阶段 动作 函数
1 分配 usb_alloc_urb()
2 初始化（填 dev、pipe、buffer、complete） usb_fill_*_urb() 或手填字段
3 提交给 usbcore usb_submit_urb()
4 核心转给 HCD 内部
5 HCD 按 URB 描述访问设备 hcpriv 里的队列头、TD
6 访问结束，HCD 通知核心 硬件中断
7 核心调 complete 回调 你的回调函数
8 回调里决定重提交还是释放 usb_submit_urb() 或 usb_free_urb()

素材里的原始描述是同一件事：驱动创建并初始化访问特定端点的 URB，提交给 usb core；usb core 提交给 HCD；HCD 按 URB 描述的信息访问设备；访问结束后 HCD 通知 usb core（这时调 usb_complete_t complete），核心再通知设备驱动。

回调的上下文与纪律 #

内核注释把这个说透了，值得逐条抄下来当规矩：

  • 完成回调在 in_interrupt() 上下文里跑。所以回调里不能睡，不能用 GFP_KERNEL 分配内存，不能拿 mutex。
  • 回调第一件事应该是查 status。status 对所有 URB 都有，用来报告被 unlink 的 URB 和非等时传输的状态。在 URB 交给回调之前不要去看它。
  • 非等时 URB 完成时，actual_length 告诉你传了多少字节。即使 URB 异常结束或被 unlink，这个字段也会更新。
  • 等时传输的状态在 iso_frame_desc 数组每项的 status 和 actual_length 里，错误总数在 error_count。等时传输的回调里一般要重新提交 URB，才能维持恒定速率。
  • 从调用 usb_submit_urb() 到进入完成例程这段时间，URB 归 HCD 所有。即使是标着 public 的字段也不许驱动去碰，包括 status、actual_length、transfer_flags。

最后一条是踩坑重灾区。你在另一个线程里改 urb->transfer_flags、或者提前 kfree(urb->transfer_buffer)，都是在和 HCD 抢 DMA 缓冲区。

建 URB：三种 fill 函数 #

c
void usb_fill_int_urb(struct urb *urb, struct usb_device *dev,
                      unsigned int pipe, void *transfer_buffer,
                      int buffer_length, usb_complete_t complete,
                      void *context, int interval);

void usb_fill_bulk_urb(struct urb *urb, struct usb_device *dev,
                       unsigned int pipe, void *transfer_buffer,
                       int buffer_length, usb_complete_t complete,
                       void *context);

void usb_fill_control_urb(struct urb *urb, struct usb_device *dev,
                          unsigned int pipe, unsigned char *setup_packet,
                          void *transfer_buffer, int buffer_length,
                          usb_complete_t complete, void *context);

参数含义：transfer_buffer 是要送/收的数据缓冲，buffer_length 是长度，complete 是完成回调入口，context 由你定义、回调里取回来用，interval 是 URB 被调度的间隔。控制 URB 多一个 setup_packet，指向即将发到端点的 8 字节 setup 数据包。

等时 URB 没有专门的 fill 函数，只能逐个字段赋值，还要按 number_of_packets 补一串 iso_frame_desc。

（素材 3 把 usb_control_msg 的原型误写成 usb_fill_bulk_urb 重载，已更正为 usb_fill_control_urb。）

释放缓冲区 #

URB_NO_TRANSFER_DMA_MAP 置位后，DMA 映射是你自己做的，缓冲区也得你自己放。配套的是 usb_buffer_alloc() / usb_buffer_free()（现代内核里这两组被 usb_alloc_coherent() / usb_free_coherent() 取代，旧代码还能编译但属于过渡态）。

素材 3 的完成回调里有一句 usb_buffer_free(urb->dev, urb->transfer_buffer_length, urb->transfer_buffer, urb->transfer_dma)，transfer_flags 里也置了 URB_NO_TRANSFER_DMA_MAP。这两句是配套的，不能只留一半：只置标志不释放，内存泄漏；只释放不置标志，HCD 还在用那块 DMA 地址。

典型的完成回调 #

素材 3 的写法：

c
static void skel_write_bulk_callback(struct urb *urb)
{
        struct usb_skel *dev = (struct usb_skel *)urb->context;

        /* sync/async unlink faults aren't errors */
        if (urb->status && !(urb->status == -ENOENT ||
                             urb->status == -ECONNRESET ||
                             urb->status == -ESHUTDOWN))
                dbg("%s - nonzero write bulk status received: %d",
                    __func__, urb->status);

        /* free up our allocated buffer */
        usb_buffer_free(urb->dev, urb->transfer_buffer_length,
                        urb->transfer_buffer, urb->transfer_dma);
}

注意那个 if 的写法：-ENOENT（URB 被 unlink 且未提交）、-ECONNRESET（被 unlink 前已提交）、-ESHUTDOWN（端点被禁）这三种状态不算错误，是驱动自己或热插拔的正常结果。只有其它非零状态才是真错。漏了这个判断的驱动，在拔出设备时会刷一屏假错误。

dbg() 和 __FUNCTION__ 是老内核的习惯，__FUNCTION__ 后来被 __func__ 取代。

取消 URB #

函数 行为

usb_unlink_urb(urb) 异步取消，立即返回，回调稍后执行

十四、usb_submit_urb 的完整流程 #

提交入口：

c
int usb_submit_urb(struct urb *urb, gfp_t mem_flags);

mem_flags 用 GFP_ATOMIC、GFP_NOIO、GFP_KERNEL 三选一。中断上下文用 GFP_ATOMIC；在 probe、open 这类能睡的上下文用 GFP_KERNEL；USB 存储这类在 IO 路径上提交、又怕死锁的用 GFP_NOIO。

调用前必须填好的字段（内核注释里的「Initialization」段）：

字段 是否必须
dev 必须
pipe 必须
transfer_flags 必须（可置 0）
complete 必须
transfer_buffer + transfer_buffer_length 必须
setup_packet 控制 URB 必须，且不能被预先 DMA 映射
interval 中断 URB 必须
number_of_packets + iso_frame_desc 等时 URB 必须

setup_packet 有个硬性要求：它不能放在 highmem，因为不能被预先映射。transfer_buffer 在控制器不支持 DMA（bus.uses_dma 为假）或跟根 Hub 通信时必须设着；如果缓冲区在 highmem 且控制器支持 DMA，可以置 NULL，让 usbmon 别去读它。

提交之后的处理路径：

text
usb_submit_urb(urb, mem_flags)
  └─> 校验 urb->dev / pipe / complete / ep->enabled
  └─> 按 pipe 找到 usb_host_endpoint（urb->ep）
  └─> 按 pipe 类型选 transfer_buffer 的 DMA 映射方式
  └─> 交给 HCD 的 urb_enqueue 回调
        └─> EHCI/OHCI/xHCI 具体实现：组 QH/TD、写寄存器、开门铃
  └─> 硬件完成 -> HCD 中断 -> urb->complete(urb)

urb_enqueue 是 struct hc_driver 里的成员。四个控制器驱动各自实现，这一段看《USB 主机控制器驱动》。

提交失败的常见返回值：

返回值 含义
-ENODEV urb->dev 为空，或设备已断开
-ENOENT urb->ep 为空，端点无效
-EINVAL 必填字段缺失，或 pipe 与端点类型不符
-EPIPE ep->enabled 为 0，端点被禁用
-ENOMEM 内存或 DMA 映射失败
-EAGAIN 并发提交超限（use_count）
-EXDEV 等时 URB 的 interval 与端点要求不一致

在 probe 里提交失败，别急着 goto error，先看 urb->status 和返回值对不对得上：-EPIPE 多半是你拿到了端点但接口还没激活，-EINVAL 多半是 pipe 用了错的宏（比如 OUT 端点用了 usb_rcvbulkpipe）。

等时传输的调度细节 #

等时端点队列没跑起来时，HCD 会在带宽允许的情况下尽快排这个 URB。队列在跑时，新 URB 排在前一个 URB 结束后的第一个传输槽，前提是那个槽还没过期。槽过期了（IRQ 延迟太久会出现），行为取决于 URB_ISO_ASAP：

  • 标志清零：URB 排进已过期的槽，意味着它的一部分包不会被传。
  • 标志置位：URB 排进第一个未过期的槽，代价是打断队列的同步。

完成后 start_frame 回填实际调度的帧号。帧号范围依控制器而定，小到 256、大到 65536 都有。

等时的数据传输模型跟别的不同，部分原因是它只提供「尽力而为」的服务质量。调用者提供专门分配的 URB，尾部带 number_of_packets 个 iso_frame_desc，每个描述一个独立的等时传输。等时 URB 一般成队列提交，至少做双缓冲，然后在完成回调里显式重提交，这样音频、视频流能以 HCD 调度器撑得住的恒定速率跑。

再补一条：等时端点和高速度中断端点的 interval 在端点描述符里是对数编码的，驱动得自己转成线性单位。UVC 驱动把 bInterval 直接当毫秒用，就是这一步漏了（1 ms 与 125 µs 差 8 倍）。

十五、同步与异步传输 #

两种用法，选错了就是白写。

用法 接口 上下文 适合
异步 usb_submit_urb() + complete 回调 回调在中断上下文 周期数据流、高吞吐、不能阻塞的路径
同步（阻塞） usb_control_msg() / usb_bulk_msg() / usb_interrupt_msg() 进程上下文，会睡 probe 里读寄存器、小数据量一次性读写、初始化
流式 usb_sg_* 进程上下文 大块散列 DMA 传输

异步的要点前面讲了：提交、回调、合法性状态判断、必要时重提交。数据量不大时不必开卡车，内核直接封了一套阻塞接口。

十六、usb_control_msg 与批量传输 #

usb_bulk_msg #

c
int usb_bulk_msg(struct usb_device *usb_dev, unsigned int pipe,
                 void *data, int len, int *actual_length, int timeout);

阻塞到传完或超时。data 是输入/输出缓冲，len 是大小，actual_length 回填实际传输量，timeout 是阻塞超时（毫秒）。返回值 0 表示成功，负值表示失败。

素材里 usb-skeleton 的读操作就是这么实现的：

c
/* do a blocking bulk read to get data from the device */
retval = usb_bulk_msg(dev->udev,
                      usb_rcvbulkpipe(dev->udev, dev->bulk_in_endpointAddr),
                      dev->bulk_in_buffer,
                      min(dev->bulk_in_size, count),
                      &bytes_read, 10000);

/* if the read was successful, copy the data to userspace */
if (!retval) {
        if (copy_to_user(buffer, dev->bulk_in_buffer, bytes_read))
                retval = -EFAULT;
        else
                retval = bytes_read;
}

两个细节值得学：用 min() 把读长度夹到缓冲区大小之内，超时给足 10 s（这个值随设备改，U 盘可以短，USB 串口长一点更稳）。

usb_control_msg #

c
int usb_control_msg(struct usb_device *dev, unsigned int pipe, __u8 request,
                    __u8 requesttype, __u16 value, __u16 index,
                    void *data, __u16 size, int timeout);

参数和 USB 协议里 setup 包的 8 个字节一一对应：

参数 对应 setup 字段 含义
requesttype bmRequestType 请求类型：方向位 + 类型（标准/类/厂商）+ 接收者（设备/接口/端点）
request bRequest 具体请求代码，如 GET_DESCRIPTOR、SET_CONFIGURATION
value wValue 请求值，含义随请求变
index wIndex 索引，多半是接口号或端点号
data + size data stage 数据阶段缓冲区与长度
timeout — 毫秒超时

（素材 3 把原型写成 Int usb_contrl_msg(...)，函数名拼错、返回类型首字母大写，已更正。）

bmRequestType 的方向位决定数据往哪边走：USB_DIR_IN 是设备到主机，USB_DIR_OUT 是主机到设备。pipe 的宏必须和方向位一致，一个 usb_sndctrlpipe 配着 USB_DIR_IN 用，控制器会给你 -EPIPE 或者直接超时。

value 和 index 分别代表什么，素材作者当年直说「暂时不是非常清晰」。这里补全：wValue 和 wIndex 的解释权归 bRequest 和 bRequestType，查 USB 协议第 9 章的表。举几个常见的：

请求 wValue wIndex
GET_DESCRIPTOR 高字节描述符类型，低字节索引 语言 ID（字符串描述符）或 0
SET_ADDRESS 新设备地址 0
SET_CONFIGURATION 配置值 0
SET_INTERFACE altsetting 号 接口号
CLEAR_FEATURE(HALT) 0 端点号

类请求（比如 HID 的 SET_REPORT、UVC 的 SET_CUR）的 wValue/wIndex 到对应类规范里查。UVC 的 wIndex 编码最绕：高字节是实体 ID，低字节是接口号，写错就是「控制不生效但也不报错」。

一个封装示例 #

项目里常见做法是包一层，把 USB_DIR_IN、USB_TYPE_VENDOR、USB_RECIP_DEVICE 这些位拼好：

c
static int xread(struct usb_device *udev, u8 req, u16 value, u16 index,
                 void *buf, u16 len)
{
        return usb_control_msg(udev, usb_rcvctrlpipe(udev, 0), req,
                               USB_DIR_IN | USB_TYPE_VENDOR | USB_RECIP_DEVICE,
                               value, index, buf, len, USB_CTRL_GET_TIMEOUT);
}

USB_CTRL_GET_TIMEOUT 是内核定义的 5000 ms。用宏别写死数字，也别忘了 usb_rcvctrlpipe 的端点号永远是 0。

十七、从设备树/ID 表实例化设备 #

主机侧 USB 设备驱动的实例化来源只有一个：设备真的插上来了，核心层枚举完，接口挂到总线上。没有「设备树里写个子节点就创建 usb_device」这条路，USB 不是平台设备。

所以 usb_driver 的实例化全在 ID 表上。设备树在 USB 场景里只干两件事：

  1. 描述控制器本身（compatible = "rockchip,rk3399-dwc3" 之类），这是 HCD 的事，看《USB 平台调试》。
  2. 描述板级供电、Host/OTG 角色切换、VBUS 使能脚，走 regulator、extcon/typec 这些子系统。

驱动代码里常见的三种绑定入口：

c
/* 1. ID 表：静态匹配，最常见 */
static const struct usb_device_id foo_table[] = {
        { USB_DEVICE(0x1234, 0x5678) },
        { USB_DEVICE_AND_INTERFACE_INFO(0x1234, 0x5678, 0xff, 0x00, 0x00) },
        { }
};
MODULE_DEVICE_TABLE(usb, foo_table);

/* 2. 动态 ID：运行时补充，调试友好 */
/* echo "1234 5678" > /sys/bus/usb/drivers/foo/new_id */

/* 3. 全捕获：只填 driver_info，probe 里自己判断 */
static const struct usb_device_id foo_all[] = {
        { .driver_info = 1 },
        { }
};

第 3 种要克制使用。{ .driver_info = 1 } 会把所有没被别人认领的接口都捞到你的 probe 里，判断逻辑写不严就会抢走 HID、存储设备的接口。

of_match_table 在这里没有位置。usb_driver 里没有 .of_match_table 成员，它不属于 platform_driver。有人把 MODULE_DEVICE_TABLE(of, ...) 塞进 USB 驱动，编译能过（宏只是生成别名段），但匹配逻辑根本不会用上，是死代码。

版本说明：usb_driver 结构体自 2.6 以来成员只增不减，3.x 到 5.x 期间新增的有 disable_hub_initiated_lpm（3.5 左右，未验证确切版本）、soft_unbind（更早）、reset_resume（2.6.30 左右）。写跨版本驱动时以目标内核头文件为准，别照 5.x 抄了往 3.10 上放。

板级怎么在 probe 里把接口变成可用设备：

c
static int foo_probe(struct usb_interface *intf, const struct usb_device_id *id)
{
        struct usb_device *udev = interface_to_usbdev(intf);
        struct usb_host_interface *alt = intf->cur_altsetting;
        struct foo_dev *dev;
        int i, ret;

        dev = kzalloc(sizeof(*dev), GFP_KERNEL);
        if (!dev)
                return -ENOMEM;

        udev = usb_get_dev(udev);
        dev->udev = udev;
        dev->intf = intf;

        /* 挑端点：只要第一个 bulk IN 和一个 bulk OUT */
        for (i = 0; i < alt->desc.bNumEndpoints; i++) {
                struct usb_endpoint_descriptor *ep = &alt->endpoint[i].desc;

                if (!dev->in_ep && usb_endpoint_is_bulk_in(ep))
                        dev->in_ep = ep->bEndpointAddress;
                if (!dev->out_ep && usb_endpoint_is_bulk_out(ep))
                        dev->out_ep = ep->bEndpointAddress;
        }
        if (!dev->in_ep || !dev->out_ep) {
                ret = -ENODEV;
                goto err_put;
        }

        usb_set_intfdata(intf, dev);
        return 0;

err_put:
        usb_put_dev(udev);
        kfree(dev);
        return ret;
}

对应的 disconnect：

c
static void foo_disconnect(struct usb_interface *intf)
{
        struct foo_dev *dev = usb_get_intfdata(intf);

        usb_set_intfdata(intf, NULL);
        if (!dev)
                return;

        usb_kill_urb(dev->urb);      /* 先杀 URB，再放资源 */
        usb_free_urb(dev->urb);
        usb_put_dev(dev->udev);
        kfree(dev);
}

顺序不能反。先 kfree(dev) 再 usb_kill_urb，回调里读的 urb->context 就是野指针。

usb_get_dev() / usb_put_dev() 管的是 usb_device 的引用计数，不是模块自己的计数。模块自己的生命周期由 kref 一类的东西管。素材 3 的 usb-skeleton 里两者都有：usb_get_dev() 给设备，kref_init()/kref_get()/kref_put() 给自己的结构体。

顺带记一下 usb_register_dev() 那条路。想让设备在 /dev 下出现一个字符设备节点，需要：

c
static struct usb_class_driver skel_class = {
        .name = "skel%d",
        .fops = &skel_fops,
        .minor_base = USB_SKEL_MINOR_BASE,
};

usb_register_dev(interface, &skel_class);

name 里的 %d 会被换成次设备号，minor_base 是起始次设备号。注销时在 disconnect 里 usb_deregister_dev(interface, &skel_class) 把次设备号还回去。

注意 usb_register_dev() 之后 interface->minor 才有意义，之前读它没有意义——素材 3 对此的判断是对的。

故障速查 #

现象 先查
dmesg 完全没有插入日志 供电、VBUS、D+/D- 上拉、控制器驱动是否加载
device descriptor read/64, error -71 信号完整性：线材、串阻、ESD 器件、供电跌落
枚举成功但没有 /dev 节点 接口驱动没 probe，lsusb -t 看 Driver=
probe 返回 -ENODEV ID 表没匹配，或端点没找到，看 probe 里的 dev_err
读写超时 usb_bulk_msg 超时太短、端点地址用错方向、设备在等控制请求
一拔就 oops disconnect 没杀 URB，回调访问已释放的 context
传输速率只有预期的一半 端点 wMaxPacketSize 读错，或中断 URB 的 interval 没转线性
等时传输大量 error_count 带宽没分够，切 altsetting 时没重新算

设备复位的坑单独提一句：usb_reset_device() 会调 pre_reset，要求驱动在返回前把所有 URB 收干净。如果驱动在 pre_reset 里还挂着 URB，核心会等，等不到就超时，复位失败，设备从此处于半死状态。用 usb_anchor 管 URB 的驱动在这条路上少掉一半麻烦。

一个真实启动日志 #

内核自带 USB 驱动，接一个 USB 鼠标，串口会打出：

text
usb 1-1: new low-speed USB device number 2 using s3c2410-ohci

这一行能读出四件事：总线 1、端口 1；低速设备；分配到的设备号是 2（1 号给根 Hub 了）；控制器驱动是 s3c2410-ohci。后面还会跟 input: ... as /devices/... 之类，那是 usbhid 已经 probe 成功、把设备注册成输入设备了。

十九、易错点速查 #

坑 表现 正解
id_table 忘写或为空 probe 从不被调用 必须有表，末尾必须有全零项，配 MODULE_DEVICE_TABLE(usb, ...)
ID 表从泛到具体排 通用项挡住了特例，quirk 不生效 具体匹配放前面，通用放后面
设备类为 Vendor-Specific 还写接口类匹配 永远不匹配 加 idVendor，或用 USB_DEVICE_AND_INTERFACE_INFO
端点方向搞反 -EPIPE 或超时 OUT 用 usb_snd*pipe，IN 用 usb_rcv*pipe，和端点描述符方向位一致
端点号猜 1、2 换设备就挂 遍历 cur_altsetting->endpoint[] 按类型与方向找
用下标访问 altsetting 某些设备取错设置 usb_altnum_to_altsetting()
bInterval 直接当毫秒 高速设备轮询快 8 倍 高速/超高速是 125 µs 为单位，且描述符里是对数编码
完成回调里睡 BUG: scheduling while atomic 回调在中断上下文，改成 workqueue 里做重活
回调不判 status 拔设备时刷假错误 放过 -ENOENT/-ECONNRESET/-ESHUTDOWN
disconnect 不杀 URB 拔插几次后 oops usb_kill_urb() 或 usb_kill_anchored_urbs()，先杀再放
usb_free_urb 后还用指针 use-after-free usb_free_urb 只减引用，最后一个引用释放才真回收；别提前置空别乱存
批量 OUT 长度是最大包长整数倍 最后一段数据不落地 置 URB_ZERO_PACKET
transfer_buffer 用 vmalloc 内存 DMA 时数据错乱 用 kmalloc 或 usb_alloc_coherent
置了 URB_NO_TRANSFER_DMA_MAP 却不自己释放 内存泄漏 配 usb_free_coherent
置了 URB_SHORT_NOT_OK 却用在写请求 标志被忽略 它只对 IN 方向有意义
probe 里先 usb_set_intfdata 后失败 悬空私有指针 失败路径统一 usb_set_intfdata(intf, NULL)
interface_to_usbdev 后不做引用计数 设备拔了还在用 配 usb_get_dev()/usb_put_dev()
在 probe 里自己 SET_CONFIGURATION 与核心策略冲突 交给核心，驱动最多 usb_reset_configuration()
直接写 udev->state 状态机错乱 用 usb_set_device_state()
等时 URB 按普通 URB 填 -EINVAL 手填 number_of_packets 和 iso_frame_desc
等时回调不重提交 传几帧就停 回调里重新 usb_submit_urb()
用 usb_register_dev 后忘了 usb_deregister_dev 次设备号泄漏，重插报错 disconnect 里还回去
驱动里写 of_match_table 编译过但没用 USB 不匹配设备树，删掉
拿 5.x 的 usb_driver 往 3.10 上编 字段不存在 按目标内核头文件写，或用 #if LINUX_VERSION_CODE
