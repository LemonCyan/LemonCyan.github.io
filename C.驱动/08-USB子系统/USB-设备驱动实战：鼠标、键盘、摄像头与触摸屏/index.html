一、四个设备驱动的共同骨架 #

四个设备看着差得远，骨架是同一套：内核匹配上接口，调你的 probe；你在 probe 里申请私有的 struct xxx，把 usb_device、input_dev 或 video_device、URB 挂进去；数据来了在 URB 完成函数里解包，往上抛给 input 或 V4L2；disconnect 里原路拆回去。

匹配由 USB 总线的 usb_device_match() 负责：先判 is_usb_device(dev) 区分设备与接口，设备侧直接返回 1，接口侧再走 usb_match_id(intf, usb_drv->id_table) 比对。id_table 是 struct usb_device_id 数组，最后一项必须是空项 {} 做终止。常用字段与匹配标志：

字段 含义 对应 match 标志
match_flags 决定哪些字段参与比较 自身
idVendor / idProduct 厂商 ID / 产品 ID USB_DEVICE_ID_MATCH_DEVICE
bcdDevice_lo / bcdDevice_hi 设备版本号范围 USB_DEVICE_ID_MATCH_DEV_LO / _HI
bInterfaceClass 等 接口描述符里的类 USB_DEVICE_ID_MATCH_INT_INFO
driver_info 驱动自用，内核只透传 不参与匹配

四个驱动都只用接口级匹配，宏 USB_INTERFACE_INFO(cl, sc, pr) 一次填 match_flags = USB_DEVICE_ID_MATCH_INT_INFO 加 bInterfaceClass/bInterfaceSubClass/bInterfaceProtocol 三个字段。

struct usb_driver 的常用回调：

回调 谁实现 干什么 版本注意
.name 全部 驱动名，lsusb -t 和 sysfs 里能看到 无变化
.probe(intf, id) 全部 匹配成功后初始化设备 3.x 起返回 int；素材鼠标例子写成 void，见勘误
.disconnect(intf) 全部 拔出或卸载时回收 3.x 起返回 void
.id_table 全部 匹配表 无变化
.suspend / .resume / .reset_resume UVC 电源管理 无变化
.supports_autosuspend UVC 允许运行时自动挂起 无变化

probe 的返回值语义必须清楚：返回 0 表示接管这个接口，返回负值表示放弃，内核不会再拿别的驱动来试。素材那个 void usb_mouse_probe() 把返回值丢了，导致 -ENOENT 的失败反而打印成 probe of 1-1:1.0 failed with error 53，这是第十七章要重点讲的坑。

四个驱动在 probe 里的动作，顺序几乎一致：

  1. interface_to_usbdev(intf) 拿 usb_device，intf->cur_altsetting 拿当前激活的 altsetting；
  2. 校验端点数量和方向（usb_endpoint_is_int_in() / usb_endpoint_is_iso()）；
  3. kzalloc 私有结构，input_allocate_device() 或 video_device_alloc() 拿上层对象；
  4. 申请 URB 与 DMA 缓冲区（usb_alloc_urb() / usb_alloc_coherent()）；
  5. 填 URB（usb_fill_int_urb() / usb_fill_control_urb() / 手工填等时 URB）；
  6. 注册上层设备（input_register_device() / video_register_device()）；
  7. usb_set_intfdata(intf, priv) 把私有数据挂到接口上，disconnect 靠它找回。

disconnect 是镜像：usb_get_intfdata()、usb_set_intfdata(intf, NULL)、usb_kill_urb()、注销上层设备、释放 URB 与 DMA 缓冲、kfree。顺序不能反——先 usb_kill_urb() 再释放缓冲区，否则 URB 还在飞时缓冲区已经还回去了。

struct usb_device 里 probe 常用的字符串字段：manufacturer、product、serial，由 USB core 从字符串描述符读出来，会为 NULL。usb_make_path(dev, buf, len) 生成 sysfs 物理路径，格式 usb-总线号-路径名，填给 input_dev->phys 正合适。

二、HID 类：鼠标与键盘的共同点 #

鼠标和键盘在 USB 层是同一类东西：bInterfaceClass = 0x03，HID（Human Interface Device）。触摸板、摇杆、绘图板也在这一类。区别只在子类和协议：

c
#define USB_INTERFACE_SUBCLASS_BOOT     1
#define USB_INTERFACE_PROTOCOL_KEYBOARD 1
#define USB_INTERFACE_PROTOCOL_MOUSE    2

这三行在 include/uapi/linux/hid.h。USB_INTERFACE_CLASS_HID 的值是 0x03。

「Boot」是什么概念？HID 规范除了完整的报告描述符（可以描述任意布局），还给键盘和鼠标额外规定了固定布局，叫 Boot Protocol。BIOS、bootloader 没能力解析报告描述符，就走 Boot Protocol 按固定格式读。内核里 drivers/hid/usbhid/usbmouse.c 和 usbkbd.c 就是照 Boot Protocol 写的，本篇示例驱动也照这个来。

三个 id_table 长一个样子，只有协议字段不同：

c
static const struct usb_device_id usb_mouse_id_table[] = {
        { USB_INTERFACE_INFO(USB_INTERFACE_CLASS_HID,
                USB_INTERFACE_SUBCLASS_BOOT,
                USB_INTERFACE_PROTOCOL_MOUSE) },
        { }     /* Terminating entry */
};

MODULE_DEVICE_TABLE (usb, usb_mouse_id_table);

c
static const struct usb_device_id usb_kbd_id_table[] = {
        { USB_INTERFACE_INFO(USB_INTERFACE_CLASS_HID,
                USB_INTERFACE_SUBCLASS_BOOT,
                USB_INTERFACE_PROTOCOL_KEYBOARD) },
        { }                                             /* Terminating entry */
};

MODULE_DEVICE_TABLE(usb, ...) 把这张表导进模块的 .modinfo 段，udev/modprobe 据此做按需加载——热插拔时才知道该 insmod 哪个 .ko。

两个 Boot Protocol 驱动的对照（bInterval 和端点最大包长都来自设备的端点描述符，不是固定值）：

项 鼠标 键盘
接口类/子类 0x03 / 1（Boot） 0x03 / 1（Boot）
接口协议 2（Mouse） 1（Keyboard）
端点 中断 IN，1 个 中断 IN，1 个（LED 走端点 0）
报告长度 4 字节（usbmouse.c 按 4 字节解） 8 字节
URB 数量 1 个（irq） 2 个（irq + led）
上报事件类型 EV_KEY + EV_REL EV_KEY + EV_LED + EV_REP

鼠标缓冲区申请的是 8 字节（usb_alloc_coherent(dev, 8, ...)），解析只用前 4 字节。这是 usbmouse.c 的历史写法，真正决定每次收多少的是 usb_fill_int_urb() 的 buffer_length，传的是端点最大包长 maxp。

三、USB 鼠标驱动：中断传输与报告解析 #

鼠标走中断传输。这里的「中断」不是设备主动打中断过来，而是主机控制器按端点描述符里的 bInterval 周期性地去问设备「有没有数据」。延迟可控，代价是占固定带宽。

一个 URB 的生命周期是固定的：创建 → 绑定到某个设备的某个端点 → 提交给 USB core → USB core 交给 HCD → HCD 发给设备 → 完成后回调你的完成函数。驱动只操心三件事：分配、填充、提交。

iso_packets 是等时 URB 里等时包的个数，中断、控制、批量传 0。URB 带 kref，最后一个使用者放掉才真正释放。

四种传输类型的用途：

类型 特性 典型设备 本篇用在哪
控制传输 固定结构（setup 包 + 数据 + 状态），可靠、有带宽保证、量小 枚举、配置、类请求 键盘发 LED（端点 0）
中断传输 固定周期轮询、可靠、实时性高、单次量小 鼠标、键盘 鼠标、键盘收数据
批量传输 可靠但不定时、量大 U 盘、打印机 本篇不用
等时传输 定速但不可靠，丢包不重传 摄像头 UVC 视频流

填充中断 URB 用 usb_fill_int_urb()，定义在 include/linux/usb.h：

c
static inline void usb_fill_int_urb(struct urb *urb,
                                    struct usb_device *dev,
                                    unsigned int pipe,
                                    void *transfer_buffer,
                                    int buffer_length,
                                    usb_complete_t complete_fn,
                                    void *context,
                                    int interval)
{
        urb->dev = dev;
        urb->pipe = pipe;
        urb->transfer_buffer = transfer_buffer;
        urb->transfer_buffer_length = buffer_length;
        urb->complete = complete_fn;
        urb->context = context;

        if (dev->speed == USB_SPEED_HIGH || dev->speed >= USB_SPEED_SUPER) {
                interval = clamp(interval, 1, 16);
                urb->interval = 1 << (interval - 1);
        } else {
                urb->interval = interval;
        }

        urb->start_frame = -1;
}

八个参数：

参数 含义 注意
urb 要初始化的 URB 必须是 usb_alloc_urb() 出来的活动 URB
dev 目标 usb_device —
pipe 端点管道 用 usb_rcvintpipe() / usb_sndintpipe() 构造
transfer_buffer 收发缓冲区 不能是静态数组，必须 kmalloc() 或 usb_alloc_coherent()
buffer_length 缓冲区长度 鼠标驱动传端点最大包长 maxp
complete_fn 完成回调 跑在中断上下文，不能睡眠
context 回调上下文 传私有结构指针
interval 轮询间隔 高速/超速与全速/低速语义不同，见下

interval 是速率相关的坑：高速和超速（USB_SPEED_HIGH、USB_SPEED_SUPER 及以上）会被 clamp(interval, 1, 16) 限制再换算成 1 << (interval - 1) 个微帧；全速和低速原样写入，单位是帧（1 ms）。设备描述符写 bInterval = 10，高速下是 2^9 = 512 微帧，全速下是 10 ms，差得远。usb_submit_urb() 里还会再校验一遍并向下取整到 2 的幂，超范围直接 -EINVAL。

pipe 用 usb_rcvintpipe(dev, endpoint->bEndpointAddress) 构造，本质是个位图：bit 7 方向、bit 8～14 设备地址、bit 15～18 端点号、bit 30～31 管道类型（0 等时、1 中断、2 控制、3 批量）。

端点最大包长用 usb_endpoint_maxp(epd) 从 wMaxPacketSize 取，usb_maxpacket() 再按 pipe 方向自动选 ep_in[] 或 ep_out[]。

DMA 一致性缓冲区用 usb_alloc_coherent(dev, size, mem_flags, &dma) 申请、usb_free_coherent(dev, size, addr, dma) 释放，前提是平台支持 DMA。

usb_submit_urb() 的 mem_flags 规则，第 5 版的函数注释写得很明白：probe 和 disconnect 可以用 GFP_KERNEL，完成回调里只能用 GFP_ATOMIC。理由只有一个——完成回调跑在中断上下文，任何会睡眠的分配都会炸。

报告解析。Boot Protocol 鼠标报告 4 字节：

字节 内容 位定义
data[0] 按键状态 bit0 左键、bit1 右键、bit2 中键、bit3 BTN_SIDE、bit4 BTN_EXTRA
data[1] X 位移 有符号 8 位，负左移正右移
data[2] Y 位移 有符号 8 位，负上移正下移
data[3] 滚轮 有符号 8 位，对应 REL_WHEEL

完成函数 usb_mouse_irq() 把位图翻译成 input 事件：先判 urb->status，-ECONNRESET/-ENOENT/-ESHUTDOWN 直接 return（URB 已被 unlink 或设备已关机，不能再提交），其它错误含 -EPIPE 打完日志 goto resubmit；成功则 input_report_key() 报五个按键位、input_report_rel() 报 X/Y/滚轮，最后 input_sync() 收尾。

-ECONNRESET、-ENOENT、-ESHUTDOWN 三个状态直接 return，因为 URB 已经被 unlink 或设备已关机，不能再提交；其它错误（含 -EPIPE 端点 stall）打完日志重新提交。input_sync() 不能省，它是 SYN_REPORT 的封装，告诉上层「这一批事件到此为止」。

data[1]/data[2] 是有符号数，但 char *data 的符号位取决于编译器把 char 当有符号还是无符号。ARM GCC 默认无符号，于是 0xFF（-1 像素）会读成 255。正确做法是把缓冲声明成 s8 *，或者显式 (s8)data[1]。素材代码没处理这一处，实测方向正常，原因未查证，标记未验证。

包尾部必须重新提交（usb_submit_urb(urb, GFP_ATOMIC)），否则鼠标动一下就断了。

四、鼠标驱动的 probe 与断开处理 #

probe 按第一章那七步走。第一步验接口形态：intf->cur_altsetting 拿 altsetting，bNumEndpoints != 1 直接 -ENODEV，再 usb_endpoint_is_int_in(endpoint) 验方向，然后 usb_rcvintpipe() 建管道、usb_maxpacket() 取 maxp。

只验 bNumEndpoints 不验方向是常见错误，结果拿到一个 OUT 端点当 IN 用，usb_submit_urb() 返回 -EPIPE，日志只有一行。

私有结构和缓冲区：kzalloc(sizeof(struct usb_mouse), GFP_KERNEL) 拿私有结构，input_allocate_device() 拿 input_dev，usb_alloc_coherent(dev, 8, GFP_ATOMIC, &mouse->data_dma) 拿 DMA 缓冲，usb_alloc_urb(0, GFP_KERNEL) 拿 URB，任一步失败就 goto 对应标签。

usb_alloc_coherent() 用 GFP_ATOMIC 是素材原样写法，理由是这块缓冲会被周期性写入，驱动不想在分配上睡眠。probe 上下文其实可以用 GFP_KERNEL。

设备名三段拼接：先 strlcpy 抄 manufacturer，再 strlcat 补 product，两个都没有时 snprintf 兜底成 USB HIDBP Mouse %04x:%04x；usb_make_path() 生成 phys 后补 "/input0"。

版本注意：strlcpy/strlcat 从 5.8 起被 strscpy/strscpy_pad 取代，6.x 树里已经删掉。素材内核 5.2.8 用着没问题，往新内核移植要一起换。

往 input_dev 上挂属性：name/phys 指到私有结构的同名缓冲，usb_to_input_id(dev, &input_dev->id) 填 input_id，input_dev->dev.parent = &intf->dev 接上 sysfs 拓扑，再对 BTN_LEFT/BTN_RIGHT/BTN_MIDDLE/BTN_SIDE/BTN_EXTRA 和 REL_X/REL_Y/REL_WHEEL 逐个 input_set_capability()，最后 input_set_drvdata() 把私有结构挂回去、设 open/close 回调。

input_set_capability() 干两件事：把事件类型位记进 evbit，把事件码位记进对应的 keybit/relbit。素材里那两行 set_bit(EV_KEY, ...)、set_bit(EV_REL, ...) 是冗余的（input_set_capability() 自己会设），没坏处。

open/close 是 input 的电源开关语义：用户态一 open("/dev/input/eventX")，URB 才开始流动；最后一个 fd 关掉，URB 就停。设备空闲时不占总线带宽。

c
static int usb_mouse_open(struct input_dev *dev)
{
   struct usb_mouse *mouse = input_get_drvdata(dev);
   mouse->urb->dev = mouse->usbdev;

   if (usb_submit_urb(mouse->urb, GFP_KERNEL))
        return -EIO;

   return 0;
}

static void usb_mouse_close(struct input_dev *dev)
{
    struct usb_mouse *mouse = input_get_drvdata(dev);

    usb_kill_urb(mouse->urb);
}

open 里那行 mouse->urb->dev = mouse->usbdev; 是必须的：disconnect 之后重新 probe 的场景下，urb->dev 已被 core 清掉。close 里用 usb_kill_urb() 而不是 usb_unlink_urb()，kill 会等完成函数跑完才返回，保证后面的释放安全。

probe 收尾用 input_register_device()，成功则 usb_set_intfdata(intf, mouse) 后返回 0，失败走 goto fail3；fail3 释放 URB，fail2 释放 DMA 缓冲，fail1 释放 input_dev 并 kfree(mouse)，靠标签级联保证每一级只回收已申请到的东西。

断开处理逐一反向拆：usb_get_intfdata(intf) 取私有结构，立刻 usb_set_intfdata(intf, NULL) 断掉新访问入口，再 usb_kill_urb() 停数据流，input_unregister_device() 注销，usb_free_urb() 与 usb_free_coherent() 释放，最后 input_free_device() 加 kfree。

驱动注册与注销：

五、USB 键盘驱动：与鼠标的差异 #

键盘和鼠标共用 HID Boot 骨架，多出来的东西集中在三处：报告比鼠标长一倍且是「修饰键位图 + 最多 6 个普通键」的形式；需要额外的控制 URB 去点亮 LED；需要用上一帧数据比对出「哪些键松开了」。

Boot Protocol 键盘报告 8 字节：

字节 内容 位定义 / 取值
new[0] 修饰键位图 bit0 左 Ctrl、bit1 左 Shift、bit2 左 Alt、bit3 左 GUI、bit4 右 Ctrl、bit5 右 Shift、bit6 右 Alt、bit7 右 GUI
new[1] 保留 厂商自定义，Boot 协议里不用
new[2]~new[7] 当前按下的普通键 每字节一个 HID usage ID，最多 6 键同时按下

修饰键在报告里是独立位图，普通键是「当前按下的这一批」而不是「这次新按下的是哪个」。所以驱动必须自己保存上一帧 old[8]，两帧做差集才知道谁按下、谁松开。

new[0] 每一位对应哪个 KEY_*，靠码表最后 32 项来找，索引是「位号 + 224」，代码里就是 input_report_key(dev, usb_kbd_keycode[i + 224], (new[0] >> i) & 1)。

内存申请拆成一对函数 usb_kbd_alloc_mem() / usb_kbd_free_mem()，前者逐项申请 URB、new 缓冲、cr、leds 缓冲，后者按同样顺序释放。

usb_kbd_alloc_mem() 中途失败直接 return -1，前面申请到的 URB 和缓冲区就漏了。素材代码就这么写，我不改逻辑，第十七章列为待修泄漏点。正确做法是每个失败分支 goto 到对应回收标签。

probe 主体和鼠标一样，差异在事件类型和 input_set_capability()：先 set_bit() 打开 EV_KEY/EV_LED/EV_REP，再 for (i = 0; i < 255; i++) input_set_capability(input_dev, EV_KEY, usb_kbd_keycode[i])，然后 clear_bit(KEY_RESERVED, input_dev->keybit)，最后给 LED_NUML/LED_CAPSL/LED_SCROLLL/LED_COMPOSE/LED_KANA 五个码设 EV_LED。

EV_REP 是自动重复（长按出字符），交给 input 子系统做，驱动不用管。clear_bit(KEY_RESERVED, input_dev->keybit) 是必要的：码表里大量项是 0，不清掉的话 input_set_capability() 会把 KEY_RESERVED 也标记成可上报，用户态会看到一个不存在的键。for (i = 0; i < 255; i++) 边界少了 [255]，这一项在表里是 140（KEY_MENU），属于素材的 off-by-one，记在勘误里。

EV_LED 的 5 个码要和发 LED 时的位运算顺序严格对上，对不上就会「按大写锁定，键盘灯乱闪」。

中断 URB 填充与鼠标同构：usb_fill_int_urb() 传 kbd->irq、kbd->usbdev、pipe、kbd->new、maxp、usb_kbd_irq、kbd、endpoint->bInterval，再挂 transfer_dma 与 URB_NO_TRANSFER_DMA_MAP。

解析函数是键盘最关键的一段，两个循环各管一摊：

c
for( i=0; i<8; i++)   /* 处理特定功能键 */
{
    input_report_key(dev, usb_kbd_keycode[i+224], (new[0] >> i) & 1);
}
for (i = 2; i < 8; i++)
{
     if (old[i] > 3 && memscan(new + 2, old[i], 6) == new + 8)
     {
         if (usb_kbd_keycode[old[i]])
             input_report_key(dev, usb_kbd_keycode[old[i]], 0);
         else
             hid_info(usbdev, "Unknown key (scancode %#x) released.\n", old[i]);
     }

     if (new[i] > 3 && memscan(old + 2, new[i], 6) == old + 8)
     {
         if (usb_kbd_keycode[new[i]])
             input_report_key(dev, usb_kbd_keycode[new[i]], 1);
         else
             hid_info(usbdev, "Unknown key (scancode %#x) pressed.\n", new[i]);
     }
}

input_sync(dev);

memcpy(old, new, 8);

逐行拆开：

  • 修饰键走位图，(new[0] >> i) & 1 直接得到 0/1，顺带处理了「松开」——上一帧按下、这一帧没按，值自然变 0。
  • 普通键走差集：old[i] 在 new[2..7] 里找不到（memscan() 返回 new + 8 表示没找到），说明这个键松开了；new[i] 在 old[2..7] 里找不到，说明是新按下的。
  • > 3 过滤跳过 HID 的 0x00（无键）、0x01～0x03（错误码 / Power / 保留），这些不是合法 usage。
  • 查表结果为 0 说明码表不认识这个 usage，打日志，不往上报。
  • 两个循环都在 input_sync() 之前，因为 SYN_REPORT 把这一帧所有事件打包送出去，拆开会上报半截帧。
  • memcpy(old, new, 8) 必须在 input_sync() 之后、resubmit 之前，放错了下一帧就永远比不出差集。

probe 结尾注册 input 设备、usb_set_intfdata()，与鼠标一致。disconnect 比鼠标多一个 usb_kill_urb(kbd->led)：irq 是数据流，led 是控制传输，漏掉任何一个，usb_free_urb() 之后 HCD 仍会回调你的完成函数，直接 UAF。两个都杀完再 input_unregister_device()、usb_kbd_free_mem()、kfree。

六、键盘的特殊按键与 LED 控制 #

LED 是键盘唯一的下行通道，走控制传输，用端点 0。整套逻辑三块：input 子系统通知驱动「LED 状态变了」、驱动拼一个 1 字节报告发出去、发完之后在完成函数里检查有没有新变化要重发。

控制请求结构体按 USB HID 1.11 规范 7.2.1 的 SET_REPORT 填，五个字段一一对应：

字段 值 含义
bRequestType USB_TYPE_CLASS | USB_RECIP_INTERFACE = 0x21 类请求、面向接口、主机到设备
bRequest 0x09 SET_REPORT
wValue 高字节 0x02 Report Type = Output
wValue 低字节 0x00 Report ID = 0（Boot 协议无 ID）
wIndex bInterfaceNumber 目标接口号
wLength 1 LED 报告 1 字节

cpu_to_le16(0x200) 看着绕：USB 的多字节字段都是小端，主机侧要保证发出去的是小端值，统一过一遍 cpu_to_le16()。

控制 URB 用 usb_fill_control_urb() 填，四个填充宏里只有它需要 setup_packet：

c
usb_fill_control_urb(kbd->led,                     /* urb */
                     dev,                          /* usb_device */
                     usb_sndctrlpipe(dev, 0),      /* 控制端点 0 */
                     (void *) kbd->cr,             /* setup_packet */
                     kbd->leds,                    /* 数据缓冲区 */
                     1,                            /* 数据长度 */
                     usb_kbd_led,                  /* 完成函数 */
                     kbd);                         /* 上下文 */
kbd->led->transfer_dma = kbd->leds_dma;
kbd->led->transfer_flags |= URB_NO_TRANSFER_DMA_MAP;

usb_fill_control_urb() 比 usb_fill_bulk_urb() 多一个 setup_packet，其余含义相同；控制传输没有 interval。

input_dev->event 是驱动收到的「输出事件」入口。用户态改 led 位图，内核就调到 usb_kbd_event()：它先判 type != EV_LED 直接返回 -1，然后在 leds_lock 保护下把 dev->led 的五个 LED 位压成 1 字节 newleds（!!test_bit() 把返回值压成 0/1，否则左移后位数会乱）；led_urb_submitted 为真说明上一个 LED URB 还在飞，直接返回；newleds 与 leds 相同也返回；否则写回 leds、设 kbd->led->dev、usb_submit_urb(kbd->led, GFP_ATOMIC)，成功才把 led_urb_submitted 置真。

LED 报告的位定义（Boot Protocol 键盘输出报告，1 字节）：

bit 定义 对应宏
0 Num Lock LED_NUML
1 Caps Lock LED_CAPSL
2 Scroll Lock LED_SCROLLL
3 Compose LED_COMPOSE
4～7 保留（部分实现把 Kana 放 bit4） —

上面那段代码把 LED_KANA 也左移 3 位，和 LED_COMPOSE 撞在同一个 bit。这是 usbkbd.c 的历史写法，日文键盘才有意义，中文键盘上看不出问题。改成 << 4 更符合规范，但你得确认设备真的按这个位置解，不清楚就别动，标记未验证。

led_urb_submitted 是「同一时刻只允许一个 LED URB 在飞」的闸门。USB 端点每次只能处理一个控制请求，重复提交会被 core 拒掉。

完成函数 usb_kbd_led() 负责「飞完再看一眼有没有新状态」，形成自驱动循环：先看 urb->status，有错就 hid_warn()；再进 leds_lock，若 leds == newleds 就清 led_urb_submitted 返回；否则写回 leds、重新 usb_submit_urb(kbd->led, GFP_ATOMIC)，提交失败时 hid_err() 并清 led_urb_submitted。

并发模型：usb_kbd_event() 和 usb_kbd_led() 会在不同 CPU 上同时跑，leds 缓冲和 newleds 被 leds_lock 保护。用 spin_lock_irqsave() 而不是 spin_lock()，因为 usb_kbd_led() 跑在中断上下文，会打断持有同一把锁的进程上下文，光禁抢占不够，得关中断。

usb_kbd_led() 里那个 if (*(kbd->leds) == kbd->newleds) 分支在正常情况下永远成立——event 里已经同步过了。它存在的意义是处理「URB 提交成功但还没回来时，用户态又改了一次 LED 状态」这个窗口：那时 event 直接返回，newleds 已更新，完成函数一比对发现有差异就立刻续发。

event 的错误处理也值得抄：type != EV_LED 返回 -1 表示事件不接；usb_submit_urb() 失败却只打日志返回 0，因为它返回负值会让 input 子系统把错误抛回用户态，LED 点不亮不值得让系统调用失败。

七、input 子系统的接入 #

四个设备里三个（鼠标、键盘、触摸屏）最终都挂到 input 子系统上。这一章把「驱动侧要填什么」讲透，UVC 走 V4L2，套路不同。

注册与释放是四步对两步：

步骤 函数 失败处理
分配 input_allocate_device() 返回 NULL，跳到错误标签
填属性 直接写 input_dev 字段、input_set_capability() 不会失败
注册 input_register_device(dev) 返回负值，先 input_free_device()
释放 input_unregister_device() + input_free_device() —

input_dev 里必须填的字段：

字段 填什么 漏填的后果
name 设备名，如 "USB HIDBP Mouse 0000:0538" sysfs 显示 (null)，udev 规则匹配不上
phys usb_make_path() + "/input0" 失去物理路径，多设备时无法区分
id usb_to_input_id() 填 bustype/vendor/product/version 用户态按 ID 匹配设备失败
dev.parent &intf->dev sysfs 拓扑断链，电源管理跟着出问题
evbit / keybit / relbit / absbit 能力位图 用户态看不见对应事件，上报被静默丢弃
open / close URB 启停 URB 不流动，或热插拔后 URB 悬空
event 只键盘需要，处理 EV_LED 键盘 LED 无响应

usb_to_input_id(dev, &input_dev->id) 把 usb_device->descriptor 里的 idVendor、idProduct、bcdDevice 抄到 input_id，bustype 设成 BUS_USB。

上报 API 分三类：

语义 函数 落到哪
按键 / 开关 input_report_key(dev, code, value) EV_KEY，value 0 松开 / 1 按下 / 2 自动重复
相对位移 input_report_rel(dev, code, value) EV_REL，鼠标的 X/Y/滚轮
绝对位移 input_report_abs(dev, code, value) EV_ABS，触摸屏坐标
LED input_report_led(dev, code, value) EV_LED，反向由 event 接

一次「事件帧」必须以 input_sync() 收尾，它等价于 input_event(dev, EV_SYN, SYN_REPORT, 0)。这一条把本次所有零散事件打包，用户态 read() 一次拿到的就是一帧。input_sync() 之前每次 input_report_* 只是往内核事件缓冲里塞一条记录，input_sync() 才是提交。

绝对坐标设备（触摸屏）还要设 absmin/absmax：

c
input_set_abs_params(input_dev, ABS_MT_POSITION_X, 0, 4095, 0, 0);
input_set_abs_params(input_dev, ABS_MT_POSITION_Y, 0, 4095, 0, 0);

五个参数：dev、事件码、最小值、最大值、fuzz（噪声容差，小于该差值的抖动被丢弃）、flat（平底容差，中心附近视为同一位置）。后两个参数鼠标、触摸屏一般填 0。absmax 必须和屏幕实际分辨率对应，填错了光标位置就差一个系数。

input_set_capability() 与直接 set_bit() 的区别：input_set_capability(dev, EV_KEY, BTN_LEFT) 等价于 set_bit(EV_KEY, dev->evbit) 加 set_bit(BTN_LEFT, dev->keybit)，但它内部还处理了 EV_SW、EV_LED、EV_SND、EV_REP 对应的 swbit/ledbit/sndbit/rep，比手写 set_bit() 安全。所以用 input_set_capability() 设能力，别手动往错误的位图上 set_bit。

open/close 的触发时机：用户态第一次 open("/dev/input/eventN") 调 open，最后一个 fd 关掉调 close。含义是：

  • 驱动在 probe 里不要直接 usb_submit_urb() 开始收数据，等 open 回调；
  • 但 probe 里必须把 URB 填好，open 只负责提交；
  • 设备没有 input 用户态消费者时，URB 一直不流动，这是 feature 不是 bug，省带宽。

反例也常见：有的驱动在 probe 里就提交，结果空闲时总线带宽被持续占用，还和 USB autosuspend 打架。素材的鼠标驱动做法是对的。

八、UVC 类：USB 摄像头 #

摄像头和前面三个完全不是一类：它属 UVC（USB Video Class），bInterfaceClass = 0x0E，对上层暴露的是 V4L2 字符设备 /dev/videoN，不是 input。驱动路径也从 drivers/hid/usbhid/ 换到了 drivers/media/usb/uvc/。

S3C2440 这种 ARM920T 平台有两类摄像头接法：CMOS 并口（CAMER 接口，走 SoC 的 camera controller）和 USB 接口。这一章只讲 USB。

UVC 是「免驱」的。免驱不是不用写驱动，是驱动写一份覆盖所有符合规范的设备：只要设备符合 UVC 描述符规范，同一份 uvcvideo.ko 就能带起来，不用为每颗 sensor 单独适配。摄像头、数码相机、采集棒、静态影像相机都在这个规范里。

V4L2 是 UVC 之上那一层。/dev/videoN 上一套 open/read/mmap/ioctl，用户态通过系统调用进内核，落到驱动的 v4l2_file_operations。FFmpeg、OpenCV、MPlayer、Skype 这类软件都跑在 V4L2 上。

素材用一颗 Sonix 摄像头验证，idVendor=0c45、idProduct=6340。插在 PC 上，dmesg 里的枚举日志是这几行：usb 1-1: new high-speed USB device number 2 using ehci-pci、uvcvideo: Found UVC 1.00 device USB 2.0 Camera (0c45:6340)、usbcore: registered new interface driver uvcvideo，中间夹着 3:1: cannot get freq at ep 0x84。从这段日志能读出四件事：

  • ehci-pci 认到设备，地址 2，高速（USB 2.0），主机侧带宽足够；
  • 同一颗设备被两个驱动分别接管：snd-usb-audio 拿下麦克风那个 Audio 接口，uvcvideo 拿下 Video 接口。一个 USB 复合设备的不同接口由不同驱动负责，这是接口驱动的常态；
  • uvcvideo 打印 Found UVC 1.00 device ...，从描述符里读出的 bcdUVC 版本是 1.00；
  • 它还注册了一个 input 设备（input/input6），因为配置里开了 USB_VIDEO_CLASS_INPUT_EVDEV，用来上报摄像头上的物理按键。素材那篇把 input6 写成了 /dev/input/event6，两者不是一个东西，见勘误。

cannot get freq at ep 0x84 是 UAC（音频类）读采样率失败的提示，和摄像头无关，不影响出图。

确认设备支不支持 UVC，直接看接口类：lsusb -d 0c45:6340 -v | grep "14 Video"，有 bInterfaceClass 14 Video 输出就是 UVC 设备（0x0E 即 USB_CLASS_VIDEO），没有就是 non-UVC，走 GSPCA 或厂商私有驱动。

九、UVC 描述符与视频流接口 #

UVC 设备至少有两个功能接口：VideoControl（VC）传控制请求，VideoStreaming（VS）传视频数据。VC 接口里再挂一串描述符，描述这颗摄像头有哪些实体（Terminal、Unit）以及它们的连接关系；VS 接口再按 altsetting 分档，每档对应一个分辨率/帧率组合。驱动要先把这棵描述符树全读下来，才谈得上打开视频流。

VC 接口描述符里最关键的是 VC Interface Descriptor，它的字段决定了这颗摄像头支持到 UVC 1.0 还是 1.1：

字段 含义
bcdUVC UVC 规范版本号，0x0100 是 1.00，0x0110 是 1.10
wTotalLength 后面所有 VC 类描述符的总长度
dwClockFrequency 设备内部时钟频率（Hz），用来把 dwTimeStamp 换算成时间
bInCollection 从属于这个 VC 的 VS 接口个数
baInterfaceNr[] 各个 VS 接口的接口号

uvcvideo: Found UVC 1.00 device 里的「1.00」就是从 bcdUVC 读出来的。

VC 里的实体描述符：

实体 描述符类型值 干什么
Input Terminal 0x02 信号源，如 Camera Terminal（感光）
Output Terminal 0x03 信号出口
Selector Unit 0x04 在多路输入里选一路
Processing Unit 0x05 亮度、对比度、饱和度、白平衡这些图像处理
Extension Unit 0x06 厂商自定义控制项

素材在开发板上插摄像头，日志里打出三行 Entity type for entity Extension 4 / Processing 3 / Camera 1 was not initialized。

Extension 4、Processing 3、Camera 1 是实体 ID，不是数组下标，也不是「第几个」。这三行提示 uvc_entity.c 里支持 Media Controller 的代码没被编进去——那次开发板配置里 CONFIG_MEDIA_CONTROLLER 不是 y，实体建了但没赋类型。它不影响出图，因为 uvc_ctrl.c 的控制项路径不走 Media Controller；要用 media-ctl 看拓扑才需要打开。

VS 接口的 altsetting 是 UVC 的性能开关。同一个 VS 接口下，altsetting 0 是零带宽待机态，只带描述符不带数据端点；altsetting 1 及以上才是工作态，每档声明不同的最大包长和带宽。切换分辨率或帧率，在 USB 层就是 SET_INTERFACE 换 altsetting。

bmInfo bit0 表示是否支持动态格式变更

MJPEG 4D 4A 50 47 V4L2_PIX_FMT_MJPEG
H.264 48 32 36 34 V4L2_PIX_FMT_H264

GUID 在描述符里是「GUID 小端」，四个字符按 ASCII 顺序倒着排；上表已按描述符里的字节序写，别按字符串 YUY2 直接比对。

帧描述符（Frame Descriptor）给的是每一档参数：

字段 含义
bFrameIndex 帧序号，1 起
bmCapabilities bit0 固定帧率 / bit1 离散帧率
wWidth / wHeight 分辨率
dwMinBitRate / dwMaxBitRate 最小/最大比特率
dwMaxVideoFrameBufferSize 单帧最大字节数，用户态申请缓冲按它算
dwDefaultFrameInterval 默认帧间隔（100ns 单位）
bFrameIntervalType 0 = 连续，N = 支持 N 个离散值
dwFrameInterval[] 离散帧间隔列表（100ns 单位）

dwFrameInterval 单位是 100 ns，30 fps 是 333333，15 fps 是 666666。这个值不落在「1 秒 = 10000000」的整数倍上，实测帧率会轻微偏离标称值，用户态软件一般能容忍。

驱动侧把这棵树解析出来，落在 struct uvc_device 里：udev/intf/intfnum/name 记设备身份，vdev（v4l2_device）/mdev/info/quirks 是 V4L2 与 Media Controller 句柄，entities/chains/streams/uvc_version/clock_frequency 存描述符解析结果，int_ep/int_urb/status/input 管状态上报，ref/users/nmappings/lock 做引用计数与并发保护。

组 字段 职责
设备身份 udev、intf、intfnum、name 一个 UVC 设备一个 uvc_device，不管它有几路视频流
V4L2 上层 vdev、mdev、info、quirks V4L2 与 Media Controller 句柄
描述符解析结果 entities、chains、streams、uvc_version、clock_frequency VC 实体链表、视频链、VS 流
状态上报与引用计数 int_ep、int_urb、status、input、ref、users、nmappings、lock 设备事件上报与并发保护

chains 和 streams 的区别值得说清：streams 是 VS 接口层的「一条视频流」，一个设备会有两条（前置、后置）；chains 是从 Terminal 到 Output Terminal 的一条完整控制链。控制项（亮度等）挂在 chain 上，因为它是跨实体的一条路径；视频数据挂在 stream 上。

nmappings 和 users 分开计数，是因为一个进程可以 mmap 多次但要 open 一次，V4L2 的 buffer 可以在 fork 之后被父子进程共享。

clock_frequency 用来解设备上报的 dwTimeStamp，单位是设备时钟周期。这颗 Sonix 的时钟频率和实际对不上时，uvcvideo 会打印警告并回落到 SOF 计数推算，具体行为按版本不同，标记未验证。

quirks 是个很有用的字段。uvc_ids[] 里给每颗有毛病的设备挂 driver_info，指向一个 uvc_device_info，里面是 quirk 位掩码，驱动在关键路径上查这几位绕开固件缺陷：

quirk 解决什么
UVC_QUIRK_PROBE_MINMAX 设备不支持 GET_MIN/GET_MAX，别去问
UVC_QUIRK_PROBE_DEF 设备不支持 GET_DEF
UVC_QUIRK_PROBE_EXTRAFIELDS 控制项报文里字段数比规范多
UVC_QUIRK_RESTRICT_FRAME_RATE 帧率必须限在某个范围内
UVC_QUIRK_BUILTIN_ISIGHT Apple iSight 专用路径
UVC_QUIRK_IGNORE_SELECTOR_UNIT 忽略描述符里的 Selector Unit
UVC_QUIRK_FORCE_Y8 强制按 8 位灰度出图
UVC_QUIRK_STATUS_INTERVAL 状态中断端点的间隔要改

这类位定义在 uvcvideo.h，值在各内核版本间有增减，具体数值以你手上的树为准。

十、UVC 驱动的 probe 与初始化 #

uvc_driver.c 的模块入口只有两步：uvc_debugfs_init() 初始化 debugfs，usb_register(&uvc_driver.driver) 注册 usb_driver；uvc_cleanup() 反向 usb_deregister() 加 uvc_debugfs_cleanup()。注册失败时先 uvc_debugfs_cleanup() 再返回错误码，别把 debugfs 节点留在 sysfs 里。

注意这里用了一个外层包装 struct uvc_driver { struct usb_driver driver; };，uvc_driver 是它的实例，probe/disconnect/suspend/resume/reset_resume/id_table 都填在内层 .driver 上，还多一个 .supports_autosuspend = 1。包一层是为了将来加字段不破坏 usb_driver 的布局。

这张表体现了三种写法：

写法 用在哪 说明
具体 VID/PID + 接口类 绝大多数条目 命中后带 driver_info 挂 quirk
具体 VID/PID + VENDOR_SPEC 接口类 Logitech、The Imaging Source、Oculus Rift Sensor 设备不符合规范但实际是 UVC，靠 VID/PID 兜进来
纯接口类匹配 表尾那两条 兜底，任何 bInterfaceClass = 0x0E、子类 1 的接口都能接上

表尾那两条是 UVC 能「免驱」的根本原因：UVC_PC_PROTOCOL_UNDEFINED（0）和 UVC_PC_PROTOCOL_15（1）覆盖 UVC 1.0 和 1.1 的 PC 协议变体，新买的摄像头不写任何 VID/PID 也能用。厂商报了怪协议值，就得在表里加一条。

uvc_probe() 的流程：分配 uvc_device、建链表、记 udev/intf/接口号、解析 quirk、拼设备名、解析 VC 描述符、注册 V4L2、初始化控制项、扫视频链、注册视频设备、注册 Media Controller、挂状态中断 URB：

c
static int uvc_probe(struct usb_interface *intf,
                     const struct usb_device_id *id)
{
        struct usb_device *udev = interface_to_usbdev(intf);
        struct uvc_device *dev;
        const struct uvc_device_info *info =
                (const struct uvc_device_info *)id->driver_info;
        int ret;

        dev = kzalloc(sizeof(*dev), GFP_KERNEL);
        if (dev == NULL)
                return -ENOMEM;

        INIT_LIST_HEAD(&dev->entities);
        INIT_LIST_HEAD(&dev->chains);
        INIT_LIST_HEAD(&dev->streams);
        kref_init(&dev->ref);
        atomic_set(&dev->nmappings, 0);
        mutex_init(&dev->lock);

        dev->udev = usb_get_dev(udev);
        dev->intf = usb_get_intf(intf);
        dev->intfnum = intf->cur_altsetting->desc.bInterfaceNumber;
        dev->info = info ? info : &uvc_quirk_none;
        dev->quirks = uvc_quirks_param == -1
                    ? dev->info->quirks : uvc_quirks_param;

        if (udev->product != NULL)
                strscpy(dev->name, udev->product, sizeof(dev->name));
        else
                snprintf(dev->name, sizeof(dev->name),
                         "UVC Camera (%04x:%04x)",
                         le16_to_cpu(udev->descriptor.idVendor),
                         le16_to_cpu(udev->descriptor.idProduct));

        if (uvc_parse_control(dev) < 0) {
                uvc_trace(UVC_TRACE_PROBE, "Unable to parse UVC "
                        "descriptors.\n");
                goto error;
        }

        if (v4l2_device_register(&intf->dev, &dev->vdev) < 0)
                goto error;

        if (uvc_ctrl_init_device(dev) < 0)
                goto error;

        if (uvc_scan_device(dev) < 0)
                goto error;
                goto error;

        usb_set_intfdata(intf, dev);

        if ((ret = uvc_status_init(dev)) < 0) {
                uvc_printk(KERN_INFO, "Unable to initialize the status "
                        "endpoint (%d), status interrupt will not be "
                        "supported.\n", ret);
        }

        usb_enable_autosuspend(udev);
        return 0;

error:
        uvc_unregister_video(dev);
        kref_put(&dev->ref, uvc_delete);
        return -ENODEV;
}

几个要点，和鼠标、键盘的写法对照着记：

  • usb_get_dev() / usb_get_intf() 是加引用计数，不是裸赋值。uvc_delete 里会对应 usb_put_dev() / usb_put_intf()。漏了这一步，热插拔时 usb_device 就悬空。
  • 失败路径统一 goto error，落到 uvc_unregister_video() + kref_put()。uvc_device 内部有 kref，即使某个使用者还没放，uvc_delete 也是延迟执行，不会 UAF。
  • uvc_parse_control() 是最容易失败的调用。描述符树残缺、长度字段不对、bNumFormats 与实际不符，都在这里打回。调试先看 Unable to parse UVC descriptors。
  • usb_enable_autosuspend() 放在最后，因为描述符解析期间需要设备全功率响应控制请求，过早挂起会让 GET_* 请求超时。
  • uvc_status_init() 失败不算致命，只打一行日志继续。状态端点上报设备事件，没有它也能出图。
  • #ifdef CONFIG_MEDIA_CONTROLLER 包着的那段（media_device_init()、dev->vdev.mdev = &dev->mdev、media_device_register()）只在打开 Media Controller 时存在。

uvc_disconnect() 走另一条路：先 usb_set_intfdata(intf, NULL)，再 uvc_unregister_video()、usb_put_intf()、kref_put(&dev->ref, uvc_delete)。uvc_delete 是 kref 的析构函数，做最后清理：停 status URB、usb_put_dev()、v4l2_device_unregister()、media_device_unregister()、kfree(dev)。

uvc_parse_control() 之后还要三步才能出 /dev/videoN：uvc_scan_device() 建出 chains，uvc_register_chains() 遍历链上的流，uvc_register_video() 调 uvc_video_init()、video_device_alloc()、video_register_device()。

uvc_scan_device() 在前一步建出 chains，uvc_register_chains() 遍历这些链，对每条链上的流注册一个 video_device。有两路视频流的设备会出 /dev/video0 和 /dev/video1。

video_register_device(video, VFL_TYPE_GRABBER, -1) 的第三个参数 -1 表示自动分配次设备号，所以节点号按顺序来，不保证稳定。要固定节点号得靠 udev 规则按 cap->bus_info 或者 USB 路径绑。

VFL_TYPE_GRABBER 在 5.10 之后改名成 VFL_TYPE_VIDEO，符号值没变。素材内核是 5.2.8，用 VFL_TYPE_GRABBER；往新内核移植要跟着改。

设备节点 /dev/videoN 的主设备号固定是 81（VIDEO_MAJOR），/dev/input/eventN 的是 13（INPUT_MAJOR）。

同一台设备上还注册了一个 input 节点，用来上报摄像头上的物理按键。

十一、V4L2 接口：驱动侧要填什么 #

V4L2 给驱动留了两个结构体：v4l2_file_operations 管文件操作，v4l2_ioctl_ops 管命令。UVC 把前者填得很薄，逻辑几乎都压到后者。

c
const struct v4l2_file_operations uvc_fops = {
        .owner          = THIS_MODULE,
        .open           = uvc_v4l2_open,
        .release        = uvc_v4l2_release,
        .unlocked_ioctl = video_ioctl2,
#ifdef CONFIG_COMPAT
        .compat_ioctl32 = uvc_v4l2_compat_ioctl32,
#endif
        .read           = uvc_v4l2_read,
        .mmap           = uvc_v4l2_mmap,
        .poll           = uvc_v4l2_poll,
#ifndef CONFIG_MMU
        .get_unmapped_area = uvc_v4l2_get_unmapped_area,
#endif
};
成员 含义 UVC 的做法
.owner 模块引用计数 THIS_MODULE，防止在用的时候被 rmmod
.open 打开设备 拿引用、建 uvc_fh、首次打开时启 status URB
.release 关闭设备 放引用、清 uvc_queue
.unlocked_ioctl 非 BKL 化的 ioctl 直接给 video_ioctl2，统一分发
.compat_ioctl32 32 位用户态在 64 位内核上 uvc_v4l2_compat_ioctl32
.read read() 逐帧读 uvc_v4l2_read，一般不推荐
.mmap 映射内核缓冲到用户态 uvc_v4l2_mmap，zero-copy 路径
.poll 等帧就绪 uvc_v4l2_poll
.get_unmapped_area 无 MMU 平台的映射地址 只有 !CONFIG_MMU 才有

mmap 和 poll 有个前置条件：必须先用 ioctl(VIDIOC_REQBUFS) 申请到 buffer，再 VIDIOC_QUERYBUF 拿到偏移，才能 mmap 和 poll。不申请直接映射返回 -EINVAL。

uvc_v4l2_open() 做三件事：usb_autopm_get_interface() 加自动挂起计数，首次打开时 uvc_status_start()，再 kzalloc 一个 uvc_fh 挂到 file->private_data。

release 是它的镜像：uvc_queue_release() 只在有特权的句柄上做，然后 v4l2_fh_del()、v4l2_fh_exit()、kfree(handle)，最后一个使用者退出时 uvc_status_stop()。

handle->state 那套 UVC_HANDLE_PASSIVE / UVC_HANDLE_DRIVER 状态机解决的是「多个进程同时打开同一颗摄像头」：谁先调 STREAMON，谁拿到 DRIVER 状态，独占数据流；其余进程留在 PASSIVE，只能读控制项不能开流。

unlocked_ioctl 直接挂 video_ioctl2，它转 video_usercopy() 做用户态指针的来回复制，再由 __video_do_ioctl() 按 cmd 查 v4l2_ioctls[] 表。表里每一项都是 IOCTL_INFO(命令号, 通用实现函数, 调试打印函数, 标志位) 的形式，例如 IOCTL_INFO(VIDIOC_QUERYCAP, v4l_querycap, v4l_print_querycap, 0)、IOCTL_INFO(VIDIOC_QBUF, v4l_qbuf, v4l_print_buffer, INFO_FL_QUEUE)。

v4l_querycap 之类的通用函数不直接干活，而是转手调驱动的 v4l2_ioctl_ops。UVC 那份把 vidioc_querycap、vidioc_enum_fmt_vid_cap、vidioc_g/s/try_fmt_vid_cap、vidioc_reqbufs、vidioc_querybuf、vidioc_qbuf/dqbuf、vidioc_streamon/off、vidioc_enum_input、vidioc_g/s_input、vidioc_queryctrl、vidioc_g/s_ctrl、vidioc_g/s/try_ext_ctrls、vidioc_g/s_parm、vidioc_enum_framesizes、vidioc_enum_frameintervals、vidioc_subscribe_event、vidioc_default 全部指向同名 uvc_ioctl_* 函数，vidioc_unsubscribe_event 直接复用 v4l2_event_unsubscribe。

整条调用链：

text
用户态 ioctl(fd, VIDIOC_QUERYCAP, &cap)
  → sys_ioctl
    → uvc_fops.unlocked_ioctl = video_ioctl2()
      → video_usercopy() → __video_do_ioctl()
        → v4l2_ioctls[] 查表，命中 v4l_querycap
          → uvc_ioctl_ops.vidioc_querycap = uvc_ioctl_querycap()

uvc_ioctl_querycap 是这条链的终点，也是调试时最常看的：strscpy 填 cap->driver = "uvcvideo"、cap->card = vdev->name；usb_make_path() 填 cap->bus_info；cap->capabilities = V4L2_CAP_DEVICE_CAPS | V4L2_CAP_STREAMING | chain->caps。

cap 里四个字段：

字段 值 用途
driver "uvcvideo" 用户态判断驱动类型，v4l2-ctl --all 里能看到
card vdev->name 来自 usb_device->product，如 USB 2.0 Camera
bus_info usb_make_path() USB 物理路径，多摄像头时靠它唯一识别
capabilities V4L2_CAP_DEVICE_CAPS | V4L2_CAP_STREAMING | chain->caps 设备能力位

V4L2_CAP_DEVICE_CAPS 很重要：设上它表示 capabilities 反映的是这个特定节点的能力，而不是整台主机的能力。系统上同时有多个 video 设备时，用户态必须靠这一位区分能力。

vdev->name 的内容来自 uvc_probe() 里的 strscpy(dev->name, udev->product, ...)，也就是 USB 2.0 Camera。设备没给 Product 字符串就回落到 UVC Camera (%04x:%04x) 格式。

十二、视频流的启动与停止 #

视频流是整篇里唯一走等时传输的地方，也是唯一需要自己管带宽的地方。STREAMON 到 STREAMOFF 之间的路径：

text
VIDIOC_STREAMON
  → uvc_ioctl_streamon()
    → uvc_queue_streamon()          置 QUEUE_STREAMING
    → uvc_video_start_streaming()
        → uvc_video_clock_reset()
        → uvc_init_video()          切 altsetting、拿带宽、提交 N 个 URB

uvc_init_video() 里有两件事做错就「能打开、没图像」：

  • 先 usb_set_interface() 切到正确的 altsetting。UVC 的 altsetting 0 是零带宽待机态，不切到 1 及以上，数据端点根本没使能，URB 提交成功也收不到数据。
  • 拿带宽。等时端点每次传输都要预留带宽，usb_submit_urb() 在带宽不足时返回 -ENOSPC。

每帧数据被拆成若干 URB 预先提交，形成流水线。URB 数量和单个 URB 的大小按分辨率和帧率算，算错的表现：

现象 原因
帧不完整、下半截绿或灰 每帧 URB 数量或单 URB 大小不够
偶发花屏 URB 数量刚好，但带宽不足，等时包被丢
首帧延迟大 URB 预提交数量过多
-ENOSPC 提交失败 同一条总线上其它等时设备抢了带宽

UVC 载荷头的解析是 uvc_video.c 里逻辑最绕的一段。每个等时包开头带一个载荷头（Payload Header）：

字段 含义
bHeaderLength 载荷头长度，最小 2 字节
bmHeaderInfo bit0 FID 帧 ID（0/1 交替）、bit1 EOF、bit2 PTS 置位、bit3 SCR 置位、bit7 错误位
dwPresentationTime 呈现时间戳，只有 PTS 位置位时才读
dwClockFrequency 设备时钟频率

解帧的三个关键点：

  • FID 翻转 = 新的一帧开始，把上一帧提交给 videobuf2；
  • EOF 位 = 这一帧的最后一个包；
  • bmHeaderInfo 的 bit7 错误位置位 = 这个包有问题，整帧该丢。有些设备带宽紧张时在这里报错但不丢包，UVC 驱动按「有错就丢帧」处理，宁可掉帧也不花屏。

uvc_queue 是 videobuf2 之上的一层薄封装，管三件事：缓冲区生命周期、帧就绪通知、序列号计数。核心状态机：

状态 含义 谁置
UVC_QUEUE_IDLE 还没申请 buffer open 之后
UVC_QUEUE_QUEUED 有 buffer 排队但没开流 QBUF
UVC_QUEUE_STREAMING 正在收帧 STREAMON
UVC_QUEUE_STOPPED 开过流又停了 STREAMOFF

用户态标准流程（mmap 版）：先 VIDIOC_REQBUFS 申请 N 个 V4L2_MEMORY_MMAP 缓冲，再对每个 index VIDIOC_QUERYBUF 拿 buf.m.offset 后 mmap 并 VIDIOC_QBUF 入队，然后 VIDIOC_STREAMON 开流。循环里 VIDIOC_DQBUF 出队取 buf.bytesused，用完立刻 VIDIOC_QBUF 还回去，最后 VIDIOC_STREAMOFF。Q 是 queue（交给驱动去填），D 是 dequeue（从驱动拿回填好的），别记反。

停流是启动的严格镜像：

text
VIDIOC_STREAMOFF
  → uvc_ioctl_streamoff()
    → uvc_queue_streamoff()
        → uvc_video_stop_streaming()
            → usb_set_interface(intf, ifnum, 0)   回到零带宽
            → uvc_video_free_urbs()               杀 URB
        → uvc_queue_cancel()                      取消所有在飞 buffer

usb_set_interface(..., 0) 不能漏：不切回 altsetting 0，等时带宽一直占着，同一条总线上的其它设备拿不到带宽。素材里 xawtv 报 v4l2: oops: select timeout 的一类现象，就是停流时 altsetting 没切干净或者 URB 没杀完，缓冲区里一直有新数据覆盖旧数据。

十三、USB 触摸屏：多点触控协议 #

触摸屏分电阻和电容两类，接口也分 I2C、SPI、USB。本篇只看 USB 的：Type-C 接口的 15.6 英寸 HDMI 屏，接在 NanoPC-T4 的 USB3.0 Type-C 口上，工作在 HOST 模式。

USB 触摸屏走的是 HID 类，不是专门的触摸类。内核里 USB HID transport layer 把键盘、鼠标、摇杆、绘图板、触摸屏都接进来，统一转成 input 事件。所以触摸屏驱动最终还是落在 input 子系统和多点触控协议上，只是数据来源从 Boot Protocol 的固定格式变成了 HID 报告描述符描述的格式。

内核有一份完整的多点触控协议文档，Documentation/input/multi-touch-protocol.rst，简称 MT 协议。它分两种：

类型 适用设备 上报方式
Type A 触摸点无法被硬件区分或跟踪 每帧把所有触点数据完整重报一遍，点与点之间用 SYN_MT_REPORT 分隔
Type B 触摸点能被硬件跟踪并区分 每个触点绑定一个 slot，只报变化的部分，用 ABS_MT_SLOT 切换当前 slot

Type B 用得最多，一般多点触摸 IC 都有跟踪能力。

触摸点信息通过 ABS_MT 系列事件上报，定义在 include/uapi/linux/input-event-codes.h。

常用几个事件码的含义：

事件码 含义
ABS_MT_SLOT 切换当前正在更新的 slot
ABS_MT_TRACKING_ID 为触摸点分配 ID，-1 表示这个点抬起
ABS_MT_POSITION_X / _Y 触点中心坐标
ABS_MT_TOUCH_MAJOR 触摸区域长轴
ABS_MT_WIDTH_MAJOR 接近椭圆的长轴（悬停时的虚拟面积）
ABS_MT_PRESSURE 压力

Type A 每帧把所有触点完整重报一遍，点间插 SYN_MT_REPORT，帧尾 SYN_REPORT。

input_report_abs() 是 input_event(dev, EV_ABS, code, value) 的封装；Type A 用 input_mt_sync() 发 SYN_MT_REPORT 分隔触点，input_sync() 发 SYN_REPORT 收尾一帧。

input_mt_sync() 触发的 SYN_MT_REPORT 告诉接收者「这个点报完了，准备接下一个点」，帧内每点一次。

Type B 用 ABS_MT_SLOT 切槽，每个槽先报一次 ABS_MT_TRACKING_ID，再报坐标，帧尾一次 SYN_REPORT。

Type B 的规则：驱动把每个识别出的触点和一个 slot 关联，通过修改该 slot 的 ABS_MT_TRACKING_ID 来完成触点的创建、替换、销毁。

  • ABS_MT_TRACKING_ID 跟踪触点属于哪一条「线」。这一帧的 ID 和上一帧相同，就是同一个触点。ID 不是随便赋的，是硬件跟踪出来的。
  • 上报 ABS_MT_TRACKING_ID = -1 表示这个触点抬起，系统清掉对应 slot。

两个关键函数：

c
static inline void input_mt_slot(struct input_dev *dev, int slot)
{
        input_event(dev, EV_ABS, ABS_MT_SLOT, slot);
}

bool input_mt_report_slot_state(struct input_dev *dev,
                                unsigned int tool_type, bool active);

input_mt_slot() 两个参数：dev 和 slot。slot 就是「第几个触摸点」，10 点触摸就是 0～9。它触发 ABS_MT_SLOT，告诉接收者下面这些数据是更新哪个 slot 的。

input_mt_report_slot_state() 负责给 slot 关联 ABS_MT_TRACKING_ID：

active 语义 内核行为
true 连续触摸 自动分配一个 ABS_MT_TRACKING_ID 给 slot
false 触点抬起 分配 -1 给 slot，清掉该点

典型驱动里，一次报告的处理长这样（结构示意，具体字段按设备报告格式填）：

c
for (i = 0; i < touch_num; i++) {
        input_mt_slot(dev, i);
        input_mt_report_slot_state(dev, MT_TOOL_FINGER, true);
        input_report_abs(dev, ABS_MT_POSITION_X, x[i]);
        input_report_abs(dev, ABS_MT_POSITION_Y, y[i]);
}

for (; i < MAX_TOUCHES; i++) {
        input_mt_slot(dev, i);
        input_mt_report_slot_state(dev, MT_TOOL_FINGER, false);
}

input_sync(dev);

这里最容易漏的是第二个循环：没上报的 slot 必须显式置 false，否则上一次遗留的触点会一直「粘」在屏幕上。这是 Type B 驱动最常见的 bug，表现为松开手指后光标还在原位置。

关键观察：这颗触摸屏没有专门的触摸驱动，是内核自带的 hid-generic 接管的。日志里 hid-generic 0003:222A:0001.0001 就说明是通用 HID 驱动在跑。触摸能正常工作，因为 HID 报告描述符里已经声明了 ABS_MT_* 这类多触点用法，hid-multitouch 或 hid-generic 直接按描述符解出来转给 input 子系统。

日志开头还有一行值得注意：

text
[    2.377212] usbcore: registered new interface driver usbtouchscreen

usbtouchscreen 是给电阻式 USB 触摸屏用的驱动（依靠厂商私有协议），和这颗电容式 HID 触摸屏不是一回事。它注册了但没接管这颗设备——接管的是 hid-generic。

Type-C 口要配成 HOST 模式，涉及三段设备树：USB3.0 OTG0 控制器、Type-C PHY0、USB2.0 OTG PHY0。

控制器节点 usbdrd3_0: usb@fe800000 在 arch/arm64/boot/dts/rockchip/rk3399.dtsi，内含 usbdrd_dwc3_0 子节点（compatible = "snps,dwc3"），phys 同时引用 u2phy0_otg 和 tcphy0_usb3。

使能成 HOST 就是在板级 dts 里覆盖这几个节点：&usbdrd3_0 { status = "okay"; }、&usbdrd_dwc3_0 { dr_mode = "host"; status = "okay"; }、&tcphy0 与 &tcphy0_usb3 置 okay、&u2phy0 置 okay、&u2phy0_otg { phy-supply = <&vbus_typec>; status = "okay"; }。

phy-supply 挂的 vbus_typec 是个 regulator-fixed，由 GPIO4_D2 使能（高电平触发），输入端是 vcc5v0_sys。这个 regulator 不配好，Type-C 口给不出 VBUS，触摸屏上电都上不了。

dr_mode = "host" 是关键。RK3399 的这个口默认是 otg，不覆盖成 host 的话，插上触摸屏也不会枚举——OTG 模式下要靠 ID 引脚或者 Type-C 的 CC 协商来决定角色，而触摸屏作为设备端不会发起角色切换。

验证控制器确实在 HOST 模式：

text
root@rk3399:/# cat /sys/kernel/debug/usb/fe800000.usb/mode
host

这个调试节点来自 DWC3 驱动，同一目录下还有几个：

节点 内容
link_state DWC3 链路状态
regdump DWC3 控制器寄存器快照
mode 当前工作模式（host / device / otg）
testmode 设置 HighSpeed 测试模式，用于眼图测试
lsp_dump 链路电源状态

触摸屏接上后如何确认触摸点数据真的在流动？用 evtest 选中触摸屏对应的 event 节点，手指按下去能看到一串 ABS_MT_* 事件，抬起来能看到 ABS_MT_TRACKING_ID 变成 -1。看不到 -1 就是第十四章末尾说的那个「slot 没清」的问题。

十六、驱动调试手段 #

调试手段按「从下往上」的顺序排：先确认 USB 层枚举成功，再看接口驱动有没有绑定，再看有没有出节点，最后看数据流。

1. 枚举层

lsusb -t 的 Driver= 一栏最有价值：一眼能看出哪个接口被哪个驱动绑上了。某个接口显示 Driver=[none]，说明 id_table 没匹配上，或者是 probe 返回了错误。lsusb 本身给出的是 Bus 001 Device 002: ID 0c45:6340 Microdia USB 2.0 Camera 这样的 VID/PID 行。

2. 驱动绑定层

/sys/bus/usb/drivers/uvcvideo/ 下既有已绑定的接口（1-1:1.0），也有一组控制文件：bind/unbind 手动解绑重绑、复现 probe；new_id 给不支持自动匹配的设备手动塞 VID/PID，写入会立刻触发一次匹配。不想改驱动重编时，new_id 最好用。

3. 设备节点层

/dev/input/event0 的主设备号 13、/dev/video0 的主设备号 81，ls -l 一眼能认出来。input 设备的详细信息在 sysfs，不在设备节点里：cat /sys/class/input/event0/device/name 得到设备名；/sys/class/input/eventN/device/capabilities/ 下是能力位图（十六进制字符串），能直接看出驱动声明了哪些 evbit/keybit/relbit/absbit；absbit 里有 0x2f（ABS_MT_SLOT）位置的位，就说明多点触摸可用。

4. 数据流层

evtest 是 input 设备的通用查看器，Supported events 这一段就是驱动 input_set_capability() 的结果——声明了但上报没反应，说明是上报路径的问题；没声明，就是 probe 里漏设了。

V4L2 设备用 v4l2-ctl -d /dev/videoN --list-formats-ext，它把描述符里所有格式和帧率列一遍，等价于解码了一遍 VS 描述符树；列表为空说明 uvc_parse_control() 或 uvc_scan_device() 出了岔子。

USB 层的原始报文抓取靠 usbmon：modprobe usbmon 之后读 /sys/kernel/debug/usb/usbmon/1u（1u 对应总线 1），拿到的是 URB 级别的十六进制流水，查「控制请求发出去没有、设备回没回」只有它可信。

5. 内核日志

dmesg 里按驱动名过滤：dmesg | grep -E "usb 1-1|uvcvideo|usbmouse|usbhid"，下面几条日志的含义对号入座就行：

日志 含义
new high-speed USB device number N using xxx 枚举成功，控制器认到了
device descriptor read/64, error -62 枚举阶段读描述符超时，见下
probe of 1-1:1.0 failed with error N probe 返回了错误码 N
can't resubmit intr, ..., status N 完成函数里重新提交 URB 失败
Unable to parse UVC descriptors UVC 描述符树有问题
Entity type for entity xxx was not initialized Media Controller 没编进来
cannot get freq at ep 0x84 UAC 音频接口读采样率失败，无害

device descriptor read/64, error -62 这个错误很经典：-62 是 ETIME（#define ETIME 62，Timer expired），read/64 表示读 64 字节描述符。它在 hub_port_init() 的 usb_control_msg() 重试循环里抛出。

这个错误发生在 probe 之前，属于 HCD 和物理层的问题，不是设备驱动代码的问题。素材在 S3C2440 上遇到的情况有两个方向：USB 时钟频率不对（改 s3c2410_start_hc() 里对 S3C2410_UPLLCON 的写入，把 UPLL 配成 48 MHz），或者供电不足。这两个方向都要单独验证，改 UPLL 那个方案在素材里「没有深究」，标记未验证。

几条通用教训收尾：

probe 的返回值一定要往回传。 第 1 条那个坑在素材的鼠标驱动里实打实发生了——probe 写成了 void，probe 里那些 return -ENODEV 全部变成「提前返回 0」，于是内核认为驱动接管成功，而实际上什么都没准备好。日志里那句 probe of 1-1:1.0 failed with error 53 是内核看到 probe 返回 -ENOENT（53）之后的抱怨，两件事对上了才知道问题在哪。

usb_kill_urb() 和 usb_unlink_urb() 不是一回事。 unlink 是异步的，发完立刻返回，完成函数还在跑；kill 是同步的，一直等到完成函数返回。disconnect 和 close 里必须用 kill。

缓冲区声明类型要跟着数据语义走。 有符号位移用 s8，无符号位图用 u8，别一律 char。ARM 上 char 默认无符号，x86 上有符号，同一个驱动在两种架构上行为不同。

input_sync() 的次数要数清。 一帧一次。漏了用户态收不到；多了会拆成半截帧，鼠标一卡一卡。

能力位不是装饰。 input_set_capability() 没声明的码，input_report_* 里上报了也会被 input core 静默丢掉，不报错、不打日志。evtest 的 Supported events 就是唯一的自查入口。
