MySQL 交叉编译与嵌入式平台移植实战 #

在物联网、工业网关以及智能车载终端等嵌入式设备开发中，我们有时需要在本地（如 ARM/ARM64 硬件开发板上）直接部署 MySQL 数据库，以满足大容量本地缓存和高效率关系型数据查询的业务需求。然而，由于 MySQL 本身逻辑极其庞大、构建期高度依赖 host（主机）本地的可执行程序来进行代码生成，且官方源码默认不支持平滑的交叉编译，这使得在 ARM 平台下交叉编译 MySQL 成为嵌入式开发中的一个硬骨头。

今天这篇实战指南，咱们就来完整拆解 MySQL 5.1.51 (基于 Autoconf) 以及 MySQL 8.0.22 (基于 CMake) 两代经典版本的交叉编译流程，同时分享我们在实际项目中的 6 大经典报错避坑排障套路，并附带生产级的多平台数据库高效迁移机制。

一、 嵌入式移植核心关注点 #

在动手编译之前，咱们作为架构师和底层开发人员，必须先搞明白交叉编译 MySQL 的几大核心“阻力”：

1.1 构建期二进制程序的宿主执行瓶颈 #

In MySQL 的编译过程中，编译器会实时生成并运行一些代码生成工具，用于动态生成 SQL 语法解析文件和字符集映射文件。这些工具包括：

  • gen_lex_hash：生成 lex 词法分析所需的哈希表表头。
  • uca9dump：转储和编译 Unicode 排序及映射字符集数据。
  • comp_sql：将系统初始化 SQL 脚本（如权限建表脚本）编译压缩成 C 语言数组常量。
  • gen_lex_token：根据词法生成解析 Token 标识符定义。

当进行交叉编译时，这些工具会被交叉编译器编译成目标板格式（如 ARM/AArch64）。当编译脚本在我们的 PC 开发机（如 x86_64 Ubuntu）上尝试执行 these 程序时，系统就会抛出 cannot execute binary file: Exec format error 报错导致构建崩溃。因此，我们必须采用“双路线构建”策略——先编译 PC 版获取原生辅助工具，再中途强行覆盖 ARM 构建目录中的对应程序。

1.2 ncurses 终端控制库依赖 #

MySQL 命令行客户端（即 mysql 终端工具）在运行和交互时，其控制台界面和交互输入底层完全依赖于 ncurses 库（终端绘图及字符处理库）。在交叉编译器环境中，默认只带了基础的 GCC/libc，缺少目标架构（ARM）下的 ncurses 静态库和头文件。因此在交叉编译 MySQL 前，必须先手动下载并交叉编译出目标架构的 libncurses.a 静态库，并将其路径显式传递给 MySQL 编译配置中。

1.3 静态链接库与密码库关联 #

现代 MySQL 8.0.x 版本在安全验证、SSL 通讯和 SASL 认证方面依赖 OpenSSL 和相关加密组件，在数据结构和基础库方面依赖 C++ Boost。在配置交叉编译时，必须理清这些外部依赖库在 ARM 平台下的对应物理路径。

二、 准备工作与依赖库交叉编译 #

我们以 /home/mysqlbuild 作为我们的工作区目录。

2.1 交叉编译 ncurses (以 5.9 版本为例) #

  1. 下载源码包：

    bash
    wget ftp://ftp.gnu.org/gnu/ncurses/ncurses-5.9.tar.gz
tar -zxvf ncurses-5.9.tar.gz -C /opt/
cd /opt/ncurses-5.9

  2. 配置与交叉编译： 我们需要指定交叉编译工具链的前缀（例如 arm-none-linux-gnueabi-gcc）并开启静态库与动态库生成：

    bash
    ./configure --prefix=/home/mysqlbuild/install \
            CC=arm-none-linux-gnueabi-gcc \
            --host=arm-none-linux-gnueabi \
            --enable-static \
            --enable-shared

  3. 编译并安装：

    bash
    make
sudo make install
    ℹ笔记

    如果在 make install 时由于权限问题抛错，可以使用超级用户拉起：sudo -i; make install。

2.2 交叉编译 OpenSSL (1.1.1g) #

如果使用自动化脚本构建，可以在配置文件中指定版本，并运行以下命令完成交叉编译部署：

bash
cd /home/mysqlbuild/openssl
./auto_install_opensrc.sh openssl

确保将生成的 libcrypto.a、libssl.a 安装至 /home/mysqlbuild/install 目录。

三、 MySQL 5.1.51 交叉编译实战 (Autoconf 路线) #

MySQL 5.x 版本采用的是经典的 configure 脚本生成 Makefile 方式。

3.1 步骤一：编译 PC 原生版本 #

为了获取 PC 版的 gen_lex_hash 辅助工具，我们先进行一次本地编译：

bash
# 解压源码
tar -zxvf mysql-5.1.51.tar.gz -C /opt/
cd /opt/mysql-5.1.51

# 检查系统是否安装了本机的 ncurses 库，若缺失先通过 apt 补充
sudo apt-get install libncurses5-dev -y

# 配置 PC 版编译
./configure --prefix=/usr/local/mysql-pc

# 开始编译 (此步只需 make 即可，无需 make install)
make

# 备份生成的 PC 版 gen_lex_hash 文件
cp sql/gen_lex_hash /opt/gen_lex_hash_pc

# 清理并重命名源码树以备后用
make clean
cd /opt
mv mysql-5.1.51 mysql-5.1.51-pc

3.2 步骤二：改写 configure 绕过交叉编译限制 #

解压一份干净的 MySQL 源码进行 ARM 编译：

bash
tar -zxvf mysql-5.1.51.tar.gz -C /opt/
cd /opt/mysql-5.1.51

使用编辑器打开 configure 脚本，搜索 $cross_compiling 变量相关的逻辑块。 官方脚本中，一旦检测到 cross_compiling=yes 就会直接通过 as_fn_error 强行终止配置。我们需要将四处包含如下逻辑的代码块：

bash
if test "$cross_compiling" = yes; then
    { { $as_echo "$as_me:${as_lineno-$LINENO}: error: cannot run test program while cross compiling" >&5
# ...

修改或注释掉，改成跳过输出：

bash
if test "$cross_compiling" = yes; then
    echo "skip cross check!"
else

确保全部 4 处类似的交叉编译阻力代码均已被正确注释。

3.3 步骤三：执行配置与源码级补丁 #

  1. 配置配置参数： 通过 --with-named-curseslibs 指向我们先前编译好的 ARM 版 libncurses.a：

    bash
    ./configure --host=arm-linux \
            --enable-static \
            --with-named-curseslibs=/home/mysqlbuild/install/lib/libncurses.a \
            --prefix=/usr/local/mysql \
            --without-debug \
            --without-docs \
            --without-man \
            --without-bench \
            --with-charset=gb2312 \
            --with-extracharsets=ascii,latin1,utf8

  2. 打上 STACK_DIRECTION 补丁： 在 ARM 架构中，系统栈的增长方向需要显式声明。用编辑器打开 /opt/mysql-5.1.51/sql/sql_parse.cc，在头部添加以下宏定义：

    cpp
    #define STACK_DIRECTION 1

  3. 覆盖 gen_lex_hash 程序： 由于我们要让构建脚本能够继续，先让编译走几步，当看到编译目录里生成了 sql/gen_lex_hash 时，立刻中止编译，并将我们备份的 PC 版 gen_lex_hash_pc 拷贝过去覆盖它，并用 touch 强行刷更新时间：

    bash
    cp /opt/gen_lex_hash_pc sql/gen_lex_hash
touch -m sql/gen_lex_hash

  4. 继续编译安装：

    bash
    make
sudo make install

四、 MySQL 8.0.22 交叉编译与 6 大报错攻坚 (CMake 路线) #

现代 MySQL 8.x 使用 CMake 进行构建。为了在 ARM64（如海思 aarch64-himix100-linux）平台上交叉编译，其构建机制和报错防线更加复杂。

4.1 步骤一：创建构建目录 #

bash
cd /home/mysqlbuild/mysql-8.0.22
mkdir build && cd build

4.2 步骤二：CMake 配置参数 #

bash
cmake .. -DCMAKE_INSTALL_PREFIX=/home/mysqlbuild/install \
         -DMYSQL_DATADIR=/home/mysqlbuild/install/data \
         -DDEFAULT_CHARSET=utf8 \
         -DDEFAULT_COLLATION=utf8_general_ci \
         -DCMAKE_CXX_COMPILER=aarch64-himix100-linux-g++ \
         -DCMAKE_C_COMPILER=aarch64-himix100-linux-gcc \
         -DWITH_BOOST=/home/mysqlbuild/mysql-8.0.22/boost/boost_1_73_0 \
         -DWITH_SSL=/home/mysqlbuild/install \
         -DCMAKE_SYSTEM_PROCESSOR=arm64 \
         -DCURSES_INCLUDE_PATH=/home/mysqlbuild/install/include \
         -DCURSES_LIBRARY=/home/mysqlbuild/install/lib/libncurses.a \
         -DIGNORE_AIO_CHECK=1 \
         -DBUILD_CONFIG=mysql_release \
         -DWITH_UNIT_TESTS=0

4.3 编译中 6 大经典报错防线破局之策 #

在执行 make 后，你会遭遇以下一连串经典报错阻力，请严格按照以下对策进行破局：

报错 1：CMakelists.txt:1374 处 patchelf 校验报错 #

  • 原因：交叉编译脚本会检查宿主机系统上是否安装了用于动态库路径修改的 patchelf 工具。
  • 对策：如果本地开发机没有，可以直接去 CMakeLists.txt 的 1374 行附近，将 patchelf 的条件分支判断代码段直接注释掉。

报错 2：LIBEVENT version must be at least 2.1, found ... #

  • 原因：CMake 的检查宏对于交叉编译下的 libevent 版本判定有误，虽然 MySQL 源码自带了 2.1.11 的库，但依然报错终止。
  • 对策：进入相关 CMake 检测脚本（如 cmake/libevent.cmake），将检查版本抛出错误的那几行 message(FATAL_ERROR ...) 强行注释掉。

报错 3：cannot execute binary file: Exec format error (uca9dump 等) #

  • 原因：构建过程中尝试在宿主机运行由交叉编译器生成的二进制代码生成工具，如 uca9dump、json_schema_embedder、comp_sql、gen_lex_token。控制台抛出如下典型错误：
    text
    [ 42%] Generating uca9dump
/home/mysqlbuild/mysql-8.0.22/build/runtime_output_directory/uca9dump: cannot execute binary file: Exec format error
make[2]: *** [runtime_output_directory/uca9dump] Error 126
  • 对策： 从我们在本机的 PC 编译树中（假设在 /home/mysqlbuild/mysql-8.0.22-pc/），找到对应的编译出的 x86_64 二进制文件，直接拷贝并覆盖当前的 ARM64 二进制：
    bash
    cp /home/mysqlbuild/mysql-8.0.22-pc/build/runtime_output_directory/uca9dump ./runtime_output_directory/
touch -m ./runtime_output_directory/uca9dump
    对于 comp_sql 等其他抛出无法执行错误的文件，同理复制并更新修改时间。

报错 4：os0atomic.ic:194:2: error: #error "Unsupported platform" #

  • 原因：InnoDB 引擎的原子操作层无法正确识别我们的 ARM 平台工具链。在较旧的 GCC 编译器中，可能缺乏对 ARM 平台原生的 64 位原子操作支持。控制台抛错：
    text
    /home/mysqlbuild/mysql-8.0.22/storage/innobase/include/os0atomic.ic:194:2: error: #error "Unsupported platform"
  • 对策：打开 storage/innobase/include/os0atomic.h，在头文件中直接强行添加宏定义：
    cpp
    #define HAVE_ATOMIC_BUILTINS 1

报错 5：/usr/lib64/libresolv.so: error adding symbols: File in wrong format #

  • 原因：在链接阶段，构建脚本默认把宿主机 PC 下的 libresolv.so 链接到了我们的 ARM64 目标程序中。
  • 对策：在 CMake 配置中显式将该库指定为交叉工具链自带的库路径：
    bash
    -DRESOLV_LIBRARY=/opt/hisi-linux/x86-arm/aarch64-himix100-linux/aarch64-linux-gnu/libc/usr/lib/libresolv.so

报错 6：‘os_compare_and_swap_thread_id’ was not declared in this scope #

  • 原因：由于线程 ID 结构在不同 CPU 架构下的位宽不同，MySQL 底层调用的比较交换函数发生了签名冲突。
  • 对策：用全局搜索该关键字，在源码中将该函数的调用全部修改为通用的底层大整数比较交换函数 os_compare_and_swap_lint。

五、 板端移植部署与 SysV Init 服务配置 #

编译完成后，我们需要将安装目录打包并部署到我们的 ARM 开发板上。

5.1 拷贝文件与分配 my.cnf 模板 #

  1. 打包库文件：

    bash
    tar -zcvf mysql-arm-install.tar.gz /home/mysqlbuild/install

    在板端将其解压至 /usr/local/mysql 目录下。

  2. 分配配置文件： 从源码中的 support-files 下拷贝 mymedium.cnf 配置文件模板至板端的 /etc/my.cnf：

    bash
    cp support-files/mymedium.cnf /etc/my.cnf

    用编辑器打开 /etc/my.cnf，指定数据路径和基础运行路径：

    text
    [mysqld]
basedir = /usr/local/mysql
datadir = /var/lib/mysql
user    = mysql

5.2 数据库初始化 #

  1. 新建 mysql 运行用户：

    bash
    adduser mysql
chown -R mysql:mysql /usr/local/mysql
chown -R mysql:mysql /var/lib/mysql

  2. 执行初始化脚本：

    bash
    cd /usr/local/mysql/bin
./mysql_install_db --user=mysql --basedir=/usr/local/mysql --datadir=/var/lib/mysql

  3. 创建进程 PID 目录：

    bash
    mkdir -p /usr/local/mysql/var/run/mysqld
chown -R mysql:mysql /usr/local/mysql/var/run/mysqld

5.3 编写 SysV Init 服务控制脚本 #

由于大部分 ARM 开发板运行的是精简的 Linux 发行版（如 BusyBox），不支持 systemctl，我们需要在 /etc/init.d/mysqld 下编写一个标准的 SysV 控制脚本，以便系统开机时能自动拉起守护进程：

bash
#!/bin/sh
# /etc/init.d/mysqld
# 用于控制嵌入式开发板上 MySQL 守护进程启动与关闭的脚本

BASEDIR="/usr/local/mysql"
DATADIR="/var/lib/mysql"
PIDFILE="/var/lib/mysql/mysqld.pid"
MYSQLD="$BASEDIR/bin/mysqld"

start() {
    echo -n "Starting MySQL daemon... "
    if [ -f "$PIDFILE" ]; then
        PID=$(cat "$PIDFILE")
        if kill -0 "$PID" 2>/dev/null; then
            echo "Already running (PID: $PID)."
            exit 0
        fi
    fi
    
    # 以后台进程形式拉起守护进程并注入参数
    $MYSQLD --basedir=$BASEDIR \
            --datadir=$DATADIR \
            --user=mysql \
            --innodb-flush-method=O_DIRECT \
            --skip-ssl \
            --auto-generate-certs=FALSE \
            --skip-sha256-password-auto-generate-rsa-keys \
            --log-error=$DATADIR/mysqld.log \
            --pid-file=$PIDFILE >/dev/null 2>&1 &
            
    # 等待 3 秒检查进程是否成功拉起
    sleep 3
    if [ -f "$PIDFILE" ]; then
        echo "SUCCESS (PID: $(cat $PIDFILE))."
    else
        echo "FAILED. Please check $DATADIR/mysqld.log"
    fi
}

stop() {
    echo -n "Stopping MySQL daemon... "
    if [ -f "$PIDFILE" ]; then
        PID=$(cat "$PIDFILE")
        kill "$PID"
        
        # 等待进程退出释放文件锁
        count=0
        while kill -0 "$PID" 2>/dev/null; do
            sleep 1
            count=$((count+1))
            if [ $count -gt 15 ]; then
                echo "Force killing... "
                kill -9 "$PID"
                break
            fi
        done
        rm -f "$PIDFILE"
        echo "SUCCESS."
    else
        echo "MySQL daemon is not running."
    fi
}

status() {
    if [ -f "$PIDFILE" ]; then
        PID=$(cat "$PIDFILE")
        if kill -0 "$PID" 2>/dev/null; then
            echo "MySQL daemon is running (PID: $PID)."
        else
            echo "PID file exists but process is dead."
        fi
    else
        echo "MySQL daemon is stopped."
    fi
}

case "$1" in
    start)
        start
        ;;
    stop)
        stop
        ;;
    status)
        status
        ;;
    restart)
        stop
        start
        ;;
    *)
        echo "Usage: $0 {start|stop|restart|status}"
        exit 1
        ;;
esac

赋予脚本可执行权限并测试：

bash
chmod +x /etc/init.d/mysqld
/etc/init.d/mysqld start

六、 跨机器与多架构间数据库迁移规范 #

在开发 and 运维中，经常需要将宿主机上已经建好的表结构和数据移植或备份拷贝到我们的目标 ARM 板上。根据业务量和数据库格式的不同，有两种最高效的拷贝姿势：

6.1 姿势一：MyISAM 表的物理单文件复制（限 MyISAM 引擎） #

如果你的表引擎使用的是 MyISAM 格式，你可以直接在两台架构相同或浮点数格式相同的机器之间物理拷贝其底层的三个核心表文件：

  • .frm：存储表结构定义。
  • .MYD：存储表内真实数据（Data）。
  • .MYI：存储表索引（Index）。

将这些文件拷贝到目标板的 /var/lib/mysql/db_name/ 目录下后，直接赋予 mysql 用户权限即可立刻使用，不需要任何 SQL 还原。

6.2 姿势二：利用 mysqldump 逻辑备份与安全导入 #

对于默认的 InnoDB 引擎，跨平台物理拷贝极易引发数据页损坏。推荐使用底层的 mysqldump 备份导入大法。

6.2.1 标准导出与网络网络管道直接对拷 #

如果你有局域网连接，可以通过管道在一行命令内将 PC 主机上的数据库拷贝至 ARM 目标板上，无需落地大文件：

bash
# 1. 在 PC 上转储并直接管道推给目标板
mysqldump --opt -h localhost -u root -p my_db | mysql -h 'ARM_IP_ADDRESS' -u root -p my_db

6.2.2 低速网络下的压缩备份 #

如果在远程弱网环境下，可以使用 gzip 压缩流来节省网络带宽：

bash
# 1. PC 侧打包压缩导出
mysqldump --quick --opt my_db | gzip > my_db_dump.sql.gz

# 2. 传到开发板上，通过解压流直接导入
mysqladmin -u root -p create my_db
gunzip < my_db_dump.sql.gz | mysql -u root -p my_db

6.2.3 极速文本导入（适合千万级超大表） #

对于包含海量数据的超级大表，常规的 INSERT 逻辑转储导入极慢。我们可以利用 --tab 进行数据格式分离导出：

  1. PC 侧导出：
    bash
    mkdir /tmp/dumpdir
mysqldump --tab=/tmp/dumpdir -u root -p my_db
    这会在 dumpdir 目录下针对每个表生成两个文件：一个 .sql（建表语句）和一个 .txt（以 Tab 分隔的纯文本数据）。
  2. ARM 板端极速恢复： 把 dumpdir 拷贝到板子上，执行：
    bash
    # 新建空库
mysqladmin -u root -p create my_db
# 1. 瞬间建表
cat /tmp/dumpdir/*.sql | mysql -u root -p my_db
# 2. 调用底层极速文件载入机制导入数据
mysqlimport -u root -p my_db /tmp/dumpdir/*.txt

6.2.4 刷新授权表缓存 #

在成功恢复了包含权限和用户表的 mysql 核心库后，必须在终端执行以下命令，强迫服务器立刻重新加载内存中的授权表信息：

bash
mysqladmin -u root -p flush-privileges

七、 数据库完整性校验与备份验证 (Verification & Integrity Checks) #

数据迁移至嵌入式开发板后，为了确保没有在传输过程中由于网络丢包或二进制对齐错误引发页面损坏（Corruption），极客开发者应按照以下步骤对数据库完整性进行审计：

7.1 使用 mysqlcheck 命令行工具一键审计 #

mysqlcheck 是官方提供的表维护工具。在板端终端中，运行以下命令检查所有的数据库：

bash
mysqlcheck -u root -p --all-databases --check

该命令会依次打印每张表的状态，如果是健康无损的，会打印 OK：

text
my_db.users                                        OK
my_db.orders                                       OK

7.2 表损毁后的修复指令 #

如果在迁移时发生错误（如 MyISAM 索引字节错乱），可以使用修复指令：

  • 对于 MyISAM 表：
    sql
    -- 在 SQL 命令行中执行物理索引重建
REPAIR TABLE my_table;
  • 对于 InnoDB 表： InnoDB 引擎不支持普通的 REPAIR，如果它检测到表损毁，我们需要重建表结构。最安全的实践是在 SQL 命令行中重新载入引擎：
    sql
    -- 这将会在底层重建表的数据物理页面，自动修复物理坏道
ALTER TABLE my_table ENGINE=InnoDB;

7.3 利用 md5sum 进行物理层离线文件校验 #

如果开发板上的数据库服务处于停止状态，我们无法运行 mysqlcheck。此时，可以使用底层的 md5sum 物理文件校验方案：

  1. 在源 PC 主机上生成各表数据文件的 MD5 校验和：
    bash
    find /var/lib/mysql/my_db -type f -exec md5sum {} \; > /tmp/db_source.md5
  2. 将生成的 db_source.md5 传到开发板上，在对应的库目录下执行核对：
    bash
    cd /var/lib/mysql/my_db
md5sum -c /tmp/db_source.md5
    如果所有的输出都显示 OK，说明底层的物理二进制字节块没有发生任何丢包或位偏移损坏。

八、 总结 #

交叉编译虽然艰苦，但是只要理清了构建期“代码生成器”在 x86_64 宿主环境下的替代机制，配合 ncurses 的静态库预编译，就能顺利在各种复杂的嵌入式系统上跑起健壮的 MySQL 服务。结合 mysqldump --tab 极速迁移机制，能够为你的物联网和边缘计算网关提供坚如磐石的数据存储后盾！
