Linux 段错误排查与 GDB 核心转储调试实战 #

在 C/C++ 开发中， **段错误（Segmentation Fault）**是令所有开发者头疼的致命崩溃故障。 程序突然异常终止， 控制台只留下一句冰冷的 Segmentation fault。

段错误的本质是程序违反了操作系统的内存管理规则。 通常是硬件 MMU 触发异常， 并由内核向进程发送 SIGSEGV 信号。 本指南将带你从段错误的底层物理机制出发， 深度解析如何启用和配置 Linux 核心转储（Core Dump）。 演示如何通过代码捕获信号自动打印崩溃调用栈。 并以实战代码演示如何利用 GDB 抓出引发崩溃的幕后黑手， 同时针对嵌入式系统提供跨平台的交叉 GDB 符号调试方案。

1. 深入理解段错误（SIGSEGV）的成因 #

段错误通常是指进程尝试访问其虚拟地址空间之外的物理内存， 或者尝试以非法方式访问合法内存（例如写入只读区域）。

1.1 常见的段错误根源 #

  1. 空指针解引用（Null Pointer Dereference）： 试图读取或写入地址为 0x0（NULL）的内存空间。 这是最典型的段错误原因。
  2. 野指针/悬空指针访问（Wild/Dangling Pointer）： 访问未初始化或已被 free/delete 释放的内存区域。
  3. 缓冲区溢出（Buffer Overflow）： 数组越界或指针加减失控， 导致读写操作覆盖了进程未分配 of 虚拟页面或破坏了函数调用栈（Stack Corruption）。
  4. 内存写入权限冲突： 试图修改只读内存段。 例如修改常量字符串：
    c
    char *str = "Hello World"; // "Hello World" 储存在 ELF 的只读数据段 (.rodata)
str[0] = 'h';             // 触发段错误
  5. 栈溢出（Stack Overflow）： 深度递归或在栈上分配了过大空间的局部变量， 超出了系统分配给该线程的栈容量空间限制。

1.2 异常内存访问相关系统信号对照表 #

信号名称 信号值 触发原因 典型场景
SIGSEGV 11 段错误 (Segmentation Violation) 空指针解引用、越界读写未分配的物理页、修改只读内存。
SIGBUS 7 总线错误 (Bus Error) 物理内存对齐错误（Alignment Error）、非法的物理地址访问。
SIGILL 4 非法指令 (Illegal Instruction) 执行了损坏的机器指令、栈破坏导致跳转到了无效的数据区。
SIGFPE 8 浮点异常 (Floating Point Exception) 除以零错误、溢出、浮点计算溢出。

2. 核心转储（Core Dump）机制与系统环境配置 #

当进程由于未捕获的严重信号（如 SIGSEGV, SIGFPE, SIGABRT 等）异常终止时， 操作系统可以将该进程当时的内存映像、CPU 寄存器状态以及系统调用堆栈等信息完整地转储（Dump）保存到一个文件中， 这个文件被称为 Core Dump（核心转储） 文件。

2.1 利用 ulimit 开启 Core Dump 功能 #

在大多数主流 Linux 发行版中， 为了防止突发崩溃占满磁盘空间， 系统默认将 Core 文件的最大限制设置为 0（即禁用转储）。

2.1.1 ulimit 命令行工具详解 #

ulimit 命令用于控制 Shell 启动的进程所占用的各种系统资源上限：

bash
# 查看当前 Shell 的所有资源配置上限
ulimit -a

其常见选项如下：

  • -H：设定或显示硬性资源限制（只有 root 可以调大）。
  • -S：设定或显示弹性资源限制（不能超过硬性限制）。
  • -c：设置 Core 文件的最大容量限制（单位：512 字节的数据块 blocks）。
  • -s：设置线程最大栈空间（单位：Kbytes）。
  • -n：设置单个进程可开启的文件描述符最大数量。

2.1.2 临时启用 #

在当前 Shell 终端下执行以下命令即可临时开启 Core Dump：

bash
# 将限制设置为无限制
ulimit -c unlimited

# 再次确认配置是否生效
ulimit -a | grep core
# 输出：core file size          (blocks, -c) unlimited

2.1.3 永久生效配置 #

为了保证系统重启后依然有效， 可选择以下方案进行配置持久化：

  • 方案 A：编辑 /etc/security/limits.conf 文件，加入以下配置：
    # 指定所有用户（*）在软限制（soft）与硬限制（hard）下 core 文件均为 unlimited
*               soft    core            unlimited
*               hard    core            unlimited
  • 方案 B：对于系统级守护进程，在启动脚本（如 systemd 的 .service 文件）中显式指定限制：
    ini
    [Service]
LimitCORE=infinity

2.2 配置 Core 文件的保存路径与命名规则 #

默认情况下， 生成的 Core 文件可能命名为 core 并生成在程序运行的当前工作目录中， 极易引起重名覆盖且散落各处。

我们可以通过修改内核参数 /proc/sys/kernel/core_pattern 来统一规范其存放目录和命名规则：

bash
# 临时配置：将 core 文件统一存放至 /tmp/cores 目录下，并以“程序名-进程PID-时间戳”命名
sudo sysctl -w kernel.core_pattern="/tmp/cores/core-%e-%p-%t"

core_pattern 支持的命名格式化占位符： #

占位符 描述说明
%e 触发崩溃的可执行文件名。
%p 发生崩溃的目标进程 PID。
%t 发生崩溃时的 UNIX 时间戳。
%u 发生崩溃进程的实际用户 ID (UID)。
%g 发生崩溃进程的实际组 ID (GID)。
%s 导致崩溃的系统信号值（例如 SIGSEGV 是 11）。
%h 主机名（Hostname）。

若要永久保存此配置， 可修改 /etc/sysctl.conf 文件， 添加如下行：

kernel.core_pattern = /var/log/cores/core-%e-%p-%t

保存后执行 sudo sysctl -p 重新加载配置生效。 注意：必须提前手动创建好指定的存储目录（如 /var/log/cores），并确保进程对该目录具有写入权限。

3. 实战 1：代码层面主动捕获 SIGSEGV 并自动输出堆栈 #

在某些生产环境中， 由于磁盘只读或安全限制， 我们可能无法获取 Core 文件。 此时， 可以在代码中挂载信号处理器（Signal Handler）。 在崩溃瞬间调用 glibc 的 <execinfo.h> 库反向解析当前线程的堆栈信息， 直接打印到日志中。

c
#include <stdio.h>
#include <stdlib.h>
#include <signal.h>
#include <execinfo.h>
#include <unistd.h>

// 崩溃信号处理回调函数
void crash_signal_handler(int sig) {
    void *array[30];
    size_t size;

    // 获取当前线程挂起的堆栈地址帧
    size = backtrace(array, 30);

    // 在标准错误中打印堆栈跟踪
    fprintf(stderr, "
=== SYSTEM CRASH DETECTED ===
");
    fprintf(stderr, "Received Fatal Signal: %d
", sig);
    fprintf(stderr, "Stack Trace:
");
    
    // 反向解析符号信息并输出到标准错误输出
    backtrace_symbols_fd(array, size, STDERR_FILENO);
    
    // 恢复默认信号处理函数并重新抛出，确保生成 Core
    signal(sig, SIG_DFL);
    kill(getpid(), sig);
}

void register_crash_handlers() {
    // 注册我们感兴趣的内存崩溃相关信号
    struct sigaction sa;
    sa.sa_handler = crash_signal_handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;

    sigaction(SIGSEGV, &sa, NULL);
    sigaction(SIGBUS,  &sa, NULL);
    sigaction(SIGILL,  &sa, NULL);
    sigaction(SIGFPE,  &sa, NULL);
}

注意：编译时需要加入 -rdynamic 选项，否则 backtrace_symbols 只能打印函数内存地址，无法映射为具体的函数名称。

4. 实战 2：模拟典型的内存崩溃崩溃用例 #

除了普通的空指针访问之外， 堆栈溢出和堆破坏也是极其常见的故障模式。

4.1 栈帧溢出模拟（无限递归） #

c
#include <stdio.h>

// 递归函数，故意没有退出基准，导致不断入栈直到溢出
void stack_overflow_func(int counter) {
    char large_buffer[4096] = {0}; // 每次压栈分配 4KB
    large_buffer[0] = (char)counter;
    printf("[Stack] Depth level: %d
", counter);
    stack_overflow_func(counter + 1);
}

void test_stack_overflow() {
    stack_overflow_func(1);
}

当此函数运行后， 内核发现进程尝试越过当前线程所能达到的极限栈边界， 便会发出 SIGSEGV。

4.2 堆内存破坏（Double Free / Heap Corruption） #

c
#include <stdlib.h>
#include <string.h>

void test_heap_corruption() {
    char* ptr = (char*)malloc(10);
    strcpy(ptr, "12345678901234567890"); // 写入 20 字节，严重越界破坏了 malloc 内存控制块结构
    
    // 故意进行双重释放
    free(ptr);
    free(ptr); // 此时会引发 glibc 内部检测并发出 SIGABRT 信号
}

5. 实战 3：编译与运行 #

我们编写一个有缺陷的 C 程序 segfault_demo.c：

c
#include <stdio.h>
#include <string.h>

void trigger_crash(const char* data) {
    char buffer[10];
    printf("[Internal] Copying data...
");
    
    // 故意引入 NULL 指针解引用逻辑
    char* null_ptr = NULL;
    *null_ptr = 'X'; 
}

void func_b(const char* data) {
    trigger_crash(data);
}

void func_a(const char* data) {
    func_b(data);
}

int main(int argc, char* argv[]) {
    printf("[Main] System initialized. Calling functions...
");
    const char* payload = "This is a very long text";
    func_a(payload);
    printf("[Main] System terminated normally.
");
    return 0;
}

使用 -g 编译选项， 指示 GCC 在可执行二进制中嵌入完整的 DWARF 调试符号信息：

bash
$ gcc -g segfault_demo.c -o segfault_demo

确保 ulimit -c unlimited 已设置， 然后运行程序：

bash
$ ./segfault_demo
[Main] System initialized. Calling functions...
[Internal] Copying data...
Segmentation fault (core dumped)

终端显示 (core dumped)， 表示核心转储成功生成。 我们去前面配置好的目录或当前目录下寻找， 发现生成了 core-segfault_demo-28564-1689587421。

6. GDB 载入 Core 文件交互式排障 #

使用 GDB 加载可执行程序与对应的 Core 文件进行联合调试。 其命令格式为：gdb [可执行文件路径] [Core 文件路径]

bash
$ gdb ./segfault_demo /tmp/cores/core-segfault_demo-28564-1689587421

GDB 启动后， 会自动读取 Core 文件内的状态数据， 定位崩溃瞬间的寄存器状态， 并给出最终报错行定位：

Core was generated by `./segfault_demo'.
Program terminated with signal SIGSEGV, Segmentation fault.
#0  0x00000000004005aa in trigger_crash (data=0x4006c0 "...") at segfault_demo.c:9
9	    *null_ptr = 'X';
(gdb)

6.1 必备的 GDB 调试诊断命令 #

此时， 我们已经进入 GDB 的交互控制台。 利用以下指令进行全方位现场勘查：

1. 查看调用堆栈：backtrace 或 bt #

这是诊断的首要动作。 它以层级列出程序崩溃时的函数嵌套调用路径：

(gdb) bt
#0  0x00000000004005aa in trigger_crash (data=0x4006c0 "...") at segfault_demo.c:9
#1  0x00000000004005cf in func_b (data=0x4006c0 "...") at segfault_demo.c:15
#2  0x00000000004005df in func_a (data=0x4006c0 "...") at segfault_demo.c:19
#3  0x0000000000400605 in main (argc=1, argv=0x7ffe178a9c48) at segfault_demo.c:25

调用链清晰地显示了从 main -> func_a -> func_b -> trigger_crash 的崩溃链路。

2. 切换当前函数上下文栈帧：frame <N> #

如果要检查父函数的内部变量， 可以切换栈帧：

# 切换到 func_b 栈帧
(gdb) frame 1
#1  0x00000000004005cf in func_b (data=0x4006c0 "...") at segfault_demo.c:15
15	    trigger_crash(data);

3. 列出代码上下文：list 或 l #

列出发生段错误前后的代码片段：

(gdb) list
4	void trigger_crash(const char* data) {
5	    char buffer[10];
6	    printf("[Internal] Copying data...
");
7	    
8	    char* null_ptr = NULL;
9	    *null_ptr = 'X'; 
10	}

4. 打印变量值：print <var_name> 或 p <var_name> #

检查引发崩溃的指针或变量值：

(gdb) print null_ptr
$1 = (char *) 0x0

证实 null_ptr 确实是 0x0（空指针）， 对其进行写入操作显然会触发段错误。

5. 检查寄存器状态与汇编指令（进阶应用） #

当代码经过链接器重度优化（如开启 -O3 导致调试符号行号对应错乱时）， 我们需要 GDB 深入汇编底层：

  • rip (Instruction Pointer)：存储当前执行的指令地址。
  • rsp (Stack Pointer)：指向当前栈顶。
  • rbp (Frame Pointer)：指向当前函数栈基址。
# 查看所有 CPU 寄存器的值
(gdb) info registers
rax            0x0	0
rbx            0x400620	4195872
rcx            0x0	0
rdx            0x7ffe178a9940	140729290070336
rsi            0x0	0
rdi            0x7ffe178a9960	140729290070368
rbp            0x7ffe178a9c00	0x7ffe178a9c00
rsp            0x7ffe178a9be0	0x7ffe178a9be0
rip            0x4005aa	0x4005aa <trigger_crash+38>
...

我们发现指令指针寄存器 rip 指向的地址为 0x4005aa。 反汇编当前函数：

(gdb) disassemble trigger_crash
Dump of assembler code for function trigger_crash:
   0x0000000000400584 <+0>:	push   %rbp
   ...
   0x00000000004005a3 <+31>:	movq   $0x0,-0x8(%rbp)
=> 0x00000000004005aa <+38>:	mov    -0x8(%rbp),%rax
   0x00000000004005ae <+42>:	movb   $0x58,(%rax)

汇编代码清晰地表明， 程序先将 0x0（即指针）送入 %rbp - 8 的内存。 接着在 0x4005aa 处将该值（0）装载进寄存器 %rax。 下一条指令尝试将字符 'X'（ASCII 码即 0x58）写入 %rax 所指向的地址（0）。 从而触发硬件缺页异常并报段错误。

7. 嵌入式跨平台交叉 Core Dump 符号解析实战 #

在嵌入式开发中， 目标板（如 ARM 板）由于磁盘空间小且主频低， 通常无法直接运行 GDB 进行本地解析。 此时， 我们需要在宿主机上使用交叉调试器来还原崩溃堆栈。

7.1 交叉调试三大必备要素 #

  1. 板端生成的 Core 文件：压缩并拷贝回宿主机。
  2. 带调试符号的未剥离（unstripped）可执行二进制文件：通常在编译输出目录中保存， 不要拷贝被 strip 后的生产固件。
  3. 带调试符号的共享库集合路径（Sysroot）：板子依赖的所有 .so 库的未剥离符号集合。

7.2 宿主机交叉 GDB 启动配置 #

在宿主机上启动针对目标板架构 of GDB 工具（以 aarch64 为例）：

bash
$ aarch64-linux-gnu-gdb ./segfault_demo_unstripped /home/dev/core-segfault-arm64

由于 GDB 默认会去宿主机本地的 /lib 路径寻找共享库符号， 我们将看到大量符号文件无法加载的警告。

在交叉 GDB 控制台内设定符号映射路径： #

# 1. 设定 sysroot，使其指向与目标板 glibc 匹配 of 未剥离系统库目录
(gdb) set sysroot /home/dev/toolchain/sysroot

# 2. 设定共享库（其他自己编写的so）的额外搜索目录
(gdb) set solib-search-path /home/dev/project/libs

# 3. 强制要求 GDB 重新加载共享库符号
(gdb) sharedlibrary

经过这一设置， GDB 将重新建立符号索引。 堆栈回溯中原本显示为 ?? 的动态库符号将能全部精确呈现出来。 从而实现与本地调试完全一致的秒级定位体验。

8. 内存崩溃排查进阶：AddressSanitizer (ASan) 诊断利器 #

8.1 什么是 AddressSanitizer？ #

虽然 GDB + Core Dump 非常强大， 但对于一些隐蔽的内存损坏（如越界读写、Use-After-Free）， Core Dump 可能发生在错误发生的很久以后， 甚至由于内存刚好合法而没有触发段错误， 导致难以定位根因。 AddressSanitizer (ASan) 是由 Google 开发的一款快速内存错误检测工具， 已经集成在 GCC (4.8+) 和 Clang 中。 它在编译期对代码进行插桩， 在运行期监控内存访问， 能在发生非法访问的瞬间立刻中断程序并打印极其详细的报告。

8.2 开启 ASan 的编译选项 #

在编译时， 向编译器和链接器同时传入 -fsanitize=address 选项， 并加入 -fno-omit-frame-pointer 以保证调用栈的完整性：

bash
$ gcc -fsanitize=address -fno-omit-frame-pointer -g segfault_demo.c -o segfault_asan

8.3 运行并解读 ASan 报告 #

运行编译好的二进制文件， 无需 ulimit 配合， 它会自动检测崩溃：

=================================================================
==31245==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x60200000011a at pc 0x000000400c2a bp 0x7ffd58c29db0 sp 0x7ffd58c29da8
WRITE of size 1 at 0x60200000011a thread T0
    #0 0x400c29 in test_heap_corruption() segfault_demo.c:16
    #1 0x400da2 in main segfault_demo.c:26
...

ASan 报告不仅指出了错误类型（heap-buffer-overflow， 堆溢出）， 还指出了越界写入的具体发生行数（segfault_demo.c:16）， 甚至打印出该内存块是在哪里申请的。

9. 段错误调试故障排查 FAQ #

Q1: GDB 加载 Core 文件后显示 "No debugging symbols found" 怎么办？ #

  • 原因：当前加载的可执行二进制文件被去除了符号（stripped）。
  • 解决：在调试时，必须让 GDB 载入包含符号的未剥离版本（编译产物里的原始二进制），而不是拷贝到生产环境下的 stripped 版本。

Q2: 崩溃发生后，没有生成 Core 文件，ulimit -c 已经设置 unlimited 了？ #

  • 原因 1：磁盘空间不足或当前目录对当前运行用户无写入权限。
  • 原因 2：程序在崩溃前自己捕获了信号并且调用了 exit()，没有以异常终止方式结束。
  • 原因 3：系统使用了 Systemd 的 coredumpd 机制，core 文件被自动收集到了 /var/lib/systemd/coredump 或 journalctl 中。可以通过 coredumpctl list 命令查看。

Q3: Core 文件大小被截断 (Truncated core file) 怎么办？ #

  • 原因：尽管设置了 ulimit，但可写磁盘剩余空间小于 Core 文件大小，或者程序被强行终止导致写入未完成。
  • 解决：检查磁盘可用空间，或通过配置 core_pattern 将 Core 文件输出到内存文件系统（如 /dev/shm 或 /tmp）。

Q4: 如何在没有 GDB 的开发板上运行远程调试？ #

  • 解法：在开发板上运行轻量级的 gdbserver，指定端口并附着到进程上；在宿主机上运行交叉调试器（如 aarch64-linux-gnu-gdb），执行 target remote <IP>:<PORT> 进行远程联调。

10. 内存错误检测利器：Valgrind 动态分析 #

10.1 什么是 Valgrind？ #

Valgrind 是 Linux 下非常强大的动态二进制分析工具。 它包含一组工具， 其中最常用的是 Memcheck， 用于检测 C/C++ 程序中的各种内存错误：

  • 使用未初始化的内存
  • 内存泄露（malloc 申请后未释放）
  • 读写已释放的内存
  • 越界读写内存（堆/栈溢出）
  • 重复释放内存（Double Free）

10.2 Valgrind 的基本用法 #

使用 Valgrind 不需要重新编译程序， 可以直接分析二进制文件。 但为了看到具体出错的函数名和代码行号， 建议在编译时加上 -g 选项。

bash
$ valgrind --tool=memcheck --leak-check=full ./segfault_demo

10.3 解析 Valgrind 错误报告 #

运行后， Valgrind 会输出详细的诊断报告。 下面是一个典型的内存泄露和非法访问的报告：

==12345== Memcheck, a memory error detector
==12345== Copyright (C) 2002-2017, and GNU GPL'd, by Julian Seward et al.
==12345== Using Valgrind-3.15.0 and LibVEX; rerun with -h for info
==12345== Command: ./segfault_demo
==12345== 
==12345== Invalid write of size 1
==12345==    at 0x4005AA: trigger_crash (segfault_demo.c:9)
==12345==    by 0x4005CF: func_b (segfault_demo.c:15)
==12345==    by 0x4005DF: func_a (segfault_demo.c:19)
==12345==    by 0x400605: main (segfault_demo.c:25)
==12345==  Address 0x0 is not stack'd, malloc'd or (recently) free'd
==12345== 
==12345== Heap Summary:
==12345==    in use at exit: 20 bytes in 1 blocks
==12345==    total heap usage: 1 allocs, 0 frees, 20 bytes allocated
==12345== 
==12345== LEAK SUMMARY:
==12345==    definitely lost: 20 bytes in 1 blocks
==12345==    indirectly lost: 0 bytes in 0 blocks
==12345==      possibly lost: 0 bytes in 0 blocks
==12345==    still reachable: 0 bytes in 0 blocks
==12345==         suppressed: 0 bytes in 0 blocks

报告清晰指出：

  1. Invalid write of size 1：在第 9 行发生非法写入， 写入长度为 1 字节。
  2. Address 0x0 is not stack'd, malloc'd or (recently) free'd：访问的地址为 0x0， 它不属于栈、堆或已被释放的内存， 明显是空指针访问。
  3. LEAK SUMMARY：程序退出时有 20 字节的数据发生泄漏， 该内存块是在 main 函数中申请但未释放。 通过使用 Valgrind， 我们可以在程序尚未崩溃时就诊断并消灭隐藏的内存溢出问题。
