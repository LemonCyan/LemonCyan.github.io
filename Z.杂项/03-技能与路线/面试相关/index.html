项目难点 #

难点一 #

航电项目难点：Windows API 在 Linux 下的重构 背景： 原有的航电系统是基于 Windows 平台下的 VS2005 开发的，里面大量使用了 Windows 特有的 API。当我们要迁移到嵌入式 Linux（RK3568）时，这些 API 在 Linux 下根本不存在。

具体难点： 最棘手的是窗口消息机制和线程同步对象的差异。

举个例子，原来的代码用 WaitForSingleObject 和 CreateEvent 来实现线程间的事件通知。这个在 Windows 下是内核对象，可以跨进程使用，而且支持超时、多对象等待等复杂场景。但 Linux 下没有完全对等的东西——POSIX 的 pthread_cond_t 只能在同一进程内使用，而且使用方式完全不同，需要配合 pthread_mutex_t 一起用。

另一个例子是窗口刷新。原来用 InvalidateRect + WM_PAINT 消息来触发局部重绘，这是 Windows GDI 的标准做法。迁移到 Qt 之后，我需要理解 Qt 的 update() 和 paintEvent() 机制，然后把原来分散在各处的绘图逻辑重新组织。

我是怎么解决的：

抽象封装：我设计了一层跨平台的同步原语封装，用宏定义和条件编译来切换实现。在 Windows 下调用原生 API，在 Linux 下用 POSIX 线程库或 Qt 的 QWaitCondition。 行为对齐：针对一些细微的行为差异（比如超时精度、信号丢失等），我写了测试用例来验证两边的行为是否一致。 渐进式迁移：不是一次性重写全部代码，而是一个模块一个模块地迁移，每迁移一个就在两个平台上同时跑测试。 收获： 这个过程让我深刻理解了"跨平台"不仅仅是换个编译器那么简单，而是要理解两个操作系统在系统调用层面的设计哲学差异。

难点二 #

医疗 PCR 项目难点：大数据量实时绘图的性能瓶颈 背景： 96 孔 PCR 设备在扩增过程中，每个孔位每隔几秒钟采集一次荧光数据，整个流程下来每个孔可能有上千个数据点。用户希望在界面上实时看到所有 96 条曲线的变化。

具体难点： 最开始我用的是 Qt 自带的 QChart。当数据量小的时候没问题，但当每条曲线有 1000+ 个点、同时显示 96 条曲线的时候，界面直接卡死了——刷新率掉到了个位数，甚至拖动窗口都会卡顿。

用 profiler 分析后发现，QChart 每次 update() 都会重绘所有数据点，而且它的抗锯齿和样式计算开销很大。96 条曲线 × 1000 个点 = 接近 10 万个图形元素，每帧都重新计算一遍，CPU 根本扛不住。

我是怎么解决的：

换用 Qwt：Qwt 是一个专门做科学绘图的库，对大数据量绘制做了优化。它支持"数据抽稀"——当缩放级别较小时，它会自动跳过一些点，只绘制对视觉效果有意义的点。 分层绘制：我把曲线分成"历史数据层"和"实时数据层"。历史数据画一次就缓存成位图，只有实时新增的那几个点才增量绘制。 延迟刷新：不是每来一个数据点就刷新一次，而是攒够一批（比如 10 个点或者 500ms）再统一刷新。 异步处理：数据接收和解析放在子线程，主线程只负责拿到处理好的数据进行绘制，避免主线程被 IO 阻塞。 效果： 优化后，帧率从个位数提升到 30fps 以上，界面操作完全流畅了。这个优化方案后来也被复用到了其他需要大量数据可视化的项目里。

收获： 这个项目让我意识到，选择正确的库比硬写代码重要得多。而且做性能优化一定要先 profiler，找到真正的瓶颈，而不是凭直觉猜测。

其他问题 #

  1. 你是如何保证多线程程序的稳定性的？ 回答：

多线程稳定性我主要从三个层面来保证：

第一是设计层面——尽量减少共享状态。比如在 PCR 项目里，我用的是"生产者-消费者"模型，数据采集线程往队列里放数据，绘图线程从队列里取数据，通过无锁队列或者带锁的环形缓冲区来隔离。这样两个线程之间的交互点就那一个队列，比较容易控制。

第二是编码层面——对于必须共享的资源，我会严格遵循 RAII 原则，用 QMutexLocker 或者 C++11 的 std::lock_guard 来管理锁，避免忘记解锁或者异常导致死锁。另外我会特别注意锁的粒度，尽量缩小临界区的范围。

第三是测试层面——多线程的 bug 往往难以复现，所以我会写一些压力测试，让程序在高并发、高负载下跑很长时间，观察是否有内存泄漏、死锁或者数据错乱。在航电项目里，我们有专门的老化测试环节，系统要连续跑 72 小时以上不能出问题。

  1. 你提到了卡尔曼滤波，能简单解释一下它的原理和你是怎么用的吗？ 回答：

卡尔曼滤波本质上是一个递归的最优估计算法，它的核心思想是：用上一时刻的预测值和当前时刻的观测值，按照一定的权重进行融合，得到当前时刻的最优估计。

在 PCR 项目里，我用它来处理荧光信号的噪声。采集回来的原始数据有高频噪点，如果直接画曲线会很毛糙。卡尔曼滤波的好处是它能根据信号的变化趋势来动态调整平滑程度——当信号变化剧烈时，它更相信观测值；当信号平稳时，它更相信预测值。

具体实现上，我先在 Matlab 里调参数（过程噪声 Q 和观测噪声 R），找到一组效果比较好的值，然后把算法移植到 C++ 里。最终的效果是曲线平滑了，但关键的拐点（比如扩增曲线的 Ct 值）没有被滤掉。

  1. 你在项目中是如何进行代码版本管理和团队协作的？ 回答：

我主要用 Git 做版本管理。在航电项目里，我们团队用的是 GitLab，采用的是 feature branch + merge request 的工作流：每个功能点拉一个分支开发，开发完提 MR，经过 code review 之后再合并到主分支。

对于一些关键的发布节点，我们会打 tag，并且在发布前做一次完整的回归测试。

在医疗项目里，因为团队比较小，我更多是自己建立了一套规范——每天下班前提交代码，提交信息写清楚这次改了什么，有意义的里程碑打 tag。我还会定期把代码备份到 NAS 上，防止意外丢失。

  1. 你离开上一家公司的原因是什么？ 回答：

坦诚地说，主要是职业发展方向的考虑。

在上一家公司，我负责的航电系统已经基本完成了迁移和验证工作，后续更多是维护和小修小补。我希望能继续接触一些新的挑战，比如更复杂的嵌入式系统、新的行业场景，或者更深入的技术方向。

另外，我也想找一个技术氛围更浓厚的环境，能跟更多志同道合的工程师一起交流和成长。

  1. 你对加班怎么看？ 回答：

我觉得加班分两种情况：

一种是项目冲刺期的阶段性加班，比如产品要发布、要交付客户，这时候加班我觉得是正常的，我之前也经历过不少这种情况，PCR 设备在做医疗器械认证之前，我们连续加了两个月的班。

另一种是常态化的加班，我觉得这可能是团队管理或者需求规划有问题。如果长期这样，效率反而会下降，人也容易倦怠。

我的态度是：项目需要的时候，我可以冲一把；但同时我也会关注效率，看看有没有办法通过优化流程、减少返工来避免不必要的加班。

  1. 你的职业规划是什么？ 回答：

短期来说，我希望继续深耕嵌入式和上位机开发这个领域，把技术做更扎实。我现在对 Qt 和 Linux 应用层开发比较熟，但在驱动层、内核层的经验还比较浅，如果有机会我想往下探一探。

中期来说，我对无人系统、机器人这些方向比较感兴趣。我已经开始学习 ROS2 的基础架构，觉得这个方向跟我现有的嵌入式经验有很多结合点。

长期来说，我希望能成为一个能独立负责系统级设计的工程师——不只是写某个模块的代码，而是能从整体架构上去思考问题，把软硬件、协议、上位机这些都串起来。

面试官：刘璐华是吧？请坐。我是这边的技术负责人张工，今天主要跟你聊聊技术方面的情况。先简单做个自我介绍吧。

刘璐华：张工好。我叫刘璐华，做嵌入式和上位机开发有 8 年了。主要的技术栈是 Linux、Qt 和 C++。

我之前做过三个比较大的项目：航电系统的跨平台迁移、PCR 核酸扩增仪、还有工业污染源监测设备。简单说就是——航电那个是把老的 Windows 系统搬到嵌入式 Linux 上；PCR 是做医疗检测设备的上位机，涉及温控、相机采集、数据分析；工业检测那个是做烟气、水质、粉尘的在线监测，要对接环保局的数据上报。

我觉得自己比较擅长的是把一整条链路打通，从底层协议到上位机界面，再到数据上云，这种"端到端"的活儿我比较有经验。

技术深挖 面试官：嗯，看你简历上说航电系统迁移是从 VS2005 迁移到 Linux，这个具体是怎么做的？遇到过什么坑？

刘璐华：最大的坑是 Windows API 在 Linux 下没有对等的实现。

举个例子，原来用 WaitForSingleObject 和 CreateEvent 做线程同步，这在 Windows 下是内核对象，支持跨进程、超时等待。Linux 下没有直接对应的东西，POSIX 的条件变量用法完全不一样，要配合 mutex 一起用，而且只能进程内用。

我的做法是抽象了一层封装，用宏定义和条件编译来切换实现。Windows 下调原生 API，Linux 下用 Qt 的 QWaitCondition 或者 POSIX 线程库。另外还写了测试用例来验证两边的行为是否一致，比如超时精度、信号会不会丢失这些。

面试官：那窗口那部分呢？Windows GDI 和 Qt 的绑定差别也挺大的。

刘璐华：对，原来用 InvalidateRect 加 WM_PAINT 消息来做局部刷新，这是 GDI 的标准做法。迁移到 Qt 之后，我需要用 update() 和 paintEvent() 来替代。而且原来的绘图代码比较分散，我花了不少时间把它们重新组织，抽成统一的绑定接口。

最后做到的效果是，同一套业务代码可以在 Windows 模拟器和 Linux 真机上跑，只是底层的渲染实现不一样。

多线程与性能 面试官：你在 PCR 项目里做过大数据量的实时绑定，是怎么优化的？

刘璐华：一开始用的是 Qt 自带的 QChart，96 条曲线、每条上千个点，画起来直接卡死。用 profiler 看了一下，发现 QChart 每次刷新都会重新计算所有点的位置和抗锯齿，10 万个图形元素，CPU 根本扛不住。

后来换成了 Qwt，它对大数据量做了优化，支持数据抽稀。另外我还做了几个优化：一是分层绑定，历史数据画一次就缓存成位图，只有新增的点才增量绘制；二是延迟刷新，攒够一批数据再统一刷新；三是把数据接收放在子线程，主线程只负责绑定。

优化完之后帧率从个位数到了 30fps 以上，操作很流畅。

面试官：多线程这块你是怎么保证稳定性的？

刘璐华：三个层面。

第一是设计上减少共享状态，能用队列隔离的就用队列，生产者-消费者模型。

第二是编码上严格用 RAII 管理锁，QMutexLocker 或者 std::lock_guard，不手动解锁，避免忘了或者异常导致死锁。

第三是测试上做压力测试和老化测试。航电那个项目要求系统连续跑 72 小时不能崩，这种测试能暴露很多隐藏的并发问题。

协议与通信 面试官：你简历上写了熟悉 ARINC 协议，这个能展开说说吗？

刘璐华：ARINC 是航空领域的一套通信标准。我主要用过 ARINC 825、429 和 422。

825 本质上是基于 CAN 的上层协议，定义了消息格式和节点寻址方式。429 是一种单向广播的串行协议，用两根线传输，速率有高速和低速两种。422 跟 RS-485 有点像，是差分信号的串口。

在航电项目里，我做了一个协议聚合中间件，把这几种协议的数据统一接入、解析、模拟。还做了负载测试，在满负载情况下观察丢帧率。

软技能 面试官：你在团队里一般是什么角色？跟其他人怎么协作？

刘璐华：技术上我一般是模块负责人的角色，负责某个子系统的设计和开发。比如在 PCR 项目里，上位机这一块基本是我主导的。

协作的话，我习惯先把接口定义清楚，写成文档，然后大家按接口开发。有问题及时沟通，不要憋到最后才发现对不上。版本管理用 Git，feature branch 工作流，code review 之后再合并。

面试官：你离开上一家公司的原因是什么？

刘璐华：主要是职业发展的考虑。航电那个项目已经基本完成了迁移和验证，后续更多是维护。我希望能接触一些新的挑战，学到更多东西。另外也想找一个技术氛围更浓厚的环境，跟更多工程师交流。

职业规划 面试官：那你对未来有什么规划？

刘璐华：短期我想继续深耕嵌入式和上位机这块，把技术做更扎实。我现在对应用层比较熟，驱动和内核层还比较浅，有机会想往下探一探。

中期对无人系统和机器人比较感兴趣，我已经在学 ROS2 的基础架构，觉得跟我现有的经验有很多结合点。

长期希望能做系统级的设计，不只是写模块代码，而是能从整体架构上思考问题。

反问环节 面试官：好的，你有什么想问我的吗？

刘璐华：有几个问题想了解一下。第一，这个岗位日常主要负责的产品线是什么，目前处于什么阶段？第二，团队的技术栈是怎样的，跟我之前做的有什么差异？第三，公司对新人有什么培养计划或者技术成长路径？

面试官：好，这些问题我来回答一下……（面试官回答）

结束 面试官：今天就先聊到这里，后续有消息 HR 会联系你。

刘璐华：好的，谢谢张工。期待后续的消息。

备注：以上对话模拟了一个约 20-30 分钟的技术面试，涵盖了自我介绍、项目深挖、技术细节、软技能和反问环节。实际面试可能会根据面试官的兴趣点有所侧重。

面试流程二 #

开场 面试官：刘璐华，你好。我是研发部的技术总监李工，一面张工那边反馈不错，今天我们再深入聊聊。先不用重新自我介绍了，我看过你的简历和一面记录。我比较好奇的是，你在这 8 年里，觉得自己成长最大的一段时间是什么时候？

刘璐华：李总好。成长最大的应该是 2017 到 2019 年做工业检测设备那段时间。

那是我真正意义上第一次"从 0 到 1"做一个产品。之前在学校和刚工作那会儿，更多是改别人的代码、做一些模块级的开发。但那个项目是从平台搭建、协议设计、业务逻辑、现场调试一路做下来的。

而且那个项目让我第一次"吃过现场的苦"。实验室里跑得好好的程序，到了工厂就出问题——电磁干扰、电源波动、传感器漂移，什么幺蛾子都有。那段时间我学会了一个道理：写代码只是工程的一半，另一半是跟现实世界打交道。

架构与设计 面试官：嗯，这个体会很实在。那我问一个架构层面的问题：如果让你从头设计一个嵌入式监测设备的软件系统，你会怎么考虑？

刘璐华：我会从几个维度来考虑：

第一是分层。我一般会分成：硬件抽象层、业务逻辑层、UI 层、通信层。层与层之间通过接口隔离，尽量减少耦合。这样做的好处是，如果以后换硬件或者换通信方式，只需要改对应的层，不用动业务代码。

第二是数据流。嵌入式系统往往是"数据驱动"的——传感器采集数据，处理后显示或上传。我会画出数据从哪里来、到哪里去，在哪里做缓存、在哪里做解析，这条链路要清晰。

第三是可测试性。我会在设计时就考虑怎么做单元测试、怎么做模拟数据注入。比如通信层我会抽象成接口，真实运行时走串口或网口，测试时可以走一个 mock 对象。

第四是容错。嵌入式设备可能 7×24 小时运行，必须考虑断电恢复、通信超时、传感器失联这些异常情况。我一般会设计一个状态机来管理设备状态，每个状态下允许什么操作、出错了怎么回退，都要想清楚。

面试官：你提到状态机，能举个具体的例子吗？

刘璐华：比如 PCR 设备，它的状态可能有：待机 → 预热 → 扩增进行中 → 数据分析 → 完成 → 待机。每个状态转移都有触发条件，比如"预热"到"扩增进行中"的条件是温度达到设定值。

如果预热过程中温度一直上不去，可能是 TEC 坏了，这时候要跳到"故障"状态，弹出报警提示。如果用户点了"紧急停止"，任何状态下都要能跳回待机并断开加热。

这些逻辑如果不用状态机，而是用一堆 if-else 来写，代码会非常混乱，后期维护也很痛苦。

技术深度 面试官：你简历里提到多线程和多协议，我想深挖一下。你在航电项目里做的协议聚合中间件，能画个简图讲讲它的架构吗？

刘璐华：好的。（假设在白板或纸上画）

┌─────────────────────────────────────┐
│           应用层（业务逻辑）          │
└─────────────────────────────────────┘
                    ↑
                    │ 统一数据结构
┌─────────────────────────────────────┐
│           协议解析/封装层             │
│  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐ │
│  │ 825 │  │ 429 │  │ 422 │  │ CAN │ │
│  └─────┘  └─────┘  └─────┘  └─────┘ │
└─────────────────────────────────────┘
                    ↑
                    │ 原始字节流
┌─────────────────────────────────────┐
│           驱动/IO 层                 │
│  ┌─────────┐  ┌─────────┐  ┌──────┐ │
│  │ CAN 驱动 │ │ 串口驱动 │  │ 网口  │ │
│  └─────────┘  └─────────┘  └──────┘ │
└─────────────────────────────────────┘

刘璐华（继续）：关键点有几个：

驱动层是阻塞接收的，每个端口对应一个接收线程，收到数据就往上抛。 解析层根据数据的来源和帧格式，自动识别是哪种协议，调用对应的解析器。解析完的数据统一成一种内部结构。 应用层只看到统一的数据结构，不关心底层是 CAN 还是串口。 另外还有一个模拟器模块，可以生成各种协议的模拟数据，用于测试和老化。 面试官：如果两个不同的协议同时来数据，你怎么处理冲突？

刘璐华：不会冲突，因为每个端口是独立的线程在收。收到数据后放到一个线程安全的队列里，有一个分发线程再从队列里取出来处理。所以是异步解耦的，不会阻塞。

如果是指业务逻辑上需要"合并"多个来源的数据，比如 ARINC 429 的姿态数据和 CAN 的发动机数据需要同时显示，那我会用时间戳对齐——每条数据带着采集时间戳，显示模块按时间戳去匹配最近的数据。

故障排查 面试官：你在现场调试时遇到过最棘手的 bug 是什么？最后怎么解决的？

刘璐华：印象最深的是在做 CEMS 烟气监测设备的时候，现场有一台设备隔几天就会卡死一次，但在实验室里怎么都复现不出来。

后来我去现场蹲了三天，带着调试工具和日志分析脚本。最后发现问题出在看门狗和主程序之间的时序冲突——我们用的是硬件看门狗，程序定时喂狗。但在某些极端情况下，比如串口缓冲区被大量数据填满导致主线程阻塞，喂狗动作会延迟，然后看门狗就把系统重启了。

但这不是卡死，是重启。后来再仔细看日志，发现在重启前有几秒钟UI 更新变得极慢，而且是发生在某个特定时间段。

一查，那个时间段刚好是外部数采仪大批量上传数据的时候。串口缓冲区被撑满了，读取线程一直在 busy-wait，把 CPU 占满了，主线程分不到时间片。

解决方案：一是把串口接收改成非阻塞+轮询，限制每次最多读多少字节；二是加大缓冲区；三是在读取线程里加了主动 yield，不让它一直霸占 CPU。

这个 bug 让我学会了一件事：现场问题往往是多个因素叠加的结果，不能只看代码逻辑，还要看运行环境的资源争用。

团队与管理 面试官：如果让你带一个 3-5 人的小团队，你会怎么分工和管理？

刘璐华：我会根据模块边界来分工，而不是按"你写前端我写后端"这种横向分。

比如一个设备上位机项目，我可能会分成：

A 负责通信模块和协议解析 B 负责业务逻辑和状态机 C 负责 UI 和数据展示 我自己负责整体架构、跨模块接口定义、以及处理一些难点问题 分工定好之后，接口要先定义清楚，写成文档或者代码里的纯虚类，然后各自开发，定期集成。

管理上我不太喜欢天天开会，但会有几个固定的同步点：

每周一简短站会，同步进度和阻塞点 每两周做一次代码走查，互相 review 上线前做一次完整的集成测试 另外我会鼓励大家先试后问——遇到问题先自己调查 15-30 分钟，实在搞不定再讨论。这样讨论的时候效率更高，因为大家已经知道问题的边界在哪里了。

薪资与期望 面试官：最后聊聊现实的问题。你现在的薪资是多少？期望是多少？

刘璐华：我目前的月薪是 XX K（可根据实际情况调整），期望涨幅在 20%-30% 左右。主要是考虑到新工作可能会有更大的技术挑战和成长空间，我愿意为此付出更多的精力。

当然，薪资只是一个方面，我更看重的是能不能做有技术含量的事情、团队氛围好不好、有没有成长空间。如果这几点都符合，具体数字可以商量。

反问 面试官：还有什么想问的吗？

刘璐华：第一，我想了解一下这个岗位接下来一年的主要目标是什么，最大的挑战在哪里？第二，团队现在的技术债务情况怎么样，会不会有很多历史包袱？第三，公司对远程办公的态度是怎样的？
