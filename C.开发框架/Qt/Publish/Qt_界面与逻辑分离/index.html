Qt_界面与逻辑分离

QT界面与逻辑分离 #

Qt 开发的一个核心理念：UI 归 UI，逻辑归逻辑，别混在一起写。

这么做有几个实打实的好处：

  • 互不干扰：改界面不怕把业务搞崩，反过来也一样。
  • 并行开发：UI 和逻辑能分头开发，效率翻倍。
  • 易于测试：业务逻辑可以单独写单元测试，不用依赖界面组件。
  • 复用性强：界面组件能复用，换肤也容易。

基本架构 #

一个典型的程序一般包含两个核心模块：

模块 职责
用户界面模块（UI） 接收用户输入、展示数据
业务逻辑模块 根据用户需求处理数据

这两块必须解耦，不能让界面代码直接调业务逻辑，也不能让业务逻辑去操作界面控件。

设计原则 #

强内聚、弱耦合，这六个字要刻脑子里：

  • 单一职责：每个模块只干一件事。
  • 模块组成：模块内部的子模块只为整体的单一功能服务。
  • 交互规则：模块之间通过约定好的接口交互。
  • 单向依赖：A 依赖 B 可以，但 A 和 B 互相依赖就是设计问题。

循环依赖是糟糕设计的典型标志之一，必须避免。

什么是接口？ #

  • 广义上：接口是模块之间的一种"契约"。
  • C++ 中：通常是只包含公开纯虚函数的抽象类。
  • 实现原则：必须有模块实现对应的接口。

Qt 开发的三种模式 #

根据项目需求，常见的开发模式有三种：

1. 纯代码模式 #

用 QWidget 纯手写界面，QSS 做样式，C++ 写逻辑。

  • 优点：灵活，啥都能控制。
  • 缺点：代码量大，复杂界面写起来累。

2. Qt Designer 模式 #

拖控件画界面（类似 MFC/WinForm），生成 .ui 文件，QSS 美化，C++ 写逻辑。

  • 现状：这是现在大部分公司的选择，开发效率高，上手也快。

3. QML 混合模式 #

QML 做 UI、JavaScript 写交互、C++ 写后台，三种语言混合。

  • 适用场景：适合做现代化、动效多的界面（比如移动端或嵌入式大屏），现在用的越来越多。

分离的核心方法 #

1. 信号与槽 (Signals & Slots) #

Qt 的招牌机制，天然适合做解耦。

界面只管发信号：用户点了按钮、输入了文字，逻辑层连上槽函数处理。两边不直接调用，通过信号槽沟通。

cpp
// 界面只管发信号
emit calculateClicked(expression);

// 逻辑层或者控制层连接
connect(ui, &CalcUI::calculateClicked, this, &CalcLogic::doCalculate);

这种机制还天然支持跨线程，做异步操作极其方便。

2. MVC 与 MVVM 模式 #

MVC (Model-View-Controller) 是经典的分层架构，Qt 官方也非常推荐。

角色 职责 Qt 中的体现
Model 数据和业务逻辑 QAbstractListModel, QAbstractTableModel
View 界面展示 QListView, QTableView
Controller 协调 M 和 V 信号槽连接 / 独立的控制器类
关于 Controller 的补充

在 Qt 简单应用中，Controller 往往是不明显的。我们经通过信号与槽直接连接 View 和 Model，或者在 View 的逻辑里简单处理一下。 但在复杂业务中，建议显式定义一个 Controller 类（或者叫 Presenter），专门负责处理 View 的信号，调用 Model 的接口，再把结果反馈给 View。这样 View 就彻底成了“哑巴组件”，只负责显示，不含任何逻辑。

MVVM (Model-View-ViewModel)

MVVM 可以看作 MVC 的变种，特别适合数据驱动的 UI。

  • ViewModel：作为 View 的替身，持有数据状态。View 和 ViewModel 之间通过双向绑定（Qt WebAssembly 或 QML 中很常用）自动同步。
  • 在 QML 开发中，MVVM 是主流模式。

MVC 代码简例：

cpp
// Model：提供数据，不知道 View 的存在
class MyModel : public QAbstractListModel {
    // ... 实现 rowCount, data 等标准接口
};

// View：展示界面，不仅限于 QListView
class MyView : public QWidget {
    // ...
    void setModel(QAbstractItemModel *model) {
        m_listView->setModel(model);
    }
signals:
    // View 并不直接改数据，而是把用户操作发出去
    void itemClicked(const QModelIndex &index);
};

// Controller：负责组装
class MyController : public QObject {
    MyModel *m_model;
    MyView *m_view;
public:
    MyController(MyModel *m, MyView *v) : m_model(m), m_view(v) {
        // 连接 View 的操作到内部逻辑
        connect(m_view, &MyView::itemClicked, this, &MyController::handleItemClick);
    }
};

3. 接口抽象 #

给业务逻辑定一个纯虚接口，界面只依赖接口，不管具体实现。

cpp
// 接口定义
class ICalculator {
public:
    virtual bool expression(const QString& exp) = 0;
    virtual QString result() = 0;
    virtual ~ICalculator() = default;
};

// 界面类只认接口
class CalcUI {
    ICalculator* m_logic;
public:
    void setLogic(ICalculator* logic) { m_logic = logic; }
    void onButtonClick() {
        // 界面不知道逻辑是谁实现的，只知道它能算 expression
        m_logic->expression("1+1");
    }
};

好处：哪天你想换个算法库，或者把本地计算改成云端计算，界面代码一行都不用动。

4. 继承封装 #

最基础的做法：自定义窗口类继承 QWidget，界面初始化封装成 initUI() 方法，业务逻辑放另一个类。

cpp
class MyWindow : public QWidget {
public:
    MyWindow(QWidget* parent = nullptr) : QWidget(parent) {
        initUI();
    }
private:
    void initUI();  // 只管界面布局
};

5. QSS 样式分离 #

样式代码（颜色、字体、边框等）写到单独的 .qss 文件，程序运行时加载。

cpp
QFile file(":/styles/dark.qss");
file.open(QFile::ReadOnly);
qApp->setStyleSheet(file.readAll());

换肤只要换加载的文件，代码不用动。这和 Web 开发里的 CSS 是一样的道理。

完整示例：四层架构的计算器 #

把上面的方法组合起来，一个典型的生产级架构：

graph TD
    UI[QCalculatorUI 界面层] -->|依赖| I[ICalculator 接口层]
    L[QCalculatorDec 逻辑层] -->|实现| I
    C[QCalculator 组装层/Controller] -->|持有| UI
    C -->|持有| L

1. 接口层 #

定义"契约"，不包含任何实现。

cpp
class ICalculator {
public:
    virtual bool expression(const QString& exp) = 0;
    virtual QString result() = 0;
};

2. 逻辑层 #

实现具体的业务，完全不引用任何 UI 相关的库（如 UIKit/QtWidgets），只依赖 QtCore 或标准库。

cpp
class QCalculatorDec : public ICalculator {
    QString m_result;
public:
    bool expression(const QString& exp) override {
        // 解析表达式、计算...
        m_result = "42"; 
        return true;
    }
    QString result() override { return m_result; }
};

3. 界面层 #

只负责画图和响应用户输入，通过接口调用功能。

cpp
class QCalculatorUI : public QWidget {
    ICalculator* m_calc; // 只依赖接口
public:
    void setCalculator(ICalculator* calc) { m_calc = calc; }
    
    void onCalculate() {
        // 只要接口没变，这里永远安全
        if (m_calc->expression(m_input->text())) {
            m_output->setText(m_calc->result());
        }
    }
};

4. 组装层 (App/Main/Controller) #

负责把零散的部件拼装在一起。

cpp
class QCalculator {
protected:
    QCalculatorUI* m_ui;
    QCalculatorDec m_cal;  // 具体的逻辑实现
public:
    QCalculator() {
        m_ui = new QCalculatorUI;
        // 把逻辑注入给 UI
        m_ui->setCalculator(&m_cal); 
    }
    void show() { m_ui->show(); }
    ~QCalculator() { delete m_ui; }
};

小结 #

  • 接口是契约：模块交互走接口，别走后门。
  • 单向依赖：UI 依赖逻辑接口，逻辑不依赖 UI。
  • 强内聚、弱耦合：这是万金油原则。

刚开始写小 Demo 可能觉得这么拆很麻烦，没必要。但等代码超过几千行，或者需求开始频繁变更时（比如老板今天说要换个皮肤，明天说算法要升级），你会感谢当初做了分离的自己。
