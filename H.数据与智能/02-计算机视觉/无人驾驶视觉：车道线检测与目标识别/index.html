本篇只回答一个问题：一张相机图片进来，我们从里面提取什么、怎么提取。上半场是传统法——颜色阈值、区域掩码、Canny 边缘、霍夫变换，最后拟合成车道线；下半场是深度学习法——YOLOv3 检测目标框，再和激光雷达点云对齐。本篇不讲针孔模型、相机内参、旋转平移矩阵、点云到像素的投影公式，那些属于同批的《激光雷达与相机融合：从针孔模型到点云投影》，两篇衔接点在第二十一章：本篇假设你已经能把一个 3D 点投到图像平面上，只关心投完之后落在哪个框里。参数一律照录原文数值，原文没给的地方直接标注「原文未给出，需按实际图像调整」，不做补全。

一、无人驾驶视觉要解决的两个任务：找车道、认目标 #

前向相机拍回来的画面里，对我们有用的信息分两类。一类是结构信息：车道在哪里，车该往哪走。另一类是语义信息：前面那坨东西是车、是人、还是路牌。两类信息处理路径完全不同。

找车道用的是几何约束。车道线在图像里表现为一段细长的、亮度和颜色与路面有明显差异的连续区域。它不需要我们认识「什么是车道线」，只需要我们假设它是边缘、是直线、并且集中在画面下方的一个梯形区域里。这三条假设撑起了整条传统流水线。

认目标用的是模式识别。车、人、自行车的形状没有统一公式，只有样本。所以走的是数据驱动的路子，用神经网络在标注数据上学出来。

任务 输出 方法族 输入假设
找车道 左右车道线的像素坐标 颜色阈值、Canny、霍夫变换、拟合 车道线是直线、位于画面下方、与路面有对比度
认目标 每个目标的 2D 边界框 + 类别 + 置信度 YOLOv3 等单阶段检测器 有预训练权重、类别属于 COCO 的 80 类

两条流水线都挂在 OpenCV 上。Python 侧的安装方式，原文给的是清华镜像：

二、颜色选择：为什么要换到 HLS 空间 #

彩色相机的原始数据是三个通道。原文先把这事讲清楚：一张 RGB 图像按三基色红（R）、绿（G）、蓝（B）分成三个通道，每个通道独立，单个通道的像素值范围是 [0, 255]。值为 0 时该通道贡献为零，表现为黑；值为 255 时表现为该通道的纯色。所以 [0,0,0] 是黑，[255,255,255] 是白，其余组合依此类推。

最朴素的车道线提取就是直接在这个空间里卡阈值。原文的第一个例子：把 R、G、B 三个通道分别与 200 比较，任一通道低于 200 就把这个像素置黑，保留下来的就是接近白色的像素。

python
# -*- coding: utf-8 -*-
import matplotlib.pyplot as plt
import matplotlib.image as mpimg
import numpy as np

image = mpimg.imread('test.jpg')
print('This image is: ', type(image), 'with dimensions:', image.shape)

ysize = image.shape[0]
xsize = image.shape[1]
# 一定用 copy，直接用 = 会改到原图
color_select = np.copy(image)

red_threshold = 200
green_threshold = 200
blue_threshold = 200
rgb_threshold = [red_threshold, green_threshold, blue_threshold]

# 任一通道低于对应阈值 → 该像素判为背景，置黑
thresholds = (image[:, :, 0] < rgb_threshold[0]) \
           | (image[:, :, 1] < rgb_threshold[1]) \
           | (image[:, :, 2] < rgb_threshold[2])
color_select[thresholds] = [0, 0, 0]

plt.imshow(color_select)
plt.show()
# mpimg.imsave("test-after.png", color_select)

三个阈值都是 200，取自原文。注意这里的逻辑是「与」关系：三个通道有一个不达标，整个像素就被丢掉。这对应的是「接近白」的语义，因为白色要求三个通道同时高。

这个做法能跑通，但有个明显问题。RGB 三个通道高度耦合：亮度一变，三个值同时变。同一段白色车道线，晴天中午是 [240,240,240] 这一档，进了隧道阴影就掉到 [130,130,135] 这一档，阈值 200 直接全部失效。而且 R、G、B 三个量都在描述「有多少光」，没有哪个量单独描述「这是白色还是黄色」。

HLS 空间把这三件事解耦了。

空间 三个分量 各分量含义 亮度变化时的影响
RGB R, G, B 三个基色通道的强度 三个分量同时大幅变化，阈值全部漂移
HLS H, S, L 色相、饱和度、明度 L 单独承载亮度，H、S 基本稳定

H：色相（Hue），描述色相角，决定「是白、是黄还是蓝」。S：饱和度（Saturation），描述颜色纯度，越接近灰越低。L：明度（Lightness），描述亮暗。

车道线主要就两种颜色：白和黄。白色在 HLS 里的特征是 S 低、L 高（几乎无色，但很亮）。黄色在 HLS 里的特征是 H 落在黄色段、S 较高。这两条判据跟光照强弱的关联比 RGB 弱得多，因为我们把「亮」这件事完全甩给了 L 通道，而判颜色的时候只需要看 H 和 S。

这里要钉一个版本问题，原文没写，但它是最容易出错的一处：

OpenCV 的 HLS 中 H 的范围是 [0, 180]，不是 [0, 360]。 因为 OpenCV 用 uint8 存 H，把 360 度压缩了一半。所以黄色的 H 在标准色轮上是 30 度左右，在 OpenCV 里写的是 15 到 30 这一带。照抄别的资料里 0 到 360 的数值，阈值会全错。

转换函数是 cv2.cvtColor(img, cv2.COLOR_RGB2HLS)。原文用的通道顺序是 RGB——因为 mpimg.imread 读出来就是 RGB。如果图像是用 cv2.imread 读的，那就是 BGR，要换成 cv2.COLOR_BGR2HLS。这个错位是无声的，不会报错，只会让你的颜色筛选结果看起来莫名其妙。

三、颜色阈值的选取方法 #

阈值不是拍脑袋定的，原文的做法是逐像素打印。取图像上一个已知是车道线的点，比如 (x, y)，把它的三个通道值打出来：

python
import cv2
import numpy as np

img = cv2.imread('test.jpg')                     # BGR
hls = cv2.cvtColor(img, cv2.COLOR_BGR2HLS)       # H: 0~180, L/S: 0~255

x, y = 500, 400                                  # 一个你肉眼确认在车道线上的像素
print('pixel HLS:', hls[y, x])                   # 顺序是 [H, L, S]，注意不是 HSL

这里有个容易踩的坑：cv2.cvtColor 的 HLS 输出，通道顺序是 H、L、S，不是 H、L、S 之外的任何别的东西，但常有人按 HSL 写代码然后去取 [2] 当 L 用。OpenCV 把 L 放在索引 1，S 放在索引 2。取错索引，得到的阈值组合不会有任何意义。

取好一组样本点之后，把它们的值合起来圈出一个区间。判据可以这样组织：

  1. 白色：S 低（接近 0），L 高（接近 255）。三个通道都要卡住——只卡 L 会把所有亮的东西都留下，只卡 S 会把所有灰色的东西都留下。
  2. 黄色：H 落在黄色带，S 中等以上，L 不能太低（压暗的黄色和棕色很难区分）。

批量筛选用的是 cv2.inRange：

python
# 判据形式：lower, upper 各是一个三元组，返回同尺寸的二值掩码
mask = cv2.inRange(img, lower, upper)

cv2.inRange 的行为是逐通道独立判定，再对三个通道的结果做「与」：只有三个通道都落在 [lower, upper] 内，输出像素才为 255，否则为 0。这正好对应上文的「白色要三个通道同时满足」。

白色和黄色分成两组阈值各做一次 inRange，然后按位或合并：

python
white_mask = cv2.inRange(hls, (0, 200, 0), (255, 255, 40))     # 阈值示意，需按实际图像调整
yellow_mask = cv2.inRange(hls, (15, 30, 115), (35, 204, 255))   # 阈值示意，需按实际图像调整
color_mask = cv2.bitwise_or(white_mask, yellow_mask)

上面对应的 (0, 200, 0)-(255, 255, 40) 与 (15, 30, 115)-(35, 204, 255) 这两组数是 OpenCV 社区里流传较广的起步值，原文未给出，需按实际图像调整。判断一个阈值合不合理，方法是把掩码二值图和原图并排看：车道线丢了就是太紧，路面和树影进来了就是太松。

四、代码实现与参数调试 #

把上文的逻辑串成一个函数，方便反复调参：

python
import cv2
import numpy as np

def color_select(img_bgr,
                 white_lo=(0, 200, 0),    white_hi=(255, 255, 40),
                 yellow_lo=(15, 30, 115), yellow_hi=(35, 204, 255)):
    hls = cv2.cvtColor(img_bgr, cv2.COLOR_BGR2HLS)
    w = cv2.inRange(hls, np.array(white_lo), np.array(white_hi))
    y = cv2.inRange(hls, np.array(yellow_lo), np.array(yellow_hi))
    return cv2.bitwise_or(w, y)

img = cv2.imread('test.jpg')
mask = color_select(img)
out = cv2.bitwise_and(img, img, mask=mask)   # 只留掩码内的像素
cv2.imshow('mask', mask)
cv2.imshow('out', out)
cv2.waitKey(0)

cv2.bitwise_and(img, img, mask=mask) 这个写法要解释一下：两个输入都传 img，结果就是 img & img = img，真正起作用的是 mask 参数——掩码为 0 的位置结果被强制为 0。这是用掩码裁剪图像的标准写法。

调参有几个可操作的手法：

  • 先看掩码，不看彩色结果。 二值掩码只有黑白两色，问题一眼能看出来。彩色结果会骗人。
  • 一次只动一个通道。 先把 S 的上下界卡死，再单独调 L 的下界，最后调 H 的区间。三个一起动，你无法归因。
  • 用两张差别大的图交叉验证。 一张亮、一张暗，或一张白线、一张黄线。只在单张图上调出来的阈值，过拟合程度和深度学习模型一样严重。
  • 别把 S 的下界设成 0。 S 下界为 0 意味着「所有灰色物体都算白」，路面、护栏、天空全部进来。反之 S 上界设得太高，会把真实车道线里偏灰的部分漏掉。

原文在颜色选择这一步之后没有直接进 Canny，而是先做区域筛选。理由也清楚：颜色筛选只能去掉颜色不对的像素，去不掉「颜色对但位置不对」的像素——比如远处对向车道的白车、天上的白云、路边的白色标牌。所以下一步是把画面切成保留区和丢弃区。

五、区域筛选：把天空和无关区域裁掉 #

原文给出的前提假设很明确，直接引用：相机位于车辆正中，相机视角中心处于车辆正前方，当前车道为直线车道。这三条假设决定了感兴趣区域的形状——一个以画面下方为底、向上收窄的三角形或梯形。

图像坐标系的约定要钉死：原点 (x=0, y=0) 在左上角，y 轴向下。这是图像处理的默认约定，跟数学课本上的笛卡尔坐标系正好反着。原文在代码注释里特意提醒了这一点，因为所有顶点坐标都依赖于这个约定。地平线在画面中靠上，所以它的 y 值小；车头附近的画面靠下，y 值大。

原文的三角形区域三个顶点，数字照录：

text
left_bottom  = [0, 539]      # 三角区域的左下角
right_bottom = [900, 539]    # 三角区域的右下角
apex         = [475, 320]    # 三角区域的顶点

对照上面的图像尺寸 (540, 960, 3)（高 540、宽 960、三通道），这三组坐标是自洽的：底边 y=539 正好是最后一行，左右两端 x=0 和 x=900（没顶到 960，留了余量），顶点在 x=475、y=320，大致是画面中上部的中间偏左一点。

区域判定的思路不是「逐像素判断是否在多边形内」，而是把三条边都写成直线方程，然后做三次不等式比较。三点定三条线，用的是 np.polyfit：

python
# 参数 1 表示最高阶数为 1，即直线；返回 [a, b] 对应 y = a*x + b
fit_left   = np.polyfit((left_bottom[0],  apex[0]),        (left_bottom[1],  apex[1]),        1)
fit_right  = np.polyfit((right_bottom[0], apex[0]),        (right_bottom[1], apex[1]),        1)
fit_bottom = np.polyfit((left_bottom[0],  right_bottom[0]), (left_bottom[1],  right_bottom[1]), 1)

np.polyfit(x, y, 1) 的第三个参数是多项式阶数，传 1 得到一次拟合，返回的 [a, b] 就是 y = a*x + b 的系数。这里传的是两个端点，所以就是两点连线。

然后生成整幅图的坐标网格，逐像素比较：

python
XX, YY = np.meshgrid(np.arange(0, xsize), np.arange(0, ysize))
region_thresholds = (YY > (XX * fit_left[0]  + fit_left[1]))  & \
                    (YY > (XX * fit_right[0] + fit_right[1]))  & \
                    (YY < (XX * fit_bottom[0] + fit_bottom[1]))

np.meshgrid 的作用是把一维的 x 序列和一维的 y 序列展开成两个同形状的二维矩阵，XX[y][x] = x，YY[y][x] = y。这样后面整个不等式运算就是逐像素的向量化比较，不需要写双重 for 循环。

三个不等式的符号方向值得说一下。YY > 左侧直线 表示在左边那条线的下方（或右方）；YY > 右侧直线 表示在右边那条线的下方（或左方）；YY < 底边直线 表示在底边的上方。三个条件同时成立，落在这个三角形里。

最后把颜色筛选和区域筛选两件事合并成一次赋值：

python
color_thresholds = (image[:, :, 0] < rgb_threshold[0]) \
                 | (image[:, :, 1] < rgb_threshold[1]) \
                 | (image[:, :, 2] < rgb_threshold[2])
color_select[color_thresholds] = [0, 0, 0]

# 颜色达标（~color_thresholds 为真）且位于区域内 → 涂红
line_image[~color_thresholds & region_thresholds] = [255, 0, 0]

~color_thresholds 是对布尔数组按位取反，也就是「颜色筛选通过」的那部分。& 再把两边「与」起来。这一步的结果是把当前车道线的像素涂成红色，叠加在原图上显示。

完整代码照录原文（含上文已出的部分，保持可运行）：

python
# -*- coding: utf-8 -*-
import matplotlib.pyplot as plt
import matplotlib.image as mpimg
import numpy as np

image = mpimg.imread('test.jpg')
print('This image is: ', type(image), 'with dimensions:', image.shape)

ysize = image.shape[0]
xsize = image.shape[1]
color_select = np.copy(image)
line_image = np.copy(image)

red_threshold = 200
green_threshold = 200
blue_threshold = 200
rgb_threshold = [red_threshold, green_threshold, blue_threshold]

left_bottom = [0, 539]
right_bottom = [900, 539]
apex = [475, 320]

fit_left = np.polyfit((left_bottom[0], apex[0]), (left_bottom[1], apex[1]), 1)
fit_right = np.polyfit((right_bottom[0], apex[0]), (right_bottom[1], apex[1]), 1)
fit_bottom = np.polyfit((left_bottom[0], right_bottom[0]), (left_bottom[1], right_bottom[1]), 1)

color_thresholds = (image[:, :, 0] < rgb_threshold[0]) \
                 | (image[:, :, 1] < rgb_threshold[1]) \
                 | (image[:, :, 2] < rgb_threshold[2])
color_select[color_thresholds] = [0, 0, 0]

XX, YY = np.meshgrid(np.arange(0, xsize), np.arange(0, ysize))
region_thresholds = (YY > (XX * fit_left[0] + fit_left[1])) & \
                    (YY > (XX * fit_right[0] + fit_right[1])) & \
                    (YY < (XX * fit_bottom[0] + fit_bottom[1]))

line_image[~color_thresholds & region_thresholds] = [255, 0, 0]

plt.imshow(line_image)
plt.show()

这套手写三角形判定的做法，好处是不依赖 OpenCV，能用纯 NumPy 完成，坏处是顶点数一多就要写一堆 polyfit。真要上四边形或更复杂的形状，应该换 cv2.fillPoly。

六、多边形掩码的实现 #

cv2.fillPoly 的用法比手写直线方程干净：给一组顶点，它把多边形内部填成指定值，得到一个二值掩码，再和边缘图做按位与。

python
mask = np.zeros_like(edges)          # 与边缘图同尺寸的全零图
ignore_mask_color = 255

imshape = image.shape
# 顶点顺序：图像左下 → 左上 → 右上 → 右下，围成四边形
vertices = np.array([[(0, imshape[0]),
                      (450, 290),
                      (490, 290),
                      (imshape[1], imshape[0])]], dtype=np.int32)

cv2.fillPoly(mask, vertices, ignore_mask_color)
masked_edges = cv2.bitwise_and(edges, mask)

这里有三个格式细节，全都会导致报错或静默失效：

  1. vertices 是三维数组。 形状是 (1, N, 2)，最外层那一维是「多边形列表」。fillPoly 一次可以填多个多边形，所以顶点必须包一层。少包这一层，代码直接抛异常。
  2. dtype=np.int32 不能省。 OpenCV 的 C++ 接口要求点坐标是 32 位整数，传浮点数组会报类型错误。
  3. cv2.fillPoly 是原地写入。 它改的是第一个参数 mask，没有返回值赋给你。写成 mask = cv2.fillPoly(mask, ...) 会拿到 None，后面全崩。

原文的四边形顶点是 (0, 540) → (450, 290) → (490, 290) → (960, 540)，和上一节的三角形思路一致，只是把顶点从单点 apex 换成了两个点 (450, 290) 和 (490, 290)，横向留了 40 像素的顶边。原文还保留了一行被注释掉的备选写法：

python
# vertices = np.array([[(0,imshape[0]),(0, 0), (imshape[1], 0), (imshape[1],imshape[0])]], dtype=np.int32)

这四个点是画面四角，等于「不裁剪，全图保留」。调试时可以临时打开，用来确认问题出在区域筛选还是出在后面的边缘检测。

cv2.bitwise_and(edges, mask) 的作用是保留掩码内的边缘像素。edges 是单通道二值图，mask 也是单通道，逐位与之后多边形外的边缘全部变 0。

原文在这里还留了一句方法论的对照：前面在手写三角形筛选时用的是 polyfit 求三个直线方程，这次换成了 fillPoly，而 fillPoly 支持任意复杂的多边形，不限边数。工程上应该直接用 fillPoly，手写直线方程那段的价值在于让你理解「区域筛选本质上是一组不等式的与」。

fillPoly 不是这套流程里唯一有版本陷阱的轮廓类函数。如果你想改成「先找轮廓、再按轮廓填充 ROI」，用的是 cv2.findContours，它的返回值个数在 OpenCV 3 和 4 之间变过：

版本 cv2.findContours 返回 正确写法
OpenCV 3.x 三个值：image, contours, hierarchy _, contours, hierarchy = cv2.findContours(...)
OpenCV 4.x 两个值：contours, hierarchy（不再返回 image） contours, hierarchy = cv2.findContours(...)

这个差异是 OpenCV 从 3 升到 4 时最常报错的一处，症状是 ValueError: not enough values to unpack (expected 3, got 2)。反过来，用 OpenCV 4 的三值写法去跑 OpenCV 3，报 too many values to unpack。本文档的车道线流程走的是 fillPoly 路线，不依赖 findContours，所以不受影响；但如果你在这条流水线后面接轮廓提取（比如用车牌或交通标志做补充校验），这处必须对齐版本。

七、Canny 边缘检测的四个步骤 #

颜色法的上限就摆在这里：车道线不止一种颜色，同一种颜色在不同光照下呈现的像素值也不一样。原文把问题说得很直接——只提取单一颜色（比如白色）的车道线，对自动驾驶来说远远不够；白天和夜晚的同一条车道线，像素值差出一倍，阈值必然失效。

出路是换特征。颜色会变，但边缘相对稳定：车道线与路面之间存在亮度突变，这个突变在白天和夜晚都成立。Canny 就是用来提取这种突变的。

原文对 Canny 原理的表述，整理成四步：

步序 操作 目的 实现要点
1 转灰度图 三通道压成一通道，每像素一个 [0,255] 整数值 cv2.cvtColor(img, cv2.COLOR_RGB2GRAY)
2 高斯模糊去噪 抑制噪声导致的伪边缘 cv2.GaussianBlur(gray, (k,k), 0)，原文 k=5
3 计算梯度 得到每像素的强度梯度，反映与邻域的变化幅度 物体边缘处梯度大
4 非极大值抑制 把粗边缘细化，只保留真正位于边缘上的像素 沿梯度方向比较，抑制非极大点

第四步是 Canny 区别于普通「求梯度再卡阈值」的关键。梯度计算得到的边缘往往是几个像素宽的一坨，非极大值抑制会沿着梯度方向检查每个像素是不是局部最大，不是就压掉。结果是单像素宽的细边缘线，后面的霍夫变换对这种细线才友好。

原文这里也把双阈值判定并入了第四步的叙述，实际是同一套机制：先从梯度图里圈出梯度幅值落在某个区间的候选边界点，再用非极大值抑制把粗边缘削细。双阈值的具体判定规则放在下一章单独讲。

函数接口就一行：

text
edges = cv2.Canny(image, low_threshold, high_threshold)

edges 与输入 image 同尺寸，是单通道二值图。

版本差异：cv2.Canny 的参数表在 OpenCV 3 和 4 之间没有变化，但有一个隐式行为要知道——cv2.Canny() 内部自带一个 5x5 的高斯滤波。所以上面第二步的高斯模糊在技术上可省。原文的代码注释里点明了这一点：

python
kernel_size = 5
blur_gray = cv2.GaussianBlur(gray, (kernel_size, kernel_size), 0)

注释原文是 this step is optional as cv2.Canny() applies a 5x5 Gaussian internally。我们建议还是显式做一次，理由有两个：一是你能控制核大小，内部那个固定 5x5 改不了；二是你要做参数实验时，多一次显式模糊和多一组可见参数，归因更清楚。cv2.GaussianBlur 的第三个参数是标准差 σ，传 0 表示由核大小自动推算。

原文的完整 Canny 示例（图像是一张出口匝道照片 exit-ramp.jpg）：

python
# -*- coding: utf-8 -*-
import matplotlib.pyplot as plt
import matplotlib.image as mpimg
import numpy as np
import cv2

image = mpimg.imread('exit-ramp.jpg')
gray = cv2.cvtColor(image, cv2.COLOR_RGB2GRAY)

kernel_size = 5
blur_gray = cv2.GaussianBlur(gray, (kernel_size, kernel_size), 0)

low_threshold = 50
high_threshold = 150
edges = cv2.Canny(blur_gray, low_threshold, high_threshold)

plt.imshow(edges, cmap='Greys_r')

low_threshold = 50、high_threshold = 150，这两个值照录原文。注意 cmap='Greys_r'——_r 是反色，因为 edges 是黑底白线，matplotlib 默认显示会把 0 画成黑、255 画成白，本来就是黑底白线，加 _r 反而变成白底黑线，在某些背景上更清楚。这是显示层面的选择，不影响数据。

八、高低阈值的选取与双阈值判定 #

两个阈值的判定规则，原文分三条：

  1. 低于 low_threshold 的像素点，判定不是边缘。
  2. 高于 high_threshold 的像素点，判定是边缘（强边缘）。
  3. 落在两者之间的像素点，若与第 2 步得到的边缘像素点相邻，则判定是边缘；否则不是。

第三条是整个机制的核心。落在中间地带的像素不单独做决定，而是依附于强边缘——只要它连着某个强边缘，就被一起接纳；孤立的中间像素被丢弃。这样做的效果是：真实边缘的弱延伸段被保留，噪声引起的孤立弱响应被滤掉。

原文给出的取值建议，是 OpenCV 官方文档的口径：low_threshold 和 high_threshold 的比率建议在 1:2 到 1:3 之间。原文用的 50:150 正好是 1:3，符合这条建议。

这条建议的实际含义：两个阈值不是独立的两个自由度，而是一个尺度参数（整体高低）加一个比例参数（宽严）。比例太小（比如 1:1.1），中间带宽窄，判定近乎硬阈值，弱边缘全丢；比例太大（比如 1:10），中间带太宽，大量噪声被强边缘带进来。

工程上的调法：

  • 先按 1:2 或 1:3 定死比例。
  • 再把两个值一起上下移动。图像对比度高、边缘清晰，就一起抬高；图像偏暗、边缘糊，就一起压低。
  • 车道线检测里，路面上的阴影边缘和裂缝会被当作边缘提取出来，这是噪声的主要来源。抬 high_threshold 能压掉一部分，但抬太高会把远处的车道线一起丢掉——远处车道线在图像上只有几个像素宽，梯度响应本来就弱。这是个此消彼长的取舍，没有一劳永逸的值。

原文没有给出针对车道线场景的推荐阈值，只有 50/150 这一组示例值。其他图像的阈值原文未给出，需按实际图像调整。

九、霍夫变换：从边缘像素到直线 #

Canny 输出的是点——一堆被认为是边缘的像素坐标。我们要的是线。从点到线的这一步，用的是霍夫变换。

原文对霍夫变换流程的概括可以直接引用：给定一个物件和要辨别的形状种类，算法在参数空间（parameter space）中执行投票来决定物体的形状，而这是由累加空间（accumulator space）里的局部最大值（local maximum）决定的。

拆开说就是三件事：把图像空间的点映射到参数空间里的一条或多条曲线，让这些曲线去投票，票数最高的参数组合就是检测到的形状。

先说最直观的直线表示。图像空间里一条直线写成：

text
y = m*x + b

这里的 m 是斜率，b 是截距。变换到霍夫空间后，横轴是 m，纵轴是 b，那么图像空间的一条直线 y = m_0*x + b_0，在霍夫空间里就是一个点 (m_0, b_0)。

反过来也成立，这是整个算法的关键：

  1. 图像空间中的一个点 (x, y)，对应霍夫空间中的一条直线 b = y - x*m。把 (x, y) 代进 b = y - x*m，x 和 y 都已知，只有 m、b 是变量，所以这是一条以 m 为自变量、b 为因变量的直线。
  2. 霍夫空间中的两条直线的交点，对应图像空间中的一条直线；这条直线上存在两个点，分别对应霍夫空间中的那两条直线。
  3. 图像空间中同一条直线上的多个点，对应霍夫空间中的多条直线，这些直线相交于同一点。

第三条就是检测的依据。Canny 给出一堆边缘点，每个点都在霍夫空间里投出一条直线，共线的那些点投出的直线会挤在同一个位置相交。找这个交点，就等于找到了图像空间里的一条直线。

实现层面不真的去解交点，而是离散化加投票：把霍夫空间切成网格（栅格），每条投出来的直线经过哪些格子，就给哪些格子加一票。最后票数超过阈值的格子，其参数就对应一条被检测到的直线。这就是「累加空间里的局部最大值」的实际含义。

十、极坐标下的直线表示 #

y = m*x + b 这个表示有个致命问题：平行于 y 轴的直线斜率无穷大。图像里的车道线在转弯或相机偏转时会接近竖直，m 就爆掉。霍夫空间的网格也就没法均匀切分。

解决办法是换参数化。原文的说明是：采用「sine Hough」空间，在图像空间用 ρ（rho）表示直线到原点的距离，用 θ（theta）表示从 x 轴到直线垂线的角度，也就是在霍夫空间用 (θ, ρ) 代替 (m, b)。

直线的法线式写法：

text
ρ = x*cos(θ) + y*sin(θ)

几何含义：从原点向这条直线作垂线，垂线长度为 ρ，垂线与 x 轴的夹角为 θ。任何一个 (θ, ρ) 唯一确定一条直线；任何一条直线也唯一对应一个 (θ, ρ)。这里没有无穷大的问题——竖直直线的 θ 是 0 或 π，ρ 是有限的。

参数范围：θ 取 [0, π)（因为 θ 和 θ+π 描述的是同一条直线，方向相反），ρ 的取值范围由图像尺寸决定，落在 [-D, D] 之间，其中 D 是图像对角线长度。

换到 (θ, ρ) 坐标后，图像空间中的一个点，对应霍夫空间里的一条正弦曲线。把 x、y 固定为常数（那是一个已知点），θ 从 0 扫到 π，ρ = x*cos(θ) + y*sin(θ) 画出来就是一条正弦曲线。原文用图说明了这个对应关系。

所以：

图像空间 霍夫空间（m, b） 霍夫空间（θ, ρ，即 sine Hough）
一条直线 一个点 (m_0, b_0) 一个点 (θ_0, ρ_0)
一个点 (x, y) 一条直线 b = y - x*m 一条正弦曲线 ρ = x*cosθ + y*sinθ
共线的 N 个点 N 条直线交于一点 N 条正弦曲线交于一点
竖直直线 斜率无穷大，不可表示 θ=0 或 π，ρ 有限，正常表示

霍夫变换要干的事，就是找出这些正弦曲线交于一点的位置。

十一、霍夫变换的累加器原理 #

(θ, ρ) 空间是连续的，计算机要离散化：

  1. 把 θ 切成固定步长（角度分辨率），把 ρ 切成固定步长（距离分辨率），得到一张二维网格，每个格子叫一个 bin。
  2. 每个格子对应一个计数器，初始全 0。这张计数器表就是累加器（accumulator）。
  3. 遍历边缘图里每一个像素 (x, y)：对每个离散的 θ 值，算出一个 ρ 值，把 (θ, ρ) 落到某个格子，该格子的计数加 1。
  4. 遍历结束后，检视累加器，计数超过阈值的格子就对应一条检测到的直线。

复杂度：如果边缘图有 N 个像素、θ 切成 T 份，则投票阶段要做 N×T 次浮点运算。这是霍夫变换的主要开销，也是为什么先做区域裁剪——裁掉一半区域，后面全流程直接省一半。

用上面那个「累加空间里的局部最大值」的说法对照一下：投票就是累加器里的计数，局部最大值就是票数突出的那些格子，阈值就是判定门槛。三件事是一回事的不同描述角度。

累加器这一步有个直观的几何检验：一条直线上的点在累加器里会全部投到同一个格子，所以那个格子的票数接近这条线上点的实际数量。反过来，如果某个格子只有零星几票，说明那只是几条不相关的曲线偶然穿过，不是真直线。

另一个细节：落在同一直线上但方向相反的点，投出的曲线也会相交，因为 θ 和 θ+π 描述同一条几何线。这也是累加器里会出现对称峰值的原因，不影响检测，只是会看到重复响应。

十二、概率霍夫变换与参数调节 #

cv2.HoughLines 是标准霍夫变换，输出的是完整直线的 (θ, ρ)——不告诉你线段的起止位置，你得自己按 θ、ρ 反解出直线方程，再和图像边界求交，才能画出来。车道线检测不需要整条无限长的直线，需要的是线段——车道线在图像里有明确的起点和终点（比如被前车挡住的那一段就没有）。

所以用 cv2.HoughLinesP，P 是 Probabilistic（概率）的意思。它不遍历所有边缘点，而是随机采样一部分点去投票，并对已经检测到的直线做「够长就停止投票」的剪枝。速度比标准霍夫快。

函数声明，原文照录：

python
lines = cv2.HoughLinesP(masked_edges, rho, theta, threshold, np.array([]),
                        min_line_length, max_line_gap)

返回的 lines 是包含线段起止点 (x1, y1, x2, y2) 的数组。各参数含义：

参数 含义 单位 原文取值 调大的后果
masked_edges 输入边缘图（Canny 输出，已做区域掩码） — — —
rho 霍夫空间栅格的距离分辨率 像素 2 分辨率变粗，相邻平行线易被合并
theta 霍夫空间栅格的角度分辨率 弧度 np.pi/180（1 度） 角度分辨变粗，接近平行但稍有夹角的线会被算作同一条
threshold 投票的最小值，即某栅格内曲线交点个数超过它才输出 票数 15 变严，弱线被丢
np.array([]) 占位符，无需修改 — — —
min_line_length 输出线段的最小长度 像素 30 变严，短线段被丢
max_line_gap 连接两个独立线段成一条输出线段的最大间隔 像素 20 变宽，断裂的两段会被连成一条

原文对 rho、theta 的取值说明：rho 单位为像素，最小值为 1；theta 单位为弧度，初始值可设为 1 度（pi/180 rad）。threshold 的实际语义是给定栅格中的曲线交点个数，只有超过它才认为该栅格对应一条应输出的线段。

返回格式的版本差异，这一处最容易踩：

版本 cv2.HoughLinesP 返回 遍历写法
OpenCV 3.x numpy.ndarray，形状 (N, 1, 4) for line in lines: for x1,y1,x2,y2 in line: ...
OpenCV 4.x numpy.ndarray，形状 (N, 1, 4) 同上，for i in range(lines.shape[0]) 也行

两个版本形状相同，这地方真正的坑不在形状，而在无直线时的返回值：lines 会是 None，而不是空数组 []。直接 for line in lines 会抛 TypeError: 'NoneType' object is not iterable。所以正确写法是先判空：

python
lines = cv2.HoughLinesP(masked_edges, rho, theta, threshold, np.array([]),
                        min_line_length, max_line_gap)
if lines is None:
    return None          # 这一帧没检出车道线
for line in lines:
    for x1, y1, x2, y2 in line:
        cv2.line(line_image, (x1, y1), (x2, y2), (255, 0, 0), 10)

内层的 for x1, y1, x2, y2 in line 是因为每条 line 是形状 (1, 4) 的二维数组，拆一层才能拿到四个标量。

原文还给了完整的一体化示例，执行流程是：加载图像 → 灰度转换 → 高斯模糊 → Canny 边缘检测 → fillPoly 目标区域筛选 → HoughLinesP 直线提取 → 结果可视化。

python
# -*- coding: utf-8 -*-
import matplotlib.pyplot as plt
import matplotlib.image as mpimg
import numpy as np
import cv2

image = mpimg.imread('exit-ramp.jpg')
gray = cv2.cvtColor(image, cv2.COLOR_RGB2GRAY)

kernel_size = 5
blur_gray = cv2.GaussianBlur(gray, (kernel_size, kernel_size), 0)

low_threshold = 50
high_threshold = 150
edges = cv2.Canny(blur_gray, low_threshold, high_threshold)

mask = np.zeros_like(edges)
ignore_mask_color = 255

imshape = image.shape
vertices = np.array([[(0, imshape[0]), (450, 290), (490, 290), (imshape[1], imshape[0])]],
                    dtype=np.int32)
cv2.fillPoly(mask, vertices, ignore_mask_color)
masked_edges = cv2.bitwise_and(edges, mask)

# 霍夫参数
rho = 2                     # 霍夫栅格的距离分辨率（像素）
theta = np.pi / 180         # 霍夫栅格的角度分辨率（弧度）
threshold = 15              # 最小投票数
min_line_length = 30        # 构成一条线的最少像素数
max_line_gap = 20           # 可连接线段之间的最大间隔（像素）
line_image = np.copy(image) * 0     # 空白画布用于画线

lines = cv2.HoughLinesP(masked_edges, rho, theta, threshold, np.array([]),
                        min_line_length, max_line_gap)

for line in lines:
    for x1, y1, x2, y2 in line:
        cv2.line(line_image, (x1, y1), (x2, y2), (255, 0, 0), 10)

# line_image 是 RGB 图像，edges 是单通道，先叠成三通道才能加权融合
color_edges = np.dstack((edges, edges, edges))

# color_edges 权重 0.8，line_image 权重 1
lines_edges = cv2.addWeighted(color_edges, 0.8, line_image, 1, 0)
plt.imshow(lines_edges)
plt.show()

几个数值都要留意。cv2.line 的线宽是 10 像素，比车道线本身粗得多，目的是让结果醒目，不是真实宽度。cv2.addWeighted(color_edges, 0.8, line_image, 1, 0) 的第三个参数 1 是 line_image 的权重，两个权重之和不要求等于 1；第五个参数 0 是叠加后的偏移量。结果里边缘图占 0.8、画出 的线占 1.0，所以线会比边缘更亮。np.dstack((edges, edges, edges)) 这步是为了解决通道数不匹配。edges 是单通道，line_image 是三通道，addWeighted 要求两个输入尺寸和通道数都一致，所以要把单通道复制三份拼成三通道。

np.copy(image) * 0 是把整幅图乘 0 得到同尺寸同类型的全黑画布，等价于 np.zeros_like(image)，原文用前者是因为能保证 dtype 和通道数跟原图完全一致。

十三、车道线拟合：把散点连成线 #

HoughLinesP 的输出是一堆短线段，不是两条车道线。画面里常检出 20 条线段，左车道线被分成 5 段，右车道线被分成 7 段，剩下 8 段是护栏、路面裂缝、前车尾部轮廓。我们需要把这些碎段归并成「左线一条、右线一条」。

这一步的通行做法是根据斜率把线段分成两组，再各自做一次多项式拟合。

分组的依据是线段斜率的符号。图像坐标系里 y 轴向下，所以：

  • 左侧车道线从下方（y 大）往上方（y 小）走，x 增大，斜率 dy/dx 为负。
  • 右侧车道线从下方往上方走，x 减小，斜率 dy/dx 为正。

代码骨架：

python
def split_and_fit(lines, img_shape):
    left_pts, right_pts = [], []
    for line in lines:
        for x1, y1, x2, y2 in line:
            if x1 == x2:                    # 竖直段，斜率无穷，先跳过
                continue
            k = (y2 - y1) / (x2 - x1)
            if abs(k) < 0.5:                # 太接近水平的段，是横向标线或噪声
                continue
            if k < 0:
                left_pts += [(x1, y1), (x2, y2)]
            else:
                right_pts += [(x1, y1), (x2, y2)]

    # 对每组点用一次多项式拟合 x = a*y + b（不是 y = a*x + b）
    left_fit = right_fit = None
    if len(left_pts) >= 2:
        left_fit = np.polyfit([p[1] for p in left_pts], [p[0] for p in left_pts], 1)
    if len(right_pts) >= 2:
        right_fit = np.polyfit([p[1] for p in right_pts], [p[0] for p in right_pts], 1)
    return left_fit, right_fit

注意 np.polyfit 的参数顺序被反过来了：自变量传的是 y，因变量传的是 x。这不是笔误。车道线在图像里接近竖直，用 y = f(x) 拟合时，同一条线的 x 变化范围只有 200 像素、y 变化 300 像素，还好；但遇到更陡的线，同一个 x 会对应多个 y，y = f(x) 就不是函数了。写成 x = a*y + b，因为 y 是单调的，永远成立。

abs(k) < 0.5 这个阈值和竖直段的跳过都是工程经验值，原文未给出这套后处理的完整代码，阈值需按实际图像调整。

真要做鲁棒的版本，拟合这一步要配合 RANSAC，或者按线段长度加权（长的、靠近画面下方的线段更可信）。原文没有涉及这部分。

十四、完整车道检测流程 #

把上面所有环节串起来，一个能跑通的车道检测单帧流程是这样的：

python
import cv2
import numpy as np

def lane_pipeline(img_bgr):
    # 1. 颜色筛选（白 + 黄），得到掩码
    hls = cv2.cvtColor(img_bgr, cv2.COLOR_BGR2HLS)
    white = cv2.inRange(hls, np.array([0, 200, 0]),    np.array([255, 255, 40]))
    yellow = cv2.inRange(hls, np.array([15, 30, 115]), np.array([35, 204, 255]))
    color_mask = cv2.bitwise_or(white, yellow)
    color_only = cv2.bitwise_and(img_bgr, img_bgr, mask=color_mask)

    # 2. 灰度 + 高斯模糊
    gray = cv2.cvtColor(color_only, cv2.COLOR_BGR2GRAY)
    blur = cv2.GaussianBlur(gray, (5, 5), 0)

    # 3. Canny 边缘检测
    edges = cv2.Canny(blur, 50, 150)

    # 4. 区域掩码（梯形 ROI）
    h, w = edges.shape
    mask = np.zeros_like(edges)
    vertices = np.array([[(0, h), (450, 290), (490, 290), (w, h)]], dtype=np.int32)
    cv2.fillPoly(mask, vertices, 255)
    masked = cv2.bitwise_and(edges, mask)

    # 5. 概率霍夫变换
    lines = cv2.HoughLinesP(masked, 2, np.pi / 180, 15, np.array([]), 30, 20)
    if lines is None:
        return img_bgr, None

    # 6. 按斜率分组 + 拟合，画回原图
    canvas = np.copy(img_bgr)
    for line in lines:
        for x1, y1, x2, y2 in line:
            cv2.line(canvas, (x1, y1), (x2, y2), (0, 0, 255), 4)

    # 7. 与原图加权叠加
    result = cv2.addWeighted(img_bgr, 0.8, canvas, 1.0, 0)
    return result, lines

执行顺序不能随便调，每一步的输入依赖上一步的输出：

步 输入 输出 关键参数 不可颠倒的理由
1 颜色筛选 BGR 原图 彩色图（掩码内保留） HLS 上下界 颜色不对的像素不全是车道线，先砍掉
2 灰度 上一步 单通道 — Canny 只吃单通道
3 高斯模糊 灰度图 灰度图 kernel=5 去噪必须在求梯度之前
4 Canny 模糊图 二值边缘图 50 / 150 边缘是霍夫的输入
5 区域掩码 边缘图 二值边缘图 顶点数组 必须在霍夫之前，否则会检测千里外的线
6 霍夫 掩码边缘图 线段数组 2, π/180, 15, 30, 20 —
7 拟合 线段数组 左右车道线 斜率符号分组 拟合必须在线段检测之后

第 5 步放在霍夫之前还是之后，这个顺序是有讲究的。放在之前，能大幅减少霍夫的投票计算量，也能直接排除掉远处区域里的假直线。放在之后，你检测完再裁剪，计算白费。所以必须在霍夫之前。

第 1 步用的是「颜色筛选后保留彩色」，而不是「颜色筛选得到二值图」。区别在于：二值图里所有通过筛选的像素都是 255，梯度信息被抹掉了；彩色图保留了灰度差异，车道线比路面亮，Canny 才能找到那条边缘。这是个容易搞错的细节——如果直接把 color_mask 喂给 Canny，得到的是掩码自己的边界，不是车道线的边界。

十五、传统方法的局限 #

这条流水线能跑通，但它的成立条件很窄。

假设 失效场景 后果
车道线是直线 弯道、匝道、环岛 拟合出的直线偏离真实车道，越远越偏
车道线在画面下部 上坡、下坡、相机俯仰角变化 ROI 顶点写死在像素坐标里，换一种坡度就框错位
车道线与路面有足够对比度 逆光、夜间、隧道口、雨雪路面反光 Canny 阈值全面失效，边缘要么全丢要么全是噪声
相机位置固定 换车、换相机型号、调整安装角度 所有硬编码坐标（ROI 顶点、阈值）全部要重调
车道线颜色只有白和黄 施工路段、特殊涂装标线 颜色筛选直接漏检
路面无强纹理 水泥路面接缝、补丁、阴影 伪边缘多，霍夫检出一堆假线

这些假设一条条列出来，你就明白了为什么业界最终转向深度学习。传统法的每一个参数都在为「某一种特定的光照条件和道路类型」调优，换一个场景，参数就废了。这不是参数没调好，是特征本身不够鲁棒——颜色、梯度这些低层特征和「这是车道线」这个语义概念之间没有稳定的映射。

传统法仍有它的位置：算力极低（整条流水线在 Cortex-A 上能跑到几十帧）、可解释（每个参数改了什么，一眼能看出来）、不需标注数据。在算力受限的嵌入式平台上，或者作为深度模型的预筛环节，它还活着。

真正要应对真实道路，得走另一条路——让模型自己去学「什么样子叫车道线」，而不是我们手工规定「什么颜色、什么梯度叫车道线」。目标识别走的就是这条路。

十六、YOLO 要解决什么 #

先回答一个前置问题：认出了目标，对自动驾驶到底有什么用？

原文给的场景是碰撞时间（TTC，Time To Collision）估计。把激光雷达 3D 点云映射到相机图像之后，我们手上有一堆匹配关键点（matched keypoints），也有一堆叠在图像上的激光雷达点。问题来了：这些点和激光点属于哪个物体，我们并不知道。路面上的点、静止护栏的点、前方前车的点全混在一起，直接拿去算 TTC，结果会被完全无关的静止物体污染。

解法是先做目标检测，把场景里每个目标用 2D 边界框圈出来。框一出来，点云和关键点就可以按框归属：落在框内的点归这个目标，框外的丢掉。这样算 TTC 用的点只来自前方那辆车，值才可信。

原文也提到了另一条路：激光雷达的点云本身可以通过聚类形成独立对象，用 PCL（点云库）实现——PCL 大致可以看作 3D 领域的 OpenCV。两条路是替代关系：一条用图像检测给点云分组，一条用点云自身的空间聚集性分组。原文在这一节里选的是前一条，因为它能直接复用上一节课已经做好的「点云投影到图像」这件事。

YOLO 的定位，原文的对照说明：

  • 不同于 HOG/SVM 这种基于分类器的系统，YOLO 针对整个图像，因此预测值依赖于整幅图像的全部内容。
  • 它的预测只用单层网络模型，不像 R-CNN 那样依赖上千层网络模型。
  • 结果是：在输出类似预测结果的条件下，YOLO 的预测速度极快。

「针对整个图像」这句话的技术含义是：YOLO 的预测不是「先抠出候选区域再分类」的两阶段流程，而是一次前向传播同时输出所有目标的位置和类别。这省掉了候选区域生成的开销，也是速度快的原因。

YOLO 的作者提供了一系列基于 COCO 数据集预训练得到的权重，当前版本 YOLOv3 能识别图像和图像中的 80 种不同目标。这意味着可以拿 YOLOv3 当一个现成的分类器用，检测图像中的汽车及其他目标。

工程上要注意的是：COCO 的 80 类覆盖了车、人、卡车、自行车、交通灯、停止标志等，但不覆盖所有驾驶场景需要的类别（比如具体的交通标志子类、路面锥桶的部分形态）。要识别 COCO 之外的东西，得自己微调。

十八、网格划分与边界框预测 #

YOLO 的第一步是把图像切成网格。原文的说明是：图像被分成 13×13 像素的栅格单元；基于输入图像的尺寸，这些栅格单元的尺寸也应该相应变化。代码里一个 416×416 像素的图像，对应的栅格单元尺寸为 32×32 像素。

原文这里「13×13 像素的栅格单元」的表述容易被误读成「每格 13×13 像素」。实际关系是：416 / 13 = 32，栅格单元是 32×32 像素，网格是 13×13 个。13 是格子数量，32 是每格的像素边长。算一下就知道 13 不会是边长——416 除不尽 13。

每个栅格单元负责预测一系列的 bounding box。对每个 box，网络预测两样东西：

  1. 该 box 包含某个特定目标的置信度。
  2. 该目标属于各类别的概率（依据 COCO 数据集的 80 类）。

为什么网格化能解决检测问题：把一个物体归属于「它的中心点落在哪个格子」，每个格子只负责中心点在自己内部的目标。这样避免了多个格子同时预测同一个目标。这也是为什么 13×13 的网格对大目标友好——大目标的中心点只有一个，落在哪个格子就由哪个格子负责；而小目标在粗网格里，中心点容易被邻近格子的预测覆盖掉。

网络输出在内存里的组织方式，用的是 blob。

Blob 是很多框架（如 Caffe）里保存、通信、操作信息的基本单元，是一个提供实际数据处理、交互以及 CPU/GPU 之间数据同步的包装器。数学上它是一个以 C-contiguous 方式存储的 N 维序列，N 是数据的 batch size。图像数据的 blob 维度记作 N×C×H×W（数量、通道、高度、宽度）：

  • N：batch size。一个 256 张图像的训练 batch，N 就是 256。批处理能让数据通信和设备处理获得更好的吞吐量。
  • C：特征维度。RGB 图像 C=3。
  • H、W：高、宽。

OpenCV 里 blob 存成 4 维 cv::Mat，维度顺序是 NCHW。在这样一个 blob 里，位置 (n, c, h, w) 的线性偏移按下面的公式算：

text
b(n, c, h, w) = ((n * C + c) * H + h) * W + w

这个公式的意义：blob 在内存里是一维连续的一串数，你要访问 (n,c,h,w) 这个逻辑位置，必须先跨过 n 个完整图像（每张 C*H*W 个元素），再跨过 c 个通道（每个 H*W），再跨过 h 行（每行 W 个），最后加上 w。这就是 NCHW 布局的「行优先」展开。

从图像生成 blob：

参数逐个说：

参数 原文取值 含义

crop=false 意味着是拉伸（resize），不是中心裁剪。原文的说法是「调整了图像尺寸为（416,416,416），从而使图像不会被裁剪」——这里「416,416,416」的第三个数是笔误，cv::Size 只有两个分量（宽、高）。

swapRB 这个参数的意义要讲清楚：OpenCV 用 cv::imread 读图，默认得到的是 BGR 顺序；而 YOLO 的权重是在 RGB 顺序上训练的。所以理论上应该设 swapRB=true。原文写的是 false。这两种设置都不会报错，差别会体现在检测精度上——颜色通道反了，模型看到的「红色车」和「蓝色车」和训练时对不上。这里按原文照录 false，但实际部署时建议两边都试一次，对比检测结果。

前向传播的执行：

cpp
// Get names of output layers
vector<cv::String> names;
vector<int> outLayers = net.getUnconnectedOutLayers();      // 输出层的索引
vector<cv::String> layersNames = net.getLayerNames();        // 全部层的名字

names.resize(outLayers.size());
for (size_t i = 0; i < outLayers.size(); ++i)
{
    names[i] = layersNames[outLayers[i] - 1];
}

// invoke forward propagation through network
vector<cv::Mat> netOutput;
net.setInput(blob);
net.forward(netOutput, names);

getUnconnectedOutLayers 返回的是「输出未被其他层连接的层」的索引——也就是网络的最终输出层。因为 YOLOv3 有三个尺度输出，这里返回的是三个索引。layersNames[outLayers[i] - 1] 里的 -1 是索引偏移：层索引从 1 开始编号，而 std::vector 的下标从 0 开始，所以要减 1。

这是 OpenCV 3 与 4 之间的一个明确 API 差异点：

版本 net.getUnconnectedOutLayers() 返回类型 取名字的写法
OpenCV 3.x std::vector<int> layersNames[outLayers[i] - 1]（需要减 1）
OpenCV 4.x std::vector<int>（C++） 同上
OpenCV 4.x（Python） numpy.ndarray，形状 (3,) net.getLayerNames()[i - 1]，i 是 numpy 元素

Python 侧从 OpenCV 4.5.4 起，getUnconnectedOutLayers 直接返回一维数组，元素就是输出层索引。早期 Python 版本返回的是形状 (3, 1) 的二维数组，元素是单元素数组，直接当下标用会报 IndexError。稳妥写法是先 .flatten()。

netOutput 是 vector<cv::Mat>，长度为 3（三个尺度）。每个元素是一个二维 Mat，行数是该尺度上的预测框总数，列数是 5 + 类别数。

输出的语义，原文的说明是：前向传播的结果是一个长度为 C（blob 类别个数）的数组，每个类别的前四个值分别为 bounding box 的 x 中心、y 中心、宽度、高度；第五个值表示该 bounding box 包含一个目标的置信度；剩余的矩阵元素是对应 coco.cfg 文件中每个目标类别的置信度。

这里要校正一处：原文「长度为 C（blob 类别个数）的数组」的表述与上下文不一致。按「前四 + 第五 + 剩余类别概率」的结构，每行的长度是 5 + 类别数，即 5 + 80 = 85 列。C 在这里指的是通道数/特征维度，不是「类别个数」。原文后文自己也写「剩余的矩阵元素是对应每个目标类别的置信度」，说明列数应大于 5 + 类别数关系明确。

另一个关键点：前四个值都是归一化到 [0, 1] 的，不是像素坐标。还原成像素坐标要分别乘图像的宽和高，这段还原代码在下一章。

这里把表示法钉死，别混。网络输出的是中心点加宽高 (cx, cy, w, h)，cx、cy 是框中心的像素坐标，w、h 是框的宽和高，四个量都是相对整幅图归一化的比例。而 OpenCV 的 cv::Rect 要的是左上角加宽高 (x, y, w, h)，x、y 是左上角像素坐标。两者差一个半宽半高的平移：

text
x = cx - w/2
y = cy - h/2
表示法 四个分量 谁在用 转换
中心式 (cx, cy, w, h) 框中心 x、框中心 y、宽、高 YOLO 网络输出 —
角点式 (x, y, w, h) 左上角 x、左上角 y、宽、高 cv::Rect、cv2.rectangle、NMSBoxes x = cx - w/2，y = cy - h/2

宽高在两个表示法里含义相同，只有中心点和左上角的区别。搞错这一处，框会整体偏半个宽高，看起来就是「框错位了一半」。

十九、置信度与类别概率 #

两个概念要分开，它们不是一回事。

  • box 置信度（objectness）：这个格子里的框是否包含一个目标，以及框的位置有多准。它和类别无关，只回答「有没有东西」。
  • 类别概率：在假定框里有东西的前提下，这个东西属于 80 类中每一类的概率。

前者乘以后者，才得到这个框里是「某类目标」的最终得分。这两个量的乘积就是筛选时真正用的分数。

原文的代码用的是另一种做法，直接取类别分数的最大值当置信度：

cpp
// Scan through all bounding boxes and keep only the ones with high confidence
float confThreshold = 0.20;
vector<int> classIds;
vector<float> confidences;
vector<cv::Rect> boxes;
for (size_t i = 0; i < netOutput.size(); ++i)
{
    float* data = (float*)netOutput[i].data;
    for (int j = 0; j < netOutput[i].rows; ++j, data += netOutput[i].cols)
    {
        cv::Mat scores = netOutput[i].row(j).colRange(5, netOutput[i].cols);
        cv::Point classId;
        double confidence;

        // 取最大分值和其位置
        cv::minMaxLoc(scores, 0, &confidence, 0, &classId);
        if (confidence > confThreshold)
        {
            cv::Rect box; int cx, cy;
            cx = (int)(data[0] * img.cols);
            cy = (int)(data[1] * img.rows);
            box.width  = (int)(data[2] * img.cols);
            box.height = (int)(data[3] * img.rows);
            box.x = cx - box.width / 2;     // left
            box.y = cy - box.height / 2;    // top

            boxes.push_back(box);
            classIds.push_back(classId.x);
            confidences.push_back((float)confidence);
        }
    }
}

逐段拆解：

netOutput[i].row(j).colRange(5, netOutput[i].cols) —— 取第 j 行的第 5 列到最后一列。左边跳过 5 列，正是跳过 x, y, w, h, objectness 这五个值。剩下的就是 80 个类别分数。

cv::minMaxLoc(scores, 0, &confidence, 0, &classId) —— 求矩阵的最小值和最大值及其位置。五个参数依次是：输入矩阵、最小值输出指针、最大值输出指针、最小值位置指针、最大值位置指针。这里第 2、4 个传 0（nullptr），表示不关心最小值。所以 confidence 拿到最大分值，classId.x 拿到最大值所在的列索引——也就是类别 id。

原文这里有个字：「cv::minMaxLoc 勇于找到元素中的最小值和最大值」，「勇于」应为「用于」。

坐标还原 —— data[0] 到 data[3] 是归一化的 cx, cy, w, h，乘 img.cols / img.rows 得到像素值。box.x = cx - box.width/2 把中心点加宽高的表示转成 OpenCV cv::Rect 要的左上角加宽高的表示。这个转换有个精度问题：(int) 是截断不是四舍五入，box.width/2 又是整数除法，两处都会引入半像素以内的偏差。对检测框来说无关紧要，但如果拿来做像素级对齐（比如框内点云裁剪），这点偏差会传导。

指针递增 —— data += netOutput[i].cols 写在循环的第三个表达式里，每轮跳过一整行。这是无拷贝遍历 Mat 数据的高效写法，代价是要自己管指针，rows、cols 算错就会越界读。

confThreshold = 0.20 —— 这个值很低。0.20 意味着只要模型有 20% 把握就保留，后面靠 NMS 和实际应用再筛。低阈值加 NMS 的组合，召回率高、假阳性也多；高阈值直接丢掉大量真目标。调这个值要看你的应用更怕漏检还是更怕误检。

二十、非极大值抑制 #

上面那轮筛选留下一个问题：同一个目标会被多个框圈住。

原因有两个。一是网格化本身——一个目标的中心点落在某一个格子，但相邻格子的先验框如果和这个目标的重叠度足够高，网络也会给它一个不错的分数。二是三个尺度输出——同一个大目标会在 13×13 和 26×26 两个尺度上都被检出。还有 anchor 因子，每个格子有多个先验框。

结果就是一辆车周围围了七八个框，全都在 boxes 里。

非极大值抑制（NMS，non-maximum suppression）的作用，原文的说明是：为了避免多个 box 实际包含了同一目标，利用 NMS 去除掉多余的 bounding box，并只保留具有最高置信度的 box。

算法流程：

  1. 把这批框按置信度从高到低排序。
  2. 取当前置信度最高的框 A，加入保留列表。
  3. 遍历剩下所有框，计算它与 A 的 IoU（交并比）。IoU 大于 nmsThreshold 的框，判定为与 A 描述同一目标，从候选里删除。
  4. 从剩下的框里再取置信度最高的，重复 2 到 3，直到候选为空。

IoU 的定义是两个框的交集面积除以并集面积，取值 [0, 1]。完全没有重叠时 IoU=0，完全重合时 IoU=1。nmsThreshold 是「算作同一个目标」的重叠上限：阈值低（比如 0.3），稍微重叠就抑制，留下的框少、容易把相邻的两个真实目标误合并；阈值高（比如 0.7），要求高度重叠才抑制，留下的框多、会出现重复框。

OpenCV 提供了现成实现：

cpp
// perform non-maxima suppression
float nmsThreshold = 0.4;      // Non-maximum suppression threshold
vector<int> indices;
cv::dnn::NMSBoxes(boxes, confidences, confThreshold, nmsThreshold, indices);

参数依次是：候选框列表 boxes、对应的置信度列表 confidences、置信度下限 confThreshold、重叠度上限 nmsThreshold、输出的保留索引 indices。函数是原地返回索引，不修改 boxes，所以后面要按 indices 去取框、取类别、画图：

cpp
for (size_t i = 0; i < indices.size(); ++i)
{
    int idx = indices[i];
    cv::Rect box = boxes[idx];
    cv::rectangle(img, box, cv::Scalar(0, 255, 0), 2);
    string label = classes[classIds[idx]] + ": " + to_string(confidences[idx]);
    cv::putText(img, label, cv::Point(box.x, box.y - 5),
                cv::FONT_HERSHEY_SIMPLEX, 0.5, cv::Scalar(0, 255, 0), 1);
}

confThreshold 传了两次——一次在上面的筛选循环里，一次在 NMSBoxes 的参数里。两处要一致，否则第二次会再做一遍收紧，容易被忽略。

版本差异补充： cv::dnn::NMSBoxes 在 OpenCV 3.4.x 与 4.x 之间的签名一致。Python 侧的对应函数是 cv2.dnn.NMSBoxes，返回值在 4.x 里是形状 (K, 1) 的 numpy 数组（部分是 (K,)），必须 .flatten() 才能当索引列表用，否则 boxes[idx] 里取到的是数组而非整数，会抛 IndexError 或 TypeError。这是移植 YOLO 后处理时最常见的崩溃点之一。

NMS 有一个已知缺陷：当一个目标真的被另一个目标遮挡、两个框重叠度超过 nmsThreshold 时，被遮挡那个会被抑制掉。在密集车流场景里这会造成漏检。业界用 Soft-NMS 之类的变体缓解，YOLOv3 本身用的是标准 NMS。

二十一、YOLO 与激光雷达的融合：把检出的框映射到点云 #

融合的思路一句话说完：既然是「点云已经很精确地投射到图像平面上了」，那么给定一组来自目标检测的边界框，只要检查某个 3D 激光雷达点在映射到相机图像后落在哪个框里，就能把它和场景中的特定目标关联起来。

注意这句话里的前提：点云投影这件事已经做完了。具体怎么从 3D 点坐标算出 2D 像素坐标，需要相机内参矩阵和外参矩阵——相机焦距、光心、激光雷达坐标系到相机坐标系的旋转和平移。这一整套推导在同批的《激光雷达与相机融合：从针孔模型到点云投影》里讲，本篇不重复。本篇只接在它的输出上：你已经有了 (u, v) 像素坐标，现在要找这个点属于哪个物体。

伪代码：

python
# 已在别处完成：project_points(points_3d) -> 每个点的 (u, v) 像素坐标
uv = project_points(points_lidar)

for idx in indices:                       # NMS 之后保留的框
    box = boxes[idx]
    inside = []                           # 落在这个框内的点
    for k, (u, v) in enumerate(uv):
        if box.x <= u < box.x + box.width and box.y <= v < box.y + box.height:
            inside.append(points_lidar[k])
    if len(inside) < 5:                   # 框内点太少，不可信
        continue
    ttc = estimate_ttc(inside)            # 只用这个目标的点算

三个要点：

用 NMS 之后的框，不是 NMS 之前的。 前面那轮 boxes 里有大量重复框，拿重复框去分点，同一个点会被算进多个目标组。必须用 indices 索引过一遍。

必须设框内点数的下限。 远处目标在图像上框很大，但投射到框里的激光点只有两三个，甚至一个都没有——因为激光雷达的角分辨率有限，远处的点本来就稀疏。两三个点算出来的 TTC 毫无统计意义。下限设多少要按激光雷达的线数决定，原文未给出，需按实际传感器参数调整。

必须检查遮挡。 框是一个矩形，前车的框和它后面的物体的投影会落在同一区域。一个点投在框内，不代表它真的属于这个物体——它被框对应的物体挡住了。严格的实现需要在点云的空间域上再做一次深度比较，而不是纯靠 2D 框归属。

原文提到，激光雷达点云的另一种分组方式是聚类。PCL 提供了对应的算法，把在空间上彼此靠近的点聚成一团，每一团就是一个疑似目标。这条路不需要相机，也不受光照影响，缺点是聚类参数（邻域半径、最小点数）对不同场景敏感，同一个目标在远处会被拆成两团。两条路配合用效果更好：图像给语义，点云给几何。

原文在这一节之后结束了，没有给出框内取点的实际代码，也没给出 TTC 的具体计算公式。这部分原文未给出，本文档也未验证。

二十二、两种方法的取舍 #

维度 传统流水线（颜色 + Canny + 霍夫） 深度学习（YOLOv3）
输出 车道线的像素坐标 每个目标的 2D 框 + 类别 + 置信度
依赖的特征 颜色、梯度（人手设计） 从数据里学出来的深层特征
门槛 无训练、无权重文件 需要 cfg、weights、names 三个文件
算力 极低，纯 OpenCV 基础算子 需要 DNN 推理，CPU 上逐帧吃力
可解释性 高，每个参数的作用可见 低，只有输入和输出
参数鲁棒性 差，换光照/路面/相机全废 好，预训练权重跨场景可用
失效模式 可预测（阈值失配、伪边缘） 难预测（误检、漏检、类别混淆）
调参方式 改常数（阈值、ROI 顶点） 微调权重、改 confThreshold/NMS threshold
适用位置 车道线 车辆、行人、交通标志

这两条线不是竞争关系，是分工。车道线不适合用通用目标检测器做，因为「车道线」不是 COCO 的 80 类之一，而且车道线是延伸的线状结构不是紧凑的矩形目标——虽然 YOLO 系也有专门做车道线的变体，但那是另一个话题。

反过来，目标检测不适合替代车道线检测，因为检测器输出的是框，框里是什么形状它不管，拿框去推车道线的几何参数（曲率、偏移）精度不够。

真实系统里两条线都在跑：传统流水线负责近场车道线的精确几何，深度学习负责中远场目标的语义识别。融合它们的输出，再加上雷达/激光雷达的距离测量，才构成完整的感知。

原文对 YOLO 的速度优势给了明确评价：「这使得 YOLO 在输出类似预测结果的条件下，具有极快的预测速度」。这个「极快」是相对 R-CNN 系的两阶段方案说的，不是说不耗时。416×416 输入在 CPU 上单帧几十毫秒到上百毫秒，车载场景要 GPU 或专门的推理加速器。

两篇素材合起来看，从「圈出框」到「用上框」还差几步，把链路补全有助于判断要不要用哪套方法：

环节 由谁提供 本篇是否覆盖
3D 点云 → 2D 像素坐标 相机内参、外参、投影公式 否，见《激光雷达与相机融合：从针孔模型到点云投影》
2D 像素坐标 → 检测框 + 类别 YOLOv3 + NMS 是，第十七至二十章
点 → 目标归属 框内判定 + 点数下限 + 遮挡检查 是，第二十一章
