这篇只讲 TensorFlow 的三样「周边」：可视化工具 TensorBoard、封装层 tf.contrib.layers、以及多机多卡的分布式训练。不讲张量基础类型和算子全表（那些在同目录的图与会话那篇里铺开），不讲卷积网络的原理推导，也不讲 Estimator、SavedModel、TF Serving 这些部署链路。代码全部是 TensorFlow 1.x 的静态图写法，tf.contrib 在 2.x 里已经移除，读的是机制不是 API。想先补计算图、会话、占位符的地基，翻同目录的图与会话那篇；想看 contrib.layers 改写出来的 CNN 完整训练流程，翻卷积函数与 CNN 手写数字识别那篇。

一、TensorBoard 能看什么 #

TensorBoard 常被误会成「训练监控」。它不监控，不连你的进程，也不读你的显存。它是一个纯离线的日志展示系统：训练脚本往磁盘上写文件，TensorBoard 起一个 web 服务去读那些文件，然后画图给你看。

这个链条只有两步，但两步之间靠的是磁盘上的一个文件，不是内存里的对象。链条断开的地方九成在文件路径上，不在代码逻辑上。

1.1 事件文件是唯一的数据源 #

训练时你调 tf.summary.FileWriter(logdir)，它会在 logdir 下创建一个子目录，并在里面新建一个文件名长这样的文件：

text
events.out.tfevents.1524035176.DESKTOP-XXXX.12345

名字里依次是：固定前缀 events.out.tfevents、写入时的 Unix 时间戳、主机名、进程号。同一个 logdir 下可以存在多个事件文件，TensorBoard 会把它们全部读进来，按时间轴拼在一起。

文件内容是 protobuf 序列化的 Event 记录，一条记录一行，追加写。每条 Event 里装着 wall_time（写入时刻）、step（全局步数），以及一个 summary 字段——真正的数据就在 summary.value 里，按 tag 分组。

用 strings 都能看出个轮廓：

bash
strings events.out.tfevents.1524035176.DESKTOP-XXXX.12345 | head -40

你会看到 loss_function、pred 这些你自己起的 tag 名字，夹在一堆二进制里。这就是 TensorBoard 的全部家当。

它带来两个直接后果。

第一，训练脚本写完之后可以直接关掉，TensorBoard 照样能看历史。第二，训练进程崩了，已经写进去的那部分照样在。日志是落盘的，不依赖进程存活。

1.2 面板清单 #

TensorBoard 的顶层标签页跟着 TensorFlow 版本变。1.x 时代常见的有这些：

面板 英文名 读的事件类型 看什么
标量 SCALARS simple_value 损失、准确率、学习率随 step 的曲线
图像 IMAGES image 输入样本、卷积核、生成样本的可视化
音频 AUDIO audio 语音任务的波形与频谱
直方图 HISTOGRAMS histo 权重、偏置、梯度的分布随训练的变化
分布 DISTRIBUTIONS histo 同上，换成百分位堆叠视图
计算图 GRAPHS 图定义（GraphDef） 节点结构、命名空间分组、设备分配
嵌入向量 EMBEDDINGS tensor + projector 配置 高维向量降维后的散点，可交互
文本 TEXT tensor（string） 样本文本、预测结果对照
PR 曲线 PR CURVES pr_curves 精确率召回率曲线

一张 summary 记录落到哪个面板，由写入时用的 API 决定，不由 tag 名字决定。你写 tf.summary.scalar('foo', x)，它进 SCALARS；你写 tf.summary.histogram('foo', x) 同名 tag，它进 HISTOGRAMS。两个面板可以同 tag，互不冲突。

1.3 启动与路径对应 #

启动命令只有一个关键参数：

bash
tensorboard --logdir=F:\python\LinearRegression\summary_log

--logdir 指向的是事件文件所在的那一层，或其任意祖先目录。指向祖先时，TensorBoard 会递归扫子目录，每个含事件文件的子目录被当成一个独立的 run，在左侧列出来。

这条规则解释了两类常见事故。

一是指错了层级，指到了事件文件的父目录的父目录的父目录，TensorBoard 递归扫到几十个不相关的 run，图上一堆颜色，你找不到自己的曲线。那就把 --logdir 精确到写日志的那一层。

二是指向了一个不存在的目录，或者拼错了盘符大小写。Windows 上大小写不敏感，但盘符写错就直接空。表现是面板全空，一个 run 都不列。

默认端口 6006，被占用就换：

bash
tensorboard --logdir=./summary_log --port=6007 --host=127.0.0.1

浏览器打开 http://127.0.0.1:6006。这个地址只是本机回环，别人要访问得把 --host 改成 0.0.0.0 并且放行防火墙。

1.4 「看不到数据」的排查顺序 #

按这个顺序过，基本能定位。

现象 先查什么 判定
一个 run 都没有 --logdir 路径写错没 在命令行 dir 一下该目录，看有没有 events.out.tfevents.*
有 run，面板全空 有没有真的调 add_summary merge_all 只造了一个 op，不 sess.run 它就什么都不写
有标量没图像 图像是否被 merge_all 收进去 merge_all 只收集默认集合里的 summary
曲线只画了一个点 step 参数是否一直传同一个值 add_summary(str, epoch) 的第二参就是横轴
训练完了才有内容 写缓冲没刷 进程正常退出会 flush，中途 kill 会丢尾部
面板有但图结构没显示 建 FileWriter 时传没传 sess.graph FileWriter(path) 不带第二参就只有标量

最隐蔽的是第三行。tf.summary.merge_all() 会去 tf.GraphKeys.SUMMARIES 这个集合里把已经构造好的 summary op 合并成一个。它不检查你有没有执行过它们，也不管你在 merge 之后又新建了什么。所以写法必须一致：先建 summary op，再 merge，最后每次 sess.run(merged)。

还有一类：换了个 logdir 名字，但浏览器缓存着旧的。Ctrl+F5 硬刷一次，或者在 TensorBoard 里把 run 全部取消勾选再勾回来。

二、标量、图像、直方图与计算图 #

2.1 五个 API 的分工 #

TensorFlow 1.x 提供的 summary 写入口子，常用的就这几个：

  • tf.summary.scalar(tags, values, collections=None, name=None)：把单个标量值写进 summary，输出 simple_value 类型的 protobuf。损失、准确率用它。
  • tf.summary.histogram(tag, values, collections=None, name=None)：把张量 values 的全部元素做直方图统计，输出带直方图的 protobuf。权重、偏置、梯度用它。
  • tf.summary.image(tag, tensor, max_images=3, collections=None, name=None)：把 4-D 张量按切片转成图片，最多取 max_images 张。输入样本、卷积核用它。
  • tf.summary.merge_all(inputs, collections=None, name=None)：把 tf.GraphKeys.SUMMARIES 集合里所有 summary op 合并成一个 op，一次 sess.run 全部产出。
  • tf.summary.FileWriter：写文件的对象。它的方法 add_summary()、add_session_log()、add_event()、add_graph() 负责把 protobuf 落到磁盘。

FileWriter 才是唯一碰磁盘的角色。前面四个 API 只在图里造 op，产出的是内存里的 protobuf 字符串，不落盘。

2.2 线性回归加上 TensorBoard #

拿线性回归做样本，全流程跑一遍。数据是 y = 2x 加一点高斯噪声。

python
import tensorflow as tf
import numpy as np
import os
import matplotlib.pyplot as plt

n_train = 100
train_x = np.linspace(-1, 1, n_train).reshape(n_train, 1)
train_y = 2 * train_x + np.random.normal(loc=0.0, scale=0.3, size=[n_train, 1])

plt.figure()
plt.plot(train_x, train_y, 'ro', label='y=2x')
plt.legend()
plt.show()

搭模型。占位符、两个参数、前向结构：

python
input_x = tf.placeholder(dtype=tf.float32)
input_y = tf.placeholder(dtype=tf.float32)

w = tf.Variable(tf.truncated_normal(shape=[1], mean=0.0, stddev=1), name='w')
b = tf.Variable(tf.truncated_normal(shape=[1], mean=0.0, stddev=1), name='b')

pred = tf.multiply(w, input_x) + b

tf.summary.histogram('pred', pred)

tf.summary.histogram('pred', pred) 这行的位置很关键。它必须在 pred 定义之后、在 merge_all 之前。放在 pred 之前会拿到未定义的名字，放在 merge_all 之后则那个 op 根本不会被合并进去。

反传部分：

python
cost = tf.reduce_mean(tf.square(input_y - pred))

tf.summary.scalar('loss_function', cost)

train = tf.train.GradientDescentOptimizer(learning_rate=0.001).minimize(cost)

到这里，图里已经有两个 summary op，一个 histogram 一个 scalar，都在 GraphKeys.SUMMARIES 集合里躺着。

迭代与写盘：

python
training_epochs = 200
display_step = 20

savedir = './LinearRegression'

with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())

    merged_summary_op = tf.summary.merge_all()

    summary_writer = tf.summary.FileWriter(
        os.path.join(savedir, 'summary_log'), sess.graph)

    plotdata = {'batch_size': [], 'loss': []}

    for epoch in range(training_epochs):
        for (x, y) in zip(train_x, train_y):
            sess.run(train, feed_dict={input_x: x, input_y: y})

        summary_str = sess.run(merged_summary_op,
                               feed_dict={input_x: x, input_y: y})
        summary_writer.add_summary(summary_str, epoch)

    print('Finished!')
    print('cost {0}  w {1}   b  {2}'.format(
        sess.run(cost, feed_dict={input_x: train_x, input_y: train_y}),
        sess.run(w), sess.run(b)))

    test_x = [2, 4, 5, 7]
    test_y = sess.run(pred, feed_dict={input_x: test_x})
    print('prediction  ', test_y)

四件事按顺序发生：merge_all 造合并 op，FileWriter 建文件并把 sess.graph 的 GraphDef 写进去，循环里 sess.run(merged_summary_op) 产出 protobuf 串，add_summary(串, epoch) 追加一条事件记录。

add_summary 的第二个参数 epoch 就是面板上的横轴坐标。传 epoch 得到 200 个点；传固定值 0，200 条记录全叠在横轴同一个位置上，面板看起来只有一个点。

最后的预测与画图：

python
    plt.figure(figsize=(4.2 * 2, 3.2 * 1))
    plt.plot(train_x, train_y, 'ro', label='Original data')
    plt.plot(train_x, sess.run(w) * train_x + sess.run(b), label='Estimate data')
    plt.legend()
    plt.show()

跑完，./LinearRegression/summary_log 下就出现事件文件。命令行启动，浏览器打开 http://127.0.0.1:6006：

text
tensorboard --logdir F:\python\LinearRegression\summary_log

--logdir 换成你自己的绝对路径。启动之前把当前目录切到 summary 日志的上级，这一步在老版本的 TensorBoard 里是必须的，新版本宽容一些，但照做不亏。

2.3 SCALARS 面板的几个开关 #

点开 SCALARS，左侧列出你在程序里起的 tag，这里是 loss_function，点它，右侧出曲线。

面板左上有三样东西值得动：

Smoothing 滚动条，对曲线做指数滑动平均，只改显示不改数据。原始曲线抖得厉害时拉一拉能看出趋势，拉过头会掩盖真实波动。

Show data download links，勾上之后每条曲线右边出现下载链接，能导出 CSV。写论文、写周报要原始数字时用它。

Ignore outliers in chart scaling，勾上会剔除极值，避免一个 NaN 或者异常大的点把纵轴拉伸到看不见主曲线。

再往下勾选 Wall time 能把横轴从 step 换成真实时间。想看「这一版跑了多久」而不是「跑了多少步」时切换。

2.4 HISTOGRAMS 与 DISTRIBUTIONS #

程序里 tf.summary.histogram('pred', pred) 把预测值以直方图形式记下来，去 HISTOGRAMS 标签能看到。

它画的是随时间变化的分布，不是某一时刻的分布。横轴是值，纵轴是 step，颜色深浅是频次。一次训练下来，你能看到分布怎么从初始的随机宽峰慢慢收窄、平移。

DISTRIBUTIONS 是同一份数据的另一种画法：把每个 step 的直方图压成几条百分位线（最大、93%、84%、69%、50%、31%、16%、7%、最小），纵轴是值，横轴是 step。看分布整体漂移比 HISTOGRAMS 清楚。

两者读的是同一批 histo 类型记录，切哪个面板都行。

max_outputs 默认只保留一定数量的分桶，数据量太大时 TensorFlow 会做等频压缩，你看不到精确的桶边界。这对观察趋势没影响，对精确统计有影响。

2.5 IMAGES 面板的坑 #

tf.summary.image 对输入张量的形状有硬要求：必须是 4-D，[batch, height, width, channels]，且 channels 是 1、3 或 4。

channels=1 按灰度处理，channels=3 按 RGB，channels=4 按 RGBA。传 2 通道会直接抛形状错误。

常见需求是看卷积核。卷积核的形状是 [kh, kw, in_ch, out_ch]，不能直接喂给 summary.image，要先把 in_ch 折进 height 或 width：

python
def put_kernels_on_grid(kernel, grid_y, grid_x, pad=1):
    """把 [kh, kw, in_ch, out_ch] 的卷积核拼成一张大图"""
    kh, kw, in_ch, out_ch = kernel.get_shape().as_list()
    assert out_ch == grid_y * grid_x

    kernel = tf.transpose(kernel, [3, 0, 1, 2])
    kernel = tf.reshape(kernel, [out_ch, kh, kw, in_ch])

    # 转成 [out_ch, kh, kw, 3]，灰度复制三份
    if in_ch == 1:
        kernel = tf.tile(kernel, [1, 1, 1, 3])

    # 归一化到 [0,1]，方便显示
    kernel = (kernel - tf.reduce_min(kernel)) / (
        tf.reduce_max(kernel) - tf.reduce_min(kernel) + 1e-8)

    rows = []
    for i in range(grid_y):
        row = tf.concat([kernel[i * grid_x + j]
                         for j in range(grid_x)], axis=1)
        rows.append(row)
    return tf.concat(rows, axis=0)

拼好之后 tf.expand_dims(grid, 0) 补上 batch 维，再喂给 summary.image。

还有一个坑：喂进去的张量必须是 float32 且在 [0,1]，或者 uint8 在 [0,255]。范围超了会被截断成纯白或纯黑，你看到的是一片白，以为是没写进去。

2.6 GRAPHS 面板 #

FileWriter 的第二个参数 sess.graph 就是图结构的来源。它把 GraphDef 序列化后作为一条 Event 写进事件文件，TensorBoard 读出来渲染成节点图。

打开 GRAPHS，看到的是带 tf.name_scope 折叠的方框。每个方框是一个命名空间，点开才展开内部节点。框上的数字是参数量或张量大小。

图上方有几个开关：

Trace inputs 选中某个节点后，高亮从输入到该节点的完整路径。查「这个 loss 到底由哪些 op 算出来」时用它。

Color by 可以按 device 着色，看哪些节点落在 GPU、哪些落在 CPU。分布式训练里查设备分配对不对全靠它。

Upload 可以把别人给的事件文件或 GraphDef 直接拖进来渲染，不用跑代码。

图太大时右上角有自动布局开关。手写的大模型几十上百个命名空间，不开这个会挤成一团。

命名空间决定这张图好不好读。全堆在 train、model 两个 scope 里，面板上就两个巨框，什么也看不出。按层拆成 conv1、conv2、fc1、loss、optimizer，图才有层次。

三、多变量与命名空间 #

一个模型里要盯的量从来不止一个。训练损失、验证损失、学习率、准确率、每个卷积层的权重范数——十几个标量要同时躺在同一张图里比较。这就带出两个问题：面板里的 tag 怎么组织，图里的节点怎么分组。

3.1 多个标量写进同一张图 #

最直接的做法是给每个量单独起 tag：

python
tf.summary.scalar('loss/train', train_cost)
tf.summary.scalar('loss/valid', valid_cost)
tf.summary.scalar('lr', learning_rate)
tf.summary.scalar('accuracy', accuracy)

tag 里的斜杠有实际作用。TensorBoard 按 / 做层级折叠，左侧列表会变成树状：

text
loss
  ├─ train
  └─ valid
lr
accuracy

量一多，没有这层折叠就得在一长串平铺名字里翻。

tf.summary.merge_all() 会把这些全合并。它返回的 op 一次 sess.run 产出全部 summary 串，你在训练循环里只调一次就行。

代价是每步都算全部。验证集的损失如果挂在另一个占位符上，每步都喂一遍验证数据纯属浪费。这时候用分组：

python
train_summaries = tf.summary.merge(
    [s for s in tf.get_collection(tf.GraphKeys.SUMMARIES)
     if 'loss/train' in s.name or 'lr' in s.name])
valid_summaries = tf.summary.merge(
    [s for s in tf.get_collection(tf.GraphKeys.SUMMARIES)
     if 'loss/valid' in s.name])

tf.summary.merge([...]) 只合并你列的这些。训练步里跑 train_summaries，每 N 步跑一次 valid_summaries。

更干净的做法是给不同用途的 summary 挂不同集合：

python
tf.summary.scalar('loss/valid', valid_cost, collections=['valid'])
valid_summaries = tf.summary.merge_all(key='valid')

collections=['valid'] 让它不进默认的 SUMMARIES 集合，merge_all(key='valid') 单独取。默认集合里就干净了，merge_all() 拉不到它。

3.2 name_scope 改变 tag 前缀 #

写在 tf.name_scope 里，summary 的 tag 会自动带上作用域前缀：

python
with tf.name_scope('train'):
    tf.summary.scalar('loss', cost)

with tf.name_scope('valid'):
    tf.summary.scalar('loss', cost)

产出两个 tag：train/loss 和 valid/loss。同一个名字 loss 在面板里分成了两条曲线，不会打架。

这也顺带解决了图的可读性。name_scope 里的所有 op 名字都带前缀，GRAPHS 面板里它们被折叠进同一个方框。

嵌套是支持的：

python
with tf.name_scope('model'):
    with tf.name_scope('conv1'):
        h = tf.nn.conv2d(x, W, strides=[1, 1, 1, 1], padding='SAME')

节点全名是 model/conv1/Conv2D。面板里就是 model 框套 conv1 框。

name_scope 和 variable_scope 的分工要分清。name_scope 只影响 op 和 tf.Variable 的名字，不影响 tf.get_variable。下一章细说。

3.3 张量的阶、形状、类型 #

要写 summary，得先知道手里的东西是什么形状。tf.summary.image 要 4-D，tf.summary.scalar 要标量，传错形状报的错很难读。

TensorFlow 用 tensor 表示所有数据，计算图里节点间传的都是它。一个 tensor 有三个属性：静态类型、阶（rank）、形状（shape）。

阶是维度的数量，和矩阵的阶不是一回事：

text
t = [[1, 2, 3], [4, 5, 6], [7, 8, 9]]

这个 3×3 的嵌套列表，作为张量是 2 阶，因为它有两层中括号。作为矩阵，习惯上叫 3 阶方阵。两套术语撞车，写代码时以 rank 为准。

阶 数学对象 形状示例 访问方式
0 标量 [] t
1 向量 [3] t[i]
2 矩阵 [3, 3] t[i, j]
3 三阶张量 [2, 3, 4] t[i, j, k]
n n 阶张量 [d1, ..., dn] t[i1, ..., in]

形状用 Python 的 int 列表或元组表示，也可以用 TensorShape 类。[None, 24, 24, 3] 里的 None 表示这一维在构图时未知，运行时才确定——batch 维一般就是 None。

数据类型决定了这张量能不能进 summary：

TensorFlow 类型 Python 类型 说明
tf.float32 float 最常用，scalar 和 image 都要它
tf.float64 float 双精度，写 summary 前要转
tf.int32 int 索引、标签
tf.int64 int 大整数索引
tf.uint8 int 图像像素，summary.image 可直接吃
tf.string bytes 文件名、文本，summary.text 用
tf.bool bool 条件判断

四、共享变量与变量作用域 #

4.1 问题的起点 #

tf.Variable 每调一次就新建一个变量。这件事在简单的线性回归里没影响，因为你就建一次。但在某些结构里会直接把模型做错。

典型场景是对抗网络：生成器和判别器要一起训，两边都要用到对方的变量。另一个是 RNN：同一组权重在时间步上反复使用，循环 20 步，权重只能有一份。

假如你写：

python
biases = tf.Variable(tf.zeros(shape=[2]), name='biases')

这行执行一次，图里多一个 biases:0。再执行一次，图里多一个 biases_1:0。TensorFlow 遇到同名变量会自动追加 _n 后缀，并且第二个变量是全新的变量，和第一个没有任何关系。

你以为在复用，实际上在新建。

python
var1 = tf.Variable(1.0, name='first_var', dtype=tf.float32)
print('var1:', var1.name)
var1 = tf.Variable(2.0, name='first_var', dtype=tf.float32)
print('var1:', var1.name)
var2 = tf.Variable(3.0, dtype=tf.float32)
print('var2:', var2.name)
var2 = tf.Variable(4.0, dtype=tf.float32)
print('var2:', var2.name)

with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())
    print('var1=', var1.eval())
    print('var2=', var2.eval())

输出里 var1 第一次是 first_var:0，第二次是 first_var_1:0。var2 第一次是 Variable:0，第二次是 Variable_1:0。

内存里躺着四个变量。Python 变量名 var1 被第二次赋值覆盖，指向后者，所以打印出来是 2.0。前一个变量还在图里活着，只是没有 Python 变量引用它——这种变量是纯粹的浪费，还会被 global_variables_initializer 一起初始化，占显存。

没指定 name 的时候系统自动起名 Variable、Variable_1、Variable_2，全靠计数器。这类名字在图里毫无意义，调试时根本认不出是哪个。

4.2 get_variable 的唯一性 #

tf.get_variable 换了一套规则：以 name 属性作为唯一标识符，不是 Python 变量名。

text
tf.get_variable(name, shape=None, dtype=None, initializer=None,
                regularizer=None, trainable=True, collections=None,
                caching_device=None, partitioner=None,
                validate_shape=True, use_resource=None,
                custom_getter=None)

同一个作用域下用同一个 name 调两次，直接报错：

python
get_var1 = tf.get_variable('first_var', shape=[1],
                           initializer=tf.constant_initializer(0.3))
print('get_var1:', get_var1.name)

get_var1 = tf.get_variable('first_var', shape=[1],
                           initializer=tf.constant_initializer(0.4))
print('get_var1:', get_var1.name)

第二行抛 Variable first_var already exists。这是设计意图，不是 bug。

注意上面这段如果跑在同一个进程里、前面已经用 tf.Variable('first_var') 建过一次，那 get_variable 拿到的名字会变成 first_var_2:0——因为 tf.Variable 占用了 first_var 和 first_var_1，get_variable 得让路。

把第二个改个名字就好了：

python
get_var1 = tf.get_variable('first_var1', shape=[1],
                           initializer=tf.constant_initializer(0.4))
print('get_var1:', get_var1.name)

with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())
    print('get_var1:', get_var1.eval())

两个变量都建成了，图里生效的是后一个，打印出来 0.4 而不是 0.3。

一个坑：get_variable 会在图里查重。在 Spyder 里反复运行同一个脚本，第二次必然报「已存在」。原因是内核没退，默认图还在。重启内核能解决，或者在脚本开头清图：

python
tf.reset_default_graph()

4.3 variable_scope 隔离同名变量 #

两个模块各要一个叫 testvar 的变量，直接 get_variable 会撞名。用作用域隔开就行：

python
with tf.variable_scope('test1'):
    var1 = tf.get_variable('testvar', shape=[2], dtype=tf.float32)

with tf.variable_scope('test2'):
    var2 = tf.get_variable('testvar', shape=[2], dtype=tf.float32)

print('var1:', var1.name)
print('var2:', var2.name)

输出 test1/testvar:0 和 test2/testvar:0。作用域名成了变量名的前缀，两个变量不同。

作用域支持嵌套：

python
with tf.variable_scope('test1'):
    var1 = tf.get_variable('testvar', shape=[2], dtype=tf.float32)

    with tf.variable_scope('test2'):
        var2 = tf.get_variable('testvar', shape=[2], dtype=tf.float32)

print('var1:', var1.name)
print('var2:', var2.name)

现在是 test1/testvar:0 和 test1/test2/testvar:0。嵌套层级直接体现在名字里。

这套前缀规则和 name_scope 是一致的，所以 GRAPHS 面板里的分组、事件文件里的 tag 前缀、变量的全名，三者对得上。整个工程的可读性就建立在这一层约定上。

4.4 reuse=True 才是共享 #

前面全是铺垫。真正实现共享变量的是 reuse 参数。

python
with tf.variable_scope('test1', reuse=True):
    var3 = tf.get_variable('testvar', shape=[2], dtype=tf.float32)

with tf.variable_scope('test2', reuse=True):
    var4 = tf.get_variable('testvar', shape=[2], dtype=tf.float32)

print('var3:', var3.name)
print('var4:', var4.name)

var3 的 name 和 var1 完全一致，var4 的和 var2 完全一致。get_variable 没有新建变量，而是去图里按名字查找已有的变量，返回同一个引用。

这就是共享：两个不同的 Python 变量名，指向同一块 GPU 内存。

实际用法是把 var1、var2 放进一个网络，var3、var4 放进另一个网络，两个网络训练时更新的都是同一份参数。RNN 的权重复用就是这么做的：

python
def rnn_cell(x, scope, reuse=None):
    with tf.variable_scope(scope, reuse=reuse):
        W = tf.get_variable('W', shape=[128, 128],
                            initializer=tf.glorot_uniform_initializer())
        U = tf.get_variable('U', shape=[128, 128],
                            initializer=tf.glorot_uniform_initializer())
        b = tf.get_variable('b', shape=[128],
                            initializer=tf.zeros_initializer())
        return tf.tanh(tf.matmul(x, W) + tf.matmul(h, U) + b)


# 第一个时间步，reuse=None，建变量
with tf.variable_scope('rnn') as scope:
    h = rnn_cell(x0, 'cell')
    scope.reuse_variables()      # 之后全部复用
    for t in range(1, timesteps):
        h = rnn_cell(xt[t], 'cell')

scope.reuse_variables() 是 with tf.variable_scope(..., reuse=True) 的另一种写法，效果一样。用它是为了省掉每步都写 reuse=True。

写错了会怎样？第一步就传 reuse=True，get_variable 找不到 rnn/cell/W，抛 Variable rnn/cell/W does not exist。反过来，第二步忘了 reuse=True，抛 already exists。两个方向的错都会立刻炸，不会静默出错，这是好事。

reuse 有三个取值：None（默认，第一次建，第二次报错）、True（只查不建）、tf.AUTO_REUSE（不存在就建，存在就复用）。AUTO_REUSE 用起来省事，代价是拼错名字时它会静默新建一个变量，你很难发现。生产代码里少用它。

4.5 初始化器的继承 #

作用域还能带初始化器，子作用域会继承：

python
with tf.variable_scope('test3', initializer=tf.constant_initializer(0.4)):
    var5 = tf.get_variable('testvar', shape=[2], dtype=tf.float32)

    with tf.variable_scope('test4'):
        var6 = tf.get_variable('testvar', shape=[2], dtype=tf.float32)
        var7 = tf.get_variable('var7', shape=[2], dtype=tf.float32,
                               initializer=tf.constant_initializer(0.3))

with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())
    print('var5:', var5.eval())
    print('var6:', var6.eval())
    print('var7:', var7.eval())

结果：

变量 所在作用域 自己的初始化器 结果
var5 test3 无 0.4，继承 test3
var6 test3/test4 无 0.4，逐层继承到 test3
var7 test3/test4 0.3 0.3，自己的覆盖继承值

优先级的规则很直白：自己传了 initializer 就用自己，没传就往上一层找，一直找到图级默认（glorot_uniform 对权重、zeros 对偏置，靠 get_variable 内建的推断）。

tf.constant_initializer 生成常量张量作为初始值。除了它，常用还有 tf.zeros_initializer、tf.ones_initializer、tf.random_normal_initializer、tf.truncated_normal_initializer、tf.glorot_uniform_initializer（即 Xavier）、tf.glorot_normal_initializer、tf.he_initializer。

4.6 作用域跳出外层限制 #

用 with ... as 拿到作用域对象，可以在别处重新进入它，而且不受当前外层作用域约束：

python
with tf.variable_scope('scope1') as sp:
    var1 = tf.get_variable('v', shape=[1])

print('sp', sp.name)
print('var1:', var1.name)

with tf.variable_scope('scope2'):
    var2 = tf.get_variable('v', shape=[1])

    with tf.variable_scope(sp) as sp1:
        var3 = tf.get_variable('v3', shape=[1])

print('sp1:', sp1.name)
print('var2:', var2.name)
print('var3:', var3.name)

看 var3 的输出。它写在第 scope2 里面，但名字是 scope1/v3:0，不是 scope2/scope1/v3:0。

原因：sp 是一个已经创建好的作用域对象，scope1 和 scope2 是并列关系，sp 没有父作用域。重新进入 sp 时，作用域链被整个换掉，scope2 不再参与前缀拼接。

这个行为在模块化封装里很有用：函数内部拿到调用方传进来的 scope 对象，无论被谁调，前缀都是固定的。

sp1 是重新进入时拿到的对象，它的 name 打印出来是 scope1，和 sp 一样。

4.7 name_scope 与 variable_scope 的分界 #

这两个作用域容易混。核心差别只有一条：name_scope 管不住 get_variable。

python
with tf.variable_scope('scope'):
    with tf.name_scope('bar'):
        t = tf.get_variable('t', shape=[1])
        x = 1.0 + t
        y = tf.Variable('y')

输出：

对象 类型 名字 受谁约束
t get_variable scope/t:0 只有 variable_scope
x op scope/bar/add:0 两个都管
y Variable scope/bar/y:0 两个都管

t 的名字里没有 bar。get_variable 只认 variable_scope 的栈，name_scope 在它眼里不存在。

x 是一个 op。op 可以理解成模型里的中间节点，由源节点（常量、变量）计算得来，是网络结构本身。x.op.name 是 scope/bar/add，tf.Variable 和 op 都吃 name_scope 前缀。

这个差别解释了一个常见困惑：为什么 name_scope 改了之后，GRAPHS 面板里 op 分组变了，但变量名没变。因为变量名归 variable_scope 管。

用哪个？想控制面板分组和 op 名，用 name_scope；想控制变量名和共享，用 variable_scope。工程里两个一起用，一层 variable_scope 套一层 name_scope，代码结构就对齐了。

4.8 空字符串回顶层 #

python
with tf.name_scope(''):
    ...

name_scope 收到空字符串，栈被清空，作用域回到最顶层。

python
with tf.variable_scope(''):
    ...

variable_scope 收到空字符串，是把它当成一个名字为空的普通作用域处理，并不是回顶层。前缀里会留下一个空段。

这个不对称在调试时坑过不少人。想让 variable_scope 回顶层，得用 tf.variable_scope(tf.get_variable_scope(), reuse=...) 显式指定，或者干脆把代码结构拆开，别嵌套。

4.9 变量共享在 TensorBoard 上的表现 #

共享变量在图里只出现一次，所以 GRAPHS 面板里 rnn/cell/W 只有一个节点。如果你在面板上看到 rnn/cell/W、rnn/cell_1/W、rnn/cell_2/W 三个节点，那就是时间步循环里每次都建了新变量，reuse 没生效。

这个检查比读代码快。训练跑起来后开 GRAPHS，按节点数对一对，一眼能看出复制了多少份参数。

变量数量还能从另一处验证：

python
for v in tf.global_variables():
    print(v.name, v.get_shape())

参数总量对不上预期时，先看这份清单有没有重复项。

4.10 TF 2.x 里的对应做法 #

上面整套机制在 2.x 里不需要手写了。tf.keras.layers 的每个层对象自己管理变量，同一个层对象被调用多次，用的是同一组权重：

python
cell = tf.keras.layers.Dense(128)

h = cell(x0)
for t in range(1, timesteps):
    h = cell(xt[t])

cell 在第一次调用时才建权重，之后每次调用复用。没有 reuse 参数，没有作用域嵌套，靠 Python 对象身份。

要手动共享权重，把同一个层对象传给两处就行：

python
shared = tf.keras.layers.Dense(64)

out_a = shared(a)
out_b = shared(b)

out_a 和 out_b 用的是同一个 kernel。

五、图操作与图的切换 #

TF 1.x 里「图」是显式对象。默认有一个全局默认图，所有 tf.Variable、tf.constant 都加进它。想建第二张图，就得显式指定。

为什么要多张图 #

三种场景会需要：

  • 同一个进程里跑两套独立模型（比如一个训练、一个推理），只能各用各的图
  • 反复建图导致节点爆炸（每轮循环都 tf.Variable，图会长得失控）
  • 调试时想对比两个结构

建图与切换 #

python
import tensorflow as tf

g1 = tf.Graph()
with g1.as_default():
    v1 = tf.Variable(1.0, name='v')

g2 = tf.Graph()
with g2.as_default():
    v2 = tf.Variable(2.0, name='v')

with tf.Session(graph=g1) as sess:
    sess.run(tf.global_variables_initializer())
    print(sess.run(v1))        # 1.0

with tf.Session(graph=g2) as sess:
    sess.run(tf.global_variables_initializer())
    print(sess.run(v2))        # 2.0

两次都定义了叫 v 的变量，但它们在两张不同的图里，互不干扰。这是命名空间隔离的作用。

会话必须绑定图 #

tf.Session(graph=g) 这一步容易漏。如果只写 tf.Session()，它绑定默认图，而你要跑的节点在 g1 里，会直接报 ValueError: Tensor must be from the same graph。

默认图的陷阱 #

python
with tf.Graph().as_default():
    # 这段里的所有节点都在新图里
    ...
# 出了 with 块，又回到全局默认图

不进入任何 with 块时，tf.Variable 会加到全局默认图。在循环里反复建模却不换图，节点会累积成几万个，显存和速度都会崩。这是 TF 1.x 里最常见的性能陷阱。

六、tf.contrib.layers 的封装 #

tf.contrib 是 TF 1.x 的「实验性功能」命名空间，其中 tf.contrib.layers 是一组高层封装——把「建权重、加偏置、接激活、做 BN」这一串动作压成一次调用。

它解决什么问题 #

裸写一个全连接层：

python
with tf.variable_scope('fc1'):
    W = tf.get_variable('W', [1024, 512],
                        initializer=tf.truncated_normal_initializer(stddev=0.1))
    b = tf.get_variable('b', [512], initializer=tf.zeros_initializer())
    h = tf.nn.relu(tf.matmul(x, W) + b)

用 contrib.layers：

python
h = tf.contrib.layers.fully_connected(x, 512, activation_fn=tf.nn.relu)

一行替掉五行。权重初始化、变量作用域、激活函数都包进去了。

常用函数 #

函数 作用
fully_connected 全连接层
conv2d 二维卷积
max_pool2d / avg_pool2d 池化
batch_norm 批量归一化
dropout Dropout
flatten 展平
l2_regularizer L2 正则项

改写 CIFAR-10 分类 #

原来的写法要手工建三组卷积+池化，用 contrib.layers 可以写成：

python
def cnn(x):
    x = tf.reshape(x, [-1, 32, 32, 3])
    net = tf.contrib.layers.conv2d(x, 64, [5, 5], padding='SAME',
                                   activation_fn=tf.nn.relu, scope='conv1')
    net = tf.contrib.layers.max_pool2d(net, [2, 2], scope='pool1')
    net = tf.contrib.layers.conv2d(net, 128, [5, 5], padding='SAME',
                                   activation_fn=tf.nn.relu, scope='conv2')
    net = tf.contrib.layers.max_pool2d(net, [2, 2], scope='pool2')
    net = tf.contrib.layers.flatten(net, scope='flatten')
    net = tf.contrib.layers.fully_connected(net, 1024,
                                            activation_fn=tf.nn.relu, scope='fc1')
    net = tf.contrib.layers.dropout(net, keep_prob=0.5, scope='drop')
    logits = tf.contrib.layers.fully_connected(net, 10,
                                               activation_fn=None, scope='logits')
    return logits

每层 scope= 保证变量名不冲突——这相当于自动管了 tf.variable_scope。

它的历史结局 #

tf.contrib 在 TF 2.0 被整体移除。理由是「实验性代码没人维护、接口不稳定、拖累主库」。对应的功能迁到了 tf.keras.layers 和 tf.nn。

看这段代码的意义不在于用它，而在于理解「高层封装」这个思路——tf.keras.layers 就是它的继任者，把「建层」这件事做得更彻底。

七、为什么要分布式训练 #

单个 GPU 训 ImageNet 上的 ResNet 要几天，用 8 张卡能压到几小时。分布式训练要解决的就是「算力不够」这一个问题。

但带来一串新问题：参数怎么同步、梯度怎么汇总、某一台挂了怎么办。

两种并行的选择 #

数据并行（Data Parallelism）：每张卡存一份完整模型，各自吃不同批次的数据，算出的梯度再汇总。

GPU0: batch0 → 梯度g0
GPU1: batch1 → 梯度g1     → 平均 → 更新参数 → 广播回所有卡
GPU2: batch2 → 梯度g2

模型并行（Model Parallelism）：一个模型太大装不进单卡，把它按层切开分到不同卡上。

GPU0: 第 1~10 层    →    GPU1: 第 11~20 层    →    GPU2: 第 21~30 层
维度 数据并行 模型并行
适用 模型能装进单卡 模型装不进单卡
通信量 大（每步同步全部梯度） 相对小（只传层间激活）
实现难度 低，主流框架都支持 高，要手工切分
实际使用 绝大多数场景 只有超大模型

八、参数服务器与 worker #

TF 1.x 的分布式用参数服务器（Parameter Server, PS）架构。

角色分工 #

角色 职责
chief 主 worker，负责保存 checkpoint、写 TensorBoard
worker 算梯度，推给 PS
ps 保存全局参数，收到梯度后更新

一次训练循环：

  1. worker 从 ps 拉最新参数
  2. 用本地 batch 算梯度
  3. 把梯度推给 ps
  4. ps 更新参数
  5. 下一轮重复

同步更新与异步更新 #

同步（Synchronous）：所有 worker 算完这一轮，等齐了再一起更新。收敛稳定，但受最慢的卡拖累。

异步（Asynchronous）：谁先算完谁就更新，不等别人。吞吐高，但会用到过期的参数（staleness），收敛不如同步稳。

实践中同步更常用，因为现在 GPU 之间通信够快，等待代价可以接受。

集群配置 #

先定义集群，再给每台机器指定角色：

python
cluster = tf.train.ClusterSpec({
    'ps': ['192.168.1.10:2222'],
    'worker': ['192.168.1.11:2222', '192.168.1.12:2222']
})

# 在 worker 0 上
server = tf.train.Server(cluster, job_name='worker', task_index=0)

# 在 ps 上
server = tf.train.Server(cluster, job_name='ps', task_index=0)
server.join()

server.join() 是让 ps 进程常驻等待——ps 不退出，worker 才能一直找到它。

用 tf.device 指定计算位置 #

python
with tf.device('/job:ps/task:0'):
    W = tf.get_variable('W', [784, 256], ...)
    b = tf.get_variable('b', [256], ...)

with tf.device('/job:worker/task:0'):
    h = tf.matmul(x, W) + b

/job: 后面跟角色、/task: 后面跟编号。变量放 ps，计算放 worker——这是数据并行的标准布局。

数据怎么分 #

每个 worker 只吃自己那一份：

python
if FLAGS.job_name == 'worker':
    batch = dataset.shard(num_workers, FLAGS.task_index)

shard(N, i) 表示「把数据切成 N 份，取第 i 份」。不切数据，所有 worker 用同一批，等于白算。

九、多卡训练的实践 #

单机多卡是最常见的场景。TF 1.x 有两种做法。

手工切分（tower 模式） #

把同一个模型在每张卡上建一遍，共享变量，梯度取平均：

python
tower_grads = []
for i in range(num_gpus):
    with tf.device('/gpu:%d' % i):
        with tf.variable_scope(tf.get_variable_scope(), reuse=(i > 0)):
            loss = build_model(x_batch[i], y_batch[i])
        grads = tf.gradients(loss, tf.trainable_variables())
        tower_grads.append(grads)

# 平均梯度
avg_grads = average_gradients(tower_grads)
train_op = optimizer.apply_gradients(zip(avg_grads, tf.trainable_variables()))

两个关键点：

  • reuse=(i > 0)：第一张卡建变量，后面的复用。漏了会建 N 份独立权重，等于在训 N 个不同模型
  • average_gradients：把各卡的梯度汇总。不平均的话，等价于只用最后一张卡的梯度

用 estimator 封装 #

TF 1.x 后期的 tf.estimator 把上面这些包起来了：

python
strategy = tf.distribute.MirroredStrategy()
with strategy.scope():
    model = build_model()
model.compile(...)
model.fit(...)

MirroredStrategy 自动处理变量复制、梯度同步、参数广播。TF 2.x 一律用这套，不再手写 tower。

十、易错点速查 #

现象 原因 处理
TensorBoard 打开是空白 logdir 指错了，或者 writer 没 flush 确认路径一致，writer.flush()，等几秒再刷新页面
TensorBoard 只有 loss 没有图 忘了写 graph FileWriter(logdir, sess.graph)
多个 scope 里变量重名报错 没用 reuse=True 显式声明复用，或者换 scope 名
Tensor must be from the same graph Session 绑定的图和节点所在的图不一致 tf.Session(graph=g) 明确指定
循环建模显存暴涨 反复往默认图里加节点 每轮 tf.Graph() 新建图，或用 tf.reset_default_graph()
分布式连不上 ps 端口没开或被防火墙拦 先 telnet ip port 确认通，检查 server.join() 是否在跑
worker 一直等不到 有的 worker 没启动 TF 要求所有角色都上线才开跑，缺一个就全体阻塞
多卡训练比单卡还慢 通信开销超过并行收益 减小模型、增大 batch、换更快的互联（NVLink）
多卡训练 loss 不降 变量没共享，训了 N 个模型 检查 reuse；或改用 strategy.scope()
所有 worker 结果一样 数据没 shard 按 task_index 切分数据
checkpoint 存不下来 只有 chief 该存，但每台都配了 saver 只在 task_index == 0 的 worker 上 saver.save
异步训练收敛震荡 staleness 太大 减小 worker 数，或用同步更新

最后压三句：

TensorBoard 看不到数据，九成是路径问题。 它不是「连上了就能看」，而是去 logdir 里读事件文件。先 ls 那个目录有没有 events.out.tfevents.*。

分布式训练的所有麻烦都来自「等待」。 同步要等最慢的卡，异步要处理过期参数。想清楚能接受哪种代价，再选架构。

单机多卡优先用 MirroredStrategy，别手写 tower。 手工切分容易漏 reuse、漏梯度平均，每漏一处就是一个静默的错——不会报错，只会训出个坏模型。

1.x 的 tf.variable_scope + reuse=True 是显式声明，2.x 的对象复用是隐式绑定。后者不容易写错，但你要跨模块传递层对象，不像作用域那样能靠字符串名字约定。两种范式各有取舍，理解共享的动机比记住 API 更重要：同一份参数被多处计算使用时，它只能有一份存储。
