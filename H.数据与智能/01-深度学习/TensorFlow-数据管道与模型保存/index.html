一、数据管道为什么重要 #

先把一笔账算清楚，后面所有的设计都是为了这笔账。

一块 GPU 算一个 batch，几十毫秒。比如 ResNet-50，batch=256，224×224 的图，前向加反向在单卡上是几十毫秒的量级。

同一批数据从磁盘读出来，再解码成张量，要多久？

  • 从机械盘顺序读 256 张 JPEG，几百毫秒起步。
  • 每张图 decode 成 uint8 数组，又是一笔。JPEG 解码在 CPU 上不是免费的，256 张图几十毫秒到上百毫秒。
  • 再加上 resize、翻转、归一化，又是一笔。

也就是说，如果读数据和算梯度串行，GPU 有一大半时间在空转。你花钱买的算力，在等硬盘。

这就是数据管道要解决的问题：IO 跟不上计算。

解决的思路只有一句：让「读数据」和「算梯度」并行起来。读数据的线程一直往内存队列里塞，算梯度的线程一直从里面取。GPU 要数据的时候，队列里有货，不用等。

text
磁盘 / 分布式文件系统
        │
        │  读取线程（可以多个）
        ▼
   文件名队列（放的是文件名，不是数据）
        │
        │  reader 读文件 + 解码
        ▼
   内存队列（放的是解码后的样本）
        │
        │  组 batch
        ▼
   批次队列 ────► 主线程：前向、反向、更新参数

这张图是 TF 1.x 的经典结构，三个队列一条链。文件名队列管 epoch，内存队列管缓冲，批次队列管形状。

TF 2.x 把这一整套换成了 tf.data，但思想一模一样：shuffle 管顺序，batch 管形状，prefetch 管并行。你理解了队列那套，tf.data 就是在看同一件事的新写法。

三种数据输入方式，先有个全景：

方式 写法 适合场景 问题
预加载 tf.constant / tf.Variable 直接存数据 数据量小，几十条到几千条 数据进了图，图会很大，保存和加载都变慢
供给 placeholder + feed_dict 调试、小批量实验、数据在 Python 侧已经算好 每个 step 都要过一遍 Python，有额外开销
文件读取 队列 / tf.data 大数据集，图片、文本、日志 代码复杂，要管线程和生命周期

选哪个不看喜好，看数据量。数据能塞进内存，预加载最省事；数据塞不进，或者要边训练边生成，就必须上管道。

有个数字可以当分界线：数据集小于几百 MB，随便怎么读都行；超过几个 GB，feed_dict 会把 CPU 吃满，训练速度掉一个档次。

二、喂数据的第一种方式：feed_dict #

先说最简单的两种，它们的问题正好解释了为什么要有管道。

预加载：把数据焊进图里 #

python
import tensorflow as tf

x1 = tf.constant([2, 3, 4])
x2 = tf.constant([4, 0, 1])

y = tf.add(x1, x2)

with tf.Session() as sess:
    print(sess.run(y))

x1、x2 是图里的常量节点，值直接写在图的定义里。会话一跑就有结果，没有任何 IO。

问题在数据量上来之后暴露：

  • 常量会被序列化进 GraphDef。几十万条样本进图，graph.pb 会膨胀到几百 MB，加载图本身就慢。
  • 每次改数据都要重建图。想换一个数据集，得改代码重新构图、重新开会话。
  • 没有任何打乱和分片能力。要自己用 Python 切好再塞进去。

所以预加载只适合一种场景：数据是你代码里写死的小表，比如做单元测试、验证一个算子的行为。

供给：placeholder 加 feed_dict #

python
import tensorflow as tf

x1 = tf.placeholder(tf.int32)
x2 = tf.placeholder(tf.int32)

# 用 python 产生数据
v1 = [2, 3, 4]
v2 = [4, 0, 1]

y = tf.add(x1, x2)

with tf.Session() as sess:
    print(sess.run(y, feed_dict={x1: v1, x2: v2}))

placeholder 是个占位符，构图的时候只有形状和类型，没有值。值在 sess.run() 时通过 feed_dict 传进去。

这套写法在训练代码里非常常见：

python
input_x = tf.placeholder(dtype=tf.float32, shape=[None, 784], name='input_x')
input_y = tf.placeholder(dtype=tf.float32, shape=[None, 10], name='input_y')

# ... 搭网络、定义 loss、定义 train_op ...

with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())
    for epoch in range(10):
        for batch_x, batch_y in make_batches(data_x, data_y, batch_size=64):
            sess.run(train_op, feed_dict={input_x: batch_x, input_y: batch_y})

它的好处很实在：

  • 数据在图外面，Python 侧想怎么处理就怎么处理，numpy、PIL、OpenCV 都能用。
  • 换数据不用改图。
  • 调 bug 的时候可以只喂一条样本，逐层看输出。

但它的开销也在这里。feed_dict 不是零成本的：

  • 每一次 sess.run()，Python 都要把 numpy 数组转成 TensorFlow 内部的 Tensor，跨语言边界做一次拷贝。
  • 这个转换在 CPU 上做，和 GPU 计算抢同一个 CPU。
  • 数据预处理（读图、解码、resize）全在 Python 主线程里，串行执行，GPU 只能干等。

小数据看不出来，数据一大就明显。你会看到一个典型现象：GPU 利用率在 30% 上下跳，top 里 python 进程的 CPU 占满一个核。

这就是为什么要往下走：把读取和解码从 Python 主线程里挪出去，交给 C++ 层的队列线程干。

一句话对比：

对比项 预加载 feed_dict 文件读取
数据在哪 图里 Python 内存 磁盘
是否走 Python 否 每个 step 都走 只在构图时走
能否打乱 自己写 自己写 队列管
多线程读 无 无 有
数据量上限 几百 MB 内存大小 磁盘大小

再补一句：TF 2.x 里 placeholder 已经从主 API 里移除了，feed_dict 只剩调试用途。但读老代码必须认识它，而且 feed_dict 的思想在 tf.data 的 from_tensor_slices 里还在——你从 numpy 灌数据进去，本质还是供给。

三、从文件读取：队列与多线程 #

数据量一大，就得让 TensorFlow 自己去读文件。这一节讲 TF 1.x 的队列机制，它是那个年代的标志性设计。

三个概念，三件东西 #

队列这套机制里只有三样东西：

概念 干什么 单独能用吗
Queue 队列本身，缓存数据的地方 能
QueueRunner 起线程，往队列里塞数据 能
Coordinator 管线程组的停止信号 能，纯 Python 线程也能用

它们经常一起出现，但拆开都能用。先分开看，再合起来看。

队列按出队规则分几种：

  • tf.FIFOQueue：先进先出。
  • tf.RandomShuffleQueue：随机顺序出队。
  • tf.PaddingFIFOQueue：按固定长度批量出队，不够的补齐。
  • tf.PriorityQueue：带优先级出队。

除了出队规则，创建和使用的方式基本一样。构造签名：

python
tf.FIFOQueue(capacity, dtypes, shapes=None, names=None,
             shared_name=None, name="fifo_queue")

capacity 是队列容量上限。到了上限，入队操作会阻塞，直到有人出队。这个阻塞是好事，它防止内存爆掉。

先看一个不涉及文件的纯队列例子，把入队出队的手感找出来：

python
import tensorflow as tf

# 一个容量为 3 的先入先出队列
q = tf.FIFOQueue(3, "float")
init = q.enqueue_many(([0.1, 0.2, 0.3],))
x = q.dequeue()
y = x + 1
q_inc = q.enqueue([y])

with tf.Session() as sess:
    sess.run(init)

    for i in range(2):
        sess.run(q_inc)

    quelen = sess.run(q.size())
    for i in range(quelen):
        print(sess.run(q.dequeue()))

跑一遍就明白：出队一个 0.1，加 1 变成 1.1，再入队。两步之后队列里是 [0.3, 1.1, 2.1]。会话保持状态，q 里的东西在 sess.run() 之间不会丢。

注意 enqueue_many、dequeue、enqueue 都是图里的操作。sess.run() 驱动它们，不是 Python 函数调用。

QueueRunner：把入队搬到别的线程 #

上面这个例子里，入队都在主线程做。文件读取的场景不行——从硬盘读一个 batch 要几百毫秒，主线程不能干这个。

QueueRunner 就是干这个的：它按 enqueue_ops 起一组线程，反复执行入队操作。

python
import tensorflow as tf

q = tf.FIFOQueue(10, "float")
counter = tf.Variable(0.0)
increment_op = tf.assign_add(counter, 1.0)
enqueue_op = q.enqueue(counter)

# 两个 op 交替，重复 2 次，一共 4 个线程
qr = tf.train.QueueRunner(q, enqueue_ops=[increment_op, enqueue_op] * 2)

with tf.Session() as sess:
    sess.run(tf.initialize_all_variables())
    enqueue_threads = qr.create_threads(sess, start=True)
    for i in range(10):
        print(sess.run(q.dequeue()))

[increment_op, enqueue_op] * 2 展开成四个 op，所以起了四个线程：两个加计数，两个入队。四个线程抢着跑，谁先谁后不确定，所以打出来的数字顺序是乱的。

这段代码能输出结果，但在 with 块结束时会报一句：

text
ERROR:tensorflow:Exception in QueueRunner: Session has been closed.

原因简单：with 块结束，会话自动关闭，而入队线程还在跑，它们拿着一个已经关掉的会话去执行 op，就报这个错。

改法一：不用 with，手动管会话。

python
sess = tf.Session()
sess.run(tf.initialize_all_variables())

enqueue_threads = qr.create_threads(sess, start=True)

for i in range(0, 10):
    print(sess.run(q.dequeue()))

会话不自动关，线程不会报错。但程序也不会退出，因为后台线程还在跑。这是个真问题，后面 Coordinator 来解决。

还有一件事值得说清楚。这个例子打印的不是 1、2、3、4 这样干净。原因是：

  • 加计数的线程一直在后台跑，counter 早就涨到几十了。
  • 入队线程跑满 10 个就阻塞（队列容量 10）。
  • 主线程消费一个，入队线程立刻补一个。

最后主线程消费完 10 个停下，其他线程继续跑。所以顺序是乱的，程序也不退出。

卡死：最典型的队列故障 #

把入队线程注释掉，程序会停在 sess.run(q.dequeue())，一动不动，不报错，不退出。

这是 TF 1.x 里最经典的故障现象。原因：图的计算要数据驱动，队列空了 dequeue 就一直等。TensorFlow 不会主动报错，因为「训练」和「读数据」本来是异步的，它没法判断你是真的没数据，还是数据在别处忙着。

现象就是进程挂在那里，CPU 占用 0，日志一个字不打。

排查顺序：

  1. 有没有调 tf.train.start_queue_runners()？没调，文件名队列就是空的。
  2. Coordinator 有没有提前 request_stop()？停了之后所有入队线程退出，dequeue 必然阻塞。
  3. num_epochs 用完了没有？epoch 走完 reader 会抛 OutOfRange，如果被吞了，主循环就在空转。
  4. 队列容量是不是设成 0 了？capacity 必须大于 0。

Coordinator：谁出事谁喊停 #

Coordinator 是个线程协调器，跟 TensorFlow 的 Queue 没有必然关系，纯 Python 线程也能用。

python
import tensorflow as tf
import threading, time

def loop(coord, id):
    t = 0
    while not coord.should_stop():
        print(id)
        time.sleep(1)
        t += 1
        # 只有 0 号线程调用 request_stop
        if t >= 2 and id == 0:
            coord.request_stop()

coord = tf.train.Coordinator()
threads = [threading.Thread(target=loop, args=(coord, i)) for i in range(10)]

for t in threads:
    t.start()
coord.join(threads)

十个线程一起跑，每个线程每轮检查 coord.should_stop()。0 号线程跑两轮之后调 request_stop()，其他九个线程下一轮检查时就退出了。主线程 coord.join() 等到所有线程结束，程序正常退出。

关键点：任何一个线程调用 request_stop，所有线程都能通过 should_stop 感知到。这是单向广播，没有回头路，一旦 stop 就不能撤销。

QueueRunner 和 Coordinator 一起用时，这个判断被封装进了入队线程的循环里。哪个线程抛异常（比如文件读坏了、OutOfRange），它就调 request_stop，其他线程跟着退。主线程也能主动调 request_stop 结束所有采集线程。

经典三段结构 #

这是 TF 1.x 数据管道的核心，必须记住。

先想清楚一个问题：什么是数据读取？

硬盘上有 0001.jpg、0002.jpg、0003.jpg……读进内存，再喂给 GPU。听起来简单，但按下式计算：

读入 0.1 秒，计算 0.9 秒。每秒里有 0.1 秒 GPU 闲着。如果读入 0.5 秒、计算 0.5 秒，GPU 利用率直接掉到 50%。

解法只有一个：读和算放两个线程，中间加一个内存队列。读线程拼命往队列塞，算线程需要时直接取。

text
[文件名队列]  ──►  [reader 读文件 + 解码]  ──►  [内存队列]  ──►  [组 batch]  ──►  计算
   管 epoch              可多线程                缓冲            管形状

三段各管一件事：

队列 里面装什么 由谁创建 管什么
文件名队列 字符串（文件路径） tf.train.string_input_producer epoch 数、文件顺序
内存队列 解码后的样本张量 reader 隐式创建 缓冲，解耦读和算
批次队列 一个 batch 的张量 tf.train.shuffle_batch / batch batch 大小、批内顺序

为什么要在内存队列前面再加一层文件名队列？

因为要管 epoch。一个 epoch 就是把数据集里所有样本过一遍。数据集是 A.jpg、B.jpg、C.jpg，跑一个 epoch 就是各算一次；跑两个 epoch 就是各算两次。

做法：在文件名队列里把 A、B、C 各放一遍，末尾打一个「结束」标记。reader 读到标记就抛 OutOfRange，外层捕捉到这个异常就知道一个 epoch 走完了。

跑 2 个 epoch，就在文件名队列里把 A、B、C 各放两遍，最后打一个结束标记。

这就是 num_epochs 参数干的事。

string_input_producer 与 start_queue_runners #

文件名队列用 tf.train.string_input_producer() 建。传一个文件名列表，它自动转成一个 FIFO 队列，还隐含地在图里加了一个 QueueRunner。

python
filenames = [os.path.join(data_dir, 'data_batch_%d.bin' % i) for i in range(1, 6)]
filename_queue = tf.train.string_input_producer(filenames, shuffle=True, num_epochs=5)

两个关键参数：

  • num_epochs：跑几个 epoch。不传就是无限跑。
  • shuffle：一个 epoch 内文件顺序是否打乱。False 就是 A→B→C，True 就是每个 epoch 内随机。

内存队列不用自己建。你用 reader 从文件名队列读，reader 内部就有内存队列。

reader 的 read() 返回两个东西：一个 key（标识这个样本来自哪个文件、第几条记录，调试用），一个字符串标量（原始字节，交给解析器解码）。

python
reader = tf.TextLineReader()
key, value = reader.read(filename_queue)

到这一步，图建好了，但系统是「停滞」的。文件名还没真的进队列，read() 会一直阻塞。必须调：

python
threads = tf.train.start_queue_runners(sess=sess, coord=coord)

这个函数启动 tf.GraphKeys.QUEUE_RUNNERS 集合里所有队列线程。调完之后文件名才开始进队，管道才转起来。

初学者看代码经常见到这个函数但不知道它干什么，原因就在这里：string_input_producer 只是往图里塞了个隐式的 QueueRunner，不启动它，管道是死的。

显式起线程：方式一 #

有两种经典写法。第一种是显式建 QueueRunner，调 create_threads 起线程。

python
import numpy as np
import tensorflow as tf

# 1000 个 4 维输入向量
data = 10 * np.random.randn(1000, 4) + 1
# 1000 个目标值，0 或 1
target = np.random.randint(0, 2, size=1000)

# 队列每一项包含一个样本和对应目标
queue = tf.FIFOQueue(capacity=50, dtypes=[tf.float32, tf.int32], shapes=[[4], []])

enqueue_op = queue.enqueue_many([data, target])
data_sample, label_sample = queue.dequeue()

# 4 个线程入队
qr = tf.train.QueueRunner(queue, [enqueue_op] * 4)

with tf.Session() as sess:
    coord = tf.train.Coordinator()
    enqueue_threads = qr.create_threads(sess, coord=coord, start=True)

    for step in range(100):
        if coord.should_stop():
            break
        data_batch, label_batch = sess.run([data_sample, label_sample])

    coord.request_stop()
    coord.join(enqueue_threads)

这里 coord 传给了 create_threads，所以线程异常时会自己调 request_stop。主循环每步检查 should_stop()，发现问题就跳出。最后 request_stop + join，干净收尾。

shapes=[[4], []] 这个参数别省。它告诉队列每一项的形状，少了它出队的张量形状是未知的，后面接 batch 会报错。

隐式起线程：方式二 #

第二种写法不显式建 QueueRunner，全靠 string_input_producer、shuffle_batch 这些函数内部隐式创建，最后用 start_queue_runners 一把全启。

CSV 读取的例子：

python
import tensorflow as tf

# 同时打开多个文件（格式必须一样），隐式创建 Queue 和 QueueRunner
filename_queue = tf.train.string_input_producer(["iris_0.csv", "iris_1.csv"])

reader = tf.TextLineReader()
key, value = reader.read(filename_queue)

# 每一列的默认值，同时指定了类型
record_defaults = [[0.0], [0.0], [0.0], [0.0], [0]]
col1, col2, col3, col4, col5 = tf.decode_csv(value, record_defaults=record_defaults)
features = [col1, col2, col3, col4]

with tf.Session() as sess:
    coord = tf.train.Coordinator()
    threads = tf.train.start_queue_runners(coord=coord)

    for _ in range(50):
        example, label = sess.run([features, col5])
        print('Step {0} {1} {2}'.format(_, example, label))

    coord.request_stop()
    coord.join(threads)

tf.decode_csv(value, record_defaults=...) 的参数说清楚：

text
tf.decode_csv(records, record_defaults, field_delim=None, name=None)
  • records：reader 读到的内容，这里是 CSV 的一行。
  • record_defaults：每一列的默认值和类型。[[0.0], [0.0]] 表示两列都是 float32。列很多的时候写 [[]] * 100，不给默认值也能跑。
  • field_delim：分隔符，默认逗号。

返回的是一个长度等于列数的 list。

python
col = tf.decode_csv(records, record_defaults=[[]] * 100, field_delim=' ')

col 就是长度 100 的 list。

三种格式的 reader 对照 #

不同文件格式用不同的 reader，配不同的解析函数：

文件格式 reader 解析 典型场景
文本 / CSV tf.TextLineReader tf.decode_csv 小数据集、特征表
定长二进制 tf.FixedLengthRecordReader tf.decode_raw CIFAR-10 这类打包好的数据集
TFRecord tf.TFRecordReader tf.parse_single_example 官方推荐，通用
整文件 tf.WholeFileReader 自己解码 一张图一个文件
不定长 tf.RandomShuffleQueue + 自定义 — 序列数据

CSV 要提醒一句：数据量大的时候，CSV/TXT 比二进制大得多，读取速度也慢很多。几百万行的 CSV 不要直接上管道，先转 TFRecord。

定长二进制：CIFAR-10 的读法 #

CIFAR-10 的 bin 格式是每条记录固定长度：1 字节标签 + 3072 字节图像（32×32×3）。用 FixedLengthRecordReader 每次读固定字节数，正好一条记录。

python
def read_cifar10(filename_queue):
    class CIFAR10Record(object):
        pass
    result = CIFAR10Record()

    label_bytes = 1  # CIFAR-100 是 2
    result.height = 32
    result.width = 32
    result.depth = 3
    image_bytes = result.height * result.width * result.depth
    record_bytes = label_bytes + image_bytes

    reader = tf.FixedLengthRecordReader(record_bytes=record_bytes)
    result.key, value = reader.read(filename_queue)

    # 字符串转 uint8 向量
    record_bytes = tf.decode_raw(value, tf.uint8)

    # 第一个字节是标签
    result.label = tf.cast(
        tf.strided_slice(record_bytes, [0], [label_bytes]), tf.int32)

    # 剩下的字节是图像，从 [depth*h*w] reshape 成 [depth, h, w]
    depth_major = tf.reshape(
        tf.strided_slice(record_bytes, [label_bytes],
                         [label_bytes + image_bytes]),
        [result.depth, result.height, result.width])

    # [depth, h, w] 转 [h, w, depth]
    result.uint8image = tf.transpose(depth_major, [1, 2, 0])

    return result

这个函数干了六件事：

  1. 算一条记录多少字节：图像字节数 + 标签字节数。
  2. reader.read() 读一条，decode_raw 转成 uint8 张量。
  3. 切出第一个字节，uint8 → int32，作为标签。
  4. 切出剩下的字节，作为图像。
  5. 把 [depth*height*width] reshape 成 [depth, height, width]。
  6. transpose 成 [height, width, depth]，返回。

返回的对象有两个张量属性：result.uint8image 是图像，result.label 是标签。

这段代码第一次看不懂很正常，可以跳过。但它的结构是所有定长格式读取的模板：定长度 → 读一条 → 按偏移切片 → reshape → 换轴。

从原图读：路径列表 + 三个算子 #

很多场景训练集就是原始图片，没有打包成 bin。做法是先做一个 train_list.txt，一行一个「路径 标签」，然后：

python
import os
import tensorflow as tf

filename = os.path.join(data_dir, trainfilename)
with open(filename) as fid:
    content = fid.read()
content = content.split('\n')
content = content[:-1]

valuequeue = tf.train.string_input_producer(content, shuffle=True)
value = valuequeue.dequeue()
dir, labels = tf.decode_csv(records=value,
                            record_defaults=[["string"], [""]],
                            field_delim=" ")
labels = tf.string_to_number(labels, tf.int32)

imagecontent = tf.read_file(dir)
image = tf.image.decode_png(imagecontent, channels=3, dtype=tf.uint8)
image = tf.cast(image, tf.float32)

# 统一成 32*32
image = tf.image.resize_images(image, [32, 32])
image = tf.reshape(image, [result.depth, result.height, result.width])
result.uint8image = tf.transpose(image, [1, 2, 0])

三个新算子：

  • tf.read_file(dir)：读整个文件，返回字符串张量。这一步是真的 IO。
  • tf.image.decode_png(content, channels=3)：解码 PNG。JPEG 用 decode_jpeg。
  • tf.image.resize_images：统一尺寸。

这条路的 IO 压力最大：一个小文件一次 open，机械硬盘上就是一次寻道。文件多、图小的时候（比如 32×32 的 CIFAR），IO 会拖垮整个管道。所以官方推荐打包成 TFRecord。

顺便提一句，如果机械盘有坏道，这一步会报 Input/Output error。这不是代码问题，得检查硬盘。

三种格式的速度对比 #

格式 单样本读取 解码开销 适合
原图（JPEG/PNG） 一次 open + 一次 decode 高 数据量小，要灵活改预处理
CSV / TXT 顺序读，解析慢 中 特征表，行数不多
定长 bin 顺序读，快 低（decode_raw） 格式固定的公开数据集
TFRecord 顺序读，快 低 大数据集，多文件分片

结论很直接：超过几万张图，先转 TFRecord。

四、TFRecord 格式 #

TFRecord 是 TensorFlow 官方推荐的数据集格式。它不是什么新技术，就是一个二进制记录文件，加一层 protobuf 封装。

优点三条：

  • 顺序读，一次 open 能读很久，绕开小文件 IO 抖动。
  • 一个文件能装几十万样本，还能分片。
  • 能被队列和 tf.data 直接吃，不用额外解析代码。

代价一条：要先把数据转一遍。这一步跑一次就好，之后的每个 epoch 都在省时间。

内部结构 #

TFRecord 文件的每条记录长这样：

text
[uint64 长度][uint32 长度 CRC][data bytes][uint32 data CRC]

外面套的是 tf.train.Example 这个 protobuf 结构。Example 里是 Features，Features 里是一个映射，key 是字段名，value 是三种之一：

类型 存什么 例子
BytesList 字符串、图像原始字节 图片的 tobytes()
FloatList 浮点数 归一化后的特征
Int64List 整数 标签

图像一般不用 FloatList 存。存 uint8 原始字节最省空间，读出来再 decode_raw 转。

写入：三步 #

python
import tensorflow as tf
import os
import cv2

def write_binary():
    '''把当前目录下所有图片存成 TFRecord'''
    cwd = os.getcwd()
    classes = ['A', 'B', 'C']

    writer = tf.python_io.TFRecordWriter('data.tfrecord')

    for index, name in enumerate(classes):
        class_path = os.path.join(cwd, name)
        for img_name in os.listdir(class_path):
            img_path = os.path.join(class_path, img_name)
            img = cv2.imread(img_path)
            img1 = cv2.resize(img, (250, 250))
            # 转成原始字节
            img_raw = img1.tobytes()

            example = tf.train.Example(features=tf.train.Features(feature={
                'img_raw': tf.train.Feature(
                    bytes_list=tf.train.BytesList(value=[img_raw])),
                'label': tf.train.Feature(
                    int64_list=tf.train.Int64List(value=[index]))}))

            serialized = example.SerializeToString()
            writer.write(serialized)

    writer.close()

三步：组 Example → SerializeToString() → writer.write()。

细节两个：

  • value=[img_raw] 用的是 list，因为 BytesList 支持一条记录存多个值。
  • writer.close() 别漏。不 close 的话最后一批还在缓冲区，文件不完整。

TF 2.x 里 tf.python_io.TFRecordWriter 改成了 tf.io.TFRecordWriter，功能一样。

读取：四步 #

python
def read_and_decode(filename):
    # 文件名队列，不限读取数量
    filename_queue = tf.train.string_input_producer([filename], shuffle=False)
    reader = tf.TFRecordReader()
    _, serialized_example = reader.read(filename_queue)

    features = tf.parse_single_example(
        serialized_example,
        features={
            'label': tf.FixedLenFeature([], tf.int64),
            'img_raw': tf.FixedLenFeature([], tf.string)
        })

    img = tf.decode_raw(features['img_raw'], tf.uint8)
    img = tf.reshape(img, [250, 250, 3])
    label = tf.cast(features['label'], tf.int32)
    return img, label

四步对应四层：文件名队列 → reader 读一条 → parse_single_example 解 protobuf → decode_raw + reshape 出图像。

tf.FixedLenFeature([], tf.int64) 的两个参数要说清：

  • 第一个是形状。[] 表示标量，一条记录一个值。[3] 表示长度 3 的向量。
  • 第二个是类型。必须和写入时一致，写 Int64List 就读 tf.int64，写错了运行时报错。

变长数据用 tf.VarLenFeature，读出来是 SparseTensor，还要 tf.sparse_tensor_to_dense 转，一般能不用就不用。

分片：为什么要拆多个文件 #

大数据集要拆成多个 TFRecord 文件。两个原因：

  • 单个文件太大，分布式训练时没法切给不同 worker。
  • 想让不同 worker 读不同分片，提高整体吞吐。

但是拆片有个坑，必须讲清楚：

text
当所有类别的图片都在一个文件夹下面时，可以将数据写入不同的文件。
但是如果同一类别的图片放在相同的文件夹下，就不可以将数据写入不同的文件。
因为后者保存的 TFRecord 文件中都是同一类别，而队列取数据时，是从一个文件读取完，
才会读取另一个文件，这样会导致一次读取的 batch_size 图像都是同一类别，对训练不利。

说白了：分片是按类别分的，一个 batch 里全是同一个类，梯度方向会偏，训练直接跑歪。

解法：分片之前先把样本列表打乱，让每个分片里都混着各类。下面这段代码就是这么做的。

完整的分片写入 #

python
import tensorflow as tf
import os
import cv2
import random
import numpy as np

random.seed(0)

def get_files(dirpath):
    '''遍历父目录下的子目录，返回图片路径列表和标签列表'''
    image_list = []
    label_list = []

    classes = [x for x in os.listdir(dirpath) if os.path.isdir(dirpath)]

    for index, name in enumerate(classes):
        class_path = os.path.join(dirpath, name)
        for img_name in os.listdir(class_path):
            img_path = os.path.join(class_path, img_name)
            image_list.append(img_path)
            label_list.append(index)

    # 打乱，连续打乱两次
    images = []
    labels = []
    indices = list(range(len(image_list)))
    random.shuffle(indices)
    for i in indices:
        images.append(image_list[i])
        labels.append(label_list[i])
    random.shuffle([images, labels])

    print('样本长度为:', len(images))
    return images, labels


def WriteTFRecord(dirpath, dstpath='.', train_data=True,
                  IMAGE_HEIGHT=227, IMAGE_WIDTH=227):
    '''把指定目录下的数据写入多个 TFRecord 文件'''
    if not os.path.isdir(dstpath):
        os.mkdir(dstpath)

    image_list, label_list = get_files(dirpath)

    # 每个记录文件的样本长度
    length_per_shard = 10000
    num_shards = int(np.ceil(len(image_list) / length_per_shard))
    print('记录文件个数：', num_shards)

    for index in range(num_shards):
        # 按 0000n-of-0000m 的后缀区分文件
        if train_data:
            filename = os.path.join(
                dstpath, 'train_data.tfrecord-%.5d-of-%.5d' % (index, num_shards))
        else:
            filename = os.path.join(
                dstpath, 'test_data.tfrecord-%.5d-of-%.5d' % (index, num_shards))
        print(filename)

        writer = tf.python_io.TFRecordWriter(filename)

        idx_start = index * length_per_shard
        idx_end = np.min([(index + 1) * length_per_shard - 1, len(image_list)])

        for img_path, label in zip(image_list[idx_start:idx_end],
                                   label_list[idx_start:idx_end]):
            img = cv2.imread(img_path)
            img = cv2.resize(img, (IMAGE_HEIGHT, IMAGE_WIDTH))
            image = img.tobytes()

            example = tf.train.Example(features=tf.train.Features(feature={
                'image': tf.train.Feature(
                    bytes_list=tf.train.BytesList(value=[image])),
                'label': tf.train.Feature(
                    int64_list=tf.train.Int64List(value=[label]))}))

            serialized = example.SerializeToString()
            writer.write(serialized)
        writer.close()

注意 %.5d 的命名：train_data.tfrecord-00000-of-00003。这个格式和 Hadoop 体系一致，也方便 match_filenames_once 用通配符匹配。

length_per_shard = 10000 是个经验值。分片太小，文件数太多，队列管理开销大；分片太大，单文件几百 MB，加载慢。1 万个样本一片，图像类任务一般在 100MB 到 1GB 之间，比较合适。

从分片读 batch #

python
def read_and_decode(filename, num_epochs=None,
                    IMAGE_HEIGHT=227, IMAGE_WIDTH=227):
    # shuffle=True 打乱文件入队顺序，出队顺序随机
    filename_queue = tf.train.string_input_producer(
        filename, shuffle=False, num_epochs=num_epochs)

    reader = tf.TFRecordReader()
    _, serialized_example = reader.read(filename_queue)

    features = tf.parse_single_example(
        serialized_example,
        features={
            'image': tf.FixedLenFeature([], tf.string),
            'label': tf.FixedLenFeature([], tf.int64)
        })

    img = tf.decode_raw(features['image'], tf.uint8)
    img = tf.reshape(img, [IMAGE_HEIGHT, IMAGE_WIDTH, 3])

    label = tf.cast(features['label'], tf.int32)
    return img, label


def input_data(filenames, num_epochs=None, batch_size=256,
               capacity=4096, min_after_dequeue=1024, num_threads=10):
    img, label = read_and_decode(filenames, num_epochs)
    images_batch, labels_batch = tf.train.shuffle_batch(
        [img, label], batch_size=batch_size, capacity=capacity,
        min_after_dequeue=batch_size * 5, num_threads=num_threads)
    return images_batch, labels_batch

参数的含义：

参数 作用 建议值
batch_size 一个 batch 多少样本 按显存定，256 起步
capacity 内存队列最多存多少 batch_size * 16 上下
min_after_dequeue 队列最少留多少才开始出队 batch_size * 5
num_threads 几个线程读 4 到 10，多了抢 CPU

min_after_dequeue 是控制打乱程度的。它保证队列里至少留这么多样本才开始出队，池子越大，随机性越好。设成 0 就是几乎不打乱，设得太大内存吃不住。

经验值：min_after_dequeue >= 5 * batch_size，capacity > min_after_dequeue + 3 * batch_size。

驱动的完整骨架 #

python
def file_match(s, root='.'):
    '''在指定目录（不含子目录）找文件名含指定字符串的文件'''
    matchs = []
    for current_name in os.listdir(root):
        add_root_name = os.path.join(root, current_name)
        if os.path.isfile(add_root_name) and s in add_root_name:
            matchs.append(add_root_name)
    return matchs


if __name__ == '__main__':
    dirpath = './data/train'
    training_step = 1

    files = file_match('train_data.tfrecord')
    if len(files) == 0:
        print('开始读图片文件并写入 TFRecord .........')
        WriteTFRecord(dirpath)
        print('写入完毕!\n')
        files = tf.train.match_filenames_once('./train_data.tfrecord')

    images_batch, labels_batch = input_data(files)

    with tf.Session() as sess:
        sess.run(tf.global_variables_initializer())

        coord = tf.train.Coordinator()
        threads = tf.train.start_queue_runners(sess=sess, coord=coord)

        print('开始训练!\n')
        for step in range(training_step):
            img, label = sess.run([images_batch, labels_batch])
            print('step :', step)
            for i in range(256):
                cv2.imwrite('%d_%d_p.jpg' % (i, label[i]), img[i])

        coord.request_stop()
        coord.join(threads)

注意 tf.local_variables_initializer() 这一句。string_input_producer 内部建了一个 epoch 计数器，那是 local variable，只跑 global_variables_initializer 不够。

用 num_epochs 的时候，一定要加：

漏了这一句，epoch 计数不对，数据会读超或者提前结束。

五、tf.data API #

TF 1.x 的队列那套现在回头看，问题很明显：

  • 要手动管线程，忘了 start_queue_runners 就卡死。
  • QueueRunner 和 Coordinator 的生命周期靠人记。
  • 想在管道里加一个新算子，得自己去接队列。
  • 队列和图绑定，调试困难。

TF 2.x 用 tf.data 把这一整套包了起来。同样的三段结构，写法变成链式调用。

一句话理解 #

text
tf.data.Dataset → 一串算子 → for batch in dataset

Dataset 是一个惰性的元素序列。你描述「数据长什么样、怎么变换」，它自己去调度执行。

对照一下老写法：

TF 1.x tf.data 干的事
string_input_producer Dataset.list_files / from_tensor_slices 建数据源
TFRecordReader + parse_single_example TFRecordDataset + map(parse) 读 + 解析
Coordinator + QueueRunner 自动 管线程
shuffle_batch .shuffle().batch() 打乱 + 组批
手写 while 循环 + try/except OutOfRange for x in dataset epoch 控制

一行老代码，一行新代码，工作量差一个数量级。

三种数据源 #

从内存数组建：

from_tensor_slices 沿第一维切片，第 0 维是样本数。1000 个样本，遍历一遍就是 1000 个元素。

从 TFRecord 建：

files = tf.data.Dataset.list_files('./data/train_data.tfrecord-*')

def parse_fn(serialized):
    features = tf.io.parse_single_example(
        serialized,

            'image': tf.io.FixedLenFeature([], tf.string),

常用算子 #

这张表要背下来，够用九成场景：

算子 作用 注意

顺序很重要 #

管道里算子的顺序直接影响性能和正确性。三条铁律：

  1. shuffle 在 batch 之前。反了就是打乱批次顺序，批内还是连续的。
  2. map 在 batch 之前。在单样本上做变换，批处理时不用手写 batch 维度。
  3. prefetch 在最后。它要预取的是最终输出的 batch。

一个标准的图像训练管道：

python
ds = tf.data.TFRecordDataset(files)
ds = ds.shuffle(10000)
ds = ds.map(parse_fn, num_parallel_calls=tf.data.AUTOTUNE)
ds = ds.map(augment_fn, num_parallel_calls=tf.data.AUTOTUNE)
ds = ds.batch(32)
ds = ds.prefetch(tf.data.AUTOTUNE)

shuffle 放在最前面，是因为在文件字节层面打乱最便宜。你要是先 map 再 shuffle，等于把解码开销花在会被丢弃的样本上。

交错读多文件 #

多个 TFRecord 分片时，TFRecordDataset 默认是读完一个文件再读下一个。这会导致 batch 内的样本集中在同一片，和前面讲的「按类别分片」一个毛病。

解法是 interleave：

python
files = tf.data.Dataset.list_files('./data/train_data.tfrecord-*')

ds = files.interleave(
    lambda f: tf.data.TFRecordDataset(f),
    cycle_length=4,
    block_length=16,
    num_parallel_calls=tf.data.AUTOTUNE)

cycle_length=4 表示同时打开 4 个文件轮流取，block_length=16 表示每次从一个文件连续取 16 条再换。4 个文件交错，一个 batch 里就混了 4 片的数据。

这个参数在分片数很多的时候尤其重要。分片 100 个但 cycle_length=1，等于没交错。

读老代码：TF 1.x 的队列还剩什么 #

TF 2.x 里 tf.train.QueueRunner、tf.train.Coordinator、tf.train.string_input_producer 都进了 tf.compat.v1。老代码要么改写成 tf.compat.v1.train.*，要么整体迁到 tf.data。

迁移顺序建议：

  1. 先把 string_input_producer + reader 换成 Dataset.list_files + TFRecordDataset。
  2. 把 shuffle_batch 换成 shuffle().batch()。
  3. 删掉 Coordinator、start_queue_runners、local_variables_initializer，这些不需要了。
  4. 最后加 prefetch。

第三步之后代码会短一大截，因为线程管理全被接管了。

六、数据增强与预处理 #

管道里除了读，还得改。改分两类，一定要分清：

类别 例子 能不能增加样本 放在哪
预处理 resize、归一化、类型转换、PCA 不能 写 TFRecord 时或读出来之后
数据增强 随机裁切、水平翻转、调亮度、加噪声 能，相当于扩充数据集 训练时实时做

分界线就一条：会不会造出原来数据集里没有的样本。归一化不会，翻转会。

在 TFRecord 里做还是读出来做 #

两种做法都行，各有代价：

做法 优点 缺点
写 TFRecord 时做 训练时省 CPU 数据固定，增强失去随机性；改一次要重写全量
读出来在管道里做 每次不一样，等效数据量翻倍 训练时吃 CPU，要并行化

结论：确定性变换写进 TFRecord（resize、归一化），随机增强放在读出来之后。

写 TFRecord 时把图固定成 227×227，是因为后面的网络要固定输入尺寸。这一步不做，每次读出来都要 resize，白花钱。

但随机翻转不能提前做。提前做了，每个 epoch 看到的都是同一张翻转图，等于没增强。

图像增广的常用算子 #

TF 1.x 的这些算子大多搬到了 tf.image 下面，换了个名字：

python
import tensorflow as tf

def augment(image, label):
    # 随机水平翻转
    image = tf.image.random_flip_left_right(image)
    # 随机调亮度，范围 [-0.1, 0.1]
    image = tf.image.random_brightness(image, max_delta=0.1)
    # 随机调对比度
    image = tf.image.random_contrast(image, lower=0.9, upper=1.1)
    # 随机裁切再缩放回原尺寸
    image = tf.image.random_crop(image, size=[200, 200, 3])
    image = tf.image.resize(image, [227, 227])
    # 归一化到 [0, 1]
    image = tf.cast(image, tf.float32) / 255.0
    return image, label

顺序有讲究：

  1. 几何变换（翻转、裁切）先做。它们改尺寸，做完再缩放。
  2. 光度变换（亮度、对比度）后做。它们只改像素值。
  3. 归一化放最后。前面用 uint8 算，省内存也省时间。

归一化做反了会很难查。random_brightness 的 max_delta 在 0 到 1 的浮点图上是 0.1，在 0 到 255 的 uint8 图上是 25。图没归一化就传 0.1，等于没调。

随机裁切的两种写法 #

random_crop 直接切一块出来，尺寸变了，后面必须接 resize。

另一种是「先补边再随机切回原尺寸」，保住视野：

python
def random_crop_with_pad(image, label, pad=16):
    image = tf.image.resize_with_crop_or_pad(
        image, 227 + pad * 2, 227 + pad * 2)
    image = tf.image.random_crop(image, size=[227, 227, 3])
    return image, label

先把 227×227 补到 259×259，再随机切 227×227。切出来的图能看到原图的边缘之外，等效于平移增强。

并行化：map 的两个参数 #

增强算子只作用在单样本上，天然可以并行。map 的两个参数决定吞吐：

python
ds = ds.map(augment, num_parallel_calls=tf.data.AUTOTUNE)

num_parallel_calls 不设，map 就在主线程串行跑。设了，就开一组线程并行处理，主线程去拿现成的结果。

tf.data.AUTOTUNE 让 TensorFlow 自己定这个数，按 CPU 核数和管道负载动态调。除了极少数要手调的场合，一律用它。

第二个参数是 deterministic：

python
ds = ds.map(augment, num_parallel_calls=tf.data.AUTOTUNE, deterministic=False)

默认 deterministic=True，保证输出顺序和输入顺序一致。代价是要等所有并行任务按序返回，慢的会拖住快的。设成 False，谁先算完谁先出，快一些，但每次跑的顺序不一样，复现实验时别用。

预热：cache 的两种模式 #

小数据集（能塞进内存）加 cache()，第一个 epoch 之后就不再读盘、不再解码：

python
ds = ds.cache()

注意 cache 的位置。放在 shuffle 之前，缓的是原始数据；放在 map 之后，缓的是处理后的数据。后者省得更多，但占内存更多。

大得放不进内存的，cache 到文件：

python
ds = ds.cache('./cache/train.cache')

这是用磁盘换 CPU。第一次跑会慢，之后每次都快，适合反复实验的场景。

cache 有个坑：它缓存的是这个 Dataset 对象当前吐出的内容。如果 cache() 后面接了随机增强，缓存里是增强前的数据，每次重放还是随机增强，行为正确。如果 cache() 放在随机增强之后，那就是把第一次增强的结果冻住了，后面每个 epoch 都一样，增强白做。

验证集不要增强 #

验证集和测试集的管道要去掉所有随机算子，只留确定性的：

python
val_ds = tf.data.TFRecordDataset(val_files)
val_ds = val_ds.map(parse_fn, num_parallel_calls=tf.data.AUTOTUNE)
val_ds = val_ds.batch(32)
val_ds = val_ds.prefetch(tf.data.AUTOTUNE)

不加 shuffle，不加 augment。验证集的指标要可比，每次跑出来不一样就没法判断模型好坏。

同一个 parse_fn 里如果混了增强，靠参数分开：

python
def parse_fn(serialized, training):
    # ... 解码 ...
    if training:
        image = tf.image.random_flip_left_right(image)
    return image, label

或者干脆写两个 parse_fn，训练一个、验证一个。后者更清楚，多几行值得。

标签处理 #

分类任务的标签在 TFRecord 里存成 int64，读出来要转 int32。如果 loss 用 sparse 交叉熵，保持整数；用 one-hot，就在管道里转：

python
def parse_with_onehot(serialized):
    features = tf.io.parse_single_example(serialized, features={
        'image': tf.io.FixedLenFeature([], tf.string),
        'label': tf.io.FixedLenFeature([], tf.int64)})
    img = tf.io.decode_raw(features['image'], tf.uint8)
    img = tf.reshape(img, [227, 227, 3])
    img = tf.cast(img, tf.float32) / 255.0
    label = tf.one_hot(features['label'], depth=10)
    return img, label

tf.one_hot 放在管道里比放在模型里省事，但要注意 depth 必须和类别数一致，写错了 loss 会静默算出一个错的数。

七、批次、打乱与预取 #

这一节把三个最影响吞吐的参数讲透：batch、shuffle、prefetch。

batch：形状的来源 #

batch(n) 把 n 个连续元素拼成一个。图像管道的形状变化：

text
单样本：(227, 227, 3)
batch 后：(32, 227, 227, 3)

模型的输入形状写 (None, 227, 227, 3)，那个 None 就是给 batch 留的。

最后一个 batch 不满是常态。1000 个样本、batch=32，最后一批是 8 个。不处理的话，模型会收到形状 (8, 227, 227, 3)，如果网络里有依赖 batch 大小的操作（BN 在训练时用 batch 统计量），结果会有小幅抖动。

两种处理方式：

python
# 丢掉最后不满的一批
ds = ds.batch(32, drop_remainder=True)

# 不丢，允许最后一批变小（默认）
ds = ds.batch(32)

训练用 drop_remainder=True 让每个 batch 形状固定，编译和 XLA 都更友好。评估时不要丢，否则最后几个样本没被评估到。

shuffle：池子要够大 #

shuffle(buffer_size) 的工作方式是个滑动窗口：

text
先填满 buffer_size 个元素
每取一个，就从剩下的里随机挑一个补进来

buffer_size 就是那个池子的容量。池子越大，打乱越充分，内存也吃得越多。

按数据集大小取值：

数据集规模 buffer_size 建议
几千条 整个数据集大小
几万条 10000
几十万以上 10000 到 50000，够用就行
分片 TFRecord 先 shuffle 文件名，再 shuffle 样本

经典错误是把 buffer_size 设成 1 或者不设。shuffle(1) 等于没打乱，shuffle 默认值是 1000，几万条的数据集用 1000 就明显不够，一个 batch 内的样本基本还是连续的。

还有个细节：shuffle 在每个 epoch 开始时是否重新打乱，取决于 reshuffle_each_iteration 参数，默认 True。设成 False 就只打乱一次，之后每个 epoch 顺序固定。要在固定顺序上做实验对比时用。

多文件的两级打乱 #

分片很多时，只在样本层面打乱不够，文件顺序也要打乱：

python
files = tf.data.Dataset.list_files('./data/train_data.tfrecord-*', shuffle=True)
ds = files.interleave(
    tf.data.TFRecordDataset,
    cycle_length=8,
    num_parallel_calls=tf.data.AUTOTUNE)
ds = ds.shuffle(10000)

list_files(shuffle=True) 打乱文件顺序，shuffle(10000) 打乱样本顺序。两级都做，一个 batch 里才有真正的随机性。

只做样本级打乱、文件顺序固定，会出现「前 N 个 batch 全来自第 1 片」的现象。这一片的类别分布如果有偏，前几百步的梯度方向就是偏的。

prefetch：把 IO 藏到计算后面 #

prefetch(n) 让管道在后台准备 n 个 batch，主线程算当前 batch 时，后台已经在准备下一个。

text
没有 prefetch：
  [读 batch1][算 batch1][读 batch2][算 batch2] ...
  GPU 有一半时间在等

有 prefetch(1)：
  [读 batch1]
  [读 batch2][算 batch1]
  [读 batch3][算 batch2] ...
  GPU 几乎不等

一行代码，一般能带来明显的吞吐提升，而且是零风险的改动。

prefetch(tf.data.AUTOTUNE) 让 TensorFlow 决定预取几个。它按每个 batch 的读取耗时和计算耗时来估，动态调整。

三个参数怎么配：

参数 取值思路
prefetch 一律 AUTOTUNE
num_parallel_calls（map） 一律 AUTOTUNE
num_parallel_calls（interleave） 等于或略小于分片数

一个能直接用的完整管道 #

python
import tensorflow as tf

def build_pipeline(files, batch_size=32, training=True):
    files = tf.data.Dataset.list_files(files, shuffle=training)

    ds = files.interleave(
        tf.data.TFRecordDataset,
        cycle_length=8,
        num_parallel_calls=tf.data.AUTOTUNE)

    if training:
        ds = ds.shuffle(10000)

    ds = ds.map(parse_fn, num_parallel_calls=tf.data.AUTOTUNE)

    if training:
        ds = ds.map(augment, num_parallel_calls=tf.data.AUTOTUNE)

    ds = ds.batch(batch_size, drop_remainder=training)
    ds = ds.prefetch(tf.data.AUTOTUNE)
    return ds

train_ds = build_pipeline('./data/train_data.tfrecord-*', 32, training=True)
val_ds = build_pipeline('./data/test_data.tfrecord-*', 64, training=False)

训练和验证复用同一个函数，靠 training 参数切换随机算子。这是最省心的写法，也最不容易漏。

性能自查清单 #

管道慢，按这个顺序查：

  1. 有没有 prefetch？没有就先加。
  2. map 有没有 num_parallel_calls？没有就加 AUTOTUNE。
  3. shuffle 的 buffer_size 够不够？太小就打乱不充分。
  4. 有没有在小文件上做 read_file？有就转 TFRecord。
  5. batch 是不是设得太小？batch 太小，每步开销占比高。
  6. cache 能不能用？能塞进内存就加。
  7. 数据增强是不是太重？random_crop + resize 连做两次很吃 CPU。

第 3 条和第 6 条经常被忽略。前者影响收敛，后者影响速度，都不报错。

八、模型保存：checkpoint #

前面七章讲数据怎么进去，从这一章开始讲模型怎么存下来。

先说一个最容易混淆的点：

checkpoint 只存权重，SavedModel 存图 + 权重 + 签名。

对比项 checkpoint SavedModel
存什么 变量的值（权重、偏置、优化器状态） 计算图 + 权重 + 输入输出签名
有没有图结构 .meta 文件里有（TF 1.x） 有
主要用途 继续训练 部署推理
加载前提 必须先把网络结构再定义一遍 不用，load 出来直接能调
跨语言调用 不方便 支持（C++、Java、Go）
典型场景 训练中断续跑、调参 上线、交付、转 TFLite/TensorRT

一句话记住：要上线交付用 SavedModel，要续训用 checkpoint。

Saver 存出来的四个文件 #

python
saver = tf.train.Saver()
with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())
    # ... 训练 ...
    saver.save(sess, 'save_path/file_name')

跑完在目录下会看到四个文件：

文件 内容
file_name.meta 图结构。所有 op、变量定义、集合
file_name.data-00000-of-00001 变量的值，二进制
file_name.index 变量名到数据块的索引表
checkpoint 文本文件，记录最新的检查点路径

.meta 是 protobuf 序列化的 MetaGraphDef，包含了整个图的完整信息。.data 里是权重、偏置、梯度和所有其他变量的值。

checkpoint 是个纯文本文件，内容长这样：

text
model_checkpoint_path: "./LinearRegression/linearmodel.cpkt-180"
all_model_checkpoint_paths: "./LinearRegression/linearmodel.cpkt-160"
all_model_checkpoint_paths: "./LinearRegression/linearmodel.cpkt-180"

tf.train.latest_checkpoint(dir) 读的就是这个文件。

一个坑：同名变量 #

checkpoint 文件里记录了多个模型的变量数据。如果同时保存了几个模型，而它们之间存在同名变量，checkpoint 里取到的数据会对应错模型。

text
如果同时保存了几个模型，则在这个文件里还有这几个模型的变量数据。
由于在这几个模型中会有同名变量，所以取得的数据会出问题。

两个解法：

  1. 不同模型存在不同目录下。最省事，最不易错。
  2. 用 tf.variable_scope 给变量名分组，让同名变量变成 scope1/w 和 scope2/w。

第一种方案在任何场景都成立，第二种在要共享部分参数时更灵活。

保存和载入的最小写法 #

python
saver = tf.train.Saver()
with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())
    # 训练......
    saver.save(sess, 'save_path/file_name')

载入：

python
saver = tf.train.Saver()
with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())
    saver.restore(sess, 'save_path/file_name')

restore 前的初始化可以省，也可以留。留着也不影响，因为 restore 会把初始化好的值覆盖掉。

但有一点必须记住：Saver 对象要在变量声明之后创建。写在 tf.Variable 之前，Saver 收集不到这些变量，保存下来的是空文件。

python
w = tf.Variable(..., name='w')
b = tf.Variable(..., name='b')
saver = tf.train.Saver()        # 必须在变量之后

tf.train.Saver() 不传参数时，默认收集 tf.GraphKeys.GLOBAL_VARIABLES 集合里的所有变量。

完整案例：线性回归的保存与恢复 #

光看片段不够，跑一个完整的。下面是线性回归，训练 200 轮，中间每 20 轮存一次，最后再恢复出来预测。

python
import tensorflow as tf
import numpy as np
import os

n_train = 100
train_x = np.linspace(-1, 1, n_train).reshape(n_train, 1)
train_y = 2 * train_x + np.random.normal(loc=0.0, scale=0.3, size=[n_train, 1])

tf.reset_default_graph()

input_x = tf.placeholder(dtype=tf.float32)
input_y = tf.placeholder(dtype=tf.float32)

w = tf.Variable(tf.truncated_normal(shape=[1], mean=0.0, stddev=1), name='w')
b = tf.Variable(tf.truncated_normal(shape=[1], mean=0.0, stddev=1), name='b')

pred = tf.multiply(w, input_x) + b

cost = tf.reduce_mean(tf.square(input_y - pred))
train = tf.train.GradientDescentOptimizer(learning_rate=0.001).minimize(cost)

training_epochs = 200
display_step = 20

# 在张量声明之后创建 Saver
saver = tf.train.Saver()

savedir = './LinearRegression'
savefile = 'linearmodel.cpkt'

if not os.path.isdir(savedir):
    os.mkdir(savedir)

with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())

    # 有旧模型就先恢复，接着练
    if os.path.isfile(os.path.join(savedir, savefile) + '.meta'):
        saver.restore(sess, os.path.join(savedir, savefile))

    plotdata = {'batch_size': [], 'loss': []}

    for epoch in range(training_epochs):
        for (x, y) in zip(train_x, train_y):
            sess.run(train, feed_dict={input_x: x, input_y: y})

        if epoch % display_step == 0:
            loss = sess.run(cost, feed_dict={input_x: train_x, input_y: train_y})
            print('Epoch {0}  cost {1}  w {2}  b {3}'.format(
                epoch, loss, sess.run(w), sess.run(b)))

            if not loss == np.nan:
                plotdata['batch_size'].append(epoch)
                plotdata['loss'].append(loss)

    print('Finished!')
    print('cost {0}  w {1}   b {2}'.format(
        sess.run(cost, feed_dict={input_x: train_x, input_y: train_y}),
        sess.run(w), sess.run(b)))

    test_x = [2, 4, 5, 7]
    test_y = sess.run(pred, feed_dict={input_x: test_x})
    print('prediction  ', test_y)

    # 保存参数
    saver.save(sess, os.path.join(savedir, savefile))

关键三行：

python
if os.path.isfile(os.path.join(savedir, savefile) + '.meta'):
    saver.restore(sess, os.path.join(savedir, savefile))

这三行的作用是「有就续训，没有就从头练」。

跑第一次，权重随机初始化，练 200 轮。跑第二次，先恢复上次的权重，再练 200 轮，等于一共练了 400 轮。你会发现 loss 一路在降，因为每次都是在之前的基础上继续。

这就是 checkpoint 的核心用途：让训练可以分多次做完。

max_to_keep：控制存几个 #

默认 Saver 只保留最近 5 个 checkpoint，更早的自动删掉。显式控制：

python
saver = tf.train.Saver(max_to_keep=1)     # 只留最近一个
saver = tf.train.Saver(max_to_keep=10)    # 留最近十个
saver = tf.train.Saver(max_to_keep=None)  # 全留，磁盘要够

训练几十万步、每步都存的话，max_to_keep=None 会在几小时内把磁盘写满。设成 3 到 5 是常见做法，够回滚，不占空间。

九、Saver 的用法 #

Saver 的构造参数决定了它保存什么、怎么存。这一节把能用的都过一遍。

指定保存哪些变量 #

不传参数就存全部。要只存一部分，有三种写法：

python
# 用字典：key 是存到文件里的名字，value 是张量
saver = tf.train.Saver({'w': w, 'b': b})

# 用列表：名字自动取变量名
saver = tf.train.Saver([w, b])

# 用字典推导：把 op 的 name 当名字
saver = tf.train.Saver({v.op.name: v for v in [w, b]})

字典形式能改名。看这个例子：

python
a = tf.Variable(1.0, name='a')
b = tf.Variable(2.0, name='b')

# a 的值存到 b_param，b 的值存到 a_param
saver = tf.train.Saver({'b_param': a, 'a_param': b})

with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())
    saver.save(sess, './test.cpkt')

保存后文件里是 a_param 值 2.0、b_param 值 1.0。名字和变量反了，值也跟着反。这个能力在迁移学习里有用：把预训练模型的 conv1/weights 映射到你新模型的 features/conv1/kernel。

风险也在这里。指定了字典之后，保存时只存这些变量，恢复时也必须能对上：

text
当我们指定了保存和恢复的变量时，恢复的时候要保证模型文件中有该变量，不然会报错。
保存的时候模型文件也只会保存指定的变量。

如果只想恢复一部分、保存全部，标准做法是两个 Saver：

python
restore_saver = tf.train.Saver({'w': w})      # 只恢复 w
save_saver = tf.train.Saver()                 # 保存全部

with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())
    restore_saver.restore(sess, './pretrained/model')
    # 训练......
    save_saver.save(sess, './finetuned/model')

这个模式在做微调时几乎必用。

查看 checkpoint 里存了什么 #

不用写代码猜，有个现成的工具：

python
from tensorflow.python.tools.inspect_checkpoint import print_tensors_in_checkpoint_file

print_tensors_in_checkpoint_file(
    os.path.join(savedir, savefile), None, True)

输出是每个张量一行，tensor_name 后面跟着它的数值。第三个参数 True 表示打印全部张量值。

看到输出你会发现变量名带后缀，比如 w、w/Adam、w/Adam_1。这是优化器的槽位：Adam 给每个变量存了两个动量，恢复的时候如果优化器状态不匹配，训练会跳一下。

迁移学习时经常只想恢复权重、不要优化器状态，这就是为什么用 Saver({'w': w, ...}) 指定变量名。

保存时带上步数 #

想让每个 checkpoint 的文件名里带步数：

python
saver.save(sess, os.path.join(savedir, savefile), global_step=epoch)

生成的文件是 linearmodel.cpkt-180。这个数字会写进文件名，checkpoint 文件里也记着。

代价是载入时必须指定步数：

python
saver.restore(sess, os.path.join(savedir, savefile + '-' + str(180)))

步数记错就找不到文件。所以实际项目里都用「载入最近一个」的方式。

四种恢复方式 #

方式一：指定完整路径

python
saver.restore(sess, './LinearRegression/linearmodel.cpkt-180')

简单直接，但要记住步数。参数必须和保存时的网络结构完全对上，对不上就报形状错误。

方式二：读 checkpoint 文件

python
ckpt = tf.train.get_checkpoint_state(savedir)
if ckpt and ckpt.model_checkpoint_path:
    saver.restore(sess, ckpt.model_checkpoint_path)

get_checkpoint_state 读目录下的 checkpoint 文件，返回一个 CheckpointState 对象，model_checkpoint_path 是最新那个。

方式三：latest_checkpoint

python
with tf.Session() as sess:
    ckpt = tf.train.latest_checkpoint(savedir)
    if ckpt is not None:
        saver.restore(sess, ckpt)

    graph = tf.get_default_graph()
    weight = graph.get_tensor_by_name('w:0')
    bias = graph.get_tensor_by_name('b:0')

    print(sess.run([w, b]))

    # 在加载的模型后继续加新层
    add_on_op = tf.multiply(w, 2)
    print(sess.run(add_on_op))

latest_checkpoint 是方式二的简化版，返回字符串或 None，用起来最干净。多数人的选择。

注意 graph.get_tensor_by_name('w:0') 的写法：变量名加 :0 表示这个 op 的第 0 个输出。少写 :0 会报 KeyError。

方式四：连图一起加载

python
tf.reset_default_graph()
with tf.Session() as sess:
    new_saver = tf.train.import_meta_graph(
        os.path.join(savedir, savefile) + '.meta')
    new_saver.restore(sess, tf.train.latest_checkpoint(savedir))

    graph = tf.get_default_graph()
    weight = graph.get_tensor_by_name('w:0')
    bias = graph.get_tensor_by_name('b:0')

    print(sess.run([weight, bias]))

    add_on_op = tf.multiply(weight, 2)
    print(sess.run(add_on_op))

前三种是一类，最后一种是另一类。差别很关键：

方式 是否要重写网络结构 说明
一、二、三 要 本质是给已定义好的变量赋值
四 不要 从 .meta 把图导入当前图

方式一二三的缺点写在原文里：

text
第一种是 saver.restore(sess, 'aaaa.ckpt') 类型的，这种方法的本质是读取全部参数，
并加载到已经定义好的网络结构上，因此相当于给网络的 weights 和 biases 赋值并执行
tf.global_variables_initializer()。这种方法的缺点是使用前必须重写网络结构，
而且网络结构要和保存的参数完全对上。

方式四的注意点：

text
直接把网络结构加载进来（.meta），不可以重写网络结构，不然会出现变量重命名冲突问题。

因为你再定义一遍 w，图里就有两个 w，TensorFlow 会自动加后缀变成 w_1，然后 get_tensor_by_name('w:0') 拿到的是旧的，序列化回来就错位了。

import_meta_graph 之前必须 tf.reset_default_graph()。不 reset，旧图还在，导入的图和旧图混在一起，变量名冲突。

迁移学习里的标准姿势 #

实际项目里最常用的是「加载预训练权重，换掉最后的分类层」：

python
tf.reset_default_graph()

# 再定义网络结构
# ...

# 只恢复能对上的那些变量
restore_vars = {v.op.name: v for v in tf.global_variables()
                if 'fc8' not in v.op.name}
saver = tf.train.Saver(restore_vars)

with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())
    saver.restore(sess, './pretrained/model.ckpt')
    # 训练分类层......

if 'fc8' not in v.op.name 把最后一层排除掉，其余照搬。这样换了类别数也不用改前面。

MonitoredTrainingSession：按时间存 #

前面都是按步数存。还有一个按时间存的：

python
tf.reset_default_graph()

savedir = './LinearRegression/checkpoints'
global_step = tf.train.get_or_create_global_step()
step = tf.assign_add(global_step, 1)

with tf.train.MonitoredTrainingSession(
        checkpoint_dir=savedir, save_checkpoint_secs=2) as sess:
    print(sess.run([global_step]))
    while not sess.should_stop():
        i = sess.run(step)
        print(i)

save_checkpoint_secs=2 表示每 2 秒存一次。两个注意点：

  • 默认值是 600 秒（10 分钟）。
  • 必须定义 global_step 变量，否则报错。tf.train.get_or_create_global_step() 就是干这个的。

MonitoredTrainingSession 的好处在分布式训练里更明显：它自动处理初始化、恢复、保存、写 summary，不用手写那一堆。

还有个路径的坑：

text
程序中如果有定义检查点文件的保存路径 savedir，则该路径必须是相对路径，且以 ./ 开头，
比如 ./data，不然运行时加载模型会出错。

这条在 Windows 上尤其容易踩。用 ./checkpoints 这种写法，别用裸目录名，也别在路径里混反斜杠。

十、SavedModel 与部署 #

checkpoint 是训练的中间产物。它默认你知道网络结构长什么样，知道变量怎么排列，知道输入要喂到哪个 placeholder。

但交付的时候，接手的人只会调一个 HTTP 接口。他不知道你的网络结构，也不该知道。

这就是 SavedModel 的定位：把「结构 + 权重 + 输入输出约定」打包成一个自包含的目录。

目录结构 #

text
saved_model/
├── saved_model.pb          # 图定义 + 签名
└── variables/
    ├── variables.data-00000-of-00001
    └── variables.index

variables/ 下面的内容，和 checkpoint 的 .data + .index 一模一样。差别全在 saved_model.pb：它里面除了图，还有 MetaGraphDef 里的一组 SignatureDef。

签名说的是：调用者要传什么、会拿到什么。

text
inputs:  {'input_x': TensorInfo(dtype=DT_FLOAT, shape=(-1, 227, 227, 3))}
outputs: {'softmax': TensorInfo(dtype=DT_FLOAT, shape=(-1, 10))}

有了这个，加载方不用看代码就知道怎么喂、拿到什么。这也是它能跨语言的原因：C++、Java、Go 的 runtime 都只认签名，不认 Python。

保存：两种写法 #

TF 1.x 的写法：

python
import tensorflow as tf

# ... 搭图，定义 input_x、pred ...

with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())
    # 训练......

    builder = tf.saved_model.builder.SavedModelBuilder('./saved_model')
    builder.add_meta_graph_and_variables(
        sess,
        [tf.saved_model.tag_constants.SERVING],
        signature_def_map={
            'predict': tf.saved_model.signature_def_utils.predict_signature_def(
                inputs={'input_x': input_x},
                outputs={'scores': pred})
        })
    builder.save()

TF 2.x 的写法短很多：

python
model.save('./saved_model')

tf.keras.Model.save 传目录路径就是 SavedModel 格式，传 .h5 结尾就是 HDF5 格式。HDF5 只存权重和结构，没有签名，不能直接给 TF Serving 用。

tag 是什么 #

add_meta_graph_and_variables 的第二个参数是 tag 集合。一个 SavedModel 里可以放多份图，用 tag 区分：

tag 用途
serve 推理用，最常用
train 训练用，包含优化器
gpu 指定在 GPU 上跑
tpu 指定在 TPU 上跑

加载时要指定同一个 tag：

python
loaded = tf.saved_model.load('./saved_model')

或者老写法：

python
with tf.Session(graph=tf.Graph()) as sess:
    tf.saved_model.loader.load(
        sess, [tf.saved_model.tag_constants.SERVING], './saved_model')
    graph = tf.get_default_graph()
    input_x = graph.get_tensor_by_name('input_x:0')
    pred = graph.get_tensor_by_name('pred:0')
    result = sess.run(pred, feed_dict={input_x: batch})

tag 对不上会报 No assets in SavedModel 或 Could not find meta graph。这是最常见的加载失败原因之一。

用签名调用 #

推理性价比最高的方式是按签名调，不碰具体张量名：

python
import tensorflow as tf

loaded = tf.saved_model.load('./saved_model')
infer = loaded.signatures['serving_default']

result = infer(tf.constant(batch))
print(result['scores'])

infer 是个可调用对象，输入输出都用签名的键名。网络内部改了张量名，这段代码不用改。

对比一下三种加载方式：

方式 需要知道张量名 需要知道结构 适用
saver.restore 要 要 续训
loader.load + get_tensor_by_name 要 不用 调试、老代码
signatures['serving_default'] 不用 不用 生产推理

部署时的三个去处 #

SavedModel 出来之后，去向有三种：

目标 怎么转 典型场景
TF Serving 直接吃目录 服务端一个 HTTP/gRPC 接口
TFLite TFLiteConverter.from_saved_model 手机、嵌入式
TensorRT trt.TrtGraphConverter 服务端极限延迟

转 TFLite：

python
converter = tf.lite.TFLiteConverter.from_saved_model('./saved_model')
tflite_model = converter.convert()
with open('model.tflite', 'wb') as f:
    f.write(tflite_model)

注意 TFLite 对算子的支持有缺口。自定义算子、有些动态形状、部分 tf.image 操作转不过去，会在 convert() 的时候报错。上线前先在目标设备上跑一遍。

一个常见误区 #

有人以为 SavedModel 存了图，就不用管输入预处理了。

不对。SavedModel 只包含图里定义过的东西。你在 Python 里做的那些 cv2.imread、resize、/ 255.0，不在图里，不会被保存。

两种处理：

  1. 把预处理写进图里。input_x 收原始 uint8，图里做 cast + resize + 归一化。这样调用方只传原图。
  2. 把预处理写进文档。调用方自己保证输入格式。

第一种对部署方友好，第二种对训练方简单。实际项目里两者常常混着做：resize 和图内归一化进图，读文件和颜色空间转换留在外面。

如果选了第一种，图里就会多一堆 tf.image 算子。这些算子在某些推理引擎上支持不好，转 TFLite 时会卡住。这是个要提前想清楚的取舍。

十一、恢复训练的完整流程 #

到这里，数据管道和模型保存都讲完了。这一章把它们拼起来，回答一个实际问题：训练跑到一半断电了，怎么接着跑？

恢复训练不只是 saver.restore 一行。要恢复的东西有四样：

要恢复的 存在哪 丢了会怎样
模型权重 checkpoint 的 .data 从头练
优化器状态 checkpoint 的 .data（Adam 的动量） loss 会跳一下，收敛变慢
迭代步数 checkpoint 文件名或 global_step 变量 学习率调度错位、日志断档
数据管道位置 一般存不了 一个 epoch 重头读，或跳过一部分样本

前三样 TensorFlow 帮你管，第四样要自己设计。

标准骨架 #

python
import tensorflow as tf
import os

savedir = './checkpoints'
savefile = 'model.ckpt'
max_steps = 100000
save_every = 1000

# 全局步数，必须建成变量，不能是 Python 整数
global_step = tf.train.get_or_create_global_step()

# ... 搭图：数据管道、模型、loss、train_op ...
# train_op 要用 global_step 自增，见下面的说明

saver = tf.train.Saver(max_to_keep=3)

with tf.Session() as sess:
    sess.run(tf.global_variables_initializer())
    sess.run(tf.local_variables_initializer())   # 队列的 epoch 计数在这里

    ckpt = tf.train.latest_checkpoint(savedir)
    start_step = 0
    if ckpt is not None:
        saver.restore(sess, ckpt)
        start_step = sess.run(global_step)
        print('从第 {0} 步恢复'.format(start_step))
    else:
        print('没有找到检查点，从头开始')

    coord = tf.train.Coordinator()
    threads = tf.train.start_queue_runners(sess=sess, coord=coord)

    for step in range(start_step, max_steps):
        _, loss_val = sess.run([train_op, loss])
        if step % 100 == 0:
            print('step {0}  loss {1}'.format(step, loss_val))
        if step % save_every == 0 and step > 0:
            saver.save(sess, os.path.join(savedir, savefile), global_step=step)

    coord.request_stop()
    coord.join(threads)

几个不能省的细节：

  • tf.train.get_or_create_global_step() 返回一个 int64 变量。它会被 Saver 一起存下来，所以恢复后 sess.run(global_step) 拿到的是断电前的步数。
  • train_op 必须让它自增。有两种写法：
python
train_op = optimizer.minimize(loss, global_step=global_step)

或者手动：

python
step_op = tf.assign_add(global_step, 1)
with tf.control_dependencies([step_op]):
    train_op = optimizer.minimize(loss)

第一种简单，推荐。第二种在需要精确控制自增时机时用。

  • 用队列的话，tf.local_variables_initializer() 在恢复后要再跑一次。epoch 计数器是 local variable，restore 不管它。

学习率也要能续 #

学习率衰减如果按步数算，恢复后自动接上：

python
lr = tf.train.exponential_decay(
    learning_rate=0.1,
    global_step=global_step,
    decay_steps=10000,
    decay_rate=0.9,
    staircase=True)

global_step 一恢复，lr 就自动算对了。

如果按 epoch 算，就要把 epoch 也存下来：

python
start_epoch = tf.Variable(0, dtype=tf.int32, name='start_epoch')

或者更省事，用 global_step 反推 epoch，别单独存。

数据管道的位置问题 #

这是最难处理的一块。checkpoint 能存变量，但存不了「读到第几个文件、队列里还剩什么」。

三种策略：

策略一：每个 epoch 存一次，恢复时从 epoch 开头重来

最省事。代价是丢掉最多一个 epoch 的进度。

python
for epoch in range(start_epoch, total_epochs):
    for batch in train_ds:
        sess.run(train_op, feed_dict=...)
    saver.save(sess, os.path.join(savedir, savefile), global_step=epoch)

用 tf.data 的时候，ds 是可重新创建的。恢复后重建一遍 ds，从头读这个 epoch，逻辑干净。

策略二：按步数存，恢复后跳过相应样本

tf.data 支持跳过：

python
ds = ds.skip(start_step * batch_size)

前提是数据顺序在每个 epoch 完全一致（shuffle=False，或者 shuffle 的种子固定）。一旦打乱了，跳过的样本就不等于已经训练过的样本。

策略三：不分 epoch，只看总步数

大数据集最常用的做法。数据集用 repeat() 变成无限流，训练按步数跑，存也是按步数存。恢复时不关心 epoch 边界，重建管道继续跑。

python
ds = ds.repeat()
ds = ds.shuffle(10000)
ds = ds.batch(32)
ds = ds.prefetch(tf.data.AUTOTUNE)

代价是每个 epoch 没有明确的起止点。要评估就在固定步数上做。

三种策略的取舍：

策略 实现难度 丢多少进度 适合
按 epoch 存 低 最多一个 epoch 小数据集，epoch 短
按步数 + skip 中 零 顺序固定的数据集
无限流 + 按步数 低 零 大数据集，长期训练

恢复后验证这几件事 #

续训最怕的是「看着在跑，其实练歪了」。恢复后先做四个检查：

  1. 步数对不对。 print(sess.run(global_step)) 应该等于断电前的步数附近。
  2. loss 有没有跳变。 恢复第一个 batch 的 loss 应该和断电前最后一个 batch 差不多。差一大截说明变量没对上，或者数据管道从不同的位置开始了。
  3. 学习率对不对。 print(sess.run(lr)) 应该等于衰减后的值，不是初始值。
  4. 变量名有没有漏。 加一句检查：
python
for v in tf.global_variables():
    print(v.name, v.shape)

变量列表应该和断电前一样长。少了说明 Saver 建的位置不对，多了说明图被重建过。

第 2 条最容易被忽略。loss 跳变的原因是优化器状态没恢复：只恢复了权重，Adam 的动量归零，第一步更新会偏大。用 tf.train.Saver() 不指定变量就会连优化器槽一起存，避免这个问题。

迁移学习和续训的区别 #

两件事经常被混。区别在于要不要优化器状态：

场景 恢复什么 Saver 怎么写
续训（断电恢复） 权重 + 优化器状态 + 步数 tf.train.Saver()
微调（换任务） 只要权重 tf.train.Saver({name: var}) 排除最后的层
蒸馏 / 特征提取 只要权重，冻结 同上，加 trainable=False

续训要全量恢复，因为训练是同一个过程。微调只要权重，因为优化器状态在新任务上没意义——新任务的梯度分布不一样，旧的动量是噪声。

十二、易错点速查 #

这一章把所有踩过的坑按出现频率排一遍。

数据管道 #

症状 原因 解法
程序卡住不动，不报错，CPU 0% 没调 start_queue_runners，或队列被 request_stop 了 补上启动；检查 coord.should_stop()
退出时报 Session has been closed 用了 with tf.Session()，入队线程还在跑 改用显式 sess 加 request_stop + join
OutOfRange 异常 num_epochs 走完了，reader 读到队列结束标记 正常结束信号，捕获它即可
epoch 数不对，读超或提前结束 忘了 tf.local_variables_initializer() 恢复后补一句
batch 里全是同一类 分片按类别分，且没打乱 写 TFRecord 前打乱样本列表；interleave 交错读
打乱不生效 shuffle 的 buffer_size 太小 至少 10000，或等于数据集大小
GPU 利用率低，CPU 打满 没 prefetch，或 map 没并行 加 prefetch(AUTOTUNE) 和 num_parallel_calls(AUTOTUNE)
IO error 硬盘坏道（机械盘常见） 换盘，不是代码问题

TFRecord #

症状 原因 解法
InvalidArgumentError: Feature: xxx 读的字段名和写的对不上 对齐 features={} 里的 key
FixedLenFeature 解析失败 类型对不上，写 int64 读 int32 类型严格一致
图像变形 reshape 的尺寸和写入时不一致 写入和读取共用一个尺寸常量
文件读不完整 忘了 writer.close() 补上，或用 with 管理
单文件几百 GB 没分片 按 1 万样本一片

Saver 与 checkpoint #

症状 原因 解法
保存的文件是空的 Saver 建在变量声明之前 移到所有 tf.Variable 之后
KeyError: 'w:0' 张量名少写了 :0 写成 'w:0'
NotFoundError: Key xxx not found 恢复的变量在 checkpoint 里没有 名字对齐；或改用 latest_checkpoint
恢复后 loss 跳变 优化器状态没恢复 用不传参的 tf.train.Saver()
变量重名冲突 import_meta_graph 前没 reset 图 tf.reset_default_graph()
磁盘写满 max_to_keep=None 设成 3 到 5
载入最新模型报错 savedir 用了裸目录名 用 ./xxx 相对路径

五个最贵的坑 #

按损失排序，前面五个最值得记：

  1. 队列卡死。不报错，进程挂着，你以为在跑。解决靠 start_queue_runners 和 Coordinator。
  2. Saver 位置写错。存了空文件，等你训练三天才发现。一个 print(len(tf.global_variables())) 就能提前发现。
  3. 批次里全是同一类。训练 loss 不降，排查半天找不到原因。根因在分片策略。
  4. 忘了 local_variables_initializer。epoch 数不对，数据读得莫名其妙。
  5. 优化器状态没恢复。续训后 loss 跳变，你以为是数据问题。

五个坑的共同点：都不报错。TensorFlow 不会告诉你「你忘了启动队列线程」，它只会安静地卡住；也不会告诉你「你的 batch 里全是猫」，它只会安静地训出一个烂模型。

所以训练开始前先跑一遍检查：

python
# 变量数量对不对
print('变量数：', len(tf.global_variables()))

# 一个 batch 的形状和标签分布
imgs, labels = sess.run([images_batch, labels_batch])
print('形状：', imgs.shape, labels.shape)
print('标签：', labels)

# 全局步数
print('步数：', sess.run(tf.train.get_global_step()))

三行输出，能挡掉上面五个坑里的大部分。花十秒，省三天。
