面条代码和馄饨代码

面条代码是一种特指冗长、控制结构复杂、混乱且难以理解的代码。这种代码通常让人感到头疼，因为它们不易于维护和扩展，会导致项目延误和开发者的挫折感。

直到某一天，在《Code Complete》一书中看到了对"面条代码"的定义和描述，才意识到原来有很多人都对这种情况感到愤恨。看来，像一样在代码面前倍感无力的人并不在少数。接着，在《The Clean Coder》中发现，关于方法长度和类规模的讨论提到："第一条规则是要短，小；第二条规则是要更短。"这让感到释然——能在复杂的编码环境中感到困惑并不丢人。

正如某位著名的工程师所言，一个团队所写的代码应该考虑到团队中最笨的人也能轻松理解。只有这样，团队整体的生产效率才能够提升。可能会选择将团队中表现不佳的成员踢出局，但剩下的人中仍然会有理解力相对较低的成员。

基于此，们只能依赖于大多数程序员的平均理解能力。研究表明，大多数人对于 7 ± 2 个元素的事物有较好的控制力。

面向对象的设计 #

在使用"面向对象"的设计范式时，如果高度重视"消除重复"、"分离关注点"和"清晰表达"，结果自然会生成一大批短小精干的类和方法。即使在使用其他编程范式，如面向过程或函数式编程的情况下，若同样将这些原则放在首位，编写出面条代码的概率也会显著降低。

实际上，某位大咖曾在演讲中提到："在面向对象的系统中，不可能产生面条代码。"这再一次强调了结构化编程和良好设计的重要性。

难解的代码：面条代码与馄饨代码 #

可能开始怀疑："们的系统都是用 C++ 或者 Java 写的，为何会存在大量的‘面条代码’？" 这引发了一个有趣的讨论。

面向对象与面条代码 #

首先，重要的一点是，"面向对象"本质上是一种编程范式，这种范式与具体语言的关系并不直接。也就是说，尽管某些语言（如 Java、C++）被称为面向对象语言，但使用面向过程的语言（如 C）也可以创建出面向对象的系统。相反，某些号称是面向对象的系统，如果结构不合理，也可能并不真正符合面向对象的原则。

在良好的面向对象思想指导下，面条代码的出现几乎是不可能的。但在一些依然使用"类结构"的系统中，面条代码却横行，这些系统通常被称为Spaghetti with meatballs。这就意味着，尽管它们采用了面向对象的结构，实际上它们可能与传统的面条代码的混乱无异。

阐述馄饨代码 #

那么，这并不是全部。演讲者进一步提出，虽然面向对象系统中通常难以找到面条代码，但可能会遭遇Ravioli Code，即"馄饨代码"。顾名思义，馄饨代码由许多结构松散的小部分组成——方法、类或包等。这些部分就像形态各异的馄饨，互不相连却又处于同一个锅里。

显然，从演讲者的角度，馄饨代码并不是一种赞美。他认为，简单地将面条代码重构为馄饨代码只不过是将一种问题转换成另一种形式。这样的看法并非个别现象。在咨询工作中，多次听到这样的反馈——与面条代码相比，馄饨代码往往让人更加难以理解和追踪。

何以见得？ #

最初，对于这种反对意见，感到深深困惑，因为这与自己的经验相悖。但当意识到持有此观点的不只是少数人时，开始思考造成这种情况的原因。

在很多工程师看来，面条代码中的大函数，尽管复杂，却能够完整地描述整个过程及其细节。而在馄饨代码中，这些过程和细节往往被拆分成更小的部分，分散在不同的类和方法之间。因此，当试图理解某个过程或算法时，会不断在不同的类和方法之间跳来跳去。例如，如果使用了多态，将面临更大的困扰：永远不知道到底哪个子类的方法正在被执行。

面向过程 vs. 面向对象 #

面对程序的复杂性，工程师需要认识到面向过程与面向对象的思维方式及其解决问题的方式存在巨大的差异。

  • 面向过程的思维方式侧重于算法或具体的流程。可以把它想象成一条流水线，或将自己视作一个亲力亲为的 CPU。这里的重点在于理解每一步骤是如何执行的，每个步骤之间的连接则可能比较单一，形成一个相对线性的结构。

  • 面向对象则更关注机制的构建。可以将目标系统视作一个由多个零件构成的机器，或者是一种高效运行的组织。在这种情况下，理解结构（类、类的职责、类之间的关系）成为首要任务。一旦掌握了类的架构，后续理解类之间的互动就会相对容易。

组织架构与事务流程 #

当试图理解某个机构的具体事务流程时，最有效的方式是首先了解其组织结构，了解各部门的职责以及它们之间的关系。在这个基础上，再去分析一个具体事务的流程，理解起来将会顺畅许多。相反，如果没有了解组织架构就直接启动详细事务的探讨，可能会希望某个部门或者个人能完成所有事情，这样就会倍感困扰。

分离 "What" 与 "How" #

另外，理解馄饨函数时也需要转换思维。面条代码中的函数不仅仅在描述"做什么（What）"，同时也在展示"怎么做（How）"。这使得函数内部充斥着大量实现细节，导致读者必须依赖注释或自己总结细节，才能最终明白"到底在做什么"。

而馄饨函数则将这两个关注点分开：使用更高层的抽象来描述"What"，而细节则在底层展示"How"。最终，这两个部分结合起来就形成了对算法的完整描述。要达到这种效果，合理的命名至关重要。

通过这种方法，代码的可读性更强，更符合人类的认知习惯。然而，对于那些已经掌握"做什么"并只希望了解"怎么做"的工程师来说，馄饨代码可能会额外增加函数间跳跃的复杂度。

综合考虑 #

然而，世上没有免费的午餐。既然问题的本质是复杂的，付出一定的时间成本是不可避免的。要成为一名出色的程序员，必然需要评估各方案的整体成本与收益，选择最合适的方式。这个选择不仅仅是编程语言或风格的问题，而是一种思维方式的选择。

馄沌代码——更好的成本受益比 #

复杂性是影响代码可理解性的重要因素。"面条代码"的复杂性常常体现在单个函数内部的细节数量和逻辑控制上，而"馄饨代码"的复杂性则更体现在函数或类的数量和结构。这种看似简单的转变实际上带来了更多的优势。馄饨代码的意义在于其可理解性、可重用性和灵活性，更符合"高内聚、低耦合"的设计原则。

复杂性与可理解性 #

尽管面条代码在实际应用中普遍存在，但其受到的批评却不计其数。相对而言，馄饨代码在面向对象的开发环境中受到了广泛支持，甚至被视为整洁代码的典范。举个例子，假设一个项目使用面条代码进行开发，随着时间的推移，维护人员会发现难以跟踪和修改原本的功能。而采用馄饨代码时，结构分明、易于理解，使得不同开发者能够快速上手并进行有效的协作。

简单与复杂的误区 #

在许多团队中，短小的函数并不等同于馄饨代码。自从"高圈复杂度"被认定为面条代码的特征后，许多团队开始规定"圈复杂度红线"，还有一些团队限制单个函数的代码行数上限。然而，仅仅依赖这些限制常常导致产生"短小代码"，但这种短小并不能保证代码的可理解性和可维护性。馄饨代码强调的是松散耦合和表达的清晰性。

案例分析 #

例如，一个看似简单的函数可能只有一行代码，但所包含的细节却令其变得难以理解：

cpp
#include <cmath>
#include <ctime>

double calculateMoonPhase() {
    return putchar((currentTime() - moonOffset) % 2551443);
}

这个程序可以编译并成功运行，但很少有开发者能够通过简单的阅读来完全理解其功能。

一个更适宜的例子是：

cpp
#include <cmath>
#include <ctime>

double calculateMoonPhase() {
    double phase = (time(NULL) % 2551443) / 405859.0;
    return determinePhase(phase);
}

在这个例子中，通过提取函数和定义常量，们使得代码的意图更加清晰。尽管增加了新的代码元素，这却是一个值得的投入。

抽象与细节的关系 #

如果一个函数的表述缺乏"对称性"，或者无法达到"抽象"与"细节"之间的有效分离，即使函数非常简单，也会导致理解上的困难。因此，编程的真实目标是"消除重复"和"清晰表达"，而不是单纯追求"馄饨代码"或"短小函数"。"馄饨代码"只是一个结果，而非们的初衷。

消除不必要的复杂度 #

控制不必要的复杂度是编写高质量代码的重要原则。当代码中的抽象或函数并未对实现功能、消除重复或提升表达能力带来实际帮助时，这些元素就不应存在。正如"简单设计"原则所述：

如果一个代码元素对于满足功能、消除重复，或者提高表达力都没有用处，那么它就不应该存在。

在没有重复的情况下，对于先期设计所引入的复杂性，开发者应当谨慎评估其价值。

一旦出现"重复"，为了消除它所引入的复杂度，是必须承受的代价。尽管这可能会降低可理解性，但在一般情况下，"重复"所带来的设计问题和维护成本更为严重。重复代码不仅意味着更高的维护成本，还可能造成逻辑错误的多次扩散。

cpp
if (isValid()) {
    area = calcArea();
} else {
    return INVALID_AREA;
}

通过上面的例子，们可以看到，简化的逻辑能够提升可理解性，让更多开发者轻松明了代码意图。
