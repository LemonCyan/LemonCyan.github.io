LemonCyan's BlogDeploy #

用 Obsidian 写笔记，用自建的 md → html 生成器（1.site/）把笔记渲染成静态站点， 经 GitHub Actions 发布到 GitHub Pages。

站点地址：https://lemoncyan.github.io/

这份 README 本身也会被渲染成站点里的「关于本站」页面（/about/）， 所以在网页上看到的排版和 GitHub 上基本一致。

Hexo 已完全移除（主题、_config.yml、根 package.json、public/、db.json 全部删除）。 现在只有一套生成器，就在 1.site/。

📁 项目结构 #

✅ 哪些目录会发布？只看目录名第一个字符 #

这是唯一判据，没有任何白名单 / 排除清单需要维护：

目录名 是否发布 说明
A.平台系统 M.新领域 Z.某目录 ✅ 发布 单个大写字母 + 分隔符（. - _ 、）
1.site 2.img 9.整理归档 ❌ 不发布 数字开头 —— 放工具、图片、私人/归档内容
api.xxx plainfolder ❌ 不发布 小写字母或无编号前缀，不匹配规则
.git .obsidian .agent ❌ 不发布 点开头

规则实现在 1.site/src/topdirs.js 的 PUBLISH_PATTERN = /^[A-Z][.\-_、．]/：

js
export function discoverTopDirs() {
  for (const ent of fs.readdirSync(ROOT, { withFileTypes: true })) {
    if (!ent.isDirectory()) continue;
    if (!PUBLISH_PATTERN.test(ent.name)) continue;   // ← 唯一判据
    if (!hasMarkdown(full)) continue;                // 空目录不出卡片
    ...
  }
}

所以：

  • 加内容 → 建 M.新领域/ 丢 md 进去，直接构建就上线
  • 放私人/工具/图片 → 用数字开头（2.img、9.整理归档），天然不会上网

内容约定：文章标题取文件名（去掉 1. 2.1. 之类序号前缀），分类取目录层级， 不需要 front matter —— 写了也会被忽略。唯一例外是 --- 包起来的块会被整段丢弃。 顶层目录的显示名与配色也可以不配置：会自动去掉 A. 前缀、按名字哈希取色；想自定义就在 1.site/src/config.js 的 topDirs 里补一条。

🖥️ 桌面 app #

桌面图标不再是内容分类（分类入口只在顶栏），而是 3.app/ 下的独立 html 页面： 一个 html 文件 = 桌面上的一个图标，构建时自动发现，不需要登记。

3.app/tiktok.html          → dist/apps/tiktok.html          图标「短视频聚合」
3.app/radar.html           → dist/apps/radar.html           图标「GitHub Radar」

3.app/ 里除了 html，还有 assets/（app 的外部 css/js）和 fetch/ （构建期数据抓取脚本，如 fetch/fetch-radar.mjs）——构建器只把顶层 .html 当 app，其余文件不会变成图标，fetch/ 下的脚本也不会复制到 dist/。

app 若需要外部 .css / .js，放进 3.app/assets/<app 名>/ 子目录，在自己 html 里用 相对路径引用（如 ./assets/quant/terminal.css）即可 —— 构建时会连同子目录结构一起复制到 dist/apps/assets/<app 名>/，构建器不需要任何登记。

新增 app 只要往 3.app/ 丢一个 html（写 <title>、<style>、<body> 内容即可）， 重新构建就出现在桌面上。顶栏 / 壁纸 / 图标栏 / 窗口标题栏由构建器统一套上， app 自己的样式与脚本留在该 html 内，不进 1.site/static。

约定与可选元数据（app-icon / app-color / app-scheme / app-scroll）见 3.app/README.md，实现见 1.site/src/apps.js 与 1.site/src/templates/app.html。

🖼️ 本地图片 #

2.img/ 是本地图片仓库，构建时会整目录复制到 dist/img/。

markdown 里按 Obsidian 的写法引用源码路径就行，不用管发布后的地址：

markdown
![说明文字](2.img/placeholder.png)
![说明文字](/2.img/placeholder.png)   <!-- 带前导斜杠也认 -->

构建时会把首段是 2.img 的图片地址自动改写成 /img/...，所以 2.img/x.png、./2.img/x.png、/2.img/x.png 三种写法都能正常显示， 而在 Obsidian 里打开 .md 也能看到图（这是不改路径的原因）。

2.img/placeholder.png 是一张占位图，可以直接删掉换成自己的图； 要新增图片目录时，在 1.site/src/config.js 的 staticDirs 里加一条 { from, to } 即可。

🚀 本地编译与测试 #

整个站点是纯静态的：先构建、再起本地服务器看效果。所有命令都在 1.site/ 下执行。

环境要求 #

依赖 版本 说明
Node.js 20.11+（推荐 24，与 CI 一致） 生成器用了 import.meta.dirname，20.11 以下会报错
npm 随 Node 附带即可 仓库已有 1.site/package-lock.json

Node 版本可在 1.site/ 下用 node -v 确认。CI 用 setup-node@v7 固定 Node 24， 本地尽量对齐，避免「本地能跑、Actions 报语法错」。

第一次：从零跑一遍全量构建 #

Windows PowerShell 与 macOS / Linux 的命令相同：

bash
cd 1.site
npm ci          # 首次装依赖；没有 lockfile 时才用 npm install
npm run build   # = node build.js && pagefind --site dist

npm run build 分两步：

  1. node build.js —— 扫描顶层 A. ~ Z. 目录里的 md，渲染成 HTML， 产出 tree.json / sitemap.xml / robots.txt；static/ 原样复制到 dist/， 2.img/ 复制到 dist/img/，3.app/*.html 套上外壳生成 dist/apps/*.html
  2. pagefind --site dist —— 对产物建中文全文索引（约 30 秒）

全量约 1~1.5 分钟（本机实测：渲染 30~55 秒 + 索引 33 秒），末尾会打印 完成：NNNN 个 HTML，产物 NN MB。产物在 1.site/dist/，被 .gitignore 忽略，不提交。

起本地预览 #

bash
npm run serve                        # 默认 http://127.0.0.1:4173/
node build.js --serve --port 4399    # 端口被占用时换一个

浏览器打开输出的那行地址即可。serve 会先全量构建一次、再起一个静态服务器，所以：

  • 它不会监听文件变化：改了 md / css / js 后，按 Ctrl+C 停掉再重跑一次
  • 浏览器可能缓存旧的 css / js，改完前端样式记得 Ctrl+F5 强制刷新
  • 预览模式会保留已有的 dist/pagefind/ 索引（临时挪到 .pagefind-cache 再放回）， 所以之前跑过一次全量 npm run build，搜索框就能用

只调前端样式时，别跑全量 #

bash
npm run build:50                              # 只渲染前 50 篇，几秒出结果
node build.js --limit 50 --filter "A.平台系统"   # 再按路径关键字缩小范围

⚠️ 两个坑：

  • build.js 每次都会清空 dist/ 再重建，所以 build:50 之后产物是不完整的
  • build:50 和 --filter 不会跑 Pagefind，此时 dist/pagefind/ 不存在，搜索会报 404

因此要检查完整效果或准备发布，最后一定要再跑一次 npm run build。 如果只想补索引而 HTML 已经是对的，可以单独执行：

bash
npm run index        # = pagefind --site dist

验证清单 #

刷新页面后逐项确认，本地就算跑通了：

  • 打开开发者工具 Console 无红色报错；Network 里 /js/window-manager.js、/tree.json
  • 搜索框能出结果（/pagefind/pagefind.js
  • 拖动窗口标题栏时窗口严格跟随鼠标
  • 随便点开几篇文章、一个 3.app/ 页面和 /about/

常见问题 #

现象 处理
Cannot find module / import.meta.dirname 报错 Node 版本过低，升到 20.11+（推荐 24）；或依赖没装全，重跑 npm ci
搜索窗口报 404 / 一直是「加载中」 只跑了 build:50 或 serve 时还没有索引 → 跑一次 npm run build
EADDRINUSE（端口被占） 用 node build.js --serve --port 4399 换端口，或先关掉占用 4173 的进程
构建中途 JavaScript heap out of memory 2000+ 篇要驻留内存；PowerShell 用 $env:NODE_OPTIONS='--max-old-space-size=4096'（bash 用 NODE_OPTIONS=--max-old-space-size=4096 npm run build），CI 已默认设好
pagefind 报找不到平台二进制 它按平台装 @pagefind/windows-x64 等 optional 依赖；别用 --no-optional，也别跨系统直接拷贝 node_modules，删掉重跑 npm ci
改了 css / js 页面没变化 浏览器缓存 → Ctrl+F5；另外确认改的是 1.site/static/ 下的源文件，改 dist/ 会在下次构建被覆盖
本地 Mermaid 图表不显示 渲染器走 jsDelivr CDN，离线预览会保留源码块并标注失败，联网后正常
本地改好了，线上没变 本地构建只产出 dist/，不会自动部署；推送到 main 触发 Actions 才会发布

生成器自身的目录结构、模板与配置说明见 1.site/README.md， 桌面 app 的写法见 3.app/README.md。

🧱 生成器要点 #

环节 做法
扫描 只发布大写字母 + 分隔符开头的一级目录；数字开头永不发布
标题 titleFromFilename() 去扩展名 + 去序号前缀（纯日期与连字符编号保留）
分类 目录层级即分类，前端渲染成侧栏树 + 目录索引页
URL /<目录>/<子目录>/<文件名>/，扁平、无日期、保留中文
Markdown markdown-it 15 + anchor / footnote / task-lists
Obsidian 语法 callout（15 种）、wikilink、%%注释%%；刻意不启用 ==高亮==
公式 KaTeX（块级 $$ + 保守的行内 $，含 CJK 的 $…$ 不解析）
代码 highlight.js（构建期）+ 复制按钮；mermaid 走 CDN 按需渲染
搜索 Pagefind 1.6，按 <html lang="zh-CN"> 自动中文分词
目录树 单文件 /tree.json + 客户端渲染（否则每页内嵌 200KB 目录树）
阅读窗 文章页默认最大化铺满，可点按钮还原为窗口（选择写入 localStorage）
图片 2.img/ 整目录复制到 dist/img/，markdown 里写 /img/xxx.png 或 2.img/xxx.png（构建时自动改写）
根文档 仓库根的 README.md 单独渲染成 /about/（1.site/src/config.js 的 rootDoc），顶栏与首页卡片都有入口

详细设计见 9.整理归档/site-design.md，生成器自身说明见 1.site/README.md （这两个目录都不发布，只在仓库里看）。

🚀 部署流程 #

  1. 在 Obsidian 里写笔记，md 落进对应的 A.平台系统/ … L.项目与设计/ 目录
  2. 提交并推送到 main
  3. GitHub Actions（.github/workflows/workflow.yml）： npm ci（1.site/）→ 抓取 ETF 与 radar 数据（3.app/fetch/fetch-etf.mjs、fetch/fetch-radar.mjs） → npm run build（生成器 + Pagefind）→ 校验 dist/ → 发布到 LemonCyan/LemonCyan.github.io 的 main 分支 → GitHub Pages 提供访问

工作流还带一个 schedule: cron '17 0 * * *'（每天 UTC 00:17 = 北京时间 08:17）， 到点自动重跑一次整条链路：ETF 是日频数据、radar 日榜也是，两者共用这一趟运行。

工作流要点 #

  • 只读权限（permissions: contents: read），发布用 secrets.ACTIONS_DEPLOY_KEY（deploy key）
  • npm 缓存按 1.site/package-lock.json 命中
  • concurrency 保证同一分支只有一次部署在跑，新推送取消旧运行
  • timeout-minutes: 20
  • 发布前校验 dist/index.html 与 dist/pagefind/ 都存在，避免推空目录
  • 目标仓库用 keep_files: false（默认）清掉 Hexo 时代残留路径；不用 force_orphan —— 那会每次重建单提交分支、全量重传 ~125MB，正是之前 Pages deploy 卡 600s 超时的成因
  • radar 数据不写回仓库：抓取步骤只改 runner 的临时工作区，脚本里没有任何 git 命令， workflow 也不 commit，数据直接随构建产物发到 Pages。所以 git log 不会多出机器人提交。
  • 抓取步骤都带 continue-on-error: true，且 fetch/fetch-radar.mjs 内有质量闸门（至少 3 个源成功、 每个窗口至少 5 条仓库），抓挂时不覆盖旧数据、也不阻断站点发布。radar 覆盖 24 小时 / 7 天 / 30 天 三个窗口，日榜有 GitHub 官方与 Trendshift 两个独立源交叉验证。

⚠️ 已知限制 #

  • 1.site/dist/ 约 125MB（HTML 85MB + Pagefind 索引 38MB），其中最大的单页约 1MB
  • 4 处 wikilink 目标不存在，原样输出 [[…]]
  • 22 处图片引用在仓库里找不到文件（历史遗留的 .note_files/ 等）
  • Mermaid 依赖 jsDelivr CDN；离线预览时图表不显示
  • 右侧「本页目录」需要文中有 ≥2 个标题，单标题页不显示
