自建静态站设计方案（md → html → lemoncyan.github.io） #

目标：不依赖 Hexo，自写生成器把笔记的 markdown 转成静态 HTML， 前端参考 PostHog Handbook（桌面 + 窗口 + 左目录 / 右正文），推送到 LemonCyan/LemonCyan.github.io。 本文所有数字均来自对本仓库 2008 篇 md 的实测，不是估算。

实施后记（2026-11-10）：方案已落地，且比本文更进了一步 —— 内容目录已从 source/_posts/<X.领域>/… 整体 git mv 到仓库顶层（A.平台系统/ … L.项目与设计/， 另有 Z.日志记录/，共 13 个内容目录），Hexo 全部移除。下文凡提到 source/_posts 的路径， 现在对应仓库顶层的同名目录；生成器代码目录为 0.Site/（本文写作时叫 site/，后改 ZSite/）， 部署步骤也已简化为 0.Site/ 下 npm run build（不再有 hexo clean、不再双构建）。 发布规则（后续补充）：只看目录名首字符 —— A.~Z. 开头的目录发布， 0.~9. 开头的目录永不发布（详见 0.Site/src/topdirs.js 的 PUBLISH_PATTERN）。

0. 先回答你的五个问题 #

问题 结论
评论系统能不能不要 能。giscus 只是 HTML 片段，去掉即可。现有 Discussions 只有 1 条 welcome 帖、0 条真实评论，无损失。
front matter 能不能不要 title 和 categories 能，date 绝对不能。详见 §2。
分类就是目录层级？tag 还有意义么 分类完全由目录推导，没有额外成本。tag 只有 27 篇在用，建议保留一个可选 tags: 但不做 UI 入口。

自建怎么部署到 lemoncyan.github.io，流程是什么 Actions 里跑生成器，产物用 deploy key 推到 LemonCyan/LemonCyan.github.io。沿用你现在的机制即可，详见 §6。

3. URL 方案 #

选定：扁平、无日期、无扩展名

/A.平台系统/Docker/Docker-Compose/
/I.数据与智能/05-信号处理/傅立叶分析：从周期现象到频域/

规则：

  1. 保留中文与 A. B. 前缀（不做 slugify，避免 Quartz 之外的转义麻烦）
  2. 空格 → -，/ \ : ? # % 移除或替换
  3. 每条 URL 输出 <slug>/index.html（尾斜杠友好，GitHub Pages 原生支持）
  4. 生成 url-manifest.json（源路径 → URL），重命名时用它写 301 映射

冲突检测实测：同目录下 basename 重复 0 组，所以扁平化不会撞车。 需要编码的字符：776 个文件名含空格或 %#?&=+，生成时统一用 encodeURI。

代价：URL 第三次变更（1-12→A-L → 去 .note → 去日期）。 但 giscus 只有 1 条 welcome 帖，没有评论历史要保，这是切换的最佳时机。

4. Markdown 方言怎么定（Obsidian vs GitHub vs 自建） #

4.1 三者关系的真相 #

CommonMark 0.31.2   ← 唯一有严格规范的地基
   ├── GFM (GitHub)      = CommonMark + 表格 + 删除线 + 自动链接 + 任务列表 + 脚注 + 告警块
   └── Obsidian flavor   = CommonMark + callout + wikilink + 嵌入 + 高亮 + 注释 + 块引用
  • GitHub：严格按 GFM。[[wikilink]] 是纯文本，==高亮== 是纯文本，%%注释%% 会原样显示。
  • Obsidian：不严格遵循 CommonMark（它的列表缩进、软换行、_ 强调规则都比 CommonMark 宽松）。
  • Hexo 现在用的 hexo-renderer-markdown-it-plus：markdown-it 13 + katex + toc-anchor + ins/mark/sup/sub —— 是第三种方言。

4.2 我的建议：做 GFM + Obsidian 子集 的超集 #

语法 处理方式 你的用量
CommonMark 基础 全支持 —
GFM 表格 / 删除线 / 任务列表 / 自动链接 全支持 259 / — / 18
GFM 脚注 全支持 22
> [!NOTE] callout 渲染成 PostHog 风格提示框，5 种类型各一色 133 ← 必做
[[note]] / [[note|别名]] 转成站内链接；解析失败降级为纯文本并记 warning 15
![[image.png]] 嵌入 支持图片嵌入；笔记嵌入降级为链接（用量 0） 0
==高亮== 不启用。你的语料里全是 x==1 误报，启用会把正文大段染色 ≈0
%%注释%% 构建期剥除 2
^block-id 块引用 解析但不渲染 0
Hexo {% tag %} 9 处逐个手工替换 9

关于 == 的特别说明：我抽出 93 个 ==...== 候选逐一核对， 92 个是 if Y==1、depth==0、A==2,B==1 这类正文里的等号表达式 （典型在 perfbook memory barrier142章节的中文翻译上.md）。 开 markdown-it-mark 会把这些全部渲染成高亮，是灾难。 这是不照抄 Quartz 的第一个理由。

4.3 渲染管线（最终选型） #

markdown-it 15.0.3
├── markdown-it-anchor 10.1.0       标题 id + 锚点
├── markdown-it-footnote 4.0.0      脚注
├── markdown-it-task-lists 2.1.1    任务列表
├── markdown-it-attrs               可选：{#id .class}
├── @shikijs/markdown-it + shiki 4.6.0   代码高亮（构建期，页面零 JS）
├── katex 0.19.1                    数学
├── mermaid 12.3.0                  图表（客户端按需加载）
└── 自写 obsidian-plugin.js         callout / wikilink / 注释剥离

选 markdown-it 而不是 unified/remark：markdown-it 的插件生态更直接， markdown-it-anchor 这类成熟插件开箱即用，而且你现有的 Hexo 也是 markdown-it 系， 渲染结果最接近现在的观感，迁移视觉差异最小。

6. 部署到 lemoncyan.github.io：现成机制直接复用 #

6.1 你现在的流程（已实测可用） #

本地写 md → git push 到 LemonCyan/BlogDeploy
   ↓ GitHub Actions: .github/workflows/workflow.yml
checkout → setup-node 24 → npm ci → hexo clean + generate ×2
   ↓ peaceiris/actions-gh-pages@v4（用 secrets.ACTIONS_DEPLOY_KEY）
推送到 LemonCyan/LemonCyan.github.io 的 main 分支
   ↓ GitHub Pages（build_type: legacy, source: main /）
https://lemoncyan.github.io/

6.2 换成自建生成器后 #

唯一变化是中间一行：

yaml
- name: Build
  run: node site/build.js          # 代替 npm run clean && npm run build

- name: Deploy
  uses: peaceiris/actions-gh-pages@v4
  with:
    deploy_key: ${{ secrets.ACTIONS_DEPLOY_KEY }}
    external_repository: LemonCyan/LemonCyan.github.io
    publish_branch: main
    publish_dir: ./site/dist

其余全部不动：同一个 deploy key、同一个目标仓库、同一个 Pages 配置。

6.3 部署阶段的坑（你已经踩过，必须记住） #

现象 原因 对策
deploy job 卡 600s 超时 一次性全量同步 145 MB artifact，Pages 的 syncing_files 有 10 分钟硬上限 控制产物体积 < 100 MB；首次上线可在目标仓库先推一个空提交触发增量
目标仓库里文件已更新，线上仍是旧版 同一次部署超时，Files 已写好但 CDN 未切换 目标仓库提一个单文件 commit，增量同步只需 ~19s

自建生成器的产物预计 80~100 MB（现在的 298 MB 主要浪费在归档页重复渲染）， 比现在健康得多。

6.4 构建性能 #

现在 Hexo 全量 1.5~4 分钟。自建生成器：

  • 2008 篇 md，markdown-it 单线程约 8~15 秒
  • shiki 高亮是瓶颈 → 用 --changed-only + dist/.manifest.json 做增量，只重渲改动文件
  • Workers 并行（worker_threads）可再压缩到 3~5 秒

7. 前端：PostHog 那套结构怎么拆 #

从 posthog.com/handbook 扒出来的骨架（可直接照抄层级）：

DesktopViewport            h-dvh, md:p-2
├── TopBar                 左：站点名 + nav；右：主题/搜索按钮
├── Aside (250px)          全局导航
└── DesktopViewport
    └── Desktop            壁纸层(absolute inset-0) + 桌面图标(nav)
        └── WindowList
            └── AppWindow  h-[95%] w-[80%] rounded-lg shadow-md
                └── AppWindowContent
                    └── ReaderView
                        ├── 左目录  basis-[250px]，@2xl 以下隐藏
                        └── 正文    max-w + 分档 padding

关键实现点：

需求 做法
窗口拖拽 / 缩放 / 最小化 / 层叠 手写 window-manager.js（约 200 行：pointerdown 起点、transform 位移、z-index 栈）或用 winbox（0.2.82，50 行接入）
壁纸切换 body[data-wallpaper] + CSS 变量，PostHog 用 data-scheme / data-skin 同款思路
移动端 @media (max-width: 768px) 下窗口变成全屏 sheet，左目录收进抽屉
左目录 构建期从 heading 提取，不要用客户端扫描 DOM（2008 篇里 h1 1667 / h2 1217 / h3 798，量大）
桌面 app 每个窗口一个 content-type，同一套 window.html 外壳：阅读器 / 搜索 / 标签图 / 时间线
搜索 pagefind 1.6.0，<html lang="zh-CN"> 即可中文分词，零配置

9. 风险清单 #

风险 等级 说明与对策
date 丢失导致时间线塌陷 高 §2.2 已证明 mtime/git 都不可用。保留 front matter date 或迁移 dates.json。
557 篇标题降级 中 建议 title 保留为可选覆盖。
URL 第三次变更 中 giscus 无历史评论，是切换窗口期；生成 manifest 备好 301 映射。
callout 误判 低 只认 ^> \[!(NOTE|TIP|IMPORTANT|WARNING|CAUTION)\] 五种，实测 133 处全命中。
== 误伤 低 不启用 markdown-mark 即可规避。

迁移期双系统漂移 中 P5 用子路径影子部署，验收通过后再切根路径。
