这篇讲 MCP（Model Context Protocol）：一套让 AI 助手访问外部工具与数据的开放协议。

讲什么：三个核心概念、Client/Server 架构、stdio 与 SSE 两种传输、配置文件怎么写、一个最小的 Python Server、Tools 与 Resources 的差别、调试方法、安全边界。

不讲什么：不逐条翻译协议规范，也不复述各家 SDK 的版本变更历史。SDK 在大版本之间调整过 API，照抄代码前先对一下你装的版本。

跨篇指路：要搭完整的本地 AI 工程环境，看同目录的 DSH 落地三篇（开发板部署、手机 Termux 部署、进阶与鉴权）；要把 AI 塞进日常编码流程，看 Vibe Coding 篇。

一、MCP 解决什么问题 #

1.1 没有 MCP 之前 #

一个 AI 助手能看到的东西只有两样：训练时吃进去的参数，以及当前对话窗口里你贴给它的上下文。

这两样都不包含你的硬盘、你的数据库、你公司内网的接口。你说「帮我查一下 test.db 里昨天失败的订单」，它只能回你一段代码，让你自己去跑。

想让 AI 真能动手，就得给它接工具。接法五花八门：

text
Claude Desktop → 自己写一套工具注册与调用
Cursor         → 自己写一套
自研 Agent     → 再写一套

每个 AI 应用都要重新实现一遍「怎么描述工具、怎么调用、怎么把结果喂回模型」。中间隔着 N 个应用和 M 个外部系统，就是 N×M 份重复劳动。

1.2 一套插槽标准 #

MCP 干的事只有一件：把「AI 怎么调工具」从「每个应用自己实现」变成「大家遵循同一套协议」。

类比 USB。鼠标、键盘、U 盘、打印机各干各的活，但插头尺寸一样，主机那一侧就不用为每种设备单独改电路。MCP 里，AI 应用是插口（Host），外部能力是设备（Server），协议就是插头尺寸。任何符合标准的 Server，插上就能用。

换个说法：MCP 是「AI 应用」与「外部能力」之间的标准接口。它只规定三件事：一个 Server 怎么向 Host 声明「我有哪些能力」、Host 怎么调用这些能力、结果怎么按统一格式返回。这三件事定死之后，Server 写一次，所有支持 MCP 的 Host 都能接；Host 支持一次，所有 Server 都能用。

1.3 它让 AI 能碰到什么 #

按能力类型分三类，细节在第二章：做动作（读文件、写文件、查数据库、发 HTTP 请求、跑一条命令）、看数据（读某个文件的内容、看某张表的结构、拉一段日志）、用模板（把固定套路的提示词存成模板，一键调用）。前两类占绝大多数场景。日常你想要的「AI 帮我看看这个仓库」「AI 帮我查一下这个接口返回了什么」，落到 MCP 上就是一个 Tool 加一个 Resource。

1.4 MCP 不是什么 #

不是模型，协议不管推理，模型该多笨还是多笨；不是沙箱，Server 跑在你的用户权限下，能碰什么取决于你给了它什么，第十章展开；不是运行时，它不负责调度、不负责重试、不负责并发；也不是只给某一家的，Claude Desktop、各类 IDE、自研 Agent 都能当 Host。

定位压缩成一句：它只解决「接口统一」，不解决「安全」和「聪明」。

二、三个核心概念 #

MCP Server 对外暴露三样东西：Tools、Resources、Prompts。三样都在握手之后由 Server 声明，Host 负责呈现给模型或用户。

2.1 Tools（工具） #

Tool 是 AI 可以调用的函数。它由 Server 注册，带名字、描述、入参 schema，调用后返回结果。三个特征：有副作用（写文件、插数据库、发请求、删记录都算）；需要模型决策（模型看描述和 schema，自己决定调不调、传什么参数）；返回内容会进上下文（返回太多会挤爆窗口）。

一个 Tool 的定义长这样。这是概念结构，不是协议原文：

json
{
  "name": "read_file",
  "description": "读取指定路径的文本文件内容，只读，不会修改文件",
  "inputSchema": {
    "type": "object",
    "properties": {
      "path": { "type": "string", "description": "文件的绝对路径" }
    },
    "required": ["path"]
  }
}

三个字段都不能糊弄。name 是模型调用时用的标识；description 是模型判断「该不该调」的主要依据；inputSchema 决定它能传什么参数。描述写得含糊，模型就会乱调，或者干脆不调。

2.2 Resources（资源） #

Resource 是 AI 可以读取的数据。它用 URI 标识，只读，不改变任何状态。

json
{
  "uri": "file:///D:/project/README.md",
  "name": "项目说明",
  "mimeType": "text/markdown"
}

特征：无副作用，读一百遍和读一遍结果一样，盘上什么都没变；由 URI 定位，file://、db://、自定义 scheme 都行，scheme 由 Server 自己定义；多数实现里由用户在 Host 界面里选中，或者由 Host 按 URI 提供给模型，模型不自主决定去拉。

资源还可以带模板。file:///logs/{date}.log 这类带占位符的 URI 模板，能一次声明一批资源，不用一个个枚举。

2.3 Prompts（提示模板） #

Prompt 是预置的提示词模板。它由 Server 提供，带参数，用户主动调用。

json
{
  "name": "review_code",
  "description": "按团队规范审查一段代码",
  "arguments": [
    { "name": "language", "required": true },
    { "name": "focus", "required": false }
  ]
}

它的价值是把团队里那套「怎么让 AI 干活」的写法固化下来，不用每人每次重新拼提示词。Host 侧多表现为一个斜杠命令或者一个菜单项。

2.4 一张表分清三样 #

维度 Tools Resources Prompts
干什么 执行动作 读取数据 套用提示模板
有无副作用 有 无 无
谁发起 模型自主调用 用户选中或按 URI 读取 用户主动触发
标识方式 name URI name
返回什么 调用结果 数据内容 一条或多条消息
典型例子 写文件、跑 SQL、发请求 读文件内容、看表结构 代码审查模板

2.5 混淆这两个，权限设计就会出错 #

记住一句：Tools 是「能做动作」，Resources 是「能看数据」。

搞混会掉进两个坑：

  • 把写操作包装成 Resource。比如「把这段内容存进 notes.md」包装成一个可读取的资源 URI。看着只读，实际每读一次都在改盘。审计日志里看不到写操作，出了问题查不出来。
  • 把只读查询包装成 Tool。查一次表结构也走 Tool 调用，模型以为它能改表，参数乱传，还白搭一次副作用审批。

判断方法很土但管用：问一句「这一步会不会改变任何东西」。会改，就是 Tool；不改，就是 Resource。

三、Client 与 Server 架构 #

3.1 三层角色 #

MCP 的架构里三个角色，别混：

  • MCP Host：AI 应用本体。Claude Desktop、IDE、你自己写的 Agent，都是 Host。它管界面、管模型、管把这个 Server 的结果塞进哪一轮对话。
  • MCP Client：Host 内部的连接器。每个 Client 只对一个 Server 负责，一对一。Host 要接三个 Server，就起三个 Client。
  • MCP Server：提供 Tools/Resources/Prompts 的程序。它可以是本机的一个 Python 进程，也可以是远端的一个 HTTP 服务。
text
┌─────────────────────────────────────┐
│            MCP Host                 │
│  （Claude Desktop / IDE / Agent）    │
│                                     │
│  ┌──────────┐  ┌──────────┐         │
│  │ Client A │  │ Client B │  ...    │
│  └────┬─────┘  └────┬─────┘         │
└───────┼─────────────┼───────────────┘
        │             │
   ┌────▼────┐   ┌────▼────┐
   │Server A │   │Server B │
   │ (本地)  │   │ (远端)  │
   └─────────┘   └─────────┘

一条连接只服务一对 Client/Server。这样做的好处是隔离：Server B 崩了，Server A 的连接不受影响，工具列表也各自独立。

3.2 为什么要拆出 Client 这一层 #

直接把 Server 塞进 Host 也能跑，麻烦在于传输方式会写死在 Host 里、连接状态会污染 Host 的状态机、换一个 Host 就得重写一遍。拆出 Client 之后它成了协议适配层：底下走 stdio 还是 HTTP 无所谓，对 Host 都吐同一套抽象。Host 只管「我要调这个 Tool」，不关心请求怎么发出去。

3.3 一次调用的完整链路 #

以一个「查天气」的工具为例，从你打一句话到屏幕上出结果：

  1. 你输入「帮我查一下北京的天气」。
  2. Host 把这句话连加上所有已连接 Server 的工具清单（名字、描述、schema）一起交给模型。
  3. 模型判断该调 get_weather，输出一个结构化调用请求：工具名 get_weather，参数 {"city": "北京"}。
  4. Host 查表，发现 get_weather 归 Client B 管，把请求转给 Client B。
  5. Client B 通过 stdio 或 HTTP 发给 Server B。
  6. Server B 执行，返回文本结果。
  7. 结果原路回到 Host，Host 把它作为一条工具结果消息追加进对话。
  8. 模型基于这个结果生成最终回答，Host 渲染出来。

关键在第 2 步：工具清单是每轮对话都要塞进上下文的。你接了十个 Server，每个 Server 二十个工具，光是工具描述就能吃掉大半个窗口。这也是工具要写精简描述的原因。

3.4 生命周期三步 #

任何一条连接都要走完这三步：

阶段 谁发起 做什么
初始化 Client 交换协议版本与双方能力声明
运行 双方 列工具、读资源、调工具、传通知
关闭 任意一方 断开连接、回收进程

初始化那一步很关键：Server 要在这一步告诉 Client 自己支持哪些能力（比如支不支持资源订阅、支不支持日志）。Client 据此决定后续能发哪些请求。版本对不上就别硬连，早失败好过调一半崩。

四、两种传输方式 #

协议本身不绑传输。目前常用的就两种：stdio 和 SSE/HTTP。

4.1 stdio：本地进程，最常用 #

Host 自己把 Server 拉起来：fork 一个子进程，把请求写进它的标准输入，从标准输出读回响应。

配置上体现为 command + args。Host 拿到这两个字段就知道怎么启动。

json
{
  "command": "python",
  "args": ["-m", "mcp_server_sqlite", "--db-path", "D:\\data\\my_database.db"]
}

对 stdio 来说，配置就是启动指令，两者是一回事。

它的好处集中在四点：最简单，装好依赖、写对路径就能跑，不用开端口不用管防火墙；进程隔离，Server 是独立子进程，崩了不拖累 Host，Host 退出也容易连带清理；天然只在本机，不监听端口，外部连不进来；好调试，换成手动在终端里跑一遍，行为基本一样。

代价也很清楚：只能本机，多个应用想共用同一个 Server 得各起一份；生命周期绑在 Host 上，Host 关闭 Server 跟着结束；不能跨机器，想给团队共享一个数据库工具做不到。

4.2 SSE / HTTP：远程服务，适合共享 #

Server 是独立部署的 HTTP 服务，监听端口。Client 通过 HTTP 连过去，用 SSE（Server-Sent Events）接收服务端推送。

配置上体现为 url：

json
{
  "url": "https://mcp.example.com/sse",
  "headers": {
    "Authorization": "Bearer <你的 token>"
  }
}

注意这里没有 command。Host 不负责启动它，Server 早已在别处跑着。

好处是多客户端共享（一个服务，团队十个人连同一份）、服务端可独立升级而客户端不用动、能跨机器跨网络。代价同样明确：要有网络，断网就没戏，延迟也比本地进程高；必须做认证，开了端口等于把能力暴露到网络上，没有鉴权的 MCP 服务等于把数据库密码贴公告板；部署成本高，要管进程、管端口、管证书、管重启；调试链路长，中间隔着反向代理、网关、鉴权层，出问题定位慢。

4.3 怎么选 #

维度 stdio SSE / HTTP
部署位置 本机子进程 独立服务，任意机器
需要端口 不需要 需要
认证 无（靠进程隔离） 必须有
多客户端共享 不支持 支持
生命周期 跟着 Host 独立
调试难度 低 中到高
适用场景 个人工具、本地文件、本地库 团队共享、跨机器、SaaS 集成

默认选 stdio。只有一条理由能让你换 SSE：这个能力必须被多台机器或多个人共用。除此之外，SSE 只是给自己加部署与安全的活。

4.4 一个容易踩的坑：stdout 是协议通道 #

stdio 模式下，标准输出就是协议信道。Server 脚本里随手一句 print("debug")，会往这条信道里插一段非协议内容，Client 解析失败，整条连接就会断。

规则很硬：

python
import sys

print("这行会破坏协议", file=sys.stderr)   # 对，走 stderr
print("这行会破坏协议")                    # 错，走 stdout

日志走 stderr，业务数据走返回值。所有 Server 框架都遵守这条，自己手写 Server 时也别破例。

五、配置一个 MCP Server #

这一节以 Antigravity 为样例 Host。别的 Host 字段名不同，结构一致。

5.1 配置文件在哪 #

Antigravity 的 MCP 配置文件在用户目录下的 .gemini 文件夹里。

Windows 路径：

text
C:\Users\<你的用户名>\.gemini\antigravity\mcp_config.json

文件不存在就手动建一个。目录不存在，就连目录一起建。

5.2 基本结构 #

json
{
  "mcpServers": {
    "<Server名称>": {
      "command": "<可执行程序>",
      "args": ["<参数1>", "<参数2>"],
      "env": {
        "<环境变量名>": "<值>"
      }
    }
  }
}

mcpServers 是顶层对象，下面每条 key 就是一个 Server 的别名。别名你自己起，起短一点、看得懂就行，它在界面和日志里都会出现。

5.3 准备工作：确认运行环境 #

大多数 MCP Server 靠 Python 或 Node.js 跑：

  • Python 写的 Server：确认 python 可用，建议 3.10 以上。
  • Node.js 写的 Server：确认 node 和 npm 可用。

先在终端里把 python --version、node --version 敲一遍再动配置。版本不对的时候，报错信息往往不是「版本不对」，而是 ImportError 或者莫名其妙的语法错误，排查起来费时间。

5.4 用一个现成的 Server：SQLite #

想让 AI 查本地 SQLite 库，先装 Server：

bash
pip install mcp-server-sqlite

装完可以直接试跑：

bash
mcp-server-sqlite --db-path ./test.db

这一步只是验证它能不能启动。配好之后不需要手动运行，Host 会按配置自动拉起进程。

5.5 实战配置 #

把 SQLite 和自己写的天气 Server 一起配进去：

json
{
  "mcpServers": {
    "sqlite_tools": {
      "command": "python",
      "args": [
        "-m",
        "mcp_server_sqlite",
        "--db-path",
        "D:\\data\\my_database.db"
      ]
    },
    "my_weather_bot": {
      "command": "python",
      "args": [
        "D:\\my-mcp-server\\weather_server.py"
      ]
    }
  }
}

5.6 三个字段的关键点 #

command：启动命令。

  • Python 脚本用 python 或 uv（用 uv 管环境时）。
  • Node.js 用 node。
  • 装在虚拟环境里的话，写解释器的绝对路径，别只写 python。依赖装在那个环境里，用系统 python 启动会报找不到模块。
json
"command": "D:/envs/myenv/Scripts/python.exe"

args：参数列表。Windows 路径里的反斜杠按 JSON 规范要转义成 \\，或者直接写正斜杠 /。写正斜杠省事，也不容易漏。

两种写法等价：

text
D:\\my-mcp-server\\weather_server.py
D:/my-mcp-server/weather_server.py

后者推荐。

env：环境变量。API Key 这类敏感信息不要写死在代码里，从 env 注入：

json
"env": {
  "API_KEY": "sk-xxxxxxxx",
  "LOG_LEVEL": "info"
}

注意这个文件是明文。里面的 Key 等同于你的账号权限，别把它提交到公开仓库。

5.7 验证与使用 #

配置改完，按顺序走。一，重启 Host，它只在启动时读配置文件，改完不重启等于没改。二，看工具列表，界面里应该出现这个 Server 名下的工具。三，自然语言试一次，对 my_weather_bot 说「请帮我查一下北京的天气」，Host 应该识别到 get_weather 并调用它，返回一句天气。四，没反应就查日志，日志在 .gemini 目录下的日志文件里，或者界面上的 Output 面板，找启动 Server 失败的那几行：路径错了、依赖缺了、命令不存在，都会在这里明说。

5.8 进阶：在工作流里引用 #

工具验证通过之后，就能在 Markdown 工作流里像内置工具一样引用。

.agent/workflows/check-weather.md：

markdown
**前置条件**
- MCP Server `my_weather_bot` 已运行

**执行步骤**
1. 使用 `get_weather` 工具查询「上海」的天气
2. 根据天气情况生成一份出行建议

工作流本身不认识 MCP。它只是描述「用某个工具做某件事」，Host 负责把这句话落到具体的 Server 上。

六、写一个最小的 Server #

这一节用 Python 的 MCP SDK 写一个能跑的 Server，注册一个 Tool 和一个 Resource。代码不长，几十行。

6.1 依赖与骨架 #

bash
pip install mcp

最小骨架：

python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("Weather Demo")   # 参数是这个 Server 的名字，会显示在 Host 界面里

@mcp.tool()
def get_weather(city: str) -> str:
    """获取指定城市的天气信息"""
    return f"{city} 的天气是晴天，气温 25°C"

if __name__ == "__main__":
    mcp.run()

四行关键东西：导入、实例化、装饰器注册、run()。跑起来之后，Host 就能在工具列表里看到 get_weather。

注意那个 docstring。它就是工具的 description，模型靠它判断该不该调。写「获取指定城市的天气信息」是合格的；写「天气工具」太糊；不写 docstring，模型基本不会主动用它。

6.2 加一个 Resource #

python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("Weather Demo")

@mcp.tool()
def get_weather(city: str) -> str:
    """获取指定城市的天气信息。传入城市中文名，返回一句话天气描述。"""
    return f"{city} 的天气是晴天，气温 25°C"

@mcp.resource("weather://cities/supported")
def supported_cities() -> str:
    """本工具支持的城市清单"""
    return "北京、上海、广州、深圳、杭州、成都"

if __name__ == "__main__":
    mcp.run()

@mcp.resource 的参数是 URI。这里用自定义 scheme weather://，Server 自己认这个 scheme 就行。函数体返回纯文本，Host 按 text/plain 处理。

6.3 一个带真实逻辑的 Tool #

光返回字符串看不出区别，加个真干活的。下面这个读本地文件行数，只读，用 stderr 打日志：

python
import sys
from pathlib import Path
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("File Tools")

@mcp.tool()
def count_lines(path: str) -> str:
    """统计一个文本文件的行数。只读，不修改文件。

    Args:
        path: 文件的绝对路径
    """
    p = Path(path)
    if not p.exists():
        return f"文件不存在：{path}"
    if not p.is_file():
        return f"不是文件：{path}"
    try:
        text = p.read_text(encoding="utf-8")
    except UnicodeDecodeError:
        return f"不是 UTF-8 文本：{path}"
    n = len(text.splitlines())
    print(f"已统计 {path}，{n} 行", file=sys.stderr)
    return f"{path} 共 {n} 行"

if __name__ == "__main__":
    mcp.run()

三个细节值得看：

  • 出错不抛异常，返回一句人话。工具抛异常，模型多数时候看不懂堆栈，返回错误描述它反而能继续处理。
  • 先判存在、再判是不是文件、再判编码。层层收窄，别一上来就 read_text。
  • 日志走 stderr。stdio 模式下这行是硬规矩。

6.4 注册到 Host #

json
{
  "mcpServers": {
    "file_tools": {
      "command": "python",
      "args": ["D:/my-mcp-server/file_server.py"]
    }
  }
}

重启 Host，工具列表里出现 count_lines，对 AI 说「统计一下 D:/data/demo.txt 有多少行」，它就会调。

6.5 别忘了手动试跑 #

写 Server 时先在终端里直接跑：

bash
python D:/my-mcp-server/file_server.py

进程挂住不动、没有报错，说明它正在等 stdin 上的协议消息，这是正常状态，按 Ctrl+C 才能退出。真正需要看的是启动瞬间有没有打异常。有异常就先在这里修干净，再去动 Host 的配置，省得两边猜。

七、Tools 的定义与调用 #

7.1 定义一个 Tool 要想清三件事 #

  1. 名字：动词加名词，read_file、query_db、send_http。模型从名字猜用途，别起 helper、util、do_stuff。
  2. 描述：一句话说清「做什么 + 什么时候用 + 有什么限制」。这是模型唯一的判断依据。
  3. schema：参数类型、哪些必填、字段含义。每个字段都写 description，别指望模型理解 a、b、c。

一段能用的描述长这样：

text
查询本地 SQLite 数据库并返回结果行。
只允许 SELECT 语句，写操作会被拒绝。
传入完整的 SQL，不要带分号结尾。

三段：做什么、边界在哪、输入有什么要求。比一句「数据库工具」有用得多。

7.2 参数 schema 的边界 #

要素 作用 写错的后果
type 限定参数类型 模型传字符串给数字字段，调用失败
required 标明必填项 可选参数被当成必填，模型反复重试
description 解释字段含义 模型瞎猜，传进来一堆无效值
enum 限定取值范围 模型自创选项，落进兜底分支

enum 特别好用。参数只有几个合法值时，直接列出来，模型乱填的概率会低很多。

json
{
  "type": "object",
  "properties": {
    "level": {
      "type": "string",
      "enum": ["info", "warn", "error"],
      "description": "日志级别，只接受这三个值"
    }
  },
  "required": ["level"]
}

7.3 一次调用的消息序列 #

text
Client → Server:  列出工具
Server → Client:  [read_file, query_db, ...]

Client → Server:  调用 query_db，参数 {"sql": "SELECT ..."}
Server → Client:  结果 {content: [{type: "text", text: "..."}]}

Client → Server:  调用 query_db，参数 {"sql": "DELETE FROM ..."}
Server → Client:  错误 {isError: true, content: [...]}

注意结果里的 content 是个数组，元素有类型。可以是文本，也可以是图片之类的其他类型。这样 Host 不用为每种返回格式单独写解析。

isError 是软失败：协议层成功，业务层失败。用它比抛协议级异常友好，模型能看懂错误内容并按提示改参数重试。

7.4 返回内容要克制 #

工具返回的东西会整段进上下文窗口。返回一份两千行的日志，模型后面的推理基本就废了。实践有四条：默认返回摘要，真需要详情让模型带参数再要一次；列表类返回加 limit 参数，默认给小值；大段二进制或者超大文本返回一个 URI，让模型按需去读 Resource；报错时只说清「哪里不对 + 怎么改」，别贴整段堆栈。

7.5 工具多的代价 #

工具清单在每轮对话都进上下文。十个 Server、每个二十个工具，描述加起来几千 token，每轮都付一次，而且工具越多模型选错的概率越高。对策就三条：一个 Server 只装一类能力，需要时再挂；工具描述压到一两行，细节挪进参数 description；长期不用的 Server 从配置里摘掉，别留着占位。

八、Resources 与 Prompts #

8.1 Resource 的 URI 设计 #

URI 是 Resource 的身份。设计得好不好，直接决定用起来顺不顺。

text
file:///D:/project/README.md        静态资源，一个文件一个 URI
db://main/schema/users              语义化的资源路径
logs://app/{date}/{level}           带占位符的模板

三种风格各有场景。文件类用 file:// 最自然，因为物理路径本身就是唯一标识。数据库这类没有天然路径的，自己定一套语义化 scheme，别硬套文件路径。

8.2 资源模板 #

一批资源没法一个个枚举时，用模板：

python
@mcp.resource("logs://app/{date}")
def app_log(date: str) -> str:
    """按日期读取应用日志，date 格式为 YYYY-MM-DD"""
    path = Path(f"D:/logs/app-{date}.log")
    if not path.exists():
        return f"没有 {date} 的日志"
    return path.read_text(encoding="utf-8", errors="replace")

Host 侧会看到模板形式，能按你的输入拼出具体 URI。一个模板顶掉上千条静态声明。

8.3 Prompts 的用法 #

Prompt 是给用户用的，不是给模型自主用的。它把一段固定写法存起来，带参数。

python
@mcp.prompt()
def review_code(language: str, focus: str = "可读性") -> str:
    """按团队规范审查一段代码"""
    return f"""请审查下面这段 {language} 代码，重点关注 {focus}。

检查项：
1. 边界条件是否处理
2. 错误处理是否完整
3. 命名是否表达意图
4. 有无明显的性能问题

把问题按严重程度排序，每条给出具体行号和修改建议。"""

调用时填语言和关注点，模板生成完整提示词。好处是标准统一：团队里十个人用同一个模板，产出的评审风格一致，不会有人忘了提边界条件。

8.4 三者怎么选 #

你的需求 该用
让 AI 执行一个动作 Tool
让 AI 看到一份数据 Resource
让用户一键套用固定提示词 Prompt
既要执行动作又要返回数据 Tool（返回内容里带数据）
数据量大、按需读取 Resource + 让 Tool 返回 URI

最后一行值得记：数据量大时，Tool 只返回一个 URI，模型再按 URI 读 Resource。这样上下文里只有引用，没有全文。

九、调试与排错 #

9.1 按层定位 #

MCP 出问题，先判断坏在哪一层，别一上来就改代码。

现象 主因 查法
工具列表里根本没出现 Server 没启动成功 看 Host 日志里启动命令的报错
列表出现了，但从不被调用 描述太含糊 把 description 写具体，重启再试
调用报「工具不存在」 别名或工具名对不上 对一下配置里的 key 与界面显示名
调用报参数错误 schema 与传参不匹配 打印收到的参数，比对 schema
时好时坏、偶发断连 stdout 被日志污染 全文搜 print(，改成 stderr
路径类全部失败 相对路径、盘符、权限 换绝对路径，写正斜杠重试

9.2 三个高频具体错误 #

路径错误：Windows 下绝对路径写成 D:/project/script.py 或 D:\\project\\script.py 都行，前者推荐。写成 D:\project\script.py 会被 JSON 当转义符吃掉。

环境问题：Python 装在虚拟环境里，command 只写 python，启动的是系统解释器，找不到装好的包。改成解释器绝对路径：

json
"command": "D:/envs/myenv/Scripts/python.exe"

stdio 通信被污染：command 是对的，进程也确实起来了，但连接立刻断。九成是脚本里有 print() 打到标准输出。MCP 默认走 stdio，标准输出是协议信道，任何无关内容都会破坏报文格式。日志必须走 stderr。

9.3 隔离变量的笨办法 #

连不上时，把 Server 从 Host 里摘出来单独跑：

bash
python D:/my-mcp-server/file_server.py

不报错、进程挂住、等 stdin，说明 Server 本身没问题，问题在配置。反过来，如果这一跑就抛异常，就别再怀疑配置了，先修代码。二分一次，能省掉半小时来回猜。

9.4 日志看什么 #

只盯三类行：启动命令与参数（确认拼出来的命令和你以为的一致）、进程退出码（非 0 说明它崩了，不是协议问题）、解析错误（信道被污染或版本不兼容）。其余日志基本是噪音。

十、安全边界 #

10.1 MCP Server 不是沙箱 #

这是本篇最要紧的一句话。Server 是个跑在你机器上的普通进程，用的是你的用户权限。它没有额外的隔离层，没有权限收缩，没有系统调用过滤。

它能做什么，取决于它被写成什么样，不取决于协议规定了什么。协议只规定通信格式，一个字都没规定「你不许读 C 盘」。

10.2 装一个 Server 等于给它你的权限 #

推演一遍。你以普通用户登录，把自己配的 Server 拉起来：它能读你用户目录下所有文件，包括 .ssh 里的私钥、浏览器配置、各种 token 缓存；能写你能写的任何位置，包括代码仓库和启动项；能发起网络请求，把你读到的东西发到任意地址；还能再启动子进程，做上面这些事的组合。

一个恶意 Server 能读你的整个硬盘。这句话不是修辞比喻，是权限模型直接推出来的结论。

所以真正的问题不是「这个 Server 功能强不强」，而是「我信不信写这个 Server 的人」。功能弱但来路不明的 Server，比功能强但源码可读的 Server 危险得多。

10.3 风险清单 #

风险 具体表现 怎么防
越权读文件 索要 ~ 或整个盘符的路径参数 只给具体子目录，别给根目录
凭证外泄 把 env 里的 Key 打到日志或发到远端 最小权限的 Key，能撤销的 Key
命令注入 参数直接拼进 shell 命令 不信来源不明的 Server，审查源码
供应链投毒 包名仿冒、依赖被替换 只装官方或知名仓库的包，锁版本
远程服务无认证 开了端口、谁都能连 必须加 token，绑内网地址
配置泄露 mcp_config.json 进了公开仓库 加进 .gitignore，Key 走环境变量

10.4 五条硬规则 #

  1. 只装你信任来源的 Server。官方仓库、读过源码的、团队内部维护的。来源不明的，宁可不装。
  2. 看清它要求的权限。配置里那个路径参数，写 D:/data/project，别写 D:/。写 C:/Users/你，等于把家底交出去。
  3. 别随手给家目录访问权。这是第一条被违反得最多的规则。图省事给 ~，后面所有文件都在这条连接的可见范围内。
  4. 敏感 Key 用最小权限，并且能撤销。给 MCP 用的 Key 不要和你日常主账号的 Key 是同一个。
  5. 远程 Server 必须带认证。SSE 地址裸奔在公网上，等于把能力开放给扫描器。

10.5 一个判断习惯 #

装任何 Server 之前，问自己三个问题：这个 Server 的作者是谁，我能追到源码吗；它需要访问的范围，比它实际干的活大多少；如果它把我给它的数据全发出去，损失有多大。

第三个问题答不上来的，先别装。

十一、MCP 与函数调用的区别 #

11.1 两者不在一个层面 #

Function Calling（函数调用）是模型侧的能力：模型输出一个结构化的调用意图，说「我要调这个函数，参数是这些」。MCP 是应用侧的协议：应用之间怎么发现工具、怎么建立连接、怎么传调用、怎么回结果。

一句话：函数调用解决「模型怎么表达想调什么」，MCP 解决「这个函数从哪来、怎么连上」。

11.2 对照表 #

维度 函数调用 MCP
层面 模型输出格式 应用间通信协议
谁定义工具 应用开发者写死在代码里 Server 独立声明，可动态接入
换应用要重写吗 要，每个应用一套 不用，Server 写一次到处接
工具来源 当前应用内的函数 任意符合协议的 Server
传输 无（只是模型输出） stdio / SSE 等
权限模型 由应用自己实现 由 Server 进程权限决定
能否复用 难 能

11.3 它们怎么配合 #

实际是叠加关系，不是替代关系：

  1. Host 通过 MCP 连上若干 Server，拿到全部工具清单。
  2. Host 把清单按函数调用的格式交给模型。
  3. 模型输出函数调用意图。
  4. Host 把意图翻译成 MCP 请求，发给对应 Server。
  5. 结果回来，Host 再按函数调用结果的格式喂回模型。

模型全程不知道 MCP 存在。它只看到「有一批函数可以调」。MCP 的价值在 Host 与 Server 之间那一层：把「工具从哪来」这件事标准化了。

所以别把两者对立。没有函数调用，模型不会表达意图；没有 MCP，工具得在每个应用里重写一遍。

十二、易错点速查 #

12.1 配置类 #

易错点 后果 正确做法
Windows 路径写单个反斜杠 JSON 解析失败或路径错 用 / 或 \\
command 只写 python 虚拟环境的包找不到 写解释器绝对路径
改完配置不重启 配置不生效 重启 Host
别名起得太随意 日志里分不清是哪个 用能力命名，别用序号
Key 明文写进配置 泄露即失守 走环境变量，文件加 .gitignore

12.2 代码类 #

易错点 后果 正确做法
用 print 打日志 stdio 信道被污染，连接断 一律走 stderr
工具函数不写 docstring 模型不知道该不该调 一句话说清做什么
工具抛裸异常 模型看不懂，无法自愈 返回一句人话错误
一次返回上千行 上下文被挤爆 返回摘要，详情走 Resource
写操作也做成 Resource 权限与审计全乱 写操作一律走 Tool

12.3 概念类 #

易错点 后果 正确做法
把 MCP 当沙箱 权限给太大 它就是普通进程，权限等于你的
混淆 Tool 与 Resource 权限设计出错 会改状态的走 Tool，只读的走 Resource
以为 Server 越多越好 token 白烧，选错率升高 按能力挂，用完摘掉
把 SSE 当默认选项 平白多出部署与安全活 默认 stdio，需要共享才上 SSE
以为 MCP 让模型更聪明 期待落空 它只统一接口，不改推理

12.4 收尾 #

MCP 的位置可以用一句话钉死：它是 AI 应用与外部能力之间的标准接口，功能上像 USB，安全上什么都不保证。

上手顺序建议是：先配一个现成的 stdio Server 跑通，确认整条链路是通的；再写一个只有 Tool 的最小 Server，理解注册与调用；最后才去碰 Resource、Prompt、远程传输。

配置写对、日志走对、权限给对，三件事做到，MCP 就是手上很顺的一件工具。做不到第三件的，前两件做得再漂亮也不该上线。
