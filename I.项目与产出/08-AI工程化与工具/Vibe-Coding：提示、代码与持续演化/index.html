这一篇讲什么 Vibe Coding 的方法层：Prompt 怎么写、阶段怎么分、改动怎么持续。

这一篇不讲什么 不讲模型选型与参数对比，不讲各家 IDE 插件的功能横评，不给未经验证的效率数字。

跨篇指路 环境搭建与工具部署见同目录 DSH 落地三篇；工具之间如何互相调用见 MCP 篇。

Vibe Coding 被讲得很玄。有人以为它是「装个 AI 插件继续写代码」，有人以为它是「让 AI 全自动写完整项目」。两种理解都会把你带进坑里。

真正的分界只有一条：写实现的人是不是你。你不写实现，你描述意图；你定边界，AI 填内容。这篇把这个分工拆开讲清楚，包括它在哪一步会崩、崩了怎么救。

一、Vibe Coding 是什么 #

两种常见误解 #

第一种，把 AI 当成高级搜索。卡住了问一句、看懂了继续手写。这有用，但协作方式没变，仍然是「我写代码，AI 解释」。

第二种，把 AI 当成全自动施工队。一句话丢进去，期待一个能上线的仓库。这不成立，因为它跳过了所有判断环节。

Vibe Coding 站在两者中间：人保留全部判断，AI 承担全部打字。

分层看这件事 #

层级 你的动作 AI 的动作 谁在承担风险
编程辅助 写代码，卡住时提问 解释代码、找 bug、给优化建议 你，AI 只提供参考
意图驱动 描述要什么，判断像不像 生成结构、生成实现、生成测试 你，AI 只提供产出
流水线化 定边界、审结果、控节奏 按 Schema 输出、按阶段改动 你，AI 被约束在 Schema 里

第一层和第二层的差别，不在于用不用 AI，而在于产出物由谁落盘。第一层你还在敲 for 循环；第二层你把「敲」这件事交出去了，剩下的工作变成改方向、纠需求、说一句「这个感觉不对」。

一个具体对照 #

传统写法：

text
用 Python 写一个日志分析工具，支持过滤和统计。

这句话的问题不是不礼貌，而是太宽。它没有角色、没有场景、没有边界、没有成功标准。AI 收到这种输入只能自由发挥，最后交给你一份教程代码：能跑、能看、不能维护。

Vibe Coding 的写法：

text
你是一个经验丰富的 Python CLI 工具作者。
这个工具会被我长期使用和维护。
我讨厌臃肿的结构、示例式代码、把所有逻辑堆在 main 里。
请设计一个清晰、可扩展、易测试的项目结构，用于分析日志文件。
如果将来要增加新的分析规则，不应该修改已有核心代码。

差别在哪？第二版没有描述任何一行实现，它描述的是评价标准。

核心不是「让 AI 写代码」 #

如果只记一句话，记这句：

人负责结构与判断，AI 负责填充实现。

这句话展开就是三个问题，全部由人回答：

  1. 要做什么（意图与范围）
  2. 不要做什么（禁令与厌恶点）
  3. 结构长什么样（模块边界、扩展点位置）

AI 回答的只有一个问题：具体每一行怎么写。

为什么分工是这个样子 #

因为两边的能力不匹配。

能力 人的位置 AI 的位置
判断「这个结构三个月后还能不能维护」 强 弱，它没有你的使用习惯
判断「这个需求到底要不要做」 强 无，它只会照着字面做
一次性产出大量样板代码 弱 强
跨文件的机械一致性 弱 强
记住你上个月否掉过哪种设计 强 弱，除非你写进 System

把强项留给强项，就是这套方法的全部原理。

边界定得越清楚，输出越可用 #

同一句话，边界不同，结果完全不同：

输入 AI 的实际反应
帮我实现一个放置类游戏 自由发挥：自己定数值、自己定结构、自己加存档
只实现 Entity 基类和 MineEntity 的最小可运行版本，不要实现升级、UI、存档 输出被压缩在一个稳定边界内，多写一行都是越界

模糊的输入不会得到「差不多」的结果，它会得到一个你没要求过的东西。而你没要求过的东西，就是后面所有返工的来源。

二、人的职责与 AI 的职责 #

分工不能停在口号上，得落到每次对话的具体分配。

一张分工表 #

事项 归属 说明
决定这次改什么 人 AI 不知道你的真实痛点
划定可改目录 人 写进 User 层，越具体越好
决定结构长什么样 人 AI 给草图，你判断顺不顺
判定命名与抽象是否到位 人 这是审美，不是逻辑
生成项目骨架 AI 人给约束，AI 落盘
写具体函数体 AI 人只看调用处是否自然
补样板与重复代码 AI 人审一致性
决定能不能提交 人 看 git diff，不看 AI 的自我评价

人负责的三件事 #

第一件：要做什么。 这是范围，也是拒绝的清单。「只实现最小可运行版本」比「实现这个功能」有用得多，因为它同时定义了不做什么。

第二件：不要做什么。 见第四章。这一条在实践里比第一条更能改善输出质量，因为 AI 的坏习惯是稳定的、可预测的，而否定句正好对着这些坏习惯。

第三件：结构长什么样。 不是让 AI 自由设计目录树，而是你给出稳定点与变化点的划分，AI 按这个划分画格子。

AI 负责的三件事 #

第一件：把意图翻译成文件。 目录、文件、函数骨架、注释密度，一次性铺开。

第二件：在既定边界内填实现。 边界内的代码写得好不好，取决于你给的约束细不细。

第三件：做机械的重复劳动。 十个文件同样的改动、同样的命名规范、同样的错误包装，交出去。

不可让渡的部分 #

有三件事交给 AI 就等于放弃项目控制权：

  1. 判定「这个抽象要不要现在引入」。AI 偏爱提前抽象，因为抽象在它见过的代码里更常见。
  2. 判定「这次改动能不能验证」。见第六章，这是持续演化的底线。
  3. 判定「这个方向还要不要继续」。AI 不会喊停，它会一直按你的话往下做，哪怕方向已经错了。

一个可操作的检查 #

每次让 AI 动手前，用三句话自检：

text
我要改的范围是：__________
我明确不要的是：__________
我怎么验证改对了：__________

三行里有任何一行空着，就先别发 Prompt。空着的那一行，最后一定会以返工的形式补回来。

三、Prompt 的第一原则 #

不要告诉 AI「怎么做」，告诉 AI「什么算好」 #

这是整套方法的第一条，也是被违反得最多的一条。

原因很直接：如果你规定「怎么做」，你就在用一个能力比你弱的环节做设计决策。AI 对具体实现有很多可选路径，你指定其中一条，等于放弃了其他更好的路径，同时把「为什么是这条」的解释责任也省了。

反过来，如果你说「什么算好」，AI 会自己找路径，你保留验收权。判断力是你的强项，实现路径是它的强项。

所以：

你在给什么 结果
任务 一份能跑的实现，对不对要靠你逐行读
标准 一份朝着你的标准收敛的实现，你用感受验收

工程能力 = 判断力，不是实现力 #

这句话要单独放大。在 Vibe Coding 里，实现力已经被外部化了，代码敲得多快不再构成优势。剩下的差距全部落在判断力上：

  • 你能不能看出这个结构三个月后会烂
  • 你能不能说出「哪里别扭」
  • 你能不能在 AI 输出一堆你没要求的东西时立刻叫停

这些判断没法外包，因为它们依赖你的使用经验，不依赖代码量。

四个要素 #

一个合格的 Prompt 有四个要素，缺一个就偏。

① 角色。 不是「你是 AI」，而是「你是一个有 5 年经验的 Python 工具链工程师」。角色决定了 AI 使用哪套默认习惯。

② 使用场景。 不是「写一个工具」，而是「这是一个每天都要用的命令行工具」。场景决定它选择什么样的鲁棒性：一次性的脚本可以不处理边界，每天用的工具必须处理。

③ 厌恶点。 这是最重要的部分。比如：

  • 不要一堆 if-else
  • 不要所有逻辑写在 main
  • 不要难以测试

④ 成功标准。 比如：

  • 目录结构一眼就懂
  • 新功能不用改老代码
  • 没用到的东西不要出现

四要素的实际效果 #

把四要素落成一句话，得到的 Prompt 是这样的：

text
你是一个经验丰富的 Python CLI 工具作者。
这个工具会被我长期使用和维护。
我讨厌臃肿的结构、示例式代码、把所有逻辑堆在 main 里。
请设计一个清晰、可扩展、易测试的项目结构，用于分析日志文件。
如果将来要增加新的分析规则，不应该修改已有核心代码。

注意它的构成：第一句是角色，第二句是场景，第三句是厌恶点，第四句是任务，第五句是成功标准。五行里没有一行在说「用 class 还是用函数」。

五个字母自检 #

一套更细的自检维度，按 C-L-E-A-R 五项过一遍：

字母 含义 检查什么
C Concise（精简） 是不是直奔主题，废话砍掉了吗
L Logical（有逻辑） 是不是拆成了步骤或条列，先做 A 再做 B
E Explicit（明确） 要什么、不要什么、输出格式、有没有给范例
A Adaptive（可调整） 不满意时能不能指出「在哪里改」，而不是推翻重来
R Reflective（反思） 做完有没有让它总结，把管用的做法存成模板

后两项容易被跳过，但它们是复利的来源。A 让你能在一版上迭代而不是每次从零开始；R 让一次成功变成下次的起点。

精简、明确、给约束 #

三个词，各管一件事。

词 管什么 反面
精简 砍掉寒暄与背景铺垫 一大段项目介绍只换来一句「好的，我理解」
明确 讲清要什么、不要什么、输出成什么样 「结构清晰一点」这种要求谁也执行不了
给约束 划出可改范围与不可引入的东西 每次改动都蔓延到整个仓库

「精简」不是说 Prompt 越短越好。是说每一句都要承担一个约束功能，没有功能的话删掉。背景故事、客套、重复强调都属于没有功能的话。

一句判断 Prompt 好不好 #

写完 Prompt，读一遍，问：如果我是接手的人，只看这段话，能不能判断产出对不对？

能，就是合格。不能，就是你把判断标准留在了自己脑子里，那 AI 只能靠猜。

四、否定式 Prompt #

为什么否定比肯定管用 #

这一章是实践里最能立竿见影的部分。

AI 的默认行为是尽量周全。你让它写一个函数，它会顺手加注释、加参数校验、加日志、加异常包装、加一个你以为它不会加的抽象层。这些行为在长期维护的库里是优点，在原型阶段全是负担。

问题是「周全」这个倾向是默认打开的，你不关掉它，它就在。

肯定句很难关掉它：

text
代码简洁一点。

AI 收到这句，理解成「注释从五行减到三行」，因为它不认为注释是不简洁的表现。它对「简洁」的理解和你不一样，而且它没法问你。

否定句能关掉它：

text
不要加注释。
不要提取工具函数。
不要写参数校验，输入是我自己传的。

这三句是没有歧义的，执行结果可验证：文件里有没有注释，一眼能看出来。

核心机制：否定句指向具体行为 #

句式 AI 的执行 结果可验证性
要写得专业 无法映射到具体动作 低，你觉得不专业也说不出哪里不对
不要用 core/common/utils 这类模糊模块 映射到目录命名 高，目录名一列就看见
结构要清晰 无法映射 低
不要为了扩展而扩展的空壳插件 映射到是否生成 plugin 目录 高，有没有一看就知道

规律：否定句里必须出现一个具体的、可被检查的东西（文件名、目录名、语法结构、代码块）。出现不了，就退化成了一句愿望。

否定句放哪一层 #

放 System，不放 User。

原因在第五章会展开：User 是弱约束，复杂任务下模型会忽略它。而否定条款是长期生效的工程审美，本来就不该跟着任务走。

text
你避免以下设计：
- 模糊职责的通用模块（core / common / utils）
- 为了扩展而扩展的空壳插件
- 仅在文档中存在、但无法直观使用的扩展点
- 把业务流程隐藏在抽象层之后

放在 System 里意味着每次对话它都生效，不用你重复。

高频坏习惯清单 #

这些是 AI 在生成项目结构时最常出现的四类问题，全部可以转成否定条款。

第一类：模块名看起来对，但味道不对。

core、common、utils、base。这四个名字的共同点是——它们什么都没说。任何东西都可以放进 utils，所以 utils 会变成垃圾桶。

第二类：框架感太重，业务感太弱。

有 framework、有 plugin，但看不出业务到底从哪开始。你打开项目，第一反应是「这是个框架」，不是「这是个日志分析工具」。

第三类：项目像 Java / Python 企业应用。

目录抽象过度、生命周期不清晰、边界模糊。为了分层而分层，每一层都只有一行转发调用。

第四类：扩展点是理论上的。

说是插件，但你看不出怎么加一个新设备。真去加的时候，要改五个文件。

否定式模板 #

针对上面的四类，模板可以直接抄：

text
我不希望看到 core / common / utils 这种模糊模块。
我不希望这是一个「框架先行」的项目。
我不希望这是「看起来可扩展，但不知道怎么用」的设计。
我不希望 Qt 项目被设计成非 Qt 风格。

最后一条值得展开：每个技术栈都有自己的「自然长法」。Qt 项目的信号槽、对象树、父子生命周期就在那里，硬套一套 service 分层，写出来的代码能用，但任何人接手都要先学一遍你的转译规则。让 AI 遵守技术栈的惯用法，比让它遵守你的抽象教条更有价值。

看到「别扭」时的正确反应 #

第一反应不是「哪里不对」，而是「我要禁止这种味道」。

前者要求你精确定位问题，代价高、容易卡住。后者只要求你描述厌恶，然后让 AI 换一版。

具体做法：

  1. 看到别扭，先别分析，只记录一句否定。
  2. 把这句话加进 System 的否定条款。
  3. 再生成一次。

迭代几轮，你的 System 里会积累出一份专属的否定清单。这份清单比任何 Prompt 教程都值钱，因为它是针对你的审美校准出来的。

否定式 Prompt 示例汇总 #

你看到的现象 无效的肯定句 管用的否定句
每个函数上面都有一段注释复述函数名 注释少一点 不要写注释，代码自己要能读懂
三个地方重复的代码被抽成了一个抽象类 别过度设计 不要为了复用两行代码就提取基类
输入是内部调用，还是加了 try-catch 简单点 不要写参数校验，调用方保证输入合法
目录里出现 utils 和 common 结构清楚点 不要出现 utils、common、core 这类目录
每个类都有 getter/setter 和接口文件 别搞这么复杂 不要给数据结构生成 getter/setter，直接用公开字段
加了一堆日志打印 日志少一点 不要加日志，这个脚本我自己会调试

五、双层 Prompt 模板 #

一句话的分工 #

System = 不能被用户推翻的规则 User = 本次要做的具体事情

这个拆分不是风格问题，它对应模型内部的一件事：优先级排序。大致是：

text
system  >  developer  >  user

模型在长对话里会衰减对前面内容的注意力，但对高优先级位置的遵循度衰减得慢。把长期约束放在 System，等于给它一个更高的留存等级。

为什么必须分两层 #

设想你把所有内容塞进 User：

text
你是一个资深工程师，请注意架构设计，不要写示例代码。
现在帮我实现一个日志分析工具。

第一轮还凑合。到第五轮，你连着说「再加个过滤」「导出改成 CSV」「性能优化一下」，前面那句「注意架构设计」在上下文里被推得越来越远，模型开始照最近的指令干活，架构约束慢慢失效。

System 层不受这个影响，它每轮都在。

什么放哪一层 #

你想写的内容 放哪层 原因
身份 / 风格 System 长期约束
架构原则 System 不可动摇
输出格式 System 防止跑偏
否定条款 System 长期压制坏习惯
这次做什么 User 每次不同
这次关注点 User 每次不同
这次限制 User 可被覆盖
临时示例 User 不影响规则

一句判断法 #

犹豫一句话该放哪时，问自己：

这句话三个月后还成立吗？

成立就放 System，不成立就放 User。

这个判断足够用。「你是一个有工程经验的开发者」三个月后成立，放 System。「这次重点是结构清晰而不是功能完整」三个月后不成立，放 User。

System 的四个职责 #

System 只回答四件事，多一件都是冗余。

① 身份。 你是谁。

② 价值观 / 审美。 你反感什么、你看重什么。

③ 架构原则。 核心稳定、变化点外置、模块边界清晰。

④ 输出硬约束。 输出格式、禁止项。

两条禁令：

  • System 里不出现具体业务。业务会变，System 不该变。
  • System 不写「这次要做什么」。那是 User 的事。

完整的 System 示例 #

text
你是一个有丰富工程经验的 Qt / C++ 高级开发工程师，遵循以下原则：

- 设计可长期维护、可演进和持续扩展的软件工程结构
- 核心框架应保持稳定
- 重视模块边界、职责清晰和扩展点设计
- 反感示例式代码、臃肿结构和模糊模块（如 core / common / utils）
- 变化点必须外置，通过模块或插件扩展
- 新功能不应修改已有核心代码
- 结构应一眼能看出职责划分

你的输出必须是工程级项目设计，而不是教学示例。
你避免以下设计：
- 模糊职责的通用模块（core / common / utils）
- 为了扩展而扩展的空壳插件
- 仅在文档中存在、但无法直观使用的扩展点
- 把业务流程隐藏在抽象层之后

拆开看：前半段是身份与价值观，中段是架构原则，后半段是输出硬约束与否定条款。整段没有任何具体业务名词。

User 的三个问题 #

User 只回答三件事：

  1. 现在要做什么
  2. 关注点是什么
  3. 这次的限制是什么

模板：

text
项目用途：
（这是干嘛的）

本次关注点：
（结构 / 扩展性 / 可测试性 / 性能 等）

额外约束：
（这次特别在意的点）

填成具体内容：

text
项目用途：
开发一款网络连接状态检测工具，用于检测设备、IP 和网址的可达性。

本次关注点：
项目结构设计，强调模块解耦和扩展边界清晰。

额外约束：
新增设备类型或检测规则时，不应修改核心模块。

三行，全部具体。User 层要的就是具体。

System 该稳、User 该具体 #

这两句话是一对。

层 稳定性要求 具体程度要求 违反后的症状
System 至少一个月不动 抽象，只讲原则 每次生成风格都不一样
User 每次都可以换 具体到能验收 AI 交出一堆你没要的东西

System 频繁改，你就失去了「同一套审美持续生效」这个最大的杠杆。User 太抽象，你就失去了「这次到底要什么」的锚点。

不要把强约束放进 User #

这三句话看着很对，放 User 里基本无效：

text
你要像一个资深工程师一样
请注意架构设计
不要写示例代码

原因：User 是弱约束，模型在复杂任务下会忽略它。这三句本身又是抽象表述，AI 很难把它们映射成具体动作，两重衰减叠加，等于没说。

正确位置是 System。放到 System 之后，它们会从「一句请求」变成「一条规则」。

六、三阶段：生成、重构、演化 #

三个阶段，三个目标 #

阶段 目标 你的动作 验收标准 允许的粗糙度
生成 先跑起来 描述意图，让它落盘 能运行、有输出 高，丑没关系
重构 稳住结构 只看目录名，判断顺不顺 结构能接受长期维护 中，功能不增不减
演化 小步可控 每次只改一块，改完就验证 每步都能回滚 低，债务不许累积

三个阶段不能跳过，也不能压缩成一个。跳过生成，你会花几天设计一个跑不起来的架构；跳过重构，你会在一个歪结构上叠功能；跳过验证，你会在一堆无法确认的改动里失去方向。

第 1 阶段：生成 #

目标只有一个：让东西跑起来。

阶段切换的标志是动作变了：从「我写代码」变成「我描述意图」。你不写实现，只给方向，代码由 AI 落地。

第一步，直接要项目结构加文件：

text
我要一个 Python CLI 工具，用来分析日志文件，
支持按关键词过滤，并输出统计结果。

结果不是聊天窗口里的一段代码，是目录里直接出现文件：

text
log_analyzer/
├── README.md
├── main.py
├── analyzer.py
└── requirements.txt

这个「直接落盘」的差别很关键。聊天里的代码你还得复制、粘贴、建目录、改路径，每一步都是打断。落盘的代码你可以立刻运行。

生成阶段为什么允许粗糙 #

因为这个阶段的产出是讨论材料，不是最终代码。

一个能跑但很丑的版本，让你能指着它说「这个感觉不对」「这里应该分开」。一个不能跑但设计精美的版本，让你什么也说不出来。

所以生成阶段的正确心态是：先要一个能运行的东西，别在第一步就要求它好看。

落盘脚本 #

如果工具本身没有写文件的能力，需要自己搭一层「生成 → 落盘」的脚本。最小版本长这样：

python
import os
import sys
import json
import requests

API_KEY = os.getenv("DASHSCOPE_API_KEY")
if not API_KEY:
    print("未检测到 DASHSCOPE_API_KEY")
    sys.exit(1)

prompt = sys.argv[1]

SYSTEM_PROMPT = """
你是一个资深软件工程师。请根据用户需求：
1. 设计项目目录结构
2. 生成所有必要文件
3. 输出 JSON，格式如下：

{
  "project_name": "xxx",
  "files": {
    "path/to/file1.py": "文件内容",
    "README.md": "说明"
  }
}

不要输出多余文字，只输出 JSON。
"""

resp = requests.post(
    "https://dashscope.aliyuncs.com/api/v1/services/aigc/text-generation/generation",
    headers={
        "Authorization": f"Bearer {API_KEY}",
        "Content-Type": "application/json",
    },
    json={
        "model": "qwen-turbo",
        "input": {
            "messages": [
                {"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": prompt},
            ]
        },
    },
)

data = resp.json()
content = data["output"]["text"]
spec = json.loads(content)

root = spec["project_name"]
os.makedirs(root, exist_ok=True)

for path, code in spec["files"].items():
    full = os.path.join(root, path)
    os.makedirs(os.path.dirname(full), exist_ok=True)
    with open(full, "w", encoding="utf-8") as f:
        f.write(code)

print(f"项目已生成：{root}")

这段代码里有三个地方会在后面变成坑，第九章会逐个解决：json.loads(content) 没有清洗（AI 会返回 Markdown）、没有校验 files 结构、直接写盘没有 dry-run。

先跑通，再加固。这也是生成阶段本身的节奏。

第 2 阶段：重构 #

目标也只有一个：调结构，不调功能。

这一步有个很管用的做法：打开刚生成的目录，只看文件名，不看内容。

然后问自己三个问题：

  1. 这个结构我三个月后还能维护吗？
  2. 职责有没有混在一起？
  3. 如果加新功能，往哪里加？

不需要精确答案，只需要一个感觉：顺，或者别扭。

用一句话重构整个项目 #

重构指令不需要指定怎么重构，只描述感觉标准：

text
重构刚才生成的项目：让核心逻辑和 CLI 解耦，结构更清晰，方便后续扩展。

注意这句话里没有任何实现细节。它说的是「解耦」「清晰」「方便扩展」，验收方式是你再看一遍目录，感觉顺不顺。

对比一下错误写法：

text
把 analyzer.py 拆成 analyzer.py 和 filter.py，
把 main.py 里的参数解析移到 cli.py。

这版指定了文件划分，等于你自己做完了设计，AI 只是个执行器。你放弃的是 AI 提出更好划分的空间。

第 3 阶段：持续演化 #

目标：每次改动都小、都验证、都可回滚。

这一阶段的真实含义经常被误解。它不是「让 AI 一直改」，而是每一次改动都要能验证。改了不能验证，就是在积累债务。

具体节奏：

  1. 定一个最小改动目标（一句话能说清，一个文件能改完）。
  2. 让 AI 输出改动。
  3. 看一眼 diff。
  4. 跑一次，确认行为符合预期。
  5. 提交。

第 4 步不能省。省掉的每一次验证，都会在后面变成一次「不知道从哪开始坏」的排查。

持续演化的三层能力 #

演化阶段不只是改代码，AI 可以接手的范围会逐步扩大：

接管对象 你保留什么 风险
重构 判断结构是否顺 中，改坏结构要重来
测试 判断测试是否覆盖真实行为 低，测试失败是显式的
文档 判断描述是否与代码一致 低，错了不阻塞运行

顺序就是从低风险往高风险走。测试和文档先交出去，重构后交出去。

演化阶段的节奏控制 #

错误节奏 后果 正确节奏
一次让它改五个文件 出问题时定位不到原因 一次一个模块
改完直接提交 债务进仓库 改完先跑一次
感觉不对就整段重生成 之前修好的点全部丢失 只针对别扭的那个点下指令
攒十个改动一起验证 失败时不知道怎么二分 一步一验证

七、从结构切到实现的时机 #

唯一标准是改动成本 #

「先定结构还是边写边调」这个问题争论很久，答案其实是成本算术：

错的东西 修正方式 代价
结构错了（层级、边界、扩展点） 大规模搬文件、改引用、重写调用链 高，且很难中途停
实现错了（函数体写歪了） 改一个函数 低

所以在结构还没定的时候写实现，是在用最低成本的阶段去承担最高成本的风险。

反过来，结构定得差不多了还在改结构，是在用高成本的方式磨一个已经够用的东西。两头都不划算，切换点必须显式判断。

三个错误信号 #

这三个想法一出现，说明你还没到切换点：

text
我们先把 main.cpp 写出来看看
先跑起来再说
逻辑可以边写边调

任何一句出现，都意味着你在用「先写一行试试」的方式逃避结构决策。而结构阶段一旦被这么打断，基本就回不去了——代码有了，你就开始围着代码修补，而不是围着问题设计。

三个必答问题 #

只有当你能用一句话回答下面三个问题，才进入实现阶段：

  1. 新增一个设备（或一种类型），要加哪一个文件？
  2. 删除一个模块，不会影响谁？
  3. 核心流程是否不依赖具体实现？

三个问题分别对应三件事：扩展点位置、边界独立性、抽象层是否成立。

答不上来，说明结构还有洞。答得出来但要用三句话，也说明还有洞——需要三句解释的结构，读者记不住。

正确的实现顺序 #

进入实现后，顺序也有讲究：

顺序 做什么 为什么这样排
1 最小可跑链路 只打通一条完整流程，不是全部功能
2 核心接口 声明形状，不写具体逻辑
3 具体实现 最后才写设备、IP、URL 等具体分支

顺序反过来的典型症状：先写了三个具体实现，然后发现它们共有的那部分每次都重写一遍，再回头抽接口——抽出来的接口是按「这三个」的形状捏的，第四个进来就不合适。

最小可跑链路的意思是：一条从头到尾能走的路径，哪怕中间都是硬编码。跑通之后，每一段替换都有参照物。

结构阶段的具体动作 #

结构阶段不是「画图」，是「描述变化」。

① 先列出一定稳定的东西。 不管以后怎么变，这些不会动。比如一个放置类游戏里：

  • 时间推进（tick / 离线结算）
  • 资源累积（金币）
  • 「产出 → 累积 → 消费 → 提升产出」这个循环

这三条是世界规则，不是功能。它们应该在最内层，且改动频率最低。

② 再列出一定变化的东西。

  • 元素类型（矿机、农田、工厂……）
  • 升级曲线
  • 产出公式
  • UI 表现方式

这些必须是扩展点，也就是「加东西不用改老代码」的位置。

③ 最后标出最危险的耦合。 如果代码里出现下面这种关系，结构就失败了：

text
UI 直接算金币
UI 直接改产出
元素类自己处理时间

三件事必须彻底隔离。理由不是教条，而是这三处正好是变化频率最高的三处：UI 天天改、产出公式经常调、时间处理涉及离线和测试。让高变化的东西互相直接依赖，等于每次改动都同时动三个模块。

一个真实的结构演进例子 #

以放置类游戏为例，看结构阶段怎么走。

第一版结构按企业软件习惯分层：

text
idle_game/
├── domain/
│   ├── economy/        Wallet / EconomyService
│   ├── production/     IProducer / ProductionSystem
│   ├── upgrade/        UpgradePolicy / UpgradeService
│   └── time/           GameClock / TickScheduler
├── elements/           Element 基类 + MineConfig
├── ui/                 viewmodels / widgets
└── persistence/        SaveRepository

三个必答问题都能过：新增元素去 elements/，改结算去 domain/economy，UI 不知道公式。逻辑上没错。

但是会觉得别扭：结构是对的，但不像一个放置类游戏自然长出来的。

真实的别扭点在抽象层级不对位，不在目录命名：

  1. domain 太像企业软件。economy / production / upgrade / time 这套拆法是后端服务的语言，不是游戏的语言。
  2. 「元素」被当成了插件，而不是主角。放置类游戏的中心是「会产出、能升级、随时间变化的实体」，但在上面这版里，产出在 production、升级在 upgrade、时间在 time，元素被拆薄了。主次反了。
  3. 系统太多，「流」被切碎了。放置游戏的本质是一句话——世界在流动，东西在变多。一堆 service 里看不出这条流。

换成「游戏脑」之后的四个概念 #

旧结构用 Economy / Production 组织，新结构用四个词：

概念 含义
World 游戏世界（时间 + 状态）
Entity 放置的东西（元素）
Rule 怎么产出 / 升级
Flow 时间推动后的结算

一句话概括：放置类 = World Flow 驱动 Entity State。

对应三条原则：

  • 元素是第一公民
  • 系统只做「推动世界」的事
  • 变化点像「加卡牌」，不是改规则

第二版结构 #

text
idle_game/
├── core/                       # 世界核心（极稳）
│   ├── World.h
│   ├── GameLoop.h
│   └── TimeSource.h
├── entities/                   # 放置元素（主角）
│   ├── base/                   Entity / EntityState / IEntityLogic
│   ├── mine/                   MineEntity / MineLogic
│   └── farm/                   FarmEntity / FarmLogic
├── rules/                      # 游戏规则（可替换）
│   ├── production/             ProductionRule
│   ├── upgrade/                UpgradeRule
│   └── economy/                CurrencyRule
├── player/                     Wallet / PlayerState
├── ui/                         viewmodels / widgets
├── persistence/                SaveGame
└── main.cpp

三个变化对应三个改进：

元素终于是完整生命体。 一个 Entity 自己有状态、自己知道用哪个规则、不碰 UI、不算时间。它像卡牌、像建筑、像单位，而不是一个数据容器。

Rule 是策略，不是系统。 ProductionRule 和 UpgradeRule 表达的是「如果这样算，就会得到这些结果」，它们不做调度。系统的调度权只在 World 手里。

World 只做一件事。

text
推进时间 → 让实体结算 → 汇总结果

World 不知道矿机是什么。这条约束是整个结构能稳住的根本。

结构阶段怎么验收 #

不要用「我觉得对」验收，用一个具体场景验收。

比如：新增一个核电站。

只需要加两个文件：

text
entities/nuclear/
├── NuclearEntity.h
└── NuclearLogic.h

World 不改、UI 不改、规则可复用或微调。

这就是「不臃肿」的检验方式：新增一种东西，加目录，不改中心。

结构阶段什么时候结束 #

判断标准只有一句：

当你自己说出「这个结构我能接受长期维护」时，结构阶段结束。

注意是「能接受」，不是「最理想」。追求最理想的结构会一直停在结构阶段，那也是一种浪费。

从结构到实现的切换，是主动决策，不是自然滑落。你必须在某一次对话里明确说出「结构定了，开始写实现」，否则会一直在两版之间来回改。

八、胶水编程 #

AI 生成的是积木，人做的是胶水 #

这一章讲的是 Vibe Coding 里人不可替代的那部分工作。

AI 生成的代码有一个共同特征：它们都是孤立的正确。每个函数单独看都对，放在一起就不对。原因很简单——AI 生成单个文件时，看到的是「这个文件应该做什么」，看不到「这个文件在什么时候被谁调用」。

把这些孤立正确的部分粘起来，就是胶水工作：

积木（AI 产出） 胶水（人负责）
一个个类与函数 它们之间的调用顺序
函数签名的实现 函数签名本身该长什么样
单个模块内的逻辑 模块之间的数据形状
正常路径的处理 边界条件、空值、失败路径
每个文件内部的命名 跨文件的概念是否一致

胶水的三件事 #

第一件：定义接口。

AI 给你 MineEntity::update()，但它不知道该不该返回产出量。这个决定跟下一个模块怎么用直接相关，只有你知道数据接下来去哪。

接口定了，两边可以各自 AI 生成，因为契约在中间。接口不定，两边都要改，改一边另一边就坏。

第二件：处理边界。

AI 写正常路径很稳，写边界很差。它倾向于在每处都加防御，或者干脆全不加——取决于你怎么说。但真正的边界处理需要知道业务事实：

  • 存档文件损坏时，是重建还是报错？
  • 离线时间跨度是 8 小时还是 8 天，结算方式一样吗？
  • 两个元素同时产出到同一个钱包，顺序有影响吗？

这些问题 AI 答不了，因为它不知道你的用户会怎么用。

第三件：编排顺序。

text
加载存档 → 补算离线收益 → 初始化 UI → 启动 tick

这个顺序里任何一步挪位置都会出 bug，而它对每个单独模块都是不可见的。这种全局顺序只能由人写，多半写成 main 里那十几行。

一个具体的胶水示例 #

假设 AI 分别生成了 World、MineEntity、GameLoop，把三者粘起来的是这样一段：

python
world = World()
mine = MineEntity()
world.add_entity(mine)

loop = GameLoop(world)
while True:
    loop.tick()
    sleep(1)

这十几行里没有一个算法，但它决定了：

  • 谁持有谁（GameLoop 通过引用操作 world）
  • 谁先创建（mine 必须在 add 之前构造完成）
  • 循环节奏在哪一层（在最外层，不在 tick 内部）

这就是胶水。它不是「剩下的活」，它是唯一能看到全局的地方。

为什么 AI 替代不了胶水 #

因为胶水需要的两个输入，AI 都没有：

输入一：这三个模块为什么在一起。 代码里没有写，写在你的脑子里。

输入二：出问题时先怀疑哪一个。 这是调试直觉，来自你被这几个模块坑过的次数。

所以胶水活永远是人写，或者是由人把「这三者的关系」明确描述给 AI，让它代写。后者也算人写的，因为关系是你定义的。

胶水越少越好 #

一个反向的工程原则：胶水代码的行数是结构质量的指标。

胶水多，说明模块之间关系复杂、需要大量手工对齐。胶水少，说明边界切得干净、每个模块自己能收口。

所以当你发现自己在写第 50 行胶水时，不是该更仔细地写，而是该停下来问：这两个模块的边界是不是切错了？

九、用 Json Schema 约束输出 #

为什么需要结构化输出 #

让 AI 返回自然语言里的代码，然后你手动复制粘贴，这条路只在第一天好用。

一旦你想让程序自动落地文件，就必须让 AI 输出机器能解析的东西。而自然语言输出有三个稳定的毛病：

毛病 表现 后果
带前言 「好的，下面是实现……」 json.loads 从第一个字符就失败
带代码块标记 内容包在 ``` 里 对人是渲染，对解析器是垃圾字符
字段漂移 这次叫 path，下次叫 file 解析器时好时坏

三种都指向同一件事：AI 的输出是不稳定的外部服务，按不稳定对待，别按魔法对待。

一个真实会踩的错 #

text
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)

看到这个报错，说明 content 多半是下面五种之一：

  1. 空字符串（API 请求失败，但你没检查状态码）
  2. 自然语言（「Sure! Here's the implementation...」）
  3. Markdown 包裹的 JSON
  4. HTML 错误页
  5. Key 无效导致的报错信息

第一条要做的不是改代码，是打印原始内容看看 AI 到底返回了什么：

python
print("==== RAW CONTENT START ====")
print(content)
print("==== RAW CONTENT END ====")

先看，再修。这一步能省掉大量瞎猜。

最小可用的 Schema #

这是能用很久的一版：

json
{
  "intent": "add | modify | refactor | explain",
  "scope": "entities/mine",
  "summary": "一句话说明这次做了什么",
  "files": [
    {
      "path": "entities/mine/MineEntity.h",
      "action": "create | modify",
      "content": "完整文件内容"
    },
    {
      "path": "entities/mine/MineEntity.cpp",
      "action": "modify",
      "content": "完整文件内容"
    }
  ],
  "notes": [
    "不修改 World",
    "不引入新模块"
  ]
}

设计上刻意避开了两样东西：

  • 没有 diff。 diff 是给人读的，机器读 diff 要额外写一层解析，而且容易在上下文行上出错。
  • 没有 patch。 patch 很脆，一行对不上整块失败。早期用不上。

留下的是「一个文件 = 一个事实」：路径、动作、完整内容。这三样足够把仓库状态确定下来。

System 层怎么写才管用 #

Schema 定得再好，System 不写死也白搭。这一段是决定后面稳定性的地方：

text
你是一个软件工程助手。

你只能输出【严格合法的 JSON】。
禁止输出：
- Markdown
- 解释性文字
- 代码块标记
- 多余字段

JSON 必须满足以下规则：
- 顶层是一个对象
- 必须包含 intent / scope / files
- files 中的 content 是完整文件内容
- 输出必须能被 json.loads 直接解析

如果你无法满足要求：
- 输出一个空的 files 数组

最后两行最重要。「输出空结果」比「乱输出」强得多——空结果会让你的程序在解析层明确失败，乱输出会让你的程序把垃圾写进文件系统。

解析层不能信 AI #

即便 System 写得再严，解析层也必须自己做检查：

python
import json

def parse_spec(content: str):
    content = content.strip()
    if not content:
        raise RuntimeError("AI returned empty content")

    try:
        spec = json.loads(content)
    except json.JSONDecodeError as e:
        raise RuntimeError(f"AI output is not valid JSON:\n{content}") from e

    if "files" not in spec or not isinstance(spec["files"], list):
        raise RuntimeError(f"'files' missing or invalid in spec:\n{spec}")

    for f in spec["files"]:
        if not all(k in f for k in ("path", "action", "content")):
            raise RuntimeError(f"File entry missing required keys:\n{f}")

    return spec

四个检查：非空、能解析、files 是数组、每个条目有三个必需键。

失败要早、要响。不要用 content.split("```")[1] 这类补锅写法——那是补锅，不是设计。它在你本地能跑，换一个模型就崩。

落地流程必须是四段 #

text
AI → JSON Spec → 校验 → 预览 → 应用

不要写成 AI → 直接写文件。中间那两步是全部的工程价值。

阶段 做什么 失败时
接收 原样保存、打日志、不解析 你能回溯 AI 到底说了什么
校验 类型、必需字段、路径合法 直接失败，不落盘
预览 打印将要改的文件清单 人看一眼就能发现方向错
应用 建目录、备份、写入 有 .bak 可回退

预览这一步的价值经常被低估。它只需要你扫一眼：

text
将要修改的文件：
- entities/mine/MineEntity.h (modify)
- entities/mine/MineEntity.cpp (create)

如果这个列表里出现了你没提到的文件，你立刻知道 AI 越权了。这个发现如果发生在写盘之后，就变成了一次 git 回滚。

落地代码 #

python
import shutil
from pathlib import Path

def apply_spec(spec, dry_run=True):
    for f in spec["files"]:
        path = Path(f["path"])
        content = f["content"]
        action = f["action"]

        if dry_run:
            print(f"[DRY-RUN] {action.upper()} {path}")
            continue

        path.parent.mkdir(parents=True, exist_ok=True)

        if path.exists():
            shutil.copy(path, str(path) + ".bak")

        with open(path, "w", encoding="utf-8") as fp:
            fp.write(content)
        print(f"{action.upper()} {path}")

三件事：目录自动创建、已存在文件先备份、dry-run 模式不写盘。

最后一点是安全阀。日常用法是 dry-run 看清单，确认后才 apply。

模块拆分 #

把上面这些拆开，得到一个能长期用的结构：

text
softengineer/
├── __main__.py           # CLI 入口
├── ai_client.py          # 调用模型 API
├── spec_parser.py        # 解析 / 校验 AI 输出 JSON
├── file_manager.py       # 安全落地，支持 dry-run / apply

每个模块的职责单一，尤其注意 ai_client 的一条规则：

python
class AIClient:
    def run_task(self, system_prompt, task_prompt):
        payload = {"system": system_prompt, "user": task_prompt}
        headers = {"Authorization": f"Bearer {self.api_key}"}
        response = requests.post(self.endpoint, json=payload)
        response.raise_for_status()

演进版 Schema #

最小 Schema 有三个限制：不能只改一小部分、不能删文件、不能表达结构性调整。升级版用四个字段解决：

json
{
  "intent": "add | modify | refactor | delete | explain",
  "scope": "entities/mine",
  "summary": "为 MineEntity 增加基础金币产出",
  "changes": {
    "files": [
      {
        "path": "entities/mine/MineEntity.h",
        "operation": "create | replace | delete",
        "content": "完整文件内容（create / replace 必须）"
      },
      {
        "path": "entities/mine/MineEntity.cpp",
        "operation": "patch",
        "patch": {
          "type": "unified",
          "content": "--- a/...\n+++ b/...\n@@ ..."
        }
      }
    ]
  },
  "constraints": [
    "不修改 core",
    "不引入新模块"
  ],
  "confidence": 0.93
}

四个改动各有理由：

operation 取代 action。 用 create / replace / patch / delete 四个词，语义不重叠，不会产生歧义。modify 到底是改一行还是整文件替换，说不清。

patch 是能力描述，不是强制实现。 你的解析器可以先看到 patch 就报错，等你准备好再实现。Schema 可以描述得比实现更多，这是常用技巧。

changes 是变更域。 不直接放 files，是为了以后能加 directories、configs、deps，位置先留好。

constraints 是自我审计。 这个字段不是给你读的，是给程序用的：可以打日志、可以在 CI 里检查、可以事后对比 AI 有没有越权。这是「思维留痕」。

confidence 是工程信号。 它不是准确率，是一个可用于分流的值：

区间 动作
高于 0.8 可直接 apply
0.6 到 0.8 强制 dry-run
低于 0.6 拒绝 apply，回去改 Prompt

第一阶段只实现两件事 #

不要一次性支持全部能力。先只做：

  • operation: create
  • operation: replace
  • patch / delete 一律报错

现在不要碰的：diff 合并、AST patch、智能冲突解决。这三样会吞掉你一整个月，而你连 Schema 都还没跑顺。

解析器的演进规则 #

text
1. 校验 intent / scope / changes.files
2. 遍历 files：
   - operation == replace → 必须有 content
   - operation == patch → 暂不支持 → fail fast
3. 不认识的字段 → 忽略，但记录

原则叫严格输入，宽松未来：已知字段严格校验，未知字段只记录不报错。这样旧代码能跑新 Schema，新 Schema 也不用为兼容性砍掉字段。

接进编辑器 #

把这套流程绑成编辑器任务，日常就变成两个快捷键：

json
{

这套流程里 AI 的角色可以精确描述为：不带写权限的高级外包。 它产出方案，落盘权在你手上。

十、多轮演化的技巧 #

同一个 System，不断修 User #

多轮演化的正确形态只有这一句：

text
一个 System，一直不动
一个 User，一次次修
项目逐步进化

它不是「不满意就重新生成」。重新生成会把之前校准好的点全部丢掉，你回到起点，再走一遍同样的路。

对比两种循环：

一次性思维（错） 演进思维（对）
一次 Prompt 同一个 System
一次生成 User 逐轮修正
不满意 → 推翻重来 不满意 → 只改别扭的那个点

差别在于你在改什么。前者在改全部的输入，后者在改一个具体决策。

三轮节奏 #

一个可复用的三轮结构：

第 1 轮：只看结构。

text
项目用途：
网络连接状态检测工具

本次关注点：
模块边界与扩展方式

额外约束：
新增检测对象不修改核心

这一轮的验收方式是：只看目录，不看实现。实现这时候还不存在。

第 2 轮：针对别扭点。

text
在上一次设计的基础上：
我不希望出现模糊职责的模块；
希望能一眼看出检测流程从哪里开始，到哪里结束。

注意这一轮没有增加任何功能。它是审美修正，不是需求变更。把这两件事分开是多轮演化的关键，混在一起你会发现每轮都在加需求，结构永远定不下来。

第 3 轮：确认稳定点。

text
请明确哪些模块是稳定核心，
哪些是预期会频繁变化的扩展点。

这一轮是在逼 AI 显式表达架构意图。它输出来的分类，你可以直接拿去当后续改动的判断依据：改稳定核心要谨慎，改扩展点是日常。

三层循环的关系 #

多轮演进、否定式 Prompt、结构到实现的切换，这三件事不是三个阶段，是一个循环的三个动作：

动作 频率 作用
修 User 每轮 推进具体设计
补否定条款 每次看到别扭 永久提高下限
判断是否切换阶段 每次结构验收后 控制节奏

第一个动作负责当下，第二个动作负责长期，第三个动作负责不跑偏。

让 AI 显式表达不确定性 #

多轮对话里最有价值的一句话：

text
如果需要新增抽象，请先停下并说明理由，不要直接实现。

这叫安全阀。AI 的默认行为是遇到选择就自己决定然后往下写，你看到的是一个已经成型的、无法追溯的决定。加上这句之后，它会先报告，你再决定。

为什么管用：它把「沉默的决策」变成了「需要你批准的决策」。多数时候你会同意，但你会知道那里发生了一次设计选择——这个知情权本身就有价值。

控制粒度的写法 #

写法 AI 的实际动作 可控性
帮我实现一个放置类游戏 一次生成几十个文件，方向自己定 失控
只实现 Entity 基类和 MineEntity 的最小可运行版本，不要实现升级、UI、存档 输出被压缩在一个模块里 可控

原则：一次只允许 AI 碰一个稳定边界。

「一个稳定边界」是指一个目录、一个模块、一组相关文件。跨边界的改动会同时产生多个不确定点，出问题时无法二分定位。

改动的三种类型要分开说 #

每一轮 User 只做一件事，先分类：

类型 例子 该怎么说
加东西 增加一个过滤选项 说清加在哪、不许动哪里
调结构 把核心逻辑和 CLI 解耦 说感觉标准，不说怎么拆
审美修正 这个模块太模糊了 说你不希望看到什么

三种的 Prompt 写法完全不同。加东西要精确说范围，调结构要抽象说标准，审美修正要用否定句。混着说，AI 会按最字面的那条执行。

一次只改一件事 #

这条听起来慢，实际最快。

一次改三件事的症状：

  1. 跑起来不对。
  2. 不知道是三件里的哪件导致的。
  3. 想把三件分开，发现已经混在一个 diff 里。
  4. 全部回滚。

一次改一件的流程：

  1. 改完，跑一次，对。
  2. 提交。
  3. 下一件。

每一步都是安全的，任何一步错了，回滚范围就是那一步。

对话太长时怎么办 #

多轮之后上下文会变长，模型对早期内容的注意力会衰减。三个处理方式：

症状 做法
开始重复你已经否掉的设计 把否定条款挪进 System，重新开一轮
忘记了最早定的分工 把结构结论写成文件，下一轮直接引用文件
每轮都要重述同样的约束 说明它该进 System，不该在 User 里重复

核心思路一致：凡是你重复说过两次的话，都应该升级成文件或 System 条款。

一次完整的多轮记录 #

把上面的技巧落成一条真实链路：

text
轮 1  只输出目录结构，不写实现。核心稳定、变化点外置。
轮 2  我不希望出现模糊职责的模块；请让主流程的起点和终点能一眼看出来。
轮 3  请标出哪些是稳定核心，哪些是计划中的扩展点。
轮 4  结构定了。只实现 World 的 tick 与 Entity 基类，不要规则、不要 UI。
轮 5  把产出逻辑从 Entity 抽出来变成 Rule。不要新增其他文件。
轮 6  增加第二个元素类型。只允许新增 entities 目录下的文件。

六轮里，System 一次没动，User 每轮只推进一件事。这就是可以长期复用的形态。

十一、这套方法的边界 #

适合什么 #

场景 为什么适合 注意
原型与一次性脚本 目标是跑通，不是长期维护 别把它当正式代码
内部工具与 CLI 输入输出明确，边界好写 边界条件要人补
UI 布局与样式 反馈即时，错了马上看见 状态管理仍要人管
CRUD 与表单流 模式重复，AI 见过大量样本 权限与校验逻辑要人定
结构重排与改名 机械劳动，最费人也最容易出错 改完必须能编译通过
测试与文档 失败显式，成本低 测试要人判断覆盖是否真实

这些场景的共同点：错了能立刻发现，或者错了代价低。

不适合什么 #

场景 为什么不适合
性能敏感的热路径 AI 没有你的实测数据，它的优化是猜的
并发与内存顺序 正确性无法靠读代码确认，需要压测与模型检验
安全关键路径 一处遗漏的边界判断就是漏洞，而漏掉的不会显形
加密与协议实现 细节错一个字节就是全错，且很难靠肉眼发现
数值精度要求高的计算 浮点顺序、累积误差这类问题不会在样例里暴露
有硬性合规要求的代码 需要可审计的决策链，AI 的决策链不可回溯

这些场景的共同点：错了不会立刻报错，会在某个特定条件下才炸。

判据不是语言或项目类型 #

不要按「C++ 还是 Python」来判断，要按验证成本判断。

验证成本 例子 能不能交给 AI
一眼能看出来 目录结构、UI 布局 能，直接生成
跑一次能验证 CLI 逻辑、数据转换 能，配合用例
要构造特定条件 并发、边界输入 谨慎，必须先有测试
只能靠推理或形式化 协议、算法正确性 不交给 AI 决策

第四档不是说不能用 AI，是不能让 AI 做决定。它可以写，但方案必须由你定，且要有独立验证。

一个容易忽略的限制 #

AI 对你的项目历史一无所知。

它不知道上次为什么否掉那套分层，不知道哪个模块因为性能原因被手写过，不知道那个看起来多余的判断是为了兼容旧存档。这些信息只在你的脑子里和 git log 里。

处理方式是把它们变成文字：

  • 关键决策写进 .ai/system.md 的否定条款
  • 关键历史写进项目内的 DECISIONS.md
  • 每次让它改动前，把相关的那一段贴进 User

不写下来，你会发现自己在反复解释同一件事，而 AI 每次都会重新犯同样的错。

不要用它做的事 #

有三件事不属于这套方法的范围：

  1. 替代你理解系统。 你不懂的代码，AI 改完你更不懂。改之前先读懂。
  2. 替代验证。 「AI 说它测过了」不构成验证。
  3. 替代决策。 该不该做这个功能，不该问 AI。

十二、易错点速查 #

Prompt 层 #

易错点 症状 改法
用肯定句表达审美 「写得简洁点」被理解成删注释 换成具体否定句

每次动手前的五行自检 #

text
1. 我这次改的范围是：
2. 我明确不要的是：
3. 我怎么验证改对了：
4. 这次只碰一个模块吗：
5. 我重复说过的话，进 System 了吗：

五行都能填出来，再发 Prompt。填不出来的那行，就是你没想清楚的地方。

一句话收尾 #

这套方法的全部杠杆在一个地方：你把边界说得多清楚。

边界清楚，AI 的输出就是可用的积木，你只需要做胶水。边界模糊，AI 会给你一个它自己觉得合理的东西，然后你花三倍时间把它改回你想的样子。

所以每次觉得「AI 不好用」的时候，先回头看一眼自己的 Prompt：范围写了吗、禁令写了吗、验收标准写了吗。三个问题里多半有一个是空的。
