边界先划清。这篇讲两件事：文件系统有哪些类型、各自适合什么场景；以及一次 write 调用从用户态到物理介质要走几层。分区、格式化、挂载的命令细节归《分区、挂载与磁盘工具》，目录树布局归《Linux 目录结构与 FHS 标准》，文件描述符的分配与回收归《文件 IO 与描述符管理》。ext4 的磁盘布局、XFS 与 Btrfs 的取舍、FAT32 / exFAT / NTFS 的跨平台定位，加上 VFS 到块层的调用链，都在这里收口。文中提到的内核版本和工具行为以 Linux 主线为准，发行版打包的补丁不单独讨论。

一、文件系统是什么：从块到文件 #

块设备给你的东西很朴素：一段从 0 开始编号的扇区数组，能读能写，没有名字，没有目录，没有权限，也没有「这个位置归谁」的记录。

偏移 0                                                    末尾
+------+------+------+------+------+------+------+--------+
| sec0 | sec1 | sec2 | sec3 | sec4 | sec5 | sec6 |  ...   |
+------+------+------+------+------+------+------+--------+
你只能做两件事：读第 N 个扇区，写第 N 个扇区

文件系统就是在这层之上加东西的软件。它要解决四件事，缺一件都不成：

要解决的问题 手段 ext4 里的实体
命名：扇区怎么变成有名字的东西 目录树 + 目录项，文件名映射到编号 目录数据块里的 name → inode 记录
归属：哪些块归哪个文件 分配位图或空闲区段树 块位图、extent 树
描述：大小、权限、时间、类型 独立的元数据结构 inode
一致性：掉电后还能救回来 日志 / 写时复制 / 校验和 journal 区、$LogFile 等价物

再往下看三个单位，别混：

  • 扇区：设备的最小读写单位，老式硬盘 512 字节，4Kn 盘和多数 NVMe 报 4096。
  • 块：文件系统的分配单位，ext4 默认 4096 字节，格式化时 -b 定死，之后改不了。
  • 簇：FAT / exFAT / NTFS 语境下的分配单位，等同「块」，只是换了个叫法。

块越大，顺序读写的吞吐越好，末尾浪费越多。一个 1 字节的文件照样占掉一个 4 KiB 块，这就是内部碎片。反过来块越小，元数据越多，寻址开销越大。4 KiB 是几十年硬件折衷下来的默认值，不是物理定律。

关键的一步抽象在这里：目录本身也是文件。它没有特殊结构，内容就是一张「名字 → inode 号」的表。所以「路径解析」本质上是一串特化的文件读取，没有魔法。

/var/log/test.txt
   |
   +-- 读 ext4 根目录 inode（固定号 2）的数据块
   +-- 在表里查 "var"     -> 得到 var 的 inode 号
   +-- 读 var 的 inode -> 读 var 的数据块
   +-- 在表里查 "log"     -> 得到 log 的 inode 号
   +-- 在 log 的数据块里查 "test.txt" -> 拿到最终 inode 号
   +-- 读该 inode -> 拿到数据块位置 -> 读内容

一句话收口：文件系统是把扇区数组翻译成「有名字、有归属、有权限、掉电后还能对上账」的对象的那层软件。下面所有类型差异，都是对这四个问题给出的不同答卷。

二、Linux 支持哪些文件系统 #

Linux 的文件系统按介质分三类，混着记会乱：

类别 代表 特点
磁盘文件系统 ext4、XFS、Btrfs、F2FS、FAT、exFAT、NTFS 数据落在块设备上，要管分配与一致性
内存伪文件系统 procfs、sysfs、devtmpfs、tmpfs、cgroup2 没有块设备，内容由内核现场生成或存在内存里
网络 / 只读封装 NFS、CIFS、overlayfs、squashfs、ISO9660、UDF 数据在别处，或打包后只读呈现

查当前内核认识哪些：

bash
cat /proc/filesystems          # 已注册的文件系统，nodev 表示不需要块设备
ls /lib/modules/$(uname -r)/kernel/fs/   # 以模块形式存在的实现
lsmod | grep -E 'ext4|xfs|btrfs'         # 谁已经被加载

内核层面有两条实现路线。一条是 in-tree 的原生实现，直接编进内核或做成模块，走块层，性能最好；另一条是 FUSE，文件系统跑在用户态，内核只做转发，写起来快但每次操作多两次上下文切换。NTFS 长期只有 FUSE 方案 ntfs-3g，内核原生 ntfs3 从 5.15 起进入主线；exFAT 也是先有 FUSE 的 exfat-fuse，5.7 起内核自带 exfat 驱动。

几个文件系统的来路，记住版本号有用，排查老机器时对得上：

文件系统 引入时间 备注
ext2 1993 无日志，结构就是后来 ext3 / ext4 的底座
ext3 内核 2.4.15 在 ext2 上加 journal，向后兼容
ext4 内核 2.6.19 进入主线，2.6.28 起去掉 experimental 标记转为稳定 多数发行版的默认根分区
XFS SGI 1994 年在 IRIX 上落地，2001 年移植进 Linux 2.4 RHEL 7 / CentOS 7 起成为默认
Btrfs 2007 年 Oracle 启动，内核 2.6.29 合入主线 openSUSE、Fedora 用它做默认
F2FS 内核 3.8 为 NAND 闪存设计，安卓设备常见
exFAT 2006 年随 Windows CE 6.0 出现，Vista SP1 起进入桌面 Windows 大容量 U 盘、SD 卡的通用格式
NTFS Windows NT 3.1（1993）起 Windows 系统盘唯一默认

确认某个路径到底落在哪个文件系统上，别靠猜：

bash
findmnt -T /var/log              # 顺着挂载树往上找，最准
df -T /var/log                   # 顺手看类型和用量
lsblk -f                         # 一次列出所有块设备的 FS 类型与 UUID
blkid /dev/nvme0n1p2             # 单看一个分区的 TYPE / UUID
stat -f /var/log                 # 报的是该文件所在文件系统的信息

stat -f 和 stat 不是一回事。前者看文件系统（块大小、总块数、inode 数），后者看单个 inode（权限、大小、时间）。

三、ext4：默认选择 #

ext4 是 ext3 的延伸，不是重写。它保留了块组那套布局，所以 ext2 / ext3 的分区能被 ext4 驱动直接挂上，反过来把 ext4 降级成 ext3 只要能关掉新特性就行。这种「兼容优先」的路线是它能当十几年默认值的根本原因。

3.1 块组布局 #

格式化时，mkfs.ext4 把整个分区切成若干个等大的块组（Block Group）。每个块组自带一份元数据加一段数据区，互不干扰：

【 ext4 单个块组内部经典布局 】
+----------+----------+-----------+----------+----------+------------+------------+
| 引导块   | 超级块   | 块组描述  | 块位图   | Inode    | Inode 表   | 真实数据块 |
| (Boot)   | (Super)  | 符表(GDT) | (Block   | 位图     | (Inode     | (Data      |
| [首 2KB] | [1KB]    |           | Bitmap)  | (iBitmap)| Table)     | Blocks)    |
+----------+----------+-----------+----------+----------+------------+------------+

各段的作用和损坏后果：

组成 作用 坏了会怎样
引导块 Boot Block 分区最前方 2KB，放主引导记录与引导程序 只影响从该分区启动，数据区不受牵连
超级块 Super Block 全局参数：块大小、总块数、总 inode 数、空闲计数、挂载状态 整块分区认不出来，靠备份超级块救
块组描述符表 GDT 记录每个块组的位图、inode 表位置、空闲块数 分配器失效，只能重建
块位图 Block Bitmap 1 个逻辑块，每位对应一个物理块是否空闲 该块组空间无法可靠分配
Inode 位图 iBitmap 1 个逻辑块，标记 inode 表里哪一项被占用 inode 分配错乱，出现重复号
Inode 表 Inode Table 存元数据：权限、大小、时间、数据块指针 文件「存在但打不开」
数据块 Data Blocks 文件内容与目录项实体 内容丢失，元数据还在

超级块的位置要记准：从分区起点偏移 1KB 处，长度 1KB。它太关键，ext4 用了稀疏备份策略，只在块组号为 3、5、7 的幂（1、3、5、7、9、25、27、49……）的块组里留冗余拷贝，平时只有 0 号块组的主拷贝参与读写。主拷贝废了就用备份顶上：

bash
mke2fs -n /dev/sda1                        # 只打印超级块备份位置，不写盘
e2fsck -b 32768 /dev/sda1                  # 指定备份超级块做检查

块位图的大小直接限制单个块组的最大块数，这是「块大小 × 8 × 块大小」算出来的硬边界。块位图、inode 位图各占一个逻辑块，剩下的才是数据块。

3.2 读一个文件的完整链路 #

以 /var/log/test.txt 为例，四步：

  1. 定位根目录：读根目录 inode（固定号 2），拿到根目录的数据块。
  2. 逐级检索：在根数据块里找到 var 的 inode 号，读 var 的数据块；再从中找到 log 的 inode 号，读 log 的数据块。
  3. 查表映射：在 log 的数据块里检索到文件名 test.txt 对应的 inode 号。
  4. 取内容：读 test.txt 的 inode，顺着里面的块指针找到物理块号，把数据读出来。

每一步都是一次「读 inode → 读数据块」，所以路径越深、目录越大，解析越慢。这也是 ext4 给大目录加上 htree（dir_index 特性）的原因：目录项按名字哈希排成 B 树，几万个文件同在一层也能一次定位。

3.3 inode 与寻址 #

inode 里没有文件名。文件名归父目录的数据块管，inode 只管「这个编号对应哪份数据、什么权限、几个名字指着它」。默认 inode 大小 256 字节（mkfs.ext4 -I 256），块大小 4096。

inode 空间有限，装不下大文件的全部块号，于是要分层寻址：

inode 内的块指针
  |-- 直接块指针 ------------> 数据块
  |-- 一级间接块 -> 索引块 ---> 一堆数据块号
  |-- 二级间接块 -> 索引块 ---> 一堆索引块 -> 数据块
  |-- 三级间接块 -> ...（最多三级）
  • 直接块：指针直接指向物理数据块，小文件（几个块）全靠它，零额外开销。
  • 一级间接：指针指向一个索引块，索引块里才是真正的数据块号。
  • 二级 / 三级间接：多级索引，逐层展开，把可寻址范围推到 TB 级单文件。

ext4 默认开了 extent 特性，写法上换了一套：不再记「单个块号」，而记「从某块开始的连续多少块」这个区间。一个 extent 项能描述一整段连续空间，大文件从几千条指针压到几十条，映射逻辑等价，元数据开销小得多。所以看到 extent 就别再照 ext2 的间接块思路去算上限。

机制 用在谁身上 元数据开销 大文件表现
直接 + 一/二/三级间接块 ext2、ext3，以及关掉 extent 的 ext4 每块一条指针 文件越大索引层级越深
extent 树 默认状态的 ext4 每段连续区间一条 连续文件一条项搞定

3.4 inode 视角：拷贝、剪切与链接 #

同样是「把文件挪个位置」，底层动作完全不同。看 inode 号变不变就知道发生了什么：

操作 Inode 变化 物理数据块变化 本质
拷贝 cp 新建 inode 号 完整复制一份新数据块 两个互不相干的文件
剪切 mv 同分区 不变 不移动任何数据 只改父目录数据块里的名字映射
剪切 mv 跨分区 新建 inode 号 在新分区写一份，再删掉原块 等于「拷贝 + 删除」
硬链接 ln 共享同一个 inode 不新建块，links 计数加 1 目录里多一条指向同一 inode 的记录，计数归 0 才真正删除。不能跨分区，不能对目录做
软链接 ln -s 新建 inode 新建一块，内容为目标路径字符串 类似 Windows 快捷方式。原文件删了，重建同名文件，链接照样生效

同分区 mv 快得离谱，因为它只是改了个名字；跨分区 mv 慢得明显，因为数据真搬了一遍。这条差异解释了「为什么把文件从一个目录移到另一个目录瞬间完成，从 U 盘移到硬盘却要等」。

3.5 ext4 的关键特性与常用命令 #

特性 作用 状态
journal 元数据先写日志再落盘，掉电后重放 默认开启
extent 用区间描述块映射，压掉间接块开销 默认开启
delayed allocation 写时先占页缓存，回写时才真正分配块 默认开启
dir_index（htree） 大目录用 B 树索引目录项 默认开启
flex_bg 把多个块组的元数据集中摆放，减少寻道 默认开启
在线扩容 resize2fs 直接放大 支持
在线缩容 — 不支持，缩容必须先备份再重建

容量上限看两个数：单文件 16 TiB，单个文件系统 1 EiB。这两个是设计上限，实际受块大小和卷管理器限制，别拿它们当容量规划依据。

日常查看与维护：

bash
dumpe2fs -h /dev/nvme0n1p2       # 只看超级块信息：特性、块大小、inode 数
tune2fs -l /dev/nvme0n1p2        # 同上，另一套参数视角
tune2fs -o journal_data_writeback /dev/nvme0n1p2   # 改默认日志模式，需重挂
filefrag -v /var/log/syslog      # 看单个文件碎成了几段
e2fsck -fn /dev/nvme0n1p2        # 只检查不修改，安全
resize2fs /dev/nvme0n1p2         # 扩容，先扩分区再扩文件系统

四、XFS：大文件与高并发 #

XFS 不是为桌面设计的。它 1994 年在 SGI 的 IRIX 上落地，目标就是多 CPU、大内存、TB 级存储的服务器。2001 年移植进 Linux 2.4，之后在 RHEL 7 / CentOS 7 上一举成为默认，从此在企业环境里和 ext4 平分。

它和 ext4 最根本的差别在分配组（Allocation Group，AG）。文件系统被切成若干等大的 AG，每个 AG 有独立的空闲空间 B+ 树和 inode B+ 树。多线程并发写不同文件时，各自落在不同 AG 上，锁不打架。ext4 也有块组，但全局的空闲块管理会形成热点，核多的时候争用明显。

XFS 的设计取向可以概括成「一切用 B+ 树」：

结构 用什么索引 带来的结果
空闲空间 两个 B+ 树，分别按块号和按区段长度 大段连续分配和精确小块分配都快
inode B+ 树动态分配 不再固定 inode 数量，df -i 不会提前耗尽
目录 B+ 树，大目录自动换形态 单目录几十万文件仍然可检索
元数据 独立日志区（log section） 元数据操作不打断数据写入

对照 ext4 看差异更清楚：

维度 ext4 XFS
出身 ext2 一路演进，兼容优先 SGI 服务器文件系统移植
并发写 块组级锁，核多时有争用 AG 并行，扩展性好
大文件 extent 树，表现良好 设计目标之一，优势明显
缩容 不支持在线缩容 完全不支持，只能扩
修复工具 e2fsck，成熟，能自动修不少东西 xfs_repair，必须先卸载
备份 任何工具都能读，tar / rsync 即可 元数据特殊，xfsdump / xfsrestore 更稳
默认发行版 Debian、Ubuntu 根分区 RHEL / CentOS / Rocky / Alma
inode 数量 格式化时定死 动态分配

XFS 的硬限制要提前知道，不然出事时很被动：

  • 不能缩小。xfs_growfs 只有加，没有减。分区规划时宁可小一点后面扩，不要一上来给满。
  • 修复必须卸载。xfs_repair 不能在挂载状态下跑，-n 是只检查不写。
  • 日志区建议单独设备。高写入场景把 log 放到低延迟盘上，收益比调挂载参数明显。
  • 删大量小文件会慢。这是元数据 B+ 树的固有代价，delayed logging 已经改善了高峰期表现，但没有变成 ext4 那种水平。

常用命令：

bash
mkfs.xfs -f /dev/nvme1n1p1        # -f 强制覆盖已有文件系统
xfs_info /mnt/data                # 看 AG 数量、块大小、log 位置
xfs_growfs /mnt/data              # 扩容，先扩底层分区或 LV
xfs_repair -n /dev/nvme1n1p1      # 只检查，不写盘
xfs_fsr /mnt/data                 # 在线碎片整理

选 XFS 的判据很直接：单文件动辄几十 GB、写入并发高、不需要缩容、跑在 RHEL 系上。四条同时成立就别犹豫。

五、Btrfs：写时复制与快照 #

Btrfs 是 2007 年 Oracle 启动的项目，内核 2.6.29 合入主线，指向的是「文件系统 + 卷管理」合成一体：不再需要 LVM 那层，创建子卷等于创建逻辑分区。

核心机制是写时复制（Copy-on-Write，CoW）。改一个数据块，不是原地覆盖，而是在新位置写一份新内容，再改指针指过去。旧块保持原样，直到没有任何指针引用它才被回收。

改前：superblock -> 树根A -> 节点X -> 数据块 D1
改后：superblock -> 树根B -> 节点Y   -> 数据块 D1'
                    (树根A 与 节点X 原封不动，仍指向 D1)

好处有三层：

  1. 快照免费。拍快照只是复制一份树根指针，不是复制数据。100 GB 的目录拍快照，占用的元数据只有几 MB。
  2. 永远不撕裂。数据要么是旧的完整版本，要么是新的完整版本，不存在中间态。掉电最多丢掉最近一次提交。
  3. 可回溯。删了东西只要快照在，就能找回来。

代价也来自同一个机制：随机写会变成随机「搬」。原地小改动先复制整块再写，碎片化会累积。数据库文件、虚拟机镜像这种不停原地随机写的负载放在 Btrfs 上会明显退化，所以有 chattr +C（关闭该文件或目录的 CoW）和 norefcount 之类的开关。

能力 Btrfs ext4 靠什么做
快照 子卷 + 可写快照，瞬间完成 只能靠 LVM 快照或文件级备份
子卷 一个文件系统内多个独立子卷，可设配额 靠目录和分区划分
数据校验和 元数据 + 数据都可校验 只有元数据校验和，数据无
在线缩容 支持，先卸载调整再挂载 不支持
自愈 RAID1 下读到坏块可从另一副本重写 不支持
多设备 原生支持 RAID0/1/10/5/6 需要 mdadm 或 LVM
压缩 透明压缩 zlib / lzo / zstd 需要上层方案
成熟度 特性多，边缘场景仍有坑 十几年实战检验，最稳

日常操作：

bash
mkfs.btrfs -L data /dev/nvme2n1            # 创建
btrfs subvolume create /mnt/data/vol1      # 建子卷
btrfs subvolume snapshot /mnt/data/vol1 /mnt/data/vol1-20260101   # 快照
btrfs filesystem df /mnt/data              # 看各子卷真实占用，比 df 准
btrfs filesystem usage /mnt/data           # 带数据/元数据/系统分区的分布
btrfs scrub start /mnt/data                # 读一遍校验和，发现问题
btrfs balance start -dusage=50 /mnt/data   # 回收不均衡的空闲块

Btrfs 的持久化开销来自快照引用计数和定期 balance。跑它就要接受「需要运维」这件事：定期 scrub、定期看 filesystem usage、别让某个子卷悄悄占满整个池。

选它的场景很明确：需要快照回滚、需要数据校验和、需要多盘灵活组合、愿意定期维护。openSUSE 和 Fedora 的默认选择就是这个路线的实证。

六、FAT32、exFAT 与 NTFS：跨平台的三件套 #

这三个是 Windows 世界的产物，但在 Linux 上天天要打交道。U 盘、SD 卡、移动硬盘、双系统共用分区，绕不开它们。

6.1 FAT32 的单文件上限 #

FAT32 用 32 位字段记录文件长度，上限是 4,294,967,295 字节，约 4 GiB。单个文件超过这个大小就写不进去，哪怕盘上还剩很多空间。

这个 4 GiB 不是随手定的，它来自目录项里那 4 个字节的「文件大小」字段。数一下就知道：2^32 - 1 字节。卷容量上限 2 TiB（簇大小 512 字节到 32 KiB），单目录文件数也有实际限制。

还有一个不太被提到的坑：FAT32 不支持日志，拔盘拔早了就是文件系统层面的一致性事故，只能靠 fsck.fat 扫。

6.2 exFAT：为大容量闪存补位 #

exFAT 是微软 2006 年随 Windows CE 6.0 推出的，Vista SP1 起进入桌面 Windows。它的定位很清楚：给闪存用，去掉 FAT32 的容量限制，又不想背上 NTFS 的日志开销。

  • 单文件上限 16 EiB（实际受卷容量限制），彻底解决 4 GiB 问题。
  • 卷容量上限远超 FAT32，大容量 SD 卡和移动硬盘都能用。
  • 结构简单，元数据开销小，闪存设备上写入放大比 NTFS 小。
  • 跨平台：Windows 原生支持，macOS 原生读写，Linux 从内核 5.7 起有原生驱动，之前靠 exfat-fuse。
  • 缺少日志和权限模型，不适合做系统盘，也不适合放需要 ACL 的数据。

6.3 NTFS：Windows 的完整方案 #

NTFS 从 Windows NT 3.1（1993）起就是默认。它是三个里唯一具备完整企业级能力的：

能力 FAT32 exFAT NTFS
单文件上限 4 GiB 16 EiB（受卷限制） 16 EiB（受卷限制）
日志 无 无 $LogFile，元数据日志
权限 / ACL 无 无 完整 ACL
压缩与加密 无 无 压缩、EFS 加密
硬链接 / 符号链接 无 无 都支持
快照 无 无 VSS 卷影副本
稀疏文件 无 无 支持
Linux 读写 原生驱动 5.7 起原生，之前 FUSE 5.15 起原生 ntfs3，之前 ntfs-3g
掉电恢复 靠 fsck 靠 fsck 日志重放

NTFS 在 Linux 上的历史值得记一笔。ntfs-3g 是 FUSE 实现，能用但每次操作多两层上下文切换；内核 5.15 起合入的 ntfs3 是 Paragon 贡献的原生驱动，走块层，读写和挂载行为都更接近本地文件系统。挂载时 mount -t ntfs3 和 mount -t ntfs-3g 是两套东西，排错时别搞混。

一个实操提醒：快速启动（Fast Startup）开着的时候，Windows 关机其实没真正卸载 NTFS 卷，Linux 侧挂载会看到脏标记而转成只读。要么关掉快速启动，要么在 Windows 里彻底关机（shutdown /s /f /t 0，不是「重启」）。

6.4 怎么选 #

场景 选择 理由

6.5 在 Windows 里换文件系统 #

FAT32 → exFAT：格式化，清空数据。

格式化会抹掉盘上所有内容，先备份。

  1. 打开「文件资源管理器」。
  2. 右键目标驱动器 →「格式化」。
  3. 文件系统选 exFAT。
  4. 点「开始」。

注意：Windows 自带的格式化对话框对 FAT32 的卷大小有限制，超过 32 GB 的卷不给格成 FAT32。要格大容量 FAT32 得上第三方工具。

FAT32 → NTFS：原地转换，保留数据。

不用格式化，convert 是原地转换：

bat
convert X: /fs:ntfs

X: 换成实际驱动器号。仍然建议先备份，转换中途掉电的后果比格式化更难收拾。convert 只能从 FAT/FAT32 往 NTFS 走，反向不行，NTFS 转回去只能格式化。

Linux 侧对应的命令：

bash
mkfs.exfat -n DATA /dev/sdb1        # 格成 exFAT，需要 exfatprogs
mkfs.vfat -F 32 -n DATA /dev/sdb1   # 格成 FAT32
mkfs.ntfs -f -L DATA /dev/sdb1      # 格成 NTFS，需要 ntfs-3g 包
mkfs.ext4 -L data /dev/sdb1         # 格成 ext4
wipefs -a /dev/sdb1                 # 清掉旧文件系统签名，格之前最稳

七、怎么选：一张决策表 #

先按介质和用途分叉，再看是否需要特殊能力。

问题 答案 结论
这块盘是系统盘吗 是，Linux ext4；要快照选 Btrfs；要大文件吞吐选 XFS
是，Windows NTFS
否 往下
需要在 Windows / macOS / Linux 间插拔 是，且文件会超过 4 GiB exFAT
是，且只放小文件、要兼容老设备 FAT32
否，只在 Linux 用 ext4 或 XFS
需要快照、校验和、多盘组合 是 Btrfs
需要缩容 是 ext4（离线）或 Btrfs（在线）；XFS 直接排除
单文件动辄几十 GB、写并发高 是 XFS
跑在 RHEL / CentOS / Rocky 上 是 XFS 更贴合发行版默认工具链

再加几条实战经验，来自踩坑而不是文档：

  • U 盘别用 NTFS。日志和权限模型在闪存上没有收益，拔盘不干净时反而更难恢复。
  • SD 卡给相机用就 FAT32。老相机只认它。
  • 移动硬盘跨平台用 exFAT，纯 Linux 用 ext4。不要为了「万一要插 Windows」而牺牲掉 ext4 的全部特性。
  • XFS 的分区不要一开始就给满。它只能扩不能缩，留 10% 到 20% 余量。
  • Btrfs 别关 scrub。校验和是它的核心价值，不跑 scrub 等于没用上。
  • ext4 空间长期占 95% 以上时，碎片会爆发。ext4 靠「预留与分散」策略：分配时把文件散落在整个分区，每个文件周围留自由空间，文件变大能原地扩。空间吃紧时这个策略失效，碎片不可避免。这时看 filefrag -v 的分段数，或者直接换更大容量的盘。

关于碎片，Windows 和 Linux 的机制差异值得单独说清：

机制 行为 后果
Windows（FAT / NTFS） 文件紧凑排列，一个紧贴下一个 初期省空间；文件变大时后面没地方，只能把溢出部分塞到远处空闲块，碎片累积，需要定期整理
Linux（ext4） 预留与分散，文件间留白 文件变大能原地扩；偶然碎片由后台在日常使用中慢慢整理

机械盘时代这条差异影响巨大：磁头寻道耗时远超顺序读，随机读写比顺序读写差一个数量级。SSD 上寻道成本消失，碎片的影响主要退化为元数据开销和预读效率，所以 fstrim 比碎片整理重要得多。

八、一次 write 调用走过的七层 #

回到主线。前面讲的是「有哪些类型、怎么选」，现在讲「一次写到底经过什么」。

Linux 内核把文件子系统拆成多层软件抽象，目的只有一个：让上层不用关心底下是 HDD、SATA SSD 还是 NVMe。从上到下七层：

+---------------------------------------------------------------+
|  用户空间层 (User Space)                                       |
|  应用调用 write() / pwrite() / writev()                        |
+---------------------------------------------------------------+
                          | System Call
+---------------------------------------------------------------+
|  虚拟文件系统层 (VFS)                                          |
|  统一抽象层，把调用分派到具体文件系统注册的操作函数指针           |
+---------------------------------------------------------------+
                          |
+---------------------------------------------------------------+
|  具体文件系统层 (ext4 / XFS / Btrfs ...)                       |
|  文件逻辑偏移 -> 物理 LBA 的转换，管理块分配与元数据             |
+---------------------------------------------------------------+
                          |
+---------------------------------------------------------------+
|  缓存层 (Page Cache)                                           |
|  以物理页为单位缓存读写数据，脏页异步回写                        |
+---------------------------------------------------------------+
                          | bio 请求
+---------------------------------------------------------------+
|  块设备层 (Block Device)                                       |
|  bio 合并、I/O 调度排序，把零散请求整理成连续请求                |
+---------------------------------------------------------------+
                          | SCSI / ATA / NVMe 命令
+---------------------------------------------------------------+
|  磁盘驱动层 (Device Driver)                                    |
|  把块请求翻译成控制器认识的协议命令                              |
+---------------------------------------------------------------+
                          |
+---------------------------------------------------------------+
|  物理介质层 (Physical Disk / Flash)                            |
|  磁头寻道读写扇区，或对 Flash 页编程                            |
+---------------------------------------------------------------+

逐层职责：

层 输入 做的事 输出
用户空间 write(fd, buf, 4096) 准备缓冲区，触发系统调用 陷入内核
VFS 文件描述符 + 偏移 fd 查 struct file，取 f_op，调用 ->write_iter 转交具体实现
具体文件系统 inode + 偏移 + 长度 定位逻辑块，分配新块，更新 extent / 位图 bio 或页面标记
页缓存 页号 + 数据 拷贝用户数据进页，标记脏页 脏页候选
块设备层 struct bio 合并相邻 bio，按调度器排序 struct request
驱动层 request 转成 SCSI / ATA / NVMe 命令，写寄存器或提交队列 硬件命令
物理层 电信号 磁介质翻转或 Flash 单元编程 数据落地

这七层是逻辑分层，不是七个独立进程。一次 write 的系统调用开销主要在前两层（陷入内核加 VFS 分派），数据真正落地的时间由后面几层决定，而且经常不在这次调用里完成，因为写走的是缓存。

一个容易搞错的点：七层里的「缓存层」在物理位置上不在文件系统之下。页缓存是内存里的一张 radix tree（新内核换成 xarray），由文件系统通过 address_space 操作挂进自己的 inode。所以画成「文件系统 → 缓存 → 块层」是数据流向，不是调用栈。

九、VFS：屏蔽差异的抽象层 #

如果没有 VFS，write() 就得这么写：if ext4 then ... else if xfs then ... else if nfs then ...。每加一个文件系统，所有系统调用都要改一遍。VFS 把这件事收成一张函数指针表。

四个核心对象，记住它们的关系就抓住了 VFS：

对象 结构体 代表什么 生命周期
超级块 struct super_block 一个已挂载的文件系统实例 挂载时创建，卸载时销毁
inode struct inode 一个文件在磁盘上的元数据在内存里的副本 首次访问时读入，无引用后可回收
dentry struct dentry 路径中的一个名字节点 随路径解析创建，进 dcache 后长期缓存
file struct file 一次打开的文件，含偏移与标志 open 时创建，close 时释放

关系是：task_struct 里的 files_struct 指向 fd 表，fd 表项指向 struct file，file 指向 dentry，dentry 指向 inode，inode 指回 super_block。

进程
 └── files_struct
      └── fd 数组 [0,1,2,3,...]
           └── struct file  (偏移 f_pos、标志 f_flags)
                ├── f_op ──> 函数指针表（ext4 / xfs / nfs 各自注册）
                └── f_path
                     └── struct dentry（名字 + 父目录）
                          └── struct inode（权限、大小、时间、块映射）
                               └── struct super_block（该文件系统的全局信息）

每次系统调用进来的动作都一样：fd 拿 struct file，file->f_op 拿操作表，调用对应的 write_iter。VFS 不关心底下的文件系统怎么摆数据，它只要求你实现这套接口。

所有文件系统对内核对外的注册入口是 register_filesystem()，把 struct file_system_type 挂进一条全局链表。这就是 /proc/filesystems 的内容来源。

这套抽象的后果，就是 Unix「一切皆文件」：字符设备、块设备、管道、socket、procfs 里的一个数字，都能用 open/read/write/close 操作。差异被压到 f_op 后面，应用层看到的都是文件描述符。

有一类差异 VFS 压不住，需要单独说：目录项缓存（dcache）。路径解析每次都要查 name → dentry，如果每次都从磁盘读目录块，性能没法看。所以 dentry 查过一次就留在缓存里，命中时整个解析在内存完成。这也是为什么 ls 一个刚访问过的目录，比冷启动时快得多。

bash
cat /proc/sys/fs/dentry-state     # 看 dcache 的条目数和未使用数
cat /proc/sys/fs/inode-state      # 看内存中 inode 的数量
cat /proc/slabinfo | grep -E 'dentry|inode_cache'   # slab 层面的占用

跨篇一句：fd 的分配、dup、fcntl 那套，在《文件 IO 与描述符管理》里，这里只讲它在 VFS 里的位置。

十、页缓存与回写 #

write() 返回成功，不代表数据到了磁盘。默认情况下它只到了页缓存。

write() --> 拷贝用户数据进页缓存 --> 标记脏页 --> 返回 0
                                     |
                          后台回写线程（周期性 / 内存压力）
                                     |
                            生成 bio --> 块层 --> 设备

这条链路带来两个直接后果：

  • 吞吐高。多次小写会在页缓存里合并成一次大写入，随机写被重排成顺序写。
  • 掉电丢数据。返回成功到真正落盘之间有一个窗口，窗口内断电，这部分数据就没了。

脏页什么时候回写，由几个参数控制：

参数 默认量级 作用
vm.dirty_ratio 20% 脏页占总内存超过这个比例，写进程自己被阻塞，同步回写
vm.dirty_background_ratio 10% 超过这个比例，后台回写线程开始干活，写进程不受影响
vm.dirty_expire_centisecs 3000 脏页存活超过 30 秒，下一轮回写必须带走它
vm.dirty_writeback_centisecs 500 回写线程多久醒一次，5 秒
vm.dirty_bytes / dirty_background_bytes 0 设了字节数就覆盖上面的比例，大内存机器建议用这个 
bash
sysctl vm.dirty_ratio vm.dirty_background_ratio
cat /proc/meminfo | grep -i dirty      # Dirty 是当前脏页量，Writeback 是正在写的量
cat /proc/vmstat | grep -E 'nr_dirty|nr_writeback'
sync                                    # 全系统脏页刷盘，慢但彻底
sync -f /var/log/syslog                 # 只刷某个文件所在的文件系统

应用层要保证数据落地，得自己调：

c
#include <fcntl.h>
#include <unistd.h>

int fd = open("/var/log/app.log", O_WRONLY | O_APPEND);
write(fd, buf, len);

fsync(fd);      /* 数据 + 元数据都落盘，最重的选择 */
fdatasync(fd);  /* 只保证数据落盘，元数据（大小/时间）延后再刷，快一些 */

fsync 和 fdatasync 的差别在文件大小变化时才明显：追加写入时 fsync 还要额外同步 inode 里的 size 字段，fdatasync 能省掉这次 I/O。真正的数据库会自己管这套，用 WAL 加批量 fsync，不是每条记录一个 fsync。

mmap 共享映射也走页缓存，改内存就是改页缓存里的页，同样要 msync 才算落地。只读映射不产生脏页。

一个实战结论：大量小文件写入时，瓶颈常常在回写而不是写入。写进程被 dirty_ratio 卡住的瞬间，应用看到的是「突然变慢」，实际是回写队列满了。

十一、IO 调度与块层 #

到了块层，请求已经是 struct bio 的形式：描述「从哪个设备的哪个扇区读/写多少字节」，可以带多个区段。

块层做三件事：

  1. 合并。相邻扇区的两个 bio 合成一个 request，减少设备命令数。
  2. 排序。按 LBA 排序，把随机请求整理成接近顺序的访问。
  3. 调度。决定下一个发给设备的是哪个 request。

机械盘靠排序收益巨大，因为省掉的是物理寻道。SSD 没有寻道，但仍有队列深度和垃圾回收的问题，所以调度器的选择不一样。

调度器 适合 行为
none NVMe、高性能 SSD 不排序，直接下发，把决策交给设备
mq-deadline 通用块设备 给每个请求设截止时间，防止饿死
bfq 桌面、机械盘、需要公平性 按 cgroup 做带宽分配，交互响应好
kyber 快速设备 按读/写两个队列做延迟目标控制 
bash
cat /sys/block/nvme0n1/queue/scheduler        # 当前可用与生效的调度器，[] 里是生效的
echo none > /sys/block/nvme0n1/queue/scheduler
cat /sys/block/nvme0n1/queue/nr_requests      # 队列深度
lsblk -t                                       # 顺带看调度器、rotational、discard 支持

现代内核默认走 blk-mq（多队列块层），每个 CPU 核有自己的软件队列，硬件队列按设备能力分配。老的单队列电梯算法（CFQ、Deadline、NOOP）在 5.0 前后被逐步移除，现在看到的是 mq-deadline 这类多队列版本。所以拿十年前的调优文章照抄 echo cfq 会失败，不是权限问题，是那个文件不存在了。

固态盘上比调度器更值得关注的是 discard：

bash
fstrim -av                    # 手动 TRIM，把所有未用块告诉设备
systemctl enable fstrim.timer # 周期性 TRIM，比挂载时开 discard 更稳

挂载选项里的 discard 是每删一个文件就发一次 TRIM，小文件删除密集时会拖慢；周期性 fstrim 批量做更划算。

十二、直接 IO 与缓冲 IO #

默认是缓冲 IO：数据过页缓存。另一条路是 O_DIRECT，让 I/O 绕过页缓存，应用自己的缓冲区直接和设备对话。

维度 缓冲 IO 直接 IO O_DIRECT
是否过页缓存 是 否
内存占用 占用页缓存，可被回收 用应用自己的缓冲区
对齐要求 无 缓冲区地址、偏移、长度都要按块大小对齐
小写入 页缓存里合并，表现好 每次都是真实设备 I/O，慢
大顺序写 好 好，且不污染页缓存
数据可见性 write 返回不代表落盘 返回时数据已交给设备
典型使用者 绝大多数应用 数据库、自建缓存、虚拟化镜像

O_DIRECT 的对齐坑是新手最容易踩的：缓冲区地址、文件偏移、写入长度三个都要是逻辑块大小（一般是 512 或 4096）的整数倍，否则 write 直接返回 EINVAL。不是「数据写歪了」，是压根不让写。

c
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdlib.h>
#include <unistd.h>

int main(void)
{
    int fd = open("/mnt/data/blob", O_WRONLY | O_CREAT | O_DIRECT, 0644);
    size_t len = 4096;
    void *buf;

    /* posix_memalign 保证地址按 4096 对齐 */
    if (posix_memalign(&buf, 4096, len) != 0)
        return 1;

    ssize_t n = pwrite(fd, buf, len, 0);   /* 偏移 0，长度 4096，都对齐 */
    if (n != (ssize_t)len)
        return 1;

    close(fd);
    free(buf);
    return 0;
}

还有一个常被忽略的选项是 O_SYNC / O_DSYNC：不绕过页缓存，但每次 write 返回前把数据刷到设备。它把「缓存」和「持久化」两件事解耦得最差，每次写都等一次设备确认，吞吐掉得厉害，只在写日志这类场景用。

三条路线对比：

写法 过页缓存 返回即落盘 适合
write 是 否 默认选择，绝大多数场景
write + fsync 是 是（显式调用时） 需要持久化点，但允许批量
O_DIRECT 否 否（但已交给设备） 自己有缓存管理，不想双重缓存
O_SYNC 是 是 写审计日志这类不能丢的少量写

O_DIRECT 不是性能银弹。它省掉一次内存拷贝和页缓存占用，但失去了合并与预读。数据库用它是因为自己已经有一层 buffer pool，再过一遍页缓存就是双份内存；普通应用用它，多半是负优化。

十三、文件系统的一致性：journal 与 fsck #

写一个文件要改好几处：数据块、inode 的大小和时间、块位图、目录项。这几处不是一次原子操作能完成的，中途掉电就会出现「元数据说文件有 10 MB，实际只写了 4 MB」这种状态。文件系统对付这件事有两条路线。

路线一：日志（journaling）。 改元数据之前，先把「要改什么」写进日志区，日志落盘后再改真正的位置。掉电重启时重放日志，把没完成的改成完成，或者整体丢弃。

ext4 用 JBD2 做日志，有三种模式：

模式 记录什么 数据安全 性能 挂载写法
journal 元数据 + 数据都先进日志 最高 最差，数据写两遍 data=journal
ordered 只记元数据，但保证数据先于元数据落盘 高，不会出现指向垃圾数据的元数据 默认，均衡 data=ordered
writeback 只记元数据，数据顺序不保证 崩溃后读到旧数据块内容 最好 data=writeback

ordered 是绝大多数发行版的默认，它保证「元数据不会指向还没写的数据块」，代价是数据要先落盘。writeback 快，但崩溃后文件里混着别人的旧数据，安全敏感场景别用。

路线二：写时复制（CoW）。 Btrfs 和 ZFS 走这条。新数据写到新块，指针更新是一次原子提交。没有日志重放这回事，因为任何时刻磁盘上的树都是一致的。代价是随机写要复制整块，以及需要定期回收旧块。

XFS 用的是元数据日志，思路和 ext4 的 ordered 接近，日志区可以单独放在低延迟设备上。

出问题之后的检查工具：

bash
e2fsck -fn /dev/nvme0n1p2       # ext4，只检查不修改
e2fsck -p /dev/nvme0n1p2        # 自动修复能安全修的部分，开机脚本用的就是这个
fsck -N                        # 只打印将要执行什么，不真跑
xfs_repair -n /dev/nvme1n1p1    # XFS，必须先卸载
btrfs check --readonly /dev/nvme2n1   # Btrfs，只读检查
fsck.fat -n /dev/sdb1           # FAT32

几条纪律：

  • 检查必须卸载。挂载状态下跑 e2fsck 会破坏数据，不是警告，是直接毁。
  • 根分区要检查，得从救援模式或 Live 环境进去。
  • e2fsck -y 无脑修有风险，先 -n 看报告，再决定。
  • 修复后异常文件会被丢进分区根目录的 lost+found，用 inode 号命名。
  • /etc/fstab 最后一列的 pass 值决定开机检查顺序：根分区 1，其他 2，不检查写 0。大容量盘设 0 能省开机时间。

掉电测试能暴露不少问题，但别在生产盘上做。要验证持久化行为，写个小程序循环「写 + fsync + 立刻断电重启」，看恢复后文件是否完整，这比读文档有用。

十四、易错点速查 #

U 盘拷 8 GB 电影失败，盘上明明有 60 GB 空 盘是 FAT32，单文件上限 4 GiB 备份后格成 exFAT，或 convert 到 NTFS
write 返回成功，掉电后文件末尾是空的 数据停在页缓存，没 fsync 关键写入后显式 fsync / fdatasync
O_DIRECT 的 write 报 EINVAL 缓冲区地址、偏移或长度没按块大小对齐 用 posix_memalign 对齐，长度取 4096 倍数

双系统时间差 8 小时 Windows 按本地时间写 RTC，Linux 按 UTC timedatectl set-local-rtc 1，或让 Windows 改用 UTC

最后一条经验：排查文件系统问题，先确认三件事。这块盘是什么文件系统（findmnt -T），它挂载时带了什么选项（/proc/mounts），错误信息是元数据层面的还是数据层面的（dmesg -T | grep -i -E 'ext4|xfs|btrfs|i/o error'）。这三条定了，方向基本也就有了。剩下的是经验和耐心。
