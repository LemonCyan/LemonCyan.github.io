一、为什么需要文件系统 #

一块新硬盘插上机器，dd if=/dev/zero of=/dev/sdb 跑完，它就是 2TB 连续不断的数据块，偏移 0 到偏移 2199023255552，每个位置都能读写。仅此而已。

这东西没法直接用。问题不在容量，在它没有名字。程序要读「上一次的日志」，它能拿到的是一个数字——偏移量。偏移量从哪来？只能由人在外面记着。整块盘就是一个巨型数组，索引表写在你脑子里。

硬件还在下面加了两道约束。第一，读写的最小单位是扇区，512 字节或 4K 字节，你没法只改一个字节，得把整块读出来、改完、写回去。第二，写到一半掉电，那块数据就是垃圾，没人知道它属于谁。这两道约束不能推给应用层，让每个程序自己处理扇区对齐和掉电恢复，那是灾难。

所以文件系统要替上层包掉三件事：

问题 文件系统给的答案
这东西叫什么 目录项里的文件名，拼成路径串
数据在哪 inode 里的块指针，落成扇区号
谁能动它 inode 里的 uid/gid 和九个权限位

这三个答案凑齐，一块裸盘才变成「能放东西的地方」。少了任何一个，上层都得自己记账。

再往下推一步。为什么机器上要装好几种文件系统？ext4、XFS、Btrfs、FAT32、NTFS、NFS、tmpfs、proc，/proc/filesystems 一列就是几十行。原因很简单：介质和需求不一样。闪存怕擦写次数，要磨损均衡；U 盘要插到 Windows 上也能读，只能 FAT；网络盘根本没有本地块设备，靠协议传；/proc 底下压根没有存储。每种场景的取舍不同，就只能各写一套。

这一堆东西对上层必须长成同一个样子，不然 cp 命令要写八个分支。Linux 的做法是在中间插一层 VFS，把「文件、目录、inode、挂载点」这几个概念抽象出来，每种实际的文件系统去实现 VFS 开出来的接口。VFS 怎么组织这张表，是《文件系统类型与 IO 路径》那篇的活，这里只记住一点：你在命令行看到的树，是 VFS 给你的视图，跟底下是哪块盘、哪种格式没关系。

二、从裸存储到文件系统的演进 #

光讲概念容易飘。我们把整个演进走一遍，设定很荒诞：把全套《盗墓笔记》八本塞进一块硬盘，需求一步步加码，看每次加码会逼出什么东西。

第一版最省事。一个字一个字顺序写进去，全书连续占一段空间。要跳读某一章，就记下「从这里到那一章跳过了多少字节」，下次直接定位过去。这个记录字节偏移的载体，可以理解成一张小纸条。

小纸条很快就顶不住了。要记的位置越来越多：最后一章在哪、某个词第一次出现在哪、上次读到哪。记的东西一多，就开始记不清哪条记过哪条没记。终于有一天纸条丢了，整本书瞬间变回一坨连续的字符。顺序存储到此为止，需求变成：我要管理这些内容。

第二版开始分区。八本书，每本固定 100MB，全套 800MB。想看第七本，从 600MB 偏移开始读就行，书名和偏移量的换算固定下来了。

第三版继续细分。每本书 50 章，每章 2MB，按 2MB 对齐。要第 6 本书第 30 章，偏移是 (500 + 29 * 2) MB。到这一步，查找完全靠算术，不再依赖任何外部记录。

然后墙来了。这块盘不是你的，800MB 被砍到 8MB。原来每章还能分 20KB，现在一章 20KB 都不够，内容多的章越界，内容少的章浪费。空间变成了最贵的东西，只能重新设计。

第四版把「小纸条」搬回硬盘。既然顺序存储最省空间，那就把索引也塞进盘里。把章节抽象成一个结构体，成员是章节名、章节起始位置、章节字数，每个对象 64 字节对齐。400 章算下来 25KB，全部放在 8MB 的最前面 32KB，后面剩余空间照旧顺序存内容。

这套设计离文件系统已经很近了，只是当时没这个自觉。

第五版被逼着放弃连续。通知下来了：要么继续用连续空间但只有 4MB，要么接受不连续但总量还是 8MB。每块最小 2048 字节，且按 2048 字节对齐。八本书不能丢一半，只能走不连续。

不连续的第一件事是给每块配身份。每条索引记录四样东西：这块在硬盘上的偏移、这块的长度、这块属于哪本书、这块内容在书内的偏移。最早还想直接用书名，一试就废——名字长了存不下，短了浪费空间。既然书只有八本，存个 1 到 8 的编号就够了。

第二件事是索引本身也要找得到。每条索引 12 字节，一个 2048 字节的块能塞 170 条，那就专门拿一个块存索引。一个索引块最多映射 170 * 2048 字节，也就是 340KB，八本书远不止这么点，得有更多索引块。

第三件事是索引块之间要串起来。170 条索引只用掉 2040 字节，一个块白白浪费 8 字节。把这 8 字节拿去存下一个索引块的偏移，索引块就串成了链表。

第四件事是得有个固定的链头。不然链表再漂亮也找不到入口。最后谈下来，硬盘第 1024 个数据块归你用，它成了串起全书的那个入口。

六个阶段排在一起看：

阶段 关键设计 撞上的墙 长出的部件
顺序存储 整本连续写，记字节偏移 偏移记录越攒越多，丢了就全废 块指针的雏形
固定分区 每本固定 100MB，靠偏移换算 空间利用率极低 分区、块组
按章切块 每章 2MB 对齐，偏移可算 总空间被砍到 8MB 块与块大小对齐
索引块 章节结构体 64 字节，索引堆在前 32KB 索引对象本身找不到 inode 结构体、inode 表
索引串联 多余的 8 字节存下一索引块偏移 链头在哪 间接块指针、多级索引
固定入口 第 1024 块作为入口 — 超级块

把演进产物和真实文件系统的部件对一下，会发现几乎一一对应：

演进产物 真实文件系统里的部件
每本书固定 100MB 的切分 分区、块组（block group）
每章 2MB 对齐 块（block）与块大小
记录偏移的那张小纸条 inode 里的块指针
章节结构体（名称/起始/字数，64 字节对齐） inode 结构体本身
把全部结构体堆在开头 32KB inode 表（inode table）
每颗星加索引信息 数据块 + 块指针
串起索引块的那 8 字节 间接块指针，多级索引
第 1024 个数据块 超级块（superblock）

这一路走下来有三条经验值得说死。空间越紧，元数据越值钱，从「整本连续、位置靠算」到「花 25KB 存索引」，本质是拿空间换查找效率，真实文件系统里 inode 表占的空间不小，就是这个交易的产物。定长对齐是能算出来的前提，定长才能用乘法和取模定位，不用遍历。不连续之后必须有人记「下一块在哪」，这就是指针；指针多了必须有人记「第一个在哪」，这就是入口。

还剩一个洞没补。上面所有设计解决的都是「我知道内容在哪」，没解决「我怎么按名字找到它」。真实文件系统里这一环由目录项补上，目录本身也是一堆数据块，里面存的就是「文件名 → inode 号」。下一节把这个链条正式串一遍。

三、文件系统抽象了什么 #

一个文件在正统的 Linux 文件系统（ext2/ext3/ext4 这一系）里由三样东西组成：目录项、inode、数据块。

部件 存什么 放在哪
目录项 文件名 + inode 号 父目录自己的数据块里
inode 文件类型、权限、属主、大小、时间戳、链接数、块指针 inode 表
数据块 文件的真实内容 数据区

目录项特别短：一个名字，一个数字。它不存大小、不存权限、不存内容，只负责「名字 → inode 号」这一次跳跃。

inode 则相反，文件的全部属性都在这里，外加一组指向数据块的指针。stat filename 打出来的东西，基本就是把 inode 的结构体摊开给你看。

数据块里才是内容。文本也好、二进制也好、别的目录也好，在文件系统眼里都是数据块。

把一次路径解析拆开，这三者的关系就清楚了：

text
读取 /etc/hosts
  1. 从根目录的 inode 出发，读它的数据块，在里面找名字 "etc"
     → 得到 /etc 的 inode 号
  2. 读 /etc 的 inode，拿到它的数据块，在里面找名字 "hosts"
     → 得到 hosts 的 inode 号
  3. 读 hosts 的 inode，拿到类型、权限、大小、块指针
  4. 顺着块指针把数据块读出来，拼成文件内容

整个过程是「按名字查表，跳到 inode，再按名字查表」，一层一层往下，直到落到一个不是目录的东西上。

inode 里到底装了什么，stat 的默认输出已经覆盖大半：

字段 stat 里的样子 说明
类型与权限 Access: (0644/-rw-r--r--) 十二位，含 setuid/setgid/sticky
链接计数 Links: 2 有多少目录项指向它
属主 / 属组 Uid: ( 1000/ alice) 数字和名字都给
大小 Size: 6 字节数
时间戳 Access、Modify、Change、Birth 访问、内容改、元数据改、创建
块数与 IO 块 Blocks: 8、IO Block: 4096 实际占的 512 字节块数
inode 号 Inode: 1310722 在本文件系统内唯一
块指针 不显示 直接、一级、二级、三级间接

Links 这个字段是后面第九、十节的枢纽，先记住它跟文件大小无关，只跟「有几个名字」有关。

路径解析的开销值得一提。上面那四步，每一层目录都要读一次目录的 inode、再读一次它自己的数据块。/usr/share/man/man1/ls.1.gz 有六级，就是十几次随机读。所以内核给每个目录项做了 dentry 缓存，把「父目录 + 名字」到 inode 的映射记在内存里，解析同一条路径第二次就快得多。/proc/sys/fs/dentry-state 里能看到这份缓存的规模。缓存失效的时机是文件被改名、被删除、被挂载覆盖——这也解释了一个老问题：为什么在别的机器上改完 NFS 上的文件，本机 ls 看到的还是旧的，echo 3 > /proc/sys/vm/drop_caches 才刷新。

这里有个必须记住的结论：文件名不存在 inode 里，只存在目录项里。inode 从头到尾不知道自己的任何一个名字。这条性质看着不起眼，却是硬链接能成立的唯一原因——同一个 inode 可以被多个目录项指向，每个名字都只是「某个目录里的一条记录」。第十节会把它用到底。

格式化这块盘的时候，文件系统在分区上划出几块区域：超级块、inode 表、数据块区，还有块位图和 inode 位图这类记录「谁被占了」的表。原始素材里常把目录单独说成一块区域，其实目录就是数据块，只是里面的内容被格式化成了一张「名字 → inode 号」的表。ext4 相比 ext2/ext3 在布局上有很多细节差别，inode 的结构也变过，但这三层的分工从来没变。

四、Linux 的单一根目录树 #

Windows 的文件结构是多个并列的树，每棵树的顶是一个分区，名字叫盘符：C:、D:、E:。往 D: 里拷东西，你心里默认知道那是另一块盘。

Linux 不是。Linux 只有一棵树，根是 /，所有存储设备都是挂到这棵树某个点上的枝，而不是各自长成一棵新树。

磁盘插上来，分区、格式化，然后必须挂到某个已经存在的目录上才能读写。这个目录叫挂载点。挂上去之后，原来那个目录里藏着的空内容被设备的根目录顶替，你 cd 进去看到的就是那块盘。umount 之后，原来的内容又露出来。注意是遮住，不是删掉——挂载点里原有的文件一个都没少，只是暂时看不见。

目录和分区的关系，四条能说清：

  • 任何分区都必须挂到某个目录上。
  • 目录是逻辑上的区分，分区是物理上的区分。两者不是一一对应。
  • 分区只有挂到目录树上的某个具体目录，才能被读写。
  • 根目录也是目录，也必须挂一个分区。这个分区叫根分区。

一块盘可以挂到多个目录（bind mount），一个目录也只能同时挂一个东西。所以「分区几分之几在哪儿」这件事，光看 df 是看不全的，lsblk 和 findmnt 才看得到树的形状。

bash
$ lsblk
NAME        MAJ:MIN RM   SIZE RO TYPE MOUNTPOINTS
nvme0n1     259:0    0 476.9G  0 disk
├─nvme0n1p1 259:1    0   512M  0 part /boot/efi
├─nvme0n1p2 259:2    0   100G  0 part /
└─nvme0n1p3 259:3    0 376.4G  0 part /home

看第三列的挂载点，三块分区、三个目录，全在同一棵树里。没有 C: 也没有 D:，只有 /、/boot/efi、/home。

再把两个体系放在一起对：

概念 Windows Linux
顶层 多个盘符并列，C: D: 唯一的 /
文件系统的根 每个分区一个根 全系统一个根
新设备怎么接入 自动分配一个盘符 挂到已有的某个目录
路径含义 带机器拓扑，D:\data 依赖盘符分配 与设备无关，/var/log 在任何机器上都指同一处
目录与分区 无固定关系 目录是逻辑划分，分区是物理划分

差异的根子在路径是程序之间传的字符串。/etc/passwd 这个字符串，在笔记本上、在机房里、在容器里、在 NFS 客户端上，含义完全一致，不管 /etc 落在哪块盘、本地还是网络。盘符一进来，路径就绑上了机器拓扑，程序就没法写死任何路径了。

开机的时候这棵树是这么搭起来的：引导器通过内核参数把根分区告诉内核，内核挂上 /，然后按 /etc/fstab 把剩下的分区逐个挂上去。fstab 里写的是 UUID 而不是 /dev/sda1，因为设备名会随插拔顺序变，UUID 不会。

text
UUID=cb1934d0-4b72-4bbf-9fad-885d2a8eeeb1   /              ext4    relatime,errors=remount-ro   0      1
UUID=c40f813b-bb0e-463e-aa85-5092a17c9b94   /home          ext4    relatime                     0      2
UUID=0f918e7e-721a-41c6-af82-f92352a568af   /work          ext4    relatime                     0      2
UUID=2f8bdd05-6f8e-4a6b-b166-12bb52591a1f   none           swap    sw                           0      0
proc                                        /proc          proc    defaults                     0      0

最后一行是伪文件系统，没有对应设备，第八节单独讲。

手动接一个新设备也是同一个动作：先分区，再格式化，然后 mount /dev/sdb1 /mnt/data。想让它开机就在，把这一行写进 fstab。分区和格式化的具体工具链，看《分区、挂载与磁盘工具》，这里只保证你知道挂载是「把设备接到树上的一个目录」这个动作。

这棵树还可以不止一份。Linux 有挂载命名空间，每个命名空间看到的挂载点集合不一样。容器用的就是这个：进程在容器里 ls /，看到的是镜像里的那棵树，跟宿主机无关。挂载还能叠加：同一目录先挂 A 再挂 B，看到的是 B，umount 一次露 A。排查「明明挂上了却看不到文件」，这两条是头号元凶。

五、FHS 标准：目录该怎么摆 #

树长出来了，接下来得回答：根下面该有哪些目录，各自该放什么。

这件事有标准，叫 FHS，Filesystem Hierarchy Standard。它规定根目录下每个目录的名字和职能，也规定 /usr、/var 里面的子目录布局。

为什么需要这个东西？因为脚本要跨发行版跑。Debian、Ubuntu、CentOS、Rocky、Alpine 的包管理器不同、服务管理工具不同，但目录布局是锁死的。你写的部署脚本敢写 cp app /usr/local/bin/，靠的就是这个约定。发行版之间的差别，集中在包管理器和少数系统管理工具上，目录结构基本一致。

FHS 的价值不在那张目录清单，在它判断「某个东西该放哪」用的两条坐标轴：

静态内容 可变内容
可共享 /usr、/opt /home、/srv、/var/mail
不可共享 /etc、/boot /var、/run、/tmp

「可共享」的意思是这份内容对多台机器都一样，可以放在只读介质上，可以 NFS 导出一堆无盘机共用。「静态」的意思是装好之后不因运行而变。

拿这两条坐标轴切，很多设计立刻讲得通：

  • /usr 是静态且可共享，所以理论可以整个只读挂载，也可以被一堆机器共享。往 /usr 里写运行时数据是错的。
  • /var 是可变的，所以日志、缓存、队列、数据库文件全在这里。它不可共享，因为每台机器产生的运行时数据不一样。
  • /etc 是静态但不可共享，因为它绑死这台机器的硬件和网络配置，不能拿来给别的机器用。
  • /home 可变且可共享，所以用户主目录可以放 NFS 上，人走到哪台机器都跟着。

另一个约束来自启动顺序。内核刚起来的时候，除了根分区，别的分区都还没挂。所以启动阶段要用的东西必须全在根分区上。这就是「启动必需的目录」的由来：

  • /boot：内核镜像 vmlinuz、内存盘 initrd.img、GRUB 的配置和 stage 文件。
  • /dev：设备文件。内核要打开控制台、要访问磁盘，得有 /dev/*。
  • /etc：全部配置。初始化进程要读它。
  • /lib：/bin 和 /sbin 里那些程序依赖的共享库。
  • /sbin、/bin：初始化脚本和执行系统命令的程序本身。

/boot、/etc、/bin、/sbin、/lib、/dev 这六个，早期必须实打实放在根分区上。现代发行版的限制松了一些，但 /etc 和 /lib 依然最好别拆出去。

还有一件近年的变化得提。/bin、/sbin、/lib、/lib64 在多数现代发行版里已经是指向 /usr 下同名目录的软链接（usr-merge）。这样做的好处是根分区只需要一份 /usr，容器镜像和只读根也更省事。ls -l / 看第一列，这几个会是 l 开头而不是 d 开头。

bash
$ ls -ld /bin /sbin /lib /lib64
lrwxrwxrwx 1 root root 7 10月  2 09:12 /bin -> usr/bin
lrwxrwxrwx 1 root root 8 10月  2 09:12 /sbin -> usr/sbin
lrwxrwxrwx 1 root root 7 10月  2 09:12 /lib -> usr/lib
lrwxrwxrwx 1 root root 9 10月  2 09:12 /lib64 -> usr/lib64

usr-merge 带来一个副作用：/bin/ls 和 /usr/bin/ls 是同一个文件的两个路径。脚本里要判断两个路径是不是同一个文件，别比字符串，用 test /bin/ls -ef /usr/bin/ls，-ef 比的是 inode。

FHS 同时规定了「不该放什么」：根分区体积要尽量小，因为内核要挂它、fsck 要扫它；/usr 里的东西装好之后不该被运行中的程序改；/var 里不该出现「装了就永远不变」的只读资源。

六、根目录下的一级目录 #

ls -l / 出来那一屏不是随机的。下面这张表把每个一级目录的职能和「要不要单独分区」一次说完。

目录 放什么 能否单独分区
/ 整个树的根，一切路径的起点 必须，这是根分区
/bin 所有用户都可用的基础命令：ls、cp、cat、mkdir 现代发行版多为指向 /usr/bin 的链接
/sbin 系统管理命令：fdisk、mkfs、fsck、iptables 同上，指向 /usr/sbin
/lib /bin 和 /sbin 依赖的共享库、内核模块 不单独拆，跟根分区走
/lib64 64 位平台上的 64 位库 视架构而定，有的发行版没有
/boot 内核 vmlinuz、内存盘 initrd.img、GRUB 配置 建议单独分区，尤其是 LVM 或加密根
/etc 全系统配置，纯文本，按服务分子目录 不建议拆
/dev 设备文件，devtmpfs 提供 由内核自动管理，不能拆
/proc 进程与内核状态的伪文件系统 由内核挂载，不能拆
/sys 内核设备、驱动、电源等信息的伪文件系统 由内核挂载，不能拆
/run 本次启动以来的运行时状态，tmpfs，重启清空 由系统自动挂载
/tmp 临时文件，所有人可写，重启清空 可以单独挂 tmpfs
/home 普通用户主目录，一人一个子目录 建议单独分区，重装系统时不丢数据
/root root 的主目录，权限 700 跟根分区走
/var 可变数据：日志、缓存、队列、数据库、网站根 建议单独分区，日志写满不拖累系统
/usr 用户程序与只读数据，占空间最大 建议单独分区，可只读挂载
/opt 第三方附加软件的安装目录 视情况
/srv 本机对外提供的服务数据，如 www、ftp 视情况
/media 可移动介质的自动挂载点，U 盘、光驱 由桌面环境自动管理
/mnt 手动临时挂载点，给管理员随手用 否，就是个空目录
/lost+found fsck 找回的孤儿数据块 每个 ext 分区根下都有一个

几处需要单独解释。

/bin 和 /usr/bin 的区别在历史包袱。早年磁盘小，根分区必须极小，只能放启动急救要用的最小命令集，其余全塞 /usr。现在磁盘不是问题了，/usr/bin 那套拆分只剩形式，usr-merge 之后两者干脆合成一个。

/home 和 /root 是两个世界。前者是所有普通用户的家，多数机器上单独分区甚至挂 NFS；后者是 root 的家，权限 700，别的用户连列目录都不行，而且它不单独分区——root 登录进去时 /home 未必可用，/root 必须一直在。

/srv 和 /var/www 常被搞混。/srv 是 FHS 规定的「本机对外提供的服务数据」，/var/www 是 Debian 系 Apache 的历史习惯。两个都对，用哪个看你装的那套软件。

/opt 和 /usr/local 也不同。/opt 是给第三方整套软件包用的，一个软件一个独立子目录，比如 /opt/google/chrome；/usr/local 是给本地编译安装的软件用的，走和 /usr 一样的三层结构：bin、lib、share。

/media 和 /mnt 的分工很明确：桌面环境插 U 盘自动挂到 /media/用户名/卷标 下面；/mnt 是给你手工挂盘用的。

/lost+found 只在 ext 系文件系统上出现，目录下一堆以 inode 号命名的文件，都是 fsck 修完盘之后捡回来的、找不到父目录的数据块。进去看过就知道，基本读不出来。

启动必须的那几个目录，有个记法：d e l s b，对应 dev、etc、lib、sbin、bin。救急模式下 mount -o remount,ro / 之后，能用的正是这几个。

标准之外，发行版和管理员还会往根目录里加东西。见到不认识的目录，先查这三类来源：

目录 谁加的 是什么
/snap Ubuntu 每个 snap 包一个只读挂载，df 里会刷出一长串
/nix 装了 Nix 的系统 函数式包管理的存储，路径带哈希
/boot/efi UEFI 引导 ESP 分区，FAT32，/boot 常是另一个分区
/dev/shm 内核 tmpfs，POSIX 共享内存，默认上限是内存的一半
/sys/fs/cgroup 内核 cgroup v2 层级，容器的 CPU/内存限制写在这里
/data、/work 管理员 非标准挂载点，装机器时按业务加的

/dev/shm 值得单独提醒：它默认能吃掉一半内存，共享内存泄漏的程序会在这里显形。df -h /dev/shm 一看就知道用了多少。

/dev 里的文件也不是普通文件，是设备号。ls -l /dev/sda 那行的大小位置显示的是 8, 0，主设备号和次设备号：前者决定用哪个驱动，后者决定是这块盘上的第几个设备。/dev/disk/by-uuid 底下那堆软链接就是 fstab 用 UUID 的实现方式：udev 按设备属性建出稳定的名字，每次开机重建，sda/sdb 怎么漂移它都指向对的那一块。

七、/etc、/var、/usr 三大重镇 #

根目录下这三个目录占掉了绝大部分空间和绝大部分日常操作。它们的界限被问得最多，也最容易被违反。

/etc /var /usr

会因为运行而变吗 不会，只有人改才变 一直在变 不会

/etc 的第一个特点是纯文本。里面几乎找不到二进制配置，因为它的定位是「人能改、能 diff、能进版本库」。第二个特点是按服务分子目录或单文件：/etc/nginx/nginx.conf、/etc/ssh/sshd_config、/etc/systemd/system/。第三个特点是它是机器的身份证明：网络配置、主机名、时区、用户表全在这里，丢了这台机器就变了个人。

/etc 下几个绕不开的：

文件 作用
/etc/passwd 用户账号，七个字段，密码位是 x
/etc/shadow 真正的密码哈希，权限 640 或 600
/etc/group 用户组定义
/etc/fstab 开机自动挂载表
/etc/hosts 静态主机名解析，优先于 DNS

还有一个容易踩的点：/etc 里既有 /etc/opt（/opt 对应软件的配置）也有 /etc/X11（X 的配置），它们是按「被谁用」分的，不是按「配置文件长什么样」分的。

/var 的判据只有一条：会随运行而变的东西全归它。

/var/log 系统和服务日志 只增不减，必须配轮转
/var/cache 包管理器缓存、应用缓存 可随时删，删了会重建
/var/lib 应用状态数据，含数据库 /var/lib/mysql 只增不减

/var/log 是运维事故高发区。journalctl 的日志在 /var/log/journal，不配上限就能把分区写满；写满之后服务起不来、SSH 登不上，症状看着像系统崩了，其实只是没空间。/var/tmp 和 /tmp 的差别也要记牢：/tmp 重启清空，/var/tmp 不清空，所以后者适合放「跨重启还要留着」的临时数据。

bash
$ journalctl --disk-usage
Archived and active journals take up 1.2G in the file system.
$ journalctl --vacuum-size=200M
$ journalctl --vacuum-time=7d

再补一条 /var 与容器的关系。容器里的 /var/lib/docker 是镜像层、容器可写层、卷的实际落点，它只增不减，docker system prune 才回收。宿主机的 /var 单独分区给小了，最先报的错不是磁盘满，而是镜像拉不下来、容器起不来，报错信息还往往指向别处。

/usr 最容易被误解，因为它名字里有 user，实际跟用户没关系。它展开是 Unix System Resource，放的是「系统提供的共享只读资源」。

子目录 放什么
/usr/bin 绝大多数用户命令
/usr/sbin 非启动必需的系统管理命令
/usr/lib 库文件、服务内部的可执行文件
/usr/include C/C++ 标准头文件，编译时用
/usr/share 与架构无关的共享数据：文档、man、locale、图标
/usr/src 源码，常见的是内核头文件
/usr/local 本地编译安装的软件，结构仿照 /usr
/usr/libexec 不供用户直接调用的内部程序

/usr/share 里有个 man，所以 man ls 读的其实是 /usr/share/man/man1/ls.1.gz。/usr/include 里是 stdio.h 这类头文件，装 build-essential 就是往这儿塞东西。

三大目录的判断可以压成一句话：配置进 /etc，会变的数据进 /var，装好的程序和只读资源进 /usr。 三者都别拿来做别的事。

八、/proc 与 /sys：内核的窗口 #

/proc 和 /sys 在目录树里，有文件名，能 cat 能 ls，但你 du -sh /proc 出来是 0，df 也看不到它们占空间。因为它们底下没有一个字节来自磁盘。

这类东西叫伪文件系统。VFS 把「按路径访问」这套接口开出来，proc 和 sysfs 各自实现，读文件的时候现算一个值返回给你，写文件的时候去调内核里的函数。文件内容是内核状态的投影，不是存储。

/proc 分两块。数字命名的目录，一个进程一个，目录名就是 PID；其余的是内核和系统的全局信息。

路径 内容
/proc/cpuinfo CPU 型号、核数、频率、特性标志
/proc/meminfo 内存总量、可用、缓存、Swap，free 的数据源
/proc/loadavg 1/5/15 分钟平均负载，uptime 的数据源
/proc/uptime 开机时长和空闲时长，单位秒
/proc/version 内核版本与编译信息
/proc/cmdline 内核启动参数
/proc/mounts 当前挂载表，/proc/self/mounts 是同一份
/proc/filesystems 内核支持的所有文件系统类型
/proc/partitions 已识别的分区和块数
/proc/sys/ 内核可调参数，sysctl 改的就是这里
/proc/<pid>/cmdline 该进程的完整命令行，参数以 \0 分隔
/proc/<pid>/status 进程状态、内存占用、线程数
/proc/<pid>/fd/ 该进程打开的所有文件描述符，软链接指向真实文件
/proc/<pid>/maps 进程的虚拟内存映射表

/proc/sys 底下是按内核子系统分类的参数，net/ipv4/ip_forward 这种路径直接对应 sysctl net.ipv4.ip_forward。写进去立刻生效，但重启就丢，要持久化得写 /etc/sysctl.d/。

bash
echo 1 > /proc/sys/net/ipv4/ip_forward        # 临时打开 IP 转发
sysctl -w net.ipv4.ip_forward=1            # 等价写法
ls -l /proc/$$/fd                          # 查进程开了哪些文件

/proc/<pid>/fd 这个目录值得单独说。查「文件被删了但磁盘没释放」，就是在这里找那个 (deleted) 标记的软链接；查进程卡在哪个 socket 上，也是看这里。它是排查文件描述符泄漏最快的手段，lsof -p <pid> 底层读的也是它。

/sys 是后来加的，专门补 /proc 里设备信息乱放的问题。它把设备、驱动、总线、电源管理组织成目录树，一个设备一个目录，属性就是目录里的文件。

路径 内容
/sys/class/net/ 所有网络接口，一个接口一个目录
/sys/class/block/ 所有块设备
/sys/class/thermal/ 温度传感器读数
/sys/block/<dev>/queue/ IO 调度器、队列深度、读写粒度
/sys/devices/ 设备的物理拓扑，按总线组织
/sys/fs/cgroup/ cgroup 层级，容器资源限制就写这里

两个目录的分工用一句话说清：/proc 看进程和内核整体状态，/sys 看设备和驱动。找进程去 /proc，找硬件去 /sys。

它们和磁盘上的文件系统还有一处本质差别：ls -l 看到的文件大小基本没有意义。/proc/meminfo 的大小显示 0，可读出来好几十行；/sys/class/net/eth0/mtu 是 1500，那是内核里的一个整数，不是文件里的一段字节。别拿 du、stat 的直觉去套它们。

九、绝对路径与相对路径 #

路径是到达某个文件或目录的走法。写法只有两种。

绝对路径从 / 起头，/etc/ssh/sshd_config。整个路径和你在哪个目录无关，在哪执行都指同一个文件。

相对路径不起头，etc/ssh/sshd_config 或 ../lib/systemd，起点是当前工作目录。同一个字符串在不同目录下执行，指向不同文件。

当前目录是进程自己的状态，pwd 打印的就是它。cd 改它，改的只是这个 shell 进程的属性，不影响别的进程。

每条路径里有两个特殊名字：. 表示当前目录，.. 表示上一级目录。cd . 不动，cd .. 上一级。真正关键的是它们在路径中间的作用：. 和 .. 都是目录项里真实存在的条目，由文件系统创建目录时自动写入。任何目录一被 mkdir 出来，里面立刻有 . 和 .. 两条记录。

. 指向自己，.. 指向父目录。根目录的 .. 是特例——/.. 还是 /。文件系统的根是它自己的父目录，不然往上走就没底了。

由此还能推出一个查链接数的技巧。一个目录的链接数等于 2 + 子目录数：. 算一条，父目录里指向它的那一条算一条，每个子目录里的 .. 又各算一条。所以 ls -ld / 显示 drwxr-xr-x 25 root root，说明根下有 23 个直接子目录。

ls -a 能看到 . 和 ..，不加参数看不到，因为 ls 主动过滤了这两个。

路径解析里有几条规则值得记死：

  • 连续的 / 等价于一个 /，/etc//ssh///sshd_config 没问题。
  • 路径以 / 结尾，强制按目录处理。
  • 路径中间出现 ..，就从当前位置往上退一级，不用管上一层是不是真的软链接——cd 用的是物理路径，cd -L 才走逻辑路径。
  • 相对路径的起点是进程的当前工作目录，不是 shell 的提示符。脚本里 cd 之后又 cd 回来，容易在这里出错，用绝对路径最省心。

绝对路径和相对路径怎么选，判据是这条命令会不会被别的东西在别的目录下执行。写进脚本、写进 systemd 单元、写进 cron 的，全用绝对路径，因为那些执行环境的当前目录不可控。命令行里临时操作，相对路径更短，cd 一下就行。

还有两个常配套用的：

bash
$ cd -            # 回到上一个工作目录，和 $OLDPWD 是一回事
$ cd                # 不带参数，回自己的家目录，读的是 $HOME
$ realpath ../x/y   # 把相对路径、软链接全部解析成绝对物理路径
$ readlink -f /bin/ls
/usr/bin/ls

最后一行顺带说明了 usr-merge 的存在：/bin/ls 这条路径走完软链接，落在 /usr/bin/ls 上。

命令的查找是另一套机制，别和路径解析混。你敲 ls，shell 不会在当前目录找，它按 PATH 里的目录顺序一个个试。PATH 是个用冒号分隔的目录列表，echo $PATH 能看见。. 默认不在 PATH 里，正是为了防止当前目录里躺着一个同名恶意程序。

bash
$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
$ which ls        # 在 PATH 里找，返回第一个匹配
$ type ls         # 更准，会告诉你这是别名、内建命令还是外部程序
$ whereis ls      # 从数据库里查，把二进制、源码、man 一起列出来

which 只看 PATH，type 连别名和 shell 内建都能识别，排查「命令行为不对」时先用 type。

PATH 的顺序就是优先级。同一个命令名在多个目录里存在时，先命中的赢。装完新版软件 -v 还是老版本，十有八九是 PATH 顺序问题，或者 shell 把命令路径缓存在了哈希表里。

bash
$ type -a python3           # 列出所有同名命令，按 PATH 顺序
$ hash -r                   # 清掉命令路径缓存，重新查找
$ which -a python3

hash -r 在「刚装完软件、当前 shell 却还找不到」的场景下几乎每次都管用。脚本里判断命令存不存在的标准写法是 command -v，退出码可靠：

bash
if command -v rsync >/dev/null 2>&1; then
    rsync -a src/ dst/
fi

PATH 里的空项，:: 或结尾的 : 都会被解释成当前目录。这是安全隐患，尤其是在 root 的 shell 里。

十、硬链接与软链接 #

到了这一节，前面埋的线全部要用上：文件名不在 inode 里，只在目录项里；目录项就是「名字 → inode 号」。

先说结论：硬链接是让多个目录项指向同一个 inode；软链接是新建一个独立的文件，文件内容是一串路径字符串。

硬链接 #

ln 原文件 新名字 造一个硬链接。造完之后，两个名字地位完全平等，没有谁是「原」谁是「副」。

bash
$ echo "hello" > /tmp/a.txt
$ ln /tmp/a.txt /tmp/b.txt
$ ls -li /tmp/a.txt /tmp/b.txt
1310722 -rw-r--r-- 2 root root 6 11月 17 10:02 /tmp/a.txt
1310722 -rw-r--r-- 2 root root 6 11月 17 10:02 /tmp/b.txt

ls -li 第一列是 inode 号，两个文件一模一样，都是 1310722。第三列是硬链接计数，两个都是 2。

拆开看发生了什么：

动作 inode 号 链接计数 数据块
echo > a.txt 1310722 1 一份，存 hello\n
ln a.txt b.txt 1310722 2 还是那一份，没多
改 b.txt 1310722 2 还是那一份，改的是同一块
rm a.txt 1310722 1 还是那一份，b.txt 照常读
rm b.txt 1310722 0 这时才回收

关键在于最后两行：rm 干的事情是删掉一个目录项，把 inode 的链接计数减一。计数归零，才真正回收数据块。所以删掉一个名字，文件并不会消失，只要还有别的名字指着它。

有一处容易误判：删掉 a.txt 之后，b.txt 的 inode 号没变，链接计数从 2 降到 1。所以「文件被删了」和「文件不存在了」是两件事。你在目录里找不到某个名字，只说明那条目录项没了。

同一个 inode 可以有几十个名字，全都平等。没有「主文件」的概念，也没有「快捷方式」的概念。硬链接省空间的原因就在这儿：加一个名字的成本只是一条目录项，几十字节。

判断一个文件是不是被删干净了，看链接计数就够：

bash
$ stat -c '%h %i %n' /tmp/a.txt /tmp/b.txt
2 1310722 /tmp/a.txt
2 1310722 /tmp/b.txt

%h 是链接数，%i 是 inode 号。

硬链接有两条硬限制，都不是设计者懒，是逻辑上做不到。

第一，不能跨文件系统。 因为 inode 号只在单个文件系统内唯一。分区 A 里的 1310722 和分区 B 里的 1310722 是两个毫不相干的东西，跨过去就没有共同语言了。inode 表是按文件系统建的，没有全局 inode 号。

第二，普通用户不能给目录建硬链接。 如果允许，会立刻出事。假设 /a 和 /b 都硬链接到同一个目录，那么在这个目录里 .. 该指向 /a 还是 /b？没法回答。更糟的是循环：/a/x 硬链接到 /a，一条 find / 就永远走不完。所以 ln 对目录会直接拒绝：

bash
$ ln /etc /tmp/etclink
ln: failed to create hard link '/tmp/etclink' => '/etc': Operation not permitted

目录的链接数限制就是这么来的。一个目录的链接计数 = 2 + 子目录数，那 2 是它自己的 . 和父目录指向它的那一条，多出来的正是每个子目录里的 ..。所以目录链接数只能往上加，永远由文件系统在 mkdir 时维护，不能手工造。

顺便区分硬链接和 cp。cp a.txt c.txt 之后 ls -li 会显示两个不同的 inode 号，链接计数各是 1，磁盘上真的有两份内容，改一份不影响另一份。

软链接 #

ln -s 目标 链接名 造一个软链接，也叫符号链接。它完全是另一种东西：它是一个独立的文件，有自己的 inode，有自己的一份数据，内容就是目标路径那一串字符。

bash
$ ln -s /tmp/a.txt /tmp/c.txt
$ ls -li /tmp/a.txt /tmp/c.txt
1310722 -rw-r--r-- 2 root root 6 11月 17 10:02 /tmp/a.txt
1310723 lrwxrwxrwx 1 root root 10 11月 17 10:03 /tmp/c.txt -> /tmp/a.txt

对比很清楚：c.txt 的 inode 号是 1310723，跟 a.txt 不是一回事；类型位是 l；权限位永远是 lrwxrwxrwx（不管怎么设，软链接的权限在 Linux 上没有实际作用）；大小是 10，正好是 /tmp/a.txt 这十个字符的长度。

所以软链接的本质可以一句话说完：一个存着路径字符串的小文件，内核在解析路径时看到类型是 l，就把内容取出来当新路径继续解析。

内核这套「换路径再走」的机制，让软链接拿到三样硬链接没有的能力。

能跨文件系统。 因为它只是一串字符，跟 inode 号无关，指向 /mnt/otherdisk/x 也行，指向网络盘也行。

能指向目录。 只要是路径就能指，不存在 .. 归属问题。

能悬空。 目标删掉，软链接还在，只是读它会报错。这叫悬空链接或断链。

bash
$ rm /tmp/a.txt
$ cat /tmp/c.txt
cat: /tmp/c.txt: No such file or directory
$ ls -l /tmp/c.txt
lrwxrwxrwx 1 root root 10 11月 17 10:03 /tmp/c.txt -> /tmp/a.txt
$ readlink /tmp/c.txt
/tmp/a.txt

ls -l 照常显示，readlink 照常能读出目标，只有真去读内容才失败。这是软链接和硬链接最直观的区别：硬链接的「目标」就是 inode 本身，只要有一个名字在，数据就在；软链接的「目标」只是一行字，字还在，东西可以没了。

两种链接摆在一起 #

维度 硬链接 软链接
本质 多个目录项指向同一 inode 一个独立文件，内容是路径字符串
inode 号 与原文件相同 与原文件不同，自己有一个
文件类型位 与目标相同（-、d 等） 固定为 l
是否占额外空间 不占，只多一条目录项 占，至少一个 inode 加一段路径
能否跨文件系统 不能 能
能否指向目录 不能（内核禁止） 能
目标删除后 数据还在，从别的名字正常访问 变成断链，访问报错
链接计数 会增加目标的链接数 不影响目标的链接数
权限位是否有意义 有，就是目标文件本身的权限 没有，恒显示 rwxrwxrwx
创建命令 ln 目标 链接 ln -s 目标 链接
常见用途 节省空间、同一文件多个入口 版本切换、配置切换、保留旧路径

ls -l 的输出里，软链接会带 ->，硬链接没有这个标记——你在 ls 里根本看不出哪个是硬链接，只能靠 stat 比 inode 号。

相对路径的软链接 #

ln -s 的第二个参数如果写成相对路径，存进去的字符串就是相对路径，解析时以软链接所在目录为起点，不是以当前目录为起点。

bash
$ cd /tmp && mkdir -p d1 d2
$ ln -s ../d2/target d1/link
$ ls -l d1/link
lrwxrwxrwx 1 root root 12 11月 17 10:05 d1/link -> ../d2/target

这里 ../d2/target 是相对 /tmp/d1 解析的，落到 /tmp/d2/target。这套写法有个实际好处：整个目录树挪到别处，相对软链接跟着一起走，不失效；绝对路径的软链接一挪就断。代价是容易搞错基准，写完之后用 readlink -f 验证，它会按真实规则一路解析到最终的绝对路径。

十一、链接的本质与陷阱 #

链接的概念不难，难在操作时的那几个反直觉的地方。这一节集中处理。

删了文件，磁盘没释放 #

这是最经典的一类事故：df 显示分区 100%，du -sh 加起来只有 30%。差额去哪了？

答案是删掉的文件还被一个进程开着。rm 只删了目录项、把链接计数减到 0，但只要有进程还持有这个文件的打开描述符，inode 和它的数据块就不能回收。内核在这时候做的是「延迟删除」。

证据就在 /proc：

bash
$ lsof +L1
COMMAND  PID USER   FD   TYPE DEVICE  SIZE/OFF NLINK    NODE NAME
java    2103  app    5w   REG  253,0 4294967296     0 1310722 /var/log/app/old.log (deleted)
$ ls -l /proc/2103/fd/5
l-wx------ 1 app app 64 11月 17 10:10 /proc/2103/fd/5 -> /var/log/app/old.log (deleted)

NLINK 是 0，(deleted) 标记在路径后面。空间就是这么丢的。解法不是 df，是重启那个进程，或者更精确一点，在 /proc/<pid>/fd/<n> 上做操作把它清掉。这也是为什么日志文件被 rm 之后空间不回，而 > file（截断）能立刻回——截断改的是 inode 的大小，删名字改的是目录项。

三种「复制」不是一回事 #

操作 inode 是否新建 是否占双份空间 原文件删了还能用吗
cp a b 是 是 能，b 是完全独立的副本
ln a b 否，共用 否 能，b 就是同一份数据
ln -s a b 是（软链接自己有） 极小 不能，b 变断链

选哪个看你要什么：要独立备份用 cp，要省空间多入口用 ln，要留一个会变的指针用 ln -s。

拷贝和打包默认不跟随软链接 #

这条坑过很多人。cp -r 遇到软链接，默认行为是复制链接本身，不是抛下链接去拷目标。

bash
$ cp -r dir1 dir2      # 软链接原样复制，链接的还是老路径
$ cp -rL dir1 dir2     # 跟随链接，把目标内容真的拷过去
$ cp -a dir1 dir2      # 归档模式，保留权限、时间、链接本身

tar 也一样。默认把软链接作为一个类型为 l 的条目存进去，解开时还原成软链接。要存目标内容得加 -h。

bash
$ tar czf backup.tar.gz /etc/nginx/          # 软链接存成链接
$ tar czhf backup.tar.gz /etc/nginx/         # 软链接解引用成实体文件
$ tar czf backup.tar.gz -C / etc/nginx/      # 更稳：用 -C 而不是带绝对路径

顺带一句：打包用绝对路径会产生一堆 tar: Removing leading '/' 警告，解法就是 -C 切到根再写相对路径。

rsync 的对应开关是 -l（保留链接，默认开）、-L（跟随链接）、-a（包含 -l）。

遍历目录时跟随链接会转圈 #

find 默认不跟随软链接，-L 才跟随。一跟随就会撞上循环：a 指向 a 自己，或者 a/b 指回 a。内核在路径解析上有层数上限，find 也会报 File system loop detected。

bash
$ find /etc -type l            # 只找软链接本身
$ find -L /etc -name '*.conf'  # 跟随，会撞循环
$ find /etc -xdev              # 不跨文件系统，扫 / 时必加

-xdev 那一行是实务习惯：扫 / 的时候不加它，会一路走进 /proc、/sys、挂载的网络盘，慢且没意义。

mv 跨文件系统等于复制加删除 #

同一个文件系统内 mv 只改目录项，inode 不变，瞬间完成。跨文件系统就做不到了，内核只能真的把数据拷过去、再删原件，于是 inode 号变了，硬链接关系也断了。

bash
$ stat -c '%i' /tmp/a.txt    # 1310722，在 /tmp 的 tmpfs 上
$ mv /tmp/a.txt /home/a.txt
$ stat -c '%i' /home/a.txt   # 1310735，换号了，说明是复制不是改名

同理，跨文件系统的硬链接根本建不出来，ln 会报 Invalid cross-device link。

ln -sf 的经典翻车 #

ln -sf 新目标 链接名 看起来是「强制覆盖」，但如果链接名已经存在且是个目录，ln 会把新链接建到那个目录里面去，而不是替换它——/usr/local/current 本来是目录，敲完 ln -sf /usr/local/app-v2 /usr/local/current，看到的是 /usr/local/current/app-v2 -> /usr/local/app-v2。

正确写法是 ln -sfn，-n 让 ln 把已存在的软链接当文件处理。版本切换、update-alternatives、Nginx 的 sites-enabled 全靠这个组合。另一个稳妥做法是 ln -sfT，-T 强制把目标当普通文件，绝不当目录。

挂载点被遮住的内容 #

前面说过挂载是遮住，不是替换。这个性质加上 rm 会造成一个怪现象：往一个目录里写满了东西，忘了挂载就直接 rm 也好、mkdir 也好，等挂载上去一看，东西不见了——不是丢了，是被盖住了。卸载之后它们会重新露出来。反过来，在挂载状态下往挂载点里删东西，删的是设备上的内容。

判断一个目录是不是挂载点，findmnt <dir> 或 mountpoint <dir> 都能答。mountpoint 的退出码直接可以用在脚本里。

bash
$ mountpoint /var/log && echo "独立分区"
$ findmnt -T /var/log
TARGET SOURCE         FSTYPE OPTIONS
/      /dev/nvme0n1p2 ext4   rw,relatime

findmnt -T 这个用法值得记：随便给一个路径，它告诉你这个路径最终落在哪个挂载点上、背后是哪块设备。排查「文件到底写进了哪块盘」用它最快。

软链接链与 inode 号复用 #

两个边角情况一起收掉。

软链接可以指向软链接。readlink 只读一层，readlink -f 一路走到底。链太长会撞上内核解析层数上限，报 Too many levels of symbolic links。自己搭的部署目录出现这个报错时，用 namei -l 逐级打出每一层的类型和权限，一眼能看出在哪一环打转：

bash
$ namei -l /usr/local/current/bin/app
f: /usr/local/current/bin/app
drwxr-xr-x root root /
drwxr-xr-x root root usr
drwxr-xr-x root root local
lrwxrwxrwx root root current -> app-v2
drwxr-xr-x root root bin
-rwxr-xr-x root root app

inode 号复用是另一个。inode 被回收之后会被后来的文件拿去重用，所以昨天记下的 inode 号，今天再查已经指向一个完全不相干的新文件。find / -inum <n> 这种按 inode 找文件的用法，只适合在短时间内、确认没有删除操作的前提下用。

还有一类特殊链接：/proc/<pid>/fd 下面的条目。它们看着是软链接，但指向的是「这个进程打开的那一份」，即使原路径被删了、被改名了，这个描述符还指着原来那个 inode。所以 ls -l /proc/$$/fd 里能出现 (deleted)，也能出现 socket:[12345] 和 pipe:[67890] 这种根本不是路径的目标。它们不是文件系统里的普通链接，是内核给打开文件拍的一张快照。

还有一个更隐蔽的版本：rm -rf /var/log/* 时 /var/log 单独挂了一块盘，命令照常执行，删的是挂上去那块盘里的东西。这没问题。真正危险的是分区没挂上就启动服务，日志全写进根分区的空目录，把根盘写满。

十二、目录的权限位为什么特殊 #

文件的权限位和目录的权限位，长得一样，含义完全不同。这一节把差别说透，因为大部分「明明有权限却打不开」的困惑都出在这里。

先看那十个字符怎么读。drwxr-xr-x 一共十位，拆成四段：

位 含义 取值
第 1 位 文件类型 - d l b c p s
第 2–4 位 属主（u）权限 rwx 的任意组合
第 5–7 位 属组（g）权限 rwx 的任意组合
第 8–10 位 其它人（o）权限 rwx 的任意组合

第一位的类型字符：

字符 类型 例子
- 普通文件 文本、二进制、脚本
d 目录 /etc
l 软链接 /bin -> usr/bin
b 块设备 /dev/sda、/dev/nvme0n1p2
c 字符设备 /dev/tty0、/dev/null
p 命名管道 进程间通信用的 FIFO
s 套接字 /run/ 下那堆 .sock

rwx 三段拼起来，每位取 4/2/1 求和：rwx=7、rw-=6、r-x=5、r--=4、-wx=3、-w-=2、--x=1、---=0。三组连写就是 chmod 的数字参数，所以 777 是所有人全权，755 是属主全权其余只读可执行，644 是属主读写其余只读，600 只有属主能读写，700 只有属主能进能改。

ls -l 那一行七段信息，按顺序是权限、链接数、属主、属组、大小、时间、文件名。只有第一段是权限，其余是元数据。

现在进正题。同样是 rwx，落在目录上就换了意思。

权限位 落在文件上 落在目录上
r 能读文件内容 能列出目录里的名字
w 能改文件内容 能在目录里新建、删除、重命名条目
x 能把文件当程序执行 能进入目录、能穿过它访问子项

三条都要单独拎出来讲。

目录的 r 只能看名字，不能看内容。 有 r 没 x 的目录，ls 能列出文件名，但 ls -l 里每个文件的大小、权限、时间全是问号，stat 也拿不到。因为那些属性在 inode 里，读 inode 需要穿过目录进去，没有 x 就穿不过去。这时文件名字是可见的，元数据和内容都不可见。

目录的 x 是通行证。 路径里任何一级目录缺 x，整条路径就断在那里。/a/b/c/d 这条路径，要求 /a、/a/b、/a/b/c 三级目录都有 x，缺一级就 Permission denied，哪怕 d 自己的权限是 777。反向也成立：只有 x 没有 r 的目录，你不能 ls，但如果你知道确切文件名，可以 cat 那个文件。这是「可执行不可读」目录的用法。

目录的 w 才是删除权的来源。 这一条最反直觉：能不能删掉一个文件，取决于它所在目录有没有 w，跟文件自己的权限无关。

bash
$ mkdir /tmp/proj && echo data > /tmp/proj/ro.txt
$ chmod 444 /tmp/proj/ro.txt          # 文件本身只读
$ chmod 755 /tmp/proj                 # 目录属主可写
$ rm /tmp/proj/ro.txt                 # 照样删掉
$ ls /tmp/proj

文件是 444，一行数据都没动过它，照样删得掉。因为 rm 删的是目录里的一条「名字 → inode 号」记录，删记录属于改目录内容，要的是目录的 w。文件自身权限管的是「内容能不能读、能不能改」，管不到「名字能不能消失」。

顺着这条推下去：对一个目录有 w，意味着你可以删掉里面任何文件，包括别人建的、你没权限读的。这正是 /tmp 必须特殊保护的原因。

粘滞位。 /tmp 是所有用户可写的共享目录，权限显示 drwxrwxrwt，最后那个 t 就是粘滞位（sticky bit），数字表示是 1777。它的作用只有一条：在有粘滞位的目录里，你只能删除自己创建的文件，删不了别人的。 没有它，/tmp 就是个人人可删的战场。/var/tmp 也带粘滞位，理由一样。chmod +t 加，chmod -t 去，t 和 T 的区别只在于其他人那一组有没有 x，功能一样。

属组位上的 setgid。 目录权限里有时会看到 drwxrwsr-x，那位的 s 是 setgid。落在目录上，它的作用是：在这个目录里新建的文件和子目录，属组继承目录的属组，而不是创建者的主组。 团队共享目录全靠这个，配合 umask 002 就能让一个组的人互相改文件：

bash
$ chgrp dev /srv/share && chmod 2775 /srv/share
$ mkdir /srv/share/a && ls -ld /srv/share/a
drwxrwsr-x 2 alice dev 4096 11月 17 10:22 /srv/share/a

目录权限另外三个容易踩的点。

一是目录的大小。ls -ld /etc 显示 4096 或 12288 这类数字，那是目录数据块占的字节数，跟里面文件总量没关系。条目多了，一个块装不下，文件系统给它加块，大小跟着涨。du -sh /etc 算的是里面所有内容的总和，是两个量。

二是 chmod 默认不递归。chmod 750 /srv/data 只改这一层，里面的东西原样不动。要递归得 -R，而 -R 会把文件的可执行位一起乱改。稳妥做法是分开处理：

bash
$ find /srv/data -type d -exec chmod 750 {} +
$ find /srv/data -type f -exec chmod 640 {} +

三是 umask。新建文件的实际权限是「请求权限减掉 umask」，不是 chmod 的结果。umask 022 下，程序请求 666 得到 644，请求 777 得到 755。0027 是实务上常用的值：新建文件落到 640，新建目录落到 750，同组能读不能写，其他人什么都看不到。

权限检查是按顺序命中的，不是叠加的。 内核拿到当前进程的 uid/gid，先看属主是不是你，是就只看属主那三位；不是，再看属组，命中就只看属组那三位；都不是，才看其他人那三位。所以「属主是 ---、属组是 rwx」的文件，属主本人反而读不了。

root 的例外。 root 不受 r/w 位限制，能读写任何文件；但 x 位仍然生效——一个文件只要有一个 x 位被置上，root 就能执行它。目录的 x 对 root 也一样要求，路径中间有一级目录是 r--，root 也穿不过去。

符号模式和数字模式的选择。 chmod +x 是在现有权限上加一位，不碰其他位；chmod 755 是把三位整体覆盖。前者适合补一个位，后者适合定死一套。写初始化脚本用数字模式更稳，它不受当前权限影响，重复执行结果一致。

bash
$ chmod 644 /etc/hosts          # 定死，幂等
$ chmod u+x /usr/local/bin/app  # 只加属主执行位
$ chmod o-rwx /srv/secret       # 只去掉其他人全部权限
$ chmod -R g+rX /srv/share      # 大写 X：目录加 x，本来有执行位的文件才加

chmod -R 里的大写 X 值得单独记：它给目录加 x、给「本来就有执行位」的文件加 x，其他普通文件不动。共享目录批量改权限时用它才不会把一堆数据文件变成可执行。

ACL 的存在。 九个权限位只能表达三档身份，团队场景常常不够用。setfacl 能在文件上额外挂几条规则，ls -l 的权限位后面出现一个 + 就表示有 ACL。cp -a 和 rsync -A 才保留 ACL，普通 cp 会丢。

目录与挂载 #

现象 原因 怎么处理
分区明明还有空间，写入报 No space left on device inode 用完了，小文件太多 df -i 看 inode 使用，清小文件
df 满了，du 加起来远小于占用 有文件被删但进程还开着 lsof +L1 找 (deleted)，重启进程
挂载后目录里原来的东西不见了 挂载是遮住，不是删除 umount 后原内容恢复
分区没挂上就启动服务，日志写进了根分区 根分区被当成了 /var/log 先 findmnt 确认挂载，再起服务
开机后设备名从 sda 变成 sdb 设备名随枚举顺序变 fstab 里用 UUID= 不用 /dev/sdX
改了 /etc/fstab 重启进不了系统 挂载点写错或设备不存在 用 nofail 选项，或进 rescue 模式修

路径与查找 #

现象 原因 怎么处理
脚本手动跑正常，cron 里失败 当前目录和 PATH 不同 脚本里全用绝对路径，显式设 PATH
敲 ls 报 command not found，文件确实在 该目录不在 PATH 里 ./script.sh 或 echo $PATH 核对
路径里有一级目录缺 x，深层文件打不开 目录 x 是通行证 逐级 ls -ld 检查 x 位
cd .. 之后位置不对 软链接影响逻辑路径 pwd -P 看物理路径
find / 扫得极慢 走进了 /proc、/sys、网络挂载 加 -xdev，或 -path 排除

链接 #

现象 原因 怎么处理
ln 目录报 Operation not permitted 内核禁止目录硬链接 用 ln -s
ln 跨分区报 Invalid cross-device link 硬链接不能跨文件系统 用 ln -s，或 cp
软链接变成断链 目标被删或被改名 readlink -f 定位，重建
拷贝后软链接指向的还是老路径 cp -r 不跟随链接 cp -a 保留链接，cp -rL 跟随
ln -sf 把链接建进了目录里 目标名已是目录 改用 ln -sfn 或 ln -sfT
目录树整体搬家后软链接全断 用了绝对路径 建相对路径的软链接
ls -l 看不出哪个是硬链接 硬链接没有标记 stat -c '%i' 比 inode 号
想给 /etc 做个「副本」却改不动它 软链接不是副本，改它就是改目标 要副本用 cp -a

权限 #

现象 原因 怎么处理
文件 444 却能删掉 删除权在所在目录的 w 上 收目录的 w，或加粘滞位
/tmp 里删不掉别人的文件 粘滞位生效 正常，属于设计
ls 能列出名字但属性全是问号 目录有 r 无 x 补 x
chmod -R 750 之后程序跑不起来 普通文件被改成可执行或丢了读位 分类型 find ... -exec chmod
共享目录里新文件属组总是创建者的主组 缺 setgid chmod 2775 加组继承
新建文件权限和 chmod 预期不符 umask 在减 先 umask 再建，或显式 chmod

伪文件系统 #

现象 原因 怎么处理
du -sh /proc 是 0 内容不占磁盘 正常
sysctl 改完重启就丢 写 /proc/sys 是临时的 写 /etc/sysctl.d/*.conf
ls -l /proc/<pid>/fd 全在，进程却卡住 在等某个 socket 或锁 看指向，配合 ss、lsof
读 /proc/<pid>/cmdline 出来是连着的 参数以 \0 分隔 tr '\0' ' ' < /proc/<pid>/cmdline

到这儿，从「一块没有名字的裸存储」到「一棵有规范的目录树」，再到「树上每个节点怎么被引用、怎么被保护」，这条线就走完了。你现在应该能答上开头那三个问题：/usr 和 /var 差的是一条「静态还是可变」的分界线；删掉一个文件不代表数据没了，只代表那条目录项没了；ln 动的是目录项指向的 inode，ln -s 造的是一个装着路径字符串的新文件。
