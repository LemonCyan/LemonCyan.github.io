一、C 程序的内存布局全景 #

先记一句话：每个进程都以为自己独占一整块内存。这不是错觉，是虚拟地址空间给的承诺。你打印的每一个 %p，都是这份承诺的一部分。

可执行文件跑起来变成进程，操作系统发给它一份独立的虚拟地址空间。32 位系统上是 4GB，地址 0x00000000 到 0xFFFFFFFF，Linux 把它切成两半：

  • 用户空间：低地址 3GB，0x00000000 到 0xC0000000，普通程序只能碰这一段。
  • 内核空间：高地址 1GB，0xC0000000 到 0xFFFFFFFF，内核代码和数据常驻，用户程序想访问只能通过系统调用切进内核态。
text
+----------------------------------+ 0xFFFFFFFF (4GB)
|        内核空间 (Kernel Space)     |  1GB，所有进程共享同一份
+----------------------------------+ 0xC0000000 (3GB)
|      环境变量 / 命令行参数          |
+----------------------------------+
|              栈 (Stack)          |  栈顶在下，向下长
|               |                  |
|               v                  |
|                                  |
|           共享映射区              |  mmap、共享库、大块 malloc
|                                  |
|               ^                  |
|               |                  |
|              堆 (Heap)           |  向上长
+----------------------------------+
|      BSS 段 (未初始化全局)         |
+----------------------------------+
|      数据段 (已初始化全局)          |
+----------------------------------+
|   只读数据 / 代码区 (Text / RO)    |  32 位下从 0x08048000 起
+----------------------------------+
|             保留区                |  0x00000000 - 0x08048000
+----------------------------------+ 0x00000000

低地址那片空洞不是浪费，是留着抓空指针的：谁解引用 NULL，谁立刻撞上未映射区域，进程当场 SIGSEGV，而不是悄悄读到一个随机值。

64 位下地址空间大得多，形状没变，只是位置挪了。/proc/self/maps 里你会看到 0x55...（PIE 可执行文件的代码和数据）、0x7f...（共享库、mmap 区、大块堆）、0x7ff...（栈）。从低到高仍然是：代码、数据、堆、共享库、栈。maps 每行格式是 起始-结束 权限 偏移 设备 inode 路径，带路径的是文件映射，00:00 配 inode 0 的是匿名映射。

五段对照 #

段 放什么 权限 生命周期 maps 里的串
代码段 Text 机器指令、只读常量、字符串字面量 只读、可执行 进程全程 r-xp / r--p
数据段 Data 已初始化的全局变量和 static 可读写 进程全程 rw-p
BSS 未初始化的全局变量和 static 可读写 进程全程，加载时清零 rw-p
堆 Heap malloc 家族拿到的内存 可读写 手动 free 前一直存在 rw-p，带 [heap]
栈 Stack 局部变量、形参、返回地址、保存的寄存器 可读写 函数返回即失效 rw-p，带 [stack]

想亲眼看到这张表，一条命令就够。输出地址每次运行都不同，格式见下文：

bash
cat /proc/self/maps

text
55d4a1c1e000-55d4a1c20000 r-xp 00001000 08:01 1234567  /usr/bin/app
55d4a3f5b000-55d4a3f7c000 rw-p 00000000 00:00 0        [heap]
7ffd2a3e1000-7ffd2a402000 rw-p 00000000 00:00 0        [stack]

权限四个字符依次是读、写、执行、私有或共享。看懂这张表，等于拿到了进程内存的地图。

从源码到段：编译四阶段 #

变量最后落进哪个段，由链接器决定。中间过四道手：预处理（展开 #include、替换 #define、处理 #ifdef）、编译（C 变汇编）、汇编（汇编变机器指令，得到目标文件）、链接（合并目标文件和系统库，解析符号、做重定位，产出 ELF）。

bash
gcc -E main.c -o main.i     # 预处理
gcc -S main.i -o main.s     # 编译
gcc -c main.s -o main.o     # 汇编
gcc main.o -o app           # 链接

符号归属可以直接查，readelf -s app | grep -E "global|static" 会告诉你每个符号将来睡在哪个段。

Ndx 列是关键：.data 是已初始化数据段，.bss 是未初始化段，.text 是代码，UND 表示要靠链接解决。在 .o 文件里，未初始化全局变量往往先挂在 COM 名下，链接阶段才收进 .bss。

打印地址验证布局 #

写段代码打脸最快：

c
#include <stdio.h>
#include <stdlib.h>

int global_init = 10;          /* Data */
int global_uninit;             /* BSS */
static int static_global = 20; /* Data */
const int global_const = 100;  /* .rodata */

void show_stack(int arg) {
    int local = 30;                 /* 栈 */
    const int const_local = 40;     /* 栈，const 只约束编译器 */
    static int static_local = 50;   /* Data，函数退出不销毁 */
    const char *lit = "ABCDE";      /* 指针在栈，字面量在 .rodata */
    char arr[] = "ABCDE";           /* 整个数组在栈 */

    printf("形参 %p  局部 %p  const %p\n",
           (void *)&arg, (void *)&local, (void *)&const_local);
    printf("静态 local %p  栈数组 %p\n", (void *)&static_local, (void *)arr);
    printf("栈上指针 &lit %p  字面量 lit %p\n", (void *)&lit, (void *)lit);
}

int main(void) {
    int *h1 = malloc(4);
    int *h2 = malloc(4);

    printf("代码段 main %p  只读常量 %p\n", (void *)main, (void *)&global_const);
    printf("已初始化 %p  静态全局 %p\n", (void *)&global_init, (void *)&static_global);
    printf("未初始化 %p  堆 %p %p\n", (void *)&global_uninit, (void *)h1, (void *)h2);
    printf("堆增长方向 : %s\n", h2 > h1 ? "由低向高" : "由高向低");

    show_stack(99);
    free(h1);
    free(h2);
    return 0;
}

编译时关掉 PIE，地址关系更直白：

bash
gcc -no-pie -O0 layout.c -o layout && ./layout

顺序会是：main < global_const < global_init < static_global < global_uninit < 堆 < 栈。堆里两次 malloc 相差几十字节（glibc 给每块加了头部），栈上则一路往下掉。

二、代码段与数据段 #

代码段是进程里权限最紧的一块。它装机器指令，也装只读常量：字符串字面量、const 修饰的全局变量，都进 .rodata。

权限是只读加可执行。你改它一个字节，硬件触发页保护异常，内核发 SIGSEGV，进程死掉。这就是「改字符串字面量报段错误」的全部原因，不是编译器脾气差，是页表不让写。

c
char *s = "hello";
s[0] = 'H';   /* 段错误，发生在运行时 */

32 位 Linux 上代码段固定在 0x08048000 起步。固定是有意的：这以下的地址永不映射，空指针加小偏移的解引用必然崩，方便定位。

数据段装已初始化的全局变量和已初始化的静态变量，int global_var = 100; 就住这儿。可读写，因为程序要能改自己的全局状态。需要看各节大小时跑 readelf -S app | grep -E "text|data|bss|rodata"，.data 的大小正好等于那几个初始值之和。

变量的三个维度 #

一个变量住哪、活多久、几个人能看见它，由三个互相独立的维度决定。C 标准把这三件事分得很清楚，混起来谈必然糊涂。

维度 取值 含义 例子
存储时期 静态存储时期 程序启动时分配，退出才回收 全局变量、static 变量
存储时期 自动存储时期 进入代码块分配，离开立即回收 普通局部变量
存储时期 动态存储时期 手动申请，手动释放 malloc 得到的内存
作用域 代码块作用域 只在声明它的 {} 内可见 函数内局部变量
作用域 文件作用域 从定义处到文件结尾可见 函数外定义的变量
链接属性 外部链接 其他源文件也能用 非 static 的全局变量、函数
链接属性 内部链接 只在当前文件可见 static 修饰的文件作用域变量
链接属性 空链接 只有声明它的块能用 块作用域变量

关键点：static 修饰局部变量时改的是存储时期（从栈挪进数据段），修饰全局变量时改的是链接属性（从外部链接变内部链接）。同一个关键字，两个完全不同的作用。

跨文件的共享与隔离 #

多文件项目里，链接属性就是权限系统。

c
/* file_provider.c：提供方 */
int shared_count = 999;              /* 外部链接，别人能用 */
static int file_private_key = 12345; /* 内部链接，只此文件可见 */

void print_private_key(void) {
    printf("Provider: Private Key = %d\n", file_private_key);
}

c
/* main_entry.c：使用方 */
extern int shared_count;
extern void print_private_key(void);

int main(void) {
    printf("Main: Shared Count = %d\n", shared_count);
    shared_count = 1000;                 /* 直接改写外部链接变量 */
    print_private_key();                 /* 通过导出函数读它的私有变量 */
    return 0;
}

bash
gcc main_entry.c file_provider.c -o app && ./app

现在把 extern int file_private_key; 加进 main_entry.c 试试，链接器直接拒绝：undefined reference to 'file_private_key'。

这就是 static 在文件作用域下的隔离作用：它把符号从全局符号表里藏起来，别的翻译单元连找都找不到。大型项目里给所有内部函数和模块级变量加 static，等于给自己划了一块不会被别人踩的地。

三、BSS 段与未初始化数据 #

BSS 是 Block Started by Symbol 的缩写，名字来自上古汇编器，含义留到今天：存放未初始化的全局变量和未初始化的静态变量。

它最特别的地方是不占可执行文件的体积：

c
int big_uninit[1000000];        /* BSS */
int big_init[1000000] = {1};    /* Data */

第二个数组得把 4MB 的零和那个 1 实实在在写进文件。第一个数组全是零，文件里一个字节都不用存，链接器只在段头记一句「这里要 4MB，全零」。所以可执行文件大小几乎只受 big_init 影响。

程序加载时，内核把 BSS 对应的页映射成匿名零页，读到就是零。C 标准保证静态存储期的对象未初始化时被初始化为零，不用你自己 memset。跑一下 size app，三列 text、data、bss 直接给答案：往 BSS 里塞大数组，bss 列涨，data 列不动，文件大小也不动。

对比项 Data 段 BSS 段
内容 有非零初值的全局 / 静态变量 无显式初值，或初值全零
是否占文件体积 占 不占，只记大小
加载时动作 从文件读入 映射零页
典型写法 int g = 100; int g; / int g = 0;
符号表标记 .data .bss（.o 阶段为 COM）

注意 int g = 0; 这种显式零初始化，编译器也会放进 BSS。零就是零，没必要在文件里存一遍。

静态局部变量的代价 #

static 局部变量住在数据段，函数返回不销毁，值一直留着。这个特性用起来方便，多线程下就是一个坑：

c
int accumulate_sum(int val) {
    static int current_sum = 0;   /* 全局区，所有线程共享同一块内存 */
    current_sum += val;
    usleep(100);                  /* 放大竞争窗口 */
    return current_sum;
}

int accumulate_sum_safe(int val) {
    static _Thread_local int current_sum = 0;   /* C11，每线程一份 */
    current_sum += val;
    return current_sum;
}

两个线程同时调 accumulate_sum(1)，读到的是同一份 current_sum。加法不是原子的，usleep 又把窗口撑开，结果不是 1 也不是 2，而是取决于调度顺序的某个值。这种 bug 在单线程测试里永远复现不了。

_Thread_local 是 C11 给的专用工具。这类变量既不进 Data/BSS，也不在普通栈上，它进 TLS 段（Thread-Local Storage）。每个线程创建时，运行时库给它单独准备一份副本，各改各的，互不干扰。它和 static 一起写也合法，此时同时具备静态存储时期和线程私有。

四、栈：自动变量的位置 #

栈管函数调用。每进一个函数压一个栈帧，每出一个函数弹掉一个。

一个栈帧从高地址往低地址依次是：寄存器放不下的参数、返回地址、调用者保存的 rbp、局部变量、对齐填充。x86-64 上函数入口几乎是固定套路：

text
push   rbp          ; 保存调用者的帧基址
mov    rbp, rsp     ; 建立本次调用的帧基址
sub    rsp, 0x30    ; 给局部变量腾空间

rbp 是帧基址，不动；rsp 是栈顶指针，随压栈弹栈移动。局部变量用 [rbp-0x8] 这样的负偏移访问，所以同一函数里的局部变量地址总比 rbp 小。

参数传递在 x86-64 System V ABI 里优先用寄存器：rdi、rsi、rdx、rcx、r8、r9 装前六个参数，第七个起才上栈。所以在 64 位下打印形参地址，它常常离局部变量不远，那是编译器把寄存器里的值溢出到了栈上。

写代码量一下栈帧的生长方向：

c
void inner(void) {
    int deep = 2;
    printf("inner 局部 : %p\n", (void *)&deep);
}

void outer(void) {
    int shallow = 1;
    printf("outer 局部 : %p\n", (void *)&shallow);
    inner();
}

地址一路递减：main 里的局部变量最高，outer 的 shallow 低一些，inner 的 deep 最低。栈从高地址往低地址长，这是事实，不是习惯。

栈数组和指向栈的指针，在机器码层面是两回事：

text
; 栈数组：直接寻址，一步到位
mov cl, byte ptr [rbp-7]

; 指针指向的内存：先取地址，再间接寻址
mov edx, dword ptr [rbp-12]
mov al, byte ptr [edx+1]

栈数组省掉一次解引用。这是栈在存取效率上占优的硬件原因，跟「栈更快」这种笼统说法不是一回事：真正的原因是局部性好，命中缓存。

五、栈的生长方向与栈溢出 #

栈为什么向下长？历史包袱加设计取舍。早期机器把栈放高地址、堆放低地址，两边向中间长，地址空间紧张的年代，谁的用量大谁就多占，中间的空闲区能被双方共用。

代价是你必须记住：栈的地址在减小，堆的地址在增大。

栈有多大 #

bash
ulimit -s            # 查当前上限，输出 8192 表示 8MB
ulimit -s 16384      # 当前 shell 及子进程改成 16MB
ulimit -s unlimited  # 解除限制，不建议，容易把系统内存吃光

unlimited 在某些发行版上会让栈长到和共享库区撞车，程序行为变得难以预测。宁可改大到一个具体数值，也别图省事写 unlimited。

三种压垮栈的写法 #

第一种，无限递归：

c
void infinite_recursion(int depth) {
    char dummy_buffer[1024];   /* 每层 1KB */
    printf("Depth: %d\n", depth);
    infinite_recursion(depth + 1);
}

每层吃掉 1KB 加一个栈帧，8MB 撑不了几千层。rsp 一路下移，撞到栈区下边界那块守护页（guard page），页保护异常，内核发 SIGSEGV，程序崩掉。

第二种，局部数组开太大：

c
void too_big(void) {
    char buffer[16 * 1024 * 1024];   /* 16MB，超过 8MB 栈上限 */
    buffer[0] = 0;
}

编译能过，运行即崩。编译器不拦你，因为它不知道你的 ulimit 是多少。

第三种，变长数组或 alloca 在循环里用：

c
for (int i = 0; i < 1000; i++) {
    char *p = alloca(8192);   /* 每次 8KB，函数退出才回收 */
}

alloca 分配的内存跟着当前函数存活，循环里申请一千次就是 8MB，函数还没返回栈就爆了。这类代码在评审里最难看出来。

判断标准很简单：单函数局部变量总量控制在 10KB 以内，超过就放堆。几百 KB 的报文缓冲区没有理由住在栈上。

六、堆与 malloc #

栈归编译器管，堆归你管。界线很清楚：栈上的东西出了作用域自动消失，堆上的东西你不 free，它就一直在。

堆在进程布局里紧挨着 BSS 之上，从低地址往高地址长。第一次 malloc 时堆往往还不存在，glibc 才去内核要第一段。

c
int *p = malloc(100 * sizeof(int));
if (p == NULL) {
    return 1;
}
p[0] = 42;
printf("p = %p, p[0] = %d\n", (void *)p, p[0]);
free(p);
p = NULL;

三个细节不能省：检查 NULL、用完 free、free 之后置空。少任何一个，都会在某个深夜让你加班。

堆和栈的差别 #

维度 栈 堆
管理者 编译器插入指令自动完成 程序员手动 malloc / free
空间大小 固定上限，默认 8MB，ulimit -s 可调 受虚拟地址空间和物理内存限制，灵活
增长方向 从高地址向低地址 从低地址向高地址
分配速度 移动 rsp，几条指令 要查找空闲块，慢一到两个数量级
释放时机 函数返回自动回收 显式 free，或进程退出
碎片问题 没有 有，长期运行的程序会碎
访问效率 局部性好，缓存命中高 指针间接寻址，多一次内存读
出错后果 爆栈，直接崩 泄漏、越界，出错时不吭声

分配速度差多少？差在机制上。栈分配就是把 rsp 减一个数，没有任何查找。堆分配要在空闲结构里找一块够大的，切出来，记账。百万次循环里这个差距是几十倍，不是几倍。

malloc 系列 #

函数 作用 是否清零 返回值 要点
malloc(size) 申请 size 字节 不清零，内容是垃圾 成功返回指针，失败返回 NULL 必须检查 NULL
calloc(n, size) 申请 n * size 字节 清零 同上 n * size 会溢出要留意
realloc(ptr, size) 调整已有块大小 新扩展部分不清零 成功返回新指针，失败返回 NULL 且原块不动 绝不能用原指针接返回值
free(ptr) 释放块 不清零，数据还在 无返回值 只能释放 malloc 家族给的指针

calloc 的零不一定是白送的。大块时内核给的匿名页本来就是零页，可以直接用；小块则要显式写零。所以别以为 calloc 一定比 malloc 加 memset 慢。

realloc 是四个里最容易用错的。它有三种行为：原地扩容、搬到新地址、失败。原地扩容时返回指针和原来一样；搬到新地址时旧块已被释放，旧指针立刻变成野指针；失败时返回 NULL，但原块还在。所以绝不能写 p = realloc(p, n)：

c
int *tmp = realloc(p, new_size);
if (tmp == NULL) {
    free(p);            /* 原块还在，自己决定保留还是释放 */
    return -1;
}
p = tmp;

realloc(p, 0) 在 C89 里是实现定义，C99 之后等价于 free(p) 并返回一个可以传给 free 的指针。别写这种代码，要释放就写 free。

alloca 是个异类。它在栈上分配，函数返回时自动回收，不需要也不能 free：

c
void use_alloca(size_t n) {
    char *buf = alloca(n);   /* 栈上分配，跟着函数走，退出自动回收 */
    buf[0] = 0;
}

它极快，就是移动栈指针。但没有失败返回值，分配不下直接爆栈，也没有可移植性保证（POSIX 里没有 alloca）。别在库的公开接口里用它。

大小决定走哪条路 #

小块（glibc 默认阈值 128KB 以下）：分配器向内核要一块连续的堆区，方式是抬高堆顶指针（brk）。free 之后这块内存不会马上还给内核，而是留在分配器自己的空闲结构里，等下次同样大小的请求复用。

大块（128KB 及以上）：改用 mmap，在共享映射区单独开一块匿名映射。free 时直接 munmap，虚拟地址空间立刻还回去。

这个差异在 free 之后量一下就能看见。读 /proc/self/statm 的第二个字段（常驻页数）乘 4 就是 RSS：

c
static long rss_kb(void) {
    FILE *f = fopen("/proc/self/statm", "r");
    long size = 0, resident = 0;
    if (f) {
        if (fscanf(f, "%ld %ld", &size, &resident) != 2) {
            resident = 0;
        }
        fclose(f);
    }
    return resident * 4;   /* 页大小 4KB */
}

int main(void) {
    printf("初始 RSS   : %ld KB\n", rss_kb());
    char *small = malloc(1024);
    memset(small, 0xAA, 1024);
    free(small);
    printf("小块释放后 : %ld KB\n", rss_kb());
    char *big = malloc(64 * 1024 * 1024);
    memset(big, 0xBB, 64 * 1024 * 1024);
    free(big);
    printf("大块释放后 : %ld KB\n", rss_kb());
    return 0;
}

小块释放后 RSS 基本没降，内存还挂在堆里；大块释放后 RSS 明显回落，映射被撤了。这就是「大块内存适合一次性分配、一次性释放」的实测依据。

阈值可以用环境变量 MALLOC_MMAP_THRESHOLD_=65536 或者 mallopt(M_MMAP_THRESHOLD, 65536) 改。阈值调低，大块走 mmap 更频繁，free 还得更彻底，代价是每次分配多了系统调用开销。

七、malloc 与 free 的行为 #

malloc 的返回值只有两种局面：一个可用指针，或者 NULL。没有第三种。所谓「内存不够」在 Linux 上多半不是 malloc 返回 NULL，而是你写的时候内核才去要页，要不到就把进程杀掉（OOM killer）。这叫 overcommit。

所以「malloc 成功」不代表「内存真的到手」，它只代表虚拟地址空间里给你划了一块，物理页还没发。

c
char *p = malloc(1024 * 1024 * 1024);   /* 1GB，往往立刻成功 */
if (p) {
    p[0] = 1;   /* 真正写的时候才分配物理页 */
}

malloc(0) 是实现定义：要么返回 NULL，要么返回一个可以 free 的最小指针。别依赖任何一种。free(NULL) 是合法的，什么都不做，这个特性能让「指针为空就跳过」的代码不加额外判断。

五条行为规则 #

第一条，谁申请谁释放。跨模块传递所有权时必须有明确约定。接口文档里写不清「返回的指针归谁释放」，这个接口就是定时炸弹。

第二条，只能释放 malloc 家族给的地址。栈上的地址、全局变量的地址、指针算术偏移过的地址，都不能传给 free。

c
int a[10];
free(a);            /* 未定义行为 */

char *p = malloc(100);
free(p + 10);       /* 未定义行为，必须传原始指针 */

第三条，不能重复释放，也不能释放后继续用。

c
char *p = malloc(100);
free(p);
free(p);            /* 双重释放，堆结构被破坏 */
p[0] = 'x';         /* use-after-free，改到谁的数据全看运气 */

第四条，free 不清零。释放后的内存里还留着你写的数据，会被下一次 malloc 读到。涉及密码、密钥的缓冲区，释放前自己清一遍，并且用 volatile 防止编译器把循环优化掉：

c
void wipe(void *p, size_t n) {
    volatile unsigned char *v = p;
    while (n--) {
        *v++ = 0;
    }
}

第五条，free 之后立刻置空。

c
free(p);
p = NULL;

这一行不是形式主义。它把后续所有「用已释放指针」从随机破坏内存降级成立刻段错误。可复现的崩溃比随机的数据损坏好一百倍。

分配失败的两种真相 #

64 位系统上你几乎不会遇到 malloc 返回 NULL，虚拟地址空间有 128TB。能把它耗尽的场景很少：申请一个负数转换来的巨大 size_t，或者循环里泄漏了上百万次。前者的根源往往是无符号整数的减法回绕，比如 size_t n = 0; n--; 之后 malloc(n) 必然失败。任何用户输入参与计算的 malloc 大小，都要先检查上界：

c
if (count > 0 && size > 0 && count > SIZE_MAX / size) {
    return NULL;            /* 乘法会溢出，提前拦住 */
}
void *p = malloc(count * size);

八、虚拟地址空间的意义 #

到这里可以回答那个核心问题了：为什么每个进程都以为自己独占整块内存？

因为进程持有的地址是虚拟的。CPU 执行 mov rax, [0x400000] 时，这个 0x400000 不会直接送到内存条，它先送到 MMU，由 MMU 按当前进程的映射表翻译成物理地址，再发出去。

于是只有两条路：虚拟地址映射到了某个物理页，访问成功；或者没映射，CPU 触发缺页异常，内核介入。整个机制的前提是每个进程有自己独立的一套映射表，进程切换时这套表跟着换。所以两个进程用同一个虚拟地址 0x400000，读到的是完全不同的物理内存，谁也看不见谁。

这一句解释了四件事。

进程之间天然隔离。A 进程写坏了自己的内存，B 进程毫无感觉。想通信只能走管道、共享内存、socket 这些明确开了口的通道。

每个进程都能用满整个地址空间。你的程序里 malloc 返回 0x7f2b6c9c0000，别人的程序里也是差不多的地址，两者互不冲突，因为背后的物理页不同。

地址看起来不连续。/proc/self/maps 里一段一段的映射之间有大片空洞，那是没映射的区域。堆和栈之间隔着共享库，共享库之间也隔着空洞。程序不需要连续的内存，只需要「我要的这块是连续的」。

共享库能省内存。十个进程都用 libc.so.6，每个进程的地址空间里都有一段映射指向它，但物理内存里只有一份代码页。只读的代码页被十个进程共享，可写的数据页各有一份。

缺页：地址第一次被碰 #

虚拟地址映射好了，物理页还没有。内核按需分配：malloc 只是登记，第一次读写某个页时才真正给物理页。

min_flt 是次要缺页，页已在内存里，只要补一条映射。maj_flt 是主要缺页，得从磁盘读，比如加载代码段、访问被换出的页。第一次跑一个程序时的启动延迟，大部分花在 maj_flt 上。用 grep -E "min_flt|maj_flt" /proc/self/stat 和 ps -o pid,vsz,rss,comm -p $$ 都能看到这两组数字。

这也解释了一个常见困惑：malloc 了 1GB，RSS 却没涨，因为那些页还没被碰过，一页物理内存都没发。

指标 含义 你该关心什么
VSZ 虚拟内存大小 映射了多大的地址空间 大不代表占内存，只是映射占位
RSS 常驻集大小 真正占了物理内存的部分 这才是内存压力来源
min_flt 次要缺页次数 大量出现说明页在反复映射
maj_flt 主要缺页次数 大量出现说明 IO 是瓶颈

VSZ 和 RSS 差得远是正常的。看到 VSZ 几个 GB 不用慌，看 RSS。

九、从虚拟地址到物理地址 #

翻译这件事由 MMU 做，按页为单位。x86-64 上一页 4KB，虚拟地址被拆成「页号 + 页内偏移」，页号去映射表里查，查到的物理页号再拼上原来的偏移。

多级页表是为了省空间：128TB 的地址空间里进程实际用到的只有零散几块，建一级大表就浪费了。多级结构让未使用的区域连表项都不用建。细节属于内核篇，你只需要知道结果：一次翻译要访问好几级表，所以 MMU 里有 TLB 缓存最近的翻译结果。TLB 命中就一次搞定，未命中要走完整流程，这也是随机访问大数组比顺序访问慢的原因之一。

/proc/self/maps 里每一行就是一个虚拟内存区域（VMA）。VMA 是内核记账的单位，描述一段连续的、权限相同的地址范围。你看到的 r-xp、rw-p 就是这一段的属性。

bash
head -20 /proc/self/maps

翻这张表能看出几件事。可执行文件被拆成好几段映射，代码段 r-xp、只读数据 r--p、可写数据 rw-p，同一段不会既可写又可执行，这是 W^X 策略。堆只有一行 [heap]，所有小块 malloc 都在里面。栈一行 [stack]，是主线程的。大块 malloc 不在 [heap] 里，而是单独一行匿名映射，路径列空着，设备号 00:00。共享库每个 .so 占好几行。

想知道某个具体地址属于哪一段，把这个函数塞进程序里查：

c
void show_maps_for(void *addr) {
    FILE *f = fopen("/proc/self/maps", "r");
    if (!f) {
        return;
    }
    char line[512];
    unsigned long start, end;
    while (fgets(line, sizeof(line), f)) {
        if (sscanf(line, "%lx-%lx", &start, &end) == 2
            && (unsigned long)addr >= start && (unsigned long)addr < end) {
            printf("%p -> %s", addr, line);
            break;
        }
    }
    fclose(f);
}

传 &local 和 malloc 返回值进去，各自归属的区域和权限串一目了然。排查「这个指针到底指向谁的地盘」时很好用。

物理地址的边界 #

进程能不能知道自己的物理地址？理论上能通过 /proc/self/pagemap，但那需要 root 权限，内核出于安全考虑对普通用户做了屏蔽。这不是该依赖的手段。你唯一需要建立的直觉是：虚拟地址连续不代表物理地址连续，也不代表内存真的存在。内核会做页面回收、迁移、合并，同一个虚拟页在不同时刻落到不同物理页。任何「地址就是内存位置」的假设都是错的。

十、mmap 与文件映射 #

mmap 把一段虚拟地址和某个对象绑起来，对象可以是文件，也可以是匿名内存。POSIX.1-2008 的接口：

c
#include <sys/mman.h>

void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);
int munmap(void *addr, size_t length);
  • addr：建议起始地址，传 NULL 让内核选，最常用。
  • length：映射字节数，内核按页大小向上取整。
  • prot：权限，PROT_READ、PROT_WRITE、PROT_EXEC、PROT_NONE 的组合。
  • flags：MAP_SHARED 或 MAP_PRIVATE 二选一，再加 MAP_ANONYMOUS、MAP_FIXED 之类的修饰。
  • fd：文件描述符，匿名映射传 -1。
  • offset：文件内偏移，必须是页大小的整数倍。
组合 含义 典型用途
PROT_READ + MAP_PRIVATE 只读私有映射 读文件，改动不影响原文件
PROT_READ|PROT_WRITE + MAP_SHARED 读写共享映射 多进程共享内存、改文件
PROT_READ|PROT_WRITE + MAP_PRIVATE 读写私有，写时复制 加载后各自修改
匿名 + MAP_PRIVATE 匿名私有内存 大块 malloc 的底层实现
PROT_NONE 完全禁止访问 守护页，抓越界

读大文件时 read 要把数据从内核页缓存拷到你的缓冲区，mmap 不用拷，直接把文件页映射进地址空间：

c
int fd = open(argv[1], O_RDONLY);
struct stat st;
fstat(fd, &st);
size_t len = (size_t)st.st_size;

char *data = mmap(NULL, len, PROT_READ, MAP_PRIVATE, fd, 0);
if (data == MAP_FAILED) {
    perror("mmap");
    return 1;
}
close(fd);                          /* 映射建立后 fd 可以关 */
for (size_t i = 0; i < len; i++) {
    if (data[i] == '\n') { /* 计行 */ }
}
munmap(data, len);

四个要点：mmap 失败返回 MAP_FAILED（(void *)-1）而不是 NULL，这是最常见的判断错误；映射建立后 close(fd) 不影响映射；访问超出文件末尾的页收到 SIGBUS 而非 SIGSEGV；文件被别的进程截断时，访问已映射区同样收到 SIGBUS。

把 MAP_PRIVATE 换成 MAP_SHARED 并配 MAP_ANONYMOUS，这块内存就能在 fork 出的父子进程之间共享，这是进程间共享大块数据最直接的方式，没有拷贝：

c
char *p = mmap(NULL, len, PROT_READ | PROT_WRITE,
               MAP_SHARED | MAP_ANONYMOUS, -1, 0);
if (fork() == 0) {
    strcpy(p, "来自子进程");
    _exit(0);
}
wait(NULL);
printf("%s\n", p);   /* 父进程能读到 */

MAP_SHARED 加文件就是持久化的共享内存，改完用 msync 刷盘。MAP_PRIVATE 加文件则是写时复制，改了只影响自己，不写回文件。

mmap 不是万能加速器。小文件顺序读一次，建立映射的成本反而更高；大文件随机访问、或者需要跨进程共享，它才划算。32 位系统映射不了超过地址空间的文件，只能分段读。

十一、常见的内存错误 #

C 的内存错误就那么几类，反复出现。认全了，调试时间能省一大半。

错误 表现 根因 正确做法
解引用空指针 立刻 SIGSEGV 没检查返回值或忘记初始化 分配后判 NULL，指针初始化为 NULL
悬空指针 随机崩溃或数据错乱 返回局部变量地址，或 free 后继续用 返回堆内存，free 后置空
改只读区 SIGSEGV 对字符串字面量写入 用字符数组 char s[] = "..."
缓冲区越界 覆盖相邻数据，金丝雀报警 strcpy / sprintf 无长度限制 用 snprintf，检查长度
双重释放 堆结构损坏，abort 两条路径都 free 同一个指针 释放后置空，理清所有权
用已释放内存 数据莫名改变 free 后还留着指针 置空，或用 ASan 抓
内存泄漏 RSS 持续上涨 异常分支漏了 free，或指针被覆盖 单一出口，统一释放
形参传值改不了实参 实参仍为 NULL 只改了形参副本 传 char ** 或用返回值
对齐不符 某些架构上 SIGBUS 强制转换未对齐指针 用 memcpy 或保证对齐
无符号回绕 malloc 返回 NULL 或崩溃 size 由减法得到负数 计算前检查上界

四个高频的展开。

返回栈地址：函数一返回，局部数组所在的栈帧就失效了，调用者拿到的是悬空地址。改成 malloc 并把 free 的责任写进接口文档。

c
char *get_memory_bad(void) {
    char p[] = "hello world!";   /* 数组在栈上 */
    return p;                    /* 函数返回，栈帧销毁 */
}

改字符串字面量：字面量在 .rodata，只读。改成数组就有了一份可写副本。指针和数组在这里的差别不是风格问题，是内存归属问题：

c
char *s = "hello";
s[0] = 'H';    /* 段错误 */

char t[] = "hello";
t[0] = 'H';    /* 正常，t 有自己的可写内存 */

形参传值：C 只有值传递，形参是实参的一份拷贝。改形参不影响实参，还会顺手泄漏掉刚申请的那块。传二级指针，或者用返回值，别指望改形参。

c
void get_memory_param(char *p) {
    p = malloc(100);   /* 只改了副本，实参仍为 NULL，这 100 字节泄漏 */
}

缓冲区溢出与栈金丝雀：char buffer[8] 里写 24 字节，多出来的 16 字节覆盖保存的 rbp 和返回地址。攻击者控制返回地址就能改变执行流，这就是栈溢出攻击。

现代 GCC 默认开 -fstack-protector-strong，在局部数组和返回地址之间插一个随机值。函数返回前校验，变了就调用 __stack_chk_fail：

text
*** stack smashing detected ***: terminated

程序直接死，而不是跳到攻击者构造的地址。这不能防溢出，只能阻止溢出被利用。真正该做的是别写出越界的代码。-D_FORTIFY_SOURCE=2 能让 strcpy、sprintf 在编译期检查目标大小，拦住一部分常量可算的越界。

十二、内存泄漏与工具 #

泄漏的定义：程序不再持有某块内存的引用，但也没有 free 它。这块内存到进程退出前一直占着。

c
void make_leak(void) {
    int *array = malloc(10 * sizeof(int));   /* 函数退出，指针没了，块还在 */
}

短命进程泄漏无所谓，退出时全还给系统。长期运行的服务泄漏就是事故：RSS 一直涨，最后被 OOM killer 干掉。最麻烦的是缓慢泄漏，一天涨几百 MB，压测看不出来，线上跑一周才炸。

Valgrind #

bash
gcc -g leak_app.c -o leak_app
valgrind --tool=memcheck --leak-check=full ./leak_app

-g 必须加，否则报错里只有地址没有行号。

text
==12345== 40 bytes in 1 blocks are definitely lost in loss record 1 of 1
==12345==    at 0x4C29F73: malloc (vg_replace_malloc.c:309)
==12345==    by 0x40052D: make_leak (leak_app.c:4)
==12345==    by 0x40053E: main (leak_app.c:9)
==12345== LEAK SUMMARY: definitely lost: 40 bytes in 1 blocks

两个数字最有用：definitely lost 是确定丢了、没有任何指针指向它；make_leak (leak_app.c:4) 直接告诉你泄漏发生在第 4 行的 malloc。

分类 含义 严重程度
definitely lost 没有任何可达指针 真泄漏，必修
indirectly lost 被另一个泄漏的结构持有 真泄漏，跟着一起修
possibly lost 有指针指向块内部而非头部 多半是问题，要查
still reachable 全局变量或栈上还有指针 进程退出才释放，多数可接受

代价是慢，程序跑得慢二三十倍，只适合单元测试和小用例。

AddressSanitizer #

ASan 是编译器插桩，慢两倍左右，可以直接挂在测试流水线里。

bash
gcc -fsanitize=address -g buffer_overflow.c -o buffer_overflow
./buffer_overflow

原理是影子内存：每 8 字节程序内存对应 1 字节影子内存，影子值记录这 8 字节里有几个是合法的。0 表示 8 字节全可访问，1 到 7 表示前 N 字节可访问，负数表示整块被隔离（已释放或越界）。每次内存访问前插一段检查，查影子值。

ASan 抓的错误比 Valgrind 更全也更快：堆越界、栈越界、全局越界、use-after-free、double-free、内存泄漏。报错直接给源码行号和分配、释放的调用栈。开泄漏检测用 ASAN_OPTIONS=detect_leaks=1 ./app，想连未定义行为一起抓就编 -fsanitize=address,undefined。

GDB #

有些崩溃只在生产环境的特定输入下出现，你手上只有 core dump。

text
(gdb) run              # 跑到崩溃
(gdb) backtrace        # 看调用栈
(gdb) frame 1          # 切到第 1 帧
(gdb) info frame       # 看这一帧的 rbp、rsp、返回地址
(gdb) info locals      # 看局部变量
(gdb) x/16xb &buffer   # 从 &buffer 起 dump 16 个字节

x/16xb 的意思是「从 &buffer 开始，显示 16 个字节，十六进制」。看越界写了什么、覆盖到哪个位置，一目了然。生产环境一般关着 core dump（占磁盘），排查时临时 ulimit -c unlimited 打开，抓完就关。

十三、内存对齐与结构体布局 #

CPU 读内存不是一个字节一个字节读的，它按字长整块读。32 位机器一次读 4 字节，64 位一次读 8 字节。一个 int 横跨两个 4 字节块时，CPU 要么发两次总线请求再拼接，要么直接报错。所以编译器主动加填充，让每个成员都落在自己大小的整数倍地址上。

c
struct DefaultStruct {
    char a;    /* 偏移 0，占 1 字节 */
               /* 偏移 1-3，填充 3 字节 */
    int  b;    /* 偏移 4，占 4 字节 */
    char c;    /* 偏移 8，占 1 字节 */
               /* 偏移 9-11，填充 3 字节 */
};             /* 总大小 12，是最大成员 4 的倍数 */

#pragma pack(1)
struct CompactStruct { char a; int b; char c; };   /* 6 字节 */
#pragma pack()

struct Bad  { char a; int b; char c; double d; };  /* 24 字节 */
struct Good { double d; int b; char a; char c; };  /* 16 字节 */

三条规则记住就够：每个成员的偏移必须是它自身大小的整数倍；结构体总大小必须是最大对齐值的整数倍，末尾补填充；嵌套结构体按内部最大对齐值参与前两条。查偏移用 <stddef.h> 里的 offsetof(struct DefaultStruct, b)，不用自己拿地址相减。

Bad 和 Good 成员完全一样，只换了顺序就从 24 降到 16。原则是按对齐值从大到小排。#pragma pack(1) 能强行压到 6，用在网络协议封包、串口传输、文件头上，这些场景多一个填充就多传一个字节。

类型 大小 对齐（x86-64） 备注
char 1 1 永远不填充
short 2 2
int 4 4
long 8 8 LP64 模型
float 4 4
double 8 8
指针 8 8 32 位下为 4
long double 16 16 x86-64 上占 16 字节

这些是 ABI 规定，不是 C 标准规定。标准只说「对齐由实现定义」，换到 ARM 或 RISC-V 上某些值会变。

#pragma pack(1) 的代价真实存在：取 int 成员时编译器不能生成一条对齐的取指，只能按字节读四次再拼。某些架构上访问未对齐地址直接触发异常。跨平台代码里更安全的做法是不动结构体布局，改用显式序列化，字节序和对齐都由你控制。

malloc 返回的地址保证适合任何基本类型（max_align_t），但指针算术之后就不保证了：

c
char *buf = malloc(1024);
int *p = (int *)(buf + 1);   /* 未对齐，某些架构上崩 */

int v;
memcpy(&v, buf + 1, sizeof(v));   /* 正确，编译器会优化成合适指令 */

类型双关也一样。把 float 的内存当 uint32_t 读，用 memcpy 或 union，别用指针强转，那是严格别名规则的违规，-O2 下会优化出错。

十四、易错点速查 #

把这一篇的坑压缩成一张表，写代码卡住时先扫一眼。

场景 错误写法 正确写法 后果
检查 mmap if (p == NULL) if (p == MAP_FAILED) 漏判失败
检查 malloc 直接用返回值 先判 NULL 空指针崩溃
free 之后 继续用指针 free(p); p = NULL; UAF / 双重释放
realloc p = realloc(p, n) 用临时变量接 失败时原块泄漏
返回字符串 return local_array; malloc 或传缓冲区 悬空指针
改字面量 char *s = "abc"; s[0]='x'; char s[] = "abc"; 段错误
拷字符串 strcpy(dst, src); snprintf(dst, n, "%s", src) 缓冲区溢出
传指针改实参 void f(char *p) void f(char **p) 或返回值 实参不变

结构体比较 memcmp(&a, &b, sizeof(a)) 逐字段比 填充字节内容不定
取成员偏移 (char*)&s.b - (char*)&s offsetof(struct S, b) 手算出错
数组参数取大小 函数内 sizeof(arr) 传长度一起给 得到指针大小
无符号减法 malloc(n - 1)，n 为 0 先判 n > 0 申请 4GB 失败

跨模块所有权 文档没写谁释放 明确约定 泄漏或双重释放
多线程静态变量 static int sum; _Thread_local 或加锁 数据竞争

再补五条不进表的经验。

给所有内部函数和模块级全局变量加 static。它把符号从全局符号表里隐藏，别人引用不到，等于免费拿到了封装。

分配和释放写在同一层。谁 malloc，谁 free。中间隔了三层函数调用，就一定有人在某个 if 分支里漏掉。接口要么返回完整的对象，要么接受调用者提供的缓冲区，别搞半所有权。

所有异常分支走同一个出口，这是防泄漏最土也最管用的办法：

c
int process(void) {
    char *a = malloc(100);
    char *b = malloc(200);
    int ret = -1;
    if (!a || !b) {
        goto out;
    }
    if (do_something(a, b) < 0) {
        goto out;
    }
    ret = 0;
out:
    free(a);
    free(b);
    return ret;
}

goto 在这里是正确用法。C 里没有析构函数，单一出口加集中释放是最不容易漏的写法。

sizeof 只在数组还在作用域内时才对。数组作为参数传给函数立刻退化成指针，函数里 sizeof(arr) 得到的是 8。

栈上不要放超过 10KB 的东西。这条不是教条，是踩过坑之后的经验值。真需要大缓冲区，用 malloc，用完 free，成本远小于一次爆栈事故。
