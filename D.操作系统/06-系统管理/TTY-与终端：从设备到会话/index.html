一、终端是什么：从电传打字机到现在 #

TTY 是 TeleTYpe 的缩写，直译就是电传打字机。拆开看：tele 指距离远、靠电信号传；type 指打字或印字的机构。合起来就是「打字和印字的机构隔着电线」。要理解这个词得回到电报时代——把 message 编成摩斯码，发端操作员敲出长长短短的 tone，收端坐一个操作员听 tone 还原 message。这种方式得专门训练才能上岗，挡住了多数人交换信息的念头。于是 teletype 被造出来。它由键盘模组、收发信息模组、字符打印模组构成，有些模组是纯机械的。发 message 时不停按字符键，字符自动送上电线；收 message 时接收器自动收下对端字符并打印。计算机出现得比 teletype 晚，而它自带键盘和 printer，正好顶上，早期机器直接拿它当终端。有些型号还支持穿孔纸带当输入或输出。往后走，印字机构和穿孔机构被显示器取代。

teletype 搬进计算机系统之后，tty 这个词已经不准了：它不再承担通信功能，只是一个计算机系统的输入输出设备，也就是 computer terminal。所以今天说终端，比说 tty 更贴切。这套东西后来被淘汰了。早年学计算机的人用的是 DEC VAX 这类大型机，一台机器接出三十多个终端，每人一个。终端收键盘输入，通过串行通信送给 VAX，VAX 处理完把输出回送，显示在各人的屏幕上。那时的终端都是 text terminal，主机和终端之间走字符流。进到微机时代，每台机器自带显示设备和键盘。图形显示器画的是点阵，不是字符；LCD 和键盘也不走慢速串口连主 CPU。按这个标准，今天你手边没有一个是真正的终端设备，准确叫法是「终端仿真设备」。Windows 里开个窗口加键盘，登本机或登远程主机，这就是仿真。终端到底在干什么？两件事：

  • 输入（input），向计算机发送指令；
  • 输出（output），计算机把执行结果显示出来。

这里有个前提要钉死：输入和输出都是针对计算机而言的。计算机本身没有输入输出的自主意识，所以人机交互实际是人和一个个软件在交互，不是人和铁壳子交涉。以 Linux 为例，这条链是这样铺开的：

  1. 内核通过控制台终端输出日志（printk）；
  2. 内核起来之后，init 进程打开控制台终端，开始和人打交道；
  3. 随后 getty 打开任意一个终端设备，等你登录；
  4. 登录成功，getty 把终端控制权交给 shell，你和 bash 对话；
  5. 你在 shell 里再起别的应用，比如地图程序，它自己去打开另一个 TTY 设备（GPS 的 UART）读写数据。这一步已经不是人机交互，是机机交互，所谓「人机」只是站在人的视角说话。

二、终端设备文件的家族 #

按输入输出设备的形态分几类，每一类在 /dev 下都有自己的落脚点。

1、控制台终端（console） #

输入设备是键盘，输出设备是显示器，两者通过各类总线直接连到计算机。「终端」在这里是这些设备的一个逻辑抽象。

2、虚拟终端（VT） #

控制台的显示器只有一个，同一时刻只能被一个应用独占。但多任务环境里，你希望在把终端让给下一个应用之前保住当前应用的输出，回头还能看。于是 Unix/Linux 在控制台之上虚拟出若干终端。不同应用在各自的虚拟终端上独立输出，需要时用组合键把某一个调到屏幕上。

3、串口终端（真正的 TTY） #

这是正牌 TTY 设备。输入设备和输出设备集成在一个独立硬件里，该硬件通过串口连计算机。

  • 键盘的输入动作，转成串口上的 RX 数据包（以计算机为视角）送进来；
  • 计算机的输出以 TX 数据包发出去，TTY 设备转换后显示在自己的屏幕上。

4、软件终端 #

今天最常用的就是这一类。既然人机交互的数据流能封装后走串口，终端设备的形式就不受限了：只要能收用户输入并发给计算机、能收计算机的输出并显示，任何设备都能当终端，比如另一台计算机。拿另一台计算机当终端时，不会把它的资源全砸进去做交互。常见做法是在这台机器上跑一个软件，模拟出一个「终端设备」。这个软件像中间商：从键盘收输入，控制串口发给对端；从串口收对端的输出，在自己的界面上显示。PuTTY、SecureCRT、Windows 超级终端，都是软件终端。

5、USB、网络等终端 #

串口能当传输媒介，USB、Ethernet 一样能。原理和串口终端完全一样，换个承载而已。

6、图形终端 #

上面几类的输出界面都是字符界面。GUI 起来之后成了主流，通过 GUI 交互的形态也可以叫图形终端。但 TTY 的势力范围只覆盖字符界面，图形终端不在本篇范围内。

7、设备号地图 #

字符设备主设备号 4 是 TTY devices 的总入口，次设备号按用途切段：0～63 归虚拟终端，64 往后归串口。USB 串口走 188（主机侧）和 127（gadget 侧）。

         1 = /dev/ttyGS1      Second USB serial converter

三、/dev/tty、/dev/pts/N 与 /dev/console #

三个名字长得像，作用完全不同，混起来就会写出诡异的东西。

1、/dev/console #

内核启动后期，kernel_init 线程（最后退化成 init 进程）要打开控制台终端。但控制台终端的类型和名字五花八门：/dev/ttyS0、/dev/ttyUSB0、某个 VT，都算。内核核心代码怎么无视这些差异？答案就是 /dev/console，设备号固定 (5, 1)。init 线程打开它时，TTY core 会去问 system console core：哪一个终端适合当控制台？最终打开的是那个具体设备。/dev/console 本身只是个占位坑，是个转接头。控制台的选定规则：

  1. 可以同时注册多个 console driver，有选择地用；
  2. 启动时通过命令行（或 device tree）指定，例如 console=/dev/ttyS0、console=/dev/ttyUSB0；
  3. 内核日志可以在所有被选中的控制台终端上同时输出；
  4. 能拿来做交互的控制台终端只有一个，也就是后指定的那个。

系统控制台有两个特殊身份：支持 single user mode 登录，接收内核的日志和告警。桌面系统把系统控制台设成某个虚拟终端（一般是 /dev/tty0），这样能在 VT 上看到内核 message。嵌入式环境则设成串口或 USB 串口。

2、/dev/tty #

/dev/tty 的设备号是 (5, 0)，代表当前进程的控制终端。它不是一个固定设备，是个每进程解析的别名：同一个 /dev/tty，在不同进程里打开，落到不同的真实设备上。什么时候用它？程序的标准输入输出被重定向了，但仍然想直接和用户对话——比如 ssh 读密码、git 开编辑器、sudo 问口令。打开 /dev/tty 就绕过了重定向。

bash
$ echo "pw" | sudo -S whoami      # 走标准输入
$ sudo -S whoami < /dev/tty       # 走控制终端

/dev/tty 的作用和 /dev/console 类似，都是中转：进程可以通过 TTY core 提供的 ioctl 选择控制终端对应的真实设备。

3、/dev/pts/N #

伪终端的从设备端。每开一个终端窗口或每建一条 ssh 连接就多一个编号。/dev/pts 是 devpts 文件系统的挂载点，节点由内核动态生成，连接断了就消失。在 xterm 里敲 tty，看到的是 /dev/pts/3 这种；在 VT 里敲，看到的是 /dev/tty1。

4、三者的选择 #

你想要的 用哪个 为什么
和当前用户直接对话，绕过重定向 /dev/tty 绑定进程的控制终端
不管谁调用，都打到系统控制台 /dev/console 由内核路由到选定的控制台
明确指定某个终端窗口 /dev/pts/N 直接指向那一路 pty
在某个 VT 上输出 /dev/ttyN 直接指向那个虚拟终端

四、虚拟终端与伪终端 #

1、虚拟终端 #

虚拟终端是虚拟出来的终端，不对应具体设备。应用打开某一个虚拟终端和人交互，对它而言和物理终端没有任何区别——应用也分不出。对整个系统来说，键盘和屏幕只有一套，同一时刻只能和一个虚拟终端对接，各 VT 轮流占用物理资源。既然没有物理终端，VT 就碰不到硬件，它要操作 display 和 keyboard，必须走 framebuffer 驱动和 keyboard driver。

Linux 内核支持 64 个虚拟终端，tty1～tty63 加上 tty0。发行版默认启动时开 6 个，Alt+F1～Alt+F6 切换，Alt+F7 进图形界面。进了桌面环境，用 Ctrl+Alt+Fx 切回字符界面的 VT。次设备号 0 的 tty0 特殊，代表当前的虚拟控制台。不开 GUI 时 tty0 默认指向 tty1，之后随用户动作切换。无论如何，tty0 永远指向当前那个 virtual terminal。内核支持 64 个，不代表你的系统真开了 64 个，得看配置。

bash
$ ls /dev/tty[0-9]*                   # 实际存在的 VT
$ cat /sys/class/tty/console/active   # 当前激活的控制台

2、伪终端（pty） #

串口能当终端和计算机之间的通道，Ethernet 也能。但这里有个卡点：Linux 的网络驱动不以 TTY 形式提供 API，网络走的是 socket。应用程序没法直接打开网络设备，再和对应的终端设备通信。解法是伪终端，Pseudo Terminal，简称 pty。字面上看它根本不是终端（虚拟终端好歹还算），它是为了让应用能从网络这类非串口接口上和终端设备交互而伪造出来的东西。pty 分两半：

  • pts（pseudo-terminal slave），伪终端从设备。它伪造出一个标准 TTY 设备，应用可以直接访问。应用往 pts 写的数据直接反映到 ptm 上；应用从 pts 读，相当于直接从 ptm 读。
  • ptm（pseudo-terminal master），伪终端主设备。实现看场景：要走网络，ptm 就打开对应 socket，把 pts 写来的数据从 socket 送出，把从 socket 收到的数据送回 pts。有了 pty，终端设备就能脱离物理限制，可以是任何形态。

3、终端窗口里的 shell #

在 GUI 里开一个 xterm：

  1. xterm 生成一对 pts 和 ptm，同时执行 shell；
  2. xterm 把 pts 交给 shell，shell 分不清真假，以为是个标准 TTY 设备，照常跑；
  3. shell 从 pts 读等于从 ptm 读，往 pts 写等于往 ptm 写，这一层由 TTY framework 自动完成；
  4. 另一端，xterm 从 ptm 读数据（实际是 shell 通过 pts 写出来的）显示在窗口上，同时从窗口收输入，经 pty 转给 shell。

窗口进程不直接开 display 加 keyboard，是因为整个屏幕和键盘都在视窗管理进程手里。用户开多个窗口，每个窗口是一个进程。视窗管理进程从键盘收到字符，送给获得焦点的窗口进程，窗口进程再送往与它配对的 ptm。键盘输入这一路，视窗管理进程干的是中转和分发。和 shell 通过 pty 连接的，不一定是终端窗口进程，换成网络服务进程就是网络终端登录：

text
sshd ──open /dev/ptmx──► ptm  ══ pty pair ══  pts ──► shell 的 stdin/stdout/stderr

sshd 打开 /dev/ptmx 拿到 ptm，同时得到一个 /dev/pts/N 作为从设备，把从设备的 fd 0/1/2 交给 shell。之后 ssh 客户端发来的字节写进 ptm，shell 就在 pts 上读到；shell 输出写进 pts，sshd 从 ptm 读出来发回客户端。

4、两条要点 #

  • pty 是成对的，缺一半不能用：没有 ptm 就没人喂数据给 pts，shell 会一直等。
  • 从设备数量由 /dev/pts 的挂载参数限制，ptmxmode、max 之类写在 /etc/fstab 或 systemd 的 devpts 挂载单元里。容器里 pts 不够用，就是这个参数压得低。

五、控制终端 #

讲控制终端绕不开 Job control。Job control 是 Unix/Linux shell 里的概念——shell 就是个普通应用，它借这套机制管理自己拉起来的活。先把三层关系摆平：

  1. job control 是 shell 用来管理、控制 jobs 的方法；
  2. job 是进程组在 shell 里的体现，shell 借用进程组实现 job；
  3. 进程组是多个进程的组合。

在这之上，控制终端（control terminal）的定义是：和某个 session 关联的那个终端。几条硬规则：

  • 一个 session 可以有一个控制终端，不能有多个，也可以一个都没有；
  • 一个终端只能和一个 session 对应，不能同时挂两个；
  • 建立与控制终端连接的那个 session 首进程（session leader）叫控制进程（controlling process）。

controlling process 这个概念的存在理由很具体：终端断开时（网络登录场景下网线被拔），终端驱动要把 hangup 信号送给对应 session 的控制进程。这一条是第九章的伏笔。控制终端怎么来的？两层机制：

隐式。创建 session 时往往没有控制终端。之后 session leader open() 了一个终端设备，只要没带 O_NOCTTY，这个终端就成为该 session 的控制终端。前提是这个终端不属于别的 session，否则一个终端对上两个 session，拓扑就烂了。一旦有了控制终端，session leader 的子进程全部继承它。

显式。程序可以用 ioctl 指定：TIOCSCTTY 设上，TIOCNOTTY 解除——解除之后该终端退回成普通终端。

对于 login session，session leader 建立和终端的连接，并把标准输入、输出、错误都定向到该终端。所以后面用 shell 跑的普通程序不用直接访问控制终端，读写标准输入输出就够了。确实需要（标准输入输出被重定向了）才去打开 /dev/tty。后台应用想输入输出还有一层拦截：读写控制终端时，TTY core 会给后台应用发 SIGTTIN（读）或 SIGTTOU（写），这会终止该后台应用。不过 shell 会重设收到 SIGTTOU 时的行为，所以后台应用写出来的内容能通过控制终端显示出来。

六、会话与进程组 #

1、进程组 #

进程组是一组进程的集合。不会无缘无故把它们捆一起，捆起来是因为有共同点：同属一个 job，来自终端的信号要能送达这个组里的每一个成员。也可以用 killpg 向整个进程组发信号。任何进程都不是独立存在的，一定属于某个进程组。fork() 之后，子进程归入创建者所在的进程组；父进程可以在子进程 exec() 之前给子进程设定进程组。拿 shell 举例。shell 在进程组 A 里，用户敲了 aaa：

  • 不带 &：shell 创建 aaa 进程，此时它还在进程组 A。exec aaa 之前，shell 把它挪进一个新的前台进程组，自己退到幕后。
  • 带 &：过程一样，区别是 shell 保持在前台进程组。

很多人以为 shell 能同时跑一个前台进程加任意多个后台进程。不是。shell 是以进程组为单位控制前后台的。一条命令行里的多个命令通过管道连起来，它们构成一个进程组：

bash
proc1 | proc2 &
proc3 | proc4 | proc5

第一行 shell 新建一个后台进程组，创建 proc1 和 proc2 放进去，这个组不能访问终端。第二行 shell 创建 proc3、proc4、proc5，放进新建的前台进程组，这个组可以访问终端。进程组怎么标识？借进程 ID。任何一个进程组都有第一个加入者，它是这个组的创始者，叫进程组的 leader，也就是进程 ID 等于进程组 ID 的那个进程。用 leader 的进程 ID 当进程组的 ID。leader 退了，进程组不一定消失。组的生命周期持续到组里最后一个进程终止，或者最后一个进程加入别的组为止。

2、会话 #

字面上，session 是用户和计算机之间的一次对话。你想用计算机资源，得开个会：参会双方是用户和计算机，你把需求告诉它，它把结果返回你，一来一往直到散会。用户通过终端设备和计算机交互，代表计算机跟你交互的是 shell 进程。每次发生这种交互过程，系统就创建一个 session 来管理。如果支持 job control，一次 session 里可以并行跑多个 job，而 job 就是进程组的抽象。所以：session 是进程组的容器，里面装一个前台进程组（只能有一个）和若干个后台进程组。没有控制终端的情况下，session 也可以没有前台进程组，只由若干后台进程组组成。创建 session 的场景有两个：

  1. 一次登录形成一个 session，叫 login session，绝大多数场景说的是这个；
  2. 系统 daemon 进程待在各自的 session 里，叫 daemon session。

两个场景都通过 setsid() 建立新 session。规矩是：调用 setsid() 的进程不能是进程组的 leader。为什么有这条限制？假设没有。进程组 leader（组 ID 等于 A）通过 setsid() 把自己塞进新建的 session。有了 session 就得有进程组，创建 session 的这个 leader 自然成为新 session 里第一个进程组的 leader，标识新组的 ID 还是 A。可旧 session 里仍有进程组成员，旧 session 里也仍有进程组 A。于是进程组 A 的成员一部分在新 session、一部分在旧 session，破坏了 session 与进程组的两级拓扑。

为满足这个要求，常规套路是：先 fork()，让父进程退出，子进程执行 setsid()。fork() 出来的子进程不会是进程组 leader，条件天然满足。

c
pid_t pid = fork();
if (pid < 0) {
    perror("fork");
    exit(1);
}
if (pid > 0) {
    exit(0);        /* 父进程退出，子进程被 init 收养 */
}
setsid();           /* 此时子进程不是组长，调用成功 */

setsid() 建了新 session，同时也建了新进程组，创建 session 的那个进程 ID 被用来标识这个新进程组。新建的 session 没有控制终端；如果调用 setsid() 的进程原本有控制终端，调用之后新 session 和那个终端就断了关系。

3、两级拓扑 #

关系摊平就是四层：

text
终端设备 (/dev/pts/3)
   └── session  (sid = 1200, leader = bash)
          ├── 前台进程组 (pgid = 1200, leader = bash)
          │      └── bash
          └── 后台进程组 (pgid = 1240, leader = tar)
                 └── tar
  • 一个进程属于且仅属于一个进程组；
  • 一个进程组属于且仅属于一个 session；
  • 一个 session 至多挂一个控制终端，一个终端至多挂一个 session。

七、进程组 ID 与会话 ID #

  • PGID（process group ID）：等于该组 leader 的 PID。用 getpgid() 取一个进程的 PGID，用 setpgid() 加入或新建进程组。
  • SID（session ID）：等于该 session 首进程的 PID。用 getsid() 取。

setpgid() 有几条限制，写代码容易踩：

  1. 一个进程只能控制自己或自己子进程的进程组；
  2. 子进程 exec() 之后，父进程就不能再用 setpgid() 动它的进程组；
  3. 调用 setpgid() 的进程、被设组的进程、以及目标进程组，必须在同一个 session 里；
  4. 按 POSIX，不能修改 session leader 的进程组 ID。

看一张表比看文档快：

bash
$ ps -eo pid,ppid,pgid,sid,tty,stat,comm
  PID  PPID  PGID   SID TT       STAT COMMAND
 1200  1195  1200  1200 pts/3    Ss   bash
 1245  1200  1245  1200 pts/3    S+   vim
 1260  1200  1260  1200 pts/3    S    tar

读法：vim 的 PGID 是 1245，和 SID 1200 不同，说明它在前台进程组里但没当上 session leader；tar 的 PGID 是 1260，是另一个进程组，也就是后台 job。三个进程的 SID 都是 1200，共享同一个 session 和同一个控制终端 pts/3。STAT 那列也有信息：Ss 的 s 表示 session leader，S+ 的 + 表示在前台进程组。开机时的样子值得看一眼。swapper 进程（也叫 idle 进程）在建内核线程，所有内核线程都在一个 session 里、属于一个进程组，PID 从 2 开始往上递增。PID 1 留给 init，它是内核空间转用户空间的接口。init 起初继承 swapper 的 SID 和 PGID，启动过程中调用 setsid()，建出新的 session 和进程组。关系对照表：

概念 标识 由谁决定 一个进程能有几个 一个容器能装几个
进程 PID 内核分配 1 —
进程组 PGID = leader 的 PID setpgid() / setsid() 1 若干进程
会话 SID = leader 的 PID setsid() 1 若干进程组
控制终端 设备号 open() 或 TIOCSCTTY 0 或 1 至多 1 个 session

一次登录的完整过程 #

把 getty 到 shell 这一段走一遍，前面那些概念就都落地了。

  1. init 按 /etc/inittab 配置 fork 并 exec getty。传统写法：

    text
    1:2345:respawn:/sbin/getty 38400 tty1
2:23:respawn:/sbin/getty 38400 tty2
3:23:respawn:/sbin/getty 38400 tty3
4:23:respawn:/sbin/getty 38400 tty4
5:23:respawn:/sbin/getty 38400 tty5
6:23:respawn:/sbin/getty 38400 tty6

    用 systemd 的系统没有 inittab，对应的是 getty@tty1.service 这种模板单元，概念一样。

  2. getty 是普通进程，既不是 session leader 也不是进程组 leader。它调用 setsid() 建新的 session 和进程组，然后打开作为参数传给它的终端设备（这里是 tty1）。于是 tty1 成了这个 session 的控制终端，getty 成了 controlling process。打开成功后 fd 0、1、2 都定向到该终端。

  3. getty 通过标准输出打出 login: 提示。用户输入用户名后，getty 完成历史使命，exec 加载 login 程序，PID、PGID、SID 全都不变。

  4. login 做鉴权。失败就退出，父进程 init 侦听这个事件并重新拉 getty（respawn 的由来）。成功就 fork 子进程并 exec shell。

  5. 刚起来时，login 和 shell 属于同一个 session、同一个前台进程组，共享同一个虚拟终端，两个进程的控制终端都指向那个登录终端。

  6. shell 不会一直屈居人下。它执行 setpgid() 建自己的进程组，然后 tcsetpgrp() 把自己那个组设成前台进程组。

text
init ──fork/exec──► getty ──setsid──► 新 session, ctty=tty1
                      └──exec──► login ──fork──► shell ──setpgid──► 自己的进程组
                                                       └──tcsetpgrp──► 前台进程组

内核接口速查 #

操作 函数 说明
取进程组 ID getpgid(pid) / getpgrp() getpgrp() 取自己的
设进程组 setpgid(pid, pgid) pgid 传 0 表示用 pid 新建组
建 session setsid() 调用者不能是组长，成功后自成 leader
取会话 ID getsid(pid)

发信号给进程组 kill(-pgid, sig) 负号表示整组

八、前台进程与后台进程 #

同一时刻只有一个应用能占有 TTY，也就是只有一个应用能通过它输入输出。占有的是前台应用，占不到的是后台应用。shell 里只有一个前台应用，可以有多个后台应用。占有的粒度是进程组，不是进程。拥有控制终端的那个进程组是前台进程组，其余是后台进程组。前后台切换靠 tcsetpgrp()。前台进程组退出或停止后，shell 收到子进程状态变化的通知（wait / waitpid），再把自己推回前台，等你敲下一条命令。

1、终端的输入归谁 #

答案简单：归前台 job。后台任务想要终端输入怎么办？这就是 job control 要解决的。这套动作按顺序发生：

  1. 后台进程组对终端发起读访问，终端驱动给它发 SIGTTIN；
  2. 该进程组的所有进程收到 SIGTTIN 后进入 stop 状态；
  3. 作为父进程的 shell 捕获状态变化，知道它停了；
  4. 用户执行 fg 把它转入前台，原来的前台任务转后台。这时 SIGTTIN 不再发，读写正常。

2、终端的输出归谁 #

输出没那么严格，两种策略：

  • 前台和后台都能输出，屏幕上会混成一团；
  • 只让前台输出。后台对终端写访问时，终端驱动发 SIGTTOU 给该后台进程组。

3、终端特殊字符 #

为了支持 job control，终端驱动还要认几个特殊字符，收到就转成信号，发给该 session 的前台进程组——前提是这个终端确实是该 session 的控制终端。

按键 别名 信号 默认动作
Ctrl+C interrupt key SIGINT 终止
Ctrl+\ quit key SIGQUIT 终止并 core dump
Ctrl+Z suspend key SIGTSTP 停止（可 fg 恢复）

这三个键产生的信号只送前台进程组，后台进程组收不到。这就是「后台跑的东西按 Ctrl+C 没反应」的原因。stty -a 能看到当前终端的这些绑定：

bash
$ stty -a | tr ';' '\n' | grep -E 'intr|quit|susp|eof'
intr = ^C; quit = ^\; susp = ^Z; eof = ^D;

4、让这套机制跑起来需要三方配合 #

  1. 支持 job control 的 shell；
  2. 支持 job control 的终端驱动；
  3. 内核支持 job control 相关的信号。

少一个都不成。有些精简 shell（比如某些容器里的 sh）没实现 job control，Ctrl+Z 和 fg 就跟没有一样。

5、& 与 bg 的差别 #

  • cmd & 是启动时就把进程组放进后台，从头到尾没碰过前台；
  • Ctrl+Z 之后 bg 是把已经存在的、停住的进程组重新放回后台继续跑。
bash
$ tar -czf home.tar.gz .      # 前台跑
^Z                            # Ctrl+Z，tar 停住
$ bg                          # 转后台继续
$ jobs
[1]+  Running                 tar -czf home.tar.gz . &

后台是后台，标准输入、标准输出、标准错误还连着终端。所以 tar 的进度、报错照样掺进控制台。这也正说明：进程依旧和控制终端绑在一起。& 启动的进程同样如此，虽然是后台任务，错误信息依旧发到终端。

6、管道的实战例子 #

在 /dev/tty1 登录之后，系统里有两个进程组：前台是 shell，后台是 login，两个组同属一个 session，所有进程的控制终端都是 tty1。

bash
$ ps -eo stat,comm,sid,pid,pgid,tty | grep tty | more

shell 创建 ps、grep、more 三个进程，放进新建的进程组（ps 是 leader），把这个组推向前台，shell 自己退到幕后。管道执行完，后台的 shell 收到子进程退出的信号，再把自己推回前台。同样的命令加个 &：

bash
$ ps -eo stat,comm,sid,pid,pgid,tty | grep tty | more &

这次 shell 不把新建的进程组推到前台，自己仍是前台进程组。因为有管道，输出沿 ps → grep → more 流到 more，more 要往标准输出（也就是 tty1）写的时候，麻烦来了：后台进程组不能写控制终端，SIGTTOU 被发给这个组的每一个进程，ps、grep、more 全部进入 stop 状态。此时在 shell 里 fg，把那个后台组推到前台，屏幕上才打印出进程信息。这个例子把「进程 → 进程组 → 会话 → 控制终端」这条链走通了：终端认的是进程组，进程组归属会话，会话绑定终端。任何一环换人，行为就变。

九、SIGHUP：终端关闭时发生了什么 #

这是「关掉终端，程序就死了」的机制根源。链条不长，但每环都得说清。

1、机制 #

text
终端断开 (pty master 关闭 / 串口掉线)
        │
        ▼
终端驱动检测到 hangup
        │
        ▼
内核向该 session 的控制进程（controlling process，即 session leader，多数是 shell）发 SIGHUP
        │
        ▼
shell 收到 SIGHUP，向自己管理的各 job（前台进程组为主）转送 SIGHUP
        │
        ▼
SIGHUP 默认动作 = 终止进程
        │
        ▼
前台进程组里的进程全部退出，shell 自己也退出
  • 内核发的第一枪打会话首进程，不是打在你那条命令上。这就是 controlling process 这个概念存在的理由——终端驱动要有个确定的收信人。
  • 你的程序是被 shell 转送的 SIGHUP 带走的，所以它挨不挨枪，取决于 shell 的 job 表里还有没有它。disown 能从 job 表里把它摘掉，原因就在这里。

SIGHUP 的默认动作是终止进程，但不带 core dump（带 core 的是 SIGQUIT）。想活下来就显式忽略：

bash
$ trap '' HUP        # shell 里忽略
$ kill -l | grep HUP # 1) SIGHUP

c
signal(SIGHUP, SIG_IGN);

2、什么时候会触发 #

场景 触发源 结果
关掉终端窗口 / 断开 ssh pty master 关闭，内核向控制进程发 SIGHUP shell 退出，前台进程组收到 SIGHUP
在登录 shell 里 exit shell 退出时向 job 表里的进程发 SIGHUP 没 disown 的后台 job 也会死
网络掉线、串口拔线 终端驱动检测到 hangup 同上
kill -HUP <pid> 手动发送 按该进程对 SIGHUP 的处理来
Ctrl+Alt+F2 切 VT 无 进程照跑，切换不影响会话
tmux / screen 里 detach 窗口的 pty 没关，pty 由 tmux server 持有 程序不受影响
nohup 启动的进程 启动时已把 SIGHUP 设为忽略 存活
setsid 脱离的进程 已不在那个 session，收不到 存活

3、为什么程序有时候没死 #

同一个动作结果不一样，原因就三类：

  • 程序自己忽略了 SIGHUP（nohup 干的就是这个，把 SIGHUP 设成 SIG_IGN，输出重定向到 nohup.out）；
  • 程序已经不在那个 session 了（setsid 建了新 session，老终端的 hangup 找不到它）；
  • 程序被移出了 shell 的 job 表（disown），shell 转送 SIGHUP 时漏掉它，但它仍挂在原 session 上，控制终端还是那个终端。

第三种最容易被误解成「彻底脱离了」，其实没有。jobs 里看不见它，fg 也叫不回来，但它的 SID 和 TTY 一点没变。第十一章专门拆这个差别。

4、验证手段 #

想确认一个进程到底挂在哪，看这几个 ID 就够了：

bash
$ ps -o pid,ppid,pgid,sid,tty,stat,comm -p <pid>
$ ls -l /proc/<pid>/fd/0        # 标准输入指向哪个终端
$ ps -o sid= -p <pid>           # 只取 SID

/proc/<pid>/stat 的第 6 个字段是 session ID，第 5 个是进程组 ID，脚本里解析比 ps 稳：

bash
$ awk '{print "pgrp="$5, "session="$6, "tty="$7}' /proc/<pid>/stat

十、让进程脱离终端 #

「脱离终端」是四件事的合集，很多人混成一件：

  1. 从 shell 的 job 表里消失（fg、bg、jobs 管不到）；
  2. 忽略 SIGHUP（终端断开不被带走）；
  3. 换一个新 session（SID 变了，老终端的 hangup 找不到它）；
  4. 断掉控制终端（/dev/tty 打不开，或者打开的是别的东西）。

多数命令只做其中一两件，所以效果看着「部分生效」。对照表：

手段 进后台 从 job 表移除 忽略 SIGHUP 换 session 断控制终端
cmd & 是 否 否 否 否
Ctrl+Z + bg 是 否 否 否 否
nohup cmd & 是 否 是 否 否
disown %1 原样 是 否 否 否
disown -h %1 原样 是 标记忽略 否 否
setsid cmd 看调用方式 是（换了会话） 否，但收不到 是 是
nohup setsid cmd & 是 是 是 是 是
守护进程（双 fork） 是 是 是 是 是

1、&：最轻的一层 #

只把进程组放进后台，其他一律不变。终端一关，照样 SIGHUP。

bash
$ tar -czf home.tar.gz . &
$ jobs

2、Ctrl+Z 加 bg：补救已经跑起来的 #

进程已经在跑了，不想重来。Ctrl+Z 发 SIGTSTP 暂停它，bg 让它到后台继续。

bash
$ tar -czf home.tar.gz .
^Z
[1]+  Stopped                 tar -czf home.tar.gz .
$ bg
[1]+ tar -czf home.tar.gz . &
$ jobs
[1]+  Running                 tar -czf home.tar.gz . &

标准输入、输出、错误还连着终端，所以输出照样掺进控制台。

3、nohup：让程序不理 SIGHUP #

nohup 干两件事：把 SIGHUP 设成 SIG_IGN，把输出重定向到 nohup.out（当前目录不可写时写到 $HOME/nohup.out）。

bash
$ nohup tar -czf iso.tar.gz Templates/* &
$ jobs

它在用户退出 shell 之后仍然保证进程在后台继续跑。但它没换 session，进程的 SID、控制终端都还是原来的。

4、disown：从 job 表里摘掉 #

disown 用在「进程已经在跑、并且已经被放到后台」之后。作用是从 shell 的活动任务列表里移走一个 job。移走之后 fg、bg 再也管不到它；关掉控制终端时，这个任务不会被挂起，shell 也不会向它发 SIGHUP。

bash
$ sudo rsync Templates/* /var/www/html/files/ &
$ jobs
$ disown -h %1
$ jobs

-h 只给 job 打上「不接收 SIGHUP」的标记，job 还在表里；不带 -h 就是整个摘掉。还有 -a 处理所有 job，-r 只处理正在跑的。

bash
$ disown -a            # 摘掉全部
$ disown -r %2         # 只摘正在跑的
$ disown -h %1         # 只打标记

5、setsid：换一个 session #

setsid 起一个新 session，新 session 没有控制终端，进程彻底和原来的终端断线。这是最干净的一层。

bash
$ setsid ./worker.sh < /dev/null > /var/log/worker.log 2>&1 &

标准输入输出不重定向的话，进程照样往老终端写，看着像脱离实际没脱——所以重定向必须做。setsid 默认在前台等命令结束，加 -f 强制 fork，命令立刻返回：

bash
$ setsid -f ./worker.sh < /dev/null > /var/log/worker.log 2>&1
$ echo $!              # 拿不到 PID，因为已经 fork 过了

拿不到 PID 时用 pgrep -f worker.sh，或者让程序自己写 pidfile。

6、/dev/null：收掉输出 #

GUI 程序尤其吃这一套。/dev/null 是个特殊设备，写在它上面的数据全被丢弃。

bash
$ firefox < /dev/null > /dev/null 2>&1 &

别写成 firefox /dev/null &：那只是给 firefox 传了一个参数，让输出闭嘴的仍是重定向。

十一、nohup 与 disown 的差别 #

这两个最常被搞混。一句话切分：nohup 管信号的默认行为，disown 管 shell 的 job 表。

维度 nohup disown
使用时机 启动命令时 进程已经在跑并且已转后台
作用对象 即将 exec 的那个程序 shell job 表里的某个 job
主要动作 signal(SIGHUP, SIG_IGN) + 输出转 nohup.out 从 job 表移除 / 打标记
SID 变不变 不变 不变
控制终端变不变 不变 不变
还能 fg 吗 能 不能（不带 -h 时）
终端关了会死吗 不会（SIGHUP 被忽略） 不会（shell 不再转送给它）
需要提前规划吗 需要 不需要

两个都不换 session 也不断控制终端。所以它们的「脱离」是有条件的：只在控制终端断开的那一刻成立，程序本身的 /proc/<pid>/fd/0 还指在老终端上，ps 的 TTY 列还是 pts/3。要连 session 一起换掉，得叠上 setsid：

bash
$ setsid nohup ./long-task.sh < /dev/null >> /var/log/long-task.log 2>&1 &
$ echo $!

顺序有讲究：setsid 是外层换 session，nohup 在内层改信号处置，两者互不干扰。反过来写 nohup setsid 也行，nohup 只是 exec setsid，setsid 再 exec 目标程序，信号忽略会被继承。

一个常见的坑：以为 disown 之后任务就彻底自由了。它自由的是 shell 不再管它，可它仍然挂在原 session 上，仍持有原终端的 fd。终端设备如果被真正销毁（不是窗口关掉，而是 pty 被回收），写操作会出 EIO，程序自己崩。所以长期跑的东西还是要 setsid 加输出重定向。

十二、守护进程与终端的关系 #

守护进程是「脱离终端」的终点形态，标准套路是双 fork。

c
#include <unistd.h>
#include <fcntl.h>
#include <stdlib.h>

int main(void) {
    pid_t pid = fork();
    if (pid < 0) exit(1);
    if (pid > 0) exit(0);       /* 第一次 fork：父进程退出 */

    setsid();                    /* 建新 session，脱离控制终端 */

    pid = fork();
    if (pid < 0) exit(1);
    if (pid > 0) exit(0);       /* 第二次 fork：确保不是 session leader */

    umask(0);
    if (chdir("/") < 0) exit(1);

    int fd = open("/dev/null", O_RDWR);
    if (fd >= 0) {
        dup2(fd, STDIN_FILENO);
        dup2(fd, STDOUT_FILENO);
        dup2(fd, STDERR_FILENO);
        if (fd > STDERR_FILENO) close(fd);
    }

    /* 到这里：无控制终端、无工作目录依赖、fd 全指向 /dev/null */
    return 0;
}

每一步都有明确目的：

步骤 解决什么
第一次 fork + 父退出 调用者拿到返回，子进程被 init 收养，不占它的进程组
setsid() 新建 session，控制终端断开，SID 换新
第二次 fork 让最终进程不是 session leader，永久堵住获取控制终端的路
chdir("/") 不占着某个挂载点，否则该文件系统卸不掉
umask(0) 文件权限由程序自己定，不受调用环境影响
dup2 到 /dev/null 残留的 printf 不会写爆磁盘，也不会因为终端消失拿到 EIO

第二次 fork 的原因值得单独说：setsid() 之后本进程就是 session leader，而 session leader 只要 open() 一个终端设备且不带 O_NOCTTY，那个终端就会成为它的控制终端。再 fork 一次，让真正干活的进程变成非 leader，这个口子就永久堵死。现代系统上这套可以省掉一大半：

  • systemd 系统里用 Type=simple 的 unit，pid 1 本身不挂在任何终端上，服务进程天然没有控制终端；
  • 容器里也一样，pid 1 是容器的 init，pty 由运行时管。
ini
[Service]
Type=simple
ExecStart=/usr/local/bin/worker
StandardInput=null
StandardOutput=journal
Restart=always

只有自己写守护进程、在没有服务管理器的环境里跑（嵌入式、老 SysV），才需要手写那套双 fork。不管哪种，判断标准一样：在 ps 里看它的 TTY 列，应该是 ?。

bash
$ ps -o pid,ppid,pgid,sid,tty,comm -C nginx
  PID  PPID  PGID   SID TT       COMMAND
 1120     1  1120  1120 ?        nginx

TTY 是 ?，SID 等于自己的 PID，说明它是某个 session 的 leader 且没有控制终端。

十三、查看当前终端与会话 #

排查「进程到底挂在哪」比查日志有用。几条命令够了。

1、我在哪个终端 #

bash
$ tty
/dev/pts/3
$ ps -o tty= -p $$
pts/3

tty 打的是标准输入的终端名，不是「我登录的那个终端」。被重定向过就变 not a tty：

bash
$ echo hi | tty
not a tty

要拿真实控制终端，走 /dev/tty：

bash
$ echo hi | tee /dev/tty        # 强制打到控制终端

2、我在哪个 session #

bash
$ ps -o pid,ppid,pgid,sid,tty,stat,comm -p $$
$ echo "sid=$(ps -o sid= -p $$) pgid=$(ps -o pgid= -p $$)"

$$ 是当前 shell 的 PID。stat 里带 s 表示它自己是 session leader。

3、这个终端上都有谁 #

bash
$ ps -t pts/3 -o pid,pgid,sid,stat,comm
$ ps -e -o tty= | sort | uniq -c | sort -rn   # 各终端上的进程数

4、谁在登录 #

bash
$ who -a
$ w
$ who am i

who -a 会打出每个登录会话的终端、时间、空闲时长和 PID。

5、某个进程的终端信息 #

bash
$ ls -l /proc/1245/fd/
lrwx------ 1 u u 64 Nov 17 10:00 0 -> /dev/pts/3
lrwx------ 1 u u 64 Nov 17 10:00 1 -> /dev/pts/3
lrwx------ 1 u u 64 Nov 17 10:00 2 -> /dev/pts/3

$ awk '{print "state="$3, "pgrp="$5, "session="$6, "tty_nr="$7}' /proc/1245/stat
state=S pgrp=1245 session=1200 tty_nr=34819

tty_nr 是设备号的编码，想解出来用 stat -c，或者直接看 ps 的 TTY 列更省事。

6、那个设备到底是什么 #

bash
$ ls -l /dev/tty /dev/console /dev/ptmx
crw-rw-rw- 1 root root  5,   0 Nov 17 10:00 /dev/tty
crw------- 1 root root  5,   1 Nov 17 10:00 /dev/console
crw-rw-rw- 1 root root  5,   2 Nov 17 10:00 /dev/ptmx

主设备号 136（devpts）之类是动态分配的，不用记。/dev/tty 的 (5, 0) 和 /dev/console 的 (5, 1) 要记牢。

7、job 视角与线路设置 #

bash
$ jobs -l
[1]+  1245 Running                 vim &
[2]-  1260 Stopped                 tar -czf a.tar.gz .

$ stty -a
speed 38400 baud; rows 40; columns 120;
intr = ^C; quit = ^\; susp = ^Z; eof = ^D;

+ 是当前 job，- 是上一个 job，不带参数的 fg 切到 + 那个。eof = ^D 是文件结束符，susp = ^Z 是挂起。改它们用 stty intr ^G 之类，改完只影响当前终端，重开就恢复。

十四、易错点速查 #

现象 真实原因 解法
关终端后程序死了 内核向控制进程发 SIGHUP，shell 转送给 job nohup / setsid / disown
& 了还是被关终端带走 & 只进后台，不改信号处置 加 nohup 或 setsid
disown 之后还想用 fg 找回 job 已从表里移除 没了，用 ps 找 PID 再 kill
后台任务按 Ctrl+C 没反应 终端信号只送前台进程组 先 fg 再按，或 kill -INT <pid>
后台任务突然停住不往下跑 读了终端触发 SIGTTIN，或写了终端触发 SIGTTOU fg，或把输入输出重定向到文件
后台任务往终端狂刷输出 fd 1/2 还连着终端 > log 2>&1
ssh 断开会杀后台 shell 退出时给 job 发 SIGHUP nohup 或 setsid
脚本里 tty 报 not a tty 标准输入被重定向或来自管道 用 /dev/tty，或判断 [ -t 0 ]
端口占用但 lsof 查不到进程 进程是僵尸，或你查的命名空间不对 ps -ef 兜底，容器里进对 namespace
在 tmux 里跑的东西关窗口不死 窗口的 pty 由 tmux server 持有，不是你的终端 正常现象，不用处理
setsid cmd & 后台还是能写终端 只换了 session，fd 还指在老终端 重定向 < /dev/null > log 2>&1
sudo cmd & 卡住等密码 密码从 /dev/tty 读，而 sudo 被放后台了 sudo -b，或先 sudo -v 再 &
nohup 不生成 nohup.out 当前目录不可写，写到了 $HOME/nohup.out 显式重定向到自己指定的文件
ps 的 TTY 显示 ? 该进程没有控制终端 正常，守护进程就该这样
容器里 fork() 报 Resource temporarily unavailable pids cgroup 打满了，不是终端问题 调 --pids-limit
Ctrl+Z 对某个命令无效 该 shell 没开 job control，或进程自己忽略 SIGTSTP kill -TSTP <pid> 硬来
  • 看进程挂在哪：ps -o pid,pgid,sid,tty,comm -p <pid>，SID 一样就是同一 session。
  • 看有没有控制终端：TTY 列是 ? 就没有。
  • 看是不是 session leader：stat 里带 s。
  • 看前台进程组是谁：ps -o tty,pgid,stat -e | grep +。
  • 看系统控制台在哪：cat /sys/class/tty/console/active。
