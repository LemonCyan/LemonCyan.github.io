本篇讲一件具体的事：程序里要存密码，怎么不落明文，而是交给操作系统提供的安全存储。这是系统层面的能力——Linux 侧是 Secret Service 与 D-Bus，Windows 侧是 Credential Manager，keyring 这类库只是把它们包了一层跨平台外壳。范围：密码该存在哪、keyring 的用法、失败模式、headless 部署的坑。不讲：密钥派生算法、TLS、以及内核 keyring 子系统怎么编程（只用它来做名字辨析）。跨篇指路：同目录另有《用户与权限管理》讲 Posix 权限模型、《系统配置速查》讲 /etc 与 /sys 下的配置位。

一、密码不能存哪里 #

一句话：密码只要落进一个不需要密码就能读到的地方，它就不再是密码，只是一段字符串。

先在纸上画一次攻击面。下面这些位置，拿到它们的人不需要知道任何秘密：

位置 谁能读到 典型事故
源码字面量 任何拿到仓库的人、二进制反编译者、git 历史里的每个人 开源仓库里搜 password = 一抓一把
配置文件 同机其他用户、备份系统、误提交的仓库 production.yaml 跟着 MR 一起合进主干
命令行参数 ps 全机可见、shell 历史文件、容器 inspect、审计日志 密码进了 ~/.bash_history
环境变量 /proc/<pid>/environ、容器编排平台的控制台、崩溃转储 排查问题时把 env 全量贴进工单
日志与异常信息 日志采集系统、磁盘、日志平台的所有读者 连接失败时把含密码的 DSN 整个打出来
内存转储 / core 文件 拿到文件的人 线上 core dump 落进对象存储

这几处有同一个性质：保护强度由文件系统权限和进程可见性决定。一个应用的数据库密码，价值往往高于它所在那台机器的普通文件；用它去换「省一次 API 调用」，账算不过来。

二、明文存储的三种典型错误 #

错误一：硬编码在源码里 #

cpp
// 不要这样写
const char* kDbPassword = "P@ssw0rd_2024";

auto conn = connect("db.internal", 3306, "app", kDbPassword);

编译之后，这串字符原样躺在二进制的只读数据段里。strings 一条命令就能捞出来。有人会把它换成 base64、十六进制、或者 xor 一个固定 key——那只是把「一秒钟」变成「五分钟」，同一份二进制里解密代码就在旁边。

错误二：写进被版本管理跟踪的配置文件 #

text
# config/production.yaml —— 提交进 git 的那一刻就泄了
database:
  host: db.internal
  user: app
  password: P@ssw0rd_2024

把这一行删掉再提交，没有任何用。历史里还在，克隆过的人本地也还在。公开仓库上的自动扫描按分钟级跑，密码泄露到被撞库的时间窗口以小时计。

错误三：运行时漏到可观测的位置 #

bash
./app --db-password 'P@ssw0rd_2024'

ps aux 全机可见，~/.bash_history 会留下一条，容器编排平台的 Pod 描述里也存了一份。同类问题还出现在日志里：

cpp
// 排查问题时顺手写的，然后就一直留着
log_info("connecting to %s with user=%s password=%s", host, user, pwd);

以及异常信息、崩溃报告、链路追踪的 tag。这些东西一旦进了日志系统，删除成本远高于当初写进去的成本。

三种错误的共同修法：

错误形态 换成语义正确的做法
源码里的字面量 交给系统凭据存储，代码里只留服务名与账号名
配置文件里的密码 配置里只留「去哪取」，密码本身移出仓库
命令行参数传密码 改成从标准输入或凭据存储读取
日志里打密码 打印的字段白名单化，密码字段永远不出口

三、keyring 库解决什么问题 #

keyring 是一个独立的 C++ 库，提供跨平台的密码管理功能。它的做法是把「存密码」外包给操作系统：你给一个服务名和一个账号名，它把密码交给系统的安全存储；取的时候用同样的两个名字要回来。

于是程序里从头到尾只有名字，没有密码：

  • 代码里不出现密码，配置里不出现密码，命令行里不出现密码；
  • 磁盘上的密文由操作系统的后端保管，解密密钥由用户的登录会话守住；
  • 换平台时不用重写业务逻辑，库自己选 Linux 的 Secret Service API 或 Windows 的 Credential Manager。

把几种存放方式放在一起比：

方案 密码存在哪 谁能解密 换机器是否带走 适合场景
源码/配置明文 文件或二进制 拿到文件的人 跟着仓库走 无
自研加密 + 硬编码密钥 文件 拿到程序和文件的人 是 无
自研加密 + 用户口令 文件 知道口令的人 是 单机工具
系统凭据存储（本篇） 系统后端 当前登录会话 否 桌面应用、本机服务
集中式密钥管理服务 远端 有权限的调用方 是（按策略） 服务端、集群

表中的取舍点很直接：系统凭据存储绑定「当前登录用户」，这既是它的保护来源，也是它的局限——下一台机器上取不到，服务器上更是另一回事（第十二章展开）。

四、名字的混淆：keyring 库与内核 keyring #

原文那句辨析值得单独占一章，因为搜「keyring C++」的人一半会掉进另一个坑。

Linux 内核确实有一套「密钥保留设施」，man 手册的标题就叫 in-kernel key management and retention facility。它提供系统调用 add_key(2)、request_key(2)、keyctl(2)，用户态配套库是 libkeyutils，命令行工具是 keyctl(1)。内核里的 key 有几个固有属性：序列号（serial number）、类型（type）、描述（description）、载荷（payload）、访问权限、过期时间、引用计数。权限位分 view、read、write、search、link、setattr，还多出一个「持有者（possessor）」维度。

而在内核这套体系里，叫 keyring 的东西是一种特殊的 key：它不存数据，存的是指向其他 key 的链接，作用类似目录放硬链接。围绕它有 process、session、thread、user、user-session、persistent 这几种锚定用的 keyring，用来把 key 的引用计数撑住，避免被垃圾回收。/proc/keys 能看到当前线程有 view 权限的 key，/proc/key-users 里是每个 UID 的配额用量。常用类型有 user、logon、big_key、keyring，其中 logon 类型的载荷不允许从用户态读回，专门放不该被读出来的口令。

这些跟本篇的 C++ 库没有任何关系。它只是一个名字撞车的用户态库：

维度 内核 keyring 子系统 本篇的 keyring 库
层次 内核 用户态 C++ 库
入口 add_key / request_key / keyctl set_password / get_password / delete_password
数据在哪 内核内存，big_key 超出阈值时会落到 tmpfs 操作系统凭据后端的加密存储
生命周期 跟进程、会话、UID 绑定，引用计数归零即回收 跟用户的登录会话绑定，跨重启保留
重启后 没了（persistent keyring 有超时限制） 还在
跨平台 只有 Linux Linux / Windows / macOS
能不能当密码库用 不能，它是给内核组件缓存凭据的 它就是干这个的

想确认自己面对的是哪一个，看这两类痕迹：

bash
# 内核侧：只有 Linux 有，输出是一堆 key 的列表
keyctl show

# 库侧：出现的是头文件和链接参数
grep -r "keyring/keyring.h" src/

一个在内核里按序列号管理链接，一个在用户态按「服务名 + 账号名」读写条目，除了拼写相同，没有交集。

五、Linux 侧的底层：Secret Service 与 D-Bus #

走到 Linux 上，keyring 库最终对接的是 Secret Service API。它是一份 D-Bus 上的规范，总线名 org.freedesktop.secrets，接口分五个：

接口 作用
org.freedesktop.Secret.Service 总入口，管会话、开集合、按属性查找
org.freedesktop.Secret.Collection 一组条目的容器，如「登录」「会话」
org.freedesktop.Secret.Item 一条记录：一组查找属性 + 一个 secret + 一个 label
org.freedesktop.Secret.Session 客户端与服务之间的会话，用于协商传输算法
org.freedesktop.Secret.Prompt 需要用户确认或解锁时弹的提示对象

数据模型很轻：每个条目挂一组属性（attributes）用来定位，属性本身不算机密，规范明说服务可以不加密地存它们；真正的密码放在 secret 里。所以「服务名」「账号名」这类定位信息可以出现在索引里，密码不行。

传输有个细节：读写 secret 之前要开一个 Session，并协商算法。可用算法是 plain 和 dh-ietf1024-sha256-aes128-cbc-pkcs7。plain 表示密码直接放在 D-Bus 消息体里，靠的是「本地 Unix socket + 同用户会话」这层保护；后一种是会话密钥协商后的对称加密。桌面环境里两类都有人用。

直接用 C 写 D-Bus 很啰嗦，官方客户端库是 libsecret。一次存取长这样：

c
#include <libsecret/secret.h>

static const SecretSchema kSchema = {
    "org.example.App.Db", SECRET_SCHEMA_NONE,
    {
        { "service", SECRET_SCHEMA_ATTRIBUTE_STRING },
        { "account", SECRET_SCHEMA_ATTRIBUTE_STRING },
        { NULL, 0 },
    }
};

int store_and_load(void) {
    GError *err = NULL;

    gboolean ok = secret_password_store_sync(
        &kSchema, SECRET_COLLECTION_DEFAULT, "db account",
        "P@ssw0rd_2024", NULL, &err,
        "service", "foo", "account", "bar", NULL);
    if (!ok) {
        g_printerr("store failed: %s\n", err ? err->message : "unknown");
        g_clear_error(&err);
        return -1;
    }

    gchar *pwd = secret_password_lookup_sync(
        &kSchema, NULL, &err,
        "service", "foo", "account", "bar", NULL);
    if (pwd == NULL) {
        g_printerr("lookup failed: %s\n", err ? err->message : "not found");
        g_clear_error(&err);
        return -1;
    }

    g_print("loaded %zu bytes\n", strlen(pwd));
    secret_password_free(pwd); // 清内存再释放，不要用 g_free
    return 0;
}

链接方式：

bash
pkg-config --cflags --libs libsecret-1
# 编译时追加：$(pkg-config --cflags --libs libsecret-1)

不想写代码验证时，命令行工具 secret-tool 就够探路：

bash
secret-tool store --label='db account' service foo account bar
secret-tool lookup service foo account bar
secret-tool clear service foo account bar

补一句容易被忽略的前提：整条链路都压在 session bus 上。没有 DBUS_SESSION_BUS_ADDRESS，连不上 org.freedesktop.secrets，keyring 库在 Linux 上就直接失败——这是第十二章的主题。

六、GNOME Keyring 与 KWallet #

Secret Service 是规范，落到具体的桌面环境上由两家后端实现。你的程序不直接选后端，它只认 D-Bus 总线上那个名字，谁占着就谁来干活。

维度 GNOME Keyring KWallet
守护进程 gnome-keyring-daemon kwalletd
规范接口 org.freedesktop.secrets 自家 org.kde.kwalletd，并提供 org.freedesktop.secrets 兼容实现
存储文件 ~/.local/share/keyrings/ 下的钥匙环文件 用户钱包文件
加密密钥来源 由登录口令派生 由钱包口令派生
登录时自动解锁 由 PAM 模块 pam_gnome_keyring 完成 由桌面会话的自动登录配置决定
条目组织 集合（collection）+ 条目（item） 钱包（wallet）+ 条目

两家的共同点是「集合要解锁才能读写」。锁着的时候客户端发起的操作会触发 org.freedesktop.Secret.Prompt——也就是桌面上那个让你输口令的弹窗。调用会一直阻塞到用户点了为止，或者超时失败。

桌面上很自然。放后台就尴尬了：没有能点弹窗的人，调用就卡在那里。这一点在第八章讲 API 阻塞行为时会再回来。

手工给环境补一个 Secret Service 后端，常见做法是让守护进程接管组件：

bash
# 启动 gnome-keyring 的 secrets 组件（前提是已经装了它）
gnome-keyring-daemon --start --components=secrets

# 确认总线上有服务在应答
busctl --user list | grep -i secret

KDE 侧对应的命令行检查：

bash
# 列出指定钱包里的条目
kwallet-query -l kdewallet

七、Windows 侧的底层：Credential Manager #

Windows 上的对应设施叫 Credential Manager。keyring 库在 Windows 上做的就是把这套 Win32 接口包一层。

用到的函数都在 wincred.h，链接 Advapi32.lib：

函数 用途
CredWriteW 新建或覆盖一条凭据
CredReadW 按目标名读一条凭据
CredDeleteW 删除一条凭据
CredEnumerateW 枚举当前用户的凭据集合
CredFree 释放 CredRead / CredEnumerate 返回的内存块

核心结构是 CREDENTIALW，几个字段决定了行为：

字段 说明
Type 存应用自定义数据用 CRED_TYPE_GENERIC
TargetName 凭据的名字，与 Type 一起唯一确定一条凭据，建成后不能改名
UserName 账号名
CredentialBlob / CredentialBlobSize 实际的机密字节流，上限 CRED_MAX_CREDENTIAL_BLOB_SIZE（2560 字节）
Persist 持久化范围：CRED_PERSIST_LOCAL_MACHINE 本机跨登录保留，CRED_PERSIST_SESSION 只在当前登录会话内存在
Comment 描述文字，最长 256 字符

自己调一遍就能看清 keyring 库底下发生了什么：

c
#include <windows.h>
#include <wincred.h>
#include <stdio.h>

static int store_secret(const wchar_t *target, const wchar_t *user,
                        const char *data, DWORD len) {
    CREDENTIALW cred;
    ZeroMemory(&cred, sizeof(cred));
    cred.Type = CRED_TYPE_GENERIC;
    cred.TargetName = (LPWSTR)target;
    cred.UserName = (LPWSTR)user;
    cred.CredentialBlob = (LPBYTE)data;
    cred.CredentialBlobSize = len;
    cred.Persist = CRED_PERSIST_LOCAL_MACHINE;

    if (!CredWriteW(&cred, 0)) {
        printf("CredWrite failed: %lu\n", GetLastError());
        return -1;
    }
    return 0;
}

static int load_secret(const wchar_t *target) {
    PCREDENTIALW pcred = NULL;
    if (!CredReadW(target, CRED_TYPE_GENERIC, 0, &pcred)) {
        DWORD err = GetLastError();
        printf("CredRead failed: %lu%s\n", err,
               err == ERROR_NOT_FOUND ? " (not found)" : "");
        return -1;
    }

    printf("blob size = %lu bytes\n", pcred->CredentialBlobSize);
    CredFree(pcred); // 必须用 CredFree，不要 free
    return 0;
}

int main(void) {
    const char *secret = "P@ssw0rd_2024";
    store_secret(L"foo/bar", L"bar", secret, (DWORD)strlen(secret));
    load_secret(L"foo/bar");
    return 0;
}

三个容易踩的点：

  • CredentialBlob 是纯字节流，编码由你自己定。存 UTF-8 还是 UTF-16 都行，但读写两端必须一致，否则取回来的是乱码。
  • 读出来的整块内存必须 CredFree，CredReadW 返回的是单块分配，内部指针都指向块内。
  • 加密由系统的 DPAPI 按用户账户完成。换个 Windows 账户登录，同一条 TargetName 读不到——这不是 bug，是设计。

存进去之后，在「控制面板 → 用户账户 → 凭据管理器 → Windows 凭据」里能看到这条记录，cmdkey /list 也能列出来。顺手记一下这个位置：调试「我明明写进去了」的时候，去这里看一眼比加日志快。

八、keyring 库的基本用法 #

库的 API 面就三个动作，成对得很整齐：

函数 参数 作用
set_password 服务名、账号名、密码 新建或覆盖一条记录
get_password 服务名、账号名、输出字符串 读回密码，通过第三个输出参数带出
delete_password 服务名、账号名 删除一条记录

「服务名 + 账号名」就是那个定位键。在 Linux 上它落到 Secret Service 的查找属性，在 Windows 上它被拼成 TargetName。这两个值要稳定：改了服务名等于换了一把钥匙，旧记录还在后端里躺着，但你的程序再也找不到它。

注意 get_password 的第三个参数是输出参数，这是它跟 set_password 在形态上最大的区别。写法上是先准备一个空串，调用后从里面取值：

cpp
std::string pwd;                          // 先空着
keyring::get_password("foo", "bar", pwd); // 调用后 pwd 里是读到的值

把库接进工程，无非是让它参与编译链接。它需要对接系统后端，所以 Linux 上要有 libsecret-1 的开发包，Windows 上要链 Advapi32：

bash
# Debian / Ubuntu 上装 libsecret 的开发文件
sudo apt install libsecret-1-dev

# 用 pkg-config 确认依赖找得到
pkg-config --exists libsecret-1 && echo ok

CMake 侧把库源码加进构建，Windows 上顺手把系统库带上：

bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build

text
# CMakeLists.txt 里 Windows 需要的一条
target_link_libraries(app PRIVATE Advapi32)

九、存储与读取密码 #

原文给的完整示例，一字不动放在这里——它就是这个库最小的可用程序：

cpp
#include <keyring/keyring.h>

#include <iostream>
#include <string>

int main() {
  std::string service_name = "foo";
  std::string account = "bar";
  std::string password_input = "password";
  std::string password_output = "";
  keyring::set_password(service_name, account, password_input);

  keyring::get_password(service_name, account, password_output);

  std::cout << password_output << std::endl;

  return 0;
}

把这段拆开看：

  • service_name = "foo"：哪个应用或哪个服务在用这条密码。换成 "com.example.myapp" 这种反域名更好，因为它要跟别人的条目共处一个命名空间。
  • account = "bar"：这条密码属于哪个账号。一个应用存多个账号的密码时，靠它区分。
  • set_password 的三个参数顺序是「服务、账号、密码」，get_password 是「服务、账号、输出变量」。顺序看着一样，语义不一样，抄代码时别顺手把输出变量填到密码的位置。
  • 示例里存的是字面量 "password"，这只是演示。真实代码里这个值是运行期拿到的，绝不能出现在源码里。

真要用，至少把「存 → 取 → 清理」走完整：

cpp
#include <keyring/keyring.h>

#include <iostream>
#include <string>

namespace {
const char *kService = "com.example.myapp";
const char *kAccount = "db-prod";
} // namespace

int main() {
  // 1. 写入（覆盖同名旧值）
  keyring::set_password(kService, kAccount, "P@ssw0rd_2024");

  // 2. 读回并校验
  std::string pwd;
  keyring::get_password(kService, kAccount, pwd);
  if (pwd.empty()) {
    std::cerr << "未取到密码：条目不存在，或后端不可用\n";
    return 1;
  }

  // 3. 用完即清理条目（例如卸载程序、轮换密钥之后）
  // keyring::delete_password(kService, kAccount);

  std::cout << "取到 " << pwd.size() << " 字节\n";
  return 0;
}

有个判断题要提前想清楚：「读到空串」不能当失败信号。空密码在某些协议里是合法的，后端返回空串，或这条记录本身就存成这样。判断存在性要靠库的错误通道，而不是看字符串长度。这个坑和它的解法，下一章和第十一章分别讲。

轮换密码的流程也要按顺序来，别反了：

text
1. 新密码写进后端（set_password 覆盖旧值）
2. 用新密码做一次连通性验证
3. 验证通过后，才让业务侧切到新凭据
4. 确认无回滚需求，再清理旧凭据

反过来先删后写，中间那几秒就是一个「谁都连不上」的窗口。

十、密码的生命周期管理 #

密码从写进来到被删掉，中间有几次状态变化，每一步都要有人负责。

阶段 该做的事 常见失误
生成 用系统随机源，长度按后端上限留余量 手写随机函数、用时间戳当盐
写入 调 set_password 并检查失败 不检查返回值，当成写成功了
使用 只在内存里存活最短时间 存进全局 std::string 一直不释放
轮换 先写新值再切流量，核对后再清理 先删后写，造成连接中断
销毁 用后立刻清零缓冲区 直接 erase()，字符还留在原位置

销毁这一条值得单独说。std::string 析构只是把内存还回去，内容不会被抹掉，那块堆内存里还留着密码，等下一次分配才被覆盖。要主动清零：

cpp
#include <openssl/crypto.h> // OPENSSL_cleanse
#include <string>

void wipe(std::string &s) {
  if (!s.empty()) {
    OPENSSL_cleanse(s.data(), s.size());
  }
  s.clear();
}

不想引 OpenSSL 就自己写一个不会被编译器优化掉的循环——用 volatile 指针写入：

cpp
#include <cstddef>

void secure_erase(char *p, std::size_t n) {
  volatile char *v = p;
  while (n--) {
    *v++ = 0;
  }
}

同一份密码不要在多处留副本：日志、异常消息、进程参数、临时文件、拷贝给同事的聊天记录。每一次复制都要单独销毁，漏一处等于没做。

条目本身的生命周期也是设计的一部分。给每条凭据定一个归属：哪个程序写的、什么时候该删。程序卸载时留一堆没有主人的条目在后端里，下一个装同名应用的倒霉。

十一、错误处理与失败模式 #

keyring 库的错误处理方式取决于它的实现：有的版本抛异常，有的把状态码塞进返回值。先读它的头文件确认，再决定写不写 try/catch——照抄别人的异常处理代码是这类问题的头号来源。

不管哪种形态，失败原因就那几类，认清它们比记住 API 有用得多：

失败场景 Linux 侧触发条件 Windows 侧触发条件 应对
后端不存在 总线上没有 org.freedesktop.secrets 无（系统组件，始终在） 降级：提示用户，或改用其它配置来源
连不上总线 缺 DBUS_SESSION_BUS_ADDRESS 不适用 检查会话环境，见第十二章
条目不存在 属性匹配不到 ERROR_NOT_FOUND 当作「首次运行」，引导录入
集合被锁 需要用户解锁，弹出 Prompt 凭据按登录会话解密，正常可读 提示用户解锁，别死等
数值超限 属性长度受后端限制 CredentialBlobSize 超过 2560 字节 校验长度，改存令牌而非原始数据
权限不足 当前用户不拥有该集合 换个 Windows 账户，DPAPI 解不开 换用户，或改用服务级凭据

三条实践规则：

第一，区分「没有」和「坏了」。「条目不存在」是正常业务分支，程序该继续走引导流程；「后端连不上」是环境故障，重试和引导都没意义，应该直接报错退出。把两件事都当成 false 混在一个分支里，排查时会浪费一整天。

第二，不要在循环里重试阻塞型调用。解锁弹窗没人点的时候，一次调用就卡到你超时；外面再套一层重试，就是把卡死时间乘上重试次数。

第三，别把密码写进错误信息。下面这种代码在无数项目里出现过：

cpp
try {
  keyring::set_password(service, account, pwd);
} catch (const std::exception &e) {
  // 千万别这么写：pwd 会跟着日志一起进日志平台
  std::cerr << "写入失败 " << service << "/" << account
            << " pwd=" << pwd << " : " << e.what() << std::endl;
}

正确做法是只记服务名、账号名、错误类别，密码字段永远不出现在任何输出里。

十二、headless 环境的麻烦 #

这是实际部署里最常见的坑，也是这篇最该记住的一章。

keyring 库在 Linux 上的工作前提是：有一个 session bus，总线上有一个 Secret Service 实现，那个实现能被当前用户解锁。这三条在桌面上自动成立，在服务器上一条都不成立。

具体会坏在哪：

环境 现象 根因
SSH 登进去跑 连接被拒或超时 没有 DBUS_SESSION_BUS_ADDRESS，起不了会话总线
systemd 服务 启动即失败 服务不在用户会话里，--user 总线也不一定在
Docker 容器 报后端不可用 镜像里没有 Secret Service 守护进程，也没有 D-Bus
CI 流水线 卡住或超时 有 D-Bus 但没有已解锁的集合，弹窗没人点
cron / 批处理 静默失败 环境被裁到最小，什么凭据服务都不在

自检三条命令，从上往下看：

bash
# 1. 会话总线地址在不在
echo "${DBUS_SESSION_BUS_ADDRESS:-<空>}"

# 2. 总线上有没有 secret service
busctl --user list 2>/dev/null | grep -i secret || echo "no secret service"

# 3. 命令行走一遍完整链路
secret-tool lookup service foo account bar || echo "lookup failed"

三条全过才说明这台机器上能用。任何一条挂了，别在 C++ 代码里想办法——问题不在代码里。

容器里更是别指望它。镜像里既没有 D-Bus 守护进程，也没有 gnome-keyring，端口和 socket 全都对不上。有人试图在容器里装一个 dbus-daemon 再塞个 keyring 守护进程，那条路子能通，但代价是你得在容器启动脚本里维护一套会话环境，还要处理「谁给钥匙环解锁」——那又回到没有人的问题上。

正确的方向是承认边界，按环境选方案：

场景 密码放哪 说明
桌面 GUI 应用 系统凭据存储 这就是 keyring 库的主场
本机常驻服务（有登录会话） 系统凭据存储 + 登录时解锁 依赖用户会话存在
服务器 / 容器 环境变量或编排平台的 secret 对象 由部署系统注入，程序只读
服务器 / 容器（更强隔离） KMS / Vault 类服务运行期拉取 程序需要网络与鉴权令牌
CI 流水线 平台提供的 secret 变量 用完即弃，不落盘

配套的工程做法是把「取密码」抽成一层接口，运行期按环境选实现：

cpp
#include <cstdlib>
#include <string>

// 桌面环境走 keyring，服务器环境走环境变量，业务代码不关心用了哪个
std::string load_secret(const std::string &service, const std::string &account) {
  if (const char *env = std::getenv("APP_DB_PASSWORD")) {
    return env; // 服务端：由部署系统注入
  }

  std::string pwd;
  keyring::get_password(service, account, pwd); // 桌面端：系统凭据存储
  return pwd;
}

这段代码的意义不在于环境变量比 keyring 更安全——恰恰相反，环境变量能被同机其他进程看到。它的意义是让程序在两种环境里都能起来，并且明确写下「这里有一个降级路径」。环境变量那条分支要不要开，取决于部署环境本身是否可信。

十三、密码学上的边界：这不是加密库 #

最常见的一类误用：把 keyring 当成 AES_encrypt() 那样的工具，拿它去加密文件、加密数据库字段、加密配置里的一整段数据。

它做不到，也不打算做。看它接受的参数就清楚了——服务名、账号名、字符串。它没有 IV 参数，没有 AEAD tag，没有密钥管理接口，没有分块，取回来的是你写进去的那段原文。它做的全部工作是「把这个字符串交给系统的凭据存储」，加解密完全由后端实现：Linux 上是 Secret Service 守护进程按集合密钥加密落盘，Windows 上是 DPAPI 按用户账户派生密钥。

于是它的加密边界和「一条口令」这件事完全贴合：

你想要的 keyring 库能不能做
存一条数据库连接密码 能
存一条 API token 能
加密一个用户上传的文件 不能
加密一整张表的字段 不能
存一个对称密钥（比如 32 字节主密钥） 勉强能，但要注意后端的长度上限与编码
做消息认证、签名、密钥交换 完全不能

数据量一大就撞墙。Windows 的 CredentialBlob 上限是 2560 字节，Linux 侧也受后端与条目属性的限制。想加密一堆业务数据，得自己选算法、自己管密钥，keyring 只能帮你保管那把密钥。

还有一点容易误解：它不提供「密钥派生」。你不能给它一个主口令，让它派生出子密钥——那是 KDF 的职责（PBKDF2、scrypt、Argon2 之类），跟凭据存储是两个层次。真需要，用专门的口令派生库，把派生结果当一条 secret 存进后端。

把定位写清楚：keyring 是凭据存取层，不是密码学层。前者管「这条秘密放哪、谁能取」，后者管「这段数据怎么变成别人看不懂的样子」。混用这两层，是这类误用的根源。

十四、其他可选方案 #

同类的封装不止一个，选哪个取决于你的依赖边界和运行环境。

方案 形态 覆盖平台 特点
keyring 库 C++，薄封装 Linux / Windows / macOS 接口极简，只做存取三件事
libsecret C 库，GLib 体系 Linux 官方 Secret Service 客户端，API 面完整
QtKeychain Qt 模块 Linux / Windows / macOS 项目本身用 Qt 时直接可用，异步接口
libcred C++ 库 跨平台 从 keytar 移植过来的思路，接口对齐 node 那一套
系统 API 直连 各家原生 单平台 没有额外依赖，代码量最大
自管加密文件 自研 任意 需要自己解决密钥保管，等于把问题往后推一步

选型时的实际判断顺序：

text
1. 目标平台有没有系统凭据存储？没有 → 别用这一类库
2. 项目已经依赖 Qt 了吗？是 → QtKeychain 少一层胶水
3. 只要 Linux 且已经用了 GLib？是 → 直接用 libsecret
4. 只要存取三件事、想少依赖？→ 本篇这个薄封装
5. 要跨语言、跨进程共享同一批凭据？→ 看集中式密钥管理服务

补一句关于第 5 条：系统凭据存储按「当前登录用户」隔离，天然不适合多机多进程共享同一套凭据。一旦出现「三台机器都要用同一个数据库密码」，需求已经从「本地凭据存储」变成了「密钥分发」，那是另一个问题域，用这类库硬凑只会把密码复制到三台机器上。

十五、易错点速查 #

易错点 表现 正确做法
把内核 keyring 当成本库 到处找不着 set_password，只有 add_key 分清内核子系统与用户态库，看头文件名
服务名写得随意 换了个名字，旧条目读不到 用反域名格式并定下来，写进文档
用空串判断成败 存了一个空密码，被当成失败 走错误通道判断，别用 size() == 0
不查后端就在服务端跑 启动即失败或卡死 部署前跑那三条自检命令
在容器里硬上 报「后端不可用」 改用环境变量或编排平台的 secret
当成加密库用 拿它加密文件，撞上长度上限 加密用密码学库，它只保管密钥
密码留在堆内存 用完后，这块内存里还是明文 用 OPENSSL_cleanse 或 volatile 循环清零
打印错误时带上密码 日志平台里出现明文 只输出服务名、账号名、错误类别
先删后写做轮换 中间几秒连接全断 先写新值，验证通过再清理旧值
弹窗阻塞在后台进程里 调用挂到超时 认出集合被锁的场景，别在循环里重试
凭据条目没有主人 卸载后残留一堆记录 卸载流程里调 delete_password
换个 Windows 账户就取不到 DPAPI 按账户派生密钥 这是设计，不是 bug；服务场景另选方案
