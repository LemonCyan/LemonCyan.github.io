一、为什么要绑核：多核下的缓存与迁移 #

先把预期摆正：绑核不会让一个核跑得更快。同一条指令在同一个核上执行的时间是固定的，绑核改变的是任务在核之间的落点分布。它省掉的是迁移成本，不是计算成本。谁把绑核当加速开关，谁就会在压测报告里看到一个不好看的数字。

现代多核 CPU 是多级缓存结构，每级缓存的归属范围不一样：

层级 归属范围 延迟量级 进程被迁走之后
L1 指令/数据缓存 单核独占 数个时钟周期 全部失效，等于清零
L2 缓存 单核独占（部分架构双核共享） 十几个时钟周期 全部失效
L3 缓存 同一插槽内多核共享 数十个时钟周期 同插槽内迁移仍可命中
主存 RAM 全部核共享 高出缓存两个数量级 只能回内存取 
text
【 多级缓存与核间迁移 】

  +-------------------------------------------------------+
  |                    主内存 (RAM)                       |
  +-------------------------------------------------------+
                          ^
                          |  高延迟
                          v
  +-------------------------------------------------------+
  |              共享 L3 缓存（同插槽多核）               |
  +-------------------------------------------------------+
        ^                                        ^
        |                                        |
        v                                        v
  +--------------+                        +--------------+
  |  L1/L2 缓存  |                        |  L1/L2 缓存  |
  +--------------+                        +--------------+
        ^                                        ^
        |                                        |
        v                                        v
  +--------------+   调度器迁移（负载均衡） +--------------+
  |   物理核心 0 | ----------------------> |   物理核心 1 |
  |  (缓存温热)  |    L1/L2 失效 + TLB 重建 |  (缓存冷态)  |
  +--------------+                        +--------------+

一个线程在核心 0 上跑了一段时间，它访问过的数据页和指令页都躺在核心 0 私有的 L1/L2 里，这时它处于温热状态，取指和数据访问几乎不碰内存。内核因为负载均衡把它挪到核心 1，接下来发生三件事：

  1. 核心 0 上的 L1/L2 数据对当前线程不再可用，那些行会随着别的任务填充而被覆盖。
  2. 线程在核心 1 上重新执行，指令和数据访问全部落空，被迫向 L3 甚至内存要数据，直到核心 1 的缓存再被捂热。
  3. 虚拟地址到物理地址的映射缓存 TLB 也要重建，活跃页多的时候这一项比前两项都贵。

这笔账在两种场景下差别巨大。批处理任务跑几秒，冷启动那点损失摊薄到总时间里可以忽略。低延迟服务一次请求只花几十微秒，一次迁移造成的冷启动直接顶掉一整次请求的预算，于是就出现了「平均延迟没变、p99 突然跳高」的曲线。

一次跨核迁移的成本拆成四层：

成本项 触发时机 量级感受 能否避免
L1/L2 冷启动 换核后重新取指取数 与工作集大小正相关 绑核可避免
TLB 重建 换核或换页表 与活跃页数正相关 绑核可避免（部分）
上下文切换 任务被抢占换出再换入 微秒级 减少候选核数可降低频率
运行队列排队 可运行核变少 与负载分布相关 绑核会加重，需算核数

第三项和第四项是一对拉扯。绑核把任务锁在少数核上，迁移没了，可调度窗口也窄了，一旦该核上有别的活，你的线程只能站在运行队列后面等。这就是为什么绑核必须和线程数、核数一起算。真正从绑核里拿到的收益指标是抖动，不是吞吐：绑核前后各压一轮，吞吐基本持平，p99 和最大延迟收窄。绑核做的是给延迟分布削尾巴。

二、NUMA 与 SMP 的差别 #

SMP 是理想化的模型：所有 CPU 到所有内存的距离一样，内存在总线后面排成一队，谁访问都花同样的时间。早年双路主板靠前端总线连多个插槽，这条路走到头了，CPU 数量一上去总线先成瓶颈。

NUMA 承认了物理现实：内存被切成若干块，每块挂在一个插槽旁边，CPU 访问自己旁边的内存快，访问别的插槽旁边的内存慢。这个差别可以量出来，是两到三倍延迟。

维度 SMP（对称多处理） NUMA（非一致内存访问）
内存访问延迟 所有核一致 本地节点低，远端节点高
硬件结构 单插槽或共享总线 多插槽，节点间用 UPI / Infinity Fabric 互联
缓存一致性 一颗芯片内维护 跨节点维护，开销随核数上升
扩展瓶颈 总线带宽先撞墙 跨节点流量先撞墙
对绑核的要求 绑到哪个核差别不大 必须 CPU 与内存绑到同一节点
典型机器 单路桌面、单路服务器 双路及以上 Xeon、EPYC
观测手段 lscpu 看核数 numactl -H、numastat 看节点 
text
【 NUMA 本地与远端访问 】

  +-----------------------+            +-----------------------+
  |      NUMA 节点 0      |            |      NUMA 节点 1      |
  |  [CPU 0-7] --> 本地内存|            | [CPU 8-15] --> 本地内存|
  +-----------------------+            +-----------------------+
          ^                                       ^
          |                                       |
          +========= UPI / Infinity Fabric =======+
                 跨节点访问：带宽下降，延迟上升

在 NUMA 机器上只做 CPU 绑核，等于只做了一半。线程被绑在节点 0 的 CPU 0 上，但它要读写的内存页在节点 1 上，每次访问都要跨互联总线走一趟。绑核省下的缓存红利被远端访问的成本吃干净，实测下来反而不如不绑。CPU 亲和性和内存亲和性要成对使用。

命令行上做双绑，用 numactl：

bash
# 只看拓扑，确认节点数、每节点的核与内存
numactl -H

# CPU 绑 0-3，内存只从节点 0 分配
numactl --physcpubind=0-3 --membind=0 ./my_server_app

# 内存需求太大、单节点装不下时改成交织分配
numactl --interleave=all ./my_large_db_app

--physcpubind 按物理核编号绑，--cpunodebind 按节点绑。前者精确到核，后者粗到节点，选哪个看线程数是否恰好整除节点核数。

内存到底是本地还是远端，numastat -c my_server_app 直接给数字。看 numa_hit、numa_miss、numa_foreign 三个计数：numa_hit 是本节点分配命中，numa_miss 是本节点分配失败退到别的节点，numa_foreign 是本节点被别的节点借走的页数。后两个数持续上涨，说明内存分布和 CPU 落点没对齐。

还有一个容易忽略的点：首次触碰决定内存落在哪个节点。--membind 能约束住后续分配，但程序启动早期的分配和大页预留走的是另一个时机。真要在 NUMA 上把延迟压下来，分配和触碰的顺序也得跟着安排。

三、CPU 亲和性是什么 #

CPU 亲和性是挂在每个任务上的一个位图，位图的第 N 位为 1，表示该任务可以在第 N 号 CPU 上运行。内核调度器选核时先看这个位图，只从为 1 的核里挑，位图之外的核一律不进候选队列。

内核里的对应字段是 task_struct 的 cpus_mask（旧版本叫 cpus_allowed），类型就是 cpu_set_t 背后的位图。用户态通过系统调用读写这个位图，读出来的就是当前生效的亲和性。

十六进制掩码 二进制 允许运行的核
0x1 0001 CPU 0
0x3 0011 CPU 0、1
0xf 1111 CPU 0、1、2、3
0x5 0101 CPU 0、2
0x80 1000 0000 CPU 7
0xff 1111 1111 CPU 0 到 7

几个必须记住的性质：

  1. 亲和性是每任务属性，不是每进程。Linux 的线程是 clone 出来的 LWP，有自己的 TID，也就有自己的亲和性。同一进程里两个线程，可以一个绑核 0、一个绑核 3。
  2. 亲和性是允许集合，不是指定集合。绑到 {2,3}，这一轮跑核 2、下一轮跑核 3 都合法，内核只承诺不跑出集合。
  3. 亲和性不保证独占。你绑了核 2，别人的进程也可以绑核 2，两个任务在同一个核上轮流跑，亲和性管不了这件事。
  4. 亲和性有继承规则。fork 出来的子进程继承父进程掩码，exec 之后掩码保留，主线程改掩码会影响之后新建的线程。

想看一个跑着的进程的亲和性，最快是读 /proc：

bash
cat /proc/12345/status | grep -i cpus_allowed

text
Cpus_allowed:   0000000f
Cpus_allowed_list:      0-3

Cpus_allowed 是十六进制掩码，Cpus_allowed_list 是给人看的核号列表。两个字段对不上，八成是位序算错了：掩码低位对应小编号核，0xf 就是低四位全 1，即 0 到 3 号核。

四、软亲和性与硬亲和性 #

社区里「软亲和性」和「硬亲和性」经常混着用，指的不是同一件事，先把定义卡死。

硬亲和性指用户态显式设置的掩码，通过 sched_setaffinity、pthread_setaffinity_np、taskset 写下去的那一份。它对调度器是强约束，调度器不得越界，越界就是 bug。

软亲和性指调度器自己维护的「尽量让任务回到上次运行的核」这套启发式。任务被唤醒时，调度器优先考虑它上次运行的 CPU，因为那上面的缓存还是热的。这个偏好实现在唤醒路径的选核逻辑里，用户态没有接口直接读写，只能通过调度行为间接感受。

维度 软亲和性 硬亲和性
设置者 内核调度器 用户态程序或管理员
表现形式 唤醒时优先回原核的启发式 任务上的 cpus_mask 位图
约束力 是偏好，负载不均时会打破 是硬约束，调度器不得越界
用户接口 无直接接口 sched_setaffinity、taskset、numactl
跨核迁移 允许，负载均衡照常搬 只在掩码内迁移
失效场景 原核空闲不下来时被放弃 掩码与 cpuset 冲突时被裁剪
调优手段 改调度器参数、调唤醒特性 写掩码

两者分层：硬亲和性先划出允许范围，软亲和性在这个范围内部做局部优化。你只绑了核 0 到 3，软亲和性就只能在 0 到 3 里挑最热的那个；你把范围收到只剩核 2，软亲和性彻底没事可干，因为只有一个候选。

硬亲和性的接口，sched_setaffinity 系列自 Linux 2.5.8 引入，一直用到今天的 6.x 内核，原型没变过。这个稳定性意味着你 2003 年写的绑核代码，拿到现在的机器上照样编译、照样生效。

五、sched_setaffinity 接口 #

Linux 给的亲和性接口就一对，设置和查询：

c
#define _GNU_SOURCE
#include <sched.h>

/*
 * 设置进程或线程的 CPU 亲和性
 * pid:        目标任务的 PID。传 0 表示当前调用线程自身
 * cpusetsize: 掩码缓冲区的字节数，用 sizeof(cpu_set_t)
 * mask:       配置好的 cpu_set_t 指针
 * 返回:       成功 0；失败 -1 并设置 errno
 */
int sched_setaffinity(pid_t pid, size_t cpusetsize, const cpu_set_t *mask);

/*
 * 获取进程或线程的 CPU 亲和性
 */
int sched_getaffinity(pid_t pid, size_t cpusetsize, cpu_set_t *mask);

参数逐个说清，这几个点是真会踩的：

参数 取值 关键说明
pid > 0 目标任务的 PID（对线程要用 TID）
pid 0 当前调用线程自身，最常用
cpusetsize sizeof(cpu_set_t) 和 sizeof 对不上不报错，但位图会被截断
mask 非空集合 传空集合会得到 EINVAL
返回值 0 / -1 失败必须查 errno，别只判非零

errno 的几种常见值，对应不同排查方向：

errno 含义 排查方向
EINVAL 掩码为空，或 cpusetsize 小于内核需要的长度 检查 CPU_ZERO 后是否忘了 CPU_SET
EPERM 权限不足，目标进程不属于当前用户 换用户或提权
ESRCH 指定的 PID 不存在 目标进程已退出
EFAULT 掩码指针指向非法地址 检查指针生命周期

三个必须知道的细节。

_GNU_SOURCE 必须在所有头文件之前定义。cpu_set_t 和 CPU_* 系列宏是 GNU 扩展，glibc 只在 _GNU_SOURCE 打开时才把它暴露出来，写在 #include 后面，编译直接报 unknown type name 'cpu_set_t'。

pid 传 0 绑的是调用线程，不是整个进程。Linux 里每个线程有自己的 TID，sched_setaffinity(0, ...) 只改当前线程那一份位图。想改整个进程，得遍历进程下所有 TID 逐个设置。

设置成功不代表立刻生效。内核负责在下次调度时把任务挪到允许集合内的核上，会有一小段延迟。刚设置完就 sched_getcpu() 读到旧核号是正常的，不要以为没绑上。

调用范式固定成这个形状，写多少遍都不会错：

c
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <errno.h>
#include <string.h>

int pin_self_to_cpu(int cpu)
{
    cpu_set_t mask;

    CPU_ZERO(&mask);
    CPU_SET(cpu, &mask);

    if (sched_setaffinity(0, sizeof(mask), &mask) == -1) {
        fprintf(stderr, "sched_setaffinity(cpu=%d) 失败: %s\n", cpu, strerror(errno));
        return -1;
    }
    return 0;
}

先用 CPU_ZERO 清空，再 CPU_SET 加核，绝不能反过来。CPU_ZERO 之后再 CPU_SET 是标准顺序，漏掉前者会把栈上残留的随机位带进去，绑到一堆你没想要的核上。

六、CPU_SET 与 cpu_set_t #

cpu_set_t 是内核暴露给用户态的固定长度位图，glibc 实现里是一个 __cpu_mask 数组，默认能装 CPU_SETSIZE 个位，CPU_SETSIZE 的默认值是 1024。

直接操作位图很危险，GNU 给了一组宏：

宏 作用 典型用法
CPU_ZERO(set) 清空集合，所有位置 0 CPU_ZERO(&mask)
CPU_SET(cpu, set) 把指定核加入集合，置 1 CPU_SET(2, &mask)
CPU_CLR(cpu, set) 把指定核移出集合，置 0 CPU_CLR(3, &mask)
CPU_ISSET(cpu, set) 检查指定核是否在集合中 if (CPU_ISSET(i, &get))
CPU_COUNT(set) 返回集合中为 1 的位数 int n = CPU_COUNT(&mask)
CPU_AND(dst, s1, s2) 交集 CPU_AND(&r, &a, &b)
CPU_OR(dst, s1, s2) 并集 CPU_OR(&r, &a, &b)
CPU_XOR(dst, s1, s2) 对称差 CPU_XOR(&r, &a, &b)
CPU_EQUAL(s1, s2) 判断两个集合是否相等 CPU_EQUAL(&a, &b)
CPU_SETSIZE 集合可容纳的位数上限，默认 1024 循环上界用它
CPU_ALLOC_SIZE(n) 算 n 个 CPU 的位图字节数 动态分配时用
CPU_ALLOC(n) 按需分配能装 n 个核的位图 核数超过 1024 时用
CPU_FREE(set) 释放 CPU_ALLOC 分配的位图 配对使用，不能用 free

CPU_SETSIZE 的容量限制是最容易忽略的一条。默认 1024，意味着栈上这个结构体只能表达 0 到 1023 号核。核数超过 1024 的机器（大规模 NUMA 服务器确实有），栈上的 cpu_set_t 装不下全部核，就得改用动态分配：

c
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>

/* 核数超过 CPU_SETSIZE 时，按需分配位图 */
int pin_with_dynamic_set(int ncpu)
{
    size_t setsize = CPU_ALLOC_SIZE(ncpu);
    cpu_set_t *mask = CPU_ALLOC(ncpu);
    if (mask == NULL) {
        perror("CPU_ALLOC");
        return -1;
    }

    CPU_ZERO_S(setsize, mask);
    CPU_SET_S(2, setsize, mask);

    int rc = sched_setaffinity(0, setsize, mask);

    printf("位图字节数: %zu，可表达的核数: %d\n", setsize, ncpu);
    CPU_FREE(mask);
    return rc;
}

动态接口是 CPU_*_S 那一套：CPU_ZERO_S、CPU_SET_S、CPU_ISSET_S、CPU_COUNT_S，都多一个 setsize 参数。三个释放路径不能混：CPU_ALLOC 配 CPU_FREE，malloc 配 free，栈上变量不用释放。混用就是堆破坏。

栈上的固定位图什么时候够用？绝大多数服务器核数在 8 到 256 之间，CPU_SETSIZE 给到 1024，绰绰有余。只有当你在写要跑在超大机器上的通用库，或者要给 cgroup cpuset 做通用适配，才需要走动态分配那条路。

CPU_COUNT 的用途常被低估。判断「到底绑上了几个核」用它最快，比循环 CPU_ISSET 干净：

c
cpu_set_t get;
CPU_ZERO(&get);
if (sched_getaffinity(0, sizeof(get), &get) != -1) {
    printf("当前允许运行的核数: %d\n", CPU_COUNT(&get));
}

七、查询当前亲和性 #

绑之前先看当前状态，是排错的起点。三个层次，从粗到细。

第一层，读 /proc/<pid>/status 的 Cpus_allowed_list，快速确认外部工具或别的进程改过什么：

bash
grep -i cpus_allowed_list /proc/$$/status

第二层，用 sched_getaffinity 在代码里拿，能逐个核判断：

c
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <errno.h>
#include <string.h>

void dump_affinity(void)
{
    cpu_set_t get;

    CPU_ZERO(&get);
    if (sched_getaffinity(0, sizeof(get), &get) == -1) {
        fprintf(stderr, "sched_getaffinity 失败: %s\n", strerror(errno));
        return;
    }

    printf("允许运行的核数: %d\n", CPU_COUNT(&get));
    printf("核列表: ");
    for (int i = 0; i < CPU_SETSIZE; i++) {
        if (CPU_ISSET(i, &get)) {
            printf("%d ", i);
        }
    }
    printf("\n当前实际运行在: cpu(%d)\n", sched_getcpu());
}

第三层，sched_getcpu() 查「此刻在哪」。它和亲和性是两回事：亲和性回答「允许在哪」，sched_getcpu 回答「现在在哪」。两者一起看，才能判断绑核是否真的生效。

sched_getcpu() 的实现走 vDSO，不走系统调用。它在 vDSO 里直接读 CPU 寄存器（x86 上读 TSC_AUX 的段，ARM 上读 MPIDR），开销在十几纳秒量级，可以放进高频循环里采样。

对比一下错误做法。老代码常见拿 popen("ps -o psr= -p ...") 查当前核，背后是 fork 一个子进程、exec 一个 shell、shell 再 exec 一个 ps、管道重定向、结果文本解析。单次开销毫秒级，放在每秒百万次的循环里，光采样就把 CPU 吃掉了。要查当前核，sched_getcpu() 是唯一正确选择。

想验证绑核效果，最小流程是这样：

c
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>

int verify_pin(int target_cpu)
{
    cpu_set_t mask, get;

    CPU_ZERO(&mask);
    CPU_SET(target_cpu, &mask);
    if (sched_setaffinity(0, sizeof(mask), &mask) == -1) {
        return -1;
    }

    /* 设置之后重新读一遍，确认内核接受的是你想要的 */
    CPU_ZERO(&get);
    if (sched_getaffinity(0, sizeof(get), &get) == -1) {
        return -1;
    }
    if (!CPU_ISSET(target_cpu, &get)) {
        printf("设置未生效，目标核 %d 不在允许集合内\n", target_cpu);
        return -1;
    }
    if (CPU_COUNT(&get) != 1) {
        printf("警告：允许集合含 %d 个核，不是独占单核\n", CPU_COUNT(&get));
    }
    return 0;
}

读回来的集合会比你请求的小，也会比你请求的「不同」。原因有两个：一是 cgroup 的 cpuset 子系统在外面又套了一层限制，你的掩码被与 cpuset 取交集；二是你在有 isolcpus 的机器上绑了一个被隔离的核，内核允许你绑，但普通调度不会来抢。前者是硬限制，后者是软隔离，读一下 cpuset.cpus.effective 就能分清。

八、线程级绑核与进程级绑核 #

Linux 里没有「进程亲和性」这个独立概念。task_struct 是调度单位，一个进程的主线程是一个 task，每个子线程也是 task，每个 task 各有一份 cpus_mask。所谓进程级绑核，只是把该进程下所有 TID 的掩码都改成一样。

接口 操作对象 引入/规范 适用场景
sched_setaffinity(0, ...) 调用线程自身 Linux 2.5.8 线程内部自绑，最直接
sched_setaffinity(tid, ...) 指定 TID 的线程 Linux 2.5.8 外部监管进程给别人绑
pthread_setaffinity_np pthread_t 句柄 GNU 扩展 POSIX 线程代码，语义清楚
pthread_getaffinity_np pthread_t 句柄 GNU 扩展 获取 POSIX 线程掩码
taskset 进程 util-linux 不改代码，运维手段
numactl 进程 numactl 包 同时管 CPU 与内存

注意 sched_setaffinity 收的是 pid_t（对线程就是 TID），pthread_setaffinity_np 收的是 pthread_t。这两个不是同一个东西，glibc 里 pthread_t 是个不透明句柄，别把它强转成 pid_t 传进去，行为未定义。要拿 TID 用 syscall(SYS_gettid)。

c
#define _GNU_SOURCE
#include <pthread.h>

int pthread_setaffinity_np(pthread_t thread, size_t cpusetsize,
                           const cpu_set_t *cpuset);
int pthread_getaffinity_np(pthread_t thread, size_t cpusetsize,
                           cpu_set_t *cpuset);

_np 后缀的意思是 Non-Portable，非可移植扩展。返回值是错误码本身而不是 -1 加 errno，这点和 sched_setaffinity 不同，判断方式要跟着改。

多线程按索引一一对核，是最常见的绑核骨架：

c
#define _GNU_SOURCE
#include <sched.h>
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

#define THREAD_LIMIT 64

void *worker(void *arg)
{
    int tid = *(int *)arg;
    cpu_set_t mask, get;

    /* 1. 绑定：线程索引即目标核号 */
    CPU_ZERO(&mask);
    CPU_SET(tid, &mask);
    if (sched_setaffinity(0, sizeof(mask), &mask) == -1) {
        perror("sched_setaffinity");
        pthread_exit(NULL);
    }

    /* 2. 回读校验 */
    CPU_ZERO(&get);
    if (sched_getaffinity(0, sizeof(get), &get) == -1) {
        perror("sched_getaffinity");
        pthread_exit(NULL);
    }
    for (int i = 0; i < THREAD_LIMIT; i++) {
        if (CPU_ISSET(i, &get)) {
            printf("[+] 线程 %d 已绑定，允许核 %d\n", tid, i);
        }
    }

    /* 3. 密集计算，看稳态下的落核 */
    double dummy = 0.0;
    for (long i = 0; i < 500000000; i++) {
        dummy += 0.1 * i;
    }
    printf("[+] 线程 %d 结束，末次运行核 cpu(%d)\n", tid, sched_getcpu());

    pthread_exit(NULL);
}

int main(void)
{
    long cores = sysconf(_SC_NPROCESSORS_ONLN);
    if (cores > THREAD_LIMIT) {
        cores = THREAD_LIMIT;
    }
    printf("[*] 在线核数 %ld，创建等量绑核线程\n", cores);

    pthread_t threads[THREAD_LIMIT];
    int ids[THREAD_LIMIT];

    for (int i = 0; i < cores; i++) {
        ids[i] = i;
        if (pthread_create(&threads[i], NULL, worker, &ids[i]) != 0) {
            fprintf(stderr, "[-] 创建线程 %d 失败\n", i);
            return 1;
        }
    }
    for (int i = 0; i < cores; i++) {
        pthread_join(threads[i], NULL);
    }
    printf("[+] 全部线程结束\n");
    return 0;
}

C++11 的 std::thread 没有标准绑核接口，但留了 native_handle() 这个口子。Linux/glibc 下它返回的就是底层 pthread_t：

cpp
#include <thread>
#include <iostream>
#include <sched.h>
#include <pthread.h>
#include <system_error>

void pin_cpp_thread(std::thread &th, int core_id)
{
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(core_id, &cpuset);

    pthread_t handle = th.native_handle();
    int rc = pthread_setaffinity_np(handle, sizeof(cpu_set_t), &cpuset);
    if (rc != 0) {
        throw std::system_error(rc, std::generic_category(),
                                "pthread_setaffinity_np failed");
    }
}

int main()
{
    std::thread worker([] {
        std::cout << "[*] 工作线程初始运行于 cpu(" << sched_getcpu() << ")\n";
    });

    try {
        pin_cpp_thread(worker, 2);
        std::cout << "[+] 已锚定至核心 2\n";
    } catch (const std::exception &e) {
        std::cerr << "[-] 绑核失败: " << e.what() << "\n";
    }

    worker.join();
    return 0;
}

native_handle() 拿到的句柄只在 th 未 join 前可用，join 之后再传进去是悬垂句柄。绑核动作要在 join 之前做完。

进程级绑核在代码里得自己遍历 /proc/self/task 下的 TID：

c
#define _GNU_SOURCE
#include <dirent.h>
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* 把当前进程下所有线程绑到同一个核 */
int pin_process_all_threads(int cpu)
{
    cpu_set_t mask;
    DIR *dir;
    struct dirent *ent;
    int failed = 0;

    CPU_ZERO(&mask);
    CPU_SET(cpu, &mask);

    dir = opendir("/proc/self/task");
    if (dir == NULL) {
        return -1;
    }
    while ((ent = readdir(dir)) != NULL) {
        if (ent->d_name[0] == '.') {
            continue;   /* 跳过 . 和 .. */
        }
        pid_t tid = (pid_t)atoi(ent->d_name);
        if (sched_setaffinity(tid, sizeof(mask), &mask) == -1) {
            failed++;
        }
    }
    closedir(dir);
    return failed;
}

这个方法有个绕不开的时机问题：只能管到调用时刻已经存在的线程。之后再 pthread_create 的新线程会继承创建者当下的掩码，创建者没绑，新线程就不绑。稳妥做法是在每个线程入口处各绑一次，别指望在 main 里绑一遍就覆盖全部。

九、命令行工具：taskset #

taskset 是 util-linux 里的工具，改的是目标进程主线程的掩码。它不需要改代码，是排查和应急的首选。两种表达方式，掩码和列表：

表达方式 写法 示例 说明
十六进制掩码 直接给十六进制数 0x3 每一位对应一个核，低位是 0 号核
核心列表 -c 加逗号与连字符 -c 0-3,8-11 人类友好，推荐

掩码和核号的换算：

掩码 二进制 核
0x00000001 1 CPU 0
0x00000003 11 CPU 0、1
0x0000000f 1111 CPU 0、1、2、3
0x00000005 101 CPU 0、2
0x000000ff 1111 1111 CPU 0 到 7

常用命令组合：

bash
# 查看进程当前亲和性，掩码形式
taskset -p 12345
# 输出：pid 12345's current affinity mask: f

# 查看进程当前亲和性，核号列表形式
taskset -cp 12345
# 输出：pid 12345's current affinity list: 0-3

# 运行中改绑，绑到 1、2 和 5 到 8 号核
taskset -cp 1,2,5-8 12345

# 启动时绑核，限定 0 到 1 号核
taskset -c 0,1 ./my_app --port=8080

# 掩码写法，等价于绑到 0 和 1 号核
taskset 0x3 ./my_app

taskset 的完整参数：

参数 含义
-p, --pid 操作已存在的进程，不启动新进程
-c, --cpu-list 用核号列表而非掩码
-a, --all-tasks 作用于进程下所有线程
--help 查看帮助

-a 是关键。不带 -a 的 taskset -p 只改主线程，进程里的工作线程还在别的核上自由飘。多线程服务用 taskset 绑核不加 -a，等于只绑了最闲的那个线程。

bash
# 给多线程服务全量绑核
taskset -acp 0-3 12345

taskset 的边界要知道：它不能设置内存亲和性（那是 numactl 的活），不能突破 cgroup cpuset 的限制，不能阻止别的进程绑到同一个核。它只改掩码。

一个实操细节：taskset -c 的核号是逻辑编号，也就是 lscpu 输出里 CPU(s) 那一栏的编号，和 /proc/cpuinfo 的 processor 字段一致。在有超线程的机器上，0 和 4 常常属于同一个物理核，绑 0,4 两个线程看着是两核，实际在抢同一套执行单元。

十、绑核的典型场景 #

不是所有程序都该绑核。判断标准只有一条：这个程序的延迟对缓存命中敏感，或者它的线程之间有明确的物理隔离需求。

场景 绑核目的 绑法要点 反向代价
低延迟交易/撮合 消除迁移抖动，稳定 p99 独占隔离核，关中断，避开超线程对 可用核变少，突发流量无弹性
DPDK 数据面 轮询线程独占核，避免被打断 每队列绑一个核，管理面另置 轮询线程 100% 占核
实时音视频编解码 单帧处理时间可预期 编码线程与采集线程分核 核数不足时帧率抖动反增
高性能数据库引擎 减少 buffer pool 的缓存失效 绑 NUMA 本地节点，内存同绑 跨节点查询无加速
高频网关/负载均衡 网络软中断与业务线程分离 中断绑一组核，业务绑另一组 配置复杂，易错配
vCPU 与物理核对齐 减少宿主机调度噪声 1:1 pin，避开宿主管理核 迁移能力受限，不利弹性伸缩
基准测试 排除调度干扰，结果可复现 单核独占，清掉其他负载 结果不代表生产

低延迟交易系统的行情处理和撮合逻辑，一次处理链路常在几十微秒。这条链路里任何一次缓存冷启动都不是稳定的几百纳秒，而是几十微秒的尖峰。做法是把业务线程绑到被 isolcpus 隔离的核上，把网卡中断导到另一组核，让业务核上只有它自己。

DPDK 的数据面线程是纯轮询，while(1) 里不停查收包描述符。这种线程本身不怕调度，怕的是被换出去。绑核加隔离核之后，它能拿到接近 100% 的核时间，收包延迟从微秒级进到亚微秒级。

实时音视频编码，一帧的处理时间必须可预期。编码线程在核 0、采集线程在核 1，两者不抢执行单元，帧间隔就稳。核数不够时强行绑，两个线程挤在有限的核上互相等，帧率抖动更大。

数据库引擎的 buffer pool 是大块热点内存，缓存命中率直接决定查询延迟。把工作线程绑到 NUMA 本地节点，内存也用 --membind 绑在同一节点，避免远端访问，这条路上拿到的收益比单纯调大 buffer 明显。

网关类服务的瓶颈常在软中断。网卡收包触发中断，中断处理完再唤醒用户态线程，如果中断和业务在同一个核，业务线程每次都要被打断。做法是拆开：中断绑到 0 到 1 号核，业务绑到 4 到 7 号核。

虚拟化场景里，vCPU 是宿主机的线程。给 vCPU 做 1:1 的物理核绑定，能减少宿主机调度器带来的噪声，让虚拟机内部的延迟更稳。代价是失去弹性，宿主负载高的时候没法把 vCPU 挪走。

基准测试必须绑核。不绑核测出来的数字混着调度器的迁移决策，同一个程序跑两遍结果能差一截。绑单核、独占、清空其他负载，测出来的才是代码本身的性能。

每个场景背后是同一个判断：这条链路的瓶颈是缓存和抖动，不是算力。如果瓶颈是算力，绑核帮不上忙，加核或者改算法才有用。

十一、绑核的副作用与陷阱 #

绑核是有代价的动作，代价不对等时它会让事情变坏。

陷阱 表现 成因 处理
超线程同核误绑 两线程绑 0 和 4，性能不升反降 0 与 4 同物理核，抢执行单元 lscpu -e 查映射，隔开同物理核
空掩码 sched_setaffinity 返回 EINVAL CPU_ZERO 后忘了 CPU_SET 设置后用 CPU_COUNT 复核
只在 main 绑一次 后续新线程跑到别的核 新线程继承创建者掩码 每个线程入口各绑一次
cgroup cpuset 裁剪 掩码写了但只生效一部分 cpuset 在外层取交集 读 cpuset.cpus.effective
绑到同一个核 线程互相等，吞吐掉 线程数大于绑定核数 核数与线程数一起算
忽略 NUMA 绑了核，延迟反而更高 内存在远端节点 加 --membind 同绑
绑到 0 号核 系统管理任务在 0 号核抢 0 号核承担引导与管理中断 业务避开 0 号核
隔离核上死循环 该核假死，无法响应 isolcpus 核上没有调度机会 循环里加 nanosleep 或 sched_yield

超线程这条展开说。现代 CPU 一个物理核暴露两个逻辑核，共享 L1、L2 和执行单元。lscpu -e 能看出映射关系，输出里 CPU 是逻辑核编号，CORE 是物理核编号，同一 CORE 下的两个 CPU 是超线程对：

bash
lscpu -e

text
CPU  NODE  SOCKET  CORE  ONLINE
0    0     0       0     yes
1    0     0       1     yes
2    0     0       2     yes
3    0     0       3     yes
4    0     0       0     yes     <- 与 CPU 0 同物理核
5    0     0       1     yes     <- 与 CPU 1 同物理核
6    0     0       2     yes
7    0     0       3     yes

按这张表，要 4 个互不争抢的执行单元，绑 0,1,2,3，而不是把 4,5,6,7 混进来。

isolcpus 的坑单独讲。用内核启动参数把核隔离出来，能避免普通任务落上去：

text
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash isolcpus=2,3"

改完 /etc/default/grub 之后执行 sudo update-grub 再 sudo reboot。重启后，调度器在自动派发和负载均衡时会把核心 2、3 从调度池里摘出去。除非你显式用 sched_setaffinity 或 taskset 把任务派过去，否则没有普通进程会占用它们。这叫独占净空核。

代价是隔离核上不会自动跑任何管理任务，包括内核的周期性工作。绑上去的线程如果是纯忙等，这个核就没有机会处理别的事；更麻烦的是，一个不主动让出的忙等线程既不让出 CPU，也不响应外部唤醒，看起来像活着，实测不干活，也就是假死。

c
/* 隔离核上的工作循环，要给内核留出让出的窗口 */
for (;;) {
    do_one_round();
    if (no_pending_work()) {
        struct timespec ts = {0, 100000};   /* 100 微秒 */
        nanosleep(&ts, NULL);
    }
}

pthread_yield() 在隔离核上帮助有限，因为核上没有别的任务可切，它只是把 CPU 还回去又立刻拿回来。真要让出，用短 nanosleep，让内核有机会跑中断和定时器。

0 号核的约定也值得记一笔。0 号核承担引导、部分管理中断和不少内核线程，业务线程绑上去会被系统噪声干扰。不是绝对不能用，但压测要公平，尽量避开。

绑核后线程数超过绑定核数，是常见配置错误。8 个线程绑在 2 个核上，8 个线程的缓存互相挤，比不绑还差。

十二、中断亲和性 #

CPU 亲和性不只属于任务，也属于中断。硬件中断有一个目标 CPU 集合，描述在 /proc/irq/<num>/smp_affinity 里，格式和任务掩码一样是十六进制位图。

问题出在默认行为上。很多发行版默认开着 irqbalance 服务，它按中断量在各核之间搬中断。这个行为和绑核直接冲突：你把业务绑到核 2，irqbalance 觉得核 2 空闲，把网卡中断搬过来，业务线程每次收包前先跑一段中断处理。

单独关掉 irqbalance 只是第一步：

bash
sudo systemctl stop irqbalance
sudo systemctl disable irqbalance

之后手动把关键中断固定到你指定的核：

bash
# 看网卡对应的中断号
grep eth0 /proc/interrupts

# 看某条中断的亲和性
cat /proc/irq/123/smp_affinity
cat /proc/irq/123/smp_affinity_list

# 把中断 123 固定到 0 和 1 号核
echo 0-1 | sudo tee /proc/irq/123/smp_affinity_list
echo 3 | sudo tee /proc/irq/123/smp_affinity

两个文件写哪个都行，smp_affinity 收十六进制掩码，smp_affinity_list 收核号列表。写掩码的时候位序容易搞错，0-1 对应 0x3，0-3 对应 0xf。

需要全量固定中断时，别拿一条循环把多队列网卡废掉：

bash
# 错误示范：所有队列挤到 0-1，把 RSS 并行度打掉
for irq in /proc/irq/*/smp_affinity_list; do
    echo 0-1 | sudo tee "$irq" > /dev/null
done

# 正确做法：按队列逐个分配
echo 0 | sudo tee /proc/irq/124/smp_affinity_list
echo 1 | sudo tee /proc/irq/125/smp_affinity_list

中断亲和性和任务亲和性的关系，理清楚就好办：

维度 任务亲和性 中断亲和性
控制对象 task_struct 的 cpus_mask 中断描述符的目标核集合
用户接口 sched_setaffinity、taskset /proc/irq/N/smp_affinity[_list]
生效方式 下次调度生效 下次中断触发生效
默认策略 继承父任务掩码 由 irqbalance 动态调整
隔离目标 让任务只在指定核 让中断避开指定核
常见冲突 cpuset 裁剪 irqbalance 搬移

隔离思路是反的：任务亲和性把任务拉到你想要的核上，中断亲和性把中断从你不想要的核上赶走。两者配合，业务核上才能只跑业务。还有一层，网卡的 ksoftirqd/N、kworker/N 也是任务，同样可以绑核，把它们和中断放在同一组核上，业务核就干净了：

bash
ps -eLo pid,tid,psr,comm | grep -E 'ksoftirqd|kworker'

psr 那一列就是线程此刻所在的核，直接能看出它有没有漂。

十三、性能观测：怎么验证绑对了 #

绑核效果不能凭感觉，要有数字。四个层面依次验证：设对了没有、跑对没有、快了多少、抖了多少。

第一层，掩码对不对。命令行版：

bash
taskset -cp <pid>
cat /proc/<pid>/status | grep -i cpus_allowed_list

第二层，线程实际落核。ps 的 psr 字段是采样值，适合粗看：

bash
# 看进程下所有线程此刻在哪个核
ps -eLo pid,tid,psr,pcpu,comm | grep my_app

# 每秒采样一次，观察是否漂移
watch -n 1 'ps -eLo pid,tid,psr,comm | grep my_app'

psr 每次读到的都是瞬时值，绑在单核上的线程读数应该始终是同一个数。读数来回变，说明掩码没生效，或者绑的核不止一个。

第三层，迁移次数。这是绑核最直接的证据：

bash
grep -E 'nr_migrations|nr_switches|se.sum_exec_runtime' /proc/<pid>/sched

nr_migrations 是任务被迁移的次数。绑单核的线程，这个数在启动后趋于不动；不绑核时它随负载均衡持续增长。看线程要换成 /proc/<pid>/task/<tid>/sched。

第四层，延迟分布，这是最终判据：

bash
# 记录一段时间的调度事件，看唤醒延迟
sudo perf sched record -p <pid> -- sleep 10
sudo perf sched latency

# 迁移次数与上下文切换次数
perf stat -e context-switches,cpu-migrations -p <pid> -- sleep 5
mpstat -P ALL 1

cpu-migrations 这个计数器直接就是迁移次数，绑核前后各跑一次，数值差异一眼可见，这是最省事的验证手段。

绑核正确的机器，mpstat 会出现几个核 %usr 接近 100、其余核接近 0 的形态。所有核都在 30% 上下晃，说明绑核没生效，或者绑了但任务根本不够重。负载均匀分布不是「绑得很均衡」，是没绑上。

内存侧配合 numastat -c my_app，numa_miss 与 numa_foreign 持续上涨，说明 CPU 和内存没绑到同一节点。

把验证流程压成一张表：

层次 检查项 命令/接口 合格标准
掩码 允许集合 taskset -cp、sched_getaffinity 与你设置的核完全一致

迁移 迁移计数 perf stat -e cpu-migrations 数值趋近于 0

十四、易错点速查 #

出问题时从上往下对。

现象 先查这里 具体动作
编译报 cpu_set_t 未定义 _GNU_SOURCE 位置 放到所有 #include 之前
sched_setaffinity 返回 EINVAL 掩码是否为空 CPU_ZERO 后必须 CPU_SET
返回 EPERM 目标进程属主 换用户或提权
返回 ESRCH 目标 PID 进程已退出，用 TID 而非 PID 绑线程
绑定成功但读数不变 是否绑了多个核 用 CPU_COUNT 确认是 1
绑了单核仍迁移 掩码被 cpuset 裁剪 读 cpuset.cpus.effective
新线程不听话 绑核时机 线程入口各绑一次，别只在 main 绑
线程全挤在一个核 索引映射 线程数与核数核对，避开超线程对
性能反而下降 超线程同核、核数不足 lscpu -e 查 CORE 列
延迟尖峰没消失 中断在同核 关 irqbalance，改 smp_affinity
NUMA 机器无收益 内存跨节点 numactl --membind 同绑
隔离核上任务假死 忙等不让出 循环里加 nanosleep
绑到 0 号核被干扰 系统管理负载 业务挪到 1 号核之后
taskset 改了没用 未加 -a 多线程要 taskset -acp
大核数机器掩码截断 CPU_SETSIZE 上限 改用 CPU_ALLOC 与 CPU_*_S

几组固定搭配，抄过去就能用：

bash
# 查拓扑：核、物理核、NUMA 节点
lscpu -e
numactl -H

# 看某个进程的亲和性与当前落核
taskset -cp <pid>
ps -eLo pid,tid,psr,comm | grep <name>

# 运行中改绑全部线程
taskset -acp 4-7 <pid>

# 带内存绑定的启动
numactl --physcpubind=4-7 --membind=0 ./my_server

# 验证迁移次数
perf stat -e cpu-migrations -p <pid> -- sleep 5

c
/* 最小可用绑核，拿去改成自己的 */
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <errno.h>
#include <string.h>

static int pin_to_cpu(int cpu)
{
    cpu_set_t set;

    CPU_ZERO(&set);
    CPU_SET(cpu, &set);

    if (sched_setaffinity(0, sizeof(set), &set) == -1) {
        fprintf(stderr, "bind cpu %d 失败: %s\n", cpu, strerror(errno));
        return -1;
    }
    return 0;
}

int main(void)
{
    int cpu = 2;

    if (pin_to_cpu(cpu) == -1) {
        return 1;
    }
    printf("已在 cpu(%d) 上，目标 %d\n", sched_getcpu(), cpu);

    /* 后续业务代码 */
    return 0;
}

回头收一遍全文的线索。绑核省掉的是跨核迁移的缓存失效和上下文切换，不是把单核算力变大，这个预期不摆正，压测结果一定会让人失望。NUMA 机器上 CPU 和内存必须一起绑，只绑一半等于白做。接口只有那么几个，sched_setaffinity 自 Linux 2.5.8 稳定至今，CPU_SETSIZE 默认 1024 位，够绝大多数场景用。taskset 管不改代码的场合，numactl 管内存，/proc/irq/N/smp_affinity 管中断，三件工具各管一段。最后一步永远是验证：掩码、落核、迁移计数、延迟分布，四层都对上了，绑核才算真的生效。
