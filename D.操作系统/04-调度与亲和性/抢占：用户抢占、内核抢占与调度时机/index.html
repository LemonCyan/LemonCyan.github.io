一条主线先记住：用户抢占看的是「返回用户空间那一刻 need_resched 有没有置位」，内核抢占看的是「内核态运行时能不能在进程不情愿的时候被换出去」。判据不同，别混。

一、什么是抢占 #

抢占是内核在进程不配合的时候，把它从 CPU 上换下来的强制行为。

进程离开 CPU 只有两条路：

  • 自己让：等锁、等 IO、等信号量，把状态改成睡眠，主动调 schedule()。
  • 被别人顶掉：时间片烧完，或者更高优先级的进程刚被唤醒，内核把当前进程踢下去。

第二条就是抢占。判据只有一条：当前进程有没有同意。

早期 Linux 内核不可抢占。调度方式很直白：进程可以调 schedule() 自愿启动一次调度；非自愿的强制调度只发生在两个位置——每次从系统调用返回的前夕，每次从中断或异常处理返回用户空间的前夕。系统空间里发生中断或异常，不会引起调度。

这套设计让内核实现简单很多，代价是两件事。

第一件是延迟。中断发生在内核中时，中断返回不调度，要等到最初让 CPU 从用户空间进入内核空间的那次系统调用或中断返回，才有机会切换。

第二件是优先级反转。内核态运行的操作优先级高于任何用户态进程。一个低优先级用户进程在内核里跑长路径，高优先级任务只能干等。当内核执行长的系统调用时，实时进程要等到内核中运行的进程退出内核才能被调度，由此产生的响应延迟在今天的硬件上仍然可以到 100ms 级。

Linux 2.6 引入内核抢占（preempt）。用户程序在执行系统调用期间可以被抢占，该进程暂时挂起，新唤醒的高优先级进程得到 CPU。这种抢占不能在内核任意位置安全进行——临界区里的代码不行。临界区指同一时间不允许超过一个进程执行的指令序列，Linux 内核里这些部分用自旋锁保护。

内核抢占有一个连带要求：内核中所有会被一个以上进程共享的变量和数据结构，都要通过互斥机制保护，也就是都要放进临界区。抢占式内核的判定口径是——只要内核不在中断处理程序里，也不在被 spinlock 这类互斥机制保护的临界代码里，就认为可以安全地切换进程。

Linux 内核把临界代码都加了互斥保护，同时在运行时间过长的代码路径上插入调度检查点，打断过长的执行路径。任务能快速切换进程状态，也为内核抢占做好准备。

抢占分两层，这是本篇的骨架：

层次 谁被换掉 判据 引入版本
用户抢占 用户态刚返回、还没跑几条指令的进程 返回用户空间时 need_resched 置位就 schedule() 2.4 起就有，2.6 沿用
内核抢占 正在内核态执行系统调用的进程 返回内核空间或抢占计数归零时，preempt_count == 0 且 need_resched 置位 2.6 引入

用户抢占对所有内核都成立，不可抢占内核也有用户抢占。内核抢占要 CONFIG_PREEMPT 打开才有。这句是后面所有讨论的地基。

二、抢占与协作式调度的区别 #

协作式调度（cooperative）的规则是：内核代码一旦开始跑，就一直跑到它自己愿意交出 CPU 为止。调度程序没有办法在一个内核级任务正在执行的时候重新调度——内核中的各任务按协作方式调度，不具备抢占性。

不可抢占内核的特点写下来就一句：内核代码一直执行到完成（返回用户空间）或者明显阻塞为止。

两者对照：

维度 协作式（不可抢占内核） 抢占式（CONFIG_PREEMPT）
内核态执行 一路跑到底，除非自己阻塞 满足条件就被换出
切换触发点 只在自己调 schedule() 或阻塞处 自己让出 + 中断返回 + 解锁 + 使能软中断
内核实现复杂度 低，共享数据不用逐处设防 高，共享数据必须进临界区
实时响应 取决于内核里最长的那条路径 取决于最长的那段不可抢占区间
吞吐 上下文切换少，缓存友好 切换多，加锁有开销
典型延迟 100ms 级 微秒到毫秒级，看配置

协作式并非没有好处。切换次数少，锁开销小，单核批处理场景跑得比抢占式舒服。它的问题只出在一件事上：你没法给响应时间一个上界。

不可抢占内核留下两个具体麻烦：

一是中断嵌套的延迟。如果中断发生在内核中，本次中断返回不会引起调度，要等到最初让 CPU 进入内核的那次系统调用或中断（异常）返回时才会发生调度。也就是说，中间嵌套多少层中断都不会触发切换。

二是优先级反转。内核态运行的任何操作都优先于用户态进程。一个低优先级用户进程由于执行软中断或硬中断处理，就能让一个高优先级任务得不到及时响应。

抢占式内核针对这两点动手，思路是给「内核不可打断」这件事划出边界：绝大多数内核代码可以被换出，少数必须原子完成的段落用计数挡住。

三、用户抢占：返回用户空间时的检查 #

用户抢占的位置很确定：内核即将返回用户空间的时候。

此刻内核知道自己是安全的——它已经把该做的事做完了，栈上状态已经收拢，返回用户空间不会把内核数据结构留在半截。所以内核无论是在从中断处理程序返回，还是从系统调用返回，都会检查 need_resched 标志。置位了就选一个更合适的进程投入运行。

用户抢占发生在：

  • 从系统调用返回用户空间。
  • 从中断处理程序返回用户空间。

只有这两个入口，因为用户态只能从这两个入口进入。

看 ARM 上的返回路径，ret_to_user 是两条路的汇合点：

text
ENTRY(ret_from_exception)          @ 异常返回
    get_thread_info tsk
    mov  why, #0
    b    ret_to_user

__irq_usr:                         @ 用户态收到中断
    usr_entry
    kuser_cmpxchg_check
    ...
    b    ret_to_user

ENTRY(ret_to_user)
ret_slow_syscall:
    disable_irq
    ldr  r1, [tsk, #TI_FLAGS]
    tst  r1, #_TIF_WORK_MASK
    bne  work_pending

work_pending:
    tst  r1, #_TIF_NEED_RESCHED
    bne  work_resched

work_resched:
    bl   schedule

这段汇编值得逐行读一遍。TI_FLAGS 是 thread_info 里的标志字，_TIF_WORK_MASK 是一组「返回用户态之前必须处理完的待办」掩码——信号、单步、need_resched 都在里面。先粗筛一次 _TIF_WORK_MASK，有活才跳 work_pending；进了 work_pending 再细查 _TIF_NEED_RESCHED，置位就 bl schedule。

两层判断的意义是省一条快路径。绝大多数返回用户空间的场合没有任何待办，第一条 tst 直接过掉，不进慢路径。

用户抢占的关键性质：它只能在返回用户空间时发生。一个进程如果在用户态跑，时间片用完了，内核不会立刻抢它的 CPU——时间片用完这个事实记在 need_resched 里，等到下一次它进内核再返回时兑现。对纯计算型进程来说，抢占的粒度就是一个 tick。

四、内核抢占：内核态能不能被抢占 #

内核抢占回答的是另一个问题：一个进程正在内核态执行系统调用，能不能被换下去。

不支持内核抢占的系统里，进程一旦运行于内核空间，就可以一直执行，直到它主动放弃或时间片耗尽。这样一些非常紧急的进程会长时间得不到运行。

支持内核抢占的系统里，更高优先级的进程可以抢占正在内核空间运行的低优先级进程。

判定能不能抢，看三个条件同时成立：

  1. 内核不在中断处理程序中。
  2. 内核不在软中断或 tasklet 的底半部里。
  3. 没有持有 spinlock、读写锁这类互斥机制保护的临界代码，即抢占计数为 0。

三个条件都满足，内核态就是可抢占点。

禁止内核抢占的情况，四条记牢：

序号 禁止抢占的场景 何时恢复抢占
1 内核正在执行中断处理例程 中断返回时再执行内核抢占
2 内核正在执行软中断或 tasklet 软中断返回时再执行内核抢占
3 处在临界区，持有自旋锁、读写锁 释放锁、抢占计数减到 0 时
4 内核正在执行调度程序本身 不需要恢复，抢占的理由就是调新进程

第 4 条的理由很直白：抢占的目的就是进行一次新的调度，没有理由把调度程序抢占掉再运行一遍调度程序。schedule() 内部会检测抢占计数，避免普通调度过程中又递归触发一次内核抢占调度。

第 1 条要注意细节：硬件中断返回前会执行软中断，此时仍然处在中断上下文里，所以软中断和硬中断的禁止是连着的一段。

第 3 条是内核抢占能成立的核心。持有自旋锁时被抢占，持锁进程被换下去，另一个 CPU 上的进程来抢同一把锁就只能自旋等死锁释放——而持锁者根本没在跑。死等就是这么来的。

用户抢占与内核抢占的判据摆在一起：

判据 用户抢占 内核抢占
发生位置 中断或系统调用返回用户空间的路径上 内核态内部，返回内核空间或抢占计数归零处
检查什么 只查 need_resched 查 preempt_count == 0 再查 need_resched
是否看抢占计数 不看 必看
前置条件 内核即将回到用户态 不处在中断上下文、不持有锁、不在调度器里
依赖配置项 无 CONFIG_PREEMPT
被换下的进程处于 用户态 内核态，正跑系统调用

一张表里最该记住的是第三行：用户抢占不看 preempt_count，因为用户态没有临界区概念；内核抢占必须看，因为内核态随时握着别人要的锁。

五、need_resched 标志 #

内核得知道什么时候该调 schedule()。只靠用户程序显式调用，它们就会一直执行下去。内核为此准备了一个 need_resched 标志，表明是否需要重新执行一次调度。

实现上它是 thread_info 里的一个标志位 TIF_NEED_RESCHED，检查它的接口是 need_resched()：

c
#define need_resched()  test_thread_flag(TIF_NEED_RESCHED)

谁来置位？两个主要来源：

置位来源 触发条件 函数
时间片耗尽 每个 tick 进程陷入内核后时间片递减 1，减到 0 时置位 scheduler_tick() / update_process_times()
高优先级进程被唤醒 被唤醒进程的优先级高于当前进程 try_to_wake_up()

第一条的链路是：时钟中断 → update_process_times() → scheduler_tick()。每个 tick 进程陷入内核后时间片递减 1，减到 0 时把 TIF_NEED_RESCHED 置 1。

第二条的链路是：某个事件唤醒一个睡眠进程 → try_to_wake_up() 算优先级 → 比当前进程高的，置位 TIF_NEED_RESCHED。这就是「唤醒即抢占」的来源，也是交互式进程响应快的原因。

标志位只是记账，它本身不切换任何东西。真正发生切换，要等某一处代码显式检查它。这个检查点就是下一章的主题。

一个容易忽略的点：need_resched 是每进程的，不是每 CPU 的全局开关。它挂在 thread_info 上，所以谁的时间片用完就置谁的位，检查的时候查的是当前进程那一个。

字段位置随版本变过。老版本把 flags 和 preempt_count 一起放在 thread_info 里，5.x 之后 thread_info 变成 task_struct 的内嵌成员，物理位置挪了。need_resched() 和 preempt_count() 这两个抽象接口没变，所以看代码时按接口走，别死记偏移。

六、抢占发生的时机 #

need_resched 置位之后，内核要在合适的点兑现它。这些点就是调度时机。

那句话要拆开看：「检查 need_resched」不等于「发生调度」，「检查」还要配上一个前提条件。五个时机，前提各不相同：

时机 检查什么 前提条件
中断返回内核空间 preempt_count 是否为 0，TIF_NEED_RESCHED 是否为 1 被中断的是内核态代码
中断或异常返回用户空间 只查 TIF_NEED_RESCHED 是否为 1 被中断的是用户态代码
显式或隐式调 preempt_enable() preempt_count 是否为 0，TIF_NEED_RESCHED 是否为 1 计数刚减到 0
使能软中断（local_bh_enable()） preempt_count 是否为 0，TIF_NEED_RESCHED 是否为 1 软中断上下文已退出
自己主动调 schedule() 不查，直接让 自愿

五条里只有最后一条是自愿的，前四条都是抢占路径。前四条又分成两组：第 2 条是用户抢占，第 1、3、4 条是内核抢占。

为什么第 1 条和第 2 条查的东西不一样？因为返回到哪儿决定了安全边界。

返回到用户空间时，内核已经彻底离开自己的数据结构，栈上不留半截状态，切走绝对安全，所以只看有没有人排队，不关心抢占计数。返回到内核空间时，内核还要继续往下跑，锁还在手上、上下文还在中断里，所以必须先确认抢占计数归零，确认自己站在可抢占点上。

第 3 条和第 4 条是「条件消失的那个瞬间」。加锁期间禁止抢占，解锁的瞬间条件消失，正好顺手检查一次。这是把检查点缝到释放路径上的做法：不用额外扫描，谁解除阻塞谁负责检查。

第 5 条是自愿调度，跟抢占无关，列在这里是为了完整——schedule() 只有这五种入口，记全了就不会漏。

还有一个隐含前提：这五条全都要当前进程在跑。如果 CPU 上正在跑的是 idle 线程，没有可抢占对象，need_resched 置位也只是让 idle 提前退出。

七、从系统调用与中断返回时的抢占 #

这一章看两条真实的返回路径。它们把上一章的第 1 条和第 2 条落地成汇编。

从硬中断返回内核空间，走的是 retint_kernel。x86 64 位（arch/x86/entry_64.S）里的骨架：

text
#ifdef CONFIG_PREEMPT
ENTRY(retint_kernel)
    cmpl $0, threadinfo_preempt_count(%rcx)
    jnz  retint_restore_args
    bt   $TIF_NEED_RESCHED, threadinfo_flags(%rcx)
    jnc  retint_restore_args
    bt   $9, EFLAGS-ARGOFFSET(%rsp)
    jnc  retint_restore_args
    call preempt_schedule_irq
    jmp  exit_intr
#endif

三道闸门，顺序不能换：

  1. cmpl $0, threadinfo_preempt_count —— 抢占计数不为 0 就直接返回，一个字都不多查。
  2. bt $TIF_NEED_RESCHED —— 没人排队也直接返回。
  3. bt $9, EFLAGS —— 中断标志位没置起来就不抢，先恢复现场。

三道都过了才 call preempt_schedule_irq。注意这三道闸门里没有一道是「判断要不要调度」，全都是「判断能不能调度」。要不要调度早就在 need_resched 里定好了，这里只负责确认现场安全。

preempt_schedule_irq 是出中断上下文时内核抢占调度的入口点。它被调用和返回时中断是关着的，这保护它不被中断递归调用：

c
asmlinkage void __sched preempt_schedule_irq(void)
{
    enum ctx_state prev_state;

    /* Catch callers which need to be fixed */
    BUG_ON(preempt_count() || !irqs_disabled());

    prev_state = exception_enter();
    do {
        __preempt_count_add(PREEMPT_ACTIVE);
        local_irq_enable();
        __schedule();
        local_irq_disable();
        __preempt_count_sub(PREEMPT_ACTIVE);
        /*
         * Check again in case we missed a preemption opportunity
         * between schedule and now.
         */
        barrier();
    } while (need_resched());

    exception_exit(prev_state);
}

几个细节：

  • BUG_ON(preempt_count() || !irqs_disabled()) 是一道自检。这个入口要求调用者进来时抢占计数为 0、中断关着，不符合就是调用者写错了。
  • 循环里 __preempt_count_add(PREEMPT_ACTIVE) 把抢占计数抬高，再开中断、调 __schedule()。抬高计数是为了让调度器知道自己在抢占路径上，别把当前进程从运行队列里摘掉——它没睡觉，只是被顶了一下。老版本用 TASK_PREEMPTED 进程状态标记同一个意思，两代实现换的是形式，语义一样。
  • local_irq_enable() 在 __schedule() 之前打开中断。切换过程本身很长，中断关着会拖坏整个系统。
  • 尾巴上的 while (need_resched()) 是复查。__schedule() 返回后到下一次检查之间有个窗口，期间又有高优先级进程被唤醒，那就再抢一次。barrier() 保证编译器不去调整这条重读的顺序。

再看 ARM 内核态接收中断的路径，__irq_svc：

text
__irq_svc:                          @ 内核态接收到中断
    svc_entry
...
#ifdef CONFIG_PREEMPT
    get_thread_info tsk
    ldr  r8, [tsk, #TI_PREEMPT]     @ 取抢占计数
    add  r7, r8, #1                 @ 进入中断，计数加 1
    str  r7, [tsk, #TI_PREEMPT]
#endif
    irq_handler                     @ 中断处理
#ifdef CONFIG_PREEMPT
    str  r8, [tsk, #TI_PREEMPT]     @ 恢复抢占计数
    ldr  r0, [tsk, #TI_FLAGS]       @ 取标志
    teq  r8, #0                     @ 抢占计数是否为 0
    movne r0, #0                    @ 非 0 就把标志清零
    tst  r0, #_TIF_NEED_RESCHED
    blne svc_preempt
#endif
svc_preempt:
    mov  r8, lr
1:  bl   preempt_schedule_irq       @ 调度
    ldr  r0, [tsk, #TI_FLAGS]
    tst  r0, #_TIF_NEED_RESCHED
    moveq pc, r8

重点在 teq r8, #0 加 movne r0, #0 这两句。它没有直接判断「计数为 0 就抢」，而是用「计数非 0 就把标志清掉」的写法，把两个条件压成一次跳转。计数不为 0 时 r0 变 0，后面的 tst 必然不命中，自然不会抢。ARM 上的老代码爱用这种写法省指令。

进入中断时把 TI_PREEMPT 加 1，退出时恢复原值——注意是恢复 r8 里存的旧值，不是减 1。中断嵌套时这样才对：三层嵌套只留最外层的原值，不会因为进出次数不配对而漂移。

软中断这一侧走的是另一个入口。在打开页出错函数 pagefault_enable 和软中断底半部开启函数 local_bh_enable 里，会调用 preempt_check_resched 检查是否需要执行内核抢占：

c
#define preempt_check_resched() \
do { \
    if (should_resched()) \
        __preempt_schedule(); \
} while (0)

should_resched() 把两件事合成一个判断：抢占计数是否为 0，need_resched 是否置位。两个都满足才进 __preempt_schedule()。

preempt_schedule 的源码与 preempt_schedule_irq 基本一样，差别在它进来时中断不一定关着，所以不需要 BUG_ON(!irqs_disabled())，也不需要临时开中断。两条路径共用一个核心循环，这个设计让「从哪进来」变得不重要——只要满足条件，切换逻辑只有一份。

八、抢占点与 preempt_count #

内核抢占能成立的前提是一个可数的开关。Linux 在进程结构里加了 preempt_count，作为内核抢占锁：为 0 表示可以进行内核抢占。

老版本它在 thread_info 里，和 flags 挨着：

c
struct thread_info {
    struct task_struct      *task;
    struct exec_domain      *exec_domain;
    __u32                   flags;
    __u32                   status;
    __u32                   cpu;
    int                     preempt_count;
    mm_segment_t            addr_limit;
    struct restart_block    restart_block;
#ifdef CONFIG_IA32_EMULATION
    void __user             *sysenter_return;
#endif
};

这个计数器不是布尔值，它是一个位域，按段划分用途：

位段 含义 谁加
PREEMPT_MASK 显式 preempt_disable() 的嵌套层数 锁、RCU 读侧、链表遍历
SOFTIRQ_MASK 软中断禁用嵌套层数 local_bh_disable()
HARDIRQ_MASK 硬中断嵌套层数 中断入口
NMI_MASK NMI 嵌套层数 NMI 入口

整段加起来非 0，内核就不许被抢占。分段的目的是让代码能单独判断「我现在在中断里吗」「我在软中断里吗」，而不是只知道「总数非 0」。

加计数和减计数的动作被包成宏，全部在 include/linux/preempt.h：

c
#define preempt_count_add(val)  __preempt_count_add(val)
#define preempt_count_sub(val)  __preempt_count_sub(val)

#define preempt_count_dec_and_test() __preempt_count_dec_and_test()

#define __preempt_count_inc()   __preempt_count_add(1)
#define __preempt_count_dec()   __preempt_count_sub(1)
#define preempt_count_inc()     preempt_count_add(1)
#define preempt_count_dec()     preempt_count_sub(1)

开抢占的那个宏是整套机制的关键：

c
#ifdef CONFIG_PREEMPT_COUNT
#define preempt_enable() \
do { \
    barrier(); \
    if (unlikely(preempt_count_dec_and_test())) \
        __preempt_schedule(); \
} while (0)

#define preempt_check_resched() \
do { \
    if (should_resched()) \
        __preempt_schedule(); \
} while (0)
#else
#define preempt_enable() \
do { \
    barrier(); \
    preempt_count_dec(); \
} while (0)

#define preempt_check_resched() do { } while (0)
#endif

preempt_count_dec_and_test() 减一并返回结果是否为 0。减完不是 0 说明还有别的禁用嵌套着，什么也不做；减到 0 说明这是最外层，unlikely 分支进去触发一次抢占检查。

barrier() 挡在减计数之前，防止编译器把计数修改挪到临界区外面去。这段代码没有加锁，全靠这个屏障保证顺序。

CONFIG_PREEMPT_COUNT 关掉时，preempt_enable() 退化成一句 preempt_count_dec()，preempt_check_resched() 退化成空语句。抢占计数整个不参与编译，代价归零——这是给不需要内核抢占的配置省开销。

再看不带检查的版本，供那些明确知道自己不该触发调度的路径使用：

c
#define preempt_disable_notrace() \
do { \
    __preempt_count_inc(); \
    barrier(); \
} while (0)

#define preempt_enable_no_resched_notrace() \
do { \
    barrier(); \
    __preempt_count_dec(); \
} while (0)

notrace 后缀是给 ftrace 用的：这些函数出现得太频繁，被追踪会淹掉 trace 缓冲，也容易在追踪器内部形成递归。

谁在用这套 API？凡是「这段代码不能被换出去」的地方：

  • 互斥机制：spinlock、读写锁、RCU 读侧临界区。
  • 中断代码：中断入口加计数，出口减计数。
  • 链表数据遍历：遍历过程中节点会被别的 CPU 摘掉，遍历期间不能换出。
  • 底半部：local_bh_disable() 到 local_bh_enable() 之间。

临界代码运行完，需要开启内核抢占。这个「关—开」配对不配对，是内核里最常见的一类 bug：多减一次会让抢占计数下溢，少减一次会让这台 CPU 永远不能被抢占，症状是系统卡死但没报错。

抢占式内核对内核的改造主要有两点：

一是改中断的入口代码和返回代码。中断入口把 preempt_count 加 1，禁止内核抢占；中断返回处把 preempt_count 减 1，使内核重新可被抢占。

二是改写自旋锁和读写锁的语义，在锁操作里增加对 preempt_count 的操作。加锁时计数加 1 禁止内核抢占；释放锁时计数减 1，并在抢占条件满足且需要重新调度时进行抢占调度。

看 _spin_unlock 的实现就能看到这个配对：

c
void __lockfunc _spin_unlock(spinlock_t *lock)
{
    spin_release(&lock->dep_map, 1, _RET_IP_);
    _raw_spin_unlock(lock);
    preempt_enable();
}

_raw_spin_unlock 放开的是锁本身，preempt_enable() 放开的是抢占。两件事分开做，顺序不能反：必须先真放锁，再允许抢占——反过来的话，抢占窗口里别人拿到锁，而你以为自己还持着。

除了加计数，抢占式内核还在运行时间过长的代码路径上插入调度检查点，打断过长的执行路径。这类检查点用 cond_resched() 落地，常见于循环体内部。

于是「可抢占点」有了精确定义：preempt_count == 0 的那一刻。一个内核函数的抢占延迟，等于它内部最长的一段连续 preempt_count != 0 的区间。

九、抢占的代价：为什么要权衡 #

内核抢占不是免费的。它的成本分四层，从里到外。

第一层，共享数据必须逐处设防。内核抢占要求内核中所有会被一个以上进程共享的变量和数据结构都通过互斥机制保护，也就是都放进临界区。这件事的工作量跟内核代码量成正比，而且没有「漏了也不会出事」的余地——漏一处就是一个竞态。

第二层，加锁本身的开销。preempt_disable/preempt_enable 各自带一条编译器屏障，一次加解锁就多两条屏障加两次内存写。看着不多，但 spinlock 在内核里每秒被拿上百万次。

第三层，上下文切换的开销。切换一次要换页表、污染 TLB、丢缓存局部性。抢占把「本来能一直跑完」的路径切成几段，每段都会被打断。

第四层，调试成本。竞态的复现依赖时序，抢占式内核里的竞态一千次里错一次，压测一周才逮到。不可抢占内核里大部分竞态压根不存在，因为不存在「跑到一半被换走」这件事。

代价和收益的对照：

维度 不可抢占内核 抢占式内核
共享数据保护 少量关键路径 所有共享数据逐处设防
每次加解锁开销 低 多两条屏障和两次计数写
上下文切换次数 少 多，尤其负载重时
缓存与 TLB 局部性 好 被打断就丢
最长响应延迟 内核里最长的那条路径，100ms 级 最长的那段不可抢占区间
竞态调试难度 低，大部分竞态不存在 高，时序依赖，难复现
吞吐上限 高 略低

这里有个反向的账要算。如果为了响应快而无脑加抢占点，切换次数上去了，吞吐掉下来，缓存全废。如果为了吞吐把临界区拉长，响应又回去了。真正的取舍点在那个「最长不可抢占区间」上——它决定了实时性上限，也决定了你愿意为实时性付多少吞吐。

反过来，不可抢占内核的「简单」也不是白拿的：它把延迟的账推给了用户。一个实时进程被低优先级进程的系统调用挡在后面，这个延迟没人管，因为内核压根没打算管。

还有一笔隐性成本容易被忽视。抢占式内核里，preempt_disable() 到 preempt_enable() 之间的代码段变多了，而这些段落每一个都是「延迟贡献者」。函数调用链一长，嵌套层数一多，实际的最坏延迟远大于单段临界区的长度。测量抢占延迟时量的不是单点，是整条链。

所以「要不要内核抢占」从来不是技术能不能做到的问题，是「你的延迟上界要求多少，愿意拿多少吞吐去换」的问题。下面几章把这个权衡拆到具体配置项上。

十、自愿抢占与非自愿抢占 #

内核统计进程被换下 CPU 的次数，分两类记账。

自愿切换：进程自己调 schedule() 让出 CPU。等锁、等 IO、等信号量、sleep()、nanosleep()，都属于这类。

非自愿切换：进程不想让，被内核顶掉。用户抢占和内核抢占都算在这一类里。

用户态能看到这两个数：

text
$ grep ctxt /proc/<pid>/status
voluntary_ctxt_switches:        1204
nonvoluntary_ctxt_switches:     37

两个数的比值说明很多东西：

比值 进程在干什么
自愿远大于非自愿 交互式或 IO 密集型，大部分时间在等
非自愿远大于自愿 CPU 密集，一直在被时间片踢下去
两个都很小 刚起来的进程，或者被阻塞住的进程
非自愿持续增长且进程很闲 CPU 争抢严重，或者被别的高优先级任务挤

要分清一个界限：非自愿切换不等于内核抢占。时间片用完被换下，发生在返回用户空间的路径上，那是用户抢占。只有进程在内核态跑着被换下去，才是内核抢占。/proc 里这两个字段不区分这层，要区分得看栈或者用 perf sched。

为什么值得分这两类？因为两者的调优手段不一样。

自愿切换多的进程，瓶颈在等待对象上——锁争用、磁盘慢、网络延迟。加 CPU 核没用，得看它等什么。

非自愿切换多的进程，瓶颈在 CPU 上——要么它自己算太久，要么别人跟它抢。这时候调 nice、绑核、减负载才有意义。

十一、抢占与实时性的关系 #

实时系统对响应时间有严格限定。一个实时进程被实时设备的硬件中断唤醒后，应该在限定的时间内被调度执行。

Linux 在不可抢占的年代满足不了这条。内核不可抢占，意味着不能确定系统在内核中的停留时间。实时进程要等到内核中运行的进程退出内核才能被调度，响应延迟能到 100ms 级。

这个 100ms 不是最坏值，是常见值。真正的上界取决于当时内核里跑的是什么：一次大的 write() 回刷、一次内存回收、一次驱动里的大循环，都能把延迟推到几百毫秒。

抢占把「内核停留时间」变成可分析的量。开了内核抢占之后，最坏调度延迟等于：

text
最坏延迟 = 最长不可抢占区间 + 关中断时间 + 中断处理时间 + 调度器自身耗时

四项里第一项是主导。找不可抢占区间，就是找 preempt_count != 0 的最长连续段——一把被长时间持有的自旋锁、一个关中断的循环、一个长遍历。

这就是为什么抢占式内核要在运行时间过长的代码路径上插入调度检查点。检查点的作用不是让代码变快，是把一条长路径切成若干短区间，把最坏值压下来。

优先级反转是另一个层面的问题。内核态运行的任何操作都要优先于用户态进程，一个低优先级用户进程由于执行软中断或硬中断处理，就能让高优先级任务得不到及时响应。抢占本身缓解了一部分——高优先级任务被唤醒后可以在中断返回时顶掉低优先级进程。但它治不了持锁导致的反转：高优先级进程在锁上等，持锁的低优先级进程跑不了，中间优先级进程在跑。

PREEMPT_RT 针对的正是这一层。它的演进脉络：

阶段 时间 做了什么
-rt 补丁树 2.6 时代起 由内核社区在主线外维护，把自旋锁改造成可睡眠的 rt_mutex，带优先级继承
中断线程化 逐步进主线 硬中断处理程序变成内核线程，可被按优先级调度，CONFIG_IRQ_FORCED_THREADING
抢占计数改造 持续 把 preempt_count 拆开，让大部分内核代码真正可抢占
合入主线 2024 年 6 月，6.12 PREEMPT_RT 进入主线，不再需要打补丁

关键差别不在「抢占得更彻底」，在锁的语义变了。spinlock 在 RT 里变成可睡眠的互斥量，带优先级继承——高优先级进程等锁时，持锁的低优先级进程会被临时提到高优先级，尽快跑完放锁。这直接掐断了优先级反转。

代价也在这儿：自旋锁变成睡眠锁，原来在原子上下文里能做的事做不了了，临界区不能关中断，性能模型整个换一套。这也是 RT 补丁花了近二十年才进主线的原因。

回到调度策略这一侧，SCHED_FIFO 和 SCHED_RR 的实时进程有个坑值得说清。一个 SCHED_FIFO 进程一旦拿到 CPU，同优先级或更低优先级的进程都拿不到，它会一直跑到自己阻塞为止。单核上如果它不阻塞，系统其它部分就全停了——谁去加载新程序？没人能加载。除非时钟中断里有更高优先级的任务等着。

内核为此设了一个兜底：RT 限流。默认参数是每 1 秒周期里给实时任务 950ms，留下 50ms 给非实时任务：

text
$ cat /proc/sys/kernel/sched_rt_runtime_us
950000
$ cat /proc/sys/kernel/sched_rt_period_us
1000000

-1 表示关掉限流，实时任务可以无限占 CPU——单核上这么设然后跑一个死循环 SCHED_FIFO，机器就死了。

至于「FIFO 实时进程运行时能加载新程序吗」这个问题，答案是能，但要靠别的核或者别的优先级。多核上加载器在另一个 CPU 上跑，不受影响；单核上要么有更高优先级的进程把它顶掉，要么等它自己阻塞，要么靠 RT 限流那 50ms 的窗口。

十二、配置项：PREEMPT_NONE/BOLUNTARY/VOLUNTARY #

内核抢占是编译期选项。Linux 2.6 引入了三级配置，之后增加了 RT 这一级和运行期切换能力。

配置项 内核态可抢占 抢占点 典型场景 延迟量级
PREEMPT_NONE 否 只有 cond_resched() 等显式点 服务器、批处理、吞吐优先 数十毫秒到百毫秒
PREEMPT_VOLUNTARY 否 显式点更密，might_sleep() 处也检查 桌面、通用发行版默认的折中 十毫秒级
PREEMPT 是 中断返回、解锁、使能软中断 桌面、低延迟、软实时 毫秒级或更低
PREEMPT_RT 是，几乎全域 上述全部，加中断线程化、可睡眠锁 硬实时 百微秒级

逐个说。

PREEMPT_NONE 是老式行为。内核态代码一路跑到底，只在显式调 cond_resched() 的地方检查 need_resched。服务器配置常用它，因为省掉抢占计数带来的开销，吞吐最好。

PREEMPT_VOLUNTARY 不改抢占模型，只是往内核里塞更多检查点。它在 might_sleep() 这类「你本来就该考虑睡眠」的位置插入一次调度检查。效果是把最长延迟从数十毫秒压到十毫秒级，代价是代码里多出一堆检查。它不产生内核抢占——检查点是代码自己走到那儿才生效的。

PREEMPT 是真正的内核抢占。中断返回、解锁、使能软中断，任意一个满足条件的点都能换进程。这是桌面发行版的主流选择。

PREEMPT_RT 在 PREEMPT 基础上换掉锁语义和中断模型，目标是把最坏延迟压到百微秒级。

怎么确认手上前内核开的是哪个：

text
$ grep -E '^CONFIG_PREEMPT' /boot/config-$(uname -r)
CONFIG_PREEMPT_BUILD=y
CONFIG_PREEMPT_NONE=y
# CONFIG_PREEMPT_VOLUNTARY is not set
# CONFIG_PREEMPT is not set

或者看 uname -a 的尾巴，里面带 PREEMPT 字样：

text
Linux host 5.15.0-91-generic #101-Ubuntu SMP ... x86_64 GNU/Linux
Linux rt-host 6.12.0-rt1 #1 SMP PREEMPT_RT ... x86_64 GNU/Linux

5.12 起多了 CONFIG_PREEMPT_DYNAMIC，编译时把三种模式都编进去，启动时用 preempt= 参数选：

text
preempt=none
preempt=voluntary
preempt=full

开了动态抢占的内核，还能在运行期从 debugfs 读当前模式：

text
$ cat /sys/kernel/debug/sched/preempt
full

这个选项解决了一个实际痛点：同一个内核镜像既能上服务器也能上桌面，不用为两种配置各编一次。代价是抢占路径上多一次间接跳转。

十三、常见误解 #

九个高频误区，逐个拆。

误解 事实
开了 PREEMPT，内核态随时能被打断 中断上下文、临界区、调度器内部都不可抢，可抢的只有抢占计数为 0 的区间
用户抢占要开 CONFIG_PREEMPT 用户抢占从 2.4 就有，任何配置下都成立；CONFIG_PREEMPT 管的是内核抢占
need_resched 一置位就立刻切换 标志只是记账，要等某个检查点兑现，中间能拖满一整个 tick
preempt_count 是个布尔开关 它是位域，分 PREEMPT、SOFTIRQ、HARDIRQ、NMI 几段，各自独立计数
抢占越激进系统越快 抢占拿吞吐换延迟，切换多、缓存丢、加锁贵，服务器上开满反而慢
PREEMPT_RT 就是把 PREEMPT 开到最大 RT 换掉了锁语义（自旋锁变可睡眠的 rt_mutex）和中断模型（中断线程化），是两个不同的东西
实时进程优先级高就一定能按时跑 优先级反转、RT 限流、多实时任务抢同一个核，任何一个都能让它迟到
cond_resched() 是内核抢占点 它是自愿让出，代码自己走到那儿才生效；抢占是代码不想让也会被换下去
有了抢占就不用管 SMP 并发了 抢占和并发是两个维度，多核上不开抢占照样有真并发，锁一个都不能少

几条展开说。

第一条最要命。很多人以为开了 PREEMPT 就是「内核态随便打断」，然后写出「反正会被抢占，临界区不用保护」的代码。内核抢占的前提恰恰是临界区已经保护好了——抢占机制是建立在锁之上的，不是替代锁的。

第五条是工程上最常见的错。从桌面换到服务器，把配置一路开满，然后发现吞吐掉了两成。原因是那些「为了低延迟而加的抢占点」在服务器上纯属开销。

第七条关于 RT 的误解值得单独强调。PREEMPT_RT 的内核里，spinlock_t 在多数上下文下不再关抢占，而是变成可睡眠的互斥量。这意味着原来在 spin_lock 保护的临界区里不能做的事（睡眠、分配内存），在 RT 里反而能做了；但原来能做的事（在中断上下文里拿锁）反而受限。语义换了一套，移植代码时不能照搬。

第八条要补一句。cond_resched() 在 PREEMPT_NONE 内核里承担了「伪抢占」的角色——它是不可抢占内核里唯一的自愿检查点来源。所以 PREEMPT_NONE 内核的延迟表现，很大程度上取决于 cond_resched() 撒得够不够密。

十四、易错点速查 #

写代码和看代码时容易踩的点，按主题归类。

判据类

  • 用户抢占只查 need_resched，内核抢占要查 preempt_count == 0 和 need_resched 两个。搞混这两个判据，就会得出「返回用户空间时要检查锁」这种错误结论。
  • 返回用户空间是安全点，返回内核空间不是。区别在于前者已经彻底离开内核数据结构。
  • 中断上下文里不会发生内核抢占，只在中断返回的那一刻发生。

计数类

  • preempt_disable() 和 preempt_enable() 必须严格配对。多减一次导致计数下溢，少减一次导致这台 CPU 永远不可抢占。
  • 嵌套是允许的，计数按层累加。只有最外层减到 0 才触发抢占检查。
  • 减计数之前有 barrier()，别在它前面插自己的代码，编译器屏障挡不住你手写的重排意图。
  • preempt_enable_no_resched() 不减检查，用完要自己补一次 preempt_check_resched()。

锁类

  • spin_lock 隐含 preempt_disable()，spin_unlock 隐含 preempt_enable()。手写 preempt_disable() 再拿 spin_lock 是重复计数，功能上没错，但会让临界区比预期长。
  • 持锁期间被抢占会让另一个 CPU 死等，这是禁止持锁抢占的唯一理由。
  • 放锁和开抢占的顺序不能反：先真放锁，再 preempt_enable()。

调度类

  • schedule() 不能在中断上下文里调。调度函数会对此作出判断，在中断里调用会打印出错信息。
  • schedule() 不能在持有自旋锁时调，会死锁。
  • 主动 schedule() 前必须先把进程状态改掉，只调 schedule() 不改状态，进程会被立刻重新选中。

配置类

  • PREEMPT_NONE 不等于没有抢占，用户抢占一直在。
  • PREEMPT_VOLUNTARY 不产生内核抢占，它只是加密了检查点。
  • 换配置要重编内核，除非开了 CONFIG_PREEMPT_DYNAMIC。
  • 延迟问题先量再加配置，别凭感觉开 PREEMPT_RT。

实时类

  • SCHED_FIFO 进程不阻塞会饿死同核上的所有低优先级任务，包括负责加载新程序的那个。
  • RT 限流默认给实时任务每周期 950ms，剩下 50ms 是保命的。设成 -1 之前想清楚。
  • 优先级反转靠优先级继承解决，不靠调高优先级。

观察类

  • /proc/<pid>/status 里的 nonvoluntary_ctxt_switches 混算用户抢占和内核抢占，要区分得看 perf sched 或者栈采样。
  • uname -a 尾巴上的 PREEMPT 字样能快速判断配置，PREEMPT_RT 会完整写出来。
  • 量抢占延迟要量整条链，不是量单个临界区——嵌套会让实际最坏值远大于单段长度。
