一、调度器在做什么 #

一句话：把可运行的线程排个队，决定下一个上 CPU 的是谁，以及它能待多久。

Linux 的做法是给每个 CPU 维护一个运行队列，队列里放着所有处于 runnable 状态的线程（就绪但没在跑，加上正在跑的那个）。调度器在调度点到来时，从队列里挑一个出来。

挑的规则由两层东西决定：

  • 调度策略（scheduling policy）：这一层决定用哪套规则挑。策略是每个线程自己的属性，存在 policy 字段里，用户态通过 sched_setscheduler() 或 sched_setattr() 改。
  • 优先级（priority）：同一套规则内部用来排序的数值。这里有两套独立的体系，不要混。

两套体系的分工：

体系 取值范围 谁在用 用户态接口
nice 值 -20 ～ 19 SCHED_OTHER / SCHED_BATCH / SCHED_IDLE nice()、setpriority()
实时优先级 rt prio 1 ～ 99（普通进程记为 0） SCHED_FIFO / SCHED_RR sched_setscheduler()、sched_setparam()

SCHED_DEADLINE 两个都不用，它用 runtime / deadline / period 三个时间参数描述自己。

在用户空间，进程优先级这个词有两层含义，说的就是上面这两套：普通进程的优先级是 nice 值，实时进程的优先级是 rt priority。后面反复出现的「优先级」，落到代码上就是这两个整数。

从用户态看过去，调度器的行为可以压成这样一张图：

text
                 ┌──────────────────────────────────┐
                 │  CPU 运行队列（每个 CPU 一个）    │
                 └──────────────────────────────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              │                     │                     │
        SCHED_DEADLINE        SCHED_FIFO/RR         SCHED_OTHER
        runtime/deadline       rt prio 1..99        nice -20..19
        period 三参数          数值大者先跑          SCHED_BATCH
              │                     │                SCHED_IDLE
              └─────────────────────┴─────────────────────┘
                        调度器按类挑，类内按优先级挑

一个必须先记住的结论：实时策略的线程只要处于 runnable 状态，普通线程就没有机会执行。这不是礼貌问题，是设计如此。所以调 sched_setscheduler() 给线程上 SCHED_FIFO 之前，先想清楚它会不会卡在一个不阻塞的循环里。

二、nice 值：-20 到 19 #

nice 值的范围是 -20 到 19：

  • -20 优先级最高，最「不 nice」，抢 CPU 最凶；
  • 0 是默认值，新建线程的起点；
  • 19 优先级最低，最「nice」，最有礼貌。

「nice」这个词的语义是「对别人有多友好」。数值调大，等于对系统里其他线程更友好，自己分到的 CPU 比例下降。所以「提高 nice 值」是降优先级，「降低 nice 值」是升优先级。这个方向别记反，反了以后调优全程都是错的。

nice 值和内核里的静态优先级是线性关系：

text
static_prio = 120 + nice

于是 nice 的 [-20, 19] 映射到静态优先级的 [100, 139]。静态优先级的数值越小优先级越高，缺省值是 120。内核里 0 ～ 99 这一段留给实时进程，100 ～ 139 这一段留给普通进程。

nice 值的几个用户态可观测事实：

事实 说明
线程私有 POSIX 标准把 nice 值定义成 per process，Linux 没照做，它是 per-thread 属性。多线程程序里 nice() 只影响调用它的那个线程
可继承 fork 出的子线程默认继承父线程的静态优先级，也就是继承 nice 值
睡眠不重置 nice 值跟着线程走，不会因为阻塞、唤醒而改变
不是配额 nice 值给出的是权重比，不是硬性时间配额。没有实时线程争抢时，一组 nice 相同的线程平分 CPU

查当前值的命令：

bash
ps -o pid,ni,pri,psr,comm -p $$
nice            # 不带参数时打印当前 nice 值

ps 里的 NI 列就是 nice 值。PRI 列是内核视角的优先级，普通线程等于 static_prio，实时线程是 99 - rt_priority 那套映射的结果。

三、nice 与权重的换算 #

nice 值本身不参与计算，内核先把它查表换成权重（weight）。这张表是 prio_to_weight[40]，下标是 nice + 20。

规则很规整：nice 每差 1，权重相差约 1.25 倍。这个 1.25 是设计出来的，不是拟合出来的，1024 / 820 ≈ 1.2488。

完整对照：

nice 权重 nice 权重 nice 权重 nice 权重
-20 88761 -10 9548 0 1024 10 110
-19 71755 -9 7620 1 820 11 87
-18 56483 -8 6100 2 655 12 70
-17 46273 -7 4904 3 526 13 56
-16 36291 -6 3906 4 423 14 45
-15 29154 -5 3121 5 335 15 36
-14 23254 -4 2501 6 272 16 29
-13 18705 -3 1991 7 215 17 23
-12 15076 -2 1586 8 172 18 15
-11 11916 -1 1277 9 137 19 10

有了权重，CPU 占比就能算出来：

text
某线程的 CPU 占比 = 该线程权重 / 队列中所有 runnable 线程权重之和

几个能直接背下来的例子：

场景 权重比 实际占比
两个 nice 0 的线程 1024 : 1024 各 50%
nice 0 与 nice 5 1024 : 335 约 75% : 25%
nice 0 与 nice 10 1024 : 110 约 90% : 10%
nice -20 与 nice 19 88761 : 10 约 99.99% : 0.01%
十个 nice 0 的线程 相同 各 10%

nice 差 10，占比差 9 倍多。这是很多人调优时的第一课：nice 的杠杆比想象中大，从 0 调到 10 已经很激烈了，从 0 调到 -20 基本等于把这个线程钉在 CPU 上。

内核内部的记账方式是给每个线程维护一个虚拟运行时间 vruntime，实际跑了多久就按权重折算进 vruntime：

text
vruntime += 实际运行时间 × (NICE_0_LOAD / 该线程权重)

权重大的线程，vruntime 涨得慢，于是下一次挑人时更容易被选上。连续跑同一批线程，最终收敛到的比例就是上面的权重比。你不需要看这段代码也能推出结论：权重是 CPU 份额的斜率，nice 是调斜率的旋钮。

两个必须知道的偏差来源：

  • 线程睡眠后醒来，内核会给它的 vruntime 做补偿（把它拉到队列最小 vruntime 附近），避免一个刚醒的交互线程被饿死。所以实际占比会低于按权重算出的理论值，睡得越久偏得越多。
  • 权重只在同一个运行队列（同一 CPU）内部做归一化。线程被迁到别的核上，参与分配的是那个核上的队列。想让占比可预测，绑核比调 nice 更直接。

四、实时优先级：0 到 99 #

实时优先级（rt priority，sched_param.sched_priority）是另一套数值体系，和 nice 值没有任何换算关系。

区间划分：

区间 含义
0 普通进程。普通线程的 rt priority 恒为 0
1 ～ 99 实时进程。数值越大优先级越高，99 最高，1 最低

边界要查，不要背死：

c
#include <sched.h>
#include <stdio.h>

int main(void)
{
    printf("SCHED_FIFO  min=%d max=%d\n",
           sched_get_priority_min(SCHED_FIFO), sched_get_priority_max(SCHED_FIFO));
    printf("SCHED_RR    min=%d max=%d\n",
           sched_get_priority_min(SCHED_RR),   sched_get_priority_max(SCHED_RR));
    printf("SCHED_OTHER min=%d max=%d\n",
           sched_get_priority_min(SCHED_OTHER), sched_get_priority_max(SCHED_OTHER));
    return 0;
}

Linux 上 SCHED_FIFO 和 SCHED_RR 都是 min = 1、max = 99，一共 99 个 level。别的调度策略这两个函数返回 0。不同 Unix 实现的 level 数量不一样，所以 sched_get_priority_min/max 存在的意义就是别把 1 和 99 写死。

内核侧的映射是翻转的：

text
内核 prio = 99 - rt_priority

于是 rt priority 99 对应内核 prio 0（最高），rt priority 1 对应内核 prio 98。这个翻转很好理解：内核里所有优先级都是「数值越小越高」，用户态的 rt priority 是「数值越大越高」，两边对不齐，所以在边界上翻一次。

两套体系的对照，用一张表定死：

维度 nice rt priority
范围 -20 ～ 19 1 ～ 99（0 = 普通进程）
依据标准 历史沿革，POSIX 定义了 nice() / setpriority() POSIX 实时扩展（2008 版）
生效策略 SCHED_OTHER / BATCH / IDLE SCHED_FIFO / SCHED_RR
方向 数值越大优先级越低 数值越大优先级越高
内核字段 static_prio（= 120 + nice） rt_priority
交叉影响 实时线程改 nice 不改变调度行为 普通线程的 rt priority 恒为 0

最后一行是关键：给一个 SCHED_FIFO 的线程调 nice 值，不会改变它的调度行为。它按 rt priority 排队，nice 值在那条路径上没被读。

五、六种调度策略 #

策略是线程的属性，用 sched_setscheduler() 设。六个常量、语义、参数如下：

策略 值 语义 生效参数 备注
SCHED_OTHER 0 普通分时，默认策略 nice 别名 SCHED_NORMAL，绝大多数线程都是它
SCHED_FIFO 1 实时，同优先级先到先跑，不主动让出就一直跑 rt priority 1 ～ 99 无时间片
SCHED_RR 2 实时，同优先级按时间片轮转 rt priority 1 ～ 99 有时间片
SCHED_BATCH 3 批处理，按普通分时算但不鼓励抢占唤醒 nice 运算密集型适用
SCHED_IDLE 5 极低优先级，系统没别的事才跑 nice nice 19 之外还有一层降级
SCHED_DEADLINE 6 按周期与截止期调度 runtime/deadline/period 3.14 引入

SCHED_NORMAL 和 SCHED_OTHER 是同一个值 0，两个名字，代码里都能用。

按优先级从高到低排：

text
SCHED_DEADLINE  >  SCHED_FIFO / SCHED_RR  >  SCHED_OTHER / SCHED_BATCH / SCHED_IDLE

这条链是硬边界：SCHED_DEADLINE 进程只要能被调度，实时进程让路；实时进程 runnable，普通进程让路。三档之间不是「高一点」，是「不同类」。

用命令看一眼系统当前的分布：

bash
ps -eLo pid,tid,cls,rtprio,ni,comm | awk '$3 != "TS" {print}' | head -30
chrt -p $$          # 查看某个进程的策略与 rt priority

CLS 列的含义：TS = SCHED_OTHER，FF = SCHED_FIFO，RR = SCHED_RR，B = SCHED_BATCH，IDL = SCHED_IDLE，DLN = SCHED_DEADLINE。

六、SCHED_OTHER：普通分时 #

这是默认策略，值是 0，别名 SCHED_NORMAL。一个线程 fork 出来不带任何调度设定，它就是 SCHED_OTHER。

语义上看不到「时间片」这个词的旧含义了。现在的做法是维护每个线程的虚拟运行时间 vruntime，每次挑 vruntime 最小的那个跑。权重大的线程跑同样的真实时间，vruntime 涨得慢，于是被选中得更频繁。这就是第三章那张权重表的作用。

但你仍然能从外部观察到「一轮」的存在。调度器维护两个参数：

参数 sysctl 路径 缺省值 作用
目标调度延迟 /proc/sys/kernel/sched_latency_ns 6 ms（6000000） 理想情况下，一轮里每个 runnable 线程至少跑一次
最小调度粒度 /proc/sys/kernel/sched_min_granularity_ns 0.75 ms（750000） 一轮里每个线程至少跑这么久，不允许切得太碎

线程数少的时候，一轮长度按目标延迟算。runnable 线程超过 8 个（sched_nr_latency）以后，一轮长度不再固定，改按「线程数 × 最小粒度」扩张，防止切换开销吃掉全部 CPU。

用户态能看到的 SCHED_OTHER 行为特征：

  • sched_param.sched_priority 必须是 0。传非 0 调 sched_setscheduler() 返回 EINVAL。
  • 只有 nice 值起作用，其余参数无效。
  • 一个新唤醒的线程会做 vruntime 补偿，被放到队列里 vruntime 最小值的附近。所以交互型线程（睡一会儿干一会儿）能拿到比权重比更高的实际份额。
  • 唤醒会尝试立刻抢占当前运行的线程。这个行为由 /proc/sys/kernel/sched_wakeup_granularity_ns 控制阈值，值越小越容易抢占。
  • ps 里 CLS 列显示 TS。

一个实际的查看方式：

bash
cat /proc/sys/kernel/sched_latency_ns
cat /proc/sys/kernel/sched_min_granularity_ns
cat /sys/kernel/debug/sched/debug    # 需要 root 且 debugfs 已挂载

七、SCHED_FIFO 与 SCHED_RR：实时策略 #

两者都叫实时策略，内核里统一判断为 rt 类。区别只有一个：同一 rt priority 的多个线程之间怎么分 CPU。

SCHED_FIFO（值 1）的规则：

  • 一个 FIFO 线程一旦上 CPU，就一直跑，直到下述任一情况发生：自己阻塞（发起 I/O、睡眠、等待锁）、自己调用 sched_yield()、自己退出、被更高 rt priority 的线程抢占。
  • 它没有时间片。不会因为跑得久而被打断。
  • 同 rt priority 的线程按进入 runnable 状态的先后排队，先来的先跑。后来的必须等前面的让出。

SCHED_RR（值 2）的规则：

  • 与 FIFO 相同的部分：高优先级压死低优先级，被高优先级抢占。
  • 不同的部分：同 rt priority 的线程之间有时间片。时间片用完，当前线程被排到同优先级队列尾部，下一个同优先级线程上。
  • 时间片长度由 /proc/sys/kernel/sched_rr_timeslice_ms 控制，缺省 100 ms。这也是 RR_TIMESLICE 的缺省值。

一句话对比：

text
SCHED_FIFO：同优先级里，谁先来谁一直跑，除非自己让。
SCHED_RR  ：同优先级里，每人 100ms，轮着跑。

跨优先级的行为两者完全一样：rt priority 99 的线程 runnable 期间，rt priority 1 的线程一次都上不去，不管是不是 RR、时间片有没有用完。

SCHED_FIFO 线程主动让出的标准做法是 sched_yield()：

c
#include <sched.h>
#include <stdio.h>
#include <errno.h>

int main(void)
{
    struct sched_param sp = { .sched_priority = 10 };

    if (sched_setscheduler(0, SCHED_FIFO, &sp) != 0) {
        perror("sched_setscheduler");
        return 1;
    }
    printf("policy now: %d\n", sched_getscheduler(0));

    for (;;) {
        /* 干活 */
        sched_yield();   /* 把 CPU 让给同优先级的其他 FIFO 线程 */
    }
}

0 作为 pid 表示「调用线程自己」。返回 0 成功，-1 失败并置 errno。没有 CAP_SYS_NICE 时，把普通线程抬成 SCHED_FIFO 会失败，errno 是 EPERM。

八、SCHED_BATCH 与 SCHED_IDLE #

这两种都是普通分时的变体，都吃 nice 值，都要求 sched_priority 为 0。

SCHED_BATCH（值 3）是给运算密集型线程用的：

  • 调度器不会那么勤快地唤醒抢占它。一个刚醒来的线程想抢它的 CPU，门槛更高。
  • 它自己按 nice 值正常参与权重分配，不吃亏。
  • 换来的是更少的上下文切换，缓存命中率更高。

典型场景：编译、视频转码、离线数据处理、批量 ETL。这类任务跑得久、切换代价高，把它们标成 batch 对整机吞吐有好处。

bash
nice -n 10 ionice -c2 -n7 make -j8      # 配合 nice 一起用
chrt -b 0 ./render --frames 1-4000      # chrt -b 设置 SCHED_BATCH

SCHED_IDLE（值 5）是给后台清理用的：

  • 权重被策略钉在一个极低档（内核里 WEIGHT_IDLEPRIO 是 3），比 nice 19 的权重 10 还要低一个量级。
  • 实际表现：只要系统里有任何 SCHED_OTHER 线程 runnable，IDLE 线程几乎推进不了。CPU 全空闲时它才跑满。
  • nice 值仍然能被设置、被读取，但对权重的计算不起作用。策略已经把权重定死了。
bash
chrt -i 0 ./cleanup-old-logs.sh    # chrt -i 设置 SCHED_IDLE

两者与 nice 19 的区别值得单独记一笔：

方式 权重 有别的普通线程在跑时
nice 19 10 仍能分到约 1/103 的 CPU
SCHED_IDLE 3 基本分不到，CPU 空下来才跑

如果你只是想让任务慢一点，用 nice 19。如果你想让任务完全让路、只在机器闲着时干活，用 SCHED_IDLE。

九、SCHED_DEADLINE：截止期调度 #

前面的策略都在回答「谁先跑」。SCHED_DEADLINE 回答的是另一个问题：「我每隔一段时间要跑一次，每次要跑够这么久，你能保证吗」。

它用三个时间参数描述自己，不用 nice，也不用 rt priority：

参数 含义 单位
sched_runtime 一个周期内需要的 CPU 时间（comp. time） ns
sched_deadline 相对于周期起点的截止期（relative deadline） ns
sched_period 周期长度 ns

约束是：

text
sched_runtime <= sched_deadline <= sched_period

三者都必须大于 0。任何一个条件不满足，sched_setattr() 返回 EINVAL。sched_period 传 0 时，内核按 sched_deadline 的值当作周期，即 period == deadline。

语义：每到周期起点（线程被唤醒的时刻），调度器在 sched_deadline 之内把线程调度上去，让它跑满 sched_runtime，跑完可以调度走；下一个周期到了再来一遍。

优先级位置：SCHED_DEADLINE 高于 SCHED_FIFO、SCHED_RR，更高于普通线程。内核里它的归一化优先级是 -1，比实时线程的 0 还要高，是整条优先级数轴的顶端。

设置接口只有 sched_setattr()：

c
#include <linux/sched/types.h>
#include <sys/syscall.h>
#include <unistd.h>
#include <string.h>
#include <stdio.h>
#include <errno.h>

static int sched_setattr_wrap(pid_t pid, struct sched_attr *attr, unsigned int flags)
{
    return (int)syscall(__NR_sched_setattr, pid, attr, flags);
}

int main(void)
{
    struct sched_attr attr;

    memset(&attr, 0, sizeof(attr));
    attr.size          = sizeof(attr);
    attr.sched_policy  = SCHED_DEADLINE;
    attr.sched_runtime  =  2000000;   /*  2 ms CPU 时间 */
    attr.sched_deadline = 10000000;   /* 10 ms 内必须跑完 */
    attr.sched_period   = 20000000;   /* 每 20 ms 一个周期 */

    if (sched_setattr_wrap(0, &attr, 0) != 0) {
        perror("sched_setattr");   /* EPERM 缺权限，EBUSY 超带宽，EINVAL 参数非法 */
        return 1;
    }
    printf("SCHED_DEADLINE set\n");
    return 0;
}

几点必须知道的：

  • glibc 没有 sched_setattr() 的包装函数，得自己用 syscall(__NR_sched_setattr, ...)。头文件用 <linux/sched/types.h> 拿 struct sched_attr。
  • 需要 CAP_SYS_NICE。
  • 内核做准入控制。把这组参数加进系统后，如果总带宽超过可用容量，返回 EBUSY。所以它不是「设了就一定成功」的接口，得处理失败。
  • sched_getattr() 原型是 int sched_getattr(pid_t pid, struct sched_attr *attr, unsigned int size, unsigned int flags)，读回来的 attr->size 是内核实际填的长度，比你自己传的 size 小的时候要用它。
  • 这是 Linux 特有接口，不在 POSIX 标准里。跨平台代码里要用 #ifdef __linux__ 包起来。

SCHED_DEADLINE 不适合拿来当「超级优先级」用。它需要你对任务的执行时间有真实的测量：sched_runtime 设小了任务做不完，设大了准不进去。没有测量数据就别上这个策略。

十、调整 nice 值：nice 与 setpriority #

1、nice() #

最老的接口，也是能力最弱的：

c
#include <unistd.h>

int nice(int inc);

语义：把调用线程的 nice 值加上 inc。inc 可正可负，结果会被裁剪到 [-20, 19]。

  • nice(3)：nice 值 +3，优先级降低 3 档。因为调大 nice 值等于对别人更友好，自己让出 CPU。
  • nice(-5)：nice 值 -5，优先级提升 5 档。

返回值这块有坑：

标准 成功时返回
POSIX 新的 nice 值
Linux 系统调用与 libc 0

失败返回 -1。于是在 Linux 上写 if (nice(-5) == -1) 判断失败是成立的，但拿不到新值。想知道当前值，只能用 getpriority()。

还有两个限制：

  • 只能改自己，没有 pid 参数。
  • 无 CAP_SYS_NICE 时只能往大调（降优先级），往小调会被裁剪回原值而不是报错。这点与 setpriority() 不同，后者会返回 EACCES。

另外记住：POSIX 标准把 nice 值定义为 per process，Linux 没遵守，它是 per-thread 属性。多线程程序里 nice() 只作用于调用它的那个线程。

2、getpriority() / setpriority() #

加强版：

c
#include <sys/time.h>
#include <sys/resource.h>

int getpriority(int which, int who);
int setpriority(int which, int who, int prio);

名字为什么不叫 getnice/setnice？历史上先用的是 nice 值，后来大家觉得「nice」这个词对初学者不直观，改叫 priority 更容易理解。这个改名后来的事实证明不算成功，因为真正的优先级（rt priority）登场后，两个「优先级」撞名了。

which 决定操作对象的口径：

which who 的含义 getpriority 返回
PRIO_PROCESS 进程（线程）ID 该线程的 nice 值
PRIO_PGRP 进程组 ID 组内所有线程中最小的 nice 值（即优先级最高的那个）
PRIO_USER 用户 ID 该用户所有线程中最小的 nice 值

who 传 0 表示当前进程 / 当前进程组 / 当前用户。

setpriority() 比 nice() 强的地方就在这个 which：它一次可以改一组线程的 nice 值。成功返回 0，失败返回 -1。

getpriority() 的返回值需要一个特殊处理。它要返回的值本身就是 -1，而 -1 是一个合法的 nice 值，而 -1 又是通用的错误标志。区分办法是动用 errno：

c
#include <sys/resource.h>
#include <errno.h>
#include <stdio.h>

int main(void)
{
    int prio;

    errno = 0;                    /* 关键：先清零 */
    prio = getpriority(PRIO_PROCESS, 0);
    if (prio == -1 && errno != 0) {
        perror("getpriority");    /* 真的失败了 */
        return 1;
    }
    printf("nice = %d\n", prio);
    return 0;
}

规则：调用前 errno 清零；调用后若返回 -1 且 errno 仍是 0，说明返回值就是 -1，不是错误。getpriority() 是少数「返回 -1 仍属正确」的接口。

3、命令行工具 #

bash
nice -n 10 ./job.sh          # 以 nice 10 启动
nice                          # 不带参数：打印当前 shell 的 nice 值
renice -n 5 -p 1234          # 改已运行进程
renice -n -5 -p 1234         # 提优先级，需要 root 或 CAP_SYS_NICE
renice -n 19 -g 4321         # 改整个进程组

renice 降低优先级时普通用户可以自己做，提升优先级需要权限。和老接口一致。

十一、设置调度策略：sched_setscheduler #

核心接口：

c
#include <sched.h>

struct sched_param {
    int sched_priority;      /* 实时策略下是 rt priority，普通策略下必须是 0 */
};

int sched_setscheduler(pid_t pid, int policy, const struct sched_param *param);
int sched_getscheduler(pid_t pid);

int sched_setparam(pid_t pid, const struct sched_param *param);
int sched_getparam(pid_t pid, struct sched_param *param);

四个接口的分工：

接口 能改策略 能改 rt priority 能改 nice
sched_setscheduler() 是 是 否
sched_setparam() 否 是 否
sched_setattr() 是 是 是
setpriority() 否 否 是

sched_setscheduler() 一次搞定策略和该策略下的参数。sched_setparam() 只改当前策略下的参数，不能换策略。sched_setattr() 是全集，策略、nice、rt priority、deadline 三件套全能设，代价是它是 Linux 专有扩展。

返回值一律是 0 成功、-1 失败并置 errno。pid 传 0 表示调用线程自己。

sched_setscheduler() 的完整用法：

c
#include <sched.h>
#include <stdio.h>
#include <string.h>
#include <errno.h>

static int set_rt(int prio)
{
    struct sched_param sp;

    memset(&sp, 0, sizeof(sp));
    sp.sched_priority = prio;                 /* 1 ～ 99 */
    if (sched_setscheduler(0, SCHED_FIFO, &sp) != 0) {
        fprintf(stderr, "set FIFO %d failed: %s\n", prio, strerror(errno));
        return -1;
    }
    return 0;
}

static int set_normal(void)
{
    struct sched_param sp;

    memset(&sp, 0, sizeof(sp));
    sp.sched_priority = 0;                    /* 普通策略必须为 0 */
    if (sched_setscheduler(0, SCHED_OTHER, &sp) != 0) {
        fprintf(stderr, "back to OTHER failed: %s\n", strerror(errno));
        return -1;
    }
    return 0;
}

int main(void)
{
    struct sched_param p;

    if (set_rt(10) != 0)
        return 1;
    sched_getparam(0, &p);
    printf("now policy=%d prio=%d\n", sched_getscheduler(0), p.sched_priority);
    set_normal();                             /* 一定要有回退路径 */
    return 0;
}

注意 set_normal() 那一行。上了实时策略就一定留回退路径，不然程序退出前那个核一直被它按着。

参数检查的几条铁律，违反了就是 EINVAL：

检查项 条件
普通策略的优先级 sched_priority 必须等于 0
实时策略的优先级 sched_priority 必须在 [sched_get_priority_min(policy), sched_get_priority_max(policy)] 内
策略值合法 必须是六个常量之一
deadline 参数 runtime <= deadline <= period 且都 > 0

SCHED_DEADLINE 只能通过 sched_setattr() 设置。用 sched_setscheduler() 传 SCHED_DEADLINE 会失败，因为 sched_param 里装不下三个时间参数。

实时策略上了台就没有保险丝。给线程设 SCHED_FIFO 之后如果它一直不阻塞，那个核就交给它了。所以：

  • 上实时策略之后，线程必须有明确的阻塞点或让出点。循环里放 sched_yield()，或者 nanosleep()。
  • 万一卡死，从另一个终端用 chrt -o 0 -p <pid> 把它打回 SCHED_OTHER。前提是你能拿到 shell。
  • 更稳的做法是给实时线程配上 RLIMIT_RTTIME，让内核在它连续霸占 CPU 超时后发 SIGXCPU 砍掉它。

十二、查询接口与权限要求 #

1、查询清单 #

想查什么 接口 pid 传 0
调度策略 sched_getscheduler(pid) 查自己
该策略下的参数 sched_getparam(pid, &param) 查自己
策略的 rt priority 下界 sched_get_priority_min(policy) 无 pid 参数
策略的 rt priority 上界 sched_get_priority_max(policy) 无 pid 参数
nice 值 getpriority(which, who) who 传 0 查自己
全部调度属性 sched_getattr(pid, &attr, size, flags) 查自己
CPU 亲和性 sched_getaffinity(pid, size, &mask) 查自己

sched_getscheduler() 成功时返回策略常量，失败返回 -1。注意它返回 -1 时也是错误，而 -1 不是合法策略值，所以这里没有 getpriority() 那种歧义。

sched_getattr() 用法：

c
#include <linux/sched/types.h>
#include <sys/syscall.h>
#include <unistd.h>
#include <string.h>
#include <stdio.h>

int main(void)
{
    struct sched_attr attr;

    memset(&attr, 0, sizeof(attr));
    attr.size = sizeof(attr);
    if (syscall(__NR_sched_getattr, 0, &attr, sizeof(attr), 0) != 0) {
        perror("sched_getattr");
        return 1;
    }
    printf("policy=%u nice=%d rt_prio=%u\n",
           attr.sched_policy, attr.sched_nice, attr.sched_priority);
    printf("runtime=%llu deadline=%llu period=%llu\n",
           (unsigned long long)attr.sched_runtime,
           (unsigned long long)attr.sched_deadline,
           (unsigned long long)attr.sched_period);
    return 0;
}

sched_getattr() 的原型里 attr 是 const struct sched_attr *，这是历史遗留的写法，实际是输出参数，需要转型或直接传非 const 指针。

命令行速查：

bash
chrt -p 1234                      # 策略 + rt priority
chrt -m                           # 列出本机各策略的优先级范围
ps -o pid,ni,pri,psr,cls,comm -p 1234
taskset -pc 1234                  # 亲和性（同目录另一篇细讲）

2、权限：CAP_SYS_NICE #

这块是硬门槛。规则来自内核的安全检查，用户态看下来是这样的：

操作 无 CAP_SYS_NICE 有 CAP_SYS_NICE
调大 nice 值（降优先级） 允许 允许
调小 nice 值（升优先级） 拒绝，EACCES 允许
SCHED_OTHER → SCHED_FIFO/RR 拒绝，EPERM 允许
SCHED_FIFO → SCHED_OTHER 允许（降级） 允许
提升 rt priority 拒绝，EPERM 允许
降低 rt priority 允许（降级） 允许
设置 SCHED_IDLE 允许（降级） 允许
设置 SCHED_BATCH 允许 允许
设置 SCHED_DEADLINE 拒绝，EPERM 允许，受准入控制
操作别人的线程 同用户同会话限制 允许

核心原则一句话：没有 CAP_SYS_NICE 时，你能做的只有降级。策略从 FIFO 降到 NORMAL 行，nice 从 0 调到 10 行，反过来全不行。

还有一层限制：没有 CAP_SYS_NICE 时，即使只是降级，操作对象也必须是同一登录用户的线程，否则 EPERM。

CAP_SYS_NICE 的常见获取方式：

bash
sudo setcap cap_sys_nice+ep ./your-daemon     # 给二进制加能力
getcap ./your-daemon                          # 确认
sudo chrt -f 50 ./server                      # 直接用 root 起

在容器里，默认的 docker run 会丢掉 CAP_SYS_NICE，得显式加 --cap-add=SYS_NICE。Kubernetes 里对应 securityContext.capabilities.add。改了没生效，先查这个。

RLIMIT_RTPRIO 是另一条路：它允许非特权进程把 rt priority 提到资源限制允许的上限以内。软硬限制都可设，值 0 表示不允许任何实时优先级。有些发行版的 rtprio PAM 限制配合 @realtime 用户组用的就是它。

RLIMIT_RTTIME 则是给实时线程兜底的：线程连续占用 CPU 超过这个微秒数且没有发起阻塞调用时，内核发 SIGXCPU。默认值多为 unlimited，但容器与 systemd 服务常会设。

十三、实时进程的坑：饿死与优先级反转 #

1、饿死 #

实时线程如果写成一个不阻塞的死循环：

c
/* 反面教材 */
for (;;) {
    /* 纯计算，没有 sleep，没有 I/O，没有 sched_yield */
}

它就是那个核上的永久占领者。同核上所有 SCHED_OTHER 线程永远拿不到 CPU，看门狗线程、日志线程、心跳线程全部停摆。表现是：SSH 连上去了但敲命令没反应，串口能进，top 里那几个 SCHED_OTHER 线程的 CPU 时间不再增长。

更隐蔽的一种：实时线程每轮都做了 I/O，但 I/O 立刻返回（命中页缓存、写内存文件系统），于是它从技术上讲「没睡眠」，照样饿死别人。判断标准不是有没有 I/O，是有没有真正阻塞。

防饿死的三件事：

  • 每个实时线程的循环里都要有一个明确的让出点。sched_yield() 只让给同优先级的，所以要真让路得用 nanosleep()。
  • 给实时线程设 RLIMIT_RTTIME，超了就被 SIGXCPU 干掉，别让它拖死整机。
  • 实时线程的 rt priority 不要随便用 99。留出高档位给真正必须最紧急的线程，比如内核线程和看门狗。

2、优先级反转 #

经典三方场景：低优先级线程 L 持有锁，高优先级线程 H 等这把锁被阻塞，中优先级线程 M 抢占 L 让 L 迟迟不释放锁。结果是 H 被 M 间接堵住。

对 SCHED_FIFO 尤其致命。L 一旦被 M 抢走，M 又是无限跑的，H 就无限期卡在锁上。

用户态能做的是用带优先级继承的锁：

c
#include <pthread.h>

pthread_mutexattr_t attr;
pthread_mutex_t lock;

pthread_mutexattr_init(&attr);
/* 优先级继承协议 */
pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT);
pthread_mutex_init(&lock, &attr);

两种协议的差别：

协议 行为 代价
PTHREAD_PRIO_INHERIT 持锁线程临时提升到所有等待者中的最高优先级 每次加解锁多一次优先级计算
PTHREAD_PRIO_PROTECT 持锁线程直接提升到锁的优先级上限 需要正确设定这个上限值，设错会拖慢别人

PTHREAD_PRIO_INHERIT 要 _GNU_SOURCE。PTHREAD_PRIO_PROTECT 只有少数实现支持，用前先测。

一个更省事的建议：实时线程之间的共享数据，尽量用无锁结构或干脆不共享，别在这条路径上赌锁的公平性。

3、别顺手改 nice 当「修复」 #

很多人碰到实时线程抢不到 CPU，第一反应是给别的线程调 nice。没用。nice 只在 SCHED_OTHER 类内部起作用，对实时线程的排队没有任何影响。要调实时线程，动的是 rt priority，那是另一个数轴。

反过来也是：给一个 SCHED_FIFO 线程设 nice 值，内核会把这个值存下来，但调度行为一点不变。这个 nice 值只在你把它改回 SCHED_OTHER 之后才开始生效。

十四、策略怎么选 #

按任务性质对号入座：

你的线程在做什么 选什么 备注
普通前台服务、Web 请求处理 SCHED_OTHER 默认值，不用动
编译、转码、批量计算 SCHED_BATCH 配合 nice 5 ～ 10
日志清理、索引重建、冷数据搬运 SCHED_IDLE 只在机器闲着时跑
中断下半部的用户态替代、低延迟采集 SCHED_FIFO + 中等 rt priority 必须有让出点
多个同优先级要公平轮转的实时线程 SCHED_RR 时间片 100 ms
有明确周期和截止期的控制回路 SCHED_DEADLINE 需要实测 runtime

优先级数值怎么定：

  • **实时优先级从低往高试，不要一上来给 99。**先用 10 到 20 之间，量出延迟，不够再往上加。留下一段高档位给系统。
  • 同一组实时线程用同一个 rt priority，靠 SCHED_RR 分时间片，而不是靠不同数值制造不公平。
  • 普通线程的 nice 差值控制在 10 以内。差 10 已经是 9 倍差距，差 20 就是 8800 倍，除了「让路」之外没有别的解释。
  • SCHED_BATCH 不要单独用，配上 nice 才有明显效果。

上线前的检查清单：

bash
# 1. 实时线程数量是否合理
ps -eLo pid,tid,cls,rtprio,comm | awk '$3=="FF"||$3=="RR"{c++} END{print "rt threads:", c+0}'

# 2. 实时带宽是否接近饱和
cat /proc/sys/kernel/sched_rt_runtime_us
cat /proc/sys/kernel/sched_rt_period_us

# 3. 有没有线程在饿死别人
pidstat -u -t -p <pid> 1

sched_rt_runtime_us 与 sched_rt_period_us 这一对是实时带宽的全局上限，缺省是 950000 / 1000000，也就是最多 95% 的 CPU 时间可以给实时线程，剩下 5% 留给普通线程保命。把这个值调到 1000000 等于取消保险，整机可以被实时线程彻底锁死。除非你非常确定，别动它。
