一、进程间为什么需要通信 #

进程默认互相看不见。每个进程一套页表，虚拟地址 0x400000 在你这里放全局变量，在隔壁进程那里放别人的堆。隔离是 MMU 做的硬件级隔离，不是约定。

fork() 之后短暂存在一种错觉：父子进程的变量看起来一样。那是写时复制（COW）造成的。任何一方真正写入，物理页立刻分家，此后各改各的。

c
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int g_counter = 0;

int main(void)
{
    pid_t pid = fork();
    if (pid == 0) {
        g_counter = 100;                       /* 改的是子进程自己那份 */
        printf("[child ] %d @ %p\n", g_counter, (void *)&g_counter);
        _exit(0);
    }
    wait(NULL);
    printf("[parent] %d @ %p\n", g_counter, (void *)&g_counter);
    return 0;
}

两个进程打印的地址相同，值却不同 —— 虚拟地址一样，物理页早已分家。要让它们交换数据只有两条路：把数据搬进内核中转（管道、消息队列、socket），或者让同一块物理页被双方同时映射（共享内存）。

按需求分类，进程间要干的事就四种：

需求 说明 典型手段
数据传递 一个进程把字节交给另一个 管道、FIFO、消息队列、socket
事件通知 只告诉对方「出事了」，不带数据 信号、eventfd
资源共享 双方操作同一块内存或同一个计数器 共享内存 + 信号灯
进程控制 让某个进程暂停、继续、退出 信号（SIGSTOP/SIGCONT/SIGTERM）

管道解决第一类，信号解决第二类和第四类。这两类能力最弱，却是内核自己天天在用的 —— shell 的 | 是管道，Ctrl+C 是信号。

二、IPC 手段的全景与选择 #

Linux 的 IPC 不是一次设计出来的，是四代人往上叠的结果。认清每一代的来路，选型时就不会拿着锤子找钉子。

手段 来路 有无名字 方向 数据边界 典型用途
信号 Signal 早期 UNIX 无（按 PID 投递） 单向通知 无数据（sigqueue 可带一个值） 进程控制、异常通知
无名管道 Pipe 早期 UNIX 无 半双工 字节流 亲缘进程单向数据流
有名管道 FIFO 早期 UNIX 文件系统路径 半双工 字节流 无亲缘进程单向数据流
System V 共享内存 AT&T System V key / ID 双向 无（自己定） 大数据量、低延迟共享
System V 消息队列 AT&T System V key / ID 双向 有（整条消息） 带类型标签的异步消息
System V 信号灯 AT&T System V key / ID — — 计数型同步
POSIX 消息队列 POSIX /name 双向 有（带优先级） 可移植的消息传递
POSIX 信号灯 POSIX /name 或匿名 — — 线程与进程同步
POSIX 共享内存 POSIX /name 双向 无 可移植的共享映射
UNIX domain socket BSD 路径或匿名 全双工 有（可保留消息边界） 本机全双工、可传 fd

D-Bus 用户态守护进程 总线名/对象路径 双向 有（消息） 桌面与服务间方法调用

选型时按四条线过一遍：要不要跨机器（要，只有套接口）；要不要双向（要，两根管道、UNIX domain socket 或共享内存）；有没有亲缘关系（有，pipe() 加 fork()；没有，FIFO、UNIX domain socket 或 System V/POSIX IPC）；数据是「事件」还是「字节流」（只是「某件事发生了」，信号最省；是持续的数据流，别用信号）。

本篇讲管道、FIFO 与信号。System V 三件套的 key_t 命名空间与权限位、D-Bus 的总线守护进程模型，各自问题域完全不同，混着学只会记混，各有专篇。

三、无名管道：pipe 的用法 #

pipe() 干一件事：在内核里开一块缓冲，返回两个文件描述符，一个只能读，一个只能写。

c
#include <unistd.h>

int pipe(int pipefd[2]);
  • pipefd[0] 固定是读端，pipefd[1] 固定是写端，顺序别记反。
  • 成功返回 0，失败返回 -1 并置 errno；失败时内核不修改 pipefd 的内容，这条是 POSIX.1-2008 TC2 才写进标准的，Linux 一直这么实现。
  • 版本：pipe() 属 POSIX.1-2001，更早的 POSIX.1-1990 已有同名接口。

要一次把标志位带上，用 pipe2()：

c
#define _GNU_SOURCE
#include <fcntl.h>
#include <unistd.h>

int pipe2(int pipefd[2], int flags);

pipe2() 是 Linux 专有接口，Linux 2.6.27 起有，glibc 2.9 起有包装，POSIX.1-2024 才把它收进标准。flags 传 0 时行为与 pipe() 完全一致。可用的位：

标志 起始版本 作用
O_CLOEXEC Linux 2.6.27 给两个 fd 置 FD_CLOEXEC，exec 后自动关闭，避免 fd 泄漏给子程序
O_NONBLOCK Linux 2.6.27 直接给两个 fd 置非阻塞，省掉两次 fcntl(F_SETFL)
O_DIRECT Linux 3.4 包模式管道，每次 write 成为一个独立包，read 一次读一个包
O_NOTIFICATION_PIPE Linux 5.8 内核通知机制建在管道上；CONFIG_WATCH_QUEUE 未编译时返回 ENOPKG

O_DIRECT 有三条硬规矩：单次写超过 PIPE_BUF 的会被切成多个包；read 给的缓冲区小于下个包时，只读到缓冲区大小，包内剩余字节被丢弃；长度为 0 的包不支持。Linux 4.5 起可以用 fcntl() 改这个标志。

最小验证，一个进程自己写自己读：

c
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(void)
{
    int fd[2];
    char buf[64] = {0};

    if (pipe(fd) < 0) {
        perror("pipe");
        return 1;
    }
    write(fd[1], "hello pipe", 10);
    ssize_t n = read(fd[0], buf, sizeof(buf) - 1);
    printf("read %zd bytes: %s\n", n, buf);

    close(fd[0]);
    close(fd[1]);
    return 0;
}

管道没有 lseek()，调用会返回 -1 并置 errno = ESPIPE。它不是可定位的文件，是先进先出的字节队列，只能从头往后取，写进去的字节也不会落到任何文件系统上。

关于这块缓冲多大：Linux 2.6.11 之前，管道容量等于一个系统页（i386 上 4096 字节）；2.6.11 起是 16 页，页大小 4096 时即 65536 字节；2.6.35 起默认仍是 16 页，但可以用 fcntl() 的 F_GETPIPE_SZ / F_SETPIPE_SZ 查询和调整，上限由 /proc/sys/fs/pipe-max-size 控制，默认 1048576 字节（1 MiB）。别把 65536 写死在代码里。

素材原文把管道说成「虚拟并挂载为环形文件系统对象」，这句不成立：管道在内核里由 struct pipe_inode_info 加一组 struct pipe_buffer 组成环，数据通路上没有 inode，也没有任何挂载动作。要拆这块实现，去 B.内核。

四、管道的读写语义与阻塞 #

管道只有两个变量需要盯：对端是否还有人持有 fd，缓冲区是满还是空。排列组合就是下面这张表。

不设 O_NONBLOCK（默认阻塞模式）：

操作 对端状态 缓冲状态 系统调用表现
read 还有进程持有写端 无数据 阻塞，直到有数据或被信号中断
read 写端已全部关闭 无数据 立即返回 0，即 EOF
read 写端已全部关闭 还有残留数据 先把残留读完，读空后才返回 0
write 还有进程持有读端 缓冲区满 阻塞，直到有空间
write 读端已全部关闭 任意 立即给写进程发 SIGPIPE

第三行是新手最常踩的坑：写端关了不代表立刻 EOF，管道里剩下的字节得先读完。

读端全关时的 SIGPIPE 要拆开说。SIGPIPE 的默认动作是终止进程（Term，见 signal(7) 默认动作表）。所以「往没人读的管道写」的默认结局是写进程被自己写死。若进程把 SIGPIPE 设成 SIG_IGN，write() 不再杀进程，而是返回 -1 并把 errno 置为 EPIPE。两种结局都得处理，服务端代码尤其如此 —— 客户端断连时 write 触发 SIGPIPE 会让整个服务进程消失。

SIGPIPE 的产生条件很明确：所有指向读端的 fd 都被关闭，且这时有人写。这解释了关闭纪律为何重要 —— 多余的 fd 只要还剩一个没关，SIGPIPE 和 EOF 都不会出现。

设了 O_NONBLOCK 之后，规则全部改写：

操作 条件 表现
read 还有写者，无数据 返回 -1，errno = EAGAIN
read 写端已全部关闭 返回 0
write n ≤ PIPE_BUF，空间够 立即写入全部 n 字节
write n ≤ PIPE_BUF，空间不够 返回 -1，errno = EAGAIN，一个字节都不写
write n > PIPE_BUF，管道已满 返回 -1，errno = EAGAIN
write n > PIPE_BUF，有部分空间 返回 1 到 n 之间某个值，即部分写，调用方自己循环补齐

PIPE_BUF 在 Linux 上是 4096 字节，POSIX.1 只要求不小于 512。原子性的分界就在这里：不超过 PIPE_BUF 的写入要么全进要么全不进，超过之后内核允许把字节与其他写者的字节交织。

EAGAIN 与 EINTR 别混淆。EAGAIN 是「非阻塞下暂时没空间或没数据」，重试即可；EINTR 是「阻塞中被信号打断」，见第十四节。

c
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(void)
{
    int fd[2];
    pipe(fd);
    close(fd[0]);                             /* 读端全关 */

    signal(SIGPIPE, SIG_IGN);                 /* 别让默认动作杀掉进程 */
    if (write(fd[1], "x", 1) < 0) {
        printf("write: errno=%d (%s)\n", errno, strerror(errno));   /* EPIPE */
    }
    return 0;
}

把 signal(SIGPIPE, SIG_IGN) 注释掉再跑，进程会被 SIGPIPE 杀掉，echo $? 得到 141，即 128 + 13。这个数字在调 shell 脚本时经常见到。

五、管道与 fork 的配合 #

pipe() 单独用没多大意思，它的正题是配合 fork()。fork() 复制父进程的文件描述符表，子进程拿到的 fd 与父进程指向同一个打开文件描述（同一个管道对象），不是两份数据。

这带来一条纪律：谁用不到哪一端，就在 fork() 之后立刻关掉。父读子写，就父关写端、子关读端。

c
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void)
{
    int fd[2];
    char buf[128];

    pipe(fd);
    pid_t pid = fork();

    if (pid == 0) {
        close(fd[1]);                     /* 子进程只读，关写端 */
        ssize_t n = read(fd[0], buf, sizeof(buf) - 1);
        if (n > 0) {
            buf[n] = '\0';
            printf("[child ] got: %s\n", buf);
        } else if (n == 0) {
            printf("[child ] EOF\n");
        }
        close(fd[0]);
        _exit(0);
    }

    close(fd[0]);                         /* 父进程只写，关读端 */
    write(fd[1], "hello child", 11);
    close(fd[1]);                         /* 关掉最后一个写端，子进程才读到 EOF */
    wait(NULL);
    return 0;
}

最后那句 close(fd[1]) 是关键。写端 fd 的引用计数减到 0，内核才会让读端看到 EOF。素材原文把这里注释成「这会向子进程发送 EOF 信号」，措辞不对 —— 没有 EOF 信号这种东西，EOF 只是 read() 返回 0 这个返回值约定。

忘关的后果很具体。删掉父进程那句 close(fd[1])，子进程的 read() 会一直挂着：写端还有父进程持有，内核认定数据还会来，于是它继续等。父进程在 wait() 里等子进程，子进程在 read() 里等数据，两边一起死锁。这是管道编程的头号 bug，strace -f 一看就清楚：两个进程分别卡在 read(3, 和 wait4(...)。

要双向通信就建两根管道，各自规定方向。素材原文有一段用两根管道加 dup2() 接管 /bin/sh 的例子，骨架正确，硬伤出在读取端：它用 usleep(150000) 加单次 read() 去「约等于」拿到子进程的全部输出。这个假设不成立 —— sh 的执行时间和输出量都不受你控制，read() 只保证拿到至少一个字节。修正版放在第八节。

六、有名管道：FIFO #

无名管道的限制很硬：只能靠继承 fd 传递，只有亲缘进程能用。FIFO（First In First Out，也叫命名管道）把入口搬到文件系统上，给管道挂一个路径名，任何有权限的进程都能 open() 它。

它只是一个标识点。ls -l 看到的类型是 p，stat 的大小是 0，数据一个字节都不写进磁盘，全部留在内核缓冲里。文件系统的作用仅仅是让无关进程找到同一个管道对象。

c
#include <sys/stat.h>
#include <sys/types.h>

int mkfifo(const char *pathname, mode_t mode);
  • mode 是权限位，实际权限为 mode & ~umask，传 0666 是常规写法。
  • 路径已存在时返回 -1，errno = EEXIST。要可重复执行，先 unlink() 或先 access(pathname, F_OK) 探测。
  • 命令行等价物：mkfifo /tmp/my_fifo；mkfifo -m 0600 /tmp/my_fifo 直接指定权限。
  • 版本：mkfifo() 属 POSIX.1-2001（更早的 POSIX.1-1990 已有），Linux 一直提供。

常见 errno：

errno 含义
EACCES 上级目录无写或执行权限
EEXIST 路径已存在（含已存在的同名 FIFO）
ENAMETOOLONG 路径名过长
ENOENT 上级目录不存在
ENOSPC 磁盘空间不足（目录项也要占空间）
EROFS 目标在只读文件系统上

打开 FIFO 的阻塞规则与无名管道不同，多了一层「open() 本身就会阻塞」：

打开方式 阻塞模式（默认） 设 O_NONBLOCK
open(path, O_RDONLY) 阻塞，直到有进程以写方式打开 立即成功返回
open(path, O_WRONLY) 阻塞，直到有进程以读方式打开 无读端时立即失败，errno = ENXIO
open(path, O_RDWR) 成功 成功

最后一行是 Linux 的行为：Linux 允许以读写方式打开 FIFO，POSIX 对此未定义，别在可移植代码里依赖。它还有副作用 —— 自己同时持有读写端，永远等不到 EOF，容易把自己写死。

打开之后的 read/write 语义与无名管道完全一致，按第四节的表处理。这里要纠正素材原文一处错误：它说非阻塞模式下「若没有数据可读，read 直接返回 0」。准确条件是写端已全部关闭时才返回 0；若还有写者持有写端只是暂时没数据，read 返回 -1 且 errno = EAGAIN。两者混为一谈，写出来的读循环会在空闲时误判成对端退出，提前收摊。

写端与读端各一个进程，用 fork() 把两个角色凑在一起跑：

c
#include <fcntl.h>
#include <stdio.h>
#include <sys/stat.h>
#include <sys/wait.h>
#include <unistd.h>

#define FIFO_PATH "/tmp/demo_fifo"

int main(void)
{
    char buf[128];
    ssize_t n;

    unlink(FIFO_PATH);
    mkfifo(FIFO_PATH, 0666);              /* 已存在则返回 -1，errno = EEXIST */

    if (fork() == 0) {                    /* 读端 */
        int rfd = open(FIFO_PATH, O_RDONLY);   /* 阻塞，等写端 open */
        while ((n = read(rfd, buf, sizeof(buf) - 1)) > 0) {
            buf[n] = '\0';
            printf("[reader] %s\n", buf);
        }
        puts("[reader] writer closed, bye");
        close(rfd);
        _exit(0);
    }

    puts("[writer] blocks until the reader shows up");
    int wfd = open(FIFO_PATH, O_WRONLY);  /* 阻塞，等读端 open */
    write(wfd, "hello fifo", 10);
    close(wfd);                           /* 关掉唯一写端，读端才读到 EOF */
    wait(NULL);

    unlink(FIFO_PATH);
    return 0;
}

两个进程谁先跑都行，open() 会互相等待到齐；这一点和无名管道不同，FIFO 的同步点就在 open() 本身。素材原文让写端负责 mkfifo()，两个进程谁先跑都会出问题：写端还没建 FIFO 时，读端 open() 会因为 ENOENT 直接返回。稳妥做法是让创建动作脱离这两个进程：脚本里先 mkfifo，或由父进程建好再 fork，把「谁负责建」「谁负责删」写进约定。

管道与 FIFO 的差别，归结起来只有一行：创建与打开的方式不同，一旦打开，I/O 语义一模一样。

维度 无名管道 pipe() 有名管道 FIFO
创建 pipe() / pipe2() mkfifo() 或 mkfifo(1)
文件系统入口 无 有路径名，ls -l 类型为 p
适用进程 仅亲缘进程（靠 fd 继承） 任意有权限的进程
打开是否阻塞 不涉及 open() 会，按打开模式与 O_NONBLOCK 决定
数据落盘 否 否
生命周期 fd 全关即释放 路径一直存在，直到 unlink
read/write 语义 相同 相同
SIGPIPE / EOF 规则 相同 相同

七、popen 与 pclose：管道的便捷封装 #

手动写 pipe() → fork() → dup2() → exec() 去跑一条 shell 命令，三十行起步。标准库把这一套包成了 popen()。

c
#include <stdio.h>

FILE *popen(const char *command, const char *type);
int pclose(FILE *stream);

popen() 内部做四件事：建管道、fork()、子进程里把管道一端 dup2() 到标准输入或标准输出、execl("/bin/sh", "sh", "-c", command, NULL)。你拿到的 FILE * 背后是 stdio 缓冲加一根管道，不是命令本身。

type 只有两种取值，方向别搞反：

type 管道方向 你拿到的是 场景
"r" 子进程 stdout → 父进程 命令的输出 抓 ping、ls、ifconfig 的结果
"w" 父进程 → 子进程 stdin 命令的输入 往 sort、grep、bc 里灌数据

记法：主语永远是你。"r" 表示你读，"w" 表示你写。

pclose() 干三件事：关流、wait4() 等子进程退出、返回状态。这个返回值是 wait 系列的编码值，不是退出码，要过一层 WEXITSTATUS()（正常退出才有意义）或 WIFSIGNALED() / WTERMSIG()（被信号杀死时）。

c
#include <stdio.h>
#include <sys/wait.h>

int main(void)
{
    char buf[256];
    FILE *fp = popen("ls -l /tmp | wc -l", "r");
    if (fp == NULL) {
        return 1;
    }
    while (fgets(buf, sizeof(buf), fp) != NULL) {
        printf("[out] %s", buf);
    }

    int status = pclose(fp);
    if (WIFEXITED(status)) {
        printf("child exit code: %d\n", WEXITSTATUS(status));
    } else if (WIFSIGNALED(status)) {
        printf("child killed by signal: %d\n", WTERMSIG(status));
    }
    return 0;
}

反方向就是换一个字母：popen("sort", "w") 之后用 fprintf(fp, "pear\napple\n") 灌数据，pclose(fp) 关掉写端，sort 收到 EOF 才会真正排序输出。少了 pclose()，sort 一直等 EOF，你什么都看不到。

两个坑必须提前说。别只 popen() 不 pclose() —— 少了它就是僵尸进程加 fd 泄漏，还丢掉了与子进程的同步点。别让管道灌满 —— 子进程的 stdout 全指向管道，容量有限（默认 16 页），popen(..., "r") 之后不读，子进程写到 65536 字节就卡在 write()，此时你在 pclose() 里等它退出，两边互等。

安全上还有一条：popen() 走 /bin/sh -c，命令字符串会被 shell 解析。字符串里拼了外部输入（文件名、URL 参数、用户填的字段），等于把 shell 注入的口子递过去。带 SUID 位的程序里更不能用 —— 它完整继承环境变量（IFS、LD_PRELOAD 之类），攻击面直接敞开。执行固定程序用 fork() + execv() 传参数数组，别过 shell。

system() 经常被拿来对比：它不建管道，子进程直接继承父进程的标准 I/O，所以取不到命令输出，也没法喂输入；返回值和 pclose() 一样是 wait 状态；底层同样是 /bin/sh -c。要拿输出就 popen，只关心成败就 system。

八、管道的典型应用：shell 的 | #

ls -l | grep '^d' | wc -l 背后是三根管道、四个进程。bash 的处理顺序：先给每个 | 建一根管道，再对每条命令 fork()，子进程里把前一根管道的读端 dup2 到 stdin、后一根的写端 dup2 到 stdout，然后 exec。父 shell 不搬数据，只建管道和 wait 整组子进程。

用 strace -f -e trace=pipe,clone,dup2,execve bash -c 'ls | wc -l' 能看到这段构造：pipe2([3, 4], O_CLOEXEC) 出现一次，接着两次 clone，子进程里 dup2(4, 1)，然后 execve("/usr/bin/ls")。

这条链上有三个容易忽略的行为。两端都要关：每个子进程 exec 前得把不用的 fd 关掉（现代 bash 用 O_CLOEXEC 自动完成），否则下游永远等不到 EOF。退出状态只看最后一个：默认 $? 是最后一条命令的状态，中间失败你看不见，set -o pipefail 改成「任一环节失败即失败」。背压是天然的：上游写快了会被管道容量卡住，自动降速等下游消费，流控不用自己写。

重定向符号本质都在操作 fd：

写法 含义 等价内核动作
cmd > file stdout 到文件 open(O_WRONLY|O_CREAT|O_TRUNC) 后 dup2 到 1
cmd >> file 追加 同上，加 O_APPEND
cmd 2>&1 stderr 合并到 stdout dup2(1, 2)
cmd < file stdin 来自文件 open(O_RDONLY) 后 dup2 到 0
cmd1 | cmd2 管道连接 pipe() + 两次 dup2

dup2(oldfd, newfd) 的语义：关掉 newfd，让 newfd 指向 oldfd 那个打开文件描述，两者共享同一个文件偏移和同一组状态标志。顺序很要紧 —— cmd 2>&1 > file 先把 2 指到当前的 1（终端），再把 1 改到文件，stderr 仍留在终端；cmd > file 2>&1 先把 1 改到文件，再把 2 指到 1，两者都进文件。

素材原文那段「双管道接管 /bin/sh」是这条链的应用版：父进程通过 pipe_in 往 sh 的 stdin 写命令，通过 pipe_out 读 sh 的 stdout。骨架对，读取端需要改：

c
#define _GNU_SOURCE
#include <poll.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void)
{
    int pipe_in[2], pipe_out[2];
    pipe(pipe_in);
    pipe(pipe_out);

    pid_t pid = fork();
    if (pid == 0) {
        dup2(pipe_in[0],  STDIN_FILENO);
        dup2(pipe_out[1], STDOUT_FILENO);
        dup2(pipe_out[1], STDERR_FILENO);
        close(pipe_in[0]);  close(pipe_in[1]);
        close(pipe_out[0]); close(pipe_out[1]);
        execlp("sh", "sh", (char *)NULL);
        _exit(127);
    }

    close(pipe_in[0]);
    close(pipe_out[1]);
    write(pipe_in[1], "id; uname -r\n", 13);

    char buf[4096];
    struct pollfd pfd = { .fd = pipe_out[0], .events = POLLIN };
    while (poll(&pfd, 1, 200) > 0) {        /* 200 ms 无新数据就收工 */
        ssize_t n = read(pipe_out[0], buf, sizeof(buf) - 1);
        if (n <= 0) {
            break;
        }
        buf[n] = '\0';
        fputs(buf, stdout);
    }

    close(pipe_in[1]);                      /* 关写端，sh 读到 EOF 自行退出 */
    close(pipe_out[0]);
    waitpid(pid, NULL, 0);
    return 0;
}

三处改动值得对照原文：usleep(150000) 加单次 read() 换成 poll() 循环（单次 read() 只保证拿到至少一个字节）；read() 返回 0 或负值立刻跳出，不空转；循环结束后才关 pipe_in[1]，让 sh 收到 EOF 自己退出，避免 waitpid() 永久阻塞。

代价也要说清：poll 加超时收尾仍是「等你先说完」的启发式，遇到慢命令会提前截断输出。要严谨就让 sh 自己退出（命令串末尾带 exit），然后一直 read() 到 EOF —— EOF 是唯一的「对方说完了」的确切信号。

九、管道的能力边界 #

管道简单，代价是能力有限。七条边界背下来，选型能少走一轮返工。另外，管道传的是字节，不是对象 —— 要传文件描述符，得用 UNIX domain socket 的 SCM_RIGHTS；要传对端凭证，得用 SO_PEERCRED。管道做不到，这是 socket 存在的一大理由。

边界 具体表现 绕过办法
单向 一根管道只有一个方向 建两根，或换 UNIX domain socket
无消息边界 字节流，read 拿到的长度与 write 次数无关 自定长度前缀，或换消息队列、O_DIRECT 管道
无名管道限亲缘进程 靠 fd 继承传递，无法交给无关进程 换 FIFO、UNIX domain socket
容量有限 默认 16 页，写满即阻塞 及时消费，或 F_SETPIPE_SZ 调整
不可定位 lseek() 返回 -1，errno = ESPIPE 用文件或共享内存
不持久 进程全退，数据即消失 用文件、消息队列
无优先级 严格 FIFO，先写先读 消息队列（带类型或优先级）

「无消息边界」最常被低估。write(fd, "abc", 3) 两次，读端一次 read(fd, buf, 100) 会拿到 6 个字节；反过来 write(fd, buf, 1000) 一次，读端缓冲区只有 100 时得读十次。这不是 bug，是流式接口的定义。写应用层协议时，固定长度、长度前缀、分隔符三者选一个，别指望管道替你保留边界。

十、信号是什么：异步事件通知 #

管道传数据，信号只传「一件事发生了」。信号不带负载（sigqueue() 能附带一个整数或指针，那是后话），标准信号不排队，时序也不保证。

「异步」两个字是理解信号的全部入口。看两行代码：

c
int a = 1 / 0;                    /* 同步：SIGFPE 在这条指令执行时立即产生 */
kill(getpid(), SIGUSR1);          /* 异步：发出后何时执行处理函数由内核调度决定 */

第一行是同步信号，由当前指令触发，内核在异常处理路径上直接投递给当前进程，时机确定。第二行是异步信号，从发出到递达之间隔着不确定的窗口，中间进程还在跑别的代码。

信号的生命周期分三段。产生：三种来源 —— 硬件异常（除零 SIGFPE、野指针 SIGSEGV、非法指令 SIGILL）、终端按键（Ctrl+C 发 SIGINT、Ctrl+\ 发 SIGQUIT、Ctrl+Z 发 SIGTSTP）、软件调用（kill()、raise()、alarm()、sigqueue()，以及内核因管道断开而发的 SIGPIPE）。未决（pending）：信号已产生但还没递达，内核在进程的 pending 位图里把对应位置 1。递达（delivered）：进程被调度运行，且该信号没被屏蔽字阻塞，内核清掉 pending 位，转去执行处理动作。

进程对每个信号有且只有三种处置：设成 SIG_DFL 走默认动作，设成 SIG_IGN 忽略，传函数指针捕获。SIGKILL 和 SIGSTOP 是例外 —— 内核不允许对它们设捕获或忽略，sigaction() 会对它们返回 EINVAL，往屏蔽字里塞会被静默忽略。这两条是内核留的底牌，否则一个死循环的进程就能彻底不可杀。

十一、信号的种类与默认行为 #

kill -l 列出全部信号。Linux 上的编号分布：1 ~ 31 是标准信号（也叫普通信号、不可靠信号），继承自早期 UNIX；34 ~ 64 是实时信号。从 34 起而不是 32，因为 glibc 的 NPTL 线程实现内部占用了两个实时信号做线程管理，SIGRTMIN 因此被抬到 34。别用硬编码数字指代实时信号，写 SIGRTMIN+n，并检查不超过 SIGRTMAX。

常用信号的默认动作（编号按 x86/ARM）：

信号 编号 默认动作 触发场景
SIGHUP 1 Term 控制终端挂断，或控制进程死亡
SIGINT 2 Term Ctrl+C
SIGQUIT 3 Core Ctrl+\
SIGILL 4 Core 非法指令
SIGABRT 6 Core abort()
SIGBUS 7 Core 总线错误，地址对齐错误
SIGFPE 8 Core 算术错误，整数除零
SIGKILL 9 Term 强制杀死，不可捕获不可忽略
SIGUSR1 10 Term 用户自定义 1
SIGSEGV 11 Core 非法内存引用
SIGUSR2 12 Term 用户自定义 2

编号只在 x86/ARM 上成立。SPARC 上 SIGUSR1 是 30，MIPS 上是 16，别把数字写进跨平台代码，用宏名。

动作列有五种取值，含义各不相同：

实际开发打交道最多的是五个：SIGINT（Ctrl+C）、SIGTERM（kill 默认）、SIGKILL（杀不掉时用）、SIGCHLD（回收子进程）、SIGPIPE（管道断开）。SIGHUP 在老式守护进程里当「重载配置」用，systemd 体系下多用 SIGTERM 加重启。

十二、信号的发送：kill 与 raise #

c
#include <signal.h>
#include <sys/types.h>

int kill(pid_t pid, int sig);
int raise(int sig);

kill() 的名字有误导性 —— 它不专管杀进程，是最通用的发信号接口，名字来自早期 UNIX 的 kill(1) 命令，历史包袱。pid 的取值有五种语义：

pid 取值 含义
pid > 0 发给进程 ID 为 pid 的那个进程
pid == 0 发给同进程组的所有进程（含自己）
pid == -1 发给调用者有权发送的所有进程（init 除外）
pid < -1 发给进程组 ID 等于 -pid 的所有进程
sig == 0 不发信号，只做存在性与权限检查

sig == 0 值得单记：它能探测「这个 PID 是否存在、我有没有权限」。返回 -1 且 errno == ESRCH 表示进程不存在，errno == EPERM 表示存在但没权限。比去读 /proc 更轻。这两种 errno 要分开处理，很多代码把它们混成一个「失败」，结果把自己的权限问题误判成进程已退出。

raise(sig) 等价于 kill(getpid(), sig)，向自己发。它在带线程的程序里更合用：raise() 只发给当前线程，kill(getpid(), sig) 是发给整个进程，内核随便挑一个没屏蔽该信号的线程投递。

相关接口：alarm(seconds) 设一次性定时器，超时发 SIGALRM，返回上次剩余秒数，传 0 表示取消；pause() 挂起直到任一信号被捕获，恒返回 -1 且 errno = EINTR；sigqueue(pid, sig, value) 发实时信号并附带一个值，需 SA_SIGINFO 才能收到；killpg(pgrp, sig) 向整个进程组发信号。

pause() 有个经典陷阱：它和「检查标志位」之间存在竞态窗口。

c
if (!flag) {
    pause();      /* flag 若在这两行之间被置位，pause 会永远等下去 */
}

信号在 if 判断之后、pause() 之前到达，处理函数把 flag 置了位，然后 pause() 挂起 —— 该来的信号已经用掉了，进程就此长眠。解法是 sigsuspend()，它把「改屏蔽字」和「挂起」合成一个原子操作，见第十五节。

十三、信号的捕获：signal 与 sigaction #

signal() 老，sigaction() 新。讲清为什么，比记住两个原型有用。

c
#include <signal.h>

typedef void (*sighandler_t)(int);
sighandler_t signal(int signum, sighandler_t handler);

signal() 的问题是语义不确定。同一个调用在不同 UNIX 上行为不同，POSIX 明确允许这种差异。两套历史实现：

方面 System V 语义 BSD 语义
处理函数执行时，处置是否恢复默认 是，恢复为 SIG_DFL，必须重新注册 否，保持捕获
处理期间同类信号是否被阻塞 否，可以递归进来 是，自动屏蔽
被中断的系统调用 返回 EINTR 自动重启（相当于 SA_RESTART）
等价于 sigaction() 的 SA_RESETHAND | SA_NODEFER SA_RESTART

第一行是致命伤。System V 语义下，处理函数一开始执行，处置就退回默认，想继续捕获必须在函数第一行重新 signal()。这中间有个窗口 —— 两个同类信号密集到达，第二个会按默认动作把进程干掉。这也是「不可靠信号」这个名字的由来之一。

Linux 上的实际情况是拧着的：

  • 内核的 signal() 系统调用是 System V 语义。
  • glibc 的 signal() 包装函数不调内核系统调用，内部用 sigaction() 配出 BSD 语义。前提是定义了合适的特性测试宏（glibc 2.19 之前是 _BSD_SOURCE，2.19 及之后是 _DEFAULT_SOURCE，缺省都开着）。宏没开，signal() 就退回 System V 语义。

同一份代码在不同编译选项下行为不同。这种坑没法用文档消灭，只能用接口消灭：建立处理函数一律用 sigaction()。signal() 唯一可移植的用法是把处置设成 SIG_DFL 或 SIG_IGN，不求返回值，不处理信号。

c
#include <signal.h>

int sigaction(int signum, const struct sigaction *act, struct sigaction *oldact);
  • signum：信号编号，给 SIGKILL 或 SIGSTOP 会返回 EINVAL。
  • act：新处置；传 NULL 表示只查询不动手。
  • oldact：传出旧处置，不需要就传 NULL。
  • 返回 0 成功，-1 失败。版本：POSIX.1-2001 起在标准里，SVr4 就有，Linux 一直提供。

结构体：

c
struct sigaction {
    void     (*sa_handler)(int);                        /* 简单处理函数 */
    void     (*sa_sigaction)(int, siginfo_t *, void *); /* 带信息的处理函数 */
    sigset_t   sa_mask;                                 /* 处理期间的附加屏蔽字 */
    int        sa_flags;                                /* 行为标志 */
    void     (*sa_restorer)(void);                      /* 内部用，别碰 */
};

sa_handler 与 sa_sigaction 常常是同一块内存的两种解释（有的架构上是 union）。只赋值其中一个，两个都写会互相覆盖。

sa_mask 的语义要说准：处理函数执行期间，内核把 sa_mask 里的信号追加到当前线程的屏蔽字上；处理函数返回后自动恢复原屏蔽字。当前正在处理的那个信号本身也会被自动加入，除非设了 SA_NODEFER —— 这就是「同类信号不会递归打断自己」的机制来源。

c
struct sigaction act = {0};
act.sa_handler = on_sigterm;
sigemptyset(&act.sa_mask);          /* 先清空，别留未初始化的位 */
sigaddset(&act.sa_mask, SIGINT);    /* 处理 SIGTERM 期间顺带屏蔽 SIGINT */
act.sa_flags = SA_RESTART;
sigaction(SIGTERM, &act, NULL);

sigemptyset() 那一行别省。栈上的 struct sigaction 内容是随机的，sa_mask 里残留的位会让内核屏蔽一堆你没打算屏蔽的信号，症状是「某些信号莫名收不到」。

sa_flags 常用位：

标志 作用 版本
SA_RESTART 被中断的系统调用自动重启，不返回 EINTR POSIX.1-2001（XSI），2008 进基础规范
SA_SIGINFO 用三参数版本，可拿 siginfo_t Linux 2.2，POSIX.1-2001
SA_NODEFER 处理期间不屏蔽当前信号，允许同类信号递归 POSIX.1-2001；旧名 SA_NOMASK
SA_RESETHAND 进入处理函数时处置恢复默认，一次性 POSIX.1-2001；旧名 SA_ONESHOT
SA_NOCLDSTOP 仅对 SIGCHLD：子进程停止或继续时不通知 POSIX.1-2001
SA_NOCLDWAIT 仅对 SIGCHLD：子进程退出后不产生僵尸 Linux 2.6，POSIX.1-2001
SA_ONSTACK 在 sigaltstack() 提供的备用栈上执行处理函数 POSIX.1-2001
SA_RESTORER 内部用，glibc 自己设置，别碰 Linux 专有

SA_RESTART 用得最多，但它不是万能的。read/write/open/wait/socket 系列能被它救回来；poll、select、epoll_wait、nanosleep、pause、sigsuspend、msgrcv 这些永远返回 EINTR，加了 SA_RESTART 也一样。这个分界在 signal(7) 里列得很清楚，写循环时必须区分对待。

SA_SIGINFO 换来的是信息量。普通处理函数只知道「是几号信号」，三参数版本还能拿到 siginfo_t：

c
static void on_usr(int sig, siginfo_t *info, void *ucontext)
{
    (void)ucontext;
    int sender_pid = info->si_pid;    /* 谁发的 */
    int sender_uid = info->si_uid;
    int code       = info->si_code;   /* SI_USER / SI_QUEUE / SI_TKILL ... */
    (void)sender_pid; (void)sender_uid; (void)code;
}

siginfo_t 里哪些字段可用取决于信号来源：kill() 发的填 si_pid/si_uid，sigqueue() 发的额外填 si_value，硬件异常填 si_addr（出错地址），SIGCHLD 填 si_status/si_utime/si_stime。别对不适用的字段做假设。

接口摆完了，下一个问题是：处理函数到底在什么时候被执行，在里面能干什么。

十四、信号处理的时机与可重入性 #

内核不会在任意一条用户指令上停下来送信号。递达只发生在两个时刻：从内核态返回用户态的前夕，或者进程在内核里睡眠被唤醒、即将返回用户态时。这条规则带来两个推论：纯用户态死循环照样能被 SIGKILL 杀掉（时钟中断会周期性把进程拉进内核，返回前就是检查点）；信号是插进来执行的，不是排队等你的主流程走到某个断点。

实现手法值得看一眼：检测到有未决且未屏蔽的信号时，内核在该进程的用户栈上构造一个临时栈帧，把返回地址（PC）改成用户处理函数的入口，把原返回地址和寄存器现场存进这个帧；处理函数执行完返回，经信号跳板调用 sigreturn，内核据帧恢复现场，执行流回到被中断处继续。处理函数是插进主流程中间的 —— 这是所有可重入问题的根源。

设想主流程正在 printf 里持有 stdio 的锁，这时 SIGINT 到达，处理函数里又调了 printf。同一把锁被同一执行流申请两次，非递归锁直接死锁。换成 malloc 也一样：arena 锁被自己卡住。因此规则只有一条：处理函数里只能调异步信号安全的函数。

清单在 signal-safety(7) 里。常用的安全项：write、read、open、close、_exit、kill、sigaction、signal、waitpid、sem_post。不安全项：printf/fprintf 系列、malloc/free、exit（会跑 atexit 和 stdio 刷新）、syslog、strtok、大多数 pthread_*。errno 可以放心用 —— 进入处理函数前内核与 glibc 会保存它，返回时恢复。

正确姿势是从处理函数里只往外抛一个标志：

c
#include <signal.h>
#include <stdio.h>
#include <unistd.h>

static volatile sig_atomic_t g_stop = 0;   /* 只能这样共享 */

static void on_term(int sig)
{
    (void)sig;
    g_stop = 1;                            /* 唯一允许的动作 */
}

int main(void)
{
    struct sigaction act = {0};
    act.sa_handler = on_term;
    sigemptyset(&act.sa_mask);
    act.sa_flags = 0;                      /* 不设 SA_RESTART，让 sleep 被打断 */
    sigaction(SIGTERM, &act, NULL);
    sigaction(SIGINT,  &act, NULL);

    while (!g_stop) {
        sleep(1);                          /* 被中断时返回剩余秒数 */
    }
    write(STDOUT_FILENO, "bye\n", 4);
    return 0;
}

volatile sig_atomic_t 是这个场景唯一可移植的共享类型。volatile 挡住编译器把循环里的读取优化掉，sig_atomic_t 保证单个读写在信号打断下不被撕裂。换成 int 加 volatile 在多数平台能跑，但标准不保证。

需要传更多信息时，别在处理函数里处理，把信号转成文件描述符事件：self-pipe 技巧（处理函数里只 write 一个字节到管道，主循环从管道读）或者 Linux 的 signalfd()。两者都能让信号并入 poll/epoll 的事件循环，逻辑回到单线程顺序执行。

十五、信号的阻塞与未决 #

屏蔽字（signal mask）决定哪些信号暂不递达。被阻塞的信号不会丢，它进入未决集，等解除阻塞再递达。

c
#include <signal.h>

int sigprocmask(int how, const sigset_t *set, sigset_t *oldset);
int sigpending(sigset_t *set);

how 三选一：SIG_BLOCK 把 set 加进屏蔽字，SIG_UNBLOCK 从中移除，SIG_SETMASK 直接替换。oldset 非空时回传旧屏蔽字，sigprocmask(SIG_SETMASK, &old, NULL) 就是恢复原状的写法。sigpending(&set) 把当前未决集读出来，内容是「进程级未决」与「调用线程未决」的并集。

信号集本身一律通过函数操作，别碰内部位域：sigemptyset() 清空，sigfillset() 全部置位，sigaddset() 加入一个，sigdelset() 删掉一个，sigismember() 判断是否在集合里（返回 1/0/-1）。

一个完整例子：进临界区前屏蔽 SIGINT，期间检查它是否已挂起，出临界区再恢复。

c
#include <signal.h>
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    sigset_t block, old, pend;

    sigemptyset(&block);
    sigaddset(&block, SIGINT);            /* 准备屏蔽 Ctrl+C */
    sigprocmask(SIG_BLOCK, &block, &old);

    printf("[main] critical section, SIGINT blocked\n");
    for (int i = 0; i < 3; i++) {
        sleep(1);
        sigpending(&pend);
        if (sigismember(&pend, SIGINT)) {
            printf("[main] SIGINT is pending (blocked as expected)\n");
        }
    }

    sigprocmask(SIG_SETMASK, &old, NULL); /* 恢复，挂起的 SIGINT 立刻递达 */
    printf("[main] unblocked\n");
    return 0;
}

在它跑的时候按 Ctrl+C，前三秒内你会看到 SIGINT is pending，等 sigprocmask 恢复屏蔽字的瞬间进程被 SIGINT 终止。

屏蔽字是每线程独立的。sigprocmask() 在多线程程序里的行为未定义，要用 pthread_sigmask()。fork() 出来的子进程继承一份屏蔽字副本，execve() 之后屏蔽字保持不变 —— 这一点和处置不同，处置里「被捕获的」会复位成默认，「被忽略的」保持忽略。

屏蔽字还解决了第十二节 pause() 的竞态。sigsuspend() 把「换屏蔽字」和「挂起」做成一个原子操作：

c
int sigsuspend(const sigset_t *mask);

它先把屏蔽字替换成 mask，然后挂起，直到某个未被屏蔽的信号被捕获；处理函数返回后 sigsuspend() 返回 -1，errno = EINTR，屏蔽字恢复成调用前的值。正确写法是先屏蔽目标信号、检查条件、再用一个「只放开目标信号」的集合调 sigsuspend()，唤醒后重新检查条件并回到屏蔽状态。这个「屏蔽—检查—原子挂起」的循环，是用户态等信号的标准骨架。

十六、可靠信号与不可靠信号 #

两套信号的差别只有一条，但这条决定了你能不能拿它数次数。

维度 标准信号（1~31） 实时信号（34~64）
是否排队 不排队 排队
阻塞期间多次产生同一信号 只记一次，其余丢失 每次产生都入队，解除阻塞后逐个递达
附带数据 不能（kill 只能发信号本身） sigqueue() 可带一个整数或指针
多个不同类型未决时的递达顺序 POSIX 未指定 编号小的先递达
同类型多个未决 不存在这种情况 按发送顺序递达
默认动作 各不相同，见 signal(7) 表 一律终止进程
用途 事件通知 需要计数或携带数据的通知

「只记一次」这条要展开。进程阻塞了 SIGUSR1，期间别的进程连发十次，内核只在 pending 位图里保留一个位。解除阻塞后，处理函数只执行一次。附带在 siginfo_t 里的信息也保留第一次的，后续到达不会覆盖。

所以用标准信号统计事件次数是错的。要计数，要么用实时信号（受 RLIMIT_SIGPENDING 限制，Linux 2.6.8 起是每用户上限，此前用 /proc/sys/kernel/rtsig-max 控制；队列满时 sigqueue() 返回 -1 且 errno = EAGAIN），要么干脆换成管道、eventfd 这类能累积的通道。

多个标准信号同时未决时，递达顺序 POSIX 没规定，signal(7) 的原话是 unspecified，别把任何顺序写进逻辑。实时信号与标准信号同时未决时，POSIX 同样未规定谁先，Linux 让标准信号优先。

素材原文说「内核按照信号值从小到大的顺序依次递送」。这句只有实时信号那部分有标准保障（编号小的先递达），标准信号那部分要按「未指定」理解。

十七、实际使用信号要注意的几件事 #

SIGCHLD 必须循环收。 五个子进程几乎同时退出，标准信号会合并成一次 SIGCHLD。处理函数里写一句 waitpid(-1, &st, 0) 只能收一个，剩下四个变僵尸。正确写法：

c
static void on_sigchld(int sig)
{
    int st;
    pid_t pid;
    (void)sig;
    while ((pid = waitpid(-1, &st, WNOHANG)) > 0) {
        /* WNOHANG 保证没有可收的子进程时立刻返回 0，不会卡住 */
    }
}

配套建议加 SA_NOCLDSTOP，否则子进程收到 SIGSTOP/SIGCONT 也会触发 SIGCHLD，waitpid() 却什么也收不到，白白空转。

SIGPIPE 在服务端要主动忽略。 客户端断连后 write 的默认结局是把服务进程杀掉。初始化时 signal(SIGPIPE, SIG_IGN)，之后统一判断 write 返回 -1 且 errno = EPIPE。

别指望在 SIGKILL 下做清理。 SIGKILL 和 SIGSTOP 不可捕获、不可阻塞、不可忽略。清理逻辑挂在 SIGTERM 处理函数里，同时接受「SIGKILL 下数据会损坏」这个事实：需要更强保证就上日志或事务，别跟信号较劲。

注意 execve 与 fork 的处置继承。 fork() 后子进程继承父进程的信号处置副本；execve() 后被捕获的信号复位成默认动作，被忽略的信号继续保持忽略。所以「忽略 SIGPIPE」这个设置会跟着 exec 传给子程序，而自定义处理函数不会。

PID 1 是特例。 内核不为 init 进程（PID 1）执行信号的默认动作，没人注册处理函数的信号直接被丢掉。这就是容器里 docker stop 或 Ctrl+C 对某些镜像没反应的原因 —— 你的进程是 PID 1，SIGTERM 没处理函数，于是被无视。写容器入口程序要么自己 sigaction，要么用 tini、--init 之类的中转。

别用信号做互斥。 信号没有队列、没有原子语义、没有所有权，两个进程用 SIGUSR1/SIGUSR2 互相打，看起来能同步，一旦信号合并或错序就崩。要同步用信号灯，要数据流用管道。
