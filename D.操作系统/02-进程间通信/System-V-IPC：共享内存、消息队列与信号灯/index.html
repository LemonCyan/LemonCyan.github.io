一、System V IPC 的共同点 #

一句话概括：这三件套都是内核里的对象，用 key 挂号、用整数 ID 引用。这条线决定了后面所有行为。

和管道摆在一起看，差别一眼就出来：

维度 管道 / FIFO System V IPC
生命周期 随进程退出销毁（FIFO 留节点，数据清空） 随内核，进程全死也不回收
寻址方式 文件描述符 key → 整数 ID
亲缘限制 无名管道必须有亲缘关系 无限制
同步 依赖读写阻塞与 PIPE_BUF 原子性 消息队列自带；共享内存完全没有
数据单位 字节流 消息包 / 内存块 / 计数器

共同点拆成四条：

  1. 内核持久（Kernel Persistent）。创建之后只要不 IPC_RMID、不重启、不手工 ipcrm，对象就一直挂在内核里。程序崩了，共享内存段还在，消息还在，信号灯值还在。
  2. 统一的 key / ID 双层寻址。ftok 算出 key，shmget / msgget / semget 拿 key 换 ID，后续读写全用 ID。同一份 ipc_perm 权限模型套在三种对象上，0666 这种八进制位和文件权限一个味道。
  3. 三类对象命名空间互相独立。同一个 key 值可以同时是一个共享内存段、一个消息队列、一个信号灯集，三者互不冲突，因为内核按类型分表管理。
  4. 不自动清理。这是它和管道最大的行为差异，也是「跑完程序 ipcs 一看一堆残留」的根源。第十六章专门处理。

三类对象的家族对齐关系如下，函数名只差前缀：

动作 共享内存 消息队列 信号灯集
创建 / 获取 shmget msgget semget
核心操作 shmat / shmdt msgsnd / msgrcv semop
控制 / 删除 shmctl msgctl semctl
数据载体 物理内存页 内核链表节点 内核计数器数组
内核是否参与每次读写 否 是 是
是否自带互斥 否 是 是（本身就是锁）
ipcs 选项 -m -q -s
ipcrm 选项 -m -q -s

记住这张表的对齐规律，后面学一个就等于学三个。

二、key 与 IPC 标识符 #

两个毫不相干的进程要挂到同一个内核对象上，得先能算出同一个「门牌号」。这个门牌号就是 key_t，32 位整型。

c
#include <sys/types.h>
#include <sys/ipc.h>

key_t ftok(const char *pathname, int proj_id);

工作机制：ftok 取 pathname 对应文件的 inode 号和设备号，再拼上 proj_id 的低 8 位，算出一个 key。只要路径和 proj_id 不变，不同进程算出的 key 必定相同。失败返回 -1。

c
key_t key = ftok("/tmp", 'S');   /* 路径 + 一个字符，最省事的写法 */
if (key == -1) { perror("ftok"); return -1; }

三个坑，先记住：

  • proj_id 只有低 8 位参与运算，传 0x1234 和传 0x34 结果一样。
  • 路径指向的文件必须先存在。ftok("msg", ...) 前得手工 touch msg，否则直接 -1。
  • 同一个文件系统上 inode 号会被复用，删文件重建后算出的 key 就变了；不同文件系统上 inode 号会撞车，key 随之冲突。

不想用 ftok 也行，直接把 key 写死成常量（老教材里常见 #define MSGKEY 1024）。代价是全网段所有程序共用这个数字，容易和别人的程序撞。自己写 demo 可以，上线不行。

另有一个特殊值 IPC_PRIVATE（值为 0）：

c
int shmid = shmget(IPC_PRIVATE, 4096, IPC_CREAT | 0666);

传 IPC_PRIVATE 时，xxxget 每次都创建一个全新对象，永远不复用已有对象，返回的 ID 只能靠 fork 继承给子进程。适合父子进程临时通信，不需要 key。

key 换到 ID 之后，ipcs 里看到的 key 列就是它，shmid / msqid / semid 列是 ID。两者别混。

三个 get 接口的签名 #

c
int shmget(key_t key, size_t size, int shmflg);
int msgget(key_t key, int msgflg);
int semget(key_t key, int nsems, int semflg);

shmget 多一个 size，semget 多一个 nsems（集合里包含几个信号量），msgget 只有标志位。

标志位表 #

三个 xxxget 的 flg 参数语义一致：

标志 含义 单独使用 与 IPC_CREAT 同用
IPC_CREAT 不存在就创建 不存在则创建，存在则返回已有 ID 同左
IPC_EXCL 独占创建 行为无定义，别这么用 已存在则返回 -1，errno = EEXIST
IPC_NOWAIT 非阻塞 —— 资源不足时立即返回 -1，不睡眠

权限位和文件一样按八进制给：0600 只有属主可读写，0666 所有人可读写。

c
int id = shmget(key, size, IPC_CREAT | 0666);            /* 有就打开，没有就建 */
int id = shmget(key, size, IPC_CREAT | IPC_EXCL | 0666); /* 只准我建，别人建过就报错 */

IPC_EXCL 单独用是没有意义的。它必须和 IPC_CREAT 一起出现，才表示「创建必须是新建」。老笔记里有种说法是「IPC_EXCL 单独用时，不存在返回 -1、存在返回 0」，这个说法是错的，见附录勘误。

三、ipcs 与 ipcrm：查看与清理 #

程序跑一半崩了、死锁了、或者报 EEXIST 建不出来，第一件事是看内核里剩了什么。两个命令够用。

查看：ipcs #

bash
ipcs -m        # 共享内存
ipcs -q        # 消息队列
ipcs -s        # 信号灯集
ipcs           # 三类一起列

输出列的含义（节选）：

text
------ Shared Memory Segments --------
key        shmid      owner      perms      bytes      nattch     status
0x53010001 32769      alice      666        4096       2

------ Message Queues --------
key        msqid      owner      perms      used-bytes   messages
0x4d010002 1          alice      666        128          2

------ Semaphore Arrays --------
key        semid      owner      perms      nsems
0x41010003 0          alice      666        1
  • nattch：当前有多少进程 shmat 挂上了这个段。归 0 之后被 IPC_RMID 标记过的段才会真正消失。
  • used-bytes / messages：队列里堆积了多少字节、多少条消息。堆着不清说明消费者死了。
  • nsems：信号灯集里有几个灯。

常用开关：

选项 作用
ipcs -l 打印系统限额：共享内存最大段、总页数，队列最大字节、最大条数，信号量集合数上限
ipcs -t 显示各对象的最近操作时间、创建时间、变更时间
ipcs -p 显示创建者 PID 和最后操作者 PID，定位「谁没清」时好用
ipcs -u 汇总当前已用 / 限额

清理：ipcrm #

bash
ipcrm -m 32769        # 按 shmid 删共享内存
ipcrm -q 1            # 按 msqid 删消息队列
ipcrm -s 0            # 按 semid 删信号灯集
ipcrm -M 0x53010001   # 按 key 删，大写字母 + 十六进制 key

ipcrm -a 会清掉所有 IPC 对象。多人共用的机器上敲这个等于搞破坏，别用。

写脚本清理时，别硬编码 ID。按属主过滤更稳：

bash
ipcs -m | awk '$3=="alice" && $6==0 {print $2}' | while read id; do ipcrm -m "$id"; done

ipcs -m 的第三列是 owner 名，不是 UID，所以上面按用户名比。跑之前先 ipcs -m 看一眼实际列位，不同 util-linux 版本列位有偏移。

四、共享内存：最快的 IPC #

原理只有一句：改页表。内核把同一块物理内存页映射进两个进程各自的虚拟地址空间，于是两个进程看到的虽然是不同的虚拟地址，落到的却是同一批物理页框。

text
   进程 A 的页表                进程 B 的页表
  虚拟地址 0x7f...  ──┐    ┌──  虚拟地址 0x7f...
                      ↓    ↓
                 +--------------+
                 |  物理内存页   |   ← 同一块，内核分配
                 +--------------+

这带来的直接结果是：进程 A 写进去，进程 B 立刻能读到，中间没有任何一次系统调用。管道、消息队列、socket 都要把数据从用户态拷进内核再拷出来，两次拷贝；共享内存零次。所以说它是最快的 IPC，这个「最快」不是调优调出来的，是机制决定的。

代价同样明确：

  • 没有同步。内核不参与读写，谁先写谁后读、写到一半被切换，全靠你自己管。第六、十二、十三、十四章都在补这个洞。
  • 没有边界。它就是一块内存，写越界了没人拦你，踩的是别的数据。
  • 大小受限。一次 shmget 的大小受 shmmax 约束，系统总用量受 shmall 约束。
bash
sysctl kernel.shmmax kernel.shmall   # 看限额
ipcs -l | grep -i "max seg size"     # 等价看法

典型用法是「共享内存当数据面，信号量当控制面」：大块数据走 shm，谁是生产者谁是消费者由 sem 决定。这套组合后面会反复出现。

五、shmget 与 shmat 的使用 #

四个接口，一张表看完：

函数 原型 作用 失败返回
shmget int shmget(key_t key, size_t size, int shmflg) 创建或获取共享内存段 -1
shmat void *shmat(int shmid, const void *shmaddr, int shmflg) 段映射进本进程地址空间 (void *)-1
shmdt int shmdt(const void *shmaddr) 解除映射 -1
shmctl int shmctl(int shmid, int cmd, struct shmid_ds *buf) 查询属性 / 删除 / 加锁 -1

shmget #

c
#include <sys/ipc.h>
#include <sys/shm.h>
int shmget(key_t key, size_t size, int shmflg);
参数 说明
key ftok 返回值，或 IPC_PRIVATE
size 字节数。内核按页（4096）向上取整分配，写 1 字节也占一页
shmflg IPC_CREAT / IPC_EXCL 加权限位

两个细节：size 一般给页大小的整数倍，虽然内核会向上取整，但你自己按页对齐能让映射长度和实际容量严格一致，省得算偏移时出错。另外，对已存在的段再次 shmget 时传的 size 小于段容量，内核不报错，直接返回原 ID——所以「传小 size 想缩容」是行不通的。

shmat #

参数 说明
shmaddr 传 NULL 让内核挑空闲虚拟地址，这是唯一推荐用法
shmflg 0 可读写；SHM_RDONLY 只读；SHM_RND 让 shmaddr 向下取整到页边界（配合非 NULL 地址才用）

返回值是映射到本进程的虚拟首地址，成功后像用普通指针一样用它：

c
struct shm_data *shm_ptr = (struct shm_data *)shmat(shmid, NULL, 0);
if (shm_ptr == (void *)-1) {         /* 必须判 -1，不能判 NULL */
    perror("shmat");
    return -1;
}
strcpy(shm_ptr->buf, "hello");

shmat 失败返回的是 (void *)-1，不是 NULL。-1 在全 1 位模式下正好等于 0xFFFF...，所以判断写成 if (shm_ptr == (void *)-1) 或 if ((long)shm_ptr == -1)。

段是新建的时候，内核会把它清零，所以第一次 shmat 读到的是 0。但段被用过一轮、有进程 shmdt 过之后再挂上去，里面还是上一轮的脏数据。别指望它干净。

shmdt #

参数就是 shmat 的返回值，不是 shmid。函数名里是 dt（detach）不是 del，它只解除映射，不删除内核里的段。传错参数、传 shmid 都会返回 -1。

进程退出时内核自动替它 shmdt，所以忘写不算致命。但长生命周期进程反复 shmat 不 shmdt，会把自己的虚拟地址空间耗光。

shmctl #

cmd 作用 buf
IPC_STAT 读属性到 buf 输出
IPC_SET 用 buf 里的值改属性（shm_perm.uid/gid/mode） 输入
IPC_RMID 标记删除 传 NULL
SHM_LOCK 锁定在物理内存，禁止换出 传 NULL，需 CAP_IPC_LOCK
SHM_UNLOCK 解除锁定 传 NULL

IPC_RMID 是这篇里最容易误解的一个。它不是立刻释放物理内存，而是打个删除标记：

  1. shmctl(shmid, IPC_RMID, NULL) 执行后，新进程不能再 shmat 这个段。
  2. 已经挂着的老进程照常读写，不受影响。
  3. 等到 nattch 归 0（所有人 shmdt 或退出），内核才真正回收物理页。

所以「我 IPC_RMID 了但 ipcs -m 还看得见」是正常现象，看 nattch 就知道还差谁。这也是资源泄漏的典型来源：消费者进程卡死了，段永远挂着。推荐的收尾顺序是先 shmdt，再 IPC_RMID：

c
shmdt(shm_ptr);                    /* 先断开自己的映射 */
shmctl(shmid, IPC_RMID, NULL);     /* 再打删除标记 */

最小可跑骨架 #

两份代码，服务端先起。

c
/* shm_write.c：创建并写入 */
#include <stdio.h>
#include <string.h>
#include <sys/ipc.h>
#include <sys/shm.h>

struct shm_data { int ready; char buf[1024]; };

int main(void) {
    int shmid = shmget(ftok("/tmp", 'S'), sizeof(struct shm_data), IPC_CREAT | 0666);
    if (shmid < 0) { perror("shmget"); return -1; }
    struct shm_data *p = (struct shm_data *)shmat(shmid, NULL, 0);
    if (p == (void *)-1) { perror("shmat"); return -1; }

    strcpy(p->buf, "hello from writer");
    p->ready = 1;
    printf("shmid=%d buf=%s\n", shmid, p->buf);
    shmdt(p);            /* 先不删，留给读者进程 */
    return 0;
}

/* shm_read.c：只挂不建，读完删段 */
int main(void) {
    int shmid = shmget(ftok("/tmp", 'S'), 0, 0);   /* size 0 + flg 0：只获取，不创建 */
    if (shmid < 0) { perror("shmget"); return -1; }
    struct shm_data *p = (struct shm_data *)shmat(shmid, NULL, SHM_RDONLY);
    if (p == (void *)-1) { perror("shmat"); return -1; }

    printf("shmid=%d ready=%d buf=%s\n", shmid, p->ready, p->buf);
    shmdt(p);
    shmctl(shmid, IPC_RMID, NULL);
    return 0;
}

编译运行：

bash
gcc -Wall -o shm_write shm_write.c && gcc -Wall -o shm_read shm_read.c
./shm_write; ipcs -m          # 此时能看到这个段，nattch 为 0
./shm_read;  ipcs -m          # 段已消失

注意读者进程 shmget(key, 0, 0) 的写法：size 传 0、flg 传 0，表示「只在已有段里找，找不到就失败」。这是读取端的标准姿势，别传 IPC_CREAT，否则读者会自己建出一个空段。

六、共享内存的同步问题 #

共享内存不提供任何互斥，这话得说得再具体一点：内核根本不参与你的读写，所以你写的每一行赋值都会被任意打断。

经典翻车现场，生产者遍历写 100 个 int，消费者同时遍历读：

c
/* 生产者 */
for (int i = 0; i < 100; i++) p->arr[i] = i;
p->flag = 1;

/* 消费者 */
if (p->flag == 1) {
    for (int i = 0; i < 100; i++) sum += p->arr[i];   /* 读到的是半截数据 */
}

p->flag = 1 那一瞬间，arr 只写了一半。因为写数组和写标志位是两条独立指令，CPU 在这里任意一处切换。这是竞态，不是概率问题，跑得够久必然出现。

还有更隐蔽的：写 8 字节的 long 在 32 位 CPU 上是两条 store 指令，读到的是新旧各半的撕裂值。CPU 重排序还能让 flag 先于 arr 写下去（编译器重排同理）。

四个解法，从粗到细：

方案 做法 代价 适用
信号量互斥 semop 加锁包住整段读写 每次加解锁一次系统调用 通用，本篇主线
信号通知 写完 kill(pid, SIGUSR1)，对方在 handler 里读 信号不可靠、会丢 单生产者单消费者，低频
原子变量 + 内存屏障 __atomic_store_n / __sync_synchronize 无系统调用，最快 只传递标志、计数器
双缓冲 + 序号 写 B 区，写完切序号，读序号的旧区 内存翻倍 高频、大数据

最稳的是信号量。信号灯集本来就是干这个的，第十章起讲。用信号做通知的版本要特别注意：pause() 和信号之间有经典丢信号窗口——信号在「判断条件」之后、「pause() 之前」到达，pause() 就永远等下去了。所以用信号同步必须配 sigprocmask 阻塞 + sigsuspend 原子解阻塞，或者干脆别用信号做数据同步。

一句话结论：共享内存负责快，同步机制负责对，两者必须分开考虑。

七、消息队列：带类型的消息 #

消息队列是内核里维护的一个消息链表。每个节点是一条独立的消息，带类型标号（mtype）和正文（mtext）。

和管道比，三个关键差异：

  1. 消息有边界。管道是字节流，你写 10 字节他写 20 字节，读端会一次读到 30 字节粘在一起。消息队列按条投递，msgsnd 一条就是一条，msgrcv 一次取一条，不存在粘包。
  2. 可按类型挑着收。发送时打上 mtype，接收时指定要哪个 mtype，其他类型的消息原封不动留在队列里。多对多通信全靠这个特性分流。
  3. 自带同步。队列空时 msgrcv 自动挂起，有消息进来内核唤醒；队列满时 msgsnd 自动挂起。你不用写一个锁。

这三条决定了消息队列的定位：低频、结构化、需要按类型分流的消息传递。高频大数据别用它，每次收发都是一次系统调用加一次数据拷贝，比共享内存慢一两个数量级。

text
  进程 A ──msgsnd(mtype=100)──┐
                              ↓
                        +-----------+
                        | [100][..] |  ← 内核链表，先进先出
                        | [200][..] |
                        | [100][..] |
                        +-----------+
  进程 C ──msgrcv(mtype=100)──┘
  进程 D ──msgrcv(mtype=200)──┘

C 和 D 各取各的，互不干扰。这是管道做不到的。

八、msgget 与 msgsnd/msgrcv #

四个接口：

函数 原型 作用
msgget int msgget(key_t key, int msgflg) 创建或获取队列
msgsnd int msgsnd(int msqid, const void *msgp, size_t msgsz, int msgflg) 发送一条
msgrcv ssize_t msgrcv(int msqid, void *msgp, size_t msgsz, long msgtyp, int msgflg) 接收一条

消息结构体 #

msgp 指向的结构体，第一个成员必须是 long mtype，这是内核强制的约定。后面的正文随便你怎么定义。

c
struct msgbuf {
    long mtype;        /* 必须 > 0 */
    char mtext[1024];  /* 正文，长度自定 */
};

struct task_msg {
    long mtype;
    int  task_id;
    int  payload_len;
    char payload[512];
};

内核只认 mtype 那 8 个字节的位置，正文它完全不管，塞结构体、数组都行。mtype 必须严格大于 0，传 0 或负数，msgsnd 直接返回 -1、errno = EINVAL。

msgget #

msgflg 除了 IPC_CREAT / IPC_EXCL / IPC_NOWAIT，还能带权限位：

c
int msgid = msgget(key, IPC_CREAT | 0666);      /* 发送端：有就打开，没有就建 */
int msgid = msgget(key, 0);                      /* 接收端：只找，不建 */

系统对消息队列的总数、单个队列的字节数、条数都有上限，ipcs -l 里 max queues system wide / max size of message / max bytes in queue 那几行就是。建不出来先查限额。

msgsnd #

参数 说明
msgsz 正文长度，不含 mtype。很多人在这里传 sizeof(struct)，多算了 8 字节，导致每次收发多搬 8 字节垃圾
msgflg 0 阻塞；IPC_NOWAIT 满则立即返回 -1、errno = EAGAIN

正确写法有两种，效果一致：

c
msgsnd(msgid, &msg, strlen(msg.mtext) + 1, 0);          /* 只发有内容的长度，含结尾 '\0' */
msgsnd(msgid, &msg, sizeof(msg.mtext), 0);              /* 发定长，简单但浪费 */

别写 sizeof(msg)——那个含 mtype，多算 8 字节。内核会用 msgsz 决定从 msgp + sizeof(long) 处拷多少字节，多算不会崩，但接收端 msgrcv 的 msgsz 也得跟着一致，否则算错。

队列满的判定：单条消息受 msgmax 限制，队列总字节受 msgmnb 限制（默认常见 16384）。超了就是阻塞或 EAGAIN。

msgrcv #

c
ssize_t msgrcv(int msqid, void *msgp, size_t msgsz, long msgtyp, int msgflg);

msgtyp 是核心参数，决定「挑哪一条」：

msgtyp 语义
0 取队列中第一条消息，不管你什么类型
> 0 取类型等于 msgtyp 的第一条消息，其他类型跳过
< 0 取类型小于等于 abs(msgtyp) 的、类型值最小的那条

msgsz 是接收缓冲区的正文容量，不含 mtype。消息正文比 msgsz 大时：

msgflg 消息太长时
0（默认） 不取，返回 -1，errno = E2BIG，消息留在队列
MSG_NOERROR 截断，只拷 msgsz 字节，返回截断后的长度，消息从队列移除

不加 MSG_NOERROR 就老老实实把 msgsz 给足，否则对方发个大包你就一直 E2BIG。返回值是实际拷到的正文字节数（不含 mtype），失败返回 -1。

msgctl #

cmd 作用
IPC_STAT 属性读到 buf，buf->msg_qnum 就是当前队列里的消息条数
IPC_SET 改 msg_perm.uid/gid/mode、msg_qbytes
IPC_RMID 立刻删除队列，唤醒所有阻塞在 msgrcv 上的进程（它们返回 -1、errno = EIDRM）

IPC_RMID 对队列是立即生效的，不像共享内存要等 nattch 归 0。这个差异记清楚：队列删了，里面没取走的消息全没了。

有个坑值得单独讲：队列里的消息不随发送进程退出而消失。先跑发送端、发几条、退出，再跑接收端，照样能收到。因为消息存在内核里，发送进程死活与它无关。老笔记里把这个当「有点意思的现象」记了一笔，其实是设计如此，不是 bug。

九、消息的类型与优先级 #

mtype 是正整数，取值范围到 LONG_MAX。它同时承担两个职责：分流标签和优先级。

分流：多通道复用一条队列 #

约定 100 是服务端发的，200 是客户端发的，一条队列就变成双向通道：

c
/* 服务端：只发 100，只收 200 */
msgsnd(msgid, &pkt_100, sizeof(pkt_100.mtext), 0);
msgrcv(msgid, &pkt, sizeof(pkt.mtext), 200, 0);

/* 客户端：只发 200，只收 100 */
msgsnd(msgid, &pkt_200, sizeof(pkt_200.mtext), 0);
msgrcv(msgid, &pkt, sizeof(pkt.mtext), 100, 0);

管道的半双工限制在这里没了。一条消息队列天然支持任意多方按类型分流，这也是它在多进程任务分发里还有生命力的原因。

mtype 用进程号也是个常见套路：发送端把自己的 getpid() 填进 mtype，接收端从收到的消息里反查是谁发的。比在正文里塞 PID 更省事。

优先级：用负 msgtyp 实现「高档先出」 #

严格说 System V 消息队列是按类型选，不按优先级排。但利用 msgtyp < 0 的语义可以模拟优先级队列：

c
/* 发送端：优先级数字越小越紧急，用 10 - priority 映射成 mtype */
#define PRIO_HIGH   1
#define PRIO_NORMAL 5
#define PRIO_LOW    9

struct msgbuf msg;
msg.mtype = 10 - priority;     /* 高优先级 → 大 mtype */

/* 接收端：取类型最小的一条 —— 也就是优先级最高的 */
msgrcv(msgid, &msg, sizeof(msg.mtext), -10, 0);

msgtyp = -10 的语义是「类型值 ≤ 10 的所有消息里，取类型值最小的那条」。发送端把高优先级映射成小 mtype，接收端就能先拿高档。这是有意的设计空间，不是 hack。

同类消息的默认顺序 #

同一条队列里，msgtyp = 0 时严格按入队顺序（FIFO）取。指定 msgtyp > 0 时，取的是该类型里最早入队的那条，也符合 FIFO。

也就是说，不同类型之间没有全局顺序保证：后入队的高优先级消息会先被取走。如果你的业务依赖跨类型顺序，就得自己加序号字段做重排。

一个能跑的双向聊天 #

两份代码，同一份头文件与宏，收发类型对调。服务端：

c
/* chat_server.c：只发 100，只收 200 */
#include <stdio.h>
#include <string.h>
#include <sys/ipc.h>
#include <sys/msg.h>

#define KEY_PATH "/tmp"
#define PROJ_ID  'M'
#define TYPE_S2C 100
#define TYPE_C2S 200

struct chat_packet { long mtype; char mtext[1024]; };

int main(void) {
    int msgid = msgget(ftok(KEY_PATH, PROJ_ID), IPC_CREAT | 0666);
    if (msgid < 0) { perror("msgget"); return -1; }
    struct chat_packet pkt;
    pkt.mtype = TYPE_S2C;
    while (1) {
        printf("server> "); fflush(stdout);
        if (!fgets(pkt.mtext, sizeof(pkt.mtext), stdin)) break;
        pkt.mtext[strcspn(pkt.mtext, "\n")] = '\0';
        msgsnd(msgid, &pkt, strlen(pkt.mtext) + 1, 0);
        if (strcmp(pkt.mtext, "exit") == 0) break;
        if (msgrcv(msgid, &pkt, sizeof(pkt.mtext), TYPE_C2S, IPC_NOWAIT) > 0)
            printf("\n[client says] %s\n", pkt.mtext);
        pkt.mtype = TYPE_S2C;
    }
    msgctl(msgid, IPC_RMID, NULL);
    return 0;
}

客户端只改三处：msgget(..., 0) 只找不建、pkt.mtype = TYPE_C2S、msgrcv 取 TYPE_S2C 而 msgsnd 发 TYPE_C2S。循环体照抄。

这个版本用 IPC_NOWAIT 做「顺手看一眼」，不阻塞，所以两边各说各的也不会卡死。要做严格的请求-应答，就把 IPC_NOWAIT 去掉换成 0，代价是必须一来一回。

十、信号灯集：不是信号量 #

先把名字掰清楚，这是最容易糊的地方：

名词 英文 是什么
信号 Signal kill 发的异步软中断，归《管道与信号》篇
信号量 Semaphore 抽象的同步原语，一个计数器
信号灯集 Semaphore Set / Semaphore Array System V 的具体实现，一个数组
POSIX 信号量 sem_t / sem_open 另一套实现，第十五章对比

本篇讲的是第三个。它有两个特殊之处：

  1. 它是一个集合。一次 semget 拿到的不是「一个信号量」，而是「一组信号量」，数量由 nsems 指定，用下标 sem_num 区分。你要一个就传 1，要十个就传 10。
  2. 操作是原子的、批量的。semop 一次可以提交多个 sembuf，内核要么全做完，要么一个都不做。第十二章展开。

四个接口：

函数 原型 作用
semget int semget(key_t key, int nsems, int semflg) 创建或获取信号灯集
semop int semop(int semid, struct sembuf *sops, size_t nsops) P/V 操作，可批量
semctl int semctl(int semid, int semnum, int cmd, ...) 初始化、查询、删除
semtimedop int semtimedop(int semid, struct sembuf *sops, size_t nsops, const struct timespec *timeout) 带超时的 semop

三种经典用途 #

  • 互斥：一个初值为 1 的灯，P 进 V 出，包住临界区，等价于互斥锁。
  • 同步：一个初值为 0 的灯，A 做完事 V 一下，B 在 P 上等着，实现「B 等 A」的先后序。
  • 计数：一个初值为 N 的灯，N 个资源，P 拿走一个，V 归还一个，天然就是资源池。

初始值决定了语义，semctl(SETVAL) 那一下是整个程序的语义锚点，写错了后面全错。semget 里的 nsems 只在创建时生效，对已存在的集合传的 nsems 会被忽略——想扩数组，只能删了重建。这和 shmget 的 size 行为一致，都是一次性定终身。

十一、semget 与 semop #

semget #

c
#include <sys/types.h>
#include <sys/ipc.h>
#include <sys/sem.h>
int semget(key_t key, int nsems, int semflg);

int semid = semget(key, 1, IPC_CREAT | 0666);              /* 建一个单灯集 */
int semid = semget(key, 1, IPC_CREAT | IPC_EXCL | 0666);   /* 只准我建 */
int semid = semget(key, 0, 0);                             /* 打开已有的，nsems 传 0 */

打开已有集合时 nsems 传 0 是惯用写法，反正会被忽略。

union semun 得自己定义 #

这是个 glibc 的历史遗留：semctl 的第四个参数是变参 ...，标准要求你自己声明 union semun，头文件里不提供。

c
union semun {
    int              val;    /* SETVAL / GETVAL */
    struct semid_ds *buf;    /* IPC_STAT / IPC_SET */
    unsigned short  *array;  /* SETALL / GETALL */
};

不定义就编译报错，或者在某些环境下静默出错。每个用到 semctl 的 .c 文件都得有这一段。

semctl 的 cmd 表 #

cmd 语义 第四参数
IPC_STAT 读集合属性 arg.buf
IPC_SET 改 sem_perm.uid/gid/mode arg.buf
IPC_RMID 删除整个集合 不用传
GETVAL 读 semnum 号灯的当前值 无
SETVAL 设 semnum 号灯的值为 arg.val arg.val
GETALL 读所有灯的值到 arg.array arg.array
SETALL 用 arg.array 设所有灯的值 arg.array
GETPID 返回最后一个操作该灯的进程 PID 无
GETNCNT 返回等待该灯值增加的进程数 无
GETZCNT 返回等待该灯值变成 0 的进程数 无

注意 IPC_RMID 删的是整个集合，不是编号 semnum 那一个灯。semctl(semid, 0, IPC_RMID) 里那个 0 是个占位，删的仍是全集合。

c
union semun arg;
arg.val = 1;
if (semctl(semid, 0, SETVAL, arg) < 0) { perror("SETVAL"); return -1; }

/* GETALL 是排查问题的好工具，一次性把整组灯的值打出来 */
unsigned short vals[8];
arg.array = vals;
semctl(semid, 0, GETALL, arg);
for (int i = 0; i < 8; i++) printf("sem[%d] = %u\n", i, vals[i]);

struct sembuf #

semop 的操作单元就这个结构体：

c
struct sembuf {
    unsigned short sem_num;   /* 灯在集合里的下标，从 0 开始 */
    short          sem_op;    /* 操作值，见下表 */
    short          sem_flg;   /* 标志：SEM_UNDO / IPC_NOWAIT */
};
字段 取值 语义
sem_num 0 ~ nsems-1 目标灯下标
sem_op > 0 V 操作：值加 sem_op，唤醒等待者
sem_op < 0 P 操作：值减 abs(sem_op)，不足则阻塞（或 EAGAIN）
sem_op = 0 等待值变成 0，变不成就阻塞（或 EAGAIN）
sem_flg SEM_UNDO 记录本次操作，进程退出时内核自动反向撤销
sem_flg IPC_NOWAIT 拿不到立即返回 -1、errno = EAGAIN，不睡眠

sem_op 是 short，单次加减幅度有限，靠 nsops 批量做大事。

P 操作与 V 操作 #

最朴素的写法，一个灯一把锁：

c
union semun { int val; };

static int sem_lock(int semid) {
    struct sembuf op = { 0, -1, SEM_UNDO };   /* sem_num, sem_op, sem_flg */
    return semop(semid, &op, 1);
}

static int sem_unlock(int semid) {
    struct sembuf op = { 0, 1, SEM_UNDO };
    return semop(semid, &op, 1);
}

/* 包住临界区 */
sem_lock(semid);
memcpy(shm_ptr->buf, src, len);    /* 只有一个人能进来 */
sem_unlock(semid);

SEM_UNDO 的作用 #

这是 System V 信号灯集相对 POSIX 信号量最有价值的一个特性。

场景：进程 A sem_lock 成功，值从 1 变 0，然后 A 被 kill -9。如果没有任何补救，这个灯永远停在 0，所有等它的进程全部永久阻塞。这就是死锁，而且是最难查的那种——代码看起来毫无问题。

SEM_UNDO 干的事：内核为每个进程维护一张「semaphore undo 表」，记录该进程在所有集合上的净操作量。进程终止（正常退出、崩溃、被 kill 都算）时，内核对表里每一项做反向操作，把这位进程欠的债还回去。

c
op.sem_op  = -1;
op.sem_flg = SEM_UNDO;    /* A 崩了，内核自动 +1，灯回到 1，别人能继续 */

要点：

  • 它是按进程记账的，fork 出来的子进程不继承父进程的 undo 记录。
  • 撤销发生在进程真正退出时，不是 semop 返回时。
  • 只对 sem_op != 0 的操作有意义。sem_op = 0 是纯等待，不改值，没有可撤销的东西。
  • 配 IPC_NOWAIT 一起用时，失败返回 EAGAIN，此时不记账，也不影响。

结论很直白：只要用 System V 信号灯做锁，sem_flg 就带上 SEM_UNDO。想不出不带它的理由。

十二、信号灯集的原子操作 #

semop 的 nsops 参数是这个接口的灵魂。传 1 就是普通 PV，传大于 1 就是批量原子操作。

原子性的准确含义：内核在检查全部 nsops 个操作都可执行之后，才一起执行；只要有一个条件不满足（比如某个灯减到负数），一个都不执行，进程阻塞或返回 EAGAIN。不存在「做了一半」的中间态。

用法一：一次拿多把锁，避免死锁 #

c
struct sembuf ops[2];
ops[0] = (struct sembuf){ 0, -1, SEM_UNDO };
ops[1] = (struct sembuf){ 1, -1, SEM_UNDO };
if (semop(semid, ops, 2) < 0) { perror("semop"); return -1; }

/* 释放时反向来一遍 */
ops[0].sem_op = 1;
ops[1].sem_op = 1;
semop(semid, ops, 2);

两个灯同时申请，要么都拿到，要么一个都不拿。这直接消掉了「A 拿了 0 号等 1 号、B 拿了 1 号等 0 号」的循环等待型死锁。分开写两次 semop 就有这个窗口。

用法二：检查 + 占位，一步完成 #

「等待值为 0，通过后立刻加 1」如果分两次 semop 调用，中间那段时间别的进程插进来，检查就白做了。合成一次批量操作才是原子的。核心就两个 sembuf：

c
ops[0] = (struct sembuf){ 0, 0, IPC_NOWAIT };   /* 等值变 0，占用中则立即 EAGAIN */
ops[1] = (struct sembuf){ 0, 1, SEM_UNDO };     /* 占坑，值 +1 */
semop(semid, ops, 2);

IPC_NOWAIT 只加在第一个操作上，第二个是必定能成功的加操作，不需要。SEM_UNDO 也只加在第二个上——第一个不改值，无可撤销。

原理：进程活着，灯值恒为 1；进程一死，SEM_UNDO 把 +1 撤回去，灯值归 0，下一个实例就能进。不需要 pidfile，不需要处理陈旧锁文件。

用法三：等 0 做「排空」 #

消费者想等生产者把缓冲写完再收尾，就等某个标志灯变 0：

c
struct sembuf op = {0, 0, 0};      /* sem_num=0, sem_op=0 等待, flg=0 阻塞 */
semop(semid, &op, 1);              /* 一直等到 sem[0] == 0 */

sem_op = 0 加 flg = 0 是阻塞等待，不消耗值，纯观察。这个语义在 POSIX 信号量里没有对应接口，是 System V 独有的。

单实例保护的完整代码 #

c
#include <stdio.h>
#include <errno.h>
#include <unistd.h>
#include <sys/ipc.h>
#include <sys/sem.h>

union semun { int val; };

int main(void) {
    int semid = semget(ftok("/tmp", 'O'), 1, IPC_CREAT | 0666);
    if (semid < 0) { perror("semget"); return -1; }

    /* 只在新建时初始化，避免把正在运行实例的锁重置掉 */
    struct semid_ds ds;
    union semun arg;
    arg.buf = &ds;
    semctl(semid, 0, IPC_STAT, arg);
    if (ds.sem_otime == 0) {              /* 从未被操作过 → 刚建出来 */
        arg.val = 0;
        semctl(semid, 0, SETVAL, arg);
    }

    struct sembuf ops[2];
    ops[0] = (struct sembuf){ 0, 0, IPC_NOWAIT };
    ops[1] = (struct sembuf){ 0, 1, SEM_UNDO };

    if (semop(semid, ops, 2) < 0) {
        if (errno == EAGAIN) { fprintf(stderr, "another instance is running, abort\n"); return -1; }
        perror("semop");
        return -1;
    }

    printf("I am the only instance, pid=%d\n", getpid());
    sleep(3);
    /* 不删集合：靠 SEM_UNDO 自动归零即可 */
    printf("done, kernel will undo the +1\n");
    return 0;
}

sem_otime == 0 的判断是必须的。如果不判，直接在每次启动时 SETVAL 0，就会出现「实例 A 正在跑（值 1），实例 B 启动时把值重置成 0，然后 B 也拿到锁」的破窗。sem_otime 是「最后一次 semop 成功的时间」，新建的集合是 0，被用过就非 0，正好可以当「是否已初始化」的标志。这是 System V 信号灯初始化竞态的经典解法，那一段别省。

十三、三件套的配合使用 #

三件套单独用都不够顺手，配起来才是完整方案。最经典的三种配法：

配法一：共享内存 + 信号灯集（数据面 + 控制面） #

text
  +-----------+                          +-----------+
  |  进程 A   |                          |  进程 B   |
  +-----+-----+                          +-----+-----+
        |  sem[0] 互斥 / sem[1] 数据就绪        |
        +----------------+---------------------+
                         |
                  +------+------+
                  |  共享内存段  |   ← 大块数据
                  +-------------+
  • sem[0] 初值 1：互斥锁，包住写操作。
  • sem[1] 初值 0：同步灯，A 写完 V 一下，B 在 P 上等。
c
/* A 的流程 */
sem_lock(semid, 0);                 /* 独占共享内存 */
memcpy(shm->buf, data, len);
shm->len = len;
sem_unlock(semid, 0);
sem_v(semid, 1);                    /* 通知 B：数据好了 */

/* B 的流程 */
sem_p(semid, 1);                    /* 等数据 */
sem_lock(semid, 0);
memcpy(out, shm->buf, shm->len);
sem_unlock(semid, 0);

单生产者单消费者其实可以省掉互斥锁，只用两个同步灯（一个「空位可用」、一个「数据可用」），这就是环形缓冲区的标准做法，第十四章的实例走这条线。

配法二：共享内存 + 消息队列（数据走 shm，通知走队列） #

text
  生产者 --msgsnd(mtype=1, {slot=3})--> 队列 --msgrcv--> 消费者去 shm 的 slot 3 拿数据

消息队列负责传控制信息（「第 3 号槽位写好了」），共享内存负责传数据本体。好处是队列里只跑十几个字节的小消息，不会撑爆 msgmnb，也不会因为拷贝大数据变慢；坏处是多了一次队列操作的开销，而且「队列满了」和「槽位满了」是两套容量，得同时管。适合数据包大、频率中等的场景。

配法三：三者全上（任务池） #

  • 共享内存：任务数据区 + 环形缓冲索引。
  • 信号灯集：empty（空槽数）、full（满槽数）、mutex（互斥）。
  • 消息队列：worker 注册与心跳。

这就是一个标准的多进程任务分发池。生产者往环里塞任务，多个 worker 抢 full 灯，谁抢到谁处理。消息队列那条线只走低频的管理消息。

什么时候不该配 #

数据量小的时候别上共享内存。传一个 int 用消息队列一条消息就够，搞共享内存加两个信号灯，代码量翻三倍，性能收益为零——一次 semop 的系统调用开销比一次 msgsnd 小不了多少。

反过来，几十 KB 以上的数据别用消息队列。msgmnb 默认常见 16384 字节，一发就 EAGAIN，调大限额又影响全系统。

判断标准就一条：数据量决定用不用 shm，同步需求决定用不用 sem，结构化消息才用 msg。

十四、一个完整的生产者-消费者实例 #

目标：一个生产者、一个消费者，通过共享内存环形缓冲区传数据，用信号灯集同步，跑完自动清理。不用互斥锁——单生产者单消费者靠两个计数灯就够。

设计 #

text
  共享内存布局：
  +--------------+--------------+-------------------+
  | head (int)   | tail (int)   | slots[N][SIZE]    |
  | 生产者写下标  | 消费者读下标  | N 个定长槽         |
  +--------------+--------------+-------------------+

  信号灯集（2 个灯）：
  sem[0] empty = N    可写槽数
  sem[1] full  = 0    可读槽数

生产者的循环：P(empty) → 写 slots[head] → head = (head+1)%N → V(full)。 消费者的循环：P(full) → 读 slots[tail] → tail = (tail+1)%N → V(empty)。

两个下标各自只被一方写，单生产者单消费者天然无冲突，所以不需要 mutex 灯。这就是环形缓冲区的经典结论。

公共头文件 #

c
/* pc_common.h：三份程序共用 */
#ifndef PC_COMMON_H
#define PC_COMMON_H

#define KEY_PATH   "/tmp"
#define SHM_PROJ   'S'
#define SEM_PROJ   'Q'
#define SLOT_NUM   8                      /* 环里 8 个槽 */
#define SLOT_SIZE  1024                   /* 每槽 1KB */
#define SHM_SIZE   (sizeof(struct shm_ring))
#define SEM_EMPTY  0                      /* 可写槽数 */
#define SEM_FULL   1                      /* 可读槽数 */

struct shm_ring {
    volatile int head;
    volatile int tail;
    int          count;                   /* 累计投递条数，仅用于校验 */
    char         slots[SLOT_NUM][SLOT_SIZE];
};

/* P/V 包装，三份程序共用 */
static int sem_p(int semid, int idx) {
    struct sembuf op = { (unsigned short)idx, -1, SEM_UNDO };
    return semop(semid, &op, 1);
}

static int sem_v(int semid, int idx) {
    struct sembuf op = { (unsigned short)idx, 1, SEM_UNDO };
    return semop(semid, &op, 1);
}

#endif

volatile 在这里只是提醒编译器别把 head / tail 缓存进寄存器，真正的顺序保证还得靠 semop 的系统调用边界——系统调用是编译器屏障，也是大部分情况下的硬件屏障。

资源初始化（只跑一次） #

c
/* pc_init.c */
#include <stdio.h>
#include <sys/ipc.h>
#include <sys/shm.h>
#include <sys/sem.h>
#include "pc_common.h"

union semun { int val; };

int main(void) {
    int shmid = shmget(ftok(KEY_PATH, SHM_PROJ), SHM_SIZE, IPC_CREAT | 0666);
    int semid = semget(ftok(KEY_PATH, SEM_PROJ), 2, IPC_CREAT | 0666);
    if (shmid < 0 || semid < 0) { perror("create"); return -1; }

    union semun arg;
    arg.val = SLOT_NUM;
    if (semctl(semid, SEM_EMPTY, SETVAL, arg) < 0) { perror("SETVAL empty"); return -1; }
    arg.val = 0;
    if (semctl(semid, SEM_FULL, SETVAL, arg) < 0) { perror("SETVAL full"); return -1; }

    struct shm_ring *r = (struct shm_ring *)shmat(shmid, NULL, 0);
    if (r == (void *)-1) { perror("shmat"); return -1; }
    r->head = 0; r->tail = 0; r->count = 0;
    shmdt(r);

    printf("ready: shmid=%d semid=%d\n", shmid, semid);
    return 0;
}

生产者 #

c
/* pc_producer.c：头部 include 与 pc_init 相同 */
int main(void) {
    int shmid = shmget(ftok(KEY_PATH, SHM_PROJ), SHM_SIZE, 0);
    int semid = semget(ftok(KEY_PATH, SEM_PROJ), 0, 0);
    if (shmid < 0 || semid < 0) { perror("attach (run pc_init first)"); return -1; }
    struct shm_ring *r = (struct shm_ring *)shmat(shmid, NULL, 0);
    if (r == (void *)-1) { perror("shmat"); return -1; }

    for (int i = 0; i < 20; i++) {
        if (sem_p(semid, SEM_EMPTY) < 0) break;        /* 先等空位 */
        snprintf(r->slots[r->head], SLOT_SIZE, "task-%03d payload", i);
        printf("[producer] write slot %d: %s\n", r->head, r->slots[r->head]);
        r->head = (r->head + 1) % SLOT_NUM;
        r->count++;
        if (sem_v(semid, SEM_FULL) < 0) break;         /* 写完再通知 */
        usleep(100000);
    }

    shmdt(r);
    printf("[producer] done\n");
    return 0;
}

消费者 #

c
/* pc_consumer.c：开头与 producer 完全一致，只是循环体对调 */
int main(void) {
    int shmid = shmget(ftok(KEY_PATH, SHM_PROJ), SHM_SIZE, 0);
    int semid = semget(ftok(KEY_PATH, SEM_PROJ), 0, 0);
    if (shmid < 0 || semid < 0) { perror("attach"); return -1; }
    struct shm_ring *r = (struct shm_ring *)shmat(shmid, NULL, 0);
    if (r == (void *)-1) { perror("shmat"); return -1; }

    for (int i = 0; i < 20; i++) {
        if (sem_p(semid, SEM_FULL) < 0) break;         /* 先等数据 */
        printf("[consumer] read slot %d: %s\n", r->tail, r->slots[r->tail]);
        r->tail = (r->tail + 1) % SLOT_NUM;
        if (sem_v(semid, SEM_EMPTY) < 0) break;        /* 读完还空位 */
    }

    shmdt(r);
    printf("[consumer] done, count=%d\n", r->count);
    return 0;
}

编译、运行、清理 #

bash
gcc -Wall -O2 -o pc_init pc_init.c
gcc -Wall -O2 -o pc_producer pc_producer.c
gcc -Wall -O2 -o pc_consumer pc_consumer.c

./pc_init            # 备资源
./pc_consumer &      # 消费者先起，会阻塞在 P(full) 上
./pc_producer        # 生产者开写
ipcs -m; ipcs -s     # 看 nattch 与信号灯值
ipcrm -m <shmid>; ipcrm -s <semid>

这段代码的四个关键点 #

  1. P(empty) 在写之前，V(full) 在写之后。顺序反了就是「先通知后写数据」，消费者读到的是旧内容。反过来消费者是 P(full) 在前、V(empty) 在后。灯的操作位置就是数据可见性的边界。
  2. SEM_UNDO 挂在所有 sem_op != 0 的操作上。生产者写到一半被 kill，P(empty) 抢走的那个槽会被内核还回去，消费者不会卡死。
  3. head / tail 各自只有一个写者。这是不需要 mutex 灯的前提。加第二个生产者就必须补一把 mutex，否则 r->head = (r->head + 1) % N 这一句的读-改-写会丢更新。
  4. count 用 int 不做原子保证，只当调试信息看。真要做精确计数，得放进临界区。

跑完记得 ipcrm。下一章讲为什么这一步不能省。

十五、System V IPC 与 POSIX IPC 的对比 #

Linux 上有两套独立实现的 IPC，接口风格完全不同。System V 这套是老资格，POSIX 那套是后来的规范化版本。

POSIX IPC 三个对应物 #

System V POSIX 头文件 命名方式
shmget / shmat / shmdt shm_open / mmap / munmap <sys/mman.h> 名字形如 /myshm
msgget / msgsnd / msgrcv mq_open / mq_send / mq_receive <mqueue.h> 名字形如 /myq
semget / semop / semctl sem_open / sem_wait / sem_post <semaphore.h> 名字形如 /mysem

对照表 #

维度 System V IPC POSIX IPC

引用方式 整数 ID 文件描述符 / 指针

现状 维护模式，新代码少用 新项目首选

同一个「信号量」的两种写法 #

c
/* System V 风格：创建 + 初始化 + P/V 三步分离，还得自己定义 union semun */
int semid = semget(key, 1, IPC_CREAT | 0666);
union semun { int val; } arg;
arg.val = 1;
semctl(semid, 0, SETVAL, arg);

struct sembuf op = {0, -1, SEM_UNDO};
semop(semid, &op, 1);           /* P */
op.sem_op = 1;
semop(semid, &op, 1);           /* V */

/* POSIX 风格：创建和初始化一次完成，P/V 就是两个函数 */
sem_t *s = sem_open("/mysem", O_CREAT, 0666, 1);
if (s == SEM_FAILED) { perror("sem_open"); return -1; }
sem_wait(s);                    /* P */
sem_post(s);                    /* V */
sem_close(s);
sem_unlink("/mysem");

POSIX 版本明显短，而且不会踩「初始值被重复设置」的坑。

共享内存的写法差异 #

c
/* System V 一步到位 */
int shmid = shmget(key, 4096, IPC_CREAT | 0666);
char *p = shmat(shmid, NULL, 0);

/* POSIX 要走三步，但换来的是可以直接当文件用 */
int fd = shm_open("/myshm", O_CREAT | O_RDWR, 0666);
ftruncate(fd, 4096);                          /* 必须显式定大小 */
char *p = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);

ftruncate 那一步不能省。忘了它，mmap 出来访问就是 SIGBUS。

怎么选 #

  • 新项目：用 POSIX。接口短、和文件系统打通、工具链友好。
  • 维护老系统：System V 动不了，继续用。
  • 需要 SEM_UNDO：只有 System V 有。做单实例保护、要求进程崩溃后自动解锁的场景，System V 信号灯集仍然是省事的那个。
  • 需要「等待值为 0」语义：只有 System V 的 sem_op = 0。
  • 跨机器：两套都不行，用 socket。

一句话：System V 是「能用但要小心」，POSIX 是「默认选择」。

十六、资源泄漏与清理 #

System V IPC 最烦人的特性在这里：它不随进程退出而释放。程序正常退出、崩溃、被 kill -9，内核里的对象都还在。

泄漏的四种典型形态 #

现象 根因 排查
shmget 报 EEXIST 上次的段没删，IPC_CREAT | IPC_EXCL 撞上了 ipcs -m 找同 key 的段
ipcs -m 里 nattch > 0 但没进程 进程崩了没来得及 shmdt，或段被 IPC_RMID 后仍有挂载 ipcs -m -p 看最后操作者 PID
消息队列 used-bytes 一直涨 消费者挂了，生产者在灌 ipcs -q
信号灯值恒为 0，全员阻塞 持锁进程非正常退出且没带 SEM_UNDO ipcs -s 后 semctl GETALL

清理策略 #

策略一：让最后一个使用者删。

共享内存的 IPC_RMID 可以放心在任意进程调，因为它只打标记，等 nattch 归 0 才真回收。所以约定「最后一个退出的进程负责删」是安全的：

c
shmdt(p);
shmctl(shmid, IPC_RMID, NULL);    /* 别人还挂着也没关系 */

注意上面这两行的顺序：先 shmdt 再 IPC_RMID。反过来也行（标记完再断开），但 nattch 要等你自己也断开才减 1，容易误判。

策略二：atexit + 信号处理，覆盖异常退出路径。

c
static int g_shmid = -1;
static int g_semid = -1;

static void cleanup(void) {
    if (g_shmid >= 0) shmctl(g_shmid, IPC_RMID, NULL);
    if (g_semid >= 0) semctl(g_semid, 0, IPC_RMID);
}

static void on_signal(int sig) {
    cleanup();
    _exit(128 + sig);          /* 信号处理里只用 async-signal-safe 调用 */
}

int main(void) {
    atexit(cleanup);
    signal(SIGINT,  on_signal);
    signal(SIGTERM, on_signal);
    /* ... */
}

这段只挡得住 SIGINT / SIGTERM，挡不住 SIGKILL。SIGKILL 无法捕获，所以任何「靠信号处理清理」的方案都有洞。真正的兜底只能是策略三。

策略三：启动时先扫一遍，清理陈旧的。 给对象加一个「属主 PID」字段，启动时检查该 PID 是否还活着：

c
static int pid_alive(pid_t pid) {
    if (pid <= 0) return 0;
    return (kill(pid, 0) == 0) || (errno == EPERM);
}

kill(pid, 0) 不发信号，只做权限检查，进程存在返回 0，不存在返回 -1 且 errno = ESRCH。这是标准的探活手段。

策略四：别用固定 key。 IPC_PRIVATE 每次创建新对象，天然不撞，但代价是只能靠 fork 继承。适合短命的父子通信。

一条可复用的清理脚本 #

bash
#!/bin/bash
me=$(id -un)   # 只清理自己名下、且 nattch 为 0 的共享内存段
ipcs -m | awk -v me="$me" 'NR>3 && $3==me && $6==0 {print $2}' | while read -r id; do ipcrm -m "$id"; done
ipcs -q | awk -v me="$me" 'NR>3 && $3==me {print $2}' | while read -r id; do ipcrm -q "$id"; done
ipcs -s | awk -v me="$me" 'NR>3 && $3==me {print $2}' | while read -r id; do ipcrm -s "$id"; done

NR>3 是跳过表头。不同发行版的表头行数不一样，跑之前先 ipcs -m 看一眼实际输出，确认行号。

容器里的注意点 #

容器重启后 /proc/sysvipc 是跟着内核命名空间走的。默认情况下 IPC 命名空间和宿主机共享，容器里的残留会污染宿主机。要隔离，启动时加 --ipc=private（Docker）或给 Pod 配独立的 IPC namespace。这也解释了一个常见困惑：「容器里 ipcs 看到一堆陌生 ID」——那些是别的容器留下的，因为共享了 IPC namespace。

十七、易错点速查 #

按踩坑频率排。每条都是真实会碰到的。

# 易错点 正确做法
1 shmat 失败判断写成 == NULL 判 == (void *)-1
2 msgsnd 的 msgsz 传 sizeof(struct) 传正文长度，不含 mtype 的 8 字节
3 msgrcv 忘了 MSG_NOERROR，遇到大包永远 E2BIG 给足 msgsz，或加 MSG_NOERROR 接受截断
4 msgsnd 的 mtype 传 0 必须 > 0，否则 EINVAL
5 sem_flg 不带 SEM_UNDO 做锁就必须带，否则崩溃即死锁
6 每次启动都 SETVAL 先查 sem_otime == 0 再初始化
7 shmdt 传 shmid 传 shmat 返回的地址
8 以为 shmctl(IPC_RMID) 立刻释放内存 它只打标记，nattch 归 0 才回收
9 ftok 的路径文件不存在 先 touch，或用已存在的目录如 /tmp
10 proj_id 以为能用满 32 位 只有低 8 位参与运算
11 semctl 不定义 union semun 每个用到的 .c 里都得写一段
12 semctl(semid, 0, IPC_RMID) 以为删的是 0 号灯 删的是整个集合
13 共享内存直接读写不加同步 必须配信号量或原子操作，见第六章
14 队列里的消息以为随发送进程退出消失 不会，消息在内核里，得 IPC_RMID
15 多个生产者共用环形缓冲区但不加锁 加 mutex 灯，head++ 是读-改-写
16 程序崩了不清理，反复跑堆一堆残留 ipcs 定期看，脚本清，或用 IPC_PRIVATE
17 用信号做共享内存同步，pause() 前丢了信号 用 sigsuspend 原子解阻塞；更好的是改用信号量
18 以为 IPC_EXCL 可以单独用 必须和 IPC_CREAT 同用
19 msgrcv 的 msgsz 小于实际消息又不加 MSG_NOERROR 同上第 3 条
20 屏障/可见性只靠 volatile volatile 不是内存屏障，跨线程要 __atomic 或系统调用边界

再补三条不和表格混的：

semop 的 nsops 传 0：合法但不做事，返回 0。有人用它当空转，没意义。

ipcrm 用 key 删的时候，key 是十六进制，前面要带 0x，跟 ipcs 输出里 key 列一致。

ipcs 的 nattch 列在某些内核版本里统计包含已 IPC_RMID 但未释放的挂载，所以看到「段已删但 nattch 不为 0」不要慌，等挂载进程退出就好。
