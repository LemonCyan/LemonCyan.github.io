一、守护进程是什么 #

先拿一次 QQ 聊天把几个容易混的概念对一下。

概念 QQ 里的对应 技术含义
控制终端 打开 QQ 并登录 进程与某个 tty 设备的绑定关系
进程 发出的每一条消息 独立调度、独占地址空间的执行单元
作业 聊天里围绕的一个话题 shell 的 job control 单位，一个作业一般就是一个进程组
会话 从打开聊天到关掉 一个或多个进程组的集合，最多绑一个控制终端

类比到这里就够了。守护进程（daemon）的定义只有三条：跑在后台、没有控制终端、不向终端输出。它的生命周期由系统决定——开机起来，关机停掉，中间不依赖任何一次登录。

sshd、crond、systemd-journald、php-fpm 都是这个模型。你在终端里敲的 ls 不是。

维度 普通前台进程 守护进程
启动者 用户的 shell init / systemd，或 shell 但已脱离
控制终端 有，形如 /dev/pts/3 无
父进程 启动它的 shell PID 1，或最近的 subreaper
会话地位 属于某次登录的会话 自己是会话首进程
标准流 指向 tty /dev/null 或 journal
生命周期 终端关掉就结束 跨终端、跨登录
收到 SIGHUP 默认终止 忽略，或用来重载配置

这张表是本篇的提纲。下面每一章都在填其中一行的细节。

二、为什么需要脱离终端 #

在终端里敲一条命令，这个进程会占住终端直到结束。期间你没法在同一个终端里输入别的东西。更麻烦的是终端本身会消失：SSH 断线、窗口关掉、tmux 挂掉，内核就会给这个会话里的进程发 SIGHUP。程序没接管这个信号，就被杀掉了。

所以「后台运行」包含两件独立的事，很多人只做了第一件：

  1. 让进程让出前台终端，你还能继续敲命令。
  2. 让进程不再受终端消失的影响。

& 只做了第 1 件。nohup 只做了第 2 件。setsid 做的是第 2 件的更彻底版本。三个都不是完整答案。

手段 让出前台 挡 SIGHUP 脱离控制终端 副作用
cmd & 是 否 否 终端一关就死
nohup cmd 否 是 否 生成 nohup.out
nohup cmd & 是 是 否 仍是原会话成员，ps 里还挂着 pts
disown 是 是 否 只对当前 shell 生效，登录退出后失效
setsid cmd 是 是 是 输出仍写到原终端
tmux / screen 是 是 是 多一层进程，靠复用会话兜底
守护进程 是 是 是 需要自己接管日志、pid、重载

nohup 的重定向行为有个细节常被记错：它只在标准输出指向终端时才把它改到 nohup.out。你事先 > app.log 2>&1 了，nohup 不会另建文件。

不想留 nohup.out，就自己指走：

bash
nohup ./worker >/dev/null 2>&1 &

setsid 的问题在另一头：它换了会话，但标准流还在原终端上。终端关掉之后再往 fd 1 写，会拿到 EIO。这个坑第八章会处理。

三、终端、控制终端与会话 #

终端在 Linux 上是一个字符设备文件。真实的串口是 /dev/ttyS0 这种，伪终端是 /dev/pts/N。SSH 登录、xterm、tmux 里的每一个窗口，背后都是一个 pts。

/dev/tty 是个特殊节点，它永远指向当前进程的控制终端。所以判断「我有没有控制终端」，读 /dev/tty 就够了：没有控制终端的进程去 open("/dev/tty")，会返回 ENXIO。

bash
$ tty
/dev/pts/3
$ ps -o pid,ppid,pgid,sid,tty,cmd -p $$
  PID  PPID  PGID   SID TT       CMD
 8812  8810  8812  8812 pts/3    -bash

五个字段放在一起看，就是进程的层级身份：

  • PID 8812，这个 shell 自己。
  • PPID 8810，是 sshd 派生出来的登录 shell 的父进程。
  • PGID 8812，进程组 ID，等于自己的 PID，说明它是组长。
  • SID 8812，会话 ID，也等于自己的 PID，说明它还是会话首进程。
  • TT 是 pts/3，它绑定了这个控制终端。

一个会话最多绑一个控制终端，一个控制终端也只属于一个会话。这个一对一关系是 setsid 能起作用的前提。

ps -t pts/3 可以按终端筛出所有相关进程：

bash
$ ps -t pts/3
  PID TTY          TIME CMD
 8812 pts/3    00:00:00 bash
 8901 pts/3    00:00:00 vim

控制终端的作用有两个。一是把键盘中断送到前台进程组：你按 Ctrl-C，内核发给的是「当前前台进程组」，不是某个 PID。二是终端消失时，内核给会话首进程发 SIGHUP，再由它扩散。

守护进程要做的，就是把这两个能力都丢掉。

四、进程组与会话的关系 #

层级是三层，从下往上：

text
会话 session (SID)
 ├── 进程组 pgrp (PGID)  ← 组长进程的 PID 就是 PGID
 │    ├── 进程 PID
 │    └── 进程 PID
 └── 进程组 pgrp (PGID)
      └── 进程 PID

进程组是为了批量发信号存在的。kill -TERM -8812 里的负号表示「发给 PGID 为 8812 的整组」。没有这个机制，shell 想杀一条管道里的三个进程，就得逐个查 PID。

组长进程创建进程组，但组的存活期不由它决定。只要组里还剩一个进程，组就在。组长退出后，这个 PGID 依然在，只是不再有进程能以「组长」的身份被指认。

会话是进程组的集合，起点是一次登录：你 ssh 上来，登录程序调用 setsid() 建会话，bash 在这个会话里跑，你敲的每条命令在它自己的进程组里跑。

操作 接口 作用
取自己的进程组 getpgrp() 返回 PGID
取指定进程的进程组 getpgid(pid) getpgid(0) 查自己
加入/新建进程组 setpgid(pid, pgid) pgid == pid 时新建组
新建会话 setsid() 同时成为组长和会话首进程
取会话 ID getsid(pid) getsid(0) 查自己

shell 的前后台切换建立在这套东西上。fg 把某个进程组提到前台，本质是 tcsetpgrp(控制终端fd, pgid)。后台进程组如果去读终端，内核发 SIGTTIN 把它停住；去写终端则发 SIGTTOU，前提是终端设了 TOSTOP。

这也解释了一个现象：守护进程如果还留着一个终端 fd，被后台读写就会莫名收到 SIGTTIN 停住。ps 里看到状态是 T，不占 CPU 也不干活。第八章的重定向就是在断这个根。

五、创建守护进程的标准步骤 #

七步，顺序不能换。表里第 5、6 步的位置尤其关键。

步 动作 接口 为什么必须在这一步
1 第一次 fork，父进程退出 fork() 父进程退出后子进程变孤儿，被 PID 1 收养
2 子进程建新会话 setsid() 调用者不能是组长，第 1 步刚好保证了这点
3 第二次 fork，第一个子进程退出 fork() 让最终进程不是会话首进程，永远拿不到控制终端
4 改工作目录到根 chdir("/") 避免占用一个会被卸载的挂载点
5 重设文件权限掩码 umask(0) 不继承父进程的 umask
6 标准流重定向到 /dev/null dup2() 断掉与终端的最后一条通路
7 关闭多余 fd、装信号处理、写 pid 文件 close()/sigaction() 收尾

一个能跑的骨架：

c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <signal.h>
#include <sys/stat.h>
#include <sys/resource.h>
#include <syslog.h>
#include <string.h>

static volatile sig_atomic_t g_stop = 0;
static volatile sig_atomic_t g_reload = 0;

static void on_term(int sig) { (void)sig; g_stop = 1; }
static void on_hup(int sig)  { (void)sig; g_reload = 1; }

static void close_all_fds(void)
{
    struct rlimit rl;
    long maxfd;

    if (getrlimit(RLIMIT_NOFILE, &rl) == 0 && rl.rlim_max != RLIM_INFINITY)
        maxfd = (long)rl.rlim_max;
    else
        maxfd = 1024;

    for (long fd = 3; fd < maxfd; fd++)
        close((int)fd);
}

static int daemonize(void)
{
    pid_t pid;

    pid = fork();
    if (pid < 0) return -1;
    if (pid > 0) _exit(0);

    if (setsid() < 0) return -1;

    pid = fork();
    if (pid < 0) return -1;
    if (pid > 0) _exit(0);

    if (chdir("/") < 0) return -1;
    umask(0);

    close_all_fds();

    int fd = open("/dev/null", O_RDWR);
    if (fd < 0) return -1;
    dup2(fd, STDIN_FILENO);
    dup2(fd, STDOUT_FILENO);
    dup2(fd, STDERR_FILENO);
    if (fd > STDERR_FILENO) close(fd);

    return 0;
}

int main(void)
{
    if (daemonize() < 0)
        return 1;

    struct sigaction sa;
    memset(&sa, 0, sizeof sa);
    sa.sa_handler = on_term;
    sigaction(SIGTERM, &sa, NULL);
    sa.sa_handler = on_hup;
    sigaction(SIGHUP, &sa, NULL);
    signal(SIGPIPE, SIG_IGN);

    openlog("mydaemon", LOG_PID | LOG_NDELAY, LOG_DAEMON);
    syslog(LOG_INFO, "started, pid=%d", (int)getpid());

    while (!g_stop) {
        if (g_reload) {
            g_reload = 0;
            syslog(LOG_INFO, "reload config");
        }
        /* 干活 */
        pause();
    }

    syslog(LOG_INFO, "stopping");
    closelog();
    return 0;
}

这段代码里有几处容易被抄错。

_exit(0) 不是 exit(0)。exit 会刷 stdio 缓冲、跑 atexit 钩子，而此时缓冲区里还有父进程留下的半行日志，刷两遍就重复了。_exit 直接走系统调用。

close_all_fds 从 3 开始，不能碰 0、1、2。这两个数字后面要交给 dup2 重新占位。

dup2 之后必须 close(fd)，前提是 fd > 2。否则 fd 3 也指向 /dev/null，白占一个。更麻烦的是如果先 close(0) 再 open("/dev/null")，新 fd 正好拿到 0，此时 dup2(fd, 0) 等于自己复制自己，close(fd) 就把唯一的标准输入也关了。

SIGPIPE 要忽略。守护进程往一个已关闭的 socket 写日志，默认动作是直接终止进程。

七步里第 4 到 7 步可以按需裁剪。第 1 到 3 步不行，缺一步就留隐患，下一章讲为什么。

六、fork 两次为什么必要 #

一句话：只 fork 一次，进程是会话首进程；再 fork 一次，它就不是了。差别全在这。

为什么会话首进程这个身份危险?因为在 System V 语义下（Linux 采用这套），一个没有控制终端的会话首进程去 open() 一个终端设备，这个终端会变成它的控制终端，除非 open() 时带上 O_NOCTTY。而守护进程的整个存在意义就是没有控制终端。

再 fork 一次之后，最终进程既不是会话首进程，也不是组长，它去 open 终端只会得到一个普通 fd，拿不到控制终端。

man 7 daemon 里也这么写：第二次 fork 是为了保证守护进程再也不会重新获得终端，理由正是「程序及其所有依赖未必在每一次 open() 上都严谨地加了 O_NOCTTY」。

对比项 只 fork 一次 fork 两次
最终进程身份 会话首进程 + 组长 普通成员进程
控制终端 特定条件下可被重新获得 无法获得
open("/dev/tty") 在特定条件下能成功 ENXIO
孤儿收养 被 PID 1 收养 被 PID 1 收养
失败风险 依赖每个 open 都写 O_NOCTTY 不依赖调用方纪律

于是有个反直觉的结论：daemon(3) 帮你省掉了第二次 fork，代价是留下了一个隐患。glibc 的实现里只有 fork、setsid、chdir、dup2，没有第二次 fork。man 3 daemon 的 BUGS 段原文承认了这点：实现取自 BSD，没有采用确保守护进程不是会话首进程的双 fork 手法，结果守护进程本身就是会话首进程。

项目里能改就自己写七步，别调 daemon(3)。systemd 官方文档的态度更直接：daemon() 不该用，它只实现了 SysV 流程的一个子集。

关于「daemon(3) 已被标记废弃」这个说法，我查了源码：glibc 的 posix/unistd.h 里它对 daemon 的声明是普通 extern int，没有挂 __attribute_deprecated__。所以准确表述是：接口层面未被标记废弃，但 man 手册和 systemd 文档都明确不推荐使用。这是本篇对素材和常见博客说法的一处修正。

七、setsid 与 getsid #

setsid() 做成三件事，一次做完：

  1. 调用进程成为新进程组的组长，PGID 等于自己的 PID。
  2. 调用进程成为新会话的首进程，SID 等于自己的 PID。
  3. 切断与控制终端的关联。

它会失败，唯一的错误是 EPERM：调用者已经是某个进程组的组长。组长不能改宗到新会话里去，否则原进程组的 PGID 会指向一个已经跑掉的进程。这正是七步流程里必须先 fork 一次的原因：fork 出来的子进程 PID 是新的，它继承了父进程的 PGID 但不等于自己的 PID，所以不是组长。

getsid(pid) 反过来查。getsid(0) 查自己，getsid(1) 查 PID 1。

bash
$ ps -o pid,ppid,pgid,sid,tty,cmd -C mydaemon
  PID  PPID  PGID   SID TT       CMD
 9127     1  9127  9126 ?        ./mydaemon

注意 SID 是 9126 而不是 9127，PGID 是 9127。PID 等于 PGID，说明它是组长；PID 不等于 SID，说明它不是会话首进程。这就是双 fork 之后应有的样子。如果 PID == SID，说明你少 fork 了一次。TT 是 ?，表示没有控制终端。

命令行上还有个同名工具 setsid(1)，来自 util-linux:

bash
setsid ./worker &

它内部就是 fork + setsid + exec，跑完立即返回。

素材里记了一个真实的坑，保留在这里：在终端里直接敲 setsid cmd，cmd 会在后台默默跑，前台不受影响；但把它写进 shell 脚本，脚本会一直阻塞到 cmd 结束。素材给的解释是 setsid 作为组长时不 wait() 子进程而立即退出，脚本里 setsid 不是组长，bash 会 fork 并 wait() 它。这个解释与 util-linux 的实际实现是否在每个版本上都成立，我没有逐版本核对，按「素材解释，未验证」看待。

绕开的办法是让它在后台跑：

bash
setsid ./worker &

或者干脆不用 setsid(1)，回到 C 代码里自己调 setsid(2)。

终端消失时，内核给会话首进程发 SIGHUP，终端驱动再把它扩散到前台进程组。setsid() 让你不再是那个会话的成员，这条路就断了。

八、重定向标准输入输出 #

close(0); close(1); close(2); 是不够的。关掉之后这三个 fd 编号就空出来了，守护进程后面 open() 一个日志文件或者一个 socket，内核按「最小可用 fd」分配，正好拿到 0。于是标准输入变成了日志文件，接着某个库读 stdin 就读到了日志内容；或者标准输出变成了监听 socket，printf 就把数据写进了网络连接。

正确的做法是把它们指到 /dev/null，占住编号不放：

c
int fd = open("/dev/null", O_RDWR);
if (fd < 0)
    return -1;
dup2(fd, STDIN_FILENO);
dup2(fd, STDOUT_FILENO);
dup2(fd, STDERR_FILENO);
if (fd > STDERR_FILENO)
    close(fd);

dup2(oldfd, newfd) 是原子的：先关 newfd 再复制，中间不会空出窗口。分成 close + dup 两步就有竞态。

O_RDWR 不能省。只开 O_WRONLY 的话，dup2 到 fd 0 之后，任何一次读标准输入都返回 EBADF。/dev/null 支持读写，开成读写最省事。

fork 之前的 stdio 缓冲区得先刷掉。父进程 _exit(0) 不刷缓冲，缓冲区内容会留在子进程里被复制一份，等子进程退出时才刷出来，日志就重复了。

systemd 管的服务是另一套逻辑。StandardOutput=journal 时，stdout 和 stderr 直接连到 journald 的 socket，printf 和 fprintf(stderr, ...) 都会变成 journal 记录，不需要自己 dup2 到 /dev/null。

场景 stdin stdout / stderr 推荐做法
自己 daemonize /dev/null /dev/null 代码里 dup2
自己 daemonize，要留日志 /dev/null 日志文件 open + dup2，日志轮转交给 logrotate
systemd 的 Type=simple /dev/null journal 直接 fprintf(stderr, ...)
systemd 的 Type=forking 取决于你的代码 取决于你的代码 仍要自己 dup2，否则 systemd 也管不了

最后一行是个常见误解：用了 systemd 不等于可以不做重定向。Type=forking 的服务是程序自己 fork 出去的，systemd 拿不到那之后新开的 fd。

九、改变工作目录与文件权限掩码 #

chdir("/") 的理由是挂载点。进程的当前工作目录会持有那个目录所在文件系统的引用，umount 时会返回 EBUSY。守护进程如果 cwd 停在 /home/user/usbdisk/work，这块 U 盘永远卸不掉。更糟的是 cwd 停在某个被删掉的目录里，进程自己也会异常。

根目录 / 一定存在，一定在根文件系统上，不会因为任何一次 umount 消失。所以 cwd 设到那里最安全。

代价是相对路径全部失效。守护进程不能写 ./config.ini，配置路径要么在启动参数里给绝对路径，要么写死在 /etc/ 下。这一点在调试时最容易踩：前台跑能读到配置文件，一 daemonize 就报「找不到文件」。

umask(0) 的理由是继承。umask 是进程属性，fork 会原样继承。如果启动你的 shell umask 是 077，守护进程创建的文件就是 0600，别的用户读不到；换个 shell 启动，权限又变了。行为随启动环境漂移，这不是服务该有的样子。

umask(0) 的含义是「不额外剥任何权限位」，不是「创建出来的文件就是 0777」。文件权限由 open() 的 mode 参数决定，mkdir() 由它自己的 mode 决定。

c
umask(0);
int fd = open("/var/lib/mydaemon/state", O_WRONLY | O_CREAT | O_TRUNC, 0644);

素材里给的是 umask(027)。两者不冲突，取向不同：

写法 语义 适合
umask(0) 权限完全由代码里的 mode 决定 想精确控制每一个文件的权限
umask(022) 去掉 group 和 other 的写位 通用服务的常见选择
umask(027) 再去掉 group 的读执行 只给同组用户部分访问权
umask(077) 只留属主权限 存密钥、会话数据

systemd 会在启动服务前把 umask 重置好，UMask= 指令可以直接声明。自己 daemonize 的程序享受不到这个待遇。

十、信号处理：SIGHUP 与 SIGTERM #

守护进程必须接管两个信号，第三个视情况。

信号 默认动作 守护进程约定 典型实现
SIGHUP 终止 重新加载配置 置 flag，主循环里读配置
SIGTERM 终止 收尾后退出 置 stop flag，收尾后 return
SIGCHLD 忽略 回收子进程 waitpid(-1, &st, WNOHANG) 循环
SIGPIPE 终止 忽略 signal(SIGPIPE, SIG_IGN)
SIGINT 终止 前台调试时退出 与 SIGTERM 同一处理函数

SIGHUP 的原始语义是「终端挂断」，是给终端会话用的。守护进程没有终端，这个信号在实用中被借来当「重载配置」：改完 /etc/mydaemon.conf，kill -HUP <pid> 让进程重读，不用重启。systemctl reload 发的也是 SIGHUP（systemd 的 notify-reload 类型把发信号这个动作标准化了）。

用 sigaction 而不是 signal。signal() 在不同 libc、不同标准下的语义不一致，尤其老 System V 的行为是「处理一次就复位」，会漏掉后续信号。sigaction 的语义是明确的，还能控制 SA_RESTART。

处理函数里只做一件事：改 flag。

c
static volatile sig_atomic_t g_stop = 0;

static void on_term(int sig)
{
    (void)sig;
    g_stop = 1;
}

int main(void)
{
    struct sigaction sa;
    memset(&sa, 0, sizeof sa);
    sa.sa_handler = on_term;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;
    sigaction(SIGTERM, &sa, NULL);
    /* ... */
    while (!g_stop) {
        do_work();
    }
}

printf、malloc、syslog 都不是异步信号安全的。信号打断主循环时，这些函数的内部状态正处在半成品阶段，在 handler 里再调一次就会破坏它。syslog 尤其危险，它内部有锁和 socket 状态。所以 handler 只置 volatile sig_atomic_t，实际动作留给主循环。

SA_RESTART 让被信号打断的系统调用自动重启，省掉一堆 EINTR 判断。代价是 pause()、sleep() 这类调用不再被信号唤醒，得配 sigsuspend() 或者换 signalfd()。

多线程进程里，信号递送给哪个线程是不确定的。要么在启动线程前统一屏蔽，要么用 sigwait 专门开一个线程收信号。单线程的守护进程不用管这个。

十一、日志记录：syslog 与 journald #

守护进程没有终端可写，日志必须交给系统。传统答案是 syslog(3) 三件套。

c
#include <syslog.h>

openlog("mydaemon", LOG_PID | LOG_NDELAY, LOG_DAEMON);

syslog(LOG_INFO,  "worker started, pid=%d", (int)getpid());
syslog(LOG_ERR,   "connect failed: %m");        /* %m 展开成 strerror(errno) */
syslog(LOG_DEBUG, "tick %llu", (unsigned long long)n);

closelog();
参数 取值 含义
ident 程序名 每条日志的前缀，用字符串常量，别用栈上变量
option LOG_PID 每条带上 PID
LOG_NDELAY 立刻连 socket，不做延迟连接
LOG_CONS syslog 不可用时写控制台
facility LOG_DAEMON 系统守护进程
LOG_LOCAL0~LOG_LOCAL7 留给本地自定义
priority LOG_ERR LOG_WARNING LOG_INFO LOG_DEBUG 级别，可在 syslog.conf 里按级别过滤

%m 是 syslog 的专有转换，等于 strerror(errno)，不用自己拼。

openlog 的 ident 指针会被原样保存，传栈上的缓冲区，函数返回后指针就悬空了。用字符串常量。

closelog() 是可选的。不加，进程退出时内核也会回收。加上是为了在 fork 前后不留连接的悬挂。

日志文件不要自己写、自己轮转。手写轮转的守护进程一旦收到 SIGHUP，经常出现「日志文件被移走，fd 还指着老 inode」的情况，新日志全写到 mydaemon.log.1 里。交给 logrotate 并向进程发 SIGHUP，或者干脆交给 journald。

journald 是 systemd 的一部分。它把 stdout、stderr、syslog 的 socket、内核的 /dev/kmsg 全都收进来，存成带结构化字段的二进制记录。

bash
journalctl -u mydaemon.service -f          # 跟踪
journalctl -u mydaemon.service -n 100      # 最近 100 条
journalctl -u mydaemon.service -o json-pretty

日志里自带 _PID、_UID、_SYSTEMD_UNIT 这些字段，journalctl -u 就是靠它们筛的。自己 daemonize 的程序如果没走 journal，_SYSTEMD_UNIT 会是空，-u 就筛不出东西。

systemd 版本差异（按 man 手册的「Added in version」标注）：

项 起始版本 说明
journald.conf 的 LineMax= 235 之前行长度上限硬编码为 2048 字节，235 起默认 48K
journald.conf 的 ReadKMsg= 235 之前不能单独关掉内核日志采集
服务单元的 LogsDirectory= 235 同一批还加了 StateDirectory=、CacheDirectory=、ConfigurationDirectory=
systemd.exec 的 LogRateLimitBurst= 未验证 单服务覆盖全局速率限制，具体版本没查到
速率限制默认值 现行默认 30 秒内 10000 条，超出丢弃并记一条「丢弃了多少」

速率限制这一条要留意。守护进程如果在一个循环里刷 LOG_DEBUG，打满 10000 条之后，后面的日志全被丢掉，还只在 journal 里留一行「suppressed」。生产环境调试时经常以为日志没打出来，其实是这个限制。

syslog() 不是异步信号安全的。信号处理函数里写日志，就是上一章说的那个问题。要记信号相关的信息，在 handler 里置 flag，主循环里再 syslog。

十二、systemd 服务单元 #

到这一章，前面十一步里有一大半可以不写了。systemd 会替你建会话、重置信号、清空环境、接好标准流、重设 umask。

ini
[Unit]
Description=My Worker Daemon
Documentation=man:mydaemon(8)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/mydaemon --foreground
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
RestartSec=5s
User=mydaemon
Group=mydaemon
WorkingDirectory=/var/lib/mydaemon
StateDirectory=mydaemon
LogsDirectory=mydaemon
UMask=0027
LimitNOFILE=65536
NoNewPrivileges=yes
PrivateTmp=yes

[Install]
WantedBy=multi-user.target

三段的分工：

段 管什么 关键指令
[Unit] 元信息与依赖关系 Description= After= Wants= Requires=
[Service] 进程本身怎么起、怎么停 Type= ExecStart= Restart= User=
[Install] systemctl enable 时链接到哪个 target WantedBy= Alias=

After= 和 Wants= 是两件事。After= 只管顺序，Wants= 才把对方拉起来。只写 After=network-online.target 而没写 Wants=，对方不启动，你也不会等它。两个一起写才对。

Type= 选错是最高频的问题：

取值 什么时候算「启动完成」 适用 起始版本
simple 主进程 fork 出来就算 程序自己不再 fork 初始版本
exec execve() 成功之后才算 想捕获「二进制不存在」这类错误 未验证
forking 父进程退出时算 老式自己 daemonize 的程序，要配 PIDFile= 初始版本
notify 收到 sd_notify("READY=1") 才算 程序集成了 libsystemd 未验证
notify-reload 同上，reload 也走协议 需要可靠的 systemctl reload 253
dbus 拿到 D-Bus 名字才算 提供 D-Bus 接口的服务 初始版本
oneshot 主进程退出才算 一次性任务 初始版本

Type=forking 是给老程序兜底的。systemd 官方文档说这个类型不推荐，优先 notify、notify-reload、dbus。原因是父进程退出和子进程真正就绪之间没有可靠信号，只能靠猜。

bash
# 放好单元文件后
sudo systemctl daemon-reload
sudo systemctl enable --now mydaemon.service
systemctl status mydaemon.service
systemctl reload mydaemon.service
journalctl -u mydaemon.service -f

daemon-reload 不能省。改了 .service 文件不 reload，systemd 用的还是内存里那份旧配置，systemctl restart 也不管用。

ExecReload=/bin/kill -HUP $MAINPID 能工作，但 man 手册明确说这不是好选择：发信号是异步动作，systemd 不知道重载什么时候结束，多个服务的重载没法排序。要可靠就用 Type=notify-reload，让程序在重载完成后回一个 READY=1。

程序侧只需要一次 sd_notify:

c
#include <systemd/sd-daemon.h>

sd_notify(0, "READY=1");      /* 启动完成 */
sd_notify(0, "RELOADING=1");  /* 重载开始 */
sd_notify(0, "READY=1");      /* 重载结束 */

不带 libsystemd 也能做：协议就是一个 unix socket 加一行 READY=1\n，地址在 $NOTIFY_SOCKET 里。systemd 文档保证这个协议稳定。

systemd 的版本差异（Added in version 取自 man 手册）：

指令 起始版本 说明
KillMode= KillSignal= SendSIGKILL= 187 之前无法细控停止时的信号
SendSIGHUP= 207 停止时顺手发 SIGHUP，默认 no
FinalKillSignal= WatchdogSignal= 240 之前超时后固定发 SIGKILL
ExitType= 250 之前停止判定只看主进程
RestartKillSignal= 244 restart 场景可以用不同信号
Type=notify-reload 253 之前只能用 ExecReload= 发信号
StateDirectory= LogsDirectory= 235 之前要自己 mkdir 加 chown
OpenFile= 253 由 manager 打开文件再传 fd

老发行版上写这些指令要小心。CentOS 7 带的是 systemd 219，上表里 235 之后的东西全部不支持，写进去会被当成未知指令忽略，且只在 systemd-analyze verify 或启动日志里给一条警告。

十三、传统 init 脚本 #

systemd 之前是 SysV init，靠 /etc/init.d/ 下的 shell 脚本。今天还能见到，多在一些老系统和容器镜像里。

bash
#!/bin/sh
### BEGIN INIT INFO
# Provides:          mydaemon
# Required-Start:    $network $remote_fs
# Required-Stop:     $network $remote_fs
# Default-Start:     2 3 4 5
# Default-Stop:      0 1 6
# Short-Description: My worker daemon
### END INIT INFO

DAEMON=/usr/local/bin/mydaemon
PIDFILE=/run/mydaemon.pid

case "$1" in
    start)
        start-stop-daemon --start --quiet --background \
            --make-pidfile --pidfile "$PIDFILE" \
            --exec "$DAEMON" -- --foreground
        ;;
    stop)
        start-stop-daemon --stop --quiet --retry=TERM/30/KILL/5 \
            --pidfile "$PIDFILE" --remove-pidfile
        ;;
    reload)
        start-stop-daemon --stop --signal HUP --quiet --pidfile "$PIDFILE"
        ;;
    restart|force-reload)
        "$0" stop; sleep 1; "$0" start
        ;;
    status)
        start-stop-daemon --status --pidfile "$PIDFILE"
        ;;
    *)
        echo "Usage: $0 {start|stop|reload|restart|status}"
        exit 3
        ;;
esac

exit 0

--background 让 start-stop-daemon 自己 fork，--make-pidfile 让它写 pid 文件。所以这里传的是 --foreground，让 mydaemon 保持前台，脱离的活由调用方做。### BEGIN INIT INFO 那段叫 LSB header，insserv、chkconfig、update-rc.d 靠它排启动顺序。

任务 Debian 系 Red Hat 系
注册开机启动 update-rc.d mydaemon defaults chkconfig --add mydaemon
打开某运行级 update-rc.d mydaemon enable chkconfig --level 35 mydaemon on
手动起停 /etc/init.d/mydaemon start service mydaemon start

和 systemd 的差别不只是「新旧」：

维度 SysV init 脚本 systemd 服务单元
描述形式 可执行 shell 脚本 声明式 ini
启动方式 串行，按 S01 S02 编号排序 并行，按依赖图调度
进程跟踪 只认 pid 文件 整个 cgroup
重启策略 脚本里自己写循环 Restart= 声明
日志 程序自己写文件或 syslog 自动收进 journal
资源限制 靠 ulimit LimitNOFILE= 等指令
依赖表达 只能表达启动顺序 顺序与需求两个维度分开表达

进程跟踪那一行最关键。SysV 只认文件里的数字，进程被 OOM 杀掉、重新拉起后 PID 变了，脚本就会杀错进程。systemd 用 cgroup 记录整个进程树，子进程也跑不掉。

systemd 文档现在的措辞是 SysV init 脚本对启动的支持「已被逐步淘汰，不应再依赖」。各发行版保留到什么程度不同，具体移除到哪一步我没查到统一版本号，按未验证对待。

十四、守护进程的调试 #

把 daemonize 写进代码，调试就变成折磨：程序在后台跑，printf 进了 /dev/null，崩了没输出。

对策是留一个前台开关。这是最有价值的一条建议，几乎所有正经守护进程都有。

c
int main(int argc, char **argv)
{
    int foreground = 0;

    if (getenv("MYDAEMON_FOREGROUND") != NULL)
        foreground = 1;

    if (!foreground && daemonize() < 0)
        return 1;

    run();
    return 0;
}

-f/--foreground 参数和环境变量都行。systemd 单元里就写 ExecStart=/usr/local/bin/mydaemon --foreground，让 systemd 负责脱离，程序只管干活。这样同一份二进制在开发机和线上都能跑。

其余排查手段：

bash
# 1. 进程身份对不对
ps -o pid,ppid,pgid,sid,tty,stat,cmd -C mydaemon
# 2. fd 重定向生效了没有
ls -l /proc/$(pgrep -o mydaemon)/fd
# 3. 信号处理装上了没有（SigCgt 位掩码）
grep -E 'SigIgn|SigCgt|SigBlk' /proc/$(pgrep -o mydaemon)/status
# 4. 系统调用层面看在哪卡住
strace -f -p $(pgrep -o mydaemon) -e trace=openat,connect,read
# 5. 从启动开始跟
strace -f -o /tmp/trace.txt ./mydaemon

/proc/PID/fd 下应该看到 0、1、2 全指向 /dev/null。如果 0 指向某个 .log 文件，说明第八章那个 fd 复用问题已经发生了。

SigCgt 是十六进制位掩码，第 N 位为 1 表示信号 N 装了处理函数。SIGHUP 是 1，最低位是 1 才说明它接管了 SIGHUP。SigIgn 里该有 SIGPIPE 的位。

排查 systemd 侧：

bash
systemd-analyze verify /etc/systemd/system/mydaemon.service
systemctl show -p MainPID -p NRestarts mydaemon.service
journalctl -u mydaemon.service --since "10 min ago"
journalctl -k | grep -i 'killed process'      # 查 OOM
systemd-run --user --pty --unit=my-test ./mydaemon --foreground

NRestarts 能看出服务是不是在反复崩溃重启。Restart=on-failure 配上 RestartSec=5s，一个启动即崩的程序会安静地每 5 秒重试一次，systemctl status 里看着像在跑。

十五、常见故障与现象 #

故障排查的顺序是固定的：先看进程身份（ps），再看 fd（/proc/PID/fd），再看信号（/proc/PID/status），最后才看日志。身份不对，日志看不出问题。

现象 常见原因 查什么
终端一关进程就没了 只用了 &，仍是原会话成员 ps -o sid，和自己的 SID 比
前台能跑，后台启动即退 chdir("/") 后相对路径失效 把所有路径改成绝对路径
进程存在但 ps 状态是 T 后台读写终端触发 SIGTTIN/SIGTTOU ls -l /proc/PID/fd
日志每条重复两遍 fork 前 stdio 缓冲没刷 父进程改用 _exit，或 fork 前 fflush
日志写进了上一轮的文件 用了 logrotate 但没发 SIGHUP 轮转配置的 postrotate
umount 报 device is busy 没做 chdir("/") ls -l /proc/PID/cwd
文件权限随机变化 继承了启动者的 umask 显式 umask() 或用 UMask=
子进程变僵尸，越积越多 没回收 SIGCHLD ps -eo stat,cmd | grep '^Z'
journalctl -u 查不到日志 程序自己 daemonize，_SYSTEMD_UNIT 为空 改用前台模式交给 systemd
systemctl start 成功但立刻退 Type=forking 但程序没有 fork 改成 Type=simple
服务起来 90 秒后被 kill Type=notify 但没发 READY=1 systemctl status 里的 timeout 提示
日志打到一半就没了 journald 速率限制触发 journalctl | grep -i suppress
标准输入读出奇怪内容 fd 0 被复用成了别的文件 /proc/PID/fd/0 的指向
重启后 pid 文件里的进程对不上 pid 文件没加锁，旧进程还在 flock 或交给 systemd

「进程状态 T」那一条最难查，因为进程在、端口在、就是不响应。触发条件是守护进程还留着一个终端 fd，并且被放到后台去读写。第八章那套重定向是唯一的解法。

十六、易错点速查 #

易错点 正确做法 后果
只 fork 一次 fork 两次 会话首进程有机会重新拿到控制终端
用 exit() 退出父进程 用 _exit() stdio 缓冲被刷两遍，日志重复
close(0/1/2) 了事 dup2 到 /dev/null fd 编号被后续 open 复用
dup2 后不 close(fd) fd > 2 时关掉 白占一个 fd，泄漏
先 close(0) 再 open("/dev/null") 先 open 再 dup2 新 fd 拿到 0，dup2 成空操作
daemon(3) 一把梭 自己写七步 少了第二次 fork，且无法控制细节
不刷缓冲就 fork fork 前 fflush(NULL) 缓冲区被复制，输出翻倍
chdir 不做 chdir("/") 挂载点卸不掉
chdir 做了还用相对路径 路径全用绝对路径 后台启动就找不到配置
umask 不管 显式 umask() 或 UMask= 文件权限随启动环境漂移
用 signal() 装处理函数 用 sigaction() 老语义下处理一次就复位
信号处理函数里 printf/syslog 只置 volatile sig_atomic_t 破坏主流程的内部状态
不忽略 SIGPIPE signal(SIGPIPE, SIG_IGN) 写已关闭的 socket 直接终止
自己写日志轮转 交给 logrotate 或 journald 轮转后日志写进旧 inode
服务自己 daemonize 又用 systemd 管 --foreground + Type=simple systemd 跟踪不到真实进程
ExecReload=kill -HUP 当可靠 Type=notify-reload 重载是异步的，无完成信号
改了 unit 不 daemon-reload 每次改完 reload 跑的仍是旧配置
在旧发行版用新指令 先 systemd-analyze verify 指令被静默忽略

最后一行值得单独说。StateDirectory=、Type=notify-reload 这些在 systemd 219（CentOS 7）上不存在，写进去不会报错，只是不生效。你以为目录会自动建好，结果服务因为没有写权限而退出，查半天查不到原因。
