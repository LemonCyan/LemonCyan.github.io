一、实时系统的定义：确定性比快更重要 #

实时操作系统（RTOS，Real Time Operating System）的定义是：当外界事件或数据产生时，能够接受并以足够快的速度处理，处理的结果又能在规定的时间之内控制生产过程、或对处理系统作出快速响应，并控制所有实时任务协调一致运行。拆开看这句话压了三个条件：要接得住事件，结果要落在截止时间（deadline）之前，多任务之间要协调一致。前两条讲时间，第三条讲调度。及时响应和高可靠性是它的两个主要特点。

于是就有了最常见的误读：把实时等同于快。快讲的是平均值，实时讲的是最坏情况的上界。一个系统平均响应 10 微秒、偶尔抖到 50 毫秒，它不实时；另一个系统每次都稳定在 200 微秒上下，它是实时的。判据不是「多快」，是「能不能保证不超过某个上限」。

text
事件 ──→ 中断到达 ──→ ISR 开始执行 ──→ 唤醒任务 ──→ 任务真正运行
        |<- 中断延迟 ->|<- 调度延迟 ->|
        |<-------------- 端到端响应延迟 -------------->|

三个量要分开算：

  • 最坏执行时间（WCET）：一段代码最长要跑多久。由代码本身决定，跟操作系统关系不大。
  • 延迟（latency）：事件发生到任务开始处理之间的时间。由内核决定，是实时性的主战场。
  • 抖动（jitter）：多次测量里延迟的波动范围。它决定你能不能做控制回路，PID 最怕的就是抖动。

实时系统真正卖的是后两者的确定性。评估一套实时方案，看最大延迟，不要看平均延迟。平均值再好看，一次超期就能让机械臂撞到工作台上。

二、硬实时、软实时与弱实时 #

按超期的后果分级，这是工程上最有用的一条分界线。

维度 硬实时（hard） 软实时（soft） 弱实时（firm）
超期后果 结果失去意义，系统判为失败 结果质量下降，系统继续工作 结果短时失效，之后仍可补救
保证方式 操作系统设计时就要保证 按优先级尽快完成即可 靠统计意义上的余量兜底
判定语气 必须在规定时间内完成 尽量在规定时间内完成 大部分时间能完成
典型场景 运动控制、安全联锁、伺服环路 音视频播放、界面交互、日志落盘 传感器采样、监控上报
超期一次 不可接受 可接受 可接受，但连续超期不行

素材里的例子最能说明差别：为了让生产线上的机器人抓住某个物体而设计的系统，「硬」实时下如果不能在允许时间内完成让物体可达的计算，操作系统将因错误结束；「软」实时下生产线还能继续工作，只是产品的输出会因物体没在允许时间内到达而减慢，机器人出现短暂的不生产现象。

硬实时的那条线是在操作系统设计阶段就焊死的。这就是为什么拿通用 Linux 改改参数改不出硬实时——它的设计目标本来就不在这。还有个常被拿来打圆场的说法：一些通用目的操作系统称自己为实时操作系统。事实是，大部分通用 OS，比如 Windows NT 或 IBM 的 OS/390，确实带一部分实时特征。即使一个系统不是严格的实时系统，它也能解决一部分实时应用问题。这话对，但只在软实时区间成立。判断一个内核够不够实时，先看它有没有这三样：多任务、线程优先级、多种中断级别。

三、RTOS 与分时 OS 的根本差别 #

分时操作系统（TSOS，Time-sharing Operating System）的出发点是另一件事：让一台计算机同时为几个、几十个甚至几百个用户服务。把计算机与许多终端用户连接起来，操作系统将处理机时间与内存空间按一定的时间间隔，轮流切换给各终端用户的程序使用。时间间隔足够短，每个用户的感觉就像独占计算机。产生分时系统是为了满足三类用户需求：人机交互、共享主机、便于用户上机，它跟多道批处理系统的性能取向截然不同。

分时的基本思想是两个词：

  • 时间片：把系统资源（尤其是 CPU 时间）在时间上切开，每个时间段是一个时间片，每个用户依次轮流使用。
  • 分时技术：把处理机的运行时间分成很短的时间片，按时间片轮流把处理机分给各联机作业使用。

设计目标写得很直白：对用户的请求及时响应，并在可行条件下尽量提高系统资源的使用率。注意「尽量」两个字——它的及时是尽力而为，没有上界承诺。工作方式是一台主机连若干终端，每个终端一个用户，交互式地提命令，系统接收命令后用时间片轮转处理，再把结果回到终端。实现上的两个关键问题是及时接收、及时处理。四个特征：交互性（用户与系统人机对话）、多路性（多用户同时在各自终端上使用同一 CPU）、独立性（用户彼此独立操作、互不干扰）、及时性（用户短时间内能得到回答）。响应时间受这些因素影响：终端数目多少、时间片的大小、信息交换量、信息交换速度。

把两条线摆在一张表里：

维度 RTOS（实时） TSOS（分时）
设计目标 在规定时间内完成任务 多用户公平分享，兼顾利用率
第一优先级 截止时间，确定性 公平性与交互体验
调度依据 优先级（静态或动态） 剥夺式动态优先 + 时间片轮转
抢占粒度 内核可剥夺，随时可抢占 按时间片轮转剥夺
时间尺度 ms 级，甚至 us 级 时间片长度可调，人不觉得卡即可
典型硬件 相对低速的 MCU、带隔离核的 SoC PC、服务器
典型场景 运动控制、按键输入、电梯上下控制 办公自动化、教学、事务处理
衡量指标 中断响应时间、最坏延迟 平均响应时间、资源利用率

素材里的落地结论：RTOS 一般用于相对低速的 MCU，比如运动控制类、按键输入等动作要求实时处理的系统，要求 ms 级甚至 us 级响应；分时是现在流行的 PC、服务器采用的模式，把 CPU 运行分成若干时间片分别处理不同运算请求；实时也常见于单片机，比如电梯的上下控制，按键动作要求实时处理。

一句话记住差别：分时系统怕你不公平，实时系统怕你慢一次。

四、调度算法：优先级抢占与时间片轮转 #

调度是内核的主要职责之一，决定轮到哪个任务运行。实时内核一般基于优先级调度法。先把几个基本概念钉住，后面全靠它们：

  • 代码临界段：处理时不可分割的代码。这部分代码一旦开始执行，就不允许中断打入。
  • 资源：任何为任务所占用的实体。共享资源：可以被一个以上任务使用的资源。
  • 任务：也叫线程，是一个简单的程序。每个任务被赋予一定的优先级，有自己的一套 CPU 寄存器和自己的栈空间。典型地，每个任务都是一个无限的循环。
  • 任务切换：把正在运行任务的当前状态（CPU 寄存器中的全部内容）保存在它自己的栈区，然后把下一个要运行任务的当前状态从它的栈里重新装入 CPU 寄存器，开始下一个任务。
  • 内核：负责管理各个任务，为每个任务分配 CPU 时间，并负责任务之间的通讯。按抢占能力分两类——不可剥夺型内核和可剥夺型内核。
  • 调度：内核决定轮到哪个任务运行的那部分逻辑。

任务在五个状态之间流转：休眠态、就绪态、运行态、挂起态、被中断态。所谓「实时」，很大程度就是这五个状态之间的迁移路径上有没有不可控的长尾。优先级分两种：优先级不可改变的静态优先级，和优先级可改变的动态优先级。静态优先级实现简单、行为可预测，硬实时系统偏爱它；动态优先级能适应负载变化，代价是分析最坏情况变难。

可剥夺型内核与不可剥夺型内核的分界，就在「能不能在高优先级任务就绪的瞬间切走」：可剥夺型内核下，高优先级任务一就绪就拿到 CPU；不可剥夺型内核下，当前任务要自己让出，最长等待时间取决于最长的那段临界段。

c
/* 优先级抢占 + 同优先级时间片轮转的骨架 */
void schedule(void)
{
    struct task *next = pick_highest_ready();

    if (next == current)
        return;

    if (next->prio > current->prio) {
        /* 高优先级就绪：立即抢占，不看时间片 */
        context_switch(current, next);
        return;
    }

    if (next->prio == current->prio &&
        current->slice_used >= current->slice) {
        /* 同优先级：时间片用完才轮转 */
        current->slice_used = 0;
        context_switch(current, next);
    }
}

两个要点。第一，抢占判断只看优先级，跟时间片无关——时间片是给同级任务分蛋糕用的，不该拖慢高优先级任务。第二，pick_highest_ready() 必须是 O(1) 或 O(log n) 的，实时内核用位图 + 就绪队列做到常数时间，通用内核在这上面花的指令数不敏感，实时内核敏感。

分时内核的调度是另一套逻辑：按时间片轮转配合动态优先级，谁等得久就把谁的优先级抬一点，保证没人被饿死。这套逻辑对交互体验友好，对截止时间毫无承诺——它关心的是「大家都跑过一遍」，不是「重要的那个先跑完」。

五、优先级反转与优先级继承 #

素材里有一句判断可以直接沿用：优先级反转是实时系统里出现最多的问题。

成因不复杂：共享资源的分配会导致优先级低的任务先运行，优先级高的任务后运行。三个任务就能复现——低优先级任务 L 拿到了锁，高优先级任务 H 就绪后要同一把锁，只能等；此时中优先级任务 M 就绪，它比 L 优先级高，于是把 L 抢了；L 不跑，锁不释放，H 就只能干等 M 跑完。一次典型的反转时序：

时刻 发生了什么 谁在 CPU 上
t0 L 拿到互斥量，进入临界段 L
t1 H 就绪，抢占 L，随后请求同一互斥量被阻塞 H → 阻塞
t2 L 恢复运行，继续临界段 L
t3 M 就绪，优先级高于 L，抢占 L M
t4 L 迟迟拿不到 CPU，锁一直不释放 M
t5 H 的等待时间被 M 撑长，与 L 的临界段长度脱钩 M

问题的恶劣之处在 t5：H 的等待时间不再由「L 的临界段有多长」决定，而由「M 要跑多久」决定。这是一条不受控的长尾，硬实时系统不能接受。影响落在四个地方：延迟不可界（高优先级任务的响应时间取决于无关任务的执行时间）、分析失效（按优先级做的可调度性分析全部作废）、抖动放大（偶发一次反转就是一次大抖动，控制回路直接震荡）、难复现（只在特定交错时序下出现，测试环境抓不到）。

解法是优先级继承：临时改变任务优先级，以遏制优先级反转。L 在持有锁期间被临时抬到 H 的优先级，M 就抢不动它，L 尽快跑完临界段、释放锁，再把优先级降回去。H 的等待时间重新变成「L 的临界段长度」，恢复可界。抬升发生在阻塞检测的那一刻（H 阻塞在 L 持有的锁上），链条可以继承多级（L 又在等 K 的锁），释放时按链回退，所以继承链必须有界，否则解锁开销变成新的长尾。

互斥本身还得先成立。保证每个任务处理共享数据时排他，一般有四条路：关中断、使用测试并置位指令（TAS）、禁止做任务切换、利用信号量。四条路代价差得远——关中断最狠，影响整个系统的响应；TAS 只保护一条指令级别的操作；禁止任务切换只在本核有意义；信号量最通用，也最需要配合优先级继承。

选哪条看临界段多长、要保护什么。硬实时系统的常规做法：临界段做到很短，短的用关中断，长的用带优先级继承的互斥量，绝不在临界段里做会阻塞的事。

六、系统滴答（Tick）与它的代价 #

系统滴答（SysTick），有些地方也叫时钟节拍、系统心跳。操作系统能在多任务间切换，靠的是一个系统定时器以固定频率中断，为操作系统提供调度（上下文切换）的时机，任务切换才成立。这个定时器就是系统滴答。

早些年的 51、430 单片机跑 RTOS，都是单独拿一个 Timer 定时器提供系统滴答。考虑到跑 RTOS 这个需求普遍存在，Cortex-M 内核直接把这个定时器做进了核里。市面上很多单片机基本都自带有 SysTick 这个定时器，Cortex-M0、M3、M4 这些内核的单片机都有，而且只要调用官方写好的 API 函数即可使用。它藏在系统配置文件里：滴答频率（OS_TICKS）位于系统配置文件，改这个文件就是配滴答，FreeRTOS 是 FreeRTOSConfig.h，uC/OS 是 os_cfg.h。一些系统通过图形化界面配置，本质上改的还是这两个文件。

c
/* FreeRTOSConfig.h 里的关键一行 */
#define configTICK_RATE_HZ    ((TickType_t)1000)

OS_TICKS 一般配成 1000。从宏定义和注释很容易理解：就是每秒系统滴答的次数。配成 1000，代表系统每 1ms 要做一次轮转调度，检查是否有更高优先级任务要执行（并切换任务）。100M 主频的单片机，执行一次调度（几十条语句），时间在 us 级别。1000 是一个比较适合的中等值，100、10000、2000 也可以，只是不利于系统以及编程。为什么取 1000，素材给了三条理由，我补成一张对照表：

OS_TICKS 每 tick 间隔 代价 影响
100 10ms 调度开销极低 调度粒度粗，延时精度只有 10ms
1000 1ms 中等 1ms 一调度，延时计算直观，推荐值
2000 0.5ms 偏高 调度更密，但系统延时不好算
10000 0.1ms 高 调度自身占的 CPU 时间开始显眼
100000 10us 很高 内核大半时间在给自己做调度

三条判断可以直接照抄：滴答太大，10K 甚至 100K，对系统的负担比较大，因为调度自身会占用 CPU 时间；1ms 滴答一次，方便编程系统延时，2K、10K 这种值在用到系统延时时不好计算；实时操作系统的 SysTick，在没有特殊情况下，最好默认配置 1000。

第二条值得展开。用 vTaskDelay(1000) 举例：滴答值为 1000 时它代表延时 1 秒；滴答值为 2000 时，同样的 1000 只代表延时 0.5 秒。同一个数字在不同配置下含义不同，代码从 A 板搬到 B 板就错，这种坑排查起来极费时间。还有两条经验：在系统允许的情况下，SysTick 数值越大，系统实时性越高，反之实时性越差；主频相对偏低（比如低于 10M）的处理器，SysTick 值可以适当配置低一点。

滴答是周期性的，这一点决定了它的代价有上限：

text
固定周期滴答：       |----|----|----|----|----|----|   每格 1ms
事件到达：              ↑                          ↑
                        即使此刻高优先级任务就绪，
                        也要等到下一个 tick 才切

等待被量化成「最多一个 tick」。1ms 的 tick 意味着平均 0.5ms、最坏 1ms 的额外延迟，而且它是周期性地叠加在真实延迟上。这就是 tickless 内核存在的理由——没活干的时候把定时器关掉，来事件了再唤醒，代价是内核逻辑复杂、长时间不 tick 会丢时间基准。

对 Linux 而言，滴答的对应物是内核时钟中断。PREEMPT_RT 之后主流做法是 CONFIG_NO_HZ_FULL：把 tick 从 CPU 上彻底摘掉，让某个核在无事可做时完全不被打断。这也是第九章里「隔离核」能测出更好延迟的原因之一。

七、Linux 为什么不是实时系统 #

道理不复杂，四个结构性原因，从上往下压。

第一，内核态不可抢占。传统 Linux 内核里，一个任务进了内核态执行系统调用，在它自己让出 CPU 之前别的任务进不来——哪怕那个任务优先级更高。这段窗口有多长，取决于内核里最长的那条不可抢占路径，应用层完全控制不了。

第二，关中断区间多且长。内核在动 per-CPU 数据、跑 RCU 回调、走某些锁路径时会关中断。关中断期间中断到达也进不来，直接变成延迟。硬实时要求这个窗口有严格上界，通用内核不承诺。

第三，中断处理不归调度器管。硬件中断优先级高于所有任务，ISR 里不能睡眠、不能阻塞，只能做最少的事然后丢给下半部。软中断、tasklet、工作队列这些下半部机制在调度上没有截止时间概念。

第四，为吞吐优化的设计取向。自旋锁、每 CPU 缓存、批量处理、RCU，全是为了「多干活」而不是「准时到」。这两件事在多数时候不冲突，在关键路径上必然冲突。

四条加起来，结果是延迟分布有一条不可控的长尾。你测一千次都是几十微秒，生产环境跑三天来一次 3 毫秒——这一下就把硬实时的假设打穿。Linux 不是不能用在实时场合，是它原生不提供上界承诺。要拿承诺，得改内核或者换架构。

方案 做法 实时性 改动成本 兼容性 适合谁

PREEMPT_RT 打实时补丁，把内核改成完全可抢占 硬实时（受硬件与驱动影响） 中，要换内核 高，仍是单内核 Linux 需要完整的 Linux 用户态 + 硬实时
双内核（Xenomai/RTAI） 加一层微内核，实时任务跑在微内核域 硬实时，最坏延迟最可控 高，要改内核 + 学新 API 中，实时任务走专有 API 硬实时要求严、能接受双套 API
AMP 拆核，一部分核裸跑或跑 RTOS 硬实时，物理隔离 高，要配核间通信与外设归属 低，等于两套系统 对实时要求最高，愿意改架构

这四条不是互斥的，实战里经常叠着用：先做隔离核（第十三章），不够就上 PREEMPT_RT，还不够就双内核，最后才是 AMP。素材里 Firefly 的固件同时提供 preempt 和 xenomai 两个版本，就是这个分层思路的现成例子。顺序不能反，AMP 听起来最彻底，代价也最大：要把外设归属、中断路由、内存布局、核间通信全部重新规划，一旦某次迭代要加功能，改动面比前三条大得多。

九、PREEMPT_RT 补丁：把内核变成可抢占 #

PREEMPT_RT 的思路是把第七章那四条逐个拆掉：自旋锁换成可睡眠的实时互斥量（rt_mutex），临界段不再关抢占；关中断区间压缩到很短，长的部分改成「关中断 + 屏蔽」的软件模拟，也就是 threaded IRQ；中断处理线程化，硬中断只做最小唤醒，真正的处理跑成一个内核线程，这个线程能被调度、能被更高优先级抢；高精度定时器接管 tick，配合 CONFIG_NO_HZ_FULL 摘掉空闲核的周期性中断。

副作用是吞吐略降、内核代码分支变多，换来的是最坏延迟变得可测量、可收敛。这不是免费的，你得接受某些场景下性能掉一截。

素材给的实测流程走一遍就有感觉。测试实时性能需要 cyclictest，可以用 apt 安装：

bash
apt update
apt install rt-tests

用 stress 或 stress-ng 模拟通用压力场景，让 CPU 处于满负荷状态：

bash
# 根据芯片核心数运行 cpu 压测线程、io 压测线程及内存压测线程

然后测每个核心的实时响应延迟，跑 3 天，结果输出到 output 文件：

bash
cyclictest -m -S -p99 -i1000 -h800 -D3d -q > output
参数 含义

-S 各线程使用同一时钟源，结果可横向比
-p99 测量线程优先级设 99，贴近真实实时任务
-i1000 周期 1000 微秒，即 1ms 一次
-h800 直方图统计到 800 微秒
-D3d 持续 3 天
-q 只在结束时打印汇总

Firefly 在 rk3568、rk3562、rk3588 上都做了 3 天延迟测试：rk3568 和 rk3562 把 CPU3 从内核 SMP 平衡和调度算法中剔除，rk3588 剔除 CPU6 和 CPU7，以便观察芯片最好的实时性能。具体数据放第十三章。

十、Xenomai：双内核方案 #

Xenomai 是一个专门为 Linux 平台设计的实时框架，它允许各种实时操作系统（RTOS）的应用程序接口（API）在 Linux 环境中使用，比如 VxWorks 和 QNX 的 API。这种技术集成提升了 Linux 系统的实时性能，提供硬实时调度的保障，使开发者能在 Linux 上实现严格的时间响应要求。这对需要快速反应的应用很关键，比如自动化控制、机器人技术和高频交易。

它不只跑在主流 Linux 内核上，还支持多种嵌入式平台。这一点对工业或消费类设备很关键，因为很多设备依赖嵌入式系统执行重要任务。官方维护了一份嵌入式硬件清单，选型前可以去 Xenomai 官方嵌入式设备列表 对照。Xenomai 版本信息：原文未标注。

它能干的三件事：设计与开发实时应用程序，在 Linux 上跑需要高实时性的程序（自动化生产线的控制系统必须在毫秒内对传感器输入做出反应）；移植已有的 RTOS 程序，很多机器人控制程序最初写在 VxWorks 上，通过 Xenomai 可以保留原有代码在 Linux 里接着用，开发流程不用推倒重来；以 Linux 原生应用程序方式运行 VxWorks、pSOS、VRTX、uITRON 和 POSIX 程序，团队已经习惯在 Linux 里开发的话，接这些 RTOS 应用的成本很低。

双内核结构 #

Xenomai 用双内核架构实现实时：一个是高优先级的微内核（co-kernel），另一个是传统的 Linux 内核。co-kernel 负责执行实时任务，Linux 内核维持其常规的服务功能。两个内核由 Adeos 管理，每个内核被分配到不同的域。这里有个必须警惕的点：微内核会切到 Linux 内核域，这会破坏 Xenomai 的实时性。触发条件是实时任务里用了 Linux 的系统调用。设计实时任务时，对 Linux 系统调用要谨慎。

text
        ┌──────────────────────────────────┐
        │            应用层                 │
        │  实时任务（Xenomai API） 普通 Linux 应用 │
        └───────────┬──────────────┬───────┘
                    │              │
        ┌───────────▼───────┐  ┌───▼───────────┐
        │  Xenomai co-kernel │  │  Linux 内核    │
        │  （域优先级高）      │  │  （域优先级低）  │
        └───────────┬───────┘  └───┬───────────┘
                    └───────┬──────┘
                    ┌───────▼────────┐
                    │  Adeos / I-pipe │
                    └───────┬────────┘
                    ┌───────▼────────┐
                    │      硬件       │
                    └────────────────┘

Adeos #

Adeos/i-pipe 是实现双内核结构的核心，它是 Xenomai 和 RTAI 等系统的基础。在基于 Adeos 的系统里，操作系统在独立的域内运行，每个域有独立的地址空间及类似进程、虚拟内存这样的软件抽象层，且这些资源可以在域间共享。

计算机系统里，操作的执行主要依赖内部和外部的中断与异常，比如系统时钟中断就是操作系统中重要的中断。Adeos 通过管理硬件中断、按域的优先级依次调用相应域的中断服务程序来驱动系统运行，还提供域间通信机制，实现域的调度等功能。为了管理中断并控制域间优先，这里引入了「中断管道（Interrupt Pipe）」的概念：通过中断管道，Adeos 在不同域之间传播中断，并提供机制让域能调整自身在中断管道中的优先级。

Xenomai 在 Adeos 系统中的域优先级高于 Linux 域。每当中断发生，Adeos 首先调度 Xenomai 处理该中断并执行相应的实时任务；只有在 Xenomai 没有实时任务和中断需要处理时，Adeos 才调度 Linux。这保证了 Xenomai 的中断响应速度和实时任务不受 Linux 干扰，从而提供可预测的实时性能。

十一、Cobalt 与 Mercury 两种模式 #

上面说的双内核那套配置，在 Xenomai 里叫 Cobalt。它还有另一套配置叫 Mercury，两者是编译期二选一，不是运行期开关。

维度 Cobalt Mercury
架构 双内核，co-kernel + Linux 单内核，纯 Linux
依赖 Adeos/I-pipe 中断管道 依赖内核自身的实时能力（PREEMPT_RT）
实时域 独立于 Linux 的高优先级域 无独立域，与 Linux 共享调度器
实时性 硬实时，最坏延迟可控 取决于底层内核，偏软实时到弱硬实时
中断接管 co-kernel 先于 Linux 处理中断 无接管，走 Linux 中断路径
可调试性 较难，两个域之间切换要小心 较好，只有一套内核视图
选型场景 明确要硬实时、能接受双套 API 想统一工具链、实时要求没那么硬

两者的取舍很干脆：Cobalt 用架构复杂度换确定性，Mercury 用确定性换简单。素材讲的双内核、Adeos、中断管道、域优先级，全部属于 Cobalt；Mercury 下这些机制都不存在。还有一个容易踩的坑：两套模式的实时任务写法与迁移路径不同，选型阶段定下来就不要来回换，换一次等于重做一遍上面那张表的全部工程。

十二、实时性的量化指标：延迟与抖动 #

指标先分清，别混着说。

指标 定义 谁决定它 怎么看
平均延迟 所有测量的算术平均 系统常态性能 只用于对比，不能作为实时判据
最大延迟 一轮测试里的最长一次 最坏路径，含长尾 硬实时的核心指标
延迟抖动 多次测量中延迟的波动幅度 调度与中断的确定性 控制回路最在意它
中断响应时间 中断到 ISR 首条指令执行 内核关中断策略 见下面的公式

中断响应时间是衡量嵌入式实时操作系统最主要、最具代表性的性能指标。

text
中断响应时间 = 中断延迟时间 + 保存 CPU 状态的时间 + 该内核的 ISR 进入函数的执行时间
中断延迟时间 = MAX(关中断的最长时间, 最长指令时间) + 开始执行 ISR 的第一条指令的时间

公式里 MAX(关中断的最长时间, 最长指令时间) 这一项是关键。它说明中断延迟不取决于你的代码写得多好，取决于内核最长的那个不可中断窗口——这又把我们送回第七章。测量方法分两类，选哪个看你要什么：

bash
# 1. 周期定时器测量：设定 1ms 周期，看实际唤醒时刻的偏差
#    cyclictest 用的就是这个模型，偏差即延迟
cyclictest -m -S -p99 -i1000 -h800 -D3d -q > output

# 2. 外力触发测量：外部信号（GPIO/串口）触发，ISR 翻转另一个引脚
#    用示波器看两个沿的时间差，排除测量程序自身的干扰
#    这一路更接近硬件真实响应，也是唯一不依赖被测系统自报的方法

两种方法的差别要清楚。周期定时器法方便、可长时间跑、能出直方图，但测量程序本身就在被测量的系统里跑，会引入自噪声。外力触发法更干净，但只能测点数、不能连续跑几天。实战里两个都要做，数字对得上才可信。

读直方图先看尾部，不看峰值。峰值告诉你常态，尾部告诉你噩梦。-h800 那种参数的意义就在于把注意力引到尾部分布上：如果 800 微秒的桶里还有计数，说明系统出现过远超标称的延迟，得去查是什么打断了它。具体数值取决于硬件与配置，本文没有实测数据；第十三章引用的是 Firefly 官方指南的实测记录，只在它标明的芯片与配置下成立，不可外推。

cyclictest 的正确用法 #

threads 选项（-t）用于指定 Cyclictest 检测延迟时使用的测量线程数；亲和性选项（-a）指定线程必须在哪个 CPU 上执行。在系统上每个 CPU 只跑一个测量线程，是标准测试方案。这些选项对最小化 Cyclictest 自身对系统的影响很关键：如果两个或多个 Cyclictest 线程的预期执行时间重叠，测量结果就会受到它自己的测量线程所造成的延迟的影响。

要分析三个特定 CPU 的延迟，就用 -a 指定这些 CPU、用 -t 指定三个测量线程，同时确保收集度量数据的主 Cyclictest 线程没有运行在这三个被评估 CPU 之一上，主线程关联性用 taskset 设置。例如两个 CPU 的系统评估 CPU0 时，主线程该固定在 CPU1：主线程不是实时的，但它在被评估的 CPU 上执行会产生额外上下文切换，从而影响延迟。针对 CPU1 到 CPU3 的延时测试这样写：

bash
# CPU1 到 CPU3 跑实时测量，主线程跑在 CPU0 上
taskset -c 0 ./cyclictest -t3 -p99 -a 1-3

taskset 还能保证系统上运行的其他程序不影响隔离 CPU 上的延迟。比如启动 top 查看线程并固定到 CPU0：

bash
taskset --cpu 0 top -H -p PID
# top 打开后点 f 键，光标移到 P 选项，空格选中，点 q 键退出，
# 就能看到实时线程在哪些 CPU 上运行

策略一：抑制控制台消息、禁用内存过度使用 #

bash
# 用内核参数 quiet 启动内核，或者在启动之后抑制控制台输出
echo 1 > /proc/sys/kernel/printk

# 禁用内存过度使用，避免 Out-of-Memory Killer 产生的延迟
echo 2 > /proc/sys/vm/overcommit_memory

两条都在砍长尾。控制台打印在串口上是同步阻塞的，一次 printk 能锁住几十毫秒；OOM Killer 一旦被触发，回收路径上的延迟完全不可控。

策略二：不上桌面，或用轻量窗口管理器 #

为了更好的实时性，不建议使用带桌面的系统，因为这会为 CPU 延迟带来很大挑战。建议用 minimal ubuntu、自己的 QT 程序等。356x 的 rt 固件默认不使用桌面，而是用窗口管理器 weston，显示协议是 Wayland。需要 X11 环境的话，可以手动切换：

bash
sudo set_display_server x11
reboot
# sudo set_display_server weston 可再次切换回 weston，重启生效

切换到 X11 环境默认使用桌面。要用轻量级窗口管理器，在 /etc/lightdm/lightdm.conf 指定 session 使用 openbox：

bash
cat /etc/lightdm/lightdm.conf.d/20-autologin.conf
[Seat:*]
user-session=openbox
autologin-user=firefly

若不用登录管理器启动 X 显示服务，可以用 xinit 手动启动 Xorg。执行 xinit 和 startx 时，它们会寻找 ~/.xinitrc 作为 shell 脚本运行，以启动客户端程序；若 ~/.xinitrc 不存在，startx 会运行默认的 /etc/X11/xinit/xinitrc（默认的 xinitrc 启动一个 Twm、xorg-xclock 和 Xterm 环境）。先关掉 lightdm 服务：

bash
systemctl disable lightdm

然后用 startx 启动自己的程序。也可以改默认 startx 指定的 client 的 xinitrc 文件，默认会运行 Xorg：

bash
vim /etc/X11/xinit/xinitrc

sh

# /etc/X11/xinit/xinitrc
#
# global xinitrc file, used by all X sessions started by xinit (startx)

# invoke global X session script
#. /etc/X11/Xsession
#chromium --window-size=1920,1080

策略三：绑定核心 #

实时要求高的事件固定到某个核心上处理，系统及其它实时要求不高的事件集中到一个核心上处理。特定的中断、实时程序等都可以用专门的核心为它们服务。rt 应用可以由特定核心处理，把它绑定到 CPU3。

中断绑定核心：ARM 把所有外设中断全部交给 CPU0 处理，对于重要的中断，可以在系统启动之后把中断绑定到其他核心。例如把 eth0 中断绑定到 CPU2：

bash
root@firefly:~# cat /proc/interrupts | grep  eth0
 38:   28600296          0          0          0     GICv3  64 Level     eth0
 39:          0          0          0          0     GICv3  61 Level     eth0

root@firefly:~# cat /proc/irq/38/smp_affinity_list
0-3

root@firefly:~# echo 2 > /proc/irq/38/smp_affinity_list

root@firefly:~# cat /proc/irq/38/smp_affinity_list
2
root@firefly:~# cat /proc/interrupts | grep  eth0
 38:   29009292          0      52859          0     GICv3  64 Level     eth0
 39:          0          0          0          0     GICv3  61 Level     eth0

这段输出里能看到效果：改亲和性之前 CPU0 独自吃满 28600296 次中断，改完之后 CPU2 上开始出现 52859 次计数。中断从 CPU0 挪走了，实时任务才有机会独占一个核。

策略四：SMP + AMP 方案 #

实时要求更高的可以用 AMP 方案，达到更好的实时控制。rk3568 支持 AMP（非对称多核架构），可以定制某些核心跑定制的系统。比如 0～2 核心跑 kernel，3 核心跑 RT-Thread；支持 Linux（Kernel-4.19、rt-kernel-4.19）、Baremetal（HAL）、RTOS（RT-Thread）组合的 AMP 构建形式，可任意搭配。不同内核之间可以用核间通信来交互信息。

四条策略的关系：

策略 手段 影响层面 成本
砍干扰源 printk、overcommit、桌面 全局长尾 低，改几个 sysctl
绑核 任务亲和、中断亲和 局部确定性 低，但要先规划核分配
隔离核 从 SMP 平衡与调度中剔除 最强的一档确定性 中，要改启动参数
AMP 拆核、物理隔离 架构级隔离 高，等于两套系统

从实测数据看，前三条叠加已经能把最大延迟压到几十微秒量级（rk3588 隔离核 3us）。要到更硬的保证，就得走 AMP。

十四、实时系统的常见陷阱 #

陷阱 表现 怎么破
只看平均值 报告漂亮，现场偶发撞机 只认最大延迟与尾部分布
在实时任务里调 Linux 系统调用 Xenomai 掉回 Linux 域，实时性瞬间消失 实时路径上禁用 Linux 调用，需要时用非实时线程代理
忽略临界段长度 优先级继承救不了长临界段 临界段压缩到最短，不在里面做 IO 与内存分配
缺页与内存分配 运行期第一次分配触发长延迟 预分配、锁内存、-m 锁页测试
用 1000 的 tick 做微秒级延时 延时被量化到 1ms 用高精度定时器，或用 tickless
忘记关闭调试与日志 一次 printk 就是一次大抖动 echo 1 > /proc/sys/kernel/printk
隔离核上还跑别的 隔离失效，延迟回到普通核水平 检查中断亲和与任务亲和，隔离核只跑实时任务
测量程序污染测量 自己测自己，数字好看但不真 测量线程绑到非评估核，或外力触发法
用单次测试下结论 跑 10 分钟没超期就以为稳了 跑够时长，覆盖各种压力场景
动态优先级用满 最坏情况无法分析 关键任务用静态优先级

第一条最要命也最常见。实时系统的验收标准写在「最坏」上，不在「平均」上。第三条和第六条是纯工程习惯，却是长尾的主要来源：你在实时路径上做一次 malloc、打一条调试日志，前面所有的隔离与绑核工作全都白做。

十五、易错点速查 #

易错点 正确做法
把「快」当「实时」 实时是延迟上界可控，看最坏值
认为硬实时能靠调参调出来 硬实时要在内核设计层面保证
分不清硬实时与软实时的判据 看超期后果：结果失效就是硬实时
改了内核却用通用发行版内核验证 实时结果只对实际跑的内核与配置成立
以为高优先级任务一定先跑 有优先级反转，共享资源会翻盘
只加优先级继承就放心了 继承链要短，临界段要更短
把 OS_TICKS 随手改成 10000 调度开销上升，延时计算还会变难
用 vTaskDelay 的字面量跨平台移植 滴答值变了延时含义就变，用毫秒换算宏
测试只用 stress 一种压力 网络、GPU 压力下的尾延迟不一样，要混着造
cyclictest 主线程和被评估核同核 用 taskset -c 把主线程挪到别的核
隔离核后仍受 SMP 负载均衡影响 隔离要同时从 SMP 平衡与调度里剔除
在 Xenomai 实时任务里做文件 IO IO 会切回 Linux 域，实时保证丢失
Cobalt 与 Mercury 混着配 编译期二选一，选型定下就别来回换
拿本文没实测的数据当自己系统的指标 具体数值取决于硬件与配置，必须自己测

最后一条留给自己：这套流程跑下来，你会拿到一堆数字，那些数字只属于你测的那块板子和那个内核配置。换块板、换个内核版本、加个驱动，全部要重测。
