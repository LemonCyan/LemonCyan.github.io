一、互斥锁解决不了的问题 #

互斥锁回答的是「同一时刻谁可以进」，它不回答「我该等到什么时候」。

把一个消费者放到空队列上，只给 mutex，你只能这么写：

c
while (1) {
    pthread_mutex_lock(&mtx);
    if (queue_empty()) {
        pthread_mutex_unlock(&mtx);
        continue;              /* 队列还是空的，转头再问一遍 */
    }
    item = queue_pop();
    pthread_mutex_unlock(&mtx);
    handle(item);
}

这段代码没有数据竞争，但它在一个核上空转。队列空多久，它就烧多久 CPU。补一句 sleep(1) 能压住占用，代价是延迟抬到最多一秒，数据密集时又在白等。

形状不对的地方在这：线程想知道的是「数据来了吗」，而 mutex 只能回答「现在轮到你了吗」。真正缺的是两样东西，一个能数「现在有几个资源可用」的计数器，一个能表达「我在等某个条件成立」的等待队列。前者是信号量，后者是条件变量。两者都落在内核的等待队列上，都用睡眠代替轮询。

还有第三种情况更难缠：条件本身不是资源数量，而是一个组合判断，比如「队列不满而且没收到退出信号」。这种条件连计数器都表达不了，只能靠条件变量加一个自己维护的谓词。

下面按「计数器 → 等待队列」的顺序走。信号量先讲，因为它的语义最简单：一个数字，加和减。

二、信号量是什么：资源计数器 #

信号量就是带原子加减的整型计数器，加上一条等待队列。sem_t 里装的是当前可用资源的份数。

Dijkstra 给它定义了两个操作，字母来自荷兰语：P 是 proberen（尝试），V 是 verhogen（增加）。教材里也写成 wait/signal、down/up、acquire/release，指的都是同一对动作。

在教科书模型里，信号量结构长这样：

c
typedef struct {
    int value;           /* 剩余可用资源计数 */
    struct process *L;   /* 挂在该信号量上的等待队列 */
} semaphore;

P 操作先减再判，减成负数就阻塞：

c
void wait(semaphore S) {
    S.value--;                 /* 先记账，申请一份资源 */
    if (S.value < 0) {
        /* 资源不够，把自己挂到 S.L 上，让出 CPU */
        block(S.L);
    }
}

V 操作先加再判，值不大于零说明队列里还有人等着：

c
void signal(semaphore S) {
    S.value++;                 /* 归还一份资源 */
    if (S.value <= 0) {
        /* 还有被挂起的等待者，从 S.L 里放一个进就绪队列 */
        wakeup(S.L);
    }
}

注意这个模型里 value 会变成负数，负数的绝对值等于等待者数量。POSIX 的 sem_t 不这么做：它对外暴露的计数永远不小于 0，排队的线程藏在实现内部，你查不到有几个。写代码时按 POSIX 理解就行。

按取值分成两种：

类型 取值 表达的意思 常见用法
二进制信号量 只有 0 和 1 资源空闲 / 已被占用 当锁用，或当「就绪」的标志位
计数信号量 0 到 SEM_VALUE_MAX 当前还有几份可用 限并发数、数缓冲区空位、数已完成的任务

二进制信号量是计数信号量的特例。工程上把它单独拎出来讲，是因为它最容易被误当成互斥锁用，而这两者的所有权语义完全不同，第八章展开。SEM_VALUE_MAX 是上限，具体数值由实现给定，别在代码里写死。计数到上限还继续 sem_post，会拿到 EOVERFLOW。

三、匿名信号量与命名信号量 #

POSIX 信号量有两个来源，区别只在「这个 sem_t 对象活在哪」。

匿名信号量（也叫未命名信号量）就是一坨内存，你负责分配，sem_init 负责初始化：

c
sem_t sem;                 /* 全局变量、栈变量、堆上的一块，都行 */
sem_init(&sem, 0, 1);      /* 第 2 个参数 0：只在同进程的线程间共享 */
/* ... 用 ... */
sem_destroy(&sem);

它的生命周期跟内存一样：内存没了，信号量就没了。内核不登记它，不占 /dev/shm，也不怕进程崩掉留垃圾。

把 pshared 传非 0 时，它就能跨进程用，但前提是这块 sem_t 必须落在共享内存里（mmap 的 MAP_SHARED 区、POSIX 共享内存对象、System V 共享内存段）。放在普通全局变量上再传非 0，父子进程各改各的副本，同步立刻失效。POSIX 允许实现对非 0 的 pshared 返回 ENOSYS，Linux 上是支持的。

命名信号量由内核保管，靠一个名字找：

c
#include <fcntl.h>
#include <semaphore.h>

sem_t *sem = sem_open("/my_sem", O_CREAT, 0644, 1);   /* 名字必以 / 开头，且只有一层 */
if (sem == SEM_FAILED) {
    /* 处理错误 */
}

sem_wait(sem);

sem_close(sem);            /* 关掉本进程的引用 */
sem_unlink("/my_sem");     /* 名字从系统里摘掉，最后一个引用关掉后对象才消失 */

命名信号量在 Linux 上表现为 /dev/shm/sem.<name> 文件。它的特点是：进程退出不会自动清掉，名字一直挂着，计数停在最后的值。所以谁 sem_open 加上 O_CREAT，谁就该在退出路径上 sem_unlink，否则下次启动会拿到上次残留的计数。

两个容易踩的点：

  • sem_close 只减引用，不等于删除。删名字只能靠 sem_unlink。
  • sem_unlink 之后已经打开的 sem_t * 仍然可用，只是新进程再 sem_open 同名会拿到新对象。想在进程间「继承」一个信号量，必须在 unlink 之前 fork。

对照一张表：

维度 匿名信号量 命名信号量
声明与初始化 sem_t 变量 + sem_init sem_open 返回 sem_t *
存储位置 你的进程内存 内核管理的 IPC 对象，Linux 落 /dev/shm/sem.*
跨进程共享 需要放在共享内存里 天然支持，靠名字
生命周期 跟随内存 跟随名字，进程退出不消失
结束方式 sem_destroy sem_close + sem_unlink
命名冲突 不存在 存在，全局可见
典型场景 进程内线程同步，用得最多 无关进程之间协作

还有第三套接口在系统里活着：System V 信号量。它用 semget 建信号量集，semop 做加减，semctl 设初值和读状态。一次能建一组，操作是「加减一个整数」而不是零一，语义比 POSIX 粗，参数也费劲。新代码不用碰它，只用知道名字里带 sem 但它不是本篇讲的 sem_t。

标准版本：sem_init / sem_destroy / sem_wait / sem_post / sem_trywait / sem_getvalue / sem_open / sem_close / sem_unlink / sem_timedwait 全部由 POSIX.1-2001 定义。Linux 上 glibc 早期把这些放在 librt，编译要加 -lrt；glibc 2.34 起并入 libc，不再需要单独链接。

四、sem_init 与 sem_destroy #

原型就两行：

c
#include <semaphore.h>

int sem_init(sem_t *sem, int pshared, unsigned int value);
int sem_destroy(sem_t *sem);

两个函数成功返回 0，失败返回 -1 并设置 errno。

sem_init 的三个参数：

  • sem：指向一块 sizeof(sem_t) 大小的内存，必须是你的变量或你申请的内存，不能是空指针。
  • pshared：0 表示只在当前进程的线程之间共享；非 0 表示跨进程共享，此时这块内存必须落在共享内存里。
  • value：初始计数，也就是「一开始有几份资源」。大于 SEM_VALUE_MAX 会返回 EINVAL。

sem_destroy 只有一个参数，作用是把这个信号量作废。

用法骨架，注意初始化必须发生在创建线程之前：

c
#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>

sem_t slots;                    /* 限并发：最多 3 个同时在跑 */
sem_t done_flag;                /* 完成通知：初始 0，等的人先睡 */

static void *worker(void *arg)
{
    sem_wait(&slots);           /* 占一个并发位，占不到就睡 */
    do_work(arg);
    sem_post(&slots);           /* 让出并发位 */
    sem_post(&done_flag);       /* 报一次完成 */
    return NULL;
}

int main(void)
{
    pthread_t tid[3];

    if (sem_init(&slots, 0, 3) != 0 || sem_init(&done_flag, 0, 0) != 0) {
        perror("sem_init");
        return 1;
    }

    for (long i = 0; i < 3; i++) {
        pthread_create(&tid[i], NULL, worker, (void *)i);
    }
    for (int i = 0; i < 3; i++) {
        sem_wait(&done_flag);   /* 收满 3 次完成才往下走 */
    }
    for (int i = 0; i < 3; i++) {
        pthread_join(tid[i], NULL);
    }

    sem_destroy(&slots);
    sem_destroy(&done_flag);
    return 0;
}

编译要带线程库：

bash
gcc -Wall -O2 sem_demo.c -o sem_demo -pthread

sem_init 和 sem_destroy 的约束不多，但每一条踩了都很难查：

约束 违反后会怎样
不能对已经初始化的信号量再 sem_init 未定义行为，内部状态被覆盖，等待者失踪
要重新初始化，先 sem_destroy 再 sem_init 同上
sem_destroy 时不能有线程阻塞在它上面 未定义行为。安全做法是让使用方全部 join 完再销毁
pshared 非 0 时内存必须真共享 各进程操作各自的副本，同步形同不存在
匿名信号量不能跨进程用栈变量 同上，栈地址在 fork 后是各自私有拷贝

最常见的错法是在 worker 还在跑的时候销毁。程序往往不报错，直到某次调度把它撞成段错误。把销毁放在所有 pthread_join 之后，这条纪律能省掉一整类深夜排查。

五、sem_wait 与 sem_post #

这对函数是信号量的全部日常：

c
int sem_wait(sem_t *sem);   /* P 操作：取一份资源，取不到就阻塞 */
int sem_post(sem_t *sem);   /* V 操作：还一份资源，并唤醒一个等待者 */

成功返回 0，失败返回 -1 并设 errno。两者都是 POSIX.1-2001。

sem_wait 的行为拆开看：

  1. 计数大于 0，原子地减一，立刻返回。
  2. 计数等于 0，线程进入该信号量的等待队列睡眠，不占 CPU。
  3. 被 sem_post 唤醒后重新竞争，减一并返回。
  4. 睡眠期间被信号打断，返回 -1，errno 为 EINTR。

第 4 条要写进代码里。信号驱动的程序如果没有屏蔽信号，sem_wait 会带着 EINTR 回来，循环里判一下就重试，别把 EINTR 当成业务失败。

sem_post 的行为：

  1. 计数原子加一。
  2. 如果有线程阻塞在这个信号量上，唤醒其中一个。
  3. 计数已到 SEM_VALUE_MAX 再加，返回 -1，errno 为 EOVERFLOW。

这里有一条别的同步原语给不了的性质：sem_post 是异步信号安全的（async-signal-safe）。它可以在信号处理函数里直接调用，用来把「信号到了」这件事转交给普通线程处理。pthread_mutex_lock、pthread_cond_signal 都不在这个名单里，信号处理函数里调它们是等着出问题。

唤醒顺序没有承诺。POSIX 不保证先睡的先醒，也不保证按优先级醒。业务逻辑依赖「谁先等谁先得」就是埋雷，那个顺序在换机器、换负载之后会变。sem_post 也不在乎是谁在等，它只是把计数加一，这带出了信号量最大的特点：没有所有权。

刚提到的「完成通知」模式值得单独看一眼，它比轮询干净得多：

c
#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>
#include <unistd.h>

static sem_t ready;             /* 初始 0：谁先到谁睡 */
static int config_value;        /* 只由 worker 写，主线程等通知后读 */

static void *loader(void *arg)
{
    (void)arg;
    sleep(1);                   /* 模拟耗时初始化 */
    config_value = 42;          /* 先写好数据 */
    sem_post(&ready);           /* 再发通知，顺序不能反 */
    return NULL;
}

int main(void)
{
    pthread_t tid;

    sem_init(&ready, 0, 0);
    pthread_create(&tid, NULL, loader, NULL);

    sem_wait(&ready);           /* 睡到有人 post 为止，全程不占 CPU */
    printf("config = %d\n", config_value);

    pthread_join(tid, NULL);
    sem_destroy(&ready);
    return 0;
}

顺序是这套模式的关键：先写数据，再 sem_post。反过来写，等待方会读到还没写完的数据，而信号量本身的加减是完全正确的，你连从返回值上都看不出问题。可见性靠的是 sem_post 与 sem_wait 之间的同步关系，前提是你确实在 post 之前写完了数据。

六、sem_trywait 与 sem_timedwait #

sem_wait 只有「等到底」一种态度。另两个函数把等待方式变成可控的：

c
int sem_trywait(sem_t *sem);                                        /* POSIX.1-2001 */
int sem_timedwait(sem_t *sem, const struct timespec *abs_timeout);  /* POSIX.1-2001 */

sem_trywait 是非阻塞版。计数大于 0 就减一并返回 0；计数为 0 立刻返回 -1，errno 为 EAGAIN。它一次也不睡。

sem_timedwait 等一个绝对时间点。注意 abs_timeout 是绝对时间，不是相对时长：

  • struct timespec 的两个成员是 tv_sec（秒）和 tv_nsec（纳秒）。
  • 时间基准默认是 CLOCK_REALTIME，也就是墙上时钟。系统时间被人改一下，你的超时会提前或者延后。
  • 想按单调时钟算超时，改用 pthread_cond_timedwait 加 pthread_condattr_setclock 设成 CLOCK_MONOTONIC。
  • 超时返回 -1，errno 为 ETIMEDOUT。

绝对时间的写法，跳过相对时长的换算错误：

c
#include <time.h>
#include <errno.h>
#include <semaphore.h>

/* 最多等 ms 毫秒去拿一个资源 */
int acquire_timeout(sem_t *sem, long ms)
{
    struct timespec ts;

    if (clock_gettime(CLOCK_REALTIME, &ts) != 0) {
        return -1;
    }
    ts.tv_sec  += ms / 1000;
    ts.tv_nsec += (ms % 1000) * 1000000L;
    if (ts.tv_nsec >= 1000000000L) {     /* 纳秒进位，漏了这步会 EINVAL */
        ts.tv_sec  += 1;
        ts.tv_nsec -= 1000000000L;
    }

    while (sem_timedwait(sem, &ts) == -1) {
        if (errno == EINTR) {
            continue;                     /* 被信号打断，按同一个截止时间重试 */
        }
        return -1;                        /* ETIMEDOUT 或其他错误 */
    }
    return 0;
}

那个纳秒进位是最常见的错。tv_nsec 合法范围是 0 到 999999999，随手加出来的 1200000000 会让 sem_timedwait 返回 EINVAL，看起来像是超时设置没生效。

sem_getvalue 顺手也放这里：

c
int sem_getvalue(sem_t *sem, int *sval);   /* POSIX.1-2001 */

它把当前计数写进 *sval。Linux 上，如果此时有线程阻塞在 sem_wait，返回的值是 0，而不是教科书的负数。所以它不能用来数「有几个线程在等」。更重要的限制：这个值在你读到的下一刻就会过期，拿它做「先看一眼再决定要不要 wait」的决策，本质上还是把原子操作拆成了两个非原子步骤。它适合打日志、做监控指标，不适合做控制流。

三个函数的选择：

需求 用哪个 计数为 0 时的行为
必须拿到，等多久都行 sem_wait 阻塞睡眠，直到有人 post
拿不到就走别的路 sem_trywait 立即返回 EAGAIN
等一会儿，等不到就放弃 sem_timedwait 睡到截止时间，返回 ETIMEDOUT

超时之后接着 sem_post 补一次是不可行的，因为你根本没拿到资源，多 post 一次会把计数虚高。想清楚超时的意图：降级、返回忙、还是丢弃任务。

七、信号量的典型用法：生产者消费者 #

有限缓冲区的生产者消费者是信号量的教科书场景，两个信号量一人管一头：

  • empty：还能塞几个，初始等于缓冲区容量。
  • full：已经存了几个，初始 0。

生产者先 sem_wait(&empty) 占一个空位，写完 sem_post(&full)。消费者反过来。两个方向都不碰对方的计数器，天然分工。

下面是环形缓冲区的完整实现，配一把互斥锁保护读写指针：

c
#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>
#include <unistd.h>

#define BUFFER_SIZE 5

static int buffer[BUFFER_SIZE];
static int in = 0;
static int out = 0;

static sem_t empty;                   /* 空位数，初始 BUFFER_SIZE */
static sem_t full;                    /* 已填数，初始 0 */
static pthread_mutex_t mtx;           /* 保护缓冲区指针与数组 */

static void *producer(void *arg)
{
    int item = 1;
    while (1) {
        sleep(1);                     /* 1 秒生产一个 */
        sem_wait(&empty);             /* P(empty)：等一个空位 */
        pthread_mutex_lock(&mtx);
        buffer[in] = item;
        printf("[Producer] put %d at %d\n", item, in);
        in = (in + 1) % BUFFER_SIZE;
        item++;
        pthread_mutex_unlock(&mtx);
        sem_post(&full);              /* V(full)：满位加一 */
    }
    return NULL;
}

static void *consumer(void *arg)
{
    while (1) {
        sleep(2);                     /* 2 秒消费一个 */
        sem_wait(&full);              /* P(full)：等一个有数据的槽 */
        pthread_mutex_lock(&mtx);
        int item = buffer[out];
        printf("[Consumer] get %d from %d\n", item, out);
        out = (out + 1) % BUFFER_SIZE;
        pthread_mutex_unlock(&mtx);
        sem_post(&empty);             /* V(empty)：空位加一 */
    }
    return NULL;
}

int main(void)
{
    pthread_t p_tid, c_tid;

    sem_init(&empty, 0, BUFFER_SIZE);
    sem_init(&full, 0, 0);
    pthread_mutex_init(&mtx, NULL);

    pthread_create(&p_tid, NULL, producer, NULL);
    pthread_create(&c_tid, NULL, consumer, NULL);

    pthread_join(p_tid, NULL);
    pthread_join(c_tid, NULL);

    sem_destroy(&empty);
    sem_destroy(&full);
    pthread_mutex_destroy(&mtx);
    return 0;
}

这段代码看着对称，里面有三处顺序不能换。

第一处，sem_wait(&empty) 必须在 pthread_mutex_lock(&mtx) 之前。反过来的话，生产者拿着锁在 sem_wait 上睡过去，消费者要消费必须拿到锁，而锁被一个等空位的生产者占着。缓冲区满的时候这个生产者永远等不到空位，拿到锁的消费者也永远来不了。这叫在临界区里阻塞，是标准的死锁配方。

第二处，sem_post(&full) 放在 pthread_mutex_unlock(&mtx) 之后。代价是消费者被唤醒后会在锁上多等一小会儿，收益是不会出现「计数已经加了，数据还没写完」的窗口。

第三处，两个信号量的初值方向相反：empty 从满容量起，full 从 0 起。写反了程序不一定立刻崩，但语义整个颠倒，表现是缓冲区越用越乱。

同一套东西也可以只当一个「限并发阀门」用，不需要缓冲区：

c
sem_t gate;

sem_init(&gate, 0, 4);        /* 最多 4 个任务同时访问某个外部资源 */

void *task(void *arg)
{
    sem_wait(&gate);          /* 拿不到就在这里睡，不去抢 CPU */
    do_work(arg);
    sem_post(&gate);
    return NULL;
}

这种用法里 gate 不是数据的前后关系，它就是一个数数器：数的是「现在有几个人在里面」。用 mutex 干这件事只能限成 1 个。

八、信号量与互斥锁的差别 #

初学者最容易把二进制信号量当互斥锁用，因为「初值为 1，减到 0 就等」看起来完全一样。差别在所有权。

维度 互斥锁 pthread_mutex_t 信号量 sem_t
语义 所有权：谁加锁谁解锁 计数：谁都能 post，不认人
初始状态 未锁定 任意值，可以是 0、1、N
并发度 只能是 1 1 到 SEM_VALUE_MAX
归还操作 pthread_mutex_unlock，必须由持有者调 sem_post，任何线程都能调
谁在等 实现内部排队，可配优先级继承 实现内部排队，能查到的只有计数
能否用于多进程 需要 PTHREAD_PROCESS_SHARED 加共享内存 pshared 非 0 加共享内存
能否在信号处理函数里用 不能 sem_post 可以
典型用途 保护共享数据 限并发、数资源、跨线程/跨进程通知

所有权带来的差异比看上去大。互斥锁能检测出一类用错：释放一把别人持有的锁，配置了 PTHREAD_MUTEX_ERRORCHECK 时返回 EPERM。信号量没有这个概念，多 post 一次没有任何报错，只是计数虚高，然后某个线程永远等不到。

反过来说，信号量的「无主」也是它有用的地方。三个人要拆掉同一个任务，谁先干完谁 post 一次表示「我这边完事了」，用 mutex 根本表达不了，因为干活的不持有任何锁。

一句话的选择标准：保护一块共享数据就是 mutex；表达「现在还有几份资源」「已经完成了几件事」就是 semaphore；当锁用的二进制信号量不是不能用，是拿不到错误检查、拿不到优先级继承、也拿不到 robust 属性，没有理由这么干。

POSIX 也给互斥锁留了跨进程的路径，但要显式设属性：

c
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED);
/* 之后把 mutex 放进共享内存再用 pthread_mutex_init 初始化 */

信号量做这件事只要 sem_init(&sem, 1, n)，少一层配置，这是它在多进程场景里更顺手的原因。

九、条件变量是什么：等一个条件成立 #

信号量能数「几份」，数不了「什么状态」。条件变量专门补这块。

pthread_cond_t 本身不存任何值。它就是一个等待队列的把手：线程挂上去，别人把它叫醒。条件成立与否，存在你的普通变量里，不存在条件变量里。

pthread_cond_t 提供六个操作，返回 0 表示成功，失败返回错误码而不是设 errno：

c
int pthread_cond_init(pthread_cond_t *cond, const pthread_condattr_t *attr);
int pthread_cond_destroy(pthread_cond_t *cond);
int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
int pthread_cond_timedwait(pthread_cond_t *cond, pthread_mutex_t *mutex,
                           const struct timespec *abs_timeout);
int pthread_cond_signal(pthread_cond_t *cond);
int pthread_cond_broadcast(pthread_cond_t *cond);

wait 类函数失败返回时锁仍在手上，失败路径也要解锁。

静态初始化省掉一次 init：

c
pthread_cond_t  cond = PTHREAD_COND_INITIALIZER;
pthread_mutex_t mtx  = PTHREAD_MUTEX_INITIALIZER;

核心模式围绕同一个谓词，等待侧和通知侧各一半：

c
/* 等待侧：谓词不成立就睡，醒来重新判断 */
pthread_mutex_lock(&mtx);
while (!condition_true()) {
    pthread_cond_wait(&cond, &mtx);
}
take_action();                         /* 此处谓词成立，且锁在手 */
pthread_mutex_unlock(&mtx);

/* 通知侧：先改状态，再叫醒 */
pthread_mutex_lock(&mtx);
make_condition_true();
pthread_cond_signal(&cond);
pthread_mutex_unlock(&mtx);

这套模式里有三条纪律，每条都对应一类真实故障：

  1. 条件必须是真的由你维护的共享变量，不是「信号量里的计数」。条件变量不知道你的谓词是什么。
  2. 检查条件时必须在持有互斥锁的状态下。裸读共享变量，读到的是正在被写的中间值。
  3. 改状态的那个线程，改完要发通知，而且通知可以在持锁时发，也可以在解锁后发。持锁时发更稳妥，代价是被唤醒的线程醒来先卡在锁上。

条件变量的语义边界值得说清楚：pthread_cond_signal 只是「把至少一个等待者标记成可继续执行」，它不保存。如果此刻没人在等，这次 signal 直接蒸发，不会留下一个「欠着一次唤醒」的记账。信号量不一样，sem_post 在没人等的时候把计数加了 1，后来的线程立刻能取到。这就是条件变量必须配一个自己的谓词变量的根本原因：

c
/* 错：signal 早于 wait，唤醒丢失，等待方永远睡下去 */
void *waiter(void *arg) {
    pthread_mutex_lock(&m);
    pthread_cond_wait(&c, &m);       /* 永远等不到 */
    pthread_mutex_unlock(&m);
    return NULL;
}

/* 对：用一个标志位记住「事情已经发生过」 */
int happened = 0;

void *producer2(void *arg) {
    pthread_mutex_lock(&m);
    happened = 1;                    /* 状态记在变量里，不指望条件变量记账 */
    pthread_cond_signal(&c);
    pthread_mutex_unlock(&m);
    return NULL;
}

void *consumer2(void *arg) {
    pthread_mutex_lock(&m);
    while (!happened) {
        pthread_cond_wait(&c, &m);   /* signal 先到也没事，happened 已经是 1 */
    }
    pthread_mutex_unlock(&m);
    return NULL;
}

happened 这个变量就是状态本身，cond 只是让等待者能睡着的工具。所有的正确性都压在 happened 上，这个认识建立起来之后，条件变量剩下的坑都好绕。

十、pthread_cond_wait 为什么必须配互斥锁 #

这个问题经常被反问：既然 pthread_cond_wait 会解锁，我为什么不能不加锁直接等？

因为解锁和睡眠必须是同一个原子动作，而这只有 mutex 能提供。

pthread_cond_wait(&cond, &mutex) 内部的四个动作：

  1. 把当前线程挂到 cond 的等待队列上。
  2. 原子地释放 mutex。
  3. 睡眠，让出 CPU。
  4. 被唤醒后，先把 mutex 重新加回来，再从函数返回。

第 1 步和第 2 步之间不能有窗口。假定没有互斥锁，线程自己先判断 if (empty) sleep()，然后才挂到等待队列上，中间这一段时间里生产者正好跑完「填数据 + signal」。signal 发出时等待队列还是空的，事件丢了，随后这个线程才挂上去，一直睡到程序结束。这就是丢失唤醒（lost wakeup）。

拿互斥锁之后，这个窗口被堵住了。生产者要发 signal，它必须先在同一个 mutex 上加锁，而消费者在挂入队列并释锁之前一直持有这把锁。于是两种顺序都安全：

  • 消费者先挂上队列并释放锁，生产者随后拿锁、改状态、signal，唤醒送达。
  • 生产者先拿锁、改状态、signal、解锁；消费者随后拿锁，一检查谓词发现已经成立，压根不进等待循环。

第 4 步同样重要。醒来时线程重新持有 mutex，所以 pthread_cond_wait 返回之后，它看到的共享状态是一致的，可以放心地再判断一次谓词。没有这把锁，返回那一刻的状态也许正在被别人改。

从调用者的角度看，有两件事必须记住：

  • 传进去的 mutex 必须是当前线程已经持有的，否则行为未定义。
  • 函数返回时，mutex 又回到持有状态，你欠它一次 unlock。醒来那一刻也会出现没有任何业务原因的情况（下一章的虚假唤醒），所以判断必须用 while 而不是 if。

最后一个常被忽略的点：条件变量与 mutex 是一对多的关系。多个条件变量共用一把 mutex 完全正常，同一个锁保护的几个不同谓词，各自挂一个 cond。反过来，一个条件变量配多把不同的 mutex，是错的。pthread_cond_wait 只认你这次传进来的那把，别的等待者传了另一把，唤醒逻辑就跟锁脱钩了。

十一、signal 与 broadcast 的区别 #

两个唤醒函数，一个叫一个或多个，一个叫全部：

c
int pthread_cond_signal(pthread_cond_t *cond);      /* 至少唤醒一个等待者 */
int pthread_cond_broadcast(pthread_cond_t *cond);   /* 唤醒全部等待者 */
维度 pthread_cond_signal pthread_cond_broadcast
唤醒范围 至少一个等待线程 该 cond 上全部等待线程
无等待者时 空操作，事件不记账 空操作，事件不记账
CPU 开销 小，只有一个线程参与调度 大，全部线程醒来抢同一把锁
适用条件 一次事件能满足其中一个等待者 一次事件能满足多个，或无法判断满足谁
典型场景 队列放进一个元素 状态整体翻转、多个等待者的条件同时成立

分界线在这里：一次状态改变，能让几个等待者通过谓词检查？

典型的生产者消费者：放进一个元素，最多让一个消费者拿到。用 signal 就够了。用 broadcast 也不会错，只是会出现「一堆消费者被叫醒，抢锁，第一个拿走，其余发现又空了，回去接着睡」，白跑一趟。这叫惊群（thundering herd）。线程少的时候感觉不出来，线程多、事件密的时候，这些空转的唤醒是实打实的开销。

反过来看另一种情况：多个等待者在等「初始化完成」这个条件。初始化一完成，所有等待者都能往下走。这时用 signal 就是 bug，因为只放行一个，其余的继续睡着，而这个事件再也不会发生第二次。

c
int inited = 0;

/* 一次完成、多人受益：必须 broadcast */
void *init_once(void *arg)
{
    pthread_mutex_lock(&m);
    do_init();
    inited = 1;
    pthread_cond_broadcast(&c);      /* 用 signal 会让其余等待者永久睡死 */
    pthread_mutex_unlock(&m);
    return NULL;
}

还有一类场景要注意：等的是不同谓词，却挂在同一个 cond 上。比如「队列非空」和「收到退出请求」共用一个 cond，signal 只是随机叫一个，叫到那个等退出请求的线程，写入方那边的事件就没人处理。被叫醒的线程检查谓词不成立，回去继续睡，这一次唤醒就此消耗掉。可以换两个 cond 分开放，也可以一律 broadcast 加谓词判断，后者简单但更耗。标准做法是给每个谓词配自己的 cond，让唤醒精度对上谓词。

signal 在实现上允许一次唤醒多于一个线程，POSIX 的措辞是「至少一个」。所以哪怕你只想要一个，也不能指望「只醒一个」这件事成立。while 循环在这里再次兜底。

这两个函数在调用时不要求持有 mutex。持锁发和释锁后发都合法，只是持锁发更可预测，唤醒方和等待方不会出现「通知已经发出，但状态还没提交」的错觉。

十二、虚假唤醒与循环判断 #

pthread_cond_wait 返回，不等于「我要等的事情发生了」。它有三种返回方式：

  1. 别的线程调了 signal 或 broadcast。
  2. 硬件信号打断了睡眠，实现选择直接返回。
  3. 内核或库内部唤醒，没有任何业务原因。

第 2、3 条合称虚假唤醒（spurious wakeup）。规范允许它出现，所以代码必须假设它会出现。

防它的办法就是把 if 换成 while：

c
/* 错：假醒来一次，直接往下走，读到的是空队列 */
pthread_mutex_lock(&mtx);
if (queue_empty()) {
    pthread_cond_wait(&cond, &mtx);
}
item = queue_pop();              /* 队列仍然空，读到垃圾 */
pthread_mutex_unlock(&mtx);

/* 对：醒来之后重新验证谓词 */
pthread_mutex_lock(&mtx);
while (queue_empty()) {
    pthread_cond_wait(&cond, &mtx);
}
item = queue_pop();
pthread_mutex_unlock(&mtx);

while 做的是「醒来后重新检查条件」，假醒来的线程发现条件不成立，重新挂回等待队列，代价是一次多余的循环。用 if 就少了这一次检查，直接把判断权交给了不知情的唤醒。第二个理由在多个线程抢同一把锁时出现：第一个抢到的人拿走资源，后面的人进临界区时条件已经变了，while 让它们退回去接着等，if 让它们误以为拿到了。使用 broadcast 时这种情形是必然的。

写成循环时，谓词要自己再读一遍共享变量。别把上次判断的结果缓存进局部变量，那个值在睡着期间会过期，醒来后必须重新算。

条件本身可以复杂，但必须是在持有锁时能算出来的判断：

c
pthread_mutex_lock(&mtx);
while (queue_count == 0 && !quit_requested) {
    pthread_cond_wait(&cond, &mtx);
}
if (queue_count == 0 && quit_requested) {
    pthread_mutex_unlock(&mtx);
    break;                        /* 退出路径一样要清锁 */
}
item = queue_pop();
pthread_mutex_unlock(&mtx);

谓词里包了退出标志，这是服务端线程最常用的写法：一个 cond 管两种事件，醒来先看退出，再看数据。

十三、条件变量的典型用法 #

最基本的形态是单生产者单消费者：

c
#include <pthread.h>
#include <unistd.h>

static pthread_mutex_t mtx  = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  cond = PTHREAD_COND_INITIALIZER;
static int storage = 0;                 /* 仓库里现有的件数 */

static void *consumer(void *arg)
{
    while (1) {
        pthread_mutex_lock(&mtx);
        while (storage == 0) {          /* 用 while 不用 if，防虚假唤醒 */
            pthread_cond_wait(&cond, &mtx);   /* 解锁挂起，醒来自动重锁 */
        }
        storage--;
        pthread_mutex_unlock(&mtx);
        sleep(2);                       /* 消费慢一点 */
    }
    return NULL;
}

static void *producer(void *arg)
{
    while (1) {
        sleep(1);                       /* 生产快一点 */
        pthread_mutex_lock(&mtx);
        storage++;
        pthread_cond_signal(&cond);     /* 叫醒一个消费者 */
        pthread_mutex_unlock(&mtx);
    }
    return NULL;
}

int main(void)
{
    pthread_t t1, t2;
    pthread_create(&t1, NULL, consumer, NULL);
    pthread_create(&t2, NULL, producer, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    return 0;
}

两个 while(1) 里没有退出路径，pthread_join 永远不会返回。示例为了把骨架压短省掉了退出条件，真实代码里必须有。

带上限的版本，两个谓词分两个 cond：

c
#define CAP 8

static int q_count = 0;
static pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;
static pthread_cond_t not_full  = PTHREAD_COND_INITIALIZER;

void *bounded_producer(void *arg)
{
    pthread_mutex_lock(&mtx);
    while (q_count == CAP) {
        pthread_cond_wait(&not_full, &mtx);    /* 满就等空位 */
    }
    q_count++;
    pthread_cond_signal(&not_empty);           /* 只有「非空」这件事变了 */
    pthread_mutex_unlock(&mtx);
    return NULL;
}

void *bounded_consumer(void *arg)
{
    pthread_mutex_lock(&mtx);
    while (q_count == 0) {
        pthread_cond_wait(&not_empty, &mtx);   /* 空就等数据 */
    }
    q_count--;
    pthread_cond_signal(&not_full);            /* 只有「不满」这件事变了 */
    pthread_mutex_unlock(&mtx);
    return NULL;
}

两侧各 signal 一个对应谓词的线程，唤醒精度最高。第三种形态是一次广播放行全部等待者，等的是「可以开工了」：

c
static int started = 0;

void *wait_start(void *arg)
{
    pthread_mutex_lock(&mtx);
    while (!started) {
        pthread_cond_wait(&cond, &mtx);
    }
    pthread_mutex_unlock(&mtx);
    do_work(arg);
    return NULL;
}

void *controller(void *arg)
{
    sleep(1);
    pthread_mutex_lock(&mtx);
    started = 1;
    pthread_cond_broadcast(&cond);      /* 所有等开工的线程都放行 */
    pthread_mutex_unlock(&mtx);
    return NULL;
}

第四种：带超时的等待，超时就退出去检查别的状态。pthread_cond_timedwait 的 abs_timeout 同样是绝对时间，纳秒进位照样要处理，ETIMEDOUT 是预计内的返回而不是错误。

c
struct timespec ts;
clock_gettime(CLOCK_REALTIME, &ts);
ts.tv_sec += 2;                          /* 最多等 2 秒 */

pthread_mutex_lock(&mtx);
while (q_count == 0) {
    if (pthread_cond_timedwait(&cond, &mtx, &ts) == ETIMEDOUT) {
        break;                           /* 超时，跳出等待去处理超时逻辑 */
    }
}

十四、三种机制怎么选 #

到这里手上有三件工具：互斥锁、信号量、条件变量。选错不难发现，症状是 CPU 占用或者挂死；选对也不难，看一句话：这次同步要表达的是什么。

判断项 互斥锁 信号量 条件变量
解决的问题 同一时刻只能一个人进 还有几份资源可用 等一个条件成立
有状态吗 有，锁/未锁 有，整数计数 没有，条件在你自己的变量里
有所有权吗 有 无 无
能限并发数吗 只能限成 1 任意 N 不能
唤醒落空会怎样 不适用 计数留着，后来者受益 通知蒸发，等待方会一直睡下去
需要配别的机制吗 单独用 单独用，常再配一把锁 必须配互斥锁
阻塞时占 CPU 吗 不占 不占 不占

再按场景对一遍：

  • 保护一个全局链表、一个计数器、一段共享内存区域的读改写。要互斥锁。信号量能替，但没好处。
  • 限制同时访问某个外部服务的并发数，比如最多 4 个连接。要信号量，初始值 4。mutex 做不到 N。
  • 线程池里「手上有多少个待处理任务」，主线程投递、worker 取走。要信号量，sem_post 投递、sem_wait 取走，顺带把任务数当长度用。
  • 等待「队列非空」这种复合条件，尤其是还要同时判断退出标志。要条件变量，因为谓词可以是任意布尔表达式。
  • 等待「某件事发生过一次」，之后所有线程都该放行。要条件变量加 broadcast，或者把信号量初值设成 0、让 N 个线程各 sem_wait 一次。
  • 跨进程同步。信号量最省事（pshared 非 0 或命名信号量），互斥锁要配 PTHREAD_PROCESS_SHARED，条件变量同样要这个属性。
  • 信号处理函数里通知线程。只有 sem_post 能用。

两个实现层面的补充，能解释一些「看起来同等」的选择为什么有差别：

  • 条件变量的唤醒是「把线程从等待队列移到就绪队列」，不记账。信号量的 post 是「计数加一」，记账。前者要求你自己维护状态，后者天然带状态。
  • 信号量配一把锁的组合，临界区里只有数据操作，等资源在临界区外。条件变量的组合，等条件本身就在临界区里（pthread_cond_wait 帮你临时放锁）。结构不一样，出错时的症状也不一样：前者容易在锁内 sem_wait 把自己锁死，后者容易把 while 写成 if。

最后一条经验：能用条件变量表达的东西，不用「信号量 + 轮询」凑。用信号量表达不了的条件，硬凑出来的一定带着一个定时器和一段 usleep。

十五、易错点速查 #

编号 症状 原因 修法
1 程序空转，CPU 打满 用 mutex 加轮询等条件 换条件变量，或信号量
2 等待线程永久睡死 signal 早于 wait，通知丢了 用共享变量记住状态，while 检查谓词
3 醒来后读到空数据 if 代替了 while，遇上假唤醒 判断条件一律用 while
4 偶发读到旧值、脏数据 改状态的顺序写在 post / signal 之后 先改数据，再通知
5 死锁，且都卡在 sem_wait 在持有互斥锁时调用 sem_wait 把等资源的操作挪到加锁之前
6 计数越用越虚高 超时或失败路径也 sem_post 了 只有真拿到资源才 post
7 段错误，位置飘忽 sem_destroy 时还有线程阻塞在它上面 销毁放到所有 join 之后
8 父子进程同步失效 pshared 设了非 0，但内存不是共享的 sem_t 放进 MAP_SHARED 共享内存
9 命名信号量初值不对 上次进程退出没清理，残留了旧计数 sem_open 后 sem_unlink，或先处理残留
10 sem_timedwait 返回 EINVAL tv_nsec 加出界没进位 满 1000000000 就进位到 tv_sec
11 超时时间不准，忽长忽短 CLOCK_REALTIME 被系统时间调整影响 换单调时钟，或用 pthread_cond_timedwait 配 CLOCK_MONOTONIC
12 sem_wait 莫名返回 -1 被信号打断，errno 是 EINTR 循环里判 EINTR 就重试
13 该醒的线程没醒 多个谓词共用一个 cond，signal 叫错了人 每个谓词配自己的 cond，或改 broadcast
14 唤醒后卡在锁上很久 持锁期间发了通知 通知移到 unlock 之后，或压缩临界区
15 信号处理函数里崩溃 在里面用了 pthread_mutex_lock / pthread_cond_signal 只用 sem_post，其余交给普通线程
16 显式初始化后行为异常 对已初始化的对象又 sem_init 一次 先 destroy 再 init，或改用静态初始化
17 程序在退出时崩溃 主线程已退出，后台线程还在用锁 join 全部线程，再销毁同步对象

配套的一组检查动作，写完之后自己过一遍：

  • 每一个 pthread_cond_wait 外面是不是 while，不是 if。
  • 每一个 pthread_cond_wait 传的 mutex，是不是在上一步 lock 过的。
  • 每一次 post / signal 之前，对应的数据是不是已经写好。
  • 每一个 sem_wait 是不是都在互斥锁外面。
  • 每一个 sem_init 都有一个配对的 sem_destroy，且位置在所有 join 之后。
  • 每一条失败路径，是不是都解锁了。

这六条过完，绝大多数坑就避开了，剩下的问题基本都在性能层面。三件工具的分工很干净：互斥锁管「谁能进」，信号量管「还有几份」，条件变量管「等到什么时候」。把每处等待归到这三类里，代码会变得好读，也会变得难写错。
