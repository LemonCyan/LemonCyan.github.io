一、futex 是什么：快在哪 #

futex 是 Fast Userspace muTEX 的缩写，由 Rusty Russell、Hubertus Franke、Mathew Kirkwood 在 Linux 2.5.7 引入。名字里塞了 mutex，用途却是通用同步底座：互斥锁、读写锁、条件变量都能在它上面搭出来，pthread_mutex、pthread_cond、sem_* 底下共用的正是这一层。

它只有两半。

一半 位置 内容
内核侧 内核空间 等待队列：hash bucket 加挂在上面的等待任务链表
用户侧 你的进程 一个 32-bit 的 futex word，所有平台都是 32 位，64 位平台上也是 32 位

「快」不是修辞。没有竞争时，持锁是一条 cmpxchg，释放是一条 xchg，系统调用一次都不发。只有出现竞争、需要把线程从 runqueue 上摘下来时，才走系统调用。

场景 用户态动作 系统调用 开销量级
无竞争获取 一条原子 CAS 0 次 十几纳秒，等于一次缓存行独占
无竞争释放 一条原子交换 0 次 同上
有竞争获取 CAS 失败，标记等待位 1 次 FUTEX_WAIT 微秒级，含两次上下文切换
有竞争释放 原子交换发现等待位 1 次 FUTEX_WAKE 微秒级

把一把锁用裸 futex 写出来，只有三十行：

c
/* 状态编码：0 = 空闲，1 = 已锁，2 = 已锁且有等待者 */
#include <linux/futex.h>
#include <sys/syscall.h>
#include <unistd.h>

static int futex_lock(int *uaddr)
{
    int c = 0;

    /* 快路径：0 -> 1，一条原子指令，不进内核 */
    if (__atomic_compare_exchange_n(uaddr, &c, 1, 0,
                                    __ATOMIC_ACQUIRE, __ATOMIC_RELAXED))
        return 0;

    /* 慢路径：先把状态升级成 2，再进内核睡 */
    do {
        if (c == 2 || __atomic_exchange_n(uaddr, 2, __ATOMIC_ACQUIRE) != 0)
            syscall(SYS_futex, uaddr, FUTEX_WAIT, 2, NULL, NULL, 0);
        c = 0;
    } while (!__atomic_compare_exchange_n(uaddr, &c, 2, 0,
                                          __ATOMIC_ACQUIRE, __ATOMIC_RELAXED));
    return 0;
}

static int futex_unlock(int *uaddr)
{
    if (__atomic_exchange_n(uaddr, 0, __ATOMIC_RELEASE) == 2)
        syscall(SYS_futex, uaddr, FUTEX_WAKE, 1, NULL, NULL, 0);
    return 0;
}

状态码 2 是关键。它把「有人正在等」这件事写进了用户态的一个 bit 里，于是释放路径不看内核、不问队列，只读一个整数就知道要不要发唤醒。少这一次系统调用，就是无竞争路径的全部收益。

二、为什么需要内核参与 #

先回答一个反问：纯用户态自旋锁不够用吗。

不够。等待线程占着 CPU 反复读那个 word，持锁线程被抢占或者优先级更低时，等待者把整段时间片烧在缓存行上。线程一多，机器全在做无用功。

要「不占 CPU 地等」，唯一办法是把线程从 runqueue 摘下来，状态改成睡眠，等条件满足再放回去。调度器归内核管，用户态做不到这件事。唤醒同理，让一个睡着的线程重新可运行，只有内核能改它的状态并重新入队。

结论很硬：同步原语里「挂起自己」和「唤醒别人」这两个动作必须穿过内核边界，其余动作不该穿。

方案 等待方式 无竞争开销 有竞争开销 适用
纯自旋锁 空转 一条 CAS 等待者烧满时间片，还会饿死 临界区只有几条指令、核数远多于线程数
纯内核锁 睡眠 两次系统调用 两次系统调用 临界区很长、竞争激烈
futex 睡在内核队列里 一条 CAS，0 次系统调用 两次系统调用 绝大多数用户态同步原语

还有个必须解决的细节：丢唤醒。假如「检查条件」和「进入睡眠」是两个独立动作，在两者之间冒出来的唤醒就丢了，线程睡到进程退出都没人管。学科里管这现象叫 lost wakeup。

futex 的解法是把检查合并进系统调用。FUTEX_WAIT 带一个期望值 val，内核在持有 bucket 自旋锁的状态下比对 futex word 与 val，相等才把任务挂进队列，不等就立刻返回 EWOULDBLOCK。比对和入队在同一把锁的保护下完成，唤醒插不进来。

text
用户态: 原子检查 word == val  ──┐
                                │  这两步若分开，唤醒会掉进空隙
内核态: 挂入等待队列并睡眠    ──┘

futex 的做法：把上面两步并成一次系统调用，val 由内核复核

三、futex 的核心思想：用户态快路径 #

一句话说完：futex 只在你有阻塞风险的时候才进内核。

这句话拆成三条推论，后面每一章都在用。

第一，锁状态住在用户态内存里。futex word 就在你的进程地址空间中，读写它不经过任何系统调用，也不需要内核维护副本。

第二，系统调用自带条件判断。FUTEX_WAIT 不是「无条件睡」，而是「如果这个 word 还等于 val，就睡」。内核先复核再决定，用户态和内核之间不存在判断与动作的缝隙。

第三，FUTEX_WAKE 不交付锁，只交付 CPU 使用权。内核不维护「锁现在是否空闲」这种语义，它只知道某条队列上挂着哪些任务。被唤醒的线程回到用户态要重新做一次原子 CAS，抢不到就再睡回去。所以多唤醒几个不会错，只会浪费。

由谁维护 维护什么
用户态 锁的语义：谁持有、是否空闲、有没有等待者
内核态 等待关系：哪个 word 上挂了哪些任务、谁先醒

决策流程就两条分支：

text
持锁尝试
  ├─ CAS 成功 ──────────────► 返回。0 次系统调用
  └─ CAS 失败
       ├─ 置等待标志再 CAS ──► 还是失败
       └─ FUTEX_WAIT(word, val) ─► 睡
              └─ 被 FUTEX_WAKE 唤醒 ─► 回到 CAS 起点重试

注意最后那个回边。被唤醒不等于拿到锁，只是获得了重新竞争的机会。整套机制里没有「移交锁所有权」这回事，那是 PI futex 才做的额外工作。

四、futex 变量与等待队列 #

内核里的互斥锁，等待队列头可以直接嵌在 mutex 对象上，因为锁对象本身就是内核对象。futex 没有对应的内核锁对象，用户态那边只有一个 32 位整数，于是问题变成：怎么把一个用户态地址映射到内核的一条等待队列。

答案是哈希。内核建一张 futex hash 表，用 futex word 算出一个 key，再按 key 哈希到桶。

类型 三元组（hash key 的组成） 理由
process-private (current->mm, address, 0) word 只在一个进程内共享，用地址空间加虚拟地址足够定位
process-shared (inode->i_sequence, page->index, offset_within_page) word 在共享内存里（mmap 或 shmat），各进程虚拟地址不同、物理页相同，只能靠页来定位

算出 key 的函数是 get_futex_key。哈希表本体很短：

c
static struct {
    struct futex_hash_bucket *queues;
    unsigned long            hashsize;
} __futex_data;

启动时按 hashsize 建好一批桶，每个桶管一条链表，链上挂 key 哈希值相同的所有阻塞任务。桶的结构是这样的：

c
struct futex_hash_bucket {
    atomic_t waiters;          /* 该队列上阻塞的任务个数 */
    spinlock_t lock;           /* 保护这条队列的自旋锁 */
    struct plist_head chain;   /* 相同 hash key 的阻塞任务挂在这里 */
} ____cacheline_aligned_in_smp;

单个等待任务用 futex_q 描述，后面统一叫「futex 阻塞任务对象」：

c
struct futex_q {
    struct plist_node list;              /* 挂队列的节点，按优先级排序 */
    struct task_struct *task;            /* 等待在这个 futex word 上的任务 */
    spinlock_t *lock_ptr;                /* 保护队列操作的自旋锁 */
    union futex_key key;                 /* 算 hash key 用 */
    struct futex_pi_state *pi_state;     /* PI 相关：futex 的 pi-aware 由 rt mutex 代理 */
    struct rt_mutex_waiter *rt_waiter;   /* 阻塞在 rt mutex 上的任务描述 */
    union futex_key *requeue_pi_key;     /* 与 requeue-PI 相关 */
    u32 bitset;                          /* FUTEX_WAKE 时判断该不该唤醒它 */
} __randomize_layout;

有了这层结构，只要手里有一个 futex word，就能算 key、定位桶、找到链表。哈希碰撞由 key 的完全相等来兜底，比对逻辑在 match_futex 里，三元组全部相等才算同一条等待队列。

三点要知道的细节。

队列是 plist，即按优先级排序的链表。RT 线程优先级高的插队首，低的排队尾；CFS 任务不按优先级，走 FIFO 的公平策略。同一把锁上混着两种调度类时，插队顺序由这个字段决定。

waiters 计数是给唤醒路径用的快捷判断，避免在不必要的时候抓锁。

pi_state 和 rt_waiter 两个字段只在 PI futex 上用，normal futex 下是空的。它们的存在说明一件事：优先级继承那套东西不是 futex 自己实现的，而是把工作外包给了 rt mutex。

五、futex 的系统调用接口 #

glibc 不给 futex 提供包装函数，头文件只有常量定义，调用要自己走 syscall：

c
#include <linux/futex.h>
#include <sys/syscall.h>
#include <unistd.h>

int futex(int *uaddr, int futex_op, int val,
          const struct timespec *timeout,   /* 某些操作码下复用为 val2 */
          int *uaddr2, int val3);

参数看着简单，麻烦在复用。同一个 val，对 FUTEX_WAIT 是期望值，对 FUTEX_WAKE 是唤醒个数；同一个指针位置，对 FUTEX_WAIT 是超时，对 FUTEX_REQUEUE 是要转移的个数。这是为一个系统调用塞进十几种操作付的代价。

futex_op 本身是位域，拆两半用：

位 含义
低 7 位 操作码，最多支持 128 个 op code
其余高位 标志位，用来修饰操作码的行为
标志 作用
FUTEX_PRIVATE_FLAG 声明 word 仅在本进程内共享（process-private）。内核可以省掉跨进程的 inode 查找，key 直接用 (mm, addr) 算
FUTEX_CLOCK_REALTIME 指定超时基准。置位用 realtime clock，不置位用 monotonic clock

PRIVATE 这个标志值得单独说。决定 key 算法的是 word 的共享范围：只在一个进程内共享叫 process-private，跨进程共享叫 process-shared，后者必须是 mmap 的共享映射或 shmat 的共享内存。设对了能省一次 inode 查找，设错了就是错误唤醒或者睡死。pthread_mutex 默认的 PTHREAD_PROCESS_PRIVATE 属性对应的就是这条快路。

常用操作码：

操作码 语义
FUTEX_WAIT word 里还存着 val 时睡眠，等 FUTEX_WAKE 来唤
FUTEX_WAKE 最多唤醒 val 个等在这个 word 上的线程
FUTEX_WAIT_BITSET 同 WAIT，多带一个 bitset 参数
FUTEX_WAKE_BITSET 同 WAKE，多带一个 bitset 参数筛选唤醒谁
FUTEX_REQUEUE 唤醒 uaddr 上 val 个，剩下的转移到 uaddr2 队列，最多转 val2 个
FUTEX_CMP_REQUEUE 同上，转移前先比对 uaddr 是否等于 val3
FUTEX_LOCK_PI PI 版本的 WAIT
FUTEX_UNLOCK_PI PI 版本的 WAKE
FUTEX_WAKE_OP 原子改 uaddr2 的值并唤醒两边的 waiter，专为 glibc 的 sem_post 提速设计

FUTEX_WAKE 里的 val 只有两种实际用法：1 表示只唤一个，INT_MAX 表示全唤。中间的数值没有特殊语义，只是上限。

六、FUTEX_WAIT 与 FUTEX_WAKE #

这一对是整个机制的骨架，其余操作码都是它们的分支。

FUTEX_WAIT(uaddr, val) 的语义要读准：内核在持有 bucket 自旋锁的前提下复核 *uaddr == val。相等，把当前任务挂进队列并睡眠；不等，立刻返回 EWOULDBLOCK，当前任务根本没睡。后面那个 val 就是抢在内核边界上的那次检查，它负责消灭 lost wakeup。

参数 FUTEX_WAIT FUTEX_WAKE
uaddr futex word 地址 futex word 地址
val word 的期望值，相等才睡 唤醒的线程个数，1 或 INT_MAX
timeout 绝对超时时刻；NULL 表示无限等 未使用
uaddr2 未使用 未使用
val3 未使用 未使用
bitset 隐含 FUTEX_BITSET_MATCH_ANY 隐含 FUTEX_BITSET_MATCH_ANY

bitset 在基础操作码里被写成固定值 FUTEX_BITSET_MATCH_ANY，意思是等的人不挑、唤的人不筛，谁在这个 word 上都能被唤醒。要精细控制就得换 FUTEX_WAIT_BITSET / FUTEX_WAKE_BITSET，两边 bitset 做按位与非零才算匹配。

futex_wait 的内核流程，按发生顺序摆平：

步骤 动作 为什么要这样
1 有 timeout 就调 futex_setup_timer 建一个 hrtimer 用它把阻塞状态打断
2 get_futex_key 算 hash key private 用 (mm, addr, 0)，shared 用 (inode->i_sequence, page->index, offset_within_page)
3 按 key 哈希到 bucket，抓自旋锁 马上要往队列里塞东西
4 复核用户态传下来的期望值 值变了说明别人改过 word，返回 EWOULDBLOCK，顺手解锁
5 futex_wait_queue_me 把 futex_q 插进链表，解锁 插队按优先级：RT 线程高的前、低的后，CFS 任务走 FIFO
6 启动步骤 1 建好的 hrtimer 马上就要真睡了，超时从这一刻算
7 再验一次自己是否仍在队列上 上锁到入睡之间会有 wake 或超时先把它摘走，此时不能再睡，睡了就醒不来
8 正常醒：被 FUTEX_WAKE 唤醒 唤醒方已经完成出队，直接返回，记得取消 hrtimer
9 异常醒：futex_q 还挂在链上 说明没人替它出队，得在当前上下文自己摘
10 判断是超时还是信号 超时路径下 timer 回调会把 hrtimer_sleeper->task 置 NULL，据此区分
11 有 pending 信号即被信号打断；没有就是假唤醒 假唤醒要重试一次入队
12 被信号打断返回 ERESTARTSYS 用户态自己决定怎么收尾；但设了 timeout 且未超时的场景要 restart syscall

第 7 步是这套流程里最容易看漏的一步。挂队列、启动定时器、真正调度出去，这三件事之间存在窗口，窗口里任何一次唤醒都能让「睡」变成永别。所以入睡前必须重新确认自己还挂在队列上。

futex_wake 短得多，核心就两个动作：出队、唤醒。

步骤 动作
1 算 hash key，定位 bucket，同 wait 路径
2 遍历链表做匹配，链上 key 哈希相同的任务未必是同一个 word，三元组全等才算匹配
3 比对 bitset，筛出允许唤醒的任务
4 把匹配到的 futex_q 从 bucket 链表摘下，挪进唤醒队列 wake queue，照 val 数到量为止，全程持 bucket 自旋锁
5 扫够数量收工，wake_up_q 逐个唤醒

为什么要单独一个 wake queue，而不是边遍历边唤醒。因为唤醒要抓 runqueue 锁，还会触发调度，不该提着 bucket 自旋锁去做。先在锁内改队列归属，再在锁外做唤醒，是内核里通用的拆锁手法。

一次典型的等值场景：

c
/* 等待方：先看条件，条件不满足才 FUTEX_WAIT */
while (atomic_load(&flag) != 1)
    syscall(SYS_futex, &flag, FUTEX_WAIT, 0, NULL, NULL, 0);

/* 唤醒方 */
atomic_store(&flag, 1);
syscall(SYS_futex, &flag, FUTEX_WAKE, 1, NULL, NULL, 0);

while 那圈不能写成 if。被唤醒只代表「重新获得运行权」，不代表条件已成立：别人抢先改了回去、这是假唤醒、或者本来就超时了，三种情况都会让条件不成立。醒来重新验条件，是 futex 编程里关于正确性的底线。

要超时就传绝对时刻：

c
struct timespec ts;
clock_gettime(CLOCK_MONOTONIC, &ts);   /* 默认基准是 monotonic */
ts.tv_sec += 2;
syscall(SYS_futex, &flag, FUTEX_WAIT, 0, &ts, NULL, 0);

基准时钟跟着 FUTEX_CLOCK_REALTIME 走，不设置就吃 monotonic。写死 CLOCK_REALTIME 算超时却传不给内核，是这类代码常见的错误来源。

七、竞争时的慢路径 #

慢路径只有一种进入方式：快路径 CAS 失败。失败之后发生什么，取决于持锁者是否还在跑。

text
线程 A（持锁）                     线程 B（等锁）
    |                                  |
    |                                  +-- CAS 失败
    |                                  +-- 置等待标志，再 CAS，仍失败
    |                                  +-- FUTEX_WAIT  ──┐
    |                                                   |  进入内核
    |                                                   +-- 算 key、找 bucket
    |                                                   +-- 复核 val 相等 → 入队
    |                                                   +-- schedule() 让出 CPU
    |                                  ┌────────────────┘
    +-- 解锁，原子交换发现等待标志 ────┐
    +-- FUTEX_WAKE  ───────────────────┤  进入内核
                                       +-- 摘出 futex_q
                                       +-- wake_up_q 置为可运行
                                       +-- 被调度回来，重做 CAS

这张图上有四次用户态与内核态的往返点：B 进、A 进、A 出、B 出。每次都伴随一次完整的寄存器保存与恢复，也是慢路径要花几微秒的原因。

慢路径值得盯的是三件事。

第一，慢路径不是「一直慢」。它只覆盖真正需要睡的线程。一个 8 核机器上 4 个线程抢一把锁，绝大多数轮次都进不了内核，快路径全部命中。

第二，进入慢路径的线程仍要做原子操作。唤醒后重试 CAS 又失败，于是再睡。这个「睡—醒—失败—再睡」的循环在极端争抢下会重复多次，表现为 futex 系统调用次数远超线程数。

第三，纯用户态的等待标志位决定了要不要发系统调用。释放线程读 word 发现没有等待者，就跳过 FUTEX_WAKE，一次系统调用都不发。这条优化把「无竞争」的定义从「没人抢」放宽到了「没人等」。

慢路径还有个 requeue 变体，能在一次系统调用里完成「唤醒一批 + 转移一批」，专为条件变量设计，细节放在第九章。

八、futex 如何支撑 pthread_mutex #

pthread_mutex_lock 展开之后就是上面那套。glibc 的普通互斥锁用一个 32 位 __lock 字段编码三种状态，和第一章手写版本同构：

字段值 含义 释放方动作
0 未锁 无
1 已锁，无等待者 原子写回 0，结束
2 已锁，有等待者 原子写回 0，发 FUTEX_WAKE，唤 1 个
大于 2 记录了 owner TID 的特殊形态（robust / PI 场景） 视具体路径而定

调用链这样对上：

pthread 接口 底层动作
pthread_mutex_lock 快路径 一条 cmpxchg，把 0 改成 1
pthread_mutex_lock 慢路径 状态升到 2，FUTEX_WAIT_PRIVATE 睡
pthread_mutex_unlock 原子交换回 0，值为 2 则 FUTEX_WAKE_PRIVATE
pthread_mutex_trylock 只做 CAS，失败立即返回 EBUSY，永不进内核
pthread_mutex_destroy 纯用户态，没有内核资源需要回收

注意 _PRIVATE 后缀。默认属性是进程内共享，所以 glibc 走 private 版本，key 直接用 (mm, addr)，不走 inode 查找。把互斥锁放进共享内存做跨进程互斥，属性必须改成 PTHREAD_PROCESS_SHARED，否则两个进程会各睡各的队列，互斥失效。

trylock 这一行值得记住：它是唯一保证不进内核的加锁接口。在信号处理函数里，或者确定临界区极短的场合，用它加上退避比阻塞式加锁可控。

九、futex 如何支撑条件变量 #

条件变量的难点不在等，在于等之前必须先放开互斥锁。这两件事有严格的顺序，且中间不能有缝：

text
pthread_cond_wait(cond, mutex) 要做三件事
  1. 把当前线程挂进 cond 对应的等待队列     ← 睡眠
  2. 释放 mutex                            ← 唤醒别人
  3. 醒来后重新获取 mutex                   ← 还要再等一次锁

第 1 步和第 2 步的顺序不能反。先解锁再挂队，中间那点时间里 pthread_cond_signal 就可以把信号发完，等的人还没到，信号丢了。所以挂队必须排在解锁前面，而挂队的动作要睡，睡就不能持锁——这个矛盾正是 FUTEX_REQUEUE 存在的理由。

看一段 Java 的同构代码，问题会更直白：

java
/* A 临界区 */
synchronized (monitor) {
    while (!ready)
        monitor.wait();   /* 挂入 cond 队列，之前需释放 monitor lock */
    /* ... */
}

/* B 临界区 */
synchronized (monitor) {
    ready = true;
    monitor.notify();     /* 唤醒 cond 队列上的一个线程，它随后抢 monitor lock */
}

wait() 背后是两个等待队列：monitor lock 的队列和 condition variable 的队列。一次 wait() 要同时碰这两条队列——把别的等待者从 monitor 队列唤醒，再把自己挂进 cond 队列。

没有 requeue 时，这是两次系统调用：

c
/* 无 requeue：两次进内核 */
syscall(SYS_futex, &mutex, FUTEX_WAKE, 1, NULL, NULL, 0);       /* 释放锁，唤醒等锁者 */
syscall(SYS_futex, &cond,  FUTEX_WAIT, seq, NULL, NULL, 0);     /* 睡在条件变量上 */

中间那个窗口是实打实的风险。有了 requeue，一次系统调用全办：

c
/* 有 requeue：一次进内核，唤醒 0 个，全部转移 */
syscall(SYS_futex, &mutex, FUTEX_REQUEUE, 0, (void *)1, &cond, 0);

FUTEX_REQUEUE 的流程只用四步：

步骤 动作
1 对 uaddr1 和 uaddr2 各算一次 hash key，各自定位 bucket
2 若是 FUTEX_CMP_REQUEUE，先校验 uaddr1 的值是否等于 val3。这步要读用户态内存，属于复杂的动作，细节在 get_futex_value_locked
3 遍历 uaddr1 队列，mark_wake_futex 把 nr_wake 个对象暂存进 wake queue，requeue_futex 把 nr_requeue 个对象转移到 uaddr2 队列。两个 bucket 的自旋锁都要持有
4 wake_up_q 唤醒暂存的那批任务

转移的含义要说清：任务并没有被唤醒，它只是从「等 mutex」的链表换到了「等 cond」的链表，继续睡着。这样 pthread_cond_wait 就能在一次系统调用里完成「释放锁并把等锁者转到 cond 队列」，既没有空隙，也省了一次往返。

参数怎么填是关键：

参数 值 含义
uaddr &mutex 源：等锁的队列
val 0 一个都不唤醒，全部转移
uaddr2 &cond 目标：条件变量队列
val2 1 最多转移 1 个
val3 当前 seq 只在 CMP_REQUEUE 下校验，防序列号过期

pthread_cond_signal 对应 FUTEX_WAKE，pthread_cond_broadcast 对应 val 传 INT_MAX 的 FUTEX_WAKE。glibc 在 cond 里还维护一个序列号 seq，用来区分「信号发生在等之前还是之后」，FUTEX_WAIT 的 val 传的就是它。这也是为什么被唤醒后必须重新检查条件：seq 变了只说明发生过唤醒事件，不说明条件成立。

十、futex 如何支撑信号量 #

信号量比前两个简单，因为它的状态本来就只是个计数器。glibc 的 sem_t 把计数和等待者数塞进同一个 32 位字：

位段 含义
高位 当前计数值
低位 正在睡眠的等待者数量

sem_wait 走一条和互斥锁同构的路：

c
/* 快路径：计数 > 0，原子减 1 直接返回，不进内核 */
while (1) {
    int val = atomic_load(&sem->value);
    if (val > 0) {
        if (__atomic_compare_exchange_n(&sem->value, &val, val - 1, 0,
                                        __ATOMIC_ACQUIRE, __ATOMIC_RELAXED))
            return 0;
        continue;
    }
    /* 慢路径：计数为 0，先把等待者数 +1，再睡 */
    val = atomic_fetch_add(&sem->value, 1);
    syscall(SYS_futex, &sem->value, FUTEX_WAIT, val + 1, NULL, NULL, 0);
}

FUTEX_WAIT 的 val 传的是「加 1 之前的快照」加 1，也就是加上等待者位之后的值。这样如果 sem_post 在 fetch_add 之后、进入内核之前就发生了，内核复核会发现 word 已经变了，直接返回 EWOULDBLOCK，重试时能吃到那个增量。丢唤醒又被这套 val 机制堵住一次。

sem_post 只需要两步：

c
/* 计数加 1；若加之前存在等待者，唤醒一个 */
int val = atomic_fetch_add(&sem->value, 1u << SEM_VALUE_SHIFT);
if (val & SEM_NWAITERS_MASK)
    syscall(SYS_futex, &sem->value, FUTEX_WAKE, 1, NULL, NULL, 0);

FUTEX_WAKE_OP 是给这条路径再砍一刀的设计。它能在一次系统调用里原子地修改 uaddr2 指向的值并唤醒两个队列上的 waiter，避免 sem_post 里「改值 + 唤醒」拆成两次内核往返。

三种原语放在一起对照：

原语 用户态快路径 慢路径系统调用 等待队列挂在 关键点
pthread_mutex cmpxchg 0→1 FUTEX_WAIT_PRIVATE / FUTEX_WAKE_PRIVATE mutex 字本身 状态 2 表示有等待者，决定释放方是否唤醒
pthread_cond 不适用，总是慢路径 FUTEX_WAIT + FUTEX_REQUEUE / FUTEX_WAKE cond 的 seq 字段 一次 requeue 完成解锁加挂队，不可拆成两次
sem_* 原子减计数 FUTEX_WAIT / FUTEX_WAKE / FUTEX_WAKE_OP sem_t 的 value 字段 计数与等待者数共用同一个 32 位字

十一、优先级继承与 PI futex #

normal futex 有个硬伤：它不认识优先级。这在实时系统里会直接炸成优先级翻转。

text
优先级：A > B > C

C（低优先级）持锁
  └─ A（高优先级）抢锁失败，进入 D 状态睡下
       └─ B（中优先级）被唤醒，抢占 C
            └─ C 拿不到 CPU，A 只能无限期等下去

C 的临界区本来很短，跑完就解锁，A 立刻能跑。问题出在 B：B 的优先级比 C 高，只要 B 就绪，C 就得让出 CPU。于是所有优先级介于 A 和 C 之间的任务都能插队，A 拿不到确定时间的 CPU 资源。优先级最高的那个反而等得最久。

PI 就是 priority inheritance，解法很直接：A 持锁失败时，把锁的 owner（也就是 C）临时提到 A 的优先级；C 释放锁时，恢复原值。C 不再被 B 抢占，跑完临界区，A 顺利接手。

原理就这么简单，实现要记两类账。

从线程视角，得知道：

记录项 用途
该线程持有哪些锁，每把锁的 top waiter 是谁 所有 top waiter 按优先级排序，决定自己该被提到多高
该线程阻塞在哪一把锁上 向上传递优先级时知道往哪走

从锁视角，得知道：

记录项 用途
这把锁的 owner 是谁 提优先级时找到目标任务
阻塞在这把锁上的线程，按优先级排序 优先级最高的那个叫该锁的 top waiter

有了这两本账，只需维持一条准则：一个任务的临时优先级，等于它持有各把锁的 top waiter 中最高的那个优先级。

rt mutex：PI 的执行体 #

PI futex 不自己实现这套逻辑，它把活包给内核的 rt mutex——就是内核里支持 PI 的那版互斥锁。看 rt mutex 怎么记账。

从锁的视角看任务：

c
/* 概念示意：描述一个阻塞在 rt mutex 上的任务 */
struct rt_mutex_waiter {
    struct task_struct *task;          /* 阻塞的任务 */
    struct rt_mutex    *lock;          /* 阻塞在哪把 rt mutex 上 */
    struct rb_node      tree_entry;    /* 挂进 blocker 红黑树的节点 */
};

rt_mutex 的 waiters 成员就是这棵红黑树的根，wait_lock 保护树操作，owner 指向持锁任务。这棵树按优先级排序，最左节点（left most）就是该锁的 top waiter。

从任务的视角看锁。task_struct 为此加了几个成员，最关键的是 pi_waiters。一个任务可以持有多把锁，每把锁都有自己的 top waiter，这些 top waiter 又组成一棵按优先级排序的红黑树，pi_waiters 是它的根。这棵树的最左节点对应的优先级，就是 PI 协议要求临时提升到的值。pi_top_task 指向那个最左节点对应的任务，称之为 top pi waiter。pi_blocked_on 则指向自己正在阻塞的那把 rt mutex 的 waiter 对象。

PI chain #

任务与锁的关系只有两种边，形状被限死了：

text
task 1 持有 Lock A、Lock B，阻塞在 Lock C 上

  Lock A ──┐
           ├──► task 1 ──► Lock C
  Lock B ──┘

箭头方向有严格约束。一个任务在任一时刻只能阻塞在一把锁上，所以「任务 → 锁」这条边永远只有一根，不能分叉。「锁 → 任务」可以有多个，因为一个任务可以同时持有多把锁，多把锁汇聚到同一个任务上。

把这种结构串起来就是 PI chain。四条链的例子：

链 形式
1 Lock D → task 2
2 task 4 → Lock D → task 2
3 Lock A → task 1 → Lock C → task 2
4 task 3 → Lock B → task 1 → Lock C → task 2

要让 PI 正常工作，链上必须维持一条不变式：右端任务的优先级必须大于等于左端任务们的优先级。以第四条链为例，task 2 的优先级要不低于 task 1 和 task 3，task 1 的优先级要不低于 task 3。一旦某个任务被提了优先级，整条链都要跟着往上调整，这就是 rt mutex 里那段传播循环在干的事。

PI futex 与 rt mutex 的分工 #

接口层面区别清晰：

类型 阻塞 唤醒
normal futex FUTEX_WAIT FUTEX_WAKE
PI futex FUTEX_LOCK_PI FUTEX_UNLOCK_PI

PI 版本里那个「lock」和「unlock」，作用对象是代理的 rt mutex，不是用户态那把锁。

两种 futex 下，被阻塞的任务都对应一个 futex_q。normal futex 有它就够了：挂队、唤醒都能实现。PI futex 还得按 PI chain 调整优先级，为此多出两个对象：

对象 承载什么
rt_mutex_waiter 一个阻塞在 rt mutex 上的任务，lock 指针指明阻塞在哪把 rt mutex 上
futex_pi_state 优先级继承的全部状态：该用户态锁对应的内核 rt mutex、rt mutex 的 owner 任务信息

FUTEX_LOCK_PI 的语义常被误读。它不表示「尝试上锁」。线程成功拿到上层锁时，根本没有 futex 系统调用发生——因为此刻 rt mutex 并没有被同时持住、owner 也没设。只有当竞争上层锁失败、准备进内核阻塞时，FUTEX_LOCK_PI 才被调用，它的真实含义是「为 PI 记账而对代理 rt mutex 执行上锁」。

第一次 FUTEX_LOCK_PI 最复杂，要同时完成两件事：让 owner 在 rt mutex 上持锁，让 current 阻塞在这把 rt mutex 上。

第一件事是建账。用户态把 owner id 传进内核，内核分配 futex_pi_state、创建一个 rt mutex，然后建立三者关系：

动作 内容
1 把 futex_pi_state 挂进 owner 任务的 pi_state 链表。一个任务可持多把上层锁，需要链表管理；没有竞争的锁不会产生 pi_state
2 把 futex_pi_state->owner 指向对应的 owner 任务

第二件事是让 current 去抢这把刚设好 owner 的 rt mutex。结果十有八九是阻塞——本来就是要靠这个阻塞关系把 PI 状态挂上链条。要建立的关系有五个：

动作 内容
1 rt_mutex_waiter->lock 指向对应 rt mutex，->task 指向当前要阻塞的任务
2 把 waiter 插进 rt mutex 的 waiters 红黑树
3 task_struct->pi_blocked_on 指向这个 waiter
4 新任务的优先级若高于当前 top waiter，更新 owner 的 top waiter：旧的从红黑树摘掉，新的插进去
5 按新 top waiter 更新 owner 的动态优先级；优先级一动，整条 PI chain 都要跟着调

第二次及以后的 FUTEX_LOCK_PI 便宜得多。rt mutex 已经现成，不必新建：在 bucket 里找到第一个 futex_q，顺它的 pi_state 指针就能定位到 rt mutex，直接在上面上锁让自己阻塞即可。

FUTEX_UNLOCK_PI 走的是反方向：把代理 rt mutex 上的 owner 摘下来，恢复它的原始优先级，再把 rt mutex 交给 top waiter。这条路径的完整细节牵涉到 rt mutex 的 stealer 逻辑和 FUTEX_CMP_REQUEUE_PI 的原子移交，链条比前面十节都长。

十二、futex 的常见误解 #

这一节把容易卡住的点摆成对照表。每一条都能在前面的章节里找到落点。

误解 实际情况 依据
futex 名字里有 mutex，所以它就是个互斥锁 它是通用同步原语，互斥锁、读写锁、条件变量都在它上面搭 内核不认识 normal futex word 的语义
futex 由内核管理锁状态 锁状态在用户态，内核只管等待队列 futex word 是你的进程内存
FUTEX_WAKE 会把锁交给被唤醒的线程 只赋予重新竞争的机会，醒来必须重做 CAS 唤醒只改调度状态，不改 word
每次加解锁都要进内核 无竞争时 0 次系统调用 状态 0→1 一条 CAS 就够
64 位平台上 futex word 是 64 位 所有平台都是 32 位 硬件架构无关
FUTEX_WAIT 是无条件睡眠 带 val 做期望值校验，不等则返回 EWOULDBLOCK 复核在 bucket 自旋锁内完成
被唤醒说明条件已成立 只说明发生过唤醒事件，条件得自己再查 唤醒上限、假唤醒、超时都会发生
优先级继承是 futex 模块自己实现的 由 rt mutex 代理完成，futex 只记录 pi_state FUTEX_LOCK_PI 锁的是代理 rt mutex
FUTEX_WAKE 的 val 任意取值有区别 实际只有 1 和 INT_MAX 两种用法：唤一个或全唤 中间值只是上限
FUTEX_PRIVATE_FLAG 只是性能提示 它决定 hash key 算法，设错会导致互斥失效 private 用 (mm, addr)，shared 用页信息
条件变量可以「先解锁再等」 顺序反过来会丢信号，必须一次 requeue 完成 FUTEX_REQUEUE 存在的理由
RT 线程和 CFS 线程在 futex 队列里先来先服务 队列是 plist，RT 按优先级插队，CFS 走 FIFO futex_q.list 是有序链表

十三、易错点速查 #

故障现象往前翻，基本都能落到下面几行。

现象 根因 处理
偶发死锁，日志里没任何异常 等待条件写在 if 里，被假唤醒后条件不成立就直接往下走 一律写成 while 循环重验条件
唤醒发出去了，等待方还在睡 检查条件与 FUTEX_WAIT 分两步做，中间出现丢唤醒 把期望值 val 传给内核，让复核和入队在锁内一次完成
跨进程互斥失效，两个进程同时进临界区 word 在共享内存里，但用了 FUTEX_PRIVATE_FLAG 或 PTHREAD_PROCESS_PRIVATE 改用非 private 版本，让 key 走页信息
线程卡在 FUTEX_WAIT 永不返回 唤醒方提前用原子操作把 word 改了却没发 FUTEX_WAKE；或 val 传错 复核 val 的取值，改完 word 后按状态位判断是否唤醒
RT 任务延迟抖动远超临界区长度 优先级翻转，低优先级 owner 被中优先级任务抢占 换用 PI 版互斥锁，走 FUTEX_LOCK_PI
加了 PI 锁但抖动仍在 PI 只解决锁链上的继承，链外任务照样抢占 检查 PI chain 之外是否还有未受保护的临界资源
pthread_cond_wait 返回后 mutex 不在手里 误以为 EWOULDBLOCK 或信号打断的路径也会重新持锁 按返回值分支处理，被打断时要自己决定是否重入
超时设了不生效，或提前超时 超时传的是相对时长而非绝对时刻；基准时钟与 FUTEX_CLOCK_REALTIME 不一致 用 clock_gettime 取当前时刻再加时长，保证基准一致
系统调用次数远高于线程数 高争抢下进入「睡—醒—失败—再睡」循环 缩短临界区，或降低并发度、改用分批唤醒
把 FUTEX_WAKE 的 val 传成等待者总数 传大了只是多唤几个，传小了唤醒不足导致长尾 记清语义：1 或 INT_MAX
在信号处理函数里调 pthread_mutex_lock 加锁路径不是异步信号安全的，撞上同一把锁就死锁 信号上下文只碰无锁结构或 trylock
requeue 用在非 cond 场景，行为诡异 被转移的任务只是换了队列，没有醒来 记住 requeue 不唤醒，只改归属

三条能压住大部分问题的习惯：

写等待，永远 while 环加条件复核，因为唤醒只是「你被允许再看一眼」。

设 val，让内核替你消除空隙。凡是「先判断再 sleep」的写法，都要问一句：判断和 sleep 之间，谁来兜底。

分清成本归属。无竞争路径是一条原子指令，所有开销都在慢路径上。把它们混为一谈，就会在临界区里塞进不必要的唤醒调用。
