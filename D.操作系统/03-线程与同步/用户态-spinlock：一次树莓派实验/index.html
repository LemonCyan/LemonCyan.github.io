一、为什么要自己实现一遍 #

进程同步机制有 spinlock、mutex、semaphore 三件套。

我的学习方式是简化再简化，然后用代码把每一个实现出来。只看书，你手里只有名词；写完一遍，你才知道名词背后是哪几条指令。spinlock 是这三件套里最底层的一个，把它做出来，同步的基本骨架就有了。

麻烦在测试。早先我的想法是：得先实现 process switch，才能测 spinlock。这个思路本身没错，因为自旋锁的失败模式是两个执行流同时进入临界区，你需要有能力制造并发。但为了测一把锁先去写调度器，代价太大，方向也跑偏了。

后来想通了：并发不用自己造，pthread 已经给了。在 rpi2 上写个 pthread 程序，把 pthread_spin_lock / pthread_spin_unlock 换成自己的 my_spin_lock / my_spin_unlock，行为一样就说明写对了。

这个办法的价值在于拿到了一个可以对照的基准。pthread 的实现是久经考验的，我的是刚写的三行汇编，两边跑同一套负载，输出一致与否就是判决书。没有基准，你连自己写的东西对不对都不知道。

测试负载这样设计：三个线程抢同一把锁，各自往同一个文件 /tmp/xyz1 里连写三行。临界区短，抢得凶。锁一旦失效，三行就会交错。判读标准非常直观，比打时间戳、算计数器好使得多。

这条路能走通，靠的是两件事：一是有硬件原子指令可用，二是有屏障能约束编译器和 CPU 的乱序。这两件事就是全文的主线。

二、spinlock 的最小语义 #

先把壳子剥掉。spinlock 的逻辑简单到可以用四行伪代码写完：

text
init:   val = 0
lock:   while (val == 1) ;    val = 1
unlock: val = 0

val 为 0 表示空闲，为 1 表示被占用。抢锁就是「看一眼，空就占上，不空就再看」，直到占上为止。解锁就是把 val 清零。

它一共只有三个要素：

要素 具体内容 要求
状态位 一个整型 val_，0 空闲、1 占用 必须能被多个执行流直接读写
测试并设置 读旧值，若空闲则写入 1 读和写合起来是一个不可分割的动作
释放 写入 0 对之后抢锁的执行流可见

数据结构也就是一个整型加个封装：

c
typedef struct {
    volatile int val_;
} Spinlock;

void spinlock_init(Spinlock *spinlock)
{
    spinlock->val_ = 0;
}

到这里一切都好。难点在第三个要素那一栏的「不可分割」四个字上。C 语言没有提供这个能力，你写出来的每一行都是可分割的。

三、核心难点：原子性从哪来 #

最直觉的实现长这样，用 goto 原地重试：

c
int spin_lock(Spinlock *spinlock)
{
lock_mutex:
    if (spinlock->val_ == 1)
        goto lock_mutex;
    else
        spinlock->val_ = 1;

    return 0;
}

int spin_unlock(Spinlock *spinlock)
{
    spinlock->val_ = 0;

    return 0;
}

短路一下：这段代码在单线程下完全正确。在多线程下它一定会坏，而且坏得概率不低。把两个线程的时间线摊开看：

时刻 线程 A 线程 B val_
t0 读 val_，得到 0 — 0
t1 — 读 val_，得到 0 0
t2 写 val_ = 1，认为抢到了 — 1
t3 — 写 val_ = 1，也认为抢到了 1
t4 进入临界区 进入临界区 1

两个线程都进了临界区。锁在这里没有失效在「判断」上，失效在「判断」和「占用」之间的那道缝里。val_ 从读到写之间，别的核随时可以插进来。

每次只差几条指令，跑一万次错一次。这种 bug 最难查，因为它不常出现，而且出现时现场已经乱了。

所以结论要说得直白些：spinlock 的全部难点不在「锁」，而在「原子性」与「内存可见性」。锁的语义四行就写完了；真正的工作量在把「读旧值 + 写新值」压成一个硬件不可打断的动作，以及保证临界区里的写对下一个持锁者可见。

第一件事靠硬件原子指令，第二件事靠内存屏障。没有硬件原子指令，用户态根本实现不出正确的 spinlock，只能实现一个「看上去像锁」的东西。

四、方案一：用原子操作做测试并设置 #

ARMv6 起有了一对指令：ldrex / strex（Load-Exclusive / Store-Exclusive）。它们配合工作，提供独占访问：

  • ldrex 读一个地址，同时在处理器的独占监视器里记下这个地址；
  • strex 往同一个地址写，只有在「从上次 ldrex 到现在没有别的核碰过这个地址」时才写成功，成功返回 0，失败返回非 0。

这就把「读—判断—写」变成了一段受监视的序列。中途被别人插了，strex 会明确告诉你失败，重试即可。

我这段汇编是从 Linux 3.10.37 的 arch/arm/include/asm/atomic.h 里 atomic_add 改出来的。自己从头写的那几版都有问题，最后还是要站在内核的肩膀上：

c
static inline int spin_trylock_asm(Spinlock *spinlock)
{
    unsigned long tmp;
    int result;

    __asm__ __volatile__("@ atomic_test_and_set\n"
    "1:     ldrex   %0, [%3]\n"      /* 独占读，%0 得到当前值 */
    "       cmp     %0, #1\n"        /* 已经是 1？ */
    "       beq     1b\n"            /* 被占了，回去重读 */
    "       mov     %0, #1\n"        /* 空闲，准备写入 1 */
    "       strex   %1, %0, [%3]\n"  /* 独占写，%1 = 0 表示成功 */
    "       teq     %1, #0\n"        /* 测成功标志 */
    "       bne     1b"              /* 写失败，说明被人插了，整体重来 */
        : "=&r" (result), "=&r" (tmp), "+Qo" (spinlock->val_)
        : "r" (&spinlock->val_)
        : "cc");

    return result;
}

逐行看关键处：

片段 作用 少了它会怎样
ldrex %0, [%3] 独占读，登记地址 退化成普通读，无任何保护
cmp/beq 1b 已被占用就重读，不写 无意义地写 1，制造总线流量
strex %1, %0, [%3] 只有独占未被破坏才写成功 用 str 的话，两个人都会写成功
teq %1, #0 + bne 1b 写失败则整段重来 丢掉一次失败，锁被两个人同时持有

约束列表也有讲究。"=&r" (result) 和 "=&r" (tmp) 上的 & 表示「早写」：这段汇编一开始就会写这两个寄存器，不能和输入操作数复用同一个寄存器。"+Qo" (spinlock->val_) 是内存操作数，+ 表示读且写。"cc" 告诉编译器这段汇编会改条件码。

少了 &，编译器优化时把输入寄存器分配到 %0 或 %1 的位置，ldrex 一执行就把输入冲掉，行为就错了。这种错不报编译错误，只在特定优化等级下出现。

同一个需求在不同平台上有不同实现：

平台 / 方案 指令或接口 失败如何得知
ARMv6 / ARMv7-A ldrex / strex strex 返回非 0
x86 lock cmpxchg、xchg cmpxchg 比较不相等
老式 ARM（无 ldrex） swp 无失败概念，靠总线锁
C11 atomic_exchange、atomic_compare_exchange_weak 返回旧值 / 返回 false
GCC 内建 __atomic_*、__sync_* 同上

写内核代码之外，日常用 C11 或 GCC 内建就够，别手写汇编。手写的唯一好处是能看清下面到底发生了什么，这也是这一节存在的理由。

五、编译器优化带来的坑 #

有了正确的汇编，还没到能收工的时候。C 语言层面的东西编译器照样会动，而编译器不知道「val_ 是锁」这件事。

最经典的一幕是这样的代码：

c
int flag = 1;

while (flag)
    ;   /* 等别人把 flag 清掉 */

编译器一眼看出循环体没改 flag，于是把读操作提到循环外，等价改写成：

text
        ldr     r0, [flag]      @ 只读一次
        cmp     r0, #0
        beq     .Lexit
.Lspin:
        b       .Lspin          @ 死循环，flag 再也不会被读

进循环时如果读到 1，这个线程就永远出不来了，哪怕另一个线程早把 flag 清零。给 flag 加上 volatile 能拦住这个优化，编译器不敢再把读提到循环外。但 volatile 到此为止，它管不了重排次序，管不了多核可见性，也不产生任何屏障语义，下一幕它就救不了场。

第二幕更隐蔽，出在解锁那一侧：

c
spinlock->data_x = 42;   /* 临界区里的写 */
spin_unlock(spinlock);   /* val_ = 0 */

编译器认为这两句没有依赖，就有机会把 val_ = 0 提前到前面。CPU 也一样，写缓冲区和乱序执行让它先看见锁的释放，再看见数据本身。结果下一个抢到锁的线程读到的还是旧值。

我们手里唯一的工具是把「我不许你跨过去」明确写出来。两种写法：

c
/* 编译器屏障：只约束编译器，不产生任何指令 */
__asm__ __volatile__("" ::: "memory");

/* 完整屏障：既约束编译器，也约束 CPU */
__asm__ __volatile__("dmb ish" ::: "memory");

__asm__ __volatile__ 里的 volatile 让编译器不要删除、不要移出循环；"memory" 这个 clobber 告诉它「内存变了，寄存器里的缓存全作废，别跨过这条边重排访存」。两个东西名字一样，作用不同，不要混：asm volatile 管的是「这条汇编不能被优化掉」，"memory" 管的是「访存顺序」。

一个常见的误解：把变量声明成 volatile 就以为万事大吉。它解决不了重排，解决不了多核可见性，也不产生任何屏障语义。真正要做同步，屏障和原子操作都得有。

六、内存屏障与乱序执行 #

屏障要解决的是两件不同的事，得分清。

第一件是编译器重排，上面已经说过。第二件是 CPU 重排：指令发出去之后，硬件为了填满流水线，会让后面的访存先于前面的访存完成。ARM 是弱内存模型，这种事每天都在发生。x86 的模型强一些，但也不是完全顺序的，写缓冲依然会让别的核晚看到你的写。

ARM 上三种屏障指令，用途各不相同：

指令 全称 管什么 典型场景
dmb Data Memory Barrier 保证之前的访存在之后的访存之前完成，不保证指令流水 锁的获取与释放、共享数据发布
dsb Data Synchronization Barrier 比 dmb 更严，等之前的访存真正完成 改页表、关 MMU、DMA 前后
isb Instruction Synchronization Barrier 清空流水线，让之后取到的指令是新的 改完系统寄存器、开了 MMU 之后

再加上编译器屏障，一共四个工具。它们的组合覆盖了从 C 源码到内存的整条链路：

text
C 语句  --(编译器重排)-->  机器指令  --(CPU 乱序)-->  内存可见
            ^                          ^
            |                          |
      编译器屏障 / "memory"          dmb / dsb / isb

dmb ish 里的 ish 是 inner shareable domain，指多核之间共享的那部分观察范围。用户态代码在 ARM Linux 上可以直接发 dmb ish，不需要特权；只约束写顺序时可以用弱一档的 dmb ishst，把读排除在外。屏障的选择上，宁可多给一个 dmb ish，别省。

屏障配锁的规矩，一句话说清：获取锁之后要一次屏障，释放锁之前要一次屏障。

  • 解锁前屏障：保证临界区里的写先落地，再放锁。否则下一个持锁者读到的就是旧数据。
  • 加锁后屏障：保证拿到锁之后的读不会被提前到锁之前执行。读提前了，你读到的就是临界区外的脏数据。

ARM 的 ldrex / strex 本身不带任何屏障语义，这两道屏障必须显式写。x86 的 lock 前缀指令自带全屏障，所以那边的实现看着「更短」，不是因为更简单，是因为硬件替它做了。

七、方案二：加上屏障的正确版本 #

把原子操作和屏障拼起来，才是完整版：

c
typedef struct {
    volatile int val_;
} Spinlock;

void spinlock_init(Spinlock *spinlock)
{
    spinlock->val_ = 0;
}

static inline int spin_trylock(Spinlock *spinlock)
{
    unsigned long tmp;
    int result;

    __asm__ __volatile__("@ atomic_test_and_set\n"
    "1:     ldrex   %0, [%3]\n"
    "       cmp     %0, #1\n"
    "       beq     1b\n"
    "       mov     %0, #1\n"
    "       strex   %1, %0, [%3]\n"
    "       teq     %1, #0\n"
    "       bne     1b"
        : "=&r" (result), "=&r" (tmp), "+Qo" (spinlock->val_)
        : "r" (&spinlock->val_)
        : "cc");

    return result;
}

int spin_lock(Spinlock *spinlock)
{
    while (spin_trylock(spinlock) != 0)
        ;   /* 抢不到就再抢，这就是自旋 */

    /* 拿到锁，禁止后面的访存被提前 */
    __asm__ __volatile__("dmb ish" ::: "memory");

    return 0;
}

int spin_unlock(Spinlock *spinlock)
{
    /* 放锁之前，保证临界区的写已经完成 */
    __asm__ __volatile__("dmb ish" ::: "memory");

    spinlock->val_ = 0;

    return 0;
}

用 C11 写等价版本，可读性好得多，也更容易跨平台：

c
#include <stdatomic.h>

typedef struct {
    atomic_int val_;
} Spinlock;

void spinlock_init(Spinlock *spinlock)
{
    atomic_init(&spinlock->val_, 0);
}

int spin_lock(Spinlock *spinlock)
{
    int expected = 0;

    while (!atomic_compare_exchange_weak_explicit(
               &spinlock->val_, &expected, 1,
               memory_order_acquire, memory_order_relaxed)) {
        expected = 0;   /* 失败后 CAS 会把旧值写回，这里重置 */
    }

    return 0;
}

int spin_unlock(Spinlock *spinlock)
{
    atomic_store_explicit(&spinlock->val_, 0, memory_order_release);

    return 0;
}

memory_order_acquire 对应加锁后的屏障，memory_order_release 对应解锁前的屏障。这一对名字和语义是直接映射的，理解起来比裸汇编轻松。compare_exchange_weak 允许伪失败（值相等但返回 false），所以外面套 while，重试一次就好。

两个版本摆在一起，差别集中在下面几处：

对比项 裸汇编版本 C11 版本
原子性来源 ldrex / strex atomic_compare_exchange_weak
屏障表达 显式 dmb ish + "memory" acquire / release 语义
可移植性 绑死 ARMv6+ 任何支持 C11 的编译器
可读性 要看懂 8 行汇编 看函数名即可
允许伪失败 strex 失败即重试 同左，由 while 兜住

八、自旋的代价：CPU 空转 #

while (spin_trylock(spinlock) != 0) ; 里的那个空分号，是最便宜的等待方式，也是最贵的。

便宜在于不需要任何系统调用，不进内核，不碰调度器，不切栈。锁被占用的时间只有几百纳秒时，自旋等待几乎立刻就能拿到，比进入内核睡眠再唤醒快一个数量级。

贵在于这段时间里，这个核什么正事都没干。争抢越激烈，空转越多：

场景 自旋的后果
临界区 100 ns，两个线程 少量空转，划算
临界区 100 ns，八个线程抢一个核 大量空转，且持锁者正等着 CPU
临界区 10 ms，任何线程数 空转变成灾难，浪费整个时间片
单核系统 持锁者拿不到 CPU，等锁者永远空转，直接死锁

最后一行要格外注意。单核上如果关掉抢占再自旋等锁，而持锁者恰好被切出去了，程序就永久卡住。用户态下 pthread 的实现会尽量规避，内核态下这是必须靠「关抢占 + 临界区极短」两条规则联手保证的。

还有一条常被忽略的成本：多个核同时对着同一个缓存行做 ldrex，这条缓存行会在核间反复弹跳（cache line bouncing）。空转不只是浪费自己的 CPU，还会把别人的缓存打掉。核数越多，这个代价越大。

所以自旋有一个前提条件，必须写清楚：临界区要足够短，短到自旋等待的时间小于一次上下文切换的代价。经验上的量级是一次切换几千纳秒，临界区得控制在这个数量级甚至更短。超过就换 mutex。

九、退让与让出：sched_yield #

空转最蠢的地方在于它不知道持锁者在干什么。如果持锁者正等着 CPU，你越转，它越轮不到。

sched_yield() 是给这种情况留的出口：主动放弃剩余时间片，把自己挪到同优先级队列的末尾，让别的线程有机会上。

spin_lock 里的自旋循环有两种写法：

c
/* 方案 A：纯自旋，抢不到就不停重试 */
while (spin_trylock(spinlock) != 0)
    ;

/* 方案 B：抢不到时先让出 CPU，再回来重试 */
while (spin_trylock(spinlock) != 0)
    sched_yield();

两种写法的差别落在「谁在等谁」上：

写法 语义 适合
纯自旋 死等，绝不让出 临界区极短、核数足够、不会被抢占
自旋 + sched_yield 等不到就让一下，让对方有机会跑 临界区稍长，或运行在会被抢占的环境
直接睡眠 用条件变量或 futex 阻塞 临界区较长，或锁争抢频繁

sched_yield() 不是免费的。每次调用都是一次系统调用，进内核，走一遍调度器。争抢激烈时，它会变成另一种形式的空转，只不过空转地点从用户态换到了内核态。有人测过在重负载下 sched_yield 反而拖慢整体吞吐，原因是它把锁交给了错误的线程，制造出「活锁」式的恶循环。

所以别把它当万能药。它适合的场景很窄：你确定持锁者在别的核上跑着，或者你在一台已经超载的机器上不想再添一把火。真正需要长期等待时，正确做法是睡眠，而不是让出。

把两行代码一改，spinlock 就变成了 mutex 的雏形：把自旋换成让出，再把让出换成阻塞，你就完成了从「占着 CPU 等」到「睡着等」的转变。这也是后面 futex 那一篇要做的事。

十、树莓派上的实测 #

整套测试在 rpi2（Cortex-A7，四核，ARMv7-A）上跑，内核 3.10.37，交叉编译加 SSH 上机。测试程序的结构是这样：

c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>
#include <signal.h>
#include <unistd.h>
#include "spinlock.h"

#define FN "/tmp/xyz1"

static FILE *fs;
static Spinlock sp;
static pthread_spinlock_t spinlock;
static volatile int run = 1;

三个线程的临界区长度刻意不同。线程 1 写三行短串，线程 2 和线程 3 写长串，这样它占着锁的时间明显更长。如果锁是错的，长临界区会更容易被切开，交错更容易被抓到。这是有意的设计，不是随手写的。

信号处理单独一个线程收，用 sigwait 而不是信号处理函数，避免在信号上下文里改全局变量带来的麻烦：

c
static void *sig_thread(void *arg)
{
    sigset_t *set = arg;
    int s, sig;

    printf("sig thread pid: %d\n", getpid());

    for (;;) {
        s = sigwait(set, &sig);
        if (s == 0) {
            printf("Signal handling thread got signal %d\n", sig);
            if (sig == SIGINT)
                run = 0;
        }
    }
    return NULL;
}

主函数把 SIGQUIT 和 SIGINT 都先屏蔽掉，再交给 sig_thread，这样所有线程都继承这个屏蔽字，信号只会落到那个专职线程上：

c
int main(int argc, char *argv[])
{
    pthread_t thread0, thread1, thread2, thread;
    sigset_t set;

#ifdef PTHREAD_FUNC
    pthread_spin_init(&spinlock, 0);
    printf("init pthread spinlock\n");
#else
    spinlock_init(&sp);
    printf("init my spinlock\n");
#endif

    sigemptyset(&set);
    sigaddset(&set, SIGQUIT);
    sigaddset(&set, SIGINT);
    if (pthread_sigmask(SIG_BLOCK, &set, NULL) != 0) {
        perror("pthread_sigmask");
        return -1;
    }

    printf("open %s to write\n", FN);
    fs = fopen(FN, "w");
    if (fs == NULL) {
        perror("open fail");
        return -1;
    }

    pthread_create(&thread, NULL, &sig_thread, (void *)&set);
    pthread_create(&thread0, NULL, write_file_1, NULL);
    pthread_create(&thread1, NULL, write_file_2, NULL);
    pthread_create(&thread2, NULL, write_file_3, NULL);

    pthread_join(thread0, NULL);
    pthread_join(thread1, NULL);
    pthread_join(thread2, NULL);

    fclose(fs);
    printf("test end\n");

    return 0;
}

编译时用 -DPTHREAD_FUNC 切到 pthread 版本，不加就是自己的实现，两边跑同一份代码：

bash
# 自己的 spinlock
gcc -O2 -pthread -o spinlock spinlock.c

# 对照组
gcc -O2 -pthread -DPTHREAD_FUNC -o spinlock_pthread spinlock.c

./spinlock && head -n 30 /tmp/xyz1

判读方法只有一条：每个线程的三行必须连在一起出现。三个线程共用一个 FILE *，fprintf 表面看是三次调用，实际会先在用户态缓冲区里攒着，凑够一块才真正写下去。这意味着锁保护的是缓冲区操作，而不是每一次 write 系统调用。

于是「成功」的样子是三个线程的数据块轮流整段出现，时序数字递增，线程号各自连续：

text

6 ## thread 11
6 ## thread 111
0 ## thread 2 long string 0123456789 ## 1977488480
0 ## thread 22 long string 0123456789
0 ## thread 222 long string 0123456789
7 ## thread 1 ## 1985877088
7 ## thread 11
7 ## thread 111
1 ## thread 2 long string 0123456789 ## 1977488480
1 ## thread 22 long string 0123456789
1 ## thread 222 long string 0123456789

「失败」的样子是三个线程的行被搅在一起，序号跳着走：

text

237 ## thread 3 long string ABCDEFGHIJKLMNOPQRSTUVWXYZ!@#$%^&*()~ ## 1968641120

第二组里，线程 1 只输出了第一行，线程 3 和线程 2 就插了进来。线程 1 明明还握着锁，其余两个却进了临界区。

我的第一版就是失败的那组。换成 pthread_spin_lock / pthread_spin_unlock 之后立刻正确。这一对照把问题范围锁死了：错在我自己写的那段，不在 pthread，不在文件操作，也不在信号处理。

顺手写了个 check_result.c，逐行扫 /tmp/xyz1，检查行结构是否成组、序号是否单调。肉眼看几十行没问题，跑几万行就得靠程序判定。

十一、用户态 spinlock 的适用边界 #

写完、跑对、也拿到了正确结果。但它到底该不该用在生产里？给一张明确的表：

维度 适合 不适合
临界区长度 几十到几百纳秒 毫秒级，含 I/O 或系统调用
核数 多于线程数 单核，线程数超过核数
抢占 不会被长时间抢占 线程被调度器切走
优先级 各线程优先级接近 持锁者优先级低于等锁者
平台 有多核原子指令 没有原子指令的单片机

优先级这一条要单独说。用户态 spinlock 不认识优先级，低优先级的线程拿到锁后被高优先级的线程按着摩擦，高优先级线程狂转，这就是优先级反转。mutex 有优先级继承机制去缓解，spinlock 没有，它连「谁在等」都不知道。实时系统里这一条足以否决掉自旋方案。

pthread_spin_lock 在 glibc 里的实现也不是纯自旋。它在有限次重试之后会退让，甚至在某些版本里会短暂睡眠，因为纯自旋在通用系统上确实不好用。你自己手写的那版没有这些保护，用它就等于默认接受所有边界。

结论摆在这里：用户态手写 spinlock 的价值在教学和极窄的嵌入式场景。日常写应用，用 mutex；写驱动，看清楚内核 spinlock 的规则；只有当你需要理解「同步的原子性从哪来」的时候，自己写一遍最管用。

十二、从用户态到内核态 #

内核里的 spinlock 和我们写的是同一个东西，但多了几条用户态用不上的规则：

维度 用户态 spinlock 内核态 spinlock
原子性来源 ldrex / strex，或 C11 原子 同一套硬件指令
屏障 显式 dmb，或 acquire / release smp_mb 系列宏，编译期按配置替换
抢占 由调度器决定，锁管不了 必须显式 spin_lock 里关抢占
中断 不涉及 与中断共享数据时要关中断，用 spin_lock_irqsave
调试 无 有 lockdep 查死锁、查锁序
持有期间 可以睡 绝对不能睡

最要紧的一条是「持有内核 spinlock 期间不能睡眠」。内核 spinlock 的获取路径会关抢占，此时如果调用了会睡眠的函数，就会出现「关着抢占等别人唤醒」的死局，而这把锁往往正是在唤醒路径上被持有的。用户态没这个问题，因为你的锁不会关抢占，调度器想来就来。

第二条是中断。中断上下文里不能睡眠，所以它只能自旋；而如果进程上下文持有锁时被中断打断，中断处理程序又去抢同一把锁，就会在同一个核上自己等自己。所以内核提供 spin_lock_irqsave 这样的组合接口，关中断加关抢占一次做完。用户态不存在这个层级，你连中断都看不到。

用 perf stat 看一眼自己的自旋有多贵，是这项实验里最值钱的一步：

bash
perf stat -e cycles,instructions,cache-misses ./spinlock
perf stat -e cs ./spinlock        # cs 是上下文切换次数

cs 特别低说明都在自旋，cs 很高说明让出太频繁。两个极端都不好，调参数得看这两个数。

十三、易错点速查 #

按踩坑频率排，前三条最致命：

错误 后果 正确做法
用普通读写实现测试并设置 两个线程同时进临界区 用 ldrex/strex、CAS 或 C11 原子
换了原子指令但漏了屏障 读到临界区外的旧数据 加锁后用 acquire，解锁前用 release
把 volatile 当同步手段 编译器不动了，CPU 照样重排 volatile 只防优化删除，不防重排
内联汇编漏了 & 早写约束 特定优化等级下输入寄存器被冲掉 输出操作数加 &，+ 标记读写
原子操作忘了重试 失败那次被当成成功，锁被两人持有 strex 非 0 就 bne 回开头
单核上纯自旋 持锁者拿不到 CPU，永久卡住 加 sched_yield，或改睡眠锁
临界区里有 printf 或系统调用 自旋时间远超一次上下文切换 把 I/O 拿出临界区
用锁保护非共享数据 性能白掉，还引入死锁风险 先想清楚谁在共享什么
调试加 printf 改变了时序 bug 消失，上线再现 用 perf、ftrace 或线程日志观察

调试这一条值得多说一句。printf 本身带锁、带系统调用、带内存屏障效果，它会把竞态窗口撑开或者干脆堵住。用 printf 调 spinlock 的结果往往是一调就好、不调就坏。要么把日志写到每线程独立的文件，要么用 perf record 采样。

最后收尾。写一遍下来，能带走的东西只有这几条：

  1. 锁的语义四行就完了，难的是让「读—判断—写」在硬件上不可分割。
  2. 原子指令解决互斥，屏障解决可见性，两者缺一不可。
  3. 编译器乱序和 CPU 乱序是两个独立的敌人，得分别对待。
  4. volatile 不是同步原语，任何时候都别指望它。
  5. 自旋的代价是实打实的 CPU 时间，临界区一长就该换成睡眠。
  6. 验证 spinlock 只能靠大规模并发跑，一次失败就足以证明它错，一次成功什么也证明不了。
