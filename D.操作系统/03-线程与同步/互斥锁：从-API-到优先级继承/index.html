一、互斥锁解决什么问题 #

counter++ 不是一条指令。编译器把它拆成读、加、写三步，三步之间随时被切走。

c
/* 两个线程各做 100 万次自增，结果几乎不会是 2000000 */
static long counter = 0;

void *worker(void *arg)
{
    for (long i = 0; i < 1000000; i++)
        counter++;      /* load / add / store，中间可以插进任何东西 */
    return NULL;
}

线程 A 读到 100 被抢占，线程 B 也读到 100 并写回 101，A 恢复后写回 101。两次自增，只留下一次的结果。这类问题叫数据竞争，编译器不会帮你，加 -O2 只会让它更爱把变量塞进寄存器。

互斥锁做的事很朴素：把「读—改—写」这一组操作压成一个不可分割的临界区，同一时刻只放一个线程进去。

c
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
static long counter = 0;

void *worker(void *arg)
{
    for (long i = 0; i < 1000000; i++) {
        pthread_mutex_lock(&lock);
        counter++;
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

锁到底给了你三个保证 #

保证 含义 反面
互斥 同一时刻只有一个线程处于临界区 两个线程同时改同一块数据
可见性 unlock 之前的写，lock 之后的线程能看见 一个线程写完了，另一个线程读到旧值
顺序 临界区里的语句不会被其他持锁者穿插 复合操作被拆散成半成品状态

可见性这条经常被忽略。它靠的是 lock 的 acquire 语义和 unlock 的 release 语义，不是靠 volatile，也不是靠 CPU 时钟对齐。你在锁外读一个被锁保护的变量，读到什么都算正常。

它不保证的事 #

  • 不保证公平。unlock 之后谁来拿锁，由调度器和 futex 队列决定，不排队先来后到。写依赖顺序的代码，是自己在赌。
  • 不防你自己写出来的死锁。锁只保证互斥，不替你想加锁顺序。
  • 不是异步信号安全的。信号处理函数里碰互斥锁，等于在雷区里跑步。
  • 不保护没走同一把锁的路径。有的线程加锁改，有的线程裸着改，等于没加锁。

二、互斥锁的创建与销毁 #

原型 #

c
#include <pthread.h>

int pthread_mutex_init(pthread_mutex_t *restrict mutex,
                       const pthread_mutexattr_t *restrict attr);
int pthread_mutex_destroy(pthread_mutex_t *mutex);

两个函数都是 POSIX.1-1996 的标准接口（Pthreads 随 POSIX.1c-1995 并入 POSIX.1）。返回值规矩统一：成功返回 0，失败返回错误号，不写 errno。所以别写 if (ret == -1) perror(...)，那套是 syscall 的规矩，这里不适用。

attr 传 NULL 就是默认属性：进程内私有，锁类型取实现默认值。

初始化的语义 #

pthread_mutex_init 把 mutex 指向的那块内存按 attr 的当前值填成一把可用的锁。它只写内存，不分配内核对象，也不注册任何全局表项（robust 锁会挂进 glibc 的健壮链表，这是例外）。

几个必须记住的点：

  • pthread_mutex_t 是值类型，可以放在全局区、栈上、堆上、结构体成员里。放哪儿都行，但放栈上就要保证栈帧活着的期间才有人用它。
  • 已经被初始化过的锁，再 init 一次是未定义行为。POSIX 允许实现返回 EBUSY，glibc 实际返回 0 并直接覆盖。别指望它报错救你。
  • 属性是在 init 那一刻拷贝进锁里的。之后改属性对象、甚至销毁属性对象，都不影响已经初始化好的锁。

错误码 #

错误码 触发条件 处理方式
EAGAIN 系统线程资源不足，拿不到初始化所需的内部资源 降并发或延后重试
ENOMEM 内存不够 检查是否有泄漏
EPERM 调用者没有权限设置请求的属性 查 setprotocol / setprioceiling 的权限前提
EBUSY 对已初始化的锁重复初始化 代码逻辑错了，回去改

销毁的语义 #

c
int pthread_mutex_destroy(pthread_mutex_t *mutex);

destroy 做两件事：检查锁的状态，把锁标记成「未初始化」。LinuxThreads 时代内核里根本没有 mutex 对象，所以这个函数几乎只是状态检查；现代 glibc 里它还要摘掉 robust 链表节点、清 PI 状态，省不掉。

两个 EBUSY 场景，一个都不能漏：

  1. 锁正被某个线程持有。销毁一把有人拿着的锁，等待队列里的线程会挂在野指针上。
  2. 锁正被某个条件变量当关联锁用，有线程卡在 pthread_cond_wait 上。条件变量内部持有这把锁的引用，先销毁锁就是把引用打断。
c
pthread_mutex_t lock;

if (pthread_mutex_init(&lock, NULL) != 0) {
    fprintf(stderr, "pthread_mutex_init failed\n");
    exit(EXIT_FAILURE);
}

/* ... 临界区 ... */

if (pthread_mutex_destroy(&lock) != 0) {
    fprintf(stderr, "pthread_mutex_destroy failed\n");
}

销毁之后，那块内存里的字节还在，但内容没有意义。要再用，就重新 init，或者干脆重新赋 PTHREAD_MUTEX_INITIALIZER。

生命周期规则 #

场景 做法
全局锁、进程活多久它活多久 PTHREAD_MUTEX_INITIALIZER，不写 init，不写 destroy
锁是某个对象的成员 对象 create 里 init，对象 destroy 里 destroy
要在锁上做属性定制 必须先 init 属性对象，再 pthread_mutex_init
锁被 cond_wait 用过 先让所有等待者退出，再 destroy 锁
要复用一把锁 destroy 之后重新 init，不要直接 init

三、静态初始化与动态初始化 #

静态初始化 #

c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

一行搞定，等价于 pthread_mutex_init(&lock, NULL)，但没有返回值可查，也不需要查。锁在程序加载时就处在可用状态，位于 .data / .bss，进程起来就能锁。

LinuxThreads 的实现里 pthread_mutex_t 是个结构体，PTHREAD_MUTEX_INITIALIZER 就是一个结构常量，形如「锁字、持有者 tid、嵌套计数、锁类型、等待队列头」逐字段置初值。glibc 改成 union 加字节数组，宏展开成一串零，锁类型字段取 PTHREAD_MUTEX_TIMED_NP。x86-64 上 sizeof(pthread_mutex_t) 是 40 字节。

静态初始化能用的前提是：编译期就得知道锁在哪儿、要什么属性。它只给默认属性，改不了类型、改不了 pshared、改不了协议。

动态初始化 #

需要非默认属性时，走这条路；锁随对象创建时，也走这条路。

c
typedef struct {
    pthread_mutex_t lock;
    int refcount;
    char *buf;
} cache_t;

int cache_create(cache_t *c)
{
    if (pthread_mutex_init(&c->lock, NULL) != 0)
        return -1;
    c->refcount = 0;
    c->buf = NULL;
    return 0;
}

void cache_destroy(cache_t *c)
{
    pthread_mutex_destroy(&c->lock);
    free(c->buf);
}

两者对照 #

项目 静态 PTHREAD_MUTEX_INITIALIZER 动态 pthread_mutex_init
属性 只能是默认属性 任意属性组合
失败处理 无返回值，构造期就定型 必须检查返回码
位置 全局、静态、编译期已知 栈、堆、结构体，运行期决定
销毁 不需要，调 destroy 也可（glibc 返回 0） 必须配对 destroy
标准 POSIX.1-1996 POSIX.1-1996
适合 单例、模块级全局锁、极简场景 带属性的锁、对象成员、需要重建的锁

属性对象与锁是两次初始化 #

顺序不能反：先配属性，再建锁，最后销毁属性对象。

text
pthread_mutexattr_init(&attr)        属性对象：填默认值
        │
        ├── settype(RECURSIVE)
        ├── setpshared(PROCESS_SHARED)
        └── setprotocol(PRIO_INHERIT)
        │
        ▼
pthread_mutex_init(&lock, &attr)     锁：拷贝属性当前值
        │
        ▼
pthread_mutexattr_destroy(&attr)     属性对象用完即毁，锁不受影响

pthread_mutex_init 拷贝的是属性对象的值。所以属性对象可以是栈上的临时变量，建完锁立刻 destroy，锁照样带着你设的属性活着。

四、互斥锁属性的完整清单 #

属性对象自己的两个函数 #

c
#include <pthread.h>

int pthread_mutexattr_init(pthread_mutexattr_t *attr);
int pthread_mutexattr_destroy(pthread_mutexattr_t *attr);

POSIX.1-1996。pthread_mutexattr_t 是 opaque 类型，头文件里只给你一个字节数组，别去碰它的内部字段，也别用 memcpy 复制一个没初始化的过来。

  • pthread_mutexattr_init 成功返回 0，失败返回 ENOMEM。
  • pthread_mutexattr_destroy 成功返回 0，attr 无效返回 EINVAL。
  • 销毁后的属性对象要重新用，必须先 init。

init 出来的默认值是：pshared = PTHREAD_PROCESS_PRIVATE，type = PTHREAD_MUTEX_DEFAULT，protocol = PTHREAD_PRIO_NONE，robustness = PTHREAD_MUTEX_STALLED。

属性函数总表 #

属性 设置函数 获取函数 取值 标准版本
锁类型 pthread_mutexattr_settype pthread_mutexattr_gettype PTHREAD_MUTEX_NORMAL / ERRORCHECK / RECURSIVE / DEFAULT POSIX.1-1996
作用范围 pthread_mutexattr_setpshared pthread_mutexattr_getpshared PTHREAD_PROCESS_PRIVATE / PTHREAD_PROCESS_SHARED POSIX.1-1996
优先级协议 pthread_mutexattr_setprotocol pthread_mutexattr_getprotocol PTHREAD_PRIO_NONE / PRIO_INHERIT / PRIO_PROTECT POSIX.1-1996 实时扩展
优先级上限（属性） pthread_mutexattr_setprioceiling pthread_mutexattr_getprioceiling SCHED_FIFO 优先级范围内的整数 POSIX.1-1996 实时扩展
优先级上限（锁本体） pthread_mutex_setprioceiling pthread_mutex_getprioceiling 同上 POSIX.1-1996 实时扩展
健壮性（旧） pthread_mutexattr_setrobust_np pthread_mutexattr_getrobust_np PTHREAD_MUTEX_ROBUST_NP / STALLED_NP Solaris 扩展，非 POSIX
健壮性（新） pthread_mutexattr_setrobust pthread_mutexattr_getrobust PTHREAD_MUTEX_ROBUST / STALLED POSIX.1-2008

带 _np 的一组是「不可移植」标记，来自 Solaris，后来 POSIX.1-2008 把健壮锁收编成不带后缀的版本。新代码用不带 _np 的。

作用范围：pshared #

c
int pthread_mutexattr_setpshared(pthread_mutexattr_t *attr, int pshared);
int pthread_mutexattr_getpshared(const pthread_mutexattr_t *attr, int *pshared);

setpshared 成功返回 0，attr 无效或 pshared 取值不认识返回 EINVAL。getpshared 同理，另外在 pshared 指针为空时返回 EINVAL。

POSIX 取值 Solaris 对应 含义
PTHREAD_PROCESS_PRIVATE USYNC_THREAD 只同步本进程内的线程，默认值
PTHREAD_PROCESS_SHARED USYNC_PROCESS 同步跨进程的线程，锁必须放在共享内存里
无 USYNC_PROCESS_ROBUST Solaris 专有，属主死了别人还能接管

跨进程用法要点：锁本体必须在 mmap(MAP_SHARED) 或 shmget 出来的共享区，而且只能有一个进程做 init。让两个进程各自 init 同一块内存，等于两套状态互相覆盖。

c
/* 父进程建锁，子进程只负责加锁解锁 */
pthread_mutexattr_t attr;
pthread_mutex_t *lock;

pthread_mutexattr_init(&attr);
pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED);

lock = mmap(NULL, sizeof(*lock), PROT_READ | PROT_WRITE,
            MAP_SHARED | MAP_ANONYMOUS, -1, 0);
pthread_mutex_init(lock, &attr);
pthread_mutexattr_destroy(&attr);

/* fork 之后两边都拿到同一个 lock 映射 */
pthread_mutex_lock(lock);
/* 操作共享区 */
pthread_mutex_unlock(lock);

一个把属性用起来的封装 #

c
static int make_mutex(pthread_mutex_t *m, int type, int protocol)
{
    pthread_mutexattr_t a;

    if (pthread_mutexattr_init(&a) != 0)
        return -1;

    /* 属性对象是栈上临时变量，设完值就能交给 pthread_mutex_init */
    if (pthread_mutexattr_settype(&a, type) != 0)
        goto fail;
    if (pthread_mutexattr_setprotocol(&a, protocol) != 0)
        goto fail;
    if (pthread_mutex_init(m, &a) != 0)
        goto fail;

    pthread_mutexattr_destroy(&a);
    return 0;

fail:
    pthread_mutexattr_destroy(&a);
    return -1;
}

注意 goto fail 走的是同一条 destroy 路径。属性对象初始化失败就不用销毁，初始化成功之后每条失败分支都要销毁，漏一条就是一次小泄漏，跑几千次就是一片。

五、锁类型：普通、检错、递归 #

锁类型决定「同一个线程第二次加锁」和「非持有者解锁」这两件事怎么处理。四种取值，其中三种有明确语义。

原型 #

c
#include <pthread.h>

int pthread_mutexattr_settype(pthread_mutexattr_t *attr, int type);
int pthread_mutexattr_gettype(const pthread_mutexattr_t *attr, int *type);

POSIX.1-1996，RECURSIVE 与 ERRORCHECK 在早期的 POSIX.1c 里就存在，不是后来补的。

  • 成功返回 0。
  • attr 无效返回 EINVAL。
  • type 不在合法取值内返回 EINVAL。

settype 的 type 参数和 gettype 的 type 参数类型不同：前者是值，后者是 int * 出参。写反了编译器不报错，运行时崩在奇怪的地方。

四种取值 #

c
PTHREAD_MUTEX_NORMAL       /* 不检测，默认行为的多数实现 */
PTHREAD_MUTEX_ERRORCHECK   /* 自查：重锁、错主解锁都报错 */
PTHREAD_MUTEX_RECURSIVE    /* 同线程可重入，要等次数的 unlock */
PTHREAD_MUTEX_DEFAULT      /* 实现映射，glibc 上等同 NORMAL */

三种类型对照 #

行为 NORMAL ERRORCHECK RECURSIVE
同线程重复加锁 死锁 返回 EDEADLK 成功，计数 +1
非持有者解锁 未定义行为 返回 EPERM 返回 EPERM
解锁未锁定的锁 未定义行为 返回 EPERM 返回 EPERM
需要几次 unlock 释放 1 1 N（N 为加锁次数）
内部维护持有者 tid 否 是 是
内部维护嵌套计数 否 否 是
每次加锁的开销 最低 中（查 tid） 中（查 tid + 计数）
典型用途 性能敏感、逻辑已自证正确 开发调试期、代码评审兜底 递归调用、回调重入
标准版本 POSIX.1-1996 POSIX.1-1996 POSIX.1-1996

NORMAL 那两行「未定义行为」是字面意思：静默通过、直接崩掉、把锁状态搞坏，都算正常表现，标准不管。

PTHREAD_MUTEX_DEFAULT 的定位是「实现自己挑一个」。Solaris 把它映射成 NORMAL；glibc 在 x86 上也走 NORMAL 的快速路径。写代码时把它当 NORMAL 看，别依赖它变成别的。

检错锁到底检了什么 #

c
pthread_mutex_t m;
pthread_mutexattr_t a;

pthread_mutexattr_init(&a);
pthread_mutexattr_settype(&a, PTHREAD_MUTEX_ERRORCHECK);
pthread_mutex_init(&m, &a);
pthread_mutexattr_destroy(&a);

pthread_mutex_lock(&m);
int r = pthread_mutex_lock(&m);     /* r == EDEADLK，自锁被抓到 */
r = pthread_mutex_unlock(&m);       /* 返回 0，正常解锁 */
r = pthread_mutex_unlock(&m);       /* r == EPERM，锁没被持有 */

EDEADLK 意思是「你自己已经拿着了，再要就是自锁」。这是唯一能在运行时抓到自锁的机制，NORMAL 锁上它表现为卡死，调试时只能靠 gdb 打断点看栈。

递归锁的坑 #

c
pthread_mutexattr_init(&a);
pthread_mutexattr_settype(&a, PTHREAD_MUTEX_RECURSIVE);
pthread_mutex_init(&m, &a);
pthread_mutexattr_destroy(&a);

pthread_mutex_lock(&m);     /* 计数 1 */
pthread_mutex_lock(&m);     /* 计数 2 */
pthread_mutex_unlock(&m);   /* 计数 1，仍然持有 */
pthread_mutex_unlock(&m);   /* 计数 0，真正释放 */

加锁几次就要解锁几次，少一次锁就永远是「被持有」，其他线程全部卡死。递归锁只解决「同一线程重入」，不解决逻辑问题：能用递归锁的地方，多半是临界区划得太大，或者回调里偷偷加了锁。解锁也必须由同一线程完成，实测中某些实现不强制检查，但别赌。

一个判断表 #

你的处境 选什么
临界区短、加锁路径唯一、性能在意 NORMAL
团队合作、库对外提供、不确定调用方怎么写 ERRORCHECK
明确有同线程重入（回调、递归下降解析器） RECURSIVE
不确定、想跟平台默认走 DEFAULT，行为按 NORMAL 预期

六、加锁与解锁 #

原型 #

c
#include <pthread.h>

int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_unlock(pthread_mutex_t *mutex);
int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_timedlock(pthread_mutex_t *restrict mutex,
                            const struct timespec *restrict abstime);

前三个是 POSIX.1-1996，pthread_mutex_timedlock 是 POSIX.1-2001 新增（同批进标准的是 pthread_cond_timedwait 的补充和 clock_nanosleep）。

pthread_mutex_lock #

  • 锁空闲：原子地拿到，返回 0。
  • 锁被占：调用线程进等待队列睡眠，直到锁可用。这一步是阻塞的，睡多久没有上限。
  • 同一线程对 NORMAL 锁重复加锁：死锁，无返回值可看。
  • 成功返回 0；ERRORCHECK / RECURSIVE 上重锁返回 EDEADLK；mutex 无效返回 EINVAL。

pthread_mutex_unlock #

  • 归还锁，唤醒等待队列里的一个线程（不是全部）。
  • NORMAL 锁上，任何线程都能解，包括没加锁的线程。这是被允许的，也是踩坑源头。
  • ERRORCHECK / RECURSIVE 上，只有持有者能解，否则 EPERM。
  • 解锁一把没锁定的锁：NORMAL 上未定义，ERRORCHECK 上是 EPERM。

必须用「单入口单出口」写法 #

临界区里出现 return、break、goto、continue 漏掉解锁，是最常见的死锁来源。两条做法，选一个并坚持到底。

做法一，goto 统一出口：

c
int update(shared_t *s, const char *name)
{
    int ret = 0;

    pthread_mutex_lock(&s->lock);

    if (s->frozen) {
        ret = -EBUSY;
        goto out;
    }
    strcpy(s->name, name);
    s->count++;

out:
    pthread_mutex_unlock(&s->lock);
    return ret;
}

做法二，拆成「加锁壳 + 无锁芯」：无锁芯里可以自由 return，加锁壳只有三行，扫一眼就知道配对了。命名上加 _locked 后缀，让下一个改代码的人知道前提。

c
static int update_locked(shared_t *s, const char *name)
{
    /* 调用者保证已持锁，函数内部绝不再加锁 */
    if (s->frozen)
        return -EBUSY;
    strcpy(s->name, name);
    s->count++;
    return 0;
}

int update(shared_t *s, const char *name)
{
    pthread_mutex_lock(&s->lock);
    int ret = update_locked(s, name);
    pthread_mutex_unlock(&s->lock);
    return ret;
}

取消与信号这两件事 #

锁的加锁函数在 Linux 上不是取消点。线程卡在 pthread_mutex_lock 里时收到 pthread_cancel，延迟取消不会让它退出，它会继续等锁。等到了锁、继续跑，直到走到下一个真正的取消点。

这带来一个真实风险：线程拿到锁之后、解锁之前，正好在临界区里撞上一个取消点（read、write、sleep、pthread_cond_wait 都算），被取消退出，锁就永远留在加锁状态。清理函数是唯一的解法：

c
void cleanup_unlock(void *arg)
{
    pthread_mutex_unlock((pthread_mutex_t *)arg);
}

void *worker(void *arg)
{
    pthread_mutex_lock(&lock);
    pthread_cleanup_push(cleanup_unlock, &lock);

    /* 这里可以安全地出现取消点 */
    write(fd, buf, len);

    pthread_cleanup_pop(1);   /* 传 1：弹出并执行，等于解锁 */
    return NULL;
}

pthread_cleanup_push / pthread_cleanup_pop 必须成对出现在同一个词法作用域里，它们是宏，不是函数，中间夹 return 会编译不过。这一对的细节在《Pthread 线程生命周期：创建、取消与清理》里展开。

另一半：互斥锁不是异步信号安全的。信号处理函数里不能 pthread_mutex_lock。原因是主流程正好持着这把锁被打断时，信号处理函数再去要同一把锁，就自己锁死自己，而且没有任何超时能救。

七、非阻塞加锁：trylock #

原型 #

c
int pthread_mutex_trylock(pthread_mutex_t *mutex);

POSIX.1-1996。行为是 lock 的「不等版本」。

  • 锁空闲：拿到，返回 0。
  • 锁被占：立刻返回 EBUSY，不睡眠、不进队列。
  • ERRORCHECK 上同一线程重入：返回 EBUSY（注意不是 EDEADLK，这一点比 lock 更容易被写错）。
  • RECURSIVE 上同一线程重入：成功，计数 +1。
  • mutex 无效：EINVAL。

典型用法 #

场景一，探测：只在没人在用时顺手做点事，抢不到就跳过。

c
if (pthread_mutex_trylock(&cache->lock) == 0) {
    cache->hits++;          /* 抢到了，顺手更新统计 */
    pthread_mutex_unlock(&cache->lock);
}
/* 抢不到直接走人，不阻塞调用者 */

场景二，有兜底路径：抢不到锁就走另一条不需要锁的路。

c
if (pthread_mutex_trylock(&pool->lock) != 0) {
    /* 池子正忙，直接开一个新的临时对象，绕开共享结构 */
    return make_temporary();
}
item = pool_take_locked(pool);
pthread_mutex_unlock(&pool->lock);
return item;

场景三，避免持锁顺序死锁：需要两把锁时，第二把用 trylock，失败就退回第一把，稍后重试。这是经典的退让策略。

c
/* 从 a 转到 b，两把锁必须同时持有；反序路径存在 */
for (;;) {
    pthread_mutex_lock(&a.lock);
    if (pthread_mutex_trylock(&b.lock) == 0) {
        transfer_locked(&a, &b);
        pthread_mutex_unlock(&b.lock);
        pthread_mutex_unlock(&a.lock);
        return;
    }
    /* 拿不到 b，先放开 a，让持 b 的线程有机会完成 */
    pthread_mutex_unlock(&a.lock);
    sched_yield();
}

不要用 trylock 代替 lock #

trylock 返回 EBUSY 时，锁的状态一点没变，你的业务也一点没往前走。写成这样就是错的：

c
/* 反面例子：忙等，CPU 空转烧满一个核 */
while (pthread_mutex_trylock(&lock) != 0)
    ;   /* 什么都不做 */

正确的做法只有两种：要么阻塞等（用 lock），要么放弃这次操作（上面的探测模式）。需要「等一会儿」的语义，用下一节的 timedlock。

三者对比 #

项目 pthread_mutex_lock pthread_mutex_trylock pthread_mutex_timedlock
锁被占时的行为 无限期睡眠 立刻返回 EBUSY 睡到超时或拿到锁
是否有超时 无 等同于超时为 0 有，由 abstime 指定
能否在信号处理函数里用 不能 不能 不能
是否是取消点 否 否 否
标准版本 POSIX.1-1996 POSIX.1-1996 POSIX.1-2001
主要用途 常规临界区 探测、退让、可选路径 有响应时间要求的等待

八、超时加锁：timedlock #

原型 #

c
#include <pthread.h>
#include <time.h>

int pthread_mutex_timedlock(pthread_mutex_t *restrict mutex,
                            const struct timespec *restrict abstime);

POSIX.1-2001 新增。abstime 是绝对时间，不是相对时长，这一点写错的人最多。

abstime 怎么算 #

基准时钟是 CLOCK_REALTIME，也就是墙上时间。要「再等 500 毫秒」，得先取当前时间再加。

c
struct timespec ts;

clock_gettime(CLOCK_REALTIME, &ts);
ts.tv_nsec += 500 * 1000 * 1000;        /* +500ms */
if (ts.tv_nsec >= 1000000000L) {        /* 进位 */
    ts.tv_sec  += ts.tv_nsec / 1000000000L;
    ts.tv_nsec %= 1000000000L;
}

int r = pthread_mutex_timedlock(&lock, &ts);
if (r == ETIMEDOUT) {
    /* 到点还没拿到锁 */
} else if (r == 0) {
    /* 拿到了，正常走临界区 */
    pthread_mutex_unlock(&lock);
}

三个必须处理的细节：

  • tv_nsec 必须在 [0, 999999999] 区间内。直接写 ts.tv_nsec += 800000000 两次就溢出，EINVAL。
  • 有人会写 ts.tv_nsec += 500000000 然后手动 ts.tv_sec += ts.tv_nsec / 1000000000，这是对的；写成 ts.tv_sec += 1 硬编码进位，只在恰好溢出时对。
  • CLOCK_REALTIME 会被 settimeofday、NTP 调整改掉。系统时间往后跳一小时，你那个「等 500ms」就变成了等一小时。安全关键代码里要评估这一点。

返回值 #

返回值 含义 处理
0 拿到锁 正常进临界区
ETIMEDOUT 超时，锁没拿到 走降级路径或报错
EINVAL abstime 的 tv_nsec 越界，或 mutex 无效 修时间计算
EDEADLK ERRORCHECK 上同线程重入 说明有自锁
EOWNERDEAD 前一属主死在这把健壮锁上 见健壮锁一节

ETIMEDOUT 时没有拿到锁，不需要解锁。这一点和「拿到了再失败」的情况不同。

重试循环 #

需要「总共等 2 秒，但中间可以检查退出标志」时，用循环加短超时。

c
struct timespec deadline;
clock_gettime(CLOCK_REALTIME, &deadline);
deadline.tv_sec += 2;

for (;;) {
    int r = pthread_mutex_timedlock(&lock, &deadline);
    if (r == 0)
        break;                      /* 拿到锁 */
    if (r != ETIMEDOUT)
        return -1;                  /* 真错误，别再试 */
    if (atomic_load(&stop_requested))
        return -ECANCELED;          /* 外部要求退出，主动放弃 */
}

循环里每一轮都传同一个 deadline，绝对时间不随循环次数漂移——这正是用绝对时间的理由。如果每轮都 now += 100ms，总时长会随重试次数膨胀。

三个函数的取舍 #

你的需求 用哪个
一定要拿到锁 pthread_mutex_lock
拿不到也要继续干别的 pthread_mutex_trylock
有明确最长等待时间 pthread_mutex_timedlock
有响应时间上限、但不能死等 timedlock + 退出标志
高优先级线程不能被低优先级拖住 不是选函数的事，见优先级继承一章

九、死锁的产生与规避 #

死锁的四个必要条件教科书上写得很清楚：互斥、占有且等待、不可剥夺、循环等待。互斥锁天生满足前三个，你能动手的只有第四个。所以规避死锁的全部工作，就是别让加锁关系成环。

形态一：自锁 #

同一个线程对 NORMAL 锁加两次，第二次永远等不到。

c
pthread_mutex_lock(&lock);
pthread_mutex_lock(&lock);   /* 卡死在这里 */

难点在于两层函数调用把加锁藏起来了：outer() 加了锁，调用的 inner() 里又加了一次。排查手段就一个：把外层锁换成 PTHREAD_MUTEX_ERRORCHECK，自锁立刻变成 EDEADLK 返回值，几秒钟定位。

形态二：加锁顺序反转 #

线程 1 拿 A 再要 B，线程 2 拿 B 再要 A。

c
/* 线程 1 */
pthread_mutex_lock(&a);
pthread_mutex_lock(&b);     /* 等线程 2 放 b */
pthread_mutex_unlock(&b);
pthread_mutex_unlock(&a);

/* 线程 2 —— 同时刻 */
pthread_mutex_lock(&b);
pthread_mutex_lock(&a);     /* 等线程 1 放 a */
pthread_mutex_unlock(&a);
pthread_mutex_unlock(&b);

两条线程各持一把，各等一把，谁也不放。这是线上最常见的一种，触发概率低，压测跑不出来，用户量上来才炸。

解法一，全局加锁顺序。给每把锁一个编号，永远按编号从小到大加。

c
/* 约定：锁有 id，加锁一律按 id 升序 */
enum { LOCK_ACCOUNT = 10, LOCK_LEDGER = 20, LOCK_AUDIT = 30 };

static void transfer(account_t *from, account_t *to, long amount)
{
    account_t *first  = from->lock_id < to->lock_id ? from : to;
    account_t *second = from->lock_id < to->lock_id ? to : from;

    pthread_mutex_lock(&first->lock);
    pthread_mutex_lock(&second->lock);

    from->balance -= amount;
    to->balance   += amount;

    pthread_mutex_unlock(&second->lock);
    pthread_mutex_unlock(&first->lock);
}

交换顺序时用指针交换，不要用条件分支写两套加锁代码，那样迟早漏掉一处。

解法二，退让重试。第二把锁用 trylock，失败就放开第一把。上一章的 transfer 示例就是这个套路。代价是活锁（两边不停退让），要加随机退避。

解法三，改成单锁。两把锁保护的到底是不是同一份状态？合并成一把锁，问题直接消失，性能损失往往比想象的小。

形态三：临界区里调用外部代码 #

c
pthread_mutex_lock(&lock);
log_write(msg);              /* 内部又去拿 log_lock */
callback(user_data);         /* 天知道它拿什么锁 */
pthread_mutex_unlock(&lock);

库函数、回调、malloc 的调试钩子、信号处理里的 printf，都会在你持锁时去拿别的锁。规矩是：持锁期间只碰自己明确知道不碰锁的东西。日志、回调、内存分配，全部挪到锁外——锁内先拷出快照，放锁之后再回调。

形态四：锁没被释放（逻辑泄漏） #

不是真死锁，效果一样。两个来源：return 绕过了解锁（见前一章的单出口写法），或者线程在临界区里被取消（见 pthread_cleanup_push）。

用工具抓。valgrind --tool=helgrind 能报锁序反转和丢锁，gdb 挂上去 thread apply all bt 看谁在等谁。

规避清单 #

措施 解决哪种形态 成本
全局锁序编号 顺序反转 需要全项目遵守，评审把关
trylock 退让 顺序反转 有活锁风险，要加退避
合并锁 顺序反转、自锁 并发度下降
缩小临界区 外部代码重入 无，只有好处
ERRORCHECK 开发期 自锁 有性能开销，只在 debug 构建开
pthread_cleanup_push 取消导致的泄漏 几行代码
单入口单出口 return 泄漏 代码风格统一
持锁期间禁阻塞 I/O 长时持锁引发的连锁阻塞 需要重构调用链

十、优先级继承与优先级上限 #

这一章讲的是实时系统里的优先级反转问题。它跟锁类型没关系，跟调度策略有关系。

优先级反转是什么 #

三个线程，优先级 高 > 中 > 低。低优先级线程持有一把锁，高优先级线程要这把锁，被阻塞。此时中优先级线程就绪，它不碰这把锁，直接抢占低优先级线程。结果是：高优先级线程在等一个被中优先级线程挤走的低优先级线程。

text
低  ──[持锁]──────────────[被抢占，迟迟不释放]
中  ──────────[抢占，一直跑]──────────────
高  ──────[等锁]──────────────────────────[终于拿到]

高优先级线程的实际等待时间 = 中优先级线程的执行时间 + 低优先级的剩余临界区

1997 年火星探路者号在火星表面反复重启，就是优先级反转撞上了看门狗。这是这个问题的经典案例。

解决办法：让持锁者快点跑完 #

两条路线，改的是持锁线程的调度属性。

协议属性 #

c
#include <pthread.h>

int pthread_mutexattr_setprotocol(pthread_mutexattr_t *attr, int protocol);
int pthread_mutexattr_getprotocol(const pthread_mutexattr_t *attr, int *protocol);

POSIX.1-1996 实时扩展（_POSIX_THREAD_PRIO_INHERIT、_POSIX_THREAD_PRIO_PROTECT）。编译和运行时都要确认这两个宏定义了，sysconf(_SC_THREAD_PRIO_INHERIT) 能再确认一次。

三个取值：

协议 取值 行为 代价
无 PTHREAD_PRIO_NONE 默认值。持锁不改变任何线程的优先级 反转完全暴露
继承 PTHREAD_PRIO_INHERIT 持锁者被临时抬到所有等待者的最高优先级 每次加锁要维护等待者优先级，内核路径长
保护 PTHREAD_PRIO_PROTECT 一进临界区就把自己抬到锁的优先级上限 上限设高了会压制别的线程

PTHREAD_PRIO_NONE：优先级与锁无关。普通分时任务用这个，别乱开继承。

PTHREAD_PRIO_INHERIT：等锁的线程把自己的优先级「借」给持锁者。低优先级 10 的线程拿着锁，高优先级 20 的线程来等，持锁者立刻变成 10→20，中优先级 15 的线程就抢不动它了。等锁的线程一放锁，优先级立刻回落。

text
thrd1（prio 10，持锁）  →  thrd2（prio 20）来等锁  →  thrd1 提升到 20
                                                       ↓
                                            释放锁后回落至 10

传播是链式的：一把 PI 锁的持锁者本身在等另一把锁，提升会沿着等待链继续传下去。glibc 的 PI 实现走 futex 的 FUTEX_LOCK_PI，比普通 FUTEX_WAIT 重不少。属主崩溃时处理也和 PI 挂钩：带 _POSIX_THREAD_PRIO_INHERIT 的锁在属主死后，内核里的 PI 状态要重置，否则等待者的优先级提升会永远挂在那儿。

PTHREAD_PRIO_PROTECT：不看谁在等，进临界区就抬到锁的优先级上限。上限必须设成「所有会锁这把锁的线程中最高的那个优先级」。哪怕没有更高优先级线程来抢，持锁者也是高优先级状态。好处是实现简单、不用维护等待链；坏处是设错了就出问题——上限过低，保护失效；上限过高，一个不相干的关键线程会被长时间压住。

两者不能同时用。一把锁只能设一个协议。

返回值 #

setprotocol 成功返回 0，失败返回错误号：

错误码 含义
ENOSYS 实现不支持，_POSIX_THREAD_PRIO_INHERIT 和 _POSIX_THREAD_PRIO_PROTECT 都没定义
ENOTSUP 实现认识这个值但当前不支持
EINVAL attr 无效，或 protocol 不是合法取值
EPERM 调用者没有设置该协议所需权限（实时调度策略相关）

getprotocol 的返回码集合相同：ENOSYS、EINVAL、EPERM。

优先级上限：属性对象上的设置 #

c
int pthread_mutexattr_setprioceiling(pthread_mutexattr_t *attr, int prioceiling);
int pthread_mutexattr_getprioceiling(const pthread_mutexattr_t *attr, int *prioceiling);

POSIX.1-1996 实时扩展，前提是 _POSIX_THREAD_PRIO_PROTECT 已定义。

  • prioceiling 取值必须在 sched_get_priority_min(SCHED_FIFO) 到 sched_get_priority_max(SCHED_FIFO) 之间。
  • 设错了返回 EINVAL；实现不支持返回 ENOSYS；权限不够返回 EPERM。
  • attr 只在 protocol 为 PTHREAD_PRIO_PROTECT 时才看这个值。协议是 NONE 或 INHERIT 时，设了也不起作用。
c
pthread_mutexattr_t a;
pthread_mutex_t lock;
int hi_max = sched_get_priority_max(SCHED_FIFO);

pthread_mutexattr_init(&a);
pthread_mutexattr_setprotocol(&a, PTHREAD_PRIO_PROTECT);
pthread_mutexattr_setprioceiling(&a, hi_max);     /* 取本场景最高优先级 */
pthread_mutex_init(&lock, &a);
pthread_mutexattr_destroy(&a);

上限的选取准则：至少等于所有会锁这把锁的线程的最高优先级。低一个档位就等于保护失效，高到顶格则把整个实时调度让给这一把锁。

优先级上限：锁本体上的修改 #

c
int pthread_mutex_setprioceiling(pthread_mutex_t *mutex, int prioceiling, int *old_ceiling);
int pthread_mutex_getprioceiling(const pthread_mutex_t *mutex, int *prioceiling);

这两个操作的是一把已经初始化好的锁，不是属性对象。前者会在内部先锁住 mutex，改完再解锁，等于顺带做了一次加锁。

  • 成功返回 0，并把旧上限写进 old_ceiling。
  • 失败时上限保持不变。
  • 内部加锁不解锁是不行的，所以调用 setprioceiling 时如果别的线程持着这把锁，你会阻塞在那里。
  • 错误码：ENOSYS（_POSIX_THREAD_PRIO_PROTECT 未定义）、EINVAL（prioceiling 越界，或 mutex 无效）、EPERM（权限不足）。
c
int old;

if (pthread_mutex_setprioceiling(&lock, new_ceiling, &old) != 0) {
    /* 上限没改成功，仍是 old */
}
/* 恢复旧上限 */
pthread_mutex_setprioceiling(&lock, old, NULL);

旧上限之所以重要，是因为上限改动是全局的：你为了自己这段代码调高了上限，别人拿这把锁时也被抬到那个高度。改动要还原。

别把继承当默认选项 #

优先级继承只在实时调度（SCHED_FIFO / SCHED_RR）下才有意义。分时调度（SCHED_OTHER）的线程没有可继承的优先级，设了 PTHREAD_PRIO_INHERIT 只是给每次加锁加了内核开销。

判断顺序：

  1. 你的线程用 SCHED_OTHER？跳过这一整章，反转不适用于你。
  2. 用实时调度且有不同优先级？先试 PTHREAD_PRIO_INHERIT，它对代码几乎无侵入。
  3. 锁的临界区极短、且能静态算出上限？PTHREAD_PRIO_PROTECT 的实现路径更短。
  4. 两者都不用，就得靠设计规避：别让低优先级线程持有高优先级线程要的锁。

十一、健壮互斥锁 #

它解决的是「持锁者死了」 #

普通锁有个死结：线程在临界区里崩掉、被 SIGKILL、或者 exit 走了，锁还是「被持有」状态，等待者永远等下去。健壮锁把这件事变成可检测的错误。

新旧两套接口 #

c
/* POSIX.1-2008 标准接口 */
int pthread_mutexattr_setrobust(pthread_mutexattr_t *attr, int robustness);
int pthread_mutexattr_getrobust(const pthread_mutexattr_t *attr, int *robustness);
int pthread_mutex_consistent(pthread_mutex_t *mutex);

/* Solaris 出身、带 _np 的旧接口 */
int pthread_mutexattr_setrobust_np(pthread_mutexattr_t *attr, int robustness);
int pthread_mutexattr_getrobust_np(pthread_mutexattr_t *attr, int *robustness);
int pthread_mutex_consistent_np(pthread_mutex_t *mutex);

新代码用不带 _np 的。glibc 两个都提供，_np 版本在 _GNU_SOURCE 或 _POSIX_C_SOURCE >= 200809L 下可见。Solaris 文档里那句「仅在 _POSIX_THREAD_PRIO_INHERIT 定义时适用」是历史包袱，POSIX.1-2008 之后健壮性与 PI 已经解耦，两个属性可以独立设置。

两个取值 #

取值 属主死后的行为
PTHREAD_MUTEX_STALLED 默认值。锁永久停在加锁状态，等待者无限期挂住
PTHREAD_MUTEX_ROBUST 下一个 lock 返回 EOWNERDEAD，新属主接管

STALLED 这个名字很直白：卡死。这就是不设健壮性的默认后果。

ROBUST 的完整流程 #

c
pthread_mutexattr_t a;
pthread_mutex_t lock;

pthread_mutexattr_init(&a);
pthread_mutexattr_setrobust(&a, PTHREAD_MUTEX_ROBUST);
pthread_mutex_init(&lock, &a);
pthread_mutexattr_destroy(&a);

加锁方要检查三种结果：

c
int r = pthread_mutex_lock(&lock);

if (r == EOWNERDEAD) {
    /* 上一个属主死在临界区里，共享数据是半成品 */
    repair_shared_state();

    if (pthread_mutex_consistent(&lock) != 0) {
        /* 一致性确认失败，这把锁已经废了 */
        pthread_mutex_unlock(&lock);
        return -1;
    }
    /* 现在可以正常使用临界区 */
} else if (r == ENOTRECOVERABLE) {
    /* 之前有人接管却没确认一致，锁进入不可恢复状态 */
    return -1;
} else if (r != 0) {
    return -1;
}

/* 临界区 */
pthread_mutex_unlock(&lock);

关键在 pthread_mutex_consistent。它做一件事：告诉系统「这块数据我已经修好了，锁状态是干净可用的」。

  • 调了它再 unlock：锁回到普通可用状态，下一个线程正常拿到。
  • 没调它就 unlock：锁进入 ENOTRECOVERABLE 状态，之后所有 pthread_mutex_lock 全部返回 ENOTRECOVERABLE，永久废掉。

唯一的复活手段是销毁重建：

c
pthread_mutex_destroy(&lock);
pthread_mutex_init(&lock, &a);     /* 需要重新提供属性对象 */

EOWNERDEAD 会连续传播 #

在 pthread_mutex_consistent 之前，锁一直标记着「属主已死」。如果接管者在 consistent 之前又崩了，下一个来锁的线程同样拿到 EOWNERDEAD。机制上看这是对的：谁都没确认数据干净，那就继续交给下一个。

什么时候值得用 #

场景 用不用
多进程共享内存中的锁 用。进程崩溃是常态，卡死共享区更糟
长时间运行的服务，线程会被 SIGKILL 用
纯线程、进程退出就一起退 不用，收益为零
临界区操作的数据无法修复 不用，改用「检测到不一致就整体重置」的设计
追求极限加锁性能 不用，robust 要在链表上挂节点，慢

健壮锁的真问题不在 API，在数据修复。锁能告诉你「上一个属主半路死了」，但修不修得好共享数据，得看你的数据结构设计。修不好的话，返回 ENOTRECOVERABLE 让整个模块重置，比假装没事更安全。

错误码 #

pthread_mutexattr_setrobust：EINVAL（attr 或 robustness 无效）。

pthread_mutex_consistent：EINVAL（mutex 无效）、EPERM（调用者不是当前属主）。

pthread_mutex_lock 在健壮锁上的额外返回：EOWNERDEAD、ENOTRECOVERABLE。

pthread_mutexattr_setrobust_np 在旧实现上还会报 ENOSYS（选项未定义）和 ENOTSUP（取值不支持）。新接口把 ENOSYS 这一条去掉了。

十二、互斥锁的性能与选择 #

一次加锁到底花多少 #

glibc 的互斥锁是 futex 的两段式设计，快慢两个路径完全不在一个量级。

路径 发生条件 做了什么 量级
无竞争 锁空闲 一次原子 cmpxchg 把锁字从 0 改成 1 几十纳秒
有竞争但短暂 几次自旋内拿到 用户态自旋一段时间，适应锁会短暂尝试 微秒级
有竞争且要睡 自旋没拿到 futex(FUTEX_WAIT) 陷入内核，挂到等待队列 微秒到毫秒，含调度延迟
PI 锁 设了 PTHREAD_PRIO_INHERIT FUTEX_LOCK_PI，维护等待链 比普通路径高一个量级

结论：无竞争的加锁很便宜，有竞争的加锁很贵。优化的核心不是让锁更快，是让锁不被抢。

决定性能的三件事 #

临界区长度。 临界区里放 printf、写文件、malloc、发网络包，等于把锁变成串行化整个 I/O 的工具。

c
/* 坏：持锁做 I/O */
pthread_mutex_lock(&log_lock);
fprintf(log_fp, "%s\n", msg);
pthread_mutex_unlock(&log_lock);

/* 好：锁内只动内存，I/O 在锁外 */
pthread_mutex_lock(&log_lock);
ring_put(&log_ring, msg);
pthread_mutex_unlock(&log_lock);

锁的粒度。 一把大锁保护整个结构，最简单也最慢；每字段一把锁，最快也最易错。先写对的，profile 之后再拆。

争抢频率。 线程数超过物理核数，等待时间被调度放大。8 核机器上开 64 个线程抢同一把锁，比 8 个线程慢得多。

选型对照 #

需求 选择 理由
临界区会被抢占，涉及系统调用 pthread_mutex 睡眠不烧 CPU
临界区只有几条指令的计数 原子操作 __atomic_fetch_add 省掉锁的进出开销
临界区短到几纳秒、核数少 自旋锁（手写 atomic_flag） 省掉内核陷入
读多写少 pthread_rwlock 读可并行
要等某个条件成立 pthread_cond + mutex 锁不能表达「等待」
要控制并发数量 pthread_sem 或 pthread_cond 锁只允许 1 个
跨进程 PTHREAD_PROCESS_SHARED + 共享内存 或者用 sem 具名信号量

自旋锁在单核上没意义：你自旋的时候持锁者没机会跑。用户态手写自旋锁还容易漏掉编译器屏障和内存序，写之前先确认真的需要。

几个降低争抢的写法 #

每线程或每核分片。 计数器分 N 份，各线程更新自己那份，读的时候汇总。结构体按 64 字节对齐隔开，避免伪共享把缓存行来回弹。

读写分离。 数据一旦发布就不改，用「拷贝—修改—换指针」代替加锁改。

缩小临界区到只包含同步点。 复杂计算先在锁外算完，锁内只做一次指针替换。

一个实测套路 #

别猜，量化。

bash
# 锁竞争的上下文切换和内核时间
perf stat -e context-switches,cpu-migrations,task-clock ./bench

# 谁在等锁
perf lock record ./bench
perf lock report

# 死锁和锁序问题
valgrind --tool=helgrind ./bench

perf lock report 能直接列出争抢最严重的锁，比盯代码快。helgrind 慢，几十倍开销，只在功能验证阶段跑。

十三、与其他同步机制的配合 #

与条件变量：锁是配套件，不是主角 #

pthread_cond_wait 的签名要求传一把互斥锁，这把锁和条件变量是绑定关系。

c
pthread_mutex_lock(&m);
while (!ready)                        /* 必须 while，不能 if */
    pthread_cond_wait(&c, &m);
/* 这里 ready 为真，且已重新持锁 */
consume();
pthread_mutex_unlock(&m);

三个约束，破一个就出问题：

  • cond_wait 前必须持锁。它返回前会重新拿到锁。
  • 判定条件用 while 而不是 if，因为唤醒会虚假发生，别的线程也会被别的条件唤醒。
  • 广播或信号之前持锁，否则有丢唤醒的窗口。

销毁顺序：先让所有等待者退出 cond_wait，再 pthread_cond_destroy，最后 pthread_mutex_destroy。反序会把锁的引用断在半路。细节在《信号量与条件变量：等待与唤醒》。

与读写锁 #

pthread_rwlock 保护的是「读可并行」的结构。它不能升级：持读锁时不能转成写锁，pthread_rwlock_rdlock 之后调 pthread_rwlock_wrlock 会死锁。要写，先放读锁再申请写锁，然后重新校验数据没被别人改过。

读写锁在写者频繁时会退化得比互斥锁还慢。判断标准是读写比：低于 10:1 的读写比，直接用互斥锁。

与信号量 #

信号量管数量，锁管排他。要「最多 4 个线程同时进」，用初值为 4 的信号量，不是用 4 把锁。锁没法表达「N 个」。

反过来说，sem_init(&s, 0, 1) 确实等价于一把锁，但它没有属性、没有优先级协议、没有健壮性，不能跨进程传递优先级信息。只用互斥语义就用 pthread_mutex。

一把锁护住多个字段时，注意复合操作 #

c
/* 每个字段单独看都受保护，合起来不是原子操作 */
int get_pair(shared_t *s, int *a, int *b)
{
    pthread_mutex_lock(&s->lock);
    *a = s->x;
    pthread_mutex_unlock(&s->lock);    /* 这里放开，x 和 y 就被别人改了 */

    pthread_mutex_lock(&s->lock);
    *b = s->y;
    pthread_mutex_unlock(&s->lock);
    return 0;
}

两次加锁之间 x 和 y 都会被改，调用方拿到的两个值不属于同一时刻。要在同一次持锁里读完。

锁不能跨线程传递语义 #

pthread_mutex_t 的内存可以被人 memcpy 走，但语义不会跟着走。复制一把已被持有的锁，副本是一份无效状态。跨进程共享只能靠共享内存加同一块地址，不是靠把字节发过去。

十四、易错点速查 #

高频错误表 #

错误写法 后果 正确做法
if (pthread_mutex_lock(&m) == -1) 判断永远不成立，错误被吞 判 != 0，返回值是错误号不是 -1
临界区内 return 不解锁 其他线程永久阻塞 goto out 单出口，或拆成加锁壳

ERRORCHECK 只在 debug 构建开 #

c
#ifdef DEBUG_LOCKS
#  define LOCK_TYPE PTHREAD_MUTEX_ERRORCHECK
#else
#  define LOCK_TYPE PTHREAD_MUTEX_NORMAL
#endif

static pthread_mutex_t g_lock;

static void g_lock_init(void)
{
    pthread_mutexattr_t a;
    pthread_mutexattr_init(&a);
    pthread_mutexattr_settype(&a, LOCK_TYPE);
    pthread_mutex_init(&g_lock, &a);
    pthread_mutexattr_destroy(&a);
}

自锁在开发机上变成 EDEADLK 返回值，在线上是无开销的 NORMAL 路径。前提是代码里真的检查了 lock 的返回值——很多人不查，那就白开。

上线前逐条过一遍 #

  1. 每一处 lock 和 unlock 在同一函数内配对，或者有成对的清理函数。
  2. 所有 return 路径都过了解锁点。
  3. 临界区内没有 printf、malloc、write、回调、sleep。
  4. 涉及两把锁的地方，加了全局顺序或 trylock 退让。
  5. destroy 之前确认无人持锁、无人等待。
  6. 跨进程的锁在共享内存里，且只有一个进程 init。
  7. 实时线程如果共享了锁，协议设成了 PTHREAD_PRIO_INHERIT 或 PRIO_PROTECT。
  8. 长期跑的服务，共享内存里的锁开了 PTHREAD_MUTEX_ROBUST，并且真的实现了 EOWNERDEAD 的修复分支。
  9. perf lock report 跑过，知道哪把锁最热。
  10. 锁的返回值检查过一遍，或者已经明确决定不检查。
