GitHub 热点榜 · 三窗口版（24 小时 / 7 日 / 30 日） #

本文已按 2026-11-12 的最终设计重写。

原标题是「三窗口精简版（日 / 7日 / 30日）」，那是一次性手工抓取的快照记录。 后来一度把日榜砍掉只剩 7 日 / 30 日，2026-11-12 又因为 ETF 改为日频同步、 整条链路每天本来就跑一次，把 24 小时榜顺着这趟车加了回来。 现在这份文档描述的是当前实际运行的机制，不是复述某一天的数据。

抓取脚本：3.app/fetch/fetch-radar.mjs 定时配置：.github/workflows/workflow.yml 数据快照：2026-11-12 11:26:14（见第五节）

一、当前设计（和本文旧版的关键区别） #

旧版（一次手工抓取） 现在
数据来源 人工抓完粘贴进 HTML，10 个源 脚本抓取，9 条源记录（4 个域名）
时间窗口 日 / 7 日 / 30 日 24 小时 / 7 日 / 30 日

1.1 日榜为什么砍掉过、又为什么加回来 #

2026-11-11 砍掉的理由：日榜的增量噪声极大。官方 trending 按滚动 24 小时算增量， 第三方站按 UTC 自然日切，同一批 star 落进不同的「天」，数值就能差 3~7 倍。 当时只有 Trendshift 一个日榜源，没有第二个源来交叉验证，噪声无法被识别，只能砍掉。

2026-11-12 加回来的理由：ETF 数据改成了日频同步，workflow 的 cron 从每周一次 改成每天一次，抓取这趟车每天都发。既然车每天都开，radar 搭车抓一份日榜几乎零成本。 更重要的是，这次能凑齐两个独立日榜源（GitHub 官方 since=daily + Trendshift daily）， 口径差异不再是盲区，而是可以在页面上显式标出来的信息 —— 这正是 1.1 当初缺的东西。

处理方式是：日榜的跨源分歧单独归入「口径差」，与 7 / 30 天的「真分歧」分开呈现。 实测这次 5 条分歧全部是 24 小时口径差（spread 最高的 meta/astryx 达 9.28×），真分歧 0 条。

1.2 每天一次，但不写回仓库 #

每天 UTC 00:17（北京 08:17）
   ↓
GitHub Actions 触发 workflow.yml
   ↓
checkout 仓库 → npm ci
   ↓
node fetch/fetch-etf.mjs      ← 抓 ETF 数据
node fetch/fetch-radar.mjs    ← 抓三窗口趋势，覆写 runner 工作区里的 radar.html
   ↓
npm run build                 ← 把 3.app/*.html 搬进 dist/apps/
   ↓
peaceiris 推送到 LemonCyan.github.io → Pages

关键点：数据不落源仓库。 抓取只改 runner 的临时工作区，脚本本身不含任何 git 命令， workflow 也不 commit。数据直接随构建产物发到 Pages。所以 git log 里不会有机器人 commit 刷屏。

这是刻意选的方案。最初写过一个 radar-refresh.yml，抓完 git commit + git push 回 main—— 每周一次看起来不多，但会永久污染提交历史，而且 GITHUB_TOKEN 推送产生的 push 事件 不会触发其它 workflow（GitHub 防递归机制），还得额外 gh workflow run 绕一圈。 改成构建时抓取后，这些问题全部消失。

1.3 两道保险：抓挂了也不能让站点崩 #

保险 位置 作用
continue-on-error: true workflow.yml 的两个抓取步骤 抓取失败不阻断站点发布，用仓库里上一次的数据继续构建
质量闸门 fetch/fetch-radar.mjs 写文件前 抓取不全时拒绝写入，宁可保留旧数据

质量闸门条件：至少 3 个源成功，且每个窗口至少 5 条仓库。不满足就打印 抓取质量不达标，拒绝写入（成功源 X/Y，窗口 24h:A 7d:B 30d:C）。 并退出，一个字节都不写。

这个闸门救过一次真实事故：早期版本只检查第一个窗口，结果某次 github.com 被网络阻断， 后面的窗口塌成 0 但第一个窗口有数据，坏数据被放行了。教训是「页面看起来有数据、 切到另一个 tab 才是空的」是最难察觉的坏数据，比整页空白更危险。 现在改成逐窗口检查。

1.4 新鲜度提示 #

页面右上角徽标不再无条件显示「LIVE 抓取」，改为按 DATA.stamp 算真实年龄 （不足 1 小时显示分钟、不足 48 小时显示小时、再往上显示天）：

数据年龄 徽标 含义
≤ 36 小时 🟢 数据 X 小时前 正常（留半天余量，cron 排队或偶发失败不该立刻告警）
36 ~ 72 小时 🟡 数据 X 小时前 · 待更新 漏了一轮
> 72 小时 ⚪ 数据 X 天前 · 已过期 停掉呼吸灯动画，说明已经三天没更新
时间戳缺失/无法解析 ⚪ 数据时间未知 不假装有数据

阈值按天设计（36h / 72h），因为刷新节奏已经改成每天一次。

2.1 三个窗口各自的独立源数 #

  • 24 小时：gh + ts 两个独立源。但两站口径差距很大（见 3.1）， 所以日榜的「命中 ≥2」主要用来排序可信度，跨源分歧一律归入「口径差」而不是「真分歧」。 本次 27 条里命中 2 源的有 8 条。
  • 7 天：gh + fa 两个真正独立的源，口径接近，spread（最高/最低比值）通常在 1.00~1.02，是很干净的交叉验证。本次 34 条里命中 2 源的有 4 条。
  • 30 天：只有官方 gh 一家。findarepo 的 range 参数被服务端忽略， 传 ?range=30d、?range=30、不传参数，返回的都是同一份 7 天榜。 Trendshift 的 /monthly 存在，但它的 gained 口径与官方差到 9 倍，与官方并列会让 30 天栏的排序失真，所以 30 天刻意只留官方一家。

结果就是：30 天窗口那一栏的「命中」恒为 1，没有信息量。 页面上的统计栏会如实显示「参与源 gh」「最多命中 1 源」，不会假装有多源共识。

旧版引用过 repositorystats（W4 / M3）作为第二源，但它现在被 Cloudflare 拦截， 完整 Chrome 头、Googlebot UA、curl、r.jina.ai 等 9 种方式全部 403，进不去。不再引用。

2.2 已删除与已剔除 #

open-repo.com（原 or）已不可用。 它的所有 API 端点现在返回 404。此前它的 surge 三榜 与官方 trending 逐行、逐值、逐顺序完全一致，是镜像不是独立源——计入命中数会让共识度凭空翻倍， 所以即使它活着也应该合并掉。

Trendshift 抓取换了入口。 它的首页只是壳，真正的数据在 RSC 流的 "initialData":[...] 里 （ld+json 的 ItemList 只有名字/语言/描述，没有 star 增量）。详见 6.2。

其它已剔除的源见第七节。

差距的成因是两个站算法根本不同：官方是滚动 24 小时窗口，任何时刻刷新都覆盖「当前时刻往回 24h」； Trendshift 是 UTC 自然日切并且对 star 增量做了热度加权（score 字段）， 不是原始增量。所以同一批 star 落进不同的「天」、再被加权一次，数值就能差几倍到十几倍。

这不是数据造假，只是口径不同。 所以页面把它放在单独的「口径差」区块里， 用暖色标注、最多显示 6 条，不与 7 / 30 天的真分歧混排。

四、GitHub Search API 的 10 次/小时额度 #

这个限制只影响 api.github.com/search/repositories（新仓库榜那 30 条）， 跟三个时间窗口的主榜毫无关系——主榜抓的是 github.com/trending 网页和 Trendshift/findarepo， 都不吃 API 额度。

场景 用量 结论
现在（每天一次） 每天 1 次 毫无压力，差 240 倍
带 GITHUB_TOKEN（线上实际） 30 次/分钟（约 1800 次/小时） 等于没有限制
匿名 IP 10 次/小时 只够偶尔跑一次，本地调试容易撞墙

workflow.yml 已经把 secrets.GITHUB_TOKEN 传进 fetch/fetch-radar.mjs 了， 所以线上跑的是认证额度，这个限制实际不生效。本地调试时如果反复跑，会看到 newcomers 板块空掉 —— 那是额度用完了，等一小时自动恢复。

额度耗尽时的影响是局部的：newcomers 板块空掉，页面显示 「GitHub Search API 不可用（限流或无网络）」，其余板块正常。它走独立 try/catch，不参与质量闸门。

真正被这个额度卡死的是「浏览器直取」那个方案——如果想让页面 JS 自己刷数据， 唯一的跨域可行接口就是 Search API，而它对匿名 IP 只有 10 次/小时。所以走构建时抓取之后， 这个限制就不再是问题了。详见 4.1。

4.1 为什么不能用页面 JS 刷新 #

实测结论：不可行。

接口 CORS 状态
github.com/trending 没有 Access-Control-Allow-Origin 浏览器 fetch 必被拦死
trendshift.io / findarepo.com 无 CORS 头 同上
api.github.com/search/repositories * ✅ 匿名 10 次/小时，不够定时刷
第三方 trending 代理（herokuapp / vercel / a9sapp 等） — 全部已停止服务

13 个候选源实测，第三方代理无一存活：gh-trending-api.herokuapp.com 连接超时、 github-trending-api.a9sapp.eu DNS 不存在、gh-trending.vercel.app 超时、 api.gitterapp.com / api.trending-github.com DNS 不存在、 api.ossinsight.io 返回 data_quality: unavailable（官方已停榜）、 cdn.jsdelivr.net/gh/robertov8/trending-github 连接被重置。

所以只能在服务端抓。这条不再讨论了。

六、实现细节（值得记住的部分） #

6.1 写回只替换一行 #

radar.html 里所有数据内联在一行 const DATA = ... 里，那一行占了全文件的 50% 以上， 其余几百行是页面骨架和样式。脚本「更新页面」的动作就是：

js
const json = JSON.stringify(DATA).replace(/<\//g, '<\\/');
lines[idx] = `const DATA = ${json};`;
fs.writeFileSync(TARGET, lines.join('\n'), 'utf8');

用副本做过逐行 sha256 对比：写回前后行数不变，DATA 行以外的每一行都变化了 0 行。 </ 转义是必须的，否则 JSON 里出现 </script> 会把 HTML 的 script 块提前截断。

6.2 踩过的坑 #

现象 原因 处理
star 总数取成了奇怪坐标 数字夹在 <svg> 之后，正则直接取 [\d,]+ 会抓到 svg path 里的坐标 用 /\/stargazers"[^>]*>[\s\S]*?<\/svg>\s*([\d,]+)/ 跳过 svg
Trendshift 拿不到增量 ld+json 的 ItemList 只有名字/语言/描述，没有 star 增量 改从 RSC 流的 "initialData":[...] 取，还需先还原 \\" 双重转义
Trendshift 的 JSON 截不完整 页面嵌在 RSC 流里，JSON 后面还跟着别的 payload，正则匹配到多行会截断 从 [ 起做括号配平，跳过字符串内的转义，配平到 0 才 JSON.parse
24h 口径差把真分歧挤掉 buildConflicts 排序后统一 slice(0, 20)，口径差 spread 常 10 倍以上 分两组各自截断：真分歧 20 条 + 口径差 8 条
日榜「≈/天」与「窗口增量」重复 days = 1 时两者相等 表头与行体都按 w.days > 1 条件渲染该列
页面语言徽标日期偏小 8 小时 stamp 是北京时间但不带时区标记，海外访客按本地时区解析 解析时补 +08:00，四时区实测徽标一致
统计栏出现「窗口 7 天 · 7 天」 w.label 本身就是「7 天」，后面又拼了 ${w.days} 天 去掉重复拼接
findarepo 静默丢行 同表里多数链接是 /repo/owner/name/，少数是 https://github.com/owner/name 两种写法都匹配；此前丢了 pingdotgg/t3code(+11,906) 和 janestreet/agent_skills
PowerShell 读写破坏 UTF-8 Get-Content | Set-Content -Raw 往返会把中文变乱码 改脚本一律用 Node 读写

6.3 每天刷新带来的取舍 #

  • 好处：源仓库零 commit；数据永远和构建产物同步；日榜有了双源交叉验证；不依赖任何额外的 workflow。
  • 代价：数据不落仓库，所以 git log 里查不到历史榜单。想回看历史得自己留快照。 本文第五节就是一份手动留的快照。
  • 注意：cron 只是「尽力而为」。GitHub 的 schedule 在高负载时会延迟，甚至跳过。 所以页面有新鲜度提示——数据超过 36 小时变黄、超过 72 小时变灰，不会假装实时。

八、使用注意 #

  1. 口径不可比。 官方 today / this week / this month 是滚动窗口，findarepo 是它自己的 7 天窗口， Trendshift 是 UTC 自然日切并做过热度加权。24 小时栏的跨源差距普遍在 2~10 倍，那是正常的； 7 天栏差 1~2% 属正常，差 1.5 倍以上才算真分歧。
  2. 30 日榜没有第二源。 那一栏的「命中」恒为 1，别当共识度看。
  3. tracking started 不是 0。 findarepo 刚跟踪的仓库没有历史基线，增量留空， 不是「涨了 0 个」。
  4. 中文榜量级差一到两个数量级。 一天涨几十 star 在中文榜算猛，在主榜垫底。
  5. 日榜看脉冲，周榜看趋势。 24 小时榜换榜极快，同一天两次抓取可能完全不同； 判断一个项目是否真的在起势，看 7 天榜更可靠。
  6. 数据是每日快照，不是实时。 看徽标判断新旧，超过 36 小时就该警惕。
  7. spread 只在两个源都有正值增量时才计算，只有一个源或一侧为空时不显示。

数据均由 fetch/fetch-radar.mjs 抓取原样记录， 未做清洗、补值或加权。唯一的加工是剔除镜像/重复源并按仓库聚合命中数。
