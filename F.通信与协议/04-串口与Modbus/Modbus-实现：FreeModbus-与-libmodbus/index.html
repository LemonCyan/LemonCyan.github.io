本篇讲 Modbus 的两个成熟开源实现：嵌入式侧的 FreeModbus，Linux 侧的 libmodbus。

讲什么：两个库各自解决什么问题、FreeModbus 的四层结构、移植要动哪五个文件、3.5 字符定时怎么落地、回调与异常码怎么对应、libmodbus 的 API 与完整例子、RTU 与 TCP 两种接法、交叉编译参数、选型与易错点。

不讲什么：RS232 的电平与接线在《串口通信基础》；串口怎么切帧、CRC 怎么算在《串口收包》；功能码 0x01 到 0x10 的报文格式与寄存器模型在《Modbus 协议》。本篇默认你已经知道 0x03 是读保持寄存器，只讲怎么用库把它发出去、怎么用库接住它。

定位：同目录四篇之一，平铺平级。从站项目、MCU 上跑，重点看三到六章；Linux 主站、要读电表读变频器，重点看七到十章。

一、为什么要用现成的库 #

一帧报文里藏着的活 #

拿读保持寄存器举例。主机发 8 个字节，从站回 7 加 2N 个字节。看上去不多，但要把这一问一答在代码里跑通，你至少得处理下面这些事。

环节 要做的事 出错会怎样
组帧 站号、功能码、起始地址、数量，按大端塞进缓冲 字节序反了，从站读到 0x0100 而不是 0x0001
校验 CRC16 查表或位运算，低字节在前 少算一位，从站整帧丢弃，你等超时
切帧 RTU 靠 3.5 字符静默判帧结束 定时器快了切半帧，慢了把两帧粘一起
地址过滤 站号不匹配就静默丢掉 回错，总线上两台设备同时开口
异常应答 功能码最高位置 1，跟一个异常码 主机收到没头没尾的字节，报帧错
超时重发 响应超时、CRC 错都要能重来 一次线路抖动，整条产线停
半双工方向 RS-485 收发切换，发完立刻转收 切换晚一个字节，把自己发的尾巴收回来
广播 站号 0 不回复 广播也回，总线冲突

这八件事，每一件单独写都不难。难的是它们互相咬合，而且都在中断和主循环的边界上。定时器里判帧结束，串口中断里收字节，主循环里跑业务，三个上下文共享一个缓冲。

手写一遍的价值 #

手写一遍值得。你会真正看懂为什么第一个字节到来时要重启定时器，为什么初始化后要先空等一个 T35，为什么 CRC 校验通过的条件是算出来等于 0 而不是等于某个常数。

但手写一遍之后，第二个项目不该再手写。协议是死的，业务是活的。你要花时间的地方是「这个寄存器地址对应哪路传感器」，不是「CRC 表的第 47 项是什么」。

库封掉了什么，留下了什么 #

这是本篇最该先记住的一句话：这两个库都把协议细节封掉了，你只需要实现业务回调。

具体拆开看：

层 谁负责 你要写的东西
电气与时序 硬件 + 串口驱动 无，配好波特率就行
帧格式与校验 库 无
切帧与超时 库（FreeModbus 靠 porttimer，libmodbus 靠帧长） 无
功能码分发 库 无
寄存器数据从哪来 你 FreeModbus 写 4 个回调，libmodbus 填数组
收到数据后干什么 你 换算、存库、上报、联动

FreeModbus 的分界线在回调：它问你「从地址 0x0000 开始读 4 个保持寄存器」，你回一个 MB_ENOERR 并把值填进去，剩下的组帧、CRC、发送、等超时全归它。

libmodbus 的分界线在函数调用：你调 modbus_read_registers(ctx, 0, 4, tab_reg)，它负责把请求拼出来发出去、把应答收回来、校验通过后把 4 个值填进 tab_reg，返回 4。

两边的分界线位置不同，但形状一样：你只回答业务问题，协议问题不落到你头上。

什么时候不用库 #

有几种情况确实不用：

  • 目标 MCU 的 Flash 只有 8K，FreeModbus 塞不进去，那就自己写个只支持 0x03 和 0x06 的极简从站
  • 只做一次性抓包分析，用现成工具比写代码快
  • 对方的「Modbus」是改过的私有变种，库的严格校验反而挡住你

反过来，只要你要维护、要交付、要别人接手，用库。库的代码被人读过一千遍，你的代码只有你读过。

二、FreeModbus 与 libmodbus 的定位 #

一句话各自站在哪边 #

FreeModbus 站在从站这边，跑在 MCU 上，C 语言，裸机或 RTOS 都行。它的设计目标很明确：把一个 Modbus 从站塞进资源紧张的芯片里，同时让你换芯片时只改五个文件。

libmodbus 站在主站这边，跑在 Linux 上，依赖 POSIX。它把「打开串口 / 建 socket / 发请求 / 收应答」这套流程压成了几个函数，主站写起来像调本地 API。

两边都支持主从双向。FreeModbus 从 V1.6 起支持主机与从机在同一协议栈里并行运行，host 侧只支持 RTU。libmodbus 也提供了完整的 server 侧（modbus_receive / modbus_reply），能当从站用。但社区里跑出来的用法，FreeModbus 九成是从站，libmodbus 九成是主站。本篇的篇幅也按这个事实分配。

选型的第一问：你站在哪边 #

这不是技术问题，是角色问题。先问自己：我的设备是被人读，还是去读别人。

被读的就是从站。传感器、电表、变频器、IO 模块、PLC 扩展卡，这些都是从站。你对外暴露一批寄存器和线圈，等着别人来问。

去读别人的就是主站。网关、上位机、SCADA、数据采集盒、工控机上的采集程序，这些是主站。你按周期去问一圈从站，把答案存下来。

主站侧用 libmodbus 更省事，因为它把「连不上怎么办、超时怎么设、多个从站怎么轮询」这些主站才有的麻烦都想到了。

从站侧用 FreeModbus 更省事，因为它的整个架构就是围绕「等一个请求、回一个应答」设计的，主循环加中断，没有线程。

选型的第二问：跑在什么平台 #

平台决定了一半的答案。

平台 从站 主站
裸机 MCU（STM32、GD32、MSP430） FreeModbus FreeModbus host 侧（仅 RTU）或自写
MCU + RTOS（RT-Thread、FreeRTOS） FreeModbus FreeModbus host 侧，用 RTOS 事件做同步
Linux 单板（ARM9、Cortex-A、RV1126） libmodbus server libmodbus client
Windows 上位机 libmodbus 改 win32 端口，或自写 同左
带 Python 的网关 pymodbus pymodbus

交叉组合也成立，但都别扭。在 Linux 上跑 FreeModbus，你得用文件描述符模拟串口寄存器和定时器中断，纯属找麻烦。在裸机上跑 libmodbus，POSIX 那套 termios 和 select 根本没有。

两个都想要的时候 #

网关是典型的两个都要：南向当主站去问一堆 RTU 从站，北向当从站被上位机问。

这种结构不要试图用一个库塞满。常见做法是南向跑 libmodbus client 收数据，北向用 libmodbus server 或另外起一个 FreeModbus（在 MCU 方案里）。两边共享一块寄存器映射表，收上来的数据写进表里，北向请求从表里读。数据流是单向的，不会互相踩。

三、FreeModbus 的协议栈分层 #

四层结构 #

FreeModbus 的源码目录结构本身就是它的分层图。从上往下：

text
应用层      user_mb_app.c        你的回调和寄存器缓冲
   ↑
功能层      functions/mb*.c      功能码 0x01~0x10 的处理
   ↑
传输层      rtu/ ascii/ tcp/     组帧、CRC、切帧、地址过滤
   ↑
物理层      port/portserial.c    串口收发字节
            port/porttimer.c     定时器中断
            port/portevent.c     事件队列

每一层只跟相邻层说话，接口是函数指针。这个写法在 eMBInit 里体现得最清楚。

物理层：只管字节进出 #

物理层不知道什么是 Modbus。它只知道两件事：从串口读一个字节，往串口写一个字节。加上定时器，它提供「过一个 T35 时间叫我一声」。

这三件事对应三个 port 文件，后面第四章细讲。

传输层：函数指针的魔法 #

eMBInit 是理解 FreeModbus 架构的钥匙。它按模式给一组全局函数指针赋值：

c
#if MB_RTU_ENABLED > 0
case MB_RTU:
    pvMBFrameStartCur = eMBRTUStart;
    pvMBFrameStopCur = eMBRTUStop;
    peMBFrameSendCur = eMBRTUSend;
    peMBFrameReceiveCur = eMBRTUReceive;
    pvMBFrameCloseCur = MB_PORT_HAS_CLOSE ? vMBPortClose : NULL;
    pxMBFrameCBByteReceived = xMBRTUReceiveFSM;
    pxMBFrameCBTransmitterEmpty = xMBRTUTransmitFSM;
    pxMBPortCBTimerExpired = xMBRTUTimerT35Expired;
    eStatus = eMBRTUInit(ucMBAddress, ucPort, ulBaudRate, eParity);
    break;
#endif

ASCII 分支和 TCP 分支写着同样形状的代码，只是右边换成 eMBASCIIStart、eMBTCPReceive 之类。上层 eMBPoll 完全不关心底下是哪种，它只调 peMBFrameReceiveCur。

这个模式值得抄。换传输方式不动一行上层代码，代价只是一组函数指针。C 语言里做多态，够用了。

功能层：功能码到处理函数 #

功能码进来后，eMBPoll 在 xFuncHandlers 数组里线性查找：

c
case EV_EXECUTE:
    ucFunctionCode = ucMBFrame[MB_PDU_FUNC_OFF];
    eException = MB_EX_ILLEGAL_FUNCTION;
    for (i = 0; i < MB_FUNC_HANDLERS_MAX; i++) {
        if (xFuncHandlers[i].ucFunctionCode == 0) {
            break;
        } else if (xFuncHandlers[i].ucFunctionCode == ucFunctionCode) {
            eException = xFuncHandlers[i].pxHandler(ucMBFrame, &usLength);
            break;
        }
    }

数组用 0 当结束标记，所以 0 号功能码不能注册。找不到处理函数就返回 MB_EX_ILLEGAL_FUNCTION，这就是异常码 0x01 的来源。

功能层里每个 mbfunc*.c 干的事都很薄：校验参数长度、调应用层的回调、把返回值按 PDU 格式填回去。真正的数据在你的回调里。

应用层：就是你的回调 #

user_mb_app.c 不属于协议栈，它属于你的项目。里面定义数据缓冲区，实现四个回调：读输入寄存器、读保持寄存器、读线圈、读离散输入。

FreeModbus 把这些回调声明成弱符号或空实现，你不实现就链接不过或运行时返回异常。这种设计把「协议」和「业务」的边界划在了编译期。

配置集中在两个头文件 #

mbconfig.h 管协议栈开关：使能哪种传输模式、功能码处理函数最多几个、PDU 最大长度、是否支持广播。这些是编译期宏，改了要重编整个栈。

mbport.h 管平台相关的宏：临界区怎么进怎么出、断言怎么写、中断服务程序怎么命名。移植时这个文件比 mbconfig.h 更需要动。

MB_SER_PDU_SIZE_MAX 决定接收缓冲多大。RTU 上限 256，但很多从站只用一个功能码，把它调小到 64 能省下近 200 字节 RAM。缓冲区是静态数组，改宏才生效，运行期改不了。

四、FreeModbus 的移植五件事 #

为什么是这五件 #

这是本篇最该讲透的一点。FreeModbus 把代码切成两半：跟 Modbus 协议有关的，和跟平台有关的。前者一行都不用改，后者全被赶到 port 目录。

跟平台有关的无非这么几类：

  • 字节怎么进怎么出 → 串口
  • 时间怎么走 → 定时器
  • 中断和主循环怎么通信 → 事件
  • 网络包怎么收发（走 TCP 才需要）→ socket
  • 你的数据放在哪、叫什么名 → 应用回调

五类对应五个文件。换一颗芯片，串口寄存器换了、定时器换了、事件机制要重写，但这五件事本身不变。所以只改这五个文件，协议栈本身不动。这就是它能跨 STM32、MSP430、AVR、GD32 的原因。

文件 管什么 关键函数 不实现会怎样
portserial.c 串口收发、RS-485 方向切换 vMBPortSerialEnable、xMBPortSerialPutByte、xMBPortSerialGetByte 一个字节都收不到，或发不出去
porttimer.c T35 定时与超时中断 xMBPortTimersInit、vMBPortTimersEnable、vMBPortTimersDisable 收满一帧也不知道帧结束，永远不响应
portevent.c 中断向主循环投递事件 xMBPortEventInit、xMBPortEventPost、xMBPortEventGet 状态机拿不到事件，eMBPoll 空转
porttcp.c TCP 模式下的 socket 收发 xMBTCPPortInit、xMBTCPPortGetRequest、xMBTCPPortSendResponse 只有走 Modbus TCP 才需要，走串口不用编
user_mb_app.c 寄存器缓冲与四个回调 eMBRegHoldingCB 等 链接失败，或所有读请求都回异常 0x02

portserial.c：串口收发 #

要实现的接口：

接口方法 功能描述
vMBPortSerialEnable 使能或失能串口的发送及接收功能。用 RS-485 总线时，要在这里切收发方向
vMBPortClose 关闭串口，释放资源
xMBPortSerialInit 串口初始化，设波特率、数据位、校验方式；RS-485 的 DE 引脚也在这里初始化
xMBPortSerialPutByte 发送单字节
xMBPortSerialGetByte 接收单字节
prvvUARTTxReadyISR 发送完成中断服务程序，默认引到 pxMBFrameCBTransmitterEmpty
prvvUARTRxISR 接收中断服务程序，默认引到 pxMBFrameCBByteReceived

还有一步经常被忘：文件末尾要把 prvvUARTTxReadyISR 和 prvvUARTRxISR 挂到你芯片的串口中断向量里。FreeModbus 不替你写 USART1_IRQHandler，那属于启动文件的世界。

RS-485 的方向切换是这块最容易出错的地方。典型写法：

c
void vMBPortSerialEnable(BOOL xRxEnable, BOOL xTxEnable)
{
    if (xRxEnable) {
        RS485_DE_LOW();               /* 先确保不发 */
        USART_ITConfig(USART1, USART_IT_RXNE, ENABLE);
    } else {
        USART_ITConfig(USART1, USART_IT_RXNE, DISABLE);
    }

    if (xTxEnable) {
        RS485_DE_HIGH();              /* 转发送 */
        USART_ITConfig(USART1, USART_IT_TXE, ENABLE);
    } else {
        USART_ITConfig(USART1, USART_IT_TXE, DISABLE);
    }
}

方向切换必须在「最后一个字节真正移出移位寄存器」之后才能转回接收。用 TXE 中断判断是不够的，TXE 只表示数据寄存器空，移位寄存器里还有一个字节正在发。要等 TC（发送完成）标志。这一步早一个位，你自己发的 CRC 后半截会被自己收回来。

porttimer.c：3.5 字符定时 #

这是 FreeModbus 最精妙的一块，也是移植时最容易配错的一块。

Modbus RTU 没有长度字段，也没有起始符。它靠时间切帧：总线上安静超过 3.5 个字符时间，就认为一帧结束。所以从站的核心机制是：每收到一个字节就重启定时器，定时器到期就认为帧结束。

定时器时基固定为 50 微秒。xMBPortTimersInit(USHORT usTim1Timerout50us) 的参数是以 50 微秒为单位的计数值。为什么是 50 微秒？因为 3.5 字符在 9600 波特率下是 3.65 毫秒，在 115200 下是 0.3 毫秒。50 微秒的粒度对高波特率勉强够用。

eMBRTUInit 里这样算这个值：

c
if (ulBaudRate > 19200) {
    usTimerT35_50us = 35;             /* 固定 1750us，规范推荐 1.75ms */
} else {
    /* 3.5 个字符，一个字符 11 位 */
    usTimerT35_50us = (7UL * ulBaudRate) / 120000 * 100 + 1;
}

波特率超过 19200 时用固定值，不再按字符数算。原因是高波特率下 3.5 字符只有几百微秒，跟中断延迟、线路延迟混在一个量级，按字符算反而误判。规范自己也是这么建议的。

现成驱动里的实现骨架：

接口方法 功能描述
xMBPortTimersInit 初始化定时器，把预分频数和 T35 计数值备份到 usPrescalerValue 和 usT35TimeOut50us
vMBPortTimersEnable 按 T35 时间启动计数，同时清计数器
vMBPortTimersDisable 停表，终止计数
prvvTIMERExpiredISR 定时器中断服务程序，默认引到 pxMBPortCBTimerExpired

usPrescalerValue 和 usT35TimeOut50us 在文件顶部定义，是全局变量。移植时这两个值要跟你的晶振频率对上，算错了整条链路的时间基准就歪了。

调用链是这样走的：定时器中断 → prvvTIMERExpiredISR → pxMBPortCBTimerExpired 指针 → xMBRTUTimerT35Expired。最后这个函数按当前接收状态决定投什么事件：

c
switch (eRcvState) {
    case STATE_RX_INIT:
        xNeedPoll = xMBPortEventPost(EV_READY);
        break;
    case STATE_RX_RCV:
        xNeedPoll = xMBPortEventPost(EV_FRAME_RECEIVED);
        break;
    case STATE_RX_ERROR:
        break;
    default:
        assert((eRcvState == STATE_RX_INIT) || (eRcvState == STATE_RX_RCV) || (eRcvState == STATE_RX_ERROR));
}

STATE_RX_INIT 时投 EV_READY，这是初始化后那次空等的收尾。STATE_RX_RCV 时投 EV_FRAME_RECEIVED，说明一帧收全了。STATE_RX_ERROR 什么都不投，那一帧直接丢。

定时器的精度直接决定帧边界的准确性。 定时器偏快，长帧会被腰斩；偏慢，两帧会被粘成一帧，CRC 对不上整帧丢弃。用内部 RC 振荡器做时钟源的板子，温漂能让这个值跑偏几个百分点，波特率一高就现原形。

portevent.c：事件机制 #

协议栈跑在主循环里，字节收在中断里。两者之间需要一个队列。FreeModbus 用的是最朴素的实现：一个全局变量存事件。

c
static eMBEventType eQueuedEvent;
static BOOL         xEventInQueue;

BOOL xMBPortEventInit(void)
{
    xEventInQueue = FALSE;
    return TRUE;
}

BOOL xMBPortEventPost(eMBEventType eEvent)
{
    xEventInQueue = TRUE;
    eQueuedEvent  = eEvent;
    return TRUE;
}

BOOL xMBPortEventGet(eMBEventType *eEvent)
{
    BOOL xEventHappened = FALSE;
    if (xEventInQueue) {
        *eEvent = eQueuedEvent;
        xEventInQueue = FALSE;
        xEventHappened = TRUE;
    }
    return xEventHappened;
}

只有一个槽位。这在从站场景够用，因为同一时刻只会有一个事件待处理：收字节的中断不会投事件，只有定时器中断投。但如果你的应用在别处也往这个队列投东西，就得加锁或者改成真队列。

裸机上把 xMBPortEventPost 做成置标志，xMBPortEventGet 在 eMBPoll 里轮询。RTOS 上换成邮箱或事件组，xMBPortEventGet 带阻塞超时，这样主循环能在没事件时睡下去，省电。

porttcp.c：只在走 TCP 时需要 #

走 Modbus TCP 时，物理层从串口变成 socket，但分层不变。要实现的接口是三个：初始化监听、取一个请求、发一个应答。协议栈里 mbtcp.c 负责 MBAP 头和 PDU 的拼接，porttcp.c 只负责把字节从 socket 搬进搬出。

走串口的项目不用编这个文件，工程里删掉即可。mbconfig.h 里 MB_TCP_ENABLED 设 0，相关的条件编译自然把代码裁掉。

user_mb_app.c：回调与缓冲 #

这个文件一半是数据，一半是函数。

数据部分定义四个缓冲区，对应四种数据类型：

c
#define REG_HOLDING_START  0x0000
#define REG_HOLDING_NREGS  8
USHORT usRegHoldingBuf[REG_HOLDING_NREGS];

#define REG_INPUT_START    0x0000
#define REG_INPUT_NREGS    8
USHORT usRegInputBuf[REG_INPUT_NREGS];

#define COIL_START         0x0000
#define COIL_NCOILS        8
UCHAR  ucCoilBuf[(COIL_NCOILS + 7) / 8];

#define DISC_START         0x0000
#define DISC_NDISCRETES    8
UCHAR  ucDiscBuf[(DISC_NDISCRETES + 7) / 8];

线圈和离散输入用位打包，一个 UCHAR 存 8 路。(N + 7) / 8 这个写法要记住，少算一个字节就是越界。

函数部分是四个回调。它们的签名来自 mbconfig.h 的声明，参数是「起始地址、数量、数据指针」，返回值是 eMBErrorCode：

c
eMBErrorCode eMBRegHoldingCB(UCHAR *pucRegBuffer, USHORT usAddress,
                             USHORT usNRegs, eMBRegisterMode eMode)
{
    eMBErrorCode eStatus = MB_ENOERR;
    USHORT i;
    USHORT usRegIndex = usAddress - REG_HOLDING_START;

    if ((usAddress >= REG_HOLDING_START) &&
        (usAddress + usNRegs <= REG_HOLDING_START + REG_HOLDING_NREGS)) {
        if (eMode == MB_REG_READ) {
            for (i = 0; i < usNRegs; i++) {
                *pucRegBuffer++ = (UCHAR)(usRegHoldingBuf[usRegIndex + i] >> 8);
                *pucRegBuffer++ = (UCHAR)(usRegHoldingBuf[usRegIndex + i] & 0xFF);
            }
        } else {
            for (i = 0; i < usNRegs; i++) {
                usRegHoldingBuf[usRegIndex + i]  = (USHORT)*pucRegBuffer++ << 8;
                usRegHoldingBuf[usRegIndex + i] |= (USHORT)*pucRegBuffer++;
            }
        }
    } else {
        eStatus = MB_ENOREG;          /* 地址越界，协议栈会转成异常码 0x02 */
    }
    return eStatus;
}

三个细节：

  • 地址要减起始地址再当下标。不做减法，地址 0x0010 会直接越界。
  • 两个字节拼一个 USHORT 时高字节在前，这是 Modbus 的大端约定，跟你的 CPU 是什么字节序无关。
  • 越界要返回 MB_ENOREG 而不是硬撑。协议栈收到这个码会自动回 0x02 异常帧，主机就知道地址不存在。

线圈回调同理，只是数据按位操作，pucRegBuffer 里一个字节装 8 个线圈。

五、FreeModbus 的回调与异常 #

四个回调的签名与分工 #

回调 对应数据类型 触发功能码 数据在缓冲里的形态
eMBRegCoilsCB 线圈，可读可写 0x01 读、0x05 写单个、0x0F 写多个 位打包，一字节 8 点
eMBRegDiscreteCB 离散输入，只读 0x02 读 位打包，一字节 8 点
eMBRegHoldingCB 保持寄存器，可读可写 0x03 读、0x06 写单个、0x10 写多个 每寄存器 2 字节大端
eMBRegInputCB 输入寄存器，只读 0x04 读 每寄存器 2 字节大端

四个回调共用一个 eMode 参数区分读写，值是 MB_REG_READ 或 MB_REG_WRITE。只读的两个（离散输入、输入寄存器）永远只收到 MB_REG_READ，但签名里还是得留这个参数。

写操作时数据已经被协议栈解析好放进 pucRegBuffer，你只管取。做量程转换、单位换算都放在回调后面，别在回调里做耗时的事——回调在 eMBPoll 上下文里跑，你卡住，整个从站就卡住。

主机侧的回调与缓冲 #

主机模式的缓冲结构不一样。从机是一维数组，主机是二维数组：列号是寄存器/线圈/离散量地址，行号是从机节点 ID。

c
USHORT usMRegHoldBuf[MB_MASTER_TOTAL_SLAVE_NUM][M_REG_HOLDING_NREGS];

行号要减 1 才能对上站号。usMRegHoldBuf[2][1] 指的是站号 3、保持寄存器地址 1 的数据。站号从 1 开始，数组从 0 开始，这个偏移是主机侧最常见的越界来源。

配套的四个主机回调：

接口 功能描述
eMBMasterRegInputCB 输入寄存器回调
eMBMasterRegHoldingCB 保持寄存器回调
eMBMasterRegCoilsCB 线圈回调
eMBMasterRegDiscreteCB 离散输入回调

主机回调的调用时机是「收到应答并解析完成之后」，协议栈把数据交给你，你决定存哪。跟从站回调的区别是：从站回调被问「给我数据」，主机回调被告知「数据来了」。

异常码：从错误码到应答帧 #

Modbus 的异常应答格式很简洁：功能码最高位置 1，后面跟一个字节的异常码。所以 0x03 的异常应答是 0x83 加码。

FreeModbus 内部用 eMBException 枚举表示异常，值跟协议定义一致：

异常码 宏 含义 什么时候产生
0x01 MB_EX_ILLEGAL_FUNCTION 非法功能码 请求的功能码不在 xFuncHandlers 里
0x02 MB_EX_ILLEGAL_DATA_ADDRESS 非法数据地址 回调返回 MB_ENOREG
0x03 MB_EX_ILLEGAL_DATA_VALUE 非法数据值 数量为 0、超出上限、值不在范围
0x04 MB_EX_SLAVE_DEVICE_FAILURE 从站设备故障 回调返回 MB_EIO 或内部执行出错
0x06 MB_EX_SLAVE_BUSY 从站忙 从站在处理长任务，暂时不能应答

eMBErrorCode 和 eMBException 是两套码。前者是函数返回值，后者是往总线上发的字节。转换在 eMBPoll 里做：

eMBErrorCode 转成异常码
MB_ENOERR 无，正常应答
MB_ENOREG 0x02 非法数据地址
MB_EINVAL 0x03 非法数据值
MB_EIO、MB_EPORTERR、MB_ENORES 0x04 从站故障

搞混这两套码的症状很好认：你在回调里 return MB_EIO（值是个负数），协议栈把它当异常处理，主机收到的码跟你以为的不一样。回调只该返回 eMBErrorCode，异常码由协议栈推导。

组异常帧的那段代码 #

异常帧在 eMBPoll 里组，就三行：

c
if (ucRcvAddress != MB_ADDRESS_BROADCAST) {
    if (eException != MB_EX_NONE) {
        usLength = 0;
        ucMBFrame[usLength++] = (UCHAR)(ucFunctionCode | MB_FUNC_ERROR);
        ucMBFrame[usLength++] = eException;
    }
    if ((eMBCurrentMode == MB_ASCII) && MB_ASCII_TIMEOUT_WAIT_BEFORE_SEND_MS) {
        vMBPortTimersDelay(MB_ASCII_TIMEOUT_WAIT_BEFORE_SEND_MS);
    }
    eStatus = peMBFrameSendCur(ucMBAddress, ucMBFrame, usLength);
}

MB_FUNC_ERROR 是 0x80，或上去就是最高位置 1。整个 PDU 只剩 2 个字节。ASCII 模式额外加一段发送前延时，因为 ASCII 帧靠冒号和换行界定，两个帧之间要留出可辨识的空隙。

注意外层的 ucRcvAddress != MB_ADDRESS_BROADCAST 判断：广播请求永远不回复，异常也不回。 广播是站号 0，所有从站都执行，谁都不许开口。

主机侧的错误码 #

主机的请求接口返回的是 eMBMasterReqErrCode，一套独立的码：

返回值 含义
MB_MRE_NO_ERR 正常，没检测到错误
MB_MRE_NO_REG 寄存器、线圈或离散输入地址不正确
MB_MRE_ILL_ARG 输入参数格式不符合要求
MB_MRE_REV_DATA 接收到的数据有误
MB_MRE_TIMEDOUT 响应超时，设定时间内没收到从机响应
MB_MRE_MASTER_BUSY 主机忙，设定时间内没拿到主机资源
MB_MRE_EXE_FUN 收到响应后，执行 Modbus 方法时出错

所有主机请求方法都是线程安全且阻塞的。设定超时内没拿到主机资源返回「主机忙」，拿到资源后就等结果。

重发机制要自己加。判断依据是这两条：收到帧数据错误，或命令响应超时。重发次数自增，超过阈值就标记该从站掉线，后续请求直接拦截。第二次重发就收到正常响应的话，计数清零。

事件类型 #

从站的状态机由四个事件驱动，全部在 eMBPoll 的 switch 里分支：

事件 谁投的 含义 eMBPoll 怎么处理
EV_READY 定时器，STATE_RX_INIT 到期 初始化空等结束 把接收状态切到 STATE_RX_IDLE，准备收
EV_FRAME_RECEIVED 定时器，STATE_RX_RCV 到期 一帧收全 取帧、验地址，合法就投 EV_EXECUTE
EV_EXECUTE eMBPoll 自己 该执行功能码了 查表调处理函数，组应答发出去
EV_FRAME_SENT 发送完成中断 应答发完了 什么都不做，仅作记录

四个事件，一个状态机，没有线程。这是 FreeModbus 从站侧的全部调度逻辑。

六、FreeModbus 的运行流程 #

三个函数撑起一个从站 #

c
int main(void)
{
    eMBErrorCode eStatus;

    eStatus = eMBInit(MB_RTU, 0x0A, 0, 38400, MB_PAR_EVEN);
    eStatus = eMBEnable();

    for (;;) {
        (void)eMBPoll();
        usRegInputBuf[0]++;          /* 业务代码放这儿 */
    }
}

初始化、使能、死循环轮询。全部代码就这三步。业务逻辑塞进 for 循环，跟协议栈共享一个上下文。

eMBInit 做了什么 #

第一步设站号。范围 1 到 247，0 是广播地址，248 到 255 保留。站号在总线上必须唯一。

第二步挂函数指针，按模式选一组，第三章那张代码已经贴过。

第三步调 eMBRTUInit，它再去调物理层：

  • xMBPortSerialInit(ucPORT, ulBaudRate, 8, eParity)：打开串口，设波特率、8 数据位、校验方式。示例参数是 9600、8 位、无校验。
  • xMBPortTimersInit(usTimerT35_50us)：初始化 T35 定时器，传进去的是以 50 微秒为单位的计数值。

第四步把 eMBState 置为 STATE_DISABLED，表示协议栈还没启用，等着 eMBEnable 来开门。

eMBEnable 做了什么 #

c
eMBErrorCode eMBEnable(void)
{
    eMBErrorCode eStatus = MB_ENOERR;

    if (eMBState == STATE_DISABLED) {
        pvMBFrameStartCur();          /* 指向 eMBRTUStart */
        eMBState = STATE_ENABLED;
    } else {
        eStatus = MB_EILLSTATE;
    }
    return eStatus;
}

只有一次机会。重复调用返回 MB_EILLSTATE，不会重复启动。

eMBRTUStart 里做三件事：把 eRcvState 设成 STATE_RX_INIT，调 vMBPortSerialEnable(TRUE, FALSE) 只开接收不开发送，调 vMBPortTimersEnable() 启动定时器。

为什么初始化后要先空等一个 T35？ 因为初始化完成那一刻，串口线上兴许已经堆着数据了——上电抖动、对端在重启、前一次通信的尾巴。如果直接进接收状态，这些残渣会被当成一帧的开头，第一帧就错位。规范要求的做法是先安静一个 T35，确认线上没有正在传输的帧，再开始收。定时器到期时投 EV_READY，eMBPoll 收到后把状态切到 STATE_RX_IDLE。

接收状态机 #

c
BOOL xMBRTUReceiveFSM(void)
{
    BOOL xTaskNeedSwitch = FALSE;
    UCHAR ucByte;

    assert(eSndState == STATE_TX_IDLE);
    (void)xMBPortSerialGetByte((CHAR *)&ucByte);

    switch (eRcvState) {
        case STATE_RX_INIT:
            vMBPortTimersEnable();
            break;
        case STATE_RX_ERROR:
            vMBPortTimersEnable();
            break;
        case STATE_RX_IDLE:
            usRcvBufferPos = 0;
            ucRTUBuf[usRcvBufferPos++] = ucByte;
            eRcvState = STATE_RX_RCV;
            vMBPortTimersEnable();     /* 重启 T35 */
            break;
        case STATE_RX_RCV:
            if (usRcvBufferPos < MB_SER_PDU_SIZE_MAX) {
                ucRTUBuf[usRcvBufferPos++] = ucByte;
            } else {
                eRcvState = STATE_RX_ERROR;
            }
            vMBPortTimersEnable();     /* 每字节都重启 */
            break;
    }
    return xTaskNeedSwitch;
}

四个状态流转：

  • STATE_RX_INIT：初始化后的空等期。这时候来的字节一律丢弃，只重启定时器。
  • STATE_RX_IDLE：空闲。第一个字节来了，记到缓冲第 0 位，切到 STATE_RX_RCV，启动 T35。
  • STATE_RX_RCV：接收中。每个字节都往缓冲里塞，塞完重启 T35。塞满了（超过 MB_SER_PDU_SIZE_MAX）转 STATE_RX_ERROR。
  • STATE_RX_ERROR：出错。继续吃字节直到超时，然后整帧丢掉。

关键点在第 4 行 vMBPortTimersEnable()：每收到一个字节都重启计时。所以只要数据还在连续进来，定时器就一直被推迟，永远不会到期。一旦线上安静超过 T35，定时器到期，xMBRTUTimerT35Expired 看到 STATE_RX_RCV，投 EV_FRAME_RECEIVED。

这就是「3.5 字符定时」的全部实现。没有特殊硬件，没有协议开销，一个定时器加每个字节重启一次。

发送状态机 #

发送状态机比接收简单得多：

  • STATE_TX_IDLE：没有发送需求。
  • STATE_TX_XMIT：正在发，每次发送中断送一个字节，发完切回 IDLE 并投 EV_FRAME_SENT。

peMBFrameSendCur（即 eMBRTUSend）负责把 PDU 加上站号和 CRC 组成完整 ADU，放进发送缓冲，然后调 vMBPortSerialEnable(FALSE, TRUE) 打开发送中断。串口发送寄存器在这种芯片上是空的，所以使能之后立刻就会进第一次发送中断。

发送完成的条件是「发送的字节数等于预期长度」，不是「发送寄存器空」。这两个差一个字节。

一帧的完整路径 #

从线上来一个字节，到回出去一帧，走这条链：

text
串口接收中断
  → prvvUARTRxISR
  → pxMBFrameCBByteReceived 指针
  → xMBRTUReceiveFSM          存字节 + 重启 T35
      ... 反复，直到线上安静 3.5 字符 ...
定时器中断
  → prvvTIMERExpiredISR
  → pxMBPortCBTimerExpired 指针
  → xMBRTUTimerT35Expired     看 eRcvState，投 EV_FRAME_RECEIVED
  → vMBPortTimersDisable
主循环
  → eMBPoll
  → xMBPortEventGet 拿到 EV_FRAME_RECEIVED
  → peMBFrameReceiveCur 指针
  → eMBRTUReceive             验长度、验 CRC、拆出站号
  → 站号匹配则投 EV_EXECUTE
  → xFuncHandlers 查表
  → eMBFuncReadHoldingRegister
  → eMBRegHoldingCB           你的回调，填数据
  → eMBRTUSend                加站号和 CRC
  → vMBPortSerialEnable(FALSE, TRUE)
串口发送中断
  → prvvUARTTxReadyISR
  → xMBRTUTransmitFSM         一个字节一个字节发
  → 发完投 EV_FRAME_SENT
  → eMBPoll 收到，忽略

这条链上有三个上下文：串口中断、定时器中断、主循环。共享的是 ucRTUBuf、usRcvBufferPos、eRcvState 三个变量。所以 eMBRTUReceive 里有 ENTER_CRITICAL_SECTION() 和 EXIT_CRITICAL_SECTION()，把取帧这段保护起来，避免主循环取到一半被中断改掉。

取帧时的校验 #

c
eMBErrorCode eMBRTUReceive(UCHAR *pucRcvAddress, UCHAR **pucFrame, USHORT *pusLength)
{
    BOOL xFrameReceived = FALSE;
    eMBErrorCode eStatus = MB_ENOERR;

    ENTER_CRITICAL_SECTION();
    assert(usRcvBufferPos < MB_SER_PDU_SIZE_MAX);

    if ((usRcvBufferPos >= MB_SER_PDU_SIZE_MIN) &&
        (usMBCRC16((UCHAR *)ucRTUBuf, usRcvBufferPos) == 0)) {
        *pucRcvAddress = ucRTUBuf[MB_SER_PDU_ADDR_OFF];
        *pusLength = (USHORT)(usRcvBufferPos - MB_SER_PDU_PDU_OFF - MB_SER_PDU_SIZE_CRC);
        *pucFrame = (UCHAR *)&ucRTUBuf[MB_SER_PDU_PDU_OFF];
        xFrameReceived = TRUE;
    } else {
        eStatus = MB_EIO;
    }

    EXIT_CRITICAL_SECTION();
    return eStatus;
}

两个条件都得过：长度不小于最小值（一个站号加一个功能码加两个 CRC，共 4 字节），CRC 校验结果为 0。

CRC 那行是重点。usMBCRC16 算的是整帧包含 CRC 的校验值，正确帧算出来恒等于 0。不是等于某个固定常数，是等于 0。原因是 CRC 算法对「数据 + 自己的校验值」再算一遍必然归零，这是 CRC 的数学性质。

CRC 不对就返回 MB_EIO，eMBPoll 收到后什么都不做，这一帧静默丢弃。主机那边表现为超时，超时后重发。从站不报告「我收到坏帧了」，因为总线上同时说话的设备兴许不止两台，报错会打架。

主机的运行流程 #

主机侧形状类似，函数名不同：

c
eStatus = eMBMasterInit(MB_RTU, 0, 38400, MB_PAR_EVEN);  /* 无站号，主机不占地址 */
eStatus = eMBMasterEnable();

for (;;) {
    eMBMasterPoll();
    /* 业务：发请求、取结果 */
}

四步走完：

  1. eMBMasterInit 初始化协议栈和硬件。
  2. eMBMasterEnable 启动。
  3. 在独立线程或定时器里周期调 eMBMasterPoll，这个周期决定命令的响应时间。
  4. 调主机请求 API 并设超时。方法阻塞，拿到结果才返回。读命令成功后，数据在主机缓冲里。

主机侧的配置也在 mbconfig.h：广播的转换延时、命令响应超时、从机数量。协议栈只支持连续的从机地址，起始值为 1。

主机的移植比从站麻烦一层，因为要处理线程同步。RTOS 下用事件机制做「请求线程」和「Modbus Poll 线程」的同步，用信号量（默认值 1）保证多线程同时发请求时只有一个能用主机。裸机下事件通知得用软件模拟，事件等待和资源等待都靠自写的延时加标志变量，比 RTOS 模式复杂。

RT-Thread 下要实现的接口：

接口 功能描述

xMBMasterPortEventPost 主机发送事件
xMBMasterPortEventGet 主机获取事件
vMBMasterOsResInit 主机操作系统资源初始化
xMBMasterRunResTake 主机资源获取
vMBMasterRunResRelease 主机资源释放
vMBMasterErrorCBRespondTimeout 响应超时回调
vMBMasterErrorCBReceiveData 接收数据错误回调
vMBMasterErrorCBExecuteFunction 执行 Modbus 方法出错回调

所有主机请求方法签名形状一致：站号、地址、数量或数据、超时。返回值都是 eMBMasterReqErrCode。

c
eMBMasterReqErrCode eMBMasterReqWriteHoldingRegister(UCHAR ucSndAddr, USHORT usRegAddr, USHORT usRegData, LONG lTimeOut);
eMBMasterReqErrCode eMBMasterReqWriteMultipleHoldingRegister(UCHAR ucSndAddr, USHORT usRegAddr, USHORT usNRegs, USHORT *pusDataBuffer, LONG lTimeOut);
eMBMasterReqErrCode eMBMasterReqReadHoldingRegister(UCHAR ucSndAddr, USHORT usRegAddr, USHORT usNRegs, LONG lTimeOut);
eMBMasterReqErrCode eMBMasterReqReadWriteMultipleHoldingRegister(UCHAR ucSndAddr, USHORT usReadRegAddr, USHORT usNReadRegs, USHORT *pusDataBuffer, USHORT usWriteRegAddr, USHORT usNWriteRegs, LONG lTimeOut);
eMBMasterReqErrCode eMBMasterReqReadInputRegister(UCHAR ucSndAddr, USHORT usRegAddr, USHORT usNRegs, LONG lTimeOut);
eMBMasterReqErrCode eMBMasterReqWriteCoil(UCHAR ucSndAddr, USHORT usCoilAddr, USHORT usCoilData, LONG lTimeOut);

eMBMasterReqErrCode eMBMasterReqReadCoils(UCHAR ucSndAddr, USHORT usCoilAddr, USHORT usNCoils, LONG lTimeOut);
eMBMasterReqErrCode eMBMasterReqReadDiscreteInputs(UCHAR ucSndAddr, USHORT usDiscreteAddr, USHORT usNDiscreteIn, LONG lTimeOut);

参数含义统一：

  • ucSndAddr：从机地址，0 表示广播。广播把请求发给所有从机，适合同步多个设备的状态。
  • usRegAddr / usCoilAddr / usDiscreteAddr：起始地址。
  • usNRegs / usNCoils / usNDiscreteIn：数量。
  • pusDataBuffer / pucDataBuffer：数据指针。读操作它是输出，写操作它是输入。读写复合那条里，它同时是读的输出和写的数据来源。
  • lTimeOut：超时时长，支持永久等待。

广播只能用于写，不能用于读。原因很直接：广播时从站不回复，你读不到任何数据。这条限制在协议层，不是库的限制。

七、libmodbus 的 API #

上下文是唯一的入口 #

libmodbus 的一切都围绕 modbus_t 这个不透明结构。它装着跟某个设备通信所需的全部信息：串口路径、波特率、校验方式、从站号、socket、超时值、内部缓冲。

不透明意味着你看不到成员，只能通过函数操作。这是好事，成员布局变了不影响你的代码。

三种上下文，对应三种后端：

创建函数 后端 用什么通信 特有行为
modbus_new_rtu RTU 串口 需要 slave id、波特率、校验、数据位、停止位
modbus_new_tcp TCP IPv4 socket 只支持 IPv4，不做主机名解析
modbus_new_tcp_pi TCP PI socket 支持 IPv4 与 IPv6，能解析主机名，多占约 1KB 内存

RTU 的签名是 modbus_new_rtu(const char *device, int baud, char parity, int data_bit, int stop_bit)。五个参数都是必填，没有默认值。

TCP 的签名是 modbus_new_tcp(const char *ip, int port)。PI 版是 modbus_new_tcp_pi(const char *node, const char *service)，node 是主机名或 IP，service 是端口字符串。

RTU 后端的时间模型 #

这一点是 libmodbus 跟 FreeModbus 最本质的差别，得单独说。

FreeModbus 严格按规范实现：靠 3.5 字符静默判帧。libmodbus 的 RTU 不基于时间，它把字节尽快发出去，按预期字符数收齐就算应答完成。

它靠什么知道该收多少？靠功能码推断。读 4 个保持寄存器的应答固定是 9 加 8 字节，库算得出来。所以它不需要定时器判帧边界，只需要一个总的响应超时。

这个实现带来两个后果：

  • 快。没有 T35 的等待，一问一答的往返时间更短。
  • 有一个坑。从设备的响应超时必须设成小于主设备的响应超时。 否则某个从站不响应时，主站还在等，其他从站兴许已经开始忽略总线上后来的请求了。多从站轮询时这个配置错了，症状是「偶发某几台读不到」。

客户端读函数 #

读寄存器的原型是 int modbus_read_registers(modbus_t *ctx, int addr, int nb, uint16_t *dest)。dest 由你分配，至少要 nb 个 uint16_t。

读位的结果不是一位一个字节。modbus_read_bits(ctx, addr, nb, uint8_t *dest) 里，dest 的每个字节装 8 个位，这是协议本身的打包方式。

函数 功能码 写什么

modbus_write_and_read_registers 是 0x17，一次事务里先写一段再读一段。它省掉一次往返，写参数同时回读设定值，比先写再读两次要快。

错误处理 #

libmodbus 按 POSIX 惯例报错：失败时返回 NULL（指针型）或负数（整数型），错误码放在 errno。

modbus_strerror(errno) 把错误码转成可读字符串。它跟 strerror 的区别是能认自己的错误码，比如协议异常（EMBEXCEPTION 类）、超时（EMBBADCRC、EMBTIMEOUT）。

c
int rc = modbus_read_registers(ctx, 0, 4, tab_reg);
if (rc == -1) {
    fprintf(stderr, "读失败: %s\n", modbus_strerror(errno));
}

注意 errno 要在失败后立刻取。中间调了别的库函数，errno 会被覆盖。

版本信息 #

LIBMODBUS_VERSION_STRING 是编译期常量，告诉你编进来的头文件是哪个版本。变量 libmodbus_version_major、libmodbus_version_minor、libmodbus_version_micro 是链接进来的库版本。

这两个值会不一致——头文件是新的，库里是旧的，或者反过来。跨机器部署时打印出来对一下，能省很多排查时间。

八、libmodbus 的完整例子 #

一个最小可用的主站 #

读一台从站设备的 4 个保持寄存器，打印出来。这段代码可以直接编译运行。

c
#include <stdio.h>
#include <errno.h>
#include <modbus.h>

int main(void)
{
    modbus_t *ctx;
    uint16_t tab_reg[4];
    int rc;
    int i;

    /* 1. 创建 RTU 上下文：串口设备、波特率、校验、数据位、停止位 */
    ctx = modbus_new_rtu("/dev/ttyUSB0", 9600, 'N', 8, 1);
    if (ctx == NULL) {
        fprintf(stderr, "创建上下文失败: %s\n", modbus_strerror(errno));
        return -1;
    }

    /* 2. 设置从站号，RTU 模式必调 */
    modbus_set_slave(ctx, 1);

    /* 3. 打开调试，能看到实际收发的报文，调试完成后再关掉 */
    modbus_set_debug(ctx, TRUE);

    /* 4. 建立连接 */
    if (modbus_connect(ctx) == -1) {
        fprintf(stderr, "连接失败: %s\n", modbus_strerror(errno));
        modbus_free(ctx);
        return -1;
    }

    /* 5. 设置响应超时：1 秒 500 毫秒 */
    modbus_set_response_timeout(ctx, 1, 500000);

    /* 6. 读 4 个保持寄存器，起始地址 0 */
    rc = modbus_read_registers(ctx, 0, 4, tab_reg);
    if (rc == -1) {
        fprintf(stderr, "读寄存器失败: %s\n", modbus_strerror(errno));
    } else {
        for (i = 0; i < rc; i++) {
            printf("reg[%d] = %d (0x%04X)\n", i, tab_reg[i], tab_reg[i]);
        }
    }

    /* 7. 收尾：先关连接，再释放上下文 */
    modbus_close(ctx);
    modbus_free(ctx);
    return 0;
}

编译：

bash
gcc -o test_rtu test_rtu.c $(pkg-config --cflags --libs libmodbus)

没有 pkg-config 的话：

bash
gcc -o test_rtu test_rtu.c -I/usr/local/include/modbus -L/usr/local/lib -lmodbus

生命周期为什么是这个顺序 #

new → set_slave → connect → 读写 → close → free。每一步的位置都有原因。

modbus_set_slave 必须在 connect 之前。它只改上下文里的一个字段，不发任何报文。但连接建立之后，请求组装时才读这个字段。放后面设，第一帧会用默认值。

modbus_close 和 modbus_free 是两件事。前者关 fd，后者释放堆内存。只调 free 不调 close，fd 泄漏，跑几天就 Too many open files。

modbus_free 之后 ctx 是野指针，再调任何函数都是未定义行为。习惯上把它置 NULL。

出错路径也要配对 #

上面那段代码里，modbus_connect 失败的分支先调了 modbus_free(ctx) 才 return。这不是啰嗦，是必须的。new 成功了 connect 失败了，上下文还在堆上，不释放就漏。

写这类资源管理代码的规矩很简单：每个 new 都要有一个配对的 free，每个成功路径的 connect 都要有一个配对的 close，失败路径也不能例外。

一次读写多台从站 #

单从站改站号就行。多从站的写法是同一个 ctx 反复改站号：

c
int slave_ids[] = {1, 2, 3};
uint16_t regs[2];
int n, i;

for (n = 0; n < 3; n++) {
    modbus_set_slave(ctx, slave_ids[n]);

    if (modbus_read_registers(ctx, 0, 2, regs) == -1) {
        /* 单台失败不要 break，其他台继续问 */
        fprintf(stderr, "站 %d 读失败: %s\n",
                slave_ids[n], modbus_strerror(errno));
        continue;
    }

    printf("站 %d: %u, %u\n", slave_ids[n], regs[0], regs[1]);
}

单个从站挂掉不能让整轮采集停摆。循环里用 continue 不用 break。

总线上有一台设备掉电，主站每次问它都要等满超时。三台里掉一台，一轮的总耗时从 30 毫秒变成 1 秒多。所以超时值要按总线规模算，不能随手写 3 秒。

写单个寄存器并回读验证 #

c
uint16_t setpoint = 500;
uint16_t feedback;

if (modbus_write_register(ctx, 0x0010, setpoint) == -1) {
    fprintf(stderr, "写失败: %s\n", modbus_strerror(errno));
} else {
    if (modbus_read_registers(ctx, 0x0010, 1, &feedback) == 1) {
        if (feedback != setpoint) {
            printf("回读不一致: 写 %u 读 %u\n", setpoint, feedback);
        }
    }
}

modbus_write_register 成功返回 1，失败返回 -1。0x06 功能码的应答是原样回显请求，所以「返回 1」就代表从站确认收到了。

回读验证是工业现场的习惯做法。写入成功只说明从站收到了报文，不说明它真的接受了这个值——很多设备对超范围的设定值会静默钳位。

读浮点数 #

电表、温度变送器经常把浮点拆在两个寄存器里。假设手册说「32 位浮点，高字在前，ABCD 顺序，起始地址 0x0000」。

c
uint16_t raw[2];
float value;

if (modbus_read_registers(ctx, 0x0000, 2, raw) == 2) {
    value = modbus_get_float_abcd(raw);
    printf("值: %f\n", value);
}

手册写的字节序跟函数后缀的对应关系要对准。常见说法与函数的选择：

手册描述 用哪个函数
高字在前，低字在后，字内高字节在前 modbus_get_float_abcd
高字在前，字内字节交换 modbus_get_float_badc
低字在前，字内高字节在前 modbus_get_float_cdab
低字在前，字内字节也反 modbus_get_float_dcba

手册不给字节序的，实测一遍最快：让从站输出一个已知值（比如 25.5），把两个原始寄存器打出来，四种组合试一遍，哪个得 25.5 就是哪个。

一个 TCP 的对应版本 #

TCP 只改三行：创建上下文、去掉串口参数、不需要 set_slave 之外的串口配置。

c
ctx = modbus_new_tcp("192.168.1.100", 502);
if (ctx == NULL) {
    fprintf(stderr, "创建上下文失败: %s\n", modbus_strerror(errno));
    return -1;
}

modbus_set_slave(ctx, 1);        /* Modbus TCP 里是单元号 */

if (modbus_connect(ctx) == -1) {
    fprintf(stderr, "连接失败: %s\n", modbus_strerror(errno));
    modbus_free(ctx);
    return -1;
}

端口 502 是 Modbus TCP 的约定端口，需要 root 权限或者 CAP_NET_BIND_SERVICE 才能监听。作客户端连别人不受这个限制。自己当服务端时，很多工程改用 1502 之类的非特权端口。

TCP 不需要校验，因为 TCP 和 IP 层已经保证完整性。所以 TCP 帧里没有 CRC，比 RTU 短 2 个字节。这也是为什么同一套 PDU 能同时跑在两种传输上。

编译验证与常见反馈 #

pkg-config --cflags --libs libmodbus 正常应该输出 -I/usr/local/include/modbus -L/usr/local/lib -lmodbus 这类东西。

输出为空说明 .pc 文件没找到。两种原因：装到了非标准路径，或者 PKG_CONFIG_PATH 没包含那个路径。手工加：

bash
export PKG_CONFIG_PATH=/usr/local/lib/pkgconfig:$PKG_CONFIG_PATH

编译过了但运行时报 error while loading shared libraries: libmodbus.so.5，是运行期找不到动态库。三条路：把库路径加进 ld.so.conf 再 ldconfig；设 LD_LIBRARY_PATH；或者干脆静态链接。

静态链接用 pkg-config --libs --static libmodbus，或者在 configure 时加 --enable-static。

九、RTU 与 TCP 两种接法 #

两者的根本差别 #

RTU 跑在串口上，靠时间切帧，带 CRC。TCP 跑在以太网上，靠 MBAP 头里的长度字段切帧，不需要 CRC。

维度 Modbus RTU Modbus TCP
承载 RS-485 / RS-232 串口 TCP/IP，默认端口 502
切帧方式 3.5 字符静默 MBAP 头里的长度字段
校验 CRC16，从站号 + PDU 无，靠 TCP/IP 保证
地址 1 字节从站号，1~247 MBAP 里 1 字节单元号 + IP 区分设备
帧头开销 1 字节站号 + 2 字节 CRC 7 字节 MBAP
一帧最大 256 字节 260 字节
广播 支持，站号 0 不支持
物理拓扑 总线，一主多从，半双工 星型，多客户端可并发
距离 1200 米（降波特率） 看网络，可跨路由
实时性 确定，毫秒级 不确定，受网络栈影响

MBAP 头 7 个字节：事务标识 2 字节、协议标识 2 字节（恒为 0）、长度 2 字节、单元号 1 字节。事务标识让客户端能把应答跟请求对上，这是 RTU 没有的能力。

FreeModbus 走 TCP #

改 mbconfig.h 把 MB_TCP_ENABLED 设为 1，然后实现 porttcp.c 的三个接口。物理层从串口换成 socket 监听，上层一行不动。

这种组合在用的人不多。原因很简单：能在 MCU 上跑 TCP 的芯片，也能跑 Linux，而 Linux 上 libmodbus 更省事。加上 FreeModbus 的 TCP 实现不带并发，一个连接一个连接地处理。

真要做嵌入式 TCP 从站，注意 socket 缓冲和协议栈缓冲的边界。xMBTCPPortGetRequest 把数据拷进 ucMBFrame，拷多了越界，拷少了帧不完整。长度必须取自 MBAP 头，不能取自 recv 的返回值——一次 recv 也许只拿到半个 PDU。

libmodbus 走 RTU 的现场配置 #

串口参数必须跟从站完全一致：波特率、数据位、校验、停止位。这四项对不上，收到的全是乱码，表现是 CRC 错或者超时。

c
/* 8 数据位、无校验、1 停止位、9600 */
ctx = modbus_new_rtu("/dev/ttyUSB0", 9600, 'N', 8, 1);

/* 8 数据位、偶校验、1 停止位、19200 */
ctx = modbus_new_rtu("/dev/ttyS1", 19200, 'E', 8, 1);

parity 参数是字符：'N' 无、'E' 偶、'O' 奇。大小写敏感。

RS-485 需要方向控制时，用 RTS 相关的函数：

函数 干什么
modbus_rtu_get_serial_mode / modbus_rtu_set_serial_mode 查/设 RS-232 还是 RS-485 模式
modbus_rtu_get_rts / modbus_rtu_set_rts 查/设 RTS 模式：无、上行下行、下行上行
modbus_rtu_set_custom_rts 自定义 RTS 切换的回调
modbus_rtu_get_rts_delay / modbus_rtu_set_rts_delay RTS 切换前后的延时，微秒

Linux 上如果串口驱动本身支持 RS-485（TIOCSRS485 ioctl），设 modbus_rtu_set_serial_mode(ctx, MODBUS_RTU_RS485) 后方向切换由内核处理，不用你管。用 USB 转 485 的转换器时，方向切换在转换器内部自动完成，也不用管。只有用 GPIO 手工控制 DE 引脚时才需要 modbus_rtu_set_custom_rts。

RTU 调试的三个标志 #

现场调 RTU 出问题时，按这个顺序看：

  1. modbus_set_debug(ctx, TRUE) 打开，看收发的原始字节。发出去的站号、功能码、地址对不对，一眼就看出来。
  2. 收到的字节是不是全 0x00 或全 0xFF。是的话，多半是波特率或校验配错，或者 A/B 接反。A/B 接反是 RS-485 最常见的接线错误。
  3. 字节看着对但 CRC 错。查终端电阻。总线两端各一个 120Ω，中间不要加。距离短、波特率低的时候不加也能跑，一加长就不行。

modbus_set_debug 的输出走 stderr，重定向要注意别跟正常输出混在一起。

TCP 的并发模型 #

RTU 是总线，一主多从，同一时刻只有一个主站在说。TCP 不是，多个客户端可以同时连同一个服务端。

libmodbus 的 server 用 modbus_tcp_listen + modbus_tcp_accept 处理并发。典型做法是 select 或 poll 监听一组 fd，哪个可读就 modbus_tcp_accept 出新连接，然后用一个独立的 modbus_t 上下文处理。

这里的坑是：一个 modbus_t 上下文不能同时给两个连接用。 它内部的收发缓冲是共享的，并发用会串数据。每个连接必须有自己的一份上下文，或者用串行的方式（一个处理完再处理下一个）。

modbus_mapping_t 反过来可以共享，因为它是数据不是状态。多个连接读同一张映射表没问题，写要加锁。

两种接法的选择 #

现场条件决定，不是技术偏好决定。

现场情况 选 RTU 选 TCP
老设备只有 RS-485 口 是 否
要拉 200 米以上的线 是 否
从站数量十几台以上 是，一条总线搞定 要加交换机
要跨网段、要远程访问 否 是
同一台设备要被多个上位机同时读 否 是
电磁干扰强（变频器旁） 差分传输抗干扰好 网线也怕干扰
要毫秒级确定性 是 否

实际项目里两种都有的情况很常见：现场一层用 RTU 总线把设备串起来，接一个网关，网关往上走 TCP 到中控室。网关就是那个翻译层。

拿源码 #

从 GitHub 拿：访问 libmodbus，点绿色的「Code」按钮，选「Download ZIP」。解压就是源码树。

或者 git clone https://github.com/stephane/libmodbus.git。要特定版本就 git checkout 到对应 tag。

交叉编译 #

关键是 --host 参数。它告诉 configure「我要生成给另一种 CPU 跑的代码」，configure 会据此去找对应的交叉编译器。

bash
./configure --build=i686 --host=arm-none-linux-gnueabi \
            --enable-static \
            --prefix=/root/libmodbus-3.1.1/install/ && make install

逐个参数说：

参数 作用 不写会怎样
--build=i686 编译这台机器本身的架构 多数情况能自动检测，交叉编译时建议写明
--host=arm-none-linux-gnueabi 目标架构，决定用哪个交叉编译器 编出 x86 的库，拷到板子上跑不了
--enable-static 同时生成 .a 静态库 只有 .so，板子上没库就起不来
--prefix=... 安装路径 装到 /usr/local，混进宿主机系统

--prefix 强烈建议写，而且写成一个独立目录。交叉编译产物混进宿主机的 /usr/local/lib，下次编本机程序链接到 ARM 的库，报一堆看不懂的架构错误。

--host 的值要跟你的交叉编译器前缀一致。工具链叫 arm-none-linux-gnueabi-gcc，--host 就写 arm-none-linux-gnueabi。工具链叫 arm-linux-gnueabihf-gcc，就写 arm-linux-gnueabihf。写错了 configure 会报 checking for arm-xxx-gcc... no。

PC 上编译就简单：

bash
./configure && make install

交叉编译的几个常见错误 #

现象 原因 怎么办
checking for arm-xxx-gcc... no --host 与工具链前缀不符，或工具链不在 PATH 对齐前缀，或 export PATH=$PATH:/opt/toolchain/bin

上面每一条都对应一个具体的报错文本，遇到别的先看 config.log。configure 的所有探测结果都在里面，比终端的最后几行有用得多。

板子上跑测试程序 #

源码的 test 目录下有 unit-test-server、unit-test-client 这类名字的文件。它们不是可执行文件，是脚本，会去调同目录下 .lib/ 里的真可执行文件。

在 PC 上执行脚本，在嵌入式平台上直接跑可执行文件。这一点不注意会白折腾半天「为什么提示找不到命令」。

跑之前先确认网络和串口设置。测 TCP 要改源码里的 IP，默认是回环地址。测 RTU 要把串口设备名改成板子上的实际名称：嵌入式开发板一般是 /dev/ttyS0、/dev/ttyS1 这种，具体哪个看板子配置；PC 上一般是 /dev/ttyUSB0。跑在虚拟机里的，串口要在虚拟机侧配置，不是宿主机侧。

unit-test-server.c 里改这几行：

c
if (use_backend == TCP) {
    ctx = modbus_new_tcp("192.168.169.209", 1502);
    query = malloc(MODBUS_TCP_MAX_ADU_LENGTH);
} else if (use_backend == TCP_PI) {
    ctx = modbus_new_tcp_pi("::0", "1502");
    query = malloc(MODBUS_TCP_MAX_ADU_LENGTH);
} else {
    ctx = modbus_new_rtu("/dev/ttyS1", 115200, 'N', 8, 1);
    modbus_set_slave(ctx, SERVER_ID);
    query = malloc(MODBUS_RTU_MAX_ADU_LENGTH);
}

unit-test-client.c 里改这几行：

c
if (use_backend == TCP) {
    ctx = modbus_new_tcp("192.168.169.209", 1502);
} else if (use_backend == TCP_PI) {
    ctx = modbus_new_tcp_pi("::1", "1502");
} else {
    ctx = modbus_new_rtu("/dev/ttyUSB0", 115200, 'N', 8, 1);
}

两个文件里 MODBUS_TCP_MAX_ADU_LENGTH 和 MODBUS_RTU_MAX_ADU_LENGTH 不能混用，长度差 2 个字节（RTU 多两个 CRC）。

Windows 上用 Qt 编 #

交叉编译之外的另一个坑：Windows 没有 POSIX，得用 win32 目录里的替代实现。

步骤：

  1. 进 src 目录，把 .cpp 和 .h 全选，加上 win32 文件夹里的 config.h。全部拷到你项目的 modbus 目录。
  2. 打开 Qt Creator，右键项目名，「添加现有文件」，把拷过去的都加进工程。
  3. .pro 文件里加 LIBS += -lws2_32。这是 Windows Socket 库，不链就一堆 undefined reference to 'WSAStartup' 之类。
  4. 构建。代码里要 #include "config.h"，让那份 win32 版的配置生效。

撞上的错误：error: undefined reference to 'qMain'。这不是 libmodbus 的问题，是工程里缺 main 函数。Qt 把第一个参数当入口，没有 main 就报这个。检查一下你的 .cpp 里有没有 int main(int argc, char *argv[])。

Windows 上还有个明显的差异：串口名是 COM3 这种，不是 /dev/ttyS0。传给 modbus_new_rtu 的就是 "COM3"。

十一、两个库的选型建议 #

按角色选 #

你的设备 首选 备选
MCU 从站（传感器、IO 模块、扩展卡） FreeModbus slave 自写极简从站
MCU 主站（采集盒、小型网关） FreeModbus host（仅 RTU） 自写
Linux 主站（工控机、上位机、SCADA） libmodbus client pymodbus
Linux 从站（跑在 ARM 板上的设备） libmodbus server 自写
Windows 主站 libmodbus 改 win32 商业库
带 Python 的网关 pymodbus 两个都行

按约束选 #

资源受限是第一优先级。Flash 小于 32K、RAM 小于 4K 的芯片，FreeModbus 要裁剪：关掉 ASCII，只编需要的功能码，把 MB_SER_PDU_SIZE_MAX 调到 64。裁完能压到 6K Flash、1K RAM 左右。

libmodbus 的上下文是堆分配的，内部缓冲加映射表，十几个 KB 起步。这种量级在裸机 MCU 上没有意义。

维护周期也要算。库有社区，你的代码只有你。三年后回来看这段代码，库还在更新，你的注释已经不知道在说什么了。

不要做的事 #

  • 不要在 MCU 上为了「统一技术栈」硬塞 libmodbus。移植 POSIX 层的代价远大于收益。
  • 不要在 Linux 上为了「代码量小」硬塞 FreeModbus。你得模拟串口寄存器、定时器中断和临界区，纯粹给自己找活。
  • 不要两个库混在一个进程里当同一角色的实例。两套超时、两套缓冲，排查问题时你会分不清是谁的锅。

一个混合架构的例子 #

网关项目：南向是 RTU 主站，挂 8 台电表；北向是 TCP 从站，被中控室轮询。

text
中控室 ── TCP 502 ──→ 网关（北向从站，映射表 A）
                          ↕ 数据同步（单向写）
                       网关（南向主站，采集缓冲 B）
                          ↕
                      RS-485 总线
                     ├── 电表 1
                     ├── 电表 2
                     └── ... 电表 8

南向用一个 libmodbus client 实例，循环问 8 台，把结果写进映射表 A 的保持寄存器区。北向用 libmodbus server，modbus_receive 等中控室的请求，modbus_reply 从表 A 里取数据。

数据流单向：B 写进 A，A 只被读。不加锁也不会读到半个值——前提是写的时候按寄存器边界写，别跨区。

这种架构里两个库各自的优势都用上了：南向要处理多从站、超时，libmodbus client 现成；北向要按需应答、要能并发，modbus_mapping + modbus_reply 现成。

移植成本的实际量级 #

说实话，不粉饰。

FreeModbus 移植到一颗新 MCU，熟手两到四小时。时间花在查串口寄存器、算定时器分频、确认中断向量名。第一次做陌生芯片，一天。

libmodbus 交叉编译，半小时。前提是工具链现成。第一次配工具链要花掉一天。

从长期看，FreeModbus 的成本集中在开头一次，之后就稳定。libmodbus 的成本分散在每次部署——换一块板子、换一个 glibc 版本、换一个动态链接器路径，都得重新调一遍。

两边共通的坑 #

站号 0 是广播，不是第一台设备。 站号从 1 开始。写 0 的请求所有从站执行且都不回复。读操作发广播，永远拿不到数据。

地址从 0 还是从 1 开始，看手册。 Modbus 规范里寄存器地址从 0 算，但很多厂家手册写 40001 这种「PLC 地址」。40001 对应实际地址 0，40002 对应 1。差一位，读出来全是隔壁寄存器的值。

16 位寄存器存不下 32 位数据的顺序。 一个字放高 16 位、下一个放低 16 位，还是反过来，厂家各写各的。手册没写就实测。

波特率不是越高越好。 9600 在 1200 米总线上很稳，115200 在同样线长上一帧都过不去。线长和波特率的乘积有个经验上限，超了就降速。

超时要按总线规模算。 一台设备超时 1 秒，八台里挂两台，一轮就是 2 秒多。上位机界面刷新比这快，就会看到数据不更新。

调试开关别忘了关。 modbus_set_debug(ctx, TRUE) 会往 stderr 打每一帧报文，跑在嵌入式板子上往串口控制台刷，能把你的正常输出淹掉。

查问题的最短路径 #

从站不出数据时，按这个顺序排：

  1. 用示波器或 USB 转 485 抓一下总线，看有没有波形。没波形是硬件或接线，跟代码无关。
  2. 有波形但主站说超时，把主站换成 modbus_set_debug 打开，看发出去的报文对不对。
  3. 发出去的报文对，从站不回，那就是从站侧的问题，去从站的 eMBPoll 里下断点。
  4. 从站回了但主站说 CRC 错，看两边波特率、校验、停止位是否一致。
  5. 都对了但数据不对，检查寄存器地址偏移和字节序。

这条路径每一步都在缩小范围。跳步骤会绕远路，比如一上来就怀疑自己的业务代码，改半天发现是 A/B 线接反。

一句话收尾 #

FreeModbus 和 libmodbus 都不是让你「学会 Modbus」的教材，是让你「不用学会 Modbus 也能用上 Modbus」的工具。它们的价值在于把组帧、校验、切帧、超时、异常应答这些死板的活接过去，把「这个地址代表什么」留给你。

想清楚你站在主站还是从站，跑在 MCU 还是 Linux，答案就出来了。剩下的时间该花在业务上——那才是你真正要交付的东西。
