本篇只讲一件事：串口上字节一个个进来，程序怎么把它们拼回一帧。

讲什么：三种切帧方案、状态机写法与错误恢复、环形接收缓冲、中断与主循环的分工、校验与丢帧统计、调试工具选型、USB 转串口驱动。

不讲什么：UART 电平标准、波特率分频、起止位怎么算，在《串口基础》；Modbus 功能码与寄存器模型在《Modbus 协议》；从机栈移植在《Modbus 实现》。

代码有两套：C 写的裸机版，贴近 MCU；Qt/C++ 写的上位机版，贴近 PC 侧。解决的是同一个问题。

一、串口收包难在哪 #

read(fd, buf, 256) 的返回值是「这一瞬间内核缓冲里有多少字节」。它不告诉你这 37 个字节属于第几帧，也不说下一帧从哪开始。

发端发 10 帧、每帧 8 字节共 80 字节，收端一次 read 拿到多少，取决于轮询间隔、波特率抖动、有没有流控、USB 转串口芯片怎么打包。实测下来 80 字节被打成 30+32+18，或者 8+72，都正常。字节顺序一定对，切分点一定不对。

这就是所有串口协议的第一道难题：串口是字节流，没有消息边界，边界得程序自己造。

和 TCP 粘包的关系 #

粘包不是 TCP 的毛病，是「流式接口 + 应用层有消息概念」这个组合的必然结果。串口比 TCP 多三条麻烦：

维度 TCP 串口
字节会不会丢 不丢，丢了重传 会丢：溢出、干扰、线松
会不会多出字节 不会 会：上电抖动、热插拔、波特率不匹配
断开怎么知道 FIN / RST 无通知，只能超时或看 DCD/DSR
出错补救 内核重传 协议自己重发，或干脆丢掉

TCP 那套「靠长度切」「靠分隔符切」搬到串口都成立，但必须再加一层：丢掉明显不合法的残渣。脏字节来源很杂——上电瞬间 TX 未稳定会读到几十字节的 0x00 或 0xFF；对端波特率配错，收来全是错位数据；线长、共地不良导致边沿畸变；USB 转串口拔插时驱动补一段空数据；对端拿串口当 printf 调试口，混进一堆 ASCII。垃圾会插在帧之间，也会插在帧中间，切帧逻辑要吞掉前者，识别并丢弃后者。

写收包代码前先回答三个问题：一帧多长（固定、靠长度、靠结束符）；帧从哪开始（数据里会不会出现和帧头相同的字节）；收错了怎么办（丢掉重来还是请求重发）。

一个反面例子 #

c
void USART1_IRQHandler(void)
{
    u8 ch = USART_ReceiveData(USART1);
    if (ch == 0xAA) {
        buf[idx++] = ch;              /* 认为一帧开始，后面全往里塞 */
    } else if (idx > 0) {
        buf[idx++] = ch;
    }
    if (idx >= 64) {
        parse_frame(buf, idx);        /* 中断里解析 + 业务处理 */
        idx = 0;
    }
}

三个坑叠在一起：中断里解析、没有超时、没有校验。实验室跑没事，现场一天丢十几帧，查一周查不出来。

二、三种切帧方案 #

2.1 固定长度 #

每帧字节数写死，收满 N 个就交给解析。

c
#define FRAME_LEN 16
static u8  s_buf[FRAME_LEN];
static u32 s_cnt;

void on_byte(u8 ch)
{
    s_buf[s_cnt++] = ch;
    if (s_cnt == FRAME_LEN) {
        frame_handle(s_buf, FRAME_LEN);
        s_cnt = 0;
    }
}

十行代码，不用状态机，不用查帧头，CPU 开销最低。代价有三条：帧长写死，短消息要补齐，长消息发不了；中途丢一个字节，后面所有帧全部错位，而且永远错不回来，因为没有重同步依据；对端或自己重启后，得靠额外握手重新对齐。

适合固定长度的采样上报，比如 3 轴加速度 6 字节 + 时间戳 4 字节 + 校验 2 字节。补救错位有个土办法：靠校验，每 N 字节算一次，连错 3 帧判失步，主动丢一个字节重新对齐，最多试 N 次。

2.2 帧头帧尾 #

以固定标志字节开始、固定标志字节结束，最常见是 0xAA ... 0x55，也有 0x7E（HDLC/PPP 风格）、0x02 ... 0x03（STX/ETX）。

c
#define HEAD 0xAA
#define TAIL 0x55

void on_byte(u8 ch)
{
    static u8  buf[128];
    static u32 n;
    static u8  in_frame;

    if (!in_frame) {
        if (ch == HEAD) { in_frame = 1; n = 0; buf[n++] = ch; }
        return;
    }
    buf[n++] = ch;
    if (ch == TAIL) {
        frame_handle(buf, n);
        in_frame = 0;
    } else if (n >= sizeof(buf)) {
        in_frame = 0;                 /* 超长，丢弃等下一个帧头 */
    }
}

问题来了：数据区里出现 0x55 怎么办？ 帧会被提前截断。三种解法。

转义（字节填充）。 约定 0x7D 为转义符，发送时把数据里的 0x7D 发成 0x7D 0x5D，0x55 发成 0x7D 0x35，0xAA 发成 0x7D 0x0A；接收时见到 0x7D，把下一字节异或 0x20 还原。这是 PPP 的经典做法。代价是最坏情况数据膨胀一倍（数据全是 0x55 时），且收发两端必须对称实现，一端漏了就全乱。

长度字段兜底。 帧头后跟长度，长度到了就结束，帧尾只当额外确认，数据里出现 0x55 不影响切帧。

多字节帧头 + 强校验。 帧头用两个不常见字节（比如 0xFF 0xEF），数据区里两个连着的概率低，再靠 CRC 兜底。代价是「概率低」不等于零，长期跑总会撞上。

解法 数据膨胀 判断成本 抗噪 适用
转义 最坏 ×2 收发两端都要实现 强，边界无歧义 二进制协议、长度不定
长度兜底 无 只查长度 中，长度打错就全错 有长度字段的协议
多字节帧头 + CRC 无 两字节 + CRC 弱，靠概率 短帧、低噪声链路

2.3 长度字段 #

帧头后跟一个（或两个）长度字节，取值是「数据区长度」或「整帧长度」。

text
+------+--------+----------+--------+
| HEAD |  LEN   |   DATA   | CRC16  |
|  2B  |   1B   | LEN 字节 |   2B   |
+------+--------+----------+--------+

收端：识别帧头 → 读 LEN → 读 LEN 字节数据 → 读 2 字节 CRC → 校验。一帧可以 5 字节也可以 200 字节。两个坑要防。

坑一：长度字段本身被干扰。 噪声把 LEN 从 0x08 打成 0xFF，收端就傻等 255 字节，后面所有正常帧都被当成这个假帧的数据吞掉。

c
#define MAX_PAYLOAD 200

void on_len(u8 len)
{
    if (len == 0 || len > MAX_PAYLOAD) {
        s_state = ST_IDLE;            /* 长度非法，立刻复位 */
        s_stat.err_len++;
        return;
    }
    s_need  = len;
    s_got   = 0;
    s_state = ST_DATA;
}

坑二：长度语义要统一。 是「数据区长度」还是「整帧长度」？文档写清楚。素材里那段 Qt 代码 m_unNeedReadNu = getData_p[4] - FRAME_HEAD_SIZE; 就是「整帧长度减去已读帧头」，属于后者。改成数据区长度就得把 CRC 字节一起算，差 2 字节会永远差 2 字节。

项目 固定长度 帧头帧尾 长度字段
切帧依据 字节计数 结束标志 长度字节
代码量 最少 中（要转义） 中
帧长可变 否 是 是
数据可放任意字节 能 需转义 能
丢字节后能否重同步 不能，靠校验硬找 能，等下个帧头 能，等下个帧头
最怕什么 中途丢字节 数据含结束符 长度字段被打错
带宽利用率 低（补齐） 中（转义膨胀） 高

实际项目最常见的是「帧头 + 长度字段 + CRC」的组合。它同时给了重同步依据（帧头）和确定边界（长度），CRC 只负责最后把关。第四种方案不靠字节内容，靠时间，单独成章。

三、超时切帧 #

发端连续发一帧时，字节与字节的间隔就是一个字符时间，由波特率决定，几乎不变。一帧发完发端停顿，间隔拉长。所以「间隔超过 N 个字符时间」等于「这一帧结束了」。这是 Modbus RTU 唯一的切帧方式，RTU 帧既没有帧头也没有帧尾，全靠静默间隔。

text
[01][03][00][00][00][0A][C5][CD]  ~~~~静默~~~~  [01][03]...
|<---- 帧内间隔约 1 字符 ---->|  |<- 3.5 字符 ->|
                                      ↑ 判一帧结束

3.1 3.5 个字符时间怎么来 #

Modbus over Serial Line 规范定了两个时间：t1.5（1.5 个字符时间）判断「帧内字节间隔过长，帧不完整」；t3.5（3.5 个字符时间）判断「帧间静默足够，上一帧结束」。

一个字符 = 起始位 + 数据位 + 校验位 + 停止位，8E1 是 11 位，8N1 是 10 位。字符时间 = 位数 ÷ 波特率。

波特率 1 字符 t1.5 t3.5
1200 9.17 ms 13.8 ms 32.1 ms
2400 4.58 ms 6.9 ms 16.0 ms
4800 2.29 ms 3.4 ms 8.0 ms
9600 1.15 ms 1.7 ms 4.0 ms
19200 573 μs 860 μs 2.0 ms
38400 286 μs 430 μs 1.0 ms
57600 191 μs 287 μs 669 μs
115200 95.5 μs 143 μs 334 μs

按 10 位算，数值是上表的 10/11，9600 时 3.65 ms，工程上取整到毫秒。注意 19200 以上那几行：规范对高于 19200 的波特率另给约定，用固定 1.75 ms，不再按字符时间等比缩小。原因很实在——334 μs 这个量级，普通 MCU 的定时器分辨率加中断延迟已经撑不住，量出来的抖动比阈值本身还大。

所以这个值随波特率变。波特率改了，定时器重装值必须跟着改，忘了改就是「9600 调通、115200 全错帧」。

3.2 实现 #

三句话：收到字节记时间戳，定时器周期检查，超时就把缓冲交出去。

c
#define FRAME_MAX 256

static u8  s_rx[FRAME_MAX];
static u32 s_rx_len;
static u32 s_last_tick;          /* 最后收到字节的时刻，ms */
static u32 s_t35_ms, s_t15_ms;

/* 中断里调 */
void rx_isr(u8 ch)
{
    u32 now = get_tick_ms();
    if (s_rx_len > 0 && (now - s_last_tick) > s_t15_ms) {
        s_stat.err_gap++;
        s_rx_len = 0;            /* 帧内断了太久，前面字节作废 */
    }
    if (s_rx_len < FRAME_MAX) {
        s_rx[s_rx_len++] = ch;
    } else {
        s_stat.err_overflow++;
        s_rx_len = 0;
    }
    s_last_tick = now;
}

/* 主循环或 1ms 定时器里调 */
void rx_poll(void)
{
    if (s_rx_len == 0) {
        return;
    }
    if ((get_tick_ms() - s_last_tick) >= s_t35_ms) {
        frame_handle(s_rx, s_rx_len);
        s_rx_len = 0;
    }
}

阈值按波特率算一次，别在中断里算：

c
void set_baud(u32 baud, u8 data_bits, u8 parity, u8 stop_bits)
{
    u32 bits = 1 + data_bits + (parity ? 1 : 0) + stop_bits;
    if (baud > 19200) {
        s_t35_ms = 2;                       /* 规范固定值，留余量 */
        s_t15_ms = 1;
    } else {
        s_t35_ms = (3500u * bits / (baud / 1000u) + 999) / 1000;
        s_t15_ms = (1500u * bits / (baud / 1000u) + 999) / 1000;
        if (s_t35_ms == 0) { s_t35_ms = 1; }
        if (s_t15_ms == 0) { s_t15_ms = 1; }
    }
}

3.3 太短与太长 #

太短会误切。 阈值小于实际字节间隔，正常帧被从中间切断，表现是「偶发 CRC 错」，断点位置随调度抖动而变，不是固定错，最难查。

太长会延迟。 一帧收完还得干等，从机响应时间被拖长，主机以为超时重发，总线上出现重复帧。

经验值：取 3.5 字符时间，别往上加太多。想留余量就把定时器周期设小（1 ms 甚至 500 μs），阈值本身别动。

3.4 短板 #

帧长完全靠猜，一帧收到一半对端掉电要等满超时才丢弃；依赖时钟精度，用 RC 振荡的低价 MCU 温漂大了阈值就偏；不适合大帧，一帧 4 KB 中间一个字节间隔超阈值就整帧报废；多帧粘一起时无法区分，主机轮询周期压太紧，从机看到「两帧连成一片」，长度翻倍，CRC 必错。

最后一条是真事。Modbus 规定帧间至少 3.5 字符静默，主机侧必须遵守。所以工业现场常做「超时切帧 + CRC」双保险，甚至再加一个帧头字节做二次确认。

四、状态机的写法 #

4.1 为什么用状态机 #

if 堆出来的切帧逻辑，状态藏在若干独立变量里：in_frame、need_len、got、crc_ok。变量一多组合就爆炸，改一处漏一处。状态机把「进展到哪一步」压成一个变量，所有分支从它出发。每个字节只走一个分支，行为可枚举；加一种帧类型只加状态不动老代码；出错时打印 state 就知道卡在哪；好写单测。

4.2 状态划分 #

按帧的物理结构切，一段结构一个状态。

text
   ┌────────┐ 头字节1 ┌─────────┐ 头字节2 ┌────────┐
   │  IDLE  │────────>│ HEADER1 │────────>│HEADER2 │
   └────────┘         └─────────┘         └────────┘
        ^                  │ 不匹配           │ 全中
        │                  │                  v
        │                  │             ┌────────┐
        │                  │             │ LENGTH │
        │                  │             └────────┘
        │                  │                  │ len
        │                  │                  v
        │                  │             ┌────────┐
        │                  │             │  DATA  │
        │                  │             └────────┘
        │                  │                  │ 收满
        │                  │                  v
        │                  │             ┌────────┐
        │                  │             │  CRC   │
        │                  │             └────────┘
        │                  │               │      │
        │                  │          通过 │      │ 失败
        │                  v               v      │
        └─────────────────────────────┌────────┐ │
                                      │  DONE  │<┘
                                      └────────┘
状态 含义 转出条件
IDLE 等帧头 命中第 1 字节 → HEADER1
HEADER1 等帧头第 2 字节 命中 → HEADER2；又是头字节 1 → 留本状态；否则 → IDLE
HEADER2 攒多字节帧头 全中 → LENGTH；不中 → IDLE
LENGTH 等长度字段 合法 → DATA；非法 → IDLE
DATA 收数据区 收满 → CRC
CRC 收校验并比对 通过 → DONE；失败 → IDLE
DONE 收尾（帧尾字节） 提交帧 → IDLE

IDLE 是唯一「可以随便丢字节」的状态。其他状态一旦进错，必须能回 IDLE，否则永久卡死。

4.3 switch 版骨架 #

c
typedef enum {
    ST_IDLE = 0, ST_HEADER1, ST_HEADER2,
    ST_LENGTH, ST_DATA, ST_CRC, ST_DONE
} frame_state_t;

#define HEAD0       0xAA
#define HEAD1       0x55
#define MAX_PAYLOAD 200

typedef struct {
    frame_state_t state;
    u8  header[2];
    u8  len;
    u8  payload[MAX_PAYLOAD];
    u16 crc_calc, crc_recv, idx;
    struct { u32 ok, err_head, err_len, err_crc, err_timeout; } stat;
} frame_parser_t;

void fp_reset(frame_parser_t *p)
{
    p->state = ST_IDLE;
    p->idx = 0;
    p->len = 0;
    p->crc_recv = 0;
    p->crc_calc = 0;
    memset(p->payload, 0, sizeof(p->payload));
    memset(p->header,  0, sizeof(p->header));
}

void fp_feed(frame_parser_t *p, u8 ch)
{
    switch (p->state) {
    case ST_IDLE:
        if (ch == HEAD0) { p->header[0] = ch; p->idx = 1; p->state = ST_HEADER1; }
        break;

    case ST_HEADER1:
        if (ch == HEAD1)      { p->header[1] = ch; p->state = ST_HEADER2; }
        else if (ch == HEAD0) { p->idx = 1; }   /* 又是头字节，继续等 */
        else                  { p->stat.err_head++; p->state = ST_IDLE; }
        break;

    case ST_HEADER2:
        p->state = ST_LENGTH;                   /* 两字节帧头，进长度 */
        break;

    case ST_LENGTH:
        if (ch == 0 || ch > MAX_PAYLOAD) { p->stat.err_len++; p->state = ST_IDLE; break; }
        p->len = ch;
        p->idx = 0;
        p->state = ST_DATA;
        break;

    case ST_DATA:
        p->payload[p->idx++] = ch;
        if (p->idx >= p->len) { p->state = ST_CRC; }
        break;

    case ST_CRC:
        if (p->idx == p->len) {                 /* 校验低字节 */
            p->crc_recv = ch;
            p->idx++;
        } else {                                /* 校验高字节，比对 */
            p->crc_recv |= (u16)ch << 8;
            p->crc_calc  = crc16_modbus(p->payload, p->len);
            if (p->crc_calc == p->crc_recv) {
                p->state = ST_DONE;
            } else {
                p->stat.err_crc++;
                fp_reset(p);
            }
        }
        break;

    case ST_DONE:
        if (ch == 0x55) { frame_deliver(p->payload, p->len); p->stat.ok++; }
        else            { p->stat.err_head++; }
        fp_reset(p);
        break;

    default:
        fp_reset(p);
        break;
    }
}

ST_CRC 里用 p->idx == p->len 判断「这是校验的第一个字节」，因为 idx 在 DATA 状态刚好停在 len 上。这种复用要写注释，否则半年后自己也看不懂。

状态一多，switch 会膨胀到几百行。改成表：一个函数指针数组，下标就是状态值，每项指向一个只处理一件事的小函数，加一种帧类型只加一个函数和一行表项。代价是间接调用开销，Cortex-M0 上多十几个周期，115200 下一个字节间隔 87 μs，够用。

写法 优点 缺点 适用
if/else if 链 无需函数指针，编译后紧凑 状态一多难读，增删易漏分支 状态数 ≤ 12
switch 分支清晰，编译期查重 单函数变长 状态数 ≤ 20
表驱动 每状态独立函数，好测好扩 间接调用开销 状态多、要复用
状态表数据化 状态机变成配置，可代码生成 抽象成本高 协议多、要生成

小项目用 switch，够用。状态数超过 15 再重构，别一上来就上表驱动。

4.4 一份实际项目的 12 状态实现 #

素材里的工程代码，UART1 协议解析，12 个状态全写在一个 if/else if 链里。协议格式：

text
[0xFF][0xEF][LEN][CRC][ACK][MODULE][ID][CMD][SUBCMD][DATA...][0xFE]
 包头2字节  长度 校验 应答 模块码 ID  命令 子命令   数据     包尾
状态 接收内容 校验规则
0 包头第 1 字节 必须 0xFF
1 包头第 2 字节 必须 0xEF；若是 0xFF 则留在本状态
2 长度 直接存
3 CRC 直接存
4 应答码 直接存
5 模块码 只接受 0x01/0x02/0x03
6 ID 码 必须 ≤ 0x0A
7 命令码 必须 ≤ 0x08
8 子命令码 按长度去 9 或去 11
9/10 数据内容 收满 FrameLen 后算 CRC
11 包尾 必须 0xFE 
c
/* 接收到的数据缓冲区首字节 */
rcvdat = RxBuffer1[0];

/* UART1 协议解析状态机 */
if (uart1_state_machine == 0) {
    /* 等待接收数据包的第一个字节 */
    if (rcvdat == 0xFF) {
        /* 接收到包头第一字节，移位到高位 */
        res_data.FrameHead |= rcvdat << 8;
        uart1_state_machine = 1;      /* 状态转移到接收包头第二字节 */
    } else {
        uart1_state_machine = 0;      /* 未接收到包头，保持当前状态 */
    }
} else if (uart1_state_machine == 1) {
    /* 接收数据包的第二个字节 */
    if (rcvdat == 0xEF) {
        /* 接收到完整包头，填充包头低位 */
        res_data.FrameHead |= rcvdat;
        uart1_state_machine = 2;      /* 状态转移到接收数据长度 */
    } else if (rcvdat == 0xFF) {
        /* 重新接收到包头第一字节，保持在当前状态 */
        uart1_state_machine = 1;
    } else {
        uart1_state_machine = 0;      /* 未接收到合法包头，复位状态机 */
    }
} else if (uart1_state_machine == 2) {
    /* 接收数据长度 */
    res_data.FrameLen = rcvdat;
    uart1_state_machine = 3;          /* 状态转移到接收 CRC */
} else if (uart1_state_machine == 3) {
    /* 接收 CRC 校验和 */
    res_data.FrameCRC = rcvdat;
    uart1_state_machine = 4;          /* 状态转移到接收应答码 */
} else if (uart1_state_machine == 4) {
    /* 接收应答码 / 读写码 */
    res_data.FrameACK = rcvdat;
    uart1_state_machine = 5;          /* 状态转移到接收模块码 */
} else if (uart1_state_machine == 5) {
    /* 接收模块码 */
    if (rcvdat == 0x01 || rcvdat == 0x02 || rcvdat == 0x03) {
        res_data.FrameModule = rcvdat;
        uart1_state_machine = 6;      /* 状态转移到接收 ID 码 */
    } else {
        uart1_state_machine = 0;      /* 无效模块码，复位状态机 */
    }
} else if (uart1_state_machine == 6) {
    /* 接收 ID 码 */
    if (rcvdat <= 0x0A) {
        res_data.FrameID = rcvdat;
        uart1_state_machine = 7;      /* 状态转移到接收命令码 */
    } else {
        uart1_state_machine = 0;      /* 无效 ID 码，复位状态机 */
    }
} else if (uart1_state_machine == 7) {
    /* 接收命令码 */
    if (rcvdat <= 0x08) {
        res_data.FrameCMD = rcvdat;
        uart1_state_machine = 8;      /* 状态转移到接收子命令码 */
    }
} else if (uart1_state_machine == 8) {
    /* 初始化数据长度计数器 */
    uart1_lencnt = 0;
    if (1) {
        /* 接收子命令码 */
        res_data.FrameSubCMD = rcvdat;
        if (res_data.FrameLen != 0) {
            /* 清除上次数据区内容 */
            memset(res_data.DataContent, 0x00, sizeof(res_data.DataContent));
            uart1_state_machine = 9;  /* 状态转移到接收数据内容 */
        } else {
            res_data.DataContent[0] = NULL;   /* 数据区为空 */
            uart1_state_machine = 11;         /* 转移到包尾处理 */
        }
    } else {
        uart1_state_machine = 0;  /* 无效子命令码，复位状态机 */
    }
} else if (uart1_state_machine == 9 || uart1_state_machine == 10) {
    /* 保存接收到的数据 */
    res_data.DataContent[uart1_lencnt++] = rcvdat;
    if (uart1_lencnt == res_data.FrameLen) {
        /* 计算 CRC 校验和 */
        __IO u8 crc1 = 0;
        crc1 = u8_CRC_Check(res_data.DataContent, res_data.FrameLen);
        if (crc1 == res_data.FrameCRC) {
            /* CRC 校验通过，转移到包尾处理 */
            uart1_state_machine = 11;
        } else {
            /* CRC 校验失败，复位状态机 */
            uart1_state_machine = 0;
        }
    } else {
        /* 继续接收数据 */
        uart1_state_machine = 10;
    }
} else if (uart1_state_machine == 11) {
    /* 接收包尾结束符 */
    if (rcvdat == 0xFE) {
        if (UART1_Rx_Done == 0) {
            uart1_len = 0;
        }
        res_data.FrameEnd = 0xFE;                  /* 设置包尾标志 */
        UART1_Rx_Done    = 0xAA;                   /* 标记接收完成 */
        UART1_RX_BUF[uart1_len] = res_data;        /* 保存数据包 */
        uart1_len += 1;                            /* 更新包计数 */
        memset(&res_data, 0x00, sizeof(res_data)); /* 清除结构体 */
    }
    uart1_state_machine = 0;               /* 复位状态机 */
}

四处值得学。状态 1 的自环：连续来两个 0xFF 时不退状态，留在状态 1 继续等 0xEF，比「错一个字节就回 IDLE」更抗帧头被干扰，等价于在两字节帧头上做了一次重叠匹配。状态 5、6、7 的域检查：模块码、ID 码、命令码都做范围校验，非法值立刻复位，这是「早期拒绝」，与其收完整帧再靠 CRC 判死刑，不如在字段层面砍掉明显不成立的候选。状态 8 的长度为零分支：FrameLen == 0 时直接跳状态 11 收包尾，避免死等。CRC 就地验证：收到最后一个数据字节就验，不等包尾。

反过来有三处可以优化。if (1) 是死代码，状态 8 里那个 else 永远走不到，说明作者想校验子命令码但没写完。状态 7 没有 else，命令码大于 0x08 时状态机既不复位也不迁移，停在 7，下个字节不管是什么都去覆盖 FrameCMD；状态 6 有 else、状态 7 没有，这种不对称是隐患。CRC 覆盖范围只有数据区，u8_CRC_Check(res_data.DataContent, res_data.FrameLen) 包头、长度、命令码都不参与，FrameLen 被干扰还能兜住，但 FrameSubCMD 被干扰完全查不出来。

素材里 Qt 版的处理函数是同一思路：切出整帧后先取结构体、算 CRC、再按消息 ID 分发。

cpp
void SerialPortDriver::slotDealFrame(QByteArray baPacket)
{
    do
    {
        MessageNode dFrame;
        MessageNode *fpNew = (MessageNode *)baPacket.data();
        dFrame = *fpNew;

        /* CRC 校验：失败应当 break 掉整帧 */
        quint8 scrc = CRC_CAL(baPacket);
        quint8 dcrc = dFrame.frameHeader.datacksum;
        if (dcrc != scrc) {
            printf("ERROR: CRC CAL FAILED!!!\n");
            break;
        }

        /* 按 payloadID 分发 */
        QString type = "none";
        switch (dFrame.frameHeader.payloadID) {
        case MSG_IRU: type = "iru"; break;
        case MSG_ADU: type = "adu"; break;
        case MSG_GPS: type = "gps"; break;
        }

        static int index = 0;
        QString outputStr = "[RecvMsg " + QString::number(index++) + " ] "
                + QDateTime::currentDateTime().toString("HH:mm:ss zzz")
                + " " + type;
        printf("%s\n", qPrintable(outputStr));

        emit sendBlockMsg(&dFrame);
    } while (0);
}

注意 (MessageNode *)baPacket.data() 这个裸转换：它假设 QByteArray 的内存布局和 MessageNode 完全一致，包括对齐和打包。结构体里有指针或编译器插了填充字节，这个转换就崩。上位机代码里这种写法常见，能跑就别动，但移植到 64 位或换编译器时第一个出事。

4.5 复位函数要清干净 #

漏清 crc_recv，上一帧的残值会和这一帧的高字节拼起来，CRC 随机对错，表现是「同一份数据，这次过下次不过」。所以复位函数要把 state、idx、len、crc_recv、crc_calc、payload、header 全部清掉。

素材那段代码在包尾处理里做了 memset(&res_data, 0x00, sizeof(res_data))，就是这个道理。它清的是整个结构体，包括 FrameHead——如果不清，下次 res_data.FrameHead |= rcvdat << 8 会和旧值或运算，包头值永远是对的，等于丢了这个字段的检查。

五、状态机的错误恢复 #

5.1 三类错误，三种处置 #

错误类型 例子 处置 记日志
可自愈 帧头前的垃圾字节 忽略，留在 IDLE 不记
需复位 帧头不对、长度非法、CRC 错 回 IDLE 等下一个帧头 计数
需上报 连续多帧 CRC 错、超时 计数 + 事件上报 计数 + 事件

第一类不能记。线上永远有噪声，每个垃圾字节记一条，日志会淹掉真问题。

5.2 CRC 错之后怎么重同步 #

直接回 IDLE、只认帧头，会让这一帧的剩余字节被逐个当垃圾丢弃。如果数据区里恰好有帧头字节序列，状态机会误入假帧，收满长度后 CRC 错再复位。这叫假同步，代价是白等一整帧。

有静默的场景，靠超时把剩余字节冲掉就行，下一帧自然对齐。没有静默的连续流式场景，得真回溯：读指针前移 1 字节重扫。

c
/* 环缓冲里找帧，返回帧长，0 表示还没有完整帧 */
u32 scan_frame(const u8 *buf, u32 n)
{
    for (u32 i = 0; i + 4 <= n; i++) {
        if (buf[i] != HEAD0 || buf[i + 1] != HEAD1) {
            continue;                        /* 滑动一格继续找 */
        }
        u8  len   = buf[i + 2];
        u32 total = 2 + 1 + len + 2 + 1;
        if (len == 0 || len > MAX_PAYLOAD) {
            continue;                        /* 长度非法，当它不是帧头 */
        }
        if (i + total > n) {
            return 0;                        /* 字节不够，等下一次 */
        }
        if (crc16_modbus(&buf[i + 3], len) !=
            (u16)(buf[i + 3 + len] | (buf[i + 3 + len + 1] << 8))) {
            continue;                        /* 校验不过，当它不是帧头 */
        }
        return total;
    }
    return 0;
}

所有判断塞进一个循环，continue 就是「这位置不像帧头，往后挪一格」，天然处理假同步和残帧。代价是最坏 O(n²)，串口一次几百字节，无所谓。

5.3 超时复位 #

任何状态停留过久就强制回 IDLE。

c
void fp_tick(frame_parser_t *p, u32 now_ms)
{
    if (p->state == ST_IDLE) {
        return;
    }
    if ((now_ms - p->last_byte_ms) >= p->timeout_ms) {
        p->stat.err_timeout++;
        fp_reset(p);
    }
}

timeout_ms 不小于 t3.5，不大于上层重发超时，Modbus 场景取 10 到 100 ms。没有这个超时，一次干扰就能让状态机永久卡在 ST_DATA，现场表现是「设备跑几小时后不响应，重启就好」。

5.4 丢帧计数器 #

至少要统计 rx_bytes（收到总字节）、frames_ok（完整且校验通过的帧）、err_head、err_len、err_crc、err_overflow、err_timeout、err_gap。排查时对着看：

现象 看哪个计数 结论
完全收不到帧 rx_bytes 为 0 物理层/波特率/接线，不是协议问题
rx_bytes 涨，frames_ok 不涨 err_head 高 帧头配错，或对端协议版本不同
err_crc 偶发 偶发即线路噪声 查屏蔽、共地、线长
err_crc 持续高 波特率偏差大，或校验算法不一致 示波器量位宽
err_len 高 长度字段被干扰，或长度语义理解错 对端拷一帧原始字节比对
err_overflow 高 主循环处理太慢，或缓冲太小 加大缓冲、降采样、拆业务
err_timeout 高 帧发到一半断了，或波特率不稳 查对端重启、供电

err_crc / frames_ok 是最有用的一个指标。正常链路在 1e-6 量级，超过 1e-3 就说明物理层有问题，别再改代码。

5.5 超时、长度上限、波特率三者联动 #

隐蔽错误：状态机在 ST_DATA 等 len 个字节，len 被干扰成 200，实际数据只有 8 字节。后面 192 个正常帧的字节全被吃进假帧，直到凑满 200 才验 CRC、失败、回 IDLE。这期间丢了十几帧。

防法两条都要有：长度上限检查治单次，超时复位治持续。只做长度检查不够，200 在合法范围内；只做超时也不够，超时阈值会比 200 字节的传输时间还长。

算一下：115200、200 字节、8N1，传输时间 = 200 × 10 ÷ 115200 ≈ 17.4 ms。所以超时必须小于这个数才不会丢帧，同时大于 t3.5（334 μs），取 5 ms 合适。9600 时 200 字节要 208 ms，超时得放到 300 ms 以上，或者把长度上限压到 32。改一个要重算另两个，这是串口参数配置的铁律。

六、环形接收缓冲区 #

6.1 为什么不用线性缓冲 #

线性缓冲的做法是收满一帧后 memmove 把剩余字节移到开头。问题在 memmove：中断里不能做（耗时不定），主循环里做也有代价——缓冲 1 KB、每帧 8 字节，每收一帧就要搬约 1 KB。115200 下每秒 11520 字节、1440 帧，一年搬约 500 GB，纯浪费。

环形缓冲把「移动数据」换成「移动指针」，收和取互不干扰。

text
       写指针 wr（中断里加）
            │
            v
   ┌───┬───┬───┬───┬───┬───┬───┬───┐
   │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │ 7 │ 8 │  buf[8]
   └───┴───┴───┴───┴───┴───┴───┴───┘
        ^
        │
       读指针 rd（主循环里加）

   wr 追上 rd → 满      rd 追上 wr → 空

只有一个指针时无法区分满和空。两种解法：留一格（容量 N 最多存 N-1 个，wr + 1 == rd 判满）；加计数（额外 count，但两个上下文都改它，8 位机上 count++ 不是原子操作会丢）。实践里用第一种更多。

6.2 代码 #

单生产者单消费者无锁版，靠「指针只由一方写」保证正确：

c
#define RB_SIZE 512                   /* 必须是 2 的幂 */

typedef struct {
    u8  buf[RB_SIZE];
    volatile u32 wr;                  /* 只由中断写 */
    volatile u32 rd;                  /* 只由主循环写 */
    volatile u32 overflow;
} ring_t;

static ring_t s_rb;

/* 中断里调 */
static inline int rb_put(ring_t *r, u8 ch)
{
    u32 next = (r->wr + 1) & (RB_SIZE - 1);
    if (next == r->rd) {              /* 满 */
        r->overflow++;
        return -1;
    }
    r->buf[r->wr] = ch;
    r->wr = next;
    return 0;
}

/* 主循环里调 */
static inline int rb_get(ring_t *r, u8 *ch)
{
    if (r->rd == r->wr) {             /* 空 */
        return -1;
    }
    *ch = r->buf[r->rd];
    r->rd = (r->rd + 1) & (RB_SIZE - 1);
    return 0;
}

static inline u32 rb_used(const ring_t *r)
{
    return (r->wr - r->rd) & (RB_SIZE - 1);
}

RB_SIZE 取 2 的幂，& (RB_SIZE - 1) 就是取模，比 % 快一个数量级（M0 没有硬件除法）。wr、rd 用无符号 u32，(wr - rd) 在回绕时自动正确，别改成有符号。

6.3 满了怎么办 #

策略 行为 适用
丢新字节 满了拒绝写入，计 overflow 帧必须完整，宁缺勿错
丢旧字节 覆盖最老的，读指针跟随 只关心最新数据
整帧丢弃 清空整个缓冲并复位状态机 有重传机制的协议

工业控制用第一种：丢一帧让上层重发。第二种用在只要最新值的场合，比如实时波形显示。第三种要小心：清空缓冲会让正在解析的帧断成两半，状态机必须同步复位，否则拿残帧去凑。

6.4 缓冲要多大 #

算出来，别拍脑袋。缓冲最小容量 = 主循环一次循环的最坏耗时 × 字节到达速率。

115200、8N1 → 11520 字节/秒；主循环最长一次耗时（处理一帧请求、写 Flash）20 ms → 需要 230 字节。留 2 倍余量，取 512。反过来验证：512 字节能扛 44 ms 的处理停顿。

printf 是个大坑：重定向到同一个串口时，一次 64 字节的 printf 在 115200 下要 5.5 ms。日志一多主循环就慢，RX 就溢出。要么关日志，要么换非阻塞的环形发送。

6.5 DMA + 空闲中断 #

MCU 有 DMA 和串口空闲中断（IDLE）时还可以走一步：DMA 把字节直接搬进内存，CPU 完全不参与；总线静默一个字符时间后触发 IDLE 中断，中断里算出「这次收了多少字节」，一次性交给处理逻辑。

c
/* STM32 风格，伪代码 */
void USART1_IRQHandler(void)
{
    if (USART_GetITStatus(USART1, USART_IT_IDLE) != RESET) {
        volatile u32 tmp = USART1->SR;
        tmp = USART1->DR;                     /* 清 IDLE：读 SR 再读 DR */
        (void)tmp;

        u32 total = RX_BUF_SIZE - DMA_GetCurrDataCounter(DMA1_Channel5);
        u32 last  = s_dma_last;

        if (total != last) {
            u32 n = (total > last) ? (total - last)
                                   : (RX_BUF_SIZE - last + total);
            frame_push_block(&s_dma_buf[last], n);   /* 只入队，不解析 */
            s_dma_last = total % RX_BUF_SIZE;
        }
    }
}

CPU 不碰每个字节，只在整块到达时动一次。代价是 DMA 环形缓冲也有回绕，last 到 total 是两段不连续内存。它和软件环不冲突：DMA 那块是硬件写的环，frame_push_block 往软件环里塞，两层各管一段。没有 IDLE 中断的 MCU 就逐字节中断 + 环形缓冲，115200 完全扛得住。

七、中断与主循环的分工 #

7.1 87 微秒意味着什么 #

115200、8N1，一个字节 10 位，一位 8.68 μs，一个字节 86.8 μs。意思是每 86.8 微秒必须把数据寄存器读走一次，否则下一个字节到达时覆盖标志位，这一字节就丢了（多数 MCU 只有 1 级硬件 FIFO）。

86.8 μs 在 72 MHz 的 Cortex-M3 上是 6250 个时钟周期，听着宽裕，但要减掉中断响应延迟（压栈 12 个寄存器约 12 到 20 周期）、更高优先级中断的抢占时间、Flash 等待周期。真正留给你在中断里干活的余量只有一两千周期。一次浮点 printf 就要上万周期，直接爆。

7.2 中断里只能做三件事 #

读数据寄存器、塞进环形缓冲、记时间戳清标志。多一件都不要。任何带循环、带查表、带内存分配的活全部推到主循环。

c
/* 正确：中断里只搬运 */
void USART1_IRQHandler(void)
{
    if (USART_GetITStatus(USART1, USART_IT_RXNE) != RESET) {
        u8 ch = (u8)USART_ReceiveData(USART1);
        rb_put(&s_rb, ch);              /* 微秒级 */
        s_last_byte_ms = get_tick_ms();
    }
}

c
/* 错误：中断里解析 + 业务 + 打印 */
void USART1_IRQHandler(void)
{
    u8 ch = (u8)USART_ReceiveData(USART1);
    fp_feed(&s_fp, ch);                       /* 几十个周期，勉强 */
    if (frame_ready(&s_fp)) {
        handle_business(&s_fp);               /* 几百微秒 */
        printf("frame ok, len=%d\n", ...);    /* 几毫秒，必然丢字节 */
    }
}

同一个中断源里打印还会死锁：printf 要通过 TX 发出，TX 缓冲满时它会阻塞等待，而 TX 中断优先级低于 RX，等不到。轻则丢字，重则卡死在中断里，看门狗复位。

7.3 主循环的写法 #

c
int main(void)
{
    uart_init(115200);
    fp_init(&s_fp);

    for (;;) {
        /* 1. 把环里的字节喂给状态机，一次最多 64 个 */
        u8  ch;
        u32 n = 0;
        while (n++ < 64 && rb_get(&s_rb, &ch) == 0) {
            fp_feed(&s_fp, ch);
        }

        /* 2. 状态机超时检查 */
        fp_tick(&s_fp, get_tick_ms());

        /* 3. 处理已完成的帧 */
        frame_t f;
        if (frame_queue_pop(&f) == 0) {
            business_handle(&f);
        }

        /* 4. 空闲任务：上报统计、喂狗 */
        idle_task();
    }
}

关键在 while (n++ < 64) 那个上限。没有它，一直有数据进来时主循环会卡在取数据上，其他任务饿死。加个上限，每轮处理一点，轮转得开。

帧队列长度取「最坏情况下主循环停顿时能到达的帧数」。主循环最长停 20 ms、帧率 100 帧/秒，就是 2 帧，取 4 或 8 够。队列满了照样丢，计 err_queue，这个计数非零就说明下游跟不上。

7.4 代价与临界区 #

逐字节中断在 1 Mbps 以上会吃掉大量 CPU（1 Mbps 下 8.7 μs 一次中断，几乎没空干别的）；环缓冲加状态机至少多几百字节 RAM；调试时不能单步进中断，得靠计数器。波特率超过 500 kbps 就该考虑 DMA，低于 115200 这套结构完全够用。

8 位机上 32 位指针变量读写要 4 条指令，中间会被打断，必须关中断保护：

c
u32 wr_snapshot(void)
{
    u32 v;
    cli();
    v = s_rb.wr;
    sei();
    return v;
}

32 位 MCU 上单次读写是原子的，不用管。但若有两个中断都往同一个环里写（UART1 和 UART2 共用一个），临界区就必须关中断。

八、校验与丢帧处理 #

8.1 校验是最后一道关 #

前面所有切帧工作靠的都是结构：帧头对不对、长度合不合法、帧尾到没到。结构对不等于内容对，一个比特翻转会让数据变了但结构没变。所以切出帧之后必须验校验。

校验 长度 能发现 不能发现 适用
奇偶校验 1 位（硬件） 单比特错 双比特错、整字节错位 UART 硬件层，很弱
累加和 1 字节 单字节错 两字节同增同减 短帧、资源极紧
CRC16 2 字节 绝大多数突发错 特定长度下的极小概率碰撞 工业协议标准
CRC32 4 字节 更强 — 大帧

Modbus RTU 用 CRC16：多项式 0x8005（反向 0xA001）、初值 0xFFFF。查表法一次一字节、占 512 字节 ROM；逐位法（每字节异或后循环 8 次，判最低位决定是否异或 0xA001）省下这张表但慢 8 倍，只有 2 KB RAM 的 MCU 上逐位反而合适。115200 下 8 字节帧逐位算约 2000 周期，占一个字节间隔（6250 周期）的三分之一，够用。

8.2 校验不过怎么办 #

丢掉整帧，不回退补。 CRC 错说明帧里有字节错了，但不知道是哪个，补不回来。

计数，但别刷日志。 每秒几千帧的系统里每次错打一行串口，日志本身就把串口占了。用计数器，定期上报。

连续错要能触发告警。 单次错是噪声，连续 10 次是配置错了或者线断了。

c
#define CRC_ERR_ALARM_CNT 10

void on_crc_error(void)
{
    s_stat.err_crc++;
    s_consecutive_crc_err++;
    if (s_consecutive_crc_err >= CRC_ERR_ALARM_CNT) {
        s_consecutive_crc_err = 0;
        link_set_state(LINK_BAD);
        event_post(EV_LINK_CRC_ALARM, s_stat.err_crc);
    }
}

void on_crc_ok(void)
{
    s_stat.frames_ok++;
    s_consecutive_crc_err = 0;            /* 这行最容易漏 */
    if (link_get_state() == LINK_BAD) {
        link_set_state(LINK_OK);
        event_post(EV_LINK_RECOVERED, 0);
    }
}

on_crc_ok 里清连续错计数这行漏了，累计错到 10 次就报警，即使中间有 100 万帧是好的。

8.3 校验范围与字节序 #

从帧头第一个字节算到数据区最后一个字节，全算。只算数据区的后果：包头、长度、命令码被干扰，CRC 依然过，命令码错了会导致执行错误的操作，比丢帧严重得多。素材那段代码只算了 DataContent，FrameSubCMD 或 FrameACK 被干扰查不出来，移植时应该改成从 FrameHead 开始算。

CRC 有四个参数：多项式、初值、输入是否反射、输出是否异或。任一不同结果就不同，写文档要写全，别只写「CRC16」。还有个坑：CRC16 的高字节在前还是低字节在前，Modbus 规定低字节在前：

c
buf[n++] = (u8)(crc & 0xFF);
buf[n++] = (u8)(crc >> 8);

很多实现写成大端，主机收不到响应还以为是超时。调不通时先查这个字节序，比查算法快得多。

8.4 丢帧之后要不要重发 #

周期性采集丢了就丢，下一帧自然会来；命令下发的确认要重发，带序号去重；固件升级传输必须重发，靠分块序号 + 整体校验；Modbus 请求响应靠主机超时重发，从机侧天然幂等。

带序号的协议要注意去重：序号等于上一帧就直接回 ACK 但不重复执行。隐含假设是序号不回绕太快——16 位序号在 1000 帧/秒下 65 秒回绕一次，回绕后恰好收到 65 秒前那个序号的帧会被误判重复，加时间窗或用 32 位序号能缓解。

8.5 完整处理链 #

text
硬件 RDR
   │ 中断，86.8 μs 内必须读走
   v
ring_put()          ── 满了记 err_overflow
   v
主循环 rb_get()     ── 每轮最多取 64 字节
   v
fp_feed()           ── 状态机逐字节推进，帧头/长度/超时错则复位计数
   v

   v

每一环都有独立的错误计数，出问题看哪个计数在涨就够了。

九、串口调试工具 #

9.1 串口工具和终端工具是两回事 #

串口工具 终端工具
收发方式 明确分开，点发送才发 敲一个字符发一个字符
典型用途 抓协议帧、发测试命令 登录设备命令行、看启动日志
例子 cutecom、SSCOM picocom、minicom、screen、PuTTY

同一个软件经常两头都干（PuTTY 既连 SSH 也连 COM 口），但你要清楚现在用的是哪种模式。用终端工具发二进制协议帧很别扭，它会把输入当键盘事件，Ctrl-C 直接被解释成中断信号。

9.2 picocom #

源码单文件，编译就一条 make，没有依赖。这是它比 minicom 好用的地方：交叉编译到 ARM 板子上，两个命令搞定。

bash
git clone https://github.com/npat-efault/picocom.git
cd picocom
make
strip picocom              # 瘦身，可选
sudo cp picocom /usr/bin/  # 装到系统路径，可选

板子上没 git 就把整个目录 scp 过去再 make。

bash
picocom -b 115200 -f h /dev/ttyS0

-b 波特率，-f h 流控（h 硬件 RTS/CTS，n 无流控，s 软件 XON/XOFF），最后是设备节点。交互键都是 Ctrl-A 起头：Ctrl-A Ctrl-X 退出，Ctrl-A Ctrl-Q 退出但不重置终端，Ctrl-A Ctrl-H 帮助，Ctrl-A Ctrl-F 设流控，Ctrl-A Ctrl-B 改波特率，Ctrl-A Ctrl-C 切本地回显。

退出一定用 Ctrl-A Ctrl-X。直接 Ctrl-C 杀不掉，终端会留在 raw 模式，之后敲命令全是乱码，真搞乱了执行 reset 回车。

-f h 值得单独说。板子跑高速率时不开硬件流控，主机侧稍微一卡，板子还在发，主机 FIFO 满了就丢字节。开 -f h 靠 RTS/CTS 握手能防丢，前提是线序里有这两根，很多三线串口（TX/RX/GND）没有。

9.3 minicom、screen、cutecom #

minicom 老牌，功能全，菜单驱动，sudo minicom -s 进配置，minicom -D /dev/ttyUSB0 -b 115200 直接用指定参数启动。能存配置、能录日志（-C file），做长期抓包比手动复制强。配置菜单难用，每项都要 Ctrl-A Z 记一遍。

screen 严格说不算串口工具，但几乎所有 Linux 都自带，拿来做串口监视很方便：

bash
screen /dev/ttyUSB0 115200,cs8,-parenb,-cstopb,-crtscts

退出 Ctrl-A 然后 k 再 y，或者 Ctrl-A d 挂后台、screen -r 恢复。好处是能挂后台，坏处是不好发二进制、参数串难记。

cutecom 是 Linux 下的图形串口工具，sudo apt install cutecom 就能装，能同时看 HEX 和 ASCII、能定时发送，做协议调试比命令行直观。缺点是依赖 Qt，没桌面的板子上跑不起来。

9.4 PuTTY #

Windows 上的默认选择，也支持 Linux。在线装 sudo apt install putty。内网离线环境只能自己编，从 0.77 起官方改用 CMake 构建，0.78 起加了 GitHub Actions 的在线编译脚本：

bash
tar xvf putty-0.78.tar.gz
cd putty-0.78
cmake .
cmake --build .
sudo cmake --build . --target install

cmake . 会检查依赖（GTK、X11），纯串口用途下缺依赖也能编。用法在 Connection → Serial 填 Serial line（COM3 或 /dev/ttyUSB0）、Speed（115200）、Connection type（Serial），Session 里存个配置名下次直接点。日志在 Session → Logging → All session output，抓协议帧必开。

有个坑：PuTTY 的串口模式默认 Flow control 是 XON/XOFF。连嵌入式板子会出问题——板子输出的二进制数据里出现 0x11（XOFF），主机会暂停接收，看起来像「收到一半卡住」。改成 None 或 RTS/CTS。

9.5 横向对比与排错顺序 #

工具 平台 二进制收发 日志 依赖 适合
picocom Linux 一般 无 无 板子上快速连一下
minicom Linux 弱 有 ncurses 长期抓包、老设备
screen Linux 差 无 无 临时看一眼启动日志
PuTTY Win/Linux 中 有 GTK（Linux） Windows 主力、存配置
cutecom Linux 好 有 Qt 桌面调试协议帧
SSCOM Windows 好 有 无 国内常用，带校验计算

抓启动日志用 screen 或 picocom 最快；调协议帧用 cutecom 或 SSCOM；要留证据用 minicom -C 或 PuTTY 日志；要在板子上跑，只有 picocom 和 screen 靠得住。调协议一定要能看 HEX——纯 ASCII 下 0x0D 0x0A 和 0x0A 看起来差不多，帧头 0xAA 显示成乱码方块。

排错别一上来就怀疑代码，按顺序走：先用示波器或逻辑分析仪确认 TX 线上有波形；再量一位宽度确认波特率（115200 应该是 8.68 μs）；然后在中断里翻转 GPIO，看字节是否到达；接着把收到的字节打成十六进制和逻辑分析仪比对；再接状态机，打印 state 迁移和 err_*；最后单独拿一帧固定数据算 CRC。

GPIO 那步是分水岭。没脉冲就是硬件或配置问题，改代码无用；有脉冲但内容错，是波特率或帧格式（数据位/校验位/停止位）不匹配。

十、虚拟串口与无硬件调试 #

10.1 Linux：socat #

bash
socat -d -d pty,raw,echo=0 pty,raw,echo=0

输出里会打两个设备节点 /dev/pts/3、/dev/pts/4，往一个写，另一个就能读到。raw,echo=0 两个参数都不能省：raw 关掉行规程（不然 0x0D 被转成 0x0A、0x11 被当 XOFF），echo=0 关回显。

/dev/pts/N 编号每次不同，脚本里不好用，用 link 选项固定：

bash
socat -d -d pty,raw,echo=0,link=/tmp/ttyV0 pty,raw,echo=0,link=/tmp/ttyV1

串口转 TCP 也很直接，socat -d -d pty,raw,echo=0,link=/tmp/ttyV0 tcp-listen:9000,reuseaddr，用 telnet 或 nc 连 9000 端口就能和串口程序对话。

限制：socat 造的是 PTY，不是真串口。没有波特率、没有流控、没有 break 信号。依赖 TIOCMGET/TIOCMSET 读 DCD/DSR 的代码在 PTY 上拿不到真值，专门测流控或 modem 信号得上真硬件。

10.2 Windows：VSPD、com0com、USR-VCOM、VSPE #

Virtual Serial Port Driver 是商业产品，图形界面点几下就有一对虚拟串口。功能里有几项真用得到：端口分流（一个物理串口被多个程序同时读）、端口合并（多个串口汇到一个）、捆绑（虚拟口绑到网络端点）、信号仿真（RS232/422/485 的 DTR/DSR/RTS/CTS 都能设）。RS485 方向控制靠 RTS 翻转，纯软件模拟不好测，信号仿真能覆盖一部分。官网 https://www.eltima.com/products/vspdxp/

com0com 开源免费（GPL），命令行配置，能建任意多对虚拟串口。Windows 11 上官方安装器有时装不上，社区做法是先用 7-Zip 解开安装包，再以管理员身份运行里面的 64 位安装程序。装完有个常见故障：设备管理器能看到端口，一打开就报「端口不可用」或「拒绝访问」，多为驱动签名或端口号冲突，参考 https://www.rozenek.com/com0com-problem-with-com-cnca0/ 。配置用 setupc install PortName=COM# PortName=COM#，# 是占位符，自动分配空闲端口号。

USR-VCOM 主打网络转串口，把 TCP/UDP 映射成本机虚拟串口，Server/Client/UDP 广播几种模式，适合把远程串口设备当本地 COM 口用，不擅长造本地一对虚拟串口。VSPE 图形化配置，能建串口对也能做端口分流，有脚本接口，对 VMware/VirtualBox 兼容性好，虚拟机里的程序能访问宿主机虚拟串口。

10.3 能测什么、不能测什么 #

能测 不能测
协议切帧逻辑 真实波特率下的时序
状态机状态迁移 字节间隔、t3.5 超时
上位机 UI 流程 硬件流控、丢字节
收发数据内容比对 电气特性、噪声导致错帧
异常帧注入 上电瞬间的电平抖动

关键：PTY 和 VSPD 都不保证时间特性。测超时切帧时往 PTY 写 8 个字节再停，读端看到的是「8 个字节一起到」，字符间隔约等于 0，t3.5 逻辑永远走不到超时分支。要测就在应用层人为加延迟：

python
import os, time

fd = os.open("/tmp/ttyV0", os.O_RDWR)
for b in bytes([0x01, 0x03, 0x00, 0x00, 0x00, 0x0A, 0xC5, 0xCD]):
    os.write(fd, bytes([b]))
    time.sleep(0.002)          # 2 ms，小于 9600 下的 t3.5(4ms)
time.sleep(0.05)               # 静默 50 ms，触发超时切帧

time.sleep 的精度受调度影响，微秒级测不了，毫秒级够用。

10.4 用虚拟串口注入异常 #

真硬件上很难造的错误，脚本里一行就行。往虚拟口依次塞正常帧、CRC 错帧、长度被打大的帧、帧头断掉的帧、纯垃圾，看 err_crc、err_len、err_head 是否按预期涨，状态机有没有卡死。这比等现场出问题快得多。

python
def send(b):
    os.write(fd, bytes(b))

send([0xAA, 0x55, 0x04, 0x01, 0x02, 0x03, 0x04, 0x00, 0x00, 0x55])  # 正常
send([0xAA, 0x55, 0x04, 0x01, 0x02, 0x03, 0x04, 0xFF, 0xFF, 0x55])  # CRC 错
send([0xAA, 0x55, 0xFF, 0x01, 0x02])                                # 长度过大
send([0xAA, 0x00, 0x00, 0xAA, 0x55, 0x01, 0xAA])                    # 帧头断裂
send([0x00] * 32)                                                    # 纯垃圾

再走一步：写脚本当假从机，收到请求就按功能码回固定响应，把上位机接在另一头，没有硬件也能跑通全流程。

十一、CH34x 等 USB 转串口驱动 #

11.1 先确认设备有没有被识别 #

bash
lsusb

正常会看到 Bus 001 Device 005: ID 1a86:7523 QinHeng Electronics CH340 serial converter。1a86 是厂商 ID（沁恒 WCH），7523 是产品 ID（CH340）。看到这行说明 USB 层通了，问题在驱动或权限层；看不到说明线坏了、口坏了，或内核 USB 子系统有问题（dmesg | tail 看枚举日志）。CH341 的 ID 是 1a86:5523，驱动不是同一个。

然后看驱动有没有加载出 tty 节点：

bash
ls /dev/ttyUSB*
ls -l /dev/serial/by-id/     # 拔插后编号会变，脚本里用这个更稳

11.2 节点不存在：先查被谁占了 #

一个实际遇到过的情况：lsusb 看到了设备，ls /dev/ttyUSB* 却报文件不存在。查 dmesg | grep tty 会看到驱动加载成功、创建了 ttyUSB0，然后马上被某个进程打开。再 dmesg | grep -i brltty 就发现占位的是它。

brltty 是给盲人提供 Linux 控制台访问的后台守护进程，用可刷新盲文显示。它为了探测盲文终端会去抢 USB 串口设备，包括 CH340。这在服务器和开发机上很常见，症状诡异：设备在、节点也有，就是打不开或被打断。

bash
sudo apt remove brltty

不想卸就只禁用服务（服务名随发行版不同，先 systemctl list-unit-files | grep brltty 确认）：

bash
sudo systemctl mask brltty.service
sudo systemctl mask brltty-udev.service

11.3 权限 #

bash
sudo chmod a+rw /dev/ttyUSB0

拔插后设备节点重建，权限失效。永久生效加 udev 规则：

text
KERNEL=="ttyUSB[0-9]*", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", MODE="0666"

bash
sudo udevadm control --reload-rules
sudo udevadm trigger

更稳妥的是把用户加进 dialout 组（Debian/Ubuntu）或 uucp 组（Arch），重新登录生效：sudo usermod -aG dialout $USER。

11.4 三条重装路径 #

装 linux-modules-extra。 Ubuntu 把很多不常用模块剥离到单独的包，缺 ch341 先试这条：

bash
sudo apt install linux-modules-extra-$(uname -r)
sudo modprobe ch341
lsmod | grep ch341
dmesg | grep ch341

从官方源码单独编译。 仓库 https://github.com/WCHSoftGroup/ch341ser_linux ，解压后进 driver 目录：

bash
make
sudo make load           # 动态加载，重启失效
sudo insmod ch341.ko     # 同上
sudo make install        # 装进系统模块目录，重启不失效
sudo make unload         # 卸载
sudo rmmod ch341
sudo make uninstall

两个常见失败。一是 make 报编译错，多为 ch34x.c 和内核版本 API 不匹配，uname -r 看版本，去 https://elixir.bootlin.com/linux/latest/source 找对应版本的 drivers/usb/serial/ch341.c，替换后重编。二是 insmod 报 Invalid module format 或 Unknown symbol，查 /lib/modules/$(uname -r)/kernel/drivers/usb/serial/ 是否已有旧 ko，把新编的拷进去覆盖，再 depmod -a。

在内核源码树里编。 配置符号是 USB_SERIAL_CH341，位置在 drivers/usb/serial/Kconfig：

text
drivers/usb/serial/Kconfig:config USB_SERIAL_CH341
drivers/usb/serial/Kconfig:	tristate "USB CH341 single port serial driver"

tristate 表示可以编成 M（模块）或 *（内联）。菜单路径：

text
Device Drivers  --->
    [*] USB support  --->
        <*> USB Serial Converter support  --->
            <*> USB CH341 single port serial driver

或者直接改 .config 写 CONFIG_USB_SERIAL_CH341=m，然后 make、make modules、sudo make modules_install、sudo modprobe ch341、lsmod | grep ch341。

11.5 交叉编译一个 ARM64 的 ko #

给 ARM64 板子（比如 4.19.206 内核）编模块，关键是指定架构和内核源码路径：

bash
export ARCH=arm64
export CROSS_COMPILE=aarch64-linux-gnu-
make -C /path/to/kernel-source M=drivers/usb/serial modules

用 file ch341.ko 确认架构，应该显示 ELF 64-bit LSB relocatable, ARM aarch64；显示 x86-64 就是交叉编译器没生效。拷到板子上后 depmod -a、modprobe ch341、lsmod | grep ch341。

编译时的内核版本必须和板子上跑的完全一致（uname -r 对比）。差一点就加载不了，报 version magic 不匹配。所以要么用板子厂商提供的源码树，要么 --force-vermagic 硬加载（危险，结构体布局变了会崩）。

三个前置检查一次做完：芯片是 CH341 还是 PL2303（驱动不同）；ch341.c 的 usb_device_id 表是否包含你的 VID/PID；板子内核里是否已经内置了 ch341。

11.6 开机自动加载 #

/etc/modules 最简单，末尾加模块名（不带路径、不带 .ko），比如 ch341。

modprobe 配置适合 ko 不在标准模块目录的情况，在 /etc/modprobe.d/ch341.conf 写：

text
install ch341 /sbin/insmod /path/to/ch341.ko

/etc/rc.local 在 exit 0 之前加 sudo insmod /path/to/your/module.ko，注意 rc.local 需要可执行权限，新发行版默认没启用这个机制。

systemd 服务方式：

text
[Unit]
Description=Load custom kernel module

[Service]
Type=oneshot
ExecStart=/sbin/insmod /path/to/your/module.ko
ExecStop=/sbin/rmmod your_module_name
RemainAfterExit=true

[Install]
WantedBy=multi-user.target

RemainAfterExit=true 是关键。没有它，oneshot 服务执行完就被判为 inactive，ExecStop 也不会在关机时跑。优先用 /etc/modules，ko 不在标准路径才用 systemd 或 modprobe 配置。

芯片 驱动模块 备注

十二、易错点速查 #

# 易错点 症状 处置
1 中断里做解析和打印 偶发丢字节，重启正常 中断只搬字节，解析放主循环
2 没有超时复位 跑几小时后不响应 加 t3.5 或固定超时
3 缓冲不满就判帧结束 长帧被切成两段 按长度或结束符判
4 只读一次就解析 半帧被丢 循环读到取不出为止，加单轮上限
5 长度字段无上限检查 干扰后死等 255 字节，吞后续帧 len == 0 || len > MAX 立刻复位
6 CRC 只算数据区 命令码被干扰查不出 从帧头算到数据区末尾
7 CRC 字节序反了 从机不响应，主机报超时 Modbus 是低字节先发
8 复位函数漏清字段 同一帧这次过下次不过 memset 整个结构体
9 修复位不带清连续错计数 累计错到阈值就误报警 CRC 通过时清零
10 环形缓冲无溢出计数 丢数据但不知道丢了多少 加 overflow 计数并上报
11 RB_SIZE 不是 2 的幂 取模慢，或索引算错 必须 2 的幂，用 & (N-1)
12 波特率改了没改超时阈值 9600 通、115200 全错 阈值随波特率重算
13 字符时间按 10 位算成 11 位 阈值偏大，响应慢 按实际数据位/校验位/停止位算
14 单字节帧头不转义 数据含 0xAA 时帧被切错 转义或换多字节帧头
15 帧间静默不足 主机连发两帧，从机当一帧 主机侧守 3.5 字符间隔
16 printf 重定向到同一串口 打印时 RX 溢出 换非阻塞发送，或降日志量
17 串口工具用 ASCII 模式看帧 帧头显示成方块，无法比对 切 HEX 显示
18 PuTTY 默认 XON/XOFF 流控 收到 0x11 后卡住 改 None 或 RTS/CTS
19 brltty 抢占 ttyUSB 设备在，节点不出来 卸掉或 mask 服务
20 /dev/ttyUSB0 编号会变 脚本重启后连错口 用 /dev/serial/by-id/
21 交叉编译的 ko 版本不匹配 version magic 错误 用板子同版本内核源码树
22 PTY 上测超时切帧 超时分支永远走不到 应用层加 sleep 造间隔
23 帧队列满不计数 下游慢但看不出来 加 err_queue
24 状态机某状态没有 else 分支 非法字节导致状态卡死 每个状态都要有兜底迁移

最该先看第 1、2、3 条。这三条占了实际项目里串口收包问题的多数，共同点是「实验室不复现、现场天天出」，都跟时序和负载有关。

排查这类问题有个通用手段：在中断入口和主循环入口各翻转一个空闲 GPIO，用逻辑分析仪一起看。中断脉冲密集但主循环脉冲稀疏，说明主循环跟不上；中断脉冲本身就缺失，说明硬件层在丢字节。两条波形一叠，问题定位到哪一层一目了然，比读代码猜快得多。

串口收包这件事说到底是两句话：中断里只搬字节，主循环里按状态机慢慢切。把这两句落实，剩下的都是细节。
