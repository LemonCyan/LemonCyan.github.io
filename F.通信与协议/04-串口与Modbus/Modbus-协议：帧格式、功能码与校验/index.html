这篇只讲 Modbus 协议本身：帧长什么样、功能码有哪几个、校验怎么算。

讲什么：Modbus 的设计定位、三种传输模式（RTU / ASCII / TCP）的帧结构差异、RTU 靠静默时间切帧的机制、四张数据表、完整功能码与读写请求响应的字节级示例、异常响应、CRC16 与 LRC 的 C 实现、一主多从的寻址与轮询。

一句话把主线钉住：Modbus 是一个一问一答的寄存器读写协议。主站发一帧「读某个地址开始的 N 个寄存器」，从站回一帧带数据的响应。所有数据都映射到四张表的地址空间里，协议本身不关心这些地址背后接的是温度探头还是继电器。

带问题来的，直接跳到第十二章「易错点速查」，那张表按现象反查原因。想弄明白帧是怎么拼出来的，从第三章开始读。

一、Modbus 是什么 #

1.1 出身 #

Modbus 在 1979 年由 Modicon 公司提出，用来让可编程逻辑控制器（PLC）跟现场设备说话。Modicon 后来并入施耐德电气，协议本身则被公开出去，谁都能实现，不收授权费。这一步放得很开，是它铺到整个工业现场的前提。

它的目标场景是 SCADA——监控与数据采集。一个上位机要盯几十上百个点：液位、温度、阀门开关、电机启停。这些点的共性是「值不大、要得勤、不能出错」。Modbus 就是照这个需求裁出来的。

1.2 本质：一问一答的寄存器读写 #

把这个协议拆到最小，只剩两件事。

主站发请求，从站回响应。 请求里装三样东西——从站地址、要干什么（功能码）、在哪个地址上干多少。响应里装两样——功能码（正常时原样回，出错时改一位）、以及数据或确认。

整个协议没有「从站主动上报」这回事。从站不会自己开口，只在被点到名的时候答一句。这条规则决定了后面的一切：轮询必须串行，实时性靠主站的轮询周期撑，总线冲突靠地址隔离。

再看数据模型，也是一句话：

所有东西都落到四张表的地址空间里。 表里存的是位（0/1）或者 16 位整数。协议不知道也不问你这些数是什么含义。地址 0x0000 上挂的是温度还是压力、值 250 代表 25.0 ℃ 还是 250 rpm，全在协议之外，靠双方的约定文档（点表）对齐。

这个「地址抽象」是它活到今天的根本原因。协议只规定搬运方式，不规定搬运内容，于是任何设备都能挂上来——只要它肯把自己的状态摊成一张寄存器表。

1.3 主要特点 #

开放且简单。协议文本不长，实现一个最小可用版本不需要复杂的状态机。用串口助手手工拼一帧能让设备动起来，这是很多现场工程师入门的第一步。低门槛换来的是大量厂商愿意把它做进固件。

设备互操作性。不同厂家的设备能挂在同一条总线上，主站软件不用为每家写一套驱动。这条特性对工程项目的意义在于采购自由，不必被单一供应商锁死。

实时通信。协议本身是确定性的：一问一答、长度固定、没有协商、没有重传窗口。主站算得出一次轮询要花多少时间，也就算得出最坏情况下的响应延迟。制造过程和监控系统需要这种可预算的行为。

低开销。一帧请求最短 8 个字节（地址 1 + 功能码 1 + 数据 4 + CRC 2），读回一个寄存器的响应也只有 7 个字节。带宽、CPU、内存占用都很小，8 位单片机能跑，一条 9600 的串口线能带几十个点。

1.4 先看一帧 #

主站要读从站 1 的保持寄存器，从地址 0 开始读 10 个：

text
01 03 00 00 00 0A C5 CD

七个字节：从站地址 01、功能码 03（读保持寄存器）、起始地址 00 00、数量 00 0A（10 个）、CRC16 C5 CD（低字节在前）。从站回来的响应在 7.3 节逐段拆。这就是全部的交互逻辑，剩下的章节都是在这个骨架上长细节。

二、三种传输模式 #

同一套功能码和数据模型，可以跑在三种完全不同的「信封」里。这就是传输模式。三者的帧结构完全不同，不能混用。

把这句话讲透一点：如果设备配的是 RTU，你按 ASCII 的格式发 :01030000000AF2 过去，设备收到的是 3A 30 31 30 33 ... 这串字节，它会当成地址 0x3A（58）、功能码 0x30（48）来解析，然后判定地址不匹配，直接沉默。它不会报错，因为它根本没认出这是一帧。

2.1 Modbus RTU #

串口上最常用的模式，二进制编码，紧凑。

  • 通信方式：串行接口，RS-232 或 RS-485，后者做多点总线
  • 数据编码：二进制，一个字节就是一个字节，不做任何转写
  • 帧定界：靠时间，帧与帧之间要有 3.5 个字符时间的静默
  • 校验：CRC16，2 字节，小端放帧尾
  • 地址：1~247，0 是广播
text
| 地址 (1 字节) | 功能码 (1 字节) | 数据 (N 字节) | CRC16 (2 字节) |

数据段里装什么由功能码决定：起始地址、数量、字节数、具体的寄存器值。CRC16 覆盖从地址到数据末尾的全部字节，校验不通过则从站丢弃整帧，不作任何回应。

RTU 的优点是效率。同样读 10 个寄存器，RTU 请求 8 字节，ASCII 请求要 17 个字符。在 9600 的线上，这差别是实打实的。资源受限的嵌入式系统、中小型工业现场，RTU 是默认选择。

2.2 Modbus ASCII #

文本模式，每个字节用两个可打印的 ASCII 字符表示。

  • 通信方式：串行接口，RS-232 或 RS-485
  • 数据编码：ASCII，字节 0x01 写成字符 0 和 1，也就是 30 31
  • 帧定界：靠显式字符，冒号 : 开头，回车换行 CR LF 结尾
  • 校验：LRC，1 字节二进制补码，2 个 ASCII 字符
  • 地址：1~247
text
| 起始 ':' | 地址 (2 字符) | 功能码 (2 字符) | 数据 (n 字符) | LRC (2 字符) | 结束 CRLF |

这个模式的价值只有一个：人能直接看懂。拿个串口助手打开，屏幕上会出现这样一行：

text
:01030000000AF2

一眼能读出「发给 1 号站，读保持寄存器，从 0 开始读 10 个」。抓不到逻辑分析仪、手上只有一台笔记本的时候，这个可读性值钱。代价是效率，每个字节翻倍成两个字符，帧头帧尾还要吃掉 3 个字符。协议规范给 ASCII 留的速率上限是 19200，再高就不划算。

2.3 Modbus TCP #

跑在以太网上的 Modbus，用 TCP/IP 栈传输。

  • 通信方式：以太网，TCP 连接，默认端口 502
  • 数据编码：二进制，跟 RTU 的数据段一致
  • 帧定界：靠 MBAP 头里的长度字段，TCP 自己管字节流边界
  • 校验：没有。CRC 和 LRC 都不带，靠 TCP 的校验和与重传保证完整性
  • 寻址：IP 地址标识设备，不再受 1~247 的限制

它在原来的 PDU 前面套了一个 7 字节的 MBAP 头：

text
| 事务标识 (2 字节) | 协议标识 (2 字节) | 长度 (2 字节) | 单元标识 (1 字节) | 功能码 (1 字节) | 数据 (n 字节) |
  • 事务标识：主站自己编号，响应里原样带回。因为有它，TCP 上可以同时挂多个未完成的请求，靠这个号配对。这是 TCP 比 RTU 宽松的地方。
  • 协议标识：Modbus 固定为 0x0000。别的值说明这不是 Modbus。
  • 长度：从单元标识到数据末尾的字节数。
  • 单元标识：网关场景下用来指明后面挂的是哪个串口从站。直连设备时填 0xFF 或 0x01 都行，设备多半不检查。

因为不用算 CRC，TCP 帧拼起来比 RTU 省事。也因为没有帧间隔的概念，TCP 上不存在「3.5 字符静默」这回事——那是串口独有的约束。

2.4 Modbus Plus #

施耐德的一条历史分支，老系统里能碰到。它走专有的令牌环（Token Passing）网络，专用双绞线，速率固定 1 Mbps，最多 64 个节点，按节点号寻址；全双工，可同时处理多个请求和响应。帧格式为令牌环优化，包含节点寻址、令牌管理和数据段。它把传统 Modbus 的功能码和数据结构封装在自己的帧里，所以上层点表能复用，下层物理层和链路层全是专有的，要专用硬件卡。### 2.5 四种模式横向对比

2.6 选型的实际考虑 #

新项目、要接 PLC 和仪表，走 RTU。芯片自带 UART，加一片 RS485 收发器就能跑，物料成本和代码量都最低。现场调试、怀疑帧拼错了、又没有分析仪，临时切到 ASCII 手工看两帧，看完切回去。上位机软件、要连几十台设备、还要跨网段，走 TCP，一台服务器开几百个连接不成问题，不用担心总线争用和终端电阻。

串口转以太网的网关会同时涉及两种：对外一面是 TCP，对内一面是 RTU。这时候 MBAP 头里的单元标识才有真正的用处——它告诉网关，这帧该转发给挂在它下面的哪一号从站。

三、RTU 的帧结构 #

3.1 四个字段逐个数 #

text
| 地址 (1 字节) | 功能码 (1 字节) | 数据 (N 字节) | CRC16 (2 字节) |

地址：1~247 是单播，0 是广播。从站只处理地址等于自己的帧和地址为 0 的帧，别的直接丢，不吭声。

功能码：决定这一帧要做什么。请求里它是「我要读」，响应里原样回来表示「我读到了」；从站出错时它会被改成「功能码 | 0x80」，第九章单独讲。

数据：长度和内容由功能码决定。读操作里装起始地址和数量，写操作里装地址和要写的值，响应里装字节数和实际数据。

CRC16：覆盖前面所有字节，2 字节，低字节先发。第十章展开，它是实现里最容易翻车的地方。

整帧长度有上限：RTU 的 ADU 最长 256 字节，去掉地址、功能码、CRC 之后，PDU（数据段）最长 253 字节。这是规范给的上限，实际设备往往卡得更紧。

3.2 靠静默时间切帧 #

这一节是 RTU 的命门。

RTU 帧里没有帧头、没有帧尾、没有长度字段。接收方怎么知道一帧从哪开始、到哪结束？靠时间。规则两条：

  • 帧与帧之间，总线上要有 3.5 个字符时间的静默（规范里叫 t3.5）
  • 一帧内部的字符间隔，不能超过 1.5 个字符时间

这是隐式边界，不是显式帧头。 接收方看到总线安静了 3.5 个字符时间，就认定「上一帧结束了，后面要是再来字节，那是新的一帧」。收到第一个字节就开始计时，字节之间一旦静默超过 1.5 字符时间，它认为这一帧断掉了，把已经收到的半截丢掉，等下一帧。

所以 RTU 的帧定界是一个纯软件的超时判断。UART 硬件只负责把字节搬进缓冲区，切帧的活儿在定时器里。

3.3 一个字符占多长时间 #

要算这个时间，得知道一个字符有多少位。8 位数据、无校验、1 位停止位时是 10 位（1 起始 + 8 数据 + 0 校验 + 1 停止）；8 位数据、偶校验、1 位停止位时是 11 位。每个位的时长就是 1 / 波特率。按 11 位算，9600 波特下位时间约 104.17 µs，字符时间约 1145.8 µs，t1.5 约 1718.8 µs，t3.5 约 4010.4 µs——帧后要静默约 4 ms 才算一帧结束。

3.4 波特率变了，时间也变 #

这是最需要刻在脑子里的一句话：3.5 字符时间不是一个固定值，它随波特率变。

3.5 切帧失败与适配器的坑 #

  • 收到半帧就断：帧内字符间隔被拉长到超过 1.5 字符时间。多半是发送端拼帧时中间插入了别的活，或被高优先级中断打断。
  • 两帧粘成一帧：帧间静默不到 3.5 字符时间。发送端连续发两帧没留空隙，接收端会把它们当成一帧，长度对不上。
  • 整帧收不到：波特率、数据位、校验、停止位不匹配。这不是切帧问题，是串口参数问题，去看串口基础那篇。
  • 偶发丢帧只在开了调试输出时出现：串口打印占用了发送通道，把应答延迟推过了主站的超时窗口。

用 USB 转 485 的适配器调试 RTU，很容易觉得「协议有毛病」。适配器内部有缓冲，芯片不急着把收到的字节交给驱动，而是攒一批再交，等一个叫 latency timer 的定时器到期，默认值在不少驱动里是 16 ms。后果有两个：收到的一帧被切碎，因为字节是一批批送上来的；发出去的帧被打散，驱动按自己的节奏推字节，帧内间隔被拉长。

解决办法是把 latency timer 调到 1 ms，Windows 上在设备管理器 → 端口属性 → 高级里改。另外别在调试时开大量串口打印。

四、ASCII 与 TCP 的帧结构 #

4.1 ASCII 的字符级构成 #

一个字节拆成两个 ASCII 字符，高 4 位一个、低 4 位一个，各映射成一个可打印字符。字节 0x01 变成字符 0（0x30）和 1（0x31）；字节 0xFF 变成字符 F（0x46）和 F。

所以 ASCII 帧的可打印部分长度恒为偶数：地址 2 字符、功能码 2 字符、数据段每字节 2 字符、LRC 2 字符。

拿「读从站 1 的保持寄存器，从 0 开始读 10 个」举例：

text
:01030000000AF2
片段 内容 含义
: 3A 起始符
01 地址 1 从站 1
03 功能码 读保持寄存器
0000 起始地址 0
000A 数量 10
F2 LRC 校验
CR LF 0D 0A 结束符

LRC 的算法在第十章。这里先给结论：01 03 00 00 00 0A 六个字节相加得 0x0E，取二进制补码得 0xF2，写成字符就是 F2。

4.2 ASCII 的定界与超时 #

  • 收到 : 就开始新的一帧，之前缓冲里的东西全丢
  • 收到 CR LF 就认为一帧结束
  • 一帧内部字符之间的间隔不能超过 1 秒（规范给的值），超过则这一帧作废

最后一条要注意：ASCII 的超时按「秒」算，不是按「字符时间」算。这是它比 RTU 宽容的地方，也是它慢的原因——宽容的代价是它必须等这么久才能判死一帧。

4.3 TCP 的 MBAP 头 #

text
| 事务标识 (2 字节) | 协议标识 (2 字节) | 长度 (2 字节) | 单元标识 (1 字节) |

这 7 个字节叫 MBAP 头（Modbus Application Protocol header），后面直接跟 PDU。

事务标识的用处是配对：TCP 上一个连接里可以同时挂好几个未完成的请求，谁先回来不重要，按号认领就行。这跟 RTU 的一问一答完全不同——RTU 上你要是并发发两帧，回来的数据你分不清谁是谁。

长度字段从单元标识开始计数，一直到数据末尾。它同时承担两个职责：告诉对方这一帧有多少字节，以及配合 TCP 的字节流把帧切开。TCP 没有消息边界，这个长度字段就是边界。

单元标识在直连设备时没什么用，填 0xFF 或从站地址都行。它的真正战场是网关：一台串口服务器后面挂着 8 个 RTU 从站，主站发 TCP 帧时把单元标识填成目标从站号，网关照着转发。

4.4 同一个读操作的三种写法 #

都是读从站 1 的保持寄存器，从地址 0 读 10 个。

text
RTU   (8 字节):  01 03 00 00 00 0A C5 CD
ASCII (17 字符): :01030000000AF2\r\n
TCP   (12 字节): 00 01 00 00 00 06 01 03 00 00 00 0A

TCP 那帧拆开：事务标识 00 01、协议标识 00 00、长度 00 06（单元标识 1 字节 + PDU 5 字节）、单元标识 01、功能码 03、起始地址 00 00、数量 00 0A。

响应同理，TCP 把事务标识原样带回，长度字段变成 00 17（23 字节：单元标识 1 + 功能码 1 + 字节数 1 + 数据 20）：

text
00 01 00 00 00 17 01 03 14 00 0A 01 02 00 64 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00

RTU 的同一帧响应是 25 字节，TCP 去掉 CRC 2 字节、加上 MBAP 7 字节，正好 30 字节。多出来的 5 个字节是 TCP 的定界和配对成本。

4.5 三者混用会发生什么 #

混用场景 现象
主站 RTU，从站配了 ASCII 从站把 01 当成字符 0 的半个字节解析，地址对不上，全程沉默
主站 ASCII，从站配了 RTU 从站把 :（0x3A）当地址 58，无此站，沉默
主站 TCP 帧直接灌进串口 串口从站把 00 当地址（广播），后面全乱，会触发意外写操作
主站 RTU 帧灌进 TCP 端口 对端按 MBAP 解析，长度字段离谱，连接被关
同一总线上 RTU 和 ASCII 从站混挂 两边都收不到能识别的东西，整条总线死掉

最后一行单独说一句：一条串口总线只能用一种模式。RTU 靠静默切帧，ASCII 帧里字节之间本来就有大间隔，两个混在一起谁都切不出正确的帧。

五、四张数据表 #

5.1 两张维度，四张表 #

Modbus 把设备里所有可访问的量按两个维度切分：

表 数据宽度 读写属性 读功能码 写功能码
线圈 Coils 1 位 可读可写 0x01 0x05 / 0x0F
离散输入 Discrete Inputs 1 位 只读 0x02 无
保持寄存器 Holding Registers 16 位 可读可写 0x03 0x06 / 0x10
输入寄存器 Input Registers 16 位 只读 0x04 无

第一刀按宽度：位还是字。位用来表达开关状态——继电器吸合没有、限位到了没有。字用来表达数值——温度、压力、计数值、设定值。

第二刀按方向：外部能改，还是只能看。线圈和保持寄存器是主站能写的，对应「控制输出」和「改设定值」；离散输入和输入寄存器是只读的，对应「采集输入」和「读测量值」。

这个划分体现了工业控制的意图：现场信号采集进来是只读的（你改不了传感器的读数），控制输出是能写的（你要能拉动继电器）。协议用地址空间把这两种语义分开，从站实现时也知道哪些地址允许写。

5.2 地址空间是分开的 #

这一节要讲得足够死：四张表的地址空间各自独立，从 0 开始各数各的。

线圈的地址 0x0000、离散输入的地址 0x0000、保持寄存器的地址 0x0000、输入寄存器的地址 0x0000 是四个完全不同的东西。它们只是恰好都叫 0。

0x03 和 0x04 读的不是同一片区域。 很多新手以为输入寄存器是保持寄存器的一部分、或者两者共享一片内存，这是错的。功能码 0x03 只能碰到保持寄存器，0x04 只能碰到输入寄存器。用 0x03 去读一个只实现输入寄存器的设备，从站会返回异常码 0x02（非法数据地址）。

text
线圈          0x0000 ────────────────── 0xFFFF   （位，读写）
离散输入      0x0000 ────────────────── 0xFFFF   （位，只读）
保持寄存器    0x0000 ────────────────── 0xFFFF   （字，读写）
输入寄存器    0x0000 ────────────────── 0xFFFF   （字，只读）

地址字段是 16 位，理论范围 0~65535。功能码里给的数量字段也是 16 位，但规范对各功能码的单次数量有额外限制，第六章的表里列了。

5.3 五位数地址与四位数地址 #

这是 Modbus 最坑人的一处历史遗留。

协议帧里的地址字段从 0 开始（0x0000~0xFFFF）。但很多设备手册、组态软件、老式文档用另一套编号：从 1 开始，并按表的类型加上万位前缀。

表 协议地址（帧里填的） 传统编号（手册里写的）
线圈 0x0000 ~ 0xFFFF 00001 ~ 065536
离散输入 0x0000 ~ 0xFFFF 10001 ~ 165536
输入寄存器 0x0000 ~ 0xFFFF 30001 ~ 365536
保持寄存器 0x0000 ~ 0xFFFF 40001 ~ 465536

看到手册写「40001」，意思是保持寄存器的第 1 个，帧里填 0x0000，也就是 0。看到「40101」，帧里填 0x0064，也就是 100。规律是：去掉万位前缀，再减 1。有些软件用六位编号（400001），规则一样。

碰到地址对不上，先确认手册用的是哪套编号，这比怀疑接线有用得多。

5.4 16 位寄存器怎么放 32 位数据 #

一个寄存器只有 16 位，装不下浮点数或 32 位整数。厂商的做法是拿两个连续的寄存器拼一个 32 位值。

问题在于拼的顺序，行业里没有统一。两种流派：高字在前（第一个寄存器放高 16 位）、低字在前（第一个寄存器放低 16 位）。再叠加每个寄存器内部两个字节的顺序，一共能凑出四种组合。这是 Modbus 调试里第二大坑（第一大是 CRC 字节序）。

判断办法只有一个：拿一个已知值去对。设备显示 25.0，你读回两个寄存器 0x41C8 和 0x0000，试哪种拼法能得到 float 的 0x41C80000，就能定下来。别猜。

5.5 这张抽象为什么能成 #

设备厂商只需要做一件事——把自己的所有状态摊成四张表，写一份点表文档，标清楚每个地址是什么、什么单位、怎么换算。主站照着点表配一遍，通信就通了。两边不需要共享头文件，不需要版本对齐，不需要协商能力集。

成本极低，扩展性极好，代价是表达能力弱：没有结构体、没有数组语义、没有类型系统，一切都靠文档约定。工程上这个交换是划算的。

六、功能码全表 #

6.1 公共功能码一览 #

功能码 名称 作用 操作对象 单次数量上限
0x01 Read Coils 读线圈 线圈 2000 位
0x02 Read Discrete Inputs 读离散输入 离散输入 2000 位
0x03 Read Holding Registers 读保持寄存器 保持寄存器 125 个
0x04 Read Input Registers 读输入寄存器 输入寄存器 125 个
0x05 Write Single Coil 写单个线圈 线圈 1 位
0x06 Write Single Register 写单个寄存器 保持寄存器 1 个
0x0F Write Multiple Coils 写多个线圈 线圈 1968 位
0x10 Write Multiple Registers 写多个寄存器 保持寄存器 123 个

这 8 个是规范定义的公共功能码，所有声称支持 Modbus 的设备都该实现其中的一部分。注意 0x0F 和 0x10 是十六进制，十进制是 15 和 16，别跟 0x15、0x16 搞混。

6.2 数量上限是怎么来的 #

上限被 256 字节的 ADU 长度挤出来。读操作要在一个响应里塞下所有数据，响应格式是「地址 1 + 功能码 1 + 字节数 1 + 数据 N + CRC 2」，扣掉固定开销，数据段最多 252 字节左右。读寄存器时每个占 2 字节，252 / 2 = 126，取规范值 125；读线圈时每个占 1 位，252 字节 = 2016 位，取规范值 2000。

写操作同理，但请求里还要多一个「字节数」字段，所以上限比读略小：0x0F 是 1968 位（246 字节），0x10 是 123 个（246 字节）。

6.3 功能码的分区 #

范围 类别 说明
1~64（0x01~0x40） 公共功能码 规范定义，一致性好
65~72（0x41~0x48） 用户自定义 厂商自己玩，别人不认
110~127（0x6E~0x7F） 公共但保留 规范预留，不该出现在现有设备上

再往上，0x80 及以上是异常响应用的，第九章讲。

现代设备还会用到几个后来补的扩展：0x17 Read/Write Multiple Registers（一次请求里既读又写）、0x16 Mask Write Register（按掩码改寄存器里的某几位）、0x2B Encapsulated Interface Transport（里面装设备标识读取，MEI 类型 0x0E）。这些不在最小实现里，碰到了查规范。别假设设备支持，发过去收到 0xAB 加异常码 0x01，说明它不认这个功能码。

七、读操作的请求与响应 #

四个读功能码的帧结构同构：请求里放起始地址和数量，响应里放字节数和数据。差别只在数据是位还是字、来自哪张表。下面所有 CRC 都是按多项式 0xA001 实算出来的，可以直接拿去对。

7.1 0x01 读线圈 #

请求读从站 1 的线圈，从地址 0x0013 开始读 19 个：

text
01 01 00 13 00 13 8C 02

从站地址 01、功能码 01、起始地址 00 13、数量 00 13、CRC 8C 02（低字节在前）。

响应里数据按位打包，一个字节装 8 个线圈，低位对应小地址：

text
01 01 03 CD 6B 05 42 82

03 是字节数。19 个线圈需要 3 个字节（ceil(19/8)）。三个数据字节 CD 6B 05 展开成二进制，第一个字节的最低位就是起始地址 0x0013 上那个线圈的状态。第 19 个线圈之后的高位补 0，接收方要按数量截断，不能把补齐位当成真实数据。

7.2 0x02 读离散输入 #

请求读从站 1 的离散输入，从地址 0x00C4 开始读 16 个：

text
01 02 00 C4 00 10 38 3B

响应结构与 0x01 完全一样，只是数据来源换成离散输入表：

text
01 02 02 A5 3F 82 F8

两个数据字节装 16 个输入位，A5 是低 8 位、3F 是高 8 位。

7.3 0x03 读保持寄存器 #

请求读从站 1 的保持寄存器，从地址 0x0000 开始读 10 个：

text
01 03 00 00 00 0A C5 CD

响应：

text
01 03 14 00 0A 01 02 00 64 00 00 00 00 00 00 00 00 00 00 00 00 00 00 AC 09
位置 值 含义
0 01 从站地址
1 03 功能码
2 14 字节数 20（10 个寄存器 × 2）
3~22 20 字节 10 个寄存器的值
23~24 AC 09 CRC16

数据段按寄存器逐个排列，每个寄存器高字节在前。这段数据对应的值是 0x000A(10)、0x0102(258)、0x0064(100)，后面 7 个都是 0。字节数必须是偶数，且必须等于请求里数量的两倍。收到奇数就是帧错了。

再看一个带非零起始地址的例子，从 0x006B 开始读 3 个：

text
01 03 00 6B 00 03 74 17

响应的字节数会是 06，数据 6 个字节。

7.4 0x04 读输入寄存器 #

请求读从站 1 的输入寄存器，从地址 0x0008 开始读 2 个：

text
01 04 00 08 00 02 F0 09

响应：

text
01 04 04 00 0A 00 64 DA 6D

04 字节数、四个数据字节、两字节 CRC。两个寄存器的值分别是 0x000A(10) 和 0x0064(100)。

这帧跟 0x03 的响应长得一模一样，唯一区别就是请求里的功能码。所以抓包时只看到响应不能判断读的是哪张表，得看请求。这也是为什么日志里要把请求和响应配对记录。

7.5 读操作的通用规律 #

四个读功能码的请求都是 8 字节定长 [地址1][功能码1][起始地址2][数量2][CRC2]，响应都是变长 [地址1][功能码1][字节数1][数据N][CRC2]。写解析代码时按这个骨架走，功能码只影响「数据段怎么解释」，不影响帧的解析流程。这也是为什么很多库把读操作收成一个函数，功能码当参数传。

八、写操作的请求与响应 #

写操作的响应有个共性：它不回数据，而是把请求原样回显。主站靠回显确认「这一帧我收到的和你发的一样」，这本身就完成了一次校验。

8.1 0x05 写单个线圈 #

请求把从站 1 的线圈 0x00AC 置为 ON：

text
01 05 00 AC FF 00 4C 1B

关键在 FF 00 这个固定值。线圈只有通断两种状态，规范用两个特定的 16 位值表示：

值 含义
FF 00 ON（吸合、置 1）
00 00 OFF（释放、置 0）

其他任何值都是非法数据值，从站该回异常码 0x03。这个设计有点笨——明明一个 bit 就够，却占了两个字节——但它是规范的一部分，实现时照抄，别自作聪明改成 00 01。

响应是请求的原样回显，也是 8 字节，CRC 相同：

text
01 05 00 AC FF 00 4C 1B

8.2 0x06 写单个寄存器 #

请求把从站 1 的寄存器 0x0001 写成 3：

text
01 06 00 01 00 03 98 0B

从站地址 01、功能码 06、寄存器地址 00 01、写入值 00 03、CRC 98 0B。响应同为 8 字节原样回显，CRC 相同：

text
01 06 00 01 00 03 98 0B

0x06 只写一个寄存器（16 位）。要写 32 位浮点，得用 0x10 一次写两个寄存器，或者连发两次 0x06。

8.3 0x0F 写多个线圈 #

请求把从站 1 的 10 个线圈（从 0x0013 开始）按位图写入：

text
01 0F 00 13 00 0A 02 CD 01 72 CB
位置 值 含义
0 01 从站地址
1 0F 功能码
2~3 00 13 起始地址 19
4~5 00 0A 数量 10
6 02 字节数 2
7~8 CD 01 位图
9~10 72 CB CRC16

位图的打包规则跟 0x01 的响应一样：一个字节装 8 个线圈，最低位对应起始地址。CD 是 1100 1101，最低位是 1，所以起始地址那个线圈是 ON。10 个线圈只用了 2 个字节（ceil(10/8)=2），第二个字节 01 只用到了最低 2 位，高位必须补 0。

字节数字段必须写对，它等于 ceil(数量/8)。写小了从站判帧错，写大了数据段里多出垃圾。

响应不是回显完整请求，只回显前 6 个字节加 CRC：

text
01 0F 00 13 00 0A 24 09

也就是「地址 + 功能码 + 起始地址 + 数量 + CRC」。数据段不回来，省字节。

8.4 0x10 写多个寄存器 #

请求把从站 1 的两个寄存器（从 0x0001 开始）分别写成 10 和 258：

text
01 10 00 01 00 02 04 00 0A 01 02 92 30
位置 值 含义
0 01 从站地址
1 10 功能码
2~3 00 01 起始地址 1
4~5 00 02 数量 2
6 04 字节数 4
7~10 00 0A 01 02 两个寄存器的值
11~12 92 30 CRC16

字节数等于「数量 × 2」，必须是偶数。数据段里每个寄存器高字节在前，顺序跟请求里的地址顺序一致。

响应同样是部分回显：

text
01 10 00 01 00 02 10 08

8.5 写操作的四条硬规则 #

回显必须逐字节比对。 从站回的 0x05/0x06 响应如果和请求有任何差异，说明帧在传输中被改坏了，不能当成功处理。

写入是异步生效的。 从站回了响应，只代表它收到了这条命令，不代表执行机构的物理动作已完成。写线圈让继电器吸合，继电器的机械动作在响应之后。要确认动作生效，得读回来验证。

多写不保证原子性。 0x10 写 10 个寄存器，中间某个地址非法，规范没规定是全部回滚还是部分生效。有的设备全写全不写，有的写到哪算哪。关键配置写完要整片读回来核对。

广播写没有响应。 地址填 0 的写命令，所有从站都执行，但谁都不回话。主站发完就走，无法确认执行结果。

功能码 请求长度 响应长度
0x05 写单个线圈 8 8（回显）
0x06 写单个寄存器 8 8（回显）
0x0F 写多个线圈 9 + N 8（部分回显）
0x10 写多个寄存器 9 + 2N 8（部分回显）

0x0F 的请求是 地址1 + 功能码1 + 起始2 + 数量2 + 字节数1 + 数据N + CRC2，N 个数据字节时总长 9 + N；0x10 的数据段每寄存器 2 字节，所以是 9 + 2N。写单个的响应跟请求等长，因为它是完整回显；写多个的响应固定 8 字节，因为数据段不回。

九、异常响应 #

9.1 规则：功能码最高位置 1 #

从站收到一帧，解析后发现干不了，它不会沉默，也不会回一个正常格式的响应。它回一帧异常响应，格式固定：

text
| 地址 (1 字节) | 功能码 | 0x80 | 异常码 (1 字节) | CRC16 (2 字节) |

请求里的功能码 0x01 到 0x10 都小于 0x80，最高位是 0。从站把它跟 0x80 按位或，得到 0x81 到 0x90，这就是「异常」的标记。主站看到响应功能码大于等于 0x80，就知道出事了；功能码减去 0x80 就是原来请求的那个。

异常响应永远只有 5 个字节（地址 1 + 功能码 1 + 异常码 1 + CRC 2），不回任何数据。

9.2 四个标准异常码 #

异常码 名称 含义 常见成因
0x01 非法功能 从站不支持这个功能码 设备只实现了 0x03/0x06，你发了 0x04
0x02 非法数据地址 地址超出从站实现的表范围 点表地址填错、数量超出范围、地址 + 数量越界
0x03 非法数据值 数据段里的值不合法 0x05 写了 FF 00 和 00 00 以外的值、数量填 0、字节数对不上
0x04 从站故障 从站处理时内部出错 硬件故障、参数没配好、执行机构拒绝动作

这是排错的关键信息。 「没反应」和「回了异常码」是两件完全不同的事：

  • 没反应 → 物理层、地址、波特率、校验、帧格式的问题
  • 回了 0x02 → 通信链路是通的，地址也对了，是点表配错了

抓到一个异常码，等于省掉了整条链路一半的排查工作。

9.3 逐字节示例 #

请求读从站 1 的保持寄存器，从 0x006B 开始读 3 个，这个地址在从站上不存在：

text
01 03 00 6B 00 03 74 17

从站回非法数据地址：

text
01 83 02 C0 F1

拆开看：01 从站地址、83 就是 0x03 | 0x80、02 异常码非法数据地址、C0 F1 是 CRC16。

再看几个：

text
01 81 01 81 90        地址 1，功能码 0x01 不被支持
03 84 03 A2 C1        地址 3，功能码 0x04 的数据值非法
11 90 04 4C 06        地址 17，功能码 0x10 执行时从站故障

9.4 异常码之外的情况 #

规范还留了几个码，实际少见但值得知道：

异常码 名称
0x05 确认（Acknowledge），长任务已接收，需要继续轮询
0x06 从站忙（Slave Device Busy），稍后重试
0x08 存储奇偶校验错（Memory Parity Error）
0x0A 网关路径不可用（Gateway Path Unavailable）
0x0B 网关目标设备无响应（Gateway Target Failed to Respond）

后两个只在网关场景出现：主站发 TCP 帧给网关，网关转不成 RTU 或者下游从站死了，它替下游回一个 0x0A 或 0x0B。看到这两个码，问题在下游，不在网关本身。

9.5 主站怎么处理异常响应 #

三步，顺序不能反。

认得出来。 响应功能码 >= 0x80 就是异常，长度也比正常响应短。别拿正常解析函数去套，会读出越界。

按码分流。 0x01 和 0x02 属于配置问题，重试没用，改了再来。0x03 属于组帧问题，查请求里的值。0x04、0x06 属于瞬时问题，可以退避重试。

记日志。 把原始字节、从站地址、功能码、异常码一起记下来。现场排故时这几个字段比任何描述都管用。

一个容易忽略的点：异常响应也是合法响应，它证明通信链路是好的。轮询框架里别把异常响应当成超时处理，两者的重试策略不一样。

十、CRC16 与 LRC 的实现 #

10.1 先分清三种校验层次 #

这三样东西经常被混着说，其实不在一个层次上。

奇偶校验（parity）：串口参数的一部分，管一个字符。校验位只有一位，紧跟在数据位后面。

  • 偶校验 even（简写 e）：让整个字符里 1 的个数是偶数。数据里 1 有奇数个，校验位就填 1；有偶数个，填 0。
  • 奇校验 odd（简写 o）：让 1 的个数是奇数。数据里 1 有偶数个，校验位填 1；有奇数个，填 0。
  • 无校验 none（简写 n）：不带校验位。

奇偶校验的盲区很明确：它只数 1 的个数，不管位置。发送 A（01000001）收到 B（01000010），1 的个数一样是 2 个，偶校验认为没问题。两个 bit 互换、或者偶数个 bit 同时翻转，它抓不到。

校验和（checksum）：管一整组字节。把帧里所有字节（或者字节对）按某种规则算出一个值附在帧尾，接收方重算一遍比对。它能覆盖整帧，比奇偶校验强得多。

所以分工是这样的：奇偶校验判断一个字符传得对不对，校验和判断一整帧传得对不对。两层都做，缺一不可。串口参数里配 8E1（8 数据位、偶校验、1 停止位）是给第一层；RTU 帧尾的 CRC 是第二层。

Modbus 各模式用的校验和不同：RTU 用 CRC16，ASCII 用 LRC。BCC（异或校验）不是 Modbus 标准，但在一些私有协议里能碰到。

10.2 CRC16 的原理 #

CRC 的思路是把整帧数据当成一个巨大的二进制数，用多项式去模 2 除，余数就是校验值。

Modbus 用的是 CRC-16/MODBUS 参数：

参数 值
宽度 16 位
多项式 0x8005，反向写法 0xA001
初始值 0xFFFF
输入反转 是
输出反转 是
结果异或 0x0000

多项式 0xA001 是 0x8005 的反向。 因为 Modbus 按低位先行处理字节，所以用反向多项式、往右移、检查最低位。你在别处看到的 0x8005 加左移的实现，是同一个算法的镜像写法，结果一致。

计算流程：

  1. 16 位 CRC 寄存器初始化为 0xFFFF
  2. 把第一个字节与寄存器的低字节异或，结果放回寄存器
  3. 寄存器右移一位，最高位填 0，检查移出的最低位
  4. 最低位是 1，寄存器与 0xA001 异或；最低位是 0，跳过
  5. 重复 3~4，直到右移满 8 次
  6. 取下一个字节，重复 2~5
  7. 全部字节处理完，寄存器里的值就是 CRC

参与计算的范围：从站地址开始，到数据段最后一个字节，不含 CRC 本身。起始位、停止位、奇偶校验位这些串口层面的东西一律不算。

10.3 逐位实现 #

不查表的版本，短、直白、便于对照规范逐条核对：

c
#include <stdint.h>
#include <stddef.h>

uint16_t modbus_crc16(const uint8_t *buf, size_t len)
{
    uint16_t crc = 0xFFFF;
    size_t i;
    int bit;

    for (i = 0; i < len; i++) {
        crc ^= (uint16_t)buf[i];
        for (bit = 0; bit < 8; bit++) {
            if (crc & 0x0001) {
                crc = (uint16_t)((crc >> 1) ^ 0xA001);
            } else {
                crc >>= 1;
            }
        }
    }
    return crc;
}

一个字节 8 次移位，速度对现代 MCU 完全够用。crc 的类型必须是无符号 16 位，右移才补 0 而不是补符号位。

10.5 CRC 的低位在前 #

这是 Modbus RTU 实现里最常见的错误。

CRC16 算出来是一个 16 位整数，比如 0xCDC5。这个整数要拆成两个字节放进帧尾，顺序是低字节先发，高字节后发：

text
帧尾字节 1 = CRC & 0xFF        = 0xC5
帧尾字节 2 = (CRC >> 8) & 0xFF = 0xCD

所以帧尾写的是 C5 CD，不是 CD C5。

规范里的例子是 CRC 值 0x1241，发送顺序是先发低字节 0x41，后发高字节 0x12。原因是「先发送低位字节，后发送高位字节」，跟其他字段的字节序保持一致。

算对了但字节序放反，对方一样校验不过，而且现象是「帧看起来完全正常、CRC 就是不对」，非常容易怀疑到算法本身。

c
/* 发送：把 CRC 追加到 buf 末尾，低字节在前 */
void crc_append(uint8_t *buf, size_t len)
{
    uint16_t crc = modbus_crc16(buf, len);
    buf[len]     = (uint8_t)(crc & 0xFF);   /* 低字节先 */
    buf[len + 1] = (uint8_t)(crc >> 8);     /* 高字节后 */
}

/* 接收：把收到的两字节按低位在前拼回来，再跟重算值比 */
int crc_check(const uint8_t *buf, size_t len)
{
    uint16_t got, calc;
    /* len 是含 CRC 的总长度，最后两字节是 CRC */
    got  = (uint16_t)buf[len - 2];
    got |= (uint16_t)buf[len - 1] << 8;
    calc = modbus_crc16(buf, len - 2);
    return got == calc;
}

注意 crc_check 里的拼接方向：buf[len-2] 是低字节，buf[len-1] 是高字节。写反了就是一个永远返回 0 的函数。

10.6 LRC 的原理与实现 #

LRC 用在 ASCII 模式，1 个字节，算法比 CRC 简单得多。

  1. 把参与校验的所有字节相加，累加器是 8 位，进位直接丢弃（每步按 0xFF 取模）
  2. 用 0x100 减去累加和的低 8 位，得到二进制补码
  3. 得到的结果就是 LRC

等价说法是「用 0xFF 减，再加 1」，因为 0xFF - x + 1 = 0x100 - x。

参与范围：ASCII 帧里从起始符 : 之后开始，到 LRC 之前结束的所有字节（地址、功能码、数据段）。原规范对起止符是否计入表述不一，工程实现的做法很一致：不含 :，不含 CRLF。这一条要跟对端对齐，差一个字节就永远校验不过。

用前面那帧验证：01 + 03 + 00 + 00 + 00 + 0A = 0x0E，LRC = 0x100 - 0x0E = 0xF2。

c
static unsigned char LRC(unsigned char *auchMsg, unsigned short usDataLen)
{
    unsigned char uchLRC = 0;                        /* 初始化 LRC 字符 */
    while (usDataLen--) {                            /* 遍历数据缓冲器 */
        uchLRC += *auchMsg++;                        /* 加缓冲器字节，丢弃进位 */
    }
    return (unsigned char)(-(signed char)uchLRC);    /* 返回二进制补码 */
}

unsigned char 的加法天然按模 256 回绕，进位自动丢，不用手写掩码。最后一步先转成 signed char 再取负，可以避免某些编译器对无符号数取负的告警。

LRC 在帧里的呈现是 ASCII 字符。算出的 0xF2 要拆成高 4 位 F 和低 4 位 2，分别映射成字符 F（0x46）和 2（0x32）。规范说先发高位字符再发低位字符，所以 F 在前、2 在后。这跟 CRC 的低位在前正好相反，别记串了。

10.7 BCC 异或校验 #

BCC（Block Check Character）不是 Modbus 标准的一部分，是一些私有协议和早期仪表协议常用的手法。算法：把参与校验的所有字节逐个异或，结果就是一个字节。

c
static unsigned char BCC(const unsigned char *buf, unsigned short len)
{
    unsigned char bcc = 0;
    while (len--) {
        bcc ^= *buf++;
    }
    return bcc;
}

它一个字节，开销最小，比累加和稍强（进位信息不丢）。盲区也明显：抓不住偶数个 bit 同时翻转，多个相同字节连写时容易失效，比如 00 00 00 的异或结果就是 00。

累加和 1 字节 是 部分 否 极低
BCC 异或 1 字节 是 否 否 极低
LRC 1 字节 是 部分 否 低
CRC16 2 字节 是 是 是 中

CRC16 是唯一在三个维度上都过的。这也是为什么 RTU 用 CRC，而 ASCII 用一个更弱的 LRC——ASCII 追求人工可读和实现简单，把可靠性让了一部分出去。

十一、寻址与轮询 #

11.1 地址范围 #

串口模式下从站地址是 1 个字节，取值有严格划分：

地址 用途
0 广播地址
1 ~ 247 单个从站
248 ~ 255 保留，不得使用

地址 0 是广播：主站发出去，所有从站都收、都处理，但谁都不回应。这个设计省掉了「一堆从站同时开口」的冲突，代价是主站拿不到任何确认。

广播只对写操作有意义。发一个广播读没意义——没人回答，主站永远等不到数据。

广播的能力边界：因为没有响应，主站不知道有几个从站收到了、有没有执行成功、有没有地址不存在。所以广播只能用在「可重复、幂等、失败也不致命」的场景，比如全站统一复位、统一置某个安全状态。不能用在「必须确认写入成功」的场合。

Modbus TCP 用 IP 地址寻址，不受这个范围限制。MBAP 头里的单元标识只在网关后面接 RTU 从站时才有实际意义。

11.2 物理层现实与终端电阻 #

串口模式下的典型拓扑是 RS-485 总线：一对双绞线，主站和所有从站并联挂上去，半双工。一条总线挂多少台设备，取决于收发器芯片的驱动能力（标称 32 个单位负载是常见值，用高阻抗收发器能更多），也取决于线长和波特率的乘积。

电信号在传输线上跑，到了末端如果阻抗突然变小甚至开路，信号会反射回来，叠加在原信号上造成波形畸变。这和光从空气进入水面会有一部分反射是同一个道理——介质变了，边界上就有回波。

办法是在总线的物理两端各接一个终端电阻，把末端阻抗拉回与线缆特性阻抗匹配：

  • 电阻只装在总线的两个物理端点，中间节点不装
  • 阻值取线缆特性阻抗，RS-485 常用双绞线是 120 Ω
  • 总线很短（几米）、速率很低时，不装也能跑，别把它当唯一原因
  • 装了终端电阻，空闲时的差分电压会被拉向 0，有些场合还要加偏置电阻把空闲态定死

「通信时好时坏、换根短线就好了」这类现象，先查终端电阻和屏蔽接地。

11.3 主站必须串行轮询 #

这是整套协议最容易违反的约束。主站必须串行轮询，不能并发。

原因在物理层：RS-485 是半双工，一对线同一时刻只能有一个方向在说话。主站发帧时，所有从站都在收；从站应答应时，其他从站和主站都在收。主站连着给两个从站发请求，两帧在总线上叠成一团，谁都解析不了。

原因也在协议层：RTU 帧不带事务标识，没有字段能告诉你「这帧响应是给哪次请求的」。响应里只有从站地址和功能码，主站只能靠「我上一次发的是什么」来配对。并发发两帧，回来的两份响应你分不清谁是谁。

所以轮询循环必须长这样：

c
for (addr = 1; addr <= 247; addr++) {
    if (!站点存在) continue;
    发请求(addr);
    等响应(超时 = T);
    if (收到) 处理();
    else 标记该站异常();
    /* 这里必须等帧间隔静默结束，才能发下一帧 */
    等待_t3_5_静默();
}

TCP 模式宽松一些，事务标识让并发成为现实。但很多设备的 TCP 实现是内部转串口的，并发一多就从站侧排队。除非确认设备支持，别在 TCP 上并发。

11.4 轮询周期怎么估 #

单次事务时间 = 请求帧传输时间 + 从站处理时间 + 响应帧传输时间 + 帧间隔，帧传输时间 = 帧字节数 × 每字符位数 / 波特率。

拿 9600 波特、8E1（11 位每字符）举例，一次「读 10 个保持寄存器」：

text
请求 8 字节  → 8 × 11 / 9600   ≈ 9.2 ms
响应 25 字节 → 25 × 11 / 9600  ≈ 28.6 ms
帧间隔 t3.5  → 4.0 ms
从站处理时间 → 设备相关，规范不限，实际几毫秒到几十毫秒

一轮下来接近 50 ms，还没算从站处理时间。挂 20 个站，完整扫一遍就是 1 秒左右。这就是为什么 Modbus 不适合做高速控制回路——它的实时性来自「可预算」，不来自「快」。

想缩短轮询周期，能动的只有几个量：提高波特率（受线长和设备能力限制）、减少单次读的寄存器数量（但会增加轮询次数）、把不常变的点降频轮询、减少从站数量或拆到多条总线上。

11.5 超时与重试 #

主站必须设超时，从站会掉电、会死机、会地址配错。超时值按「最坏情况的响应传输时间 × 2 左右」设，工程上常用几百毫秒。太短会把正常的慢设备踢掉，太长会让一个坏站拖垮整轮轮询。

重试要克制。一次轮询里某个站失败，重试 1~2 次是合理的；重试多次会把整轮周期拉长，而且如果这个站是硬件坏了，重试一万次也没用。实际做法是：连续 N 轮失败后把该站从轮询表里摘掉，隔一段时间再放回去探测。这样单个坏站不会持续拖累整个系统。

11.6 开发和调试工具 #

Modbus Poll：模拟主站。按点表配置地址、功能码、数据类型，自动循环轮询，把响应实时显示在表格里。写主站之前用它验证从站是否正确，能省掉一半互相甩锅的时间。

Modbus Slave：模拟从站。可以让寄存器里长出任意的值，用来测试主站软件的读取、写入、异常处理路径。没有真实硬件时特别有用。

Wireshark：抓 Modbus TCP 的包。它有内置的 modbus 解析器，能直接展开功能码、地址、字节数，不用手工数，抓 TCP 就能看到 MBAP 头和 PDU 的分层。

libmodbus：跨平台的 C 库，主站从站都能做。API 屏蔽了三种模式的差异，modbus_new_rtu 和 modbus_new_tcp 换一下就行。做快速原型比从零写帧省事得多，具体用法在 Modbus 实现那篇。

串口上抓 RTU 帧，靠这些工具不够——RTU 没有 TCP 那样的包边界，Wireshark 抓不到串口。要么用逻辑分析仪接在 485 差分线上，要么在自己代码里把收发字节带时间戳打出来。后者成本低，绝大多数问题够用。

12.2 按现象反查的三条路径 #

路径一：完全没反应。 这是在问物理层和链路层。顺序是：线接对没有 → 供电有没有 → 波特率和帧格式对不对 → 地址对不对 → 从站是否真的在跑。全都对了还是没反应，用示波器或逻辑分析仪看差分线上有没有波形，没有就是发送端的问题。

路径二：有反应但是异常码。 这说明链路是通的，问题在应用层。0x01 查功能码支持列表，0x02 查地址和范围，0x03 查写入的值，0x04 查设备本身。这条路最好走，因为错误码直接指了方向。

路径三：偶尔成功偶尔失败。 这是最难的一类，往三个方向查：终端电阻和屏蔽接地（电气问题）、波特率误差累积（时钟问题）、主站超时太紧（时序问题）。在日志里加时间戳，看失败的帧和成功的帧有什么差别。

12.3 上电联调的顺序 #

  1. 单站、短接线、低波特率先跑通。9600、线长一米、只挂一台从站。
  2. 用手工拼的帧验证一遍。读一个已知地址，把响应逐字节对一遍，确认地址、功能码、字节数、CRC 都对。
  3. 确认点表的编号体系。手册上的 40001 到底对应帧内 0x0000 还是 0x0001，用读一个已知值的方式验证。
  4. 确认 32 位数据的拼接顺序。读一个已知的浮点数，把四种拼法都试一遍。
  5. 加长线、加设备、提波特率，一次只改一个变量。
  6. 把异常响应和超时都跑一遍。拔掉一台从站，看主站多久发现、怎么处理。

第三步和第四步是现场最容易翻车的两处，都是「文档和实现对不上」造成的，不是协议的问题。

12.4 一页纸收束 #

回到最开始那句话：Modbus 是一个一问一答的寄存器读写协议。主站发一帧请求，写清地址、功能码、起始地址和数量；从站回一帧响应，带着数据或者异常码。

所有数据都映射到四张表的地址空间里，协议本身不关心地址背后是温度还是开关。这个「地址抽象」是它能成为工业标准的原因——任何设备都能挂上来，只要它肯把自己的状态摊成一张寄存器表。

RTU 靠静默时间切帧，3.5 个字符时间分帧、1.5 个字符时间判帧内断裂，这个时间是随波特率变的，不是常数。

CRC 算对了还要按低位在前放，字节序反了，对方一样校验不过。

主站必须串行轮询。物理层是半双工，协议层没有事务标识，两条都指向同一个结论。

这四句话记住了，剩下的都是细节。
