一、MQTT 解决什么问题 #

先把场景摆出来。物联网的典型形态是这样：

  • 设备数量多，一个项目几千到几十万台，每台都在往上报数据。
  • 单条数据很小，一个温度值、一个开关状态，几十个字节。
  • 网络不稳，Wi-Fi 掉线、4G 信号弱、NB-IoT 有休眠，连接随时断。
  • 设备算力低，单片机跑不动完整 TLS 栈 + JSON 解析 + HTTP 客户端。
  • 拓扑常变，设备上线、下线、换位置，服务端事先不知道谁在。

拿 HTTP 轮询硬做，会撞上四个坑。

维度 HTTP 轮询 MQTT
连接模型 短连接，每次请求重新握手 长连接，一次 TCP 用到底
报文开销 请求头动辄几百字节 固定头最小 2 字节
服务端推送 做不到，只能客户端来问 天然支持，Broker 主动转发
一对多 每个客户端都得单独问一遍 发一条，所有订阅者都收到
设备掉线感知 要靠超时和业务心跳 协议层有 Keep Alive 与遗嘱

MQTT（Message Queuing Telemetry Transport，消息队列遥测传输协议）就是冲着这几条去的。它构建在 TCP/IP 之上，是客户端与服务器之间的发布/订阅式通讯协议，专门针对低带宽和不可靠网络下的远程传感器与控制设备设计。

它的六个特性，我们逐条对上场景：

  1. 发布/订阅消息模式：允许一对多的消息发布，减少应用程序之间的耦合，系统设计更灵活。设备不需要知道谁在消费它的数据。
  2. 负载内容屏蔽：Broker 不解析负载，二进制数据原样透传。加密、压缩、序列化格式都由应用层自己定，协议不插手。
  3. TCP/IP 网络连接：默认走 TCP，享受 TCP 的有序、无损、基于字节流的双向传输。
  4. 消息服务质量（QoS）：提供三个等级，让「丢一条」和「重一条」的取舍由你决定，而不是协议替你决定。
  5. 小型传输和低开销：固定头最小 2 字节，协议交换本身几乎不占带宽。
  6. Last Will and Testament：客户端可以预先登记一条遗嘱，异常断开时由 Broker 代发，用于设备掉线告警。

那 2 字节是怎么算出来的 #

「消息头固定 2 字节」这个说法容易被误解。准确讲，最小是 2 字节，因为 Remaining Length 字段本身是变长的。

text
固定头（Fixed Header）

  byte 1      报文类型 4 bit（PUBLISH = 3） + 标志 4 bit（DUP / QoS / RETAIN）
  byte 2..5   Remaining Length，变长编码，占 1~4 字节

可变头（Variable Header，按报文类型决定）

  2 字节      Topic Name 的长度
  N 字节      Topic Name
  2 字节      Packet Identifier（只有 QoS > 0 时才存在）

负载（Payload）

  M 字节      应用数据，Broker 不解析

拿一条最小的情况算：固定头 2 字节 + 可变头 5 字节（2 字节长度 + 3 字节 Topic a/b）+ 0 字节负载 = 7 字节。

同样的信息用 HTTP POST 发出去，光是请求行加 Host 加 Content-Type 加 Content-Length 就超过 100 字节。设备一天发一万条，差出来的流量是实打实的。

这就是 MQTT 的定位：不是因为它功能多，而是因为它在该省的地方省到底。

二、发布订阅模型 #

MQTT 里有三种身份角色。

角色 英文 职责
发布者 Publisher 往某个 Topic 发消息，可以同时是订阅者
代理 Broker（服务器） 接收发布的消息，按订阅关系转发给订阅者
订阅者 Subscriber 订阅 Topic，收到匹配的消息

关键点在这里：发布者和订阅者互不知道对方存在，谁也不知道对方在不在线，甚至不知道对方是人是机。它们之间唯一的联系是 Topic 字符串。

text
                    ┌─────────────────┐
   温度传感器 ──────▶│                 │
   （Publisher）     │                 │──────▶ 手机 App
                    │     Broker      │        （Subscriber）
   开关面板   ──────▶│    （服务器）    │
   （Publisher）     │                 │──────▶ 数据入库服务
                    └─────────────────┘        （Subscriber）
                            ▲
                            │
                     只看 Topic 字符串匹配
                     不管对方是谁、在不在线

这种解耦拆成了三个维度：

  • 空间解耦：发布者不需要知道订阅者的地址、数量、身份。
  • 时间解耦：发布者发消息时，订阅者可以不在线，消息由 Broker 留着（QoS > 0 且持久会话时）。
  • 同步解耦：发布者发完就走，不需要等订阅者处理完才继续。它不是请求/响应。

跟请求/响应模型摆在一起对比，差别就很清楚。

维度 请求/响应（HTTP） 发布/订阅（MQTT）
谁是主动方 客户端发起，服务端被动响应 双方都可以主动，靠 Broker 中转
寻址方式 URL 定位到具体服务 Topic 字符串匹配，不定位具体谁
一对多 需要循环调用 N 次 发一条，N 个订阅者都收到
调用方是否要知道被调方 必须知道 不需要
耦合点 接口契约（方法、路径、字段） Topic 命名约定
失败语义 请求失败，调用方立刻知道 发布成功不代表有人收到

最后一行值得多说一句。发布者收到 Broker 的 PUBACK，只说明 Broker 收下了，不说明订阅者收到了。订阅者那边有没有处理、处理对不对，协议不知道，也不负责。要确认端到端送达，得在应用层自己做回执 Topic。

消息由什么组成 #

MQTT 的消息结构只有两块：

  1. Topic：消息的类型标签。订阅者订阅某个主题后，会收到该主题下的所有消息。
  2. Payload：具体的消息内容，订阅者处理时用的实际数据。

Topic 是协议要解析的，Payload 是协议不碰的。这条分界线贯穿整篇：Broker 只按 Topic 路由，负载里装的是 JSON、Protobuf、裸二进制还是加密后的密文，它一概不看。

所以「负载内容屏蔽」不是一句空话，它意味着你在 Payload 里塞什么，协议层都不会因为「格式不对」拒收。好处是灵活，坏处是格式错了没人提醒你，一直到消费端解析崩了才发现。

三、Broker 的角色 #

MQTT 服务器，也就是「消息代理」，可以是一个独立应用进程，也可以是一台专门的设备。它在发布者与订阅者之间，承担四件事：

  1. 接收来自客户端的网络连接请求。
  2. 处理客户端发布的应用消息，转发给匹配的订阅者。
  3. 处理订阅与退订请求，维护每个客户端的订阅状态。
  4. 把消息广播给订阅的客户端。

这四件事是协议规范里明写的。落到实现上，还得再加几条不那么显眼但同样关键的：

  • 认证：校验用户名密码或客户端证书，拒绝非法连接。
  • 会话管理：记住 ClientID 对应的订阅关系、未确认消息、离线队列。
  • 订阅树维护：把 Topic Filter 组织成可快速匹配的结构，新消息进来后找出所有命中的订阅。
  • QoS 状态机：QoS 1 记着哪条消息还没收到 PUBACK，QoS 2 记着四次握手走到哪一步。
  • 保留消息存储：每个 Topic 留最后一条 RETAIN 消息，新订阅者一来就发。
  • 遗嘱触发：检测到客户端异常断开时，把登记好的遗嘱发出去。

对应的客户端侧能力是四条：发布别人会订阅的信息、订阅别人发布的消息、退订不再需要的主题、主动断开连接结束会话。

Broker 不做什么 #

这条边界比「做什么」更重要，很多误用都出在这里。

事情 谁负责
按 Topic 路由消息 Broker
维持 QoS 握手状态 Broker
保存保留消息 Broker
检测心跳超时并触发遗嘱 Broker
解析 Payload 内容 应用层
保证同一条消息不被重复处理 应用层（幂等）
保证跨 Topic 的消息顺序 没人保证
保证消息在某个时间点前送达 没人保证
端到端送达确认 应用层（回执 Topic）

看到中间那几行没有：Broker 只保证「按协议约定的尽力转发」，它不保证你业务上的任何东西。

常见开源与商用 Broker 有 Mosquitto（C 写的单机实现）、EMQX（Erlang 写的，主打集群）、HiveMQ（Java，商业授权）、VerneMQ，以及各云厂商的托管服务（AWS IoT Core、阿里云物联网平台）。它们的差异在扩展性、管理界面、规则引擎这些工程层面，协议语义是一致的。本篇不涉及具体配置。

四、Topic 与通配符 #

Topic 是 MQTT 里唯一的路由依据，所以命名规则必须先立住。

分层结构 #

Topic 用 / 分层，像文件路径，但跟文件路径有一个关键差别：不需要预先创建，也不需要存在。客户端想发 home/room1/temp，直接发就行，Broker 不检查这个 Topic 有没有被订阅过。

text
home/room1/temp
home/room1/humidity
home/room2/temp
factory/line3/machine7/status

层级数没有硬限制，但实际用起来，三层到五层足够。层数堆太多，订阅方写通配符时容易一刀切过头。

两个容易混的概念 #

概念 英文 用在哪 能否含通配符
主题名 Topic Name PUBLISH 报文里 不能，必须写全
主题筛选器 Topic Filter SUBSCRIBE / UNSUBSCRIBE 里 能，可以用 + 和 #

发布时不允许用通配符。你不能往 home/+/temp 发消息，协议层会视为非法。只有订阅时才用通配符。

这一条经常被问：为什么发布不能通配？因为通配符是「一次匹配多个」的语义，而发布是「一条消息落到一个具体 Topic」，落哪儿必须唯一。

两个通配符 #

+ 匹配单层

text
订阅：home/+/temp
命中：home/room1/temp
命中：home/room2/temp
不中：home/room1/floor2/temp     ← + 只吃一层
不中：home/temp                  ← 层数不对

+ 可以放在任意层级，也可以一层里用好几个，甚至单独占一层。

# 匹配多层，且必须放末尾

text
订阅：home/room1/#
命中：home/room1/temp
命中：home/room1/floor2/temp
命中：home/room1/a/b/c/d
不中：home/room2/temp

# 只能出现在最后一级，而且必须是单独一个 #。home/#/temp、home/room# 都是非法写法。这条规则没有例外，因为 # 的语义就是「剩下的全部」，它不是正则里的 *。

特殊情况：单独一个 # 是合法的，表示订阅所有非 $ 开头的 Topic。

筛选器 是否合法 说明
home/room1/temp 合法 精确订阅
home/+/temp 合法 单层通配
home/room1/# 合法 该层以下全部
# 合法 全部非 $ 开头的 Topic
+/+ 合法 恰好两层的所有 Topic
home/#/temp 非法 # 不在末尾
home/room# 非法 # 没单独占一层
home/room1+ 非法 + 没单独占一层
home/+/ 非法 末尾空层（有的实现容忍，别依赖）

几条硬规则 #

  • 区分大小写。Home/Room1 和 home/room1 是两个 Topic。
  • + 和 # 必须单独占一层。sensor+ 不是通配符，只是一个含加号的普通 Topic 名。
  • 不能有空层级。home//temp 是否合法，各实现处理不一致，别写。
  • 以 / 开头会产生空的第一层。/home/room1 和 home/room1 不同，前者的第一层是空字符串。
  • $ 开头的 Topic 是系统保留的。$SYS/broker/uptime 这类是 Broker 自己发布的运行状态，# 和 +/+ 不会匹配到它们，必须显式订阅 $SYS/#。

命名方案怎么定 #

Topic 一旦上线就是对外契约，改一次要动所有发布方和订阅方。定命名方案时把这几条想到：

text
建议结构：{业务域}/{设备类型或位置}/{设备ID}/{数据类型}

home/room1/sensor42/temp
factory/line3/machine7/status
farm/zoneA/node108/soil

几条实践约束：

  1. 设备 ID 放固定层级，这样能用 home/room1/+ 一次订阅整个房间的所有设备。
  2. 数据类型放最末层，这样能用 home/room1/sensor42/# 拿到一台设备的全部数据。
  3. 不要拿 Topic 传数据。见过把时间戳和温度值拼进 Topic 的：home/room1/temp/23.5/1712...。这样每发一条就新建一个 Topic，Broker 的订阅树会被撑爆，通配符匹配也退化成无意义的全表扫描。
  4. 用 Payload 承载变化的部分，Topic 只承载分类维度。

一个边界要提醒 #

订阅 home/+ 不会收到发往 home 的消息，因为 home/+ 要求至少两层。反过来，订阅 home/# 会收到发往 home 的消息，因为 # 包括父层本身。

五、QoS 0：至多一次 #

QoS 是 MQTT 最核心的设计，也是最多人只看结论不看代价的地方。我们一级一级拆。

QoS 0 是「At most once」，至多一次。

它的行为只有一句话：发布者把 PUBLISH 报文丢给 Broker，然后就不管了。

text
Publisher                Broker                Subscriber
    │                      │                       │
    │──── PUBLISH QoS 0 ──▶│                       │
    │   （发完即忘，不等待）  │──── PUBLISH QoS 0 ───▶│
    │                      │                       │

整个过程里没有确认报文。发布者不知道 Broker 收没收到，Broker 不知道订阅者收没收到。

  • 报文数：1 条（只算 MQTT 报文）。
  • 是否有 Packet Identifier：没有。QoS 0 的 PUBLISH 报文不带报文标识符，因为不需要对应任何确认。
  • 是否重传：不重传。DUP 标志在 QoS 0 下必须是 0。
  • 是否保序：同一条 TCP 连接上，QoS 0 消息按发送顺序到达 Broker。跨连接、跨重连就不保证了。

什么时候会丢 #

丢的环节有三个，全都不通知任何人：

环节 场景
发布者 → Broker TCP 连接刚好在发送瞬间断掉，缓冲区里的数据没出去
Broker 内部 Broker 重启、内存队列溢出、被限流策略丢弃
Broker → 订阅者 订阅者掉线，而它的会话不是持久的（CleanSession=1）

最后一条最常被忽略：订阅者用 CleanSession=1 断开后，Broker 立刻丢掉它的订阅，这期间发的 QoS 0 消息全部消失，重连后也补不回来。

它适合什么 #

QoS 0 不是「低级选项」，它在很多场景是正确选择：

  • 高频传感器数据：一秒一条的温度，丢几条不影响趋势判断，下一条马上补上。
  • 可容忍丢失的状态广播：设备在线状态每 10 秒广播一次，丢一次 10 秒后就刷新了。
  • 带宽极紧的链路：NB-IoT 按流量计费，确认报文也是钱。
  • 低延迟优先：QoS 0 没有等待确认的往返，端到端最快。

选 QoS 0 的前提是想清楚一件事：丢一条会怎样。如果答案是「下一条就覆盖了」，那就选它。

六、QoS 1 与 QoS 2 #

QoS 1：至少一次 #

QoS 1 是「At least once」。它给 PUBLISH 加了一个确认：PUBACK。

text
Publisher                    Broker
    │── PUBLISH QoS 1, ID=7 ──▶│
    │◀──────── PUBACK, ID=7 ───│

发布者发出 PUBLISH 后，启动一个重传计时器。在收到 PUBACK 之前，它会把这条消息留着。计时器到期还没等到 PUBACK，就重发一次，并把 DUP 标志置 1。

这就是「至少一次」的由来：它保证消息不丢，代价是允许重复。

重复从哪来？就一个原因：ACK 丢了，但消息其实到了。

text
Publisher                      Broker
    │                            │
    │── PUBLISH QoS 1, ID=7 ─────▶│   Broker 收到了，转发出去了
    │                            │
    │        ✗ PUBACK 在路上丢了   │
    │                            │
    │── PUBLISH QoS 1, ID=7 ─────▶│   Broker 又收到一次，又转发一次
    │      （DUP=1）              │
    │◀───────── PUBACK, ID=7 ─────│

订阅者侧收到两条一模一样的数据。Broker 从头到尾行为的都符合规范，是发布者的重传导致的。协议层没有办法区分「这条是新消息」还是「这条是重传」，只能靠 DUP 标志提示，而 DUP 本身也不可靠（重连后第一次重发时，某些实现不置 DUP）。

结论很直接：QoS 1 必须配套应用层幂等。

幂等的做法就那几种：

  • 消息体里带一个全局唯一 ID（设备 ID + 单调递增序号，或 UUID），消费端记录已处理的 ID。
  • 消息体里带业务时间戳和状态版本号，消费端只接受更新的版本。
  • 数据库写入用唯一索引或 INSERT ... ON CONFLICT DO NOTHING 这类语义。
  • 计数、累加这类操作改造成「写入幂等键 + 后台聚合」，别直接 UPDATE count = count + 1。

最后一条是重灾区。一条「电量 +1」的指令重复执行两次，账就错了。

QoS 2：恰好一次 #

QoS 2 是「Exactly once」。它用四次握手换来不丢不重。

text
Publisher                                  Broker
    │                                        │
    │── PUBLISH QoS 2, PacketID=9 ─────────▶│   Broker 存下消息，但不投递
    │                                        │   也不转发给订阅者
    │◀────────────── PUBREC, ID=9 ──────────│
    │                                        │
    │── PUBREL, ID=9 ───────────────────────▶│   Broker 现在才释放消息
    │                                        │
    │◀────────────── PUBCOMP, ID=9 ─────────│
    │                                        │

四步分别是 PUBLISH → PUBREC → PUBREL → PUBCOMP。

关键在 PUBREC 之后、PUBREL 之前这个窗口：Broker 收到 PUBLISH 并回了 PUBREC，但它不会把消息转发给订阅者，直到收到 PUBREL。所以如果发布者没等到 PUBREC 就重发，Broker 认得同一个 PacketID，只回 PUBREC，不会存第二份。

  • 报文数：4 条。
  • PacketID 生命周期：从 PUBLISH 开始，到 PUBCOMP 结束。这期间这个 ID 不能被同连接上的其它消息复用。
  • 重传规则：没等到 PUBREC 就重发 PUBLISH（DUP=1）；没等到 PUBCOMP 就重发 PUBREL。

别忽略了接收方向 #

上面讲的是发布者到 Broker。Broker 到订阅者那一段是另一个独立的过程，也是 QoS 2 的四次握手（方向反过来，Broker 当发送方）。所以一条 QoS 2 消息端到端走完，链路上实际跑的报文远不止 4 条。

text
PUBLISH QoS2 ─▶      PUBLISH QoS2 ─▶
◀─ PUBREC            ◀─ PUBREC
PUBREL ─▶            PUBREL ─▶
◀─ PUBCOMP           ◀─ PUBCOMP
  （发布者↔Broker）     （Broker↔订阅者）

这就是为什么有人以为 QoS 2 是「四条报文」，实际端到端是八条。选 QoS 2 之前先算清楚这笔账。

三级摆在一起 #

维度 QoS 0 QoS 1 QoS 2
语义 至多一次 至少一次 恰好一次
握手报文数（单向） 1 2 4
报文序列 PUBLISH PUBLISH → PUBACK PUBLISH → PUBREC → PUBREL → PUBCOMP
带 PacketID 否 是 是
会丢 会 不会（限会话存续期间） 不会
会重复 不会（因为压根没重传） 会 不会
延迟 最低 中 最高
带宽开销 最小 约 2 倍 约 4 倍
应用层要做什么 无需处理 必须做幂等 无需处理重复

注意「会丢」那一行给 QoS 1 和 QoS 2 加的条件：会话存续期。如果会话没持久化、离线队列长度有限、消息过期时间到了，一样会丢。QoS 不是万能保险。

降级的现实 #

订阅时声明的 QoS 和发布时的 QoS 会取一个较小值生效。你订阅时写 QoS 2，但发布者用 QoS 0 发，你收到的还是 QoS 0。

text
生效 QoS = min(发布 QoS, 订阅 QoS)

这条规则必须知道，否则会出现「我明明订阅了 QoS 2 怎么还丢消息」的困惑。答案在发布侧。想全链路都达到某个等级，两个方向都要设定，还要确认 Broker 没做降级配置。

七、三个等级怎么选 #

选 QoS 的判断只有一句话：「丢一条」和「重一条」，哪个更不能接受。

  • 丢一条更不能接受 → 往 QoS 1 以上走。
  • 重一条更不能接受 → QoS 1 就得配幂等，或者直接上 QoS 2。
  • 两个都能接受 → QoS 0。

把这句话展开成场景表：

场景 选 为什么
温度、湿度、电压等周期上报 QoS 0 下一条几秒后就覆盖，丢了无所谓
设备在线状态心跳广播 QoS 0 状态会重复刷新
告警上报（门磁被打开、烟感触发） QoS 1 丢一条就是漏报，重复上报可接受
指令下发（开灯、关阀） QoS 1 + 幂等 重复执行开灯无害，但要在应用层防重
计费、扣款、用量结算 QoS 2 重一条就是多扣钱
固件分片传输 QoS 1 每片带偏移量，消费端按偏移写，天然幂等
配置下发、参数同步 QoS 1 或 QoS 2 看配置能不能重复应用
高频行情类推送 QoS 0 延迟比完整更重要

开销是怎么涨上去的 #

堆 QoS 不是免费的。我们按一条 20 字节负载的消息、Topic 长 18 字节，粗算 MQTT 报文本身的字节数。

text
QoS 0：PUBLISH
  固定头 2 字节（含 Remaining Length）+ 可变头 2 字节 Topic 长度 + 18 字节 Topic
  + 20 字节负载
  ≈ 42 字节，1 个报文

QoS 1：PUBLISH + PUBACK
  PUBLISH ≈ 42 + 2 字节 PacketID = 44 字节
  PUBACK  = 4 字节（固定头 2 + PacketID 2）
  ≈ 48 字节，2 个报文

QoS 2：PUBLISH + PUBREC + PUBREL + PUBCOMP
  PUBLISH ≈ 44 字节
  PUBREC  = 4 字节
  PUBREL  = 4 字节
  PUBCOMP = 4 字节
  ≈ 56 字节，4 个报文

只看字节，QoS 2 是 QoS 0 的 1.33 倍，好像不多。但真正贵的地方不在字节，在往返次数。

QoS 0 是单向发出，不等。QoS 1 要等一个 RTT。QoS 2 要等两个 RTT（PUBLISH→PUBREC 一个，PUBREL→PUBCOMP 一个）。

text
QoS 0        发送 ───────────────────────────▶  完毕
             耗时 ≈ 0 个 RTT

QoS 1        发送 ──────▶          ◀────── 确认
             耗时 ≈ 1 个 RTT

QoS 2        发送 ──▶     ◀── PUBREC
             发送 PUBREL ──▶     ◀── PUBCOMP
             耗时 ≈ 2 个 RTT

在 4G 网络下 RTT 50~100ms 是常态，QoS 2 单条消息就多出 100~200ms。一秒要发 100 条的设备，QoS 2 直接卡死。

还有个隐藏成本：状态机内存。Broker 和客户端都要为每条未完成握手的消息保存状态。QoS 0 零状态，QoS 1 存一条待确认消息，QoS 2 存到 PUBCOMP 为止。连接数上万的时候，这个内存差是会压死 Broker 的。

所以真实项目里的常见配置是：

text
遥测数据通道     QoS 0 或 QoS 1
告警通道         QoS 1
指令通道         QoS 1 + 应用层幂等（少数场景 QoS 2）

全链路 QoS 2 的项目，要么量极小，要么没算过账。

MQTT 不保证实时 #

这条要单独讲，因为它是被误解最多的一条。

MQTT 的 PUBLISH 在协议层只承诺「最终会送到」，没有任何时序保证：

  • Broker 转发有延迟。它要做 Topic 匹配、查订阅树、排队、还要落盘。这些都不在协议时限里。
  • 网络抖动时不保证顺序。同一条 TCP 连接上，TCP 保证字节顺序；但重连之后，前一条在旧连接的缓冲区里，后一条在新连接上，到达顺序就反了。
  • QoS 1 的重传会打乱顺序。消息 A 未确认、消息 B 已确认，A 重传后到得比 B 晚，消费端看到的是 B、A。
  • 不同 QoS 混发更容易乱。QoS 0 直接过，QoS 1 要等确认，两条消息的到达顺序跟发送顺序可以完全不一致。
  • 离线补发是批量倒出来的。订阅者重连后，Broker 把攒下的离线消息一次性推过去，跟它们原本的产生时间没有关系。

结论：要顺序、要实时，就得靠应用层自己带序号和时间戳。

c
/* 负载里带上这两个字段，比调 QoS 有用得多 */
typedef struct {
    uint32_t seq;          /* 单调递增序号，设备重启后从持久化存储恢复 */
    int64_t  ts_ms;        /* 采样时刻，毫秒级 Unix 时间戳 */
    int16_t  temp_x10;     /* 温度 ×10，避免浮点 */
    uint8_t  flags;
} telemetry_t;

消费端拿到之后：

  • seq 比已见的最大值小 → 判断为乱序或重传，按业务决定丢弃还是缓存重排。
  • ts_ms 与本地时间差超过阈值 → 判定为延迟数据或设备时钟漂移，标记而不是直接入库。
  • 两条 seq 之间断了 → 知道丢了哪几条，可以触发补拉。

想把 MQTT 当实时总线用，这些都是应用层必须补的东西。协议只负责把字节送过去。

八、遗嘱消息与保留消息 #

这两个特性容易被混在一起讲，其实解决的是完全不同的问题。遗嘱管「掉线怎么通知别人」，保留管「新来的怎么知道当前状态」。

遗嘱消息（Will） #

客户端在 CONNECT 报文里预先登记一条遗嘱：一个 Topic、一段 Payload、一个 QoS、一个 RETAIN 标志。

登记的时机是连接建立时，遗嘱内容在 CONNECT 报文的 Payload 里。

触发的条件很关键，我们分清两种情况：

断开方式 遗嘱是否触发
客户端发 DISCONNECT 正常断开 不触发，遗嘱被丢弃
Keep Alive 超时 触发
TCP 连接被 RST 或异常关闭 触发
客户端网络断开（断电、断网、飞行模式） 触发（靠心跳超时发现）
Broker 认为协议错误，关闭连接 触发
Broker 自身重启 取决于实现，不保证

正常断开不触发，这个设计是对的：主动下线不该被当成故障告警。

典型用法是设备上下线通知：

text
设备 CONNECT 时登记：
  Will Topic   = device/sensor42/status
  Will Payload = {"online":false,"reason":"lost"}
  Will QoS     = 1
  Will Retain  = true

设备上电后自己再发一条：
  Topic   = device/sensor42/status
  Payload = {"online":true}
  QoS     = 1
  Retain  = true

监控端订阅 device/+/status，就能收到完整的上下线事件流。设备正常上线时发 online，掉线时 Broker 代发 offline。

注意遗嘱只能登记一条，而且只在 CONNECT 时设，连接期间不能改。想让不同故障发不同遗嘱，做不到，得在 Payload 里自己写清楚，或者用多个 Topic 由服务端推断。

遗嘱的 QoS 和 RETAIN 是独立的。设 Will Retain = true 时，这条遗嘱也会被存成保留消息，后订阅的人一上来就看到「该设备离线」。

保留消息（Retained） #

保留消息解决的是「新订阅者不知道当前值」的问题。

正常情况：订阅者连上之前发布的那些消息，它一概收不到。它得等到下一次发布才知道状态。

保留消息改掉这个：Broker 为每个 Topic 保存最后一条 RETAIN=1 的消息。任何新订阅者订阅该 Topic（或匹配的筛选器）时，Broker 立刻把这条推给它。

text
t0  设备发布 temp/room1 = 23.5 (RETAIN=1)     → Broker 存下
t1  设备发布 temp/room1 = 23.8 (RETAIN=1)     → Broker 覆盖为 23.8
t2  新订阅者订阅 temp/room1                    → 立刻收到 23.8

规则要记清：

  • 每个 Topic 只保留一条。新的一条覆盖旧的，不累积。
  • Broker 只按 Topic 精确存储。它不会为一个订阅筛选器构造一条汇总消息。
  • 通配符订阅会收到多条。订阅 temp/# 时，Broker 会把所有匹配的保留消息各推一条过来，Topic 各不相同。
  • 收到时 RETAIN 标志为 1，订阅者可以据此区分「历史值」和「实时值」。
  • 发一条空 Payload 且 RETAIN=1 的消息可以清除保留。这是标准的清除方式。

清除的写法：

text
Topic   = temp/room1
Payload = （长度为 0）
QoS     = 1
Retain  = true

很多客户端库会对空 Payload 做特殊处理，发不出去。遇到这种情况，直接把库的 API 换成底层 publish 并显式给空字节数组。

两个特性的对照 #

维度 遗嘱消息 保留消息
谁登记 客户端在 CONNECT 时 任何发布者
谁发送 Broker，在异常断开时代发 Broker，在新订阅时补发
触发时机 客户端异常掉线 有新的订阅建立
保存几条 每个连接一条 每个 Topic 一条
主要用途 掉线告警 状态快照
生命周期 连接期间生效，正常断开即丢弃 一直存在，直到被覆盖或清除

组合起来用效果最好：设备上线发 online:true（RETAIN），并登记一条 online:false 的遗嘱（RETAIN）。监控端不管什么时候订阅，都能立刻拿到当前状态，且后续变化持续推送。这就是「设备影子」思路的最简实现。

一个坑 #

保留消息不清会一直占着内存，而且会误导新订阅者。设备下线后如果没人清 online:true，新来的监控端会以为它还活着。

处理方式只有两条：靠遗嘱把状态刷成 false，或者在上线时用带时间戳的 Payload，让消费端自己判断这条状态过期了多久。

九、心跳与掉线检测 #

TCP 连接看起来是长连接，实际上中间隔着 NAT、防火墙、运营商网关，这些设备都会悄悄丢弃空闲连接。等你下次真要发数据了，才发现连接早就死了。

MQTT 用 Keep Alive 解决这个。

机制 #

CONNECT 报文里有一个 Keep Alive 字段，单位是秒，取值范围 0~65535。设为非 0 时：

  • 客户端：在 Keep Alive 时间内没有向 Broker 发送任何其它报文（PUBLISH、SUBSCRIBE 等），就必须发一个 PINGREQ。
  • Broker：收到 PINGREQ 后回 PINGRESP。
text
Client                        Broker
   │                            │
   │  （Keep Alive 内发了数据，不用 PING）
   │── PUBLISH ────────────────▶│
   │                            │
   │  （空闲了，快到 Keep Alive 了）
   │── PINGREQ ────────────────▶│
   │◀──────────────── PINGRESP ─│
   │                            │
   │  （又空闲，再 ping）
   │── PINGREQ ────────────────▶│
   │◀──────────────── PINGRESP ─│

1.5 倍这个判断 #

Broker 侧的判断标准是：1.5 倍 Keep Alive 时间内没收到该客户端的任何报文，就认定它掉线，关闭连接并触发遗嘱。

为什么是 1.5 倍而不是 1 倍？因为要给网络留一个 RTT 的余量。客户端在第 1.0 倍的时间点发出 PINGREQ，这个包要花时间才能到 Broker。如果 Broker 卡在正好 1.0 倍就超时，所有正常客户端都会莫名掉线。

1.5 倍是规范给的建议值，具体实现可以配得更宽松，但不能更严（更严会误杀）。

举个例子，Keep Alive = 60 秒：

text
t=0     客户端发 PINGREQ
t=0.2   Broker 收到，回 PINGRESP
t=60    客户端该发下一个 PINGREQ 了
t=90    Broker 还没收到任何报文 → 判定掉线（60 × 1.5）

客户端侧的判断不同：它不判断「掉线」，它只看 PINGRESP 有没有回来。在设定时间内没收到 PINGRESP，客户端自己应主动关闭 TCP 连接并重连。

取值怎么定 #

Keep Alive 太短，心跳包浪费带宽和电量；太长，掉线发现得慢。

Keep Alive 掉线发现时间 适用
0 永不检测 只在稳定内网用，等于放弃遗嘱能力
10 秒 15 秒 强实时的控制类设备，但耗电
30 秒 45 秒 常见折中值
60 秒 90 秒 电池供电的传感器
300 秒 450 秒 极低功耗，容忍长时间才发现掉线

一个实用的估算：取你的业务能容忍的掉线发现时间，除以 1.5，就是上限。

另外，心跳包本身很小（PINGREQ 和 PINGRESP 各 2 字节），带宽不是问题，电量才是。电池设备每 30 秒醒一次跟每 5 分钟醒一次，续航差好几倍。

Keep Alive 设为 0 的含义 #

设为 0 表示关闭 Keep Alive 机制。Broker 不会因为空闲而判定掉线，遗嘱也就永远不会因为心跳超时触发。

这个配置在实内网、有其它保活手段时可以接受。但在移动网络下几乎等于灾难：NAT 表项老化后连接被静默丢弃，双方都不知道，直到下次发数据才发现，中间这段时间的消息全丢，遗嘱也没发出去。

还有一层：MQTT 心跳不替代 TCP keepalive #

两级保活是不同层次的：

机制 层次 能发现什么
TCP keepalive 传输层 对端主机彻底不可达
MQTT PINGREQ 应用层 对端进程不响应，或链路单向故障

TCP keepalive 的默认间隔动辄两小时，远水不解近火。而且 TCP keepalive 探不通只说明 TCP 层有问题，Broker 进程卡死但 TCP 栈还在响应的情况，只有 MQTT 层的 PINGRESP 才能发现。所以两者都要，不能互相替代。

十、会话与离线消息 #

会话是 MQTT 里最容易被忽略、又最影响可靠性的概念。

会话里存什么 #

一个会话（Session）跟一个 ClientID 绑定，包含四样东西：

  1. 订阅关系：这个客户端订了哪些 Topic Filter、各自的 QoS。
  2. 未完成的 QoS 1 / QoS 2 消息：等着重传的那些。
  3. 离线消息队列：客户端不在线期间，匹配它订阅的 QoS > 0 消息。
  4. 待发出的消息：Broker 正在往它推、还没确认的那些。

订阅关系属于会话，不属于连接。连接断了，只要会话还在，订阅就还在。

Clean Session 两个取值 #

CONNECT 报文里有一个 Clean Session 标志。

取值 行为
CleanSession = 1 每次连接都新建会话。Broker 丢弃该 ClientID 之前的全部状态：订阅、未确认消息、离线队列
CleanSession = 0 恢复该 ClientID 的已存在会话。没有则新建，有则接着用

CleanSession = 1 是很多客户端库的默认值，也是很多「消息莫名丢了」的根因。

text
CleanSession = 1 的重连过程：

  设备断开  →  Broker 立刻删除会话（订阅没了，队列没了）
  设备重连  →  全新会话，必须重新 SUBSCRIBE
  断开期间的消息  →  全部丢失，不会补发

text
CleanSession = 0 的重连过程：

  设备断开  →  Broker 保留会话，继续把匹配的 QoS>0 消息排进离线队列
  设备重连  →  恢复会话，Broker 把队列里的消息补发出去
  订阅关系  →  自动恢复，不用重新 SUBSCRIBE

用持久会话必须做对三件事 #

这三件漏一件，CleanSession = 0 就等于没生效。

  1. ClientID 必须固定且唯一。用随机 UUID 当 ClientID，每次重连都是新身份，旧会话永远找不回来。用固定字符串，又会在两台设备上撞车——后连的会把先连的踢下线（这是规范行为，正常现象，但常被误判为「连接不稳定」）。

  2. 所有订阅的 QoS 必须大于 0。离线队列只存 QoS 1 和 QoS 2 的消息。订阅时写 QoS 0，离线期间的 QoS 0 消息一条都不留，因为协议本来就不承诺它。

  3. 订阅要重新确认，别依赖自动恢复。规范要求恢复会话时订阅仍然生效，但部分实现在会话过期、Broker 重启、集群节点迁移后会丢订阅。稳妥做法：每次连上之后无条件重发一遍 SUBSCRIBE，幂等，成本极低。

离线队列不是无限的 #

Broker 不会为离线设备无限攒消息，否则一个僵尸设备就能撑爆内存。实现上会设几道限制：

  • 队列长度上限（条数）
  • 队列总字节上限
  • 消息保留时长
  • 会话过期时间

超出之后，新消息被丢弃，或者最旧的被挤出。这些参数由 Broker 配置决定，不在协议里。用持久会话之前，先去确认你用的 Broker 这几项默认值是多少。

一个反直觉的点 #

持久会话不是「消息不会丢」的保证，它只是「重连后能补发」的机制。补发了多少条、有没有因为队列满被截断、会话还在不在存续期内，全都得你自己确认。

真正在意一条都不能丢的场景，标准做法是双层：MQTT 负责唤醒与推送，落库确认走另一条可靠路径（比如上线后调一次 HTTP 批量拉取缺失区间的数据）。

十一、报文类型与连接过程 #

MQTT 3.1.1 一共 14 种报文类型，编号 1~14，占固定头的第一个字节的高 4 位。

编号 报文 方向 作用 QoS 关联
1 CONNECT 客户端 → Broker 建立连接，带 ClientID、Keep Alive、Will、用户名密码 —
2 CONNACK Broker → 客户端 连接确认，带返回码和 Session Present 标志 —
3 PUBLISH 双向 发布消息 QoS 0/1/2
4 PUBACK 双向 QoS 1 的发布确认 QoS 1
5 PUBREC 双向 QoS 2 第一步确认，表示已收到 QoS 2
6 PUBREL 双向 QoS 2 第二步，释放消息 QoS 2
7 PUBCOMP 双向 QoS 2 第三步确认，握手结束 QoS 2
8 SUBSCRIBE 客户端 → Broker 订阅，可一次带多个 Topic Filter QoS 0/1/2
9 SUBACK Broker → 客户端 订阅确认，逐个返回授予的 QoS 或失败码 —
10 UNSUBSCRIBE 客户端 → Broker 退订 —
11 UNSUBACK Broker → 客户端 退订确认 —
12 PINGREQ 客户端 → Broker 心跳请求 —
13 PINGRESP Broker → 客户端 心跳响应 —
14 DISCONNECT 客户端 → Broker 正常断开，指示丢弃遗嘱 —

几个要点：

  • 只有 PUBLISH、PUBACK、PUBREC、PUBREL、PUBCOMP、SUBSCRIBE、SUBACK、UNSUBSCRIBE、UNSUBACK 带 PacketID。CONNECT、PINGREQ 这些没有。
  • SUBACK 返回的是「授予的 QoS」，可以低于你请求的 QoS。返回 0x80 表示该 Topic Filter 订阅失败。
  • 没有 Broker → 客户端的 DISCONNECT。Broker 要断你，直接关 TCP。
  • 没有「查询订阅列表」的报文。客户端想知道自己订了什么，只能自己记。

完整连接过程 #

text
Client                                    Broker
  │                                          │
  │  TCP 三次握手（1883 / 8883 / 8083）        │
  │◀────────────────────────────────────────▶│
  │                                          │
  │── CONNECT（ClientID, KeepAlive=60,      │
  │            CleanSession=0,              │
  │            Will Topic/Payload/QoS/Retain,│
  │            username, password）─────────▶│
  │                                          │  认证、检查 ClientID 冲突、
  │                                          │  恢复或新建会话、登记遗嘱
  │◀── CONNACK（return code=0,              │
  │            session present=1）───────────│
  │                                          │
  │── SUBSCRIBE（topic/+/temp, QoS=1,        │
  │              packetID=1）───────────────▶│
  │◀── SUBACK（packetID=1, granted QoS=1）───│
  │                                          │
  │◀── PUBLISH（QoS 1, packetID=3, payload）─│   开始收到匹配消息
  │── PUBACK（packetID=3）──────────────────▶│
  │                                          │
  │  ... 业务收发 ...                          │
  │                                          │
  │── PINGREQ ──────────────────────────────▶│
  │◀───────────────────────────── PINGRESP ──│
  │                                          │
  │── DISCONNECT ───────────────────────────▶│   丢弃遗嘱，保留会话
  │  TCP 关闭                                 │

CONNACK 的返回码里，0x00 是接受，0x01 协议版本不支持，0x02 ClientID 被拒，0x03 服务不可用，0x04 用户名或密码错，0x05 未授权。

session present 这个标志很有用：为 1 说明 Broker 恢复了旧会话（订阅还在），为 0 说明是全新会话（必须重新订阅）。用它判断要不要重发 SUBSCRIBE，比自己猜可靠。

一次完整的 QoS 2 端到端 #

把前面几节的碎片拼起来，看一条 QoS 2 消息从发布者到订阅者，报文层面的全貌：

text
Publisher            Broker            Subscriber
    │                   │                   │
    │─PUBLISH id=9 ────▶│                   │
    │◀─────── PUBREC ───│                   │
    │─PUBREL id=9 ─────▶│                   │
    │                   │─PUBLISH id=21 ───▶│
    │                   │◀─────── PUBREC ───│
    │                   │─PUBREL id=21 ────▶│
    │◀────── PUBCOMP ───│                   │
    │                   │◀────── PUBCOMP ───│

8 个报文，两个独立的四次握手，PacketID 在两个方向上各自独立编号（9 和 21 没关系）。这就是 QoS 2 的真实成本。

端口与安全 #

端口 传输 说明
1883 TCP 明文 标准 MQTT 端口，仅内网或已由上层加密时使用
8883 TCP + TLS 标准 MQTT over TLS 端口，生产环境默认选它
8083 WebSocket MQTT over WebSocket，供浏览器直连
8084 WebSocket + TLS MQTT over WSS
80 / 443 HTTP 伪装 部分云服务走 443 突破网络限制，非标准

认证方式两种：

  1. 用户名密码：写在 CONNECT 报文里。注意明文端口下密码是裸奔的，因为 MQTT 自己不加密载荷。
  2. 客户端证书：TLS 双向认证，客户端出示证书，Broker 校验。设备量大、无法安全保管密码的场景用这个。证书吊销比改密码麻烦，要提前想好轮换方案。

还有一层是授权，认证之后才有：认证解决「你是谁」，授权解决「你能发/订哪些 Topic」。基于 ClientID 或用户名做 Topic 前缀限制（设备只能往 device/{自己的ID}/# 发）是必须配的，否则任何一台设备能冒充任何一台。

记住一点：MQTT 协议本身不提供加密。加密全靠 TLS 那层，端口选 1883 就是明文。

十二、易错点速查 #

把前面散落的坑集中成一张表。左边是现象，中间是原因，右边是处理。

现象 原因 处理
新订阅的客户端收不到当前状态 只用了普通消息，没设 RETAIN 状态类数据发布时 RETAIN=1
设备掉线了但监控端不知道 没登记遗嘱，或 Keep Alive 设为 0 连上就登记 Will，Keep Alive 取非 0
设备主动下线也收到离线告警 遗嘱设计没区分正常/异常断开 正常下线上线各发一条状态，靠 Payload 区分
重连后订阅失效了 CleanSession=1，或 Broker 重启丢了会话 每次连上都重发 SUBSCRIBE
离线期间的消息没补发 订阅读 QoS 0，或 ClientID 每次都变 订阅 QoS > 0，ClientID 固定
消息重复导致计数错误 用了 QoS 1 但没做幂等 消息带唯一 ID 或版本号，消费端去重
订阅 QoS 2 还是丢消息 发布侧用了 QoS 0，取 min 后降级 两端都要设，确认 Broker 没配降级
上了 QoS 2 反而更慢 两个 RTT 的往返开销 除非确实不能重复，否则退回 QoS 1 + 幂等
消息顺序乱 重连、重传、混发不同 QoS 负载里带 seq 与 ts_ms，应用层重排
订阅 home/# 收不到 home 想当然以为 # 不含父层 # 实际包含父层本身，收不到是别的问题（如 $ 开头）
通配符订阅不生效 写成了 home/#/temp 或 home/room+ # 必须末尾且独层，+ 必须独层
$SYS 主题收不到 # 不匹配 $ 开头的 Topic 显式订阅 $SYS/#
Broker 频繁踢掉同一台设备 两台设备用了相同 ClientID ClientID 用设备唯一标识，别用固定常量
连接看起来活着但不收数据 NAT 老化把连接静默丢弃了 Keep Alive 别设 0，客户端等不到 PINGRESP 就重连
电量掉得很快 Keep Alive 太小，频繁唤醒 电池设备用 60~300 秒
报文被拒，连接被断 Topic 里有通配符，或超过长度限制 PUBLISH 的 Topic 不用 + #
大文件传不过去 单条消息受 Broker 最大报文限制 分片传，每片带偏移量
Broker 内存一直涨 保留消息越积越多，遗嘱 Topic 没人清 及时发空 Payload 清除，控制 Topic 数量
Broker 端设备数一多就卡 QoS 2 状态机占用大量内存 评估是否真需要 QoS 2

最后一条边界 #

MQTT 是传输层之上的消息管道，它保证的是「按约定尽力把字节送到」，不是业务语义。丢了要补、重了要去重、乱了要重排、实时要自己打时间戳，这四件事协议一件都不管。把这条想清楚，剩下全是配置和代码。
