本篇讲 ZeroMQ 这个库：它把 socket 编程抽象成几种固定的通信模式，以及这些模式在内部怎么跑起来。

讲什么：五种核心模式（REQ/REP、PUB/SUB、PUSH/PULL、DEALER/ROUTER、PAIR）、四种传输方式（inproc / ipc / tcp / pgm）、I/O 线程与 Poller 的内部结构、无 Broker 带来的好处与代价。

不讲什么：libzmq 的编译期裁剪、各语言绑定的安装细节、建在 ZMQ 之上的扩展协议（Majordomo、Zyre 这类）的设计取舍。构建步骤只在讲传输方式时顺带提一句，不展开。

跨篇指路：MQTT 那篇讲协议——报文格式固定，必须有 Broker 中转，Topic 是协议的一部分。通讯概念辨析那篇讲 socket、RPC、消息队列这些词的边界。本篇讲库——没有标准报文，没有中心节点，对端必须是 ZeroMQ。

一句话分清：MQTT 是大家共同遵守的规矩，ZeroMQ 是两个程序之间私下的约定。

一、ZeroMQ 是什么 #

ZeroMQ 是一个基于消息的多线程网络库。它把底层套接字类型、连接处理、数据帧、路由这些细节全部包起来，让你用同一套 API 跨多种传输协议发消息。

它的位置很有意思：夹在应用层和传输层之间。下面的 TCP/UDP 它照用，上面的消息语义它自己造。拿 TCP/IP 的四层划分去看，它既不属于传输层，也不是完整的应用层协议，更像是「应用层的一部分，只是被做成了库」。

它到底抽象掉了什么 #

裸写 socket 的时候，每一件事都要你自己做：

  • 连接管理：谁 listen，谁 connect，accept 之后 fd 怎么存
  • 重连：对端挂了，退避多久重试，重试几次放弃
  • 消息边界：TCP 是字节流，你发两个 100 字节的包，对端收到一次 200 字节，得自己定长度前缀
  • 多对多路由：三个生产者对五个消费者，谁分给谁
  • 线程安全：socket 能不能跨线程用

ZeroMQ 把这些全部收进库内部。你剩下的工作只有两件：选一个模式，收发消息。

c
/* 裸 socket 的服务器：listen / accept / 自己拆包 / 自己管连接 */
int fd = socket(AF_INET, SOCK_STREAM, 0);
bind(fd, ...);
listen(fd, 128);
while (1) {
    int c = accept(fd, ...);        /* 每个客户端一个 fd，自己存 */
    /* 读到的是一串字节，在哪断开？自己定协议 */
}

同样的东西，用 ZeroMQ 写：

c
void *ctx  = zmq_ctx_new();
void *sock = zmq_socket(ctx, ZMQ_REP);
zmq_bind(sock, "tcp://*:5555");

while (1) {
    char buf[256];
    zmq_recv(sock, buf, sizeof(buf), 0);   /* 一次调用就是一条完整消息 */
    zmq_send(sock, "ok", 2, 0);
}

没有 accept，没有 fd 数组，没有拆包。zmq_recv 一次返回的就是一条完整消息——边界由库保证，不用你拼。

「选模式」是这个库的全部设计 #

别的网络库给你一堆函数，你自己组合成架构。ZeroMQ 反过来：它先替你把架构定成几种，你从中挑一个。

这个选择带来两件事。一件是省事——模式的坑有人替你踩过了，PUB/SUB 的扇出、PUSH/PULL 的负载均衡都是现成的。另一件是束手——模式之外的东西它不管，你要做模式没覆盖的事，就得自己加一层。

所以判断一个需求适不适合 ZeroMQ，问题不是「能不能连上」，而是「能不能塞进这五种模式之一」。塞得进去，代码很短；塞不进去，硬凑会比裸写 socket 更难受。

名字的来历 #

ZeroMQ 最早脱胎于 AMQP 相关的实现工作，后来走成了独立的一条线：不做 Broker，不做报文规范，只做库。名字里的 MQ 是那个阶段留下来的，跟今天的功能已经对不上。

这就是下一章要说的事：它不是消息队列。

二、它不是消息队列 #

第一次看到这个名字的人，脑子里多半浮出 RabbitMQ、Kafka 那种图：一堆客户端连到中间一个服务器，服务器存消息、转发消息、管队列。

ZeroMQ 没有那个中间服务器。

没有 Broker 进程 #

这是最硬的一条差别。ZeroMQ 的部署里，不存在一个需要单独启动、单独监控、单独扩容的中心进程。你的进程调 zmq_bind，另一个进程调 zmq_connect，消息就从内核直接过去。

text
RabbitMQ / Kafka：
  producer ──→ [ Broker 进程 ] ──→ consumer
                 ↑ 要部署、要监控、挂了全断

ZeroMQ：
  peer A ←──────── 直连 ────────→ peer B
       （tcp / ipc / inproc，中间没有第三者）

没有 Broker 意味着几件事：

维度 有 Broker（RabbitMQ / Kafka） 无 Broker（ZeroMQ）
部署 多一个必须运行的进程 只有你的程序本身
消息落盘 Broker 负责持久化 库不管，要自己做
服务发现 连 Broker 的地址就行 得自己知道对端在哪
单点故障 Broker 挂了全断 没有中心点可挂
跨语言互通 各语言连同一个 Broker 即可 对端也得是 ZeroMQ
运维 要盯队列深度、堆积、磁盘 没得盯，出事只看自己的日志

「MQ」在这里指什么 #

不指队列，指消息。ZeroMQ 处理的是消息（message）这个单位——一次发送就是一条消息，有明确边界，要么整条到，要么不到。它不负责替你决定收完之后放哪、满了丢不丢。

队列在 ZeroMQ 里只发生在内部：每个连接两端各有一对管道（inbound / outbound pipe），带高水位限制。水位满了，发送端要么阻塞要么丢弃——这取决于套接字类型，也取决于你设的选项。它不是给你当存储用的。

那它到底解决了什么问题 #

问题不在「消息存哪」，在「消息怎么走」。

分布式程序要并行，最直接的做法是共享状态加锁。锁一多，死锁、优先级反转、调试困难全来。换成消息传递，每个线程或进程只管自己那份状态，之间靠消息沟通，耦合度立刻降下来。

ZeroMQ 干的就是把「消息传递」这件事做成几行代码。你不必先架一个 Broker 才能让两个进程通上消息——这是它被大量采用的真实原因。

什么时候它不适用 #

  • 需要消息不丢、重启后还能重放：去找 Kafka 这类带日志的
  • 需要 Topic 订阅、通配符、QoS 分级：去找 MQTT Broker
  • 需要跨语言、跨团队、对端技术栈不受你控制：去找有标准协议的东西
  • 需要中心化的服务发现与鉴权：ZeroMQ 这块是空的

反过来，进程内多线程解耦、低延迟的进程间管道、内部服务的 N:M 扇出——这些场景里，ZeroMQ 的代码量和延迟都比架一套 Broker 低。

三、五种通信模式 #

模式是 ZeroMQ 的骨架。选错模式，后面写多少代码都别扭。

先把五种摊开看：

模式 方向 拓扑 有应答 谁 bind 典型用途
REQ/REP 双向，一问一答 1:N 或 N:1 有，严格配对 两侧都行 同步 RPC
PUB/SUB 单向，发布→订阅 1:N 无 PUB 端 广播、行情推送
PUSH/PULL 单向，推→拉 1:N 或 N:1 无 两侧都行 任务分发、流水线
DEALER/ROUTER 双向，异步 N:M 有，自己管 两侧都行 异步 RPC、代理
PAIR 双向，独占 1:1 无 两侧都行 线程或进程间的私线

看这张表的时候盯四个自由度：方向（单向还是双向）、扇出（能不能一对多、多对一、多对多）、应答（有没有请求回应这层语义）、独占（是不是只能有一个对端）。

这四件事决定了一切。模式一旦定了，连接管理、重连、消息边界、多对多路由这些活就全归库管，你只管收发。

谁 bind 谁 connect #

ZeroMQ 里 bind 和 connect 的语义跟 TCP 不完全一样：

  • 两侧都可以 bind，也都可以 connect，没有「服务器必须 listen」这条
  • connect 端可以在 bind 端还没起来的时候就 connect，库内部会自动重试，直到对面出现
  • 一个套接字可以 bind 多个端点，也可以 connect 多个端点

第二条尤其反直觉。你不用再操心启动顺序——先起的连后起的，照样能通。这条特性在容器编排里很实用，因为副本的启动顺序本来就没保证。

PAIR：一对一独占 #

PAIR 是五种模式里最不起眼的一个，规则也最简单：一个 PAIR 套接字只跟一个对端说话，双向，谁都能发。

c
void *a = zmq_socket(ctx, ZMQ_PAIR);
zmq_bind(a, "inproc://pair");       /* 或者 tcp / ipc */

void *b = zmq_socket(ctx, ZMQ_PAIR);
zmq_connect(b, "inproc://pair");

zmq_send(a, "ping", 4, 0);          /* 两边都能主动发 */

它没有应答语义，没有扇出，也没有身份路由。连第二个对端会失败——这是它的定义，不是缺陷。

用途很窄但很实在：

  • 两个线程之间的一条私线，比共享内存加锁干净
  • 父进程与刚 fork 出来的子进程之间的控制通道
  • 临时加一条旁路，不干扰主拓扑的模式

有一点要留意：PAIR 不做任何消息重排或去重，发多少收多少。如果一端比另一端快太多，高水位到了照样阻塞。它简单，但不「自动」帮你平衡。

关于 Device #

素材里提到的 Device（也叫 proxy），是 ZoneMQ 里把一种模式转成另一种的中间件。最经典的用法是 ROUTER 接 DEALER，把一个 1:N 的请求应答扩展成 N:M：

c
/* 一个极简的转发器：前端收请求，后端分发给 worker */
zmq_proxy(frontend, backend, NULL);   /* frontend: ROUTER, backend: DEALER */

一行 zmq_proxy 就能撑起一个 brokerless 的中间层。它不是独立进程，还是你的程序，只是套接字类型选得对。

选模式的顺序 #

拿到需求，按这个顺序问自己：

  1. 需要应答吗？不需要就往下走，需要就看是不是一问一答的同步语义
  2. 消息是一对多广播，还是分给某一个消费者？
  3. 生产者会不会有多个？消费者会不会有多个？
  4. 一个请求的往返能不能接受串行等待？

四个问题答完，模式基本就锁定了。答案对不上的时候，别硬套，先想清楚业务到底要什么。

四、REQ/REP 与它的限制 #

REQ/REP 是最容易上手的模式，也是最多人第一个撞墙的地方。

最小实现 #

请求端：

c
void *ctx  = zmq_ctx_new();
void *req  = zmq_socket(ctx, ZMQ_REQ);
zmq_connect(req, "tcp://127.0.0.1:5555");

zmq_send(req, "hello", 5, 0);
char buf[64];
zmq_recv(req, buf, sizeof(buf), 0);    /* 阻塞，直到对面答话 */

应答端：

c
void *rep = zmq_socket(ctx, ZMQ_REP);
zmq_bind(rep, "tcp://*:5555");

while (1) {
    char buf[64];
    zmq_recv(rep, buf, sizeof(buf), 0);
    zmq_send(rep, "world", 5, 0);      /* 必须回，不回就卡死 */
}

代码只有十来行，但里面有两条强制性的规矩：REQ 端发完必须收，REP 端收完必须发。这两条不是建议，是库强制的状态机。

严格同步的真相 #

REQ 和 REP 各有一个内部状态机，只认两种状态：

text
REQ 套接字：
  [可发送] --send--> [等待回应] --recv--> [可发送]

REP 套接字：
  [可接收] --recv--> [必须回应] --send--> [可接收]

在「等待回应」状态里再调 zmq_send，库会返回 -1，errno 是 EFSM（Operation cannot be accomplished in current state）。在「必须回应」状态里再调 zmq_recv，同样报 EFSM。

这条规矩的含义：一个 REQ 套接字在同一时刻只能有一个未完成的请求。发了第一个请求，没等到回应之前，你发不出第二个。

这个限制为什么让人难受 #

想一下真实场景：客户端要向同一台服务器发两个独立的查询，两个查询之间没有依赖关系，理论上可以并行。

用 REQ/REP，你只能写成串行：

c
zmq_send(req, q1, ...);   /* 发查询一 */
zmq_recv(req, buf, ...);  /* 等结果一 —— 这段时间空转 */
zmq_send(req, q2, ...);   /* 才能发查询二 */
zmq_recv(req, buf, ...);

两次往返时间相加。第一个请求飞出去、服务器处理、结果回来的这整段时间，客户端什么也干不了。还有更糟的：REP 端只要有一次忘了调 zmq_send，或者处理中途崩了，REQ 端就永久阻塞。ZeroMQ 不会给你超时报错，zmq_recv 就那么等着。想加超时，得自己设 ZMQ_RCVTIMEO 或者用 poller 轮询。

超时怎么写 #

c
int timeout = 3000;   /* 毫秒 */
zmq_setsockopt(req, ZMQ_RCVTIMEO, &timeout, sizeof(timeout));

int rc = zmq_recv(req, buf, sizeof(buf), 0);
if (rc == -1 && errno == EAGAIN) {
    /* 超时了。注意：此刻套接字状态还是「等待回应」，
       REQ 套接字没法靠 close 之外的手段复位 */
}

这里有个坑：REQ 套接字超时之后状态机没有复位，它仍然认为自己在等回应。想继续用这个套接字，常规做法是销毁重建，或者干脆换 DEALER。

1:N 怎么来的 #

REQ 端 connect 多个 REP 端点，或者 REP 端 bind 多个端点、多个 REQ 连上来——这两种都成立。REQ 侧的多个连接之间，请求是轮询分发的；REP 侧的多个客户端，回应会回到正确的那一个。

也就是说，REP 端天然处理「多个客户端各发各的」，但每个客户端自己仍然是串行的。1:N 说的是服务端能同时接多个客户端，不是说单个客户端能并行发多个请求。

什么时候该用它 #

  • 请求少、延迟不敏感的内部调用
  • 一次交互能解决的事，比如取一个配置、查一次状态
  • 学习或验证原型，代码最短

需要并发、需要流水线、需要超时后继续用同一套接字——换成 DEALER/ROUTER，这是第六章的内容。

五、PUB/SUB 与 PUSH/PULL #

这两个模式都是单向的，但用途差得很远。

PUB/SUB：广播 #

PUB 端只管发，不管有没有人听。SUB 端只管收，而且要先声明自己收什么。

c
/* 发布端 */
void *pub = zmq_socket(ctx, ZMQ_PUB);
zmq_bind(pub, "tcp://*:5556");
while (1) {
    zmq_send(pub, "tick 42", 7, 0);   /* 发完就不管了 */
}

/* 订阅端 */
void *sub = zmq_socket(ctx, ZMQ_SUB);
zmq_connect(sub, "tcp://127.0.0.1:5556");
zmq_setsockopt(sub, ZMQ_SUBSCRIBE, "", 0);   /* 空串 = 订阅全部 */
while (1) {
    char buf[64];
    zmq_recv(sub, buf, sizeof(buf), 0);
}

订阅过滤的机制 #

ZMQ_SUBSCRIBE 传的是一个前缀，不是正则，也不是通配符。"tick" 会匹配 tick 42、ticker，不会匹配 a tick。传空串匹配一切，不设任何订阅则一条也收不到——这个默认值坑过不少人。

过滤发生在订阅端，不在发布端。发布端把所有消息发给所有连上的订阅者，每条消息都要完整走一遍网络，订阅端在自己的进程里丢掉不匹配的。想靠 SUB 的过滤省带宽，做不到。

慢订阅者会被丢 #

PUB 端有一个高水位（ZMQ_SNDHWM，默认值在千条量级）。某个订阅者处理太慢，发往它的队列堆到水位，PUB 端就开始丢消息——丢给这个订阅者，不影响别人。这是设计选择：宁可丢，也不让一个慢节点拖垮整个发布端。

所以 PUB/SUB 适合「最新值有意义、旧值没意义」的场景：实时行情、传感器当前读数、状态广播。不适合「每条都不能丢」的场景，那种要么降速，要么自己加确认层。

连接时序也是坑 #

订阅端在发布端启动之前就连上，可以。但如果订阅端连上之后、发布端开始发之前，中间有消息过去了，订阅端收不到——因为订阅关系要经过一段时间的握手才生效。等待订阅者全部就位再开始发，常见做法是让 SUB 端反向发个「我准备好了」，或者干脆先睡一会儿。这类握手 ZeroMQ 不管，得你加。

PUSH/PULL：管道 #

PUSH 端往下游推，PULL 端从上游拉。方向固定，PUSH 只能发，PULL 只能收。

c
/* 上游：产生任务 */
void *push = zmq_socket(ctx, ZMQ_PUSH);
zmq_bind(push, "tcp://*:5557");
for (int i = 0; i < 1000; i++) {
    zmq_send(push, &i, sizeof(i), 0);
}

/* 下游：消费任务，可以起很多个 */
void *pull = zmq_socket(ctx, ZMQ_PULL);
zmq_connect(pull, "tcp://127.0.0.1:5557");
while (1) {
    int task;
    zmq_recv(pull, &task, sizeof(task), 0);
    /* 干活 */
}

它自带负载均衡 #

多个 PULL 端连到同一个 PUSH 端，任务会被均分给各个消费者。ZeroMQ 内部做的是轮询式分发，不是「谁空闲给谁」。所以下游每个任务耗时不一样的时候，分到手的活就不均匀。

这个特性让 PUSH/PULL 成了最常用的并行骨架：

text
              ┌──→ PULL worker 1
producer ──→ PUSH ├──→ PULL worker 2
              └──→ PULL worker 3

上游只管产生，下游想加就加。没有中心调度器，扩容就是多起一个 worker 进程。

反过来也能用 #

PULL 端 bind、PUSH 端 connect 同样成立。想要「worker 主动来找活干」，就让 worker 的 PULL 去 connect 一个固定的 PUSH 地址；想要「worker 在固定端口等」，就反过来。

多级管道也能串：PUSH → PULL 收下、处理、再 PUSH → 下一级 PULL。这就是流水线。

两者对比 #

维度 PUB/SUB PUSH/PULL
消息去向 广播给所有订阅者 分给其中一个消费者
是否丢消息 慢订阅者会被丢 水位满时阻塞或丢
过滤 订阅端按前缀过滤 无过滤
方向 PUB → SUB PUSH → PULL
典型用途 行情、状态广播 任务分发、流水线
扩容方式 多加订阅者（不减少发布端压力） 多加 worker（真分担）

记一条：要复制消息用 PUB/SUB，要分掉消息用 PUSH/PULL。这两个需求搞混，架构从一开始就是错的。

六、DEALER/ROUTER：异步应答 #

REQ/REP 的同步限制不是缺陷，是设计取舍。真要异步，ZeroMQ 给的答案是 DEALER 和 ROUTER。

这两个套接字做了什么 #

DEALER 和 ROUTER 是 REQ 和 REP 的「脱掉状态机」版本：

套接字 相当于 限制
DEALER 去掉收发配对的 REQ 可任意次收发，无 EFSM
ROUTER 去掉收发配对的 REP，且带身份路由 可任意次收发，知道对端身份

DEALER 想发几次发几次，想什么时候收什么时候收。这就是异步的入口。

ROUTER 的身份信封 #

ROUTER 最特别的地方：每条收到的消息前面，库会自动塞一个身份帧（identity frame），标识这条消息来自哪个连接。回消息的时候，把这个身份帧原样带上，ROUTER 就把它送回对应那一条连接。

c
/* ROUTER 端：收两条帧，第一条是身份，第二条才是内容 */
char ident[64]; char body[256];
zmq_recv(router, ident, sizeof(ident), 0);
zmq_recv(router, body, sizeof(body), 0);

/* 回应：先发身份，再发内容，顺序不能反 */
zmq_send(router, ident, strlen(ident), ZMQ_SNDMORE);
zmq_send(router, reply, strlen(reply), 0);

ZMQ_SNDMORE 是这里的关键：一条逻辑消息可以由多个帧组成，库里保证它们要么整组到、要么整组不到，不会被别的连接的消息插进中间。多帧消息是 ZeroMQ 里唯一可靠的「打包」手段。

一个异步客户端的骨架 #

c
void *dealer = zmq_socket(ctx, ZMQ_DEALER);
zmq_connect(dealer, "tcp://127.0.0.1:5555");

/* 一口气发三个请求，不等回应 */
for (int i = 0; i < 3; i++) {
    zmq_send(dealer, &reqs[i], sizeof(reqs[i]), 0);
}

/* 然后按到达顺序收，收到几个算几个 */
for (int i = 0; i < 3; i++) {
    int r;
    zmq_recv(dealer, &r, sizeof(r), 0);
    /* 处理，注意这里不保证和发送顺序一一对应 */
}

注意最后那句：回应到达的顺序跟请求发出的顺序不保证一致，除非对端是严格串行处理的。要在乱序回应里对上号，得自己在消息体里带请求 ID。

ROUTER + DEALER 撑起 N:M #

这是最经典的一段组合拳。ROUTER 面对客户端（每个客户端一个身份），DEALER 面对 worker 池（无状态，随便分），中间由 zmq_proxy 打通：

c
void *frontend = zmq_socket(ctx, ZMQ_ROUTER);
void *backend  = zmq_socket(ctx, ZMQ_DEALER);
zmq_bind(frontend, "tcp://*:5555");
zmq_bind(backend,  "tcp://*:5556");

zmq_proxy(frontend, backend, NULL);   /* 一直跑，直到进程结束 */

客户端看到的是一个普通的请求应答接口，背后是一个能横向扩缩的 worker 池。这就是素材里说的「把 1:N 扩展成 N:M」，用一行函数实现。

状态机没了，责任就回来了 #

DEALER/ROUTER 给你自由，代价是几件事得自己管：

  • 超时：没有内建超时，ZMQ_RCVTIMEO 或 poller 自己上
  • 请求与回应的配对：消息体里带 ID，自己维护一张待回表
  • 对端存活检测：ZeroMQ 有心跳选项，但断线后的业务语义（重发还是放弃）得你定
  • 背压：高水位到了是阻塞还是丢，看你怎么设

一句话：REQ/REP 把复杂度藏在状态机里，DEALER/ROUTER 把它还给你。中小规模用 REQ/REP 更省心，规模上去或者要异步，就得接受这份复杂度。

七、四种传输方式 #

ZeroMQ 的端点用类似 URL 的字符串写，格式是 协议://地址。库自己解析出协议、地址、端口，你不用碰 sockaddr。

text
inproc://name        进程内，线程之间
ipc:///tmp/name      进程间，走本机文件系统
tcp://host:port      机器间，走 TCP
pgm://iface;addr     组播，一对多

四种传输的定位 #

传输 作用域 底层 速度 跨越主机
inproc 同一进程内的线程 内存拷贝 最快 否
ipc 同一台机器的进程 UNIX 域套接字 快 否
tcp 任意可达主机 TCP 受网络限制 是
pgm 局域网组播 PGM / UDP 封装 取决于网络 是（限组播域）

inproc 为什么最快 #

inproc:// 不经过内核。发消息时，库把消息的所有权从发送线程的队列转移到接收线程的队列，没有系统调用，没有上下文切换，没有序列化。

有一条硬限制：inproc 的 bind 必须先于 connect。因为它本质上是在同一进程的套接字注册表里查名字，名字还没注册，连接就失败了，而且不会重试成功。这点跟 tcp 完全相反——tcp 的 connect 可以先于 bind，库会一直重试。这个差异踩过一次就记住了。

inproc 适合的场景：把本来要跨线程共享状态的代码，改成消息传递。多线程写锁的痛苦，换成一对 PUSH/PULL 就没了。

ipc 的路径写法 #

UNIX 域套接字，端点后面接绝对路径：

c
zmq_bind(sock, "ipc:///tmp/worker.ipc");

注意是三个斜杠：ipc:// 加上绝对路径 /tmp/...。少写一个斜杠，路径就变成相对的了。这条在 Linux 上表现为「连不上」，在 Windows 上 ipc 支持有限，跨平台代码里最好别依赖它。

ipc 比 tcp 快，因为绕过了整个 TCP/IP 协议栈和回环接口，但它只能在同一台机器上，而且权限走文件系统那一套。

tcp 的两个细节 #

c
zmq_bind(sock, "tcp://*:5555");        /* 绑所有网卡 */
zmq_bind(sock, "tcp://127.0.0.1:5555");/* 只绑回环 */
zmq_connect(sock, "tcp://10.0.0.5:5555");

* 表示所有网卡。想只让本机访问就绑 127.0.0.1，这一点跟普通 socket 一致。

tcp 上 ZeroMQ 会自己处理重连，默认的间隔是指数退避，上限在秒级。对端重启的这段时间里，zmq_send 不会失败，消息进了本地队列等着。这意味着——对端不在的时候你照样「发成功了」，别拿 zmq_send 的返回值当送达确认。

pgm 的适用面 #

PGM 是可靠组播协议，用在「一个发布者、很多订阅者、都在同一个局域网」的场景，比如机房里的行情分发。它的可靠性靠 NAK 重传实现，不是 TCP 那种逐连接确认。

pgm 需要网络设备配合（交换机要开组播），跨公网基本不可用。实际项目里用得少，知道有这个东西就行。

一份代码换端点 #

传输方式的最大好处：换传输不用改代码。开发时用 inproc，测试用 ipc，上线用 tcp，改的只是一个字符串。

c
const char *ep = getenv("ZMQ_EP");     /* inproc://x / ipc:///tmp/x / tcp://*:5555 */
zmq_bind(sock, ep);

把端点做成配置项，本地调试和部署就能用同一套二进制。

顺带说构建 #

要用这些传输，先得有库。

UNIX 类系统上的流程：确认 libtool、pkg-config、build-essential、autoconf、automake 都在；检查 uuid-dev 包或等效的 RPM 是否已装（缺它 make 会在链接阶段报错）；解压 .tar.gz；跑 ./configure 再 make；要装到系统里就 sudo make install；Linux 上装完跑一次 sudo ldconfig，否则动态链接器找不到新库。

Windows 上：需要 Visual Studio 2008 或更高版本；解压 .zip；在 Visual C++ 里打开 builds\msvc\msvc.sln；编译解决方案；产物在 lib 子目录下。

多数语言有现成的绑定包，能跳过这一步。自己编译主要为了控制版本和编译选项。

八、内部架构：I/O 线程与 Poller #

这一章是素材里最硬的部分，也是最容易被略过的部分。不理解内部结构，前面那些模式的行为就只能靠背。

一切从 zmq_init 开始 #

调 zmq_ctx_new() 的时候，ZeroMQ 创建一个上下文（context）。上下文里可以带参数，其中一个就是 I/O 线程的数量：

c
void *ctx = zmq_ctx_new();
zmq_ctx_set(ctx, ZMQ_IO_THREADS, 4);   /* 4 个 I/O 线程 */

素材里说的「调用 zmq_init 时根据传入参数创建对应数量的 I/O 线程」，讲的就是这件事。默认值是 1 个 I/O 线程，这个数字对吞吐影响很大——单线程的 I/O 在跑满一个核之后就成了瓶颈，加线程能上去。

但也不是越多越好。每个 I/O 线程有自己的 Poller、自己的事件循环，线程间的消息传递要跨队列。线程数超过实际并发连接数能带来的收益，只会增加调度开销。经验上按核数走，别超过连接数。

主线程与 I/O 线程分工 #

text
┌─────────────────────────────────────────────┐
│ 你的线程（主线程 / 应用线程）                  │
│   zmq_send / zmq_recv  ← 只碰队列，不碰网络    │
└──────────────┬──────────────────────────────┘
               │  Mail Box（进程内的消息队列）
┌──────────────┴──────────────────────────────┐
│ I/O 线程（可多个）                            │
│   Poller ── Reactor 循环 ── 读写内核 socket   │
└─────────────────────────────────────────────┘

关键在于：应用线程从来不直接做网络 I/O。你调 zmq_send，消息被塞进队列就返回了；真正的 send() 由 I/O 线程完成。你调 zmq_recv，如果没有消息就阻塞在条件变量上，等 I/O 线程收完放进队列再唤醒。

这就是素材里那句「几乎所有的 I/O 操作都是异步的，从而确保主线程不会被阻塞」的实际含义。

Poller 与 Reactor #

每个 I/O 线程配一个 Poller。Poller 是经典的 Reactor 模式实现：

  1. 把所有关心的文件描述符注册进去
  2. 调用 poll/epoll_wait/kqueue 之类的系统调用，阻塞等待
  3. 有事件就绪，返回事件列表
  4. 逐个分发到对应的处理器（读、写、连接建立、连接关闭）

选哪套系统调用，取决于平台和编译时的探测结果：

平台 / 条件 使用的机制
Linux epoll
macOS / BSD kqueue
Solaris devpoll / poll
Windows IOCP（完成端口）
兜底 select

select 是最后的选择，因为它有文件描述符数量上限且有 O(n) 的扫描开销。能用 epoll 的地方不会退到 select。

Reactor 的价值在于「一个线程管很多连接」。事件循环不阻塞在任何单个连接上，谁有事就处理谁。这也是为什么 1 个 I/O 线程能撑住成百上千条连接。

连接是怎么建立起来的 #

素材里这段流程讲得很清楚，展开成时序：

  1. 你调 zmq_bind 或 zmq_connect
  2. 主线程创建 zmq_listener（bind 时）或 zmq_connecter（connect 时）对象
  3. 通过 Mail Box 把这个对象交给某个 I/O 线程
  4. I/O 线程把它加入自己的 Poller，开始监听可读/可写事件
  5. 连接建立后，双方做一次握手，交换身份标识
  6. 握手成功，为这条连接创建一个 Session
  7. Session 关联一对管道（inbound pipe / outbound pipe）

之后的收发，主线程只需要读写管道，完全不关心底下是 tcp 还是 ipc。

Session、Engine、管道 #

素材里还提到一层很多人忽略的结构：Session 不直接跟内核交换数据，中间隔着一个 Engine。

text
应用线程
   │  zmq_send / zmq_recv
   ▼
 管道（pipe，无锁队列）
   │
   ▼
 Session  ←── 协议语义层（消息边界、多帧组装、身份）
   │
   ▼
 Engine  ←── 传输适配层（读写 tcp / ipc / inproc）
   │
   ▼
内核 socket

分层的好处是：tcp 和 ipc 的差异被压在 Engine 里，Session 以上的逻辑不用改。想加一种新传输，主要工作就是写一个 Engine。

为什么线程数能调 #

因为 I/O 线程之间是独立的：各有一组 Poller、各管一批连接，共享的只有上下文里的少量全局状态。所以加线程能线性扩 I/O 能力，代价是应用线程与 I/O 线程之间的队列竞争会变多。

这也解释了一个常见现象：单 I/O 线程的程序跑满一个 CPU 核就上不去了，而 top 里看你的应用线程几乎空闲。瓶颈在 I/O 线程，不在你的业务代码。

九、消息在内部怎么流转 #

从一次 zmq_send 到对端 zmq_recv 返回，中间发生了这些事。

发送路径 #

text
1. 应用线程调 zmq_send
2. 库把数据拷进一个 zmq_msg_t（或直接引用，视 API 而定）
3. 检查目标连接的高水位：满了就阻塞或丢弃（看套接字类型和选项）
4. 消息挂到对应连接的 outbound pipe（无锁队列）
5. 唤醒 I/O 线程（或者 I/O 线程本来就在轮询，直接就看到）
6. I/O 线程从 pipe 取出消息
7. 加帧头（长度等），写进内核 socket
8. 内核发送

第 3 步的水位很关键。ZMQ_SNDHWM 控制的是「每个连接上允许积压多少条」。设太小，突发流量立刻触发阻塞或丢弃；设太大，内存吃不住。默认值在千条量级，够用但不算宽裕。

接收路径 #

text
1. I/O 线程被 Poller 唤醒，发现 socket 可读
2. 从内核读出字节，交给 Engine 还原成消息
3. Engine 把消息交给 Session（处理多帧、身份等语义）
4. Session 写进 inbound pipe
5. 唤醒阻塞在 zmq_recv 上的应用线程
6. 应用线程从 pipe 取出消息，返回

第 2 步是「消息边界」真正被实现的地方。TCP 给你的是一段字节流，Engine 靠帧头把字节流重新切成一条条消息。这就是你不用自己拆包的原因。

无锁队列在这里的角色 #

pipe 是无锁队列（lock-free queue），典型实现是单生产者单消费者（SPSC）的环形缓冲。

为什么能无锁：这条 pipe 的两端是固定的——一头只有应用线程在写，另一头只有某个 I/O 线程在读。既然生产者只有一个、消费者只有一个，就不需要互斥锁，靠原子操作加内存序就能保证正确。

代价是每条连接要一对 pipe（一个方向一个）。连接数上万的时候，这些队列本身的内存开销也要算进去。

多帧消息怎么走 #

带 ZMQ_SNDMORE 的消息，内部是一个消息组。库里保证这组消息连续地进入 pipe、连续地被写出，不会被其他连接的消息插进来。

接收端拿到第一个帧之后，可以用 zmq_msg_more() 判断后面还有没有。多帧的意义在于：它给了你一个原子的打包单位，而不用自己在消息体里拼长度前缀。

身份标识在哪一层 #

第六章讲 ROUTER 会自动加身份帧。这个身份是握手阶段协商出来的——素材里说的「第一次通信时用 zmq_init 发送身份标识进行认证」，就是这段。

身份默认是自动生成的随机串，也可以自己设：

c
zmq_setsockopt(sock, ZMQ_IDENTITY, "worker-7", 8);

给 worker 设固定身份，ROUTER 端就能认出「这条消息来自 worker-7」。这套机制只做标识，不做鉴权——它不验证身份的真假，别拿它当安全措施。

十、没有 Broker 的代价 #

第二章讲了没有 Broker 能省什么。这一章讲它要收什么账。

收获：延迟与部署 #

直连的路径是最短的：

text
有 Broker：A → Broker → B     两次网络往返（或一次入队+一次出队）
无 Broker：A → B              一次网络往返

一次中转听起来不多，但在高频调用的链路上会累加。Broker 还要做反序列化、路由查表，有时候还要落盘，这些开销 ZeroMQ 直接没有。单点的问题也没有了——Broker 是集群里最容易变成单点的一环，它挂的时候所有依赖它的服务一起哑。部署上也简单：不用先起中间件，不用配集群，不用管磁盘配额。

代价一：拓扑是静态的 #

这是最实在的代价。ZeroMQ 的端点必须在代码或配置里写死——tcp://10.0.0.5:5555 这串东西在编译或者启动时就得存在。对端换了 IP，你得改配置重启；对端扩了一台，新的那台得让所有人知道它在哪。想「按名字找服务」，ZeroMQ 不提供这套东西。

对比一下有 Broker 的世界：客户端只连一个固定地址，具体有几个后端、后端在哪，全由 Broker 决定。客户端完全不需要知道后端的存在。

要在 ZeroMQ 上补这块，常见做法是外挂：

做法 思路 代价
配置文件 端点列表写进文件，启动时读 改配置要重启或热加载
环境变量 容器编排注入端点 编排系统成了事实上的注册中心
自己写注册服务 一个 REQ/REP 或 PUB/SUB 的注册端点 又造了一个中心点
服务网格 / DNS 用外部设施解析 引入了新的复杂度
随机接入点 + 发现协议 扩展协议（如 Zyre）解决 非标准，团队要一起学

没有哪一条是「标准答案」。这就是无中心化架构的真实成本：自由换来了责任。

代价二：协议是你的私有约定 #

ZeroMQ 只保证「一条消息完整送达某个端点」，消息体里是什么，它不管。

要传一个结构体，序列化你自己做。要区分消息类型，自己在消息体里加类型字段。要有版本兼容，自己设计版本号。要做请求超时重发，自己实现重发逻辑。

有 Broker 的世界里，很多这类事由协议或者 Broker 的插件兜了：MQTT 有 Topic 和 QoS，AMQP 有 exchange 和 routing key，Kafka 有 partition 和 offset。ZeroMQ 一个都不给。

所以用它的时候，团队里得有人负责「消息格式规范」这件事。规范没定清楚，两个服务对接就会在各种边界上打架。

代价三：对端必须是 ZeroMQ #

这条最容易被低估。ZeroMQ 的握手、帧格式、订阅机制都是库自己的，不是公开标准。浏览器连不上它，curl 连不上它，一个用了别的库的服务也连不上它。

text
ZeroMQ 能连：任何链接了 libzmq 的程序
ZeroMQ 不能连：HTTP 客户端、MQTT 客户端、gRPC 客户端、裸 socket

要跟外部系统对接，中间得加一层转换——把 ZeroMQ 消息转成 HTTP 或者消息队列协议。这一层一旦加上，Broker 的那份复杂度又请回来了。

判断标准很直白：通信两端都是你能控制的程序，才适合用 ZeroMQ。

代价四：可观测性靠自己 #

没有 Broker，也就没有一个可以统看的中间层。想知道「现在积压了多少消息」「哪个消费者慢了」，ZeroMQ 不提供这类指标端点。

能拿到的是套接字级别的统计：

c
uint64_t msgs;
size_t len = sizeof(msgs);
zmq_getsockopt(sock, ZMQ_EVENTS, &msgs, &len);   /* 只看得到事件位 */

管道深度、每个对端的状况，得自己埋点。生产环境常见的做法是加一条 PUB 通道，专门发内部指标，再找个地方聚合。

怎么权衡 #

给一张判断表：

你的情况 倾向
通信两端都是自己写的，追求低延迟 ZeroMQ
需要跨团队、跨语言、对端不可控 上标准协议
需要消息持久化、重放、审计 上 Kafka 这类
拓扑会频繁变化、要动态扩缩 上 Broker 或外挂发现
进程内多线程解耦 ZeroMQ 的 inproc
设备侧低带宽、要 QoS 分级 MQTT

这个表不是二选一，很多系统两种都用：对外用 MQTT 或 HTTP，对内用 ZeroMQ 打通自己的服务。

十一、与 MQTT 的对比 #

这两个名字里都带 MQ，功能上也有重叠（都能做发布订阅），但它们的性质完全不同。混淆它们的代价是选错技术栈。

最根本的差别 #

MQTT 是协议，ZeroMQ 是库。

协议的意思是：报文格式写在规范里，任何实现只要照做就能互通。你可以用 C 写的客户端连 Java 写的 Broker，因为双方都遵守同一份文档。

库的意思是：行为由这个库的实现决定，另一端必须也用这个库。它没有公开的线格式规范，跨实现互通不是目标。

这决定了后面所有差异。

逐项对比 #

维度 MQTT ZeroMQ
性质 应用层协议（有规范文档） 编程库（无标准线格式）
中心节点 必须有 Broker 没有，节点直连
报文格式 固定，头部 2 字节起 自定义，消息体你说了算
通信模式 本质只有发布订阅一种 五种（REQ/REP、PUB/SUB、PUSH/PULL、DEALER/ROUTER、PAIR）
消息质量 QoS 0/1/2 三档 无内建语义，自己实现
跨语言 任何语言都有标准客户端 需链接 libzmq（多数语言有绑定，但对端也得是它）
会话保持 有 Session、遗嘱消息、保留消息 无，重连后状态要自己恢复
传输 TCP（及 WebSocket 等变体） inproc / ipc / tcp / pgm
设备侧适配 专为低带宽、不稳定网络设计 未针对弱网优化
发现机制 连 Broker 地址即可 端点需预先配置
部署成本 要架 Broker 并运维 只要你的程序
典型场景 物联网设备、传感器上报 内部服务通信、并行计算

关于「模式数量」的误解 #

有人看到 ZeroMQ 有五种模式，觉得它比 MQTT 灵活得多。这个判断只对一半。

MQTT 的发布订阅确实只有一种形态，但它把大量语义做进去了：Topic 层级和通配符、QoS 分级重传、保留消息、遗嘱消息、会话恢复。这些在 ZeroMQ 里全都没有，得自己写。

ZeroMQ 的模式多，是因为它把「怎么连」这件事拆得细；MQTT 的模式少，是因为它把「怎么保证送达」这件事做进了协议。前者给你结构自由度，后者给你语义保障。

名字里的 MQ 都是历史 #

两个名字都带 Message Queue，两个都不是传统意义上「存消息的队列」。MQTT 的 Broker 转发完就不留（保留消息是特例），ZeroMQ 连 Broker 都没有。

真正像消息队列的，是 Kafka、RabbitMQ 那些——消息能存、能堆、能重放。判断标准是：关掉消费者，消息还在不在？ 在，那是消息队列；不在，那只是消息传输。

选哪个 #

问题不是「哪个更好」，是「你的约束是什么」。

  • 对端有单片机、有电池、有弱网 → MQTT
  • 对端是自己写的一批服务，追求低延迟 → ZeroMQ
  • 需要跨组织对接、对方技术栈不明 → MQTT（或者 HTTP）
  • 需要动态扩缩、要中心化的可观测性 → MQTT 的 Broker 帮你想了一半
  • 进程内多线程要解耦 → ZeroMQ 的 inproc，没有第二个选择

一个系统里同时用两种是正常的。设备侧接 MQTT，服务内部用 ZeroMQ，交界处放一个桥接进程。

十二、易错点速查 #

都是实际会撞上的，按出现频率排。

模式相关 #

现象 原因 处理
zmq_send 返回 -1，errno 是 EFSM REQ 端在等回应时又发了请求 换 DEALER，或者拆成两个套接字
REP 端 zmq_recv 报 EFSM 上一个请求没收完就收下一个 每个请求必须配一次 zmq_send
SUB 端一条消息都收不到 忘了设 ZMQ_SUBSCRIBE 至少设一次，空串收全部
SUB 端收不到匹配的消息 订阅是前缀匹配，不是通配符 用 "tick" 而不是 "tick*"
PAIR 连第三个对端失败 PAIR 是独占的 1:1 想多对多用别的模式
客户端一直阻塞 REP 端没回或者崩了 设 ZMQ_RCVTIMEO

连接与端点 #

现象 原因 处理
inproc 连不上 bind 晚于 connect 先 bind，再 connect
ipc 连不上 路径少写斜杠，变成相对路径 写 ipc:///tmp/x 三个斜杠
zmq_send 成功但对端没收到 消息还在本地队列，对端未连上 别把返回值当送达确认
换机器后连不上 端点写死在配置里 把端点做成可配置项
Windows 上 ipc 报错 平台支持有限 跨平台代码别依赖 ipc

消息与流控 #

现象 原因 处理
慢订阅者丢消息 PUB 端高水位触发丢弃 调 ZMQ_SNDHWM，或者接受丢
内存一路涨 对端不在，消息堆在本地队列 设高水位上限，加对端存活检测
消息被拆成两半收到 用了 DEALER/ROUTER 却按单帧处理 多帧消息用 ZMQ_SNDMORE + 收全
回错了客户端 ROUTER 忘了把身份帧带回去 先发身份再发内容，顺序不能反
回应和请求对不上号 异步模式不保证顺序 消息体里带请求 ID

线程与生命周期 #

现象 原因 处理
程序卡在 zmq_ctx_term 还有套接字没关 先 zmq_close 所有套接字
跨线程用同一个套接字崩了 ZeroMQ 的套接字不是线程安全的 一个线程一个套接字
吞吐上不去，应用线程却空闲 I/O 线程数太少 zmq_ctx_set(ctx, ZMQ_IO_THREADS, n)
fork 之后行为异常 继承了父进程的上下文 子进程里重新建上下文

三条记牢 #

第一章说的那句话，值得在结尾再说一次：ZeroMQ 的价值是把 socket 编程抽象成通信模式。连接管理、重连、消息边界、多对多路由，这些活它都收了，你只要选一个模式、调 zmq_socket、收发消息。

顺带记住三条：

  1. 它不是消息队列，没有 Broker，不替你存消息
  2. 五种模式选错，后面怎么写都别扭
  3. 没有 Broker 意味着省了部署，也意味着拓扑、发现、序列化、可观测这些事全归你自己

把这三条想清楚，再回头看那些 API，就没什么难懂的了。
