这一篇只讲 HTTP 本身：请求怎么发、响应怎么回、连接怎么管。 不讲 HTTP/3 与 QUIC，不讲反向代理和 CDN 的调度策略，也不碰各家 Web 框架的路由实现。 HTTP 跑在 TCP 之上，套接字那一层的细节在前几篇；域名解析的报文格式在 DNS 那篇。 同目录另有 DHCP、SNMP、CWMP 三篇，管的是设备侧；HTTP 是应用侧最常用的那个。

一、一次 HTTP 请求的全过程 #

地址栏敲一个 URL，回车，页面出来。中间这几十到几百毫秒里发生的事，按顺序拆开是这样：

顺序 动作 归属
1 解析 URL，拆出 scheme、host、port、path 浏览器
2 域名换成 IP 地址 DNS
3 与目标 IP 的端口做 TCP 三次握手 TCP
4 客户端写出一段文本请求 HTTP
5 服务端解析请求，定位资源 HTTP
6 服务端写出状态行、头标、空行、数据 HTTP
7 客户端解析，按 HTML 语法渲染 浏览器

第 4 步到第 6 步，就是 HTTP 的全部舞台。

HTTP 的规则可以压成一句话：客户端发一段格式固定的文本，服务端回一段同样格式的文本。请求这段文本由四块拼成，依次是请求行、请求头标、一个空行、请求数据；响应这段文本也是四块，依次是状态行、响应头标、一个空行、响应数据。

一次完整交互在链路上就是这个样子：

http
GET /index.html HTTP/1.1
Host: www.myweb.com
User-Agent: Mozilla/5.0 (Windows NT 10.0)
Accept: text/html, application/json

服务端回：

http
HTTP/1.1 200 OK
Date: Apr 11 2006 15:32:08 GMT
Server: Apache/2.0.46(win32)
Content-Length: 119
Content-Type: text/html

<HTML>
<HEAD>
<LINK REL="stylesheet" HREF="index.css">
</HEAD>
<BODY>
<IMG SRC="image/logo.png">
</BODY>
</HTML>

注意那个空行。请求里空行之后什么都没有，说明没有请求体；响应里空行之后是 119 字节的 HTML，长度写在 Content-Length 里。

「文本」这两个字不是修辞。你可以用一条命令手工拼出请求，跳过浏览器：

bash
printf 'GET /index.html HTTP/1.1\r\nHost: www.myweb.com\r\n\r\n' | nc www.myweb.com 80

只要 \r\n 拼对了，服务器就认。这个特性让 HTTP 特别好抓、特别好调、特别好实现，也让它在三十多年里活成了基础设施。

代价是：HTTP 自己什么额外的事都不做。它不加密、不压缩、不保序、不重传，也不记状态。这些全被推给了下层和上层。

HTTP 不做的事 由谁补上 表现出来
不加密 TLS HTTPS，默认端口 443
不压缩 Content-Encoding / Transfer-Encoding 传输中用 gzip 或分块
不保序、不重传 TCP 字节流按序到达，丢了就重发
不做域名解析 DNS 先拿 IP 才能连
不记用户状态 Cookie / Session 会话靠额外字段挂上去

这个分工是 HTTP 的设计选择，不是缺陷。它让协议本身足够薄，薄到任何能写 socket 的语言几十行就能实现一个客户端。

还有一点要先说清：打开一个页面不是一次请求。上面那份 HTML 里引用了 index.css 和 image/logo.png，浏览器读完 HTML 之后要再发两次请求把它们取回来。碰上复杂页面，几十上百个请求是常态。所以「HTTP 性能」这个词，一半在单次请求的延迟，一半在请求的数量和并发。

二、连接建立与 DNS #

客户端要跟服务器说话，第一步是连到对方的 HTTP 端口。HTTP 的默认端口是 80，URL 里不写端口就用它。

URL 里也可以显式写端口，比如：

text
http://www.myweb.com:8080/index.html

一个 HTTP URL 拆开来是这几个部分：

部分 例子 说明
scheme http 决定默认端口和是否走 TLS
host www.myweb.com 要解析的域名，或直接写 IP
port 8080 省略时 http 用 80，https 用 443
path /index.html 请求行里出现的就是这一段
query ?id=7&page=2 跟在 path 后面，一起进请求行
fragment #top 只在浏览器内部用，不会发给服务器

端口是分层的信号：80 是明文 HTTP，443 是 HTTPS，8080、8443 是常见的备用端口。写代码时把端口写死成 80，换到 HTTPS 环境就会连不上。

连之前得先有 IP。域名到 IP 的那一步由 DNS 完成，查的是 A 记录（IPv4）或 AAAA 记录（IPv6）。这一步发生在 HTTP 之外，HTTP 报文里根本看不到域名解析的痕迹。

在 Java 里，一行代码同时做了 DNS 解析和 TCP 握手：

java
Socket socket = new Socket("www.myweb.com", 8080);

构造函数返回的时候，域名已经变成 IP，三次握手（SYN、SYN+ACK、ACK）已经完成，连接可用。三次握手本身要花掉一个往返多一点的时间，如果还要走 TLS，TLS 握手再叠上去。所以「第一次请求慢」不是错觉，慢在建连，不在传数据。

握手完成后拿到的是一个 Socket，对着它取两个流：

java
InputStream in = socket.getInputStream();
OutputStream out = socket.getOutputStream();

这两个流就是 HTTP 的全部输入输出通道。你往 out 里写那几行 ASCII 文本，从 in 里读回那几行 ASCII 文本。HTTP 不知道 TCP 怎么保证字节按序到达，TCP 也不关心这些字节是 HTTP 还是别的什么。

三、请求报文的结构 #

请求报文由四段构成，顺序固定，一段都不能少（请求数据可以为空）：

text
请求行 CRLF
请求头标 CRLF
...（若干行）
CRLF
请求数据（可选）

3.1 请求行 #

请求行由三部分构成，中间用单个空格隔开：

位置 内容 例子
第一段 请求方法 GET
第二段 请求 URI /index.html
第三段 HTTP 版本 HTTP/1.1

示例：

http
GET /index.html HTTP/1.1

这里有个容易踩的点：请求行里的 URI 是路径加查询串，不带 scheme 和 host。也就是说你不能写 GET http://www.myweb.com/index.html HTTP/1.1。host 那一半信息放在 Host 头里，HTTP/1.1 规定 Host 必须存在，缺了服务器会回 400。

3.2 请求头标 #

头标一行一个，格式是「关键字: 值」，冒号后面有一个空格，每行以 CRLF 结尾：

text
关键字: 值

常见的请求头标：

头标 作用 示例值
Host 目标主机与端口 www.myweb.com
User-Agent 客户端软件信息 Mozilla/5.0 (Windows NT 10.0)
Accept 客户端能处理的媒体类型 text/html, application/json
Accept-Language 期望的语言 zh-CN,zh;q=0.9
Content-Type 请求体的媒体类型 application/json
Content-Length 请求体的字节长度 34
Cookie 携带的会话标识 sid=abc123

两条规则要记住：头标名大小写不敏感，content-length 和 Content-Length 是同一个东西；头标值大小写敏感，text/html 不能写成 TEXT/HTML 还指望服务器认。

同一个头标能出现多次，等价于用逗号合并成一个。Accept: text/html 加 Accept: application/json，跟 Accept: text/html, application/json 效果一样。

3.3 空行 #

头标结束后必须有一个空行，也就是单独一个 CRLF。它的作用是告诉服务端「头标到此为止，后面要么是空，要么是数据」。

这个空行不是排版，是语法。少了它，服务端会把后面的内容当成头标继续解析，直到读满缓冲区或者超时。

3.4 请求数据 #

带请求体的方法（POST、PUT 等）在这一段放数据。这一段前面常常跟着两个头标：Content-Type 说明数据的媒体类型，Content-Length 说明数据的字节长度。

一个完整的 POST 请求：

http
POST /api/login HTTP/1.1
Host: www.myweb.com
User-Agent: Mozilla/5.0 (Windows NT 10.0)
Content-Type: application/json
Content-Length: 34

{"user":"alice","pass":"secret123"}

Content-Length: 34 这个数字要数准。它指的是请求体的字节数，不是字符数。中文在 UTF-8 里一个字符占三字节，按字符数写会短，服务端读不全就会一直等剩下的字节。

请求体的结束位置靠两种方式确定：

情况 服务端怎么判断体读完了
有 Content-Length 读满这么多字节就停
有 Transfer-Encoding: chunked 读到长度为 0 的那个块
两个都没有 只能靠对端关闭连接来定界，HTTP/1.1 里这属于异常

第三种情况是 HTTP 解析里的经典坑，后面讲头字段时还会展开。这里先记住：一个带体的请求，必须让服务端知道边界在哪。

四、请求方法与幂等性 #

前面的请求行示例里只出现了 GET。规范里定义的常用方法有八个：

方法 语义 有请求体 幂等 安全
GET 检索资源 不该有 是 是
HEAD 与 GET 相同，但只返回响应头 不该有 是 是
POST 提交数据给服务器处理 有 否 否
PUT 把数据上传到指定 URI，整体替换 有 是 否
DELETE 删除指定 URI 的资源 可有 是 否
OPTIONS 查询服务器支持的方法 无 是 是
TRACE 环回请求，用于诊断 无 是 是
CONNECT 建立网络连接的隧道（如 HTTPS） 无 否 否

三个概念要拆开看，它们经常被混成一句「GET 和 POST 的区别」。

安全说的是这个方法会不会改变服务器上的状态。GET、HEAD、OPTIONS、TRACE 是安全的，读一读而已；POST、PUT、DELETE 不安全，它们会写。

幂等说的是同一个请求执行一次和执行十次，服务器上的最终状态一样。PUT 幂等：PUT /user/1 {"name":"alice"} 执行几次，结果都是 alice。POST 不幂等：同一个订单提交两次，就是两笔订单。

可缓存是第三件事，看的是方法语义和响应头标，跟幂等不是一回事。

GET 和 POST 的差别，落到报文上看只有三处：

对比项 GET POST
参数位置 拼在 URI 的查询串里 放在请求体里
是否出现在日志 出现在访问日志和浏览器历史里 不在 URI 里，不进历史
典型用途 取数据 交数据

所以「GET 有长度限制」这个说法要加限定。限制来自浏览器、服务器或代理对 URI 长度的处理，不是规范里的数字。规范里对 URI 长度没有硬性上限。

HEAD 常被用来探活。它返回的头标跟 GET 一模一样，只是不带响应体。想知道一个文件多大、改没改过、是什么类型，发 HEAD 比发 GET 省带宽。

CONNECT 的用法特殊：客户端让代理开一条隧道，之后这条隧道里跑的是 TLS，HTTP 看不到里面的东西。这就是 HTTPS 走代理时的机制。

OPTIONS 还有一个现代用途：浏览器跨域时先发一个预检请求，问服务器允不允许这个方法、这些头标。这一步是 CORS 的基础，报文本身还是 OPTIONS。

写代码时有个习惯值得养成：不要把会改状态的操作放在 GET 里。「删除」用 GET /delete?id=7，看起来能用，但爬虫、预取、缓存、浏览器的自动重试都会替你执行一遍。这是 GET 语义被破坏后的典型事故。

五、响应报文的结构 #

服务器收到请求，解析出方法和路径，定位到资源，然后往套接字里写回一段文本。这段文本同样是四段：

text
状态行 CRLF
响应头标 CRLF
...（若干行）
CRLF
响应数据（可选）

5.1 状态行 #

状态行也由三段构成：

位置 内容 例子
第一段 HTTP 版本 HTTP/1.1
第二段 三位数字的状态码 200
第三段 原因短语 OK

示例：

http
HTTP/1.1 200 OK

原因短语是给人看的，程序判断结果只看那三位数字。HTTP/2 起原因短语干脆被去掉了，链路上只有 HTTP/2 200。

5.2 响应头标 #

响应头标的结构跟请求头标一样，作用不同：它描述响应本身、描述服务器、描述接下来那段数据。

头标 作用 示例值
Date 响应生成的时间 Apr 11 2006 15:32:08 GMT
Server 服务端软件标识 Apache/2.0.46(win32)
Content-Type 响应体的媒体类型 text/html
Content-Length 响应体的字节长度 119
Connection 连接管理意图 keep-alive
Cache-Control 缓存策略 max-age=3600
Set-Cookie 让客户端保存会话标识 sid=abc123; Path=/

Set-Cookie 可以出现多次，每个 Cookie 一行，不能合并成逗号分隔——因为它自己的值里就带逗号（比如 Expires=Wed, 21 Oct 2026 07:28:00 GMT）。这是 HTTP 头标合并规则的一个例外。

5.3 空行 #

响应头标之后的空行是分界线。它后面要么什么都不跟（204、304 这类没有响应体），要么跟着响应数据。

服务端写完头标忘了写这个空行，客户端会把响应体的头几个字节当头标解析，表现为一串莫名其妙的解析错误。

5.4 响应数据 #

实际返回的数据体。一段 HTML、一个 CSS 文件、一张 PNG 的二进制字节、一段 JSON，都在这个位置。

二进制数据也走同一套报文，区别只在 Content-Type。图片不是文本，但对 HTTP 来说它只是一串字节，长度由 Content-Length 说清。

5.5 实例：三个连续的请求 #

素材里的完整例子值得逐步走一遍，因为它同时展示了连接管理。

第一次请求，取主页面：

http
GET /index.html HTTP/1.1

http
HTTP/1.1 200 OK
Date: Apr 11 2006 15:32:08 GMT
Server: Apache/2.0.46(win32)
Content-Length: 119
Content-Type: text/html

<HTML>
<HEAD>
<LINK REL="stylesheet" HREF="index.css">
</HEAD>
<BODY>
<IMG SRC="image/logo.png">
</BODY>
</HTML>

第二次请求，取样式表：

http
GET /index.css HTTP/1.1

http
HTTP/1.1 200 OK
Date: Apr 11 2006 15:32:08 GMT
Server: Apache/2.0.46(win32)
Connection: Keep-alive, close
Content-Length: 70
Content-Type: text/plain

h3 {
    font-size: 20px;
    font-weight: bold;
    color: #005A9C;
}

第三次请求，取图片：

http
GET image/logo.png HTTP/1.1

http
HTTP/1.1 200 OK
Date: Apr 11 2006 15:32:08 GMT
Server: Apache/2.0.46(win32)
Connection: Keep-alive, close
Content-Length: 1280
Content-Type: image/png

{Binary image data follows}

三次请求，三个响应。Content-Length 分别是 119、70、1280，一个不多一个不少，客户端照这个数字读满就停。

Content-Type 分别是 text/html、text/plain、image/png。注意第二个给的是 text/plain——这是素材里那台老服务器的取值。浏览器拿到 CSS 的 text/plain，在标准模式下会拒绝应用；现代服务器返回 CSS 给的是 text/css。

Connection: Keep-alive, close 这一行有问题。它把两个互斥的指令写进了同一个头标，语义是自相矛盾的：到底是保持还是关闭，收方只能猜。正确的写法是单选一个：Connection: keep-alive 或 Connection: close。这个例子有价值的地方就在这儿——它是真实设备上会出现的脏报文，也是排查连接被意外复用或被意外断开时要找的那类痕迹。

第三次请求的路径 image/logo.png 是相对路径。严格说请求行里该给绝对路径 /image/logo.png。带前导斜杠是规范写的形态，不带的时候服务器怎么解释取决于实现，有的会补斜杠，有的直接 404。

六、状态码的五类 #

状态码是三位数字，第一位决定了它属于哪一类：

类别 语义 含义 典型用途
1xx 信息性 请求已接收，继续处理 协商升级、预检
2xx 成功 请求已被接受并处理 正常返回
3xx 重定向 需要后续动作才能完成 跳转、缓存校验
4xx 客户端错误 请求不合法或无法完成 参数错、路径错、没权限
5xx 服务器错误 服务器未能完成合法请求 后端崩了、超时

这五类的划分本身就是排障工具。看到 4xx，问题在请求这一侧；看到 5xx，问题在服务端。抓包时先看第一位，方向就定了。

常见状态码：

代码 原因短语 含义
100 Continue 服务器已收到头标，客户端可以继续发请求体
101 Switching Protocols 同意切换协议，WebSocket 握手用的就是它
200 OK 请求成功，响应体在下面
204 No Content 成功，但没有响应体
206 Partial Content 返回部分内容，断点续传和分段下载用
301 Moved Permanently 永久移动，之后的请求该直接去新地址
302 Found 临时跳转
304 Not Modified 资源没变，用你本地的缓存
400 Bad Request 请求报文有语法错误
401 Unauthorized 未认证，需要先登录
403 Forbidden 认证过了，但不允许访问
404 Not Found 资源不存在
405 Method Not Allowed 路径在，但这个方法不支持
408 Request Timeout 等请求太久，服务器放弃
413 Payload Too Large 请求体太大
500 Internal Server Error 服务器内部错误
502 Bad Gateway 作为网关时，上游返回了无效响应
503 Service Unavailable 服务暂时不可用，过载或维护
504 Gateway Timeout 上游超时没回

几个值得单独说的：

301 与 302 的差别在缓存和后续行为。301 是永久的，浏览器和搜索引擎会记住，之后的请求直接去新地址；302 是临时的，每次都还问老地址。站点换域名用 301，做临时活动页用 302。这对排障有直接影响：改错了会把人长期钉在错误的地址上。

304 是缓存机制的一半。客户端带上 If-None-Match 或 If-Modified-Since 去问，服务器判断没变就回 304，不带响应体。省下的是带宽，不是请求次数。

401 与 403 的差别在认证和授权。401 是「你是谁我不知道」，会带一个 WWW-Authenticate 头标；403 是「我知道你是谁，但你不能进」。

5xx 里 502 和 504 都跟上游有关。502 是上游给了个读不懂的响应，504 是上游压根没在时限内回话。这两个码几乎总出现在有代理或网关的链路上，看到它们先怀疑上游，别先怀疑客户端。

七、常用头字段 #

头标按作用范围分四类：通用头标（请求和响应都能用）、请求头标（客户端传自身信息）、响应头标（服务器传自身信息）、实体头标（描述被传送的资源）。

格式统一是：

text
<name>:<value><CRLF>

这个格式有个硬性细节：冒号之后、值之前的空白会被裁掉，值末尾的空白也会被裁掉。所以 Content-Length: 119 等价于 Content-Length: 119。但也正因如此，值本身不能靠前后空格来承载信息。

7.1 Host #

http
Host: www.myweb.com

HTTP/1.1 要求请求必须带 Host。它的作用是让同一台服务器上的多个站点区分开——一个 IP 上跑十个域名，服务器靠 Host 决定给你哪个站的内容。缺了它，服务器回 400。

Host 的值不带 scheme，可以带端口：Host: www.myweb.com:8080。

这一行还决定了 TLS 握手里的 SNI 用哪个名字。虚拟主机和证书选择都挂在这上面。

7.2 Content-Length #

http
Content-Length: 119

它说明实体有多长，单位是字节。这是收方判断「读到哪里算读完」的主要依据。

在响应里它的意义更关键：客户端不知道服务器要发多少，只能靠 Content-Length 或分块编码来判断边界。数字给错了，客户端要么提前截断，要么一直等后续字节直到超时。

还有一类长度变化要留意：值是按实体字节算的，不是按压缩后的传输字节算。开了 Content-Encoding: gzip 之后，链路上跑的字节数和 Content-Length 报的数字未必一致，收方要先解压再对齐长度。这两个口径混用，是排查「内容被截断」时最容易走偏的地方。

7.3 Transfer-Encoding: chunked #

http
Transfer-Encoding: chunked

内容总长度事先不知道的时候用它。服务器边生成边发，每一块前面写上这一块的十六进制长度，最后用一个长度为 0 的块收尾：

text
1a\r\n
这里是一段 26 字节的内容\r\n
10\r\n
这是 16 字节\r\n
0\r\n
\r\n

1a 是十六进制的 26。客户端按块长逐块读，读到 0 就知道结束了。

它和 Content-Length 是二选一的关系，而且不能同时出现。两个都在的报文属于非法报文，按规范应该被拒绝——这正是 HTTP 请求走私（request smuggling）那类漏洞的入口。中间设备和服务端对同一个报文的边界理解不一致，就会把一段数据切出两种解读。

一句话分清分工：Content-Length 回答「有多长」，Transfer-Encoding: chunked 回答「不知道多长时怎么边发边划块」。前者是数字，后者是分块规则。

7.4 Content-Type #

http
Content-Type: text/html

说明体的媒体类型，用 MIME 类型写法，可以带字符集：

http
Content-Type: text/html; charset=utf-8

常见取值：

类型 用途
text/html HTML 文档
text/css 样式表
text/plain 纯文本
application/json JSON
application/x-www-form-urlencoded 表单提交
multipart/form-data 带文件的表单
image/png PNG 图像
application/octet-stream 未知二进制

Content-Type 给错会引发一连串怪现象：JSON 接口标成 text/plain，前端按字符串拿到手，解析失败；CSS 标成 text/plain，浏览器拒用；HTML 漏了 charset，中文会乱码。

7.5 Connection #

http
Connection: keep-alive

它管理的是连接层面的行为，不是报文内容。HTTP/1.0 默认短连接，要长连接得显式加这一行；HTTP/1.1 默认长连接，要关掉得写 Connection: close。

7.6 Cache-Control #

http
Cache-Control: max-age=3600

控制缓存怎么存、能存多久、谁能存。常用取值：

值 含义
no-store 完全不许缓存
no-cache 可以存，但每次用之前必须回源校验
max-age=3600 3600 秒内可直接用本地副本
public 中间代理也能缓存
private 只有浏览器能缓存，代理不行

no-cache 和 no-store 常被搞混。no-cache 允许存，只是用前要问；no-store 是连存都不许。

7.7 Cookie 与 Set-Cookie #

请求里带 Cookie，响应里下发 Set-Cookie：

http
Cookie: sid=abc123; theme=dark

http
Set-Cookie: sid=abc123; Path=/; HttpOnly; Secure

HttpOnly 让脚本读不到这个 Cookie，Secure 让它只在 HTTPS 上发送。这两个属性是会话安全的最低配置，后面讲无状态时细说。

7.8 头标速查 #

八、连接管理：短连接与长连接 #

HTTP 跑在 TCP 上，而 TCP 连接不是免费的。一次建连要三次握手，一次拆连要四次挥手，每个来回都是一个 RTT。如果每取一个资源都重新建连，那么取 30 个资源的页面就要付 30 次握手的时间。

这就是连接管理要解决的问题。两种模式：

模式 行为 建连次数 关闭时机
短连接 一问一答，答完就关 每个请求一次 响应写完立刻关
长连接 一条连接上串多个请求 多个请求共用一次 空闲超时、收到 close、异常

8.1 HTTP/1.0 的短连接 #

HTTP/1.0 默认是短连接。一次请求一个响应，之后服务器主动关掉连接。客户端要接着取资源，就再建一条。从客户端角度看，连接的生命周期就是一个请求。这对服务器也简单：一个连接一个线程，处理完就回收，状态干净。

代价是每个资源都要重付一次握手。页面里嵌 20 张图，握手就付 20 次。

8.2 Connection: keep-alive 与长连接 #

HTTP/1.0 想复用连接，得在请求里显式要求：

http
Connection: keep-alive

服务器同意的话，响应里也带上这个头标，然后不关连接，等下一个请求。

HTTP/1.1 把这个默认值反转了：连接默认就是持久的，想关得显式写 Connection: close。

版本 默认行为 想改怎么改
HTTP/1.0 短连接 加 Connection: keep-alive 变长连接
HTTP/1.1 长连接 加 Connection: close 变短连接

长连接不是永久连接。服务端和客户端都会设空闲超时，一段时间没请求就主动关。抓包时看到连接在某次请求之后安静地消失，那是超时到了，不是故障。

8.3 长连接带来的三个麻烦 #

长连接省掉了握手，但把三个问题摆到了台面上。

第一个是边界。 一条连接上跑多个请求，收方必须精确知道上一个响应在哪里结束。这就是 Content-Length 和 Transfer-Encoding: chunked 存在的根本原因。两个都没有，收方只能靠连接关闭来判断结束——而在长连接上连接根本不关，于是解析卡死。这是 HTTP 解析里最经典的坑，没有之一。

第二个是队头阻塞。 HTTP/1.1 的请求在一个连接上严格串行：前一个响应没读完，后一个请求的响应就不能开始发。前一个响应很大或者很慢，后面的全被堵住。浏览器只好对同一域名开多条连接来绕，但连接数本身有上限，每条还要握手。

第三个是并发与顺序。 开了多条连接之后，响应到达的顺序不等于请求发出的顺序。应用层要自己维护请求和响应的对应关系，不能假设先发先回。

8.4 关闭连接的两种方式 #

正常关闭是发完响应、双方走完 TCP 的四次挥手。这种方式下收方能确定数据读全了。

另一种是直接断（RST）。收方看到连接被重置，已经发出的请求不知道服务器处理没处理。对不幂等的方法是麻烦事：POST 提交了一半断了，到底该不该重试？

这就是幂等性在工程上真正起作用的地方。GET、PUT、DELETE 幂等，断了可以放心重发；POST 不幂等，重发会造成重复下单、重复扣款。常见做法是给 POST 加一个客户端生成的唯一请求号，服务端去重——把不幂等的操作改造成幂等。

九、无状态与 Cookie #

HTTP 协议是无状态的。每个请求都是独立的，服务器不会保存任何关于先前请求的状态。它收到请求，处理，回响应，然后忘掉。

这句话要精确理解，因为它经常被误读成「HTTP 连接不能保持」。

说法 对错 说明
HTTP 协议无状态 对 每个请求独立，服务端不记得上一个请求
HTTP 不能保持连接 错 连接层可以 keep-alive，那是 TCP 的事
服务器不保存任何数据 错 服务器当然存数据，只是不自动跟你的请求关联

关键在这一句：「无状态」说的是协议层，不是连接层。协议不规定服务端要记住上下文；连接愿不愿意复用，是 TCP 和 Connection 头标的事。两件事在不同层，混起来就永远想不通。

无状态有它的好处：服务器不用为每个客户端分配会话内存，请求可以随便落到任意一台机器上，扩容简单，重试安全。代价是——登录状态怎么办？

答案是让客户端自己带着身份来。每一轮请求都附上标识，服务端从标识里认出你。这个标识就是 Cookie。

9.1 Cookie 的往返 #

第一步，登录。客户端 POST 账号密码，服务端验证通过，在响应里下发一个 Cookie：

http
HTTP/1.1 200 OK
Set-Cookie: sid=abc123; Path=/; HttpOnly; Secure
Content-Type: application/json

{"ok":true}

第二步，之后的每个请求都自动带回它：

http
GET /profile HTTP/1.1
Host: www.myweb.com
Cookie: sid=abc123

服务端拿 sid 去查会话表，找到对应的用户，这次请求就有了身份。协议本身还是无状态的，状态被搬到了客户端和服务端共享的一块存储里。

Set-Cookie 的常用属性：

属性 作用
Path 这个 Cookie 在哪些路径下发送
Domain 允许发送到哪些域名
Expires / Max-Age 过期时间，不写就是会话 Cookie，关浏览器就没
HttpOnly 脚本读不到，降低 XSS 窃取风险
Secure 只在 HTTPS 上发送
SameSite 跨站请求时是否携带，挡 CSRF

9.2 服务端会话 #

服务端有两种存法。一种是会话 ID 指向服务端的一张表：sid=abc123 对应 {user: alice}，数据在服务端，客户端只拿一个不透明的 ID。缺点是这张表要共享——多台服务器之间得同步，否则请求落到另一台就认不出人。

另一种是把状态签好名直接放进 Cookie，服务端不存表。客户端能看到内容但改不了（改了签名对不上），水平扩展无压力，代价是撤销困难：发出去的凭证在过期前一直管用。

两种做法都是把「无状态」这个前提保住，再在协议之上补一层上下文。

9.3 无状态带来的重试语义 #

无状态还有个直接后果：服务端不知道你这个请求是不是重发的。网络抖一下，客户端没收到响应，重发一次——服务端看到的是两个一模一样的新请求。

这也解释了为什么幂等性这么重要。协议层不替你去重，去重必须由应用自己设计。给每个写操作配一个唯一的请求号，服务端记住最近处理过的号，重复的丢掉，这是把无状态协议用在不幂等操作上的标准补丁。

十、HTTP/2 与 HTTPS #

前面九章讲的都是 HTTP/1.x 的形态：一行一行的 ASCII 文本，一条连接上串行跑请求。它撑起了整个 Web，但两处瓶颈摆在那儿——队头阻塞，和明文传输。

10.1 HTTP/2 改了什么 #

HTTP/2 的核心变化是把报文从文本改成二进制帧，再在一条连接上并发跑多条流。

维度 HTTP/1.1 HTTP/2
报文形态 ASCII 文本，逐行解析 二进制分帧
连接数 每域名多条（浏览器绕队头阻塞） 一条连接跑完
并发单位 连接 流（stream）
队头阻塞 应用层存在 应用层消除，TCP 层仍在
头标传输 每次全量发送 HPACK 压缩，复用表
服务端推送 无 有（PUSH_PROMISE）

多路复用是最实质的那一条。一条 TCP 连接上开多个流，每个流有自己的编号，请求和响应在流内按序，流之间互不等待。前面那个「大响应堵住后面所有请求」的问题，在应用层被解决了。

头标压缩针对另一个老问题：HTTP/1.x 每个请求都重发一遍几十上百字节的头标，Cookie 一多能到好几 KB。HTTP/2 用一张动态表，重复的头标只发索引。

二进制分帧是代价也是收益。链路更紧凑、解析更快，但你不能再用 nc 手工拼一个 HTTP/2 请求了，调试要换工具。

有两条没变。HTTP/2 的语义跟 HTTP/1.1 一样：方法、状态码、头标含义、幂等性、缓存规则全部沿用，变的是帧格式和传输方式。另外，多路复用仍建立在一条 TCP 连接上，TCP 保证字节按序到达，一个 TCP 段丢了，后面所有流都得等它重传——队头阻塞从 HTTP 层下沉到了 TCP 层。这是 HTTP/3 换用 QUIC 的动机，本篇不展开。

10.2 HTTPS 是 HTTP 加 TLS #

HTTPS 不是另一个协议。它就是 HTTP 的报文，套在 TLS 里传输。

text
HTTP/1.1 或 HTTP/2 的报文
        ↓
      TLS
        ↓
      TCP
        ↓
       IP

端口从 80 变成 443。URL 的 scheme 从 http 变成 https。报文内容一个字没改，只是外面包了一层加密。

TLS 给了三样东西：

能力 解决什么
加密 中间人看不到报文内容，包括 Cookie 和表单
完整性校验 报文被改动会被发现
身份认证 证书证明你连的确实是那个域名

注意第三样。加密和完整性是「别被看见」，认证是「别看错人」。没有认证的加密挡不住中间人，因为他可以两头分别建连，各自加密。证书链的作用就在这儿。

TLS 握手本身要花时间，比 TCP 三次握手多。HTTP/2 规定浏览器对同一域名只开一条连接，握手成本被摊薄了；反过来，连接复用越彻底，握手的边际成本越低。

10.3 升级路径 #

明文环境下从 HTTP/1.1 升到 HTTP/2，靠请求头标里的 Connection: Upgrade 加 Upgrade: h2c，服务端同意就回 101 Switching Protocols，之后这条连接改用 HTTP/2 帧格式。

HTTPS 环境下不用这一套。TLS 握手阶段用 ALPN 扩展协商协议版本，h2 或 http/1.1，谈完直接按约定跑。

10.4 版本对照 #

特性 HTTP/1.0 HTTP/1.1 HTTP/2
默认连接 短连接 长连接 一条长连接
并发 多连接 多连接 多流复用
报文形态 文本 文本 二进制帧
Host 头标 可选 必须 用 :authority 伪头标
状态行 HTTP/1.0 200 OK HTTP/1.1 200 OK :status: 200，无原因短语
分块传输 无 chunked 帧自带长度
头标压缩 无 无 HPACK
服务端推送 无 无 有

这张表在排障时有用：抓包看到 :status: 200 这样的伪头标，说明这是 HTTP/2，别再找状态行了。

十一、HTTP 的标准化与规范来源 #

前面所有规则都不是谁拍脑袋定的，它们有一份份编号文档作依据。想知道某个头标的确切行为、某个状态码的适用条件，最终要回到这些文档。

11.1 IETF 与 RFC #

HTTP 的标准文档由互联网工程任务组（IETF）发布，文档形式叫 RFC，全称 Request for Comments——「请求评论」。名字听着像征求意见稿，实际上一旦被广泛接受，它就是标准文档。

RFC 的编号是永久的。一份文档写出来、定稿、发布，就拿到一个号，从此这个号指的就是这份内容，不会变。修订的做法是发一份新文档、拿一个新号，旧的那份保留在原处，只在元数据里标注已被谁取代。所以查资料时会看到同一个协议对应好几个 RFC 号——这不是重复，是版本演进留下的层次。

11.2 编号规则的几个要点 #

要点 说明
编号不回收 一份 RFC 作废了，它的号也不会分给别人
编号不代表新旧 号大只代表发布更晚，不代表内容更新
编号不分类 标准、草案、实验性文档混在同一号段里
状态单独记录 是「标准」还是「已被取代」，查元数据，不看号

最后一条最容易踩坑。看到一份 RFC 描述的行为跟你实测不一致，先去查它的状态——多半它早被新版本取代，你手上那份只是历史。

11.3 几个关键 RFC #

按时间顺序看 HTTP 的规范化进程：

RFC 内容
RFC 1945 描述 HTTP/1.0 的基本特性
RFC 2068 初步描述 HTTP/1.1
RFC 2616 正式规范 HTTP/1.1
RFC 7230 HTTP/1.1 的报文语法与路由
RFC 7231 HTTP/1.1 的语义与内容：方法、状态码
RFC 7232 条件请求：If-Match、If-None-Match
RFC 7233 范围请求：Range、206
RFC 7234 缓存：Cache-Control、ETag
RFC 7235 认证：401、WWW-Authenticate
RFC 7540 HTTP/2
RFC 9110 HTTP 语义（7231 等篇的整合重写）
RFC 9111 HTTP 缓存
RFC 9112 HTTP/1.1 报文语法
RFC 9113 HTTP/2

RFC 2616 是很多人记忆里的那一份，它把 HTTP/1.1 塞进了一个文档。后来发现太大，拆成了 7230 到 7235 六份，各管一摊。再后来 9110 系列又整合重写了一遍。

排查时按这个路径找依据：确定行为在哪一类（语义、语法、缓存、认证、范围），去对应那份 RFC 里查具体条款。比翻博客可靠。

11.4 URI 的角色 #

请求行第二段那个路径，学名叫统一资源标识符（URI），用来标识互联网上的资源。URI 包含「标识哪个资源」的路径和「怎么访问它」的 scheme 两部分，HTTP URL 是它的一个子集，专用于 HTTP 访问。

关于 URI 还有一句要补：fragment（# 后面那段）永远不会出现在请求行里，它只属于浏览器。哪些部分会进请求行，第二章的表格已经列过。

11.5 状态码速查 #

响应代码 含义
100 继续
101 切换协议
200 OK
204 无内容
206 部分内容
301 永久性移动
302 临时移动
304 未修改

401 未认证

404 未找到资源

记法只用记第一位：1 开头是过程话，2 开头是成，3 开头是让你去别处，4 开头是你错了，5 开头是我错了。

11.6 头标分类速查 #

查规范时先确定头标的归属，就知道它该出现在请求里还是响应里，也知道去哪份 RFC 找它。

类别 作用 例子
通用头标 请求和响应都能用 Connection、Date、Cache-Control
请求头标 客户端传递自身信息 Host、Accept、User-Agent、Cookie
响应头标 服务器传递自身信息 Server、Set-Cookie、Location
实体头标 描述被传送的资源 Content-Type、Content-Length、Content-Encoding

格式还是那一行 <name>:<value><CRLF>。头标的价值在于把「描述报文」和「报文内容」分开了：同一段 HTML，配不同的 Content-Type、Content-Encoding、Cache-Control，行为完全不同。协议的可扩展性几乎全在这几十行头标里。

十二、易错点速查 #

把前面散落各处的坑收拢成一张表。

现象 常见原因 怎么确认
请求发出后卡住不返回 缺 Content-Length 和 Transfer-Encoding，服务端不知道体在哪结束 抓包看请求头标有没有这两个
中文内容乱码 Content-Type 缺 charset，或声明的编码与实际不符 看响应的 Content-Type
CSS 不生效 Content-Type 是 text/plain 不是 text/css 看响应头标
收到 400 缺 Host 头标，或请求行语法错 检查第一行和 Host
收到 405 路径对但方法不支持 看服务端允许哪些方法
收到 502 / 504 上游异常或超时，不是客户端问题 看链路里有没有网关
连接被莫名复用 Connection 头标写了自相矛盾的值 抓包看 Connection 那一行
重定向后地址错乱 该用 301 用了 302，或反过来 看历史响应里的状态码
重复提交产生两条记录 POST 不幂等，重试被当成新请求 查应用层有没有请求号去重
响应体被截断 Content-Length 数值小于实际内容 对比实际字节数与声明值
登录状态丢失 Cookie 的 Path 或 Domain 设窄了 看 Set-Cookie 的属性
HTTPS 站点连不上 端口写死 80，或没走 TLS 检查端口和 scheme

再补几条不在表里但值得单独记住的：

别把「无状态」当成「不能保持连接」。 协议不记上下文是协议层的事，连接能不能复用是 TCP 和 Connection 头标的事。这两句话在不同层，混了就永远绕不出来。

Content-Length 数的是字节，不是字符。 中文一个字三字节，按字数写必错。

Content-Length 与 Transfer-Encoding: chunked 不能并存。 两个都写，边界就有两种读法，这是请求走私的入口。

请求行里的路径是绝对路径，不带 scheme 和 host。 GET /index.html HTTP/1.1 对，GET http://host/index.html HTTP/1.1 错（除非是发给代理）。

头标名不区分大小写，值区分。 content-length 和 Content-Length 一样，text/HTML 和 text/html 不一样。

空行是语法不是排版。 少一个 CRLF，后面全乱。

GET 不该改状态。 写操作塞进 GET，会被爬虫、预取、缓存和自动重试替你执行。

端口别写死。 80 与 443 是两个世界，硬编码换环境就断。

最后收一句：HTTP 的全部复杂度，都长在那句「一问一答的文本协议」之上。请求是文本、响应是文本、边界靠长度或分块划分、状态靠 Cookie 外挂、安全靠 TLS 兜底、并发靠 HTTP/2 的多路复用解决。把这几层的分工分清楚，抓包时看到的每一行都有地方落。
