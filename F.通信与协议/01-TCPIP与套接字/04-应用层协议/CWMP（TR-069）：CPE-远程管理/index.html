本篇边界：只讲 CWMP（TR-069）怎么让运营商远程管光猫和路由器。讲体系结构、SOAP/HTTP 协议栈、会话流程、RPC 方法、数据模型、事件上报、固件升级、抓包调试。不讲 SNMP 的 MIB 和 OID 细节，不讲 TR-111 的完整实现，也不讲 ACS 服务端代码怎么写。

同目录另有三篇：HTTP 讲报文格式与连接管理，DHCP 讲地址分配和 option 字段，SNMP 讲企业网设备监控。CWMP 底下跑的 HTTP、开局时 DHCP 下发的 ACS 地址，这两块直接引用，不重讲。

一、CWMP 解决什么问题 #

运营商在城里放了几百万台光猫、家庭网关、IPTV 机顶盒。这些盒子在用户家里，没有公网 IP，躲在 NAT 后面，地址还是 DHCP 临时分的。用户打电话说「网断了」，你要判断是线路坏了、光猫配置错了、还是账号欠费。

派人上门，一次几十到上百块，一年几十万次。这条路走不通。

你要的是坐在机房里点一下鼠标就能：读到那台光猫的软件版本、WAN 连接状态、光衰值；改它的 Wi-Fi 密码；让它重启；给它推一个新固件。CWMP 就是为这个场景造出来的。

1.1 一个被 NAT 逼出来的反向模型 #

这里有个死结。运营商没法主动连用户家里的设备，原因很直白：

  • 光猫拿的是私网地址，10.x 或者 192.168.x，公网上不可路由
  • 就算 NAT 上做了端口映射，你也得先知道映射到哪个端口，而这件事得进光猫后台看
  • 用户随时关机、拔电、换房间，IP 和端口全变

正向的「管理端连被管端」这条路，在家庭网络里是关着的。

CWMP 的办法是把方向反过来：

text
传统网管（SNMP）：   NMS ──────► Agent        管理端主动连被管端
CWMP（TR-069）：     CPE ──────► ACS          被管端主动连管理端

CPE 就是光猫，ACS 是 Auto-Configuration Server，自动配置服务器，部署在运营商机房。光猫开机后自己去找 ACS，把「我是谁、我在哪、我什么版本、我现在什么状态」一次性报上去。这个动作叫 Inform。

Inform 一到位，一条以「光猫 → ACS」为方向的 TCP 连接就建立起来了。之后 ACS 的所有命令，都顺着这条现成的连接往回发。

这就是 CWMP 的全部秘密：用 CPE 的出站连接，换来 ACS 的入站管理能力。 穿透 NAT 不用打洞、不用端口映射，因为「从外往里连」这个动作压根没发生。谁发起，谁负责——NAT 表项是 CPE 建的，外面那些连不进来的限制自然不成立。

1.2 ACS 想立刻找设备怎么办 #

Inform 的时机是 CPE 说了算的，那 ACS 想马上下一道命令，难道要等下一个周期？

绕一圈还是有办法。CPE 在 Inform 里会把自己的 ConnectionRequestURL 报给 ACS，也就是它自己那个可被寻址到的 HTTP 端口。ACS 对这个 URL 发一个空的 HTTP GET（带 HTTP Basic 认证），CPE 收到后立刻反手发一个 Inform，EventCode 填 6 CONNECTION REQUEST。这仍然是「CPE 主动发起会话」，只不过是被 ACS 敲了一下门才发起，NAT 规则没被破坏。细节在 5.6 节展开。

TR-069 本身只做到这里：ACS 不能直接发起会话。TR-111 是对这部分的补充，用 STUN 一类的机制让 ACS 能主动发起会话。本篇不展开 TR-111。

1.3 它到底能改什么 #

按 TR-069 的功能划分，CWMP 管四类事：

能力 干什么 典型场景
自动配置与动态服务 下发参数，改设备行为 开业务时下发 WAN 连接、VoIP 账号、Wi-Fi SSID
软件与固件镜像管理 下载、上传、校验、上报结果 全网推固件、备份配置文件
诊断 让 CPE 跑预定义测试并回传结果 远程 Ping、PPPoE 拨号测试、光衰检测
告警 CPE 主动上报事件 掉线、重启、配置变更、升级完成

前两类是「写」，后两类是「读」。企业网那套 SNMP 偏读，CWMP 偏写，这个差别第十章再摊开。

参数这块要留个口子：机制里涉及的参数既有规范规定的标准参数，也允许厂商自定义参数，给软件实现留了空间。标准参数在设备树上的位置全行业统一，自定义参数挂在厂商自己的私有分支下。

二、TR-069 的体系结构 #

2.1 两类逻辑设备，一条南向接口 #

TR-069 定义的管理模型里只有两类逻辑设备：CPE（被管的那台盒子）和 ACS（管人的那台服务器）。核心思想是定义一套 ACS 与 CPE 之间自动协商的交互协议，把终端的自动配置过程标准化。厂商只要照这套协议实现，任何一家 ACS 都能管任何一家的 CPE，这是它真正的价值。

接口分两个方向：

text
┌──────────────┐   北向接口   ┌──────────────┐   南向接口   ┌──────────┐
│ 第三方网管系统 │ ◄─────────► │     ACS      │ ◄─────────► │   CPE    │
│ 业务管理系统   │             │              │   TR-069    │  光猫    │
└──────────────┘             └──────────────┘             └──────────┘
  • 南向接口：ACS 与 CPE 之间，TR-069 定义的就是这一段
  • 北向接口：ACS 与第三方网管系统、业务管理系统（BSS/OSS）之间，各家自己定，有的用 CORBA，有的用 REST

你在光猫上抓包看到的全是南向流量；机房那边「工单系统派了个开业务请求」，那是北向。

2.2 网络里跑的四件套 #

CWMP 网络元素不止 ACS 和 CPE，还有两个配角在开局阶段决定成败：

元素 全称 作用 缺了会怎样
ACS Auto-Configuration Server 管理设备，下发配置、收事件 光猫永远找不到管理端
CPE Customer Premises Equipment 被管设备，执行命令、上报状态 没人可管
DNS Server Domain Name Server 解析 ACS 的 URL 域名 只能写死 IP，换机房就得全网改配置
DHCP Server Dynamic Host Configuration Protocol Server 给 CPE 分 IP，同时用 option 字段下发 ACS 地址 光猫不知道自己该连谁

DNS 这一行要拆开讲。CWMP 规定 ACS 和 CPE 之间用 URL 互相识别和访问，不是用 IP。所以 CPE 出厂配置里存的是一条 URL，比如 https://acs.example-carrier.com:8443/acs。域名靠 DNS 解析，好处是换 ACS 机房时只改 DNS，几百万台设备不用动。

DHCP 这一行是本篇和《DHCP》的分界点。CPE 上电先 DHCP 拿地址，服务器在 DHCPACK 里塞一个 option，把 ACS 的 URL 带下来。常见做法是用 option 43（Vendor Specific Information）携带厂商私有子选项，配合 option 60（Vendor Class Identifier）让服务器认出这是哪家设备、该发哪套参数。这一步在 CWMP 里叫「自动发现 ACS」。顺序是：DHCP DISCOVER → OFFER → REQUEST（带 option 60）→ ACK（带 option 43）→ DNS 查询 ACS 域名 → TCP 连 ACS → POST /acs 发 Inform。DNS 和 TCP 之间还会有一次 HTTP 层面的认证，看 ACS 怎么配。

2.3 ACS 侧的部署形态 #

一台 ACS 撑不住一个省。真实部署里，前面挂负载均衡把百万级长连接摊到多台实例；后面挂数据库存设备档案、参数快照、任务状态、事件历史；固件包单独放文件服务器，支持 HTTP Range 断点续传。

关键组件是任务队列。ACS 收到的下发需求（改配置、推固件）不是马上能执行的——设备不在线，或者正在别的会话里。任务先进队列，等这台设备下一次 Inform 上来，会话建立后先把队列里挂着的任务捞出来执行。CWMP 的下发天生是异步的，别指望点了按钮设备立刻改。

2.4 出厂到在管的完整时间线 #

出厂时 CPE 里烧一条默认 ACS URL；上电后 DHCP 拿地址、用 option 43 拿到（或覆盖）ACS URL；首次连接发 Inform，EventCode = 0 BOOTSTRAP，ACS 下发全套开局参数（WAN、Wi-Fi、VoIP、ACS 用户名密码）；进入正常周期 Inform（EventCode = 2 PERIODIC），参数变了发 EventCode = 4 VALUE CHANGE；业务变更时 ACS 挂任务，下次 Inform 时执行；固件升级走 Download → CPE 去文件服务器拉 → TransferComplete；退服用 FactoryReset 或者 ACS 摘掉设备档案。

三、协议栈：SOAP over HTTP #

3.1 五层结构 #

层 内容 说明
TCP/IP 标准 TCP/IP 底层传输，TCP 不是 UDP
SSL/TLS 标准互联网传输层安全协议 可选，加密、服务器认证、消息完整性、可选客户机认证
HTTP HTTP 1.1 承载 SOAP，一个 RPC 调用映射成一个 HTTP 请求
SOAP 基于 XML 语法的编码标准 封装 RPC 方法名和参数
RPC Methods CWMP 定义的各类 RPC 方法 实现 ACS 与 CPE 的交互
CPE/ACS Management Application 各端自己的管理应用 可以做本地定义，不必是 CWMP 的一部分

最上面那层要说一句：应用层的东西不强制属于 CWMP。设备厂商可以在这层塞私有逻辑，比如把某个参数映射到自家的看门狗，或者根据参数变化触发本地脚本。规范不管这一层。

关键点：TCP，不是 UDP。 记住这一条，第十章还要用。

3.2 为什么要套 SOAP 这层壳 #

在 Internet 环境下做分布式组件互操作，有个很现实的问题：防火墙。

大多数防火墙按端口做策略。基于 CORBA 的 RPC 用的不是常用端口，不经过特殊配置，这种分布式组件调用会被当恶意访问直接拒掉。为了管光猫让全国用户的防火墙开一堆高端口，这条路走不通。

TR-069 的解法是把 RPC 报文用 SOAP 封装，然后走标准 HTTP 传送。HTTP 的 80/443 是放行的，包能过去。规范里明确写了这么做的理由——SOAP 编码避免了与防火墙的冲突。

绑定方式是：一个 RPC 调用映射成一个 HTTP 请求，一个 RPC 应答映射成一个 HTTP 应答，SOAP 不覆盖 HTTP 现有语义，而是自然映射过去。这么绑的好处是两边都占：SOAP 的分散性、灵活性，加上 HTTP 丰富的特征库（认证、缓存、代理、Cookie、分块传输全都能用上）。第五章那个靠 Cookie 维持状态机的做法，就是「HTTP 特征库」的直接收益。

3.3 SOAP 信封结构 #

部分 是否必需 内容
Envelope（信封） 必需 根元素，声明命名空间
Header（头部） 可选 CWMP 的 ID、NoMoreRequests 等控制字段
Body（体） 必需 RPC 方法名 + 参数

规范里没说明一个 SOAP 包能不能装多个 Envelope，TR-069 自己选择了多信封机制。目的很直白：一次交换多带点信息，减少设备之间的来回次数。实际设备上常见 MaxEnvelopes 填 1，也就是不用多信封，但协议是允许的。

3.4 SSL/TLS 是可选的，但别省 #

栈里 SSL/TLS 那层标着「可选」。可选不等于可以不管。TR-069 做的是远程管理，安全的信息交换是必需的——你要在公网上传 ACS 的密码、用户的 PPPoE 账号、Wi-Fi 密钥。规范里提到用 128 bit 加密算法、数字认证机制，实现 CPE 和 ACS 之间的安全信息交换。

SSL 这层提供四件事：数据加密、服务器认证、消息完整性、可选的客户机认证。数据加密防中间人看到参数值；服务器认证让 CPE 确认对面真是运营商的 ACS；消息完整性防报文被篡改；客户机认证让 ACS 确认对面真是自己家的设备。

实际部署里，早期光猫大量跑明文 HTTP 7547。这个端口是扫描和利用的重灾区，各类 CWMP 漏洞打的都是它。新部署一律上 HTTPS，这不是性能问题，是安全问题。

3.5 谁的端口连谁 #

连接 发起方 目标地址 端口
CWMP 会话 CPE ACS 的 URL 7547（或 9090、8443）
Connect Request ACS CPE 的 ConnectionRequestURL 设备侧随机高位端口
文件下载 CPE Download 里的 URL 80 / 443
DHCP CPE 广播 67 / 68
DNS CPE DHCP 下发的 DNS 53

这张表里只有第二行是「外面往里连」。它的成功率取决于 NAT 有没有给设备那个高位端口做映射，这也是它最容易失败的原因。

四、连接建立与握手 #

4.1 一次会话的骨架 #

CWMP 的一次会话从 CPE 发起，到 CPE 关闭连接为止：

text
CPE                                    ACS
 ├──── 1. TCP 三次握手 ───────────────► │
 ├──── 2. TLS 握手（可选）─────────────► │
 ├──── 3. POST Inform ────────────────► │   会话开始
 │◄──── 4. 200 OK + InformResponse ─────┤
 ├──── 5. 空 POST ────────────────────► │   等 ACS 下命令
 │◄──── 6. 200 OK + 第一个 RPC 请求 ────┤
 ├──── 7. 200 OK + RPC 应答 ──────────► │
 │            ... 反复 6/7 ...          │
 │◄──── 8. 200 OK + 空 Body ───────────┤   没有更多请求
 ├──── 9. 关闭连接 ───────────────────► │   会话结束

第 5 步那个「空 POST」是 CWMP 最反直觉的地方，下一章细讲。

4.2 三步握手拆开看 #

第 1 步，TCP 连接。 CPE 主动发 SYN，目标就是 ACS 的 URL 里的主机和端口。这一步和普通 HTTP 没区别。

第 2 步，SSL 初始化，建立安全机制。 如果 ACS 用的是 HTTPS，这里跑完整的 TLS 握手：ClientHello → ServerHello + 证书 → 密钥交换 → Finished。CPE 校验 ACS 证书的 CN/SAN 是否匹配 URL 里的域名，校验签发链是否可信。很多现网故障就栽在这一步——光猫固件里的根证书过期了，或者 ACS 换了证书但设备侧没更新 CA。

第 3 步，CPE 发送 Inform，开始建立 CWMP 连接。 这是整个协议的起点。Inform 里必须带的信息：

字段 作用 举例
DeviceId 标识设备身份 Manufacturer + OUI + ProductClass + SerialNumber
Event 说明这次为什么上报 0 BOOTSTRAP / 1 BOOT / 2 PERIODIC / 6 CONNECTION REQUEST / 8 DIAGNOSTICS COMPLETE
CurrentTime 设备本地时间 2012-12-10T13:21:37+00:00
RetryCount 第几次重试 0
ParameterList 关键参数快照 版本号、ConnectionRequestURL、外部 IP

DeviceId 那四个字段合起来是设备的唯一身份。OUI 是厂商的 IEEE 组织唯一标识符，六位十六进制；SerialNumber 是序列号。OUI + ProductClass + SerialNumber 这个三元组在 ACS 数据库里建唯一索引，是设备档案的主键。

RetryCount 容易被忽略。会话中途断了，CPE 会自动重连，每重连一次这个值加一。规范里说重连次数有上限，达到上限就停手，等下一个周期。这个上限由设备厂商实现决定，调不出来。

ParameterList 是 Inform 里最有价值的部分。这是设备主动「交底」：我是什么版本、我有哪些能力、我的 ACS 连接地址是什么、我的外部 IP 是什么。DeviceSummary 特别值得看，它用一行文本列出了设备支持的所有数据模型能力集，形如 InternetGatewayDevice:1.1[](Baseline:1, EthernetLAN:1, USBLAN:1, WiFiLAN:1, EthernetWAN:1, Time:1, IPPing:1, DeviceAssociation:1), VoiceService:1.0[1](Endpoint:1, SIPEndpoint:1)。

这串东西要会读。InternetGatewayDevice:1.1 是数据模型版本，方括号里是 []（空的，表示没有扩展），圆括号里是能力集清单——支持以太网 LAN、USB LAN、Wi-Fi LAN、以太网 WAN、时间同步、IP Ping 诊断、设备关联；VoiceService:1.0[1] 表示有一路语音服务，支持 SIP 终端。ACS 拿到这串，就知道这台设备能下发哪些业务、能跑哪些诊断。

4.3 InformResponse：ACS 的第一个回应 #

CPE 的 Inform 上去，ACS 认证通过（认证方式看 ACS 配置：校验 DeviceId 是否在库、校验 HTTP Basic 凭据、或只做 IP 白名单），返回 HTTP 200 加一个 SOAP 体：

xml
HTTP/1.1 200 OK
Server: Apache-Coyote/1.1
Set-Cookie: JSESSIONID=5CEB426075A42489AC3A7E6BAE004C61; Path=/
Content-Type: text/xml
Content-Length: 574

<SOAP-ENV:Envelope
    xmlns:SOAP-ENV="http://schemas.xmlsoap.org/soap/envelope/"
    xmlns:SOAP-ENC="http://schemas.xmlsoap.org/soap/encoding/"
    xmlns:cwmp="urn:dslforum-org:cwmp-1-0"
    xmlns:xsd="http://www.w3.org/2001/XMLSchema"
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance">
  <SOAP-ENV:Header>
    <cwmp:ID SOAP-ENV:mustUnderstand="1">2044897763</cwmp:ID>
    <cwmp:NoMoreRequests>0</cwmp:NoMoreRequests>
  </SOAP-ENV:Header>
  <SOAP-ENV:Body>
    <cwmp:InformResponse>
      <MaxEnvelopes>1</MaxEnvelopes>
    </cwmp:InformResponse>
  </SOAP-ENV:Body>
</SOAP-ENV:Envelope>

三个细节：cwmp:ID 原样回传，CPE 发的 2044897763，ACS 回的也是 2044897763，这个 ID 用来配对请求和应答，多信封场景下尤其重要，SOAP-ENV:mustUnderstand="1" 表示接收方必须理解这个头，不认识就得报错；NoMoreRequests 这里是 0，如果 ACS 填 1 意思是「我这边没别的请求了」，CPE 就不会再发空 POST 等命令，直接准备关会话；Set-Cookie: JSESSIONID=... 是 JBoss 的会话 Cookie，CPE 之后的每个请求都得带上它，ACS 靠它把同一个会话里的若干 HTTP 请求串成一条状态机。

NoMoreRequests 和 Set-Cookie 放在同一个响应里，说明 ACS 是拿一个普通 Web 容器在跑 CWMP 业务：HTTP 层的状态靠 Cookie，CWMP 层的流程靠 NoMoreRequests。

4.4 会话超时与重连 #

CWMP 会话没有独立的心跳，靠 HTTP 的 keep-alive 维持连接。所以超时是两层叠加的：

超时类型 谁设置的 典型值 触发后
TCP keep-alive 内核 7200 秒 发探测包，无响应则断
HTTP 空闲超时 ACS 容器 30～300 秒 服务端主动断
CWMP 会话上限 CPE 实现 无标准 到点强制关会话
ACS 处理超时 ACS 业务层 看任务复杂度 放弃当前 RPC，回错误

会话异常中断后，CPE 会重连，RetryCount 递增。重连次数没到上限就一直试，到了就放弃，等下一个 PERIODIC 周期。

做运维时要盯住一个指标：RetryCount 的平均值。这个值持续偏高，说明 ACS 侧不稳或者网络质量差；一直等于 0，说明链路干净。突然有大批设备的 RetryCount 一起上涨，多半是 ACS 侧的负载均衡或者证书出了问题。

五、会话的完整流程 #

5.1 用一份真实抓包走完这十一步 #

素材里有一段完整的通信过程，一步一步走。这条流程是理解 CWMP 的核心，每一步都不能跳。

这十一步是个「迁移 ACS」的场景，不是日常开业务。选它当例子有道理——它把「读参数」和「写参数」两类操作都串了一遍，还捎带一个 ACS 想收手时怎么收的完整示范。

步骤 方向 报文 RPC 方法 说明
1 CPE → ACS TCP SYN/ACK — 建立传输层连接
2 CPE ↔ ACS TLS 握手 — SSL 初始化，建立安全机制；可选，HTTPS 时才有
3 CPE → ACS POST + Inform Inform 唯一由 CPE 发起的 RPC，开始建立 CWMP 连接
4 ACS → CPE 200 OK + InformResponse — CPE 通过认证，会话建立
5 CPE → ACS POST + 空 Body — 没有别的请求，发空报文满足 HTTP 交互规则
6 ACS → CPE 200 OK + GetParameterValues GetParameterValues 查询 CPE 上设置的 ACS URL
7 CPE → ACS 200 OK + Response — 把 ACS URL 的值回给 ACS
8 ACS → CPE 200 OK + SetParameterValues SetParameterValues ACS 发现 URL 是自己，要求改成备用 ACS
9 CPE → ACS 200 OK + Response — 设置成功，回报响应
10 ACS → CPE 200 OK + 空 Body — NoMoreRequests，通知没别的请求了
11 CPE 关闭连接 — 会话结束，之后向备用 ACS 发起连接

5.2 第 5 步那个空报文 #

第 5 步在纸面上是废话：CPE 发一个 Content-Length: 0 的 POST，什么内容都没有。

为什么必须发？CWMP 把「RPC 请求-应答」硬映射到了「HTTP 请求-响应」上，而 HTTP 是严格的请求-响应模型：客户端不问，服务端不能答。第 4 步 ACS 回完 InformResponse 后，HTTP 的事务已经结束了。CPE 手里没有别的问题要问，但 ACS 手里还攥着一堆命令想下。HTTP 不允许 ACS 主动发，于是 CPE 发一个空 POST，等于说：「我这边没问题了，你有什么要下的，趁这个请求回给我。」

http
POST /openacs/acs HTTP/1.1
Host: 192.168.7.1:9090
User-Agent: BCM_TR69_CPE_04_00
Connection: keep-alive
SOAPAction:
Cookie: JSESSIONID=5CEB426075A42489AC3A7E6BAE004C61
Content-Type: text/xml
Content-Length: 0

Content-Length: 0 和 Cookie 都还在。这个请求是一个纯粹的「轮询占位」，ACS 的回答就是它的第一条命令。ACS 手里没命令时回 HTTP/1.1 204 No Content，一个字节的 Body 都不带——这也是一个合法信号：会话该结束了。

5.3 RPC 阶段的完整报文 #

第 6 步到第 9 步是真正的 RPC 阶段，一次读一次写。先看 ACS 下发的 GetParameterValues：

xml
HTTP/1.1 200 OK
Content-Type: text/xml
Content-Length: 722

<SOAP-ENV:Envelope
    xmlns:SOAP-ENV="http://schemas.xmlsoap.org/soap/envelope/"
    xmlns:SOAP-ENC="http://schemas.xmlsoap.org/soap/encoding/"
    xmlns:cwmp="urn:dslforum-org:cwmp-1-0"
    xmlns:xsd="http://www.w3.org/2001/XMLSchema"
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance">
  <SOAP-ENV:Header>
    <cwmp:ID SOAP-ENV:mustUnderstand="1">ID:intrnl.unset.id.GetParameterValues1414832028729.539118694</cwmp:ID>
    <cwmp:NoMoreRequests>0</cwmp:NoMoreRequests>
  </SOAP-ENV:Header>
  <SOAP-ENV:Body>
    <cwmp:GetParameterValues>
      <ParameterNames SOAP-ENC:arrayType="xsd:string[1]">
        <string>InternetGatewayDevice.DeviceSummary</string>
      </ParameterNames>
    </cwmp:GetParameterValues>
  </SOAP-ENV:Body>
</SOAP-ENV:Envelope>

cwmp:ID 换成了 ID:intrnl.unset.id.GetParameterValues1414832028729.539118694。这个格式能反推实现：intrnl.unset.id 说明调用方没显式指定 ID，GetParameterValues 是方法名，后面是毫秒时间戳加随机数。这是 Java 侧自动生成的。你在抓包里看到 intrnl.unset 就知道对面跑的是某个 Java ACS。

CPE 的应答，HTTP 状态还是 200，Body 是 GetParameterValuesResponse：

xml
<SOAP-ENV:Body>
  <cwmp:GetParameterValuesResponse>
    <ParameterList SOAP-ENC:arrayType="cwmp:ParameterValueStruct[1]">
      <ParameterValueStruct>
        <Name>InternetGatewayDevice.DeviceSummary</Name>
        <Value xsi:type="xsd:string">InternetGatewayDevice:1.1[](Baseline:1, EthernetLAN:1, USBLAN:1, WiFiLAN:1, EthernetWAN:1, Time:1, IPPing:1, DeviceAssociation:1), VoiceService:1.0[1](Endpoint:1, SIPEndpoint:1)</Value>
      </ParameterValueStruct>
    </ParameterList>
  </cwmp:GetParameterValuesResponse>
</SOAP-ENV:Body>

CPE 处理这个请求的动作是：调用后台的脚本或者本地实现去查 DeviceSummary 的值，填进响应。这一句听着简单，落地很麻烦——设备上得有个参数存取层，把设备树上的路径映射到真实的配置存储（有的是 /etc/config 下的文件，有的是 SQLite，有的是内存结构加持久化）。最后 ACS 结束会话，回 HTTP/1.1 204 No Content。

5.4 Cookie 维持状态机 #

InformResponse 里 ACS 给了 Set-Cookie: JSESSIONID=...，之后 CPE 的每个请求都带上这个 Cookie，直到会话结束。

为什么需要？因为 HTTP 是无状态协议。一次 CWMP 会话里有十几个 HTTP 事务，ACS 得知道这十几个事务属于同一台设备、同一次会话、同一个流程。没有 Cookie，服务器只能靠源 IP 猜——而百万台设备在 NAT 后面共享几个出口 IP，猜不准。

两边都是通过 Cookie 来建立通信过程的顺序、维持状态机的正常工作。这也是判断「这个 ACS 实现靠不靠谱」的一个观察点：不返回 Cookie 的 ACS，多半把会话状态压在了 URL 参数或者数据库里，性能和并发都会吃亏。

5.5 XML 节点的 type 声明 #

SOAP 消息里的 XML 节点是带类别的，比如 xsi:type="xsd:string" 说明这个 Value 是 String 类型，xsd:unsignedInt 是整数，xsd:boolean 是布尔。标准要求的类型有 string、int、unsignedInt、boolean、dateTime 等，都是 SOAP/XSD 定义的类型里的一个子集——规范里写得很清楚，只能使用 SOAP 定义的数据类型中的部分。

不同 ACS 对参数检查的严格程度不一样。有些 ACS 即使去掉 xsi:type 也能工作（它按参数定义自己推断），有些会直接报 9007 Invalid arguments。建议一定要加上，这不是风格问题，是互通性问题。设备侧和 ACS 侧是两个厂商写的，别指望对方宽容。

5.6 ACS 主动触发的会话：Connect Request #

日常的会话都是 CPE 发起，但 ACS 想立刻下命令时，得先有一个敲门的动作：ACS 对 CPE 报上来的 ConnectionRequestURL 发一个带 Basic 认证的 HTTP GET，CPE 回 200 OK 后立刻发起一个全新的 CWMP 会话，Inform 里 EventCode = 6 CONNECTION REQUEST，ACS 一看就知道「我敲的门起作用了」。

敲门用的 URL 形如 http://192.168.7.143:30005/，就是设备的外部地址（Inform 里也报了 ExternalIPAddress = 192.168.7.143）。CPE 收到敲门后不在这条连接上执行任何命令，而是新开一条会话。为什么绕这么一圈？因为 CPE 的 HTTP 服务只监听内网地址，ACS 能不能访问到完全取决于 NAT 有没有给这个端口做映射。如果设备在双层 NAT 后面，这个地址是错的，敲门必然失败。

ConnectionRequestURL 打不通是 CWMP 现网最常见的故障之一，第十一章讲怎么排查。

六、RPC 方法一览 #

6.1 分类框架 #

CWMP 的 RPC 方法按「谁调用谁」分两大类：

类别 谁实现 谁调用 数量
CPE 方法 CPE 设备实现 ACS 调用 9 种基本 + 6 种可选
ACS 方法 ACS 设备实现 CPE 调用 2 种基本 + 2 种可选

这个分类的意义在于：ACS 方法只有 Inform 和 TransferComplete 两个必须实现。整套 CWMP 里，CPE 主动发起的 RPC 只有这两个，其余全部是 ACS 往下发的。这就是第一章反向模型在方法层面的体现。

6.2 方法总表 #

方法 方向 必需/可选 用途
Inform CPE → ACS 必需 上报设备信息、事件、参数快照，开启会话
GetParameterValues ACS → CPE 必需 按名字读一个或多个参数的值
SetParameterValues ACS → CPE 必需 按名字写参数值，带 ParameterKey
GetParameterNames ACS → CPE 必需 列某个路径下的参数名（不含值）
SetParameterAttributes ACS → CPE 必需 改参数属性（是否可写、是否通知）
GetParameterAttributes ACS → CPE 必需 读参数属性
AddObject ACS → CPE 必需 在设备树上新建一个多实例对象
DeleteObject ACS → CPE 必需 删除一个多实例对象
GetRPCMethods ACS → CPE 必需 查询 CPE 支持哪些 RPC 方法
Download ACS → CPE 必需 让 CPE 从指定 URL 下载文件
Upload ACS → CPE 必需 让 CPE 把文件上传到指定 URL
Reboot ACS → CPE 必需 远程重启
FactoryReset ACS → CPE 可选 恢复出厂设置
ScheduleInform ACS → CPE 可选 让 CPE 在指定时刻发一次 Inform
ScheduleDownload ACS → CPE 可选 让 CPE 在指定时间窗内下载文件
TransferComplete CPE → ACS 必需 文件传输结束后回报结果
RequestDownload CPE → ACS 可选 CPE 主动请求下载
Kicked ACS → CPE 可选 通知 CPE 被踢下线（Issue 2 起）
AutonomousTransferComplete CPE → ACS 可选 自主传输完成后回报

那些标「可选」的要打个问号。素材里说得直白：Optional 为可选，Required 为必须实现，不过这个只能作为参考，还得看各家设备商的标准。现网现实是：标 Required 的不一定实现，标 Optional 的不一定没有。 你接手一台盒子，第一件事是发一个 GetRPCMethods，看它到底支持哪些。别对着规范写代码。

6.3 Inform：唯一的会话发起者 #

Inform 的地位特殊，因为它是唯一由 CPE 发起、且用于开启会话的 RPC。调用时机就三种：CPE 与 ACS 建立连接时、底层配置发生改变时、CPE 周期性发送本地信息到 ACS 时。三个时机对应三种 EventCode，第八章展开。

Inform 的参数结构分六块：

参数 类型 内容
DeviceId 结构体 Manufacturer、OUI、ProductClass、SerialNumber
Event 结构体数组 每个元素含 EventCode 和 CommandKey
MaxEnvelopes unsignedInt 一次最多几个信封
CurrentTime dateTime 设备当前时间
RetryCount unsignedInt 本次会话是第几次重试
ParameterList 结构体数组 Name + Value 列表

CommandKey 这个字段要留意。它是 ACS 在 SetParameterValues 时带下来的一个字符串，CPE 存着，下次 Inform 时原样回传。ACS 靠它判断「我上次下发的配置，设备到底应没应用」。如果 CommandKey 是 unset，说明这台设备从没被成功下发过。

6.4 GetParameterValues 与 SetParameterValues #

这一对是读和写的主力。

xml
<cwmp:GetParameterValues>
  <ParameterNames SOAP-ENC:arrayType="xsd:string[2]">
    <string>InternetGatewayDevice.DeviceInfo.SoftwareVersion</string>
    <string>InternetGatewayDevice.WANDevice.1.WANConnectionDevice.1.WANIPConnection.1.ExternalIPAddress</string>
  </ParameterNames>
</cwmp:GetParameterValues>

应答里每个参数回一个 ParameterValueStruct。关键点：设备上不存在的参数也要在应答里出现，但 Value 留空。 这是规范要求，目的是让 ACS 能区分「参数存在但值为空」和「参数不存在」。很多实现图省事直接跳过不存在的参数，导致 ACS 判断错误。

SetParameterValues 请求，多两个字段：

xml
<cwmp:SetParameterValues>
  <ParameterList SOAP-ENC:arrayType="cwmp:ParameterValueStruct[1]">
    <ParameterValueStruct>
      <Name>InternetGatewayDevice.LANDevice.1.WLANConfiguration.1.SSID</Name>
      <Value xsi:type="xsd:string">MyHome-5G</Value>
    </ParameterValueStruct>
  </ParameterList>
  <ParameterKey>cfg-20241118-001</ParameterKey>
</cwmp:SetParameterValues>

ParameterKey 是 ACS 自己生成的标记，CPE 存下来，下次 Inform 时回填到 CommandKey。这是下发成功与否的凭证。

应答有两种：全成功时回 SetParameterValuesResponse，带一个 Status（0 表示全部应用成功，1 表示会应用但要重启后才生效）；有一个参数失败就整体回 Fault，带 9007 Invalid arguments 之类的错误码，一条都不写。这个「全有或全无」的语义很关键，写脚本时要按这个假设设计。

6.5 GetParameterNames：摸清设备树 #

不带值的列表查询，ACS 拿它来发现设备的能力边界：

xml
<cwmp:GetParameterNames>
  <ParameterPath>InternetGatewayDevice.WANDevice.1.</ParameterPath>
  <NextLevel>1</NextLevel>
</cwmp:GetParameterNames>

NextLevel = 1 表示只返回下一层的节点名，不递归；NextLevel = 0 表示整棵子树全返回。递归一次要返回几千个节点，网络和内存都吃不住，实践里都是一层层往下扒。返回的每个节点带一个 writable 标记，告诉 ACS 这个参数能不能写——这个标记比规范文档靠谱，文档说可写的，设备未必真让你写。

6.6 Download / Upload：文件传输的入口 #

Download 让 CPE 去拉文件，是固件升级和配置下发的核心方法，完整参数在 9.2 节拆开讲。FileType 的取值决定这次传输干什么：

FileType 含义 说明
1 Firmware Upgrade Image 固件升级包 最常见的用法
2 Web Content Web 页面内容 定制设备管理页面
3 Vendor Configuration File 厂商配置文件 整包配置下发或备份
4 Tone File 音调文件 VoIP 相关
5 Ring File 铃声文件 VoIP 相关
6 Vendor Log File 厂商日志文件 上传日志用

Upload 反过来，让 CPE 把文件推上去：

xml
<cwmp:Upload>
  <CommandKey>bak-20241118</CommandKey>
  <FileType>3 Vendor Configuration File</FileType>
  <URL>http://files.example-carrier.com/bak/27FD6001F8F748602.cfg</URL>
  <Username>bakuser</Username>
  <Password>bakpass</Password>
</cwmp:Upload>

现网设备的支持情况，素材里说得很实在：目前设备支持下载的文件类型有系统启动文件和配置文件，支持上传的文件类型只有配置文件。数字签名方式的文件下载，设备不支持。

Download 和 Upload 都是异步的。ACS 发完命令立刻收到一个「已接受」的响应，但文件还没开始传。真正的传输由 CPE 在后台发起，传输结束后 CPE 用 TransferComplete 单独开一次会话回报结果。

6.7 Reboot / FactoryReset #

Reboot 就是远程重启，参数只有一个 CommandKey。CPE 回 RebootResponse 之后立刻重启，不等会话结束。所以 ACS 侧经常收不到干净的收尾——连接被 RST 掉。这不是故障，是正常现象。实际用得最多的就是「用户打电话说网慢，先重启一下试试」。

FactoryReset 恢复出厂设置，可选方法。这个要谨慎——很多设备的 FactoryReset 会把 ACS URL 一起抹掉，抹完之后设备再也连不上 ACS，直接失联，只能上门。真要用，先确认设备的实现细节。

6.8 TransferComplete：又一个 CPE 主动的 #

CPE 主动发起的第二个必需 RPC。文件传完后，CPE 自己发起一次新的 CWMP 会话，上来先发 Inform（EventCode 是 7 TRANSFER COMPLETE），然后发 TransferComplete：

xml
<cwmp:TransferComplete>
  <CommandKey>fw-20241118</CommandKey>
  <FaultStruct>
    <FaultCode>0</FaultCode>
    <FaultString></FaultString>
  </FaultStruct>
  <StartTime>2024-11-18T10:30:00+08:00</StartTime>
  <CompleteTime>2024-11-18T10:34:12+08:00</CompleteTime>
</cwmp:TransferComplete>

FaultCode = 0 表示成功。非 0 时 FaultString 会带具体原因，比如 404（URL 不通）、401（认证失败）、磁盘空间不足。CommandKey 在这里的作用是把这次传输和当初那条 Download 命令对上号，ACS 收到后按 CommandKey 找原任务，更新状态。

6.9 GetRPCMethods #

最小的一个方法，用来探设备能力，请求体就是一个空元素 <cwmp:GetRPCMethods/>。应答是一个字符串数组，列出所有支持的方法名。接新设备时先跑这个，比翻手册快。

6.10 用 RPC 打一套 Ping 诊断 #

素材里有个例子，说明「用 CWMP 做一件小事有多绕」。需求：测 CPE 能不能 Ping 通某个地址。

直觉做法是 SSH 或 telnet 登上去敲 ping 命令。CWMP 里不行，得分两步。第一步，SetParameterValues 配参数：

xml
<cwmp:SetParameterValues>
  <ParameterList SOAP-ENC:arrayType="cwmp:ParameterValueStruct[2]">
    <ParameterValueStruct>
      <Name>InternetGatewayDevice.IPPingDiagnostics.Host</Name>
      <Value xsi:type="xsd:string">202.96.128.86</Value>
    </ParameterValueStruct>
    <ParameterValueStruct>
      <Name>InternetGatewayDevice.IPPingDiagnostics.DiagnosticsState</Name>
      <Value xsi:type="xsd:string">Requested</Value>
    </ParameterValueStruct>
  </ParameterList>
  <ParameterKey>ping-001</ParameterKey>
</cwmp:SetParameterValues>

关键在最后一个参数：把 DiagnosticsState 设成 Requested，这才是「启动」的动作。前面那些参数（Host、NumberOfRepetitions）只是配置，不触发执行。

第二步，GetParameterValues 查结果，看 DiagnosticsState 是不是变成了 Complete，以及 SuccessCount、AverageResponseTime 的值。如果 DiagnosticsState 停在 Requested 不动，说明设备没执行——这个能力它压根没实现。

这个设计确实繁琐。素材里的评价很直接：这样的设计有些繁琐；不过确实也想不出更好的办法。繁琐的根源是 CWMP 的抽象方式：它没有「执行一条命令」这种动作，只有「读参数」和「写参数」。所有操作都得翻译成对设备树节点的读写。Ping 这样的一次性动作，被迫建模成「一个状态机参数 + 一组结果参数」。

至于为什么用 XML 这么重的格式，素材里给了解释：XML 足够成熟，可以很方便地定义 Schema 文件，方便验证；TR-069 出现的年代 JSON 格式并没有流行起来，那还是 XML 的年代。这个解释站得住——2004 年发第一版规范时，JSON 还没影。

6.11 RPC 错误码 #

CPE 处理失败时回 Fault，不是正常响应。常见错误码：

错误码 名称 什么情况
9000 Method not supported 设备不支持这个方法
9001 Request denied 请求被拒（权限或状态不允许）
9002 Internal error 设备内部错误
9003 Invalid arguments 参数不合法（类型错、路径不存在）
9004 Resources exceeded 资源不足（如新建对象超过上限）
9005 Invalid parameter name 参数名路径写错
9006 Invalid parameter type xsi:type 和参数定义不匹配
9007 Invalid parameter value 值超范围
9008 Attempt to set non-writable parameter 试图写只读参数
9009 Notification request rejected 通知请求被拒
9010 Download failure 下载失败
9011 Upload failure 上传失败
9012 File transfer server authentication failure 文件服务器认证失败
9013 Unsupported protocol for file transfer 不支持的传输协议（如给了 FTP URL）

9003 和 9005 最容易混：9003 是「参数值不合法」，9005 是「参数名不存在」。抓包看到一个 Fault，先看码再猜原因。

9013 也常见。规范只要求支持 HTTP 下载，有些设备完全不支持 FTP。你给了个 ftp:// 的 URL，它就回 9013。文件服务器上别只开放 FTP。

七、设备数据模型 #

7.1 为什么需要数据模型 #

RPC 统一了设备的接口，那 RPC 操作的数据怎么统一？TR-069 因此提出了 DataModel。

问题很具体：华为的光猫、中兴的光猫、贝尔的光猫，硬件不同、软件不同、参数命名各有一套。Set 的时候，ACS 怎么知道「Wi-Fi 密码」在这台设备上叫什么、在哪一层、取值范围是什么？

答案是把所有设备抽象成同一棵树。TR-069 把很多不同的设备都抽象出了设备模型，挂到公共的设备树上，根节点叫 InternetGatewayDevice。后面所有的参数，都是这棵树上的一个节点路径：

text
InternetGatewayDevice
├── DeviceSummary                          ← 能力集摘要（一行文本）
├── DeviceInfo                             ← 设备身份
│   ├── Manufacturer / ManufacturerOUI / ProductClass / SerialNumber
│   ├── HardwareVersion / SoftwareVersion / SpecVersion / ProvisioningCode
│   └── UpTime                             ← 运行时长（秒）
├── ManagementServer                       ← 管理通道
│   ├── URL / Username / Password          ← ACS 地址与凭据
│   ├── PeriodicInformEnable / Interval / Time
│   ├── ParameterKey                       ← 上次下发的标记
│   └── ConnectionRequestURL / Username / Password
├── LANDevice.1.WLANConfiguration.1        ← Wi-Fi 配置（多实例）
│   └── Enable / SSID / Channel
├── WANDevice.1.WANConnectionDevice.1
│   ├── WANIPConnection.1                  ← IP 连接
│   │   └── Enable / ConnectionType / ExternalIPAddress
│   └── WANPPPConnection.1                 ← PPPoE 连接
└── IPPingDiagnostics                      ← IP Ping 诊断
    ├── DiagnosticsState                   ← 状态机
    └── Host / NumberOfRepetitions / SuccessCount / AverageResponseTime

这棵树的全部意义：ACS 只需要操作这些节点上的 value 和 attribute，就能改变设备的配置。 换个厂商的设备，路径一模一样，代码不用改。

7.2 节点三种类型 #

类型 含义 例子 操作
参数（Parameter） 叶子，有值可读可写 ...WLANConfiguration.1.SSID GetParameterValues / SetParameterValues
对象（Object） 单实例节点，容器 ...WLANConfiguration 路径直接走下去
多实例对象 可以有多个实例，带数字编号 ...WLANConfiguration.1、.2 AddObject / DeleteObject

编号从 1 开始，不连续。删掉 .2 之后，.1 和 .3 还在，不会重新编号。新加的实例用最小的空闲编号，所以顺序在设备生命周期里会变——别拿编号当业务标识，要判 Wi-Fi 频段得看参数不看编号。

7.3 参数属性 #

每个参数除了值，还有属性，用 GetParameterAttributes / SetParameterAttributes 读写：

属性 含义 影响
Notification 值变化时是否上报 0=不上报，1=被动上报，2=主动上报
AccessList 哪些 ACS 能读这个参数 多 ACS 场景的限制
Name 参数完整路径 只读

Notification 是第八章事件上报的开关。设成 1 或 2，参数值一变，CPE 就会在下次 Inform 时带上 4 VALUE CHANGE 事件和该参数的新值。设成 0，改了也不报。

这里有个实践坑：Notification 是持久化的。ACS 把某个参数的 Notification 设成 2 之后，如果忘了改回 0，这台设备会不停上报，一直产生会话。大批设备都这样，ACS 会被自己家的通知淹掉。

7.4 两个根：1.x 和 181 #

DeviceSummary 那行的 InternetGatewayDevice:1.1 是数据模型版本号。1.0 是 TR-098 Issue 1，最基础的一套；1.1 是 TR-098 Issue 2 修订，补充了诊断、多 WAN、部分 IPv6 支持；2.0 是 TR-181 Issue 2，根节点改成 Device，层级扁平化，能覆盖更多业务。

Device 和 InternetGatewayDevice 是两套并行的根。TR-181 的 Device 根更现代，去掉了 1.x 里很多冗余层级。现网存量光猫绝大多数还是 1.x。新设备开始往 TR-181 迁，但迁移慢——数据模型一改，ACS 侧的脚本全得改。你抓包看到根是 InternetGatewayDevice 就是 1.x，看到 Device. 开头就是 181。

7.5 设备树怎么落到设备上 #

抽象层和设备实现之间还有一层映射，这层是厂商自己写的。设备上的实现是 UCI 配置文件、SQLite、C 结构体数组，CWMP 代理进程负责把树路径翻译成对这些存储的读写。

这层是 bug 高发区。Set 返回成功但值没真正生效、Get 读的是缓存不是实时值、重启后配置丢了——全是这层没写对。诊断这类问题时，上设备直接看配置文件，比反复抓 CWMP 包管用。

八、事件与主动通知 #

8.1 EventCode 全表 #

EventCode 名称 触发时机 必需
0 BOOTSTRAP 首次安装 CPE 第一次连上 ACS（出厂后或恢复出厂后） 必需
1 BOOT 上电启动 每次上电或重启 必需
2 PERIODIC 周期上报 PeriodicInformInterval 到期 必需
3 SCHEDULED 定时上报 PeriodicInformTime 指定的时刻到 可选
4 VALUE CHANGE 参数变更 被监控的参数值发生变化 必需
5 KICKED 被踢 ACS 主动断开并要求重连 可选
6 CONNECTION REQUEST ACS 敲门 ACS 访问 ConnectionRequestURL 后 必需
7 TRANSFER COMPLETE 传输完成 文件下载/上传结束 必需
8 DIAGNOSTICS COMPLETE 诊断完成 诊断测试跑完 必需
9 AUTONOMOUS TRANSFER COMPLETE 自主传输完成 CPE 自己发起的文件传输结束 可选

M 前缀是厂商自定义事件，X_ 前缀是厂商自定义参数。看到这两个前缀就知道是私有扩展，标准 ACS 多半不认识。

8.2 五种必须实现的上报时机 #

时机 EventCode 说明
CPE 初次安装使用 0 BOOTSTRAP 出厂配置第一次连上 ACS
上电或重启 1 BOOT 每次开机
PeriodicInformInterval 周期到 2 PERIODIC 心跳，间隔默认 3600 秒左右
ACS 请求 CONNECTION REQUEST 6 CONNECTION REQUEST ACS 敲门后的回应
Monitor 的值发生改变 4 VALUE CHANGE 被监控参数变化
更详细的支持要看设备手册。不同厂商实现的事件集不一样，有些还支持 3 SCHEDULED，有些不支持。

0 BOOTSTRAP 和 1 BOOT 的区别要分清。BOOTSTRAP 是「我这辈子第一次上线」，一台设备一辈子只会发有限几次（出厂一次，恢复出厂各一次）。BOOT 是「我这次开机了」，每天都在发。ACS 侧对这两个的处理完全不同：收到 BOOTSTRAP 判定为新设备，走完整入网流程，下发全套开局参数，在库里建档；收到 BOOT 走轻量流程，只核对版本和关键参数，有差异才下发。如果一台设备反复发 BOOTSTRAP，说明它的配置存不住，每次重启都退回出厂状态——这是硬件或者存储故障的信号。

8.3 事件是数组，不是单值 #

Inform 里的 Event 是个结构体数组，一次可以带多个 EventCode：

xml
<Event SOAP-ENC:arrayType="cwmp:EventStruct[2]">
  <EventStruct>
    <EventCode>1 BOOT</EventCode>
    <CommandKey>fw-20241118</CommandKey>
  </EventStruct>
  <EventStruct>
    <EventCode>4 VALUE CHANGE</EventCode>
    <CommandKey>fw-20241118</CommandKey>
  </EventStruct>
</Event>

这个设计很实用：设备重启后发现上次的固件任务已经应用，同时检测到版本参数变了，两件事可以在一次 Inform 里报完。CommandKey 在每个 EventStruct 里都有，是 ACS 上次下发时带的标记。设备重启后上来第一件事是回传这个 key，ACS 一看就知道「上次那个任务，设备重启过了，得重新核对结果」。

8.4 参数变更通知怎么开 #

4 VALUE CHANGE 不是默认就有的，要 ACS 先显式开启——用 SetParameterAttributes 把目标参数的 Notification 设成 1 或 2，NotificationChange 填 true。取 0 不上报，取 1 是被动上报（值变了等下次 Inform 才带出去），取 2 是主动上报（值变了立刻发起一次 Inform）。

2 和 1 的差别在延迟。WAN 口 IP 变了这种事件需要 2，因为要立刻知道；Wi-Fi 密码变了用 1 就够，等下次周期上报顺手带出去。

2 用多了会出事。一台设备开着几十个参数 Notification = 2，网络一抖，参数连环变化，每次都触发 Inform，一条会话接一条会话。百万台设备一起这么干，ACS 直接过载。开启前算一下量。

8.5 一次主动通知的完整路径 #

用户在光猫后台改了 Wi-Fi 密码，CPE 内部检测到 ...WLANConfiguration.1.KeyPassphrase 变化（前提是这个参数的 Notification = 2），发起新的 CWMP 会话，POST Inform 带 EventCode = 4 VALUE CHANGE，ParameterList 里附上变化参数的新值。ACS 回 200 OK + InformResponse，CPE 发空 POST，ACS 下发后续命令——或者 SetParameterValues 把值改回去，或者只记日志，然后会话结束。

注意最后一步：ACS 会否决这个改动。用户自己在光猫上改了 Wi-Fi 密码，运营商的策略不允许，ACS 就会在下一次会话里把值改回原样。

8.6 告警怎么落地 #

CWMP 没有独立的「告警」RPC，告警全靠事件上报：

告警类型 实现方式
设备掉线 ACS 侧算：超过 PeriodicInformInterval 的 3 倍没收到 Inform
设备重启 1 BOOT 事件
配置变更 4 VALUE CHANGE 事件
升级失败 TransferComplete 里 FaultCode != 0
诊断异常 8 DIAGNOSTICS COMPLETE 后读结果参数
链路告警 厂商私有事件 M X_XXXX

「设备掉线」这条要划重点：CWMP 协议里没有「离线通知」这个概念。 CPE 掉电了不会发任何东西，ACS 只能靠「下次心跳该来没来」推断。所以判断设备离线的时效性等于心跳周期的 3 倍左右——心跳 1 小时，最慢 3 小时才能确认掉线。要做准实时离线检测，得靠接入网层的其他手段（OLT 的 ONU 状态、PPPoE 会话状态），不能只靠 CWMP。

九、固件升级与配置下发 #

9.1 升级的完整时序 #

固件升级是 CWMP 里最长的流程，跨三次会话：

text
会话 1：CPE ── Inform ──► ACS ── Download(FileType=1, URL=...) ──► CPE
        CPE 回 DownloadResponse（已接受），关闭连接。目的：下发升级指令
会话 2：CPE ── HTTP GET /fw/HA930e_V2.1.bin ──► 文件服务器（不走 CWMP）
        校验大小、CRC、版本、签名、硬件型号，写 flash，标记下次启动用新镜像
会话 3：CPE ── Inform(7 TRANSFER COMPLETE) + TransferComplete(FaultCode=0) ──► ACS
        设备重启，加载新固件，再用 Inform(1 BOOT，SoftwareVersion 已变) 上线

会话 2 不是 CWMP 会话。 这点容易搞混：文件传输本身是标准 HTTP 下载，ACS 只是把 URL 和凭据给了 CPE。所以固件服务器和 ACS 服务器是两台不同的机器，甚至在不同机房。带宽压力落在文件服务器上，不在 ACS 上。

9.2 Download 参数逐个说 #

xml
<cwmp:Download>
  <CommandKey>fw-20241118-batch003</CommandKey>
  <FileType>1 Firmware Upgrade Image</FileType>
  <URL>http://files.example-carrier.com/fw/HA930e_V2.1.bin</URL>
  <Username>fwuser</Username>
  <Password>fwpass</Password>
  <FileSize>8388608</FileSize>
  <DelaySeconds>0</DelaySeconds>
</cwmp:Download>
参数 必需 作用 实践建议
CommandKey 是 任务标识，TransferComplete 时回传 用「批次-设备-序号」形式，方便对账
FileType 是 文件类型，决定怎么处理 固件固定填 1 Firmware Upgrade Image
URL 是 文件地址 用域名不用 IP，方便换服务器
Username / Password 否 HTTP 下载认证凭据 别和 ACS 的凭据混用，定期轮换
FileSize 否 文件字节数，用于校验 一定要给，设备能提前发现空间不足
TargetFileName 否 本地存储路径 留空，让设备自己决定
DelaySeconds 否 延迟多少秒后开始下载 错峰用，比如 3600 散开一小时
SuccessURL / FailureURL 否 成功后/失败后 CPE 额外 GET 一次 不依赖 CWMP 也能知道结果

FileSize 值得单说。大包下载最怕「下到一半发现空间不够」，带上准确的文件大小，设备能在开始前判断存储余量，不够就直接失败，省一次几十分钟的无用传输。

DelaySeconds 是错峰的核心手段。百万台设备同时去拉 8MB 的包，文件服务器出口带宽瞬间打满。按区域、按 OUI 分几批，DelaySeconds 分别填 0、3600、7200。别切太多批——延迟太大设备会在下载前就重启了，CommandKey 对不上。

9.3 固件校验：设备侧必须做的四件事 #

检查项 做错了会怎样
文件完整性（大小、CRC） 半包固件刷进去，设备起不来
版本比对（防降级/防重刷） 刷同版本浪费时间，刷旧版本回退功能
签名校验 恶意固件能刷进去
硬件匹配（ProductClass、硬件版本） 刷错型号，彻底砖

素材里明确写了：目前设备不支持以数字签名的方式进行的文件下载。这是老设备的现实——签名校验做不了，只能靠 CRC 加 URL 权限控制。新设备应该做签名。ProductClass 匹配最容易被忽略，同一批下发的 URL 如果被一台 ProductClass 不同的设备拿到，它会把自己刷成砖。ACS 侧下发前必须按 ProductClass 过滤任务范围。

9.4 批量升级的节奏 #

阶段 覆盖比例 停留时间 卡住的条件
灰度 0.1%（内测设备） 24 小时 成功率 < 95%
小批 1% 48 小时 在线率降 1 个点
中批 10% 72 小时 用户投诉异常抬升
大批 40% 96 小时 同上
全量 剩余 — 同上

这套东西本质是发布流程，和互联网发版一个逻辑。区别在于你发的是几百万台不可控的硬件，用户在家里，出问题就是断网。

9.5 配置下发的三条纪律 #

xml
<cwmp:SetParameterValues>
  <ParameterList SOAP-ENC:arrayType="cwmp:ParameterValueStruct[2]">
    <ParameterValueStruct>
      <Name>InternetGatewayDevice.ManagementServer.PeriodicInformInterval</Name>
      <Value xsi:type="xsd:unsignedInt">1800</Value>
    </ParameterValueStruct>
    <ParameterValueStruct>
      <Name>InternetGatewayDevice.LANDevice.1.WLANConfiguration.1.SSID</Name>
      <Value xsi:type="xsd:string">CMCC-Home</Value>
    </ParameterValueStruct>
  </ParameterList>
  <ParameterKey>provision-20241118</ParameterKey>
</cwmp:SetParameterValues>

第一条，一批别超过 50 个参数。 大包在某些设备上会触发超时或者内存不足。分几批发，每批一个 ParameterKey，好定位问题。

第二条，按依赖顺序排。 有些参数依赖别的参数先就位。比如改 WANPPPConnection 的 Username 和 Password，得先把 Enable 打开。顺序错了会返回 9007。

第三条，ParameterKey 必须唯一且在库里有记录。 设备下次 Inform 会把它填进 CommandKey。ACS 收到一个不认识的 CommandKey，说明有任务在库里丢了记录，这是要告警的异常。

9.6 ACS URL 迁移：把第五章那个例子讲透 #

第五章那十一步，落到操作上就是改三个参数：ACS 查 ManagementServer.URL，发现是自己（http://old-acs.example-carrier.com:9090/openacs/acs），于是下发 SetParameterValues 把 URL 改成 http://new-acs.example-carrier.com:9090/acs，Username 和 Password 同步换成新的，CPE 回 Status = 0，会话结束，之后用新 URL 连新 ACS。

三个参数必须一起改。只改 URL 不改凭据，新 ACS 认证不过，设备从此失联。

一个更危险的情况：SetParameterValues 成功了，但新 ACS 地址是错的（网络没通、DNS 没生效）。设备下次连不上，回退机制要看厂商实现——有的设备连不上之后会回退到旧 URL，有的不回退，直接失联。

稳妥做法是两步走：先下发备用 ACS 地址（如果厂商支持备用槽位），不动主 URL；确认新 ACS 上有这台设备的上线记录，再改主 URL。不支持备用槽位的设备，只能靠「改完立刻验证」——下发后 5 分钟内查新 ACS 的上线列表，没上线就赶紧改回去。这需要 ACS 侧有自动回滚机制。

十、与 SNMP 的对比 #

10.1 一张表看懂差别 #

同目录那篇《SNMP》讲的是另一条路。两个协议都叫「管设备」，设计目标完全不同：

维度 CWMP（TR-069） SNMP
传输层 TCP UDP（161/162）
应用层承载 SOAP（XML）over HTTP BER 编码的 PDU

这张表里三行最重要：TCP vs UDP、反向 vs 正向、写 vs 读。把这三行记住，两个协议就不会混。

10.2 为什么一个用 TCP 一个用 UDP #

这不是随便选的，是两个场景逼出来的。

CWMP 必须用 TCP。 它的报文大。一个 SetParameterValues 带上几十个参数，XML 编码后几 KB；Inform 的 ParameterList 也能到几 KB。UDP 单包 1472 字节就得分片，分片一丢整包重传，效率反而更差。而且 CWMP 的下发必须可靠——Set 命令丢了，设备配置就是错的，没人知道。TCP 的重传、保序、流控正好都是必需的。

SNMP 用 UDP 是合理的。 它的 PDU 小，一个 GET 几十个字节，一个包装得下。监控场景对丢包容忍度高——这次没采到，15 秒后再采一次就行。用 UDP 省掉握手开销，一台 NMS 能轮询几千台设备。Trap 用 UDP 更彻底：设备出事了先把告警发出去，不关心对面收没收到。

反过来说，如果你要用 SNMP 做配置下发（SET），可靠性就成了问题——UDP 丢了不知道。这也是为什么企业网的真实配置下发大多走 CLI/SSH/NETCONF，不走 SNMP SET。

10.3 设备树 vs MIB 树 #

两个都是树，长得像，用起来差别大。SNMP 的 MIB 树用数字 OID 定位，1.3.6.1.2.1.1.1.0 是 sysDescr.0。你得查 MIB 文件才知道这个数字是什么意思，而且不同厂商的私有 MIB 各占一个分支，互不兼容。

CWMP 的设备树用字符串路径，InternetGatewayDevice.DeviceInfo.SoftwareVersion 看名字就知道是什么。这是 CWMP 的一个实在优势——可读性直接决定排障效率，抓包一眼能看懂。代价是路径长、报文大，InternetGatewayDevice.WANDevice.1.WANConnectionDevice.1.WANIPConnection.1.ExternalIPAddress 这一条 88 个字符，编码进 XML 又要加一层标签。

10.4 谁在什么场景下用哪个 #

场景 选哪个 理由
企业机房交换机端口流量监控 SNMP 轮询几十个 OID，UDP 开销小
运营商管理百万台家庭光猫 CWMP 穿透 NAT，能改配置，能推固件
服务器 CPU/内存采集 SNMP 标准 MIB-II 现成，Zabbix/Prometheus 都有插件
远程给光猫改 Wi-Fi 密码 CWMP SNMP 没标准方法，且穿不过 NAT
设备告警上报 都能做 Trap 轻量但会丢；Inform 可靠但重
固件批量升级 CWMP SNMP 完全没有这套机制

一个容易忽略的事实：很多运营商的家庭网关同时开着 SNMP 和 CWMP。 SNMP 用于本地网管或者接入网设备侧采集，CWMP 用于省侧 ACS 的远程管理。两个 agent 跑在同一台盒子上，端口不同，互不干扰。你在设备上抓包看到 161 和 7547 同时有流量，正常。

十一、调试与抓包 #

11.1 抓包位置 #

抓包位置 能看到 看不到
光猫 LAN 侧 CPE ↔ ACS 全流程（如果 ACS 可达） 上游 NAT 后的真实端口
光猫 WAN 侧 出站到 ACS 的流量 内网侧的 Connect Request
运营商汇聚点 聚合流量，量大 单设备细节，除非过滤
ACS 服务器上 完整会话，最好排查 网络层问题（丢包、TLS 失败）

实战里最管用的组合是在 ACS 服务器上抓 + 在光猫上 tcpdump。两边对时间轴，问题基本藏不住。

text
tcpdump -i any -s 0 -w /tmp/cwmp.pcap port 7547        # 抓默认端口
tcpdump -i any -s 0 -w /tmp/cwmp.pcap port 9090        # 抓非标准端口
tcpdump -i br0 -s 0 -w /tmp/dev.pcap host 192.168.7.143 # 抓单台设备
tcpdump -i any -A -s 0 port 7547 | grep -E 'POST|Inform|SOAP'  # 直接打印 HTTP 层

-s 0 必须加，否则默认只抓 262144 字节，大 XML 会被截断，Wireshark 里显示 [Packet size limited during capture]。

11.2 Wireshark 怎么读 #

CWMP 走 7547 端口时，Wireshark 会自动识别成 HTTP 并尝试解析 SOAP。实用过滤条件：

目的 过滤表达式
过滤一台设备 http and ip.addr == 192.168.7.143
只看 Inform http.request.method == "POST" and frame contains "Inform"
看 RPC 方法名 frame contains "GetParameterValues" or frame contains "SetParameterValues"
找错误 frame contains "Fault" or frame contains "9007"
看会话正常结束 http.response.code == 204

Follow > TCP Stream 是最快的读法，一次会话的完整 XML 都在里面，比逐包点开快十倍。如果 ACS 用了非标准端口而 Wireshark 没识别成 HTTP，右键 Decode As > HTTP 手动指定。

11.3 从零验证一台设备 #

接手一台新设备或者排查一台失联设备，按这个顺序走：

步骤 动作 期望结果 失败说明
1 确认设备有 IP ip addr 能看到地址 DHCP 没通
2 确认能解析 ACS 域名 nslookup acs.xxx.com DNS 配错或没下发
3 确认能连 ACS 端口 nc -zv acs.xxx.com 7547 路由或防火墙
4 确认 TLS 能握手 openssl s_client -connect acs.xxx.com:8443 证书过期或 CA 不对
5 手动发一个 Inform curl 构造 POST 见下面的命令
6 看 ACS 侧有没有记录 查设备档案表 认证失败或 URL 错
7 验证 ConnectionRequestURL 从外网 curl 那个地址 NAT 没映射 
text
curl -v -X POST 'http://acs.example-carrier.com:7547/acs' \
  -H 'Content-Type: text/xml' -H 'SOAPAction:' \
  -u 'cpeuser:cpepass' --data-binary @inform.xml

inform.xml 就是第三章那个报文，把 DeviceId 和 SerialNumber 改成被测设备的。这个办法在验证 ACS 侧行为时特别有用——可以绕开设备，直接测 ACS 对各种异常报文的处理。

11.4 五个高频故障 #

设备一直发 BOOTSTRAP。 配置存不住。查设备的持久化存储，多半是 flash 只读或者配置分区满了。

ConnectionRequestURL 打不通。 最常见。三种原因：设备在双层 NAT 后面，报的地址是内层私网；NAT 没给那个高位端口做映射；防火墙拦了入站。先让设备重新 Inform 刷一次 ConnectionRequestURL，再测。

ACS 显示设备在线，但下发命令全部超时。 多半是会话卡住了。CPE 发了空 POST，ACS 处理业务逻辑时阻塞（比如查库慢），超过 HTTP 空闲超时，连接被断。查 ACS 侧的线程栈和慢查询。

SetParameterValues 返回成功但配置没变。 设备侧参数存取层的 bug。Set 只写了内存没写持久化，或者写了持久化但没通知业务进程 reload。这种情况抓 CWMP 包看不出问题，得上设备看配置文件。

固件下载卡在 99%。 文件服务器的问题居多。Content-Length 和实际文件大小不一致，或者代理层做了 gzip 压缩导致字节数对不上。检查文件服务器的 Content-Length 头，再检查中间有没有反向代理。

11.5 常用的排查命令 #

text
ps | grep -i cwmp                            # 看 CWMP 进程
logread | grep -i cwmp                       # 看客户端日志
uci show tr069                               # 看 ACS 地址等配置（OpenWrt 系）

十二、易错点速查 #

12.1 协议理解类 #

易错点 正确理解
以为 ACS 能主动连 CPE 不能。CPE 主动连 ACS，ACS 只能用 ConnectionRequestURL 敲门
以为 CWMP 走 UDP 走 TCP。UDP 是 SNMP
以为一个 HTTP 请求就是一个 RPC 一次会话里可以有多个 RPC，靠空 POST 循环
以为 Inform 只有开机才发 还有 PERIODIC、VALUE CHANGE、CONNECTION REQUEST 等
以为会话结束是 ACS 关连接 是 CPE 关。ACS 只回 204 No Content
以为 Download 返回成功就升级完了 那只是「命令已接受」，要看 TransferComplete
以为 Set 成功就一定生效 Status=1 表示重启后才生效；也会被设备侧实现吞掉
以为 CWMP 能推实时告警 掉线靠心跳超时推断，最慢 3 个周期

12.2 报文构造类 #

易错点 后果 正确做法
xsi:type 漏写 严格 ACS 报 9006 每个 Value 都写
cwmp:ID 没原样回传 ACS 认不出应答 逐字节复制
Content-Type 带 charset 部分设备不认 用 text/xml
SOAPAction 非空 部分 ACS 拒绝 留空
单包塞 200 个参数 设备超时或 OOM 分批发，每批 ≤ 50
用 ftp:// URL 回 9013 用 http:// 或 https://
路径拼错一个层级 回 9005 先 GetParameterNames 确认
多实例编号当固定值 删加实例后错乱 先枚举再操作

12.3 部署运维类 #

易错点 后果 正确做法
PeriodicInformInterval 设太小 ACS 被心跳打满 最少 900 秒，常网用 1800～3600
Notification = 2 开太多 通知风暴 只对关键参数开，其余用 1
全网同时推固件 文件服务器带宽打满 DelaySeconds 分批，灰度先行
只改 URL 不改凭据 设备全部失联 三个参数一起改
FactoryReset 前不确认 抹掉 ACS 地址，设备失联 先确认设备的实现细节
FileSize 不传 空间不足时下到一半才失败 一定带上准确值
不按 ProductClass 过滤 刷错型号变砖 任务范围按型号精确圈定
明文 HTTP 跑 7547 被扫描利用 上 HTTPS，关外网直连

12.4 排障思路 #

遇到 CWMP 问题，先分层定位，别一上来就抓包：

text
现象：设备在 ACS 上显示离线
  ├─ 1. 网络层：能 ping 通 ACS 吗？
  │     └─ 不能 → 查线路、DHCP、路由
  ├─ 2. 传输层：TCP 7547 能连上吗？（nc -zv）
  │     └─ 不能 → 查防火墙、ACS 监听、负载均衡
  ├─ 3. 安全层：TLS 握手成功吗？（openssl s_client）
  │     └─ 失败 → 查证书到期日、CA 链、域名匹配
  ├─ 4. 应用层：Inform 发出去了吗？ACS 回了吗？（抓包）
  │     └─ 发出没回 → 查 ACS 日志、认证配置
  └─ 5. 业务层：ACS 认得这台设备吗？档案建了吗？
        └─ 不认 → 查 DeviceId 三元组、库里有没有记录

这五层从下往上，一层层排。跳层排查的结果往往是白费功夫——你盯着 SOAP 报文看半天，问题其实在 VLAN 没通。

最后一条实践心得：CWMP 的绝大多数「协议问题」，根子都不在协议。 协议本身很稳定，2004 年定下来到现在没大改。出问题的永远是网络、证书、设备实现、配置错误这四样。把排查精力按这个比例分配，效率最高。
