这一篇讲 SNMP。一个用「按编号读指标」的方式管理网络设备的协议。我们会拆开它为什么长成这样、五个操作怎么分工、MIB 和 OID 到底谁是谁、v1/v2c/v3 的安全差在哪。

讲什么：SNMP 的定位、三个角色、五个基本操作、报文结构、MIB 与 OID、MIB 树与常用节点、v1/v2c/v3 的认证与报文差异、部署与排查、易错点速查。

不讲什么：BER 编码的逐字节拆解、SMI 的完整 ASN.1 语法、厂商私有 MIB 的逐个节点、SNMP 与 gNMI/NetFlow 的替代关系、以及 SNMP 表格索引的完整推导规则。

跨篇指路：要改家庭网关（CPE）的配置、要远程下发参数，走的是 CWMP/TR-069，见同目录《CWMP（TR-069）》。HTTP 和 DHCP 也在同目录。SNMP 的强项是读，不是写——这一点先记住。

一、SNMP 解决什么问题 #

机房里有三十台交换机、八台路由器、两台防火墙。你要回答几个日常问题：哪个口在丢包、哪台设备的 CPU 打满了、谁的电源模块温度偏高、核心路由表里有没有多余的路由。

没有 SNMP 的年代，答案是 telnet 进去敲 show interface，一台一台看。三十台设备，一轮巡检两小时，还没法做趋势。这是 SNMP 要解决的第一件事：把「看设备」从人工逐台登录，变成程序按编号批量取数。

有 SNMP 之后，设备上跑一个常驻进程，对外暴露一棵带数字编号的指标树。管理站想读什么，就发一个带编号的请求过去，代理把那个编号对应的值填回来。

这就是 SNMP 的第一个核心认知：它是「查字典」模型。

设备上每一个可读（有些可写）的指标，都有一个唯一的 OID，长得像文件路径：

text
1.3.6.1.2.1.1.5.0        →  sysName，设备名字
1.3.6.1.2.1.1.3.0        →  sysUpTime，开机多久
1.3.6.1.2.1.2.2.1.8.3    →  ifOperStatus.3，第 3 个接口的 up/down 状态

管理站不需要知道设备是华为还是思科，不需要知道它的 CLI 语法，它只需要知道「设备名字在 1.3.6.1.2.1.1.5.0」。代理也不需要理解管理站想问什么业务，它只需要按 OID 查表，把值填进响应报文。

这个设计有个硬性后果，很多人第一次用 SNMP 就栽在这里：OID 只有数字，数字本身没有语义。1.3.6.1.2.1.1.5.0 返回 SW-CORE-01，你能猜出是名字；但 1.3.6.1.2.1.2.2.1.8.3 返回 1，你不查 MIB 就不知道 1 是 up 还是 down——在 ifOperStatus 的枚举里 1 是 up，2 是 down，3 是 testing。MIB 就是这本字典的定义：它给每个 OID 配上名字、类型、取值范围、读写权限。没有 MIB 文件，你手里只有一串数字和一串数字。

所以完整的一套 SNMP 系统包含三件东西，缺一件就用不顺：

组成 英文 作用
管理信息库 MIB 定义有哪些对象、叫什么、什么类型、能不能写
管理信息结构 SMI 规定 MIB 文件本身怎么写（语法、宏、基本类型）
报文协议 SNMP 规定管理站和代理之间怎么问、怎么答、怎么主动上报

MIB 是内容，SMI 是写 MIB 的语法规则，SNMP 是搬内容的车。三者分工清楚，缺 MIB 只能看裸数字，缺 SMI 写不了自己的 MIB，缺报文协议两头说不上话。

一段历史，只看结论 #

SNMP 不是凭空设计的。1988 年它被定下来，前身是 SGMP（简单网关监视协议）。当时 TCP/IP 正在铺开，IAB 需要一个能立刻用的网络管理方案，OSI 那套 CMIP 太重、太慢、太贵。SNMP 被当作短期方案采纳，逻辑是「先能用」。

结果短期方案活成了长期标准。设备厂商愿意实现它，因为它简单：UDP 承载、请求-响应、没有复杂的状态机。1992 年出了 SNMPv2，补了安全和功能；再往后是 SNMPv3，把认证和加密正经做了进去。今天我们见到的设备，v1、v2c、v3 三个版本经常同时开着。

这个历史解释了 SNMP 所有让人别扭的地方：

  • 为什么用 UDP 不用 TCP：1988 年的取舍，省连接状态。代价是要自己做超时和重传。
  • 为什么认证这么弱：v1 设计时假设网络内部可信，团体名当口令用。
  • 为什么 GETBULK 是后来才加：v1 只有 GETNEXT，遍历一张大表要几百个来回。
  • 为什么 v3 这么啰嗦：安全是后期补的，只能在报文头上加一层，不能推倒重来。

SNMP 不做什么 #

这一点必须先划清，不然容易把它和配置管理混在一起。SNMP 是监控协议，不是配置下发协议。

它的 SET 操作确实能写，但实践中很少用 SET 去改业务配置。原因很实在：一台设备几千个可写 OID，写错一个就是业务中断，而且没有事务、没有回滚、没有变更审计。厂商也不乐意把配置项全开成可写 OID。

真正要批量改配置、要下发参数、要远程升级家庭网关，那是 CWMP（TR-069）的活。两者的外形确实像——都是「一个中心站管一堆设备」——但分工不同：

维度 SNMP CWMP（TR-069）
主要对象 交换机、路由器、防火墙、服务器、UPS 家庭网关、机顶盒、光猫这类 CPE
主要动作 读指标、收告警 读参数 + 改配置 + 升级固件 + 重启
传输 UDP 161/162 HTTP/HTTPS 上的 SOAP
数据模型 MIB + OID 编号树 参数树（InternetGatewayDevice.…）
谁发起 管理站主动轮询；代理发 Trap CPE 主动连 ACS（Connection Request 反向通知）
典型场景 流量采集、接口状态、告警 装机开通、远程排障、批量升级

一句话记法：SNMP 盯着设备看，CWMP 伸手进设备改。要改，看《CWMP（TR-069）》那篇。

二、三个角色：管理站、代理、MIB #

SNMP 的通信模型是「管理站 / 代理」模型，加上一个双方共享的 MIB 作为接口契约。

角色 英文 跑在哪 干什么
管理站 NMS / Manager 网管服务器 发请求、收响应、收 Trap、存时序数据、画图告警
代理 Agent 被管设备上 监听 161、校验团体名/用户、按 OID 查本地 MIB、回响应
管理信息库 MIB 两边都有 定义对象的名称、类型、权限；是双方的接口契约

严格说 MIB 不是「角色」，它是契约。但把它当第三个角色理解更省事：管理站手里有一份 MIB，知道 1.3.6.1.2.1.2.2.1.8 叫 ifOperStatus、是枚举；代理手里也有一份 MIB，知道这个节点怎么从硬件取值。两边 MIB 版本对不上，就会出现「我按名字问，你按数字答，答的还是另一棵树上的东西」。

一次查询的完整路径 #

管理站发 GET 1.3.6.1.2.1.1.5.0，报文被封装进 UDP，目的端口 161。代理收到后依次做：

  1. 按 ASN.1 的 BER 规则解码报文。解不出来，丢包，不回应。
  2. 取版本号。跟本机支持的版本对不上，丢包。
  3. 取团体名（v1/v2c）或走 USM 认证（v3）。校验不过，丢包，同时产生一个 authenticationFailure 陷阱。
  4. 取出 PDU，按类型分派：GET 就查树、GETNEXT 就找后继、SET 就写值、GETBULK 就批量取。
  5. 把结果编成响应报文，源地址填成请求的目的地址，发回管理站的 161。

管理站收到响应，比对 request-id 和自己发出去的那条，确认是这条请求的答案，然后把值交给上层存库或展示。

注意第 3 步那个细节：团体名校验失败会产生一个 Trap。这是 SNMP 里少见的「安全事件上报」机制，扫段工具打过来的时候，设备会往 162 端口吐一串 authenticationFailure。排查「谁在扫我」时这条很有用。

端口与封装 #

方向 源 → 目的 端口 承载
GET / GETNEXT / GETBULK / SET 管理站 → 代理 161 UDP
Response 代理 → 管理站 161 UDP
Trap（v1/v2c/v3） 代理 → 管理站 162 UDP
Inform 代理 → 管理站 162 UDP
Inform Response 管理站 → 代理 162 UDP

161 是代理的「服务端口」，162 是管理站的「接告警端口」。这俩必须分清楚：防火墙只放了 161，你的 GET 能通，但一台设备都收不到 Trap。反过来只放 162，告警哗哗来，snmpget 全超时。

共享的是编号，不是实现 #

管理站和代理能对话，靠的是双方对「编号 → 含义」的理解一致。这个一致性由 MIB 保证，不由代码保证。

举个能直接踩到的例子。标准 MIB-II 里 ifDescr 是 1.3.6.1.2.1.2.2.1.2，返回接口描述，类型是 DisplayString。华为某些型号在这上面返回 GigabitEthernet0/0/1，思科返回 GigabitEthernet1/0/1，某国产小厂返回 eth0。编号一样，类型一样，值的内容各写各的。你的采集脚本如果按值做字符串匹配取接口类型，换一批设备就崩。

正确的做法是按编号取 ifType（1.3.6.1.2.1.2.2.1.3，IANAifType 枚举），按编号取 ifSpeed 或 ifHighSpeed。编号是标准，值是厂商的自由发挥空间。所有「换设备就采集乱」的问题，八成是把值当成了语义。

ifIndex 的坑更经典。ifIndex 是接口在表里的索引，不是端口号。设备重启、插拔板卡、加个 VLAN 口，ifIndex 就会重排。今天 ifIndex=3 是 Gi0/0/1，明天就变成 Gi0/0/3。这就是为什么正经的监控系统每次轮询都要把 ifDescr 或 ifName 一起取回来做映射，不能靠 ifIndex 硬编码。

三、五个基本操作 #

SNMP 的操作数不多，五个加一个响应。这五个的分工是关键，用错一个就多跑几百个来回。

操作 PDU 类型码 谁发起 方向 用途 版本
GET 0 管理站 → 代理 读一个指定 OID 的值 v1
GETNEXT 1 管理站 → 代理 读指定 OID 的下一个节点，用于遍历 v1
SET 3 管理站 → 代理 写一个 OID 的值 v1
RESPONSE 2 代理 → 管理站 回上面三种请求 v1
TRAP 4（v1）/ 7（v2+） 代理 → 管理站 设备主动上报，不等回应 v1
GETBULK 5 管理站 → 代理 一次批量读多个后继 v2c
INFORM 6 代理 → 管理站 主动上报，等一个回应 v2c

GET：读一个 #

GET 是最直白的操作。给它一个完整 OID（带实例后缀），它返回那个实例的值。

bash
snmpget -v2c -c public 192.168.2.1 1.3.6.1.2.1.1.5.0
# SNMPv2-MIB::sysName.0 = STRING: SW-CORE-01

一次 GET 可以在变量绑定列表里塞多个 OID，代理一次回全。这是省往返的正当手段，抓包能看到 varbind 里排着三五个 OID，响应里按同样顺序回来。

注意那条 .0。标量对象（就一个值，不成表）的实例后缀固定是 0。sysName 的对象 OID 是 1.3.6.1.2.1.1.5，但你不能 GET 它，GET 的是 1.3.6.1.2.1.1.5.0。少了这个 .0，很多代理直接回 noSuchName。这是新手第一个坎。

GETNEXT：遍历 MIB 树的基础 #

GETNEXT 是 SNMP 里最重要的操作，也是最多人没真正理解的操作。

它问的不是「这个 OID 的值是多少」，而是「比这个 OID 大的下一个 OID 和它的值是什么」。按 MIB 树的先序遍历顺序找直接后继，把后继的完整 OID 和值一起返回。

这个「不告诉你有什么，只告诉你下一个是什么」的设计，解决了一个大问题：管理站事先不知道设备上有哪些接口、哪些路由、多少行。表有多大，管理站事先不知道。用 GETNEXT，它可以从一个已知起点出发，一路问下去，直到走出这棵子树。

snmpwalk 就是这个过程的封装：反复发 GETNEXT，直到返回的 OID 不再落在起始子树的范围内。

bash
# 从 mib-2 的 system 子树起点开始，把整棵子树走一遍
snmpwalk -v2c -c public 192.168.2.1 1.3.6.1.2.1.1

用路由表看 GETNEXT 怎么走 #

素材里那个例子值得完整走一遍，因为它把「表遍历」讲透了。

被管设备上有一张路由表：

Destination NextHop Metric
10.0.0.99 89.1.1.42 5
9.1.2.3 99.0.0.3 3
10.0.0.51 89.1.1.42 5

这张表的索引是目的网络地址。管理站想取三列：ipRouteDest、ipRouteNextHop、ipRouteMetric1。

第一步，管理站发：

text
GetNextRequest ( ipRouteDest, ipRouteNextHop, ipRouteMetric1 )

注意这里给的是列的对象 OID，不带实例。代理按后继规则，返回每一项的第一个实例，也就是字典序最小的那一行：

text
GetResponse (( ipRouteDest.9.1.2.3       = "9.1.2.3" ),
             ( ipRouteNextHop.9.1.2.3   = "99.0.0.3" ),
             ( ipRouteMetric1.9.1.2.3   = 3 ))

第二步，管理站把刚拿到的实例 OID 原样发回去，代理返回下一行：

text
GetNextRequest ( ipRouteDest.9.1.2.3, ipRouteNextHop.9.1.2.3, ipRouteMetric1.9.1.2.3 )
GetResponse (( ipRouteDest.10.0.0.51     = "10.0.0.51" ),
             ( ipRouteNextHop.10.0.0.51 = "89.1.1.42" ),
             ( ipRouteMetric1.10.0.0.51 = 5 ))

第三步，再推一轮：

text
GetNextRequest ( ipRouteDest.10.0.0.51, ... )
GetResponse (( ipRouteDest.10.0.0.99     = "10.0.0.99" ),
             ( ipRouteNextHop.10.0.0.99 = "89.1.1.42" ),
             ( ipRouteMetric1.10.0.0.99 = 5 ))

第四步，管理站拿 10.0.0.99 再问一次。这一轮代理必须诚实回答：这张表已经走完了，下一个节点是 MIB 树里 ipRouteTable 整棵子树的后继——netToMediaIndex。返回的 OID 跳出了 ipRouteTable 的范围，管理站据此判定遍历结束。

text
GetNextRequest ( ipRouteDest.10.0.0.99, ... )
GetResponse (( netToMediaIndex = ... ))     ← 出界了，停止

代理这一侧的硬要求是：必须能确定下一个管理变量名，保证每个变量被取到、且只被取到一次。听起来不难，实际有坑——表在遍历过程中变了（有进程在插路由），「下一个」就会跳过一个节点或重复一个节点。所以严格遍历要配 snmpwalk 之外的稳健策略，比如取完再校验行数、或者用 GETBULK 减小时窗。

标量（不成表的对象）走 GETNEXT 时，它的「下一个」是 MIB 树里的下一个节点。所以从 1.3.6.1.2.1.1 开始 walk，你会依次拿到 sysDescr.0、sysObjectID.0、sysUpTime.0、sysContact.0、sysName.0、sysLocation.0、sysServices.0，然后跳到 1.3.6.1.2.1.2（interfaces）。这个顺序就是 MIB 文件的定义顺序，反过来讲，MIB 文件的书写顺序决定了遍历顺序。

GETBULK：v2c 的批量读 #

GETNEXT 效率低在哪，算一下就清楚。一张 48 口的接口表，要取 8 个字段，等于 384 个实例。一次 GETNEXT 拿一个实例，就得 384 个请求-响应来回。每个来回哪怕 5ms，也是接近 2 秒。设备 CPU 还得处理 384 次解码、校验、查树。

GETBULK 把这件事压成一次往返。它在 PDU 里带两个参数：

参数 含义
non-repeaters 变量列表里前 N 个只取一个后继，不重复
max-repetitions 剩下的变量各重复取 M 个后继

对上面那个场景，把 8 个字段作为 repeating 变量、max-repetitions 给 48，一次请求就能拿回 8×48 个实例，响应塞满一个接近 1500 字节的 UDP 包。

bash
# snmpbulkwalk 就是 GETBULK 版的 walk
snmpbulkwalk -v2c -c public -Cr 10 192.168.2.1 1.3.6.1.2.1.2.2.1

参数选择有讲究。max-repetitions 给小了没省多少，给大了响应超过链路的 MTU 会给分片，设备直接回 tooBig。实践值 10 到 25 之间比较稳，按设备的 snmpEngineMaxMessageSize 和网络 MTU 调。

GETBULK 的本质仍是 GETNEXT，它只是把「代理替你连续调用 N 次」这件事打包进一个报文。理解这一点，你就不会被「为什么 GETBULK 也能遍历」这个问题绕住：它返回的照样是后继链，只是链更长。

SET：写 #

SET 在报文层面和 GET 几乎一样，只差 PDU 类型码。它把变量绑定里的值写进设备。

能写什么由 MIB 里的 ACCESS（或 SMIv2 的 MAX-ACCESS）字段决定：

权限值 含义
read-only / not-accessible 只能读或根本不能访问，写入必回 noSuchName
read-write 可读可写
read-create 可读、可写、还可创建新行（表里的新增行）
accessible-for-notify 只出现在 Trap 里，不可读写

实践中 SET 用得少，理由前面讲过：没有事务、没有回滚、风险高。真正会用 SET 的场景有几种：

  • 改 sysContact / sysLocation（设备归属信息，运维台账用）
  • 关某个接口：ifAdminStatus.3 = down（比登录设备敲命令快，批量做很方便）
  • 清计数器、重置某些状态位
  • 少数厂商把 save config 暴露成一个可写 OID

ifAdminStatus 是 SET 最经典的例子。它和 ifOperStatus 是一对：ifAdminStatus 是「你想让它什么状态」，可写；ifOperStatus 是「它实际是什么状态」，只读。写 ifAdminStatus 为 down，物理链路协商完 ifOperStatus 会变成 down。这两个混淆了会写出很奇怪的排查结论。

TRAP：设备主动上报，不等回应 #

前面四个都是管理站发起、代理应答。TRAP 反过来：设备自己出事，主动往管理站的 162 端口发一个报文，发完就走，不等任何回应。

典型场景：接口 up/down、设备冷启动/热启动、IP 地址变更、认证失败、电源模块异常、风扇停转、CPU 越阈。

发完不等回应这件事有两面。好处是代理不会被卡住，一个管理站挂了不影响设备。坏处是丢包没人管：UDP 本身不保证送达，TRAP 又没有确认，链路上丢一个，管理站永远不知道那次接口抖动发生过。核心告警靠 TRAP 是有风险的，得配合轮询兜底。

INFORM：带确认的 TRAP #

v2c 加的 INFORM 就是给 TRAP 补确认。机制很像：代理发一个 INFORM 到管理站 162，管理站必须回一个 Response。代理收到 Response 才算送达，没收到可以重发。

对比项 TRAP INFORM
发起方 代理 代理
目的端口 162 162
有无回应 无 有，管理站必须回 Response
可靠性 不保证送达 可重传，可靠
代价 低 代理要维护重传队列和状态
引入版本 v1 v2c

抓包时区分这两个很快：TRAP 是单条报文，没有下文；INFORM 后面跟一条从管理站发回的 Response。

PDU 类型码速查 #

报文里的 PDU 类型是一个整数，值得记住几个：

类型码 PDU 上下文（v1） 上下文（v2c/v3）
0 GetRequest A0 A0
1 GetNextRequest A1 A1
2 GetResponse A2 A2
3 SetRequest A3 A3
4 Trap（v1 格式） A4 —
5 GetBulkRequest — A5
6 InformRequest — A6
7 SNMPv2-Trap — A7
8 Report — A8

A0 到 A8 是 BER 编码里的 tag 字节（上下文类构造型）。抓包工具里看到 A0 就知道是 GET，看到 A7 就知道是 v2 格式的 Trap。v1 的 Trap 是 A4，v2 改成 A7 并且换了结构，这是版本对比那一章的重点。

四、报文结构 #

一个 SNMP 报文分三段：公共首部、PDU 首部（GET/SET 一种、Trap 另一种）、变量绑定。全部用 ASN.1 的 BER 规则编码，整个报文塞进一个 UDP 数据报。

总体布局 #

text
+--------------------------------------------------+
| Message（SEQUENCE）                              |
|  Version         INTEGER    版本号（v1 写 0）    |
|  Community       OCTET STRING   团体名（明文）    |
|  PDU（GET/SET/Response/GETNEXT/GETBULK）         |
|    request-id      INTEGER                       |
|    error-status    INTEGER                       |
|    error-index     INTEGER                       |
|    variable-bindings  SEQUENCE OF                |
|       name(OID) + value                          |
+--------------------------------------------------+

Trap 的 PDU 换一套字段，下面单独说。

公共首部三个字段 #

字段 编码类型 说明
version INTEGER 版本号减 1。SNMPv1 写 0，SNMPv2c 写 1，SNMPv3 写 3
community OCTET STRING 团体名，明文口令，v1/v2c 靠它认证
PDU type tag 决定后面跟哪套 PDU 字段

版本字段「减 1」这个细节容易记错。v1 的版本字段是 0，不是 1。v2c 是 1（因为 v2 是 1），v3 是 3。抓包时看到 version: 0 就是 v1，version: 1 是 v2c，version: 3 是 v3。

团体名就是明文口令。出厂默认最常见的是 public（只读）和 private（可写）。抓包能直接看到 ASCII 的 public——安全性的问题就在这儿，后面 v1/v2c 那章细讲。

GET/SET/Response/GETNEXT/GETBULK 首部 #

字段 类型 说明
request-id INTEGER 请求标识，响应原样带回，用于匹配请求与响应
error-status INTEGER 差错状态，0~5（v2c 起扩展到 0~18）
error-index INTEGER 差错索引，指出变量列表里第几个变量出的错
variable-bindings SEQUENCE 变量名-值对列表

request-id 的作用值得单独说。管理站可以同时向许多代理发 GET，报文都走 UDP，先发的会后到。响应回来时，管理站靠 request-id 认出这是哪一条请求的答案。自己实现的采集器如果 request-id 复用了、或者不校验，就会把 A 接口的流量记到 B 接口上——这种错非常难查，因为数值都对，就是配错了行。

error-status 差错状态 #

v1 定了 6 个值，从 0 到 5：

值 名称 含义
0 noError 一切正常
1 tooBig 响应报文超过本地长度限制
2 noSuchName 请求的变量名在 MIB 树里不存在（或只读变量被 SET）
3 badValue SET 的值类型或长度不符合要求
4 readOnly 试图写一个只读变量（v1 早期用法，后被 noSuchName 归并）
5 genErr 其他原因导致失败

error-index 配 error-status 一起看。它是「出错变量在变量列表里的偏移」，从 1 开始数。一次 GET 带 5 个 OID，第 3 个不存在，回 noSuchName + error-index = 3。实现采集器时这一对必须解出来，否则你只知道「这次请求失败了」，不知道是哪个指标失败。

v2c 把错误码扩到 18 个，加了 noAccess、wrongType、wrongLength、wrongEncoding、wrongValue、noCreation、inconsistentValue、resourceUnavailable、commitFailed、undoFailed、authorizationError、notWritable、inconsistentName 这些。区分更细，这也是 v2c 相对 v1 的实质改进之一：v1 只说「错了」，v2c 说「错在哪一类」。

v1 的 Trap 首部 #

v1 的 Trap 报文完全不共用 GET/SET 的字段，它自己一套：

字段 类型 说明
enterprise OID 产生 Trap 的设备的对象标识符，在 1.3.6.1.4.1（enterprises）子树下
agent-addr IpAddress Trap 源的地址
generic-trap INTEGER 通用 Trap 类型，0~6
specific-trap INTEGER 企业私有 Trap 代码；generic-trap 为 6 时才有意义，否则填 0
time-stamp TimeTicks 从代理进程初始化到事件发生的时间，单位 10ms
variable-bindings SEQUENCE 变量绑定列表

generic-trap 的 7 个值：

值 名称 含义
0 coldStart 冷启动，设备重新初始化，配置跟着变
1 warmStart 热启动，设备重新初始化，配置没变
2 linkDown 一个链路 Down 了
3 linkUp 一个链路 Up 了
4 authenticationFailure 收到一个认证失败的报文（团体名错）
5 egpNeighborLoss EGP 邻居丢失（历史遗留，现在几乎见不到）
6 enterpriseSpecific 厂商自定义，具体含义看 specific-trap

用 2、3、5 这三种类型时，报文变量部分的第一个变量必须标识对应的接口（ifIndex）。这是规范要求，很多设备的实现会带上，但你的解析代码不能假设它一定在第一位——按 OID 找 1.3.6.1.2.1.2.2.1.1，别按位置取。

time-stamp 的单位是 10ms，容易看错。时间戳 1908 表示代理初始化后 19080ms（约 19 秒）发生了该事件，不是 1908 毫秒。素材原文写成「1908ms」是笔误。这个字段的绝对值没意义，两台设备的 sysUpTime 起点不同，只能做「同一台设备内的相对时间」用。

变量绑定 variable-bindings #

变量绑定是「名字 + 值」的列表，整个报文里只有这部分承载业务数据。

报文类型 变量的值字段
GET / GETNEXT 忽略，填 null（编码为 05 00）
SET 填入要写的值
Response 填入读到的值
Trap / INFORM 填入告警相关的值（如 ifIndex、ifAdminStatus）

GET 的值填 null 这一点，看抓包时会觉得奇怪：明明只关心名字，为什么还要带个空值字段？因为 BER 的 SEQUENCE 结构要求每个 varbind 都是完整的两元组，不能省。这也是 SNMP 报文偏大的原因之一。

管理变量的表示：x.y #

这一节是全文最该反复看的地方，因为它决定了你写的 OID 对不对。

管理变量的表示形式是 x.y：

  • x 是管理对象的 object identifier（对象本身的编号）
  • y 是能唯一确定该对象类型某个值的一组数字，叫实例（instance）

规则：

对象类型 实例部分 y
非表型（标量） 固定为 0
表型 该表的索引值

非表型的例子：sysName 的对象 OID 是 1.3.6.1.2.1.1.5，它的实例是 1.3.6.1.2.1.1.5.0，那个 .0 就是「标量只有一个值」的占位。

表型的例子，素材里那个 ipAdEntNetMask：对象 OID 为 1.3.6.1.1.5.6.1.3（注：这是旧版编号，MIB-II 里应为 1.3.6.1.2.1.4.20.1.3），它是 IP 地址表的一项，取某一行的子网掩码。这一行的索引是目的网络地址 129.102.1.0，那么这个变量的完整名字是：

text
1.3.6.1.2.1.4.20.1.3.129.102.1.0

索引是 IP 地址时，y 就变成 4 段数字。索引是整数（比如 ifIndex）时，y 就是一个数字。索引是字符串时，y 是一串字符的 ASCII 码加长度前缀——这是最容易写错的一类，后面 OID 那章再拆。

BER 编码的 TLV #

所有字段都是 TLV 三元组：Tag、Length、Value。不用深究，但知道这几点排查时够用：

现象 含义
抓包里字符串前面有个 04 OCTET STRING 的 tag
整数前面有个 02 INTEGER 的 tag
OID 前面有个 06 OBJECT IDENTIFIER 的 tag
看到 30 SEQUENCE 的开始
看到 05 00 NULL，长度 0
看到 A0~A8 PDU 类型的 tag

OID 的编码有个特点：前两个节点（1.3）被压进一个字节（1*40+3 = 43 = 0x2B），后面每个节点用 base-128 变长编码。所以 1.3.6.1.2.1.1.5.0 在报文里的字节是 2B 06 01 02 01 01 05 00。手工核对报文时，这条能帮你快速定位 OID 在哪。

五、MIB：管理信息库 #

MIB 是这本字典本身。不是数据，是数据的目录。

被管理的每一样资源都是一个对象：一个接口、一行路由、一个风扇转速、一块磁盘的剩余空间。MIB 是这些对象的集合，给每个对象定义四件事：

属性 说明 例子
名称 人能读的标识符 sysName
编号 OID，机器读的唯一地址 1.3.6.1.2.1.1.5
类型 值的语法与取值范围 DisplayString (SIZE (0..255))
访问权限 能读、能写、能创建、还是只能出现在告警里 read-only

每个 SNMP 设备（Agent）都有自己的 MIB。严格说，设备实现的是标准 MIB 的一个子集，加上厂商私有 MIB。管理站和代理之间共享的正是这份定义——MIB 就是 NMS 与 Agent 之间的沟通桥梁。

这句话的方向别搞反：MIB 不是「管理站去查代理的数据库」，而是「双方对同一份编号表达成共识」。代理按编号取值，管理站按编号解释值。

mib-2：标准的那棵树 #

Internet 结点（1.3.6.1）下面有个 mgmt（管理），编号 2。mgmt 下面就是管理信息库，原先结点名叫 mib，1991 年定义了新版本 MIB-II，结点名改成 mib-2，标识为 1.3.6.1.2.1，即 { internet(1) 2 1 }。

最初的 mib 结点把它管理的信息分成 8 个类别，现在的 mib-2 已包含超过 40 个类别，覆盖 system、interfaces、at、ip、icmp、tcp、udp、egp、snmp 这些基础组，后面又加了几十个扩展组。

mib-2 的 40 多个组，日常运维真正常用的不到十个。这件事很重要：不要一上来就 snmpwalk 整棵树。一台中端交换机整棵 MIB 走一遍，是几万个 OID、几十秒、几兆流量。缺省 snmpwalk 不带起点的话，就是从头走起。

MIB 的定义与具体的网络管理协议无关，这一点对厂商和用户都是好事：厂商在产品里塞一个符合标准的 SNMP 代理，定义新 MIB 项目时不用改代理；用户用同一套网管软件就能管不同版本 MIB 的多台路由器；没有某个新 MIB 项目的路由器，就是取不到那几项，不影响其它项。

enterprises：厂商私有子树 #

1.3.6.1.4.1 是 enterprises（企业），下面挂了全世界几千家厂商的私有子树：

厂商 私有子树 OID
IBM 1.3.6.1.4.1.2
Cisco 1.3.6.1.4.1.9
Novell 1.3.6.1.4.1.23
Huawei 1.3.6.1.4.1.2011
H3C 1.3.6.1.4.1.25506
APC（UPS） 1.3.6.1.4.1.318

申请流程很简单：任何公司、学校发一封邮件到 IANA 的 MIB 申请地址，就能拿到一个私有结点号。拿到号之后，厂商可以在这棵子树下自由定义自己产品的被管理对象，照样能用 SNMP 管。

这条机制解释了一个常见现象：厂商的私有指标都在这棵子树下。设备的 CPU 利用率、内存占用、温度、电源状态，标准 MIB-II 里没有，各家都在自己的 1.3.6.1.4.1.<厂商号> 下面定义。所以采一台设备的 CPU，你得先知道它是哪家的，用对应的私有 MIB。

sysObjectID（1.3.6.1.2.1.1.2.0）返回的就是厂商私有子树的某个 OID，用它反查设备型号是最稳的做法——比匹配 sysDescr 字符串可靠得多，因为 sysDescr 是可以随便改的字符串，sysObjectID 是编号。

MIB 文件长什么样 #

MIB 文件本身是一段 ASN.1 定义，语法由 SMI（管理信息结构）规定。SMIv1 来自 RFC 1155 和 RFC 2578，SMIv2 做了扩充。

看一个真实 MIB 文件的头部：

text
-- PowerNet-MIB {iso org(3) dod(6) internet(1) private(4) enterprises(1) apc(318)}

PowerNet-MIB DEFINITIONS ::= BEGIN

IMPORTS
    enterprises, IpAddress, Gauge, TimeTicks FROM RFC1155-SMI
    DisplayString                            FROM RFC1213-MIB
    OBJECT-TYPE                              FROM RFC-1212
    TRAP-TYPE                                FROM RFC-1215;

apc      OBJECT IDENTIFIER ::= { enterprises 318 }
products OBJECT IDENTIFIER ::= { apc 1 }
apcmgmt  OBJECT IDENTIFIER ::= { apc 2 }

END

逐行拆：

语法元素 作用
-- 开头 注释，MIB 里唯一的注释方式
DEFINITIONS ::= BEGIN 模块定义的开始
IMPORTS … FROM … 从其它 MIB 借用类型和宏，避免重复定义
OBJECT IDENTIFIER ::= { 父 子 } 定义一个结点，花括号里是「父地址 + 自己的地址」
END 模块结束

花括号这种写法值得单独说。{ enterprises 318 } 的意思是「在 enterprises 下面挂一个编号 318 的结点」。{ apc 1 } 就是「在 apc 下面挂 1」。一层套一层，整棵树就是这么长出来的。所以你在 MIB 文件里看到的每一个 ::= { X Y }，都是在给树添一个结点。

OBJECT-TYPE：对象类型的完整描述 #

结点只给了编号和名字，具体是标量还是表、什么类型、能不能写，靠 OBJECT-TYPE 宏。看素材里那个 UPS 状态的例子：

text
upsBasicOutputStatus OBJECT-TYPE
    SYNTAX  INTEGER {
                unknown(1),
                onLine(2),
                onBattery(3),
                onSmartBoost(4),
                timedSleeping(5),
                softwareBypass(6),
                off(7),
                rebooting(8),
                switchedBypass(9),
                hardwareFailureBypass(10),
                sleepingUntilPowerReturn(11),
                onSmartTrim(12)
            }
    ACCESS  read-only
    STATUS  mandatory
    DESCRIPTION
        "The current state of the UPS. If the UPS is unable
         to determine the state of the UPS this variable is set
         to unknown(1)."
    ::= { upsBasicOutput 1 }

四个子句各有分工：

子句 说明
SYNTAX 数据类型。可以是基础类型（INTEGER、OCTET STRING、IpAddress、Counter32、Gauge32、TimeTicks），也可以是枚举或表结构
ACCESS 访问权限（SMIv2 里叫 MAX-ACCESS）
STATUS 状态：mandatory 必实现、optional 可选、obsolete 已废弃、deprecated 已不推荐
DESCRIPTION 文字说明，采集代码里的人话就靠它
::= { 父 编号 } 这个对象在树上的位置

SYNTAX INTEGER { onLine(2), onBattery(3), … } 这种枚举是 SNMP 里信息量最大的地方。设备返回 3，你查 MIB 才知道是 onBattery（UPS 靠电池供电，市电断了）。没有 MIB 文件，你只知道「值是 3」。

这就是「MIB 是字典」这句话的具体形态。抓包抓到 1.3.6.1.4.1.318.1.1.1.4.1.1.0 = 3，光看这个数字毫无意义。装上 PowerNet-MIB，工具会告诉你这是 upsBasicOutputStatus.0 = onBattery(3)。

不用 MIB 也能干活 #

素材里有一句判断很实在：可以不用 MIB 与设备交互，只不过拿到 Up 这样的返回值，比拿到 1 要直观得多。

这件事两种姿势都有用：

场景 推荐 理由
人在排查、临时看一眼 装 MIB，按名字输出 onBattery 比 3 好读
脚本采集、写时序库 不装 MIB，直接存数字或按枚举表翻译 解析 MIB 文件慢，而且设备上不一定有完整 MIB

用 net-snmp 的命令行工具，-m 和 -M 参数控制 MIB 的加载和搜索路径，-On 强制输出数字 OID，-Oe 输出枚举名。想两边都要，用 -Oqv 抓值时配自己的映射表。

一个实战取舍：采集器的 OID 列表里永远写数字，不写名字。名字要靠 MIB 解析，MIB 文件在服务器上多一份少一份就是一次故障；数字是硬编码的，设备换代也不会变（只要还是标准 MIB 节点）。

六、OID：对象标识符 #

OID 是 SNMP 代理提供的、具有唯一标识的键值。MIB 提供的是「数字 OID → 可读文本」的映射。

这个分工要记牢：OID 是地址，MIB 是词典。地址是设备的客观存在，词典是你手里的一份解释。两者可以独立存在，合起来才好用。

树状结构与命名 #

SNMP 的 OID 按层次化、树状结构组织，用树中的唯一地址表示，跟 DNS 的层次很像。区别在于 DNS 是从左到右由粗到细，OID 是从左到右由根到叶，每一层是一个数字。

第一级有三个结点：ccitt(0)、iso(1)、iso-ccitt(2)。网络设备管理取的是 iso 下面的内容。一个对象的标识符，就是从根走到该对象的路径。

举例，名字空间 ip 结点下一个叫 ipInReceives 的 MIB 变量，在 ip 下被指派数字值 3，于是：

text
名字：iso.org.dod.internet.mgmt.mib.ip.ipInReceives
数字：1.3.6.1.2.1.4.3
实例：1.3.6.1.2.1.4.3.0

三层写法，同一个对象。最后那个 .0 是实例后缀，因为 ipInReceives 是标量，标量实例固定为 0。

全名与相对名 #

全名（完全验证格式）：从根开始，一路写到底，等价于绝对路径。

text
iso.org.dod.internet.private.enterprises      →  1.3.6.1.4.1

注意 private 的位置是 internet(1).private(4)，数字表达是 1.3.6.1.4。这里有个容易抄错的点：网上不少资料写成 .1.3.6.4，漏了 internet(1) 那一层。1.3.6 是 dod，1.3.6.1 才是 internet，1.3.6.1.4 才是 private。少一层，整条路径就指到别处去了。

相对名（相关格式）：从 enterprises 值开始，略过前面所有隐含的层级。

text
enterprises.netapp.netappl.raid.diskSummary.diskSpaceCount.0
.1.789.6.4.8.0

相对格式在写私有 MIB 时常见，因为文件头已经把起点声明过了。

MIB 名称简写 #

最常用的写法是「MIB 模块名 + 双冒号 + 键值 + 实例」，规则就是 <MIB 模块名>::<对象名>.<实例>：

text
NETWORK-APPLIANCE-MIB::diskSpareCount.0
SNMPv2-MIB::sysName.0
IF-MIB::ifOperStatus.3

这个格式的好处一眼可见：IF-MIB::ifOperStatus.3 比 1.3.6.1.2.1.2.2.1.8.3 好读太多。代价是需要对应的 MIB 文件在搜索路径里，否则工具会报 Unknown Object Identifier。

为什么大多数 OID 以 .0 结尾 #

因为实例。某些对象的键值可用多个实例表示，所以 OID 都以实例值结尾。标量对象只有一个值，实例固定为 0；表对象有 N 行，实例是索引值。

这解释了 OID 世界里一个规律：看到 .0 结尾，八成是标量；看到一串数字结尾，八成是表里某一行。

OID 类型 说明
1.3.6.1.2.1.1.5.0 标量 sysName 唯一实例
1.3.6.1.2.1.2.2.1.8.3 表 ifOperStatus，第 3 行
1.3.6.1.2.1.4.21.1.7.202.120.86.71 表 ipRouteNextHop，索引是 IP

三种索引的编码方式 #

表对象的实例后缀怎么编，取决于索引列的类型。这是写 OID 最容易出错的地方，三种情况都要会。

整数索引：直接把索引值接在后面。ifOperStatus.3 就是 1.3.6.1.2.1.2.2.1.8.3，指第 3 个接口（ifIndex = 3）。

IP 地址索引：四段各算一个节点。

text
ipRouteNextHop.202.120.86.71
→  1.3.6.1.2.1.4.21.1.7.202.120.86.71

这里 ipRouteTable 是 1.3.6.1.2.1.4.21，ipRouteEntry 是 .1，ipRouteNextHop 是 .7，后面四段是目的网络地址。素材里那个例子就是这个结构：要指明地址 202.120.86.71 的下一站路由，就拼成这一串。

字符串索引：先写长度，再写每个字符的 ASCII 码。

text
某个以名字为索引的表，索引值 "eth0"
→  ... .4.101.116.104.48
        ↑  ↑
        长度 4，然后是 e(101) t(116) h(104) 0(48)

字符串索引是新手写 OID 最容易翻车的一类。忘了写长度前缀，或者把长度写成十六进制，都会得到一个「格式正确但查不到」的 OID，代理回 noSuchName，你还以为是设备不支持这个节点。

动态 OID #

并非所有 OID 都能预先枚举。IP 路由表就是典型：路由条目是运行时生成的，ipRouteNextHop.202.120.86.71 这条实例在设备启动时并不存在，是某条路由被学到之后才出现的。

这就带来一个工程约束：动态 OID 无法转成固定的符号名。任何依赖「预先配置一份 OID → 变量名映射表」的系统，都支持不了这类对象，只能走「先 GETNEXT 遍历，再按返回值动态建表」的路子。

这也是采集路由表必须用 snmpwalk / snmpbulkwalk 而不能用固定 OID 列表的原因。同理，ARP 表、MAC 地址表、邻居表都是动态的。

第二，ifSpeed 也是 32 位。万兆口 10000000000 bps 超出 2^32，很多设备在 ifSpeed 里回 4294967295（截断或饱和）。判断链路带宽要用 ifHighSpeed（单位 Mbps，万兆回 10000）。

一张表怎么走 #

以接口表为例，取法就是定一个起点加几列：

text
起点：1.3.6.1.2.1.2.2.1          （ifEntry）
列：  1.3.6.1.2.1.2.2.1.2       ifDescr
      1.3.6.1.2.1.2.2.1.3       ifType
      1.3.6.1.2.1.2.2.1.8       ifOperStatus
      1.3.6.1.2.1.31.1.1.1.6    ifHCInOctets
      1.3.6.1.2.1.31.1.1.1.10   ifHCOutOctets

对每一列做一次 walk，拿到一串「同索引的实例」，再按索引拼成行。这是采集表数据的通用套路：按列遍历，再按索引 join。不要指望一次 GET 拿一整行——SNMP 没有「按行读」这种操作。

代价也在这：5 列就是 5 次遍历。48 口的交换机，用 GETNEXT 是 240 个来回；用 GETBULK（max-repetitions=25）压到 10 来个。这是 GETBULK 存在的实际意义。

八、SNMPv1 与 v2c #

v1：最小可用的网络管理 #

SNMPv1 是 SNMP 的最初版本，提供最小限度的网络管理功能。它的 SMI 和 MIB 都比较简单，同时存在较多安全缺陷。

v1 的 SMI 是 SMIv1，MIB 是 MIB-I（后来是 MIB-II），操作集就是五个：GET、GETNEXT、SET、RESPONSE、TRAP。够用，但只够用。

v1 的根本问题在于认证机制：团体名认证。团体名就是一个字符串，作用类似密码，用来限制 NMS 对 Agent 的访问。如果报文携带的团体名没得到 NMS/Agent 的认可，报文直接被丢弃。

问题在于这个「密码」是明文放在报文里的。抓包就能看到。

团体名的两种权限 #

团体名分可读和可写两种：

操作 使用的团体名 出厂默认（常见）
GET / GETNEXT / GETBULK 可读团体名 public
SET 可写团体名 private

很多设备允许读团体名和写团体名配成同一个值，那是自找麻烦。正确做法是分开，而且都要改掉默认值。

public 和 private 是全世界都知道的两个字符串。一台设备开着 SNMPv1 用默认团体名，等于把只读权限（有时是可写权限）开放给任何能到达 161 端口的人。这不是理论风险，扫描器默认就带这两个字符串试。

v1 的报文 #

v1 的报文由三段构成：

text
+----------+-----------+-------------------+
| Version  | Community |      SNMP PDU     |
|    0     |  public   |  GET / GETNEXT /  |
| (INTEGER)| (OCTET    |  SET / RESPONSE / |
|          |  STRING)  |  TRAP             |
+----------+-----------+-------------------+

各字段的作用：

字段 定义
Version SNMP 版本。v1 填 0
Community 团体名，Agent 与 NMS 之间的认证凭据
Request ID 匹配请求与响应，每个请求分配全局唯一 ID
Error status 处理请求时的状态：noError、tooBig、noSuchName、badValue、readOnly、genErr
Error index 差错索引，指出变量绑定列表里哪个变量导致异常
Variable bindings 变量绑定列表，变量名与变量值成对

v1 的 Trap 是另一套字段，前面报文结构那章已经列全。Generic trap 的 7 个枚举值：coldStart、warmStart、linkDown、linkUp、authenticationFailure、egpNeighborLoss、enterpriseSpecific。Specific trap 是企业私有 Trap 代码。Time stamp 是上次重新初始化到产生 Trap 之间的时长，也就是 sysUpTime 的取值。

v1 的抓包现场 #

抓一次 v1 的 GET，能看到两个结论。

一是团体名是明文。Wireshark 里 community 字段直接显示 ASCII 的 public，不用解密、不用破解。任何人拿到这个包，就知道该用什么团体名去问这台设备。

二是Trap 只有发送没有响应。抓包时你只看到一条从 Agent 到 NMS 的 Trap，NMS 那边不回任何东西。设备发完就当送达了，链路上丢了也没有下文。这就是为什么核心告警不能只靠 v1 Trap。

v2c：加了功能，没加安全 #

v2c 里的 c 就是 community。名字已经说明了它的定位：用团体名认证的 SNMPv2。

它的做法是兼容 v1 的同时扩充 v1 的功能，干了三件事：

扩充 具体内容
更多操作类型 新增 GETBULK 和 INFORM
更多数据类型 支持 Counter32、Counter64、Gauge32、UInteger32、Opaque 等
更细的错误码 从 v1 的 0~5 扩展到 0~18，细分错误原因

GetBulk 与 Inform 的实质 #

GETBULK 对应的是 GETNEXT。通过 non-repeaters（前 N 个变量只取一个后继）和 max-repetitions（其余变量各重复取 M 个）两个参数，从 Agent 高效地批量获取大量管理对象数据。它的本质仍是「连续多次 GETNEXT」的打包，代理替你把循环做完了。

INFORM 是 Trap 的升级版，两者差在确认：

对比 Trap Inform
发出后是否收响应 不收 收，NMS 必须回 Response
可靠性 发完不管 可重传，可靠送达
抓包特征 单条报文，无下文 报文后面跟一条 Response

抓包对比这两个很快：Trap 就一条孤零零的报文；Inform 后面跟一条从 NMS 发回的响应。这个差异在排查「告警为什么丢」时是决定性的——如果设备配的是 Inform 而 NMS 不回 Response，设备会一直重传，抓包能看到重复的同 ID 报文。

v2c 改了 Trap 的格式 #

这是最容易忽略的一处变化。v2c 重写了 Trap 报文结构：不再用 v1 那套 enterprise/agent-addr/generic-trap/specific-trap/time-stamp 字段，改用 v1 GET/GETNEXT/SET 的 PDU 格式，把 sysUpTime 和 snmpTrapOID 作为变量绑定列表里的两个变量塞进去。

对比一下就清楚：

text
v1 Trap PDU（tag A4）：
  enterprise        OID
  agent-addr        IpAddress
  generic-trap      INTEGER
  specific-trap     INTEGER
  time-stamp        TimeTicks
  variable-bindings varbind list

v2c Trap PDU（tag A7）：
  request-id        INTEGER
  error-status      INTEGER   （恒为 0）
  error-index       INTEGER   （恒为 0）
  variable-bindings：
      sysUpTime.0    = TimeTicks       ← 固定第 1 个
      snmpTrapOID.0  = OID             ← 固定第 2 个，标识告警类型
      ... 业务变量 ...                  ← 后面才是业务数据

v2 的 Trap 变成「一个带两个特殊 varbind 的通用 PDU」，好处是格式统一了——解析 GET 响应的代码稍作修改就能解析 Trap。代价是告警类型不再是一个整数，而是一个 OID，你得先用 MIB 把这个 OID 翻译成告警名。

snmpTrapOID 取值举例，接口 down 的告警是 1.3.6.1.6.3.1.1.5.3（linkDown），v1 里对应的是 generic-trap = 3。同一件事，两种表达。

v2c 的安全状况 #

和 v1 完全一样：团体名明文，没有认证，没有加密。功能变强了，安全原地踏步。

这一点在实际运维里经常被搞混。有人看到设备配了 v2c，就以为比 v1 安全。不是。v2c 相对 v1 的全部改进都在功能和效率上，安全上零进步。要安全只能上 v3。

看下面这张表就明白：

能力 v1 v2c v3
认证 团体名（明文） 团体名（明文） USM 摘要认证
加密 无 无 DES / AES
批量读 无 GETBULK GETBULK
可靠告警 无 INFORM INFORM
访问控制 无（只有读写团体名之分） 无 VACM 视图

v2c 的价值是效率，v3 的价值是安全。选版本时按需求剪：内网只读采集，v2c 够了；跨网段、跨机房、要写操作，上 v3。

九、SNMPv3 的安全模型 #

v3 的核心不是新操作，是安全。它补上 v1/v2c 缺的两件事：认证（这个报文真是它发的）和加密（路上的人看不懂）。

v3 靠两个框架，分工不同：

框架 全称 管什么
USM User-based Security Model，基于用户的安全模型 报文级的认证与加密
VACM View-based Access Control Model，基于视图的访问控制模型 用户能访问哪些 MIB 对象、以什么方式访问

一个管「报文是不是伪造的、路上有没有被看」，一个管「这个用户准不准读这部分 OID」。两个都要配。只配 USM 等于「认证过了，但不区分权限」，所有用户看到的是同一棵树。

USM：用户 + 认证 + 加密 #

USM 引入了用户名和组的概念，可以设置认证和加密功能。

能力 作用 不做的后果
认证 验证报文发送方的合法性，避免非法用户访问 谁都能冒充管理站发 SET
加密 对 NMS 与 Agent 之间传输的报文加密，避免被窃听 数据明文，抓包直接看

通过「有无认证」和「有无加密」的组合，得到三个安全级别：

securityLevel 认证 加密 适用
noAuthNoPriv 无 无 只认用户名，水平等同 v2c，不要用
authNoPriv 有 无 报文完整性有保证，内容仍明文
authPriv 有 有 认证加加密，生产环境唯一推荐

算法这边，认证可选 HMAC-MD5-96、HMAC-SHA-96、SHA-224/256/384/512，MD5 淘汰了，SHA 起步；加密可选 DES-CBC、AES-128、AES-192/256，DES 强度不够，条件允许就 AES-128。

有一处必须说清：认证密码和加密密码是两个密码。配 v3 用户时 authPassphrase 和 privPassphrase 分开填，各自至少 8 个字符。很多人只填认证密码，加密那栏留空，结果 authPriv 配不上，表现是 authorizationError 或者干脆超时。

VACM：五个元素决定权限 #

VACM 定义五个元素，它们同时决定用户有没有访问权限，只有全匹配上的用户才能操作对象：

元素 说明
group（组） 用户的集合。用户先归组，权限按组配
securityLevel（安全等级） 该组要求的最低安全级别
context（上下文） 把同一台设备的 MIB 切成几块，多实例场景用
MIB view（MIB 视图） 一个 OID 子树的白名单或黑名单
access policy（访问策略） 上述四者的绑定，并指定 read / write / notify 权限

同一台 SNMP 实体上可以定义不同组，组与 MIB 视图绑定，组内可以定义多个用户。用某个用户名访问时，只能访问它所对应视图里定义的对象。

一个实用配置——给监控账号一个只读视图，把敏感节点排除掉：

text
view      monitor       included  1.3.6.1.2.1
view      monitor       excluded  1.3.6.1.2.1.1.4     # sysContact
view      monitor       excluded  1.3.6.1.2.1.1.6     # sysLocation
group     monitorGroup  usm  monitor  authPriv  read  monitor
createUser monitor  SHA  "auth-pass-here"  AES  "priv-pass-here"

配置完，监控账号连 sysContact 和 sysLocation 都读不到，写更别想。

v3 的消息格式 #

v3 的报文头和 v1/v2c 完全是两套，它是「三段式」：消息头 + 安全参数 + 数据。

text
+--------------------------------------------------------+
| SNMPv3 Message                                         |
|   msgVersion    INTEGER   固定为 3                      |
|   msgGlobalData:                                       |
|       msgID            请求/响应匹配                    |
|       msgMaxSize       能容纳的最大字节数                |
|       msgFlags         OCTET STRING（1 字节）           |
|       msgSecurityModel INTEGER                         |
|   msgSecurityParameters:                               |
|       authoritativeEngineID / Boots / Time             |
|       userName / authParams / privParams               |
|   msgData（加密范围）:                                  |
|       contextEngineID / contextName / PDU              |
+--------------------------------------------------------+

整个消息可以使用认证机制，EngineID、ContextName、PDU 消息体这三部分可以被加密。RequestID、MaxSize、Flags、SecurityModel、SecurityParameters 构成 v3 的消息头。

两段字段一起看：

字段 说明
msgID 请求报文的序列号。等价于 v1/v2c 的 request-id
msgMaxSize 发送方能容纳的最大字节数，同时表明能接收的最大字节数
msgFlags 消息标识位，占一字节，含 authFlag、privFlag、reportableFlag
msgSecurityModel 安全模型值 0~3：0 任何模型，1 SNMPv1，2 SNMPv2c，3 SNMPv3
contextEngineID 唯一识别一个 SNMP 实体。接收时决定如何处理；发送时由应用提供
contextName 唯一识别相关联上下文引擎范围内的特定上下文
authoritativeEngineID 权威 SNMP 的 snmpEngineID，用于实体识别、认证、加密。在 Trap/Response/Report 里是源端的，在 Get/GetNext/GetBulk/Set 里是目的端的
authoritativeEngineBoots 权威 SNMP 的 snmpEngineBoots，从初次配置起引擎已初始化或重新初始化的次数
authoritativeEngineTime 权威 SNMP 的 snmpEngineTime，用于时间窗判断
userName 用户名。NMS 和 Agent 配置的用户名必须一致
authenticationParameters 认证参数，认证运算所需密钥。未启用认证则为空
privacyParameters 加密参数，比如 DES-CBC 形成初值 IV 用到的取值。未启用加密则为空

这个结构解释了一个现象：v3 的报文比 v2c 大一截。哪怕不加密，光引擎参数加用户名就占掉几十字节。

EngineID 发现：v3 为什么先要问一轮 #

v3 在正式取数据之前，有一轮前置交互，问「引擎参数」。

原因在时间窗。authPriv 的认证计算要用 engineBoots 和 engineTime，这两个值有时间窗，用来防重放攻击。NMS 不知道 Agent 的引擎参数，算不出正确的认证摘要，所以必须先问：

  1. NMS 先向 Agent 请求 authoritativeEngineID（标识一个 SNMP 实体）、authoritativeEngineBoots 和 authoritativeEngineTime。这三个既是同步 NMS 与 Agent 时间的依据，也是数据认证和加密的参数。
  2. Agent 回复这几个参数。
  3. NMS 继续向 Agent 取 engineBoots 和 engineTime。
  4. Agent 响应。
  5. 开始正常数据操作。
  6. Agent 响应数据请求，传输的数据已全部加密。

抓包里能看得很清楚：前面几组报文 PDU 里没有真实 varbind，后面的才有业务数据。前面那几条的回复 PDU 叫 Report（tag A8）。

这是排查 v3 不通的关键路径。v3 连不上，先看第一轮有没有回：

现象 判断
第一条引擎发现请求无响应 设备没开 v3，或 ACL/防火墙挡了 161
有回应但后续认证失败 用户名、密码、认证算法两边不一致
偶尔成功、大量 notInTimeWindow 时钟偏差过大，或设备重启后 engineBoots 变了
unknownUserName 用户名大小写或空格不对

时间窗还有一个隐患：设备重启后 engineBoots 加一、engineTime 归零，NMS 缓存的旧值立刻失效。所以 v3 采集器必须处理 notInTimeWindow 这类 Report，收到就重走一次引擎发现，不能把引擎参数写死在配置文件里。

报文结构的三种形态 #

text
── v1 ─────────────────────────────────
[ Version=0 | Community | PDU ]
    PDU: request-id, error-status, error-index, varbinds
    或 Trap: enterprise, agent-addr, generic-trap,
             specific-trap, time-stamp, varbinds

── v2c ────────────────────────────────
[ Version=1 | Community | PDU ]
    新增 PDU：GetBulk(A5)、Inform(A6)、SNMPv2-Trap(A7)
    Trap 改为通用 PDU + 两个固定 varbind

── v3 ─────────────────────────────────
[ Header | SecurityParameters | ScopedPDU ]
    Header:   msgID, msgMaxSize, msgFlags, msgSecurityModel
    Security: engineID, boots, time, user, authParams, privParams
    ScopedPDU: contextEngineID, contextName, PDU

从 v1 到 v2c，外层只换了个数字，PDU 增加了类型。从 v2c 到 v3，外层结构整个换了，报文头从「两字段」变成「三段式」。

一处容易搞错的地方 #

v3 并没有废弃 v2c 的 PDU。v3 的 ScopedPDU 里装的仍然是 request-id / error-status / error-index / varbinds 这套结构，GETBULK 和 INFORM 也照旧可用。

也就是说，v3 = v2c 的 PDU + 一层安全信封。理解这个层次关系，报文对比就不用背了：

text
v3 报文 = [v3 头 + 安全参数] + [contextEngineID, contextName] + [v2c 的 PDU]

反过来说，抓包看到 msgSecurityModel=3，往里的 PDU 结构和 v2c 一模一样。你写过的 v2c 解析代码，剥掉外层就能复用。

同一件事，三种问法 #

取设备名（sysName.0）这件事，三个版本的差别只在命令行参数：

bash
snmpget -v1  -c public 192.168.2.1 1.3.6.1.2.1.1.5.0
snmpget -v2c -c public 192.168.2.1 1.3.6.1.2.1.1.5.0
snmpget -v3 -l authPriv -u monitor -a SHA -A '<auth>' -x AES -X '<priv>' 192.168.2.1 1.3.6.1.2.1.1.5.0

报文层面多的是引擎发现、认证摘要、加密。这是「简单协议」这个词晚节不保的地方——功能没变复杂，安全补丁的代价全在后来的报文头上。

十一、SNMP 的部署与排查 #

设备侧最小配置 #

以典型的交换机为例，v2c 四步：

text
snmp-server enable                                  # 1. 起 SNMP 代理
snmp-server community <改过的只读串> ro              # 2. 配只读团体名，改掉默认值
snmp-server host 192.168.2.110 version 2c <只读串>   # 3. 限制访问源
access-list 10 permit 192.168.2.110
snmp-server enable traps                            # 4. 开 Trap

四步里最容易漏的是第 3 步。只配团体名不配 ACL，等于把 161 端口对全网开放。扫段脚本不用猜，public 是字典第一项。

v3 换三行，视图、组、用户：

text
snmp-server view monitor 1.3.6.1.2.1 included
snmp-server group monitorGroup v3 priv read monitor
snmp-server user monitor monitorGroup v3 auth sha "<auth>" priv aes 128 "<priv>"

网管站侧排查顺序 #

设备采不到数据，别一上来就怀疑设备。按这个顺序走，八成问题在前三步：

步骤 动作 通过标准
1 ping <设备IP> 通。不通先查三层
2 snmpget -v2c -c <团体名> <IP> 1.3.6.1.2.1.1.1.0 返回 sysDescr 字符串
3 snmpget 改用 -v1 或 -v3 再试 排除版本不匹配
4 snmpwalk -v2c -c <团体名> <IP> 1.3.6.1.2.1.2 接口表能走完
5 tcpdump / Wireshark 抓 161 看请求有没有出去、响应有没有回来

第 2 步返回 Timeout: No Response，按这个表分支：

现象 常见原因
超时，抓包看不到任何回包 UDP 161 被 ACL/防火墙挡、代理没起、团体名 ACL 不匹配
超时，抓包看到 request 没 response 团体名错（设备直接丢弃，不回应）
No Such Object available 设备不支持该 OID，或漏了 .0 实例后缀
Error in packet: noSuchName 同上，v1 的错误表达
AuthorizationError v3 用户权限不足或 VACM 视图没覆盖该 OID
Timeout: No Response（v3） 引擎发现阶段就断了，先确认设备开了 v3

有个细节值得记住：团体名错的时候设备是静默丢弃，不回任何错误。所以你看到的是超时，不是「认证失败」。这个设计让排查变难——超时既是网络不通的样子，也是团体名错的样子，只能靠抓包区分：包到了设备、没回包，就是团体名的问题。

轮询与告警的配合 #

SNMP 的两种取数方式要配合用。

方式 优点 缺点 适合
轮询（GET/GETBULK） 数据齐、可控、能算趋势 有延迟、吃设备 CPU、间隔内的事件会漏 流量、CPU、内存、会话数
Trap/Inform 实时、不吃轮询额度 会丢包、易成风暴 接口 up/down、重启、认证失败

接口抖动这种事，光靠 60 秒轮询一次是抓不到的——抖一下又恢复了，采不到。必须靠 linkDown/linkUp 的 Trap。反过来，CPU 利用率不是事件，只能轮询。

Trap 风暴是另一个要防的。一台核心设备挂掉，所有邻居同时发 linkDown，几千条 Trap 涌向 162 端口，管理站的 UDP 缓冲区直接溢出。缓解办法三个：限制每台设备的 Trap 速率、在中间加一层 Trap 汇聚、接收端用队列而不是同步处理。

性能上的几个数 #

参数 建议值 理由
轮询间隔 60s（流量）/ 300s（状态） 太密吃 CPU，太疏丢趋势
GETBULK max-repetitions 10~25 大了响应超 MTU 被分片或回 tooBig
并发设备数 按设备能力定，一般 20~50 路并发 单台设备并发太多会丢包
超时 1~3s 内网 1s 够，跨广域给 3s
重试 1~2 次 再多会加剧拥塞

这些数不是标准，是起点。真实值要按设备型号和链路质量调，用丢包率去校准。

三条压箱底的判断 #

第一条：超时先抓包，别猜。 包没到设备，是网络问题；包到了没回，是认证或 ACL 问题；包回了但对不上，是解析问题。这三类的修法完全不同，靠猜只会改错配置。

第二条：看到 noSuchName 先看实例后缀。 90% 的 noSuchName 是 OID 少写了 .0，或者表对象没带索引。剩下 10% 才是设备真不支持——那时候用 snmpwalk 从上一层走一遍，看这棵子树到底长什么样。

第三条：能读就不要写。 SNMP 的 SET 没有事务、没有回滚、没有审计。真要改配置，走设备的配置管理通道（CLI 脚本、NETCONF、或者 CWMP）。SNMP 的价值在「看得见」，不在「改得动」。

三条都记住，SNMP 这部分就不会出大事。真要动配置，那篇《CWMP（TR-069）》接着看。
