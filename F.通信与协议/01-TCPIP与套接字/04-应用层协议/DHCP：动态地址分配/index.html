本篇讲什么：一台机器插上网线，从「没有地址」到「能上网」的那几十毫秒里，DHCP 到底干了什么。重点是四报文握手（DORA）、租约定时器、DHCP 中继、静态绑定与地址池、常见选项，末尾给故障排查路径和安全防护清单。

本篇不讲什么：不讲子网划分与路由的数学（去看同层的 IP 与路由篇），不讲 DNS 递归解析的完整流程（看 HTTP 篇的域名部分），不讲运营商网管模型。

跨篇指路：同目录另有 HTTP、SNMP、CWMP 三篇。HTTP 讲应用层协议怎么跑在 TCP 上；SNMP 讲怎么读设备状态；CWMP 讲运营商怎么远程管家庭网关。DHCP 是这四篇里最靠「开局」的一篇——设备还没有地址时，能开口说话的协议只有它。

一、DHCP 解决什么问题 #

DHCP，Dynamic Host Configuration Protocol，动态主机配置协议。名字里三个词都是重点：Dynamic 说明地址是会变的，Host 说明它管的是主机而不是路由器之间的链路，Configuration 说明它给的不止一个 IP。

它是一个应用层协议，跑在 UDP 上，服务端用 67 端口，客户端用 68 端口。报文本身借用了 BOOTP 的结构，所以你在 Wireshark 里过滤 DHCP 包时，输入 bootp 才管用——字段名和协议名在抓包工具里沿用了老名字。旧版本（比如 1.12.9）确实只认 bootp，新版本对 dhcp 也能识别，两个都试一下。

一台主机要真正接入 IPv4 网络，需要的不是「一个 IP」，是四样东西：

要素 作用 缺了会怎样
IP 地址 自己在网络里的门牌号 无法被寻址
子网掩码 判断谁是同网段、谁能直发 跨网段判断全错，包发不出去
默认网关 出本网段的下一跳 只能访问同网段，上不了外网
DNS 服务器 域名到地址的翻译官 能 ping 通 IP，打不开网页

手工把这四样填进每台机器，在十台以内还行。上百台就是灾难：写错一个数字，全网找半天；两台机器抢同一个地址，两边都时通时断；换一台 DNS 服务器，几百台机器挨个改。

DHCP 把这四样收拢到一台服务器上，客户端只要说一句「给我一套」，剩下的按模板发。

DHCP 的前身是 BOOTP（Bootstrap Protocol）。BOOTP 被造出来的目的就是给连进网络的设备自动分配地址，后来被 DHCP 取代。DHCP 比 BOOTP 复杂，功能更多，其中最关键的一条增量就是租约——地址借给你用一段时间，不是永久写死。BOOTP 那种「一次分配、永久记录」的静态表，在笔记本、手机、虚拟机满天飞的环境里维护不动。

还有一个容易忽略的点：DHCP 报文的传输层封装是 UDP，但它不依赖 IP 层能通到对端——因为客户端此时连自己的地址都没有。整个协议的起点是「用广播找一个还不知道在哪儿的服务器」，这是它跟 HTTP 那种「先有地址再对话」的协议最大的区别。

二、为什么需要自动分配 #

不自动分配也能活，只是活得很累。把需求摊开看，自动分配解决的是四类现实问题。

规模。一个办公网 500 个工位，加上无线、打印机、摄像头、门禁、AP 本身，实际设备数轻松过千。手工维护一张「MAC 到 IP」的表，改一次就错一次。

移动。笔记本从会议室挪到工位，从有线切到无线，从公司带回家里。地址跟着人走，静态配置做不到。

临时。访客手机、外包同事的电脑、测试用的树莓派。这些设备不该进固定资产表，但必须能上网。给它们一段临时地址池，来就发，走就收。

回收。设备拔了、虚拟机删了、员工离职了，手工配置的地址没人清理，几年下来地址池里全是「僵尸占用」。DHCP 靠租约自动回收——租期到了没续，地址回到池子里。

集中管理带来的第二个好处是改一处生效一片。公司换 DNS，只在 DHCP 服务器的 option 6 上改一个值，客户端下次续租自动拿到新值。网关换设备，改 option 3。这种「配置下发」的能力，比地址分配本身更有价值。

反过来，DHCP 也带来一个新的依赖：DHCP 服务器挂了，新设备就上不了网。所以生产环境里 DHCP 要么做主备，要么把租期拉长，让已在线设备在故障窗口内不受影响。

三、四个报文：DORA #

DHCP 分配地址的核心流程是四步，业界按首字母叫 DORA：

  • DISCOVER：客户端喊「谁在？谁有地址给我？」
  • OFFER：服务器答「我这儿有一个，你要不要？」
  • REQUEST：客户端喊「我要了，这个地址归我」
  • ACK：服务器答「确认，归你了，这是配套参数」

最直观的复现方式：在 Windows 上抓包，ipconfig /release 之后执行 ipconfig /renew，Wireshark 里会依次冒出四个包——Discover、Offer、Request、ACK。这四步就是一次完整的动态分配。

3.1 第一步：DHCPDISCOVER #

客户端此时没有地址，所以源 IP 只能填 0.0.0.0。它不知道服务器在哪，所以目的 IP 填广播地址 255.255.255.255。目的端口 UDP 67，源端口 UDP 68。

这个包的意义是「探路」：局域网内所有监听 67 端口的 DHCP 服务器都会收到，谁有可用地址，谁就回话。

0.0.0.0 这个源地址不是随便填的，它是「我没有地址」的标准表达。任何设备在拿到地址之前，用 0.0.0.0 发报文都是合法的，路由器不会转发它，但同一广播域内的设备都能收到。

3.2 第二步：DHCPOFFER #

服务器收到 DISCOVER，从地址池里挑一个没用过的地址，回一个 OFFER。这个包里带的不只是 IP：

  • Your (client) IP Address（yiaddr 字段）：打算给客户端的地址
  • 子网掩码、路由器（网关）、DNS、域名、IP 租用期，全在 option 里

关于目的地址，这里有个容易走偏的细节：服务器仍然用广播地址。原因是此时客户端还没有 IP，服务器没法直接单播给它；而且有多台客户端同时用 0.0.0.0 在请求时，服务器也分不清该发给谁，于是用广播，告诉正在请求的这批客户端——这儿有一台可用的 DHCP 服务器。

严格说，协议里客户端可以在报文 flags 字段里置一个广播位，要求服务器用广播回应；不置位时服务器会尝试单播到 yiaddr。但抓包里绝大多数 OFFER 是广播，因为服务器在发之前没法确认那个地址真的没被占用。抓包看到 255.255.255.255，不必意外。

OFFER 阶段服务器只是预留，还没真正把地址划出去。这一步的预留是有超时的，客户端不回应，地址会还给池子。

3.3 第三步：DHCPREQUEST——广播，而且是故意的 #

客户端同时收到多台服务器的 OFFER 时（比如网段里有两台 DHCP 服务器做主备），它挑一个，然后广播一个 REQUEST。

首次请求时，源 IP 还是 0.0.0.0，目的 IP 还是 255.255.255.255。这两点跟 DISCOVER 一样，但目的完全不同：DISCOVER 是「我找人」，REQUEST 是「我通知所有人我的选择」。

为什么第三步必须广播？这是整个协议里最容易看漏的设计点。

假设客户端单播给选中的那台服务器，其他发过 OFFER 的服务器永远不知道自己落选了。它们会一直等着，那段预留的地址就卡在那儿，直到超时才释放。地址池被这种「悬空预留」慢慢吃掉，是很典型的隐性故障。

广播解决了这个问题：所有发过 OFFER 的服务器都收到这条 REQUEST，看到里面 option 54（服务器标识符）写的不是我，立刻把刚才预留的地址收回池子。一次广播换全网状态同步，这买卖不亏。

所以第三步的广播不是「浪费带宽的偷懒设计」，是协议里刻意安排的状态收敛机制。

3.4 第四步：DHCPACK #

服务器确认，回 ACK。这个包是最终发牌：Your (client) IP Address 给出正式分配的地址，后面一长串 option 把配套参数全给你。

ACK 包的拆解值得逐项记住：

  • 前两项 option 是消息类型（ACK）和服务器身份标识，这两项决定了这个包是什么意思、从谁那儿来
  • 往后的 option 才是真正的配置：Subnet Mask、Router、Domain Name Server、Domain Name、IP Address Lease Time

客户端收到 ACK 才算真正拿到地址。这之后它会做一次 ARP 探测（免费 ARP），确认这个地址在网段里没有别人在用。真撞上了，客户端发 DHCPDECLINE 告诉服务器「这地址有人」，服务器标记为冲突，重新给一个。

3.5 四报文对照 #

报文 方向 源 IP 目的 IP 端口 一句话作用
DHCPDISCOVER 客户端 → 广播 0.0.0.0 255.255.255.255 68 → 67 找服务器，我还没有地址
DHCPOFFER 服务器 → 客户端 服务器地址 广播（依 flags） 67 → 68 我这儿有个地址，先给你留着
DHCPREQUEST 客户端 → 广播 0.0.0.0 255.255.255.255 68 → 67 我选它了，其他人收摊
DHCPACK 服务器 → 客户端 服务器地址 广播/单播 67 → 68 定了，连参数一起给你

时序看起来是这样：

text
客户端 0.0.0.0:68                                服务器 x.x.x.x:67
    |                                                   |
    |---- DHCPDISCOVER  dst 255.255.255.255 ----------->|
    |                                                   |
    |<--- DHCPOFFER    yiaddr = 待分配地址 --------------|
    |                                                   |
    |---- DHCPREQUEST   dst 255.255.255.255 ----------->|
    |     （所有发过 OFFER 的服务器都收到）              |
    |                                                   |
    |<--- DHCPACK       option 3/6/51 ... ---------------|
    |                                                   |
    |  免费 ARP 探测 → 无冲突 → 地址生效                 |

四个包，客户端的源地址在头三个里都是 0.0.0.0。只有 ACK 到达之后，它才第一次拥有一个真实地址。这是理解 DHCP 的锚点。

四、报文格式与选项 #

DHCP 报文沿用 BOOTP 的固定头部，后面接一段可变的选项区。头部字段里，抓包时最该盯住的是这几个。

字段 长度 含义 抓包时怎么看
op 1 报文方向，请求还是应答 区分客户端发的和服务器发的
htype / hlen 1 / 1 硬件类型与地址长度，以太网是 1 和 6 基本恒为 1 和 6
hops 1 经过的中继跳数 中继场景下会变成 1
xid 4 事务 ID，一次交互全程不变 用它把四个包串成一次会话
secs 2 客户端已等待秒数 卡住时能看出等了多久
flags 2 标志位，含广播回应请求位 决定 OFFER 走广播还是单播
ciaddr 4 客户端已有地址 续租时这里有值
yiaddr 4 服务器分配给客户端的地址 OFFER/ACK 里就是你要拿的 IP
siaddr 4 下一个要用的服务器地址 涉及引导时才有意义
giaddr 4 中继代理地址 有中继时这里是中继的地址
chaddr 16 客户端硬件地址，以太网占前 6 字节 MAC 就藏在这儿
sname / file 64 / 128 可选服务器名与引导文件名 多数场景为空

三个字段值得单独说。

xid 是这次交互的身份证。同一台机器上开两个抓包，或者一个网段里十台机器同时开机，包里全是 DISCOVER，你怎么知道哪个 OFFER 回应的是哪个 DISCOVER？看 xid，四个包必须同值。排查「拿了地址但不是自己的」这类怪事，第一件事就是核对 xid 和 chaddr。

ciaddr 是「我现在用的地址」。DISCOVER 阶段它为 0，续租阶段的 REQUEST 它填的是正在用的地址。这个字段的值直接告诉你当前处于哪个阶段。

giaddr 是跨网段的关键。客户端发出的包里它是 0；中继代理转发时把它改成自己的接口地址，服务器靠它判断该从哪个地址池取地址。看到 giaddr 有值，说明这个请求跨了网段。

4.1 选项区：真正干活的部分 #

固定头部只解决「谁给谁发、地址是多少」，其余配置全在选项区，格式是 code + len + value 的 TLV 三元组。

选项分两类。一类是标准选项，编号由 RFC 定义，比如 option 1 子网掩码、option 3 路由器、option 6 DNS。另一类是厂商私有选项，编号在 43（厂商特定信息）里再嵌套一层，或者直接用私有编号。CWMP 那篇讲的 ACS 地址下发，经常就藏在厂商私有选项里。

选项区以 option 53（消息类型）开头，这一项决定了整个包该被理解成 DISCOVER 还是 ACK。抓包工具解析 DHCP 时第一眼看的就是它。紧随其后的一般是 option 54（服务器标识符）或 option 50（请求的地址）。

4.2 消息类型对照 #

类型值 报文 谁发 什么时候出现
1 DHCPDISCOVER 客户端 开机、断开重连、租约彻底失效
2 DHCPOFFER 服务器 收到 DISCOVER 后
3 DHCPREQUEST 客户端 选定服务器、续租、重启后确认
4 DHCPDECLINE 客户端 ARP 探测发现地址被占
5 DHCPACK 服务器 确认分配
6 DHCPNAK 服务器 客户端要的地址不对，或租约已失效
7 DHCPRELEASE 客户端 主动放弃地址（如 ipconfig /release）
8 DHCPINFORM 客户端 有地址，只想补要其他配置

后四个报文平时抓不到，但每个都有明确的登场时机。

DHCPNAK：客户端要的地址服务器不认。典型场景是机器休眠很久后醒来，还在用旧地址发 REQUEST，服务器说「这个地址已经不属于你了」。客户端收到 NAK 必须立刻放弃地址，退回 0.0.0.0，重新走 DISCOVER。这是「断电久了 IP 会变」的直接原因之一。

DHCPDECLINE：客户端做免费 ARP 探测，发现有人已经用了这个地址，于是告诉服务器「这地址是脏的」。服务器把它标成冲突地址，一段时间内不再分配。

DHCPRELEASE：主动退租。执行 ipconfig /release 抓到的就是这个包，抓完主机 IP 变成 0.0.0.0，与网络断开，不能上网。

DHCPINFORM：客户端已经有地址（比如手工配的），但还想知道网关、DNS 之类的参数。服务器回 ACK，但不分配地址。这个报文在排查「地址是对的但上不了网」时很好用——它说明客户端自己认为地址已经有了。

五、租约与续租 #

DHCP 给的不是永久地址，是租。租期写在 option 51（IP Address Lease Time）里，单位是秒。

租约机制解决的问题很实际：如果地址一发出去就永久归你，那么设备搬走了、虚拟机删了、员工离职了，地址永远回不来。地址池就那么大，几年下来一定耗尽。加上租期，服务器就有了回收依据。

5.1 三个定时器 #

客户端拿到 ACK 之后，不是等到期才动。它按租期比例启动两个定时器。

定时器 触发点 动作 报文
T1（续租） 租期的 50% 向原服务器单播续租 DHCPREQUEST
T2（重绑定） 租期的 87.5% 广播找任意服务器续租 DHCPREQUEST
租约到期 100% 放弃地址，重新开局 DHCPDISCOVER

T1 到点，客户端单播给当初那台服务器：ciaddr 填当前地址，option 50 不填，意思是「我还要续这个」。服务器同意就回 ACK，租期重置，计时器归零。

T2 到点，说明原服务器没理它（挂了，或者被隔离了）。这时候客户端不再指望那台机器，直接广播找任意能接手的服务器。有别的服务器在，就续上；没有，就等死。

租约到期，地址作废，客户端退回 0.0.0.0，从 DISCOVER 重来。

流程图：

text
拿到 ACK，租期 = T
    |
    |---- 50% T (T1) ----> 单播 REQUEST 给原服务器
    |                         ├─ 收到 ACK → 租期重置，回到起点
    |                         └─ 无响应 → 继续等
    |
    |---- 87.5% T (T2) --> 广播 REQUEST 给任意服务器
    |                         ├─ 收到 ACK → 续上
    |                         └─ 无响应 → 继续等
    |
    |---- 100% T --------> 地址失效，退到 0.0.0.0
                              └─ 重新 DHCPDISCOVER

5.2 为什么断电久了 IP 会变 #

这是最常被问的问题。答案就在上表里。

短时间断电，比如重启、合盖休眠两小时。机器醒来时租期还没过 T1，或者刚过 T1 但服务器还在。它单播续租，服务器看记录还是它，回 ACK，地址不变。所以你感觉「IP 没变」。

长时间断电，比如出差一周、放假回来。租约到期了，服务器已经把地址回收，甚至已经分给了别人。机器一开机，客户端手里的租约已经作废，只能从 DISCOVER 开始。这时候服务器按当前池子状态重新分配，给你哪个就是哪个——多半不是原来那个。

还有一种情况是服务器重启且没有持久化租约记录。醒来后它不认旧账，客户端发 REQUEST 它回 NAK，客户端也只能重新 DISCOVER。

想让某台设备地址稳定，两条路：拉长租期，或者静态绑定。后者更可靠，后面第七章细讲。

5.3 续租时的报文差异 #

同样是 DHCPREQUEST，三种场景的字段不一样，抓包时靠这个区分：

场景 ciaddr option 50 目的地址 目的端口
首次选定（SELECTING） 0.0.0.0 填想拿的地址 255.255.255.255 67
续租（RENEWING） 当前地址 不填 服务器单播地址 67
重绑定（REBINDING） 当前地址 不填 255.255.255.255 67

首次请求必须带 option 50，因为服务器得知道你要的是哪一个。续租时 ciaddr 已经有值，服务器看源地址就知道是谁在续，不需要再问。

抓到 ciaddr = 0.0.0.0 且目的地址是广播的 REQUEST，说明这是开机首次请求；抓到 ciaddr 有值且是单播，说明这是 T1 续租。这一条能快速判断设备当前处于生命周期的哪一段。

六、DHCP 中继 #

广播是 DHCP 的起点，也是它的边界。

DHCPDISCOVER 的目的地址是 255.255.255.255，这是本地广播，路由器默认不转发。也就是说，如果 DHCP 服务器和客户端不在同一个二层网络里，客户端喊破喉咙服务器也听不见。

一个中等规模网络里，按部门、按楼层划了十几个 VLAN，每个 VLAN 一个网段。难道每个网段都放一台 DHCP 服务器？成本高，管理还乱——十几台机器要同步地址池配置。

解法是 DHCP 中继（relay agent）。它就跑在路由器或三层交换机上，配置一行指向 DHCP 服务器地址的命令即可。

6.1 中继怎么工作 #

中继代理在客户端所在网段的接口上监听 UDP 67。收到广播的 DISCOVER，它做两件事：

  1. 把报文里的 giaddr 改成自己这个接口的 IP——服务器靠这个字段知道「请求来自哪个网段」
  2. 把广播转成单播，直接发给配置里指定的 DHCP 服务器

服务器收到后，看 giaddr 落在哪个地址池的网段里，就从那个池子取地址，回 OFFER 给中继（单播）。中继再把 OFFER 广播到本地网段，客户端收到。

text
客户端 VLAN 10                三层设备（中继）            DHCP 服务器（VLAN 99）
10.10.10.0/24                 10.10.10.1                10.99.99.10
    |                              |                          |
    |-- DISCOVER 广播 ------------>|                          |
    |   src 0.0.0.0                | giaddr = 10.10.10.1      |
    |   dst 255.255.255.255        |-- 单播转发 ------------->|
    |                              |                          | 查 giaddr
    |                              |                          | 命中 10.10.10.0/24 池
    |                              |<-- OFFER 单播 -----------|
    |<-- OFFER 广播 ---------------|                          |
    |                              |                          |
    |-- REQUEST 广播 ------------->|-- 单播转发 ------------->|
    |                              |<-- ACK 单播 -------------|
    |<-- ACK 广播 -----------------|                          |

整个过程客户端毫无感知。它仍然以为自己是在跟本地广播域里的服务器对话。

6.2 中继配置的坑 #

giaddr 是唯一的路由依据。服务器不看报文的源 IP（那是中继的地址），只看 giaddr。中继接口地址配错、或者接口上没配地址，服务器就找不到对应池子，直接丢包。症状是客户端一直 DISCOVER，服务器日志里啥也没有。

hops 会累加，且有上限。每过一跳中继加 1，超过阈值（协议规定 16）报文被丢弃。正常拓扑只有一跳，看到 hops 大于 1 说明中继配成了链式转发，属于配置错误。

中继和服务器之间必须三层可达。中继到服务器的单播路径断了，客户端表现还是「拿不到地址」。排查时先在服务器上抓包，看有没有来自中继的请求——有请求没回应是池子问题，连请求都没有是链路或中继配置问题。

多个 VLAN 共用一个服务器时，池子边界要写清。服务器靠 giaddr 匹配网段，网段没在配置里出现，请求就被静默丢弃。这类问题在新增 VLAN 时最常见：交换机配了中继，服务器没加池子。

七、静态绑定与地址池 #

地址池是动态分配的地盘，静态绑定是池子里挖出来的一块「保留地」。

7.1 池子的组成 #

一个典型的 IPv4 网段，地址会切成几段：

区段 例子（10.10.10.0/24） 用途
网络地址与网关 .0、.1 保留，不分配
基础设施段 .2 – .20 交换机、AP、打印机、服务器，静态配
静态绑定段 .21 – .60 按 MAC 绑定的特殊设备
动态池 .61 – .240 普通终端，DHCP 动态发
预留/广播 .241 – .255 留白，不要把池子塞满

池子不要吃满整个网段，这是经验也是纪律。留白有几个用处：临时调试手工配个地址、给新设备腾位置、出问题时手动指定地址绕过 DHCP。

option 51 设的租期决定池子周转速度。租期太长，设备走了地址回不来，池子看着大实际不够用；租期太短，续租报文多，服务器压力大。具体给多少要看服务器文档里的默认值和实际设备流动率，各家实现的默认值不一样，别直接抄别人的数。

7.2 静态绑定：MAC 与 IP 对齐 #

有些设备必须是固定地址：服务器、网络打印机、监控 NVR、门禁控制器。给它们改静态 IP 是可以的，但一旦要改网关或 DNS，就得逐台去改。更省事的做法是在 DHCP 服务器上做静态绑定——把 MAC 和 IP 绑死，设备侧仍然用自动获取。

配置的形态大致是：

text
host printer-3f {
    hardware ethernet 00:1a:2b:3c:4d:5e;
    fixed-address 10.10.10.30;
}

这样设备换网关、换 DNS，只要服务器改一处，它下次续租自动跟上。而且地址不会因为租约到期被别人抢走。

绑定的前提是 MAC 稳定。有线网卡的 MAC 一般写在硬件里，稳定。无线设备默认会随机化 MAC（手机为了隐私），这时候绑定会失效——要么在设备上关掉随机 MAC，要么改用别的手段。

虚拟机要注意：克隆虚拟机时如果不重新生成 MAC，两台机器的 MAC 一样，绑定就冲突了。表现是两台机器抢同一个地址，或者其中一台反复收到 NAK。

7.3 池子耗尽的信号 #

池子快满的时候有几个前兆：

  • 客户端 DISCOVER 之后收不到 OFFER，或者收到 OFFER 但 REQUEST 之后被 NAK
  • 服务器日志里出现「no free leases」之类的记录
  • 新设备连上后地址显示 169.254.x.x——这是链路本地地址，意味着 DHCP 彻底失败
  • 老设备正常，新接入的设备全都不行

排查顺序：先看池子使用率，再看是否有大量「僵尸租约」（设备已经不在了但租约还在租期内），最后看是不是被 DHCP 饥饿攻击打了一轮（见第十一章）。

租约回收不是实时的。设备拔了不会通知服务器（除非正常关机发了 RELEASE），服务器只能等到租约自然到期。所以池子大小要按「峰值设备数 × 1.3」估，不能按平均值算。

八、常见选项 #

选项是 DHCP 真正有价值的部分。地址只是入场券，参数才决定你能干什么。

编号 名称 作用 用错的表现
1 Subnet Mask 子网掩码 跨网段访问异常，同网段正常
3 Router 默认网关，可多个 上不了外网，内网通
6 Domain Name Server DNS 服务器，可多个 能 ping 通 IP，域名解析失败
15 Domain Name 域名后缀 短名解析失败
28 Broadcast Address 广播地址 极少需要手动配
42 NTP Servers 时间服务器 时间漂移，证书校验失败
51 IP Address Lease Time 租期（秒） 太长地址回收慢，太短续租风暴
53 DHCP Message Type 报文类型 配错直接报文无法识别
54 Server Identifier 服务器标识 多服务器环境下选错
55 Parameter Request List 客户端想要哪些选项 客户端拿不到想要的参数
58 Renewal Time (T1) 续租定时器 不填则按 50% 推算
59 Rebinding Time (T2) 重绑定定时器 不填则按 87.5% 推算
66 TFTP Server Name 引导服务器 网络启动失败
67 Bootfile Name 引导文件名 网络启动拿不到镜像
82 Relay Agent Information 中继附加信息 按端口/电路定位的策略失效

几个必须记住的：

option 3 是网关。这是最容易配错也最容易查的一项。配错的表现非常典型：能 ping 通同网段的所有设备，ping 不通任何跨网段地址，域名当然也解析不了。查的时候在客户端 ipconfig /all（Windows）或 ip addr（Linux）看默认网关，再跟服务器配置对一遍。

option 6 是 DNS。可以给多个，客户端按顺序尝试。第一台挂了会等超时才试第二台，所以顺序有意义。域名解析慢但最终能通，八成是第一台 DNS 不通在等超时。

option 51 是租期。这个值不写会取服务器默认值。租期改动的生效时机是下次续租，不是立刻——已经在线的设备还按老租约走。

option 55 是客户端的点菜单。客户端在 DISCOVER 里列出它想要的选项编号，服务器按这个列表回。客户端没要的，服务器可以不发。抓包时看 option 55 就知道这台机器期待什么配置，比猜快。

option 82 只在有中继时出现。中继把自己的接口信息、VLAN、甚至客户端接入的物理端口号塞进去，服务器可以据此做精细策略——比如「同一个 MAC 在会议室端口拿 192.168.20.x，在研发端口拿 10.10.30.x」。想做「按位置分配地址池」，靠的就是它。

8.1 选项下发的优先级 #

服务器上可以配全局选项、网段选项、主机选项。优先级从窄到宽：

层级 作用范围 优先级
主机级（静态绑定里） 单台设备 最高
网段级（subnet 内） 一个 VLAN 中
全局（服务器级） 所有池子 最低

配 DNS 一般在全局，网关必须在网段级（每个网段网关不同），个别设备的特殊参数放主机级。层级搞混是常见配置事故——全局配了网关，结果所有 VLAN 的客户端都拿到同一个网关，除了那一个网段全废。

九、DHCPv6 与其他自动配置 #

IPv6 没有广播。这是它跟 IPv4 最根本的差别，直接导致 DHCPv6 的设计完全不同。

9.1 IPv6 的三种地址来源 #

方式 全称 谁给地址 典型场景
SLAAC 无状态地址自动配置 客户端自己算 家用网络、简单办公网
DHCPv6 无状态 只发 DNS 等参数 服务器给参数 与 SLAAC 配合
DHCPv6 有状态 地址和参数都给 服务器给地址 需要集中管控的环境

SLAAC 的做法是：路由器发 RA（Router Advertisement）通告前缀，客户端拿前缀加上自己的接口标识拼出一个地址，然后做重复地址检测。整个过程没有服务器分配动作，所以叫「无状态」。

DHCPv6 有状态模式则由服务器统一分配地址，能记录「谁用了哪个地址」，审计和追责需要这个能力。

两者可以共存，靠 RA 里的两个标志位协调：

  • M 位（Managed）：置 1 表示「地址找我（DHCPv6）要」
  • O 位（Other）：置 1 表示「地址你自己配，其他参数找我（DHCPv6）要」

M=1 是有状态，M=0 O=1 是无状态 DHCPv6 配 SLAAC，M=0 O=0 是纯 SLAAC。

9.2 DHCPv6 的报文 #

DHCPv6 的交互不像 DORA 那么规整，报文名字也不一样：

报文 作用 对应 IPv4
SOLICIT 客户端找服务器 DISCOVER
ADVERTISE 服务器应答 OFFER
REQUEST 客户端请求 REQUEST
REPLY 服务器确认 ACK
RENEW 续租 REQUEST（T1）
REBIND 重绑定 REQUEST（T2）
RELEASE 释放 RELEASE
DECLINE 地址冲突 DECLINE
INFORMATION-REQUEST 只求参数 INFORM

同样是四步开局，但 SOLICIT 走的是组播地址 FF02::1:2（所有 DHCP 服务器和中继），不是广播——IPv6 里没有广播这个机制。

端口也换了：服务器 547，客户端 546。

9.3 为什么很多网络还在用 IPv4 的 DHCP #

不是技术原因，是迁移成本。IPv4 的 DHCP 配套成熟，中继、选项、Snooping、地址池管理都有现成工具。IPv6 上来以后，很多网络先用 SLAAC 让设备能通，DHCPv6 有状态分配反而推得慢。

实际部署里常见的是「双栈 + 双 DHCP」：IPv4 走 DHCP 拿地址和网关，IPv6 走 SLAAC 或 DHCPv6 只拿 DNS。这个组合能跑，但排障时要注意两条链路给出的 DNS 不一样，谁生效取决于系统偏好。

9.4 其他自动配置手段 #

DHCP 不是唯一的「自动拿到地址」路径，另外两个也常见：

PPPoE。拨号上网，地址在 PPP 协商阶段由 BRAS 分配。家用宽带和部分园区网在用。它跟 DHCP 的区别是链路层先建立会话再分配地址。

静态配置 + 配置管理工具。服务器和网络设备在数据中心里经常不用 DHCP，而是靠 Ansible、Puppet 之类工具推送配置。原因是这些机器的地址必须在下发配置前就确定，不能依赖「开机时随机拿一个」。

这三种方式的选择标准很简单：设备会移动、数量大、临时接入，用 DHCP；设备固定、需要可预测、有配置管理系统，用静态。混着用就按接口类型分。

十、故障排查 #

DHCP 故障的表现高度趋同：上不了网，地址是 169.254.x.x，或者干脆没有地址。但原因分布极广。按层次往下捋。

10.1 症状对照表 #

症状 头号嫌疑 下一步查什么
地址 169.254.x.x 完全没收到 DHCP 响应 抓包看有没有 DISCOVER 发出
一直 DISCOVER，无 OFFER 服务器不可达 / 池子空 / 中继没配 服务器侧抓包
有 OFFER，REQUEST 后被 NAK 要的地址服务器不认 看服务器租约记录
拿到地址但上不了网 网关或 DNS 选项错 对照 option 3 / option 6
同网段通，跨网段不通 网关配错或缺网关 看默认路由
能 ping 通 IP，域名不行 DNS 没下发或不可用 看 option 6
地址频繁变化 租约太短 / 服务器无持久化 看 option 51
两台设备同地址 静态配置冲突 / 绑定重复 扫全网 ARP
地址拿到了但很慢 DISCOVER 重传 / 服务器响应慢 看 secs 字段

10.2 分平台的操作 #

Windows 上四件事最常用：

bash
ipconfig /all           # 看完整参数，含租约起止时间、DHCP 服务器地址
ipconfig /release       # 释放地址，IP 变 0.0.0.0
ipconfig /renew         # 重新申请，抓包就是 DORA 四步
ipconfig /displaydns    # 看 DNS 缓存，排查解析问题时用

ipconfig /? 能列出全部参数。/all 的输出里，Lease Obtained 和 Lease Expires 两行直接告诉你租期还剩多久，DHCP Server 一行告诉你是哪台机器发的——排查「分配了错网关」时，先确认是不是自己那台服务器发的，别去查无关的机器。

Linux 上：

bash
ip addr show                    # 看地址
ip route                        # 看默认网关
cat /etc/resolv.conf            # 看 DNS
dhclient -v eth0                # 前台跑 DHCP 客户端，能看到完整交互
journalctl -u NetworkManager    # 看 NetworkManager 日志

dhclient -v 是排查主力——它把 DISCOVER、OFFER、REQUEST、ACK 每一步都打出来，卡在哪一步一目了然。

还有一种情况：系统同时跑着 NetworkManager 和 systemd-networkd，两个 DHCP 客户端抢着干活，表现是地址反复变。查 systemctl status 看谁在跑。

10.3 抓包定位法 #

抓包是唯一能一锤定音的手段。Wireshark 里过滤 bootp（老名字，见第一章），一次完整的成功分配应该看到四个包。

按缺失的包判断问题所在：

看到什么 结论
只有 DISCOVER 服务器没收到，或没回。查链路、中继、池子
DISCOVER + OFFER，无 REQUEST 客户端拒绝了 OFFER，多为地址冲突
DISCOVER + OFFER + REQUEST，无 ACK 服务器拒绝，查租约记录和池子
四个都有但地址不对 服务器配置错，或有多台服务器抢答
有多个 OFFER，来自不同服务器 网段里有多台 DHCP 服务器，需要确认哪台该留

「多台服务器抢答」是隐蔽故障。表现是同一批设备有的拿到 10.10.10.x，有的拿到 192.168.1.x，后者当然上不了网。抓包看 OFFER 的源地址就能确认。成因多半是有人在路由器上误开了 DHCP，或者测试用的设备忘了关。

10.4 服务端排查 #

客户端侧看完，转到服务器侧。先看服务状态和最近日志，再对照租约文件，最后在服务器上抓包确认请求是否到达：

bash
systemctl status isc-dhcp-server
journalctl -u isc-dhcp-server -n 100
cat /var/lib/dhcp/dhcpd.leases
tcpdump -i any -n port 67 or port 68

服务器上抓不到包，说明问题在中继或链路上；抓到包但不回，说明是配置或池子问题。这两条分岔能把排查范围砍一半。

十一、安全风险与防护 #

DHCP 没有任何内建的身份认证。任何人插上一台机器，跑个 DHCP 服务，就能参与这场广播游戏。这是协议设计时没考虑攻击面的结果，不是实现缺陷。

11.1 饥饿攻击 #

饥饿攻击（DHCP starvation attack）就是这一类。

原理不复杂：攻击者伪造大量 MAC 地址，不断向 DHCP 服务器发 REQUEST，把池子里的地址耗尽。服务器以为真的来了几百台设备，把地址一个个分出去。

池子空了以后，正常设备拿不到地址。这时候攻击者再起一台自己的 DHCP 服务器（这就是「流氓 DHCP」），接管所有新接入设备的配置下发。

它跟 SYN 洪泛的思路确实像：都是耗尽服务端的某种有限资源（这里是租约表，那里是半连接队列），让合法请求进不来。

11.2 流氓 DHCP #

比饥饿攻击更简单的路子，是不搞破坏，直接抢答。

攻击者起一台 DHCP 服务器，配置里把 option 3（网关）指向自己、option 6（DNS）也指向自己。因为它是先回 OFFER 的那台（或者客户端按先到先得选），一部分设备就会拿到这套配置。

拿到以后，所有出网流量都经过攻击者的机器。他可以：

  • 记录明文流量
  • 做 DNS 劫持，把域名指到自己的服务器
  • 直接丢包，制造「网络故障」

这就是中间人攻击的标准手法。路径分两段：先用伪 MAC 把真服务器的池子打空，再伪造一台把网关和 DNS 都指向自己。

11.3 防护手段 #

DHCP Snooping 是第一道闸。它在交换机上把端口分成两类：

端口类型 允许做什么 接什么设备
信任端口（trusted） 可以发 OFFER/ACK 等服务器侧报文 上联口、DHCP 服务器所在口
非信任端口（untrusted） 只允许客户端侧报文，丢弃 OFFER/ACK 接终端的所有口

配好之后，普通接入端口上冒出来的 OFFER 会被直接丢弃。攻击者再起服务器也发不出配置。

Snooping 还顺手带来一个能力：它会监听 DORA 过程，在交换机本地建立一张「IP、MAC、端口、VLAN」的绑定表。这张表能喂给动态 ARP 检测（DAI）和 IP Source Guard 用，把「伪造 IP」和「伪造 ARP」也一起挡住。

端口安全限制单个端口学到的 MAC 数量，直接压制「伪造大量 MAC」的饥饿攻击。一个接终端的口，学到一个 MAC 就够了，多出来的直接违规处理。

DHCP 报文限速在交换机上对 DHCP 报文做速率限制，防止瞬间大量请求打爆服务器。

静态绑定 + 池子留白降低影响面。关键设备绑死，即使池子被打空也不影响它们。

服务器侧限制：给单端口或单 VLAN 的分配速率设上限，租约表加清理机制。

11.4 防护的边界 #

Snooping 只在交换机上生效。如果接入的是个没有管理功能的傻瓜交换机，或者有人绕过交换机直接插到墙上的信息面板，防护就断了。物理安全是网络安全的前提，这句话在这儿特别实在。

无线侧的做法不同：企业级 WLAN 在 AC 上做客户端隔离和 DHCP 代理，不让终端之间直接通信，也由 AC 统一转发 DHCP 请求。

再补三条不写在表里但踩过的人最多的：

一、169.254 开头的地址不是「分配失败」。 它是链路本地地址，是系统在 DHCP 彻底失败后自己挑的一个，只保证同链路能通。看到它，说明 DISCOVER 没有回应，问题在服务器或链路，不在客户端配置。

二、地址拿到了但网关 ping 不通，先看网关地址是不是本网段的。DHCP 服务器按网段选池子，但如果池子里配的 option 3 是别的网段的网关，客户端就会把包发给一个够不着的地址。这类配置错误在多 VLAN 环境里相当常见。

三、改完 DHCP 配置别急着说「好了」。 已经在线的客户端不受影响，它们要等 T1 才续租。想立刻验证，用 ipconfig /renew 或 dhclient -r && dhclient 强制走一轮。给用户报结论之前，至少拿一台没配过静态地址的机器实测。

DHCP 就是这样一个协议：报文只有四个，字段看着一堆，但真正的难点全在「广播怎么跨网段」「租约什么时候续」「参数到底配在哪一级」这三件事上。把这三点吃透，抓包看一眼 xid、giaddr、option 53，基本就能定位到问题在哪一跳。
