范围：本篇讲交换机之间那条线怎么配。一是 Trunk——一根线承载多个 VLAN；二是链路聚合——多根线合成一条。 不讲：VLAN 的收发规则、Access/Trunk/ Hybrid 三种端口的标签处理细节、PVID 怎么推导，这些在 03-协议栈与内核实现/VLAN 原理与配置 里；iptables 与 NAT、ACL、主机侧网络配置在同目录另外三篇。 前置：知道 VLAN 是什么，认得 tagged 和 untagged 两个词。

一、Trunk 解决什么问题 #

先摆场景。两台交换机，每台划了 vlan 10、20、30、40。你要让这四个 VLAN 在两边都通。

不用 Trunk 的笨办法：一个 VLAN 拉一根线，两端各占一个 Access 口。四个 VLAN 四根线，八个端口没了。加到十个 VLAN，就是十根线、二十个端口。机房里线一多，接错一根够你查一晚上。

用 Trunk：一根线，两端各一个口，四个 VLAN 全过去。省端口、省线、省事。

它凭什么能在一根线上分清四个 VLAN？靠标签。

交换机从 vlan 10 的口收到一个帧，要往 Trunk 口发的时候，在帧头插进 4 个字节，里面写着 VLAN ID = 10。对端 Trunk 口收到，读标签知道这是 vlan 10，撕掉标签，从 vlan 10 的成员口送出去。vlan 20 的帧走同一根线，只是标签里的数字不同。

所以 Trunk 的本质就一句话：逐帧加标签，用标签区分归属。

标签是逐帧加的，不是给整条链路打个记号。同一根线上跑着的帧，有的标签写 10，有的写 20，混着走。链路上没有「这条线属于 vlan 10」这种说法——Trunk 链路本身不属于任何一个 VLAN，它在交换机之间起 VLAN 管道的作用。

把 Trunk 口当成什么看，决定了它的行为。Trunk 口在转发层面被当作一个逻辑端口，交换机会把 Trunk 之外、且与 Trunk 中端口同属一个 VLAN 的其它端口的负载，自动分配到该 Trunk 的各个物理端口上。同一个 VLAN 的端口之间要互相转发数据帧，如果这些负载不摊到各个成员口，帧就会被随机塞进某一条，顺序乱了。因为 Trunk 口按一个逻辑端口对待，所以设了 Trunk 之后，这条 Trunk 会自动加入它的成员端口原来所属的那些 VLAN，而成员端口自己从 VLAN 里被摘出去。

这就是 Trunk 和 Access 的根本差别：Access 口属于一个 VLAN，Trunk 口不属于任何 VLAN，它承载一批 VLAN。

链路两端可以都是交换机，也可以是交换机和路由器，还可以是主机和交换机或路由器。点到点，没有第三个端点。

有一个词要拆开。很多资料把 Trunk 直接说成「端口汇聚」「端口捆绑」——把 2 个或多个物理端口合成一条逻辑路径来加带宽。这个描述说的是链路聚合，不是 802.1Q Trunk。老设备文档里两个概念经常混着写，厂商命令也各叫各的。我们这篇把两件事分开讲：Trunk 管「多个 VLAN 走一根线」，链路聚合管「多根线当一个口用」。它们能叠在一起用，但解决的问题不一样。

两端必须对称 #

这是 Trunk 最容易踩的坑，没有第二个。

一端配成 Trunk，另一端还是 Access，不通。用户报的现象是「跨交换机同一个 VLAN 内 ping 不通」，你去查 IP、查掩码、查 ARP 表，全是好的，因为问题在二层。

Access 口收到带标签的帧会怎样？多数设备直接丢弃——它不认标签，认为这帧不属于自己管的这个 VLAN。带标签的帧被丢，无标签的帧被塞进本口 VLAN，两边对不上，流量就断了。

所以记住这条：Trunk 是两端协商出来的成对配置，不是单边开关。封装标准也要一致，一边 802.1Q 一边 ISL，同样不通，而且这种错比 Trunk/Access 混配更难看出来。

text
正确                             错误
[SW1]==========[SW2]             [SW1]==========[SW2]
 Trunk         Trunk              Trunk         Access
 802.1Q        802.1Q             802.1Q        (无标签)
 |
 vlan 10/20/30 全通               带标签帧被对端丢弃，全断

还有一种半对半错的：两端都 Trunk，但允许通过的 VLAN 列表不一样。vlan 10 在 SW1 的允许列表里、不在 SW2 里，那 vlan 10 就单方向断。

二、Trunk 的封装标准 #

要在一根线上传多个 VLAN 的通信，得用专门的协议封装或者加标记（tag），让接收设备能区分数据属于哪个 VLAN。历史上主流就两套：IEEE 802.1Q 和 Cisco 专有的 ISL。

802.1Q 的标签长什么样 #

802.1Q 的正式名称是虚拟桥接局域网标准。它不动整个帧，只在源 MAC 地址后面插 4 个字节。

text
| 目的MAC 6B | 源MAC 6B | TPID 2B | TCI 2B | 类型/长度 2B | 数据 ... | FCS 4B |
                          \_________________/
                           802.1Q 标签（4 字节）

TPID 固定 0x8100，交换机见到这两个字节就知道后面跟着 VLAN 信息。TCI 里再切三段：

字段 长度 作用
TPID 16 bit 固定 0x8100，标识这是 802.1Q 标签
PCP 3 bit 优先级，QoS 用，值越大越优先
DEI 1 bit 丢弃资格，拥塞时可优先丢
VID 12 bit VLAN ID，0～4095，可用范围 1～4094

12 bit 的 VID 决定了 802.1Q 能表达的 VLAN 上限是 4094 个（0 和 4095 保留）。这也解释了为什么很多交换机的 VLAN 号上限是 4094。

插了 4 个字节，帧就变长了：标准以太帧上限 1518 字节，加了标签变成 1522。这个超出 1518 的帧，就是素材里说的「小巨人帧」。普通网卡不认，超过它理解的帧长会被当错帧丢掉，所以标签必须在交换机上被撕掉——终端设备看到的是干净的原始帧。

ISL 的路子 #

交换机间链路（ISL）是 Cisco 专有协议，用于连接多台交换机，在数据于交换机之间传递时负责保持 VLAN 信息。它和 802.1Q 的做法完全不同：不是插标签，是把整个原始帧外面再包一层。26 字节的 ISL 头加 4 字节 CRC 尾，原帧原封不动装进去。

在一个 ISL 干道端口上，所有收到的数据包都被期望带着 ISL 头；所有发出的包也都带 ISL 头。从一个 ISL 端口收到的本地帧（non-tagged）会被丢弃——因为它没有封装，不符合这个口的要求。它只用在 Cisco 产品里。

帧长了 30 字节，1518 变 1548。ISL 头里的 VLAN 字段只有 10 bit，能表达的 VLAN 数比 802.1Q 少。ISL 不支持无标签流量，所以没有 Native VLAN 这回事，也就没有 VLAN 跳变那条攻击路径。

新设备上基本见不到 ISL 了。Cisco 自己的新一代产品也以 802.1Q 为主。你只有在接手老网络时才需要认它。

两套标准对照 #

维度 IEEE 802.1Q ISL
标准化 IEEE 标准，跨厂商 Cisco 专有
封装方式 源 MAC 后插 4 字节标签 整帧外包 26 字节头 + 4 字节尾
帧长变化 1518 → 1522 1518 → 1548
VLAN 容量 4094 约 1000
无标签流量 支持，归 Native VLAN 不支持，本地帧丢弃
跨厂商互通 可以 不行
现状 事实标准 老网络遗留

选型没什么可纠结的，除非对面是台只能在 ISL 上跑的老 Cisco，一律 802.1Q。

帧过滤与帧标记 #

在 Trunk 线路上识别不同 VLAN 的数据，历史上有两种方法：帧过滤和帧标记。

帧过滤法靠交换机的过滤表检查帧的详细信息。每台交换机要维护复杂的过滤表，对通过主干的每一个帧逐帧细查，网络延迟跟着涨。这法子现在已经不用了。

现在用的是帧标记法。数据帧在中继线上传输时，交换机在帧头信息里加标记指定 VLAN ID；帧穿过中继后，去掉标记，交换到对应的 VLAN 端口。帧标记法被 IEEE 选为标准化中继机制。

我们前面讲的 802.1Q 和 ISL，都是帧标记法的两种具体实现。

干线的三种建立方式 #

帧标记法之下，干线怎么建起来，有三种处理办法。

方式 做法 特点
静态干线配置 程序里写死，两端用指定协议收发 最直观；自动协商坏了时用；要手工维护
干线功能通告 周期性发通告帧，说明自己支持哪种帧标记 VLAN 适合端节点与干线混接的网段
干线自动协商 周期性发指示帧表示希望转干线模式，对端识别后自动配 依赖两端已有链路，端口需专用

静态干线最容易理解：干线上每台交换机都由程序设定发送及接收使用特定干线协议的帧。这种设置下端口专用于干线连接，不能拿去接端节点——至少不能接那些不用干线协议（trunking protocol）的端节点。缺点是必须手工维护，好处是自动协商坏了或压根没开的时候，它照样能起来。

通告方式的思路是「我先声明我能干什么」。交换机周期性地发通告帧，比如通告自己支持某种帧标记 VLAN，那么按它通告的帧格式发过去就不会错。它还能通告自己现在想给哪个 VLAN 提供干线服务。

自动协商则是双向确认：两端都发指示帧表示想进干线模式，收到并识别后自动把端口设成干线。它依赖两台交换机之间已有的链路，且相连的端口要专用于干线。

三、Native VLAN #

Native VLAN 是 802.1Q 里最容易被忽略、又最容易出事的一个参数。

它是什么 #

802.1Q 干道端口同时支持加标签和未加标签的流量。这个端口被指派一个缺省的端口 VLAN ID，也就是 PVID。所有未加标签的流量，在这个端口的缺省 PVID 上传输。

换个说法：Native VLAN 就是这个 Trunk 口上不打标签的那个 VLAN。

反过来说也成立：一个带着 VLAN ID 的帧，如果它的 VLAN ID 正好等于外出端口的缺省 PVID，那么它发出去的时候不加标签。所有其它流量发出去都带标签。

text
从 Trunk 口发出：
  vlan 10 的帧 → 打 tag(10) → 发出
  vlan 20 的帧 → 打 tag(20) → 发出
  Native vlan 的帧 → 不打标签 → 发出

从 Trunk 口收进：
  带 tag 的帧 → 按标签 VLAN 归属
  不带 tag 的帧 → 归到本口 Native VLAN

为什么要留这么一个「不带标签」的缺口？因为要给不认 802.1Q 的设备留条活路。一台老服务器、一台不支持 VLAN 的打印机接在 Trunk 口上，只能收发无标签帧，靠 Native VLAN 落到某个 VLAN 里。

两端不一致会怎样 #

问题就在这：无标签帧不带 VLAN 信息，它的归属完全由本地配置决定。

SW1 的 Trunk 口 Native VLAN 是 10，SW2 那头是 20。SW1 上 vlan 10 的帧发出去时不打标签，SW2 收到一个无标签帧，按自己的 Native VLAN 把它归到 vlan 20。于是 vlan 10 的广播、vlan 10 的网关请求，全跑进了 vlan 20。

这种错很难查。两端的 VLAN 配置看上去都正确，Trunk 也起来了，show 出来的状态是 up。但流量在悄悄串门。表现是「某些网段能通、某些网段地址冲突、DHCP 发错网段」。

所以配置 Trunk 时，两端 Native VLAN 必须一致。这是硬要求。

VLAN 跳变 #

Native VLAN 还开了一扇门，叫 VLAN 跳变（VLAN hopping）。手法是双重标签。

攻击者在帧里塞两层 802.1Q 标签。外层标签的 VID 写成 Trunk 口的 Native VLAN。交换机收到这个帧，看外层标签等于本口 Native VLAN，认为它就是本地的无标签流量——剥掉外层，转给 Trunk 口。

Trunk 口发出时，剥掉的那层已经没了，剩下内层标签还在。内层标签写着攻击者想去的那个 VLAN（比如 vlan 100，一个他本来没权限碰的隔离网段）。对端交换机收到带 tag(100) 的帧，老老实实按 vlan 100 转发。

一层标签撕掉、一层标签留下，帧就跨过了本来不该跨的边界。

text
攻击者构造：  [ 外层 tag(Native) | 内层 tag(100) | 数据 ]
交换机1：     剥外层 → 以为是本地 Native 流量
Trunk 口：    转发时内层 tag(100) 保留
交换机2：     收到 tag(100) → 送进 vlan 100

防法很直接。

实践上的三条 #

第一，把 Native VLAN 改成一个不承载业务的 VLAN 号。素材里那句「缺省是 1」是必须改的理由——出厂默认所有口的 Native VLAN 都是 VLAN 1，全世界的默认值都一样，等于没设防。改成 999 之类没人用的号，两端改成同一个。

第二，Trunk 口的 Native VLAN 上不接任何业务终端。既然没人用这个 VLAN，双重标签打进来也没有落点。

第三，Trunk 口上不要的 VLAN 就从允许列表里删掉。允许列表越长，能跳进去的目标越多。

再加一条运维习惯：把 Native VLAN 不一致当成 Trunk 上线前的必查项写进检查单，别靠记性。

四、Trunk 的配置 #

先说清楚：下面出现的命令是按老式 Cisco CatOS 的写法给的，只用来讲清参数结构。具体厂商、具体型号的语法差别很大，以所用设备的命令为准。你要做的是理解每个参数在管什么。

一条命令的四个部分 #

text
set trunk mod/port [on | off | desirable | auto | nonegotiate] \
                  [vlan_range] [isl | dot1q | dot10 | lane | negotiate]

拆成四块看。

第一块 mod/port：你要跑 Trunk 的那个端口。

第二块是 Trunk 的运行模式：on、off、desirable、auto、nonegotiate。

第三块是承载的 VLAN 范围。缺省是 1～1005，可以改，但必须有 Trunk 协议在。用 Trunk 时，相邻端口上的协议要一致。

第四块是封装类型：isl、dot1q、dot10、lane、negotiate。dot1q 就是 802.1Q，isl 是 Cisco 专有封装，negotiate 让两端协商。

五个模式在管什么 #

模式 主动发起 响应对方 说明
on 不协商，直接起 —— 强制 Trunk，不发协商帧
off 不起 不起 强制 Access
desirable 主动发协商帧 响应 希望起 Trunk，等对端点头
auto 不发 响应才起 被动等对端来谈
nonegotiate 不协商，直接起 —— 强制 Trunk，且彻底关闭协商

两条配套的规则，素材点得很准：

想在快速以太网和千兆以太网上自动识别出 Trunk，必须保证两端在同一个 VTP 域内。不在同一个域，协商帧对不上号，desirable 和 auto 白搭。

也可以用 on 或 nonegotiate 模式强行把一个端口上起 Trunk，不管它在不在同一个 VTP 域内。

on 和 nonegotiate 的区别值得说一句：两者都强制起 Trunk，但 on 仍然会发协商帧，nonegotiate 连协商帧都不发。对端如果是 auto，on 能配上，nonegotiate 配不上——因为 auto 那头在等帧。所以两端都用 nonegotiate，或者一端 nonegotiate 一端 on。

模式配对表 #

两个口能不能起 Trunk，看两端模式怎么组合。

本端 \ 对端 on desirable auto nonegotiate off
on 起 起 起 起 不起
desirable 起 起 起 不起 不起
auto 起 起 不起 不起 不起
nonegotiate 起 不起 不起 起 不起

auto + auto 不起，这是最典型的错误组合。两端都在等对方先开口，谁都不动，链路就一直是 Access。

从表里能看出一个规律：只要有一端是 on，基本都能起来。所以不想折腾协商，两端配 on 或 nonegotiate 最稳——代价是端口被写死，换设备、改拓扑都要人工同步。

配在哪里 #

拓扑上，需要把中心交换机上和下级交换机相连的端口配成 Trunk，这样子交换机里的多个 VLAN 才能通过一条链路和中心交换机通信。

text
        [中心交换机]
        /     |     \
   Trunk     Trunk   Trunk
     |         |       |
  [接入SW1] [接入SW2] [接入SW3]
   每个接入交换机内部有 vlan 10/20/30
   每条 Trunk 上跑 10/20/30 三个 VLAN

接入层交换机之间的横向链路，如果只是同 VLAN 互联，Access 口就够；要让多个 VLAN 跨过去，还是得上 Trunk。

配完要确认的两件事 #

一是两端封装标准一致（dot1q 对 dot1q）。二是两端允许列表包含你要通的 VLAN，且 Native VLAN 一致。任何一条不满足，前面的模式配对全白费。

五、Trunk 的排错 #

Trunk 不通，八成不是玄学问题，而是某个参数不对称。按固定顺序查，比乱翻配置快。

命令名各家不同，下面用 show 开头举例，具体以所用设备为准。思路是通用的：看状态、看封装、看 Native VLAN、看允许列表。

第一步：链路本身通不通 #

先看物理层。端口是不是 up？光模块亮不亮？两端速率双工对不对？

这一步错的人不少。端口 down 的时候，你盯着 Trunk 配置看半小时，全是白看。Trunk 起不来的第一个原因永远是物理链路没起来。

text
show interface <port>            # 看 up/down、速率、双工、CRC 错误计数

CRC 计数在涨，说明线或模块有问题，跟 Trunk 配置无关。

第二步：Trunk 起没起来 #

text
show interface <port> trunk      # 看模式、封装、Native VLAN、允许 VLAN 列表
show interface <port> switchport # 看 administrative/operational 模式对比

重点看两处：管理配置模式和你预期的模式是否一致，运行状态是 trunking 还是 static access。

配置写的是 desirable，运行状态显示 static access，说明协商没成功。回去查模式配对——对端是不是 auto，或者两条链路不在同一个 VTP 域。

第三步：封装标准对不对 #

一端 dot1q 一端 isl，运行状态照样显示 trunking，但流量不过。这种错最坑，因为状态看起来是好的。

抓到包看就明白了：帧里是 4 字节标签还是 26 字节 ISL 头，对端按另一套解，全错位。

排查时把两端的封装类型并列写出来对一遍，别只看一端。

第四步：Native VLAN 对不对 #

两端 Native VLAN 不一致，Trunk 状态正常，无标签流量串 VLAN。这个错在状态里看不出来，得两边比配置。

素材里说「相邻端口上的协议要一致」，扩展一下：Native VLAN 也要一致，允许的 VLAN 范围也要能对上。

第五步：允许列表对不对 #

Trunk 允许列表是个白名单。不在列表里的 VLAN，帧直接被丢掉。

一个 VLAN 只在一个方向通，多半是两端允许列表不一致。查的时候把两端的允许列表都打出来，做差集。

text
SW1 允许: 1,10,20,30
SW2 允许: 1,10,20,40
                ↑ vlan 30 和 40 各断一个方向

第六步：STP 有没有在捣乱 #

Trunk 链路被生成树阻塞，你看到端口 up、Trunk 也 up，就是不转发。查生成树端口状态，看是不是 discarding 或者 alternate。

两个交换机之间有两条线，又都配了 Trunk，STP 会阻塞其中一条。这时候不是 Trunk 的问题，是拓扑有环。

常见故障对照 #

现象 头号嫌疑 查什么
端口 up，Trunk 不起来 模式组合无效（auto+auto） 两端模式、VTP 域
Trunk 起来了，全 VLAN 不通 封装标准不一致 两端 dot1q/isl
部分 VLAN 通，部分不通 允许列表不一致 两端允许 VLAN 做差集
能通但流量跑错网段 Native VLAN 不一致 两端 Native VLAN
一个方向通，另一方向不通 允许列表单向缺失 两端允许列表
端口 up 但不转发 STP 阻塞 生成树端口状态
通了但丢包严重 物理层错误、双工不匹配 CRC 计数、双工设置

一个快速验证手法 #

怀疑某个 VLAN 不通时，把 Trunk 允许列表临时收窄到只剩这一个 VLAN，两端都收窄。通了，说明是列表问题；不通，问题在更底层（封装、Native VLAN、STP）。

测完记得改回去。

六、链路聚合是什么 #

Trunk 解决「一根线跑多个 VLAN」，链路聚合解决「一根线不够快」。

素材里那个定义 #

端口汇聚是通过配置软件的设置，把 2 个或多个物理端口组合在一起成为一条逻辑路径，从而增加交换机和网络节点之间的带宽——把属于这几个端口的带宽合并，给端口提供一个几倍于独立端口的独享高带宽。

基于端口汇聚功能，交换机与交换机、交换机与路由器、主机与交换机或路由器之间，可以通过两个或多个端口并行连接同时传输，提供更高带宽、更大吞吐量。

这段描述讲的是链路聚合，只是把名字叫成了 Trunk。厂商文档、老教材、招聘 JD 里三个词——Trunk、端口汇聚、链路聚合——经常指同一个东西。看上下文判断它说的是「多个 VLAN 走一根线」还是「多根线当一个口用」。

为什么需要它 #

不用聚合时，百兆以太网的双绞线这种传输介质特性，决定了两台互连的普通 10/100 交换机之间带宽只有 100M。全双工模式下最大能到 200M（收发各 100M）。这个数字在今天不算什么，在当年就是网络主干和服务器的瓶颈。

要更高的传输率，路子是换介质——千兆光纤，或者升级成千兆以太网。带宽能上千兆，成本很贵，连交换机都得换掉，对预算有限的中小企业和学校不划算。

用聚合就不一样了：把四个百兆端口捆在一起，得到 800M 带宽。成本和性能之间的矛盾，这样解决。

text
单链路：      [SW]----100M----[SW]      峰值 200M（全双工）
四口聚合：    [SW]====400M=====[SW]      峰值 800M（全双工）
                  四条物理线，一个逻辑口

这就是聚合的全部吸引力：不换线、不换设备，用现成的空闲端口换带宽。

三个应用场景 #

场景 做法 收益
服务器接入 服务器多网卡绑成一个聚合口接交换机 服务器独享高带宽
交换机级联 两台交换机之间多条线捆成一条 突破单链路瓶颈，提高骨干吞吐
容错 成员口互相备份 一条断了剩下的继续跑

服务器接入这条要提醒一句：主机侧的绑定（bonding/teaming）和交换机侧的聚合组，两边的哈希算法和模式要对得上，对不上会出现「链路 up 但丢包」。

容错这条值得展开。聚合实时平衡各个成员口的流量，一旦某个端口出现故障，它会自动把故障端口从聚合组里撤掉，然后把流量重新分配到剩下的成员口上。这是聚合自带的系统容错，不需要额外配什么。级联那条的代价是牺牲端口数——四个口捆成一条，你就少了四个可接终端的口。

老式设备的七个限制 #

下面这些是早期端口汇聚设备的规则，来自安奈特 AT-8224XL 那类产品的手册。新设备已经放开了大部分限制，但理解它们有助于明白聚合为什么会「起不来」。

序号 限制 说明
1 端口数目必须是 2、4 或 8 早期硬件按 2 的幂分组
2 必须来自同一组端口 交换机端口被分成若干组，成员口不能跨组
3 端口必须连续 比如用端口 4、5、6、7 组一个聚合
4 一组端口只产生一个聚合 AT-8224XL 有三组，最多三个聚合；加扩展槽多一个
5 接线顺序要对应 一端最低编号口对另一端最低编号口，依次连
6 参数以最低编号口为准 端口 4、5、6、7 组聚合，端口 4 是主端口，配置扩散到其它口
7 扩展槽是否支持要看模块 取决于模块上的端口数量

第 5 条要说得具体些。接线时最重要的是两头的连接线必须相同。假定你从 OPF-8224E 的端口 12、13、14、15 聚合到另一台 OPF-8288XL 的第一组端口 5、6、7、8，那么 12 必须对 5、13 对 6、14 对 7、15 对 8。顺序错了，流量会从一个口的发送端进到对端的发送端，链路直接不通。

第 6 条也很关键。聚合上的所有端口自动认为具有和最低端口号端口相同的配置，比如 VLAN 成员关系。端口 4 是主端口，它的配置被扩散到 5、6、7。只要端口已经被配成聚合成员，你就不能单独改 5、6、7 的任何参数——改了会和端口 4 的配置打架。

这条规则后来演化成了现代交换机的硬约束：成员口的参数必须一致，配置只能下在逻辑口上。我们在第十章细讲。

逻辑口 #

聚合组对外表现为一个逻辑接口。Cisco 叫 Port-channel，华为叫 Eth-Trunk，Linux 主机上叫 bond 或 team。名字不同，行为一样：上层看到的是一个口，底层是 N 条物理线。

text
       ┌──────── Port-channel 1（逻辑口）────────┐
       │            │            │            │
    Gi0/1        Gi0/2        Gi0/3        Gi0/4
       │            │            │            │
       └────────────┴────────────┴────────────┘
                    四条物理链路

VLAN 配置、Trunk 配置、IP 地址，统统配在逻辑口上。物理成员口只负责搬字节。

带宽不是简单相加 #

四个千兆口聚合成 4G 的逻辑口，总容量确实是 4G，但一条流只能走一个成员口。单条 TCP 连接被哈希到某个口上，最多跑 1G，剩下三个口在旁边闲着。聚合提高的是并发流的聚合吞吐，不是单流带宽。第九章展开。

七、静态聚合与动态协商 #

聚合怎么建立，有两种路子：手工静态配，或者让协议自己谈。

静态聚合 #

两端手工把同样的几个口划进同一个聚合组，不跑任何协商协议。

优点是简单、可控、不依赖协议。缺点是没有健康检查——一端认为聚合里有四个口，另一端只配了三个，这个错误协议不会告诉你，流量会往那个不存在的口上发，丢一半。

静态聚合适合两端都是自己管、配置能保证同步的场景。跨机房、跨运营商、跨团队的场景，别用静态。

有些设备上静态聚合的模式名叫 on 或 mode on。注意这个名字和 Trunk 的 on 模式是两个东西，别混。

PAgP：Cisco 的私有协议 #

端口聚合协议（PAgP）是 Cisco 私有，两个模式：desirable 主动发协商包，auto 被动响应。desirable 配 desirable 能成，desirable 配 auto 能成，auto 配 auto 不成——和 Trunk 的 DTP 模式配对是同一套逻辑。只在全 Cisco 环境里能用。

LACP：标准协议 #

链路聚合控制协议（LACP）来自 IEEE 802.3ad，后来并入 802.1AX。跨厂商环境用它。

两个模式：

active：主动发 LACPDU，主动谈。

passive：被动，收到 LACPDU 才回。

active + active 成，active + passive 成，passive + passive 不成。

三种方式对照 #

维度 静态聚合 PAgP LACP
标准 无协议 Cisco 私有 IEEE 802.3ad / 802.1AX
主动模式 —— desirable active
被动模式 —— auto passive
两端都被动 —— 不成 不成
跨厂商 可以（手工对齐） 不行 可以
成员口故障检测 只看物理层 有 有
错配检测 无 有 有
适用 同团队自管两端 全 Cisco 通用

模式配对矩阵 #

本端 \ 对端 静态 on desirable/active auto/passive
静态 on 起 不起 不起
desirable/active 不起 起 起
auto/passive 不起 起 不起

静态 on 和协商模式混配不起，原因很直白：on 不发协商包，对端在等包，等不到就一直是独立端口。

这条和 Trunk 的 nonegotiate 很像——强制模式只跟强制模式配对。

怎么选 #

两端都是自己的设备、配置能一起下发，用静态聚合，省事。两端有厂商差异，或者链路跨管理边界，用 LACP active + active，让协议去校验。对端是不支持聚合的设备（比如某些老服务器网卡），只能静态，但要接受没有健康检查的代价。

八、LACP 的工作过程 #

LACP 干的事比想象中窄：它只负责告诉对端「我这几个口想跟你组一个聚合」，以及「我们俩谁说了算」。它不检查你的 VLAN 配置对不对，不检查速率双工，也不检查 Trunk 允不允许。

LACPDU 里装了什么 #

LACP 靠 LACPDU 交换信息，这是二层帧，目的 MAC 是 01:80:C2:00:00:02，不经过普通转发流程。

里面几个关键字段：

字段 含义
System Priority 系统优先级，值小的优先
System ID 系统优先级 + 交换机 MAC
Port Priority 端口优先级
Port ID 端口优先级 + 端口号
Actor/Partner 本端信息 / 对端信息
Key 聚合组标识，Key 相同才能进同一组
状态位 主动/被动、同步/不同步、可聚合/不可聚合、超时长短

Key 这个字段容易被忽略。它决定了「哪些口属于同一个聚合组」。两端的 Key 要能对上，端口才会被划进同一组。

四个步骤 #

第一步，两端在成员口上周期性发 LACPDU，里面有本端的 System ID、Port ID、Key。

第二步，收到对端的 LACPDU，比对 Key。Key 一致，说明双方都认为这些口该在一组。

第三步，选主。比 System Priority，小的赢；相同就比 System MAC，小的赢。赢的那端叫 Actor，它的 Port Priority 决定哪些口被选中。

第四步，按端口优先级和端口号排序，选出活动端口（selected），其余的进备用（standby）。

text
SW1 (SysPri 32768, MAC 00:11:22:33:44:01)  ←Actor
SW2 (SysPri 32768, MAC 00:11:22:33:44:02)  ←Partner
比 MAC：SW1 小，SW1 说了算
SW1 按 Port Priority 排序，选前 N 个口为 selected

selected 与 standby #

一个聚合组最多能同时转发几个成员口，由设备能力决定。超出的口进入 standby 状态——物理上 up，但不转发流量，等着顶上。

这个设计有意义：四个口捆一组，硬件只支持两个口同时转发，那另外两个就是热备。活动的断了，备用的立刻顶上去。

查聚合状态时看到某个口是 standby，不是故障，是设计如此。

超时 #

LACPDU 的发送周期有两种。短超时：每 1 秒发一次，3 秒收不到就认为对端没了。长超时：每 30 秒发一次，90 秒收不到才认为对端没了。要快速切换就用短超时，代价是对端得扛住每秒一个包的协商流量。

LACP 不检查什么 #

这点必须说清，它决定了「聚合起来了但流量不通」这类问题的排查方向。

LACP 不检查成员口的速率是否一致、双工是否一致、VLAN 配置是否一致、Trunk 允许列表是否一致。

这些参数不一致时，LACP 照样能把聚合谈起来，但转发会出问题：慢的口变瓶颈，VLAN 不一致的口丢帧，双工不匹配的口大量冲突。

所以「LACP 起来了」不等于「聚合配对了」。状态检查和配置检查是两件事。

九、聚合的负载均衡 #

聚合组收到一个帧，要从 N 个成员口里选一个发出去。怎么选，就是负载均衡算法。

这里有个误解要先破：它不是轮询，不是平均分，不是「这帧走口 1、下一帧走口 2」。

它算的是哈希 #

交换机把帧的某些字段提出来，算一个哈希值，再对成员口数量取模，得到出口编号。

text
hash(源MAC, 目的MAC, 源IP, 目的IP, 源端口, 目的端口, ...) % 成员口数 = 出口编号

参与哈希的字段由配置决定，不同设备支持的组合不同。粗的只用 MAC，细的能带到端口号。

依据 粒度 特点
源 MAC 最粗 同一台主机的所有流量走同一个口
目的 MAC 最粗 去同一台主机的流量走同一个口
源 + 目的 MAC 粗 一对主机之间固定一个口
源 IP 中 同一台主机的所有连接走同一个口
目的 IP 中 去同一个目的的所有连接走同一个口
源 + 目的 IP 中 一对 IP 之间固定一个口
源 + 目的 IP + 端口 细 每条连接各自哈希，分布最均匀

粒度越细，分布越均匀，设备开销越大。选哪个看你的流量形态。

同一条流永远同一个口 #

这是哈希和轮询的根本差别。

一个 TCP 连接，五元组（源 IP、目的 IP、源端口、目的端口、协议）在整个连接生命周期里不变。哈希算出来是几，就一直走那个口。这叫「逐流负载均衡」。

为什么要这么设计？因为乱序。

如果同一条流的前一个包走口 1、后一个包走口 2，两条物理链路的延迟不一样，包到对端就乱序了。TCP 收到乱序包要重排，重排不了就当丢包重传，吞吐直接崩。

哈希把一条流钉死在一个口上，就是为了保住顺序。

单流跑不满总带宽 #

推论很直接：一条流只能用一个成员口，那它的上限就是单个成员口的带宽。

四个千兆口聚合成 4G 的逻辑口，你用单线程 scp 传一个大文件，速度上限还是 1G。剩下的 3G 在旁边看。

text
四个成员口，单条流：
  Gi0/1  ██████████████ 1G  ← 这条流全在这
  Gi0/2  ░░░░░░░░░░░░░░  0
  Gi0/3  ░░░░░░░░░░░░░░  0
  Gi0/4  ░░░░░░░░░░░░░░  0

四条流并行：
  Gi0/1  ████████████ 1G
  Gi0/2  ████████████ 1G
  Gi0/3  ████████████ 1G
  Gi0/4  ████████████ 1G

所以聚合的收益要用并发流来体现。备份服务器配八个并发任务，或者用多线程传输工具，才能把四个口喂饱。单线程传大文件，聚合等于没配。

这条认知差造成的现场事故不少：配了四口聚合，测试用单线程 iperf，测出 1G，然后怀疑聚合没配好，回头折腾一整天。

分布不一定均匀 #

哈希的均匀性依赖字段的随机性。

如果参与哈希的字段是源 MAC，而链路对面只有一台服务器，那么所有流量都是同一个源 MAC，哈希值固定，全部挤到一个口上。聚合配了四个口，实际只用了一个。

这种场景要换成基于 IP 加端口的哈希，让不同的连接散开。

反过来，如果流量天然只有一对 IP（比如两个存储设备之间），换成什么哈希都没用，它就只有一条流。这种场景聚合解决不了问题，得上更快的单链路。

两端的哈希不要求一致 #

交换机各自决定从哪个成员口发出，两端算法不同不会导致链路不通。差异大的时候，两个方向的分布会不一样，出现「发出去均衡、收回来挤一个口」。这不算故障，是流量形态决定的。

怎么验 #

配完聚合，先确认成员口全部 selected，再用并发流打流量，看各成员口的计数增长是否接近。

text
show interface <port> counters    # 逐个成员口看收发字节数

只用一个线程测，测出的是单口带宽；用八到十六个并发线程，测出的才是聚合带宽。测试工具和参数要对，不然测出来的数字没参考价值。

十、聚合的故障排查 #

聚合的失败原因高度集中，八成是成员口参数不一致。

一致性清单 #

成员口之间，下面这些必须一模一样。不是「差不多」，是逐项相同。

项目 说明 不一致的后果
速率 全千兆或全百兆，不能混 慢口成瓶颈，或直接不加入
双工 全双工，不能一端半双工 冲突、丢包、CRC 错误
端口类型 电口/光口，模块型号 部分口无法加入
VLAN 配置 成员口的 VLAN 归属 加入后丢帧
Trunk 模式 都 Access 或都 Trunk 加入后不通
Trunk 允许列表 两端、各成员口 部分 VLAN 断
Native VLAN 两端一致 无标签流量串 VLAN
MTU 一致 大包被丢
STP 参数 成员口不能各自跑独立的 STP 实例 生成树反复收敛
端口数量 两端一致 单边多出的口不转发

状态读法 #

聚合起来之后，成员口的状态有几种：

状态 含义 要不要处理
selected / 活动 正常转发 不用
standby / 备用 热备，不转发 不用，设计如此
suspended / 挂起 参数不一致或协商失败，被踢出 要
独立 / individual 没进聚合，当普通口跑 要
down 物理层没起来 要

suspended 是最常见的一个。它表示这个口物理上 up，但因为某项参数和组内其它口不一致，被聚合逻辑排除了。

排查顺序 #

第一步，看两端的成员口数量是否一致。一端四个一端三个，多出来的那个口要么独立跑（容易成环），要么被挂起。

第二步，逐项比对一致性清单。速率、双工最常出错——一端手工写死 1000M 全双工，另一端自适应协商成了别的，看着都是 up，实际参数不匹配。

第三步，看是不是端口本身就有限制。有些设备的某些端口不支持聚合，或者只能和特定端口组合。老设备的「必须同组、必须连续」就是这类限制。

第四步，看 STP。成员口各自参与生成树，会互相阻塞，聚合永远起不来。正确做法是让聚合逻辑口参与 STP，成员口不单独参与。

第五步，看协商模式。两端都是 passive，或者一端静态 on 一端 active，聚合谈不起来。回去查第八章那张配对矩阵。

一个典型现场 #

四个口配聚合，三个 selected，一个 suspended。

查那个口的速率配置——另外三个是自适应协商到 1000M 全双工，这一个是手工写死的 100M。改回一致，立刻 selected。

这类问题的特征是「物理 up、聚合 partially up、吞吐只有预期的四分之三」。看到吞吐不是整数比例，先怀疑有成员口没进组。

聚合口不通但成员口都正常 #

这种时候问题往往不在聚合，在逻辑口的上层配置。VLAN 划在逻辑口上了吗？Trunk 是配在逻辑口上还是成员口上？IP 地址配在哪？

正确做法是：所有配置下在逻辑口，成员口保持默认。成员口上残留的旧配置（比如之前当 Access 口时配的 VLAN）会覆盖或者冲突。

十一、Trunk 与聚合的组合 #

两个技术能叠：一条聚合链路同时当 Trunk 用，承载多个 VLAN 且带宽翻倍。这是交换机之间的标准骨干做法。

配置顺序 #

先建聚合组，把成员口划进去，等聚合起来（成员口 selected）。然后把 Trunk 配置下在逻辑口上。

text
1. 建聚合组，划入成员口        → 成员口 selected
2. 在逻辑口上配 Trunk 模式
3. 在逻辑口上设 Native VLAN
4. 在逻辑口上设允许 VLAN 列表
5. 两端核对：封装、Native VLAN、允许列表

顺序不能反。先在成员口上配 Trunk 再划进聚合组，多数设备会拒绝把已配 Trunk 的口加进聚合，或者加进去后配置被清掉。

配置只下在逻辑口 #

这是组合场景的头号原则。

成员口上不要配 switchport mode trunk，不要设 Native VLAN，不要加允许列表。全部下在逻辑口（Port-channel / Eth-Trunk）上。

text
逻辑口（唯一配置点）：
  switchport mode trunk
  switchport trunk native vlan 999
  switchport trunk allowed vlan 10,20,30

成员口（保持默认）：
  channel-group 1 mode active
  ← 其它 switchport 命令一概不配

有些设备在成员口上配了东西会报错，有些默默接受但行为诡异。统一的做法是：成员口只配「加入哪个聚合组」这一条。

组合场景的对称性检查 #

聚合要求成员口参数一致，Trunk 要求两端对称。两条要求叠起来，检查项变多了。

检查项 在哪一层 两端都要看
聚合模式（静态/LACP） 逻辑口 是
成员口数量 逻辑口 是
成员口速率双工 物理口 是
是否 Trunk 逻辑口 是
封装标准 逻辑口 是
Native VLAN 逻辑口 是
允许 VLAN 列表 逻辑口 是
成员口无残留配置 物理口 是

表格里任何一项不对称，症状都是「链路 up，流量不通或部分不通」。Trunk 的排错和聚合的排错要一起做，不能分开做。

排错时先看哪一层 #

链路不通，先分层定位。

成员口有 selected 的吗？没有，问题在聚合层，去查一致性清单。

有 selected 的成员口，但逻辑口状态不是 up？问题在逻辑口配置。

逻辑口 up、Trunk 起来了，但不通？问题在 Trunk 层，去查封装、Native VLAN、允许列表。

text
物理层 up?
  └─ 是 → 成员口 selected?
           └─ 是 → 逻辑口 up?
                    └─ 是 → Trunk 起来了吗?
                             └─ 是 → 允许列表包含目标 VLAN?
                                      └─ 是 → 查 STP / 上层

一层一层往下卡，比对着全局配置猜要快得多。

十二、易错点速查 #

把前面散落的关键点收成一张表，配完对一遍。

编号 易错点 正确做法
1 一端 Trunk 一端 Access 两端都配 Trunk，成对配置
2 两端封装标准不同 统一 802.1Q
3 两端 Native VLAN 不同 两端设成同一个不用的 VLAN 号
4 Native VLAN 留默认的 VLAN 1 改掉，避免双重标签跳变
5 允许列表两端不一致 两端做差集核对
6 两端都 auto，Trunk 起不来 至少一端 on 或 desirable
7 nonegotiate 配 auto 强制模式只跟强制模式配对
8 两端都不在同一 VTP 域还指望自动协商 用 on/nonegotiate 强制
9 把 Trunk 当聚合用 两个概念分开：多 VLAN 走一线 vs 多线合一
10 成员口速率双工不一致 逐项对齐，别一头自适应一头写死
11 成员口数量两端不同 两端数量一致
12 成员口上残留旧配置 配置只下在逻辑口
13 先配 Trunk 再加聚合组 先建组，再在逻辑口上配 Trunk
14 两端都 passive，LACP 不起来 至少一端 active
15 静态 on 配 active 强制配强制，协商配协商
16 以为聚合能提速单条流 单流上限等于单成员口带宽
17 哈希字段选错，流量挤一个口 按流量形态选粒度，多用 IP + 端口
18 把 standby 当故障 备用口不转发是设计如此
19 看到 suspended 不查参数一致性 挂起就是参数不一致的信号
20 成员口各自参与 STP 让逻辑口参与，成员口不单独参与

再补一条不在表里但经常被忽略的：文档。

聚合组和 Trunk 的配置是成对的，一端改了另一端不改就断。改之前把两端配置都导出来存档，改完对比差异。比事后抓包猜要省时间。

到这里，交换机之间的那条线就配完了。一根线跑多个 VLAN，靠的是逐帧的 802.1Q 标签，两端对称是前提，Native VLAN 是那个不起眼但会咬人的参数。多根线合成一条，靠的是聚合组，成员口参数一致是入组门槛，哈希决定流量怎么摊开。两个技术叠在一起，就是骨干链路的常规做法。
