本篇只讲一件事：交换机、路由器上的 ACL，怎么用规则控制「谁能过、谁不能过」。

讲什么：ACL 的组成、作用位置、标准与扩展的区别、编号与命名、通配符掩码、匹配顺序与隐式拒绝、inbound/outbound 方向、配置步骤、与 NAT 和策略路由的配合、排错方法，以及与 iptables 的对照。

不讲什么：Linux 主机上的软件防火墙（netfilter 的链、表、NAT 细节）在《iptables 规则与 NAT 配置》里；主机自己的网卡、路由、DNS 配置在《Linux 主机的网络配置》里；端口速率、VLAN、链路聚合在《交换机端口配置》里。

命令示例统一用华为 VRP 风格（acl number / rule / traffic-filter）。别的厂商在编号范围、关键字、匹配选项上都不一样，落配置时以所用设备的命令手册为准。

一、ACL 是什么 #

ACL，Access Control List，访问控制列表。一句话说完：一张按顺序排好的规则表，每条规则描述「什么样的报文」，命中之后给出「permit 还是 deny」。

素材里的比喻很准。ACL 是报文过滤器，ACL 规则就是过滤器的滤芯。装什么样的滤芯，就滤出什么样的报文。

一条规则由三块拼起来。

组成 干什么 素材里的例子
规则编号 决定这条规则在表里排第几 5、10、15、4294967294
动作 命中之后怎么办 deny / permit
匹配选项 报文长什么样才算命中 源地址、目的地址、协议、端口、时间段

拼起来，一条 ACL 长这样：

text
acl number 2000
 rule 5   deny   source 1.1.1.1 0
 rule 10  deny   source 1.1.1.2 0
 rule 15  permit source 1.1.1.0 0.0.0.255

左边编号，中间动作，右边匹配条件。就这么朴素。

ACL 能拿来干什么，素材给了三件事：

  • 阻塞攻击报文。把已知的坏源、坏端口挡在门外。
  • 为不同类报文流提供差分服务。ACL 先把流量分类出来，QoS 再给不同待遇。
  • 控制 Telnet 登录、FTP 文件下载。谁能登设备、谁能拉文件，规则说了算。

再加一条实战里最常干的：决定哪些流量走 NAT、哪些流量走策略路由。这条留到第九章。

有个认知要一开始就立住：ACL 本身不转发报文，也不产生路由。它只是一张判断表，必须被某个地方引用才起作用。引用它的地方分两大类——接口上的过滤，和业务模块（NAT、策略路由、QoS、登录控制）的调用。

二、ACL 的作用位置 #

同一个 ACL，挂在不同地方，效果完全不同。位置分两类。

第一类是接口过滤。ACL 挂在某个物理口、子接口或者 VLAN 接口上，再加上方向（in 或 out）。报文经过这个口、朝这个方向走，就进这张表里比对一次。

text
interface GigabitEthernet0/0/1
 traffic-filter inbound acl 2000

第二类是被业务模块调用。ACL 不挂在接口上，而是作为参数传给别的功能，让那个功能按 ACL 的分类结果做事。这时候 ACL 只负责「挑出流量」，动手的是调用它的模块。

引用位置 ACL 的角色 命中 permit 的含义
接口 traffic-filter 过滤器 放行
NAT（nat outbound） 地址转换的选流条件 这条流要做 NAT
策略路由（PBR） 改下一跳的选流条件 这条流按策略转发
QoS 流分类 流量分类器 归入这个类，按类限速或标记
路由策略（filter-policy） 路由收发的过滤条件 这条路由被接收或发布
用户界面（VTY） 管理面登录控制 允许登录

这张表要背下来，因为它直接决定排错方向。接口过滤里 permit 是「放行」；NAT 里 permit 是「这条流要转换」。同一个 permit，两种意思。很多人把 NAT 用的 ACL 写成「deny 掉不想转换的」，结果一条都不转换，就是踩了这个语义差。

还有一处容易漏：设备自身产生的流量、发给设备自身的流量（比如你 telnet 上去），不走接口上的 traffic-filter。管登录要在用户界面下配：

text
user-interface vty 0 4
 acl 2000 inbound

所以一条 ACL 写完了不通，先问自己三个问题：挂在哪了？什么方向？这个位置 permit 是什么语义？

三、标准 ACL 与扩展 ACL #

按规则能看多深，ACL 分成两大类。华为的叫法是基本 ACL 和高级 ACL，Cisco 的叫法是标准 ACL 和扩展 ACL，指的是同一件事。

标准 ACL（基本 ACL）只看源 IP。加一点辅助条件，比如分片标记、生效时间段。它不看目的地址，不看协议，不看端口。

text
acl number 2000
 rule 5 deny   source 1.1.1.1 0
 rule 15 permit source 1.1.1.0 0.0.0.255

扩展 ACL（高级 ACL）能看的字段多得多。素材列了一串：源 IP 地址、目的地址、IP 优先级、ToS、DSCP、IP 协议类型、ICMP 类型、TCP 源端口/目的端口、UDP 源端口/目的端口号。

text
acl number 3000
 rule 5 permit tcp source 1.1.1.0 0.0.0.255 destination 2.2.2.2 0 destination-port eq 80
 rule 10 deny   ip source 1.1.1.0 0.0.0.255 destination 2.2.2.2 0

高级 ACL 可以定义比基本 ACL 更准确、更丰富、更灵活的规则，规则表达能力更强。

两者的差别摆在一起看：

对比项 标准 ACL（基本） 扩展 ACL（高级）
能看的层次 三层，源地址为主 三层加四层，源/目的/协议/端口
关键字段 源 IP、分片标记、时间段 源 IP、目的 IP、协议号、ICMP 类型、TCP/UDP 端口、IP 优先级、ToS、DSCP
规则粒度 粗，按人（源）拦 细，按事（源到目的的某种服务）拦
规则长度 短 长，参数多
设备转发开销 低 高一些，要看四层头
典型用途 限制某段地址访问管理面 精确放行某个服务的某个端口
放哪儿合适 靠近目的端 靠近源端
编号范围 2000～2999 3000～3999

选型只有一句话：能用标准 ACL 说清的需求，别上扩展 ACL。标准 ACL 只看源，所以它天然放不住「同一台主机可以访问 A 服务、不能访问 B 服务」这种需求，那是扩展 ACL 的活。

反过来，如果你要拦的是「整个 10.1.1.0/24 不许进来」，标准 ACL 就够，而且设备匹配起来更快。

四、ACL 的编号与命名 #

ACL 有两种写法：数字型和命名型。

数字型靠一个编号标识自己，编号像身份证号，唯一区分这张表。命名型除了编号，还能带一个名字，用名字代替编号来定义 ACL。就像用域名代替 IP 地址一样，方便记忆，也让人一眼看出这张表的用途。

素材给了一个例子：既有名字 deny-telnet-login，又有编号 3998。命名型 ACL 实际上是「名字 + 数字」的形式，定义时可以把编号一起写上；不写编号，由系统自动分配。

text
acl name deny-telnet-login 3998
 rule 5 deny source 1.1.1.1 0

text
acl name deny-telnet-login
 rule 5 deny source 1.1.1.1 0

两种写法都能建表，差别是第二种的编号由系统分配，你下次登录未必记得住，所以运维里优先手动指定。

再看编号本身。按规则功能的不同，ACL 被划分为基本 ACL、高级 ACL、二层 ACL、用户自定义 ACL、用户 ACL 这五类，每类对应的编号范围不一样。这张表是素材的核心内容，原样保留：

ACL 类别 规则定义描述 编号范围
基本 ACL 仅使用报文的源 IP 地址、分片标记和时间段信息来定义规则 2000～2999
高级 ACL 既可使用报文的源 IP 地址，也可使用目的地址、IP 优先级、ToS、DSCP、IP 协议类型、ICMP 类型、TCP 源端口/目的端口、UDP 源端口/目的端口号等来定义规则 3000～3999
二层 ACL 可根据报文的以太网帧头信息来定义规则，如根据源 MAC 地址、目的 MAC 地址、以太帧协议类型等 4000～4999
用户自定义 ACL 可根据报文偏移位置和偏移量来定义规则 5000～5999
用户 ACL 既可使用 IPv4 报文的源 IP 地址或源 UCL（User Control List）组，也可使用目的地址或目的 UCL 组、IP 协议类型、ICMP 类型、TCP 源端口/目的端口、UDP 源端口/目的端口号等来定义规则 6000～9999

ACL 2000 属于基本 ACL，ACL 3998 属于高级 ACL。同一个编号 3998 落在 3000～3999 区间里，所以它是高级 ACL——编号就决定了类型，这一点没有例外。

Cisco 设备是另一套编号习惯，对照着看：

编号范围 类型（Cisco 习惯）
1～99 标准 ACL
100～199 扩展 ACL
1300～1999 扩展 ACL（IP 扩展）
2000～2699 扩展 ACL（大编号区间）

两套编号体系不能混着背。华为记 2000/3000/4000/5000/6000 这一段一段的区间，Cisco 记 1～99 和 100～199 这两个小区间。落配置前先确认你手上是哪家的设备。

规则本身也有编号。素材说得很清楚：ACL 规则的编号范围是 0～4294967294，所有规则均按照规则编号从小到大进行排序。所以 rule 5 排在首位，规则编号最大的 rule 4294967294 排在末位。系统按编号从小到大的顺序，把规则依次与报文匹配，一旦匹配上一条规则即停止匹配。

接下来是步长，它是理解规则编号为什么跳着走的关键。

步长是系统自动为 ACL 规则分配编号时，相邻规则编号之间的差值。ACL 2000 的步长是 5，系统就按 5、10、15 这样的规律分配编号。把步长改成 2，规则编号会自动从步长值开始重排，变成 2、4、6。

ACL 的缺省步长值是 5。用 display acl acl-number 可以查看 ACL 规则、步长等配置信息，用 step step 命令可以修改步长值。

bash
display acl 2000

设置步长的目的只有一个：方便在已有规则之间插入新规则。素材的例子值得完整走一遍。

假设一条 ACL 里已经有下面三条规则：

text
rule 5  deny   source 1.1.1.1 0            // 表示禁止源 IP 地址为 1.1.1.1 的报文通过
rule 10 deny   source 1.1.1.2 0            // 表示禁止源 IP 地址为 1.1.1.2 的报文通过
rule 15 permit source 1.1.1.0 0.0.0.255    // 表示允许源 IP 地址为 1.1.1.0 网段的报文通过

现在要让源 IP 为 1.1.1.3 的报文也被禁止通过。分析一下：ACL 匹配报文时遵循「一旦命中即停止匹配」的原则，所以 1.1.1.1 和 1.1.1.2 的报文会在匹配上编号较小的 rule 5 和 rule 10 后停止匹配，被禁止通过；1.1.1.3 的报文只会命中 rule 15，得到允许通过。要想让 1.1.1.3 也被禁止，必须为它加一条新的 deny 规则。

text
rule 5  deny   source 1.1.1.1 0            // 表示禁止源 IP 地址为 1.1.1.1 的报文通过
rule 10 deny   source 1.1.1.2 0            // 表示禁止源 IP 地址为 1.1.1.2 的报文通过
rule 11 deny   source 1.1.1.3 0            // 表示禁止源 IP 地址为 1.1.1.3 的报文通过
rule 15 permit source 1.1.1.0 0.0.0.255    // 表示允许源 IP 地址为 1.1.1.0 网段的报文通过

在 rule 10 和 rule 15 之间插入 rule 11 后，1.1.1.3 的报文会先命中 rule 11 而停止往下匹配，于是被禁止通过。

试想一下，如果规则之间间隔不是 5 而是 1（rule 1、rule 2、rule 3…），这时再想插入新规则，只能先删除已有规则，再配新规则，最后把删掉的规则重新配回去。代价很大。

所以步长的价值在于：为规则之间留出空间，后续插入新规则就很轻松。

text
acl number 2000
 rule 5  deny source 1.1.1.1 0
 rule 10 deny source 1.1.1.2 0
 step 2

改成步长 2 之后，编号重排成 2、4、6，中间只留一个空位，插入空间变窄了。步长不是越大越好，5 到 10 是比较常见的取值。

五、通配符掩码 #

ACL 里写地址，后面总跟着一串奇怪的数字：0.0.0.255、0、0.0.0.0。这就是通配符掩码，也叫反掩码。

它的规则只有两条：

  • 0 表示「这一位必须匹配」。
  • 1 表示「这一位忽略」。

它和子网掩码的每一位含义正好相反。子网掩码里 1 是网络位、0 是主机位；反掩码里 0 是要匹配的位、1 是不管的位。这是最常见的理解错误：把子网掩码直接填进反掩码的位置，规则看起来写了，实际匹配范围完全不对。

换算公式很干脆：

text
反掩码 = 255.255.255.255 - 子网掩码

举个最常见的例子。要匹配 1.1.1.0/24 这个网段，子网掩码是 255.255.255.0，反掩码就是 255.255.255.255 - 255.255.255.0 = 0.0.0.255。

text
rule 15 permit source 1.1.1.0 0.0.0.255

这条规则的意思是：前 24 位（1.1.1）必须一致，最后 8 位随便。所以 1.1.1.1 到 1.1.1.254 全部命中。

再看单个地址：

text
rule 5 deny source 1.1.1.1 0

0 等价于 0.0.0.0，每一位都必须匹配，所以它精确匹配 1.1.1.1 这一台主机。

常用长度的对照表，可以直接抄：

前缀长度 子网掩码 通配符掩码（反掩码） 说明
/32 255.255.255.255 0.0.0.0 单个地址
/31 255.255.255.254 0.0.0.1 两个地址
/30 255.255.255.252 0.0.0.3 四个地址
/29 255.255.255.248 0.0.0.7 八个地址
/28 255.255.255.240 0.0.0.15 十六个地址
/27 255.255.255.224 0.0.0.31 —
/26 255.255.255.192 0.0.0.63 —
/25 255.255.255.128 0.0.0.127 半个 C
/24 255.255.255.0 0.0.0.255 一个 C 类网段
/16 255.255.0.0 0.0.255.255 一个 B 类网段
/8 255.0.0.0 0.255.255.255 一个 A 类网段
/0 0.0.0.0 255.255.255.255 任意地址

看这张表的诀窍：掩码越长，反掩码越短。/24 的通配符是 0.0.0.255，/8 的通配符是 0.255.255.255。

几个特殊写法要认识：

text
rule 20 permit source any

any 等价于 0.0.0.0 255.255.255.255，匹配所有地址。设备上 any 是关键字，不用展开。

text
rule 25 deny source 1.1.1.1 0

0 这种单值写法，有的设备支持 host 1.1.1.1 关键字，两者等价。以所用设备命令为准。

反掩码还能不连续，这是它比子网掩码更灵活的地方。比如要匹配一个 /24 里所有偶数地址：

text
rule 30 permit source 1.1.1.0 0.0.0.254

0.0.0.254 的最后一个二进制位是 0，其余是 1，所以只有最低位被忽略——偶数地址命中，奇数地址不命中。连续掩码做不到这件事。

排错时怎么一眼看出写错了？把反掩码和子网掩码摆一起比：

你想要的 正确的反掩码 初学者常误填 后果
1.1.1.0/24 0.0.0.255 255.255.255.0 匹配范围错乱，规则形同虚设或误杀
1.1.0.0/16 0.0.255.255 255.255.0.0 同上
单个主机 1.1.1.1 0.0.0.0 255.255.255.255 变成匹配所有地址，等于放行全网

最后一行是最危险的：把单主机的反掩码写成 255.255.255.255，一条 deny 就变成了 deny 所有。

六、匹配顺序与隐式拒绝 #

这是全篇最需要记住的一节。

ACL 匹配只有一条规则：从上到下逐条比对，命中即执行，都不命中就走隐式拒绝。

拆成四步看：

步骤 做什么
1 按规则编号从小到大，取第一条规则
2 用这条规则的匹配选项和报文比对
3 命中就执行动作（permit 或 deny），然后立刻停止，后面的规则不再看
4 没命中就取下一条，回到第 2 步

四步走完还没命中，会落到一条你没写过、也看不见的规则上：隐式 deny any。

这条隐式规则的意思是：所有规则都没匹配上的报文，一律丢弃。

它是最容易忘的坑。你写了一条 permit 1.1.1.0/24，测试却不通，第一反应是规则写错了、方向配反了。但很多时候规则本身没问题，是它前面有一条更宽的 deny，流量根本没走到你那条 permit。

举个具体的：

text
rule 5  deny   source 1.1.0.0 0.0.255.255
rule 10 permit source 1.1.1.1 0

你想放行 1.1.1.1，但它落在 1.1.0.0/16 里，rule 5 先命中，直接丢掉。rule 10 永远轮不到。

正确的顺序是窄规则在前、宽规则在后：

text
rule 5  permit source 1.1.1.1 0
rule 10 deny   source 1.1.0.0 0.0.255.255

调个位置，行为就对了。这就是「顺序决定结果」。

再看隐式拒绝的另一面。很多人在末尾写一条兜底：

text
rule 1000 permit ip

这条规则的目的不是放行攻击流量，而是把那条看不见的隐式拒绝盖住，让「都不命中」变成「都放行」。编号取 1000 是为了给中间的规则留足插入空间，跟步长是一个思路。

text
acl number 3000
 rule 5  permit tcp source 10.1.1.0 0.0.0.255 destination 2.2.2.2 0 destination-port eq 80
 rule 10 deny   ip source 10.1.1.0 0.0.0.255 destination 2.2.2.2 0
 rule 20 permit ip

这三条读起来是：允许 10.1.1.0/24 访问 2.2.2.2 的 80 端口；其余去 2.2.2.2 的全拒；其他流量全放行。去掉 rule 20，等于把整个网段除了这条 80 之外的去路全断了——因为隐式 deny 接管了所有剩余报文。

所以写 ACL 的固定动作是：写完先从头读一遍，问一句「剩下的报文去哪了」。

七、方向：inbound 与 outbound #

ACL 挂在接口上时必须指定方向：in 或 out。这个方向是站在设备自己的视角说的，不是站在主机视角说的。这是第二个高频错误。

方向 含义 检查时机（设备视角）
inbound / in 报文从接口进入设备 报文刚到本接口，还没查路由
outbound / out 报文从接口离开设备 报文已查完路由，准备从这个口发出去

一句话记法：in 是进门，out 是出门，门是设备自己的门。

换个角度对照一下同一个流量：

谁在看 in 指的是 out 指的是
设备 A（转发设备） 从 A 的某接口收到报文 从 A 的某接口发出报文
主机 X（终端） 从 X 的网卡收到报文 从 X 的网卡发出报文

所以「允许 1.1.1.0/24 进入 G0/0/1」写成：

text
interface GigabitEthernet0/0/1
 traffic-filter inbound acl 2000

而「允许 1.1.1.0/24 从 G0/0/2 出去」写成：

text
interface GigabitEthernet0/0/2
 traffic-filter outbound acl 2000

同一张 ACL 2000，挂 in 和挂 out，拦的是两个完全不同的方向。挂反了的表现是：该拦的没拦，该通的也不通。

一个接口可以同时挂 in 和 out 两张 ACL，各管一边；同一个接口同一个方向，只能挂一张，后配的会覆盖先配的。

关于把 ACL 放在哪个接口、哪个方向，有一条通用的经验原则：

ACL 类型 放在靠近 理由
标准 ACL 目的端 它只看源地址，放源端会连不该拦的流量一起拦掉
扩展 ACL 源端 能精确描述五元组，越早丢越省带宽和转发资源

第一条的理由要说透。标准 ACL 只会说「禁止源 1.1.1.1」，如果把它挂在源端的出口，那这台主机去任何地方的流量都被拦了，包括它该去的服务器。挂在目的端，它只影响这批流量通往这一个方向的路径。

还有一处边界：接口上的 traffic-filter 管的是穿过设备的转发流量。设备自己发起的流量、目的地是设备自己的流量（telnet、ssh、snmp、ping 设备地址），不走这里。要限制登录设备，得在用户界面下用 acl acl-number inbound。这两套配置互不替代，别指望挂个接口 ACL 就能挡住别人登设备。

八、ACL 的配置 #

配 ACL 就四步，顺序不能乱。

步骤 做什么 关键决策
1 定义 ACL 选类型（基本/高级/二层…），定编号或名字
2 配规则 每条的编号、动作（permit/deny）、匹配选项
3 引用 挂接口带方向，或交给 NAT、策略路由、VTY 调用
4 验证 display acl，再实测连通性

第 3 步最容易被跳过。表建好了、规则也写对了，但没引用，等于没配。设备不会提醒你。

先走一遍最小可用的完整流程。需求：禁止 1.1.1.1 和 1.1.1.2 进入 G0/0/1，放行 1.1.1.0/24 的其他地址。

第一步，建表并写规则：

text
system-view
acl number 2000
 rule 5  deny   source 1.1.1.1 0
 rule 10 deny   source 1.1.1.2 0
 rule 15 permit source 1.1.1.0 0.0.0.255

第二步，挂到接口：

text
interface GigabitEthernet0/0/1
 traffic-filter inbound acl 2000

第三步，验证：

bash
display acl 2000
display traffic-filter inbound interface GigabitEthernet0/0/1

display acl 会列出规则和步长，display traffic-filter 会告诉你哪个口挂了哪张表。这两个命令是排错时最先敲的。

几个带编号的实操细节：

  • 删一条规则用 undo rule 11，命令里只写编号，不用把整条规则重打一遍。
  • 改一条规则的匹配条件，先 undo 再重配，不要指望原地改。
  • 步长用 step 10 调整，改完编号会重排，之前的引用关系按编号走，引用本身不受影响。
  • 想清空整张表，先把它从接口上摘掉，再删 ACL，顺序反了会留下悬空引用。

再看一个高级 ACL 的实际写法。需求：只允许 10.1.1.0/24 访问 2.2.2.2 的 80 和 443，其余到 2.2.2.2 的全拒，其他流量不动。

text
acl number 3000
 rule 5  permit tcp source 10.1.1.0 0.0.0.255 destination 2.2.2.2 0 destination-port eq 80
 rule 10 permit tcp source 10.1.1.0 0.0.0.255 destination 2.2.2.2 0 destination-port eq 443
 rule 15 deny   ip source any destination 2.2.2.2 0
 rule 20 permit ip

四条规则读下来就是一句话：先放行两个端口，再拒掉剩下的，最后兜底放行其他一切。rule 20 不能省，省了以后凡是没被前三条命中的流量，全被隐式拒绝吃掉。

管理面限制登录，是另一个高频需求。只允许 10.1.1.0/24 telnet 上来：

text
acl number 2001
 rule 5 permit source 10.1.1.0 0.0.0.255

user-interface vty 0 4
 acl 2001 inbound
 authentication-mode password

这里有个坑：一旦挂上去，不在 10.1.1.0/24 的人立刻被挡在外面。配置前先确认自己的管理地址在 permit 范围里，或者手上还有带外通道。

用时间段限制访问，规则里可以挂一个时间段：

text
time-range work-time 08:30 to 18:00 working-day
acl number 3000
 rule 5 deny tcp destination-port eq 80 time-range work-time

不同版本、不同厂商的时间段关键字和写法差别很大，以所用设备命令为准。时间段是 ACL 的匹配选项之一，素材在基本 ACL 的定义里已经点明过这个字段。

Cisco 的写法是另一套，对照着认个脸：

text
access-list 10 permit 1.1.1.0 0.0.0.255
interface GigabitEthernet0/1
 ip access-group 10 in

编号落在 10，就是标准 ACL；挂在接口用 ip access-group，方向关键字是 in/out。两家的命令长得不像，但三件事完全一样：规则列表、动作、挂载点加方向。学会一套，另一套看手册就能上手。

九、ACL 与 NAT、策略路由的配合 #

ACL 在设备上很少单独存在，它常被别的功能当「选流器」用。这一章说的是最容易出事的配合。

先看 NAT。把内网 10.1.1.0/24 送出去做源地址转换：

text
acl number 2000
 rule 5 permit source 10.1.1.0 0.0.0.255

interface GigabitEthernet0/0/0
 nat outbound 2000

这里 ACL 2000 的作用不是「过滤」，而是「告诉 NAT 哪些流量需要被转换」。permit 的 10.1.1.0/24 就是被选中的那批。

语义差就在这里，必须记死：

场景 permit 的含义 deny 的含义
接口 traffic-filter 放行 丢弃
NAT 选流 这条流做地址转换 这条流不做转换，继续走
策略路由选流 这条流按策略转发 这条流不按策略走，回到正常路由
QoS 流分类 归入此类 不归入此类

在 NAT 和策略路由里，deny 不等于丢包。它只是说「不选中」。所以写「deny 掉不想转换的流量」这种思路是错的——你 deny 了它，它只是不做 NAT，照样往外走，出去的时候源地址是私网地址，在公网上没人认。

正确做法是反过来：只 permit 想转换的那批，剩下的自然不匹配。

策略路由也是同一个套路：

text
acl number 3000
 rule 5 permit ip source 10.1.1.0 0.0.0.255 destination 8.8.8.8 0

traffic behavior pbr1
 redirect ip-nexthop 192.168.1.1

traffic classifier c1 operator or
 if-match acl 3000

traffic policy p1
 classifier c1 behavior pbr1

意思是：源 10.1.1.0/24 去 8.8.8.8 的流量，走 192.168.1.1 这个下一跳，不看路由表。ACL 在这里只负责「挑出来」。

三者叠在一起时，要想清楚先后。同一份流量会同时被三张表各看一遍：接口入方向的过滤 ACL、NAT 的选流 ACL、策略路由的选流 ACL。三个 ACL 是独立的表，各自判断，互不继承。

功能 用的 ACL 判断结果
接口过滤 ACL A 过了才继续，不过就丢
目的 NAT / 策略路由 ACL B 决定怎么转发、怎么改地址
源 NAT（出方向） ACL C 决定出方向是否转换源地址

一个常见故障：接口入方向 ACL 只放行了业务端口，结果回程流量被同一张表拦掉。原因是 ACL 无状态，它不认识「这是刚才那条连接的回包」。回程流量在反方向上走的是另一个接口的另一个方向，得单独放行。

处理办法有两个。一是在回程方向单独配一张放宽的 ACL。二是改用状态化防火墙策略（如果有），让设备自己维护会话表。ACL 本身没有会话概念，这一点别抱幻想。

十、ACL 的排错 #

ACL 的问题九成出在四个地方：顺序、方向、反掩码、隐式拒绝。按这个顺序查，比乱试快得多。

第一步，确认表和规则真的存在：

bash
display acl 2000

看不到规则，说明命令没生效、进错了视图，或者 ACL 编号写错落到别的区间去了。比如想配高级 ACL 却写了 acl number 2000，那条带端口的规则根本没法加进去。

第二步，确认引用关系：

bash
display traffic-filter inbound interface GigabitEthernet0/0/1

没挂上，或者挂到了别的口、别的方向，这是第二大来源。

第三步，从头到尾读一遍规则顺序，重点找「有没有一条更宽的 deny 挡在前面」。

症状 先查什么 怎么确认
该通的流量不通 前面有没有更宽的 deny 逐条读编号，看命中顺序
该拦的流量没拦住 引用是不是挂反了方向 display traffic-filter
部分地址通、部分不通 反掩码算错 用对照表核对掩码
配完立刻全断 命中了隐式拒绝 末尾有没有 permit 兜底
换个端口就不通 扩展 ACL 只放了 ICMP 加对应 TCP/UDP 端口规则
单向通、回程不通 ACL 无状态 反方向单独放行
大包不通、小包通 分片报文没有端口信息 放行分片或调整匹配方式
自己也登不上了 管理面 ACL 把自己挡了 带外通道恢复

几条值得单独说。

「ping 通但业务不通」是最常见的误判。ping 走 ICMP，业务走 TCP。ACL 里 permit 了 icmp，不代表 permit 了 tcp 80。测试要用真实业务端口，别只 ping。

text
acl number 3000
 rule 5 permit icmp source 10.1.1.0 0.0.0.255 destination 2.2.2.2 0
 rule 10 permit tcp source 10.1.1.0 0.0.0.255 destination 2.2.2.2 0 destination-port eq 80

「单向通、回程不通」要理解 ACL 的无状态特性。你在 A 口 in 方向放行了请求，回包从 B 口进、或者从 A 口 out 出去，走的是另一条判断路径。只要那个方向上没有对应 permit，回包就被隐式拒绝丢掉。表现是连接建立不起来，或者 TCP 握手只完成一半。

「分片报文」是扩展 ACL 的隐藏坑。扩展 ACL 要看四层端口，但 IP 分片只有首片带四层头，后续分片没有端口信息。规则按端口匹配时，非首片匹配不上，会被隐式拒绝丢掉，表现是大包不通、小包通。

「改配置把自己关在门外」是运维事故里最经典的一种。改 VTY 上的 ACL 之前，先开一个已经登录的会话别断，或者留一条带外/console 通道，或者干脆先配一个宽一点的 permit 再逐步收紧。

真查不出来的时候，用最笨的办法：在最前面临时加一条针对测试源和测试目的的 permit，看通不通。通了说明是被前面的规则拦的，不通说明问题不在 ACL 这一层，去查路由和接口。

text
acl number 3000
 rule 1 permit ip source 10.1.1.100 0 destination 2.2.2.2 0

rule 1 排在最前，谁也挡不住它。查完记得删。

十一、ACL 与 iptables 的对照 #

这两样东西经常被混着叫「防火墙规则」，实际管的是两个地方。ACL 跑在网络设备上，管转发；iptables 跑在 Linux 主机上，管本机和本机做的网关。

对比项 设备 ACL Linux iptables
跑在哪 交换机、路由器 Linux 主机、Linux 网关
组织结构 一张规则列表 表（filter/nat/mangle）里挂多条链
挂载点 接口 + 方向（in/out） 链（INPUT/FORWARD/OUTPUT/PREROUTING/POSTROUTING）
匹配顺序 编号从上到下，命中即停 链内从上到下，命中即停
未命中时 隐式 deny 由链的默认策略决定（ACCEPT 或 DROP）
状态化 无状态，不看连接 有 conntrack，能识别established/related
地址写法 通配符掩码（反掩码） 掩码或 CIDR 前缀
典型命令 traffic-filter / ip access-group iptables -A FORWARD -j DROP
配置保存 多数设备需显式 save 需要持久化工具或规则文件

最实质的差别是状态化。iptables 里有 -m state --state ESTABLISHED,RELATED -j ACCEPT 这一条，回程流量自动放过；ACL 里没有对应机制，回程必须自己写。这就是为什么同样的需求，在 iptables 上一条规则搞定，在 ACL 上要写两条。

第二个差别是未命中的默认行为。iptables 的链有默认策略，你可以设成 ACCEPT，也可以设成 DROP，它写在链上、看得见。ACL 的隐式拒绝是硬编码的，你改不了它，只能在自己表的末尾补一条 permit 把它盖住。

第三个差别是粒度来源。ACL 靠编号区间区分类型（2000 段是基本、3000 段是高级），iptables 靠表和链区分阶段（PREROUTING 做 DNAT，POSTROUTING 做 SNAT）。

两边相通的地方也不少：都是规则从上往下比、命中即停；都要求你在写规则时想清楚顺序；都会因为漏了兜底规则而出现「配完就全断」。

哪个该用哪个，看你要控的是什么。控「谁能穿过这台设备到哪去」，用 ACL。控「这台 Linux 主机自己能不能被访问、它的转发要不要做 NAT」，用 iptables。两者同时存在于一张网络里是常态，主机防火墙和网络设备 ACL 叠着用，这时候排错要分清是哪一层拦的——从丢包的位置、能 ping 通到哪一跳来判断。

iptables 的链、表、NAT 细节在《iptables 规则与 NAT 配置》里，本篇不重复。

十二、易错点速查 #

把全篇的坑压成一张表，配完 ACL 照着扫一遍。

# 现象 根因 处理
1 配了 permit 还是不通 前面有更宽的 deny 先命中 调整规则顺序，窄规则在前
2 只剩部分流量通 末尾缺兜底规则，隐式 deny 生效 补 rule N permit ip
3 该拦的没拦住 接口方向挂反（in 当 out） 改 traffic-filter 方向关键字
4 规则完全不生效 建了表没引用 挂接口或交给模块调用
5 匹配范围离谱 把子网掩码当反掩码填 用 255.255.255.255 减一遍
6 一条 deny 拦了全网 单主机反掩码写成 255.255.255.255 单主机用 0 或 0.0.0.0
7 NAT 不生效 用 deny 表达「不转换」 只 permit 需要转换的流量
8 回程不通 ACL 无状态，反向没放行 反方向单独配 permit
9 大包不通小包通 分片非首片匹配不上端口 放行分片或不用端口匹配
10 ping 通但业务不通 只放行了 ICMP 同时放行对应 TCP/UDP 端口
11 高级规则加不进去 编号落在基本 ACL 区间 高级 ACL 用 3000～3999
12 改完 ACL 自己登不上 VTY 上的 ACL 挡了自己的地址 保留已登录会话或走 console
13 规则编号跳号看不懂 步长在起作用 step 调整，display acl 查
14 删规则后行为突变 删掉的那条原本在做兜底 删前确认剩余规则覆盖完整

第 13 条补一句：编号 5、10、15 是步长 5 分出来的，不是系统的限制。看到跳号不要以为配错了。

第 14 条是删改时的通用提醒：删一条规则，等于把一条路径上的判断交还给「下一条」或「隐式拒绝」。改之前先把剩余规则在纸上走一遍。

写 ACL 的心法很短：想清楚报文从哪进、往哪出，想清楚剩下的报文该去哪，然后按「窄规则在前、兜底在后」排一遍编号。做到这三件事，八成的坑就绕开了。
