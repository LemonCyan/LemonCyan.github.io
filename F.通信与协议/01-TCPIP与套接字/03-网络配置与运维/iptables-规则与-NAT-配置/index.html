本篇讲什么：用户态怎么写 iptables 规则。表、链、规则三层的语法，匹配条件怎么挑，动作怎么定，SNAT/DNAT 怎么配，规则怎么存下来不丢。

本篇不讲什么：内核里 Netfilter 怎么注册 hook、nf_hook_ops 长什么样、hook 函数返回 NF_ACCEPT/NF_DROP 之后协议栈怎么继续走。这些归 03-协议栈与内核实现/Netfilter 与 hook 点。

一句划界：那篇讲「内核留了哪五个口子、口子上怎么挂处理函数」，本篇讲「你用什么命令往这些口子上塞规则、规则写了为什么生效或为什么不生效」。

同目录另外三篇各管一段：ACL 访问控制列表 讲交换机与路由器上的包过滤，Linux 主机的网络配置 讲 IP、路由、网卡配置，交换机端口配置 讲二层口。四篇平铺，不重叠。

一、iptables 是什么 #

先把「防火墙」拆开 #

防火墙就是 Linux 上实现访问控制的组件，硬件、软件两类都有。它工作的地方永远在网络边缘。你的任务是定义它怎么干活——这就是策略，就是规则，让它对进出网络的 IP 和数据做检测。

按层次分两种：

类型 工作层 检查什么 代价
三层/四层防火墙 网络层、传输层 源 IP、目的 IP、协议、端口 快，看不穿应用内容
七层防火墙 应用层，本质是代理网关 不管源端口目的端口源地址目的地址，统统查 安全，慢

七层更安全，效率更低。市面方案多是两者结合：边缘用三层快速筛一遍，关键入口后面再挂代理。所有访问都得从防火墙这个口过，它的处理效率直接决定用户能拿到多少数据，配得不好就是流量瓶颈。

它是怎么长出来的 #

阶段 内核 名字 能力
一代 1.x ipfirewall 从 FreeBSD 移植，规则全塞进内核，功能极其有限
二代 2.x ipchains 能定义多条规则，串起来共同起作用
当代 2.4+ iptables 规则组成列表，做细粒度访问控制

三代工具有个共同点：都在用户空间，都只是「定义规则的工具」，本身不算防火墙。它们写下的规则交给内核里的 netfilter 去读，防火墙才真正开始工作。

规则不能随便放，必须放在 TCP/IP 协议栈必经的位置。这些位置叫 netfilter，网络过滤器。

它到底是不是服务 #

这句要分清：

  • iptables 是用户态工具，负责把规则写进内核。规则写进去立即生效，不用重启任何东西。
  • 发行版又把 iptables 包成了一个服务。start 就把规则灌进去生效，stop 就把规则撤掉。
  • 所以「改完规则必须 service iptables restart」是误解。restart 只是把配置文件重新读一遍再灌，你手工敲的规则根本不在那个文件里。

在新一点的发行版上，iptables 命令后面挂的已经是 nftables 兼容层（iptables-nft）。命令语法没变，内核里的实现换了。本篇讲语法和语义，两条后端都通用。

一句话记住它 #

iptables 干的事只有三件：定义规则，挂到链上，让内核照着执行。规则是静态文本，链是执行位置，表是按功能分组的规则集合。

二、四张表与五条链 #

五个 hook 点 #

内核里选了五个位置卡住数据包。这五个位置叫钩子函数，也叫五条规则链：

链 位置 干什么
PREROUTING 路由前 包刚进网卡，还没决定去哪
INPUT 流入用户空间 目的地是本机，要交给进程
FORWARD 转发关卡 目的地不是本机，只是过路
OUTPUT 用户空间流出 本机自己发的包
POSTROUTING 路由后 出口已定，正要发上物理链路

任何一个包只要经过本机，必然走这五条链里的某几条。这句话是整篇的地基。

为什么要专门在路由前和路由后各卡一道？三层防火墙要靠目的地址做过滤，包刚进来时路由表还没查，你还不知道它是给本机还是过路，没法分流到 INPUT 或 FORWARD。而 DNAT 改的正是目的地址，必须赶在查路由表之前改完，否则路由用旧地址查表，包就去错地方了。SNAT 改源地址，得等出接口定了才知道改成哪个地址，所以放在路由之后。这两个位置不是冗余设计，是 NAT 的硬需求逼出来的。

四张表 #

表是按功能切分的规则集合。四张表的分工：

表 管什么 含哪些链 用得多不多
filter 过滤，允许或拒绝 INPUT、FORWARD、OUTPUT 最常用，默认表
nat 地址转换 PREROUTING、OUTPUT、POSTROUTING 做网关必用
mangle 改报文原数据 五条链全有 少用，打标记、改 TTL 时用
raw 绕过连接追踪 PREROUTING、OUTPUT 极少数场景

逐张说。

filter：不写 -t 就是它。放行、丢弃、拒绝全在这儿。三条链覆盖「进本机」「出本机」「过路转发」三种情形，正好是过滤需要管的全部流量。

nat：改源地址或目的地址。三条链各有专职——PREROUTING 做 DNAT，POSTROUTING 做 SNAT，OUTPUT 管本机自己产生的包的目的地址转换。记住这个对应关系，挂错链是新手第一大坑。

mangle：把包的元数据拆开改。TTL、TOS、打防火墙标记都归它，五条链都能挂。MARK 动作打上的标记，后面在别的表里用 -m mark 就能匹配到，策略路由和多链路分流都靠这个。

raw：唯一职责是「别对我做连接追踪」，动作用 -j NOTRACK。挂在 PREROUTING 或 OUTPUT，必须早于 conntrack 生效，所以 raw 的优先级排在所有表最前面。

日常干活的就前两张。mangle 和 raw 是专项工具，没需求别碰。

四张表和五条链的矩阵 #

不是任意表都能挂任意链。内核只在特定 hook 上注册特定表的处理函数：

PREROUTING INPUT FORWARD OUTPUT POSTROUTING
raw ✓ ✓
mangle ✓ ✓ ✓ ✓ ✓
nat ✓ ✓ ✓
filter ✓ ✓ ✓

同一个 hook 上，表也有先后：raw → mangle → nat → filter 依次过。这个顺序会影响结果——mangle 里打上的标记，filter 里才匹配得到；反过来写在 filter 里再指望 mangle 看见，永远不成立。

内置链和自定义链 #

这两个是完全不同的东西，别混：

内置链 自定义链
谁创建 内核，随表固定存在 你用 -N 建
是不是 hook 是，包流经时自动进入 不是，包不会自己走进去
怎么被调用 内核在 hook 点调用 只能被内置链或其他自定义链 -j 跳过去
用途 承接流量 把一堆规则打包，方便复用和阅读
默认策略 有，-P 设 没有，-P 设不上

自定义链只是「规则的组织手段」，不是「新的卡点」。你建一条 inbound_tcp_web，它不会自动拦下任何流量。只有哪天某条内置链写了 -j inbound_tcp_web，包才会跳进去。跳进去执行完，没命中任何终结动作，走到链尾会自动返回调用它的那条链的下一行——RETURN 动作就是这个「提前返回」的显式写法。

自定义链还有两条硬规矩：

  • 删除自定义链（-X）之前，必须先把链里的规则清空，否则报错。
  • 自定义链进了内置链才有意义，光建不引用，等于写了段没人调用的代码。

三层结构：表 > 链 > 规则 #

拼起来，iptables 的结构就三层：

text
表（filter / nat / mangle / raw）
 └─ 链（PREROUTING / INPUT / FORWARD / OUTPUT / POSTROUTING，或自定义链）
     └─ 规则（匹配条件 + -j 动作），按写入顺序排列

一个包到达某个 hook，内核先按 raw → mangle → nat → filter 过表；进了某张表的某条链，就从第一条规则开始逐条比对。

规则匹配是「顺序扫描 + 命中即停」。条件全中才算命中，命中就执行 -j 动作：

  • ACCEPT、DROP、REJECT、SNAT、DNAT 这类终结动作直接决定包的命运，后面的规则一条都不再看。
  • LOG、MARK 这类非终结动作执行完，接着比对下一条。
  • -j 自定义链 是跳出去执行，链尾或 RETURN 之后回来，接着比对下一行。

这条机制解释了一切关于顺序的争吵：为什么一条 DROP 放在前面会挡住后面所有规则。包已经被它杀了，后面精心写好的 ACCEPT 根本没有机会被看到。iptables 不评价你的规则合不合理，只认谁先被扫到。所以越严格、越具体的规则，越要往前放。

三、数据包经过哪些链 #

讲完结构，看包怎么走。三种情形，三条路径。

情形一：访问本机 #

text
网卡收包
  → PREROUTING      （raw → mangle → nat）
  → 路由决策：目的地址是本机
  → INPUT           （mangle → filter）
  → 用户空间进程（sshd、nginx）

回程包不走这条路，它是本机自己产生的，从 OUTPUT 出去：

text
用户空间进程
  → OUTPUT          （raw → mangle → nat → filter）
  → 路由决策：从哪个口出
  → POSTROUTING     （mangle → nat）
  → 网卡发出

情形二：本机发出 #

就是上面那段 OUTPUT → POSTROUTING。注意 nat 表在 OUTPUT 也有链，本机访问别人的地址要改写目的地址时，规则写在这里。

情形三：穿过本机转发 #

text
网卡收包
  → PREROUTING      （raw → mangle → nat）
  → 路由决策：目的地址不是本机，且允许转发
  → FORWARD         （mangle → filter）
  → POSTROUTING     （mangle → nat）
  → 另一个网卡发出

这条路径是网关、路由器、NAT 服务器、容器宿主的命脉。你的机器一旦要给别人转发，FORWARD 链就是主战场。

三条推论 #

从上面三张图直接能推出来规则该写在哪：

你要干的事 规则写哪
限制别人访问本机的服务 filter / INPUT
放行或限制本机发起的访问 filter / OUTPUT
过滤穿过本机的流量 filter / FORWARD
改目的地址，发布内网服务 nat / PREROUTING
改源地址，让内网共享上网 nat / POSTROUTING
改本机自己发出的包的目的地址 nat / OUTPUT

转发要开两个开关 #

想当网关，光写 FORWARD 规则不够，还得开内核转发：

bash
# 临时开，重启失效
echo 1 > /proc/sys/net/ipv4/ip_forward

# 永久开
echo 'net.ipv4.ip_forward = 1' >> /etc/sysctl.conf
sysctl -p

/proc/sys/net/ipv4/ip_forward 是 0 的时候，路由决策一步就把包扔了，FORWARD 链上的规则一条都不会被执行。新手排查「NAT 配好了但内网上不了网」，先看这个文件。

DNAT 之后还要过 FORWARD #

DNAT 只做翻译，不做放行。包改完地址继续走 FORWARD，不放行照样丢。放行规则要匹配翻译之后的端口：外网 2022 映射到内网 22，FORWARD 里就写 --dport 22，写 2022 永远匹配不上。第九章有完整翻车案例。

四、规则的结构 #

一条规则的完整骨架 #

text
iptables [-t 表] COMMAND 链 匹配条件 -j 动作

五段拆开：

段位 含义 能否省略
-t 表 操作哪张表：filter、nat、mangle、raw 能，省了就是 filter
COMMAND 怎么改规则：增、删、改、查、管链 不能
链 在哪个链上操作 部分命令能省，比如 -F 不带链名就是清空整张表
匹配条件 什么样的包算命中 能，一条不写就是匹配所有包
-j 动作 命中之后干什么 不能

读一条规则的时候，按这个顺序念一遍就懂了：在哪张表的哪条链上，抓什么样的包，然后怎么处理它。

举个例子 #

不允许 172.16.0.0/16 的机器来查本机的 DNS：

bash
iptables -t filter -A INPUT -s 172.16.0.0/16 -p udp --dport 53 -j DROP

拆开看：

  • -t filter：filter 表。
  • -A INPUT：追加到 INPUT 链末尾。
  • -s 172.16.0.0/16：源地址在这个网段。
  • -p udp --dport 53：UDP 协议，目的端口 53。
  • -j DROP：悄悄丢掉，不回任何包。

想拒绝得更彻底，让对方知道「这里有人但我不让你进」，换成 REJECT，并且插到链首：

bash
iptables -t filter -R INPUT 1 -s 172.16.0.0/16 -p udp --dport 53 -j REJECT

DROP 和 REJECT 的区别，是「沉默」和「明说」。对外网做防护用 DROP，藏住主机存在；对内网调试用 REJECT，排错快。

查看确认：

bash
iptables -L -n -v

五个常见写错 #

写法 问题 改法
iptables -A PREROUTING -j DNAT ... 忘了 -t nat，规则落到 filter 表，而 filter 没有 PREROUTING 链，直接报错 加 -t nat
iptables -A INPUT --dport 80 -j ACCEPT 没写 -p tcp，--dport 依赖协议扩展，报错「unknown option」 补 -p tcp
iptables -A INPUT -s www.example.com -j DROP -s 只吃 IP，不吃域名 先解析成 IP 再写
iptables -A INPUT -j DROP 放在链首 后面的规则全废 塞到链尾，或先写放行规则
iptables -P INPUT DROP 直接敲 当前 SSH 会话立刻断，包括 Xshell 这类远程连接 先放行 22 端口和已建立连接，最后再改默认策略

最后一条是运维事故高发点。改默认策略之前，先把管理口的放行规则和 ESTABLISHED 放行写好，再 -P。顺序反了，只能去机房接显示器。

五、匹配条件 #

匹配条件决定「这条规则抓哪些包」。多个条件写在一起是与关系，全部满足才算命中。

通用匹配 #

不依赖任何扩展模块，四条规则直接可用：

选项 含义 说明
-s 源地址 只吃 IP，不吃主机名
-d 目的地址 同上
-p 协议 tcp、udp、icmp 三种最常用
-i 从哪块网卡流入 只能用在 INPUT、PREROUTING、FORWARD
-o 从哪块网卡流出 只能用在 OUTPUT、POSTROUTING、FORWARD

-s 和 -d 的取值有三种写法：

bash
-s 192.168.1.10              # 单个 IP
-s 192.168.1.0/24            # 网段
-s 0.0.0.0/0.0.0.0           # 全部地址，等价于不写

取反在选项前面加感叹号，表示「除了这个之外」：

bash
iptables -A INPUT -s ! 192.168.1.10 -j DROP    # 除了 192.168.1.10，其他全丢
iptables -A INPUT ! -s 192.168.1.10 -j DROP    # 感叹号放前面也成立

-i 和 -o 不能乱用。PREROUTING 只认 -i（包刚进来，出口还没定），POSTROUTING 只认 -o（出口已定，入口信息在这是历史了）。写反了直接报错。

隐含扩展：跟着 -p 走 #

指定了 -p tcp，就自动获得了 TCP 相关的匹配能力，不用额外 -m：

bash
-p tcp --sport 1024:65535 --dport 80

端口写法只有两种：单个端口，或者连续范围（用冒号或连字符）。--dport 21-23 和 --dport 21:23 都表示 21、22、23 三个端口。不能写成 --dport 21,23,80 这种不连续的列表，那是 multiport 的活。

--tcp-flags 检查 TCP 标志位，要跟两个参数：

bash
--tcp-flags 要检查的位 必须为 1 的位

bash
# 检查 SYN、ACK、FIN、RST 这四个位，其中只有 SYN 为 1，其余必须为 0
--tcp-flags syn,ack,fin,rst syn

这个组合的意思是「三次握手的第一个包」。因为它太好用，给了个简写：

bash
--syn

-p udp 的扩展只有 --sport 和 --dport，没有标志位可查。

-p icmp 用 --icmp-type 匹配类型：

类型名 数字 含义
echo-request 8 请求回显，也就是 ping 出去
echo-reply 0 回显应答，也就是 ping 回来 
bash
--icmp-type 8      # 匹配 ping 请求
--icmp-type 0      # 匹配 ping 应答

显式扩展：-m 开头 #

需要额外能力时用 -m 模块名 显式加载。常用的四个：

模块 作用 典型写法
multiport 一次匹配多个不连续端口 -m multiport --dports 21,23,80
state 按连接状态匹配 -m state --state NEW,ESTABLISHED
conntrack 连接追踪的完整版，功能是 state 的超集 -m conntrack --ctstate NEW
mark 匹配 mangle 表打的标记 -m mark --mark 0x1

multiport 最多支持 15 个端口，正好补上 --dport 不能写不连续列表的短板：

bash
iptables -A INPUT -p tcp -m multiport --dports 21,23,80,443 -j ACCEPT

状态检测 #

-m state 是实战里最有价值的一个匹配条件。它不管端口号，只看这个包属于哪个连接、处在什么阶段。

TCP 是有连接的协议。三次握手，第一个包叫 NEW；从第二次握手之后 ack 位都是 1，进入正常数据传输，第二、三次握手连同后续数据都算 ESTABLISHED。还有一类诡异的组合，比如 SYN=1 ACK=1 RST=1，协议上解释不通，归为 INVALID。最后一种是「有关系但不是同一个连接」，比如 FTP 的 21 号控制端口和 20 号数据端口，一去一回互相牵连，这种关系叫 RELATED。

四种状态：

状态 含义 典型场景
NEW 连接的第一个包 发起 TCP 握手、发出第一个 UDP 包
ESTABLISHED 连接已建立，双向都有流量 握手完成后的所有数据包
RELATED 与已有连接有关联的新连接 FTP 数据通道、ICMP 差错报文
INVALID 无法识别，不属于任何已知连接 畸形标志位组合、超时的残包

有了状态检测，一条规则能顶一片：

bash
# 本机发出的连接，回程全部放行，不用为每个服务写一条
iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT

这个写法的附带效果是挡掉了不少反弹式木马：木马从内网主动连出去，回程是 ESTABLISHED 能过；但外部主动连进来的 NEW 包进不来，因为 INPUT 链没给它开口子。

state 和 conntrack 的区别只在写法。-m state --state 是老接口，-m conntrack --ctstate 是新接口，语义一致。新脚本用后者，老文档见前者，读的时候知道是一回事就行。

六、动作 target #

-j 后面跟的就是 target，决定命中之后怎么办。按「是否终结」分两类，这个分类比记住名字更重要。

终结动作 #

命中之后包的去向就定了，后面的规则不再看：

动作 行为 用在哪
ACCEPT 放行，交给协议栈继续处理 任何链
DROP 悄悄丢弃，不回任何响应 任何链
REJECT 明确拒绝，回一个错误包 filter 表
SNAT 改源地址 只能 nat / POSTROUTING
DNAT 改目的地址 只能 nat / PREROUTING、OUTPUT
MASQUERADE 源地址伪装，自动取出口地址 只能 nat / POSTROUTING
REDIRECT 目的地址改成自己，做端口重定向 只能 nat / PREROUTING、OUTPUT

DROP 和 REJECT 的取舍：DROP 静默，对方只看到超时，藏得住主机存在；REJECT 会回 ICMP port-unreachable 或者 tcp-reset，对方立刻知道被拒。对外防御用 DROP，对内排错用 REJECT。

REJECT 能指定回什么包：

bash
iptables -A INPUT -p tcp --dport 113 -j REJECT --reject-with tcp-reset

--reject-with 的常用取值有 icmp-port-unreachable、icmp-net-unreachable、icmp-host-prohibited、tcp-reset。不写就是默认的 icmp-port-unreachable。

REDIRECT 把目的地址改成本机地址，端口可以一起改。透明代理就靠它：把用户发往 80 端口的流量劫持到本机的 3128 端口，交给 squid 处理。

bash
iptables -t nat -A PREROUTING -p tcp --dport 80 -j REDIRECT --to-ports 3128

SNAT、DNAT、MASQUERADE 三个是第九章的主角，这里只记位置：改源的在 POSTROUTING，改目的的在 PREROUTING，挂错链规则不报错但不生效。

非终结动作 #

执行完接着比对下一条规则：

动作 行为
LOG 把包的信息写进内核日志，然后继续
MARK 给包打一个 32 位标记，然后继续
RETURN 从当前自定义链返回调用它的链
自定义链名 跳到那条链执行，执行完回来

LOG 是排错的好帮手，但它不拦包，必须配一条 DROP 才拦得住：

bash
iptables -A INPUT -p tcp --dport 22 -j LOG --log-prefix "SSH-IN: " --log-level 4
iptables -A INPUT -p tcp --dport 22 -j DROP

日志默认落到 /var/log/messages（或 /var/log/kern.log，看发行版的 rsyslog 配置），级别 4 对应 warning。--log-prefix 一定要写，不写的话几十条 LOG 规则混在一起，根本分不清是哪条触发的。

MARK 打上的标记不会跟着包离开本机，只在本机内核内部起作用：

bash
# mangle 表里打标
iptables -t mangle -A PREROUTING -s 192.168.10.0/24 -j MARK --set-mark 0x1

# filter 表里按标记匹配
iptables -A FORWARD -m mark --mark 0x1 -j ACCEPT

配合策略路由（ip rule fwmark 0x1 table 100）可以做多出口分流：哪个网段走联通、哪个走电信，全靠 MARK 和 ip rule 配合。

RETURN 的语义是「这条链我不处理了，回到调用我的地方」。写在自定义链里，作用相当于提前 return；写在自定义链末尾是多余的，因为链尾本来就会自动返回。

一条规则只能有一个 target #

-j 只能写一次。想既记日志又丢包，写两条规则，LOG 在前 DROP 在后。

自定义链也是 target #

-j 自定义链名 属于跳转，不是终结。包跳进去执行，没命中终结动作就回到原链继续往下走。这正是自定义链能当「规则子程序」用的原因：

bash
iptables -N web_in
iptables -A web_in -p tcp --dport 80 -j ACCEPT
iptables -A web_in -p tcp --dport 443 -j ACCEPT
iptables -A INPUT -p tcp -j web_in

INPUT 里所有 TCP 包跳进 web_in，命中 80 或 443 就放行，没命中走到链尾自动回 INPUT 继续。规则一多，这种拆法比几百行平铺好维护。

七、规则的增删查改 #

命令分三组：管链的、管规则的、看规则的。

链管理 #

命令 作用 例子
-N 新建自定义链 iptables -N inbound_tcp_web
-X 删除自定义空链 iptables -X inbound_tcp_web
-E 给自定义链改名 iptables -E oldname newname
-P 设内置链的默认策略 iptables -P INPUT DROP
-F 清空链里的规则 iptables -t nat -F PREROUTING
-Z 清零计数器 iptables -Z

-F 不带链名就是清空整张表：

bash
iptables -t nat -F          # 清空 nat 表所有链
iptables -F                 # 清空 filter 表所有链

-X 只能删空链，链里还有规则会报错。想删干净得两步：

bash
iptables -F mychain
iptables -X mychain

-P 只对内置链起作用，而且只有 ACCEPT 和 DROP 两个取值：

bash
iptables -P INPUT DROP      # 默认门关着
iptables -P INPUT ACCEPT    # 默认门开着

-P INPUT DROP 一敲，当前这条 SSH 连接立刻断，Xshell 这类远程工具直接掉线。要改就先放行管理口，再改默认策略。

-Z 清的是计数器。每条规则都有两个计数器：被匹配到多少个数据包、多少字节。这两个数字是排查规则有没有生效的第一手证据。

规则管理 #

命令 作用 说明
-A 追加到链尾 最常用，顺序最安全
-I num 插入为第 num 条 不写 num 默认插到第 1 条
-R num 替换第 num 条 整条规则被换掉
-D num 删除第 num 条 也可以 -D 链 规则原文
-D 链 规则原文 按内容删除 必须和原规则逐字一致

用 -I 插到最前面是最容易出事的地方。-I INPUT 1 -j DROP 一写，链里后面的规则全成摆设。

-I 的编号从 1 开始，-I 0 会报错。不写编号等价于 -I 1：

bash
iptables -I INPUT -p tcp --dport 22 -j ACCEPT    # 插到第 1 条
iptables -I INPUT 3 -p tcp --dport 80 -j ACCEPT  # 插到第 3 条

-R 是整条替换，不是改某个字段。写 -R 3 的时候，除了链和编号，其余部分要写全，漏写就等于把条件删了：

bash
iptables -R INPUT 2 -s 172.16.0.0/16 -d 172.16.100.1 -p tcp --dport 22 \
  -m state --state NEW,ESTABLISHED -j ACCEPT

-D 按内容删最容易失败，因为规则原文一个空格不对就匹配不上。习惯是先用 --line-numbers 看清行号，再按编号删。

查看 #

-L 是查看入口，靠子选项控制显示内容：

子选项 作用
-n 数字显示 IP 和端口，不做反向解析
-v 显示详细信息，含收发包数和字节数
-vv 更详细
-vvv 最详细，含规则的原始参数
-x 计数器显示精确值，不做 K/M 换算
--line-numbers 显示规则行号
-t 表名 看指定表，不写看 filter

组合起来最实用的三条：

bash
iptables -L -n --line-numbers          # 看 filter 表，带行号
iptables -L -n -v                      # 看每条规则命中过多少包
iptables -t nat -L -n -v               # 看 nat 表

不加 -n 会把 IP 反解成主机名。DNS 慢的时候，一条 iptables -L 能卡十几秒，所以养成为每条查看命令加 -n 的习惯。

-v 输出的两列 pkts 和 bytes 是排查的核心。规则写了却 pkts 一直是 0，说明包根本没走到这条规则——要么前面的规则先命中了，要么包压根没过这条链。

改默认策略的次序 #

动作次序固定：先放行回环，再放行管理口，再放行服务，最后才 -P DROP。顺序反了，当前 SSH 会话立刻断。

保存单张表 #

只想备份 nat 表，不动 filter：

bash
iptables-save -t nat > /root/nat.rules

这条命令输出的是规则文本，可以直接 iptables-restore 回去。第十章细讲持久化。

八、filter 表实战 #

规则语法讲完了，落到具体场景。这一章全部在 filter 表里做，不涉及地址转换。

场景一：只让某个网段访问本机 SSHD #

需求：172.16.0.0/16 网段可以访问本机 172.16.100.1 的 SSHD，其他一律不行。

先分析。这是访问本机服务，规则写 INPUT，不用碰 nat。SSHD 在 22 端口，处理方式是接受。访问本机服务要一来一回两条规则，会话的初始端先定义——进的方向先写，出的方向再写。

bash
# 进来的
iptables -t filter -A INPUT -s 172.16.0.0/16 -d 172.16.100.1 -p tcp --dport 22 -j ACCEPT

# 出去的
iptables -t filter -A OUTPUT -s 172.16.100.1 -d 172.16.0.0/16 -p tcp --sport 22 -j ACCEPT

回程这条要特别注意端口方向：包从本机 22 端口发出，所以是 --sport 22。写成 --dport 22 是最常见的笔误，在加了状态检测之后能歪打正着地通，去掉状态检测就立刻断。

然后把默认策略改成 DROP：

bash
iptables -P INPUT DROP
iptables -P OUTPUT DROP
iptables -P FORWARD DROP

三条一起改是标准动作。只改 INPUT 不改 OUTPUT，出方向全放行，内鬼往外连就挡不住了。

改完确认：

bash
iptables -L -n --line-numbers

场景二：叠上状态检测 #

场景一的写法有个硬伤：每加一个服务，就要写两条规则，一进一出。服务一多，规则数量翻倍，还容易漏。

用 -m state 改写成「进来的收 NEW 和 ESTABLISHED，出去的一律只要 ESTABLISHED」：

bash
# 先看清原规则在第几行
iptables -L -n --line-numbers

# 改写 INPUT 第 2 条
iptables -R INPUT 2 -s 172.16.0.0/16 -d 172.16.100.1 -p tcp --dport 22 \
  -m state --state NEW,ESTABLISHED -j ACCEPT

# 改写 OUTPUT 第 1 条：回程只认已建立的连接
iptables -R OUTPUT 1 -m state --state ESTABLISHED -j ACCEPT

这样 OUTPUT 只剩一条规则，以后加任何服务都不用动它。

再放行 80 端口，以及本机对外提供 DNS（53/udp，插到第 1 条）：

bash
iptables -A INPUT -d 172.16.100.1 -p tcp --dport 80 -m state --state NEW,ESTABLISHED -j ACCEPT
iptables -R INPUT 1 -d 172.16.100.1 -p udp --dport 53 -j ACCEPT

场景三：我能 ping 别人，别人 ping 不通我 #

这个需求看着绕，拆开很直白。ICMP 的 echo-request 是 8 号类型，echo-reply 是 0 号类型。ping 出去是 8，回程是 0。要「我 ping 得出去、别人 ping 不进来」，就是放行 8 出去、放行 0 进来：

bash
# 出去的 ping 请求
iptables -A OUTPUT -p icmp --icmp-type 8 -j ACCEPT

# 进来的 ping 应答
iptables -A INPUT -p icmp --icmp-type 0 -j ACCEPT

别人 ping 我，进来的包是 8 号类型，INPUT 链没有放行 8，被默认策略 DROP 掉。我 ping 别人，出去 8 放行，回来 0 也放行，通。

注意这两个动作是「非对称」的：一个方向 8，另一个方向 0。只放行 8 出去不放行 0 回来，包出得去回不来，表现就是 Request timeout。

场景四：回环地址要单独放行 #

127.0.0.1 是个特殊地址，INPUT 和 OUTPUT 的默认策略一旦改成 DROP，本机进程走回环的通信也会被拦。很多服务（数据库、缓存、PHP-FPM）都靠回环通信，不放行就一堆莫名其妙的连接失败。

bash
iptables -A INPUT -s 127.0.0.1 -d 127.0.0.1 -j ACCEPT
iptables -A OUTPUT -s 127.0.0.1 -d 127.0.0.1 -j ACCEPT

有人图省事直接 -i lo -j ACCEPT，也能达到目的。写完整地址的好处是能一眼看出在放行什么。

场景五：网关的 FORWARD 放行 #

一台双网卡机器当网关，内网口 eth1，外网口 eth0。要放行内网出去、只允许外网的回程进来：

bash
# 内网主动发起，双向都放
iptables -A FORWARD -i eth1 -o eth0 -m state --state NEW,ESTABLISHED -j ACCEPT

# 外网方向只认已建立的和关联连接
iptables -A FORWARD -i eth0 -o eth1 -m state --state ESTABLISHED,RELATED -j ACCEPT

# 默认拒绝
iptables -P FORWARD DROP

-i 和 -o 成对写，能精确表达「这个方向」。只写 -i eth1 不写 -o eth0，从 eth1 进来的包发往哪里都放行，包括绕回 eth1 这一种性。

一台 Web 服务器的完整规则集 #

把上面几段拼起来，一台对外的 Web 服务器大致长这样：

bash
# 清空旧规则
iptables -F
iptables -X

# 回环
iptables -A INPUT -s 127.0.0.1 -d 127.0.0.1 -j ACCEPT
iptables -A OUTPUT -s 127.0.0.1 -d 127.0.0.1 -j ACCEPT

# 已建立的连接，回程一律放行
iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT
iptables -A OUTPUT -m state --state ESTABLISHED,RELATED -j ACCEPT

# 管理口，建议限制源网段
iptables -A INPUT -s 10.0.0.0/8 -p tcp --dport 22 -m state --state NEW -j ACCEPT

# 对外服务
iptables -A INPUT -p tcp -m multiport --dports 80,443 -m state --state NEW -j ACCEPT

# 本机要能出去：DNS、NTP、软件源
iptables -A OUTPUT -p udp --dport 53 -m state --state NEW -j ACCEPT
iptables -A OUTPUT -p udp --dport 123 -m state --state NEW -j ACCEPT
iptables -A OUTPUT -p tcp -m multiport --dports 80,443 -m state --state NEW -j ACCEPT

# 放行本机对外 ping，挡住别人 ping 进来
iptables -A OUTPUT -p icmp --icmp-type 8 -j ACCEPT
iptables -A INPUT -p icmp --icmp-type 0 -j ACCEPT

# 记一笔被丢弃的包，方便排错
iptables -A INPUT -j LOG --log-prefix "INPUT-DROP: " --log-level 4

# 默认策略
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT DROP

每条规则在干什么，一张表看完：

规则 目的
回环两条 本机进程互通
ESTABLISHED,RELATED 两条 回程不用逐服务开口子
22 端口 远程管理，限定源网段
80/443 对外服务
53/123/80/443 出方向 DNS 解析、时间同步、拉软件包
ICMP 8 出 / 0 入 单向 ping
LOG 丢弃前留痕
默认 DROP 没写的一律不放

LOG 放在默认策略前面，作用是把「被默认策略丢掉」的包记下来。没这条，你只知道服务不通，不知道是哪个包被丢了。

九、nat 表：SNAT 与 DNAT #

nat 表三条链，各有专职：

链 动作 改什么 方向
PREROUTING DNAT 目的地址 外 → 内
POSTROUTING SNAT、MASQUERADE 源地址 内 → 外
OUTPUT DNAT 本机产生的包的目的地址 本机 → 任意

挂错链规则不报错，但永远不生效。这是 nat 表第一大坑：SNAT 写在 PREROUTING 里，iptables 会直接拒绝并提示 SNAT target only valid in POSTROUTING；但把 DNAT 写在 POSTROUTING 里，某些版本只给警告，你以为配好了，包其实没变。

两个方向的执行顺序 #

先看 DNAT 方向。路由只查目的 IP，所以改目的地址必须赶在路由之前：

text
PREROUTING 做 DNAT 翻译
  → 路由决策（用翻译后的新地址查表）
  → FORWARD 过滤（匹配的也是新地址）
  → 从内网口发出

路由和 FORWARD 里匹配到的目的地址，都是 PREROUTING 翻译之后的。放行规则要按新地址、新端口写。

再看 SNAT 方向：

text
路由决策（用原始源地址）
  → FORWARD 过滤（匹配的还是原始源地址）
  → POSTROUTING 做 SNAT 翻译
  → 从外网口发出

FORWARD 里匹配到的源地址是翻译前的。这个不对称是理解 NAT 排错的钥匙：出去看原地址，进来（DNAT 之后）看新地址。

SNAT：改源地址 #

用途：一堆内网用户共享一个外网口上网。把内网源地址统一换成外网地址，回程包才能找回来。

text
-j SNAT --to-source ipaddr[-ipaddr][:port-port]

只能用在 nat 表的 POSTROUTING 链。

bash
# 192.168.10.0/24 全部转成 172.16.100.1
iptables -t nat -A POSTROUTING -s 192.168.10.0/24 -j SNAT --to-source 172.16.100.1

这样来自本地网络、想通过网卡访问外网的包，源地址统统变成 172.16.100.1。

--to-source 有三种写法：

写法 含义 效果
--to-source 172.16.100.1 单个地址 所有流共用一个公网 IP
--to-source 172.16.100.1-172.16.100.10 地址范围 每个流随机分一个地址，天然负载均衡
多条 --to-source 并列 多个地址 简单轮询（round-robin）

地址范围带端口限定，只能配 -p tcp 或 -p udp 使用：

bash
iptables -t nat -A POSTROUTING -p tcp -s 192.168.1.0/24 \
  -j SNAT --to-source 219.142.217.161:1024-32000

不指定端口范围时，源端口小于 512 的包会被映射到另一个小于 512 的端口。这条限制来自早期端口分配习惯，配上端口范围就不会踩到。

多个内网段要上网，就是多条 SNAT 语句，一条一个网段：

bash
iptables -t nat -A POSTROUTING -s 192.168.0.0/24 -o eth0 -j MASQUERADE
iptables -t nat -A POSTROUTING -s 192.168.1.0/24 -o eth0 -j MASQUERADE
iptables -t nat -A POSTROUTING -s 192.168.100.0/24 -o eth0 -j MASQUERADE

-o eth0 限定出口网卡，双出口机器上必写。不写的话，从哪个口出去的包都会被改成 eth0 的地址，回程就乱了。

用非外网口地址做 NAT，必须先绑到接口上，比如 eth0:1、eth0:2：

bash
ifconfig eth0:1 172.16.100.1 netmask 255.255.255.0 up

地址不绑上去，内核不认这个地址属于本机，NAT 配了也不通，回程包直接被丢。

MASQUERADE：动态源地址伪装 #

外网地址不固定怎么办？联通、电信的宽带每次拨号都随机给一个公网 IP，SNAT --to-source 写死了就失效。

MASQUERADE 就是干这个的：自动找到出口网卡的地址，把它填进去。

bash
iptables -t nat -A POSTROUTING -s 192.168.10.0/24 -j MASQUERADE

带出口网卡和端口范围：

bash
iptables -t nat -A POSTROUTING -o eth1 -s 192.168.1.0/24 -j MASQUERADE
iptables -t nat -A POSTROUTING -o ppp0 -j MASQUERADE
iptables -t nat -A POSTROUTING -o eth1 -s 192.168.1.0/24 -j MASQUERADE --to-ports 1024-30000

--to-ports port[-port] 只对 -p tcp 或 -p udp 的规则生效。

MASQUERADE 比 SNAT 多一层开销：每个包都要去查出口地址。地址固定时用 SNAT，地址动态时才用 MASQUERADE。它也不是万能的——出口地址频繁变化、或者需要固定映射关系的场景，它顶不上。

DNAT：改目的地址 #

用途：把外网访问重定向到内网机器。比如只有一个公网 IP，要让外部访问内网的两台服务器。

text
-j DNAT --to-destination ipaddr[-ipaddr][:port-port]

只能用在 nat 表的 PREROUTING 链（本机发出的包用 OUTPUT）。

bash
# 把访问 192.168.10.18:80 的流量转给内网 172.16.100.2
iptables -t nat -A PREROUTING -d 192.168.10.18 -p tcp --dport 80 -j DNAT --to-destination 172.16.100.2

目标地址转换必须赶在到达网卡之前完成，所以挂在 PREROUTING。这是位置决定的，不是习惯问题。

--to-destination 的三种写法：

写法 含义
--to-destination 192.168.1.4 只换地址，端口不变
--to-destination 192.168.1.4:8080 地址和端口一起换
--to-destination 192.168.1.24-192.168.1.25 地址范围，做负载均衡

地址范围那种写法相当于 Cisco 的 rotary，每个新连接随机落到范围内某台机器上。iptables 没有 Cisco 那种 static map 语法，一对一映射就是写死一条 DNAT。

一个完整例子。外网口地址 210.83.2.206，内网口 192.168.1.1，内网有 FTP 服务器 192.168.1.3 和 Web 服务器 192.168.1.4：

bash
# 外网访问 21 端口 → 内网 FTP
iptables -t nat -A PREROUTING -d 210.83.2.206 -p tcp --dport 21 -j DNAT --to 192.168.1.3

# 外网访问 80 端口 → 内网 Web
iptables -t nat -A PREROUTING -d 210.83.2.206 -p tcp --dport 80 -j DNAT --to 192.168.1.4

# 地址范围，两台机器分摊
iptables -t nat -A PREROUTING -d 219.142.217.161 -j DNAT --to-destination 192.168.1.24-192.168.1.25

--to 是 --to-destination 的简写，两个都能用。

带端口映射的例子，把内网 192.168.100.125:21 的 FTP 发布到公网 216.94.87.37:2121：

bash
iptables -t nat -A PREROUTING -p tcp -d 216.94.87.37 --dport 2121 \
  -j DNAT --to-destination 192.168.100.125:21

外部用户连 216.94.87.37:2121，包到内网变成连 192.168.100.125:21。

DNAT 之后必须过 FORWARD #

再强调一次，因为这是 DNAT 排错里最高频的一条。

DNAT 只做地址翻译，不做放行。包改完地址之后继续走 FORWARD，FORWARD 不放行照样丢。而且放行规则匹配的是翻译之后的地址和端口，因为 FORWARD 在 PREROUTING 之后执行。

一个真实的翻车过程。配了三组端口映射：外网 2022 → 内网 22，外网 9000 → 内网 9000，外网 9001 → 内网 9001：

bash
iptables -t nat -A PREROUTING -d 124.126.86.138 -p tcp --dport 2022 -j DNAT --to-destination 10.4.3.150:22
iptables -t nat -A PREROUTING -d 124.126.86.138 -p tcp --dport 9001 -j DNAT --to-destination 10.4.3.150:9001
iptables -t nat -A PREROUTING -d 124.126.86.138 -p tcp --dport 9000 -j DNAT --to-destination 10.4.3.150:9000

FORWARD 按「原始端口」写：

bash
iptables -A FORWARD -i $WAN_INT -m state --state NEW -p tcp --dport 9000 -j ACCEPT
iptables -A FORWARD -i $WAN_INT -m state --state NEW -p tcp --dport 9001 -j ACCEPT
iptables -A FORWARD -i $WAN_INT -m state --state NEW -p tcp --dport 2022 -j ACCEPT

结果：9000 和 9001 都通，2022 怎么都不通。

原因是 9000 和 9001 都是端口不变的翻译（9000→9000），FORWARD 匹配 --dport 9000 时包的目的端口还是 9000，能中。而 2022 是 2022→22 的翻译，包进 FORWARD 时端口已经变成 22 了，--dport 2022 永远匹配不上，被默认策略丢掉。

改法只有一处：

bash
iptables -A FORWARD -i $WAN_INT -m state --state NEW -p tcp --dport 22 -j ACCEPT

FORWARD 里写翻译后的端口。这条规则覆盖了所有走到 22 端口的包，不管是外网 2022 映射来的，还是别的路径来的。

DNAT 的回程要单独配 SNAT #

外网通过 DNAT 访问内网服务器时，服务器回包的源地址往往不是外网用户期望的那个人。这部分不由 DNAT 负责，需要另一条 SNAT 单独处理。

端口被改过的场景尤其明显。上面那个 FTP 例子，外网用户请求的是 216.94.87.37:2121，如果服务器直接回一个源端口 21 的包，客户端只认自己发出去的 2121，收到 from 21 的响应会直接丢掉。

补一条针对回程的 SNAT：

bash
iptables -t nat -A POSTROUTING -p tcp -s 192.168.100.125 --sport 21 \
  -j SNAT --to-source 216.94.87.37:2121

这条规则把服务器发出的源端口 21 改回 2121，客户端就认了。

点对点的网络应用也有同样的要求：DNAT 只改了一半的路径，回程那一半必须配一条和它对称的 SNAT，否则会话建立不起来。

内网访问内网服务器的外网地址 #

这是 NAT 里最绕的一个场景，绕在路由上。

内网客户机 10.4.3.119 发起请求，目标是「服务器对外的公网地址」124.126.86.138（它真正是 10.4.3.150）。防火墙收到包，匹配到 DNAT 规则，于是按纯路由的方式把包转给 10.4.3.150。

问题出在回程。服务器 10.4.3.150 收到请求，看到源地址是 10.4.3.119，跟自己同一个网段，于是直接回 SYN+ACK 给 10.4.3.119，不经过防火墙。

客户机收到这个包就懵了：它从没给 10.4.3.150 发过连接请求，它只找过 124.126.86.138。地址对不上，包被丢弃，连接卡死。

解决办法是加一条朝内网方向的 SNAT，把源地址改成防火墙内网口地址，让回程必须经过防火墙：

bash
iptables -t nat -A POSTROUTING -d 10.4.3.150 -j SNAT --to 10.4.0.198

发往 10.4.3.150 的包，源地址被改成防火墙内网口 10.4.0.198。服务器看到的源地址不在同网段，回包走网关（也就是防火墙），防火墙再按连接追踪把地址还原成 10.4.3.119。整条路径闭合了。

这个场景有个名字叫 hairpin NAT，也叫 NAT 回流。判断特征：外网能访问、内网访问不了公网地址、抓包看到 SYN 到了服务器但 SYN+ACK 没回来。

反过来还有一种需求：禁止服务器自己用公网地址访问自己。做法是在 PREROUTING 里排除掉它自己的地址：

bash
iptables -t nat -A PREROUTING -d 210.83.2.206 -s ! 192.168.1.24 -p tcp --dport 21 -j DNAT --to 192.168.1.24

-s ! 192.168.1.24 的意思是「源地址不是 192.168.1.24」。服务器自己发起的包源地址就是它自己，被这条规则排除，DNAT 不生效，它老老实实走内网访问。

没有 PAT，只有 NAPT #

先把词理清。PAT 是 Cisco 自己的概念，没有对应的 RFC。Linux 实现的是完整的 NAT 加 NAPT（网络地址端口转换，见 RFC 3022），能做地址替换，也能做端口替换。

有个细节值得知道：Linux 做端口替换时，端口并没有 bind 到本地协议栈上，所以不受本地 65535 个端口资源的限制。转换也有范围约束：

约束 内容
源端口下限 必须大于 1024
转换后范围 落在 1024 到 32000 之间
限定场景 只转换 1024 以上、30000 以下的源端口

这些约束解释了为什么手动指定 --to-ports 1024-30000 更稳：把可用区间圈死，避免和系统临时端口打架。

十、规则的保存与持久化 #

规则全在内核内存里，重启机器全没了。想活过重启，必须落盘。

三条命令 #

bash
service iptables save                       # 存进 /etc/sysconfig/iptables
iptables-save > /etc/sysconfig/iptables     # 等价的工具调用
iptables-restore < /etc/sysconfig/iptables  # 手动灌回内核

开机时初始化脚本读这个文件灌回去。开机没自动加载，或者想让手写的 iptables.2 立刻生效：

bash
iptables-restore < /etc/sysconfig/iptables.2

iptables-restore 的行为要记清：先清空文件里出现过的表，再按文件内容重建。文件里没提到的表不动——从 nat 备份恢复，filter 的规则原封不动留着。

各发行版的机制不一样 #

发行版 保存命令 文件
CentOS 6 / 7 service iptables save（7 要装 iptables-services） /etc/sysconfig/iptables
CentOS 8+ 默认 firewalld，装 iptables-services 才有这套 /etc/sysconfig/iptables
Debian / Ubuntu netfilter-persistent save /etc/iptables/rules.v4

Ubuntu 上装包再存：

bash
apt install iptables-persistent
netfilter-persistent save
netfilter-persistent reload

备份文件长什么样 #

text
*filter
:INPUT DROP [0:0]
:OUTPUT ACCEPT [12:840]
-A INPUT -s 127.0.0.1/32 -d 127.0.0.1/32 -j ACCEPT
-A INPUT -p tcp -m multiport --dports 80,443 -j ACCEPT
COMMIT

:链名 默认策略 [包计数:字节计数] 是链声明，默认策略就藏在这几行里。只想备份一张表：iptables-save -t nat > /root/nat.rules。

存完先 iptables-restore < 文件 跑一遍验证语法。有错会整段失败，重启后你面对的是一台完全不设防的机器。

十一、调试与排错 #

规则不生效，按顺序排查，别乱猜。

先看计数器 #

bash
iptables -L -n -v --line-numbers

pkts 是 0，说明包没走到这条规则。两种情况：前面的规则先命中了，或者包压根没进这条链。

确认包进了哪条链 #

回第三章三条路径对照。访问本机服务走 INPUT，过路走 FORWARD，别在 FORWARD 里找 SSH 的规则。用 LOG 打足迹比猜快：

bash
iptables -t nat -I PREROUTING 1 -p tcp --dport 80 -j LOG --log-prefix "PRE80: "
iptables -I FORWARD 1 -p tcp --dport 80 -j LOG --log-prefix "FWD80: "
iptables -I INPUT 1 -p tcp --dport 80 -j LOG --log-prefix "IN80: "
tail -f /var/log/messages        # Debian/Ubuntu 上是 /var/log/kern.log

哪个前缀出现，包就走到哪一步。三个都没出现，包在网卡那层就被丢了，方向搞错了。

查连接追踪 #

bash
cat /proc/net/nf_conntrack       # 或 conntrack -L，要装 conntrack-tools

记录前半段是原始方向，方括号前是回程方向。回程的 dst 已经是 SNAT 之后的公网地址，说明转换生效。追踪表里没记录，NAT 必然不通。

表满了表现为新连接时通时不通，对比这两个数：

bash
sysctl net.netfilter.nf_conntrack_count
sysctl net.netfilter.nf_conntrack_max

count 逼近 max 就调大上限，或者缩短 nf_conntrack_tcp_timeout_established。

NAT 的 -i / -o 限制 #

链 只能用 指哪块网卡
PREROUTING -i 外网入口
POSTROUTING -o 外网出口
OUTPUT -o 外网出口

PREROUTING 写 -o 直接报错，那时还没决定从哪出去；POSTROUTING 写 -i 同样不行。

抓包兜底 #

bash
tcpdump -i eth0 -nn 'tcp port 2022'    # 外网口：包有没有被改地址
tcpdump -i eth1 -nn 'tcp port 22'      # 内网口：包有没有转发进去

外网口看到 2022、内网口看到 22，DNAT 生效。外网口有、内网口没有，包在 FORWARD 被丢了。

症状对照 #

症状 最常见原因
规则写了，pkts 一直是 0 顺序被前面规则挡住，或者链挂错
内网能上外网，外网访问不了内网服务 缺 FORWARD 放行，或放行口写的端口是翻译前的
外网能访问，内网访问不了公网地址 hairpin NAT 没配，见第九章
SSH 一连就断 -P INPUT DROP 早于放行 22 端口
NAT 配好但内网完全不通 ip_forward 是 0
端口映射通了但服务回了错端口 缺回程 SNAT，见第九章 FTP 例子
一切正常但偶尔丢包 conntrack 表打满

清场重来 #

bash
iptables -F; iptables -X
iptables -t nat -F; iptables -t nat -X
iptables -t mangle -F; iptables -t mangle -X
iptables -P INPUT ACCEPT
iptables -P FORWARD ACCEPT
iptables -P OUTPUT ACCEPT

默认策略最后改成 ACCEPT，不是最先。顺序反了，中间那几秒机器完全不设防。

十二、易错点速查 #

把这些记住，能省掉大半排错时间。

现象 错在哪 怎么改
SNAT 报 only valid in POSTROUTING 挂到了 PREROUTING 挪到 POSTROUTING
DNAT 配好但包没变 忘了 -t nat，规则落进 filter 表 加 -t
端口映射 2022→22 不通，同端口映射通 FORWARD 规则按翻译前端口写 FORWARD 写翻译后的 22
DNAT 通了但连接立刻断 FORWARD 没放行，DNAT 不是放行 补 FORWARD ACCEPT
内网访问不了服务器的公网地址 回程绕过防火墙 加朝内网的 POSTROUTING SNAT
改了 -P INPUT DROP 后 SSH 掉线 放行规则在默认策略之后 先放行再改策略
一条 -j DROP 让后面规则全失效 顺序错了，命中即停 具体规则前置，DROP 后置
--dport 报 unknown option 缺 -p tcp 补协议
--dport 21,23,80 报错 --dport 不吃不连续列表 用 -m multiport --dports
规则重启后消失 没落盘 iptables-save 存文件
反解主机名卡住十几秒 查看没加 -n iptables -L -n
-X 删链报错 链里还有规则 先 -F 再 -X
-I 之后规则顺序全乱了 插到了第 1 条 用 -A，或按 --line-numbers 算好位置
换了外网 IP 后内网上不了网 SNAT --to-source 写死了旧地址 换 MASQUERADE
双出口机器回程乱 POSTROUTING 没写 -o 按出口网卡分别写规则
MASQUERADE 换了机器就不通 出口地址不是本机绑定的地址 先把地址绑到接口或子接口

最后一条最隐蔽。非外网口地址做 NAT，地址必须先绑到接口上（eth0:1、eth0:2），内核才认它属于本机。地址不绑，规则语法全对，包就是不回来。

把上面这些点串起来，其实只有一条主线：包按路径走链，链按顺序扫规则，规则命中即停，NAT 的翻译位置由路由决定。任何一条规则不生效，都从这四句里找答案。
