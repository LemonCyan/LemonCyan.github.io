这一篇只回答一个问题：一台 Linux 主机的网络，到底是怎么配起来的。

配网络拆开看只有五样东西：网卡本身、IP 地址和掩码、默认网关、DNS 服务器、一条能让流量走出去的路由。剩下的全是「这五样写进哪个文件」。

本篇管的事：

  • 临时配置和持久化配置是两套东西，以及为什么「我配好了，一重启就没了」。
  • 持久化的入口因发行版而异：/etc/network/interfaces、Netplan 的 YAML、NetworkManager、systemd-networkd。
  • DNS 的两层结构：/etc/resolv.conf 生效，但它随时会被别的服务重写。
  • VMware / VirtualBox 里桥接、NAT、Host-Only 三种模式的区别，以及开发板连虚拟机该选哪个。

本篇不管的事：

  • 抓包、看连接、读路由表条目，那是「怎么看」，在 03-协议栈与内核实现 的「网络命令与排错基础」里。
  • 防火墙规则和地址转换，在同目录的 iptables 规则与 NAT 配置 里。
  • 访问控制列表，在同目录的 ACL 访问控制列表 里。
  • 交换机侧的端口、VLAN、Trunk，在同目录的 交换机端口配置 里。

分界线一句话：本篇动手改文件，隔壁篇动手看状态。

一、网络配置要配哪几样 #

很多人一上来就抄一段配置贴进去，改完发现不通，再抄一段。问题出在不知道自己在配哪一层。先把这五样对齐，后面所有文件都只是「五样东西的另一种写法」。

要素 干什么用 配错会怎样
接口（interface） 数据从哪块网卡进出 网卡没起来，下面全白配
IP 地址 + 掩码 本机在哪个网段，网段内谁直连 同网段互相 ping 不通
掩码 划出「直连」与「要走网关」的边界 掩码错一位，整段路由判断都错
默认网关 出本网段的路口 能 ping 通同网段，出不去
DNS 服务器 域名换 IP 能 ping 通 IP，ping 不通域名

一台机器配好之后长什么样 #

我们拿一台虚拟机举例，要求是：地址 192.168.1.151，掩码 255.255.255.0，网关 192.168.1.2，DNS 202.38.64.1。配好之后，四条信息必须同时成立：

bash
ip -4 addr show          # 有 192.168.1.151/24 挂在某块网卡上，且 state UP
ip route show            # 有一行 default via 192.168.1.2
cat /etc/resolv.conf     # 有一行 nameserver 202.38.64.1
ping -c 3 192.168.1.2    # 网关能通，说明链路和地址没问题

少任何一条，症状都不一样。这四条就是排错的顺序，从上往下查。

两个世界：内核状态和配置文件 #

这是本篇最要紧的一节。

ip addr、ip route 读的是内核里的运行时状态。你在命令行敲 ip addr add，改的就是这块内存。机器一关机，内存没了，配置也就没了。

配置文件则是开机时被读一遍的文本。开机后由 ifupdown、Netplan、NetworkManager、systemd-networkd 这些程序把文件内容翻译成 ip 命令，喂给内核。

text
配置文件  ---(开机 / 重启网络时被解析)--->  内核运行时状态  ---(关机清空)---> 没了
/etc/...                                    ip addr / ip route

反过来不成立：ip addr add 加进去的地址，不会被任何程序写回配置文件。所以下面这条循环，新手几乎都要撞一次：

bash
sudo ip addr add 192.168.1.151/24 dev eth0   # 注意是 /24 前缀写法，不是 netmask
sudo ip route add default via 192.168.1.2
ip addr show eth0

重启之后：

bash
ip addr show eth0                            # 空的，地址没了

不是命令没生效，是这个地址从来就没进过配置文件。想让它活过重启，只有一条路：改文件。

一个反过来的坑：改了文件没生效 #

配置文件也不会自己往内核里灌。改完必须触发一次重新加载：

bash
sudo systemctl restart networking    # ifupdown 体系
sudo netplan apply                   # Netplan 体系
sudo nmcli con up <连接名>            # NetworkManager 体系
sudo systemctl restart systemd-networkd

改对了文件、没重载，现象和改错文件一模一样：ip addr 里还是老地址。所以在「改了没生效」这条抱怨里，一半是文件拿错了，一半是没重载。

二、网络接口的命名 #

内核眼里的网卡是设备，用户眼里的网卡是名字。名字对不上，后面所有命令都白敲。

名字 含义
lo 本地回送接口，地址 127.0.0.1
eth0、eth1 第 0、1 块以太网卡（老式命名）
ppp0、ppp1 第 0、1 个 PPP 接口，拨号用
wlan0 无线网卡
eno1、ens33、enp0s3 现代可预测命名
docker0、br0、veth* 网桥、容器虚拟网卡
eth0:1 老式子接口，一块网卡挂第二个 IP

lo：永远在的那个 #

回送接口不做真实收发。程序往 127.0.0.1 发的包，协议栈原地转回来，一个字节都不出网卡。它的用途是让本机进程之间有个统一的通信地址，也方便在完全没网的情况下测程序。

lo 是内核预置的，开机自动就绪，坏了才需要管它。ping 127.0.0.1 不通，说明协议栈本身有问题，跟网线、网关都没关系。

ethn：以太网卡 #

eth 表示以太网类型，后面的数字是卡的序号，从 0 开始。两块网卡就是 eth0 和 eth1。

老式命名的问题是序号取决于内核探测顺序。加一块卡、换个插槽，eth0 和 eth1 就会对调，配置文件里写死的名字瞬间指错网卡。现代发行版改成了可预测命名：

  • eno1：板载网卡，按固件里的索引编号。
  • ens33：按 PCI 热插拔槽位编号。
  • enp0s3：按 PCI 总线位置编号。
  • enx 开头：按 MAC 地址生成。

名字里 en 是以太网，wl 是无线，ww 是蜂窝。换机器、换发行版，名字就变，这是抄配置文件最容易翻车的地方。抄之前先看一眼自己机器上叫什么：

bash
ip link show
ls /sys/class/net/

pppn：点对点接口 #

ppp 是 Point-to-Point Protocol。它和以太网不是一回事：没有广播、没有 ARP，链路两端就两个地址。拨号上网、PPPoE 宽带、部分 4G 模块都走它。

ppp0、ppp1 按建立连接的顺序编号。这类接口是「拨上去才有，挂断就消失」的动态接口，不是一个开机就躺在那儿的网卡。所以它的配置重点不在地址（地址由对端分配），而在于「谁来发起这次拨号」。

三、临时配置：ip 命令 #

ip 属于 iproute2 工具集，现在是所有发行版的标准件。它改的是内核运行时状态，重启清空。它的定位是调试和验证，不是配置。

地址 #

bash
sudo ip addr add 192.168.1.151/24 dev eth0   # 加地址，/24 就是掩码 255.255.255.0
ip addr show                                 # 看全部接口
ip -4 addr show dev eth0                     # 只看 eth0 的 IPv4
sudo ip addr del 192.168.1.151/24 dev eth0   # 删掉这个地址
sudo ip addr flush dev eth0                  # 清空这块卡上的所有地址

一个接口可以挂多个地址，加几次 ip addr add 就行。这是 iproute2 比 ifconfig 强的地方之一：别名接口才做得到的事，现在直接叠。

启停接口 #

bash
sudo ip link set eth0 up
sudo ip link set eth0 down
ip link show eth0

down 会把这块卡上的路由一起撤掉，所以远程连着的机器上别随手 ip link set eth0 down。

网关和路由 #

bash
sudo ip route add default via 192.168.1.2      # 默认网关
sudo ip route del default                      # 删掉
sudo ip route replace default via 192.168.1.2  # 换一个，先删再加也行
ip route show                                  # 看路由表
ip route get 8.8.8.8                           # 问内核：去这个地址走哪条路

ip route get 是排错时最省事的一条命令，它直接告诉你内核会把这个包从哪块网卡、经哪个网关发出去。

老命令对照 #

素材里的年代用的是 ifconfig 和 route。这些命令在 net-tools 包里，很多新系统默认不装。老教程照抄会报 command not found，对照关系如下：

老命令 新命令 说明
ifconfig ip addr 看地址
ifconfig eth0 up ip link set eth0 up 启接口
ifconfig eth0 192.168.1.10 netmask 255.255.255.0 up ip addr add 192.168.1.10/24 dev eth0 配地址
ifconfig eth0 down ip link set eth0 down 停接口
route -n ip route 看路由
route add default gw 192.168.1.1 ip route add default via 192.168.1.1 配默认网关
route add 0.0.0.0 netmask 0.0.0.0 eth0 ip route add default dev eth0 不指定网关的默认路由
netstat -tuln ss -tuln 看监听端口

老命令的完整写法，参数模板是 ifconfig [interface] [ip-address] [netmask ...] [broadcast ...] [up] [down]：

bash
sudo ifconfig eth0 192.168.1.10 netmask 255.255.255.0 up

网关的写法是 route add default gw [IP 地址]：

bash
sudo route add default gw 192.168.1.1

ifconfig 配的地址一样是临时的，重启就丢。别因为它是「老命令」就以为它会持久化。

别忘了 sudo #

普通用户改不了网络配置，内核直接把操作拦掉。用 sudo 提权，输入自己的密码，这一条命令以 root 身份跑：

bash
sudo ifconfig eth0 192.168.152.30 netmask 255.255.255.0
sudo route add default gw 192.168.152.2

sudo 给的权限只在这一条命令的生命周期里起作用，不是「变成 root 了」。配置效果也一样是临时的。

四、持久化配置的几种方式 #

持久化没有统一答案，因为 Linux 发行版各有各的历史。同一台机器上，两三套同时装着的场面很常见，谁最后跑谁说话。

方式 配置文件 生效命令 谁在用
ifupdown /etc/network/interfaces systemctl restart networking Debian / Ubuntu 老版本
Netplan /etc/netplan/*.yaml netplan apply Ubuntu 17.10 之后
NetworkManager /etc/NetworkManager/system-connections/ 等 nmcli con up <名> 桌面版、RHEL 系
systemd-networkd /etc/systemd/network/*.network systemctl restart systemd-networkd 服务器、容器宿主
ifcfg 脚本 /etc/sysconfig/network-scripts/ifcfg-* systemctl restart network RHEL 系老版本

四套东西不是并列的选项，是不同年代的不同答案。Netplan 本身不干活，它在 YAML 里写 renderer: networkd 或 renderer: NetworkManager，转手把配置生成给下面那套执行。所以「Ubuntu 上改了 NetworkManager 却没反应」这种事，查到最后常常是 Netplan 把它盖掉了。

先判断自己该改哪个文件 #

别看教程，看机器：

bash
ls /etc/netplan/                              # 有没有 Netplan
cat /etc/network/interfaces                   # 有没有 interfaces，有 iface 行才算数
nmcli device status                           # 谁在管这块网卡
systemctl is-active NetworkManager systemd-networkd systemd-resolved
networkctl status

判断规则很短：

  • /etc/netplan/ 下有 .yaml，就改 YAML，别的先不动。
  • 只有 /etc/network/interfaces 且内容里有 iface 行，走 ifupdown。
  • nmcli device status 里那块网卡状态是 connected，说明 NetworkManager 在管。
  • 两套同时在跑，先确认哪套是权威的，再改。两套都写同一块网卡，等于给自己埋雷。

那堆系统文件都管什么 #

素材里列过一圈 TCP/IP 相关文件，按「管什么」重新归一下：

文件 管什么
/etc/sysconfig/network 系统级网络开关，是否启用网络
/etc/sysconfig/network-scripts/ 网络配置脚本目录，开机初始化网络
/etc/sysconfig/network-scripts/ifcfg-eth0 单块网卡的地址、网关等参数
/etc/sysconfig/network-scripts/ifcfg-eth0:1 同一块网卡的第二个 IP（子接口）
/etc/network/interfaces Debian 系的接口配置总入口
/etc/resolv.conf DNS 服务器地址
/etc/hosts 主机名与 IP 的静态映射
/etc/host.conf 名字解析顺序：先 hosts 还是先 DNS
/etc/services 服务名与端口、协议的对应表
/etc/xinetd.conf 超级进程 xinetd 托管的服务与访问控制

/etc/services 不参与配置，它是查询表。telnet 主机 22 里的 ssh 能被翻成 22，靠的就是它。改它没有配置效果。

/etc/xinetd.conf 也不是配 IP 的，它管「哪些服务由 xinetd 拉起、谁能访问」。它属于服务管理，和地址、网关不在一个层面。

图形化的那条路 #

有些发行版带 netconfig 一类的菜单工具，敲命令起一个交互界面，按提示填地址、掩码、网关、DNS，最后它替你写文件。

这类工具的定位是「帮你写配置文件」，它不引入新机制。好处是不用背语法，坏处是出问题时你不知道它写了什么。用过一次就该去看看它到底改的是哪个文件——那才是真相。

五、Netplan #

Ubuntu 从 17.10 起换成 Netplan。配置文件是 YAML，放在 /etc/netplan/ 下，文件名多半是 01-netcfg.yaml、50-cloud-init.yaml 这种「数字-名字」的形式，数字决定加载顺序。

静态地址 #

yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    ens33:
      addresses:
        - 192.168.1.151/24
      routes:
        - to: default
          via: 192.168.1.2
      nameservers:
        addresses:
          - 202.38.64.1

逐段拆：

  • version: 2 是必写的格式版本。
  • renderer 决定谁来干活：networkd（服务器默认）或 NetworkManager（桌面默认）。
  • ethernets 下面写各块网卡的配置，键名是你机器上的接口名，不是 eth0。
  • addresses 用 CIDR 写法，/24 就是掩码 255.255.255.0。
  • routes 里 to: default 就是默认路由，via 是网关。老写法 gateway4: 已弃用，别再抄。
  • nameservers 这一段会一路传到 DNS 那一层，比手改 resolv.conf 靠谱。

DHCP #

yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    ens33:
      dhcp4: true

四行搞定。要指定 DHCP 送来的 DNS 不要覆盖某些设置，可以加 dhcp4-overrides，但多数场景用不上。

生效 #

bash
sudo netplan generate    # 只做语法检查并生成后端配置，不应用
sudo netplan apply       # 生成并应用
sudo netplan try         # 应用，等你确认，超时自动回滚

netplan try 值得养成习惯。远程改网络配置，apply 一下地址写错，SSH 直接断线，人就被锁在外面了。netplan try 会问你要不要保留，不确认就回滚到改之前。

YAML 的三个坑 #

第一，缩进只能用空格，不能有 Tab。YAML 对 Tab 零容忍，报错信息还很难看懂。

第二，文件权限。Netplan 要求配置文件权限足够严，太松会直接警告并忽略：

bash
sudo chmod 600 /etc/netplan/*.yaml

第三，同目录多个 YAML 会合并。50-cloud-init.yaml 和 01-netcfg.yaml 都在，谁的数字小谁先加载，后面的覆盖前面的。云主机上自己新建一个文件，被 cloud-init 那份盖回去，是很经典的一种「改了没生效」。

改完还是老地址 #

按这个顺序查：

bash
ip addr show                       # 内核里到底是什么
networkctl status ens33            # networkd 侧认到的配置
sudo netplan generate              # 语法错会在这里报出来
ls /etc/netplan/                   # 是不是有第二份文件在抢

netplan apply 不报错也不生效，九成是文件没被扫到、或者被另一份覆盖了。

六、interfaces 文件 #

/etc/network/interfaces 是 Debian / Ubuntu 老版本的入口，由 ifupdown 包解析。文件名叫 interfaces，读它的是 ifup 和 ifdown，文件头那行 # interfaces(5) file used by ifup(8) and ifdown(8) 说的就是这事。

文件原样 #

ini
auto lo
iface lo inet loopback

auto eth0
iface eth0 inet static
    address 192.168.1.151
    netmask 255.255.255.0
    gateway 192.168.1.2

三组关键字的含义：

  • auto lo：开机自动把 lo 拉起来。
  • iface lo inet loopback：这块接口用 IPv4、回送类型，不需要地址参数。
  • iface eth0 inet static：eth0 用 IPv4、静态地址，下面几行是它的参数。

缩进不影响解析，但统一用四个空格，读起来清楚。掩码这里写点分十进制 255.255.255.0，和 ip 命令的 /24 是两种写法，别混。

DHCP 写法 #

ini
auto eth0
iface eth0 inet dhcp

iface 一行就够，地址全由 DHCP 服务器给。要加自定义 DNS 或者客户端标识，再接参数行。

把 DNS 一起写进这个文件 #

这是素材里最有价值的一条实践。手改 /etc/resolv.conf 会被重写，那就把 DNS 写进 interfaces：

ini
auto lo
iface lo inet loopback

auto eth0
iface eth0 inet static
    address 192.168.1.151
    netmask 255.255.255.0
    gateway 192.168.1.2
    dns-nameservers 202.38.64.1

dns-nameservers 这一行在接口起来时被读取，优先级高于手写的 resolv.conf，网络初始化时会把它写进解析配置。多个 DNS 服务器用空格隔开：

ini
    dns-nameservers 202.38.64.1 8.8.8.8

同一个机制下还有 dns-search（补全搜索域）和 dns-domain（本域声明），需要哪个补哪个。

生效方式 #

bash
sudo service networking restart              # 整机网络
sudo /etc/init.d/networking restart          # 老式的同一件事
sudo systemctl restart networking

sudo ifup eth0                               # 只动一块网卡
sudo ifdown eth0
sudo ifconfig eth0 down
sudo ifconfig eth0 up

只重启单块网卡更好。networking restart 会把所有接口全拆了重建，远程连着的时候等于自断。ifdown eth0 && ifup eth0 只影响 eth0，其他网卡照常跑。

注意 ifdown 之后再 ifup，如果地址配错，这块卡就彻底没配置了。远程操作时用 ifup 前先想好回滚办法。

拨号接口和 PPPoE #

拨号场景的老工具链，素材里的那一套是这么用的。

先确认装没装 pppoe：

bash
rpm -qa | grep pppoe

在 Debian 系上对应的是 dpkg -l | grep pppoe。确认装了之后跑配置向导：

bash
sudo adsl-setup

它会问 ISP 给的账号密码、网卡、DNS，然后把配置写成接口文件：

text
/etc/sysconfig/network-scripts/ifcfg-ppp0

之后看状态、开连接、断连接：

bash
adsl-status          # 看当前连接状态
sudo adsl-start      # 拨上去，等价于 ifup ppp0
sudo adsl-stop       # 挂断，等价于 ifdown ppp0

adsl-start 和 ifup ppp0 是一回事，adsl-stop 和 ifdown ppp0 也一样。这两条路径都指向同一个 ppp0 接口，区别只是前者把拨号细节包了一层。

拨号接口的地址是 PPP 协商出来的，不能写死。所以 ppp0 的配置里没有 address，重点是账号、认证方式和「谁发起拨号」。

七、NetworkManager 与 nmcli #

桌面版和 RHEL 系的主力是 NetworkManager。它有图形界面、有文本界面，也有命令行 nmcli。服务器上不装图形环境，nmcli 就是唯一入口。

nmcli 的语法是固定的三段：nmcli <对象> <动作> <参数>。对象常用的有 device（物理设备）、connection（连接配置）、general（全局状态）。看懂这层，「device 和 connection 有什么区别」这个问题就消了一半。

先看状态 #

bash
nmcli general status              # 总开关、连通性
nmcli device status               # 设备列表：DEVICE / TYPE / STATE / CONNECTION
nmcli connection show             # 连接配置列表：NAME / UUID / TYPE / DEVICE
nmcli connection show "有线连接 1"  # 某个连接的完整参数

device status 里 STATE 是 connected、disconnected、unmanaged 三态：

  • connected：这块设备正被某个连接配置驱动。
  • disconnected：设备在，但没激活任何配置。
  • unmanaged：NetworkManager 不管它，另一个服务在管。看到这个就先别用 nmcli 折腾。

设备（device）是硬件，连接（connection）是一套参数。同一个设备可以挂多套参数，切换就是换一套激活。改参数改的是 connection，不是 device。

配静态地址 #

bash
sudo nmcli connection modify "有线连接 1" \
  ipv4.method manual \
  ipv4.addresses 192.168.1.151/24 \
  ipv4.gateway 192.168.1.2 \
  ipv4.dns "202.38.64.1 8.8.8.8"

sudo nmcli connection up "有线连接 1"

ipv4.method 是关键开关：manual 是静态，auto 是 DHCP。写成 auto 却塞了 ipv4.addresses，地址不会生效。

多个地址就在 ipv4.addresses 里用逗号分隔：

bash
sudo nmcli connection modify "有线连接 1" ipv4.addresses "192.168.1.151/24,192.168.1.152/24"

配 DHCP #

bash
sudo nmcli connection modify "有线连接 1" ipv4.method auto
sudo nmcli connection down "有线连接 1"
sudo nmcli connection up "有线连接 1"

从静态切回 DHCP，要 down 再 up。只 up 有时留着旧地址，因为连接本来就在激活状态，up 变成了空操作。

新建一个连接 #

不想动原来的连接，就新建一套：

bash
sudo nmcli connection add type ethernet con-name eth0-static ifname eth0 \
  ipv4.method manual ipv4.addresses 192.168.1.151/24 \
  ipv4.gateway 192.168.1.2 ipv4.dns 202.38.64.1
sudo nmcli connection up eth0-static

con-name 是这套配置的名字，ifname 绑定的物理设备。删掉用 nmcli connection delete eth0-static。

配置文件在哪 #

NetworkManager 把连接存成 keyfile，路径是 /etc/NetworkManager/system-connections/<连接名>.nmconnection。权限必须是 600，松了 NetworkManager 直接不认。手写这种文件之后要让它重读：

bash
sudo chmod 600 /etc/NetworkManager/system-connections/*.nmconnection
sudo nmcli connection reload
sudo nmcli connection up <连接名>

reload 只重读磁盘上的文件，不激活。改完只 reload 然后发现没变化，原因就在这儿。

不想背参数就用 nmtui #

sudo nmtui 起一个纯文本菜单，方向键选、回车进，改完退出即生效。能力与 nmcli 相同，只是把参数换成了表单，在只有 SSH 的环境里省事。

八、地址、网关与掩码 #

掩码在说什么 #

掩码回答一个问题：这个 IP 里，前多少位是「网络」，后多少位是「主机」。

写法 点分十进制 一个网段能放多少主机 场景
/24 255.255.255.0 254 家用、实验室最常见
/25 255.255.255.128 126 切一半用
/16 255.255.0.0 65534 大内网
/30 255.255.255.252 2 点对点互联

/24 的 254 是怎么来的：256 个地址，减去网络号（.0）和广播地址（.255）。剩下的 .1 到 .254 能分给主机。

掩码决定「直连还是走网关」。192.168.1.151/24 认为 192.168.1.x 全在本地，直接 ARP 找对方；192.168.2.x 不在本地，交给默认网关。掩码错一位，这个判断就整片错掉。

网关必须和地址同网段 #

192.168.1.151/24 配上网关 192.168.10.1，会直接报错或静默不通：

text
RTNETLINK answers: Network is unreachable

理由很直白：网关本身得是「直连可达」的。不在同一网段，内核连怎么把包送到网关都不知道。

素材里那条注意点值得单独拎出来：网关地址要和 VMware Virtual Network Editor 里 NAT Settings... 看到的地址一致，形如 192.168.x.2。虚拟机里配的网关不是随便填的，它由虚拟化软件那侧的虚拟网络决定。

配网关的两条路径：

写进配置文件才是持久的，那一行长这样：

ini
    gateway 192.168.1.2

命令行临时加，重启就丢：

bash
sudo route add default gw 192.168.1.1
sudo ip route add default via 192.168.1.1

一块网卡挂多个 IP #

按体系挑一种。ifupdown 就在同一个 iface 块里重复 address：

ini
iface eth0 inet static
    address 192.168.1.151/24
    address 192.168.1.152/24

ifcfg 脚本体系用子接口文件 /etc/sysconfig/network-scripts/ifcfg-eth0:1：

ini
DEVICE=eth0:1
IPADDR=192.168.1.152
NETMASK=255.255.255.0

Netplan 就是 addresses 列表多写一行：

yaml
      addresses:
        - 192.168.1.151/24
        - 192.168.1.152/24

临时验证用 sudo ip addr add 192.168.1.152/24 dev eth0，重启就没了。

ifcfg 脚本长什么样 #

RHEL 系的单文件写法，素材里给过完整示例，文件是 /etc/sysconfig/network-scripts/ifcfg-eno16777736。逐键解释：

ini
TYPE=Ethernet            # 设备类型
BOOTPROTO=static         # 地址分配模式：static / dhcp / none
NAME=eno16777736         # 网络接口名称
ONBOOT=yes               # 开机是否启用
IPADDR=192.168.10.10     # IP 地址
NETMASK=255.255.255.0    # 子网掩码
GATEWAY=192.168.10.1     # 默认网关
DNS1=192.168.10.1        # DNS 服务器

几个容易忽略的点：

  • 文件名必须和 NAME 一致，ifcfg-eno16777736 对 NAME=eno16777736。
  • ONBOOT=no 意味着开机不激活。手写文件忘了改这一项，重启后网卡躺着不动。
  • BOOTPROTO=dhcp 时，IPADDR、NETMASK、GATEWAY 全部失效，写了也不看。
  • DNS1、DNS2 由这套脚本写进 /etc/resolv.conf。这是它和手改文件不冲突的原因。

改完重载：

bash
sudo systemctl restart network    # 老 RHEL 系
sudo nmcli connection reload      # 由 NetworkManager 接管时

两条默认路由会打架 #

双网卡机器上，两块卡都写了 GATEWAY=，就会出现两条 default 路由。内核按 metric 挑小的用，谁小走谁，另一条基本闲置。

text
default via 192.168.1.2 dev eth0 proto static metric 100
default via 10.0.0.1 dev eth1 proto static metric 101

要让某块卡优先，就把它那条路由的 metric 调小；要彻底避免，只在一块卡上写网关。

九、DNS 配置 #

最终生效的那个文件 #

/etc/resolv.conf 是解析器真正读的地方。格式极简，三个关键字：

关键字 作用 例子
nameserver DNS 服务器地址，可写多个 nameserver 202.38.64.1
search 补全搜索域 search lan local
options 解析器行为 options timeout:2 attempts:2 
ini
nameserver 202.38.64.1
nameserver 8.8.8.8

多个 nameserver 按顺序问，第一个不应答才问第二个。所以把快的、内网的放前面。校园网环境里填校园网的 DNS，内网域名才解析得出来；8.8.8.8 解析不了只在内网存在的名字。

options timeout:2 attempts:2 是超时 2 秒、重试 2 次。默认值偏长，DNS 服务器挂了的时候，一条 ping 会卡好几秒，把这两项调小能明显感觉出差别。

它为什么会被重写 #

这是本篇第三个高频困惑：改完 resolv.conf，重启或者重连网络之后，内容变回去了。

原因是有别的程序在管这个文件。它会自己算出一份 DNS 配置，覆盖写入。文件开头的注释多半直接写着是谁干的，先看那段注释：

bash
head -5 /etc/resolv.conf

谁来写，决定了该改哪里：

谁在管 正确改法
ifupdown interfaces 里加 dns-nameservers
Netplan YAML 里写 nameservers.addresses
NetworkManager nmcli con mod ... ipv4.dns
systemd-resolved 改 resolved 的配置，或关掉接管
DHCP 客户端 改 /etc/dhcp/dhclient.conf 的 supersede

素材里的那条实践对应第一行：把 dns-nameservers 202.38.64.1 写进 interfaces，接口起来时它会盖过手写的 resolv.conf，因为它在网络初始化的流程里执行，晚于你的手工编辑。

systemd-resolved 那一层 #

现代发行版上常见的一个局面：/etc/resolv.conf 根本不是文件，是个符号链接。ls -l /etc/resolv.conf 的输出是：

text
lrwxrwxrwx 1 root root 39 ... /etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf

链接指向 stub-resolv.conf，里面写的是 nameserver 127.0.0.53。这是 systemd-resolved 在本机开的桩（stub）监听器，解析请求先到它，它再按自己的配置转发出去。手改这个文件，改的是链接指向的运行时文件，重启就重生成。真正的配置在 resolved 那边：

bash
resolvectl status                 # 看每块网卡实际用的 DNS
resolvectl query www.example.com  # 用当前配置解析一次
sudo resolvectl flush-caches      # 清缓存

resolvectl status 会列出每个 link 上的 DNS Servers 和 DNS Domain，核对 DNS 到底用谁，看这里最直接。想让静态 DNS 稳住有两条路：一是 sudo systemctl disable --now systemd-resolved，删掉链接、自己写 resolv.conf；二是不动 resolved，用它的机制配，Netplan 的 nameservers 会流到它这里。

关掉接管有个副作用：127.0.0.53:53 不再监听，有些程序或容器网络依赖它做本地解析，关之前确认没有这种依赖。

/etc/hosts 与解析顺序 #

/etc/hosts 是本地静态表，格式是「IP 主机名 别名」：

ini
127.0.0.1   localhost
::1         localhost ip6-localhost
192.168.1.20 myserver

加上最后那行之后，ping myserver 直接命中 192.168.1.20，一次 DNS 查询都不发。内网几台机器互相访问，写 hosts 比搭 DNS 省事得多。

谁先谁后由 /etc/host.conf 和 /etc/nsswitch.conf 决定。前者的内容是：

ini
order hosts,bind
multi on

order hosts,bind 是先查 hosts、再问 DNS。/etc/nsswitch.conf 里对应的一行是：

text
hosts:      files dns

files 是 hosts，dns 是 DNS。两处说法不同，含义一致。

解析顺序带来的一个经典现象：DNS 服务器上把 myserver 指到了新地址，本机却还通到老地址。十成是 hosts 里那条旧记录还在，hosts 优先级更高。排这种问题先看 hosts，再看 DNS。

验证 DNS 到底通不通 #

分四步走，一步定位一层：

bash
ping -c 3 202.38.64.1        # 1. DNS 服务器本身通不通（IP 层）
getent hosts www.baidu.com   # 2. 用系统的解析顺序试一次
nslookup www.baidu.com       # 3. 单独试 DNS 解析
dig @202.38.64.1 www.baidu.com +short   # 4. 指定服务器问，绕开本机配置

第 1 步不通，是网络问题，跟 DNS 无关。第 1 步通、第 2 步不通，是解析配置问题，回头看 resolv.conf 和 hosts。第 3 步通、第 4 步不通，说明那台 DNS 服务器不对外服务。

getent hosts 比 nslookup 更贴近真实——它走的就是程序实际会走的那条 nsswitch 路径。

十、虚拟机的三种网络模式 #

虚拟机里的网络配不通，一半原因不在 Linux 里，在虚拟化软件选的那个模式上。三种模式的差别只有一句话：虚拟机的流量从哪个口出宿主机。

模式 虚拟机地址 能不能上网 外部能不能访问虚拟机 VMware 虚拟网络
桥接 Bridge 与宿主机同网段，占局域网一个 IP 能 能 VMnet0
NAT 私有网段，由虚拟 DHCP 分配 能 不能，除非做端口转发 VMnet8
Host-Only 私有网段，主机当网关 不能 只有宿主机能访问 VMnet1

桥接 Bridge #

虚拟机与宿主机共享同一个物理网络，虚拟机像是局域网里多出来的一台真机。它在主机所在网段里拿地址，网关和 DNS 与主机一致，对外直接通信。

DHCP 情况下，虚拟机会向主机所在网络里的 DHCP 服务器请求地址，拿到什么就是什么。手动指定时要注意三件事对齐：

  • 地址落在主机所在网段，且没被别人占用。
  • 网关与主机的网关相同。
  • DNS 与主机可用的一致。

桥接的代价是占一个局域网 IP。实验室、办公室这种 IP 紧张又有人管的环境，多开几台虚拟机就要报备。

NAT #

宿主机会多出一块隐藏网卡，充当虚拟机的出口。虚拟机的网卡从这块网卡后面的虚拟 DHCP 服务拿地址。

素材里的实例：宿主机侧那块网卡地址是 192.168.153.2，虚拟机侧就该是：

项目 值
IP 地址 192.168.153.139
子网掩码 255.255.255.0
网关 192.168.153.2
DNS 192.168.153.2

网关和 DNS 都指宿主侧那块网卡，因为它既是出口也是转发 DNS 的那一跳。虚拟机发出的包经它做地址转换，对外表现为宿主机的地址，所以外部主动连不进来。

NAT 的地址由虚拟 DHCP 发，让它自动获取最省事。手动写也行，前提是同网段、网关和 DNS 都指向宿主侧那块网卡。

Host-Only #

结构与 NAT 相同，区别是不做地址转换，主机是唯一的网关。虚拟机只能和主机交换数据，出不了这台机器。

它的用途是隔离：几台虚拟机互相通信、和主机通信，但完全不接触外网。做集群实验、内网服务测试，用这个模式不会被外部流量干扰。

该选哪个 #

你要干的事 选
开发板要直连虚拟机、双向访问 桥接
虚拟机只上网，不想占局域网 IP NAT
虚拟机之间搭内网实验 Host-Only
从别的电脑 SSH 到虚拟机 桥接
虚拟机里跑服务给自己调试 NAT + 端口转发，或 Host-Only

开发板连虚拟机这个场景，答案基本固定：桥接。开发板是网络里的一台真设备，它要主动找到虚拟机，就得和虚拟机在同一网段，双方都能互访。NAT 模式下虚拟机的地址在宿主机内部，开发板根本路由不到。

新装虚拟机默认走桥接，装完建议手动指定一个固定 IP。NAT 模式下反过来，让地址自动获取更省事。

十一、配置完了怎么验证 #

验证要分层做，从下往上。跳层会误判——直接 ping www.baidu.com 失败，你分不清是网卡没起、地址错了、网关错了，还是 DNS 错了。

层 命令 通过的标准
网卡 ip link show eth0 有 state UP
地址 ip -4 addr show eth0 地址和前缀正确
网关 ping -c 3 <网关> 有回包
出网 ping -c 3 8.8.8.8 有回包
DNS ping -c 3 www.baidu.com 域名被解析成 IP 且有回包
服务 ss -tuln 目标端口在 LISTEN

一条条的写法 #

bash
ip link show eth0                            # 接口状态
ip addr show eth0                            # 地址
ip route show                                # 默认路由在不在
ip route get 8.8.8.8                         # 去某个地址走哪条
ping -c 3 192.168.1.2                        # 网关
ping -c 3 8.8.8.8                            # 出网
ping -c 3 www.baidu.com                      # 域名
resolvectl status                            # 每块网卡实际用的 DNS
getent hosts www.baidu.com                   # 按系统解析顺序试一次
ss -tuln                                     # 本机在监听什么端口

ping 的层次感值得记住：能 ping 通 IP、ping 不通域名，就是 DNS 的事，别再折腾网关。

老命令也能用 #

素材里那套 ifconfig / netstat / traceroute / tcpdump 仍然能用，装上 net-tools 就能跑：

bash
ifconfig                  # 所有接口的地址、掩码、MAC、状态
netstat -tuln             # 监听端口
route -n                  # 路由表
traceroute www.example.com   # 逐跳路径，看在哪一跳断
tcpdump -i eth0           # 抓包，看包到底发没发出去

traceroute 显示每一跳的 IP，卡在第几跳就说明问题在那一段。tcpdump -i eth0 能看到本机到底有没有把包发出去——这是判断「配置问题」还是「对端问题」的分水岭。

这几条命令的完整用法在 03-协议栈与内核实现 的「网络命令与排错基础」里，本篇只借它们验证配置结果。

最后一步：重启再验 #

临时配置在重启前一切正常，重启后一片空白。这是最容易骗过自己的一次验证。

bash
sudo reboot

起来之后重新跑一遍：

bash
ip addr show
ip route show
cat /etc/resolv.conf
ping -c 3 www.baidu.com

只有重启后四条还成立，才算真配好了。这一步不做，等于没配持久化。

十二、易错点速查 #

现象 最常见的原因 处置
配好了能上网，重启后没了 用的是 ip / ifconfig 临时配置 写配置文件，重载
改了文件，ip addr 没变化 文件拿错（Netplan / interfaces / nmcli）或没重载 先判断哪套在管，再改再重载
改完 resolv.conf，一会儿又变回去 被 systemd-resolved / NetworkManager 接管 改上游配置，或关掉接管
ping IP 通，ping 域名不通 DNS 地址错，或 hosts 里有旧记录 查 resolv.conf 与 /etc/hosts
报 Network is unreachable 网关不在本机网段 网关改成同网段地址
同网段两台机器互相不通 掩码写错，把对方划到网段外 核对前缀与点分写法
抄了 eth0，命令报设备不存在 机器用的是 ens33 / enp0s3 ip link 看真实名字
Netplan 改了不生效 YAML 里有 Tab，或文件权限太松，或多份文件互相覆盖 netplan generate 看报错，chmod 600
两块网卡都有 default 路由 两条默认路由抢道 只留一条，或用 metric 分优先级
ifdown 之后连不上了 地址配错，接口没再起来 有带外手段再动，或先备好回滚
开发板连不上虚拟机 虚拟机用了 NAT 改桥接，同网段固定地址
命令全部 Permission denied 忘了 sudo 加 sudo 重来

排查的固定顺序 #

撞上任何一个，按这个顺序走，别跳：

text
1. ip link show          接口起来了没
2. ip addr show          地址对不对
3. ip route show         默认路由在不在
4. ping 网关              二层三层通不通
5. ping 8.8.8.8          出网通不通
6. ping 域名              DNS 通不通
7. tcpdump -i eth0       包到底出没出去

前六步都是本机视角，第七步开始看线上的真实流量。卡在第七步，问题就不在这台机器的配置里了。
