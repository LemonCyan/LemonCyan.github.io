网桥转发落到内核代码里是一条很短的链。一个帧从端口进来，先记下源 MAC，再拿目的 MAC 去查表，查到就从对应端口发出去，查不到就往别的端口各送一份。这条链一句话说完：学源、查目的、查不到就泛洪。

本篇只讲这条链怎么跑起来：函数从哪进、表在哪查、帧往哪送、哪一步被丢掉。

讲什么

  • 网桥怎么把端口的收包流劫持进 br_handle_frame
  • 三个结构体：net_bridge、net_bridge_port、net_bridge_fdb_entry
  • 主线函数链：br_handle_frame → br_handle_frame_finish → br_forward / br_flood_forward / br_pass_frame_up
  • FDB 的学、查、老化
  • 转发决策的每个分支和判据

不讲什么

  • 网桥是什么、学习/转发/泛洪三个动作的概念、FDB 表怎么读，去《链路层与网桥基础》
  • 802.1Q 帧格式、PVID、tagged/untagged 规则，去《VLAN 原理》和《VLAN 源码》
  • STP 状态机、BPDU 字段、根桥选举，本篇只在代码里撞见 p->state 时交代一句
  • 驱动到 netif_receive_skb 的完整路径，去《数据收发路径》
  • 本地发出的帧走 NF_BR_LOCAL_OUT，本篇只标位置

一、从收包到转发 #

先看全景。这张图只画主干，中途被丢弃的帧不标——我们约定帧一路发成功，先把链路跑通。

text
驱动 → netif_receive_skb() → __netif_receive_skb_core()
  ├─ skb->dev->rx_handler 存在?
  │    └─ 是 → br_handle_frame()
  │         ├─ 保留地址 → NF_BR_LOCAL_IN → __br_handle_local_finish()
  │         └─ 普通帧，看 p->state → NF_BR_PRE_ROUTING
  │              └─ br_handle_frame_finish()
  │                   ├─ 学源   br_fdb_update()
  │                   ├─ 查目的 __br_fdb_get()
  │                   ├─ 命中 → br_forward() → __br_forward()
  │                   │    └─ NF_BR_FORWARD → br_forward_finish()
  │                   │         └─ NF_BR_POST_ROUTING
  │                   │              └─ br_dev_queue_push_xmit() → dev_queue_xmit()
  │                   ├─ 未命中 → br_flood_forward() → br_flood() → __br_forward() ×N
  │                   └─ 目的为本机 → br_pass_frame_up()
  │                        └─ NF_BR_LOCAL_IN → br_netif_receive_skb()
  │                             └─ netif_receive_skb()
  └─ 否 → 按 skb->protocol 交给 ip_rcv 等协议处理函数

从上往下走一遍。

第一步，skb 从驱动出来，进到 __netif_receive_skb_core 撞上第一个岔路口：看自己身上有没有 skb->dev->rx_handler。有，就进 br_handle_frame；没有，直接按协议号上交协议栈。

第二步，br_handle_frame 里还有岔路。这个函数只干一件事——判断这一帧该走哪条路，然后把它塞进对应的 netfilter 钩子点。两条路是 NF_BR_PRE_ROUTING 和 NF_BR_LOCAL_IN。链路本地地址（BPDU、LLDP 这类）走本地那条；判断不了去处的普通帧先走 NF_BR_PRE_ROUTING。

第三步，NF_BR_PRE_ROUTING 后面的函数是 br_handle_frame_finish。这一帧的命运在这里定：转发、泛洪、还是上交本机。

第四步，转发分支要再过 NF_BR_FORWARD、NF_BR_POST_ROUTING，最后 dev_queue_xmit 出网卡。上交本机的分支重新进 NF_BR_LOCAL_IN，回到 netif_receive_skb 让上层协议处理。本机发出的帧走另一条路：NF_BR_LOCAL_OUT → NF_BR_POST_ROUTING → 发出。

五个钩子点的位置

钩子点 代码里的位置 谁在用
NF_BR_PRE_ROUTING br_handle_frame → br_handle_frame_finish 之间 ebtables prerouting 链；br_netfilter 加载后是 IP 层第一道门
NF_BR_LOCAL_IN br_handle_frame 本地分支；br_pass_frame_up 里 ebtables input 链
NF_BR_FORWARD __br_forward → br_forward_finish 之间 ebtables forward 链
NF_BR_POST_ROUTING br_forward_finish → br_dev_queue_push_xmit 之间 ebtables postrouting 链
NF_BR_LOCAL_OUT 本机发包路径 ebtables output 链

NFPROTO_BRIDGE 这一族钩子是给 ebtables 用的。ebtables 能过滤和改写任意类型的以太帧，不限于带 IP 头的那些。br_handle_frame 和 br_handle_frame_finish 这两个回调，只在 netfilter 没有把帧丢掉或吃掉时才会被执行。

一个容易看漏的点：NF_BR_PRE_ROUTING 上挂的函数不一定是 br_handle_frame_finish 本身。装了 br_netfilter 之后，这一位是 br_nf_pre_routing，它做完 IP 层的 conntrack 和 NAT 前置检查，再回调 br_nf_pre_routing_finish，最后才走到 br_handle_frame_finish。

二、网桥的数据结构 #

转发状态全挂在三个结构体上。看代码之前先把它们认全，后面每个函数都在这些字段上取东西。

2.1 skb 里跟桥有关的字段 #

字段 桥怎么用它
skb->dev 这一帧属于哪个设备。进桥时是物理端口，br_pass_frame_up 里被换成桥设备
skb->protocol 以太类型。br_handle_frame_finish 用它判 ARP，决定要不要走 proxy ARP
skb->pkt_type 目的 MAC 等于桥自己的 MAC 时被改成 PACKET_HOST
skb->data 指向以太头，h_source / h_dest 从这里取
skb->vlan_tci 携带的 VLAN tag，br_handle_vlan 决定清不清
BR_INPUT_SKB_CB(skb)->brdev 桥的私有控制块，存桥设备指针
BR_INPUT_SKB_CB(skb)->vlan_filtered 入口做没做过 VLAN 过滤

BR_INPUT_SKB_CB 挂在 skb->cb 上，只有 brdev 和 vlan_filtered 两个字段有用。

2.2 net_bridge #

一个网桥一个 net_bridge，放在桥设备的私有区，netdev_priv(br0) 拿到。

c
struct net_bridge {
    spinlock_t              lock;
    spinlock_t              hash_lock;          /* 保护 FDB 哈希表 */
    struct list_head        port_list;          /* 所有端口 */
    struct net_device       *dev;               /* 桥设备，比如 br0 */
    struct pcpu_sw_netstats __percpu *stats;
    struct hlist_head       hash[BR_HASH_SIZE]; /* FDB 哈希桶，256 个 */
    unsigned long           ageing_time;        /* 老化时间，默认 300 秒 */
    struct delayed_work     gc_work;            /* 老化定时器载体 */
    u16                     group_fwd_mask;          /* 允许放行的保留地址位 */
    u16                     group_fwd_mask_required; /* 内核强制放行位 */
    bridge_id               designated_root;
    bridge_id               bridge_id;
    unsigned                root_path_cost;
    unsigned char           stp_enabled;
    unsigned long           forward_delay;      /* 默认 15 秒 */
    struct net_bridge_vlan_group *vlgrp;
    u16                     default_pvid;
    bool                    vlan_enabled;
    bool                    multicast_enabled;
    bool                    vlan_stats_enabled;
    /* ... */
};

hash 是转发性能的关键。查表就是拿目的 MAC 算个哈希值，落到 256 个桶里的一个，桶内链表大多只有两三个元素，所以查表是常数级操作，不随端口数增长。

ageing_time 和 gc_work 决定表项能活多久、谁去清理。默认 300 秒，也就是 5 分钟。

group_fwd_mask 决定哪些该被本地吃掉的保留地址可以破例转发出去。默认只放行 802.1X 需要的位。

2.3 net_bridge_port #

一个端口一个 net_bridge_port，是桥和物理设备之间的粘合层。br_add_if 时分配，br_del_if 时释放。

c
struct net_bridge_port {
    struct net_bridge       *br;        /* 属于哪个桥 */
    struct net_device       *dev;       /* 物理设备，比如 eth0 */
    struct list_head        list;       /* 挂在 br->port_list 上 */
    unsigned long           flags;      /* BR_LEARNING / BR_FLOOD / BR_HAIRPIN_MODE */
    u16                     port_no;    /* 端口号，STP 用 */
    unsigned char           state;      /* DISABLED / BLOCKING / LISTENING /
                                           LEARNING / FORWARDING */
    u16                     priority;
    u32                     path_cost;
    u16                     group_fwd_mask;  /* 端口级放行位，和桥级取或 */
    bridge_id               designated_root;
    bridge_id               designated_bridge;
    u16                     designated_port;
    u32                     designated_cost;
    unsigned long           designated_age;
    bool                    topology_change_ack;
    struct timer_list       message_age_timer;
    struct timer_list       forward_delay_timer;
    u8                      multicast_router;
    struct rcu_head         rcu;
    /* ... */
};

三个字段要盯住。

state 是端口的 STP 状态，转发决策里出现频率最高。BR_STATE_FORWARDING 才允许转发，BR_STATE_LEARNING 只学不发，BR_STATE_DISABLED 直接丢。

flags 是功能开关，和 state 完全两码事。state 说端口处在哪个 STP 阶段，flags 说这个端口被允许干哪些事。BR_LEARNING 没置位就不学源 MAC；BR_FLOOD 没置位，单播泛洪时跳过它。

port_no 只在 STP 和日志里有意义，转发路径不看它。

2.4 net_bridge_fdb_entry #

FDB 表项，一个 MAC 一条。

c
struct net_bridge_fdb_entry {
    struct hlist_node       hlist;      /* 挂在 br->hash[hash] 桶上 */
    struct net_bridge_port  *dst;       /* 这个 MAC 在哪个端口后面 */
    unsigned long           updated;    /* 最后一次刷新，老化靠它 */
    unsigned long           used;       /* 最后一次被转发命中，统计用 */
    mac_addr                addr;
    __u16                   vid;        /* 属于哪个 VLAN，0 表示不过滤 */
    unsigned char           is_local:1,       /* 桥自己的 MAC */
                            is_static:1,      /* 手工配置，不老化 */
                            added_by_user:1,
                            added_by_external_learn:1;
    struct rcu_head         rcu;
};

dst 是转发落点，br_forward(dst->dst, skb, skb2) 里那个参数就是它。is_local 标记桥自己的地址，这类表项查到时不该转发、该上交。is_static 是 bridge fdb add ... static 配出来的，永不过期。

老内核里两个时间字段叫 ageing 和 used，字段名统一成 updated / used 是新一点的内核干的事。你手上的代码如果写的是 dst->used = jiffies，那是老内核。

2.5 三个结构体的关系 #

text
net_bridge (br0)
 ├── dev ──────────────→ net_device (br0 这个虚拟设备)
 ├── port_list
 │    ├── net_bridge_port (port_no=1) ── dev ──→ net_device (eth0)
 │    ├── net_bridge_port (port_no=2) ── dev ──→ net_device (eth1)
 │    └── net_bridge_port (port_no=3) ── dev ──→ net_device (eth2)
 └── hash[256]
      ├── fdb_entry: 52:54:00:aa:bb:cc → dst = port(eth0)
      ├── fdb_entry: br0 自己的 MAC     → dst = NULL, is_local=1
      └── fdb_entry: 52:54:00:dd:ee:ff → dst = port(eth2)

两条连线：端口结构体单向指向桥，FDB 表项单向指向端口。查表拿到表项，表项里的 dst 就是出口端口。

is_local 的表项 dst 是 NULL，因为没有「去哪个端口」这回事，它代表桥自己。代码里判的是 dst->is_local，不是 dst 是否为空。

三、net_bridge 与 net_bridge_port #

结构体是死的，把 eth0 加进 br0 的那一刻才被串起来。这一步在 br_add_if 里做完，转发链的起点也在这里埋下。

c
int br_add_if(struct net_bridge *br, struct net_device *dev)
{
    struct net_bridge_port *p;
    int err = 0;
    /* 只允许以太网设备，回环口、非 6 字节地址一律拒绝 */
    if ((dev->flags & IFF_LOOPBACK) || dev->type != ARPHRD_ETHER ||
        dev->addr_len != ETH_ALEN || !is_valid_ether_addr(dev->dev_addr))
        return -EINVAL;
    if (dev->netdev_ops->ndo_start_xmit == br_dev_xmit)
        return -ELOOP;                       /* 不许桥套桥 */
    if (br_port_exists(dev))
        return -EBUSY;                       /* 已经是某个桥的端口了 */
    if (dev->priv_flags & IFF_DONT_BRIDGE)
        return -EOPNOTSUPP;                  /* 部分无线驱动声明不可桥接 */
    p = new_nbp(br, dev);                    /* 分配并初始化端口结构体 */
    if (IS_ERR(p))
        return PTR_ERR(p);
    call_netdevice_notifiers(NETDEV_JOIN, dev);
    /* 端口设备被强制拉进混杂模式 */
    err = dev_set_promiscuity(dev, 1);
    if (err)
        goto put_back;
    err = br_sysfs_addif(p);                 /* /sys/class/net/eth0/brport/ */
    if (err)
        goto err2;
    /* 先把端口自己的 MAC 作为 local 表项塞进 FDB */
    err = br_fdb_insert(br, p, dev->dev_addr, 0);
    if (err)
        goto err3;
    /* 注册设备接收帧函数：把 eth0 的收包流交给 br_handle_frame */
    err = netdev_rx_handler_register(dev, br_handle_frame, p);
    if (err)
        goto err4;
    dev->priv_flags |= IFF_BRIDGE_PORT;
    /* 挂到桥的端口链表，到这一步它才真的属于这个桥 */
    list_add_rcu(&p->list, &br->port_list);
    br_stp_recalculate_bridge_id(br);        /* 桥 MAC 取端口里最小的那个 */
    br_fdb_update(br, p, dev->dev_addr, 0, false);
    netdev_update_features(br->dev);
    return 0;
    /* ... 错误回滚 ... */
}

顺序有讲究，四步是关键。

dev_set_promiscuity(dev, 1) 让端口进混杂模式。网桥必须这样：端口要收所有目的 MAC 的帧，否则目的 MAC 不是它自己的帧在网卡那一层就被丢了，桥根本没有机会学到东西。所以桥下所有设备都是混杂模式。桥设备 br0 自己不是——只有用户明确 ip link set br0 promisc on 才进。

br_fdb_insert(br, p, dev->dev_addr, 0) 把端口 MAC 登记成 is_local 表项。作用很直接：别人发帧给 eth0 的 MAC，桥知道这是本机地址，该上交而不是转发。

netdev_rx_handler_register 换掉收包入口。这是全篇的枢纽。

list_add_rcu(&p->list, &br->port_list) 之后，泛洪时才会遍历到这个端口。

3.1 netdev_rx_handler_register 逐行 #

c
int netdev_rx_handler_register(struct net_device *dev,
                               rx_handler_func_t *rx_handler,
                               void *rx_handler_data)
{
    ASSERT_RTNL();
    if (dev->rx_handler)
        return -EBUSY;
    /* Note: rx_handler_data must be set before rx_handler */
    /* 把 rx_handler_data 指向第三个参数，在 br_add_if 里就是 p，端口结构体 */
    rcu_assign_pointer(dev->rx_handler_data, rx_handler_data);
    /* 把 dev->rx_handler 指向 br_handle_frame */
    rcu_assign_pointer(dev->rx_handler, rx_handler);
    return 0;
}

两行赋值，一个 -EBUSY。-EBUSY 的意思是「一个设备只能有一个 rx_handler」，所以同一个网口不能被两个网桥抢，也不能同时挂给 bridge 和 macvlan 抢收包权。

顺序注释说的是：rx_handler_data 必须先写。rx_handler 一旦可见，别的 CPU 立刻就会通过 br_handle_frame 去读 rx_handler_data，读到 NULL 就崩了。rcu_assign_pointer 保证写指针的动作对其他 CPU 要么完全可见要么完全不可见，配合读侧的 rcu_dereference 就能安全并发。

3.2 rx_handler_data 指向谁 #

这一条最容易搞混。

指针 指向 谁写
eth0->rx_handler br_handle_frame 函数 br_add_if
eth0->rx_handler_data eth0 的 net_bridge_port br_add_if
br0->rx_handler NULL 没人写

所以 br_handle_frame 里那句 p = br_port_get_rcu(skb->dev) 就是读 skb->dev->rx_handler_data，拿到的是入帧那个物理端口的 net_bridge_port，不是桥的。有了 p，p->br 就是桥，p->state 是端口状态，p->flags 是端口功能位。

注册 rx_handler 的是桥下的设备，不是桥设备。br0 自己没有注册过 rx_handler——这一条在后面「不二次进桥」里还会用到。

3.3 br_del_if 的反向拆解 #

反向操作是 br_del_if：br_fdb_delete_by_port 删掉指向这个端口的表项，netdev_rx_handler_unregister 把 rx_handler 置空，dev_set_promiscuity(dev, -1) 退出混杂模式，list_del_rcu 摘下链表。

br_fdb_delete_by_port 必须做。端口拔掉以后，指向它的表项全是黑洞——查表命中、转发时端口已不存在，帧直接进坑。顺序也要注意：先删表项再注销 rx_handler，否则中间那一小段时间里还有帧在往这个端口查表。

四、br_handle_frame #

br_handle_frame 是帧进入网桥的总入口。它干两件事：分拣、塞进钩子点。分拣的判据全写在代码里。

c
/* note: already called with rcu_read_lock */
rx_handler_result_t br_handle_frame(struct sk_buff **pskb)
{
    struct net_bridge_port *p;
    struct sk_buff *skb = *pskb;
    const unsigned char *dest = eth_hdr(skb)->h_dest;
    br_should_route_hook_t *rhook;
    /* 回环包不归桥管，原样放行 */
    if (unlikely(skb->pkt_type == PACKET_LOOPBACK))
        return RX_HANDLER_PASS;
    /* 源 MAC 是否合法：不是组播地址，也不是全 0 地址 */
    if (!is_valid_ether_addr(eth_hdr(skb)->h_source))
        goto drop;
    /* 共享 skb 先克隆，因为后面既要转发又要上交 */
    skb = skb_share_check(skb, GFP_ATOMIC);
    if (!skb)
        return RX_HANDLER_CONSUMED;
    /* 取入帧端口的信息 */
    p = br_port_get_rcu(skb->dev);
    /* BPDU 这类保留地址，目标 MAC 落在 01:80:C2:00:00:0x */
    if (unlikely(is_link_local_ether_addr(dest))) {
        u16 fwd_mask = p->br->group_fwd_mask_required;
        switch (dest[5]) {
        case 0x00:  /* Bridge Group Address，也就是 STP 的 BPDU */
            /* 关掉 STP 时必须转发，否则环路检测没戏 */
            if (p->br->stp_enabled == BR_NO_STP ||
                fwd_mask & (1u << dest[5]))
                goto forward;
            *pskb = skb;
            __br_handle_local_finish(skb);
            return RX_HANDLER_PASS;
        case 0x01:  /* IEEE MAC (Pause)，802.3 流控帧 */
            goto drop;
        case 0x0E:  /* 802.1AB LLDP */
            fwd_mask |= p->br->group_fwd_mask;
            if (fwd_mask & (1u << dest[5]))
                goto forward;
            *pskb = skb;
            __br_handle_local_finish(skb);
            return RX_HANDLER_PASS;
        default:
            /* 其余保留地址按 group_fwd_mask 选择性转发 */
            fwd_mask |= p->br->group_fwd_mask;
            if (fwd_mask & (1u << dest[5]))
                goto forward;
        }
        /* 只投递给本机，不再转发 */
        NF_HOOK(NFPROTO_BRIDGE, NF_BR_LOCAL_IN, dev_net(skb->dev),
                NULL, skb, skb->dev, NULL, br_handle_local_finish);
        return RX_HANDLER_CONSUMED;
    }
forward:
    switch (p->state) {
    case BR_STATE_FORWARDING:
        /* ebtables 拿路由的 hook 点 */
        rhook = rcu_dereference(br_should_route_hook);
        if (rhook) {   /* 转发状态下先让 hook 表态 */
            if ((*rhook)(skb)) {
                *pskb = skb;
                return RX_HANDLER_PASS;
            }
            dest = eth_hdr(skb)->h_dest;   /* hook 改过目的 MAC 的话重新取 */
        }
        /* fall through */
    case BR_STATE_LEARNING:
        /* 目的地址是否是桥设备自己的链路层地址 */
        if (ether_addr_equal(p->br->dev->dev_addr, dest))
            skb->pkt_type = PACKET_HOST;
        /* 将数据包送入帧处理函数 br_handle_frame_finish */
        NF_HOOK(NFPROTO_BRIDGE, NF_BR_PRE_ROUTING,
                dev_net(skb->dev), NULL, skb, skb->dev, NULL,
                br_handle_frame_finish);
        break;
    default:
drop:
        kfree_skb(skb);
    }
    return RX_HANDLER_CONSUMED;
}

4.1 返回值 #

rx_handler 的返回值决定 __netif_receive_skb_core 接下来干什么，所以每个分支都得给一个明确态度。

返回值 含义 内核接下来做什么
RX_HANDLER_CONSUMED 帧被接手了 释放 skb 引用，返回
RX_HANDLER_PASS 桥不管，继续走普通流程 回到主流程，按 ptype 分发
RX_HANDLER_ANOTHER 换个设备重新来一遍 goto another_round，重跑整个 core

br_handle_frame 只用前两个。转发、泛洪、上交本机都在函数内部把帧送走了，送完返回 CONSUMED；保留地址放行给上层的情况返回 PASS。另外两个（ANOTHER、EXACT）是 macvlan、bond 这类设备用的，桥不碰。

4.2 为什么保留地址要先判断 #

is_link_local_ether_addr(dest) 判的是 01:80:C2:00:00:00 到 01:80:C2:00:00:0F 这一段，IEEE 802.1D 划的保留地址。桥必须对它们格外小心：BPDU 是 STP 的心跳，不能被当成普通数据帧泛洪出去，也不能被学进 FDB。

代码按 dest[5] 分情况：

dest[5] 地址 处理
0x00 Bridge Group Address（STP BPDU） 关 STP 或 fwd_mask 对应位为 1 时转发，否则交本机
0x01 MAC Control（802.3 流控 Pause） 直接丢
0x02 Link Aggregation 走 default，看 group_fwd_mask
0x03 802.1X PAE 走 default
0x0E 802.1AB LLDP 看 group_fwd_mask，放行就转发，否则交本机
其他 保留 看 group_fwd_mask

group_fwd_mask 就是给这些地址开的口子。要在桥两边跑 LLDP，就 echo 0x4000 > /sys/class/net/eth0/brport/group_fwd_mask（1 << 14 对应 0x0E）。不开的话 LLDP 帧全被桥吃掉，邻居看不到。

group_fwd_mask_required 是内核强制的位，用户改不了，和用户配的 group_fwd_mask 取或。

4.3 state 分支：转发、学习、丢弃 #

forward 标签之后是 p->state 的 switch，只有三个出口。

BR_STATE_FORWARDING——正常转发态。先给 br_should_route_hook 一次机会，这是 br_netfilter 装的钩子，让桥接的 IP 帧走一遍 IP 路由。hook 返回真表示它自己处理了，帧返回 PASS；返回假表示照样走桥的路径。hook 之后重新取一次 dest，因为 hook 改过目的 MAC 的话，原先那个指针就指向旧内容了。

BR_STATE_LEARNING——只学不发。代码里和 FORWARDING 走同一段 fall through，靠 br_handle_frame_finish 里那句 if (p->state == BR_STATE_LEARNING) goto drop; 把转发拦下。学习态的帧能学到源 MAC，但不会转发出去。

default——DISABLED、BLOCKING、LISTENING 全落到 drop，kfree_skb。这三个状态在 STP 里各有含义，对转发路径来说结果一样：不发。

进 br_handle_frame_finish 之前还有一句 ether_addr_equal(p->br->dev->dev_addr, dest)。目的 MAC 等于桥自己的 MAC 时把 pkt_type 改成 PACKET_HOST，上层协议栈收到的就是一个「发给我」的帧。这一句不改，桥设备上的 IP 收不到直连广播以外的单播。

4.4 两个 finish 回调 #

保留地址分支走 __br_handle_local_finish，它是不经过钩子点的内部版本，负责把 BPDU、LLDP 这类本地帧喂给 STP 状态机。普通帧分支走 br_handle_frame_finish，负责学源、查目的、决定去向。带不带钩子的版本区别只有一个：br_handle_local_finish 挂在 NF_BR_LOCAL_IN 后面，__br_handle_local_finish 不走 netfilter。这两个回调只在 netfilter 没把帧丢掉或吃掉时才执行。

五、收包路径的入口 #

br_handle_frame 是怎么被调到的？答案在 __netif_receive_skb_core。它是收包后半段的总调度，每个帧都要过一遍，网桥就在这儿插了一脚。

c
static int __netif_receive_skb_core(struct sk_buff **pskb, bool pfmemalloc)
{
    struct sk_buff *skb = *pskb;
    struct packet_type *ptype, *pt_prev = NULL;
    rx_handler_func_t *rx_handler;
    struct net_device *orig_dev = skb->dev;
another_round:
    /* 抓包钩子：AF_PACKET 的 ptype_all 先拿一份，tcpdump 靠这一段 */
    list_for_each_entry_rcu(ptype, &ptype_all, list) { /* ... */ }
    list_for_each_entry_rcu(ptype, &skb->dev->ptype_all, list) { /* ... */ }
    /* 剥 802.1Q 头，把 VID 塞进 skb->vlan_tci */
    if (skb->protocol == htons(ETH_P_8021Q) || /* ... */) { /* ... */ }
    /* 桥的落脚点就在这几行 */
    rx_handler = rcu_dereference(skb->dev->rx_handler);
    if (rx_handler) {
        if (pt_prev) {
            deliver_skb(skb, pt_prev, orig_dev);
            pt_prev = NULL;
        }
        switch (rx_handler(&skb)) {
        case RX_HANDLER_CONSUMED:
            ret = NET_RX_SUCCESS;
            goto unlock;          /* 桥吃掉了，后面全跳过 */
        case RX_HANDLER_ANOTHER:
            goto another_round;   /* 换设备从头再来 */
        case RX_HANDLER_EXACT:
            deliver_exact = true;
            /* fall through */
        case RX_HANDLER_PASS:
            break;                /* 继续往下走 */
        }
    }
    /* 按 skb->protocol 查 ptype_base 哈希表，分发给 ip_rcv、arp_rcv 等 */
    list_for_each_entry_rcu(ptype, &ptype_base[ntohs(skb->protocol) & PTYPE_HASH_MASK], list) {
        ret = deliver_skb(skb, ptype, orig_dev);
    }
    /* ... */
}

关键在位置：rx_handler 的调用在 ptype 分发之前。这一段顺序决定了很多现象。

5.1 顺序带来的三个推论 #

第一，端口上配的 IP 收不到包。ip_rcv 挂在 ptype_base 上，只有走到函数尾部才被调用。桥返回 CONSUMED 就 goto unlock 了，ip_rcv 一次都不执行。

第二，tcpdump -i eth0 还能看到帧。抓包钩子在 rx_handler 之前就把副本投出去了，拿到的是还没进桥的那份。想看桥处理完的结果，抓 br0 或者出方向的端口。

第三，skb->dev 一换，后面的逻辑全跟着换。桥在 br_pass_frame_up 里把 skb->dev 从 eth0 改成 br0，然后重新调 netif_receive_skb。这一趟 __netif_receive_skb_core 看到的是 br0，而 br0->rx_handler 是 NULL，所以不会再进 br_handle_frame，直接走到 ptype 分发交给 ip_rcv。

这就是「不二次进桥」的机制。不是靠标志位防重入，是靠桥设备本身没有注册 rx_handler。

5.2 为什么网口加进网桥后就不能再用 IP #

把 eth0 加进 br0 之后，在 eth0 上配 IP 是能配上的，命令行不报错，ip addr 也看得见，但流量不通。原因有三层：

层级 发生了什么
收包方向 eth0->rx_handler 被换成 br_handle_frame，所有帧在 ip_rcv 之前被截走，返回 CONSUMED。eth0 的 IP 等不到自己的包
skb->dev 桥要上交本机时先把 skb->dev 改成 br0 再调协议栈，IP 层认的是 br0 的地址
ARP 方向 对端 ARP 请求的是 br0 的 MAC，因为桥才是对外那张脸。eth0 自己的 MAC 只在 FDB 里作为 local 表项存在

规矩很直白：IP 配在 br0 上，端口上不配。加桥之前先把端口 IP 删掉。

eth0 的 MAC 没有消失。它在 br_add_if 里被登记成 is_local 表项，同时 br_stp_recalculate_bridge_id 会把 br0 的 MAC 改成所有端口里最小的那个。默认配置下，br0 的 MAC 就是第一个加入的端口的 MAC。

收包路径上出问题，按这个顺序问自己：帧到网卡了吗（ethtool -S eth0 的 rx 计数）→ tcpdump -i eth0 有没有 → /sys/class/net/eth0/brport 在不在 → bridge link show 里 state 是不是 FORWARDING → bridge fdb show 里有没有这个源 MAC。五步里任何一步断了，后面的都看不到。

tcpdump -i eth0 有包但 bridge fdb show 没记录，说明帧进了 br_handle_frame 但在学源之前被丢了——回头查 is_valid_ether_addr(h_source) 和 br_allowed_ingress。

六、FDB 的查找与更新 #

FDB 是网桥唯一的记忆。学是往里写，查是从里读，老化是往外删，三个动作围绕同一张哈希表。

c
#define BR_HASH_SIZE 256
static inline struct hlist_head *br_hash(struct net_bridge *br,
                                         const unsigned char *addr, __u16 vid)
{
    return &br->hash[br_mac_hash(addr, vid)];
}

br_mac_hash 把 6 字节 MAC 和 vid 混成一个 0 到 255 的索引。同一个 MAC 在 vid=10 和 vid=20 下算出不同的桶，所以是两条独立表项。桶用 hlist_head，桶内是 hlist_node 串的链表。表项带 struct rcu_head 延迟释放，读侧走 RCU 不加锁。

6.1 查表：__br_fdb_get #

br_handle_frame_finish 里那句 __br_fdb_get(br, dest, vid) 就是查表。它是 br_fdb_find 的内部版本，外面看到的名字是 br_fdb_find_rcu。

c
struct net_bridge_fdb_entry *__br_fdb_get(struct net_bridge *br,
                                          const unsigned char *addr, __u16 vid)
{
    struct net_bridge_fdb_entry *fdb;
    hlist_for_each_entry_rcu(fdb, br_hash(br, addr, vid), hlist) {
        if (fdb->vid == vid && ether_addr_equal(fdb->addr.addr, addr))
            return fdb;
    }
    return NULL;
}

vid 要一起比。桶是按 (MAC, vid) 算的，但哈希有碰撞，桶里会躺着别的 MAC，所以桶内还得逐个比 MAC 和 vid。

对外的封装是 br_fdb_find_rcu。名字带 _rcu 的函数要求调用方已经处在 RCU 读临界区里——br_handle_frame 是在 __netif_receive_skb_core 的 rcu_read_lock 里被调的，整条链都安全。

6.2 表项的五种身份 #

类型 判定字段 怎么来的 会不会老化
动态表项 全 0 从源 MAC 学到 会
本地表项 is_local=1 br_add_if 登记端口 MAC，桥自己的 MAC 不会
静态表项 is_static=1 bridge fdb add <MAC> dev eth0 static 不会
用户态表项 added_by_user=1 bridge fdb add 加的非静态项 会
外部学习表项 added_by_external_learn=1 驱动或用户态通过 netlink 塞进来 会

is_local 最容易忽略。桥自己的 MAC、每个端口的 MAC，都以 is_local=1 躺在表里。查表命中这类表项时 dst 是 NULL，代码走 br_pass_frame_up 而不是 br_forward。

6.3 查表之后的三条路 #

dst 的情况 动作 说明
非空且 !is_local br_forward(dst->dst, skb, skb2) 单播，从一个口出去
非空且 is_local skb2 = skb; skb = NULL 目的就是本机，只上交不转发
空 br_flood_forward(br, skb, skb2, unicast) 查不到，泛洪

第三种不是异常处理，是网桥的设计。表里没有的目的地，桥只知道「它在别的某个口后面」，唯一能做的就是每个口试一遍。泛洪出去的那份被别人回过来时，回程的源 MAC 就学到了，下一次就能直达。

转发命中时那句 dst->used = jiffies; 只记「最后一次被转发用到」，是老化和统计之外的第三个时间戳。老化看的始终是 updated。

br->dev->stats.multicast++ 只在组播分支里加，单播和广播都不加这个计数。

七、br_fdb_update 与老化 #

学源只有一个函数：br_fdb_update。它被 br_handle_frame_finish 在 VLAN 过滤之后、组播处理之前调用。

c
void br_fdb_update(struct net_bridge *br, struct net_bridge_port *source,
                   const unsigned char *addr, u16 vid, bool added_by_user)
{
    struct net_bridge_fdb_entry *fdb;
    /* 老化时间为 0 的用户就是想一直泛洪 */
    if (hold_time(br) == 0)
        return;
    /* 只有学习和转发状态的端口才学 */
    if (!(source->state == BR_STATE_LEARNING ||
          source->state == BR_STATE_FORWARDING))
        return;
    fdb = br_fdb_find(br, addr, vid);
    if (unlikely(fdb)) {
        if (unlikely(fdb->is_local)) {
            /* 撞上本机地址：有人冒用，或者环路 */
            if (net_ratelimit())
                br_warn(br, "received packet on %s with own address as source address\n",
                        source->dev->name);
        } else {
            fdb->dst = source;        /* 端口变了就改，这就是 MAC 漂移 */
            fdb->updated = jiffies;   /* 同一端口只刷新存活时间 */
        }
    } else {
        spin_lock(&br->hash_lock);
        if (likely(!br_fdb_find(br, addr, vid)))
            fdb_create(br, source, addr, vid, 0);   /* 新表项 */
        spin_unlock(&br->hash_lock);
    }
}

7.1 三个提前返回 #

第一个是 hold_time(br) == 0，回来得最早。hold_time 的定义：

c
static inline unsigned long hold_time(const struct net_bridge *br)
{
    return br->topology_change ? br->forward_delay : br->ageing_time;
}

ageing_time 设成 0，br_fdb_update 直接返回，什么也学不到。效果是全表空、全流量泛洪。有人用这招排查「是不是 FDB 学错了」，代价是带宽顶满。

第二个看端口状态。DISABLED、BLOCKING、LISTENING 的端口不学。这和 br_handle_frame 的 state 分支是两道独立的闸，那儿拦整帧，这儿只拦学源。

第三个由 br_fdb_find 的结果决定，命中就更新，没命中就新建。

7.2 MAC 漂移 #

同一个 MAC 在 eth0 出现过又在 eth1 出现，fdb->dst 从 eth0 的端口改成 eth1 的端口，代码里就是一行 fdb->dst = source。漂移本身不是错误，虚拟机迁移、bond 主备切换都会让它正常发生。漂移频率是拓扑健康的体温计：bridge fdb show 连着看几遍，同一 MAC 在两端来回跳，多半是二层环路，或者 STP 没把其中一个口堵住。

is_local 那条分支是另一个信号。源 MAC 等于桥自己或某个端口的 MAC，说明有人在冒用，或者你把两块同 MAC 的网卡接进了同一个桥。net_ratelimit() 限速是为了不把日志刷爆。

7.3 老化：br_fdb_cleanup #

表项不会自己消失，得靠定时器扫。

c
static void br_fdb_cleanup(struct work_struct *work)
{
    struct net_bridge *br = container_of(work, struct net_bridge, gc_work.work);
    unsigned long delay = hold_time(br);
    int i;
    spin_lock_bh(&br->hash_lock);
    for (i = 0; i < BR_HASH_SIZE; i++) {
        struct net_bridge_fdb_entry *f;
        struct hlist_node *h, *n;
        hlist_for_each_entry_safe(f, h, n, &br->hash[i], hlist) {
            unsigned long this_timer;
            if (f->is_static)
                continue;                  /* 静态表项跳过 */
            this_timer = f->updated + delay;
            if (time_after_eq(jiffies, this_timer)) {
                if (f->is_local)           /* 本地表项不删 */
                    continue;
                br_fdb_delete(br, f);      /* 超时，删 */
            }
        }
    }
    spin_unlock_bh(&br->hash_lock);
    /* ... 排下一次 gc_work ... */
}

判据是 f->updated + delay 和当前 jiffies 比。updated 只在 br_fdb_update 里刷新，也就是只有这个 MAC 再发帧才续命。老化时间的真实含义是「这个 MAC 沉默多久后从表里消失」。

默认 BR_DEFAULT_AGEING_TIME = 300 * HZ，300 秒。delay = hold_time(br)，拓扑变化时 hold_time 变成 forward_delay（默认 15 秒）。STP 一抖，整张表的老化速度快 20 倍。

is_static 和 is_local 两类表项永远不删。前者是手工配的，后者是桥和端口的自身地址。

7.4 表项过期后会发生什么 #

这是网络抖动的一个常见来源，单独说清。

一个 MAC 沉默超过 300 秒，表项被删。下一帧发给它时 __br_fdb_get 返回 NULL，br_handle_frame_finish 走 br_flood_forward，往所有端口各发一份——包括那个原本不该收到它的端口。表项重新学到之后泛洪停止，整个过程持续到下一帧回来为止，短则几十毫秒，长则几秒。

现象 原因
闲时正常，一有交互就短暂延迟抖动 表项过期后首包触发泛洪，泛洪经过的口多
单向大流量里突然出现重复包 泛洪到不该去的口，被上游设备又送回来
抓包看到同一帧出现在多个口 表项不存在，泛洪的正常表现
交互越稀疏越抖 沉默时间越接近 300 秒越容易踩线

调法有两个方向。一是把 ageing_time 调大，让表项活得久一点：

bash
ip link set dev br0 type bridge ageing_time 6000   # 单位 1/100 秒，6000 即 60 秒
bridge fdb show | wc -l

单位要盯住。netlink 接口里 ageing_time 是百分之一秒，300 秒写成 30000。sysfs 的 /sys/class/net/br0/bridge/ageing_time 也是这个单位，直接把 300 写进去等于 3 秒，越调越糟。

二是让关键 MAC 变静态，谁不老化谁就不抖：

bash
bridge fdb add 52:54:00:aa:bb:cc dev eth0 static
bridge fdb show | grep -i static

静态表项不参与老化，代价是拓扑变了它也不跟着变。用在固定的服务器和网关 MAC 上合适，用在会漂的虚拟机上更难受。

八、转发决策：br_forward #

决策在 br_handle_frame_finish 里做完，br_forward 只负责执行。两个函数连着看才完整。br_handle_frame_finish 的作用是把不同类别的帧分发到不同路径。

c
/* note: already called with rcu_read_lock */
int br_handle_frame_finish(struct net *net, struct sock *sk, struct sk_buff *skb)
{
    const unsigned char *dest = eth_hdr(skb)->h_dest;
    struct net_bridge_port *p = br_port_get_rcu(skb->dev);
    struct net_bridge *br;
    struct net_bridge_fdb_entry *dst;
    struct net_bridge_mdb_entry *mdst;
    struct sk_buff *skb2;
    bool unicast = true;
    u16 vid = 0;
    /* 端口不存在或已关闭，直接丢 */
    if (!p || p->state == BR_STATE_DISABLED)
        goto drop;
    /* 判断是否允许进入桥内：没开 vlan 全部放行，开了就按 vlan 规则 */
    if (!br_allowed_ingress(p->br, nbp_vlan_group_rcu(p), skb, &vid))
        goto out;
    /* insert into forwarding database after filtering to avoid spoofing */
    br = p->br;
    /* 可以学习就学源 MAC —— 整条链的第一步「学源」 */
    if (p->flags & BR_LEARNING)
        br_fdb_update(br, p, eth_hdr(skb)->h_source, vid, false);
    if (!is_broadcast_ether_addr(dest) && is_multicast_ether_addr(dest) &&
        br_multicast_rcv(br, p, skb, vid))
        goto drop;
    /* 学习态只学不发 */
    if (p->state == BR_STATE_LEARNING)
        goto drop;
    BR_INPUT_SKB_CB(skb)->brdev = br->dev;
    /* The packet skb2 goes to the local host (NULL to skip). */
    skb2 = NULL;
    if (br->dev->flags & IFF_PROMISC)
        skb2 = skb;
    dst = NULL;
    if (IS_ENABLED(CONFIG_INET) && skb->protocol == htons(ETH_P_ARP))
        br_do_proxy_arp(skb, br, vid, p);
    if (is_broadcast_ether_addr(dest)) {
        skb2 = skb;
        unicast = false;
    } else if (is_multicast_ether_addr(dest)) {
        mdst = br_mdb_get(br, skb, vid);
        if ((mdst || BR_INPUT_SKB_CB_MROUTERS_ONLY(skb)) &&
            br_multicast_querier_exists(br, eth_hdr(skb))) {
            if ((mdst && mdst->mglist) || br_multicast_is_router(br))
                skb2 = skb;
            br_multicast_forward(mdst, skb, skb2);
            skb = NULL;
            if (!skb2)
                goto out;
        } else
            skb2 = skb;
        unicast = false;
        br->dev->stats.multicast++;
    } else if ((dst = __br_fdb_get(br, dest, vid)) && dst->is_local) {
        skb2 = skb;
        /* 目的就是本机，不转发 */
        skb = NULL;
    }
    if (skb) {
        if (dst) {
            dst->used = jiffies;
            br_forward(dst->dst, skb, skb2);          /* 查到，单播 */
        } else
            br_flood_forward(br, skb, skb2, unicast); /* 查不到，泛洪 */
    }
    /* 副本上交本机 */
    if (skb2)
        return br_pass_frame_up(skb2);
out:
    return 0;
drop:
    kfree_skb(skb);
    goto out;
}

九段各有分工，按顺序记：

段 代码 作用
① 端口校验 !p || p->state == BR_STATE_DISABLED 端口不存在或关闭，丢
② VLAN 入口 br_allowed_ingress(...) 这帧能不能从这个口进来，顺带算出 vid
③ 学源 br_fdb_update(...) 记下源 MAC 和入端口
④ 组播预处理 br_multicast_rcv(...) IGMP/MLD 报文在这儿被消化，返回真就丢
⑤ 学习态拦截 p->state == BR_STATE_LEARNING 只学不发
⑥ 混杂备份 IFF_PROMISC → skb2 = skb 给本机留一份
⑦ proxy ARP br_do_proxy_arp(...) 桥替 ARP 代答
⑧ 目的分支 广播 / 组播 / 单播 定 skb 和 skb2 两个指针
⑨ 执行 br_forward / br_flood_forward / br_pass_frame_up 三个出口

核心就一句话：学源、查目的、查到就 br_forward 单播、查不到就 br_flood 泛洪、目的就是本机就 br_pass_frame_up 上交。其余全是这句的边界条件。

skb 和 skb2 是两个指针，别当副本理解。skb 是要转发出去的那份，skb2 是要上交本机的那份，两者可以为同一个 skb（这时 br_forward 内部会克隆）。

8.1 br_forward #

c
void br_forward(const struct net_bridge_port *to, struct sk_buff *skb,
                struct sk_buff *skb0)
{
    if (should_deliver(to, skb)) {
        if (skb0)
            deliver_clone(to, skb, __br_forward);   /* 还要上交本机，先克隆 */
        else
            __br_forward(to, skb);                  /* 直接发 */
        return;
    }
    if (skb0)
        kfree_skb(skb0);   /* 端口不发，那份本机副本也没人管了 */
}

三个参数：to 是出口端口，skb 要发的帧，skb0 要上交本机的副本（NULL 表示本机不需要）。

should_deliver 管两件事：端口得是 BR_STATE_FORWARDING（单播命中一个 BLOCKING 的口，帧直接不发，也不退回去泛洪，就这么丢了——这是 STP 挡环路的代价），出接口不能等于入接口（除非开了 BR_HAIRPIN_MODE）。

skb0 非空时克隆，场景是桥设备处在混杂模式、skb2 = skb，一份 skb 不能同时进两个方向。桥设备开混杂模式带来的 skb 复制开销就在这里。

8.2 __br_forward #

c
static void __br_forward(const struct net_bridge_port *to, struct sk_buff *skb)
{
    struct net_bridge_vlan_group *vg;
    struct net_device *indev;
    /* LRO 聚合过的帧不能转发，聚合后校验和语义变了 */
    if (skb_warn_if_lro(skb)) {
        kfree_skb(skb);
        return;
    }
    /* 取出出口端口的 vlan 组，br_handle_vlan 要在里面找自己的 vid */
    vg = nbp_vlan_group_rcu(to);
    /* 按出口配置决定打不打 tag */
    skb = br_handle_vlan(to->br, vg, skb);
    if (!skb)
        return;
    indev = skb->dev;      /* 入接口，记下来给 netfilter 用 */
    skb->dev = to->dev;    /* 换成出接口 */
    skb_forward_csum(skb);
    NF_HOOK(NFPROTO_BRIDGE, NF_BR_FORWARD,
            dev_net(indev), NULL, skb, indev, skb->dev,
            br_forward_finish);
}

四件事：LRO 检查、VLAN 出口处理、skb->dev 切换到出接口、进 NF_BR_FORWARD。

skb_warn_if_lro 容易被忽略。LRO 把多个小帧聚合成一个大 skb，带着 GRO 的元数据，直接转发出去对端会解错。所以桥在转发路径上必须拦下来。开着 LRO 的网卡加进桥之后性能不如预期，原因就在这里，帧被丢了一批。

skb->dev = to->dev 是转发的核心动作。之前 skb->dev 一直是入接口，从这一句开始变成出接口，后面 dev_queue_xmit 才知道往哪张网卡发。

NF_HOOK 的第五、六个参数是 indev 和 skb->dev，也就是「从哪进、往哪出」，ebtables 的 forward 链靠这两个参数做过滤。

8.3 最后一站 #

c
int br_forward_finish(struct net *net, struct sock *sk, struct sk_buff *skb)
{
    return NF_HOOK(NFPROTO_BRIDGE, NF_BR_POST_ROUTING,
                   net, sk, skb, NULL, skb->dev,
                   br_dev_queue_push_xmit);
}

NF_BR_POST_ROUTING 之后再走 br_dev_queue_push_xmit：检查 is_skb_forwardable（设备还开着、MTU 够用），skb_push(skb, ETH_HLEN) 把 br_netfilter 剥掉的以太头补回去，br_drop_fake_rtable 扔掉那个模块挂上的假 dst_entry，最后 dev_queue_xmit 交给队列规则出网卡。

到这里，帧从 eth0 进、br0 处理、eth1 出，整条路走完。

九、本机投递与转发到其他口 #

转发出去和上交本机是两条平行的路。前面那条走 br_forward，这条走 br_pass_frame_up。两条都在 br_handle_frame_finish 尾部按 skb 和 skb2 分派。

c
static int br_pass_frame_up(struct sk_buff *skb)
{
    struct net_device *indev, *brdev = BR_INPUT_SKB_CB(skb)->brdev;
    struct net_bridge *br = netdev_priv(brdev);
    struct net_bridge_vlan_group *vg;
    struct pcpu_sw_netstats *brstats = this_cpu_ptr(br->stats);
    /* 统计该桥上的流量 */
    u64_stats_update_begin(&brstats->syncp);
    brstats->rx_packets++;
    brstats->rx_bytes += skb->len;
    u64_stats_update_end(&brstats->syncp);
    /* 获取该桥上的 vlan 组 */
    vg = br_vlan_group_rcu(br);
    /* 桥和其他端口一样，出口也要过 VLAN 检查。混杂模式下有人抓包就放行 */
    if (!(brdev->flags & IFF_PROMISC) && !br_allowed_egress(vg, skb)) {
        kfree_skb(skb);
        return NET_RX_DROP;
    }
    indev = skb->dev;      /* 入帧设备，给 netfilter 用 */
    skb->dev = brdev;      /* 替换掉数据包中的设备信息，改为桥设备 */
    /* 配置数据包 vlan 的相关信息 */
    skb = br_handle_vlan(br, vg, skb);
    if (!skb)
        return NET_RX_DROP;
    /* 进入 NF_BR_LOCAL_IN */
    return NF_HOOK(NFPROTO_BRIDGE, NF_BR_LOCAL_IN,
                   dev_net(indev), NULL, skb, indev, NULL,
                   br_netif_receive_skb);
}
static int br_netif_receive_skb(struct net *net, struct sock *sk, struct sk_buff *skb)
{
    return netif_receive_skb(skb);
}

四件事：记统计、查出口 VLAN 权限、把 skb->dev 换成桥设备、进 NF_BR_LOCAL_IN。

indev 那一步很关键。skb->dev 已经被改成 br0，如果不另存一份入帧设备，netfilter 就不知道这帧从哪个物理口进来。所以先 indev = skb->dev，再换 skb->dev，最后 NF_HOOK 里两个分开传。

br_netif_receive_skb 只是一层壳，里面调 netif_receive_skb，等于把帧重新塞回收包流程。这一趟 skb->dev 是 br0，br0->rx_handler 是 NULL，所以不会再进桥，直接走到 ptype 分发交给 ip_rcv。

9.1 br_handle_vlan：两条路共用 #

转发和上交本机都要调 br_handle_vlan，区别只在传进去的 VLAN 组——转发传出口端口的 nbp_vlan_group_rcu(to)，上交本机传桥的 br_vlan_group_rcu(br)。

c
struct sk_buff *br_handle_vlan(struct net_bridge *br,
                               struct net_bridge_vlan_group *vg,
                               struct sk_buff *skb)
{
    struct net_bridge_vlan *v;
    u16 vid;
    /* 入口没做过滤，这帧不归 VLAN 管，原样放行 */
    if (!BR_INPUT_SKB_CB(skb)->vlan_filtered)
        goto out;
    /* 走到这里说明帧被过滤过，带合法 vlan id */
    br_vlan_get_tag(skb, &vid);
    /* 在 vlan 组里找自己所属的 vid */
    v = br_vlan_find(vg, vid);
    /* 这个 vid 必须配过。唯一例外是桥在混杂模式且帧的目的就是桥 */
    if (!v || !br_vlan_should_use(v)) {
        if ((br->dev->flags & IFF_PROMISC) && skb->dev == br->dev) {
            goto out;
        } else {
            kfree_skb(skb);
            return NULL;
        }
    }
    /* vlan 统计，只有 vlan_stats_enabled 才记 */
    if (br->vlan_stats_enabled) { /* stats->tx_bytes / tx_packets 累加 */ }
    /* 出口配了 untagged，把 tag 清掉 */
    if (v->flags & BRIDGE_VLAN_INFO_UNTAGGED)
        skb->vlan_tci = 0;
out:
    return skb;
}

逻辑很短：在传进来的 VLAN 组里找自己所属的 vid；找不到就看是不是混杂模式加本机投递，是就放行，不是就丢；找到且 VLAN 启用，统计出口流量，最后按 BRIDGE_VLAN_INFO_UNTAGGED 位决定清不清 skb->vlan_tci。

vlan_filtered 是入口留下的记号。br_allowed_ingress 在 br_handle_frame_finish 开头已经跑过，它判断这一帧能不能从该端口进来、属于哪个 vid。入口没做过滤的帧，出口也不处理 tag。

9.2 泛洪：br_flood #

查不到目的时走 br_flood_forward，它是个薄壳，直接调 br_flood，后者遍历 br->port_list，对每个端口调 br_forward：

c
list_for_each_entry_rcu(p, &br->port_list, list) {
    /* 单播泛洪可以通过 BR_FLOOD 关掉 */
    if (unicast && !(p->flags & BR_FLOOD))
        continue;
    /* 开了 proxy ARP 的口不参与泛洪 */
    if (p->flags & BR_PROXYARP)
        continue;
    br_forward(p, skb, skb2);
    skb2 = NULL;   /* 副本只发一次，发完置空 */
}
if (skb2)
    kfree_skb(skb2);

should_deliver 在里面再挡掉状态不对的端口和入接口。skb2 在第一个端口就被消耗掉，之后都传 NULL。

unicast 区分两种泛洪：广播和组播的泛洪（false）不看 BR_FLOOD，单播查不到时的泛洪（true）要看。关掉某个口的单播泛洪，能让未知单播不进这个口，代价是这个口后面的新 MAC 学不到。

9.3 两条路的分水岭 #

转发和上交的骨架一样：都是先查 VLAN 出口权限（转发用出口端口的 nbp_vlan_group_rcu(to)，上交用桥的 br_vlan_group_rcu(br)），都调 br_handle_vlan，都要过一道 netfilter，最后才落地。

分水岭只有三处。skb->dev 的目标不同：转发指向物理口 to->dev，上交指向桥设备 br->dev。钩子点不同：转发走 NF_BR_FORWARD 加 NF_BR_POST_ROUTING，上交走 NF_BR_LOCAL_IN。最终落点不同：转发进 dev_queue_xmit 出网卡，上交进 netif_receive_skb 回协议栈。统计也分两处记，转发记出口端口的 dev->stats，上交记 br->stats。

记住这三处，看任何桥转发问题都能先定位在「哪条路上」。

十、组播与广播的处理 #

br_handle_frame_finish 在查单播表之前，先把广播和组播分了出去。代码在上面已经贴过，这里只拆判断。

目的地址 判断函数 动作
广播 ff:ff:ff:ff:ff:ff is_broadcast_ether_addr skb2 = skb，unicast = false，泛洪 + 上交本机
组播 is_multicast_ether_addr 查 MDB 按表送，unicast = false，multicast++
单播 剩下都是 查 FDB，命中转发，未命中泛洪

广播分支只有两行。skb2 = skb 表示这份帧同时也要给本机，br_forward 里会 deliver_clone 克隆一份。unicast = false 是告诉 br_flood 别拿 BR_FLOOD 挡端口，广播必须发到所有口。

10.1 组播分支逐句 #

mdst = br_mdb_get(br, skb, vid); 查组播转发表。MDB 是 IGMP/MLD snooping 学出来的「哪个组播组在哪几个口后面」。

br_multicast_querier_exists(br, eth_hdr(skb)) 判断当前有没有 IGMP querier。没有 querier 就不做 snooping 决策，直接走 else 分支 skb2 = skb，按泛洪处理——没人管成员关系，桥不敢自己裁。

mdst->mglist 表示这个组还有成员口在听；br_multicast_is_router(br) 表示桥自己就是组播路由口。两种情况都要留一份给本机。

br_multicast_forward(mdst, skb, skb2) 按 MDB 精确送，不是泛洪。送完 skb = NULL，帧的所有权转移给它了。

if (!skb2) goto out; 判的是「本机需不需要这一份」。不需要就直接返回，skb 已经是 NULL，没什么可做的。

10.2 六种落地差异 #

分支 skb skb2 最后发生什么
广播 保留 = skb skb 泛洪，skb2 上交
组播，有 querier 且有 MDB NULL 按需 br_multicast_forward 送完，skb2 上交或释放
组播，无 querier 保留 = skb 走泛洪
单播，命中非本机 保留 NULL br_forward 单播发出
单播，命中本机 NULL = skb 只上交，不转发
单播，未命中 保留 NULL（非混杂） br_flood_forward 泛洪

单播命中本机那一行是 skb2 = skb; skb = NULL;，两个指针互换内容，结果是「只上交、不转发」。源码注释写得直白：Do not forward the packet since it's local.

单播未命中那一行，非混杂模式下 skb2 一直是 NULL，泛洪出去时没有 deliver_clone 的开销，本机也收不到这份帧。桥不会因为「不知道目的在哪」就顺手给自己一份。

10.3 proxy ARP 与混杂模式备份 #

三个分支之前有两段准备。第一段是混杂模式备份：

c
skb2 = NULL;
if (br->dev->flags & IFF_PROMISC)
    skb2 = skb;
dst = NULL;

桥设备处不处在混杂模式，直接决定 skb2 的初值，也决定后面每次转发要不要克隆。桥设备默认不进混杂模式，端口设备必然进——这个区别同时影响收包（端口必须收全）和克隆开销（桥设备混杂才需要复制）。

第二段是 proxy ARP：

c
if (IS_ENABLED(CONFIG_INET) && skb->protocol == htons(ETH_P_ARP))
    br_do_proxy_arp(skb, br, vid, p);

开了 BR_PROXYARP 的口，遇到 ARP 帧由桥代答。它在查表之前动手，代答完这个帧就不再往下走了。典型用途是让一个子网跨网桥延伸，两端互相以为对方在同一条线上。

十一、内核代码的关键函数链 #

把前面散落的函数按层归位，一条链看全。

层 函数 一句话
收包调度 __netif_receive_skb_core 看 skb->dev->rx_handler，有就交给桥
入桥 br_handle_frame 分拣保留地址，按 p->state 决定去向
决策 br_handle_frame_finish 学源、查目的、定三个出口
学源 br_fdb_update 新 MAC 建表项，旧 MAC 刷新 updated
查表 __br_fdb_get 按 (MAC, vid) 哈希，桶内比对
单播出 br_forward → __br_forward 判 should_deliver，换 skb->dev，进 NF_BR_FORWARD
泛洪 br_flood_forward → br_flood 遍历端口，逐口 br_forward
上交 br_pass_frame_up 换 skb->dev 为 br0，进 NF_BR_LOCAL_IN
VLAN 出口 br_handle_vlan 按出口配置打 tag 或清 tag
收尾 br_forward_finish → br_dev_queue_push_xmit 过 NF_BR_POST_ROUTING，dev_queue_xmit
绕回 br_netif_receive_skb 壳函数，调 netif_receive_skb
老化 br_fdb_cleanup gc_work 定时扫表，删超时表项

调用顺序收成一行：__netif_receive_skb_core → br_handle_frame → br_handle_frame_finish，然后分三路——br_forward → __br_forward → br_handle_vlan → NF_BR_FORWARD → br_forward_finish → NF_BR_POST_ROUTING → br_dev_queue_push_xmit → dev_queue_xmit；br_flood_forward → br_flood → br_forward × N；br_pass_frame_up → br_handle_vlan → NF_BR_LOCAL_IN → br_netif_receive_skb → netif_receive_skb → ip_rcv。

br_handle_frame 里的两个 NF_HOOK 决定了入口之后分两条：保留地址走 NF_BR_LOCAL_IN 加 br_handle_local_finish，普通帧走 NF_BR_PRE_ROUTING 加 br_handle_frame_finish。br_handle_frame_finish 尾部的三个出口决定了出口之前分三条：br_forward、br_flood_forward、br_pass_frame_up。

几条压舱的判断。skb->dev 是桥梁代码里最会骗人的一个字段。同一帧在 br_handle_frame 里指向 eth0，到 br_pass_frame_up 里指向 br0，在 __br_forward 里指向 eth1。调试时先确认「此刻 skb->dev 是谁」，一半的问题当场就清楚了。

state 和 flags 别混，is_local 决定「转发还是上交」——查表命中的表项带 is_local 就别指望 br_forward，br_handle_frame_finish 里已经把 skb 置 NULL 了。

老化时间和拓扑变化联动。hold_time 在 topology_change 为真时返回 forward_delay（15 秒）而不是 ageing_time（300 秒）。STP 抖动期间 FDB 清得比平时快得多，泛洪量跟着上来，这就是「一改网络配置就抖一阵」的来源。
