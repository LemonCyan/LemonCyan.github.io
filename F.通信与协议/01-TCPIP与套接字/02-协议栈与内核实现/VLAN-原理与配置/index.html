一、VLAN 解决什么问题 #

讲 VLAN 的文章常常一上来就画标签格式。我们反过来，先问一句：没有 VLAN 的时候，网络坏在哪。

先把广播域定义清楚。广播域指广播帧（目的 MAC 全 1）能传到的范围，也就是能直接通信的范围。严格说，装进来的不只是广播帧：组播帧、目的不明的单播帧，同样在这个范围里跑。

一台二层交换机出厂只构建一个广播域。收到广播帧，除入端口外每个口都发一份，这个动作叫泛洪（Flooding）。五台交换机串起来，泛洪就串五层。

最常见的场景：计算机 A 要和 B 通信。以太网必须在帧里写目的 MAC，A 不知道 B 的 MAC，先发 ARP 请求。这个请求是广播，交换机 1 泛洪给它的所有口，交换机 2 接着泛洪，一路传遍全网。

可这个请求本来只为了让 B 收到。结果是全公司每台机器都收了一份：带宽被白吃一遍，每台机器的 CPU 都要从软中断里把帧捞出来看一眼，再扔掉。

有读者会问：广播真有那么频繁？真的。TCP/IP 里除了 ARP，还有 DHCP、RIP。RIP 每 30 秒往邻居广播一次路由信息；OSPF、IS-IS 走组播，交换机照样泛洪。TCP/IP 之外，NetBEUI、IPX、AppleTalk 也靠广播过日子——Windows 里双击「网络计算机」，先出去一串广播。

协议 用的什么帧 干什么
ARP 广播 建立 IP 与 MAC 的映射
DHCP 广播 自动下发地址、网关、DNS
RIP 广播 / 组播 每 30 秒通告一次路由信息
OSPF、IS-IS 组播 链路状态通告与邻居发现
NetBEUI 广播 Windows 早期的名字解析
IPX 广播 Novell NetWare 的服务通告
AppleTalk 广播 苹果机的名字绑定
mDNS、LLMNR 组播 局域网名字解析，打印机、投影仪常发

一句话收口：一个广播域，一个广播出去就传遍全网。设计局域网时第一件要想清楚的事，就是广播域的边界画在哪。

切广播域的老办法是路由器，一个 LAN 接口划一个广播域。问题在接口数量：路由器上的 LAN 口少得可怜，多则 4 个。那种带 4 个 LAN 口的宽带路由器，LAN 侧其实是内置交换机，切不了广播域。

能切几个域，全看路由器有几个口，人被硬件卡死。二层交换机不一样，24 口、48 口满地都是。让它在二层就把广播域切开，灵活性立刻上一个台阶。

干这件事的技术就是 VLAN（Virtual Local Area Network，虚拟局域网）。

把定义钉死：VLAN 的本质是在二层帧里插一个 4 字节标签，用标签里的 12 位 VID 划分广播域。一台交换机配上 VLAN，等于在里面装了几台互不相通的独立交换机。研发的广播出不了研发那 12 个口，财务的广播也进不来。

直观一点看：一台交换机切成红、蓝两个 VLAN，就当它是红蓝两台虚拟交换机摞在一起。再建第三个 VLAN，就再摞一台。这几台虚拟交换机之间互不相通——两台机器明明插在同一台设备上，偏偏 ping 不通。这个事实既是 VLAN 好用的根源，也是它让人绕不明白的地方。

它只解决「广播域太大」这一个问题。不是安全问题。

VLAN 不做访问控制。同一个 VLAN 里的两台机器照样能互扫端口、照样能 ARP 欺骗。跨 VLAN 也不等于安全隔离——VLAN 跳变攻击（VLAN hopping）到今天依然可行：攻击者发双标签帧，外层标签是自己所在 VLAN、内层是目标 VLAN，交换机剥掉外层之后就把帧送进了目标 VLAN；或者利用 DTP 协商把对端端口谈成 trunk，然后自己打标签进来。真要把两个 VLAN 的流量管住，得上 ACL 或者防火墙，不能指望交换机上的 vlan 10 / vlan 20 两行配置。

广播域大到底坏在哪，列成表更直观：

问题 具体表现
ARP 请求泛滥 每台主机都要处理全网的 ARP，终端 CPU 被无谓唤醒
未知单播泛洪 MAC 表装不下，大量帧被复制到所有端口，带宽被吃掉
广播风暴 一个二层环路或者一张坏网卡，整网瘫痪，交换机 CPU 打满
故障域过大 一次 ARP 欺骗、一次 DHCP 抢答，影响面是全公司
管理边界模糊 按部门、按业务切分只能靠拉线，换个工位就得改配线架

划分广播域的手段就那么几种，摆在一起对比：

手段 隔离在哪一层 跨域靠什么 成员变更成本
多拉一根线，物理分开 物理层 路由器 高，要动线、要工位
用路由器划子网 三层 路由器 中，要改网关和掩码
VLAN 二层 路由器或三层交换机 低，改一行端口配置

举个具体的：一台 24 口接入交换机，1~12 口给研发，13~24 口给财务。不配 VLAN，要么买两台交换机，要么拿路由器把两边隔开，钱和线都得花。配 VLAN，一台机器两行命令。

两台交换机、两个部门 #

把规模放大一点，看一个两层楼的办公网：

text
        研发 VLAN 10                      财务 VLAN 20
   PC1 ──┐                            ┌── PC4
   PC2 ──┤  SW1 1~12 口：VLAN 10      │
   PC3 ──┘  SW1 13~24 口：VLAN 20 ───┼── PC5
                    │                 └── PC6
                    │
              trunk：放行 VLAN 10、20
                    │
              SW2 1~12 口：VLAN 10
                    │
                  PC7（研发，在另一层楼）

两根交换机之间只有一根网线，两个 VLAN 的流量都从这根线上过。帧在线上带着 VID，到了对端按 VID 分开。PC1 找 PC7 走二层，一次路由都不用；PC1 找 PC4 走三层，要过网关。

如果没有 VLAN，这个拓扑得拉两根楼层间的线，一根给研发、一根给财务。楼层间竖井的位置是死的，加一根线的审批流程比配 VLAN 长得多。

VLAN 在哪儿用到 #

  • 企业接入层：按部门、按业务切，一个 VLAN 一个子网。最经典的用法，也是本篇的主线。
  • 数据中心：按租户、按业务系统切。规模上去之后 VLAN 不够用，才有了 VXLAN 那种把二层封进三层的方案。
  • 运营商：用 QinQ 给每个宽带用户套一个外层 VLAN，用户自己内部怎么配都不冲突。
  • 虚拟化与容器：宿主机上的网桥开 vlan_filtering，给虚拟机、容器划广播域，和硬件交换机用同一套语义。

四种场景的共同点只有一个：要在同一批物理设备上，拿出多套互不干扰的二层网络。

代价是配置复杂度全压在人身上——VID 配错、PVID 配错、trunk 允许列表漏了一个 VLAN，故障现象往往只是「不通」或者更阴的「能通但串了」。后面的章节就是在拆这些坑。

二、VLAN 标签的结构 #

标准以太网 II 帧长这样：目的 MAC 6 字节、源 MAC 6 字节、类型/长度 2 字节、载荷 46~1500 字节、尾部 FCS 4 字节。

IEEE 802.1Q 的改动只有一处：在源 MAC 之后、类型/长度之前，插进 4 字节（32 比特）的 VLAN Tag。

text
未打标：
+---------------+---------------+---------------+---------------------+
| DMAC (6)      | SMAC (6)      | Type/Len (2)  | Payload (46-1500)   |
+---------------+---------------+---------------+---------------------+

打标后（802.1Q）：
+-----------+-----------+-------------+---------------+---------------------+
| DMAC (6)  | SMAC (6)  | VLAN Tag(4) | Type/Len (2)  | Payload (46-1500)   |
+-----------+-----------+-------------+---------------+---------------------+
                              |
        +---------------------+---------------------+
        | TPID (16)           | PRI (3) | CFI (1) | VID (12) |
        +---------------------+---------+---------+----------+
        \_____________________ TCI (16 bits) ______________/

4 个字段逐个拆：

字段 位宽 取值 作用
TPID 16 0x8100 标识这是 802.1Q 帧。0x88a8 是 802.1ad 外层标签，0x9100 是某些设备的私有 QinQ
PRI 3 0~7 802.1p 优先级，供 QoS 队列调度用，和 VLAN 归属无关
CFI 1 以太网取 0 规范格式指示，早年用于兼容令牌环。802.1ad 把它改名 DEI，表示丢弃资格
VID 12 1~4094 可用 决定这个帧属于哪个广播域

TPID 的位置很关键：它占的就是原来「类型/长度」那个位置。交换机读到这里是 0x8100，就知道后面跟的是标签，真正的上层类型被推到标签之后再读。这个设计让不认标签的老设备把 802.1Q 帧当成长度字段异常帧直接丢弃，不会被误解析。

VID 是 12 位，取值范围 0~4095，其中两端保留：

  • 0：不用来划分 VLAN。带 VID=0 的帧叫 priority-tagged 帧，意思是「我只要优先级，不要 VLAN 归属」，进了交换机后按端口 PVID 补齐 VID。
  • 4095：协议保留，任何配置都别用。
  • 1~4094：能配的区间，4094 个 VLAN。

所以一台交换机理论上能切 4094 个广播域。接入层设备只用到几十个，运营商城域网会用到几千个。

按标签有无，一个帧只有三种形态：

形态 有无 TPID VID 谁发出来的
Untagged 无 无 普通终端网卡，根本不认 802.1Q
Priority-tagged 0x8100 0 只关心 QoS、不关心 VLAN 的终端，少数 IP 话机
Tagged 0x8100 1~4094 交换机 trunk 口、服务器上的 vlan 子接口

这三种形态的区别，直接决定了第三章 PVID 为什么要存在：交换机内部统一用 tagged 帧处理，可外面接的终端只会发 untagged 帧，中间得有个东西负责补标签。

再补两件容易被忽略的事。

一是帧长。4 字节标签把最大帧从 1518 撑到 1522（不含前导码）。路径上任何一段不支持 1522 的设备都会丢大包。典型症状：ping -s 1472 通，ping -s 1473 不通，TCP 能握手但传不了文件。

二是嵌套。QinQ（802.1ad）在 802.1Q 标签外面再套一层，外层叫 S-VLAN、TPID 用 0x88a8，内层叫 C-VLAN、TPID 用 0x8100，帧长再加 4 字节。运营商用它给每个用户的 VLAN 打上自己的 VLAN，用户内部的 VID 怎么配都不冲突。

谁打标、谁剥标 #

标签不是全程都在。它只存在于「需要区分归属」的那一段链路上，两头都不带。

位置 帧的形态 谁负责切换
终端网卡发出 untagged 终端不认 802.1Q，也不会打标
接入交换机入口 补成 tagged 交换机按端口 PVID 打标
交换机内部转发 tagged 硬件流水线统一按带标处理
交换机之间（trunk） tagged 保持原样，不增不减
接入交换机出口 剥成 untagged 出口端口在该 VID 上是 untagged 成员
终端网卡收到 untagged 终端一无所知

这条链路解释了一个常见困惑：在服务器上抓包，明明配了 vlan 子接口，抓到的帧却没有标签。因为抓包点在内核剥标之后。要看真标签得回到宿主物理口，并关掉网卡的接收剥离。

也解释了为什么「给终端配个带标的网卡」这么别扭：绝大多数消费级网卡驱动不认 802.1Q，交换机一打标它就把帧丢了。真要让终端自己打标，得上支持 VLAN 的服务器网卡，或者在操作系统里建 vlan 子接口——那是第六章的事。

PRI 三位拿来干什么 #

12 位 VID 决定归属，3 位 PRI 决定排队。两者互不干扰：同一个 VLAN 里可以跑不同优先级，不同 VLAN 也可以有同样的优先级。

PRI 值 0~7，映射到交换机的 8 个出队列。常见的用法：

PRI 典型流量 期望行为
5 语音 RTP 优先转发，抖动要小
4 视频会议 优先于普通数据
3 信令、呼叫控制 中高
0 普通数据 尽力而为
1 后台批处理、备份 让路

终端自己打不上标签，那 PRI 谁来填？入口交换机填。端口上配一条「收到裸帧就按这个优先级打标」，或者按 ACL 给特定流量改优先级。语音方案里那套 mls qos trust cos / trust dscp 就是干这个的。

标签的四个字段到这里就齐了。真正天天打交道的是后两个：VID 决定「你是谁家的」，PRI 决定「你排哪队」。

标签在抓包里长什么样 #

带标签的帧用 tcpdump -e 抓下来，形态是这样：

text
12:01:33.551204 aa:bb:cc:00:00:01 > ff:ff:ff:ff:ff:ff, ethertype 802.1Q (0x8100), length 64:
        vlan 100, p 0, ethertype ARP, Request who-has 192.168.10.20 tell 192.168.10.10

ethertype 802.1Q 是外层，vlan 100 就是 VID，p 0 是 PRI。同一台机器上抓不带标的口，同样的包会显示成：

text
12:01:33.551204 aa:bb:cc:00:00:01 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 60:
        Request who-has 192.168.10.20 tell 192.168.10.10

两条输出的差别，就是链路中间那段到底有没有标签。后面排查「这个口是不是 trunk」全靠这个对比。抓不到标签不一定是没打标，网卡的接收剥离特性会把标签提前摘掉，第六章讲 offload 时再说。

三、VID 与 PVID #

这两个词天天一起出现，配错的根子也常在这儿。先把归属分清：VID 是帧上的东西，PVID 是端口上的东西。

VID：帧的身份证 #

VID（VLAN ID）就是 VLAN 的标识，交换机拿它划分端口。一台 8 口交换机，把 port1、port2、port5 的 VID 设成 1111，这三个口就能收发 VLAN tag = 1111 的帧。

交换机内部维护一张 VLAN 表：每个 VID 一行，后面跟着「哪些端口属于它、在这些端口上带标还是不带标」。这张表就是全部配置的落点，命令行敲的 vlan 10 / port link-type access 最后都变成这张表的行。

这里有个容易咬住的地方：所谓 Untagged Port 和 Tagged Port，讲的不是物理端口的固有状态，而是这个物理端口在某个 VID 上的状态。同一个口，在 VID = 10 上可以是 Untagged Port，在 VID = 100 上可以是 Tagged Port。端口属性是二维的：口 × VLAN。

所以别问「这个口是 access 还是 trunk」，要问「这个口在 VLAN 10 上是什么角色」。一台交换机的配置对不对，拿这句话去套一遍就清楚了。

PVID：端口的所属 VLAN #

PVID 是 Port-base VLAN ID，基于端口的 VLAN ID。一个端口可以属于多个 VLAN，但只能有一个 PVID。收到不带 tag 的帧，按 PVID 打标，就当这个 VLAN 的帧处理。所以也有人直接说 PVID 就是端口的默认 VLAN 号。

三条硬性质：

  1. 一个物理端口只有一个 PVID。
  2. 端口有了 PVID，就必定拥有一个和 PVID 相等的 VID。
  3. 在这个 VID 上，该端口必定是 Untagged Port。

PVID 的作用只发生在一个时刻：交换机从外部收到 untagged 帧、需要给它补标签的时候。交换机内部转发帧时，PVID 不参与判断。

把这句话钉死：PVID 是端口的「所属 VLAN」。收无标签帧按 PVID 打标（VID = PVID），发出时若 VID == PVID 就剥标。两个动作，同一个值，一进一出。

PVID 不是加在帧头上的标记，它是端口的属性。它回答的问题只有一个：从这个口进来、身上没标签的帧，算哪个 VLAN 的。

跨设备才需要帧上真有 VID。所有 VLAN 都在一台交换机里，光靠「从哪个口进来的」就能区分；一旦要过 trunk 去另一台交换机，就得在帧里写上 VID，让对方也知道这帧是谁的。终端不会打标，所以必须给接终端的口配一个属性，告诉交换机「这个口收到的裸帧归哪个 VLAN」——这个属性就是 PVID。反过来说，trunk 口收到的帧本来就带 VID，VID 自己说明归属，PVID 只在收到裸帧时才上场。

PVID 对 tag 端口的影响 #

很多人以为 PVID 只对 untagged 口有意义，tag 口无所谓。不对。tag 端口也有 PVID，而且它会影响出帧。

实验设计：3 个口 Port 1、2、3。

  • Port 1：PVID = n
  • Port 2：PVID = 2
  • Port 3：PVID = 3

建 2 个 VLAN：

  • vlan2：VID = 2，包含 Port 1（tag）、Port 2（untag）
  • vlan3：VID = 3，包含 Port 1（tag）、Port 3（untag）

三台主机 A、B、C 分别接 Port 1、2、3。用 B、C 去 ping A，在 A 上抓包。

tag 口接计算机本来没意义，计算机解析不了带 tag 的帧；但抓包软件抓得到，正好拿来观察。

n 的取值 B 发来的帧到 A 时 C 发来的帧到 A 时 谁能 ping 通 A
n = 1 带 802.1Q 标签 带 802.1Q 标签 都不通，A 解析不了带标签的帧
n = 2 不带标签 带标签 只有 B
n = 3 带标签 不带标签 只有 C

机制拆开，以 n = 2、B ping A 为例：

  1. B 不知道 A 的 MAC，先发 ARP 广播，帧从 Port 2 进来。
  2. Port 2 的 PVID = 2，交换机给帧打上 VID = 2，转发到 VLAN 2 内所有口。
  3. Port 1 属于 VLAN 2，能收到这个帧。
  4. 出 Port 1 之前，拿 Port 1 的 PVID 与帧的 VID 比较：PVID = 2、VID = 2，相等，所以从 Port 1 出去的帧不打标签。

n = 3 时反向同理。n = 1 时两个都不等，于是都打标签，A 一个都收不了。

结论一句话：tag 端口转发本 VLAN 的帧、发出之前，先比该端口的 PVID 与帧的 VID；相等就剥标发出，不等就带标发出。

接收侧还有一条不对称的规则，这也是为什么上面要拿 tag 口做实验：

  • 端口拥有和帧标签一致的 VID，不管它在这个 VID 上是 untagged 还是 tagged，都能接收来自交换机内部的带标帧。
  • 端口拥有和帧标签一致的 VID，只有在它于该 VID 上是 tagged port 时，才能接收来自交换机外部的带标帧。

第一条管内部转发，第二条管外部入帧。Access 口对外部来的带标帧一律丢掉，原因就在第二条：它在自己的 PVID 上是 untagged port，没有资格收外部带标帧。

配置上的三条注意 #

  1. 对 untag 端口，PVID 要和所属 VLAN 的 VID 一致。
  2. 对 tag 端口，PVID 要不同于它所属所有 VLAN 的 VID。
  3. 两台设备互联，两端 PVID 保持一致，有利也有弊，取决于你想让哪个 VLAN 裸奔出去。

简化记忆：ACCESS 口接 PC，VID = PVID；TRUNK 口级联，VID = 全部，PVID = 1（出厂默认）。

再给一个组合例子收口：端口 1 同时属于 VLAN 1、2、3，PVID = 1。那么端口 1 能收到 VLAN 1、2、3 的帧，但它发出去的裸帧只会进 VLAN 1。「收」看 VID 成员关系，「发裸帧」看 PVID，两个方向不共用一张表。

一个实例：帧走完全程 #

一个数据包从 PC 出来，经 ACCESS → TRUNK → TRUNK → ACCESS → PC，中间帧长什么样。

先换成 802.1Q 的标准描述：

  • 发出时：untagged 帧
  • 第一个交换机的 ACCESS 口：PVID = 100，VID = 100 上是 Untagged Port
  • 第一个交换机的 TRUNK 口：PVID = 1（出厂配置，没改过），VID = 1 上是 Untagged Port，VID = 100 上是 Tagged Port
  • 第二个交换机的 TRUNK 口：同上
  • 第二个交换机的 ACCESS 口：PVID = 100，VID = 100 上是 Untagged Port
  • 收到时：untagged 帧

过程：

  1. 两台交换机刚开机，MAC 表为空。PC 的裸帧进 ACCESS 口，按 PVID 打上 VID = 100 的标签。
  2. 交换机把这个帧转发给 VID = 100 的所有端口（除进口），这一步叫 VLAN Flood。
  3. TRUNK 口拥有 VID = 100，所以能接收这个标签为 100 的 tagged 帧。
  4. TRUNK 口在 VID = 100 上是 Tagged Port，出交换机时不改动带标帧的结构。
  5. 到对端 TRUNK 口，同样因为拥有 VID = 100 而接收，收下后也不做改动。
  6. 对端交换机按转发原理把帧送给 VID = 100 的所有端口（除进口）。MAC 表还空着，所以仍是泛洪。
  7. 对端 ACCESS 口收到标签为 100 的帧，发出时去掉标签，以 untagged 交给 PC。

全程标签只在交换机之间那一段存在。两端的 PC 一无所知。

把 VID 和 PVID 摆在一起，差别一眼能看出来：

维度 VID PVID
归属对象 帧 端口
存在形式 帧头 4 字节标签里的 12 位 交换机配置里的一项属性
数量 一个帧只能有一个（QinQ 除外） 一个端口只有一个
作用时机 转发时决定去哪些口 收裸帧时决定补什么标、发帧时决定剥不剥

四、Access、Trunk 与 Hybrid 口 #

一句话把区别说完：Access 口只属于一个 VLAN、收发都不带标签，对终端；Trunk 口承载多个 VLAN、收发都带标签，对交换机。

维度 Access Trunk Hybrid
承载 VLAN 数 1 多个 多个
典型对端 PC、打印机、单网卡服务器 交换机、路由器、虚拟化宿主 交换机、需要混合标签的终端
收 untagged 帧 按 PVID 打标 按 PVID 打标，部分设备直接丢 按 PVID 打标

Access 口的完整定义：

  • 场景：接普通终端计算机、打印机这类不识别 VLAN 标签的设备。
  • 接收：从这个口收到 untagged 帧，强制打上该端口关联的 VLAN Tag（PVID）。
  • 接收：收到带标签的帧，丢弃。
  • 发送：给终端的帧自动剥离 VLAN Tag，终端察觉不到 VLAN 的存在。

Trunk 口的完整定义：

  • 场景：交换机与交换机之间，或者交换机与三层路由器之间（单臂路由）。
  • 保留标签：允许携带不同 VID 的 tagged 帧通过，收发都保留 802.1Q Tag。
  • 作用：一条物理线缆承载成百上千个 VLAN 的流量，跨交换机的同 VLAN 成员借此直连通信。

Hybrid 是华为、H3C 体系里的第三种模式。它一头能像 Access 那样给某个 VLAN 发裸帧，另一头能像 Trunk 那样给别的 VLAN 带标发帧——对同一个端口，逐 VLAN 配「带标」还是「不带标」。

典型用法：一个口接 IP 话机，话机自己会打 VLAN 100 的标签（语音），话机下挂的 PC 只会发裸帧（数据，VLAN 200）。

bash
port hybrid pvid vlan 200
port hybrid untagged vlan 200
port hybrid tagged vlan 100

结果：PC 的裸帧按 PVID 200 归进数据 VLAN；话机自己打的 VLAN 100 标签原样放行；交换机往这个口发 VLAN 200 的帧时剥标，发 VLAN 100 时带标。一个口干了两件事，省一根线。

Cisco 体系里没有 Hybrid 这个模式，等价的能力要靠 switchport trunk native vlan 加语音 VLAN 的组合去凑，效果不如 Hybrid 直白。

Linux 上没有「端口模式」这个概念。这些角色靠「物理口挂不挂 vlan 子接口」和「网桥开不开 vlan_filtering」来表达，第八章展开。

接反了就不通 #

现场最常见的错误，症状朴素得让人抓狂——就是不通。

场景 现象 原因

Trunk 口接 PC 不通 PC 协议栈不认 802.1Q，带标帧被丢

判断方法很直接：tcpdump -e -i eth0 抓一下，帧里有没有 vlan 100 一眼就看出来。带标签说明对端在发 trunk，这边当 Access 收，必然不通。

还有一个方向常被忽略：两端都配 Hybrid，但一边写了 tagged 另一边写了 untagged。帧发出去带标，对端按 untagged 收，直接丢。Hybrid 的自由度高，配置要求也就更严。

三种口怎么选 #

  • 接终端，一律 Access。除非终端自己会打标（服务器、IP 话机、无线 AP 的管理口）。
  • 交换机之间、交换机和路由器之间，一律 Trunk。
  • 一个口要同时给两种设备服务，或者要和虚拟化宿主对接一根线跑多个 VLAN，用 Hybrid 或者 trunk 加 native VLAN。
  • 拿不准的时候先按最笨的配：两端都 Trunk，允许列表写清楚。跑通了再优化。

五、VLAN 的划分方式：静态与动态 #

到这里端口类型说完了，往上退一层，问个更根上的问题：交换机凭什么决定「端口 1 属于 VLAN 10」？

配 VLAN 的动作永远是两步：先建 VLAN，再决定各端口归哪个 VLAN。第二步的手法有两条路——事先写死，或者跟着接进来的机器动态改。前者叫静态 VLAN，后者叫动态 VLAN。

静态 VLAN：按端口划分 #

静态 VLAN 又叫基于端口的 VLAN（Port Based VLAN），做法就是明确指定各端口属于哪个 VLAN。

在交换机上建若干 VLAN，把物理端口直接指定到对应的 VLAN。每个 VLAN 由一个 VID 标示，再由一个 vlan_mask 标示哪些端口和它同属一个虚拟网。这两样都放在设备寄存器里，由硬件自动访问识别，配一次就定死，跟谁在说话无关。

简化一点看，进交换机的帧上都可以不带 VID：硬件拿「这个帧是哪个口收到的」去索引 VID 表，就知道它该跟哪些口待在一起。这就是 untagged 模式的全部秘密——归属信息不在帧里，在硬件的端口表里。

一个 Access 口在某一时刻只有一个 PVID，交换机转发从该口进入的 untagged 帧时，完全依据该口的 PVID 查表。

它的局限很实在：

  • 得一个个端口地指定。网络里超过几百台机器，配置量就上来了，改一次要动几十条命令。
  • 客户机换了所连端口，必须同时改端口所属 VLAN。频繁调整拓扑的网络，这套方式很难受。
  • 两台交换机要打通两个 VLAN，就得在它们之间连两根网线，一个 VLAN 占一根。

它的好处同样实在：配一次管很久，行为可预测，转发时零额外开销，出问题只看配置就能定位。现场九成以上的部署都是这个。

动态 VLAN：按机器划分 #

动态 VLAN 反过来：根据每个端口所连的计算机，随时改变端口所属的 VLAN。机器走了，端口回到默认 VLAN；机器来了，端口自动进它该在的 VLAN。

按用到的信息层次，动态 VLAN 分三类：

类型 判定依据 在 OSI 哪一层
基于 MAC 地址的 VLAN 端口所连网卡的 MAC 地址 第二层
基于子网的 VLAN 端口所连计算机的 IP 地址 / 子网 第三层
基于用户的 VLAN 端口所连计算机上登录的用户 第四层以上

三层之间的差别就一句话：判定用的信息越靠上层，网络结构越灵活。下面逐个看。

基于 MAC 地址的 VLAN #

交换机查询并记录端口所连计算机网卡的 MAC 地址，拿这个决定端口归属。假定 MAC 地址 A 被设定为属于 VLAN 10，那么不论这台机器插在交换机的哪个口，那个口都会被划进 VLAN 10：插 1 号口时 1 号口属于 VLAN 10，插 2 号口时 2 号口属于 VLAN 10。

它的好处是「人跟着 VLAN 走」。员工换工位、搬楼层，不用改任何交换机配置，插上就进自己的 VLAN。会议室、共享工位这种场景，听起来正合适。

代价在维护上：部署前得把全公司每台机器的 MAC 地址调查清楚并登记进数据库，几千台机器的工程量不小；机器换了网卡，MAC 变了，数据库要跟着改；交换机每收到一个帧都要查这张表来决定端口归属，开销比静态方案大。

基于子网（IP 地址）的 VLAN #

按所连计算机的 IP 地址（准确说是它属于哪个子网）决定端口所属 VLAN。

它比 MAC 方案好在一个地方：机器换了网卡、MAC 变了，只要 IP 不变，仍然留在原先设定的 VLAN 里。改网络结构的时候，动 IP 就够，不用碰交换机端口配置。

代价在依赖关系上：交换机得解析三层头，要能看见 IP 地址才谈得上判断。判断的时机也有讲究——机器刚上电还没拿到 IP 时，端口归哪个 VLAN？多数实现会先放进一个临时 VLAN，等地址拿到再迁移，这个过渡期能出问题。IP 配错的情况下，机器会被划进错误 VLAN，现象是「网线插对了、地址也 ping 不通」。

基于用户的 VLAN #

按端口所连计算机上当前登录的用户决定归属。识别信息一般是操作系统登录名，比如 Windows 域里的用户名。

这类方案背后要有一套认证在跑——802.1X、RADIUS、Portal，用户认证过了，交换机收到 RADIUS 返回的属性，把端口挪进对应的 VLAN。医疗、教育行业里见得到：医生在哪个诊室登录，那个诊室的口就进他所在科室的 VLAN。

它的麻烦之处在于全是厂商私有协议，不同厂商的设备之间对接，兼容性问题得提前验证。

我们怎么选 #

默认全上静态。理由三条：行为可预测、排错只看一侧配置、转发没有额外开销。办公网里按部门划端口，一个部门一片口，配一次能管两三年。

动态只在「口不固定」的地方有价值：会议室、培训教室、医院病房、共享工位，或者设备频繁迁移的产线。这些场景里，静态方案每搬一次机器就得改一次配置，人力成本比数据库维护高。

真要用动态，先确认三件事：交换机厂商支持哪种动态 VLAN、认证系统能不能配合、跨厂商互联时协议是否兼容。这三件事没确认，先按静态做，别拿生产网试。

静态 VLAN 的两种落法：裸帧与带标 #

同样是静态划分，端口在 VLAN 上的形态还有两种：

Untagged 模式：端口只认裸帧，进来打标，出去剥标。上面说的「硬件用端口表索引 VID」就是这种，一个口一个 VLAN，帧上不带 VID 也能跑完全部功能。

Tagged 模式（Tagged VLAN）：端口支持接收并转发带 Tag 的帧（Tagged Port）。连在这个口上的设备必须兼容 802.1Q，能解析并还原帧头的 VID 字段。靠着它，一根 Trunk 网线就能跨交换机传多个 VLAN，隔离照旧。

对比项 基于端口（untagged） Tagged VLAN
帧里有没有 VID 没有 有
归属信息存在哪 交换机的端口表、寄存器 帧头的 VID 字段
交换机之间要几根线 每个 VLAN 一根 一根 trunk 足够
对端设备要求 无 必须认 802.1Q

承载多个 VLAN 的端口叫 trunk 口，上面收发的帧必须带 vlan_head，否则分不清属于谁；只承载一个 VLAN 的端口叫 access 口，硬件支持的话不带 vlan_head 也能完成全部功能。

裸帧与带标这套二分法，是理解「为什么需要汇聚链路」的钥匙：一根线上跑多个 VLAN，帧上必须写清楚归属。至于这个「写」用哪种格式，是第七章的事。

六、VLAN 的转发规则 #

交换机配了 VLAN，内部的帧统一按带标签处理。这一条是整个转发逻辑的前提：硬件流水线只有一套，不做两套路径，所以进门先补标签，出门再按需剥掉。

入口三判定 #

端口收到帧，第一件事是读 TPID，判断它带不带标签。

  1. tagged 帧、且 VID ≠ 0：在端口所属的 VLAN 表里查这个 VID 存不存在。存在，进下一步；不存在，丢弃（或者提交 CPU 处理）。
  2. tagged 帧、且 VID = 0：这是 priority-tagged 帧，给它补上端口 PVID，变成 tagged 帧。
  3. untagged 帧：给它补上端口 PVID 并指定优先级，变成 tagged 帧。
入帧形态 识别依据 交换机的动作
untagged 无 TPID 打上端口 PVID，指定优先级，转成内部 tagged 帧
priority-tagged TPID = 0x8100，VID = 0 补上端口 PVID，保留原优先级
tagged TPID = 0x8100，VID ≠ 0 查端口 VLAN 成员表，在表内放行，不在表内丢弃
其它 TPID 0x88a8 等 按设备能力处理，QinQ 设备认，普通设备当无效帧丢

这三条判定的本质是「补标签」：内部只有带标帧，进来的裸帧必须先被赋予归属。补的依据是端口，不是帧。所以同一个帧从不同的口进来，归属就不同——这正是静态 VLAN 的全部魔法。

MAC 表从二维变三维 #

没配 VLAN 时，MAC 表记的是「MAC 地址 → 物理端口」。配了 VLAN 之后，表项升级成「MAC 地址 + VLAN ID → 物理端口」。

项目 未配 VLAN 配了 VLAN
表键 目的 MAC 目的 MAC + VID
表值 出端口 出端口
逻辑结构 一张全局表 按 VID 分区，等价于每个 VLAN 一张表
冲突后果 不同 VLAN 的同 MAC 会互相覆盖 不同 VID 下同名 MAC 互不干扰

学习规则不变：只学单播源地址，广播和组播地址不学，组播表项由 CPU 配置建立。

  • 在表里找到收帧 VID 对应的源 MAC 表项 → 更新老化时间。
  • 找不到 → 学习「源 MAC + VID + 端口」，写进表。

三维表带来的一个直接后果：VRRP、HSRP 这类虚拟网关会在多个 VLAN 里出现相同的虚拟 MAC。没配 VLAN 的交换机会被这种重复 MAC 打乱，配了 VLAN 之后按 VID 分区，各走各的表项，互不干扰。

目的查找与转发 #

  • 目的 MAC 是广播或组播 → 在该 VLAN 内广播 / 组播。
  • 否则在 MAC 表里查 VID 对应的目的 MAC 表项：
    • 找到完全匹配的 DMAC + VID → 转发到表项里的端口。若那个端口就是收帧端口，丢弃。
    • 没找到 → 向本 VLAN 内除收包端口外的所有端口洪泛。

这里有个说法要抠清楚：洪泛送出去的是未知单播帧，不是广播帧。只是在行为上，它们一样会被复制到多个端口。

Trunk 上那个剥标的 VLAN，Cisco 叫 native VLAN，华为叫 PVID VLAN，值就是端口的 PVID。两台交换机互联时 native VLAN 配成不一样，就会出现著名的一类故障：VID = 10 的帧从这头出去时被剥了标，到那头按对端 PVID = 20 打标，于是 VLAN 10 的流量整段串进了 VLAN 20。VLAN 泄漏大多是这个来源。

这条故障的阴险之处在于「能通」。业务看起来正常，只是偶尔有机器拿到别的网段的地址，或者两台本该隔离的机器突然能互访。查的时候别只看配了哪些 VLAN，要专门核对两端的 native VLAN。

洪泛与广播的边界 #

配了 VLAN 之后，广播帧的转发被约束成两条原则：

  1. 发给本交换机中同一个 VLAN 的其它端口。
  2. 发给本交换机包含该 VLAN 的所有汇聚链路，让其它交换机上同一 VLAN 的端口也收到。

拿一台 4 口交换机举例：端口 1、2 属于红色 VLAN，端口 3、4 属于蓝色 VLAN。PC1 接端口 1，它发出的广播帧只被转发到同在红色 VLAN 的端口 2，绝不会到端口 3、4，也不会顺着没有红色 VLAN 的链路跑出去。

VLAN 就是这样靠限制广播帧的转发范围来分割广播域，顺带把网络效率和终端负载一起改善了。

三步走 #

把前面的规则压成三步，任何一次二层转发都是这三步：

  1. 确定和查找 VLAN：读 TPID，决定打标、补标还是丢弃。
  2. 查找和学习源 MAC：在「MAC + VID + 端口」表里更新。
  3. 查找目的 MAC 并转发：命中就单播，没命中就在本 VLAN 内洪泛。
text
  PC1 ---[Access/PVID=100]---[ SW1 ]===trunk===[ SW2 ]---[Access/PVID=100]--- PC2

完整走一遍 #

SW1 的 Access 口接 PC1，Trunk 口接 SW2；SW2 的 Trunk 口接 SW1，Access 口接 PC2。两台交换机刚开机，MAC 表为空。

  1. PC1 发出的裸帧进 SW1 的 Access 口，按端口 PVID 打上 VID = 100 的标签。SW1 把这个帧的源 MAC 学进表（源 MAC + VID 100 + 入端口），再把帧洪泛到 VID = 100 的所有端口（除入端口）。
  2. SW1 的 Trunk 口属于 VID = 100，所以接受这个标记为 100 的 tagged 帧。该口在 VID 100 上是 Tagged Port，出交换机时不改动帧结构。
  3. tagged 帧到达 SW2 的 Trunk 口。该 Trunk 口拥有 VID = 100，接受。它不改动帧结构，学完源 MAC 后把帧洪泛给所有 VID = 100 的端口（除入端口）。
  4. SW2 的 Access 口收到帧，剥掉标签，裸帧交给 PC2。
  5. PC2 回一个响应帧给 PC1。
  6. 响应帧按类似过程回到 SW1。此时 SW1 的 MAC 表里已经有 PC1 的表项，只转发给 PC1，不再洪泛。

收发双方同属一个 VLAN，全程二层完成，一次路由都没走。

为什么内部统一带标 #

交换机内部有一条处理原则：为提高处理效率，内部所有数据帧都携带 VLAN 标签，用统一方式处理。所以入口必须做标签检查、按需补齐。

802.1Q 环境下帧分三种：tagged、untagged、priority-tagged。tagged 帧按自带的 VID 做 MAC 学习转发；untagged 和 priority-tagged 帧进端口后按 PVID 做 MAC 学习转发。

如果硬件为带标帧和不带标帧各做一条流水线，代价是面积翻倍、逻辑复杂。统一成带标帧之后，后面所有模块只需要处理一种格式，这就是「进门补标、出门剥标」这个设计的来源。

VLAN 密度带来的负担 #

Trunk 上每个 VLAN 的广播都要占一份带宽。VLAN 越多，trunk 上的广播负载越重——因为每条链路都要给每个 VLAN 送一份广播。接入层把几百个 VLAN 全推上一条 trunk，等于把所有广播域又拼回了一个。

这也是为什么大二层设计里要给 trunk 做 VLAN 裁剪：只放行真正需要的 VLAN，别图省事写 allowed vlan all。

一台二层交换机最核心的三个功能，配了 VLAN 之后都在原基础上加了一层判定：MAC 地址学习带上 VID、数据帧转发（单播 / 广播 / 洪泛）限在本 VLAN、标签在进出口处添加与剥离。

七、汇聚方式：802.1Q 与 ISL #

第六章一路说「帧上带标」，这一章说清楚这个标是怎么加上去的。

一根线要跑多个 VLAN，帧上就得写清楚「这帧是谁的」。干这件事的协议有两个代表：IEEE 802.1Q 和 ISL。

802.1Q：在帧中间插 4 字节 #

IEEE 802.1Q，口头叫「Dot One Q」，是经过 IEEE 认证的、给数据帧附加 VLAN 识别信息的标准协议。

它的做法在第二章已经画过：在「发送源 MAC 地址」与「类型域」之间插入 2 字节 TPID 加 2 字节 TCI，一共 4 字节。

text
802.1Q：插进去
+-----------+-----------+-------------+-----------+------------------+
| DMAC (6)  | SMAC (6)  | TPID=0x8100 | TCI (2)   | Type + Payload   |
+-----------+-----------+-------------+-----------+------------------+
                              ^ 新插入 4 字节，原帧内容不变

有两件事跟着变：

  • CRC。帧里多了 4 字节，校验值自然变了。帧上的 CRC 是插入 TPID、TCI 之后对包括它们在内的整个帧重新算出来的。
  • 帧长。最大帧从 1518 变 1522，第二章说过。

帧离开汇聚链路时，TPID 和 TCI 被去掉，这时还要再算一次 CRC。也就是说，一次进出 trunk，交换机要算两次 FCS。现在的网卡和交换芯片都把这个算在硬件里，代价看不见；早期用软件转发的时候，这笔开销是实打实的。

基于 802.1Q 附加 VLAN 信息，像在传递物品时贴一张标签，所以它也被叫「标签型 VLAN」（Tagging VLAN）。

ISL：整个帧外面包一层 #

ISL（Inter Switch Link）是 Cisco 产品支持的、与 802.1Q 类似的协议，作用同样是给汇聚链路上的帧附加 VLAN 信息。

做法完全相反：它不动原帧，而是把整个帧包起来。

每个数据帧前面加 26 字节的 ISL 包头，帧尾再加 4 字节 CRC——这个 CRC 是对包括 ISL 包头在内的整个帧算出来的。两笔加起来，总共多 30 字节。

text
ISL：包起来
+------------------+------------------------------------+---------------+
| ISL Header (26)  | 原始以太网帧（含它自己的 4 字节 FCS）| 新 FCS (4)    |
+------------------+------------------------------------+---------------+
       ^ 含 VLAN ID 15 位、BPDU/CDP 标志、序号等

26 字节包头里塞的东西：40 位固定目的地址（0x01000C0000，标记这是 ISL 帧）、4 位帧类型、4 位用户字段、源 MAC、长度、SNAP 头 0xAAAA03、源 MAC 高 24 位、15 位 VLAN ID、BPDU 与 CDP 标志、端口索引、保留位。

15 位 VLAN ID 是 ISL 的一个技术优势：它能表达 1~4095 中的大部分值，802.1Q 只有 12 位。实际部署里谁也用不到 4094 个 VLAN，这个优势没换来市场。

剥的时候特别省事：把 ISL 包头和新 CRC 扔掉就完了。原帧和它自己的 CRC 完整保留在里面，不用重算 FCS。这是封装型方案唯一比插入型方案便宜的地方。

因为整个帧被包起来，ISL 也被叫「封装型 VLAN」（Encapsulated VLAN）。

两者摆一起 #

维度 IEEE 802.1Q ISL
归属 标准，IEEE 定义 Cisco 私有
附加方式 在源 MAC 后插入 4 字节 原帧外包 26 字节头 + 4 字节尾
总开销 4 字节 30 字节
原帧是否改动 改了（插入标签） 不改，整体保留
出链路时 删掉标签，重算 FCS 扔掉包头和新 FCS，不重算
VLAN 数量 12 位，4094 个可用 15 位
跨厂商 通用 只能纯 Cisco 环境
抓包 tcpdump 直接看得见 vlan 要专用解析，wireshark 认但少见
现状 事实标准 边缘化，新设备默认推 802.1Q

开销上的差别在小包上最明显。64 字节的帧（不含前导码）走 802.1Q 变 68 字节，走 ISL 变 94 字节。同样一段链路，ISL 的每秒包数上限被拉低近三成。跑大量小包的场景（语音、DNS、游戏、金融行情），这个差别不能忽略。

结论不复杂：跨厂商的链路必须用 802.1Q，没有第二个选择。ISL 只在纯 Cisco 的老环境里见到，新上设备不要再配。真碰上 ISL 的老网络要接新设备，把两端封装改成 dot1q 是最省事的做法。

两端封装必须一致 #

一条 trunk 的两端封装协议不同，结果就是完全不通：一端按 ISL 打包，另一端按 802.1Q 解析，TPID 对不上，帧被当垃圾丢掉。

Cisco 设备上查这一项：

bash
show interfaces GigabitEthernet0/1 trunk
show interfaces switchport

输出里的 Encapsulation: 802.1q 或 ISL 就是它。看到 Encapsulation: negotiate，说明端口还在自动协商（DTP），这种配置在生产网里是隐患——协商结果谁都不确定，配成固定值更稳。

trunk 的默认行为与裁剪 #

默认条件下，汇聚链路会转发交换机上存在的所有 VLAN 的数据。换个角度看，可以认为汇聚链路同时属于交换机上所有的 VLAN。

实际不需要转发所有 VLAN。为了减轻交换机负载、也为了少浪费带宽，要限制能经由汇聚链路互联的 VLAN：

bash
# Cisco：只放行 10、20、30
switchport trunk allowed vlan 10,20,30
switchport trunk allowed vlan add 40
switchport trunk allowed vlan remove 20

bash
# 华为 / H3C：允许列表
port trunk allow-pass vlan 10 20 30

改允许列表的时候有个顺序讲究：add 是加，remove 是减，别用「重新配一遍完整列表」的方式，那会把中间态暴露出来。生产网上改 trunk 允许列表，先加后删，分两次提交。

另外，汇聚链路上流通着多个 VLAN 的数据，负载本来就比接入链路重。设定汇聚链路有个前提：链路速率要够。早年这条写的是「必须 100Mbps 以上」，现在的入门设备都是千兆起，这句话的真正含义变成了——别拿一条百兆线当十几条 VLAN 的骨干。

以太网封装之外还有一层历史包袱：早年有些设备的 trunk 只能用 ISL，有些只能用 802.1Q，混着用就必须两端对齐。今天这个包袱基本没了，802.1Q 通吃。

后面几章换到 Linux 视角：手里没有交换机的 ASIC，VLAN 怎么做。

八、Linux 下 VLAN 的实现方式 #

没有交换机硬件，那就造一个设备 #

Linux 做 VLAN 不去改交换机的寄存器，它在软件里造虚拟设备。加载 8021q 模块，你就在一块真实网卡上虚拟出若干个带标签的网口。eth0.10 对上层来说是一张网卡：有自己的 IP、自己的路由表项、自己的 netfilter 规则链。

关键是理解 net_device 不等于硬件。只要把一个 struct net_device{} 注册进内核，这个网络设备就存在了，哪怕背后一根线都没有，lo 回环设备就是最好的例子。VLAN 设备和网桥设备走的都是这条路。

设备类别 是否依赖别的设备 例子 模块初始化函数
传统设备 独立存在 eth0、lo netdev_init()，net/core/dev.c
VLAN 设备 依赖宿主，宿主没了它不能用 eth0.10 vlan_proto_init()，net/8021q/vlan.c
网桥设备 虚拟，依赖从设备 br0 br_init()，net/bridge/br_device.c

这三类都以 module 形式进内核，可以看成网络子系统的顶层模块，下面那些驱动模块都依赖它们。它们有各自特有的初始化动作，比如 netdev_init() 里要分配 softnet_data；也有共同的套路，比如都要处理网络设备的 ioctl。

控制面怎么进来 #

在 Linux 里，所有网络设备的 ioctl 都被抽象成对 /proc/net/ 下文件的操作，最终落到内核的 sock_ioctl()，再由各子系统的 hook 函数分发。这些 hook 就是各模块 init 时用 ioctl_set_func() 装上去的。

vconfig add eth0 10 就是打开 /proc/net/vlan/config 做 ioctl。映射到内核是 net/8021q/vlan.c 的 vlan_ioctl_handler()，add 这条最终调 register_vlan_device(real_dev, vid)。vconfig 的源码很短，全是对这个文件的 ioctl 调用。

这套设计的好处是用户态不用为每种虚拟设备学一套系统调用，网桥、VLAN、tunnel 都塞进同一个框架。今天的 ip link 改走 rtnetlink，内核里那条 ioctl 路径还留着兼容，报文格式与实现在「Netlink」那篇。

创建时干了三件事 #

register_vlan_device() 的过程拆开看：

  1. 申请一个新的 struct net_device，并为它分配 struct vlan_dev_priv 型的私有空间（vlan.h），把初始化函数指为 vlan_setup。
  2. vlan_setup 把 flag 设成 802.1Q，把发送队列数设成 0，把 netdev_ops 指为通用的 vlan_netdev_ops。这个 ops 表直接决定了 vlan 设备的工作方式。
  3. 回填私有空间里的宿主设备指针与 VID，同时更新宿主设备的 vlan_info 信息；最后把新设备注册进全局 netdevice 链表。

第三步做完，eth0.10 与其它设备地位平等，能用 ifconfig 配，能加进网桥，也能被路由选中。

发送队列设成 0 这件事直接影响发送路径：dev_queue_xmit() 发现没有队列，就绕开 qdisc 直接进 dev_hard_start_xmit()。排队、qdisc、软中断的细节看「数据收发路径」。

相关代码分布在三个文件：vlan.c 主要是 ioctl 与设备注册，vlan_core.c 是与 VLAN 相关的核心操作，vlan_dev.c 是设备侧代码。

VLAN 处理挂在哪个钩子上 #

网络设备的驱动框架里，每个驱动最要紧的是 5 个函数：

函数 职责
dev_open() 打开设备，初始化私有空间
hard_start_xmit() 把数据写进发送缓存、写寄存器通知硬件
interrupt() 中断处理，收包时准备 skb 并往上递
poll() NAPI 轮询，批量取包
tx_timeout() 发送超时回调，由 watchdog_timer 触发

私有空间由 netdev_alloc() 分配（本质是 alloc_netdev_mqs(n, 1, 1)），默认一发送队列一接收队列。队列结构 netdev_queue 里挂着 Qdisc，负责多进程共用一块网卡时的锁定。

VLAN 的处理不在这 5 个函数里，而在两个设备无关的中间层：

  • 发送：dev_queue_xmit() → dev_hard_start_xmit()（VLAN 检查与插标在这里）→ ndo_start_xmit()
  • 接收：中断或 NAPI → netif_receive_skb() / __netif_receive_skb()（VLAN 检查与剥标在这里）→ deliver_skb() 交给上层协议

所以 VLAN 对驱动是透明的：驱动不知道自己在传一个带标签的帧，插标剥标全在框架层完成。驱动框架与收发队列的完整展开看「数据收发路径」。

发送：改指向，回到真实网卡 #

eth0.10 被路由选中当出口时，上层调 dev_queue_xmit(vlan_dev)。tx_queue 为 0，流程直奔 dev_hard_start_xmit()。

这个函数是设备无关的，负责检查并处理 skb 上的各种特性，VLAN 的处理就落在这里：

  1. 检查 skb 的 VLAN 标志。有，就往帧里插入 vlan_tag，把 skb->protocol 改成 802.1Q。
  2. 清掉 skb 里的 VLAN 标志。
  3. 调 skb->dev->ops->ndo_start_xmit()，也就是 vlan_netdev_ops 里的 vlan_dev_hard_start_xmit()（net/8021q/vlan_dev.c）。

vlan_dev_hard_start_xmit() 干的是重定向：把 skb 的设备改回 real_dev，用真实网卡重新走一遍发送流程。

为什么不直接调 real_dev->ndo_start_xmit()？因为 real_dev 会同时被多个 vlan_dev 共用，必须重新做设备锁定、重新选队列。网桥不同：网桥的端口从设备只为它自己所用，直接调 real_dev->ops->ndo_start_xmit() 就行。

skb 里为什么一开始就带着 VLAN 标志？上层选中 vlan_dev 时，靠它的 priv_flags 认出这是个 VLAN 设备，于是给它打上标志。标签插入的精确时机和位域操作在「VLAN 模块源码分析」那篇逐行看。

接收：先剥标签，再改指向 #

接收是被动过程，入口一定是 real_dev 的驱动。网卡收到的只是一串比特流，协议栈只能按比特流里特定字节的取值判断它是不是 VLAN 包——MAC 地址后面跟着 0x8100，那就是。

  1. netif_receive_skb() 走到 __netif_receive_skb()，检查 skb，包括 VLAN 检查。
  2. 判定是 802.1Q 帧，调 vlan_untag()：读出数据流里的 VID 填进 skb->vlan_tci，然后删除 VLAN 头。此刻 skb 里是一个干净的以太网包，对上层完全透明。
  3. 发现 skb->vlan_tci 置位，调 vlan_do_receive()：由 tci 找到该帧要去的 vlan_dev，把 skb->dev 改成它，再清掉 tci 标志。
  4. 流程回到 netif_receive_skb() 继续往上。此时这个包看起来就像是从 eth0.10 收到的。

vlan_tci 只是中转路标，不跟着包往上走。真要让用户态看见标签，得用 PACKET_AUXDATA。

vlan_dev 的硬件地址必须和 real_dev 相同，否则发往 vlan_dev 的包到不了真实硬件。

硬件加速 #

真实网卡大多支持 VLAN offload，此时标签由网卡插、由网卡剥，内核完全不碰：

特性 ethtool 键 行为
发送插入 txvlan 内核只写 skb->vlan_tci，网卡发帧时插标签
接收剥离 rxvlan 网卡剥掉标签，把 VID 填进 skb->vlan_tci 再交给内核 
bash
ethtool -k eth0 | grep vlan
ethtool -K eth0 rxvlan off    # 关掉接收剥离，让 tcpdump 看得见标签

这也解释了那个常见困惑：链路确实是 trunk，tcpdump -e 却看不到 vlan 字段。标签在网卡里就被摘掉了，抓包点在其后。

虚拟机网卡、虚拟交换机这类纯软件设备也有同样的开关：virtio-net 支持 VLAN 剥离，DPDK 里也有对应的 offload 标志位。抓不到标签时先查这个，别急着改交换机。

宿主口必须是对端的 trunk #

Linux 的 VLAN 模型是「宿主设备 + 若干虚拟子接口」，宿主物理口对应的对端必须是 trunk 口，并且允许这些 VID 通过。

原因很直接：发往 vlan 设备的数据包都会被打上 vlan_head，vlan 设备收到的数据包默认都带 vlan_head 并被剥掉。这正好是 trunk 口的定义。对端要是 Access 口，带标帧全被丢，一个都通不了。

这套虚拟化架构为了虚拟出 vlan 端口，做得比较臃肿：每个 VLAN 一个 net_device，帧要一层层重定向。真要把一台交换机的芯片用 Linux 驱动起来，得充分利用硬件的 VLAN 表与端口掩码，照搬这套模型性能不会好看。

十、VLAN 与网桥的组合 #

Linux 里把 VLAN 和网桥放在一起，有两种完全不同的模型。选错了，后面每一行配置都在跟自己打架。

模型一：桥接 VLAN 子接口 #

先建 vlan 子接口，再把子接口塞进网桥。物理口不做任何 VLAN 相关配置，它只是承载标签的通道。

bash
# 每个 VLAN 一个网桥，一个网桥就是一个广播域
ip link add link eth0 name eth0.10 type vlan id 10
ip link add link eth0 name eth0.20 type vlan id 20
ip link add name br10 type bridge
ip link add name br20 type bridge

ip link set eth0.10 master br10
ip link set eth0.20 master br20

ip link set eth0.10 up
ip link set eth0.20 up
ip link set br10 up
ip link set br20 up

虚拟机、容器、tap 设备接进来，就是往对应的网桥上挂：

bash
ip link set veth10 master br10

要三层能力，就给网桥本身配地址——此时 br10 上的 IP 就是 VLAN 10 的网关地址。

bash
ip addr add 192.168.10.1/24 dev br10

这个模型里，VLAN 的划分完全由「哪个子接口挂在哪个网桥」表达，网桥本身对 VLAN 一无所知。

模型二：网桥开 vlan_filtering #

物理口直接进网桥，网桥自己认 VLAN 标签，用 bridge vlan 配端口成员与 PVID。这才是和交换机对齐的那套语义。

bash
# 建网桥时就要打开 vlan_filtering，运行中改要重建
ip link add name br0 type bridge vlan_filtering 1
ip link set eth0 master br0
ip link set eth1 master br0
ip link set eth0 up
ip link set eth1 up
ip link set br0 up

# eth0 当 trunk：VLAN 10、20 带标通过
bridge vlan add dev eth0 vid 10
bridge vlan add dev eth0 vid 20

# eth1 当 access：PVID = 10，出帧不带标
bridge vlan add dev eth1 vid 10 pvid untagged

# 网桥自身也要加入 VLAN，否则配不上 IP、当不了网关
bridge vlan add dev br0 vid 10 self

bridge vlan show

三条规则决定这个口是什么角色：

命令形态 端口在该 VID 上的角色
bridge vlan add dev X vid 10 tagged 成员，出帧保留标签，等同 trunk 上放行 VLAN 10
bridge vlan add dev X vid 10 pvid untagged untagged 成员 + 该 VLAN，等同 Access 口
bridge vlan add dev X vid 10 untagged untagged 成员，但不改 PVID，用于 Hybrid 那种混搭

几个要点：

  • pvid 一个口只有一个，重复设置会覆盖前一个。
  • self 表示这项 VLAN 成员是给网桥设备自己的，不给它，br0 就没有 VLAN 10 的接口，配 IP 也没用。
  • vlan_filtering 1 需要内核 3.15 以上，老内核会直接报错。
  • 一个口既是 trunk 又是 access 的场景（Hybrid），在模型二里天然支持：对 VLAN 10 加 pvid untagged，对 VLAN 20 只加 vid 20。

两种模型怎么选 #

维度 桥接子接口 网桥 vlan_filtering
一个网桥承载几个广播域 1 个 多个
net_device 数量 每 VLAN 一个子接口 + 每 VLAN 一个网桥 一个网桥 + 若干物理口
与交换机概念对应 弱，靠命名约定 强，pvid / tagged / untagged 一一对应
上手成本 低 中
支持 Hybrid 那种混搭 不支持，一个子接口只有一种 VID 支持，逐 VLAN 配
典型场景 虚拟化宿主、容器网络 软交换机、OpenWrt、家用路由器

判断标准不复杂：VLAN 数量少、结构固定，模型一写起来直白；VLAN 多、要跟硬件交换机对配置、或者一个口要同时跑带标与不带标，上模型二。

两种模型都不能干的事 #

  • 一个网桥不能同时属于两个 VLAN。VLAN 是广播域，网桥也是广播域，一对一。
  • 别在同一个物理口上既挂 vlan 子接口又开 vlan_filtering，两套机制会互相拆台，症状是随机丢帧。

十一、VLAN 间的通信与三层交换机 #

同 VLAN 与跨 VLAN #

  • 同 VLAN：二层直接转发，不经过任何三层设备。
  • 跨 VLAN：ARP 请求出不了自己的广播域，主机拿不到对方 MAC，必须经三层设备。

把这件事说透一点：LAN 内通信必须在帧头写目的 MAC，拿到 MAC 靠 ARP，ARP 靠广播。广播过不去，MAC 就解析不出来，通信自然不成立。VLAN 切开了广播域，也就切断了这条链。

网关是那道门 #

路由器可以看成各个 VLAN 的网关。通过路由器互通的主机，必须知道路由器的存在，以及它在本 VLAN 上的接口地址——这就是默认网关。配好默认网关后，跨 VLAN 的报文不会直接发给目的主机，而是先交给网关。

反过来看一条判据：当报文的目的 MAC 是网关的 MAC 时，这个报文就是要做三层转发的报文。抓包看到这一条，立刻能分清这个包是留在本网段还是出网段。

三种做法 #

做法 设备 接口形态 适用场景
单臂路由 路由器 一个物理口 + 多个 802.1Q 子接口 小网络，VLAN 少
SVI 三层交换机 interface vlan 10 虚拟接口 主流做法，转发走硬件
Linux 主机路由 Linux 服务器 多个 vlan 子接口 + ip_forward 实验、小规模、边缘节点

单臂路由（Cisco 风格），物理口不配地址，全靠子接口：

bash
interface GigabitEthernet0/0
 no shutdown
interface GigabitEthernet0/0.10
 encapsulation dot1Q 10
 ip address 192.168.10.1 255.255.255.0
interface GigabitEthernet0/0.20
 encapsulation dot1Q 20
 ip address 192.168.20.1 255.255.255.0

子接口的 dot1Q 号必须和交换机 trunk 允许的 VLAN 对上，对不上就是「网关配了但没人能到」。

三层交换机用 SVI，配置更短，转发靠 ASIC：

bash
vlan 10
vlan 20
interface vlan 10
 ip address 192.168.10.1 255.255.255.0
interface vlan 20
 ip address 192.168.20.1 255.255.255.0
ip routing

Linux 自己当网关，就是把本篇的东西组装起来：

bash
ip link add link eth0 name eth0.10 type vlan id 10
ip link add link eth0 name eth0.20 type vlan id 20
ip addr add 192.168.10.1/24 dev eth0.10
ip addr add 192.168.20.1/24 dev eth0.20
ip link set eth0.10 up
ip link set eth0.20 up
sysctl -w net.ipv4.ip_forward=1

两个网段都直连在这台主机上，路由表自动生成，不用手写。主机侧配 ip route add default via 192.168.10.1 就能跨 VLAN。

要留意的两点：ip_forward 只在当前生效，持久化得写 /etc/sysctl.d/；主机如果只在一个 VLAN 上有地址，另一个 VLAN 的机器访问它就得靠策略路由，不能指望加一条静态路由解决。

单臂路由走一遍 #

设 VLAN 1（红）是 192.168.1.0/24，VLAN 2（蓝）是 192.168.2.0/24，四台机器 A、B、C、D 分别接在端口 1、2、3、4，端口 6 接路由器，MAC 为 R。

交换机的 MAC 表是这样的：

端口 MAC VLAN
1 A 1
2 B 1
3 C 2
4 D 2
6 R 汇聚（所有 VLAN）

A 找 B（同 VLAN）：A 发 ARP，交换机按 MAC 表查同 VLAN 表项，找到 B 在端口 2，转发过去。全程在交换机内部完成。

A 找 C（跨 VLAN）：A 比较 IP，发现不同网段，于是把帧发给默认网关，先 ARP 求出 R 的 MAC。之后是四步：

  1. A 发出数据帧：目的 MAC 是 R，目的 IP 仍是 C。从端口 1 进来。
  2. 交换机查与端口 1 同属 VLAN 1 的表项。汇聚口被视为属于所有 VLAN，所以端口 6 参与查找，查到 R 在端口 6。出端口 6 是汇聚链路，帧被加上红色 VLAN 的识别信息。
  3. 路由器收下，按 VLAN 标签判定归红色 VLAN 子接口。查路由表，目的网段 192.168.2.0/24 直连蓝色 VLAN 子接口，于是从蓝色子接口转发：目的 MAC 改写成 C，打上蓝色 VLAN 标签。
  4. 交换机收到，按蓝色 VLAN 查表，C 在端口 3，端口 3 是 access 口，剥掉标签交给 C。

注意第 3 步：一块物理网卡上，两个子接口各自收发，帧的 MAC 被改写两次。跨 VLAN 通信即使双方接在同一台交换机上，也要走「发送方 → 交换机 → 路由器 → 交换机 → 接收方」这一整圈。

路由器为什么成了瓶颈 #

路由器做 VLAN 间路由，瓶颈在三处：

  • 路由器基本靠软件转发，即使以线速收到包，也发不那么快。交换机用 ASIC 转发，能做到线速。
  • 所有跨 VLAN 流量都挤在「交换机—路由器」那一条汇聚链路上，这条链路是单点。
  • 物理上要摆两台设备，机柜空间紧张的地方连位置都成问题。

运营商和企业网里，跨 VLAN 流量的占比不低。一个机房里几十个 VLAN 互访，全靠一台路由器，它必然成为整个网络最慢的一跳。

三层交换机：把路由模块搬进机箱 #

三层交换机本质上是「带路由功能的二层交换机」。路由是第三层的活，所以带三层路由功能的交换机就叫三层交换机。

它在一个机箱里放了两块东西：交换模块和路由模块。关键在后者——路由模块和交换模块一样用 ASIC 处理，不是软件转发。两块模块之间用内部汇聚链路连接，是内部总线，带宽远高于外部线缆。

text
+------------------------------------------+
|  三层交换机                              |
|  +-------------+       +--------------+  |
|  |  交换模块   |=======|   路由模块   |  |
|  |  (ASIC)     | 内部  |   (ASIC)     |  |
|  +-------------+ 汇聚  +--------------+  |
|     |  |  |      链路                    |
+-----+--+--+-------------------------------+
      |  |  |
     PC A  PC B  PC C

一台路由器用子接口对应各 VLAN；三层交换机在内部生成「VLAN 接口」（VLAN Interface），Cisco 的 Catalyst 系列管它叫 SVI（Switched Virtual Interface）。每个 VLAN 一个 SVI，SVI 上配这个 VLAN 的网关地址。

同 VLAN 内通信：A 找 B，交换机查同 VLAN 的 MAC 表，B 在端口 2，直接转发。路由模块压根不参与。

跨 VLAN 通信：A 找 C，走四步。

  1. A 判断 C 不在同网段，把帧发给网关（SVI 的地址）。帧进交换机（Frame 1）。
  2. 交换机查 MAC 表，发现下一跳在内部路由模块，于是经内部汇聚链路把帧送给路由模块。过内部链路时，帧被打上红色 VLAN 标签（Frame 2）。
  3. 路由模块按标签判定归红色 VLAN 接口，查路由表，目的网段 192.168.2.0/24 对应蓝色 VLAN，于是从蓝色 VLAN 接口经内部链路转回交换模块，这次打蓝色标签（Frame 3）。
  4. 交换模块收到，查蓝色 VLAN 的 MAC 表，C 在端口 3，端口 3 是 access 口，剥标转发（Frame 4）。

流程和外部路由器几乎一样，只是「交换机—路由器」那一段从一根网线变成了机箱内部的总线。这一步变化带来两个后果：延迟从微秒级降到亚微秒级，汇聚链路的瓶颈消失了。

为什么还要 Flow 缓存 #

按上面的流程，每个跨 VLAN 的包都要过一遍路由模块：查路由表、改 MAC、改 TTL、重算校验和。这在硬件里做得很快，但仍然是一笔固定开销。

这里有个观察：不是所有包都需要重新路由。用 FTP 传一个几十 MB 的文件，IP 层会把它切成很多小块，这些块的「发送目标」完全相同——同样的目的 IP、同样的目的端口，源 IP 和源端口也相同。这样一连串的包叫一条「流」（Flow）。

一条流里，第一块数据被正确路由之后，后续每一块必然走同一条路。于是：

  • 只有流的第一块走完整路由流程：交换模块 → 路由模块 → 交换模块。
  • 路由结果写进缓存。缓存项包含目的 IP、源 IP、目的 TCP/UDP 端口、源 TCP/UDP 端口、入端口、出端口、改写后的目的 MAC。
  • 同一条流的第二块及以后，进来直接查缓存拿到出端口，转发出去，不再进路由模块。

转发时该做的改写一样不少：MAC 地址、IP 头的 TTL、TCP/UDP 校验和都要按路由的规则改。区别只是「路径已经知道，不用再算一遍」。

于是就有了那个说法：第一次路由，之后都交换。整条流跑在线速上，收得进多少就转得出多少。

这套机制各家叫法不同。Cisco Catalyst 上叫「多层交换」（Multi Layer Switching），有些厂商叫「一次路由多次交换」，还有的叫快速转发、 shortcut 转发。名字不同，原理是同一个：缓存转发结果，跳过重复决策。

缓存要老化。拓扑一变，缓存里的表项立刻失效，同一条流的下一个包重新走一遍路由，缓存重建。所以故障切换的瞬间，会看到流量短暂走慢路径，恢复之后又快起来。

顺带说一句 Linux 的对照：内核早年也有路由缓存（dst entry），后来在 3.6 里删掉了，理由是缓存命中率不够高、维护成本比收益大，改成每个包都查 FIB，靠 LC-trie 把查找做得足够快。三层交换机的 Flow 缓存能活下来，是因为它跑在 ASIC 上，命中率由硬件保证。

路由器还没被淘汰的理由 #

三层交换机比路由器快、比路由器便宜、还少占一个机柜位。那路由器还有用吗？有，三个地方。

  • 连 WAN。三层交换机终究是交换机，绝大多数机型只有以太网口。接专线、接 SDH、接 4G/5G 模块，还是要路由器。
  • 安全。路由器上有 IPSec VPN、有 RADIUS 认证、有成熟的状态化包过滤。三层交换机也能做 ACL，功能深度不如专业路由器。
  • 异构协议。IPX/SPX、AppleTalk 这类非 TCP/IP 协议，三层交换机基本不支持，路由器还留着。

所以典型的企业网分工是：接入层二层交换机划 VLAN，楼层间用三层交换机做高速路由，出口放一台路由器接 WAN、跑 VPN、做边界过滤。三样各干各的活。

隔离没被破坏 #

VLAN 之间挂路由器，不会破坏 VLAN 的隔离效果。路由器不转发以太网广播帧，广播仍旧停在本 VLAN 内。三层设备只是给跨域流量开了一道受控的闸门。

要不要 NAT #

纯内部互通不需要 NAT，开 ip_forward 就够。要让两个 VLAN 的机器共用一个公网出口，才需要在外出方向做一次地址转换，和 VLAN 有几个无关。NAT 的形态与坑看「NAT」那篇。

十二、用 VLAN 设计局域网 #

前面十一章讲的是「VLAN 怎么工作」。这一章换个视角：把一个真实的局域网拆开，看 VLAN 到底改变了什么。

逻辑结构与物理结构分离 #

没有 VLAN 的时候，网络的逻辑结构和物理结构是绑死的。一个部门在三楼，它的网络就在三楼那台交换机上；搬到五楼，就得重新布线、重新配交换机。

有了 VLAN，这两个结构可以分开：

  • 物理结构是「谁和谁用网线连着」——三楼交换机、五楼交换机、机房核心交换机。
  • 逻辑结构是「谁和谁在一个广播域里」——研发部 VLAN 10、财务部 VLAN 20、访客 VLAN 30。

研发部的人坐在三楼还是五楼，只要他的端口划进 VLAN 10，他就还在研发部的网络里。这就是 VLAN 最本质的价值：把「网的边界」从物理位置里解耦出来。

组织维度：按什么划分 #

划分 VLAN 的依据不止「部门」一种。常见的几种：

划分依据 适合场景 代价
按部门 企业网最常见 部门调整要改配置
按楼层/位置 布线方便 同一部门被拆散
按设备类型 服务器、打印机、摄像头各自成域 数量多时 VLAN 编号吃紧
按安全等级 生产网、办公网、访客网、管理网 边界规划要提前想清楚
按项目 临时项目组 项目结束要清理

实际部署里常见的是混合：「安全等级」定大框架（生产/办公/访客/管理），框架内再按部门细分。

一个具体的设计 #

假设一栋三层办公楼，每层一台接入交换机，机房一台核心交换机：

VLAN 10  研发    192.168.10.0/24
VLAN 20  财务    192.168.20.0/24
VLAN 30  行政    192.168.30.0/24
VLAN 40  服务器  192.168.40.0/24
VLAN 99  管理    192.168.99.0/24

配置要点：

  • 每层接入交换机上，连终端的口是 Access，划进对应部门的 VLAN。
  • 每层连核心交换机的上行口是 Trunk，放行所有业务 VLAN。
  • 核心交换机上为每个 VLAN 建一个 SVI（VLAN 接口），配上网关地址，VLAN 间路由在核心上完成。
  • 管理 VLAN 99 单独划出，交换机自己的管理地址放在这里，业务口不放行 99（防止从业务侧打到设备管理面）。

结构复杂化的代价 #

VLAN 不是免费的。用了之后会多出这些麻烦：

  • 配置量成倍增加。N 个 VLAN 跨 M 台交换机，每台交换机都要配一遍；漏配一台，那台下面的用户就不通。
  • 排错链路变长。一个「上不了网」的问题，原因会是端口 VLAN 配错、Trunk 没放行该 VLAN、SVI 没配、路由没写、ACL 挡了——五层都要查。
  • 广播域的边界变成人为边界。原来「插上网线就能通」的直觉失效了，新设备上线要先确认端口划在哪个 VLAN。
  • VLAN 编号成了要管理的资源。几百个 VLAN 的时候，编号规划和文档比配置本身更要紧。

所以设计的原则是「够用就好」：小型网络（几十台设备）分三五个 VLAN（业务、管理、访客）足够；上百台以后再考虑按部门细化。

什么时候不该用 VLAN #

有两种情况，VLAN 反而是负担：

  • 物理隔离就能满足的场景。两个网络本来就不该有任何交集（比如生产控制网和办公网），直接两台独立交换机，比划 VLAN 更安全、更好审计。
  • 设备数量很少的小网络。十几台电脑加一台路由器，不划 VLAN 更快、更好维护。

十三、常见故障与排查 #

VLAN 的故障有个共同点：现象都差不多（不通），但原因分布在不同层。按顺序查能少走弯路。

故障定位的顺序 #

自下而上，一层一层排除：

  1. 物理层：网线、光模块、端口灯。链路没起来，后面全是白查。display interface 看 UP/DOWN。
  2. 端口 VLAN 归属：Access 口的 PVID 是不是目标 VLAN。这条最常错，尤其是新装或改过的端口。
  3. Trunk 放行列表：路径上每一台交换机的 Trunk 口，allow-pass vlan 里有没有这个 VLAN。漏一台就断。
  4. SVI 与网关：三层交换机上有没有这个 VLAN 的接口，地址对不对，up 没 up。SVI 要 up 的前提是至少有一个属于该 VLAN 的端口 up。
  5. 路由：跨 VLAN 要不要路由、路由表里有没有对端网段、ip_forward 开没开。
  6. ACL 与防火墙：前面五步都通还不行，才轮到查规则。

症状与原因对照 #

症状 最常见的原因
同 VLAN 内互通，跨 VLAN 不通 SVI 没配或路由没写
同一台交换机内同 VLAN 通，跨交换机同 VLAN 不通 Trunk 没放行该 VLAN
部分终端通、部分不通 端口 PVID 配错（个别口漏改）
全部不通，端口灯不亮 物理链路问题
能 ping 通网关但 ping 不通外网 缺默认路由或 NAT 没做
通了一阵后突然断 FDB 老化后泛洪被 ACL 或风暴抑制挡了
换了个端口就不通了 新端口 VLAN 归属和原端口不一致
无线能连、有线不行 有线端口 VLAN 配错（无线常走另一条路径）

三个常用的排查命令 #

text
display vlan                      # 看有哪些 VLAN、每个 VLAN 有哪些端口
display port vlan                 # 看每个端口的 PVID 与放行列表
display interface brief           # 看所有端口的物理状态与 VLAN 归属

Linux 上对应的：

bash
ip -d link show type vlan         # 看 VLAN 子接口
bridge vlan show                  # 看网桥的 VLAN 表
ip link show master br0           # 看哪些口挂在桥上

抓包看标签 #

排查 Trunk 问题时，抓包是最直接的确认手段：

bash
tcpdump -i eth0 -e -n vlan

-e 打出链路层头，vlan 过滤器只留带标签的帧。如果预期带标签却没看到，说明这台设备没按 Trunk 处理；如果该剥标签的地方还带着标签出去，说明 PVID 与 VID 的匹配关系不对。

注意一个陷阱：在本机网卡上抓包，很多情况下标签已经被硬件剥掉了，tcpdump 看不到。要抓带标签的帧，得在 Trunk 口上抓或者用镜像口。

十四、易错点速查 #

现象 原因 处理
端口划进 VLAN 后还是不通 忘了给该 VLAN 建 SVI 或配网关 三层设备上补 VLAN 接口与地址
Trunk 两端都配了还是不通 一端 Access 一端 Trunk，或封装标准不一致 两端统一成 Trunk + 802.1Q
Native VLAN 不一致导致串流 两端 native 配了不同的 VLAN 号 两端统一，或改成不用的 VLAN 号
改完 VLAN 立即失效，重启后恢复 配置没保存 save 写进启动配置
跨交换机同 VLAN 不通，本机内通 中间某台交换机 Trunk 没放行该 VLAN 逐跳检查 allow-pass vlan
两个 VLAN 的机器莫名能互访 有端口 PVID 配错，把两个 VLAN 桥到一起 逐个端口核对 PVID
VLAN 间能通但速度很慢 走的是路由器单臂路由而非三层交换 改用 SVI 或优化路径
无线终端和有线终端不在同一网段 无线控制器/BSSID 绑了不同 VLAN 统一无线业务 VLAN 与有线 VLAN
新建 VLAN 后 DHCP 拿不到地址 DHCP 服务器上没有该网段的作用域或中继 补作用域或配 DHCP relay
VLAN 1 上设备特别多、广播大 默认所有端口都在 VLAN 1，没划走 把业务口划到业务 VLAN，VLAN 1 只留管理
三层交换机上 SVI 一直是 down 该 VLAN 没有任何端口 up 先接一台设备或建个 loopback 端口
Trunk 上抓包看不到 VLAN 标签 网卡硬件已剥标 在 Trunk 口或镜像口抓
加了 VLAN 后环路 Trunk 上误接成环，STP 没启用 开 STP，Trunk 口配好 BPDU 保护
管理地址配在了业务 VLAN 管理面与业务面没隔离 单划管理 VLAN，业务口不放行

写到最后，VLAN 这件事的主线可以压成三句：

标签只分广播域，不分权限——VLAN 隔离的是广播，不是安全边界，跨 VLAN 的访问控制要靠 ACL 或防火墙。

PVID 决定口属于谁——收到无标签帧按 PVID 打标，发出时 VID 等于 PVID 就剥标。配错 PVID，流量就跑到别的 VLAN 去了。

边界在两端，中间要放行——VLAN 的两个端点在接入交换机，中间的每一跳 Trunk 都必须放行它，漏一跳就断。
