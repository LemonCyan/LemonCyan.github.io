这篇只讲二层的地基：链路层到底做什么、以太网帧长什么样、网桥靠哪三个动作把几个口拼成一个广播域、br0 怎么建、怎么管。

不讲的部分：FDB 的查找路径、br_handle_frame 的逐行代码、VLAN tag 的处理与源码、STP 的完整状态机。转发表的代码级实现放在同目录的《二层桥转发的实现》里，VLAN 有独立两篇，路由与 NAT 也不在这篇范围。

先记住一句话：网桥就是软件实现的交换机。交换机用交换芯片干的活，Linux 用一段内核代码加一颗通用 CPU 干，逻辑一模一样。

一、链路层在做什么 #

链路层（L2）在协议栈里位置有点夹：往下要跟网卡驱动打招呼，往上要给 IP、ARP、VLAN、网桥喂数据。它的全部工作就是这段中间层，外加一件上层不干的事——直接按 MAC 把帧转出去。

先划边界。接收方向上，网卡驱动按以太网格式把帧拼好，调 netif_receive_skb 交给链路层，到这里驱动的活就结束了。发送方向反过来：链路层有帧要发，才去叫驱动，入口是 dev_queue_xmit。

c
/* 接收：驱动 -> 链路层 */
netif_receive_skb(skb);

/* 发送：链路层 -> 驱动 */
dev_queue_xmit(skb);

这两个函数是链路层与驱动之间仅有的通道。你把这两个名字记住，整条收发路径都能对上号。

链路层不是终点 #

收上来的帧不会都停在链路层。绝大多数帧的最终归宿是某台主机的应用层，只是终结的层次不同：

  • IP 报文：链路层交给网络层，入口 ip_rcv。
  • ARP 报文：交给 ARP 模块，入口 arp_rcv。
  • VLAN 报文：交给 VLAN 处理，入口 vlan_skb_recv，剥掉 tag 再往上走。
  • 原始套接字抓的包：直接送 socket 层，不进网络层。

发送方向也是各家有各家的入口。网络层通过 ip_finish_output（最终落到 ip_finish_output2）告诉链路层要发帧，真正发的时候还过了邻居子系统一层——邻居子系统做的是链路层与网络层的地址映射，IPv4 下就是 ARP，可以把它当成夹在两层之间的模块。原始套接字最简单，直接调 dev_queue_xmit。

网桥和 VLAN 子接口的收发就不一样了，链路层必须亲自深度参与。从分层理论看，网桥、VLAN 本来就是逻辑链路层的内容，它们的协议字段——以太网类型、VLAN tag、源目 MAC——全在二层头上。二层隧道也是同一类活，典型的是按 IP 地址转发的 EoIP（Ethernet over IP），不需要三层路由参与，纯粹在链路层把帧塞进隧道。

六项职责 #

链路层要干的事，掰开就这么六条：

序号 职责 说明
1 对接网卡驱动与上层协议 netif_receive_skb 收，dev_queue_xmit 发
2 实现网桥 按 MAC 地址转发的二层交换机功能
3 实现 VLAN 处理 带 tag 报文的收发与剥离
4 实现邻居子系统 链路层地址与网络层地址的映射（IPv4 用 ARP）
5 按以太网类型分发 依类型字段把帧交给注册过的处理函数
6 实现二层隧道 EoIP 这类按 IP 转发的隧道

这六条里，第 2 条和第 3 条是本篇的主角。

一个帧进栈之后的顺序 #

netif_receive_skb 拿到帧，处理顺序大致是这样：

text
netif_receive_skb
  ├─ 网桥处理（入接口属于某个网桥时）
  │    ├─ 送给本机：把 skb->dev 改成桥端口，重新回协议栈
  │    └─ 转发出去：直接 dev_queue_xmit 从出接口发走
  ├─ L2 隧道处理：按隧道目的 IP 查路由，从路由指出的接口发
  └─ 按以太网类型分发
       ├─ 0x8100 → vlan_skb_recv
       ├─ 0x0800 → ip_rcv
       ├─ 0x0806 → arp_rcv
       └─ 原始套接字抓的包 → 直接送 socket 层

网桥处理那一步要看报文是发给本机还是转发，两条岔路完全不同：发给本机的，改掉输入接口再回栈；要转发的，直接发走，根本不进上层。

输入接口会被改写 #

这点容易漏。网桥和 VLAN 上送本机的报文，链路层会把报文的输入接口改掉——从「网卡驱动的接收接口」换成「桥端口」或「VLAN 子接口」，VLAN 报文还会顺手剥掉 tag。

原因很简单：上层协议栈关心的是报文的「逻辑」输入接口，不是「物理」输入接口。这些报文的反向报文也是先发到桥端口或 VLAN 子接口，再由它们转回原始的物理接口。对上层来说，网桥和 VLAN 报文可见的接口就是 br0、eth0.5，底下那层它看不见。

还有一点：netif_receive_skb 是在软中断处理函数里被调用的，也就是说整条协议栈的收包路径跑在软中断上下文里。这个上下文限制会一路影响后面所有处理逻辑，包括网桥的转发判断。

接口就是 net_device #

接口可以看成链路层的每一个收发单元。它可以对应一块真实网卡，也可以是没有物理设备支撑的「虚」接口，比如网桥接口、VLAN 子接口。虚实之分只在有没有驱动，在内核里它们一视同仁，全部用 net_device 结构体描述。

对网络层来说，最要紧的工作是选路：决定报文是转发还是上送本机，转发的话从哪个接口出去（记在 skb->_skb_dst）。而路由判决的输入条件里就包括报文的输入接口，也就是 skb->dev——报文是从哪个口上到网络层的。除了路由，上层其他模块也常盯着输入接口和转发出口看。

所以接口是报文实际输入输出的逻辑路径，不必是物理路径。举两个例子：

  • 路由结果是从 eth0.5 转发，这条逻辑路径没有物理驱动，VLAN 子接口处理完，最终还是 eth0 把帧发出去。
  • 报文从 br0 上送网络层，上层就认为它是从 br0 收的；实际是 eth1 收到的，过了网桥之后输入接口被改成 br0。

虚接口之所以存在，就是因为 Linux 要提供网桥、要提供 VLAN，而这些是逻辑概念，物理上不存在一台叫「网桥」的设备。造出虚接口，是为了让上层往下处理时接口形态统一。虚与实的转换，正是链路层要实现的活。

分工也很清楚：

类型 典型接口 谁生成 谁实现 ops
实接口 eth0、wlan1、usb2 网卡驱动 网卡驱动
虚接口 br0、eth0.5 内核模块或应用（brctl、ip） 内核对应模块

换个角度看，一台 Linux 机器就是「交换机 + 路由器 + 主机」的三合一。实接口是它的物理端口，虚接口在表面上补齐二层功能——VLAN 子接口给物理口加上 VLAN 能力，网桥接口给一组口加上交换能力——而这些虚接口同样被这台机器的三层、四层、五层识别使用。

二、以太网与 MAC 地址 #

以太网的寻址靠 MAC 地址，48 位，6 个字节。前三字节是 OUI，由 IEEE 分配给厂商；后三字节是厂商自己编的序列号。

写法有两种，含义一样：

text
00:1a:2b:3c:4d:5e     冒号分隔，Linux 下最常见
0001.0002.000a        Cisco 点分四位，交换机配置里常见

地址里的两个标志位 #

第一个字节的最高两位有讲究，看第一个字节就能判断这个地址的性质：

位 名称 取值含义
bit 0（最低位） I/G 0 单播，1 组播
bit 1 U/L 0 全局管理（厂商烧录），1 本地管理（软件指定）

所以 01:00:5e:... 是组播（第一字节 0x01，最低位为 1），00:1a:2b:... 是单播。ff:ff:ff:ff:ff:ff 是全 1，广播地址，它是组播的一个特例。

网桥、VLAN 接口、虚拟机的 MAC 常属于本地管理地址，由软件指定，不占用厂商 OUI。

三类目的地址 #

目的 MAC 类型 二层怎么处理
某一台设备的单播地址 已知单播 查 FDB，从对应端口发
单播但表里没有 未知单播 泛洪到其他所有端口
ff:ff:ff:ff:ff:ff 广播 泛洪到其他所有端口
01:00:5e:xx:xx:xx 这类 组播 同广播，泛洪（除非做了组播抑制）

网卡默认只收三类帧：目的 MAC 是自己的、广播的、以及自己已加入的组播组。其他帧在硬件层就丢了。要收「不是给自己的帧」，得开混杂模式——这是网桥端口的前提条件，后面细说。

二层只有老化，没有 TTL #

三层有 TTL，报文绕圈会被逐跳减到 0 然后丢弃。二层没有这个机制。一个帧如果因为拓扑成环而在网桥之间来回转，它会一直转下去，直到广播风暴把链路打满。二层防环靠的是 STP，不是 TTL。

这也是二层网络的一个性格：它不会自己收敛，你得告诉它边界在哪。后面讲的 FDB 老化、VLAN 划分、STP，都是在给这个「不会自己停」的层加约束。

三、链路层的帧格式 #

以太网帧（Ethernet II，DIX 格式）的字段固定，从上到下：

字段 长度 作用
目的 MAC 6 字节 这一帧送给谁
源 MAC 6 字节 这一帧谁发的，网桥靠它学习
类型 / 长度 2 字节 上层协议标识，大于 0x0600 时表示类型
数据 46 ~ 1500 字节 上层载荷，不足 46 字节要填充
FCS 4 字节 帧校验序列，由网卡计算与校验

帧最小 64 字节、最大 1518 字节，都不含前导码，但含 FCS。数据字段最小 46 字节是为了把整帧顶到 64 字节——早年的共享介质需要足够的碰撞检测时间，这个下限留到了今天。

帧大小的几个边界 #

数值 含义
64 字节 最小帧长，含 FCS 不含前导码，载荷不够就填充
1500 字节 MTU 的常见取值，指数据字段能装多少
1518 字节 标准最大帧长，14 字节头 + 1500 数据 + 4 字节 FCS
1522 字节 带 802.1Q tag 时的最大帧长，多出的 4 字节就是 tag
9000 字节 巨帧，两端和中间设备都要开，混跑必然出问题

MTU 说的是数据字段的上限，不是整帧长度。算链路开销时要把 6+6+2 的头部和 4 字节 FCS 加回去，才是一帧在线上真正占的字节数。

类型字段是分发的依据 #

链路层收到帧之后，靠类型字段决定往上递给谁：

类型值 上层协议 处理入口
0x0800 IPv4 ip_rcv
0x0806 ARP arp_rcv
0x86dd IPv6 ipv6_rcv
0x8100 802.1Q VLAN vlan_skb_recv
0x88cc LLDP 链路层邻居发现
0x8847 MPLS 单播 MPLS 处理

驱动收包、链路层分发，中间靠的就是这张表。类型不认识，帧就丢。

VLAN 标签插在哪 #

802.1Q 的 tag 是 4 个字节，插在源 MAC 之后、类型字段之前：

text
目的MAC(6) | 源MAC(6) | TPID 0x8100(2) | TCI(2) | 类型(2) | 数据 | FCS

TCI 里高 3 位是优先级（PCP），中间 1 位是 DEI，低 12 位是 VLAN ID，所以 VLAN 号范围是 0~4095，可用的是 1~4094。打了 tag 的帧最长 1522 字节，这是交换机常说的「 baby giant 」由来。

对不支持 VLAN 的设备，这 4 个字节就是普通载荷的一部分，它看到的是一个陌生类型 0x8100。这也解释了为什么有些老网卡收到带 tag 的帧会直接丢——它不认识这个类型。

二层转发不改帧，三层转发才改 #

这是两条转发路径最本质的差别：

对比项 二层转发 三层转发
依据 目的 MAC 目的 IP
头部改动 不改，帧原样转发 改二层头：换源 MAC、换目的 MAC、TTL 减一
设备 网桥、交换机 路由器、三层交换机
表 FDB（MAC → 端口） 路由表（网段 → 下一跳）

二层转发不改帧，所以桥设备在链路上是「透明」的——两端主机根本不知道中间隔了一台网桥。三层转发必须改二层头，因为跨网段之后，下一跳的 MAC 和原来的目的 MAC 不是一回事。

四、网桥是什么 #

桥接就是把一台机器上的若干个网络接口「连接」起来。结果是：其中一个网口收到的帧，会被复制给其他网口并发出去，口与口之间的帧能互相转发。

交换机就是这么个设备——若干网口，桥接在一起，与它相连的若干主机就能通过它的转发互相通信。主机 A 发的帧到了交换机 S1 的 eth0，因为 eth0 与 eth1、eth2 桥接在一起，帧被复制到 eth1 和 eth2 发出去，被主机 B 和交换机 S2 收到；S2 再往主机 C、D 转发。

交换机转发时不会篡改帧数据，只做原样复制。但桥接并不是在物理层实现的，它在数据链路层。交换机看得懂二层头部，所以桥接不是单纯的「复制一份往外发」——它还要读头部里的 MAC 地址，决定复制给谁。

二层转发设备的通称叫网桥（bridge）。它可以是一台独立的网桥设备，也可以是跑在某台设备里的软件实例，后者叫虚拟桥，也叫软桥。这篇讲的是软桥。

Linux 的桥接怎么落地 #

Linux 内核用一个虚拟的网桥设备来实现桥接（目前只支持以太网接口）。这个虚拟设备可以绑定若干个以太网接口，把它们桥接起来。

text
        协议栈上层（IP / ARP / 应用）
                  │
            br0（虚拟网桥设备）
                  │
      ┌───────────┼───────────┐
    eth0        eth1        eth2
      │           │           │
    主机A       主机B       主机C

br0 绑定了 eth0 和 eth1。对协议栈上层来说，只看得到 br0——桥接在数据链路层完成，上层不关心细节。

  • 上层要发包：报文送到 br0，网桥的处理代码判断该从 eth0 发、从 eth1 发，还是两个都发。
  • 从 eth0 或 eth1 收到帧：交给网桥代码，判断该转发、丢弃，还是提交给协议栈上层。

有时候 eth0、eth1 也会作为报文的源地址或目的地址，直接参与收发，这时就绕过网桥了。这种情况在网关设备上很常见——管理口留在网桥上，业务口直通。

和交换机的一处硬差别 #

交换机只是个二层设备：收到的帧，要么转发，要么丢弃。小型交换机里一块交换芯片就够了，不需要 CPU，也就没有「本机」这个概念。

Linux 机器不一样，它本身是一台主机，往往就是报文的目的地。收到的帧除了转发和丢弃，还会被送进协议栈上层，被自己消化掉。所以 Linux 网桥是「二层设备 + 主机」的合体，比裸交换机多了一条上送的岔路。

这个差别带来一个直接后果：Linux 网桥上的 QoS、过滤、抓包能力比交换机丰富得多，因为它背后有一整个 netfilter 框架和一套 socket 接口可用。

五、网桥的三个核心动作 #

网桥的所有行为，拆到最底层就三个动作。三个动作凑齐，二层转发的逻辑就齐全了。

动作 触发条件 具体做法 目的
学习 每收到一帧 取源 MAC，在 FDB 中查；没有就新增「MAC → 入端口」，有就刷新老化计时 让表越来越全，转发越来越准
转发 目的 MAC 在表中命中 从表项记录的端口发出去，只发这一份 已知单播不打扰别人
泛洪 目的 MAC 查不到，或是广播/组播 从除入端口外的所有端口各发一份 保证目标一定能收到

三者是一套配合：学习负责建表，转发负责用表，泛洪负责兜底。表全的时候泛洪少，表空的时候泛洪多。

一次 ping 走完全程 #

用同一网段两台 PC 互 ping 来看这三个动作怎么串起来。拓扑：交换机上跑一个软桥实例，eth0、eth1 两个物理口加入软桥，两口都不配 IP，且都置为混杂模式。PC1 接 eth0，IP 192.168.2.2；PC2 接 eth1，IP 192.168.2.3。交换机刚启动，FDB 是空的。

text
1. PC1 ping PC2，先封三层头：sip 192.168.2.2，dip 192.168.2.3。
   PC1 发现目的 IP 与自己同网段，知道对方在同一个局域网，
   于是先发 ARP 请求，问 PC2 的 MAC。

2. ARP request 是广播帧，到交换机进软桥。
   桥先学源 MAC：报文源 MAC 为 0001.0002.000a，
   FDB 里查不到，新增表项：0001.0002.000a → eth0。

3. 桥发现这是广播帧，在桥内广播：
   除入端口 eth0 外，每个端口各发一份，从 eth1 发出。

4. PC2 收到，发现是问自己的 MAC，先做 ARP 学习：
   按请求里的源 MAC 与源 IP 记下 192.168.2.2 → 0001.0002.000a。

5. PC2 封装 ARP 回应，发出。

6. 回应从 eth1 进软桥。桥学源 MAC，
   FDB 新增：0001.0002.000b → eth1。

7. 桥按回应的目的 MAC 0001.0002.000a 查表，命中 eth0，
   从 eth0 转发出去——这一次是已知单播，不泛洪。

8. PC1 收到 ARP 回应，做 ARP 学习：
   记下 192.168.2.3 → 0001.0002.000b。

9. PC1 这才有本事封 ping 请求的二层头：
   Dmac 0001.0002.000b，Smac 0001.0002.000a，
   dip 192.168.2.3，sip 192.168.2.2。发给交换机。

10. 交换机查表，从 eth1 发出。

11. PC2 收到，确认是发给自己的，封 ping 回应，发给交换机。

12. 交换机查表，从 eth0 发出。PC1 收到回应，ping 结束。

这段流程里有三处细节值得盯住：

  • 第 3 步的广播和第 7 步的已知单播走的是两条路，前者泛洪，后者精确转发。同一次 ping 里两种行为先后出现。
  • 第 2 步和第 6 步的学习是「顺带」发生的。桥不需要谁通知它，只要帧从某个口进来，它就知道那个源 MAC 在那个口后面。设备只要往外发帧，桥就能学到东西，所以 FDB 建得很快，泛洪的帧不会太多。
  • ARP 表是主机的事，FDB 是桥的事，两张表互不相干。PC1 学的是「192.168.2.3 的 MAC 是多少」，桥学的是「这个 MAC 在哪个口」。

报文分类与处理规则 #

报文类型 FDB 命中情况 网桥动作
已知单播 目的 MAC 命中，出端口不是入端口 从该端口转发一份
已知单播，目的在本机 目的 MAC 是某桥端口自身 MAC 上送本机协议栈
未知单播 目的 MAC 查不到 泛洪，除入端口外各发一份
广播 目的 MAC 为 ff:ff:ff:ff:ff:ff 泛洪，除入端口外各发一份
组播 目的 MAC 首字节最低位为 1 泛洪（网关设备上可改内核禁止组播在桥上传播）
入端口即出端口 目的 MAC 学到的端口就是入端口 丢弃，不回发

最后一条是常被忽略的过滤规则：报文从哪个口进来，就不能从哪个口再发出去。这既是协议要求，也省掉了无意义的回环。

六、转发表 FDB #

每个桥内部维护一张转发信息表，叫 FDB（Forwarding DataBase），早期交换机文档里也叫 CAM 表——名字不同，指的是同一张「MAC → 端口」映射。交换芯片把这张表放在 TCAM 里做硬件查表，Linux 网桥把它放在内核内存里做软件查表。

表项最少包含两个字段，实际内核里更多：

字段 含义
MAC 设备的 MAC 地址
port 该设备接在哪个端口后面
vlan_id 属于哪个 VLAN（划分 VLAN 后才有意义）
is_local 是否为桥端口自身 MAC，决定是否上送本机
ageing 还有多久老化，动态表项才计时

桥收到帧，用目的 MAC 查这张表就知道出端口，直接发出去即可。

brctl showmacs br0 的输出长这样：

MAC 端口 类型 老化
0001.0002.000a eth0 动态 300 秒倒计时中
0001.0002.000b eth1 动态 300 秒倒计时中
0001.0002.0001 eth2 静态（eth2 自身 MAC） 不老化
0001.0002.00ff br0 本地（is local） 不老化

动态项的后两列是重点：每收到一条从这个 MAC 发来的帧，倒计时就重置一次；超过老化时间没动静，整条表项消失。

表项的三种来源 #

来源 建立方式 是否老化
动态学习 帧从某口进入，记下源 MAC 与该口 会，默认 300 秒
桥端口静态项 添加桥端口时，把该接口 MAC 记为静态项 不会
用户静态项 bridge fdb add 手动指定 不会（可配）

一个桥刚建好、口刚加进去，表里只有静态项，没有任何动态项。这时候所有单播都是未知单播，全得泛洪。

静态项不老化是有道理的：目的地址是某个桥端口自身 MAC，说明这一帧是送给那台接口所在主机的，也就是送本机的帧。这种表项要是被老化掉，本机就收不到自己的包了。

老化：二层网络广播多的根源 #

内核里网桥的老化时间字段是 br->ageing_time，new_bridge_dev 初始化时设成 300 * HZ，也就是 300 秒，和文档里常说的「默认 5 分钟」是同一个数。

老化机制要解决的是拓扑变化。假设主机 C 原来接在 eth2，后来挪到了 eth1：

  • C 一发包，eth1 收到，桥立刻把「C 在 eth2」改成「C 在 eth1」，表项跟着更新。
  • C 要是一直不发包，桥就始终认为它在 eth2，别人发给 C 的帧全从 eth2 出去，全丢。
  • 所以必须有超时：距最后一次收到 C 的帧超过老化时间，桥就忘掉这条记录。之后发给 C 的帧重新变成未知单播，泛洪到所有口，其中从 eth1 出去的那份能被 C 收到。

老化到期 → 表项消失 → 该 MAC 变未知 → 未知单播泛洪。这条链条就是二层网络里广播/泛洪流量偏多的根本原因。网络越大、MAC 越多、终端越安静（比如休眠的 IoT 设备），泛洪占比越高。

看表与调参 #

bash
#老工具：列出 FDB 全部表项，带端口和是否本地
brctl showmacs br0

#新工具：等价能力，输出更结构化
bridge fdb show
bridge fdb show dev eth1

#谁在这个网桥下
ip link show master br0

#调老化时间（秒）
brctl setageing br0 600
ip link set dev br0 type bridge ageing_time 60000   # 单位 1/100 秒

注意 brctl setageing 收的是秒，ip link ... ageing_time 收的是百分之一秒，同一个概念两个单位，写脚本时容易搞错。

泛洪能不能压下去 #

能，但都是「划边界」的思路，没有哪招能让泛洪消失：

手段 做法 效果
划分 VLAN 一个桥切成多个广播域 泛洪只在 VLAN 内扩散
端口隔离 标出隔离口，口间不互通 隔离口之间不互相泛洪
组播抑制 关掉组播在桥上的传播，或上 IGMP snooping 组播不再全口泛洪
缩短老化 调小 ageing_time 表项掉得快，泛洪反而更多，慎用

顺序上先划 VLAN，再考虑组播，最后才是动老化时间。老化调小是拿泛洪换收敛速度，多数场景不划算。

七、广播域与冲突域 #

这两个概念经常被混着说，其实分工不同。

  • 冲突域：共享介质上会互相碰撞的范围。同一个冲突域里，两台设备同时发，信号会撞。
  • 广播域：一个广播帧能到达的范围。同一个广播域里，任何一台发的广播，其他所有设备都能收到。

二层设备对这两个域的作用完全不一样：

设备 分割冲突域 分割广播域
集线器（HUB） 否，所有口同一个冲突域 否
网桥 / 二层交换机 是，每个口一个冲突域 否，整桥一个广播域
路由器 是 是，每个接口一个广播域
VLAN 不涉及 是，每个 VLAN 一个广播域

网桥分割冲突域，但不分割广播域。这是它和路由器的根本差别。网桥把冲突域切成一段段，让每个口下面独立跑；但广播帧照样从每个口泛洪出去，整桥还是一个广播域。

全双工链路普及之后，冲突域这个概念在实际网络里已经淡了——每个口独占一对线，不会冲突。但它留下的结论还在：二层设备不隔广播。

VLAN 才能切广播域 #

不配 VLAN 时，整个桥就是一个广播域。桥里端口一多，每个广播帧都要从每个口发一份：浪费带宽，也给接在口上的设备添负担，组网管理上也不好切分。

VLAN 解决的就是这个。常见做法是按端口划分 VLAN：一个桥里划多个 VLAN，每个 VLAN 里加多个端口。

场景 二层能否互通 说明
同一 VLAN 内的两个口 能 桥内正常转发
不同 VLAN 的两个口 不能 二层隔离，帧不出 VLAN
不同 VLAN 要互通 不能靠二层 只能走三层转发，由路由器或三层接口转

一个 VLAN 就是一个广播域。广播帧只在本 VLAN 的端口内泛洪，不会溢出到别的 VLAN。这样既压住了广播范围，也让「哪些口属于哪个网」这件事在配置上显式化。

对于带 VLAN 的二层转发，接口不再是一个扁平的口集合，而是「口 + VLAN」的二元组。同一个物理口可以承载多个 VLAN（trunk 口），FDB 里也就要带 vlan_id 才能唯一定位一条表项。这块细节在后面 VLAN 的两篇里展开。

八、Linux 网桥 br0 #

网桥也是 net_device #

链路层里任何一个收发实体都用 net_device 描述：可以是真网卡 ethX、USB 网卡、无线网卡，也可以是没物理设备的虚接口，比如 VLAN 接口、网桥接口。收发逻辑全走统一接口，这是内核面向对象那套思路的体现。

所以每个网桥在内核里也是一个 net_device。区别在「私货」部分：网桥的私货是 struct net_bridge，它把网桥和其他类型的 net_device 区分开。不同类型的 net_device，差异主要就体现在私货上。

c
/* 网桥的私货：net/bridge/br_private.h */
struct net_bridge {
    struct net_device  *dev;          /* 网桥自身的 net_device */
    unsigned long       ageing_time;  /* 动态 MAC 老化时间，默认 300 * HZ */
    unsigned long       stp_enabled;  /* 是否开 STP，默认 BR_NO_STP */
    /* 桥端口链表、FDB 哈希表、各定时器等，这里略去 */
};

/* 桥端口：网桥下的每一个接口 */
struct net_bridge_port {
    struct net_bridge  *br;    /* 属于哪个网桥 */
    struct net_device  *dev;   /* 对应哪个真实接口 */
    int                 state; /* BR_STATE_FORWARDING 等 */
};

net_bridge 里三个字段最值得记：

字段 含义 为什么重要
dev 网桥自身的 net_device 上层可见的是网桥而不是桥下接口；它也是区分不同网桥的依据
ageing_time 动态 MAC 的老化时间 决定 FDB 多久忘记一条记录
stp_enabled 是否开 STP，默认关闭 不开 STP 时桥端口就是简单转发，成环会炸

net_bridge_port 里三个字段：

字段 含义
br 这个桥端口属于哪个网桥
dev 对应哪个真实接口（eth1、usb1、vlan2、wlan3）
state 端口状态，不开 STP 时就是 BR_STATE_FORWARDING

建好一个网桥，等于造了一台交换机，只是这台「交换机」底下还没有任何接口。

创建过程 #

应用（brctl 或 ip）建网桥时只传一个名字，核心函数是 br_add_bridge：它创建网桥的 net_device 并注册进内核。网桥的私货由 new_bridge_dev 初始化，做的四件事：

text
1. 创建网桥自身的 net_device，并让私货回指：br->dev = dev
2. 关掉 STP：br->stp_enabled = BR_NO_STP
3. 设默认动态 MAC 老化时间：br->ageing_time = 300 * HZ
4. 启动老化定时器：br_stp_timer_init(br)

加接口走的是网桥 net_device 的 ops：为每个接口建一个 net_bridge_port，把它挂到所属网桥上，状态置 BR_STATE_FORWARDING。做完这两步，网桥就能当二层交换机用了。

代码都在 net/bridge/ #

文件 职责
br.c 网桥模块初始化
br_device.c 网桥 net_device 的 ops 实现
br_fdb.c MAC 地址表（FDB）实现
br_forward.c 报文转发逻辑
br_if.c 网桥与桥端口的创建、增删
br_input.c 网桥报文处理入口
br_ioctl.c 用户态 ioctl 接口
br_netfilter.c netfilter 框架与默认挂载的 hook
br_netlink.c netlink 接口
br_notify.c 内核通知链
其余文件 STP 协议相关、默认 netfilter 处理函数

看这张表能摸到内核的分层习惯：设备模型（br_device.c）、表（br_fdb.c）、转发（br_forward.c）、配置通道（br_ioctl.c / br_netlink.c）各自独立。FDB 的查找和 br_forward.c 的具体走法在《二层桥转发的实现》里讲，这里不重复。

加接口时的五条约束 #

序号 约束 原因
1 同一个接口不能作为不同网桥的桥端口 一个口只能有一个归属，否则转发域混乱
2 桥端口必须是混杂模式 要转发就得收目的 MAC 不是自己的帧
3 网桥自身不一定是混杂模式 设成混杂是为了抓包时把桥下所有帧复制一份送本机
4 每个桥端口建立时，其接口 MAC 作为静态项记入 FDB 目的地址是该 MAC 说明是送本机的帧，不能老化
5 网桥自身接口的 MTU 和 MAC 取所有桥端口的最小值 保证桥能承载任意一个口的帧；两者都可手工改

第 2 条和第 3 条容易混。桥端口开混杂，是因为它得看别人的帧；br0 自己开混杂，纯粹是为了抓包时能看到桥上转发的全部流量——正常转发不需要它。

第 4 条解释了一个现象：brctl showmacs br0 里总有几条 is local 的表项，挂着每个桥端口的 MAC，永远不老化。

报文怎么进出网桥 #

收包入口是 handle_bridge，实际干活的是 br_handle_frame。要点六条：

  1. 要做桥接处理的帧，入接口必须属于某个网桥，否则直接跳过网桥环节。
  2. 桥接处理前会查 ebtables 规则。ebtables 类似 iptables，工作在链路层，能实现接近二层交换机的 QoS 与过滤。
  3. 每收一帧，先做动态 MAC 学习，或刷新已有表项的老化时间。
  4. 网桥自身处于混杂模式时（比如在抓包），必须把帧复制一份送本机。
  5. 组播、广播、未知单播泛洪到每个桥端口；已知单播若目的在本机就上送，否则从对应桥端口转发。
  6. STP 报文的处理单独一条分支，不开 STP 时这条分支不参与。

发包入口是 br_dev_xmit，挂在网桥的 ops 里。应用用 send 系列系统调用从网桥发包，最终走到这里。逻辑还是二层交换那套：已知单播按 MAC 转发，广播/组播/未知单播泛洪。

帧的三种流向 #

流向 触发条件 走法
传入本机 目的 MAC 是某桥端口对应接口的 MAC 穿过网桥，改输入接口，继续走本机协议栈
转发出去 目的 MAC 命中的出端口不是本机 调 dev_queue_xmit，换出接口，从该桥端口发
传入本机后再转发 上送本机后路由判决认为该从某网桥口出 上送一次，再回到网桥发出去

第一条要注意措辞：传入本机不等于送到传输层。它只表示目的 MAC 是这个网桥下某个桥端口接口的 MAC，帧穿过网桥继续被本机协议栈处理，后面是丢弃、是转发、还是送 socket，由上层决定。

第二条有两个细节：转发最终都落到 dev_queue_xmit，和所有发送路径一致；网桥转发会过两次 netfilter——一次在桥接层（br_netfilter 的 hook），一次在三层，这是桥接防火墙能做策略的基础。

第三条是最绕的一种：帧先上到本机，路由判决之后发现出口是某个网桥接口，于是又塞回网桥发出去。它也可以从别的接口出去——以太网口、USB 口、无线口都行，具体看路由。

一个完整例子 #

机器有 4 个网卡：eth0 接外网，eth1、eth2、eth3 接三台 PC，要做网桥。

bash
#建网桥并起来
ip link add name br0 type bridge
ip link set br0 up

#三个业务口加入网桥：不配 IP，交给网桥统一管
ip link set eth1 master br0
ip link set eth2 master br0
ip link set eth3 master br0
ip link set eth1 up
ip link set eth2 up
ip link set eth3 up

#给网桥配地址，兼作管理口和局域网网关
ip addr add 192.168.10.1/24 dev br0

#验证
ip link show master br0
bridge fdb show

老系统上等价的一套：

bash
brctl addbr br0          # 建网桥，同时在内核里创建虚拟网卡 br0
brctl addif br0 eth1     # 为 br0 添加接口 eth1
brctl addif br0 eth2     # 添加 eth2
brctl addif br0 eth3     # 添加 eth3
ifconfig br0 192.168.10.1 netmask 255.255.255.0 up

br0 既是网桥，也是一个虚拟网络设备。它可以当网桥的管理端口，也可以当这个局域网的网关，看你需要。要用 br0 这个接口，就得给它配 IP；PC1、PC2、PC3 和 br0 的地址要落在同一网段。

什么叫二层口 #

eth1~eth3 加进网桥之后，就成了「二层口」：只有二层转发功能，没有 IP 地址，处于混杂模式，并且是某个网桥的成员。

从开发者角度看，二层口和三层口在内核里都是一个 net_device，形态完全一样，差别全在配置上：

特征 三层口 二层口
IP 地址 有 无
混杂模式 不开（默认只收自己的帧） 开
是否属于网桥 否 是
收发路径 直接进出协议栈 先过网桥，再决定上送或转发

混杂模式的定义：端口可以接收目的 MAC 不是自己的帧。端口默认只收目的 MAC 是自己的帧；要转发，就必须收别人的帧，所以桥端口必须开混杂。加进网桥时内核会自动处理，不用手工 promisc on。

十、网桥与交换机的异同 #

把功能拆开对比，网桥和交换机在二层的行事方式几乎一模一样：

对比项 Linux 网桥 二层交换机 路由器
工作层次 链路层 链路层 网络层
转发依据 目的 MAC 目的 MAC 目的 IP
转发表 FDB（内核内存） FDB / CAM（交换芯片） 路由表

差异集中在三点：

  1. 实现介质不同。网桥每个包都要 CPU 过一遍，转发能力受 CPU 和内存带宽限制；交换机靠 ASIC，线速转发。所以网桥适合口少、流量不大的场景，不适合做核心汇聚。
  2. 本机可为目的。交换机的帧只有转发和丢弃两个去向，Linux 网桥多一个「上送本机」。这也是 br0 能配 IP 当代网关的原因。
  3. QoS 与过滤更细。网桥能挂 netfilter，五元组、连接跟踪、限速、NAT 都能用上；交换机的 ACL 只能匹配有限字段。

素材里提过一处实现差异：在某些网关设备上，通过改内核禁止组播报文在网桥上传播。交换机的默认行为是组播泛洪，而这类设备直接掐掉了这条路，因为组播在网关场景里往往是噪音。

十一、网桥的常见用途 #

1. 网关设备测二层业务流性能

做网关测试，要打双向二层业务流，常把 WAN 口和 VLAN1 口桥接起来，然后双向打流。桥会学习两个口进来的源 MAC 与入端口的对应关系，两侧就能对打。这跟二层交换机的 MAC 学习与转发是一个道理，只是把交换机换成了软件桥。

2. 虚拟机和容器的网络接入

虚拟机或容器用 veth pair 接到宿主机，宿主机把一堆 veth 和物理口放进同一个 br0。对容器来说 br0 就是它的交换机；宿主机则在 br0 上配 IP 当网关。

bash
ip link add name br0 type bridge
ip link set br0 up
ip link set eth0 master br0
ip link set veth1 master br0
ip link set veth2 master br0
ip addr add 172.18.0.1/24 dev br0

3. 抓包与流量镜像

把要观察的口和抓包口放同一个桥，桥在转发的同时复制一份送本机（网桥自身开混杂模式），就能在不影响链路的情况下看到全部流量。这类用法在排查现场问题时省事。

4. 透明防火墙

桥接模式部署的防火墙，两个口一个桥，不进路由表、不改 IP、不改 MAC，串在链路中间做过滤。对两端设备完全透明，不用改网关地址。靠的正是网桥转发时的两次 netfilter。

5. 无线接入点

无线口和有线口桥接，无线客户端与有线主机进同一个广播域，看起来在同一台交换机下。这就是家用 AP 的典型做法。

6. 网络命名空间互联

两个 netns 各放一个 veth 端，宿主机把两个 veth 放进同一个桥，两个命名空间就在同一广播域里。

一排排看下来，二层的麻烦几乎都出在「边界」上：口属于谁、广播域多大、表什么时候过期、环在哪里。链路层自己不解决问题，它只是把这些问题原样放大到整个广播域。网桥就是软件实现的交换机——学习建表、查表转发、查不到就泛洪，这三个动作加一张会老化的 FDB，就是全部逻辑。剩下的事，交给 VLAN 去切广播域，交给 STP 去断环，交给三层去跨网段。
