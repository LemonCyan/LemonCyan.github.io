本篇只讲内核源码：VLAN 虚拟设备在内核里是什么结构、怎么注册出来、发的时候标签插在哪、收的时候标签在哪剥。不讲「VLAN 是什么」「VID 和 PVID 怎么配」——那些在《VLAN 原理与配置》里。也不讲网桥转发算法本身，只在第八章说清楚 VLAN 设备进网桥后收发走哪条路。代码基准是 linux 3.14 的 net/8021q/，遇到 2.6.x 的老实现会在关键处点一句，因为网上流传的分析文章大半是 2.6 时代的，混着看会迷惑。

一句话抓住主线：VLAN 设备是一个虚拟网络设备，它没有自己的硬件，vlan_dev_priv 建在一个真实设备之上。收的时候由它剥掉帧头那 4 字节，发的时候由它插进去。内核视角里它和物理网卡没有区别——都是 struct net_device，所以能配 IP、能进网桥、能被策略路由选中，这也是整个模块设计的立足点。

一、VLAN 模块在内核里的位置 #

先看目录。VLAN 功能的代码在 net/8021q/ 下，编译出来是一个独立模块 8021q.ko，也可以直接编进内核。别去 net/core/ 或驱动目录找，那些地方只有配合它的钩子。

文件 职责 关键符号
vlan.c 设备注册/注销、ioctl、GVRP/MVRP 入口、模块初始化 register_vlan_dev、vlan_ioctl_handler、vlan_proto_init
vlan_dev.c netdev_ops 回调、收发包函数、统计 vlan_dev_hard_start_xmit、vlan_dev_init
vlan_core.c 与协议栈主干的交接 vlan_do_receive、vlan_skb_recv、__vlan_find_dev_deep
vlan_netlink.c rtnetlink 接口 vlan_link_ops、vlan_newlink
vlan_gvrp.c GVRP 协议帧收发 vlan_gvrp_request_join
vlan_mvrp.c MVRP 协议帧收发 vlan_mvrp_request_join
vlanproc.c procfs 调试入口 vlan_proc_init
vlan.h 内部声明 vlan_dev_priv

这堆文件对外的门面只有三处注册，记住这三处，整章就有了骨架：

c
/* 1. 协议类型注册：收到 0x8100 的帧交给 vlan_skb_recv */
static struct packet_type vlan_packet_type __read_mostly = {
    .type = cpu_to_be16(ETH_P_8021Q),
    .func = vlan_skb_recv,
};

/* 2. rtnetlink 注册：ip link add link eth0 name eth0.100 type vlan id 100 */
static struct rtnl_link_ops vlan_link_ops __read_mostly = {
    .kind     = "vlan",
    .maxtype  = IFLA_VLAN_MAX,
    .policy   = vlan_policy,
    .priv_size = sizeof(struct vlan_dev_priv),
    .setup    = vlan_setup,
    .validate = vlan_validate,
    .newlink  = vlan_newlink,
    .dellink  = vlan_dellink,
};

/* 3. ioctl 钩子注册：老接口 vconfig 走 SIOCSIFVLAN/SIOCGIFVLAN */
vlan_ioctl_set(vlan_ioctl_handler);

第三处在 vlan_proto_init 里完成。vlan_ioctl_set 本身很薄，就是给函数指针赋值，加锁是为了防止并发改指针：

c
void vlan_ioctl_set(int (*hook)(struct net *, void __user *))
{
    mutex_lock(&vlan_ioctl_mutex);
    vlan_ioctl_hook = hook;
    mutex_unlock(&vlan_ioctl_mutex);
}

sock_ioctl 里遇到 SIOCGIFVLAN、SIOCSIFVLAN 两个命令号，就转给 vlan_ioctl_hook。这个钩子的设计意图是把 VLAN 从 socket 层解耦——net/socket.c 不需要知道 VLAN 存在，只需要知道有个钩子。你读 sock_ioctl 时看到 vlan_ioctl_hook 是 NULL 判断，原因就在这：模块没加载时它是空的。再看层次，一个 eth0.100 在协议栈里长这样：

text
发送：IP 层选中 eth0.100 --> vlan_dev_hard_start_xmit（dev=eth0.100）
       --> skb->dev 改成 eth0 --> dev_queue_xmit --> 驱动 --> 带 4 字节标签出线

接收：网卡 DMA --> netif_receive_skb --> 0x8100 --> vlan_skb_recv
       --> skb->dev 改成 eth0.100，剥掉标签 --> netif_rx 再走一遍
       --> IP 层看到的是 eth0.100 收的包

这张图里有个点值得停一下：VLAN 设备对外是一个完整的 net_device，所以上层完全不知道标签这回事。你给 eth0.100 配 IP，路由表里出接口写 eth0.100，ARP 邻居表挂在 eth0.100 上，iptables 的 -i eth0.100 能用——这些能够成立，全靠 net_device 这一层抽象。内核没有为 VLAN 设备另造一套对象体系，这是它简洁的地方。

register_vlan_device 的注释写得很直白：

c
/* Attach a VLAN device to a mac address (ie Ethernet Card).
 * Returns 0 if the device was created or a negative error code otherwise.
 */
static int register_vlan_device(struct net_device *real_dev, u16 vlan_id)

「Attach a VLAN device to a mac address」——挂到一块网卡的 MAC 地址上。这句话就是模块的全部含义。

模块的整体架构可以拆成四块，后文按这四块展开：

  1. struct net_device 的接口函数实现。VLAN 设备也是 net_device，就必须提供 header_ops 和 netdev_ops，包括 vlan_dev_hard_header、vlan_dev_hard_start_xmit、vlan_dev_open、vlan_dev_stop。
  2. 和 socket 模块的关联。应用层要能建/删 VLAN 设备、设优先级映射，走的就是 ioctl 那条路。
  3. 协议栈的收发处理函数。发送走 ndo_start_xmit，接收走 packet_type.func 加 netif_receive_skb 里的预剥标签。
  4. 调试手段。一个成熟模块得能看状态，VLAN 在 procfs 里注册了 /proc/net/vlan/。

把这四块记住，再看任何一个具体函数，你都知道它在哪一格。

二、核心数据结构 vlan_dev_priv #

先看帧头，这是理解一切的起点。802.1Q 标签就是 4 个字节：2 字节 TCI（Priority 3 bit + DEI 1 bit + VID 12 bit）加 2 字节内层协议类型。内核把它拆成两个结构体。

c
/**
 * struct vlan_ethhdr - vlan ethernet header (ethhdr + vlan_hdr)
 * @h_dest: destination ethernet address
 * @h_source: source ethernet address
 * @h_vlan_proto: ethernet protocol
 * @h_vlan_TCI: priority and VLAN ID
 * @h_vlan_encapsulated_proto: packet type ID or len
 */
struct vlan_ethhdr {
    unsigned char h_dest[ETH_ALEN];
    unsigned char h_source[ETH_ALEN];
    __be16        h_vlan_proto;
    __be16        h_vlan_TCI;
    __be16        h_vlan_encapsulated_proto;
};

/*
 * struct vlan_hdr - vlan header
 * @h_vlan_TCI: priority and VLAN ID
 * @h_vlan_encapsulated_proto: packet type ID or len
 */
struct vlan_hdr {
    __be16 h_vlan_TCI;
    __be16 h_vlan_encapsulated_proto;
};

两个结构体的关系是包含：vlan_hdr 是 vlan_ethhdr 的后 4 字节。vlan_ethhdr 用于「从帧头开始看整帧」，vlan_hdr 用于「skb->data 已经指到标签位置」的场景。sizeof(struct vlan_ethhdr) 是 VLAN_ETH_HLEN 即 18，sizeof(struct vlan_hdr) 是 VLAN_HLEN 即 4，ETH_HLEN 是 14。这三个常量在收发代码里到处出现，记牢。

h_vlan_proto 的注释写「Should always be 0x8100」，但内核留了扩展余地：VLAN_PROTO_NUM 支持两种，ETH_P_8021Q（0x8100）和 ETH_P_8021AD（0x88a8，QinQ 外层）。所以后续很多函数签名里带一个 __be16 vlan_proto 参数，用 vlan_proto_idx() 换算成数组下标。

外层还有个容易搞混的点：帧里有两个「类型」字段。h_vlan_proto 是 0x8100，告诉对端「这是个 802.1Q 标签帧」；h_vlan_encapsulated_proto 是内层真实协议，比如 0x0800（IP）或 0x0806（ARP）。读代码时看到 vlan_set_encap_proto 从后者取值往 skb->protocol 里塞，不要惊讶。

接下来是本篇的主角：

c
/**
 * struct vlan_dev_priv - VLAN private device data
 * @nr_ingress_mappings: number of ingress priority mappings
 * @ingress_priority_map: ingress priority mappings
 * @nr_egress_mappings: number of egress priority mappings
 * @egress_priority_map: hash of egress priority mappings
 * @vlan_id: VLAN identifier
 * @flags: device flags
 * @real_dev: underlying netdevice
 * @real_dev_addr: address of underlying netdevice
 * @dent: proc dir entry
 * @cnt_inc_headroom_on_tx: statistic - number of skb expansions on TX
 * @cnt_encap_on_xmit: statistic - number of skb encapsulations on TX
 */
struct vlan_dev_priv {
    unsigned int                nr_ingress_mappings;
    u32                         ingress_priority_map[8];
    unsigned int                nr_egress_mappings;
    struct vlan_priority_tci_mapping *egress_priority_map[16];

    u16                         vlan_id;
    u16                         flags;
    __be16                      vlan_proto;
    struct net_device           *real_dev;
    unsigned char               real_dev_addr[ETH_ALEN];

    struct proc_dir_entry       *dent;
    struct vlan_pcpu_stats __percpu *vlan_pcpu_stats;
    unsigned long               cnt_inc_headroom_on_tx;
    unsigned long               cnt_encap_on_xmit;

    struct netdev_hw_addr_list  mc;
    struct hlist_node           hlist;
};

字段逐个过一遍，这张表建议记住前五个：

字段 作用 读代码时注意什么
vlan_id 这个虚拟设备的 VID，12 bit 建好之后不可改，改 VID 要删了重建
flags VLAN_FLAG_REORDER_HDR / GVRP / LOOSE_BINDING / MVRP 决定收发路径走哪一支，最关键的开关
real_dev 底下那块真实网卡 所有收发的终点，skb->dev 最终指向它
real_dev_addr 建设备时抄下来的真实网卡 MAC 真实网卡 MAC 变了不影响已建好的 VLAN 设备
vlan_proto 0x8100 或 0x88a8 决定发出去的标签外层协议号
egress_priority_map[16] 发送方向 skb 优先级到 802.1p 的映射哈希 数组下标是 skb_prio & 0xF，冲突挂链
ingress_priority_map[8] 接收方向 802.1p 到 skb 优先级的映射 下标是 vlan_prio & 0x7，3 bit 直接寻址
dent /proc/net/vlan/<name> 的目录项 卸载设备要记得摘掉
vlan_pcpu_stats 每 CPU 统计 无锁累加，读的时候要处理撕裂
hlist 挂到 real_dev->vlan_list 上的节点 3.10 之后靠它找设备
mc 组播 MAC 列表 配合 IGMP Snooping 用

内存怎么来的？alloc_netdev(sizeof(struct vlan_dev_priv), name, vlan_setup)。alloc_netdev 会在 net_device 后面多分配这么一块私有空间，vlan_dev_priv(dev) 就是 netdev_priv(dev) 的包装：

c
static inline struct vlan_dev_priv *vlan_dev_priv(const struct net_device *dev)
{
    return netdev_priv(dev);
}

所以拿到 net_device * 就等于拿到了全部 VLAN 私有数据，一次指针偏移而已，没有查表。

一个坑：老文章里这个结构体叫 struct vlan_dev_info，取数据的宏叫 vlan_dev_info(dev)。这个命名在 linux 3.10 左右被改成了 vlan_dev_priv。你照 2.6 的文章去 3.14 的代码里搜 vlan_dev_info，搜不到，别以为代码被删了。

还差一个历史包袱要交代：struct vlan_group。

c
struct vlan_group {
    unsigned int nr_vlan_devs;
    struct hlist_node hlist;                        /* linked list */
    struct net_device **vlan_devices_arrays[VLAN_PROTO_NUM]
                                             [VLAN_GROUP_ARRAY_SPLIT_PARTS];
};

这是 2.6 / 早期 3.x 的做法：一块真实网卡上挂的所有 VLAN 设备，塞进一个二维指针数组，第一维是协议（0x8100 / 0x88a8），第二维是 VID 分段；数组本身又挂在一个全局哈希表上：

c
static struct hlist_head vlan_group_hash[VLAN_GRP_HASH_SIZE];

为什么不把链表头直接塞进 struct net_device？源码作者自己讨论过这个问题：塞进去查找更快，省掉哈希计算；但每个 net_device 都要多一个链表指针，全系统几万个设备就是几万次额外内存。这是内存和性能的取舍。

查找和设置就围绕这个二维数组：

c
/* 功能：根据 vlan id 以及 vlan_group 变量，查找符合条件的 vlan device */
static inline struct net_device *vlan_group_get_device(struct vlan_group *vg,
                                                       __be16 vlan_proto,
                                                       u16 vlan_id)
{
    struct net_device **array;
    array = vg->vlan_devices_arrays[vlan_proto_idx(vlan_proto)]
                                   [vlan_id / VLAN_GROUP_ARRAY_PART_LEN];
    return array ? array[vlan_id % VLAN_GROUP_ARRAY_PART_LEN] : NULL;
}

/* 功能：在 vlan_devices_arrays 中增加相应的 vlan 设备。
 * 由于是直接增加设备，没有进行存在性判断，因此在调用该函数之前，
 * 应该调用 vlan_group_get_device 判断要添加的 vlan 设备是否已存在。 */
static inline void vlan_group_set_device(struct vlan_group *vg, __be16 vlan_proto,
                                         u16 vlan_id, struct net_device *dev)
{
    struct net_device **array;
    if (!vg)
        return;
    array = vg->vlan_devices_arrays[vlan_proto_idx(vlan_proto)]
                                   [vlan_id / VLAN_GROUP_ARRAY_PART_LEN];
    array[vlan_id % VLAN_GROUP_ARRAY_PART_LEN] = dev;
}

用 CIDR 分段是为了省内存：VID 有 4096 个，一次性铺满太浪费，按 VLAN_GROUP_ARRAY_PART_LEN 切段，用到哪段才分配哪段。

到了 3.10 之后，vlan_group 被整个删掉了，取而代之的是 struct net_device 里一个 struct list_head vlan_list，所有 VLAN 设备通过 vlan_dev_priv(dev)->hlist 挂上去。查找退化成遍历链表：

c
struct net_device *__vlan_find_dev_deep(struct net_device *real_dev,
                                        __be16 vlan_proto, u16 vlan_id)
{
    struct vlan_dev_priv *vlan;
    struct net_device *dev, *found = NULL;

    if (vlan_id < VLAN_VID_MASK) {
        rcu_read_lock();
        vlan = vlan_dev_priv(real_dev);
        if (vlan->vlan_id == vlan_id && vlan->vlan_proto == vlan_proto)
            found = real_dev;
        else
            hlist_for_each_entry_rcu(vlan, &real_dev->vlan_list, hlist) {
                dev = vlan->real_dev;
                if (vlan->vlan_id == vlan_id &&
                    vlan->vlan_proto == vlan_proto) {
                    found = dev;
                    break;
                }
            }
        rcu_read_unlock();
    }
    return found;
}

一块网卡上挂不了几个 VLAN，遍历比哈希更快也更好写。老代码里的 VLAN_GROUP_ARRAY_SPLIT_PARTS、vlan_group_hash 这些符号在新内核里全没了，读到相关分析要能分清年代。

数据结构的账到此结清。后面所有流程都只操作这几样东西：vlan_dev_priv 里的 vlan_id、flags、real_dev，外加 skb 上的 vlan_tci 字段。

三、VLAN 设备的注册与创建 #

建一个 VLAN 设备有两条入口，殊途同归：

text
ip link add link eth0 name eth0.100 type vlan id 100
        └─> rtnl_link_ops->newlink = vlan_newlink
                                        └─> register_vlan_dev

vconfig add eth0 100
        └─> ioctl(SIOCSIFVLAN) -> vlan_ioctl_handler
                                        └─> ADD_VLAN_CMD
                                                └─> register_vlan_device

register_vlan_device 是两条路的汇合点，也是整个模块最值得读的函数之一。它做的事用一句话说清：申请一个 net_device，把 VLAN 私有数据填好，把 netdev_ops 指到 VLAN 自己的那套回调上，然后注册进系统。

c
/* Attach a VLAN device to a mac address (ie Ethernet Card).
 * Returns 0 if the device was created or a negative error code otherwise.
 */
static int register_vlan_device(struct net_device *real_dev, u16 vlan_id)
{
    struct net_device *new_dev;
    struct vlan_dev_priv *vlan;
    struct net *net = dev_net(real_dev);
    struct vlan_net *vn = net_generic(net, vlan_net_id);
    char name[IFNAMSIZ];
    int err;

    if (vlan_id >= VLAN_VID_MASK)
        return -ERANGE;

    err = vlan_check_real_dev(real_dev, htons(ETH_P_8021Q), vlan_id);
    if (err < 0)
        return err;

    /* Gotta set up the fields for the device. */
    switch (vn->name_type) {
    case VLAN_NAME_TYPE_RAW_PLUS_VID:
        /* name will look like: eth1.0005 */
        snprintf(name, IFNAMSIZ, "%s.%.4i", real_dev->name, vlan_id);
        break;
    case VLAN_NAME_TYPE_PLUS_VID_NO_PAD:
        /* Put our vlan.VID in the name.
         * Name will look like: vlan5
         */
        snprintf(name, IFNAMSIZ, "vlan%i", vlan_id);
        break;
    case VLAN_NAME_TYPE_RAW_PLUS_VID_NO_PAD:
        /* Put our vlan.VID in the name.
         * Name will look like: eth0.5
         */
        snprintf(name, IFNAMSIZ, "%s.%i", real_dev->name, vlan_id);
        break;
    case VLAN_NAME_TYPE_PLUS_VID:
        /* Put our vlan.VID in the name.
         * Name will look like: vlan0005
         */
    default:
        snprintf(name, IFNAMSIZ, "vlan%.4i", vlan_id);
    }

    new_dev = alloc_netdev(sizeof(struct vlan_dev_priv), name, vlan_setup);
    if (new_dev == NULL)
        return -ENOBUFS;

    dev_net_set(new_dev, net);
    /* need 4 bytes for extra VLAN header info,
     * hope the underlying device can handle it. */
    new_dev->mtu = real_dev->mtu;
    new_dev->priv_flags |= (real_dev->priv_flags & IFF_UNICAST_FLT);

    vlan = vlan_dev_priv(new_dev);
    vlan->vlan_proto = htons(ETH_P_8021Q);
    vlan->vlan_id = vlan_id;
    vlan->real_dev = real_dev;
    vlan->dent = NULL;
    vlan->flags = VLAN_FLAG_REORDER_HDR;

    new_dev->rtnl_link_ops = &vlan_link_ops;

    err = register_vlan_dev(new_dev);
    if (err < 0)
        goto out_free_newdev;

    return 0;

out_free_newdev:
    free_netdev(new_dev);
    return err;
}

按段落拆开看。

第一段是参数校验。VLAN_VID_MASK 是 0x0fff，vlan_id >= 0x0fff 直接返回 -ERANGE。注意这里用的是 >= 不是 >，所以 VID 0 到 4094 合法，4095（0x0fff）被挡掉。0 和 4095 是协议保留值，4095 尤其不能碰——它在某些实现里表示「任意 VLAN」。

vlan_check_real_dev 检查两件事：真实网卡支不支持 VLAN，以及这个 VID 在此网卡上是不是已经建过了。

c
static int vlan_check_real_dev(struct net_device *real_dev,
                               __be16 protocol, u16 vlan_id)
{
    const char *name = real_dev->name;

    if (real_dev->features & NETIF_F_VLAN_CHALLENGED) {
        pr_info("VLANs not supported on %s\n", name);
        return -EOPNOTSUPP;
    }

    if (vlan_find_dev(real_dev, protocol, vlan_id) != NULL)
        return -EEXIST;

    return 0;
}

NETIF_F_VLAN_CHALLENGE（代码里是 NETIF_F_VLAN_CHALLENGED）这个 feature 标记的意思是「这块网卡发不出超过自身 MTU 的帧」。有些老网卡、还有部分软件设备会置这个位，因为插了 4 字节标签后帧长超了它承受上限。这也是为什么 new_dev->mtu 直接照抄 real_dev->mtu——标签的 4 字节要从报文里挪出空间，而不是把 MTU 撑大。

-EEXIST 那条保证了「一个真实网卡的每个 VID 只对应一个 VLAN 设备」。这个唯一性是整个模块的地基，查找函数都建立在这个前提上。

第二段是命名。四种命名策略由网络命名空间级的 /proc/net/vlan/config 里那一行 VLAN Dev name | VLAN ID 控制，用 SET_VLAN_NAME_TYPE_CMD 改：

策略 结果示例 备注
VLAN_NAME_TYPE_RAW_PLUS_VID eth0.0100 默认值，四位补零
VLAN_NAME_TYPE_PLUS_VID_NO_PAD vlan100 名字里不带真实网卡名
VLAN_NAME_TYPE_RAW_PLUS_VID_NO_PAD eth0.100 不补零，最符合直觉
VLAN_NAME_TYPE_PLUS_VID vlan0100 不补零的反面

注意 vlan_newlink（netlink 那条路）用的是用户指定的名字，不走这个 switch；name_type 只影响老 ioctl 接口和按默认规则生成的设备。

第三段是 alloc_netdev。三个参数要看清：私有数据大小 sizeof(struct vlan_dev_priv)、设备名、以及 vlan_setup。vlan_setup 是设备的初始化回调，在 alloc_netdev 内部就被调用，负责把以太网那一套默认值铺好：

c
void vlan_setup(struct net_device *dev)
{
    ether_setup(dev);

    dev->priv_flags     |= IFF_802_1Q_VLAN;
    dev->priv_flags     &= ~IFF_XMIT_DST_RELEASE;
    dev->tx_queue_len   = 0;

    dev->netdev_ops     = &vlan_netdev_ops;
    dev->destructor     = vlan_dev_free;
    dev->ethtool_ops    = &vlan_ethtool_ops;

    memset(dev->broadcast, 0, ETH_ALEN);
}

IFF_802_1Q_VLAN 是关键标记，is_vlan_dev(dev) 就是查它：

c
static inline bool is_vlan_dev(const struct net_device *dev)
{
    return dev->priv_flags & IFF_802_1Q_VLAN;
}

tx_queue_len = 0 意思是不给这个设备排队——VLAN 设备只是个转发层，真正的队列在下面的真实网卡上，再排一次队纯属浪费。

第四段填私有数据，五个字段：

  • vlan_proto = htons(ETH_P_8021Q)，标签外层 0x8100。
  • vlan_id = vlan_id，VID。
  • real_dev = real_dev，挂靠的真实网卡。
  • dent = NULL，procfs 目录项等注册成功后再加。
  • flags = VLAN_FLAG_REORDER_HDR，默认开重排头。这个位决定收发时标签的插入时机，第五章细说。

第五段 register_vlan_dev，光看名字像是「注册设备」，实际还多两件事：

c
int register_vlan_dev(struct net_device *dev)
{
    struct vlan_dev_priv *vlan = vlan_dev_priv(dev);
    struct net_device *real_dev = vlan->real_dev;
    int err;

    /* Account for reference in struct vlan_dev_priv */
    dev_hold(real_dev);

    err = netdev_upper_dev_link(real_dev, dev);
    if (err)
        goto unregister;

    err = register_netdevice(dev);
    if (err < 0)
        goto unregister_netdev;

    /* Account for the class address for this device */
    dev_hold(dev);
    vlan->dent = vlan_proc_add_dev(dev);
    pr_info("adding VLAN %d to %s\n", vlan->vlan_id, real_dev->name);

    hlist_add_head_rcu(&vlan->hlist, &real_dev->vlan_list);
    return 0;
    ...
}

三件事：dev_hold(real_dev) 给真实网卡加引用计数，netdev_upper_dev_link 建立上下层从属关系（ip link 输出里那层 master/vlan 的缩进就是它），hlist_add_head_rcu 挂进 real_dev->vlan_list 供查找。dev_hold(dev) 是给 procfs 那个 class 地址加的账。卸载时逐项反向拆掉，unregister_vlan_dev 里一一对应。

老 ioctl 那条路由 vlan_ioctl_handler 走。它先 copy_from_user 把参数捞进来，然后加 rtnl_lock——因为接下来要动设备链表，必须拿全局 RTNL 锁：

c
static int vlan_ioctl_handler(struct net *net, void __user *arg)
{
    int err;
    struct vlan_ioctl_args args;
    struct net_device *dev = NULL;

    if (copy_from_user(&args, arg, sizeof(struct vlan_ioctl_args)))
        return -EFAULT;

    /* Null terminate this sucker, just in case. */
    args.device1[23] = 0;
    args.u.device2[23] = 0;

    rtnl_lock();

    /* 第一个 switch 只做公共前置检查：设备存在、是不是 VLAN 设备 */
    switch (args.cmd) {
    case SET_VLAN_INGRESS_PRIORITY_CMD:
    case SET_VLAN_EGRESS_PRIORITY_CMD:
    case SET_VLAN_FLAG_CMD:
    case ADD_VLAN_CMD:
    case DEL_VLAN_CMD:
    case GET_VLAN_REALDEV_NAME_CMD:
    case GET_VLAN_VID_CMD:
        err = -ENODEV;
        dev = __dev_get_by_name(net, args.device1);
        if (!dev)
            goto out;

        err = -EINVAL;
        if (args.cmd != ADD_VLAN_CMD && !is_vlan_dev(dev))
            goto out;
    }

    switch (args.cmd) {
    case ADD_VLAN_CMD:
        err = -EPERM;
        if (!ns_capable(net->user_ns, CAP_NET_ADMIN))
            break;
        err = register_vlan_device(dev, args.u.VID);
        break;

    case DEL_VLAN_CMD:
        err = -EPERM;
        if (!ns_capable(net->user_ns, CAP_NET_ADMIN))
            break;
        unregister_vlan_dev(dev, NULL);
        err = 0;
        break;

    case GET_VLAN_REALDEV_NAME_CMD:
        err = 0;
        vlan_dev_get_realdev_name(dev, args.u.device2);
        if (copy_to_user(arg, &args, sizeof(struct vlan_ioctl_args)))
            err = -EFAULT;
        break;

    case GET_VLAN_VID_CMD:
        err = 0;
        args.u.VID = vlan_dev_vlan_id(dev);
        if (copy_to_user(arg, &args, sizeof(struct vlan_ioctl_args)))
            err = -EFAULT;
        break;

    case SET_VLAN_INGRESS_PRIORITY_CMD:
        err = -EPERM;
        if (!ns_capable(net->user_ns, CAP_NET_ADMIN))
            break;
        vlan_dev_set_ingress_priority(dev, args.u.skb_priority, args.vlan_qos);
        err = 0;
        break;

    case SET_VLAN_NAME_TYPE_CMD:
        err = -EPERM;
        if (!ns_capable(net->user_ns, CAP_NET_ADMIN))
            break;
        if ((args.u.name_type >= 0) &&
            (args.u.name_type < VLAN_NAME_TYPE_HIGHEST)) {
            struct vlan_net *vn;
            vn = net_generic(net, vlan_net_id);
            vn->name_type = args.u.name_type;
            err = 0;
        } else {
            err = -EINVAL;
        }
        break;

    /* 为省篇幅略去两个 case 的完整代码：
     * SET_VLAN_EGRESS_PRIORITY_CMD -> vlan_dev_set_egress_priority
     * SET_VLAN_FLAG_CMD           -> vlan_dev_change_flags */

    default:
        err = -EOPNOTSUPP;
        break;
    }

out:
    rtnl_unlock();
    return err;
}

两个 switch 的写法值得学：第一个 switch 只做「参数里指定的设备是否存在、是不是 VLAN 设备」的公共前置检查，靠 fallthrough 空 case 把命令聚成一组；第二个 switch 才真正执行。ADD_VLAN_CMD 是唯一允许操作非 VLAN 设备的命令——它要传真实网卡名字，本来就是普通设备。

args.device1[23] = 0 那两行是防越界的兜底。IFNAMSIZ 是 16，但结构体里这个字段开了 24 字节，用户态塞满不带 \0 也能用。

两个小函数顺手看完，都只做一次指针偏移，没有查表：

c
/* 根据 vlan device 的名称，获取其所依附的 real device 的名称 */
void vlan_dev_get_realdev_name(const struct net_device *dev, char *result)
{
    strncpy(result, vlan_dev_priv(dev)->real_dev->name, 23);
}

vlan_dev_vlan_id(dev) 同理，返回 vlan_dev_priv(dev)->vlan_id。那个 23 就是 IFNAMSIZ 减一，是上面 args.device1[23] = 0 的来源。

设备建好之后，eth0.100 出现在 ip link 里，但还没有 IP、没有 up。它能不能工作，取决于底下 eth0 的状态，也取决于它自己的 netdev_ops——下一章。

四、vlan_ops：netdev_ops 的实现 #

vlan_setup 里把 dev->netdev_ops 指向了 vlan_netdev_ops，但这只是一份「兜底」赋值。真正定下来是在 vlan_dev_init 里，它会根据真实网卡有没有硬件 VLAN 能力，在两个 ops 表之间选一个：

c
static int vlan_dev_init(struct net_device *dev)
{
    struct vlan_dev_priv *vlan = vlan_dev_priv(dev);
    struct net_device *real_dev = vlan->real_dev;

    /* 根据 real device 是否支持 NETIF_F_HW_VLAN_TX，
     * 让 vlan device 的 netdev_ops 指向不同的接口函数。 */
    if (real_dev->features & NETIF_F_HW_VLAN_CTAG_TX) {
        dev->header_ops      = real_dev->header_ops;
        dev->hard_header_len = real_dev->hard_header_len;
        dev->netdev_ops      = &vlan_netdev_accel_ops;
        dev->vlan_features   = real_dev->vlan_features;
    } else {
        dev->header_ops      = &vlan_header_ops;
        dev->hard_header_len = real_dev->hard_header_len + VLAN_HLEN;
        dev->netdev_ops      = &vlan_netdev_ops;
    }

    dev->needed_headroom = real_dev->needed_headroom;

    if (is_vlan_dev(real_dev))
        dev->features &= ~(NETIF_F_TSO | NETIF_F_TSO6);

    return 0;
}

这段是硬件加速和软件路径的分岔口，第七、八两章反复回来看它。现在先记住两点结论：

  • 网卡能自己插标签（NETIF_F_HW_VLAN_CTAG_TX）→ 用 vlan_netdev_accel_ops，hard_header_len 不含那 4 字节，也不改 header_ops。
  • 网卡不能 → 用 vlan_netdev_ops，hard_header_len = real_dev->hard_header_len + VLAN_HLEN（18 而不是 14），header_ops 换成 VLAN 自己那套。

hard_header_len 加 4 不是摆设。上层按它算 headroom，skb_realloc_headroom 会多留 4 字节，正好够 skb_push 塞标签。

vlan_dev_init 挂在哪？它是 netdev_ops->ndo_init。设备注册时 register_netdevice 会调一次，返回非 0 就注册失败。对应的 ndo_uninit 是 vlan_dev_uninit，负责 vlan_vid_del 撤掉协议注册。

vlan_netdev_ops 这张表不长，逐项都有明确用意：

回调 VLAN 实现 作用
ndo_init vlan_dev_init 选 ops 表、设 header_ops 和 hard_header_len
ndo_uninit vlan_dev_uninit 撤掉 VID 相关的协议注册

open 和 stop 得看行为。VLAN 设备没有自己的收发队列，ndo_open（vlan_dev_open）主要干四件事：

  1. 查底层状态：if (!(real_dev->flags & IFF_UP) && !(vlan->flags & VLAN_FLAG_LOOSE_BINDING)) return -ENETDOWN;
  2. dev_uc_add(real_dev, dev->dev_addr)：VLAN 设备的 MAC 和真实网卡不同时，把它注册到真实网卡的单播地址表。
  3. IFF_ALLMULTI 时 dev_set_allmulti(real_dev, 1)，IFF_PROMISC 时 dev_set_promiscuity(real_dev, 1)。
  4. netif_carrier_off(dev)，随后等真实网卡 carrier 变化时由 netdev_upper_dev_link 建的上层关系通知下来。

第 1 条里的 VLAN_FLAG_LOOSE_BINDING 是实用开关。默认情况下底层网卡 down 了，VLAN 设备 up 会失败并返回 -ENETDOWN；打开 loose binding（ip link set eth0.100 type vlan loose_binding on）就允许在底层没 up 时先把 VLAN 设备 up 起来，等底层起来再通。做网络自动化脚本时这个位能省不少事。

第 2、3 条是把 VLAN 设备的状态透传给真实网卡。为什么必须透传？因为真实网卡不认识 VLAN 设备，收到的帧是带标签的，混杂模式必须由真实网卡打开，才能把不属于自己 MAC 的帧也捞上来给 VLAN 层处理。

ndo_stop（vlan_dev_stop）是上面每一步的逆操作，逐个 dev_uc_del、dev_set_allmulti(-1)、dev_set_promiscuity(-1)、dev_mc_unsync。这类成对函数读源码时建议一起看，只读一半容易漏掉引用计数配平。

ndo_change_rx_flags 就是把上层改 IFF_PROMISC、IFF_ALLMULTI 的请求转给真实网卡：

c
static void vlan_dev_change_rx_flags(struct net_device *dev, int change)
{
    struct net_device *real_dev = vlan_dev_priv(dev)->real_dev;

    if (dev->flags & IFF_UP) {
        if (change & IFF_ALLMULTI)
            dev_set_allmulti(real_dev, dev->flags & IFF_ALLMULTI ? 1 : -1);
        if (change & IFF_PROMISC)
            dev_set_promiscuity(real_dev,
                                dev->flags & IFF_PROMISC ? 1 : -1);
    }
}

ndo_get_stats64（vlan_dev_get_stats64）的处理方式在这里很有代表性。统计是 per-CPU 的，它 for_each_possible_cpu 逐个累加，读的时候用一对序列计数器函数 u64_stats_fetch_begin_irq() / u64_stats_fetch_retry_irq() 包住，写侧在 u64_stats_update_begin/end 里把 syncp 加一，读侧发现前后不一致就重读。VLAN 的收发统计全走这个机制，所以 vlan_pcpu_stats 里没有锁。

header_ops 这块是 VLAN 特有的，单独看。普通以太网设备的 header_ops 是 eth_header / eth_rebuild_header，VLAN 换成了自己的两个：

c
static const struct header_ops vlan_header_ops = {
    .create  = vlan_dev_hard_header,
    .rebuild = vlan_dev_rebuild_header,
    .parse   = eth_header_parse,
};

先看 vlan_dev_rebuild_header。它只在一种场景被调用：第一次 dev->hard_header 时目的 IP 还没解析，目的 MAC 填不出来，等 ARP 回来后由它补上：

c
static int vlan_dev_rebuild_header(struct sk_buff *skb)
{
    struct net_device *dev = skb->dev;
    struct vlan_ethhdr *veth = (struct vlan_ethhdr *)(skb->data);

    switch (veth->h_vlan_encapsulated_proto) {
#ifdef CONFIG_INET
    case htons(ETH_P_IP):
        /* TODO: Confirm this will work with VLAN headers... */
        return arp_find(veth->h_dest, skb);
#endif
    default:
        pr_debug("%s: unable to resolve type %X addresses\n",
                 dev->name, ntohs(veth->h_vlan_encapsulated_proto));
        ether_addr_copy(veth->h_source, dev->dev_addr);
        break;
    }

    return 0;
}

注意它是从 h_vlan_encapsulated_proto 取协议号的——因为 VLAN 设备的 skb->data 指向的是一个已经带标签的帧头，第 13、14 字节是 0x8100，真正的类型在偏移 16、17。

再看 vlan_dev_hard_header，这个函数背后有个老问题，源码作者自己都在注释里打问号：

c
/*
 * Create the VLAN header for an arbitrary protocol layer
 *
 * saddr=NULL means use device source address
 * daddr=NULL means leave destination address (eg unresolved arp)
 *
 * This is called when the SKB is moving down the stack towards the
 * physical devices.
 */
static int vlan_dev_hard_header(struct sk_buff *skb, struct net_device *dev,
                                unsigned short type,
                                const void *daddr, const void *saddr,
                                unsigned int len)
{
    struct vlan_dev_priv *vlan = vlan_dev_priv(dev);
    struct vlan_hdr *vhdr;
    unsigned int vhdrlen = 0;
    u16 vlan_tci = 0;
    int rc;

    if (!(vlan->flags & VLAN_FLAG_REORDER_HDR)) {
        vhdr = (struct vlan_hdr *) skb_push(skb, VLAN_HLEN);

        vlan_tci = vlan->vlan_id;
        vlan_tci |= vlan_dev_get_egress_qos_mask(dev, skb->priority);
        vhdr->h_vlan_TCI = htons(vlan_tci);

        /*
         * Set the protocol type. For a packet of type ETH_P_802_3/2 we
         * put the length in here instead.
         */
        if (type != ETH_P_802_3 && type != ETH_P_802_2)
            vhdr->h_vlan_encapsulated_proto = htons(type);
        else
            vhdr->h_vlan_encapsulated_proto = htons(len);

        skb->protocol = vlan->vlan_proto;
        type = ntohs(vlan->vlan_proto);
        vhdrlen = VLAN_HLEN;
    }

    /* Before delegating work to the lower layer, enter our MAC-address */
    if (saddr == NULL)
        saddr = dev->dev_addr;

    /* Now make the underlying real hard header */
    dev = vlan->real_dev;
    rc = dev_hard_header(skb, dev, type, daddr, saddr, len + vhdrlen);
    if (rc > 0)
        rc += vhdrlen;
    return rc;
}

两条分支对应两种 flags：

  1. 支持重排头（VLAN_FLAG_REORDER_HDR 置位，默认）：这里只造普通二层头，不动标签。标签留给 vlan_dev_hard_start_xmit 加。
  2. 不支持重排头：这里就把 4 字节标签塞进去了，vlan_dev_hard_start_xmit 里不会再塞。

源码作者留了个疑问：既然有不支持重排头的设备，那 vlan_dev_hard_start_xmit 里为什么没有按 vlan->flags 判断，而是去判断「包上是否已经有标签」？

答案在 vlan_dev_hard_start_xmit 的判断条件里：

c
if (veth->h_vlan_proto != vlan->vlan_proto ||
    vlan->flags & VLAN_FLAG_REORDER_HDR) {

它既看 h_vlan_proto 又看 flags。只要包上已经有 0x8100，第一个条件就不成立，配合 flags 一或，整体为假，跳过插标签。所以不必再单独判断一次 flags。

但这个写法本身有缺陷：它只看最外层有没有标签，判断不出是单层还是双层。想发 QinQ 双标签，第二次插标签的动作会被这个条件挡掉。要做双层标签只能改架构——把 vlan_hwaccel_put_tag 的检查逻辑换成语义化的「需要几层」，而不是「有没有」。这也是为什么内核后来引入了 vlan_dev_priv->flags 之外的 QinQ 支持（8021ad 模块），单靠 8021q 塞两层是做不到的。

ndo_fix_features 和 vlan_features 这条链要单独提一句：VLAN 设备对外宣告的 TSO/GSO/GRO 能力，来自真实网卡的 vlan_features 而不是 features。原因很直白——网卡如果连标签都处理不了，那它的分段卸载能力对带标签的帧也没意义。所以真实网卡驱动填 vlan_features 时只填「带标签也能做」的那部分能力。读驱动时看到 netdev->vlan_features = ... 就是填这个。

五、发送路径：加标签 #

发送走两个函数，一个造头，一个发射。造头的是 vlan_dev_hard_header（上一章看过），发射的是 ndo_start_xmit 指向的 vlan_dev_hard_start_xmit。3.14 的实现：

c
static netdev_tx_t vlan_dev_hard_start_xmit(struct sk_buff *skb,
                                            struct net_device *dev)
{
    struct vlan_dev_priv *vlan = vlan_dev_priv(dev);
    struct vlan_ethhdr *veth = (struct vlan_ethhdr *)(skb->data);
    unsigned int len;
    int ret;

    /* Handle non-VLAN frames if they are sent to us, for example by DHCP.
     *
     * NOTE: THIS ASSUMES DIX ETHERNET, SPECIFICALLY NOT SUPPORTING
     * OTHER THINGS LIKE FDDI/TokenRing/802.3 SNAPs...
     */
    if (veth->h_vlan_proto != vlan->vlan_proto ||
        vlan->flags & VLAN_FLAG_REORDER_HDR) {
        u16 vlan_tci;
        vlan_tci = vlan->vlan_id;
        vlan_tci |= vlan_dev_get_egress_qos_mask(dev, skb->priority);
        skb = __vlan_hwaccel_put_tag(skb, vlan->vlan_proto, vlan_tci);
    }

    skb->dev = vlan->real_dev;
    len = skb->len;
    if (unlikely(netpoll_tx_running(dev)))
        return vlan_netpoll_send_skb(vlan, skb);

    ret = dev_queue_xmit(skb);

    if (likely(ret == NET_XMIT_SUCCESS || ret == NET_XMIT_CN)) {
        struct vlan_pcpu_stats *stats;
        stats = this_cpu_ptr(vlan->vlan_pcpu_stats);
        u64_stats_update_begin(&stats->syncp);
        stats->tx_packets++;
        stats->tx_bytes += len;
        u64_stats_update_end(&stats->syncp);
    } else {
        this_cpu_inc(vlan->vlan_pcpu_stats->tx_dropped);
    }

    return ret;
}

四步，一步不能少：

  1. 判断要不要打标签，要就打。
  2. skb->dev 改成真实网卡。
  3. dev_queue_xmit 交给下一层。
  4. 记统计。

第 1 步是重点，也是最容易被误读的地方：__vlan_hwaccel_put_tag 并不往帧里插 4 个字节，它只改 skb 的两个字段：

c
static inline struct sk_buff *__vlan_hwaccel_put_tag(struct sk_buff *skb,
                                                     __be16 vlan_proto,
                                                     u16 vlan_tci)
{
    skb->vlan_proto = vlan_proto;
    skb->vlan_tci = vlan_tci | VLAN_TAG_PRESENT;
    return skb;
}

skb->vlan_tci 是非线性区之外的一个 __u16 字段，VLAN_TAG_PRESENT 是 0x1000，用它当「这个 skb 声明自己带标签」的标记位。真正的 4 字节插入发生在后面 dev_hard_start_xmit 里——或者根本不在软件里发生，网卡自己插。

所以 3.x 的发送路径可以这样概括：

text
vlan_dev_hard_start_xmit  --> 只设置 skb->vlan_tci，skb->dev = real_dev
        |
        v
dev_queue_xmit --> dev_hard_start_xmit
        |
        +--> 网卡支持 HW VLAN TX：把 skb->vlan_tci 交给驱动，
        |    驱动写进硬件的插入寄存器，网卡自己往帧里塞 4 字节
        |
        +--> 网卡不支持：__vlan_insert_tag 在软件里 skb_push 4 字节

vlan_dev_hard_start_xmit 里那个 if 的语义值得抠一遍：

c
if (veth->h_vlan_proto != vlan->vlan_proto ||
    vlan->flags & VLAN_FLAG_REORDER_HDR)

第一种情况 h_vlan_proto != vlan->vlan_proto：帧头上不是 0x8100（也不是 0x88a8），说明这个包是干净的、没标签，得补上。这也是注释里说的「Handle non-VLAN frames if they are sent to us, for example by DHCP」——DHCP 客户端会在 VLAN 设备上直接发不带标签的帧。

第二种情况 flags & VLAN_FLAG_REORDER_HDR：默认位，见上一章的分析——hard_header 阶段没插标签，所以这里补。

两个条件一或，覆盖了「该插标签」的全部场景；反过来说，帧头已经是 0x8100 且没有重排头标志时，说明标签已经在 hard_header 里插好了，跳过。

vlan_dev_get_egress_qos_mask 负责把 skb->priority 翻译成 802.1p 的三个 bit，填进 TCI 的高位：

c
u16 vlan_dev_get_egress_qos_mask(const struct net_device *dev, u32 skb_prio)
{
    struct vlan_priority_tci_mapping *mp;

    smp_rmb(); /* coupled with smp_wmb() in vlan_dev_set_egress_priority() */

    mp = vlan_dev_priv(dev)->egress_priority_map[(skb_prio & 0xF)];
    while (mp) {
        if (mp->priority == skb_prio)
            return mp->vlan_qos;
        mp = mp->next;
    }
    return 0;
}

smp_rmb() 和设置端（vlan_dev_set_egress_priority）的 smp_wmb() 配成一对。哈希桶是 (skb_prio & 0xF)，桶内挂链。返回的 vlan_qos 已经左移好了：

c
u32 vlan_qos = (vlan_prio << VLAN_PRIO_SHIFT) & VLAN_PRIO_MASK;

VLAN_PRIO_SHIFT 是 13，VLAN_PRIO_MASK 是 0xe000。TCI 的 bit15-13 是优先级，紧挨其上的 bit12 是 DEI，低 12 位是 VID，所以优先级要左移 13 位。vlan_dev_set_egress_priority 分两步：先在 (skb_prio & 0xF) 那个桶的链表里找同 priority 的节点，找到就改 vlan_qos 并维护 nr_egress_mappings（只在值从 0 变非 0 或反之时动计数）；找不到就 kmalloc 一个新节点插到桶头，插之前先 smp_wmb() 保证字段都已落内存，再发布指针。

第 2 步 skb->dev = vlan->real_dev 是整个发送路径的枢纽。在它之前 dev 是 eth0.100，之后 skb->dev 是 eth0。为什么必须在 dev_queue_xmit 之前改？因为 dev_queue_xmit 会拿 skb->dev 找发送队列、找 qdisc、找驱动的 ndo_start_xmit。指向虚拟设备会直接空指针。

第 3 步前面那个 netpoll_tx_running 分支是网络控制台（netpoll）专用的旁路。netconsole 打印日志时走的是轮询模式，不能进正常队列，所以直接调 vlan_netpoll_send_skb 把标签插好再 ndo_start_xmit。

第 4 步统计，注意 len = skb->len 是在 dev_queue_xmit 之前取的——dev_queue_xmit 会改 skb（比如 GSO 分段），取完再用会算错字节数。

老版本（2.6 / 早期 3.x）的发送函数长得不一样，标签是用 __vlan_put_tag 真往帧里插的：

c

vlan_tci |= vlan_dev_get_egress_qos_mask(dev, skb);
skb = __vlan_put_tag(skb, vlan_tci);   /* 真往帧里插 4 字节 */
...
skb->dev = vlan_dev_info(dev)->real_dev;   /* 插完标签才改 dev */

六、接收路径：剥标签 #

接收比发送绕，因为有两条路径同时存在，取决于网卡有没有硬件 VLAN 能力：

路径 触发条件 skb 状态 处理函数
硬件加速 网卡剥离标签，置 skb->vlan_tci 帧里没有标签，protocol 已是内层类型 vlan_hwaccel_do_receive
软件路径 帧里带 0x8100，skb->protocol == 0x8100 帧里 4 字节还在 vlan_skb_recv

两条路径都在 netif_receive_skb 这个交汇点上分出来。3.14 的主干逻辑（裁掉和 VLAN 无关的）：

c
int netif_receive_skb(struct sk_buff *skb)
{
    struct packet_type *ptype, *pt_prev;

    /* 这里是重点，但是只有网卡支持 VLAN 时才会设置 skb->vlan_tci */
    if (skb->vlan_tci && vlan_hwaccel_do_receive(skb))
        return NET_RX_SUCCESS;

    /* ……遍历 ptype_all 链表（ptype 为 ETH_P_ALL 的那些）…… */

    /* bridge 逻辑（可以看到 bridge 逻辑在 VLAN 处理之前） */
    skb = handle_bridge(skb, &pt_prev, &ret, orig_dev);

    /* 这里和 VLAN 没有关系，而是 mac-vlan 的相关功能，
     * 编译内核时选上 MAC_VLAN 模块，下面才会执行 */
    skb = handle_macvlan(skb, &pt_prev, &ret, orig_dev);

    /* 这里的 type 被置为 VLAN 协议，即 0x8100 */
    type = skb->protocol;

    /* 处理 ptype_base[ntohs(type) & PTYPE_HASH_MASK] 上所有 packet_type->func() */
    list_for_each_entry_rcu(ptype,
            &ptype_base[ntohs(type) & PTYPE_HASH_MASK], list) {
        if (ptype->type == type &&
            (ptype->dev == null_or_orig || ptype->dev == skb->dev ||
             ptype->dev == orig_dev)) {
            if (pt_prev)          /* 此时 orig_dev 为物理 dev，如 eth0 */
                ret = deliver_skb(skb, pt_prev, orig_dev);
            pt_prev = ptype;
        }
    }
}

三个观察点。

第一，skb->vlan_tci && vlan_hwaccel_do_receive(skb) 这一行是硬件加速路径的入口，它在 ptype_all 遍历之前就把包处理掉了，直接返回。所以开了硬件 VLAN offload 的机器上，抓包工具在物理网卡上看到的是剥掉标签的帧。

第二，为什么软件路径能命中？因为不支持 VLAN 的网卡把 0x8100 当普通 ethertype 收上来。驱动填 skb->protocol 的规则是「取帧的第 13、14 字节」，也就是 h_vlan_proto，于是 skb->protocol 就成了 0x8100。这行为在协议栈看来和收到了一个「以太网类型为 0x8100 的帧」没区别，于是按常规去 ptype_base 哈希桶里找注册了这个类型的处理函数。

第三，handle_bridge 排在 VLAN 之前。这个顺序有实际影响，第八章讲。

ptype_base 里那个 0x8100 的处理函数，是模块加载时注册的：

c
static struct packet_type vlan_packet_type __read_mostly = {
    .type = cpu_to_be16(ETH_P_8021Q),
    .func = vlan_skb_recv,   /* VLAN receive method */
};

所以软件路径的下一步就是 vlan_skb_recv。

c
int vlan_skb_recv(struct sk_buff *skb, struct net_device *dev,
                  struct packet_type *ptype, struct net_device *orig_dev)
{
    struct vlan_hdr *vhdr;
    struct net_device_stats *stats;
    u16 vlan_id;
    u16 vlan_tci;

    /* skb_share_check() 会调用 3 个函数：skb_shared()、skb_clone()、kfree_skb()，
     * 都很重要。skb_shared() 检查 skb->users 数目是否为 1，不为 1 则表示有多个
     * 协议栈模块要处理它，此时就需要使用 skb_clone() 来复制一份 skb；
     * kfree_skb() 并不一定释放 skb，只有当 skb->users 为 1 时，才会释放；
     * 否则只是递减 skb->users。 */
    skb = skb_share_check(skb, GFP_ATOMIC);
    if (skb == NULL)
        goto err_free;

    /* VLAN_HLEN 的值为 4 */
    if (unlikely(!pskb_may_pull(skb, VLAN_HLEN)))
        goto err_free;

    /* 从 skb 中获取到 vlan_id */
    vhdr = (struct vlan_hdr *)skb->data;
    vlan_tci = ntohs(vhdr->h_vlan_TCI);
    vlan_id = vlan_tci & VLAN_VID_MASK;

    rcu_read_lock();

    /* 这一步是核心，此时 skb->dev 为真正的设备，经过 vlan 处理后，
     * 报文应该被上层协议看作是由 vlan 虚拟设备接收的，
     * 因此这里设置 skb->dev 为虚拟的 vlan 设备。 */
    skb->dev = __find_vlan_dev(dev, vlan_id);
    if (!skb->dev)
        goto err_unlock;

    /* 更新设备统计计数 */
    stats = &skb->dev->stats;
    stats->rx_packets++;
    stats->rx_bytes += skb->len;

    /* 更新校验和，此时 data 指向了真正的数据字段，如 ip 或 arp 头 */
    skb_pull_rcsum(skb, VLAN_HLEN);

    skb->priority = vlan_get_ingress_priority(skb->dev, vlan_tci);

    vlan_set_encap_proto(skb, vhdr);   /* 重新设置 skb->protocol */

    skb = vlan_check_reorder_header(skb);   /* 去掉报文中的 VLAN tag */
    if (!skb)
        goto err_unlock;

    netif_rx(skb);   /* 再次送回协议栈 */

    rcu_read_unlock();
    return NET_RX_SUCCESS;

err_unlock:
    rcu_read_unlock();
err_free:
    kfree_skb(skb);
    return NET_RX_DROP;
}

逐段读。

skb_share_check 是必需的。这个 skb 走到这里时会被别的模块引用着（比如抓包程序、或者 ptype_all 上其他协议的处理函数），要改它就得先复制。skb->users 为 1 原样返回，大于 1 就 skb_clone 一份。

pskb_may_pull(skb, VLAN_HLEN) 保证 skb->data 处至少有 4 个字节线性可读。标签如果落在非线性（分页）的片段里，这时 pskb_may_pull 会把它拉到线性区。没这一步，直接解引用 vhdr->h_vlan_TCI 就是读越界。

SKB 数据结构这块有个细节容易错：vhdr = (struct vlan_hdr *)skb->data。此时 skb->data 指向的是标签起点，不是帧头。因为驱动在 eth_type_trans 里已经 skb_pull 过 14 字节了。所以 skb->data 正好落在 TCI 上。

__find_vlan_dev(dev, vlan_id) 用真实设备和 VID 找到虚拟设备。找不到就丢弃——说明这块网卡上没建过这个 VID 的 VLAN 设备，这个带标签的帧没人要。

skb_pull_rcsum(skb, VLAN_HLEN) 同时做两件事：skb_pull 把 4 字节标签从线性区摘掉（data 后移 4），rcsum 修正校验和。如果上一步是硬件校验和卸载（CHECKSUM_UNNECESSARY），rcsum 会改成 CHECKSUM_COMPLETE 让后面的协议层重算。注意它只动 data 指针，帧内容没变——标签 4 字节还留在那块内存里，只是不在 data 之前了。

vlan_set_encap_proto 把 skb->protocol 从 0x8100 改成内层的真实类型：

c
static inline void vlan_set_encap_proto(struct sk_buff *skb,
                                        struct vlan_hdr *vhdr)
{
    __be16 proto;
    unsigned char *rawp;

    /* 根据 VLAN 的报文格式可知，vhdr->h_vlan_encapsulated_proto
     * 就是真正以太网帧的类型，如 IP、ARP */
    proto = vhdr->h_vlan_encapsulated_proto;

    if (ntohs(proto) >= 1536) {
        skb->protocol = proto;
        return;
    }

    rawp = skb->data;
    if (*(unsigned short *)rawp == 0xFFFF)
        skb->protocol = htons(ETH_P_802_3);
    else
        skb->protocol = htons(ETH_P_802_2);
}

1536 是 0x0600，以太网 II 与 802.3 的分界线。小于它说明那个字段是长度而不是类型，于是按 802.3 处理：以 0xFFFF 开头是 ETH_P_802_3（原生的 802.3 帧），否则 ETH_P_802_2（带 LLC 的）。

vlan_check_reorder_header 处理标签残留在报文里的问题：

c
static inline struct sk_buff *vlan_check_reorder_header(struct sk_buff *skb)
{
    if (vlan_dev_priv(skb->dev)->flags & VLAN_FLAG_REORDER_HDR) {
        if (skb_cow(skb, skb_headroom(skb)) < 0)
            skb = NULL;
        if (skb) {
            /* 这个是重点，ETH_HLEN＝14，VLAN_ETH_HLEN＝18 */
            memmove(skb->data - ETH_HLEN,
                    skb->data - VLAN_ETH_HLEN, 12);
            skb->mac_header += VLAN_HLEN;   /* VLAN_HLEN=4 */
        }
    }
    return skb;
}

为什么不直接 skb_pull？因为 skb_pull 只挪 data 指针，帧头里那 4 字节的洞还在。上层拿到帧后按「14 字节以太网头 + payload」解释，中间夹着 4 字节垃圾就全乱了。所以这里要把 MAC 头挪回去，用拷贝覆盖的方式消掉那个洞。

memmove 的三个参数：目的 skb->data - ETH_HLEN（离开 14 字节处），源 skb->data - VLAN_ETH_HLEN（离开 18 字节处），长度 12——只搬两个 MAC 地址（6+6），因为后面两个类型字段已经被 skb_pull 处理掉了。

text
处理前：  [dst 6B][src 6B][0x8100 2B][TCI 2B][内层类型 2B][payload]
                                     ^data 指向这里（已 pull 14 字节）
处理后：  [dst 6B][src 6B][内层类型 2B][payload]
          ^---------- memmove 12 字节把 dst+src 前移 4 字节 ----------^

skb->mac_header += VLAN_HLEN 同步 MAC 头偏移，不然 skb_mac_header(skb) 会指错位置，后面 netfilter 取 MAC 头就取到标签上去了。

开 skb_cow 是因为要原地改帧内容，得先确保这块 skb 是私有的、可写的。

最后 netif_rx(skb) 把包再送回协议栈一次。因为 skb->dev 已经变成了 eth0.100、skb->protocol 已经变成内层类型、标签已经抹掉，第二次进 netif_receive_skb 时走的完全是另一条路：bridge 不会重复处理（有标志位）、0x8100 的 packet_type 不会再命中（protocol 变了），直接进 IP/ARP 的处理函数。

netif_receive_skb 这个函数在报文接收中会多次进入，这一点读代码时要有心理准备：网卡驱动收到报文是第一趟（dev=eth0），bridge 处理完后重入一趟（dev 换成 br0 或另一个口），vlan 处理完成后又重入一趟（dev=eth0.100）。

bridge 处理完会设置标志，再次进入时 handle_bridge 会跳过，所以不会死循环。VLAN 这一趟同理——skb->vlan_tci 已被清零、protocol 已改，硬件加速分支和 0x8100 分支都不会再命中。

3.x 还有另一条更常用的路径，不再走 netif_rx 重入，而是在 netif_receive_skb 内部就地转换。这就是 vlan_untag 加 vlan_do_receive：

c
bool vlan_do_receive(struct sk_buff **skbp)
{
    struct sk_buff *skb = *skbp;
    __be16 vlan_proto = skb->vlan_proto;
    u16 vlan_id = vlan_tx_tag_get_id(skb);
    struct net_device *vlan_dev;
    struct vlan_pcpu_stats *rx_stats;

    vlan_dev = vlan_find_dev(skb->dev, vlan_proto, vlan_id);
    if (!vlan_dev)
        return false;

    skb = *skbp = skb_share_check(skb, GFP_ATOMIC);
    if (unlikely(!skb))
        return false;

    skb->dev = vlan_dev;
    if (skb->pkt_type == PACKET_OTHERHOST) {
        /* 下层认为不是本机的，再比一次：允许 VLAN 设备的 MAC 与底层不同 */
        if (ether_addr_equal(eth_hdr(skb)->h_dest, vlan_dev->dev_addr))
            skb->pkt_type = PACKET_HOST;
    }

    if (!(vlan_dev_priv(vlan_dev)->flags & VLAN_FLAG_REORDER_HDR)) {
        unsigned int offset = skb->data - skb_mac_header(skb);
        /* vlan_insert_tag 要求 skb->data 指向 mac header，
         * 所以先挪回去，插完再挪回原位 */
        skb_push(skb, offset);
        skb = *skbp = vlan_insert_tag(skb, skb->vlan_proto, skb->vlan_tci);
        if (!skb)
            return false;
        skb_pull(skb, offset + VLAN_HLEN);
        skb_reset_mac_len(skb);
    }

    skb->priority = vlan_get_ingress_priority(vlan_dev, skb->vlan_tci);
    skb->vlan_tci = 0;

    rx_stats = this_cpu_ptr(vlan_dev_priv(vlan_dev)->vlan_pcpu_stats);
    u64_stats_update_begin(&rx_stats->syncp);
    rx_stats->rx_packets++;
    rx_stats->rx_bytes += skb->len;
    if (skb->pkt_type == PACKET_MULTICAST)
        rx_stats->rx_multicast++;
    u64_stats_update_end(&rx_stats->syncp);

    return true;
}

这个函数有个反直觉的地方：关掉重排头时它把标签插回去。因为关了重排头的设备，上层期望看到的帧头里带标签（和发送路径对称），而此时标签已经被剥到 skb->vlan_tci 里了，得重新 vlan_insert_tag 塞回帧里。插进去之后 skb_pull(offset + VLAN_HLEN) 把 data 挪回原位，skb_reset_mac_len 修正 MAC 长度。

PACKET_OTHERHOST 那一段解决一个实际问题：真实网卡和 VLAN 设备的 MAC 可以不同。驱动判断「目的 MAC 不是我的」就标成 PACKET_OTHERHOST 准备丢掉，但 VLAN 设备认这个 MAC。所以这里再比一次，命中就升级成 PACKET_HOST，否则路由会错。

vlan_do_receive 返回 true 表示「这个包归我处理了」，调用方 __netif_receive_skb_core 会直接进上层协议分发，不再走 netif_rx 那一圈。返回 false 表示不是 VLAN 包或者找不到对应设备，交回主干继续。

两套实现放一起对照：

项 linux 2.6.x linux 3.x
接收注册方式 dev_add_pack，注册进三层协议链表 packet_type 加 netif_receive_skb 里的 vlan_untag
剥标签的位置 VLAN 的接收函数里，改完 skb->dev 之后 netif_receive_skb 里，改 skb->dev 之前

最后这张表的最后一行是理解整个演进的钥匙：老实现把 VLAN 当「一个独立设备的事」，新实现把 VLAN 当「一块网卡的事」——标签在真实网卡这一层统一处理，VLAN 设备退化成纯粹的身份标识。这也解释了为什么 skb->vlan_tci 要设计成一个独立字段而不是帧内数据。

feature 位 含义 出现在哪
NETIF_F_HW_VLAN_CTAG_TX 硬件负责在发送时插标签 网卡驱动的 features
NETIF_F_HW_VLAN_CTAG_RX 硬件负责在接收时剥标签并填 skb->vlan_tci 网卡驱动的 features
NETIF_F_HW_VLAN_CTAG_FILTER 硬件能做 VLAN 过滤 网卡驱动的 features
NETIF_F_HW_VLAN_STAG_TX 对 0x88a8 外层标签的插标签能力 同上，QinQ 用

vlan_dev_init 只看 TX 那一位就决定 ops 表，因为发送路径完全由它决定；RX 那一位不改变 VLAN 设备的代码路径，只改变 skb 进来时的形态。

软件发送：__vlan_hwaccel_put_tag 设好 skb->vlan_tci，skb->dev 改成真实网卡，dev_queue_xmit 下去。到 dev_hard_start_xmit 里发现有 VLAN_TAG_PRESENT 而网卡没能力，就 __vlan_insert_tag 在软件里 skb_push 4 字节，把 TCI 和 encapsulated_proto 填好，再交给驱动：

c
/* net/core/dev.c，dev_hard_start_xmit 里的关键几行 */
if (skb_vlan_tag_present(skb) &&
    !vlan_hw_offload_capable(netif_skb_features(skb), skb->vlan_proto)) {
    skb = __vlan_insert_tag(skb, skb->vlan_proto, skb_vlan_tag_get(skb));
    skb->vlan_tci = 0;
}

硬件发送：dev_hard_start_xmit 把 skb 原样交给驱动，驱动从 skb->vlan_tci 里取出 TCI 写进网卡的插入寄存器，网卡在发帧时自己补 4 字节。软件里从头到尾没出现过那 4 字节。

硬件接收：网卡剥掉标签，把 TCI 放进接收描述符，驱动 __vlan_hwaccel_put_tag 填到 skb->vlan_tci，skb->protocol 已经是内层类型。netif_receive_skb 一进门就命中 skb->vlan_tci && vlan_hwaccel_do_receive(skb)，直接 return NET_RX_SUCCESS。软件接收则是帧带着 4 字节上来、skb->protocol == 0x8100，走 vlan_skb_recv。四条路放一张表：

软件路径 硬件路径
发送插标签 dev_hard_start_xmit 里 skb_push(4) 网卡硬件插，软件不碰帧
发送时 skb->vlan_tci 有值，仅作中转 有值，驱动读走
接收剥标签 vlan_skb_recv 里 skb_pull(4) 加 memmove 网卡剥，进栈时已无标签
接收时 skb->protocol 0x8100，需要 vlan_set_encap_proto 改 已是内层类型
抓包看到什么 物理网卡上带标签，VLAN 设备上不带 两边都不带标签
性能 每包多一次 skb_push/memmove 零拷贝，省 CPU

那个「抓包看到什么」的差异坑过不少人：在开了 rx-vlan-offload 的机器上 tcpdump -i eth0 看不到 802.1Q 标签，因为标签在驱动层就被摘走了，只有 tcpdump -i eth0.100 能看到解析好的内层报文。想看原始带标签的帧，得 ethtool -K eth0 rxvlan off 关掉卸载。反过来，虚拟化环境里为了让 guest 看到 VLAN，往往要求宿主机关掉 txvlan，否则虚拟机网卡收到的帧没标签，VLAN 感知的 guest 会认为是无标签帧。

八、VLAN 与网桥的交互 #

顺序问题在第六章埋了伏笔：netif_receive_skb 里 handle_bridge 排在 VLAN 分发之前。这意味着带标签的帧先过网桥，再过 VLAN。这个顺序决定了两种常见的接法完全不同：

第一种，把 VLAN 设备加进网桥（brctl addif br1 eth0.100）。帧的处理顺序是：网卡收包 → 网桥看 skb->dev 是 eth0，不是 br1 的成员，直接放行 → VLAN 剥标签、skb->dev 变 eth0.100 → netif_rx 重入 → 网桥发现 skb->dev 是 eth0.100，属于 br1，开始转发。VLAN 设备作为网桥端口时，网桥看到的是已经剥干净的帧，转发出去时由出口端口的 VLAN 设备再插标签。

第二种，把物理网卡加进网桥，让网桥自己做 VLAN 过滤（bridge vlan add）。这条路要求内核开了 CONFIG_BRIDGE_VLAN_FILTERING，网桥在 handle_bridge 里按 802.1Q 标签查 VLAN 表，vlan_filtering=1 时网桥自己解析 TCI。这时 VLAN 设备基本不参与，标签由网桥的 br_handle_frame 处理。

两种接法别混着用。第一层 eth0 上既有 eth0.100 又在 br0 里，再叠一个 VLAN 感知网桥，帧会被剥两次或标签对不上，排查起来很费劲。

还有一个细节：VLAN 设备的 priv_flags 带 IFF_802_1Q_VLAN，网桥据此在 br_add_if 里做特殊判断（比如不允许把 VLAN 设备设成 br0 的 vlan_filtering 端口）。读 net/bridge/ 时看到 is_vlan_dev() 就知道是这一层。

九、GVRP 与 VLAN 的动态注册 #

GVRP 是 802.1Q 的动态 VLAN 注册协议，让交换机之间自己协商哪些 VID 需要放行，省掉手工配。内核里的支持很薄，就一个 VLAN_FLAG_GVRP。

打开这个位走 vlan_dev_change_flags：

c
int vlan_dev_change_flags(const struct net_device *dev, u32 flags, u32 mask)
{
    struct vlan_dev_priv *vlan = vlan_dev_priv(dev);
    u32 old_flags = vlan->flags;

    if (mask & ~(VLAN_FLAG_REORDER_HDR | VLAN_FLAG_GVRP |
                 VLAN_FLAG_LOOSE_BINDING | VLAN_FLAG_MVRP))
        return -EINVAL;

    vlan->flags = (old_flags & ~mask) | (flags & mask);

    if (netif_running(dev) && (vlan->flags ^ old_flags) & VLAN_FLAG_GVRP) {
        if (vlan->flags & VLAN_FLAG_GVRP)
            vlan_gvrp_request_join(dev);
        else
            vlan_gvrp_request_leave(dev);
    }

    if (netif_running(dev) && (vlan->flags ^ old_flags) & VLAN_FLAG_MVRP) {
        if (vlan->flags & VLAN_FLAG_MVRP)
            vlan_mvrp_request_join(dev);
        else
            vlan_mvrp_request_leave(dev);
    }

    return 0;
}

两处设计值得记：第一，mask 只允许改四个已定义的位，其他位传进来直接 -EINVAL，避免用户态把保留位写坏。第二，只在 netif_running(dev) 时才去发协议帧——设备没 up 就发了也没意义，等 up 的时候再补。

vlan_gvrp_request_join 在 vlan_gvrp.c 里，做的事就是构造一个 GARP 格式的帧，把本设备的 VID 通告出去。它注册在 garp_init_applicant 上，用 GARP 的通用状态机（net/802/garp.c），自己只提供 vlan_gvrp_attr_* 几个回调。MVRP 是同一套框架的另一个应用（net/802/mrp.c），走 VLAN_FLAG_MVRP。

模块初始化时把这两个应用挂上去：

c
vlan_gvrp_init();   /* garp_init_applicant(dev, &vlan_gvrp_app) */
vlan_mvrp_init();

反过来，接收到的 GVRP/MVRP 帧由 garp_rcv / mrp_rcv 处理，处理后调 vlan_gvrp_app 的回调，回调里会 register_vlan_dev 或 unregister_vlan_dev。这就是「动态注册」的完整链路：协议帧进来 → GARP 状态机 → VLAN 模块建/删设备。

生产环境里 GVRP 用得少，多数交换机默认关着，原因是安全性——谁都能往线路上通告 VID 就能蹭进别人的 VLAN。这也是为什么内核默认不开 VLAN_FLAG_GVRP。

十、procfs 与调试信息 #

VLAN 模块的调试入口在 /proc/net/vlan/，由 vlanproc.c 注册。两个文件：

text
/proc/net/vlan/config      全局配置：命名策略、已有 VLAN 设备列表
/proc/net/vlan/eth0.100    单个设备的详情：VID、真实设备、flags、统计

config 的内容长这样：

text
VLAN Dev name    | VLAN ID
Name-Type: VLAN_NAME_TYPE_RAW_PLUS_VID_NO_PAD
eth0.100         | 100  | eth0

第二行就是 vn->name_type 对应的字符串，SET_VLAN_NAME_TYPE_CMD 改的就是它。单设备文件里能看到 VID、Device、Flags（REORDER_HDR、GVRP、LOOSE_BINDING 的开关状态），以及 INGRESS priority mappings 和 EGRESS priority mappings 两段——前面写的 ingress_priority_map[8] 和 egress_priority_map[16] 在这里能直接看到内容，调 QoS 映射时很有用。

设备创建时 vlan_proc_add_dev 造目录项，把返回值存进 vlan->dent；卸载时 vlan_proc_rem_dev 拿 dent 删。dent 这个字段就是为了这件事存在的。

十一、读源码的方法 #

这套代码自己读一遍比看十篇分析都强。顺序建议这样：

  1. 先读 vlan.h 和 vlan_dev.c 顶部，把 vlan_dev_priv 的字段和 vlan_netdev_ops 的表看全，知道有哪些入口。
  2. 再读 register_vlan_dev，搞清楚设备怎么来的、hlist 挂在哪、dev_hold 谁欠谁的账。
  3. 然后顺着 ndo_start_xmit 读发送，在 dev_hard_start_xmit 上打断点最直观。
  4. 接收方向从 netif_receive_skb 开始，先找 vlan_hwaccel_do_receive 那一行，再找 ptype_base 分发的 vlan_packet_type。
  5. 最后看 vlan_core.c 里的 vlan_do_receive，和 vlan_skb_recv 对照，就能看清两代实现的差别。

配合三个实战手段：

  • ethtool -k eth0 | grep vlan 看卸载能力，决定走哪条路。
  • cat /proc/net/vlan/eth0.100 看 flags 和统计，确认设备真的在收发。
  • bpftrace -e 'kprobe:vlan_skb_recv { printf("%s\n", comm); }' 直接验证软件路径有没有被走到。

读的时候注意两件事：一是内核版本，网上大量分析基于 2.6，函数名和调用的函数都不一样（vlan_dev_info 对 vlan_dev_priv，__vlan_put_tag 对 __vlan_hwaccel_put_tag）；二是看 flags 的分支，收发两条路上的行为差异大半由 VLAN_FLAG_REORDER_HDR 决定，忽略它就会出现「代码和文章对不上」的困惑。
