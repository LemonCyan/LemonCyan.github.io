本篇只讲一件事：Linux 网络协议栈的整体骨架——它分几层、每层落在哪些代码里、一个包怎么在层与层之间流动。

讲什么：四层 Internet 模型与内核实现的对应关系；sk_buff 的结构与指针操作；四张注册表（packet_type、net_proto_family、proto_ops、proto）；Netfilter 的五个 hook 点；一次收发的完整函数链；源码目录怎么翻。

不讲什么：Netlink 的报文格式与实现、Wireshark 抓包实操、链路层与网桥的二层转发、VLAN 原理与源码、路由表与策略路由、NAT、组播、Netfilter 的规则语法与 conntrack 内核机制。

跨篇指路：套接字 API 与 TCP/UDP 基本功看同目录的「网络协议基础」；收发路径逐个函数的展开看「数据收发路径」；iptables 规则怎么排、conntrack 怎么跟，看「Netfilter」和「NAT」。

一、协议栈在系统中的位置 #

用户态和内核态的分界线就是系统调用。网络这件事横跨这条线。

应用层调 socket(AF_INET, SOCK_STREAM, 0)，落到内核是 sys_socket，最终走到 sock_create()，返回一个文件描述符。这个 fd 属于文件系统，网络 socket 和普通文件共用一套读写接口——read/write 能直接作用在 socket 上。

所以「网络通信」在 Linux 里被建模成「对文件的操作」。这不是修辞，是代码事实：socket 走的是 struct file + struct file_operations 那条路。

struct socket 和 struct sock 一对一。前者是给文件系统看的壳，后者是协议栈的实体。struct sock 里有三个队列：rx 存待上层读取的接收报文，tx 存待发送的报文，err 存错误与异常通知。它们在 struct sock 初始化时建好，后面收发过程中，队列里的每个元素都是一个 sk_buff 实例的 skb。

分层不是 Linux 发明的。OSI 七层在那，四层 Internet 模型在那，Linux 做的是把模型翻译成数据结构、函数表和指针。

中间那五块就是本篇要逐层拆开的东西。顶部系统调用接口和底部驱动之间，流动的东西只有一个——sk_buff 指针。

二、分层结构总览 #

四层 Internet 模型从下往上：链路层、网络层、传输层、应用层。

  • 链路层：提供对物理层访问的设备驱动程序。介质可以是串口链路，也可以是以太网。代表协议有 SLIP、CSLIP、PPP，以太网是最常用的高速介质。
  • 网络层：把报文定向到目标位置，管主机与主机之间的通信。核心是 IP，同层还有 ICMP、ARP 这类满足其他需求的协议。
  • 传输层：管端到端通信，也就是主机内部各端口之间的通信。上面是 TCP 和 UDP。
  • 应用层：语义层，理解要传输的数据是什么。HTTP 管 Web 请求响应，SMTP 管邮件。

把模型和内核实现对起来：

Internet 模型 内核里的对应物 数据单位 代表协议 主要文件
应用层 用户态程序 + 系统调用接口 消息、字节流 HTTP、SMTP、DNS net/socket.c
传输层 struct proto（tcp_prot/udp_prot） 段（segment）、数据报 TCP、UDP、SCTP net/ipv4/tcp*.c、udp.c
网络层 struct packet_type、路由表 包（packet） IP、ICMP、ARP、IGMP net/ipv4/ip_input.c、ip_output.c
网络接口层 struct net_device + 驱动 帧（frame） Ethernet、PPP、SLIP net/core/dev.c、drivers/net/

2.1 五个核心元素 #

序号 元素 职责 位置
1 系统调用接口 给用户态提供访问内核网络子系统的入口 net/socket.c 的 sys_socketcall
2 协议无关层 用一套通用函数支持各种协议 struct socket、struct sock
3 网络协议 TCP、UDP、IP 的实际实现 net/ipv4/、net/ipv6/
4 设备无关层 提供与各类驱动通信的通用接口 net/core/dev.c
5 设备驱动程序 操作具体硬件或虚拟设备 drivers/net/

第 1 块同时是两样东西。用户发起网络调用时通过它进内核，过程是多路的，最后在 sys_socketcall 收口，再按调用号分路发到指定目标。换个角度看，它又是一套普通文件操作——socket 用 fd 表示，read/write 直接可用。它还承担了「在用户空间和内核之间转移控制」的职责。

第 2 块是 socket 层，协议无关的操作集合。同一个 socket() 调用，AF_INET 走 inet 簇，别的 family 走别的簇。第 4 块把协议和功能各异的硬件隔开，向上给协议一套通用函数，向下给驱动一套通用函数。

2.2 分层与注册：这套结构的两个支点 #

很多人把「分层」理解成「上层函数调下层函数」。Linux 协议栈不是这么干的。

真正的机制是：每层拿到数据后，读一个协议号字段，去一张注册表里查，查到谁就交给谁。 层与层之间是查表关系，不是硬编码的调用关系。

具体到四处查表：

位置 看哪个字段 查哪张表 查到什么
链路层收完帧 skb->protocol（0x0800 = IPv4） ptype_base 哈希表 / ptype_all 链表 packet_type，其 func 指向 ip_rcv 或 arp_rcv
网络层收完包 iph->protocol（6 = TCP，17 = UDP） inet_protos[] net_protocol，其 handler 指向 tcp_v4_rcv / udp_rcv
建 socket 时 family（AF_INET） net_families[] net_proto_family，其 create 指向 inet_create
建 socket 时 type + protocol inetsw[] inet_protosw，其 prot 指向 tcp_prot，ops 指向 inet_stream_ops

这张表是整篇文章的骨架，后面每章都会回来看它。

为什么这么设计？因为加一个新协议不需要改上下层代码。塞一个新传输层协议进去，写好自己的 proto 和 proto_ops，初始化时 proto_register() 一次，再 inet_register_protosw() 挂进 inetsw[]。IP 层一个字都不用动，它照样按 iph->protocol 查表，查到你的 handler 就调。

反过来，没有注册表的话，每加一个协议就要去 ip_local_deliver_finish 里加一个 switch/case。加十个协议，改十次核心文件。这就是「分层 + 注册」相对「分层 + 硬编码」的全部区别。

text
应用层 ─┐  socket() 查 net_families[]
传输层 ─┤  收包查 inet_protos[]   by iph->protocol
网络层 ─┤  收帧查 ptype_base[]    by skb->protocol
链路层 ─┘

一个协议想插进来，就在对应那一层注册一次。上下的代码不认识它，但表认得它。

三、网络接口层 #

链路层的功能定义：在物理层提供比特流服务的基础上，建立相邻结点之间的数据链路，通过差错控制让数据帧在信道上无差错传输。

拆开是五件事：物理地址寻址、数据的成帧、流量控制、数据的检错、重发。数据单位叫帧（frame）。代表协议有 SDLC、HDLC、PPP、STP、帧中继，以及最常打交道的以太网。

3.1 net_device：所有网络设备的统一抽象 #

Linux 给所有网络设备一个统一接口，struct net_device。它表示网络设备在内核中的情况，也就是网络设备接口。

它同时覆盖两类东西：软件虚拟设备（环路设备 lo、网桥、veth、tun/tap）和网络硬件设备（以太网卡，比如 DM9000、igb、ixgbe）。内核对网络设备用面向对象的思想设计。

net_device 定义在 include/linux/netdevice.h。主要成员分组：

成员组 内容
设备名称 name，如 eth0
总线参数 IRQ 号、I/O 基地址、DMA 通道
协议参数 硬件头长度 hard_header_len、MTU
链路层变量 dev_addr（MAC 地址）、flags
接口标志 IFF_UP、IFF_BROADCAST、IFF_PROMISC
设备方法 ndo_start_xmit（老代码叫 hard_start_xmit）、ndo_init
统计信息 stats，收发字节数、错误数、丢包数

内核有一个 dev_base 全局指针，指向设备链表，链起来的每个节点是一个 net_device。系统内所有网络设备都在这条链上。想知道机器上有几张网卡、各自什么状态，从 dev_base 顺着走一遍就完了。

net_device 里提供了大量供系统访问和协议层调用的设备方法：初始化、打开关闭、数据包发送、数据包接收。

3.2 注册与注销 #

c
int  register_netdevice(struct net_device *dev);
void unregister_netdevice(struct net_device *dev);

注册流程是固定套路：

  1. 驱动分配并填好一个 net_device 结构。
  2. 调用 register_netdevice，把结构传进去。
  3. 内核调用它的 init 方法（定义了的话）。
  4. 跑一组健全性检查。
  5. 创建一个 sysfs 条目。
  6. 把新设备加入设备链表（内核中的活动设备链表）。

这两个函数在 net/core/dev.c 里实现。驱动在 dev 结构中把接口配置好之后，调一次 register_netdevice，配置就生效了。网络设备专用的驱动都在 linux/drivers/net 下。

3.3 发送方向：dev_queue_xmit #

协议层要把 sk_buff 交给设备，用 dev_queue_xmit。它把 sk_buff 排进队列，由底层驱动完成最终传输，用的是 sk_buff 里引用的 net_device，也就是 skb->dev。

dev 结构里有个方法叫 hard_start_xmit，保存着真正发起传输的驱动函数。它只有一个参数：sk_buff。具体操作取决于底层硬件，套路是把 sk_buff 描述的报文搬进硬件环或队列。

以 DM9000 为例，链路层调 dev_queue_xmit 处理发送队列，之后调用网卡的 dm9000_xmit() 发数据包，发完调 dm9000_xmit_done() 处理结果。

3.4 接收方向：netif_rx 与 NAPI #

报文接收有两条路。

老路：驱动收完报文（已经在分配好的 sk_buff 里），调用 netif_rx 把 sk_buff 上传。这个函数通过 netif_rx_schedule 把 sk_buff 在上层协议队列里排队，等以后处理。

新路（NAPI）：内核 2.5 引入的一组新 API。高负载下性能更好，因为它不给每个进来的帧都产生一次中断。部分驱动用 NAPI，老式帧接收接口也有大量驱动在用。NAPI 驱动会对底层硬件能力做一些限制。两条路最后都汇到软中断 NET_RX_SOFTIRQ，由 net_rx_action 统一处理。netif_rx、netif_rx_schedule、dev_queue_xmit、net_rx_action 全在 net/core/dev.c。

3.5 驱动队列：只存指针，不存数据 #

IP 栈和 NIC 驱动之间有一个 driver queue（驱动队列）。典型实现是 FIFO ring buffer，可以当成固定大小看待。

关键点：这个队列不包含 packet data，只存 sk_buff 的指针。

队列的输入端是 IP 栈处理完的报文——要么本机应用产生的，要么进本机又要被路由出去的。被 IP 栈加入队列的报文，会被网络设备驱动取出，通过数据总线发到 NIC 硬件，然后上线路。不用 TSO/GSO 的情况下，IP 栈发到这个队列的报文长度必须小于 MTU。

3.6 MTU 与 IP 分片 #

绝大多数网卡有一个固定的最大传输单元（MTU），是该设备能传输的最大帧。以太网默认 1500 字节，支持巨帧的能到 9000。

在 IP 栈内，MTU 表示能发给 NIC 的最大 packet 大小。应用往 TCP socket 写 2000 字节，IP 栈就得造两个 IP 包，保证每个不超过 1500。这就是 IP 分片（IP fragmentation）。对大数据传输，较小的 MTU 会导致大量小包涌进驱动队列——这是分片的代价，不是收益。

text
payload 1500 bytes
MTU=1000 → 两个包：1000 + 500
MTU=600  → 三个包：600 + 600 + 300

3.7 物理层：最后一步与清理 #

物理层收到发送请求后，通过 DMA 把主存中的数据拷到内部 RAM（buffer）。拷贝过程中同时加入符合以太网协议的 header、IFG、前导符和 CRC。以太网物理层发送采用 CSMA/CD，边发边侦听链路冲突。

网卡发完报文会产生中断通知 CPU，驱动层的中断处理程序此时才去删掉那个保存着的 skb。整个发送链条到这里才算收尾——中间任何一层都不是终点，skb 的生命周期由最后一环负责释放。

四、网络层与 IP #

网络层的任务：选择合适的网间路由和交换结点，确保数据及时传送。它把链路层提供的帧组成数据包，包中封装网络层包头，包头里含有逻辑地址——源站点和目的站点的网络地址。

五件主要任务：

  1. 路由处理，即选择下一跳。
  2. 添加 IP header。
  3. 计算 IP header checksum，用于检测 IP 报文头部在传播过程中是否出错。
  4. 长度超过 MTU 且允许分片时，做 IP 分片。
  5. 处理完毕，获取下一跳的 MAC 地址，设置链路层报文头，转入链路层处理。

第 5 步是关键。网络层不碰网线，它只知道下一跳的逻辑地址，必须借 ARP 换成 MAC 地址才能交给链路层。这一层是「逻辑寻址」和「物理寻址」的转换点。

4.1 IP 首部 #

c
struct iphdr {
    __u8  version;      /* 版本，4 = IPv4 */
    __u8  ihl;          /* 首部长度，单位 4 字节 */
    __u8  tos;          /* 服务类型 */
    __u16 tot_len;      /* 总长度（首部 + 数据） */
    __u16 id;           /* 分片标识 */
    __u16 frag_off;     /* 分片偏移 + 标志位（DF / MF） */
    __u8  ttl;          /* 生存时间，每跳减一 */
    __u8  protocol;     /* 上层协议号：6=TCP，17=UDP，1=ICMP，2=IGMP */
    __u16 check;        /* 首部校验和 */
    __u32 saddr;        /* 源地址 */
    __u32 daddr;        /* 目的地址 */
};

两个字段后面会被反复提到：protocol 是网络层查 inet_protos[] 的键；frag_off 里的 DF 位一旦置位就表示禁止分片，分片时看到这个位，就得回一个 ICMP 差错报文。

4.2 发送：ip_queue_xmit #

传输层把 skb 交给 IP 层，入口是 ip_queue_xmit（TCP 走这里）或 ip_append_data（UDP 走这里）。

text
ip_queue_xmit(skb)
  ├─ 检查 skb->dst 路由信息，没有（比如套接字的第一个包）就 ip_route_output() 选一条
  ├─ 填充 IP 包各字段：version、ihl、tos、ttl、protocol...
  ├─ 长度 > mtu 且 gso 长度不为 0 ?
  │    ├─ 是 → ip_fragment()  分片
  │    │        └─ 检查 IP_DF：禁止分片则 icmp_send() 回「需要分片」的
  │    │           目的不可达报文，设置分片失败状态，释放 skb，返回消息过长
  │    └─ 否 → ip_finish_output2() 直接发
  └─ ip_finish_output2()
       ├─ 链路层报头缓存有（hh 不为空）→ 拷进 skb
       └─ 没有 → neigh_resolve_output()  用 ARP 获取

ip_finish_output2 那一步是「设置链路层报文头」。邻居子系统（neighbour）负责把下一跳 IP 解析成 MAC，结果缓存在 hh（硬件头缓存）里。第一次发往某个下一跳要等 ARP，之后直接命中缓存。

4.3 接收：ip_rcv 到 ip_local_deliver #

IP 层的入口函数是 ip_rcv。它先做各种检查，包括 packet checksum。然后按需做 IP defragment——把多个分片合并回一个完整报文。接着把 packet 交给已经注册的 Pre-routing netfilter hook，走完 hook 到达 ip_rcv_finish。

ip_rcv_finish 调 ip_router_input，进入路由处理环节。它先调 ip_route_input 更新路由，再查 route，然后决定这个包的命运：发到本机、转发出去、还是丢弃。

发到本机：调 ip_local_deliver，这里会做 defragment（合并多个 IP packet），然后进 ip_local_deliver_finish。该函数按包的下一个处理层的协议号（iph->protocol）查表，调用下一层接口：

iph->protocol 处理函数 协议
6 tcp_v4_rcv TCP
17 udp_rcv UDP
1 icmp_rcv ICMP
2 igmp_rcv IGMP

TCP 的话，tcp_v4_rcv 被调用，处理流程进入 TCP 栈。

需要转发：进入转发流程。该流程处理 TTL（减一，归零就丢并回 ICMP 超时），再调 dst_input。dst_input 做三件事：处理 Netfilter Hook、执行 IP fragmentation（出接口 MTU 更小的话）、调用 dev_queue_xmit 进入链路层。

这一段是「本机」和「转发」的分岔口。同一份 ip_rcv 代码，路由判决之后走向完全不同。防火墙设备就是靠在这条路径上插 hook 实现功能的。

五、传输层 #

传输层的最终目的是向它的用户提供高效、可靠、成本可控的数据传输服务。主要功能四项：构造 TCP segment、计算 checksum、发送回复（ACK）包、滑动窗口（sliding window）等保证可靠性的操作。

传输层是唯一关心「可靠性」的层。IP 层能丢包、能乱序、能重复，这些在传输层被修正。UDP 选择不修正，所以它简单。

5.1 TCP 发送：tcp_sendmsg 的四个动作 #

tcp_sendmsg 先检查已建立的 TCP connection 状态，然后获取该连接的 MSS，开始 segment 发送流程。

  1. 构造 TCP 段的 payload：在内核空间创建该 packet 的 sk_buff 实例 skb，从 userspace buffer 把数据拷到 skb 的 buffer。
  2. 构造 TCP header。
  3. 计算 TCP 校验和（checksum）和顺序号（sequence number）。
  4. 发到 IP 层处理：调用 IP handler 句柄 ip_queue_xmit，把 skb 传入 IP 处理流程。

关于第 3 步的校验和，几点必须记清：

  • TCP 校验和是端到端的。发送端计算，接收端验证。
  • 目的是发现 TCP 首部和数据在发送端到接收端之间发生的任何改动。
  • 接收方检测到校验和有差错，该 TCP 段会被直接丢弃。
  • 校验和覆盖 TCP 首部和 TCP 数据，TCP 的校验和是必需的。

MSS 在连接建立阶段就协商好了。三次握手期间双方确定各自使用的 Maximum Segment Size，这个值直接决定 tcp_sendmsg 每次能塞多少数据进一个段。UDP 面向无连接，没有这一步。

5.2 UDP 发送：两步 #

  1. 把 message 封装成 UDP 数据报。
  2. 调用 ip_append_data() 把 packet 送到 IP 层处理。

入口不同：TCP 走 ip_queue_xmit，一次一个 skb；UDP 走 ip_append_data，它支持把多个片段追加进同一个 skb。

5.3 TCP 接收：tcp_v4_rcv #

TCP 的处理入口是 tcp_v4_rcv，位于 net/ipv4/tcp_ipv4.c。它做 TCP header 检查等处理，然后：

  1. 调用 __tcp_v4_lookup（老代码叫 _tcp_v4_lookup），查找该 packet 的 open socket。找不到，包被丢弃。
  2. 检查 socket 和 connection 的状态。
  3. 状态正常的话，调 tcp_prequeue，让 packet 从内核进入 user space 方向——放进 socket 的 receive queue。之后 socket 被唤醒，应用调 system call，最终调 tcp_recvmsg 从 socket receive queue 取 segment。

第 1 步「找不到就丢」是排查问题的常见落点。抓包看到包到了网卡但应用收不到，先查这里——端口没监听，或者四元组对不上。

5.4 UDP 接收 #

udp_rcv 检查 UDP 头合法性，交给 udp_queue_rcv（不同内核版本名字有差异），最终提交给 sock_queue_rcv，把 skb 挂进 socket 的接收队列。

数据包进入 socket 部分的第一个函数是 skb_recv_datagram()，它从内核的 socket 队列取出数据包，交给 udp_recvmsg()，该函数负责处理 UDP 数据。

六、应用层与套接字 #

应用层的各种网络程序，都是通过 Linux Socket 编程接口和内核空间的协议栈通信的。

Socket 是从 BSD Socket 发展来的。它在层次上位于应用层，是操作系统给应用程序员提供的 API，通过它，应用可以访问传输层协议。

三句话概括它的地位：

  • socket 位于传输层协议之上，屏蔽了不同网络协议之间的差异。
  • socket 是网络编程的入口，提供了大量系统调用，构成网络程序的主体。
  • socket 属于文件系统的一部分，网络通信被看作对文件的读取，我们对网络的控制和对文件的控制一样方便。

6.1 创建与连接 #

socket(int family, int type, int protocol) 最终调 socket() 系统调用，再调 sock_create()，返回创建好的 socket 的 file descriptor。每个 userspace 网络应用创建的 socket，在内核里都有一个对应的 struct socket 和 struct sock。三个参数就是查表的三个键，2.2 节那张表说的就是它们。

TCP socket 接下来调 connect()，客户端和服务器端通过该 socket 建立虚拟连接。过程中 TCP 协议栈通过三次握手建立连接。这个 API 默认会等到 TCP 握手完成、连接建立后才返回。建立连接过程中有一个重要步骤：确定双方使用的 MSS。UDP 面向无连接，不需要这一步。

6.2 发送 #

应用调 send 或 write 发一个 message 给接收端。内核侧：

text
send() / write() / sendto() / sendmsg()
  └─ sock_sendmsg()
       ├─ 用 socket descriptor 拿到 sock struct
       ├─ 创建 message header 和 socket control message
       └─ _sock_sendmsg()
            └─ 按 socket 的协议类型调对应协议的发送函数
                 ├─ TCP → tcp_sendmsg()
                 └─ UDP → udp_sendmsg()

UDP 的话，userspace 可以调 send()、sendto()、sendmsg() 三个 system call 中任意一个来发 UDP message，它们最终都会调到内核里的 udp_sendmsg()。

6.3 接收 #

text
read() / recvfrom() / recvmsg()
  └─ sys_recv()            net/socket.c
       └─ sys_recvfrom()
            └─ sock_recvmsg()
                 └─ inet_recvmsg()     net/ipv4/af_inet.c
                      ├─ TCP → tcp_recvmsg()  从 socket buffer 拷数据到 user buffer
                      └─ UDP → udp_recvmsg()

对 INET 类型的 socket，net/ipv4/af_inet.c 里的 inet_recvmsg 会被调，它再调相关协议的数据接收方法。tcp_recvmsg 从 socket buffer 里把数据拷到 user buffer。

6.4 系统调用到内核入口对照表 #

用户态调用 内核入口 最终协议函数
socket() sys_socket → sock_create inet_create
connect() sys_connect → sock->ops->connect inet_stream_connect → tcp_v4_connect
send() / write() sys_sendto → sock_sendmsg → _sock_sendmsg tcp_sendmsg / udp_sendmsg
recv() / read() sys_recvfrom → sock_recvmsg → inet_recvmsg tcp_recvmsg / udp_recvmsg
close() sys_close → sock_close inet_release

规律：所有系统调用都先穿进 net/socket.c 的通用层，通用层拿 struct sock 的 ops（proto_ops）指针，再跳到协议实现。应用层不认识 TCP，它只认识 proto_ops 接口。

这就是「协议无关层」的真实含义——不是抽象概念，是一个函数指针表。

七、sk_buff：贯穿全栈的数据载体 #

前面反复出现一个词：skb。这一章把它拆开。

7.1 它是干什么的 #

网络包被内核处理时，底层协议的数据被传送到更高层，发送时过程反过来。不同协议产生的数据（包括头和负载）不断往下层传递，直到最终被发送出去。这些操作的速度对网络层表现至关重要，所以内核用一个专门的结构：sk_buff。Socket buffer 被用来在网络实现层交换数据而不用拷来拷去——这是速度收益的来源。

skb 是 Linux 内核网络栈（L2 到 L4）处理网络包所使用的 buffer，类型是 sk_buff，定义文件在 include/linux/skbuff.h。一句话：一个 skb 表示 Linux 网络栈中的一个 packet。TCP 分段和 IP 分组产生的多个 skb，用一个 skb list 的形式保存。

还有一句更重要的话，这里先立住：

整个协议栈传递的不是数据本身，而是 sk_buff 指针。

数据在内存里只有一份。每层拿到的都是同一个结构体的地址，改的是这个结构体里的几个指针。

7.2 结构：数据缓冲区 + 头部指针 + 元数据 #

sk_buff 分成两部分：一部分是存储数据包的缓存，另一部分是一组用于内核管理的指针。

c
struct sk_buff {
    /* These two members must be first. */
    struct sk_buff      *next;      /* packet 可存在于 list 或 queue 中，这两个成员用于链表处理 */
    struct sk_buff      *prev;
    struct sk_buff_head *list;      /* 该 packet 所在的 list */
    struct sock         *sk;        /* 跟该 skb 相关联的 socket */
    struct timeval       stamp;     /* packet 发送或接收的时间，主要给 packet sniffers 用 */
    struct net_device   *dev;       /* 三个设备指针，跟踪该 packet 相关的 devices */
    struct net_device   *input_dev;
    struct net_device   *real_dev;
    union {                         /* 指向各协议层 header 结构 */
        struct tcphdr  *th;   struct udphdr  *uh;   struct icmphdr *icmph;
        struct igmphdr *igmph; struct iphdr  *ipiph; struct ipv6hdr *ipv6h;
        unsigned char  *raw;
    } h;
    union {                         /* 网络层 header */
        struct iphdr   *iph;  struct ipv6hdr *ipv6h;
        struct arphdr  *arph; unsigned char  *raw;
    } nh;
    union { unsigned char *raw; } mac;   /* 链路层 header */
    struct dst_entry *dst;          /* 指向该 packet 的路由目的结构 */
    char              cb[40];        /* SKB control block，各协议层存私有信息 */
    unsigned int len, data_len, mac_len, csum;
    unsigned char local_df, cloned:1, nohdr:1;
    __u8          pkt_type, ip_summed;
    __u32         priority;
    unsigned short protocol;        /* 接收 packet 的协议 */
    ...
};

元数据字段逐个说清：

字段 含义
sk 关联的 struct sock，收包时据此找到目标 socket
stamp 收发时间戳，抓包工具用
dev / input_dev / real_dev 三个设备指针：当前设备、收包设备、真实设备
h / nh / mac 三个协议头指针，各层头部的定位锚点
dst 路由目的结构，告诉我们这个包会被如何路由到目的地
cb[40] 控制块，协议层存私有状态，TCP 用来存顺序号和重发状态
len / data_len 报文总长度 / 分片数据长度
mac_len MAC 头长度
csum 校验和。发送时开了 checksum offloading 就不设，接收时由 device 计算
local_df IPv4 在已分片后的再分片场景，比如 IPSEC
cloned 被 clone 时置位：成员变量各是自己的，数据是共享的
nohdr 支持 TSO 用
pkt_type 包类型（PACKET_HOST、PACKET_BROADCAST、PACKET_OTHERHOST 等）
ip_summed 网卡校验和能力的类型，NONE 表示不支持，HW 表示支持
priority QoS 优先级
protocol 收包时的链路层协议类型，就是 2.2 节里查 ptype_base 用的那个键

7.3 四个管理指针 #

指针 指向 会不会动
head 数据缓冲（PacketData）的内核首地址 不动
data 当前数据包的首地址 会动
tail 当前数据包的尾地址 会动
end 数据缓冲的内核尾地址 不动

数据包的大小在处理过程中会变，所以 data 和 tail 不断变化，而 head 和 end 不变。

text
 head                data                tail        end
  |                   |                   |           |
  v                   v                   v           v
+---+---+-----------+-------------------+-----------+---+
|   |   |  headroom |    packet data    |  tailroom |   |
+---+---+-----------+-------------------+-----------+---+

head 到 data 之间是 headroom，预留给各层往里加头部。tail 到 end 之间是 tailroom，留给追加数据。

7.4 三个协议头指针 #

除四个管理指针，sk_buff 还提供几个指针直接指向各层协议头。以 TCP 数据包为例：

指针 指向 TCP 包的实际情况
mac 数据帧的 MAC 头 以太网头，14 字节
nh 网络协议头 一般是 IP 协议头
h 传输层协议头 本例中是 TCP 协议头

给各层设好指针，方便了协议栈对数据包的处理。网络层不用自己算「IP 头在缓冲区里偏移多少」，直接 skb->nh.iph 就是；传输层直接 skb->h.th。这也解释了为什么收包时一层层往上走、指针一个个往前推，却没有任何内存拷贝。

7.5 主要操作 #

三个基本动作，全靠挪指针：

c
/* 1. 分配：len 是需要的线性数据区大小 */
skb = alloc_skb(len, GFP_KERNEL);

/* 2. 添加 payload：从 tail 往后扩 n 字节 */
skb_put(skb, user_data_len);

/* 3. 加/删协议头 */
skb_push(skb, header_len);   /* data 往前走，头部塞进 headroom */
skb_pull(skb, header_len);   /* data 往后走，剥掉一层头 */

对应到协议栈的动作：

时机 调什么 谁在调
建包 alloc_skb() 传输层
拷用户数据进来 skb_put() + copy_from_user 传输层
构造 TCP 头 skb_push() 传输层
构造 IP 头 skb_push() 网络层
收包解析完一层剥头 skb_pull() 网络层、传输层
释放 kfree_skb() 最后一环

skb_push 和 skb_pull 只改 data 一个字段。这就是「每层只调整指针、不拷贝数据」的物理含义。

7.6 队列与高效性 #

struct sock 有三个 sk_buff 队列（rx、tx、err），队列元素都是 skb。针对给定 socket，socket 缓冲区可以链接在一起，包含众多信息：到协议头的链接、时间戳、以及与这个报文相关的设备。

再往外一层，IP 栈和 NIC 驱动之间的 driver queue 也不含 packet data，只存 skb 指针。整条链路上，队列都是「指针队列」。

把整条链路的拷贝次数点一遍：

动作 数据拷贝
应用 write → 内核 1 次（copy_from_user）
传输层加头 0 次，skb_push 挪指针
网络层加头 0 次，skb_push 挪指针
链路层加头 0 次，拷 14 字节硬件头进 hh 缓存后挂上
交给驱动 0 次，指针传进 ring buffer
驱动 → 网卡 1 次（DMA，不占 CPU）
收包侧同理反向 1 次（驱动 DMA 到内核内存）+ 1 次（内核到用户态）

一次 TCP 发送，CPU 参与的拷贝就是两次。如果每层都拷贝一遍完整报文，四层就是四次，加上头部越来越大，开销翻几倍。

这就是 sk_buff 的全部价值：数据只有一份，各层持有的是同一块内存上不同的头指针。

八、协议栈的注册机制 #

第二章埋的「查表」伏笔，这里兑现。搞清楚四张表，就搞清了协议栈的扩展机制。

8.1 第一张表：packet_type（链路层 → 网络层） #

链路层收完帧，要决定交给哪个网络层协议。依据是帧头里的以太网类型，存在 skb->protocol。

表 内容 用途
ptype_base 哈希数组，按协议类型散列 正常协议分发
ptype_all 链表 所有协议都想看的包，抓包工具挂这里 
c
struct packet_type {
    __be16          type;       /* 以太网类型，ETH_P_ALL 表示全收 */
    struct net_device *dev;     /* 只收某个设备，NULL 表示全部 */
    int (*func)(struct sk_buff *, struct net_device *,
                struct packet_type *, struct net_device *);
    ...
};

void dev_add_pack(struct packet_type *pt);
void dev_remove_pack(struct packet_type *pt);

netif_receive_skb 是链路层接收数据报的最后一站。它根据注册在全局数组 ptype_all 和 ptype_base 里的网络层数据报类型，把数据报递交给不同的网络层协议接收函数。INET 域里主要是 ip_rcv 和 arp_rcv。

tcpdump、AF_PACKET 原始套接字就是往 ptype_all 上挂的。所以抓包能看到「所有」包，而不只是发给本机的。

8.2 第二张表：net_proto_family（应用层 → socket 层） #

建 socket 时传的 family 参数，决定用哪个地址簇的实现。

c
struct net_proto_family {
    int  family;                                    /* AF_INET / AF_INET6 / AF_PACKET ... */
    int (*create)(struct net *net, struct socket *sock, int protocol);
    struct module *owner;
};

int  sock_register(const struct net_proto_family *fam);
void sock_unregister(int family);

表是 net_families[]，按 family 索引。AF_INET 查到的是 inet_family_ops，其 create 指向 inet_create。

8.3 第三张表：proto_ops 与 proto #

socket 层是协议无关接口，提供一组通用函数支持各种不同协议。它能支持 TCP、UDP，也能支持 IP、裸以太网、SCTP。网络子系统通过一个定义了自己功能的特殊结构来了解可用协议。每个协议都维护一个名为 proto 的结构，在 include/net/sock.h 里。这个结构定义了从 socket 层到传输层可以执行的特定 socket 操作：如何创建一个 socket、如何用 socket 建立连接、如何关闭一个 socket。

这里要分清两个结构：

结构 定义什么 谁用
struct proto 传输层特有的方法，如 tcp_sendmsg、tcp_recvmsg 传输层内部
struct proto_ops 通用 socket 方法，如 inet_release、inet_stream_connect socket 层调用

proto 定义传输特有的方法，proto_ops 定义通用的 socket 方法。两层各看各的表。

8.4 第四张表：inetsw（协议数组） #

TCP 和 UDP 都是 inet 簇协议的一部分，它们在 net/ipv4/af_inet.c 的 inet_init 函数里初始化。

inet_init 用 proto_register 注册每个内嵌协议。这个函数在 net/core/sock.c 里定义。除了把协议加入活动协议列表，它还能按需分配一到多个 slab 缓存——为每个协议的对象做专用内存池。

各协议的 proto 接口按类型和协议映射到 inetsw_array，这个数组把内嵌协议与操作映射到一起。inet_init 里的 inet_register_protosw 把数组里每个协议初始化进 inetsw。

c
/* 简化示意 */
static struct inet_protosw inetsw_array[] = {
    { .type = SOCK_STREAM, .protocol = IPPROTO_TCP,
      .prot = &tcp_prot, .ops  = &inet_stream_ops },
    { .type = SOCK_DGRAM,  .protocol = IPPROTO_UDP,
      .prot = &udp_prot, .ops  = &inet_dgram_ops  },
    { .type = SOCK_RAW,    .protocol = IPPROTO_IP,
      .prot = &raw_prot, .ops  = &inet_dgram_ops  },
};

inet_init 还会初始化各个 inet 模块：ARP、ICMP、IP，以及 TCP 和 UDP 模块。

回想建 socket 时那句 socket(AF_INET, SOCK_STREAM, 0)：

参数 值 作用
family AF_INET 一个 Internet 地址簇，查 net_families[]
type SOCK_STREAM 流式 socket，查 inetsw[]
protocol 0 由 type 推导，得到 IPPROTO_TCP

三个参数全部对应到 inetsw_array 里的一行。

8.5 加一个新协议要做什么 #

把 SCTP 当例子。SCTP 通过 net/sctp/protocol.c 里的 sctp_init 加入 inetsw。

它做的事就三件：注册 proto、把手里的 proto_ops 和 proto 挂进 inetsw、让 inet_create 能按 family 找到它。IP 层完全不动，ip_local_deliver_finish 里照样按 iph->protocol 查 inet_protos[]，查到 SCTP 的 handler 就调。

四张表汇总：

注册表 键 值结构 注册函数 查表位置
ptype_base / ptype_all skb->protocol packet_type dev_add_pack() netif_receive_skb
net_families[] family net_proto_family sock_register() __sock_create
inetsw[] type + protocol inet_protosw inet_register_protosw() inet_create
inet_protos[] iph->protocol net_protocol inet_add_protocol() ip_local_deliver_finish

四张表，四个协议号字段，四种结构体。这就是「分层 + 注册」的全部实现。

加一个新协议不需要改上下层代码，只需注册。 这句话不是口号，是上面这四行的直接推论。

九、hook 点与拦截 #

查表机制解决「包该交给谁」。还有另一个需求：包在交付之前，能不能被第三方拦下来看一眼、改一改、或者直接扔掉。

这件事由 Netfilter 干。它在内核协议栈的关键路径上埋了 5 个钩子点（Hooks），允许注册自定义的钩子函数，对流经的网络数据包进行拦截、修改、或者直接丢弃。iptables、nftables、NAT 都建立在这套机制上。

9.1 五个钩子点 #

text
                       +-------------------+
                       |  本地主机 (Local) |
                       +---^-----------+---+
                           |           |
                    [LOCAL_IN]    [LOCAL_OUT]
                           |           |
                           |      +----v-----+
                           |      | 路由判决 |
                           |      +----+-----+
                           |           |
+------------+        +----+----+      |       +-------------+
| 网卡接收器  +=======>| 路由判决 +====>F====>| 网卡发送器  |
+------------+        +----+----+  [FORWARD]  +-----^-------+
                           |                   |
                     [PRE_ROUTING]       [POST_ROUTING]
钩子点 触发时机 典型用途
NF_INET_PRE_ROUTING 数据包刚从网卡收上来，还没做路由决策 DNAT（目的地址转换）
NF_INET_LOCAL_IN 路由决策后判定发给本机，送往用户空间协议栈之前 入站过滤
NF_INET_FORWARD 路由决策后判定不是给本机，要从另一个网口转发 转发过滤
NF_INET_LOCAL_OUT 本机用户态程序通过 socket 发包，刚出协议栈、做完路由决策 出站过滤、本机流量重定向
NF_INET_POST_ROUTING 转发包和本机发送包，送往网卡驱动之前 SNAT（源地址转换）

几个补充判断：

  • FORWARD 需要双网口并开启转发功能（ip_forward）才会触发。
  • LOCAL_OUT 是唯一「从本机发起」的钩子点，其余四个都出现在转发路径上。
  • 路由表由网络层维护。Linux 下用 ip route 或 route -v 看，Windows 下用 route print。

9.2 关键数据结构与注册接口 #

每一个注册的钩子都对应一个 struct nf_hook_ops 实例，定义在 <linux/netfilter.h>：

c
struct nf_hook_ops {
    struct list_head list;
    nf_hookfn        *hook;     /* 指向自定义的钩子函数 */
    struct module    *owner;    /* 填充 THIS_MODULE */
    void             *priv;
    u_int8_t          pf;       /* 协议族，如 PF_INET (IPv4) */
    unsigned int      hooknum;  /* 钩子点，如 NF_INET_PRE_ROUTING */
    int               priority; /* 优先级，数字越小优先级越高，如 NF_IP_PRI_FIRST */
};

int  nf_register_hook(struct nf_hook_ops *reg);      /* 注册单个 */
void nf_unregister_hook(struct nf_hook_ops *reg);    /* 注销单个 */

钩子回调函数原型叫 nf_hookfn。这个函数的定义随内核演进有变化。以 Linux 3.14 为例：

c
typedef unsigned int nf_hookfn(const struct nf_hook_ops *ops,
                               struct sk_buff *skb,
                               const struct net_device *in,
                               const struct net_device *out,
                               int (*okfn)(struct sk_buff *));

三个参数要分清：

  • skb：指向套接字缓冲区的指针，封装了数据包内容。
  • in：接收该数据包的网卡设备。
  • out：发送该数据包的网卡设备。

转发场景下 in 和 out 都有值。本机发出的包 in 为 NULL，本机接收的包 out 为 NULL。

9.3 返回值（Verdict） #

钩子函数必须返回一个决策值，告诉内核怎么处置这个包：

返回值 值 含义
NF_ACCEPT 1 放行，让数据包继续在协议栈中传递
NF_DROP 0 直接丢弃，释放 skb，后续协议栈不再处理
NF_STOLEN 2 强行接管。告诉协议栈「忘掉这个包」，内核不再释放它
NF_QUEUE 3 把包推入队列，交给用户空间排队处理
NF_REPEAT 4 再次调用当前钩子函数

NF_STOLEN 是最容易出事的一个。返回它意味着你自己负责释放 skb，忘了就是内存泄漏。NF_DROP 则是「内核帮你释放」。两者的责任划分完全相反。

9.4 收发两个方向都能插 #

这是本章的重点。钩子点在收包和发包两条路上都有：

方向 路径
接收 网卡 → PRE_ROUTING → 路由判决 → LOCAL_IN（本机）或 FORWARD（转发）→ POST_ROUTING → 网卡
发送 socket → LOCAL_OUT → 路由判决 → POST_ROUTING → 网卡

发送侧的钩子少，因为本机发出的包不经过 PRE_ROUTING 和 LOCAL_IN——那两个点是给「从外面进来的包」准备的。

挂哪个点取决于你要干什么：

目标 挂载点
拦所有入站包，改目的地址 PRE_ROUTING
拦发给本机的包，进应用层之前过滤 LOCAL_IN
拦过路流量 FORWARD
拦本机程序发出的包 LOCAL_OUT
统一在出网卡前改源地址、统计总量 POST_ROUTING

9.5 实战：报文解析过滤驱动 #

写一个内核钩子函数，在 PRE_ROUTING 处拦截源 IP 为 192.168.1.1 的 TCP 数据包，打印它的 MAC 地址、源/目的 IP、TCP 源/目的端口。

从 sk_buff 里剥各层首部指针，用内核给的辅助函数最稳：

c
#define MAC_FMT "%02x:%02x:%02x:%02x:%02x:%02x"
#define MAC_ARG(x) ((u8*)(x))[0],((u8*)(x))[1],((u8*)(x))[2], \
                   ((u8*)(x))[3],((u8*)(x))[4],((u8*)(x))[5]

void print_mac(struct ethhdr *eth)
{
    if (eth == NULL) return;
    if (eth->h_source)
        printk("SOURCE MAC: " MAC_FMT "\n", MAC_ARG(eth->h_source));
    if (eth->h_dest)
        printk("DEST MAC: " MAC_FMT "\n", MAC_ARG(eth->h_dest));
}

struct iphdr  *iph = ip_hdr(skb);     /* 获取 IP 头部 */
struct tcphdr *th  = tcp_hdr(skb);    /* 获取 TCP 头部 */

完整驱动：

c
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/netfilter.h>
#include <linux/netfilter_ipv4.h>
#include <linux/skbuff.h>
#include <linux/ip.h>
#include <linux/tcp.h>
#include <linux/if_ether.h>

unsigned int filter_hook(const struct nf_hook_ops *ops,
                         struct sk_buff *skb,
                         const struct net_device *in,
                         const struct net_device *out,
                         int (*okfn)(struct sk_buff *))
{
    struct iphdr *iph;
    struct tcphdr *th;
    unsigned char *p_src, *p_dst;

    if (!skb) return NF_ACCEPT;
    iph = ip_hdr(skb);
    if (!iph) return NF_ACCEPT;

    /* 只过滤 TCP 协议的数据包 */
    if (iph->protocol == IPPROTO_TCP) {
        th = tcp_hdr(skb);
        if (!th) return NF_ACCEPT;
        /* 匹配源 IP 192.168.1.1，即 0xc0a80101
         * 注意：网络字节序是 Big-Endian 格式 */
        if (ntohl(iph->saddr) == 0xc0a80101) {
            printk("Intercepted target packet:\n");
            /* 打印 TCP 端口（从网络字节序转换为主机字节序） */
            printk("  sport: %d -> dport: %d\n",
                   ntohs(th->source), ntohs(th->dest));
            /* 打印源地址 */
            p_src = (unsigned char *)(&(iph->saddr));
            printk("  saddr: %d.%d.%d.%d\n",
                   p_src[0], p_src[1], p_src[2], p_src[3]);
            /* 打印目的地址 */
            p_dst = (unsigned char *)(&(iph->daddr));
            printk("  daddr: %d.%d.%d.%d\n",
                   p_dst[0], p_dst[1], p_dst[2], p_dst[3]);
            /* 需要实现包过滤拦截，把下面改写成 return NF_DROP; 即可 */
        }
    }
    return NF_ACCEPT;
}

static struct nf_hook_ops pkt_filter = {
    .hook     = filter_hook,
    .owner    = THIS_MODULE,
    .pf       = PF_INET,                  /* IPv4 协议族 */
    .hooknum  = NF_INET_PRE_ROUTING,      /* 挂载在路由前钩子点 */
    .priority = NF_IP_PRI_FIRST,          /* 最高优先级 */
};

static int __init filter_init(void)
{
    printk("Registering filter hook...\n");
    return nf_register_hook(&pkt_filter);
}

static void __exit filter_exit(void)
{
    printk("Unregistering filter hook...\n");
    nf_unregister_hook(&pkt_filter);
}

module_init(filter_init);
module_exit(filter_exit);
MODULE_LICENSE("GPL");

代码里几个点值得单独盯：

  • ip_hdr(skb) 不是 skb->nh.iph 的裸访问，它带类型检查和偏移修正。不同内核版本对 nh 的封装不一样，用辅助函数才可移植。
  • ntohl 不能省。iph->saddr 是网络字节序，直接和 0xc0a80101 比，在小端机器上比的是反过来的地址。
  • 打印 IP 用 (unsigned char *)& 取地址，而不是直接拆 u32。前者按内存字节序读，后者会搞错字节顺序。
  • nf_register_hook 的返回值必须透传。注册失败要返回错误码，否则模块加载成功但钩子没挂上。

新内核里 nf_register_hook 被 nf_register_net_hook 取代，原型多了 struct net * 参数，nf_hookfn 也多了一个 struct nf_hook_state *。迁移时按 nf_hook_ops 的 pf/hooknum 字段对照改。

9.6 高阶扩展 #

真实项目里（简易 Web 重定向、软网关防火墙），这套东西还能往下推。

扩展方向 做法
动态控制 建一个字符设备，用户态通过 ioctl() 下发过滤规则（黑白名单 IP、重定向目标地址）到内核
HTTP 重定向 在 PRE_ROUTING 拦 80 端口流量，改 TCP 包的目的 IP 和目的端口，重算校验和，把请求引到指定 Web 服务器

改包有坑：改了 IP 地址或端口，IP 头校验和与 TCP 校验和都得重算。TCP 校验和覆盖伪首部（含 IP 地址），所以动 IP 地址会连带影响 TCP 校验和。少算一处，包到了对端被静默丢掉，抓包只能看到「发出去了但没回音」。

hook 的执行顺序由 priority 决定，数字小的先跑。同一点上挂多个钩子时，前一个返回 NF_ACCEPT 才轮到下一个，返回 NF_DROP 后面全不看。iptables 的各个表就是在同一点上用不同 priority 排出来的。

十、一次收发的完整路径 #

前面各层拆完了，这里拼回去。发送是自上而下，接收是自下而上。

10.1 发送：自上而下 #

text
应用 write/send → sock_sendmsg → _sock_sendmsg
  → tcp_sendmsg / udp_sendmsg          传输层：建 skb、拷数据、加 TCP 头、算校验和与序号
    → ip_queue_xmit / ip_append_data   网络层：查 dst、填 IP 头、按需分片
      → ip_finish_output2              hh 缓存命中？否则 neigh_resolve_output 走 ARP
        → dev_queue_xmit               链路层
          → dev->hard_start_xmit → dm9000_xmit    驱动 → DMA + 前导符/IFG/CRC   物理层
            → 网卡发完中断，释放 skb

每一层的动作都能用一句话概括：加自己的头、填自己的字段、把 skb 往下递。

10.2 接收：自下而上 #

text
网卡收到帧 → DMA 送到内核内存 rx_ring → 触发中断
  → 中断处理：分配 skb、从 I/O 端口拷数据、设 skb->protocol
     → 发软中断 NET_RX_SOFTIRQ（netif_rx 或 NAPI 的 netif_rx_schedule）
        → net_rx_action                       软中断
            → netif_receive_skb               链路层最后一站
                查 ptype_base/ptype_all，按 skb->protocol 分发
                → ip_rcv                      网络层入口
                    校验和检查、IP defragment
                    → PRE_ROUTING hook
                        → ip_rcv_finish
                            → ip_route_input 查路由
                    ├─ 本机 → ip_local_deliver → 再 defragment → ip_local_deliver_finish
                    │       按 iph->protocol 查表 → tcp_v4_rcv / udp_rcv / icmp_rcv / igmp_rcv
                    │       → __tcp_v4_lookup 找 socket（找不到就丢）→ tcp_prequeue 进队列
                    │       → 唤醒 socket → tcp_recvmsg → 拷到 user buffer
                    └─ 转发 → 处理 TTL → dst_input
                                （1）Netfilter Hook  （2）IP 分片  （3）dev_queue_xmit

接收路径比发送长，多出的部分全在「决定这个包是谁的」这件事上：先查到本机还是转发，再查哪个传输层协议，再查哪个 socket。

10.3 各层入口函数 #

层 发送入口 接收入口
应用层 sys_sendto / sys_write sys_recvfrom / sys_read
套接字层 sock_sendmsg sock_recvmsg → inet_recvmsg
传输层 tcp_sendmsg / udp_sendmsg tcp_v4_rcv / udp_rcv
网络层 ip_queue_xmit / ip_append_data ip_rcv → ip_rcv_finish

10.4 两个方向上的 hook 插入点 #

方向 hook 出现的位置
发送 LOCAL_OUT（ip_output 附近）、POST_ROUTING（ip_finish_output 附近）
接收 PRE_ROUTING（ip_rcv 之后）、LOCAL_IN（ip_local_deliver 之前）
转发 PRE_ROUTING → FORWARD（ip_forward 附近）→ POST_ROUTING

实际代码里这些点由 NF_HOOK() 宏插入，宏展开后就是「跑完 hook 再调 okfn」。okfn 传的是这一层原本要调的下一个函数。这也是 nf_hookfn 最后一个参数叫 okfn 的原因。

10.5 skb 的生命周期 #

发送侧：alloc_skb() 建包 → skb_put() 拷数据 → 三层各自 skb_push() 加头 → 指针进 ring buffer → DMA 发出去 → 发送完成中断里 kfree_skb()。接收侧反过来：中断里 alloc_skb，头部指针一路 skb_pull 剥掉，最后一环释放。谁最后放手，谁负责 kfree_skb。 记这一条，泄漏和重复释放的 bug 少一半。

十二、易错点速查 #

现象 根因 排查方向
包到了网卡，应用收不到 tcp_v4_rcv 里 lookup 不到 socket 端口没监听、四元组对不上、socket 状态不对
抓包看到包发出去了，对端没回音 改了包没重算校验和 IP 头校验和、TCP 校验和（含伪首部）都要重算
模块加载成功，过滤不生效 nf_register_hook 返回值没检查，或 hooknum/pf 填错 打印注册返回值，核对 PF_INET 与 hooknum
传大包时看到大量小包 MTU 小于应用写入量，触发 IP 分片 看 ip_fragment 路径，考虑 GSO/TSO
内核 Oops 在 ip_hdr 附近 在错误的 hook 点取头指针，或 skb 非线性 用 skb_header_pointer，确认线性区
返回 NF_STOLEN 后内存持续增长 自己没释放 skb NF_STOLEN 由调用方释放，NF_DROP 由内核释放
想给新协议做支持，改了 ip_local_deliver_finish 用了硬编码而不是注册 改走 inet_add_protocol()
改了 skb->data 后上层读到乱数据 直接移动了 data 而没同步 len 一律用 skb_push/skb_pull
新内核编译旧驱动报错 nf_register_hook / nf_hookfn 原型变了 换 nf_register_net_hook，补 nf_hook_state 参数
双网口设备上 FORWARD 不触发 ip_forward 未开 sysctl net.ipv4.ip_forward

三句收尾：结构上，协议栈是分层 + 注册，层负责边界、表负责接线，加协议只注册不改代码；数据上，全栈传递的是 sk_buff 指针，每层只挪指针不加拷贝；路径上，发送自上而下，接收自下而上，hook 在两侧都能插。
