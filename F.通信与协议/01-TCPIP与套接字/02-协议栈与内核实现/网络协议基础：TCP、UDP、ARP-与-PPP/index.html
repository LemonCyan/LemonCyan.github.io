这篇只讲四件事：TCP 怎么保证可靠，UDP 为什么不保证，ARP 怎么把 IP 换成 MAC，PPP 怎么在点对点链路上封装报文。

不碰的：内核收发代码路径（见同目录「数据收发路径」）、协议栈整体架构（见「协议栈架构」）、Netlink（见「Netlink」）、抓包实操（见「Wireshark 实战」）、链路层与网桥（见「链路层与网桥」）、二层桥转发、VLAN 原理、VLAN 源码、路由表、策略路由、NAT、组播、Netfilter——这 13 篇各自成文，本篇不重复。

要立的坐标：四个协议覆盖了从链路层到传输层的四种典型需求。ARP 解决「知道 IP 怎么找到 MAC」，这是跨层映射；PPP 解决「点对点链路怎么封装」，这是链路层；TCP 和 UDP 解决「端到端怎么传」，这是传输层。

读完能判断：一个需求该落到哪一层，该挑哪个协议，排障时先看哪张表。

一、四个协议各在哪一层 #

从以太网和 IP 说起 #

最底层是以太网协议（Ethernet），它规定电子信号怎么组成数据包，解决子网内部的点对点通信。一个局域网里，两台机器靠 MAC 地址互相找到对方。

以太网解决不了多个局域网互通。这件事交给 IP 协议。IP 定义自己的地址规则，也就是 IP 地址，实现路由功能：某个局域网的 A 主机，能向另一个局域网的 B 主机发消息。

路由的原理不复杂。路由器背后一排网口，要插多根网线。路由器内部一张路由表，写明 A 段 IP 地址走出口一，B 段地址走出口二。靠这套指路牌，数据包被一跳一跳转出去。本机也有路由表，注明不同目的 IP 的包该从哪个网口（interface）出去。

IP 只是地址协议，不保证包的完整。路由器缓存满了，新进来的包直接丢掉。丢了哪一个、怎么补发，IP 不管。这是 TCP 的活。

分层位置 #

层次 代表协议 寻址单位 解决什么 本篇章节
应用层 HTTP、DNS URL、域名 业务语义 十一
传输层 TCP、UDP 端口 端到端传输、复用与分用 二～五
网络层 IP、ICMP IP 地址 跨网段寻址与逐跳转发 一
链路层 以太网、PPP MAC 地址、链路标识 一跳之内怎么把帧发出去 八、九
物理层 双绞线、光纤 比特 电信号与光信号 不讲

ARP 的位置比较特别。OSI 七层里，TCP 在第 4 层传输层，IP 在第 3 层网络层，ARP 落在第 2 层数据链路层。它长在链路层，干的却是把 IP 地址映射成 MAC 地址。高层对低层有强依赖，所以 TCP 建连之前，得先完成 ARP 的请求和应答。

认为 ARP 只适用于局域网，这个判断站得住。ARP 请求是广播，广播不出网段，跨网段只能问网关。

封装与 MSS：1460 从哪来 #

以太网帧大小固定，最初 1518 字节，后来增加到 1522 字节。其中 1500 字节是负载（payload），22 字节是头信息（head）。这 1500 就是常说的 MTU。

IP 包装在以太网帧的负载里，自己也有头，最少 20 字节。所以 IP 包的负载最多 1480 字节。

TCP 包装在 IP 包的负载里，头最少也要 20 字节。TCP 包的最大负载 = 1480 - 20 = 1460 字节，这个数就是 MSS。IP 和 TCP 往往带额外选项头，实际负载落在 1400 字节左右。

text
Ethernet frame (1522 B total)
+---------+---------+---------+------------------+
| ETH hdr | IP hdr  | TCP hdr |     payload      |
|  14 B   | >=20 B  | >=20 B  |     ~1400 B      |
+---------+---------+---------+------------------+
|<------------------ 1500 B MTU ----------------->|

一条 1500 字节的信息，得拆成两个 TCP 包。HTTP/2 的一大改进就是压缩 HTTP 头信息，让一个请求塞进一个 TCP 包，不用分成多个，速度就上来了。

需求对上协议 #

四层里各有一个典型问题，四个协议正好对上：

你手上的问题 落在哪层 交给谁 核心机制
知道对方 IP，怎么把帧发到它网卡上 链路层与网络层之间 ARP 广播问、单播答、结果进缓存
一根串行线上怎么跑多种上层报文 链路层 PPP 定界、协议域、LCP 协商
端到端要字节流、顺序、不丢 传输层 TCP 序号、确认、重传、窗口
端到端要短报文、低延迟、不重传 传输层 UDP 加个端口就走

二、TCP：面向连接 #

「连接」连的是什么 #

TCP 提供的是面向连接的服务，对应 socket 类型 SOCK_STREAM。收发数据之前必须先建立连接；连接是双向的，任何一方都能收发；协议本身带保障机制，保证可靠、有序，每个包按发送顺序到达接收方。

连接不是一根物理线。两端内核里各存一份状态，用四元组标识：源 IP、源端口、目的 IP、目的端口。四元组相同，就是同一条连接。两台机器之间可以并存成千上万条连接，全靠这四元组区分。

面向连接的代价在建立和释放这两个动作上。UDP 没有这两个动作，所以它快。

三次握手 #

text
Client                                Server
  |  SYN  seq=x            --------->  |   LISTEN -> SYN_RCVD
  |  <---------  SYN+ACK  seq=y,ack=x+1|   分配接收缓冲、记下对方能力
  |  ACK  ack=y+1          --------->  |   ESTABLISHED
  |  ESTABLISHED                        |

三次要解决的问题：

  1. 双方都确认自己的发送能力和接收能力正常。
  2. 双方交换并同步初始序号（ISN）。
  3. 双方协商 MSS、窗口缩放、SACK 这类选项。

初始序号取随机值，不取 0。原因有两个：旧连接的迟到报文不会串进新连接；外人不好猜下一个序号，注入门槛高一些。

两次握手不够。服务端收到 SYN 就建连，此时它并不知道客户端收没收到自己的 SYN+ACK，历史重复 SYN 会让服务端攒一堆无效连接。

四次挥手 #

text
Client                                Server
  |  FIN                    --------->  |   CLOSE_WAIT
  |  <---------------------  ACK        |
  |                                     |   应用处理完，发 FIN
  |  <---------------------  FIN        |   LAST_ACK
  |  ACK                    --------->  |   CLOSED
  |  TIME_WAIT (2*MSL) -> CLOSED        |

TCP 是全双工，两个方向各关一次，所以是四次。一方发完 FIN 只是说自己不发数据了，还能继续收，这叫半关闭。

主动关闭的一方最后进入 TIME_WAIT，等 2 倍 MSL 才真正关掉。两个作用：最后的 ACK 丢了，对方重发的 FIN 还能被接住并重发 ACK；这条连接的迷路报文在网络里自然消亡，不会污染下一个用同样四元组的新连接。

TCP 头里跟本篇有关的字段 #

字段 长度 干什么
源端口、目的端口 各 2 字节 找到两端的应用进程，实现复用与分用
序号 SEQ 4 字节 本段第一个字节在字节流里的位置
确认号 ACK 4 字节 期待收到的下一个字节编号
数据偏移 4 bit 头有多长，用来定位负载
标志位 6 bit SYN、ACK、FIN、RST、PSH、URG
窗口 2 字节 本方接收窗口的剩余容量，告诉对方还能发多少
校验和 2 字节 覆盖伪首部 + TCP 头 + 数据
选项 可变 MSS、窗口缩放、SACK、时间戳

最小头 20 字节，带选项会变长。这 20 字节就是上面算 MSS 时减掉的那 20。

数据被切成段 #

一个段装 1400 字节左右，发大量数据就必须切成多个段。一个 10MB 的文件，按 1400 字节一段算，要发 7100 多个包。

发送时 TCP 给每个字节编号，不是给每个包编号——序号落在字节上，所以「包」这个概念在 TCP 里其实是段，重组时按字节位置拼。这就是面向字节流和面向报文的分水岭：TCP 没有报文边界，UDP 有。

三、TCP 的可靠性从哪来 #

丢包是常态。带宽小、路由器过热、缓存溢出，随便一个都能让包消失。线路不好时，发得越快丢得越多。理想状态是在线路允许的前提下跑到最高速率，可对方的线路能跑多快，发之前并不知道。答案只能慢慢试。

TCP 的做法是四样东西配合：序号、确认、重传、滑动窗口。这四件缺一个，可靠传输都做不出来，缺的环节和后果摆在这里：

机制 干什么 缺了会怎样
序号 给字节流编号，标出每一段在文件里的位置 收到一堆段，拼不出原文顺序
确认 接收方回报「我期待的下一个编号」 发送方不知道对端收没收到，只能一直发
重传 判定丢包后补发那一段 知道丢了也不补，数据永远缺一块
滑动窗口 一次允许多少未确认数据在途 只能一发一等，退化成停等协议，带宽吃不满

除了这四样，还有一个常被漏掉的环节：超时重传要等多久。等多久由 RTO 决定，RTO 靠 RTT 估算。这一段放到最后单独讲。

序号 #

发送时 TCP 给每个包编号，叫 sequence number，简称 SEQ，接收方靠它按顺序还原。万一丢包，也知道丢的是哪一个。

第一个包的编号是随机数。为了讲清楚，这里当成 1 号包。假定这个包的负载是 100 字节，下一个包的编号就是 101。

每个数据包都能拿到两个编号：自身编号，以及下一个包的编号。接收方由此知道该按什么顺序还原原始文件。抓包看到的当前包 SEQ 是 45943，下一个包的 SEQ 是 46183，两者相减，就知道这个包的负载是 240 字节。

编号落在字节上，包只是承载它，所以确认号能精确到「我要第 46183 号字节」，中间少一个字节都能被发现。

确认 #

接收方每收到 TCP 数据包，就回一个确认消息。确认的英文是 acknowledgement，简称 ACK。这里说「每收到就回」是语义，内核实际用延迟确认把多个 ACK 合并，减少包数。

ACK 携带两个信息：

  1. 期待要收到的下一个数据包的编号。
  2. 接收方的接收窗口的剩余容量。

发送方拿到这两个信息，再加上自己已经发出的最新编号，就能推测出接收方的接收速度，从而调整发送速率。这就是「发送窗口」，大小可变。

TCP 通信是双向的，所以双方都要发 ACK，两方的窗口大小往往不一样。ACK 只是几个字段，一般跟数据合并在同一个包里发，不单独占一个包。

四步通信的例子：

text
A -> B : seq=1,   len=100        B 回 ACK: ack=101
B -> A : seq=1,   len=200        A 回 ACK: ack=201
A -> B : seq=101, len=...        B 回 ACK: ack=101+len
B -> A : seq=201, len=...        A 回 ACK: ack=201+len

第一次 A 发 1 号包，长度 100，B 的 ACK 编号就是 101；A 下一段从 101 开始。反方向同理，B 发 1 号包长度 200，A 回 ACK 201。

重传 #

每一个包都带着下一个包的编号。下一个包没收到，ACK 的编号就不会变。

举例：现在收到 4 号包，没收到 5 号包，ACK 就记录「期待 5 号」。过一段时间 5 号到了，下一轮 ACK 更新编号。5 号一直没到，但 6 号、7 号陆续到了，ACK 里的编号照样显示 5，一个字都不动。这时候发送方会收到大量重复内容的 ACK。

发送方发现两种信号就判定丢包，重发那一段：

  • 收到连续多个重复 ACK（常见实现是 3 个），走快速重传，不必等计时器。
  • 超时了还没收到任何 ACK，走超时重传。
text
Host A                          Host B
  |  seq=100  ------------------>  |  收到
  |  seq=200  ----- X 丢失
  |  seq=300  ------------------>  |  ACK 200
  |  seq=400  ------------------>  |  ACK 200  (重复 1)
  |                               |  ACK 200  (重复 2)
  |  <--------------- ACK 200 ---  |  ACK 200  (重复 3) -> 触发快速重传
  |  seq=200  ------------------>  |

滑动窗口与慢启动 #

有了窗口，发送方能在没收到确认前连续发多个段。窗口越大，在途数据越多，吞吐越高；窗口太大，接收方缓冲装不下，中间链路也会堵。

实际能发多少，取两个值的小者：拥塞窗口 cwnd 和接收窗口 rwnd。rwnd 来自对端 ACK 里报的剩余容量，cwnd 由本机根据丢包情况自己算。

TCP 为了兼顾效率和可靠性，设计了慢启动（slow start）：开始发得慢，然后按丢包情况调整速率。不丢包就加快，丢包就降速。

Linux 内核里有个常量 TCP_INIT_CWND，刚开始通信时发送方一次发 10 个数据包，即发送窗口为 10，然后停下来等确认，再继续。即使带宽很大、线路很好，TCP 也从 10 个包开始试，过一段时间才爬到最高速率。这就是慢启动这四个字的由来。

窗口的增长分两段：慢启动阶段每收到一个 ACK 把 cwnd 加一个 MSS，窗口按指数涨；涨到慢启动阈值 ssthresh 后转拥塞避免，每个 RTT 只加一个 MSS，线性涨。碰上丢包就把 ssthresh 砍半，cwnd 回落，重新爬。

RTO：超时到底等多久 #

超时重传有个前提没解决：等多久算超时。

拍一个固定值不行。固定 1 秒，在 RTT 只有 10ms 的机房里，丢一个包要白等 1 秒；固定 100ms，在 RTT 500ms 的卫星链路上，包还在路上就被判死，重传的全是废包，链路越堵越糟。

所以 RTO 必须跟着实测的 RTT 走。内核做三件事：

  1. 每个被确认的段采一个 RTT 样本 r。
  2. 维护平滑 RTT（srtt）和 RTT 偏差（rttvar）。
  3. 用 srtt 加若干倍偏差算出 RTO。
text
srtt   = (7 * srtt + r) / 8
rttvar = (3 * rttvar + |srtt - r|) / 4
RTO    = srtt + max(4 * rttvar, 200ms)

偏差这一项是 Jacobson/Karels 那套算法的核心。RTT 抖动大的链路，光看平均值不够，必须把波动算进去，否则一半的重传都是误判。Linux 把偏差下限压在 200ms，意思是 RTO 不小于 200ms，避免对短 RTT 连接过度敏感。

上限是 120 秒。连续超时时 RTO 翻倍退避，1、2、4、8 秒往上叠，顶到 120 秒为止，避免网络已经瘫了还继续灌包。

这就是可靠性链条上最容易漏的一环：序号、确认、重传、窗口四个机制都到位，RTO 拍错，整条链照样不成立。等太短，网络里全是重复包；等太长，丢包恢复慢到应用层超时。

四、UDP：无连接 #

UDP 对应 socket 类型 SOCK_DGRAM，全称 User Datagram Protocol。它无连接、不可靠：双方发完数据，不知道对方收没收到，也不知道收得对不对。任何一方建好 socket 就能 sendto 发、recvfrom 收，根本不关心对方在不在、发没发。

它的特点是快。TCP 要三次握手才开传，UDP 没有这套。

8 字节的头 #

字段 长度 干什么
源端口 2 字节 对方的回包往哪送，可以不填
目的端口 2 字节 交付给哪个进程
长度 2 字节 头 + 数据的总长，最小值 8
校验和 2 字节 覆盖伪首部 + UDP 头 + 数据，IPv4 下可置 0 关闭

头部固定 8 字节，没有选项，没有序号，没有确认号，没有窗口。TCP 那套机制它一个都没有，所以它也做不了那些事。

校验和是端到端的，只查错，不纠错。IPv4 里可以关掉，IPv6 里强制打开。

报文边界 #

UDP 是数据报模式，一次 sendto 对应一次 recvfrom，边界保留。发 100 字节就收到 100 字节，不会像 TCP 那样把两次发送粘成一次读。

代价是缓冲区给小了会截断。TCP 是字节流，读多读少自己拼；UDP 一次读不完，剩下的部分直接丢弃，不给你第二次机会。

这也是 UDP 程序结构简单的原因：不用维护收发缓冲的拼接逻辑，来一个报文处理一个报文。

UDP 编程 #

UDP 服务端和客户端都比 TCP 少几步。服务端不需要 listen 和 accept，因为没有连接可等。

服务端：

  1. 创建 socket，用 socket()。
  2. 设置 socket 属性，用 setsockopt()，可选。
  3. 绑定 IP 地址和端口，用 bind()。
  4. 循环接收数据，用 recvfrom()。
  5. 关闭网络连接。

客户端：

  1. 创建 socket，用 socket()。
  2. 设置 socket 属性，用 setsockopt()，可选。
  3. 绑定 IP 地址和端口，用 bind()，可选。
  4. 设置对方的 IP 地址和端口。
  5. 发送数据，用 sendto()。
  6. 关闭网络连接。
c
#include <sys/socket.h>
#include <netinet/in.h>
#include <string.h>

int fd = socket(AF_INET, SOCK_DGRAM, 0);      /* 关键在 SOCK_DGRAM */

struct sockaddr_in addr;
memset(&addr, 0, sizeof(addr));
addr.sin_family      = AF_INET;
addr.sin_port        = htons(9000);
addr.sin_addr.s_addr = htonl(INADDR_ANY);
bind(fd, (struct sockaddr *)&addr, sizeof(addr));

char buf[1500];
struct sockaddr_in peer;
socklen_t plen = sizeof(peer);

ssize_t n = recvfrom(fd, buf, sizeof(buf), 0,
                     (struct sockaddr *)&peer, &plen);
if (n > 0)
    sendto(fd, buf, n, 0, (struct sockaddr *)&peer, plen);

两个细节容易踩：

  • 地址信息在 sendto/recvfrom 里每次都要给。TCP 的地址在 connect/accept 时就定死了，UDP 没有那个时机。
  • shutdown 函数对 UDP 无效。它没有半关闭的概念，关就是 close。

广播和组播只能靠 UDP #

一个包要发给网段里所有主机（广播），或者发给一组订阅者（组播），TCP 做不到——TCP 是一对一的连接，目标必须是一个确定的四元组。这类需求只有 UDP 能承载。

细节展开在「组播」篇，这里只记住结论：UDP 保留了这个能力，也把可靠性责任推给了应用。

五、TCP 与 UDP 的取舍 #

两者都在传输层，都在 IP 之上，都用端口区分应用。除此之外，设计取向几乎相反。

主要区别 #

维度 TCP UDP
连接 面向连接，先握手 无连接，直接发
资源占用 每条连接要维护状态、缓冲、定时器，占用较多 几乎不占状态，占用少
程序结构 复杂，要处理连接、断连、重传 简单，一个报文一个处理
数据模式 字节流（SOCK_STREAM） 数据报（SOCK_DGRAM）
正确性 校验、确认、重传，保证数据正确 只做校验和查错，丢包不补
顺序 保证按发送顺序交付 不保证顺序
速度 握手、确认、拥塞控制都带来开销 快，没有这些开销
头部 最少 20 字节，带选项更长 固定 8 字节
流量与拥塞控制 有，窗口 + 慢启动 + 拥塞避免 没有，发多快由应用自己定
传输对象 只能一对一 一对一、一对多、广播、组播

UDP 适合什么场景 #

五条判断标准，对上越多越该用 UDP：

  1. 面向数据报方式，应用自己按报文处理。
  2. 网络数据大多是短消息，一问一答，连接开销比数据本身还大。
  3. 有大量客户端，服务端不想为每个客户端维护连接状态。
  4. 对数据安全性没有特殊要求，丢一两个报文不影响业务。
  5. 网络负担很重，但对响应速度要求高，宁肯丢也不愿等。

DNS 查询、SNMP、日志上报、音视频实时流、游戏同步，都是这套逻辑。丢了就丢了，重发一个过期数据没意义。

TCP 编程步骤 #

服务端一般步骤：

  1. 创建 socket，用 socket()。
  2. 设置 socket 属性，用 setsockopt()，可选。
  3. 绑定 IP 地址、端口到 socket，用 bind()。
  4. 开启监听，用 listen()。
  5. 接收客户端上来的连接，用 accept()。
  6. 收发数据，用 send() 和 recv()，或 read() 和 write()。
  7. 关闭网络连接。
  8. 关闭监听。

客户端一般步骤：

  1. 创建 socket，用 socket()。
  2. 设置 socket 属性，用 setsockopt()，可选。
  3. 绑定 IP 地址、端口，用 bind()，可选。
  4. 设置要连接的对方 IP 和端口。
  5. 连接服务器，用 connect()。
  6. 收发数据，用 send() 和 recv()，或 read() 和 write()。
  7. 关闭网络连接。
c
int lfd = socket(AF_INET, SOCK_STREAM, 0);    /* 关键在 SOCK_STREAM */
bind(lfd, (struct sockaddr *)&addr, sizeof(addr));
listen(lfd, 128);

int cfd = accept(lfd, NULL, NULL);            /* 没有连接就阻塞在这里 */
char buf[4096];
ssize_t n = read(cfd, buf, sizeof(buf));      /* 字节流，读多少算多少 */
write(cfd, buf, n);

对照着看，两边的差异就落在这几处：

对比项 TCP UDP
socket() 第二个参数 SOCK_STREAM SOCK_DGRAM
listen / accept 需要 不需要
收发函数 send / recv，或 read / write sendto / recvfrom
地址信息确定时机 connect / accept 时确定 每次 sendto / recvfrom 都要指定
shutdown 可用，支持半关闭 无效
连接数 每连接一个 fd 一个 fd 收所有对端

怎么选 #

先问一句：丢一个包，业务能不能自己兜住？

能兜住，而且对延迟敏感，用 UDP。应用层自己加序号、加超时、加去重，比在内核里堆一层重传更贴合业务——实时流宁可丢一帧，也不要为了补一帧卡住后面三十帧。

兜不住，或者不想自己写重传逻辑，用 TCP。文件传输、HTTP、数据库连接都在这条线上。

TCP 提供可靠的通信传输，UDP 把广播和细节控制交给应用。这句话是两者的分工总结，也是选型时唯一要判断的事：可靠性放在内核，还是放在你的代码里。

六、ARP：IP 到 MAC 的映射 #

两个地址，两套语义 #

讲 ARP 之前先把两个「地址」分清。

第一个是 TCP/IP 的 32 bit IP 地址。它是逻辑地址，可以配、可以改、可以借。只知道主机的 IP 地址，内核没法把数据帧发出去。

第二个是网络接口的硬件地址，48 bit，用来标识不同的以太网或令牌环网络接口。这是物理地址，烧在网卡上，在硬件层次上交换数据必须有正确的接口地址，内核必须知道目的端的硬件地址才能发数据。

在以太网里，一台主机要把数据帧发到同一局域网上的另一台主机，设备驱动程序必须知道以太网地址。而我们手里只有 IP。ARP 就是干这件事的：把 IP 地址映射成以太网地址。一般说以太网地址，就是指 MAC 地址。

一句话概括：IP 是逻辑地址，负责「送到哪台机器」；MAC 是物理地址，负责「这一跳怎么送到那张网卡」。跨层映射这件事，只有 ARP 在做。

ARP 分组格式 #

ARP 报文直接封在以太网帧里，帧类型字段为 0x0806。报文结构不长：

序号 字段 长度 取值与含义
1 目的以太网地址 6 字节 请求时全 1，即广播地址；应答时填对端 MAC
2 源以太网地址 6 字节 发送 ARP 请求一方的 MAC
3 帧类型 2 字节 ARP 请求和应答都是 0x0806
4 硬件地址类型 2 字节 以太网为 1
5 协议地址类型 2 字节 映射 IPv4 时为 0x0800
6 硬件地址长度 1 字节 MAC 占 6 字节，填 6
7 协议地址长度 1 字节 IP 占 4 字节，填 4
8 操作类型 Opcode 2 字节 1 请求、2 应答、3 RARP 请求、4 RARP 应答
9 发送端硬件地址 6 字节 与本字段 2 相同
10 发送端 IP 地址 4 字节 发起方 IP
11 目的端硬件地址 6 字节 请求时未知，全 0 填充
12 目的端 IP 地址 4 字节 要解析的目标 IP 
c
/* Linux 暴露的 ARP 头，见 <linux/if_arp.h> */
struct arphdr {
    __be16        ar_hrd;   /* 硬件类型，以太网为 1        */
    __be16        ar_pro;   /* 协议类型，IPv4 为 0x0800    */
    unsigned char ar_hln;   /* 硬件地址长度，6             */
    unsigned char ar_pln;   /* 协议地址长度，4             */
    __be16        ar_op;    /* 操作码，1 请求 / 2 应答     */
    /* 后面依次是发送端 MAC、发送端 IP、目的端 MAC、目的端 IP */
};

抓包时对照这 12 个字段看，请求和应答的差别一眼就能认出来。

怎么区分请求和应答 #

ARP 请求分组里，目的 MAC 地址未知，用全 0 填充，以太网目的地址设成全 1 广播。应答分组把请求里的源和目的地址对调，Opcode 从 1 变成 2，其余字段不变。

地址字段和其他字段都没有区分能力，只能靠 Opcode：1 是请求，2 是应答，3 和 4 是 RARP。RARP 是反过来的映射，MAC 找 IP，今天基本被 DHCP 取代。

七、ARP 的过程与缓存 #

一次 TCP 建连背后的 ARP #

应用接受用户提交的数据，触发 TCP 建立连接。TCP 的第一个 SYN 报文通过 connect 函数到达 IP 层，IP 层先查路由表，然后分两条路走。

目的 IP 和自己同网段：

  • ARP 缓存表里有目的 IP 对应的 MAC，直接调网络接口的 send 函数，参数是 IP Packet 和目的 MAC。网卡完成 Ethernet Header + IP + CRC 的封装，发出去。
  • 缓存表里没有，IP 层把 TCP 的 SYN 先缓存住，发 ARP 广播请求目的 IP 的 MAC。收到应答后，把「目的 IP - MAC」这一对写进缓存表，再完成 SYN 的 IP 封装，调 send 发出去。

目的 IP 和自己不同网段：

  • 包要交给默认网关，得先知道网关的 MAC。缓存表里有网关的 MAC，直接调 send，参数换成 IP Packet 和网关 MAC，封装后发出。
  • 缓存表里没有网关 MAC，同样先把 SYN 缓存住，发 ARP 广播请求网关的 MAC。收到应答后写入缓存表，封装 SYN，调 send 发出。

四条路径归到一张表里：

目的位置 缓存状态 ARP 问谁 帧的目的 MAC 填谁
同网段 命中 不问，直接用表项 目的主机
同网段 未命中 问目的主机（广播） 目的主机
跨网段 命中 不问，直接用表项 默认网关
跨网段 未命中 问默认网关（广播） 默认网关

这张表是本篇最该记住的一页。同网段 ARP 问目的主机，跨网段 ARP 问网关，原因是路由器只把包转发到下一跳，本机根本不需要知道远端主机的 MAC。IP 端到端不变，MAC 逐跳重写。

报文往返 #

text
Host A                          Switch/Broadcast            Host B
  | ARP Request (dst MAC = ff:ff:ff:ff:ff:ff)  -->  flood  -->
  | src MAC = A, src IP = 10.0.0.1, dst MAC = 00:00:00:00:00:00, dst IP = 10.0.0.2
  |                                                          |
  | <--  ARP Reply (unicast to A)  <--  forward  <--  B 收到广播，发现问的是自己
  | src MAC = B, src IP = 10.0.0.2, dst MAC = A, dst IP = 10.0.0.1
  |                                                          |
  | 写入缓存: 10.0.0.2 -> B 的 MAC，然后把缓存的 SYN 发出去

请求是广播，应答是单播。这一问一答在毫秒级结束，但它是 TCP 建连前面的第一道门槛。ARP 不通，ping 都不通，更别说握手。

ARP 高速缓存 #

ARP 缓存是一块缓冲区，存 IP 地址和 MAC 地址的对应表。表里一个条目记录网络上某台主机的 IP 和它对应的 MAC。每一个以太网或令牌环网络适配器都有自己单独的表。

地址解析协议被问一个已知 IP 的 MAC 时，先查缓存：有就直接返回对应 MAC，没有才发 ARP 请求向局域网查询。

为什么必须有缓存：每次建 TCP 连接都发 ARP 请求，效率顶不住。主机、交换机、路由器上都维护 ARP 缓存表，建连前先查表，命中就直接读表项做二层封装，只有表项失效才走请求应答。

缓存分两类：

类型 怎么来 生命周期 用途
动态表项 ARP 请求应答自动学习 带 TTL，到期删除，Windows 下一般不超过 10 分钟 日常通信
静态表项 手工添加 永久，需手动增删 常用本地地址（路由器、服务器）不发 ARP 请求

TTL 到 0，表项从表里删除，下次通信重新解析。这个设计让 IP 和 MAC 的对应关系能跟着网络变化自动收敛。

缓存的收益和风险是一体的。好处是减少广播量，网络通信量降下来，主机之间的通信效率上去。坏处是埋了安全隐患——ARP 表项可以被伪造的应答改写，后面免费 ARP 那节会看到这条路怎么被利用。

免费 ARP #

免费 ARP 指主机发送 ARP 查找自己的 IP 地址，一般发生在系统引导、接口配置的时候。它和标准 ARP 的区别只有一个：分组里的目的 IP 字段封装的是自己的 IP，等于向所在网络请求自己的 MAC。

四个作用：

  1. 查地址冲突。正常情况下发免费 ARP 请求不会收到应答。如果收到应答，说明网络里存在与本机 IP 相同的主机，地址冲突了。
  2. 刷新别人缓存里的旧硬件地址。主机换了网卡，MAC 变了，其他主机收到这个 ARP 请求，发现自己缓存里这个 IP 对应的 MAC 对不上，就用收到的请求更新本地表项。
  3. 网关防 ARP 攻击。有些网关设备按固定间隔主动发免费 ARP，让网内主机更新网关 MAC 表项，缓解 ARP 欺骗。
  4. 反过来也能用来做 ARP 攻击。

第 4 条值得单独说。ARP 协议不要求先发请求才收应答：主机只要收到 ARP 应答，就会拿应答里的 IP 和 MAC 更新本地缓存。攻击者构造一个虚假的免费 ARP 应答，把源 MAC 写成自己的，广播出去，所有收到的主机都会把某个 IP 指向攻击者的 MAC。之后这些主机的报文全被送到错误的地方，这就是 ARP 欺骗。中间人、断网、流量劫持，都从这一步开始。

代理 ARP #

代理 ARP 是用一台主机（一般是路由器）代替另一台设备，用自己的 MAC 回应针对那台设备的 ARP 请求。

为什么需要它：路由器的重要功能之一是把局域网的广播包限制在网内，阻止扩散，否则会形成网络风暴。ARP 请求是广播包，询问对象在同一局域网内就能收到应答；询问对象不在同一局域网，广播到不了，就没法应答。代理 ARP 补上这个缺口。

工作过程：主机 A 和主机 B 在同一网段但不同广播段。A 发 ARP 请求 B 的 MAC，因为路由器不转发广播，请求只能到达路由器。路由器开了代理 ARP，又知道 B 属于它连接的网络，就用自己的接口 MAC 代替 B 回应 A。A 收到应答，并不知道代理存在，照常把帧发给路由器。

优缺点都在这：

  • 优点：不改路由表就能加一台路由器，子网对主机透明。适合主机没配默认网关、也没有路由策略的网络。
  • 缺点：本质是一种 ARP 欺骗；两台物理网络被路由器互相隐藏，网络拓扑没法概括；那段网络的 ARP 流量变大，主机需要更大的 ARP 缓存；对不做 ARP 解析的网络完全无效。

八、PPP：点对点链路 #

它解决什么问题 #

PPP 是二层协议，也就是数据链路层协议，常出现在拨号上网的场景里：客户端拨号，向 ISP 获取 IP 地址。

它支持在各种物理类型的点对点串行线路上传输上层协议报文。特性一列就明白它的定位：支持多协议、提供可选的身份认证、支持数据压缩、支持协商、支持多链路捆绑。

和以太网对比着看更清楚。以太网是广播型共享链路，一个网段挂一堆机器，所以必须有 MAC 地址来区分「发给谁」。PPP 是点对点链路，一根线的两端各一台设备，对端唯一，所以不需要地址区分——这就是它把地址域固定成 0xFF 的原因。

PPP 更像一种应用。拨号成功后，本地主机能正常上网，能跑 TCP/IP，完全感觉不到 PPP 的存在。它把链路建立、身份核验、参数协商都做完了，然后把一条「能用」的链路交给上面的网络层。

帧格式 #

text
+------+------+------+--------+------------------+------+------+
| Flag | Addr | Ctrl | Proto  | Information      | FCS  | Flag |
| 0x7E | 0xFF | 0x03 | 2 B    | default 1500 B   | 2 B  | 0x7E |
+------+------+------+--------+------------------+------+------+
   1B     1B     1B                  payload

每个 PPP 数据帧以一个标志字节开始，也以它结束，这个字节是 0x7E。字段逐个看：

字段 长度 取值 含义
标志 1 字节 0x7E 帧定界，首尾各一个
地址 1 字节 0xFF 点对点协议，对方地址固定，没有寻址意义
控制 1 字节 0x03 无编号帧
协议域 2 字节 见下表 区分信息域承载的是什么报文
信息域 缺省 1500 字节 上层报文 IP 包、LCP 报文、认证报文都放这里
校验 2 字节 FCS 帧校验序列
标志 1 字节 0x7E 帧结束

协议域是这张表里信息量最大的字段，接收端靠它决定把信息域交给谁：

协议域取值 承载内容
0xC021 LCP 协议报文
0xC023 PAP 协议的认证报文
0xC223 CHAP 协议的认证报文
0x8021 NCP 协议报文
0x0021 IP 数据报文

LCP、PAP、CHAP 都在 0xC0 段里，NCP 用 0x8021，纯 IP 报文走 0x0021。抓包时认出这几个值，PPP 的协商过程就能一段段看明白。

三个组件 #

组件 全称 干什么
LCP 链路控制协议 完成数据链路的配置和测试
NCP 网络控制协议 完成点对点通信设备之间网络层通信所需参数的配置
PPP 扩展协议 如 Multilink Protocol 多链路捆绑一类的增强能力

LCP 管链路，NCP 管网络层参数，扩展协议管加强项。三者分段负责，链路层的事不掺和网络层，网络层的事不掺和链路层。

九、PPP 的协商过程 #

七步 #

用户拨号到能上网，中间要走完七步：

text
(1) 拨号接入 ISP，建立 PC 到 ISP 的物理连接
        |
(2) PC 向 ISP 发一系列 LCP 分组（封装成多个 PPP 帧），建立 LCP 连接
        |
(3) 这些分组及其响应选定将要使用的一些 PPP 参数
        |
(4) NCP 给新接入的 PC 分配一个临时 IP 地址，PC 成为互联网上有 IP 的主机
        |
(5) 通信完毕，NCP 释放网络层连接，收回分出去的 IP 地址
        |
(6) LCP 释放数据链路层连接
        |
(7) 释放物理连接

建立是自下而上，释放是自上而下，顺序刚好倒过来。第 4 步是很多人的盲点：拨号拿到的 IP 是 NCP 分配的，不是 LCP 分配的。

链路建立：LCP #

用户 PC 通过调制解调器呼叫 ISP 服务器，服务器检测到载波信号，双方建立物理连接。之后 PPP 进入「链路建立」状态，目的是建立链路层的 LCP 连接。

双方通过请求-响应帧通信，协商这些配置参数：

  • 链路上的最大帧长。
  • 所使用的鉴别协议的规约，如果有的话。
  • 是否不使用 PPP 帧中的地址和控制字段。

协商完成，LCP 连接建立，进入鉴别阶段。

第三项值得停一下：地址和控制字段可以协商省略，省掉 2 个字节。在拨号那种低带宽链路上，每帧省 2 字节是实打实的收益。省掉之后帧里就没有 0xFF 和 0x03 了，抓包看到这种帧不要以为是坏包。

鉴别：PAP 与 CHAP #

拨号上网要输用户名和密码，向服务器确认身份，这一步在 LCP 连接建立完成之后进行。

身份认证有两种方法：口令验证协议（PAP）和质询握手协议（CHAP）。双方在 LCP 配置时达成一致的话，也可以不做任何认证。三种选择由运营商决定。

对比项 PAP CHAP
握手次数 两次 三次
密码传输 明文传送用户名和密码 不传明文，传摘要算法加工过的随机序列
加密手段 无 MD5 加随机数
认证时机 建立连接时一次 随时可做，包括正常通信过程中
资源开销 小 大，要多次质询、响应，耗 CPU
适用场合 一般接入 安全要求很高的场合

CHAP 比 PAP 安全，原因不在算法强度，而在两点：线路上没有明文密码可截；认证可以随时重来，非法用户截获并破解了一次密码，这个密码过一段时间就失效了。

代价是对端系统要求高，要反复做质询和响应，占 CPU。所以它只出现在对安全要求高的场景，普通家宽拨号还是 PAP 居多。

身份认证通过，进入 NCP 连接建立阶段。

网络层配置：NCP #

NCP 根据网络层的不同协议，互相交换网络层特定的网络控制分组。这套设计允许 PPP 两端的网络层跑不同协议，仍然用同一个 PPP 通信。

NCP 会配置客户端的 IP 地址，配完就能上网。注意一点：上网过程中，仍然需要 PPP 协议对 IP 包做封装传输。NCP 只是把地址谈好，封装这件事一直由 PPP 干到最后。

链路状态的整体流转：

text
物理连接建立 -> 链路建立(LCP) -> 鉴别(PAP/CHAP) -> 网络层配置(NCP) -> 可通信
                    |                  |                  |
                    +------------------+------------------+--> 失败则回退/断开

PPPoE #

PPP 要求通信双方是点到点关系，不适于广播型以太网和另外一些多点访问网络。于是有了 PPPoE（Point-to-Point Protocol over Ethernet）。

它给使用桥接以太网接入的用户提供了一种宽带接入手段，同时带来接入控制和计费能力。每个接入用户建立一个独一无二的 PPP 会话，会话 ID 把同一个以太网广播域里的用户区分开。

这就是家里宽带要「拨号」的原因：以太网本身没有身份概念，套一层 PPP 才有账号、有会话、有计费。PPPoE 报文跑在以太网上，链路层还是以太网，上面再叠 PPP 的协商流程，ARP 和 PPP 就这样在同一条链路上各管一段。

十、四个协议的协作 #

单独看每个协议都清楚，串起来才见真章。三个场景，把四个协议摆在同一张图里。

场景一：同网段访问 #

浏览器向 10.0.0.2 的 80 端口发起请求，两台机器在同一个交换机下。

  1. 应用调 connect，内核组 SYN 段，选源端口，查路由表发现目的地址在本网段，出口是 eth0。
  2. 查 ARP 缓存找 10.0.0.2 的 MAC。没命中就广播 ARP 请求，收到应答后写入缓存。
  3. 组帧：以太网头（源 MAC 是自己的，目的 MAC 是对方的）+ IP 头（源 IP、目的 IP）+ TCP 头（端口、SEQ、SYN）+ 空负载。
  4. 交换机按目的 MAC 转发，对方网卡收下，逐层解封装，TCP 层回 SYN+ACK。
  5. 握手完成，TCP 连接建立，HTTP 报文开始在上面跑。

这一路里，ARP 只负责第 2 步，但它卡在最前面。ARP 不出结果，后面全都动不了。

场景二：跨网段访问 #

目的地换成 192.168.5.10，不在本网段。

  1. 查路由表，命中默认路由，下一跳是网关 10.0.0.1。
  2. 查 ARP 缓存找网关的 MAC，不是找目的主机的 MAC。没命中就广播问网关。
  3. 组帧：目的 MAC 填网关的，目的 IP 还是 192.168.5.10。
  4. 网关收下，剥掉以太网头，查自己的路由表，往下一跳转发，重新封一个以太网头，源 MAC 换成自己出口的 MAC。
  5. 每一跳都重复第 4 步，直到最后一跳的网关发现目的主机就在自己直连的网段，ARP 问出它的 MAC，投递。

关键在两点：IP 地址端到端不变，MAC 地址逐跳重写。ARP 的广播范围不出网段，所以跨网段只能一跳一跳问过去。

场景三：拨号链路 #

PC 通过 PPP 上网，链路是串行的点对点。

  1. 物理连接建立，LCP 协商链路参数。
  2. PAP 或 CHAP 完成身份认证。
  3. NCP 分配 IP，PC 拿到一个临时地址。
  4. 之后每个 IP 包都被封进 PPP 帧的信息域，协议域填 0x0021，从串口发出去。

这条链路上没有 ARP。点对点只有一个对端，不需要问「这个 IP 对应哪张网卡」，帧发出去只能到对面那台设备。ARP 解决的是「多台设备里选哪一台」，点对点链路里这个问题不存在。

层次 以太网接入 PPP 拨号接入
应用层 HTTP、DNS HTTP、DNS
传输层 TCP、UDP TCP、UDP
网络层 IP，靠 ARP 找下一跳 MAC IP，链路唯一对端，不需要 ARP
链路层 以太网，靠 MAC 寻址 PPP，靠协议域区分上层
地址来源 静态配置或 DHCP NCP 分配

四种需求在这里各就各位：ARP 做跨层映射，PPP 做点对点封装，TCP 和 UDP 做端到端传输。少任何一个，这条链路都跑不通。

十一、从协议到应用 #

组装是内核的事 #

收到 TCP 数据包以后，组装还原由操作系统完成。应用程序不会直接处理 TCP 数据包。

对应用来说，不用关心通信细节。除非线路异常，收到的总是完整数据。应用需要的数据放在 TCP 包里面，有自己的格式，比如 HTTP。

TCP 没有提供任何机制来表示原始文件的大小，这件事由应用层协议规定。HTTP 有个头信息 Content-Length，写明信息体多大。对操作系统来说，就是持续接收 TCP 包，按顺序组装好，一个包都不少。

操作系统不处理 TCP 包里的数据内容。组装好就转交给应用。TCP 头里有个端口参数，用来指定交给监听该端口的应用。21 端口是 FTP 服务器，25 端口是 SMTP 服务，80 端口是 Web 服务器。

应用收到组装好的原始数据，以浏览器为例，会按 HTTP 的 Content-Length 字段读出这一段段数据。这也意味着一次 TCP 通信可以包含多个 HTTP 通信——连接复用，就是这么来的。

应用该管什么，不该管什么 #

事项 谁负责
分段、编号、重传、排序 TCP
端口到进程的交付 内核
数据边界与长度语义 应用层协议（Content-Length、chunked、TLV）
一条连接上跑几个请求 应用层（keep-alive、多路复用）
超时、重试、幂等 应用层
消息是否可信 应用层（TLS 在 TCP 之上，DTLS 在 UDP 之上）

分界线很清楚：TCP 保证字节到齐、按序，不保证「一个请求一个响应」，也不保证业务意义上的送达。应用的超时和重试逻辑，得自己写。

手上能验证的命令 #

读完概念，落到命令行确认一遍，比看图快：

text
ss -tan                 # 看 TCP 连接状态、收发队列、拥塞窗口
ss -uan                 # 看 UDP 套接字，没有状态机，只有收队列
ip neigh                # 看 ARP 缓存表，对应本篇第六、七章
ip neigh flush all      # 清空缓存，再抓包就能看到完整 ARP 请求应答
ip -s link show eth0    # 看网卡的收发计数和错误计数
tcpdump -i eth0 -nn arp # 只看 ARP，验证广播问、单播答

ss -ti 还能看到 rtt、cwnd、retrans 这些数字，正好对上第三章那套机制。丢包排查的第一步不是猜，是看 retrans 计数涨没涨。

十二、易错点速查 #

易错点 事实
以为 IP 地址够用，不需要 MAC 内核发帧必须给目的 MAC，只有 IP 发不出去
以为跨网段要 ARP 目的主机 跨网段 ARP 问的是网关，路由器只转发到下一跳
以为 ARP 能跨网段解析 ARP 请求是广播，广播不出网段
以为 ARP 是网络层协议 ARP 在第 2 层链路层工作，服务的是 IP 映射
以为收到 ARP 应答才更新缓存 收到任何 ARP 应答都会更新，这是 ARP 欺骗的入口
以为 TCP 一次发送对应一次接收 TCP 是字节流，没有报文边界，读到的多少由缓冲决定
以为 UDP 会重传 UDP 只查错不补，丢包由应用自己兜
以为 MTU 1500 就能装 1500 字节数据 减去 IP 头 20、TCP 头 20，MSS 只剩 1460
以为 RTO 拍个固定值就行 RTO 要靠 RTT 采样估算，拍错就误重传或恢复慢
以为有窗口就够了 序号、确认、重传、窗口四件套缺一不可
以为 ACK 一定单独成包 ACK 常与数据合并，双向都要发
以为 PPP 需要 MAC 地址 点对点对端唯一，地址域固定 0xFF，没有寻址含义
以为拨号拿到的 IP 是 LCP 给的 是 NCP 分配的，LCP 只管链路参数
以为 PAP 和 CHAP 差不多 PAP 明文两次握手，CHAP 摘要三次握手，安全性差一档
以为 PPPoE 还是 PPP 链路层是以太网，上面套 PPP 会话，两者叠着用
以为 ARP 缓存不用管 TTL 到期要重新解析，静态表项则要手动维护

十六个坑，多半是把某一层的职责记到了另一层头上。回到第一章那张分层表，把每个协议的位置摆正，这些错就犯不了。
