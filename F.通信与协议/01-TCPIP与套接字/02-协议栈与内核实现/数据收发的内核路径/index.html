这篇只讲两个函数：netif_receive_skb() 与 dev_queue_xmit()。前者是数据包从网卡进入协议栈的唯一入口，后者是协议栈把包交给链路层的唯一出口。所有包，不管上层是 TCP、UDP、ICMP、ARP，不管底层是物理网卡、veth、bond 还是 loopback，都要从这两个闸门过一遍。

讲什么：dev_queue_xmit 的逐段流程、qdisc 排队与出队、dev_hard_start_xmit 到驱动回调、netif_receive_skb 的四步分发、ptype_all 与 ptype_base 两套注册表、NAPI 的调度链、sk_buff 在两条路径上的字段变化、一个包从发到收的完整旅程。

不讲什么：socket 层与 TCP 状态机、IP 层转发与分片重组、netfilter 五条链的钩子细节、驱动里 DMA ring 的寄存器操作。这些各有专篇。

跨篇指路：协议栈整体分层看《协议栈架构》；sk_buff 的内存布局看数据结构那篇；网桥在 handle_bridge() 里被调用，展开在《二层桥转发》；handle_macvlan() 展开在《VLAN 源码》；NF_HOOK 展开在《Netfilter》；fib_lookup() 展开在《路由表》。

两个函数读完，数据流的骨架就立起来了，剩下的工作都是往骨架上挂肉。

一、两个总闸门 #

先给结论，再拆细节。Linux 收包只有一条主干：网卡 DMA 把帧写进内存，驱动在中断里把帧包成 sk_buff，然后交给 netif_receive_skb()。从这个函数往下，才是 IP、ARP、网桥、抓包这些消费方。发包也只有一条主干：上层把 sk_buff 填好，路由查完，邻居表给出目的 MAC，然后交给 dev_queue_xmit()。从这个函数往下，才是 qdisc、驱动、硬件。

中间那些名字看着很多的函数，netif_rx()、process_backlog()、napi_gro_receive()、dev_hard_start_xmit()、qdisc_run()，全是包着这两个主干跑的外壳。外壳可以换，主干不会换。

有个容易忽略的对称性：两个函数都不保证「发出去」或「交上去」，它们保证的是「包的归属权转移了」。dev_queue_xmit 返回成功，意思不是包已经到了网线上，是包已经进了 qdisc 或者已经塞进驱动的发送环，后续成不成看硬件。netif_receive_skb 返回 NET_RX_DROP，意思也不是「丢了个坏包」，是「没有协议认领它」。

dev_queue_xmit 的前置条件比接收侧严格得多。它要求 skb->dev 已经指向真实设备，要求链路层头已经建好，要求 skb->len 是完整帧长。接收侧宽松：驱动只管把 skb->data 挪到网络层头的位置，把 skb->protocol 填上，剩下的判断全交给协议分发。

为什么是「唯一」 #

看内核代码时你会数出一堆发送入口：dev_queue_xmit()、dev_direct_xmit()、__dev_queue_xmit()；也会数出一堆接收入口：netif_receive_skb()、netif_receive_skb_list()、__netif_receive_skb()、netif_rx()。这些是同一套东西的不同马甲，__dev_queue_xmit() 是真正干活的实现，dev_queue_xmit() 是它对外的皮；netif_receive_skb() 调 netif_receive_skb_internal()，再调 __netif_receive_skb_core()。皮会变，实现只有一份。

你写驱动、写模块、抓包、做 eBPF 挂点，最终都要落到这两处。记住位置比记住名字有用。

二、发送路径的全貌 #

发送方向的起点在协议栈上层。TCP 的重传队列、UDP 的 sendmsg、ICMP 的 echo、ARP 的应答，各自把数据装进 sk_buff，各自加上自己的头，最后都汇到 IP 层输出。IP 层做完路由决策，知道从哪张网卡出去、下一跳是谁，就去邻居表要目的 MAC。MAC 拿到了，链路层头拼上，然后调用 dev_queue_xmit()。往下就是本篇的领地。

阶段划分 #

阶段 位置 干的活
1 ip_finish_output2() 查路由结果、查邻居、拼以太头
2 dev_queue_xmit() 线性化、校验和兜底、选队列
3 qdisc_enqueue_root() 按 qdisc 规则入队
4 qdisc_run() → __qdisc_run() 循环出队尝试发送
5 qdisc_restart() 出队、加发送锁、调 dev_hard_start_xmit()
6 dev_hard_start_xmit() 给 ptype_all 补一份、GSO 分段、调驱动
7 dev->hard_start_xmit() 驱动把帧塞进 DMA ring、敲门铃
8 硬件 信号发出去，完成后回中断

八步里第 2 到第 6 步全在 net/core/dev.c 一个文件里，这是 dev.c 被称作协议栈「神经中枢」的原因。

上面那条链路里，dev_queue_xmit() 是唯一能把 sk_buff 从「协议栈视角」翻译成「设备视角」的地方。翻过去之后，包不再属于协议栈，它属于 queue discipline，属于驱动，属于硬件。这就是理解发送路径的关键分界：你抓包抓不到出方向的包，先问自己钩子挂在 dev_queue_xmit 之前还是之后。

三、dev_queue_xmit 的流程 #

函数不长，两百行出头，但每一段都对应一类真实的坑。把它切成四段看：前置整理、选队列、入队出队、无队列兜底。入口条件很明确：出口设备在 skb->dev，载荷从 skb->data 起，长度 skb->len。上层该给的都给了，这个函数不改语义，只做整理和投递。

第零段：前置整理 #

四件事，都带「驱动能力协商」的味道。

c
int dev_queue_xmit(struct sk_buff *skb)
{
    struct net_device *dev = skb->dev;
    struct netdev_queue *txq;
    struct Qdisc *q;
    int rc = -ENOMEM;

    /* GSO will handle the following emulations directly. */
    if (netif_needs_gso(dev, skb))
        goto gso;

    if (skb_shinfo(skb)->frag_list &&
        !(dev->features & NETIF_F_FRAGLIST) &&
        __skb_linearize(skb))
        goto out_kfree_skb;

第一件：这块包要走 GSO，就跳过后面所有「合成一个大包」的整理。理由很直白，GSO 的活儿就是把大包切小，这时候再把散片拼起来纯属反向操作。

第二件：frag_list 非空，且网卡不支持 NETIF_F_FRAGLIST，就把整条 skb 链拼成一个线性缓冲。__skb_linearize() 内部是 __pskb_pull_tail(skb, skb->data_len)，语义上跟 pskb_may_pull() 一路。后者判断主 buf 里够不够 pull 出 len 字节，不够就重新分配并把 frags 里的数据拷进新主 buf。这里把长度参数设成 skb->data_len，等于「把全部非线性数据都搬进主 buf」，线性化就是这么完成的。

c
    /* Fragmented skb is linearized if device does not support SG,
     * or if at least one of fragments is in highmem and device
     * does not support DMA from it.
     */
    if (skb_shinfo(skb)->nr_frags &&
        (!(dev->features & NETIF_F_SG) || illegal_highdma(dev, skb)) &&
        __skb_linearize(skb))
        goto out_kfree_skb;

第三件：nr_frags 非空，且网卡不支持 scatter-gather，或者有分片落在高端内存而设备不能从那儿 DMA，同样线性化。上面两段里已经拼过的，第二次 __skb_linearize() 会立刻返回，不重复干活。

frags 和 frag_list 是两个东西，混起来会看错代码：

结构 存什么 skb 个数 典型来源
skb_shinfo(skb)->frags[] 额外数据页的引用 1 个 skb 零拷贝发送、sendpage、大页拼接
skb_shinfo(skb)->frag_list 指向下一个 skb 一条链 GSO 分段结果、IP 分片重组

前者是「一个包，多块内存」，影响 DMA 能不能直接读；后者是「多个包，串成链」，影响是否要整体线性化。

c
    /* 校验和没算，且驱动不支持硬件算，就在这儿补 */
    if (skb->ip_summed == CHECKSUM_PARTIAL) {
        skb_set_transport_header(skb, skb->csum_start - skb_headroom(skb));
        if (!dev_can_checksum(dev, skb) && skb_checksum_help(skb))
            goto out_kfree_skb;
    }
gso:

第四件：CHECKSUM_PARTIAL 表示「校验和字段先留空，谁发谁算」。网卡支持硬件校验和就留给网卡，不支持就软件算，算不出来就丢。skb_set_transport_header() 那行在修正传输层头指针，因为 csum_start 是相对 skb->head 记的，而 skb->data 已经挪过位置，必须换算。

第一段：选队列 #

c
    rcu_read_lock_bh();
    txq = dev_pick_tx(dev, skb);
    q = rcu_dereference(txq->qdisc);
#ifdef CONFIG_NET_CLS_ACT
    skb->tc_verd = SET_TC_AT(skb->tc_verd, AT_EGRESS);
#endif

rcu_read_lock_bh() 一次性关掉下半部和抢占，为的是安全读 txq->qdisc 这个 RCU 指针，同时挡住后续锁路径上的软中断。

dev_pick_tx() 决定包进哪个发送队列。设备提供了 ndo_select_queue 回调就用它，没提供就内核按流哈希挑。多数驱动不设多队列，分配 net_device 时队列数就是 1，txq 永远指向那唯一一个。q 是从 netdev_queue 上取下来的 qdisc，一个发送队列挂一个 qdisc，这是 Linux 流量控制的基本粒度。NET_CLS_ACT 打开时顺手打上 egress 标记，给 tc action 用。

第二段：有队列，入队再出队 #

c
    if (q->enqueue) {
        spinlock_t *root_lock = qdisc_lock(q);
        spin_lock(root_lock);

        if (unlikely(test_bit(__QDISC_STATE_DEACTIVATED, &q->state))) {
            kfree_skb(skb);
            rc = NET_XMIT_DROP;
        } else {
            rc = qdisc_enqueue_root(skb, q);
            qdisc_run(q);
        }
        spin_unlock(root_lock);
        goto out;
    }

q->enqueue 非空，说明这个 qdisc 会缓存包，判断依据是函数指针在不在，不是队列长度。__QDISC_STATE_DEACTIVATED 置位表示 qdisc 正在被销毁，这时的包无处可去，直接 kfree_skb() 并返回 NET_XMIT_DROP。

正常路径两句话：qdisc_enqueue_root() 入队，qdisc_run() 触发发送。注意这里不是「把传进来的 skb 直接发出去」，而是「先塞进队列，再由调度器决定发哪个」，这正是排队规则的意义：入队顺序不等于出队顺序。默认 qdisc 由 qdisc_create_dflt() 在 dev_open() → dev_activate() 里装上，驱动不需要自己建。

第三段：没队列，直接怼硬件 #

有些设备压根不排队，软件设备是主力：loopback、各种隧道、veth。

c
    /* The device has no queue. Common case for software devices:
     * loopback, all the sorts of tunnels...
     * Really, it is unlikely that netif_tx_lock protection is necessary
     * here. (f.e. loopback and IP tunnels are clean ignoring statistics
     * counters.)
     * However, it is possible, that they rely on protection
     * made by us here.
     * Check this and shot the lock. It is not prone from deadlocks.
     * Either shot noqueue qdisc, it is even simpler 8)
     */
    if (dev->flags & IFF_UP) {
        int cpu = smp_processor_id();  /* ok because BHs are off */
        if (txq->xmit_lock_owner != cpu) {
            HARD_TX_LOCK(dev, txq, cpu);
            if (!netif_tx_queue_stopped(txq)) {
                rc = 0;
                if (!dev_hard_start_xmit(skb, dev, txq)) {
                    HARD_TX_UNLOCK(dev, txq);
                    goto out;
                }
            }
            HARD_TX_UNLOCK(dev, txq);
            if (net_ratelimit())
                printk(KERN_CRIT "Virtual device %s asks to "
                       "queue packet!\n", dev->name);
        } else {
            /* Recursion is detected! It is possible,
             * unfortunately */
            if (net_ratelimit())
                printk(KERN_CRIT "Dead loop on virtual device "
                       "%s, fix it urgently!\n", dev->name);
        }
    }
    rc = -ENETDOWN;

逐层看。dev->flags & IFF_UP 不过，设备没起，返回 -ENETDOWN，包被丢。

txq->xmit_lock_owner != cpu 是递归检测。它记录当前持锁 CPU 号，如果就是自己，说明这个虚拟设备的发送路径绕回了自己，典型的隧道配置错误，内核只能打一条 Dead loop on virtual device 并丢包。

netif_tx_queue_stopped(txq) 是队列停止位，由驱动设置，停着就不发，落到下面的 printk。dev_hard_start_xmit() 返回 0 表示包已经被驱动接管，这里有个反直觉的地方：它返回 0 是成功，返回非 0 才要继续走兜底逻辑。两条 printk 都不常见，见到就是配置或驱动有问题。

出口条件 结果
IFF_UP 未置位 -ENETDOWN，丢包
检测到递归持锁 打 Dead loop on virtual device，丢包
队列处于 stopped 打 Virtual device asks to queue packet，丢包
dev_hard_start_xmit() 成功 返回 0，包进驱动

无队列分支的残酷之处：没有缓冲，发不出去就是发不出去，不存在「等等再发」。所以这条分支的行为可以一句话概括：有队列的设备循环从队列里取包发，没队列的设备只发一次，失败即丢。

c
out_kfree_skb:
    kfree_skb(skb);
    return rc;
out:
    rcu_read_unlock_bh();
    return rc;
}

两个出口，一个负责在失败时释放 skb，一个负责成功时只解锁。

四、qdisc：排队规则 #

qdisc 是「queue discipline」的缩写，直译排队纪律。位置很固定：netdev_queue 上一个指针，dev->qdisc 指向它。它在发送路径上的作用一句话说清：dev_queue_xmit() 先把包入队，再由 qdisc 出队交给驱动，流量控制、优先级、限速全挂在这一层。

默认是 pfifo_fast #

新建队列时内核装的是 pfifo_fast，三个 FIFO 带（band），按 skb 的优先级字段映射到不同带，高优先级带先出。纯软件实现，没动过配置就是它。

带 优先级范围（skb->priority） 用途
0 1 ~ 3 交互流量、控制报文
1 4 ~ 7 普通业务流量
2 0 或 8 以上 批量、后台流量

tc qdisc show 看到 pfifo_fast 就是默认状态；tc -s qdisc show dev eth0 会给出每个带的 backlog 和丢包计数。

qdisc 对外是三个方法：

方法 职责
enqueue 按规则把 skb 放进队列，队列满时丢包
dequeue 按规则取出下一个该发的 skb
requeue 发送失败时把 skb 放回队首

这套方法集合就是「队列规则」的定义。先进先出是最简单的一种，pfifo、bfifo 就是它。htb、tbf、fq_codel、netem 各有各的出队策略，能做的事远超 FIFO：限速、整形、加延迟、模拟丢包。

调度：qdisc_run 到 qdisc_restart #

c
static inline void qdisc_run(struct Qdisc *q)
{
    if (!test_and_set_bit(__QDISC_STATE_RUNNING, &q->state))
        __qdisc_run(q);
}

__QDISC_STATE_RUNNING 是防重入位。测试并置位是原子的，谁抢到谁跑，抢不到说明已经有 CPU 在跑这个 qdisc，直接返回。这保证同一个 qdisc 不会被两个 CPU 同时出队。

c
void __qdisc_run(struct Qdisc *q)
{
    unsigned long start_time = jiffies;

    while (qdisc_restart(q)) {
        /*
         * Postpone processing if
         * 1. another process needs the CPU;
         * 2. we've been doing it for too long.
         */
        if (need_resched() || jiffies != start_time) {
            __netif_schedule(q);
            break;
        }
    }
    clear_bit(__QDISC_STATE_RUNNING, &q->state);
}

循环条件就是 qdisc_restart() 的返回值：非 0 表示队列里还有包，继续取。两个跳出条件：有更高优先级的进程要跑（need_resched()），或者已经干满一个时间片（jiffies 变了）。跳出之前调 __netif_schedule(q)，把 qdisc 挂到 softnet_data.output_queue 上并触发 NET_TX_SOFTIRQ，剩下的活儿交给软中断。这个「干一会儿就交棒」的设计，是为了不让一个发包的进程把 CPU 抓死。

c
static inline int qdisc_restart(struct Qdisc *q)
{
    struct netdev_queue *txq;
    int ret = NETDEV_TX_BUSY;
    struct net_device *dev;
    spinlock_t *root_lock;
    struct sk_buff *skb;

    /* Dequeue packet */
    if (unlikely((skb = dequeue_skb(q)) == NULL))
        return 0;

    root_lock = qdisc_lock(q);
    /* And release qdisc */
    spin_unlock(root_lock);
    dev = qdisc_dev(q);
    txq = netdev_get_tx_queue(dev, skb_get_queue_mapping(skb));
    HARD_TX_LOCK(dev, txq, smp_processor_id());

    if (!netif_tx_queue_stopped(txq) &&
        !netif_tx_queue_frozen(txq))
        ret = dev_hard_start_xmit(skb, dev, txq);
    HARD_TX_UNLOCK(dev, txq);
    spin_lock(root_lock);

    switch (ret) {
    case NETDEV_TX_OK:
        /* Driver sent out skb successfully */
        ret = qdisc_qlen(q);
        break;
    case NETDEV_TX_LOCKED:
        /* Driver try lock failed */
        ret = handle_dev_cpu_collision(skb, txq, q);
        break;
    default:
        /* Driver returned NETDEV_TX_BUSY - requeue skb */
        if (unlikely(ret != NETDEV_TX_BUSY && net_ratelimit()))
            printk(KERN_WARNING "BUG %s code %d qlen %d\n",
                   dev->name, ret, q->q.qlen);
        ret = dev_requeue_skb(skb, q);
        break;
    }

    if (ret && (netif_tx_queue_stopped(txq) ||
                netif_tx_queue_frozen(txq)))
        ret = 0;
    return ret;
}

这是真正把包交给驱动的函数。出队之后先放 qdisc 锁，再取发送锁：两把锁不是一把，持锁顺序是「先 qdisc 后 txq」，主动放开队列锁再去拿 txq 锁，避免长时间占着队列锁。skb_get_queue_mapping(skb) 给出该走哪个子队列，多队列网卡靠它把流打散到不同硬件队列。调 dev_hard_start_xmit() 之前还要查队列是否 stopped 或 frozen，停着的队列不往里塞。

返回值三分支：

dev_hard_start_xmit 返回 qdisc_restart 的处理 返回值含义
NETDEV_TX_OK 驱动已发出，ret = qdisc_qlen(q) 剩余队列长度，非 0 就继续循环
NETDEV_TX_LOCKED handle_dev_cpu_collision() 抢锁冲突，重入队或丢弃
NETDEV_TX_BUSY dev_requeue_skb() 驱动忙，skb 退回队列
其他值 打 BUG 警告，然后按 busy 处理 驱动返回值不合法

handle_dev_cpu_collision() 的逻辑不复杂，两种情况。占着锁的正是当前 CPU，说明重入，释放这个包并打警告；占着锁的是别的 CPU，就把包重新入队，等下次再试。NETDEV_TX_BUSY 是最常见的一种「忙」，发送环满了、队列被停了，驱动都会这么回，包不能丢，只能退回队列。

最后那个 if 让函数返回 0，条件是队列停了或冻了。返回 0 会让 __qdisc_run 的循环结束，因为再取也是白取。结果就是本节开头那句话：发送成功时返回剩余队列长度，发送失败时返回 0，发送成功但队列已空也返回 0。

既然有 dev_queue_xmit，为什么要软中断 #

这个问题问得对。dev_queue_xmit() 已经把包整理干净，也尝试发了一次，软中断还来干什么。

第一，它没发完。qdisc 循环会因为时间片、因为队列停止、因为驱动忙而中途退出，剩下的包还在队列里躺着。

第二，队列被停止期间，dev_queue_xmit() 仍然能把包塞进队列，只是发不出去。队列被驱动唤醒的那一刻，得有人把积压的包取出来发，这个人就是软中断。

第三，这件事不能由 dev_queue_xmit() 自己的调用者做。发包的有的是 write() 系统调用，有的是 TCP 重传定时器，有的是另一个软中断，谁都不该被拖在那儿等硬件。

第四，释放 skb 也得有人做。部分驱动在硬件中断里完成发送，为了不拖长中断处理时间，内核把 skb 释放挪到软中断：驱动调 dev_kfree_skb_irq() 把 skb 挂到 softnet_data.completion_queue，再触发发送软中断，net_tx_action() 在软中断里统一释放。

软中断只做两件事，而且都不碰已经整理过的包：

动作 操作对象 说明
释放 completion_queue 上的 skb 逐个 kfree_skb()，清空已完成队列
发送 output_queue 上的 dev 对每个设备调 qdisc_run()，继续出队

边界很清楚：dev_queue_xmit() 做整理加第一次尝试，软中断只做「把剩下的发出去」和「把发完的释放掉」。软中断不需要再线性化，不需要再算校验和，那些活儿前面已经干完了。

五、网卡驱动的发送 #

qdisc_restart() 把包交给 dev_hard_start_xmit()。这一层还在 dev.c 里，还没到驱动。它要做的最后一件事，是让抓包程序也有机会看一眼。

c
int dev_hard_start_xmit(struct sk_buff *skb, struct net_device *dev,
                        struct netdev_queue *txq)
{
    if (likely(!skb->next)) {
        /*
         * 每一个发送的包，也会给 ptype_all 一份
         * packet 套接字创建时，proto 为 ETH_P_ALL 的会在 ptype_all 里注册一个成员
         * 所以 ETH_P_ALL 的 packet 套接字收发的数据都能看到
         */
        if (!list_empty(&ptype_all))
            dev_queue_xmit_nit(skb, dev);

        if (netif_needs_gso(dev, skb)) {
            if (unlikely(dev_gso_segment(skb)))
                goto out_kfree_skb;
            if (skb->next)
                goto gso;
        }

        /* 驱动提供的发送回调 */
        return dev->hard_start_xmit(skb, dev);
    }
gso:
    do {
        struct sk_buff *nskb = skb->next;
        int rc;

        skb->next = nskb->next;
        nskb->next = NULL;
        rc = dev->hard_start_xmit(nskb, dev);
        if (unlikely(rc)) {
            nskb->next = skb->next;
            skb->next = nskb;
            return rc;
        }
        if (unlikely(netif_tx_queue_stopped(txq) && skb->next))
            return NETDEV_TX_BUSY;
    } while (skb->next);

    skb->destructor = DEV_GSO_CB(skb)->destructor;
out_kfree_skb:
    kfree_skb(skb);
    return 0;
}

skb->next 是判据：空着走单包主干，非空说明这是一条链，属于 GSO 分段后的产物，走 gso: 标签的循环。

dev_queue_xmit_nit() 是抓包钩子，ptype_all 非空才调，空的就跳过，这是一处纯性能考虑的判断。挂在 ptype_all 上的 AF_PACKET 套接字，发送方向也能收到拷贝，这件事第八章细说。

netif_needs_gso() 为真说明硬件支持大包分片卸载，得先把大包切成硬件能接受的长度，切完如果成了链，进 gso: 循环逐段交出去。循环里的失败处理值得记住：任意一段发送失败，把剩下的链重新串回去，返回错误码让上层重排队；发到一半队列被停，剩下的塞不进去了，返回 NETDEV_TX_BUSY。

条件 动作
单包且不需要 GSO 调 dev->hard_start_xmit()，原样返回其结果
需要 GSO 且分出链 进 gso: 循环，逐段发
GSO 分段失败 kfree_skb() 后返回 0，包丢弃

dev->hard_start_xmit 就是驱动的回调了，到这一步，协议栈的代码彻底让位。

驱动里发生了什么 #

驱动拿到 skb 后干三件事，各家用词不同，骨架一致：把 skb->data 指向的缓冲区映射成 DMA 地址，写进发送描述符环的下一个空位；更新环的尾指针，也就是门铃寄存器，通知硬件「有新活了」；环满了就回 NETDEV_TX_BUSY，并在合适的时候 netif_stop_queue()。

返回 NETDEV_TX_OK 的含义要说清楚：帧已经进了设备的发送缓冲区，硬件会自己把它送上网线。这不等于对端收到了，也不等于没有冲突，真正的完成由硬件中断告知。

c
/* 驱动里的典型收尾 */
txq_trans_update(txq);
if (unlikely(netif_xmit_frozen_or_stopped(txq)))
    return NETDEV_TX_BUSY;
return NETDEV_TX_OK;

队列的停与启 #

队列停不停由驱动说了算，两个函数管这件事：

函数 作用 谁调用
netif_stop_queue(dev) 置停止位，qdisc 不再往里塞包 驱动发现发送环将满
netif_wake_queue(dev) 清停止位，并触发一次 NET_TX_SOFTIRQ 驱动在发送完成中断里释放了描述符

停止位的意义是反压。硬件吃不下就往上顶，顶到 qdisc，qdisc 顶到协议栈，协议栈让 socket 发送队列积压，最终 write() 阻塞。整条链路上唯一能「顶住」的地方就是 qdisc。netif_wake_queue() 里那次软中断触发很关键：队列停着的时候积压的包没人管，唤醒时必须主动踢一脚，让 net_tx_action() 去调 qdisc_run()。

看门狗 #

还有种坏情况：设备硬件出问题，发送环一直满着。包发不出去，就不会有发送完成中断，队列永远醒不过来，网络直接瘫。

dev_watchdog() 定时器盯着这件事。发现队列处于停止状态，且距最后一次发送成功已经超过 dev->watchdog_timeo，就认定设备卡死，调驱动的 ndo_tx_timeout，驱动在里面复位硬件、重建描述符环，最后 netif_wake_queue() 把流程接回去。ip link 里能看到 TX errors 和 drops 上涨，配上 dmesg 里一行 NETDEV WATCHDOG: eth0 (xxx): transmit queue 0 timed out，这条路径就锁定了。

loopback 的特殊性 #

回环设备没有队列，dev_queue_xmit() 走无队列分支，hard_start_xmit 是 loopback_xmit()。它的结尾直接调 netif_rx() 把包送回接收路径。

c
static netdev_tx_t loopback_xmit(struct sk_buff *skb, struct net_device *dev)
{
    skb_orphan(skb);
    skb->protocol = eth_type_trans(skb, dev);
    /* 直接进接收队列，一步不落地绕回来 */
    if (likely(__netif_rx(skb) == NET_RX_SUCCESS))
        dev->stats.tx_bytes += skb->len;
    ...
    return NETDEV_TX_OK;
}

这就是 ping 127.0.0.1 不碰网卡的原因：包从发送路径出发，走了几十行代码就进了接收路径。

六、接收路径的全貌 #

接收方向和发送方向对称，但多了两道调度。发送方向只有 qdisc，接收方向有两级：软中断调度的 poll_list，驱动自己的环。起点永远是硬件中断——网卡收到帧，DMA 写进内存，发中断。中断处理函数由驱动注册，往下的处理分老式和新式两条路。

老式：netif_rx 加 backlog #

中断处理里干四件事：分配一个 sk_buff；操作设备，把收到的帧拷进 skb 的缓冲区；设置 skb->protocol，从以太头里取出来；调 netif_rx(skb)。

netif_rx() 给 skb 补时间戳之类的附加信息，然后把它塞进当前 CPU 的 softnet_data.input_pkt_queue。塞之前要看队列长度：队列太长说明收得比处理得快，上层来不及消化，设备算陷入拥塞，新包直接被丢。这就是 netdev_max_backlog 的作用，/proc/sys/net/core/netdev_max_backlog 里能改。

一切正常就调 netif_rx_schedule(dev)。这里有个巧妙的地方：netif_rx() 用的是 softnet_data 里内嵌的 backlog_dev 作为 dev 参数，这个「设备」是虚拟的，专门给老式路径当壳用；netif_rx_schedule() 把它加进 softnet_data.poll_list，如果它不在队列里的话。新式 NAPI 在中断里只做一件事：拿真实设备调 netif_rx_schedule(dev)。就这一句。

两条路最后都触发 NET_RX_SOFTIRQ 软中断，然后 net_rx_action() 被调用。

net_rx_action 与配额 #

net_rx_action() 遍历当前 CPU 的 poll_list，对每个 dev 调 dev->poll()。这个方法由驱动实现，接收并处理报文，backlog_dev 是个例外，它的 poll 不是驱动写的。每轮有配额，不会无限跑：处理够数量的包，或者耗时超过 netdev_budget_usecs，就收工返回，返回前再触发一次 NET_RX_SOFTIRQ，下一轮继续。

限制 内核参数 默认量级
单轮最多处理多少个包 netdev_budget 300
单轮最多跑多长时间 netdev_budget_usecs 2000 微秒

超过任一条就退出，避免软中断把 CPU 占死导致用户态饿死。

process_backlog(backlog_dev, budget) 是老式的落点，它遍历 input_pkt_queue，对每个 skb 调 netif_receive_skb()，调用时把当前剩余配额 budget 传下去，一层层扣减。它只有两个结局：配额用完或时间到，直接返回，backlog_dev 留在 poll_list 里；把队列清空，则把 backlog_dev 从 poll_list 里摘掉。

softnet_data 的三个成员 #

这是每 CPU 一份的调度结构，收包全靠它。

成员 类型 干什么
poll_list 设备链表 有包待处理的设备排队等 poll
input_pkt_queue skb 队列 老式路径下已收待处理的包
backlog_dev 虚拟 net_device 老式路径的假设备，poll 指向 process_backlog

后两个是为兼容老式处理方式存在的。理解方式：老式路径借一个假设备的名义排队，真设备的 poll 直接处理自己的环，假的 poll 去翻 input_pkt_queue。

接收路径比发送路径多一层结构，原因在硬件：发送是「你推它」，接收是「它推你」。硬件推过来的时候你在中断里，中断里不能干重活，只能挂个号慢慢处理，poll_list 就是这个号。这也解释了为什么抓包在收方向上比发方向更常见地影响性能：每个包都要过一遍 ptype_all，有钩子就得复制。

七、netif_receive_skb 的流程 #

这个函数把包从「设备视角」翻译回「协议视角」。翻译分四步，顺序不能乱。

c
int netif_receive_skb(struct sk_buff *skb)
{
    struct packet_type *ptype, *pt_prev;
    struct net_device *orig_dev;
    __be16 type;
    int ret = NET_RX_DROP;

    /* 略去一些代码 */
    rcu_read_lock();

    /* 第一步：处理 ptype_all 上所有的 packet_type->func() */
    list_for_each_entry_rcu(ptype, &ptype_all, list) {
        if (!ptype->dev || ptype->dev == skb->dev) {
            if (pt_prev)
                ret = deliver_skb(skb, pt_prev, orig_dev);
            pt_prev = ptype;
        }
    }

    /* 第二步：编译内核时选上 BRIDGE，会走网桥 */
    skb = handle_bridge(skb, &pt_prev, &ret, orig_dev);
    if (!skb)
        goto out;

    /* 第三步：选上 MACVLAN，会走 macvlan */
    skb = handle_macvlan(skb, &pt_prev, &ret, orig_dev);
    if (!skb)
        goto out;

    /* 第四步：按 skb->protocol 走 ptype_base */
    type = skb->protocol;
    list_for_each_entry_rcu(ptype,
            &ptype_base[ntohs(type) & PTYPE_HASH_MASK], list) {
        if (ptype->type == type &&
            (!ptype->dev || ptype->dev == skb->dev)) {
            if (pt_prev)
                ret = deliver_skb(skb, pt_prev, orig_dev);
            pt_prev = ptype;
        }
    }

    if (pt_prev) {
        ret = pt_prev->func(skb, skb->dev, pt_prev, orig_dev);
    } else {
        kfree_skb(skb);
        ret = NET_RX_DROP;
    }
out:
    rcu_read_unlock();
    return ret;
}

第一步：ptype_all 先过 #

ptype_all 是条链表，挂在上面的每个 packet_type 都要求看所有包。遍历时用 ptype->dev 过滤，空的表示全收，非空只收指定设备进来的包。

这里有个手法要注意：pt_prev 是延迟交付的。循环里并不立刻调当前节点的 func，而是先调上一个，把当前这个存起来，等下一轮再交。原因是 deliver_skb() 要加引用计数，每多一个消费者就多一份引用，最后一次交付不需要加，直接调 func 就行，省一次原子操作。

c
int deliver_skb(struct sk_buff *skb, struct packet_type *pt_prev,
                struct net_device *orig_dev)
{
    atomic_inc(&skb->users);
    return pt_prev->func(skb, skb->dev, pt_prev, orig_dev);
}

atomic_inc 是引用计数，调用方拿到的是一份独立引用，得自己负责还。这就是为什么抓包程序挂在 ptype_all 上不会影响正常收包：它拿的是副本引用，用完 kfree_skb() 只是减计数。ptype_all 为空时这段直接跳过，所以默认内核里抓包一开，收包路径就慢了那么一点。

第二步：网桥 #

c
skb = handle_bridge(skb, &pt_prev, &ret, orig_dev);
if (!skb)
    goto out;

handle_bridge() 是个包装，里面调 br_handle_frame_hook(skb)，钩子指向 br_handle_frame()。内核没编网桥模块时钩子是空的，这段什么也不干。网桥在这里把 skb->pkt_type 初始化成 PACKET_HOST 或 PACKET_OTHERHOST：目标 MAC 是本机的就是 HOST，是别人的就是 OTHERHOST，后者意味着要转发。返回 NULL 说明包被网桥吞了，不再往上走。二层桥转发的细节在《二层桥转发》里，这里只需要知道调用点在这儿。

第三步：macvlan #

c
skb = handle_macvlan(skb, &pt_prev, &ret, orig_dev);
if (!skb)
    goto out;

同一个套路，钩子指向 macvlan_handle_frame()。这一步会把 skb->pkt_type 再细化成 PACKET_BROADCAST、PACKET_MULTICAST、PACKET_HOST。macvlan 的场景是一张物理网卡上挂多个虚拟接口，每个有自己的 MAC，包进来先判断该交给哪个虚拟接口，交出去之后正常路径就看不见它了。VLAN 的源码分析在《VLAN 源码》。

第四步：按协议号分发 #

c
type = skb->protocol;
list_for_each_entry_rcu(ptype,
        &ptype_base[ntohs(type) & PTYPE_HASH_MASK], list) {
    if (ptype->type == type &&
        (!ptype->dev || ptype->dev == skb->dev)) {
        if (pt_prev)
            ret = deliver_skb(skb, pt_prev, orig_dev);
        pt_prev = ptype;
    }
}

if (pt_prev) {
    ret = pt_prev->func(skb, skb->dev, pt_prev, orig_dev);
} else {
    kfree_skb(skb);
    ret = NET_RX_DROP;
}

skb->protocol 是以太头里那个 16 位类型字段，0x0800 是 IP，0x0806 是 ARP。这些值由标准规定，不是内核随便定的。ntohs(type) & PTYPE_HASH_MASK 算出桶号，ptype_base 是个哈希表，不是数组也不是 switch。查表分两步：先定位桶，再在桶里的链表上比对 ptype->type == type。

为什么不用 switch-case？因为协议号是注册进来的，模块可以在运行时增删，哈希表能容纳这种动态性，switch 不能。匹配上的节点也不会被立刻调用，靠 pt_prev 递延到下一轮或函数末尾，末尾那一句才是真正的交付。

pt_prev 为空，说明四步走完没有一个协议认领这个包，这时 kfree_skb() 释放，返回 NET_RX_DROP。协议号不认识、或者设备被 ptype->dev 过滤掉了，都会走到这里。注意 kfree_skb() 的时机：skb 没进 socket 接收队列才在这里释放；如果进了，系统调用取包时才释放，这里的 kfree_skb() 只是把引用数减一。

四步的次序有讲究：

步 处理者 关注点 返回 NULL 的后果
1 ptype_all 链表 所有包，抓包用 不会返回 NULL，只是多份引用
2 handle_bridge() 二层转发、本机还是他机 网桥吞包，不再上送
3 handle_macvlan() 虚拟接口归属 macvlan 接管，不再上送
4 ptype_base[hash] 上层协议号 无协议认领，kfree_skb

抓包放在第一步，是为了让抓到的包完整、未被任何处理改动过。网桥放在协议分发之前，是因为二层转发根本不需要知道上层是 IP 还是 ARP。

以太头在哪剥的 #

这个问题看代码时容易卡住：netif_receive_skb() 处理的全是 ARP、IP 这些三层以上的协议，那二层头呢。答案在驱动里，调 netif_receive_skb() 之前，驱动要先做一次转换：

c
skb->protocol = eth_type_trans(skb, bp->dev);

eth_type_trans() 干三件事：把 skb->data 往后挪 14 字节（ETH_HLEN），跳过以太头；用 skb->mac_header 记住以太头的原位置，方便后续回溯；从以太头里取出类型字段，填进 skb->protocol，顺手判一下是不是广播或多播。

text
[ 以太头 14B ][ IP 头 ][ 载荷 ]
 ^              ^
 mac_header     data

挪完之后 skb->data 指向网络层头，所以进 netif_receive_skb() 的包，已经是「三层起点」的视角了。分工很清楚：驱动懂硬件，也懂以太网帧格式，剥头它来做；协议栈懂协议，按 skb->protocol 分发；中间交接的就是 netif_receive_skb()。VLAN 帧的 ETH_HLEN 是 18，eth_type_trans() 对 0x8100 有单独处理，会多跳 4 字节并把真实类型取出来。

八、协议分发：ptype_all 与 ptype_base #

两套注册表，分工完全不同。看代码时把这两张表混了，后面全乱。

ptype_base：哈希表，按协议号 #

ptype_base 是哈希桶数组，桶数由 PTYPE_HASH_SIZE 定，同号协议挂在同一个桶的链表上。

c
/* net/core/dev.c */
static struct list_head ptype_base[PTYPE_HASH_SIZE] __read_mostly;
static struct list_head ptype_all __read_mostly;

void dev_add_pack(struct packet_type *pt)
{
    int hash;

    spin_lock_bh(&ptype_lock);
    if (pt->type == htons(ETH_P_ALL))
        list_add_rcu(&pt->list, &ptype_all);
    else {
        hash = ntohs(pt->type) & PTYPE_HASH_MASK;
        list_add_rcu(&pt->list, &ptype_base[hash]);
    }
    spin_unlock_bh(&ptype_lock);
}

注册就这一个函数，干两件事：ETH_P_ALL 进 ptype_all，其他进 ptype_base 对应桶。这就是 ptype_all 的来历。

两张表的结构差异：

项 ptype_base ptype_all
形态 哈希表（数组加链表） 单向链表
索引 协议号低 4 位 无，全链遍历
挂谁 IP、ARP、IPv6、8021Q 等 AF_PACKET 抓包、ETH_P_ALL 套接字
收到哪些包 只有 ptype->type == skb->protocol 的 所有包，每个都复制一份
调用时机 第四步 第一步，最早
性能影响 按协议分流，开销可控 全链遍历加原子引用，钩子越多越慢

ptype_all 的语义就是「所有包复制一份给我」。tcpdump、AF_PACKET 抓包、部分网络监控都挂这里。它排在 ptype_base 之前，是为了拿到未经协议处理的原始帧。常见协议号：

值 宏 处理函数 所属模块
0x0800 ETH_P_IP ip_rcv() IPv4
0x0806 ETH_P_ARP arp_rcv() ARP
0x86DD ETH_P_IPV6 ipv6_rcv() IPv6
0x8100 ETH_P_8021Q vlan_skb_recv() VLAN
0x88CC ETH_P_LLDP lldp_rcv() LLDP
0x0003 ETH_P_ALL 各抓包者的 packet_rcv() AF_PACKET

同一个协议号的链表上可以挂多个节点，所以一个包能被多个处理函数看到。ptype->dev 是过滤条件：填了设备就只有那张网卡进来的包会交给它，空的表示所有网卡。

以 ARP 为例走一遍 #

ARP 模块的 packet_type 定义很朴素，arp_init() 里注册进 ptype_base。之后每个 skb->protocol == 0x0806 的包，第四步分发都会命中它，走 arp_rcv() → arp_process()。

c
static struct packet_type arp_packet_type __read_mostly = {
    .type = cpu_to_be16(ETH_P_ARP),
    .func = arp_rcv,
};

arp_process() 先解析报文字段，指针挨个挪：

c
arp = arp_hdr(skb);
/* ... */
arp_ptr = (unsigned char *)(arp + 1);

sha = arp_ptr;                 /* 发送端 MAC */
arp_ptr += dev->addr_len;
memcpy(&sip, arp_ptr, 4);      /* 发送端 IP */
arp_ptr += 4;
arp_ptr += dev->addr_len;      /* 跳过目标 MAC */
memcpy(&tip, arp_ptr, 4);      /* 目标 IP */

这是标准的 ARP 报文布局：硬件类型、协议类型、硬件地址长度、协议地址长度、操作码，然后是发送端 MAC、发送端 IP、目标 MAC、目标 IP。dev->addr_len 是以太网的 6，协议地址长度固定 4。

判断是请求报文，就去查路由表：

c
if (arp->ar_op == htons(ARPOP_REQUEST) &&
    ip_route_input(skb, tip, sip, 0, dev) == 0)

ip_route_input() 先查缓存，rt_hash(daddr, saddr, iif, rt_genid(net)) 算哈希，再沿 rt_hash_table[hash].chain 找。缓存项里带着源 IP、目的 IP、入口网卡三元组。缓存没有命中，或者指定跳过缓存，就走慢路径 ip_route_input_slow()，最终 fib_lookup() 给出 fib_result：

c
if ((err = fib_lookup(net, &fl, &res)) != 0)

查到了就把结果写回缓存：

c
hash = rt_hash(daddr, saddr, fl.iif, rt_genid(net));
err = rt_intern_hash(hash, rth, NULL, skb, fl.iif);

回到 arp_process()，路由项指向本机就说明该由本机应答：

c
if (addr_type == RTN_LOCAL) {
    /* ... */
    if (!dont_send) {
        n = neigh_event_ns(&arp_tbl, sha, &sip, dev);
        if (n) {
            arp_send(ARPOP_REPLY, ETH_P_ARP, sip, dev,
                     tip, sha, dev->dev_addr, sha);
            neigh_release(n);
        }
    }
    goto out;
}

先 neigh_event_ns() 更新邻居表，把请求方的 MAC 和 IP 记下来，再 arp_send() 回一个应答。回包走的是 dev_queue_xmit()，绕回本篇的发送路径。整条链在这里合上了：收包进 netif_receive_skb()，分发到 arp_rcv()，处理完构造应答，从 dev_queue_xmit() 出去。一个函数的入口和另一个函数的出口，中间隔着协议层。

九、NAPI 与新接口 #

老式接收的问题很直接：一个包一次中断。千兆线速小包跑满，每秒上百万个中断，CPU 全在进出中断，没空干活。NAPI 的思路是「中断只用来报信，干活靠轮询」：中断来了不处理包，只把设备挂进 poll_list，然后软中断统一批量取，取到没包可取了再把中断打开。

项 老式（netif_rx） NAPI
中断里干什么 分配 skb、拷数据、入 input_pkt_queue 只调 napi_schedule()
谁真正收包 process_backlog() 翻队列 驱动的 poll() 直接读硬件环
一次处理几个包 一个个进队列，逐个处理 批量，由驱动和 budget 决定
中断频率 每包一次 一批一次，负载高时中断可关
适用场景 低速设备、虚拟设备 高速网卡

NAPI 的收益不在「少一次中断」这么简单，真正的好处是缓存局部性和批处理：连续从同一个环里取几十个包，描述符和 skb 都在热缓存里。驱动程序还能灵活控节奏，负载大就多轮几次，没包可收就退出轮询、把中断打开，等下一次中断再进来。

调度链 #

c
/* 中断处理里，就这一句 */
napi_schedule(&napi->napi);

napi_schedule() 检查 napi->poll_list 是否已在链表上，不在就加进去，然后触发 NET_RX_SOFTIRQ。

c
static __latent_entropy void net_rx_action(struct softirq_action *h)
{
    struct softnet_data *sd = this_cpu_ptr(&softnet_data);
    unsigned long time_limit = jiffies +
        usecs_to_jiffies(netdev_budget_usecs);
    int budget = netdev_budget;
    LIST_HEAD(list);
    LIST_HEAD(repoll);

    local_irq_disable();
    list_splice_init(&sd->poll_list, &list);
    local_irq_enable();

    for (;;) {
        struct napi_struct *n;

        if (list_empty(&list)) {
            if (!sd_has_rps_ipi_waiting(sd) && list_empty(&repoll))
                goto out;
            break;
        }

        n = list_first_entry(&list, struct napi_struct, poll_list);
        budget -= napi_poll(n, &repoll);

        if (unlikely(budget <= 0 ||
                     time_after_eq(jiffies, time_limit))) {
            sd->time_squeeze++;
            break;
        }
    }
    /* 没跑完的重新挂回去 */
    list_splice_tail_init(&sd->repoll, &sd->poll_list);
}

三处细节。预算 budget 递减，napi_poll() 返回这一轮实际处理了多少个包，扣到 0 或超时就跳出，sd->time_squeeze++ 加一。time_squeeze 是个诊断指标，/proc/net/softnet_stat 第二列就是它，这个数一直涨说明软中断时间不够用，该调 netdev_budget、调 RSS 队列数，或者看是不是有单核在扛全部流量。没跑完的 napi_struct 挂回 poll_list，下次接着来，这就是为什么高负载下设备可以长时间不进中断：它一直在 poll_list 里被轮着。

驱动的 poll() 长这样，结构很固定：

c
static int my_poll(struct napi_struct *napi, int budget)
{
    int work_done = 0;

    while (work_done < budget) {
        /* 从描述符环取一个 */
        skb = ring_take(rx_ring);
        if (!skb)
            break;
        skb->protocol = eth_type_trans(skb, dev);
        napi_gro_receive(napi, skb);
        work_done++;
    }

    if (work_done < budget) {
        napi_complete_done(napi, work_done);
        /* 重新开中断 */
        网卡开中断();
    }
    return work_done;
}

work_done < budget 表示环已经取空，这批活干完了，调 napi_complete_done() 把自己从 poll_list 摘掉，再把网卡中断打开，下次有包进来重新走中断。反过来 work_done == budget 说明还没取完，什么都不做，poll_list 里留着，软中断下一轮继续。这就是自适应：负载高就不开中断，纯轮询。

现代接口的名字 #

内核演进后名字有一堆变体，认准层次就行。

接口 层次 用途
netif_rx() 最老 虚拟设备、低速路径，进 input_pkt_queue
netif_receive_skb() 主入口 单包进协议栈
netif_receive_skb_list() 主入口批量 一次交多个包，减少函数开销
napi_gro_receive() NAPI 内 先做 GRO 合并，再进协议栈
napi_consume_skb() 释放侧 批量回收，减少 kfree_skb 开销

napi_gro_receive() 里的 GRO 是另一层优化，方向与 GSO 相反：把多个同流小包合成一个大包再往上交，减少上层处理次数。发送侧 GSO 切，接收侧 GRO 合，两个方向对称。netif_receive_skb() 下面还压着一层 __netif_receive_skb_core()，第七章那段四步分发就住在里面，外层函数只负责 RPS、tracepoint 这些前后处理。

NET_RX_SOFTIRQ 在中断退出时执行。处理时间过长，内核线程 ksoftirqd/N 接管，避免把用户态进程饿死太久。top 里看到 ksoftirqd/0 占满一个核，八成是收包软中断堆在 CPU 0 上，查 smp_affinity 和网卡多队列，把中断打散。

十、sk_buff 在两个路径中的变化 #

同一个 sk_buff，在两条路径上被改的字段完全不同。搞清楚谁改了什么，调 bug 时能少猜一半。

发送路径上的变化 #

阶段 字段 变化
ip_finish_output2() skb->data 往前挪 14 字节，headroom 里填以太头
neigh_output() skb->data 填目的 MAC
dev_queue_xmit() skb->data_len 线性化后归零，全部数据进主 buf
dev_queue_xmit() skb->ip_summed CHECKSUM_PARTIAL 时补算或标记硬件卸载
dev_queue_xmit() skb->tc_verd 打 egress 标记（开了 NET_CLS_ACT）
qdisc_restart() skb->queue_mapping 决定进哪个硬件子队列
dev_hard_start_xmit() skb->next GSO 分段后成为链
dev_hard_start_xmit() skb->users 抓包钩子存在时加一
驱动 无 只读，不改结构，直接映射 DMA

发送路径的核心动作是「加头」。每过一层往前挪一点 skb->data，头就长一点，到驱动手里 skb->data 指向以太头开头，skb->len 是整帧长度。headroom 是分配时预留的，不是临时挤出来的，这就是为什么越深的封装越费 headroom，隧道套隧道套多了会 pskb_expand_head() 重分配。

接收路径上的变化 #

阶段 字段 变化
驱动分配 skb->dev 指向收包的网卡
eth_type_trans() skb->data 往后挪 14 字节，跳过以太头
eth_type_trans() skb->mac_header 记住以太头位置
eth_type_trans() skb->protocol 填以太类型，0x0800/0x0806 等
eth_type_trans() skb->pkt_type 初判 HOST/BROADCAST/MULTICAST
handle_bridge() skb->pkt_type 细化为 PACKET_HOST / PACKET_OTHERHOST
handle_macvlan() skb->pkt_type 再细化为 BROADCAST/MULTICAST/HOST
deliver_skb() skb->users 每个消费者加一
协议处理 skb->data 继续往后挪，剥三层头
进 socket 队列 skb->users 保持，等系统调用取走

接收路径的核心动作是「剥头」。skb->data 一路往后走，mac_header 和 network_header 记着各路头的位置，随时能回指。两张表放一起看，规律很清楚：发送是 data 往前推并在空隙里填头，接收是 data 往后挪并把头位置记下来。

引用计数的两条线 #

skb->users 是整条路径上最要紧的一个字段，规则只有一条：谁持有一份引用，谁负责释放。

场景 users 变化 谁释放
单协议消费，无抓包 1 协议处理完 kfree_skb()
有 ptype_all 钩子 消费者数加一 抓包者释放自己那份
进 socket 接收队列 1 系统调用 recvmsg 取走后释放
发送成功进驱动 1 驱动发完后 dev_kfree_skb_irq()
发送失败 1 dev_queue_xmit() 内 kfree_skb()

计数错一次就是内存泄漏或者 use-after-free。skb->destructor 存着析构函数，sock_wfree 之类挂在这里，释放时顺手扣 socket 的写缓冲配额。

十一、追踪一个包的完整旅程 #

用一个具体场景把前面所有章节串起来。本机 192.168.1.20，网卡 eth0，网关 192.168.1.1，执行 curl http://192.168.1.10/，邻居表里已经有网关的 MAC。

发出去 #

  1. 应用调 connect()，TCP 三次握手，套接字层组包
  2. tcp_transmit_skb() 加 TCP 头，交给 ip_queue_xmit()
  3. IP 层查路由，找到出口 eth0、下一跳 192.168.1.1，加 IP 头
  4. ip_finish_output2() 查邻居表拿到 aa:bb:cc:dd:ee:ff，填以太头，skb->data 前移 14 字节
  5. 调 dev_queue_xmit(skb)，闸门在这里；GSO、线性化、校验和兜底依次过
  6. dev_pick_tx() 选中 txq[0]，取出 qdisc
  7. qdisc_enqueue_root() 把包放进 pfifo_fast 的 band 1，qdisc->q.qlen 加一
  8. qdisc_run() 抢 __QDISC_STATE_RUNNING 位成功，进 __qdisc_run()
  9. qdisc_restart() 出队拿到刚进去的 skb，加 HARD_TX_LOCK，查队列没停
  10. ptype_all 非空（假设开着 tcpdump），dev_queue_xmit_nit() 复制一份给抓包
  11. 不需要 GSO，调 e1000_xmit_frame()：映射 DMA、写描述符、敲门铃，返回 NETDEV_TX_OK
  12. qdisc_restart() 返回 qdisc_qlen(q) 为 0，__qdisc_run() 循环结束，清运行位，返回 NET_XMIT_SUCCESS
  13. 硬件把帧送上网线，完成后发中断，驱动 dev_kfree_skb_irq() 把 skb 挂进 completion_queue，触发 NET_TX_SOFTIRQ
  14. net_tx_action() 释放 skb

收回来 #

  1. 对端回包到达 eth0，DMA 写进接收环，硬中断
  2. 驱动中断处理里 napi_schedule()，触发 NET_RX_SOFTIRQ，中断退出
  3. net_rx_action() 取出 poll_list 上的 napi，预算 300
  4. e1000_poll() 从环里取包，eth_type_trans() 剥以太头，skb->protocol = 0x0800
  5. napi_gro_receive() 先试合并，合不了就调 netif_receive_skb()
  6. 第一步，ptype_all 链表遍历，tcpdump 的 packet_rcv() 拿到副本，users 加一
  7. 第二步，handle_bridge() 判断目标 MAC 是本机，pkt_type = PACKET_HOST，继续上送
  8. 第三步，handle_macvlan() 没有虚拟接口，原样返回
  9. 第四步，ptype_base[0x0800 & 15] 桶里找到 ip_packet_type，调 ip_rcv()
  10. ip_rcv() 校验、剥 IP 头、查路由，发现是本机，调 ip_local_deliver()
  11. 交给 TCP，tcp_v4_rcv() 找到对应 socket，skb 进接收队列，users 仍为 1
  12. 应用 read() 取走数据，kfree_skb() 生效，包的生命结束

二十六步，两个闸门在第 5 步和第 20 步。往前一步是协议栈，往后一步是设备。把这两步记住，再看任何抓包、任何 tcpdump 抓不到、任何 TX dropped，都有一张图可以对。

十二、易错点速查 #

这些是踩过的坑，按遇到频率排序。

现象 真实原因 查法
tcpdump 抓不到出方向的包 抓包点在 dev_queue_xmit_nit()，走的是 ptype_all 的发送分支；某些 offload 路径或 XDP 直通会绕过 换 tc 或 bpftrace 在 dev_queue_xmit 上打点
tcpdump 显示的包比实际大 GRO 合并了同流小包，抓包点在上层 ethtool -K eth0 gro off 对照
发了但网线上没有 dev_queue_xmit 返回成功只代表进了 qdisc 或驱动环，不代表上线 tc -s qdisc show，看 backlog 和 drops
TX dropped 一直涨 qdisc 满了，txqueuelen 太小或下游太慢 ip -s link show eth0，tc -s qdisc show
transmit queue timed out 发送环卡死，看门狗复位 dmesg 找 NETDEV WATCHDOG，查驱动
收包全堆在一个 CPU 中断没打散，RPS/RSS 没配 /proc/interrupts、/proc/net/softnet_stat
softnet_stat 第二列猛涨 软中断预算不够，time_squeeze 在涨 调 netdev_budget、加队列
改 netdev_max_backlog 没效果 只对老式 netif_rx 路径生效，NAPI 不走这个队列 看驱动是 NAPI 还是 netif_rx
抓包位置不同结果不同 ptype_all 在网桥和 macvlan 之前，看到的是原始帧 明确要抓「进协议栈前」还是「转发后」
虚拟设备报 Dead loop 隧道配置成环，包在设备间来回 dmesg 里的设备名，查路由和隧道配置
Virtual device asks to queue packet 无队列设备被要求排队，驱动或虚拟设备配置有问题 查该设备的 hard_start_xmit 实现
校验和字段是 0 CHECKSUM_PARTIAL 留给硬件算，抓包点太靠上 抓包时 ethtool -K eth0 tx off 对照
loopback 抓不到二层头 loopback_xmit() 里也调了 eth_type_trans()，但帧没有真实以太头 用 AF_PACKET 看，别指望有真实 MAC
kfree_skb 后崩溃 引用计数没加就多挂了一个消费者 查 deliver_skb 前后的 users

最后一条值得展开一句。ptype_all 上加钩子必须用 dev_add_pack()，让框架替你处理引用；自己手工往链表里塞节点，deliver_skb() 里的 atomic_inc 不会执行，后面必然出问题。

两个函数，一条收，一条发。内核网络子系统几万行代码，骨架就长在这两个函数上。看懂它们，剩下的都是枝叶。
