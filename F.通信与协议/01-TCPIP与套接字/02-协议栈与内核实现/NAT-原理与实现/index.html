本篇只讲一件事：NAT 怎么让一堆内网机器共用一个公网地址。

讲什么：NAT 到底改了报文的哪个字节；私有地址为什么存在；SNAT 与 DNAT 的方向差别；NAPT 怎么靠端口把一台公网 IP 撑成几千条连接；转换表长什么样；出方向与入方向各自怎么转；NAT 和路由谁先谁后；iptables 里怎么配；MASQUERADE 与 SNAT --to-source 该选哪个；NAT 破坏了什么，打洞为什么难；最后一页易错点。

不讲什么：Netfilter 钩子框架本身的实现（NF_HOOK、优先级注册、nf_hook_ops）归「Netfilter」那篇；conntrack 的内核数据结构（nf_conn、哈希桶、扩展区）只在这里提到字段名，不拆源码；IPv6 的 NAT66 不展开；GRE/VXLAN 这类隧道封装里的 NAT 行为不碰。

跨篇指路：一个包从网卡进来到 socket 的路径看「数据收发的内核路径」；包在协议栈里被哪些钩子拦下看「Netfilter」；NAT 改完地址后重新查表的那一步看「路由表详解与配置」；按源地址打标记再选出口的玩法看「策略路由与 ping 的执行过程」；网桥上的 ebtables 与 NAT 的边界看「二层桥转发的实现」。

一、NAT 解决什么问题 #

先把场景摆出来。你家路由器后面挂了五台设备，手机、笔记本、电视盒子，地址是 192.168.1.101 到 192.168.1.105。运营商只给了你一个公网地址，221.137.148.209。

这五台机器要访问 www.example.com。它们发出的 IP 包，源地址写的是 192.168.1.101 这种。这个地址在公网上没有任何意义——全球有无数个局域网在用同一个 192.168.1.101。包发出去，服务器的回包写目的地址 192.168.1.101，骨干网上的路由器一看，这地址我不认识，丢掉。连接建不起来。

NAT 干的就是这一件事：在网关把源地址换掉。换成 221.137.148.209 再发出去。回包自然回到网关，网关再把目的地址换回 192.168.1.101，交给内网那台机器。

到这儿听着简单。真正的问题是：换地址不是改一个字段那么轻松。

改的是两个头，不是一个 #

一个 TCP 报文长这样：

text
+------------------+------------------+------------------+
|      IP 头       |     TCP 头       |      载荷        |
|  源 IP / 目的 IP |  源端口/目的端口 |                  |
+------------------+------------------+------------------+

NAT 要改的位置有两处：

改哪里 具体字段 什么时候改
IP 头 源 IP 或目的 IP SNAT 改源，DNAT 改目的
传输层头 源端口或目的端口 多台内网机抢同一个公网 IP 时必须改
校验和 IP 头校验和、TCP/UDP 校验和 上面两处一改，必须重算

IP 头的校验和只覆盖 IP 头自己，改完地址顺手重算一遍就行，十六位反码求和，几行代码的事。

麻烦在传输层。TCP 和 UDP 的校验和不是只算自己的头，它算的是一个「伪首部」加整个报文：

text
伪首部（12 字节，不随报文发送，只参与校验和计算）
+--------+--------+--------+
| 源 IP（4 字节）          |
+--------+--------+--------+
| 目的 IP（4 字节）        |
+--------+--------+--------+
| 全 0   | 协议号 | TCP长度 |
+--------+--------+--------+

看见没有，伪首部里装着源 IP 和目的 IP。也就是说，只要 NAT 动了 IP 地址，TCP/UDP 的校验和就必然失效，必须重算。同理，只要 NAT 动了端口号，TCP/UDP 头本身变了，也要重算。

这一条推出来一个结论，是全篇的根：

NAT 设备必须看得懂传输层。它不能只当一个三层转发器。

三层转发器只看 IP 头，改完地址重算 IP 校验和就完事，根本不用管后面装的是什么。NAT 不行，它要伸进传输层头里去改端口、去重算校验和。所以 NAT 天然依赖「这个包是 TCP 还是 UDP，头有多长，端口在哪」。

加密协议为什么过 NAT 会出问题 #

顺着上面那条推下去，答案自己就浮出来了。

IPsec 的 ESP 模式，整个传输层头和载荷一起加密。NAT 设备拿到这个包，加密后的字节流在它眼里就是一坨随机数，它找不到 TCP/UDP 头在哪，更找不到端口在哪。端口改不了，校验和也没法重算。

更硬的一条：ESP 的完整性校验值（ICV）覆盖范围包含 IP 头里的地址字段。NAT 一改地址，接收端算出来的 ICV 和报文里带的对不上，包直接被丢。

AH 模式更彻底，它连 IP 头都纳入认证范围，过 NAT 必死。

所以现实里 IPsec 要过 NAT，靠的是 NAT-T（UDP 封装，把 ESP 塞进 UDP 500/4500 端口里），让 NAT 设备能看见一个 UDP 头。这是绕，不是解。

一句话收束本章：NAT 的本质是改 IP 头 + 改传输层头 + 重算校验和。改得动的前提是看得见。

二、地址短缺与私有地址 #

NAT 是被逼出来的。逼它的东西叫 IPv4 地址不够用。

IPv4 用 4 个字节表示一个地址，1 字节 8 位，所以是 4 × 8 = 32 位。32 位二进制能表示的组合数是：

text
2^32 = 4294967296

四十二亿九千四百九十六万七千二百九十六个。这就是 IPv4 的地址总数上限。

一个地址写成 221.137.148.209，只是为了人看着方便，它实际的二进制是：

text
221 . 137 . 148 . 209
11011101.10001001.10010100.11010001

把点去掉连起来，就是 11011101100010011001010011010001，一个 32 位的整数。点号纯粹是排版，没有技术含义。

IPv6 是 128 位：

text
2^128 = 340282366920938463463374607431768211456

这个数字大得没边，够用到天荒地老。但 IPv6 的铺开是另一条线的事。在 IPv4 还得继续跑几十年这个前提不变的情况下，剩下的办法只有一个：

让多台机器共用少量公网地址。

于是地址被劈成两半：能上公网的路由器认识的，叫公有地址；出了局域网就没人认的，叫私有地址。

五类地址的划分 #

IP 地址按第一个字节的高位分成五类：

类别 地址范围 默认掩码 可用地址数 用途
A 类 0.0.0.0 – 127.255.255.255 255.0.0.0 16777216 超大型网络
B 类 128.0.0.0 – 191.255.255.255 255.255.0.0 65536 中型网络
C 类 192.0.0.0 – 223.255.255.255 255.255.255.0 256 小型网络
D 类 224.0.0.0 – 239.255.255.255 无 无 组播
E 类 240.0.0.0 – 255.255.255.255 无 无 科研保留

A、B、C 三类是能分配给主机用的。D 类专供组播，E 类留作研究，这两类不能当单播地址配到网卡上。

127.0.0.1 单独拎出来说：这是环回地址，永远指向本机，走的是 loopback 接口，包不出网卡。抓包调试本地服务时看到的就是它。

私有地址的三段 #

私有地址是从 A、B、C 三类里各划走一块，专门留给内网：

类别 私有地址范围 说明
A 类 10.0.0.0 – 10.255.255.255 只有网络号 10 这一段，一个 /8，容量最大
B 类 172.16.0.0 – 172.31.255.255 占用 172.16 到 172.31 共 16 个 B 类网络号
C 类 192.168.0.0 – 192.168.255.255 占用 192.168.0 到 192.168.255 共 256 个 C 类网络号

这三段地址在全球范围内被无数个局域网反复复用，互不冲突，因为它们从来不出局域网。私有地址不用向任何人申请，随便用。

对应的，公有地址就是这三段之外的部分：

text
1.0.0.0      ~ 9.255.255.255
11.0.0.0     ~ 126.255.255.255
128.0.0.0    ~ 172.15.255.255
172.32.0.0   ~ 191.255.255.255
192.0.0.0    ~ 192.167.255.255
192.169.0.0  ~ 223.255.255.255

可以看出来，这张表就是在 A、B、C 三类的完整范围里，把三段私有地址挖掉之后剩下的部分。公有地址在全球唯一，用了别人的就冲突，所以必须申请。

为什么内网要用私有地址 #

假设一个网络里有 400 台主机。分一个 C 类网段，256 个地址不够；分一个 B 类网段，65536 个地址，400 台机器用掉 0.6%，剩下的全浪费。这个取舍在地址紧张的年代是不能接受的。

用私有地址就没这个问题。选哪一段只看内网主机有多少：几十台用 192.168.1.0/24，几百台用 172.16.0.0/16，上千台用 10.0.0.0/8。整个网络对外只共享一个（或少数几个）公网地址。

再往深一层看，私有地址带来三样东西：

  1. 省地址。几十台甚至几千台机器共用一个公网 IP，把 IPv4 的寿命硬生生拉长了几十年。
  2. 内部结构不外露。外部只能看到网关那一个地址，内网有多少台机器、怎么编址，外面看不到。
  3. 换运营商不用改内网。公网地址变了，内网地址一个都不用动。

代价也埋在这里，第十章慢慢算。

三、SNAT 与 DNAT #

按改哪个地址分，NAT 只有两种。所有花哨的名字都是在讲这两种的组合。

SNAT（Source NAT）改源地址。 内网机器往外发，网关把源地址换成自己的公网地址。这样回包的目的地址就是网关，网关能收到，也能记住该还给谁。

DNAT（Destination NAT）改目的地址。 外网请求进来，网关把目的地址换成内网某台服务器的地址。这样包就转进了内网。

两个方向，一句话记住：

SNAT 管出去，DNAT 管进来。

方向对照 #

维度 SNAT DNAT
改哪个字段 源 IP（+ 源端口） 目的 IP（+ 目的端口）
方向 内网 → 外网 外网 → 内网
触发时机 包发出之前 包进入内网之前
在 iptables 的位置 POSTROUTING PREROUTING
转换发生点 路由决策之后 路由决策之前
典型用途 共享上网、数据伪装 端口映射、负载均衡、透明代理
回程怎么转 查表把目的地址改回内网 查表把源地址改成网关

转换表的方向是反的 #

这是最容易绕晕的一处，单独拎出来讲。

SNAT 在出方向记下的是：

text
内网 192.168.1.101:51234  →  公网 221.137.148.209:40001

回程包进来，目的地址是 221.137.148.209:40001。网关拿这个当键去查表，查出对应的内网地址，把目的地址改回去。注意：去的时候改源，回来的时候改目的，改的字段换了。

DNAT 反过来。入方向记下的是：

text
公网 221.137.148.209:8080  →  内网 192.168.1.50:80

回程包从内网服务器发出，源地址是 192.168.1.50:80。网关拿这个当键去查表，把源地址改回 221.137.148.209:8080 再发出去。去的时候改目的，回来的时候改源。

去方向改 回方向改
SNAT 源地址 目的地址
DNAT 目的地址 源地址

记住这张表就够了：NAT 是一次有状态的、可逆的改写。去方向改哪个字段，回方向就改另一个字段。

三种 NAT 类型 #

按「公网地址怎么分配」再分一层，是三种：

静态 NAT（Static NAT）：内网一台主机的私有地址，永久绑定到外网一个合法地址。一对一，固定不变。配置最简单，一台内网主机独占一个公网 IP。

动态地址 NAT（Pooled NAT）：外网侧准备一池合法地址，内网主机要出去时，从池里临时借一个，用完还回去。这就是「地址池」。适用于拨号场景，也适用于远程接入——用户连上来时分配一个，断开时释放，留给下一个人用。

NAPT（Network Address Port Translation）：把内网地址映射到外网同一个 IP 的不同端口上。多对一。这是家用网关和小型办公网络里跑的那种。

类型 映射关系 靠什么区分 需要几个公网 IP
静态 NAT 一对一，固定 IP 地址本身 每台内网机一个
动态地址 NAT 一对一时租用 IP 地址本身 少于内网机数量
NAPT 多对一 IP 地址 + 端口号 一个

静态 NAT 和动态地址 NAT 只动 IP 地址，不动端口。NAPT 必须动端口——因为多台内网机挤在同一个公网 IP 后面，光靠 IP 已经分不出谁是谁了。

静态 NAT 贵，一台内网机吃掉一个公网 IP，地址紧张的年代没人这么用。动态地址 NAT 稍微省一点，但同一时刻能上网的机器数受地址池大小限制。NAPT 一个地址撑起整个局域网，这才是它变成默认选择的原因。

两个被反复提起的应用 #

数据伪装：把内网包里的地址改成统一的对外地址，内网主机不直接暴露在公网上。共享上网就是它的副产品——一台机器拨号上网，全家设备借这个连接出去。

端口转发：内网主机对外提供服务时，它拿的是私有地址，外网访问不到。必须在网关上做映射，把落到某个公网端口的数据包转给内网那台机器。这是 DNAT 最典型的用法。

还有三个用法：负载平衡（用 DNAT 把连接重定向到随机选定的服务器）、失效终结（路由器发现关键服务器当机，用 DNAT 把连接转到备份机）、透明代理（把去往互联网的 HTTP 连接重定向到本地代理，缓存数据、过滤请求）。前两个是 DNAT 在四层做分发，第三个是 DNAT 改目的地址把流量拐去代理。原理上都归到前面那张表，只是换了个用法。

四、NAPT：端口复用 #

先看不改端口行不行。

内网只有一台客户机 192.168.1.101 访问 Web Server。网关做 SNAT，把源地址换成 221.137.148.209，回包回来再改回去。一对一，全程只需要动 IP 地址，端口原样保留，工作正常。

现在内网有两台，Client A 和 Client B，同时访问同一台 Web Server。两个包都做了 SNAT，源地址都变成 221.137.148.209。服务器回两个包，目的地址都是 221.137.148.209。网关收到，傻了——这两个包该给 A 还是给 B？

IP 地址这一层的信息已经用完了，区分不出来。

办法是把端口也纳入转换。

text
Client A  192.168.1.101:51234  →  221.137.148.209:40001
Client B  192.168.1.102:51234  →  221.137.148.209:40002

网关在转换表里加一列端口。回包的目的端口是 40001，查表知道是 A；是 40002，知道是 B。区分开了。

还有一种情况：两台客户机的源端口恰好一样（上面这个例子就是，都是 51234）。那么 SNAT 的时候，源 IP 要改，源端口也要改，两个字段一起动。改完再重算 TCP 校验和。这就是 NAPT 名字里「Port」的含义——它不只换地址，还换端口。

端口复用的账 #

一个公网 IP 能撑多少条连接？理论上，源端口是 16 位，范围 1 到 65535。TCP 和 UDP 的端口空间独立，所以一个 IP 上有 65535 × 2 个可用的映射位。

实际远达不到这个数。原因有几条：

  • 一部分端口被系统保留或已被占用（比如网关自己要往外发连接）。
  • 端口分配要避开还在 TIME_WAIT 状态的旧连接，不能立刻复用。
  • 每个映射都要占一条 conntrack 表项，表项有上限，内存也有上限。
  • 同一目标 IP + 目标端口的组合下，端口冲突的概率随连接数上升。

所以真实设备上，一个公网 IP 撑几千条并发连接是常态，撑几万条要看内存和表容量配置。这个数字因设备而异，跟内核版本、nf_conntrack_max 的设置、内存大小都有关，没有一个通用的常数。

NAPT 的位置 #

NAPT 是使用最普遍的一种转换方式，家用网关（HomeGW）主要就用它。它又分成前面说的 SNAT 和 DNAT 两个方向。

NAPT 与动态地址 NAT 的差别在这里：动态地址 NAT 给每个内网 IP 分配一个临时的外部 IP，一对一；NAPT 把内部连接映射到外部网络中的一个单独的 IP 地址上，同时在该地址上加一个由 NAT 设备选定的端口号。

在 Internet 上看，所有不同的信息流都像是从同一个 IP 发出来的。这个特性在小型办公室里非常实用：从 ISP 申请一个 IP，多条连接全走 NAPT 出去。

还有一个细节：许多 SOHO 远程访问设备支持基于 PPP 的动态 IP 地址。这种情况下 ISP 甚至不需要支持 NAPT，多个内网 IP 也能共用一个外部 IP 上 Internet。代价是信道会有一定拥塞，但省下的上网费用和好管理这两点，让 NAPT 依然划算。

五、NAT 的转换表 #

NAT 不是无状态改写。改了源地址就得记住原来是什么，否则回包来了不知道还给谁。这份记忆就是转换表。

在 Linux 里，这份记忆由 conntrack 子系统维护。它不是 NAT 专用的——防火墙的状态检测也读同一份表。

一条表项长这样，这是 /proc/net/nf_conntrack 的真实格式：

text
tcp 6 431990 ESTABLISHED src=192.168.1.101 dst=202.20.65.4 sport=51234 dport=80
    src=202.20.65.4 dst=221.137.148.209 sport=80 dport=40001 [ASSURED] mark=0 use=1

一行里塞了两组四元组：前一组是原始方向（内网机器发起时的样子），后一组是应答方向（经过转换之后，外部看到的样子）。中间那个 6 是协议号（TCP 是 6，UDP 是 17）。ESTABLISHED 是状态，431990 是这条表项还剩多少秒过期。

表项字段 #

字段 含义 在本例中的值
协议 传输层协议号 tcp（6）
状态 连接所处的阶段 ESTABLISHED
超时 距离过期还剩多少秒 431990
原始 src / dst 内网主机看到的源、目的 192.168.1.101 / 202.20.65.4
原始 sport / dport 内网主机看到的源、目的端口 51234 / 80
应答 src / dst 外部世界看到的源、目的 202.20.65.4 / 221.137.148.209
应答 sport / dport 外部世界看到的源、目的端口 80 / 40001
ASSURED 已确认双向都通过 有
mark 防火墙标记，给策略路由用 0

查表用的键是五元组：

text
源 IP、源端口、目的 IP、目的端口、协议号

为什么是这五个？因为这五个字段唯一确定一条连接。两个包如果五元组完全相同，它们就属于同一条连接，走同一条表项，用同一套转换规则。反过来，任何一个不同，就是另一条连接，要另开一条表项。

这也解释了四层负载均衡为什么能做到「同一台客户端、同一个 VIP，不同请求分发到不同后端」——靠的是五元组里的端口或协议差异，加上哈希。

状态与过期 #

conntrack 给连接分了几个状态：

状态 含义
NEW 只看到去方向的第一个包，还没看到回包
ESTABLISHED 两个方向都见过包，连接确认建立
RELATED 和已有连接有关联的新连接，比如 FTP 的数据连接、ICMP 差错报文
INVALID 不属于任何已知连接，或者报文本身不合法
UNTRACKED 明确配置为不跟踪的流量

表项不是永久存在的。每种协议有自己的超时：

  • TCP 已建立连接，Linux 的默认值是 432000 秒，也就是 5 天。
  • TCP 的 TIME_WAIT、SYN_SENT 这些中间状态，超时短得多。
  • UDP 更短，因为没有连接的概念，只能靠「多久没包了就认为结束了」。
  • ICMP 的差错报文挂在一个很短的超时上。

这些值都能通过 sysctl 调，路径在 net.netfilter.nf_conntrack_*_timeout_* 下面。调长能减少表项反复建立的开销，调短能更快回收表空间。哪个合适，看你网关上的连接模式——短连接多的场景，把 TCP 已建立的超时调成 5 天是纯浪费。

表容量同样可调，net.netfilter.nf_conntrack_max。这个数取多大，取决于内存和并发连接规模，没有一个放之四海皆准的值。表满了会出现什么，看第十二章。

表为什么必须双向 #

表项里存了两组四元组，不是一组。内网机器发出去的时候，网关按「原始 src + 原始 dst」匹配；回包进来的时候，按「应答 src + 应答 dst」匹配。两个方向的匹配键不同，所以两边都要存。

这也是 NAT 只能做在连接的第一个包上的原因。第一个包来了，查表查不到，新建一条表项，算出一个映射，把地址改掉。后面同一条连接的包，直接查表命中，照表项里的映射改，不用再跑一遍 NAT 规则。

六、出方向与入方向的转换 #

把前面那个例子完整走一遍。

拓扑是这样：

text
   私有网络                         NAT 网关                    公共网络
+--------------+                +----------------+           +--------------+
| 192.168.1.2  |---- 私有口 ----| 192.168.1.1    |           |              |
|  内网主机     |                |                |           | 202.20.65.4  |
+--------------+                |  202.20.65.5   |---- 公网口 |  Web Server  |
                                +----------------+           +--------------+

网关有 2 个网络端口。公网口的地址是统一分配的 202.20.65.5，私网口的地址是保留地址 192.168.1.1。

出方向：改源 #

内网主机 192.168.1.2 要向公网主机 202.20.65.4 发一个 IP 包。它构造出来的包是：

text
Dst = 202.20.65.4
Src = 192.168.1.2

这个包先到网关（因为网关是它的默认路由）。网关做三件事：

  1. 查 conntrack，查不到，新建一条表项。
  2. 把 IP 包的源 IP 换成网关自己的公网 IP。
  3. 重算 IP 头校验和（如果动了端口，还要重算 TCP/UDP 校验和）。

转发出去的包变成：

text
Dst = 202.20.65.4
Src = 202.20.65.5

这个包里已经不含任何私有网 IP 的信息。

回方向：改目的 #

Web Server 收到请求，构造响应包。它只知道请求来自 202.20.65.5，所以回包是：

text
Dst = 202.20.65.5
Src = 202.20.65.4

因为目的地址是网关的公网 IP，这个包会送到网关。网关拿到它，查 conntrack，命中刚才那条表项，知道这条连接对应内网哪台机器，于是把目的 IP 改回去：

text
Dst = 192.168.1.2
Src = 202.20.65.4

然后把包转发到私有网。内网主机收到，看到的是「服务器直接回给我了」，它不知道中间被人改过两次。

全程变化 #

阶段 源 IP 目的 IP 谁看到的
内网主机发出 192.168.1.2 202.20.65.4 内网主机
网关收到 192.168.1.2 202.20.65.4 网关
网关转发出去 202.20.65.5 202.20.65.4 公网、Web Server
服务器响应 202.20.65.4 202.20.65.5 公网、Web Server
网关收到回包 202.20.65.4 202.20.65.5 网关
网关转回内网 202.20.65.4 192.168.1.2 内网主机

对通信双方来说，这个转换过程是完全透明的。内网主机始终认为自己在和 202.20.65.4 直接通信，服务器始终认为自己在和 202.20.65.5 通信。

不做 NAT 会怎样 #

记住这一点：如果内网主机发出的请求包未经过 NAT，那么 Web Server 收到请求后，回复的响应包中目的地址就是私网 IP 地址，在 Internet 上无法正确送达，导致连接失败。

原因很直白。私网地址在全球被无数个局域网重复使用，骨干网的路由表里根本没有 192.168.1.0/24 这条路由——它不敢有，因为指向哪个方向都是错的。包到了运营商的设备上，查表查不到，回一个「网络不可达」，然后丢掉。

入方向：请求从外面进来 #

入方向和出方向是镜像的，但发起方换了。

外网某台机器要访问内网的一台 Web 服务器 192.168.1.50:80。它没法直接写这个目的地址，于是写的是网关的公网地址加一个约定好的端口：

text
Dst = 221.137.148.209:8080
Src = 203.0.113.7:41200

网关在 PREROUTING 上撞到这条规则，把目的地址换掉：

text
Dst = 192.168.1.50:80
Src = 203.0.113.7:41200

然后按 192.168.1.50 查路由，转发进内网。服务器看到的是「有人从 203.0.113.7 直接访问我」，它不知道外面还有个网关。

回包从服务器发出，源是 192.168.1.50:80，目的是 203.0.113.7:41200。网关查表，把源地址改回 221.137.148.209:8080，发到公网。外网客户端收到，认为自己在和 221.137.148.209:8080 通信。

七、NAT 与路由的关系 #

NAT 和路由不是两件平行的事，它们有严格的先后顺序，顺序错了就转不通。

一个包穿过 Linux 协议栈的 NAT 路径是这样：

text
收包
  ↓
PREROUTING 钩子   ← conntrack 在这里建表项；DNAT 在这里改目的地址
  ↓
路由决策（查路由表）  ← 按「改完之后」的目的地址查
  ↓
  ├─ 目的地址是本机 → 交给本地进程（INPUT）
  └─ 目的地址不是本机 → 转发（FORWARD）
        ↓
    POSTROUTING 钩子  ← SNAT / MASQUERADE 在这里改源地址
        ↓
      发包

四条钩子的分工：

钩子 在路由之前还是之后 NAT 在这里干什么
PREROUTING 之前 DNAT 改目的地址
INPUT 之后 不做 NAT
FORWARD 之后 不做 NAT（过滤在这里）
POSTROUTING 之后 SNAT / MASQUERADE 改源地址
OUTPUT 本机发出，路由之后、POSTROUTING 之前 对本机发起的连接做 DNAT

顺序为什么是这样 #

两个方向的原因完全不同。

DNAT 必须放在路由之前。 因为它改的是目的地址，而路由决策的依据就是目的地址。如果先查了路由，查出「这个包该从 eth0 转出去」，再去改目的地址，那这个路由结果是按旧地址算的，包就发错地方了。反过来先 DNAT，再查路由，按 192.168.1.50 查出来「从私网口出，下一跳直连」，转发才对。

SNAT 必须放在路由之后。 因为它改的是源地址。源地址不参与目的地的选路（除非你用策略路由按源地址匹配，见下一节），所以在哪改都不影响「包往哪发」。但改成什么地址，要看包从哪个口出去——MASQUERADE 就是靠这个：它必须知道出口网卡，才能取到出口网卡的地址。出口是路由算出来的，所以 SNAT 只能等路由算完。

一句话记：DNAT 在路由前，因为它改的字段正是路由要用的字段；SNAT 在路由后，因为它要用的信息正是路由算出来的结果。

改完地址要重新查路由 #

DNAT 改了目的地址，之前查过的路由结果就作废了。Linux 靠顺序规避：PREROUTING 改完之后，路由查找才真正发生。有一类场景会碰到二次查路由——本机发出的包被 OUTPUT 链上的 DNAT 改了地址（透明代理常这么干），改完得重新查出口，新地址走另一块网卡时路由结果会跟着变。

策略路由下的坑 #

常规场景里，源地址变了不影响转发。但只要上了策略路由，这条就不成立了。

策略路由的规则可以按源地址匹配：

text
ip rule add from 192.168.1.0/24 lookup 100

意思是「这 24 位的机器，查 100 号路由表」。问题在于，这个匹配发生在包进入协议栈之后、SNAT 之前——源地址还是 192.168.1.x，规则能命中。

如果这个包被转发出去，经过 POSTROUTING 做了 SNAT，源地址变成了 221.137.148.209。这时候再想按源地址匹配，就匹配不上了。

反过来，如果一条策略路由规则按「公网源地址」匹配，而实际到的包还是内网源地址（还没 SNAT），也匹配不上。

规则和 NAT 的先后顺序，必须心里有数：

匹配依据 在 SNAT 之前还是之后生效
源地址（内网段） 之前，能看到真实源地址
源地址（公网段） 之后，只能看到转换后的地址
目的地址（改过的） DNAT 之后，能看到内网真实目的
fwmark 看你在哪条链上打的标记，PREROUTING 打的早于 DNAT 之外的一切

多出口的网关最容易翻车：两条宽带，按源地址把不同楼层的机器分流到不同出口。这个场景不能让 NAT 抢在选路之前改源地址，否则分流规则全部失效。正确的做法是把两条出口做成两张路由表，规则里按内网的源地址匹配，NAT 的 -o 参数跟着出口网卡走。

八、iptables 里的 NAT #

iptables 把 NAT 规则单独放一张表，叫 nat 表。它有三条链：

链 对应钩子 用途
PREROUTING 路由之前 DNAT、端口映射、透明代理重定向
POSTROUTING 路由之后 SNAT、MASQUERADE
OUTPUT 本机发出 对本机发起的连接做 DNAT

三条链的规则是「谁先匹配谁生效」。同一张链里的规则按顺序从上往下走，命中一条 -j SNAT 或 -j DNAT 就终止，不再往下看。

先开转发 #

动手之前，这一条不做，后面配什么都是白配：

bash
sysctl -w net.ipv4.ip_forward=1

echo 'net.ipv4.ip_forward = 1' >> /etc/sysctl.d/99-forward.conf
sysctl -p /etc/sysctl.d/99-forward.conf

第一条临时开了，第二段写进文件让它开机还在。ip_forward 关着的时候，内核在路由阶段就把「不是本机的包」判掉，压根走不到 FORWARD 和 POSTROUTING。表现是：规则都配了，iptables -t nat -L 看着好好的，包就是不通，计数器一直是 0。这个坑踩一次就记住了。

配 SNAT #

内网 192.168.1.0/24 从 eth0 出去，源地址统一换成那个固定的公网 IP：

bash
iptables -t nat -A POSTROUTING -s 192.168.1.0/24 -o eth0 -j SNAT --to-source 221.137.148.209

拆开看：-s 限定内网源段，-o 限定出口网卡，-j SNAT --to-source 指定换成哪个地址。

配 MASQUERADE #

出口是 PPPoE 拨号，每次重拨地址都会变，干脆不写地址，交给它自己取：

bash
iptables -t nat -A POSTROUTING -s 192.168.1.0/24 -o ppp0 -j MASQUERADE

不用写地址，它从出口网卡上现取。

配端口映射 #

把公网的 8080 转到内网 Web 服务器的 80：

bash
iptables -t nat -A PREROUTING -i eth0 -p tcp --dport 8080 -j DNAT --to-destination 192.168.1.50:80

-i eth0 限定从哪块网卡进来，-p tcp --dport 8080 限定协议和端口，--to-destination 指定转到哪去。

端口范围一次转一段 #

20000 到 20100 这一百个端口整段转给同一台内网机器，端口保持不变：

bash
iptables -t nat -A PREROUTING -i eth0 -p tcp --dport 20000:20100 -j DNAT --to-destination 192.168.1.50

--to-destination 后面不写端口，就是端口原样保留。要挪端口，写成 --to-destination 192.168.1.50:20000-20100 显式指定一段。

地址池 #

SNAT --to-source 后面可以给一段地址，内核从一个池子里挑：

bash
iptables -t nat -A POSTROUTING -s 192.168.1.0/24 -o eth0 -j SNAT --to-source 221.137.148.209-221.137.148.215

这就是「在外部网络中定义一系列合法地址，用动态分配映射到内部网络」那一套。连接少的时候大家共享，连接多的时候摊到不同的公网 IP 上，单个 IP 的端口上限就被绕开了。

DNAT 做四层分发 #

同一个公网端口，按概率分给两台后端：

bash
iptables -t nat -A PREROUTING -i eth0 -p tcp --dport 80 -m statistic --mode random --probability 0.5 -j DNAT --to-destination 192.168.1.50:80
iptables -t nat -A PREROUTING -i eth0 -p tcp --dport 80 -j DNAT --to-destination 192.168.1.51:80

第一条以 50% 概率命中，剩下的落到第二条。这就是「负载平衡」的手工实现。

本机发出的连接也做 DNAT #

本机访问 80 端口的流量，拐到本地代理上：

bash
iptables -t nat -A OUTPUT -p tcp --dport 80 -j DNAT --to-destination 127.0.0.1:3128

注意落在 OUTPUT 链上。本机进程发出的包不走 PREROUTING，只在 OUTPUT 和 POSTROUTING 出现。透明代理要拦本机流量，就得配在这里。

看结果 #

三个命令，各看一层：

bash
iptables -t nat -L -n -v
conntrack -L
conntrack -L -p tcp --dport 80

第一条看规则命中了多少包，第二条看 NAT 之后的实际连接，第三条把范围收窄到某个具体端口。

-v 那一列 pkts 和 bytes 是关键。配了规则却不通，先看这里的计数器动不动。不动说明包没走到这条链，问题在路由或转发开关；动了但连接不通，问题在规则写错或者回程被拦。

只在第一个包上生效 #

nat 表的规则不是每个包都跑。连接的第一个包跑一次，之后同一条连接的所有包直接查 conntrack，按表项里的映射改。

这个特性带来两个后果。

一，nat 表的计数器不涨，不代表规则没生效。一条长连接跑了一小时，只有开头那一个包计过数。

二，改规则不影响已经建立的连接。你把 --to-source 从 A 改成 B，已经在表里的连接还是按 A 转，直到超时或者手动清表。要立刻生效：

bash
conntrack -F

这个命令会清空整张表，所有连接全部断开重连。生产环境上敲之前想清楚。

nft 时代，NAT 的动作改成 snat to 和 dnat to，挂在 nat 类型的链上，位置的语义不变：prerouting 做 dnat，postrouting 做 snat/masquerade。会了 iptables 那一套，换过去只是语法差异。

九、MASQUERADE 与 SNAT 的差别 #

两个动作改的都是源地址，结果一样。差别只在一处：源地址从哪来。

SNAT --to-source 的地址是你在规则里写死的常量。内核建表项时直接读这个值。

MASQUERADE 不带地址。内核建表项时，去查这个包从哪块网卡出去，再取那块网卡当前配的地址，拿它当源地址。

一个写死，一个现取。

为什么会有两个 #

因为家宽的地址是变的。

PPPoE 拨号，每次重拨运营商给的地址都会变。你在规则里写死 --to-source 221.137.148.209，一重拨，地址变成 221.137.148.211，规则还指着旧地址——包发出去源地址是个不属于你的地址，回包全丢。而且这个错很难查：规则看着在，计数器在涨，就是不通。

MASQUERADE 就没这个问题。重拨之后地址变了，下一条新连接的包进来，它照样去网卡上取当前地址，自动跟上。

机房里的固定 IP 反过来。地址永远不变，写死最省事，也省掉每次建连接时那次取址动作。所以：

家宽、PPPoE、动态地址，用 MASQUERADE；机房固定 IP，用 SNAT --to-source。

差别清单 #

维度 SNAT --to-source MASQUERADE
地址来源 规则里写死的常量 出口网卡当前地址
地址变了 要改规则，否则全断 自动跟上，无需干预
-o 出口参数 建议写，能收窄匹配范围 必须写，不然不知道去哪取地址
地址池 支持一段，--to-source A-B 只取一个地址，不支持池
每条新连接的开销 略低，直接读常量 略高，要先取一次出口地址
典型场景 机房、云主机、固定 IP 出口 家宽、PPPoE、4G/5G 路由

性能差在哪儿 #

MASQUERADE 的代价在「每条新连接」上，不在「每个包」上。连接建好之后，后面的包都查 conntrack，不再取地址。所以短连接密集的场景里差距被放大，长连接为主时差距可以忽略。出口是固定 IP 却用了 MASQUERADE，等于每条新连接白花一次取址——这就是「性能略好」的实际含义。

十、NAT 破坏了什么 #

互联网的设计原则叫端到端：网络中间只管转发，两端的任何主机都能直接连任何主机。NAT 把这个原则破了。

破的方式很具体，一共几条。

外部连不进内网 #

内网主机的地址在公网上不可达，外部主动发起的连接根本到不了它。要给外部提供服务，只能在网关上开一个洞——端口映射。这个洞必须提前配好，而且一个服务一个洞。

P2P 难了 #

两台都在 NAT 后面的机器想直连，谁都连不上谁。这是第十一章的话题。

载荷里带 IP 的协议失效 #

有些协议不老实。它们在应用层载荷里写着 IP 地址和端口，让对端「连这个地址」。

FTP 的 PORT 模式就是这样：客户端告诉服务器「你来连我 192.168.1.101:50000」。NAT 只改了 IP 头，载荷里那串字符原样过去。服务器照着这个私网地址去连，连不上。

需要 ALG（Application Level Gateway）来救。ALG 是一个协议感知的旁路模块，它盯着指定端口上的载荷，发现里面有私网地址就改成公网地址，回方向再改回去。Linux 的 nf_nat_ftp、nf_conntrack_ftp 就是干这个的，加载模块之后 FTP 才能过 NAT。

同一个坑埋着 SIP、H.323、RTSP、以及一堆老的游戏协议。ALG 是补丁，不是方案——它要解析载荷，加密了就废，协议改版就废，端口不标准就废。现在正经的做法是把这些协议换成不把地址写进载荷的版本，或者直接走 TLS 让 ALG 彻底放弃治疗。

ICMP 没有端口 #

ICMP 没有端口号，NAPT 那套「靠端口区分」的办法失效了。Linux 的处理是拿 ICMP 头里的 query id 当端口用。ping 出去的 Echo Request 带一个 id，conntrack 把它当作「端口」记进表项，回包按这个 id 找回来。所以多台内网机器同时 ping 同一个目标，NAT 必须改这个 id，不然分不清。

ICMP 差错报文（Destination Unreachable、Time Exceeded）更绕：它们本身不发起连接，是「关于某条连接的报错」。里面嵌着触发它的那个原始 IP 头。conntrack 得把内嵌的那个头挖出来，反查表项，才知道这个差错属于哪条连接，然后连内嵌头一起改。Linux 有个 nf_conntrack_icmp 专门处理这件事。

分片也受影响 #

NAT 要改端口，就得看到传输层头。但 IP 分片之后，只有第一片带传输层头，后面几片全是纯数据。后几片过 NAT 时设备找不到端口，只能按 IP 头做映射；同一个内网 IP 上多条连接分到不同端口时，后几片就没法判断自己属于哪条，还原回去的源端口是错的，接收端组装失败。所以很多 NAT 设备干脆对分片做特殊处理，或者直接丢——「大包过 NAT 容易出问题」，根子就在 PMTU 没协商好，中间一分片，NAT 就开始出错。

汇总 #

被破坏的东西 具体表现 补救
端到端可达 外部无法主动连内网 端口映射（DNAT）
双向发起 P2P 直连建不起来 打洞、STUN、TURN
载荷里的地址 FTP PORT、SIP、H.323 失效 ALG，或者换协议
无端口的协议 ICMP 没有端口可复用 用 query id 当端口
分片报文 非首片读不到端口 避免分片，靠 PMTU
加密载荷 ESP/AH 校验覆盖地址 NAT-T 把 ESP 塞进 UDP
可追溯性 服务器只看到网关地址 网关侧记 NAT 日志

十一、NAT 穿透与打洞 #

两边都在 NAT 后面的时候，谁也不能先连谁。这是死结吗？

不是。靠的是 NAT 的一个性质：表项是「谁先出去，就为谁开一条回来的路」。

A 要连 B。A 先朝 B 的公网映射地址发一个包。这个包会被 A 的 NAT 拦下来（因为对端地址没在表里），但它同时在 A 的 NAT 上建了一条表项，记下「A 的内网地址 ↔ A 的公网端口，对端是 B 的公网地址」。从这一刻起，从 B 的方向发回 A 的包就能穿过 A 的 NAT 了。

B 那边做同样的动作。两边各朝对方发几个包，两边的表项都建好，路就通了。这就是打洞。

前提只有一个：双方得先知道对方的公网映射地址。这个信息靠第三方服务器给，那个服务器叫 STUN。

四种 NAT 行为 #

打洞能不能成，取决于 NAT 有多「严」。按严格程度分四类：

类型 行为 打洞难度
全锥形（Full Cone） 内网某地址端口映射到一个公网端口后，任何外部地址都能通过这个端口进来 最容易
地址受限锥形（Restricted Cone） 只有内网先主动发过包的那个外部 IP 才能进来 容易
端口受限锥形（Port Restricted Cone） 只有内网先主动发过包的那个外部 IP + 端口 才能进来 中等
对称 NAT（Symmetric） 每条新连接换一个新的公网端口，同一个内网端口对不同目标是不同映射 很难

对称 NAT 是打洞的死敌。A 通过 STUN 服务器知道了自己的映射端口是 40001，这个 40001 只对 STUN 服务器成立。A 换成朝 B 发包，NAT 给它换了个 40002。B 拿到 40001 去打，打不进去。两边互相拿到的都是过期信息。

家用宽带大多是锥形（前三种之一），对称 NAT 主要出现在企业网络、部分移动网络和云环境里。

STUN、TURN、ICE 三个角色 #

名字 干的事 什么时候用
STUN 告诉客户端「你在公网上看起来是 1.2.3.4:40001」 拿到自己的公网映射地址
TURN 一个中继服务器，双方都把包发给它，由它转发 打洞失败时兜底
ICE 把 STUN 和 TURN 的候选地址全试一遍，挑能通的那条 实际部署时的统一框架

ICE 的工作方式很朴素：把所有能想到的地址对都列出来（本机地址、STUN 拿到的公网映射、TURN 中继地址），两两组合逐个试连通性，谁先通就用谁。先试直连，不通再降级到中继。WebRTC 里的音视频通话就是这个流程。

代价也得说清楚：走 TURN 中继，带宽全压在服务器上，延迟还多一跳。所以能打洞成功就是省钱。TCP 打洞比 UDP 难得多，因为 TCP 的状态机不接受「凭空来一个包就算连上」，而且 NAT 对 TCP 表项的超时管得更严。实际工程里基本是 UDP 打洞，TCP 走中继。

十二、易错点速查 #

最后把踩过的坑堆在这儿，配规则之前扫一眼。

现象 根因 处理
规则全配了，包就是不通，计数器为 0 net.ipv4.ip_forward 是 0 sysctl -w net.ipv4.ip_forward=1
DNAT 配了，外网能连进来，内网自己用公网地址访问不了 回程经过网关但没做 SNAT，服务器直接回给内网客户端，源地址对不上 加一条 hairpin NAT（对 -s 内网 -d 内网 的流量也做 SNAT）
端口映射生效了，但只有第一个包过规则 nat 表只处理连接首包，后续走 conntrack 属正常行为，别指望计数器跟着涨
改了 --to-source，老连接还是旧地址 已在 conntrack 表里的表项不重算 conntrack -F 清表（会断所有连接）
重拨之后全网断 用了 SNAT --to-source 写死了旧地址 换 MASQUERADE，或者脚本里跟着改规则
多出口网关，分流规则失效 按源地址匹配的规则和 SNAT 抢顺序 规则看内网源地址，NAT 的 -o 跟出口走
FTP 能登录不能列目录 PORT 模式把私网地址写进载荷 加载 nf_conntrack_ftp / nf_nat_ftp
大包传输失败，小包正常 分片之后非首片没有端口信息 修 MTU / PMTU，别让中间设备分片
内网两台机器同时 ping 同一目标，一台不通 没开 ICMP 的 id 转换 加载 nf_conntrack_icmp
conntrack 表满，新连接全丢 nf_conntrack_max 太小，或者短连接堆积 调大上限，缩短 nf_conntrack_tcp_timeout_*
抓包看内网 IP 出现在公网上 抓包点选错了，或者真没做 NAT 在网关两侧分别抓，对比源地址
服务器日志里全是同一个 IP 这是 NAT 的正常结果 让网关把源端口和真实源地址一起记日志

一，不通的时候先判断「包到没到 NAT」。 在网关内网口和外网口各抓一次。两个口都有包，是转换或回程的问题；只有内网口有，是规则没匹配上；两个口都没有，问题在更前面（路由、转发开关、ARP）。

二，永远记住 NAT 是有状态的。 去方向怎么改，回方向就照着表反着改。表项在，连接就在；表项没了，连接就断。所有「莫名其妙断流」的问题，先怀疑表项超时或者被冲掉。

NAT 这一层没有魔法。它做的就是改两个头的字段，重算校验和，再记住自己改了什么。把这四句话记住，剩下的都是细节。
