开篇先把边界划清楚。

这一篇讲什么：Wireshark 抓到的包，从以太网帧头一路读到 TCP 头。每个字段在界面上落在哪一行、这个值说明了什么、看到这个值该往哪儿想。重点不是协议教科书，而是「你盯着一个真实抓下来的包，怎么把它读明白」。

这一篇不讲什么：不讲协议为什么这么设计，不讲套接字怎么调，也不讲内核里 tcp_v4_rcv 之后发生了什么。协议栈分层与收发路径在同目录的《网络协议栈架构与分层》《数据包收发路径》里，那些东西抓包抓不出来。

跨篇指路：

  • 想从编程视角看「报文长什么样才能理解收发」，看《01-套接字编程基础/协议分析与报文格式》。那篇的落点是 send/recv 怎么和报文边界对上，本篇的落点是抓到的字节怎么逐字段拆。
  • 链路层、网桥、VLAN 的帧结构，看同目录《链路层与网桥》《VLAN 原理》。
  • 路由表与转发决策，看《路由表》《策略路由》。抓包只能看到「包从哪个口出去了」，看不到「为什么选这个口」。

一、抓包能解决什么问题 #

先把一句话摆在最前面：抓包的价值是看到真实发生的字节，而不是相信文档。

文档写的是「应该」。内核写的是「实际」。这两者之间永远有缝。RFC 说 TCP 首部 20 字节，你的抓包里却是 32 字节，因为时间戳选项默认开着。RFC 说 UDP 校验和可选，抓包里一堆 0x0000，那是不算校验和的意思。教科书说 MSS 默认 536，抓包里 SYN 报的是 1460。你按文档去推，推出来的结论和线上跑的不是一回事。

缝在哪里，只有抓包能告诉你。

1.1 文档和实现常见的几处出入 #

下面这些，都是「照文档理解会错，照抓包理解才对」的典型。

现象 文档怎么说 抓包看到什么 为什么会差
TCP 首部长度 20 字节 32 字节 Linux 默认开 net.ipv4.tcp_timestamps=1，多了 12 字节选项
TCP 窗口值 16 位，最大 65535 抓到 501、29200 这类值 窗口扩大选项生效后，真实窗口 = 值 << 移位
UDP 校验和 可选项 大量 0x0000 值为 0 表示发送方没算校验和，不是算出来等于 0
IP 首部校验和 必须正确 一片 incorrect 网卡 checksum offload，抓包点在网卡算之前
TTL 初值 64 128、255 都有 初值由发送端自己定，Windows 用 128
MSS 默认 536 1460、1452 实现按出口 MTU 反算，不是用默认值
分片 超 MTU 就分 线上看不到分片 发送侧 GSO/TSO 把分片推迟到网卡
TCP 选项顺序 未规定 SYN 里 NOP 数量对不上 选项按内核版本排列，NOP 只用于 4 字节对齐

这张表就是本篇存在的理由。你看文档学「协议是什么」，你看抓包学「这台机器上的协议长什么样」。

1.2 抓包能回答的问题 #

你想知道 抓包怎么看
包到底发出去没有 抓出口网卡，按 ip.addr 过滤
对端回没回 看反向的包在不在同一个 tcp.stream 里
是谁先断的 找第一个 RST 或 FIN，看方向
卡在哪一跳 看 TTL 逐跳递减，配合 ICMP 超时
重传了几次 tcp.analysis.retransmission 过滤计数
应用层发了多少字节 tcp.len 求和，不是看 frame 长度
窗口是不是被压到 0 tcp.window_size == 0
是不是 MTU 问题 看大包有没有回，小包通不通

1.3 抓包点决定你看到什么 #

同一个包，在不同位置抓，看到的内容不一样。这一点比字段定义重要。

text
send() → TCP 分段 → IP 加头查路由 → 网卡 offload → 物理链路
          ↑抓这里     ↑抓这里        ↑抓这里        ↑线上真正的字节

三个结论。

第一，tcpdump -i any 抓的是内核协议栈里的一份副本，不是线上的电信号。网卡 offload 干的活（算校验和、拆大包）这份副本上看不到。

第二，自己发的包抓出来校验和是错的、长度超过 MTU，先怀疑 offload，不要怀疑协议栈写错了。

第三，抓别人机器的流量要靠交换机端口镜像，或者 hub。普通交换机不会把别人的包送到你的网口。

1.4 抓包抓不到的东西 #

抓包有边界，得认。

  • 加密流量只能看到 TCP 头，看不到应用层内容。TLS 之后全是密文。
  • 内核丢包抓不到。包在 netif_receive_skb 之后被 qdisc 丢掉，抓包点在上游，你只看到它进来了。
  • 时间戳精度有限。普通网卡微秒级，高精度要硬件时间戳。
  • 抓包本身有开销。高pps场景下抓包进程抢 CPU，抓出来的时序已经变形。

二、Wireshark 的安装与配置 #

Wireshark 装起来不费事，费事的是权限。装完打开一片空白、网卡列表里什么都没有，是这个原因占多数。

2.1 各平台的装法 #

平台 命令或方式 附带要装的东西
Windows 官网下载安装包 Npcap，随安装包一起勾选
macOS brew install --cask wireshark 首次运行要允许系统扩展
Debian / Ubuntu sudo apt install wireshark 安装过程弹窗问非 root 抓包权限
CentOS / RHEL sudo dnf install wireshark 权限得单独处理

Windows 上 Wireshark 只负责解析，真正从网卡取字节的是 Npcap。Npcap 没装上，Wireshark 就是个空壳。安装向导里那个「Support raw 802.11 traffic」的勾，做无线抓包才需要。

2.2 装完看不见网卡 #

Linux 下用普通账号启动，界面上给出这一句：

text
没有接口可以用于在当前配置的系统中进行捕获。

换成 root 启动就能看到 eth0，那就可以确定是权限问题，跟网卡驱动、跟内核模块都没关系。

Wireshark 是前端加后端的结构：wireshark 是图形界面，dumpcap 才是真正打开网卡取包的程序。界面有没有权限不重要，dumpcap 有没有权限才重要。

2.3 六步把权限配好 #

按顺序执行。

bash
sudo groupadd wireshark                                   #1 建组
sudo usermod -a -G wireshark "$USER"                      #2 把当前用户加进组
sudo chgrp wireshark /usr/bin/dumpcap                     #3 属组改掉
sudo chmod 750 /usr/bin/dumpcap                           #4 只给属主属组执行
sudo setcap cap_net_raw,cap_net_admin=eip /usr/bin/dumpcap #5 发两项能力
getcap /usr/bin/dumpcap                                   #6 验证

第六步的输出应该是 /usr/bin/dumpcap cap_net_admin,cap_net_raw=eip。改完退出登录再进来，组关系才落到会话上。用 id 看一眼，输出里带 wireshark 就对了。

2.4 为什么是这两项能力 #

抓包要干两件事，对应两项能力。

能力 干什么 缺了会怎样
cap_net_raw 打开原始套接字，拿链路层的原始帧 抓不到完整以太网头
cap_net_admin 切混杂模式、改抓包参数 混杂模式打不开

能力发给 dumpcap，不发给人。这样 GUI 仍然以你的身份跑，解析一个构造过的畸形包，最多把你的账号坑掉，不会直接交出 root。

chmod 4755 那种 SUID 写法别用在 dumpcap 上。SUID 给的是完整的 root 权力，capabilities 只给点名的那几项，粒度差一个量级。

2.5 首次启动要确认的三处 #

位置 选什么 判断标准
网卡列表 承载业务的那一块 选中后下面会显示这块网卡的 IP
Promiscuous 默认勾着 网卡把不是发给自己的帧也收上来
Snaplen 大流量场景调小 每帧只留前 N 字节，省内存和写盘

网卡选完看不到 IP，说明这块口没起来，抓下去也抓不到东西。

混杂模式有个边界要认：它让网卡收下所有到达本口的帧，可交换机按 MAC 表转发，A 发给 B 的帧压根不会出现在 C 的口上。想抓别人的流量，去交换机上配端口镜像（SPAN），或者串一个 TAP。勾混杂模式解决不了这件事。

2.6 界面上的按钮 #

抓包工具条从左到右：列出所有网卡、打开抓包选项、重新开始、停止、清空、重启抓包。

日常只用两个。抓包选项——在这里选网卡、写捕获过滤器，然后点 Start。停止——抓够了就按，别让它一直挂着跑。

清空那个按钮值得记：抓久了包列表会拖慢界面，清掉再抓比重新开一个进程省事。

抓完要交给别人分析，File → Save As 存 pcapng；要跨老工具用，存 pcap。

2.7 tshark 和图形界面共用一套权限 #

tshark 和 dumpcap 走同样的权限检查。给 dumpcap 配好能力之后，tshark -i eth0 用普通账号也能跑，不用 sudo tshark。反过来，tshark 报 permission denied 的时候，先去查 getcap /usr/bin/dumpcap，别急着往命令前面加 sudo。

三、Wireshark 的界面与常用操作 #

3.1 三栏结构 #

打开一个包，界面固定是这三块。

text
Packet List    一行一个包：No./Time/Source/Destination/Protocol/Length/Info
Packet Details 树形按层折叠：Frame → Ethernet II → IP → TCP → 应用层
Packet Bytes   十六进制 + ASCII，选中哪行高亮哪段

Details 面板的层级就是协议栈的层级，从上往下：物理帧 → 以太网 → IP → TCP/UDP → 应用层。点开哪一层，Bytes 面板就高亮那一层对应的字节。这是读包最省力的动作：先看树，再看高亮。

3.2 Packet List 的列 #

列 含义 容易看错的地方
No. 帧序号 不是 TCP 序号，两个完全无关
Time 相对第一帧的时间 默认相对，不是绝对时间
Source / Destination 网络层地址 二层地址要展开看 Ethernet 头
Protocol 最高层协议 显示的是 Wireshark 解析到的最高层
Length 帧总长度 含二层头，不含 FCS
Info 摘要 各协议自定义，TCP 这里是「端口 → 端口 [标志] Seq Ack Win Len」

Info 列信息密度最高。TCP 那一行直接给你标志位、seq、ack、窗口、数据长度，多数问题只看这一列就够了。

3.3 常用操作 #

操作 快捷键 用途
开始/停止抓包 Ctrl+E 最常用的一个
重新开始 Ctrl+R 清空重抓，改过滤器后用
查找包 Ctrl+F 按字符串、十六进制、过滤器找
跳到指定帧 Ctrl+G 大文件里定位
标记帧 Ctrl+M 打上黑底标记，方便回看
跟随流 右键 → Follow → TCP Stream 看应用层完整会话
导出对象 File → Export Objects 从 HTTP 里捞文件
显示过滤 顶部输入框 见第四章

3.4 值得打开的统计面板 #

Statistics 菜单里这几个，比逐个翻包快得多。

  • Conversations：按会话聚合，直接看哪对 IP 流量最大、持续多久、传了多少字节。排故障先看它。
  • Protocol Hierarchy：协议占比，一眼看出是不是有人在传大文件。
  • Expert Information：Wireshark 自己给出的异常提示，重传、乱序、校验和错都在里面，这是最快的入口。
  • TCP Stream Graphs → Time-Sequence：把 seq 对时间画出来，斜率是吞吐，平台就是卡住，重传和零窗口在这种图上一眼能认。

默认配色已经带信息量，别忽略。黑色底是有问题的包（重传、校验和错、RST），红色是异常（RST、ICMP 差错），浅紫是 TCP 流，深蓝是 DNS。看着色先定位，再用过滤器精确筛。

3.5 命令行：tshark #

GUI 不适合远程和脚本。同一套引擎有命令行版本。

bash
tshark -i eth0 -f "tcp port 80" -c 100 -w /tmp/http.pcap          # 抓包存文件
tshark -r /tmp/http.pcap -Y "tcp.flags.syn==1 and tcp.flags.ack==0" \
  -T fields -e ip.src -e ip.dst -e tcp.srcport -e tcp.dstport     # 读文件筛字段
tshark -r /tmp/http.pcap -q -z io,phs                            # 协议占比
tshark -r /tmp/http.pcap -q -z expert                            # 异常统计

-f 后面是捕获过滤器，-Y 后面是显示过滤器。两个参数的位置和语法都不同，第四章专门讲。

3.6 抓包的准备动作 #

抓之前做三件事，能省掉一半返工：确认网卡（ip -br addr 看清哪个口，抓错网卡是最常见的空手而归）、确认权限（Linux 普通用户要 CAP_NET_RAW，setcap cap_net_raw,cap_net_admin+eip /usr/bin/dumpcap 比 root 跑安全）、确认空间（用 ring buffer：-b filesize:100000 -b files:10 只留最近 10 个 100MB 文件）。

四、过滤表达式 #

这是新手翻车最多的地方。Wireshark 有两套完全独立的过滤语法，长得像，作用阶段完全不同。

4.1 两类过滤器 #

维度 捕获过滤器 显示过滤器
语法体系 BPF（Berkeley Packet Filter） Wireshark 自有
填写位置 抓包选项里的 Capture filter 主界面顶部的显示过滤框
生效时机 抓之前，内核里就筛掉 抓之后，对已抓的包筛
改的代价 必须重抓，漏掉的永远没有 随时改，数据还在
语法例子 tcp port 80 tcp.port == 80
端口写法 直接写数字，无点号 tcp.port，有点号
比较运算 没有 == 必须有 ==、!=、>
逻辑运算 and / or / not && / || / !（and/or 也认）
能用的字段 只有链路/网络/传输层的粗粒度 所有协议所有字段
典型用途 大流量下减负 分析时反复筛

一句话记住差别：捕获过滤器把包挡在门外，显示过滤器把包藏起来。

4.2 捕获过滤器语法 #

BPF 的表达方式是「限定词 + 值」，没有字段路径的概念。

限定词分三段：协议、方向、对象。三段都可以省略，省略就用默认值。

段 可选值 默认值
协议 ether fddi ip arp rarp decnet lat sca moprc mopdl tcp udp 所有支持的协议
方向 src dst src and dst src or dst src or dst
对象 net port host portrange host

默认值这条要记住，它解释了一批「我明明只写了一个 IP，怎么两个方向都抓到了」的疑问。host 10.2.2.2 与 src or dst host 10.2.2.2 完全等价。src 10.1.1.1 与 src host 10.1.1.1 等价，因为对象省了就是 host。

bash
port 80                       # 80 端口，tcp + udp 都算
tcp port 80                   # 只要 TCP 的 80
portrange 8000-8080           # 端口范围
host 192.168.1.10             # 主机
net 192.168.1.0/24            # 网段
src host 192.168.1.10         # 只抓源方向
dst port 443                  # 只抓目的端口
ether host 00:11:22:33:44:55  # 按 MAC
icmp                          # 协议名可以直接当过滤器
arp
tcp port 80 and host 192.168.1.10
not port 22 and not port 3306
(vlan and port 80) or arp     # 组合，括号要写

4.2.1 BPF 的运算符 #

三个逻辑词，优先级不一样。

text
not > and == or

and 和 or 同优先级，从左到右结合。这一条会让下面两个式子出现完全不同的结果：

bash
not tcp port 3128 and tcp port 23        # 等价于 (not tcp port 3128) and tcp port 23
not (tcp port 3128 and tcp port 23)      # 跟上面完全不同

判断不定就加括号。BPF 里括号不加钱。

4.2.2 关键字当值用要加反斜杠 #

协议名同时也是 BPF 的关键字，直接写会歧义。要让解析器把它当值，前面补一个 \。

bash
ether proto \ip        # 与关键字 ip 相同
ip proto \icmp         # 与关键字 icmp 相同

ip proto \icmp 抓的就是 ping 用的那类包。

ip 和 ether 后面能跟 multicast 和 broadcast 这两个词。想排掉局域网里的广播噪声：

bash
ip and not broadcast
ether and not broadcast

4.2.3 捕获过滤器常用写法 #

目的 BPF
某个主机的全部流量 host 10.1.2.3
只抓某个来源 src host 10.7.2.12
某网段 src net 192.168.0.0/24
老式掩码写法 src net 192.168.0.0 mask 255.255.255.0
某台机器的某个端口 tcp dst port 3128
一段端口 src portrange 2000-2500
按 MAC 抓 ether host e0:05:c5:44:b1:3c
排掉 SSH 和 MySQL not port 22 and not port 3306
只要 ICMP icmp
排掉 ICMP not icmp
源地址在内网、目的不在 src host 10.7.2.12 and not dst net 10.200.0.0/16

最后一个表项这类复合条件，实际排查里最常用。它的意思是「盯着这台机器往外发的东西，但别把发往另一片内网的那部分算进来」。

再复杂一点：

bash
(src host 10.4.1.12 or src net 10.6.0.0/16) \
  and tcp dst portrange 200-10000 \
  and dst net 10.0.0.0/8

多个条件之间用 \ 折行，shell 下能读。

4.2.4 捕获过滤器做不到的事 #

BPF 只能看链路层、网络层、传输层的固定位置，表达不了「SYN 位置 1 吗」这种位域判断。想在抓包阶段就按标志位筛，做不到。

两件事只能落到显示过滤器：

  • 按 TCP 标志位筛（tcp.flags.syn == 1）
  • 按应用层内容筛（http.host contains "x"）

所以大流量场景的策略是：捕获阶段按 IP 和端口粗筛，把数据量降到能承受，再在显示阶段按标志位和内容细筛。

4.2.5 捕获过滤器写错的两种表现 #

写完不一定报错，要分两种看。

第一种，启动时直接提示 filter 无效，抓包不开始。这算好结果，至少你知道写错了。

第二种，启动成功，但抓出来的文件是空的。BPF 对某些表达式宽容，编译通过了，语义却是「什么都不匹配」。这种最坑，因为你以为是没流量，其实是没匹配上。

判断办法：开抓之后盯一眼包计数。十秒钟还是 0，先怀疑过滤器，把捕获过滤器清空抓一次对照。

捕获过滤器的坑：它在内核里执行，写错了不一定报错，而是抓出空文件，写完先试抓 10 个包看看。另一个坑是 port 80 会同时匹配 TCP 和 UDP 的 80，想只要 TCP 就写 tcp port 80。

4.3 显示过滤器语法 #

五、以太网帧的字段 #

抓到的每一个包，最外层都是 Frame，Frame 里是 Ethernet II。先把它读掉，后面才有意义。

5.1 帧的组成 #

text
┌────────┬─────┬──────────┬──────────┬────────┬───────────────┬─────┐
│ 前导码 │ SFD │ 目的 MAC │ 源 MAC   │ 类型   │ 数据 + 填充    │ FCS │
│  7 B   │ 1 B │   6 B    │   6 B    │  2 B   │ 46 ~ 1500 B   │ 4 B │
└────────┴─────┴──────────┴──────────┴────────┴───────────────┴─────┘
字段 长度 含义
前导码 7 字节 全是 10101010，给接收方做时钟同步
SFD 1 字节 10101011，帧起始定界符
目的 MAC 6 字节 接收方硬件地址，全 1 是广播
源 MAC 6 字节 发送方硬件地址
类型 2 字节 上层协议标识，见下表

Wireshark 的 Frame 层会告诉你「这个帧在线上占多少字节」，Ethernet II 层才是帧头。两个数别混。

5.2 三个长度数字 #

这三个数字要背下来，抓包时天天用。

数字 含义 怎么算
64 字节 以太网最小帧长 不含前导码和 SFD，含 FCS
1500 字节 MTU，最大载荷 就是数据字段的上限
1518 字节 最大帧长 6+6+2+1500+4

抓到的帧如果只有 54 字节（14 字节头 + 20 字节 IP + 20 字节 TCP），那是正常的最小 TCP 包，不是残缺。如果载荷不足 46 字节，网卡会补零到 46，Wireshark 里看到一堆 00 就是填充。

5.3 类型字段 #

0x8847 MPLS 单播
0x8863 PPPoE 发现阶段
0x8864 PPPoE 会话阶段

看到 0x8100，说明后面还套了一层 VLAN 标签，真正的类型字段在 4 字节标签之后。Wireshark 会自动再展开一层。如果只看到 0x8100 就停住，多半是过滤器把 vlan 挡住了。

判断是 Ethernet II 还是 802.3：看类型字段。值大于等于 0x0600 是类型，是 Ethernet II；小于 0x0600 是长度，是 802.3。今天跑的以太网基本都是 Ethernet II。

5.4 MAC 地址的三种形态 #

形态 例子 判定
单播 a4:5e:60:11:22:33 第一个字节最低位为 0
广播 ff:ff:ff:ff:ff:ff 全 1，只在本广播域内传
组播 01:00:5e:00:00:01 第一个字节最低位为 1

IPv4 组播 MAC 固定以 01:00:5e 开头，后 23 位来自组播 IP 的低 23 位。IPv6 组播 MAC 是 33:33 开头。抓包看到 33:33 一堆，那是 IPv6 的 NDP，不是故障。

5.5 为什么抓不到 FCS #

FCS 由网卡在发送时算、接收时校验，正常情况不会交给内核。抓包点在内核里，所以默认看不到这 4 字节。

想看 FCS 要网卡支持，并且抓包工具直接从硬件取。绝大多数场景不需要：链路层错了，上层会表现为丢包和重传，从 TCP 层就能看出来。

六、ARP 报文分析 #

ARP 是地址解析协议，把 IP 地址解析成以太网 MAC 地址。

在局域网里，主机有数据要发给另一台设备，它必须知道对方的网络层地址（IP）。光有 IP 不够，因为 IP 报文必须封装成帧才能通过物理网络，帧头里要填对方的物理地址。所以要从 IP 地址求出物理地址，这就是 ARP 干的活。

6.1 报文结构 #

IPv4 配以太网时，ARP 报文固定 28 字节。

字段 长度 含义
硬件类型 2 字节 值为 1 表示以太网地址，其他值表示令牌环等
协议类型 2 字节 要映射的协议地址类型，0x0800 表示 IP
硬件地址长度 1 字节 ARP 报文里为 6
协议地址长度 1 字节 ARP 报文里为 4
op 2 字节 操作码，见下表
发送端以太网地址 6 字节 发送方硬件地址
发送端 IP 地址 4 字节 发送方 IP
目的以太网地址 6 字节 接收方硬件地址
目的 IP 地址 4 字节 接收方 IP

op 有四种取值。

op 含义
1 ARP 请求
2 ARP 应答
3 RARP 请求
4 RARP 应答

这 28 字节之外，还要套一层 14 字节的以太网头：目的 MAC、源 MAC、类型 0x0806。抓包时看到 0x0806，后面跟的就是 ARP。

6.2 请求和应答的差别 #

看懂 ARP 抓包，只看三个字段：op、目的 MAC、目的 IP。

项 ARP 请求 ARP 应答
op 1 2
以太网目的 MAC ff:ff:ff:ff:ff:ff（广播） 请求方的单播 MAC
目的 MAC 字段 全 0，因为还不知道 填请求方的 MAC
目的 IP 要问的那个 IP 请求方的 IP
谁发 想知道答案的一方 被问的一方

请求是广播，全广播域都会收到，只有 IP 匹配的那台会应答。应答是单播，直接回给问的人。

抓包时的过滤器：

text
arp                            # 所有 ARP
arp.opcode == 1                # 只要请求
arp.opcode == 2                # 只要应答
arp.dst.proto_ipv4 == 192.168.1.1   # 关于某个 IP

6.3 免费 ARP #

源 IP 和目的 IP 相同的 ARP 请求，叫免费 ARP（Gratuitous ARP）。用途有两个：一是设备上线时宣告自己，让别人的缓存立刻更新；二是检测 IP 冲突，如果发出去有人应答，说明这个 IP 已经被占用。

抓包里看到 op=1、源 IP 等于目的 IP、源 MAC 是自己，那就是免费 ARP。虚拟机迁移、VIP 漂移的时候会大量出现，这是正常现象，别当成攻击。

6.4 ARP 缓存 #

ARP 结果会缓存，不会每个包都问一次。Linux 上看：

bash
ip neigh show
192.168.1.1 dev eth0 lladdr a4:5e:60:aa:bb:cc REACHABLE

状态依次是：REACHABLE 可达可用、STALE 过期待确认、DELAY 已发确认等回应、PROBE 正在探测、FAILED 解析失败没人应答。抓包看到同一 IP 反复请求却无人应答，ip neigh 里就是 FAILED，要查对端是不是真在这个网段、VLAN 通不通。

6.5 两种异常 #

现象 抓包特征 意味着什么
ARP 风暴 短时间内海量 ARP 广播 环路，或者有设备疯狂重试
ARP 欺骗 同一个 IP 对应两个不同 MAC 的应答 有人抢答，中间人攻击的典型手法

ARP 欺骗的抓法：先记下网关的正常 MAC，然后过滤 arp.src.proto_ipv4 == 网关IP，看 src MAC 有没有变过。变了就是不正常。

七、IP 报文头的字段 #

IP 数据报也叫 IP 报文分组，跑在网络层。它由 IP 报文头和 IP 报文用户数据组成。报文头长度在 20 到 60 字节之间，一个 IP 分组的最大长度不能超过 65535 字节。

报文头的前 20 个字节固定，后面可变。

text
版本 4 bit │ 首部长度 4 bit │ 服务类型 8 bit │ 总长度 16 bit
标识 16 bit │ 标志 3 bit │ 片偏移 13 bit
TTL 8 bit │ 协议 8 bit │ 首部校验和 16 bit
源 IP 地址 32 bit
目的 IP 地址 32 bit
选项（可变长，0 ~ 40 字节）+ 填充

7.1 逐个字段 #

版本号：4 bit，标识 IP 版本。值 0100 是 IPv4，0110 是 IPv6。今天抓到的包绝大多数是 4。

首部长度：4 bit，指明包括选项在内的 IP 头部长度。单位是 32 位字，所以值 5 表示 20 字节，值 15 表示 60 字节。字段最大 15，对应头部最长 60 字节，减去固定 20 字节，可变部分最多 40 字节。

抓包里这个字段写成 0101 就是 5，头部无选项。要是值大于 5，说明有选项，在 Wireshark 里会多出一行 Options。

服务类型：8 bit。这个字段被分成两个子字段：3 bit 的优先级和 4 bit 的 TOS，最后一位置 0。4 bit 的 TOS 分别代表最小时延、最大吞吐量、最高可靠性和最小花费，四位里只允许其中一位置 1。四位全 0 代表一般服务。

多数 TCP/IP 实现并不实现 TOS 特性，但自 4.3BSD Reno 之后的新版系统都对它做了设置。OSPF 和 IS-IS 可以根据这些字段的值做路由策略。类似 SLIP 这样的协议虽然提供基于服务类型的排队方法，允许对交互型数据优先处理，但它的排队机制由 SLIP 自身判断和处理：驱动先看协议字段确认是不是 TCP 段，再检查 TCP 源和目的端口号，判断是不是一个交互服务。

TOS 字段后来作为区分服务（Diffserv）架构的一部分，语义换了一套。Diffserv 比 TOS 允许的处理更灵活。在 Diffserv 下，可以在一台路由器上定义服务分类（COS），把数据包归类到这些分类里，路由器按分类用不同优先级转发。每一次排序和转发处理称为一个 PHB。利用开头的 6 位构成 DSCP，可以用任意数值，也可以按区分服务体系里预先定义的服务类别，最多定义 64 个不同类别并归到 PHB 中。ECN 是显式拥塞通知位，路由器支持这个特性时，这些位可以用来传拥塞信号（ECN=11）。

抓包时关心一件事：DSCP 非 0，说明有人在用 QoS 标记。ip.dsfield.dscp != 0 能把它们筛出来。

总长度：16 bit，报头长度加数据部分长度。接收者用总长度减去 IP 报头长度，就得到载荷大小。IP 数据报最长 65535 字节。

这个字段和以太网帧的 Length 列不是一回事。帧长度含二层头，IP 总长度不含。以太网 MTU 1500 的时候，IP 总长度上限就是 1500。

标识：16 bit，唯一标识主机发送的每一份数据报。接收方根据分片里的标识字段是否相同，判断这些分片是不是同一个数据报，从而重组。每发送一份报文，这个值加 1。

标志：3 bit，标识数据报是否分片。第 1 位没用。第 2 位是不分段（DF）位，置 1 表示路由器不能对这个包做分段处理；如果包因为不能分段而无法转发，路由器丢弃它并回一个 ICMP 不可达。第 3 位是分段（MF）位，路由器分段时，除了最后一片的 MF 为 0，其他片的 MF 都为 1，接收者据此知道还没收完。

位 名称 含义
第 1 位 保留 未使用，恒为 0
第 2 位 DF（Don't Fragment） 1 = 不分片
第 3 位 MF（More Fragments） 1 = 后面还有分片

片偏移：13 bit，接收方重组时用来标识分片的顺序，指明分段起始点相对报头起始点的偏移量。分片到达时顺序会乱，这个字段让接收者能按正确顺序拼回去。

单位是 8 字节。抓包里 ip.frag_offset 显示的值已经乘过 8，是字节偏移，不用自己再乘。

包长超过下一跳链路的 MTU 时，路由器要分片。数据被切成小片，每片封装在独立的数据包里。接收端用标识、片偏移和 MF 位重组。

生存时间：8 bit。TTL 防止丢失的包在网络上无休止地传播。这个字段是一个 8 位整数，由产生包的主机设定，设置了数据报可以经过的最多路由器数。初始值由源主机设置，多数系统用 32 或 64，每经过一个处理它的路由器减 1。路由器把 TTL 减到 0 时，丢弃这个包，并发一个 ICMP 超时消息给源地址。TTL 经过某些防火墙设备时不一定减 1，抓包看到 TTL 不按跳数递减，先想想路径上有什么设备。

TTL 在排障里有两个用法：一是用初值反推对端系统（64 是 Linux 和多数 Unix，128 是 Windows，255 是网络设备），二是用 traceroute 逐跳探路。

协议：8 bit，标识哪个协议把数据交给 IP。ICMP 为 1，IGMP 为 2，TCP 为 6，UDP 为 17，GRE 为 47，ESP 为 50。

值 协议 值 协议
1 ICMP 47 GRE
2 IGMP 50 ESP
6 TCP 51 AH
17 UDP 58 ICMPv6
41 IPv6 封装 89 OSPF
4 IP-in-IP 132 SCTP

抓包看到 ip.proto == 47，那是 GRE 隧道，里面还有一层完整的 IP。Wireshark 会自动往下解析，别被嵌套的层级绕晕。

首部校验和：根据 IP 首部计算的校验和。只校验首部，不校验数据，因为数据由上层自己校验。每经过一个路由器 TTL 要减 1，校验和必须重算，所以这个字段逐跳都在变。

抓包里看到 Header checksum: 0x0000 [validation disabled]，别当故障。这是发送侧 offload 没算，接收侧也跳过校验。

源 IP 地址 / 目的 IP 地址：各 32 位，4 个字节，每个字节是 0 到 255 之间的整数，也就是我们日常见到的点分十进制格式。

选项：可变长的可选信息。选项字段以 32 bit 为界，不足时插入值为 0 的填充字节，保证 IP 首部始终是 32 bit 的整数倍。常见的选项有记录路由、时间戳、源路由。今天的互联网上基本看不到，看到就要留意，多半是探测或者特定设备的行为。

7.2 结构体定义 #

把上面的字段写成 C 结构，对着抓包看更直观。

typedef struct _IP_HEADER {
    unsigned char  iph_verlen;    /* 版本（高 4 位）+ 首部长度（低 4 位） */
    unsigned char  iph_tos;       /* 服务类型 */
    unsigned short iph_length;    /* 总长度，2 字节所以最大 65535 */
    unsigned short iph_id;        /* 标识 */
    unsigned short iph_offset;    /* 标志（高 3 位）+ 片偏移（低 13 位） */
    unsigned char  iph_ttl;       /* 生存时间 */
    unsigned char  iph_protocol;  /* 协议 */
    unsigned short iph_xsum;      /* 首部校验和 */
    unsigned int   iph_src;       /* 源地址 */
    unsigned int   iph_dest;      /* 目的地址 */

注意 iph_verlen 和 iph_offset 这两个字段，一个字节或一个字里塞了两个语义。取值要移位和掩码：

c
ver      = (iph->iph_verlen >> 4) & 0x0F;   /* 高 4 位 */
hdr_len  = (iph->iph_verlen & 0x0F) * 4;    /* 低 4 位，单位是 32 位字 */

这个结构在写嗅探程序的时候直接用得上。抓到一个包，把指针往后移 14 字节（以太网头）就是 IP 头，按这个结构读字段，比手算偏移可靠。

所有多字节字段在网络序里是大端，读之前必须 ntohs / ntohl 转成本机序。忘了这一步，长度和端口会读出一堆诡异的数字。这是抓包解析代码里最常见的 bug。

八、ICMP 报文分析 #

ICMP 是因特网控制报文协议，IPv4 协议族里的一个子协议，用于 IP 主机、路由器之间传递控制消息。控制消息指的是网络通不通、主机是否可达、路由是否可用这类网络本身的消息。它们不传用户数据，但对用户数据的传递起关键作用。

ICMP 和 ARP 不同：ICMP 靠 IP 协议完成任务，所以 ICMP 报文要封装 IP 头。它和 TCP、UDP 的目的也不一样，一般不在端系统之间传数据，不被用户程序直接使用，除了 ping 和 tracert 这类诊断程序。

8.1 报文结构 #

ICMP 报文在 IP 数据报里被传输。实际抓到的结构是：

一个装满的 ping 包是 20 字节 IP 首部 + 8 字节 ICMP 首部 + 1472 字节数据 = 1500 字节。1472 是 MTU 减这两个头得来的，所以 ping 的载荷上限就是 1472。

ICMP 首部固定 8 字节：

字段 长度 含义
类型 8 bit 报文的种类，见 7.2
代码 8 bit 同一类型下的细分原因
校验和 16 bit 覆盖整个 ICMP 报文
类型相关字段 32 bit 回显报文填标识 + 序列号；差错报文填原始 IP 头等信息

回显请求和回显应答的这 4 个字节是标识和序列号：标识一般填发送进程的 ID，用来在多个 ping 实例之间区分；序列号从 0 开始递增，应答原样带回，用来配对和统计丢包。

时间戳类报文（类型 13/14）在这 4 字节之后还有三个 32 位时间：发起时间、接收时间、发送时间，用来算往返时延。

8.2 类型和代码 #

具体是什么报文，由类型字段和代码字段共同决定。粗分两类：ICMP 差错报告报文和 ICMP 询问报文。

类型 名称 用途
0 回显应答 节点回应回显请求，ping 的返回值
8 回显请求 ping 发出去的包
3 无法到达目标 路由器和目标主机报告数据传不到
4 源抑制 路由器发生拥塞，通知发送主机降速
5 重定向 路由器告诉发送主机去目标有更好的路由
11 超时 TTL 耗尽，或分片在规定期限内没重组完

这里有个流传很广的错：不少旧资料把回显请求写成类型 0、回显应答写成类型 8，正好反了。抓个 ping 一看就清楚：icmp.type == 8 是请求，icmp.type == 0 是应答。以抓到的字节为准，不要以二手资料为准。

类型 3「无法到达目标」的代码细分：

代码 含义 触发场景
0 网络不可达 路由器没有到目标网段的路由
1 主机不可达 路由器找不到目标的地址解析结果
3 端口不可达 目标的 UDP 端口没有程序在监听
4 需要分片但设置了 DF 必须分片，但报文 DF 位为 1，路由器只能丢

代码 3 是做服务探测的常用手段：往一个 UDP 端口发包，回来 type=3 code=3 说明主机活着但这个端口没人听；没回应说明被防火墙挡了。

ICMP 只是试图报告错误、对特定情况提供反馈，它并没有让 IPv4 变成一个可靠的协议。ICMP 消息本身以未确认的 IPv4 数据报传送，自己也不可靠。

8.3 校验和怎么算 #

发 ICMP 报文时，程序要自己算校验和，填进 ICMP 头部对应的域。

算法分四步：把数据按 16 位为单位累加到一个双字里；数据长度是奇数时，最后一个字节扩展成字再累加；把结果的高 16 位和低 16 位相加；取反。

c
/* 计算 ICMP 包校验值
 * 参数 1：ICMP 包缓冲区
 * 参数 2：ICMP 包长度
 */
unsigned short GetCheckSum(unsigned char *lpBuf, unsigned int dwSize)
{
    unsigned int   dwCheckSum = 0;
    unsigned short *lpWord = (unsigned short *)lpBuf;

    /* 累加，每次吃 2 字节 */
    while (dwSize > 1) {
        dwCheckSum += *lpWord++;
        dwSize -= 2;
    }

    /* 长度是奇数，最后一个字节单独加 */
    if (dwSize == 1)
        dwCheckSum += *((unsigned char *)lpWord);

    /* 高 16 位与低 16 位相加 */
    dwCheckSum = (dwCheckSum >> 16) + (dwCheckSum & 0xFFFF);

    /* 取反 */
    return (unsigned short)(~dwCheckSum);
}

三点提醒。第一，算之前校验和字段要清 0，不然把自己的旧值也算进去了。第二，这个逐 16 位累加的做法叫反码求和，进位要回卷到低位，(sum >> 16) + (sum & 0xFFFF) 做的就是回卷。第三，接收方用同样方式算一遍，包括校验和字段，结果应该是 0。

8.4 抓一次 ping 看 #

让 Wireshark 开始抓包，显示过滤器填 icmp，开一个终端 ping www.youku.com。ping 默认发 4 个请求，抓包里就有 8 个报文，请求应答各 4 个。

展开一个请求报文，结构是这样的：

text

  Ethernet II, Src: 8c:16:45:xx:xx:xx, Dst: 5c:1d:xx:xx:xx:xx
  Internet Protocol Version 4, Src: 192.168.1.20, Dst: 117.x.x.x

几个点值得盯。

  • Total Length: 84 = 20 IP 头 + 8 ICMP 头 + 56 载荷。帧长度 98 = 14 以太网头 + 84。
  • Header checksum: 0x0000 [validation disabled] 是自己发出去的包，offload 没算，正常。
  • Checksum: 0x4d3a [correct]，ICMP 校验和是程序自己填的，所以是对的。

8.5 用 ICMP 看路由 #

Traceroute 利用报文的 TTL 信息获取路由。

做法是：先向目的主机发一个 TTL=1 的数据报。到第一台路由器时 TTL 减到 0，路由器回一个 ICMP 超时报文，说明数据报超时。由此拿到第一跳地址。再发 TTL=2 的，拿到第二跳。一路加下去，就得到主机到目的主机之间经过的路由。

text
TTL=1 → [R1] TTL 归零 → 回 icmp.type==11
TTL=2 → [R1] → [R2] TTL 归零 → 回 icmp.type==11
TTL=N → 到达目的主机 → 回 icmp.type==0 或 type==3 code==3

Linux 上 traceroute 可以选包类型：-I 用 ICMP，-U 用 UDP，-T 用 TCP。Windows 的 tracert 用 ICMP。实际测试里会出现问题：中间设备会限速甚至不回应 ICMP，* * * 就是这么来的，不代表那一跳不通。

抓 traceroute 的过滤器：

text
icmp.type == 11 || icmp.type == 3 || icmp.type == 0

一次 traceroute 会同时产生三类包，只看超时是看不全的。最后一跳回的是回显应答或端口不可达，不是超时。

8.6 抓包界面和协议栈的对应 #

Details 面板从上往下的层级，就是协议栈从下往上封装顺序的反向：Frame（物理层，帧长度、时间戳）→ Ethernet II（链路层，MAC、类型）→ Internet Protocol（网络层，IP 地址、TTL、协议号）→ TCP（传输层，端口、seq/ack、标志、窗口）→ 应用层协议。

排查时按层往上看：二层通了看三层，三层通了看四层，四层通了看应用层。哪层断了，问题就在哪层。

九、TCP 报文头的字段 #

TCP 是面向连接的可靠传输协议。两个进程互发数据之前要建立连接，这个连接只是端系统里分配的一些缓存和状态变量，中间的分组交换机不维护任何连接状态信息。

TCP 首部字段比 UDP 多得多，因为它要负责可靠性。

text
源端口 16 bit            │ 目的端口 16 bit
序列号 seq 32 bit
确认号 ack 32 bit
首部长度 4 bit │ 保留 6 bit │ 标志位 6 bit
接收窗口 16 bit          │ 校验和 16 bit
紧急指针 16 bit          │ 选项（可变长，0 ~ 40 B）
数据

9.1 端口 #

源端口和目的端口各 16 bit。它们用于多路复用和多路分解，把上层应用的数据区分开。端口用来标识同一台计算机上的不同进程，抓包里 tcp.srcport 和 tcp.dstport 就是这两个值。

9.2 seq 和 ack：字节序号，不是包序号 #

这是读 TCP 最要紧的一条。

序列号是本报文段所发送数据的第一个字节的字节流编号。 TCP 把数据看成有序的字节流，隐式地对每个字节编号。当报文被拆成多个报文段时，序列号就是报文段首字节在整个报文里的偏移量。

确认号是期望收到对方下一个报文段数据的第一个字节的序号。

TCP 是全双工的。假设 A 收到了 B 发来的数据，A 填进报文段的确认号，就是 A 期望从 B 收到的下一个字节序号。

所以这里有两个推论，全靠这一条推出来：

  • 一个 1000 字节的报文段，seq=1，下一个报文段的 seq 就是 1001。不是 2。
  • 对端回了 ack=1001，意思是「1 到 1000 我全收到了，下一个我要 1001」。

抓包里 tcp.seq_raw 和 tcp.ack_raw 是原始值。Wireshark 默认显示的是相对序号（Relative sequence numbers），把第一个 SYN 的 seq 归零，看起来从 0 开始。这是为了人好看，真实值是随机初始序号。要对照原始值，在 Preferences 里关掉 Relative sequence numbers。

把 seq 当包序号用，是所有 TCP 分析错误的源头。1000 字节一个段，seq 每次加 1000；1 字节一个段，seq 每次加 1。差值等于数据长度，跟包数无关。

9.3 首部长度和保留 #

数据偏移（首部长度）占 4 bit，指出报文段数据起始处距离报文段起始处多远，实际就是 TCP 首部的长度。单位是 32 位字，所以 5 表示 20 字节，15 表示 60 字节。首部最长 15×4=60 字节，选项最长 40 字节。

保留占 6 bit，留着以后用。后来的规范把其中两位用掉了：一位是 NS（ECN-nonce），一位是 CWR（拥塞窗口减小）。抓包里看到这两个标志，说明启用了 ECN。

9.4 六个标志位 #

Flags 决定这个包的性质，比任何字段都重要。

标志 全名 置 1 的含义
URG Urgent 报文段里有紧急数据，紧急指针生效
ACK Acknowledgement 确认号字段生效；为 0 时确认号字段无意义
PSH Push 接收方收到后立即交给上层，不等缓冲区满
RST Reset 连接出现严重差错，必须释放；也用来拒绝非法报文段或拒绝连接请求
SYN Synchronize 连接建立时同步序号
FIN Finish 发送端数据发完，要求释放连接

逐个说清楚。

URG：指示报文段里存在被上层标记为「紧急」的数据。URG=1 时，紧急指针指出紧急数据在当前数据段中的位置，是相对当前序列号的字节偏移量。接收方必须通知上层实体。今天的应用基本不用这个机制，看到 URG=1 反而要留意，这是老式带外数据的用法。

ACK：ACK=0 表示这个数据段不包含确认信息；ACK=1 表示报文段里有一个对成功接收报文段的确认。连接建立之后的每一个包，ACK 都是 1。

PSH：PSH=1 时，接收方收到数据后立即交给上层，而不是等整个缓冲区满。交互式应用（比如 telnet、SSH 的按键）会用到，抓包里 PSH 常和一段小数据一起出现。

RST：用来重置一个已经混乱的连接（比如对端崩溃），也用来拒绝一个无效的数据段或拒绝一个连接请求。拿到被置了 RST 的数据段，说明你这一端有问题了。RST 是最干脆的信号，它不给任何解释，看到它就要往回找原因。

SYN：用于建立连接。连接请求里 SYN=1、ACK=0，表示没有使用捎带的确认；连接应答捎带一个确认，即 SYN=1、ACK=1。

捎带（piggyback）是指对客户机到服务器数据的确认，被装在一个承载服务器到客户机数据的报文段里。这样一个包同时完成两件事，省一个包。

FIN：用于释放连接，表示发送方没有数据要传了。此时接收方还可以继续发数据，这就是半关闭。SYN 和 FIN 数据段都有序列号，所以这两种段能以正确顺序被处理。

标志位的经典组合：

组合 含义
SYN=1, ACK=0 连接请求（第一次握手）
SYN=1, ACK=1 连接接受（第二次握手）
ACK=1 普通数据传输、纯确认（第三次握手也是这个）
FIN=1, ACK=1 主动关闭方发起挥手
RST=1 连接被重置或被拒绝

9.5 窗口 #

窗口大小占 16 bit，用于流控制，确保连接的任何一方都不会过快发送过量分组把另一方淹了。窗口大小指定的是从被确认的字节算起，可以发送多少个字节。

这是接收方告诉发送方「我还能收多少」。抓包里 tcp.window_size_value 是首部里的原始值，tcp.window_size 是乘过窗口扩大因子之后的值。看流控要看后者。

窗口收到 0，说明接收方缓冲区满了，发送方必须停下。这就是零窗口，抓包里标成 [Zero Window]。之后接收方会发窗口更新（Window Update），把窗口重新打开。

9.6 校验和 #

校验和占 16 bit，提供额外可靠性。计算时 TCP 的 Checksum 域设为 0；数据域字节数为奇数时，数据域补一个 0 字节。

算法是把所有 16 位字按 1 的补码形式累加，取累加结果的补码。接收方执行同样的计算（包括 Checksum 域），结果应该是 0。

TCP 校验和要加 12 字节伪首部，UDP 也一样，见 9.3。伪首部里含源 IP、目的 IP、协议号、TCP 长度，用来把传输层和网络层绑在一起校验，防止包被投错地址还能通过校验。

抓包里看到 Checksum: 0x1a2b [incorrect, should be 0x8f3c] 一片红，先别急着查。本机发出的包，offload 没算，就是全错。判断方法：只在接收方向看，或者抓对面机器。

9.7 紧急指针 #

占 16 bit，指出本报文段中紧急数据最后一个字节的序号，只在 URG=1 时才有意义。

9.8 选项 #

选项部分是为了适配复杂网络环境、更好服务应用层而设计的，最长 40 字节。选项几乎只在连接建立阶段出现，也就是三次握手里。实际用到的有五种。

最大报文段长度 MSS：发送方与接收方协商最大报文段长度，这个长度只算净荷数据，不含 TCP 首部。三次握手中每一方都会通告自己期望收到的 MSS，只出现在 SYN 包里。如果一方不接受另一方的值，就用默认的 536 字节净荷，即主机能接受 20+536 字节的 TCP 报文段。

窗口扩大选项：TCP 首部的窗口字段只有 16 位，最大 65535。时延和带宽乘积大的链路（比如卫星通信）需要更大的窗口才能跑满带宽，窗口扩大选项就是为这个存在的。

窗口扩大选项占 3 个字节，最后一个字节是移位值。首部的 16 位窗口值向左移位，移位值为 14 时，新的窗口上限增大到 65535×(2^14)。

这个选项在连接建立之初协商，双方都发了才生效。已经实现扩大后，如果不再需要，发移位值 0 就恢复到原窗口大小 65535。

选择确认 SACK：考虑这种情况，A 发报文段 1、2、3、4、5，B 只收到 1、3、5 且报文无差错。没有 SACK，A 不知道 2 和 4 丢了，只能把 2345 全重传。SACK 用来确保只重传真正缺的段。

SACK 选项需要 2 个功能字节：一个指明使用 SACK，一个指明这个选项占多少字节。

说明丢失的报文段 2，就是给出 2 的左右边界 1 和 3。TCP 的数据报文有字节块边界，这个边界由序列号表示。

最多能指明 4 个字节块的边界。因为选项最大 40 字节，去掉 2 个功能字节，序列号 32 位即 4 字节，每个块要左右边界两个序号，所以 (40-2)/8 = 4。

时间戳选项：用来计算往返时间 RTT。发送方发报文段时把当前时钟值放进时间戳字段，接收方把这个值复制到确认报文里。发送方收到确认，用当前时钟减去确认报文里带回的时间戳，就得到 RTT。

时间戳还用于防止序号回绕 PAWS。序列号只有 32 位，每 2^32 个序号就回绕一圈。靠时间戳能区分相同序列号但属于不同轮次的报文段。

时间戳选项让 TCP 首部从 20 字节变成 32 字节。这就是为什么抓包看到的 TCP 头经常不是 20 字节。

NOP：TCP 首部必须是 4 字节的倍数，而多数选项不是 4 字节倍数，不足的用 NOP 填充。NOP 也用来分隔不同选项，比如窗口扩大选项和 SACK 之间用 NOP 隔开。

9.9 数据 #

无数据的 TCP 段也是合法的，纯 ACK 就是这种。它只承担确认和控制信息。

抓包时用 tcp.len > 0 把纯 ACK 全滤掉，剩下的才是真正传了数据的包。这一步能砍掉一半以上的噪声。

9.10 结构体定义 #

c
typedef struct _TCP_HEADER {
    unsigned short nSourPort;       /* 源端口 16 bit */
    unsigned short nDestPort;       /* 目的端口 16 bit */
    unsigned int   nSequNum;        /* 序列号 32 bit */
    unsigned int   nAcknowledgeNum; /* 确认号 32 bit */
    unsigned short nHLenAndFlag;    /* 前 4 位首部长度，中 6 位保留，后 6 位标志 */
    unsigned short nWindowSize;     /* 窗口大小 16 bit */
    unsigned short nCheckSum;       /* 校验和 16 bit */
    unsigned short nUrgentPointer;  /* 紧急数据偏移 16 bit */
} TCP_HEADER, *PTCP_HEADER;

nHLenAndFlag 一个字段装了三样东西，取值同样要移位：

c
hlen  = (ntohs(tcp->nHLenAndFlag) >> 12) & 0x0F;  /* 首部长度，单位 32 位字 */
flags = ntohs(tcp->nHLenAndFlag) & 0x003F;         /* 低 6 位是标志位 */

标志位从低到高依次是 FIN、SYN、RST、PSH、ACK、URG。判断 SYN：

c
if ((flags & 0x02) && !(flags & 0x10))   /* SYN=1 且 ACK=0 */
    puts("第一次握手");

十、UDP 报文头 #

UDP 是不可靠的、无连接的数据报服务。源主机发数据前不需要和目标主机建立连接，数据冠以源、目的端口号等 UDP 报头字段后直接发往目的主机，每个数据段的可靠性靠上层协议保证。传的数据少、包小的时候，UDP 比 TCP 高效。

UDP 首部固定 8 字节，四个字段。

字段 长度 含义
源端口号 16 bit 作用与 TCP 端口字段相同，标识源端应用进程
目标端口号 16 bit 标识目标端应用进程
长度 16 bit UDP 头部和 UDP 数据的总长度字节数，最小为 8
校验和 16 bit 对 UDP 头部和数据进行校验

三个容易读错的地方。

第一，长度字段含头部。抓包里 udp.length 是 8 + 数据长度，不是数据长度。要算应用层收了多少字节，用 udp.length - 8，别直接拿 frame.len。

第二，校验和是可选的。这一点和 TCP 不同，TCP 的校验和字段必须有。IPv4 下发送方不算校验和就填 0，抓包显示 Checksum: 0x0000 [no checksum]。IPv6 下 UDP 校验和强制。

第三，算校验和要加 12 字节伪首部：源 IP、目的 IP、一个全 0 字节、协议号 17、UDP 长度。伪首部不传输，只参与计算。目的是把传输层绑定到具体的地址对上，防止包被投错地址还能通过校验。

Wireshark 里对应的字段：

显示字段 含义
udp.srcport / udp.dstport 源、目的端口
udp.length 含 8 字节头的总长度
udp.checksum 校验和，0 表示未计算
udp.stream 会话编号，配合 Follow 用

判断 UDP 丢包没有 TCP 那么好办：没有序号可依赖，抓包只能看到「发了多少、收了多少」。要精确统计，得让应用层自己在载荷里带序号。

十一、跟着一次 TCP 连接看握手 #

理论讲完，看一次真的。以访问百度首页为例：先用 DNS 把域名解析成 IP，再在客户机和服务器之间建立 TCP 连接。抓包结果是这样：

text
No.  Source          Destination     Info
19   192.168.1.20    117.x.x.x      50000 → 80 [SYN] Seq=0 Win=64240 Len=0 MSS=1460 WS=256
20   192.168.1.20    117.x.x.x      50000 → 80 [SYN] Seq=0 Win=64240 Len=0 MSS=1460 WS=256
21   117.x.x.x       192.168.1.20   80 → 50000 [SYN, ACK] Seq=0 Ack=1 Win=29200 Len=0 MSS=1452
22   192.168.1.20    117.x.x.x      50000 → 80 [ACK] Seq=1 Ack=1 Win=64240 Len=0

你一看会觉得奇怪：理论上握手是 3 个包，这里怎么有 4 个，实际环境里更多。原因是客户机发了两个 SYN。这是为了更快建连：假设其中一个丢了，不至于要等一个重传超时再重发。抓包里看到重复的 SYN，先别当成故障。

接下来看 19、21、22 三个包。

11.1 第一次握手（19） #

标志字段 SYN=1、ACK=0，表示这个数据段没有使用捎带的确认。这就是连接请求。

MSS 报 1460，怎么来的：链路的以太网特性决定帧载荷 1500（MTU），1460 = 1500 − 20（IP 首部）− 20（TCP 首部）。不要被这个报文 32 字节的首部长度迷惑，那是选项撑起来的，只在建连阶段出现。

选项里有 3 个 NOP（01 01 01），作用是不足 4 字节倍数时填充，也作为选项之间的分隔。

11.2 第二次握手（21） #

服务器响应，此时确认号变成 1，因为 SYN 占一个序号。SYN=1、ACK=1 表明连接应答捎带了一个确认。

MSS 为什么是 1452 而不是 1460？因为这条链路是 PPPoE 拨号，PPPoE 首部 8 字节，MTU 变成 1492，MSS 就是 1492 − 40 = 1452。

Win=29200 是服务器通告的接收窗口，WS=256 是窗口扩大因子（移位 8）。

11.3 第三次握手（22） #

客户机再回一个报文段，Seq=1、Ack=1，标志只有 ACK，没有选项字段。

值得注意的一点：如果窗口扩大协商没谈成，就不扩大窗口，窗口上限停在 65535。

11.4 数据阶段用哪个 MSS #

一个常被问的问题：连接建好后，MSS 到底是 1460、1452，还是教科书的 536？

答案是取双方通告值的较小者，也就是 1452。536 只是「对方没报 MSS」时的默认值，报了值就不用默认值。这件事从抓包看最直接：建连后第一个满长的数据包，Len 就停在 1452。

11.5 状态对照 #

包 标志 seq ack 状态迁移
第一次 SYN=1, ACK=0 J 无效 客户端 SYN_SENT
第二次 SYN=1, ACK=1 K J+1 服务端 SYN_RCVD
第三次 ACK=1 J+1 K+1 双方 ESTABLISHED

客户端收到第二次握手后检查 ack 是否为 J+1、ACK 是否为 1，都对就把 ACK 置 1、ack 填 K+1 发出去。服务端检查完 ack 是否为 K+1、ACK 是否为 1，连接建立，之后才开始传数据。

抓握手的过滤器：

text
tcp.flags.syn == 1 || (tcp.flags.ack == 1 && tcp.len == 0)

想只看某一条连接的握手，先 Follow TCP Stream 拿到流号，再用 tcp.stream eq N 收窄。

11.6 四次挥手长什么样 #

握手建连，挥手断开。断开要在两个方向上各做一次，所以是四个包。

text
No.  Source        Destination   Info
31   192.168.1.20  117.x.x.x     50000 → 80 [FIN, ACK] Seq=1 Ack=1 Win=64240 Len=0
32   117.x.x.x     192.168.1.20  80 → 50000 [FIN, ACK] Seq=1 Ack=2 Win=29200 Len=0
33   192.168.1.20  117.x.x.x     50000 → 80 [ACK] Seq=2 Ack=2 Win=64240 Len=0

实际抓下来常是三个包，不是理论上的四个。原因是对端把 ACK 和 FIN 合成一个发了，省了一趟。理论模型是这样四步：

步 方向 标志 含义
1 主动方 → 被动方 FIN, ACK 我这边的数据发完了
2 被动方 → 主动方 ACK 收到你的 FIN
3 被动方 → 主动方 FIN, ACK 我这边的数据也发完了
4 主动方 → 被动方 ACK 收到你的 FIN

两个细节。

第一，FIN 一定带 ACK。只有 FIN 没有 ACK 的包，正常协议栈发不出来，抓到了就往扫描或者人为构造上想。

第二，挥手期间两个方向还在各传各的数据。FIN 只表示「我不再发数据了」，不表示「我不能再收」。这就是半关闭状态，shutdown(SHUT_WR) 干的事。

抓挥手：

text
tcp.flags.fin == 1
tcp.flags.fin == 1 || tcp.flags.reset == 1

11.7 挥手时谁先发 FIN #

一线排查里，这个问号的频率很高：连接断了，是客户端断的还是服务端断的？

看第一个 FIN 的方向。Source 是谁，就是谁先要求关闭。

谁先发 FIN 常见原因
客户端先发 用户关页面、应用主动 close、浏览器超时
服务端先发 会话超时、空闲连接回收、后端主动踢人、负载均衡摘节点

服务端先发 FIN 这件事，容易被误判成网络故障。它不是网络问题，是服务端的业务逻辑决定不聊了。一个真实的例子：某游戏客户端在无盘系统上反复掉线，抓包看到每次都是服务器先发 [FIN, ACK]，客户端回 ACK 收场。方向一看就明白，是服务端主动断的，客户端这边再怎么查网络也查不出东西。顺着服务端为什么不认这个客户端去找，才落到点上。

这条经验可以推广：抓包里「谁先动手」比「动手之后发生了什么」信息量大。前者回答责任方，后者只描述过程。

十二、连接复位 RST #

挥手是正常关闭，RST 是直接掐断。一条连接走到 RST，说明有人不愿意再谈了。

12.1 RST 的形态 #

RST 位在 TCP 首部的标志字段里，位置紧挨着 SYN。

形态 标志组合 谁发的
纯 RST RST=1，其余全 0 端口没监听的那一端
带 ACK 的 RST RST=1, ACK=1 已建立连接上发现问题的那一端

RST 只有两种合法写法：单发 RST，或者带 ACK 的 RST。RST 跟 SYN、FIN 一起出现都是非法组合，正常协议栈发不出来。抓包里见到 SYN+RST 或 FIN+RST，就当成扫描或者人为构造看。

RST 有个特殊之处：它不需要对方确认。发出去即生效，对方收到就把连接状态清掉，也不会回任何东西。所以抓包里看到 RST，后面跟着一片安静。

12.2 什么时候会发 RST #

RST 不是异常处理，是协议里明确定义的动作。四个场景最常见。

场景 谁发 抓包特征 指向哪里
连一个没监听的端口 目标主机 SYN → RST，只有两个包 服务没起、端口写错
已关闭的连接收到数据 收到数据那一端 中间隔一段空闲，突然 RST 空闲超时、中间设备清表
应用主动 abort 应用所在主机 数据流中途突然 RST 应用 SO_LINGER 设 0、进程崩
中间设备拦截 防火墙、负载均衡 RST 的源 IP 与预期不符 安全策略、会话表超时

第一种最好认。客户端发 SYN，服务端直接回 RST，三次握手第 1 步就结束，压根没有第 2、3 步。看到这个形状，先 ss -lntp 确认服务在不在听。

第二种最容易误判。一条连接空闲久了，中间防火墙的会话表先超时清掉，再发数据时防火墙回一个 RST，两边都以为是对端断的。特征是 RST 之前有一段很长的空闲，而且 RST 的 TTL 或源 MAC 跟真正的服务端对不上。

第三种跟应用代码有关。套接字设了 SO_LINGER 且超时为 0，close 时内核发 RST 而不是 FIN，缓冲区里没发完的数据直接丢。抓包看到 RST，先问代码里有没有动过 SO_LINGER。

12.3 怎么读 RST #

三步。

第一步看方向。Source 是谁，谁发的 RST。

方向 含义
服务端 → 客户端 端口没监听，或服务端主动拒绝
客户端 → 服务端 客户端应用 abort，或收到了不认识的报文
第三方 → 双方 中间设备注入，源 IP 和端口对不上就是它

第二步看 RST 之前发生了什么。只看 RST 本身信息量很低，得看它前面那几个包。

  • 前面是 SYN，那就是端口不通，结束。
  • 前面是一段正常收发，然后突然 RST，那就是应用或者超时。
  • 前面有一堆重传，RST 是最后的放弃动作。

第三步看 tcp.stream 号，把这个流的全过程拉出来。RST 是结果，原因在流的前半段的某个包里。

抓 RST 的三种写法：

text
tcp.flags.reset == 1
tcp.flags.reset == 1 && tcp.flags.ack == 0
tcp.flags.reset == 1 && tcp.flags.syn == 1

第二条找纯 RST，也就是端口不通那一类。第三条找非法组合，正常网络里不该出现。

12.4 RST 与 FIN 的取舍 #

维度 FIN RST
数据完整性 保证，发完才关 不保证，缓冲区丢掉
对方感知 正常关闭流程 异常，连接被重置
要几步 四步（常合成三步） 一步
谁会用 正常应用退出 端口不通、超时、abort
连接状态 走完 TIME_WAIT 直接删除

TIME_WAIT 只属于正常关闭的路径。被 RST 打断的连接不进 TIME_WAIT，所以「TIME_WAIT 太多」和「RST 太多」是两类完全不同的问题，不要混在一起查。

十三、常见异常的特征 #

异常在抓包里都有固定长相。认形状，比逐字段推快。

异常 抓包特征 过滤器 指向哪里
重传 同一 seq 出现两次，第二次标 [TCP Retransmission] tcp.analysis.retransmission 丢包、对端未确认
快速重传 三个重复 ACK 后紧跟重传 tcp.analysis.fast_retransmission 单个包丢失
乱序 后到的包先到达，标 [TCP Out-of-Order] tcp.analysis.out_of_order 多路径、负载均衡
零窗口 Win=0，标 [Zero Window] tcp.window_size == 0 接收方应用没读数据
窗口探测 零窗口后周期性发 1 字节 tcp.analysis.zero_window_probe 接收方卡死
连接重置 RST=1，标 [RST] tcp.flags.reset == 1 端口未监听、中间设备拦截
校验和错 红字 [incorrect] tcp.checksum.status == 2 多数是 offload，不是真错
重复 ACK 连续多个 ack 相同且 Len=0 tcp.analysis.duplicate_ack 对端在等缺失的段
分片 MF=1 或 frag_offset > 0 ip.flags.mf == 1 MTU 不匹配
ICMP 不可达 type=3，内含原始 IP 头 icmp.type == 3 路由缺失、端口关闭
TTL 超时 type=11 icmp.type == 11 路由环路、TTL 设太小
ARP 无应答 反复请求同一 IP 无人回 arp.opcode == 1 对端不在线、VLAN 不通

几个判读要点。

重传要看间隔。间隔接近 RTO（Linux 默认 200ms 起步、逐次翻倍），是超时重传；间隔极短，是快速重传。前者说明包彻底丢了，后者说明还能收到后续包。

RST 要看方向。服务端回 RST，多半是端口没监听；客户端发 RST，多半是应用主动 abort 或者收到了不认识的数据。

零窗口要看后续。零窗口之后有窗口更新，说明只是一时拥塞；一直不发更新，说明接收方应用卡住了，这时候查应用比查网络有用。

十四、易错点速查 #

坑 正确理解
把 Seq 当包序号 是字节序号，差值等于数据长度
用相对序号对日志 Wireshark 默认归零，对原始值要关掉相对序号
捕获过滤器写 tcp.port == 80 BPF 不认识点号，写 tcp port 80
显示过滤器写 tcp port 80 显示过滤器要写 tcp.port == 80
用 frame.len 算应用字节 含所有头部，用 tcp.len 或 udp.length - 8
窗口值直接当字节数 要乘窗口扩大因子，看 tcp.window_size
校验和红字就断定故障 本机发出的包受 offload 影响
把 No. 当 TCP 序号 帧序号和 TCP 序号无关
认为 ICMP 回显请求是类型 0 请求是 8，应答是 0
认为 MSS 默认 536 双方都报值时取较小者
以为能抓到 FCS 网卡校验后丢弃，内核看不到
以为抓包就是线上字节 抓包点在内核，offload 之后才上线
只看单方向抓包 半双工视角会漏掉一半因果
用 ip.addr 抓 ARP ARP 没有 IP 头，用 arp
普通用户打不开网卡就 sudo 跑 给 dumpcap 发 cap_net_raw,cap_net_admin 比给 root 强
chmod 4755 /usr/bin/dumpcap SUID 等于交出完整 root，capabilities 只给点名的那几项
加了 wireshark 组不生效 组关系要重新登录才落到会话上，id 里能看到才算数
勾了混杂模式就以为能抓别人的包 交换机按 MAC 转发，要端口镜像或 TAP
捕获过滤器写 tcp.flags.syn == 1 BPF 没有位域，按标志位筛只能用显示过滤器
捕获过滤器写错但启动成功 抓出空文件，先看包计数是不是 0
显示过滤器写了但列表空 输入框变黄说明语法对、只是这个 pcap 没有匹配项
把 ip.src != A or ip.dst != B 当排两个地址 or 几乎全放行，要排两个地址用 and
以为 RST 也要对方确认 RST 单方面生效，后面没有回包
看到 RST 只查网络 先看方向，服务端发的多半是端口或服务端逻辑，客户端发的查应用 abort

最后一条经验：读不懂一个包的时候，先看它属于哪条流，再看它前后的包。孤立的单包几乎没有信息量，上下文才有。

抓包这件事的本质，是把「我以为」换成「我看到」。文档给你应该，内核给你实际，抓包是唯一能同时看到两者的工具。下一个包卡在哪儿，抓下来就知道了。
