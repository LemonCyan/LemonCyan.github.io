这篇讲 Netfilter 这套框架本身：五个 hook 点钉在协议栈的哪几个位置、钩子函数怎么注册进去、包流到那里会发生什么、谁返回什么值能让包活下来、谁返回什么值能让包消失。

讲什么：Netfilter 的定位、它与 iptables 的分工、五个 hook 点的确切位置、hook 点与路由决策的先后顺序、nf_hook_ops 注册结构、优先级常量的执行顺序、五个返回值的语义、表与链的对应、conntrack 挂在哪、一个能跑起来的过滤模块。

不讲什么：iptables 命令行语法与规则写法、nftables、eBPF 与 XDP 挂点、NAT 的地址转换细节与端口分配算法、连接跟踪状态机的内部实现。这些各归各篇。

跨篇指路：包怎么走进 ip_rcv() 看《数据收发的内核路径》；sk_buff 的字段语义看数据结构那篇；路由决策本身看《路由表》与《策略路由》；NAT 的转换过程看《NAT 原理与实现》；组播路径上的 hook 调用点看《组播与 IGMP Snooping》。

一句话先记住：Netfilter 不是协议栈里的一层，它是插在协议栈几个固定位置的一排钩子。iptables 只是往这些钩子上挂规则的配置工具，内核里干活的是 Netfilter。

一、Netfilter 是什么 #

Netfilter 是 Linux 2.4 之后引入的内核子系统，一套通用的钩子管理框架。它自己不做判断，只提供机制：在协议栈的关键位置留出插槽，谁想插手包的处理就往插槽里注册函数。

先破一个常见误解。你没法在 ip_input.c 里找到一个叫「Netfilter 层」的东西。协议栈该走的流程一步不少，ip_rcv()、ip_forward()、ip_output() 该怎么跑还怎么跑。Netfilter 干的事，是在这几个函数的末尾插一句 NF_HOOK(...)，把包临时借出来给注册者过一遍，过完再还给协议栈。

这个「借调」关系决定了后面所有章节的顺序：先有协议栈，才有钩子；先有路由，才有转发；钩子只负责在正确的时刻打断一下。

主文件与模块 #

内容 位置
Netfilter 主文件 net/core/netfilter.c
主头文件 include/linux/netfilter.h
IPv4 相关实现 net/ipv4/netfilter/*.c
IPv4 头文件 include/linux/netfilter_ipv4.h、include/linux/netfilter_ipv4/*.h
IPv4 协议栈切入位置 ip_input.c、ip_forward.c、ip_output.c、ip_fragment.c

基于这套框架的功能模块分四类：

  • 数据报过滤模块（filter）
  • 连接跟踪模块（conntrack）
  • 网络地址转换模块（NAT）
  • 数据报修改模块（mangle）

这四类是 Netfilter 的用户，不是 Netfilter 本身。分清这一点，读代码时就不会把它们混成一坨。

表、链、规则 #

Netfilter 用三级结构组织规则：Netfilter 是表的容器，表是链的容器，链是规则的容器。一层套一层，最终落到「某个包在某条链上匹配到某条规则，执行某个动作」。

注意这三级是 iptables 那套模型的概念，Netfilter 框架本身只认「hook 点 + 钩子函数 + 优先级」。表和链是 ip_tables 模块在钩子函数内部自己实现的一层抽象。这句话是理解全篇的钥匙，第七章和第九章会回到它。

钩子表 #

真正在内存里存钩子的，是一个二维数组：

c
struct list_head nf_hooks[NPROTO][NF_MAX_HOOKS];

NPROTO 是内核支持的协议簇上限，值为 32。NF_MAX_HOOKS 是每个协议簇的挂载点数量，2.6 内核里为 8。行是协议族，列是 hook 点。

include/linux/socket.h 里 AF_INET（即 PF_INET）的序号是 2，于是 IPv4 的五个点落在：

text
PRE_ROUTING    nf_hooks[2][0]
LOCAL_IN       nf_hooks[2][1]
FORWARD        nf_hooks[2][2]
LOCAL_OUT      nf_hooks[2][3]
POST_ROUTING   nf_hooks[2][4]

这个下标会反复出现。记住「2 是 IPv4，后面那个数字是点的序号」，看任何一段 Netfilter 代码都不会迷路。

数组做成二维，是为了让 IPv6、DECnet 这些协议栈共用同一套框架。协议族不同，行不同；hook 点不同，列不同。框架只有一份，钩子各挂各的。

每个格子里放的不是一个函数，是一条按优先级排好序的双向链表。一个点上挂了多少个钩子，链表就有多少个节点，包来的时候从表头走到表尾。

二、与 iptables 的关系 #

iptables 是用户态工具，Netfilter 是内核里的机制。分工两句话说完：iptables 负责把规则写进内核，Netfilter 负责在包经过时按优先级调用这些规则背后的函数。

你敲的 iptables -A INPUT -j DROP 是个配置动作，它不会凭空产生一个「拦截点」。它做的是把自己的规则塞进 iptable_filter 模块的表结构里，而 iptable_filter 早就已经在 LOCAL_IN 上注册好钩子了。包来的时候，是那个钩子跑起来，遍历 INPUT 链，命中你的规则，返回 NF_DROP。

整条链路是这样：

  1. iptables 命令解析规则，组装成内核认的结构
  2. 通过 setsockopt() 把整张表或单条规则递给内核
  3. 内核里 ip_tables 模块接住，存进对应表的内存结构
  4. ip_tables 家族的模块在五个 hook 点上各注册一个钩子，优先级按表定
  5. 包经过时，钩子遍历本表的链，逐条 match，命中就执行 target，把结果翻译成 Netfilter 的返回值

所以 iptables 的内核部分，本质是「挂在 Netfilter 上的一个模块」。分表看：

iptables 表 内核模块 干的活
filter iptable_filter 放行还是丢弃
nat iptable_nat 改写源/目的地址与端口
mangle iptable_mangle 改 TTL、TOS、打标记
raw iptable_raw 绕过 conntrack

每个模块自己注册自己的钩子，互不知情。它们之间靠优先级排序，不靠代码调用。

两个层次的顺序 #

这里有个容易混的地方，必须掰开：

  • 链内规则的顺序，是 iptables 遍历时自己保证的，从上往下匹配
  • hook 点之间的顺序，是 Netfilter 按 priority 排的，从小到大执行

iptables -L 看到的是第一层。第二层藏在 nf_hooks[][] 的链表里，你在用户态看不到。改规则顺序改的是第一层，动优先级常量才影响第二层。

名词对照 #

一套东西两个名字，对照记：

iptables 里 Netfilter 里
-j ACCEPT NF_ACCEPT
-j DROP NF_DROP
-j NFQUEUE NF_QUEUE
-j RETURN 链内跳转，不产生返回值
没有对应 NF_STOLEN
没有对应 NF_REPEAT

NF_STOLEN 和 NF_REPEAT 在 iptables 语法里没有直接出口，它们是给写内核模块的人用的。第八章细说。

顺带一句：iptables-nft 是另一条路，命令还是 iptables，规则却翻译给了 nftables 后端，不再走 ip_tables。本篇讲的 hook 机制它照样在用，只是挂规则的模块换人了。

三、数据包在协议栈里的旅程 #

发送方向从上至下是「加头」的过程，每过一层加一个该层的头部。接收方向反过来，从网卡收上来之后逐层剥头，到用户态手里就是裸数据。

Netfilter 不参与加头剥头，它只在中间几个位置把包拦下来看一眼。这套路径图里用 A、B、C、D、E 五个字母标出这五个位置：

text
收包：网卡 → A(PRE_ROUTING) → 路由判决 ─┬─ 给本机 → B(LOCAL_IN) → 上层协议
                                        └─ 要转发 → C(FORWARD) ──┐
发包：本机 → 路由判决 → D(LOCAL_OUT) ──────────────────────────┴→ E(POST_ROUTING) → 网卡

换成文字说一遍：

  • 收到的每个包都从 A 点进来，经过路由判决，发给本机的走 B 点继续往上，不发给本机的走 C 点，然后顺着 E 点转发出去
  • 本地发出的包先做路由判决，确定从哪个口出去，然后走 D 点，最后顺着 E 点发出去

五个字母就是 Netfilter 下手的地方。A 到 E 在头文件里被重新起了名字，这套名字一直用到今天。

切入方式：一行宏 #

这五个点不是画在纸上的概念，它们是协议栈里五个函数末尾的一行宏调用。切入宏长这样：

c
#define NF_HOOK(pf, hook, skb, indev, outdev, okfn) \
    NF_HOOK_THRESH(pf, hook, skb, indev, outdev, okfn, INT_MIN)

参数逐个说清：

参数 含义
pf 协议族，IPv4 是 PF_INET；框架不限于 IP，还能是 PF_INET6、PF_DECnet
hook hook 点编号，IPv4 取 0 到 4
skb 网络设备数据缓存区
indev 包进来的设备，struct net_device *，不关心就传 NULL
outdev 包出去的设备，struct net_device *，不关心就传 NULL
okfn 函数指针，本点所有钩子跑完没人拦时，转去走这个流程

NF_HOOK 只是把 thresh 填成 INT_MIN 的壳。真正的宏是下一层：

c
#define NF_HOOK_THRESH(pf, hook, skb, indev, outdev, okfn, thresh)          \
({  int __ret;                                                              \
    if ((__ret = nf_hook_thresh(pf, hook, &(skb), indev, outdev,            \
                                okfn, thresh, 1)) == 1)                     \
        __ret = (okfn)(skb);                                                \
    __ret; })

比上一层多了 thresh，含义是「从哪个优先级开始遍历」。填 INT_MIN 就是从最小的开始，一个不漏。

再往里是 nf_hook_thresh()：

c
static inline int nf_hook_thresh(int pf, unsigned int hook,
                                 struct sk_buff **pskb,
                                 struct net_device *indev,
                                 struct net_device *outdev,
                                 int (*okfn)(struct sk_buff *), int thresh,
                                 int cond)
{
    if (!cond)
        return 1;

#ifndef CONFIG_NETFILTER_DEBUG
    if (list_empty(&nf_hooks[pf][hook]))
        return 1;
#endif

    return nf_hook_slow(pf, hook, pskb, indev, outdev, okfn, thresh);
}

又多了个 cond。它有两个作用：

  • cond 为 0，放弃遍历，连 okfn 也不执行
  • cond 为 1，去调 nf_hook_slow() 完成遍历，按优先级从小到大依次执行

返回值 1 是个约定，意思是「这里没什么事，直接走 okfn」。所以 NF_HOOK_THRESH 里那个 == 1 判断，等价于「没钩子或者被条件挡掉了，那就正常往下走协议栈」。

编译时没开 CONFIG_NETFILTER_DEBUG 的话，还有个短路：链表是空的就直接返回 1。没装任何防火墙规则时，这一句省掉的是一次函数调用加一次加锁。绝大多数机器上，这个分支天天命中。

okfn 的分量 #

六个参数里最容易被当成配角的是 okfn，它其实是主角。

okfn 指向的是协议栈原本要走的下一站，比如 ip_rcv_finish、ip_forward_finish、ip_local_deliver_finish、ip_finish_output。Netfilter 没有把包从协议栈里摘出来另走一条路，它是在原路上设了个关卡，关卡过完继续走原来的路。

这也是为什么返回值必须严谨。钩子函数拿到的是协议栈的包，处理完必须交代清楚：包还在不在、归谁、下一步往哪走。交代不清，协议栈就不知道该怎么收拾。

一句话概括整套机制：包流经某个预定义的关键点时，按协议族去那个点上查有没有钩子；没有就直接走 okfn，有就进 nf_hook_slow() 逐个调，再按返回值决定还走不走 okfn。

四、五个 hook 点 #

五个点的编号、数组位置、切入函数、okfn 一张表对齐。老内核叫 NF_IP_*，现在的头文件里叫 NF_INET_*，数值一样。

序号 老名字 现名字 数组位置 切入函数 okfn
0 NF_IP_PRE_ROUTING NF_INET_PRE_ROUTING nf_hooks[2][0] ip_rcv() ip_rcv_finish
1 NF_IP_LOCAL_IN NF_INET_LOCAL_IN nf_hooks[2][1] ip_local_deliver() ip_local_deliver_finish
2 NF_IP_FORWARD NF_INET_FORWARD nf_hooks[2][2] ip_forward()、ipmr_queue_xmit() ip_forward_finish
3 NF_IP_LOCAL_OUT NF_INET_LOCAL_OUT nf_hooks[2][3] ip_push_pending_frames() dst_output
4 NF_IP_POST_ROUTING NF_INET_POST_ROUTING nf_hooks[2][4] ip_output()、ip_mc_output() ip_finish_output

下面逐点过。每个点讲三件事：挂在哪个函数末尾、放行之后交给谁、iptables 的哪条链对应它。

PRE_ROUTING：包刚进来 #

挂在 ip_rcv()（net/ipv4/ip_input.c）的最后。挂接之前做的事都跟类型、长度、版本有关：版本号不是 4、长度不够、校验和不对，这类形状就不对的包在这之前已经被扔了。钩子看到的已经是「像样的 IP 包」。

c
NF_HOOK(PF_INET, NF_IP_PRE_ROUTING, skb, dev, NULL, ip_rcv_finish);

参数本身就在讲位置：indev 填 dev，包刚从这张网卡进来；outdev 填 NULL，因为此刻路由还没跑，不知道从哪出去；okfn 是 ip_rcv_finish，钩子放行后去查路由表。

放行之后进 ip_rcv_finish()（同文件），那里查路由表，判断这包是给本机还是要转发。所以 PRE_ROUTING 是唯一一个「路由未知」的点，也正因为如此，它才是改目的地址的最佳位置。

这个点上主要做报头检测，抓异常情况。挂在这的功能按优先级排开：conntrack（-200）、mangle（-150）、DNAT（-100）。

LOCAL_IN：给本机 #

目的地是本机的包，在 ip_local_deliver()（net/ipv4/ip_input.c）的最后经过这里。

c
NF_HOOK(PF_INET, NF_IP_LOCAL_IN, skb, skb->dev, NULL, ip_local_deliver_finish);

经过之后进 ip_local_deliver_finish()（同文件），按协议号往上分发给 TCP、UDP、ICMP。

iptables 的 INPUT 链表就在这个点上做规则匹配。防火墙一般建在这里——挡在门口，别让坏包摸到服务进程。

涉及功能：mangle（-150）、filter（0）、SNAT（100）、conntrack（INT_MAX-1）。

这一行里有点反直觉的两条，都跟「谁挂上来的」有关，跟点的位置关系不大：

  • SNAT（100）这一条对应 nat 表在 INPUT 链上的那部分规则，用于给本机收下的包改写地址的少数场景
  • conntrack（INT_MAX-1）是连接跟踪的「确认」钩子，故意排到几乎最后，保证前面所有钩子看到的状态一致

记住一个原则：点只提供位置，谁往上挂、挂什么优先级，是模块自己定的。

FORWARD：转发 #

目的地不是本机的包，包括被 NAT 改过地址的包，都在 ip_forward()（net/ipv4/ip_forward.c）的最后经过这里。

c
NF_HOOK(PF_INET, NF_IP_FORWARD, skb, skb->dev, rt->u.dst.dev, ip_forward_finish);

经过之后进 ip_forward_finish()（同文件）。这一刻三个设备信息都齐了：skb->dev 是入口，rt->u.dst.dev 是出口。所以转发路径上的钩子能同时看到进和出。

还有一条调用路径：net/ipv4/ipmr.c 里的 ipmr_queue_xmit() 最后也过这个点，组播路由转发走这条。所以 FORWARD 不止一个入口，别以为只有 ip_forward()。

iptables 的 FORWARD 链表挂这里。涉及功能：mangle（-150）、filter（0）。

LOCAL_OUT：本机发出 #

本机产生的包，在 ip_queue_xmit() 和 ip_build_and_send_pkt()（都在 net/ipv4/ip_output.c）的最后经过这里。前者最常用，承载真正有数据的包；后者用于那些不承载数据的 SYN/ACK 类包。

c
NF_HOOK(PF_INET, NF_IP_LOCAL_OUT, skb, NULL, skb->dst->dev, dst_output);

经过之后进 ip_queue_xmit2()，再往下就是输出路径。

还有两处也过这个点：ip_build_xmit_slow()、ip_build_xmit() 里用于错误检测；igmp_send_report()（net/ipv4/igmp.c）的最后也过，处理组播报告。

iptables 的 OUTPUT 链表挂这里。涉及功能：conntrack（-200）、mangle（-150）、DNAT（-100）、filter（0）。

这一点上拦自己发出的包要谨慎。路由器也好，PC 也好，很少有人限制本机出向流量，配错一条规则就能让某个服务彻底哑掉，而且排查起来得先怀疑半天 DNS。所以这个点上拦包的情况非常少，特殊需求除外。

这里的 DNAT 值得单独记一笔：本机发出的包在 OUTPUT 上被改了目的地址之后，需要重新查一次路由，内核给 skb 打上 IPSKB_REROUTED 标记。带着这个标记的包走到 ip_output() 时，会被 NF_HOOK_COND 挡住，不再进 POST_ROUTING。理由很简单，重路由一次就够了，再走一遍后面的钩子等于对同一个包处理两次。

POST_ROUTING：离开之前 #

所有包，不管源地址是本地还是非本地，在通过网络设备离开本机之前，都在 ip_finish_output()（net/ipv4/ip_output.c）的最后经过这里。

c
NF_HOOK_COND(PF_INET, NF_IP_POST_ROUTING, skb, NULL, dev, ip_finish_output,
             !(IPCB(skb)->flags & IPSKB_REROUTED));

经过之后进 ip_finish_output2()，再往下交给邻居子系统查 MAC，最后进驱动。

ip_mc_output()（同文件）在克隆新的 skb 时也过这个点。

涉及功能：mangle（-150）、SNAT（100）、conntrack（INT_MAX）。

从无条件宏 NF_HOOK 变成有条件宏 NF_HOOK_COND，加的就是最后那个表达式。条件成立才进 Netfilter，不成立就直接调 okfn 走协议栈。两个宏除此之外没有差别，NF_HOOK 相当于条件恒为真。

这个条件就是上面说的 IPSKB_REROUTED：包被重新路由过，就跳过 POST_ROUTING。判断放在这里而不是放在宏里面，是因为「要不要跳过」这个知识只有调用点知道。

组播路径上的三处补充 #

除了主路径，IPv4 里还有三处切入，都跟组播有关：

函数 文件 hook 点
ipmr_queue_xmit() net/ipv4/ipmr.c FORWARD
igmp_send_report() net/ipv4/igmp.c LOCAL_OUT
ip_mc_output() net/ipv4/ip_output.c POST_ROUTING

组播转发和 IGMP 报告也走同一套钩子，不是另开一套。组播本身的机制展开在《组播与 IGMP Snooping》。

五、hook 点与路由的关系 #

五个点不是随便挑的位置，每一个都卡在路由决策的前面或后面。搞错这个顺序，NAT 为什么必须挂在特定点上就永远想不通。

hook 点 与路由的先后 此刻已知 典型用途
PRE_ROUTING 路由之前 只知从哪个口进来 DNAT、建连接跟踪、报头检测
LOCAL_IN 路由之后 知道包是给本机的 过滤上送本机的包
FORWARD 路由之后、转发之前 入口、出口、下一跳都知 过滤转发的包
LOCAL_OUT 首次路由之后、输出之前 知道是本机产生 过滤出向包、DNAT 后触发重路由
POST_ROUTING 路由之后、发出之前 出口设备已定、源地址已选 SNAT、改 TTL/TOS

为什么 DNAT 必须在 PRE_ROUTING #

路由决策在 PRE_ROUTING 之后。这是整段话的前提。

你先把目的地址改了，路由就按新地址查表。改成内网某台机器的地址，路由一查，目的不在本机，判为转发，包走 FORWARD 出去。整条链路顺理成章。

反过来推一遍：如果把 DNAT 放到路由之后，会怎样？路由已经按老地址（比如路由器自己的公网地址）查过表，判定这包是给本机的，于是走 LOCAL_IN 往上送。等包到了 LOCAL_IN 你再改目的地址，已经晚了，包的归宿定了，转发出不去。

这就是 DNAT 只能挂在 nat 表的 PREROUTING 和 OUTPUT 两条链上的原因。前者改转发包的地址，后者改本机出向包的地址，两个位置都在「路由会受影响的时刻」。

为什么 SNAT 必须在 POST_ROUTING #

源地址的选择依赖出口。包从哪张网卡出去，是路由决定的；出口一定，源地址才选得出来。

提前 SNAT 有个直接问题：万一出口变了，源地址得跟着改第二次。放在 POST_ROUTING，出口已定、源地址已定，改完就把包交给邻居子系统，中间没有变量了。

所以 SNAT 挂在 nat 表的 POSTROUTING 和 INPUT 两条链上，都在「出口已定」之后。

一条 NAT 转发的完整轨迹 #

外网客户端访问路由器的 200.x:80，路由器把它 DNAT 到内网 192.168.1.10:8080。包怎么走：

text
eth0 收到 dst=200.x:80
  → PRE_ROUTING
      conntrack(-200)：查到没有对应连接，建一条 NEW
      mangle(-150)：改 TTL、打标记
      DNAT(-100)：命中规则，dst 改成 192.168.1.10:8080
  → 路由决策：目的不是本机 → 走转发
  → FORWARD
      filter(0)：放行
  → POST_ROUTING
      mangle(-150)：改 TTL
      SNAT(100)：按 conntrack 记录把源地址改成路由器出口地址
  → eth1 发出

回程包反着来：从 eth1 进来，PRE_ROUTING 上 conntrack 认出这是已建连接的回程方向，顺手把目的地址改回 200.x，再转发出去。

注意 DNAT 在 -100，conntrack 在 -200。顺序不能反：连接跟踪得先建好记录，NAT 才有地方记「这条连接被改成了什么」，回程包才知道怎么改回来。这是一条硬依赖，不是风格问题。

顺带说清一层 #

路由管的是「包去哪」，Netfilter 管的是「包能不能去」。两者正交，但共享同一个 skb。

所以改地址的钩子会改变路由结果，改过滤的钩子不会。前者必须卡在路由前后正确的时刻，后者卡在哪个点上都只是「看的是哪个阶段的包」的区别。理解这个差别，iptables 各条链为什么能做某些事、不能做另一些事，就都能推出来。

六、注册一个 hook #

写一个钩子模块，要准备两样东西：一个 nf_hook_ops 结构体，一个符合签名的钩子函数。注册就是把前者塞进 nf_hooks[][] 的某个链表。

nf_hook_ops #

c
struct nf_hook_ops {
    struct list_head list;
    nf_hookfn       *hook;
    int              pf;
    int              hooknum;
    int              priority;
};
字段 作用
list 挂进 nf_hooks[pf][hooknum] 链表的节点，内核自己维护，你别碰
hook 钩子函数指针，包来的时候被调用
pf 协议族，IPv4 填 PF_INET
hooknum 挂到哪个点，取 0 到 4 之一
priority 排序依据，数值小的先执行

钩子函数的签名是五个参数：

c
unsigned int nf_hookfn(unsigned int hooknum,
                       struct sk_buff *skb,
                       const struct net_device *in,
                       const struct net_device *out,
                       int (*okfn)(struct sk_buff *));

跟 NF_HOOK 宏吃的那几个参数对得上：hooknum、skb、indev、outdev、okfn。宏把自己收到的上下文原样转交给了钩子，所以钩子知道的一切都来自这五个值。

后来的内核把后面四个参数收进了一个 struct nf_hook_state *，还在前面加了个 priv 指针，语义没变：谁在哪个点、包从哪来、往哪去、放行后走哪个函数。

注册与注销 #

c
int  nf_register_hook(struct nf_hook_ops *ops);
void nf_unregister_hook(struct nf_hook_ops *ops);

注册时内核不会把整条链表重排一遍。它顺着链表找第一个 priority 比新节点大的项，把新节点插到它前面。链表因此永远保持有序，遍历的时候直接走，不用比较排序。

这个设计说明一件事：优先级只在注册那一刻起作用，注册完就固定了。运行中想换顺序，只能先注销再注册。

三条约束，写模块的人必须守：

  1. 注册放在模块的 init 里，注销放在 exit 里。漏了注销，模块卸载之后链表里留着一个指向已释放内存的节点，下一个包过来就是野指针
  2. 注销前要确认没有包正跑在钩子函数里。这一步靠 RCU 宽限期保证，不同内核版本的写法不一样，照你手上那版内核的现成模块抄
  3. 钩子函数跑在软中断上下文（收包）或进程上下文（本机发包）里，不能睡眠。要睡眠就得用 NF_QUEUE 把包扔给用户态

一个骨架 #

c
#include <linux/module.h>
#include <linux/netfilter.h>
#include <linux/netfilter_ipv4.h>

static unsigned int demo_hook(unsigned int hooknum,
                              struct sk_buff *skb,
                              const struct net_device *in,
                              const struct net_device *out,
                              int (*okfn)(struct sk_buff *))
{
    return NF_ACCEPT;
}

static struct nf_hook_ops demo_ops = {
    .hook     = demo_hook,
    .pf       = PF_INET,
    .hooknum  = NF_INET_PRE_ROUTING,
    .priority = NF_IP_PRI_FILTER,
};

static int __init demo_init(void)
{
    return nf_register_hook(&demo_ops);
}

static void __exit demo_exit(void)
{
    nf_unregister_hook(&demo_ops);
}

module_init(demo_init);
module_exit(demo_exit);
MODULE_LICENSE("GPL");

nf_register_hook() 返回 0 是成功，负数要原样往上抛。注册失败还继续跑，模块看着加载成功，钩子其实没挂上，这种 bug 最难查。

优先级填 NF_IP_PRI_FILTER（0）意味着跟 filter 表同档。同档的多个钩子之间谁先谁后，看注册顺序，别在这上面押注。要保证顺序就用不同的值。

骨架里的 demo_hook 什么都没做，返回 NF_ACCEPT，包照常走。这是最安全的起点：先确认模块能加载、能卸载、dmesg 没报错，再往里加逻辑。

七、优先级与执行顺序 #

一个点上挂多个钩子，谁先跑由 priority 决定：数值小的先跑。负数比正数早，INT_MIN 最早，INT_MAX 最晚。

常量表 #

这些常量定义在头文件里，数值是固定的，写模块时直接用名字，别写裸数字。

常量 数值 谁在用
NF_IP_PRI_FIRST INT_MIN 抢在所有人之先的钩子
NF_IP_PRI_RAW -300 raw 表，赶在 conntrack 之前
NF_IP_PRI_CONNTRACK -200 连接跟踪，建状态、标 NEW
NF_IP_PRI_MANGLE -150 mangle 表，改 TTL、TOS、打标记
NF_IP_PRI_NAT_DST -100 nat 表的 DNAT，改目的地址
NF_IP_PRI_FILTER 0 filter 表，放行或丢弃
NF_IP_PRI_SECURITY 50 security 表
NF_IP_PRI_NAT_SRC 100 nat 表的 SNAT，改源地址
NF_IP_PRI_CONNTRACK_CONFIRMED INT_MAX - 1 连接确认，LOCAL_IN 上用
NF_IP_PRI_LAST INT_MAX 垫底，POST_ROUTING 上的确认

看表里这几条的位置就懂了：raw 最早，因为它要能在 conntrack 之前把某些包排除掉；conntrack 紧接着，因为后面所有要判断状态的钩子都依赖它先建好记录；mangle 在 NAT 之前，改完包头字段再改地址；filter 在 NAT 之后，判断的是「最终形态」的包。

遍历代码 #

排序的结果在遍历里体现。net/netfilter/core.c 的 nf_iterate() 是核心，它被 nf_hook_slow() 调用：

c
struct list_head **i;

list_for_each_continue_rcu(*i, head) {
    struct nf_hook_ops *elem = (struct nf_hook_ops *)*i;

    if (hook_thresh > elem->priority)
        continue;

    verdict = elem->hook(hook, skb, indev, outdev, okfn);

    if (verdict != NF_ACCEPT) {
        /* 不是 ACCEPT，按 verdict 处理 */
    }
}

return NF_ACCEPT;

三段逻辑，逐句读：

  • list_for_each_continue_rcu 沿链表走，节点已经按优先级排好，不用比较
  • hook_thresh > elem->priority 命中就 continue，意思是「这个钩子的优先级低于门槛，跳过」。NF_HOOK 传的 INT_MIN 保证了谁都不会被跳过；传别的值可以只让一部分钩子参与
  • verdict != NF_ACCEPT 就跳出常规流程，去处理非接受的情况

整段跑完返回 NF_ACCEPT，表示「所有钩子都放行了」，宏那边接着调 okfn。

这里能看出 NF_ACCEPT 的确切含义：它不是「包安全了」，它只是「我这一关放行」。后面还有钩子，它们照样会被调用，任何一个返回 NF_DROP，包还是没了。

一个点上的真实顺序 #

以 PRE_ROUTING 为例，一个完整的包经过的钩子顺序：

text
raw(-300) → conntrack(-200) → mangle(-150) → DNAT(-100) → 其它注册者

每个箭头是一次函数调用、一次 verdict 判断。任何一步返回非 NF_ACCEPT，后面的全部不执行。

两个细节 #

同一优先级的多个钩子，先后取决于注册顺序，nf_register_hook() 插到第一个比它大的节点之前，等值的会排在新来的前面。想让两个钩子有确定先后，就给不同的 priority，别指望注册顺序这种隐性约定。

priority 只在注册时用一次。链表有序之后，运行时不再比较。所以改顺序必须重新注册，没有「热改优先级」这种操作。

八、五个返回值 #

钩子函数必须报一个 verdict，这是钩子对 Netfilter 的交代。五个值，含义差别很大，搞混了就是内存泄漏或者包凭空消失。

返回值 一句话 包归谁 后续
NF_ACCEPT 我放行 协议栈 继续下一个钩子，全过完走 okfn
NF_DROP 扔掉 由框架释放 不再往下走，直接返回
NF_STOLEN 我接管了 你 框架不管了，也不释放
NF_QUEUE 交给用户态 队列 用户态裁决后送回
NF_REPEAT 重跑一遍 还是你 从本点再调一次本钩子

NF_ACCEPT #

继续正常传输。告诉 Netfilter：这个包到目前为止是被接受的，应当被递交到协议栈的下一个阶段。

注意「下一个阶段」的准确含义——先是本点的下一个钩子，不是直接跳 okfn。一个点上挂了五个钩子，只有五个都返回 NF_ACCEPT，包才会走到 okfn。

NF_DROP #

丢弃，不再传输。包的 sk_buff 由框架负责释放，返回之后你就别再碰它了。

这是最常用的拦截手段，iptables 的 -j DROP 就是它。丢完之后协议栈收不到任何通知，对端看到的是超时，不是拒绝，这个区别在网络诊断里经常是关键线索。

NF_STOLEN #

模块接管该包，告诉 Netfilter「忘掉它」。从此这个包的处理归你，Netfilter 放弃对它的任何处理。

但接管不等于资源已释放。包的 sk_buff 仍然活着，只是所有权从框架转到了你手上。你得自己负责什么时候把这个 skb 释放掉，忘了就是内存泄漏，泄漏速度跟包速率一样快。

NF_STOLEN 的典型用法是「包不往下走了，但要留下来做别的事」：缓存起来、塞进别的队列、延迟处理。如果你只是想让包消失，用 NF_DROP，别用 NF_STOLEN，省得自己收拾。

NF_QUEUE #

把包排队，交给用户态进程处理。内核这边把包挂进队列，等用户态裁决完再把 verdict 送回来。

用户态得有进程在读这个队列（nfnetlink_queue 那一套），没有监听者的时候包会被丢掉。所以装完 -j NFQUEUE 规则却忘了起监听进程，现象就是「网络突然不通」，而且内核日志里什么都没有。

NF_QUEUE 是钩子里唯一能绕开「不能睡眠」限制的路子：内核这边不睡，把包扔出去就行。

NF_REPEAT #

再次调用本钩子。从当前这个钩子的开头重新跑一遍。

这个值要谨慎使用，用错就是死循环：钩子返回 NF_REPEAT，框架立刻再调它，它又返回 NF_REPEAT，CPU 就卡在这里了。真要用，钩子内部必须有个状态保证第二次不再返回 NF_REPEAT。

谁在为这些返回值收尾 #

nf_hook_slow() 拿到非 NF_ACCEPT 的 verdict 之后，做的事分三类：

verdict 框架的动作
NF_ACCEPT 继续遍历下一个节点
NF_DROP 释放 skb，返回错误码，协议栈当这个包没来过
NF_STOLEN 什么都不做，直接返回，skb 交给你
NF_QUEUE 把 skb 挂进队列，返回排队结果
NF_REPEAT 回到本节点重新调用

一句话总结这五个值的设计：它们在回答同一个问题的不同版本——「这个包接下来归谁管」。协议栈、你、框架、用户态，四个候选，加上「重新问一遍」。

九、表与链的对应 #

iptables 的每张表在哪些链上有链，对应到 Netfilter 就是「这个模块在哪些 hook 点上注册了钩子」。一张表看全：

表（优先级） PREROUTING INPUT FORWARD OUTPUT POSTROUTING
raw（-300） 有 — — 有 —
mangle（-150） 有 有 有 有 有
nat（-100 / 100） 有（DNAT） 有（SNAT） — 有（DNAT） 有（SNAT）
filter（0） — 有 有 有 —
security（50） 有 有 有 有 有

几个结论直接读出来：

  • mangle 和 security 覆盖全部五个点，因为改包头字段和打安全标记在哪个阶段都有需求
  • filter 没有 PREROUTING，也没有 POSTROUTING，因为那两处还没确定包的去向或已经确定，过滤的判断没有落脚点
  • nat 的 DNAT 只在 PREROUTING 和 OUTPUT，SNAT 只在 POSTROUTING 和 INPUT，理由在第五章讲过

同一个点上的多张表 #

一个 hook 点上挂的不是一张表，是好几张表各自的钩子，按优先级排开。所以 PREROUTING 上的实际执行顺序是：

text
raw → conntrack → mangle → nat(DNAT)

POSTROUTING 上是：

text
mangle → nat(SNAT) → conntrack 确认

你在 iptables -t nat -L 和 iptables -t mangle -L 里看到的是两条各自独立的链，它们在同一个点上按优先级插队执行。用户态看起来是两张表，内核里是同一个链表上的不同节点。

链内与链间 #

-A INPUT 把规则追加到 INPUT 链尾，-I INPUT 1 插到链头，这两种都在同一个钩子函数内部生效，跟 Netfilter 的优先级无关。所以：

  • 想调整同一张表内的规则先后，用 -I 和 -D 重排
  • 想调整不同表之间的先后，改不了，那是内核里写死的优先级

十、conntrack 与状态检测 #

连接跟踪是 Netfilter 上挂得最深的一个模块，值得单独说清它的位置。

挂在哪 #

点 优先级 干什么
PRE_ROUTING -200 看进来的包，查表，没有记录就新建，标 NEW
LOCAL_OUT -200 看本机发出的包，同样建记录
LOCAL_IN INT_MAX - 1 确认连接已建立
POST_ROUTING INT_MAX 确认连接，把记录落定

前面建、后面确认，一前一后夹住整条路径。确认钩子故意排到最后，保证前面所有钩子看到的状态一致——不然 mangle 改完包，conntrack 那边记录还没定，回程包就对不上了。

状态表 #

状态 含义
NEW 看到一个方向的第一个包
ESTABLISHED 两个方向都见过包
RELATED 跟已有连接有关联的新连接，比如 FTP 的数据连接、ICMP 错误
INVALID 不属于任何已知连接，或者状态不对

-m state --state ESTABLISHED,RELATED -j ACCEPT 这条规则几乎出现在每台 Linux 防火墙的配置里。它快的原因是：判断状态只查哈希表，不用逐条匹配规则。

与 NAT 的依赖 #

NAT 的改写记录存在 conntrack 的扩展里。DNAT 改了目的地址，记录里存下「原地址 → 新地址」；回程包进来，conntrack 认出它属于这条连接，自动按记录反着改回去。

所以顺序是硬约束：conntrack(-200) 必须早于 DNAT(-100)。反过来，NAT 没有地方记改写关系，回程包就找不到路。

raw 表为什么在最前面 #

raw（-300）比 conntrack 还早。它的用途只有一个：给某些包打上 NOTRACK，让它们完全跳过连接跟踪。

大流量、短连接、纯转发的场景里，关掉跟踪能省掉哈希表的开销。代价是这些包不能用状态匹配，也不能被 NAT 处理——它们没有记录可查。

十一、写一个简单的过滤模块 #

理论够了，写一个能跑的。功能：丢掉所有进来的 ICMP echo request，也就是别人 ping 不通本机。选这个是因为好验证，ping 一下就知道生效没有。

完整代码 #

c
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/ip.h>
#include <linux/icmp.h>
#include <linux/netfilter.h>
#include <linux/netfilter_ipv4.h>

static unsigned int icmp_drop_hook(unsigned int hooknum,
                                   struct sk_buff *skb,
                                   const struct net_device *in,
                                   const struct net_device *out,
                                   int (*okfn)(struct sk_buff *))
{
    struct iphdr *iph;
    struct icmphdr *icmph;

    if (!skb)
        return NF_ACCEPT;

    iph = ip_hdr(skb);
    if (iph->protocol != IPPROTO_ICMP)
        return NF_ACCEPT;

    if (!pskb_may_pull(skb, sizeof(struct iphdr) + sizeof(struct icmphdr)))
        return NF_ACCEPT;

    iph = ip_hdr(skb);
    icmph = (struct icmphdr *)((unsigned char *)iph + iph->ihl * 4);

    if (icmph->type != ICMP_ECHO)
        return NF_ACCEPT;

    pr_info_ratelimited("nf_demo: drop icmp echo %pI4 -> %pI4\n",
                        &iph->saddr, &iph->daddr);

    return NF_DROP;
}

static struct nf_hook_ops icmp_drop_ops = {
    .hook     = icmp_drop_hook,
    .pf       = PF_INET,
    .hooknum  = NF_INET_PRE_ROUTING,
    .priority = NF_IP_PRI_FILTER,
};

static int __init nf_demo_init(void)
{
    int ret;

    ret = nf_register_hook(&icmp_drop_ops);
    if (ret < 0) {
        pr_err("nf_demo: register failed, ret=%d\n", ret);
        return ret;
    }

    pr_info("nf_demo: loaded\n");
    return 0;
}

static void __exit nf_demo_exit(void)
{
    nf_unregister_hook(&icmp_drop_ops);
    pr_info("nf_demo: unloaded\n");
}

module_init(nf_demo_init);
module_exit(nf_demo_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("drop incoming icmp echo request");

逐段解释 #

  • hooknum 填 NF_INET_PRE_ROUTING，挂在包刚进协议栈的位置。选它是为了在所有本地处理之前就丢掉，后面的路由、过滤都省了
  • 先看 iph->protocol，不是 ICMP 立刻放行。这是最快的短路，让绝大多数包只付一次比较的代价
  • pskb_may_pull() 不能省。skb 的线性区不一定够长，直接按偏移取 ICMP 头会读到不该读的内存。这个函数把需要的字节拉进线性区，返回 0 就是拉不动，放行
  • iph->ihl * 4 是 IP 头长度，单位是 4 字节，不能直接拿 ihl 当字节数
  • 打印用 pr_info_ratelimited()，带速率限制。钩子在软中断里跑，灌满 dmesg 的后果比你想的严重
  • 返回 NF_DROP，包在这里消失

验证 #

bash
make
sudo insmod nf_demo.ko
ping -c 3 8.8.8.8          # 全部超时，说明钩子生效
dmesg | tail -n 5          # 看到 drop icmp echo 的日志
sudo rmmod nf_demo
ping -c 3 8.8.8.8          # 恢复正常
现象 说明
ping 超时，dmesg 有日志 钩子正常，返回 NF_DROP 生效
ping 通，dmesg 有日志 日志打了但没拦住，检查返回值是不是写成了 NF_ACCEPT
ping 通，dmesg 无日志 钩子没被调用，查 nf_register_hook 的返回值、pf、hooknum
insmod 报错 Invalid argument 优先级或 hooknum 填了非法值
rmmod 报 Resource temporarily unavailable 模块还被引用，或者注销路径没走干净

测试别在生产机上做，用虚机或者容器里起个 netns。丢 ICMP 看着无害，某些监控系统靠 ping 探活，一丢就是一堆告警。

十二、易错点速查 #

现象 原因 怎么查
规则加了不生效 挂错表或挂错链 iptables -t nat -L -n -v 看计数器涨不涨
DNAT 不生效 挂到了 FORWARD 或 INPUT NAT 的目的地址改写只能在 PREROUTING、OUTPUT
SNAT 不生效 挂到了 PREROUTING 源地址依赖出口，只能在 POSTROUTING、INPUT
模块卸载后内核崩 忘了 nf_unregister_hook() 每个 module_init 必须有配对的 module_exit
注销瞬间 oops 还有包正跑在钩子函数里 注销前等 RCU 宽限期，照现成模块写
钩子收不到包 nf_register_hook() 返回负值被忽略 检查返回值，检查 pf 和 hooknum
钩子收不到包 优先级低于传入的 thresh 被跳过 确认调用方传的 thresh
同优先级的顺序乱 注册顺序决定，等值不保证 给不同的 priority，别依赖插入顺序
钩子函数里 oops 睡了、拿了会阻塞的锁 软中断上下文，不能 msleep、不能等信号量
内存一直涨 返回 NF_STOLEN 却没释放 skb 接管了就得自己 kfree_skb()
自己写的日志刷屏 没做速率限制 用 pr_info_ratelimited()
改了地址包不出去 没重新查路由 改完设 IPSKB_REROUTED 并触发重路由
返回 ACCEPT 却没拦住 后面的钩子把它丢了 同一个点上不止你一个，verdict 要全链路看
以为 nf_hooks[2][0] 可以直接当 hooknum 那是数组下标 hooknum 传 NF_INET_* 枚举值

最后一条值得多看一眼。nf_hooks[2][0] 是内核内部的二维数组下标，hooknum 是给注册者用的枚举，两者的数值在这里恰好都从 0 开始，很容易被当成一回事。写模块时只传 NF_INET_*，别手写数字。

到这里，Netfilter 的骨架就完整了：五个点钉在协议栈固定的位置，钩子按优先级排队，包经过时逐个过审，verdict 决定它往哪走。剩下的所有复杂功能——状态检测、NAT、限速、打标记——都是往这几个点上挂钩子的具体做法。
