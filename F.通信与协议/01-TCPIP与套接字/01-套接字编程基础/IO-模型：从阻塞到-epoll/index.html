这篇讲服务器性能的理论底座：一次 IO 到底把时间花在哪，五种 IO 模型各自怎么处理这段时间。

讲什么：IO 的两个阶段、阻塞与非阻塞、同步与异步、五种 IO 模型（阻塞 / 非阻塞 / 多路复用 / 信号驱动 / 异步）、select 与 poll 的接口和就绪条件、epoll 的三个接口、水平触发与边缘触发、五种模型的选型、易错点。

不讲什么：socket/bind/listen/accept 的参数细节、TCP 三次握手与状态机、套接字选项的调优、UDP 与广播。这些各有专篇。

跨篇指路：

  • socket 函数族、地址结构体、字节序转换 → 同组《套接字与网络字节序》
  • 回声服务器、完整可编译的并发改造 → 同组《TCP 套接字编程》

读完你应该能回答三个问题：为什么非阻塞 IO 单独用是浪费 CPU；为什么 select 被叫作「同步」却又「不阻塞」；为什么 epoll 的 ET 模式漏读一次就再也收不到通知。

一、IO 到底在等什么 #

从一行代码开始。

c
n = recv(fd, buf, sizeof(buf), 0);

这行调用返回时，buf 里有了数据。数据是从哪来的？很多人第一反应是「从网卡来的」。不准确。网卡收到的是一串电信号，协议栈把它拼成报文，校验、去头、按四元组找到对应的 socket，再把载荷放进这个 socket 在内核里的接收缓冲区。recv 干的事，是把内核缓冲区里的字节搬进你的 buf。

所以一次 socket 读操作，中间隔着两个完全不同的世界：内核态和用户态。两块内存：内核的 socket 接收缓冲区和你的用户缓冲区。搬运动作由内核做，你只负责发出请求、等它做完。

一次输入操作拆成两个阶段：

  1. 等数据准备好。数据从网络到达，被协议栈放进内核的 socket 接收缓冲区。
  2. 从内核向进程复制数据。把内核缓冲区里的字节拷进应用进程的缓冲区。

第一阶段等的是网络和对端。第二阶段等的是内存带宽和 CPU。

画成时间轴更清楚：

text
recv 调用
  │
  ├──── 阶段一：等数据就绪 ────┐        这段时间长度不可控
  │    （对端什么时候发、发多少，你说了不算）
  │                            │
  ├──── 阶段二：拷数据 ────────┘        这段时间由数据量决定
  │    （内核缓冲区 → 用户缓冲区）
  ▼
recv 返回

这两个阶段的耗时比例，决定了服务器的性能上限。阶段二的成本基本固定：数据量定了，拷贝就是那么久，再优化也省不了多少。阶段一才是变量。对端十毫秒后发数据，还是十分钟后发，还是永远不发，你说了不算。一个连接上如果没事干，你的线程就卡在阶段一里干耗。

于是所有 IO 模型要解决的问题只有一个：阶段一这段时间，怎么处理。

不光是套接字。读磁盘、读管道、读终端，都是这两段。你敲键盘，字符先在终端驱动的缓冲区里排着，read 的第一阶段等的是「你按下回车」，第二阶段才是把字符拷给你。

五种 IO 模型的差别，全在「等」这一段怎么处理：

模型 等数据就绪 拷数据 一句话
阻塞 IO 进程睡在调用里 进程睡在调用里 死等
非阻塞 IO 反复问，问一次返回一次 进程睡在调用里 反复问
IO 多路复用 睡在 select/epoll 上，一次盯一批 进程自己拷 一次问一批
信号驱动 IO 等内核发 SIGIO 通知 进程自己拷 等通知
异步 IO 内核全包，完成后才通知 内核全包 内核全包

注意最后一列。前四种模型在阶段二上完全一样：数据到了内核缓冲区，进程得自己调 recvfrom 去拷，这一拷就阻塞。只有异步 IO 把阶段二也交给内核。这一条差异，后面会反复用到，它是「同步」与「异步」的分界线。

二、阻塞与非阻塞 #

先看阻塞。

最流行的 IO 模型是阻塞式 IO（blocking I/O）。默认情况下，所有的套接字都是阻塞的。

阻塞调用的定义：调用结果返回之前，当前线程被挂起。挂起指线程进入非可执行状态，在这个状态下 CPU 不会给它分配时间片，线程暂停运行。函数只有在拿到结果之后才返回。

以数据报套接字为例，进程调用 recvfrom：

text
进程                                内核
  │                                  │
  │── recvfrom ─────────────────────►│
  │                                  │  等数据报到达
  │   （进程被挂起，不占 CPU）         │  把数据报拷进内核缓冲区
  │                                  │  再拷进用户缓冲区
  │◄───────────────── 返回数据报 ─────│
  │                                  │
处理数据报

系统调用一直到数据报到达、被拷贝到应用进程的缓冲区，或者发生错误，才返回。最常见的错误是系统调用被信号中断。从调用 recvfrom 开始到它返回的整段时间里，进程都是被阻塞的。recvfrom 成功返回后，进程才开始处理数据报。

有个误会要先拆掉：阻塞不等于慢。阻塞的意思是「这段时间你什么都干不了」。数据一秒后来，线程就睡一秒；数据十分钟后来，线程就睡十分钟。CPU 不用为这段睡眠付钱，代价在别处——这个线程被占住了，它没法去服务第二个连接。

一个线程一个连接，就是阻塞 IO 的宿命。十个客户端要十个线程，一千个客户端要一千个线程。线程本身要栈、要调度、要上下文切换，一千个线程的空转和切换开销能把机器吃干净。这就是服务器并发模型要单独开一篇讲的原因。

非阻塞和阻塞的概念相对应：在不能立刻得到结果之前，函数不阻塞当前线程，而立刻返回。

把套接字设置成非阻塞，等于通知内核：当所请求的 IO 操作非得把本进程投入睡眠才能完成时，不要把本进程投入睡眠，而是返回一个错误。

还是那段 recvfrom，前三次调用没有数据可返回，内核转而立即返回一个 EWOULDBLOCK 错误。第四次调用时已经有一个数据报准备好，它被复制到应用程序缓冲区，recvfrom 成功返回，我们接着处理数据。

text
第 1 次 recvfrom  →  EWOULDBLOCK（没数据）
第 2 次 recvfrom  →  EWOULDBLOCK（还没数据）
第 3 次 recvfrom  →  EWOULDBLOCK（仍然没数据）
第 4 次 recvfrom  →  成功，拷贝完成，返回字节数

EWOULDBLOCK 和 EAGAIN 在 Linux 上是同一个值。你写代码判断哪一个都行，看 EWOULDBLOCK 更符合语义。

一个应用进程像这样对一个非阻塞描述符循环调用 recvfrom，我们称之为轮询（polling）。应用程序持续轮询内核，查看某个操作是否就绪。

轮询的代码长这样：

c
int n;
while ((n = recv(fd, buf, sizeof(buf), 0)) < 0) {
    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        continue;   /* 没数据，马上再问一次 */
    }
    perror("recv");
    break;
}

这样做往往耗费大量 CPU 时间。continue 转一圈就是一次系统调用，一次系统调用就是一次用户态到内核态的切换。数据没到的时候，这个循环百分之百的运行时间都在做无用功，而且它把 CPU 占死了，同一台机器上的其他进程抢不到时间片。

设置非阻塞有两个口子：

c
/* 推荐：fcntl 取旧标志再按位或，别直接覆盖 */
int flags = fcntl(fd, F_GETFL, 0);
fcntl(fd, F_SETFL, flags | O_NONBLOCK);

/* 老写法：ioctl */
int on = 1;
ioctl(fd, FIONBIO, &on);

要回到阻塞，同样是 fcntl，把 O_NONBLOCK 位清掉。accept 出来的新连接不继承监听套接字的非阻塞标志，Linux 上要单独设一遍——这是后面易错点里的一条。

三、同步与异步 #

这一节是整篇最容易讲岔的地方。

先把 POSIX 的定义摆出来：

  • 同步 IO 操作（synchronous I/O operation）导致请求进程阻塞，直到 IO 操作完成。
  • 异步 IO 操作（asynchronous I/O operation）不导致请求进程阻塞。

定义干净，判据只有一个：真正的 IO 操作（数据从内核缓冲区拷到用户缓冲区）这一步，是谁在等。进程自己在等，就是同步。内核把数据拷完了才来通知你，才是异步。

按这个判据回头看那五种模型：

  • 阻塞 IO 是同步的。进程睡在 recvfrom 里，一直睡到拷贝完成。
  • 非阻塞 IO 是同步的。轮询到数据就绪，然后调 recvfrom 拷数据，拷的时候照样阻塞。
  • IO 多路复用的前四种模型都是同步的。select 返回只代表「数据可以读了」，真正的 recvfrom 还得你自己调，拷数据这一步照样阻塞进程。
  • 信号驱动 IO 是同步的。SIGIO 只告诉你「可以启动了」，recvfrom 还得自己调。
  • 只有异步 IO 与 POSIX 定义的异步 IO 相匹配。内核把数据拷进你的缓冲区之后，才通知你。

前面四种模型的主要区别在于第一阶段。第二阶段是一样的：数据从内核复制到调用者的缓冲区期间，进程阻塞于 recvfrom 调用。异步 IO 模型在两个阶段都要处理，从而不同于其他四种模型。

所以有一句话要背下来：select 是同步的，它只是非阻塞地等。

这两个概念是两组独立的轴，不是一根滑杆的两端。

阻塞 非阻塞
同步 默认 socket 上的 read/recv 轮询 recv，或 select/epoll 等就绪后自己 recv
异步 几乎没有实际意义 aio_read / io_uring，内核拷完再回调

四个格子都有内容，说明两件事不冲突。阻塞与非阻塞描述的是「调用返回的方式」：调用是立刻返回，还是卡住等到有结果。同步与异步描述的是「IO 操作由谁完成并等待」：是进程自己完成并等待，还是内核完成后再通知进程。

很多资料把这两组概念混成一团，说着说着就出现「异步非阻塞」「同步阻塞」这种把两件事焊在一起的词。词本身没错，错在拿它当分类标准。真正的分类标准只有一条：拷数据那一段，谁在等。

顺带澄清一个流传很广的叫法。IO 多路复用模型常被叫作「异步阻塞 IO」：select 调用会阻塞线程，所以是「阻塞」；用户线程注册完就去干别的，所以是「异步」。这个叫法能用，但很容易把人带偏——它说的「异步」是「你不需要盯着」，不是 POSIX 定义的异步。在 POSIX 的语境里，select 加 recv 这一套是彻头彻尾的同步 IO。

还有一个缩写坑：非阻塞 IO 写成 NIO 时，别跟 Java 的 NIO（New IO）库混。Java 的 NIO 是另一套东西，底层用的是多路复用。

至于「异步阻塞 IO」里的那个「阻塞」指的是什么，也要说清：指的是 select 函数执行时线程被阻塞，不是指 socket 被阻塞。用多路复用时 socket 多数会设成 O_NONBLOCK，这不会带来麻烦，因为用户发起 recv 时数据已经到了，那一次调用不会被阻塞。

四、五种 IO 模型总览 #

Unix 下可用的 5 种 IO 模型，一份清单：

  1. 阻塞 IO
  2. 非阻塞 IO
  3. IO 复用（select 和 poll）
  4. 信号驱动 IO（SIGIO）
  5. 异步 IO（POSIX 的 aio_ 系列函数）

把五条时间轴并排画在一起，差异一眼可见。竖线是「调用发起」，横线长度是「进程不干活的时间」：

text
阻塞 IO      ├████████ 等数据 ████████├██ 拷 ██┤
非阻塞 IO    ├问┤问┤问┤问┤问┤问┤问┤问├██ 拷 ██┤
多路复用     ├████ select 等一批 ████├██ 拷 ██┤
信号驱动     ├──── 干自己的事 ────┤SIGIO├██ 拷 ██┤
异步 IO      ├──────── 干自己的事 ────────┤数据已就位┤

对着这张图读三条结论。

第一条，前四条的「拷」都一样长，都是进程自己动手。只有异步 IO 把这一段吃进内核，进程被通知的时候数据已经在自己的缓冲区里了。

第二条，非阻塞 IO 的那串「问」全在阶段一。它没有省掉等待，只是把等待摊成了一堆立刻返回的系统调用。

第三条，多路复用的黑条并不比阻塞 IO 短，一个 fd 的时候甚至更长——它多了一次 select 调用。它的价值在「一批」：黑条覆盖的是 N 个 fd，摊到每个 fd 上就短了。

模型的骨架对照：

模型 关键函数 进程阻塞在哪 一次能等几个 fd 阶段二谁拷
阻塞 IO recvfrom 调用里，直到拷贝完 1 个 进程
非阻塞 IO recvfrom 只在拷贝那一瞬 1 个 进程
IO 多路复用 select / poll / epoll_wait 多路分离函数上 一批 进程
信号驱动 IO sigaction + recvfrom 只在自己调 recvfrom 时 取决于信号 进程
异步 IO aio_read 全程不阻塞 多个 内核

一个容易忽略的细节：多路复用模型比阻塞 IO 多了一次「两次调用、两次返回」。对一个 IO 端口来说，这并没有优越性，纯属倒贴。它的全部意义在「同时」。

五、阻塞 IO #

这是最直觉的模型，也是默认行为。

c
n = recv(fd, buf, sizeof(buf), 0);   /* 没数据就睡，睡到有数据 */
if (n > 0) {
    process(buf, n);
}

数据没到，进程就挂在这个调用上。挂起期间不占 CPU，也不响应任何别的事。数据到了、拷完了，调用返回字节数，代码往下走。

阻塞 IO 的优点：

  • 代码简单。一个连接一个循环，读-处理-写，顺序直白。
  • 不浪费 CPU。等的时候真的在睡，调度器不用管它。
  • 出错路径清楚。要么返回正数，要么 0（对端关闭），要么 -1。

缺点也直接：

  • 一个线程同时只能盯一个 fd。要服务 N 个连接就得 N 个线程（或多进程）。
  • 线程和连接绑死。连接空闲时线程也空闲，但它占着栈和调度名额。
  • 规模上不去。几千个连接意味着几千个线程，上下文切换和内存占用两笔账都难看。

阻塞调用被打断要单独处理。系统调用被信号中断时返回 -1，errno 为 EINTR。这不是错误，重来一次就行：

c
do {
    n = recv(fd, buf, sizeof(buf), 0);
} while (n < 0 && errno == EINTR);

漏了这一层，你的服务器会在收到 SIGCHLD、SIGALRM 之类的信号时莫名其妙地退出。多进程服务器里这个坑几乎必踩。

阻塞 IO 并不是过时的东西。它的替代方案是「每连接一个线程」——Thread-per-Connection。这个模型在连接数可控（几百以内）、每个连接的事都不轻（比如要查库、要算）时，比多路复用更省心，调试也更好受。真正让它失宠的是海量长连接：C10K 那种场景，一个连接一个线程撑不住。

六、非阻塞 IO #

把 socket 设成 O_NONBLOCK，recv 的行为就变了：没数据立刻返回 EWOULDBLOCK，不等。

上一节那段 recv 改成循环：

c
int n;
for (;;) {
    n = recv(fd, buf, sizeof(buf), 0);
    if (n > 0) {
        process(buf, n);
        break;
    }
    if (n == 0) {
        break;                        /* 对端关了 */
    }
    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        continue;                     /* 没数据，再来一次 */
    }
    perror("recv");
    break;
}

这段代码和阻塞版的区别只有一个：没数据的时候它不退让，立刻重来。

问题就出在这。循环转一圈是一次系统调用，一次系统调用是一次特权级切换。数据没到的时候，这个循环烧掉百分之百的 CPU，产出的结果为零。更糟的是它不释放 CPU，同机器上的其他进程抢不到时间片。轮询的另一个变种是加个 usleep 让一让，但睡多久全靠猜：睡短了还是空转，睡长了延迟上去了。

所以，非阻塞 IO 单独用没有意义。它几乎总是作为别的模型的零件出现。

  • 在多路复用里：select 告诉你哪个 fd 就绪，recv 用非阻塞模式去读，读到 EAGAIN 就收手。
  • 在 ET 模式的 epoll 里：必须用非阻塞，因为 epoll_wait 只通知一次，你得一口气读到 EAGAIN 为止。
  • 在 accept 循环里：非阻塞 accept 才能安全地把就绪队列一次抽干。

三个阶段的行为，写代码时要分清楚：

调用结果 含义 该做什么
返回值 > 0 读到 n 字节 处理数据，按需继续读
返回 0 对端关闭了写端 close(fd)，从监听集合摘掉
返回 -1，EAGAIN 暂时没数据 收手，回去等通知
返回 -1，EINTR 被信号打断 重试
返回 -1，其他 真错误 记日志，关 fd

EAGAIN 不是错误，是「现在没有」的礼貌说法。把它当错误处理，服务器会随机踢掉健康连接。

非阻塞还有个副作用要留意：它影响的是这个 fd 上所有会阻塞的调用，包括 read、write、accept、connect。非阻塞 connect 会立刻返回 EINPROGRESS，得靠 select 可写或 SO_ERROR 去确认连上没有。写侧也一样：write 返回 EAGAIN 说明发送缓冲区满了，得把剩下的数据缓存起来，等下次可写再发。这就是「写半包」问题，写服务器时绕不开。

七、IO 多路复用 #

一句话说清它的定位：一次系统调用，问一批 fd 谁就绪了。

主要可以调用 select、poll、epoll。对一个 IO 端口，两次调用、两次返回，比阻塞 IO 并没有什么优越性。关键是能实现同时对多个 IO 端口进行监听，可以等待多个描述符就绪。

这几个函数也会使进程阻塞，但和阻塞 IO 不同：它们可以同时阻塞多个 IO 操作，同时对多个读操作、多个写操作的 IO 函数进行检测，直到有数据可读或可写时，才真正调用 IO 操作函数。

text
用户线程                                  内核
  │                                        │
  │── select(fd_set) ─────────────────────►│  盯着集合里所有 fd
  │                                        │  一个都没就绪 → 睡着
  │                                        │  fd 7 有数据了
  │◄──────────── 返回，fd 7 置位 ──────────│
  │                                        │
  │── recv(7, ...) ───────────────────────►│  拷贝（这一段照样阻塞）
  │◄──────────── 数据 ────────────────────│

单线程服务多个连接的骨架：

c
fd_set rfds;
int maxfd = listenfd;

FD_ZERO(&rfds);
FD_SET(listenfd, &rfds);

while (1) {
    fd_set cur = rfds;                  /* 每次都要重新拷一份，见下一章 */
    int n = select(maxfd + 1, &cur, NULL, NULL, NULL);
    if (n < 0 && errno == EINTR) continue;

    for (int i = 0; i <= maxfd; i++) {
        if (!FD_ISSET(i, &cur)) continue;
        if (i == listenfd) {
            int c = accept(listenfd, NULL, NULL);
            FD_SET(c, &rfds);
            if (c > maxfd) maxfd = c;
        } else {
            /* 就绪的连接，读一次 */
        }
    }
}

注意 select 的第一个参数是「最大 fd 加一」，不是 fd 个数。这个 +1 忘掉的人不少，后果是最后一个 fd 永远不生效。

多路复用为什么值得？把话说透：

  • 从流程上看，用 select 做一次 IO 请求，和同步阻塞模型没太大区别，还多了添加监视 fd、调用 select 的开销。
  • 但它最大的优势是一个线程内同时处理多个 socket 的 IO 请求。注册一批 fd，不断调用 select 读取被激活的那个，就在单线程里做到了阻塞模型必须多线程才能做到的事。
  • 线程数从「跟连接数走」变成「跟 CPU 核数走」。这一条，是它能撑住 C10K 的全部原因。

这套机制有个名字：Reactor 设计模式。结构不复杂：

  • EventHandler：抽象类，持有 IO 句柄 Handle（通过 get_handle 取），以及操作句柄的 handle_event（读 / 写等）。子类定制具体行为。
  • Reactor：管理 EventHandler 的注册与删除，用 handle_events 跑事件循环，不断调用内核的多路分离函数 select。
text
        ┌─────────────┐
        │   Reactor   │  handle_events() 死循环
        │             │  ├─ select() 等就绪
        └──┬───────┬──┘  └─ 分发 handle_event
           │       │
    ┌──────▼──┐ ┌──▼───────┐
    │Handler A│ │Handler B │   各自绑定一个 fd
    └─────────┘ └──────────┘

用户自己写的部分：

c
void UserEventHandler::handle_event() {
    if (can_read(socket)) {
        read(socket, buffer);
        process(buffer);
    }
}

/* 注册阶段：把 handler 挂到 Reactor 上就行 */
Reactor.register(new UserEventHandler(socket));

Reactor 那侧的循环：

c
Reactor::handle_events() {
    while (1) {
        sockets = select();
        for (socket in sockets) {
            get_event_handler(socket).handle_event();
        }
    }
}

通过 Reactor，用户线程轮询 IO 状态的工作统一交给了 handle_events 事件循环。用户线程注册完事件处理器就可以去干别的，Reactor 线程负责调内核的 select 检查 socket 状态；某个 socket 被激活，就调对应的 handle_event 去读数据、处理数据。

多路复用是最常使用的 IO 模型，但它的异步程度不够彻底——它内部用的是会阻塞线程的 select 系统调用。所以它只能叫「异步阻塞 IO」，不是真正的异步 IO。真正异步的门槛在后面的对比表里。

八、select 与 poll #

select 干的事：允许进程指示内核等待多个事件中的任何一个发生，并在有一个或多个事件发生、或者经历一段指定时间之后唤醒它。

举个例子，我们可以调用 select，告知内核仅在下列情况发生时才返回：

  1. 集合 { 1, 4, 5 } 中任何描述符准备好读
  2. 集合 { 2, 7 } 中任何描述符准备好写
  3. 集合 { 1, 4 } 中任何描述符有异常条件待处理

也就是说，我们通过 select 告知内核：对哪些描述符（读、写或异常条件）感兴趣，以及愿意等多久。感兴趣的描述符不局限于套接字，任何描述符都能用 select 测试。这一点有时很有用——标准输入、管道、终端都能塞进同一个循环里。

函数原型：

c
#include <sys/select.h>
#include <sys/time.h>

int select(int maxfdp1, fd_set *readset, fd_set *writeset,
           fd_set *exceptset, const struct timeval *timeout);

struct timeval {
    long tv_sec;    /* seconds */
    long tv_usec;   /* microseconds */
};

从最后一个参数 timeout 说起，它告知内核：等待指定描述符中任何一个就绪，可以花多长时间。timeval 结构用秒和微秒指定这段时间。这个参数有三种取值：

取值 行为 说明
空指针 NULL 永远等下去 仅在有一个描述符准备好 IO 时才返回
指向一个正值的 timeval 等一段固定时间 有描述符就绪就返回，不超时也返回
指向全零的 timeval 根本不等待 检查完立即返回，这叫轮询（polling）

中间的三个参数 readset、writeset、exceptset 指定要让内核测试读、写、异常条件的描述符。

select 用描述符集，本质上是一个整数数组，每个整数里的每一位对应一个描述符。假设用 32 位整数，那么数组的每个元素对应描述符 0~31，第二个元素对应 32~63，依次类推。它们被包装成 fd_set 数据类型，配四个宏：

c
void FD_ZERO(fd_set *fdset);            /* 清空集合里所有描述符 */
void FD_SET(int fd, fd_set *fdset);     /* 把 fd 加进集合 */
void FD_CLR(int fd, fd_set *fdset);     /* 把 fd 从集合里清掉 */
int  FD_ISSET(int fd, fd_set *fdset);   /* 判断 fd 是否在集合里 */

定义一个 fd_set，然后打开描述符 1、4、5 对应的位：

c
fd_set rset;
FD_ZERO(&rset);
FD_SET(1, &rset);
FD_SET(4, &rset);
FD_SET(5, &rset);

描述符集的初始化非常关键。作为自动变量分配的一个描述符集如果没有初始化，里面是栈上的垃圾值，后果不可预期。FD_ZERO 不能省。

还有一处是 select 最反直觉的设计。select 函数会修改由指针 readset、writeset、exceptset 指向的描述符集，所以这三个参数都是值-结果参数。调用时你指定所关心的描述符，函数返回时，结果指示哪些描述符就绪。返回后要用 FD_ISSET 逐个测。集合里与未就绪描述符对应的位，返回时全被清零。

结果是：每次重新调用 select，都得把关心的位重新置一遍。这个「拷一份、传进去、被改掉、再拷一份」的循环，是 select 性能问题的根源，也是 epoll 出现的理由。

返回值：表示跨所有描述符集的已就绪总位数。任何描述符就绪之前定时器到时，返回 0。返回 -1 表示出错。

select 能报什么，取决于内核怎么判定「就绪」。这个判定标准必须记牢，否则你会盯着一个「可读」的 fd 读不到数据。

可读，四种情况会置位：

  1. socket 接收缓冲区中的数据量大于或等于当前缓冲区的低水位线。此时 read 不会被阻塞，返回一个正值（读取的字节数）。低水位线可以通过 SO_RCVLOWAT 选项设定，对 TCP 和 UDP 来说默认值为 1。
  2. socket 连接的读端被关闭，比如 shutdown(socket, SHUT_RD) 或 close(socket)。底层此时会收到一个 FIN 包，read 不会被阻塞，但返回 0，代表读到 socket 末端。
  3. socket 是一个监听 socket，并且有新连接等待。此时 accept 不会被阻塞。
  4. 发生 socket 错误。此时 read 会返回 -1，可以通过 errno 取具体错误信息。

可写，四种情况会置位：

  1. socket 发送缓冲区中的可用空间大于或等于低水位线，并且满足以下条件之一：socket 已连接；或 socket 本身不要求连接，典型如 UDP。低水位线通过 SO_SNDLOWAT 设置，对 TCP 和 UDP 来说多为 2048。
  2. socket 连接的写端被关闭，比如 shutdown(socket, SHUT_WR) 或 close(socket)。在一个已经关闭写端的句柄上写数据会收到 SIGPIPE。
  3. 一个非阻塞的 connect 操作连接成功，或者 connect 操作失败。
  4. 发生 socket 错误。此时 write 会返回 -1，可以通过 errno 取具体错误信息。

异常，只有一种情况（针对带外数据）：收到带外数据（out-of-band），或者 socket 的带外数据标志未被清除。平时用不到，但它在，就说明 select 的三个集合不是对称的。

看一个能跑的例子。服务端用 select 同时盯住监听 fd 和所有已连接 fd，收到什么就回什么：

c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <arpa/inet.h>
#include <sys/socket.h>
#include <sys/select.h>

#define PORT    8888
#define MAXSIZE 128

int main(void)
{
    int i, nbyte;
    int listenfd, confd, maxfd;
    char buffer[MAXSIZE];
    fd_set global_rdfs, current_rdfs;
    struct sockaddr_in addr, clientaddr;
    int addrlen  = sizeof(struct sockaddr_in);
    int caddrlen = sizeof(struct sockaddr_in);

    if ((listenfd = socket(AF_INET, SOCK_STREAM, 0)) == -1) {
        perror("socket error");
        exit(-1);
    }
    printf("socket successfully!\n");
    printf("listenfd : %d\n", listenfd);

    memset(&addr, 0, addrlen);
    addr.sin_family      = AF_INET;
    addr.sin_port        = htons(PORT);
    addr.sin_addr.s_addr = htonl(INADDR_ANY);

    if (bind(listenfd, (struct sockaddr *)&addr, addrlen) == -1) {
        perror("bind error");
        exit(-1);
    }
    printf("bind successfully!\n");
    printf("listen port:%d\n", PORT);

    if (listen(listenfd, 5) == -1) {
        perror("listen error");
        exit(-1);
    }
    printf("listening...\n");

    maxfd = listenfd;
    FD_ZERO(&global_rdfs);
    FD_SET(listenfd, &global_rdfs);

    while (1) {
        current_rdfs = global_rdfs;              /* 值-结果参数，每轮都要重置 */
        if (select(maxfd + 1, &current_rdfs, NULL, NULL, 0) < 0) {
            perror("select error");
            exit(-1);
        }

        for (i = 0; i <= maxfd; i++) {
            if (!FD_ISSET(i, &current_rdfs)) {
                continue;
            }
            if (i == listenfd) {
                if ((confd = accept(listenfd,
                                    (struct sockaddr *)&clientaddr,
                                    &caddrlen)) == -1) {
                    perror("accept error");
                    exit(-1);
                }
                printf("Connect from [IP:%s PORT:%d]\n",
                       inet_ntoa(clientaddr.sin_addr),
                       ntohs(clientaddr.sin_port));
                FD_SET(confd, &global_rdfs);
                if (confd > maxfd) {
                    maxfd = confd;
                }
            } else {
                nbyte = recv(i, buffer, sizeof(buffer) - 1, 0);
                if (nbyte < 0) {
                    perror("recv error");
                    exit(-1);
                } else if (nbyte == 0) {
                    close(i);
                    FD_CLR(i, &global_rdfs);
                } else {
                    buffer[nbyte] = '\0';
                    printf("recv:%s\n", buffer);
                    send(i, buffer, nbyte, 0);
                }
            }
        }
    }
    return 0;
}

跑起来像这样：

text
fs@ubuntu:~$ ./select_srv
socket successfully!
listenfd : 3
bind successfully!
listen port:8888
listening...
Connect from [IP:192.168.3.51 PORT:1992]
recv:hello
Connect from [IP:192.168.3.53 PORT:2248]

几个坑在这段代码里全占了：

  • current_rdfs = global_rdfs 这一句不能挪出循环。select 会把没就绪的位清零，不重置就只剩第一轮管用。
  • listenfd 和 confd 都放在同一个循环里判 FD_ISSET，靠 i == listenfd 区分。
  • maxfd 只增不减。有连接关闭时它没跟着降，代价是每轮多扫几个空位，不影响正确性。
  • 收到 0 字节要 close 加 FD_CLR，只 close 不 FD_CLR 会让下一轮 select 拿着一个已关闭的 fd 报错。

select 有一个绕不过去的上限。fd_set 是位图，位数由 FD_SETSIZE 决定，Linux 上默认 1024。这意味着一个 select 循环最多盯 1024 个 fd。想改就得改宏并重新编译内核和 libc，不现实。这是 select 在服务器上被淘汰的直接原因。

poll 是同一思路的修补版。它不用位图，用结构体数组：

c
#include <poll.h>

int poll(struct pollfd *fdarray, unsigned long nfds, int timeout);

struct pollfd {
    int   fd;        /* 要检查的描述符 */
    short events;    /* 感兴趣的事件 */
    short revents;   /* 实际发生的事件（内核填） */
};

events 里填 POLLIN、POLLOUT、POLLERR 这些标志。poll 返回时，内核把结果写进 revents，所以「输入」和「输出」分开了，不需要每次调用前重置。

poll 解掉了 1024 的数量限制，也免掉了每轮重置位图的麻烦。但它的问题没解决：每调一次，整个 pollfd 数组还是从用户态拷进内核态，内核对每个元素还是线性扫一遍。fd 越多，这两笔开销越大。

对比项 select poll
数据结构 fd_set 位图 pollfd 数组
数量上限 FD_SETSIZE，默认 1024 无上限，只受内存限制
每次调用是否要重置 要，select 会改写集合 不要，revents 由内核填
事件与 fd 的分离 三个集合分开传 一个结构体带 events / revents
用户态到内核态的拷贝 每轮拷三个位图 每轮拷整个数组
内核扫描方式 线性扫位数 线性扫数组元素
超时精度 微秒 毫秒

九、epoll 的三个接口 #

epoll 换了一套思路：注册一次，之后只取结果。

三个函数，一个都不多：

c
int epoll_create(int size);                                    /* 1. 建个实例 */
int epoll_ctl(int epfd, int op, int fd, struct epoll_event *ev); /* 2. 增删改关注 */
int epoll_wait(int epfd, struct epoll_event *evs,
               int maxevents, int timeout);                    /* 3. 取就绪 */

epoll_create 返回一个 epoll 实例的 fd，size 在早期内核里是「预计监视多少个 fd」的提示，现在被忽略，传个大于 0 的数就行。

epoll_ctl 是注册动作，op 取三个值：

op 含义
EPOLL_CTL_ADD 把 fd 加进监听集合，注册感兴趣的事件
EPOLL_CTL_MOD 改一个已在集合里的 fd 的感兴趣事件
EPOLL_CTL_DEL 摘掉一个 fd

事件结构体：

c
struct epoll_event {
    uint32_t     events;    /* EPOLLIN / EPOLLOUT / EPOLLET / EPOLLONESHOT ... */
    epoll_data_t data;      /* 用户数据，常用 .fd 或 .ptr */
};

epoll_wait 取结果，返回就绪的 fd 个数，maxevents 是这次最多取几个，timeout 是毫秒（-1 表示一直等，0 表示立刻返回）。

epoll 快在哪，三句话说清：

  • 监听集合存在内核的一棵红黑树里。注册一次就一直在，epoll_wait 不需要把整个集合从用户态拷进去。select / poll 每轮都要拷，select 拷三个位图，poll 拷整个数组。
  • 内核把就绪的 fd 挂到一条就绪链表上。epoll_wait 只要看这条链表有没有东西，不用线性扫描全部 fd。select 每次调用都要把位图扫一遍，fd 越多越慢。
  • 数量没有上限，只受能打开多少 fd 限制（ulimit -n）。

一个最小的 epoll 服务端骨架：

c
#include <sys/epoll.h>

#define MAXEVENTS 64

int epfd = epoll_create(1);
struct epoll_event ev, events[MAXEVENTS];

ev.events  = EPOLLIN;
ev.data.fd = listenfd;
epoll_ctl(epfd, EPOLL_CTL_ADD, listenfd, &ev);

while (1) {
    int n = epoll_wait(epfd, events, MAXEVENTS, -1);
    for (int i = 0; i < n; i++) {
        int fd = events[i].data.fd;

        if (fd == listenfd) {
            int c = accept(listenfd, NULL, NULL);
            set_nonblock(c);
            ev.events  = EPOLLIN | EPOLLET;      /* 边缘触发，见下一章 */
            ev.data.fd = c;
            epoll_ctl(epfd, EPOLL_CTL_ADD, c, &ev);
        } else if (events[i].events & EPOLLIN) {
            /* 读，一直读到 EAGAIN */
        } else if (events[i].events & EPOLLERR) {
            epoll_ctl(epfd, EPOLL_CTL_DEL, fd, NULL);
            close(fd);
        }
    }
}

三个接口的用量对比，一眼看出 epoll 的调用次数是常数级：select 每轮一次调用传全量，epoll 只在增删改时调 epoll_ctl，事件循环里只调 epoll_wait。

对比项 select poll epoll
fd 数量上限 1024（FD_SETSIZE） 无 无（受 ulimit -n）
内核里的数据结构 无，每次重建 无，每次重建 红黑树 + 就绪链表
每次调用是否拷贝整个集合 是，三个位图 是，整个数组 否，只在 epoll_ctl 时拷
判断谁就绪的方式 线性扫位图 线性扫数组 直接取就绪链表
时间复杂度 O(n) O(n) O(就绪数)
触发模式 只有水平触发 只有水平触发 水平 + 边缘
跨平台 全平台 全平台 Linux 专有
适用规模 几百以内 几百到几千 万级以上

一句话收尾：select 的限制不在「1024」这个数字本身，而在「每轮全量拷进内核 + 线性扫一遍」这个做法。1024 只是把这套做法撑不住的地方提前画了条线。

十、水平触发与边缘触发 #

epoll 比 select / poll 多给了一个开关：事件怎么通知。水平触发（Level Triggered，LT）和边缘触发（Edge Triggered，ET）。这个开关决定了你的读取循环写成什么样，也决定了一批线上事故。

先用一句话记住差别：LT 看的是「状态」，ET 看的是「变化」。

text
缓冲区里有数据的时长：   ├────────────────────┤
LT 通知：                ↑        ↑        ↑
                       （还有数据就一直叫）

ET 通知：                ↑
                       （只在从空变满那一刻叫一次）

epoll 默认是 LT。想用 ET，注册时加 EPOLLET：

c
ev.events  = EPOLLIN | EPOLLET;
ev.data.fd = fd;
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev);

行为差异写进代码里就非常具体。LT 的读法，读一次就走，剩下的下次再说：

c
/* LT：读多少算多少，没读完下次 epoll_wait 还会返回这个 fd */
n = recv(fd, buf, sizeof(buf), 0);
if (n > 0) process(buf, n);

ET 的读法，必须一次读到 EAGAIN：

c
/* ET：必须循环读到 EAGAIN，否则剩下的数据没有第二次通知 */
for (;;) {
    n = recv(fd, buf, sizeof(buf), 0);
    if (n > 0) {
        process(buf, n);
        continue;
    }
    if (n == 0) {                 /* 对端关闭 */
        close(fd);
        break;
    }
    if (errno == EAGAIN || errno == EWOULDBLOCK) {
        break;                    /* 读干净了，收手 */
    }
    if (errno == EINTR) continue;
    perror("recv");
    break;
}

ET 模式下这个 for 循环不是可选的。假设缓冲区里有 10 KB，你的 buf 只有 1 KB，读一次只拿走 1 KB。LT 下一轮 epoll_wait 还会告诉你「这个 fd 可读」，剩下的 9 KB 迟早读走。ET 不会再有第二次通知——「可读」这个状态没有再次发生变化，内核认为你已经知道了。剩下的 9 KB 就烂在缓冲区里，直到对端再发一个包触发下一次变化。

这就是 ET 最典型的故障形态：连接不断、不报错、数据丢一半、业务层超时。抓包看数据都到了，程序里就是没有。查一天也查不出，因为代码看起来完全正常。

对比项 水平触发 LT 边缘触发 ET
通知条件 缓冲区还有数据就通知 只在状态变化时通知一次
一次 epoll_wait 能否重复返回同一 fd 能 不能
是否必须一次读到 EAGAIN 不必 必须
是否必须非阻塞 不必 必须
漏读的后果 下次还会通知，能自愈 数据滞留，不再通知，业务超时
通知次数 多 少
系统调用次数 多 少
代码难度 低，写错也不容易卡死 高，一处漏读就卡死
适合场景 通用，中小规模，逻辑复杂 高并发，追求少唤醒

ET 的效率优势在哪：epoll_wait 的返回次数少了，epoll_wait 的调用次数也跟着少了。数据一次到齐，一次通知、一次循环抽干，省掉大量「返回一次只读一点」的空转。代价是代码必须严丝合缝。

ET 配阻塞 fd 是自找麻烦。ET 要求「读到 EAGAIN」，阻塞 fd 上最后一次 recv 没有 EAGAIN，它会睡在那里等下一条数据。整个事件循环就此停摆，所有连接一起卡死。所以 EPOLLET 和 O_NONBLOCK 是一条绳上的两件事，缺一不可：

c
set_nonblock(fd);                  /* 这行在前 */
ev.events = EPOLLIN | EPOLLET;     /* 这行在后 */

ET 下 accept 也要循环。监听 fd 注册成 ET 之后，一次事件可以对应多个已完成握手的连接。只 accept 一次，剩下的连接躺在全连接队列里等下一个事件——而那个事件很久都不来：

c
for (;;) {
    int c = accept(listenfd, NULL, NULL);
    if (c < 0) {
        if (errno == EAGAIN || errno == EWOULDBLOCK) break;  /* 抽干了 */
        if (errno == EINTR) continue;
        break;
    }
    set_nonblock(c);
    add_to_epoll(epfd, c, EPOLLIN | EPOLLET);
}

还有一个配套的坑：一个 fd 上的事件如果交给线程池处理，多个线程会同时被唤醒去处理同一个 fd。要独占就用 EPOLLONESHOT，事件处理完后必须重新 epoll_ctl 加 EPOLL_CTL_MOD 把它挂回去，否则这个 fd 从此静默。

选 LT 还是 ET，别纠结理论。连接数在万级以内、逻辑分支多、团队里有人不熟这套，用 LT。压到十万级、要抠每一次唤醒、团队能把读写循环写死，用 ET。搞不清就用 LT，它容错。

十一、五种模型的对比与选型 #

把前面所有内容压进一张表。

模型 阶段一怎么等 阶段二谁拷 同步/异步 一个线程能管几个 fd 主要缺点
阻塞 IO 睡在 recvfrom 里死等 进程 同步 1 连接数 = 线程数
非阻塞 IO 反复 recvfrom 轮询 进程 同步 1 空转烧 CPU
IO 多路复用 睡在 select/epoll_wait，一次盯一批 进程 同步 一批 两次系统调用；逻辑分散
信号驱动 IO 内核发 SIGIO 通知 进程 同步 多个 信号处理难写，队列易溢出
异步 IO 内核全包，完成后回调 内核 异步 多个 支持不完善，库少

这张表的每一行，都在回答开篇那个问题：等数据这段时间怎么办。死等、反复问、一次问一批、等通知、内核全包。

再看两个设计模式的对应关系，它们在工程里比模型名字更常用：

Reactor Proactor
谁读数据 用户线程 内核
通知什么 「可以读了」 「已经读完了」
对应模型 IO 多路复用 异步 IO
编程模型 事件循环 + 回调 异步调用 + 完成回调
典型实现 epoll + 事件循环 IOCP、io_uring、Java AIO

Proactor 的结构跟 Reactor 长得很像，差别在用户怎么用。Reactor 里，用户线程向 Reactor 注册感兴趣的事件，事件触发时调用事件处理函数。Proactor 里，用户线程把异步操作（读 / 写等）、Proactor 本身、以及操作完成时的 CompletionHandler 一起注册给 AsynchronousOperationProcessor。

AsynchronousOperationProcessor 用 Facade 模式提供一组异步操作 API 给用户，用户调用后继续干自己的事。它内部开独立的内核线程执行异步操作，这才是真异步。操作完成时，它把用户注册的 Proactor 和 CompletionHandler 取出来，把结果数据和 CompletionHandler 一起转发给 Proactor，Proactor 回调对应的事件完成处理函数。

c
void UserCompletionHandler::handle_event(buffer) {
    process(buffer);        /* buffer 是内核已经拷好的数据，直接用 */
}

/* 注册阶段：把回调交给内核，然后立刻返回 */
aio_read(socket, new UserCompletionHandler);

代码只有这么多。用户重写 CompletionHandler::handle_event 处理数据，参数 buffer 是 Proactor 已经准备好的缓冲区。用户线程调完 aio_read 就往下走，数据到达、读取、拷进用户缓冲区全由内核做，做完才回调。

Proactor 在操作系统里多被实现成 Singleton，集中分发操作完成事件。每个异步操作理论上都能绑一个 Proactor 对象，实际不会这么干。

信号驱动 IO 为什么列在表里却少有人用，理由具体：SIGIO 信号不排队，TCP 上信号一到就意味着「有新数据」，但信号处理函数里能做的事很少，读写逻辑塞进信号上下文容易出问题；通知密集时信号会被合并，你收不到「每个包一次」的粒度。它适合的是少量、低频、状态简单的场景。

异步 IO 的现状要摆明。相比多路复用，异步 IO 并不十分常用。不少高性能并发服务用「IO 多路复用 + 多线程任务处理」的架构就能满足需求。操作系统对异步 IO 的支持也谈不上完善：Linux 原生 aio 长期只对 O_DIRECT 真正异步，缓冲 IO 会退化成同步；直到 io_uring 才把这套东西做实。更多时候大家用多路复用模拟异步：IO 事件触发时不直接通知用户线程，而是在把数据读写完放到用户指定缓冲区之后再回调。

Java 那边，Java 7 之后有了异步 IO 支持（AIO / NIO.2），Selector 则是多路复用的封装。

选型按规模来，别按名词来：

  • 连接数几十个，每个连接的计算都重（查库、编解码、算力密集）：阻塞 IO + 线程池。代码最短，问题最好查。
  • 连接数几百到几千，每个连接的数据量不大：select 或 poll 够用，代码直观。
  • 连接数上万，长连接多，事件稀疏：epoll 的 LT，稳。
  • 连接数十万级，每次唤醒都要省：epoll 的 ET，读写循环写死，配非阻塞。
  • 磁盘 IO 密集且内核支持：io_uring，这是当下真异步的方向。

还有一句要说给做业务的人：多路复用解决的是「等」的问题，不解决「算」的问题。事件循环里塞一个耗时操作，整条链路一起卡。读到了数据要处理，处理这段应该扔给线程池，事件循环只负责收发和分发。这就是「多路复用 + 线程池」成为标配的原因——它同时管住了等待和计算两件事。

十二、易错点速查 #

现象 根因 处理
select 第一轮正常，之后再也不返回 每轮没重新置位集合，被 select 清零了 循环内重新 FD_ZERO + FD_SET
最后一个 fd 永远没反应 select 第一个参数传成 maxfd 传 maxfd + 1
fd 数超过 1024 就乱 FD_SETSIZE 限制 换 poll 或 epoll
accept 报 EMFILE fd 用光了，连接还堆在队列里 预留一个 fd，满了就关它再 accept 一个丢掉
ET 模式下数据丢一半 没循环读到 EAGAIN 循环抽干，读到 EAGAIN 才收手
ET 模式下事件循环整个卡死 fd 是阻塞的，最后一次 recv 睡着了 O_NONBLOCK 必须在注册前设好
ET 模式下新连接迟迟不处理 accept 只调了一次 accept 也要循环到 EAGAIN
fd 静默，再也不触发 用了 EPOLLONESHOT 没重新挂 处理完 epoll_ctl 用 MOD 加回去
服务器被信号打断就退出 系统调用返回 EINTR 没重试 while (n < 0 && errno == EINTR) 或 do/while 包一层
非阻塞 connect 判断错 只看了返回值 -1 看 errno == EINPROGRESS，再用可写事件查 SO_ERROR
写数据只发出去一半 非阻塞 write 返回 EAGAIN 剩余数据挂到写缓冲，注册 EPOLLOUT 再发
EAGAIN 被当错误处理 把「暂时没有」当成故障 EAGAIN / EWOULDBLOCK 直接收手，别关 fd
recv 返回 0 被忽略 对端关闭了写端 返回 0 就 close + 从集合摘掉
新连接继承不了非阻塞 accept 出来的 fd 不继承监听 fd 的标志 每个新 fd 单独设一次
缓冲区打出乱码 打印 buffer 没补 \0 buffer[n] = '\0'，长度用 n 而不是 sizeof

三条最常踩的，单独说一句。

第一条，select 的集合每轮都要重置。这不是编码风格问题，是接口本意——它是值-结果参数，进去是你的输入，出来是内核的输出，同一块内存被当两个东西用。写成循环外一次 FD_SET，代码看起来干净，跑起来只有第一轮管用。

第二条，ET 加阻塞 fd 等于死锁。这个组合的错误不在逻辑上，在时序上：epoll_wait 正常返回、recv 正常执行、然后它就永远不返回了。现象是全服无响应，CPU 掉到零。看到「CPU 为零且不响应」，先查这个。

第三条，EAGAIN 不是错误。初学者常写 if (n < 0) { perror(); close(fd); }，结果高并发下连接被随机关掉，日志里全是「Resource temporarily unavailable」。正确做法是把 EAGAIN 和 EWOULDBLOCK 单独拎出来，它是「现在没有，回头再来」的正常信号。

最后一句话收整篇：IO 模型这件事，说到底就一句话——数据从内核缓冲区到你的缓冲区，那一段拷贝躲不掉；在它之前的那段等待，你怎么排布线程、怎么让内核替你盯着，决定了服务器能撑多少连接。
