这一篇只讲一件事：网络调用不能永远等下去。超时怎么设，设在哪一层，设完返回什么，返回之后代码该往哪走。

不讲套接字选项的全表和广播组播的配置，那部分在同组另一篇《套接字选项与广播组播》。也不讲 epoll 事件循环怎么写，I/O 模型在同组《IO 模型：从阻塞到 epoll》。

代码按 Linux + C（POSIX）写，gcc 编译。示例只留能说明问题的部分，头文件在该写全的地方写全。

一、为什么网络调用必须设超时 #

阻塞式套接字上，recv、recvfrom、accept、connect、send 都有不返回的时候。对面不发数据，recv 就一直在等；三次握手没人应，connect 就在等；对端窗口满了，send 也在等。

单连接的原型程序不在乎这个，Ctrl-C 就完事。一上生产就是事故：一个客户端连上来不发数据，服务端那条线程就永久挂在 recv 上，线程池少一个；来上一千个这样的客户端，线程池空，整个服务不再响应任何人。日志不写、心跳不发、信号也不处理。

UDP 上更直接。TCP 有重传和超时机制，链路断了协议栈自己会告诉你连接出问题；UDP 发出去就不管了，数据丢了没人通知。所以「没有数据」和「数据没到」这两件事，在 UDP 上只能由程序自己判。判的办法只有超时。

超时的意义不是「让程序更健壮」这种空话，是让失败早点暴露：

  • 卡住的调用会占住线程、fd、内存，故障从点扩到面。
  • 没有超时就没有失败，没有失败就没有重试，没有重试就没有降级。
  • 上游的健康检查探不到你卡住，负载均衡照样往你这台机器打流量。

一句话：超时是把「不确定的等待」换成「确定的失败」。失败可以处理，等待不能。

二、超时该设在哪一层 #

从下往上数，能挂超时的地方有六处：TCP 连接层、套接字选项、I/O 多路复用、应用协议心跳、业务 deadline，还有一条老路——信号。跨篇的 I/O 模型、套接字选项全集不在这里重复，只看它们各自能管住哪段时间。

层 手段 管到哪 粒度 影响别的线程
业务 请求进来记时间戳，链路里一路传 deadline 一整次请求 任意 否
应用协议 心跳、ping/pong 连接是否还活着 秒级 否
多路复用 select / poll / epoll_wait 的超时参数 等事件的时间 微秒到毫秒 否
套接字选项 SO_RCVTIMEO / SO_SNDTIMEO 单次 recv / send 微秒 否
信号 alarm + SIGALRM 被中断的那个调用 秒 是
TCP TCP_USER_TIMEOUT、TCP_KEEPIDLE 已建立连接的数据确认 毫秒 / 秒 否

三条选型原则：

第一，单次 I/O 用套接字选项，等事件用多路复用的超时参数，整体请求用应用层 deadline。别指望一个 SO_RCVTIMEO 管住整条链路。

第二，别把超时设成同一个值。请求总超时 3 秒，链路里五跳每跳都设 3 秒，最坏情况就是 15 秒，上游早就判你死了。每一跳的超时必须小于上游给你的剩余时间。

第三，alarm 那一层现在不要用。原因在第六章讲透，先记住结论：它是进程级共享的，多线程下一用就错。

三、套接字选项：SO_RCVTIMEO 与 SO_SNDTIMEO #

socket(7) 里定义的两个选项，挂在 SOL_SOCKET 层，值是 struct timeval：

c
#include <sys/socket.h>
#include <sys/time.h>

struct timeval {
    time_t      tv_sec;   /* 秒 */
    suseconds_t tv_usec;  /* 微秒，0 ~ 999999 */
};

struct timeval tv = { .tv_sec = 5, .tv_usec = 0 };

setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof(tv));
setsockopt(fd, SOL_SOCKET, SO_SNDTIMEO, &tv, sizeof(tv));

几个语义要点，一条条说：

  • SO_RCVTIMEO 管读：read、recv、recvfrom、recvmsg，Linux 上还包括 accept。
  • SO_SNDTIMEO 管写：write、send、sendto、sendmsg。它管的是「发送缓冲区腾不出地方」这件事，不是「对方收到没有」。数据进了内核缓冲区，send 就返回了。
  • 值设成 {0, 0} 表示不超时，回到永久阻塞。
  • 超时是每次调用重新计时的。设 5 秒，循环里调一百次 recv，每次都有独立的 5 秒。
  • 超时不影响套接字状态。超时之后这个 fd 仍然可读可写，接着调 recv 就行，不需要重连。
  • 精度写着微秒，实际受内核时钟节拍和调度延迟影响。要毫秒级精确的超时，别指望它。

最要紧的一条是返回值。超时的时候 recv 返回 -1，errno 是 EAGAIN（或 EWOULDBLOCK），和「真出错」长得一模一样，都是 -1。

用 SO_RCVTIMEO 给 accept 加超时，代码长这样：

c
struct timeval t = {5, 0};

if (setsockopt(listenfd, SOL_SOCKET, SO_RCVTIMEO, &t, sizeof(t)) == -1) {
    perror("setsockopt");
    return -1;
}

memset(&peeraddr, 0, sizeof(peeraddr));
len = sizeof(peeraddr);

if ((connfd = accept(listenfd, (struct sockaddr *)&peeraddr, &len)) == -1) {
    printf("errno=%d: %s\n", errno, strerror(errno));
    if (errno == EAGAIN) {
        printf("timeout\n");
        return -1;
    }
}

这里注意两处：

第一，struct timeval t = {5, 0} 这种写法依赖 tv_sec、tv_usec 的声明顺序，POSIX 不保证。老实写 .tv_sec = 5, .tv_usec = 0。

第二，时间到没等到连接，accept 返回 -1，errno == EAGAIN。但 accept 返回 -1 还有别的缘故：连接在握手中被对端复位、fd 用尽（EMFILE / ENFILE）、被信号打断（EINTR）。只判 EAGAIN 就以为「超时」是错的，其余情况一律得按错误处理。

这就是「两种 -1」的问题，必须分开判：

返回值 errno 含义 该怎么办
-1 EAGAIN / EWOULDBLOCK 超时，时间到了没数据 可以继续等，可以重试，也可以收摊
-1 EINTR 被信号打断，不一定超时 看是哪个信号，多数情况重试
-1 ECONNRESET 对端复位了连接 连接已废，关掉重建
-1 ETIMEDOUT 协议栈层面判定超时（常见于带超时的 connect） 连接没建成，别复用
-1 EBADF / ENOTSOCK fd 不对，或根本不是套接字 代码 bug，别重试
-1 EINVAL 参数不合法 代码 bug
0 — 对端有序关闭（TCP） 读到 EOF，收摊
>0 — 真读到字节数 正常

EAGAIN 和 EWOULDBLOCK 在 Linux 上是同一个值，判断写哪个都行，写成 errno == EAGAIN || errno == EWOULDBLOCK 可移植性更好。

还有一个常被忽略的点：SO_RCVTIMEO 的返回是「两次 recv 之间的空档」超时，不是「整个请求」。对端每隔 4 秒发一个字节，你设的 5 秒超时永远不触发，可这条连接已经慢得没法用了。这种场景要靠应用层 deadline 兜住，不是靠套接字选项。

SO_RCVTIMEO 对 accept 的作用在 Linux 上成立（accept 在 socket(7) 的说明里被算作读操作），上面那种写法能跑。别的 Unix 不保证，跨平台就退回 select。

四、select 与 poll 的超时参数 #

套接字选项管单次调用，多路复用管「等事件」。等的过程中最多等多久，由最后一个参数决定：

c
#include <sys/select.h>
#include <poll.h>

int select(int nfds, fd_set *readfds, fd_set *writefds,
           fd_set *exceptfds, struct timeval *timeout);

int poll(struct pollfd *fds, nfds_t nfds, int timeout);
int epoll_wait(int epfd, struct epoll_event *events,
               int maxevents, int timeout);

三个函数表达超时的方式不一样：

函数 超时参数类型与单位 传什么表示永久等 传什么表示立刻返回 返回后参数被修改
select struct timeval *，秒 + 微秒 NULL {0, 0} 会，改写成剩余时间
poll int，毫秒 -1 0 不会
epoll_wait int，毫秒 -1 0 不会

select 的返回值三种：>0 是就绪的 fd 个数，0 是超时，-1 是出错（errno 里看原因）。

一个常见写法：

c
struct timeval t = {3, 0};

while (1) {
    /* ... */

    t.tv_sec  = 3;
    t.tv_usec = 0;

    if ((ret = select(maxfd + 1, &rdfs, NULL, NULL, &t)) == -1) {
        perror("select");
        return -1;
    }

    /* ... 处理就绪的 fd ... */
}

t.tv_sec = 3; t.tv_usec = 0; 这两行放在循环里不是随手写的，有硬原因：Linux 上 select 返回时会把 timeout 改写成「还剩多久」。第一轮等了 1 秒后返回，t 变成 {2, 0}；第二轮直接拿它当上限，就只等 2 秒。循环套几轮，超时越缩越短，最后变成 0 —— 退化成忙轮询，CPU 跑满。

同理，fd_set 也会被内核改。每轮进 select 之前必须重新 FD_ZERO + FD_SET：

c
fd_set rdfs;
int ret;

for (;;) {
    FD_ZERO(&rdfs);
    FD_SET(connfd, &rdfs);

    t.tv_sec  = 3;
    t.tv_usec = 0;

    ret = select(connfd + 1, &rdfs, NULL, NULL, &t);
    if (ret == 0) {
        printf("3 秒没数据，超时\n");
        break;
    }
    if (ret < 0) {
        if (errno == EINTR) {
            continue;              /* 被信号打断不算错，重来 */
        }
        perror("select");
        break;
    }
    if (FD_ISSET(connfd, &rdfs)) {
        n = recv(connfd, buf, sizeof(buf), 0);
        if (n <= 0) {
            break;
        }
    }
}

这段代码里 select 返回 -1 就直接 perror + return -1，把 EINTR 当成了致命错误。信号一来进程就退出，这在带 SIGCHLD、SIGALRM 的程序里会出大问题，EINTR 必须 continue。

poll 的写法不需要重置超时，因为它把超时当输入参数，不会写回去：

c
struct pollfd pfd;
int ret;

pfd.fd     = connfd;
pfd.events = POLLIN;

ret = poll(&pfd, 1, 3000);      /* 最多等 3000 毫秒 */
if (ret == 0) {
    printf("超时\n");
} else if (ret < 0) {
    /* errno == EINTR 就重来，其余是错 */
} else {
    if (pfd.revents & POLLIN) {
        n = recv(connfd, buf, sizeof(buf), 0);
    }
}

epoll_wait 的 timeout 语义和 poll 一样，毫秒，-1 永久，0 立刻返回。区别是它返回的是事件数组，不是 fd 集合。

两张常用的坑：

  • select 的 nfds 是「最大 fd 加一」，不是 fd 个数。传成 fd 个数是常见 bug，小 fd 下看不出问题，一上量就漏事件。
  • select 受 FD_SETSIZE 限制，默认 1024 个 fd。要上千连接别用 select，用 poll 或 epoll。

一条选型建议：连接数少、跨平台，select；连接数中等，poll；Linux 上高并发，epoll + 在业务层算 deadline。别用 epoll_wait 的长超时当请求超时，它的超时是「等事件」，不是「处理请求」。

五、alarm + 信号的老办法 #

在 SO_RCVTIMEO 还没被广泛信任的年代，超时是靠 alarm 做的。这套写法现在老了，可大量存量代码里还有它，读得懂才改得动。

c
#include <unistd.h>

unsigned int alarm(unsigned int seconds);

返回值是「上一个定时器还剩多少秒」，之前没设过定时器就返回 0。

语义一条条列：

  • alarm 又叫闹钟函数，在进程里设一个定时器，时间到了向进程发送 SIGALRM 信号。
  • 一个进程只有一个定时器。 后设的覆盖前设的，不是排队。
  • 子进程继承父进程的报警时钟值，但实际的时钟并不共享。父子各自计时，互不干扰。
  • 执行 exec 之后，报警时钟仍然保持其设置。换了程序映像，定时器还在，这一点容易吓人。
  • seconds 传 0 表示关闭报警时钟。

关闭这件事必须做，而且要写在超时正常结束的路径上。道理很直白：如果 recvfrom 读到数据、没到设定时钟值就返回了，而你忘了关闭报警时钟，它会在不久后照样报警。在计算机看来 1 秒都是很漫长的时间，这声迟到的报警会打断本进程里其他函数的执行。因为一个进程只有一个定时器，用完一定要关。

完整写法：

c
#include <signal.h>
#include <unistd.h>
#include <errno.h>
#include <stdio.h>
#include <string.h>

static volatile sig_atomic_t timed_out;

static void dealSigAlarm(int signo)
{
    (void)signo;
    timed_out = 1;
    return;              /* 只做一件事：打断 recvfrom */
}

void setup_alarm_handler(void)
{
    struct sigaction alrmact;

    bzero(&alrmact, sizeof(alrmact));
    alrmact.sa_handler  = dealSigAlarm;
    alrmact.sa_flags    = 0;      /* 关键：不写 SA_RESTART */
    alrmact.sa_restorer = NULL;
    sigemptyset(&alrmact.sa_mask);

    sigaction(SIGALRM, &alrmact, NULL);
}

int recv_with_alarm(int peerSocket, char *recvbuf, size_t buflen,
                    struct sockaddr *peer_Addr, socklen_t *peer_len)
{
    int n;

    for (;;) {
        timed_out = 0;
        alarm(5);                          /* 每次调用前重新设 */

        n = recvfrom(peerSocket, recvbuf, 1420, 0,
                     peer_Addr, peer_len);

        if (n < 0) {
            if (errno == EINTR && timed_out) {
                printf("recvfrom timeout.\n");
                return -1;
            }
            if (errno == EINTR) {
                continue;                  /* 别的信号，重来 */
            }
            printf("recvfrom error.\n");
            return -1;
        }

        alarm(0);                          /* 很重要：读到就关定时器 */
        return n;
    }
}

另一种写法把 n 设成全局变量、在信号处理函数里置 -1，思路一样：让被中断的调用返回，然后靠 errno 判断。这里的差别在于用 volatile sig_atomic_t 标志区分「这声 EINTR 是不是我自己的闹钟」，n 留给 recvfrom 的返回值，不混用。

sig_atomic_t 的含义：读写它不会被信号处理函数打断到一半，这是信号处理函数与主流程共享变量的最低要求。volatile 防止编译器把它优化进寄存器。两个限定词都不能省。

bzero 是老 BSD 的函数，memset 也行，sigemptyset(&alrmact.sa_mask) 该写。sa_restorer 是 Linux 的历史遗留字段，新代码里不用碰。

signal 与 sigaction 的区别 #

这是整套老办法里最容易踩的地方。

sigaction 能自己设是否重启动被中断的系统调用：

  • alrmact.sa_flags = 0，不带 SA_RESTART：不重启动，中断已经阻塞的函数 recvfrom，程序继续往下执行。超时才能被看见。
  • alrmact.sa_flags = SA_RESTART：重启动函数，效果与 signal 相同，recvfrom 被中断后自动重新阻塞，超时等于没设。

不少老代码会把这件事记在 SA_NOMASK 上：

c
alrmact.sa_flags = SA_NOMASK;   /* 使用 SA_RESTART 将会阻塞在 recvfrom，
                                   与直接使用 signal 效果相同 */

SA_NOMASK 在现代 Linux 里是 SA_NODEFER 的旧别名，管的是「处理函数执行期间不屏蔽这个信号」。真正决定是否重启的是 SA_RESTART 有没有出现。那种注释的结论是对的（没写 SA_RESTART 就不重启），但这个 flag 名字本身不背这个责任——写新代码直接写 0，意图清楚。

signal 的行为：

  • 老的 signal 装的处理函数默认是重启动的。信号的默认语义是先重置回 SIG_DFL 再调用处理函数，重启行为在各 Unix 上一直不统一，POSIX 干脆让 sigaction 接管。
  • 用 signal 装处理器，超时到了 recvfrom 会被重新拉起来继续阻塞。给人的感觉是：明明用了 alarm，程序依然卡在 recvfrom 上不往下走；如果在处理函数里 printf，能看到超时后输出了一条超时信息，然后 signal 又把 recvfrom 启动起来，继续阻塞。

所以要让 recvfrom 在 SIGALRM 到了之后真的跳出来，必须用 sigaction，而且不能带 SA_RESTART。

还有个更细的控制手段：int siginterrupt(int sig, int flag);，flag 传 1 表示「这个信号打断系统调用」，传 0 表示「重启」。它改的是某个信号自身的重启属性，sigaction 的 SA_RESTART 是按处理器设的。两者别混着用，一个信号只挑一种方式配。

用 alarm 给 accept 加超时 #

还有一种版本，拿闹钟兜住 accept：

c
struct sigaction act;

sigaction(SIGALRM, NULL, &act);      /* 先取 SIGALRM 当前的属性 */
act.sa_handler = handler;            /* 只换处理函数，其余沿用 */
sigaction(SIGALRM, &act, NULL);      /* 写回去 */

alarm(3);                            /* 定时器设 3 秒 */

while (1) {
    if ((connfd = accept(listenfd, (struct sockaddr *)&peeraddr, &len)) == -1) {
        if (errno == EINTR) {
            printf("timeout\n");
            return -1;
        }
    }
    /* ... */
}

先 sigaction(SIGALRM, NULL, &act) 取旧值再改，比从零填一个 struct sigaction 稳，sa_mask、sa_flags 这些字段就不用自己猜该填什么。这个技巧值得记。

注意这段代码的 alarm(3) 在循环外，只设了一次。后果是：第一个连接如果在 1 秒内就来了，accept 返回成功，定时器还剩 2 秒，它在循环下一轮 accept 阻塞时到点，把这个 accept 打断，代码打印「timeout」然后 return -1。明明有连接，程序却报超时退出。把 alarm(3) 挪进循环、accept 成功后立刻 alarm(0)，才对。

这里有个容易漏的点：定时器 3 秒内没有数据到来，内核产生 SIGALRM 中断当前操作。设置信号捕捉函数可以用 signal 或 sigaction，但这里只能使用 sigaction，因为 signal 设的处理函数执行完后会重新执行被中断的操作。

六、信号方式的三个问题 #

上一章那套代码能跑，条件是「单线程、只做一件事」。条件一变就崩。它被淘汰不是因为写法丑，是因为三个硬伤。

问题一：信号是进程级的，定时器只有一个 #

这是根本原因，必须讲透。

alarm 属于进程，不属于线程。SIGALRM 的递送目标是进程，内核从进程里挑任意一个没有屏蔽 SIGALRM 的线程去执行处理函数。你不控制它挑谁。

多线程下会变成这样：

text
线程 A：alarm(5)  ->  recv()，本意是等 5 秒
线程 B：alarm(3)  ->  recv()，本意是等 3 秒
                     ^
                     |
        后设的覆盖前设的，进程里只剩 3 秒这一个定时器

3 秒后内核发 SIGALRM
  -> 送到哪个线程？内核挑，不保证是 B
  -> 送给了 A 的 recv，A 返回 -1/EINTR，A 认为「我超时了」
  -> B 还在原地等，永远等不到自己的超时

结果就是超时设置错乱：谁的调用被打断，谁就误判超时；真正的超时方一直挂着。线程越多、越复杂，错乱越随机，复现越难。

多进程里有另一份麻烦。子进程继承父进程的报警时钟值，父进程在 fork 前设了 5 秒，子进程落地时也带着这 5 秒的倒计时，exec 之后还在。父子的时钟不共享，但那个值被继承了，子进程会在毫无预期的时候收到一声 SIGALRM，而它根本没调过 alarm。

所以那条铁律是：alarm + 信号的方式在单线程程序里能用，在多线程、多进程程序里不能用。 现代做法是 SO_RCVTIMEO 或者 select / poll，超时状态挂在 fd 上，天然是每个 fd 独立的。

推论：库代码里绝对不能调 alarm。你调一次，就把调用者进程的定时器改掉了，还顺手给调用者塞了一个 SIGALRM 处理器。

问题二：和 SA_RESTART 打架，超时静默失效 #

信号到了，处理函数也跑了，可被中断的调用被内核自动重启，超时看起来毫无效果。程序照样挂在 recvfrom 上。

要让它生效，必须用 sigaction 且不带 SA_RESTART。用 signal 装的处理器在多数平台上默认重启，白干。

更绕的是：就算你改好了，程序里别的库、别的模块也会给 SIGALRM 装处理器，或者把 sa_flags 改成带 SA_RESTART。信号处理器是进程级全局状态，谁都能改，改完还不通知你。

问题三：粒度只有秒，且状态是全局的 #

alarm 的参数是 unsigned int 秒。要 200 毫秒的超时，做不到。setitimer 能给到微秒，可它同样是进程级、同样发信号，前面两个问题一个不少。

全局状态带来的第二个麻烦是嵌套。A 函数设了 5 秒闹钟，调 B；B 也设了 3 秒闹钟；B 返回后没关，A 的 5 秒已经不存在了，A 剩下来那段代码在一个 3 秒的闹钟底下跑。

历史遗留的坑还有一个：老实现里 sleep 就是 alarm 的一层包装，程序里同时用 sleep 和 alarm 会互相打断、互相吞掉对方的定时器。现代 glibc 的 sleep 用 nanosleep 实现，不抢 SIGALRM 了，但源码里的老习惯还是别留。

三个问题合起来，结论落成一张表：

场景 alarm 能不能用 该用什么
单线程，单连接，原型验证 能，够用 alarm 或干脆 SO_RCVTIMEO
单线程，多连接 勉强，要自己管定时器队列 select / poll
多线程 不能用 SO_RCVTIMEO + select
多进程 不能用 SO_RCVTIMEO + select
库函数内部 绝对不能用 SO_RCVTIMEO
要毫秒级 不能用 poll / epoll_wait

七、EINTR 与重试 #

信号打断一个阻塞的系统调用，调用没做任何工作就返回 -1，errno 是 EINTR。这叫「中断」，不是「失败」。

哪些调用会被重启，取决于两件事：调用本身是否可重启，以及处理器有没有 SA_RESTART。

调用 带 SA_RESTART 时 不带 SA_RESTART 时
read / recv / recvfrom 自动重启，不返回 返回 -1 / EINTR
write / send 自动重启 返回 -1 / EINTR，或返回已写的字节数
accept 自动重启 返回 -1 / EINTR
connect（阻塞式） 不重启 返回 -1 / EINTR，连接状态不确定
select / poll / epoll_wait 不重启 返回 -1 / EINTR
nanosleep 不重启，返回剩余时间 同左

select 和 poll 即使带 SA_RESTART 也会返回 EINTR。它们有超时参数，重启一次等于把超时重新算一遍，内核不做这种事。所以事件循环里收到 EINTR 必须自己 continue。

connect 被中断后连接是否还在推进，标准里没有明确定义，最稳的处理是关掉重来。

重试的写法要点：

  • 只对 EINTR 重试，其他 errno 一律不重试。
  • 重试要带上限。alarm 每 5 秒来一声，无限重试就等于没有超时。
  • 重试前先判断这次中断是不是「我自己要的超时」。用 alarm 时这一点靠标志位，不能只靠 errno。
c
#include <errno.h>
#include <signal.h>

static volatile sig_atomic_t alarm_fired;

static int recv_retry(int fd, void *buf, size_t len)
{
    ssize_t n;
    int saved_errno;

    for (;;) {
        n = recv(fd, buf, len, 0);
        if (n >= 0) {
            return (int)n;
        }

        saved_errno = errno;
        if (saved_errno == EINTR) {
            if (alarm_fired) {
                errno = saved_errno;
                return -1;              /* 这才是超时 */
            }
            continue;                   /* 别的信号，重来 */
        }

        errno = saved_errno;
        return -1;
    }
}

一个细节：信号处理函数里如果调了 printf，printf 会改 errno，主流程回来就判错了。处理函数里只写 sig_atomic_t 是最省事的做法；非要调函数，进出各存一次 errno：

c
static void handler(int signo)
{
    int saved_errno = errno;
    /* ... */
    errno = saved_errno;
}

八、connect 的超时控制 #

TCP 的 connect 在三次握手期间会停在 SYN_SENT。对端不回 SYN+ACK，内核就重传 SYN，重传多少轮、总共等多久，视系统配置而定，量级在几十秒到两分钟以上。这个默认值对线上服务太长了：一个不可达的地址能把你的线程按住一分多钟。

SO_SNDTIMEO 在这里帮不上忙。POSIX 没有规定 connect 受 SO_SNDTIMEO 约束，各系统行为不一致，Linux 上也不能依赖它当连接超时。谁在代码里靠 SO_SNDTIMEO 掐 connect，谁就是在赌。

可用的手段有三个：

手段 平台 管到哪 靠不靠得住
非阻塞 connect + select/poll 等可写 全平台 单次连接建立 靠得住，标准做法
TCP_USER_TIMEOUT Linux 专有 已建立连接上的数据确认 治不了握手阶段
SO_SNDTIMEO — 阻塞 connect 不能依赖

非阻塞 connect 的完整套路 #

c
#include <fcntl.h>
#include <sys/select.h>
#include <sys/socket.h>
#include <errno.h>

int connect_timeout(int fd, const struct sockaddr *addr, socklen_t addrlen,
                    int timeout_ms)
{
    int flags, ret, err = 0;
    socklen_t errlen = sizeof(err);
    fd_set wfds;
    struct timeval tv;

    flags = fcntl(fd, F_GETFL, 0);
    if (flags < 0) {
        return -1;
    }
    if (fcntl(fd, F_SETFL, flags | O_NONBLOCK) < 0) {
        return -1;
    }

    ret = connect(fd, addr, addrlen);
    if (ret == 0) {
        /* 本机地址或立刻成功，不用等 */
        fcntl(fd, F_SETFL, flags);
        return 0;
    }
    if (errno != EINPROGRESS) {
        fcntl(fd, F_SETFL, flags);
        return -1;                 /* 立刻失败，比如 ECONNREFUSED */
    }

    FD_ZERO(&wfds);
    FD_SET(fd, &wfds);
    tv.tv_sec  = timeout_ms / 1000;
    tv.tv_usec = (timeout_ms % 1000) * 1000;

    ret = select(fd + 1, NULL, &wfds, NULL, &tv);

    if (ret == 0) {
        errno = ETIMEDOUT;
        close(fd);
        return -1;                 /* 超时 */
    }
    if (ret < 0) {
        fcntl(fd, F_SETFL, flags);
        return -1;                 /* EINTR 或其他错误 */
    }

    /* 可写了不代表连上了，必须取 SO_ERROR */
    if (getsockopt(fd, SOL_SOCKET, SO_ERROR, &err, &errlen) < 0) {
        fcntl(fd, F_SETFL, flags);
        return -1;
    }
    if (err != 0) {
        errno = err;
        close(fd);
        return -1;                 /* ECONNREFUSED / EHOSTUNREACH / ETIMEDOUT */
    }

    fcntl(fd, F_SETFL, flags);     /* 恢复原来的阻塞属性 */
    return 0;
}

几个必须知道的点：

  • connect 在非阻塞 fd 上返回 -1 / EINPROGRESS，是「正在连」，不是错误。
  • select 报可写之后 getsockopt 拿 SO_ERROR。**可写不等于是连上了。**连接失败时 fd 同样可写，错误藏在 SO_ERROR 里。不查 SO_ERROR 就发数据，会在下一次 send 上收到 EPIPE，还附赠一个 SIGPIPE（默认动作是杀进程）。
  • getsockopt 本身返回 0 只说明「取到了」，不代表连接成功。判成功要看 err == 0。
  • 超时之后直接 close。不要对同一个 fd 再 connect 一次，状态是脏的。
  • 上面保留了 fcntl 恢复阻塞属性这一步。高并发服务里常不恢复，直接把 fd 丢进 epoll，全程非阻塞，那样就不用每次都改 flag。

TCP_USER_TIMEOUT #

Linux 2.6.37 之后有的选项，IPPROTO_TCP 层，值是毫秒：

c
#include <netinet/tcp.h>

unsigned int ms = 30000;

setsockopt(fd, IPPROTO_TCP, TCP_USER_TIMEOUT, &ms, sizeof(ms));

它的语义是：发出去了但一直没被确认的数据，最多能留多久，超过就掐掉连接。适用于 ESTABLISHED、FIN_WAIT_1、FIN_WAIT_2、CLOSE_WAIT、CLOSING、LAST_ACK 这些同步状态。

关键限制：它不管 SYN_SENT。 握手阶段连接还没建立，这个选项不生效。所以 TCP_USER_TIMEOUT 替代不了非阻塞 connect + select，它解决的是另一个问题——连接建起来了，对端突然静默，内核还在那儿重传，你以为连接活着。这个场景留到第九章。

九、长连接的保活检测 #

前面几章处理的都是「调用卡住」。还有一种情况更阴：连接早断了，本地 fd 还稳稳地躺在 ESTABLISHED 里，recv 一点返回的意思都没有。

断的原因跟两头都没关系：中间那台 NAT 把表项回收了，防火墙静默丢包，对端机器断电，网线被人踢了。这些都不产生 RST，协议栈毫不知情。你的线程就挂在那儿，一直到进程重启。

保活要解决的就是这件事：怎么知道对面还在。

TCP 层的 keepalive #

c
#include <netinet/tcp.h>

int on = 1;
setsockopt(fd, SOL_SOCKET, SO_KEEPALIVE, &on, sizeof(on));

int idle = 30;    /* 连接空闲多久开始探测，秒 */
int intvl = 5;    /* 探测间隔，秒 */
int cnt = 3;      /* 探测几次没回应判死 */

setsockopt(fd, IPPROTO_TCP, TCP_KEEPIDLE,  &idle,  sizeof(idle));
setsockopt(fd, IPPROTO_TCP, TCP_KEEPINTVL, &intvl, sizeof(intvl));
setsockopt(fd, IPPROTO_TCP, TCP_KEEPCNT,   &cnt,   sizeof(cnt));
选项 层 单位 作用
SO_KEEPALIVE SOL_SOCKET int 开关 打开 TCP 保活探测
TCP_KEEPIDLE IPPROTO_TCP 秒 空闲多久发出第一个探测
TCP_KEEPINTVL IPPROTO_TCP 秒 探测之间的间隔
TCP_KEEPCNT IPPROTO_TCP 次 连续失败几次判定连接已死
TCP_USER_TIMEOUT IPPROTO_TCP 毫秒 未确认数据最多留多久

SO_KEEPALIVE 默认是关的。开了之后，系统默认的空闲阈值很长，按小时计，具体值视系统配置而定，看 /proc/sys/net/ipv4/tcp_keepalive_time。这个量级对线上服务没有意义，必须用 TCP_KEEPIDLE 自己调。

keepalive 有两个先天局限：

  • 它只在连接空闲时探测。有数据持续在发，它一次都不探。对端「收得下但不处理」这种状态它看不出来。
  • 探测失败要等满 KEEPIDLE + KEEPINTVL × KEEPCNT 才判死。这三项一放大，判死时间就很长。

TCP_USER_TIMEOUT 补的是另一个洞：连接上有数据发出去、迟迟没被确认。设成 30 秒，那么任何一段发出去 30 秒还没 ACK 的数据，都会让内核把连接掐掉，recv / send 立刻返回错误。它比 keepalive 敏感，因为触发条件是「有数据没确认」，不要求空闲。

应用层心跳 #

TCP keepalive 有个绕不开的问题：它探的是「TCP 连接通不通」，不是「对面那个进程还活着没」。对端进程死锁了、卡在 GC 了、业务线程池满了，TCP 层照样 ACK 你的探测包，keepalive 一次都不报错。

所以长连接服务要有自己的心跳：客户端发 ping，服务端回 pong，超过 N 个周期没收到 pong 就判定连接已死。

心跳包要带序号和时间戳，回来时算 RTT。这样一次心跳同时给三样东西：连接活性、往返时延、丢包线索。

心跳周期怎么定，取决于链路上最不耐心的那个中间设备。NAT 表项的空闲回收时间往往比你想的短，心跳周期要比它小一截。具体值看设备配置，别照抄。

手段 探测谁 触发条件 判死依据 穿透 NAT
SO_KEEPALIVE 链路 连接空闲 探测次数用完 有包就行
TCP_USER_TIMEOUT 链路 数据未确认 超时未 ACK 有包就行
应用心跳 对端进程 应用自己定 心跳超时 有包就行

三层一起上不冲突。常规做法是 TCP_USER_TIMEOUT 兜底（管住内核重传），应用心跳做主判据（管住对端进程），SO_KEEPALIVE 可以不刻意调，留着当最后一层。

十、超时值的确定 #

这事没有标准答案，但有推导方法。

第一步，量。拿真实链路的 RTT 分布，看 P99，不要看平均值。平均值 2 毫秒、P99 800 毫秒的链路，按平均值设超时会打掉一大批正常请求。

第二步，算预算。一次请求在路上要经过若干跳，每一跳都分到一段时间，加起来必须小于上游给你的总时限：

text
上游（网关）给这个请求 3000 ms
  |
  +-- 本服务总预算         2500 ms   （留 500 ms 给网络和序列化）
        |
        +-- 建连            300 ms
        +-- 等后端响应      1500 ms
        +-- 重试一次        700 ms   （预算已经在缩，不能按原值再来一遍）

这张图的意思：超时是减法，不是并列。 每一层拿到的都是「还剩多少」，不是「我该等多久」。

第三步，定层次关系。一个不出错的次序：

text
连接超时  <  单次 I/O 超时  <  请求总超时  <  上游对我的超时

反过来的写法一定出事：单次 I/O 超时 5 秒，请求总超时 3 秒，那 5 秒永远用不上，因为业务层早就放弃了，而线程还卡在那 5 秒里。

第四步，加抖动。同一批客户端、同一批下游，超时值完全相同的话，下游一抖，它们会在同一毫秒集体放弃、又会在同一毫秒集体重试，下游被自己人打第二遍。给超时乘一个 [0.8, 1.2) 的随机系数，把这批请求摊开。

要设的超时 定值依据 常见反例
连接建立 目标机房跨地域还是同机房，量出来 直接抄内核默认，一卡一分多钟
单次读写 链路 RTT 的 P99 乘以几倍 设 5 秒，业务总超时才 3 秒
空闲心跳 链路上 NAT 表项回收时间的一半以下 设 30 分钟，中间设备 5 分钟就回收了
请求总时限 上游 SLA 减去留给自己的余量 每一跳都设成一样，累加成 N 倍
重试总预算 总时限减去首次尝试耗时 每次重试都用原始超时值

一个纪律：这些数字必须写在配置里，别硬编码在代码里。不同机房、不同下游，合适的值不一样，改配置比改代码快。

十一、超时与重试的配合 #

超时之后干什么，是另一半问题。超时本身不产生价值，把超时接上重试、降级、熔断才有。

先问三个问题：

  • 这个操作幂等吗？GET、查询、按主键读，可以重试。扣款、下单、发消息，不能随便重试，除非对端有去重。
  • 现在还有时间重试吗？总预算还剩 200 毫秒，而一次正常往返要 300 毫秒，重试就是纯浪费，还多压一次下游。
  • 重试会不会放大故障？下游已经过载，所有客户端一起重试，等于给它加了两三倍流量。

把 deadline 传下去，比传「超时值」靠谱：

c
#include <time.h>

struct deadline {
    struct timespec expire;
};

static long ms_left(const struct deadline *d)
{
    struct timespec now;
    long ms;

    clock_gettime(CLOCK_MONOTONIC, &now);
    ms = (d->expire.tv_sec - now.tv_sec) * 1000L
       + (d->expire.tv_nsec - now.tv_nsec) / 1000000L;

    return ms > 0 ? ms : 0;
}

用 CLOCK_MONOTONIC，不要用 CLOCK_REALTIME。墙上时间会被 NTP 调，调一次你的超时就算歪了。

每次调用前算剩余，拿剩余去设本次的 SO_RCVTIMEO 或 select 超时：

c
long left = ms_left(&d);
if (left <= 0) {
    return -1;                     /* 预算用完，直接失败，别再发请求 */
}

tv.tv_sec  = left / 1000;
tv.tv_usec = (left % 1000) * 1000;
setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof(tv));

重试的几条纪律：

  • 指数退避加抖动。第二次等 100 毫秒，第三次 200 毫秒，每次乘一个随机系数。不要固定间隔重试，那是同步攻击。
  • 重试次数有上限，总时长也有上限。两个都要，只限次数不限时长会在慢链路上拖死。
  • 只在一层重试。网关重试 3 次、服务重试 3 次、客户端重试 3 次，下游看到的是 27 次。这就是重试风暴。
  • 超时后不要拿同一个连接立刻重发。TCP 上超时的连接状态不确定：请求说不定已经到了对端，只是响应慢；重发就变成重复请求。要么关掉重建，要么业务层带去重 ID。
  • 连续失败到阈值就熔断，让请求快速失败，给下游恢复的时间。熔断期间的重试是纯浪费预算。

还有一条容易忘：send 超时和 recv 超时的后果不一样。recv 超时，数据没来，连接完好，重试读就行。send 超时，你不知道内核到底发出去了多少字节，这条连接上的数据流说不定已经错位，最稳的处理是关掉重建。

十二、易错点速查 #

现象 原因 改法
多线程下超时随机错乱，谁被打断谁报超时 用 alarm 做超时，定时器进程级唯一，SIGALRM 送给任意线程 换 SO_RCVTIMEO 或 select
用了 alarm，程序还是卡在 recvfrom 上 处理器带了 SA_RESTART，或用 signal 装的处理器默认重启 用 sigaction，sa_flags 写 0
循环里 select 的超时越跑越短，最后忙轮询 select 返回时改写了 timeval 每轮重置 tv_sec / tv_usec
select 第二轮开始漏事件 fd_set 每轮没重新 FD_ZERO / FD_SET 进 select 前重建集合
select 的 nfds 传成 fd 个数 少了一个，最后一个 fd 的事件看不到 传 maxfd + 1
把 EAGAIN 当成唯一失败原因 只有超时才返回 EAGAIN，EINTR / ECONNRESET / EMFILE 也是 -1 按 errno 分支处理，别一网打尽
fd 用尽时 accept 死循环 EMFILE / ENFILE 被当成「再来一次」，accept 立刻又失败 识别这两个 errno，停一下再接受
accept 超时后连接丢了 用了 SO_RCVTIMEO 但没处理「已完成的连接还在队列里」 超时后继续收，不要 close 监听 fd
SO_SNDTIMEO 设了，connect 还是卡一分多钟 connect 不受 SO_SNDTIMEO 可靠约束 非阻塞 + select 等可写
非阻塞 connect 可写了就以为成功 忘了 getsockopt(SO_ERROR) 可写后必须查 SO_ERROR
SO_ERROR 取完不判，send 收到 SIGPIPE 进程被杀 连接失败时 fd 也可写，错误藏在 SO_ERROR 判 err == 0，并在全局 SIG_IGN 掉 SIGPIPE
超时后同一个 fd 又 connect 一次 connect 超时后 fd 状态不确定，不能复用 close 后重建
心跳设了 30 分钟，连接早断了却不知道 中间设备空闲回收远快于心跳周期 心跳周期压到回收时间一半以下
keepalive 开了，对端进程死锁照样不断 keepalive 只探链路，探不到进程 加应用层心跳
TCP_USER_TIMEOUT 治不了连不上 它只管已建立连接的未确认数据，不管 SYN_SENT 握手阶段用非阻塞 connect
超时后 NTP 一跳，超时立刻触发 用 CLOCK_REALTIME 算剩余时间 换 CLOCK_MONOTONIC
信号处理函数把 errno 改了，主流程判错 处理函数里调了 printf 之类 进出存一次 errno，或用 sig_atomic_t 标志
重试 3 次，下游收到 27 次请求 每一层各重试 3 次 只在一层重试
重试把过载的下游打死 固定间隔、所有客户端同步重试 指数退避加抖动，加熔断
超时返回 -1 后按真错误关闭连接 没区分「超时」和「真错」 按 errno 分流，超时不关 fd

最后一条放在最前面也成立：先分清 -1 是超时还是错误，再谈重试。 这两种情况走错方向，后面的代码写得再漂亮也没用。
