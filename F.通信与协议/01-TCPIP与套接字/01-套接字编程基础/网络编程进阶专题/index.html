这一篇接在套接字基础之后，只讲三类事：描述符在进程之间怎么流动，信号与超时怎么打断阻塞调用，以及那些「代码能跑、上线出事」的细节。

不讲 TCP 三次握手与状态机，不讲报文逐字节的格式，也不做抓包命令速查。协议分析与报文格式在同组另一篇，抓包与排错命令在第三篇。

代码按 Linux + C（POSIX）写，用 gcc 编译。示例只留能说明问题的部分，错误处理该有还是有。

一、从基础到进阶 #

基础篇的流程是 socket → bind → listen → accept → 读写 → close。跑通一遍不难。难的是把几百个连接挂上去之后，程序不 hung、不漏 fd、不因为一个信号就退。

进阶这一层要盯三块：

  • 进程与描述符。fork 之后父子怎么共享套接字，exec 之后描述符还在不在，一个进程怎么把 fd 交给另一个进程，fd 用完了怎么办。
  • 信号与超时。信号打断阻塞的系统调用，超时到了怎么返回，返回之后该重试还是该收摊。
  • 数据与健壮性。缓冲区怎么用，广播组播怎么配，出错路径怎么收干净。

这三块互相咬着。举个连环：accept 被 SIGCHLD 打断返回 EINTR，代码当成错误 exit，进程退了；退之前 fd 没关干净，端口还被 TIME_WAIT 占着；重启报 Address already in use。三个问题，一条链。

先说基础篇容易漏掉的差异。TCP 有重传和超时机制，链路断了协议栈自己会告诉你；UDP 什么都没有，发出去就不管了。所以「没有数据」和「数据没到」这两件事，在 UDP 上只能由程序自己判。判的办法就是超时。

超时检测绕不开 setsockopt：

c
#include <sys/socket.h>

int setsockopt(int sockfd, int level, int optname,
               const void *optval, socklen_t optlen);

参数四个：

参数 含义
sockfd 套接字描述符
level 选项所属协议层，通用选项用 SOL_SOCKET，IP 层用 IPPROTO_IP，TCP 层用 IPPROTO_TCP
optname 选项名
optval / optlen 选项值的缓冲区与长度

成功返回 0，失败返回 -1 并置 errno。

SOL_SOCKET 这一层的常用选项，这张表值得记住：

选项 说明 数据类型
SO_BROADCAST 允许发送广播数据 int
SO_DEBUG 允许调试 int
SO_DONTROUTE 不查找路由 int
SO_ERROR 获得套接字错误 int
SO_KEEPALIVE 保持连接 int
SO_LINGER 延迟关闭连接 struct linger
SO_OOBINLINE 带外数据放入正常数据流 int
SO_RCVBUF 接收缓冲区大小 int
SO_SNDBUF 发送缓冲区大小 int
SO_RCVTIMEO 接收超时 struct timeval
SO_SNDTIMEO 发送超时 struct timeval
SO_REUSEADDR 允许重用本地地址和端口 int
SO_TYPE 获得套接字类型 int

后面几章反复出现的只有四个：SO_RCVTIMEO / SO_SNDTIMEO（第九章）、SO_BROADCAST（第十一章）、SO_REUSEADDR（第十二章）。SO_TYPE 拿来自检有用，判断一个 fd 到底是 TCP 还是 UDP 不用靠猜。

选项按 level 分层，别混。广播走 SOL_SOCKET + SO_BROADCAST，组播走 IPPROTO_IP + IP_ADD_MEMBERSHIP。层写错了 setsockopt 直接返回 ENOPROTOOPT，看一眼 errno 就能定位。

二、fork 与套接字的共享 #

先摆结论：fork 之后，父子进程各有一张描述符表，但表里那个 fd 指向的是内核里同一个套接字对象。父子共享的是套接字，不是描述符。

text
        父进程                      子进程
   +--------------+           +--------------+
   |  fd 表        |           |  fd 表        |
   |   3 ---------+|           |   3 ---------+|
   +--------------+           +--------------+
                 |                          |
                 +------------+-------------+
                              v
                   +---------------------+
                   | 内核 file 对象       |  引用计数 +1
                   | 状态标志 / 偏移量     |
                   +----------+----------+
                              v
                   +---------------------+
                   | socket / sock 对象   |  真正的连接
                   | 收发缓冲区 / TCP 状态 |
                   +---------------------+

一条连接，内核里只有一份接收队列、一份发送队列、一个状态机。两个进程读的是同一个队列。

由此能推出几件事。

close 不等于断连接。 描述符只是引用，close 一次引用计数减一。要等所有引用都关了，内核才真正销毁套接字、才发 FIN。这就是「父进程 close 了 fd，子进程照样能读写」的原因：子进程手里还攥着一个引用。

反过来也成立：泄漏一个 fd，等于这条连接永远不断。对端一直看到连接活着，你这边进程退了才算完。

shutdown 断的是连接本身。 shutdown 作用于套接字对象，不作用于描述符。一个进程 shutdown(fd, SHUT_RDWR)，另一个进程下一次 read 立刻拿到 0（EOF）。

动作 作用对象 对其他进程的影响 之后本进程的 fd 还能用吗
close(fd) 本进程的描述符引用 对方手里的 fd 完全不受影响 不能，已释放
shutdown(fd, SHUT_WR) 套接字的写方向 对端立刻收到 FIN 能，还能读
shutdown(fd, SHUT_RDWR) 套接字的两个方向 对端收到 FIN，本端读到 EOF 能，但没有意义

父子会抢数据。 两个进程阻塞在同一个连接的 recv 上，数据来了只唤醒一个，唤醒谁看调度。想让一个连接只由一个进程处理，就得在架构上把角色分开，不能让两个进程同时读。

同样的道理作用在 listen fd 上就是多进程 accept：N 个子进程都阻塞在同一个 listen fd 的 accept 上，内核保证只有一个能拿到新连接。这是 prefork 服务器成立的基础。老内核上有过惊群，所有进程都被唤醒再抢，抢不到的重睡，白白烧 CPU；后来的内核用互斥等待队列解决了。

prefork 骨架：

c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/socket.h>
#include <sys/wait.h>
#include <netinet/in.h>

#define WORKERS 4

int main(void)
{
    int listenfd, connfd;
    struct sockaddr_in addr;
    int on = 1;
    pid_t pid;

    listenfd = socket(AF_INET, SOCK_STREAM | SOCK_CLOEXEC, 0);
    if (listenfd < 0) { perror("socket"); exit(1); }

    setsockopt(listenfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof(on));

    memset(&addr, 0, sizeof(addr));
    addr.sin_family = AF_INET;
    addr.sin_port = htons(8888);
    addr.sin_addr.s_addr = htonl(INADDR_ANY);

    if (bind(listenfd, (struct sockaddr *)&addr, sizeof(addr)) < 0) {
        perror("bind"); exit(1);
    }
    if (listen(listenfd, SOMAXCONN) < 0) {
        perror("listen"); exit(1);
    }
    for (int i = 0; i < WORKERS; i++) {
        pid = fork();
        if (pid < 0) { perror("fork"); exit(1); }
        if (pid == 0) {
            /* 子进程：继承来的描述符该关就关，只留 listenfd */
            for (;;) {
                connfd = accept(listenfd, NULL, NULL);
                if (connfd < 0) {
                    if (errno == EINTR)
                        continue;
                    perror("accept");
                    break;
                }
                /* 处理连接 …… */
                close(connfd);
            }
            _exit(0);
        }
    }
    close(listenfd);            /* 父进程不再需要，子进程各自还有一份 */
    while (wait(NULL) > 0)      /* 回收子进程 */
        ;
    return 0;
}

几个细节值得拎出来：

  • 父进程 close(listenfd) 之后，端口并没有释放。子进程各有一份引用，监听继续。要停服务，得把所有子进程都收掉。
  • 子进程用 _exit 而不是 exit，避免把父进程 stdio 缓冲区里没 flush 的内容再刷一遍。
  • 子进程 fork 之后要清理继承来的描述符。否则父进程打开的那些日志、管道、别的连接，会一直挂在子进程身上。
  • 别让两个 worker 都去读同一个连接。要协作，先按第十一章的办法把角色拆开。

fork 与文件偏移还有一层：普通文件的偏移量存在 file 对象里，fork 之后父子共享同一个偏移。两边同时写日志会互相覆盖。管道和套接字没有偏移概念，这条不适用；但写入原子性依旧有限，管道一次写入不超过 PIPE_BUF（Linux 上是 4096 字节）才有原子保证，套接字上多进程写一块大数据会交错。

三、描述符的继承与 FD_CLOEXEC #

fork 复制整张描述符表，exec 只保留没打 FD_CLOEXEC 标记的那些。

默认不打这个标记，这是历史包袱。结果是：execve 出去的任意程序，都会继承父进程所有打开的 fd。popen 起个 shell、system 调个命令，监听套接字就跟着过去了。子程序攥着 fd 不放，父进程管不了；父进程退了子程序还活着，端口就一直被占着，重启报 EADDRINUSE，你 ps 一遍还找不到是谁占的。

场景 子进程是否保留 fd 说明
fork 全部保留 复制描述符表，指向同一个 file 对象
fork 后 exec 保留未打 FD_CLOEXEC 的 端口被莫名占用的头号来源
fork 后 exec，fd 打了 FD_CLOEXEC 关闭 exec 时由内核关掉
标准输入输出 0 / 1 / 2 保留 除非显式重定向
FD_CLOEXEC 标记本身 子进程继承 fork 复制的是描述符标志
O_NONBLOCK 等状态标志 共享 存在 file 对象里，一个进程改了另一个立刻受影响

最后两行是重点。FD_CLOEXEC 是描述符标志，用 fcntl(fd, F_GETFD / F_SETFD) 读写，fork 会继承这个标记，exec 时按它决定关不关。O_NONBLOCK 是文件状态标志，用 fcntl(fd, F_GETFL / F_SETFL) 读写，存在 file 对象里，fork 之后父子共享同一份。子进程非要设非阻塞，父进程的 fd 也跟着变成非阻塞，这类问题查起来很费劲。

加标记的三种写法，从省事到麻烦：

c
#include <fcntl.h>
#include <sys/socket.h>
#include <unistd.h>

/* 1. 创建时就带标记，首选 */
int fd  = socket(AF_INET, SOCK_STREAM | SOCK_CLOEXEC, 0);
int cfd = accept4(listenfd, NULL, NULL, SOCK_CLOEXEC);   /* Linux 2.6.28+ */

/* 2. 事后补，fcntl 两步 */
int flags = fcntl(fd, F_GETFD);
fcntl(fd, F_SETFD, flags | FD_CLOEXEC);

/* 3. 文件与管道的新接口 */
int lfd = open("access.log", O_WRONLY | O_APPEND | O_CLOEXEC);
int pfd[2];
pipe2(pfd, O_CLOEXEC);

第二种写法有窗口期：取标志和设标志之间如果有别的线程 fork，那一刻的子进程还没拿到标记。所以能用 SOCK_CLOEXEC / accept4 / open(O_CLOEXEC) 就别用 fcntl 补。

dup 出来的新 fd 不带 FD_CLOEXEC，dup2 同样，得重新设。这条在复制标准输入输出时经常被忘掉。

什么时候留、什么时候关，判断标准很简单：

  • 只给本进程用的（日志、配置、内部管道、epoll 实例）：一律 CLOEXEC。
  • 要交给子程序直接用的（把某个 fd 重定向成子进程的 stdout）：不打标记，并且显式安排。
  • 第三方库开的 fd 你控制不了：exec 之前自己遍历 /proc/self/fd 逐个关掉，这是最笨也最稳的一招。glibc 2.34 起 posix_spawn 有 addclosefrom_np 可以省掉手写循环。

四、进程间传递文件描述符 #

场景很具体：主进程 accept 到连接，想交给某个 worker；或者 worker 想把日志 fd 交给统一的收集进程。数字不能直接传——fd 3 在你这儿是套接字，在别人那儿是别的文件。传的必须是「那个内核对象」，让接收方在自己的描述符表里建一条新引用。

Linux 的做法是 Unix 域套接字（AF_UNIX）的辅助数据，SCM_RIGHTS。传的是引用：内核在接收方的描述符表里新建一个 fd，指向同一个 file 对象。

约束先列清楚：

  • 必须走 AF_UNIX。socketpair(AF_UNIX, SOCK_STREAM, 0, sv) 最省事，TCP 不行。
  • 辅助数据用 CMSG_* 宏算长度和对齐。手算 sizeof 在 ARM64 这类平台上会错位。
  • 一次发送至少要带 1 字节普通数据。带 0 字节的写法在部分实现上收不到。
  • 接收方拿到的 fd 是它自己表里最小的空位，编号和发送方没有任何关系。
  • 发送方 sendmsg 成功后可以立刻 close 自己的 fd，连接不受影响，接收方那边还握着引用。
c
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/socket.h>

/* 把 fd 通过 unix 域套接字 sock 发给对端 */
int send_fd(int sock, int fd)
{
    struct msghdr msg;
    struct iovec iov;
    char buf[1] = { 'x' };
    char ctrl[CMSG_SPACE(sizeof(int))];
    struct cmsghdr *cmsg;
    memset(&msg, 0, sizeof(msg));
    memset(ctrl, 0, sizeof(ctrl));

    iov.iov_base = buf;
    iov.iov_len = 1;
    msg.msg_iov = &iov;
    msg.msg_iovlen = 1;
    msg.msg_control = ctrl;
    msg.msg_controllen = sizeof(ctrl);

    cmsg = CMSG_FIRSTHDR(&msg);
    cmsg->cmsg_level = SOL_SOCKET;
    cmsg->cmsg_type = SCM_RIGHTS;
    cmsg->cmsg_len = CMSG_LEN(sizeof(int));
    memcpy(CMSG_DATA(cmsg), &fd, sizeof(int));

    if (sendmsg(sock, &msg, 0) < 0) {
        perror("sendmsg");
        return -1;
    }
    return 0;
}

/* 接收方：返回值就是新描述符 */
int recv_fd(int sock)
{
    struct msghdr msg;
    struct iovec iov;
    char buf[1];
    char ctrl[CMSG_SPACE(sizeof(int))];
    struct cmsghdr *cmsg;
    int fd = -1;

    memset(&msg, 0, sizeof(msg));
    memset(ctrl, 0, sizeof(ctrl));
    iov.iov_base = buf;
    iov.iov_len = 1;
    msg.msg_iov = &iov;
    msg.msg_iovlen = 1;
    msg.msg_control = ctrl;
    msg.msg_controllen = sizeof(ctrl);

    if (recvmsg(sock, &msg, 0) < 0) {
        perror("recvmsg");
        return -1;
    }
    if (msg.msg_flags & MSG_CTRUNC) {
        fprintf(stderr, "control data truncated\n");
        return -1;
    }

    cmsg = CMSG_FIRSTHDR(&msg);
    if (cmsg != NULL && cmsg->cmsg_level == SOL_SOCKET &&
        cmsg->cmsg_type == SCM_RIGHTS) {
        memcpy(&fd, CMSG_DATA(cmsg), sizeof(int));
    }
    return fd;
}

两个函数各自的坑：

  • 接收端一定要查 MSG_CTRUNC。控制缓冲区不够时内核会截断，被截掉的 fd 就丢了，而 recvmsg 照样返回成功。不查这个标志，你拿到一个 -1 却不知道哪一步出的问题。
  • 收到的 fd 不带 FD_CLOEXEC，接收方要自己补。
  • 一次可以传多个 fd：数组塞进 CMSG_DATA，cmsg_len 用 CMSG_LEN(sizeof(int) * n)。读的时候按 (cmsg_len - CMSG_LEN(0)) / sizeof(int) 算个数，别写死 1。

方案对比：

方案 适用场景 代价
fork 继承 父子长期协作，fd 从 fork 那刻起就固定 只发生在 fork 瞬间，之后无法新增
SCM_RIGHTS 运行时按需把某个连接交给别的进程 要维护一条 AF_UNIX 通道，代码稍长
SO_REUSEPORT 多进程各自监听同一端口，内核分流 不传 fd，连接从一开始就分开
/proc/[pid]/fd 打开 临时调试 需要权限，语义绕，别用在生产链路

SO_REUSEPORT 值得展开一句：每个进程自己 socket + setsockopt(SO_REUSEPORT) + bind 同一端口，内核按四元组哈希把新连接分下去。没有共享 fd，也就没有惊群和传 fd 这些事。代价是连接亲和性由内核定，做不了按业务分配。

五、文件描述符的数量限制 #

一个进程能开多少 fd，由 RLIMIT_NOFILE 管。它有 soft 和 hard 两个值：soft 是当前生效的上限，进程自己可以调，但不能超过 hard；hard 只有 root（准确说是带 CAP_SYS_RESOURCE）才能往上抬。

bash
ulimit -n                                  # soft limit
ulimit -Hn                                 # hard limit
grep 'open files' /proc/self/limits        # 进程自己看到的

默认值视系统配置而定。不同发行版、systemd 单元里的 LimitNOFILE、容器运行时给的默认值，三处各有各的数，别拿一台机器上的数字当基准。

撞上限的表现很直白：

text
accept: Too many open files

errno 是 EMFILE（本进程 fd 用光）或 ENFILE（系统级文件表满）。socket、accept、open、pipe 都报这个。

服务器为什么会撞：每个连接一个 fd，再加监听 fd、日志文件、配置文件、定时器管道、epoll 实例。几千个长连接足以撞穿一个偏小的 soft limit。

调法按顺序试：

c
#include <sys/resource.h>

int raise_nofile(rlim_t want)
{
    struct rlimit rl;

    if (getrlimit(RLIMIT_NOFILE, &rl) < 0)
        return -1;
    if (want <= rl.rlim_cur)
        return 0;
    if (rl.rlim_max != RLIM_INFINITY && want > rl.rlim_max)
        want = rl.rlim_max;

    rl.rlim_cur = want;
    return setrlimit(RLIMIT_NOFILE, &rl);
}

临时改也行：ulimit -n 65535 管当前 shell 及其子进程，prlimit --nofile=65535:65535 ./server 只管本次启动。

再有一种是改 systemd unit 的 LimitNOFILE，然后 daemon-reload 加重启。容器里还要看运行时给的上限，光改程序没用。hard 抬不动、或者单进程就是顶不住的时候，改架构：拆成多进程，每个进程一份描述符表，或者换 epoll 让一个 fd 管住几千个连接。

EMFILE 之后最怕死循环：accept 返回 EMFILE，程序 continue，下一次还是 EMFILE，CPU 打满而连接一个也进不来。经典处理是预留一个空闲 fd：

c
int idle_fd = open("/dev/null", O_RDONLY);   /* 启动时留一手 */

/* accept 报 EMFILE 时 */
if (connfd < 0 && errno == EMFILE) {
    close(idle_fd);                          /* 腾出一个位置 */
    connfd = accept(listenfd, NULL, NULL);   /* 把待处理连接接下来 */
    if (connfd >= 0)
        close(connfd);                       /* 直接关掉，让客户端收到 EOF */
    idle_fd = open("/dev/null", O_RDONLY);   /* 重新占位 */
}

这一手不是用来救活连接的，是让程序从死循环里退出来，把错误暴露到日志，剩下的交给外部限流和扩容。

还有一个容易混的上限：select 的 FD_SETSIZE。

FD_SETSIZE 是编译期常量，glibc 头文件里定的是 1024。fd_set 是一张固定长度的位图，FD_SET(fd, &set) 就是往第 fd 位写 1。fd 的值一旦大于等于 FD_SETSIZE，写的位置跑到 fd_set 之外，直接踩内存。它不是返回错误，是静默破坏。

所以 select 能管多少连接，看的是最大 fd 编号，不是连接数。程序里 0/1/2 加日志、加管道，随手就顶到 10 以上；连接一多，某个 fd 编号必然过千。

限制项 查看 / 修改 影响 处理
RLIMIT_NOFILE soft ulimit -n / setrlimit 单进程 fd 上限，超了 EMFILE 调高到 hard；hard 不够找 root
RLIMIT_NOFILE hard ulimit -Hn soft 的上限 需要 CAP_SYS_RESOURCE
系统级文件表 /proc/sys/fs/file-nr 全系统 fd 总数，超了 ENFILE 调 fs.file-max
FD_SETSIZE 编译期常量 select 的 fd 编号上限 换 poll / epoll
进程 / 线程数 ulimit -u 线程栈和调度开销 线程池，别一连接一线程

最后一行值得单说：一个连接一个线程的模型，几百个连接就把线程栈和上下文切换吃满。fd 还没到上限，CPU 先在切换上耗光了。

六、资源泄漏的排查 #

泄漏的典型形态三种：

  • 出错路径提前 return，忘了 close。
  • accept 成功、后续处理失败，只 free 了业务对象，没关连接。
  • dup / accept4 / 传 fd 的场景里，多出一份引用没人管。

症状是慢性的：跑一天没事，第三天开始 accept 报 EMFILE，重启就好，过几天再来一次。

查的顺序：

bash
ls /proc/<pid>/fd | wc -l                                # 1. 开了多少 fd
ls -l /proc/<pid>/fd | awk '{print $NF}' | sort | uniq -c | sort -rn   # 2. 都是些什么
grep 'open files' /proc/<pid>/limits                     # 3. 上限是多少
ss -s                                                    # 4. 连接堆积情况
lsof -p <pid> | wc -l                                    # 5. 对照

ls -l 的输出里 socket:[123456] 这类是套接字，inode 号能跟 ss -tanp 的输出对上，顺着找到哪条连接没关。

代码层面，C 里最实用的还是单一出口：

c
int handle_conn(int connfd)
{
    int ret = -1;
    char *buf = NULL;

    buf = malloc(BUF_SIZE);
    if (buf == NULL)
        goto out;

    if (read_request(connfd, buf, BUF_SIZE) < 0)
        goto out;

    if (write_response(connfd, buf) < 0)
        goto out;

    ret = 0;
out:
    free(buf);
    close(connfd);          /* 唯一出口，漏不掉 */
    return ret;
}

函数里多处 return 不是不行，是出错分支一多就容易漏。把释放收到一个标签下，漏的概率立刻降下来。

三个同类问题，症状像 fd 泄漏但不是：

  • 僵尸进程：fork 了不 wait，子进程退掉之后 PCB 还留着。父进程要处理 SIGCHLD，在 handler 里起 waitpid 循环（注意 EINTR），或者双 fork 让孙子进程被 init 收养。
  • TIME_WAIT 堆积：主动关闭方会留 2MSL 的 TIME_WAIT，四元组占着。短连接压测时 ss -tan | grep TIME-WAIT 能刷满屏。它不是泄漏，但会让 bind 报 EADDRINUSE，处理办法是 SO_REUSEADDR。
  • 内存泄漏：每次请求 malloc 一小块，出错路径就漏。valgrind --leak-check=full 或者 ASan 跑一遍压测能抓出来。
症状 先看什么 常见原因
accept: Too many open files ls /proc/[pid]/fd 连接处理完没 close
fd 数持续涨、连接数却平稳 按 socket inode 分类统计 出错路径漏 close
子进程状态 Z ps -ef 里找 defunct 父进程没 wait
重启报 Address already in use ss -tan 查端口 旧连接 TIME_WAIT，或别的进程占着
端口被陌生进程占着 lsof -i:端口 exec 出去的子程序继承了 fd
内存只涨不跌 top / pmap 看 RSS 差一个 free，或缓冲区越界踩坏堆

七、信号与系统调用的中断 #

先讲机制。进程阻塞在 read 上等数据，内核把它挂进等待队列。这时候来一个信号，内核把进程唤醒，从内核态返回用户态的路上先执行信号处理函数。执行完，那个 read 怎么办，分两种：

  1. 装处理函数时带了 SA_RESTART，内核自动重新发起这个系统调用。用户态看不到任何异常。
  2. 没带 SA_RESTART，read 提前返回 -1，errno 置成 EINTR。

能被打断的是「慢调用」：终端 / 管道 / 套接字上的 read 和 write、accept、阻塞的 connect、recv / send、select / poll / epoll_wait、wait、sleep。纯计算和普通文件的读写不在这个名单里。

素材里那个定时器超时的例子，就是靠这条机制把 recvfrom 从阻塞里拽出来的。

sigaction 是安装处理函数的标准接口：

c
#include <signal.h>

int sigaction(int signum, const struct sigaction *act,
              struct sigaction *oldact);
  • signum：除 SIGKILL 和 SIGSTOP 之外的信号都能装。
  • act：新的处理方式，结构体里放函数地址和各种标志。传 NULL 表示只查不改。
  • oldact：传出参数，拿到原来的处理方式。传 NULL 表示不关心。

struct sigaction 的字段：

c
struct sigaction {
    void (*sa_handler)(int);
    void (*sa_sigaction)(int, siginfo_t *, void *);
    sigset_t sa_mask;
    int sa_flags;
    void (*sa_restorer)(void);
};
字段 作用
sa_handler 老式单参处理函数，形式和 signal() 的 handler 一致
sa_sigaction 三参形式，能拿到信号编号、原因和上下文，需要 SA_SIGINFO
sa_mask 处理本信号期间要额外屏蔽的信号集合
sa_restorer 未使用，历史遗留
sa_flags 行为开关，见下表

sa_flags 常用的几个，按位或组合：

标志 含义
SA_RESTART 被信号中断的系统调用自动重启
SA_NOCLDSTOP signum 为 SIGCHLD 时，子进程暂停不通知父进程
SA_ONESHOT / SA_RESETHAND 调用处理函数后把处理方式恢复成默认
SA_NOMASK / SA_NODEFER 处理期间不屏蔽本信号，允许嵌套
SA_SIGINFO 使用三参的 sa_sigaction 而不是单参的 sa_handler

SA_RESTART 是本章的关键开关。它默认就是开着的，装上函数不做处理，被中断的调用会被悄悄重启，你的超时逻辑永远等不到 EINTR。

素材的写法值得照抄：

c
struct sigaction act;

sigaction(SIGALRM, NULL, &act);      /* 先取出当前设置 */
act.sa_handler = handler;
act.sa_flags &= ~SA_RESTART;         /* 关键：允许被中断 */
sigaction(SIGALRM, &act, NULL);      /* 再装回去 */

alarm(6);                            /* 6 秒后发 SIGALRM */
recvfrom(sockfd, buf, N, 0, NULL, NULL);
alarm(0);                            /* 收到数据就撤掉闹钟 */

为什么先 sigaction(SIGALRM, NULL, &act) 再改：直接 memset 一个全零的结构体传进去，sa_mask 变空集、sa_flags 变 0，顺手把原来配好的东西冲掉。先取旧的再改，只动自己想动的那两项。

这里有个明确的反例要说。素材的 handler 里写的是 printf：

c
void handler(int signo)
{
    printf("interrupted by SIGALRM\n");   /* 不要这么写 */
}

printf 不是 async-signal-safe 的函数，内部有锁和缓冲区。在信号处理函数里调用它会死锁，或者破坏 stdio 的状态。handler 里只该做一件事：改一个 sig_atomic_t 类型的标志位，或者往已经打开的 fd 上 write。

c
static volatile sig_atomic_t g_timeout = 0;

void handler(int signo)
{
    int saved = errno;         /* handler 会改 errno，出去前必须还原 */
    (void)signo;
    g_timeout = 1;
    errno = saved;
}

主循环里检查 g_timeout，该收摊收摊。这句 errno 的保存还原不是洁癖：handler 跑在你正在执行的那个线程上，把 errno 改了，外面的 read 判断 EINTR 时就会读到别的值。

八、EINTR 与错误重试 #

EINTR 的全部含义就一句：调用被打断了，什么也没发生，再调一次。

它不是错误。可在网络程序里，它是被误判成错误最多的一种返回值。素材里那段 recvfrom 的失败输出就是证据：

text
fs@ubuntu:~/qiang/socket/time$ ./alarm
socket successfully!
sockfd:3
bind successfully!
PORT:8888
interrupted by SIGALRM
fail to recvfrom: Interrupted system call
fs@ubuntu:~/qiang/socket/time$

程序收到 SIGALRM 之后 exit(-1) 了。它本来只想做「等 6 秒没数据就走超时分支」，结果变成「收到任何信号就自尽」。线上跑着的服务因为一个 SIGCHLD 就退出，就是这种写法。

正确的姿势是把重试封进读写函数：

c
#include <unistd.h>
#include <errno.h>

ssize_t read_n(int fd, void *buf, size_t n)
{
    size_t left = n;
    char *p = buf;

    while (left > 0) {
        ssize_t r = read(fd, p, left);
        if (r < 0) {
            if (errno == EINTR)
                continue;              /* 打断，重来 */
            return -1;                 /* 真错误 */
        }
        if (r == 0)
            break;                     /* 对端关闭 */
        p += r;
        left -= (size_t)r;
    }
    return (ssize_t)(n - left);
}

ssize_t write_n(int fd, const void *buf, size_t n)
{
    size_t left = n;
    const char *p = buf;

    while (left > 0) {
        ssize_t r = write(fd, p, left);
        if (r < 0) {
            if (errno == EINTR)
                continue;
            return -1;
        }
        p += r;
        left -= (size_t)r;
    }
    return (ssize_t)n;
}

read 一侧的重点是读满，以及把返回 0 认成 EOF。write 一侧的重点是部分写：返回值小于请求长度是正常的，缓冲区满了就这样，指针要往前走。

常见 errno 的处理动作：

errno 场合 该做什么
EINTR 任意阻塞调用被信号打断 重试，别当错误
EAGAIN / EWOULDBLOCK 非阻塞无数据，或超时到期 等下一次事件，不算失败
EMFILE 本进程 fd 用光 别重试，先腾位置（第五章那招）
ENFILE 系统文件表满 同上，比 EMFILE 更难收拾
ECONNRESET 对端发了 RST 关掉连接，别重试
EPIPE 写一个已关闭的连接 关连接；同时会收到 SIGPIPE
EINPROGRESS 非阻塞 connect 刚发起 等可写，再查 SO_ERROR
EADDRINUSE bind 的端口被占 开 SO_REUSEADDR，或换端口
ETIMEDOUT 连接超时 关掉重连，注意别死循环
ENOBUFS / ENOMEM 内核缓冲区不足 退避后重试，同时加限流

EAGAIN 和 EWOULDBLOCK 在 Linux 上是同一个值。写哪个都行，判断时拿一个比较即可，别写两个分支还以为是两种错误。

SIGPIPE 单独拎出来说，因为它的表现和 EINTR 正好相反：写一个对端已经关闭的套接字，内核先给进程发 SIGPIPE，默认动作是终止进程。你等不到 EPIPE，进程已经没了。两个办法：

c
signal(SIGPIPE, SIG_IGN);                  /* 全局忽略，之后 write 返回 -1 / EPIPE */

send(fd, buf, len, MSG_NOSIGNAL);          /* 或者每次发送都带这个标志 */

还有一种重试要克制：非幂等的操作。已经发出半个请求的连接，重连重发会让对端收到两遍，扣两次款。重试只对幂等操作说得通，其余得先在协议层做去重。

九、阻塞调用的超时控制 #

三种做法，各有各的坑。

套接字选项超时 #

设 SO_RCVTIMEO / SO_SNDTIMEO，到期内核让调用返回 -1，errno 是 EAGAIN（和 EWOULDBLOCK 同值），perror 打出来是 Resource temporarily unavailable。

c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>
#include <sys/socket.h>
#include <netinet/in.h>

#define N 64
#define PORT 8888

int main(void)
{
    int sockfd;
    char buf[N];
    struct sockaddr_in seraddr;
    struct timeval t = { 6, 0 };          /* 6 秒 */

    sockfd = socket(AF_INET, SOCK_DGRAM, 0);
    if (sockfd < 0) { perror("socket error"); exit(-1); }
    printf("socket successfully!\n");
    printf("sockfd:%d\n", sockfd);

    memset(&seraddr, 0, sizeof(seraddr));
    seraddr.sin_family = AF_INET;
    seraddr.sin_port = htons(PORT);
    seraddr.sin_addr.s_addr = htonl(INADDR_ANY);

    if (bind(sockfd, (struct sockaddr *)&seraddr, sizeof(seraddr)) < 0) {
        perror("bind error");
        exit(-1);
    }
    printf("bind successfully!\n");
    printf("PORT:%d\n", PORT);
    if (setsockopt(sockfd, SOL_SOCKET, SO_RCVTIMEO, &t, sizeof(t)) < 0) {
        perror("setsockopt error");
        exit(-1);
    }

    if (recvfrom(sockfd, buf, N, 0, NULL, NULL) < 0) {
        if (errno == EAGAIN || errno == EWOULDBLOCK)
            printf("recv timeout after 6s\n");     /* 超时，不是错误 */
        else {
            perror("fail to recvfrom");
            exit(-1);
        }
    } else {
        printf("recv data: %s\n", buf);
    }

    close(sockfd);
    return 0;
}

素材里的运行结果：

text
fs@ubuntu:~/qiang/socket/time$ ./setsockopt
socket successfully!
sockfd:3
bind successfully!
PORT:8888
fail to recvfrom: Resource temporarily unavailable

6 秒内没有包进来，recvfrom 就返回了。素材把它当错误打了出来，语义上它就是超时。

这个方案的特性：

  • 一旦设了，之后每一次收发都按这个时间走，不是一次性的。要取消，把时间值设成 0 重新 setsockopt。
  • 精度看内核，微秒字段别当真，秒级才是它擅长的。
  • 对 connect 无效，SO_SNDTIMEO 管不到连接建立阶段。

定时器信号 #

alarm 加 SIGALRM，配合清掉 SA_RESTART，让阻塞调用以 EINTR 返回。第七章已经拆过 sigaction 那几步，这里补完整的主循环：

c
#define N 64
#define PORT 8888

void handler(int signo)
{
    write(STDOUT_FILENO, "interrupted by SIGALRM\n", 23);
}

/* socket / bind 部分与上一段相同，略 */
sigaction(SIGALRM, NULL, &act);
act.sa_handler = handler;
act.sa_flags &= ~SA_RESTART;
sigaction(SIGALRM, &act, NULL);

alarm(6);
if (recvfrom(sockfd, buf, N, 0, NULL, NULL) < 0) {
    if (errno == EINTR)
        printf("recv timeout, interrupted by SIGALRM\n");
    else
        perror("fail to recvfrom");
} else {
    printf("recv data: %s\n", buf);
}
alarm(0);

素材的运行结果：

text
fs@ubuntu:~/qiang/socket/time$ ./alarm
socket successfully!
sockfd:3
bind successfully!
PORT:8888
interrupted by SIGALRM
fail to recvfrom: Interrupted system call

这个方案的特性：

  • 一次 alarm 只发一次信号，要重复超时得每轮重新 alarm。
  • alarm 和 sleep / usleep 抢同一个定时器，别混用。
  • 多线程里信号投递到哪个线程不确定，这套在单线程进程里靠谱。
  • handler 的能力受限，第十章和第七章都提过。

I/O 多路复用 #

先用 select / poll / epoll_wait 带超时等可读，等到再 recv。这层超时不改套接字本身的状态。

c
fd_set rfds;
struct timeval tv;
int ret;

FD_ZERO(&rfds);
FD_SET(sockfd, &rfds);
tv.tv_sec = 6;
tv.tv_usec = 0;

do {
    ret = select(sockfd + 1, &rfds, NULL, NULL, &tv);
} while (ret < 0 && errno == EINTR);

if (ret == 0)
    printf("timeout\n");
else if (ret > 0)
    recvfrom(sockfd, buf, N, 0, NULL, NULL);

三个注意：select 会修改 tv，循环里得重新赋值；fd 编号不能超 FD_SETSIZE（第五章）；select 返回后集合被改过，下一轮要重新 FD_SET。

方案 精度 是否影响后续调用 能用在哪 多线程
SO_RCVTIMEO / SO_SNDTIMEO 秒级，微秒字段不可靠 是，持续生效 单次收发 友好
alarm + SIGALRM 秒级 否 阻塞的任意慢调用 信号落哪个线程不定
select / poll / epoll 毫秒级 否 多路复用等待 友好

connect 的超时三个方案都用不上第一个，标准做法是非阻塞 connect 加等待可写：

c
int connect_timeout(int fd, const struct sockaddr *addr, socklen_t len, int ms)
{
    int flags = fcntl(fd, F_GETFL);
    fcntl(fd, F_SETFL, flags | O_NONBLOCK);

    int ret = connect(fd, addr, len);
    if (ret < 0 && errno != EINPROGRESS)
        return -1;

    if (ret < 0) {
        struct pollfd pfd = { fd, POLLOUT, 0 };
        do {
            ret = poll(&pfd, 1, ms);
        } while (ret < 0 && errno == EINTR);

        if (ret == 0) { errno = ETIMEDOUT; return -1; }    /* 超时 */

        int err = 0;
        socklen_t el = sizeof(err);
        getsockopt(fd, SOL_SOCKET, SO_ERROR, &err, &el);
        if (err != 0) { errno = err; return -1; }
    }
    fcntl(fd, F_SETFL, flags);        /* 恢复阻塞 */
    return 0;
}

关键是 getsockopt(SO_ERROR)：poll 报可写不代表连接建成了，连接被拒也是「可写」。错误码存在 SO_ERROR 里，取出来读一次就清零。

十、常见的内存与缓冲区问题 #

  • recv 返回 0 是对端关闭，不是收到空包。UDP 上一个 0 长度报文也返回 0，两者按套接字类型分开判。
  • 返回值的类型。recv 第三个参数是 size_t，返回值是 ssize_t。用 int 接返回值，比较 -1 和长度时容易写错。
  • 没有结束符。recv 只填字节，不会补 '\0'。素材里 char buf[N] 收完直接 printf("%s", buf) 的写法，靠的是栈上碰巧有 0。
  • 部分读写。send 返回小于请求长度属正常，要循环推进指针。read 同理，读到 0 才算完。
  • 地址长度。accept / recvfrom 的 addrlen 是传入传出参数，调用前必须赋成 sizeof(addr)，否则地址被截断或者直接 EINVAL。
  • 结构体清零。每个 sockaddr_in 填字段前先 memset，sin_zero 那 8 个字节不清会留垃圾。
  • 栈上大缓冲。char buf[1 << 20] 声明在函数里，线程栈小的时候直接爆栈。大块缓冲用 malloc 或放静态区。
  • 字节序。端口和地址要过 htons / htonl；inet_addr 返回的已经是网络序，别转两次；inet_ntoa 返回静态缓冲区，两次调用会互相踩。
  • 协议结构体对齐。直接 (struct hdr *)buf 强转，字段偏移会因对齐错位。用 #pragma pack(1) 或者逐字段 memcpy 解。
  • 用 %s 打网络数据。内容里带 % 或者不可见字符，printf 会出问题。按长度输出用 %.*s。
问题 表现 正确做法
recv 返回 0 当正常数据 死循环处理空包 判成对端关闭，关连接
不循环 send 大数据发一半，对端解析卡住 write_n 循环推进指针
buf 无终止符 日志乱码或越界读 留一字节补 '\0'，或按长度输出
addrlen 没初始化 accept 返回 EINVAL，或地址错 调用前赋 sizeof
强转协议头 字段值离谱 逐字段解析，注意字节序
栈上大数组 段错误，栈溢出 malloc 或静态缓冲
缓冲区比报文小 数据被截断，协议错位 先读长度头，再按长度分配

十一、网络程序的健壮性要点 #

这一章收两个大件：广播与组播的正确配置顺序，以及几条通用的收尾规矩。

广播：能发出去，不一定收得到 #

单播是一对一。要把数据同时发给局域网里所有主机，用广播，ARP 找目标 MAC 就是这么干的。

广播地址是网段里主机号全 1 的那个地址。拿 C 类网段 192.168.1.x、掩码 255.255.255.0 说：

  • 192.168.1.0 是网段地址
  • 192.168.1.1 ~ 192.168.1.254 可分配给主机
  • 192.168.1.255 是广播地址，发给它的包，该网段所有主机都收

发广播包时，目标 IP 是广播地址，目标 MAC 是 ff:ff:ff:ff:ff:ff。

发送流程四步：建 UDP 套接字、指定目标地址和端口、打开 SO_BROADCAST、sendto。第二步和第三步顺序能换，第三步不能省——套接字默认不许发广播。

c
#define N 64
#define PORT 8888

int main(void)
{
    int sockfd;
    int on = 1;
    char buf[N] = "This is a broadcast package!";
    struct sockaddr_in dstaddr;

    sockfd = socket(AF_INET, SOCK_DGRAM, 0);
    if (sockfd < 0) { perror("socket error"); exit(-1); }

    memset(&dstaddr, 0, sizeof(dstaddr));
    dstaddr.sin_family = AF_INET;
    dstaddr.sin_port = htons(PORT);
    dstaddr.sin_addr.s_addr = inet_addr("192.168.1.255");   /* 网段广播地址 */

    if (setsockopt(sockfd, SOL_SOCKET, SO_BROADCAST, &on, sizeof(on)) < 0) {
        perror("setsockopt error");
        exit(-1);
    }

    while (1) {
        sendto(sockfd, buf, N, 0, (struct sockaddr *)&dstaddr, sizeof(dstaddr));
        sleep(1);
    }
    return 0;
}

接收端三步：建 UDP 套接字、bind 地址、recvfrom 循环。bind 的地址就填广播地址。

c
    seraddr.sin_addr.s_addr = inet_addr("192.168.1.255");   /* 接收方绑广播地址 */
    if (bind(sockfd, (struct sockaddr *)&seraddr, sizeof(seraddr)) < 0) {
        perror("bind error");
        exit(-1);
    }

    while (1) {
        if (recvfrom(sockfd, buf, N, 0,
                     (struct sockaddr *)&seraddr, &peerlen) < 0) {
            perror("fail to recvfrom");
            exit(-1);
        }
        printf("[%s:%d]", inet_ntoa(seraddr.sin_addr), ntohs(seraddr.sin_port));
        printf("%s\n", buf);
    }

广播三个坑：默认不跨路由器，只在本网段内可达；绑定 255.255.255.255（受限广播）和绑定某个网段的定向广播地址行为不同，前者只在本机所有接口上生效；广播会打断网段里每一台主机的链路层，发太频繁就是广播风暴，业务里能上组播就别用广播。

组播：先加入组，再 bind #

组播介于单播和广播之间：只发给加入了这个组的主机，其余主机在链路层直接丢掉。IPv4 地址分五类，D 类是组播：

类别 前缀 范围 用途
A 最高位 0 1.0.0.1 ~ 126.255.255.254 单播
B 最高位 10 128.0.0.1 ~ 191.254.255.254 单播
C 最高位 110 192.0.1.1 ~ 223.255.254.254 单播
D 最高位 1110 224.0.0.0 ~ 239.255.255.255 组播
E 最高位 1111 240.0.0.0 起 保留

一个组播地址代表一个多播组。224.0.0.1 是本地链路上所有主机，属于永久组，不用加入也能收。

发送流程三步：建 UDP 套接字、指定目标组播地址和端口、sendto。发送端不必加入组。

c
    dstaddr.sin_addr.s_addr = inet_addr("224.10.10.1");     /* 绑定组播地址 */

    while (1) {
        sendto(sockfd, buf, N, 0, (struct sockaddr *)&dstaddr, sizeof(dstaddr));
        sleep(1);
    }

接收流程四步，顺序不能乱：建 UDP 套接字、加入多播组、bind 地址和端口、recvfrom。素材原话：紧接着 bind 的那个 setsockopt，作用是把 socket 加入组播组，因为 socket 要收 224.0.0.1 的数据，就必须先加入该组。

加入组用 IPPROTO_IP 层的 IP_ADD_MEMBERSHIP，参数是 struct ip_mreq：

c
struct ip_mreq {
    struct in_addr imr_multiaddr;   /* 组播组的 IP 地址 */
    struct in_addr imr_interface;   /* 本地某个网络设备接口的 IP 地址 */
};

一台主机有多块网卡、接多个子网时，imr_interface 指定在哪个接口所在的子网加入这个组。填 INADDR_ANY 让内核自己选。填错了，包从另一块网卡进来，你就收不到。

c
    memset(&mreq, 0, sizeof(mreq));
    mreq.imr_multiaddr.s_addr = inet_addr("224.10.10.1");   /* 加入多播组 */
    mreq.imr_interface.s_addr = htonl(INADDR_ANY);

    if (setsockopt(sockfd, IPPROTO_IP, IP_ADD_MEMBERSHIP,
                   &mreq, sizeof(mreq)) < 0) {
        perror("fail to setsockopt");
        exit(-1);
    }

    memset(&myaddr, 0, sizeof(myaddr));                     /* 绑定组播地址和端口 */
    myaddr.sin_family = AF_INET;
    myaddr.sin_port = htons(PORT);
    myaddr.sin_addr.s_addr = inet_addr("224.10.10.1");

    if (bind(sockfd, (struct sockaddr *)&myaddr, sizeof(myaddr)) < 0) {
        perror("bind error");
        exit(-1);
    }

组播四个坑：只 bind 不加组收不到，链路层就把包丢了，bind 成功也没用；加了组不 bind 到组播地址和端口同样收不到，加组只告诉链路层「这个组我收」，bind 决定哪个套接字拿数据；组播 TTL 默认是 1，出不了本地网段，要跨网段得设 IP_MULTICAST_TTL，中间路由器还得开组播路由；本机发本机收能收到，是因为 IP_MULTICAST_LOOP 默认开着，关掉之后就收不到，调试时容易懵。

其余几条收尾规矩 #

  • 每个系统调用都查返回值。socket、bind、listen、accept、setsockopt 都会失败，把 errno 打出来。
  • 长连接要有超时和心跳。SO_KEEPALIVE 是 TCP 层探测，默认空闲两小时后才开始，指望它发现断线不现实。
  • 主动关闭先 shutdown(SHUT_WR)，让对端读到 EOF，把自己该发的发完，再 close。SO_LINGER 设成 {1, 0} 会直接发 RST，只在明确要重置连接时用。
  • 服务端几乎都要开 SO_REUSEADDR。不开的话，重启时上个进程留下的 TIME_WAIT 会让 bind 失败。
  • 崩溃前把日志 write 出去，别留在 stdio 缓冲区。fork 之前先 fflush，避免子进程重复输出父进程缓冲区里的内容。

十二、易错点速查 #

现象 原因 处理
父进程 close 了套接字，子进程还能用 描述符只是引用，内核对象还在 正常现象；要真断用 shutdown
进程退出后端口仍被占 exec 出去的子程序继承了监听 fd 创建时加 SOCK_CLOEXEC
重启报 Address already in use 旧连接 TIME_WAIT，或别的进程占着 SO_REUSEADDR；lsof -i 查占用者
子进程设了 O_NONBLOCK，父进程也变了 状态标志在 file 对象里，共享 别在 fork 之后改共享 fd 的标志
关掉自己这份 fd，另一端连接还在 SCM_RIGHTS 传的是引用 两边都关才算断
recvmsg 成功但 fd 不见了 控制缓冲区太小，MSG_CTRUNC 用 CMSG_SPACE 算足长度并查标志
收到信号后程序莫名退出 EINTR 被当成错误 判断 errno == EINTR 后重试
设了 alarm 超时却从不触发 SA_RESTART 让调用自动重启 sa_flags &= ~SA_RESTART
信号处理函数里 printf 卡死 printf 不是 async-signal-safe handler 只改 sig_atomic_t 标志
超时报 Resource temporarily unavailable 那是 EAGAIN，不是错误 判 EAGAIN 当超时处理
写已关闭的连接，进程直接没了 SIGPIPE 默认终止进程 SIG_IGN 或 MSG_NOSIGNAL
accept 报 Too many open files fd 用光，EMFILE 调 RLIMIT_NOFILE；查泄漏；预留 idle fd
select 在 fd 编号大时崩 超 FD_SETSIZE，越界写位图 换 poll / epoll
跑几天后 fd 数只涨不跌 出错路径漏 close 单一出口释放；ls /proc/pid/fd 定位
连接一多 CPU 全在上下文切换 一连接一线程 线程池，或者 epoll
广播 sendto 报权限错误 没开 SO_BROADCAST setsockopt 打开它
组播一个包也收不到 没 join，或 bind 的地址端口不对 先 IP_ADD_MEMBERSHIP 再 bind
组播出了本网段就断 TTL 默认 1 设 IP_MULTICAST_TTL
两个子进程抢同一份数据 fork 后共享同一个读队列 一个连接只交给一个进程
printf 打 recv 的缓冲区出现乱码 数据没有 '\0' 终止 按长度输出，或自己补结束符
解析协议头字段值离谱 对齐错位或漏了字节序转换 逐字段解析，配 ntohs / ntohl

排错顺序，从外往里：

  1. 数 fd：ls /proc//fd | wc -l，盯着涨不涨。
  2. 看上限：grep 'open files' /proc//limits。
  3. 看连接状态：ss -tanp 里有没有成片的 CLOSE_WAIT 或 TIME_WAIT。
  4. 看 errno：所有失败分支都要打出来，别只打一个 error。
  5. 回代码里看出错路径，八成漏在某个 goto 之前。

CLOSE_WAIT 那条多说一句：成片的 CLOSE_WAIT 一定是你这边的问题，对端发了 FIN，你的程序没 close。这不是网络故障，是代码问题。TIME_WAIT 反过来，是主动关闭太多，短连接改长连接能压下去。

写到这儿，进阶这一层该覆盖的都覆盖了。把 fork 的共享关系想清楚，把 EINTR 判断补上，把 fd 上限和泄漏盯住，剩下的靠业务打磨。真让线上不安静的从来不是协议本身，是这些边角上的返回值。
