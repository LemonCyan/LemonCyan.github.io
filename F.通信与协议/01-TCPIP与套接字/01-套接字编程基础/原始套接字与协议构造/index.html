这篇讲两件事：一是绕过传输层、自己造协议头的原始套接字；二是一个 HTTP 请求在字节层面到底长什么样。

讲什么：SOCK_RAW 与 SOCK_STREAM/SOCK_DGRAM 的差别、创建它的权限门槛、IP_HDRINCL 下怎么自己填 IP 头、校验和怎么算、原始包怎么发怎么收、AF_PACKET 怎么抓链路层帧、原始套接字的典型用途，以及一次 HTTP 请求从 socket() 到 close() 的完整字节流。

不讲什么：内核里原始套接字的实现细节（收包队列怎么走、协议栈在哪一层复制副本）、不同发行版对能力位的默认配置差异、防火墙与原始套接字的交互。这些要翻内核源码和发行版手册，本篇不编。

跨篇指路：普通 TCP/UDP 套接字的建连、收发、关闭在《TCP 套接字编程》一篇；主机与开发板之间的串口、网口通信在《主机与开发板通信》一篇；阻塞与非阻塞、select/poll/epoll 在 IO 模型那一组；抓到的包怎么逐字段读在协议分析那一组。

一、原始套接字是什么 #

打开一个普通 TCP 套接字，你交出去的是应用层的一段字节，收回来也是应用层的一段字节。中间那段路——加 TCP 头、算校验和、加 IP 头、查路由、发 ARP 问 MAC 地址——全由内核协议栈代劳。你从头到尾没见过一个首部字段。

这套分工好用，代价是你也改不了它。

原始套接字把这条界线往下挪。socket(AF_INET, SOCK_RAW, IPPROTO_TCP) 拿到的 fd，写入的数据直接落到 IP 层：内核不再替你生成 TCP 头，你写好一个完整的 TCP 报文段塞给它，它补上 IP 头发出去。再把 IP_HDRINCL 打开，连 IP 头也归你填，内核只管把这一串字节交给网卡。

一句话：原始套接字把「造协议头」的责任从内核交还给应用。

能力和门槛是同一件事的两面，这点要先摆清楚：

  • 能自己填源 IP，所以能造出源地址不属于本机的包。
  • 能自己填 TCP 标志位，所以能只发一个 SYN，不跟内核的握手状态机走。
  • 能拿到带 IP 头的原始数据，所以能看见 TTL、看见分片、看见协议号。
  • 正因为头是你填的，校验和错一个字节，包在对端被静默丢弃，没有任何错误码回到你手上。

一条数据从应用到网卡，责任怎么分 #

环节 普通 SOCK_STREAM SOCK_RAW（默认） SOCK_RAW + IP_HDRINCL
应用数据 你写 你写 你写
TCP/UDP 首部 内核生成 你写 你写
TCP/UDP 校验和 内核算 你算 你算
IP 首部 内核生成 内核生成 你写
IP 校验和 内核算 内核算 内核算（填 0 让它补）
路由查找、ARP 内核 内核 内核
以太网帧、MAC 地址 内核 + 网卡 同左 同左
重传、排序、去重 内核 无 无

右侧那两列，落到应用上的工作量差着一个数量级。这也是原始套接字写完第一版就得调半天的原因。

原始套接字能做什么，不能做什么 #

能做：

  • 发 ICMP，自己拼 Echo Request，写一个不依赖系统 ping 的探测程序。
  • 发自定义协议号的 IP 包（比如协议号 253、254 这两个实验用号）。
  • 抓本机收到或发出的 IP 包，做流量观测和协议学习。
  • 构造特定标志位组合的 TCP 段，做协议一致性测试和教学演示。

不能做：

  • 不能让包绕过路由和 ARP。IP_HDRINCL 只给你首部的笔，不给你选路的权，包还是按目的地址查路由表走。
  • 不能保证对方一定收到。原始套接字没有重传，丢了就是丢了。
  • 不能靠它替内核建立 TCP 连接。你自己发的 SYN，内核的 TCP 状态机不知道，对端回的 SYN+ACK 会被内核当成「无此连接」回 RST。要自己完成握手，得同时管住收方向的包并关掉内核的 RST，这是另一件事，本篇不展开。
  • 不能伪造任意源 MAC 跨网段。链路层的源 MAC 是你的网卡，出了网关第一跳就被改写。

二、与流式、数据报套接字的区别 #

三种套接字最硬的区别只有一个：你写入的第一个字节，落在协议栈的哪一层。

维度 SOCK_STREAM（TCP） SOCK_DGRAM（UDP） SOCK_RAW（原始）
所属层次 传输层 传输层 网络层（AF_INET）或链路层（AF_PACKET）
创建调用 socket(AF_INET, SOCK_STREAM, 0) socket(AF_INET, SOCK_DGRAM, 0) socket(AF_INET, SOCK_RAW, IPPROTO_TCP)
第三个参数 0，内核按类型选协议 0，同上 协议号，必须自己指定
写入起点 应用数据 应用数据 IP 头之后（默认）／IP 头第一字节（IP_HDRINCL）
内核补的首部 IP + TCP IP + UDP IP（默认）／什么都不补（IP_HDRINCL）
连接状态 有，三次握手、四次挥手 无 无，内核不维护
可靠性 重传、排序、去重 无 无
校验和 内核算 内核算 你算
权限 普通用户 普通用户 root 或 CAP_NET_RAW
收包范围 本连接的数据 发给本端口的数据报 匹配协议号、目的为本机的包
数据边界 无，字节流，要靠协议自己划界 有，一个数据报一次 recvfrom 按 IP 包划界

三个需求，对应三种选择 #

需求 A：把一段 HTML 取回来。 走 SOCK_STREAM，因为你既不想自己算校验和，也不想自己管重传和乱序，更需要「字节流一定完整」这个保证。HTTP 就建在这上面。

需求 B：发一条 DNS 查询。 走 SOCK_DGRAM。一问一答，短，丢了重发一次就行，不需要握手的三次往返。数据报天然带边界，一个响应正好一个 recvfrom。

需求 C：发一个 TTL 设成 1 的探测包，看哪台路由器回 ICMP 超时。 走 SOCK_RAW。TTL 在 IP 头里，setsockopt 的 IP_TTL 能改，但你要看的是返回的 ICMP 报文原文——够到原始报文这一层，就只能上原始套接字。

第三个参数不是 0，这是关键区别 #

socket() 的第三个参数在流式、数据报套接字里填 0，含义是「交给内核挑」。在原始套接字里它必须是一个明确的协议号，因为内核要靠它决定两件事：

  1. 发送时，IP 头的协议字段填什么（未开 IP_HDRINCL 时）。
  2. 接收时，哪些协议的包复制一份给你。
c
// 只管 TCP
int fd_tcp = socket(AF_INET, SOCK_RAW, IPPROTO_TCP);
// 只管 ICMP，ping 的实现基础
int fd_icmp = socket(AF_INET, SOCK_RAW, IPPROTO_ICMP);
// 只管 UDP
int fd_udp = socket(AF_INET, SOCK_RAW, IPPROTO_UDP);

协议号本身是 IP 头里那个 8 位字段，/etc/protocols 里有对照：ICMP 是 1，TCP 是 6，UDP 是 17。想让内核把收到的包都给你一份，Linux 上可以传 IPPROTO_RAW 或 ETH_P_ALL（后者是链路层的事，见第七章）。

三、权限要求 #

原始套接字不是给普通用户程序准备的，这是安全设计，不是疏漏。

想想它允许什么：构造源 IP 不属于本机的包、构造任意标志位的 TCP 段、嗅探本机收到的所有包。这三件事任何一件交给普通用户，主机所在的网络就不再可信。所以内核在 socket() 这一步就把门关上了。

平台 需要什么 创建失败时的表现
Linux root，或进程具备 CAP_NET_RAW 能力 返回 -1，errno 为 EPERM
Linux 容器 默认能力集不含 CAP_NET_RAW，需显式授予 同上，容器内是 root 也不行
Windows 管理员权限 返回 INVALID_SOCKET，WSAGetLastError() 给 WSAEACCES
macOS root 返回 -1，errno 为 EPERM

先看代码怎么判断：

c
#include <stdio.h>
#include <errno.h>
#include <string.h>
#include <sys/socket.h>
#include <netinet/in.h>

int main(void) {
    int fd = socket(AF_INET, SOCK_RAW, IPPROTO_ICMP);
    if (fd < 0) {
        fprintf(stderr, "socket failed: %s (errno=%d)\n", strerror(errno), errno);
        return 1;
    }
    printf("raw socket fd = %d\n", fd);
    close(fd);
    return 0;
}

以普通用户跑，输出是 Operation not permitted (errno=1)，也就是 EPERM。以 sudo 跑，打印出一个 fd。这就是全部的门槛，没有中间态。

不给 root 也能跑：能力位 #

生产环境里给整个进程 root 太重。Linux 的能力机制允许只给一项：

bash
sudo setcap cap_net_raw+ep ./rawping   # 挂上能力位，普通用户执行也能建
capsh --print                          # 看当前进程有哪些能力
getcap ./rawping                       # 看某个文件挂了哪些能力

系统自带的 ping 就是这么做的。它历史上是 setuid root，现在多数发行版改成只挂 CAP_NET_RAW 的文件能力——效果一样，风险面小得多。

容器里要单独放开：

bash
docker run --cap-add=NET_RAW --rm -it myimage ./rawping

注意 --privileged 会把所有能力一次性给全，为了一个原始套接字开这个开关不划算。

抓包还要多一项 #

抓包只读 CAP_NET_RAW 够了。要把网卡切到混杂模式（第七章），改的是接口标志位，这属于网络管理，得再要 CAP_NET_ADMIN：

bash
sudo setcap cap_net_raw,cap_net_admin+ep ./sniffer

tcpdump 在多数发行版上挂的正是这两项。

四、自己构造 IP 头 #

IPv4 首部最短 20 字节，字段是固定的。开了 IP_HDRINCL 之后，这 20 个字节归你填，填错哪个字段就出哪种问题。

字段 位宽 填什么 容易踩的地方
版本 ip_v 4 4 填 6 就是 IPv6，整包作废
首部长度 ip_hl 4 首部字节数 ÷ 4 20 字节要填 5，不是 20
服务类型 ip_tos 8 0 要试 DSCP 才填别的
总长度 ip_len 16 首部 + 负载字节数 网络字节序；含 IP 头，不含以太网头
标识 ip_id 16 0 分片重组用，内核会补
标志 + 片偏移 ip_off 16 0 不分片就是 0
生存时间 ip_ttl 8 64 每过一个路由器减 1，减到 0 回 ICMP 超时
协议 ip_p 8 IPPROTO_TCP 等 要与 socket 第三个参数一致
首部校验和 ip_sum 16 0 Linux 下填 0，内核补
源地址 ip_src 32 本机 IP，或你想伪造的值 乱填就别指望收到回包
目的地址 ip_dst 32 目标 IP 决定了包往哪走

IP_HDRINCL 关与开的区别 #

  • 不启用（默认）：你写入的数据从 IP 首部之后的第一个字节开始。IP 首部由内核生成，协议字段按 socket() 第三个参数自动填。
  • 启用：你从 IP 报头的第一字节开始写，整个 IP 头加 TCP/UDP 头都是你的活。只有 IP 校验和与标识 ID 可以留给内核。

开关就一行：

c
const int on = 1;
if (setsockopt(sockfd, IPPROTO_IP, IP_HDRINCL, &on, sizeof(on)) < 0) {
    perror("setsockopt IP_HDRINCL failed");
}

IPPROTO_IP 是层级，说明这个选项作用在 IP 层；IP_HDRINCL 是选项名。

逐字段填一遍 #

c
char buf[128] = {0};

struct ip *ip = (struct ip *)buf;
struct tcphdr *tcp = (struct tcphdr *)(buf + sizeof(struct ip));
int ip_len = sizeof(struct ip) + sizeof(struct tcphdr);

// IP 首部
ip->ip_v   = IPVERSION;                 // 4
ip->ip_hl  = sizeof(struct ip) >> 2;    // 20 >> 2 = 5
ip->ip_tos = 0;
ip->ip_len = htons(ip_len);             // 20 + 20 = 40
ip->ip_id  = 0;
ip->ip_off = 0;
ip->ip_ttl = MAXTTL;                    // 255
ip->ip_p   = IPPROTO_TCP;
ip->ip_sum = 0;                         // 留 0，内核补
ip->ip_dst = target->sin_addr;

三个点必须记牢：

  1. ip_hl 的单位是 4 字节，sizeof(struct ip) >> 2 这个写法比写死 5 稳，换平台不会错。
  2. 只有 ip_len、ip_id、ip_off、ip_sum 这些多字节字段要过 htons。ip_v/ip_hl/ip_tos/ip_p/ip_ttl 是单字节，直接赋值。
  3. 数据区从 buf + sizeof(struct ip) 开始，指针强转成 struct tcphdr * 之后按结构体填 TCP 字段，跟填 IP 头一个套路。

五、校验和怎么算 #

校验和是原始套接字最劝退的一环。算法本身十行，坑在「对哪段数据求和」。

算法：16 位反码和取反 #

把数据按 16 位分组，全部相加，溢出的高位加回低位，最后按位取反。

c
unsigned short checksum(unsigned short *addr, int len) {
    int nleft = len;
    int sum = 0;
    unsigned short *w = addr;
    unsigned short answer = 0;

    // 每次吃 2 字节
    while (nleft > 1) {
        sum += *w++;
        nleft -= 2;
    }

    // 奇数长度，最后一个字节补高位
    if (nleft == 1) {
        *(unsigned char *)(&answer) = *(unsigned char *)w;
        sum += answer;
    }

    // 高位进位回卷，做两次
    sum = (sum >> 16) + (sum & 0xffff);
    sum += (sum >> 16);
    answer = ~sum;
    return answer;
}

拿一个手算例子走一遍。假设要对 2 字节 0x1234 和 0x5678 求和：

  • 0x1234 + 0x5678 = 0x68AC，没有进位。
  • 取反：~0x68AC = 0x9753。校验和就是 0x9753。
  • 收端把三个值一起加起来：0x1234 + 0x5678 + 0x9753 = 0xFFFF，再取反得 0，判定通过。

带进位的例子：0xFFFF + 0x0002 = 0x10001。取低 16 位是 0x0001，进位 1 加回低位：0x0002。取反得 0xFFFD。

IP 头校验和：只算首部 #

IP 首部校验和只覆盖 IP 首部那 20 字节（或带选项的更长首部），不覆盖负载。字段里的 ip_sum 在计算时置 0。

c
ip->ip_sum = 0;
ip->ip_sum = checksum((unsigned short *)ip, sizeof(struct ip));

Linux 的 IP_HDRINCL 允许你把 ip_sum 留 0，内核发出去前会补。想自己算也没问题，两者不冲突。

TCP 校验和：必须带伪首部 #

这是最容易错的地方。TCP 和 UDP 的校验和不止覆盖自己的首部加数据，还要在前面拼一个 12 字节的「伪首部」：

伪首部字段 长度 内容
源 IP 地址 4 取 IP 头里的源地址
目的 IP 地址 4 取 IP 头里的目的地址
保留 1 0
协议号 1 TCP 填 6，UDP 填 17
TCP/UDP 长度 2 首部 + 数据的字节数

伪首部只参与计算，不真的发到网上。它的存在是为了让 TCP 能校验「这个段是不是被送到了错误的地址上」。

所以「对 TCP 头单独调一次 checksum」是不够的，算出来的值对端不认。正确写法：

c
// 伪首部结构
struct pseudo_header {
    unsigned int   src_addr;
    unsigned int   dst_addr;
    unsigned char  placeholder;
    unsigned char  protocol;
    unsigned short tcp_length;
};

// 带伪首部的 TCP 校验和
unsigned short tcp4_checksum(struct ip *ip, struct tcphdr *tcp, int tcp_len) {
    struct pseudo_header psh;
    char *pseudo_buf = malloc(sizeof(struct pseudo_header) + tcp_len);
    if (!pseudo_buf) return 0;

    psh.src_addr    = ip->ip_src.s_addr;
    psh.dst_addr    = ip->ip_dst.s_addr;
    psh.placeholder = 0;
    psh.protocol    = IPPROTO_TCP;
    psh.tcp_length  = htons(tcp_len);

    memcpy(pseudo_buf, &psh, sizeof(struct pseudo_header));
    memcpy(pseudo_buf + sizeof(struct pseudo_header), tcp, tcp_len);

    unsigned short result = checksum((unsigned short *)pseudo_buf,
                                     sizeof(struct pseudo_header) + tcp_len);
    free(pseudo_buf);
    return result;
}

调用时顺序有讲究：先把 IP 头的源和目的地址填好，再算 TCP 校验和，因为它要读这两个字段。

c
ip->ip_src.s_addr = src_ip;              // 先定源地址
tcp->check = 0;
tcp->check = tcp4_checksum(ip, tcp, sizeof(struct tcphdr));

六、发送与接收原始包 #

发送：sendto 的两个地址 #

原始套接字用 sendto 发，但它要两个「目的地址」，容易混：

  • IP 头里的 ip_dst：决定包最终去哪，对端看到的就是这个地址。
  • sendto 的 sockaddr_in：给内核查路由用，决定从哪块网卡出去。

两个不一致时，包会按 sendto 的地址选路，但 IP 头里写着另一个目的地址，结果就是包寄到了错误的网络。所以这两个要一致，除了故意做测试。

c
sendto(skfd, buf, ip_len, 0,
       (struct sockaddr *)target, sizeof(struct sockaddr_in));

第三个参数 ip_len 是整个 IP 包的长度，从 IP 头第一字节算起。

完整例子：手搓一个 SYN 段 #

下面这段把前面几节串起来：开原始套接字、开 IP_HDRINCL、填 IP 头、填 TCP 头、算校验和、发出去。伪造源 IP 的部分保留原样，它演示的正是「源地址不由内核决定」这件事。

c
// syn.c —— 手工构造 TCP SYN 报文，用于协议学习和授权测试
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/socket.h>
#include <sys/types.h>
#include <netinet/in.h>
#include <netinet/ip.h>
#include <netinet/tcp.h>
#include <arpa/inet.h>

// checksum() 与 tcp4_checksum()、struct pseudo_header
// 三个定义照抄第五章，这里省掉，只看主线

void send_syn(int skfd, struct sockaddr_in *target, unsigned short srcport) {
    char buf[128] = {0};
    struct ip *ip   = (struct ip *)buf;
    struct tcphdr *tcp = (struct tcphdr *)(buf + sizeof(struct ip));
    int ip_len = sizeof(struct ip) + sizeof(struct tcphdr);

    // 1. 自制 IP 首部
    ip->ip_v   = IPVERSION;
    ip->ip_hl  = sizeof(struct ip) >> 2;
    ip->ip_tos = 0;
    ip->ip_len = htons(ip_len);
    ip->ip_id  = 0;
    ip->ip_off = 0;
    ip->ip_ttl = MAXTTL;
    ip->ip_p   = IPPROTO_TCP;
    ip->ip_sum = 0;
    ip->ip_dst = target->sin_addr;

    // 2. 自制 TCP 首部
    tcp->source = htons(srcport);
    tcp->dest   = target->sin_port;
    tcp->seq    = htonl(random());
    tcp->doff   = sizeof(struct tcphdr) >> 2;   // 20 >> 2 = 5
    tcp->syn    = 1;                            // 第一次握手
    tcp->check  = 0;

    // 3. 伪造源 IP，然后算校验和
    //    注意 ip_src 必须在算校验和之前定下来，伪首部要读它
    ip->ip_src.s_addr = random();
    tcp->check = tcp4_checksum(ip, tcp, sizeof(struct tcphdr));

    // 4. 发送
    sendto(skfd, buf, ip_len, 0,
           (struct sockaddr *)target, sizeof(struct sockaddr_in));
}

int main(int argc, char **argv) {
    if (argc != 4) {
        printf("Usage: %s target_ip dst_port src_port\n", argv[0]);
        exit(1);
    }

    struct sockaddr_in target;
    memset(&target, 0, sizeof(target));
    target.sin_family = AF_INET;
    target.sin_port = htons(atoi(argv[2]));
    inet_pton(AF_INET, argv[1], &target.sin_addr);

    int skfd = socket(AF_INET, SOCK_RAW, IPPROTO_TCP);
    if (skfd < 0) {
        perror("socket");
        exit(1);
    }

    const int on = 1;
    if (setsockopt(skfd, IPPROTO_IP, IP_HDRINCL, &on, sizeof(on)) < 0) {
        perror("setsockopt IP_HDRINCL");
        exit(1);
    }

    send_syn(skfd, &target, atoi(argv[3]));
    close(skfd);
    return 0;
}

在授权环境里跑，抓包能看到这个 SYN。想把 while(1) 的循环打满，得自己加循环和发速控制——原素材是直接死循环无节制地发，这里收成一次发送，重点是报文怎么拼。

接收：从 IP 头开始读 #

原始套接字收包时，内核把匹配协议号的包复制一份给你，从 IP 头第一字节开始，recvfrom 返回值就是整个 IP 包的长度。内核自己的协议栈照常处理这些包，你只是多了一份副本。

c
char rbuf[65536];

while (1) {
    struct sockaddr_in from;
    socklen_t fromlen = sizeof(from);

    ssize_t n = recvfrom(skfd, rbuf, sizeof(rbuf), 0,
                         (struct sockaddr *)&from, &fromlen);
    if (n < 0) {
        perror("recvfrom");
        break;
    }

    struct ip *ip = (struct ip *)rbuf;
    int ip_hdr_len = ip->ip_hl << 2;              // 4 位字段 ×4
    int total_len  = ntohs(ip->ip_len);

    printf("from %s proto %d ttl %d len %d payload %d\n",
           inet_ntoa(ip->ip_src), ip->ip_p, ip->ip_ttl, total_len,
           (int)(n - ip_hdr_len));

    // 想往下看负载，就按 ip_hdr_len 跳过 IP 头
    unsigned char *payload = (unsigned char *)rbuf + ip_hdr_len;
    (void)payload;
}

两个细节：

  • ip_hl 要乘 4 才是字节数，反方向和填空时正好相反。
  • recvfrom 拿到的是整包长度，用 ip_len（网络序转过来）核对一遍，能发现截断。

struct ip 还是 struct iphdr #

引入头文件时这两个名字会打架，分清楚：

结构体 来源 用在哪
struct ip BSD 风格，<netinet/ip.h> 用户空间程序按它填和读
struct iphdr Linux 内核协议栈内部，<linux/ip.h> 内核 INET 传输层实现
struct icmp BSD 风格 用户空间拼 ICMP
struct icmphdr Linux 内核内部，<linux/icmp.h> 内核实现

应用层统一用 struct ip、struct icmp 这一套。同时 include <netinet/ip.h> 和 <linux/ip.h> 会重定义报错，遇到这个报错先看头文件清单，别改代码。

字段名也不同：struct ip 是 ip_src、ip_dst、ip_p，struct iphdr 是 saddr、daddr、protocol。混着抄别人的代码，编译期就能看出问题。

七、AF_PACKET：抓链路层帧 #

AF_INET 的原始套接字往下只到 IP 头。想再往下——看以太网帧那 14 个字节的 MAC 头，或者自己填 MAC 头做链路层广播——协议族要换成 AF_PACKET：

c
int sock = socket(AF_PACKET, type, protocol);

PF_PACKET 和 AF_PACKET 是同一个值，写哪个都行。这是 Linux 专有的接口，不在 POSIX 里；BSD 系对应的是 BPF，写法完全不同，代码不通用。

第一个参数 type：给不给你 MAC 头 #

type 接收时拿到什么 发送时要做什么
SOCK_RAW 完整数据帧，含 14 字节以太网首部 自己填 MAC 头
SOCK_DGRAM 内核剥掉 MAC 头，从上层协议开始给 内核按 sockaddr_ll 里的地址补 MAC 头

要抓「整帧长什么样」，选 SOCK_RAW。只关心帧里的 IP 包，选 SOCK_DGRAM 能省掉自己跳 14 字节的活。

第三个参数 protocol：收哪些帧 #

这个参数是个过滤器，能挡掉绝大多数无关帧。要过 htons：

常量 值 收什么
ETH_P_IP 0x0800 IPv4 数据帧
ETH_P_ARP 0x0806 ARP 帧
ETH_P_IPV6 0x86DD IPv6 数据帧
ETH_P_ALL 0x0003 所有进出的帧 
c
// 只想看 ARP
int sock = socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ARP));
// 什么都收，包括本机自己发出的
int sock_all = socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ALL));

ETH_P_ALL 是抓包工具的默认选择：它同时收「发给本机的」和「本机发出的」，两个方向都能看见。

混杂模式：让网卡别过滤 #

网卡有个硬件行为：目的 MAC 不是自己、也不是广播或组播的帧，直接扔掉，不上交。这是好事，省 CPU。但抓局域网里的明文流量时，你得让网卡闭嘴照收——这就是混杂模式。

c
#include <net/if.h>
#include <sys/ioctl.h>

struct ifreq ethreq;
memset(&ethreq, 0, sizeof(ethreq));
strncpy(ethreq.ifr_name, "eth0", IFNAMSIZ - 1);

// 1. 读当前标志位
if (ioctl(sock, SIOCGIFFLAGS, &ethreq) < 0) {
    perror("SIOCGIFFLAGS");
}

// 2. 打开混杂位
ethreq.ifr_flags |= IFF_PROMISC;

// 3. 写回
if (ioctl(sock, SIOCSIFFLAGS, &ethreq) < 0) {
    perror("SIOCSIFFLAGS");
}

三步不能省中间那步：先读、改位、再写回，直接写会覆盖掉网卡原有的其他标志位。

改接口标志位要 CAP_NET_ADMIN，光有 CAP_NET_RAW 会在这里失败。

实战：手搓一个 ARP 请求 #

ARP 干的事是拿 IP 问 MAC：往全网广播「谁是这个 IP，把你的 MAC 告诉我」。整个过程 42 字节，一个以太网帧装得下。

c
// arp_req.c —— 手工拼装以太网帧 + ARP 请求并广播
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/socket.h>
#include <sys/ioctl.h>
#include <netinet/in.h>
#include <netinet/if_ether.h>
#include <net/if.h>
#include <net/if_arp.h>
#include <netpacket/packet.h>
#include <arpa/inet.h>

#define BUFLEN 42        // 14 字节以太网头 + 28 字节 ARP 报文

int main(int argc, char **argv) {
    if (argc != 3) {
        printf("Usage: %s net_device target_ip\n", argv[0]);
        exit(1);
    }

    int skfd = socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ALL));
    if (skfd < 0) {
        perror("socket");
        exit(1);
    }

    struct sockaddr_ll toaddr;
    memset(&toaddr, 0, sizeof(toaddr));

    struct ifreq ifr;
    memset(&ifr, 0, sizeof(ifr));
    strncpy(ifr.ifr_name, argv[1], IFNAMSIZ - 1);

    // 1. 网卡接口索引，sendto 靠它选出口
    if (ioctl(skfd, SIOCGIFINDEX, &ifr) < 0) {
        perror("SIOCGIFINDEX");
        exit(1);
    }
    toaddr.sll_ifindex = ifr.ifr_ifindex;

    // 2. 网卡自己的 IP（擦掉，避免被 mtu 等字段干扰）
    if (ioctl(skfd, SIOCGIFADDR, &ifr) < 0) {
        perror("SIOCGIFADDR");
        exit(1);
    }
    struct in_addr srcIP = ((struct sockaddr_in *)&(ifr.ifr_addr))->sin_addr;

    // 3. 网卡自己的 MAC
    if (ioctl(skfd, SIOCGIFHWADDR, &ifr) < 0) {
        perror("SIOCGIFHWADDR");
        exit(1);
    }
    unsigned char src_mac[ETH_ALEN];
    memcpy(src_mac, ifr.ifr_hwaddr.sa_data, ETH_ALEN);

    // 4. 以太网首部 14 字节
    char buf[BUFLEN] = {0};
    struct ethhdr *eth = (struct ethhdr *)buf;
    memset(eth->h_dest, 0xff, ETH_ALEN);        // 目的 MAC: FF:FF:FF:FF:FF:FF 广播
    memcpy(eth->h_source, src_mac, ETH_ALEN);   // 源 MAC: 本机
    eth->h_proto = htons(ETH_P_ARP);            // 帧类型 0x0806

    // 5. ARP 报文 28 字节
    struct ether_arp *arp = (struct ether_arp *)(buf + sizeof(struct ethhdr));
    arp->arp_hrd = htons(ARPHRD_ETHER);   // 硬件类型：以太网
    arp->arp_pro = htons(ETH_P_IP);       // 上层协议：IP
    arp->arp_hln = ETH_ALEN;              // MAC 长度 6
    arp->arp_pln = 4;                     // IP 长度 4
    arp->arp_op  = htons(ARPOP_REQUEST);  // 操作码 1 = 请求

    memcpy(arp->arp_sha, src_mac, ETH_ALEN);  // 源 MAC
    memcpy(arp->arp_spa, &srcIP, 4);          // 源 IP

    struct in_addr targetIP;
    inet_pton(AF_INET, argv[2], &targetIP);
    memcpy(arp->arp_tpa, &targetIP, 4);       // 要查询的目标 IP

    // 6. 发送整帧
    toaddr.sll_family = AF_PACKET;
    if (sendto(skfd, buf, BUFLEN, 0,
               (struct sockaddr *)&toaddr, sizeof(toaddr)) < 0) {
        perror("sendto");
    }

    close(skfd);
    return 0;
}

帧结构摆出来看更清楚：

部分 字节数 内容
目的 MAC 6 FF:FF:FF:FF:FF:FF，广播
源 MAC 6 本机网卡地址
帧类型 2 0x0806，ARP
硬件类型 2 1，以太网
协议类型 2 0x0800，IPv4
硬件地址长度 1 6
协议地址长度 1 4
操作码 2 1 请求，2 应答
发送方 MAC 6 本机
发送方 IP 4 本机
目标 MAC 6 请求时全 0，等对方填
目标 IP 4 要问的那个地址

合计 14 + 28 = 42 字节。ARP 报文自己没有校验和字段，以太网帧尾的 FCS 由网卡硬件生成，所以这 42 个字节填完就能发。

memset(eth->h_dest, 0xff, ETH_ALEN) 这行是广播的关键——目的 MAC 全 F，交换机就会把帧复制给同网段所有端口。

八、原始套接字的典型用途 #

由「谁能填首部」这条线往下推，能做的事就那几类：

用途 用什么 为什么非得原始套接字
ping SOCK_RAW + IPPROTO_ICMP 要读 ICMP 回包原文，还要自己拼 Echo Request
traceroute SOCK_RAW，逐跳改 IP_TTL 要控 TTL，并收沿途路由器回的 ICMP 超时
抓包 AF_PACKET + SOCK_RAW 要看到 MAC 头在内的整帧
流量观测 SOCK_RAW + ETH_P_ALL 要按 IP/TCP 字段做统计，普通套接字给不了
自定义协议实验 SOCK_RAW + 自定义协议号 内核不认识这个协议号，不替你处理
协议一致性测试 SOCK_RAW + IP_HDRINCL 要造异常的标志位组合、异常的字段值
教学演示 SOCK_RAW 亲手填一遍首部，比看图记字段强
ARP 探测 AF_PACKET 要在链路层广播，IP 层做不到

反过来说，这些活不该用它：

  • 传文件、写业务 RPC —— 用 SOCK_STREAM，别自己造可靠性。
  • 发心跳、发日志 —— 用 SOCK_DGRAM，够用且不用权限。
  • 需要 NAT 穿透或过防火墙的场景 —— 原始套接字造出来的包更容易被判为异常。

判断标准很短：要不要动传输层以上的首部。要动，才上原始套接字。

九、一次 HTTP 请求的字节流 #

转个方向。前面几章是自己造头，这一章看别人造好的头长什么样——一个 HTTP 请求，落到 TCP 字节流里到底是什么。

HTTP 是应用层协议，跑在 TCP 上。它的报文没有任何二进制魔法，就是按格式写的文本。一个请求由三部分组成：

  1. 请求行：方法 + 路径 + 版本，以 \r\n 结尾。
  2. 请求头：若干个 名字: 值，每行一个 \r\n。
  3. 一个空行：单独一个 \r\n，宣告头部结束。有请求体时，空行后面紧跟请求体。

把 GET /index.html HTTP/1.1 这个请求按字节写出来，就是这样：

text
GET /index.html HTTP/1.1\r\n
Host: example.com\r\n
Accept: */*\r\n
Accept-Language: zh-cn\r\n
User-Agent: Mozilla/5.0 (Windows NT 6.1) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/27.0.1453.116 Safari/537.36\r\n
Connection: close\r\n
\r\n

\r\n 在这里是真实的两字节 0x0D 0x0A，不是可以省的排版。写代码时用字符串字面量里的 \r\n 转义，别写成 \n——不少服务器对只有 \n 的请求行直接回 400。

逐行读一遍：

部分 内容 作用
请求行 GET /index.html HTTP/1.1 方法、路径、协议版本，空格分隔
Host 域名 HTTP/1.1 必须带，一台服务器上会挂多个站点
Accept */* 告诉服务器能接受什么类型
Accept-Language zh-cn 语言偏好
User-Agent 浏览器标识 服务器据此返回不同页面
Connection close 请求完就断开，不复用连接
空行 \r\n 头部到此结束

Connection: close 这一行在「用 socket 手写请求」的场景里几乎是必填的。原因在下一章：不带它，服务器默认 HTTP/1.1 长连接，响应发完也不关 socket，你的 recv 就一直等下去，看起来像卡死。

用 C# 发出去 #

原素材的写法，逐段拼字符串再一次性 Send：

csharp
private void SendRequest(Socket socket)
{
    string h1 = "GET " + _path + " HTTP/1.1\r\n";
    string h2 = "Accept: */*\r\n";
    string h3 = "Accept-Language: zh-cn\r\n";
    string h4 = "Host: " + _host + "\r\n";
    string h5 = "User-Agent: Mozilla/5.0 (Windows NT 6.1) AppleWebKit/537.36 "
              + "(KHTML, like Gecko) Chrome/27.0.1453.116 Safari/537.36\r\n";
    string h7 = "Connection: close\r\n\r\n";   // 最后这个空行是结束标志

    byte[] send_buffer = Encoding.UTF8.GetBytes(h1 + h2 + h3 + h4 + h5 + h7);
    socket.Send(send_buffer);

    Print("请求发送完毕，等待 Web Server 回复...");

    socket.BeginReceive(_buffer, 0, 640 * 1024, SocketFlags.None,
                        new AsyncCallback(OnReceive), socket);
}

两个细节值得停下来看：

  • h7 里是两个 \r\n，第二个就是那个空行。少了它，服务器会以为头部还没发完，一直等。
  • 缓冲区给了 640 KB。HTTP 响应大的时候一次 Receive 收不全，BeginReceive 的回调里要看返回值决定是否继续收。

同样的事，用 C 写 #

C 里没有字符串拼接的便利，直接一段字面量更清楚：

c
const char *req =
    "GET /index.html HTTP/1.1\r\n"
    "Host: example.com\r\n"
    "Accept: */*\r\n"
    "Connection: close\r\n"
    "\r\n";

ssize_t sent = send(sockfd, req, strlen(req), 0);
if (sent < 0) {
    perror("send");
}

长度直接用 strlen(req)：字面量末尾的 \0 不计入长度，发出去的最后一个字节正好是空行结尾的 \n，一个字节不多不少。

收回来的是什么 #

服务器回的也是一段文本，结构对称：状态行、响应头、空行、响应体。

text
HTTP/1.1 200 OK\r\n
Server: nginx\r\n
Date: Mon, 17 Nov 2025 12:00:00 GMT\r\n
Content-Type: text/html; charset=utf-8\r\n
Content-Length: 42\r\n
Connection: close\r\n
\r\n
<html><body><h1>hello</h1></body></html>
部分 内容 怎么读
状态行 HTTP/1.1 200 OK 版本、状态码、原因短语
响应头 若干 名字: 值 逐行按第一个 : 切开
空行 \r\n 头部结束，后面全是响应体
响应体 HTML、JSON、图片字节 长度看 Content-Length

读响应的第一个判断点是找那个空行：\r\n\r\n。前面是头，后面是体。第二个判断点是 Content-Length：有它就照着长度收，收够就停。

没有 Content-Length 时看 Transfer-Encoding: chunked，响应体被切成若干块，每块前面是十六进制长度。或者像我们这样发了 Connection: close，那就一直收到对端 close、recv 返回 0 为止——这种「读到 EOF」的做法最省事，代价是没法复用连接。

十、从 socket 到 Web 服务器的全过程 #

HTTP 的「无连接」常被误读成「不用建连接」。这条先理清：无连接指的是一次连接只处理一个请求，处理完就断开，不是说不建连接。

浏览器访问一个 Web 服务器，从头到尾八步：

  1. 建 socket。AF_INET + SOCK_STREAM + 协议 0。这一层不给权限门槛，普通用户就能建。
  2. connect。按域名解析出的 IP 和端口（HTTP 默认 80）发起连接，这一步就是三次握手：SYN、SYN+ACK、ACK。
  3. 发请求。连接建立后，把第九章那段文本写进 socket。请求行、请求头、空行，一个字节不少。
  4. 服务端 accept。监听 socket 收下握手，accept 返回一个新的已连接 socket，与这个客户端一一对应。
  5. 服务端处理并回写。读请求文本、解析路径、生成 HTML，再写回去。
  6. 服务端 close。响应发完，关掉这个连接。
  7. 浏览器收响应。recv 读到字节，按 \r\n\r\n 切开头和体，渲染。
  8. 浏览器 close。一次请求结束；下次请求重新从第 1 步走。
text
浏览器                                              服务器
  |                                                   |
  |-- socket() -------------------------------------->|
  |-- connect() --- SYN ----------------------------->|
  |<---------------- SYN + ACK -----------------------|
  |-- ACK ------------------------------------------->|   三次握手完成
  |-- send("GET / HTTP/1.1\r\nHost: ...\r\n\r\n") --->|
  |                                                   |   accept() 拿到新 socket
  |                                                   |   解析、处理、生成响应
  |<--------------- "HTTP/1.1 200 OK\r\n..." ---------|   send()
  |<--------------- FIN -------------------------------|   服务端 close
  |-- ACK ------------------------------------------->|
  |-- FIN ------------------------------------------->|   浏览器 close
  |<--------------- ACK ------------------------------|   四次挥手完成

原来那两条特性，摆到一起看：

特性 指的是 不是指
无连接 一次连接只服务一个请求，用完即断 不需要建立连接
无状态 服务器不保留上一次请求的信息 不能保存状态，cookie/session 补的正是这块

无状态的意思是：第二次请求要用第一次的结果，得由浏览器自己带回来（Cookie 头）。服务器不替你记。

协议到底是什么 #

把「协议」拆到底，它就是一段有格式的字节流：规定第一个字节代表什么、第二个字节代表什么、第几个字节到第几个字节合起来又是哪个字段。跟代码里的结构体是同一个东西，区别是这个结构体要跨机器传。

这件事有个直接后果：C 的结构体默认按编译器对齐规则排布，中间带填充字节，直接 send 一个结构体会把填充也发出去。跨语言、跨平台的通信要按协议文档逐字段序列化，解析方按同一张字段表读回来。协议写下来还有两个用处：自己按规范做的东西别人容易理解；规范写成文档，后来的人能照着写扩展模块，不必来问原作者。

协议还有一件更实际的作用：TCP 是字节流，本身没有消息边界。不事先约定「读到什么算一条消息结束」，收方就不知道在哪停。HTTP 用 \r\n\r\n 划出头部、用 Content-Length 划出身体，干的正是这件事。

对我们写程序的人来说，应用层协议才是天天打交道的那层。TCP、UDP 的首部内核管，应用层协议的格式得自己守。浏览器和 Web 服务器都守 HTTP，所以能对话；我们自己写的程序只要也守 HTTP，就能像 Chrome 一样去访问服务器。

这件事能用一条命令验证，不用写任何代码：

bash
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80

屏幕上出现的那段 HTML，就是服务器对你手敲的这段文本的回应。HTTP 不神秘的地方就在这儿：它只是 TCP 字节流里按格式写好的文本。

十一、易错点速查 #

现象 原因 改法
socket() 返回 -1，errno=EPERM 没有 CAP_NET_RAW 用 sudo，或给文件挂能力位
包发出去了，对端毫无反应 TCP 校验和漏了伪首部 用带伪首部的函数算，且先定 ip_src
抓包看到 IP 长度离谱 ip_len 没转网络序 多字节字段一律 htons
ip_hl 填了 20 单位是 4 字节 填 5，或写 sizeof(struct ip) >> 2
IP 首部校验和总是错 算之前没把 ip_sum 清 0 先置 0 再算，Linux 下直接留 0
编译报结构体重定义 同时 include netinet/ip.h 和 linux/ip.h 只用 netinet 那一套
混杂模式设不上 只有 CAP_NET_RAW 补 CAP_NET_ADMIN
抓包收到自己发的帧 ETH_P_ALL 两个方向都收 按 sll_pkttype 过滤 PACKET_OUTGOING
ARP 帧发出去没人应 h_dest 没设广播，或 sll_ifindex 是 0 目的 MAC 全 FF，接口索引从 SIOCGIFINDEX 取
HTTP 请求发完 recv 卡住 没带 Connection: close，服务端不关 补上这一行，或按 Content-Length 收够就停
服务器回 400 行尾只有 \n 全部用 \r\n，末尾补一个空行
只收到半截 HTML 一次 recv 不等于一个完整响应 循环读，收到 EOF 或收够长度为止

最后把两件事合起来看：首部是字节，协议是格式。内核替你填首部时，你只管应用数据；内核不填时，你自己就是协议栈里被跳过的那一段，校验和错一位，包就废在对端。而 HTTP 之所以看着简单，是因为它的格式已经被人定义好、写进文档、做成库了，你只需要照着写那几行文本。
