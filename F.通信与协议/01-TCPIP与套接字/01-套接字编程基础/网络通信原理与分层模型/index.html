这篇讲网络通信的底层原理：不同主机上的两个进程，怎么找到对方，数据怎么一层层传过去。

讲什么：单机进程通信的局限、IP + 协议 + 端口三元组、OSI 七层与 TCP/IP 四层、分层的好处与代价、数据封包与解包、TCP 与 UDP 的分界、TCP 的连接与可靠性、UDP 的无连接、一次通信的完整路径。

不讲什么：套接字函数的逐个参数拆解、主机字节序与网络字节序的转换细节、select/poll/epoll 的 IO 模型对比、网卡交换机路由器的排查命令。这些各有专篇。

一、网络进程通信要解决什么 #

进程通信这个概念，最早来自单机。

每个进程在自己的地址范围内跑，谁也看不见谁。两个进程要交换数据，还得互不干扰、协调一致，这件事只能由操作系统出面，提供设施。

UNIX BSD 给的是管道、命名管道、软中断：

  • pipe：管道，父子或兄弟进程之间的单向字节流
  • named pipe：命名管道，有文件系统里的名字，无亲缘关系的进程也能用
  • signal：软中断，只能传一个信号编号，传不了数据

UNIX System V 给的是消息、共享内存、信号量：

  • message：消息队列，按消息为单位收发，有类型
  • shared memory：共享存储区，最快的本机通信方式，同步要自己做
  • semaphore：信号量，不传数据，只管互斥与同步

这些设施有一个共同前提：双方在同一台机器上。

跨主机，前提崩了。

第一个问题，进程号不通用。同一台主机上，PID 唯一标识一个进程，这句话成立。到了网络环境里，每台主机独立分配 PID。A 机把 5 号给了某个进程，B 机上同样可以有一个 5 号进程。于是「5 号进程」这四个字失去了指向，你不知道说的是哪台机器上的 5 号，等于什么也没说。

第二个问题，多重协议识别。操作系统支持的网络协议很多，不同协议的工作方式不同，地址格式也不同。同一个 IP 上可以同时跑 TCP 服务和 UDP 服务，光知道 IP 不够，还得知道走哪个协议、敲哪个门。

TCP/IP 协议族把这两个问题一起解决了：

  • 网络层的 IP 地址，唯一标识网络中的主机
  • 传输层的协议加端口，唯一标识主机中的应用程序（进程）

把三者拼起来，三元组 (IP, 协议, 端口) 就能唯一标识网络中的一个进程。网络中的进程通信，靠这个标志去找对方。

这句话是网络编程的起点。后面所有的 API 调用、所有的抓包分析、所有「连不上」的排查，本质上都在给这个三元组填值：

text
客户端                                   服务端
192.168.1.10 : 52341   TCP   ────────►   192.168.1.20 : 80
    IP        端口     协议                  IP        端口

同一个 IP、同一个协议、端口不同，就是两个不同的进程。192.168.1.10 + TCP + 80 和 192.168.1.10 + UDP + 80 也是两个不同的进程。协议是三元组里最容易被忽略的一维，恰恰是它把命名空间切成了互不干扰的几块。

还有一层要交代：这些能力怎么用上。TCP/IP 协议存在于操作系统里，网络服务通过操作系统提供。操作系统里要增加支持 TCP/IP 的系统调用，就是 Berkeley 套接字：socket、connect、send、recv。另一套是 UNIX System V 的 TLI，早就淘汰了。现在几乎所有应用程序都走 socket 这条路。

所以网络编程的日常是：拿三个数字定位对方，用一组系统调用跟对方说话。

二、三元组：IP、协议、端口 #

IP：定位主机 #

IP 是网络层的逻辑地址，负责在互联网中唯一标识设备与网络，干的是寻址和路由选择的活。

  • IPv4：32 位，写成点分十进制，192.168.1.20
  • IPv6：128 位，写成八组十六进制

IP 只回答一个问题：这个包该送到哪台主机。它不关心主机上哪个进程在等，也不保证送达。IPv4 头部里的校验和只覆盖头部，数据对不对，IP 层不管。

写代码时有个特殊值要记住：INADDR_ANY。服务端把 sin_addr.s_addr 设成 htonl(INADDR_ANY)，意思是「本机所有网卡上的这个端口都收」，系统自动取本机 IP。单机测试时写 127.0.0.1 也行，但那样只有回环网卡收包，别人连不进来。

协议：定位用哪套规则说话 #

三元组里的「协议」，指传输层协议：TCP、UDP，以及 SCTP、TIPC 这类冷门货。

这里有个高频混淆：HTTP、FTP、SMTP 也常被叫「协议」，但它们在应用层，是跑在 TCP 之上的另一层约定。三元组填的是 TCP，不是 HTTP。抓包工具里 tcp.port == 80 能过滤出 HTTP 流量，因为 HTTP 只是 TCP 载荷里的一段字节。

socket() 的第三个参数 protocol 就是填这个：IPPROTO_TCP、IPPROTO_UDP、IPPROTO_SCTP、IPPROTO_TIPC。填 0 表示「按 type 自动选默认协议」，这是最常用的写法。

端口：定位主机里的进程 #

端口是 16 位整数，范围 0~65535。它是传输层给进程发的门牌号。

区间 名称 谁在用
0 ~ 1023 熟知端口（well-known） 系统服务与标准协议，绑定要 root 或 capabilities
1024 ~ 49151 注册端口 应用自己申请，MySQL 3306、Redis 6379 都在这里
49152 ~ 65535 动态端口、临时端口 客户端 connect 时内核从这里挑一个

几个常见端口，记住能省不少查文档的时间：

端口 协议 服务
22 TCP SSH
25 TCP SMTP
53 UDP 与 TCP DNS（查询走 UDP，区域传送和大响应走 TCP）
80 TCP HTTP
443 TCP HTTPS
3306 TCP MySQL
6379 TCP Redis

服务端要绑定大家都知道的地址，客户端不用。这是 bind 只在服务端出现的原因：客户端调 connect 时，内核自动分配一个动态端口，跟本机 IP 拼成自己的三元组。抓包里看到客户端端口是 52341 这种大数字，就是这个机制。

三元组怎么唯一确定一个进程 #

三件事同时成立，才锁定一个进程：

  1. 包送到了正确的主机（IP 对上）
  2. 交给了正确的协议栈（协议对上）
  3. 协议栈递给了正确的套接字（端口对上）

缺一条就落到别处去。IP 错，包根本不到；协议错，TCP 的包扔给 UDP 的套接字表，找不到；端口错，内核回一个 RST 或者 ICMP 端口不可达。

从三元组到四元组、五元组 #

三元组标识「一个进程」，四元组标识「一条连接」。

一条 TCP 连接由四元组唯一确定：源 IP、源端口、目的 IP、目的端口。再加上协议号，就是五元组，交换机的流表、防火墙的会话表、抓包工具的会话视图，都按五元组组织。

粒度 组成部分 唯一确定什么
三元组 目的 IP + 协议 + 目的端口 主机上的一个进程（服务）
四元组 源 IP + 源端口 + 目的 IP + 目的端口 一条 TCP 连接
五元组 四元组 + 协议号 一条网络流，交换机与防火墙的会话单位

这个区分不是文字游戏。一个监听 80 端口的服务进程，手上挂着成百上千条连接，这些连接的三元组完全相同，四元组各不相同。后面讲监听套接字与连接套接字的分离，根子就在这里。

端口不是进程号 #

端口是协议栈里的编号，跟 PID 没有任何对应关系。三个推论：

  • 同一个端口、同一个协议，同一时刻只能被一个套接字独占绑定。想多进程共用，得开 SO_REUSEPORT。
  • 进程退出，端口随之释放。服务重启，端口号不变，PID 换了。
  • netstat 里看到端口被占，EADDRINUSE，去杀进程杀的是持有套接字的那个进程，不是端口号本身。

三、OSI 七层与 TCP/IP 四层 #

网络分层有两套主流说法。

TCP/IP 参考模型由 IETF 定义，四层，是实际互联网通信在用的模型。OSI 参考模型由 ISO 制定，七层，粒度更细，拿来描述功能和教学。

四层，从底层到应用层：

  • 网络接口层：处理物理网络接口和链路层协议，例如以太网
  • 网络层：负责 IP 协议、路由、分组转发
  • 传输层：提供端到端的数据传输服务，包括 TCP 和 UDP
  • 应用层：各种应用层协议，例如 HTTP、FTP、SMTP

七层，从物理传输到应用层：

  • 物理层：负责物理介质传输和电信号传输
  • 数据链路层：处理数据帧的传输、物理寻址和错误检测
  • 网络层：负责逻辑寻址、路由和分组转发
  • 传输层：提供可靠的端到端数据传输，包括流量控制和错误恢复
  • 会话层：管理不同应用程序之间的会话和数据交换
  • 表示层：处理数据的表示和转换，包括数据加密和解密
  • 应用层：提供特定应用程序的服务和接口

两套模型的对照 #

OSI 七层 TCP/IP 四层 这一层管什么 典型协议 数据单元
物理层 网络接口层 电信号、光信号、比特流 以太网物理层、RS-232 比特
数据链路层 网络接口层 组帧、MAC 寻址、差错检测 以太网、PPP 帧

两处合并要说清：

  • OSI 的会话层和表示层，在 TCP/IP 里被并进应用层。原因很实在：这两层的功能在实际系统里由应用自己处理。会话管理是你代码里的状态机，表示层那套编码转换是你链接的库（TLS、gzip、JSON），协议栈不替你做。
  • OSI 的物理层和数据链路层，在 TCP/IP 里合称网络接口层。因为对 IP 来说，底下是以太网、Wi-Fi 还是 PPP，它不关心，只要能把包递出去就行。

各层协议归属 #

这几个协议经常被问「属于哪一层」，一次说清。

协议 属于哪层 干什么
MAC 地址 数据链路层 48 位（6 字节）物理硬件地址，局域网内唯一标识网络设备，实现直接通信
PPP 数据链路层 点对点连接上的数据通信，建立和管理点对点链路，拨号、串口、GPRS/3G/4G 拨号接入
ARP 网络层（有的资料归链路层） 把 IP 地址解析成 MAC 地址，局域网内建立 IP 与 MAC 的映射
RARP 网络层（有的资料归链路层） 反过来，按 MAC 地址取 IP，无盘终端引导时用
IP 网络层 逻辑地址，跨网络寻址与路由
ICMP 网络层 传递控制消息与错误报告，ping 和 traceroute 基于它
IGMP 网络层 管理组播组成员关系，多播通信里主机与路由器之间的组管理

ARP 和 RARP 的归属有分歧，看划分口径：按「服务于 IP」算网络层，按「在链路上跑」算链路层。写文章不用争，记住它干的是 IP 与 MAC 的翻译。

用哪套 #

  • 写代码：用四层。你的代码在应用层，调 socket 进传输层，往下都是内核的事。
  • 看抓包：用七层。Wireshark 的分层面板是按七层展示的，从 Frame、Ethernet II、IP、TCP 一路展开。
  • 定位故障：先按四层砍。物理通不通、IP 通不通、端口通不通、应用答不答，一层层往上排。

分层是逻辑划分，不是物理隔离。一个包从你的 send 到对方的 recv，中间没有任何一层「跳过去」，全是同一块内存里加头、拆头。

四、分层的好处与代价 #

好处一：每层只关心自己的事 #

写 HTTP 的人不用管 TCP 怎么重传，写 TCP 的人不用管 IP 怎么选路，写 IP 的人不用管底下是以太网还是 Wi-Fi。你的代码把字节塞进 send，剩下的由协议栈接管。

这就是分工。每一层的输入输出被固定成「数据 + 头部」，层内的实现随便改，只要把头部的格式和语义守住。

好处二：上层不需要知道底层怎么传 #

同一个 HTTP 客户端，跑在千兆以太网、Wi-Fi、4G 上，一行代码都不用改。底下换了介质、换了链路层协议，对上面来说不存在。

这是分层最值钱的地方：实现可以替换，接口不动。你写的程序不知道也不想知道网线是铜的还是光的。

好处三：可以分头演进 #

IPv4 换 IPv6 是网络层的事，TCP 的实现不用重写。链路从双绞线换光纤，IP 层不知道。传输层加个 SACK 选项，应用层无感。

三件事各自按自己的节奏走，这在工程上比「设计得漂亮」更实用。

代价一：封装开销 #

每下一层加一个头，头是纯粹的额外字节。一个 1 字节的应用数据，跑到线上是几十字节。

层 加了什么 累计字节
应用层 裸数据 1 字节 1
传输层 TCP 头（不含选项） 21
网络层 IPv4 头 41
链路层 以太网头 14 + FCS 4 59
物理层 前导 8 + 帧间隙 12 79

为了 1 字节数据付了 78 字节运费。大块传输时这点开销可以忽略，小包高频的协议就受不了：心跳包、游戏状态同步、IM 的每条消息，载荷比都很难看。这也是为什么这些场景会自己在应用层做批量合并或者干脆换 UDP。

代价二：层间信息重复 #

同一件事，好几层各存一份：

  • 长度：IP 头有总长度，UDP 头有长度，以太网帧有长度/类型字段，TCP 头没有长度字段（靠 IP 的总长倒推）
  • 校验：以太网帧尾有 FCS，IP 头有头部校验和，TCP/UDP 有带伪首部的校验和
  • 地址语义：链路层认 MAC，网络层认 IP，传输层认端口，每层都要重新解释一遍「发给谁」
  • 尺寸：链路层有 MTU，网络层有分片偏移，传输层有 MSS

这些重复不是设计失误，是分层的必然。每层都得能独立工作，就得自带够用的元信息，不能指望下层替它记着。代价是头部膨胀，以及改一处要顺着改多层。

代价三：跨层需求一直存在 #

有些东西天然横跨几层，硬塞进某一层就变形：

  • NAT 改了 IP 和端口，破坏传输层的端到端假设。FTP、SIP 这类把地址写进载荷的协议直接废掉，得靠 ALG 打补丁
  • 隧道（VXLAN、IPIP）在 IP 里套 IP，层数叠起来，可用 MTU 就吃紧
  • 抓包工具要看传输层的内容，就得懂应用层格式；Wireshark 的 dissector 本质是一个跨层解析器

结论：分层是默认正确的做法。碰到跨层需求，先想清楚破坏哪条边界的代价最小，再动手，别一上来就绕开协议栈自己发包。

五、数据封包与解包 #

发出去：逐层加头 #

应用层准备好字节，往下交一次，加一个头：

  1. 应用层给出一段字节，比如 HTTP 请求 GET / HTTP/1.1
  2. 传输层加 TCP 头：源端口、目的端口、序号、确认号、标志位、窗口、校验和。TCP 把字节流切成段，单位叫 TCP 段（segment）
  3. 网络层加 IP 头：源 IP、目的 IP、协议号、TTL、总长度、分片字段。单位叫 IP 包（packet），也叫数据报
  4. 链路层包上一层以太网头：目的 MAC、源 MAC、类型字段（0x0800 表示上层是 IP），尾部加 4 字节 FCS。单位叫帧（frame）
  5. 物理层把帧变成电信号、光信号或者无线电波发出去

|  头14  | 头20  | 头20  |          |

1 应用层 — 报文（message） 无
2 传输层 TCP 头 20 字节起 段（segment） 端口
3 网络层 IP 头 20 字节起 包（packet）、数据报 IP
4 链路层 以太网头 14 + 尾 4 帧（frame） MAC
5 物理层 前导 8 字节 比特流 无

第 4 步的寻址依据换了：前三层都在说 IP，到链路层必须换成 MAC。这一步的翻译由 ARP 完成——拿目的 IP 去问「谁是 192.168.1.1，报上你的 MAC」，问到了填进以太网头。同网段直接问，跨网段问的是网关的 MAC。所以跨网段通信时，以太网头里的目的 MAC 是网关的，IP 头里的目的 IP 才是最终目标的。

以太网帧长什么样 #

字段 长度 作用
前导字段 Preamble 7 字节 时钟同步
帧开始标志 SFD 1 字节 标识帧的开始
目的 MAC 地址 6 字节（旧标准 2 字节） 这帧给谁
源 MAC 地址 6 字节（旧标准 2 字节） 这帧谁发的
长度/类型 Length/Type 2 字节 上层协议类型，0x0800 是 IP，0x0806 是 ARP
LLC 数据 46 ~ 1500 字节 上层网络层封包，即整个 IP 包
填充字段 Pad 0 ~ 46 字节 数据太少时补齐，保证帧不小于最小长度
CRC 校验和 FCS 4 字节 检测传输过程中的比特差错

物理长度限制：最小 64 字节，最大 1518 字节。这两个数推导一下就有意思：

  • 最大 1518 = 14（头）+ 1500（数据）+ 4（尾），那个 1500 就是 MTU
  • 最小 64 = 14 + 46 + 4，数据不足 46 字节要填充

为什么定 64 这个下限？早年共享式以太网用 CSMA/CD 检测碰撞，最短帧的发送时间必须大于信号在最远两台机器之间往返的时间。帧太短，发完了还没收到碰撞信号，碰撞就检测不出来。

MTU 与 MSS #

两个数容易混：

  • MTU（Maximum Transmission Unit）：链路层一次能承载的最大数据量，以太网是 1500 字节，指帧的载荷上限
  • MSS（Maximum Segment Size）：TCP 段里数据部分的上限，双方在握手时通过选项协商，IPv4 上常见值 1460 = 1500 - 20（IP 头）- 20（TCP 头）

关系一句话：MSS + TCP 头 + IP 头 ≤ MTU。所以 MSS 永远小于 MTU，差值就是两层的头。

抓包里能看到 options [mss 16396] 这种大数，那是回环接口或者网卡开了 TSO/GSO 分载，真正上线前由网卡切开。物理出口上的 MSS 还是 1460 上下。

收进来：逐层拆头 #

对端收到信号，过程正好反过来：

  1. 物理层把信号还原成帧，校验 FCS，错了直接扔
  2. 链路层看目的 MAC，不是自己（也不是广播、组播地址）就扔；是自己的，剥掉以太网头，按类型字段交给上层
  3. 网络层看目的 IP，不是自己且不需要转发就扔；是自己的，剥掉 IP 头，按协议号交给传输层
  4. 传输层按目的端口找到对应套接字，剥掉 TCP/UDP 头，把数据放进该套接字的接收缓冲区
  5. 应用层 read/recv，从缓冲区拿字节

每一层都在做同一件事：读头、判断、剥头、上交。任何一层判断失败，包到此为止，不通知上面。这就是分层最直观的样子。

分片：包太大怎么办 #

IP 包超过 MTU 就得处理，两条路：

  • 分片（fragmentation）：IP 层把大包切成几片，每片带偏移量和 MF 标志，各自独立传输，到对端重组。任一片丢了，整个包作废
  • 路径 MTU 发现：靠 ICMP 的「需要分片但 DF 置位」，把 MTU 一路降到最窄的那段链路

TCP 里还有第三层保护：MSS 协商。双方握手时就把段大小压到对端能收的范围，让 IP 层压根不需要分片。这是分层协作的典型，传输层主动帮网络层避坑。

UDP 没有这层保护。sendto 一个 3000 字节的数据报，IP 层直接分片，丢一片整包报废，接收端什么也拿不到。UDP 大包容易出事的根源就在这。

六、TCP 与 UDP #

传输层有两个主要成员。

  • TCP（Transmission Control Protocol，传输控制协议）：面向连接、可靠、有序、双向的字节流
  • UDP（User Datagram Protocol，用户数据报协议）：无连接、不可靠、有消息边界的数据报

TCP/IP 本身是「传输控制协议/网间协议」的合称，是一套工业标准的协议集，为广域网设计。UDP 属于这个协议族，和 TCP 并列在传输层，工作方式跟 TCP 完全相反。

分界线：丢一条数据会不会导致业务出错 #

这就是那条线。

会出错，用 TCP。不会出错，可以用 UDP。

「出错」指的不是体验差一点，是业务逻辑本身被破坏：少一条数据，账对不上、文件解不开、消息缺字。

TCP 不是免费的：握手多一个 RTT，重传要等超时，拥塞控制会主动降速，队头阻塞让后面的数据干等前面的。UDP 便宜，但可靠性、有序性、流量控制这些活得你自己补。

七、TCP 的连接与可靠性 #

握手之前：两端各自准备 #

服务端先调 socket、bind、listen 三步，这叫被动打开（passive open）。listen 把套接字从主动类型改成被动类型，从此它只等别人来连，不主动往外连。

客户端调 connect，这叫主动打开（active open）。

c
/* 服务端：被动打开 */
int listen_fd = socket(AF_INET, SOCK_STREAM, 0);
bind(listen_fd, (struct sockaddr *)&serv_addr, sizeof(serv_addr));
listen(listen_fd, 10);          /* 10 是连接队列长度 */

/* 客户端：主动打开 */
int fd = socket(AF_INET, SOCK_STREAM, 0);
connect(fd, (struct sockaddr *)&serv_addr, sizeof(serv_addr));

三次握手 #

TCP 通过三个报文段完成连接建立，这个过程叫三次握手（three-way handshake）。

第一次握手：客户端调 connect，TCP 发出一个 SYN 分节（SYN=J），告诉服务器「我在这个连接里发送的数据，初始序列号是 J」。客户端进入 SYN_SEND 状态，等服务器确认。

第二次握手：服务器收到 SYN，必须确认它（Ack=J+1），同时自己也得发一个 SYN 分节，带上自己的初始序列号 K。两个动作合在一个报文里发出去，即 SYN+ACK 包。服务器进入 SYN_RECV 状态。

第三次握手：客户端收到 SYN+ACK，发出确认包 ACK（Ack=K+1）。这个包发完，客户端和服务器都进入 ESTABLISHED，连接建立。

一句话概括：请求——应答——再次确认。

把序号摆出来看更清楚：

步骤 方向 报文 seq ack 状态变化
第一次 客户端 → 服务端 SYN 100 — 客户端 SYN_SEND
第二次 服务端 → 客户端 SYN + ACK 200 101 服务端 SYN_RECV
第三次 客户端 → 服务端 ACK — 201 双方 ESTABLISHED

确认号的规则要记住：SYN 只占一个字节的序列号空间，所以对 SYN 的 ACK 里，确认号是相应初始序列号加 1。FIN 同理，对 FIN 的 ACK 确认号也是 FIN 的序列号加 1。ACK 里的确认号含义是「我期待你下一个发来的字节编号」。

未连接队列 #

握手过程中服务器维护一个未连接队列。每个客户端来的 SYN 包都在队列里开一个条目，条目表示：已收到 SYN，已发出确认，正等客户端确认。

这些条目对应的连接在服务器上处于 SYN_RECV 状态。服务器收到客户端的最终 ACK，删掉条目，连接转入 ESTABLISHED，同时挪进另一个队列，等 accept 来取。

listen 的 backlog 参数管的就是这些队列的容量。超出容量的客户端请求被直接拒绝——注意是内核拒绝，跟你 accept 的代码没关系。

为什么是三次而不是两次 #

两句话。

第一，服务端必须确认「客户端收到了我的 SYN K」。只发 SYN+ACK 就进 ESTABLISHED，服务端不知道自己的初始序列号有没有送达。客户端若不认 K，接下来按什么编号收数据就说不清。

第二，网络里有滞留的旧 SYN。一个早该失效的连接请求如果迟到了，服务端照样回 SYN+ACK 并分配资源。三次握手的第三步给了客户端一次否决的机会：收到不认识的 SYN+ACK，回一个 RST 就把这条幽灵连接拆了。

accept 与握手的关系 #

这一点必须说清，很多人在这里绕不过去。

三次握手由内核完成，跟 accept 没关系。即使应用层一次 accept 都没调，内核照样把三次握手走完，连接进入 ESTABLISHED 并挂进队列。

accept 干的事只有一件：从已完成队列里取一条记录，返回一个新的套接字描述符。

推论：

  • 应用 accept 慢、负载高，握手仍然能完成，只是队列会积压
  • 队列满了之后，新来的 SYN 会被丢弃或者被拒绝，客户端看到的是 connect 超时
  • 「连不上的问题」先查三处：网络不通、网卡超负荷、连接数已经打满

四次挥手 #

建连接三次，关连接四次。原因在 TCP 的半关闭（half-close）。

TCP 连接是全双工的，两个方向必须单独关闭。一方完成数据发送任务，就发一个 FIN 终止这个方向的连接。收到一个 FIN 只意味着这个方向没有数据流动了，这条连接仍然可以发送数据。

先关的一方执行主动关闭，另一方执行被动关闭。

步骤 方向 报文 动作
第一次 主动关闭方 → 被动方 FIN 应用调 close，表示数据发完了
第二次 被动方 → 主动方 ACK 确认号是收到的 FIN 序号加 1；内核给应用进程递一个 EOF
第三次 被动方 → 主动方 FIN 被动方处理完残留数据，也调 close
第四次 主动方 → 被动方 ACK 确认号是收到的 FIN 序号加 1，连接彻底终止

每个方向各有一个 FIN 和一个 ACK。

对应到应用进程的视角：

  1. 某个进程调 close 主动关闭，TCP 发出 FIN M
  2. 另一端收到 FIN M，执行被动关闭并确认。这个 FIN 的接收也作为文件结束符（EOF）递给应用进程，因为此后这条连接上再也收不到额外数据
  3. 过一段时间，收到 EOF 的进程调 close 关闭它的套接字，它的 TCP 发出 FIN N
  4. 原发送端对这个 FIN N 进行确认

为什么关闭要四次 #

服务端在 LISTEN 状态下收到 SYN 建连请求，可以把 ACK 和 SYN 放进一个报文发送——ACK 起应答作用，SYN 起同步作用，两件事同时成立。

关闭时不行。收到对方的 FIN，只表示对方没有数据发给你了，但你自己的数据未必发完了。你还有数据要发完，发完了才发 FIN 表示同意关闭。所以 ACK 和 FIN 多数情况下分开发送，多出一次往返。

TIME_WAIT 为什么等 2MSL #

双方都同意关闭、四个报文也收发完毕，按说可以直接回 CLOSED。实际不行。

网络是不可靠的，你无法保证最后发出的 ACK 一定被对方收到。对方停在 LAST_ACK 状态下等这个 ACK，等不到就超时重发 FIN。TIME_WAIT 就是为了补上那个丢失的 ACK。

2MSL 是两个最大报文生存时间，也就是「一个来回」。等够这个时间，要么对方的 FIN 早就到了，要么它重发的 FIN 已经在这条路上消失，端口可以安全复用。

副作用要知道：主动关闭的一方会短时间占着四元组。高并发短连接的服务端如果主动关闭，会堆出大量 TIME_WAIT，端口被吃光，connect 报 EADDRNOTAVAIL。缓解办法是让客户端主动关闭，或者调 tcp_tw_reuse，或者改用长连接。

可靠性靠什么 #

机制 干什么
序号 给每个字节编号，接收端能拼接、排序、去重
确认 ACK 告诉发送方「到第 N 个字节为止都收到了」，累计确认
超时重传 发出后起定时器，RTO 到期没收到 ACK 就重发
快速重传 收到三个重复 ACK 立刻重发，不等超时
滑动窗口 win 字段声明接收能力，一次能发多少不用等一个 ACK
流量控制 接收端窗口为 0 时发送方停发，等窗口更新通知
拥塞控制 慢启动、拥塞避免、快重传、快恢复，按网络状况调速率
校验和 覆盖伪首部、TCP 头、数据，错了丢弃等重传

这些机制都建立在「有连接」这个前提上。连接意味着两端各自维护一份状态：序列号、窗口、定时器、重传队列。状态一旦建立，后面所有可靠性手段才有地方放。

八、UDP 的无连接 #

没有握手 #

UDP 不建立连接。没有三次握手，没有 listen，没有 accept，也没有状态机。

socket 之后直接就能发。发出去之后 UDP 不留任何记录，不关心对方收没收到，也不等回应。

两个必须带地址的函数 #

UDP 用 sendto 代替 write，因为必须显式指定目标主机的地址结构体：

c
int sendto(int sockfd, void *buffer, size_t len, int flags,
           struct sockaddr *to, socklen_t tolen);

用 recvfrom 代替 read，顺便拿到数据包的发送方源地址：

c
int recvfrom(int sockfd, void *buffer, size_t len, int flags,
             struct sockaddr *from, socklen_t *fromlen);

为什么非要带地址？因为没有连接。UDP 套接字不绑定对端，一个套接字能收任何人的包，服务端只有从每个包里读出源地址，才知道回给谁。这也是 UDP 服务端能一个套接字服务所有客户端的原因。

消息边界 #

UDP 保留消息边界：一次 sendto 对应一次 recvfrom。

  • 发 100 字节，收就是 100 字节，不会多也不会少
  • 接收缓冲区比数据报小，多出的部分被丢掉，数据报本身不会拆开分两次给你
  • 发两个包，收的时候一定是两次，先后顺序不保证

TCP 完全相反。TCP 是字节流，没有边界：

  • 一次 send 的 100 字节，对端分成两次 recv 收到，60 加 40
  • 两次 send 的 50 字节，对端一次 recv 收满 100 字节
  • 对端 recv 一次读多少，取决于它给的缓冲区大小和当时内核里攒了多少

所以 TCP 上的应用必须自己分包：长度前缀、固定长度、分隔符，三选一。这是「TCP 是字节流」最直接的后果，也是新手最容易踩的坑——把 recv 的返回长度当成一条消息的长度。

两边的调用顺序 #

角色 调用链
TCP 服务端 socket → bind → listen → accept → recv/send → close
TCP 客户端 socket → bind（可省）→ connect → read/write → close
UDP 服务端 socket → bind → recvfrom/sendto → close
UDP 客户端 socket → sendto → recvfrom → close

两边一对比就看出差别：TCP 服务端多 listen 和 accept，客户端多 connect。UDP 一条链路都没有，收发顺序甚至可以反过来先发后收。

一次完整交互 #

UDP 服务端绑好地址，recvfrom 阻塞等着。来了一个包，peeraddr 和 peerlen 被填上对端地址，处理完调用 sendto 按这个地址回过去。

服务端只用一个套接字、一个端口，就能跟成百上千个客户端说话。这是广播、组播、发现协议的基础。

丢包与超时 #

UDP 没有超时重传。recvfrom 默认永久阻塞，对端不发你就一直挂着，什么也不会发生。

要给 UDP 加超时，有两条路：setsockopt 设 SO_RCVTIMEO（见《套接字选项》），或者用 alarm 加信号。

alarm 的机制：

  • 头文件 unistd.h，原型 unsigned alarm(unsigned seconds)
  • 到点后内核向当前进程发一个 SIGALRM 信号
  • alarm(0) 取消定时器
  • 一个进程同一时刻只能有一个活动的闹钟。再次调用 alarm 会覆盖前一次，并返回前一次剩余的秒数

这里有个陷阱。用 signal(SIGALRM, handler) 注册处理函数，在多数现代 Linux 发行版上，signal() 会给信号行为附上 SA_RESTART 标志。后果是：alarm(3) 到点触发 SIGALRM、执行完 handler 之后，内核自动重启被中断的阻塞系统调用（比如 recvfrom），让它接着阻塞。超时跳出完全失效。

要让阻塞函数真的超时返回，必须用 sigaction() 显式去掉 SA_RESTART。这样阻塞调用被信号打断时立刻返回 -1，errno 设为 EINTR。

c
void handle_alarm(int sig) {
    /* 什么都不用做，打断 recvfrom 就是目的 */
}

struct sigaction action;
sigaction(SIGALRM, NULL, &action);   /* 先取当前动作 */
action.sa_handler = handle_alarm;
action.sa_flags &= ~SA_RESTART;      /* 关键：清掉自动重启 */
sigaction(SIGALRM, &action, NULL);

alarm(3);
int n = recvfrom(sockfd, buf, sizeof(buf) - 1, 0,
                 (struct sockaddr *)&peeraddr, &peerlen);
if (n < 0 && errno == EINTR) {
    printf("recvfrom 3 秒超时\n");    /* 被信号打断，就是超时 */
    continue;
}
if (n >= 0) {
    alarm(0);                        /* 关键：收到数据立刻取消闹钟 */
    buf[n] = '\0';
}

最后那句 alarm(0) 别漏。收到数据不取消闹钟，后面在做耗时操作时闹钟突然响了，程序会被无端打断，errno 又被写成 EINTR，排查起来很难受。

九、一次通信的完整路径 #

把前面的东西串起来，走一遍真实过程。目标：从你在浏览器敲下 URL，到对面机器上那个进程拿到字节。

第一步：先找 IP #

应用层拿到域名，先解析。DNS 查询走 UDP 53 端口（大响应或者区域传送才走 TCP 53）。拿到目的 IP，三元组的第一维有了。

第二步：客户端封装 #

text
浏览器 ──HTTP 请求字节──► TLS ──密文──► TCP 段 ──► IP 包 ──► 以太网帧 ──► 网线
                                                    ▲
                                              查路由表决定从哪块网卡走、下一跳是谁
  1. 应用层组装 HTTP 请求，一串字节
  2. 传输层 socket() 拿到描述符，connect() 发出 SYN。内核从动态端口区挑一个，比如 52341
  3. 三元组填完：目的 (服务端 IP, TCP, 443)，源 (本机 IP, TCP, 52341)
  4. 网络层查路由表，确定出口网卡和下一跳
  5. 链路层用 ARP 查下一跳的 MAC。同网段直接问目标主机，跨网段问网关
  6. 物理层把帧变成信号发出去

第三步：中间设备怎么处理 #

  • 交换机：只看 MAC，按 MAC 地址表转发，不碰 IP 头
  • 路由器：剥掉旧的链路层头，看 IP 头查路由表，TTL 减 1，加上新的链路层头再发
  • NAT 网关：改源 IP 和源端口，回来时按映射表还原内网地址

NAT 这一步会破坏端到端假设。内网两台主机的四元组会撞车，出网后被端口映射区分开，回包再改回来。这是第三、四章说的「层间信息重复」在现实里的代价。

第四步：服务端解包 #

  1. 物理层还原帧，FCS 校验
  2. 链路层对 MAC，剥头，按 0x0800 交给 IP
  3. 网络层对 IP，剥头，按协议号 6 交给 TCP
  4. 传输层按目的端口 443 找到监听套接字
  5. 内核回 SYN+ACK，三次握手完成，连接进已完成队列
  6. accept() 取出连接，返回新套接字
  7. recv() 读到 HTTP 请求字节
  8. 应用层处理，send() 回响应，close() 或者保持长连接等下一个请求

一路上的寻址依据 #

层 靠什么找到对端 客户端填的值 服务端填的值
链路层 MAC 地址 下一跳（网关或目标主机）的 MAC 网关或客户端的 MAC
网络层 IP 地址 服务端 IP 客户端 IP
传输层 端口 52341（内核分配） 443（bind 指定）
应用层 域名与路径 Host: example.com、/index.html 按 Host 与路径路由到站点

每一层都在回答同一个问题：这个单元该交给谁。答案的粒度从机器缩到进程，从进程缩到具体资源。

别忘了这是双向的 #

上面列的只是「请求去」这一个方向。完整一次交互还有「响应回」的另一个方向，它有自己的序列号、自己的窗口、自己的 ACK。TCP 连接是全双工的，两个方向独立记账。

抓包时看到 seq 1:8 和 seq 1:19 两组不同的序号，就是这个原因——两个方向各自从 1 开始数。

十、常见概念辨析 #

socket 到底是什么 #

socket 起源于 Unix。Unix/Linux 的基本哲学之一是「一切皆文件」，都可以用「打开 open → 读写 write/read → 关闭 close」这个模式操作。socket 是这个模式的一个实现：它就是一种特殊的文件，socket 函数就是对它做打开、读写、关闭。

本质定位：socket 是应用层与 TCP/IP 协议族通信的中间软件抽象层，是一组接口。用设计模式的话说，它是一个门面（facade），把复杂的协议族藏在接口后面。对你来说，几个简单函数就是全部，剩下的交给 socket 去组织数据。

要说清一点：socket 没有层的概念。它不是协议栈里的一层，只是一个软件抽象层，让编程变简单。它站在应用层和传输层之间，替你把「填三元组、切段、加头」这些活接过去。

套接字的三个属性 #

一个套接字由三个属性唯一确定：

属性 取值 含义
域 Domain AF_UNIX / AF_LOCAL 本地文件系统域，协议层就是文件 I/O，地址是文件名，单机进程间通信用，效率高
AF_INET Internet 网络域，走 TCP/IP 协议栈跨网络通信
AF_INET6 IPv6 网络域
类型 Type SOCK_STREAM 流套接字，对应 TCP，有序、可靠、双向、面向连接的字节流
SOCK_DGRAM 数据报套接字，对应 UDP，无连接、不可靠、有最大长度限制、快
SOCK_RAW 原始套接字，自己拼 IP 头，抓包和自定义协议用
协议 Protocol IPPROTO_TCP / IPPROTO_UDP / 0 填 0 表示由系统按类型自动选默认协议

type 和 protocol 不能随意组合。SOCK_STREAM 配 IPPROTO_UDP 是错的，内核直接返回错误。protocol 填 0 是最省事的写法，让内核自己配。

域决定地址格式：AF_INET 用 32 位 IP 加 16 位端口的组合，AF_UNIX 用一个绝对路径名。这也是为什么 bind 的第二个参数是 struct sockaddr * 而不是具体结构体——它是通用地址类型，实际传的是 sockaddr_in 或 sockaddr_un 的指针，强转过去。

套接字描述符 #

就是一个整数。

最熟悉的三个句柄是 0、1、2：0 标准输入，1 标准输出，2 标准错误。它们是整数，对应的 FILE * 是 stdin、stdout、stderr。

套接字 API 最初作为 UNIX 操作系统的一部分开发，所以跟系统其他 I/O 设备集成在一起。应用程序要为一个因特网连接创建套接字时，操作系统返回一个小整数作为描述符来标识它。之后应用程序以这个描述符为参数，调函数完成操作，比如发送或者接收数据。

许多系统里套接字描述符和其他 I/O 描述符是集成在一起的，所以应用程序既可以做套接字 I/O，也可以对文件做读写，两者的调用形式一样。

实现上：系统为每个运行的进程维护一张文件描述符表。进程打开文件时，系统把指向该文件内部数据结构的指针写进表里，把表的索引值返回给调用者。应用程序只记住这个索引；内核拿索引访问表，通过指针找到保存全部文件信息的数据结构。

文件描述符与文件指针 #

对比项 文件描述符 文件指针
是什么 一个小的正整数 C 语言里的 I/O 句柄，FILE *
存在哪 进程 PCB 里的文件描述符表，是表的索引 进程用户区的 FILE 结构体
内容 表项指向已打开文件的数据结构 含一个缓冲区和文件描述符
关系 底层 句柄的句柄，FILE 里装着描述符
平台叫法 Linux 叫文件描述符 Windows 上描述符被称作文件句柄

FILE 结构里有缓冲区，这是关键差别：fwrite 先落进用户态缓冲区就返回，write 直接进内核。写网络程序时用错这一层，会出现「数据明明发了，抓包里没有」的情况。

监听套接字与连接套接字 #

对比项 监听套接字 连接套接字
谁创建 socket() 创建，listen() 之后生效 accept() 返回
数量 一个服务器只开一个 每个已建立的客户端连接一个
生命周期 服务器整个生命周期都在 服务完某个客户端就 close
用途 等新连接，不读写数据 真正收发数据
端口 占用 bind 的端口 复用监听套接字的同一个端口

为什么要分两种？一个原因是功能太多会让语义不直观：监听和读写混在一个描述符上，代码读起来费劲。另一个原因是内核确实产生了新的描述符。

一个容易错的点：连接套接字没有占用新端口，跟客户端通信时用的还是监听套接字的那个端口号。区分不同连接靠的是四元组，不是端口。所以 netstat 里会看到同一个本地端口后面挂着好几行，那是几条不同的连接。

accept 默认阻塞，直到有客户连接建立后才返回。参数 addr 和 addrlen 是结果参数，用来回填客户端地址，不关心就传 NULL。

收发的几组函数 #

同一件事，五组写法：

函数对 特点 什么时候用它
read / write 最通用，套接字和文件都能用 有连接的 TCP，不关心标志位
recv / send 多一个 flags 参数 要用 MSG_PEEK、MSG_WAITALL 这类标志
recvfrom / sendto 带地址结构 UDP，必须显式指定对端
readv / writev 一次读写多个缓冲区，分散/聚集 I/O 头和数据分在不同内存块，想一次发出去
recvmsg / sendmsg 最通用，msghdr 里能带地址和控制信息 要拿辅助数据，比如带外标记、包的本机目的地址

recvmsg/sendmsg 能力最全，前面几个都能用它们替掉。日常代码用 recv/send 就够，read/write 在套接字上和它们等价。

返回值必须分清：read 返回实际读到的字节数，返回 0 表示读到文件结束（对端关了），小于 0 表示出错。出错看 errno：EINTR 是被信号打断，ECONNRESET 是连接出了问题。write 成功返回写入字节数，失败返回 -1；EINTR 是写的时候被中断，EPIPE 是对端已经关闭连接。

端口、进程、套接字 #

三个东西的数量关系：

  • 一个进程可以有多个套接字（一个监听，若干连接）
  • 一个套接字绑定一个端口（connect 时由内核分配，或者 bind 显式指定）
  • 同一端口同一协议，同一时刻只能被一个套接字独占绑定（不加 SO_REUSEPORT）
  • 一个端口可以被不同协议的套接字同时占用：TCP 80 和 UDP 80 互不干扰

这三句连起来，就解释了大量「端口被占用」和「端口明明空着」的疑惑。

域名与服务名解析 #

程序里不写死 IP 和端口，靠网络信息数据库函数查：

函数 干什么
gethostbyname(const char *name) 传域名，返回 struct hostent *，含官方主机名、别名列表、IP 地址二进制列表 h_addr_list
inet_ntoa(struct in_addr in) 网络字节序的二进制 IP 转点分十进制字符串
gethostname(char *name, size_t len) 取本机主机名
getservbyname(const char *name, const char *proto) 传 "http"、"tcp"，查出 80 端口，用符号名代替死数字

这几个函数按值来说够用，但都有硬伤：gethostbyname 不支持 IPv6，返回的是静态缓冲区地址，多线程下两个线程的结果会互相覆盖。新代码用 getaddrinfo，它的签名和用法在《套接字与字节序》里。

多路复用归到哪一类 #

select 让单进程同时监控多个文件描述符的状态。没有任何描述符处于活跃就绪状态时，进程安全地进入阻塞，不做忙等待，CPU 开销很低。

它解决的问题是「一个线程怎么伺候多个连接」，属于 IO 模型那一组的知识，展开在《IO 模型》。在这里只需要记住：它跟三元组没关系，跟套接字的数量有关系。

十一、易错点速查 #

现象 原因 怎么改
端口和 IP 都对，别的主机连不进来 服务只 bind 了 127.0.0.1，只有回环网卡收包 绑 INADDR_ANY
accept 还没调，客户端已经是 ESTABLISHED 握手由内核完成，跟 accept 无关 这不是 bug，去查队列长度
一次 recv 读不到一条完整消息 TCP 是字节流，没有消息边界 自己做长度前缀或分隔符
两次 send 变成一次 recv 同上，内核合并了字节 不要依赖 send 的次数划分消息
绑定 3366 端口，netstat 里显示 9741 没调 htons。3366 是 0x0d26，小端机上被解析成 0x260d，即 9741 端口用 htons，IP 用 htonl
UDP 发大包，对端什么也收不到 IP 层分片，丢一片整包作废 单包控制在 MTU 以内
UDP 客户端起第二个实例就 EADDRINUSE 手动 bind 了固定端口 客户端不 bind，让内核分配
服务端堆满 TIME_WAIT，connect 报 EADDRNOTAVAIL 服务端主动关闭，主动方要等 2MSL 改由客户端主动关，或者用长连接
close 之后连接还在 close 只是引用计数减 1，计数为 0 才发 FIN 查有没有 dup 或 fork 复制导致计数不为 0
connect 一直超时，不是 connection refused 包被防火墙或安全组丢了，没有 RST 回来 抓包看有没有 SYN 出去、有没有回包
断连时收到 RST 而不是 FIN 强制切断，关闭时仍有数据未被处理 查对端应用是否异常退出、是否被反作弊或网关踢掉
gethostbyname 在多线程里结果被覆盖 返回静态缓冲区，不可重入 换 getaddrinfo
抓包里大量 length 0 的 [.] 包 纯 ACK，不带数据 正常流量，别当成异常
accept 返回的套接字端口和监听端口一样 连接套接字复用监听端口 正常，区分连接靠四元组

这份清单按两类问题排。前半段多是「定位不到进程」，查三元组；从 recv 分包往下，多是「数据形态搞错」，查你面对的是字节流还是数据报。

定位不到，就一层层看三元组哪一维错了。数据不对，就回头想清楚封装和解包的边界在哪。这两条查完，八成的问题自己就露出来了。
