这一篇只讲一件事：一台 Linux 机器连不上网、连不上别的机器、或者别人连不上它，你打开终端该敲什么，敲完怎么看输出，看完往哪一步走。

命令范围就是排错桌上那一排：ip 全家（ip link、ip addr、ip route、ip neigh）、ss、ping、traceroute/mtr、tcpdump、dig/nslookup、nc、curl，外加 ifconfig、route、netstat、arp、lsof、telnet 这些老面孔。老命令已废弃，可它们还活在无数台老机器和无数篇老文档里，你迟早得读懂。

不讲的东西也划清楚：报文的逐字节格式、各层头部的字段布局，在《协议分析与报文格式》里；套接字 API 的进阶用法、多路复用的实现，在《网络编程进阶专题》里。本篇只盯「命令 → 输出 → 下一步」这条链，不碰代码。

一句话定位：排错不是凭感觉试，是按固定顺序逐层排除。顺序错了，敲一百条命令也是白敲。

一、排错从哪下手 #

排错的顺序是自下而上，一步都不能跳。

先看接口起没起（link），再看有没有 IP（addr），再看路由通不通（route），然后测连通（ping），最后看端口与连接（ss）。这五步是一条链，前一步不成立，后一步的结论就不作数。

为什么必须这个顺序？因为下面几层的故障会把上面几层的现象全部污染。链路是 DOWN 的，你 ping 网关得到 100% 丢包，这结论毫无信息量——它只说明链路不通，不说明网关有问题。路由表里没有默认路由，你 dig www.example.com 超时，这也不能怪 DNS，包根本没出门。

跳过底层直接查应用层，是无头苍蝇。新手最典型的动作是「网站打不开，先重装浏览器」；运维最典型的动作是「服务连不上，先 curl 十遍」。十遍输出一模一样，因为你没有换变量。

按层排，每一层只回答一个问题：

顺序 层次 要回答的问题 主力命令 不通时的典型输出
1 链路层 网卡起来了吗？有载波吗？ ip link、ip -s link state DOWN、NO-CARRIER、errors 计数在涨
2 网络层（本机） 本机有 IP 吗？掩码对吗？ ip addr、ip -br addr 只有 lo，或地址是 169.254.x.x
3 网络层（转发） 出门的路由有吗？下一跳是谁？ ip route、ip route get 没有 default，或 default 指向不存在的网关
4 链路层（邻接） 网关的 MAC 拿到了吗？ ip neigh、arp -a FAILED、INCOMPLETE
5 网络层（连通） 到对端通不通？丢多少？ ping、nc -zv 100% loss，或只丢一部分
6 传输层 端口在听吗？连接建起来了吗？ ss -lntp、ss -tanp 没有监听行，或一堆 SYN-SENT
7 应用层 协议对话对不对？ curl -v、dig、tcpdump 400/502，或 DNS 返回空

这张表是整篇的目录骨架，后面每一章对应其中一行。

分层模型为什么值得先记住 #

网络体系结构指的是网络的分层结构，以及每层使用的协议集合。最有名的是 OSI 参考模型，基于国际标准化组织（ISO）的建议发展起来，分七层：应用层、表示层、会话层、传输层、网络层、数据链路层、物理层。这七层规定得很细很全，实际中没被广泛使用，主要原因之一是它过于复杂。它仍然是此后很多协议模型的基础，TCP/IP 模型就是把它简化成四层，换取实现成本和通信效率。

OSI 七层 TCP/IP 四层 这一层坏了，现象是什么 拿什么查
应用层、表示层、会话层 应用层 能连上，返回码不对，内容乱码 curl -v、dig、看服务日志
传输层 传输层 端口不通，连接建不起来，半开一堆 ss、nc -zv、tcpdump 看握手
网络层 网络层 本机通、跨网段不通，TTL 到期 ip route、ping、traceroute
数据链路层、物理层 网络接口层 完全不通，连网关都摸不到 ip link、ip -s link、ip neigh

排错时你只需要记住一件事：每条命令都工作在某一层上，输出也只对那一层有解释力。用 dig 去判断网线插没插，是用错了工具。

四层各自管什么 #

网络接口层是 TCP/IP 的最底层，把二进制流转化成数据帧，并负责帧的收发。帧是网络传输的基本单元。

网络层负责在主机之间选择数据包的传输路径，也就是路由。它收到传输层的请求后，传输某个带目的地址信息的分组，把分组封装进 IP 数据包，填好首部，用路由算法判断是直接交付还是交给路由器，最后把包交给合适的网络接口发出去。它还要处理进来的包：校验合法性，用路由算法决定本地处理还是转发。目的机在本网段时，剥掉首部，选合适的传输层协议往上交。需要时它还负责收发 ICMP 差错与控制报文——ping 和 traceroute 吃的就是这碗饭。

传输层负责应用程序之间的通信服务，也就是端到端通信。它管理信息流动，提供可靠传输，保证数据到达时无差错、无乱序。为此双方要协商：接收方回送确认，发送方重发丢失的分组。传输层把数据流切成分组，连同目的地址交给网络层。

应用层是最高层。应用程序用相应的应用层协议，把封装好的数据交给传输层，或者从传输层收数据来处理。

TCP 与 UDP 的差别，决定了你查什么 #

TCP 向应用层提供可靠的、面向连接的数据流传输服务，保证数据无误、无丢失、无失序、无重复到达。源/目的 IP 唯一区分网络中两台设备，源/目的端口唯一区分两个通信的应用程序——这四个元素就是一条连接的身份。

TCP 会话靠三次握手初始化，目标是让收发双方的序号同步，同时告诉对端自己一次能收多少数据（窗口大小），建立逻辑连接：

  1. 源主机发一个 SYN 置 1 的段，同时带上初始序号 ISN。ISN 是随时间变化的随机值。
  2. 目标主机回一个段，SYN 与 ACK 都置 1，确认序号字段里填自己期待收到的下一个序号（表示前一段已收到且无错），同时带上自己的初始序号。
  3. 源主机再回一个段，带递增的发送序号与确认序号。

到这一步握手完成，双方可以互发数据。这个三段过程在 tcpdump 里就是 [S]、[S.]、[.] 三个包；在 ss 里就是 SYN-SENT 到 ESTAB 的状态迁移。

UDP 是面向无连接的不可靠传输协议，资源消耗少、处理速度快。适用场合有两类：发送小尺寸数据，比如向 DNS 服务器查 IP 地址；流媒体这类网络多媒体服务做实时传输。

差别落到排错上：TCP 不通，你能看到明确的状态机痕迹（SYN 发出没人应、连接被 RST）；UDP 不通，你什么都看不到，只能靠 tcpdump 抓包确认包到底发出去没有。查 UDP 服务，别指望 ss 给你连接状态——UDP 无连接，ss 里只有 UNCONN 的本地端口。

三个动作，循环使用 #

排错不是一次性的判断，是三动作循环：看状态（ip、ss、ip neigh，零成本、无副作用，先做）、测连通（ping、nc -zv、curl，有流量但很轻）、抓包（tcpdump，成本最高，结论最硬）。

前两步给出假设，第三步验证假设。ping 不通但你怀疑 ICMP 被防火墙拦了，就去抓包看 SYN 出去没有、回没回来；ss 显示端口在听但客户端连不上，就去抓包看 SYN 到没到网卡。

二、看接口：ip 与 ifconfig #

第一步永远是 ip link。它回答的是「这块网卡在内核眼里存不存在、管理状态是开还是关、物理层有没有信号」。

bash
ip link
ip link show eth0
ip -br link
ip -s link

完整输出形如：

text
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP mode DEFAULT group default qlen 1000
    link/ether 52:54:00:8f:3a:11 brd ff:ff:ff:ff:ff:ff

一行里有五个信息块，逐个拆开看。

尖括号里那串 flag #

<BROADCAST,MULTICAST,UP,LOWER_UP> 是接口标志位，逗号分隔，全大写表示已置位。

标志 含义 排错意义
UP 管理状态已开启 没这个，接口被 ip link set down 了
LOWER_UP 物理层有载波，链路层可达 没这个，网线没插、对端没开、虚拟交换机没接
BROADCAST 支持广播 缺它，ARP 和 DHCP 都别想工作
MULTICAST 支持多播 缺它，多播路由、mDNS 会挂
LOOPBACK 回环接口 只有 lo 有
PROMISC 混杂模式 抓包时临时开，长期开着是隐患
NOARP 不用 ARP 隧道类接口常见，别拿它跟以太网比

关键是分清 UP 和 LOWER_UP。这两个字常常一起出现，含义完全不同。

UP 是管理状态：你敲 ip link set eth0 up，它就出现。LOWER_UP 是物理状态：内核从驱动那里得知链路上有信号，它才出现。

于是有三种组合，对应三种故障定位：

现象 管理状态 物理状态 说明 往哪查
<UP,LOWER_UP> 开 有信号 正常 继续看地址与路由
<UP> 无 LOWER_UP 开 无信号 接口开着，链路上没东西 网线、对端交换机端口、光模块、虚拟机的网络配置
无 UP 关 无意义 接口被禁用 ip link set eth0 up

第二种是硬件或虚拟化层面的事，软件层做什么都没用。ifconfig 里对应的标志叫 RUNNING，它跟 LOWER_UP 是同源的。

state 字段是 ip link 单独给出的运营状态：UP、DOWN、UNKNOWN、DORMANT。UNKNOWN 在隧道和点对点接口上很常见，不代表故障，别被它骗。

MTU 与 qdisc #

mtu 1500 是以太网的标准值，指接口一次能发出去的最大载荷。qdisc 是排队规则，fq_codel、pfifo_fast、noqueue 都会出现——lo 就是 noqueue。qlen 1000 是发送队列长度。

MTU 只在一种场景下需要你动手：隧道、VPN、VXLAN 叠加时，封装会撑大包，实际可用 MTU 变小，大包发不出去，现象是「小请求正常、大请求卡死」或者「SSH 登录成功但一传文件就断」。这类问题在应用层查一辈子也查不出来。改法是 ip link set eth0 mtu 1400，立刻生效；要固化得写配置文件，那属于发行版的事。

ip -s link 看错误计数 #

ip -s link show eth0 的输出分 RX、TX 两组，每组都是 bytes packets errors dropped overrun mcast。你要盯的是后四个：

字段 含义 涨了说明什么
errors 收/发失败的包数 物理层质量问题，网线、光衰、双工不匹配
dropped 被丢弃的包数 队列满了，或者有 tc 规则在丢
overrun 来不及处理的包数 网卡缓冲区溢出，中断处理跟不上
mcast 多播包数 只在 RX 出现，量大说明网段里多播太吵

errors 和 dropped 一直在涨，就是硬件或内核层面的问题，上面几层怎么调都没用。这两个计数适合在两个时间点各取一次，做差看增量——单次读取的绝对值没法解释。ifconfig 里也有同类信息，字段名叫 RX packets、RX errors、RX dropped、RX overruns、frame、collisions。

临时改接口状态 #

bash
ip link set eth0 down
ip link set eth0 up
ip link set eth0 promisc on      # 抓包用，抓完记得关
ip link set eth0 name lan0       # 改名，接口必须先 down

网卡名不再是清一色的 eth0：lo 是回环；eth0 是老系统与容器里的传统命名；ens33、enp0s3 按固件与 PCI 槽位排序；wlan0、wlp2s0 是无线；docker0、br-xxxx、vethxxxx 是虚拟设备；tun0、wg0 是隧道与 VPN。别死记 eth0，很多脚本的 bug 就出在写死了这个名字。

down 不会清掉这个接口上的 IP 地址，地址还在配置里，但接口不可用，路由随之失效。这一点跟「删地址」不是一回事，别把 down 当清理手段。promisc on 让网卡收所有经过它的帧，tcpdump 会自动开关，长期开着多耗 CPU，也会被安全审计盯上。

ifconfig：能看，但别用来改 #

ifconfig 属于 net-tools 包，在多数新发行版里默认根本不装。敲 ifconfig 或 ifconfig eth0，输出形如：

text
eth0: flags=4163<UP,BROADCAST,RUNNING,MULTICAST>  mtu 1500
        inet 192.168.1.10  netmask 255.255.255.0  broadcast 192.168.1.255
        ether 52:54:00:8f:3a:11  txqueuelen 1000  (Ethernet)
        RX packets 128374  bytes 94213380 (89.8 MiB)
        RX errors 0  dropped 0  overruns 0  frame 0

字段对照：

字段 对应 ip 的什么 解读
flags=4163<UP,BROADCAST,RUNNING,MULTICAST> flag 串 数字是位掩码，看尖括号里的名字就够
inet / netmask / broadcast inet 192.168.1.10/24 brd ... 掩码以点分十进制写，ip 用前缀长度
ether link/ether MAC 地址
RX/TX packets ip -s link 的对应行 收发计数
collisions 无 冲突计数，全双工下应恒为 0

三个 ifconfig 干不了的事，正好是排错最需要的三件事：

  1. 看不到 secondary 地址。一块网卡配了多个 IP，ifconfig 老版本只显示主地址，附加地址要加 eth0:1 这种别名才看得见。用 ip addr 一次全列。
  2. 不支持多路由表。route 命令只认 main 表，策略路由配了一堆表它一无所知。
  3. 没有状态机信息。接口的 DORMANT、UNKNOWN 这些状态，它不显示。

所以要改配置，一律用 ip。要读老文档、看老截图、在老机器上救急，ifconfig 还得会看。

接口层的收尾动作 #

接口这一层查到 UP 且 LOWER_UP，并且 errors/dropped 不涨，就可以往上走。走之前顺手确认接口名：后面所有命令都要带 -i 接口名，名字写错，tcpdump 会直接报 No such device exists；而 ping 走的是路由表选的接口，未必跟你想的是同一个。先把名字钉死，能省掉一轮误判。

三、看地址与掩码 #

接口起来了，下一步看它有没有 IP、掩码是多少。命令是 ip addr。

bash
ip addr
ip addr show eth0
ip -br addr

完整输出形如：

text
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP group default qlen 1000
    link/ether 52:54:00:8f:3a:11 brd ff:ff:ff:ff:ff:ff
    inet 192.168.1.10/24 brd 192.168.1.255 scope global dynamic eth0
       valid_lft 86132sec preferred_lft 86132sec
    inet6 fe80::5054:ff:fe8f:3a11/64 scope link
       valid_lft forever preferred_lft forever

ip -br addr 是精简版，一行一个接口，适合快速扫：

text
lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0             UP             192.168.1.10/24 fe80::5054:ff:fe8f:3a11/64

inet 那一行的每个字段都有话要说：

字段 含义 排错时的用途
inet 192.168.1.10/24 IPv4 地址加前缀长度 前缀长度就是掩码，/24 即 255.255.255.0
brd 192.168.1.255 广播地址 主机位全 1，发包给全网段用
scope global 作用域，全球可路由 link 只在本地链路可达，host 只在本机可用
dynamic 由 DHCP 等协议动态分配 出现它说明地址是租来的，机器重启会变
valid_lft 86132sec 租约剩余生命期 数字在倒数，说明 DHCP 续约正常
secondary 附加地址 一块网卡上的第二个及以后的 IP
eth0 绑定到哪个接口 多网卡机器上，这一项决定你查的是不是对的那块

看 IP 有没有，先看 lo 之外的接口有没有 inet。只有回环有地址，说明这块网卡没配地址，或者 DHCP 没拿到。

拿到 169.254.x.x 开头（IPv4 链路本地地址段 169.254.0.0/16）的地址，是 DHCP 失败的信号——系统自己编了一个，只能跟同一链路上同样自编了地址的机器说话，出不了网段。看到这个直接去查 DHCP 服务器和 dhclient/networkd 的日志。

前缀长度与掩码 #

/24 这种写法叫 CIDR 前缀，数字是网络位的个数。它和点分十进制掩码是同一件事的两种写法。

前缀 掩码 每个网段可用主机数 常见场合
/8 255.0.0.0 16777214 A 类默认掩码
/16 255.255.0.0 65534 B 类默认掩码
/24 255.255.255.0 254 C 类默认掩码，家用与办公网最常见
/25 255.255.255.128 126 大网段对半切
/30 255.255.255.252 2 点对点链路
/31 255.255.255.254 2（RFC 3021 点对点特例） 路由器互联
/32 255.255.255.255 1 单主机路由、环回

可用主机数总是「主机位能表示的总数减 2」：一个给网络地址（主机位全 0），一个给广播地址（主机位全 1）。/24 是 256 减 2 得 254。

掩码配错是本机最容易犯的错。地址 192.168.1.10 配成 /16，这台机器会认为整个 192.168.0.0/16 都在本地链路上，于是它不去找网关，直接对 192.168.2.x 发 ARP。ARP 没有应答，现象就是「同一台交换机上的机器都 ping 不通」。这类故障查路由表查不出来，因为路由表是照着错的掩码算出来的。

一块网卡配多个地址 #

bash
ip addr add 192.168.1.20/24 dev eth0
ip addr add 192.168.1.21/24 dev eth0 label eth0:1
ip addr del 192.168.1.21/24 dev eth0
ip addr flush dev eth0

第二条 ip addr show eth0 就能看到两个 inet，第二个带 secondary 标记。第三个地址再加，ip addr 照样全列。

secondary 标记有一个副作用要留意：内核对附加地址的源地址选择有偏好，同一网段有多个地址时，出包不一定用你以为的那个。判断实际用哪个源地址，用 ip route get，它在输出里直接告诉你 src。ifconfig 在这一项上是残的：它默认只显示主地址，附加地址要配成 eth0:1 这种别名标签才看得见，而 ip addr add 加的地址不带标签也不影响使用。这就是「ip 取代 ifconfig」的头号理由。

ip addr add 不加 label 也能用，加了标签的老习惯来自 ifconfig eth0:1 时代。加不加，ip addr 都看得见。

ip addr flush dev eth0 会一次性清掉这个接口上的所有地址，包括 IPv6。这条命令没有确认提示，敲完就生效。远程连着的机器上执行它，等于自己把自己踢下线。别在 SSH 会话里试。

IP 地址是什么 #

IP 地址是 IP 协议提供的统一地址格式，给互联网上每个网络、每台主机分配一个逻辑地址，用来屏蔽物理地址的差异。物理地址（MAC）烧在网卡上，跟着硬件走；IP 地址是逻辑的，跟着网络位置走。一台机器换个网段就要换 IP，MAC 不用换。

地址分两类用途：

  • 公有地址。由 Inter NIC（Internet Network Information Center，因特网信息中心）负责分配。这些地址分配给注册并提出申请的组织机构，通过它直接访问因特网。
  • 私有地址。非注册地址，专门给组织机构内部使用，不出现在公网上。

留用的内部私有地址就三段：

类别 私有地址范围 前缀写法 容量
A 类 10.0.0.0 - 10.255.255.255 10.0.0.0/8 1600 多万个
B 类 172.16.0.0 - 172.31.255.255 172.16.0.0/12 100 多万个
C 类 192.168.0.0 - 192.168.255.255 192.168.0.0/16 6 万多个

私有地址出公网要靠 NAT 转换。排错时这条最实用：看到 192.168.x.x、10.x.x.x、172.16~31.x.x，就知道这是内网地址，跨公网不通不是故障，是设计如此。

分类地址：历史定义 #

早期设计互联网时，为了便于寻址和层次化构造网络，每个 IP 地址包含两个标识码：网络 ID 和主机 ID。同一个物理网络上的所有主机使用同一个网络 ID，网上的每台主机（工作站、服务器、路由器）有一个主机 ID 与之对应。Internet 委员会定义了五类地址适应不同容量的网络，即 A 类到 E 类。其中 A、B、C 三类由 Internet NIC 在全球范围内统一分配，D、E 类为特殊地址。

类别 最大网络数 地址范围 最大主机数 私有地址范围 默认掩码
A 126（2^7-2） 0.0.0.0 - 127.255.255.255 16777214 10.0.0.0 - 10.255.255.255 255.0.0.0
B 16384（2^14） 128.0.0.0 - 191.255.255.255 65534 172.16.0.0 - 172.31.255.255 255.255.0.0
C 2097152（2^21） 192.0.0.0 - 223.255.255.255 254 192.168.0.0 - 192.168.255.255 255.255.255.0
D 多播 224.0.0.0 - 239.255.255.255 无 无 无
E 保留实验 240.0.0.0 - 255.255.255.255 无 无 无

A 类：四段号码里第一段是网络号，后三段是本地主机号。二进制表示下，A 类由 1 字节网络地址和 3 字节主机地址组成，网络地址最高位必须是 0。网络标识长度 8 位，主机标识长度 24 位。A 类网络数量少，只有 126 个，每个网络能容纳主机 1600 多万台。地址范围 1.0.0.0 到 127.255.255.255，二进制从 00000001 00000000 00000000 00000000 到 01111110 11111111 11111111 11111111，最后一个是广播地址。子网掩码 255.0.0.0，最大主机数 256 的 3 次方减 2，即 16777214。

B 类：前两段是网络号。二进制下由 2 字节网络地址和 2 字节主机地址组成，网络地址最高位必须是 10。网络标识 16 位，主机标识 16 位，适合中等规模网络，有 16384 个网络，每个网络容纳 6 万多台。范围 128.0.0.0 到 191.255.255.255，二进制从 10000000 00000000 00000000 00000000 到 10111111 11111111 11111111 11111111，最后一个是广播地址。子网掩码 255.255.0.0，最大主机数 256 的 2 次方减 2，即 65534。

C 类：前三段是网络号。二进制下由 3 字节网络地址和 1 字节主机地址组成，网络地址最高位必须是 110。网络标识 24 位，主机标识 8 位，网络数量多，有 209 万余个，适合小规模局域网，每个网络最多 254 台。范围 192.0.0.0 到 223.255.255.255，二进制从 11000000 00000000 00000000 00000000 到 11011111 11111111 11111111 11111111。子网掩码 255.255.255.0，最大主机数 256 减 2 得 254。

这套分类办法叫分类寻址，是历史产物。现在配地址一律写前缀长度，路由按最长前缀匹配，分类边界早就不参与计算了。

有两段要单独记住，它们不在上表的「可用主机」之列：

  • 127.0.0.0/8 整段留给回环。127.0.0.1 是本机，ping 127.0.0.1 通只证明内核的 TCP/IP 协议栈活着，不证明网卡正常，也不证明网线插着。
  • 169.254.0.0/16 是链路本地地址，DHCP 拿不到租约时自动生成，只在本地链路可达。

本机地址这一层的判据 #

走到这里，你手里有三条结论：接口 UP + LOWER_UP，地址不是 169.254.x.x，掩码和同网段别的机器一致。三条都成立，才能往上走。

ip addr 之外还有一份配置要看：/etc/hosts 与 /etc/resolv.conf。那不是本机地址，是名字解析，留到第十章。

四、看路由表 #

地址有了，包要出门得知道往哪走。这一步看路由表。

bash
ip route
ip route show
ip route show table main
ip -4 route

输出形如：

text
default via 192.168.1.1 dev eth0 proto dhcp src 192.168.1.10 metric 100
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.10
172.17.0.0/16 dev docker0 proto kernel scope link src 172.17.0.1 linkdown

每一列都是一个判据：

列 含义 怎么读
default 默认路由，目的写成 0.0.0.0/0 没有它，出网段的包无处可去
via 192.168.1.1 下一跳地址 这个地址必须本网段可达，否则先把邻接修好
dev eth0 从哪个接口发 接口 DOWN，这条路由就失效
proto kernel 路由来源 kernel 是自动生成，dhcp 来自 DHCP，static 是手工加，boot 来自内核启动参数
scope link 作用域 目的地址就在本地链路上，直接 ARP，不经过路由器
src 192.168.1.10 源地址选择结果 出包用哪个 IP 当源，这一项说了算
metric 100 优先级度量 同一目的前缀有多条时，数字小的优先
linkdown 接口已不可用 这条路由挂着但发不出去，Docker 停机后常见

default 那行是重点。整张表里它排第一，不是因为它重要，是因为排序规则。真正的选路规则是最长前缀匹配：目的地址同时匹配多条路由时，选前缀最长的那条。所以 192.168.1.0/24 永远赢过 default，哪怕 default 写在前面。

proto kernel 那条 192.168.1.0/24 ... scope link src 192.168.1.10 不需要你手工加。系统给接口配上 192.168.1.10/24，内核自动生成这条直连路由。这也是为什么掩码配错会连环出错——掩码决定直连路由覆盖多大范围。

ip route get：问内核它会怎么走 #

路由表是一堆规则，人脑算容易错。直接问内核：

bash
ip route get 8.8.8.8
ip route get 192.168.1.50
ip route get 1.1.1.1 from 192.168.1.10

输出形如：

text
8.8.8.8 via 192.168.1.1 dev eth0 src 192.168.1.10 uid 0

这条命令不发送任何包，只做一次查表，把内核的选择结果打出来。四个值都有用：走哪条路（via）、从哪个接口（dev）、用哪个源地址（src）、按哪个用户的策略（uid）。

判断「本机到底从哪块网卡出去」「源地址是哪一个」这类问题，ip route get 比读路由表快十倍，也不会读错。多网卡、多 IP、配了策略路由的机器上，它是第一选择。

多路由表与策略路由 #

ip route 默认只显示 main 表。系统里不止一张表：

bash
ip route show table all
ip rule show
cat /etc/iproute2/rt_tables
ip route show table 100
ip route add 10.8.0.0/24 via 192.168.1.1 table 100
ip rule add from 192.168.1.20 lookup 100

ip rule show 输出形如：

text
0:      from all lookup local
32766:  from all lookup main
32767:  from all lookup default

查表顺序按优先级数字从小到大。local 表管本机地址，main 表是你日常看到的那张，default 表是空的。

这条链解释了一类诡异故障：ip route 里明明有默认路由，ping 却不通。原因是 ip rule 里插了更高优先级的规则，把包导到了一张空表。VPN 客户端装完常常干这事——它插一条 from all lookup 220，你不看 ip rule 就永远想不通。

route 这条老命令只能操作 main 表，敲 route -n 输出形如：

text
Kernel IP routing table
Destination     Gateway         Genmask         Flags Metric Ref    Use Iface
0.0.0.0         192.168.1.1     0.0.0.0         UG    100    0        0 eth0
192.168.1.0     0.0.0.0         255.255.255.0   U     100    0        0 eth0

字段对照：

列 含义 说明
Destination / Genmask 目的网络与掩码 两个都是 0.0.0.0 就是默认路由
Gateway 网关 0.0.0.0 表示直连，不用网关
Flags 标志位 U 可用，G 走网关，H 单主机，! 拒绝
Metric 度量 数字小的优先
Iface 接口 从哪块网卡发

Flags 里的 ! 要留意，它表示拒绝路由，包会被丢掉并回一个不可达。-n 不能省，不加它会尝试反解主机名，DNS 不通时命令会卡住十几秒。route add/route del 也能改，可它只认 main 表，改不了策略路由——多路由表这件事上它完全无能为力，这就是「ip 取代 route」的核心原因。

临时改路由 #

bash
ip route add 10.8.0.0/24 via 192.168.1.254
ip route replace default via 192.168.1.1
ip route del default
ip route add blackhole 10.9.9.0/24

add 加一条，del 删一条，replace 有则改无则加。blackhole 是丢弃路由，包进来直接扔、不回报文，适合临时屏蔽一个网段。这些改动重启就没了，要持久化得写发行版自己的配置。

双默认路由是常见坑。两条 default、metric 一样，内核按加表顺序选，行为不稳定，表现是「有时能上有时不能」。看到两条 default，先删掉多余那条。

路由这一层的判据 #

三条：有 default，via 指向的网关在本网段可达，dev 指的接口是 UP。三缺一，往上查都是浪费——没有 default，包连门都出不了；网关不在本网段，包会先去 ARP 一个根本不存在的邻居；接口 DOWN，路由表里那条会被标成 linkdown。

网关在不在本网段，用掩码算一下就清楚：192.168.1.1 配 /24 掩码，网络是 192.168.1.0，它落在里面，可达。网关写成 10.0.0.1 而本机是 192.168.1.10/24，这条路由压根加不进去，ip route add 会直接报 Nexthop has invalid gateway。

五、看 ARP 表 #

路由表告诉你下一跳的 IP，但在以太网上发帧靠的是 MAC。从 IP 到 MAC 这一步，是 ARP。表里的每一行就是一次「IP 到 MAC」的缓存。

bash
ip neigh
ip neigh show dev eth0
ip -s neigh

输出形如：

text
192.168.1.1 dev eth0 lladdr aa:bb:cc:dd:ee:01 REACHABLE
192.168.1.50 dev eth0 lladdr aa:bb:cc:dd:ee:32 STALE
192.168.1.77 dev eth0  FAILED

三列关键信息：邻居 IP、接口、MAC，末尾是状态。

状态 含义 判断
REACHABLE 近期确认过可达 正常
STALE 缓存可用但未复验 正常，用的时候会复验
DELAY 已发包，等确认 短暂过渡态
PROBE 正在发 ARP 探测 短暂过渡态
FAILED 解析失败 二层不通，或对端不响应 ARP
INCOMPLETE 请求发出，没有应答 正在失败的路上
PERMANENT 静态表项，永不过期 手工配的，别乱删
NOARP 该接口不做 ARP 隧道类接口

FAILED 和 INCOMPLETE 是信号。网关那一行是 FAILED，说明本机连网关的 MAC 都拿不到——问题在二层，不在路由，也不在网关后面的世界。查交换机的那个口、查 VLAN、查是否有人开了端口安全。

老命令是 arp -a，输出格式不同，信息一样：

text
? (192.168.1.1) at aa:bb:cc:dd:ee:01 [ether] on eth0

ip neigh 有一个 arp -a 没有的能力：它能显示 FAILED 状态的失败项，而 arp -a 只列已经解析成功的。排错时这一项很关键——「表里没有网关」和「网关解析失败」是两回事，前者只是缓存过期，后者是明确的故障。

清理表项用 ip neigh del 192.168.1.1 dev eth0，或者 ip neigh flush dev eth0 清掉整张表。换过网关、迁移过虚拟机之后，旧表项会让流量打到错的 MAC 上，清一下就能好。ARP 欺骗的现场也在这里看：同一个 MAC 对应多个 IP，或者网关的 MAC 与已知值不符，都是被劫持的迹象。

六、看连接与端口 #

前五步都在查「包能不能出去」。这一步开始查「谁在听、谁连着」。

到这一层，先回答一个选择题：用 ss 还是 netstat。

ss 取代 netstat 的理由 #

netstat 属于 net-tools 包，已经多年不更新，在多数新发行版里默认不装。ss 属于 iproute2 包，跟 ip 命令同一个来源，系统装了 ip 就有 ss。

差别不只是「新旧」：

维度 netstat ss
所属软件包 net-tools（多年未更新） iproute2（与 ip 同源，活跃维护）
取数方式 读 /proc/net/*，连接多时慢 走 netlink 直接问内核
连接数上万时 明显卡顿 依旧很快
定时器信息 没有 -o 可看重传、保活定时器
TCP 内部状态 没有 -i 可看 rtt、cwnd、拥塞算法
过滤语法 只能靠 grep 内置 state、dport、sport 过滤

新系统一律优先 ss。只有一种情况必须回到 netstat：机器太老，ss 不存在。那时候先 netstat 顶着，能装 iproute2 就装上。

ss 的常用组合 #

bash
ss -lntp              # 看 TCP 监听端口和进程
ss -tanp              # 看全部 TCP 连接
ss -uanp              # 看 UDP
ss -s                 # 按协议汇总计数
ss -ti                # 看 TCP 内部信息，rtt 与拥塞窗口
ss -o state established
ss -tn dport = :443

参数拆开记：-t 只 TCP，-u 只 UDP，-l 只看监听，-a 全都要（监听加非监听），-n 不做名字反解，-p 显示进程，-i 内部信息，-o 定时器，-s 汇总。

-n 必须加。不加它会把地址反解成主机名、把端口反解成服务名，DNS 一慢，命令就卡在那儿，排查现场最忌讳这个。

输出形如：

text
State    Recv-Q  Send-Q  Local Address:Port   Peer Address:Port   Process
LISTEN   0       128     0.0.0.0:22           0.0.0.0:*
LISTEN   0       128     127.0.0.1:8888       0.0.0.0:*
ESTAB    0       0       192.168.1.10:22      192.168.1.50:51588   users:(("sshd",pid=1121,fd=3))
列 含义 怎么读
State 连接状态 见下面的状态表
Recv-Q 接收队列里还没被应用读走的字节 监听态下是当前已完成握手的连接数
Send-Q 发送队列里还没被确认的字节 一直不为 0，说明对端收得慢或网络在丢
Local Address:Port 本地地址加端口 0.0.0.0 表示所有地址都听，127.0.0.1 表示只听本机
Peer Address:Port 对端地址加端口 监听态下是 *
Process 进程名、PID、文件描述符 要 root 权限才看得全

Local Address 那一列藏着最经典的一个坑。

服务监听在 127.0.0.1:8888，本机怎么连都通，别的机器怎么连都不通。原因不是防火墙，是它压根没在对外地址上听。改成 0.0.0.0:8888 才对外。反过来，监听 0.0.0.0 而你以为只有本机能访问，那是安全漏洞。看 ss -lntp 时先看这一列，能省掉一半「端口不通」的排查。

状态字段 #

TCP 是有状态机的东西，ss 把这些状态原样摊给你：

状态 含义 异常时说明
LISTEN 在监听，等握手 服务活着，端口通了
SYN-SENT 已发 SYN，等 SYN+ACK 一直停在这里，说明包出去了没回来：对端没开、被防火墙丢、路由不通
SYN-RECV 收到 SYN，回了 SYN+ACK，等 ACK 大量堆积，是 SYN flood 或对端不回 ACK
ESTAB / ESTABLISHED 连接已建立 正常数据传输
FIN-WAIT-1 已发 FIN，等对端的 ACK 或 FIN 主动关闭方的第一个状态
FIN-WAIT-2 收到 ACK，等对端 FIN 对方迟迟不发 FIN，半关闭
CLOSE-WAIT 收到对端 FIN，本端还没关 大量堆积就是应用层的 bug：程序没调 close()
LAST-ACK 等最后一个 ACK 短暂过渡
TIME-WAIT 等 2MSL，确保最后一个 ACK 到达 主动关闭方停留，量大不代表故障
CLOSED 连接结束 短暂过渡

三个状态值得记住对应的病因：

  • SYN-SENT 堆积：包发出去了，没回来。方向是「我这边的包能不能到对端」和「对端的回包能不能到我」。tcpdump 抓一下就知道卡在哪边。
  • CLOSE-WAIT 堆积：对端已经关了，你的程序没关。这是代码问题，不是网络问题，调内核参数没用，只能改程序。
  • TIME-WAIT 量大：主动关闭方要等 2MSL。短连接多的服务上这属正常现象，但端口会被占用一段时间，压测时会撞上端口耗尽。

这九个状态正好对应三次握手和四次挥手。握手在 tcpdump 里是三个包，在 ss 里是 SYN-SENT 到 ESTAB；挥手是四个包，在 ss 里是 FIN-WAIT-1、FIN-WAIT-2、TIME-WAIT（主动方）和 CLOSE-WAIT、LAST-ACK（被动方）。看状态表能反推握手进行到哪一步，这比盲抓包高效。

汇总与过滤 #

连接数太多，先看汇总：

bash
ss -s

text
Total: 213
TCP:   48 (estab 12, closed 20, orphaned 0, timewait 18)

Total 是套接字总数，estab 是已建立连接，timewait 是等待关闭的。orphaned 不为 0 要留意，那是没有进程认领的套接字，多是程序崩了留下的。

精确过滤比 grep 干净，state 后面接状态名，小写连字符写法（time-wait）与全大写常量写法（TIME-WAIT）都认：

bash
ss -tn state established
ss -tn state time-wait
ss -tan 'sport = :22'
ss -tn '( dport = :80 or dport = :443 )'

过滤交给内核做，比 grep 一遍再筛准。

netstat：老命令还得会读 #

netstat 用于显示各种网络相关信息：网络连接、路由表、接口状态（Interface Statistics）、masquerade 连接、多播成员（Multicast Memberships）等。

常见参数：

参数 含义
-a（all） 显示所有选项，默认不显示 LISTEN 相关
-t（tcp） 仅显示 TCP 相关
-u（udp） 仅显示 UDP 相关
-n 拒绝显示别名，能显示数字的全部转成数字
-l 仅列出处于 Listen（监听）状态的服务
-p 显示建立相关链接的程序名
-r 显示路由信息，即路由表
-e 显示扩展信息，例如 uid 等
-s 按各个协议进行统计
-c 每隔一个固定时间，重复执行该命令

一个提示：LISTEN 和 LISTENING 状态只有加 -a 或 -l 才看得到。默认输出里它们被过滤掉了，所以新手常以为「服务没监听」，其实是没加参数。

列端口和监听状态：

bash
netstat -a      # 所有端口，含监听与未监听
netstat -l      # 只列监听状态的 socket

netstat -l 的输出里能看到 :::8888 或 0.0.0.0:8888 处于 LISTEN，这就证明服务在听。查一个自己写的服务到底起没起，这一条最快。netstat -r 等于 route -n 的活儿，netstat -s 是分协议统计，netstat -c 是循环刷新，适合盯计数变化。

lsof：按端口找进程 #

ss -p 能给出进程，但有时你只想知道「谁占着 8888 这个端口」。lsof -i:8888 就是干这个的，它列出所有访问这个端口的进程。我们有一个 TCP 服务器在 8888 上监听，同时用 telnet 连上去测，这条命令就能看到两个进程——一个是自己的 TCP 服务器，另一个是 telnet 客户端。一个在听，一个在连。

bash
lsof -i -P -n           # 所有网络文件，不反解端口与主机名
lsof -i tcp:8888        # 只要 TCP
lsof -i @192.168.3.51   # 按远端地址筛
lsof -p 1121            # 按进程号看它打开了什么

-P 和 -n 跟 ss 里的 -n 一个道理，别让它去查 DNS。查「端口被谁占了」，lsof 比 ss 直观，因为它把进程名摆在第一列。

telnet：最原始的端口探测 #

Telnet 协议是 TCP/IP 协议族的一员，是 Internet 远程登录服务的标准协议和主要方式。它让用户在本地计算机上完成远程主机的工作：在终端运行 telnet 程序连到远端，在 telnet 程序里输入命令，命令在服务器上运行，就像直接在服务器控制台上敲一样。登录一台远程主机时实际启动两个程序：客户程序跑在本地，服务器程序跑在远程。

本地主机上的客户程序负责五件事：建立与远程服务器的 TCP 连接；从键盘接收本地输入的字符；把输入的字符串变成标准格式并传送给远程服务器；从远程服务器接收输出信息；把信息显示在本地主机屏幕上。

远程主机的服务程序是个常驻进程，平时守候在那里，一接到请求就活跃起来，负责五件事：通知本地主机远程主机已准备好；等候本地主机输入命令；对命令作出反应，比如显示目录内容、执行某个程序；把执行结果送回本地计算机显示；重新等候下一条命令。

今天没人用 telnet 做远程登录了，明文传密码。可它有个副作用极大的用途：当一个裸 TCP 客户端用。我们写过一版 TCP 服务器，功能是 echo——客户端发什么，它原样发回什么，在 192.168.3.51 上监听，端口 8888。服务器起来后先确认它在听，然后 telnet 192.168.3.51 8888。

连上就说明 TCP 层通了。接着敲一行字回车，屏幕上出现同一行字，echo 就有了反应；服务器端的终端上也能看到连接建立。整条链路从套接字到应用逻辑，一次验证完。这个用法值得留着，是因为它验证的是端口级连通性，不涉及任何应用层协议。curl 只能测 HTTP，dig 只能测 DNS，而 telnet 什么协议都能连——因为它根本不懂协议。

它的三个短板也明显：连不上时只给一句 Connection refused 或干等超时，没有细节；不支持超时参数，卡住只能 Ctrl+] 再 quit；传的是明文。所以现代做法用 nc：

bash
nc -zv 192.168.3.51 8888
nc -zv -w 2 192.168.3.51 8888
nc -zuv 192.168.3.51 53
nc -l 9000                     # 自己当服务端听一个端口

-z 是扫描模式，只建连不发数据；-v 打印结果；-w 2 设两秒超时；-u 走 UDP。输出就是 succeeded 或 refused，比 telnet 干净。

nc -l 9000 反过来用：在 A 机上听，在 B 机上 nc 192.168.3.51 9000，两边打字能互相看见，用来验证一条链路能不能双向通。这条命令不需要任何服务端程序，比写个测试程序快。

Connection refused 和超时的区别必须分清：refused 是有回应的——对端主机活着，包到了，只是那个端口没有程序在听，内核回了 RST；超时是没回应——包丢在中间，或者对端主机根本不回。前者查服务，后者查网络。

七、连通性测试 #

到这一步，前面四关都过了：接口起、地址有、路由通、邻居可达。现在真的发个包试试。

bash
ping -c 4 192.168.1.1
ping -c 4 -W 1 -i 0.2 8.8.8.8
ping -c 4 -s 1400 192.168.1.50
ping -I eth0 -c 4 10.0.0.5

-c 指定包数，不加会一直发；-W 1 是单包等待秒数；-i 0.2 是发包间隔；-s 1400 指定载荷大小，用来测 MTU；-I eth0 强制从某个接口发，多网卡机器上绕开路由表做对照实验。

输出形如：

text
PING 192.168.1.1 (192.168.1.1) 56(84) bytes of data.
64 bytes from 192.168.1.1: icmp_seq=1 ttl=64 time=0.312 ms
64 bytes from 192.168.1.1: icmp_seq=2 ttl=64 time=0.287 ms

--- 192.168.1.1 ping statistics ---
2 packets transmitted, 2 received, 0% packet loss, time 1001ms
rtt min/avg/max/mdev = 0.287/0.299/0.312/0.012 ms
字段 含义 怎么读
icmp_seq 序号 不连续说明中间丢包
ttl=64 生存时间，每过一跳减 1 Linux 默认起 64，Windows 起 128，据此反推跳数
time=0.312 ms 往返时延 同网段应小于 1 ms，跨城 10~30 ms 量级
packet loss 丢包率 0% 才叫通
rtt min/avg/max/mdev 时延统计 max 与 min 差得大、mdev 大，都是链路抖动

四次 ping 是分层验证的四个探针，按顺序打：

  1. ping 127.0.0.1 —— 只证明内核协议栈活着。不通，是系统级问题，重启网络服务。
  2. ping 本机 IP —— 证明地址配到了接口上。不通，地址或接口有问题。
  3. ping 网关 —— 证明二层和邻居解析正常。不通，回到 ip link 和 ip neigh。
  4. ping 外网 IP，比如 8.8.8.8 —— 证明路由和 NAT 正常。不通但网关通，查路由与出口。

四个探针逐级失败的位置，就是故障所在的层。这比一次 ping www.xxx.com 有用得多——后者把 DNS、路由、二层全混在一起了。

有一个坑必须记住：ping 不通不等于服务不通。ICMP 是独立协议，防火墙拦 ICMP 而放行 TCP 是常见做法，云主机的默认安全组就常这么配。要判断服务通不通，用 nc -zv 或 curl，别用 ping。反过来，ping 通也只说明 ICMP 通，不说明 80 端口通。

同网段内还有一个更底层的探针：arping -I eth0 -c 3 192.168.1.50。它发 ARP 请求，验证的是 IP 到 MAC 这一步，不需要对端协议栈配合。ping 不通而 arping 通，说明对端主机活着但不回 ICMP——问题在防火墙；两个都不通，说明二层就没戏。

八、路径追踪 #

打通了，但慢，或者时通时不通。下一步看路径。

traceroute 的原理是拿 TTL 做文章：发一个 TTL=1 的包，第一跳路由器把 TTL 减到 0，回一个 ICMP 超时报文，于是你知道了第一跳是谁；TTL=2 就探出第二跳，一路递增到目的。

bash
traceroute -n www.example.com
traceroute -n -q 1 -m 20 8.8.8.8
traceroute -I -n 8.8.8.8
traceroute -T -p 443 -n www.example.com

-n 不反解主机名，必加；-q 1 每跳只探一次，快；-m 20 最多 20 跳；-I 用 ICMP 探测，-T 用 TCP SYN 探测——后者能穿过只放行特定端口的防火墙，是老手常用的一招。

输出形如：

text
 1  192.168.1.1      0.412 ms  0.388 ms  0.401 ms
 2  * * *
 3  10.10.0.1        4.221 ms  4.108 ms  4.377 ms
 4  202.97.1.1      12.334 ms 12.201 ms 12.560 ms

每跳给三个时延，是三次探测的结果。解读只有三条规则：

  • 时延在某跳突然从个位数跳到几十毫秒，跨网或跨境就发生在那里。
  • 某一跳是 * * *，但后面的跳还能探出来，说明那台设备不回 ICMP，不是故障。路由器不回超时报文是常态。
  • 从某一跳开始全是 * * *，那才是真断了。

所以别看到 * 就下结论，要看到结尾。

要盯连续的抖动，用 mtr，它把 ping 和 traceroute 合起来做成动态视图：

bash
mtr -n -c 50 8.8.8.8
mtr -n -rw -c 100 8.8.8.8

text
HOST: lab                    Loss%   Snt   Last   Avg  Best  Wrst StDev
  1.|-- 192.168.1.1           0.0%    50    0.4   0.4   0.3   0.9   0.1
  2.|-- 10.10.0.1             0.0%    50    4.2   4.3   3.9   9.1   0.8
  3.|-- 202.97.1.1            2.0%    50   12.3  13.1  11.8  41.2   4.6
  4.|-- 8.8.8.8               0.0%    50   11.9  12.6  11.5  30.4   3.1

Loss% 是丢包率，Snt 是发出包数，后五列是时延统计，StDev 是标准差。只看最后一跳的 Loss%——中间跳的丢包多数是设备限速 ICMP，最后一跳丢了才是真丢。中间跳丢失而最后一跳 0%，是采集抑制，不是链路问题。

Windows 上是 tracert，参数不同，输出格式也不同，逻辑一样。

九、抓包分析 #

前面的命令都在看内核给的结论。tcpdump 直接看线上的包，是唯一能自证的工具。

bash
tcpdump -i eth0 -nn
tcpdump -i any -nn -c 20 port 80
tcpdump -i eth0 -nn host 192.168.3.51 and port 8888
tcpdump -i eth0 -nn -w /tmp/cap.pcap -c 1000
tcpdump -i eth0 -nn -A -s 0 port 80

参数要记的就这几组：

参数 作用 说明
-i eth0 指定接口 any 表示全部接口，抓隧道与容器时用它
-nn 不反解地址与端口 两个 -n，一个管网址，一个管端口
-c 20 抓够 20 个包就停 不加会一直刷屏
-w file.pcap 写文件 拿去 Wireshark 慢慢看
-r file.pcap 读文件 离线分析
-s 0 抓完整包长 老版本默认只抓 68 字节，会截断
-A / -X 按 ASCII 或十六进制显示载荷 看明文协议与二进制协议
-e 打印链路层头部 看 MAC 时用

过滤表达式用 and、or、not、括号组合，优先级靠括号明确。只抓 SYN 包，看握手发起：

bash
tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack == 0'

一次 TCP 握手的三个包，标志位是 [S]、[S.]、[.]。判断「连不上」卡在哪一步，就看这三个包齐不齐：

抓到的包 结论
只有 [S]，没有 [S.] 请求到了对端，响应没回来：对端服务没开、被防火墙 DROP、回程路由错
[S] 重复发，序号间隔递增 内核在重传 SYN，一直没应答
[S] 后立刻 [R] 或 [R.] 对端明确拒绝，端口没监听
[S] [S.] [.] 都有，随后 [F] 连接建起来又断了，问题在应用层或超时

tcpdump 需要 root 或 CAP_NET_RAW 权限。抓包本身会给 CPU 带来负担，生产机上一定加 -c 限量，并写文件而不是刷屏。-w 抓出来的文件动辄几百兆，先算好磁盘空间。

十、DNS 查询 #

前面全靠 IP。一旦用域名，就多了一层故障来源：解析。

bash
dig www.example.com
dig +short www.example.com
dig @8.8.8.8 www.example.com A
dig -x 8.8.8.8
dig +trace www.example.com

+short 只输出答案，适合塞进脚本；@8.8.8.8 指定服务器，用来对比「本地 DNS 有问题还是域名本身有问题」；-x 做反向解析，IP 查域名；+trace 从根开始逐级查，链路断在哪一级一目了然。

完整输出形如：

text
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 41235
;; ANSWER SECTION:
www.example.com.        3600    IN      A       93.184.216.34
;; Query time: 24 msec
;; SERVER: 192.168.1.1#53(192.168.1.1)

三处值得看：status 是返回码，ANSWER SECTION 是答案，SERVER 是真正回答你的那台服务器——这一行常被人忽略，它告诉你用的是哪个 DNS，而不是你以为的那个。

status 含义 该查什么
NOERROR 查询成功 看 ANSWER 段有没有记录
NXDOMAIN 域名不存在 域名拼错，或记录没配、没同步
SERVFAIL 服务器处理失败 权威服务器故障、DNSSEC 校验失败
REFUSED 服务器拒绝回答 访问控制，或该服务器不对外服务

记录类型要记几个：A 是 IPv4 地址，AAAA 是 IPv6 地址，CNAME 是别名，MX 是邮件交换服务器，NS 是该域的权威服务器，TXT 是文本记录，PTR 是反向解析记录，SOA 是起始授权记录。

nslookup 和 host 也能查，输出更简短。dig 的信息量最大，优先用它。

解析链路上还有两份本机文件要先看：/etc/hosts 是静态映射，优先级高于 DNS；/etc/resolv.conf 里的 nameserver 才决定问谁。改了 DNS 不生效，八成是 hosts 里有一条旧记录压着，或者 resolv.conf 被别的程序覆盖了。

十一、新旧命令对照 #

一张表收完全篇的替代关系。

老命令（net-tools） 新命令（iproute2） 差别
ifconfig ip addr、ip link 新命令看得到 secondary 地址与接口状态机
route -n ip route 新命令支持多路由表与策略路由
arp -a ip neigh 新命令显示 FAILED 等失败状态
netstat -an ss -an 新命令走 netlink，连接多时不卡
netstat -lntp ss -lntp 参数几乎一一对应
netstat -i ip -s link 新命令的错误计数更全
netstat -r ip route 同上
netstat -s ss -s 加 /proc/net/snmp 汇总项有出入
netstat -c watch -n 1 ss -s 新命令本身没有循环参数
iptables nft 规则模型不同，不完全等价

ifconfig 和 route 都被 ip 取代，netstat 被 ss 取代，理由都是同一个：旧命令读 /proc，信息不全、性能差；新命令走 netlink，能拿到内核的全部状态。

新系统上优先新命令。老命令存在的价值只有两个：读老文档，上老机器。脚本里别再写 ifconfig，很多发行版装完就没有这个命令。

十二、易错点速查 #

最后收一张表，把前面散落的坑集中起来。

现象 常见原因 动作
ping 网关 100% 丢包 接口 DOWN 或没有载波 ip link 看 UP 与 LOWER_UP
地址是 169.254.x.x DHCP 没拿到租约 查 DHCP 服务与客户端日志
同交换机机器互 ping 不通 掩码配错，不走网关也不 ARP 对端 ip addr 核对前缀长度
有默认路由但出不去 ip rule 把流量导到了别的表 ip rule show
两条默认路由 metric 相同，行为随机 删掉多余那条
网关邻居 FAILED 二层不通，或网关 IP 配错 ip neigh、arping
端口在听但外部连不上 监听在 127.0.0.1 ss -lntp 看 Local Address
连上就被拒 端口没监听，内核回 RST ss -lntp、nc -zv
大量 CLOSE-WAIT 程序没关连接，是代码 bug 改程序，别调内核参数
大量 TIME-WAIT 短连接多，主动关闭方在等 2MSL 属正常，压测时留意端口耗尽
ping 通但服务不通 ICMP 放行、TCP 被拦 nc -zv 或 curl 复核
小请求正常、大传输卡死 MTU 不匹配，封装后超限 ping -s 试探，调 mtu
dig 超时但 ping 8.8.8.8 通 DNS 服务器不可达 换 @ 指定的服务器对照

表格之外还有三条原则，比任何命令都重要。

第一，顺序不能跳。接口、地址、路由、邻居、连通、端口，六步走完，故障一定在最后不通的那一步。跳过底层查应用，等于蒙。

第二，每一步只看本层的信息。ip link 的回答里没有端口，ss 的回答里没有路由。用错层的输出下结论，是误判的主要来源。

第三，两个命令的结论矛盾时，信抓包。ss 说端口在听、客户端说连不上，tcpdump 会告诉你 SYN 到底有没有到网卡。抓包是唯一不依赖任何一方说法的证据。

命令记不住没关系，把第一节那张顺序表钉在脑子里，需要什么再查手册。排错的能力不在于背参数，在于知道下一步该问谁。
