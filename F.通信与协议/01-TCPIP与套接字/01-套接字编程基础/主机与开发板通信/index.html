这篇讲三件事：主机和开发板怎么把网打通，网络程序怎么接数据库，一个完整的课程项目怎么落地。

不讲什么：socket 每个 API 的逐个拆解、TCP 状态机、原始套接字怎么构造报文。这些在同组的《TCP 套接字编程》和《原始套接字与协议构造》里。IO 模型的理论部分在父目录另一组。

前置：手上有一份能编译的最小 server/client，跑起来不崩。这篇不教你写第一个 socket。

一、主机与开发板通信要解决什么 #

场景很具体。PC 上编译一份 server.c，开发板上跑一份 client.c，或者反过来。两边 gcc 都不报错，一连就卡在 connect，或者连上了发过去没反应。

我们把这件事按四层拆开看。跨设备通信出问题，一定落在某一层上，没有玄学。

层 你盯的东西 出问题的典型表现
链路层 网线、指示灯、交换机端口 网卡灯不亮，ifconfig 没地址
网络层 IP、掩码、路由表、ARP 表 ping 不通
传输层 端口、监听队列 ping 通，telnet 端口 不通
应用层 协议格式、字节序、缓冲区 连上了，数据对不上

开发板比 PC 多几道坎：

  • 没有显示器。你靠串口终端或者 ssh 上去，ifconfig 的输出得会读。
  • 根文件系统常是 busybox 拼的。ifconfig 有，ip 不一定有；netstat 还得看板子自带不带，参数是 netstat -anp。
  • 内存小。char buf[1024] 够用，别在栈上开 64K 的包。
  • 板子上的时钟常年不准。做超时判断时，别把它的本地时间当真。

两台机器要通信，代码职责分工是固定的：

角色 必走的调用 谁先跑 绑定动作
服务端 socket → bind → listen → accept 先跑，长期挂在监听状态 必须 bind 一个本机地址加端口
客户端 socket → connect 后跑，服务端不在就报 Connection refused 系统自动分配源端口

accept 之前服务端一步都不能少，connect 之前客户端只差一个 connect。bind 是服务端的特权，客户端不用它，除非你要指定源端口。

有个坑从第一天就埋下。常见的写法是把对端地址写成编译期常量：

c
#define SERVER_PORT 8888
#define SERVER_IP   "192.168.1.17"

换一个实验室、换一个路由器，网段就从 192.168.1.x 变成 192.168.0.x，代码里的 IP 立刻失效。两种处理方式，选一个：

  • 服务端 bind 用 INADDR_ANY，让内核挑本机任意地址；客户端的目标 IP 从命令行参数或配置文件读。
  • 统一用主机名，靠 getaddrinfo 解析。

服务端绑定 INADDR_ANY 是常规做法，因为一台机器常有多张网卡，绑死某张网卡的地址，换个口插就不通了：

c
server_addr.sin_family      = AF_INET;
server_addr.sin_port        = htons(SERVER_PORT);
server_addr.sin_addr.s_addr = htonl(INADDR_ANY);

二、网络连通性的前置条件 #

网络层干的事只有一件：路由的查找。它保证一个数据包从一个 IP 地址送到另一个 IP 地址。它不保证送到、不保证顺序、不保证不重复，那些是 TCP 的事。

路由表决定包往哪个网卡出。Windows 上 route print，Linux 上 route -n 或 ip route：

bash
route print
tracert 192.168.1.20

bash
route -n
ip route

开发板上先看默认路由，输出认出这两行就够：

text
Destination     Gateway         Genmask         Flags  Iface
192.168.1.0     0.0.0.0         255.255.255.0   U      eth0
0.0.0.0         192.168.1.1     0.0.0.0         UG     eth0

那行 UG 就是默认网关。少了它，同网段能通，出了网段全废，ping 8.8.8.8 直接没回音。

同一网段内发包，靠的不是 IP，是 MAC。IP 到 MAC 的映射由 ARP 完成。

每台主机在自己的 ARP 缓冲区里维护一张 ARP 表，记录 IP 与 MAC 的对应关系。流程是这样：

  1. 源主机要发一个包到目的主机，先查自己的 ARP 表里有没有这个 IP 对应的 MAC。
  2. 有，直接把数据包发到这个 MAC 地址。
  3. 没有，就往本地网段发一个 ARP 请求广播包。包里带源主机的 IP、硬件地址，以及目的主机的 IP。
  4. 网段内所有主机收到广播，检查包里的目的 IP 是否等于自己的 IP。不等就丢掉。
  5. 相等的那台主机，先把发送端的 MAC 和 IP 写进自己的 ARP 表，表里已有这条记录就覆盖。
  6. 然后它给源主机回一个 ARP 响应包，告诉对方自己就是它要找的 MAC。
  7. 源主机收到响应，把目的主机的 IP 和 MAC 写进自己的 ARP 表，开始传数据。
  8. 源主机一直收不到响应，就是 ARP 查询失败。

举个具体例子。A 的地址是 IP 192.168.10.1、MAC AA-AA-AA-AA-AA-AA；B 的地址是 IP 192.168.10.2、MAC BB-BB-BB-BB-BB-BB。

A 要和 B 通信，得先知道 B 的以太网地址，于是 A 发一个 ARP 广播：「谁是 192.168.10.2，请告诉 192.168.10.1」。B 收到广播，发现问的是自己，回一个 ARP 单播应答：「192.168.10.2 在 BB-BB-BB-BB-BB-BB」。这条应答进了 A 的 ARP 缓存，之后 A 才发得出以太网帧。

查表用 arp -a。开发板上看到一条 incomplete 的记录，说明对方没回，包发不出去。

ARP 缓存有超时。条目过期就重新广播一次，所以链路第一次握手会多花几毫秒。这个行为对我们排错有用：如果 ping 第一包丢、后面通，多半是 ARP 正在解析，不是配置错。

同网段靠 ARP，跨网段靠网关的下一跳。判断两台机器是否同网段，只看 IP 与掩码的按位与：

机器 IP 掩码 网段
PC 192.168.1.100 255.255.255.0 192.168.1.0
开发板（对） 192.168.1.20 255.255.255.0 192.168.1.0
开发板（错） 192.168.0.20 255.255.255.0 192.168.0.0

第三种情况下，两台机器插在同一个交换机上，ping 也不通。原因不在物理连接，在它们认为彼此不在同一网段，包会交给网关，而网关不知道怎么送回来。

三、开发板的网络配置 #

板子上电后第一件事是确认网卡起来了、拿到地址。

bash
ifconfig eth0
ip addr show eth0

ifconfig eth0 up          # 网卡没起
ip link set eth0 up

ifconfig eth0 三个东西必须看：

  • UP：网卡被启用。
  • RUNNING：链路真的通了，网线接好、对端设备在线。
  • inet 192.168.1.20：拿到了 IPv4 地址。

只有 UP 没有 RUNNING，问题在网线或交换机，去查物理层，别再看代码。

配静态地址。板子做服务端时，地址不能变，否则每次都要重编客户端。两条路，ifconfig 和 ip，改完都是重启失效：

bash
ifconfig eth0 192.168.1.20 netmask 255.255.255.0 up
ip addr add 192.168.1.20/24 dev eth0

网关单独加：

bash
route add default gw 192.168.1.1
ip route add default via 192.168.1.1

要重启保留，写配置文件。发行版不同，位置不同：

text
/etc/network/interfaces
    auto eth0
    iface eth0 inet static
        address 192.168.1.20
        netmask 255.255.255.0
        gateway 192.168.1.1

/etc/systemd/network/20-eth0.network
    Address=192.168.1.20/24
    Gateway=192.168.1.1

PC 侧用 ipconfig /all 看完整信息，地址不对时先放掉再续租：

bash
ipconfig /all
ipconfig /release
ipconfig /renew

Linux 侧是 ip addr。

主机和板子直连也可以，现代网卡支持自动翻转，直通线照用。但直连少了一个 DHCP，两边都得手配静态地址，而且必须同网段。用交换机或路由器接起来更省事，路由器还会发地址。

一张清单，配完逐条打勾：

检查项 命令 期望
网卡启用 ifconfig eth0 出现 UP RUNNING
地址 同上 inet 那行有值
掩码一致 两边对比 同为 /24 或同为 /16
同网段 手算按位与 网段部分相同
默认路由 route -n 跨网段访问时有 UG 行
双向可达 两边互相 ping 都通

最后一条最容易漏：只 ping 了单向就以为通了。板子到 PC 通、PC 到板子不通，常见原因是 PC 的防火墙拦了入站 ICMP。

防火墙这一条单独说，因为它伪装得最像代码错误。Windows 默认拦入站连接：

bash
Set-NetFirewallProfile -Profile Private -Enabled False

New-NetFirewallRule -DisplayName "dictionary-8888" -Direction Inbound `
  -Protocol TCP -LocalPort 8888 -Action Allow

第一条只用于临时验证，验证完记得开回去。第二条才是常态做法。

板子做服务端、PC 做客户端时，PC 的防火墙不影响结果。反过来，PC 做服务端、板子去 connect，PC 的防火墙能把连接直接吞掉，客户端看到的是超时，不是拒绝。这种表现特别容易被当成「服务端没写对」。

Linux 侧对应的是 iptables 或 nft：

bash
iptables -L -n
iptables -I INPUT -p tcp --dport 8888 -j ACCEPT

改完配置立刻 ping 一次，别攒着改。一步一验证，出错时才知道是哪一步引入的。

四、跨设备通信的调试顺序 #

这一节是整篇最值钱的部分。

跨设备通信失败，九成在「网络层不通」，不在「代码错」。我们见过太多人一连不上就开始翻 connect 的返回值、改缓冲区大小、重写协议结构体，改了两小时，最后发现是板子地址配错一位。

排错顺序只有一个：先 ping 通，再 telnet 端口 通，最后才查代码。顺序不能颠倒，颠倒就是白干。

步 动作 通说明什么 不通先查
1 ping 对端IP 链路、IP、掩码、路由都对 网线、ifconfig、掩码、同网段、防火墙 ICMP
2 telnet 对端IP 端口 对端有进程在 listen，端口可达 服务端有没有起、bind 的地址、防火墙端口
3 对端 netstat -anp 端口处于 LISTEN，绑的地址对不对 bind 参数、端口冲突
4 本机自测 127.0.0.1 代码逻辑本身没问题 协议组包、字节序、缓冲区
5 跨设备联调 应用层格式对得上 结构体对齐、长度字段、分包

第 1 步不通，第 2 步之后所有动作都是浪费时间。这句话请当纪律。

ping 走的是 ICMP，跟 TCP 端口没关系。所以会出现「ping 通、telnet 不通」的组合，这个组合的意思非常明确：网络层没问题，是服务没起来或者被拦了。

telnet 在 Windows 上默认没装。PowerShell 自带一个替代品：

bash
Test-NetConnection 192.168.1.17 -Port 8888

Linux 和板子上用 telnet 或 nc：

bash
telnet 192.168.1.17 8888
nc -vz 192.168.1.17 8888

板子上确认自己有没有在听，看 netstat：

bash
netstat -anp | grep 8888

text
tcp  0  0 0.0.0.0:8888  0.0.0.0:*  LISTEN  1023/server

0.0.0.0:8888 表示监听所有网卡，这是对的。如果显示 127.0.0.1:8888，那么只有本机能连，板子从外面连一律被拒。绑成 127.0.0.1 是新手最容易犯的 bind 错误，因为它在板子上自测完全正常。

失败表现按 errno 分方向，记住这张表就够用：

表现 errno 真实原因 先动哪里
connect 立刻返回失败 ECONNREFUSED 对端端口没进程在听，或被 RST 服务端起没起、端口对不对
connect 卡几十秒才失败 ETIMEDOUT 包发出去没回，防火墙丢了或路由不对 防火墙、路由、网段
connect 成功，recv 一直阻塞 — 对端在等更多数据，或协议长度字段错 协议格式、是否发完
bind 失败 EADDRINUSE 端口被占，或上次的 socket 还在 TIME_WAIT SO_REUSEADDR、换端口
bind 失败 EADDRNOTAVAIL bind 的地址不属于本机 改成 INADDR_ANY

第三条特别能骗人。连接建起来了，双方都不报错，就是一个字都不出。这已经不是网络问题，是应用层在互相等。查协议里的长度字段是不是按网络字节序发的，查发送端是不是少发了一个字节。

EADDRINUSE 的标准解法：

c
int on = 1;
if (setsockopt(sockfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof(on)) < 0)
{
    perror("setsockopt");
    exit(1);
}

这段必须在 bind 之前调用。它解决的是服务端重启时端口还挂在 TIME_WAIT 的问题，不是解决端口被别的进程占着。

联调时还有个便宜手段：本机跑两份进程，客户端 connect 到 127.0.0.1。这一步能过，说明协议、组包、收发逻辑都成立，跨设备再不通就只剩网络层。这个自测把问题空间砍掉一半，做项目的都该养成习惯。

五、网络程序怎么访问数据库 #

数据库在网络程序里的位置，只有一个正确答案：数据库在服务端，客户端不直接连数据库。

三层结构，从上到下：

层 谁 干什么 不该干什么
客户端 板子或 PC 上的前台 采集输入、发请求、显示结果 不连数据库、不写 SQL、不做权限判断
服务端 后台进程 收请求、做业务校验、查库、组包回发 不信任客户端传来的任何字段
数据库 SQLite 文件或 MySQL 服务 存数据、执行查询 不暴露给客户端

为什么客户端直连数据库是架构错误，四条理由：

  • 数据库账号密码必须随客户端分发，等于人手一份，权限控制直接失效。
  • 业务规则写在客户端，客户端被改就绕过规则。用户表里的 isonline 想怎么改就怎么改。
  • 数据库的连接数、文件句柄是有限资源。板上几十个客户端同时开库，服务端先崩。
  • 客户端一旦绕过服务端，服务端掌握的在线状态、历史记录全都不准了。

所以正确的数据流是客户端发请求，服务端查库，结果再回给客户端。客户端从头到尾不知道表名和字段名。

嵌入式场景用 SQLite 最合适，单文件、零配置。它 2000 年 1 月由 Hipp 起头，想法是做一个用 GNU DBM 哈希库（gdbm）做后台的嵌入式 SQL 库，不需要安装和管理支持。2000 年 8 月 SQLite 1.0 发布。它满足 ACID：原子性 Atomicity、一致性 Consistency、独立性 Isolation、持久性 Durability。

命令行先熟悉表操作，后面写代码才有参照：

bash
sqlite3 my.db

sql
-- 建表。类型写不写都不影响存储，但约束照样生效
create table stu(sno integer primary key,
                 sname text not null,
                 ssex text default 'man',
                 sage integer default 19,
                 sdept text default 'cs');

-- 全字段赋值
insert into stu values('95001','liyong','m',20,'cs');
insert into stu values('95002','liuchen','m',20,'cs');
insert into stu values('95003','wangmin','f',20,'cs');
insert into stu values('95004','zhangli','f',20,'cs');

-- 部分赋值。设了 not null 的列必须给值，主键会自动填充
insert into stu(sname,sage) values('pengdan',34);

-- 查
select * from stu;
select sname,ssex from stu;
select sage from stu where sname='liuchen';

-- 删。or 与 and 的区别直接决定删几条
delete from stu where sno=95003 or sname='pengdan';
delete from stu where sno=95003 and sname='pengdan';

-- 改
update stu set sage=22 where sno=95003;

-- 改表结构
alter table stu add spwd text default '1234578';
alter table student rename to stu;
drop table stu;

SQL 关键字不区分大小写，create 和 CREATE 一样。命令行里两个点命令让输出能看：

text
.headers on      显示列标题
.mode column     列对齐

数据库编程就三步：打开数据库、通过函数执行对应命令、关闭。任何语言、任何驱动都是这个结构。

现在说注入。拼接 SQL 字符串是重灾区，问题的根在「SQL 语句」和「数据」混在同一个字符串里。服务端本来想拼：

c
char sql[256];
sprintf(sql, "select * from user where name='%s' and pwd='%s'", name, pwd);

用户在密码框里填一个 ' or '1'='1，拼出来变成：

sql
select * from user where name='admin' and pwd='' or '1'='1'

条件恒真，密码校验被绕过。填 '; drop table user; -- 更狠，一条查询把表删了。这不是理论攻击，课程项目里裸拼字符串的代码一抓一大把。

解法是参数绑定，让数据永远只是数据。MySQL 的 C 接口这样写：

c
MYSQL_STMT *stmt = mysql_stmt_init(mysql);
const char *sql = "select sno, sname from user where name=? and pwd=?";

mysql_stmt_prepare(stmt, sql, strlen(sql));

MYSQL_BIND bind[2];
memset(bind, 0, sizeof(bind));

bind[0].buffer_type = MYSQL_TYPE_STRING;
bind[0].buffer      = name;
bind[0].buffer_length = strlen(name);
bind[0].length      = &name_len;

bind[1].buffer_type = MYSQL_TYPE_STRING;
bind[1].buffer      = pwd;
bind[1].buffer_length = strlen(pwd);
bind[1].length      = &pwd_len;

mysql_stmt_bind_param(stmt, bind);
mysql_stmt_execute(stmt);

mysql_stmt_bind_result(stmt, result_bind);
while (mysql_stmt_fetch(stmt) == 0)
{
    /* 取一行 */
}
mysql_stmt_close(stmt);

要点三条：

  1. mysql_stmt_prepare 先把语句骨架编译好，? 是占位符，之后不会再把字符串当 SQL 解析。
  2. bind 把变量地址交给驱动，驱动按类型把值单独送过去。
  3. 用户输入里有多少引号、分号、--，都只是字面字符。

SQLite 的等价写法是 sqlite3_prepare_v2 加 sqlite3_bind_text：

c
sqlite3_stmt *stmt;
sqlite3_prepare_v2(db,
    "select sno, sname from user where name=? and pwd=?",
    -1, &stmt, NULL);

sqlite3_bind_text(stmt, 1, name, -1, SQLITE_TRANSIENT);
sqlite3_bind_text(stmt, 2, pwd,  -1, SQLITE_TRANSIENT);

while (sqlite3_step(stmt) == SQLITE_ROW)
{
    const unsigned char *sno  = sqlite3_column_text(stmt, 0);
    const unsigned char *sname = sqlite3_column_text(stmt, 1);
}
sqlite3_finalize(stmt);

占位符编号从 1 开始，不是 0。这个下标错一位，绑进去的永远是错误的值，而代码不会报错。

再补一条：就算用了参数绑定，也不要让客户端传来的字符串直接当表名或列名。表名不能绑，只能拼，拼之前必须用白名单判定。

六、连接数据库的完整流程 #

数据库编程只有三步：打开数据库、通过函数执行对应的命令、关闭。服务端进程从启动到退出，走的就是这个骨架。

第一次打开，库文件不存在会自动创建。这一步之后，db 就是后面所有操作的句柄。

c
#include <sqlite3.h>
#include <stdio.h>

#define CREATE_USER \
    "create table if not exists user(" \
    " name text primary key,"         \
    " pwd text not null,"             \
    " isonline integer default 0,"    \
    " sex text default 'm');"

int main(void)
{
    sqlite3 *db = NULL;
    char *errmsg = NULL;

    if (sqlite3_open("dict.db", &db) != 0)
    {
        fprintf(stderr, "open failed: %s\n", sqlite3_errmsg(db));
        sqlite3_close(db);
        return -1;
    }

    if (sqlite3_exec(db, CREATE_USER, NULL, NULL, &errmsg) != 0)
    {
        fprintf(stderr, "exec failed: %s\n", errmsg);
        sqlite3_free(errmsg);
        sqlite3_close(db);
        return -1;
    }

    sqlite3_close(db);
    return 0;
}

sqlite3_exec 的 errmsg 由库内部 malloc 出来，用完必须 sqlite3_free，不然每失败一次漏一块。这个细节在小项目里查不出来，跑一天才发现内存涨。

接口逐个说清，写代码时不用再翻文档。

打开是 int sqlite3_open(char *path, sqlite3 **db)。path 是数据库文件路径，:memory: 表示内存库；db 是指向句柄指针的指针，函数把句柄写回来；成功返回 0，失败返回非零错误码。

关闭是 int sqlite3_close(sqlite3 *db)，成功返回 0，失败返回非零。库里还有语句没 finalize 时，关闭会失败。

取错误信息用 const char *sqlite3_errmsg(sqlite3 *db)，返回静态字符串，不用释放，下次调用就被覆盖，要留存先复制一份。

带回调执行：

c
typedef int (*sqlite3_callback)(void *para, int f_num, char **f_value, char **f_name);
int sqlite3_exec(sqlite3 *db, const char *sql, sqlite3_callback callback, void *para, char **errmsg);
  • db 数据库句柄；sql 要执行的语句，多条可以用分号隔开；callback 在语句有返回结果时，每查到一条记录自动调用一次；para 原样传给回调，塞自己的结果结构体进去；errmsg 是错误信息指针的地址。
  • 回调四个参数：para 是透传的那个指针，f_num 是这条记录的字段数目（结果列数），f_value 是每个字段值的指针数组，f_name 是每个字段名称的指针数组（列标题）。
  • 回调返回 0 继续取下一条，返回 -1 中止；exec 成功返回 0，失败返回错误码。

f_value 里全是字符串，select age from stu 拿到的是 "20"，不是整数 20。f_value[0] 和 f_name[0] 下标对齐，新手常把 f_name 当成第一行数据，因为它在输出里确实出现在表头位置。字段值为 NULL 时拿到的是 NULL 指针，不是空字符串，直接 strcpy 会段错误。

不要回调的写法：

c
int sqlite3_get_table(sqlite3 *db, const char *sql, char ***resultp,
                      int *nrow, int *ncolumn, char **errmsg);

resultp 指向结果，返回的是一维字符串数组，前 ncolumn 个是列名，后面才是数据；nrow 是满足条件的记录数；ncolumn 是每条记录的字段数；成功返回 0，失败返回非零。取值下标要自己算，第 i 行第 j 列在 result[(i + 1) * ncolumn + j]，漏掉那个 +1，取到的全是列名。用完必须 sqlite3_free_table(result)，别用 free。

函数 干什么 关键点
sqlite3_open 打开或创建库 失败也要 close 一次
sqlite3_close 关闭 语句没 finalize 会失败
sqlite3_errmsg 取错误文本 静态缓冲，别长期持有
sqlite3_exec 执行 SQL，可带回调 errmsg 要 sqlite3_free
sqlite3_get_table 执行并一次性取全表 结果要 sqlite3_free_table
sqlite3_prepare_v2 预编译语句 带占位符，防注入
sqlite3_bind_* 绑参数 下标从 1 开始
sqlite3_step 逐行推进 返回 SQLITE_ROW 才有数据
sqlite3_finalize 释放语句 每条 prepare 都要配一个

服务端的规律：库里三张表，user 存账号，dict 存单词和释义，history 存查询记录。三条 create table if not exists 放在 db_open() 里，进程起来先建表，之后所有业务函数假定表存在。

按课程项目的要求，数据库操作要单独成文件：

c
/* sql.h */
#ifndef SQL_H
#define SQL_H

#include <sqlite3.h>

int  db_open(const char *path, sqlite3 **db);
void db_close(sqlite3 *db);
int  db_exec(sqlite3 *db, const char *sql, char **errmsg);
int  db_get_table(sqlite3 *db, const char *sql, char ***result,
                  int *nrow, int *ncol, char **errmsg);
void db_free_table(char **result);

#endif

这样做的好处很直接：server.c 里看不到一句 SQL，业务逻辑和存储逻辑分开，换库只改 sql.c。项目要求里写的 sql.c sql.h 就是这件事。

七、查询结果的封装与传输 #

客户端和服务端之间的数据交互，要用统一的结构体。每加一个功能就新写一套收发格式，是这类项目最常见的失控方式。

c
#define MAXLEN_DATA 1024

struct XProtocol
{
    uint16_t cmd_type;              /* 网络字节序 */
    uint16_t state;                 /* 网络字节序 */
    uint32_t data_len;              /* 网络字节序 */
    unsigned char name[32];
    unsigned char data[MAXLEN_DATA];
} __attribute__((aligned(4)));

五个字段各管一件事：

字段 类型 字节序 用途
cmd_type uint16_t 网络字节序 请求类型或响应类型
state uint16_t 网络字节序 服务端返回的状态码
data_len uint32_t 网络字节序 data 里实际字节数
name unsigned char[32] 无 用户名，定长
data unsigned char[1024] 无 载荷，单词、释义、历史条目

data_len 不能省。data 是定长数组，里面往往只用了前几十字节，接收方靠 data_len 才知道该解析到哪。没有它，就只能靠 strlen 碰运气，而二进制载荷里本来就有 \0。

命令类型和响应类型成对定义，响应码统一在高位置 1：

c
/* 数据包类型 cmd_type */
#define REQ_REGISTER   (unsigned short)0x0001 /* 客户端发起的用户注册请求 */
#define RPL_REGISTER   (unsigned short)0x8001 /* 服务器对用户注册请求的响应 */

#define REQ_LOGIN      (unsigned short)0x0002 /* 客户端发起的用户登陆请求 */
#define RPL_LOGIN      (unsigned short)0x8002 /* 服务器对用户登陆请求的响应 */

#define REQ_QUERYWORD  (unsigned short)0x0003 /* 客户端发起的单词查询请求 */
#define RPL_QUERYWORD  (unsigned short)0x8003 /* 服务器对单词查询请求的响应 */

#define REQ_HISTORY    (unsigned short)0x0004 /* 客户端发起的历史记录查询请求 */
#define RPL_HISTORY    (unsigned short)0x8004 /* 服务器对历史查询请求的响应 */

#define REQ_EXIT       (unsigned short)0x0005 /* 客户端发起的退出登陆请求 */

0x8000 这一位就是「这是响应」的标记。服务端收到包先 if (cmd_type & 0x8000) 判断方向，收到响应包说明客户端写错或者包错位了，直接丢。

状态码单独一套，放在 state 字段里：

c
/* 服务器发送给客户端 返回状态说明 */
#define RTL_SUCCESS       (unsigned short)0x0000 /* 成功 */
#define RTL_USEREXIST     (unsigned short)0x0001 /* 用户已存在 */
#define RTL_NUSEREXIST    (unsigned short)0x0002 /* 用户不存在 */
#define RTL_INSERTERR     (unsigned short)0x0004 /* 插入用户失败 */
#define RTL_WRONGPASSWD   (unsigned short)0x0005 /* 用户密码错误 */
#define RTL_RIGHTPASSWD   (unsigned short)0x0006 /* 用户密码正确 */
#define RTL_USERONLINE    (unsigned short)0x0007 /* 用户已在线 */
#define RTL_USEROFFLINE   (unsigned short)0x0008 /* 用户不在线 */
#define RTL_NOFINDWORD    (unsigned short)0x0009 /* 未找到单词 */
#define RTL_NOHISTORY     (unsigned short)0x0010 /* 查找用户历史失败 */
#define RTL_DBERR         (unsigned short)0x0011 /* 数据库查询出错 */
#define RTL_HISTORYOVER   (unsigned short)0x0012 /* 历史记录发送完毕 */

RTL_HISTORYOVER 是一条独立设计的消息，作用是把「结果发完了」这件事显式告诉客户端。历史记录动不动几十条，服务端一条一条发，客户端不知道什么时候停。有了这个结束标记，客户端收到就退出收集循环，不用靠超时猜。这条设计能省掉大量「历史记录显示不全」的 bug。

RTL_RIGHTPASSWD 看着多余，登录成功不是有 RTL_SUCCESS 吗。但在协议里区分「登录成功」和「一般操作成功」，客户端的状态机好写，不用回头查上一条请求是什么。

打包：所有多字节整数转网络字节序。name 和 data 是字节数组，不转。

c
int pack_request(unsigned char *out, unsigned short cmd, const char *name,
                 const void *payload, unsigned int len)
{
    struct XProtocol pkt;
    if (len > MAXLEN_DATA) return -1;
    memset(&pkt, 0, sizeof(pkt));
    pkt.cmd_type = htons(cmd);
    pkt.state    = htons(RTL_SUCCESS);
    pkt.data_len = htonl(len);
    if (name)           strncpy((char *)pkt.name, name, sizeof(pkt.name) - 1);
    if (payload && len) memcpy(pkt.data, payload, len);
    memcpy(out, &pkt, sizeof(pkt));
    return (int)sizeof(pkt);
}

解包反过来，先 ntohs / ntohl，再按长度取载荷：

c
int unpack(const unsigned char *in, struct XProtocol *pkt,
           char *name, unsigned char *payload)
{
    memcpy(pkt, in, sizeof(struct XProtocol));   /* 定长头，一次读满 */
    pkt->cmd_type = ntohs(pkt->cmd_type);
    pkt->state    = ntohs(pkt->state);
    pkt->data_len = ntohl(pkt->data_len);
    if (pkt->data_len > MAXLEN_DATA) return -1;
    memcpy(name, pkt->name, sizeof(pkt->name));  /* 定长 32，尾部未必有 \0 */
    name[sizeof(pkt->name) - 1] = '\0';
    memcpy(payload, pkt->data, pkt->data_len);
    return 0;
}

htons 漏掉的表现很有特征：端口写的 8888，实际连 22543；data_len 写的 20，服务端读成 335544320。看到这种数量级离谱的值，先查字节序，别查逻辑。

__attribute__((aligned(4))) 是为了让 uint32_t 对齐到 4 字节边界。两端编译器一致时它不改变布局，但跨架构时，结构体里塞指针或者不同类型会是灾难。协议结构体只用定长整型和定长数组，不上指针、不上 size_t，这条守则能免掉一半的兼容问题。

发送侧还要处理「一次没发完」。TCP 是字节流，send 返回的字节数小于请求的字节数，是完全正常的：

c
int send_all(int fd, const void *buf, int len)
{
    const char *p = (const char *)buf;
    int sent = 0, n;

    while (sent < len)
    {
        n = send(fd, p + sent, len - sent, 0);
        if (n <= 0)
            return -1;
        sent += n;
    }
    return sent;
}

接收侧对应一个 recv_all，按头部定长读满 sizeof(struct XProtocol)，再用 data_len 判断载荷是否完整。recv 返回 0 是对端关闭，返回 -1 是出错，两个分支要分开写，别都 break。

八、C/S 架构下的数据流 #

把一次「查单词」拆开，看得最清楚。

序 谁 动作 数据
1 客户端 读键盘输入，组包 cmd_type=REQ_QUERYWORD，data="apple"
2 客户端 send_all 发出整包 定长 1064 字节
3 服务端 recv_all 读满头部 解出 cmd_type、data_len
4 服务端 业务校验 state 里没登录就回 RTL_USEROFFLINE
5 服务端 查库 select meaning from dict where word=?
6 服务端 组包 cmd_type=RPL_QUERYWORD，state=RTL_SUCCESS
7 服务端 写历史 insert into history(word,name) values(?,?)
8 客户端 收包、拆包 按 state 分支显示
9 客户端 未命中 显示 RTL_NOFINDWORD 对应的提示

第 4 步是架构的分界线。校验在服务端做，客户端只负责显示。客户端把「密码对不对」算出来再告诉服务端，等于没做鉴权。

服务端要同时接多个客户端。两个路子：多线程，或者 select 单线程轮询。先看单线程的。

select 解决的是「一个进程怎么同时盯多个套接字」。fd_set 就是要检测的文件描述符的集合。

c
int select(int n, fd_set *read_fds, fd_set *write_fds,
           fd_set *except_fds, struct timeval *timeout);

一次监听多个套接字，只要有一个套接字的数据发生变化，函数立刻返回。

  • n：所有被监听的套接字里最大的那个描述符值加 1。
  • read_fds：读集合。有数据可读的描述符会被置位。
  • write_fds：写集合。可写时置位。
  • except_fds：异常集合。
  • timeout：NULL 一直阻塞；指向 0 值的时间结构表示非阻塞立即返回；非零值表示超过这个时间还没有数据变化就返回。

返回值大于 0 是发生变化的描述符个数，等于 0 是超时，小于 0 是出错。

四个操作集合的宏：

c
void FD_ZERO(fd_set *fdset);              /* 清空整个集合 */
void FD_SET(int fd, fd_set *fdset);       /* 把 fd 加入集合 */
void FD_CLR(int fd, fd_set *fdset);       /* 把 fd 从集合中清除 */
int  FD_ISSET(int fd, fd_set *fdset);     /* 判断 fd 是否还在集合中 */

FD_ISSET 有个细节必须记住：数据发生变化的描述符会被从集合里删掉，所以剩下还在集合里的，就是没动静的。这正是为什么每次 select 之前都要重新从模板集合复制一份。

服务端骨架：

c
fd_set global_rdfs, current_rdfs;
int maxfd, listenfd, connfd, i;

FD_ZERO(&global_rdfs);
FD_SET(listenfd, &global_rdfs);
maxfd = listenfd;

while (1)
{
    current_rdfs = global_rdfs;              /* 每轮都要重置 */
    int n = select(maxfd + 1, &current_rdfs, NULL, NULL, NULL);
    if (n <= 0)
        continue;

    for (i = 0; i <= maxfd; i++)
    {
        if (!FD_ISSET(i, &current_rdfs))
            continue;

        if (i == listenfd)                   /* 监听套接字有动静 = 新连接 */
        {
            connfd = accept(listenfd, NULL, NULL);
            FD_SET(connfd, &global_rdfs);
            if (connfd > maxfd)
                maxfd = connfd;
        }
        else                                  /* 连接套接字有动静 = 有数据 */
        {
            char buf[1024];
            int len = recv(i, buf, sizeof(buf), 0);

            if (len <= 0)
            {
                FD_CLR(i, &global_rdfs);
                close(i);
                continue;
            }
            /* 处理请求，回发响应 */
        }
    }
}

三个易错点在代码里已经埋着了：current_rdfs 每轮必须重置，maxfd 只增不减，accept 出来的 connfd 要更新 maxfd。少一条，表现都是「第一个客户端正常，第二个连上没反应」。

监听套接字只在有新连接时才有动静，它本身不传数据。连接套接字才传数据。把这两类描述符混在一个分支里处理，是另一个常见错误。

退出的时机也要分清：监听套接字不关，程序就一直能接新连接；连接套接字关了，只影响那一个客户端。

客户端侧反而不需要 select。要同时收发，最简单的做法是双线程：

c
/* 主线程：一直读键盘、发包 */
while (1)
{
    fgets(buf, sizeof(buf), stdin);
    send_all(sockfd, buf, strlen(buf));
}

c
/* 子线程：一直收包、打印 */
void *recv_thread(void *arg)
{
    int fd = *(int *)arg;
    char buf[1024];

    while (recv(fd, buf, sizeof(buf), 0) > 0)
        printf("%s\n", buf);

    return NULL;
}

两个线程一个 send 一个 recv，代码短，理解成本低。代价是并发写同一个 buf 要加锁，退出时的线程回收要写对。

单线程也能做，靠 select 同时盯标准输入和套接字，课程项目里那份 server/client 就是这么做：

c
FD_ZERO(&rfds);
FD_SET(0, &rfds);          /* 标准输入 */
FD_SET(sockfd, &rfds);     /* 连接套接字 */
maxfd = sockfd > 0 ? sockfd : 0;
tv.tv_sec = 5;
tv.tv_usec = 0;

retval = select(maxfd + 1, &rfds, NULL, NULL, &tv);
if (retval == -1)
    perror("select");
else if (retval == 0)
    printf("没有输入也没有消息，继续等\n");
else
{
    if (FD_ISSET(0, &rfds)) { /* 键盘有输入 */ }
    if (FD_ISSET(sockfd, &rfds)) { /* 网络有数据 */ }
}

这段里 maxfd 那个三目运算是为了兼容 sockfd < 0 的情况，实际正常流程用不到。tv 每轮都要重设，select 返回后会把剩余时间写回 tv，不重置就变成「第二次卡 4 秒、第三次卡 3 秒」。

非阻塞也能用，open 时带上标志就行：int fd = open("test", O_NONBLOCK);。标志位是位掩码，可以按位或：

text
0000 0001  READ_ONLY
0000 0010  NONBLOCK

READ_ONLY | NONBLOCK 得到 0000 0011。判断某一位有没有置上，用与运算：if (flag & NONBLOCK)。

文件描述符上的异步信号是 SIGIO，数值 29，要配 sigaction 装处理器。它比 select 省 CPU，代价是一个信号来了你不知道是哪个 fd。课程项目里用 select 或线程就够。

socket 这个手段在整个进程通信家族里的位置，一张表看清：

方式 范围 特点
管道 pipe / fifo 同一台机器，有亲缘关系的进程 单向字节流，简单
信号 同一台机器 异步打断，只能传一个整数值
sigaction 同一台机器 装信号处理器，可带上下文
sem 信号灯 同一台机器，线程或进程 IPC 的 P/V 操作，做同步
共享内存 同一台机器 最快，要自己配信号灯保护
消息队列 同一台机器 有边界，按类型取
syslog 日志 不是通信手段，是投递通道
socket 不同主机上两个进程 跨机器，走协议栈

域套接字是 socket 的变体，地址用文件路径，不走协议栈，省资源。同一台机器上客户端和服务端分两个进程时，用它比走 127.0.0.1 快一点，缺点是不能跨机器，项目部署到板子上就没法用。

dict word、meaning apple / 苹果
history word、name a / peng、b / peng

history 表没有主键也行，同一个词查两次就两行，这正好是「历史记录」该有的样子。要按时间倒序显示，就再加一个自增 id 或者时间列。

功能对应到命令，一条请求配一条响应，全部用第七章那套结构体：

功能 请求 响应 主要状态码
注册 REQ_REGISTER RPL_REGISTER RTL_SUCCESS、RTL_USEREXIST、RTL_INSERTERR
登录 REQ_LOGIN RPL_LOGIN RTL_RIGHTPASSWD、RTL_WRONGPASSWD、RTL_USERONLINE、RTL_NUSEREXIST
查词 REQ_QUERYWORD RPL_QUERYWORD RTL_SUCCESS、RTL_NOFINDWORD、RTL_DBERR
查历史 REQ_HISTORY RPL_HISTORY RTL_SUCCESS、RTL_NOHISTORY、RTL_HISTORYOVER
退出登录 REQ_EXIT — 服务端把 isonline 置 0
修改信息 登录后的一条 REQ_ RPL_ RTL_SUCCESS、RTL_DBERR

服务端还要有两个管理员用的功能：查看用户信息、查看在线用户。这两件事不做成协议命令，直接查库，或者只在服务端本地打印。

sql
-- 在线用户
select name from user where isonline=1;

-- 全部用户
select name, sex, isonline from user;

数据库表的格式要提前定死，因为服务端和客户端是两个人在写，字段错一位就是联调一天。定完之后，sql.c 里的建表语句就是这个格式的唯一来源。

dict 表的数据从词库转过来。词库原本是个文本文件，一行一个词加释义，中间用制表符或者固定宽度分隔。转换的活交给一个脚本，或者在 db_open() 之后跑一次导入函数，转完就不用再管。别在运行期每次查词都去读文本文件，那样数据库就没意义了。

扩展部分也写清楚了，有余力再做：聊天功能，公聊、私聊、在线用户列表、离线消息推送。公聊是一条消息群发所有连接套接字，私聊是按 name 找到对应的 connfd 再发，离线消息要落库，等对方登录再推。这四个功能全建在 user 表和 isonline 字段上，前面的架构不用改。

十、从需求到实现的拆解 #

题目看着大，拆成七步就不吓人。这七条技巧本身就是一份施工顺序。

步 做什么 完成标志
1 先把框架搭起来 客户端和服务端能正常收发数据包，内容先不管
2 先写一个功能，注册 能注册成功、能报「用户已存在」
3 加入数据库操作 注册的信息进库，重开进程还在
4 补齐登录、查词、查历史 五个功能全通
5 每天备份代码 前一天能跑，今天改崩了能回退
6 编译错误太多时，把没调通的功能先注释掉 用 #if 0 / #endif 整块屏蔽
7 守住编程规范 函数名英文单词，不用拼音

第 1 步最容易被跳过。很多人一上来就写注册，注册里又要查库又要回包，一出错三个方向一起查。正确做法是先用一个空协议包来回打一遍：

c
/* 服务端收到什么就回什么，只为验证链路 */
int len = recv(connfd, buf, sizeof(buf), 0);
if (len > 0)
    send_all(connfd, buf, len);

这段代码通了，说明套接字、协议结构、长度字段全对。后面加功能才有地基。

第 6 步的 #if 0 是实用技巧。编译错误几十条，往往来源于一个没写完的函数。整块屏蔽，让它先编过，一个一个放开：

c
#if 0
static int query_history(sqlite3 *db, const char *name)
{
    /* 没调通，先不编 */
}
#endif

注意 #if 0 只屏蔽预处理之后的代码，函数声明还在 sql.h 里的话，链接照样报错，头文件里也要同步屏蔽。

工程管理用 makefile，功能不同的代码放不同文件。一个能用的 makefile 不到二十行：

text
CC      = gcc
CFLAGS  = -Wall -g
LIBS    = -lsqlite3 -lpthread
OBJS    = server.o sql.o protocol.o
COBJS   = client.o protocol.o

all: server client

server: $(OBJS)
	$(CC) $(CFLAGS) -o $@ $(OBJS) $(LIBS)

client: $(COBJS)
	$(CC) $(CFLAGS) -o $@ $(COBJS) $(LIBS)

clean:
	rm -f server client *.o

.PHONY: all clean

server.o 和 client.o 都要链接 protocol.o，协议打包解包只有一份实现。复制粘贴两份，改了一边忘了另一边，就是「服务端能通、客户端解析错」的来源。

联调顺序按第四章那套走，落到这个项目上是四轮：

  1. 本机跑 server 和 client，都连 127.0.0.1，五个功能全通。
  2. 把 client 拷到板子上，make 出可执行文件，先 ping 通 PC。
  3. 板子上 telnet PC地址 8888，确认端口可达。
  4. 改客户端里的目标 IP，联调。行为不一致时，先怀疑字节序和对齐，再怀疑逻辑。

第 4 轮最容易出现的现象是「本机好好的，上板子全是乱码」。原因八成是结构体里混进了指针，或者没转字节序。板子是 32 位 ARM 小端，PC 是 x86 小端，字节序一致，所以问题出在对齐和长度上，逐个字段打印十六进制对一遍。

十一、易错点速查 #

把这类项目里反复出现的坑列全，出错时按现象查表。

现象 根因 动作
bind 报 Address already in use 端口被占，或上次进程没退干净 加 SO_REUSEADDR，或 netstat -anp 找占用的进程
bind 报 Cannot assign requested address bind 的地址不属于本机 改成 INADDR_ANY 或本机实际地址
本机能连，别的机器连不上 bind 成 127.0.0.1 换成 INADDR_ANY，查防火墙
connect 卡很久然后超时 防火墙丢包，或网段不对 先 ping，再查防火墙规则
connect 立刻 Connection refused 服务端没起，或端口写错 netstat -anp 确认监听
第一个客户端正常，第二个没反应 select 没重置 fd_set，或 maxfd 没更新 每轮 current_rdfs = global_rdfs
连接建立了，一直收不到数据 发送端少发，或长度字段没转字节序 打印 data_len 的原始值
收到的数字是 335544320 这种 漏了 ntohl / htons 补字节序转换，重编两端
传中文变乱码 一端按 char 有符号处理 载荷用 unsigned char，别做字符串比较
用户名尾部带一串乱码 name[32] 没清零就 strncpy memset 整包，或手动补 \0
服务端重启后登录状态全错 退出没把 isonline 置 0 每个断开分支都要更新库
历史记录显示不全 没有结束标记，客户端提前退出循环 发 RTL_HISTORYOVER
密码框输入 ' or '1'='1 就登录成功 拼 SQL 字符串 改成 prepare + bind
查库返回 NULL 时崩溃 回调里 f_value[i] 有时是 NULL 取值前判空
内存一直涨 errmsg / result 没释放 sqlite3_free、sqlite3_free_table
每次 make 都全量重编 头文件依赖没写 加 -MMD -MP，或先不管
编译报一堆未定义符号 .c 里调了别处的函数，头文件没声明或没链接 查 makefile 的 OBJS

前三行全是网络层的事，压根不归代码管。这也是为什么排错要从 ping 开始。我们把这句再放一次：跨设备通不了，先证明网络通，再证明端口通，最后才动代码。

网络打通之后，剩下的事就是协议和数据库。协议定好一个结构体，命令和状态码提前定义齐，服务端做校验、做查库、做组包，客户端只发请求和显示结果。这个结构撑得住电子词典，也撑得住后面任何一个 C/S 小项目。
