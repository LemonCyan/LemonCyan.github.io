这一篇只讲网络里的实体和排错手法：路由器怎么定位、怎么转发，网卡怎么收怎么发，ARP 表怎么建，超时怎么等，出问题从哪一步开始查。

不讲套接字的编码细节，也不讲字节序。分层模型与封装解封装在《网络通信原理与分层模型》，htons/htonl 与地址结构体在《套接字与网络字节序》。再往外，setsockopt 的全部选项、IO 多路复用的实现、抓包文件的解析，分别落在父目录的套接字选项、IO 模型、协议分析几组里。

一句话定位：本篇是把「分层」从纸面搬到机房里——看每一层用的是哪个头部，就知道设备是谁、故障在哪一段。

一、路由器在分层模型里的位置 #

先纠一个名字。OSI 在计算机网络里指 开放系统互连参考模型（Open System Interconnection Reference Model，OSI/RM），由 ISO 提出，不是那个同名的开源组织。七层模型的作用是把「不同系统、不同网络之间如何可靠传数据」拆成七件可以分别讨论的事。

拆完的第一个好处：设备能分类了。

中继系统是完成中继功能的节点。判断一个设备工作在几层，只看一件事——它转发时依据哪一层的头部。网桥靠 MAC 头部决定从哪个口出去，那它就是数据链路层设备；路由器靠 IP 头部查表决定下一跳，那它就是网络层设备。这条判据比背设备名录管用。

层次 数据单位 转发依据 典型设备 代表协议/规范
物理层 比特 bit 电平、引脚、速率 网卡、网线、集线器、中继器、调制解调器 RS-232、RS-449、V.35、RJ-45
数据链路层 帧 frame MAC 头 网桥、二层交换机 SDLC、HDLC、PPP、STP、帧中继
网络层 数据包 packet IP 头 路由器 IP、IPX、RIP、OSPF
传输层及以上 段/报文 端口号、应用语义 网关（四层及以上） TCP、UDP

物理层 #

物理层规定通信设备的机械、电气、功能、过程四类特性，用来建立、维护、拆除物理链路。

机械特性管接插件的规格尺寸、引脚数量与排列；电气特性管线路上信号电平大小、阻抗匹配、传输速率与距离限制；功能特性给各条线路分配确切的信号含义，即定义 DTE 与 DCE 之间每根线的功能；过程特性定义用信号线传比特流的一组操作规程，也就是链路建立、维护、交换信息时双方在各电路上的动作序列。

这一层的数据单位是比特。功能上分三块：

  1. 提供传送数据的通路。通路可以是一段物理媒体，也可以是多段拼接。一次完整传输包含激活物理连接、传送数据、终止物理连接；激活指的是不管中间有多少段媒体，都要在两个数据终端设备之间接通成一条路。
  2. 传输数据。要形成适合传输的实体，一是保证数据能正确通过，二是提供足够带宽（每秒钟能通过的比特数）来减少拥塞。传输方式要能覆盖点到点、一点到多点、串行与并行、半双工与全双工、同步与异步。
  3. 完成物理层自身的管理工作。

主要设备是中继器和集线器。集线器把收到的电信号向所有口复制一份，它不看 MAC，也不看 IP，所以它连冲突域都不隔离。

数据链路层 #

在物理层提供的比特流之上，链路层建立相邻节点之间的数据链路，通过差错控制让帧在信道上无差错传输。它在不可靠的物理介质上提供可靠的传输，做的是物理地址寻址、数据成帧、流量控制、检错、重发。

这一层的数据单位是帧。功能有四条：

  • 链路连接的建立、拆除、分离。
  • 帧定界与帧同步。不同协议帧长和界面不一样，但帧必须能定界，否则收方不知道一帧从哪开始到哪结束。
  • 顺序控制，即对帧的收发顺序做控制。
  • 差错检测与恢复。差错检测多用方阵码校验、循环码校验来发现信道误码，帧丢失这类问题用序号检测，恢复靠反馈重发。

协议代表是 SDLC、HDLC、PPP、STP、帧中继。主要设备是二层交换机和网桥。

网络层 #

两台计算机通信，中间会经过多条数据链路，还会穿过多个通信子网。网络层的任务是选择合适的网间路由与交换节点，把数据及时送到。它把链路层交上来的帧拆成数据包，包里有网络层包头，包头带着逻辑地址——源站与目的站的网络地址。

这一层的数据单位是数据包。功能清单：

  1. 路由选择与中继。
  2. 激活、终止网络连接。
  3. 在一条数据链路上复用多条网络连接，多采用分时复用。
  4. 差错检测与恢复。
  5. 排序、流量控制。
  6. 服务选择。
  7. 网络管理。

要落地这些功能，网络层得解决四个问题：

问题 内容
寻址 链路层的 MAC 只解决网络内部寻址。跨子网通信时每个子网内的设备要有一个唯一地址，各子网物理技术不同，这个地址得是逻辑地址，比如 IP
交换 规定信息交换方式。常见是线路交换与存储转发，后者又分报文交换与分组交换
路由算法 源与目的之间有多条路径时，按算法选出最佳路径
连接服务 与链路层的流量控制不同：前者管相邻节点之间，这里管源到目的的端到端流量，用来防阻塞并做差错检测

协议代表是 IP、IPX、RIP、OSPF。主要设备就是路由器。

路由器与交换机的分工 #

这段是全篇的地基。

路由器是三层设备，交换机是二层设备。 路由器按 IP 转发，每过一跳都要把 MAC 头拆掉重写；交换机按 MAC 转发，从头到尾不看 IP。交换机心里的世界是一张「MAC 地址 → 端口」表，路由器心里的世界是一张「目的网段 → 下一跳」表。

由此推出来的差别，一条条对得上：

对比项 二层交换机 路由器
工作层次 数据链路层 网络层
转发依据 目的 MAC 目的 IP
维护的表 MAC 地址表（MAC → 端口） 路由表（网段 → 下一跳/出接口）
是否改帧头 不改，原帧转发 改，拆掉旧 MAC 头，按出接口重封装
广播域 不隔离（除非划 VLAN） 隔离，路由器不转发广播
冲突域 每个口一个冲突域 每个口一个冲突域
典型用途 同一网段内接入 网段之间互联、出口

为什么路由器必须改 MAC 头：以太网帧的源和目的 MAC 只在本地链路有意义，帧过一跳就作废。IP 包才是端到端不变的东西。所以「IP 不变、MAC 每跳都变」——这一句能解释抓包时看到的大部分现象。

数据链路层解决同一网络内节点之间的通信，网络层解决不同子网之间的通信。广域网里通信必然会碰上路由选择问题（两个节点之间有多条路径），这就是三层存在的理由。

网关工作在第四层传输层及其以上，它看端口号、看应用语义，这也是它和路由器最容易混的地方：路由器只看到 IP 头就转发，网关要看到 TCP/UDP 头甚至载荷才动手。

二、路由器的工作原理 #

为什么需要把网络连起来 #

网络的目的很朴素：让人交换信息。可需求是分裂的——有人要高带宽不在乎距离，有人要长距离不在乎带宽，有人盯着可靠性，有人只要便宜。需求一分岔，网络就长成了好几个样子：局域网有以太网、令牌环、FDDI，广域网有 DDN、X.25、帧中继、ATM。

这些网的物理介质和协议都不一样，彼此直接连不上。把它们连起来、让不同网上的用户能换信息，这套技术叫网络互联。实现方式有两条路：

路线 做法 代表
协议转换 在某一层把一种协议翻译成另一种 TCP/IP、Novell IPX
隧道 不翻译，把整包原样套进另一层协议里运走 VPN

IPX 曾经很红，现在网络互联说了算的是 TCP/IP——Internet 本身就是 TCP/IP 做互联协议的实例。路由器是协议转换技术的设备形态，VPN 是隧道技术的形态。

路由器是一台专用计算机 #

路由器实质上是一台把网络互联起来的专用计算机，在 TCP/IP 语境里又叫 IP 网关。它的软件结构以 TCP/IP 协议栈为核心，上面跑路由协议，下面挂各个物理接口的驱动。

协议转换发生在 IP 层。举个完整的例子：一台以太网主机要访问 Internet，局域网上是 IEEE 802.2/802.3 以太网，路由器和接入服务器之间是专线、链路层跑 PPP，两侧的网络层都是 IP。

text
主机               路由器                        接入服务器
  |                  |                              |
  |-- 以太网帧 ----->|                              |
  |   (IP 包在里面)  |  1. 收帧，处理帧头            |
  |                  |  2. 上交 IP 层                |
  |                  |  3. 查 IP 头，选出口          |
  |                  |  4. IP 包交给广域网口的 PPP   |
  |                  |-- PPP 帧（IP 包在里面）----->|
  |                  |                              |  5. 拆 PPP，取 IP

按步骤看更清楚：

  1. 主机把 IP 包封装在以太网帧里发向路由器。
  2. 路由器的以太网口收到帧，处理帧头，把载荷上交到 IP 层。
  3. IP 查报文头（目的地址），决定从哪个口出去。
  4. IP 包交给广域网口的 PPP，PPP 把它封装进 PPP 帧。
  5. PPP 帧通过专线发往接入服务器。
位置 链路层封装 网络层
主机到路由器以太网口 以太网帧 IP
路由器内部 拆掉以太网帧头 IP 原样
路由器广域网口到接入服务器 PPP 帧 IP 原样

这条链路里 IP 包一字未改，被拆掉又重装的只有链路层帧头。这就是「路由器改 MAC 头、不改 IP」的实物版。

一条普遍规律 #

某种网络设备要在第 n 层上互联异种网 N1 和 N2，那么 N1 和 N2 在第 n 层及以上的协议必须相同。这既是条件，也是充要条件。

拿路由器套一遍：它在第三层互联，所以两侧网络层及以上必须都是 IP；链路层可以完全不同——一边是以太网，一边是 PPP，路由器照转。反过来，如果一侧跑 IP、另一侧跑 IPX，路由器在 IP 层就没法翻译，得换别的设备。二层交换机在第二层互联，要求两侧链路层帧格式相同（都是以太网），网络层它不管，IP 和 IPX 都能过。

多穴主机 #

IP 地址标识一台工作在 IP 层的网络设备。在一个互联起来的网络里 IP 地址要唯一，一个地址不能同时给多台设备用。但 TCP/IP 允许一台设备占多个 IP 地址，这种设备叫多穴主机。

路由器就是典型的多穴主机：每个端口一个 IP 地址，甚至一个端口可以配多个 IP 地址。这就解释了为什么路由器上的地址总是按口来配——出口地址、内口地址是两套。

主机凭什么把包交给这台路由器 #

以太网上有多台主机和多台路由器，主机怎么知道去 Internet 的报文交给谁？路由器有多个广域网口、每个口连一台接入服务器，它又怎么知道发给哪一台？

答案是寻址加路由机制。主机靠路由表里的默认网关决定交给谁，路由器靠自己的路由表决定下一跳。两者用的是同一套逻辑，只是表的规模不同。

广域网口的验证 #

专线拨号这类链路上，PPP 提供验证功能，两种方式：

方式 密码形式 方向 时机
PAP 明文 单向 只在协商开始时验证一次
CHAP 密文 相互验证 传输过程中随时验证

PAP 把密码明文扔上线，链路上抓包就能看到，能用 CHAP 就别用 PAP。

隧道的形态 #

VPN 的目的是用较少的钱拿到私有网的服务。它用 Internet 上的隧道技术，把 PPP 包封装进 UDP 包传送。分支访问中心，传统选择是 DDN 或电话网，两者都相当于自建私有网络，方便但贵。

ISP 提供的 VPN 服务是另一条路：ISP 在 Internet 里建一条隧道，把自己的接入服务器和中心的路由器（或服务器）连起来。分支发来的 PPP 报文，ISP 收到后不解析，直接塞进隧道送到中心。Internet 从此成了一条从分支到中心的虚拟私有线路，用户付的是两端本地通信费加 Internet 访问费，比长途电话费或 DDN 费用低得多。

「不解析」是隧道的关键动作：中间设备只当搬运工，不关心里面装的是什么协议。这也是隧道能跨越异构网络的原因——它绕开了协议转换。

三、路由表与转发 #

地址与掩码 #

IP 地址长四字节，TCP/IP 把它划成 A、B、C 三个基本类（D 类和 E 类很少用到）。地址分网络部分和主机部分，作用相当于电话号码里的局号和用户线号。书写用点分十进制，比如 129.102.1.56——129.102 是北研所局域网的网络号，属 B 类网，1.56 是主机号。RFC 不推荐把 0 作为某个字节，比如 129.102.1.0 这种写法要避开。

掩码用来做非标准划分（与三个基本类不同）。掩码写成二进制，IP 地址中与掩码「1」对应的比特属网络部分，与「0」对应的属主机部分。习惯也表示成点分十进制。用基本划分时 A 类掩码 255.0.0.0，B 类 255.255.0.0，C 类 255.255.255.0。

拿 129.102.1.56 试两种掩码：

掩码 网络部分 主机部分
255.255.0.0（基本掩码） 129.102 1.56
255.252.0.0 129.100 2.1.56

掩码里的「1」可以不是连续的，但既没必要又费劲，RFC 也不推荐。

一条路由长什么样 #

一条路由主要包括目的地址和下一跳两部分。

目的（记作 D）可以是一台主机、一个网络，也可以是某个网络的一个子集。下一跳（记作 N）是 next-hop 的直译，理解成「下一个驿站」更形象。整条路由表达的意思就一句：要去 D，先到 N。「经北京去美国」就是一条路由。

目的由「IP 地址 + 掩码」组成一个复合成员：

  • 掩码全 1（255.255.255.255）的路由叫主机路由，目的地是一台主机。
  • 掩码不是全 1 的路由，目的地是某个网段或子网。

按下一跳的性质分两类：

类型 下一跳 含义 例子
直接路由 不是路由器，就是本口直连的网段 目的地就在这个接口所在的链路上，直接发 路由器以太网口接在局域网上，启动后自动生成一条目的为该以太网的路由，不用手配、不用跑协议
间接路由 一台路由器 要经别人转发 去 Internet 的默认路由

直接路由理解起来别扭，换成出行类比就顺了：人在北京要去美国，北京有直飞美国的航班，不需要中转——这就是直接路由。

路由从哪来 #

获取方式两种：手工配置的静态路由，路由协议学来的动态路由。

静态路由用于规模较小、相对稳定的网络。网络规模大或经常变动（经常增减网络、主机），就得上路由协议。

协议 算法 说明
RIP DV（距离矢量） 常见的老协议，跳数作度量
IGRP DV Cisco 私有
EIGRP DV Cisco 私有，IGRP 的增强版
OSPF LS（链路状态） 开放标准，规模大的网常用

路由表字段 #

字段 含义 排错时看什么
目的网络/掩码 这条路由覆盖的范围 掩码对不对，有没有写窄或写宽
下一跳 交给谁 下一跳可达吗，是不是自己
出接口 从哪个口发 口 up 了吗，是不是接反了
度量值 走这条路的代价 多路径时选谁
来源/优先级 静态、直连还是某个协议学的 谁把这条路由盖掉了

转发动作 #

收到一个包，路由器做四件事，顺序固定：

text
取目的 IP
  → 在路由表里找匹配项（同一目的常有多条匹配）
  → 取掩码最长的那条（最长前缀匹配）
  → 按该条目的出接口重封装链路层帧头，从口发出
  → 一条都不匹配就丢弃，回 ICMP 不可达

最长前缀匹配是查表的核心：目的 192.168.10.5，表里同时有 192.168.0.0/16 和 192.168.10.0/24，选 /24。默认路由 0.0.0.0/0 是兜底，掩码长度 0，永远排最后。

「一条都不匹配就丢弃」这条能解释一类怪现象：ping 不通但没有报错，或者浏览器一直转圈——包在中间某台路由器上被静默丢了，因为那台机器上没有回去的路由。

配置的顺序 #

所有路由器的《用户手册》都会讲配置方法，框架是通用的三步：

  1. IP 地址：每个要使用的端口都要配。
  2. 线路：专线方式要配波特率；拨号方式复杂些，模拟拨号除了物理属性（异步、modem、波特率）还要配 IP 地址与电话号码的对应关系。
  3. 路由：地址和线路属性都好了才能配路由。跑动态路由，把协议打开即可；配静态路由，先画组网草图，标出各网络地址和所有相关路由器的各端口地址，再对着草图逐台配置。

命令行界面把配置状态分四级，以 Quidway 为例：

级别 进入方式 能干什么
用户态 登录后即在 只有少数简单命令
特权态 enable 非配置类命令，比如打开调试开关
全局配置态 configure 配全局参数，比如配置路由
端口配置态 从全局态进某个端口 配 IP 地址这类端口特有属性

记住这四级的名称和意义不只是为了敲命令——跟项目组沟通时，说「我在全局配置态」比说「我进了那个界面」省一半时间。

出口上还做两件事 #

地址转换（NAT）。地址代理的另一个名字就是地址转换，它建立 IP 地址与传输层端口的映射。

内网 PC（129.102.1.56）访问远端 WWW 服务器（9.9.9.9），发出报文（9.9.9.9, 80; 129.102.1.56, 5000），四个成员依次是目的地址、目的端口、源地址、源端口。经过路由器转换后变成（9.9.9.9, 80; 202.38.161.1, 10000）——源地址换成了路由器广域网口的地址。为保持一一对应，源端口也一起改了。回文（202.38.161.1, 10000; 9.9.9.9, 80）到达后做反向替换，还原成（129.102.1.56, 5000; 9.9.9.9, 80），这个报文就能被 IP 正确送到内网 PC。

做这些事，路由器得维护一张 IP 地址与端口号的对应表。表项有存活时间，超时回收——这跟 ARP 缓存是一个思路。

外部主动访问内网的 WWW 服务器（129.102.1.5）就反过来了：外部发来的报文目的地址不能直接填 129.102.1.5，得填 202.38.161.1，否则报文到不了路由器。那路由器怎么知道把报文转给谁？靠配置。这个例子里，要把 129.102.1.5 配成本地的 WWW 服务器。这就是端口映射的由来。

按规则过滤。防火墙是安全措施之一，分两种：

类型 检查什么 能做什么
包过滤 源地址、目的地址、源端口、目的端口 实现「禁止 129.102.1.56 被访问」这类简单规则
应用网关 报文内容 管得更细，能对载荷内容做限制

抓包时看到「TCP 握手都没开始」，先怀疑包过滤；看到「握手成功但内容不对」，往应用网关上想。

四、网卡的角色 #

网卡站在物理层和数据链路层中间。往上它给协议栈递帧，往下它把比特推上电线。抓包里看到的 MAC 头、FCS，都是它管的活。

发送 #

  1. 网络设备驱动从上层协议栈拿到 sk_buff。
  2. 取出载荷数据与长度，放进临时缓冲区（DMA 缓冲）。
  3. 以太网要求帧最小 64 字节，不足就在尾部补 0。
  4. 设置硬件寄存器，启动发送。
  5. 发送完成中断里回收缓冲区、更新统计。

第 3 步是最容易吃亏的地方：小包要补齐到 64 字节，补的是尾部 0，不是真实数据。用 tcpdump 抓到一个 60 字节的帧是正常的（不含 FCS），不是驱动有 bug。

接收 #

  1. 由中断触发——收到包，网卡拉中断。
  2. 中断处理程序判断中断类型，是接收中断就把数据读进 sk_buff。
  3. 把 sk_buff 通过 netif_rx / NAPI 上抛给上层协议栈。
方向 触发方式 关键缓冲 谁干活
发送 协议栈调用驱动 DMA 缓冲 驱动 + 硬件寄存器
接收 硬件中断 sk_buff 中断处理程序（上半部），随后交给软中断/NAPI 轮询

这就是「中断上半部只管把数据搬走，协议栈处理放到软中断或 NAPI 轮询」的由来。高速收包时如果每包一次中断全处理完，CPU 就全耗在中断上下文里，业务线程拿不到时间片。NAPI 的做法是：第一个包用中断通知，随后关中断改轮询，一次捞一批。

读这段代码的人常问：sk_buff 是不是零拷贝？不是。数据在 DMA 缓冲和 sk_buff 之间要搬一次，真正的零拷贝要在更上层用 mmap 或 sendfile 这类手段绕开。

网卡在分层里的边界 #

动作 网卡做不做
加/去 MAC 头 做
算/校验 FCS 做（多由硬件完成）
补齐最小帧 做（发送方向）
判断是不是发给自己 做（过滤目的 MAC，混杂模式除外）
看 IP 头 不做
查路由表 不做

「网卡不看 IP」这条决定了混杂模式的价值：把网卡设成 promisc，它就不再按目的 MAC 过滤，链路上所有帧都收上来，抓包才有得看。

看网卡的计数 #

排查链路问题时，网卡统计是最先该看的东西之一：

bash
ip -s link show eth0

四组计数各有含义：

计数 涨了说明什么
RX errors 收方向出错，线缆、光模块、双工不匹配
RX dropped 收上来但缓冲区不够，被丢掉，CPU 跟不上
TX errors 发方向出错，多半是链路层协商问题
TX dropped 发送队列满，出口带宽打满

RX dropped 一直涨而 RX errors 不动，是典型的「包来了但没人收得及」，把锅甩给 CPU 或应用，别甩给网线。

五、ARP：IP 到 MAC 的映射 #

为什么非要 ARP #

IP 地址属于高层地址，物理层只能靠物理地址通信。数据发送者拿着接收者的 IP 地址，怎么找到它对应的物理地址？

如果发送者和接收者在同一个物理网上，两条路：用地址解析协议（ARP，Address Resolution Protocol）自动问，或者手工配置。如果不在同一个物理网上，就需要路由。

ARP 用于共享式网络，比如以太网。它的原理一句话：IP 是逻辑地址，真正上线传输还得靠 MAC，ARP 就是这座桥。

工作方法 #

  1. IP 把要发送的报文交给以太网链路层，同时告诉链路「这个报文要转给哪个 IP」，记作 A。
  2. 链路用以太网广播帧的形式向本网询问：谁是 A。
  3. A 收到 ARP 请求后，回答自己的物理地址，记作 P。
  4. 发送者收到 ARP 响应后，把 IP 报文发给 P。

设备可以用缓存提速：只有缓存里查不到的才发 ARP 请求，收到回答后把学到的物理地址插进缓存。为适应网络变化，缓存要有时限，超时后失效。

同网段问目的主机，跨网段问网关 #

这是 ARP 最容易讲错的一点，也是最该记牢的一点。

发包之前，主机先拿目的 IP 和自己的掩码做判断：

  • 目的 IP 在本网段 → ARP 请求里问的是目的主机的 IP。
  • 目的 IP 不在本网段 → ARP 请求里问的是默认网关的 IP。

为什么跨网段不能直接问目的主机？因为 ARP 请求是广播帧，广播不出网段。路由器不转发广播，你在 192.168.1.0/24 里喊「谁是 8.8.8.8」，没人应答，包就卡在第一步。

场景 ARP 请求里的目标 IP 帧的目的 MAC IP 包的目的 IP
同网段 目的主机 IP 目的主机 MAC 目的主机 IP
跨网段 网关 IP 网关 MAC 目的主机 IP

看第三列和第二列的落差：IP 包的目的地址始终是最终目标，帧的目的 MAC 只到下一跳。 这就是「IP 端到端、MAC 逐跳」在 ARP 层的表现。

抓包时看到一个包的目的 IP 是 8.8.8.8，目的 MAC 是网关，不要怀疑抓错了——这就是正常行为。

不能跑 ARP 的网络怎么办 #

手工配置主要用于不能运行 ARP 的非共享式网络。比如 2501 上要配 Dialer map，把 IP 地址与电话号码对应起来，这里的电话号码相当于电话网里的物理地址。X.25 网、帧中继网也一样，得手工把 IP 地址和物理地址匹配上。

道理不复杂：ARP 靠广播，点到点或虚电路网络没有广播这个概念，只能人工填表。

ARP 报文长什么样 #

text
0        8        16                31
+--------+--------+-----------------+
| HTYPE  | PTYPE  |  HLEN |  PLEN    |
+--------+--------+-----------------+
| OPER(1=请求 / 2=应答)              |
+------------------------------------+
| 发送端 MAC（6 字节）                |
+------------------------------------+
| 发送端 IP（4 字节）                 |
+------------------------------------+
| 目标 MAC（请求时全 0，应答时填实）   |
+------------------------------------+
| 目标 IP（4 字节）                   |
+------------------------------------+

两个字段值得盯：OPER 为 1 是请求、2 是应答；请求包里目标 MAC 全 0，因为问的人本来就不知道。

六、ARP 表的建立与查询 #

表是怎么来的 #

每台主机都会在自己的 ARP 缓冲区里建一个 ARP 列表，表示 IP 地址和 MAC 地址的对应关系。这张表不是配出来的，是用出来的。

完整流程：

步骤 动作 谁做
1 查自己的 ARP 列表里有没有该 IP 对应的 MAC 源主机
2 有，直接把数据包发到这个 MAC 源主机
3 没有，向本地网段发一个 ARP 请求广播包 源主机
4 广播包里带源主机 IP、硬件地址、目的主机 IP 源主机
5 网上所有主机收到后检查目的 IP 是否与自己一致 全部主机
6 不一致就忽略 其他主机
7 一致则把发送端的 MAC 与 IP 写进自己的 ARP 列表，已存在就覆盖 目的主机
8 向源主机发 ARP 响应，告诉对方自己的 MAC 目的主机
9 源主机收到响应，把目的 IP 与 MAC 写进自己的列表 源主机
10 用这条信息开始传数据 源主机

第 7 步是个常被忘的细节：回答 ARP 的那一方也在学地址。B 收到 A 的请求时，顺手就把 A 的 IP-MAC 记下了，所以 A 到 B 的第一次通信会同时把两边的表都建起来。

第 9 步之后数据才开始发，意味着第一个包要多等一个 ARP 往返。这也是为什么长连接比短连接省事——表项还在存活期内，不用重问。

查不到会怎样 #

如果源主机一直没有收到 ARP 响应包，表示 ARP 查询失败。

表现是：ping 报 Destination Host Unreachable（本机自己回的，不是对端回的），ip neigh 里该地址显示 FAILED，抓包看到 ARP 请求重发了几次然后放弃。原因无非几种：对端不在线、对端防火墙挡了 ARP、不在同一网段却硬要 ARP、VLAN 划错。

一个具体例子 #

text
A：IP 192.168.10.1  MAC AA-AA-AA-AA-AA-AA
B：IP 192.168.10.2  MAC BB-BB-BB-BB-BB-BB

A 要和 B 通信：

  1. A 需要知道 B 的以太网地址，于是 A 发一个 ARP 请求广播：谁是 192.168.10.2，请告诉 192.168.10.1。
  2. B 收到广播后检查，发现和自己一致，向 A 发一个 ARP 单播应答：192.168.10.2 在 BB-BB-BB-BB-BB-BB。
  3. A 把 192.168.10.2 → BB-BB-BB-BB-BB-BB 写进表，开始发数据。

注意请求是广播、应答是单播。应答没必要广播，问的人只有一个。

表里都有什么 #

字段 含义 例
IP 地址 逻辑地址 192.168.10.2
MAC 地址 物理地址 bb:bb:bb:bb:bb:bb
类型 动态学来的还是手工配的 dynamic / static
接口 从哪个口能到这个地址 eth0
状态 表项当前的可信程度 REACHABLE / STALE / DELAY / PROBE / FAILED
老化时间 还有多久过期 由内核参数决定

状态字段是排错的好帮手：

状态 含义 该怎么办
REACHABLE 最近确认过，可以直发 不用管
STALE 条目还在但没验证 发包时会先确认，正常现象
DELAY 正在等确认 稍等
PROBE 正在发 ARP 探测 连续停在这，多半对端不回
FAILED 解析失败 查对端、查网段、查 VLAN

查询与维护命令 #

老工具 net-tools：

bash
arp -a
arp -d 192.168.10.2                     # 删一条
arp -s 192.168.10.2 bb:bb:bb:bb:bb:bb   # 手工绑静态

新工具 iproute2：

bash
ip neigh show
ip neigh show dev eth0
ip neigh del 192.168.10.2 dev eth0
ip neigh flush dev eth0
ip neigh replace 192.168.10.2 lladdr bb:bb:bb:bb:bb:bb nud permanent

arp -a 输出里的 (incomplete) 表示请求发了没回应，和 FAILED 是一个意思。

动态表项会老化，静态表项不会。把网关的 ARP 绑成静态，是治 ARP 欺骗最土也最直接的办法——代价是网关换 MAC 时你得手动改。

七、挥手排错要点 #

状态机 #

text
  主动关闭方                        被动关闭方
  ESTABLISHED                       ESTABLISHED
      │  FIN (seq=x)                    │
      ├───────────────────────────────►│  被动方收到，通知应用进程
      │                                │
  FIN_WAIT_1                           │
      │  ACK (ack=x+1)                  │
      │◄───────────────────────────────┤
  FIN_WAIT_2                     CLOSE_WAIT
      │  FIN (seq=y)                    │
      │◄───────────────────────────────┤  被动方处理完数据后关
      │                                │
      │  ACK (ack=y+1)                  │
      ├───────────────────────────────►│
  TIME_WAIT                        CLOSED
      │  等待 2MSL
      ▼
  CLOSED

为什么是四次 #

TCP 是全双工，两个方向要各自关闭一次。ACK 与 FIN 不能像握手那样合并——被动方收到 FIN 时，它自己的数据还没发完，所以先回一个 ACK 表示「我知道你要关了」，等数据发完再补一个 FIN。合并了就等于逼它立刻闭嘴。

为什么等 2MSL #

MSL 是报文在网络中被丢弃前的最长存活时间。等 2MSL 有两个理由：

  1. 让最后那个 ACK 有机会重传。这个 ACK 丢了，被动方会重发 FIN，主动方还在 TIME_WAIT 才能再回一次 ACK；已经 CLOSED 就只能回 RST，对端会看到一个异常终止。
  2. 让本次连接的旧报文在网络中彻底消失，不会串到下一个同端口连接上。同端口的新连接如果收到上一条连接的迟到报文，序列号对不上，数据就乱了。

谁先进 TIME_WAIT #

主动关闭的一方。所以服务器端频繁短连接会出现大量 TIME_WAIT——不是 bug，是协议在保护你。这正是 SO_REUSEADDR 存在的原因：让新连接能复用处于 TIME_WAIT 的端口。

状态与故障对照 #

ss -tan 看状态分布，比看日志快得多：

状态 数量异常说明什么 往哪查
TIME_WAIT 堆积 主动关闭太频繁，短连接多 改成长连接、连接池，或调 tcp_tw_reuse
CLOSE_WAIT 堆积 收到对端 FIN，本端应用没 close() 代码漏关 fd，这是应用 bug，别怪内核
FIN_WAIT_2 卡住 本端发了 FIN，对端一直不回 FIN 对端应用不关，或对端机器挂了
SYN_SENT 大量 SYN 发出去了没有 SYN+ACK 对端没监听、被墙、路由不通
SYN_RECV 大量 收到 SYN 回了 SYN+ACK，等不到 ACK SYN flood，或本机回包出不去
ESTABLISHED 但无数据 连接活着，应用不发 应用层逻辑

CLOSE_WAIT 是最该记住的一条：它出现说明对端已经礼貌地关了，本端还把 fd 攥在手里。这个数只涨不降，代码里一定有一处 accept 之后没 close，或者异常分支 return 之前忘了关。

八、超时检测的三种方法 #

网络通信中很多操作会让进程阻塞，我们要设定时间，到点强制返回，避免进程在没有数据的情况下无限等下去。

方法一：套接字选项 SO_RCVTIMEO #

c
struct timeval t = {5, 0};

if (setsockopt(listenfd, SOL_SOCKET, SO_RCVTIMEO, &t, sizeof(t)) == -1) {
    perror("setsockopt");
    return -1;
}

memset(&peeraddr, 0, sizeof(peeraddr));
len = sizeof(peeraddr);

if ((connfd = accept(listenfd, (struct sockaddr *)&peeraddr, &len)) == -1) {
    printf("errno=%d: %s\n", errno, strerror(errno));
    if (errno == EAGAIN) {
        printf("timeout\n");
        return -1;
    }
    return -1;
}

设一次，之后所有阻塞读写都受它管。超时后 accept 返回 -1，errno 是 EAGAIN（有些系统给 EWOULDBLOCK，两个值在 Linux 上相等）。判 errno 时把两个都写上，移植到别的系统不吃亏。

好处是设置成本低，一行 setsockopt 管一辈子。坏处是精度只到秒，且只对收方向管用——connect 超时得用 SO_SNDTIMEO，而这个选项对 connect 的行为在不同内核上不完全一致。

方法二：select 的等待参数 #

c
struct timeval t = {3, 0};
int ret;

while (1) {
    t.tv_sec = 3;
    t.tv_usec = 0;
    if ((ret = select(maxfd + 1, &rdfs, NULL, NULL, &t)) == -1) {
        perror("select");
        return -1;
    }
    if (ret == 0) {
        printf("timeout, nothing ready\n");
        continue;
    }
    /* rdfs 里有 fd 就绪，往下读 */
}

两个坑要提前说清：

  • timeval 是输入输出参数。select 返回时会把它改成「剩余时间」，所以循环里每轮都要重置 tv_sec/tv_usec，否则第二轮等到的是一个被改小的值，第三轮直接 0，退化成忙轮询。
  • rdfs 同样会被改写，每轮进 select 之前必须重新 FD_ZERO + FD_SET，不能只设一次。

返回 0 表示超时，返回正数是就绪的 fd 个数，返回 -1 才是出错。

方法三：定时器加 SIGALRM 信号 #

c
void handler(int sig)
{
    /* 什么都不用做，唤醒阻塞的系统调用就够了 */
}

struct sigaction act;
sigaction(SIGALRM, NULL, &act);        /* 取 SIGALRM 现有属性 */
act.sa_handler = handler;              /* 装处理函数 */
sigemptyset(&act.sa_mask);
act.sa_flags &= ~SA_RESTART;           /* 关键：不要自动重启被中断的系统调用 */
sigaction(SIGALRM, &act, NULL);        /* 写回 */

alarm(3);                              /* 定时器设 3 秒 */

if ((connfd = accept(listenfd, (struct sockaddr *)&peeraddr, &len)) == -1) {
    if (errno == EINTR) {
        printf("timeout\n");
        return -1;
    }
    return -1;
}

定时器 3 秒内没有数据到来，内核产生 SIGALRM 中断当前操作，被中断的系统调用返回 -1、errno 置 EINTR。

这里只能使用 sigaction，不能用 signal。原因在语义上：signal 装的 handler 执行完后会重新执行被中断的操作（早期实现如此，glibc 的 signal 也是 BSD 语义，带 SA_RESTART），accept 会被自动重启，超时永远触发不了，进程继续阻塞。sigaction 可以显式清掉 SA_RESTART，让 accept 老实返回 EINTR。

三种方法怎么选 #

维度 SO_RCVTIMEO select/poll alarm + 信号
设置成本 一行 setsockopt 每轮重置 fd 集合和时间 装 handler + 起定时器
超时精度 秒级（timeval，但内核按 tick 计） 微秒级 秒级
能否同时等多个 fd 不能 能 不能
超时后的表现 返回 -1，errno 为 EAGAIN 返回 0 返回 -1，errno 为 EINTR
对已有数据的影响 无 无 信号打断的位置不可控
多线程可用 可用（选项是每 fd 的） 可用 不可用
适合场景 简单收数据，超时兜底 要同时等多个连接、还要控超时 单线程老代码

结论直给：默认用 SO_RCVTIMEO，要同时等多个连接就用 select/poll，信号方式只在维护老代码时碰。

为什么信号方式在多线程里不能用 #

三个理由，一个比一个硬：

  1. alarm() 是进程级的，一个进程只有一个闹钟。线程 A 设 3 秒，线程 B 也设 3 秒，后来的把前面的覆盖掉，A 的定时器凭空消失。
  2. 信号送到哪个线程由内核决定——哪个线程没屏蔽 SIGALRM 就会被挑中。想精确控制得给所有线程 pthread_sigmask，只在目标线程放开，代码立刻变复杂。
  3. handler 里能做的事极少（只能调异步信号安全的函数），而超时后续多半要打日志、改状态、释放资源，这些都不能在 handler 里干。

所以信号超时是单线程时代的产物。多线程程序里，把定时器换成 SO_RCVTIMEO，或者干脆上 epoll + 超时队列。

poll 版的超时 #

c
struct pollfd pfd;
pfd.fd = connfd;
pfd.events = POLLIN;

int ret = poll(&pfd, 1, 3000);   /* 毫秒 */
if (ret == 0) {
    printf("timeout\n");
} else if (ret > 0 && (pfd.revents & POLLIN)) {
    /* 可读 */
}

poll 的第三个参数直接是毫秒数，传 -1 表示永久阻塞。它比 select 好在不用重置时间参数，也不用管 FD_SETSIZE 上限，fd 数量上千时选它。

九、排错的基本顺序 #

自下而上，逐层排除 #

网络故障的排查顺序不是凭感觉，是按分层来。链路没起来就查三层，等于白查。

步 命令 看什么 结论
1 ip addr / ifconfig 接口 UP 吗，有 IP 吗 没 UP，问题在网卡、驱动、线缆
2 ip -s link 收发计数、错包、丢包 有错包，问题在物理层
3 ping 网关 三层通不通 不通，查网段、掩码、ARP
4 ping 8.8.8.8 出网通不通 通网关不通外网，查路由和 NAT
5 ss -lntp 端口在听吗，谁在听 没听，问题在应用
6 traceroute 路径通到哪一跳断 定位到某台路由器
7 tcpdump 报文到没到，长什么样 到本机没上来，查过滤规则
8 应用日志 协议层交互对不上 问题在应用语义

这个顺序的骨架来自课堂板书，一句话能背：ifconfig 看链路是否 up → ping 看三层通不通 → ss -lntp 看端口是否监听 → traceroute 看路径 → tcpdump 看报文。

一条实际走过的路 #

「curl http://10.0.0.5:8080 不通」这么查：

text
ip addr                 → 本机有 IP，接口 UP，跳过第 1 步
ip route                → 有默认路由，网关 10.0.0.1
ping 10.0.0.1           → 通，链路和三层都正常
ss -lntp | grep 8080    → 本机没监听 8080，但我们要连的是对端
ping 10.0.0.5           → 不通
arp -a                  → 10.0.0.5 显示 incomplete

到 arp -a 这一步就定案了：ARP 都没解析出来，压根没走到 TCP。对端不在线、IP 写错、或者不同网段却按同网段 ARP，三种里必有一种。这时候 curl 报什么错都不重要，问题在三层以下。

反向的例子：ping 通、arp 有表项、ss -lntp 在对端看到 8080 在听，curl 还是不通——那就往 tcpdump 走，看 SYN 到没到对端、SYN+ACK 有没有回、被谁拦了。

常见症状对照 #

症状 多半的成因 先查
Destination Host Unreachable ARP 没解析，或没有路由 arp -a、ip route
Network is unreachable 没有到目的网段的路由 ip route
Connection refused 对端回了 RST，端口没监听 对端 ss -lntp
Connection timed out 包被静默丢弃，无回应 中间防火墙、traceroute
ping 通但端口不通 三层通、四层被挡 对端防火墙规则
时通时不通 ARP 冲突、链路双工不匹配、丢包 ip -s link、tcpdump
大包不通小包通 MTU 问题，ICMP 被挡导致 PMTU 失效 ping -s 1473 -M do
DNS 慢但 IP 访问快 解析环节 /etc/resolv.conf、dig

「Connection refused 比 Connection timed out 可爱」这句话值得记住：前者说明包到了、对端回话了，链路和路由都是好的，只剩端口问题；后者说明包消失在某个环节，得一段段找。

十、常用观察手段 #

网络状态检测命令一览 #

命令 用途
ifconfig / ip addr 查看、配置网络接口
ping 检测网络连通性（ICMP）
netstat / ss 查看网络状态：监听端口、连接、协议栈统计
traceroute 检测到目的主机经过的路由器
tcpdump 抓包，显示本机网络流量

老系统上 netstat 还在，新系统上 ss 更快（不走 /proc 全表遍历）。两个都会用，换机器不慌。

接口 #

bash
ip addr show
ip link show
ip -s link show eth0

看三样：状态是不是 UP、有没有 LOWER_UP（链路层真的通了）、IP 和掩码对不对。UP 但没有 LOWER_UP，说明网卡自己起来了但线没插好或对端没通电。

连通性 #

bash
ping -c 4 10.0.0.5
ping -c 4 -s 1473 -M do 10.0.0.5    # 探 MTU，禁止分片
arping -I eth0 10.0.0.5             # 绕过 IP 层，直接测二层

arping 是查 ARP 问题的专用工具：ping 不通时，arping 通说明二层没问题、三层配置有问题；arping 也不通，问题在二层以下。

端口与连接 #

bash
ss -lntp                # 监听的 TCP 端口和进程
ss -tanp                # 所有 TCP 连接
ss -tan state time-wait | wc -l
ss -s                   # 协议栈统计汇总

-l 听、-n 数字、-t TCP、-a 全部、-p 带进程名。这五个字母组合起来能覆盖九成场景。

路径 #

bash
traceroute 8.8.8.8
traceroute -T -p 443 8.8.8.8     # 用 TCP 探，穿 ICMP 被挡的网络
mtr 8.8.8.8                      # 持续观察每一跳的丢包

路径上出现 * * * 不一定是断，很多路由器不回过期的 ICMP。真正断的位置是「之后每一跳都 *」，而不是中间某一跳单独 *。

抓包 #

bash
tcpdump -i eth0 -nn                      # 最基本
tcpdump -i eth0 -nn port 8080            # 按端口
tcpdump -i eth0 -nn host 10.0.0.5        # 按主机
tcpdump -i eth0 -nn -c 100 -w /tmp/a.pcap  # 存文件，用 Wireshark 看
tcpdump -i any -nn 'tcp[tcpflags] & tcp-syn != 0'   # 只看 SYN

看抓包先看三件事：SYN 有没有出去、SYN+ACK 有没有回来、谁先发的 RST。这三步能定位绝大部分连接问题。

ARP 表 #

bash
arp -a
ip neigh show

排错时把 ARP 表放在 ping 旁边一起看，很多「不通」在这一步就能定案。

十一、易错点速查 #

易错点 错在哪 正确认识
把路由器当二层设备 看它插了很多网线就以为是交换机 路由器按 IP 头转发，是三层设备；交换机按 MAC 头转发，是二层设备
以为路由器转发时 IP 不变、MAC 也不变 混了端到端和逐跳 IP 端到端不变，MAC 每跳都改，路由器会重封装帧头
以为交换机也看 IP 把三层交换机和二层交换机混了 纯二层交换机不看 IP，只看目的 MAC
跨网段还去 ARP 目的主机 不知道广播不出网段 跨网段 ARP 问的是网关地址，不是目的主机
认为 ARP 只有请求方学地址 漏了第 7 步 被请求的一方也会把请求方的 IP-MAC 写进自己的表
把 ARP 请求也发成单播 不知道没表项时无从单播 请求是广播、应答是单播
(incomplete) 当成表损坏 不知道它表示解析失败 请求发了没回应，查对端是否在线
把 CLOSE_WAIT 当内核问题 以为要调内核参数 是本端应用没 close()，改代码
看到大量 TIME_WAIT 就慌 不知道这是主动方的正常状态 短连接必然产生，复用连接或调 SO_REUSEADDR
用 signal 装 SIGALRM 做超时 不知道 SA_RESTART 会重启系统调用 必须用 sigaction 并清掉 SA_RESTART，否则超时不生效
多线程里用 alarm 做超时 不知道定时器是进程级的 一个进程一个闹钟，线程间互相覆盖，改用 SO_RCVTIMEO 或 epoll
select 循环里不重置时间参数 不知道 timeval 是输入输出参数 每轮都要重设 tv_sec/tv_usec，fd 集合也要重设
超时后不判 errno 把超时和真错误混在一起 EAGAIN 是超时，EINTR 是被信号打断，其他才是错
拿 ping 通就当服务正常 三层通不等于四层通 还要看端口监听和防火墙规则
小包通大包不通还查应用 不知道是 MTU 问题 用 ping -s 加 -M do 探 MTU，查 PMTU 是否被 ICMP 挡了
抓包在错误的接口上做 多网卡机器抓了 eth0 但流量走 eth1 先 ip route get 目的IP 确认出口，再抓那个口

最后一条最省时间：抓包抓错口，看半天什么都看不到，还以为是没流量。

排查这件事的顺序永远是先分层、再定位、最后看报文。分层定位置，命令定范围，抓包定证据。三步走完，问题基本就剩一个答案了。
