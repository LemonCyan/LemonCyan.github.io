这篇讲的是「在 Rockchip 平台上把 CAN 跑起来」这件事本身：设备树怎么配、内核怎么编、NAPI 怎么工作、板子刚上电时怎么验证。它是一份贴着代码和板子的操作记录，不是协议教材。

协议的帧格式、仲裁机制、位定时、物理层电平、终端电阻这些，归《CAN 总线基础》那篇。CANOpen 的对象字典、SDO/PDO、NMT 状态机，归《CANOpen 协议》那篇。本篇只在必要的地方提一句，然后指过去。

平台范围是 Rockchip 的 RK3568 和 RK3588 一类芯片，内核基线 5.10，驱动在 drivers/net/can/rockchip/。别的厂商的 CAN 控制器思路相通，但寄存器名和代码路径对不上，不要硬套。

全篇的主线只有一条：CAN 帧很短，短帧来得很密，如果每帧都进一次中断，CPU 会被中断吃掉。Rockchip 的驱动最初就是每帧一次中断的写法，后来改成 NAPI，把「每帧一次中断」压成「每次唤醒收一批」。这条主线会从第六节一直贯到第九节。

一、Rockchip CAN 的驱动结构 #

先弄清楚代码在哪、由谁调、按什么顺序初始化。后面配设备树、改中断，都是在这个骨架上动刀。

驱动文件位置 #

内核源码里的路径是固定的：

text
drivers/net/can/rockchip/rockchip_canfd.c

Rockchip 的 CAN 支持走的是内核标准 CAN 子系统，不是自己另起一套字符设备。也就是说，驱动最终注册出来的是一个网络设备，用 ip link 看得到，用 can-utils 打得到。这一点决定了后面所有工具的用法。

内核版本基线是 5.10.110。不同版本的函数签名会变，比如 netif_napi_add 在 6.x 多了几个参数，napi_complete 和 napi_complete_done 的用法也有差异。移植前先确认版本。

设备树匹配表 #

驱动的入口是这张表：

c
static const struct of_device_id rockchip_canfd_of_match[] = {
	{
		.compatible = "rockchip,canfd-1.0",
		.data = (void *)ROCKCHIP_CANFD_MODE
	},
	{
		.compatible = "rockchip,can-2.0",
		.data = (void *)ROCKCHIP_CAN_MODE
	},
	{
		.compatible = "rockchip,rk3568-can-2.0",
		.data = (void *)ROCKCHIP_RK3568_CAN_MODE
	},
	{}, // 结束标记
};

三个 compatible 对应三种工作模式，.data 字段把模式号带进 probe：

compatible 模式 含义
rockchip,canfd-1.0 ROCKCHIP_CANFD_MODE 支持 CAN FD，能处理更高数据速率和更大的数据帧
rockchip,can-2.0 ROCKCHIP_CAN_MODE 传统 CAN 2.0，车辆和工业控制里最常见
rockchip,rk3568-can-2.0 ROCKCHIP_RK3568_CAN_MODE RK3568 专用兼容项，走 2.0 帧格式

这里的坑很直接：设备树里写哪个字符串，就决定了驱动按哪种模式初始化控制器。RK3568 的 dtsi 默认写的是 rockchip,rk3568-can-2.0，如果板级 dts 里又把它覆盖成 rockchip,canfd-1.0，那就是主动切到 FD 模式。反过来，只想跑经典 CAN 却留着 FD 的兼容串，ip -details link show can0 会显示出 <FD> 标记，波特率和帧格式都和总线上其他节点对不上。

platform_driver 结构 #

c
static struct platform_driver rockchip_canfd_driver = {
	.driver = {
		.name = DRV_NAME,
		.pm = &rockchip_canfd_dev_pm_ops,
		.of_match_table = rockchip_canfd_of_match,
	},
	.probe = rockchip_canfd_probe,
	.remove = rockchip_canfd_remove,
};

逐项看：

  • .name：驱动名，由 DRV_NAME 宏给出。这个名字会出现在 dmesg 和 /sys/bus/platform/drivers/ 下面，排查时用它找线索。
  • .pm：电源管理回调集合。CAN 控制器在系统休眠时要保存寄存器状态、关闭时钟，唤醒后恢复。
  • .of_match_table：指向上面那张匹配表，内核拿它和设备树节点的 compatible 做比对。
  • .probe：真正干活的初始化函数。
  • .remove：卸载路径，负责反向释放。

注册用一个宏收尾：

c
module_platform_driver(rockchip_canfd_driver);

这个宏展开后包含 module_init 和 module_exit，模块加载时自动调用 probe。如果编译成 =y 直接进内核，那就是启动阶段由 platform bus 扫到设备树节点后调用。

probe 的初始化顺序 #

probe 里的顺序是有讲究的，每一步失败都会影响后面的资源获取，函数骨架长这样：

c
static int rockchip_canfd_probe(struct platform_device *pdev) {
    ...
}

第一步，拿中断号。

c
irq = platform_get_irq(pdev, 0);

中断号从设备树的 interrupts 属性来。取不到就没法注册中断处理函数，直接返回错误。这里失败，dmesg 里会看到 -ENXIO 或者 failed to get irq。

第二步，拿内存资源并映射。

c
res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
addr = devm_ioremap_resource(&pdev->dev, res);
if (IS_ERR(addr))
    return -EBUSY;

platform_get_resource 取的是设备树 reg 属性描述的物理地址范围。devm_ioremap_resource 把它映射成内核虚拟地址，同时向内核申请这块 IO 内存的独占权。返回 -EBUSY 说明地址被别人占了，十有八九是 reg 写错、和另一个节点重叠。

第三步，分配 CAN 设备。

c
ndev = alloc_candev(sizeof(struct rockchip_canfd), 1);
if (!ndev) {
    dev_err(&pdev->dev, "could not allocate memory for CANFD device\n");
    return -ENOMEM;
}

alloc_candev 是 CAN 子系统的分配函数，内部会调 alloc_netdev，再挂上 CAN 私有的 can_priv 结构。第二个参数是报文对象（message object）的数量，这里给 1。这个值决定硬件能并行挂多少个收发邮箱，和后面的 NAPI 权重、FIFO 深度相关。

第四步，注册中断处理函数。

c
err = devm_request_irq(&pdev->dev, irq, rockchip_canfd_interrupt, 0, ndev->name, ndev);

最后传的 dev_id 是 ndev，中断处理函数里会把它还原成网络设备和私有结构。用 devm_ 前缀意味着不用手动 free_irq，设备卸载时内核自动回收。

第五到第七步，复位、时钟、模式。

c
rcan->reset = devm_reset_control_array_get(&pdev->dev, false, false);
if (IS_ERR(rcan->reset)) {
    if (PTR_ERR(rcan->reset) != -EPROBE_DEFER)
        dev_err(&pdev->dev, "failed to get canfd reset lines\n");
    return PTR_ERR(rcan->reset);
}

rcan->num_clks = devm_clk_bulk_get_all(&pdev->dev, &rcan->clks);
if (rcan->num_clks < 1)
    return -ENODEV;

-EPROBE_DEFER 不是真错误。它表示复位控制器还没就绪，内核会把 probe 排队延后重试。看到它就去查依赖的时钟、复位驱动有没有先加载，而不是去改 CAN 驱动。

devm_clk_bulk_get_all 会把 clocks 属性里列出的时钟一次性全取回来，不用一个个按名字取。返回数量小于 1 就是 -ENODEV。

模式靠 of_device_get_match_data 取匹配表里 .data 那个值：

c
rcan->mode = (unsigned long)of_device_get_match_data(&pdev->dev);

switch (rcan->mode) {
    case ROCKCHIP_CANFD_MODE:
        /* 设置 FD 模式的参数 */
        break;
    case ROCKCHIP_CAN_MODE:
        /* 设置常规 CAN 模式的参数 */
        break;
    default:
        return -EINVAL;
}

两种模式的差别在数据段长度、位速率切换能力、寄存器布局。FD 模式要额外配数据段波特率（dbitiming），经典 CAN 只配仲裁段波特率。

第八步，挂网络设备操作集，注册设备。

c
ndev->netdev_ops = &rockchip_canfd_netdev_ops;

err = register_candev(ndev);
if (err) {
    dev_err(&pdev->dev, "registering %s failed (err=%d)\n", DRV_NAME, err);
    goto err_disableclks;
}

netdev_ops 是 CAN 驱动和网络子系统之间的契约，里面至少要有 ndo_open、ndo_stop、ndo_start_xmit。ndo_open 里会 napi_enable，ndo_stop 里会 napi_disable，这正好接上第六节之后的 NAPI 内容。

register_candev 成功后，can0 这类名字才会出现在 ip link 里。在这之前，即使 probe 一路跑通，用户空间也看不到设备。

失败路径统统走 goto，这是内核驱动的常规写法。goto 标签的顺序必须和资源申请顺序相反，否则会漏释放或者重复释放。devm_ 系列能省掉一部分，但时钟使能、运行时 PM 这类还是要手动关。

控制器内部模块 #

知道驱动怎么初始化之后，再看控制器里有哪些部件在配合。Rockchip 的 CAN 控制器有这么几块：

  • 接口管理逻辑：对接外部主控制器，解析命令，控制寄存器寻址。CPU 读写寄存器走的就是这条路。
  • CAN 核心模块：负责帧的串并转换，把并行数据变成总线上的串行位流，反过来也一样。
  • 发送缓冲器：完整报文先放这里，等总线空闲再发。
  • 验收滤波器：按 ID 筛报文，不该收的直接在硬件层丢掉，不占 CPU。
  • 接收 FIFO：从总线收到的报文先落这里，深度由 rx-fifo-depth 决定。

四块里和性能最相关的是后两块。滤波器配得好，软件少收一半无用帧；FIFO 够深，突发流量才不会溢出丢帧。这两件事都能在设备树里调，不用改代码。

两种工作模式 #

控制器本身支持两种帧处理模式：

模式 协议范围 适用场景
BasicCAN 只支持标准 CAN 简单应用，节点少，ID 范围窄
PeliCAN 支持 CAN 2.0B，标准帧和扩展帧都能处理 多节点系统，需要 29 位扩展 ID

PeliCAN 是 2.0B 的实现，扩展帧靠它。如果总线上有节点用 29 位 ID，BasicCAN 模式收不到。这个模式由驱动根据 compatible 和控制器能力决定，不是设备树里单独某个属性。

二、设备树配置 #

设备树是这一整套东西的地基。配错了，驱动根本不会 probe，后面所有调试都是空谈。

控制器节点在 SoC 级 dtsi 里 #

SoC 级的描述放在 rk3568.dtsi 或 rk3588s.dtsi，它定义的是硬件能力，默认 disabled，等板级去打开。

dts
can0: can@fe570000 {
	compatible = "rockchip,rk3568-can-2.0";
	reg = <0x0 0xfe570000 0x0 0x1000>;
	interrupts = <GIC_SPI 1 IRQ_TYPE_LEVEL_HIGH>;
	clocks = <&cru CLK_CAN0>, <&cru PCLK_CAN0>;
	clock-names = "baudclk", "apb_pclk";
	resets = <&cru SRST_CAN0>, <&cru SRST_P_CAN0>;
	reset-names = "can", "can-apb";
	tx-fifo-depth = <1>;
	rx-fifo-depth = <6>;
	status = "disabled";
};

RK3588 上是另一组地址和中断号，形状完全一样：

dts
can0: can@fea50000 {
	compatible = "rockchip,can-2.0";
	reg = <0x0 0xfea50000 0x0 0x1000>;
	interrupts = <GIC_SPI 341 IRQ_TYPE_LEVEL_HIGH>;
	clocks = <&cru CLK_CAN0>, <&cru PCLK_CAN0>;
	clock-names = "baudclk", "apb_pclk";
	resets = <&cru SRST_CAN0>, <&cru SRST_P_CAN0>;
	reset-names = "can", "can-apb";
	pinctrl-names = "default";
	pinctrl-0 = <&can0m0_pins>;
	tx-fifo-depth = <1>;
	rx-fifo-depth = <6>;
	status = "disabled";
};

两份看起来差不多，差别在 reg 基址、interrupts 编号、以及 RK3588 这份把 pinctrl 直接写在了 SoC 节点里。位置不同不影响功能，只要最终生效的那份有就行。

先改 CANFD 为 CAN，再改缓冲深度。这是最常见的两处板级改动目的。

关键属性逐个看 #

属性 示例值 作用 配错的后果
compatible "rockchip,rk3568-can-2.0" 匹配驱动和模式 匹配不上，probe 不执行
reg <0x0 0xfe570000 0x0 0x1000> 寄存器基址和大小 映射失败或被别的设备占用
interrupts <GIC_SPI 1 IRQ_TYPE_LEVEL_HIGH> 中断源和触发方式 取不到中断号，收不到任何帧
clocks / clock-names CLK_CAN0, PCLK_CAN0 波特率时钟和总线时钟 时钟取不到，-ENODEV
resets / reset-names SRST_CAN0, SRST_P_CAN0 控制器和 APB 复位 控制器停在复位态，寄存器读写全废
pinctrl-names / pinctrl-0 "default", <&can0m0_pins> 引脚复用 引脚不是 CAN 功能，总线上没波形
tx-fifo-depth <1> 发送 FIFO 深度 并发发送时丢帧或阻塞
rx-fifo-depth <6> 接收 FIFO 深度 高负载时溢出丢帧
status "okay" 节点是否启用 是 disabled，驱动完全不加载

compatible 这一项单独再说一遍，因为它最容易被搞混。实际用到的字符串有 rockchip,can-1.0、rockchip,can-2.0、rockchip,canfd-1.0、rockchip,rk3568-can-2.0 几个。写哪个决定走哪条分支，也决定 ip -details 里会不会出现 <FD>：

dts
/* rockchip,can-1.0 用来匹配 can 控制器驱动 */
compatible = "rockchip,can-1.0";
/* rockchip,can-2.0 用来匹配 canfd 控制器驱动 */
compatible = "rockchip,can-2.0";

interrupts 里三个字段：中断控制器（GIC_SPI）、SPI 中断号、触发类型。IRQ_TYPE_LEVEL_HIGH 是电平高触发。这个必须和硬件接法一致，写成边沿触发会漏中断。

clocks 里两个时钟各有分工。baudclk 喂给波特率发生器，决定位定时的精度；apb_pclk 是 APB 总线时钟，决定寄存器访问速度。clock-names 的顺序必须和 clocks 严格对应，反了就拿错时钟。

FIFO 深度怎么定 #

rx-fifo-depth 是板级最常动的参数。它的含义是接收 FIFO 能存多少条 CAN 消息，等软件来取。改深了有什么影响，分四面看：

  • 缓冲容量：深度大，能存更多消息。控制器高频收帧而软件来不及处理时，深 FIFO 直接防丢帧。
  • 延迟：FIFO 深了，消息会在缓冲区里多等一会儿才被取走。这点延迟相比丢帧的代价，可以接受。
  • 资源占用：深度增加会多吃一点硬件资源（内存），合理范围内可以忽略。
  • 系统响应性：软件读 FIFO 慢的时候，深 FIFO 能吸收突发流量，系统不至于因为一个尖峰就丢数据。
dts
tx-fifo-depth = <1>;
rx-fifo-depth = <32>;

RK3568 的实测改动是把 <6> 提到 <32>。默认 6 条，在 1Mbps 满负载下很容易溢出；32 条给了软件缓冲余地。tx-fifo-depth 一般保持 <1>，因为 CAN 发送本来就是排队发出的，深度 1 意味着发完一帧再发下一帧，逻辑简单。

引脚复用 #

pinctrl 把物理引脚切成 CAN 功能。Rockchip 的 pinctrl 用「bank + 组 + 序号 + 功能号」四元组描述：

dts
can1 {
	/omit-if-no-ref/
	can1m0_pins: can1m0-pins {
		rockchip,pins =
			/* can1_rxm0 */
			<1 RK_PA0 3 &pcfg_pull_none>,
			/* can1_txm0 */
			<1 RK_PA1 3 &pcfg_pull_none>;
	};

	/omit-if-no-ref/
	can1m1_pins: can1m1-pins {
		rockchip,pins =
			/* can1_rxm1 */
			<4 RK_PC2 3 &pcfg_pull_none>,
			/* can1_txm1 */
			<4 RK_PC3 3 &pcfg_pull_none>;
	};
};

每组四列分别是：GPIO bank 号、组内引脚（RK_PA0 是 A 组第 0 脚）、功能号（这里的 3 表示该脚的第 3 种复用功能是 CAN）、上下拉配置。

&pcfg_pull_none 表示不启用内部上下拉。CAN 是差分总线，内部上下拉会破坏终端匹配，所以这里必须是 none。

/omit-if-no-ref/ 的意思是：如果没有任何节点引用这个 pin group，就把它从最终 dtb 里删掉。省体积，也避免无用节点。

M0 和 M1 是同一个控制器的两套可选引脚，物理上连到不同的管脚。板子上 CAN_H/CAN_L 实际接到哪组脚，就得选哪组。选错了引脚，寄存器配置全对，总线上一根波形都没有。

RK3568 的换 M1 是直接覆盖 pinctrl-0：

dts
&can1 {
	assigned-clocks = <&cru CLK_CAN1>;
	assigned-clock-rates = <150000000>;
	pinctrl-names = "default";
	pinctrl-0 = <&can1m1_pins>;
	status = "okay";
};

这里顺带把 CAN1 的完整 SoC 节点也列出来，它和 CAN0 的区别就是基址、中断号、时钟和复位指向：

dts
can1: can@fe580000 {
	compatible = "rockchip,canfd-1.0";
	reg = <0x0 0xfe580000 0x0 0x1000>;
	interrupts = <GIC_SPI 2 IRQ_TYPE_LEVEL_HIGH>;
	clocks = <&cru CLK_CAN1>, <&cru PCLK_CAN1>;
	clock-names = "baudclk", "apb_pclk";
	resets = <&cru SRST_CAN1>, <&cru SRST_P_CAN1>;
	reset-names = "can", "can-apb";
	tx-fifo-depth = <1>;
	rx-fifo-depth = <6>;
	status = "disabled";
};

CLK_CAN1 喂波特率发生器，PCLK_CAN1 是 APB 总线时钟；SRST_CAN1 复位控制器本体，SRST_P_CAN1 复位 APB 接口。reset-names 里的 can-apb 对应的就是 SRST_P_CAN1。这套命名规律在 CAN0、CAN1、CAN2 上完全一致，换个编号就是另一个控制器。

IOMUX 这个词值得解释一句：Input/Output Multiplexer，输入/输出多路复用器。芯片的一个物理引脚内部连着好几个功能模块，同一时刻只能选一个接到引脚上。IOMUX 就是那个选择开关，设备树里的 pinctrl 就是在拨这个开关。

板级怎么启用 #

SoC 级节点是 disabled，板级 dts 里重新打开并补上板子特有的部分：

dts
&can0 {
	compatible = "rockchip,can-1.0";
	assigned-clocks = <&cru CLK_CAN0>;
	assigned-clock-rates = <300000000>;
	pinctrl-names = "default";
	pinctrl-0 = <&can0m0_pins>;
	rx-fifo-depth = <32>;
	status = "okay";
};

这个片段的文件位置是 kernel/arch/arm64/boot/dts/rockchip/OK3568-C-common.dtsi。

只写一行 status = "okay" 是能用的，因为其余属性会从 SoC 级节点继承。上面这份多写了 assigned-clocks、pinctrl-0、rx-fifo-depth，是在覆盖默认值。

最容易出的两个错，就在这里：

第一，status 还是 "disabled"。表现是驱动压根不 probe，/sys/bus/platform/devices/ 下都找不到节点，ip link 没有 can0，dmesg 干净得像什么都没发生。查半天代码，最后发现少了一行。

第二，pinctrl-0 指错了 pin group。表现是设备能 probe、ip link 能看到 can0、ip link set can0 up 也不报错，但总线上没有波形，收发全静默。这时候要看 /sys/kernel/debug/pinctrl/ 下面确认引脚复用状态。

assigned-clock-rates 决定时钟频率，和波特率精度直接相关。经验值：比特率低于 1Mbps 时把 CAN 时钟设到 200MHz，信号更稳；高于 1Mbps 时设 300MHz。RK3568 的示例里给了 300MHz，150MHz 那份对应的是 CAN1 的配置。

复用引脚做 CAN2 #

OK3568 上有一个典型场景：UART8 和 CAN2 共用引脚，要用 CAN2 就得先关掉 UART8。两处都在 kernel/arch/arm64/boot/dts/rockchip/OK3568-C-common.dtsi：

dts
&can2 {
	status = "okay";
};

&uart8 {
	status = "disabled";
};

顺序无所谓，但两个都得改。只开 CAN2 不关 UART8，两个驱动会抢同一组引脚，最后谁赢看 probe 顺序，现象是串口输出乱码或者 CAN 没波形。

改完回 OK3568-linux-source 目录执行 ./build.sh kernel，编完单独烧 kernel/boot.img。

三、内核配置与编译 #

设备树描述硬件，内核配置决定驱动编不编进去。两件事都对了，设备才会出现。

必开的配置项 #

配置文件位置随 SDK 而定，OK3568 的路径是 kernel/arch/arm64/configs/OK3568-C-linux_defconfig。里面至少要这几行：

bash
CONFIG_CAN=y
CONFIG_CAN_DEV=y
CONFIG_CAN_ROCKCHIP=y
CONFIG_CANFD_ROCKCHIP=y

逐项解释：

  • CONFIG_CAN：打开整个 CAN 协议栈。关掉它，can-utils 的所有命令都会报 Protocol not supported。
  • CONFIG_CAN_DEV：启用 CAN 设备的支持层，can0 这类接口靠它出现。
  • CONFIG_CAN_ROCKCHIP：Rockchip 平台 CAN 驱动本体。
  • CONFIG_CANFD_ROCKCHIP：CAN FD 支持。只跑经典 CAN 时这一项可以不选，但驱动里如果引用了 FD 相关符号，编译会失败。

y/m/n 三种取值的含义：

取值 含义 结果
y 编进内核 启动即可用，体积大
m 编成模块 需 insmod/modprobe 加载
n 不编译 功能不存在

CAN 驱动建议 =y。做成模块的话，根文件系统起来之前没法用，而且启动脚本里要额外加加载步骤。

关掉 CANFD 的争议 #

早期有一种做法是先把 FD 关掉再改设备树：

text
修改 vi ./kernel/arch/arm64/configs/OK3568-C-linux_defconfig
中的 CONFIG_CANFD_ROCKCHIP=n，关闭 CANFD

这个思路是想通过关内核选项强制走经典 CAN 路径。但同一份 rockchip_canfd.c 里同时编着 CAN 和 CAN FD 两套逻辑，靠 compatible 的 .data 分派。把 CONFIG_CANFD_ROCKCHIP 关掉，如果代码里有 #ifdef 保护不当的引用，编译会直接报未定义符号。

更可靠的做法是改设备树的 compatible，让 of_device_get_match_data 返回 ROCKCHIP_CAN_MODE，走经典 CAN 分支。内核配置保持能编过就行。

编译和产物 #

Rockchip SDK 用统一的构建脚本：

bash
./build.sh kernel

编完的产物在 kernel/boot.img。这个镜像是 boot 分区，包含内核 Image 和 dtb。只改了设备树的话，重新烧 boot.img 就够，不用动 rootfs。

只验证设备树语法的话可以不编译，用 make ARCH=arm64 dtbs_check 过一遍。这个命令会报设备树绑定错误，比如属性名拼错、必需属性缺失。比烧进去再猜快得多。

编译期常见报错 #

undefined reference to 'rockchip_canfd_...'：符号没编进来，检查 CONFIG_CAN_ROCKCHIP 是否为 y。

netif_napi_add 参数不匹配：内核版本不对。5.10 的签名是三个参数加权重，6.x 多了 napi_budget 之类。按实际内核版本的头文件改。

implicit declaration of function 'napi_complete_done'：缺 #include <linux/netdevice.h>，或者内核版本太老没有这个函数，改用 napi_complete。

编译过了但设备树报 Failed to find node：dtsi 的 include 链没接上，板级 dts 里没 #include 对应的 SoC dtsi。

四、使能与自收测试 #

板子刚起来，手上不一定有第二个 CAN 节点、也不一定有分析仪。这种情况下怎么确认驱动是好的？答案是自收。

先把接口拉起来 #

设备出现了，第一件事是看它长什么样：

bash
ip -details link show can0

输出里重点看三样：接口状态是不是 DOWN、有没有 <FD> 标记、bitrate 和 sample-point 的值。

CANFD 节点的输出会带 <FD> 字样：

text
can0: <NOARP,ECHO> mtu 72 qdisc pfifo_fast state DOWN mode DEFAULT
    link/can  promiscuity 0
    can <FD> state STOPPED (berr-counter tx 0 rx 0) restart-ms 0
      bitrate 500000 sample-point 0.875
      dbitrate 2000000 dsample-point 0.750

经典 CAN 节点没有 <FD>，mtu 是 16：

text
can0: <NOARP,ECHO> mtu 16 qdisc pfifo_fast state DOWN mode DEFAULT
    link/can  promiscuity 0
    can state STOPPED (berr-counter tx 0 rx 0) restart-ms 0
      bitrate 500000 sample-point 0.875

这个 <FD> 就是判断「设备树里的 compatible 到底生效成哪种模式」的直接证据。想跑经典 CAN 却看到 <FD>，回设备树改 compatible。

配波特率并拉起来：

bash
ip link set can0 type can bitrate 500000
ip link set can0 up

state STOPPED 会变成 state ERROR-ACTIVE，说明控制器进入了正常工作态。如果一直是 STOPPED，检查时钟和 pinctrl。

回环模式：不用外部硬件 #

CAN 控制器内部支持回环。发出去的帧在控制器内部直接绕回接收路径，不经过收发器和总线。

bash
ip link set can0 down
ip link set can0 type can bitrate 500000 loopback on
ip link set can0 up

loopback on 打开内部回环。这时候一个终端挂着收，另一个终端发：

bash
# 终端 1
candump can0

# 终端 2
cansend can0 123#DEADBEEF

终端 1 应该打出 can0 123 [4] DE AD BE EF。收到了，说明从 ndo_start_xmit 到中断、到 NAPI（如果已改）、到 netif_receive_skb、再到 SocketCAN 的整条路径都通了。这条链上任何一环断了都收不到。

loopback 有两个层级，别搞混：

模式 命令 行为
内部回环 loopback on 控制器内部绕回，不出引脚，不需要收发器
外部回环 硬件短接 CAN_H 和 CAN_L 信号真的出引脚再回来，能测收发器

内部回环测的是驱动和控制器逻辑；外部回环测的是收发器和引脚复用。引脚配错时内部回环照样能过，外部回环会失败。这是区分「软件问题」和「硬件问题」的分界线。

listen-only 模式 #

只想听不想发的时候用，控制器不发 ACK、不发错误帧，纯粹旁路监听。接在别人已经跑着的总线上做抓包时用它，不会干扰总线。

bash
ip link set can0 type can bitrate 500000 listen-only on

还有 triple-sampling on（三次采样，低波特率下提高抗噪能力）和 berr-reporting on（上报错误计数变化）。几个可以叠在一条命令里：ip link set can0 type can bitrate 125000 listen-only on berr-reporting on。

自收测试的判读 #

自收收不到，分三种情况定位：

  • candump 完全没输出，ip -s link show can0 的 RX 计数也是 0：接收路径没走通。查中断有没有注册（cat /proc/interrupts | grep can）、NAPI 有没有 enable、ndo_open 有没有跑完。
  • RX 计数在涨但 candump 没输出：数据到了驱动但没送到协议栈。查 netif_receive_skb 有没有调、skb 有没有正确填充。
  • 发送就报错 Network is down：接口没 up，或者 ndo_open 返回了错误。看 dmesg。

ip -s link show can0 是最省事的观测点。输出里的 RX: bytes packets errors dropped overrun mcast 和 TX: 那一行，直接反映驱动层的收发计数。自收一次应该 TX +1、RX +1。

不需要总线的完整验证顺序 #

板子刚上电，按这个顺序推：

bash
# 1. 设备在不在
ls /sys/bus/platform/devices/ | grep can

# 2. 驱动绑上了没
ls /sys/bus/platform/drivers/rockchip_canfd/ 2>/dev/null

# 3. 网络接口在不在
ip link show | grep can

# 4. 中断注册了没
cat /proc/interrupts | grep -i can

# 5. 引脚复用对不对
cat /sys/kernel/debug/pinctrl/pinctrl-rockchip-pinctrl/pinmux-pins | grep can

# 6. 回环自收
ip link set can0 type can bitrate 500000 loopback on
ip link set can0 up
candump can0 &
cansend can0 123#11223344

第 1 步就失败，问题在设备树 status。第 2 步失败但第 1 步成功，问题在 compatible 或者驱动没编进去。第 4 步为空，问题在 interrupts。第 5 步看不到 CAN，问题在 pinctrl。

顺序别乱。每一步都排除掉一批原因，跳着查会绕远路。

五、SocketCAN 接口与工具 #

驱动通了之后，日常操作全在用户态。这套东西叫 SocketCAN，把 CAN 设备抽象成网络设备，用标准 socket API 收发。

为什么是网络设备 #

CAN 驱动注册的是 net_device，不是字符设备。好处是能直接复用网络子系统的队列、统计、多播、以及 ip 命令族。代价是收发要按网络设备的规矩走：发送走 ndo_start_xmit，接收走 netif_receive_skb。

SocketCAN 的 socket 家族是 PF_CAN，协议号 CAN_RAW。原始套接字意味着你自己组帧、自己解析，内核只负责搬运。CANOpen 之类的上层协议在用户态实现。

can-utils 工具表 #

工具 用途 典型命令
candump 接收并打印 candump can0
cansend 发送单帧 cansend can0 123#DEADBEEF
cangen 生成随机/压力流量 cangen can0 -g 1 -I 123
canplayer 回放录制的日志 canplayer -I log.txt
candump -l 录制到文件 candump -l can0
cansniffer 按 ID 分组变化的实时视图 cansniffer can0
canbusload 统计总线负载率 canbusload can0@500000
cansend --help 查 FD 帧格式 cansend can0 123##1DEADBEEF

最常用的就两个，一收一发：candump can0 和 cansend can0 123#DEADBEEF。

cansend 的数据格式是 <ID>#<DATA>。ID 是十六进制，# 后面跟十六进制字节，最多 8 字节（经典 CAN）。

  • 123#DEADBEEF：标准帧，ID 0x123，4 字节数据。
  • 123#：标准帧，DLC 为 0，空数据帧。
  • 12345678#11：8 位 ID，扩展帧，不加标记时按 29 位解析。
  • 123##1DEADBEEF：FD 帧用双 #，## 后面第一位是标志位。

candump 的输出格式也要认：

text
  can0  123   [4]  DE AD BE EF
  can0  12345678   [8]  11 22 33 44 55 66 77 88

第一列接口名，第二列 ID，方括号里是 DLC，后面是数据字节。扩展帧的 ID 会占满 8 位显示。

压力测试 #

自收能过，接着测高负载。这是暴露 NAPI 问题的最好方式：

bash
# 一边狂发，一边看收
cangen can0 -g 0 -I 7ff -L 8 &
candump can0 > /dev/null &

-g 0 是最小间隔，尽最大速度发。这时候盯着 ip -s link show can0 和 cat /proc/interrupts | grep can 两个输出：看 RX 的 dropped 和 overrun 有没有涨，看中断计数涨得多快。中断计数疯长而收包数没跟上，就是 NAPI 该上场了。改完 NAPI 之后，同样压力下中断计数应该明显下降，收包数不变。

再测总线负载：

bash
canbusload can0@500000

它会周期性打印负载百分比。1Mbps 总线上，经典 CAN 满负载的理论极限在 70%~80%（取决于帧长和 ID 分布），跑到 90% 以上就会开始丢帧。

录制与回放 #

现场抓的问题要带回来复现，用录制回放：

bash
candump -l can0
canplayer -I candump-2024-07-12_0918780.log

第一条生成 candump-2024-07-12_0918780.log 这样的文件，canplayer 按原始时间戳重放，间隔一致。想加速用 -t 参数。这条路子配合 NAPI 调试很好用：现场录一份真实的高负载流量，拿回实验室反复回放，比现场改内核快得多。

用 ip 查状态 #

不用 can-utils 也能查不少东西：

bash
# 详细参数
ip -details -statistics link show can0

# 看错误计数
ip -details link show can0 | grep berr

# 动态改波特率（要先 down）
ip link set can0 down
ip link set can0 type can bitrate 250000
ip link set can0 up

berr 那段显示 berr-counter tx N rx M。TX 错误计数涨得快，说明总线上没人 ACK（对端不在或者波特率不匹配）；RX 错误计数涨，说明收到的帧有格式错误或者位错误。

改波特率必须先 down 再 up。运行中改会被拒绝，报 Device or resource busy。

六、NAPI 是什么 #

NAPI 是 Linux 上处理高速收包的一套机制。它的核心就一句话：中断唤醒，关中断轮询，收完再开中断。这一节把这个机制拆开讲清楚，第七节再看它在 CAN 驱动里怎么落地。

纯中断为什么不行 #

老式网络设备只用一个中断收包。每来一个包，硬件拉一次中断线，CPU 停下当前活，跳进中断处理函数，把包读出来，返回，继续原来的活。

这个模型在低速下没问题。但算一下高负载的账：

假设一秒收 5000 个包，每个包只有几个字节。那就是一秒 5000 次中断。每次中断的固定开销包括：保存现场、跳转、读中断状态寄存器、清中断标志、恢复现场。这几步加起来几百个时钟周期，5000 次就是一秒里烧掉了大量 CPU 时间，而真正搬数据的时间占比很小。

CPU 的时间几乎全花在「切换」上，而不是「干活」上。这就是中断开销的本质：开销是每次中断固定的，和这一批数据有多少无关。

混合机制：中断 + 轮询 #

NAPI 的思路是拆掉「每包一中断」，改成两级：

  • 第一级：中断只负责唤醒。第一个包到达，硬件中断触发，驱动在中断处理函数里做一件很轻的事——把设备挂到待轮询队列上，然后马上返回。这里会关闭该设备的接收中断。
  • 第二级：软中断上下文里轮询。内核在软中断（NET_RX_SOFTIRQ）里遍历待轮询队列，调用驱动的 poll 函数，一次读走一批包。
  • 收尾：这一批读完了，poll 返回的处理数量小于预算值，就调用 napi_complete，重新打开接收中断，等下一个人来叫。

所以完整的循环是：

text
数据来 → 中断（只唤醒） → 关中断 → 轮询收一批 → 收完 → 开中断 → 等下次中断

关键在于：一批包只花一次中断的钱。100 个包密集到达，中断只触发一次（第一批），后面 99 个全靠轮询捞出来。中断次数从「每包一次」降到「每批一次」。

三个核心动作 #

napi_schedule：在中断处理函数里调用，把 napi_struct 挂进当前 CPU 的软中断待处理列表，然后触发 NET_RX_SOFTIRQ。它不搬数据，只登记「这个设备有活要干」。

poll 函数：由内核软中断回调，签名固定是 int (*poll)(struct napi_struct *napi, int budget)。它在预算范围内尽量多读包，返回实际处理的包数。

napi_complete：poll 发现活干完了（处理数小于预算），调用它把自己从待轮询列表摘掉，并重新打开设备中断。

这三个动作咬合成一条链。缺任何一个，机制就断了：不调 napi_schedule 就没人轮询；poll 不返回真实数量内核无法判断是否收完；不调 napi_complete 中断永远关着，下一批数据来了没人叫。

napi_struct 里有什么 #

netif_napi_add 的旧版原型，把字段一个个列出来看：

c
void netif_napi_add(struct net_device *dev, struct napi_struct *napi,
                    int (*poll)(struct napi_struct *, int), int weight) {
    INIT_LIST_HEAD(&napi->poll_list);
    napi->gro_count = 0;
    napi->gro_list = NULL;
    napi->skb = NULL;
    napi->poll = poll;
    napi->weight = weight;
    list_add(&napi->dev_list, &dev->napi_list);
    napi->dev = dev;

    #ifdef CONFIG_NETPOLL
    spin_lock_init(&napi->poll_lock);
    napi->poll_owner = -1;
    #endif

    set_bit(NAPI_STATE_SCHED, &napi->state);
}

各字段的作用：

字段 作用
poll_list 挂到 CPU 待轮询队列用的链表节点
gro_count / gro_list GRO（收包合并）用的链表和计数，CAN 场景基本不用
skb 存放当前处理的 skb
poll 轮询函数指针
weight 预算值，一次轮询最多处理多少包
dev_list 挂进 dev->napi_list，一个设备可以有多个 NAPI 实例
dev 反向指回网络设备
state 状态位图，NAPI_STATE_SCHED 表示已排入待轮询队列

set_bit(NAPI_STATE_SCHED, ...) 这一句容易看漏。它在注册时就把 SCHED 位置上了，意思是「初始状态视为已调度」，配合 napi_enable 的流程用。后面 napi_schedule_prep 会检查这个位来防止重复调度。

为什么轮询要有预算 #

如果不设上限，一个 poll 函数可以一直读，读到 FIFO 空为止。听起来很美好，实际上会把系统拖死：软中断长时间不返回，用户进程和内核线程全都得不到 CPU，网络看起来吞吐很高，但整机卡住。

预算值（weight）就是给轮询设一个上限：一次最多处理这么多包，处理完就交还 CPU。如果还有剩，内核会重新调度这一轮，但中间给了其他任务运行的机会。这个设计把「公平性」引进来，NAPI 的取舍很明确：牺牲一点延迟，换吞吐和公平。第一包到达时会有轮询的启动延迟，但换来的是高负载下系统不被打爆。

和中断下半部的区别 #

容易混淆的一点：NAPI 的 poll 也跑在软中断里，那它和 tasklet、workqueue 有什么不同？

机制 上下文 能否睡眠 适合场景
硬中断 中断上下文 否 极短的状态读取
tasklet 软中断上下文 否 短小的延迟处理
NAPI poll 软中断上下文（NET_RX_SOFTIRQ） 否 批量收包
workqueue 进程上下文 是 需要睡眠的活

NAPI 的特别之处在于它有预算、有完成判定、和中断开关联动。它不是通用的「延迟处理」，而是专为收包设计的有界批处理。

七、CAN 驱动里怎么用 NAPI #

CAN 为什么也需要 NAPI？这一节先回答这个问题，再看代码。

CAN 帧短，来得密 #

CAN 帧的数据段最多 8 字节（经典 CAN），整帧加上仲裁段、控制段、CRC、ACK 也就一百多位。在 1Mbps 总线上，一帧最短几十微秒就能传完。

算一下：1Mbps 总线跑满，每帧按 130 位算（含帧间隔），理论上一秒能传约 7700 帧。如果每个帧都触发一次中断，那就是一秒 7700 次中断。这个数量级已经足够把一颗 Cortex-A 核的中断处理能力吃掉相当一部分。

而 CAN 的典型用法恰恰是高频率小数据：车身控制里几十个节点周期性上报状态，10ms 一轮，每轮几十帧。这种流量模式就是为「密集短帧」量身定做的，也正是纯中断模型最吃亏的场景。

所以 CAN 引入 NAPI 的动机和网卡完全一样：把中断次数从「每帧一次」降到「每次唤醒收一批」。CAN 的 FIFO 天然适合批量读——一次进中断，把 FIFO 里攒的 6 条、32 条全读出来，只付一次中断的钱。

改造前的样子 #

Rockchip 的 CAN 驱动最初是每个接收中断里直接把帧读出来、直接送给协议栈：

c
static irqreturn_t rockchip_can_interrupt(int irq, void *dev_id)
{
    struct net_device *ndev = dev_id;
    struct rockchip_can *rcan = netdev_priv(ndev);
    u32 isr;

    isr = readl(rcan->base + CAN_INT);
    if (!isr)
        return IRQ_NONE;

    /* 直接在这里把帧读出来、处理掉 */
    ...
    return IRQ_HANDLED;
}

这段写法简单直接，问题是每帧一次中断，且中断处理函数里做了太多活（读寄存器、组 skb、送协议栈）。中断上下文里干活越久，其他中断被延迟得越厉害。

改造后的样子 #

改造成 NAPI，要做六件事。这六件事按顺序就是一次完整的改造。

第一件，在驱动私有结构里加 NAPI 结构体。

c
struct rockchip_can {
    struct can_priv can;
    struct napi_struct napi;
    /* ... 其他成员 ... */
};

struct can_priv 是 CAN 子系统的私有数据，dev->priv 指向的其实是包含它的外层结构。加 napi 之后，container_of 能从 napi 反推回 rockchip_can。

第二件，在 probe 里注册 NAPI。

c
netif_napi_add(ndev, &rcan->napi, rockchip_can_poll, 64);

四个参数：网络设备、NAPI 结构指针、轮询函数、初始预算。这里的 64 是 RK3568 实际改的时候用的值。

NAPI_POLL_WEIGHT 是内核给的默认值（64）。用它也行，但 CAN 的帧小，一次处理 64 帧不算多，可以按需调。

第三件，改中断处理函数，只做唤醒。

c
static irqreturn_t rockchip_can_interrupt(int irq, void *dev_id)
{
    struct net_device *ndev = dev_id;
    struct rockchip_can *rcan = netdev_priv(ndev);
    u32 isr;

    isr = readl(rcan->base + CAN_INT);
    if (!isr)
        return IRQ_NONE;

    /* 处理接收中断 */
    if (isr & RX_FINISH) {
        /* 禁用接收中断 */
        writel(readl(rcan->base + CAN_INT_MASK) | RX_FINISH,
               rcan->base + CAN_INT_MASK);
        napi_schedule(&rcan->napi);
    }

    /* 处理其他中断... */

    return IRQ_HANDLED;
}

读 CAN_INT 拿到中断状态，if (!isr) 返回 IRQ_NONE 告诉内核「这个中断不是我的」。这不是保守写法，是必要的：共享中断线上挂着多个设备，读到 0 就说明不是自己。

RX_FINISH 位置位时，先写 CAN_INT_MASK 把接收中断屏蔽掉，再 napi_schedule。顺序不能反。反了会出现这样的窗口：调度完 NAPI，还没来得及关中断，新帧到达又触发一次中断，重复调度同一轮询，NAPI_STATE_SCHED 位虽然能挡住一部分，但中断风暴的根子还在。

另一种更严谨的写法用 napi_schedule_prep 加 __napi_schedule：

c
if (napi_schedule_prep(&rcan->napi)) {
    rockchip_can_disable_interrupts(rcan);
    __napi_schedule(&rcan->napi);
}

napi_schedule_prep 检查 SCHED 位并做测试置位，返回 false 表示已经调度过了，直接跳过。这样能在驱动层挡住重复调度，比依赖硬件屏蔽更早一步。

第四件，实现轮询函数。

c
static int rockchip_can_poll(struct napi_struct *napi, int budget)
{
    /* budget 是本次调用最多处理的包数量 */
    struct rockchip_can *rcan = container_of(napi, struct rockchip_can, napi);
    struct net_device *ndev = rcan->can.dev;
    int work_done = 0;

    while (work_done < budget) {
        if (!(readl(rcan->base + CAN_STATE) & RX_BUF_FULL))
            break;

        rockchip_can_rx(ndev);
        work_done++;
    }

    if (work_done < budget) {
        napi_complete_done(napi, work_done);
        /* 重新启用中断 */
        writel(readl(rcan->base + CAN_INT_MASK) & ~RX_FINISH,
               rcan->base + CAN_INT_MASK);
    }

    return work_done;
}

container_of(napi, struct rockchip_can, napi) 从 NAPI 结构反推回驱动私有结构，这是内核里最常见的取父结构手法。

while 循环里先查 CAN_STATE 的 RX_BUF_FULL 位，FIFO 空了就 break。这个判断顺序很重要：先查后读，避免读到空 FIFO 拿到垃圾数据。work_done < budget 是循环的上界，防止无限制读。

收尾那段是核心判定：work_done < budget 说明 FIFO 已经掏空了（或者只剩不到预算的量），可以收工。napi_complete_done 把 NAPI 从待轮询队列摘掉，然后清 RX_FINISH 的屏蔽位，重新打开接收中断。

如果 work_done == budget，说明预算用完了但 FIFO 里还有数据。这时候既不能 napi_complete，也不能开中断——内核看到返回值和预算相等，会自动重新调度这一轮 poll 继续读。这个约定必须严格遵守，返回值和预算的关系就是驱动和内核之间的通信协议。

napi_complete_done 比 napi_complete 多传一个 work_done，它会把处理数量记进统计，供 netdev 的 gro_stats 和 busy poll 判断用。新内核优先用它。

第五件，open/stop 里开关 NAPI。

c
static int rockchip_can_open(struct net_device *ndev)
{
    /* ... 其他初始化代码 ... */
    napi_enable(&rcan->napi);
    /* ... 其他初始化代码 ... */
}

static int rockchip_can_stop(struct net_device *ndev)
{
    struct rockchip_can *rcan = netdev_priv(ndev);

    /* ... 其他清理代码 ... */
    napi_disable(&rcan->napi);
    /* ... 其他清理代码 ... */
}

napi_enable 必须在上报中断使能之前调用，napi_disable 必须在关闭中断之后调用。顺序错了会出现「中断来了但 NAPI 没启用」或者「NAPI 还在轮询但设备已经关了」。

napi_disable 是同步的，它会等到当前正在跑的 poll 结束才返回。所以不能在中断上下文或者持锁的地方调它。

第六件，卸载时删除 NAPI。

c
static int rockchip_can_remove(struct platform_device *pdev)
{
    struct net_device *ndev = platform_get_drvdata(pdev);
    struct rockchip_can *rcan = netdev_priv(ndev);

    /* ... 其他清理代码 ... */
    netif_napi_del(&rcan->napi);
    /* ... 其他清理代码 ... */
}

netif_napi_del 把 NAPI 从设备列表里摘掉，等待所有进行中的轮询结束。漏掉这一步，卸载模块时会出现 use-after-free。

完整改动清单 #

把六件事汇总成一张表，改驱动时照着勾：

步骤 位置 动作 漏掉的后果
1 私有结构体 加 struct napi_struct napi 无处存放 NAPI 状态
2 probe netif_napi_add poll 永不执行
3 中断处理函数 关中断 + napi_schedule 还是每帧一次中断
4 新增 实现 poll 函数 调度了没人处理

八、中断与轮询的配合 #

第七节讲的是骨架。这一节看一个更完整的实例，d_can 驱动，它把状态中断、收发中断、错误处理都揉进了 NAPI 框架里。这个例子最能说明中断和轮询如何分工。

中断处理：只读状态、关中断、调度 #

c
static irqreturn_t d_can_isr(int irq, void *dev_id) {
    struct net_device *dev = (struct net_device *)dev_id;
    struct d_can_priv *priv = netdev_priv(dev);

    priv->irqstatus = d_can_read(priv, D_CAN_INT);
    if (!priv->irqstatus)
        return IRQ_NONE;

    /* disable all interrupts and schedule the NAPI */
    d_can_interrupts(priv, DISABLE_ALL_INTERRUPTS);
    napi_schedule(&priv->napi);

    return IRQ_HANDLED;
}

这段代码一共四步，每一步都值得说。

d_can_read(priv, D_CAN_INT) 把中断状态读进 priv->irqstatus。注意这里读的是状态寄存器，不是数据。中断处理函数不碰接收 FIFO，一帧都不搬。

if (!priv->irqstatus) return IRQ_NONE; 这一句是共享中断线上的礼貌。读到全 0 意味着不是自己触发的，直接交还。漏了这一句，共享中断的兄弟设备会被误判成「已处理」，中断丢失。

d_can_interrupts(priv, DISABLE_ALL_INTERRUPTS) 关掉全部中断，不是只关接收。为什么这么狠？因为 poll 里要处理的不只是收包，还有状态变化、错误计数、发送完成。这些事件同样要暂存到 irqstatus 里统一处理，中断进来插一脚会打架。

napi_schedule(&priv->napi) 把设备挂进软中断队列。从这一刻起，活交给 poll。

把中断状态存进 priv->irqstatus 而不是直接处理，这个设计是关键。它把「发生了什么」和「怎么处理」分离，中断只负责记录，poll 负责执行。这也是 NAPI 能批量处理的根本原因。

轮询函数：按状态分派 #

c
static int d_can_poll(struct napi_struct *napi, int quota) {
    int lec_type = 0;
    int work_done = 0;
    struct net_device *dev = napi->dev;
    struct d_can_priv *priv = netdev_priv(dev);

    if (!priv->irqstatus)
        goto end;

    /* status events have the highest priority */
    if (priv->irqstatus == STATUS_INTERRUPT) {
        ...
    }
    else if ((priv->irqstatus >= D_CAN_MSG_OBJ_RX_FIRST) &&
             (priv->irqstatus <= D_CAN_MSG_OBJ_RX_LAST)) {
        /* handle events corresponding to receive message objects */
        work_done += d_can_do_rx_poll(dev, (quota - work_done));
    }
    else if ((priv->irqstatus >= D_CAN_MSG_OBJ_TX_FIRST) &&
             (priv->irqstatus <= D_CAN_MSG_OBJ_TX_LAST)) {
        /* handle events corresponding to transmit message objects */
        d_can_do_tx(dev);
    }

end:
    if (work_done < quota) {
        napi_complete(napi);
        /* enable all IRQs */
        d_can_interrupts(priv, ENABLE_ALL_INTERRUPTS);
    }

    return work_done;
}

入口的 if (!priv->irqstatus) goto end; 处理「空转」：被调度了但没活干，直接跳到收尾。这种情况在中断误触发或者状态已被别的路径清掉时会出现。

三个分支按优先级排：

  • 状态中断优先。priv->irqstatus == STATUS_INTERRUPT 说明是错误/状态变化事件，比收包重要。总线进 bus-off、错误计数越过警告线，这些必须先处理，不然继续收包没意义。
  • 接收中断其次。落到 D_CAN_MSG_OBJ_RX_FIRST 到 _LAST 这个区间，说明某个接收邮箱满了，调 d_can_do_rx_poll 批量读。
  • 发送中断最后。发送完成通知，调 d_can_do_tx 释放 skb、唤醒队列。

d_can_do_rx_poll(dev, (quota - work_done)) 里传的预算是剩余量，不是原始预算。前面状态处理如果已经花掉了一些 work_done，收包能用的就少了。这个细节保证总量不超预算。d_can_do_tx(dev) 不增加 work_done——预算约束的是收包，发送是另一条路。

状态分支里的处理 #

状态中断那条分支内容最多，值得展开：

c
priv->current_status = d_can_read(priv, D_CAN_ES);

/* handle Tx/Rx events */
if (priv->current_status & D_CAN_ES_TXOK)
    d_can_write(priv, D_CAN_ES, priv->current_status & ~D_CAN_ES_TXOK);

if (priv->current_status & D_CAN_ES_RXOK)
    d_can_write(priv, D_CAN_ES, priv->current_status & ~D_CAN_ES_RXOK);

读错误状态寄存器 D_CAN_ES，然后把 TXOK/RXOK 两个位写回去清零。这是典型的「写 1 清零」语义：写入 1 的位被清掉，写 0 的位不变。所以要用 & ~位 构造写值。

current_status 和 last_status 对比是状态机的核心：

c
if ((priv->current_status & D_CAN_ES_EWARN) &&
    (!(priv->last_status & D_CAN_ES_EWARN))) {
    netdev_dbg(dev, "entered error warning state\n");
    work_done += d_can_handle_state_change(dev, D_CAN_ERROR_WARNING);
}

当前有 && 上次没有 = 刚进入这个状态。反过来 当前没有 && 上次有 = 刚退出：

c
if ((!(priv->current_status & D_CAN_ES_BOFF)) &&
    (priv->last_status & D_CAN_ES_BOFF)) {
    netdev_dbg(dev, "left bus off state\n");
    priv->can.state = CAN_STATE_ERROR_ACTIVE;
}

CAN 的四个错误状态：error-active（正常）、error-warning（错误计数过 96）、error-passive（过 128）、bus-off（TEC 过 255，控制器自动脱离总线）。状态迁移必须是边沿触发的，每次 poll 都无条件上报会造成上层收到重复通知。

d_can_handle_state_change 的返回值加进了 work_done。这看起来奇怪——状态处理为什么算进收包预算？原因是这些处理也在 poll 上下文里消耗时间，计入预算才能保证单次 poll 的总工作量有界。

最后一段处理 LEC（Last Error Code）：

c
lec_type = d_can_has_handle_berr(priv);
if (lec_type)
    work_done += d_can_handle_bus_err(dev, lec_type);

LEC 记录了最近一次总线错误的具体类型：位错误、填充错误、CRC 错误、格式错误、ACK 错误。这些信息最终通过 can_get_berr_counter 上报给用户态，ip -details link show 里的 berr-counter 就是从这里来的。

收尾顺序：为什么 napi_complete 必须在开中断之前 #

c
if (work_done < quota) {
    napi_complete(napi);
    /* enable all IRQs */
    d_can_interrupts(priv, ENABLE_ALL_INTERRUPTS);
}

这两行的顺序是绝对不能反的。反了会丢中断：

假设先开中断，再 napi_complete。在两个操作之间的这个窗口里，如果新帧到达，硬件触发中断，d_can_isr 执行 napi_schedule。但此时 NAPI 的 SCHED 位还挂着（napi_complete 还没跑），napi_schedule 看到已调度，直接返回。紧接着 napi_complete 把 SCHED 位清掉，把设备从待轮询队列摘掉。结果：那一帧的数据还在 FIFO 里，中断已经关了又开，但没人再来轮询它。

正确的顺序是从根上避免这个问题：先 napi_complete（摘掉自己、清 SCHED 位），再开中断。这样窗口期内到达的中断会成功调度一轮新的 poll。

napi_complete 和 napi_complete_done 的行为一样，后者多记一笔统计。新代码用 napi_complete_done(napi, work_done)。

两个层面的「关中断」 #

这里有两套东西很容易混为一谈：

层面 谁在动 作用范围 目的
NAPI 状态位 napi_schedule / napi_complete 内核调度层 防止重复排入待轮询队列
硬件中断屏蔽 d_can_interrupts(DISABLE/ENABLE) 控制器寄存器 减少中断线触发次数

两层都需要。只做 NAPI 状态位，硬件还在不停拉中断线，CPU 照样被打搅，只是 poll 不重复进入而已。只做硬件屏蔽，中断是少了，但内核层没有「已调度」的记录，napi_schedule 会重复排队。

第七节里 rockchip_can_interrupt 用 writel 改 CAN_INT_MASK 是硬件层，napi_schedule 里的 SCHED 位是调度层。两个都在，机制才完整。

enable/disable 的配对 #

d_can_open 里 napi_enable(&priv->napi)，d_can_close 里 napi_disable(&priv->napi)。napi_enable 在 dev_open 时把 NAPI 状态重置成可用，允许后续 napi_schedule 生效。napi_disable 反过来，同时会等待正在跑的 poll 结束。

配对关系是硬要求。只 enable 不 disable，接口 down 掉之后 NAPI 仍能被调度，poll 会去读已关闭的控制器寄存器。

九、NAPI 预算与调节 #

预算是 NAPI 唯一的调节旋钮。调对了，高负载下既能吃饱又不噎着；调错了，要么吞吐上不去，要么延迟炸掉。

预算的确切含义 #

weight 是一轮 poll 最多处理的包数。它同时约束两件事：

  • 单次软中断的时长。预算 64 意味着最多读 64 帧就交还 CPU。
  • 重新调度的频率。预算用完返回，内核立刻再排一轮，中间给了其他软中断和进程一个机会。

预算太小，poll 频繁进出，调度开销占比上升。预算太大，一次 poll 占用软中断太久，其他网络设备的收包被延迟。

三种设置预算的方式 #

编译期给个初值：

c
netif_napi_add(ndev, &rcan->napi, rockchip_can_poll, NAPI_POLL_WEIGHT);
/* 或者直接写数字，RK3568 的实际改动用的是 64 */
netif_napi_add(ndev, &rcan->napi, rockchip_can_poll, 64);

经验起点是 16 或 32，跑起来看表现再调。

运行时通过 sysfs 动态改。

c
static ssize_t napi_budget_store(struct device *dev,
                                 struct device_attribute *attr,
                                 const char *buf, size_t count)
{
    struct net_device *ndev = to_net_dev(dev);
    struct rockchip_can *priv = netdev_priv(ndev);
    unsigned int budget;

    if (kstrtouint(buf, 0, &budget))
        return -EINVAL;

    priv->napi.weight = budget; /* 更新 NAPI 预算 */
    return count;
}

static DEVICE_ATTR_WO(napi_budget);

/* 在驱动初始化时创建 sysfs 接口 */
device_create_file(&ndev->dev, &dev_attr_napi_budget);

DEVICE_ATTR_WO 是只写属性宏。kstrtouint 解析用户输入，失败返回 -EINVAL。创建完以后可以直接写 echo 128 > /sys/class/net/can0/napi_budget。

运行时改的好处是不用重烧内核就能扫参数。注意改 weight 不是原子的，poll 正在跑的时候改会有一轮用旧值，无所谓。

按负载自动调。

c
static void rockchip_can_adjust_napi_budget(struct rockchip_can *priv)
{
    if (priv->rx_overflow_count > THRESHOLD) {
        priv->napi.weight = min(priv->napi.weight * 2, MAX_NAPI_WEIGHT);
    } else if (priv->rx_overflow_count == 0) {
        priv->napi.weight = max(priv->napi.weight / 2, MIN_NAPI_WEIGHT);
    }
}

逻辑很直白：FIFO 溢出了说明预算不够（读得比来得慢），翻倍；一次溢出都没有说明预算有余量，减半。上下限用 min/max 夹住，防止调飞。

阈值的取法有讲究。THRESHOLD 设 100 的话，只有当溢出计数累积过 100 才翻倍，反应偏慢。设太小又会被偶发抖动带偏。经验上取「一个统计周期内能接受的溢出数」，比如 10。

自动调节挂在哪 #

调节函数必须在接收路径里调用，才能反映真实负载：

c
static int rockchip_can_rx(struct rockchip_can *priv, int limit) {
    /* 接收处理逻辑 */
    /* ... */

    rockchip_can_adjust_napi_budget(priv);

    return processed;
}

注意调用的位置。放在 poll 里的 while 循环外面（每次 poll 调一次），比放在循环里面（每帧调一次）合理。每帧都调会让预算疯狂震荡。

还有一个前提：rx_overflow_count 必须真的有人维护。它得在检测到 FIFO 满、丢弃新帧的时候自增，并在统计周期结束时清零。没有这个计数器，整个自动调节就是空转。

三种方案的取舍 #

方案 生效范围 好处 代价
编译期常量 全局固定 简单，零运行开销 场景变了要重编
sysfs 动态 单次运行 可扫参数，不用重编 需要人工值守
负载自适应 持续 自动跟随负载 逻辑复杂，调不好会震荡

先用编译期常量把基本功能跑通，再用 sysfs 扫出合适区间，最后决定要不要上自适应。跳着来容易在参数上纠缠不清。

预算和其他优化的配合 #

预算只是 NAPI 这一层。CAN 驱动还有几个可调的硬件参数，效果叠加：

手段 位置 效果
加深 rx-fifo-depth 设备树 吸收突发，减少溢出
配硬件验收滤波器 驱动/设备树 少收无关帧，直接降低负载
提高 NAPI 预算 weight 单轮多读，减少调度次数
中断亲和性 /proc/irq/N/smp_affinity 多路 CAN 分散到不同核
DMA 传输 控制器配置 减少 CPU 搬运开销

中断亲和性这块，多路 CAN 的场景值得单独做：

bash
echo 2 > /proc/irq/45/smp_affinity_list
echo 3 > /proc/irq/46/smp_affinity_list

把 can0 和 can1 的中断分到不同核上，两个控制器的中断处理并行跑，不互相排队。smp_affinity 是位掩码（十六进制），smp_affinity_list 是核编号列表，后者更好读。

观测预算效果 #

改完预算，用这三个观测点看效果：

bash
# 中断次数（改完应该下降）
cat /proc/interrupts | grep can

# 收包与丢包（dropped/overrun 应该为 0）
ip -s link show can0

# 软中断分布
cat /proc/softirqs | grep NET_RX

/proc/softirqs 的 NET_RX 那一行按 CPU 分列。所有 CPU 都跟着涨，说明 RPS 在扩散处理；只有一列涨，说明单核在扛，可以考虑加亲和性。

压力对比的做法是固定发送端，改预算，看两个数：中断计数的增速、dropped 是否为零。中断降下来了且没有丢包，就是这个场景下的合适值。

预算调不动的三种情况 #

改了预算没效果，检查这三处：

  • 中断根本没走 NAPI。看代码里 napi_schedule 到底有没有被调到。有的驱动改了 poll 但中断处理函数还留着老的直接处理路径，两条路同时在跑。
  • 中断是别的源。/proc/interrupts 里数的是整条中断线。CAN 控制器和别的外设共享中断时，数的不是 CAN 的。看 ip -s 的包数对比更准。
  • FIFO 太浅，轮询没料。rx-fifo-depth 只有 6，中断进来时 FIFO 里就一条，poll 读一次就退出。加深到 32 之后批量效果才出得来。这个依赖关系容易忽略：NAPI 的收益依赖 FIFO 能攒得住。

十、RK3568 上的验证实录 #

前面九节是拆开讲的，这一节把它们串成一次真实改动。板子是 OK3568-C，内核来自 OK3568-linux-source。

改动方案 #

三条，按依赖顺序：

  1. 设备树中原节点配置为 CANFD，修改为 CAN。目标是走经典 CAN 2.0 路径，和老节点互通。
  2. 设备树中修改节点接收缓冲区，由原来的 6 改为 32。给软件留出批量处理的窗口。
  3. 修改驱动中的中断处理机制，原来是进中断直接处理，修改为 NAPI 的方式进入中断进行轮询处理。

第 1 条和第 3 条是配套的：切成经典 CAN 之后帧更短、更密，NAPI 的收益才明显。如果继续跑 CAN FD，帧长一点，中断频率低一些，改 NAPI 的紧迫性反而没那么高。

改前的基线 #

先测旧状态，不然改完没法对比。

bash
ip -details link show can0
cat /proc/interrupts | grep -i can

改造前是 CANFD 节点，输出里带 <FD>：

text
can0: <NOARP,ECHO> mtu 72 qdisc pfifo_fast state DOWN mode DEFAULT
    link/can  promiscuity 0
    can <FD> state STOPPED (berr-counter tx 0 rx 0) restart-ms 0
      bitrate 500000 sample-point 0.875
      dbitrate 2000000 dsample-point 0.750

mtu 72 是 FD 的特征（FD 帧最长 64 字节数据，加上头部）。改完之后应该变成 mtu 16 且没有 <FD>，说明经典 CAN 生效了。这一条比翻代码可靠得多。中断计数也留一份基线，用来和改完对比。

三处具体修改 #

设备树。 文件 kernel/arch/arm64/boot/dts/rockchip/OK3568-C-common.dtsi：

dts
&can0 {
	compatible = "rockchip,can-1.0";
	assigned-clocks = <&cru CLK_CAN0>;
	assigned-clock-rates = <300000000>;
	pinctrl-names = "default";
	pinctrl-0 = <&can0m0_pins>;
	rx-fifo-depth = <32>;
	status = "okay";
};

对照第二章的 SoC 级原始定义，板级改动只覆盖四个属性：compatible 换成 rockchip,can-1.0、assigned-clock-rates 定 300MHz、rx-fifo-depth 提到 32、status 打开。reg、interrupts、clocks、resets 全部继承。

内核配置。 文件 kernel/arch/arm64/configs/OK3568-C-linux_defconfig：

bash
CONFIG_CAN=y
CONFIG_CAN_ROCKCHIP=y
CONFIG_CANFD_ROCKCHIP=y

y/n/m 的语义再确认一遍：y 编译进内核，n 不编译，m 编成模块加载。

驱动。 文件在 drivers/net/can/rockchip/，按第七节的六步改：加 napi_struct、probe 里 netif_napi_add(..., 64)、中断处理函数改成关中断加 napi_schedule、实现 poll、open/stop 里配对 enable/disable、remove 里 netif_napi_del。

网络设备中断处理的通用背景，可以对照《网络设备驱动的中断处理》那篇看。

编译烧写 #

bash
./build.sh kernel

产物在 OK3568-linux-source/kernel/boot.img。只改设备树和驱动的话，单独烧这个分区就够，把 boot.img 放进板子的升级工具。烧完上电，先看 dmesg 有没有 probe 记录，再看 ip link。

验证步骤 #

bash
# 1. 模式对不对
ip -details link show can0 | head -5

# 2. 拉起来
ip link set can0 type can bitrate 500000
ip link set can0 up

# 3. 状态位
ip -details link show can0 | grep state

# 4. 回环自收
ip link set can0 down
ip link set can0 type can bitrate 500000 loopback on
ip link set can0 up
candump can0 &
cansend can0 123#DEADBEEF

第 1 步确认 mtu 16 且无 <FD>。第 3 步 state 应该是 ERROR-ACTIVE。第 4 步 candump 要打出 can0 123 [4] DE AD BE EF。

压测对比 #

自收过了，上压力，改前改后各跑一次：

bash
cangen can0 -g 0 -I 7ff -L 8 &
sleep 10
ip -s link show can0
cat /proc/interrupts | grep -i can

比三个数：中断计数、收包数、dropped。理想结果是中断计数显著下降、收包数持平或上升、dropped 为 0。

如果中断降了但 dropped 涨了，说明预算不够，rx-fifo-depth 再加深或者 weight 调大。如果两个都没变，napi_schedule 没被执行到，回代码查。

LED 状态指示 #

一个可选的加法：让板子上的 LED 跟着 CAN 收发闪，一眼看出总线有没有活动。思路是在 poll 里收到帧之后翻转一个 GPIO：

c
/* 每收到一帧就翻转 LED，高负载下肉眼看到的是常亮 */
rockchip_can_led_toggle(rcan);

实际做的时候限制一下频率，不然高负载下 LED 闪得看不出规律。按「收到 N 帧翻转一次」或者「100ms 内有过收发就亮」都行。后者更实用，poll 里记一个时间戳，用定时器或者 workqueue 在 100ms 后熄灯。

ndo_start_xmit 里也可以同样加一份，收发分开用两个灯，收一个发一个。这是排查手段，不是必须功能。现场没有分析仪的时候，一个会闪的灯能省很多时间。

十一、常见故障与排查 #

按现象分。每条给排查顺序，不给结论——同一个现象有好几个原因。

接口根本不出现 #

ip link 里没有 can0，/sys/bus/platform/devices/ 里也找不到节点。按顺序查：

bash
# 设备树里节点到底编进去没有
ls /proc/device-tree/ | grep can

# 有没有 probe
dmesg | grep -i can

# 驱动骨不骨干
ls /sys/bus/platform/drivers/ | grep can

/proc/device-tree/ 是运行时的设备树，能看到就说明 dtb 编进去了。看不到就是 dtsi 没改对或者烧错了 boot.img。

dmesg 干净得像什么都没发生，说明连 probe 都没进——status 还是 "disabled"。有 probe 记录但失败，看错误码：-ENODEV 查 clocks，-EBUSY 查 reg，-ENXIO 查 interrupts，-EPROBE_DEFER 是依赖没就绪不算错。

有接口但 up 不起来 #

bash
ip link set can0 up
# RTNETLINK answers: Invalid argument

这个错误常见于波特率没配就 up。CAN 必须先设 bitrate，也就是 ip link set can0 type can bitrate 500000 再 ip link set can0 up。

另一个原因：assigned-clock-rates 和 bitrate 算不出精确的位定时。CAN 的位定时要求时钟能被分频出目标波特率，误差要在容差内。时钟给 300MHz 配 125kbps 这类组合凑不出理想采样点，换 200MHz 时钟再试。

RTNETLINK answers: Device or resource busy 是接口已经 up 了还在改参数。先 down。

up 了但收不到 #

最常见的一类，三个方向。

中断没进来。 自收一次，cat /proc/interrupts | grep -i can 的计数不涨就是中断没通。查 interrupts 属性的中断号和触发类型。

中断进了但数据没上来。 计数涨、ip -s 的 RX 也涨，但 candump 没输出。这是 netif_receive_skb 之前的环节有问题，或者 NAPI 的 poll 没把 skb 正确送上去。

引脚没复用。 内部回环能过、外部不通，基本就是 pinctrl 错了，用 cat /sys/kernel/debug/pinctrl/*/pinmux-pins | grep -i can 看。看不到 CAN 相关引脚，说明 pinctrl-0 指的 group 没生效。检查 group 名字和 M0/M1 的选择是否和板子实际接线一致。

发送失败 #

cansend 报 Network is down：接口没 up。

发送成功但没 ACK，ip -details 里 berr-counter tx N 疯涨：总线上没有第二个节点应答。CAN 需要至少两个节点，单节点必须开 loopback。

发送队列满，ndo_start_xmit 返回 NETDEV_TX_BUSY：tx-fifo-depth 太浅或者对端太慢。加深 tx-fifo-depth，或者在上层控制发送速率。

高负载丢帧 #

ip -s link show can0 的 RX dropped 或 overrun 在涨。按从易到难处理：

  1. 加深 rx-fifo-depth，6 提到 32。
  2. 提高 NAPI 预算，64 提到 128。
  3. 加硬件验收滤波器，只收需要的 ID。
  4. 多路 CAN 分开中断亲和性。

前两个改设备树就行，第三个要改驱动或者用过滤规则，第四个要动系统配置。用户态过滤是 candump can0,123:7FF 这种写法，能减少 candump 的负担，但帧已经到了内核，救不了 FIFO 溢出。硬件过滤要用 can-filters 或者驱动里配。

总线错误状态 #

ip -details link show can0 | grep state 看到 ERROR-PASSIVE 或 BUS-OFF。

ERROR-PASSIVE 说明错误计数过了 128。查波特率是否和总线上其他节点一致、终端电阻是否装了（120 欧，两端各一个）。

BUS-OFF 是 TEC 过 255，控制器自动脱网。恢复有三条路：

bash
# 1. 重启接口
ip link set can0 down
ip link set can0 up

# 2. 配自动恢复
ip link set can0 type can restart-ms 100

# 3. 硬件复位

restart-ms 是自动恢复间隔，配了之后控制器会自动尝试重新接入总线。现场调试时建议配上，省得每次手动重启。

多路 CAN 互相干扰 #

can0 和 can1 都开了，其中一个收不到。先确认两者的 interrupts 中断号不同、pinctrl-0 的引脚不重叠。M0/M1 两套引脚如果被两路 CAN 各占一套但实际是同一个控制器的复用组，就会打架。

再看中断亲和性，cat /proc/interrupts | grep -i can 两行的 CPU 列如果是同一个核，用 smp_affinity_list 分开。压在一个核上会互相延迟。

排查用的几条命令 #

集中列一遍，出问题先跑这几条：

bash
dmesg | grep -i can
ip -details -statistics link show can0
cat /proc/interrupts | grep -i can
cat /proc/softirqs | grep NET_RX
ls /sys/class/net/can0/
cat /sys/kernel/debug/pinctrl/*/pinmux-pins | grep -i can

ls /sys/class/net/can0/ 能看到 statistics/ 目录，里面的 rx_packets、rx_dropped、tx_packets 都是独立文件，cat 单个比 ip -s 更细。

一句话总结各层的分工 #

设备树决定硬件能不能被找到，内核配置决定驱动在不在，驱动代码决定中断怎么处理，NAPI 决定高负载下的效率，工具和计数决定你怎么知道它坏了。四层依次往下，上一层错了下一层全是白费。排查就按这个顺序走：先确认节点在，再确认驱动绑上，再确认中断进得来，最后才谈性能和丢帧。跳层排查是浪费时间。
