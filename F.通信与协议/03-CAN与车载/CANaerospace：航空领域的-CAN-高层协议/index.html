这篇只谈 CANaerospace 本身：它为什么存在、报文怎么排、标识符怎么分、时间触发怎么算、跟 CANOpen 差在哪。CAN 控制器的寄存器配置、收发器选型、Rockchip 平台的驱动适配都不在范围内，那些看同目录的《CAN 总线基础》《CANOpen 协议》《Rockchip CAN 驱动》。文中位宽、字段、时间参数以公开的 CANaerospace 规范与维基材料为准；规范没有写死的地方，我会明确标成推断。

一、CANaerospace 是什么 #

CANaerospace 是架在 CAN 之上的高层协议。1998 年，Stock Flight Systems 为航空应用开发了它。规范免费公开，谁都能下载 PDF，谁都能照着实现，不收任何授权费。

它面对的对象是 LRU——Line Replaceable Unit，航线可更换单元。航电设备按这个思路设计：一个盒子坏了，地勤整块拆下来换新，不用整机返厂。LRU 之间要交换数据，线束越少越好，CAN 那两根差分线正好对味。

光有 CAN 不够。CAN 只规定到帧，不规定这帧里的 8 个字节该怎么解释。同样的 0x55AA，一家厂商当电压，另一家当转速，总线就废了。CANaerospace 补的就是这一层：定义 CAN 物理层特性、网络层、通信机制、数据类型、航空坐标系，让不同厂商的 CAN LRU 真能互通。

它的原始动机很明确：在系统级标准化 CAN LRU 之间的接口。不是定一颗芯片，是定一份接口契约。

2001 年，NASA 把它当作 AGATE Databus Standard 发布出来。AGATE 是 Advanced General Aviation Transport Experiments，通用航空运输试验计划，成果直接灌进了一批轻型飞机的航电方案。这一点很关键——它说明 CANaerospace 不是某个厂商的自留地，它进过官方标准文档。

应用面铺得比想象中宽：

  • 科研机：SOFIA 平流层红外天文台，一架波音 747SP 背 2.5 米口径望远镜，机上用好几套 CANaerospace 网络做实时计算机互联。
  • 飞行模拟器：整舱座舱设备连到仿真主机，Eurofighter Typhoon 的模拟器就这么干。
  • 无人机：意大利把它当作 UAV 的数据总线技术。
  • 通用航空：多套通航航电系统把它当通信网络。

二、它要解决的航空问题 #

Bosch 的 CAN 规范允许报文周期发，也允许非周期发。但它不管三件事：数据怎么表示、节点怎么寻址、面向连接怎么搞。

CAN 的通信模型是 Anyone-to-Many，简称 ATM。一帧发出去，总线上所有站都收到。好处是数据天然一致——大家看到的是同一份东西。坏处同样明显：CAN 本身没有节点寻址，而节点寻址是 Peer-to-Peer 通信的地基。你想让 A 单独问 B 要个值，CAN 没法表达「只发给 B」。

航空场景偏偏需要 PTP。理由不复杂：飞机上的设备要互相盯着。飞控想知道大气数据计算机还活着、算得对不对；显示系统想知道惯导有没有漂。没有点对点通道，系统监控就落不了地。

所以 CANaerospace 在 CAN 之上补了 ISO/OSI 的第 3、4、6 层功能，把节点寻址和统一的 ATM/PTP 机制做出来。PTP 让任意两个站之间建立 client/server 交互，可以临时建，也可以长期挂着。同一时刻可以有多组交互在跑，同一个节点在一个交互里是 client，在另一个交互里当 server，互不干扰。

这套机制叫 Node Service Concept。它能干两件事：把系统功能拆到多个站上分布式跑；故障时控制系统动态重构。

原始设计要求一共十条，逐条对应一个具体痛点：

设计要求 解决的问题 落地手段
民主网络 不要主从、不要总线控制器，掐掉单点失效 每个节点对总线的访问权完全相同
自识别报文格式 接收方要能认出这条数据是谁发的、是什么 报文头带 Node-ID 与 Data Type
连续消息编号 接收方要能判断有没有丢帧、迟帧 每个标识符独立递增的 Message Code
报文状态码 接收方要能判断数据本身好不好 Service Code 携带自检与合法性信息
紧急事件信令 异常要能广播出去，不能闷在节点里 EED 通道，最高优先级
节点服务接口 节点之间要能点对点说话 Node Service，面向连接加无连接
预定义标识符分配 不能让每家自己拍脑袋定 ID 标准分配表 300～1799，另留用户自定义段
实现成本低 航安关键系统的测试与认证太贵 代码量刻意做小，减少验证面积
可扩展 未来加东西不能推翻重来 所有定义留扩展位，留用户自定义区

这张表里，民主网络和免费可得是两条最不像航空标准的条款。航空领域习惯命令/响应、习惯总线控制器、习惯指定供应商。CANaerospace 反过来：谁都不是主，谁也不收钱。

物理层写死了什么 #

互操作性不能只靠软件。线上电平不对，报文格式再漂亮也没用。所以 CANaerospace 在 ISO 11898 的基础上，把电气特性、收发器要求、数据速率及其容差都写清楚了。

重点落在三块：

  • 位定时计算：波特率精度怎么算、采样点定在哪。这两个参数决定一帧能不能被正确采样，也决定晶振漂移能忍多少。
  • 抗电磁干扰能力：飞机上电机、继电器、雷达一堆干扰源，物理层要说明白在这种环境下怎么活。
  • 布线工程：CAN 连接器、线缆走向、设计准则，目标是电磁兼容性最大化。

这几项是硬约束，不是建议。你在实验室里拿两根杜邦线跑 CAN 能通，不代表装到机上能通。

从 ATM 到 PTP，靠的是标识符分组 #

要让 ATM 和 PTP 在同一根总线上共存，就得把两类通信隔离开。CANaerospace 的做法是划 CAN 标识符分组，每一组构成一个 Logical Communication Channel，简称 LCC，每个 LCC 绑定一种通信类型。

用户自定义的 LCC 还留了口子，让系统设计者按具体项目裁剪。这一点决定了 CANaerospace 既是标准，又能变形。

三、消息 ID 的三段结构 #

CANaerospace 用的是 29 位扩展标识符，不是 11 位标准帧。原因很实际：11 位只有 2048 个编号，光是给节点和参数分坑位就花光了，还得留用户自定义区，根本不够用。

29 位标识符在 CANaerospace 里不是一串随便排的号。它同时承担两件事：一是划出通信信道，二是定位具体的参数。理解这两件事，才看得懂总线上跑的是什么。

第一层：标识符分组划出信道 #

规范按 CAN 标识符分组，每一组是一个 Logical Communication Channel，也就是 LCC，每个 LCC 绑定一种通信类型。因为 CAN 的仲裁规则是编号越小优先级越高，所以这组编号同时就是优先级表。

信道 全称 通信类型 干什么 相对优先级
EED Emergency Event Data Channel 只走 ATM 需要立即动作的消息，系统降级、重构 最高
NSH High Priority Node Service Data Channel PTP 高优先级 client/server 交互、测试维护 高
NSL Low Priority Node Service Data Channel PTP 低优先级 client/server 交互 中高
NOD Normal Operation Data Channel ATM 为主 正常工作数据，按标识符分配表走 中
UDH High Priority User-Defined Data Channel 设计者定 装不进其他信道的自定义通信 中低
UDL Low Priority User-Defined Data Channel 设计者定 同上，低优先级段 低
DSD Debug Service Data Channel 设计者定 仅开发测试期用，正常运行不发 最低

这张表有两个细节值得盯住。

第一个：信道顺序就是优先级顺序，而这个顺序是按「相对重要性」排的。紧急事件排最前，调试排最后。总线仲裁失败的那个节点会自动退让，无需软件干预——这是 CAN 硬件给的，CANaerospace 只是把编号分配合规化。

第二个：UHD/UDL 与 DSD 这两类信道，规范只限定编号范围，报文内容与通信类型（ATM 还是 PTP）全交给系统设计者。规范原文还专门加了一句：为了保证互操作性，强烈建议尽量少用这些信道。这句话翻译过来就是——留了口子，但别滥用。

第二层：报文头里的三段 #

看清「谁发的、什么类型、第几条」，靠的是每个 CANaerospace 报文开头那 4 个字节。4 个字节拆成四个字段，每个字段一个字节：

偏移 字段 位宽 ATM 语义 PTP 语义
0 Node-ID 8 位 发送该报文的节点 被寻址的节点（client 或 server）
1 Data Type 8 位 载荷按哪种数据类型解释 同左
2 Service Code 8 位 参数完整性信息：自检结果、合法性标志 该次交互的服务编号
3 Message Code 8 位 该标识符报文的连续计数，0～255 循环 与 Service Code 配合，细化服务

把这四个字段按语义归并，就是三段结构：

text
29 位扩展 ID  ──┐
                ├── 定位：这是哪一类数据 / 哪个参数 / 哪条信道
                │
报文头 byte 0 ──┼── 段一：节点 ID ── 谁发的（PTP 下是谁收）
报文头 byte 1 ──┼── 段二：数据类型 ── 这堆字节怎么解释
报文头 byte 2 ──┤   （服务码，ATM 下是质量，PTP 下是服务号）
报文头 byte 3 ──┴── 段三：消息码 ── 第几条

三段各自解决一个具体问题：

  • 节点 ID 段：这条报文归谁。ATM 通信（EED、NOD）里它指发送节点；PTP 通信（NSH、NSL）里它指被寻址的节点。PTP 下 Node-ID 填 0 表示广播，即发给网络里所有站。
  • 数据类型段：这堆字节怎么读。是浮点还是整数，整数占几个字节，都从 CANaerospace 数据类型表里取编号。表里还留了用户自定义类型的入口。
  • 消息码段：这是第几条。发送节点对每个特定 CAN 标识符独立维护一个计数器，每发一帧加一，到 255 后回绕到 0。接收方拿它跟上一帧的计数一比，丢帧、迟帧立刻暴露。

为什么这个设计比「功能码」更贴航空 #

多数高层协议的做法，是把功能语义塞进标识符，让标识符本身当「地址」用。CANaerospace 的做法反过来：标识符负责定信道和参数位置，真正解释语义的字段搬进载荷头。

代价摆在明面上——每个报文固定花掉 4 个字节做头，载荷只剩 4 个字节，等于一半带宽没用来传数据。

收益也摆在明面上：

  • 接收节点不需要维护一张庞大的映射表，也不用记住「这个 ID 属于哪个服务」。拿到帧，读头四个字节，来源、类型、质量、序号全齐。
  • 报文可以独立解读。抓一个包就能判断它好不好，不需要上下文，不需要握手历史。对故障排查和系统监控来说，这一点省掉大量工具链。
  • 冗余做起来简单。两路总线各跑一份，接收端按 Message Code 和 Service Code 挑质量好的那份，不需要额外协议。

规范原文对「浪费带宽」这个质疑的回应很直接：就算不用这个头，这些信息也得占载荷字节。该花的信息量省不掉，只是换个地方放。

一个容易踩的坑 #

三段结构里的「节点 ID」跟「CAN 标识符里的节点信息」不是同一回事，别混着用。标识符段决定的是通信信道与该信道内的参数位置；节点 ID 段决定的是这条报文的归属。排查问题时先分清看的是哪一层，否则日志对不上号。

四、节点服务消息 #

CAN 只给广播。CANaerospace 在广播之上长出点对点，靠的就是 Node Service。

这套机制能干什么 #

PTP 让网络中任意两个站之间建立 client/server 交互，可以临时建一次就拆，也可以长期挂着。同一时刻允许多组交互并行，同一个节点在一个交互里是 client、在另一个里是 server，两种角色同时成立，互不冲突。

规范拿以太网做类比：这套机制同时支持面向连接与无连接两类交互，对应关系就是 TCP/IP 与 UDP/IP。面向连接的那类有建立、有维持、有拆除；无连接的那类发完就走，不保证对端在不在。

落到用途上，Node Service 干三类活：

用途 说明
功能分布式部署 把系统功能拆到多个站上跑，不必集中在一个计算机里
故障时动态重构 某站失效后，由其他站接管或切换配置
测试与维护 NSH/NSL 也用于承载测试、维护类功能

消息怎么表达「服务」 #

Node Service 走 NSH 与 NSL 两个信道。一个服务由报文头里的两个字段共同指定：

  • Service Code：指定这是哪一类服务。
  • Message Code：与 Service Code 配合，把服务细化到具体哪一个。

这里跟 NOD 信道的语义不同。NOD 里 Service Code 表示参数完整性，Message Code 是连续计数；NSH/NSL 里这两个字段都变成服务标识的一部分。同一个字段在不同信道下语义不同，写协议栈的时候这是最容易写错的地方。

强制项：节点识别服务 #

规范里有一条是强制的：每个 CANaerospace LRU 都必须响应 Node Identification Service。

这条服务的作用是扫描网络——谁在线、每个在线的 LRU 用的是哪一份标识符分配表、版本号是多少。系统设计者可以用自定义的标识符分配表，但前提是能查出来对端用的是哪一份，否则两边理解不一致，总线看着通、数据全错。

这条强制项的工程价值很高。装机前的自检、故障后的定位、混装不同厂商设备时的排查，都靠它。它也解释了为什么 CANaerospace 敢允许用户自定义分配表——有个强制的自描述入口兜底。

服务的组合方式 #

把 Node Service 想成一套很小的 RPC 就对了。请求方选 NSH 或 NSL（决定优先级），填 Node-ID（发给谁，填 0 是广播），填 Service Code 与 Message Code（调哪个服务），参数塞进 4 字节参数字段。响应方原路返回，Node-ID 填请求方的编号。

4 字节参数装不下复杂结构，这是硬限制。真要做大数据量传输，只能在协议之上自己分段——规范没把这条路封死，但也没替你铺好。

五、数据消息与传输 #

字节序：大端，定死 #

航空领域的实时控制系统，多数用大端处理器架构。CANaerospace 因此把大端定成规范。大端的意思是最重要的位排在最左边，在 CANaerospace 上先被发送。

这条不写死会出事。你拿一颗小端 MCU 接进来，浮点数不转字节序就发出去，对面解出来是个完全不同的值，而且不会报错——它只是「理解成另一个数」。这是排查起来最费时间的一类故障。

项目 规定
字节序 大端（big endian）
位序 最高位在最左，先发
依据 航空实时控制系统多用大端处理器
涉及范围 所有多字节参数

报文结构：4 加 4 #

自识别格式的落地方式，是把载荷切成两段：4 字节报文头加 4 字节参数区。

text
CAN 数据帧（8 字节载荷）
┌──────────┬──────────┬──────────┬──────────┬──────────────────┐
│ Node-ID  │Data Type │Service Cd│Msg Code  │  4 字节参数区     │
│  1 字节  │  1 字节  │  1 字节  │  1 字节  │                  │
└──────────┴──────────┴──────────┴──────────┴──────────────────┘
     └──────────── 报文头 4 字节 ────────────┘ └─ 载荷 4 字节 ─┘

4 字节参数区能装什么？一个 float32，或者两个 int16，或者四个 uint8，或者一个 uint32。再多就得自己拆帧。这个尺寸是 CANaerospace 的硬边界，也是它面向「单个参数一帧」这种设计哲学的体现：一帧一个物理量，简单、可预测、好验证。

Data Type 字段的值取自 CANaerospace 数据类型表。表里列出每个类型的编码与长度，也留了用户自定义段的入口。

类别 说明
整数 按字节数区分，如 1/2/4 字节整数
浮点 单精度浮点为主

这里只给类别，不给具体编码表——编码表在规范里，各版本会有调整，照抄数字容易过时，也容易抄错。真要用，去查手上那份规范的 Data Type List。

标识符分配表：300～1799 #

CANaerospace 标准标识符分配表把 CAN 标识符 300 到 1799 这段留出来，逐个分配给具体参数。规范里给出摘录表，每一项是「标识符 + 参数名 + 类型」的组合。

这个范围之外的编号由系统设计者自己安排，或者用于信道划分与用户自定义段。

分配表不是死的。系统设计者可以用自定义的分配表，前提有两条：一是通过 Node Identification Service 能被查出来；二是表里留了用户自定义段可以扩展。

坐标系与物理单位 #

为了互操作，光统一次序和类型还不够。同样的参数名，一家用右手系、一家用左手系，俯仰角正负号相反，接起来照样是错的。

所以规范定义了航空专用坐标系，连同符号约定（sign conventions）和物理单位一起写死。三样东西加上预定义标识符分配表，把 CANaerospace 网络上的流量描述成无歧义的一套定义。

六、时间触发与确定性 #

这一章是 CANaerospace 最硬的部分，也是它跟通用协议拉开差距的地方。

先纠正一个概念 #

飞行安全关键系统有一个共同要求：行为要被精确定义、分析、测试，以通过正式认证。很多人把这个要求理解成「时间确定性」，规范原文明确说这是误读——真正的目标是可预测性（predictability）。

两个词差在哪？时间确定性说的是「每次都必须在同一个时刻发生」。可预测性说的是「在任何可预见的条件下，行为都在已知的边界内」。前者要求精确的时钟，后者要求有界的最坏情况。

后者的门槛低得多，也实用得多。你到底需要多高的时间精度，取决于具体应用，得由系统分析量化出来。真正必须达到的目标只有一个：向认证当局（FAA、EASA 这类机构）证明，这个安全关键系统在有预见性的情况下行为可预测。

CANaerospace 提供的正是这个。

Time Triggered Bus Scheduling #

这套机制叫 Time Triggered Bus Scheduling，时间触发总线调度。核心只有一句话：限制每个节点在一个 minor time frame（次时间帧）内可以发射的报文条数。

规则拆开看：

  • minor time frame 的长度在系统设计初期就定下来，不是运行时算的。
  • 每个节点在单个 minor time frame 内的最大报文条数可以不同，逐节点计算。
  • 如果系统设计允许，这个上限里可以预留增长余量。
  • 每个节点在产生网络流量时，必须始终遵守自己的发送时间表。这一条是整套机制成立的前提，破一次就全盘失效。
  • 节点之间是否同步发送顺序与发送时刻，规范既不要求也不禁止。

最后这条容易被忽略。很多时间触发协议强制全总线时钟同步，CANaerospace 不强制。它只要求每个节点管住自己的发送配额，剩下交给 CAN 的仲裁机制。

为什么要压到 50% 带宽 #

CAN 错误帧会吃掉带宽。网络或节点出故障时，错误帧会挤占本来用于正常通信的带宽，行为就变得不可预测。

规范的应对很保守：建议把带宽使用率限制在最大带宽的 50% 以内，把不可预测性压下去。

这个数字不漂亮，但有用。Time Triggered Bus Scheduling 需要余量，它不追求带宽利用率最优。换来的是一个安全、直接、可证明的构法——造得出可认证（可预测）的系统。

代价就是：带宽浪费一半。在机载环境里，这个交换是划算的。总线成本远低于认证成本。

延迟上界能算出来 #

这是 CANaerospace 最值钱的一个结论。

采用 Time Triggered Bus Scheduling 后，调度表里任何一条报文的延迟都不会超过：一个 minor time frame 的 50%，加上最长那条报文的传输时长。

写成式子：

text
最大报文延迟  ≤  0.5 × minor time frame 长度  +  t_最长报文

其中：
  minor time frame 长度   —— 系统设计阶段确定
  t_最长报文              —— 由帧长与波特率算出

有了上界，控制律的时间预算就能倒推。这是认证材料里必须有的一行字。

另外，这套机制还削弱了报文优先级的影响。原因很直接：每个节点都被要求给自己的发送量限流，谁也没法靠高优先级长期霸占总线。优先级还在，但不再是决定性的。

晶振误差会带来什么 #

节点本地晶振有容差，节点之间又没有时间同步，各个 minor time frame 会互相漂移。

规范说这不影响报文延迟，前提是所有节点的 minor time frame 时长足够接近。注意这个前提——是「时长」接近，不是「相位」对齐。相位漂没关系，节拍长短不一致才有问题。

还有一条硬要求：所有非周期报文都必须算进带宽管理的账里。漏算一条非周期报文，上界就作废了。

故障条件下的责任划分 #

规范不替你定义故障行为，它把这件事推给系统设计者。明确要求定义两件事：

  • 错误帧出现时的系统行为。
  • 优先级反转的规避方式。

优先级反转在 CAN 上是个真实威胁：低优先级报文长期占线，高优先级报文被堵在门外。Time Triggered Bus Scheduling 靠限流削弱它，但彻底解决要靠设计。

增长与共存 #

系统寿命期内流量会涨，Time Triggered Bus Scheduling 留了空间。如果设计阶段预留了增长余量，可以往网络里加节点，而且不影响已有节点——已有节点的发送配额不动，新节点在自己的配额内发。

还有一条更有意思：因为行为可预测，不同关键性等级的系统可以共存于同一张网络。飞控那种最高等级的功能，和座舱显示那种低一档的功能，跑在同一个 CAN 上，各自的可预测性都能证明。这个能力对减重减线束的价值很大。

七、冗余与故障容错 #

航空对冗余的定义跟消费电子不同。消费电子追求「不出错」，航空追求「出错了还能飞」。这两件事的技术路径完全不一样。

CANaerospace 的冗余不是靠协议层重新造一套可靠性机制。CAN 硬件已经把 CRC、应答、错误帧、自动重发做完了，上层再抄一遍只是浪费。它做的是另一件事：让接收方能自己判断这份数据值不值得信。

规范里有一句话点明了这个设计意图——报文头里的信息足够判定参数的完整性，用于飞行安全关键系统，并支撑系统冗余。

拆开看，报文头给冗余留了三个入口：

入口 字段 冗余场景里怎么用
数据质量 Service Code 连续自检结果、导航信号合法性标志，告诉你这份数据本身好不好
新鲜度 Message Code 连续计数，告诉你这份数据是不是最新的、中间丢了几帧
来源 Node-ID 告诉你这份数据出自哪个节点，用于分辨主备与交叉比对

三个字段拼起来，接收端就能做一件很关键的事：同一条参数收到两份时，挑一份用。哪份 Service Code 说自检通过、哪份 Message Code 更新，就用哪份。

双总线怎么落地 #

规范给了字段，没规定拓扑。工程上常见的做法是两条独立 CAN 各跑一份相同流量，接收端逐帧比对。

text
         ┌──────────────┐      ┌──────────────┐
         │  节点 A      │      │  节点 B      │
         │  (双 CAN)    │      │  (双 CAN)    │
         └──┬────────┬──┘      └──┬────────┬──┘
            │        │            │        │
      ┌─────┴──┐  ┌──┴─────┐  ┌───┴──┐  ┌──┴─────┐
      │ CAN 主 │  │ CAN 备 │  │CAN 主│  │ CAN 备 │
      └─────┬──┘  └──┬─────┘  └───┬──┘  └──┬─────┘
            └────────┴────────────┴────────┘
                  两张物理独立的总线

接收端策略：
  1. 两路都收到 → 比 Service Code，取质量好的
  2. 质量相同   → 比 Message Code，取新的
  3. 一路断了   → 直接用另一路，不需要切换动作
  4. 两路都断   → 进入规范之外定义的失效状态

这套做法能成立，前提就是报文自识别。如果语义藏在标识符里、质量信息要靠额外请求去查，那每帧都要多一轮交互，冗余的成本立刻翻倍。

没有总线控制器本身就是容错 #

民主网络的深层含义在这里显出来。

传统航空总线大量采用命令/响应模型，一条总线有一个总线控制器，所有传输由它发起。好处是调度清晰，坏处是这个控制器一旦失效，整条总线停摆。为了补这个洞，往往得再配一个备份控制器，成本与复杂度一起上去。

CANaerospace 把这个角色取消了。每个节点对总线的访问权完全相同，谁都可以在任何时刻发起传输，谁都不需要许可。仲裁由 CAN 控制器硬件按标识符优先级解决，不需要软件排队。

这样一来，「总线控制器失效」这个故障模式根本不存在。失效的只会是某个节点，而节点失效的影响被限制在它自己负责的参数上。加上 Node-ID 与 Service Code，接收端立刻知道哪些参数没人喂了。

紧急事件与系统重构 #

EED 通道专管需要立即动作的消息：系统降级、系统重构。它只走 ATM 通信，占最高优先级。

优先级高到这里意味着什么？意味着只要 EED 有报文在等，总线仲裁一定让它先过。这是硬件保证的，不依赖任何软件调度。

配合 Node Service 的 PTP 能力，故障处理能做成一串联动动作：某节点上报异常 → EED 广播降级 → 系统通过 NSH/NSL 把功能迁到备份节点 → 各节点更新自己负责的参数表。规范把「控制动态系统重构」明确列为 Node Service 的用途之一。

50% 带宽余量也是容错设计 #

前面提过建议把带宽使用率压到 50% 以下，理由是 CAN 错误帧会吃掉带宽。

从冗余角度看，这 50% 就是故障余量。正常时它闲着，故障时错误帧涌上来，它还够用。如果平时跑到 95%，一个节点开始疯狂发错误帧，整条总线立刻失去可预测性。

这也是为什么规范说 Time Triggered Bus Scheduling 不优化带宽利用率。它优化的是「出故障时还在边界内」。

规范没管的部分 #

有几件事 CANaerospace 明确交给系统设计者，别以为协议会兜底：

事项 谁负责
错误帧出现时的系统行为 系统设计者定义
优先级反转的规避 系统设计者定义
冗余拓扑与切换策略 系统设计者定义
报文丢失后的降级动作 系统设计者定义
节点失效后的功能迁移 靠 Node Service 实现，策略自定

这条界线划得很清楚：协议给工具，工程给方案。航空认证审的是整个系统，不是协议本身。所以规范不越界替你承诺任何可靠性等级。

八、与 CANOpen 的对比 #

两个都是 CAN 高层协议，都是 1990 年代末成型，都把 CAN 从「能发帧」推到「能组网」。设计取向完全不同。

先把最容易混的一点摆清楚：两者都用标识符表达语义，但表达方式相反。

  • CANOpen：标识符里放功能码 + 节点号，告诉你「这是一条 PDO，来自 3 号节点」。语义由功能码定义，具体是哪个参数，要去查对象字典。
  • CANaerospace：标识符里放信道 + 参数位置，报文头里放节点 + 类型 + 质量 + 序号。语义在载荷里，收到就能读。

一句话：CANOpen 把设备建模成对象字典，CANaerospace 把参数钉死在分配表里。

三处关键差异 #

第一处是节点号怎么放。

CANOpen 把节点号编进标识符，7 位节点号加功能码拼成 11 位 COB-ID。好处是硬件过滤效率高：CAN 控制器按 ID 掩码筛帧，节点只收自己的。坏处是 11 位空间很快见底，一台设备的功能一多就得压缩功能码。

CANaerospace 用 29 位，一个字节给节点号，剩下全用来划分信道和参数位置。硬件过滤同样能设，但设计者更在意的是另一件事：抓一个包能立刻读懂。这在调试和适航审查时值钱。

第二处是配置在哪一刻发生。

CANOpen 的哲学是「先描述，再通信」。设备上电，主站读 EDS，按对象字典下发配置，配置完了才开始跑过程数据。灵活，可裁剪，同一套固件能装进不同项目。

CANaerospace 的哲学是「参数表就是约定」。系统设计阶段定好分配表，所有节点照着表发、照着表收，上电直接跑。省掉了配置环节，也就省掉了一整类配置出错的风险。代价是改一个参数要改全网的表，而且必须版本对齐——这就是为什么 Node Identification Service 是强制的，它要能查出对端用的是哪一版表。

第三处是时间怎么保证。

CANOpen 的确定性来自周期性 SYNC 加 PDO 的传输类型设定，本质是「让周期报文按周期发」。它对最坏情况延迟不给上界，工业场景里够用。

CANaerospace 直接给上界：一个 minor time frame 的一半加上最长报文时长。这个数字能写进认证材料。为了拿到它，付出的是 50% 带宽。

谁该用哪个 #

选型不用纠结，看需求落在哪一侧：

  • 要通用、要可配置、要现成的协议栈与工具、设备种类多且经常改 → CANOpen。
  • 要可预测的延迟上界、要每帧自带质量信息、要过适航审查、参数集合在项目初期就冻结 → CANaerospace。

反过来选都难受。拿 CANOpen 做适航关键路径，你得自己补质量字段和延迟分析；拿 CANaerospace 做通用工业控制，你会发现每加一个参数都要走一遍全网表更新，还找不到现成的配置工具。

九、与其他航空总线的对比 #

航空总线不止 CAN 这一支。CANaerospace 在里面属于「低成本、中等速率、多节点」那一格。

先把主要对手摆上桌：

总线 物理基座 速率（公开量级） 拓扑与仲裁 典型定位
MIL-STD-1553B 双绞屏蔽，命令/响应 1 Mbit/s 总线控制器集中调度 军机、直升机存量主力
ARINC 429 单向下行差分 12.5 或 100 kbit/s 一发多收，无仲裁 大型客机海量存量
ARINC 664（AFDX） 交换式以太网 100 Mbit/s 星型交换，虚拟链路 新一代客机主干
ARINC 825 CAN 经典 CAN 量级 多主，按 ID 仲裁 航空标准化组织背书的 CAN 方案
CANaerospace CAN 经典 CAN 量级 多主，民主对等 通航、无人机、科研与仿真

逐条看差异 #

对 MIL-STD-1553B：1553 是命令/响应模型，总线控制器统一发令，终端应答。它的确定性来自集中调度，天生好证明。CANaerospace 把它反过来做——取消控制器，用标识符优先级加节点限流换确定性。1553 的线材与变压器耦合成本高，节点数上限也低；CANaerospace 用普通 CAN 收发器，节点数和布线自由度都更好。两条路的取舍是「集中可控」对「去中心化加低成本」。

对 ARINC 429：429 最简单，一个发送端、若干接收端、单向、32 位字。简单到几乎不会错，所以客机上用得极多。它的短板同样明显：一条线只能一个方向，双向通信要两对线；节点多了线束爆炸；速率只有 12.5 或 100 kbit/s。CANaerospace 用两根线跑双向多主，线束省下大量重量。但 429 的存量太大，替换等于重做认证，所以它还在新飞机上出现。

对 ARINC 664（AFDX）：AFDX 是交换式以太网，100 Mbit/s，靠虚拟链路和流量整形保证确定性。带宽比 CAN 高两个数量级，代价是交换机、线缆、端系统的成本与重量都上去了。它适合客机主干，不适合一个几十个节点、每帧只传一个浮点参数的小系统。CANaerospace 在这类小系统里性价比高得多。

对 ARINC 825：这一条最值得说。ARINC 825 同样跑在 CAN 上，同样面向航空，由航空标准化组织发布。它和 CANaerospace 抢的是同一块地。

差异在出发点上：ARINC 825 更贴近 CANopen 的思路，用功能码与参数组组织报文；CANaerospace 坚持自识别报文头与时间触发限流。ARINC 825 的优势是标准化组织的背书与供应链认可度。这也是 CANaerospace 在稍大的项目里被分流的原因之一——同样解决问题，采购与适航部门更认有航空标准编号的那一份。

CANaerospace 的位置 #

把上面几条画成一条轴，按「单位成本」与「确定性证明难度」摆：

text
成本低 ←──────────────────────────────────────→ 成本高
CANaerospace   ARINC 825   MIL-1553B   ARINC 429   ARINC 664

确定性来源：
CANaerospace  限流 + 仲裁 + 延迟上界
ARINC 825     功能码分组 + 周期调度
MIL-1553B     集中命令/响应
ARINC 429     单向下行，无竞争
ARINC 664     交换 + 虚拟链路整形

这张图不是精度表，只是定位。CANaerospace 站在最左边：用最便宜的物理层，拿到可证明的延迟上界，代价是速率和功能丰富度。

十、典型应用场景 #

规范原文列出的场景不多，但每一个都挺硬。

科研机：SOFIA #

SOFIA 是平流层红外天文台，一架改装过的波音 747SP，机背开个门，装一台 2.5 米口径望远镜。它飞在平流层，避开水汽，做红外观测。

机上用好几套 CANaerospace 网络做实时计算机互联。这个场景的特殊之处在于：望远镜的指向控制、陀螺稳定、科学仪器数据采集是几套独立的实时系统，它们之间要交换状态与指令，但不能互相拖累。多套网络物理分开，各跑各的 CANaerospace，是这个量级的科研设备能接受的方案。

飞行模拟器：整舱对接 #

这一条最能体现 CANaerospace 的实用性。Eurofighter Typhoon 的模拟器用它把整个座舱设备连到仿真主机。

模拟器要的是什么？大量离散量输入输出、大量开关与指示灯、几十毫秒级的刷新、不能有抖动。座舱里几百个信号，如果每个都拉一根线到主机，线束能堆满一间屋。挂到 CAN 上，按 CANaerospace 的参数表排好，主机一侧只留一个接口。

模拟器还有个好处：它不需要适航认证。所以这里用 CANaerospace 纯粹是因为它好用——参数化、每帧自识别、延迟有上界，出问题好查。这是它在非航空认证场景里活得挺好的证据。

无人机 #

意大利把 CANaerospace 当作 UAV 的数据总线技术。无人机这个场景对重量极端敏感，对成本也敏感，对认证的要求比有人机低一档。

UAV 的典型负载是：飞控计算机、惯导、大气数据、舵机、发动机控制、任务载荷。这些设备分散在机身各处，线束越短越轻越好。CAN 两根线串起来，CANaerospace 定好参数表，正是它的主场。

通用航空 #

多套通航航电系统把它当通信网络。这条要和 AGATE 一起看：NASA 的 AGATE 计划目标就是把通航座舱数字化，让小飞机也装上玻璃座舱。计划需要一个便宜、开放、能多厂商互通的总线，CANaerospace 被选中并发布为标准。

通航客户对价格极度敏感，一套航电几十万人民币就到顶了。CAN 收发器几块钱一颗，这个成本结构决定了它只能用 CAN 这一档的物理层。

地面车辆与试验台 #

规范没把这两个列进场景，但它们在实际工程里常见，也不算超出协议能力：

场景 为什么用得上
地面测试车辆 与机上设备同构，便于把机载软件搬到地面验证
硬件在环试验台 需要确定性的激励与采集，参数表本身就是接口定义
系统联试台 多厂商 LRU 混装，靠 Node Identification Service 查表对齐

这里要划一条线：这些属于「公开的 CANaerospace 用法」，不是规范承诺的场景。写技术方案时不要把它们当成规范条款引用。

共同点 #

把这几个场景叠起来看，共同需求很清楚：

  • 节点数量中等，几十个量级，不需要以太网的带宽。
  • 每个参数独立、小、频率固定，一帧一个物理量正好。
  • 需要可预测的延迟，需要能证明的最坏情况。
  • 多厂商设备要拼在一起，接口必须写死。
  • 成本与重量敏感。

五条全中的场景，CANaerospace 就很难被替代。

十一、为什么它没能普及 #

先把结论放前面：CANaerospace 是一个做得很干净的专用方案，它没普及的原因不在技术，在产业。

第一条：配套几乎为零 #

你去买 CANOpen，能买到主站协议栈、从站协议栈、配置工具、一致性测试套件，甚至有现成的 SoC 带 CANOpen 固件。

CANaerospace 没有这些。规范是一份 PDF，代码要自己写。写得出来，但每一行都要自己验证。对一个几十人的航电团队，这意味着几个月的前期投入。

这条是致命的。协议设计的「实现成本低」是指代码量小，不是指「有现成的给你用」。这两件事差得很远。

第二条：认证门槛不因协议免费而降低 #

这是最容易被误解的一点。规范免费下载，使用零授权费。但适航认证的成本跟协议授权费完全不在一个量级。

机载软件的认证走 DO-178C 那一套，工作量按代码规模与关键性等级折算。协议栈代码量小确实是优势——验证面积小。可流程一步都不能少：需求追溯、结构覆盖分析、最坏执行时间分析、工具鉴定，全套走完，成本远超协议本身。

再加上硬件侧的考量、系统安全评估、供应商审查，这些成本与「协议是否免费」毫不相干。

一句话：免费的是纸，贵的是证明。

第三条：大飞机市场被 ARINC 占死了 #

客机市场的盘面很清楚：

  • ARINC 429 存量巨大，简单可靠，几十年验证过的方案。换掉它意味着重做接口、重做认证、重做供应链，收益只是省点线束重量。这笔账很难算平。
  • ARINC 664 占了新一代客机的主干。带宽需求一旦上去，CAN 这一档直接出局。
  • ARINC 825 占了「航空 + CAN」这个细分位置，而且它背后有航空标准化组织的编号与流程。

CANaerospace 在这三条线之间没有留下明显缺口。它能干的活，要么被 429 用成本优势守着，要么被 825 用标准背书拿走。

第四条：CAN 的带宽上限 #

这一条是物理限制，跟协议设计无关。

算一笔粗账，只看数量级：

text
经典 CAN，1 Mbit/s，标准帧 8 字节载荷
  单帧位时间   ≈ 108 位（含帧头帧尾与间隔）
  理论帧率     ≈ 1 000 000 / 108 ≈ 9 200 帧/s
  规范建议限流 → 实际按 50% 算 ≈ 4 600 帧/s
  CANaerospace 每帧可用载荷 4 字节
  实际数据速率 ≈ 4 600 × 4 ≈ 18 KB/s

同样的总线跑 CANOpen（8 字节基本全给数据）
  实际数据速率 ≈ 4 600 × 8 ≈ 37 KB/s

18 KB/s 对「一帧一个浮点参数」的机载系统够用，对任何带图像、带波形、带大块状态的负载都不够。带宽上不去，场景就只能停在低数据率这一类。

注意这只是位宽层面的粗算，实际值受帧间间隔、填充位、错误帧影响，会再低一点。但数量级不会变。

第五条：一个厂商维护一份规范 #

CANaerospace 由 Stock Flight Systems 开发并持续维护，主页在 canaerospace.net，规范放在厂商域名下的 PDF 里。这跟 CiA 那种几百家会员共同推进的模式不一样。

一家公司维护一份规范，好处是方向统一、迭代快、不扯皮。坏处也很实际：文档、示例、勘误的知识产权集中在一处，第三方想贡献没有通道，想提问没有社区。工程师选型时会想一个问题——五年后这份规范还在更新吗？这个问题没有确定答案，选型就倾向于保守。

第六条：名字带来的误解 #

这条听起来琐碎，但真实存在。名字里带 CAN，很多人第一反应是「车载那套东西，速率不够，不适合航空」。

实际上 CANaerospace 解决的不是速率问题，是可预测性与互操作问题。但选型会上，名字的影响比技术细节大。

它的实际位置 #

把上面六条合起来，结论很清楚：

判断 内容
技术上 干净、自洽、延迟有上界、报文可自解释
适用面 节点几十个、单参数小报文、要求可预测性、成本重量敏感
不适用面 高带宽、需要丰富设备模型、需要现成工具链、大机型主干
现状 科研、仿真、无人机、通航里活得不错，没有成为通用标准
定性 小而美的专用方案

这个定位不是失败。一个协议能被 NASA 收进标准文档，能装到 SOFIA 上，能撑起整舱模拟器，已经超出绝大多数协议的一生。它只是在「通用标准」这条赛道上没有参赛。

十二、易错点速查 #

这些是读规范、写协议栈、排查现场问题时最容易翻车的地方。

现象 根因 怎么查
浮点参数解出来是个莫名其妙的数 字节序反了，CANaerospace 定死大端 抓一帧，按大端手工解一遍对比
丢帧识别不出来 Message Code 没做逐标识符独立计数，用了全局计数 检查计数器作用域是不是绑在标识符上
Message Code 到 256 就溢出 忘了回绕，规范是 255 之后回 0 检查自增代码的取模处理
节点地址冲突，两台设备互发乱码 Node-ID 分配重复，分配表没对齐 用 Node Identification Service 扫全网
广播消息没人收 PTP 下广播要填 Node-ID 为 0 检查报文头第一个字节
状态字段被当成数据解析 Service Code 在 NOD 与 NSH/NSL 下语义不同 按信道区分解析分支
紧急消息发不出去 走了 NOD 信道，没走 EED 检查标识符是否落在 EED 段
带宽跑满后延迟不可预测 没有按 minor time frame 限流 统计每个节点单帧内的报文条数

自己定义的 ID 和标准表撞了 标准表占了 300～1799，自定义段要用表外编号 对照标准分配表核范围
3 字节参数发不出去 参数区只有 4 字节，装不下就得拆帧 核对参数长度与数据类型编码

还有三条概念性的坑，比上面这些更容易踩：

第一，把「可预测」当成「实时」。 规范原文特意纠正过这个误读。可预测说的是最坏情况有界，不是每次都精确同一时刻发生。你要是拿 CANaerospace 去保证微秒级同步，方向就错了——它不要求节点间时钟同步，只要求节拍时长一致。

第二，把协议当认证。 用了 CANaerospace 不等于系统可认证。错误帧下的行为、优先级反转的规避、节点失效后的降级策略，规范全部推给系统设计者。这些不写清楚，认证材料过不去。

第三，漏算非周期报文。 带宽管理的账里必须包含所有非周期消息。少算一条，延迟上界那条不等式就作废了，而它作废了整份分析都得重做。

最后给一条实践建议：真要上手，先做两件事——把手上那份规范的标识符分配表和数据类型表打印出来贴在工位，再写一个能按报文头四字节解析的抓包小工具。有了这两样，CANaerospace 剩下的部分都不难。
