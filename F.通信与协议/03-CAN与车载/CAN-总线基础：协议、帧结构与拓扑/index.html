这篇讲 CAN 总线本身：它是什么、帧长什么样、负载率怎么算、终端电阻和拓扑怎么接。

不讲 CANOpen 的对象字典和 PDO/SDO 映射，也不讲 Rockchip 平台的驱动适配细节。那两块在 F.通信与协议/03-CAN与车载 的另外两篇里，遇到交接的地方会指一下。

代码以 Linux SocketCAN 为准。平台相关的部分会单独标出来。

一、CAN 是什么 #

CAN（Controller Area Network）是一条总线，不是一个完整的通信协议栈。Bosch 在 1986 年提出，1993 年进 ISO 11898 系列。它要解决的问题很具体：车里几十个电控单元，怎么用最少的线互相说话。线束越少，重量越轻，接插件故障点越少。

物理层面它只有两条线，CAN_H 和 CAN_L。这是一对差分信号，总线电平由两者的压差决定，不看某一根对地的绝对电压。抗共模干扰的能力就来自这里：电机、点火线圈在车里制造的干扰对两根线几乎一样，接收端相减，干扰自己抵消掉了。

差分只有两种状态，名字叫显性和隐性：

总线状态 逻辑值 CAN_H CAN_L 压差
显性 dominant 0 约 3.5V 约 1.5V 约 2V
隐性 recessive 1 约 2.5V 约 2.5V 约 0V

显性压过隐性。两个节点一个发 0 一个发 1，总线上呈现的是 0。这个「线与」关系是整个 CAN 仲裁机制的地基，后面第七节会反复用到。

CAN 有三个性质，缺一个都不成立：

  • 多主。总线空闲时，任何节点都可以立刻开始发。没有主节点，没有轮询，没有令牌传递。
  • 广播。发出去的帧，总线上所有节点都收得到。帧里没有目的地址这个字段。
  • 基于优先级仲裁。两个节点同时开口，靠 ID 逐位比较定胜负，输的那个自动退让。

想清楚这三点，再看 CAN 的编址方式就不别扭了：帧头那 11 位或 29 位 ID，表达的是「这包数据是什么」，不是「发给谁」。这种做法叫面向内容的编址方案。接收方拿 ID 比对过滤规则，决定收还是不收。

由此得到一个反直觉的结论：CAN 不需要主节点，也不需要冲突检测后的重传协商。

以太网是 CSMA/CD，撞了就各自退避一个随机时间重发，退避完照样会再撞。CAN 的仲裁是逐位进行的，输的那个节点在丢掉某一位的瞬间就知道自己输了，当场停发转接收。此时赢家的波形一个边沿都没被破坏，这一帧照常传完。这叫非破坏性位仲裁。

代价是输的那一方必须自己重发。但重发时刻不用协商，也不用随机退避：总线一空闲，它重新参与一次仲裁就行。谁的 ID 小谁先走，规则是确定的。

一个节点发数据的完整流程：

  1. 应用把数据和自己的标识符交给本节点的 CAN 控制器。
  2. 控制器等总线空闲，把报文按帧格式组织好往总线上发。
  3. 每发一位，控制器同时读回总线电平。读回值和发出的值不一致，说明有更高优先级的节点在同时发，自己立刻停发、转接收。
  4. 一帧发完，其他节点各自按 ID 判断这帧跟自己有没有关系。
  5. 收下的节点在 ACK 槽里回一个显性位，告诉发送方「有人听懂了」。

层次结构 #

CAN 被切成三层。对象层和传输层合并起来，覆盖了 ISO/OSI 模型里数据链路层的全部服务和功能。

层 干什么 谁实现
对象层 查找被发送的报文、决定收哪个报文、给应用层提供接口 驱动 + 应用 API
传输层 帧结构、仲裁、错误检测、出错标定、故障界定、位定时 CAN 控制器硬件
物理层 节点之间按电气属性做位信息的实际传输 收发器 + 线束

我们平时写代码是在对象层。这一层直接跟应用打交道，提供收发 CAN 消息的接口。所谓「打包」，就是在原始数据外面套上帧起始、仲裁段、控制段、CRC、ACK、帧结束，按固定格式排好，一条通道就能表达各种信号。接收方按同一套约定拆包，原始数据就还原了。

传输层的活由 CAN 控制器硬件加驱动干。写应用的人不直接碰传输层，都是通过对象层的 API 间接用它的能力。位级传输、错误处理、仲裁这些低级细节，硬件已经包掉了。

物理层就是收发器芯片加电气接口。同一个网络里，所有节点的物理层必须一致，混用高速收发器和容错收发器会出问题。

CAN 报文的属性 #

下面这张表是 CAN 协议对报文行为的完整定义，调试时对不上现象就回来查：

属性 说明
报文（Messages） 把数据、操作命令、同步信号打包，打包结果叫报文，就是有固定格式的数据包
信息路由（Information Routing） 报文找节点的方式，靠 ID 而不是地址
位速率（Bit rate） 数据位的传输速度
优先权（Priorities） 报文发送的优先权，由 ID 决定
远程数据请求（Remote Data Request） 发远程帧，请另一个节点把对应数据帧发出来
多主机（Multimaster） 总线空闲时，任何节点都可以开始传送报文
仲裁（Arbitration） 两个及以上节点同时开传时的总线访问冲突裁决
安全性（Safety） 每个节点都有错误检测、错误标定、错误自检的措施
错误检测（Error Detection） 监视、循环冗余检查、位填充、报文格式检查
错误标定与恢复时间 检测到错误的节点标出坏报文，该报文失效并自动重传。不再出新错时，从检错到下一帧开始最多 29 个位时间
故障界定（Fault Confinement） 能区分永久故障和短暂扰动，永久故障的节点会被关掉
连接（Connections） 一条总线可挂很多节点。理论上无上限，实际受延迟和电气负载限制
单通道（Single Channel） 总线是单一的双向位信号传送通道
总线值（Bus value） 两种互补逻辑值：显性（逻辑 0）、隐性（逻辑 1）
应答（Acknowledgment） 所有接收器检查报文连贯性，连贯就应答，不连贯就标错
睡眠/唤醒（Sleep / Wake-up） 可置睡眠模式停止内部活动并断开总线驱动，靠总线活动或内部状态唤醒

二、CAN 2.0A 与 2.0B #

CAN 2.0 有两个版本，区别只在标识符长度。

  • CAN 2.0A：标准格式，11 位 ID。
  • CAN 2.0B：扩展格式，29 位 ID，由 11 位基本 ID 加 18 位扩展 ID 拼成。

两个格式共存于同一条总线，靠帧里的 IDE 位区分。IDE 为 0 是标准帧，为 1 是扩展帧。

对比项 标准帧（2.0A） 扩展帧（2.0B）
标识符长度 11 位 29 位（11 位基本 + 18 位扩展）
ID 空间 2048 个 约 5.37 亿个
IDE 位 0 1
RTR 位位置 仲裁段内 仲裁段内，基本 ID 之后
SRR 位 无 有，固定为 1
仲裁段总长 12 位 32 位
典型用途 车身、传感器、私有协议 J1939、诊断、需要大 ID 空间的场景

2.0B 的实现还分两种，买控制器时会碰到：

  • 2.0B passive：能正确接收扩展帧并应答，但自己不发扩展帧。收到扩展帧不报错。
  • 2.0B active：收发都支持扩展帧。

现在市面上的控制器基本都是 active，passive 只在很老的芯片上见得到。

扩展帧的仲裁段里有个 SRR 位（Substitute Remote Request，替代远程请求位），它顶替了标准帧里 RTR 位的位置，固定发 1（隐性）。数据帧的 RTR 是 0（显性）。所以一个标准帧和一个 ID 完全相同的扩展帧同时竞争，标准帧赢。

这两个格式都禁止 ID 的高 7 位全为隐性，也就是不允许出现 1111111XXXX 这样的 ID。原因是这 7 个隐性位加后续位会凑出足够长的连续隐性电平，跟帧间隔（Intermission）撞车，接收端无法区分帧结束和帧开始。写协议分配 ID 时要主动避开这段区间。

11 位 ID 的 2048 个编号看着不少，扣掉禁用区间、留给诊断和网络管理的，实际能自由分配的不到一半。节点一多就会挤，所以车身以外的领域基本都转 29 位了。

三、CAN FD：更快也更长 #

CAN FD 的 FD 是 Flexible Data-rate。它解决经典 CAN 的两个硬伤：数据段最多 8 字节太短，整帧只能跑一个速率太慢。

FD 有两个速率，各有一套位时间定义寄存器，配置时都要配：

  • 仲裁比特率（arbitration bitrate）：最高 1Mbps，跟经典 CAN 一样。帧头帧尾走这个速率。
  • 数据比特率（data bitrate）：最高 8Mbps（早期文档写 5Mbps）。只有数据段走这个速率。

变速的位置由 BRS 位控制。BRS 及其之后到 CRC 界定符之前这一段切到高速率，仲裁段和 ACK 段回到低速。为什么只提速数据段？因为仲裁要在全网节点间逐位比较，速率必须全网统一且受线束长度限制；数据段只需要收发双方同步，不涉及仲裁，可以放开跑。

配置 FD 最常见的错误，是照抄经典 CAN 的命令：

bash
# 错：只给了 bitrate，没给 dbitrate，没开 fd
ip link set can0 type can bitrate 500000

# 对：仲裁段 500k，数据段 2M，显式打开 FD
ip link set can0 up type can bitrate 500000 dbitrate 2000000 fd on

第一条命令操作 FD 一定有问题。现象是能 up 起来但收发出错，或者干脆报错。CAN FD 的数据比特率必须大于等于仲裁比特率，两个寄存器都得写。

FD 与经典 CAN 的差别汇总：

对比项 经典 CAN CAN FD
仲裁段速率 最高 1Mbps 最高 1Mbps（相同）
数据段速率 与仲裁段相同 最高 8Mbps，可变速
一帧数据长度 0~8 字节 0~64 字节
DLC 编码 0~8 线性 0~15，9 以上跳档
CRC 长度 15 位 17 位 / 21 位，按长度选
远程帧 有 RTR 不存在，RTR 位置换成 RRS
错误状态广播 只有本节点知道 ESI 位可告知全网
帧格式标志 无 FDF 位区分
收发兼容性 — 收发双方都必须支持 FD

最后一行是踩坑重灾区。FD 帧在经典 CAN 控制器眼里就是一帧格式错误的数据，它会直接发错误帧。所以总线上只要挂了一个不支持 FD 的节点，整条总线就不能开 FD。升级 FD 从来不是改一端的配置，是全网的替换工程。

FD 新增的位 #

  • RRS（Remote Request Substitution）：替代经典 CAN 的 RTR 位。FD 没有远程帧，这个位置固定发 0。
  • IDE：跟经典 CAN 一样，1 是扩展帧，0 是标准帧。
  • FDF（FD Format）：0 表示传统 CAN 报文，1 表示 FD 报文。接收端靠这一位决定后面按哪套规则解析。
  • BRS（Bit Rate Switch）：0 表示全程恒定速率，1 表示数据段切到高速率。
  • ESI（Error State Indicator）：0 表示发送节点处于主动错误状态，1 表示处于被动错误状态。

ESI 值得单独说。经典 CAN 里一个节点是主动错误还是被动错误，只有它自己知道，别人看不见。FD 用 ESI 把这个状态广播出来。总线上某个节点开始频繁报 ESI=1，说明它在累积错误计数，是线束或收发器出问题的前兆信号，比等它 bus-off 早得多。

FD 的 CRC #

数据场从 8 字节扩到 64 字节，15 位 CRC 的检错能力不够了。FD 做了两件事：

  • CRC 计算范围扩大。不只算数据位，还把从 SOF 起的 Stuff Count 和填充位一起算进去。
  • CRC 长度按数据长度选，不再固定 15 位：
数据长度 CRC 位数
16 字节以下 17 位
16 字节以上 21 位
（经典 CAN 对照） 15 位

有一份流传较广的说法是「15 字节用 15 位、16 字节及以下用 17 位、超过 16 字节用 21 位」。实际以控制器手册为准，主流实现是上面这张表。写协议文档时把具体芯片型号带上，别只抄位数。

Stuff Count 是 FD 加的固定填充计数：在 CRC 之前把填充位的数量用 3 位格雷码加 1 位奇偶校验发一遍，接收端拿它跟实际数到的填充位对比，能抓出填充位错位这类问题。

DLC 与数据长度的映射 #

FD 的 DLC 还是 4 位，范围 0~15。但 9 以上不再线性对应字节数，而是跳档：

DLC 数据字节数
0~8 0~8
9 12
10 16
11 20
12 24
13 32
14 48
15 64

这个跳档设计是为了用 4 位表达 64 字节，同时保持低段的线性。

在 Linux SocketCAN 里，应用只操作 canfd_frame 的 len 字段，不用管 DLC。len 在 0~8 时 DLC 就等于 len；大于 8 时，内核选能装下它的最小 DLC：

text
len = 9  ~ 12  -> DLC = 9  (12 字节)
len = 13 ~ 16  -> DLC = 10 (16 字节)
len = 17 ~ 20  -> DLC = 11 (20 字节)
len = 21 ~ 24  -> DLC = 12 (24 字节)
len = 25 ~ 32  -> DLC = 13 (32 字节)
len = 33 ~ 48  -> DLC = 14 (48 字节)
len = 49 ~ 64  -> DLC = 15 (64 字节)

举个例子：要发 33 字节，len 填 33，内核选 DLC=14（对应 48 字节）。帧里实际只带 33 字节真实数据，DLC 标 14 表示这一帧的容量上限是 48 字节。带宽账要按 DLC 算，不是按 len 算：发 33 字节，总线上占的是 48 字节的数据段时间，一帧 33 字节和 48 字节的总线开销完全一样。

四、总线的物理层与拓扑 #

物理层要解决的问题很窄：怎么把一串 0 和 1 变成两根线上能传、能被正确采样的电压。CAN 用差分加终端匹配，两个手段。

收发器与控制器 #

节点上的芯片分两颗，职责完全不同，新手很容易混：

  • CAN 控制器（CAN Controller）：实现 CAN 协议的逻辑部分。组帧、算 CRC、做位填充、跑仲裁、维护错误计数器，全在它里面。比如 STM32 内置的 CAN 模块、MCP2515（SPI 接口）、SJA1000（并口 I/O）。
  • CAN 收发器（CAN Transceiver）：把控制器的 TTL/CMOS 逻辑电平转成总线上的差分电平，反过来也转。比如 MCP2551、TJA1050、TJA1042、SN65HVD230。

选型的实际考虑：一般 PC 和 ARM 都没有内置 CAN 控制器。独立控制器里 MCP2515 是 SPI 接口，5~6 个管脚就能控制，占资源少；SJA1000 是 I/O 接口，占的管脚多，但时序上更直接。所以小系统多用 MCP2515，带地址总线的老平台多用 SJA1000。有些 MCU 把控制器和收发器都集成了，但集成收发器的很少，因为收发器要接 12V 域的东西，工艺上不划算。

线性拓扑 #

线性拓扑是多点连接的结构。信号线是 CAN_H 和 CAN_L，两端各端接一个 120Ω 终端电阻，这条线叫主干线，也叫总线。所有设备挂在这条共同的传输介质上。

任意节点发，其他节点都收得到。从主干线分出去接设备的短线叫分支线（stub）。Stub length 就是从主干线到终端节点那段短分支线的长度。

text
 120Ω                                                    120Ω
   │                                                        │
   ├───────┬───────────┬───────────┬───────────┬───────────┤
  CAN_H    │           │           │           │           │
           │           │           │           │           │
  CAN_L    │           │           │           │           │
   ├───────┴───────────┴───────────┴───────────┴───────────┤
   │                                                        │
 节点A      节点B        节点C        节点D        节点E
   └── stub ─┘  ← 分支线要尽量短

Stub length 越短越好。长了会引起信号反射，反射在总线上叠加出振铃，增加噪声和误码率。ISO 11898 的建议是 stub 保持在 0.3 米（30 厘米）以下。

不同速率对分支线的要求不一样：

速率 建议 stub 长度
1Mbps 小于 30 厘米
500kbps 小于 1 米
125kbps 及以下 不超过 3 米

这张表是经验值，不是标准的硬性条款。但现场调试时它非常好用：通信一上高速就丢帧，先量分支线。

星型、树型与环形 #

星型是多个节点通过各自的分支线连到一个中心节点或集线器上，由中央节点向目的节点转发，执行集中式的通信控制。星型在纯 CAN 里不常见，因为 CAN 的仲裁要求所有节点同时看到总线电平。用集线器转发就引入了延迟，延迟超过一个位时间仲裁就崩了。真要做星型，得用专门的 CAN 集线器（带同步逻辑的），成本不低。实际工程里出现的「星型」多半是一条主干线穿过几个接插件，接插件处再分线，看起来像星型，本质还是线性加长 stub。

树型是在线性主干上再接二级主干。每一级主干都要考虑终端匹配，接得不好就会出现阻抗不连续点。它适合车内这种空间分散的布线：主线沿车身走一圈，各区域再分出去。分支点要尽量少，每个分支点都是一个反射源。

环形把 CAN 总线首尾相接成环，好处是线缆任意位置断开，通信还能绕另一边走。环形的终端匹配不能用两个 120Ω 收尾，要用分布式匹配，保证总体阻抗还是 60Ω：在环路上均匀布若干电阻，让任意一点看进去的等效阻抗都接近 60Ω。环形在 CAN 上少见，因为断线后总线长度变成两倍，传播延迟翻倍，速率就得降。它是可靠性优先场景的选择，比如某些轨道交通和工业现场。

拓扑选择的实际准则 #

现场布线时按这几条走，能躲掉八成问题：

  1. 优先线性。一条主干线，节点挂在上面，两端各一个 120Ω。
  2. 分支线总长控制在主干线长度的 1/10 以内，单根不超 30 厘米（1Mbps 时）。
  3. 节点不要挂在主干线末端之外，末端就是终端电阻的位置。
  4. 速率与长度成反比。500kbps 大约能跑 100 米，125kbps 能到 500 米左右，1Mbps 只有 40 米上下。
  5. 线缆用双绞，CAN_H 和 CAN_L 绞在一起，别用两根平行线。

第 4 条背后是仲裁的物理约束：发送节点必须在采样点之前收到所有节点的电平，传播延迟加上收发器延迟不能超过一个位时间里的传播段。速率提上去，位时间变短，能容纳的距离就变短。这是硬物理，不是设计余量。

CAN 网桥与网关 #

一条总线挂不下、或者要跨协议时，靠网桥和网关扩展。两个东西名字接近，职责差得远。

特性 CAN 网桥 CAN 网关
功能 转发 CAN 报文 转发、过滤、处理报文，做协议转换
网络连接 连接同协议的 CAN 网络 连接不同协议或不同波特率的网络
报文处理 不修改报文，直接转发 可以修改、过滤或组合报文
应用场景 连接多个 CAN 网络，延长物理距离 连接不同协议网络，过滤数据流

CAN 网桥负责物理连接两个或多个 CAN 网络，让它们在同一或不同波特率下通信。目的是透明转发，不做协议转换。

  • 连接不同波特率：一边 1Mbps，一边 500kbps，网桥在中间转。
  • 透明传输：不改报文内容，收到就往外发。
  • 延长物理距离：CAN 总线长度与波特率成反比，用网桥把几段短网络串起来，间接扩大了覆盖范围，而不突破单段网络的距离限制。

CAN 网关更聪明，除了连网络，还能过滤、转换、处理。

  • 协议转换：把 CAN 报文转成 LIN、FlexRay、Ethernet 的格式，在不同网络间交换数据。
  • 报文过滤和路由：按预设规则只转发符合条件的报文，或者改完内容再转。这能压低网络负载，也提高数据安全性。
  • 数据处理：跑应用逻辑，比如按收到的 CAN 消息触发操作，或者把多条消息合成一条再发。
  • 网络隔离与保护：连接不同网络时把故障和攻击隔在各段之内，不让它们扩散。

选网桥还是网关，看你要不要改动报文。只是延长距离、统一波特率，网桥够了。要做协议翻译或按 ID 筛选转发，必须网关。

五、终端电阻与布线 #

终端电阻是 CAN 现场调试最高频的物理层故障，没有之一。通信时好时坏、冷机正常热机出错、短线上正常长线上丢帧，先量终端电阻。

为什么必须要有 #

CAN 用双绞线，双绞线的特性阻抗约 120Ω。信号传到线的末端，如果末端阻抗跟线的特性阻抗不匹配，能量没地方去，就会反射回来。

反射波跟入射波叠加，总线电平上出现振铃。接收端在采样点看到的不再是干净的高低电平，而是带着毛刺的包络。轻则偶发 CRC 错，重则完全通不了。

终端电阻的作用就是吸收这份能量：末端接一个跟特性阻抗相等的 120Ω，信号到末端等于走进了无限长的线，不反射。

怎么接 #

规则很短：

  • 总线的两端各一个 120Ω 电阻，接在 CAN_H 和 CAN_L 之间。
  • 中间节点不能加。
  • 两个终端电阻是并联关系，用万用表在任意一点量 CAN_H 到 CAN_L 的电阻，正常值是 60Ω 左右。
text
        ┌──── 120Ω ────┐                ┌──── 120Ω ────┐
        │              │                │              │
CAN_H ──┴──┬───────┬───┴────────────────┴───┬───────┬──┴── CAN_H
           │       │                        │       │
         节点1    节点2                    节点3    节点4
           │       │                        │       │
CAN_L ─────┴───────┴────────────────────────┴───────┴───── CAN_L
        │                                       │
        └── 只在两端，中间不接 ──────────────────┘

量到 60Ω：正常。 量到 120Ω：只有一端接了电阻，另一端漏了，或者另一端电阻虚焊。 量到 40Ω 左右：多接了一个，三个 120Ω 并联。 量到 无穷大：两端都没接。 量到 明显偏小（比如 20Ω 以下）：接了太多，或者线间短路。

还有一种情况：量到 60Ω 但通信照样不稳。一种情况是电阻接了，但不在物理末端，而在中间某两个节点上。这种接线电气上量不出差别，但末端还是开放，反射照旧。查这个只能看拓扑图，量电阻没用。

少了和多了分别会怎样 #

终端电阻 现象 机理
少（只有一端或都没有） 反射、振铃、偶发 CRC 错、距离一长就丢帧、速率一高就崩 末端阻抗不匹配，信号能量反射回总线
多（三个以上） 总线负载过重，差分幅值下降，节点驱动能力不够 并联阻抗过低，收发器要灌/拉更大的电流
位置不对（不在末端） 量电阻正常但不稳 真正的末端仍然开放，照样反射

「多了会让总线负载过重」这句话要理解对：不是指总线负载率那个百分比，是指电气负载。每个 120Ω 都在常态消耗电流，并联越多等效阻抗越低，收发器输出的差分电压被拉低，远端节点收到的幅值不够，采样就出错。

所以终端电阻不是「多了更保险」，是「精确的两个」。

布线要点 #

  1. 双绞。CAN_H 和 CAN_L 必须绞在一起，绞距均匀。绞起来两根线拾取的干扰几乎相同，共模干扰在接收端相减抵消。
  2. 不要用屏蔽层的单端接地当地。屏蔽层只在一端接地，两端接地会形成地环路，反而引入干扰。
  3. CAN 地要连。很多现场只拉两根信号线不拉地，短距离能跑，距离一长共模电压漂出收发器的共模范围就挂了。
  4. 避开动力线。跟电机线、变频器输出线分开走线，平行距离越短越好，交叉时尽量垂直。
  5. 分支线尽量短。前面说过，1Mbps 时不超过 30 厘米。
  6. 接插件要可靠。现场故障里虚接的比例不低，尤其是压接端子和螺钉端子。

节点数量的实际上限，就是被这条「电气负载」卡住的：标准收发器能驱动的负载有限，挂太多节点等效电容变大，边沿变缓。常见经验值是单段不超过 110 个节点，实际工程里超过 30 个就该考虑分网加了网关了。

六、数据帧的结构 #

CAN 一共定义了 5 种帧：

帧类型 作用
数据帧 发送单元向接收单元传送数据
远程帧 接收单元向发送单元请求数据
错误帧 检测出错误时向其他单元通知错误
过载帧 接收单元通知自己还没就绪
间隔帧 把数据帧、远程帧与前面的帧隔开

我们平时说「发一帧 CAN」，99% 是数据帧。远程帧现在用得少，因为它的机制有坑：多个节点会同时响应同一个远程帧，撞在一起。FD 干脆取消了这个帧类型。

数据帧的 7 个段 #

数据帧由帧起始、仲裁段、控制段、数据段、CRC、ACK、帧结束共 7 段构成。数据帧和远程帧都有标准帧和扩展帧两种，标准帧 11 位 ID，扩展帧 29 位 ID。

text
标准帧（11 位 ID）
┌────┬──────────────┬────────┬──────────┬────────┬──────┬─────┬─────┐
│ SOF│  仲裁段       │ 控制段  │ 数据段    │  CRC   │ ACK  │ EOF │ IFS │
│ 1  │ 11位ID + RTR  │ IDE+   │ 0~8 字节  │ 15+1   │ 2    │ 7   │ 3   │
│    │              │ r0+DLC │          │        │      │     │     │
└────┴──────────────┴────────┴──────────┴────────┴──────┴─────┴─────┘

扩展帧（29 位 ID）
┌────┬────────────────────────────┬────────┬──────────┬────────┬──────┬─────┬─────┐
│ SOF│ 仲裁段                      │ 控制段  │ 数据段    │  CRC   │ ACK  │ EOF │ IFS │
│ 1  │ 11位ID+SRR+IDE+18位ID+RTR  │ r1+r0+ │ 0~8 字节  │ 15+1   │ 2    │ 7   │ 3   │

└────┴────────────────────────────┴────────┴──────────┴────────┴──────┴─────┴─────┘

逐段说。

帧起始（SOF, Start Of Frame），1 位。 表示帧开始的段，固定为显性（0）。总线空闲是隐性，第一个显性位就是 SOF。接收端靠这个下降沿做硬件同步。

仲裁段。 表达数据帧优先级的段。标准帧 11 位 ID，扩展帧 29 位 ID（11 位基本 ID + SRR + IDE + 18 位扩展 ID）。两种格式都禁止 ID 高 7 位全为隐性，也就是不允许 1111111XXXX。

ID 决定优先级，也决定其他节点收不收这帧。CAN 总线不给节点分配优先级和地址，对总线的占有权由信息的 ID 决定：重要的信息给小的 ID，就能优先发出去。

RTR 位（Remote Transmission Request），1 位。 区分数据帧和远程帧。0 是数据帧，1 是远程帧。

控制段，6 位。 由 IDE、保留位 r0（或 r1+r0）、DLC 组成，表示数据段的字节数。

IDE 位（Identifier Extension），1 位。 区分标准帧与扩展帧。0 是标准帧，1 是扩展帧。

SRR 位（Substitute Remote Request），1 位。 只存在于扩展帧，顶替标准帧里 RTR 的位置，固定为 1。数据帧的 RTR 是 0，所以 ID 相同时标准帧优先级更高。

DLC（Data Length Code），4 位。 数据的字节数，经典 CAN 里必须 0~8。

数据段，0~64 位。 包含 0~8 个字节的数据。经典 CAN 上限 8 字节，FD 到 64 字节。

CRC 段，16 位。 15 位 CRC 值加 1 位 CRC 界定符（隐性分隔位）。CRC 按多项式生成，计算范围包括帧起始、仲裁段、控制段、数据段。接收方用同样的方式算 CRC 再比较，不一致就发错误帧请求重发。

ACK 段，2 位。 包含 ACK 槽和 ACK 界定符。

  • 发送方在 ACK 段发两个隐性位。
  • 任何一个正确收到这帧的节点，在 ACK 槽发一个显性位，告诉发送方「我收到了」。这叫「发送 ACK」或「返回 ACK」。

注意 ACK 是「有人收到」而不是「目标收到了」。CAN 没有目的地址，发送方无法知道具体是哪个节点确认的。这也是为什么 CAN 的可靠性只在「至少一个节点收到」这个层面成立。

帧结束（EOF, End Of Frame），7 位。 7 个连续隐性位，表示帧结束。

关于 EOF 长度，有个流传的说法是「125kbps 以下用 7 位，以上用 3 位」。ISO 11898-1 定义的就是固定 7 位隐性位，没有按速率缩短这回事。那段说法把 EOF 和帧间隔（Intermission）搞混了。写协议分析工具时按 7 位实现。

帧间隔（IFS, Intermission），3 位。 EOF 之后紧跟 3 个隐性位。这 3 位不是任何帧的一部分，作用是给控制器留出处理时间。数据帧和远程帧之前必须有 IFS，错误帧和过载帧之后可以有。

位填充的影响 #

数据帧里，从 SOF 到 CRC 序列，连续 5 个相同电平之后必须插一个反向位。这条规则让帧的实际长度比标称长度长，也让「算帧有多长」变成一件要小心的事。

  • 发送单元：发数据帧和远程帧，SOF~CRC 段里相同电平持续 5 位，下一位插反型数据。
  • 接收单元：同样范围内相同电平持续 5 位，就删掉下一个位再收。如果删完发现还是相同，判定为错误并发错误帧。

填充是控制器自动做的，写应用的人不用管。但算总线负载时必须把它算进去，这是第十节的内容。

五种帧的长度（不含位填充） #

标准帧（DLC=8）是 108 位，逐段拆开：帧起始 1 + 仲裁段 12 + 控制段 6 + 数据段 64 + CRC 16 + ACK 2 + EOF 7。

扩展帧（DLC=8）是 128 位：帧起始 1 + 仲裁段 32 + 控制段 6 + 数据段 64 + CRC 16 + ACK 2 + EOF 7。

FD 帧因为多了 FDF、BRS、ESI 和更长的 CRC，标称长度都要重算：

帧型 仲裁段 控制段 数据段 CRC ACK EOF 合计
CAN 标准帧 DLC=8 12 6 64 16 2 7+1 108
CAN 扩展帧 DLC=8 32 6 64 16 2 7+1 128
FD 标准帧 DLC=8 12 9 64 22 2 7+1 117
FD 标准帧 DLC=64 12 9 512 26 2 7+1 569
FD 扩展帧 DLC=8 32 8 64 22 2 7+1 136
FD 扩展帧 DLC=64 32 8 512 26 2 7+1 588

表里有几处加起来对不上整数，是因为 FD 的 CRC 场在 17/21 位之外还有固定填充位和 Stuff Count，不同手册的归类方式不同（有的把 Stuff Count 算进控制段，有的算进 CRC）。工程上算负载按整帧位数量，别按段去对账。后面第十节给的是可用的整体估算。

一段真实的驱动代码 #

看内核里怎么把 can_frame 变成寄存器值，是理解帧结构最快的路子。这是 mcp251x 的发送函数：

c
static void mcp251x_hw_tx(struct spi_device *spi, struct can_frame *frame, int tx_buf_idx)
{
	struct mcp251x_priv *priv = spi_get_drvdata(spi);
	u32 sid, eid, exide, rtr;
	u8 buf[SPI_TRANSFER_BUF_LEN];
	/* 取 can_id 的 31 位，判断是标准帧还是扩展帧 */
	exide = (frame->can_id & CAN_EFF_FLAG) ? 1 : 0;
	if (exide)	/* 扩展帧：can_id 的 0-28 位为 ID，其中高 11 位是标准 ID */
		sid = (frame->can_id & CAN_EFF_MASK) >> 18;
	else
		sid = frame->can_id & CAN_SFF_MASK;	/* Standard ID */
	eid = frame->can_id & CAN_EFF_MASK;		/* Extended ID */
	rtr = (frame->can_id & CAN_RTR_FLAG) ? 1 : 0;	/* 是否是远程帧 */

	buf[TXBCTRL_OFF] = INSTRUCTION_LOAD_TXB(tx_buf_idx);
	buf[TXBSIDH_OFF] = sid >> SIDH_SHIFT;
	/* 5-7 位放标准 ID 低 3 位，3 位放帧格式，
	 * 0-1 位放扩展标识符低 18 位的高两位（16-17） */
	buf[TXBSIDL_OFF] = ((sid & SIDL_SID_MASK) << SIDL_SID_SHIFT)
		| (exide << SIDL_EXIDE_SHIFT)
		| ((eid >> SIDL_EID_SHIFT) & SIDL_EID_MASK);
	buf[TXBEID8_OFF] = GET_BYTE(eid, 1);	/* 扩展 ID 低 18 位的 8-15 位 */
	buf[TXBEID0_OFF] = GET_BYTE(eid, 0);	/* 扩展 ID 低 18 位的低 8 位 */
	buf[TXBDLC_OFF] = (rtr << DLC_RTR_SHIFT) | frame->can_dlc;
	memcpy(buf + TXBDAT_OFF, frame->data, frame->can_dlc);

	mcp251x_hw_tx_frame(spi, buf, frame->can_dlc, tx_buf_idx);
	/* 用 INSTRUCTION_RTS，避免「重复发送」问题 */
	priv->spi_tx_buf[0] = INSTRUCTION_RTS(1 << tx_buf_idx);
	mcp251x_spi_trans(priv->spi, 1);
}

几个点值得注意：can_id 是 32 位，ID 只占低 29 位，高 3 位是标志位，硬件寄存器里要拆开重新摆位置；TXBSIDL 那个寄存器一个字节塞了三样东西（标准 ID 的低 3 位、IDE 值、扩展 ID 的高 2 位），这种「一格多用」在 CAN 控制器里很常见，也是移植驱动时最容易写错的地方；TXBEID8 和 TXBEID0 拼出扩展 ID 的低 18 位；DLC 寄存器的高位还塞了 RTR 位。

七、仲裁：优先级怎么定 #

仲裁是 CAN 最核心的机制。看懂它，前面的「多主」「广播」「不需要主节点」全都顺了。

逐位比较，显性赢 #

总线空闲时，最先开口的节点拿到发送权。如果两个或多个节点同时开口，它们从仲裁段第一位开始逐位比较。

规则只有一条：连续输出显性电平最多的单元继续发送。

因为线与关系，显性覆盖隐性。A 发 0，B 发 1，总线上是 0。A 读回 0，跟自己发的一致，继续。B 读回 0，跟自己发的 1 不一致，知道自己输了，立刻停发改接收。

结果：ID 最小的节点赢。ID 越小，靠前的位越是 0（显性），也就越早占优。

举个数：

text
节点 A   ID = 0x123 = 000 0001 0010 0011
节点 B   ID = 0x124 = 000 0001 0010 0100
节点 C   ID = 0x0F0 = 000 0000 1111 0000

前 6 位 A、B、C 全是 0，继续比较第 7 位：
  第 7 位：A、B 发 1（隐性），C 发 0（显性）
  总线上是 0，A、B 读回 0 ≠ 自己发的 1，退出
  C 继续发完这一帧

结果：ID 最小的 C（0x0F0）赢得仲裁

整个过程没有浪费任何一个位时间。C 的波形从头到尾没被干扰，这一帧完整传完。这就叫非破坏性位仲裁。

A 和 B 退让之后干什么？转接收状态，收完这一帧，然后等总线空闲再重新参与仲裁。它们不需要随机退避，因为下一轮仲裁规则一样确定：ID 小的还是会先赢。

为什么这不需要主节点 #

以太网的做法是 CSMA/CD：先发，撞了再退，退避一个随机时间重试。冲突是「事后发现」的，撞坏的那段帧要丢掉重发，带宽浪费了。

CAN 的做法是 CSMA/CA（带仲裁的载波侦听）：一边发一边听，谁输在第几位就当场知道，赢家的帧一点没坏。冲突在「位级别」就解决了，不需要事后协商。

所以 CAN 上没有「谁先说话」的协调者。谁急（ID 小）谁先说，说不上的自动等下一轮。这是分布式的确定行为，不是协议约定的策略。

影响仲裁结果的几种情况 #

标准帧 vs 扩展帧，ID 相同。 标准帧赢。仲裁段里标准帧在 RTR 位置发 0（显性，数据帧），扩展帧在同一位置发 SRR=1（隐性），标准帧先取得优势。

数据帧 vs 远程帧，ID 相同。 数据帧赢。RTR 位在数据帧里是 0，在远程帧里是 1。这个设计很合理：请求数据的帧不该压过实际带数据的帧。

FD 帧 vs 经典 CAN 帧，ID 相同。 总线不允许混跑（经典控制器看到 FD 帧会报格式错），所以实际不会遇到。

仲裁失败的代价 #

对发送方来说，仲裁失败不是错误。错误计数器不加，不进错误状态。控制器只是把这一帧放回发送缓冲，等下次总线空闲重发。所以总线上大量低优先级帧频繁仲裁失败，也不会让节点进入错误状态。只有「重发一直失败」导致发送队列积压时，应用层才会感觉到延迟。

优先级怎么分配 #

设计阶段就要定好。几条经验：

  1. 安全相关的 ID 最小。刹车、转向、扭矩请求这些，给 0x000~0x0FF 段。
  2. 周期性实时控制次之。电机转速、电流环反馈，0x100~0x2FF。
  3. 状态和诊断再次。温度、电压、故障码，0x300~0x5FF。
  4. 标定、大数据量传输最后。诊断响应、软件刷写，0x600 以上。
  5. 留出余量。别把 0x000 用完，也别忘了 0x7FF 附近有禁用区间。

高优先级 ID 是稀缺资源。给多了等于没给，所有帧都急就都不急。

一个容易忽略的陷阱 #

仲裁只在「同时开口」时发生。如果高优先级帧的下一次发送时刻比低优先级帧晚，低优先级帧是可以先发的。

所以优先级保证的是「争用时谁先走」，不是「谁一定先走」。要严格保证时序，得配合时间触发机制（TTCAN 或上层协议的时间同步），纯靠 ID 优先级做不到硬实时。

这一点在设计安全相关功能时要算清楚：最坏情况下的延迟，是「一帧最长低优先级帧的传输时间」乘以「排在你前面的帧数」，不是零。

八、位定时与采样点 #

位定时是 CAN 里最容易被跳过、又最容易出问题的一节。两个节点的位定时不一致，会出现「各自单独通信都正常，一连上就大量错误帧」的现象。

NRZ 编码与同步需求 #

CAN 用 NRZ（Non-Return to Zero，不归零）编码。一个位的电平在整个位时间内保持不变，位的开头和结尾都不加同步信号。

  • 发送单元按自己的位时序发，不与别人同步。
  • 接收单元靠总线上的电平变化来重新同步。

没有时钟线，就没有共享时钟。每个节点用自己的晶振算位时间，晶振有误差，位时间就有误差。连续多个相同电平期间没有边沿，接收端无从校准，误差会累积。

两条机制对付这个：位填充（保证最多 5 个相同位就有一个边沿）和同步（用边沿重新对齐位时序）。

一位分四段 #

一个位被切成 4 段，每段由若干个 Time Quantum（Tq）构成。这个划分叫位时序。

段 全称 作用
SS 同步段（Sync Segment） 固定 1 Tq，边沿应该落在这里
PTS 传播时间段（Propagation Segment） 补偿信号在总线上的传播延迟和收发器延迟
PBS1 相位缓冲段 1（Phase Buffer Segment 1） 可加长，用于重新同步
PBS2 相位缓冲段 2（Phase Buffer Segment 2） 可缩短，用于重新同步

1 位由多少个 Tq 构成、每段占几个 Tq，都可以设定。通过设定位时序，多个节点能在同一个时刻采样，采样点位置也能任意选。

text
|<------------------ 1 位时间 (1 bit time) ------------------>|
|  SS  |      PTS      |     PBS1      |     PBS2     | 下一个位
| 1Tq  |    6Tq        |     7Tq       |     2Tq      |
                ↑ 采样点在这（PBS1 结束处）

采样点是读取总线电平、把读到的电平作为位值的那一点，位置在 PBS1 结束处。

用 ip 命令算位速率 #

一条真实的配置命令：

bash
ip link set can0 type can tq 125 prop-seg 6 phase-seg1 7 phase-seg2 2 sjw 1

逐个参数拆：

参数 值 含义
tq 125 ns 时间量化，CAN 控制器内部的基本时间单位
prop-seg 6 Tq 传播段，补偿总线传播延迟。6 × 125ns = 750ns
phase-seg1 7 Tq 相位缓冲段 1，采样点之前。7 × 125ns = 875ns
phase-seg2 2 Tq 相位缓冲段 2，采样点之后。2 × 125ns = 250ns
sjw 1 Tq 同步跳跃宽度，重新同步时允许跳的最大时间量，1 × 125ns = 125ns

算总位时间：

text
Sync Segment        : 1 Tq
Propagation Segment : 6 Tq
Phase Buffer Seg 1  : 7 Tq
Phase Buffer Seg 2  : 2 Tq

总时间量化数 = 1 + 6 + 7 + 2 = 16 Tq
总位时间     = 16 × 125 ns = 2000 ns = 2 μs
位速率       = 1 / 2 μs  = 500 kbps

同步段固定 1 Tq（有的控制器把它算进 prop-seg，用命令时注意看手册）。采样点位置 = (1 + 6 + 7) / 16 = 87.5%。

采样点该放哪 #

采样点的位置是个权衡：放太靠前，信号还没稳定就采样，容易读到边沿上的振铃；放太靠后，留给 PBS2 的余量不够，重新同步的能力变弱。

位速率 建议采样点
1Mbps 75% ~ 80%
500kbps 80% ~ 87.5%
250kbps 及以下 87.5%

CANopen 规定采样点 87.5%，这是设备互通的硬要求。做 CANopen 从站就必须配到 87.5%，否则一致性测试过不了。同一条总线上的所有节点，采样点必须接近，最好完全一致。差得太多（比如一个 75% 一个 87.5%），在长线、高负载、晶振偏差叠加的条件下会开始丢帧。

同步的两种方式 #

硬件同步。 接收单元在总线空闲状态检测出帧起始（SOF 的下降沿）时做的同步。检测到边沿的地方不考虑 SJW 的值，直接认为那是 SS 段。每帧开头都做一次，误差不会跨帧累积。

再同步（重同步）。 接收过程中检测到总线电平变化时做的调整。根据 SJW 的值，通过加长 PBS1 或缩短 PBS2 来对齐，最大调整量不超过 SJW。边沿出现在 PTS 和 PBS1 之间就加长 PBS1，边沿出现在 PBS2 之间就缩短 PBS2。采样点位置不变（始终在 PBS1 结束处），变的是这一位的总长度，让它向发送方对齐。

SJW 设大一点抗抖动能力强，但设太大又会在噪声边沿上误同步。经验值是 SJW 取 1 Tq（高速时）到 4 Tq（低速时）。

位填充 #

位填充是为了防止突发错误而设的功能。同样的电平持续 5 位，就插入一个反型的位。

  • 发送单元：发数据帧和远程帧时，SOF~CRC 段里相同电平持续 5 位，下一位插反型数据。
  • 接收单元：接收时同样范围内相同电平持续 5 位，删掉下一个位再收。如果删完发现还是和前面 5 位相同，判定为错误并发错误帧。
  • SOF 之前总线空闲，不需要同步，不需要填充；CRC 之后是固定格式，不允许填充。
  • 全部由 CAN 控制器自动实现，应用层不感知。

填充还有一个副作用：它让帧的实际长度不确定。同样 8 字节数据的两帧，填充位数各不相同。算负载时必须按最坏情况估。

位定时的现场调试顺序 #

  1. 先确认两端（或多端）的 bitrate 完全一致。最常见的问题是「以为都是 500k，其实一边是 500k 一边是 250k」。
  2. 用示波器量一位的宽度。500kbps 时应该是 2μs。量出来是 4μs 就是 250k。
  3. 量采样点位置。如果两端采样点差超过 10%，改成一致。
  4. 检查晶振精度。CAN 要求晶振误差在 ±0.5% 以内（用陶瓷谐振器常常超标，尤其温度变化时）。
  5. 最后才考虑调 sjw 和 prop-seg。这两个参数是补偿用的，不是修错的。

九、错误处理与总线关闭 #

CAN 的可靠性是设计出来的，不是运气好。它的错误处理有 5 种检测机制、3 种错误状态、2 个计数器，连成一个自愈系统。

五种错误检测 #

机制 谁做 检什么
位监视（Bit Monitoring） 发送方 发出去的位和读回的总线电平是否一致
位填充检查 收发双方 5 个相同位之后是否跟了反向位
CRC 校验 接收方 按多项式重算 CRC，与帧里的是否一致
格式检查 接收方 固定格式的位（CRC 界定符、ACK 界定符、EOF）是否为隐性
ACK 检查 发送方 ACK 槽里有没有节点回显性位

位监视有个例外：仲裁段和 ACK 槽里，发送方发出的隐性位被别人的显性位覆盖是正常现象，不算错误。这两处的监视是关掉的。

五种机制覆盖的错误类型不一样。位监视抓短路和驱动失效，填充检查抓同步丢失，CRC 抓随机位翻转，格式检查抓帧结构错乱，ACK 检查抓「没人收到」。

错误帧 #

任何节点检测到错误，下一个位时间就发错误帧：6 个连续显性位（故意违反位填充规则，让全网立刻发现异常）加 8 个隐性位的错误界定符。

6 个显性位会破坏当前正在传的那一帧的位填充规则，所有正在收的节点都会检测到填充错误，跟着发自己的错误标志。结果是错误标志叠加，总线上出现 6~12 个显性位。这一帧就此作废，发送方稍后重发。ISO 11898 规定：从检测到错误到下一帧开始，恢复时间最多 29 个位时间。

三种错误状态与两个计数器 #

每个节点维护两个计数器：TEC（Transmit Error Counter，发送错误计数器）和 REC（Receive Error Counter，接收错误计数器）。计数规则的核心思想是「谁出错谁负责」：

事件 TEC REC
发送方检测到错误 +8 —
接收方检测到错误 — +1
发送成功后 -1 —
接收成功后 — -1（若 REC > 0）

发送方出错加 8，接收方出错加 1。这个不对称是关键：一直发错的节点计数器涨得快，很快就被关掉；只是偶尔收到坏帧的节点涨得慢，不会被误伤。

按 TEC/REC 的值划分三种状态：

状态 条件 行为
主动错误（Error Active） TEC ≤ 127 且 REC ≤ 127 正常通信，检出错误发主动错误标志（6 个显性位）
被动错误（Error Passive） TEC > 127 或 REC > 127 能正常收发，但检出错误只发被动错误标志（6 个隐性位），且发送后要多等 8 位挂起时间
总线关闭（Bus Off） TEC > 255 主动断开与总线的连接，不再收发 
text
    TEC/REC ≤ 127            > 127              > 255
  ┌──────────────┐      ┌──────────────┐    ┌──────────┐
  │ Error Active │ ───> │ Error Passive│──> │ Bus Off  │
  │  主动错误     │      │  被动错误     │    │ 总线关闭  │
  └──────────────┘      └──────────────┘    └──────────┘
         ↑                     │                  │
         └─────────────────────┘                  │
           恢复到 ≤ 127                          │
                                   复位/自动恢复 ┘

重要区别：主动错误的节点发的是显性错误标志，能压制总线；被动错误的节点发隐性标志，压不住别人。这是故意的设计：一个自己都不太靠谱的节点，不该有权力打断全网通信。FD 的 ESI 位就是把这个状态广播出去。

总线关闭之后 #

TEC 超过 255，节点进入 bus-off，彻底退出总线。

bus-off 是个自我保护机制：一个持续发错的节点如果继续发，会用错误帧把整条总线拖垮。把它关掉，其他节点还能正常工作。

恢复方式有两种：

  • 自动恢复：控制器检测到总线连续 128 次出现 11 个连续隐性位（总线空闲），自动复位计数器回到主动错误状态。
  • 手动恢复：驱动或应用显式调用复位（比如 SocketCAN 里 ip link set can0 down 再 up）。

Linux 下可以配 restart-ms 让内核自动重启：

bash
# 100ms 后自动尝试恢复
ip link set can0 type can bitrate 500000 restart-ms 100

bus-off 频繁发生，说明有硬件问题。常见原因是终端电阻缺失或过多导致反射、某个节点收发器损坏一直往总线上灌错误电平、波特率配错、线缆断了一根或 CAN_H/CAN_L 接反、分支线过长高速率下采样错、电源不稳导致收发器间歇失效。排查顺序：先量终端电阻，再看有几个节点 bus-off，然后逐个拔节点试。

在 SocketCAN 里看错误 #

SocketCAN 把错误帧也送到用户态，can_id 带 CAN_ERR_FLAG 标志：

c
can_err_mask_t err_mask;
err_mask = CAN_ERR_ACK | CAN_ERR_CRTL | CAN_ERR_BUSOFF | CAN_ERR_BUSERROR;

ret = setsockopt(fd, SOL_CAN_RAW, CAN_RAW_ERR_FILTER, &err_mask, sizeof(err_mask));
if (ret < 0) {
	log_printf(LOG_ERR, CAN_ERROR_FILTER_FAILED, ifName);
	log_printf(LOG_DEBUG, DBG_ERRNO, "setsockopt(can err)");
	return CO_ERROR_SYSCALL;
}

四个标志位的含义：

标志 含义
CAN_ERR_ACK 收到错误应答（发送时没人 ACK）
CAN_ERR_CRTL 控制器错误，data[1] 里带具体状态
CAN_ERR_BUSOFF 总线关闭
CAN_ERR_BUSERROR 总线错误（位错误、填充错误等）

CAN_ERR_CRTL 的 data[1] 编码了更细的状态：错误主动、错误被动、接收溢出、发送溢出等，完整定义在 linux/can/error.h 里。

生产环境里建议至少打开 CAN_ERR_BUSOFF，bus-off 事件必须记录并上报，否则现场反馈「设备突然不发数据了」时无从查起。

十、负载率怎么算 #

负载率是 CAN 网络设计里最容易算错的一个数。常见的错法是拿「数据字节数 ÷ 带宽」，算出来一片美好，实际一上量就崩。

错在哪：CAN 的每一帧都带着一堆不携带数据的位。帧头、仲裁段、控制段、CRC、ACK、EOF、帧间隔，全都要花时间。再加上位填充，实际位数还得往上加。

所以正确的问题不是「我要传多少数据」，而是「我要传多少帧，每帧多少位」。

一帧到底多少位 #

先把标称位数摆出来（不含位填充，DLC=8）：

帧型 标称位数
标准帧（11 位 ID） 108
扩展帧（29 位 ID） 128

实际发送时，还要加：

  • 3 位的帧间隔（IFS）。
  • 位填充：最坏情况每 4 个原始位插 1 位，也就是 ×1.25。平均值在 1.1~1.15 之间。

工程上按下面的口径估：

口径 标准帧 8 字节 扩展帧 8 字节
标称位数 108 128
+ IFS 3 位 111 131
平均填充（约 1.15 系数） ≈ 128 ≈ 150
最坏填充（×1.25） ≈ 135 ≈ 160

流传最广的一个数字是「一帧 8 字节的标准帧约占 108~130 位」。这个区间正好覆盖标称值和平均值。工程估算用 111~130 位都算合理，做安全余量就取最坏值。

这就是为什么 500kbps 下能传的实际数据远少于想象。500kbps 是每秒 500000 个位时间，看着能传 62500 字节/秒。但按每帧 130 位算，每秒最多 3846 帧，每帧 8 字节净数据，实际上限是 30769 字节/秒。净载荷只占带宽的 49%。

换成长帧能好一点：FD 的 64 字节帧，标称 569 位，载荷占比提到 90%。这是 FD 存在的第二个理由（第一个是快）。

总线负载的计算 #

总线负载是「总线实际占用的带宽」与「总带宽」的比值，用百分比表示。一帧的发送时间就是总位数除以波特率：111 位（108 标称 + 3 IFS）在 500kbps 下是 222μs。要保守一点用 130 位算，一帧就是 260μs。

text
总线负载 = ((总帧时间 × 每秒发送的帧数) / 总可用时间) × 100%

总帧时间     ：一帧数据的发送时间
每秒发送的帧数：一秒钟内发送的帧数
总可用时间   ：每秒可用的时间，即 1 秒

举例：每秒发 1000 帧。

text
总帧时间 = 222 μs = 222 × 10^-6 秒
每秒发送帧数 = 1000 帧/秒
总可用时间 = 1 秒

总线负载 = ((222 × 10^-6 × 1000) / 1) × 100%
         = 0.222 × 100%
         = 22.2%

每秒 1000 帧、每帧 8 字节，在 500kbps 上是 22.2% 的负载。这个数看着很宽松，但如果这 1000 帧都是同一个 ID，突发集中在一起，瞬时负载会远高于 22.2%。

多个 ID 混跑怎么算 #

实际网络是多条报文按各自周期发。算法是逐条累加：

text
总线负载 = Σ (每帧位数 / 波特率) × (1000 / 周期ms) × 100%

假设 500kbps 上有这么几条：

报文 ID 周期 每帧位数（含填充估算） 每秒帧数 占用时间/秒
电机转速 0x101 10ms 130 100 26.0 ms
电机电流 0x102 10ms 130 100 26.0 ms
温度 0x201 100ms 130 10 2.6 ms
电压 0x202 100ms 130 10 2.6 ms
心跳 0x701 500ms 130 2 0.52 ms
合计 212 帧/秒 57.7 ms

负载 = 57.7ms / 1000ms = 5.77%。非常宽松。

再加 20 条 10ms 周期的报文，负载会跳到 60% 上下。这时候就开始危险了。

负载率的红线 #

负载率 状态 判断
< 30% 健康 有充足余量应对突发和重传
30% ~ 50% 可用 正常，但要监控增长趋势
50% ~ 70% 紧张 低优先级报文延迟明显，需要优化
70% ~ 80% 危险 延迟不可预测，偶发超时
> 80% 不可接受 一旦有重传就会连锁雪崩

为什么不建议超过 80%：CAN 的报文在仲裁失败、错误重传时会额外占用时间。负载本来就 80%，一帧重传就把瞬时负载推到 100%，后面的帧全部延迟，延迟又会触发上层的超时重发，正反馈形成雪崩。这不是理论上的担心，现场见过。一般设计目标定在 40% 以下，留一半余量给故障和扩展。

估算的常见错误 #

  1. 只算数据字节。 8 字节数据占 64 位，但整帧 130 位，误差一倍。
  2. 忘了位填充。 填充在最坏情况下让帧长 25%，突发的连续 0 或连续 1 会让负载比估算高。
  3. 忘了 ACK 和 IFS。 这两块不大，但乘以几万帧就不小。
  4. 按平均值算安全余量。 负载率要看峰值，不是均值。1000 帧集中在 100ms 内发完，瞬时负载是均值的 10 倍。
  5. 扩展帧按标准帧算。 扩展帧多 20 位，差 15%。
  6. FD 帧按整帧一个速率算。 FD 帧前段和后段速率不同，要分段算：仲裁段位数 / 仲裁速率 + 数据段位数 / 数据速率。

按第 6 条算一帧 FD 标准帧 DLC=64：仲裁段约 30 位（含 SOF、ID、控制段前半），数据段约 530 位。仲裁速率 500k、数据速率 2M：

text
时间 = 30 / 500000 + 530 / 2000000
     = 60 μs + 265 μs
     = 325 μs

对比经典 CAN 传同样 64 字节需要 8 帧（8 × 222μs = 1776μs），FD 快了 5 倍多。

一个实测的小工具 #

can-utils 里的 canbusload 能直接算实测负载，按实际抓到的帧和位数算，比手算准：

bash
canbusload can0@500000 -t    # 每秒打印一次 can0@500k 的负载

压测阶段用它对照设计值，偏差超过 20% 就说明有额外的帧在跑（重传、诊断、错误帧）。

十一、SocketCAN：Linux 下的 CAN 编程 #

SocketCAN 是 Linux 内核的 CAN 子系统。它的设计思路很干脆：把 CAN 设备当成网络设备，用标准 socket API 操作。

好处是不需要为 CAN 学一套新 API，socket/bind/read/write 直接能用；ip link 能配 CAN 接口；tcpdump 能抓 CAN 报文。坏处是它跟 TCP/IP 是两套东西，别指望用 connect 连到对端。CAN 无连接、无地址，bind 绑的是本机接口索引。

一个 CAN 功能要定哪些参数 #

写一个通用的 CAN 收发工具，需要暴露的参数就这些：

参数 说明 默认
接口名 can0 / can1 can0
波特率 单位 kbps，或直接给 Tq 500 kbps
发送 ID 11 位或 29 位 —
发送数据 字节数组，注意大小端转换 —
发送间隔 单位 ms 250 ms，最小 1 ms
发送次数 0 表示一直发 —
帧格式 标准帧 / 扩展帧 标准帧
本地回环 发出去的帧是否回给自己 关闭
错误判断 发送失败时的处理 —

大小端这一条要注意。CAN 报文里的多字节信号，字节序由上层协议规定（J1939 用大端，CANopen 用小端）。can_frame.data 只是个字节数组，内核不管字节序，你自己按协议摆。

流程固定：socket(PF_CAN, SOCK_RAW, CAN_RAW) 创建套接字 → ioctl(SIOCGIFINDEX) 取接口索引 → bind(AF_CAN, ifindex) 绑定设备 → setsockopt 设过滤规则、缓冲区、回环 → read/write 收发 → close。

初始化 #

SocketCAN 的数据结构和函数大多定义在 linux/can.h。套接字创建用标准网络套接字操作，定义在 sys/socket.h。

c
int s;
struct sockaddr_can addr;
struct ifreq ifr;

s = socket(PF_CAN, SOCK_RAW, CAN_RAW);	/* 创建 SocketCAN 套接字 */
strcpy(ifr.ifr_name, "can0");
ioctl(s, SIOCGIFINDEX, &ifr);		/* 指定 can0 设备 */

addr.can_family = AF_CAN;
addr.can_ifindex = ifr.ifr_ifindex;
bind(s, (struct sockaddr *)&addr, sizeof(addr));	/* 绑定 */

三个容易写错的地方：

  • PF_CAN 和 AF_CAN 值相同，但习惯上 socket() 用 PF_CAN，sockaddr 里用 AF_CAN。
  • SOCK_RAW + CAN_RAW 是两个参数，前者是 socket 类型，后者是协议。写错成 SOCK_DGRAM 就变成广播管理器（BCM）了。
  • ifr.ifr_ifindex 要在 ioctl 成功之后才可用，别只看返回值就往下走。

can_frame 结构 #

帧结构体是理解 SocketCAN 的钥匙：

c
/* CAN payload length and DLC definitions according to ISO 11898-1 */
#define CAN_MAX_DLC 8
#define CAN_MAX_DLEN 8

struct can_frame {
	canid_t can_id;	/* 32 bit CAN_ID + EFF/RTR/ERR flags */
	__u8 can_dlc;	/* frame payload length in byte */
	__u8 data[CAN_MAX_DLEN] __attribute__((aligned(8)));
};

就三个成员：帧头 canid_t 是 32 位无符号整数，按位定义功能；帧长 can_dlc 是 8 位无符号，表示数据区长度；数据区 data 是 CAN_MAX_DLEN 个 8 位无符号数的数组。

__attribute__((aligned(8))) 告诉编译器把 data 放在地址是 8 的倍数的内存位置上。这是为了对齐访问，某些架构上不这么写会触发非对齐访问异常。

canid_t 的位分配：

位 含义
0~28 标识符（11 位或 29 位）
29 错误消息帧标志（0 = 数据帧，1 = 错误帧）
30 远程帧标志（1 = RTR 帧）
31 帧格式标志（0 = 标准帧 11 位，1 = 扩展帧 29 位）

对应的宏定义：

c
/* special address description flags for the CAN_ID */
#define CAN_EFF_FLAG	0x80000000U	/* EFF/SFF is set in the MSB */
#define CAN_RTR_FLAG	0x40000000U	/* 远程帧 */
#define CAN_ERR_FLAG	0x20000000U	/* error frame */

/* valid bits in CAN ID for frame formats */
#define CAN_SFF_MASK	0x000007FFU	/* 标准帧 (SFF) */
#define CAN_EFF_MASK	0x1FFFFFFFU	/* 扩展帧 (EFF) */
#define CAN_ERR_MASK	0x1FFFFFFFU	/* omit EFF, RTR, ERR flags */

用的时候记住：标准帧 ID 直接填，扩展帧要 | CAN_EFF_FLAG，远程帧要 | CAN_RTR_FLAG。 忘了或标志，帧会被内核按 11 位 ID 截断后发出去，接收端看到的 ID 是错的，排查起来很折腾。

FD 用的是另一个结构：

c
#define CANFD_MAX_DLC 15
#define CANFD_MAX_DLEN 64

struct canfd_frame {
	canid_t can_id;
	__u8 len;
	__u8 flags;
	__u8 __res0;
	__u8 __res1;
	__u8 data[CANFD_MAX_DLEN] __attribute__((aligned(8)));
};

flags 里放 BRS 和 ESI 位（CANFD_BRS、CANFD_ESI）。len 是实际长度，DLC 由内核推（见第三节的映射表）。

用 C 代码配位速率 #

有时候不方便调 ip 命令（嵌入式环境没有 iproute2），得在代码里配：

c
#include <string.h>
#include <linux/can.h>
#include <linux/can/netlink.h>
#include <linux/sockios.h>
#include <sys/ioctl.h>
#include <sys/socket.h>
#include <net/if.h>

/* 改位速率之前必须先 down，接口 up 着改会返回 EBUSY */
static int set_bitrate(const char *ifname, int bitrate, int dbitrate)
{
	struct ifreq ifr;
	struct can_bittiming bt, dbt;
	int s = socket(PF_INET, SOCK_DGRAM, 0);

	if (s < 0)
		return -1;
	strncpy(ifr.ifr_name, ifname, IFNAMSIZ);

	ioctl(s, SIOCGIFFLAGS, &ifr);
	ifr.ifr_flags &= ~IFF_UP;
	ioctl(s, SIOCSIFFLAGS, &ifr);

	/* 仲裁段位速率 */
	memset(&bt, 0, sizeof(bt));
	bt.bitrate = bitrate;
	ifr.ifr_data = (void *)&bt;
	if (ioctl(s, SIOCSCANBT, &ifr) < 0)
		goto err;

	/* CAN FD 数据段位速率 */
	memset(&dbt, 0, sizeof(dbt));
	dbt.bitrate = dbitrate;
	ifr.ifr_data = (void *)&dbt;
	if (ioctl(s, SIOCSCANDBT, &ifr) < 0)
		goto err;

	ioctl(s, SIOCGIFFLAGS, &ifr);
	ifr.ifr_flags |= IFF_UP;
	if (ioctl(s, SIOCSIFFLAGS, &ifr) < 0)
		goto err;

	close(s);
	return 0;
err:
	perror("can config");
	close(s);
	return -1;
}

/* 调用：set_bitrate("can0", 500000, 4000000); */

两个要点：SIOCSCANBT 和 SIOCSCANDBT 不是 POSIX 标准，属于 Linux 的 CAN 扩展，头文件在 linux/can/netlink.h；参数只填 bitrate 时其余位时序字段留 0，内核按 CAN bit-timing calculation 自动算。另外 canconfig 来自 libsocketcan，比 ip 出现更早，老系统上只有它。

数据发送 #

CAN 的收发跟标准 socket 稍有不同：每次通信都用 can_frame 结构体把数据封装成帧。发远程帧只要把 CAN_RTR_FLAG 或进 can_id，can_dlc 填期望的数据长度。

c
struct can_frame frame;

/* 扩展帧写法：frame.can_id = CAN_EFF_FLAG | 0x123; */
frame.can_id  = 0x123;
frame.can_dlc = 1;		/* 数据长度 1 */
frame.data[0] = 0xAB;		/* 数据内容 0xAB */

int nbytes = write(s, &frame, sizeof(frame));

send、sendto、sendmsg 也能发，区别只在参数：send 不用给地址，sendto 传 sockaddr_can，sendmsg 用 msghdr 加 iovec 把缓冲地址和长度分开摆。

返回值 nbytes 必须检查。写成功返回 sizeof(struct can_frame)（16 字节），不是实际数据长度。返回 -1 时看 errno：ENOBUFS 是发送队列满了（总线太忙或没人 ACK）。

数据接收 #

c
struct can_frame frame;
int nbytes = read(s, &frame, sizeof(frame));

recv、recvfrom、recvmsg 也能收，MSG_DONTWAIT 是非阻塞模式。不带这个标志时 read 会一直阻塞到有帧到达，单线程程序里要小心。

一次收多帧用 recvmsg 配大缓冲，nbytes / sizeof(struct can_frame) 就是帧数：

c
struct can_frame frames[10];	/* 一次最多读 10 帧 */
struct msghdr msg = { 0 };
struct iovec iov = { .iov_base = frames, .iov_len = sizeof(frames) };
msg.msg_iov    = &iov;
msg.msg_iovlen = 1;

int nbytes = recvmsg(s, &msg, MSG_DONTWAIT);
if (nbytes > 0) {
	int num = nbytes / sizeof(struct can_frame);
	for (int i = 0; i < num; i++)
		printf("ID: 0x%X, DLC: %d\n", frames[i].can_id, frames[i].can_dlc);
}

过滤规则 #

接收时系统可以按预设规则过滤报文，规则用 can_filter 表示：

c
struct can_filter {
	canid_t can_id;
	canid_t can_mask;
};

/* 过滤原理：按位与比较 */
if ((received_can_id & filter.can_mask) == (filter.can_id & filter.can_mask))
	/* 接收此帧 */
else
	/* 丢弃此帧 */

can_id 里的 CAN_INV_FILTER 标志置位时，可以在过滤前把 can_id 按位取反。

一个套接字能设多条独立规则：

c
struct can_filter rfilter[2];
rfilter[0].can_id   = 0x123;
rfilter[0].can_mask = CAN_SFF_MASK;	/* 0x000007FF */
rfilter[1].can_id   = 0x200;
rfilter[1].can_mask = 0x700;

setsockopt(s, SOL_CAN_RAW, CAN_RAW_FILTER, &rfilter, sizeof(rfilter));
规则 can_id mask 收到什么
第一条 0x123 0x7FF 只收 ID 恰好为 0x123 的标准帧
第二条 0x200 0x700 收 ID 从 0x200 到 0x2FF 的帧

第二条为什么是区间：0x200 & 0x700 = 0x200，任何 0x2XX 的 ID 跟 0x700 按位与都等于 0x200。

禁用过滤规则后，原始套接字会忽略所有收到的报文。只发不收的应用可以在内核里省掉接收队列，减少 CPU 开销：

c
setsockopt(s, SOL_CAN_RAW, CAN_RAW_FILTER, NULL, 0);	/* 禁用过滤 */

错误帧也能用掩码过滤，CAN_ERR_TX_TIMEOUT、CAN_ERR_BUSOFF 按位或出想要的组合：

c
can_err_mask_t err_mask = (CAN_ERR_TX_TIMEOUT | CAN_ERR_BUSOFF);
setsockopt(s, SOL_CAN_RAW, CAN_RAW_ERR_FILTER, &err_mask, sizeof(err_mask));

缓冲区大小 #

CAN 帧在高负载时来得很密，默认接收缓冲区经常不够，表现为丢帧。加大的方法：

c
int bytes, sLen, ret;

bytes = 512 * 1024;
sLen  = sizeof(bytes);
/* root 用户用 SO_RCVBUFFORCE，能突破内核上限 */
ret = setsockopt(fd, SOL_SOCKET, SO_RCVBUFFORCE, (void *)&bytes, sLen);
/* 普通用户用 SO_RCVBUF */
ret = setsockopt(fd, SOL_SOCKET, SO_RCVBUF, (void *)&bytes, sLen);

sLen = sizeof(bytes);
getsockopt(fd, SOL_SOCKET, SO_RCVBUF, (void *)&bytes, &sLen);
if (sLen == sizeof(bytes))
	log_printf(LOG_INFO, CAN_SOCKET_BUF_SIZE, ifName, bytes / 446, bytes);

内核给每个 CAN 报文预留约 446 字节的骨架开销，所以 bytes / 446 才是能缓存的消息条数。512KB 差不多能存 1170 条。

回环与套接字状态 #

本地回环默认开启。关掉或打开：

c
int loopback = 0;	/* 0 关闭，1 开启（默认） */
setsockopt(s, SOL_CAN_RAW, CAN_RAW_LOOPBACK, &loopback, sizeof(loopback));

回环开着时，所有发送帧都会被回环到与 CAN 接口对应的套接字上。但默认情况下，发送套接字自己不收自己发的报文，所以发送端的回环是关的。想改这个行为：

c
int ro = 1;	/* 0 关闭（默认），1 开启 */
setsockopt(s, SOL_CAN_RAW, CAN_RAW_RECV_OWN_MSGS, &ro, sizeof(ro));

单机调试时这个功能很有用：没接总线也能测收发逻辑。RK3568 的原生 CAN 自收方案就是靠它做扩展帧校验的，细节在那篇驱动文章里。

查接收缓冲区里还有多少字节可读：

c
int bytes_available;
ioctl(sock, FIONREAD, &bytes_available);
if (bytes_available > 0)
	printf("套接字中有 %d 字节的 CAN 数据可接收\n", bytes_available);

ioctl 是往内核发控制命令的系统调用。SIOCSIFFLAGS 是它的一个命令常量，用来设置网络接口标志，启停接口、改工作模式都靠它。

从应用层到驱动的一条链路 #

发送时内核里的完整路径：

  1. sendto 进内核。sys_sendto 先把用户空间数据拷进内核并检查可读性。
  2. sys_sendto 调 sock_sendmsg()，再调 __sock_sendmsg()。
  3. __sock_sendmsg() 返回一个 sendmsg 函数指针（sock->ops->sendmsg）。
  4. net/can/raw.c 把 raw_sendmsg 的地址赋给这个指针，于是走到 raw_sendmsg()。
  5. net/can/af_can.c 的 can_send() 负责协议层传输。skb 指向套接字缓冲区和数据段的 CAN 帧，loop 参数决定要不要给本地监听者回环。

再往下是驱动。CAN 驱动编进内核，启动时注册，注册过程初始化 d_can_netdev_ops：这个结构体定义 3 个函数指针，其中 ndo_start_xmit 指向 d_can_start_xmit，后者调 d_can_write_msg_object() 准备报文并发送。

接收走中断 + NAPI。NAPI（New API）靠减少中断次数提性能：网卡发一次中断，处理程序调 NAPI，NAPI 看缓冲区里有没有够多的数据，有就一次处理完，不再反复触发中断。

CAN 的接收链路：

  1. 初始化时用 netif_napi_add() 把设备加进 NAPI 列表。
  2. 中断处理函数 d_can_isr 里用 napi_schedule() 调度 d_can_poll()。
  3. d_can_poll() 轮询收数据。进 poll 之前先判总线状态，因为 CAN 总线状态中断优先级最高。
  4. 状态正常才从接收寄存器取数据。

总线错误状态有三种：主动错误、被动错误、关闭，对应第九节。

Qt 走的是 QtSerialBus 模块，底层可以是 SocketCAN 插件，也可以是 Peak、Vector 等厂商插件。用 SocketCAN 需要先编译安装插件，关键字查「Using SocketCAN Plugin」。

pro 文件加一行：

text
QT += serialbus

枚举可用设备：

cpp
QString errorString;
const QList<QCanBusDeviceInfo> devices =
	QCanBus::instance()->availableDevices(QStringLiteral("socketcan"), &errorString);

if (!errorString.isEmpty())
	qDebug() << errorString;

多线程做高速收发时，用 PC 加 USBCAN-II 能达到 1ms 的通信周期。实践过的线程划分：

  • 3 个线程：1 个接收、1 个发送、1 个解析。
  • 接收线程给最高权限 QThread::HighestPriority，其余用 QThread::HighPriority。
  • 循环发送靠发送线程里再加一个定时器，timeout 设成需要的周期，能做到 1ms。
  • 主界面把待发报文组织成 OBJ 结构体数组，构造函数传进发送线程。
  • 解析线程：接收线程每收 n 帧就转给解析线程，按 ID 解析后把结果送主界面显示。

最后一条括号里的「不要 append」是实践出来的：主界面用 append 追加文本，高速率下会疯狂重排，UI 直接卡死。要么限制显示行数，要么用固定大小的环形缓冲。

十二、易错点速查 #

这一章把前面散落的坑集中列一遍。现场出问题先来这里对一遍，多数情况能直接定位。

物理层 #

现象 根因 处理
通信时好时坏，量电阻 120Ω 只有一端接了终端电阻 补上另一端
量电阻 40Ω 左右 多接了终端电阻 拆到只剩两端两个
量电阻正常但不稳 电阻接在中间节点，不在物理末端 按拓扑图挪到末端
距离一长就丢帧 分支线过长、线缆不是双绞 缩短 stub，换双绞线
差分幅值明显偏低 终端电阻过多、节点数超限 减电阻，分网加网关
只能短距离跑 波特率与线长不匹配 降速或缩短总线
某个节点一直 bus-off 该节点收发器损坏 换收发器
CAN_H / CAN_L 接反 布线错 对调

终端电阻那四条是老生常谈，但确实是最高频的故障。记住一句话：两端各一个 120Ω，中间不加，量出来 60Ω。

配置与位定时 #

现象 根因 处理
up 不起来，报设备忙 接口还 up 着就改位速率 先 ip link set can0 down
两节点各自正常，一连就大量错误帧 两边波特率不一致 用示波器量一位宽度

CAN FD 配了 bitrate 不收发 缺 dbitrate 和 fd on 补全三个参数
FD 帧发出去全网报错 总线上有经典 CAN 节点 FD 要求收发双方都支持

FD 那条单独强调：ip link set can0 type can bitrate 500000 这条经典 CAN 的命令直接套到 FD 上一定出问题。必须 bitrate ... dbitrate ... fd on，而且 dbitrate >= bitrate。

现象 根因 处理
接收端看到的 ID 不对 扩展帧忘了 | CAN_EFF_FLAG 补上标志位
标准帧 ID 被截断 ID 超过 0x7FF 换扩展帧或改 ID 分配

负载与时序 #

现象 根因 处理
实际负载远高于估算 只算了数据字节，没算帧开销 按 108~130 位/帧重算
突发时大量丢帧，均值负载却不高 按均值评估，没看峰值 用峰值窗口算瞬时负载
低优先级帧延迟不可控 负载超过 70% 降负载或拆网
高优先级帧也没按时到 优先级只在争用时生效 补时间触发机制或缩短帧长
重传风暴 负载超 80%，重传推高瞬时负载 立刻降负载，加错误监控

负载率这条的算法回顾：一帧 8 字节的标准帧约占 108~130 位，500kbps 下每秒最多传 3800 多帧，实际数据吞吐上限约 30KB/s。别拿 500kbps ÷ 8 位去算，那是错的。

高负载与内核 #

现象 根因 处理
高速率下应用层丢帧 接收缓冲区太小 调大 SO_RCVBUF，512KB 约存 1170 条
CPU 占用跑满，出现 RCU stall 错误帧中断过多 查物理层，或按平台改驱动配置
收到的帧没被处理 过滤规则写错 按位与验算 can_id & mask
发送返回 ENOBUFS 发送队列满，总线太忙或没人 ACK 降速率、查 ACK
单机测试收不到自己发的 发送套接字默认不开自收 CAN_RAW_RECV_OWN_MSGS 置 1

RCU stall 那条来自 RK3568 的实际案例：高速接收 CAN 帧时出现 rcu INFO: rcu_sched self-detected stall on CPU，CPU 跑满，根因是错误帧中断过多。把设备树里的驱动从 CANFD 改成 CAN 后恢复正常。这类问题的判断依据是「错误计数在涨 + CPU 满」，两个条件同时出现，先查物理层，别急着改代码。

平台坑 #

RK3568 有一份应用通告（RKAN18055）写明了两个设计缺陷，用这颗芯片做 CAN 要提前知道：

  • 作为发送方，扩展帧会概率性变成标准帧，接收方因此丢帧，影响通讯和控制。原因是发扩展帧时内部寄存器状态值在特定组合下触发 load 失败，最后按标准帧而不是扩展帧的格式发 ID 和 DLC 段。
  • 作为接收方，概率性出现 CRC 校验错误和 ID 段填充位错误，接收方会往总线发错误帧，由发送方重发。

规避方案之一是改 kernel/arch/arm64/boot/dts/rockchip/rk3568.dtsi，注释掉 workround 帧的配置，改完会自动打开 CAN 的 TXtoRX，原生 CAN 发扩展帧时会收回自己发的数据做校验，校验发现不是扩展帧就重发一帧。

这个方案有个明确的坑：扩展 ID 部分为 0 时会触发无限重发。用之前想清楚 ID 分配。

平台相关的细节不在这篇展开，驱动适配的部分看同目录那篇 Rockchip CAN 驱动。

一句话清单 #

上线前把这几条过一遍：

  1. 两端各有且仅有一个 120Ω，量出来 60Ω。
  2. 所有节点 bitrate 一致，采样点一致（CANopen 用 87.5%）。
  3. 单根分支线不超过 30 厘米（1Mbps），总线长度符合速率要求。
  4. 负载率峰值留一半余量，别按均值算。
  5. 每个报文 ID 有明确归属，安全相关的最小。
  6. 错误计数和 bus-off 事件有监控和上报。
  7. FD 网络里没有经典 CAN 节点，dbitrate >= bitrate。
  8. 扩展帧记得 CAN_EFF_FLAG，多字节信号按协议转字节序。

这八条过了，剩下的问题基本都能在软件层找到。
