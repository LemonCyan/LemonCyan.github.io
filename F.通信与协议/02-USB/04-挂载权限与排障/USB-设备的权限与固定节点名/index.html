讲什么：一块 USB 设备插到 Linux 上，普通用户为什么打不开它，以及它的设备节点名为什么每次开机都换。这两件事隔着好几章，根子是同一个 —— udev。udev 匹配到设备之后，既写它的权限，也写它在 /dev 下叫什么。一个规则文件能把两件事一起办掉。

不讲什么：USB 协议、枚举流程、描述符字段，看同系列《USB 2.0 协议：从物理层到枚举》；libusb 的 API 语义、编译与交叉编译，看 03-libusb与无驱方案 那几篇；设备插上之后怎么自动挂进目录树，看同目录另一篇《USB 设备的自动挂载》。

写法：命令给完整可粘贴的形态，规则文件逐字段拆开。涉及发行版差异的地方给查实际值的命令，不塞一个数值让你照抄。

一、为什么普通用户打不开 USB 设备 #

先看现象，别的都放一边。设备插好，普通用户跑程序：

text
$ ./can_tool
open /dev/bus/usb/001/004: Permission denied
$ sudo ./can_tool
（程序跑起来了）

加个 sudo 就好，这条线索指向权限，不指向驱动。有人第一反应是内核模块没加载、固件没烧、设备坏了，于是 lsmod、dmesg、换线换口折腾一圈。判断顺序应该反过来：

bash
lsusb

能列出这个设备，说明枚举走完了、驱动绑上了、内核知道它存在。问题只剩一个 —— 节点权限。

卡住你的是哪一类节点 #

Linux 上访问同一个 USB 设备，有两条完全不同的路，走的是两类节点，权限模型不一样。

节点 谁创建 默认属主与权限 谁会被卡住
/dev/bus/usb/001/004 内核 devtmpfs 建节点，udev 套规则定权限 root:root，0644（部分发行版 0664） 用 libusb 直接读写设备的程序
/dev/ttyUSB0 tty 驱动建节点，udev 定权限 root:dialout，0660 用串口库打开设备的程序，用户不在 dialout 组

第一条路是 usbfs，libusb 走的就是它。第二条路是串口驱动把设备暴露成 tty 节点，pyserial、minicom、picocom 走这条。

两条路的共同点：属主和权限都不是程序自己争来的，是 udev 在设备 add 那一刻写上去的。

手工 chmod 为什么不算数 #

最省事的办法是 sudo chmod 666 /dev/bus/usb/001/004。当场能用，重启就废。原因有三层：

  • /dev 是 devtmpfs，内存里的文件系统，每次开机重新生成
  • 就算不重启，设备拔下来再插回去，节点会重新创建，权限回到默认值
  • 重新枚举之后设备号会变，001/004 变成 001/005，你 chmod 的那个路径已经不指向它了

第三条最坑。你以为权限改好了，其实改的是上一个设备留下的旧节点。

结论很短：改权限只有一条正路，写 udev 规则，让 udev 每次建节点时自动按你的要求写权限。

二、/dev/bus/usb 的权限模型 #

路径是怎么拼出来的 #

/dev/bus/usb/<总线号>/<设备号>，两个数字都是十进制、三位补零。lsusb 的第二列和第四列就是它们：

text
Bus 001 Device 004: ID 04d8:0053 Microchip Technology, Inc.

对应到 /dev/bus/usb/001/004。

总线号跟着物理控制器走，插在同一个口上基本不变。设备号每次枚举重新分配，从 001 往上加，谁先枚举谁拿小号。所以 /dev/bus/usb/001/004 这个路径本身就漂 —— 和第七章讲的 ttyUSB0、ttyUSB1 换位置是同一种病，只是没人拿它当设备名用。

默认值长什么样 #

bash
ls -l /dev/bus/usb/*/*

text
crw-rw-r-- 1 root root 189,   0 11月 18 10:12 /dev/bus/usb/001/001
crw-rw-r-- 1 root root 189, 132 11月 18 10:12 /dev/bus/usb/001/004

189 是 usbfs 的主设备号，逗号后面那个次设备号由总线号和设备号算出来。

权限位 crw-rw-r-- 翻译成八进制是 0644。拆开看：

位段 八进制 含义 后果
rw-（属主 root） 6 root 可读可写 root 一切正常
rw-（属组 root） 6 root 组成员可读可写 root 组里没别人
r--（其他人） 4 其他用户只可读 普通用户能读描述符，不能发传输

libusb 干活时要用写权限：提交 URB、发控制传输、claim 接口，都是写操作。只给读权限，症状是在 libusb_open 之后、libusb_claim_interface 或传输那一步失败，报 LIBUSB_ERROR_ACCESS 或者内核直接甩 Permission denied。

这个 0644 是谁定的 #

内核 devtmpfs 只保证节点存在、属主是 root。0644 是 udev 在 add 事件里套完规则落下来的。规则来自发行版自带的基础文件：

bash
grep -n "usb" /usr/lib/udev/rules.d/50-udev-default.rules

老一点的发行版这个目录是 /lib/udev/rules.d/。不同发行版这一行写的数值不一样，0644 和 0664 都见过，plugdev 组也是有的发行版才默认加。

所以别照抄别人截图里的权限值。用这条命令看你自己的机器：

bash
ls -l /dev/bus/usb/*/* | head -5

一个更粗的老办法：usbfs 挂载参数 #

老内核上 usbfs 支持 devmode= 与 devgid= 两个挂载参数，一次把所有 USB 节点的权限放开到某个组。挂上之后 /dev/bus/usb/*/* 全是 0666 或者 0660 plugdev。

代价是全局生效：所有 USB 设备一个待遇，没法按 VID/PID 区分，也没法只对某一块设备放开。现在的发行版默认不再这么挂，看到这类教程可以直接跳过 —— 它不是错的，是过时的。

查设备身份的几条命令 #

写规则之前得先把 VID 和 PID 拿到手。三个层次，从粗到细：

text
Bus 001 Device 004: ID 04d8:0053 Microchip Technology, Inc. USBCAN Analyzer

冒号前面是 idVendor，后面是 idProduct，都是十六进制。只想看某一颗设备用 lsusb -d 04d8:0053；要完整描述符（序列号、供电、接口、端点）用 lsusb -vvv -d 04d8:0053。sysfs 里读同样的值，脚本里好使：

bash
for d in /sys/bus/usb/devices/*/; do
    [ -f "$d/idVendor" ] && echo "$d $(cat $d/idVendor):$(cat $d/idProduct)"
done

这些 /sys/bus/usb/devices/1-1 这样的目录名，就是第七章要用的端口号。

三、用 udev 规则授权 #

整个流程四步：拿 ID、建文件、写规则、让它生效。素材里两篇文章走的是同一套流程，差别只在规则文件的数值和文件名，下面两个版本都给。

第 1 步：拿到 VID 与 PID #

bash
lsusb -vvv

输出很长，往下翻找 idVendor 和 idProduct 两行：

图里那两行十六进制数抄下来，就是规则的匹配键。注意 -vvv 要带三个 v，带一个只给出概览，看不到描述符字段。

第 2 步：建规则文件 #

bash
sudo vi /etc/udev/rules.d/99-myusb.rules

命令里 vi 和路径之间那个空格别漏。素材原文印成 sudo vi/etc/udev/rules.d/50-myusb.rules，照抄会得到 sudo: vi/etc/udev/rules.d/50-myusb.rules: command not found。

路径和文件名有几条硬要求：

  • 必须在 /etc/udev/rules.d/，扩展名必须是 .rules，改别的后缀 udev 不认
  • 文件名前面的数字决定加载顺序，越小越先。99- 排最后，压过发行版基础规则；50- 早一些
  • 不同目录下同名文件，/etc/udev/rules.d/ 压过 /usr/lib/udev/rules.d/
  • 属主 root，权限 0644。给成 world-writable 的文件 udev 会跳过并打警告

建完之后看一眼目录，多出来的那一行就是你的：

bash
ls -l /etc/udev/rules.d/

第 3 步：写规则 #

USBCAN 的版本，文件名 99-myusb.rules：

bash
# USBCAN 分析仪：VID 04d8 / PID 0053
ACTION=="add", SUBSYSTEMS=="usb", ATTRS{idVendor}=="04d8", ATTRS{idProduct}=="0053", GROUP="users", MODE="0777"

PL2303 串口的版本，文件名 50-myusb.rules：

bash
# PL2303 串口：VID 067b / PID 2303
SUBSYSTEMS=="usb", ATTRS{idVendor}=="067b", ATTRS{idProduct}=="2303", GROUP="users", MODE="0666"

三个差异值得说清楚：

差异 第一个版本 第二个版本 怎么选
ACTION=="add" 显式写了 省略 省略也行，改权限的规则只在 add 时有意义
SUBSYSTEMS usb usb 这里必须用复数形式，第七章讲为什么
MODE 0777 0666 字符设备不需要执行位，0666 够用，见第五章

写进文件后长这样：

文件里一行一条规则，不要换行折行 —— udev 按行解析，折成两行就是两条残缺规则。注释用 # 开头，必须独占一行，规则行尾加 # 注释会被当成规则的一部分解析失败。

第 4 步：让它生效 #

bash
sudo udevadm control --reload
sudo udevadm trigger

两条命令分工不同，缺一不可：

  • --reload 只让 udev 重新读一遍规则文件，已经建好的节点不会动
  • trigger 才会把规则重新套用到现有设备上，把权限改过来

除此之外还有两条路：把设备拔了再插，或者重启。效果一样，reload + trigger 最快，不用碰硬件。

写完规则之后正常应该这样：普通用户直接跑程序，不用 sudo。

bash
$ ./can_tool
（正常收发）
$ ls -l /dev/bus/usb/001/004
crw-rw-rw- 1 root users 189, 132 11月 18 10:20 /dev/bus/usb/001/004

组从 root 变成了 users，权限位从 0644 变成 0666，两个字段都对上了，规则就生效了。

四、udev 规则的匹配字段 #

规则文件一行一条规则。一条规则由若干个 键 操作符 值 用逗号连起来，操作符只有五个：

操作符 作用 出现在
== 比较，不相等则整条规则不成立 匹配键
!= 不等于 匹配键
= 赋值，覆盖之前的值 赋值键
+= 追加到列表 赋值键
:= 赋值并锁定，后续规则改不动 赋值键

匹配键和赋值键可以混在同一行。从左到右求值，遇到不成立的匹配键，整条规则直接放弃。

匹配键一览 #

匹配键 匹配对象 例子 单复数含义
ACTION 事件类型 add、remove、change、bind 无单复数
SUBSYSTEM 当前设备自己的子系统 tty、usb、block 只看自己
SUBSYSTEMS 沿设备树向上的所有父设备子系统 usb 向上翻
KERNEL 当前设备自己的节点名 ttyUSB0、ttyUSB* 只看自己
KERNELS 沿设备树向上的所有父节点名 3-1.1 向上翻
ATTR{文件} 当前设备自己 sysfs 目录里的属性文件 ATTR{bInterfaceNumber} 只看自己
ATTRS{文件} 当前设备与所有祖先设备的属性文件 ATTRS{idVendor} 向上翻
DRIVER 当前设备绑定的驱动 pl2303 只看自己
DRIVERS 祖先设备的驱动 usb 向上翻
ENV{键} 环境变量 ENV{ID_VENDOR_ID} 无单复数
TAG 系统标签 uaccess 无单复数
TEST{路径} 判断某个 sysfs 文件存不存在 TEST=="power/control" 无单复数

规律就一条：单数只看自己，复数沿设备树往上翻。记住这条，ATTR 和 ATTRS 不会用错。

ATTR 与 ATTRS 的区别 #

这是写 udev 规则最容易错的一处，值得单独讲。一颗 USB 转串口设备插上之后，sysfs 里的设备树分层是这样：

text
... USB 控制器
└── 3-1                     usb_device，本层属性有 idVendor、idProduct、serial
    └── 3-1.1               usb_device，设备插在 3-1 的第 1 个口上
        └── 3-1.1:1.0       usb_interface，本层属性有 bInterfaceNumber
            └── ttyUSB0
                └── tty
                    └── ttyUSB0   ← 内核在这一层建出 /dev/ttyUSB0

idVendor、idProduct 挂在最上面那层 usb_device 上，离 tty 节点隔了三层。可 udev 改权限时，盯的是最底下那个 tty 节点 —— 因为要改的是 /dev/ttyUSB0。

于是：

写法 查找范围 匹配 idVendor 什么时候用
ATTR{idVendor}=="067b" 只翻当前设备自己的 sysfs 目录 找不到这个文件，匹配失败 匹配当前节点独有的属性，比如 ATTR{bInterfaceNumber}=="00"
ATTRS{idVendor}=="067b" 当前设备加上所有祖先设备 在 usb_device 那层找到，匹配成功 匹配 USB 描述符里的 VID、PID、序列号

写 ATTR{idVendor} 的后果不是报错，是规则静默失效。文件语法没错、udevadm test 也没报错，就是权限不变，很容易怀疑到别的地方去。

判断该用哪个不用背口诀，跑一条命令看属性树：

bash
udevadm info -a --name=/dev/ttyUSB0 | head -40

text
looking at device '/devices/ff540000.usb/usb3/3-1/3-1.1/3-1.1:1.0/ttyUSB0/tty/ttyUSB0':
    KERNEL=="ttyUSB0"
    SUBSYSTEM=="tty"
    DRIVER==""

looking at parent device '/devices/ff540000.usb/usb3/3-1/3-1.1':
    KERNELS=="3-1.1"
    SUBSYSTEMS=="usb"
    DRIVERS=="usb"
    ATTRS{idVendor}=="067b"
    ATTRS{idProduct}=="2303"
    ATTRS{serial}=="A10K1234"

输出按层分段。出现在 looking at parent device 那一段里的属性，匹配时必须用复数键。idVendor 出现在 parent 段，所以只能写 ATTRS{idVendor}。

单复数混用是正常写法 #

一条规则里同时用单数和复数没毛病，各管一件事：

bash
SUBSYSTEM=="tty", ATTRS{idVendor}=="067b", ATTRS{idProduct}=="2303", GROUP="users", MODE="0666"
  • SUBSYSTEM=="tty" 锁住「我要改的对象是 tty 节点」
  • ATTRS{idVendor}、ATTRS{idProduct} 锁住「哪一颗设备」
  • GROUP、MODE 是赋值，真正改动的东西

这是给串口设备授权的标准形态。换成 USBCAN 那种裸设备（无 tty 节点，走 libusb），对象就是 usb 设备本身，此时 SUBSYSTEM 用 usb、ATTR 也能写通 —— 但沿用 SUBSYSTEMS + ATTRS 的写法更保险，两层都能命中。

KERNEL 用 glob，不是正则 #

bash
KERNEL=="ttyUSB*"
KERNEL=="ttyUSB[0-9]"
KERNEL=="ttyUSB?"

* 任意长度，? 单个字符，[] 字符集，| 二选一（ttyUSB0|ttyUSB1）。这是 shell 风格的 glob，\d+、.* 这类正则语法不认。

KERNEL=="ttyUSB*" 一次性命中所有 USB 串口节点，不区分是哪一颗设备。只想改权限、不在乎是哪颗设备时可以这么写；要按设备身份区分就靠 ATTRS。

五、三种授权方式对比 #

给权限的写法有三种，效果、安全边界、依赖都不一样。

方式 写法 谁能访问 依赖 适用
改权限位 MODE="0666" 所有用户 无 单人开发机、内网测试台
改组 GROUP="users", MODE="0660" 指定组的成员 组存在 多人共享机、后台服务
授权标签 TAG+="uaccess" 本地登录的那个用户 systemd-logind 桌面系统、即插即用

方式一：MODE #

bash
MODE="0666"

给所有用户读写。字符设备用不上执行位，0666 就是全开。素材里第一版写的 MODE="0777" 一样能跑，多出来的执行位对字符设备没有意义 —— 内核在字符设备上不看 x 位。统一写 0666 更清楚。

反向的取值：

值 效果 说明
0600 只有 root 等于没改，普通用户照样打不开
0660 属主与属组读写 必须配 GROUP，否则属组还是 root
0664 属主属组读写，其他人只读 只读够用时可取，libusb 要写，不够
0666 所有人读写 最省事，也最不设防

代价直白：所有用户都能读写这块设备。单用户开发机、离线设备、产线测试台，这就是最优解，别为了「安全」把自己绕进组管理里。多用户共享的机器上，等于把设备交出去。

方式二：GROUP #

bash
GROUP="users", MODE="0660"

把节点属组改成 users（或者更贴切的 plugdev、dialout），权限 0660，组内成员能读写，组外一律不行。授权和收回都靠成员管理，比 0666 可控。

组得先存在：

bash
getent group users
getent group dialout
getent group plugdev

没有就建：

bash
sudo groupadd -f users
sudo usermod -aG users $USER

usermod 加组之后当前 shell 里不生效，要重新登录，或者临时 newgrp users 切一个子 shell 出来。改完确认：

bash
id

两个字段必须配对。只写 GROUP="users" 不写 MODE，权限还是 0644，组员依旧只能读。GROUP 只改属主归属，不动权限位。

方式三：TAG+="uaccess" #

bash
TAG+="uaccess", TAG+="udev-acl"

systemd 体系里的做法。udev 给节点打上 uaccess 标签，systemd-logind 收到通知，给「坐在机器前登录的那个用户」发一条 POSIX ACL，让他独占访问。

好处是不写死用户名，也不写死组名：谁在本地登录，谁就有权限；注销就收走。远程 SSH 进来的会话拿不到，因为 logind 只认本地 seat。

bash
getfacl /dev/bus/usb/001/004

text
# file: dev/bus/usb/001/004
# owner: root
# group: root
user::rw-
user:liuluhua:rw-
group::r--
mask::rw-
other::r--

user:liuluhua:rw- 这行就是 ACL。

限制很硬：必须有 systemd-logind 在跑。纯 sysvinit、容器里、initramfs 阶段、把程序做成 systemd 服务并切到别的用户身份跑 —— 这些场景 uaccess 全都不管用。服务场景老老实实用 GROUP。

另一个坑：桌面登录之后 sudo -i 切到 root，再切回来，ACL 已经跟着会话走了。确认权限时用普通用户直接跑，别在 root shell 里判断。

怎么选 #

场景 选哪个 理由
单用户开发机，图省事 MODE="0666" 一行搞定，安全边界本来就不是问题
多人共享测试机 GROUP + MODE="0660" 按组授权，能收回
桌面系统，插上就用 TAG+="uaccess" 跟着登录会话走，不用维护组
后台服务、开机自启 GROUP + MODE="0660" 服务运行时没有 seat，uaccess 失效
容器里 MODE 或设备直通 logind 不在容器里

三个键都是赋值键，不冲突，可以同一条规则里一起写。GROUP 配 MODE="0666" 时组信息还在，但权限位放得太宽，组隔离已经没意义了。

六、udev 规则的生效与调试 #

reload 与 trigger 的分工 #

bash
sudo udevadm control --reload
sudo udevadm trigger

第一条让 udev 重新读一遍规则文件，第二条把规则重新套用到已经存在的设备上。只做第一条，新规则躺在内存里，现有节点的权限一点没变 —— 改完规则看不到效果，多数是漏了第二条。

只想重放某个子系统，缩小范围：

bash
sudo udevadm trigger --subsystem-match=usb
sudo udevadm trigger --subsystem-match=tty

--action=change 可以强制重放 change 事件，有些内核上比默认的 add 更容易命中规则：

bash
sudo udevadm trigger --action=change --subsystem-match=tty

看 udev 眼中的这台设备 #

bash
udevadm info --query=all --name=/dev/ttyUSB0

text
P: /devices/ff540000.usb/usb3/3-1/3-1.1/3-1.1:1.0/ttyUSB0/tty/ttyUSB0
N: ttyUSB0
S: serial/by-id/usb-Prolific_Technology_Inc._USB-Serial_Controller-if00-port0
E: DEVPATH=/devices/ff540000.usb/usb3/3-1/3-1.1/3-1.1:1.0/ttyUSB0/tty/ttyUSB0
E: SUBSYSTEM=tty
E: DEVNAME=/dev/ttyUSB0
E: ID_VENDOR_ID=067b
E: ID_MODEL_ID=2303
E: ID_SERIAL_SHORT=A10K1234
E: DEVLINKS=/dev/serial/by-id/usb-Prolific_Technology_Inc._USB-Serial_Controller-if00-port0 /dev/serial/by-path/platform-ff540000.usb-usb-0:1.1:1.0-port0

P: 是 sysfs 路径，N: 是节点名，S: 是已有软链，E: 是环境变量。规则里能拿来匹配的东西，这里基本都能对上。

S: 和 E: DEVLINKS 出现的两个路径，就是第九章要用的 by-id 和 by-path，系统已经替你建好了。

预演规则 #

bash
sudo udevadm test /sys/class/tty/ttyUSB0

它按当前规则集把事件走一遍，打印每条命中的规则和最终赋值，不作用于真实设备。改规则之前先跑一遍，语法错当场就能看见。

输出里盯三类行：

  • 你的规则文件路径出现了 —— 说明文件被加载
  • MODE 0666、GROUP users 出现了 —— 说明赋值键认上了
  • 任何 invalid、unknown、failed to 字样 —— 语法有问题

udevadm test 只是预演，它不替你做 reload + trigger。预演通过不等于设备已经生效。

开着日志改规则 #

bash
sudo udevadm control --log-priority=debug
sudo journalctl -u systemd-udevd -f

另开一个终端插拔设备，日志里能看到每条规则的求值过程。debug 会刷很多，排查完调回 sudo udevadm control --log-priority=info。只想看事件本身、不看规则细节，用 sudo udevadm monitor --udev --property：插一次设备，把打印出来的 ID_VENDOR_ID、ID_MODEL_ID、DEVPATH 抄进规则，比手抄 lsusb 输出靠谱。

常见失效原因 #

现象 原因 处理
规则文件像没被读过 后缀不是 .rules，或放在了临时目录 挪到 /etc/udev/rules.d/，后缀改对
改完权限没变 只 reload，没 trigger 补 sudo udevadm trigger
一整条规则不生效 规则被编辑器折成两行 一条规则写在一行里
行尾注释导致解析失败 在规则行尾加了 # 注释 注释单独一行，# 开头
匹配不上 idVendor 用了 ATTR，该用 ATTRS 改成复数键
匹配不上 文件名不是 .rules 结尾，或者逗号漏了 逐字段核对
权限被改回去 有更晚加载的规则覆盖了同一个键 udevadm test 看最终赋值，调文件名数字
只重启才管用 规则对了但没重放事件 reload + trigger
权限对了名字没变 只写了 MODE，没写 SYMLINK 见第八章

规则文件的加载顺序 #

同一台设备会被多个规则文件命中，按文件名数字从小到大执行，后面的覆盖前面的。99-myusb.rules 排在发行版自带的 50-udev-default.rules 之后，所以能用 MODE 盖掉默认的 0644。

数字小的先跑、数字大的后跑 —— 想让自己的规则最后说话，就用 99-。反过来，如果你的规则总被别人的改回去，把数字加大到自己排最后一位。

:= 能锁定一个键，让后续规则改不动：

bash
MODE:="0666"

这个键用得少，靠文件顺序能解决的事不用它。用之前想清楚，锁定之后连你自己后面的规则也改不了。

七、设备节点名为什么会变 #

内核按枚举顺序发号 #

USB 转串口设备插上之后，内核在 /dev 下建出 ttyUSBx，x 从 0 数起。这个数字怎么来的？就是枚举顺序。

先插的那颗拿 0，后插的拿 1。逻辑简单到一个程度：它是「第几个被认出来的」，不是「它是谁」。设备没有身份，只有一个排队号。

于是顺序一变，名字就换。两个口几乎同时上电时，谁先枚举完谁拿 0，每次开机都会换边。

时刻 3-1.1 上的设备 3-1.2 上的设备
第一次开机 ttyUSB0 ttyUSB1
第二次开机 ttyUSB1 ttyUSB0
拔掉 A，只留 B B 变成 ttyUSB0 （空）
再插回 A A 拿 ttyUSB2 B 还是 ttyUSB0

最后一行容易被忽略：编号只增不减，反复插拔会一直往上加，能加到 ttyUSB7、ttyUSB8。不看 /sys 光看名字，早晚对不上。

/dev 下没有哪条命令能告诉你「ttyUSB0 永远是那颗设备」。这条路走不通，得换标识。

端口号是稳定的 #

USB 端口有唯一标识，形态是 3-1.1、3-1.2 这种。读法：3 是总线号，-1 是根集线器往下第一级，.1 是第二级。像门牌号，物理位置不变，插什么都一样。

同一颗设备插同一个口，端口号永远是这个；换到另一个口，端口号跟着变。这个特性和枚举顺序无关，也和插入先后无关。

查看方式：

bash
ls -l /sys/class/tty/ttyUSB*

text
lrwxrwxrwx 1 root root 0 11月 18 10:12 ttyUSB0 -> ../../devices/ff540000.usb/usb3/3-1/3-1.1/3-1.1:1.0/ttyUSB0/tty/ttyUSB0
lrwxrwxrwx 1 root root 0 11月 18 10:12 ttyUSB1 -> ../../devices/ff540000.usb/usb3/3-1/3-1.2/3-1.2:1.0/ttyUSB1/tty/ttyUSB1

链路里 3-1/3-1.1 和 3-1/3-1.2 两段就是端口号。ttyUSB0 在 3-1.1，ttyUSB1 在 3-1.2。

把两颗设备换个口插，结果反过来：3-1.1 上的那颗变成 ttyUSB1，3-1.2 上的变成 ttyUSB0。名字换了，端口号没换。

这不是「有时候」，是「必然」。上层软件如果硬编码 /dev/ttyUSB0，就等着收错误数据 —— 打开是成功的，读回来的字节属于另一台设备。

一眼看出当前对应关系 #

bash
for t in /sys/class/tty/ttyUSB*; do
    printf '%s -> %s\n' "$(basename $t)" "$(readlink -f $t)"
done

text
ttyUSB0 -> /sys/devices/ff540000.usb/usb3/3-1/3-1.1/3-1.1:1.0/ttyUSB0/tty/ttyUSB0
ttyUSB1 -> /sys/devices/ff540000.usb/usb3/3-1/3-1.2/3-1.2:1.0/ttyUSB1/tty/ttyUSB1

采集脚本启动时跑一次，把映射打日志里。以后出问题，先看这段日志确认拿到的是哪个口。

三套解法 #

方案 依据 稳定性来源 在哪一章
udev 规则建软链 设备属性（VID/PID/序列号/端口） udev 每次 add 时重建 第八章
by-id / by-path 系统预建的软链目录 内核 + udev 自动维护 第九章
程序里动态查找 运行时遍历 sysfs 或 udev 枚举 代码每次启动重新查 第十章

三套方案都不是「让 ttyUSB0 固定」。内核发号这件事改不了，能改的只是「你怎么找到它」。

八、方案一：udev 规则建固定软链 #

和权限是同一条规则 #

回到本篇的主线：udev 匹配到设备之后干两件事 —— 定权限、定名字。这两个动作可以写在同一个规则文件里，甚至同一行里。

bash
# /etc/udev/rules.d/99-myusb.rules
SUBSYSTEM=="tty", ATTRS{idVendor}=="067b", ATTRS{idProduct}=="2303", \
    ATTRS{serial}=="A10K1234", \
    SYMLINK+="ttydata", GROUP="users", MODE="0666"

上面为了排版折了行，实际写进文件时必须是一整行：

bash
SUBSYSTEM=="tty", ATTRS{idVendor}=="067b", ATTRS{idProduct}=="2303", ATTRS{serial}=="A10K1234", SYMLINK+="ttydata", GROUP="users", MODE="0666"

SYMLINK+="ttydata" 让 udev 在 /dev 下建一个 ttydata 指向真实节点；GROUP 和 MODE 同时把权限落好。一个文件、一次 reload + trigger，两个问题一起解决 —— 这就是本篇开头那句话的具体形态。

SYMLINK+= 用 += 不用 =。= 会覆盖别人已经设好的软链列表，+= 是追加。写 = 的后果是把你不想破坏的 by-id、by-path 链一起抹掉。

只按 VID/PID 建链 #

手边没有序列号，或者不关心具体是哪一颗，只按型号区分：

bash
SUBSYSTEM=="tty", ATTRS{idVendor}=="067b", ATTRS{idProduct}=="2303", SYMLINK+="ttydata"

两颗同型号设备同时插上时，规则会命中两个事件，两个事件都往 /dev/ttydata 建链，后建的那个覆盖前面的。结果不确定。同型号多颗的场景不能用这一条，得靠序列号或端口号区分。

按端口号建链 #

物理位置固定的设备，直接用端口号最省事：

bash
SUBSYSTEM=="tty", KERNELS=="3-1.1", SYMLINK+="ttydata"
SUBSYSTEM=="tty", KERNELS=="3-1.2", SYMLINK+="ttyother"

KERNELS 是复数键，沿设备树向上匹配 3-1.1 这个父目录名。端口号就是第七章 ls -l /sys/class/tty/ttyUSB* 里读出来的那一段。

板子上设备焊死、口不动的场景，这条规则最短也最稳。代价写在规则里：换口就得改规则。

命名空间与子目录 #

bash
SYMLINK+="mydev/ttydata"

/dev 下的子目录 udev 会自动创建，最后得到 /dev/mydev/ttydata。设备多的时候按用途分目录，/dev 不至于堆成一团。

用 ENV 里的现成值 #

udev 已经替你算好一批环境变量，udevadm info 的 E: 行里能看到。拿它们建链能少写条件：

bash
SUBSYSTEM=="tty", ATTRS{idVendor}=="067b", SYMLINK+="tty-$env{ID_SERIAL_SHORT}"

$env{...} 取环境变量值。ID_SERIAL_SHORT 是序列号，ID_PATH 是路径标识，ID_MODEL 是型号名。这些值在插入时才确定，规则里只能在赋值侧用，不能在匹配侧用。

生效与验证 #

bash
sudo udevadm control --reload
sudo udevadm trigger --subsystem-match=tty
ls -l /dev/ttydata

text
lrwxrwxrwx 1 root root 7 11月 18 10:20 /dev/ttydata -> ttyUSB1

验证要连着做两次，第二次把两颗设备换个顺序插：

bash
readlink -f /dev/ttydata

两次都指向同一个端口对应的那颗设备，方案就成立。readlink -f 给的是真实的 /dev/ttyUSBx，比看软链本身直观。

常见错误 #

写法 问题 改成
SYMLINK="ttydata" 覆盖别的软链 SYMLINK+="ttydata"
SYMLINK+="/dev/ttydata" 名字里不能带 /dev SYMLINK+="ttydata"
ATTR{idVendor} 匹配不到父设备属性 ATTRS{idVendor}
折成两行 udev 按行解析，两条残规则 一整行
只 reload 不重放事件，软链不出现 补 trigger

九、方案二：by-id 与 by-path #

系统已经给你建好了 #

不用写任何规则，插上设备就有：

bash
ls -l /dev/serial/by-id/
ls -l /dev/serial/by-path/

text
/dev/serial/by-id:
usb-Prolific_Technology_Inc._USB-Serial_Controller_A10K1234-if00-port0 -> ../../ttyUSB0

/dev/serial/by-path:
platform-ff540000.usb-usb-0:1.1:1.0-port0 -> ../../ttyUSB0

这两套链由发行版自带的规则生成（60-serial.rules 或类似文件）。换个发行版，目录名不变，链的具体命名格式会有出入，用之前先 ls 确认。

by-id：按设备身份 #

命名规则：usb-<厂商>_<型号>_<序列号>-if<接口号>-port<端口号>。核心是序列号 —— 每颗设备出厂烧死，唯一。

特征 说明
依据 设备序列号
稳定性 最高，换口换顺序都不变
弱点 插另一颗设备，链名就变了
适合 定点绑一颗特定设备

「插不同设备就变」这条要讲清楚。它不是不稳定，是太精确：认的是「这一颗」，不是「这个型号」。你换一颗同型号的备件上去，序列号变了，by-id 路径跟着变，硬编码在里面就找不到。

by-path：按物理位置 #

命名规则：platform-<控制器>-usb-0:<集线器端口链>:<接口号>-port<端口号>。读法是「挂在哪个控制器的哪条端口链上」。

特征 说明
依据 物理端口位置
稳定性 高，同一端口插什么都一样
弱点 换 USB 口就变；控制器换名（换内核、换设备树）也跟着变
适合 端口固定、设备会换的场景

板子上 USB 口是焊死的，设备是产线换的 —— 用 by-path。端口不动，插上什么设备，路径都一样。

两者对比 #

对比项 by-id by-path
认的是 设备身份（序列号） 物理位置（端口）
换 USB 口 路径不变 路径变
换设备 路径变 路径不变
依赖 设备必须上报序列号 依赖 sysfs 的端口拓扑
序列号缺失时 退化，链名里没有唯一段 不受影响

by-id 依赖序列号。有些廉价 USB 转串口芯片不上报序列号，或者所有批次的序列号相同 —— 那种设备用 by-id 是不安全的，同型号两颗插上会撞名。先确认：

bash
udevadm info --name=/dev/ttyUSB0 | grep ID_SERIAL
cat /sys/bus/usb/devices/3-1.1/serial

第二条命令没输出，就是没序列号。

目录的补充说明 #

/dev/serial/by-id 和 /dev/serial/by-path 只覆盖串口类。其他类型设备的软链在别处：

设备类型 软链目录
串口（ttyUSB、ttyACM） /dev/serial/by-id、/dev/serial/by-path
块设备（U 盘） /dev/disk/by-id、/dev/disk/by-path、/dev/disk/by-uuid
输入设备 /dev/input/by-id、/dev/input/by-path
摄像头 /dev/v4l/by-id、/dev/v4l/by-path

用 U 盘做数据盘时，/dev/disk/by-uuid/ 是最常用的一条 —— 和 by-id 一样认身份，但认的是文件系统 UUID，格式化才会变。挂载相关的细节看同目录《USB 设备的自动挂载》。

什么时候就该用这一套 #

条件 建议
只插一颗设备 直接用 by-id，不用写规则
设备有唯一序列号，会换口 by-id
端口固定，设备会换 by-path
同型号多颗，且序列号重复 只能 by-path 或按端口写 udev 规则
需要更短更好记的名字 写 SYMLINK+="ttydata" 指向真实节点

最后一行说明：by-id 的名字又长又难打，/dev/serial/by-id/usb-Prolific_Technology_Inc._USB-Serial_Controller_A10K1234-if00-port0 这串东西写进代码里，同事看一次骂一次。做法是先用 by-id 确认身份，再用 udev 规则建一个短名软链指过去。

十、方案三：程序里动态查找 #

前两套方案都依赖 udev 预先建链。还有一种做法：不在系统层固定，每次启动时由程序自己查「那颗设备现在叫什么」。

好处是上线快 —— 不碰 /etc，不重启，换个板子拷过去就能跑。代价是每个需要串口的程序都得带这段逻辑。

先摸清端口 #

第一次通电时，按第七章的办法确认哪个端口是自己要的数据口。认定 3-1.1 之后，后面每次通电都重新查「3-1.1 上现在挂的是 ttyUSB0 还是 ttyUSB1」，再建一个固定名字的软链（比如 ttydata）指过去。业务代码只认 /dev/ttydata。

素材里的实现是 bash 采集 + Python 正则解析，落地成一个 getUSB 目录。

文件 作用
cmd.sh 等设备就绪，把 ls -l /sys/class/tty/ttyUSB* 的结果存进 device_usb.txt
getUSB.py 读 device_usb.txt，正则捞出端口 3-1.1 对应的是哪个 ttyUSBx，写进 usbdev
usbdev 中间结果，一行设备名

采集脚本 #

bash
#!/bin/bash
# 等 ttyUSB 就绪，最多等 3 秒
a=0
while [[ ! -e /sys/class/tty/ttyUSB0 && ! -e /sys/class/tty/ttyUSB1 ]]; do
    sleep 0.01
    a=$((a + 1))
    [ $a -eq 300 ] && break
done

# 把当前的节点信息落盘
ls -l /sys/class/tty/ttyUSB0 /sys/class/tty/ttyUSB1 > ./device_usb.txt 2>/dev/null
if [ ! -s ./device_usb.txt ]; then
    echo "未检测到 ttyUSB0 或 ttyUSB1"
    exit 1
fi

# 删掉上一次留下的软链
[ -e /dev/ttydata ] && rm -f /dev/ttydata

# 调 Python 判断端口对应的设备名
./getUSB.py || exit 1
usbdev=$(cat ./usbdev)
echo "当前设备为: $usbdev"

ln -s "/dev/$usbdev" /dev/ttydata

素材原文的等待逻辑写成了两个 while 加 $a -ne 0 的跳出条件，第一个循环一旦超时，第二个会被立刻跳过，实际只等到一颗设备。上面这版合成一个条件。sudo sleep 这种写法也去掉了 —— sleep 不需要权限，ln -s 到 /dev 才需要。

解析脚本 #

python
#!/usr/bin/env python3
# coding:utf-8
import re

# 端口号：换成你自己的 3-1.1
PORT = r"3-1\.1"

with open("./device_usb.txt", "r", encoding="utf-8") as f:
    text = f.read()

# 端口后面的第一个 ttyUSBx 就是答案
m = re.search(PORT + r".+?(ttyUSB[0-9]+)", text)
if not m:
    print("没有找到端口 %s 上的设备" % PORT)
    raise SystemExit(1)

with open("./usbdev", "w", encoding="utf-8") as f:
    f.write(m.group(1) + "\n")

print("端口 %s -> %s" % (PORT, m.group(1)))

素材原文用 "rb" 打开、re.findall 取 output[0]。字节流配 Python 3 的 str 正则直接抛 TypeError；findall 取下标在没命中时抛 IndexError。上面这版按文本读、用 search 取第一处命中，两端都做了判空。

两处细节值得留意：

  • 正则里 3-1\.1 的点必须转义。不转义时 . 匹配任意字符，3-1x1 也能命中
  • .+? 用非贪婪。贪婪写法在同时有两颗设备时会跨过分隔符，抓成后面那颗的名字

挂上开机自启 #

getUSB 目录放到固定位置，比如 /opt/getUSB，然后加一条开机任务。现代发行版没有 /etc/rc.local 就用 systemd 单元：

bash
# /etc/systemd/system/getusb.service
[Unit]
Description=resolve ttyUSB to /dev/ttydata
After=dev-ttyUSB0.device dev-ttyUSB1.device

[Service]
Type=oneshot
WorkingDirectory=/opt/getUSB
ExecStart=/bin/bash /opt/getUSB/cmd.sh
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target

bash
sudo systemctl daemon-reload && sudo systemctl enable --now getusb.service
systemctl status getusb.service

开机后业务程序打开 /dev/ttydata，拿到的永远是 3-1.1 上那颗。

这套方案的硬伤：设备热插拔之后就失效了。软链是开机那一刻快照下来的，拔掉重插，内核重新发号，/dev/ttydata 还指着旧名字。真要应对热插拔，得让脚本盯着 udev 事件，或者干脆回到第八、第九套方案 —— 那也是它们更值得推荐的原因。

用 libudev 查 #

不想拼正则，可以直接问 udev。C 接口的骨架：

c
#include <libudev.h>
#include <stdio.h>

int main(void)
{
    struct udev *u = udev_new();
    struct udev_enumerate *en = udev_enumerate_new(u);

    udev_enumerate_add_match_subsystem(en, "tty");
    udev_enumerate_add_match_property(en, "ID_VENDOR_ID", "067b");
    udev_enumerate_add_match_property(en, "ID_MODEL_ID", "2303");
    udev_enumerate_scan_devices(en);

    struct udev_list_entry *devs = udev_enumerate_get_list_entry(en);
    struct udev_list_entry *e;
    udev_list_entry_foreach(e, devs) {
        struct udev_device *d = udev_device_new_from_syspath(u, udev_list_entry_get_name(e));
        printf("%s\n", udev_device_get_devnode(d));
        udev_device_unref(d);
    }

    udev_enumerate_unref(en);
    udev_unref(u);
    return 0;
}

bash
gcc find_tty.c -o find_tty $(pkg-config --cflags --libs libudev)

udev_enumerate_add_match_property 匹配的是 udevadm info 的 E: 行，ID_VENDOR_ID、ID_MODEL_ID、ID_SERIAL_SHORT 都能用。要按物理端口筛，把匹配键换成 udev_enumerate_add_match_sysattr(en, "idVendor", "067b") 之类的 sysfs 属性，或者遍历时用 udev_device_get_property_value(d, "ID_PATH") 比对路径。

Python 侧用 pyudev，同一套东西：

python
import pyudev

ctx = pyudev.Context()
for dev in ctx.list_devices(subsystem="tty", ID_VENDOR_ID="067b"):
    print(dev.device_node, dev.properties.get("ID_PATH"))

libusb 走的是另一条路，按 VID/PID 直接拿设备句柄，不碰 /dev：libusb_get_device_list 拿列表，逐个 libusb_get_device_descriptor 比 idVendor/idProduct，命中就是目标。要用端口链筛，libusb_get_port_numbers() 能拿到。这条路适合 USB 裸设备（USBCAN 这类），不适合 tty 串口 —— tty 已经绑了内核驱动，libusb 拿不到。完整读写流程看 03-libusb与无驱方案 那几篇。

十一、三种方案的取舍 #

对比项 udev 规则建软链 by-id / by-path 程序动态查找
写代码 不用 不用 要
改系统配置 要，/etc/udev/rules.d/ 不用 不用
名字长度 自己定，可以很短 长，带序列号或路径 自己定
热插拔 自动重建 自动重建 开机快照，拔插后失效
跨机器移植 要拷规则文件 直接可用 直接可用
同型号多颗 按序列号或端口区分 按序列号或端口区分 遍历时按端口筛
依赖 udev udev + 内核 sysfs 拓扑 运行时环境
权限能一起办 能，同一个规则文件 不能 不能
出错时排查看哪 udevadm test ls -l /dev/serial/ 脚本日志

选法可以按这三条走：

  • 设备固定、机器固定、长期跑 —— 写 udev 规则。一个文件同时解决权限和名字，配置在系统里，业务代码干净
  • 只想快点通、换个板子就用 —— 先看 /dev/serial/by-id 有没有现成的。有就直接用，一行代码都不用写
  • 设备会在运行中插拔，且软件不能改系统配置 —— 程序里查，但要监听 udev 事件重查，别只做开机快照

优先级建议：by-id/by-path 先看，能满足就不写规则；不能满足就写 udev 规则建短名；两者都不合适（比如容器里没有 udev、设备身份信息不全）再落到代码里查。

一条实践：规则文件和代码不要同时固定同一个名字。规则建了 /dev/ttydata，代码里又去扫 /sys 找 ttyUSBx，两套逻辑迟早打架。定一套。

十二、易错点速查 #

现象 根因 处理
Permission denied 打开 /dev/bus/usb/*/* 默认 root:root 0644，普通用户没写权限 写 udev 规则给 MODE/GROUP
chmod 之后重启又没了 /dev 是 devtmpfs，节点每次重建 别手工 chmod，改规则
chmod 当场管用、重插失效 重新枚举后设备号变了 同上，规则里按 VID/PID 匹配
规则写了但完全不生效 ATTR{idVendor}，该用 ATTRS 换复数键
规则文件没被读 后缀不是 .rules，或不在 /etc/udev/rules.d/ 挪位置、改后缀
改完规则没反应 只 --reload，没 trigger 补 sudo udevadm trigger
报语法错误 规则被编辑器折成两行，或行尾加了 # 注释 一条一行，注释独占行
vi/etc/udev/... 报 command not found 命令里 vi 和路径粘在一起 sudo vi /etc/udev/rules.d/xx.rules
组改对了权限还是不对 只写了 GROUP，没写 MODE 两个键都写
组员还是打不开 加组后没重新登录 重新登录，或 newgrp 起子 shell
MODE="0777" 与 0666 混用 字符设备用不到执行位 统一 0666
桌面能用、服务里不能用 TAG+="uaccess" 依赖 logind 的本地会话 服务场景改 GROUP + MODE
软链指向错的设备 ATTR 匹配到了父设备以外的层 逐层看 udevadm info -a
软链被自己抹掉 SYMLINK="x" 覆盖了列表 用 SYMLINK+="x"
by-id 路径每次都不一样 换了一颗设备，序列号变了 换设备就用 by-path；绑设备就用 by-id
by-id 里没有唯一段 芯片不上报序列号 用 by-path 或按端口写规则
换 USB 口后 by-path 变了 by-path 认的是物理位置 规则里改端口号，或改用 by-id
同型号两颗抢同一个 ttydata 规则只按 VID/PID 匹配 加 ATTRS{serial} 或 KERNELS
ttyUSB 数字越来越大 编号只增不减，一直到重启 别按数字硬编码，按端口或序列号
程序开机时打不开设备 服务启动早于设备枚举完成 服务加 After=dev-ttyUSB0.device，或启动前轮询

两条排查顺序，建议按这个走：

  1. 权限问题 —— lsusb 能列出来吗？能，就是权限；不能，往驱动层查。再 ls -l /dev/bus/usb/*/* 看当前权限位和属组对不对
  2. 名字问题 —— ls -l /sys/class/tty/ttyUSB* 拿端口号，udevadm info -a --name=/dev/ttyUSB0 拿属性，两边一对，规则该写哪个键就清楚了

最后还是那句话：权限和名字不是两件事。udev 匹配到设备，同一份规则里 MODE/GROUP 定权限，SYMLINK 定名字。写完规则记得 reload + trigger，然后拔一次插一次验证 —— 只验证一次不算数，要验证「换个顺序插，结果还对不对」。
