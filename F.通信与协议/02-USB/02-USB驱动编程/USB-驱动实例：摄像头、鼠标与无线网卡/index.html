本篇边界：讲三个具体设备的驱动差异。摄像头、鼠标、无线网卡，各属于什么 USB 类，套的是哪个上层框架，代码里有哪些绕不开的特殊处理。 通用骨架——usb_driver 怎么注册、probe/disconnect 时序、热插拔、URB 生命周期——在「编写一个 USB 驱动：从骨架到热插拔」里讲透了，这里只做对照。 本篇只做主机侧驱动。把开发板做成设备的那一侧，看「USB gadget 设备驱动解析」。CDC 类看「USB CDC 类驱动详解」和「USB linux NCM usbnet 驱动详解」。自定义 Bulk 看「如何实现自定义 USB Bulk 批量传输设备」。 三篇旧稿基于 2.4 到 2.6 早期内核，老 API 原样保留：video_device 还带 priv，input_dev 还能直接改 keybit，usb_device 还能摸 actconfig。旁边标出现代写法。看懂老代码的调用关系，比背新 API 管用。

三个设备插在同一台机器上，都是 USB，插上都能用。内核里跑的却是三套完全不同的代码。

摄像头变成 /dev/video0，你 read 或 mmap 它，拿到 YUV 帧。鼠标变成 /dev/input/event3 里流出的一串 input_event。网卡变成 wlan0 上的一个 net_device。

三条路从 USB 出发，出了 probe 就分岔，再无交集。USB 在这三个例子里只干一件事：搬字节。搬来的字节怎么解释、往哪个框架塞、对用户态暴露成什么，由上层子系统说了算。

设备 USB 类码 上层框架 注册的核心对象 主要传输 用户态接口
USB 摄像头 UVC（0x0e/0x10）或厂商私有（0xff） V4L2 video_device 等时 /dev/videoN
USB 鼠标 HID（3/1/2） 输入子系统 input_dev 中断 /dev/input/eventN
USB 无线网卡 厂商私有 网络子系统 net_device 批量 wlanN
USB 串口（对照） CDC-ACM（2/2/1） tty tty_struct 批量 + 中断 /dev/ttyACMn
U 盘（对照） Mass Storage（8/6/80） 块设备 gendisk 批量 /dev/sdX

一、三个实例的共同骨架 #

三个驱动，三个子系统。拆开看，USB 这一层的活是同一套：设备插上来，USB 核心读描述符，在全局驱动链表里找匹配项，匹配上就调 probe；拔掉调 disconnect；模块装卸走 module_init/module_exit。

先看注册。摄像头是老式写法，鼠标和网卡用字段初始化：

c
static struct usb_driver spca5xx_driver = {
    "spca5xx",
    spca5xx_probe,        /* 设备自我侦测 */
    spca5xx_disconnect,   /* 设备自我断开 */
    {NULL, NULL}
};

static struct usb_driver usb_mouse_driver = {
    .owner      = THIS_MODULE,
    .name       = "usbmouse",
    .probe      = usb_mouse_probe,
    .disconnect = usb_mouse_disconnect,
    .id_table   = usb_mouse_id_table,
};

static struct usb_driver rtusb_driver = {
    .name       = "rtusb",
    .probe      = ad_probe,
    .disconnect = ad_disconnect,
    .id_table   = ad_usb_ids,
};

差别只在名字和回调。这是 USB 层强制统一的，不是巧合。

1.1 模块装卸的固定形状 #

c
module_init(usb_spca5xx_init);

static int __init usb_spca5xx_init(void)
{
#ifdef CONFIG_PROC_FS
    proc_spca50x_create();                  /* 建立 PROC 设备文件 */
#endif
    if (usb_register(&spca5xx_driver) < 0)  /* 注册 USB 设备驱动 */
        return -1;
    info("spca5xx driver %s registered", version);
    return 0;
}

module_exit(usb_spca5xx_exit);

static void __exit usb_spca5xx_exit(void)
{
    usb_deregister(&spca5xx_driver);        /* 注销 USB 设备驱动 */
    info("driver spca5xx deregistered");
#ifdef CONFIG_PROC_FS
    proc_spca50x_destroy();                 /* 撤消 PROC 设备文件 */
#endif
}

鼠标少了 procfs 那两行，网卡的卸载绕一层（先 usb_rtusb_exit() 再 usb_deregister()），本质一样。usb_register 失败返回负值，usb_deregister 之后不能再碰任何设备资源，两条共同红线。

1.2 匹配：谁决定 probe 被调用 #

usb_register 成功，不代表 probe 会立刻跑。只有总线上出现匹配的设备，才会调 probe。

platform_bus_type 比驱动名和设备名是否相同；USB 总线比 id_table。

c
struct bus_type usb_bus_type = {
    .name    = "usb",
    .match   = usb_device_match,
    .hotplug = usb_hotplug,
    .suspend = usb_generic_suspend,
    .resume  = usb_generic_resume,
};

static int usb_device_match(struct device *dev, struct device_driver *drv)
{
    struct usb_interface *intf;
    struct usb_driver *usb_drv;
    const struct usb_device_id *id;

    if (drv == &usb_generic_driver)     /* 通用驱动不匹配任何设备 */
        return 0;

    intf    = to_usb_interface(dev);
    usb_drv = to_usb_driver(drv);
    id      = usb_match_id(intf, usb_drv->id_table);
    return id ? 1 : 0;
}

usb_match_id 逐条遍历 id_table，按 match_flags 里置位的字段比对，任意一项不符就 continue，全部对上返回该 id：

c
for (; id->idVendor || id->bDeviceClass || id->bInterfaceClass ||
       id->driver_info; id++) {
    if ((id->match_flags & USB_DEVICE_ID_MATCH_VENDOR) &&
        id->idVendor != le16_to_cpu(dev->descriptor.idVendor))
        continue;
    if ((id->match_flags & USB_DEVICE_ID_MATCH_INT_CLASS) &&
        (id->bInterfaceClass != intf->desc.bInterfaceClass))
        continue;
    /* PRODUCT / DEV_LO / DEV_HI / DEV_CLASS / DEV_SUBCLASS /
       DEV_PROTOCOL / INT_SUBCLASS / INT_PROTOCOL 结构完全相同 */
    return id;
}
return NULL;

循环的终止条件是「全零项」。所以 id_table 结尾那个 { } 不能省，省了会一路读越界。

驱动 匹配依据 意味着什么
鼠标 接口类 3 / 子类 1 / 协议 2 任何符合 HID 鼠标规范的设备都能驱动
摄像头 厂商号 + 产品号 只驱动白名单里的芯片
网卡 厂商号 + 产品号 一家厂商一个私有驱动

匹配粒度决定通用性。类级匹配写一份驱动管一片设备，厂商级匹配写一份只管几款。

1.3 接口私有数据 #

c
/* probe 里存 */
usb_set_intfdata(intf, mouse);

/* disconnect 里取，取完立刻清 */
mouse = usb_get_intfdata(intf);
usb_set_intfdata(intf, NULL);

usb_set_intfdata 干的事就是 intf->dev->driver_data = data。封装很薄，意义不小：它把「这块数据属于这个接口」写进了框架，而不是靠驱动自己找全局变量。

驱动 挂在 intf 上的私有结构 里面装了什么
摄像头 struct usb_spca50x 帧缓冲、URB、video_device、等待队列、传感器型号
鼠标 struct usb_mouse URB、DMA 缓冲、input_dev、名称、物理路径
网卡 struct priv_dev 802.11 通道表、skb 队列、锁、固件缓冲、EEPROM 副本

1.4 三个 probe 的签名差异 #

c
/* 摄像头（2.4 风格，参数是 usb_device） */
static void *spca5xx_probe(struct usb_device *dev, unsigned int ifnum,
                           const struct usb_device_id *id);

/* 鼠标（2.6 风格，参数是 usb_interface） */
static int usb_mouse_probe(struct usb_interface *intf,
                           const struct usb_device_id *id);

/* 网卡（2.6 风格） */
static int ad_probe(struct usb_interface *intf,
                    const struct usb_device_id *id);

老接口直接给 usb_device 和接口号，你得自己从 dev->actconfig->interface[ifnum] 翻接口描述符；新接口直接给 usb_interface，intf->cur_altsetting 就是当前设置。

区别不只在参数类型。老接口 probe 返回 void *，这个指针会被当作 disconnect 的第二个参数传回来：

c
static void spca5xx_disconnect(struct usb_device *dev, void *ptr)
{
    struct usb_spca50x *spca50x = (struct usb_spca50x *)ptr;

这条通道在新接口里被砍掉了，统一改成 intfdata。旧写法看着方便，但 void * 没有类型检查，probe 里任何一条错误路径忘了返回 NULL，disconnect 就拿野指针。

1.5 先钉住三条共识 #

  • 都要一个 id_table，决定自己管哪些设备
  • 都要在 probe 里把私有数据挂到 usb_interface，在 disconnect 里摘下并释放
  • 都在 probe 里做「USB 层资源预留」，在 disconnect 里按相反顺序撤销

反过来，三家在 probe 里干的事完全不同：摄像头分配 video_device 注册到 V4L2，鼠标填 input_dev 注册到输入子系统，网卡分配 net_device 注册到网络栈。USB 只是入场券，进门之后各走各的路。

二、USB 摄像头：UVC 与 V4L2 #

摄像头是所有 USB 外设里上层框架最重的一个。视频数据量大、格式多，还要 ioctl 控制曝光、亮度、分辨率。这些功能在 USB 层无处安放，只能交给 V4L2。

2.1 两条路线：标准 UVC 和厂商私有 #

情况 接口类码 内核里跑什么 谁维护
标准摄像头 0x0e（视频）、0x10（音视频） drivers/media/usb/uvc/ 的 uvcvideo 主线
早期私有摄像头 0xff（厂商自定义） spca5xx / gspca 部分 staging，多数被 gspca 收编

后一种就是本篇素材里的 spca5xx，它自己定义一套寄存器协议，靠 usb_control_msg 往芯片写值。

分岔点在 probe 第一句：UVC 驱动从设备读 UVC 描述符，读完就知道有几个 streaming 接口、支持哪些格式。私有驱动没有描述符可读，只能靠硬编码的厂商号 → 芯片型号 → 寄存器序列。对用户态来说两条路线没差别，/dev/video0 就是 /dev/video0，因为不管底层是谁，最终都要注册一个 video_device 到 V4L2 核心里。

2.2 V4L2 的入口：video_device #

c
struct video_device spca50x_template = {
    .owner    = THIS_MODULE,
    .name     = "SPCA5XX USB Camera",
    .type     = VID_TYPE_CAPTURE,
    .hardware = VID_HARDWARE_SPCA5XX,
    .fops     = &spca5xx_fops,
};

static struct file_operations spca5xx_fops = {
    .owner   = THIS_MODULE,
    .open    = spca5xx_open,      /* 打开 */
    .release = spca5xx_close,     /* 关闭 */
    .read    = spca5xx_read,      /* 读取 */
    .mmap    = spca5xx_mmap,      /* 内存映射 */
    .ioctl   = spca5xx_ioctl,     /* 信息获取 */
    .llseek  = no_llseek,         /* 定位未实现 */
};

五个字段各有用。owner 保住模块引用计数。name 是 v4l2-ctl --list-devices 显示的名字。type 声明这是纯采集设备——没有输出，所以没有 write。hardware 供旧版应用查询。fops 是系统调用挂接表。

没有 .write 是设备类型的直接体现，不是偷懒。no_llseek 也不能省——不给 .llseek 赋值会跑到默认实现上，lseek 返回一个看起来成功的位置，后面 read 就乱了。

现代内核里 type/hardware 被 device_caps 取代，.ioctl 被 .unlocked_ioctl 取代，priv 字段也没了。但「一个 video_device + 一张 file_operations」的结构没变。

2.3 为什么摄像头必须用等时传输 #

传输类型 带宽保证 是否重传 时间保证 适合什么
控制 有 有 有 配置、读写寄存器
中断 有 有 有（轮询） 小数据低延迟，鼠标键盘
批量 无 有 无 大数据可等，U 盘、网卡
等时 预留 无 有 实时音视频

视频帧不能等。30fps 就是 33ms 预算，晚到的数据毫无价值。但等时传输不重传，丢一个包就是丢一块数据，画面上留一条横线。这就是驱动里到处是 FRAME_DONE、FRAME_ERROR、FRAME_ABORTING 状态机的原因——它们全在处理「丢了怎么办」。

等时还有个硬约束：带宽要事先预留。所以摄像头必须先选好分辨率帧率把带宽占住，想换配置得先停流再来。

三、摄像头的探测与初始化 #

spca5xx_probe 干四件事：校验接口、分配设备结构、识别芯片、配置并注册。

3.1 校验与分配 #

c
static void *spca5xx_probe(struct usb_device *dev, unsigned int ifnum,
                           const struct usb_device_id *id)
{
    struct usb_interface_descriptor *interface;   /* USB 设备接口描述符 */
    struct usb_spca50x *spca50x;                  /* 物理设备数据结构 */
    int err_probe, i;

    /* 探测设备是不是可配置 */
    if (dev->descriptor.bNumConfigurations != 1)
        goto nodevice;
    if (ifnum > 0)
        goto nodevice;

    interface = &dev->actconfig->interface[ifnum].altsetting[0];

    MOD_INC_USE_COUNT;

    interface = &intf->altsetting[0].desc;
    if (interface->bInterfaceNumber > 0)
        goto nodevice;

    /* 分配物理地址空间 */
    if ((spca50x = kmalloc(sizeof(struct usb_spca50x), GFP_KERNEL)) == NULL) {
        err("couldn't kmalloc spca50x struct");
        goto error;
    }
    memset(spca50x, 0, sizeof(struct usb_spca50x));

    spca50x->dev   = dev;
    spca50x->iface = interface->bInterfaceNumber;

bNumConfigurations != 1 值得停一下。USB 协议允许设备有多套配置，同时只激活一套，有些设备拿它做「固件下载模式 / 正常工作模式」切换。这颗芯片不支持，驱动干脆在门口拦住。「只支持最简单的合法情况」在私有驱动里很常见——设备是自家造的，知道它只报一种配置，多判断没收益。ifnum > 0 同理。

spca50x->dev 和 spca50x->iface 是两笔账：记住哪个 USB 设备、哪个接口。disconnect 里要靠这两个值调 usb_driver_release_interface。

3.2 识别芯片：写进去读回来 #

c
    /* 具体物理设备查找，匹配厂商号、设备号 */
    if ((err_probe = spcaDetectCamera(spca50x)) < 0) {
        err(" Devices not found !! ");
        goto error;
    }
    PDEBUG(0, "Camera type %s ", Plist[spca50x->cameratype].name);

spcaDetectCamera 不只看 id_table。id_table 只保证厂商号产品号对得上，但同一颗芯片会配不同传感器、走不同接法。真正的识别靠写寄存器、读回来、比对：

c
    /* 给控制寄存器写值，读回返回值，以此判断具体的传感器型号 */
    if (!spca50x_configure(spca50x)) {
        spca50x->user     = 0;
        init_MUTEX(&spca50x->lock);          /* 信号量初始化 */
        init_MUTEX(&spca50x->buf_lock);
        spca50x->v4l_lock  = SPIN_LOCK_UNLOCKED;
        spca50x->buf_state = BUF_NOT_ALLOCATED;
    } else {
        err("Failed to configure camera");
        goto error;
    }

标准设备有 iSerialNumber、bcdDevice 能唯一标识。私有驱动面对的是同款板子换传感器，描述符完全一样，只能试探硬件。三把锁分工不同：

锁 类型 保护什么 能不能睡眠
lock mutex 整个设备操作序列（open/close/read/ioctl） 能
buf_lock mutex 帧缓冲区分配与释放 能
v4l_lock spinlock tasklet 和中断上下文里的帧状态 不能

3.3 等待队列与注册 video_device #

c
    for (i = 0; i < SPCA50X_NUMFRAMES; i++)
        init_waitqueue_head(&spca50x->frame[i].wq);   /* 初始化帧等待队列 */
    init_waitqueue_head(&spca50x->wq);                /* 初始化驱动等待队列 */

两套队列，两种等待。frame[i].wq 一个帧缓冲区一队列，等的是「这一帧采完了」，mmap 之后的应用睡在这上面，粒度细，避免所有读者一起被叫醒。wq 是全局的，等的是「四帧里任意一帧好了」，read 走这条路。这是纯软件抽象，跟 USB 无关。

probe 最后一段是整条链路的终点：

c
    /* Init video stuff */
    spca50x->vdev = video_device_alloc();   /* 设备控制块内存分配 */
    if (!spca50x->vdev)
        goto error;

    /* 系统调用的挂接，在此将驱动实现的系统调用挂到内核中 */
    memcpy(spca50x->vdev, &spca50x_template, sizeof(spca50x_template));

    video_set_drvdata(spca50x->vdev, spca50x);

    /* video 设备注册 */
    if (video_register_device(spca50x->vdev, VFL_TYPE_GRABBER, video_nr) < 0) {
        err("video_register_device failed");
        goto error;
    }

    spca50x->present = 1;
    if (spca50x->force_rgb)
        info("data format set to RGB");

    spca50x->task.sync    = 0;
    spca50x->task.routine = auto_bh;
    spca50x->task.data    = spca50x;
    spca50x->bh_requested = 0;

    MOD_DEC_USE_COUNT;
    return spca50x;         /* 返回数据结构 */

四步顺序不能换：video_device_alloc 分配 video_device 本身（不是私有结构）；memcpy 拷模板，浅拷贝，fops 指针共享同一张表；video_set_drvdata 把私有数据反向挂到 video_device 上，和 usb_set_intfdata 同一个思路——框架给你的句柄上要能找回自己的数据；video_register_device 注册，VFL_TYPE_GRABBER 表示采集设备，video_nr 传 -1 让内核自动分配。

present = 1 是给 open 看的，设备拔了但进程还没退出时能挡住新的打开请求。task 是 tasklet 描述符，routine 填 auto_bh——帧解码的延迟处理入口。等时回调在软中断上下文跑，那里不能睡眠也耗不起解码时间。

3.4 错误路径：按相反顺序回滚 #

c
error:      /* 错误处理 */
    if (spca50x->vdev) {
        if (spca50x->vdev->minor == -1)
            video_device_release(spca50x->vdev);
        else
            video_unregister_device(spca50x->vdev);
        spca50x->vdev = NULL;
    }
    if (spca50x) {
        kfree(spca50x);
        spca50x = NULL;
    }
    MOD_DEC_USE_COUNT;
    return NULL;

nodevice:
    return NULL;
}

vdev->minor == -1 是关键判断。video_device_alloc 之后、video_register_device 成功之前，minor 一直是 -1，这时只能 video_device_release 单纯释放内存。注册成功后 minor 被赋成真实编号，必须 video_unregister_device——它除了释放内存，还会把 /dev/videoN 从 devtmpfs 上摘掉。搞混了会怎样？注册成功后用 release，/dev/videoN 变成悬空设备节点，open 它会打到已释放的内存上。

另一处细节：MOD_DEC_USE_COUNT 在 error 里调，nodevice 里没调。因为 MOD_INC_USE_COUNT 在 nodevice 跳转点之后才执行，前面的检查失败时压根没加计数。两个出口分开，就是因为清理范围不同。

新内核里手工计数已废，改成 try_module_get/module_put。但「错误路径必须和分配顺序相反」这条一直没变。

3.5 disconnect：和 probe 对着干 #

c
static void spca5xx_disconnect(struct usb_device *dev, void *ptr)
{
    struct usb_spca50x *spca50x = (struct usb_spca50x *)ptr;
    int n;

    MOD_INC_USE_COUNT;
    if (!spca50x)
        return;

    down(&spca50x->lock);
    spca50x->present = 0;       /* 驱动卸载置 0 */

    /* 标示所有帧 ABORTING 状态 */
    for (n = 0; n < SPCA50X_NUMFRAMES; n++) {
        spca50x->frame[n].grabstate = FRAME_ABORTING;
        spca50x->curframe = -1;
    }

    /* 唤醒所有等待进程 */
    for (n = 0; n < SPCA50X_NUMFRAMES; n++) {
        if (waitqueue_active(&spca50x->frame[n].wq))
            wake_up_interruptible(&spca50x->frame[n].wq);
        if (waitqueue_active(&spca50x->wq))
            wake_up_interruptible(&spca50x->wq);
    }

    spca5xx_kill_isoc(spca50x);     /* 终止 URB 包的传输 */
    up(&spca50x->lock);

    /* 如果还有进程在使用，进程切换 */
    while (spca50x->user)
        schedule();

    down(&spca50x->lock);
    if (spca50x->vdev) {
        video_unregister_device(spca50x->vdev);   /* 注销 video 设备 */
        usb_driver_release_interface(&spca5xx_driver,
            &spca50x->dev->actconfig->interface[spca50x->iface]); /* 端口释放 */
        spca50x->dev = NULL;
    }
    up(&spca50x->lock);

#ifdef CONFIG_PROC_FS
    destroy_proc_spca50x_cam(spca50x);   /* 注销 PROC 文件 */
#endif

    if (spca50x && !spca50x->user) {     /* 释放内存空间 */
        spca5xx_dealloc(spca50x);
        kfree(spca50x);
        spca50x = NULL;
    }
    MOD_DEC_USE_COUNT;
}

顺序是门学问：先 present = 0，再标记帧状态，再 kill_isoc，最后才注销 video_device。

反过来会怎样？先 video_unregister_device，此刻还有进程卡在 read 里等帧。设备节点没了，进程不知道，继续在 wq 上睡，而 wq 永远没人唤醒——永久挂起。所以要先置状态再唤醒：FRAME_ABORTING 让等待条件从「等到 FRAME_DONE」变成「等到一个错误状态」，wait_event_interruptible 条件满足，返回错误码，进程退出。

while (spca50x->user) schedule(); 原始但管用：拔设备时如果还有进程开着，就原地让出 CPU 反复等，直到对方 close。逻辑上没错——物理设备已经没了，必须等使用者意识到。但 disconnect 里忙等是明确不推荐的，新内核用 usb_kill_urb 加引用计数等待取代。

四、摄像头的视频流采集 #

probe 只完成注册，一帧数据都没采。真正的采集从 open 开始。

4.1 open：拉起硬件 #

c
static int spca5xx_open(struct video_device *vdev, int flags)
{
    struct usb_spca50x *spca50x = video_get_drvdata(vdev);
    int err;

    MOD_INC_USE_COUNT;
    down(&spca50x->lock);

    err = -ENODEV;
    if (!spca50x->present)      /* 设备在不在，有没有驱动，忙不忙 */
        goto out;

    err = -EBUSY;
    if (spca50x->user)
        goto out;

    err = -ENOMEM;
    if (spca50x_alloc(spca50x))
        goto out;

    err = spca50x_init_source(spca50x);    /* 初始化传感器和解码模块 */
    if (err != 0) {
        up(&spca50x->lock);
        spca5xx_dealloc(spca50x);
        goto out2;
    }

    spca5xx_initDecoder(spca50x);       /* 解码模块初始化，采用 huffman 算法 */
    spca5xx_setFrameDecoder(spca50x);

    spca50x->user++;

    /* 初始化 URB 包，启动摄像头，采用同步传输的方式传送数据 */
    err = spca50x_init_isoc(spca50x);
    if (err) {
        spca50x->user--;
        spca5xx_kill_isoc(spca50x);
        up(&spca50x->lock);
        spca5xx_dealloc(spca50x);
        goto out2;
    }

    spca50x->brightness = spca50x_get_brghtness(spca50x) << 8;
    spca50x->whiteness  = 0;

out:
    up(&spca50x->lock);
out2:
    if (err)
        MOD_DEC_USE_COUNT;
    PDEBUG(2, err ? "Open failed" : "Open done");
    return err;
}

if (spca50x->user) goto out; 说明摄像头是独占设备。第二个进程 open 同一台摄像头拿到 -EBUSY，这是 V4L2 采集设备的常规约定：带宽被一个流占住了，没法再分。

spca50x_init_source 的注释是重点：对每一款 DSP 芯片的初始化都不一样，对中星微 301P 的初始化在子函数 zc3xx_init 里，实现方法是寄存器填值。 这句话点出了私有驱动的成本结构：一个芯片型号一份初始化表，加一款新芯片就得反汇编一份完整寄存器序列。

spca50x_init_isoc 是 USB 层的核心动作——构造等时 URB 并提交，摄像头在这里真正开始出数据。两条错误路径的回滚范围不同，必须精确对应它之前成功的步骤。

4.2 等时 URB 的组织 #

等时和批量在驱动写法上最大的差别：一个 URB 可以带多个包。

text
一个 URB
├── iso_frame_desc[0]  →  offset=0,     length=N  (收完才知道实际长度)
├── iso_frame_desc[1]  →  offset=N,     length=N
├── iso_frame_desc[2]  →  offset=2N,    length=N
│   ...
└── iso_frame_desc[k]  →  offset=k*N,   length=N

urb->number_of_packets        = k + 1
urb->transfer_buffer_length   = (k + 1) * N
urb->interval                 = 1        ← 每个服务间隔都发一次

每个 iso_frame_desc 描述一个包：在 transfer_buffer 里的偏移、要传多长、传完之后的实际长度和状态。批量 URB 是一次搬一整块，成功全成功；等时 URB 里 N 个包各自成败，驱动必须逐包检查 iso_frame_desc[i].status。一颗摄像头挂多个 URB 轮转：一个在传，驱动处理上一个已经回来的，这样才有时间解码。

4.3 数据到帧：tasklet 与软解码 #

等时回调在软中断上下文跑，不能睡，也做不了 Huffman 解码。所以驱动分两级。第一级是 URB 完成回调，只做搬运和状态更新：把 iso_frame_desc 里的数据接进帧缓冲区，满了就标记，然后调度 tasklet。

c
void outpict_do_tasklet(unsigned long ptr)
{
    int err;
    struct spca50x_frame *taskletframe = (struct spca50x_frame *)ptr;

    taskletframe->scanlength = taskletframe->highwater - taskletframe->data;

    PDEBUG(2, "Tasklet ask spcadecoder hdrwidth %d hdrheight %d method %d",
           taskletframe->hdrwidth, taskletframe->hdrheight, taskletframe->method);

    err = spca50x_outpicture(taskletframe);     /* 输出处理过的图片数据 */
    if (err != 0) {
        taskletframe->grabstate = FRAME_ERROR;
    } else {
        taskletframe->grabstate = FRAME_DONE;
    }

    /* 如果有进程等待，唤醒等待进程 */
    if (waitqueue_active(&taskletframe->wq))
        wake_up_interruptible(&taskletframe->wq);
}

scanlength = highwater - data 算出这一帧实际有多少字节。然后调解码器，成功置 FRAME_DONE，失败置 FRAME_ERROR，最后唤醒等在这一帧上的进程。三件事，一件不多。

解码在 spcadecode.c 里，把压缩流还原成 RGB：

text
输入格式（硬件压缩，取决于 DSP）
├── YYUV
├── YUVY
├── JPEG411
└── JPEG422
        ↓  spca50x_outpicture() → spcadecode.c
输出：RGB

关键事实：解压缩算法的实现依赖于压缩格式，而压缩格式归根结底依赖于 DSP 芯片里的硬件压缩算法。 解码表不是通用算法，是逆向出来的。这解释了私有摄像头驱动为什么难写——USB 那一层几百行就够，真正的工作量在「厂商用哪颗 DSP、它吐什么格式、怎么还原成图像」。

4.4 read：从内核缓冲拷到用户空间 #

c
static long spca5xx_read(struct video_device *dev, char *buf,
                         unsigned long count, int noblock)
{
    struct usb_spca50x *spca50x = video_get_drvdata(dev);
    int i, frmx = -1, rc;
    volatile struct spca50x_frame *frame;

    if (down_interruptible(&spca50x->lock))     /* 获取信号量 */
        return -EINTR;

    if (!dev || !buf) {                         /* 判断设备情况 */
        up(&spca50x->lock);
        return -EFAULT;
    }
    if (!spca50x->dev || !spca50x->streaming) {
        up(&spca50x->lock);
        return -EIO;
    }

    /* 在指定的队列上睡眠，直到四帧里有一帧 DONE */
    if ((rc = wait_event_interruptible(spca50x->wq,
            spca50x->frame[0].grabstate == FRAME_DONE ||
            spca50x->frame[1].grabstate == FRAME_DONE ||
            spca50x->frame[2].grabstate == FRAME_DONE ||
            spca50x->frame[3].grabstate == FRAME_DONE))) {
        up(&spca50x->lock);
        return rc;
    }

    /* 当数据到来，找出标识数据已到的那一帧 */
    for (i = 0; i < SPCA50X_NUMFRAMES; i++)
        if (spca50x->frame[i].grabstate == FRAME_DONE)
            frmx = i;

    if (frmx < 0) {
        PDEBUG(2, "Couldnt find a frame ready to be read.");
        up(&spca50x->lock);
        return -EFAULT;
    }

    frame = &spca50x->frame[frmx];
    if (count > frame->scanlength)
        count = frame->scanlength;

    /* 实现用户空间和内核空间的数据拷贝 */
    if ((i = copy_to_user(buf, frame->data, count))) {
        PDEBUG(2, "Copy failed! %d bytes not copied", i);
        up(&spca50x->lock);
        return -EFAULT;
    }

    frame->grabstate = FRAME_READY;     /* 标识数据已空 */
    up(&spca50x->lock);
    return count;                       /* 返回拷贝的数据数 */
}

四个 FRAME_DONE 的或写死在条件里，说明 SPCA50X_NUMFRAMES 就是 4。不灵活，但省一次循环。

down_interruptible 之后马上 wait_event_interruptible 睡下去——这个写法有问题。持着互斥锁去睡眠，别的进程连 ioctl 都进不来。正确做法是先释放锁再等，等到之后重新加锁。老代码里这类问题不少，读的时候要能分辨。

copy_to_user 返回未拷贝的字节数，0 才是全成功。frame->grabstate = FRAME_READY 把帧还回去——采集是环形复用，四帧轮转，一帧被读走就标 READY，等下一轮填充。count > frame->scanlength 时截断到实际长度，用户传一个巨大的 count 也不会越界。

4.5 mmap：零拷贝 #

read 每次都要 copy_to_user，一帧几十万字节，拷贝不便宜。所以 V4L2 采集更常用 mmap。

c
static int spca5xx_mmap(struct video_device *dev, const char *adr,
                        unsigned long size)
{
    unsigned long start = (unsigned long)adr;
    struct usb_spca50x *spca50x = dev->priv;
    unsigned long page, pos;

    if (spca50x->dev == NULL)
        return -EIO;

    if (size > (((SPCA50X_NUMFRAMES * MAX_DATA_SIZE) + PAGE_SIZE - 1) &
                ~(PAGE_SIZE - 1)))
        return -EINVAL;

    if (down_interruptible(&spca50x->lock))     /* 获取信号量 */
        return -EINTR;

    pos = (unsigned long)spca50x->fbuf;

    while (size > 0) {                          /* 循环实现内存映射 */
        page = kvirt_to_pa(pos);
        /* 实现内存映射 */
        if (remap_page_range(start, page, PAGE_SIZE, PAGE_SHARED)) {
            up(&spca50x->lock);
            return -EAGAIN;
        }
        start += PAGE_SIZE;
        pos   += PAGE_SIZE;
        if (size > PAGE_SIZE)
            size -= PAGE_SIZE;
        else
            size = 0;
    }

    up(&spca50x->lock);                         /* 释放信号量 */
    return 0;
}

容量上限：SPCA50X_NUMFRAMES * MAX_DATA_SIZE 向上取整到页边界，用户想映射更大直接 -EINVAL。不设这个上限，用户能拿到驱动分配范围外的物理页。

kvirt_to_pa：内核虚拟地址转物理地址。remap_page_range 要物理地址，是老接口的约束。现代内核用 remap_pfn_range，参数是 PFN 不是物理地址。

逐页循环：remap_page_range 一次只映射一页，必须每轮把 start 和 pos 各推进一页。这是最容易写错的地方——只调一次，用户只拿到 4KB。

PAGE_SHARED：映射属性，用户态可读写。给成只读，用户态写就触发 SIGSEGV。

mmap 之后用户态拿到的是驱动里 fbuf 那块内存的直接视图，帧填进去用户就能看见。代价是同步责任转移了：驱动不能随便复用已被映射的帧，否则用户正在读的数据会被覆盖。所以 FRAME_READY 之后才能重新填。

4.6 ioctl 与 close #

c
static int spca5xx_ioctl(struct inode *inode, struct file *file,
                         unsigned int cmd, unsigned long arg)
{
    struct video_device *vdev = file->private_data;
    struct usb_spca50x *spca50x = vdev->priv;
    int rc;

    if (down_interruptible(&spca50x->lock))     /* 获取信号量 */
        return -EINTR;

    /* 将信息传送到用户进程，关键函数是 spca5xx_do_ioctl */
    rc = video_usercopy(inode, file, cmd, arg, spca5xx_do_ioctl);

    up(&spca50x->lock);
    return rc;
}

video_usercopy 是 V4L2 核心提供的辅助函数。它干两件麻烦事：按 cmd 里的方向标志把用户态 arg 拷进来或拷出去；处理 _IOC_SIZE，让子函数拿到一个已在内核空间的参数副本。不用它，每个 ioctl 命令都得自己写 copy_from_user/copy_to_user，几十个命令写下来必然出错。

spca5xx_do_ioctl 本体素材里没展开，注释说明了思想：通过 copy_to_user(arg, &b, sizeof(struct video_capability)) 把设备信息传给用户进程。 素材原话是「本驱动为了支持多种芯片，实现程序过于烦琐」——一个 VIDIOCGCAP 要填几十个字段，每个字段在不同芯片上的取值都不同。

c
static void spca5xx_close(struct video_device *vdev)
{
    struct usb_spca50x *spca50x = vdev->priv;
    int i;

    down(&spca50x->lock);       /* 参数设置 */

    spca50x->user--;
    spca50x->curframe = -1;

    if (spca50x->present) {     /* present：是否有驱动加载 */
        spca50x_stop_isoc(spca50x);         /* 停止摄像头工作和数据包送 */
        spcaCameraShutDown(spca50x);        /* 关闭摄像头 */
        for (i = 0; i < SPCA50X_NUMFRAMES; i++) {   /* 唤醒所有等待进程 */
            if (waitqueue_active(&spca50x->frame[i].wq))
                wake_up_interruptible(&spca50x->frame[i].wq);
        }
        if (waitqueue_active(&spca50x->wq))
            wake_up_interruptible(&spca50x->wq);
    }

    up(&spca50x->lock);
    spca5xx_dealloc(spca50x);       /* 回收内存空间 */
    MOD_DEC_USE_COUNT;
}

顺序是先停流、再关硬件、再唤醒、最后释放内存。spca50x_stop_isoc 必须调——等时 URB 提交之后会一直跑，不 kill 就持续往已释放的缓冲区写数据。spcaCameraShutDown 给芯片下关电或待机命令，省电，也避免下次打开时状态残留。if (spca50x->present) 让「设备已拔但进程还在」也能走完释放路径。

4.7 寄存器读写：回到 USB 层 #

前面所有寄存器操作，最终都落到两个函数上：

c
static int spca50x_reg_write(struct usb_device *dev, __u16 reg,
                             __u16 index, __u16 value)
{
    int rc;

    /* 通过 USB CORE 提供的接口函数设置寄存器的值 */
    rc = usb_control_msg(dev,
                         usb_sndctrlpipe(dev, 0),
                         reg,
                         USB_TYPE_VENDOR | USB_RECIP_DEVICE,
                         value, index, NULL, 0, TimeOut);

    PDEBUG(5, "reg write: 0x%02X,0x%02X:0x%02X, 0x%x",
           reg, index, value, rc);
    if (rc < 0)
        err("reg write: error %d", rc);
    return rc;
}
参数 值 含义
dev 设备 发给谁
pipe usb_sndctrlpipe(dev, 0) 控制端点 0，发送方向
request reg 请求码，这里复用成寄存器地址
requesttype USB_TYPE_VENDOR | USB_RECIP_DEVICE 厂商自定义请求，目标是设备
value value 覆盖 wValue 字段
index index 覆盖 wIndex 字段
data/size/timeout NULL, 0, TimeOut 没有数据阶段，只有设置阶段

USB_TYPE_VENDOR 是关键：它告诉 USB 核心这不是标准请求，别按 USB 规范解释，直接透传给设备。整个 bRequest 空间（0x00–0xFF）都归厂商用，配合 wValue 和 wIndex 两个 16 位字段，能拼出足够丰富的寄存器寻址。

usb_sndctrlpipe(dev, 0) 的 0 是端点号。控制端点永远是 0，USB 规范强制。NULL, 0 表示没有数据阶段——这就是「写寄存器」和「写数据块」的区别。读寄存器换 usb_rcvctrlpipe 和 USB_DIR_IN 即可。

素材里提到，USB 核心向上层提供的这类接口还包括 usb_control_msg、usb_sndctrlpipe、usb_rcvctrlpipe 等一批函数，私有驱动的所有配置动作都从这几个出去。

五、USB 鼠标：HID 协议 #

鼠标是三个例子里代码最短的。这不代表它简单。复杂度不在驱动行数上，而在「为什么它这么短」——HID 规范把设备行为标准化了，内核只写一份驱动就能管住市面上绝大多数鼠标。

5.1 HID 的类码约定 #

HID 规范给鼠标定死了三个描述符字段：

text
接口类     bInterfaceClass    = 0x03   （HID）
接口子类   bInterfaceSubClass = 0x01   （Boot Interface）
接口协议   bInterfaceProtocol = 0x02   （Mouse）

这三字节就是鼠标的身份证。驱动的 id_table 只要写这三个数，就能匹配全部符合规范的鼠标：

c
static struct usb_device_id usb_mouse_id_table[] = {
    { USB_INTERFACE_INFO(3, 1, 2) },
    { }     /* Terminating entry */
};

#define USB_INTERFACE_INFO(cl, sc, pr) \
    .match_flags        = USB_DEVICE_ID_MATCH_INT_INFO, \
    .bInterfaceClass    = (cl), \
    .bInterfaceSubClass = (sc), \
    .bInterfaceProtocol = (pr)

#define USB_DEVICE_ID_MATCH_INT_INFO \
    (USB_DEVICE_ID_MATCH_INT_CLASS | \
     USB_DEVICE_ID_MATCH_INT_SUBCLASS | \
     USB_DEVICE_ID_MATCH_INT_PROTOCOL)

match_flags 是「要比哪些字段」的位图，没置位的字段不参与比较。这就是同一个 usb_match_id 能同时支持「按厂商号匹配」和「按类码匹配」的原因。{ } 空项不能省——循环在第一个全零项上停下来，没有终止项会一路读越界。

除了 HID，走类码匹配的还有 Mass Storage、Printer、Audio。好处一样：设备厂商可以直接利用标准的驱动程序，不用自带光盘。反过来说，摄像头那个 spca5xx 走厂商号匹配，就意味着每款芯片都得配一份驱动，这就是通用性的代价。

5.2 probe 前半段：三项硬性检查 #

c
static int usb_mouse_probe(struct usb_interface *intf,
                           const struct usb_device_id *id)
{
    struct usb_device *dev = interface_to_usbdev(intf);
    struct usb_host_interface *interface;
    struct usb_endpoint_descriptor *endpoint;
    struct usb_mouse *mouse;
    int pipe, maxp;
    char path[64];

    interface = intf->cur_altsetting;

    if (interface->desc.bNumEndpoints != 1)
        return -ENODEV;

    /* 端点 0 描述符，此处的 0 表示中断端点 */
    endpoint = &interface->endpoint[0].desc;

    if (!(endpoint->bEndpointAddress & 0x80))
        return -ENODEV;

    if ((endpoint->bmAttributes & 3) != 3)   /* 判断是否是中断类型 */
        return -ENODEV;

第一项：端点数量必须是 1，HID 鼠标只需要一个中断 IN 端点。

这里要把端点 0 讲清楚。bNumEndpoints 不包含端点 0。端点 0 是任何 USB 设备都有的控制端点，专门用于控制传输。正因为如此，即使设备没做任何配置，主机也能通过端点 0 跟它通信——不知道其它端点，但至少知道它有一个控制端点。

第二项：方向必须是 IN。bEndpointAddress 的 bit7 是方向位，0 表示 OUT，1 表示 IN，都是对主机而言：OUT 是主机到设备，IN 是设备到主机。

c
#define USB_DIR_OUT  0      /* to device */
#define USB_DIR_IN   0x80   /* to host */

鼠标把数据报给主机，必然是 IN。这一位不对，说明这端点不送鼠标事件。

第三项：传输类型必须是中断。bmAttributes 的 bit1 和 bit0 合起来叫 Transfer Type：

值 类型 用在哪
00 控制 配置、枚举、读写寄存器
01 等时 音视频流
10 批量 U 盘、网卡
11 中断 鼠标、键盘

三项错一项就返回 -ENODEV。驱动不试图兼容非标设备——真遇到非标的，让通用 usbhid 去处理。

5.3 中断端点：构造 pipe 与数据布局 #

c
    /* 构造中断端点的输入 pipe */
    pipe = usb_rcvintpipe(dev, endpoint->bEndpointAddress);
    maxp = usb_maxpacket(dev, pipe, usb_pipeout(pipe));

usb_rcvintpipe 把「设备 + 端点号 + 方向 + 传输类型」编码成一个整数，后面所有 URB 操作都用它，不再单独传端点号。usb_maxpacket 从 pipe 里反解出端点，再读 wMaxPacketSize：

c
int usb_maxpacket(struct usb_device *udev, int pipe, int is_out)
{
    struct usb_host_endpoint *ep;
    unsigned epnum = usb_pipeendpoint(pipe);

    if (is_out) {
        WARN_ON(usb_pipein(pipe));
        ep = udev->ep_out[epnum];
    } else {
        WARN_ON(usb_pipeout(pipe));
        ep = udev->ep_in[epnum];
    }
    if (!ep)
        return 0;

    return le16_to_cpu(ep->desc.wMaxPacketSize);
}

usb_pipeendpoint(pipe) 取的是 pipe 里存着的端点号。pipe 是个整数，里面塞了设备号、端点号、方向、传输类型，端点号占 bit15–bit18 一带，一共 16 个端点位置。usb_pipeout(pipe) 是查询方向，传 0 表示「我不确定，你帮我判断」。

鼠标的 maxp 一般是 4。四字节数据包，逐字节含义固定：

text
byte 0:  bit0 BTN_LEFT   左键
         bit1 BTN_RIGHT  右键
         bit2 BTN_MIDDLE 中键
         bit3 BTN_SIDE   侧键
         bit4 BTN_EXTRA  扩展键
byte 1:  REL_X          水平位移（有符号）
byte 2:  REL_Y          垂直位移（有符号）
byte 3:  REL_WHEEL      滚轮（有符号）

这是 Boot Protocol 的标准布局。真正的 HID 设备会用 Report Descriptor 描述自己的格式，不止 4 字节。这份驱动只处理 boot 布局，够用就行。

5.4 分配与 input_dev 装配 #

c
    if (!(mouse = kmalloc(sizeof(struct usb_mouse), GFP_KERNEL)))
        return -ENOMEM;
    memset(mouse, 0, sizeof(struct usb_mouse));

    mouse->data = usb_buffer_alloc(dev, 8, SLAB_ATOMIC, &mouse->data_dma);
    if (!mouse->data) {
        kfree(mouse);
        return -ENOMEM;
    }

    mouse->irq = usb_alloc_urb(0, GFP_KERNEL);
    if (!mouse->irq) {
        usb_buffer_free(dev, 8, mouse->data, mouse->data_dma);
        kfree(mouse);
        return -ENODEV;
    }

    mouse->usbdev = dev;

usb_buffer_alloc 分配「能被 DMA 访问」的内存，同时给出两个指针：mouse->data 是 CPU 视角的虚拟地址，mouse->data_dma 是设备视角的 DMA 地址。两者指向同一块物理内存，只是地址表示不同。usb_alloc_urb(0, ...) 的第一个参数是等时包数，非等时传 0。错误路径已经把前面分配的吐回去了。

c
    /* 设置 input 系统响应按键和 REL（相对结果）事件 */
    mouse->dev.evbit[0] = BIT(EV_KEY) | BIT(EV_REL);

    mouse->dev.keybit[LONG(BTN_MOUSE)] = BIT(BTN_LEFT) | BIT(BTN_RIGHT) |
                                         BIT(BTN_MIDDLE);
    mouse->dev.relbit[0] = BIT(REL_X) | BIT(REL_Y);

    mouse->dev.keybit[LONG(BTN_MOUSE)] |= BIT(BTN_SIDE) | BIT(BTN_EXTRA);
    mouse->dev.relbit[0] |= BIT(REL_WHEEL);

这段是 input_dev 的声明式配置，也是它和 video_device 最大的不同。file_operations 是「你实现，内核调」——被动的。input_dev 的位图是「你声明，内核替你转发」——主动的。

位图 声明什么 举例
evbit 能产生哪几类事件 EV_KEY、EV_REL
keybit 能产生哪些按键码 BTN_LEFT、BTN_RIGHT
relbit 能产生哪些相对位移码 REL_X、REL_Y、REL_WHEEL

LONG(BTN_MOUSE) 把按键码换算成 keybit 数组下标——按键码空间很大，一个 long 装不下。BIT(n) 是 1UL << n，赋值就是在位图里把对应位置 1。声明了才能报告：驱动后面调 input_report_key(dev, BTN_LEFT, ...)，如果 keybit 里没置这一位，内核会把它当无效事件丢掉。

c
    mouse->dev.private = mouse;
    mouse->dev.open    = usb_mouse_open;
    mouse->dev.close   = usb_mouse_close;

    usb_make_path(dev, path, 64);
    sprintf(mouse->phys, "%s/input0", path);

    mouse->dev.name = mouse->name;
    mouse->dev.phys = mouse->phys;

    usb_to_input_id(dev, &mouse->dev.id);

    mouse->dev.dev = &intf->dev;

    if (dev->manufacturer)
        strcat(mouse->name, dev->manufacturer);
    if (dev->product)
        sprintf(mouse->name, "%s %s", mouse->name, dev->product);
    if (!strlen(mouse->name))
        sprintf(mouse->name, "USB HIDBP Mouse %04x:%04x",
                mouse->dev.id.vendor, mouse->dev.id.product);

private 是回调上下文。open/close 是输入子系统回调，不是 USB 回调——用户态打开 /dev/input/eventN 时触发。usb_make_path 生成形如 usb-0000:00:1d.0-1 的物理路径，加 /input0 后缀就是 phys，热插拔后排到不同 event 节点也能认回同一台设备。

usb_to_input_id 把 USB 描述符翻译成 input_id：

c
void usb_to_input_id(const struct usb_device *dev, struct input_id *id)
{
    id->bustype = BUS_USB;
    id->vendor  = le16_to_cpu(dev->descriptor.idVendor);
    id->product = le16_to_cpu(dev->descriptor.idProduct);
    id->version = le16_to_cpu(dev->descriptor.bcdDevice);
}

命名是三级降级：厂商名加产品名 → 有哪个用哪个 → 都没有就用 ID 拼。兜底那句不能少——很多杂牌鼠标不提供 iManufacturer 和 iProduct 字符串描述符。

5.5 填 URB：间隔从哪来 #

c
    usb_fill_int_urb(mouse->irq, dev, pipe, mouse->data,
                     (maxp > 8 ? 8 : maxp),
                     usb_mouse_irq, mouse, endpoint->bInterval);

七个参数，最后一个 endpoint->bInterval 是重点。

c
static inline void usb_fill_int_urb(struct urb *urb, struct usb_device *dev,
                                    unsigned int pipe, void *transfer_buffer,
                                    int buffer_length, usb_complete_t complete,
                                    void *context, int interval)
{
    spin_lock_init(&urb->lock);
    urb->dev      = dev;
    urb->pipe     = pipe;
    urb->transfer_buffer = transfer_buffer;  /* 不用 DMA 时的缓冲指针 */
    urb->transfer_buffer_length = buffer_length;
    urb->complete = complete;
    urb->context  = context;

    if (dev->speed == USB_SPEED_HIGH)
        urb->interval = 1 << (interval - 1);
    else
        urb->interval = interval;

    urb->start_frame = -1;
}

urb->interval 的语义随速度变化，这个 1 << (interval - 1) 是最容易踩的坑：

设备速度 bInterval 单位 换算方式 bInterval = 8 实际间隔
低速 / 全速 帧（1ms） 直接用 8ms
高速 微帧指数 1 << (n-1) 128 微帧 = 128µs

高速设备里 bInterval 是指数，不是线性，这是 USB 2.0 的规定：高速中断端点的轮询周期范围是 1–16 个微帧。urb->start_frame = -1 告诉 USB 核心「别按帧号排，尽快发」。

c
    mouse->irq->transfer_dma = mouse->data_dma;
    mouse->irq->transfer_flags |= URB_NO_TRANSFER_DMA_MAP;

两个 DMA 标志别搞混：

c
#define URB_NO_TRANSFER_DMA_MAP 0x0004   /* urb->transfer_dma valid on submit */
#define URB_NO_SETUP_DMA_MAP    0x0008   /* urb->setup_dma valid on submit */

URB_NO_SETUP_DMA_MAP 专为控制传输准备——只有控制传输有 setup 阶段，才需要 setup packet。URB_NO_TRANSFER_DMA_MAP 是通用数据传输标志。transfer_buffer 用于各种传输方式里真正的数据搬运；setup_packet 只在控制传输里发 setup 包，控制传输除 setup 阶段之外还有数据阶段，那一阶段仍然靠 transfer_buffer。

设了 URB_NO_TRANSFER_DMA_MAP，就必须给 urb->transfer_dma 赋值。漏了会怎样？USB 核心以为 transfer_dma 非零，直接拿 0 当地址去 DMA，轻则传输失败，重则写坏内存。

usb_fill_int_urb 只构造不提交，提交在 open 里。probe 结尾：

c
    input_register_device(&mouse->dev);       /* 向 input 系统注册 input 设备 */
    printk(KERN_INFO "input: %s on %s\n", mouse->name, path);

    usb_set_intfdata(intf, mouse);
    return 0;
}

input_register_device 之后 /dev/input/eventN 就出现了，但此时 URB 还没提交，一个字节的鼠标数据都还没有。

六、鼠标的中断传输与输入子系统 #

6.1 不是中断，是主机定期来问 #

USB 设备没有主动通知主机的能力。整个总线是主从结构：只有主机能发起传输，设备只能应答。设备想说「我这儿有数据了」，办不到，它不能拉一根中断线。

所以「中断传输」这名字有误导性。真实含义是：

text
主机                        设备
 |-- IN token (端点3) ------>|
 |                           |  准备好数据就回
 |<----- DATA0 (4 bytes) ----|
 |-- ACK ------------------->|
 |      （等待 bInterval）    |
 |-- IN token (端点3) ------>|
 ...

主机按 bInterval 指定的周期主动发 IN token 来问。有数据就收，没数据设备回 NAK，主机等下一轮。对设备来说这等价于「被定期采一次」，对主机来说这就是轮询。好处是带宽有保证、延迟可预测，代价是轮询开销跟设备数量成正比——一个 1ms 间隔的鼠标每秒占 1000 次传输机会。

6.2 bInterval 配大了会怎样 #

这是可调参数里最立竿见影的一个。假设把鼠标端点 bInterval 从 4ms 改成 32ms：

text
bInterval = 4  →  每秒 250 次采样
bInterval = 8  →  每秒 125 次采样
bInterval = 16 →  每秒 62 次采样
bInterval = 32 →  每秒 31 次采样

31Hz 意味着你一秒钟最多能看到 31 个位置点。快速移动时鼠标物理上走了一条曲线，主机只拿到 31 个离散点，光标在屏幕上跳跃前进。手感差异非常直接：4ms 顺滑，32ms 拖影。这不是心理作用，是采样丢失。

反过来也不是越小越好。低速/全速设备最小 1ms（一帧）。高速能到 125µs，但一个 125µs 的鼠标每秒占 8000 次总线机会，接四五只这样的设备，总线上别的设备就没带宽了。选值是权衡：延迟、带宽、设备数。

bInterval 由设备固件决定，正常情况下驱动不该改。usb_fill_int_urb 把它原样传进 urb->interval，就是「尊重设备声明」。驱动确实能改 urb->interval 来省带宽，但改完必须重新 usb_submit_urb，运行中改不生效。

6.3 open 与 urb 回调 #

c
static int usb_mouse_open(struct input_dev *dev)
{
    struct usb_mouse *mouse = dev->private;

    mouse->irq->dev = mouse->usbdev;

    if (usb_submit_urb(mouse->irq, GFP_KERNEL))
        return -EIO;

    return 0;
}

mouse->irq->dev = mouse->usbdev 为什么还要设一次？因为 URB 可以复用，usb_submit_urb 成功后 urb->dev 会被核心清空，下次提交前必须重设。GFP_KERNEL 是因为 open 跑在进程上下文，可以睡；回调里重新提交就必须用 GFP_ATOMIC。

注意这句注释：此处是成功递交给 USB 核心以后就返回，而不是等到从设备取得鼠标数据。 这是异步模型的全部要害。open 返回 0 只代表「请求排进队列了」。

c
static void usb_mouse_irq(struct urb *urb, struct pt_regs *regs)
{
    struct usb_mouse *mouse = urb->context;   /* usb_fill_int_urb 里赋过 */
    signed char *data = mouse->data;
    struct input_dev *dev = &mouse->dev;
    int status;

    switch (urb->status) {
    case 0:             /* success */
        break;
    case -ECONNRESET:   /* unlink */
    case -ENOENT:
    case -ESHUTDOWN:
        return;
    /* -EPIPE: should clear the halt */
    default:            /* error */
        goto resubmit;
    }

    input_regs(dev, regs);

    input_report_key(dev, BTN_LEFT,   data[0] & 0x01);
    input_report_key(dev, BTN_RIGHT,  data[0] & 0x02);
    input_report_key(dev, BTN_MIDDLE, data[0] & 0x04);
    input_report_key(dev, BTN_SIDE,   data[0] & 0x08);
    input_report_key(dev, BTN_EXTRA,  data[0] & 0x10);

    input_report_rel(dev, REL_X,     data[1]);
    input_report_rel(dev, REL_Y,     data[2]);
    input_report_rel(dev, REL_WHEEL, data[3]);

    input_sync(dev);

resubmit:
    status = usb_submit_urb(urb, SLAB_ATOMIC);   /* 重新递交 urb */
    if (status)
        err("can't resubmit intr, %s-%s/input0, status %d",
            mouse->usbdev->bus->bus_name,
            mouse->usbdev->devpath, status);
}

状态码分类是第一件要紧事：

urb->status 含义 处理
0 成功 正常解析数据
-ECONNRESET URB 被 unlink 直接返回，不重提
-ENOENT URB 已被 unlink 直接返回
-ESHUTDOWN 设备已断开 直接返回
-EPIPE 端点 stall 应 clear halt 后重提
其它 临时错误 goto resubmit 重提

前三个必须返回。设备已经拔了或 URB 已被撤销，这时候 usb_submit_urb 必然失败，重提只是刷日志，严重时会死循环。

数据解析：data[0] & 0x01 取 bit0 就是左键，五个键全用位与，一次数据报把五个键的状态全刷新。input_report_key 的第三个参数非 0 表示按下，0 表示释放，所以位与结果直接传进去就行。

data[1]、data[2] 声明成 signed char，因为位移有符号，取值 -128 到 127。

input_sync(dev) 必须调。输入子系统的模型是「一次原子报告」：先攒一堆事件，最后一次 sync 提交。少了它，用户态会读到半个报文——拿到 X 位移但拿不到同一批的 Y 位移。

最后 resubmit。中断传输是持续轮询，一次完成就再提交，永不停歇。这是中断 URB 和批量 URB 的根本差别。用 SLAB_ATOMIC（等价 GFP_ATOMIC），因为回调在软中断上下文，不能睡。

6.4 数据从哪来，拔掉怎么办 #

回调里所有 input_report_* 攒起来，input_sync 一提交，输入子系统就把这批事件写进 event 设备的队列。用户态 read 出来的是 struct input_event 数组：

c
struct input_event {
    struct timeval time;    /* 时间戳 */
    __u16 type;             /* 事件类型：EV_KEY / EV_REL / EV_SYN */
    __u16 code;             /* 事件码：BTN_LEFT / REL_X */
    __s32 value;            /* 值：1/0 或位移量 */
};

这就是输入子系统的价值：不管底下是 USB 鼠标、PS/2 鼠标、蓝牙鼠标还是触摸板模拟的鼠标，用户态看到的都是这个结构。

usb_mouse_disconnect 素材里没给代码，但每一步都是前面几步的逆操作：

text
input_unregister_device(&mouse->dev)   先摘 input，用户态不能再打开
usb_kill_urb(mouse->irq)               保证回调不再被调用
usb_free_urb(mouse->irq)               释放 URB
usb_buffer_free(...)                   释放 DMA 缓冲
kfree(mouse)                           释放私有结构

usb_kill_urb 必须在 usb_free_urb 之前。URB 已经提交出去，回调随时会进来，不先 kill 就释放 URB，回调里 urb->context 是个野指针。

6.5 中断传输的适用边界 #

特征 适合中断传输 适合批量传输
数据量 小（几字节到 64 字节） 大（任意）
延迟要求 高（ms 级） 低（可等）
带宽是否保证 保证（预留） 不保证（竞争）
丢数据容忍度 低 低（有重传）
典型设备 鼠标、键盘、手柄 U 盘、网卡、打印机

鼠标选中断传输，因为它三个条件全占：数据小（4 字节）、延迟要求高（手感）、带宽要保证（不能被 U 盘挤掉）。网卡选批量，因为它量大（一个以太网帧 1500 字节），而且能等——批量不保证带宽，但保证不丢，出错了会重传。

看懂鼠标为什么用中断，就明白网卡为什么不用。

七、USB 无线网卡：私有驱动路线 #

无线网卡是三个例子里最特殊的一个。摄像头和鼠标都有标准类框架兜底，无线网卡没有。

7.1 为什么没有标准类 #

USB 规范给 HID、Mass Storage、CDC、Audio、Video 都定义了类码。无线网卡没有。IEEE 802.11 定义的是空口上的帧格式，不管 USB 这层怎么封装。USB-IF 后来搞了个 WLAN 类（0xe0），但市面上绝大多数 USB 无线网卡不遵守。

结果是每款芯片一套私有协议。驱动必须自己做三件标准框架本该做的事：

标准框架会帮你做的 私有驱动必须自己做
定义设备能力描述 硬编码芯片能力表（通道、速率）
提供配置接口 自己实现 ndo_do_ioctl / cfg80211_ops
处理上层协议适配 自己拼 802.11 帧头，自己管重传

这就是这类驱动代码量动辄上万行、几乎进不了内核主线的原因。

驱动 芯片 位置 说明
rtl8188eu Realtek RTL8188EU staging（曾长期） 代码质量不达标，长期在 staging 维护
zd1211rw ZyDAS ZD1211 主线 少数被接受的完整实现
rt2800usb Ralink RT28xx 主线 走 mac80211 框架，质量好
rtl8xxxu Realtek 多款 主线 逐步替代厂商私有驱动
厂商包 Realtek 多款 树外 厂商自己发布，需自行编译

规律很清楚：走 mac80211 框架、代码规范的能进主线；自己造一套 802.11 栈的，只能蹲 staging 或树外。素材里的驱动属于后一类——它定义了 ieee80211_ops，但私有结构里塞满 priv_rate、priv_channel、privdev_rx_status 这类东西，说明它在自己管通道和速率表，没有完全依赖 mac80211 的抽象。

7.2 硬件构成 #

text
USB 接口
   ↓
MAC 控制器  ← 核心部件
   ↓
基带处理 + ADC/DAC
   ↓
调制解调器
   ↓
功率放大器 → 收发器
   ↓
天线

MAC 控制器是核心。它负责从主机读数据并发送出去，或者接收数据并发送给主机，还管通道选择、速率选择、加密解密。

固件存储区存 MAC 控制器要跑的微码。固件是编译过的可执行代码，一般由芯片执行。很多 USB 网卡插上时是个「裸芯片」，驱动得先把固件灌进去它才开始工作——这就是 fw_name 字段存在的原因。

帧缓存是数据中转站。EEPROM 不一定有，它一般存设备参数，比如 MAC 地址、型号。驱动把 EEPROM 内容一次性读进内存副本，好处是读参数不用每次走 USB，也防止错误代码把 EEPROM 里的数据冲掉。基带处理加 ADC/DAC 是数模转换部分。收发器内部有功率放大器，把弱信号增强，同时负责滤波。天线负责把数据发出去，作用是让传输距离更远。

7.3 端点回顾：四种传输 #

端点类型 传什么 谁用 方向
控制端点 控制信息，如配置设备 所有设备（端点 0） 双向
中断端点 中断信息（主机周期查询） 鼠标键盘 一般单向
批量端点 批量信息，大量数据 U 盘、网卡 单向
等时端点 实时性高的信息 音视频 单向

端点像一栋大楼的传达室。每个楼层一个，要访问 5 楼 10 号房间，就向 5 号端点发起对话并提供偏移量。控制端点一般双向，其它端点一般单向——方向站在主机角度说。

USB 无线网卡用批量端点传数据，发送和接收函数都走批量端点。理由和鼠标正好相反：一个以太网帧 1500 字节，用中断传输要拆成几十个包，每次都占一个预留时隙，把总线压死。批量传输不预留带宽，有空就传。

素材里那句「USB 总线没有中断资源」值得单拎出来。PCI 网卡有真实的中断线，数据到了拉中断线，CPU 进中断处理。USB 网卡没有这条路，只能靠 URB 回调。

7.4 端点描述符 #

c
struct usb_endpoint_descriptor {
    __u8  bLength;
    __u8  bDescriptorType;
    __u8  bEndpointAddress;
    __u8  bmAttributes;
    __le16 wMaxPacketSize;
    __u8  bInterval;
    __u8  bRefresh;
    __u8  bSynchAddress;
} __attribute__((packed));

bLength 是本结构有多少字节，后两个成员 bRefresh/bSynchAddress 是给音频设备用的。bDescriptorType 是描述符类型，端点在内核里是 0x05。

bEndpointAddress 含端点号和方向。bit0–bit3 是端点号，所以一个 USB 设备最多 16 个端点。bit7 是方向：1 输入（读设备），0 输出（写设备）。

bmAttributes 是端点类型。wMaxPacketSize 是这个端点一次最多传多少字节，要传的数据大于这个数就得分多次。bInterval 是端点希望主机轮询自己的间隔——注意是「希望」，具体还得看主机怎么做。

__attribute__((packed)) 要求成员之间不留内存对齐空隙。比如相邻两个成员是 u8 和 u16，一般情况下 u8 后面要空一个字节才开始 u16，加了 packed 就不留。设备里的数据结构一般没有内存对齐要求，所以内核里很多要直接映射设备内存的结构都带这个属性。忘了它会怎样？读出来的 wMaxPacketSize 高低字节错位，值完全不对。

7.5 私有数据结构 #

probe 里要通过 usb_set_intfdata 挂一个私有结构。这个结构怎么分配，是无线网卡特有的：

c
ieee80211_hw *ieee80211_alloc_hw(size_t priv_data_len,
                                 const struct ieee80211_ops *ops)

第一个参数是私有数据长度，第二个参数是函数表指针——驱动把实现的所有函数通过这张表交给 802.11 层。这个函数一次分配两块内存：802.11 层需要的内存结构，加上驱动自己的私有数据。返回 struct ieee80211_hw *，它的 priv 成员指向私有数据区。这样设计的原因：hw 和 priv 内存连续，container_of 一算就到，不用额外指针。现代内核里它换成了 ieee80211_alloc_hw_nm，思路一样。

c
struct priv_dev {
    unsigned long flags;
    struct usb_device *udev;
    struct usb_interface *intf;
    struct ieee80211_hw *hw;
    loff_t savep;
    char fw_name[64];
    char path[64];
    u8 *eeprom;
    struct ieee80211_supported_band bands[IEEE80211_NUM_BANDS];
    enum ieee80211_band curr_band;
    spinlock_t list_lock;
    struct mutex list_op, rw_lock;
    int timeout;
    struct list_head cfmg_list[30];
    u8 bulk[BULKSIZE];
    struct config_msg *msg_fun[10];   /* record config_msg() position */
    unsigned char *skb_data, *skb_tail, *rx_skb_data, *rx_skb_tail;
    struct data_queue *rx, *tx, *beacon;
    struct prob_desc probdesc;
    struct priv_rate *privrate;
    struct priv_channel *privchannel;
    struct privdev_rx_status rxstatus;
    struct priv_intf privintf;
    u32 parameter[PRIV_PARAMETER_SIZE];
    int sparameter[PRIV_PARAMETER_SIZE];
    struct pstack ps;
};

分几类看。

指向上层的：udev、intf、hw，从私有数据能反向找到 USB 设备和 802.11 层结构。文件相关的：savep 记录读参数文件时的偏移量，path 是参数文件路径和文件名。固件相关的：fw_name 存固件名字，运行时按它 request_firmware。EEPROM 副本：eeprom 指向一块和设备 EEPROM 等大的内存，读参数从内存读，速度快也不会误写。频带信息：bands 和 curr_band 记录设备所在的频带、通道和速率列表。

三把锁分工明确：

锁 类型 用途 获取失败的行为
list_lock spinlock 短时间保护链表 不睡眠，循环查询
list_op mutex 长时间操作 阻塞在锁的链表上
rw_lock mutex 长时间读写保护 阻塞在锁的链表上

timeout 是和设备通信的定时器时间。驱动框架想支持多个设备，所以值从参数文件读，不写死。

cfmg_list[30] 是参数链链头指针数组。struct list_head 是内核常用双向链表：

c
struct list_head {
    struct list_head *next, *prev;
};

用法是把 list_head 嵌进宿主结构，只要知道 list_head 的地址，就能算出宿主结构的地址：

c
#define list_entry(ptr, type, member) \
    container_of(ptr, type, member)

ptr 是宿主里 list_head 成员的地址，type 是宿主类型，member 是该成员的名字。本文里如果知道某个 list_head 指针 head，那么 config_msg 的地址就是 list_entry(head, struct config_msg, list)。这个手法贯穿整个内核。

bulk[BULKSIZE] 是批量缓冲，msg_fun[10] 记录 config_msg() 的位置，skb_data/skb_tail/rx_skb_data/rx_skb_tail 是收发 skb 的游标。rx/tx/beacon 是三个队列——信标帧队列单独分出来，因为 AP 模式下它要按固定节奏发。

7.6 通道与速率 #

c
struct ieee80211_channel {
    enum ieee80211_band band;
    u16 center_freq;
    u16 hw_value;
    u32 flags;
    int max_antenna_gain;
    int max_power;
    bool beacon_found;
    u32 orig_flags;
    int orig_mag, orig_mpwr;
};

band 是频带（2.4G / 5G），center_freq 是中心频率，hw_value 是硬件寄存器值——驱动要用它去配置芯片。max_antenna_gain 和 max_power 是法规限制，不同国家允许的发射功率不同，这两个值来自 EEPROM 加国家的组合。flags 标通道能力，比如「允许主动扫描」「禁用」，beacon_found 记录这个通道上扫到过信标没有。

有线网卡没有这个概念。一根网线插上去，速率是自协商出来的，驱动不用管。无线的每一个通道都要先扫、再选、再驻留，全是驱动和 802.11 栈的事。

7.7 操作函数集与注册 #

c
struct ieee80211_ops {
    int  (*tx)(struct ieee80211_hw *hw, struct sk_buff *skb);
    int  (*start)(struct ieee80211_hw *hw);
    void (*stop)(struct ieee80211_hw *hw);
    int  (*add_interface)(struct ieee80211_hw *hw,
                          struct ieee80211_if_init_conf *conf);
    void (*remove_interface)(struct ieee80211_hw *hw,
                             struct ieee80211_if_init_conf *conf);
    int  (*config)(struct ieee80211_hw *hw, u32 changed);
    void (*bss_info_changed)(struct ieee80211_hw *hw,
                             struct ieee80211_vif *vif,
                             struct ieee80211_bss_conf *info,
                             u32 changed);
};

这里只列了部分。驱动不必把结构里所有函数指针都实现，按设备情况挑。tx 是发送，start 是开始，config 是配置，stop 是停止。必须实现的几个填完，驱动就算写好了。

tx 的签名值得看：参数是一个 sk_buff *，返回 int。这和 net_device_ops 里的 ndo_start_xmit 是同构的——上一层构造好一个完整的帧，交给驱动发出去。区别是 tx 收到的是已经是 802.11 格式的帧，驱动只管塞进 USB URB，不用自己拼帧头。

注册只要三行：

c
static struct usb_driver rtusb_driver = {
    .name       = "rtusb",
    .probe      = rtusb_probe,
    .disconnect = rtusb_disconnect,
    .id_table   = rtusb_usb_ids,
};

module_usb_driver(rtusb_driver);

module_usb_driver 展开成 module_init + module_exit 加两行注册/注销，省了样板代码。

probe 里的注册流程，素材写得很清楚：

text
probe(intf, id)
   ↓
分配 hw = ieee80211_alloc_hw(sizeof(priv), &ops)
   ↓
私有数据 = hw->priv，填 udev / intf / hw
   ↓
usb_set_intfdata(intf, priv)
   ↓ 返回 0 表示支持该设备

usb_set_intfdata 的作用就是把接口和它的驱动要用到的数据结构关联起来，成功后返回 0；不支持该设备返回 -ENODEV。probe 的第一个参数 usb_interface 验证了一个接口对应一个驱动这条规则。本文涉及的设备都是单接口的，所以没太区分接口和设备的差别。

素材还专门写了设备插入到找到驱动的两步：第一步，获取设备信息。 设备插到 USB 接口上，主机控制器检测到有设备插入，内核分配一个 struct usb_device 代表它，挂到全局 USB 设备链上，这期间主机通过 0 号端点得知设备信息，并知道了厂家号和产品号。第二步，找到匹配的驱动。 内核到全局 USB 驱动链上查找，看哪个驱动程序支持的设备列表里有这个厂家号和产品号，找到后设备就和驱动匹配上了。

理解这两步，就明白为什么 usb_register 成功之后 probe 不一定立刻跑——得等真有一个匹配的设备插进来。

7.8 设备断开与模块卸载 #

disconnect 是 probe 的逆过程，主要工作是释放驱动已分配的系统资源：

text
disconnect(usb_interface *intf)
   ↓
priv = usb_get_intfdata(intf)
   ↓
usb_set_intfdata(intf, NULL)     先把关联断掉
   ↓
停止 URB、注销 net_device、释放 skb 队列、释放 hw

先取、再清、最后释放。清空这一步不能省——disconnect 返回后内核还会访问 intfdata，留着野指针就是隐患。

模块卸载对应模块加载。module_exit 先调 usb_rtusb_exit() 卸载网卡驱动，再调 usb_deregister(&rtusb_driver) 注销设备。顺序是先停驱动内部动作，再摘 USB 注册；反过来会在注销过程中还有活动 URB，容易撞上 -ESHUTDOWN。

八、网卡的数据收发包 #

收包和发包，是网卡驱动的全部实质工作。其余都是配置和状态管理。

8.1 收包：open 里先埋一个读请求 #

素材里点明了关键差异：与 PCI、PCMCIA 等无线网卡不同，USB 总线没有中断资源。因此 USB 无线网卡的数据接收不通过中断实现，而是在 open 函数里通过主机主动查询是否有数据需要读取。

所以 open 里必须向 USB 核心递交一个读请求 URB，让网络数据到来时主机能收到。

c
usb_fill_bulk_urb(dev->rx_urb,                  /* 构造读请求的 urb */
                  dev->udev,
                  usb_rcvbulkpipe(dev->udev, 6),/* 指定读的端点 */
                  dev->rx_skb->data,
                  512,                          /* count */
                  rx_complete,                  /* 读请求的回调函数 */
                  dev);
if (result = usb_submit_urb(dev->urb, GFP_KERNEL))
    ...

端点 6 是硬编码的。这颗芯片的接收批量端点固定是 6，发送固定是 2。端点号由硬件设计决定，描述符里也读得到，但驱动选择直接写死。

数据直接落进 skb 是个值得注意的设计。dev->rx_skb->data 是 skb 的数据区指针，URB 把 USB 数据包直接写进去，省了一次内存拷贝。代价是 skb 必须在 URB 提交之前准备好，而且 URB 完成之前不能动它，所以接收路径要准备多个 skb 轮转。usb_submit_urb 用 GFP_KERNEL——open 跑在进程上下文，可以睡。

8.2 读请求完成：转给网络栈 #

text
rx_complete(urb)
   ↓
检查 urb->status，非 0 走错误路径
   ↓
从 urb->actual_length 得到实际收到多少字节
   ↓
skb_put(skb, len) 把数据区长度推上去
   ↓
skb->protocol = eth_type_trans(skb, netdev)
   ↓
netif_rx(skb)      交给网络子系统
   ↓
重新 usb_submit_urb 等下一包

netif_rx 之后 skb 的所有权就交给网络栈了，驱动不能再碰它，所以下一次提交 URB 必须用新的 skb，不能复用刚交出去的那个。

eth_type_trans 干的事是解析以太网帧头、取协议号、把 skb 的 data 指针挪到帧头之后。有些驱动自己做这一步，但用现成函数更保险。

素材原话：读请求完成时，read_bulk_callback 函数将被内核调用，它构造一个 sk_buff 数据结构来描述数据包，并调用 netif_rx 把数据包传给网络子系统，从而完成一次数据的接收过程。 USB 那一层只负责把字节搬进内存，剩下全是网络栈的活。

8.3 发包：从 hard_start_xmit 开始 #

当网络子系统要发送一个数据时，上层协议会构造一个 sk_buff 描述数据包，并调用驱动注册实现的 hard_start_xmit 发送。

这里有个关键前提：该函数被调用时，网络子系统持有 xmit_lock 自旋锁，因此驱动不必考虑设备写操作的同步问题。 也就是说，hard_start_xmit 天然是串行的，不用自己加锁——这条保证省掉了发送路径上最难写的一块。

c
usb_fill_bulk_urb(dev->tx_urb,                  /* 构造写请求的 urb */
                  dev->udev,
                  usb_sndbulkpipe(dev->udev, 2),/* 指定写端点 */
                  skb->data,
                  512,                          /* count */
                  write_bulk_callback,          /* 写请求的回调函数 */
                  dev);
if (result = usb_submit_urb(dev->tx_urb, GFP_ATOMIC)) {
    /* 提交失败的处理 */
}

和收包对着看，四处对称：

项 收包 发包
端点号 6 2
pipe usb_rcvbulkpipe usb_sndbulkpipe
回调 rx_complete write_bulk_callback
提交标志 GFP_KERNEL GFP_ATOMIC

GFP_ATOMIC 这一处差别最重要。 hard_start_xmit 被网络子系统在持有自旋锁的情况下调用，处于软中断上下文。这种上下文不能睡眠，所以只能用 GFP_ATOMIC。写成 GFP_KERNEL 会在持锁上下文里触发调度，轻则 CPU 卡住警告，重则死锁。

512 这个长度也值得看一眼。以太网帧最大 1500 字节，这里一次只传 512，意味着一个完整帧要拆成三次。每传完一段，回调里接着传下一段，直到整帧发完才 dev_kfree_skb。512 是这颗芯片的批量端点能力上限。

8.4 完成回调与 ioctl #

写请求完成时，write_bulk_callback 回调函数被调用，根据发送情况更新统计数据。

text
netdev->stats.tx_packets++     成功发出的包数
netdev->stats.tx_bytes += len  成功发出的字节数
netdev->stats.tx_errors++      发送错误数
netdev->stats.tx_dropped++     丢弃的包数

这些值最终出现在 ifconfig 和 /proc/net/dev 里，用户排查「为什么网卡发不出去」时看的就是这几个数。write_bulk_callback 还有一件必做的事：释放 skb。发送路径上的 skb 是网络栈给你的，发完必须还回去，否则内存一路漏。

Linux 中要让网卡正常工作需要配置 IP 地址、SSID、工作频段、工作模式，这些控制操作都是通过 ifconfig 和 iwconfig 调用驱动实现的 IOCTL 函数。 驱动通过 IOCTL 为应用提供诸如 IO 内存地址读写、配置空间寄存器读写、数据成员读写等能力。

c
static int rtxxx_ioctl(struct net_device *net_dev, struct ifreq *ifr, int cmd)

三个参数：网络设备、ifreq 结构（承载参数和结果）、命令码。ifreq 是个联合体，装 IP 地址、接口名、MTU、MAC 地址等各种东西，按 cmd 决定用哪一支。

代次 入口 典型命令
老（Wireless Extensions） ndo_do_ioctl SIOCSIWESSID、SIOCGIWRATE、SIOCSIWFREQ
新（cfg80211/nl80211） netlink NL80211_CMD_CONNECT、NL80211_CMD_SET_CHANNEL

素材里写的是旧接口。iwconfig 属于 Wireless Extensions，现在已被 iw 和 nl80211 取代。但 ifconfig 那部分没变——IP 地址、MTU、MAC 地址仍然走 ioctl，走的是标准的 SIOCSIFADDR 这类命令，任何网卡都得实现。所以现代无线网卡驱动两边都沾。

8.5 net_device 的完整生命周期 #

text
module_init
   ↓
usb_register_driver(&rtusb_driver)
   ↓
probe(intf, id)                          设备插入
   ├─ ieee80211_alloc_hw(sizeof(priv), &ops)
   ├─ 填 priv: udev / intf / hw
   ├─ usb_set_intfdata(intf, priv)
   ├─ 读 EEPROM → priv->eeprom
   ├─ request_firmware(priv->fw_name) → 灌固件

   ├─ register_netdev(netdev)             ← wlan0 出现

   ↓

   ↓

USB 类码的作用是让内核知道「该把这个设备交给哪个子系统」。 0x03 就找输入子系统，0x08 就走 SCSI，0xff 内核不知道，只能让厂商驱动自己处理。这就是私有类码驱动必须自带上层框架适配的原因——要么自己实现一套（像 spca5xx 直连 V4L2），要么在框架里塞私有逻辑（像网卡自带速率表）。

9.4 谁在主动 #

设备 谁发起数据传输 触发方式
摄像头 主机 open 提交等时 URB，之后持续收
鼠标 主机 open 提交中断 URB，按 bInterval 反复问
网卡（收） 主机 open 提交批量 URB，收到即重提
网卡（发） 网络栈 ndo_start_xmit 被调用

 * usb_mouse_test.c
 * by lht
 */
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <linux/input.h>

int main(void)
{
    int fd, i, count;
    struct input_event ev_mouse[2];

    fd = open("/dev/input/event3", O_RDWR);
    if (fd < 0) {
        printf("fd open failed\n");
        exit(0);
    }
    printf("\nmouse opened, fd=%d\n", fd);

    while (1) {
        count = read(fd, ev_mouse, sizeof(struct input_event));

        for (i = 0; i < (int)count / sizeof(struct input_event); i++) {
            if (EV_REL == ev_mouse[i].type || EV_KEY == ev_mouse[i].type) {
                printf("type=%d time:%ld.%d code:%d value:%d\n",
                       ev_mouse[i].type, ev_mouse[i].time.tv_sec,
                       ev_mouse[i].time.tv_usec, ev_mouse[i].code,
                       ev_mouse[i].value);
            }
        }
    }

    close(fd);
    return 0;
}

time:1712345678.123456 type:2 code:0 value:3      ← REL_X 向右 3
type=2
time:1712345678.123456 type:2 code:1 value:-2     ← REL_Y 向上 2

time:1712345678.123456 type:1 code:272 value:1    ← BTN_LEFT 按下

type 是事件类型，2 是 EV_REL（相对位移），1 是 EV_KEY（按键），0 是 EV_SYN（同步标记）。code 是事件码，0 是 REL_X，1 是 REL_Y，8 是 REL_WHEEL；按键码 272 是 BTN_LEFT，273 是 BTN_RIGHT，274 是 BTN_MIDDLE。value 对 EV_REL 是位移量（有符号），对 EV_KEY 是 1（按下）或 0（释放）。

素材原程序里有个 bug：read 的长度是 sizeof(struct input_event)，每次只读一个事件，但缓冲区声明成 [2] 数组、循环按 count / sizeof(struct input_event) 迭代。count 永远等于一个结构大小，循环永远只跑一次。能工作，但高频移动时系统调用太多。把缓冲区开大就行：struct input_event ev[64]; count = read(fd, ev, sizeof(ev));，再按结构大小切片。

12.1 匹配与端点 #

现象 原因 排查
usb_register 成功，probe 不跑 id_table 不匹配 lsusb -v 对描述符，逐字节比

错误 后果 正确做法

down() 持锁去 wait_event 其它进程全卡住 先释放再等

等时那条最容易忽略：批量 URB 只有一个总状态，等时 URB 有 N 个分包状态，每个都得看。

7 usb_kill_urb 在 usb_free_urb 之前 野指针回调
8 框架对象先注册后使用，先注销后释放 use-after-free
9 disconnect 里先清 intfdata 再释放 野指针
10 释放顺序严格镜像获取顺序 各种泄漏和崩溃

第十条是纲，其余九条是目。

三个驱动看完，能带走的最硬的一条不是某个 API 怎么调，而是这个：USB 那一层只有一种写法，上层框架有无数种写法。搞懂你要接的是哪个框架，比背 USB 协议有用得多。

摄像头接 V4L2，就得懂 video_device 和帧状态机。鼠标接输入子系统，就得懂能力位图和事件上报。网卡接网络栈，就得懂 sk_buff 和 net_device_ops。

USB 只是插头。真正决定这个驱动长什么样的，是插头后面那个框架。
