本篇边界。讲什么：从零定义一个厂商自定义（bDeviceClass = 0xFF）的 USB 设备，只用批量端点收发，描述符、固件、主机程序、Windows 驱动一条链走完。不讲什么：HID、MSC、CDC 这些标准类内部怎么工作，那些在同目录另外几篇里。跨篇指路：标准类的驱动框架看《编写 USB 驱动》，gadget 侧（板子当设备）的框架看《USB gadget 设备驱动解析》，CDC 的通信接口加数据接口结构看 CDC 类那一篇。本篇干的事，是把 CDC 的壳拆掉，换成自己的协议。

一、为什么需要自定义设备 #

先说结论，免得你被标题带偏。自定义 USB 设备不是发明一套新 USB。枚举流程没变，描述符结构没变，端点编号规则没变，四种传输方式也没变。你改的只有一处：设备类代码填 0xFF，告诉主机「我没有标准类，别拿系统自带的类驱动来配我，协议是我自己定的」。

剩下的活，全落在批量端点上。一帧数据怎么切、帧头几个字节、序号怎么编、校验放哪儿、谁先发，这些都由你定。主机侧的程序也得你自己写，因为没有任何系统组件认识你这份协议。

所以自定义设备的本质是：换协议，不换物理层。

标准类在什么时候够用，心里要有数。

标准类 类代码 主机侧长什么样 边界在哪
HID 0x03 系统自带驱动，免安装 只走中断传输，最快 1ms 一次，适合小数据
CDC 0x02 一个串口设备（COM / ttyACM） 背了通信接口那套 AT 命令语义的包袱
MSC 0x08 一个 U 盘 只认文件系统语义，传的是块，不是你的帧
Audio 0x01 一个声卡 格式被类规范钉死
Vendor 0xFF 什么都没有，等你补 全部自己写

什么时候非自定义不可，四条判据。

数据格式是你自己的。一帧里有帧头、通道号、序号、CRC、尾巴，标准类里没有哪个能装下这种结构。

吞吐超出标准类的舒适区。要连续灌几十 KB 到几 MB，中断传输那 1ms 一次的节奏会拖住你。

端点的数量和方向要自己排。两路 bulk IN 加一路 bulk OUT 并行跑，标准类不会给你这种自由度。

时序由你控制。什么时候回 NAK、什么时候用短包收尾、什么时候挂起接收，这些得你自己说了算。

代价要提前看清。描述符自己写，固件自己写，Windows 驱动自己搞，主机程序自己写。这四条里最耗时间的不是固件，是 Windows 驱动那一环，因为设备管理器会直接甩给你一个黄色感叹号。

有个误解得先拆掉：有人以为填了 0xFF 就等于免驱。正好反了。0xFF 恰恰意味着系统里没有现成的类驱动能匹配你，Windows 找不到驱动，设备枚举成功但驱动绑不上。Linux 那边有 usbfs 兜着，看起来像免驱，Windows 这边必须自己补一个。这一点后面第九、第十章各讲一遍。

再说批量传输的取舍，这是全篇的地基：保证正确，不保证时间。

数据一定会到。硬件层有 CRC16 校验，有握手包，出错了自动重传，主机侧收到的一定是完整的一包。

但没有固定速率，也没有延迟上限。批量传输只使用总线上「剩下的」带宽，总线忙的时候你就等着。设备端没数据可给时回 NAK，主机会一遍遍重试，这一等是多久没人保证。

要实时性，就该用同步传输（isochronous），它预留带宽、按帧发、宁可丢也不重传，音频视频那条路。要小数据低延迟，就该用中断传输（interrupt），它有 bInterval 保证轮询间隔。批量传输夹在中间，走的是「量大、不许错、慢点没关系」这条路。

本篇的路线：先讲清类和描述符（第二、三章），再讲端点特性（第四章），然后设备侧固件（第五章）、主机侧访问（第六章），最后把 CDC 改造成 Bulk 的具体步骤（第七、八章），收尾讲 Windows 与 Linux 两套驱动方案（第九、十章）和测试验证（第十一章）。

二、标准类与厂商自定义类 #

类代码有两个落点，别看混。

第一个是设备描述符的 bDeviceClass。填了具体值，就是整台设备属于这个类，比如一个纯键盘填 0x03。

第二个是接口描述符的 bInterfaceClass。设备级填 0x00 的时候，表示「类不在设备级定义，去接口上看」。复合设备就这么干：一个配置里塞多个接口，键盘接口填 0x03，自定义数据口填 0xFF，互不干扰。

规范还有一条硬约束：bDeviceClass 填 0xFF 时，bDeviceSubClass 和 bDeviceProtocol 必须都是 0x00。真正的类信息落到接口描述符上，接口的 bInterfaceClass 也填 0xFF。

常见标准类代码摆一张表，方便你对照手上的设备。

类 代码 典型设备
Audio 0x01 声卡、耳麦
CDC 0x02 虚拟串口、4G 模块、网卡（ECM/NCM）
HID 0x03 键盘、鼠标、游戏手柄
Physical 0x05 力反馈摇杆
Image 0x06 扫描仪、PTP 相机
Mass Storage 0x08 U 盘、移动硬盘
Hub 0x09 USB 集线器
Video 0x0E 摄像头、采集卡
Wireless 0xE0 蓝牙适配器
Miscellaneous 0xEF 复合设备（配合接口关联描述符）
Application Specific 0xFE 厂商固件升级（DFU）
Vendor Specific 0xFF 你自己

0xFF 这一行的意思很直白：规范里没有为这个类定义任何标准请求、任何标准数据格式、任何标准驱动。主机拿到它，只能按通用流程把描述符读完，然后开始找你装的驱动。

为什么 Windows 下会立刻变成一个带感叹号的未知设备，原因就在这儿。设备管理器里那行字会写成「该设备的驱动程序未被安装」或者「未知设备」，硬件 ID 是 USB\VID_XXXX&PID_XXXX。系统翻遍自己的驱动库，没有一条 bDeviceClass = 0xFF 的通用驱动能匹配，于是停在那儿。这不是枚举失败，枚举是成功的，描述符全读到了，只是驱动没绑上。

标准类和自定义的差别，摊开对比更清楚。

维度 标准类设备 厂商自定义设备
类代码 0x01 到 0xFE 的某个值 0xFF
描述符来源 类规范规定好了格式 你自己按 USB 基础规范手写
固件逻辑 实现类规范定义的行为 实现你自己定义的协议
Windows 驱动 系统自带 自己装（WinUSB / libusb / 自写 WDM）
Linux 访问 内核类驱动自动绑定 内核不绑，走 usbfs + libusb
主机应用 系统组件代劳 全部自己写
改一版协议 受类规范约束 想怎么改就怎么改

复合设备值得单独提一句。一个配置里多个接口，各自带自己的类代码，这种结构在真实产品里很常见：一个 HID 接口负责按键和指示灯，一个自定义 bulk 接口负责大数据通道。Windows 对这种组合的处理方式有两种，要么用 WCID（微软操作系统描述符）让系统自动装 WinUSB，要么在 .inf 里按接口的硬件 ID 精确匹配。这块第九章展开。

三、描述符要自己写 #

主机不认识你，它认识描述符。整个枚举过程就是主机在一层层问、设备在一层层答。

text
主机                          设备
 |--- GET_DESCRIPTOR 设备(8B) -->|   先只要前 8 字节，拿到 bMaxPacketSize0
 |<-- 8 字节设备描述符 ----------|
 |--- SET_ADDRESS -------------->|   分配地址
 |--- GET_DESCRIPTOR 设备(18B)-->|   这次要完整的
 |<-- 18 字节设备描述符 ---------|
 |--- GET_DESCRIPTOR 配置 ------>|   要配置描述符（含接口、端点）
 |<-- 配置 + 接口 + 端点 --------|
 |--- GET_DESCRIPTOR 字符串 ---->|   厂商名、产品名、序列号
 |<-- Unicode 字符串 -----------|
 |--- SET_CONFIGURATION(1) ----->|   配置生效，端点可用
 |--- 开始批量传输 ------------->|

自定义设备要写的描述符有五种，标准类设备里其中两三种由类规范代劳，这里全归你。

描述符 bDescriptorType 长度 必须写吗 作用
设备描述符 0x01 18 字节 必须 VID/PID、类代码、端点 0 包长
配置描述符 0x02 9 字节 必须 供电方式、接口数量、总长度
接口描述符 0x04 9 字节 必须 类代码、端点数量
端点描述符 0x05 7 字节 有端点就得写 传输类型、方向、包长、轮询间隔
字符串描述符 0x03 可变 可选 厂商名、产品名、序列号
设备限定符 0x06 10 字节 高速设备建议写 兼容全速时的能力
其它速度配置 0x07 可变 多速度时写 另一速度下的配置

先从设备描述符开始。VID 和 PID 一定要改，两家的产品不能撞号，改了主机才知道是你。

c
const uint8 Device_Descriptor[18] =
{
    0x12,       // bLength          描述符长度：18 字节
    0x01,       // bDescriptorType  描述符类型：0x01 = 设备描述符
    0x00, 0x02, // bcdUSB           USB 规范版本，BCD 码：2.00
    0xFF,       // bDeviceClass     设备类：0xFF = 厂商自定义
    0x00,       // bDeviceSubClass  子类：自定义类必须为 0
    0x00,       // bDeviceProtocol  协议：0x00 = 不使用任何类协议
    0x20,       // bMaxPacketSize0  端点 0 最大包长：32 字节
    0xA2, 0x15, // idVendor         供应商 ID（VID），小端存放
    0x0F, 0xA5, // idProduct        产品 ID（PID），小端存放
    0x00, 0x00, // bcdDevice        设备版本号，BCD 码
    0x01,       // iManufacturer    厂商字符串描述符索引
    0x02,       // iProduct         产品字符串描述符索引
    0x03,       // iSerialNumber    序列号字符串描述符索引
    0x01        // bNumConfigurations 配置数量：1 个
};

几个字段值得盯一眼。

bMaxPacketSize0 是端点 0 的包长。全速设备可以填 8、16、32、64，高速设备必须是 64。填 32 也能跑，但枚举阶段每个控制传输要多来回几趟，速度慢一点。

idVendor 和 idProduct 都是 16 位小端。0xA2, 0x15 实际值是 0x15A2，0x0F, 0xA5 是 0xA50F。别按书写顺序当大端理解，主机拼出来的是反的。

后面三个 iXxx 是字符串索引，填 0 表示「没有这个字符串」。如果你的设备不打算给名字，三个全填 0，主机就只能显示 USB\VID_15A2&PID_A50F。

接着是配置描述符，它自己只有 9 字节，但要带上接口和端点，整体是一块连续数据。

c
/* 配置描述符：9 字节 */
0x09,       // bLength
0x02,       // bDescriptorType = 配置描述符
0x20, 0x00, // wTotalLength = 32 字节（配置 9 + 接口 9 + 端点 7 + 端点 7）
0x01,       // bNumInterfaces = 1 个接口
0x01,       // bConfigurationValue = 1（SET_CONFIGURATION 时用这个值）
0x00,       // iConfiguration = 0，无字符串
0x80,       // bmAttributes = 0x80，总线供电，不支持远程唤醒
0x32,       // bMaxPower = 100mA（单位 2mA，0x32 = 50）

wTotalLength 是这里最容易算错的一处。它等于配置描述符本身加上后面所有接口描述符、端点描述符、类描述符的总字节数。少算了，主机会少读几个端点，你以为配置了两个批量端点，实际只认出来一个；多算了，主机会读越界，拿到的尾巴是垃圾数据，枚举直接失败。

接口描述符把类代码再声明一遍，同时告诉主机这个接口有几个端点。

c
/* 接口描述符：9 字节 */
0x09,       // bLength
0x04,       // bDescriptorType = 接口描述符
0x00,       // bInterfaceNumber = 接口 0
0x00,       // bAlternateSetting = 0
0x02,       // bNumEndpoints = 2 个端点（1 个 IN + 1 个 OUT）
0xFF,       // bInterfaceClass = 0xFF，厂商自定义
0x00,       // bInterfaceSubClass = 0
0x00,       // bInterfaceProtocol = 0
0x00        // iInterface = 0，无字符串

然后是端点描述符，这是「只走批量」这句话落到字节上的地方。

c
/* 端点描述符：批量 IN，7 字节 */
0x07,       // bLength
0x05,       // bDescriptorType = 端点描述符
0x81,       // bEndpointAddress = 0x81，EP1，方向 IN（bit7 = 1）
0x02,       // bmAttributes = 0x02，批量传输
0x40, 0x00, // wMaxPacketSize = 64 字节（全速批量端点上限）
0x00,       // bInterval = 0，批量端点不用

/* 端点描述符：批量 OUT，7 字节 */
0x07,       // bLength
0x05,       // bDescriptorType = 端点描述符
0x02,       // bEndpointAddress = 0x02，EP2，方向 OUT（bit7 = 0）
0x02,       // bmAttributes = 0x02，批量传输
0x40, 0x00, // wMaxPacketSize = 64 字节
0x00        // bInterval = 0

bEndpointAddress 的 bit7 是方向位，低 4 位是端点号。所以 0x81 是 EP1 的 IN 方向，0x02 是 EP2 的 OUT 方向，0x83 是 EP3 的 IN 方向。同一个端点号的两个方向是两个独立端点，描述符里要各写一条。

bmAttributes 的 bit1-0 决定传输类型：00 控制、01 同步、10 批量、11 中断。填 0x02 才是批量。

wMaxPacketSize 的取值有硬上限。全速批量端点可以是 8、16、32、64，高速批量端点必须是 512。填超了，主机会拒绝配置。

bInterval 对批量端点没有意义，填 0。这一条后面第八章还会拎出来单独说，因为它是 CDC 改造时最容易漏的字段。

字符串描述符是可选的，用了就得按 Unicode 编码，一个 ASCII 字符占两字节。

c
uint8_t USB_STR_2[USB_STR_2_SIZE + USB_STR_DESC_SIZE] =
{
    sizeof(USB_STR_2),        // bLength，整个描述符的字节数
    USB_STRING_DESCRIPTOR,    // bDescriptorType = 0x03
    'B', 0, 'U', 0, 'L', 0, 'K', 0, ' ', 0,
    'T', 0, 'R', 0, 'A', 0, 'N', 0, 'S', 0,
    'A', 0, 'C', 0, 'T', 0, 'I', 0, 'O', 0, 'N', 0
};

注意第一个元素写的是 sizeof(USB_STR_2)，这里依赖数组定义长度和实际字节数对齐。手写字符串描述符时，bLength 算错一个字节，主机会读到截断的名字或者直接丢弃这个字符串。稳妥做法是先算出长度再定义数组，别让 bLength 靠推断。

字符串描述符的索引 0 有个特殊约定：GET_DESCRIPTOR 请求字符串索引 0 时，返回的是一张支持的语言 ID 表（LANGID），不是名字。设备描述符里 iManufacturer 之类填的 1、2、3 都是从 1 开始，0 留给这张表。

四层描述符串起来看，结构是这样的。

text
设备描述符（1 份，18 字节）
  └─ 配置描述符（1 份，9 字节）
       ├─ 接口描述符（1 份，9 字节）  bInterfaceClass = 0xFF
       │    ├─ 端点描述符（0x81，批量 IN，64 字节）
       │    └─ 端点描述符（0x02，批量 OUT，64 字节）
       └─ （可选）第二个接口描述符 ...
字符串描述符（0 到 N 份，按索引取）

描述符写完之后，枚举能过，但事情只完成了一半。主机现在知道你有个批量端点，可它不知道往里写什么、按什么节奏读。协议那一层，全在你脑子里，得靠主机程序实现。

四、批量端点的特性 #

先把四种传输摆在一起，看批量传输站在哪儿。

传输类型 bmAttributes 带宽保证 时间保证 数据完整性 典型用途
控制 control 0x00 有预留 有 CRC 加重传 枚举、配置、类请求
同步 isochronous 0x01 有预留 有 无重传，出错就丢 音频、视频
中断 interrupt 0x03 有预留 有（按 bInterval） CRC 加重传 键盘、鼠标、小数据
批量 bulk 0x02 无预留 无 CRC 加重传 大块数据、存储、打印机

这张表要这么读：批量和同步是两极。同步牺牲正确性换时间，宁可丢帧也要按时发；批量牺牲时间换正确性，晚一点没关系，但一个字节都不能错。中断传输两者都占一点，代价是数据量小。

批量传输的三个机制，决定了上面那条性质。

事务里带 CRC16。每一包数据的 PID 后面跟着 CRC16，收端算不对就丢弃、不回 ACK，发端等不到 ACK 就重传。所以错的数据不会被上层看到。

有握手包。数据包之后是 ACK 或 NAK，NAK 表示「我现在收不了，你待会儿再来」。设备缓冲满了就回 NAK，主机不会因此报错，只会重试。

用短包标记结束。一个传输请求（transfer）里可以塞多个包，收端怎么知道传完了？收到一个小于 wMaxPacketSize 的包，就认为本次传输结束。要传 64 字节的数据在 64 字节端点上，发一个整包还不够，得再补一个 0 长度的包来收尾。

端点的两个参数，取值有明确边界。

全速设备：批量端点的 wMaxPacketSize 可以是 8、16、32、64，最大 64。高速设备：批量端点必须是 512，这是规范定死的，写 64 反而不合规。超速（SuperSpeed）另外还有 burst 的概念，本篇不碰。

text
全速 USB（12 Mbps）  bulk 端点包长上限 64 字节
高速 USB（480 Mbps） bulk 端点包长上限 512 字节

bInterval 在批量端点上没有实际意义，填 0 就好。它是给中断端点和同步端点用的：中断端点用它表示轮询间隔（全速 1 到 255 毫秒，高速按 2 的幂编码微帧），同步端点用它表示每隔几个帧发一次。

注意一个坑：同一个端点号，全速下配 64、高速下配 512，这是合法的，因为有两个配置描述符或一个设备限定符来描述两种速度下的能力。如果你只写了一份配置描述符，设备插到高速口上，主机会按高速要求去检查包长，64 就不合格。稳妥做法是高速设备直接写 512，只做全速就写 64 到 64 之间能整除的值。

吞吐怎么估，给个手感。全速总线理论 12 Mbps，扣掉协议开销，批量传输实际能跑到 1 MB/s 上下。高速总线理论 480 Mbps，批量实际能到 30 到 40 MB/s。这个数字是量级感，不是承诺，总线上一堆设备抢带宽时会更低。

批量传输做不了什么，也说清楚。

做不了硬实时。没有一个「最迟多少毫秒内必须送到」的承诺。工控里那种 1ms 周期的同步采样，靠批量传输实现不了。

做不了低延迟小包。一包 2 字节的控制命令走批量，效率极低，还不如走中断端点。

做不了带宽预留。总线被一个等时设备占满，你的批量传输就是会被挤。USB 2.0 里同步传输和中断传输占了预留带宽，批量传输只能吃剩下的。

反过来，批量传输最擅长的场景：固件升级包、日志回读、大批量采样数据上传、图像数据回传、打印机数据流。共同点是量大、不许错、晚一点无所谓。

五、设备侧：固件要做什么 #

固件的骨架，从一次插上电开始。

上电先初始化 USB 控制器外设：时钟、引脚复用、DMA 通道。然后使能上拉电阻（全速设备是把 D+ 拉高，告诉主机「有设备接上了」）。主机检测到之后开始复位和枚举，控制器产生中断，固件在中断里响应标准请求。

标准请求就那么几个，枚举期间会被反复问到。

请求 bmRequestType 你要做的
GET_DESCRIPTOR 0x80 把设备/配置/字符串描述符按长度切好递出去
SET_ADDRESS 0x00 把主机分配的地址写进控制器
SET_CONFIGURATION 0x00 使能端点、清缓冲、准备收发
GET_CONFIGURATION 0x80 返回当前配置值
GET_STATUS 0x80 返回两个字节的状态
CLEAR_FEATURE 0x00 清端点 STALL 之类的状态
SET_INTERFACE 0x01 切换备用设置（没用到就不用管）

固件里分三个请求处理函数：标准请求、类请求、厂商请求。0xFF 设备没有类请求，那一段可以整块删掉。厂商请求（bmRequestType 的 bit6 置 1，即 0x40 或 0xC0）是你自己定的，可以放一些「复位」「取版本号」「切模式」的命令。

这是 Freescale USB Stack 4.1.1 里自定义 bulk 设备的端点表，三个端点对应三种角色。

c
/* structure containing details of all the endpoints used by this device */
USB_EP_STRUCT ep[CDC_DESC_ENDPOINT_COUNT] =
{
    {
        CIC_NOTIF_ENDPOINT,      /* 端点号 */
        USB_INTERRUPT_PIPE,      /* 传输类型：中断 */
        USB_SEND,                /* 方向：发送（IN） */
        CIC_NOTIF_ENDP_PACKET_SIZE
    },
    {
        DIC_BULK_IN_ENDPOINT,    /* 批量 IN，设备发给主机 */
        USB_BULK_PIPE,
        USB_SEND,
        DIC_BULK_IN_ENDP_PACKET_SIZE
    },
    {
        DIC_BULK_OUT_ENDPOINT,   /* 批量 OUT，主机发给设备 */
        USB_BULK_PIPE,
        USB_RECV,
        DIC_BULK_OUT_ENDP_PACKET_SIZE
    }
};

这段代码是从 CDC 直接搬过来的，所以第一个条目还是那个中断端点。改造的思路看得很清楚：只留后两个，把第一个的 CIC_NOTIF_ENDPOINT 那一项整条删掉，再把数量从 3 改成 2。

数据结构层面，每个端点要准备三样东西：发送缓冲、接收缓冲、长度计数。典型写法是两个全局变量加两个指针。

c
static uint8_t  g_send_buf[BULK_BUF_SIZE];
static uint8_t  g_recv_buf[BULK_BUF_SIZE];
static uint32_t g_send_size = 0;   /* 待发字节数 */
static uint32_t g_recv_size = 0;   /* 已收字节数 */

发送流程走的是「填缓冲 + 发起传输 + 等回调」。

c
/* 应用侧填好 g_send_buf 和 g_send_size 后调用 */
void bulk_send_start(void)
{
    if (g_send_size == 0) {
        return;
    }
    /* 把缓冲交给控制器，传输完成会回调，回调里清 g_send_size */
    USB_Class_Send_Data(g_app_handle,
                        DIC_BULK_IN_ENDPOINT,
                        g_send_buf,
                        g_send_size);
}

接收流程反过来，是「控制器收完触发回调，回调里把缓冲取走」。

c
/* USB 栈收到 OUT 数据后回调进来 */
void bulk_recv_callback(uint8_t ep, uint8_t *buf, uint32_t len)
{
    if (ep != DIC_BULK_OUT_ENDPOINT) {
        return;
    }
    memcpy(g_recv_buf, buf, len);
    g_recv_size = len;
    /* 立刻重新挂接收，否则后续数据会 NAK 到超时 */
    USB_Class_Recv_Data(g_app_handle, DIC_BULK_OUT_ENDPOINT, NULL, MAX_LEN);
}

主循环里做的是「有空就处理」。

c
static bool start_transactions = TRUE;   /* 自定义设备默认使能传输 */

int main(void)
{
    uint8_t start_app = FALSE;

    TestApp_Init();                      /* 初始化 USB 栈并挂上接口 */

    while (TRUE)
    {
        USB_CDC_Periodic_Task();         /* 周期性任务，别漏 */

        /* 枚举完成且传输已使能，才进应用 */
        if ((start_app == TRUE) && (start_transactions == TRUE))
        {
            Virtual_Com_App();
        }
    }
}

这里有个从 CDC 继承下来的麻烦，第七章会细讲：start_transactions 原本由主机发 SET_CONTROL_LINE_STATE 置位，自定义设备没有这个请求，变量永远停在 FALSE，应用层一次也进不去。解决方式是把初始值写成 TRUE，或者干脆删掉这个判断。

固件里还有几处细节值得定下来。

零长度包的处理。前面说过，数据刚好是 wMaxPacketSize 的整数倍时，要补一个 ZLP，否则主机以为传输没完。控制器一般有现成接口，或者靠「长度等于缓冲长度就不发后续包」这种逻辑控制。

STALL 的使用。收到不认识的请求、缓冲溢出、状态不对时，用 STALL 回复比静默忽略好。主机会立刻知道出错，而不是等到超时。STALL 之后要用 CLEAR_FEATURE 清掉才能恢复，固件里不能一直停在 STALL。

端点缓冲大小。批量端点双缓冲能提高吞吐，但吃 RAM。小资源的 MCU 用一个缓冲也能跑，只是主机会频繁收到 NAK。

六、主机侧：怎么访问 #

主机侧有两代 API，别混着用。它们名字很像，但一个是老 libusb-0.1 风格，一个是 libusb-1.0。网上抄代码时看清头文件就知道是哪一代。

老的一代来自 LibUSB-Win32。它是一套 Windows 上的通用 USB 设备驱动，卖点是「不写一行内核驱动代码就能访问任意 USB 设备」。能力清单摆出来：

能力 说明
访问任意 USB 设备 已安装驱动的设备也能接着访问
当自己设备的驱动用 配一份 .inf 就绑上去
支持批量与中断传输 正好覆盖自定义设备的需求
支持所有标准设备请求 枚举、配置那一套全通
支持厂商自定义请求 控制端点上的私有命令能发

发布源是 libusb-win32.sourceforge.net，许可证是 LGPL 加 GPL，条款明确允许用在商业软件里，不只是开源项目。这点对做产品的人有意义，别看到 GPL 就以为整条产品线都得开源。

接入工程只要三个文件：libusb0.dll、libusb.lib、usb.h。前两个是运行库和导入库，后一个是头文件。上机通信也只用到七个函数，流程四步：初始化、打开设备、批量读写、关闭。

第一代长这样，函数名前缀是 usb_，libusb0.dll 那一套。

c
usb_init()
usb_find_busses()
usb_find_devices()
usb_get_busses()
usb_open()
usb_bulk_read() / usb_bulk_write()
usb_close()

第二代长这样，函数名前缀是 libusb_，返回统一是错误码。

c
libusb_init()
libusb_get_device_list()
libusb_open()
libusb_claim_interface()
libusb_bulk_transfer()
libusb_release_interface()
libusb_close()
libusb_exit()

两代的关键差别在接口管理。第二代要求先 libusb_claim_interface 才能读写，内核驱动如果已经占了这个接口，还得先 libusb_detach_kernel_driver。第一代把 usb_claim_interface 放在 usb_set_configuration 之后，顺序错了也会失败。

第一代的完整流程，四步走：初始化、打开设备、批量读写、关闭。

第一步是 usb_init，把库初始化起来。第二步找设备：先依次调 usb_find_busses、usb_find_devices、usb_get_busses，拿到已发现的 USB 总线链表；再遍历链表里的每个设备，按已知的 VID/PID 比对，命中就 usb_open 打开。这一步有个前提，前面提过一次，这里再强调：总线上不能有两台 VID/PID 相同的设备。有的话得再比设备名或序列号，否则打开的那台不一定是你想要的。

第三步收发，用 usb_bulk_read 和 usb_bulk_write。第四步 usb_close 关闭句柄。

c
void libusb_test(void)
{
    usb_dev_handle *dev = NULL;   /* 设备句柄 */
    char tmp[BUF_SIZE];
    int ret;

    usb_init();           /* 1. 初始化库 */
    usb_find_busses();    /* 扫描所有总线 */
    usb_find_devices();   /* 扫描所有已连接设备 */

    if (!(dev = open_dev()))
    {
        printf("error opening device: \n%s\n", usb_strerror());
        return;
    }
    else
    {
        printf("success: device %04X:%04X opened\n", MY_VID, MY_PID);
    }

    usb_set_configuration(dev, 1);   /* 选配置 1 */
    usb_claim_interface(dev, 0);     /* 占用接口 0，之后才能读写 */

    tmp[0] = 0x3;
    ret = usb_bulk_write(dev, 0x3, tmp, 64, 1000);   /* 端点 0x3，64 字节，1000ms 超时 */
    if (ret < 0)
    {
        TRACE("error writing:\n%s\n", usb_strerror());
    }
    else
    {
        TRACE("success: bulk write %d bytes\n", ret);
    }

    if (dev)
    {
        usb_close(dev);
    }
}

找设备那一步，第一代只能靠遍历链表比 VID/PID。

c
usb_dev_handle *open_dev(void)
{
    struct usb_bus *bus;
    struct usb_device *dev;

    for (bus = usb_get_busses(); bus; bus = bus->next)
    {
        for (dev = bus->devices; dev; dev = dev->next)
        {
            if ((dev->descriptor.idVendor  == MY_VID) &&
                (dev->descriptor.idProduct == MY_PID))
            {
                return usb_open(dev);
            }
        }
    }
    return NULL;
}

这个写法有个前提：总线上只能有一台 VID/PID 相同的设备。插了两台，打开的是先遍历到的那台，另一台你摸不到。要区分就再比一下 iSerialNumber 对应的序列号字符串，或者比 bcdDevice。

第二代的打开流程，多了几步，但错误码清晰。

c
libusb_device_handle *dev = NULL;
int rc;

libusb_init(NULL);

dev = libusb_open_device_with_vid_pid(NULL, MY_VID, MY_PID);
if (dev == NULL) {
    printf("open failed\n");
    goto out;
}

/* 内核驱动若已占用该接口，先摘掉 */
if (libusb_kernel_driver_active(dev, 0) == 1) {
    libusb_detach_kernel_driver(dev, 0);
}

rc = libusb_claim_interface(dev, 0);
if (rc < 0) {
    printf("claim failed: %s\n", libusb_error_name(rc));
    goto out;
}

/* 一次批量写 */
int transferred = 0;
rc = libusb_bulk_transfer(dev, 0x03, buf, 64, &transferred, 1000);
if (rc < 0) {
    printf("bulk write failed: %s\n", libusb_error_name(rc));
}

libusb_release_interface(dev, 0);
out:
if (dev) libusb_close(dev);
libusb_exit(NULL);

端点地址那一位别搞错。libusb_bulk_transfer 的 endpoint 参数是完整地址，包含方向位：0x03 是 EP3 的 OUT（方向位 0），0x83 是 EP3 的 IN（方向位 1）。传 0x3 去读数据会失败。

读写分开看，代码几乎对称。

c
/* 写：主机到设备，OUT 端点 */
int transferred = 0;
libusb_bulk_transfer(dev, EP_OUT, tx_buf, tx_len, &transferred, 5000);

/* 读：设备到主机，IN 端点 */
int nread = 0;
libusb_bulk_transfer(dev, EP_IN, rx_buf, sizeof(rx_buf), &nread, 5000);

超时参数是必填项。0 表示无限等待，除非你确定设备一定会回，否则别用，程序会挂死在那一行。

还有一个坑：读的时候传的缓冲长度不必等于端点包长。传 4096、端点 64，底层会拆成 64 个包，收满 4096 或者收到短包就返回。返回值 transferred 才是实际字节数，不要拿请求长度当结果。

设备被拔掉了怎么办。第一代 API 会返回负数，usb_strerror() 里是 error writing: No such device。第二代是 LIBUSB_ERROR_NO_DEVICE。这种情况要重新枚举、重新打开，别把旧句柄接着用。

七、从 CDC 改造成 Bulk #

这一节是 CDC 那篇的落地版。CDC 设备为什么不能直接当 bulk 用，得先说清楚它的结构。

CDC 一个配置里有两个接口。

text
配置描述符
  ├─ 接口 0：通信接口（Communication Interface Class）
  │    bInterfaceClass = 0x02
  │    ├─ 端点 0x82：中断 IN，上报串口状态（线路状态、串口事件）
  │    └─ 类特定描述符：CDC 功能描述符、Call Management、ACM
  └─ 接口 1：数据接口（Data Interface Class）
       bInterfaceClass = 0x0A
       ├─ 端点 0x81：批量 IN
       └─ 端点 0x02：批量 OUT

通信接口负责「控制面」：SET_CONTROL_LINE_STATE（DTR/RTS）、GET_LINE_CODING（波特率、数据位、停止位、校验）、SEND_BREAK。数据接口负责「数据面」，就是那两个批量端点。

改造的核心动作一句话：把通信接口去掉或简化，只留数据接口的批量端点。

为什么必须动通信接口。它不是可有可无的装饰。CDC 的设备类代码是 0x02，主机看到这个代码就加载 CDC 类驱动（Windows 上是 usbser.sys，Linux 上是 cdc_acm），然后这个驱动会去等通信接口上的类请求。你带着通信接口却把类代码改成 0xFF，主机不再加载 CDC 驱动，那个中断端点就成了没人读的孤儿，白占一个端点资源。更糟的是，如果主机侧有程序按 CDC 语义去发 SET_CONTROL_LINE_STATE，固件已经不处理了，start_transactions 永远不置位。

改造分五步，顺序别乱。

第一步，改 VID/PID 和类代码。

c
const uint8 Device_Descriptor[18] =
{
    0x12, 0x01,
    0x00, 0x02,
    0xFF,       /* 原来是 0x02（CDC），改成 0xFF（厂商自定义） */
    0x00, 0x00,
    0x20,
    0xA2, 0x15,
    0x0F, 0xA5,
    0x00, 0x00,
    0x01, 0x02, 0x03,
    0x01
};

VID/PID 换成你自己的。如果沿用原厂的 VID 配新 PID，主机会因 VID 匹配上某个已有驱动而误绑，改了更干净。

第二步，改配置描述符的总长度和接口数。

原来两个接口三个端点，现在一个接口两个端点。wTotalLength 要从原来的（大约 67 字节）降到 32 字节，bNumInterfaces 从 2 改成 1。

c
/* 改造前 */
0x09, 0x02,
0x43, 0x00,  /* wTotalLength = 67 */
0x02,        /* bNumInterfaces = 2 */

/* 改造后 */
0x09, 0x02,
0x20, 0x00,  /* wTotalLength = 32 */
0x01,        /* bNumInterfaces = 1 */

这个数字算错是改造里最常见的失败原因，症状是枚举失败或者端点数量不对。算法很简单：9（配置）+ 9（接口）+ 7（端点）+ 7（端点）= 32。

第三步，删掉通信接口和它的中断端点描述符。

整块删，包括接口 0 的接口描述符、0x82 的中断端点描述符、以及 CDC 功能描述符、Call Management 描述符、ACM 描述符、Union 描述符这几条类特定描述符。剩下的接口描述符里，bInterfaceClass 从 0x0A 改成 0xFF。

c
/* 改造后的接口描述符 */
0x09, 0x04,
0x00,        /* bInterfaceNumber = 0（原来是 1，现在唯一接口从 0 开始） */
0x00, 0x02,
0xFF,        /* 原来是 0x0A（CDC Data），改成厂商自定义 */
0x00, 0x00,
0x00

bInterfaceNumber 从 1 改回 0，这一处容易忘。接口编号不连续（比如只有一个接口但编号是 1）会让部分主机侧代码找接口时失败。

第四步，改端点表和固件收发逻辑。

端点表从 3 条删成 2 条，删掉 CIC_NOTIF_ENDPOINT 那一条，CDC_DESC_ENDPOINT_COUNT 跟着改。

c
USB_EP_STRUCT ep[2] =
{
    {
        DIC_BULK_IN_ENDPOINT,
        USB_BULK_PIPE,
        USB_SEND,
        DIC_BULK_IN_ENDP_PACKET_SIZE
    },
    {
        DIC_BULK_OUT_ENDPOINT,
        USB_BULK_PIPE,
        USB_RECV,
        DIC_BULK_OUT_ENDP_PACKET_SIZE
    }
};

固件里的 Virtual_Com_App() 这个名字保留也无所谓，但里面的逻辑要按自己的协议写：收到一帧解析一帧，回一帧组一帧。原来那种「收到什么就原样回显什么」的写法，只适合做连通性测试。

第五步，处理 start_transactions。

CDC 的初始化里有这么一段，start_transactions 初始是 FALSE，靠主机发 SET_CONTROL_LINE_STATE 置位。自定义设备没这个请求。

c
static bool start_transactions = TRUE;   /* 从 FALSE 改成 TRUE */

void TestApp_Init(void)
{
    /* …… */
    g_app_handle = USB_Class_CDC_Init(&cdc_config);
    g_recv_size = 0;
    g_send_size = 0;

    while (TRUE)
    {
        USB_CDC_Periodic_Task();

        /* 枚举完成且传输已使能，才进应用 */
        if ((start_app == TRUE) && (start_transactions == TRUE))
        {
            Virtual_Com_App();
        }
    }
}

两种做法任选：初始值写 TRUE，或者把 start_transactions 相关的判断整段删掉，条件只留 start_app == TRUE。前者改动小，后者更干净。别只改注释不改值，这个错误查起来能耗掉半天。

改造完，原来那条「插上就是 COM 口」的路消失了。现在插上，Linux 里 dmesg 显示一个新设备但没有 ttyACM 节点，Windows 里显示未知设备。这是预期行为，不是改造失败。下一步是给它写主机程序，再下一步是解决 Windows 驱动。

八、改造时要注意的细节 #

改造的动作不难，坑全在细节上。

端点描述符里的 wMaxPacketSize 与 bInterval，最容易漏。

这句单独拎出来讲。CDC 的数据接口本来就有两个批量端点，改造时是把它们挪位置、改地址，很容易连包长带间隔一起抄过去，不再核对。结果就是全速设备上包长写成 512，主机会判定配置无效；高速设备上写成 64，带宽白扔一大半。

bInterval 的坑更阴。通信接口那个中断 IN 端点（0x82）的 bInterval 是有值的，比如 16 或 32。你删掉它的描述符，却照着同一套字段结构复制给了新的批量端点，那个非零值就留下来了。多数主机不吭声，但描述符已经不自洽：规范要求批量端点的这个字段为 0。

字段 全速 高速 批量端点的正确值
wMaxPacketSize 8 / 16 / 32 / 64 512 按速度取上限
bInterval — — 0（批量不使用）

端点地址不必重排，计数必须改。 删掉 0x82 之后，剩下的 0x81 和 0x02 照样能用。要改的是 bNumEndpoints 那个字节（3 变 2），以及 wTotalLength 跟着减：两个端点描述符减 14，通信接口那一坨再减掉。

类特定描述符要清干净。 CDC 通信接口底下挂着 CDC 功能描述符、Call Management、ACM、Union，bDescriptorType 是 0x24 或 0x25，跟标准描述符混在同一块连续内存里。删接口描述符时只删那 9 字节标准描述符，很容易把它们留在原地。主机读到一串不认识的描述符类型，配置直接废掉。

宏和数组要同步。 Freescale 栈里 CDC_DESC_ENDPOINT_COUNT 是 3，ep[] 按这个值定义。删了一条不改宏，数组里多出一个空条目；宏改小了数组还按 3 初始化，运行时端点表被读越界。编译不报错，跑起来才炸。

bLength 别靠推断。 字符串描述符写成 sizeof(USB_STR_2) 依赖数组长度定义正确，改名字时长度和 bLength 会脱钩，主机读到截断的字符串。算一遍：开头 2 字节，之后每个 ASCII 字符 2 字节。

描述符只在枚举时读一次。 改完烧写，必须拔插或软复位让主机重新枚举，热改不生效。同理，SET_CONFIGURATION 之前端点还没使能，这时候往批量端点塞数据，控制器会报错或者静默丢弃。等 start_app 置位再进收发循环。

九、Windows 下的驱动问题 #

这是自定义设备最劝退的一环。结论先摆出来：必须装驱动，不装就是设备管理器里那个黄色感叹号。

两条路。

方案 内核驱动 需要准备什么 工作量 适用
WinUSB 微软自带 winusb.sys 一个 .inf 把设备绑上去 小 绝大多数场景
libusb-win32 自带 libusb0.sys .inf 加驱动文件 小 老项目、老系统
自写 WDM/KMDF 自己写 驱动工程、签名、双机调试 大 需要内核态功能

第一条路是主流。WinUSB 从 Vista 起内置，它能干的活正好是自定义设备要的：读描述符、发控制请求、读写批量端点。它不认识你的协议，但把「端点读写」抽象成了 ReadFile / WriteFile 加几个 DeviceIoControl，协议解析留给你在应用层做。

关键在那个 .inf。WinUSB 不会自动认领你的设备，得写一份 inf 告诉系统：这个硬件 ID 用 winusb.sys，并且挂上一个接口 GUID 给应用层找设备用。

text
[Version]
Signature  = "$WINDOWS NT$"
Class      = USBDevice
ClassGuid  = {88BAE032-5A81-49f0-BC3D-A4FF138216D6}
Provider   = %ManufacturerName%

[Manufacturer]
%ManufacturerName% = DeviceList,NTamd64

[DeviceList.NTamd64]
%DeviceName% = USB_Install, USB\VID_15A2&PID_A50F

[USB_Install]
Include = winusb.inf
Needs   = WINUSB.NT

[USB_Install.Services]
Include = winusb.inf
Needs   = WINUSB.NT.Services

[USB_Install.HW]
AddReg = Dev_AddReg

[Dev_AddReg]
HKR,,DeviceInterfaceGUIDs,0x00010000,"{填你自己的GUID}"

HKR 那一行是给应用层的：注册表里挂一个接口 GUID，程序侧按这个 GUID 枚举设备，不用自己遍历 VID/PID。装的时候右键 inf 选「安装」，或者 pnputil /add-driver xxx.inf /install。设备管理器里名字前面的感叹号消失，就算成了。

第二条路 libusb-win32 是老方案，素材那篇走的正是这条。它自带 libusb0.sys，配自己的 .inf，用第一代 usb_* API。项目早已停更，新系统上装驱动还要处理签名，新项目别选。

现成工具能省事。Zadig 可以把 WinUSB 或 libusb-win32 一键绑到指定设备上，不用手写 inf；libusb-win32 自带的 inf-wizard.exe 干的是同一件事——扫描当前插着的 USB 设备，选中你要的那个，生成一份 .inf，这份 inf 就是产品发布时用的驱动文件。

Win7 之后驱动要签名。测试阶段可以临时开测试签名模式（bcdedit /set testsigning on 再重启），正式发布走正规签名流程。

还有个更省事的做法：WCID，微软操作系统描述符。在字符串描述符里加一个索引 0xEE 的特殊条目，Windows 读到之后自动装 WinUSB，用户插上就能用，完全不用手动装驱动。代价是固件里多写几十字节，而且这套东西不属于 USB 规范，是微软的私有约定。

两套系统的差别摆在一起最清楚。

项目 Windows Linux
内核驱动 必须（winusb.sys 或自写） 不需要
绑定方式 .inf 文件 udev 规则（只配权限）
用户态库 libusb / WinUSB API libusb
设备节点 无，走 GUID 或设备路径 /dev/bus/usb/BBB/DDD
免驱 做不到 可以（usbfs）
主要门槛 驱动签名 权限配置

十、Linux 下的免驱方案 #

Linux 的模型不一样。内核不认你的类，就不绑类驱动，但设备节点照样出现在 /dev/bus/usb/ 下。用户态用 libusb 对着这个节点发 USB 请求，全程不写一行内核代码。

这就是「免驱」的真实含义：绕过内核驱动，不是没有驱动。

节点路径按总线和设备号排，001/003 表示 1 号总线上的 3 号设备。插拔一次设备号会变，别写死在代码里。libusb 的 libusb_get_device_list 会帮你枚举，按 VID/PID 挑。

默认权限是个坎。节点属于 root:root，普通用户读写拿到的是 LIBUSB_ERROR_ACCESS。两条解法：跑 sudo，或者加一条 udev 规则。

存成 /etc/udev/rules.d/99-custom-bulk.rules，内容一行。

bash
SUBSYSTEM=="usb", ATTR{idVendor}=="15a2", ATTR{idProduct}=="a50f", MODE="0666"

改完重载。

bash
sudo udevadm control --reload-rules
sudo udevadm trigger

MODE="0666" 图省事，谁都能读写。多人机器上改成 GROUP="plugdev" 加 MODE="0660"，把自己加进那个组更稳。权限不够的典型症状是「能枚举、一读就失败」：lsusb 看得到设备，程序里 libusb_open 返回 LIBUSB_ERROR_ACCESS。

内核模块的干扰要防一手。usb-storage、cdc_acm、usbhid 会抢绑某些设备，尤其在你没改类代码、只改了协议的时候。lsusb -t 能看绑定情况，被占了就在程序里 libusb_detach_kernel_driver。类代码填 0xFF 的设备没这个烦恼，内核压根不认识它。

然后就是编译。

bash
sudo apt install libusb-1.0-0-dev
gcc main.c -o test -lusb-1.0

代码逻辑和第六章第二代那套完全一样：libusb_init、libusb_open、libusb_claim_interface、libusb_bulk_transfer、libusb_close。同一份主机程序，Windows 上链 libusb-1.0.lib，Linux 上链 -lusb-1.0，源码不动。

十一、测试与验证 #

改完别急着上业务逻辑，按顺序过六关。

第一关，枚举。 先确认描述符读全了。

bash
lsusb                              # 设备在不在
lsusb -v -d 15a2:a50f              # 描述符逐字节看

Windows 侧用 USBView，或者 libusb 自带的 testlibusb-win.exe。重点看五处：设备描述符的 bDeviceClass 是不是 0xFF、配置描述符的 wTotalLength 跟实际读到的字节数是否一致、接口有几个、端点是不是 Bulk 类型、wMaxPacketSize 是不是你要的值。这关不过，后面全是白搭。

第二关，控制传输。 用 libusb_control_transfer 发一条厂商自定义请求，看设备回不回。通了说明端点 0 的收发和请求分发都对。

第三关，批量环回。 主机发 64 字节，设备原样回 64 字节。这一步同时验两个方向的端点，第六章那个 64 字节写入加接收的例子，测的就是这一关。

第四关，边界长度。 逐个试 1、63、64、65、128、4096。64 和 128 是 wMaxPacketSize 的整数倍，专门暴露零长度包的问题；1 和 63 试短包；4096 试多包拼接。

第五关，吞吐。 连续发 10 MB 计时。全速下 1 MB/s 量级，高速下 30 MB/s 量级。差一个数量级，八成是主机侧每次只发一个小包，或者设备侧回 NAK 太频繁。

第六关，异常。 传输中途拔线看程序卡不卡死；设备缓冲塞满看 NAK 处理；不发 SET_CONFIGURATION 直接读写，看返回什么错误码。

抓包工具备一个。Linux 用 modprobe usbmon 加 Wireshark 抓 usbmon0，Windows 用 Wireshark 加 USBPcap，或者 Bus Hound。抓一次完整枚举，对着包核描述符的每个字节，比对着代码猜快得多。

十二、易错点速查 #

现象 常见原因 怎么改
设备管理器黄色感叹号 没装驱动，0xFF 没有类驱动 写 .inf 绑 WinUSB，或用 Zadig
枚举失败，读不到配置 wTotalLength 算错 9 + 9 + 7 × 端点数，重算
只认出一个端点 bNumEndpoints 没改 从 3 改成 2
接口找不到 bInterfaceNumber 还是 1 唯一接口改回 0
配置被主机拒绝 wMaxPacketSize 超上限 全速 64、高速 512
数据传一半就断 缺短包收尾或零长度包 整包之后补一个 0 长度包
应用层一直不进循环 start_transactions 还是 FALSE 改 TRUE 或删掉判断
读写返回错误 端点地址的方向位错 IN 要 0x8x，OUT 要 0x0x
Linux 报 ACCESS udev 权限没配 加规则 MODE="0666"
改了描述符没生效 主机缓存了旧的 拔插一次重新枚举
工具挑刺说描述符不规范 bInterval 残留非零值 批量端点填 0
编译过，运行时越界 CDC_DESC_ENDPOINT_COUNT 没同步 宏和数组长度一起改

自定义 USB 设备说到底就三句：0xFF 是给主机的一句声明，批量端点是数据通道，协议自己定。正确性由 CRC 加重传兜住，时间上没有任何承诺——要实时就换同步传输，要小数据低延迟就换中断传输。Windows 认这份声明的方式是让你写 inf 装驱动，Linux 认它的方式是让你配好 udev 权限。改造 CDC 的活，删掉通信接口、留下数据接口、把 wMaxPacketSize 和 bInterval 核一遍，剩下的都是固件里那点收发逻辑。
