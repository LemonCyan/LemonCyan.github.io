本篇讲 USB 的 CDC 类，也就是通信设备类（Communications Device Class）。落点是三个子类：ACM 把 USB 当串口，ECM 和 NCM 把 USB 当网卡。

讲什么：CDC 的定义、双接口结构、三个子类的分工、cdc_acm 与 cdc_ether/cdc_ncm 在 Linux 里的实现路径、ECM 的配置与坑。

不讲什么：USB 枚举、描述符解析、URB 生命周期这些底座在《编写 USB 驱动》里；具体设备的驱动注册流程在《驱动实例》里；设备侧怎么造一个 CDC 设备在《gadget》里；Bulk Only 那一套在《自定义 Bulk》里。

一句话先立住：CDC 不是一种新总线，是把 USB 模拟成传统接口的一套标准。串口和网卡在系统里活得跟真的一样，因为 TTY 子系统和网络子系统根本没察觉对面是 USB。

一、CDC 是什么 #

CDC 是 USB 定义的一类设备行为，类代码 0x02。它做的事一句话说完：把 USB 总线包装成一种传统接口，让主机侧拿现成的子系统去接。

串口、以太网、电话线，这些东西在操作系统里有几十年的积累。让 USB 设备冒充它们，比给每种 USB 设备写一套私有协议栈省事得多。CDC 就是这个「冒充」的标准。

主机凭什么知道该加载哪个驱动？靠接口描述符里的三个字节。

字段 作用 CDC 下的取值
bInterfaceClass 大类 0x02 通信接口，0x0A 数据接口
bInterfaceSubClass 模拟成什么 ACM=0x02，ECM=0x06，NCM=0x0D
bInterfaceProtocol 上层协议 ACM 下 0x01 表示 AT 命令集（v.25ter），0x00 表示无

主机枚举时把这三个字节读出来，拿去和已经注册的通用类驱动比对。对上了就绑定，对不上就是未知设备。

所以「免驱」的准确含义是：驱动早就编进内核里了，不用你写。不是没有驱动。

这跟 UVC 摄像头同一个路子。UVC 类代码 0x0E，插上就是 /dev/video0；CDC 类代码 0x02，插上是 /dev/ttyACM0，或者多出一块网卡。规矩是同一套规矩。

规范文档的名字叫 usbcdc11，CDC 1.1。里面只规定三件事：

  1. 描述符怎么写。告诉你这个设备属于哪个子类、有几个接口、控制面走哪个端点。
  2. 类请求怎么发。SET_LINE_CODING、GET_ENCAPSULATED_RESPONSE、SET_ETHERNET_PACKET_FILTER 这些都是类请求，走控制端点或者通信接口的中断端点。
  3. 数据面走哪。哪个接口是数据接口，数据接口上挂什么类型的端点。

注意到没有，规范管的是「怎么声明」和「怎么控制」，对数据怎么组织只给了框架。这就是为什么 ACM、ECM、NCM 三个子类在数据面上的差别那么大——标准留了余地。同样的硬件，声明成 ACM，数据接口上就是一对 Bulk 端点，搬的是串口字节流，没有边界概念；声明成 ECM，同一对 Bulk 端点上搬的是完整的以太网帧，一帧一个 USB 传输；声明成 NCM，搬的是一串聚合起来的帧，叫 NTB。上层子系统看到的完全是三种东西。

CDC 的版本信息写在 CDC Header 功能描述符的 bcdCDC 里，1.10 就是 CDC 1.1。这个字段在实际开发里用处不大，看描述符时知道它在说什么就行。

二、CDC 的接口结构 #

CDC 设备最硬的标志，是一个功能占两个接口：通信接口 + 数据接口。少一个都不成，这是 CDC 和普通单接口设备的分水岭。

接口 bInterfaceClass 端点 干什么
通信接口 0x02 Communications 1 个中断 IN 发类请求、上报线状态、上报串口信号变化、上报速率变化
数据接口 0x0A CDC Data 1 对 Bulk IN/OUT 只搬数据，不发命令

为什么拆两个？因为控制面和数据面的节奏完全不一样。控制面是低频、小包、要求及时（一个中断端点足够，设备有事件就 IN 一下）；数据面是高频、大包、要求吞吐（必须是 Bulk）。混在一个接口上，端点配置就没法各自最优。

通信接口上那个中断端点不是可选摆设。ACM 靠它上报串口线状态（CDC Notify Serial State），ECM 靠它上报网络连接和速率变化，NCM 也是。它要是没配好，链路能不能起来都成问题。

复合设备里还会多一段 IAD（Interface Association Descriptor），把功能边界划清楚：

text
Interface Association:
  bLength                 8      bDescriptorType        11
  bFirstInterface         2      bInterfaceCount         2
  bFunctionClass          2 Communications
  bFunctionSubClass       2 Abstract (modem)
  bFunctionProtocol       1 AT-commands (v.25ter)

bFirstInterface 加 bInterfaceCount 的意思是「从第几个接口开始，连着几个接口，组成一个功能」。上例里就是从接口 2 开始的两个接口构成一个 ACM 功能——说明这台设备不止一个功能，ACM 排在后面。没有 IAD 的老设备靠 CDC Union 表达同一件事。

几个功能描述符的分工理一下，看描述符时按这张表对。

功能描述符 关键字段 含义
CDC Header bcdCDC 设备支持的 CDC 版本
CDC Union bMasterInterface、bSlaveInterface 主接口是通信接口，从接口是数据接口，两者成对
CDC Call Management bmCapabilities、bDataInterface 是否自己管呼叫、数据走哪个接口
CDC ACM bmCapabilities 支持发 break、支持 line coding 与串口状态、支持 comm features 读写
CDC Ethernet Networking iMACAddress、bmEthernetStatistics 网卡的 MAC 地址、统计项位图
CDC NCM wNtbOutMaxSize、wNdpOutPayloadRemainder 等 NTB 聚合参数，见第八章

CDC Union 是这几个里最要紧的。它把从接口明确挂在主接口下面，主机才知道这两个接口属于同一个功能，不该被别的驱动抢走。bSlaveInterface 那个数字就是数据接口的 bInterfaceNumber，内核 probe 里要拿它去 usb_driver_claim_interface，这个后面讲。

端点规格记住两组数就够排查了：

端点 传输类型 全速包大小 高速包大小 用途
通信接口中断 IN Interrupt 64 64 类通知，bInterval 决定轮询间隔
数据接口 Bulk IN Bulk 64 512 设备到主机
数据接口 Bulk OUT Bulk 64 512 主机到设备

三、CDC 的三个常用子类 #

CDC 规范里子类不止三个，但真正在 Linux 里有成熟驱动、天天能碰到的就三个。其余几个先摆出来认个脸，免得看描述符时懵。

子类 子类码 模拟成什么 Linux 驱动 系统里的样子
ACM 0x02 串口（调制解调器） cdc_acm /dev/ttyACM0
ECM 0x06 以太网卡 cdc_ether usb0 / eth1
NCM 0x0D 以太网卡（聚合版） cdc_ncm wwan0 / usb0
OBEX 0x0B 对象交换（红外那套） cdc_obex 少见
WDM 0x09 拨号终端设备 cdc-wdm /dev/cdc-wdm0，给 4G 模块用
Ethernet Emulation Model 0x0C 以太网（简化版） cdc_subset 少见的轻量设备

ACM 是最常见的一个。绝大多数单片机开发板、Arduino、ST-Link、J-Link、USB 转串口模块，插上来就是一个 ttyACM 设备。原因是实现简单：设备侧只要一对 Bulk 端点搬字节流，再加一个中断端点报线状态，就能用了。

ECM 是第二个。USB 转以太网芯片（RTL8152 那类）走的就是它。插上之后不需要额外驱动，多一块网卡，ifconfig 能看见。工程上管这叫「免驱网卡」。

NCM 是 ECM 的进化版。它解决的问题是：ECM 一个 USB 传输只搬一个以太网帧，小包场景下 USB 开销大得离谱。NCM 把多个帧塞进一个 NTB 里一次搬完，传输次数降一个量级。4G/5G 模块、USB 3.0 网卡基本都用它。

WDM 得单说一句，因为它和 4G 模块强绑定。cdc-wdm 不是网卡也不是串口，是一条「控制通道」，专门收发 QMI/MBIM 这类管理命令。数据还是走 NCM 或者 ECM，一块网卡一个 /dev/cdc-wdm0，两个配合用。

OBEX 和 EEM 在 PC 侧基本碰不到。EEM 是 ECM 的精简变体，省掉了不少可选功能描述符；OBEX 是当年红外和蓝牙传文件那套，现在只有老设备上还有。

三个子类的共性回到一句话：都是 CDC，都有通信接口管控制，都有数据接口搬数据。差别只在数据接口上搬的东西怎么组织。

四、ACM：把 USB 当串口 #

ACM 全称 Abstract Control Model，抽象控制模型。抽象在哪？它不假定对面是真 modem，只假定对面能收 AT 命令、能配波特率、能报线状态。真串口能做到，虚拟串口也能做到，于是两者共用一套接口。

设备侧要提供的东西不多：

  1. 一个通信接口，子类 0x02，协议 0x01（AT 命令集）。挂一个中断 IN 端点。
  2. 一个数据接口，类 0x0A。挂一对 Bulk 端点。
  3. CDC Union 把这两个接口绑一起。
  4. CDC ACM 功能描述符，声明自己支持哪些能力。

主机侧看到的 /dev/ttyACM0 就是这么来的。open、read、write、ioctl、tcsetattr 全都能用，stty 也能改波特率。应用层代码一行不用改，原来的串口程序直接跑。写数据是 write() 进 TTY 层，TTY 层交给 cdc_acm，cdc_acm 组 URB 发 Bulk OUT。读数据反过来：Bulk IN 的 URB 常驻提交，回来一包就丢进 TTY 的 flip buffer，read() 从里面取。

有几件事它做不到或者做不好，得提前知道：

  • 波特率是假的。USB 全速 12Mbps，实际吞吐跟波特率无关。你 stty 设成 9600，数据照样按 USB 的速度跑。设这个值只是让设备侧知道「假装是 9600」，有些设备会据此决定行为。
  • 没有真正的流控。RTS/CTS 是虚拟的，靠类通知传，不是物理线。硬件流控指望不上，只能靠应用层协议自己收着发。
  • 延迟不稳定。批量传输的调度受总线负载影响，不像真串口那样有确定的字节间隔。做时序敏感的东西要小心。
  • break 信号能发。这是 ACM 少数比真串口还标准的点，tcsendbreak() 走类请求发到设备，设备该输出一段 logic zero。

一个典型场景是调试串口。板子上的 UART 通过 CDC-ACM 转到 USB，PC 上 minicom -D /dev/ttyACM0 直接用。速度快、不需要 USB 转串口芯片、还能顺便收 log。另一个场景是给没有串口的设备加一条带外通道：正常工作时跑业务，出错时通过同一根 USB 线上的 ACM 接口吐诊断信息，两个接口在同一个配置里，互不干扰。

/dev/ttyACM0 这个编号不是固定的。同时插两个 ACM 设备，谁先枚举谁拿 0。要稳定，用 /dev/serial/by-id/ 下面的软链接，那里带序列号。

五、ACM 驱动的实现 #

源码在 drivers/usb/class/cdc-acm.c。这个名字值得记，因为它是 CDC 里唯一一个不在 drivers/net/usb/ 下的驱动——ACM 属于 TTY 子系统，跟网络没关系。

整体分两步走，这个顺序是理解 ACM 的钥匙。

第一步，module_init 注册 tty_driver。 此时驱动已经挂进 TTY 子系统，但对用户空间毫无意义。为什么？因为还没有对应的 tty_device。tty_driver 是「一类设备」的模板，tty_device 是「一个具体设备」的实例。没有实例，就不会创建设备节点。

第二步，usb_driver 的 probe 里注册 tty_device。 设备插上，USB 核心匹配到 cdc_acm 的 usb_driver，调 probe。probe 走完，才调：

c
tty_register_device(acm_tty_driver, minor, &control_interface->dev);

这一句是关键。它把 tty_driver 和一个具体设备绑起来，创建设备节点。从这一刻起，/dev/ttyACM0 才存在，用户空间才访问得到。

probe 中间还有一步不能漏。ACM 设备有两个接口，但 usb_driver 的 probe 只会因为一个接口被调——多半是通信接口（接口 0）。数据接口（接口 1）得驱动自己去认领：

c
usb_driver_claim_interface(&acm_driver, data_interface, acm);

这句的作用是让数据接口也归属 cdc_acm。不认领的话，数据接口会被 USB 核心当成未绑定接口，要么没人管，要么被别的驱动抢走，数据通路就断了。

认领哪个接口？靠 CDC Union 里的 bSlaveInterface。前面描述符例子里是 1，所以认领接口 1。这个数字不能写死，得从描述符里读。

probe 结束时手里有三个端点，三个各有各的用法：

端点 类型 什么时候动 干什么
Epcontrol Interrupt IN tty_open 时提交 URB 常驻监听类通知，报串口线状态变化
Epread Bulk IN tty_open 时提交 URB 收数据，回调里推给 TTY flip buffer
Epwrite Bulk OUT tty_write 时组 URB 发数据

Epcontrol 的 URB 一提交就常驻，设备有事件就回一包，回调处理完再重新提交。这是 ACM 能感知「对端 DTR 拉起来了」「线断了」的唯一途径。

Epread 的 URB 同样常驻。它回来的每一包，回调里都调一次：

c
tty_flip_buffer_push(&acm->port);

数据先进 flip buffer，read() 再从 flip buffer 取。中间这层缓冲是 TTY 子系统的常规做法，不是 ACM 特有。

写路径短得多。tty_write 进来，cdc_acm 分配 URB、填数据、usb_submit_urb，完成回调里释放。没有队列，没有聚合，一次 write 对一次传输。

然后是一组 tty_operations，逐个说清它们各自对应哪条 CDC 类请求。

回调 触发方式 干的事
acm_tty_open open("/dev/ttyACM0") 提交 Epcontrol 和 Epread 的 URB
acm_tty_close close() 撤销 URB，清状态
acm_tty_write write() 组 URB 发 Bulk OUT
acm_tty_throttle flip buffer 满 停止提交新的 read URB
acm_tty_unthrottle flip buffer 有空位 恢复提交 read URB
acm_tty_break_ctl tcsendbreak() 发 break 类请求
acm_tty_tiocmset ioctl(TIOCMBIS/TIOCMBIC) 置位/清位 RTS、DTR 等调制解调器信号
acm_tty_tiocmget ioctl(TIOCMGET) 读回当前信号状态
acm_tty_set_termios tcsetattr() 设波特率、数据位、校验位、停止位

throttle 和 unthrottle 这一对值得单独讲，因为它是 TTY 层的流控机制，很多人调 ACM 吞吐时栽在这。

机制是这样：翻转缓冲（flip buffer）容量有限。如果应用层读得慢，Epread 的 URB 还在不停回数据，flip buffer 迟早溢出，数据就丢了。acm_tty_throttle 的作用就是踩刹车——在最后一次 read URB 的回调里判断，如果发现 buffer 快满了，就不再提交新的 read URB。等应用层把数据读走，flip buffer 腾出空间，acm_tty_unthrottle 被调用，才恢复提交。

所以一个现象就好解释了：应用层不读，设备侧发不动。不是设备坏了，是 throttle 生效了。调试时 cat /dev/ttyACM0 卡住不动，往往就是这个原因。

break_ctl 对应 RS232 的 break 语义。规范里说得很清楚：收到 break 信号后，要 output 一段时间的 logic zero。串口上这就是把 TX 线拉低几百毫秒，接收方会读到一个全零字节加帧错误。虚拟串口照做，走一条类请求通知设备。

tiocmset / tiocmget 管的是 RS232 那几根硬件握手线。能设的位包括 RTS、DTR，能读的包括 CTS、DSR、DCD、RI。虚拟串口没有物理线，全靠在 CDC Notify Serial State 通知里带过来。所以这两个 ioctl 本质是「查一下设备有没有在通知里报过这个信号」。

set_termios 管串口传输特性：波特率、数据位、停止位、奇偶校验。实现上就是打包一个 SET_LINE_CODING 类请求，7 个字节，往通信接口的控制端点发。设备收到后自己决定怎么处理——真串口改分频器，虚拟串口直接忽略。

看一遍 ACM 的完整数据流，把上面这些串起来。

text
写入：
  write(/dev/ttyACM0) → TTY 层 → acm_tty_write → usb_submit_urb(Bulk OUT)
                                                  → 完成回调，释放 URB
读出：
  usb_submit_urb(Bulk IN, 常驻)
    → 回调 → tty_flip_buffer_push()
      → flip buffer 满 → acm_tty_throttle → 停止提交
      → read() 取走 → acm_tty_unthrottle → 恢复提交
控制：
  设备有事件 → 中断端点回包 → 回调解析类通知
    → 线状态变化 → 更新 port 状态，唤醒等待的进程
    → 串口信号变化 → 记录，供 tiocmget 查询

六、ECM：把 USB 当网卡 #

ECM 全称 Ethernet Networking Control Model，以太网控制模型。规范 3.8.2 节的原话大意是：用于在主从设备间交换以太网帧数据；通信接口负责配置和管理以太网功能，数据接口负责在总线上交换封装了完整以太网包的 USB 数据包。

这段话里有三个技术点，每个都影响实现。

第一，数据接口搬的是「完整的以太网帧」。 一个 USB 传输，帧头到帧尾，中间不切。对端收到就知道这是一帧的边界。这跟 ACM 完全不同——ACM 的字节流没有边界，靠上层协议自己找。 第二，CRC 校验和不能包含在传输的数据里。 以太网的 FCS 是 4 字节，硬件算的。走 USB 传输时这 4 字节要去掉，因为 USB 自己有 CRC，再带一层纯属浪费。接收侧补回来。这条在规范里写死了，实现时容易忘。

第三，校验失败的帧不能再发给主机。 规范明确要求：检验失败的帧数据不能发送到主机，这意味着设备必须能够缓冲至少一个完整的以太网帧。为什么？因为帧在接收时 CRC 错了，得整帧丢掉，不能收一半就往上送。这就逼着设备侧至少有帧级别的缓冲。

这三条加起来，ECM 的语义就成了：一帧一个 USB 传输，帧不完整不发，错帧不发。

规范还提了一句网络管理的现实问题：USB 虚拟网络接口一直保持连接状态，但某些网络管理操作需要正确初始化设备和主机两边的网络栈，也会出现配置或状态的偶然变化，比如增加组播过滤器。这话的意思是——链路是常连的，但「链路状态」和「过滤规则」这些是可以变的，得走控制通道改。

ECM 的类请求都走通信接口，规范表 10 列了一组，常用的几个：

类请求 方向 干什么
SET_ETHERNET_MULTICAST_FILTERS 主机到设备 设组播过滤表
SET_ETHERNET_POWER_MANAGEMENT_PATTERN_FILTER 主机到设备 设唤醒模式过滤
GET_ETHERNET_POWER_MANAGEMENT_PATTERN_FILTER 设备到主机 读唤醒模式
SET_ETHERNET_PACKET_FILTER 主机到设备 设包过滤（全收/只收自己/广播/组播/混杂）
GET_ETHERNET_STATISTIC 设备到主机 读统计计数

SET_ETHERNET_PACKET_FILTER 是这里面最常用的一个。混杂模式（promiscuous）就是靠它开的——tcpdump 想抓到不是发给自己的包，得让设备把过滤关掉。

七、ECM 的配置与使用 #

内核里得先把驱动编进去。路径在 Device Drivers → Network device support → USB Network Adapters：

text
Device Drivers  --->
    [*] Network device support  --->
        USB Network Adapters  --->
            <*> Multi-purpose USB Networking Framework
            -*-   CDC Ethernet support (smart devices such as cable modems)

两个选项的关系要看清：

  • Multi-purpose USB Networking Framework 就是 usbnet，是框架本体，必须编进去。
  • CDC Ethernet support 就是 cdc_ether，依赖 usbnet，所以它显示成 -*-（被别的选项选中的依赖状态）而不是 <*>。

省事的话直接开 CONFIG_USB_USBNET 和 CONFIG_USB_NET_CDCETHER，别的不用管。

插上一块 RTL8152B 的免驱网卡，dmesg 长这样：

text
usb 1-1: new full speed USB device using s3c2410-ohci and address 3
usb 1-1: New USB device found, idVendor=0bda, idProduct=8152
usb 1-1: New USB device strings: Mfr=1, Product=2, SerialNumber=3
usb 1-1: Product: USB 10/100 LAN
usb 1-1: Manufacturer: Realtek
usb 1-1: SerialNumber: 00E04C36004F
usb 1-1: configuration #2 chosen from 2 choices
eth1: register 'cdc_ether' at usb-s3c24xx-1, CDC Ethernet Device, 00:e0:4c:36:00:4f

逐行读一遍，信息量不小。

new full speed USB device — 全速设备，12Mbps。这是 RTL8152B 接在 OHCI 控制器上的结果，说明这块芯片跑全速也够用。

idVendor=0bda, idProduct=8152 — Realtek 的 VID，8152 是芯片型号。

configuration #2 chosen from 2 choices — 设备有两个配置，选了第 2 个。注意这点：ECM 功能不一定在第一个配置里，选错了配置就找不到网卡。

eth1: register 'cdc_ether' — 关键行。cdc_ether 是驱动名，eth1 是分配到的网络接口名，后面跟 MAC 地址 00:e0:4c:36:00:4f。MAC 是从设备的 CDC Ethernet Networking 功能描述符里的 iMACAddress 字符串读出来的。

然后就没有然后了。ifconfig eth1 up、dhclient eth1，它跟一块插在 PCI 上的网卡没任何区别。这就是 ECM 的价值——网络子系统完全不知道底下是 USB。

cdc_ether.c 在 drivers/net/usb/ 下。它和传统以太网芯片驱动长得完全不一样。传统驱动要实现 xxx_open()、xxx_stop()、xxx_tx()、xxx_hard_header()、xxx_get_stats()、xxx_tx_timeout() 这一长串，因为网卡寄存器、DMA 描述符、中断都得自己管。

cdc_ether 一个都不实现。它只填 4 个回调，交给 usbnet 去调：

回调 干什么
usbnet_generic_cdc_bind 通用 CDC 绑定，解析功能描述符、找数据接口、拿 MAC
usbnet_cdc_bind ECM 专属绑定，接在通用绑定后面
usbnet_cdc_unbind 解绑，释放绑定阶段拿的资源
usbnet_cdc_status 处理中断端点上来的类通知

这 4 个就是 cdc_ether 的全部。剩下的 net_device 注册、收发队列、URB 管理、PHY 状态，全是 usbnet 干的。

配置阶段最容易踩的坑按出现频率排一下。

坑一：cdc_ether 没编进内核。 dmesg 里能看到设备枚举成功，USB 层认得它，就是不出现网卡。用 lsusb -t 看，接口后面是空的，没有 Driver=。原因是内核配置里 CONFIG_USB_NET_CDCETHER 是 n 或者没选。

坑二：设备声明成厂商私有类，不是 CDC。 不少 USB 网卡芯片出厂时描述符写的是 bInterfaceClass=0xFF（厂商自定义），靠 VID/PID 匹配专用驱动。这种设备插上不会有 cdc_ether，lsusb -t 能看到接口没绑定。要么装厂商驱动，要么改描述符。

坑三：选错配置。 设备有多个 configuration，ECM 功能在配置 2 里，内核默认选了配置 1。日志里 configuration #1 chosen from 2 choices 而网卡不出现，就是这个。可以试 echo 2 > /sys/bus/usb/devices/1-1/bConfigurationValue。

坑四：RNDIS 和 ECM 混了。 Windows 上免驱网卡走的是 RNDIS（微软自己的标准），Linux 上走 ECM。同一个硬件两种模式，靠设备侧的切换命令或者不同的配置。设备默认给 RNDIS，Linux 上就认不出来。

坑五：MAC 地址全是 0 或者重复。 有些便宜模块的 iMACAddress 写死成 00:00:00:00:00:00。内核会给它随机生成一个，但每次插都不一样。多个同样的模块同时接入，容易撞地址。得在设备侧或者 udev 规则里改。

cdc_ether 不需要添加 VID/PID 就能用，这是它和专用驱动的本质区别——它匹配的是接口类，不是具体设备。这条是 ECM 被称为「免驱」的技术根据。

八、NCM：更高效的以太网 #

NCM 全称 Network Control Model，网络控制模型，子类码 0x0D。它是 ECM 的升级版，解决的问题只有一个：ECM 的 USB 传输效率太低。

算笔账就明白。ECM 一个 USB 传输搬一个以太网帧。一个 64 字节的小包（ACK、ping、TCP 握手），在高速模式下要占一个 512 字节的 Bulk 传输配额。USB 协议本身有握手包、有令牌包，一次传输的实际开销远超 64 字节的载荷。小包多了，总线全在做无用功。

NCM 的解法是聚合。把多个以太网帧打包成一个 NTB（NCM Transfer Block），一次 USB 传输搬走。64 个 64 字节的包，一次传输解决，USB 的开销只付一次。

NTB 的结构是三层：

text
NTB = NTH + NDP + datapayload

NTH（NCM Transfer Header）
  固定 12 字节，描述整个 NTB 的长度和内部 NDP 的位置
  
NDP（NCM Datagram Pointer）
  描述符数组，每个 entry 是一个 datagram 的 index + length
  告诉接收方：payload 里第几个字节到第几个字节是一帧

datapayload
  真正的以太网帧，一个接一个紧挨着放

Linux 侧的格式就是 NTH + NDP + datapayload，NDP 里含 n 个 datagram 的（index, len）对。

数据结构对得上：

c
struct usb_cdc_ncm_nth16 {
    __le32 dwSignature;    /* "NCMH" */
    __le16 wHeaderLength;
    __le16 wSequence;
    __le16 wBlockLength;
    __le16 wNdpIndex;      /* 第一个 NDP 在 NTB 里的偏移 */
} __packed;

struct usb_cdc_ncm_ndp16 {
    __le32 dwSignature;    /* "NCM0" */
    __le16 wLength;        /* NDP 总长，含所有 dpe */
    __le16 wNextNdpIndex;
    struct usb_cdc_ncm_dpe16 dpe16[];   /* 变长数组 */
} __packed;

struct usb_cdc_ncm_dpe16 {
    __le16 wDatagramIndex;  /* 该帧在 payload 里的偏移 */
    __le16 wDatagramLength; /* 该帧的长度 */
} __packed;

一个 NTB 可以有多个 NDP（通过 wNextNdpIndex 串起来），但实际驱动基本只用第一个。wBlockLength 是整个 NTB 的长度，接收侧第一件事就是校验它。

驱动整体分三层，调用关系是单向的：

text
cdc_ncm  →  usbnet device  →  net_device
   具体实现      通用框架        网络子系统

cdc_ncm 只管 NTB 的打包和解包，别的全交给 usbnet 和网络子系统。

枚举流程从 probe 开始：

cdc_ncm_probe 直接调 usbnet_probe。 自己没有额外逻辑，把活交出去。usbnet_probe 里分配 net_device 和 usbnet 结构，然后把控制权交回 cdc_ncm 的 bind 回调。

cdc_ncm_bind 解析 NCM 的附加描述符，初始化一个 cdc_ncm_ctx 对象。 这个 ctx 是 cdc_ncm 的私有数据，装着 NTB 的参数、收发缓冲、状态标志。NCM 的 CDC NCM 功能描述符里有几个字段直接决定 ctx 的配置：wNtbOutMaxSize（设备能收的最大 NTB）、wNdpOutPayloadRemainder（对齐余数）、wMaxDatagramSize。

接着调 init_status，给中断端点分配 URB。 这是通信接口上那个中断 IN 端点，专门收类通知。URB 提交后常驻，每回一包就进 complete 回调。

中断回调里交给 cdc_ncm_status 处理。 主要两种 event：

USB_CDC_NOTIFY_NETWORK_CONNECTION：根据 wValue 判断是 connect 还是 disconnect，然后调 netif_carrier_on / netif_carrier_off 通知上层。上层看到的是「网线插上了/拔掉了」。这是链路状态，不是接口 up/down。

USB_CDC_NOTIFY_SPEED_CHANGE：简单地打印一句 log 而已。规范里这个通知本来是上报上下行速率的，Linux 侧没拿它做实际的事。

最后注册 net_device，走 register_netdev 和 netif_device_attach。到这一步，ip link 就能看到这块网卡了。

几个辅助函数也顺手说一下。

cdc_ncm_check_connect 在 ifconfig 到 net_device 的 open 函数时被调用，判断 ctx 是否为空。为什么？因为设备 disconnect 的时候，ctx 会被设成 NULL。不检查就解引用，直接 oops。

cdc_ncm_manage_power 用来开/关 remote wakeup。链路空闲时让设备进低功耗，有包来的时候设备自己唤醒主机。

接收流程是一条完整链路，从 rx_submit 到 netif_rx。

text
rx_submit
  → alloc_skb → usb_fill_bulk_urb → usb_submit_urb
      submit 成功 → skb 挂到 rxq 上
rx_complete
  → state = rx_done
  → urb->status == 0（成功）→ state = rx_cleanup
  → defer_bh：skb 从 rxq 移除，挂到 done 链表
      done 的 qlen == 1 → tasklet_schedule(&dev->bh)
usbnet_bh
  → 从 done 里 dequeue 一个 skb
  → state == rx_done    → 置 rx_cleanup，调 rx_process
  → state == rx_cleanup → free_urb，free_skb
rx_process
  → 调 driver_info->rx_fixup（这里是 cdc_ncm_rx_fixup）
  → 设了 FLAG_MULTI_PACKET → 直接 dev_kfree_skb_any 释放
  → 没设 → usbnet_skb_return

FLAG_MULTI_PACKET 是个关键标志。设了它，说明驱动会在 rx_fixup 里自己把 skb 拆开、自己往上送，usbnet 就不用再帮忙送一次，只负责释放原始 skb。NCM 必须设，因为一个 NTB 里有多帧。

cdc_ncm_rx_fixup 是解包的核心，七步：

一、 从 NTH 里取 wBlockLength（NTB 长度），如果大于驱动支持的最大 size，返回错误。这一步是防设备乱来。

二、 解析 NTH 里的 wNdpIndex，取得第一个 NDP 的索引。

三、 memcpy，把第一个 NDP 拷贝到 ctx->rx_ncm.ndp16 里。为什么要拷贝？因为 NTH 和 NDP 在原始 skb 里的位置不保证对齐，拷到结构体里访问更安全。

四、 解析 NDP。NDP 包含一个或多个 dpe，每个 dpe 对应一个以太网帧。先算帧数：

c
nframes = ((le16_to_cpu(ctx->rx_ncm.ndp16.wLength) -
            sizeof(struct usb_cdc_ncm_ndp16)) /
            sizeof(struct usb_cdc_ncm_dpe16));

wLength 是 NDP 的总长，减去 NDP 头部的固定长度，剩下的全是 dpe，一个 dpe 16 字节，除一下就得到帧数。

五、 判断 nframes 是否大于 CDC_NCM_DPT_DATAGRAMS_MAX，超了就截断到 CDC_NCM_DPT_DATAGRAMS_MAX。这是防设备一次塞太多帧把驱动缓冲冲爆。

六、 把所有 dpe 都拷贝到 ctx->rx_ncm.dpe16 里。

七、 一个 for 循环遍历每个 dpe。对每个 dpe 调 skb_clone 创建一个 skb 备份，然后调 usbnet_skb_return，最终通过 netif_rx 把 datapayload 里的数据提交给网络子系统。

skb_clone 而不是 skb_copy，是因为原始 skb 里装着整个 NTB，各帧共享底层数据区，克隆只复制元数据，省内存。

发送流程反过来走一遍。

起点是 net_device 的 ndo_start_xmit。 网络栈要发一个 skb，调它。

第一步，调 cdc_ncm 的 tx_fixup。 cdc_ncm_tx_fixup 里调 cdc_ncm_fill_tx_frame，把上层传下来的 skb 转成 NTB。上层的 skb 只有一帧，这里要判断是攒着还是立刻发——攒的话把帧追加到已有的 NTB 后面，等条件满足一次发出去。这就是聚合发生的地方。

第二步，创建 URB，在 skb->cb 里创建 skb_data。 skb->cb 是 skb 的私有控制区，usbnet 拿它挂自己的收发元数据。然后处理 ZLP——有些设备要求发送一个 zero packet 作为结束请求，特别当 NTB 长度正好是端点的整数倍时，必须补一个空包，否则设备不知道该结束了。

第三步，提交 URB。 成功返回后把对应的 skb 加到 txq。如果 txq 里的 skb 数量超过 maxSegmentSize，调 netif_stop_queue 告诉上层别再发了，快爆了。

恢复靠 tx_complete。 URB 完成回调里最后调 usbnet_bh，usbnet_bh 判断出 txq 里的 skb 少于 maxSegmentSize 后，调 netif_wake_queue 恢复上层的数据传送。

这一停一启就是 usbnet 的流控，跟 ACM 的 throttle/unthrottle 是同一个思路——底下处理不过来就踩刹车，缓过来就松开。区别在 ACM 踩在 TTY 的 flip buffer 上，网卡踩在 usbnet 的 txq 上。

九、NCM 与 ECM 的差别 #

两个子类都是「USB 网卡」，表面上用起来一模一样：插上多一块网卡，ifconfig 能看见，能配 IP。底下差得远。

核心差别就一条：ECM 一个 USB 传输搬一个以太网帧，NCM 一个 USB 传输搬一整个 NTB。

维度 ECM NCM
子类码 0x06 0x0D
传输单元 一个以太网帧 一个 NTB（多帧聚合）
聚合 无 有，NDP 索引定位每帧
小包场景开销 大，每帧一次传输 小，多帧一次传输
中断通知频率 相对高 相对低
描述符复杂度 简单 复杂，要协商 NTB 参数
驱动文件 cdc_ether.c cdc_ncm.c
典型场景 10/100M 网卡、嵌入式 4G/5G 模块、USB 3.0 网卡

传输次数降下来，两件事同时改善。一是总线利用率，USB 的令牌包和握手包开销被摊薄。二是中断次数，每次传输完成要处理一次完成回调，传输少了回调就少了，CPU 在中断上下文里的时间跟着降。这就是 NCM 存在的全部理由。

不过 NCM 的复杂度也是真的。ECM 的驱动拿到一个 Bulk 包，包就是帧，交上去完事。NCM 的驱动拿到一个 Bulk 包，得先解析 NTH、再解析 NDP、再按 dpe 逐个切帧、逐帧 skb_clone 往上送。多出来的每一步都是出错点——NTB 长度不对、NDP 偏移越界、dpe 数量超限，任何一种都会让包丢掉。

参数协商也更麻烦。NCM 的 CDC NCM 功能描述符里有一组字段，主机和设备得就这些参数达成一致才能工作：

字段 作用
wNtbOutMaxSize 设备能接收的最大 NTB 长度
wNdpOutPayloadRemainder payload 起始位置相对 NDP 的对齐余数
wNdpOutAlignment NDP 的对齐要求
wMaxDatagramSize 单个 datagram（帧）的最大长度
bmNetworkCapabilities 能力位图，比如是否支持 NTB 输入格式

ECM 没有这些。ECM 的描述符里就一个 MAC 地址和一个统计位图，剩下的靠约定。

选哪个？看包大小分布。大包为主（文件传输、视频流），ECM 和 NCM 差别不大，一帧本来就接近端点包大小，聚合省不下多少。小包为主（TCP 短连接、大量 ACK、游戏、SSH 交互），NCM 优势明显。

还有一个现实因素：兼容性。ECM 出现早，几乎所有系统都认，包括很老的内核和嵌入式 RTOS。NCM 支持晚一些，某些精简系统上没编。做产品时如果目标平台不确定，ECM 更保险；确定了是主流 Linux 或 Windows 10 以上，NCM 更合适。

顺带说一句 Windows。Windows 上免驱网卡走的是 RNDIS 和 CDC-NCM（Win10 之后原生支持 NCM），ECM 反而支持得不好——Windows 从来没认真实现过 ECM。所以同一块硬件，插 Linux 跑 ECM 或 NCM，插 Windows 跑 RNDIS 或 NCM。做双系统兼容的产品，NCM 是交集。

十、cdc_ether 与 usbnet 的关系 #

这一章讲清楚 drivers/net/usb/ 这一层的组织结构，看完就不会再搞混哪个文件干什么。

usbnet 是框架，一个通用的「USB 网卡」抽象层。它把 USB 网卡这件事里所有共通的部分都做完了：

  • 网络接口的注册与管理，net_device 的分配、注册、注销
  • 收发队列，rxq、txq、done 三条链表
  • URB 的分配、提交、回收，收发两个方向的完整生命周期
  • 底半部处理，usbnet_bh 那个 tasklet
  • 链路状态，netif_carrier_on / netif_carrier_off 的调用时机
  • 统计计数，net_device_stats 的维护
  • 电源管理，remote wakeup 的开关
  • 队列流控，netif_stop_queue / netif_wake_queue

这些跟具体是 ECM 还是 NCM 没有任何关系，所以抽出来做成框架。具体驱动只需要填 usbnet 留出的回调。

usbnet 的核心是一个 driver_info 结构，每个具体驱动填一份：

回调 什么时候被调 具体驱动要做什么
bind probe 阶段 解析自己的附加描述符，分配私有 ctx
unbind disconnect 阶段 释放 bind 阶段拿的资源
rx_fixup 收到数据后 把 USB 包转成以太网帧，往上送
tx_fixup 要发数据时 把以太网帧转成 USB 包
status 中断端点有通知 解析类通知，更新链路状态
manage_power 电源管理 开关 remote wakeup

这张表就是「具体实现」和「通用框架」的分界线。左边是 usbnet 提供的骨架，右边是每个驱动自己填的肉。

drivers/net/usb/ 下的几个 CDC 驱动，全是 usbnet 的具体实现：

驱动文件 对应子类 填的回调 特点
cdc_ether.c ECM usbnet_generic_cdc_bind、usbnet_cdc_bind、usbnet_cdc_unbind、usbnet_cdc_status 一帧一传输，最简单
cdc_ncm.c NCM cdc_ncm_bind、cdc_ncm_unbind、cdc_ncm_rx_fixup、cdc_ncm_tx_fixup、cdc_ncm_status、cdc_ncm_manage_power NTB 聚合，回调最多
cdc_subset.c 厂商私有 CDC 复用 cdc_ether 的那几个 描述符不合规的兼容层
cdc_mbim.c MBIM 自己的整套 4G 模块的管理协议
rndis_host.c RNDIS 自己的整套 微软的标准
cdc_eem.c EEM 自己的收发 ECM 的精简变体

cdc_subset.c 值得单独提一句。它的存在是因为现实世界里一堆设备的描述符写法不合规范——该有的功能描述符没有，该声明的子类没声明，但数据面行为又确实是 ECM 那一套。cdc_subset 就是个宽容的兼容层，不较真描述符，能通就行。

cdc_ncm 的回调数量比 cdc_ether 多，原因前面说过：NTB 的打包解包是它自己的活，usbnet 帮不上忙。cdc_ether 那边，一帧就是一个 USB 包，usbnet 的默认处理基本够用，所以只要 4 个回调。

调用关系拉直了看，一共五层，每层只跟上下相邻的层说话：

text
网络子系统     netif_rx / dev_queue_xmit
     ↓
net_device     usbnet 注册的那块网卡
     ↓
usbnet         队列 rxq/txq/done、URB 生命周期、usbnet_bh
     ↓ driver_info 回调
cdc_ether      只填 bind/unbind/rx_fixup/tx_fixup/status
cdc_ncm
     ↓
USB 核心       主机控制器

看这张图就明白为什么 cdc_ether 只有 4 个函数：中间那一整层都被 usbnet 吃掉了。

反过来说，写一个自己的 USB 网卡驱动，步骤就是：挑一个最像的现有驱动做模板，填 driver_info 里的回调，注册 usb_driver。不用从头实现 ndo_start_xmit、不用管 URB 回收、不用写 tasklet。这是 usbnet 框架省下的活。

十一、三个子类的选型 #

三个子类，选哪个取决于你要模拟什么，以及对面是什么系统。

先按用途分：

你要的 选 系统里的样子 关键理由
一条能收发字节的通道 ACM /dev/ttyACM0 现成串口程序直接跑，不用改代码
一块能配 IP 的网卡 ECM 或 NCM usb0 / eth1 / wwan0 直接进网络栈，TCP/IP 全都白送
4G/5G 模块的管理通道 WDM + NCM /dev/cdc-wdm0 + 网卡 QMI/MBIM 走 WDM，数据走 NCM

再按场景细看。

调试通道、命令行交互、传感器数据。 选 ACM。数据量小、有来有回、应用层想用简单的 read/write。minicom、picocom、screen 这些工具全都能用，出问题好排查。

要给设备一个 IP，跑 TCP/IP。 选 ECM 或 NCM。设备侧跑个 lwIP 或者 Linux，主机侧配个网段，两端就能通信。比 ACM 上套一层 SLIP/PPP 干净得多。

高吞吐、小包多。 选 NCM。4G/5G 模块、USB 3.0 网卡都是这个选择。聚合带来的收益在小包场景最明显。

要兼容 Windows。 选 NCM 或 RNDIS，别选 ECM。Windows 对 ECM 的支持一直是缺的。

要兼容最老的内核。 选 ECM。ECM 进内核早，cdc_ether 到处都是。

设备侧资源紧张（MCU、RTOS）。 选 ACM 或 ECM。NCM 要维护 NTB 缓冲，至少要能放下一个最大 NTB 的内存，MCU 上不划算。

这几条能不能做，列成表对照。有些事谁都做不了，别指望。

能力 ACM ECM NCM
字节流传输 是 否（帧为单位） 否（帧为单位）
帧边界 无 有 有
多帧聚合 否 否 是
硬件流控 虚拟 无 无
链路状态通知 串口线状态 网络连接状态 网络连接状态
免驱（Linux） 是 是 是
免驱（Windows） 是 否 是（Win10+）

一个容易忽略的点：ACM 和 ECM/NCM 可以在同一个 USB 设备上共存。复合设备里两个功能各自两个接口，互不干扰。4G 模块就是这么干的——WDM 管控制、NCM 跑数据、有时再加一个 ACM 做 AT 命令通道。

十二、易错点速查 #

这一章按现象查原因。每条都是实际踩过的。

现象：插上设备，没有 /dev/ttyACM0。

查什么 怎么查 结论
内核有没有 cdc_acm ls /sys/bus/usb/drivers/cdc_acm/ 目录不存在说明没编进去
设备有没有绑定驱动 lsusb -t 接口后面没有 Driver=cdc_acm 就是没绑上
描述符对不对 lsusb -v -d VID:PID 看 bInterfaceClass 是不是 2，子类是不是 2
是不是被别的驱动抢了 dmesg | grep cdc_acm 有 ignoring 之类的字样就是被抢了

最常见的原因是设备声明成了厂商私有类（bInterfaceClass=0xFF），靠 VID/PID 匹配专用驱动，cdc_acm 认不出来。

现象：/dev/ttyACM0 出来了，但写进去没反应。

先看 Epwrite 的 Bulk OUT 端点。设备侧如果没在等这个端点上的数据，包发出去会被 NAK 或者直接丢掉。用 usbmon 抓一下，看 OUT 事务有没有 ACK。

再一个，DTR 没拉起来。不少 ACM 设备要等到主机置位 DTR 才开始工作——这是串口的老习惯，用来判断「对面有没有程序在听」。用户态代码里补一句：

c
int fd = open("/dev/ttyACM0", O_RDWR | O_NOCTTY);
int status;
ioctl(fd, TIOCMGET, &status);
status |= TIOCM_DTR;
ioctl(fd, TIOCMSET, &status);

不设 O_NOCTTY 的话，这个 tty 会变成进程的控制终端，Ctrl+C 直接把程序杀掉，看起来像「设备断了」。

现象：cat /dev/ttyACM0 卡住不动。

throttle 生效了，前面讲过。应用层读得慢，flip buffer 满，驱动停掉 read URB。这时候设备侧发数据也发不动——不是设备死机，是主机在背压。

要验证的话，改用 dd if=/dev/ttyACM0 bs=1 count=100 这类定长读，读一点就退出，看数据是不是断断续续地来。持续卡死才是真问题。

现象：网卡没出现，但设备枚举成功。

查什么 怎么查 结论
usbnet 编了没 lsmod | grep usbnet 或看 /sys/bus/usb/drivers/ 框架没编，具体驱动也起不来
cdc_ether 编了没 ls /sys/bus/usb/drivers/cdc_ether/ 没这个目录就是没编
选了哪个配置 dmesg | grep configuration 看是不是选到了没有 ECM 功能的那个配置
接口类是不是 0x0A lsusb -v 数据接口必须是 CDC Data

现象：网卡出现了，但 ifconfig eth1 up 之后不通。

先看 ip link 里 LOWER_UP 有没有——这表示 carrier 状态。没有的话，是设备的 USB_CDC_NOTIFY_NETWORK_CONNECTION 没上报，或者上报的是 disconnect。dmesg 里应该有一行 cdc_ether ... : register 后面跟的链路状态。

再看两端 IP 是不是同一网段。ECM/NCM 没有 DHCP 服务器，除非设备侧跑了一个。手工配：

bash
#主机侧
sudo ip addr add 192.168.7.1/24 dev usb0
sudo ip link set usb0 up

#设备侧（假设设备跑 Linux）
sudo ip addr add 192.168.7.2/24 dev usb0
sudo ip link set usb0 up

ping 不通先看 ARP：ip neigh show dev usb0。没有 ARP 表项，说明链路层就没通。

现象：MAC 地址每次插都不一样。

设备的 iMACAddress 字符串没写或者写成了全零。内核检测到无效 MAC 会随机生成一个。修法有两个：设备侧把 MAC 烧进描述符；或者 udev 规则里固定。

bash
#/etc/udev/rules.d/70-usbnet-mac.rules
ACTION=="add", SUBSYSTEM=="net", ATTRS{idVendor}=="0bda", ATTRS{idProduct}=="8152", \
  ATTR{address}=="00:e0:4c:36:00:4f"

现象：NCM 网卡能 up，但大包丢。

看 NTB 长度。wNtbOutMaxSize 是设备声明的能力上限，驱动发出去的 NTB 不能超这个值。超了设备会丢掉整块。抓 usbmon 看每次传输的字节数，和描述符里的 wNtbOutMaxSize 对比。

还有一个 ZLP 的坑。NTB 长度正好是端点包大小的整数倍时，不发 ZLP 设备就不知道该结束了，会一直等下一段数据。这种问题表现为「小包通、大包卡」，因为小包不会正好凑成整数倍。

现象：dmesg 里刷 cdc_acm 的 urb status -71 之类。

-71 是 -EPROTO，协议错误。USB 线上信号质量差、线太长、供电不足都会引起。先换根短一点的线，再换个带供电的 HUB。

-110 是 -ETIMEDOUT，超时。端点没响应，设备侧卡死了或者端点配置错了。

-19 是 -ENODEV，设备被拔了。这个正常，disconnect 时会出现。

现象：两个同样的设备，/dev/ttyACM0 和 /dev/ttyACM1 每次上电顺序不定。

用 /dev/serial/by-id/ 下面的软链接，那个带序列号：

bash
ls -l /dev/serial/by-id/
#usb-FTDI_FT232R_USB_UART_A12345-if00-port0 -> ../../ttyUSB0
#usb-STM32_Virtual_ComPort_123456-if00 -> ../../ttyACM0

设备序列号得是唯一的。便宜模块经常序列号全一样，那就没法区分，只能在 udev 里按 USB 端口路径（ID_PATH）绑。

最后一张表，把三个子类的驱动文件位置和关键函数摆一处，方便翻代码时定位。

子类 源码 注册的东西 关键入口 子系统
ACM drivers/usb/class/cdc-acm.c tty_driver + tty_device tty_register_device TTY
ECM drivers/net/usb/cdc_ether.c net_device（经 usbnet） usbnet_probe 网络
NCM drivers/net/usb/cdc_ncm.c net_device（经 usbnet） usbnet_probe 网络
通用框架 drivers/net/usb/usbnet.c 无（框架） usbnet_probe 网络

记住一句话就够用：ACM 注册 tty，ECM/NCM 注册 net_device。两个子系统，两套规矩，CDC 只是把 USB 翻译成它们各自认识的样子。
