这一篇讲设备侧。同目录另外四篇讲的是主机侧——你在 PC 或板子上写一个 USB 主机驱动，去识别一个插上来的设备。方向正好相反：这里是我们自己的板子插到 PC 上，让 PC 认出它。

说白了，让一块跑 Linux 的开发板扮演 U 盘、网卡、串口，被 Windows 或 Linux 主机正常枚举、正常读写。整篇围绕 Linux 的 gadget 框架展开，从三层架构讲到 Mass Storage 协议栈、Bulk-Only 传输、SCSI 命令集，再讲一个完整 gadget 项目的代码分析。

不讲什么：不展开 USB 主机侧驱动框架（那是同目录其他篇的内容），不讲 USB 电气层与信号完整性,不逐行解读 S3C2410 的寄存器手册。控制器相关的硬件细节能省就省，重点在软件结构。

跨篇指路：想写主机侧驱动，去看《编写USB 驱动程序》；想弄明白热插拔与枚举的主机视角，看《热插拔那点事》；CDC 类与自定义 Bulk 各有专篇，本篇只在网卡功能上碰一下 CDC Ethernet 和 RNDIS。

一、gadget 是什么：主机侧与外设侧 #

任何一个 USB 连接都有两端。一端是主机（Host），掌握总线，发令牌包、发命令、管供电。另一端是设备（Device），只能应答。

大部分时候我们写的是主机侧代码：PC 上插一个摄像头，写个驱动去认它。这时候 USB 控制器工作在 Host 模式。

设备侧反过来。板子上的 USB 控制器工作在 Device 模式，它必须自己维护描述符、自己响应主机发来的标准请求、自己处理枚举。所有 USB 通讯的设备端都有 usb device 程序，业内叫它 usb 固件。

功能简单的设备用专用可编程 USB 控制器就够了。但在跑了 Linux 这种复杂系统的板子上写 usb device 程序，要求你同时熟悉两件事：usb device 控制器的操作，以及操作系统的驱动架构。

Linux 把这套东西抽象成了 gadget 框架。

能拿来做什么 #

模拟 U 盘。产品里的一块存储设备,或者某个分区,可以被 PC 识别成一个 U 盘。手机连电脑弹出「便携设备」就是这个路子。文件交互不用装驱动,不用开网络。

USB 网卡。设备通过 USB 连到 PC 后,PC 端多出一个网络连接,板子上多出一个网卡设备。两边配上 IP 就能通,俗称 USBNET。调试板子时这条链路比串口好用,能传文件、能跑 NFS、能开 ssh。

USB 串口。板子上没有串口芯片,一个 gadget 驱动就能把 USB 变成 tty。

为什么不该「直接写固件」 #

裸机上写 usb device 是写一个状态机:上电、等复位、收 SETUP 包、回描述符、进配置、开端点、搬数据,全手写。

在 Linux 上还这么干,等于把内核里现成的枚举逻辑、描述符管理、端点队列重新实现一遍,还会和 USB 子系统打架。gadget 框架的意义是:枚举的通用部分框架做了,你只描述「这个设备长什么样」和「数据往哪搬」。

二、三个层次：UDC、gadget 驱动、上层功能 #

Linux USB 设备端驱动由两部分组成:USB 设备控制器(USB Device Controller,UDC)驱动,和硬件无关的功能驱动(鼠标、U 盘、USB 串口、USB 网络等)。也可以分成三层:Controller Drivers、Gadget Drivers、Upper Layers。说法不同,意思差不多。

三层里最容易搞混的是中间层。把下面这张表记住,gadget 就懂了一半。

层次 代码里是什么 干什么 典型文件
最底层:UDC 驱动 实现 struct usb_gadget_ops、提供 struct usb_gadget 操作芯片的 USB 设备控制器,收发包、管端点、控制上拉电阻 s3c2410_udc.c、pxa2xx_udc.c
中间层:gadget 驱动 实现 struct usb_gadget_driver 处理枚举与配置:响应 SETUP、激活端点、注册上层功能 zero.c、file_storage.c、ether.c
最上层:功能驱动 字符设备 / 块设备 / 网络设备 提供实际功能:U 盘、网卡、串口 g_mass_storage、g_ether、g_serial

注意"gadget 驱动"这个词在中文资料里被用得很乱。有人用它指整个框架,有人用它指最上层那个 .ko。本篇统一:中间层叫 gadget 驱动,最上层叫功能驱动。

三层的分界线在哪 #

分界线其实就是两个结构体。

UDC 驱动对上暴露一个 struct usb_gadget,里面挂着操作集 usb_gadget_ops。这是"硬件能力"的抽象:你能做几个端点、支持什么速度、怎么上拉 D+。

gadget 驱动对上暴露一个 struct usb_gadget_driver,里面是 bind / unbind / setup / disconnect / suspend / resume 六个回调。这是"设备行为"的抽象:主机发来 SETUP 我怎么办,主机把我配置了我怎么办。

框架在中间做媒:UDC 一旦就绪,就把 usb_gadget 交给注册上来的 usb_gadget_driver,调它的 bind。从这一刻起,主机的每个 SETUP 包都被转给 gadget 驱动的 setup。

c
EXPORT_SYMBOL(usb_gadget_register_driver);   /* 注册一个 gadget 功能驱动 */
EXPORT_SYMBOL(usb_gadget_unregister_driver); /* 注销一个 gadget 功能驱动 */

这两个符号就是中间层和上层之间的门槛。你写的功能驱动,入口函数里调一次 usb_gadget_register_driver,把自己的 usb_gadget_driver 交上去,框架就会找 UDC 绑定。

一个限制要提前知道:S3C2410 这类控制器同一时刻只能注册一个 gadget 功能驱动。原因在协议和硬件:一个设备地址、一套描述符,你不能同时对主机说"我是 U 盘"又说"我是网卡"。多功能的做法是在一个 gadget 驱动里放多个 configuration 或多个 interface,不是注册多个驱动。

c
int usb_gadget_register_driver(struct usb_gadget_driver *driver)
{
    ...
    if (udc->driver)          /* 如果已经注册过了 */
        return -EBUSY;
    ...
}

想同时要 U 盘和网卡,现代内核用 g_multi(mass storage + CDC + ACM 合一),或者 configfs 组态。这是后话。

数据怎么流动 #

从主机的角度看,一次批量传输是:主机发一个 Bulk-OUT 令牌,跟着一包数据,设备回 ACK。这一层由 UDC 硬件完成。

从内核代码看,是另一套东西:功能驱动分配一个 struct usb_request,把 buffer 挂上去,调 usb_ep_queue(ep, req, gfp) 塞进端点的队列。UDC 驱动把它翻译成硬件操作。数据搬完,硬件中断,UDC 驱动调 req->complete 回调。

c
struct usb_request *req;

req = alloc_ep_req(ep, buflen);          /* 分配请求,方向由 ep 本身决定 */
req->complete = source_sink_complete;    /* 请求完成后的处理函数 */
status = usb_ep_queue(ep, req, GFP_ATOMIC); /* 递交请求 */
free_ep_req(ep, req);                    /* 释放请求,在 complete 里调用 */

这个模型和主机侧的 URB 是一一对应的。usb_request 之于设备端,就是 urb 之于主机端。写过主机驱动的人看到这里会有熟悉感:都是"提交一个请求,等回调"。

区别在所有权。URB 是主机发起传输,设备被动响应。usb_request 是设备准备好 buffer 等主机来拿(IN)或者等主机送过来(OUT)。谁先动,方向相反。

后面所有章节都在往这三层里填内容。第三到第八章是功能层怎么用,第九章是 UDC 层,第十到第十二章是中间层和一个完整项目。

三、让板子变成一个 U 盘 #

先跑通一个成品,建立直观感受。硬件是华清远见的 FS2410 平台,芯片 S3C2410,软件是 linux-2.6.26。目标是让这块板子插到 Windows 上,弹出一个可移动磁盘。

整条路分四步:改板级代码、配内核、编译、加载测试。

第一步:板级代码里处理上拉电阻 #

USB 设备要被主机发现,靠的是 D+ 线上那个 1.5k 上拉电阻。设备把这根线拉高,主机才认为"有东西插进来了",然后开始复位和枚举。所以 gadget 能不能被看到,第一件事就是能不能控制这个上拉。

S3C2410 上这颗上拉不是芯片内部的,是板子上用 GPG9 这个 GPIO 控制的。要在板级代码里给它一个回调。

修改 arch/arm/mach-s3c2410/mach-smdk2410.c:

c
/* USB device 上拉电阻处理 */
static void smdk2410_udc_pullup(enum s3c2410_udc_cmd_e cmd)
{
    u8 *s3c2410_pullup_info[] = {
        " ",
        "Pull-up enable",
        "Pull-up disable",
        "UDC reset, in case of"
    };

    printk("smdk2410_udc: %s\n", s3c2410_pullup_info[cmd]);

    s3c2410_gpio_cfgpin(S3C2410_GPG9, S3C2410_GPG9_OUTP);

    switch (cmd) {
    case S3C2410_UDC_P_ENABLE:
        s3c2410_gpio_setpin(S3C2410_GPG9, 1);   /* set gpg9 output HIGH */
        break;
    case S3C2410_UDC_P_DISABLE:
        s3c2410_gpio_setpin(S3C2410_GPG9, 0);   /* set gpg9 output LOW */
        break;
    case S3C2410_UDC_P_RESET:
        /* FIXME!!! */
        break;
    default:
        break;
    }
}

static struct s3c2410_udc_mach_info smdk2410_udc_cfg __initdata = {
    .udc_command    = smdk2410_udc_pullup,
};

把 UDC 平台设备登记进去,并且把这份配置挂上去:

c
static struct platform_device *smdk2410_devices[] __initdata = {
    ...,
    &s3c_device_usbgadget,  /* USB gadget device 设备登记 */
};

static void __init sdmk2410_init(void)
{
    u32 upll_value;

    set_s3c2410fb_info(&smdk2410_lcdcfg);

    s3c24xx_udc_set_platdata(&smdk2410_udc_cfg);   /* 初始化 UDC 平台数据 */

    s3c_device_sdi.dev.platform_data = &smdk2410_mmc_cfg;

    /* Turn off suspend on both USB ports, and switch the
     * selectable USB port to USB device mode. */
    s3c2410_modify_misccr(S3C2410_MISCCR_USBHOST |
                          S3C2410_MISCCR_USBSUSPND0 |
                          S3C2410_MISCCR_USBSUSPND1, 0x0);

    /* 设置 USB 时钟 */
    upll_value = (0x78 << S3C2410_PLLCON_MDIVSHIFT)
               | (0x02 << S3C2410_PLLCON_PDIVSHIFT)
               | (0x03 << S3C2410_PLLCON_SDIVSHIFT);

    while (upll_value != readl(S3C2410_UPLLCON)) {
        writel(upll_value, S3C2410_UPLLCON);
        udelay(20);
    }
}

这里有两个关键点。

S3C2410_MISCCR_USBHOST 那一段把 USB 口切换到 device 模式。S3C2410 的两个 USB 口功能是复用的,不改这个寄存器,控制器就还在主机模式。

UPLL 那段是给 USB 供时钟的。48MHz 或者 12MHz 来自 UPLL,不是主 PLL。写进去要轮询回读确认生效,while 循环就是这个用意。

第三步:配置内核 #

菜单路径在 Device Drivers → USB Gadget Support:

text
<*>   USB Gadget Support  --->
          USB Peripheral Controller (S3C2410 USB Device Controller)  --->
              S3C2410 USB Device Controller
    [*]       S3C2410 udc debug messages
          USB Gadget Drivers
              File-backed Storage Gadget

三个选项各管一层,对应刚讲的三层架构。USB Peripheral Controller 是 UDC 驱动,最底层,硬件相关。USB Gadget Drivers → File-backed Storage Gadget 是功能驱动,最上层,选它编译出来就是 g_file_storage.ko。S3C2410 udc debug messages 打开后 UDC 层会打一堆调试信息,调枚举问题时很有用,跑通了可以关掉。

编译:

bash
#make zImage
#make modules

编译完成后,在 drivers/usb/gadget 目录下会生成 g_file_storage.ko。

第四步:加载测试 #

用前面生成的内核启动系统,然后加载模块。先把设备节点和挂载点准备好:

bash
# mkdir /mnt/gadget

加载模块。第一个参数 file 指定 backing file,也就是这个「U 盘」背后到底存的什么东西。这里直接指到一个 MTD 分区上:

bash
# insmod g_file_storage.ko
# insmod g_file_storage.ko file=/dev/mtdblock2 stall=0 removable=1

三个参数要解释一下。

file=/dev/mtdblock2 是介质。它既可以是普通文件(/tmp/disk.img),也可以是块设备。指到 mtdblock 上,等于把整个 flash 分区交给 PC 当 U 盘用。

stall=0 表示遇到不支持的请求不回 STALL,而是返回空数据。有些主机(尤其 Windows)对 STALL 反应比较激烈,调试阶段先关掉。

removable=1 让主机认为这是可移动介质。Windows 会走「可移动磁盘」的路径,而不是固定磁盘。

加载成功的日志长这样:

text
0.03 USB: usb_gadget_register_driver() 'g_file_storage'
0.04 USB: binding gadget driver 'g_file_storage'
0.05 USB: s3c2410_set_selfpowered()
g_file_storage gadget: File-backed Storage Gadget, version: 20 October 2004
g_file_storage gadget: Number of LUNs=1
g_file_storage gadget-lun0: ro=0, file: /dev/mtdblock3
0.06 USB: udc_enable called
smdk2410_udc: Pull-up enable

逐行读一遍,信息量不小。

第一行是 usb_gadget_register_driver() 被调,功能驱动把自己交给了框架。第二行 binding gadget driver 是 bind 回调进来了,UDC 和 gadget 驱动配上了。

set_selfpowered() 声明设备自供电,不从 VBUS 取电。Number of LUNs=1 是逻辑单元数,一个 LUN 就是一个盘符。

ro=0, file: /dev/mtdblock3 要注意:命令里传的是 mtdblock2,日志里打的是 mtdblock3。这是那份老代码里的手误或者历史遗留,不影响结论,但你自己调试时看到日志和参数不一致,先怀疑这个。

最后两行最关键:udc_enable called 和 Pull-up enable。上拉电阻拉起来了,主机马上就能看到设备。

第五步:主机端和板子端验证 #

把 USB 线接到 Windows,系统会自动发现一个新 U 盘。格式化,存几个文件进去。

拔掉 U 盘,回到目标板上:

bash
# mount -t vfat /dev/mtdblock2 /mnt/gadget/
# ls

能看到 Windows 存进去的文件。这条链路就通了:PC 写的是 FAT16 文件系统,板子这边把它当普通 vfat 分区挂载,中间所有 USB 协议、SCSI 命令、块读写,全被 gadget 框架和 Mass Storage 功能驱动吃掉了。

值得注意的是,板子完全没有参与 FAT16 文件系统的管理。格式化、分配簇、写目录项,全是 Windows 干的。板子只负责把"第几个扇区的读写"翻译成对 mtdblock 的读写。这个分工是 Mass Storage 类的设计前提,也是它好用的原因。

到这里,一个 U 盘 gadget 跑通了。但为什么能跑通、中间经历了什么协议、为什么需要那个 udelay(800),下面几章拆开看。

四、Mass Storage 类规范 #

U 盘不是"一个能存东西的 USB 设备"这么模糊的东西,它遵循一份写死的规范。

USB 组织在 Universal Serial Bus Mass Storage Class Specification 1.1 里定义了海量存储设备类(Mass Storage Class)。这份类规范下面挂了四个独立的子规范:

text
1. USB Mass Storage Class Control/Bulk/Interrupt (CBI) Transport
2. USB Mass Storage Class Bulk-Only Transport
3. USB Mass Storage Class ATA Command Block
4. USB Mass Storage Class UFI Command Specification

前两个管传输:数据、命令、状态在 USB 上怎么走。后两个管命令:存什么、怎么操作介质。

这个划分方式要记牢,它对应三层协议栈。

层 管什么 本项目的选择
传输层 命令/数据/状态怎么在 USB 上搬 Bulk-Only Transport(BBB)
命令层 主机发的命令块怎么解释 SCSI 透明命令集
介质层 实际往哪读写 MTD 分区 mtdblock2

Bulk-Only 传输规范只用 Bulk 端点传送数据、命令和状态。CBI 传输规范则用 Control、Bulk、Interrupt 三种类型的端点。ATA 命令规范用于硬盘,UFI 命令规范针对 USB 移动存储。

Windows 自带 Mass Storage 协议的支持。所以 USB 移动设备只要遵循 Mass Storage 协议来组织数据和处理命令,就能和 PC 交换数据,不用装任何驱动。

再加上介质侧用 FAT16 文件系统,就可以直接在 Windows 资源管理器里通过可移动磁盘交换文件。Windows 负责 FAT16 的管理,USB 设备不需要干预文件系统操作的具体细节。

这句话是整个方案能成立的关键。板子不需要懂 FAT,不需要懂目录项,不需要懂长文件名。它只要会「读第 N 个扇区」和「写第 N 个扇区」。

描述符决定一切 #

USB 主机唯一通过描述符了解设备。在描述符里规定了设备使用的协议、端点情况。所以正确地提供描述符,是 USB 设备正常工作的先决条件。

在 linux-2.6.26 里,模拟 U 盘主要涉及两个文件:file_storage.c 和 s3c2410_udc.c。前者是我们这章关心的,后者在第九章。

调试的第一步,是先从代码里找到描述符,从中确定用的哪个存储类规范,从而确定协议。协议定了,才知道抓包该看什么。

存储类规范是由接口描述符决定的。接口描述符里三个字段就能判断设备的身份:

字段 含义 值 说明
bInterfaceClass 设备类 0x08 Mass Storage,存储类
bInterfaceSubClass 子类,决定命令集 0x06 Transparent SCSI,透明 SCSI 指令
bInterfaceProtocol 协议,决定传输方式 0x50 Bulk-Only Transport

三个字节,把三层协议栈全定死了。看到 08 06 50 这个组合,就是一个标准的 Bulk-Only SCSI U 盘,不用再猜。

file_storage.c 里的常量表 #

代码里这几个值都是有宏定义的。看 file_storage.c 的开头:

c
/* USB protocol value = the transport method */
#define USB_PR_CBI      0x00        /* Control/Bulk/Interrupt */
#define USB_PR_CB       0x01        /* Control/Bulk w/o interrupt */
#define USB_PR_BULK     0x50        /* Bulk-only */

/* USB subclass value = the protocol encapsulation */
#define USB_SC_RBC      0x01        /* Reduced Block Commands (flash) */
#define USB_SC_8020     0x02        /* SFF-8020i, MMC-2, ATAPI (CD-ROM) */
#define USB_SC_QIC      0x03        /* QIC-157 (tape) */
#define USB_SC_UFI      0x04        /* UFI (floppy) */
#define USB_SC_8070     0x05        /* SFF-8070i (removable) */
#define USB_SC_SCSI     0x06        /* Transparent SCSI */

子类那几个值,正好对应不同的介质形态:0x01 RBC 是简化块命令,闪存盘用的;0x02 SFF-8020i 是 ATAPI,光驱;0x03 QIC-157 是磁带;0x04 UFI 是软驱;0x05 SFF-8070i 是可移动介质;0x06 Transparent SCSI 是所有 SCSI 命令原样透传。

file_storage.c 的默认参数就选了 BBB + SCSI:

c
static struct fsg_mod_data mod_data = {          /* Default values */
    .transport_parm = "BBB",
    .protocol_parm  = "SCSI",
    ...
};

BBB 就是 Bulk-Bulk-Bulk,也就是 Bulk-Only Transport。SCSI 对应 USB_SC_SCSI。这两个参数还能在加载模块时改,但绝大多数场景不需要。

推导出来的三个字段值:bInterfaceClass=0x08 存储类,bInterfaceSubClass=0x06 透明 SCSI 指令,bInterfaceProtocol=0x50 bulk-only 传输。

怎么验证自己的设备报了什么 #

有两种办法。

一是看代码。fsg_intf_desc 这个结构体就是接口描述符,里面的 .bInterfaceClass、.bInterfaceSubClass、.bInterfaceProtocol 字段,在 fsg_bind() 里会按 mod_data 的值填进去。

二是抓包。Windows 上用 Bushound 或者 USB Device Tree Viewer,Linux 上用 lsusb -v。看 Interface Descriptor 那一段,三个字节一目了然。用 USB View 也能看到 USB 设置阶段获取到的全部信息,这个工具轻,但要装驱动,调试阶段建议常备。

描述符为什么必须自己写 #

有一个反直觉的地方:主机侧驱动可以靠 idVendor/idProduct 匹配,设备侧的描述符却是硬编码在驱动里的。

file_storage.c 里那几个 static struct usb_*_descriptor,在没有 configfs 的年代就是写死的。想要不同的 VID/PID,得改代码重编。

这也是 g_zero 那类例子存在的意义:它们把「怎么组一套描述符」摊开给你看。第十一章会逐段过一遍。

到这里,协议栈的传输层定了(Bulk-Only),命令层定了(SCSI)。下面两章分别拆开。

五、Bulk-Only 传输协议 #

Bulk-Only 的细节在《Universal Serial Bus Mass Storage Class Bulk-Only Transport》这份文档里。这里讲实际要懂的部分。

设备插入 USB 后,主机对设备进行搜索,要求设备提供相应的描述符。主机拿到描述符,就完成了配置,识别出这是一个 Bulk-Only 的 Mass Storage 设备,然后进入 Bulk-Only 传输方式。

从这里开始,主机和设备之间的所有数据都通过 Bulk-IN 和 Bulk-OUT 传输,不再通过控制端点传任何数据。

注意这句话:控制端点只用来做标准请求和类请求。真正搬数据、下命令、回状态,全走两个 Bulk 端点。这就是 Bulk-Only 里「Only」的意思。

三种数据 #

在这种传输方式下,USB 和设备之间传送三种类型的数据:

名称 全称 方向 作用
CBW Command Block Wrapper 主机 → 设备 包一条命令
Data 普通数据 双向 命令要读写的实际内容
CSW Command Status Wrapper 设备 → 主机 回报命令执行状态

CBW 是主机发到设备的命令,命令格式遵从接口中 bInterfaceSubClass 指定的命令块。我们这里是 SCSI 传输命令集。

设备需要把 SCSI 命令从 CBW 里提取出来,执行相应的操作。完成后向主机发一个 CSW,反映当前命令执行状态。

主机根据 CSW 决定是否继续发下一个 CBW 或数据。如果命令是要设备发数据,设备先把数据发出去,完毕后再发 CSW。

整个流程是一个严格的三段式,而且不能乱序:

text
主机 --CBW--> 设备
主机 <--Data--> 设备     (方向由 CBW 里的 bmCBWFlags 决定,长度由 dCBWDataTransferLength 决定)
主机 <--CSW-- 设备

一次传输只有一个 CBW、一个 CSW,中间夹 0 到 N 个数据包。设备在任何时刻只能处理一个 CBW,不能流水线。

CBW 的格式 #

31 字节,固定结构。逐字段看:

字段 长度 含义
dCBWSignature 4 固定值 0x43425355,小端。ASCII 就是 USBC
dCBWTag 4 主机给的命令块标识,设备要原样带回
dCBWDataTransferLength 4 本次命令要传的字节数,为 0 则不传数据
bmCBWFlags 1 方向。0 表示来自主机,1 表示发往主机
bCBWLUN 1 逻辑单元号,多 LUN 设备用来选目标,单 LUN 写 0
bCBWCBLength 1 命令块长度,范围 0~16
CBWCB 16 具体命令,这里是 SCSI 命令块

一句一句补。

dCBWSignature 是 CBW 的标识,固定值 43425355h,小端存储。抓包看到 55 53 42 43 就是这个,ASCII 读出来是 USBC。设备收到后先校验这 4 个字节,不对就丢掉。

dCBWTag 是主机发的一个命令块标识,设备要原样作为 dCSWTag 再发回去,作用是把 CSW 关联到对应的 CBW。设备不解析它的含义,只负责复制。

dCBWDataTransferLength 是本次 CBW 要求在命令与回应之间传输的字节数,为 0 则不传。这个值决定了设备该准备多大的 buffer,也决定了 CSW 里的 residue 怎么算。

bmCBWFlags 反映数据传输方向:0 表示来自主机(OUT,主机写设备),1 表示发至主机(IN,主机读设备)。bit7 是方向位,其余位保留。

bCBWLUN 对有多个 LUN 的设备用来选择具体目标,没有多个 LUN 就写 0。

bCBWCBLength 是命令的长度,范围 0~16。SCSI 命令有 6、10、12、16 字节几种,这个字段告诉设备该读几个字节。

CBWCB 是具体命令,符合 bInterfaceSubClass 中定义的命令规范,此处是 SCSI。

CSW 的格式 #

13 字节,比 CBW 短得多。

字段 长度 含义
dCSWSignature 4 固定值 0x53425355,小端。ASCII 就是 USBS
dCSWTag 4 必须和 CBW 里的 dCBWTag 一致
dCSWDataResidue 4 还需要传送的数据量
bCSWStatus 1 命令执行状态

dCSWDataResidue 由 dCBWDataTransferLength 减去本次已经传送的数据得到。正常应该为 0;设备实际传的比主机要的少,这里就是差额。

bCSWStatus 三个值:

值 含义
0x00 命令正确执行
0x01 命令失败
0x02 阶段错误(Phase Error)

返回 1 时,主机会接着发 REQUEST SENSE 去问具体原因,这就是下一章 SCSI 里那个 03h 命令的用处。

一个完整回合长什么样 #

把三层串起来看,主机读一个扇区的完整过程:

text
1. 主机 -> 设备  CBW:  dCBWSignature=USBC, dCBWTag=T,
                        dCBWDataTransferLength=512,
                        bmCBWFlags=0x80 (IN),
                        CBWCB = 28 00 00 00 12 34 56 78 00 00 01 00
                        (READ(10), LBA=0x12345678, 传 1 个块)

2. 设备解析 CBWCB,认出是 READ(10),从 backup file 读到 512 字节

3. 设备 -> 主机  Data: 512 字节扇区内容

4. 设备 -> 主机  CSW:  dCSWSignature=USBS, dCSWTag=T,
                        dCSWDataResidue=0, bCSWStatus=0x00

四个阶段里有三个在设备发,主机只在第一步动。

注意第 3 步的数据方向是被 CBW 里的 flag 决定的,不是设备自己决定的。设备要是搞反了方向,主机就会一直等,超时后复位。

第八章那个 bug 就是第 4 步没做:设备发完数据,CSW 没发出去。主机拿到数据了,但不知道命令结束了,于是不出盘符。抓包能直接看出来——DI 有数据,后面没有 CSW。

为什么 Bulk 而不是中断或等时 #

Bulk 传输的特点是"有带宽就用,没带宽就让"。它不保证时延,但保证数据正确,而且有 CRC 和重传。

U 盘的访问模式是突发的大块读写,对时延不敏感,对正确性要求极高。Bulk 正好合适。

同理,命令和状态也走 Bulk,因为 CBW/CSW 也是关键数据,丢了就得重来。虽然它们很小,但正确性比速度重要。

这个选择带来一个后果:Bulk 端点必须在配置阶段被激活,而且主机要先把配置选好(SET CONFIGURATION),才会有 Bulk 传输。所以枚举的顺序不能乱:先拿描述符,再设地址,再设配置,然后才能传 CBW。

六、SCSI 指令集 #

Bulk-Only 的 CBW 里,CBWCB 字段的内容就是命令块描述符(Command Block Descriptor)。

SCSI-2 有三种字长的命令:6 字节、10 字节、12 字节。Windows 环境下支持 12 字节长的命令。

字长不同,能表达的地址和长度范围不同。6 字节命令的 LBA 只有 21 位,最多 2TB 级别;10 字节是 32 位;12 字节是 32 位 LBA 加 32 位长度。实际用 10 字节的最多。

命令块里的字段 #

不管几字节,结构逻辑是一样的。

字段 含义
Operation Code 操作代码。高 3 位是 Group Code,共 8 组;低 5 位是 Command Code,可定义 32 种。一个字节最多定义 256 条命令
Logical Unit Number 为兼容 SCSI-1 而设,可以不必关心。Bulk-Only 已在 CBW 里用 bCBWLUN 指定 LUN,这个字段是历史包袱
Logical block address 逻辑块地址,即扇区地址,高位在前。10 字节命令里占 4 字节。SCSI 是大端,代码里要 be32_to_cpu()
Transfer length 需要从该地址开始传输的扇区数,比如 Write 要写几个扇区
Parameter list length 需要传输的数据长度,比如 Mode Sense
Allocation length 初始程序为返回数据分配的最大字节数,可以为零,表示不传数据

实际会用到的命令 #

SCSI 的 Direct Access 类型存储介质的传输命令有很多,Mass Storage 协议只用到其中一部分。

代码 命令 说明
00h Test Unit Ready 请求设备报告是否处于 Ready 状态
03h Request Sense 请求设备向主机返回执行结果及状态数据
12h Inquiry 索取器件信息
1Bh Start/Stop load/unload,启停介质
1Dh Send Diagnostic 执行固件复位并执行诊断
23h Read Format Capacity 查询当前容量及可用空间
25h Read Capacity 要求设备返回当前容量
28h Read(10) 主机读存储介质中的二进制数据
2Ah Write(10) 从主机向介质写二进制数据
2Bh Seek(10) 为设备分配到特定地址
2Eh Write and Verify 写二进制数据并验证
2Fh Verify 在存储中验证数据
04h Format Unit 格式化存储单元

这张表背不下来也没关系,但要知道主机会问什么。

Inquiry 是第一个要答的:你是什么设备、什么厂商、什么型号、支持什么版本。Windows 拿到它才会画盘符。

Read Capacity 是第二个:你有多少个扇区、每个扇区多大。没有这个,主机算不出容量,文件系统也挂不起来。

Mode Sense 是第三个:介质类型、写保护状态、缓存参数。

Read(10) / Write(10) 是干活的。前面三个是「认识你」,这两个是「用你」。Request Sense 在出错时被调用,上一章说了,CSW 返回 0x01 时主机会来问原因,答案就在这条命令的返回数据里。

主机怎么走完识别流程 #

Host 会依次发出 INQUIRY、Read Capacity、Mode Sense 请求。如果上述请求的返回结果都正确,Host 会发出 READ 命令,读取文件系统 0 簇 0 扇区的 MBR 数据,进入文件系统识别阶段。

这条路径很重要。它说明了为什么「只回 Inquiry」不够:盘符出来之前,主机会连问三个问题,任何一个答错都停在原地。

MBR 那一步更有意思:主机读完第一个扇区,看到 0x55AA 结束标志和分区表,才知道这是个有文件系统的盘。如果 backing file 是空的(全是 0),主机会认为磁盘未格式化,弹窗让你格式化——这就是新 U 盘第一次插电脑的体验。

命令块的具体长相 #

对于不同的命令,其命令块描述符略有不同,要求的返回内容也不同。举例看 INQUIRY。

INQUIRY 的 CDB 是 6 字节:操作码 12,字节 1 是 LUN 加保留,字节 2 是 Page Code(标准查询页为 0),字节 3 保留,字节 4 是分配长度 24(即 0x24 = 36 字节),字节 5 是控制字节。

text
字节 0: 12          操作码
字节 1: 00          LUN + 保留
字节 2: 00          Page Code(标准查询页为 0)
字节 3: 00          保留
字节 4: 24          分配长度,0x24 = 36 字节
字节 5: 00          控制字节

返回数据至少 36 字节:

text
字节 0:   00        外设类型。00 = 直接存取设备(硬盘/U盘)
字节 1:   80        设备类型修饰符,bit7=1 表示可移动介质
字节 2:   02        ISO/ECMA 版本
字节 3:   02        SPC 版本
字节 4:   1F        额外长度,后面还有 31 字节
字节 5-7: 00        保留
字节 8-15: 厂商标识,8 字节 ASCII,不足补空格
字节 16-31: 产品标识,16 字节 ASCII,不足补空格
字节 32-35: 产品版本,4 字节 ASCII

第八章抓包里的那段数据正好印证了这个格式:

text
00 80 02 02 - 1f 00 00 00 - 4c 69 6e 75 - 78 20 20 20
........Linux
46 69 6c 65 - 2d 53 74 6f - 72 20 47 61 - 64 67 65 74
File-Stor Gadget
30 33 31 32
0312

00 80 是可移动的直接存取设备。4c 69 6e 75 78 20 20 20 读出来是 Linux 。后面 16 字节拼出 File-Stor Gadget。最后 0312 是版本号。

设备把自己的名字老老实实报上去了。这些字符串在 file_storage.c 里是写死的,想改就改那几个 char 数组。

命令集和介质的关系 #

SCSI 这一层不关心介质是 flash 还是 SD 卡还是 NAND。它只发"读第 N 块",不关心怎么读。

所以 g_file_storage 可以在不同的 backing file 之间切换:file=/dev/mtdblock2 走 MTD,file=/tmp/disk.img 走文件系统的普通文件,file=/dev/mmcblk0p1 走 SD 卡。对主机来说完全一样。

这也是三层协议栈最实用的地方。换介质不用改协议,换协议不用改介质驱动。

三层到此讲完:Mass Storage 类规范定了身份,08/06/50 三个字节;Bulk-Only 定了传输,CBW/CSW 一来一回;SCSI 定了命令,一堆 CDB。三者叠起来,才是一个能被 Windows 认出来的 U 盘。

七、让板子变成一张网卡 #

同样的框架,换一个功能驱动,板子就从 U 盘变成网卡。这条路叫 USBNET。

配置内核支持 usbnet:

text
<*>   USB Gadget Support  --->
          USB Peripheral Controller (S3C2410 USB Device Controller)  --->
              S3C2410 USB Device Controller
    [*]       S3C2410 udc debug messages
          USB Gadget Drivers
              Ethernet Gadget (with CDC Ethernet support)
    [*]       RNDIS support

Ethernet Gadget (with CDC Ethernet support) 是功能驱动,编译出来是 g_ether.ko。

RNDIS support 一定要勾。CDC Ethernet 是 USB 组织定的标准,Linux 天然支持,Windows 不行。Windows 认的是 RNDIS(Remote NDIS),微软自己搞的一套把以太网帧封装在 USB 上的协议,驱动在系统里自带。不勾这个,RNDIS 主机拿不到合适的描述符,会装不上驱动。

编译:

bash
#make zImage
#make modules

在 drivers/usb/gadget 目录下生成 g_ether.ko。

加载测试 #

启动系统,加载模块,给网卡配 IP:

bash
# insmod g_ether.ko
#ifconfig usb0 192.168.1.120

usb0 这个名字是 g_ether 注册网卡时固定的,不会变成 eth1 或者别的。ifconfig 的输出:

text
usb0      Link encap:Ethernet  HWaddr 5E:C5:F6:D4:2B:91
          inet addr:192.168.1.120  Bcast:192.168.1.255  Mask:255.255.255.0
          UP BROADCAST RUNNING MULTICAST  MTU:1500  Metric:1
          RX packets:253 errors:0 dropped:0 overruns:0 frame:0
          TX packets:43 errors:0 dropped:0 overruns:0 carrier:0
          collisions:0 txqueuelen:1000
          RX bytes:35277 (34.4 KiB) TX bytes:10152 (9.9 KiB)

几个细节值得看。

HWaddr 5E:C5:F6:D4:2B:91 这个 MAC 是自动生成的。第一个字节 5E 的 bit1 是 1,表示本地管理地址,不会和真实厂商的 MAC 冲突。内核用随机数生成,每次加载会不同,需要固定就传 dev_addr=xx:xx:xx:xx:xx:xx。

MTU:1500 是标准以太网帧。USB 这边用 Bulk 端点搬这些帧,所以大包会被切成多个 512 字节的 USB 包。RX packets:253 说明已经收到包了:即使你还没配好 IP,USB 链路上已经有主机发的广播和发现报文。

主机端 #

连到 Windows,系统会提示安装驱动,根据提示装上 RNDIS 驱动。Windows 10/11 一般自带,插上就能认。老一点的系统需要手动指定,把驱动指向系统里的 usb8023 或者厂商提供的 RNDIS inf。

装好之后,Windows 会新生成一个网络连接,配置它的 IP 地址等信息,然后在同一网段下就能和目标系统通过 USB 实现网络通讯。

配好之后的玩法很多:板子上跑个 telnetd,PC 直接 telnet 进去;板子挂 NFS 从 PC 加载根文件系统;PC 上开个 ftp 传文件。比串口快几个数量级,比网线省一根线。

四种以太网 gadget 怎么选 #

内核里其实有不止一个以太网 gadget 驱动,容易选错。

驱动 协议 Linux 主机 Windows 主机 说明
g_ether CDC Ethernet + RNDIS 支持 需要 RNDIS 编译时勾 RNDIS 就两个都支持
g_cdc CDC Ethernet 支持 不支持 只走标准 CDC,兼容性最广
g_ncm CDC NCM 支持 Win10 之后 新标准,一次传多帧,效率高
g_rndis RNDIS 支持 支持 只走微软那套

选 g_ether 最省事,它按主机的操作系统自动切换:连 Linux 就报 CDC Ethernet,连 Windows 就报 RNDIS。

g_ncm 是更新的选择,NCM(Network Control Model)把多个以太网帧打包进一次 USB 传输,减少了事务开销,高速下吞吐明显好于 ECM。代价是 Windows 支持要 Win10 1703 之后。

网卡 gadget 和 U 盘 gadget 的结构差异 #

同样跑在 gadget 框架上,两个功能驱动的组织方式不一样,这个差异反映了它们干的事不一样。

g_file_storage 是块设备语义。它自己管 SCSI 命令解析、CBW/CSW 收发,只需要一对 Bulk 端点,不需要注册任何内核设备(除非你要它顺便在本地也可见)。

g_ether 是网络设备语义。它需要在 bind 里 register_netdev() 注册一个真正的网卡,让内核网络栈能往上挂 IP、路由、socket。数据方向是双向流动的:主机发来的帧要往上交给网络栈,网络栈要发的帧要往下塞进 USB 端点。

这就是第十章要讲的那个规律:功能驱动在 bind 里注册内核设备,在 unbind 里注销。g_ether 是最典型的例子。

怎么读这份抓包 #

先看阶段列。CTL 是控制传输,DI 是 Data In(设备往主机发数据),DO 是 Data Out(主机往设备发数据),USTS 是 USB 状态。

前面的 CTL/DI 全是标准枚举。逐段对一下。

80 06 00 01 是 GET_DESCRIPTOR,类型 01 是设备描述符。设备回了 18 字节:12 01 10 01 00 00 00 10 25 05 a5 a4 12 03 01 02。12 是长度,01 是类型,10 01 是 USB 1.1,25 05 是 VID 0x0525,a5 a4 是 PID 0xa4a5——NetChip 的 VID 加 Linux 的 mass storage PID。

80 06 00 02 是配置描述符。先只取 9 字节看总长,再取 32 字节拿完整配置。完整数据里能看到 09 04 00 00 02 08 06 50 05——接口描述符,08 类、06 子类、50 协议,完全符合第四章推出来的三个值。

80 06 00 03 是字符串描述符。先取语言 ID,再依次取厂商、产品、序列号。序列号那段 1a 03 33 00 37 00 32 00 ... 是 UTF-16,读出来一串数字。

然后 00 09 01 00 SET CONFIGURATION,01 0b 00 00 SET INTERFACE,配置阶段完成。

再是 a1 fe 00 00——a1 是方向 IN + 类请求 + 接口接收者,fe 是 GET_MAX_LUN(0xFE)。设备回一个 00,表示 1 个 LUN。到这里一切正常。

问题点 #

看 DO 那一行:

text
26     DO      55 53 42 43 - 08 60 e0 86 - 24 00 00 00 - 80 00 06 12

55 53 42 43 是 CBW signature(USBC)。08 60 e0 86 是 tag。24 00 00 00 是 dCBWDataTransferLength = 0x24 = 36 字节。80 是 bmCBWFlags,0x80 表示 IN,设备要往主机发数据。00 是 LUN。06 是 bCBWCBLength,6 字节命令。12 是操作码——INQUIRY。

然后设备通过 DI 返回了数据:

text
26     DI      00 80 02 02 - 1f 00 00 00 - 4c 69 6e 75 - 78 20 20 20

36 字节的 Inquiry 返回,格式完全正确,00 80 可移动直接存取,Linux 加 File-Stor Gadget。

按规范,返回完数据后,设备端还应该通过 DI 向系统返回 CSW。但实际的捕获内容里没有。

所以主机拿不到命令结束的信号,盘符出不来。

这就是 Bulk-Only 三段式的完整性问题:数据发了,状态没发。主机在等 CSW,等不到就认为命令没完成。

怎么修 #

在 file_storage.c 里,发送数据时都会调用到 start_transfer() 函数。在这个函数里加 printk 调试语句,观察现象。结果有点意外:只要加入调试语句,Windows 端就能正常识别设备了。

加 printk 就好,说明问题不在逻辑,在时序。printk 会往串口打字符,在 115200 的波特率下打一行字约几十微秒到几百微秒,这个延时恰好补上了缺失的间隔。

于是猜测:连续两次发送之间需要一些延时。在函数里加入 udelay(800) 之后,Windows 系统可以正常发现设备了。

c
static void start_transfer(struct fsg_dev *fsg, struct usb_ep *ep,
                           struct usb_request *req, int *pbusy,
                           enum fsg_buffer_state *state)
{
    int rc;

    udelay(800);

    ...
}

800 微秒是个经验值,不是规范要求。根因在硬件:数据写完的那个 Bulk 请求完成得太快,紧接着要发 CSW 的请求排进队列时,控制器还在处理上一个包的握手。主机侧收到数据后立刻要 CSW,而这中间没有给设备留出准备时间。调试语句或者 udelay 拉开了间隔,主机就能正确收到 CSW。

这类问题在 gadget 调试里很常见:逻辑对,时序不对。抓包看不出来,因为抓包只记录总线上的包,不记录设备内部队列的状态。

调试方法论 #

这两条里第二条更实际。协议文档读一百遍,不如抓一次包。抓包能直接告诉你哪一步少了什么,比对着代码猜快十倍。

再补一条这次学到的:逻辑正确不等于能跑,时序问题要靠延时和二分法试。printk 加进去就好了,这个现象本身就是线索——凡是加了打印就正常的 bug,九成是时序。

九、UDC 控制器驱动 #

回到三层架构的最底层。

Gadget 框架提出了一套标准 API。在底层,USB 设备控制器驱动实现这一套 API。不同的 UDC 需要不同的驱动,甚至基于同样的 UDC 的不同板子也需要进行代码修改。

这一层是硬件相关层。它不关心你要做 U 盘还是网卡,只关心一件事:把这个芯片的 USB 设备控制器操作好。

Linux 标准内核里支持各种主流 SOC 的 udc 驱动,比如 S3C2410、PXA270。可以通过内核直接配置支持。也可以修改它们获取更高的效率。比如 s3c2410_udc.c 里没有利用到控制器的 DMA 功能,你可以根据需要改。没有 DMA,大数据量传输全靠 CPU 搬,吞吐会明显受限。

要理解 UDC 驱动代码,必须对相应的硬件控制器熟悉。如果对此不感兴趣或者没时间熟悉,可以暂时跳过硬件相关部分,只看软件结构。本章也侧重软件结构,不深挖寄存器。

五个核心结构体 #

gadget api 提供了 usb device controller 驱动和上层 gadget 驱动交互的接口。这几个结构体是全部交互的载体。

第一个,struct usb_gadget,代表一个 UDC 设备:

c
struct usb_gadget {          /* 代表一个 UDC 设备 */
    /* readonly to gadget driver */
    const struct usb_gadget_ops *ops;   /* 设备的操作集 */
    struct usb_ep   *ep0;               /* ep0(USB 协议中的端点 0),处理 setup() 请求 */
    struct list_head ep_list;           /* 本设备支持的端点链表,元素是 usb_ep */
    enum usb_device_speed speed;        /* 如 USB_SPEED_LOW、USB_SPEED_FULL 等 */
    unsigned is_dualspeed:1;            /* 支持 full/high speed */
    unsigned is_otg:1;                  /* OTG 的特性 */
    unsigned is_a_peripheral:1;         /* 当前是 A-peripheral,而不是 A-host */
    unsigned b_hnp_enable:1;
    unsigned a_hnp_support:1;
    unsigned a_alt_hnp_support:1;
    const char *name;
    struct device dev;
};

注释里那句 readonly to gadget driver 很重要。这个结构由 UDC 驱动填充,功能驱动只能读,不能改。你改了就破坏了 UDC 的状态机。

ep0 是端点 0,专门处理控制传输。所有 SETUP 请求都从这里来,所以 gadget 驱动一定会在 setup 回调里用 gadget->ep0 回数据。ep_list 是双向链表,挂的是这个控制器支持的所有端点,usb_ep_autoconfig 就在这个链表里挑一个合适的给你。speed 和 is_dualspeed 决定设备报什么速度:全速 12Mbps,高速 480Mbps。

第二个,struct usb_gadget_driver,代表一个 gadget 设备 driver:

c
struct usb_gadget_driver {   /* 代表一个 gadget 设备 driver,
                                如 file_storage.c 中的 fsg_driver,
                                又如 zero.c 中的 zero_driver */
    char *function;                             /* 一个字符串,如 "Gadget Zero" */
    enum usb_device_speed speed;
    int  (*bind)(struct usb_gadget *);
    void (*unbind)(struct usb_gadget *);
    int  (*setup)(struct usb_gadget *, const struct usb_ctrlrequest *);
    void (*disconnect)(struct usb_gadget *);
    void (*suspend)(struct usb_gadget *);
    void (*resume)(struct usb_gadget *);

    /* FIXME support safe rmmod */
    struct device_driver driver;
};

这个结构就是第十到十二章反复出现的东西。你写一个 gadget 驱动,本质上就是填这个结构。

第三个,struct usb_gadget_ops,代表设备的操作集:

c
struct usb_gadget_ops {      /* 代表设备的操作集 */
    int (*get_frame)(struct usb_gadget *);
    int (*wakeup)(struct usb_gadget *);
    int (*set_selfpowered)(struct usb_gadget *, int is_selfpowered);
    int (*vbus_session)(struct usb_gadget *, int is_active);
    int (*vbus_draw)(struct usb_gadget *, unsigned mA);
    int (*pullup)(struct usb_gadget *, int is_on);
    int (*ioctl)(struct usb_gadget *, unsigned code, unsigned long param);
};

ep0 上的 usb_ep_ops 才是数据通路,而 usb_gadget_ops 是「设备级」操作。

pullup 是第三章那个上拉电阻的入口。usb_gadget_connect() 最终就调到这里,板级代码 smdk2410_udc_pullup 就是在实现它。set_selfpowered 决定设备是否自供电。vbus_draw 在设备从 VBUS 取电时用,告诉控制器要拉多少毫安。vbus_session 处理 VBUS 的插入和拔出。

第四个,struct usb_ep,代表一个端点:

c
struct usb_ep {              /* 代表一个端点 */
    void *driver_data;
    ...
    const struct usb_ep_ops *ops;   /* 端点的操作集 */
    struct list_head ep_list;       /* gadget 的所有 ep 的 list */
    ...
};

struct usb_ep_ops {          /* 表示端点的操作集 */
    ...
    int (*queue)(struct usb_ep *ep, struct usb_request *req, gfp_t gfp_flags);
    /* 将一个 usb_request 提交给 endpoint,是数据传输的关键函数 */
    ...
};

queue 是整个框架里最核心的一个函数。所有数据收发,最终都是一次 usb_ep_queue。driver_data 这个字段用法有讲究:它是给上层用的私有指针,在 gadget 驱动里设成自己的设备结构体指针,这样在 complete 回调里能从 ep 反查到 dev。

第五个,struct usb_request,表示一个传输的请求。这和 usb host 端的 urb 类似:

c
struct usb_request {         /* 表示一个传输的请求,这与 usb host 端的 urb 类似 */
    void *buf;
    unsigned length;
    dma_addr_t dma;
    unsigned no_interrupt:1;
    unsigned zero:1;
    unsigned short_not_ok:1;
    void (*complete)(struct usb_ep *ep, struct usb_request *req);
    void *context;
    struct list_head list;
    int status;
    unsigned actual;
};

逐个字段说清楚,因为这是最容易踩坑的地方。

字段 含义 踩坑点
buf 数据缓冲区 必须提供。有些控制器只支持 PIO,或者对某些端点不用 DMA
length 缓冲区长度 是「你要多少」,不是「实际收到多少」
dma 对应 buf 的 DMA 地址 不设而控制器又需要时,由控制器映射/取消映射。注意 cache 一致性
no_interrupt 提示不需要完成中断 对 DMA 控制器直接处理深队列有帮助,省中断开销
zero 写数据时补零长度包 数据长度恰是端点最大包整数倍时,主机不知道传完了,得补 ZLP
short_not_ok 把短包当错误 设置后队列停止推进,直到清理
complete 完成回调 此后请求和缓冲区可复用
context 给完成回调的上下文
list 给 gadget 驱动用的链表节点
status 完成码,零或负 errno -ESHUTDOWN 表示设备断开或驱动禁用端点
actual 实际进/出缓冲区的字节数 读会小于 length;IN 传输报完成时数据还留在设备 FIFO 里

complete 的语义再展开一句。读操作以短包结束或者缓冲区填满结束,谁先到算谁。写操作结束时,另有一些数据字节在飞,常在硬件 FIFO 里。错误(读或写)会阻止队列推进,直到完成函数返回,这样被错误作废的传输可以先被出队。

actual 那一行是很多人踩过的地方:IN 传输报告 complete,不代表数据已经到主机了。第八章那个 CSW 没发出去的问题,根子就在这里——前一个请求报完成,硬件还在发,后一个请求排进去时序就错了。

这些请求通过使用它们的端点来分配和释放。硬件的驱动可以在它返回的内存上加额外的 per-request 数据,这样能避免后面队列请求时单独分配内存(会失败)。Bulk 端点可以用任意大小的缓冲区,也可以用于中断传输;只支持中断的端点功能会弱很多。

参考文档在 http://tali.admingilde.org/linux-docbook/gadget/,每个结构体的每个字段都有官方说明。查字段含义时先去那儿,比翻代码快。

UDC 驱动要做什么 #

把要做的事列一下,共五件。

第一,初始化硬件。时钟、PHY、端点 FIFO 大小、上拉 GPIO。第三章那段 UPLL 配置就属于这里。

第二,填充 struct usb_gadget。告诉框架:我叫什么名字、支持几个端点、支持什么速度、ops 在哪。

第三,实现 usb_gadget_ops。至少要有 pullup,别的看硬件能力。

第四,实现每个端点的 usb_ep_ops。核心是 queue、dequeue、enable、disable。

第五,处理中断。传输完成、SETUP 到达、复位、挂起、唤醒,全在中断里分发。

第三和第四是工作量的大头。queue 要做的事:把 usb_request 挂到端点的软件队列上,如果硬件空闲就立刻启动一次传输;如果忙就等着。中断里要做的事:判断是哪个端点,取出完成的请求,填 status 和 actual,调 complete。

为什么这一层最难写 #

因为它和硬件强绑定,没有文档,只有参考实现。S3C2410 的 UDC 驱动一千多行,一半在处理硬件怪癖:某个端点 FIFO 只有 64 字节、某些寄存器写完要延时、复位后要重新配时钟。

这也是为什么移植 gadget 到新芯片上,90% 的工作量在这一层,功能驱动基本不用改。好消息是主流芯片的 UDC 驱动内核里都有,大部分场景直接配就行。

UDC 和 gadget 驱动怎么绑上 #

看第三章那段日志就明白了:

text
0.03 USB: usb_gadget_register_driver() 'g_file_storage'
0.04 USB: binding gadget driver 'g_file_storage'

功能驱动调 usb_gadget_register_driver(),框架拿到 UDC 的 usb_gadget,调功能驱动的 bind,从此两者绑定。

解绑走 usb_gadget_unregister_driver(),它调 unbind。如果此时主机还连着,先 disconnect 再 unbind。

disconnect 和 unbind 的区别常被搞混。disconnect 是「主机拔了」或者「主机复位了」,设备还在,驱动还能再被连;unbind 是「驱动要卸载了」,之后这个 usb_gadget_driver 就不存在了。所以资源释放要做在 unbind 里,状态清理可以做在 disconnect 里。

UDC 层到此。下一章往上一层,看 gadget 驱动怎么写。

十、gadget 功能驱动框架 #

如果内核已经支持了 SOC 的 UDC 驱动,很多时候我们只需要关心这一层。

那么如何编写一个类似 usb 功能驱动的东西?

三个必答问题 #

usb 功能驱动至少要干三件事。

第一,实现 USB 协议中端点 0 部分和具体功能相关的部分。 也就是 UDC 驱动无法替我们做完的部分,比如 USB_REQ_GET_DESCRIPTOR、USB_REQ_GET_CONFIGURATION 这些标准请求的处理。完成了这个,USB 主机端系统就会识别出我们是一个什么样的设备。

注意「和具体功能相关」这个限定。对 GET_DESCRIPTOR 的处理框架不管,因为只有你知道你的设备描述符长什么样。对 SET_ADDRESS 的处理 UDC 硬件管,不用你操心。

第二,实现数据交互功能。 即如何向硬件控制器的端点发出读、写请求来完成数据交互。这就是 usb_ep_queue + complete 那套。

第三,具体功能的实现。 比如如何实现一个 usb net 驱动,或者一个 usb storage 驱动。这一条决定了你的驱动叫什么名字。前两条是骨架,第三条是肉。

zero 设备介绍 #

作为一个简单的 gadget 驱动,zero 的功能基于两个 BULK 端点实现了简单的输入输出功能。它可以用作写新 gadget 驱动的一个实例。

两个 BULK 端点,一个 IN,一个 OUT。基于这两个由底层提供的端点,g_zero 驱动实现了两个 configuration。

第一个提供 sink/source 功能:两个端点一个负责输入,一个负责输出。输出的内容根据设置可以是全 0,也可以是按某种算法生成的数据。

第二个提供 loopback 接口:IN 端点把从 OUT 端点收到的数据反馈给 Host。

两个配置用 bConfigurationValue 区分,主机在 SET_CONFIGURATION 时选择。这个设计让一个驱动能演示两种数据流向,但对初学者增加了理解负担。

注册与注销 #

zero.c 的入口极短:

c
static int __init init(void)
{
    return usb_gadget_register_driver(&zero_driver);
}

module_init(init);

static struct usb_gadget_driver zero_driver = {
#ifdef CONFIG_USB_GADGET_DUALSPEED
    .speed      = USB_SPEED_HIGH,
#else
    .speed      = USB_SPEED_FULL,
#endif
    .function   = (char *) longname,
    .bind       = zero_bind,
    .unbind     = __exit_p(zero_unbind),
    .setup      = zero_setup,
    .disconnect = zero_disconnect,
    .suspend    = zero_suspend,
    .resume     = zero_resume,
    .driver = {
        .name  = (char *) shortname,
        .owner = THIS_MODULE,
    },
};

init 就一行代码,把 zero_driver 交出去,框架负责剩下的。

.driver 这个内嵌的 device_driver 是给驱动模型用的,name 会出现在 /sys/bus/platform/drivers/ 下面。.owner = THIS_MODULE 是引用计数,防止模块在使用中被卸载。

.speed 那个 #ifdef 是老代码的写法。现在用 USB_SPEED_HIGH 加上 is_dualspeed 判断更常见。

六个回调的分工 #

事实上我们的工作就是构建这个 usb_gadget_driver 结构。

回调 何时被调 该做什么
bind 注册驱动时,UDC 可用时 分配资源、申请端点、注册内核设备
setup 主机发来 SETUP 包 处理标准请求和类请求,回数据
disconnect 主机断开或复位 清状态,停端点
unbind 注销驱动 释放资源,注销内核设备
suspend 总线挂起 省电处理
resume 总线唤醒 恢复

setup 是最关键的一个。它处理 host 端发来的 request,比如 get_descriptor 请求。这实现了前面提到的第一个目标。

bind 是另一个关键。它绑定 dev 与 driver,在 gadget driver 注册驱动时被 usb_gadget_register_driver 调用。绑定之后 driver 才能处理 setup 请求。

bind 里通过 usb_ep_autoconfig 函数,可以分配到名为 EP_IN_NAME、EP_OUT_NAME 的端点。后面可以对两个端点发起数据传输请求,和 USB 主机端的 urb 请求非常相似。

发起数据请求大致有这么几步:

c
struct usb_request *req;

req = alloc_ep_req(ep, buflen);              /* 分配请求,数据传输的方向由 ep 本身决定 */
req->complete = source_sink_complete;        /* 请求完成后的处理函数 */
status = usb_ep_queue(ep, req, GFP_ATOMIC);  /* 递交请求 */
free_ep_req(ep, req);                        /* 释放请求,在 complete 中调用 */

这四行是 gadget 数据通路的全部。所有功能驱动都长这样,区别只在于 buffer 里放什么、complete 里做什么。

GFP_ATOMIC 这个标志要注意。端点队列常常在中断上下文里调用,不能睡眠,所以只能用 GFP_ATOMIC。用 GFP_KERNEL 在中断里会直接崩。

在 bind 里注册内核设备 #

如果为了实现某个特定功能,需要在设备端注册字符、块、网络设备驱动,选择的场合是 bind 中注册,unbind 中卸载。

ether.c 是最典型的例子:

c
static int __init
eth_bind(struct usb_gadget *gadget)
{
    ...
    status = register_netdev(dev->net);    /* 注册网卡驱动 */
    ...
}

static void /* __init_or_exit */
eth_unbind(struct usb_gadget *gadget)
{
    ...
    unregister_netdev(dev->net);           /* 注销网卡驱动 */
    ...
}

这个规律解释了第七章那个现象:为什么 g_ether 加载后系统里凭空多出一个 usb0 网卡。因为它的 bind 里调了 register_netdev。同样的道理,g_serial 的 bind 里注册 tty 设备,板子上就多出 /dev/ttyGS0。

g_file_storage 是个例外:它默认不注册任何内核设备,因为它的服务对象是 USB 主机,不是本地内核。加 luns= 或者用 configfs 才能让它在本地也可访问。

这个规律也提醒我们一件事:注册和注销必须在对称的位置。bind 里 register_netdev,unbind 里就得 unregister_netdev,否则模块卸载后网卡还在,再加载就冲突。这也让我们对在设备端实现一个字符、块、网络驱动的结构有了一些了解——它就是普通的内核设备驱动,只不过注册时机由 USB 的 bind/unbind 触发。

描述符的组装 #

zero.c 里描述符是分开定义的,最后用一张表串起来。设备描述符、端点描述符、配置描述符、接口描述符四段:

c
static struct usb_device_descriptor device_desc = {     /* 设备描述符 */
    .bLength            = sizeof device_desc,
    .bDescriptorType    = USB_DT_DEVICE,
    .bcdUSB             = __constant_cpu_to_le16(0x0110),
    .bDeviceClass       = USB_CLASS_VENDOR_SPEC,
    .idVendor           = __constant_cpu_to_le16(DRIVER_VENDOR_NUM),
    .idProduct          = __constant_cpu_to_le16(DRIVER_PRODUCT_NUM),
    .iManufacturer      = STRING_MANUFACTURER,
    .iProduct           = STRING_PRODUCT,
    .iSerialNumber      = STRING_SERIAL,
    .bNumConfigurations = 1,
};

static struct usb_endpoint_descriptor fs_sink_desc = {  /* 端点描述符 */
    .bLength          = USB_DT_ENDPOINT_SIZE,
    .bDescriptorType  = USB_DT_ENDPOINT,
    .bEndpointAddress = USB_DIR_OUT,       /* 对主机端来说,输出 */
    .bmAttributes     = USB_ENDPOINT_XFER_BULK,
};

static struct usb_config_descriptor loopback_config = { /* 配置描述符 */
    .bLength             = sizeof loopback_config,
    .bDescriptorType     = USB_DT_CONFIG,
    /* compute wTotalLength on the fly */
    .bNumInterfaces      = 1,
    .bConfigurationValue = CONFIG_LOOPBACK,
    .iConfiguration      = STRING_LOOPBACK,
    .bmAttributes        = USB_CONFIG_ATT_ONE | USB_CONFIG_ATT_SELFPOWER,
    .bMaxPower           = 1,      /* self-powered */
};

static const struct usb_interface_descriptor loopback_intf = { /* 接口描述符 */
    .bLength         = sizeof loopback_intf,
    .bDescriptorType = USB_DT_INTERFACE,
    .bNumEndpoints   = 1,
    .bInterfaceClass = USB_CLASS_VENDOR_SPEC,
    .iInterface      = STRING_LOOPBACK,
};

static const struct usb_descriptor_header *fs_loopback_function[] = {
    (struct usb_descriptor_header *) &loopback_intf,
    (struct usb_descriptor_header *) &fs_sink_desc,
    NULL,
};

四个结构体各有一处要注意。

bDeviceClass = USB_CLASS_VENDOR_SPEC 是厂商自定义类。zero 不模拟任何标准设备,所以报这个。第三章的 U 盘报 0x08,第七章的网卡报 0x02,差别就在这一个字节。

bEndpointAddress 只写了方向位,没写端点号。这是故意的:端点号由 usb_ep_autoconfig 动态分配后再填进去。不同控制器能给的端点号不一样,写死了就不可移植。

wTotalLength 没写,注释说 on the fly,由 usb_gadget_config_buf() 在 config_buf() 里算出来。bMaxPower = 1 是自供电的含义;真从总线取电要按 2mA 为单位填,250mA 填 125。

最后那张 fs_loopback_function[] 表就是「一个配置里有什么」的声明。config_buf() 拿到它,算出总长度,拼出完整的配置数据。第三章的 U 盘项目里 fsg_config 也是这么一张表,只是端点更多。

字符串描述符单独一组,序列号故意做成 32 字符:

c
static char manufacturer[50];
/* default serial number takes at least two packets */
static char serial[] = "0123456789.0123456789.0123456789";

static struct usb_string strings[] = {          /* 字符串描述符 */
    { STRING_MANUFACTURER, manufacturer, },
    { STRING_PRODUCT,      longname,     },
    { STRING_SERIAL,       serial,       },
    { STRING_LOOPBACK,     loopback,     },
    { STRING_SOURCE_SINK,  source_sink,  },
    { }   /* end of list */
};

static struct usb_gadget_strings stringtab = {
    .language = 0x0409,     /* en-us */
    .strings  = strings,
};

注释说 takes at least two packets,这是在测多包字符串描述符的处理,因为端点 0 一次只能发 64 字节。bInterfaceClass 填 USB_CLASS_VENDOR_SPEC 则意味着主机不认,得自己写主机端驱动。

setup 的三个分支 #

zero_setup 处理主机发来的所有 SETUP 包。简化后的骨架:

c
static int
zero_setup(struct usb_gadget *gadget, const struct usb_ctrlrequest *ctrl)
{
    struct zero_dev *dev = get_gadget_data(gadget);
    struct usb_request *req = dev->req;
    int value = -EOPNOTSUPP;
    u16 w_index  = le16_to_cpu(ctrl->wIndex);
    u16 w_value  = le16_to_cpu(ctrl->wValue);
    u16 w_length = le16_to_cpu(ctrl->wLength);

    req->zero = 0;

    switch (ctrl->bRequest) {
    case USB_REQ_GET_DESCRIPTOR:
        ...
        break;
    case USB_REQ_SET_CONFIGURATION:
        ...
        break;
    default:
    unknown:
        printk("unknown control req %02x.%02x v%04x i%04x l%d\n",
               ctrl->bRequestType, ctrl->bRequest,
               w_value, w_index, w_length);
    }

    /* respond with data transfer before status phase */
    if (value >= 0) {
        req->length = value;
        req->zero = value < w_length;
        value = usb_ep_queue(gadget->ep0, req, GFP_ATOMIC);
        if (value < 0) {
            printk("ep_queue --> %d\n", value);
            req->status = 0;
            zero_setup_complete(gadget->ep0, req);
        }
    }
    return value;
}

结构固定:三个 le16_to_cpu 取字段,一个 switch 分发,最后统一 usb_ep_queue。

le16_to_cpu 不能省。USB 是小端,ARM 会是大端。漏了转换在 x86 上跑得好好的,换块板子就疯。

req->zero = value < w_length 处理短包:设备返回的数据比主机要的少时,补零长度包告诉主机动静。

value 初值 -EOPNOTSUPP。走完 switch 还是负数,就是不认识的请求,直接返回让控制器回 STALL。

GET_DESCRIPTOR 分支再套一层,按描述符类型分:

c
case USB_REQ_GET_DESCRIPTOR:
    if (ctrl->bRequestType != USB_DIR_IN)
        goto unknown;
    switch (w_value >> 8) {
    case USB_DT_DEVICE:                       /* 获取设备描述符 */
        value = min(w_length, (u16) sizeof device_desc);
        memcpy(req->buf, &device_desc, value);
        break;
    case USB_DT_CONFIG:
        value = config_buf(gadget, req->buf, w_value >> 8, w_value & 0xff);
        if (value >= 0)
            value = min(w_length, (u16) value);
        break;
    case USB_DT_STRING:
        value = usb_gadget_get_string(&stringtab, w_value & 0xff, req->buf);
        if (value >= 0)
            value = min(w_length, (u16) value);
        break;
    }
    break;

min(w_length, sizeof device_desc) 这个 min 是关键。主机第一次请求设备描述符时只要 8 字节,先看长度;第二次才要 18 字节。你无脑返回 18 字节,老主机会出错。

配置描述符走 config_buf(),里面把 9 + 9 + 7 = 25 字节拼好:

c
static int config_buf(struct usb_gadget *gadget,
                      u8 *buf, u8 type, unsigned index)
{
    int len;
    const struct usb_descriptor_header **function;
    function = fs_loopback_function;
    /* 配置(9) + 1 个接口(9) + 1 个端点(7) = 25 */
    len = usb_gadget_config_buf(&loopback_config, buf, USB_BUFSIZ, function);
    if (len < 0)
        return len;
    ((struct usb_config_descriptor *) buf)->bDescriptorType = type;
    return len;
}

注释里那个 25 是主机拿到的 wTotalLength。多算少算都会让主机解析错位。

SET_CONFIGURATION 分支才是真正激活端点的地方:

c
case USB_REQ_SET_CONFIGURATION:
    if (ctrl->bRequestType != 0)
        goto unknown;
    spin_lock(&dev->lock);
    value = zero_set_config(dev, w_value);    /* 激活相应的端点 */
    spin_unlock(&dev->lock);
    break;

为什么加锁?SET_CONFIGURATION 会和传输完成中断并发,锁保护的是 dev->out_ep 这个指针。

往下走到 set_loopback_config:

c
static int set_loopback_config(struct zero_dev *dev)
{
    int result = 0;
    struct usb_gadget *gadget = dev->gadget;
    struct usb_ep *ep = dev->out_ep;
    const struct usb_endpoint_descriptor *d = &fs_sink_desc;

    result = usb_ep_enable(ep, d);        /* 激活端点 */
    if (result == 0)
        printk("connected\n");            /* 如果成功,打印 connected */
    else
        printk("can't enable %s, result %d\n", ep->name, result);
    return result;
}

usb_ep_enable() 是端点从「分配了」变成「能用」的一步。分配在 bind 里做,激活在 SET_CONFIGURATION 里做。两个时机不能混——bind 时主机还没配置你,激活端点没有意义,有些控制器会直接报错。

printk("connected\n") 就是第十一章测试步骤里那个 connected 的来源。

bind 里的完整流程 #

zero_bind 是资源准备的地方,步骤多但逻辑清楚:

c
static int __init zero_bind(struct usb_gadget *gadget)
{
    struct zero_dev *dev;
    struct usb_ep *ep;
    int gcnum;

    usb_ep_autoconfig_reset(gadget);
    ep = usb_ep_autoconfig(gadget, &fs_sink_desc);
    /* 根据端点描述符及控制器端点情况,分配一个合适的端点 */
    if (!ep)
        goto enomem;

    EP_OUT_NAME = ep->name;                      /* 记录名称 */

    gcnum = usb_gadget_controller_number(gadget); /* 获得控制器代号 */
    if (gcnum >= 0)
        device_desc.bcdDevice = cpu_to_le16(0x0200 + gcnum);
    else {
        pr_warning("%s: controller '%s' not recognized\n",
                   shortname, gadget->name);
        device_desc.bcdDevice = __constant_cpu_to_le16(0x9999);
    }

    dev = kzalloc(sizeof(*dev), GFP_KERNEL);     /* 分配设备结构体 */
    if (!dev)
        return -ENOMEM;

    spin_lock_init(&dev->lock);
    dev->gadget = gadget;
    set_gadget_data(gadget, dev);

    dev->req = usb_ep_alloc_request(gadget->ep0, GFP_KERNEL);
    if (!dev->req)
        goto enomem;
    dev->req->buf = kmalloc(USB_BUFSIZ, GFP_KERNEL);
    if (!dev->req->buf)
        goto enomem;
    dev->req->complete = zero_setup_complete;

    dev->out_ep = ep;                            /* 记录端点 */
    printk("name=%s\n", dev->out_ep->name);      /* 打印端点名称 */
    ep->driver_data = dev;

    device_desc.bMaxPacketSize0 = gadget->ep0->maxpacket;
    usb_gadget_set_selfpowered(gadget);
    gadget->ep0->driver_data = dev;

    snprintf(manufacturer, sizeof manufacturer, "%s %s with %s",
             init_utsname()->sysname, init_utsname()->release,
             gadget->name);

    /* 字符设备注册 */
    dev_t usb_zero_dev = MKDEV(usb_zero_major, 0);
    int result = register_chrdev_region(usb_zero_dev, 1, "usb_zero");
    if (result < 0) {
        printk(KERN_NOTICE "Unable to get usb_transfer region, error %d\n",
               result);
        return 0;
    }
    usb_zero_setup_cdev(dev, 0);

    return 0;

enomem:
    zero_unbind(gadget);
    return -ENOMEM;
}

几个要点。

usb_ep_autoconfig(gadget, &fs_sink_desc) 拿描述符去问 UDC:你有没有符合这个条件的空闲端点?有就返回一个,并把端点号和最大包长填进描述符副本。这就是为什么 fs_sink_desc 里不用写端点号。

usb_gadget_controller_number() 给控制器一个编号,写进 bcdDevice。纯粹是便于抓包时认芯片,没有协议含义。

set_gadget_data(gadget, dev) 把 dev 挂到 gadget 上,之后任何一个回调都可以用 get_gadget_data(gadget) 取回来。这是 gadget 层的私有指针机制。

ep->driver_data = dev 是另一套指针,挂在端点上的。complete 回调只有 ep 参数,靠这个取到 dev。

device_desc.bMaxPacketSize0 = gadget->ep0->maxpacket 从硬件读端点 0 的最大包长。低速是 8,全速可以 8/16/32/64,高速固定 64。不能瞎填。

snprintf(manufacturer, ...) 把内核版本拼成厂商字符串,所以抓包能看到 Linux 2.6.26 with ...。

最后那段字符设备注册就是第三条目标的体现:这个 gadget 驱动同时提供一个本地字符设备,用户态可以 cat /dev/usb_rcv 读到主机发来的数据。

描述符之外的一个细节 #

zero_bind 里 register_chrdev_region 失败时 return 0,而不是返回错误。

这是老代码的写法,意思是"字符设备注册失败不算致命,USB 功能还能用"。代价是后面的 unbind 会去 unregister_chrdev_region 一个没注册成功的区域,虽然不会崩但不干净。

新写驱动时应该区分:USB 功能必需资源失败就返回错误,可选资源失败打警告继续。

到此,gadget 驱动这一层的骨架讲完了。下一章把这个骨架拿来,做一个只有单个端点、单向接收的最小项目。

十一、一个完整的 gadget 项目 #

通过前面几章的基础,这一章动手写一个简单的 gadget 驱动。重点在让大家快速了解 gadget 驱动结构,不在功能多。

前面介绍的 zero.c 考虑到了多配置、高速传输、USB OTG 等因素。应该说写得比较清楚,是了解 gadget 驱动架构的一个非常好的途径。但把这些东西都放在一起,对很多初学人员来说还是不能快速理解。

那就再简化一些。针对 S3C2410 平台,只实现:

  • 一个配置
  • 一个接口
  • 一个端点
  • 不考虑高速和 OTG
  • 只完成单向从 host 端接收数据
  • 把字符设备驱动结合在里面

这五条约束把复杂度砍掉一大半。不用管 is_dualspeed,不用管多配置切换,不用管 IN 端点,只专心把"主机发数据 → 设备收到 → 用户态读到"这条链打通。

这需要一个 host 端的驱动,来完成向 device 端发送数据。关于在主机端编写一个简单的 USB 设备驱动程序,有很多资料。写完 gadget 端,主机端那个驱动只是配套工具。

两个驱动,一个链路 #

整个项目是两半:

端 模块 作用
PC 主机 usbtransfer.ko 向设备端发送数据
目标板 g_zero.ko 接收数据,暴露成字符设备

板子上的 g_zero.ko 是本章的主角。PC 上的 usbtransfer.ko 只是测试工具,原理就是主机侧驱动里 usb_bulk_msg() 往端点写。

主机端驱动的详细写法,同目录《编写USB 驱动程序》里有,这里不重复。

file_operations 只填了三个:

没有 write,因为方向是单向的,主机发、设备收。想双向就再加 IN 端点和一个 write 实现。

c
static int usb_zero_open(struct inode *inode, struct file *file)  /* 打开设备 */
{
    struct zero_dev *dev = container_of(inode->i_cdev, struct zero_dev, cdev);
    file->private_data = dev;
    init_waitqueue_head(&dev->bulkrq);
    return 0;
}

container_of 从 cdev 反查到 zero_dev,这是内核里标准的反向容器技巧。

init_waitqueue_head 放在 open 里其实不严谨。等待队列应该在 bind 里初始化一次,放 open 里每次打开都重置,如果两次打开之间有请求在等,会被搞乱。单用户测试无所谓,写产品代码要挪出去。

read 是核心:

c
ssize_t
usb_zero_read(struct file *file, const char __user *buf, size_t count, loff_t *f_pos)
{
    struct zero_dev *dev = file->private_data;
    struct usb_request *req;
    int status;
    struct usb_ep *ep;
    struct usb_gadget *gadget = dev->gadget;
    ssize_t ret = 0;
    int result;

    ep = dev->out_ep;

    source_sink_start_ep(ep);            /* 构造、递交读请求 */

    if (count < 0)
        return -EINVAL;

    interruptible_sleep_on(&dev->bulkrq); /* 睡眠,等请求完成 */

    if (copy_to_user(buf, dev->data, dev->data_size)) {  /* 拷到用户空间 */
        ret = -EFAULT;
    } else {
        ret = dev->data_size;
    }

    return ret;
}

顺序值得琢磨。先递交 USB 请求,再睡。这样主机数据到的时候,请求已经在端点队列里等着了,不会错过。

interruptible_sleep_on 这个函数在新内核里已经被删了,因为它有竞态:检查和睡眠之间会有唤醒丢失。正确写法是 wait_event_interruptible(dev->bulkrq, dev->data_size > 0)。老代码能跑,但不够健壮。

copy_to_user 的返回值要检查。返回非零说明有页没拷成功,必须报 -EFAULT,不能装作成功。

还有个隐患:data_size 没有清零。连续两次 read,如果第二次主机没发数据,copy_to_user 会重复拷上一次的内容。完整实现应该在每次 read 开始时把 data_size 归零。

请求的分配和释放 #

c
static struct usb_request *alloc_ep_req(struct usb_ep *ep, unsigned length)
{
    /* 分配请求 */
    struct usb_request *req;

    req = usb_ep_alloc_request(ep, GFP_ATOMIC);
    if (req) {
        req->length = length;
        req->buf = kmalloc(length, GFP_ATOMIC);
        if (!req->buf) {
            usb_ep_free_request(ep, req);
            req = NULL;
        }
    }
    return req;
}

static void free_ep_req(struct usb_ep *ep, struct usb_request *req)
{
    kfree(req->buf);
    usb_ep_free_request(ep, req);
}

两个函数成对,分配顺序和释放顺序相反:先 usb_ep_alloc_request 再 kmalloc,释放时先 kfree 再 usb_ep_free_request。

这个顺序不能颠倒。usb_ep_free_request 之后,req 指针就无效了,再去碰 req->buf 就是 use-after-free。

真正完善的实现会用 usb_ep_alloc_request 的第二个参数让 UDC 驱动把 req 和 buf 分配在一块连续内存上,省一次 kmalloc。老代码没这么做。

完成回调 #

c
static void source_sink_complete(struct usb_ep *ep, struct usb_request *req)
{
    struct zero_dev *dev = ep->driver_data;
    int status = req->status;

    switch (status) {
    case 0:                                   /* normal completion */
        if (ep == dev->out_ep) {
            memcpy(dev->data, req->buf, req->actual);
            /* 返回数据拷贝到 dev->data 中 */
            dev->data_size = req->actual;
            /* 实际长度为 req->actual;需要确认 req->short_not_ok 为 0。
               参考 gadget.h 中关于 usb_request 结构的注释 */
        }
        break;

    /* this endpoint is normally active while we're configured */
    case -ECONNABORTED:                       /* hardware forced ep reset */
    case -ECONNRESET:                         /* request dequeued */
    case -ESHUTDOWN:                          /* disconnect from host */
        printk("%s gone (%d), %d/%d\n", ep->name, status,
               req->actual, req->length);
        /* fall through */
    case -EOVERFLOW:                          /* buffer overrun on read means
                                               * we didn't provide a big
                                               * enough buffer */
    default:
        printk("%s complete --> %d, %d/%d\n", ep->name,
               status, req->actual, req->length);
        /* fall through */
    case -EREMOTEIO:                          /* short read */
        break;
    }

    free_ep_req(ep, req);
    wake_up_interruptible(&dev->bulkrq);      /* 唤醒读函数 */
}

这段是全书最值得逐行读的回调。

dev = ep->driver_data 就是 bind 里那句 ep->driver_data = dev 的回报。complete 只有 ep 参数,不这么传就拿不到设备结构。

case 0 里用 req->actual 而不是 req->length。这是关键:length 是你请求的(128),actual 是实际收到的。主机发 5 字节,actual 就是 5。用 length 会拷进 123 字节垃圾。

回调的顺序也值得对照着看。

-ECONNABORTED / -ECONNRESET / -ESHUTDOWN 三个是端点被复位、请求被取消、主机断开。这三种情况数据都没了,只打印。-EOVERFLOW 是缓冲区溢出,说明你给的 buffer 太小,要加大 USB_BUFSIZ。-EREMOTEIO 是短读,USB 里短包是正常现象,不算错误,直接 break。

fall through 的写法有讲究:-EOVERFLOW 落到 default 是为了统一打印,default 又落到 -EREMOTEIO 是为了统一 break。这个写法能省重复代码,但要注意 -EREMOTEIO 分支里没有 printk,所以短读不会刷屏。

最后两句是无条件执行的:释放请求、唤醒等待的 read。放在 switch 外面很重要,出错路径也要唤醒,否则 cat 就永远睡死了。

递交请求 #

c
static struct usb_request *source_sink_start_ep(struct usb_ep *ep)
{
    /* 构造并发送读请求 */
    struct usb_request *req;
    int status;

    req = alloc_ep_req(ep, 128);
    if (!req)
        return NULL;

    memset(req->buf, 0, req->length);
    req->complete = source_sink_complete;       /* 请求完成函数 */

    status = usb_ep_queue(ep, req, GFP_ATOMIC); /* 递交请求 */
    if (status) {
        struct zero_dev *dev = ep->driver_data;
        printk("start %s --> %d\n", ep->name, status);
        free_ep_req(ep, req);
        req = NULL;
    }
    return req;
}

memset(req->buf, 0, req->length) 清缓冲区。不清的话,主机发 5 字节而 actual 算错时会带出上一次的残留数据。usb_ep_queue 失败要立刻 free_ep_req,不释放就是内存泄漏,而且端点队列里留下一个半成品。

注意 status 非零时 req 被设成 NULL 返回,但调用方 usb_zero_read 没有检查返回值。它照样往下走去睡等待队列——如果队列失败,永远等不到唤醒。这是个真 bug,只是测试场景里 queue 很少失败,没暴露出来。

端点 0 的完成处理 #

c
static void zero_setup_complete(struct usb_ep *ep, struct usb_request *req)
{
    /* 配置端点 0 的请求完成处理 */
    if (req->status || req->actual != req->length)
        printk("setup complete --> %d, %d/%d\n",
               req->status, req->actual, req->length);
}

控制传输的完成回调只做检查,不打正常日志。因为控制传输频率高,每次打会把串口刷爆。

req->actual != req->length 这个判断在控制传输里是有意义的:主机只要 8 字节描述符,你准备了 18 字节,actual 会是 8。这不一定是错误,但值得记录。

复位和断开 #

c
static void zero_reset_config(struct zero_dev *dev)    /* 复位配置 */
{
    usb_ep_disable(dev->out_ep);
    dev->out_ep = NULL;
}

static void zero_disconnect(struct usb_gadget *gadget) /* 卸载驱动时被调用 */
{
    struct zero_dev *dev = get_gadget_data(gadget);

    unregister_chrdev_region(MKDEV(usb_zero_major, 0), 1);
    cdev_del(&(dev->cdev));
    zero_reset_config(dev);

    printk("in %s\n", __FUNCTION__);
}

zero_disconnect 里同时做了两件事:注销字符设备、禁用端点。

严格说,字符设备的注销应该在 unbind 里,disconnect 只该停端点。这里混在一起,后果是主机拔线再接上,字符设备就没了,/dev/usb_rcv 打不开。这是那份代码的一个设计缺陷。写自己的驱动时按第十章那个规律:disconnect 清状态,unbind 放资源。

zero_reset_config 里 usb_ep_disable 之后把指针置 NULL,是为了防止重复 disable,usb_ep_disable(NULL) 会崩。

十二、代码分析 #

代码读得懂和代码跑得起来是两件事。上一章按文件顺序过了一遍,这一章按时序过一遍:主机做一步,设备这边哪个函数被调。

这样读的好处是能建立因果。看到 insmod 后打印 connected,你知道它是 SET_CONFIGURATION 触发的;看到 cat 卡住,你知道它睡在哪个等待队列上。

  └─ usb_zero_open(): init_waitqueue_head(&dev->bulkrq), file->private_data = dev
  └─ usb_zero_read()
       ├─ source_sink_start_ep(dev->out_ep)
       │    ├─ alloc_ep_req(ep, 128)          分配 req + 128 字节 buf
       │    ├─ memset(req->buf, 0, 128)       清零
       │    ├─ req->complete = source_sink_complete
       │    └─ usb_ep_queue(ep, req, GFP_ATOMIC)  请求挂进端点队列
       └─ interruptible_sleep_on(&dev->bulkrq)    ◄── 睡眠,CPU 让出去

此时进程睡死了,但端点队列里挂着请求。主机什么时候发数据,什么时候被唤醒。

text
PC: echo "12345" > /dev/usbtransfer
  └─ 主机侧驱动 usb_bulk_msg() 往 OUT 端点写
       └─ USB 总线传输 ── 设备 UDC 硬件收到,中断
            └─ UDC 驱动取出完成的 req,调 req->complete(ep, req)
                 └─ source_sink_complete()
                      ├─ dev = ep->driver_data
                      ├─ memcpy(dev->data, req->buf, req->actual)
                      ├─ dev->data_size = 5
                      ├─ free_ep_req(ep, req)
                      └─ wake_up_interruptible(&dev->bulkrq)  ◄── 唤醒
                           └─ usb_zero_read 醒来
                                ├─ copy_to_user(buf, dev->data, 5)
                                └─ return 5  ── cat 打印 "12345"

这条链上有两次「交接」,是理解这个驱动的关键。

第一次是 ep->driver_data。UDC 中断里只有 ep,靠这个指针把请求交回给 zero_dev。

第二次是 dev->bulkrq。完成回调在中断上下文里跑,不能直接 copy_to_user,只能把数据放进 dev->data、设置 data_size、唤醒睡着的进程,让进程在进程上下文里做拷贝。

这个「中断里准备数据,进程里拷贝」的模式在内核里到处都是。中断上下文不能睡眠,copy_to_user 会睡眠,所以必须分开。

数据流向图 #

把上面三次时序拼起来,得到完整的调用关系:

层 代码 上下接口
用户态 cat /dev/usb_rcv / echo > /dev/usbtransfer read() / write()
字符设备层 usb_zero_read / usbtransfer_write usb_ep_queue() / usb_bulk_msg()
gadget 层 zero_setup / source_sink_complete(usb_gadget_driver) usb_ep_ops.queue
UDC 层 s3c2410_udc 的 ep_ops / 中断处理(usb_gadget) 寄存器读写
硬件 S3C2410 USB Device Controller USB 总线

上面四层在板子上,最上面那层的一半(usbtransfer)在 PC 上。两个栈通过 USB 总线在中间对接。

这张表能解释很多问题。比如为什么 cat 卡住不动:它在等最下面那层来数据。为什么 connected 在 insmod 之后才出现:因为最下面那层要等主机发配置命令。

三处设计取舍 #

代码里有几个地方可以有不同写法,原作者选了其中一种。理解取舍比记住写法有用。

取舍一:控制请求只分配一个。 dev->req 在整个驱动里只有一个,所有 SETUP 复用。这是因为控制传输天然串行——主机不会同时发两个 SETUP。省内存,也不用管并发。代价是不能在不同 SETUP 之间保留控制请求的 buffer。

取舍二:接收缓冲区固定 128 字节。 data[128] 和 alloc_ep_req(ep, 128) 硬编码。主机一次发超过 128 字节,Bulk 传输会被切成多个包,actual 只报第一个包的长度,后面的丢掉。要支持大块传输得把 buffer 加大,或者做环形缓冲。

取舍三:只用 OUT 端点。 单向接收,所以 fs_loopback_function[] 里只有一个端点描述符。真实的 U 盘 gadget 需要两个 Bulk 端点(一 IN 一 OUT),因为主机既要读也要写。

和 file_storage.c 的对照 #

把这个一百多行的小驱动和第三章那个三千行的 g_file_storage 对照,差别只在功能复杂度。

维度 本项目 g_file_storage
端点数 1 个 Bulk OUT 2 个 Bulk(IN + OUT)+ ep0
描述符 4 个结构体 十几个,含多个 LUN
setup 分支 2 个 case 十来个,含类请求
数据方向 单向 双向,CBW/Data/CSW 三段
协议层 无,裸数据 Bulk-Only + SCSI + 介质
代码量 约 150 行 约 3000 行

最后一列说明一件事:框架是同一套,复杂度全在协议上。g_file_storage 之所以长,是因为它要实现第四章到第六章那三层协议;g_zero 之所以短,是因为它没有协议,主机发什么它就收什么。

这也是为什么学 gadget 应该先读 g_zero:把框架的部分和协议的部分分开,先弄懂前者。

到这里,三层架构、三套协议、两份代码全过了一遍。最后一章把容易踩的坑列成表,当速查用。

三层架构的对应关系 #

搞混层次是最常见的认知错误。一张表定位:

你想改的东西 该改哪一层 文件
设备叫什么名字、VID/PID 功能驱动 zero.c 的描述符
支持几个端点、什么速度 UDC 驱动 s3c2410_udc.c
主机发来某命令怎么答 功能驱动 setup 回调
端点怎么搬数据 UDC 驱动 usb_ep_ops.queue
U 盘读哪个分区 功能驱动 mod_data.file
上拉电阻接哪个 GPIO 板级代码 mach-smdk2410.c

一个判据:凡是和"我这个设备是什么"有关的,在功能驱动;凡是和"这块芯片怎么动"有关的,在 UDC 驱动。

学习路径建议 #

USB 驱动比较难掌握,主要原因有几条:复杂的 USB 协议(基本协议加类规范);控制器包括主机端和设备端,本身相对复杂,其对应的主、从控制器驱动比较复杂;Hub 功能及驱动、管理程序比较复杂;需要专业的硬件测试工具,硬件信号调试较困难;主、从端上层驱动程序本身不难,但由于对硬件不理解,又不好编写测试程序,所以往往望而却步。

针对这几点,建议按下面的顺序学。

步骤 做什么 目标
1 熟悉 USB 协议 不用看完所有协议,重点关注概念、配置过程和数据包格式。枚举流程必须吃透
2 跑通一个现成的 gadget g_file_storage 或 g_ether,先让板子被认出来
3 读 g_zero 一百多行,框架的每个机制都在里面
4 改 g_zero 加 IN 端点做双向,加第二个配置学多配置,加 OTG 支持
5 读 file_storage.c 协议层和框架层都清楚了,三千行只是重复
6 工具备齐 Bushound 或 USB Device Tree Viewer 抓主机侧,lsusb -v 看描述符,串口看内核日志

第三步到第四步之间的跨度最大,也是最容易卡住的地方。读懂和改通是两回事,改的过程才是真正理解的过程。

回到最开始那句话:gadget 是让设备扮演外设的一整套框架,分三层。UDC 管芯片,功能驱动管行为,上层功能管业务。这三层的分界搞清了,gadget 就懂了。

协议那三层也一样:Mass Storage 定身份,Bulk-Only 定传输,SCSI 定命令。任何 USB 设备类都是这个套路。

板子当 U 盘、当网卡、当串口,换的只是最上面那层 .ko。下面两层一个字节都不用动。
