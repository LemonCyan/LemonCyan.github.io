这一篇讲动手。一个 USB 驱动从空文件到插上就能跑，骨架长什么样，每个回调各自管什么，设备拔了以后谁来收尾。写完 probe 和 disconnect，驱动的活就干完了一大半，剩下的都是往这两个函数之间的空隙里填业务。

不讲什么：struct usb_device 的每个成员、urb 在内核里怎么被拆成传输描述符、HCD 怎么扫完成队列——那些在 01-协议与基础概念 的《Linux USB 驱动的结构与 urb》里。差分电平、包格式、枚举时总线上一共走了哪些请求，在《USB 2.0 协议：从物理层到枚举》里。本篇只保留写代码必须知道的那一层。

也不讲：具体设备类的业务实现。摄像头、鼠标、无线网卡各有一篇实例分析，gadget、CDC、自定义 Bulk 也各有专篇。这里用的例子是内核自带的 usb-skeleton（drivers/usb/usb-skeleton.c），它只做数据搬运，不掺任何业务，正好当模板。

怎么读：第一次写驱动，从第一章顺着看，第二章到第五章是骨架的四块砖。要给用户态开接口看第六章，数据怎么发出去看第七章。插上不 probe、拔了不 disconnect，直接翻第八章和第十二章。

一、一个 USB 驱动的最小骨架 #

Linux 的设备模型是三样东西：总线、设备、驱动。USB 这一支也不例外。总线是 usbcore 建出来的那一条，设备是插上去的 U 盘、鼠标、摄像头，驱动是你写的那个 .ko。驱动把自己注册到总线上，总线手里攥着设备和驱动两份名单，负责撮合。

撮合的依据是 ID。设备一侧有 vendor ID 和 product ID，驱动一侧有一张 id_table。两边一对上，总线就把这个设备交给这个驱动。往下的一切都由这个动作发起。

最要紧的一句话先摆在这里：

USB 驱动的骨架 = usb_driver 结构 + probe/disconnect 两个回调 + id_table 匹配表。

设备插入时，内核拿它的 VID/PID 去和所有驱动的 id_table 比对，匹配上就调 probe；拔掉就调 disconnect。驱动的全部工作都在这两个回调之间。第一章到第五章讲的就是这个框怎么搭。

1.1 三块砖，缺一块都跑不起来 #

砖 写什么 缺了会怎样
匹配表 usb_device_id 数组，外加 MODULE_DEVICE_TABLE 设备插上以后内核不知道找你，probe 永远不进
两个回调 probe 负责认领和初始化，disconnect 负责收尾 匹配上了也没代码去接，设备保持无主
外壳 struct usb_driver + usb_register/usb_deregister 模块加载成功，但总线上看不见这个驱动

struct usb_driver 本身没什么神秘的，它就是一张函数指针桌子。老内核里初始化五个字段就够：

字段 填什么 作用
owner THIS_MODULE 引用计数，模块在用的时候不能被 rmmod 掉
name "skeleton" 驱动名，出现在日志和 /sys/bus/usb/drivers/ 下
id_table skel_table 支持的设备列表，匹配就看它
probe skel_probe 匹配成功后内核调它
disconnect skel_disconnect 设备移除或驱动卸载时内核调它

.owner 这一项在 4.x 之后的内核里已经删了，driver core 自己管引用计数。你手上的老代码写着它不要紧，新内核照着抄会编译不过，删掉那行就行。后面还有一堆可选项：suspend、resume、pre_reset、post_reset、supports_autosuspend。先不用管，一个能跑的驱动不需要它们。

1.2 一份能编译的骨架 #

把上面那张表变成代码。这个版本不注册字符设备，只在 probe 里打印设备的 VID/PID 和端点表，验证匹配链路是否打通。

c
#include <linux/module.h>
#include <linux/usb.h>

#define USB_SKEL_VENDOR_ID	0xfff0
#define USB_SKEL_PRODUCT_ID	0xfff0

static const struct usb_device_id skel_table[] = {
	{ USB_DEVICE(USB_SKEL_VENDOR_ID, USB_SKEL_PRODUCT_ID) },
	{ }					/* 终止项，全零 */
};
MODULE_DEVICE_TABLE(usb, skel_table);

static int skel_probe(struct usb_interface *interface,
		      const struct usb_device_id *id)
{
	struct usb_device *udev = interface_to_usbdev(interface);
	struct usb_host_interface *alt = interface->cur_altsetting;
	int i;

	dev_info(&interface->dev, "skel: vid=%04x pid=%04x speed=%d\n",
		 le16_to_cpu(udev->descriptor.idVendor),
		 le16_to_cpu(udev->descriptor.idProduct), udev->speed);

	for (i = 0; i < alt->desc.bNumEndpoints; i++) {
		struct usb_endpoint_descriptor *ep = &alt->endpoint[i].desc;

		dev_info(&interface->dev, "skel: ep addr=0x%02x attr=0x%02x\n",
			 ep->bEndpointAddress, ep->bmAttributes);
	}

	usb_set_intfdata(interface, udev);	/* disconnect 靠它找回来 */
	return 0;
}

static void skel_disconnect(struct usb_interface *interface)
{
	usb_set_intfdata(interface, NULL);
}

static struct usb_driver skel_driver = {
	.owner      = THIS_MODULE,
	.name       = "skeleton",
	.id_table   = skel_table,
	.probe      = skel_probe,
	.disconnect = skel_disconnect,
};

module_usb_driver(skel_driver);
MODULE_LICENSE("GPL");

module_usb_driver() 是个宏，展开就是 module_init/module_exit 加上 usb_register_driver() 与 usb_deregister()。老代码里这两种写法都能见到，效果一样。第二章会把这个宏拆开看。

probe 返回 0 表示认领成功。返回负数表示放弃这个接口，内核接着去找别的驱动。id 参数是匹配表里命中的那一项，你写 { USB_DEVICE(0xfff0, 0xfff0) }，它就把这一项指给你。

1.3 内核里谁在撮合 #

驱动往下发的每一个请求，都要穿过三层。搞清楚哪层管什么，后面看结构体才不会串。

层 代码位置 它管什么 你不该在这一层干的事
设备类驱动 drivers/usb/serial、storage、各类具体驱动 认领接口、跑业务协议、收发数据 直接读写控制器寄存器
usbcore（USBD） drivers/usb/core 枚举、配置、接口与驱动匹配、urb 排队、hub 驱动 关心 qTD 长什么样
HCD drivers/usb/host urb 翻成传输描述符、DMA 映射、中断处理、根 hub 关心你的业务协议

HCD 是直接和硬件打交道的模块，是协议栈最底下那层。它向上只对总线驱动服务，提供一套 HCDI 接口，把各家控制器的硬件差异抹平；向下管控制器本身：初始化、根 hub 的配置与控制、四种传输类型的落地。usbcore 是中间那层，管总线、设备、带宽、四种传输、hub 驱动，还负责给设备类驱动提供接口。你写的驱动是第三层，只和 usbcore 说话。

嵌入式 Linux 里 HCD 和 usbcore 已经有了，不需要重写。你要补的就是最上面那层设备类驱动。驱动目录按这个分层摆着，找参考代码的时候照着翻：

text
drivers/usb/core        usbcore，所有驱动都注册到它里面
drivers/usb/host        主机控制器驱动（嵌入式 OTG 常见 dwc_otg、dwc3）
drivers/usb/serial      串行设备（3G 卡、蓝牙这类）
drivers/usb/storage     大容量存储（U 盘）
drivers/usb/usb-skeleton.c   客户驱动框架，本篇的模板

数据往下走只有一条路，回来靠中断。这条路径的细节归《Linux USB 驱动的结构与 urb》，这里只留一句：你的驱动从头到尾没碰过寄存器，你表达的只有「往哪个端点发多少字节，发完叫我」。

1.4 一次插入到拔出，五段 #

设备插到 hub 端口上，hub 的中断端点报上来一位状态变化。hub 线程醒来，复位端口、分配总线地址、读设备描述符、读配置描述符。usbcore 按配置建出 usb_interface，逐个和已注册驱动的 id_table 比对。对上了，调你的 probe。设备拔掉或者驱动被 rmmod，走 disconnect。

段 谁干的 你的代码在哪
1. 端口电平变化被发现 hub 驱动 + 中断 没你的事
2. 复位、分配地址、读描述符 hub 线程 没你的事
3. 建接口，比对 id_table usbcore 你提供匹配表
4. 调用 probe usbcore 你的初始化全在这里
5. 调用 disconnect usbcore 你的清理全在这里

第 3 步那一次比对是分水岭。在这之前，设备在总线上是个没人管的孤儿；在这之后，它有了主人。第 4 步到第 5 步之间，就是你这个驱动的全部人生。

1.5 这篇要建立的三个直觉 #

驱动挂在接口上，不是挂在设备上。probe 一次只给你一个 usb_interface，其他的接口不归你。新手常犯的错是把 usb_driver 想成「一个设备一个驱动」，然后在 probe 里遍历所有接口。不要这么干。摄像头带麦克风的设备，视频接口归 uvcvideo，音频接口归 snd-usb-audio，两个驱动互不知道对方存在，共享同一个 usb_device。你要拿父对象，用 interface_to_usbdev(intf)。

probe 里能睡。它在进程上下文跑，kmalloc(GFP_KERNEL)、usb_control_msg()、msleep() 都能用。这一点和中断上下文里的代码完全不同，别搞混。数据收发的完成回调在中断上下文里跑，那里不能睡。

错误处理要用 goto 链。资源一项一项申请，失败就顺着标号往回退。这是内核驱动的标准写法，不是坏习惯。第四章会把这个链条完整写一遍。

二、模块的加载与卸载 #

USB 驱动尤其是这种热插拔设备的驱动，绝大多数编译成模块，需要的时候才挂到内核里。所以它的注册与卸载和普通模块没什么两样，只是把「向内核注册一个字符设备」换成了「向 USB 子系统注册一个 usb_driver」。

2.1 注册与注销的一对函数 #

向 USB 子系统注册用 usb_register()，注销用 usb_deregister()。对比 I2C 那边的 i2c_add_driver() 和 i2c_del_driver()，形状是一样的：传一个结构体指针进去，内核把它挂到总线的驱动链表上。

c
static int __init usb_skel_init(void)
{
	int result;

	/* 把驱动注册进 USB 子系统 */
	result = usb_register(&skel_driver);
	if (result)
		err("usb_register failed. Error number %d", result);

	return result;
}

static void __exit usb_skel_exit(void)
{
	usb_deregister(&skel_driver);	/* 从 USB 子系统里注销 */
}

module_init(usb_skel_init);
module_exit(usb_skel_exit);
MODULE_LICENSE("GPL");

err() 是 usb-skeleton 自己定义的打印宏，展开成带文件名前缀的 printk(KERN_ERR ...)。你自己写驱动的时候换成 pr_err() 或者 dev_err()，别去抄这个宏。

这两段就是整个模块的进出口。__init 和 __exit 两个标记让内核在初始化完成后把这些代码占的内存释放掉，模块卸载函数只在编译成模块时才有意义。

2.2 那行 module_usb_driver 展开是什么 #

内核后来加了个宏，把上面这一整套压成一行 module_usb_driver(skel_driver);。展开之后等价于：

c
static int __init skel_driver_init(void)
{
	return usb_register_driver(&skel_driver, THIS_MODULE, KBUILD_MODNAME);
}

static void __exit skel_driver_exit(void)
{
	usb_deregister(&skel_driver);
}

module_init(skel_driver_init);
module_exit(skel_driver_exit);

usb_register_driver() 比 usb_register() 多两个参数：模块指针和模块名。usb_register() 是个兼容包装，内部转调它并补上 THIS_MODULE。新代码直接写宏最省事，老代码写全套也照样能编译。

2.3 加载和卸载时到底发生了什么 #

insmod 的时候，模块初始化函数跑起来，usb_register() 把 skel_driver 挂到 USB 总线的驱动链表上。挂上去的瞬间，usbcore 会拿当前总线上已有的所有设备去和这张 id_table 比对一遍。所以有一种情况你会看到：模块一加载，probe 立刻就进了，因为设备早就插着了，只是之前没驱动认领。

动作 内核做了什么 你看到的现象
insmod skeleton.ko 注册 usb_driver，回头扫一遍已有设备 设备已在位的话，probe 立刻执行
rmmod skeleton 注销 usb_driver，对每个绑定的接口调 disconnect 一连串 disconnect 日志
设备插入 枚举完成后比对 id_table，命中就 probe probe 日志 + 设备节点出现
设备拔出 找到绑定驱动，调 disconnect disconnect 日志 + 节点消失

rmmod 之前要确认引用计数归零。如果你的设备节点还开着（用户态有进程 hold 着），rmmod 会返回 -EBUSY。这不是内核在找麻烦，是 owner 那个字段在起作用。

2.4 卸载顺序的坑 #

usb_deregister() 会替你调 disconnect，这一点别搞错。有人在 usb_skel_exit() 里先手动调一遍清理函数，再调 usb_deregister()，结果 disconnect 里对着已经释放的内存又清一次，直接 panic。

正确的顺序只有一句：清理逻辑全部写在 disconnect 里，卸载函数只调 usb_deregister()。这样不管是拔设备还是卸模块，走的都是同一条路径，不会有两套清理代码需要同步维护。

还有一条：usb_deregister() 返回的时候，可以认为所有 probe 和 disconnect 都已经跑完了，不会再有回调进来。所以卸载函数返回之后，模块的代码段就可以安全回收。这个保证是 usb_deregister 内部拿锁等出来的，不用你自己加同步。

三、id_table 与设备匹配 #

匹配表是驱动和内核之间的第一句话。它说的是：这些设备归我管，别的别找我。

id_table 的类型是 struct usb_device_id 数组，末尾一项全零。内核从头扫到尾，命中哪一项就把那一项作为 probe 的第二个参数递给你。

c
static const struct usb_device_id skel_table[] = {
	{ USB_DEVICE(USB_SKEL_VENDOR_ID, USB_SKEL_PRODUCT_ID) },
	{ }					/* 终止项 */
};
MODULE_DEVICE_TABLE(usb, skel_table);

3.1 usb_device_id 里到底有什么 #

这个结构体只保留两个字段，其余全是匹配依据：

c
struct usb_device_id {
	__u16		match_flags;	/* 下面哪些字段参与匹配 */

	__u16		idVendor;	/* 制造商 ID */
	__u16		idProduct;	/* 产品 ID */
	__u16		bcdDevice_lo;	/* 设备版本号下限 */
	__u16		bcdDevice_hi;	/* 设备版本号上限 */

	__u8		bDeviceClass;	/* 设备类 */
	__u8		bDeviceSubClass; /* 设备子类 */
	__u8		bDeviceProtocol; /* 设备协议 */

	__u8		bInterfaceClass;    /* 接口类 */
	__u8		bInterfaceSubClass; /* 接口子类 */
	__u8		bInterfaceProtocol; /* 接口协议 */

	kernel_ulong_t	driver_info;	/* 给驱动自己用的私有数据 */
};
字段 从哪来 什么时候用它匹配
match_flags 你自己填 决定上面哪些字段参与比对
idVendor / idProduct 设备描述符 单一功能设备，最常用的路子
bcdDevice_lo / _hi 设备描述符 同 PID 不同硬件版本的型号要分开处理
bDeviceClass/SubClass/Protocol 设备描述符 整个设备都属于某一类（HID、Mass Storage）
bInterfaceClass/SubClass/Protocol 接口描述符 复合设备，一个物理设备里的某个功能归你
driver_info 你自己填 不参与匹配，纯粹是随身带的数据

match_flags 不用手写，那几个宏会替你拼好。

3.2 四个宏，四种匹配尺度 #

宏 匹配依据 用在什么设备上
USB_DEVICE(vid, pid) vid + pid 单一功能设备，最常见
USB_DEVICE_VER(vid, pid, lo, hi) vid + pid + 版本号范围 同 PID 但硬件改过版
USB_DEVICE_INFO(cls, sub, proto) 设备类 / 子类 / 协议 整设备属于某一类
USB_INTERFACE_INFO(cls, sub, proto) 接口类 / 子类 / 协议 复合设备必须用这个 
c
static const struct usb_device_id demo_ids[] = {
	/* 精确到 vid/pid */
	{ USB_DEVICE(0x1234, 0x5678) },
	/* 同 vid/pid，只认版本 0x0100 到 0x01ff */
	{ USB_DEVICE_VER(0x1234, 0x5678, 0x0100, 0x01ff) },
	/* 按设备类匹配，三个参数是 class/subclass/protocol */
	{ USB_DEVICE_INFO(0xe0, 0x01, 0x01) },
	/* 按接口类匹配，HID 设备 */
	{ USB_INTERFACE_INFO(USB_CLASS_HID, 0, 0) },
	{ }
};

USB_INTERFACE_INFO 的三项分别对应 bInterfaceClass、bInterfaceSubClass、bInterfaceProtocol。想通配某一项，填 USB_CLASS_ANY（就是 0xff 那套约定）或者干脆用更宽的宏。复合设备必须走接口匹配，因为你只认领其中一个功能，设备级的类字段描述的是整体，对不上。

也可以直接写位，不绕宏：

c
static const struct usb_device_id demo_ids[] = {
	{ .match_flags = USB_DEVICE_ID_MATCH_INT_CLASS,
	  .bInterfaceClass = 0x08 },	/* 大容量存储 */
	{ }
};

这种写法比宏直白，也更容易在旁边写注释说明为什么这么匹配。调试匹配问题时，把 match_flags 的位和 usb_device_id 的字段对上，是最快定位的方法。

3.3 MODULE_DEVICE_TABLE 那行不能省 #

第一个参数是设备类型，USB 设备就写 usb；第二个参数是表名。这行宏把匹配表导出成模块信息，depmod 读它生成别名（形如 usb:v1234p5678d*dc*dsc*dp*ic*isc*ip*），udev 在设备插入时按别名去找该 modprobe 哪个模块。

写没写 手动 insmod 热插拔自动加载
写了 正常 正常，udev 能顺着别名找到模块
没写 正常 不会自动加载，你得自己 modprobe

漏了这一行，代码本身没错，手动加载时 probe 也照进，但插上设备自动加载这条路就断了。这个坑很隐蔽，因为编译、加载、匹配全部正常，只有「插上就自动跑」不好使。

3.4 匹配不上怎么办 #

probe 不执行的排查顺序：

检查项 怎么看 常见原因
驱动的 ID 有没有注册 ls /sys/bus/usb/drivers/ 模块没加载成功
设备的 VID/PID 是多少 lsusb 或 /sys/bus/usb/devices/*/idVendor 表和实际设备对不上
匹配表导出没有 modinfo skeleton.ko | grep alias 漏了 MODULE_DEVICE_TABLE
接口是否已被别的驱动占了 ls /sys/bus/usb/devices/X-Y:1.0/ 有 driver 软链说明已被认领
是设备级还是接口级匹配 对比 bDeviceClass 与 bInterfaceClass 复合设备用错了宏

最后一项最容易踩。一个 U 盘的整体设备类是 0，具体功能挂在接口上（接口类 8）。你用 USB_DEVICE_INFO(0x08, ...) 去匹配设备级，永远匹配不到。

临时验证还有个办法：往 sysfs 里写 new_id，绕过 id_table 直接让驱动认领一个设备，echo "1234 5678" > /sys/bus/usb/drivers/skeleton/new_id。写进去 probe 就进了，说明问题出在匹配表；还是不进，问题在 probe 内部或者接口已经被占用。生产驱动一般把 no_dynamic_id 置 1 关掉这个入口。

四、probe：探测与初始化 #

probe 是驱动真正开始干活的地方。它拿到一个接口和一个命中的 ID，要在这一个函数里完成三件事：判断这个接口能不能干、把资源申请齐、把私有数据挂上去让后面找得到。

签名是这样的：

c
static int skel_probe(struct usb_interface *interface,
		      const struct usb_device_id *id)
参数 是什么 你拿它干什么
interface 要被认领的接口，一般是设备的第 0 号接口 拿端点表、挂私有数据、注册设备节点
id 匹配表里命中的那一项 读 driver_info 区分同驱动的多个型号

返回值只有两种含义：0 表示认领成功，负值表示放弃。放弃以后内核会继续拿别的驱动去试这个接口。

4.1 probe 里干的六件事 #

顺序很重要，写乱了出错处理就会漏资源。

步 做什么 失败返回
1 拿 cur_altsetting，确认端点够不够 -ENODEV
2 分配私有结构 usb_skel -ENOMEM
3 遍历端点，找出 bulk in/out，存地址和包长，申请接收缓冲 -ENODEV/-ENOMEM
4 usb_set_intfdata() 把私有数据挂到接口上 不会失败
5 usb_register_dev() 注册字符设备，拿次设备号 负值
6 设备相关初始化，发控制请求配硬件 负值，走回滚

第 1 步别省。设备实际的端点表和你写在代码里的假设不一定对得上，先确认再干活，不对就干净退出。省掉它，后面遍历端点找不到 bulk 端点时才失败，那时候已经分配了内存。

4.2 私有结构：把接口状态攒在一个地方 #

c
struct usb_skel {
	struct usb_device	*udev;			/* USB 设备 */
	struct usb_interface	*interface;		/* 当前接口 */
	struct semaphore	limit_sem;		/* 限制同时进行的写操作数 */
	unsigned char		*bulk_in_buffer;	/* 接收缓冲区 */
	size_t			bulk_in_size;		/* 接收缓冲区大小 */
	__u8			bulk_in_endpointAddr;	/* bulk in 端点地址 */
	__u8			bulk_out_endpointAddr;	/* bulk out 端点地址 */
	struct kref		kref;			/* 引用计数 */
};
成员 干什么用
udev 发 urb 时填 urb->dev，也从这儿取 VID/PID
interface 出错打印用 &interface->dev，注册设备用
limit_sem 信号量，限制并发写的数量，防止一次塞太多 urb
bulk_in_buffer / bulk_in_size 接收缓冲，probe 里按端点包长申请
bulk_in_endpointAddr 端点地址，发 urb 时填 urb->pipe
bulk_out_endpointAddr 同上，方向相反
kref 引用计数，多进程同时打开时靠它判断最后一个用户何时走

这是 usb-skeleton 的定义。你自己写的时候照着这个形状来，字段按业务加减，习惯别改：一个接口一份私有数据，全部状态都塞在里面。全局变量在 USB 驱动里是灾难，因为同时插两个同型号设备是常态。

4.3 找端点，存地址 #

下面是 probe 里最核心的一段循环。它扫一遍接口的端点表，把第一个 bulk in 和第一个 bulk out 记下来。

c
	/* 只用第一个 bulk in 和第一个 bulk out 端点 */
	iface_desc = interface->cur_altsetting;
	for (i = 0; i < iface_desc->desc.bNumEndpoints; ++i) {
		endpoint = &iface_desc->endpoint[i].desc;

		if (!dev->bulk_in_endpointAddr &&
		    ((endpoint->bEndpointAddress & USB_ENDPOINT_DIR_MASK) == USB_DIR_IN) &&
		    ((endpoint->bmAttributes & USB_ENDPOINT_XFERTYPE_MASK) ==
		     USB_ENDPOINT_XFER_BULK)) {
			/* 找到了 bulk in */
			buffer_size = le16_to_cpu(endpoint->wMaxPacketSize);
			dev->bulk_in_size = buffer_size;
			dev->bulk_in_endpointAddr = endpoint->bEndpointAddress;
			dev->bulk_in_buffer = kmalloc(buffer_size, GFP_KERNEL);
			if (!dev->bulk_in_buffer) {
				err("Could not allocate bulk_in_buffer");
				goto error;
			}
		}

		if (!dev->bulk_out_endpointAddr &&
		    ((endpoint->bEndpointAddress & USB_ENDPOINT_DIR_MASK) == USB_DIR_OUT) &&
		    ((endpoint->bmAttributes & USB_ENDPOINT_XFERTYPE_MASK) ==
		     USB_ENDPOINT_XFER_BULK)) {
			/* 找到了 bulk out */
			dev->bulk_out_endpointAddr = endpoint->bEndpointAddress;
		}
	}

	if (!(dev->bulk_in_endpointAddr && dev->bulk_out_endpointAddr)) {
		err("Could not find both bulk-in and bulk-out endpoints");
		goto error;
	}

这段代码里的判断条件分三层，缺一层都会认错端点：!dev->bulk_in_endpointAddr 表示还没找到过，这是「只取第一个」的实现方式；(bEndpointAddress & USB_ENDPOINT_DIR_MASK) == USB_DIR_IN 判方向，端点地址第 7 位是方向位，1 为 IN；(bmAttributes & USB_ENDPOINT_XFERTYPE_MASK) == USB_ENDPOINT_XFER_BULK 判类型。三个条件同时成立才认。少第一个会覆盖成最后一个端点，少第二个会把 OUT 当成 IN，少第三个会把中断端点当批量端点用。wMaxPacketSize 要过 le16_to_cpu()，USB 描述符是小端，跑在大端机器上不过这一下就是天文数字。发送的 bulk 包可以大于这个值，控制器会拆成多个包发，但缓冲区分配还是按它来最省。

端点描述符里每个字段的含义，以及四种端点类型：

字段 含义 怎么用
bEndpointAddress 8 位地址，第 7 位是方向 判方向用掩码 USB_ENDPOINT_DIR_MASK
bmAttributes 端点类型 掩码 USB_ENDPOINT_XFERTYPE_MASK 取值后比对
wMaxPacketSize 端点一次能处理的最大字节数 申请缓冲区按它来，注意 le16_to_cpu
bInterval 中断端点的轮询间隔（毫秒） 批量端点用不上
bmAttributes 掩出来的值 类型 典型用途
USB_ENDPOINT_XFER_CONTROL 控制 枚举、类请求
USB_ENDPOINT_XFER_ISOC 等时 音视频流
USB_ENDPOINT_XFER_BULK 批量 大块数据，U 盘、打印机
USB_ENDPOINT_XFER_INT 中断 小数据、低延迟，鼠标键盘

4.4 把私有数据挂到接口上 #

c
	usb_set_intfdata(interface, dev);

这一行把 dev 指针存进 interface 的 devdata 字段。之后任何一个拿到 interface 的地方，都能用 usb_get_intfdata(interface) 把它取回来。为什么必须这么绕？因为 file_operations 里的 open、read、write 只给你一个 struct inode * 或者 struct file *，你不能直接从里面变出私有数据。走的路是：inode → i_cdev → container_of 拿到 usb_class 里的 interface，再 usb_get_intfdata。中间那一步就靠这里挂上去的指针。

这一步必须早于任何会触发异步操作的调用。urb 的完成回调里要靠 usb_get_intfdata() 找回私有数据，挂晚了就是空指针。它的位置在端点信息填完之后、注册字符设备之前，是最稳的。

4.5 注册字符设备 #

如果驱动没有挂到别的子系统中（输入、tty、视频、网络），而是直接用 USB 主设备号给用户态提供传统字符设备接口，那就要在 probe 里注册：

c
	retval = usb_register_dev(interface, &skel_class);
	if (retval) {
		err("Not able to get a minor for this device.");
		usb_set_intfdata(interface, NULL);
		goto error;
	}

第二个参数是 struct usb_class_driver，不是 file_operations：

c
static struct usb_class_driver skel_class = {
	.name       = "skel%d",
	.fops       = &skel_fops,
	.minor_base = USB_SKEL_MINOR_BASE,
};
字段 填什么 作用
name "skel%d" 设备节点名，%d 会被换成次设备号
fops &skel_fops 真正的文件操作表，IO 全在这里
minor_base 次设备号起点 内核从这个基数开始分配

usb_class_driver 才是定义设备 IO 的地方，它的核心是 fops。注册成功之后，interface->minor 就有值了，用 USB_SKEL_MINOR_BASE + interface->minor 拼出完整次设备号，设备节点 /dev/skel0 也就出来了。

为什么 usb_register_dev() 的第一个参数是 interface 而不是 device？因为一个 USB 设备可以有多个接口，每个接口的 IO 操作完全不同。注册的单位是接口，不是设备。minor_base 加 minor 这套机制本来就是用来区分不同接口的，只不过 usb-skeleton 这个例子只有一个接口，从代码上不容易察觉。

4.6 用 goto 搭错误处理链 #

资源一项一项申请，失败就顺着标号往回退。这是内核驱动的标准写法，不是坏习惯。

c
static int skel_probe(struct usb_interface *interface,
		      const struct usb_device_id *id)
{
	struct usb_skel *dev;
	struct usb_host_interface *iface_desc;
	struct usb_endpoint_descriptor *endpoint;
	size_t buffer_size;
	int i, retval = -ENOMEM;

	/* 1. 分配私有结构，kzalloc 会清零 */
	dev = kzalloc(sizeof(*dev), GFP_KERNEL);
	if (!dev)
		return -ENOMEM;
	kref_init(&dev->kref);
	sema_init(&dev->limit_sem, USB_SKEL_MAX_WRITES);
	dev->udev = usb_get_dev(interface_to_usbdev(interface));
	dev->interface = interface;

	/* 2. 找端点：循环体见 4.3，内部失败 goto error */
	iface_desc = interface->cur_altsetting;
	for (i = 0; i < iface_desc->desc.bNumEndpoints; ++i) {
		endpoint = &iface_desc->endpoint[i].desc;
		/* ... */
	}

	/* 3. 挂私有数据 */
	usb_set_intfdata(interface, dev);

	/* 4. 注册字符设备 */
	retval = usb_register_dev(interface, &skel_class);
	if (retval) {
		err("Not able to get a minor for this device.");
		usb_set_intfdata(interface, NULL);
		goto error;
	}

	dev_info(&interface->dev, "USB Skeleton now attached to USBSkel-%d",
		 interface->minor);
	return 0;

error:
	/* 走到这里说明前面某一步失败了，把已经申请的按倒序退掉 */
	kref_put(&dev->kref, skel_delete);
	return retval;
}

链条的形状看清楚：正向申请，反向释放，标号只放一处。前面申请了 A、B、C，C 失败跳 err_c，退 B 和 A；B 失败跳 err_b，退 A；A 失败直接 return。多个标号层层往下，最后一个标号后面是公共清理。三个容易写错的地方：

错法 后果 正确做法
每个失败点都手写一遍清理 改代码时漏改一处，漏资源 用标号，一处清理
标号里的释放顺序和申请顺序一致 依赖关系颠倒，释放了还在用的东西 严格倒序
goto 跳过去以后又 return 后面的标号永远执行不到 标号只往下走，不往回跳

资源计数要成对。usb_get_dev() 对应 usb_put_dev()，usb_alloc_urb() 对应 usb_free_urb()，kmalloc() 对应 kfree()，usb_register_dev() 对应 usb_deregister_dev()。少一对就是泄漏，多一对就是 use-after-free。这两样在内核里都是慢慢积累、随机爆发的故障，查起来极费劲。

kref 这一层是为多进程同时打开准备的。skel_open() 里 kref_get()，skel_release() 里 kref_put()，最后一个用户走的时候才真正释放内存。disconnect 里也 kref_put() 一次，把 probe 时建立的那份引用交回去。三方各持一份，谁都不越界。

五、disconnect：断开与清理 #

设备被拔掉，或者驱动被卸载，usbcore 就会调你的 disconnect。它干的事和 probe 严格相反：把 probe 申请的东西一样一样还回去。

c
static void skel_disconnect(struct usb_interface *interface)
{
	struct usb_skel *dev;
	int minor = interface->minor;

	dev = usb_get_intfdata(interface);
	usb_set_intfdata(interface, NULL);

	/* 交还次设备号，去掉设备节点 */
	usb_deregister_dev(interface, &skel_class);

	/* 减少引用计数，最后一个用户走时才会真正释放 */
	kref_put(&dev->kref, skel_delete);

	dev_info(&interface->dev, "USB Skeleton #%d now disconnected", minor);
}

disconnect 做的事情不多，但顺序一步都不能错。核心就两句：先把私有数据从接口上摘下来，再把在飞的 urb 收干净，最后才释放内存。

5.1 顺序：先摘，再停，后放 #

步 动作 为什么放这个位置
1 usb_get_intfdata() 取私有数据 后面全靠这个指针
2 usb_set_intfdata(interface, NULL) 掐断并发路径，防止别人再取到
3 usb_deregister_dev() 交还次设备号 节点没了，用户态开不了新 fd
4 停掉定时器、workqueue、在飞的 urb 不再有新的回调进来
5 kref_put() 交回引用 引用归零才真正释放

第 2 步必须紧跟第 1 步。这两行之间如果插进别的活，并发路径上就有机会再拿一次指针，然后你把它释放了，那边还在用。

第 3 步要在第 4 步之前。节点先消失，用户态就没法再 open 出新的使用者，你在第 4 步停 urb 的时候才不用考虑新来的请求。

5.2 在飞的 urb 必须收干净 #

c
	/* 停掉所有还在飞的 urb，并等回调都执行完 */
	usb_kill_urb(dev->urb);

	/* 放缓冲 */
	usb_free_coherent(dev->udev, dev->bulk_in_size,
			  dev->bulk_in_buffer, dev->bulk_in_dma);

	/* 放 urb */
	usb_free_urb(dev->urb);

	/* 放私有数据 */
	kfree(dev);

usb_kill_urb() 会同步等待 urb 的完成回调执行完才返回。这是它和 usb_unlink_urb() 的关键差别，也是 disconnect 里唯一安全的做法。设备已经拔了，urb 提交上去必然失败，回调会立刻带着 -ESHUTDOWN 进来。如果你在这之前就把 dev 释放了，那个回调就是标准的 use-after-free。

忘了停 urb，故障现象是这样的：拔掉设备当时没事，过几秒内核报 BUG: unable to handle kernel paging request，调用栈停在你的完成回调里。这种延迟崩溃最难查，因为它和拔线这个动作在时间上隔了一段。

5.3 定时器和 workqueue 要提前停 #

驱动里用了定时器或者工作队列的，在第 4 步要先把它们停掉：del_timer_sync(&dev->timer); 和 cancel_work_sync(&dev->work);。两个都是同步的，返回时能保证回调已经不在跑了。用 del_timer() 不行，它不等待。

最容易漏的一种写法：定时器回调里重新提交 urb。你在 disconnect 里停了 urb，但定时器还在跑，过一会它又提交一次，那个 urb 已经被 usb_free_urb() 释放了。停定时器这一步必须排在停 urb 之前，或者至少和它在同一个同步范围内。

5.4 卸载路径和拔出路径是同一条 #

usb_deregister() 会遍历所有绑定在这个驱动上的接口，逐个调 disconnect。所以卸载模块和拔设备的清理路径完全一样，你不需要写两套。

这也意味着一件事：disconnect 里不能去区分「是拔线还是卸模块」。有些驱动想在卸模块时多做点事，用标志位去区分，这么做早晚会漏一条路径。真有必要区分的逻辑，放到模块退出函数里、usb_deregister() 之后去做。

disconnect 返回之后，usbcore 认为这个接口已经干净了，不会再往你的回调里送任何东西。这个保证让 kfree(dev) 放在函数最后是安全的。

六、file_operations：给用户态提供接口 #

到这里，驱动在内核侧已经完整了：能匹配、能初始化、能清理。但用户态还看不见它。要开一个 /dev/skel0 出来，让 read/write/ioctl 能落到你的代码上，就得填 file_operations。

c
static const struct file_operations skel_fops = {
	.owner   = THIS_MODULE,
	.read    = skel_read,
	.write   = skel_write,
	.open    = skel_open,
	.release = skel_release,
};
回调 什么时候进来 你在这里干什么
open 用户态 open("/dev/skel0") 取私有数据、加引用、取自动挂起
release 最后一个 fd 被 close 放引用、放自动挂起
read 用户态 read() 从设备收数据，拷到用户缓冲
write 用户态 write() 从用户缓冲取数据，发到设备
ioctl 用户态 ioctl() 类请求、私有命令

6.1 open：从 inode 摸回私有数据 #

open 的签名只有 inode 和 file，私有数据不在参数里。得自己摸回去：

c
static int skel_open(struct inode *inode, struct file *file)
{
	struct usb_skel *dev;
	struct usb_interface *interface;
	int subminor = iminor(inode);
	int retval = 0;

	/* 从次设备号摸回 interface，再取私有数据 */
	interface = usb_find_interface(&skel_driver, subminor);
	if (!interface) {
		err("can't find device for minor %d", subminor);
		return -ENODEV;
	}
	dev = usb_get_intfdata(interface);
	if (!dev)
		return -ENODEV;

	/* 加一次引用，防止 open 期间被 disconnect 释放掉 */
	kref_get(&dev->kref);
	file->private_data = dev;

	/* 通知 USB 核心：接口正在被使用，别自动挂起 */
	if (!dev->open_count++) {
		retval = usb_autopm_get_interface(interface);
		if (retval) {
			dev->open_count--;
			kref_put(&dev->kref, skel_delete);
		}
	}
	return retval;
}

kref_get() 这一步很关键。假设用户态刚 open 成功，usb_get_intfdata() 也取到了指针，下一秒设备被拔，disconnect 跑起来把引用放掉、内存释放，你手里的 dev 就成了野指针。加了这一次引用，disconnect 那边 kref_put() 只减不释放，真正释放要等你的 release 也放一次。

链条是这样的：

text
inode --iminor()--> 次设备号
次设备号 --usb_find_interface()--> usb_interface
usb_interface --usb_get_intfdata()--> usb_skel（你的私有数据）
usb_skel --> file->private_data

usb_find_interface() 是 usbcore 提供的，它拿驱动指针和次设备号去反查接口。这就是为什么 probe 里 usb_set_intfdata() 那一步不能省，链条的最后一环靠它。

6.2 release：把 open 借的都还回去 #

c
static int skel_release(struct inode *inode, struct file *file)
{
	struct usb_skel *dev = file->private_data;

	if (!dev)
		return -ENODEV;
	if (!--dev->open_count)
		usb_autopm_put_interface(dev->interface);
	kref_put(&dev->kref, skel_delete);
	return 0;
}

open 和 release 里的 kref_get/kref_put 必须成对，usb_autopm_get_interface/usb_autopm_put_interface 也必须成对。漏掉前一对是内存泄漏，漏掉后一对是设备永不休眠。这两组计数器都不会报错，出问题只表现为资源慢慢不见。

skel_delete() 是 kref_put 的第二个参数，引用归零时由它真正释放：

c
static void skel_delete(struct kref *kref)
{
	struct usb_skel *dev = to_usb_skel(kref);

	usb_put_dev(dev->udev);
	kfree(dev->bulk_in_buffer);
	kfree(dev);
}

to_usb_skel() 是个 container_of 包装，从 kref 成员反推出整个结构体的地址。这个宏是内核里到处都是的基本功。

6.3 read：把数据从设备搬到用户态 #

read 这条路径比较长，因为数据要先从设备收上来，再拷给用户。

c
static ssize_t skel_read(struct file *file, char __user *buffer,
			 size_t count, loff_t *ppos)
{
	struct usb_skel *dev = file->private_data;
	int retval, bytes_read;

	/* 一次只处理一次接收，用信号量挡住并发 */
	if (down_interruptible(&dev->limit_sem))
		return -ERESTARTSYS;

	retval = usb_bulk_msg(dev->udev,
			      usb_rcvbulkpipe(dev->udev, dev->bulk_in_endpointAddr),
			      dev->bulk_in_buffer,
			      min(dev->bulk_in_size, count),
			      &bytes_read, 10000);

	if (!retval && copy_to_user(buffer, dev->bulk_in_buffer, bytes_read))
		retval = -EFAULT;

	up(&dev->limit_sem);
	return retval ? retval : bytes_read;
}

usb_bulk_msg() 是同步接口，内部做了「分配 urb、填 urb、提交、等完成、释放 urb」这一串。它自己会睡，所以只能用在进程上下文。read 是系统调用进来的，进程上下文，能用。第四个参数取 min(bulk_in_size, count)：用户要的比缓冲区大就按缓冲区来，比缓冲区小就按用户来，反过来写就是缓冲区溢出。超时那个 10000 是毫秒，不填就是永远等，设备不回数据你的 read 就永远挂着。

6.4 write：把用户数据发到设备 #

write 是反方向，先把用户数据拷进内核缓冲，再发出去。

c
static ssize_t skel_write(struct file *file, const char __user *user_buffer,
			  size_t count, loff_t *ppos)
{
	struct usb_skel *dev = file->private_data;
	size_t writesize = min(count, (size_t)dev->bulk_out_size);
	int retval;

	if (copy_from_user(dev->bulk_out_buffer, user_buffer, writesize))
		return -EFAULT;

	retval = usb_bulk_msg(dev->udev,
			      usb_sndbulkpipe(dev->udev, dev->bulk_out_endpointAddr),
			      dev->bulk_out_buffer, writesize,
			      &writesize, 10000);
	return retval ? retval : writesize;
}

两边的 pipe 函数方向相反：收用 usb_rcvbulkpipe()，发用 usb_sndbulkpipe()。第二个参数 ep 是端点号（低 4 位），不是 bEndpointAddress 的完整值。你从端点描述符里拿到的是 0x02 这种完整地址，存进 bulk_out_endpointAddr，传给 pipe 函数时它会自己掩掉方向位。用完整地址也行，掩码会处理掉，但概念上要清楚。

6.5 ioctl 与类请求 #

标准字符设备接口不够用的时候加 ioctl。USB 驱动里的 ioctl 主要干两件事：转发类特定请求，或者配置设备参数。

c
static long skel_ioctl(struct file *file, unsigned int cmd, unsigned long arg)
{
	struct usb_skel *dev = file->private_data;

	switch (cmd) {
	case SKEL_SET_TIMEOUT:
		dev->timeout = arg;
		return 0;
	case SKEL_RESET:
		return usb_reset_device(dev->udev);
	default:
		return -ENOTTY;
	}
}

发类请求用 usb_control_msg()。比如给设备发一个 vendor 命令：

c
	ret = usb_control_msg(dev->udev,
			      usb_sndctrlpipe(dev->udev, 0),
			      0x01,				/* bRequest */
			      USB_DIR_OUT | USB_TYPE_VENDOR | USB_RECIP_DEVICE,
			      0x0000,				/* wValue */
			      0x0000,				/* wIndex */
			      buf, len, 1000);

五个打包参数各管一段：request 是命令号，requesttype 里塞方向、类型、接收者，value 和 index 是命令参数。这套编码在协议篇里有完整对照，这里只要记住 requesttype 那三个位段不能写反。

usb_control_msg() 也是同步的，返回实际传输的字节数，负值表示出错。长度限制是 wLength 那 16 位，一次最多 65535 字节。

七、数据的发送与接收 #

第六章用的是同步接口，图省事。真正跑数据流的时候得用 urb，因为同步接口一次只能挂一个请求，等它回来的这段时间你的进程什么也干不了。urb 是异步的，提交完立刻返回，数据到了再回调通知你。

USB 设备驱动和所有 USB 设备通信，靠的都是 urb，它在 include/linux/usb.h 里用 struct urb 描述。一个驱动可以按需要给一个端点分配多个 urb，也可以把同一个 urb 复用到多个端点。设备里的每个端点都有一个 urb 队列，队列清空之前可以继续往里塞。

7.1 urb 的一生 #

步 动作 对应函数
1 创建 usb_alloc_urb()
2 分配给特定端点 填 urb->pipe，或走 usb_fill_*_urb()
3 提交给 USB 核心 usb_submit_urb()
4 核心转交主机控制器驱动 内部完成，你看不见
5 控制器处理，发到设备 内部完成，你看不见
6 完成后回调通知驱动 urb->complete

urb 可以随时被提交它的驱动取消；设备被移除时，核心也会替你取消。urb 动态创建，内部带引用计数，最后一个使用者放手时自动销毁。

这个引用计数用 usb_get_urb() 和 usb_free_urb() 操作。usb_submit_urb() 内部会加一次，完成回调里减一次，所以你 usb_alloc_urb() 之后只要保证自己那一份被 usb_free_urb() 放掉就行。

7.2 创建和释放 #

struct urb 不能静态定义，必须用函数分配。usb_alloc_urb(int iso_packets, gfp_t mem_flags) 的第一个参数是等时传输要几个数据包，不用等时就填 0；第二个和 kmalloc 那套标志一样。返回值是 urb 指针，NULL 表示分配失败，这时候要先清理再返回错误。用完调 usb_free_urb(struct urb *urb)。

7.3 四个 fill 函数 #

分配出来是个空壳，得填。四种传输类型里有三个有现成的 fill 函数：

c
static inline void usb_fill_bulk_urb(struct urb *urb, struct usb_device *dev,
				     unsigned int pipe, void *transfer_buffer,
				     int buffer_length,
				     usb_complete_t complete_fn, void *context);

另外两个形状一样：usb_fill_int_urb() 多一个尾部参数 interval（中断端点的轮询间隔，毫秒），usb_fill_control_urb() 把 transfer_buffer 前面多插一个 setup_packet（8 字节设置包）。

参数 填什么
dev 目标 usb_device，就是 interface_to_usbdev() 拿到的那个
pipe 端点管道，用 usb_sndbulkpipe() 这类函数建
transfer_buffer 数据缓冲，必须是 kmalloc 出来的，不能是静态数组或栈上变量
buffer_length 缓冲长度
complete_fn 完成回调，传输结束或出错时被调用
context 随手带的数据，回调里从 urb->context 取回来

等时传输没这个福气，四个 fill 函数都不管它，得手工一项一项填：

c
	urb->dev = dev;
	urb->context = uvd;
	urb->pipe = usb_rcvisocpipe(dev, uvd->video_endp - 1);
	urb->interval = 1;
	urb->transfer_flags = URB_ISO_ASAP;
	urb->transfer_buffer = cam->sts_buf[i];
	urb->complete = konicawc_isoc_irq;
	urb->number_of_packets = FRAMES_PER_DESC;
	urb->transfer_buffer_length = FRAMES_PER_DESC;
	for (j = 0; j < FRAMES_PER_DESC; j++) {
		urb->iso_frame_desc[j].offset = j;
		urb->iso_frame_desc[j].length = 1;
	}

transfer_buffer 那条规矩常被忽略：必须用 kmalloc 分配。用静态数组或者栈上的局部变量，控制器做 DMA 的时候按物理地址访问，你那个地址根本不在设备能访问的范围里，结果是数据发到别处去了。栈上的更惨，函数一返回那块内存就被复用。

7.4 提交 #

urb 填好了就交出去：int usb_submit_urb(struct urb *urb, gfp_t mem_flags);

成功后函数返回 0，urb 的控制权就交给 USB 核心了。从提交成功那一刻起，到完成回调被调用之前，你不能碰 urb 结构的任何成员。这不是建议，是硬规矩。核心和主机控制器正在读写它，你插一脚进去就是数据竞争。

mem_flags 有三个取值，选错了要么分配不到内存，要么把中断上下文睡死：

值 什么情况用
GFP_ATOMIC 在完成回调、中断处理、底半部、tasklet、定时器回调里；或者持着自旋锁/读写锁；或者 current->state 不是 TASK_RUNNING
GFP_NOIO 驱动处在块 IO 处理过程中，以及所有存储类型的错误处理路径
GFP_KERNEL 以上都不是的情况

还有一个细节：持着信号量的时候不必用 GFP_ATOMIC，因为信号量允许睡眠。持着自旋锁才必须用。这两者搞混，代码能跑，但高负载下会莫名其妙丢 urb。

usb_submit_urb() 不设置 urb->transfer_flags，要改这个成员得自己动手。

7.5 完成回调 #

提交成功以后，urb 结束的时候完成回调会被调一次。内核把 urb 的 status 填好，把控制权还给你。

只有三种情况会走到回调：

情况 urb->status 说明
成功发送，设备正确应答 0 正常结束
发生错误 负的错误码 具体值看 urb->status
urb 被 unlink -ECONNRESET / -ENOENT 你主动取消，或者设备被拔

回调的典型骨架：

c
static void skel_write_bulk_callback(struct urb *urb)
{
	struct usb_skel *dev = urb->context;

	/* 同步 urb 的完成回调会被同步接口自己接管，这里提前返回 */
	if (urb->status == -ENOENT ||
	    urb->status == -ECONNRESET ||
	    urb->status == -ESHUTDOWN)
		return;
	if (urb->status)
		dev_info(&dev->interface->dev, "nonzero write bulk status %d\n",
			 urb->status);

	/* 用完了，放掉这次提交时加的引用 */
	usb_free_urb(urb);
}

urb->status 那三个负数要提前返回。-ENOENT 表示 urb 被 unlink 了，-ECONNRESET 表示被 kill 了，-ESHUTDOWN 表示设备没了。这三种都是「正常的不正常」，不要打成错误日志，否则每次拔设备都刷一屏告警。回调里不能睡，所以不能用 GFP_KERNEL 再提交下一个 urb，要用 GFP_ATOMIC；也不能调 usb_control_msg()、usb_bulk_msg() 这类同步接口。

7.6 取消 #

两个函数，用途不同：usb_kill_urb() 等，回调执行完才返回，用在 disconnect、release、错误处理里；usb_unlink_urb() 不等，立刻返回，用在中断处理里、持着自旋锁时。

usb_kill_urb() 会把 urb 的生命周期终止掉。它内部用 wait_event() 等回调跑完，所以要求调用者能睡。disconnect 能睡，用它。usb_unlink_urb() 不等待，适合在不能睡的上下文里停 urb。代价是你返回之后 urb 还在飞，得靠回调自己处理后续。

对批量端点还有一种做法：复用同一个 urb。在完成回调里重新 usb_submit_urb()，形成连续接收。这样不用每次分配释放，省开销，也不会漏数据。注意重新提交时缓冲要重新填，urb->transfer_buffer_length 要重置。

7.7 同步接口：图省事的时候用它 #

自己填 urb 太啰嗦，日常收发用同步接口就够：

c
int usb_bulk_msg(struct usb_device *usb_dev, unsigned int pipe,
		 void *data, int len, int *actual_length, int timeout);

int usb_control_msg(struct usb_device *dev, unsigned int pipe,
		    __u8 request, __u8 requesttype, __u16 value, __u16 index,
		    void *data, __u16 size, int timeout);

两个都是内部走 urb，只不过用完成量把自己挂起，等回调唤醒。返回 0 表示成功，负值表示失败，actual_length 带出实际传输的字节数。它们只能用在进程上下文，因为会睡；中断处理里用不了，disconnect 里也尽量别用（那时候设备已经不在了，直接超时等满 10 秒）。

数据量小、频率低的场景用同步接口最省事。数据量大、有实时性要求的，老实写 urb。这就是第六章和本章的分界线。

八、热插拔是怎么实现的 #

这一章先把一个误解拆掉：

「热插拔」不是驱动自己实现的功能。

你的驱动里没有任何一行代码是「检测设备插入」的。设备插上来，你先知道还是后知道，取决于内核有没有枚举完、匹配上、然后调你。拔掉的时候同理，是 disconnect 被调，不是你去轮询。

热插拔是三拨人合作的结果：内核负责发现和通知，udev 负责建节点和加载模块，应用负责响应节点变化。三层各干各的，中间靠 uevent 串起来。

8.1 硬件层：插上去的瞬间电平就变了 #

USB 集线器的每个下游端口，D+ 和 D- 上各接一个 15K 欧姆下拉电阻到地，端口悬空时两根数据线都是低电平。设备那一侧，D+ 或者 D- 上接一个 1.5K 欧姆上拉电阻。全速和高速设备上拉在 D+，低速设备上拉在 D-。

设备插进去，1.5K 上拉和 15K 下拉分压，差分线里的一根被拉高。集线器检测到这个变化，报告给主控制器（多层 hub 一层层往上转），主机就知道有设备来了。高速设备先被当成全速设备握手，协商通过才切到高速模式；切过去以后 D+ 上的上拉电阻会断开，高速模式下是电流传输，不再靠上拉电阻表意。

这个设计还顺带解决了带电插拔的安全问题。USB 插头的地引脚和电源引脚比两个数据引脚长，插进去的时候电源和地先接通，数据线后接通；拔的时候数据线先断、电源后断。这样保证不会在数据线带电时建立连接，避免闩锁。

项目 规定 说明
线色 Vbus 红、D- 白、D+ 绿、GND 黑 很多线缆不守规矩，用前拿表量
低速线长 ≤ 3 米 线缆有延迟，太长响应不上
全速线长 ≤ 5 米 同上
全速线缆 屏蔽双绞 低速可以不屏蔽不双绞
miniUSB 5 线，多一条 ID OTG 靠 ID 线判断主从

8.2 内核层：hub 线程发现，然后发 uevent #

系统初始化时，usb_init() 调 usb_hub_init()。这个函数干两件事：注册 hub 驱动，再起一个内核线程。

c
int usb_hub_init(void)
{
	if (usb_register(&hub_driver) < 0) {
		printk(KERN_ERR "%s: can't register hub driver\n", usbcore_name);
		return -1;
	}

	khubd_task = kthread_run(hub_thread, NULL, "khubd");
	if (!IS_ERR(khubd_task))
		return 0;

	/* 线程起不来就把驱动注册退掉 */
	usb_deregister(&hub_driver);
	printk(KERN_ERR "%s: can't start khubd\n", usbcore_name);
	return -1;
}

注意这里的错误处理也是 goto 那套思路：注册成功了但线程起不来，回头把注册退掉再返回。资源申请和回滚必须成对，内核里到处都是这个模式。

线程主体是个循环，平时睡在 wait_event_interruptible 上，不占 CPU。有事件进 hub_event_list 就被唤醒，跑一遍 hub_events()，处理完接着睡：

c
static int hub_thread(void *__unused)
{
	do {
		hub_events();
		wait_event_interruptible(khubd_wait,
					 !list_empty(&hub_event_list) ||
					 kthread_should_stop());
		try_to_freeze();
	} while (!kthread_should_stop() || !list_empty(&hub_event_list));

	return 0;
}

事件的来源是中断。hub 驱动在 hub_configure() 里分配一个 urb，用 usb_fill_int_urb() 初始化，轮询周期填进 bInterval。设备插拔导致端口电平变化，hub 在中断端点上回一个包，触发 hub_irq()，这个函数把 hub 挂进 hub_event_list 并唤醒 khubd。hub_events() 里拿 usb_port_status() 逐个端口看状态位，发现变化就调 hub_port_connect_change()。新设备走 usb_alloc_dev() 分配，再 usb_new_device() 配置。

USB 设备和 PCI 设备的区别就在这儿：PCI 设备在启动时就固定了，枚举一遍就完事，递归扫树就行。USB 设备随时来随时走，所以必须有一个常驻的线程盯着端口。

8.3 枚举：从插入到能通信的五步 #

枚举是热插拔的起始步骤。主机在这几步里把设备的信息拿全，把它配好。

步 做什么
1 根集线器报告端口电流变化，hub 驱动检测到，唤醒 khubd
2 khubd 定位到状态变化的那个端口
3 通过控制端点 0 发控制 urb，从 1~127 里挑一个地址给设备
4 用端点 0 读设备描述符，再读配置描述符，挑一个配置
5 请求 USB 核心为这个设备找匹配的设备驱动，挂钩

第 5 步就是你那个 probe 被调用的时刻。前面四步全在内核里跑完，你的代码一行都没执行。

usb_new_device() 具体做六件事，顺序不能乱：

text
1. usb_set_address()        把新分配的地址告诉设备
2. usb_get_descriptor()     读设备描述符，拿到端点 0 的最大包长
3. usb_get_configuration()  读全部配置、接口、端点描述符
4. usb_set_configuration()  激活选中的配置，作为默认工作配置
5. 在 proc/bus/usb 下建设备节点
6. usb_find_drivers / usb_find_interface_driver 给每个接口找驱动

第 2 步有个细节：读完设备描述符才知道端点 0 的最大包长，后面的控制传输都按这个长度分片。所以这个顺序不能颠倒。第 6 步是逐接口进行的，一个设备有几个接口，就调几次匹配、几次 probe；每个接口被成功驱动之后，这个设备才算完全工作起来。

拔掉的路径是镜像的：hub 检测到拔下信号，通过中断上报，hub 驱动验证确实拔了，调 usb_disconnect()。它找到当前活动配置的每个接口的驱动，逐个调 disconnect，中断数据传输、释放资源。设备自己是 hub 的话递归处理它的子设备。最后释放设备地址、去掉文件节点、放掉 USBD 分配的资源。

8.4 三个层次的分工 #

这是本章最重要的一张表。

层 谁在干 干了什么 你的代码在哪
内核层 hub 驱动 + khubd + usbcore 发现电平变化、枚举、匹配驱动、调 probe/disconnect、发 uevent probe/disconnect 两个回调
用户层 udev（或 mdev、busybox 的 hotplug） 收到 uevent，建 /dev 节点、改权限、加载模块 不用写，但要配规则
应用层 你的用户态程序 监听节点变化、打开设备、开始干活 应用代码

内核层做的是：设备插上，枚举完，probe 调完，然后往 sysfs 里写一个 uevent 文件，内容是这个设备的属性（PRODUCT、TYPE、BUSNUM、DEVNUM 等）。写这个文件会触发 netlink 广播，用户态的守护进程在收。

用户层的 udev 收到广播，按 /etc/udev/rules.d/ 里的规则匹配，然后建节点。默认规则会建 /dev/bus/usb/BBB/DDD（BBB 是总线号，DDD 是设备号）。你自己写的规则可以额外建一个稳定名字的软链，或者设权限。

应用层有两条路。一路是直接用 inotify 监听 /dev 目录，节点出现就打开。另一路是监听 netlink 的 NETLINK_KOBJECT_UEVENT 套接字，自己解析 uevent 报文。前者简单，后者信息全。

8.5 你的驱动在热插拔里扮演什么角色 #

只有两个回调。设备来，probe 被调；设备走，disconnect 被调。就这些。

事件 内核动作 你的动作
插入 枚举 → 匹配 → 调 probe 申请资源、注册设备、启动传输
拔出 调 disconnect → 发 uevent（remove） 停 urb、注销设备、释放资源
驱动加载 扫已有设备 → 匹配上就 probe 和设备插入时一样
驱动卸载 对每个接口调 disconnect 和设备拔出时一样

有一条推论值得记住：「设备已插入」这件事，你的驱动未必知道。如果模块是在设备插好之后才 insmod 的，那 probe 会在注册的那一刻被补调一次。反过来，如果设备从来不被匹配，probe 一次都不会进，你的驱动看起来像没加载。

九、udev 与设备节点 #

内核把设备认出来了，但用户态要访问它，还得有个路径。这一章讲节点是怎么冒出来的。

9.1 节点从哪来 #

有三条独立的路，分别对应不同的驱动写法：

路 谁建的 节点长什么样 你的驱动要做什么
usb_register_dev() usbcore + udev /dev/skel0 probe 里调注册，disconnect 里注销
devfs 老内核的 devfs 子系统 /dev/usb/skel0 老写法，新内核已经没有
手动 mknod 你自己 任意 不推荐，主次设备号容易对不上

老代码里能见到 devfs 的写法：

c
	sprintf(name, "skel%d", skel->minor);
	skel->devfs = devfs_register(usb_devfs_handle, name, DEVFS_FL_DEFAULT,
				     USB_MAJOR, USB_SKEL_MINOR_BASE + skel->minor,
				     S_IFCHR | S_IRUSR | S_IWUSR | S_IRGRP |
				     S_IWGRP | S_IROTH, &skel_fops, NULL);

devfs 在 2.6.13 之后就被移除了，这段代码只能当历史看。现代内核走的是 udev 那套：驱动调 usb_register_dev()，usbcore 在 sysfs 里暴露 dev 属性（主次设备号），udev 读它然后建节点。注册失败也无所谓，udev 子系统会把情况报给用户，你在 dmesg 里能看到。

9.2 节点名的组成 #

skel_class.name 填的是 "skel%d"，那个 %d 就是次设备号。主设备号是 USB_MAJOR，全系统所有 USB 字符设备共用。次设备号用来区分具体是哪个接口：USB_SKEL_MINOR_BASE + interface->minor。

号码 谁分配 怎么查
主设备号 全系统固定为 USB_MAJOR /proc/devices
次设备号 usbcore 在 usb_register_dev() 时分配 interface->minor
节点名 你的 usb_class_driver.name /dev/ 下看

9.3 sysfs 里的设备层级 #

udev 建节点靠 sysfs，排障也要看 sysfs：

bash
ls /sys/bus/usb/devices/                  # 设备树，一层 hub 一段
cat /sys/bus/usb/devices/1-1/idVendor     # 某个设备的属性
ls -l /sys/bus/usb/devices/1-1:1.0/driver # 接口绑定的驱动
ls /sys/bus/usb/drivers/                  # 所有已注册的 USB 驱动

设备名是「根集线器-集线器端口号」拼出来的，层次更深就是「根集线器-端口-端口」，冒号后面是配置号和接口号。1-1:1.0 是根 hub 的 1 号口、配置 1、接口 0；1-1.2:1.0 是那个设备后面又挂了一个 hub，它的 2 号口。这个规则在看日志时很有用——dmesg 里报的设备和 lsusb 看到的能对上。

9.4 udev 规则能干什么 #

默认规则只建节点，实际项目里三件事绕不开：

需求 规则写法 场景
固定节点名 SYMLINK+="mydev" 应用不想关心 busnum/devnum 变化
设权限 MODE="0666", GROUP="plugdev" 免 sudo 访问
插入时执行脚本 RUN+="/usr/local/bin/on_usb.sh" 自动挂载、自动测速

写规则用设备的 idVendor/idProduct 做匹配最稳：

text
SUBSYSTEM=="usb", ATTR{idVendor}=="1234", ATTR{idProduct}=="5678", \
MODE="0666", SYMLINK+="myusb"

改完规则要 udevadm control --reload-rules，然后 udevadm trigger 让已插入的设备重新走一遍。忘了 reload，新规则不生效，你会以为是规则写错了。

9.5 mdev：嵌入式那边的一套 #

跑 Buildroot、BusyBox 的板子一般不用 udev，用 mdev。它的定位一样：内核发 uevent，它建节点。配置文件在 /etc/mdev.conf，写法是「设备名 属主:属组 权限」，比如 usb* root:root 0666。

内核命令行要让 uevent 走到用户态：/proc/sys/kernel/hotplug 里写 mdev 或者 sbin/mdev。开发板上最常见的一个坑是没写这个值，插拔设备内核什么反应都没有，dmesg 里枚举日志是全的，就是节点不出现。

对比项 udev mdev
用在哪 桌面、服务器发行版 BusyBox、嵌入式
规则文件 /etc/udev/rules.d/*.rules /etc/mdev.conf
配置入口 自动，systemd 拉起 要写 /proc/sys/kernel/hotplug
调试命令 udevadm monitor cat /proc/sys/kernel/hotplug 先确认

9.6 应用层怎么收到通知 #

用户态要知道设备插拔，有三条路：

c
/* 路 1：netlink 直接收 uevent 报文 */
int fd = socket(AF_NETLINK, SOCK_DGRAM, NETLINK_KOBJECT_UEVENT);
struct sockaddr_nl snl = { .nl_family = AF_NETLINK };
bind(fd, (struct sockaddr *)&snl, sizeof(snl));
/* 然后 recv() 拿到的就是 "add@/devices/..." 这种字符串 */

/* 路 2：inotify 盯 /dev 目录 */
int ifd = inotify_init();
inotify_add_watch(ifd, "/dev", IN_CREATE | IN_DELETE);

/* 路 3：轮询，最简单也最浪费 */
while (1) {
	if (access("/dev/skel0", F_OK) == 0)
		break;
	usleep(100000);
}
路 优点 缺点
netlink 信息最全，插入和移除都带完整属性 要解析报文，uevent 格式在内核版本间有小改
inotify 简单，标准 POSIX 只知道节点变了，不知道是哪个设备的什么属性
轮询 一行代码 延迟 100ms 起，CPU 白烧

netlink 那条路拿到的报文长这样，ACTION 是 add 还是 remove，后面的 @ 是 sysfs 路径：

text
add@/devices/pci0000:00/0000:00:14.0/usb1/1-1
ACTION=add
DEVPATH=/devices/pci0000:00/0000:00:14.0/usb1/1-1
SUBSYSTEM=usb
PRODUCT=1234/5678/100
TYPE=0/0/0
BUSNUM=001
DEVNUM=003

监听的时候记得先 bind，不然收不到广播。netlink 套接字还要 setsockopt 加接收缓冲，插拔风暴的时候默认大小会丢消息。

十、调试手段 #

驱动写完了不跑，或者跑起来不对，靠猜没用。这一章是手边要有的几把工具。

10.1 先看日志 #

probe 到底进没进，第一件事就是看内核日志：

bash
dmesg -w | grep -i usb            # 实时跟，只看 USB 相关
dmesg -c > /dev/null; dmesg       # 清空重来，插一次设备看新增

probe 里一定要有打印，哪怕就一行 dev_info(&interface->dev, "probe: vid=%04x pid=%04x\n", ...)。没有打印，你连它进没进都不知道。日志里常见的几条：

日志 含义
new full-speed USB device number 3 using xhci_hcd 枚举开始了
New USB device found, idVendor=1234, idProduct=5678 描述符读到了
usb 1-1: new high-speed USB device number 3 高速握手完成
usbcore: registered new interface driver skeleton 你的驱动注册成功
skeleton 1-1:1.0: USB Skeleton device now attached to USBSkel-0 probe 跑通了

倒数第二条对应 usb_register() 成功，最后一条对应 usb_register_dev() 成功。两条都在，说明链路全通。

10.2 驱动到底绑没绑上 #

bash
ls -l /sys/bus/usb/devices/1-1:1.0/driver  # 某个接口绑了谁
ls /sys/bus/usb/drivers/skeleton/          # 某个驱动下挂了哪些接口
lsusb -t                                   # 所有 USB 设备的树状图
lsusb -v -d 1234:5678                      # 详细描述符

lsusb -t 能直接看出来设备挂在哪一层 hub 上、跑什么速度、用哪个驱动。lsusb -v 输出全描述符，端点地址、包长、类字段全在里面，对照 probe 里的打印一眼就能看出哪里读错了。/sys/bus/usb/drivers/skeleton/ 下面除了 bind、unbind、new_id 这几个控制文件，剩下的软链就是绑上的接口，形如 1-1:1.0。空的说明一个都没绑上。

10.3 抓总线上的包 #

协议层看不到的问题，抓包。usbmon 是内核自带的：

bash
modprobe usbmon                        # 出现 /sys/kernel/debug/usb/usbmon/
mount -t debugfs none /sys/kernel/debug
lsusb                                  # 看 Bus 001 Device 003
cat /sys/kernel/debug/usb/usbmon/1u    # 抓 1 号总线

1u 里的 u 表示按 urb 记录，比 1t（按传输记录）信息全。抓下来的格式是每行一个 urb，字段有 urb 地址、时间戳、事件类型（S 提交 / C 完成 / E 错误）、长度、状态，最后是数据。Wireshark 支持直接读这个文本格式，也有实时抓包接口。

10.4 常用的几个 sysfs 小工具 #

路径 干什么
/sys/bus/usb/devices/1-1/speed 当前速度（1.5 / 12 / 480 / 5000）
/sys/bus/usb/devices/1-1/bMaxPower 设备要多少电
/sys/bus/usb/devices/1-1/authorized 写 0 可以禁掉这个设备
/sys/bus/usb/drivers/skeleton/unbind 往里面写设备名可以强制解绑
/sys/bus/usb/drivers/skeleton/bind 强制绑定，绕过匹配表

unbind/bind 这对文件在调试 disconnect 时特别好用：不用真拔线，往 unbind 里 echo "1-1:1.0" 就能触发一次完整的 disconnect，插拔逻辑不动线就能反复验证。

10.5 打印级别 #

dev_info 打出来的是 KERN_INFO，某些发行版默认不显示在控制台（只在 dmesg 里）。dev_dbg 更狠，要开 CONFIG_DYNAMIC_DEBUG 并用 dyndbg 打开：

bash
echo 'module skeleton +p' > /sys/kernel/debug/dynamic_debug/control
echo 'file skel.c +p' > /sys/kernel/debug/dynamic_debug/control

调试期直接用 dev_info，别用 dev_dbg，省得被日志级别绕进去。定稿之前把多余的全删掉，dev_dbg 留着。

十一、开发过程的复盘 #

回头看整个流程，一个 USB 驱动从零到能跑，走的是这么一条路。

11.1 六个阶段 #

阶段 干什么 完成标志
1. 摸清设备 lsusb -v，抄下 VID/PID、端点表、传输类型 手里有一张端点清单
2. 搭空壳 usb_driver + id_table + 两个空回调 insmod 后日志里有 probe
3. 开接口 注册字符设备，fops 全填成返回 0 /dev/skel0 出现，能 open
4. 通数据 先把 write 打通，用同步接口 设备有反应
5. 换异步 urb 替掉同步接口，加完成回调 连续收发不掉数据
6. 补清理 disconnect 全链路，反复 unbind/bind 验 连续插拔 100 次不崩

第 2 阶段最容易卡住，因为「日志里没有 probe」有一堆说法。查的顺序在第三章的 3.4 节。第 6 阶段最容易被跳过，也是现场故障的主要来源。

11.2 设备类驱动要提供的两套接口 #

站在系统角度看，一个设备类驱动同时面向两边：朝上给 usbcore 一个 usb_driver 结构（含 probe、disconnect、id_table），告诉内核「这些设备归我」；朝下给用户态一套 file_operations（或挂进别的子系统），告诉应用「这么用我」。

摄像头这类驱动更典型，文件接口一长串：

c
static struct file_operations cam_fops = {
	.owner   = THIS_MODULE,
	.open    = cam_v4l2_open,
	.release = cam_v4l2_release,
	.ioctl   = cam_v4l2_ioctl,
	.llseek  = no_llseek,
	.read    = cam_v4l2_read,
	.mmap    = cam_v4l2_mmap,
	.poll    = cam_v4l2_poll,
};

mmap 和 poll 是视频类的特有需求：前者把内核缓冲直接映射到用户态，省一次拷贝；后者让应用能阻塞等帧。普通的批量传输设备用不上这两个。

11.3 端口和端点的关系 #

再捋一遍这个嵌套，写代码时脑子里要有这张图：

text
设备（device）
  └─ 配置（configuration）       一个以上
       └─ 接口（interface）       一个以上
            └─ 设置（altsetting）  一个以上
                 └─ 端点（endpoint） 零个或多个

probe 拿到的是接口，接口的 cur_altsetting 指向当前活动的那个设置，设置里的 endpoint[] 数组才是端点表。一个具体例子，一个中断端点的描述符：bEndpointAddress = 0x81（第 8 位为 1，输入端点）、bmAttributes = 0x03（中断传输）、wMaxPacketSize = 0x0008（一次 8 字节）、bInterval = 0x08（8 毫秒轮询一次）。

这四个值就是 probe 里要抄进私有结构的东西。0x81 的 1 是方向位，真正的端点号是低 4 位的 1；0x03 掩掉 USB_ENDPOINT_XFERTYPE_MASK 得到 3，对应 USB_ENDPOINT_XFER_INT。

一个设备能有多个接口，每个接口是一个独立的逻辑连接。USB 扬声器一个接口走键盘控制、一个走音频流，多半是两个不同的驱动在管。反过来，蓝牙设备两个接口（一个 ACL/EVENT，一个 SCO 链路），却由一个驱动统一管。这是设计选择，不是规矩。interface 转 usb_device 用 interface_to_usbdev(intf)；反方向没有常规需求，因为一个设备对应多个接口，反查没有唯一解。

11.4 四个数据结构的定位 #

写驱动时会反复和这四个打交道：usb_device 保存设备地址和设备描述符、配置描述符，usbcore 在枚举时分配；usb_bus 保存总线上的地址使用情况、根 hub、带宽，usbcore 在控制器注册时分配；usb_driver 保存驱动名、回调函数指针、id_table，你自己静态定义；urb 保存一次传输的全部参数和状态，由你的驱动 usb_alloc_urb() 出来。

前两个你不用管，第三个是你写的，第四个是你最常打交道的。usb_driver 是「我是谁」，urb 是「我要干什么」。

11.5 一条建议 #

先把骨架跑通，再补业务。

骨架跑通的标志很简单：insmod 之后 dmesg 里有你的 probe 打印，rmmod 之后有 disconnect 打印，中间不崩。这三条都满足，再往里加数据通路。

反过来做——一上来就写完整驱动——调试时你不知道问题出在匹配、初始化、还是数据收发。骨架是最小可验证单元，这个思路在驱动开发里比在应用开发里更值钱，因为内核崩了没有栈回溯可看，只有一行 oops。

十二、易错点速查 #

按出现频率排，前五条占实际故障的绝大多数。

12.1 骨架与匹配 #

症状 原因 修法
probe 从不执行 漏了 MODULE_DEVICE_TABLE 补上，modinfo 里应该能看到 alias
probe 从不执行 VID/PID 和设备对不上 lsusb 核对，注意大小端
probe 从不执行 复合设备用了 USB_DEVICE_INFO 换 USB_INTERFACE_INFO
probe 从不执行 接口已被别的驱动占了 看 driver 软链，unbind 或加黑名单
rmmod 报 -EBUSY 设备节点还被打开着 关掉用户态进程，或查 owner 引用计数
编译报 owner 未定义 新内核删了这个字段 删掉 .owner 那行

12.2 probe 与资源 #

症状 原因 修法
拔插几次后内存泄漏 某个失败分支漏了释放 用 goto 链，只在标号处释放
拔插几次后崩溃 释放了没申请的东西 标号顺序错，检查申请/释放是否严格倒序
第二个同型号设备 probe 失败 用了全局变量 私有数据挂 usb_set_intfdata，别用全局
完成回调里空指针 usb_set_intfdata 挂晚了 挪到端点信息填完之后、注册设备之前
拔线后几秒崩溃 没停 urb 就释放了私有数据 disconnect 里先 usb_kill_urb
定时器还在提交 urb 漏了 del_timer_sync 停定时器要排在停 urb 之前

12.3 数据通路 #

症状 原因 修法
数据发到别处 transfer_buffer 用了静态数组或栈变量 必须 kmalloc / usb_alloc_coherent
收到乱码 wMaxPacketSize 没做 le16_to_cpu 描述符字段全是小端
端点找不到 只判了方向没判类型 三个条件一起判，见 4.3
每次只收到一个包 一次 read 只发一个 urb 复用 urb，回调里重新提交
高负载丢 urb 在回调里用了 GFP_KERNEL 回调在中断上下文，改 GFP_ATOMIC
pipe 方向反了 收发用错 snd/rcv 发用 usb_sndbulkpipe，收用 usb_rcvbulkpipe
自己拼了 0x81 端点地址和端点号搞混 pipe 函数只传端点号，方向它自己补
提交后访问 urb 崩溃 提交成功后还在读 urb->status 提交到回调之间不能碰 urb

12.4 热插拔与节点 #

症状 原因 修法
设备插上内核有日志，/dev 没节点 没配 /proc/sys/kernel/hotplug（mdev） 写进 sbin/mdev
节点出现了但打不开 权限或主次设备号不对 看 ls -l，加 udev 规则
节点名每次都变 用了 skel%d 这种按 minor 命名的 加 udev SYMLINK 规则
插拔后应用不响应 应用在轮询且间隔太长 换 netlink 或 inotify
插拔风暴时丢事件 netlink 接收缓冲太小 setsockopt 加大 SO_RCVBUF
拔了设备节点还在 驱动没调 usb_deregister_dev 补在 disconnect 里

12.5 最后三句 #

骨架就是三样东西：usb_driver 结构、probe/disconnect 两个回调、id_table 匹配表。第一章那一句话说完了整篇的骨架。

热插拔不是驱动实现的。内核发现、枚举、通知，udev 建节点，应用响应，你的驱动只负责在被调的时候把活干对。

probe 里正向申请，goto 往回退；disconnect 里先停在飞的 urb，再倒序释放。这两段写对了，驱动就稳了一大半。
