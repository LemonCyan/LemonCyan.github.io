一、USB 的物理层 #

1.1 一根线里只有四根导线 #

USB 2.0 的线缆里就是四根线：VBUS、D-、D+、GND。没有片选，没有时钟线，没有地址线。时钟从数据里恢复，地址在包头发，仲裁靠主机排班。

线 作用 电平与约束
VBUS 供电 5V，单口 500mA 上限，可在配置里协商
D- 差分负端 3.3V 差分电平，非 CMOS 5V
D+ 差分正端 3.3V 差分电平，非 CMOS 5V
GND 地 与 VBUS 成对回流

D+ 和 D- 是差分输入线，用的是 3.3V 电平。这点容易踩：USB 收发器的 I/O 不是 5V 容忍的 CMOS 电平，你拿 5V 单片机的 GPIO 直接怼 D+/D- 上去，验不过。

电源线和地线向设备提供 5V，最大电流 500mA，这个上限可以在编程中设置。单位负载是 100mA，设备枚举完成、拿到配置之前只能索取 100mA，配置态才按配置描述符里 bMaxPower 申报的值给。总线供电设备在挂起态要把总电流压到 280uA 以内。

物理连接要求使用屏蔽双绞线。D+/D- 必须成对绞合，屏蔽层单端接地，这不是讲究，是 480Mbps 下的硬指标。

1.2 三种速度等级 #

等级 速率 典型设备 上拉位置
低速 Low Speed 1.5Mbps 鼠标、键盘 D-
全速 Full Speed 12Mbps 早期 U 盘、HID、CDC D+
高速 High Speed 480Mbps U 盘、摄像头、网卡 D+

同一根总线在不同时刻跑不同速率。高速设备先以全速身份接入，握手成功后才切到高速。低速设备永远上不了高速，它连高速握手的门都进不去。

1.3 NRZI：0 翻转，1 保持 #

USB 用不归零取反（NRZI）传数据。规则只有一条：

  • 差分数据输入 0，电平翻转
  • 差分数据输入 1，电平保持原值

字面上看不懂，落到波形上就一句：看线有没有跳变，跳了就是 0，没跳就是 1。

NRZI 的软肋是长串的 1——电平一直不跳，接收端的时钟就会漂。解决办法是位插入（bit stuffing）：发送方在数据流里每连续出现 6 个 1 之后，强行塞一个 0，逼 NRZI 产生一次跳变。接收方看到连续 6 个 1 后的那个 0，就知道是填充位，丢掉。

这一层全由硬件做。你在固件里写的是字节，SIE 替你完成串行化、NRZI、位插入、CRC 生成与校验。这也是为什么协议分析仪抓到的数据是「位插入之后」的波形，而软件看到的是「位插入之前」的字节。

数据在 USB 线里由低位到高位发送。一个字节 0x81，先发 bit0，最后发 bit7。抓包软件显示字节顺序，不显示位顺序，两边对不上时先想起这一条。

1.4 复位是一个电平，不是一个命令 #

USB 的复位没有专门的包，就是让 D+ 和 D- 同时拉低——这叫 SE0（Single Ended Zero）——并保持一段时间。全速/低速设备要求至少 10ms。主机侧看到的是「总线复位」，设备侧看到的是「我被要求回到初始状态」。

包的结尾也用 SE0 加一个单比特宽的 J 状态来标记 EOP（End of Packet）。所以你在抓包工具里看到的每一个包边界，物理上就是这段电平。

高速握手也建在电平上：设备在全速状态下发出 Chirp K 信号，主机回应一串 Chirp K/J，双方确认都能跑 480Mbps，才切到高速。这一步失败，设备退回全速继续工作，功能照跑，带宽差 40 倍。

二、USB 的拓扑：主机、HUB 与设备 #

2.1 一个主机，最多 127 个设备 #

一个 USB 系统里只有一个主机（Host）。设备分两类：功能设备（Function）和集线器（HUB）。设备可以直接和主机通信，也可以通过 HUB 和主机通信。地址域 7 位，地址 0 保留给未配置设备，所以最多 127 个地址——这就是 127 这个数字的来处。

拓扑是分层星型。主机是根，每个 HUB 是一个星型的中心，往下再挂 HUB 或功能设备。规范限制 7 层（含根层）。物理上是树，逻辑上是一条广播总线：主机发出的每个包，所有设备都能在线上看到。

text
        [Host / Root Hub]
           |        |
        [HUB]    [Function]
        |   |
   [HUB] [Function]
     |
 [Function]

2.2 HUB 干了什么 #

HUB 提供一种低成本、低复杂度的 USB 接口扩展方法。它的上行 PORT 面向主机，下行 PORT 面向设备（HUB 或功能设备）。

下行口上，HUB 负责四件事：

  1. 设备连接检测
  2. 设备移除检测
  3. 给各下行 PORT 供电
  4. 单独使能/禁用各下行 PORT

不同 PORT 可以工作在不同的速度等级——一个 HUB 上同时挂一个 1.5Mbps 的鼠标和一个 480Mbps 的 U 盘，完全正常。HUB 替主机把这个差异吃掉。

2.3 插上去，主机怎么知道 #

答案在两颗电阻上。

HUB 端口的两根信号线，每一根都有一个 15kΩ 的下拉电阻，把空闲时的 D+ 和 D- 都拉到接近地。设备侧在 D+ 上有一个 1.5kΩ 的上拉电阻（低速设备在 D- 上）。

用 USB 线把 PC 和设备接通，设备的上拉电阻和 HUB 的下拉电阻构成分压，把那根信号线的电位抬起来。HUB 一测就测到了：这根线的空闲电平不该这么高。于是它记下「这个口有设备接入」，通过自己的中断端点把事件报告给主机。

拔出是反过程：上拉消失，电平回落，HUB 同样上报。

这个设计还顺带解决了速度识别：D+ 被拉高是全速/高速设备，D- 被拉高是低速设备。HUB 通过测定哪根信号线在空闲时有更高的电压来判断，把结果放在端口状态里交给主机。

主机侧的流程是：先收 HUB 的中断报告，再发 Get_Port_Status 问细节，拿到「哪个口、什么速度、什么时候接的」。这两个动作合起来，就是枚举的第一步。

2.4 主机主导的轮询式总线 #

这是整篇最关键的一句话，后面所有现象都由它推出来：

USB 上任何一次数据传输都由主机发起，设备从不主动开口。

具体到线上，就是主机按自己的排班表，一个包一个包地往外发。每个包都带地址和端点号，被点名的设备才允许回应，其他设备闭嘴。同一时刻整个 USB 体系里只允许有一个数据包在传，不同物理线上看到的是同一个被广播的包。

由此推出三个结论：

  • 不存在冲突。 以太网是多个节点抢同一根线，撞了要退避重传，所以需要 CSMA/CD 和冲突检测。USB 没有争用，主机排好谁在什么时候说话，冲突这个概念根本不存在。
  • 没有站点能「发送」。 设备想上报数据，它只能等着。主机来问了（发 IN 令牌），它才把数据吐出来；主机不问，它只能把数据压在端点缓冲里。所谓设备「主动上报」，在总线上永远是「主机先问，设备后答」。
  • 带宽是先分配的。 主机在每一帧/微帧开始排班，同步和中断传输先占坑，控制传输拿剩下的，批量传输捡漏。这是策略，不是协商。

后面讲「中断传输」时你会发现，它一点都不中断——那是主机每隔固定间隔来敲一次门。

三、数据的编码：域与包 #

3.1 四层结构 #

USB 的数据是层层套起来的。先在脑子里建好这条链，后面所有细节都挂得上去：

text
二进制位  →  域(Field)  →  包(Packet)  →  事务(Transaction)  →  传输(Transfer)
  • 域是数据的最小单位，位数由域的类型决定。
  • 包由几个域拼成，是总线传输的最小单位，不能被打断，也不能被干扰。
  • 事务由令牌包、数据包、握手包三个阶段构成，回答「一次完整的问答」。
  • 传输由一次到多次事务构成，回答「一次有意义的业务」。

一次传输可以跨帧完成，一次事务不行。属于同一次事务的几个包必须连续，中间不能插别的。

3.2 七个域 #

域 长度 出现位置 作用
SYNC 8 位（高速 32 位） 所有包的起点 本地时钟与输入同步
PID 8 位 所有包 标识包的类型
ADDR 7 位 令牌包 设备地址
ENDP 4 位 令牌包 端点号
FRAM 11 位 SOF 令牌包 帧号
DATA 0~1023 字节 数据包 载荷
CRC 5 位 / 16 位 令牌包 / 数据包 校验

SYNC。 所有 USB 包都以 SYNC 开始。高速包的 SYNC 宽度是 32 位，全速/低速是 8 位。8 位的值固定为 0000 0001。实际接收到的 SYNC 长度受 HUB 影响，会小于标称值——HUB 转发时会重新生成同步头，所以多级 HUB 下级联的设备，抓到的 SYNC 会短一截，这是正常的。

PID。 4 位标识符 + 4 位标识符反码。反码的用处是让接收端一眼确认这 8 位没坏：高 4 位取反不等于低 4 位，直接丢掉这个包。4 位只能编出 16 个值，USB 2.0 就用这 16 个。

ADDR。 7 位，代表设备在主机上的地址。000 0000 是零地址，任何设备第一次连到主机、在被配置和枚举之前都用这个默认地址。7 位地址、扣掉地址 0，是「一个主机最多 127 个设备」的由来。

ENDP。 4 位，所以一个设备的端点号最大 15，加上端点 0 共 16 个编号空间。

FRAM。 11 位，每帧一个帧号，最大容量 0x800。帧号到 0x7FF 回绕。对同步传输有实际意义——同步端点靠帧号对齐时序。

DATA。 长度 0~1023 字节，不同类型传输的上限不同，但必须是整数个字节。

CRC。 令牌包用 5 位 CRC，数据包用 16 位 CRC。CRC 是模 2 除法，不是十进制除法，别用普通除法去手算校验。CRC 覆盖的是包内除 PID 以外的域。

3.3 十六个 PID #

PID 决定这个包的属性和格式。16 个码分四组：

组 值 名称 含义
令牌 0x01 OUT 启动一次主机到设备的传输，带地址和端点
令牌 0x09 IN 启动一次设备到主机的传输，带地址和端点
令牌 0x05 SOF 帧起始，带 11 位帧号
令牌 0x0D SETUP 启动一次控制传输，用于主机初始化设备
数据 0x03 DATA0 偶数据包
数据 0x0B DATA1 奇数据包
数据 0x07 DATA2 高速高带宽同步传输用
数据 0x0F MDATA 高速高带宽同步传输用
握手 0x02 ACK 接收无误
握手 0x0A NAK 忙，暂时给不了
握手 0x0E STALL 端点被禁止，或不支持该控制管道请求
握手 0x06 NYET 尚未准备好，等下一包
特殊 0x0C PRE 前导，启动下行端口上低速设备的数据传输
特殊 0x08 SPLIT 分离传输令牌
特殊 0x04 PING 流量控制探测，只用于高速批量/控制 OUT
特殊 0x0C 保留 —

PING 值得单独说：它是高速批量传输的探路包。主机想往设备送数据之前，先发 PING 问一句「你能收吗」，设备回 ACK 表示能收、回 NAK 表示别送、回 NYET 表示这一包收了但下一包先别来。低速和全速设备没有 PING。

PRE 是低速设备的护身符。低速设备的信号质量差，它的包不能在高速 HUB 的上行口直接跑，得先发一个 PRE 前导，告诉 HUB「后面这段是低速的，你帮我转发并且降速」。

3.4 四种包 #

令牌包。 分 IN、OUT、SETUP、SOF 四种。前三种格式一致：

text
SYNC + PID + ADDR(7) + ENDP(4) + CRC5(5)

SOF 包换成帧号：

text
SYNC + PID + FRAM(11) + CRC5(5)

注意 IN 令牌包和 OUT 令牌包本身不带数据，它们只是「发令」。IN 是让设备往主机送，OUT 是主机要往设备送。方向的定义从主机视角出发，这点别绕晕。

数据包。 只有 DATA0 和 DATA1（高速高带宽场景还有 DATA2/MDATA）：

text
SYNC + PID + DATA(0~1023 字节) + CRC16

数据超过端点容量时要拆包，DATA0 和 DATA1 交替发。第一个包 DATA0，第二个 DATA1，第三个 DATA0，如此往复。例外只有一个：同步传输里所有数据包都是 DATA0。

握手包。 结构最简单，只有 SYNC + PID，连 CRC 都没有——8 位 PID 自带反码校验，够了。

四种握手：ACK 是肯定应答，传输成功；NAK 是否定应答，接收方忙，要求重传；STALL 是功能错误，端点被设了 STALL 属性，或者设备不支持这个请求；NYET 是尚未准备好，要求等待。

特殊包。 PRE、SPLIT、PING 三个。PRE 前面说了。SPLIT 在第九章展开。PING 上面说了。

3.5 三种事务 #

事务是「一问一答」的完整单元。分 IN、OUT、SETUP 三种，每一种都由三个阶段构成：

  1. 令牌包阶段：主机发出令牌，点名地址和端点，说明这是读还是写。
  2. 数据包阶段：按令牌指定的方向搬数据。这一步不一定有。
  3. 握手包阶段：返回接收结果。同步传输的 IN 和 OUT 事务没有这个阶段，这是它最特殊的地方。

IN 事务——主机要数据：

  • 令牌阶段：主机发 PID 为 IN 的令牌包给设备，通知设备往主机送数据。
  • 数据阶段：设备按自己的情况三选一。
    • 端点正常：发出数据包，DATA0/DATA1 交替。
    • 设备正忙：发 NAK，IN 事务提前结束，等下一个 IN 事务再来问。
    • 端点被禁止：发 STALL，事务提前结束，总线回空闲。
  • 握手阶段：主机正确收到数据后向设备发 ACK。注意方向——ACK 是主机发的。

OUT 事务——主机给数据：

  • 令牌阶段：主机发 PID 为 OUT 的令牌包，通知设备准备接收。
  • 数据阶段：主机把数据送出去，DATA0/DATA1 交替。
  • 握手阶段：设备三选一。
    • 接收正确：回 ACK，主机可以发下一包。若数据包 CRC 校验错，设备什么都不回。
    • 设备正忙：回 NAK，让主机重发。
    • 端点被禁止：回 STALL，事务提前结束，总线进空闲。

「CRC 错就什么都不回」这条要记住。抓包时看到某个 OUT 事务后面没有握手包，不是分析仪漏了，是设备故意沉默。主机靠超时判定失败，然后重传。

SETUP 事务——主机下命令：

  • 令牌阶段：主机发 PID 为 SETUP 的令牌包。SETUP 也是 OUT 方向，但用专门的 PID。
  • 数据阶段：主机送出一个固定 8 字节的 DATA0 包，这 8 个字节就是标准设备请求命令。SETUP 事务的数据包永远是 DATA0，永远是 8 字节。
  • 握手阶段：设备收到命令后回 ACK，总线进入空闲，准备下一次传输。SETUP 阶段设备只能回 ACK，或者什么都不回。

一次控制传输的第一个事务一定是 SETUP。SETUP 之后一般跟一个 IN 或 OUT 事务。

3.6 帧与微帧 #

全速和低速的时间基准是帧，1 帧 = 1ms。高速把每帧再切成 8 个微帧，1 微帧 = 125us。主机在每个帧/微帧开头发一个 SOF 包，把帧号广播出去，所有设备据此对齐时钟。

带宽预算就是按帧/微帧算的。规范给每类传输划了上限：高速控制传输不能占用超过 20% 的微帧，全速和低速控制传输不能超过 10%；高速中断传输不超过 80%，全速和低速不超过 90%；全速同步传输不超过 80%，高速同步不超过 90%。剩下的零头留给批量传输。

四、USB 设备请求 #

4.1 八个字节定天下 #

标准设备请求命令放在控制传输的建立阶段，就是 SETUP 事务里那个 8 字节 DATA0。所有命令都是 8 字节，结构完全一致，由 5 个字段构成：

text
bmRequestType(1) + bRequest(1) + wValue(2) + wIndex(2) + wLength(2)

字段名首字母有讲究：bm 是位图（bitmap），b 是单字节（byte），w 是双字节（word）。

字段 长度 含义
bmRequestType 1 方向 + 请求类型 + 接收者
bRequest 1 命令代码
wValue 2 命令参数，含义随命令变
wIndex 2 索引或偏移，含义随命令变
wLength 2 后续数据阶段的字节数，0 表示没有数据阶段

4.2 bmRequestType 的位图 #

这一个字节把三件事压在一起：

text
D7 D6 D5 D4 D3 D2 D1 D0
 |  └─┬─┘ └────┬────┘
 |    |        └── 接收者
 |    └── 请求类型
 └── 传输方向

D7 方向位。 0 表示主机到设备（OUT），1 表示设备到主机（IN）。

D6D5 请求类型。 00 标准请求，01 类请求，10 用户自定义，11 保留。

D4~D0 接收者。 00000 设备，00001 接口，00010 端点，00011 其他，其余保留。

所以 0x80 是「设备到主机、标准请求、接收者是设备」，0x00 是「主机到设备、标准请求、接收者是设备」，0x81 是「设备到主机、标准请求、接收者是接口」，0x02 是「主机到设备、标准请求、接收者是端点」。抓到包先拆这一个字节，后面的字段怎么解释就有了依据。

4.3 十一个标准请求 #

编号 名称 bmRequestType 常见值 作用
0 GET_STATUS 0x80 / 0x81 / 0x82 返回特定接收者的状态
1 CLEAR_FEATURE 0x00 / 0x01 / 0x02 清除或禁止接收者的某些特性
3 SET_FEATURE 0x00 / 0x01 / 0x02 启用或激活接收者的某些特性
5 SET_ADDRESS 0x00 给设备分配地址
6 GET_DESCRIPTOR 0x80 获取指定描述符
7 SET_DESCRIPTOR 0x00 修改或增加描述符
8 GET_CONFIGURATION 0x80 获取当前配置值
9 SET_CONFIGURATION 0x00 让设备采用指定配置
10 GET_INTERFACE 0x81 获取当前接口的备用设置编号
11 SET_INTERFACE 0x01 让设备用某个备用设置
12 SYNCH_FRAME 0x82 设置并报告端点的同步帧

编号 2 和 4 是空的，历史遗留，别去找。

GET_DESCRIPTOR 是枚举期间被调用最多的一个。它的 wValue 高字节是描述符类型、低字节是索引，wIndex 是语言 ID 或 0，wLength 是想要多少字节。

4.4 抓到的第一个包，逐字节拆 #

主机插入设备后发的第一个 GET_DESCRIPTOR：

text
80 06 00 01 00 00 40 00

拆开看：

字节 值 含义
bmRequestType 0x80 设备到主机，标准请求，接收者=设备
bRequest 0x06 GET_DESCRIPTOR
wValue 0x0100 高字节 0x01 = 设备描述符，低字节 0x00 = 索引 0
wIndex 0x0000 语言 ID，设备描述符不用
wLength 0x0040 最多要 64 字节

注意 USB 是多字节小端。00 01 读成 0x0100，40 00 读成 0x0040。抓包时看十六进制串，别按大端读。

枚举早期还会看到 80 06 00 01 00 00 08 00——同样的请求，只要 8 字节。原因在第十章讲，那是整个枚举最关键的一步。

SET_ADDRESS 的样子：

text
00 05 03 00 00 00 00 00
字节 值 含义
bmRequestType 0x00 主机到设备，标准请求，接收者=设备
bRequest 0x05 SET_ADDRESS
wValue 0x0003 新地址是 3
wIndex 0x0000 无
wLength 0x0000 无数据阶段

设备收下这个请求后回一个 0 长度的状态包，主机再回 ACK，设备从此只对地址 3 应答。

SET_CONFIGURATION 的样子：

text
00 09 01 00 00 00 00 00

wValue 低字节 0x01 就是选中的配置值，对应配置描述符里的 bConfigurationValue。传 0 表示让设备回到未配置状态。

GET_STATUS 用来读设备、接口或端点的状态位，返回 2 个字节。设备级的状态位里有一位是「自供电」，有一位是「远程唤醒已使能」。端点级的状态位里有一位是「端点暂停」，这就是 STALL 状态的可读版本。

CLEAR_FEATURE 和 SET_FEATURE 用来改这些状态位。最常用的场景是实现远程唤醒：设备侧 SET_FEATURE(DEVICE_REMOTE_WAKEUP)，主机侧远程唤醒时清掉它。

这 11 个命令是控制传输的重心，控制传输又是 USB 协议的重心。枚举全程只用这些命令，一个都不多。

五、描述符：设备的自我介绍 #

5.1 描述符是什么 #

描述符是一个完整的数据结构，存在设备的固件里，用固定字段描述设备的某一层属性。主机通过 GET_DESCRIPTOR 一条条要过来，拼出完整的设备画像：什么功能、属于哪一类、要占多少带宽、用哪种传输、单次能收多大。

设备不主动说，主机不猜。主机问一个，设备答一个。主机哪一条没问，设备就永远不开口。这就是描述符和枚举的关系。

标准描述符五类，编号是固定的：

编号 描述符 数量关系
1 设备描述符 Device 一个设备有且只有一个
2 配置描述符 Configuration 一个设备可有多个
3 字符串描述符 String 可选，按索引取
4 接口描述符 Interface 一个配置可有多个
5 端点描述符 Endpoint 一个接口有几个端点就有几个

除此之外还有设备限定符描述符、其他速度配置描述符、接口关联描述符、类特定描述符（HID 的报表描述符、集线器的端口描述符），都用 GET_DESCRIPTOR 取，编号各不相同。HID 的报表描述符类型是 0x22，这个编号会经常见到。

5.2 层级关系 #

五类描述符不是平铺的，是嵌套的：

text
设备描述符 (1 个)
 └── 配置描述符 (1..n 个)
      └── 接口描述符 (1..n 个)
           └── 端点描述符 (0..n 个，不含端点 0)
字符串描述符 (0..n 个，被上面各处用索引引用)

一句话记住：一个设备只有一个设备描述符；一个设备描述符可以包含多个配置描述符；一个配置描述符可以包含多个接口描述符；一个接口用了几个端点就有几个端点描述符。

拿一个既能播视频又能放音频的播放器当例子：整个设备对应一个设备描述符；视频功能对应一个接口描述符，音频功能对应另一个接口描述符；为了喂饱视频，下层会开好几个端点并行搬数据，于是有好几个端点描述符。

配置和接口是对设备功能的抽象，真正搬数据的是端点。用设备之前必须先指明用哪个配置、哪个接口——这个动作在枚举里完成。

设备侧还可以这么理解：一个 USB 设备由三个功能模块组成——USB 总线接口、USB 逻辑设备、功能单元。总线接口就是串行接口引擎（SIE），逻辑设备被系统软件看成一堆端点，功能单元被客户软件看成一堆接口。SIE、端点、接口都是设备的组成单元。

5.3 设备描述符 #

c
struct usb_device_descriptor {
    __u8  bLength;             // 描述符长度，固定 0x12
    __u8  bDescriptorType;     // 类型编号，固定 0x01
    __le16 bcdUSB;             // USB 版本号，BCD 编码，0x0200 表示 2.0
    __u8  bDeviceClass;        // 设备类代码
    __u8  bDeviceSubClass;     // 设备子类代码
    __u8  bDeviceProtocol;     // 设备协议代码
    __u8  bMaxPacketSize0;     // 端点 0 最大包长：8/16/32/64
    __le16 idVendor;           // 厂商编号 VID
    __le16 idProduct;          // 产品编号 PID
    __le16 bcdDevice;          // 设备出厂版本号
    __u8  iManufacturer;       // 厂商字符串索引
    __u8  iProduct;            // 产品字符串索引
    __u8  iSerialNumber;       // 序列号字符串索引
    __u8  bNumConfigurations;  // 配置数量
} __attribute__ ((packed));

字段里有几个坑：

bDeviceClass。 0x01~0xFE 是 USB 组织分配的类代码，0xFF 是厂商自定义，0x00 表示「类在接口描述符里定义」。最后这一条很重要：绝大多数复合设备在设备级填 0x00，真正说明自己是什么的在接口级的 bInterfaceClass。你在设备描述符里看到 0x00 别以为是空的。

bMaxPacketSize0。 端点 0 单次能收的最大字节数，合法的只有 8、16、32、64。这个值是枚举的第一个门槛——主机在还不知道这个字段之前，只能按最小值 8 字节去要数据。第十章会展开。

idVendor / idProduct。 驱动匹配的主要依据。lsusb 输出的那串 0951:1666 就是这两个字段。

三个 i 开头的字段。 都是字符串描述符的索引，0 表示没有。它们不是字符串本身，是索引，要另发 GET_DESCRIPTOR 去取。

5.4 配置描述符 #

c
struct usb_config_descriptor {
    __u8  bLength;             // 固定 0x09
    __u8  bDescriptorType;     // 固定 0x02
    __le16 wTotalLength;       // 本配置下所有描述符的总长度
    __u8  bNumInterfaces;      // 本配置支持的接口数
    __u8  bConfigurationValue; // SET_CONFIGURATION 要传的值
    __u8  iConfiguration;      // 描述本配置的字符串索引
    __u8  bmAttributes;        // 供电模式
    __u8  bMaxPower;           // 从总线取的最大电流，单位 2mA
} __attribute__ ((packed));

wTotalLength 是这一层的枢纽。 它给的是「配置描述符 + 它下面所有接口描述符 + 所有端点描述符 + 所有类特定描述符」的字节总数。主机先只要前 9 字节拿到它，再按这个长度一次性把整块取回来。省了一次次猜长度的麻烦。

bmAttributes 各位的含义。 bit7 固定为 1；bit6 表示自供电；bit5 表示支持远程唤醒；低 5 位保留为 0。所以一个自供电且支持远程唤醒的设备的 bmAttributes 是 0xE0，总线供电且不支持唤醒是 0x80。

bMaxPower 的单位是 2mA。 字段值 0x32 表示 100mA，0xFA 表示 500mA。写固件时按 2mA 一步算，别按 1mA。

配置可以有多个。低功耗模式一个配置，高性能模式一个配置，靠 bConfigurationValue 区分。同一时刻设备只能处于一个配置下。

5.5 接口描述符 #

c
struct usb_interface_descriptor {
    __u8 bLength;            // 固定 0x09
    __u8 bDescriptorType;    // 固定 0x04
    __u8 bInterfaceNumber;   // 接口编号，从 0 开始
    __u8 bAlternateSetting;  // 备用设置编号
    __u8 bNumEndpoints;      // 本接口用到的端点数，不含端点 0
    __u8 bInterfaceClass;    // 接口类
    __u8 bInterfaceSubClass; // 接口子类
    __u8 bInterfaceProtocol; // 接口协议
    __u8 iInterface;         // 描述本接口的字符串索引
} __attribute__ ((packed));

接口是端点的集合，代表设备的一个独立功能。一个光驱读盘时用大容量存储接口，放 CD 时用音频接口，两个接口在同一个配置下并存。

bAlternateSetting 是接口的「档位」。 同一功能可以有多套端点配置，用不同的 bAlternateSetting 区分。设备处于配置态时，主机用 SET_INTERFACE 切换档位。典型用途是等时带宽协商：先按 0 号设置（不占带宽）枚举，协商好了切到 1 号设置（真正开流）。

类的判定顺序是接口优先。 bDeviceClass 为 0x00 时，看 bInterfaceClass。HID 是 0x03，大容量存储是 0x08，CDC 通信类是 0x02，厂商自定义是 0xFF。

5.6 端点描述符 #

c
struct usb_endpoint_descriptor {
    __u8  bLength;          // 固定 0x07
    __u8  bDescriptorType;  // 固定 0x05
    __u8  bEndpointAddress; // bit7 方向，bit3~0 端点号
    __u8  bmAttributes;     // 传输类型
    __le16 wMaxPacketSize;  // 本端点单次收发最大包长
    __u8  bInterval;        // 轮询间隔
} __attribute__ ((packed));

bEndpointAddress 是打包的。 bit7 是方向，0 表示 OUT（主机到设备），1 表示 IN（设备到主机）；bit3~0 是端点号。所以 0x81 是端点 1、IN 方向，0x02 是端点 2、OUT 方向。这两个是不同的端点，共用一个编号是合法的。

bmAttributes 的低 2 位定传输类型。 00 控制，01 同步，10 批量，11 中断。剩下几位在同步传输里表示同步类型和用途（bit3~2 表示同步方式，bit5~4 表示用途是数据还是反馈）。

wMaxPacketSize 低 11 位是单包最大字节数，高 5 位在高速高带宽端点里表示每微帧额外的事务数。 别整个字段当数值读。高速批量端点这个值是 512，全速批量是 8/16/32/64。

bInterval 只对中断和同步端点有意义。 批量端点和控制端点忽略它。同步端点还要求这个值为 1。中断端点的含义随速度变，第六章给表。

5.7 字符串描述符 #

c
struct usb_string_descriptor {
    __u8  bLength;
    __u8  bDescriptorType;  // 固定 0x03
    __le16 wData[];         // UTF-16LE 编码的字符串
} __attribute__ ((packed));

内容是 UNICODE 编码，可以被客户软件读取。设备制造商名称、产品名、序列号都放这里。字符串描述符是可选的，省略不影响功能。

取字符串要走两步：先取索引 0 的字符串描述符，它不带内容，只给出一串支持的语言 ID；再用目标语言 ID 去取真正的字符串。索引 0 那个描述符的长度字段除以 2 再减 1，就是支持的语言数。

六、端点与四种传输类型 #

6.1 端点是可寻址的 FIFO #

端点在设备内部，是所有通信数据的来源或目的地，本质是一个可寻址的 FIFO。设备有唯一地址，端点编号上限是 16；主机发出设备地址加端点号，就把数据投递到具体的 FIFO。

三条规则：

  1. 端点地址 0~15，一个端点地址对应一个方向。所以端点 2-IN 和端点 2-OUT 是两个完全不同的东西。
  2. 每个设备有一个默认的双向控制端点 0，它同时具备 IN 和 OUT 两个物理单元，不存在「端点 0-IN」和「端点 0-OUT」的区分。
  3. 端点 0 在设备上电后即可使用；非 0 号端点必须配置之后才能用。

利用设备地址、端点号、传输方向，三者合起来才能唯一指定一个端点。

6.2 端点号不是越多越好 #

设备支持的端点数有限制。除默认端点外，低速设备最多 2 组（2 个输入、2 个输出），全速和高速设备最多 15 组。

芯片侧的例子：S5PV210 有 EP0~EP15 共 16 个端点；MC68HC908JB8 只有端点 1 和端点 2，其中端点 1 只能发（IN），端点 2 收发都行；MC9S12UF32 有 6 个。

实际项目里常用的只有 3 个：EP0 传配置和控制信息，EP1 做 IN，EP2 做 OUT。为什么够用——因为端点只是一段缓冲，真正的带宽由主机排班决定，堆端点不会变快。

这里有个流传很广的错误说法要纠正：「IN 端点用于把数据从 Host 传到 Device」是错的。 IN 的方向永远是从设备到主机，无一例外。

名字一律按主机视角读。usb_rcvbulkpipe(dev, ep) 是主机接收，走的是设备的 IN 端点；usb_sndbulkpipe(dev, ep) 是主机发送，走的是设备的 OUT 端点。看反了会把收发调个头，而且它不会报错，只会数据错位，排查起来很费劲。

6.3 端点分两类 #

按用途分：0 号端点和非 0 号端点。

端点 0 特殊在它必须存在、必须支持控制传输、上电即可用，是设备的默认控制管道。系统软件就是通过这条管道跟设备做配置通信的。枚举全程只用这条管道。

非 0 号端点 在配置之后才能用，按接口分配，每个有自己的传输类型和方向。

端点的传输特性决定了它跟主机通信时用哪种传输类型。控制端点只能用控制传输，中断端点只能走中断传输，这条绑定关系在硬件和协议两层都成立。

6.4 管道：端点在主机侧的对偶 #

数据传输这件事，从系统结构看是主机软件和设备的各个端点之间直接进行的，它们之间的连接叫管道（Pipe）。管道在设备配置过程中建立。

管道是对主机与设备间通信流的抽象，表示主机的数据缓冲区与设备端点之间存在逻辑数据传输，实际搬运由总线接口层完成。

管道的三个性质：

  • 管道与端点一一对应。设备有多少端点，主机就有多少条管道。
  • 端点的类型决定管道的传输类型。中断端点对应中断管道，该管道只能做中断传输。
  • 各管道里的数据传输相互独立，互不干扰。

还有一个概念叫「消息管道」：只有控制传输能用，因为它的建立阶段和状态阶段的数据包有协议规定的固定结构，主机和设备要按格式解析。其他三种传输的载荷没有格式定义，都是裸数据，走的是「流管道」。

管道落到 Linux 里就是 struct usb_host_endpoint 的 urb_list——设备驱动调 usb_submit_urb() 时，urb 被挂到目标端点的队列尾巴上：

c
struct usb_host_endpoint {
    struct usb_endpoint_descriptor desc;  // 端点描述符
    struct list_head urb_list;            // 本端点的 URB 队列，由 USB 核心维护
    void *hcpriv;
    struct ep_device *ep_dev;             // sysfs 信息
    unsigned char *extra;                 // 额外的描述符
    int extralen;
    int enabled;
};

这一段属于驱动侧的话题，这里只放出来说明「管道」在代码里长什么样。urb 怎么排队、怎么回收，看同目录那篇。

6.5 四种传输类型：先看取舍 #

四种传输不是四套技术，是四种调度策略。分成两个维度：

  • 是不是周期性要带宽：中断和同步是周期性的，主机为它们预留带宽；控制和批量是异步的，有空就用。
  • 要不要保证正确：控制和批量、中断都保证正确（有握手、有重传）；同步不保证，丢就丢了。
维度 控制 中断 批量 同步

选哪种，只看两个问题：延迟重不重要，正确性重不重要。

  • 两者都要：控制传输。这是最贵的一种，带宽有硬配额，所以只用来做配置，不用来搬业务数据。
  • 延迟重要、数据量小、必须正确：中断传输。鼠标键盘就是它。
  • 正确性重要、延迟不重要、数据量大：批量传输。U 盘就是它。
  • 延迟最重要、允许少量出错：同步传输。音视频就是它。

四种传输的事务结构只有三种：中断和批量的结构完全一样（都是 OUT 或 IN 事务，带握手），同步最简（没有握手阶段，数据包全用 DATA0），控制最复杂（三个阶段，有专门的 SETUP 事务）。

6.6 事务、传输、帧的关系 #

三个词经常被混用，理一下：

  • 包（Packet） 是最小单位，不能被打断，被干扰就作废。
  • 事务（Transaction） 由若干个包组成，也不能被打断。属于同一次事务的几个包必须连续，不能跨帧完成。
  • 传输（Transfer） 由一次到多次事务组成，可以跨帧完成。

一次传输可以横跨好几帧，中间插别的设备的事务也没关系，只要每次事务内部连续。这就是主机能在同一根线上同时伺候多个设备的原因。至于为什么能这样，回到第二章那句话：一切由主机排班。

七、控制传输 #

7.1 三个阶段的骨架 #

控制传输是可靠的双向传输，最重要也最复杂。一次控制传输分三个阶段，每个阶段本身可以看作一次独立的传输：

阶段 事务类型 方向 内容 是否可省
建立 Setup SETUP 主机 → 设备 固定 8 字节的请求命令 不可省
数据 Data IN 或 OUT 由请求决定 请求要求的数据 可省
状态 Status IN 或 OUT 与数据阶段相反 0 长度包 不可省

三个阶段里，每个阶段都可以由一次或多次事务组成。数据阶段在传输量大时会拆成多次事务。

枚举全程只用控制传输。主机通过它交换信息、分配地址、读描述符，让设备被识别、被匹配驱动。每个做 USB 的人都要吃透这一段。

7.2 建立阶段 #

建立阶段就是一个 SETUP 事务，主机发 SETUP 令牌包，跟一个 8 字节的 DATA0，内容是标准请求命令。设备只能回 ACK，或者什么都不回。

这里的关键是：建立阶段就决定了后面有没有数据阶段、数据往哪个方向走。 看 wLength：为 0 就没有数据阶段，非 0 就有。看 bmRequestType 的 D7 位：为 1 是设备到主机（数据阶段是 IN 事务），为 0 是主机到设备（数据阶段是 OUT 事务）。

所以主机在发完 SETUP 之后，下一步该发什么令牌，完全是算出来的，不是试出来的。

7.3 数据阶段 #

数据阶段通过一次或多次控制事务完成，同样采用 PID 翻转机制。

流程上和批量传输没什么区别。差别只在于发生的端点不一样（控制传输永远走端点 0）、支持的最大包长不一样、优先级不一样——这些对用户都是透明的。

最大包长有硬规定：高速设备端点 0 是 64 字节，低速设备是 8 字节，全速设备可以是 8、16、32、64。这就是 bMaxPacketSize0 字段的合法取值集合。

最大包长表征端点单次收发的能力，实际反映的是端点缓冲的大小。缓冲越大，单次能搬运的包越大。数据超过端点的最大包长，就要拆成多个包传，并且除最后一个包外，所有包的长度都必须等于最大包长。

由此得到一条极有用的判据：收到的包长度小于最大包长，就说明这次传输结束了。 主机靠这个判断数据阶段何时收尾，不需要额外的长度信号。如果数据长度恰好是最大包长的整数倍，那就要再来一个 0 长度的包做结尾，否则接收方一直等下去。

7.4 状态阶段 #

状态阶段用一次方向与前一次相反的事务表明传输成败。

成功返回一个长度为 0 的数据包，失败返回 NAK 或 STALL。

「方向相反」这条要拆开看。状态阶段的两个方向名字有点绕：

  • 数据阶段是 IN（设备往主机送数据），状态阶段就是 OUT（主机往设备送一个 0 长度包），设备回 ACK 表示一切收到。
  • 数据阶段是 OUT（主机往设备送数据），状态阶段就是 IN（设备往主机送一个 0 长度包），主机回 ACK。

这里的 IN/OUT 名字没变，变的是「谁在发数据」。而且状态阶段的数据包永远是 0 长度的，格式就是 SYNC + PID + CRC16，载荷为空。

为便于对照，把控制传输的一个完整例子按事务列出来（读设备描述符，要 18 字节，端点 0 最大包 8 字节）：

text
SETUP  令牌  ADDR=0 ENDP=0    数据 DATA0: 80 06 00 01 00 00 12 00   设备回 ACK
IN     令牌  ADDR=0 ENDP=0    数据 DATA1: 8 字节描述符              主机回 ACK
IN     令牌  ADDR=0 ENDP=0    数据 DATA0: 8 字节描述符              主机回 ACK
IN     令牌  ADDR=0 ENDP=0    数据 DATA1: 2 字节描述符              主机回 ACK
OUT    令牌  ADDR=0 ENDP=0    数据 DATA1: 0 长度（状态）            设备回 ACK

注意最后那个 OUT：它是「主机告诉设备，前面这些数据我都收到了」。设备回 ACK，整次控制传输结束。

7.5 控制传输的带宽限制 #

控制传输访问总线时受限。高速端点的控制传输不能占用超过 20% 的微帧，全速和低速不能超过 10%。

如果一帧里有多余的未用时间，并且没有同步和中断传输占着，这些时间可以用来做控制传输。这就是为什么枚举在某些满载总线上会变慢——控制传输只能捡剩下的时间片。

7.6 为什么控制传输必须可靠 #

因为它的语义就是「下命令」和「取信息」。SET_ADDRESS 丢了，设备地址就错了，后面全乱。SET_CONFIGURATION 丢了，设备的端点都没使能，业务根本起不来。

所以控制传输不只是「可靠」——它是整个 USB 体系的地基。它在协议里有最高的保障：每个事务都有握手，失败必重传，带宽还给它留了配额，保证它总有机会发出去。

八、中断、批量与同步传输 #

8.1 中断传输：名字骗人 #

先说清一件事：USB 的中断传输跟 CPU 中断没有半点关系。

它叫中断，是因为它起源于「让 HID 设备能像 PS/2 中断那样及时上报」这个需求。实现方式和中断正好相反：主机按固定间隔主动来问端点「你有数据吗」，有就取走，没有就回 NAK。

设备想上报一个按键，它只能把状态写进端点缓冲，然后等。等主机在下一个轮询点来问。这个间隔就是 bInterval，最坏情况下按键延迟就是一个间隔。

所以「中断传输」这个名字应该理解成「有保证的定期轮询」，而不是「设备主动打断主机」。

参数。

项目 高速 全速 低速
最大包长 1024 字节 64 字节 8 字节
轮询间隔 (2^bInterval-1)×125us，bInterval 取 1~16 1~255ms 10~255ms
带宽上限 不超过 80% 微帧 不超过 90% 帧 不超过 90% 帧

特性。 单向传输、延迟有保证、非实时、可靠、支持错误重传。优先级仅次于同步传输。

「单向」指的是在某个端点上只支持一个方向，或输入或输出。要在两个方向上各做一次，就占两个端点，配置成不同方向，可以用相同的端点编号——这就是为什么 0x81 和 0x01 能同时存在。

除高速高带宽端点外，一个微帧内只允许一次中断事务。高速高带宽端点最多在一个微帧内做三次中断事务，一帧能搬 3072 字节。

流程。 除不支持 PING 之外，中断传输跟批量传输一模一样，也是令牌—数据—握手三段，也用 PID 翻转保证收发同步。主机按端点描述符里的 bInterval 排班，到点就来问。

典型设备。 键盘、鼠标、摇杆、触摸屏、各种 HID。数据量小、要求低延迟、丢了要重传。

8.2 批量传输：正确第一，时间不管 #

批量传输是可靠的单向传输，延迟没有保证。它尽量利用一切可利用的带宽，适合数据量大的场合。

低速设备不支持批量传输。高速批量端点最大包长 512 字节，全速批量端点可以是 8、16、32、64。

优先级最低。 主机总是优先安排其他类型的传输，等总线带宽有富余时才排批量。所以一个正在读 U 盘的同时插鼠标，鼠标绝不会有延迟，U 盘的吞吐会掉下来——这是设计意图，不是 bug。

高速批量必须支持 PING。 主机想送数据前先发 PING 探测：设备回 ACK 表示能收，回 NAK 表示忙，回 NYET 表示这包收了但下一包先别来。低速和全速没有 PING，它们靠 NAK 就够。

重试机制。 批量传输可靠，靠握手包表明结果。数据量大时用多次批量事务完成，过程中 PID 按 DATA0-DATA1-DATA0 翻转，保证收发同步。

成功就把错误计数器清零，失败就累加。USB 允许连续 3 次以内的传输错误并重试该传输。超过三次，主机认为该端点功能错误（STALL），放弃该端点的传输任务。

这个「三次」是个硬数字。你抓包看到某个端点连续几个事务都没有 ACK、随后主机不再发令牌，就是撞到这堵墙了。

PID 翻转的细节值得单独说。发送端按 DATA0-DATA1-DATA0 的顺序发，但只有成功的事务才导致 PID 翻转。发送方收到 ACK 之后才翻 PID 发下一包，没收到 ACK 就重试本次事务，PID 不变。

接收端同样靠这个检测重复：如果连续收到两个 DATA0，第二个就是前一个的重传，丢掉即可。这就是 USB 在「可靠传输」之上还能做到「幂等」的办法——不用序号，用一比特的翻转状态。

典型设备。 U 盘、移动硬盘、打印机、扫描仪、USB 网卡。共同点：数据量大，慢一点没关系，错一个字节都不行。

8.3 同步传输：实时第一，错了就错了 #

同步传输是实时的、不可靠的传输，不支持错误重发。

只有高速和全速端点支持同步传输。高速同步端点最大包长 1024 字节，全速是 1023。低速设备没有同步传输。

两个特殊之处，必须记住。

  1. 同步传输的 IN 和 OUT 事务没有握手包阶段。整个事务只有令牌和数据两段。因为不关心数据到没到，也就不需要确认。
  2. 数据阶段所有的数据包都是 DATA0，不做 PID 翻转。没有重传，就不需要区分新旧。

参数。

项目 高速 全速
最大包长 1024 字节 1023 字节
带宽上限 不超过 90% 微帧 不超过 80% 帧
优先级 最高 最高

除高速高带宽端点外，一个微帧内只允许一次同步事务。高速高带宽端点最多一个微帧三次，一帧 3072 字节。同步端点和中断端点一样，有固定的访问间隔。

为什么允许出错。 音视频流的场景是：这一毫秒的采样没了就没了，重传来一包过期的数据反而更糟。播放器宁可插一段静音或者重复上一帧，也不要一个 50ms 后才到的正确样本。所以协议直接放弃重传，把带宽全部用来保证「每秒有固定量的数据」。

这也是为什么同步传输的带宽是预留的：主机在配置阶段就要按端点的 wMaxPacketSize 和 bInterval 算出每帧要占多少，算不进去就直接拒绝这个配置。SET_INTERFACE 切换备用设置，主要就是为了这件事。

典型设备。 USB 音频（麦克风、音箱、声卡）、USB 视频（摄像头）、实时数据采集。共同点：恒定速率、允许少量误码、延迟敏感。

九、分离传输 #

9.1 要解决的问题 #

高速总线上挂了全速或低速设备，怎么办？

如果让高速主机直接跟低速设备做一次完整事务，问题很明显：低速设备的响应慢，一次事务的往返时间被它拖得很长，这段时间高速总线在干等。480Mbps 的线路上空转几十微秒，浪费惊人。

分离传输（Split Transaction）就是为了这个。它在主机控制器和 HUB 之间执行，把一次完整事务拆成两段，中间的空档让给别的高速传输。

对设备完全透明。 设备不知道自己被拆了，它看到的还是一次正常的事务。只有主机控制器和 HUB 知道内情。

9.2 怎么拆 #

一次完整事务本来是这样：

text
主机 ──── 令牌 + 数据 ────> 设备
主机 <─── 握手/数据 ──────── 设备

拆成两段：

text
第 1 段(SSPLIT)：主机 ── 令牌+数据 ──> HUB        （HUB 立刻回 ACK，收下活）
                  中间插入其他高速事务
第 2 段(CSPLIT)：主机 ── 查询 ──────> HUB         （问：办完了吗？）
                  HUB ── 结果 ──────> 主机        （办完了，给你结果）

用一个 SPLIT 令牌包（PID 0x08）标记，里面带一个 S 位区分起始还是完成。

  • SSPLIT（Start Split）：主机把令牌和数据交给 HUB，HUB 立刻回 ACK 表示收下了，主机随即走人去做别的事。
  • CSPLIT（Complete Split）：过一会儿主机回来问结果。HUB 这时回去跟低速设备完成剩下的往返，把结果给主机。如果 HUB 还没办完，它回 NYET，让主机下次再来问。

这样一来，主机在等低速设备的时间里去服务了别的高速设备，总线利用率上去了。

9.3 两种分离传输 #

按数据方向分：

  • 分离 IN：设备要往主机送数据。SSPLIT 阶段主机只发令牌，HUB 去设备那儿取数据，暂存；CSPLIT 阶段主机来取这份暂存的数据。
  • 分离 OUT：主机要往设备送数据。SSPLIT 阶段主机把数据连同令牌一起交给 HUB，HUB 存下来；CSPLIT 阶段主机来问「发出去了吗」，HUB 去跟设备完成写入，回报结果。

这两种的差别在于数据在哪一段走。IN 的数据在第二段才到主机，OUT 的数据在第一段就交给了 HUB。

9.4 什么时候你会碰到它 #

你写驱动时基本碰不到——HCD 全替你做了。但有两种场合会看到它：

  1. 抓包。分析仪上会看到成对的 SPLIT 事务，看起来像「同一个端点被访问了两次」。别以为是重传，那是一次被拆开的传输。
  2. 性能分析。低速设备多的总线上，SPLIT 事务本身也占带宽。一个 HUB 上挂 8 个低速设备，SPLIT 的开销能吃掉可观的微帧时间。

还有一条：分离传输只在主机控制器和 HUB 之间执行，不能跨两级 HUB。多级级联的低速设备，每一级都要自己做一次分离。

十、枚举：从插入到可用 #

10.1 枚举要解决什么 #

设备插上主机，主机对它的了解是零。不知道它是什么、要多少电、有几个端点、走哪种传输。这些信息全在设备自己的描述符里，得问出来。

枚举就是这一串问答。走完，主机有了完整的设备画像，可以选配置、装驱动、开始传数据。USB 的即插即用，就建立在这上面。

枚举只用一条通道：设备的默认控制管道，也就是端点 0，用默认地址 0 访问。这条管道在设备上电后立即可用，不需要任何配置。

10.2 六个状态 #

从插入到可用，设备会经过六个状态。理解这些状态，比背流程更有用——所有「设备认不出来」的问题，答案都是「它卡在哪个状态」。

状态 触发条件 关键特征
接入 Attached 设备物理接入 主机靠信号线电平变化发现
供电 Powered 端口供电 先 100mA，配置后按申报值
缺省 Default 复位完成 用地址 0 通信，可响应端点 0 控制传输
地址 Address SET_ADDRESS 成功 用主机分配的唯一地址通信
配置 Configured SET_CONFIGURATION 成功 端点使能，可以和客户软件传数据
挂起 Suspended 3ms 无总线操作 电流压到 280uA 以下

状态之间是单向推进的，除非复位。复位把设备打回缺省态，地址清零，重新开始。这个特性是枚举能容错的基础——任何一步出错，主机复位再来一遍就行。

注意顺序：先有地址态，才有配置态。 不分配地址就发 SET_CONFIGURATION，设备根本不知道你在跟谁说话。

10.3 六步主流程 #

把整个枚举压到最简，就是六步。这六步是骨架，每一步中间还夹着许多细节，但那都是枝叶。

步骤 主机动作 目的
1 检测到 D+ 上拉，读端口状态 确认有设备接入、什么速度
2 复位端口（SE0 ≥ 10ms） 让设备回到缺省态、地址 0
3 GET_DESCRIPTOR 只要 8 字节 拿到 bMaxPacketSize0
4 再次复位，SET_ADDRESS 分配地址 后续用新地址通信
5 按新地址重读全部描述符 拿到 VID/PID、配置、接口、端点
6 SET_CONFIGURATION 选择配置 端点使能，设备进入配置态

第 3 步和第 4 步之间为什么还要再复位一次？因为 SET_ADDRESS 之后设备就换地址了，而换地址的瞬间总线上不许有第二个设备也占着地址 0。复位能把状态清干净。规范要求主机在 SET_ADDRESS 之后让设备稳定一段时间（至少 2ms 无信号），再开始用新地址通信。

10.4 第 3 步：为什么先只读 8 字节 #

这一步是整个枚举最精妙的地方，值得单独一节。

问题是这样：主机要读设备描述符，共 18 字节。但主机现在只能发 IN 令牌，设备会按端点 0 的最大包长把数据切包送回来。如果主机不知道这个最大包长是多少，它就不知道该按多大的缓冲去接。

反过来，bMaxPacketSize0 这个字段本身就在设备描述符里，偏移量是 7（从 0 开始数），第 8 个字节。

所以主机只读前 8 个字节。这 8 个字节一定装得下——因为 bMaxPacketSize0 的最小合法值是 8。不管这个设备是 8、16、32 还是 64，前 8 个字节一定能在一包里拿到。

拿到这 8 个字节，主机读出 bMaxPacketSize0 的值，就知道了端点 0 的包长。后面所有的读操作都按这个值来算缓冲和拆包。

举个真实抓到的例子：

text
主机 → 设备:  80 06 00 01 00 00 08 00     (wLength = 8)
设备 → 主机:  12 01 10 01 00 00 00 40

返回 8 个字节，最后那个 0x40 就是 bMaxPacketSize0，等于 64。主机记下这个 64，放进端点 0 的描述符里（bit16~bit31 的 MPS 字段），后面的读操作就按 64 字节切包。

如果不做这一步直接要 18 字节会怎样？假设设备端点 0 的包长是 8，主机按 18 字节的缓冲去接，实际会收到 8 字节的包然后停住；假设设备包长是 64，主机按 8 字节的缓冲去接，会截断。两种都不对。

所以「先读 8 字节」不是优化，是必需。 这是主机在信息不足下唯一能自洽的做法。

同一个时刻，主机一次只能枚举一个设备。因为所有未配置设备都在地址 0 上，两个设备同时响应就撞了。这就是为什么插两个 U 盘，系统是一个一个认的。

10.5 完整流程，逐步展开 #

把六步展开成实际操作，就是下面这十几步。其中一部分是 HUB 的事，一部分是主机控制器的事，一部分是 USB 核心的事。

第 1 步：插入，供电，检测。

用户把设备插进端口，主机为端口供电，设备上电。HUB 通过 D+ 或 D- 上的上拉电阻发现接入，用它的中断端点把事件报告给主机。这一步设备处在接入态，随后进入供电态。

第 2 步：读端口状态。

主机发 Get_Port_Status 给 HUB，问细节。返回的信息告诉主机：这个口什么时候接的设备、现在是什么状态、设备跑什么速度。HUB 已经通过测哪根线电压高判定了低速还是全速，把结果放在状态字里。

第 3 步：复位端口。

主机发 Set_Port_Feature 给 HUB，要求复位这个端口。HUB 把该口的 USB 数据线置为复位状态，至少保持 10ms。

第 4 步：高速握手。

主机用 Chirp K 信号探测全速设备是否支持高速。双方握手成功就切到高速；不成功，设备留在全速。

第 5 步：确认复位结束。

主机再发一次 Get_Port_Status，确认设备已退出复位。返回数据里有一位表示设备仍在复位中。HUB 释放复位后，设备进入缺省态，准备好通过端点 0 响应控制传输。此时地址是 00h，设备能从总线取到最多 100mA 电流。

第 6 步：读 8 字节描述符。

这就是上一节说的那一步。80 06 00 01 00 00 08 00，拿回 8 字节，记录 bMaxPacketSize0。

第 7 步：分配地址。

主机发 SET_ADDRESS，wValue 就是新地址。设备读这个请求，回一个确认，保存新地址。从此所有通信都用这个新地址。

text
00 05 03 00 00 00 00 00      地址 = 0x03

具体分配几号，看主机当时挂了多少设备。设备产生接收中断后，把地址寄存器相应位设成新值。

第 8 步：按新地址读完整设备描述符。

text
80 06 00 01 00 00 12 00      wLength = 18，要全部 18 字节

主机这次知道端点 0 的包长了，按那个值分几次读。如果包长是 8，就分三次（8+8+2）；如果包长是 16，分两次（16+2）；如果包长是 64，一次够（18 < 64）。读到的内容包含 VID、PID，主机据此判断该装哪个驱动。

这里有个细节：如果一次读不完，最后一个包的长度会小于最大包长，主机据此判定结束。如果长度恰好是最大包长的整数倍，还需要再发一次 IN 拿一个 0 长度包作为结束标志。

第 9 步：循环读配置描述符。

主机发 GET_CONFIGURATION（更常见的是 GET_DESCRIPTOR 要配置描述符），先读 9 字节拿到 wTotalLength，再按这个长度读整块。读回来的是一整片字节，里面依次是配置描述符、接口描述符、端点描述符、类特定描述符，主机自己按 bLength 和 bDescriptorType 逐条切分。

第 10 步：读字符串描述符。

主机发 GET_DESCRIPTOR 要字符串，拿到厂商名、产品名、序列号。UNICODE 编码。这时候系统界面上会弹出「发现新设备」的提示，显示的就是这些内容。

第 11 步：匹配并加载驱动。

根据设备描述符和配置描述符，操作系统判断能不能提供驱动。现代系统内置了绝大多数设备类驱动（HID、存储、打印机、扫描仪、CDC、音视频），匹配上就直接加载，全程后台完成，用户看不到任何对话框。找不到匹配的驱动才会提示。

第 12 步：选择配置。

主机发 Set_Configuration(x)，x 是非 0 的配置值。配置成功后设备进入配置态，端点点使能，可以和客户软件传数据。

text
00 09 01 00 00 00 00 00      选择配置 1

到这一步，常规的配置和连接工作全部完成，设备可以开始用了。

第 13 步：接口级驱动。

复合设备要给每个接口分配驱动。一个设备如果同时有音频接口和 HID 接口，就会有两个不同的驱动分别绑定到两个接口上。

第 14 步：异常处理。

如果 HUB 检测到过流，或者主机要求 HUB 关掉端口电源，USB 总线会切断设备供电。这种情况下设备和主机无法通信，但仍处于物理连接状态。

10.6 枚举失败，卡在哪 #

按六个状态去对，比看日志快。

现象 卡在哪 常见原因
插入无任何反应 接入态之前 上拉电阻没接、D+/D- 接反、线缆断
认成 unknown device 缺省态 端点 0 不应答、SETUP 事务没回 ACK、固件没跑起来
有 VID/PID 但没驱动 地址态之后 描述符内容错、类代码写错、缺接口描述符
驱动加载了但传不了数据 配置态之前 bNumEndpoints 与实际的端点描述符数量不符、wTotalLength 算错
传一会儿就断 配置态之后 端点 STALL、缓冲区溢出、bMaxPower 申报不足导致掉电
偶尔能认，偶尔不能 供电或信号 电源纹波、D+ 上拉电阻阻值偏离 1.5kΩ、差分对没绞合

bNumEndpoints 与实际不符是很常见的一类。主机按 bNumEndpoints 预分配端点资源，字段写 2 但实际给了 3 个端点描述符，第三个就会被忽略；反过来写 3 只给 2 个，主机会去访问一个不存在的端点。两种都表现为「驱动起来了但通信异常」。

wTotalLength 算错也一样。这个字段是主机切分描述符块的唯一依据，少算一个端点描述符的长度，后面的解析全错位。

十一、枚举实例与抓包分析 #

11.1 一次真实的枚举：2440 读 U 盘 #

拿一块 S3C2440 的板子做主机，插一个 U 盘，把整个过程抓下来。这个例子能覆盖前面讲的每一步。

前提是主机侧已经初始化完毕：符合 OHCI 规范的寄存器都配好了，总线复位、中断使能、中断标志清除、电源管理、内存指针寄存器、各种数据结构初始化都做完，就等着设备插入。

枚举本质上就是主机和设备建立连接的过程——主机问，设备答，主机据此知道该怎么操作这个设备。

用到的传输只有一种：控制传输。 全程只走端点 0 的控制管道，因为它的建立阶段和状态阶段有协议规定的固定结构，能承载标准请求。

一次完整控制传输的三个过程，回顾一下：

  1. 建立连接：由主机发起，一个 SETUP 令牌包加一个 DATA0 包。
  2. 数据过程：可选。控制输入传输就是输入数据，控制输出传输就是输出数据。要不要这一段，由建立阶段的 wLength 决定——为 0 就没有。
  3. 状态过程：跟在数据过程之后，方向与数据过程相反，用来确认前面两阶段的数据都正确传到了。

下面按包看。

第一个 Setup 包：要 8 字节，拿端点 0 的包长。

text
80 06 00 01 00 00 08 00

wLength 是 0x0008，只要设备描述符的前 8 个字节。目的很明确：拿到端点 0 的最大包长，也就是第 8 个字节。

设备返回：

text
12 01 10 01 00 00 00 40

逐字节读：12 是 bLength，01 是 bDescriptorType（设备描述符），10 01 是 bcdUSB = 0x0110，00 是 bDeviceClass，00 是子类，00 是协议，最后 40 是 bMaxPacketSize0 = 64。

把 0x40 记下来，填进端点 0 描述符结构的 MPS 字段（bit16~bit31）。

第二个 Setup 包：分配地址。

text
00 05 01 00 00 00 00 00

bmRequestType 是 0x00（主机到设备、标准、设备接收者），bRequest 是 0x05（SET_ADDRESS），wValue 是 0x0001，分配地址 1。

设备接受这个地址设置包后，返回一个长度为 0 的数据包。主机收到这个 0 长度状态包后回一个 ACK 给设备，设备收到 ACK 后才启用新地址。

顺序不能反：设备必须等 ACK 到了才切地址。如果它在回完 0 长度包之后就立刻切，主机的 ACK 会发到旧地址上，设备收不到——当然实际上主机此时也还没切。

第三个 Setup 包：读配置描述符的前 9 字节。

text
80 06 00 02 00 00 09 00

wValue 是 0x0200（高字节 0x02 = 配置描述符），wLength 是 9。目的：拿到 wTotalLength，它位于配置描述符的第 3、4 字节。

设备返回：

text
09 02 20 00 01 01 00 80 32

逐字节读：09 是长度，02 是类型（配置描述符），20 00 是 wTotalLength = 0x0020 = 32 字节，01 是 bNumInterfaces = 1，01 是 bConfigurationValue = 1，00 是 iConfiguration，80 是 bmAttributes（总线供电、不支持远程唤醒），32 是 bMaxPower = 0x32 × 2mA = 100mA。

第四个 Setup 包：读整块配置描述符。

text
80 06 00 02 00 00 09 00

命令和上一个完全一样，不同的只是意图——这次要把整个配置描述符区域读回来。实际发的时候 wLength 直接写 0xFF 或写 wTotalLength 的值都行，读回多少算多少。有的程序干脆一次要 0xFF 个字节，同样能达到读回描述符集合的目的。

设备返回 32 字节：

text
09 02 20 00 01 01 00 80 32
09 04 00 00 02 08 06 50 00
07 05 82 02 40 00 00
07 05 02 02 40 00 00

按 bLength 和 bDescriptorType 切开：

字节串 长度 类型 解读
09 02 20 00 01 01 00 80 32 9 0x02 配置 总长 32，1 个接口，配置值 1，100mA
09 04 00 00 02 08 06 50 00 9 0x04 接口 接口 0，备用设置 0，2 个端点，类 0x08（大容量存储），子类 0x06（SCSI 透明命令集），协议 0x50（仅批量）
07 05 82 02 40 00 00 7 0x05 端点 端点 0x82（端点 2，IN），属性 0x02（批量），包长 64，间隔 0
07 05 02 02 40 00 00 7 0x05 端点 端点 0x02（端点 2，OUT），属性 0x02（批量），包长 64，间隔 0

到这里设备的身份就清楚了：U 盘，大容量存储类，SCSI 透明命令集，只有批量传输，一进一出两个 64 字节的批量端点。总共 9+9+7+7 = 32 字节，和 wTotalLength 对得上。

这也是自检的一个办法：把每个描述符的 bLength 加起来，看等不等于 wTotalLength。 不等就是描述符表本身写错了。

第五个 Setup 包：选择配置。

text
00 09 01 00 00 00 00 00

bRequest = 0x09（SET_CONFIGURATION），wValue = 0x0001，选配置 1。设备返回一个长度为 0 的数据包，表明正确接收。

至此枚举完成。设备进入配置态，两个批量端点使能，可以开始跑 SCSI 命令了。

11.2 状态阶段的特殊之处 #

上面的例子里，第五个 Setup 包后面跟的就是状态阶段。这里有两个容易想错的地方，单独拎出来。

状态阶段的 IN 和 OUT 事务，与数据阶段的 IN 和 OUT 事务有两点不同：

第一，方向的定义要按「谁在发数据」来读，不是按名字。

  • 平常：IN 是设备往主机送，OUT 是主机往设备送。
  • 状态阶段：IN 这个令牌下是主机往设备送，OUT 这个令牌下是设备往主机送。

这不是协议写错了，是为了和数据阶段配合：状态阶段的方向总和数据阶段相反。数据阶段是设备送数据过来（IN），状态阶段就是主机送一个空包过去确认（OUT 令牌，主机发数据）。反过来，数据阶段是主机送数据过去（OUT），状态阶段就是设备送一个空包过来确认（IN 令牌，设备发数据）。

第二，数据包长度永远是 0。

状态阶段的数据包就是 SYNC + PID + CRC16，没有载荷。它的作用不是搬数据，是「我收到了」这个信号本身。0 长度包配 PID 翻转，就能表达确认或否认。

11.3 协议分析仪在看什么 #

枚举跑得通不代表跑得好。设备偶发认不出、某个请求超时、大数据量传输时吞吐上不去，这些光看代码看不出来，得看线上的包。

这就是协议分析仪的位置。它是协议层的工具——对 USB 这种高速串行总线，只测物理层远远不够。高低电平里藏着丰富的指令，得有个东西按标准协议把数据分解开，把有用的信息提出来，再解释它们的含义。

它做的事很朴素：抓线上的信号，翻译成数据，按协议逐层解析，还原出「主机发了什么请求、设备回了什么」。传输过程中的错误会被明确标出来，你按上下文关系找问题就行。

SATA、SAS、Ethernet、FC 这些高速串行总线都有自己的协议分析工具，道理一样。

11.4 一个实际的调试例子 #

环境是这样：左边一台 PC 装分析仪软件，加分析仪主机，构成分析系统。DE2 实验板当 USB 设备，右边一台 PC 跑应用程序操作 DE2。要看的是两台 PC 之间——准确说是应用 PC 和 DE2 之间——的 USB 通信到底对不对。

DE2 是教学开发板，USB 接口那部分有一片接口控制芯片，加载固件就能控制 USB 数据传输。写固件的人最难受的地方在于：程序跑起来了，但没法验证它是不是按你想的执行。PC 端还得写驱动、写应用。所以硬件工程师和软件工程师都需要这个工具。

应用程序的功能： 按 ADD 键，给 DE2 发「加 1」指令，结果显示在 DE2 的液晶屏上；按 CLEAR 键，发清零指令，液晶屏显示 00。

期望发出去的数据：

  • ADD → AA AB AC AD AE AF A0 A1
  • CLEAR → 55 55 5C 5D 5E 5F 50 51

抓到的结果： 在分析仪上搜 DATA0 和 DATA1 包，内容都是上面这两组字节，和源码一致。按一次 ADD 就能捕到一次，按 CLEAR 同理。

结论很直接：USB 通信没有问题，可以进下一步的大数据量传输。

这个例子的价值不在结论，在方法。先定一个已知的、特征明显的字节序列，再在总线上找它。 找到了，说明从应用到固件到总线整条链路都通；找不到，问题在链路的哪一段就清楚了。比猜快得多。

协议分析仪的另一个用途是学习。枚举过程可以在分析仪上一步步看清楚，每个请求、每个响应、每个握手都摆在那里。教学时拿它讲 USB 通信过程，比讲十遍理论直观。

误区 事实
USB 用普通二进制电平传数据 用 NRZI：0 翻转、1 保持，还叠加了位插入
可以自己算 CRC 验证包的完整性 令牌包 5 位、数据包 16 位，模 2 除法。手算容易错，用工具
握手包也有 CRC 没有，只有 SYNC + PID。8 位 PID 自带反码校验
PID 的高 4 位是低 4 位的值 是低 4 位的反码。不相等就说明这 8 位坏了
一帧就是一包数据 一帧是 1ms 的时间单位，里面装着好几个事务，每个事务好几个包
高速也是一帧 1ms 高速的调度单位是微帧，125us，一帧切 8 个微帧
抓包看到的 SYNC 长度是固定的 HUB 会重新生成同步头，级联后 SYNC 会短于标称值
一个包可以跨帧传 包不能被打断。事务也不能。只有传输可以跨帧

12.3 描述符层 #

误区 事实
bDeviceClass 为 0 表示没有类 表示类定义在接口描述符里。复合设备多数这么填
bMaxPacketSize0 可以随便填 只能 8/16/32/64。填别的值主机直接认不出设备
bMaxPower 单位是 mA 单位是 2mA。要 100mA 就填 0x32
wTotalLength 只算配置描述符自己 要算上它下面所有接口、端点、类特定描述符的总长度
bEndpointAddress 就是一个端点号 bit7 是方向，bit3~0 才是端点号。0x81 ≠ 0x01
wMaxPacketSize 整个字段是包长 低 11 位是包长，高 5 位在高速高带宽端点里是每微帧额外事务数
bInterval 对批量端点有意义 批量端点忽略这个字段。填什么都一样
bNumEndpoints 包含端点 0 不包含。它只数非 0 号端点
字符串描述符必须有 可选。索引填 0 就表示没有
一个设备可以有多个设备描述符 有且只有一个。多个的是配置描述符

12.4 请求与传输层 #

误区 事实
标准请求有 16 个 11 个。编号 2 和 4 是空的
wLength 单位是位 字节。为 0 表示没有数据阶段
多字节字段按大端读 小端。00 01 是 0x0100
SETUP 事务的数据包长度可变 永远 8 字节，永远是 DATA0
控制传输的数据阶段必须存在 可以没有。看 wLength 是不是 0
状态阶段就是「读一下状态」 是一个 0 长度包，方向与数据阶段相反，表示「我收到了」
同步传输也有握手包 没有。同步事务只有令牌阶段和数据阶段
所有传输的 PID 都会翻转 同步传输不翻转，全用 DATA0
收到包就翻 PID 只有收到 ACK 才翻。失败重传时 PID 不变
收到两个连续的 DATA0 是异常 是重复包，第二个是重传，丢掉即可
批量传输会无限制重试 连续 3 次错误就 STALL，主机放弃该端点
NAK 是错误 是「忙」，不是错。会重试。STALL 才是错误

12.5 枚举层 #

误区 事实
枚举第一步是分配地址 是先复位。设备带着上一次的残留状态没法通信
第一次读描述符就读全部 18 字节 只读前 8 字节，为了拿 bMaxPacketSize0。此时不知道端点能收多大包
地址 0 可以同时给多个未配置设备用 每次只能枚举一个设备，否则地址 0 上撞车
SET_ADDRESS 之后立刻用新地址 设备要等主机的 ACK 到了才切地址，主机也要等至少 2ms 再发下一包
枚举用的是中断传输 全程只用控制传输，只走端点 0
设备一上电就能传业务数据 必须走完枚举，SET_CONFIGURATION 之后端点才使能
设备描述符读到了就知道全部信息 配置、接口、端点都在配置描述符块里，得另读
插上就挂起不是问题 3ms 无总线操作就是挂起态，电流要压到 280uA 以下

12.6 上手自查 #

拿到一个 USB 问题，按这个顺序过一遍，多数情况能定位：

  1. 看电平。 D+ 有没有 1.5kΩ 上拉。主机侧 D+ 和 D- 有没有 15kΩ 下拉。这一步错，后面全白搭。
  2. 看速度识别。 D+ 上拉是全速/高速，D- 上拉是低速。拉错线，设备会被识别成另一个速率。
  3. 看端点 0 应答。 复位后主机发 80 06 00 01 00 00 08 00，设备必须回 8 字节。不回，固件没跑或者 SIE 没使能。
  4. 看 bMaxPacketSize0。 抓 8 字节响应的最后一字节。值不在 8/16/32/64 里，描述符就写错了。
  5. 合 wTotalLength。 把配置块里每个描述符的 bLength 加起来，必须等于 wTotalLength。不等就是描述符表本身有问题。
  6. 核 bNumEndpoints。 数一下接口下实际挂了几个端点描述符。
  7. 看 SET_CONFIGURATION 的返回。 设备回 0 长度包才算成功。回了 STALL，说明配置值对不上或者端点资源不够。
  8. 看传输类型。 端点描述的 bmAttributes 低 2 位必须和你代码里用的传输方式一致。中断端点用批量传输 API，根本发不出去。
  9. 看 bInterval 的物理含义。 高速中断端点是 (2^bInterval-1)×125us，不是毫秒。填 1 表示 125us，不是 1ms。
  10. 看供电。 bMaxPower 申报太小，设备在大负载时会掉电重启，表现是「偶尔能认，偶尔不能」。

前面九条都能在抓包工具上验证，第十条只能靠万用表或者示波器看 VBUS 的跌落。

12.7 三句话收尾 #

第一句：USB 是主机主导的轮询式总线。 设备从不主动发数据，一切由主机发起。这一句解释了为什么没有冲突检测，也解释了为什么「中断传输」其实是主机定期来问。

第二句：四种传输是四种调度策略，选哪种取决于延迟和正确性哪个重要。 控制要两者兼顾所以带宽有配额，中断要延迟所以周期预留，批量要正确所以能等，同步要实时所以允许出错。

第三句：枚举的六步里，第三步「先只读 8 字节」是关键。 因为此时还不知道端点 0 能收多大包，只能先要一个最小的、一定装得下的量，从里面把 bMaxPacketSize0 挖出来，再拿这个值去规划后面所有的读。
