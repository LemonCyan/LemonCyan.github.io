这一篇只谈 Linux 侧的驱动代码：结构体长什么样，urb 怎么发出去，热插拔是谁在背后顶着跑。你敲下的每一个 usb_submit_urb()，从调用到落到总线上，中间过了哪几层，这里给全。

不讲什么：差分电平、包格式、四种传输类型的线上时序、枚举时总线上一共走了哪些请求。那些属于同目录的另一篇《USB 2.0 协议：从物理层到枚举》。在那边搞清楚「设备怎么被认出来」，回这边看「认出来之后驱动怎么接住它」。

怎么读：手里有代码、想动 probe 的，看第一、五章。结构体嵌套看晕的，看第二、三、四章。urb 提交了没反应、回调不进的，看第七、八、九章。hub 报错、TT 概念打结的，看第十章。插上去 probe 不触发，看第十一章。

一、USB 驱动的整体结构 #

内核里的 USB 代码切成三层。搞清楚哪层管什么，后面看结构体才不会串。

层 代码位置 它管什么 你不该在这一层干的事
设备驱动层 drivers/usb/ 下各具体驱动 认领接口、跑业务协议、收发数据 直接读写控制器寄存器
usbcore drivers/usb/core/ 枚举、配置、接口与驱动匹配、urb 排队、设备模型 关心 qTD 长什么样
HCD drivers/usb/host/ urb 翻译成传输描述符、DMA 映射、中断处理、根 hub 虚拟化 关心你的业务协议

数据往下走只有一条路，往回走靠中断：

text
你的驱动 --urb--> usbcore --urb--> HCD --qTD/QH--> 控制器 --包--> 设备
控制器中断 --> HCD irq handler --> 扫完成队列 --> usb_hcd_giveback_urb --> urb->complete

驱动从头到尾没碰过寄存器。你表达的意思只有一句：往哪个端点发多少字节，完了叫我。这句话的载体就是 urb，本篇后面一半篇幅都在讲它。

1.1 驱动挂在接口上，不是挂在设备上 #

struct usb_driver 和 struct usb_interface 对等。一个物理设备插上来，内核先建一个 usb_device，再按配置里的接口数目建若干 usb_interface，每个接口单独去和驱动匹配。

所以一个复合设备会同时被两个驱动认领：摄像头带麦克风的，视频接口归 uvcvideo，音频接口归 snd-usb-audio。两个驱动互不知道对方存在，共享同一个 usb_device。你在自己驱动里看到的 interface_to_usbdev(intf)，拿到的就是这个公共父对象。

另一条路是 struct usb_device_driver，它和整个 usb_device 对等，一个设备只能挂一个。usbfs、通用驱动走这条。

驱动结构 匹配对象 一个设备能有几个 典型使用者
struct usb_driver usb_interface 每个接口一个，可以有多个 绝大多数设备驱动
struct usb_device_driver usb_device 1 usbfs、通用驱动

新手常犯的错：把 usb_driver 想成「一个设备一个驱动」，然后在 probe 里遍历所有接口。不用。probe 一次就给你一个接口，其他的接口不归你。

1.2 一份最小骨架 #

先把骨架摆出来，后面所有章节都是往这个框里填。

c
#include <linux/module.h>
#include <linux/usb.h>

static const struct usb_device_id my_ids[] = {
	{ USB_DEVICE(0x1234, 0x5678) },
	{ }
};
MODULE_DEVICE_TABLE(usb, my_ids);

static int my_probe(struct usb_interface *intf, const struct usb_device_id *id)
{
	struct usb_device *udev = interface_to_usbdev(intf);
	struct usb_host_interface *alt = intf->cur_altsetting;
	int i;

	dev_info(&intf->dev, "vid=%04x pid=%04x speed=%d\n",
		 le16_to_cpu(udev->descriptor.idVendor),
		 le16_to_cpu(udev->descriptor.idProduct), udev->speed);

	for (i = 0; i < alt->desc.bNumEndpoints; i++) {
		struct usb_endpoint_descriptor *ep = &alt->endpoint[i].desc;
		dev_info(&intf->dev, "ep addr=0x%02x attr=0x%02x\n",
			 ep->bEndpointAddress, ep->bmAttributes);
	}

	usb_set_intfdata(intf, udev);
	return 0;
}

static void my_disconnect(struct usb_interface *intf)
{
	usb_set_intfdata(intf, NULL);
}

static struct usb_driver my_driver = {
	.name       = "my_usb",
	.id_table   = my_ids,
	.probe      = my_probe,
	.disconnect = my_disconnect,
};

module_usb_driver(my_driver);
MODULE_LICENSE("GPL");

id_table 决定谁来 match 你，匹配靠 vid/pid、设备类、接口类三组字段，写法在第五章展开。probe 返回 0 表示认领成功，返回负数表示放弃这个接口，放弃以后内核会去找别的驱动。disconnect 里必须停掉所有在飞的 urb，否则回调会打到已经释放的私有数据上。

module_usb_driver() 是宏，展开就是 module_init/module_exit 加 usb_register_driver() 与 usb_deregister()。老代码里这两种写法都能见到。

1.3 一次完整的生命周期 #

把时间轴摊开，一共五段。

  1. 设备插到 hub 端口上，hub 的中断端点报上来一位状态变化。
  2. hub 线程 khubd 醒来，复位端口、分配总线地址、读设备描述符、读配置描述符。这一段全在第十一章。
  3. usbcore 按配置建出 usb_interface，逐个和已注册驱动的 id_table 比对。
  4. 对上了，调你的 probe。你在 probe 里申请 urb、提交第一个控制请求、或者注册字符设备。
  5. 设备被拔掉，或者驱动被 rmmod，走 disconnect。在飞的 urb 必须已经被 usb_kill_urb() 或 usb_poison_urb() 收干净。

第 2 步和第 5 步是内核自动的，第 3、4 步跨 usbcore 与你的代码，第 4 步之后的数据收发是你自己的活。

1.4 这篇要建立的三个直觉 #

所有数据传输都走 urb。控制传输也一样。usb_control_msg() 只是帮你把「分配 urb、填 urb、提交、等完成、释放 urb」这一串包了起来，你用得多了会忘了底下有个 urb，但它一直都在。第七章会把这个封装拆开。

urb 不全是一次性的。中断端点、批量端点可以复用一个 urb，回调里重新提交，这叫 urb 复用。等时端点必须预先准备多个 urb 形成流水，一个回调里提交下一个，才不会断流。这一点决定了你的驱动是能跑还是能稳。

同步与异步只差在一个等待。usb_control_msg()、usb_bulk_msg() 是同步接口，内部一样提交 urb，只是用完成量把自己挂起，等回调唤醒。同步接口在中断上下文里不能用，因为它会睡。第八章会列出这套实现。

二、核心数据结构 #

一共八个结构体，按「谁包着谁」排一遍：

结构体 对应什么 关键成员 谁分配
struct usb_device 一个物理设备 descriptor、config、actconfig、ep0 usbcore 枚举时
struct usb_host_config 一个配置 desc、interface[] usbcore 读完配置描述符
struct usb_interface 一个接口 cur_altsetting、dev、minor usbcore 按接口数目建
struct usb_host_interface 一个设置 desc、endpoint[]、extra usbcore 解析描述符时
struct usb_host_endpoint 一个端点 desc、urb_list、hcpriv usbcore 解析描述符时
struct usb_bus 一条总线 busnum、root_hub、devmap HCD 注册时
struct usb_hub 一个 hub 实例 urb、event_bits、tt hub 驱动 probe 时
struct urb 一次传输 pipe、transfer_buffer、complete 你的驱动

内存分配的方向是自上而下的：usb_device 先建，读描述符，再按描述符里的数目建配置、接口、设置、端点。所以你在 probe 里拿到的所有下层指针，都是 usbcore 早就填好的，你只读不写。

2.1 指针网 #

text
usb_device
 ├── descriptor          ← 设备描述符（18 字节）
 ├── ep0                 ← 端点 0，内嵌的 usb_host_endpoint
 ├── config / actconfig  → usb_host_config（全部配置／当前激活）
 ├── ep_in[16] / ep_out[16] ← 端点的快速索引
 └── bus                 → usb_bus → root_hub → usb_device（环）

usb_host_config:  desc + interface[] → usb_interface + intf_cache[]
usb_interface:    cur_altsetting + altsetting + 内嵌 struct device dev
usb_host_interface:  desc + endpoint[] → usb_host_endpoint
usb_host_endpoint:   desc + urb_list + hcpriv（HCD 私有，你千万别动）

usb_interface 里嵌了一个 struct device dev，usb_device 里也嵌了一个。这是 Linux 设备模型的统一做法：USB 设备在 sysfs 里的路径，就是从这两个 device 长出来的。

2.2 配置 / 接口 / 设置 / 端点：四层 #

这是全篇最该记牢的一张表。USB 描述符的嵌套关系、驱动绑定的粒度、alternate setting 的用途，全挂在这四层上。

层级 内核结构 描述符 数量关系 绑定粒度
设备 usb_device 设备描述符 1 —
配置 usb_host_config 配置描述符 1..n，同一时刻只激活 1 个 不绑定
接口 usb_interface 接口描述符 每个配置 1..n 驱动绑在这一层
设置 usb_host_interface 接口描述符 每个接口 1..n 切换用 usb_set_interface()
端点 usb_host_endpoint 端点描述符 每个设置 0..n urb 发往这一层

一个设备有多个配置。手机就是典型：插到电脑上可以当 U 盘，也可以当摄像头，这两种用法对应两个配置，同一时刻只能选一个。切换靠标准请求 SET_CONFIGURATION，参数是配置描述符里的 bConfigurationValue。

一个配置有多个接口。接着上面的例子，当 U 盘用的时候，设备只需要启用 1 个接口（大容量存储类）；当摄像头用的时候，要启用 2 个接口（视频类加音频类）。剩下的接口在硬件上存在，但当前配置用不到，就不列进这个配置的 bNumInterfaces 里。

一个接口有多个设置。这一层最容易被忽略。设置就是 alternate setting，用来在同一套接口框架下切换带宽或数据格式。USB 摄像头调分辨率就是这个动作：每个分辨率对应一个 altsetting，不同的 altsetting 下端点数目和 wMaxPacketSize 都不一样。默认生效的永远是 0 号设置，要换别的必须显式调用 usb_set_interface(udev, ifnum, alt)。

一个设置有多个端点。端点 0 不算在里面，它在每个设备上都有，走控制传输，是设备出厂就带的默认管道。所以接口描述符里的 bNumEndpoints 不含端点 0。

四层里只有「接口」这一层参与驱动匹配。你的 probe 收到的是 usb_interface *，不是 usb_device *，也不是 usb_host_interface *。想拿当前设置，走 intf->cur_altsetting。还有一个坑：usb_host_config 里的 interface[] 数组顺序，未必等于配置里接口号的顺序，判断接口身份要看 cur_altsetting->desc.bInterfaceNumber，不要按数组下标猜。

2.3 usb_host_config 与 usb_host_interface #

c
struct usb_host_config {
	struct usb_config_descriptor	desc;
	char *string;			/* iConfiguration string, if present */
	struct usb_interface *interface[USB_MAXINTERFACES];
	struct usb_interface_cache *intf_cache[USB_MAXINTERFACES];
	u8 *extra;			/* Extra descriptors */
	int extralen;
};

struct usb_host_interface {
	struct usb_interface_descriptor	desc;
	/* array of desc.bNumEndpoint endpoints associated with this
	 * interface setting.  these will be in no particular order. */
	struct usb_host_endpoint *endpoint;
	char *string;			/* iInterface string, if present */
	unsigned char *extra;		/* Extra descriptors */
	int extralen;
};

interface[] 是配置所包含的接口数组，顺序不保证按接口号排。intf_cache[] 是接口缓存，即使这个配置当前没被激活，它的接口信息也留着，这样 lsusb -v 能列出所有配置下的接口，而不只是当前激活的那个。

extra 和 extralen 装的是额外描述符。类特定描述符（HID 的 report descriptor、音频的 class-specific 描述符）都塞在这里，原始字节流，要自己按 bDescriptorType 解析。HID 驱动 probe 时第一件事就是从 usb_host_interface.extra 把 report descriptor 捞出来。endpoint 不是数组声明，是指针，指向一块连续内存，长度是 desc.bNumEndpoints，遍历写法就是 for (i = 0; i < alt->desc.bNumEndpoints; i++)。

2.4 usb_host_endpoint 与 usb_interface_cache #

c
struct usb_host_endpoint {
	struct usb_endpoint_descriptor	desc;
	struct list_head		urb_list;
	void				*hcpriv;
	struct ep_device		*ep_dev;	/* For sysfs info */
	unsigned char *extra;	/* Extra descriptors */
	int extralen;
};

struct usb_interface_cache {
	unsigned num_altsetting;	/* number of alternate settings */
	struct kref ref;		/* reference counter */
	/* variable-length array of alternate settings for this interface,
	 * stored in no particular order */
	struct usb_host_interface altsetting[0];
};

usb_interface_cache 存在的理由只有一条：把「这个接口的所有设置」打包在一起，用引用计数管住。altsetting[0] 是柔性数组写法，实际长度是 num_altsetting。设备在运行时切换配置，旧配置的接口信息不能立刻释放，因为还有人在用，就是这个 kref 在挡着。

urb_list 是这个端点的 urb 待处理队列。每个端点维护自己的一条链，你提交的 urb 就是挂到这条链上，HCD 从这条链上取。同一个端点上你在飞的 urb 排成一队，按提交顺序走。hcpriv 是给 HCD 用的私有指针，别碰。你改了它，HCD 的内部数据结构就崩了。ep_dev 只在 sysfs 里用，给每个端点挂上 ep_XX 节点。

2.5 usb_bus 与 usb_devmap #

c
struct usb_bus {
	struct device *controller;	/* host/master side hardware */
	int busnum;			/* Bus number (in order of reg) */
	char *bus_name;			/* stable id (PCI slot_name etc) */
	u8 uses_dma;			/* Does the host controller use DMA? */
	u8 otg_port;			/* 0, or number of OTG/HNP port */
	unsigned is_b_host:1;		/* true during some HNP roleswitches */
	unsigned b_hnp_enable:1;	/* OTG: did A-Host enable HNP? */
	int devnum_next;		/* Next open device number, round-robin */
	struct usb_devmap devmap;	/* device address allocation map */
	struct usb_device *root_hub;	/* Root hub */
	struct list_head bus_list;	/* list of busses */
	int bandwidth_allocated;	/* periodic time used, us/frame.
					 * Full/low speed reserve 90%,
					 * high speed reserves 80%. */
	int bandwidth_int_reqs;		/* number of Interrupt requests */
	int bandwidth_isoc_reqs;	/* number of Isoc. requests */
	struct device *dev;		/* device for this bus */
};

struct usb_devmap {
	unsigned long devicemap[128 / (8 * sizeof(unsigned long))];
};

三条值得单独拎出来。

devnum_next 做轮转分配，总线初始化时置为 1。地址分配不是从最小可用号找起，是轮着来，避免同一个地址反复给不同设备。

devmap 是地址位图，每条总线一张，128 位。一条 usb_bus_type 类型的总线上最多 128 个设备，choose_address() 在这张位图里找空闲位，找到了就把设备的总线地址定下来。bandwidth_allocated 是带宽记账：中断传输和等时传输要预留带宽，全速/低速总线允许预留到 90%，高速总线 80%。你申请等时管道时如果超了预算，usb_submit_urb() 会返回 -ENOSPC。这个报错不是设备坏了，是带宽不够。

三、usb_device 与 usb_interface #

这两个结构是驱动里摸得最多的。usb_device 代表物理设备，usb_interface 代表设备里的一个逻辑功能，你的 probe 收到的就是后者。

3.1 usb_device #

c

逐组过。

成员 讲什么 要知道的
devnum 总线上的编号 枚举时主机分配，一条总线上限 128 个设备。跟固件里的序列号无关
devpath[16] 树里的位置 形如 /port/port/...，根 hub 的 devpath[0] 是字符 '0'
state 设备状态 六种取值，见下表
speed 速度 枚举时由 hub_port_wait_reset() 按端口状态字填，第十一章讲
tt / ttport TT 归属 只有挂在高速 hub 后面的低速/全速设备才有值
toggle[2] DATA0/DATA1 翻转位 [0] 管 IN，[1] 管 OUT，一位一个端点。内核维护，驱动别碰
parent / children[] 树的边 parent 指父 hub，根 hub 为空；maxchild 是端口数
bus 所属总线 usb_bus.root_hub 又指回树根，构成一个环
ep0 端点 0 内嵌结构体不是指针，设备一创建就得初始化好
descriptor 设备描述符 内嵌，bMaxPacketSize0 存端点 0 最大包长
config / actconfig 配置 前者全部配置，后者当前激活的
ep_in[16] / ep_out[16] 端点索引 端点号 0..15，所以开 16 项
rawdescriptors 原始字节流 lsusb -v 的输出从这儿拼出来
bus_mA 总线能给的电流 HCD 设置，一般 500mA。需求方在 bMaxPower
portnum / level 端口号与层级 根 hub 的 level 是 0，往下依次加一
product / manufacturer / serial 字符串 读之前先确定语言 ID（have_langid、string_langid）
quirks 怪设备补丁位 遇到怪设备先翻 unusual_devs.h 有没有现成条目
autosuspend_delay 等 自动挂起 延迟多久没活动就睡，last_busy 记最后一次活动
filelist / usbfs_dentry usbfs 用户态直接发请求（libusb 那条路）走这里

state 的六种取值是理解枚举进度的标尺：

状态 含义 此时能用什么
USB_STATE_NOTATTACHED 没接上 什么都不行
USB_STATE_ATTACHED hub 已检测到插入，还没有地址 只有默认地址 0
USB_STATE_POWERED 端口已上电 同上
USB_STATE_DEFAULT 复位完成，处于默认态 默认控制管道，地址 0
USB_STATE_ADDRESS 主机已分配唯一地址 可用默认管道响应请求
USB_STATE_CONFIGURED 收到非 0 值的 SET_CONFIGURATION 设备所有功能可用
USB_STATE_SUSPENDED 挂起，省电 设备自己维护地址与配置信息

挂起这一条多说一句。总线 3ms 没有传输活动，设备就进挂起态。挂起期间设备必须自己保住地址和配置。恢复时主机不会重新枚举，直接接着用。toggle 这一位丢了会导致重传或者数据错乱，它是硬件握手的一部分。quirks 是给那些不守规矩设备打的补丁开关：某个型号的 U 盘复位后包长报错、某个摄像头控制传输超时，都在这里挂一个位，代码里按位判断绕过去。

3.2 usb_interface #

c
struct usb_interface {
	/* array of alternate settings for this interface,
	 * stored in no particular order */
	struct usb_host_interface *altsetting;

	struct usb_host_interface *cur_altsetting;	/* the currently
					 * active alternate setting */
	unsigned num_altsetting;	/* number of alternate settings */

	int minor;			/* minor number this interface is
					 * bound to */
	enum usb_interface_condition condition;		/* state of binding */
	unsigned is_active:1;		/* the interface is not suspended */
	unsigned needs_remote_wakeup:1;	/* driver requires remote wakeup */

	struct device dev;		/* interface specific device info */
	struct device *usb_dev;		/* pointer to the usb class's device */
	int pm_usage_cnt;		/* usage counter for autosuspend */
};

cur_altsetting 是驱动里用得最多的成员。当前生效的设置是哪个，端点表就在它下面。你 probe 里所有端点遍历都从它开始。altsetting 是全部设置的数组，num_altsetting 是长度。要切到别的设置，调 usb_set_interface()，它会把 cur_altsetting 换成新的那个，同时按新设置的端点重新配置管道。minor 是这个接口绑定的次设备号。如果你的驱动注册字符设备，usbfs 会分一个次设备号，记在这儿。

condition 是绑定状态，四种取值：

取值 含义
USB_INTERFACE_UNBOUND 没有驱动认领
USB_INTERFACE_BINDING 正在 probe
USB_INTERFACE_BOUND 已绑定
USB_INTERFACE_UNBINDING 正在断开

is_active 表示接口没被挂起。needs_remote_wakeup 表示这个驱动要求设备能远程唤醒。dev 是内嵌的设备模型对象，sysfs 里 /sys/bus/usb/drivers/<driver>/<busnum>-<port>:<config>.<interface> 这一层就是它。usb_dev 是 usb 类的设备指针，主要给 usbfs 用。

3.3 从接口拿设备 #

驱动里最常写的一句：

c
struct usb_device *udev = interface_to_usbdev(intf);

这个宏实际做的是 container_of(intf->dev.parent, struct usb_device, dev)：从接口的设备对象往上找父设备对象，再反推出 usb_device。

私有数据用 usb_set_intfdata() / usb_get_intfdata()：

c
usb_set_intfdata(intf, my_priv);		/* probe 里存 */
struct my_priv *p = usb_get_intfdata(intf);	/* 别处取 */

别自己往 intf 上挂全局变量。一个设备可以有多个接口，多个同型号设备可以同时在系统里，全局变量撑不住。

四、描述符在代码里的表示 #

描述符是设备跟主机自我介绍的格式。协议层面怎么排布，那篇讲协议的说全了。这里只说内核里怎么把那段字节流变成结构体。

4.1 设备描述符 #

c
struct usb_device_descriptor {
	__u8	bLength;		__u8	bDescriptorType;
	__le16	bcdUSB;			__u8	bDeviceClass;
	__u8	bDeviceSubClass;	__u8	bDeviceProtocol;
	__u8	bMaxPacketSize0;	__le16	idVendor;
	__le16	idProduct;		__le16	bcdDevice;
	__u8	iManufacturer;		__u8	iProduct;
	__u8	iSerialNumber;		__u8	bNumConfigurations;
} __attribute__ ((packed));

bcdUSB 是协议版本号。能跑高速的设备，这一项是 0200H。

bDeviceClass、bDeviceSubClass、bDeviceProtocol 是类信息。这里有个容易踩的地方：bDeviceClass 为 0 时，类信息在各接口描述符里，不能拿设备级的这三个字段判断设备类型。绝大多数复合设备都这么干。三者还有第三种用法在 hub 上：bDeviceProtocol 决定 TT 的类型。全速/低速 hub 的这个值是 0；高速 hub 的值是 1 表示 single TT，是 2 表示 multiple TT。第十章会用到。

bMaxPacketSize0 是端点 0 的最大包长。为什么放在设备描述符而不是端点描述符？因为端点 0 没有自己的描述符。这个值只能是 8、16、32、64 四者之一，而且高速设备只能是 64，低速设备只能是 8。255 这个值在处理代码里也出现过，那是给某些不规矩设备留的容错分支。

bNumConfigurations 是当前速度模式下的配置数量。有的设备在不同速度下能提供的配置数不一样，这个字段只算当前速度那一种。idVendor / idProduct 是驱动匹配的钥匙，多数情况用 USB_DEVICE(vid, pid) 宏。bcdDevice 是设备版本号，要区分同一个 pid 的不同批次就靠它。

4.2 配置描述符 #

c
struct usb_config_descriptor {
	__u8	bLength;		__u8	bDescriptorType;
	__le16	wTotalLength;		__u8	bNumInterfaces;
	__u8	bConfigurationValue;	__u8	iConfiguration;
	__u8	bmAttributes;		__u8	bMaxPower;
} __attribute__ ((packed));

struct usb_interface_descriptor {
	__u8	bLength;		__u8	bDescriptorType;
	__u8	bInterfaceNumber;	__u8	bAlternateSetting;
	__u8	bNumEndpoints;		__u8	bInterfaceClass;
	__u8	bInterfaceSubClass;	__u8	bInterfaceProtocol;
	__u8	iInterface;
} __attribute__ ((packed));

struct usb_endpoint_descriptor {
	__u8	bLength;		__u8	bDescriptorType;
	__u8	bEndpointAddress;	__u8	bmAttributes;
	__le16	wMaxPacketSize;		__u8	bInterval;
	__u8	bRefresh;		__u8	bSynchAddress;
} __attribute__ ((packed));

bDescriptorType 不只可以是 USB_DT_CONFIG，还能是 USB_DT_OTHER_SPEED_CONFIG。后者表示这是另一速度下的配置，参数一样但数值不同。

wTotalLength 是整个配置的总长度，包括配置描述符本身加上后面跟着的所有接口描述符、端点描述符、类特定描述符。用 GET_DESCRIPTOR 请求读配置时，返回的数据长度就是这个值。先读 9 字节拿 wTotalLength，再按它读全，是标准做法。bNumInterfaces 是这个配置包含的接口数量。

bConfigurationValue 是切换配置时的参数。设备可以有多个配置，同一时间只有一个激活，用 SET_CONFIGURATION 请求加这个值切。切之前要确保旧配置上的接口都没人在用。bmAttributes 表征配置特点：bit 6 为 1 表示自供电，bit 5 为 1 表示支持远程唤醒，bit 7 必须为 1。

bMaxPower 是设备正常工作要从总线拿的最大电流，单位 2mA。设备靠这个字段向 hub 申报需求，要得太多超过 hub 能给的上限，hub 直接拒绝。usb_device 里的 bus_mA 是供给方，这里是需求方。

4.3 接口描述符 #

bInterfaceNumber 是接口号，每个配置里多个接口靠它索引。bAlternateSetting 是设置号，协议规定接口默认用 0 号设置，一个接口的多个设置就是靠这个字段区分。

bNumEndpoints 是接口拥有的端点数，不含端点 0。端点 0 是控制传输，所有设备都有，没必要重复计入。hub 做例证：它的传输是中断传输，所以这个值是 1。

bInterfaceClass / bInterfaceSubClass / bInterfaceProtocol 是接口级的类信息。复合设备靠这三个字段区分每个接口的功能。HID 的 bInterfaceClass 是 3，大容量存储是 8，CDC 是 0x0A。匹配驱动时用 USB_INTERFACE_INFO() 宏按这三项比对。hub 的 bInterfaceSubClass 是 0，bInterfaceProtocol 是 0（全速）或 1（高速 single TT）。

4.4 端点描述符 #

bEndpointAddress 的 bits 0~3 是端点号（掩码 USB_ENDPOINT_NUMBER_MASK），bit 7 是方向（掩码 USB_ENDPOINT_DIR_MASK，1 为 IN）。拿端点信息用 usb_endpoint_num()、usb_endpoint_dir_in()、usb_endpoint_type() 这几个辅助函数，比自己移位清楚。

bmAttributes 的 bit1 和 bit0 合起来是传输类型（掩码 USB_ENDPOINT_XFERTYPE_MASK）：

bit1:bit0 传输类型 常量 典型用途
00 控制 USB_ENDPOINT_XFER_CONTROL 枚举、类请求
01 等时 USB_ENDPOINT_XFER_ISOC 音频、视频流
10 批量 USB_ENDPOINT_XFER_BULK U 盘、打印机
11 中断 USB_ENDPOINT_XFER_INT 键鼠、hub 状态回报

等时端点还用 bit3:bit2 表示同步类型（无同步、异步、自适应、同步），用 bit5:bit4 表示用途（数据、反馈、隐式反馈）。

wMaxPacketSize 是端点一次能处理的最大字节数。你发的数据超过这个值，协议层会自动拆成多次传输。高速设备的高带宽等时端点，这里还编码了每微帧的额外事务数。

bInterval 是轮询间隔。USB 是轮询式总线，这个值表示端点希望主机多久来问一次。批量和控制端点忽略这个字段。单位随速度变：低速/全速中断端点按毫秒算，高速中断端点按 2 的幂次微帧算，等时端点按 2 的幂次算。bRefresh 和 bSynchAddress 只在音频端点里有意义，其他端点这两个字段不用看。

端点 0 没有自己的端点描述符，这是协议里的特例。它的所有特性在 spec 里定死了，唯一需要协商的 max packet size 放在设备描述符的 bMaxPacketSize0 里。

4.5 hub 描述符与 hub 结构体 #

hub 设备有类特定描述符，结构是这样：

c
struct usb_hub_descriptor {
	__u8	bDescLength;
	__u8	bDescriptorType;
	__u8	bNbrPorts;
	__le16	wHubCharacteristics;
	__u8	bPwrOn2PwrGood;
	__u8	bHubContrCurrent;
	__u8	DeviceRemovable[(USB_MAXCHILDREN + 1 + 7) / 8];
	__u8	PortPwrCtrlMask[(USB_MAXCHILDREN + 1 + 7) / 8];
} __attribute__ ((packed));

bNbrPorts 是下行端口数，不能大于 31，这个上限直接决定了 usb_hub 里那些位图的长度。wHubCharacteristics 记录一堆位域特性：是不是复合设备、有没有过流保护、电源切换方式、TT 的思考时间等。bPwrOn2PwrGood 是从加电到端口供电稳定所需的时间，单位 2ms。bHubContrCurrent 是 hub 控制器自身的最大电流需求，单位 mA。

DeviceRemovable 每个 bit 对应一个端口，0 表示该端口设备可移除，1 表示不可移除，用来区分内置设备和外插设备。PortPwrCtrlMask 是端口电源控制掩码。

usb_hub 结构体是 hub 驱动自己的运行时状态：

c
struct usb_hub {
	struct device		*intfdev;	/* the "interface" device */
	struct usb_device	*hdev;
	struct kref		kref;
	struct urb		*urb;		/* for interrupt polling pipe */

	/* buffer for urb ... with extra space in case of babble */
	char			(*buffer)[8];
	dma_addr_t		buffer_dma;	/* DMA address for buffer */
	union {
		struct usb_hub_status	hub;
		struct usb_port_status	port;
	}			*status;	/* buffer for status reports */
	struct mutex		status_mutex;	/* for the status buffer */

	int			error;		/* last reported error */
	int			nerrors;	/* track consecutive errors */
	struct list_head	event_list;	/* hubs w/data or errs ready */
	unsigned long		event_bits[1];	/* status change bitmask */
	unsigned long		change_bits[1];	/* ports with logical connect
						   status change */
	unsigned long		busy_bits[1];	/* ports being reset or resumed */

	struct usb_hub_descriptor *descriptor;	/* class descriptor */
	struct usb_tt		tt;		/* Transaction Translator */

	unsigned		mA_per_port;	/* current available for each port */
	unsigned		limited_power:1;
	unsigned		quiescing:1;
	unsigned		activating:1;
	unsigned		disconnected:1;
	unsigned		has_indicators:1;
	u8			indicator[USB_MAXCHILDREN];
	struct delayed_work	leds;
};

struct usb_hub 结构体的几个位域值得单独看一眼。urb 是那个常驻的中断管道 urb，用来轮询端口状态变化。它只分配一次，回调里重新提交，一直转。buffer 和 buffer_dma 是它的传输缓冲区，(*buffer)[8] 表示每个端口 8 字节，够放 hub 状态和端口状态，多留一点空间是为了防 babble（设备发超了）。status 是状态上报的缓冲区，status_mutex 保护它。

event_bits 是状态变化位掩码，change_bits 是逻辑连接状态有变化的端口，busy_bits 是正在复位或恢复的端口。busy_bits 那个标志只在复位和恢复函数内部设置，测它的相应位就能知道某个端口是不是正在忙。mA_per_port 是给每个端口的电流额度，一般 500mA。但如果 hub 本身供不上，或者上游主机控制器供不上，这个值会低于 500mA。limited_power 为 1 表示额度被上游卡住了。

quiescing 是「停」的意思，复位和挂起时置 1。一旦置 1，hub 驱动就不再提交任何 urb。activating 为 1 表示 hub 驱动要给每个端口发一次 Get Port Status 请求。正常流程里只有某个端口状态变了才去查，activating 是强制全查一遍。正常情况下 quiescing 和 activating 都该是 0。

五、usb_driver 与 probe/disconnect #

usb_driver 是你要写的那个结构。它的三个回调把驱动的生命周期钉死了：匹配上就 probe，设备走就 disconnect，不匹配还能给个预处理机会。

5.1 完整结构 #

c
struct usb_driver {
	const char *name;

	int (*probe) (struct usb_interface *intf,
		      const struct usb_device_id *id);
	void (*disconnect) (struct usb_interface *intf);

	int (*ioctl) (struct usb_interface *intf, unsigned int code, void *buf);

	int (*suspend) (struct usb_interface *intf, pm_message_t message);
	int (*resume) (struct usb_interface *intf);
	int (*reset_resume)(struct usb_interface *intf);
	int (*pre_reset)(struct usb_interface *intf);
	int (*post_reset)(struct usb_interface *intf);

	const struct usb_device_id *id_table;

	struct usb_dynids dynids;
	struct usbdrv_wrap drvwrap;
	unsigned int no_dynamic_id:1;
	unsigned int supports_autosuspend:1;
	unsigned int soft_unbind:1;
};

name 出现在 sysfs 的驱动目录名和日志里，起个能搜到的名字。id_table 匹配表，设成 NULL 且 probe 也不设，那就只当个占位，让设备保持无主状态（usbfs 用得上）。ioctl 是给 usbfs 留的钩子，一般不用。

电源管理三个：suspend、resume、reset_resume。reset_resume 在复位后恢复时调用，比 resume 多做一层重配。复位前后钩子两个：pre_reset、post_reset。设备被 usb_reset_device() 复位时会先调 pre_reset 让你把在飞的 urb 收干净，复位完再调 post_reset 让你重新配置。

supports_autosuspend 置 1 表示你的驱动支持自动挂起，置了以后设备空闲一段时间会自动睡，你的 suspend/resume 必须能正确响应。soft_unbind 置 1 表示解绑时你的驱动自己负责停 urb，别让 usbcore 替你停。no_dynamic_id 置 1 表示禁止运行时通过 sysfs 的 new_id 添加新的设备 ID，生产驱动关掉更稳妥。

5.2 id_table 怎么写 #

匹配表是一串 usb_device_id，以全零项结尾：

c
static const struct usb_device_id my_ids[] = {
	{ USB_DEVICE(0x1234, 0x5678) },			/* vid/pid 精确匹配 */
	{ USB_DEVICE_VER(0x1234, 0x5678, 0x0100, 0x01ff) },	/* 版本号范围 */
	{ USB_DEVICE_INFO(0xe0, 0x01, 0x01) },		/* 按设备类 */
	{ USB_INTERFACE_INFO(USB_CLASS_HID, 0, 0) },	/* 按接口类，复合设备用 */
	{ .match_flags = USB_DEVICE_ID_MATCH_INT_CLASS,
	  .bInterfaceClass = 0x08 },			/* 手工控制匹配位 */
	{ }						/* 终止项 */
};
MODULE_DEVICE_TABLE(usb, my_ids);
宏 匹配依据 用在什么设备上
USB_DEVICE vid + pid 单一功能设备
USB_DEVICE_VER vid + pid + 版本号范围 需要区分硬件的同 pid 型号
USB_DEVICE_INFO 设备类/子类/协议 类设备
USB_INTERFACE_INFO 接口类/子类/协议 复合设备

USB_INTERFACE_INFO 的三项参数是 bInterfaceClass、bInterfaceSubClass、bInterfaceProtocol。要匹配任何子类或协议，用 USB_CLASS_* 配合通配写法，或用 match_flags 手工控制哪几项参与比对，后者更容易加注释说明为什么这么匹配。

MODULE_DEVICE_TABLE(usb, my_ids) 这句一定要写。它把匹配表导出到模块信息里，depmod 才能生成别名，udev 才能在设备插入时按需 modprobe。漏了这行，热插拔时模块不会自动加载，你只能手动 insmod。

5.3 probe 里做什么 #

顺序很重要。写乱了，出错处理的路径就会漏资源。

c
static int my_probe(struct usb_interface *intf, const struct usb_device_id *id)
{
	struct usb_device *udev = interface_to_usbdev(intf);
	struct usb_host_interface *alt;
	struct my_priv *priv;
	int ret;

	/* 1. 判断这个接口能不能干 */
	alt = usb_altnum_to_altsetting(intf, 0);
	if (!alt || alt->desc.bNumEndpoints < 1)
		return -ENODEV;

	/* 2. 分配私有数据 */
	priv = kzalloc(sizeof(*priv), GFP_KERNEL);
	if (!priv)
		return -ENOMEM;

	/* 3. 存端点信息，端点地址直接抄下来，别每次重算 */
	priv->in_ep = &alt->endpoint[0].desc;
	priv->maxp = usb_maxpacket(udev, usb_rcvbulkpipe(udev, 1), 0);

	/* 4. 分配 urb */
	priv->urb = usb_alloc_urb(0, GFP_KERNEL);
	if (!priv->urb) {
		ret = -ENOMEM;
		goto err_free;
	}

	/* 5. 申请传输缓冲区 */
	priv->buf = usb_alloc_coherent(udev, priv->maxp, GFP_KERNEL, &priv->dma);
	if (!priv->buf) {
		ret = -ENOMEM;
		goto err_urb;
	}

	/* 6. 挂到 intf 上，disconnect 才找得到 */
	usb_set_intfdata(intf, priv);

	/* 7. 必要的设备初始化 */
	ret = my_init_device(udev);
	if (ret)
		goto err_data;

	return 0;

err_data:
	usb_free_coherent(udev, priv->maxp, priv->buf, priv->dma);
err_urb:
	usb_free_urb(priv->urb);
err_free:
	kfree(priv);
	return ret;
}

第 1 步别省。设备实际的端点表跟你写在代码里的假设不一定对，先确认再干活，失败就干净退出。第 3 步有个细节：usb_rcvbulkpipe(udev, 1) 里的 1 是端点号，不是地址。管道编码里会把方向位补上，你别自己拼 0x81。第 6 步必须早于任何能触发异步操作的调用，urb 的回调里要靠 usb_get_intfdata() 找回私有数据，挂晚了就是空指针。

probe 里能睡。它在进程上下文跑，kmalloc(GFP_KERNEL)、usb_control_msg() 都能用。这一点跟中断上下文里的代码不同，别搞混。

5.4 disconnect 里做什么 #

disconnect 的核心只有一句：先把在飞的 urb 全收干净，再释放资源。

c
static void my_disconnect(struct usb_interface *intf)
{
	struct my_priv *priv = usb_get_intfdata(intf);

	usb_set_intfdata(intf, NULL);
	if (!priv)
		return;

	/* 1. 停掉所有还在飞的 urb，并等它们出来 */
	usb_kill_urb(priv->urb);

	/* 2. 释放缓冲区 */
	usb_free_coherent(interface_to_usbdev(intf), priv->maxp,
			  priv->buf, priv->dma);

	/* 3. 放 urb */
	usb_free_urb(priv->urb);

	/* 4. 放私有数据 */
	kfree(priv);
}

usb_kill_urb() 会同步等待 urb 的回调执行完才返回。这是它和无条件取消的区别，也是唯一能保证安全的行为。先 usb_set_intfdata(intf, NULL) 再干活，是为了防止并发路径上还有人在取私有数据。如果驱动里用了定时器或者 workqueue，在 1 之前要先把它们停掉，用 del_timer_sync() / cancel_work_sync()。定时器里提交 urb 的写法最容易漏，一漏就是 use-after-free。

5.5 复位与挂起 #

设备被复位时，usbcore 会走一遍这个顺序：

text
usb_reset_device()
  -> pre_reset(intf)        你可以在这里停掉在飞的 urb
  -> 实际复位
  -> post_reset(intf)       重新配置接口、重新提交 urb
  -> reset_resume(intf)     或者走 resume 路径

pre_reset 里只做一件事：usb_kill_urb() 把所有 urb 停下来。USB 规范规定复位后设备的所有状态清空，urb 提交上去必然失败。post_reset 里把设备重新配一遍：重设接口设置、重设类特定参数、重新提交 urb。

自动挂起要配合 supports_autosuspend 和 pm_usage_cnt。简单的做法是在空闲时调 usb_autopm_put_interface(intf)，活跃时调 usb_autopm_get_interface(intf)。这两个函数是成对的计数器，漏掉一个就是永不休眠或者随机休眠。

六、设备号与 dev_t #

内核里每个能打开的字符设备都有个设备号，USB 驱动注册字符设备时绕不开这块。

6.1 主次设备号各管什么 #

主设备号标明设备种类，也决定了打开这个设备时走哪个驱动。次设备号是因为一个驱动要支持多个设备才有的，给驱动自己用来区分具体操作哪个。

一句话分工：主设备号帮你找到驱动，次设备号给驱动用来决定操作哪个设备。

例如 U 盘驱动的主设备号固定，系统里插了两个 U 盘，两个盘共用同一个主设备号，靠次设备号区分 /dev/sda 和 /dev/sdb。

6.2 分配方式与设备节点 #

两条路。第一条，静态指定，编译期写死一个主设备号，风险是跟别人撞。第二条，动态分配，让内核给你挑一个空闲的，这是推荐做法。

c
/* 静态：写死主设备号 */
#define MY_MAJOR 240
ret = register_chrdev_region(MKDEV(MY_MAJOR, 0), MY_COUNT, "my_usb");

/* 动态：让内核挑，再拆回来 */
dev_t devt;
int ret = alloc_chrdev_region(&devt, 0, MY_COUNT, "my_usb");
int major = MAJOR(devt);
int minor = MINOR(devt);
unregister_chrdev_region(devt, MY_COUNT);	/* 释放 */

MKDEV(major, minor) 拼成一个 dev_t，MAJOR() 和 MINOR() 拆回来。dev_t 是 32 位，主设备号 12 位，次设备号 20 位。次设备号能到 1048576，够用。

usb_interface 里的 minor 字段是 usbfs 分配的次设备号。如果你的驱动跑在 usbfs 之上，用它就行。走字符设备这条路，流程是这样：

c
/* 1. 申请设备号区域 */
alloc_chrdev_region(&devt, 0, count, "my_usb");

/* 2. 初始化 cdev 并绑定 file_operations */
cdev_init(&priv->cdev, &my_fops);
priv->cdev.owner = THIS_MODULE;
cdev_add(&priv->cdev, devt, count);

/* 3. 创建设备节点 */
device_create(my_class, NULL, devt, NULL, "my_usb%d", index);

第 3 步的 device_create 让 udev 自动在 /dev 下建节点，不用手工 mknod。模块卸载时对应 device_destroy、cdev_del、unregister_chrdev_region，三样都要清。

一个容易忽略的点：多个同型号设备在系统里时，设备号要按实例分配，不能每个 probe 都申请同一段。把 index 做成全局递增计数器，配一个锁。

6.3 从 sysfs 看设备号 #

不写代码也能查，/sys/class/my_usb/my_usb0/dev 里面是 major:minor，/sys/bus/usb/devices/1-1:1.0/ 是接口的 sysfs 目录。USB 设备的 sysfs 路径有固定格式：<busnum>-<portpath>:<config>.<interface>。1-1:1.0 表示 1 号总线上、路径为 1 的设备、配置 1、接口 0。调试匹配问题时这个路径比设备名有用得多。

七、urb：USB 传输的载体 #

前面六章都在铺路。这一章开始讲主角。

urb 是 USB Request Block 的缩写。它是 USB 驱动收发数据的基本单位，一个 urb 封装了一句话：往哪个端点、传什么数据、传多少、完了回调哪个函数。一次 urb 提交对应一次 USB 传输。驱动要自己分配它、填充它、提交它、在回调里回收它。

这四步是你写 USB 驱动时重复最多的动作。封装好的同步接口（usb_control_msg()、usb_bulk_msg()）也是在做这四步，只是不让你看见。

7.1 结构体 #

c

	/* private: usb core and host controller only fields in the urb */
	struct kref kref;		/* reference count of the URB */
	void *hcpriv;			/* private data for host controller */
	atomic_t use_count;		/* concurrent submissions counter */
	atomic_t reject;		/* submissions will fail */
	int unlinked;			/* unlink error code */

	struct list_head anchor_list;	/* the URB may be anchored */
	struct usb_anchor *anchor;
	struct usb_device *dev;		/* (in) pointer to associated device */
	struct usb_host_endpoint *ep;	/* (internal) pointer to endpoint */
	unsigned int pipe;		/* (in) pipe information */
	unsigned int stream_id;		/* (in) stream ID */
	int status;			/* (return) non-ISO status */
	unsigned int transfer_flags;	/* (in) URB_SHORT_NOT_OK | ...*/
	void *transfer_buffer;		/* (in) associated data buffer */
	dma_addr_t transfer_dma;	/* (in) dma addr for transfer_buffer */
	struct scatterlist *sg;		/* (in) scatter gather buffer list */
	int num_mapped_sgs;		/* (internal) mapped sg entries */
	int num_sgs;			/* (in) number of entries in the sg list */
	u32 transfer_buffer_length;	/* (in) data buffer length */
	u32 actual_length;		/* (return) actual transfer length */

	dma_addr_t setup_dma;		/* (in) dma addr for setup_packet */

分三组看，注释里的 (in) 是「你提交前填」，(return) 是「回调里读」。

分组 成员 用法
你填的 dev、pipe、transfer_buffer、transfer_buffer_length、complete、context、interval、transfer_flags 提交前必须就位
内核填的 ep（从 pipe 解析）、hcpriv、kref 你别动
回调里读的 status（0 成功，负数错误）、actual_length（实际传了多少） 判断结果用

iso_frame_desc[0] 是柔性数组，只有等时传输用。number_of_packets 表示这帧里有几个包，每个包的状态记在 iso_frame_desc[i].status 里。

7.2 pipe：一个整数编码五件事 #

pipe 不是文件描述符，是个位域打包的整数。内核给了一组宏拼装和拆解。

拼装 作用 拆解 取出什么
usb_sndctrlpipe(dev, ep) 控制 OUT usb_pipeendpoint(pipe) 端点号
usb_rcvctrlpipe(dev, ep) 控制 IN usb_pipedevice(pipe) 设备地址
usb_sndbulkpipe(dev, ep) 批量 OUT usb_pipein(pipe) 方向，非 0 为 IN
usb_rcvbulkpipe(dev, ep) 批量 IN usb_pipetype(pipe) 传输类型
usb_sndintpipe(dev, ep) 中断 OUT usb_pipebulk(pipe) 是否批量管道
usb_rcvintpipe(dev, ep) 中断 IN
usb_sndisocpipe(dev, ep) 等时 OUT
usb_rcvisocpipe(dev, ep) 等时 IN

注意管道宏的第二个参数是端点号（0~15），不是端点地址。你从描述符里读到 bEndpointAddress 是 0x81，端点号是 1，方向是 IN，对应 usb_rcvbulkpipe(udev, 1)。直接把 0x81 传进去是错的。

7.3 urb 生命周期 #

阶段 调用 谁做 失败怎么办
分配 usb_alloc_urb(iso_packets, mem_flags) 你 返回 NULL，退 -ENOMEM
填充 usb_fill_*_urb() 你 无返回值，填错就是运行时故障
提交 usb_submit_urb(urb, mem_flags) 你 返回负数，按错误码处理
传输 HCD 执行 内核 出错记在 urb->status
完成 urb->complete() 内核调你 读 status 分情况处理
回收 usb_free_urb(urb) 你 无返回值

iso_packets 参数只有等时传输要填非 0，其他传输填 0。

一条铁律：一个 urb 在飞的时候不能碰它的字段。usb_submit_urb() 返回 0 之后，这个 urb 归属 HCD，你只能等回调。想改什么，等回调里改完再重新提交。

另一条：usb_free_urb() 可以在提交后立刻调。它只是减引用计数，不会真的释放。真正的释放在回调执行完、最后一次引用放掉之后。所以常见写法是 usb_submit_urb() 紧跟 usb_free_urb()，看起来危险其实安全。但如果你打算复用这个 urb，就别急着 free。

7.4 填充：四个 fill 函数与等时手工填 #

7.5 transfer_flags 常用位 #

标志 作用
URB_SHORT_NOT_OK IN 传输收到短包时视为错误
URB_ISO_ASAP 等时传输自动选起始帧
URB_NO_TRANSFER_DMA_MAP 缓冲区已经 DMA 映射好了，用 transfer_dma
URB_ZERO_PACKET 批量 OUT 在整数倍包长时补一个零长包
URB_NO_INTERRUPT 不要完成中断，靠轮询收结果

URB_SHORT_NOT_OK 值得单独说。IN 传输时设备返回的字节数少于请求长度，默认算成功（actual_length 会小于 transfer_buffer_length）。如果你的协议要求必须收满，就设这个标志，否则短包会被静默接受，上层解析出错。URB_ZERO_PACKET 是很多 U 盘驱动的固定项：设备在等齐一个完整包才算一次传输结束，你的数据刚好是 512 的整数倍时，不补零长包设备就一直等下去，表现为传输卡住。URB_NO_TRANSFER_DMA_MAP 配合 DMA API 用：你自己调 dma_map_single()，把地址写进 transfer_dma，再设这个标志，usbcore 就不重复映射了。

7.6 三条分配路径 #

全手工。最大控制权，适合中断端点和批量端点。

c
urb = usb_alloc_urb(0, GFP_KERNEL);
if (!urb)
	return -ENOMEM;
usb_fill_int_urb(urb, udev, usb_rcvintpipe(udev, ep_num),
		 buf, len, my_complete, priv, ep_desc->bInterval);
usb_submit_urb(urb, GFP_KERNEL);

同步接口。省事，但不能在中断上下文用。

c
ret = usb_control_msg(udev, usb_rcvctrlpipe(udev, 0),
		      USB_REQ_GET_DESCRIPTOR, USB_DIR_IN,
		      (USB_DT_DEVICE << 8), 0,
		      buf, len, USB_CTRL_GET_TIMEOUT);

ret = usb_bulk_msg(udev, usb_sndbulkpipe(udev, ep_num),
		   buf, len, &actual, 5000);

这两个函数内部走的是「分配 urb → 填充 → 提交 → 等完成 → 释放」全套。它们返回负数是错误码，非负数是实际传输字节数。

DMA 一致缓冲区。要求 DMA 的场合用这个。

c
buf = usb_alloc_coherent(udev, size, GFP_KERNEL, &dma);
usb_fill_bulk_urb(urb, udev, usb_rcvbulkpipe(udev, ep),
		  buf, size, my_complete, priv);
urb->transfer_dma = dma;
urb->transfer_flags |= URB_NO_TRANSFER_DMA_MAP;

usb_alloc_coherent() 保证缓冲区和 DMA 地址一致，适合反复提交的 urb。配套释放用 usb_free_coherent()。

八、urb 的发送流程 #

从你调 usb_submit_urb() 到数据真正上了线，中间过了四层。

text
usb_submit_urb()
  -> usb_hcd_submit_urb()
       -> is_root_hub(urb->dev) ?
            是: rh_urb_enqueue(hcd, urb)
            否: hcd->driver->urb_enqueue(hcd, urb, mem_flags)
                  -> 以 EHCI 为例 ehci_urb_enqueue()
                       -> qh_urb_transaction()    urb → qTD 链
                       -> submit_async()          qTD 链 → QH → 调度表
层 函数 干什么
usbcore usb_submit_urb 校验、引用计数、锚点、统计
usbcore usb_hcd_submit_urb 判断根 hub 还是真实设备、DMA 映射
HCD urb_enqueue urb 转传输描述符、排调度表
控制器 硬件 按调度表把包发出去

8.1 usb_submit_urb 做了什么 #

它不是一个简单的转发。进来以后按顺序做这些：

  1. 检查 urb->dev 和 urb->ep 是否合法，设备是否处于 USB_STATE_CONFIGURED。
  2. 检查 urb->status 是否已被设为 -EINPROGRESS，防止重复提交。
  3. 增加 use_count，防止并发提交同一个 urb。
  4. 按管道的传输类型校验参数：等时要有 number_of_packets，控制要有 setup_packet，批量长度不能超端点最大包长的倍数。
  5. 处理 anchor：如果 urb 已经挂在一个锚点上，把它从锚点里摘出来。
  6. 调 usb_hcd_submit_urb()；失败时回滚计数，成功则返回 0。

返回负数的常见原因：

错误码 含义 排查方向
-ENODEV 设备已经断开 检查 udev->state
-ENOENT 端点无效 检查 pipe 的端点号
-EPIPE 端点被 stall 需要 usb_clear_halt()
-ENOMEM 内存不够 检查 mem_flags
-EINVAL 参数不合法 检查长度、interval、setup_packet
-ENOSPC 带宽不足 等时/中断带宽预留满了
-EACCES 接口被挂起 先 usb_autopm_get_interface()
-EXDEV 锚点被 poison 了 检查 usb_poison_urb 的调用

-EPIPE 是串口调试时最常见的。设备端点上一次传输出了错，端点自动进入 halt 状态，后续所有 urb 都返回 -EPIPE。恢复办法是调 usb_clear_halt() 清掉 halt 位。

8.2 usb_hcd_submit_urb 的分叉 #

这一段是理解根 hub 特殊性的关键。

c
if (is_root_hub(urb->dev))
	status = rh_urb_enqueue(hcd, urb);
else
	status = hcd->driver->urb_enqueue(hcd, urb, mem_flags);

is_root_hub() 判断 urb->dev == hcd->self.root_hub。是根 hub，走 rh_urb_enqueue()；是真实设备，走 HCD 自己的 urb_enqueue。以 UHCI 为例走 uhci_urb_enqueue()，以 EHCI 为例走 ehci_urb_enqueue()。

这段代码还有个顺序上的细节：usb_hcd_submit_urb() 在调 urb_enqueue 之前会做 DMA 映射。映射的目标是 urb->transfer_buffer，把虚拟地址换成设备能访问的总线地址，写进 urb->transfer_dma。

8.3 ehci_urb_enqueue 的分流 #

EHCI 的处理按端点类型分两条路：

text
control   -> qh_urb_transaction() + submit_async()
bulk      -> qh_urb_transaction() + submit_async()
interrupt -> qh_urb_transaction() + submit_periodic()
isoc      -> itd/sitd 路径 + submit_periodic()

前两种走异步调度表（asynchronous schedule list），后两种走周期调度表（periodic schedule list）。这个分法的理由是带宽：中断和等时要求时间确定性，必须挂在周期表上按帧预约；控制和批量可以等，挂在异步表上占剩余带宽。

qh_urb_transaction() 的活是把 urb 拆成一串 qTD（Queue Element Transfer Descriptor）。qTD 是 EHCI 能认识的传输单元，一个 qTD 描述一次不超过一定长度的传输。你的 urb 传 8KB，端点最大包长 512，就会生成多个 qTD，每个 qTD 挂到 qtd_list 上。

submit_async() 的活是把这串 qTD 挂到端点对应的 QH（Queue Head）上，再把 QH 排进异步调度表。QH 是端点的硬件代表，一个端点一个 QH，里面存着端点特性、当前 qTD 指针、以及 DATA0/DATA1 翻转位。

8.4 同步接口怎么等 #

usb_start_wait_urb() 提交完 urb 以后，调用 wait_for_completion_timeout() 把自己挂起。这是个非中断的等待，进程睡眠，不占 CPU。等谁唤醒它？等 urb->complete 里的 complete(&ctx->done)。

把 usb_control_msg() 的整条链路串起来：

text
usb_control_msg()
  -> usb_internal_control_msg()
       -> usb_alloc_urb()                分配
       -> usb_fill_control_urb()         填充
       -> usb_start_wait_urb()
            -> usb_submit_urb(GFP_NOIO)  提交
            -> wait_for_completion_timeout()  睡
                 ... 硬件跑完，中断进来 ...
                 -> urb->complete = usb_api_blocking_completion
                      -> complete(&ctx->done)   醒
       -> usb_free_urb()                 回收

超时的情况也走这条线：wait_for_completion_timeout() 返回 0，说明没人叫它。这时要 usb_kill_urb() 把 urb 撤下来，再返回 -ETIMEDOUT。

GFP_NOIO 这个标志有讲究。它不允许内存分配触发 IO，因为提交 urb 本身就在 IO 路径上，如果再进 IO 就死锁了。写同步等待路径时必须用这个标志，不能用 GFP_KERNEL。

8.5 什么时候能用 GFP_KERNEL #

一条简单判据：这段代码能睡吗。

上下文 能用 GFP_KERNEL 吗 提交 urb 用 同步接口能用吗
进程上下文（probe、ioctl、write） 能 GFP_KERNEL 能
中断上下文（irq handler） 不能 GFP_ATOMIC 不能
完成回调（urb->complete） 不能 GFP_ATOMIC 不能
定时器回调 不能 GFP_ATOMIC 不能
持有自旋锁 不能 GFP_ATOMIC 不能

urb->complete 是在中断上下文里跑的（软中断或 tasklet），这一点经常被忘记。在回调里调 usb_control_msg() 会直接崩，因为那个函数会睡。需要发同步请求的场合，把活扔给 workqueue，在 work 里发。

九、urb 的完成回调 #

传输跑完了，硬件中断进来，内核得找到你的 urb 把结果还回去。这一段是驱动里最容易写出 bug 的地方，因为它在中断上下文跑。

9.1 真实设备的回收路径 #

以 EHCI 为例，从中断入口到你的回调，一路是这样：

text
系统中断入口
  -> asm_do_IRQ
       -> handle_level_irq
            -> handle_IRQ_event
                 -> usb_hcd_irq            控制器中断
                      -> ehci_irq
                           -> ehci_work
                                -> scan_async
                                     -> qh_completions
                                          -> qtd_copy_status     填 urb->status
                                          -> ehci_urb_done
                                               -> usb_hcd_giveback_urb
                                                    -> urb->complete(urb)

qh_completions() 里做的是逐个 qTD 看完成状态，把结果汇总写进 urb->status。qtd_copy_status() 把 qTD 的状态码翻译成 urb 的错误码，这一步决定了你在回调里看到的 status 是什么值。ehci_urb_done() 把已经完成的 urb 从端点的 urb_list 上摘下来，然后交给 usb_hcd_giveback_urb()。

usb_hcd_giveback_urb() 是统一的回收出口：

c
void usb_hcd_giveback_urb(struct usb_hcd *hcd, struct urb *urb, int status)
{
	urb->status = status;
	unmap_urb_for_dma(hcd, urb);
	usb_hcd_unlink_urb_from_ep(hcd, urb);
	usb_unanchor_urb(urb);
	urb->complete(urb);
	usb_put_urb(urb);
}

顺序不能乱：先解映射再回调，因为回调里会重新提交这个 urb、重新映射。usb_unanchor_urb() 把 urb 从锚点链表上摘掉，否则锚点会一直涨。

9.2 根 hub 的回收路径 #

根 hub 没有真实硬件端点，走另一条：

text
rh_timer_func(timer)
  -> usb_hcd_poll_rh_status(hcd)
       -> hcd->driver->hub_status_data(hcd, buffer)
            -> 有变化就取出 hcd->status_urb，拷数据
                 -> usb_hcd_unlink_urb_from_ep
                 -> usb_hcd_giveback_urb(hcd, urb, 0)
                      -> urb->complete

rh_timer_func 本身就是个定时器函数，一行转发，在 usb_create_hcd() 里挂上：

c
static void rh_timer_func(unsigned long _hcd)
{
	usb_hcd_poll_rh_status((struct usb_hcd *)_hcd);
}

hcd->rh_timer.function = rh_timer_func;

根 hub 的中断端点用轮询实现，不是真中断。这是它的第二个特殊之处（第一个是不做 DMA 映射，见 9.4）。驱动请求状态时注册一个 urb 到 hcd->status_urb，之后靠这个定时器定期去查。轮询主体：

c
void usb_hcd_poll_rh_status(struct usb_hcd *hcd)
{
	struct urb *urb;
	int length;
	unsigned long flags;
	char buffer[4];		/* Any root hubs with > 31 ports? */

	if (unlikely(!hcd->rh_registered))	/* 驱动还没注册就退出 */
		return;
	if (!hcd->uses_new_polling && !hcd->status_urb)
		return;

	/* 让 HCD 自己报有没有状态变化，返回值大于 0 表示有 */
	length = hcd->driver->hub_status_data(hcd, buffer);
	if (length > 0) {
		spin_lock_irqsave(&hcd_root_hub_lock, flags);
		urb = hcd->status_urb;
		if (urb) {
			hcd->poll_pending = 0;
			hcd->status_urb = NULL;
			urb->actual_length = length;
			memcpy(urb->transfer_buffer, buffer, length);
			usb_hcd_unlink_urb_from_ep(hcd, urb);
			spin_unlock(&hcd_root_hub_lock);
			usb_hcd_giveback_urb(hcd, urb, 0);
			spin_lock(&hcd_root_hub_lock);
		} else {
			length = 0;
			hcd->poll_pending = 1;
		}
		spin_unlock_irqrestore(&hcd_root_hub_lock, flags);
	}

	if (hcd->uses_new_polling ? hcd->poll_rh :
	    (length == 0 && hcd->status_urb != NULL))
		mod_timer(&hcd->rh_timer, (jiffies / (HZ / 4) + 1) * (HZ / 4));
}

hub_status_data 是 HCD 提供的回调，EHCI 里是 ehci_hub_status_data()，负责检测端口状态和 td 队列状态，返回有变化的端口数。返回值大于 0 就是有事情发生。

hcd->status_urb 非空就把状态数据拷进去，urb->actual_length = length，然后交回上层。空就说明还没人申请，置 poll_pending 记一笔，等下次有人申请时立刻补发。

注意 usb_hcd_giveback_urb() 调用时是放了 hcd_root_hub_lock 的。回调里会重新提交 urb，重新提交要拿这把锁，不放开就自锁死。回调返回后再把锁拿回来。

最后那句 mod_timer 决定下次什么时候来。(jiffies / (HZ/4) + 1) * (HZ/4) 让所有 USB 设备的定时器对齐到同一批时间点触发，减少 CPU 被打断的次数。规范要求 256ms 内必须报一次，HZ/4 在 HZ=100 时是 25ms，远快于要求。

9.3 根 hub 为什么不做 DMA 映射 #

普通设备提交 urb 时，usb_hcd_submit_urb() 会把 transfer_buffer 做 DMA 映射，让设备能直接访问这块内存。根 hub 不走这一步。

原因是根 hub 不是真硬件。它是 HCD 虚拟出来的一个设备，代表主机控制器自己。根 hub 的「端点」没有物理实体，所谓传输只是把 HCD 内部的状态字拷到一块内存里。具体到代码：usb_hcd_poll_rh_status() 里那句 memcpy(urb->transfer_buffer, buffer, length)，数据源是栈上的 char buffer[4]，目的地是 urb 的传输缓冲区。两边都是普通内存，中间没有总线传输，没有设备发起 DMA 读。

所以 Linux 按 spec 的规定把根 hub 的状态静态放在内存里，操作的时候直接拷贝过去就行。既然没有真实的总线传输，就没有必要映射——映射了也没有任何设备会去读那个地址。这也是为什么根 hub 的传输不会失败。它不依赖线缆、不依赖对端设备响应，拷贝完就算完成。你在 lsusb -t 里看到的根 hub 就是这一层虚拟化出来的。

项目 真实设备 根 hub
提交入口 hcd->driver->urb_enqueue rh_urb_enqueue
传输描述符 qTD / iTD / siTD 无
DMA 映射 需要 不需要
数据来源 设备通过总线发来 HCD 内部状态字，memcpy
完成触发 硬件中断 定时器 rh_timer_func
会失败吗 会（超时、stall、CRC 错） 不会

9.4 回调里能做什么，不能做什么 #

回调签名只有 urb 一个参数（typedef void (*usb_complete_t)(struct urb *)），要拿私有数据走 urb->context。

能做 不能做
读 status 和 actual_length 判断结果 任何会睡的操作：kmalloc(GFP_KERNEL)、mutex_lock()、usb_control_msg()、msleep()
改 context 指向的数据（无并发访问时） 调 usb_kill_urb()，它会等自己，直接死锁
重新提交这个 urb（GFP_ATOMIC） 假设 status == 0 就等于数据完整，短包也是 0
complete() / wake_up() 唤醒等待者 直接释放 transfer_buffer，如果 urb 还要复用
数据入环形缓冲区、调度 workqueue

一个必须处理的边界：urb->status 为 -ENOENT 或 -ECONNRESET 表示 urb 是被取消的，不是传输失败。disconnect 里调 usb_kill_urb() 就会让在飞的 urb 回调收到这个值。这时候不要重试，直接返回。

9.5 三种收尾写法 #

同步等待型。回调只负责叫醒：

c
static void my_sync_complete(struct urb *urb)
{
	struct my_ctx *ctx = urb->context;
	ctx->status = urb->status;
	ctx->actual = urb->actual_length;
	complete(&ctx->done);
}

流式重提交型。中断端点常用，回调里处理数据然后立刻重新提交：

c
static void my_int_complete(struct urb *urb)
{
	struct my_priv *priv = urb->context;

	if (urb->status) {
		if (urb->status == -ENOENT || urb->status == -ECONNRESET)
			return;			/* 被取消，退出 */
		if (++priv->errors > 5)		/* 其他错误，计数后重试 */
			return;
	}

	my_handle_data(priv, urb->transfer_buffer, urb->actual_length);

	usb_submit_urb(urb, GFP_ATOMIC);	/* 保持一直有 urb 在飞 */
}

这个模式的关键是「一直有 urb 在飞」。中断端点的意义就是持续等待设备上报，中间断了就会漏事件。

等时流水型。等时传输不能只有一个 urb，必须预先准备多个形成环：

c
for (i = 0; i < N_URBS; i++) {
	urb = usb_alloc_urb(packets_per_urb, GFP_KERNEL);
	/* 等时字段手工填，见 7.4 */
	usb_submit_urb(urb, GFP_KERNEL);
}

static void my_iso_complete(struct urb *urb)
{
	struct my_priv *priv = urb->context;
	int i;

	if (!urb->status) {
		for (i = 0; i < urb->number_of_packets; i++) {
			struct usb_iso_packet_descriptor *d =
				&urb->iso_frame_desc[i];
			if (!d->status)
				my_queue_audio(priv, urb->transfer_buffer +
					       d->offset, d->actual_length);
		}
	}
	usb_submit_urb(urb, GFP_ATOMIC);
}

等时的错误处理要注意：每个包的 status 单独判断，一个包错了不代表整帧丢。音频设备允许偶尔丢几个采样，视频允许偶尔丢几帧，业务层能做补偿就补偿。

9.6 停 urb 的三种方式 #

函数 行为 用在什么场合
usb_kill_urb(urb) 取消并同步等待回调执行完 disconnect、pre_reset
usb_poison_urb(urb) 取消并标记，后续提交全部失败 让端点彻底停用
usb_unpoison_urb(urb) 清掉 poison 标记 恢复正常使用

usb_kill_urb() 是最常用的。它返回时保证回调已经跑完了，你可以安全释放私有数据。代价是它会睡，不能在中断上下文调。usb_poison_urb() 除了取消，还会把 urb 标记成中毒状态，之后再 usb_submit_urb() 返回 -EXDEV，用来防止某个路径上还在偷偷重提交。

一次要停很多个 urb 时，用锚点批量操作：

c
struct usb_anchor anchor;

init_usb_anchor(&anchor);
usb_anchor_urb(urb, &anchor);		/* 提交前挂上 */
usb_submit_urb(urb, GFP_KERNEL);

usb_kill_anchored_urbs(&anchor);	/* 停止全部 */

锚点比你自己维护链表可靠，因为它处理了提交和完成之间的竞态。自己写链表，很容易出现在「刚判断完链表为空、新 urb 又进来了」的窗口里出错。

十、HUB 与 TT 电路 #

前面反复提到 TT，这一章说清楚它是什么、为什么有它、以及单 TT 和多 TT 的差别。

10.1 TT 是什么 #

TT 是 Transaction Translator，翻译过来叫事务翻译器。你可以把它想成一块特殊的电路，物理上在 hub 里面，确切地说在高速 hub 里面。

USB 有三种速度：低速（1.5Mbps）、全速（12Mbps）、高速（480Mbps）。USB 1.x 时代只有前两种，主机控制器也只有 OHCI 和 UHCI 两种。USB 2.0 推出 EHCI 之后，高速设备出现了，hub 也分成高速 hub 和老 hub。

问题来了：高速 hub 能不能直接挂低速/全速设备？答案是不行。高速 hub 的下行端口跑在高速信令上，低速/全速设备的电平、包格式、握手全都不一样，双方说不上话。

解决方式是加一块 TT 电路。它负责高速与低速/全速之间的数据转换：上游按高速协议收发，下游按低速/全速协议收发，中间做包的拆分与重组、速度转换、时序对齐。

结论：一个高速 hub 里如果有 TT，就能挂低速/全速设备；没有 TT，低速/全速设备就没法用，只能插到 OHCI/UHCI 出来的 hub 口上。

10.2 单 TT 与多 TT #

类型 结构 bDeviceProtocol 值 影响
Single TT 整个 hub 共用一块 TT 1 多个低速设备互相拖慢
Multiple TT 每个端口各配一块 TT 2 各端口互不干扰

区别在并发能力。单 TT 的 hub 上，所有低速/全速设备共用一套翻译电路，同一时刻只能有一个设备在做转换。你插三个低速设备上去，它们的事务要排队，总带宽被一块 TT 卡住，表现就是三个设备一起变慢。多 TT 的 hub 每个端口一块独立电路，各走各的，互不排队。

现实情况：大多数消费级 hub 是单 TT。理由很直接——一个 hub 一块 TT 就够应付常见的键鼠场景，多加电路要成本。买 hub 时不看这个参数，插上一堆低速设备才发现互相拖累。

代码里判断靠设备描述符的 bDeviceProtocol：

c
/* 全速/低速 hub 的这个字段是 0 */
if (udev->descriptor.bDeviceProtocol == 1)
	dev_info(&udev->dev, "single TT hub\n");
else if (udev->descriptor.bDeviceProtocol == 2)
	dev_info(&udev->dev, "multiple TT hub\n");

usb_device 里的 tt 和 ttport 就是给这种设备用的。设备挂在高速 hub 的某个端口后面、且自己是低速/全速设备时，tt 指向那个 hub 的 TT 结构，ttport 记住是哪个端口。

c
struct usb_tt {
	struct usb_device	*hub;		/* hub that implements this TT */
	wait_queue_head_t	wait;
	int			multi;		/* nonzero for multi-TT */
	unsigned		think_time;	/* from hub descriptor */
	struct list_head	tt_list;
};

multi 非 0 表示多 TT。think_time 从 hub 描述符里来，是 TT 在两次事务之间需要的最小间隔，调度时要考虑。

10.3 hub 的传输特点与端口状态位 #

USB 存储设备最常见的是控制传输加批量传输。hub 不一样，它用的是控制加中断，其中最有特色的是中断传输。hub 的那个中断端点只有一个用途：上报端口状态变化。设备插拔、过流、端口使能状态改变，都从这个端点报上来。这个端点常驻一个 urb，回调里重新提交，一直转。这就是第十一章那个 hub 线程的触发源。

hub 上报的状态有两个寄存器，一个叫端口状态（port status），一个叫端口状态变化（port change）。两个都是位图。

位 名称 含义
USB_PORT_STAT_CONNECTION Current Connect Status 当前有没有设备接在这个口上
USB_PORT_STAT_ENABLE Port Enabled 端口是否已使能
USB_PORT_STAT_SUSPEND Suspend 端口是否挂起
USB_PORT_STAT_RESET Reset 端口是否正在复位
USB_PORT_STAT_LOW_SPEED Low Speed 设备是低速
USB_PORT_STAT_HIGH_SPEED High Speed 设备是高速
USB_PORT_STAT_C_CONNECTION Connect Change 连接状态变过
USB_PORT_STAT_C_ENABLE Enable Change 使能状态变过
USB_PORT_STAT_C_RESET Reset Change 复位完成过

两个寄存器的用法有本质区别。状态位是「现在是什么」，变化位是「变过没有」。USB_PORT_STAT_CONNECTION 为 1，说明现在有设备连着。USB_PORT_STAT_C_CONNECTION 为 1，说明这个连接状态自上次清除以来变过。变化位是粘滞的，读完之后必须发 Clear Port Feature 请求清掉，否则下次还会报。这个请求也是 hub 的标准请求之一。

判断逻辑很直白：

c
/* 有设备接着，且连接状态刚变过 */
if ((portstatus & USB_PORT_STAT_CONNECTION) &&
    (portchange & USB_PORT_STAT_C_CONNECTION))
	connect_change = 1;

插入和拔出都会让这两位置起来。区别在于 portstatus 的 CONNECTION 位：插入时是 1，拔出时是 0。

10.4 什么情况要重新枚举 #

hub 线程对每个端口做判断，三种情况要往 hub_port_connect_change() 走：

  1. 连接有变化。插了或者拔了。
  2. 端口本身重新使能，也就是 enable 状态变了。这种情况多半是为了对付电磁干扰——瞬时干扰让端口掉了使能，重新使能后设备其实还在。
  3. 在复位一个设备的时候发现它的描述符变了。这对应硬件本身做了升级，比如某些设备支持在线更新固件。

第一种是真正的物理变化，后两种算逻辑变化。循环里那个端口号计数器不只是遍历用，它还保证了「有几个端口，才能接几个设备」这个逻辑。usb_bus 最多接 128 个设备，hub 最多接 31 个设备，但 hub 上没那么多物理端口，你也没法接更多。端口数是 hub 描述符的 bNbrPorts 拿的。

十一、热插拔与 hub 线程 #

设备插上去，probe 就被调用。中间这一大段是内核自动跑的，但它决定了你 probe 能不能被调到。

11.1 谁在盯着端口 #

hub 驱动在初始化时创建一个内核线程，线程主体是个循环：

c
khubd_task = kthread_run(hub_thread, NULL, "khubd");

do {
	hub_events();
	wait_event_freezable(khubd_wait,
			!list_empty(&hub_event_list) ||
			kthread_should_stop());
} while (!kthread_should_stop() || !list_empty(&hub_event_list));

hub_event_list 把所有 usb_hub 的 event_list 串在一起。hub 的中断 urb 回调报告有事件，就把这个 hub 挂进 hub_event_list，然后唤醒 khubd_wait。线程醒来跑一圈 hub_events()，跑完再睡。

这个设计的意义：中断上下文里只做最少的事（把 hub 挂链表、唤醒线程），所有耗时操作（发控制请求、复位端口、读描述符）全在 hub_events() 里做。因为它在进程上下文，可以睡。

hub_events() 对每个 hub 的每个端口做检查。端口号从 1 到 bNbrPorts，这个值从 hub 描述符里读：

c
for (i = 1; i <= hub->descriptor->bNbrPorts; i++) {
	if (connect_change)
		hub_port_connect_change(hub, i, portstatus, portchange);
}

11.2 hub_port_connect_change 的重试结构 #

真正的枚举在这里。核心是一个四次循环：

c
for (i = 0; i < SET_CONFIG_TRIES; i++) {	/* SET_CONFIG_TRIES = 4 */
	udev = usb_alloc_dev(hdev, hdev->bus, port1);
	udev->speed = USB_SPEED_UNKNOWN;

	choose_address(udev);				/* 分配 udev->devnum */
	status = hub_port_init(hub, udev, port1, i);
	...
}

前两次（i=0、i=1）走新策略，后两次（i=2、i=3）走旧策略。所有这一切只有一个目的：拿到设备描述符。早年有些设备不按规范来，读描述符的路径必须换个问法才通。新策略是「先读 64 字节看看」，旧策略是「先读 8 字节，再按 bMaxPacketSize0 读全」。

choose_address() 在 usb_bus 的 devmap 位图里找一个空闲地址填进 udev->devnum。这一步必须在读描述符之前，因为设备需要地址才能响应非默认管道的请求。

11.3 hub_port_init 干的三件事 #

原型：

c
static int hub_port_init(struct usb_hub *hub, struct usb_device *udev,
			 int port1, int retry_counter)

它依次做：调 hub_port_reset() 复位端口，顺便把 udev->speed 定下来；根据 udev->speed 猜一个 udev->ep0.desc.wMaxPacketSize，填 udev->tt 和 udev->ttport；在循环里读设备描述符，直到成功或者重试用完。

第二步的「猜」是个关键点。端点 0 的最大包长在设备描述符的 bMaxPacketSize0 里，但要读到设备描述符，得先用端点 0 发控制传输。这是个鸡生蛋问题。内核的解法是按速度猜：低速设备猜 8，全速猜 8 或 16 或 32 或 64，高速猜 64。猜错了就重试，每次换一种。GET_DESCRIPTOR_TRIES 是 2，配合外层 4 次循环，一共 8 次机会。

c
#define GET_DESCRIPTOR_BUFSIZE	64
buf = kmalloc(GET_DESCRIPTOR_BUFSIZE, GFP_NOIO);
for (j = 0; j < 3; ++j) {
	buf->bMaxPacketSize0 = 0;
	r = usb_control_msg(udev, usb_rcvaddr0pipe(),
	    USB_REQ_GET_DESCRIPTOR, USB_DIR_IN,
	    USB_DT_DEVICE << 8, 0,
	    buf, GET_DESCRIPTOR_BUFSIZE, USB_CTRL_GET_TIMEOUT);
	switch (buf->bMaxPacketSize0) {
	case 8: case 16: case 32: case 64: case 255:
		if (buf->bDescriptorType == USB_DT_DEVICE) {
			r = 0;
			break;
		}
		/* FALL THROUGH */
	default:
		if (r == 0)
			r = -EPROTO;
		break;
	}
	if (r == 0)
		break;
}
udev->descriptor.bMaxPacketSize0 = buf->bMaxPacketSize0;
kfree(buf);

for (j = 0; j < SET_ADDRESS_TRIES; ++j) {	/* SET_ADDRESS_TRIES = 2 */
	retval = hub_set_address(udev, devnum);
	if (retval >= 0)
		break;
	msleep(200);
}
if (retval < 0) {
	dev_err(&udev->dev, "device not accepting address %d, error %d\n",
		devnum, retval);
	goto fail;
}

三次内循环是为了容错。读到合法的 bMaxPacketSize0 并且 bDescriptorType 正确才算成功，255 那个分支是给某些不守规矩设备留的后门。读到之后再用这个值读完整设备描述符，如果返回长度等于 sizeof(udev->descriptor)，说明控制传输正常、端点 0 包长也验证对了。

device not accepting address 这个报错很有名。它表示 SET_ADDRESS 请求设备没应答，多半意味着设备供电不足、线缆质量差、或者设备已经在别的状态里。

11.4 hub_port_reset 与端口复位 #

c
static int hub_port_reset(struct usb_hub *hub, int port1,
			  struct usb_device *udev, unsigned int delay)
{
	int i, status;

	/* Block EHCI CF initialization during the port reset.
	 * Some companion controllers don't like it when they mix. */
	down_read(&ehci_cf_port_reset_rwsem);

	for (i = 0; i < PORT_RESET_TRIES; i++) {	/* PORT_RESET_TRIES = 5 */
		status = set_port_feature(hub->hdev, port1, USB_PORT_FEAT_RESET);
		if (status)
			dev_err(hub->intfdev, "cannot reset port %d (err = %d)\n",
				port1, status);
		else {
			status = hub_port_wait_reset(hub, port1, udev, delay);
			if (status && status != -ENOTCONN)
				dev_dbg(hub->intfdev, "port_wait_reset: err = %d\n",
					status);
		}

		switch (status) {
		case 0:
			/* TRSTRCY = 10 ms; plus some extra */
			msleep(10 + 40);
			udev->devnum = 0;	/* Device now at address 0 */
			/* FALL THROUGH */
		case -ENOTCONN:	/* 107, transport endpoint is not connected */
		case -ENODEV:	/* 19, no such device */
			clear_port_feature(hub->hdev, port1, USB_PORT_FEAT_C_RESET);
			usb_set_device_state(udev, status
				? USB_STATE_NOTATTACHED : USB_STATE_DEFAULT);
			goto done;
		}
		dev_dbg(hub->intfdev, "port %d not enabled, trying reset again\n",
			port1);
		delay = HUB_LONG_RESET_TIME;
	}
	dev_err(hub->intfdev, "Cannot enable port %i.  Maybe the USB cable is bad?\n",
		port1);
done:
	up_read(&ehci_cf_port_reset_rwsem);
	return status;
}

ehci_cf_port_reset_rwsem 这把读写信号量挡的是 EHCI 的伴随控制器初始化。老式主板上 EHCI 和 UHCI/OHCI 共存，端口复位期间不能让伴随控制器捣乱。

msleep(10 + 40) 里的 10ms 是规范要求的复位恢复时间（TRSTRCY），后面 40ms 是余量。成功复位后 udev->devnum = 0，因为设备回到地址 0 的默认态，状态置成 USB_STATE_DEFAULT。

失败分支的三种状态码：0、-ENOTCONN（107，连接已断）、-ENODEV（19，设备不存在）。只有这三种才清复位变化位。其他错误码会走到循环末尾重试，五次都失败就打那句「Maybe the USB cable is bad?」。

11.5 hub_port_wait_reset #

c
static int hub_port_wait_reset(struct usb_hub *hub, int port1,
			       struct usb_device *udev, unsigned int delay)
{
	ret = hub_port_status(hub, port1, &portstatus, &portchange);

	if (!(portstatus & USB_PORT_STAT_CONNECTION))
		return -ENOTCONN;	/* 复位期间设备被拔了 */
	if (portchange & USB_PORT_STAT_C_CONNECTION)
		return -ENOTCONN;	/* 复位期间又报插入，不正常 */

	if (!(portstatus & USB_PORT_STAT_RESET) &&
	    (portstatus & USB_PORT_STAT_ENABLE)) {
		if (hub_is_wusb(hub))
			udev->speed = USB_SPEED_VARIABLE;
		else if (portstatus & USB_PORT_STAT_HIGH_SPEED)
			udev->speed = USB_SPEED_HIGH;
		else if (portstatus & USB_PORT_STAT_LOW_SPEED)
			udev->speed = USB_SPEED_LOW;
		else
			udev->speed = USB_SPEED_FULL;
		return 0;
	}
	return -ETIMEDOUT;		/* 常见的是 -110 */
}

udev->speed 就是从端口状态字里读出来的。复位完成后状态位应该是 ENABLE 置起、RESET 落下，这时候看 HIGH_SPEED 和 LOW_SPEED 两个位就知道速度：都不置就是全速。返回 -ETIMEDOUT（-110）是实践中最常见的失败值，意思是等了这么久端口还没完成复位，原因多为设备固件卡住、供电不足、或者线缆太差。

hub_port_status() 底下就是发 GET_STATUS 请求：

c
static int get_port_status(struct usb_device *hdev, int port1,
			   struct usb_port_status *data)
{
	int i, status = -ETIMEDOUT;	/* ETIMEDOUT = 110 */

	for (i = 0; i < USB_STS_RETRIES && status == -ETIMEDOUT; i++) {
		status = usb_control_msg(hdev, usb_rcvctrlpipe(hdev, 0),
		    USB_REQ_GET_STATUS, USB_DIR_IN | USB_RT_PORT, 0, port1,
		    data, sizeof(*data), USB_STS_TIMEOUT);
	}
	return status;
}

注意 USB_RT_PORT 这个请求类型，它表示这是发给 hub 端口的类请求，不是发给设备的。hub 的所有端口操作都靠这个类型区分。

11.6 probe 为什么没被调用 #

现象 检查点
dmesg 完全没有插入日志 供电、线缆、端口本身
有 new high-speed USB device 但没绑定 id_table 是否匹配，MODULE_DEVICE_TABLE 漏没漏
有 device not accepting address 供电不足、线缆质量、设备状态
有 Cannot enable port 端口复位失败，多半是硬件
有 -110 超时 设备固件没响应，或 TT 配置有问题
绑定到了错误的驱动 id_table 太宽，用 USB_INTERFACE_INFO 收窄

lsusb -t 看树形结构和速度，lsusb -v 看全部描述符，cat /sys/kernel/debug/usb/devices 看内核眼里的设备状态。三个一起用，比反复加 printk 快。

十二、易错点速查 #

12.1 结构体与描述符 #

现象 原因 处理
遍历端点越界 alt->endpoint 的长度没跟 desc.bNumEndpoints 循环上界用 desc.bNumEndpoints
接口顺序对不上 usb_host_config.interface[] 顺序不等于接口号 用 bInterfaceNumber 判断
拿不到类特定描述符 在错误的结构里找 extra 接口级在 usb_host_interface.extra
复合设备识别成单一功能 用了 USB_DEVICE 而不是 USB_INTERFACE_INFO 按接口类匹配
端点号传错 把 bEndpointAddress（如 0x81）当端点号 用 usb_endpoint_num() 取低 4 位

12.2 urb #

现象 原因 处理
提交返回 -EPIPE 端点被 stall usb_clear_halt() 清掉
提交返回 -EACCES 接口处于挂起 先 usb_autopm_get_interface()
提交返回 -ENOSPC 等时/中断带宽不够 减小包长或间隔，或减少并发 urb
回调永远不进 urb 提交失败但返回值没检查 检查 usb_submit_urb() 返回值
回调进两次 同一个 urb 重复提交 别并发提交，看 use_count
大块传输卡住 批量 OUT 缺零长包 加 URB_ZERO_PACKET
短包被当成功 默认行为 需要严格长度就设 URB_SHORT_NOT_OK
传输后数据是垃圾 DMA 缓冲区没映射或映射错 用 usb_alloc_coherent()
传输后内存被改 改了在飞 urb 的字段 只在回调里改

12.3 上下文与生命周期 #

现象 原因 处理
回调里崩在 might_sleep 回调里调了会睡的函数 改用 workqueue
拔设备后 oops disconnect 没停 urb usb_kill_urb() 之后再释放
偶发 use-after-free 定时器还在跑就释放了私有数据 del_timer_sync() 提前停
disconnect 卡住 在回调里调了 usb_kill_urb() 回调里不能等自己
设备休眠后传输出错 自动挂起计数没配平 get/put 成对调用
rmmod 报设备忙 还有打开的文件或未停的 urb 关文件、停 urb

12.4 枚举与 hub #

现象 原因 处理
低速设备插高速 hub 不认 hub 没有 TT 换多 TT hub 或插到 OHCI/UHCI 口
多个低速设备互相拖慢 单 TT hub 共用翻译电路 换多 TT hub
端口状态一直不变化 变化位没清 发 Clear Port Feature
复位总超时（-110） 设备固件或供电问题 换线、外接供电、复位重试
地址分配失败 devmap 满了或设备不应答 检查 128 设备上限、检查供电

12.5 最后三句 #

第一句，urb 是唯一的数据通道。所有同步接口底下都是它。搞不清的时候，把封装拆开，看完整的四步。

第二句，回调在中断上下文。能睡的函数一律不能在回调里调，需要睡眠的活交给 workqueue。

第三句，disconnect 的唯一义务是停干净。usb_kill_urb() 之后才动内存，顺序反了就是 oops。
