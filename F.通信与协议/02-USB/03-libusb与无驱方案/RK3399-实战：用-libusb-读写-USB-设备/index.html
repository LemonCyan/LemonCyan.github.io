这篇是一次完整的实战记录：在 SOM-RK3399 板子上插一块外接 USB 触摸屏，用 libusb 在用户态把触摸数据读出来，解析成坐标，再通过板子模拟出来的 HID 触摸屏转发到 PC，让 PC 上的鼠标跟着手指动。

讲什么：认设备、装环境、枚举、claim 接口、选端点、读数据、解析、踩坑、复盘，一整条链路走完。

不讲什么：libusb 的编译安装与交叉编译，看同目录《安装与交叉编译》；同步与异步的 API 模型、事件循环怎么组织，看《libusb 编程：从同步到异步》；usbmon 的抓包步骤与 URB 字段怎么读，看《usbmon 抓包》。

定位：本篇不解释 API 语义，只回答一个问题 —— 一块具体的板子、一个具体的设备、一堆具体的报错，怎么把数据读出来。

一、任务背景：要读什么设备 #

开发板 SOM-RK3399 核心板 + 定制底板

这条链路上有两块「触摸屏」 #

刚接触容易懵：明明是读一块屏，代码里怎么冒出来两个设备。因为这里要读一块真屏，同时还要模拟一块假屏，两者都在同一块板子上。

角色 身份 物理形态 在本篇里的作用
真触摸屏 VID 0x1a86 / PID 0xe5e3 USB 线插在板子的 Host 口上 数据来源，用 libusb 读它
模拟触摸屏 gadget 的 hidg2 Type-C 口配成 device 模式，线接 PC 数据出口，把解析结果写给它

真屏的参数如下，后面匹配设备、选端点、算缓冲区长度全用得上。

描述符字段 值 含义
idVendor 0x1a86 厂商 ID，沁恒 wch.cn
idProduct 0xe5e3 产品 ID
速度 12M 全速设备，不是高速
bInterfaceNumber 0 唯一接口
bInterfaceClass 3 HID 类
bInterfaceSubClass / Protocol 0 / 0 非键盘非鼠标的自定义 HID

四步走的核心 #

用户态读一个 USB 设备，剥掉所有细节就四步。顺序不能乱，一步失败后面全废。

步骤 用到的 API 拿到什么 失败的典型表现
1. 找到设备 libusb_get_device_list + libusb_get_device_descriptor 一个 libusb_device * 列表里根本没有你要的 VID/PID
2. 声明接口 libusb_claim_interface 接口的独占使用权 LIBUSB_ERROR_BUSY，内核驱动占着不放
3. 找到端点 libusb_get_endpoint_descriptor bEndpointAddress、bmAttributes、wMaxPacketSize 拿错端点地址，读的时候 Input/Output Error
4. 按端点类型收发 libusb_interrupt_transfer / libusb_bulk_transfer 一段原始字节 长度不对报 Overflow，缓冲区太小

第 4 步的 API 不能随便挑，它必须和第 3 步拿到的 bmAttributes 对上。端点说自己中断，你就得用 interrupt 版本；端点说自己批量，你就得用 bulk 版本。搞错了内核直接甩错误码。

为什么用 libusb，不走内核驱动 #

这块屏插上板子，内核的 usbtouchscreen / hid-multitouch 立刻接管，/dev/input/eventX 下面就有现成的事件流，读坐标其实更省事。

但我们要的不是坐标，是原始报文。我们要验证报告描述符的解析对不对、要看 52 个字节里每个字节的含义、要把这份数据原样搬到另一块模拟屏上。内核驱动已经把这些字节嚼碎成 input_event，看不到原始包。

libusb 绕开驱动，直接在用户态发 URB，读上来的就是总线上跑的那 52 个字节。代价是得自己 detach 内核驱动，还得自己解析报文。

最终要达成的效果 #

板子上跑 usb_test -v 0x1a86 -p 0xe5e3 -o /dev/hidg2：手指点真屏，从 0x82 端点读到 52 字节，按描述符把对应字节拼成 X/Y，按模拟屏的 0~0x7fff 范围缩放，拼成 5 字节报告写进 /dev/hidg2，PC 上的鼠标箭头跟着手指走。

中间任何一环断了，PC 那边就没反应。所以调试时要把每个环节单独验证，这点在第八章展开。

模拟触摸屏：gadget 脚本 #

板子的 USB3.0 Type-C 口被配成了从设备模式，所以它能反过来模拟成一个 USB 设备插到 PC 上。我们用 configfs 手工搭一个 HID gadget，同时模拟键盘、鼠标、触摸屏三个功能。在 /opt/hid 下新建 hid_keyboard_mouse.sh：

bash
#!/bin/bash

gadget=g1

do_start(){
    has_mount=$(mount -l | grep /sys/kernel/config)
    if [[ -z  $has_mount ]];then
        mount -t configfs none /sys/kernel/config
    fi
    cd /sys/kernel/config/usb_gadget

    # 创建完这个文件夹之后，系统自动在这个文件夹中创建usb相关的内容，内容需要由创建者自己填写
    if [[ ! -d ${gadget} ]]; then
        mkdir ${gadget}
    else
    	exit 0
    fi
    cd ${gadget}

    # 设置USB协议版本USB2.0
    echo 0x0200 > bcdUSB

    # 定义产品的VendorID和ProductID
    echo "0x0525"  > idVendor
    echo "0xa4ac" > idProduct

    # 实例化"英语"ID：
    mkdir strings/0x409

    # 将开发商、产品和序列号字符串写入内核
    echo "76543210" > strings/0x409/serialnumber
    echo "mkelehk"  > strings/0x409/manufacturer
    echo "keyboard_mouse"  > strings/0x409/product

    # 创建一个USB配置实例
    if [[ ! -d configs/c.1 ]]; then
        mkdir configs/c.1
    fi

    # 定义配置描述符使用的字符串
    if [[ ! -d configs/c.1/strings/0x409 ]]; then
        mkdir configs/c.1/strings/0x409
    fi

    echo "hid" > configs/c.1/strings/0x409/configuration

    # 创建接口
    mkdir functions/hid.0   #键盘
    mkdir functions/hid.1   #鼠标
    mkdir functions/hid.2   #触摸屏

    # 接口0，模拟键盘
    echo 1 > functions/hid.0/subclass   #启动设备符
    echo 1 > functions/hid.0/protocol   #标识键盘设备
    echo 8 > functions/hid.0/report_length  #标识该hid设备每次发送的报表长度为8字节
    echo -ne \\x05\\x01\\x09\\x06\\xa1\\x01\\x05\\x07\\x19\\xe0\\x29\\xe7\\x15\\x00\\x25\\x01\\x75\\x01\\x95\\x08\\x81\\x02\\x95\\x01\\x75\\x08\\x81\\x03\\x95\\x05\\x75\\x01\\x05\\x08\\x19\\x01\\x29\\x05\\x91\\x02\\x95\\x01\\x75\\x03\\x91\\x03\\x95\\x06\\x75\\x08\\x15\\x00\\x25\\x65\\x05\\x07\\x19\\x00\\x29\\x65\\x81\\x00\\xc0 > functions/hid.0/report_desc

	# 接口1，模拟键盘鼠标
    echo 1 > functions/hid.1/subclass  #启动设备符
    echo 2 > functions/hid.1/protocol  #鼠标协议
    echo 4 > functions/hid.1/report_length  # 相对值是4
    echo -ne \\x05\\x01\\x09\\x02\\xa1\\x01\\x09\\x01\\xa1\\x00\\x05\\x09\\x19\\x01\\x29\\x03\\x15\\x00\\x25\\x01\\x95\\x03\\x75\\x01\\x81\\x02\\x95\\x01\\x75\\x05\\x81\\x03\\x05\\x01\\x09\\x30\\x09\\x31\\x09\\x38\\x15\\x81\\x25\\x7f\\x75\\x08\\x95\\x03\\x81\\x06\\xc0\\xc0 > functions/hid.1/report_desc

    # 接口2，模拟触摸屏
    echo 0 > functions/hid.2/subclass
    echo 0 > functions/hid.2/protocol
    echo 5 > functions/hid.2/report_length  #标识该hid设备每次发送的报表长度为5字节
    echo -ne \\x05\\x01\\x09\\x02\\xa1\\x01\\x09\\x01\\xa1\\x00\\x05\\x09\\x19\\x01\\x29\\x05\\x15\\x00\\x25\\x01\\x95\\x05\\x75\\x01\\x81\\x02\\x95\\x01\\x75\\x03\\x81\\x01\\x05\\x01\\x09\\x30\\x09\\x31\\x15\\x00\\x26\\xff\\x7f\\x35\\x00\\x46\\xff\\x7f\\x75\\x10\\x95\\x02\\x81\\x02\\xc0\\xc0 > functions/hid.2/report_desc

    # 捆绑接口到配置config.1
    ln -s functions/hid.0 configs/c.1
    ln -s functions/hid.1 configs/c.1
    ln -s functions/hid.2 configs/c.1

    # 配置USB3.0 OTG0的工作模式为Device（设备）：
    #echo peripheral > /sys/devices/platform/ff770000.syscon/ff770000.syscon:usb2-phy@e460/otg_mode

    echo "sleep 3s"
    sleep 3s

    # 将gadget驱动注册到UDC上，插上USB线到电脑上，电脑就会枚举USB设备。
    echo fe900000.dwc3 > UDC
}

do_stop() {
    cd /sys/kernel/config/usb_gadget/${gadget}
    echo "" > UDC
}

case $1 in
    start)
        echo "Start hid gadget "
        do_start
        ;;
    stop)
        echo "Stop hid gadget"
        do_stop
        ;;
    *)
        echo "Usage: $0 (stop | start)"
        ;;
esac

几个点动手前要看清。

mount -t configfs none /sys/kernel/config 只在没挂载时执行，已经挂过就跳过，重复挂会报 Device or resource busy。if [[ ! -d ${gadget} ]]; then mkdir ... else exit 0 fi 的意思是「已经建过就不重建」，直接退出。改完脚本想重新生效，得先 echo "" > UDC，再把 /sys/kernel/config/usb_gadget/g1 删掉，重启也行。

echo fe900000.dwc3 > UDC 才是真正让 PC 看到设备的动作，写进去之前板子对 PC 来说什么都不是。UDC 这个名字来自 SoC 的 DWC3 控制器地址，换板子名字不同，用 ls /sys/class/udc/ 查。

do_stop 里原稿写作 ${gadaget}，少了一个 r，路径拼出来是空串，cd 会跑到 /sys/kernel/config/usb_gadget/ 下，后面的 echo "" > UDC 在那个目录里找不到文件。改成 ${gadget} 才能用。

让它开机自动跑 #

在 /etc/profile.d 下新建 hid.sh，内容就一行 /opt/hid/hid_keyboard_mouse.sh start。/etc/profile.d 下的脚本在登录时执行，前提是板子得有人登录，或者开机自动登录到某个终端。纯后台无登录的场景，把这条命令塞进 systemd unit 或 /etc/rc.local 更稳。

重启之后脚本自己跑完，/dev/hidg* 下面冒出三个字符设备：

bash
root@SOM-RK3399v2:/home/pi# ls /dev/hidg* -nR
crw------- 1 0 0 236, 0 Sep 26 14:25 /dev/hidg0    # 键盘
crw------- 1 0 0 236, 1 Sep 26 14:25 /dev/hidg1    # 鼠标
crw------- 1 0 0 236, 2 Sep 26 14:25 /dev/hidg2    # 触摸屏
root@SOM-RK3399v2:/home/pi# ls /sys/kernel/config/usb_gadget/g1/
UDC           bDeviceProtocol  bMaxPacketSize0  bcdUSB   functions  idVendor  strings
bDeviceClass  bDeviceSubClass  bcdDevice        configs  idProduct  os_desc

三个设备主设备号都是 236，从设备号 0/1/2 对应 functions/hid.0 / hid.1 / hid.2，我们要写的是 hidg2。配置目录里的 idVendor / idProduct 就是写进去的 0x0525 / 0xa4ac，PC 设备管理器里看到的是这两个值。

gadget 的触摸屏接口有一份自己的 HID 报告描述符，写进去的字节必须符合它。这份描述符怎么拆、5 个字节怎么排，放到第七章和真屏的描述符一起讲，两边对比着看才清楚。

三、枚举与识别目标设备 #

libusb 的第一步不是打开设备，是拿设备列表。这个动作和内核枚举 USB 是两回事：内核早就枚举完了，libusb 只是把内核建好的设备树读一遍，翻译成 libusb_device 数组。

c
r = libusb_init(NULL);
if (r < 0)
    return r;

cnt = libusb_get_device_list(NULL, &devs);
if (cnt < 0) {
    libusb_exit(NULL);
    return 1;
}

libusb_init(NULL) 传 NULL 表示用默认上下文，多线程各自要独立设备列表时才需要自己造上下文。libusb_get_device_list 返回设备个数，负数表示失败，拿到的 devs 是以 NULL 结尾的指针数组，遍历条件是 devs[i] 为真，不是 i < cnt。libusb_free_device_list(devs, 1) 第二个参数传 1，表示把数组里每个 libusb_device 的引用一并释放；传 0 的话设备对象还在，得自己 libusb_unref_device。

用 VID/PID 匹配 #

c
bool device_match_vid_pid(libusb_device *dev, uint16_t vid, uint16_t pid)
{
    struct libusb_device_descriptor desc;
    int ret;
    ret = libusb_get_device_descriptor(dev, &desc);
    if (ret < 0) {
        fprintf(stderr, "failed to get device descriptor");
        return false;
    }
    return desc.idVendor == vid && desc.idProduct == pid;
}

libusb_get_device_descriptor 只读 18 个字节的设备描述符，不产生 URB，不碰总线，纯内存操作。所以哪怕设备已经被别的驱动占着，这个调用照样成功，匹配 VID/PID 这一步不会因为「设备忙」失败。它失败只有一种原因：设备在列表里但描述符读不出来，多半是设备已经掉线，拔了线或者供电不稳。返回 false 跳过就行，不要当致命错误。

打印设备、配置、接口、端点 #

print_device 从设备描述符往下钻，一直打到端点：

c
switch (libusb_get_device_speed(dev)) {
    case LIBUSB_SPEED_LOW: speed = "1.5M"; break;
    case LIBUSB_SPEED_FULL: speed = "12M"; break;
    case LIBUSB_SPEED_HIGH: speed = "480M"; break;
    case LIBUSB_SPEED_SUPER: speed = "5G"; break;
    case LIBUSB_SPEED_SUPER_PLUS: speed = "10G"; break;
    default: speed = "Unknown";
}

ret = libusb_get_device_descriptor(dev, &desc);
if (ret < 0) { return; }

if (!handle)
    libusb_open(dev, &handle);

printf("Dev (bus %u, device %u): %04X - %04X speed: %s\n",
       libusb_get_bus_number(dev), libusb_get_device_address(dev),
       desc.idVendor, desc.idProduct, speed);

我们的屏报出来是 12M，全速。全速设备的中断端点 wMaxPacketSize 最大 64，所以描述符里写 64 是顶格。换成高速设备能到 1024，那时缓冲区得跟着放大。

libusb_get_bus_number 和 libusb_get_device_address 拼起来就是 sysfs 里的 1-1.2 一类路径。handle 允许传空，函数内部自己 open，为的是能打印字符串描述符（厂商、产品、序列号）。每个字符串读之前先判索引非 0，索引为 0 表示设备没提供这个字符串，去读会返回错误，不是设备坏了。libusb_get_string_descriptor_ascii 会把 UTF-16 强转成 ASCII，中文厂商名会被丢弃或显示成问号，调试阶段够用。

配置描述符才是重点，接口和端点信息全在里头：

c
for (i = 0; i < desc.bNumConfigurations; i++) {
    struct libusb_config_descriptor *config;

    ret = libusb_get_config_descriptor(dev, i, &config);
    if (LIBUSB_SUCCESS != ret) {
        printf("  Couldn't retrieve descriptors\n");
        continue;
    }

    print_configuration(config);
    libusb_free_config_descriptor(config);
}

print_configuration 先打配置层的 wTotalLength、bNumInterfaces、bConfigurationValue、iConfiguration、bmAttributes、MaxPower。我们的 bmAttributes 是 0x80，表示总线供电；MaxPower 单位是 2mA，32 就是 64mA。再往下走接口层，一个接口可以有多个 altsetting，我们的屏只有 0 号，很多音频设备有好几个，选错了采样率就不对。

c
for (i = 0; i < interface->num_altsetting; i++)
    print_altsetting(&interface->altsetting[i]);

最后是端点层，这段信息密度最高：

c
printf("        bEndpointAddress:    %02xh\n", endpoint->bEndpointAddress);  // 位[3:0]端点号，第7位方向：0输出、1输入
printf("        bmAttributes:        %02xh\n", endpoint->bmAttributes);      // 位[1:0]：00控制 01等时 10批量 11中断
printf("        wMaxPacketSize:      %u\n", endpoint->wMaxPacketSize);      // 本端点收发单包的最大字节数
printf("        bInterval:           %u\n", endpoint->bInterval);            // 轮询间隔，中断传输用它
printf("        bRefresh:            %u\n", endpoint->bRefresh);
printf("        bSynchAddress:       %u\n", endpoint->bSynchAddress);

USB 3.0 设备还有端点伴随描述符，挂在 extra 里，按「首字节是长度」的规则逐条跳：判断 endpoint->extra[i + 1] 是否等于 LIBUSB_DT_SS_ENDPOINT_COMPANION，是就调 libusb_get_ss_endpoint_companion_descriptor 取出来打印，用完 libusb_free_ss_endpoint_companion_descriptor 释放，然后 i += endpoint->extra[i] 跳到下一条。写成 i++ 会死循环。

USB 2.0 及以上还有 BOS 描述符，bcdUSB >= 0x0201 时才走，我们的屏是 0x0200，正好卡在门槛下面，不经过这个分支，跳过它没有副作用。BOS 里存在两种能力描述符，libusb_get_usb_2_0_extension_descriptor 和 libusb_get_ss_usb_device_capability_descriptor 各有配套的 free 函数，取出来用完就释放。

整棵描述符树的遍历顺序是固定的：

层级 结构体 关键字段 我们要的答案
设备 libusb_device_descriptor idVendor、idProduct、bNumConfigurations 是不是我要的那块屏
配置 libusb_config_descriptor bNumInterfaces、bmAttributes、MaxPower 有几个接口可用
接口 libusb_interface_descriptor bInterfaceNumber、bInterfaceClass、bNumEndpoints claim 哪个接口号
端点 libusb_endpoint_descriptor bEndpointAddress、bmAttributes、wMaxPacketSize 用哪个 API 读、缓冲区开多大

四层一起看，就是「找到设备 → 声明接口 → 找到端点」这三步在代码里的落点。

四、打开设备与接口配置 #

设备在列表里找到了，接下来做两件事：把它从内核驱动手里抢过来，然后声明接口。两件都不做直接读，内核给你返回错误。

三种打开方式 #

第一种，自己拿 libusb_device 打开，控制权在手上：

c
libusb_device_handle *handle = NULL;
int r = libusb_open(dev, &handle);
if (r != 0) {
    fprintf(stderr, "libusb_open: %s\n", libusb_strerror(r));
    return -1;
}

第二种，按 VID/PID 一步到位：

c
handle = libusb_open_device_with_vid_pid(NULL, vendor_id, product_id);
if (handle == NULL) {
    printf("libusb_open() failed\n");
    return -1;
}

libusb_open_device_with_vid_pid 内部把「取列表、遍历、匹配、打开、释放列表」全做完，代码只剩一行。代价是总线上有两块一模一样的屏时，它只打开先找到的那块。我们这个场景只有一块屏，够用。调试阶段两份都写更舒服：先用它快速跑通，等要处理多设备竞争时再换回 libusb_open 配 bus_number + device_address 精确定位。

第三种，从已打开的文件描述符封装进来：

c
fd = open(device_name, O_RDWR);
if (fd < 0) {
    printf("Error could not open %s: %s\n", device_name, strerror(errno));
    return 1;
}

r = libusb_wrap_sys_device(NULL, fd, &handle);
if (r) {
    printf("Error wrapping device: %s: %s\n", device_name, libusb_strerror(r));
    close(fd);
    return 1;
}

libusb_wrap_sys_device 接的是 /dev/bus/usb/001/005 这种 usbfs 节点，适合权限已经由外部处理好、或者你想自己控制 open 的时候。两个坑：fd 关掉之后 handle 就废了，close(fd) 之前必须 libusb_close(handle)；同一路径的 fd 已经被 libusb 接管过就别再 wrap，会冲突。libusb_open 失败最常见的返回值是 LIBUSB_ERROR_ACCESS，本质是 usbfs 节点权限不够。我们的程序用 root 跑，所以这个坑一直没踩到。非 root 跑的话，要么加 udev 规则改权限，要么 sudo。

抢接口：detach 内核驱动 #

设备打开成功，不代表能读数据。内核的 HID 驱动早就把接口 0 认领了，你直接 libusb_interrupt_transfer 会拿到 LIBUSB_ERROR_IO，或者干脆读不到东西。步骤是先问再摘：

c
if (libusb_kernel_driver_active(handle, hid->interface_number)) {
    printf("Kernel Driver Active\n");
    r = libusb_detach_kernel_driver(handle, hid->interface_number);
    if (r == 0) {
        printf("Detach Kernel Driver\n");
        kernelDriverDetached = 1;
    } else {
        fprintf(stderr, "Error detaching kernel driver.\n");
        return -1;
    }
}

libusb_kernel_driver_active 检查指定接口上有没有内核驱动绑定，1 表示有，0 表示没有，负数表示查询失败。对 HID 设备来说返回值基本永远是 1，因为 hid-generic 一定会绑上去。libusb_detach_kernel_driver 成功返回 0，它摘的是整个接口，不是某个端点，接口上所有端点从这一刻起都归你。kernelDriverDetached 这个标志位很关键，程序退出前必须还回去：

c
exit:
    if(kernelDriverDetached){
        //恢复驱动绑定，否则鼠标不可用
        libusb_attach_kernel_driver(handle, hid->interface_number);
    }

    libusb_close(handle);

不还的后果是这块屏在当前系统里变成哑设备：内驱没绑上，/dev/input/eventX 消失，桌面触摸完全失效，只能拔插或者重启恢复。调试时程序崩溃退出，attach 不会执行，所以你会遇到「改了几行代码重跑，触摸屏不响应了」，拔插一次即可。顺序不能反：libusb_attach_kernel_driver 必须在 libusb_release_interface 之后、libusb_close 之前。接口还占着就 attach，内核会拒绝。

claim 接口 #

摘掉驱动之后才轮到 claim，这一步告诉 libusb「这个接口归我管，别让别人碰」：

c
r = libusb_claim_interface(handle, hid->interface_number);
if (r != 0){
    fprintf(stderr, "Error claiming interface.\n");
    goto exit;
}

interface_number 就是上一章打印出来的 bInterfaceNumber，我们这块屏是 0。claim 失败最常见的原因是 LIBUSB_ERROR_BUSY，接口已经被人声明过了。三种情形：上一次运行的程序没退干净、内核驱动没摘掉、同进程里别处声明过。有个概念要清楚：libusb 会自动声明接口上的所有端点，不需要也无法单独 claim 一个端点。所以 claim 到接口 0，端点 0x82 就自动可用。用完要还：

c
r = libusb_release_interface(handle, hid->interface_number);
if (0 != r){
    fprintf(stderr, "Error releasing interface.\n");
}

多接口设备怎么挑 #

我们这块屏只有一个接口，bInterfaceNumber 固定是 0，闭眼填都行。换成多接口的复合设备，比如带触摸的键盘、带触摸板的一体机，就必须挑对。看三个字段的组合：

判据 触摸屏的值 含义
bInterfaceClass 3 HID 类
bInterfaceSubClass 0 无引导子类
bInterfaceProtocol 0 无固定协议

键盘是 class 3 / subclass 1 / protocol 1，鼠标是 class 3 / subclass 1 / protocol 2，触摸屏落在 class 3 / subclass 0 / protocol 0，或者 subclass 1 / protocol 0。光看这三个字段不够保险，最终判据是接口上的 HID 报告描述符里有没有 Digitizer / Touch Screen。系统里也有现成的口子佐证：

bash
root@SOM-RK3399v2:/etc/profile.d# cat /sys/bus/usb/devices/1-1.2/1-1.2\:1.0/
0003:1A86:E5E3.0007/  bInterfaceNumber      bInterfaceSubClass    driver/               modalias
authorized            bInterfaceClass       bInterfaceProtocol    bNumEndpoints         ep_82/

1-1.2:1.0 这个目录名里的 .0 就是接口号 0，冒号前那个 1 是配置号。bInterfaceNumber 文件里的值也是 0，两处对得上。目录里直接能看到 ep_82/，这是端点目录，第五章细说。

libusb_open 之后、libusb_claim_interface 之前，设备处于半自由状态：接口还没被独占，但内核驱动已经被你摘了。这段时间别做耗时操作，比如大量 printf 或 sleep。我们的代码里这段只有两句，实际耗时微秒级。如果你在这里加了日志、加了延时，触摸中断会在这段时间丢失，表现为「刚开始读之前总会漏掉几个包」。读循环里也别在每包之间写文件或者打重日志，理由一样。

五、端点与传输方式的选择 #

设备找着了、接口也占上了，剩下就是「从哪读、怎么读」。答案全在端点描述符里。

端点地址的编码 #

这是本篇最容易搞错的知识点。bEndpointAddress 一个字节，不只是一个编号：

位段 掩码 含义
bit7 0x80 方向：1 = IN（设备→主机），0 = OUT（主机→设备）
bit6~bit4 0x70 保留，恒 0
bit3~bit0 0x0F 端点号，0~15

我们的触摸屏端点地址是 0x82，拆开看：

text
0x82 = 1000 0010
       ^      ^
       |      +--- 低4位 0010 = 端点号 2
       +---------- 最高位 1 = IN，设备到主机

所以 0x82 读作「端点 2，方向 IN」。读触摸数据必须用它，因为数据从设备流向主机。

方向搞反写成 0x02（端点 2，OUT），后果有两层。一是 libusb_interrupt_transfer 会去一个根本不存在的 OUT 方向等数据，等不到，超时或者直接报错。二是就算设备真有 OUT 端点 2，你发出去的数据也是主机发给设备，跟读数据完全不是一回事。

这就是为什么代码里 hid->endpoint_address 是从描述符里抄出来的常量，不是自己拼的。抄的时候把方向位一起抄下来，别手抖只写端点号。

判方向用位运算最不容易错：

c
if (ep_addr & 0x80) {
    /* IN，读方向 */
} else {
    /* OUT，写方向 */
}

端点号用 ep_addr & 0x0F 取。别用 ep_addr - 0x80，那样对 OUT 端点就错了。

传输类型的编码 #

bmAttributes 的低 2 位决定端点类型：

bit[1:0] 类型 对应 API 典型用途
00 控制传输 libusb_control_transfer 枚举、读描述符、类请求
01 等时传输 等时传输接口 音频、视频流
10 批量传输 libusb_bulk_transfer U 盘、打印机、大块数据
11 中断传输 libusb_interrupt_transfer 键盘、鼠标、触摸屏、HID 报告

我们的端点 bmAttributes 是 0x03，二进制 11，中断传输。所以代码里必须用 libusb_interrupt_transfer，不能换成 bulk 版本。

用错 API 的表现很明确：拿 bulk 去读中断端点，内核返回 LIBUSB_ERROR_IO，日志里就是 Input/Output Error。反过来拿 interrupt 读批量端点，部分情况能过，但行为没保证，别赌。

HID 设备基本都走中断传输，这是 HID 规范的约定。中断传输的语义是「主机按 bInterval 周期轮询」，不是设备主动推。所以哪怕手指一直不动，端点照样被周期性查询，只是没有新数据时返回 NAK。

端点信息从哪来 #

三种办法，从可靠到方便排。

办法一，读 sysfs，不需要写代码：

bash
root@SOM-RK3399v2:/# cat /sys/bus/usb/devices/1-1.2/
1-1.2:1.0/           bDeviceProtocol      bNumInterfaces       descriptors          driver/              manufacturer         ep_00/               idProduct            busnum               devpath              idVendor

接口目录下会列出端点目录，名字就是端点地址的十六进制：

bash
root@SOM-RK3399v2:/# ls /sys/bus/usb/devices/1-1.2/1-1.2:1.0/ | grep "ep"
ep_82

ep_82 就是端点 0x82。目录名里的十六进制直接对得上描述符，这是最省事的交叉验证。顺带说清 1-1.2 这个路径：前面是总线拓扑，插拔换口会变。dmesg 里搜 usb 1-1.2 能看到它被枚举时的完整日志。目录里的 ep_00 是枚举设备时用的默认控制端点，不算在 bNumEndpoints 里。

办法二，让程序自己打。上一章 print_endpoint 干的就是这事，输出里 bEndpointAddress: 82h 那行。这最不会出错，因为值是从内核读上来的，不是你手抄的。办法三，usbmon 抓包对照，抓到的 URB 里端点字段同样是 0x82，三方对得上才算确认。

缓冲区开多大 #

wMaxPacketSize 是单个包的上限，64 字节。但一次中断传输有时凑不满一个包，有时正好一个包。所以缓冲区不能按 64 开，要按实际报告长度开。报告长度 52 有两个来源互相印证，一是 usbmon 抓到的实际长度：

text
ffffffc0c88dab00 1925775309 C Ii:1:004:2 0:1 52 = 01010075 09080930 00000000 00000000 00000000 00000000 00000000 00000000
                               |__ 输入       |_______ 实际读取的长度

Ii:1:004:2 里最后的 2 是端点号，52 是这一次传输的实际字节数。二是 hids 数组里那个常量。两个值一致，就可以放心用。

c
unsigned char data[64] = {0};
...
r = libusb_interrupt_transfer(handle, hid->endpoint_address, data, hid->report_length, &length, 0);

data 开 64 是留余量，实际交给 libusb 的长度是 hid->report_length（52）。两个数别搞混：数组大小决定不越界，传参长度决定内核给你多少。传参长度写大了（传 64 而实际报告 52）不报错，length 返回 52，剩下 12 字节保持 0。写小了（传 32）内核直接 LIBUSB_ERROR_OVERFLOW，一个字节都拿不到。

零超时的含义 #

libusb_interrupt_transfer 最后一个参数是超时，单位毫秒。传 0 表示无限等待，直到有数据或者出错才返回。这个选择对调试友好，手指不碰屏程序就静静挂着，不刷屏。代价是设备被拔掉时这个调用会长时间不返回，Ctrl+C 也不一定立刻生效。生产代码给一个具体超时更稳，比如 100ms 配循环重试。这里为了看清「按一下出一个包」的对应关系，用了无限等待。

六、读取数据的完整代码 #

前面几章的零件，这一章装成一台完整的机器。整份代码在 /opt/libusb/usb_test.c，编译一条命令。下面按执行顺序拆。

全局量与结构体 #

c

#include <stdint.h>

rcv_exit 必须是 volatile sig_atomic_t，不是普通 int。少了 volatile，编译器能把循环里的判断缓存进寄存器，Ctrl+C 之后循环永远不退出。两个 gadget_*_logical_maximum 从模拟屏描述符的 LOGICAL_MAXIMUM (0x7fff) 来，第七章用它做缩放。

hids[] 下标 0 就是一直在用的 wch.cn 那块，每个字段从描述符手算，过程第七章讲。用指定初始化器 [0] = {...} 写，顺序错了编译器也不会静默错位。查找用 sizeof(hids) / sizeof(hids[0]) 算长度，别写死 3。

读循环的主体 #

c
static int interrupt_data_rw(uint16_t vendor_id, uint16_t product_id, const char *gadget_device_name)
{
    int kernelDriverDetached = 0;
    unsigned char data[64]={0};
    int length = 0;
    int r,j,fd_gadget = 0,fd_event = 0;
    libusb_device_handle *handle;
    struct touch_screen_report_t report;
    const struct hid_descriptor_t *hid = NULL;

    for(int i=0; i< sizeof(hids) / sizeof(hids[0]); i++){
        if((hids[i].vid == vendor_id) && (hids[i].pid == product_id)){
            hid = &hids[i];
        }
    }
    if(!hid){
        printf("Error please config hid descriptor info for usb device vid:0x%x pid:0x%x \n", vendor_id, product_id);
        return -1;
    }

    handle = libusb_open_device_with_vid_pid(NULL, vendor_id, product_id);
    if (handle == NULL) {
        printf("libusb_open() failed\n");
        return -1;
    }

    /* 驱动必须解绑定，否则数据由驱动程序处理 */
    if(libusb_kernel_driver_active(handle, hid->interface_number)){
        printf("Kernel Driver Active\n");
        r = libusb_detach_kernel_driver(handle, hid->interface_number);
        if (r == 0) {
            printf("Detach Kernel Driver\n");
            kernelDriverDetached = 1;
        }else{
            fprintf(stderr, "Error detaching kernel driver.\n");
            return -1;
        }
    }
    r = libusb_claim_interface(handle, hid->interface_number);
    if (r != 0){
        fprintf(stderr, "Error claiming interface.\n");
        goto exit;
    }

    if(gadget_device_name){
        fd_gadget = open(gadget_device_name, O_RDWR, 0666);
        if (fd_gadget < 0) {
            printf("Error could not open usb gadget device %s: %s\n", gadget_device_name, strerror(errno));
            return 1;
        }
    }
    fd_event = create_touch_screen();

    while(!rcv_exit){
        memset(data, 0, sizeof(data));

        /* 中断方式读取端点数据，超时设为0无限等待，直至有值 */
        r = libusb_interrupt_transfer(handle, hid->endpoint_address, data, hid->report_length, &length, 0);
        if ((r < 0) || (length == 0)){
            printf("bulk recive error,r:%s length:%d\n", libusb_strerror(r),length);
            usleep(500000);  // 单位微秒
        }else{
            printf("receive data:\n");
            for(j=0; j<length; j++) {
                printf("0x%x ",data[j]);
            }
            printf("\n");

            r = parse_usb_package(hid,data,&report);
            if(fd_gadget > 0 && r == 0){
               send_usb_packet(fd_gadget,&report);
            }
            if(fd_event > 0 && r == 0){
               touch_screen_pressed(fd_event, report.x, report.y, report.buttons);
            }
        }
    }

    if(fd_gadget > 0){ close(fd_gadget); }
    if(fd_event > 0){ close(fd_event); }

    r = libusb_release_interface(handle, hid->interface_number);
    if (0 != r){
        fprintf(stderr, "Error releasing interface.\n");
    }

    exit:
        if(kernelDriverDetached){
            //恢复驱动绑定，否则鼠标不可用
            libusb_attach_kernel_driver(handle, hid->interface_number);
        }
        libusb_close(handle);

    return r;
}

detach 失败时直接 return -1，没有 libusb_close(handle)，这是个资源泄漏。进程马上退，影响不大，严格写应该走 goto exit。

fd_gadget 是写到 PC 的通道，fd_event 是本地 uinput 虚拟设备。两个都可以不要：不给 -o 就不开 gadget，create_touch_screen 失败返回 -1 也不中断流程。这是有意的设计，方便分步验证。

memset 每轮清一次。不清的后果是这一包只有 52 字节而缓冲区里还留着上一包残留时，length 之外的字节会污染日志，看着像多发了一堆 0。(r < 0) || (length == 0) 两个条件都要判。前者是传输失败，后者是传输成功但一个字节都没有。设备返回 NAK 时 libusb 会给出 0 长度。日志里那句 bulk recive error 是复制粘贴留下的措辞，实际走的是中断传输，别被这两个字带偏。出错后 usleep(500000) 睡半秒再重试，避免设备刚拔出时疯狂刷错误日志，代价是设备拔了要半秒才知道。

清理顺序是 close 输出设备 → release 接口 → attach 驱动 → close handle。attach 在 release 之后，这点前面强调过，这里就是它的落点。

解析与转发 #

解析函数把报告字节拆成按键和坐标：

c
static int parse_usb_package(const struct hid_descriptor_t *hid,const char *data, struct touch_screen_report_t *report)
{
    if(!hid){
        printf("Error parse usb package, invalid hid descriptor.\n");
        return -1;
    }

    // logical_minimum-logical_maximum 映射到 0~0x7fff
    double x_scale =  1.0 * (gadget_x_logical_maximum-0) / (hid->x_logical_maximum - hid->x_logical_minimum);
    double y_scale =  1.0 * (gadget_y_logical_maximum-0) / (hid->y_logical_maximum - hid->y_logical_minimum);

    report->buttons = (data[hid->btn_offset/8] &  (1<< hid->btn_offset%8)) >> (hid->btn_offset%8);
    report->x = (data[hid->index_x_low] | data[hid->index_x_high] << 8) * x_scale ;
    report->y = (data[hid->index_y_low] | data[hid->index_y_high] << 8) * y_scale;
    return 0;
}

btn_offset 单位是位，所以取字节要 /8、取位要 %8。坐标是低字节在前，data[low] | data[high] << 8 拼成 16 位无符号数。

转发到 gadget，每次 5 字节：

c
static int send_usb_packet(int fd, struct touch_screen_report_t *report)
{
    char data[5] = {0,0,0,0,0};
    data[0] = report->buttons;
    data[1] = report->x & 0xFF;
    data[2] = (report->x >> 8) & 0xFF;
    data[3] = report->y & 0xFF;
    data[4] = (report->y >> 8) & 0xFF;

    if (write(fd, data, 5) != 5) {
        printf("Error write usb gadget device\n");
        return -1;
    }
    return 0;
}

write 返回值必须等于 5。hidg 设备的写入是原子报告，不足 5 字节的写入会被内核直接丢弃，返回值就是实际写入字节数。判 != 5 而不是 < 0，能抓到这个情况。

入口与信号 #

c

        switch (option) {
        case 'v': vid = strtoul(optarg, NULL, 0); break;
        case 'p': pid = strtoul(optarg, NULL, 0); break;
        case 'o': gadget_device_name = optarg; break;

    r = libusb_init(NULL);
    if (r < 0) return r;

    cnt = libusb_get_device_list(NULL, &devs);
    if (cnt < 0) { libusb_exit(NULL); return 1; }

    for (i = 0; devs[i]; i++){
        if(device_match_vid_pid(devs[i], vid, pid)){
            print_device(devs[i], handle);
            break;
        }
    }
    libusb_free_device_list(devs, 1);

    signal(SIGTERM, sig_handler);

getopt_long_only 允许 -vendid 这种单横线长选项，比标准 getopt_long 宽容。短选项串里 d: 声明了但从没处理，是历史残留。strtoul(optarg, NULL, 0) 第三个参数 0 表示自动识别进制，0x1a86 和 6658 都能用。print_device(devs[i], handle) 第二个参数此时是 NULL，函数内部自己 open 一次、打完再 close，这个设计让打印阶段完全独立，不影响后面真正干活的那次打开。

sig_handler 只把 rcv_exit 置 1，不做任何 libusb 调用。信号处理函数里调 libusb 不是异步安全的。Ctrl+C 之后循环不会立刻醒，因为 libusb_interrupt_transfer 超时是 0。退出方式是按下 Ctrl+C，再点一下触摸屏，让调用返回一次，循环才能看到 rcv_exit。这是本篇最反直觉的操作。

缩放：0~4096 到 0~32767 #

两边范围不同，必须等比映射：

c
double x_scale =  1.0 * (gadget_x_logical_maximum-0) / (hid->x_logical_maximum - hid->x_logical_minimum);
report->x = (data[hid->index_x_low] | data[hid->index_x_high] << 8) * x_scale;

1.0 * 这个写法不能省。C 里整数除法会截断，32767/4096 直接算成 7，坐标全挤到屏幕最顶上。这个缩放是线性的，真屏 0 → 模拟屏 0，真屏 2048 → 模拟屏 16383，真屏 4096 → 模拟屏 32767。精度不够是正常的，真屏 4096 个刻度映射到 32767 个刻度，每个真屏刻度对应 8 个模拟屏刻度，会有台阶感，但不影响使用。

按键位怎么取 #

按键是位域，不是整字节：

c
report->buttons = (data[hid->btn_offset/8] &  (1<< hid->btn_offset%8)) >> (hid->btn_offset%8);

btn_offset = 8 时，8/8 = 1 取字节 1，8%8 = 0 取 bit0，移位后得到 0 或 1。真屏的 Tip Switch 就是「手指是否接触」，报 1 表示按下。注意这里取的是 1 位，不是 3 位。左键、右键、中键是模拟屏那边的概念，真屏只有一个「接触」状态，我们把它映射成 bit0，PC 就当成左键。

八、遇到的实际问题与排查 #

这一章记的是实际调试中真踩到的坑，按出现频率排。

报错 Input/Output Error #

text
bulk recive error,r:Input/Output Error length:0

LIBUSB_ERROR_IO。三个原因，按排查顺序：

原因 怎么确认 怎么改
端点地址错 看 hids[] 里端点值 抄描述符里的 bEndpointAddress，含方向位
端点类型配错 看 bmAttributes 中断端点用 libusb_interrupt_transfer
内核驱动还在 看程序有没有打 Detach Kernel Driver 确认 detach 返回值

我们的场景里第一种最常见。0x82 写成 0x02、或者写成 0x2，都会得到这个错误。

报错 Overflow #

text
bulk recive error,r:Overflow length:0

LIBUSB_ERROR_OVERFLOW，意思是「设备要给的数据比你的缓冲区大」。唯一的修法是放大传参长度，传 hid->report_length 而不是写死 32。有个陷阱：把 report_length 写小了，比如填 32 而实际报告 52，得到的不是截断的 32 字节，而是一个字节都拿不到，全被丢弃。

卡在 Kernel Driver Active #

打印出 Kernel Driver Active 之后就没下文，说明 detach 失败。常见原因：接口号填错，detach 了一个不存在的接口；当前不是 root，没有权限；接口已经被别的用户态程序声明了。libusb_detach_kernel_driver 失败时我们直接 return，没有输出具体错误码，加一行 libusb_strerror(r) 就能看清是 NOT_SUPPORTED 还是 BUSY。

双击总是失灵 #

这是这套转发方案最明显的体验问题。PC 上双击，经常变成两次单击。原因在链路延迟：一个数据包从真屏读到、解析、转发给 gadget、再由 PC 接收，中间有多次进程调度和 USB 传输。Windows 判定双击靠两次点击的时间间隔，超过阈值（默认约 500ms）就算两次独立单击。

思路 做法 代价
缩短处理时间 屏蔽循环里的 printf 改一行，效果最直接
合并相邻点击 记录上一触摸点和时间戳，间隔过小时先补一次抬起再按下 需要自己调阈值
放宽系统阈值 Windows 控制面板 → 硬件和声音 → 设备和打印机 → 鼠标 → 双击速度，调到最慢 治标，换机器就得重设

printf 看着无害，但每包 52 个 printf 走 stdout，在慢速串口终端上能吃掉几十毫秒。先把日志关掉再看双击，往往就好了。

指针移动太快，选不中图标 #

这是物理尺寸的锅，不是代码问题。真屏小，PC 屏大，同一个相对位移在两块屏上的比例完全不同。解决办法是把真屏的 HDMI 也接到 PC，让 PC 用同一块屏显示，缩放比自然变成 1。

退出要按两下 #

Ctrl+C 之后程序不退出，得再点一下触摸屏。这不是 bug，是 libusb_interrupt_transfer 超时为 0 的必然结果：线程阻塞在等数据上，信号只是把 rcv_exit 置 1，循环体没机会执行下一轮判断。想让它立刻退，把超时改成 100ms 并处理 LIBUSB_ERROR_TIMEOUT，或者用 libusb_handle_events 那套异步模型。

触摸屏在系统里彻底失效 #

调试时程序崩溃（段错误、Ctrl+Z 挂起后 kill），libusb_attach_kernel_driver 没执行，内核驱动回不来。表现是 /dev/input/eventX 消失，桌面完全没触摸反应。恢复办法两个：拔插一次 USB 线，或者重启。这也是为什么 exit: 标签那段代码必须写在所有异常路径的汇合处。

九、性能与稳定性 #

这套方案能跑起来，但离「稳定可用」还有距离。这一章讲清楚瓶颈在哪、怎么量、怎么改。

一轮读取的耗时构成 #

环节 典型耗时 能不能优化
真屏中断上报 1~8ms 不能，物理限制
libusb_interrupt_transfer 返回 微秒级 已经是最快的同步 API
52 字节的 printf 循环 1~50ms 能，直接删掉
解析与缩放 微秒级 不用管
写 /dev/hidg2 几十微秒到几毫秒 取决于 PC 侧取数据的速度
gadget 经 USB 上报给 PC 1~8ms 不能

耗时的大头是两处：真屏 bInterval 决定的最快 1ms 轮询间隔，以及那串 printf。bInterval = 1 对全速设备意味着每 1 个微帧（1ms）轮询一次，理论上限 1000 包/秒，实际到不了，因为手指动作本身就稀疏。

关掉 printf 的收益 #

这是改动最小、收益最大的一条。循环里那段每包输出 52 个数字，在 HDMI 终端上看着很快，通过串口看就慢得明显。实测关掉之后，双击成功率从「经常失灵」变成「偶尔失灵」。要留日志就攒着批量输出，或者加个开关：

c
if (verbose > 1) {
    printf("receive data:\n");
    for(j=0; j<length; j++) printf("0x%x ",data[j]);
    printf("\n");
}

verbose 在参数里控制，跑正式场景时传 0。

超时该怎么设 #

同步接口传 0（无限等）适合观察，不适合长期运行。设备拔掉时线程卡死、Ctrl+C 不退、没法做分级重试，三个毛病都来自这个 0。

c
r = libusb_interrupt_transfer(handle, hid->endpoint_address, data, hid->report_length, &length, 100);
if (r == LIBUSB_ERROR_TIMEOUT) {
    continue;   /* 这一轮没数据，正常，继续等 */
}
if (r < 0) {
    /* 真错误，计数并决定要不要退出 */
}

100ms 是个折中：比 bInterval 大两个数量级，不会误判；比人手反应时间小，不影响体验。LIBUSB_ERROR_TIMEOUT 不是故障，手指没碰屏时它每秒会出现 10 次。

断线重连 #

现在的代码拔掉设备就只剩刷屏报错，插回去也不会自动恢复。要支持热插拔，得重新走一遍「找设备 → 摘驱动 → claim」。一个折中的做法是外层套重启循环：

bash
#!/bin/bash
while true; do
    ./usb_test -v 0x1a86 -p 0xe5e3 -o /dev/hidg2
    sleep 1
done

粗糙，但比自己实现热插拔可靠。libusb_hotplug_register_callback 那套更正规，属于异步模型的范畴，同目录《libusb 编程：从同步到异步》里讲。

多触点数据的完整性 #

我们的解析只取第一个触摸点，六指同时按时后面五个点的数据读上来了但没用上。真屏的报文布局是「字节 0 报告 ID → 字节 1 Tip Switch 与保留位 → 字节 2~3 第 1 点 X → 字节 4~5 第 1 点 Y → 后续点按描述符布局重复 → 最后一字节是当前触摸点个数」。模拟屏那边一次只接受 5 字节、单点报告，所以就算解析出六点也发不出去。真要做多点，两边描述符都得改。

稳定性检查清单 #

检查项 通过标准
拔掉真屏 程序不崩，日志有明确报错，不刷屏
拔掉 Type-C 写 gadget 失败被捕获，不影响读循环
Ctrl+C 在 1 秒内退出（配合超时改造）
正常退出 真屏触摸功能恢复，/dev/input/eventX 重新出现
连续运行 1 小时 无内存增长，无句柄泄漏
双击 成功率高于 90%

「正常退出后触摸功能恢复」这条最容易被忽略。开发阶段程序崩溃几次，屏就哑了，还得拔线。

2 搭 gadget，产生 /dev/hidg2 hid_keyboard_mouse.sh ls /dev/hidg*
3 取设备列表 main 打印出 Dev (bus 1, device 4)
4 匹配 VID/PID device_match_vid_pid 打印出 1A86 - E5E3

这张表的价值在排查：出问题时从上往下对，第一个不满足的行就是故障点。几个实际的对应关系：第 3 步就停住说明设备没插好或者 VID/PID 打错；第 6 步没打印说明内核驱动没绑上或者接口号填错；第 8 步报 Input/Output Error 是端点地址或传输类型错；第 8 步报 Overflow 是缓冲区传参太小；第 10 步 write 返回负数是 /dev/hidg2 不存在或权限不对；第 11 步没反应但前面全对，说明 PC 端没识别 gadget，检查 Type-C 线和 UDC。

三个环境变量的坑 #

/sys/kernel/config 必须挂载过 configfs，否则 gadget 建不起来。开机脚本第一句就是检查这个。/dev/hidg2 需要 root 权限写入，非 root 用户要么加 udev 规则，要么用 sudo。/dev/bus/usb/* 的权限同理。我们的程序用 root 跑，所有权限问题都被掩盖了，换普通用户跑会集中爆发。

一份可对照的最小验证序列 #

不想一次跑完整程序，可以按顺序做这四步，每步都用现成命令：

bash
# 1. 设备在不在总线上
lsusb | grep 1a86

# 2. 端点地址对不对
ls /sys/bus/usb/devices/1-1.2/1-1.2:1.0/ | grep ep

# 3. 报告描述符是不是触摸
cat /sys/kernel/debug/hid/0003\:1A86\:E5E3.0007/rdesc | head -c 100

# 4. gadget 就绪没
ls -l /dev/hidg2

四条命令全过，再跑 usb_test，问题范围就窄到代码里了。

十一、可复用的代码结构 #

这套代码不止能读触摸屏。把设备相关的常量抽出去，剩下的骨架能直接套给任何 HID 设备。

骨架的分层 #

层 职责 和具体设备的关系
枚举层 取列表、匹配、打印描述符 完全通用
接入层 open、detach、claim、release、attach 完全通用，只需接口号
传输层 按端点类型选 API 收发 通用，只需端点地址和长度
解析层 原始字节 → 业务结构体 设备相关，靠描述符表
输出层 业务结构体 → 目标格式 场景相关

前三层一行不用改。第四层就是 hids[] 那张表，换设备换表。第五层看你要往哪送，写 gadget、写 uinput、发网络都行。

把设备参数外置 #

当前 hids[] 是编译期常量，加一款屏就要重编。想做成通用的，可以改成从配置文件读，或者再往前走一步，运行时解析 HID 报告描述符，自动算出 btn_offset、index_x_low 这些值。那需要一个完整的 HID 描述符解析器，工作量不小，但一次投入之后任何 HID 设备都能自动适配。

按当前需求，三款屏写死一张表是最省事的。要支持第四款，加一行 [3] = { 0x1234, 0x5678, 0x81, 64, 8, 3, 4, 5, 6, 0, 0x0fff, 0, 0x0fff, 0 },，前提是先把那款屏的描述符读出来，按第七章的表填。

复用时的替换点 #

顺序 改什么 在哪
1 VID/PID 命令行 -v -p
2 接口号 hids[] 最后一个字段
3 端点地址 hids[] 第 3 个字段，带方向位
4 报告长度 hids[] 第 4 个字段
5 各字段索引 hids[] 中间几个字段
6 逻辑范围 hids[] 后四个字段
7 输出格式 send_usb_packet

前六项都是填表，只有第七项要写代码。

一个反向用法 #

这套骨架也能用来「发」数据给设备，不只是读。把 libusb_interrupt_transfer 换成 OUT 方向的端点：

c
/* ep_out 是设备描述符里方向位为 0 的端点 */
r = libusb_interrupt_transfer(handle, ep_out, buf, len, &sent, 1000);

其余结构（枚举、claim、释放）完全不变。差别只在端点方向和传输方向，这也是第五章那个方向位为什么重要的原因。

同理，控制传输走 libusb_control_transfer，参数是 bmRequestType / bRequest / wValue / wIndex，适合发标准请求和类请求。批量传输走 libusb_bulk_transfer，适合大块数据。

十二、易错点速查 #

最后收一份清单，都是这次实战里真踩过或者差点踩到的。

端点与传输 #

现象 原因 修法
Input/Output Error 端点地址方向位写反 0x82 不能写成 0x02
Input/Output Error 端点类型和 API 不匹配 中断端点用 interrupt 版
Overflow 传参长度小于实际报告 传 report_length，别写死
读到全 0 端点地址指向了别的端点 核对 bEndpointAddress
读不到数据也不报错 内核驱动还占着接口 检查 detach 是否执行

接口与驱动 #

现象 原因 修法
LIBUSB_ERROR_BUSY 接口已被占用 杀残留进程，确认 detach 成功
LIBUSB_ERROR_ACCESS usbfs 节点权限不够 root 或 udev 规则
触摸屏在系统里失效 没执行 attach 拔插恢复，检查 exit: 路径
多接口设备读错数据 接口号填错 按 class/subclass/protocol 挑

gadget 侧 #

现象 原因 修法
/dev/hidg2 不存在 gadget 没建 跑 hid_keyboard_mouse.sh start
PC 看不到设备 UDC 没写 echo fe900000.dwc3 > UDC
PC 收到但没反应 报告格式不匹配 按模拟屏描述符排 5 字节
write 返回小于 5 报告长度没对齐 固定写满 report_length
do_stop 报错 ${gadaget} 拼写错 改成 ${gadget}

解析与逻辑 #

现象 原因 修法
坐标全是 0 索引没算报告 ID 真屏数据从字节 1 开始
坐标缩放成整数倍 整数除法截断 乘 1.0 转浮点
按键取不出来 btn_offset 当字节用了 单位是位，要 /8 和 %8
坐标超出屏幕 逻辑范围填错 真屏 0x1000，模拟屏 0x7fff
只认第一个触摸点 代码只解析了点 1 扩成数组，两边描述符一起改

运行时 #

现象 原因 修法
Ctrl+C 不退出 超时为 0 卡在传输 再点一下屏，或改有限超时
双击失灵 处理链路太长 关 printf，或放宽系统阈值
指针移动过快 两块屏物理尺寸不同 真屏 HDMI 也接 PC
拔设备后狂刷错误 没有退避 usleep 或计数退出
运行一小时后变慢 日志或句柄堆积 检查循环里有没有分配

六条最容易忘的 #

  1. bEndpointAddress 的 bit7 是方向，抄的时候连带方向位一起抄。
  2. bmAttributes 的低 2 位决定用哪个传输 API，不是随便挑。
  3. claim 之前必须 detach 内核驱动，close 之前必须 attach 回去。
  4. 报告 ID 会让所有字节索引偏移 1，真屏有、模拟屏没有。
  5. 整数除法会截断，缩放必须乘 1.0。
  6. 同步接口的超时 0 是无限等，不是「不超时」。

这六条吃透了，换一块 HID 设备也能一次跑通。
