这篇只讲一件事：怎么在用户态直接跟一个 USB 设备说话，全程不写内核驱动。

讲什么：libusb 的编程模型、初始化与枚举、打开与声明接口、同步传输（批量/控制/中断）、异步传输、事件循环、资源释放、无驱方案的边界，结尾给一份能对着改的完整例子。

不讲什么：USB 协议本身的字段细节（描述符布局、令牌包、握手包怎么走线）；libusb 的编译与交叉编译（同目录另一篇专讲）；内核驱动怎么写（那是《编写一个 USB 驱动》的地盘）。

跨篇指路：装库、编库、交叉编译看《libusb 安装与交叉编译》；想看真实设备跑通的案例看《libusb 实战》；串不上就抓包，看《usbmon 抓包》。

一、libusb 的编程模型 #

先把定位说清。同一个 USB 设备，两条路可以走。

走内核驱动：你写一个 .ko，注册 usb_driver 结构，实现 probe/disconnect，把设备挂到某个子系统上（tty、net、input、v4l2……）。系统认可它，别的程序通过标准设备节点就能用。代价是你得编进内核树，跟着内核版本跑，insmod 还得有权限。

走 libusb：不注册任何东西。库在用户态拿 /dev/bus/usb/BBB/DDD，用 ioctl(USBDEVFS_*) 把 URB 递给内核的 usbfs 层，数据到了再收回来。你的程序就是一个普通进程，make 完就能跑，不需要 root 装模块（只需要设备节点的读写权限）。

两条路的根本差别就一句：内核驱动让设备变成系统的一部分，libusb 只是让进程占用设备。

1.1 固定六步 #

libusb 把一次设备访问拆成六步，顺序不能乱。后面所有 API 都只是往这六步里填内容。

步骤 函数 你拿到什么 漏了会怎样
1 初始化 libusb_init() libusb_context 后面每个调用都返回 LIBUSB_ERROR_NOT_INITIALIZED
2 枚举 libusb_get_device_list() libusb_device** 数组 没有设备指针，打不开
3 打开 libusb_open() libusb_device_handle 没有句柄，发不了传输
4 声明接口 libusb_claim_interface() 该接口的独占使用权 内核驱动还占着，传输报 LIBUSB_ERROR_BUSY
5 传输 libusb_bulk_transfer() / libusb_submit_transfer() 等 数据 ——
6 释放 libusb_release_interface() / libusb_close() / libusb_free_device_list() / libusb_exit() 资源归还 句柄泄漏、设备下次打不开

写成代码骨架：

c
libusb_context       *ctx  = NULL;
libusb_device       **list = NULL;
libusb_device_handle *h    = NULL;
libusb_init(&ctx);                                /* 1 初始化 */
libusb_get_device_list(ctx, &list);               /* 2 枚举 */
/* 在 list 里按 vid/pid 挑一个，h 指向它 */
libusb_open(dev, &h);                             /* 3 打开 */
libusb_claim_interface(h, 0);                     /* 4 声明接口，0 是 bInterfaceNumber */
/* 5 传输：同步直接收发，异步 submit + handle_events */
libusb_release_interface(h, 0);                   /* 6 释放，顺序和申请相反 */
libusb_close(h);
libusb_free_device_list(list, 1);                 /* 1 表示顺便把 device 引用也放掉 */
libusb_exit(ctx);

1.2 对象层次 #

text
libusb_context                一次库会话，管事件循环、管 pollfd 集合
  └── libusb_device           设备本身，只读的描述信息 + 引用计数
        └── libusb_device_handle    打开后的句柄，能发起传输
              └── interface        接口，必须 claim 才能用
                    └── endpoint    端点，地址最高位决定方向

两个容易混的点：

  • libusb_device 不等于句柄。它只代表「系统里有这么个设备」，可以读描述符，但不能收发数据。要收发就得 libusb_open 出 handle。
  • 端点地址 bEndpointAddress 的 bit7 是方向位。0x81 是 IN 端点 1，0x01 是 OUT 端点 1。填传输函数时别让方向位和函数参数打架。

1.3 claim_interface 为什么是关键 #

六步里第 4 步最容易被忽略，但它决定了「无驱」能不能成立。

c
int r = libusb_claim_interface(h, 0);

这一句是向内核申请接口 0 的独占权。申请成功以后，内核里原本绑在这个接口上的驱动就不能再碰它了——usbfs 会把该接口从原驱动手里摘下来，之后的传输全部由你的进程发起。

所以：

  • 你 claim 过的接口，内核驱动那边就哑了。这也是为什么对 HID 键盘做实验会把手边的输入设备停掉。
  • claim 之前别的驱动（或另一个进程）正在用这个接口，会返回 LIBUSB_ERROR_BUSY。
  • 想从已被内核驱动占用的接口上抢过来，得先 libusb_detach_kernel_driver(h, 0)，或者一开始就 libusb_set_auto_detach_kernel_driver(h, 1) 让库自动摘。
  • 一个设备可以有多个接口。你只需要 claim 自己要用的那个，别的接口留给系统，互不影响。复合设备（键盘上带个音量旋钮）就是靠这个共存的。

释放时对称：libusb_release_interface() 之后内核驱动可以重新绑回去。

1.4 老 API 与新 API 的对应 #

网上流传的 libusb 教程一大半是 0.1 时代的，函数名是 usb_*，没有 context 概念，设备用两条链表遍历。1.0 改成了 libusb_*，链表换数组。看到老代码别慌，对着表改名就行。

libusb 0.1 libusb 1.0 差别
usb_init() libusb_init(&ctx) 0.1 是全局状态，1.0 有 context 可多实例
usb_find_busses() + usb_find_devices() libusb_get_device_list(ctx, &list) 两次扫描变一次取全表
usb_get_busses() / 全局 usb_busses 直接遍历 list 数组 链表换数组，->next 变下标
usb_open(dev) libusb_open(dev, &h) 返回值改成出参 + 错误码
usb_set_altinterface(h, alt) libusb_set_interface_alt_setting(h, if, alt) 1.0 多要一个接口号
usb_resetep(h, ep) 无 已被 clear_halt 取代
usb_reset(h) libusb_reset_device(h) 改名
usb_control_msg(...) libusb_control_transfer(...) 参数表一致
usb_bulk_write/read libusb_bulk_transfer(..., 方向, &n, t) 写读合一，方向靠标志
usb_interrupt_write/read libusb_interrupt_transfer(..., &n, t) 同上
usb_get_string_simple(h, idx, buf, len) libusb_get_string_descriptor_ascii() 自动挑语言 ID
usb_get_descriptor(h, type, idx, ...) libusb_get_descriptor(h, type, idx, ...) 同名同义
usb_get_descriptor_by_endpoint(...) 无便捷函数 用 control_transfer 手搓
无 libusb_detach_kernel_driver() 1.0 新增，无驱方案的门票
无 libusb_hotplug_register_callback() 1.0.16 起支持热插拔
无 libusb_alloc_transfer() / libusb_submit_transfer() 1.0 才有异步框架

老文档里两个坑：usb_bulk_write 和 usb_interrupt_read 被反复抄串行，批传输小节写的是中断读，中断传输小节还是中断读。真实签名是 usb_bulk_write / usb_bulk_read / usb_interrupt_write / usb_interrupt_read 四个，读写成对。看到哪份教程只列了两个，别跟着抄。

二、初始化与设备枚举 #

2.1 初始化 context #

c
libusb_context *ctx = NULL;
int r = libusb_init(&ctx);
if (r < 0) {
    fprintf(stderr, "libusb_init: %s\n", libusb_error_name(r));
    return -1;
}

三件事值得说：

  • ctx 是库会话。单设备、单线程的程序直接传 NULL，库内部用一个默认 context，后面所有调用也都能传 NULL。省事。
  • 只有要多个线程各用一套 context 才需要自己申请。多数程序不需要。
  • 初始化之后建议开日志，出问题时能看见库在干什么：
c
libusb_set_option(ctx, LIBUSB_OPTION_LOG_LEVEL, LIBUSB_LOG_LEVEL_WARNING);
/* 1.0.22 之前的老写法：libusb_set_debug(ctx, 3); */

结束时 libusb_exit(ctx)。传 NULL 清默认 context。调用它之前所有 handle 都得已经 libusb_close，所有 device list 都得已经 free。

2.2 取设备列表 #

c
libusb_device **list = NULL;
ssize_t cnt = libusb_get_device_list(ctx, &list);
if (cnt < 0) return -1;

cnt 是设备个数，list 是以 NULL 结尾的指针数组。数组里每个 libusb_device* 的引用计数都被加过，用完必须这样收：

c
libusb_free_device_list(list, 1);   /* unref_devices=1：连设备引用一起放 */

第二个参数填 1，等于对数组里每个设备都做一次 libusb_unref_device。填 0 的话，你打算留着的设备得自己 libusb_ref_device，否则数组一释放指针就悬空。

2.3 按 VID/PID 挑设备 #

c
#define VENDOR_ID   0x1234
#define PRODUCT_ID  0x5678
libusb_device *target = NULL;
for (ssize_t i = 0; i < cnt; i++) {
    struct libusb_device_descriptor d;
    if (libusb_get_device_descriptor(list[i], &d) < 0)
        continue;
    if (d.idVendor == VENDOR_ID && d.idProduct == PRODUCT_ID) {
        target = list[i];
        break;
    }
}
if (!target) {
    fprintf(stderr, "device %04x:%04x not found\n", VENDOR_ID, PRODUCT_ID);
    libusb_free_device_list(list, 1);
    libusb_exit(ctx);
    return -1;
}

libusb_get_device_descriptor 只读缓存在 libusb_device 里的那 18 字节，不产生 USB 流量，循环里放心调。

描述符里几个字段够你判断设备：

字段 含义 用途
idVendor / idProduct 厂商号 / 产品号 最常用的匹配条件
bcdUSB 支持的 USB 版本（BCD 编码） 分清 1.1 / 2.0 / 3.0
bDeviceClass 设备类 0x00 表示类信息在接口描述符里
bNumConfigurations 配置数 大于 1 时要选配置
iManufacturer / iProduct / iSerialNumber 字符串索引 0 表示没有，非 0 要再发请求取

只靠 VID/PID 不够时，还有这些定位手段：

c
uint8_t bus  = libusb_get_bus_number(dev);       /* 总线号 */
uint8_t addr = libusb_get_device_address(dev);   /* 设备地址 */
uint8_t port = libusb_get_port_number(dev);      /* 挂在哪号口 */

总线号 + 设备地址 就是 /dev/bus/usb/BBB/DDD 里的那两个数，插拔一次就变。设备序列号才是不变的身份，但取序列号要发控制传输，得先打开设备。

2.4 取字符串描述符 #

c
libusb_device_handle *h = NULL;
libusb_open(target, &h);
char manu[128] = {0}, prod[128] = {0}, sn[128] = {0};
if (d.iManufacturer)
    libusb_get_string_descriptor_ascii(h, d.iManufacturer, (unsigned char *)manu, sizeof(manu));
if (d.iProduct)
    libusb_get_string_descriptor_ascii(h, d.iProduct, (unsigned char *)prod, sizeof(prod));
if (d.iSerialNumber)
    libusb_get_string_descriptor_ascii(h, d.iSerialNumber, (unsigned char *)sn, sizeof(sn));

libusb_get_string_descriptor_ascii 内部先读语言 ID 表，再按第一个语言 ID 取值，最后把 UTF-16 转成 ASCII。所以非 ASCII 字符（比如中文厂商名）会被替换掉，要原始内容就得自己走 libusb_get_string_descriptor 拿 UTF-16 再转。

2.5 遍历配置、接口、端点 #

光有设备描述符不够，传输要用到接口号和端点地址，这些在配置描述符里。

c
struct libusb_config_descriptor *cfg;
if (libusb_get_config_descriptor(target, 0, &cfg) == 0) {   /* 0 = 第 0 个配置 */
    for (int i = 0; i < cfg->bNumInterfaces; i++) {
        const struct libusb_interface *itf = &cfg->interface[i];
        for (int a = 0; a < itf->num_altsetting; a++) {
            const struct libusb_interface_descriptor *id = &itf->altsetting[a];
            printf("itf %d alt %d class %02x eps %d\n",
                   id->bInterfaceNumber, id->bAlternateSetting,
                   id->bInterfaceClass, id->bNumEndpoints);
            for (int e = 0; e < id->bNumEndpoints; e++) {
                const struct libusb_endpoint_descriptor *ep = &id->endpoint[e];
                printf("  ep %02x attr %02x maxpkt %u interval %u\n",
                       ep->bEndpointAddress, ep->bmAttributes,
                       ep->wMaxPacketSize, ep->bInterval);
            }
        }
    }
    libusb_free_config_descriptor(cfg);
}

这段输出就是你的「设备地图」。拿到之后，接口号填 claim_interface，端点地址填传输函数。

端点的 bmAttributes 低两位决定传输类型，选哪个 API 全看它：

bmAttributes & 0x03 类型 用哪个 API
0 控制 libusb_control_transfer（端点 0，不在接口里列）
1 同步（isochronous） libusb_alloc_transfer(LIBUSB_TRANSFER_TYPE_ISOCHRONOUS)
2 批量（bulk） libusb_bulk_transfer
3 中断（interrupt） libusb_interrupt_transfer

2.6 老 API 的枚举写法 #

c
struct usb_bus *bus;
struct usb_device *dev;
int device_num = 0;
usb_init();            /* 初始化，必须先调 */
usb_find_busses();     /* 扫系统上的 USB 总线，返回总线数 */
usb_find_devices();    /* 扫每条总线上的设备，必须在 find_busses 之后 */
for (bus = usb_busses; bus; bus = bus->next) {
    for (dev = bus->devices; dev; dev = dev->next) {
        if (dev->descriptor.idVendor  == VENDOR_ID &&
            dev->descriptor.idProduct == PRODUCT_ID)
            device_num++;
    }
}

两个细节：早期版本要用 usb_get_busses() 拿链表头，后来的版本直接暴露全局变量 usb_busses（在 usb.h 里声明为 extern），函数就没用了。另外 usb_find_devices() 依赖 usb_find_busses() 的结果，顺序反了扫到零个设备。

2.7 一定要认接口类 #

光凭 VID/PID 打开设备时，设备若是复合设备，你操作的接口未必是想要的那个。稳妥做法是匹配接口类：

c
/* 找 bInterfaceClass == 0xFF（厂商自定义）的接口 */
int want_if = -1;
for (int i = 0; i < cfg->bNumInterfaces && want_if < 0; i++) {
    const struct libusb_interface_descriptor *d = &cfg->interface[i].altsetting[0];
    if (d->bInterfaceClass == 0xFF)
        want_if = d->bInterfaceNumber;
}

常见类码：0x03 HID、0x08 大容量存储、0x0A CDC 通信、0x0E 视频、0xE0 无线、0xFF 厂商自定义。自己设计的板子基本都落在 0xFF。

三、打开设备与声明接口 #

3.1 打开 #

c
libusb_device_handle *h = NULL;
int r = libusb_open(target, &h);
if (r < 0) {
    fprintf(stderr, "open: %s\n", libusb_error_name(r));
    return -1;
}

libusb_open 只做两件事：打开设备节点，读一遍设备描述符。它不碰接口，不动驱动，所以即使设备正被内核驱动用着，open 也能成功。

失败常见原因：

返回码 原因 处理
LIBUSB_ERROR_ACCESS 设备节点权限不够 加 udev 规则，或临时 sudo
LIBUSB_ERROR_NO_DEVICE 设备已经拔了 回枚举重来
LIBUSB_ERROR_BUSY 少见，多为别的进程 open 了同一个 查进程
LIBUSB_ERROR_NO_MEM 内核 usbfs 内存不足 查有没有泄漏的 URB

权限问题的正解是 udev 规则，别一直用 root 跑程序：

text
/etc/udev/rules.d/50-myusb.rules
SUBSYSTEM=="usb", ATTR{idVendor}=="1234", ATTR{idProduct}=="5678", MODE="0666"

改完 sudo udevadm control --reload-rules && sudo udevadm trigger，重新插拔。

3.2 设配置与备用设置 #

一个设备能有多个配置（configuration）。默认是 1 号，多数设备不用管。需要切的时候：

c
int cur = -1;
libusb_get_configuration(h, &cur);          /* 先读当前的，方便以后还原 */
if (cur != 1) {
    r = libusb_set_configuration(h, 1);     /* 参数是 bConfigurationValue */
    if (r < 0)
        fprintf(stderr, "set_configuration: %s\n", libusb_error_name(r));
}

libusb_set_configuration 必须在 claim_interface 之前调，而且切换配置会把已经 claim 的接口全断掉。设配置会重新枚举该设备的所有接口，代价不小，不要放进循环。

一个接口还可以有好几个 alt setting，用不同的带宽/端点组合，默认 bAlternateSetting = 0：

c
r = libusb_set_interface_alt_setting(h, 0, 1);   /* 接口 0 切到 alt 1 */

注意顺序：claim_interface 之后才能设 alt setting。

3.3 摘内核驱动 #

这是无驱方案的入场券。设备被内核驱动（usbhid、usb-storage、cdc_acm……）绑着时，直接 claim 会返回 LIBUSB_ERROR_BUSY。两种解法：

c
/* 手动摘，记得用完挂回去 */
if (libusb_kernel_driver_active(h, 0) == 1)
    libusb_detach_kernel_driver(h, 0);
libusb_claim_interface(h, 0);
/* ... 干活 ... */
libusb_release_interface(h, 0);
libusb_attach_kernel_driver(h, 0);        /* 挂回去，让系统恢复原样 */

c
/* 自动挡：让库在 claim 时自己摘，release 时自己挂 */
libusb_set_auto_detach_kernel_driver(h, 1);
libusb_claim_interface(h, 0);

手动挡能控制归还时机，自动挡代码短。做产品用手动挡，调试用自动挡。libusb_kernel_driver_active 在部分平台永远返回 0（比如 Windows 的 WinUSB 后端），别依赖它判断设备状态。

3.4 claim 的语义再确认 #

c
r = libusb_claim_interface(h, 0);
if (r < 0) {
    fprintf(stderr, "claim: %s\n", libusb_error_name(r));
    libusb_close(h);
    return -1;
}
  • 参数 0 是 bInterfaceNumber，不是接口下标，也不是端点号。复合设备里这个号是 0、1、2 中的一个，从配置描述符里读。
  • 同一个 handle 对同一个接口 claim 两次，有的实现返回成功（引用计数），有的返回 busy，别这么写。一个接口 claim 一次。
  • 一个 handle 可以 claim 多个接口，每个都配对 release。
  • claim 是按接口独占，不是按设备独占。一个进程聊接口 0，另一个进程聊接口 1，可以共存。

claim 成功那一刻起，这个接口上的传输就归你了。内核里原驱动收不到 URB，也就不会跟你抢数据。

四、同步传输：批量与控制 #

同步 API 的心智模型最简单：调一个函数，线程卡住，等这次传输彻底完成，函数返回。返回正数表示实际字节数，负数表示错误码。中间没有回调，没有事件循环。

代价也直白：传输期间这个线程什么也干不了。一次批量读 512 字节，超时给 1000ms，设备不发数据，线程就实打实卡 1000ms。

4.1 批量传输 #

批量传输用于「数据量大、不要求时间、但要保证不丢」的场合。U 盘、打印机、自定义高速采集板都用它。

c
#define EP_OUT     0x01
#define EP_IN      0x81
#define TIMEOUT_MS 1000
unsigned char buf[64];
int transferred = 0;
/* 写 */
int r = libusb_bulk_transfer(h, EP_OUT, buf, sizeof(buf), &transferred, TIMEOUT_MS);
if (r == 0 && transferred == (int)sizeof(buf))
    printf("wrote %d bytes\n", transferred);
else if (r == LIBUSB_ERROR_TIMEOUT)
    fprintf(stderr, "bulk write timeout, %d bytes done\n", transferred);
else
    fprintf(stderr, "bulk write: %s\n", libusb_error_name(r));
/* 读 */
r = libusb_bulk_transfer(h, EP_IN, buf, sizeof(buf), &transferred, TIMEOUT_MS);

参数表：

参数 含义 注意
dev_handle 打开的设备句柄 已 claim 过接口
endpoint bEndpointAddress bit7 决定方向，0x81 是 IN
data 缓冲区 长度至少 length
length 本次最多要传多少字节 可大于端点最大包长，底层自动拆包
transferred 出参，实际传了多少 超时/短包时也要看它
timeout 毫秒，0 表示不限 不限很危险，设备一挂线程就永久阻塞

返回值要分三档：

  • 0：传输成功。但不代表 transferred == length，短包在批量传输里是正常现象。
  • LIBUSB_ERROR_TIMEOUT：超时。此时 transferred 非 0 就说明已经传出去的部分是真的传了。做协议时这里要当心——你发了一半，对端已经在解析。
  • 其他负值：LIBUSB_ERROR_PIPE（端点 stall）、LIBUSB_ERROR_NO_DEVICE（拔了）、LIBUSB_ERROR_IO。

端点 stall 的处理：

c
if (r == LIBUSB_ERROR_PIPE) {
    libusb_clear_halt(h, EP_IN);       /* 清 halt，端点恢复可用 */
    /* 然后重试，或者按协议重发整包 */
}

4.2 控制传输 #

控制传输走端点 0，是所有 USB 设备都必须支持的那条「管理通道」。发标准请求（取描述符、设地址、设配置）、类请求、厂商自定义请求都走它。

c
unsigned char data[16] = {0};
int r = libusb_control_transfer(h,
                               0x40,        /* bmRequestType */
                               0x01,        /* bRequest */
                               0x0000,      /* wValue */
                               0x0000,      /* wIndex */
                               data, sizeof(data),
                               TIMEOUT_MS);
if (r < 0)
    fprintf(stderr, "ctrl: %s\n", libusb_error_name(r));

bmRequestType 一个字节塞了三段信息，是最容易填错的参数：

位 字段 取值
bit7 方向 0x00 主机→设备，0x80 设备→主机
bit6:5 类型 0x00 标准，0x20 类，0x40 厂商
bit4:0 接收者 0x00 设备，0x01 接口，0x02 端点，0x03 其他

库提供了宏，别手算位：LIBUSB_ENDPOINT_OUT（0x00）、LIBUSB_ENDPOINT_IN（0x80）、LIBUSB_REQUEST_TYPE_STANDARD（0x00）、LIBUSB_REQUEST_TYPE_CLASS（0x20）、LIBUSB_REQUEST_TYPE_VENDOR（0x40）、LIBUSB_RECIPIENT_DEVICE（0x00）、LIBUSB_RECIPIENT_INTERFACE（0x01）、LIBUSB_RECIPIENT_ENDPOINT（0x02）。

组合出来就是常见请求：

c
/* 取设备描述符：标准 + IN + 设备 */
libusb_control_transfer(h, 0x80, LIBUSB_REQUEST_GET_DESCRIPTOR,
                        (LIBUSB_DT_DEVICE << 8) | 0, 0, buf, 18, 1000);
/* 厂商请求，主机发数据给接口 */
libusb_control_transfer(h, 0x40, 0x05, 0x1234, 0, payload, 8, 1000);
/* 厂商请求，从接口读数据 */
libusb_control_transfer(h, 0xC0, 0x06, 0, 0, rbuf, 64, 1000);

wValue 和 wIndex 是 16 位字段，含义完全由设备固件定义。做自定义协议时我们习惯把 wValue 当命令码、wIndex 当寄存器地址，这只是约定。

返回值是实际传输的字节数，负数是错误。方向位和长度写矛盾（比如 IN 请求但长度填 0）会在主机侧就被拒，返回 LIBUSB_ERROR_INVALID_PARAM。

4.3 同步的坑 #

  • 超时设 0。timeout 传 0 表示无限等待。设备拔掉之后某些平台上这个调用会一直挂着不返回。跑自己机器上无所谓，做产品必须给有限值。
  • 忽略 transferred。返回 0 不等于全传了。协议依赖「必须收满 N 字节」时就得自己凑满：
c
static int read_full(libusb_device_handle *h, uint8_t ep, uint8_t *buf, int want, int tmo)
{
    int got = 0;
    while (got < want) {
        int n = 0;
        int r = libusb_bulk_transfer(h, ep, buf + got, want - got, &n, tmo);
        if (r < 0) return r;
        if (n == 0) return LIBUSB_ERROR_IO;   /* 设备不回数据了 */
        got += n;
    }
    return got;
}
  • 一个线程只能被一次传输占着。想让 UI 不卡、想让收和发同时进行，只能开线程或改用异步。这就是后面几章要解决的问题。

五、中断传输与轮询 #

中断传输这个名字容易骗人，它跟中断没关系。它是主机定时来问设备有没有事，靠的是「保留带宽 + 有界延迟」，不是设备真的发信号过来。

适合它的场合：数据量小（几个字节到 64 字节）、要求有确定响应时间，比如鼠标、键盘、自定义按键板、状态上报。

5.1 同步中断传输 #

c
#define EP_INT_IN  0x82
#define EP_INT_OUT 0x02
uint8_t buf[64];
int n = 0;
int r = libusb_interrupt_transfer(h, EP_INT_IN, buf, sizeof(buf), &n, 500);
if (r == 0) {
    /* buf[0..n-1] 是设备上报的数据 */
} else if (r == LIBUSB_ERROR_TIMEOUT) {
    /* 这段时间设备没东西上报，正常，继续下一轮 */
} else {
    fprintf(stderr, "intr: %s\n", libusb_error_name(r));
}

参数和 libusb_bulk_transfer 完全一致，只是底层用的传输类型不同。

对比项 批量传输 中断传输
带宽 抢剩余带宽，设备空闲时能跑满 主机预留，每帧/微帧固定配额
延迟 不保证 有上界，由 bInterval 决定
典型包长 512（HS）/ 64（FS） ≤64 字节
超时是否常态 说明设备没数据，要查 轮询里超时是常态，别当错误
适合 大文件、采集流 状态上报、按键、小命令

bInterval 在端点描述符里，全速设备单位是毫秒（1~255），高速设备是指数编码（2^(bInterval-1) 个微帧）。填 1 表示每个微帧都问一次——此时中断传输的实时性其实比批量还高。

5.2 轮询循环的写法 #

c
volatile int running = 1;
while (running) {
    uint8_t buf[64];
    int n = 0;
    int r = libusb_interrupt_transfer(h, EP_INT_IN, buf, sizeof(buf), &n, 200);
    if (r == 0 && n > 0) {
        handle_report(buf, n);
    } else if (r == LIBUSB_ERROR_TIMEOUT) {
        continue;                          /* 没数据，很正常 */
    } else if (r == LIBUSB_ERROR_NO_DEVICE) {
        break;                             /* 设备拔了，退出 */
    } else if (r == LIBUSB_ERROR_PIPE) {
        libusb_clear_halt(h, EP_INT_IN);   /* 端点 stall，复位重来 */
        continue;
    } else {
        fprintf(stderr, "intr: %s\n", libusb_error_name(r));
        break;
    }
}

三点经验：

  • 超时值别设太大。轮询的意义是「及时拿到」，200ms 超时意味着设备拔了你最多 200ms 后知道。设 5000ms 就等于反应迟钝。
  • 超时返回不算错误，别 break。很多新手在这里把循环退出了，然后说「设备偶尔失联」。
  • 这个循环独占一个线程。要同时做别的事，要么再开线程，要么转异步。

5.3 中断 OUT 与老 API #

中断 OUT 方向一样能发：

c
uint8_t cmd[8] = {0x01, 0x00, 0x00, 0x00, 0, 0, 0, 0};
int n = 0;
int r = libusb_interrupt_transfer(h, EP_INT_OUT, cmd, sizeof(cmd), &n, 100);

有些设备的 OUT 端点不回任何信息，n 就等于 sizeof(cmd)，返回 0。这类设备不需要读回执，发完就走。

0.1 时代的中断接口是 usb_interrupt_read / usb_interrupt_write，签名和批量那对完全一样：

c
int usb_interrupt_read(usb_dev_handle *dev, int ep, char *bytes, int size, int timeout);
int usb_bulk_write(usb_dev_handle *dev, int ep, char *bytes, int size, int timeout);

问题在于当年的教程在「批传输接口」和「中断传输接口」两节里抄了同样的内容，两节都写成 usb_bulk_write + usb_interrupt_read。按那份文档写代码，你会得到一个批写加一个中断读的怪组合。正确的四个函数是 usb_bulk_read、usb_bulk_write、usb_interrupt_read、usb_interrupt_write。

六、异步传输：libusb_transfer #

同步 API 的边界很清楚：一次只能有一个传输在飞，线程被占死。要做到高吞吐或低延迟，就得上异步。

异步的模型只有一句话：提交后立刻返回，完成后走回调。

text
libusb_alloc_transfer()      分配一个 transfer 对象
libusb_fill_bulk_transfer()  填参数，把 buffer 和回调挂上去
libusb_submit_transfer()     扔给库，立刻返回
        ↓  （库在后台收数据）
回调被调用，status / actual_length / buffer 都填好了
        ↓
要么处理完释放，要么 re-submit 继续收

submit 返回的时候数据还没到。所以 buffer 不能是栈上的临时数组，必须活到回调执行完。

6.1 transfer 的关键字段 #

c
struct libusb_transfer {
    libusb_device_handle *dev_handle;
    uint8_t              type;          /* BULK / INTERRUPT / CONTROL / ISOCHRONOUS */
    unsigned char       *buffer;        /* 数据缓冲区 */
    int                  length;        /* buffer 有多长 */
    int                  actual_length; /* 实际传了多少，回调里看这个 */
    int                  status;        /* 回调里判断成败 */
    int                  flags;
    int                  timeout;       /* 毫秒，0 = 不限 */
    libusb_transfer_cb_fn callback;
    void                 *user_data;    /* 状态通道，回调里拿回来 */
    unsigned char        num_iso_packets;
};

三个字段是核心：status 判成败，actual_length 取长度，buffer 取数据。user_data 是你唯一的状态通道，把所有上下文塞进去。

status 取值：

值 含义 处理
LIBUSB_TRANSFER_COMPLETED 正常完成 取数据
LIBUSB_TRANSFER_ERROR 传输出错 重提交或放弃
LIBUSB_TRANSFER_TIMED_OUT 超时 看协议，可重提交
LIBUSB_TRANSFER_CANCELLED 被取消 走清理流程
LIBUSB_TRANSFER_STALL 端点 stall clear_halt 后重提交
LIBUSB_TRANSFER_NO_DEVICE 设备没了 退出，别再提交
LIBUSB_TRANSFER_OVERFLOW 数据超过 buffer 加大 buffer

6.2 批量异步的流程 #

c
struct xfer_ctx { libusb_transfer *t; int done; };
static void LIBUSB_CALL bulk_cb(libusb_transfer *t)
{
    struct xfer_ctx *c = (struct xfer_ctx *)t->user_data;
    switch (t->status) {
    case LIBUSB_TRANSFER_COMPLETED:
        printf("got %d bytes\n", t->actual_length);   /* t->buffer 里是数据 */
        c->done = 1;
        break;
    case LIBUSB_TRANSFER_NO_DEVICE:
        c->done = 2;
        break;
    default:
        c->done = 2;
        break;
    }
}
int async_read_once(libusb_device_handle *h)
{
    struct xfer_ctx c = {0};
    c.t = libusb_alloc_transfer(0);        /* 0 = 不分包，批量/中断用 0 */
    if (!c.t) return -1;
    uint8_t *buf = malloc(4096);
    libusb_fill_bulk_transfer(c.t, h, 0x81, buf, 4096, bulk_cb, &c, 1000);
    int r = libusb_submit_transfer(c.t);   /* 立刻返回 */
    if (r < 0) {
        libusb_free_transfer(c.t);
        free(buf);
        return r;
    }
    while (c.done == 0)
        libusb_handle_events(NULL);        /* 跑事件循环，等回调 */
    libusb_free_transfer(c.t);
    free(buf);
    return 0;
}

libusb_fill_bulk_transfer 的签名（1.0.16 之后带 timeout）：fill(transfer, dev_handle, endpoint, buffer, length, callback, user_data, timeout)。更老的版本没有 timeout 参数，得自己写 transfer->timeout = 1000;。看编译报错就知道是哪个版本。

6.3 中断与控制异步 #

中断异步只是换个 fill 函数：libusb_fill_interrupt_transfer(t, h, 0x82, buf, sizeof(buf), intr_cb, user_data, 0);

中断端点用 timeout 0 有道理：让它一直躺着，设备一有数据立刻回调，不用反复超时重提交。代价是设备拔掉时收到的是 LIBUSB_TRANSFER_NO_DEVICE 而不是超时，回调里得处理。

控制异步要把 8 字节 setup 包自己拼好：

c
unsigned char setup[8];
setup[0] = 0xC0;                  /* bmRequestType */
setup[1] = 0x06;                  /* bRequest */
setup[2] = 0x00; setup[3] = 0x03; /* wValue，小端 */
setup[4] = 0x00; setup[5] = 0x00; /* wIndex */
setup[6] = 0x40; setup[7] = 0x00; /* wLength，小端 */
libusb_fill_control_transfer(t, h, setup, buf, ctrl_cb, user_data, 1000);

buffer 对应 wLength 那段数据区，length 要和 wLength 一致。填错这一处返回 LIBUSB_ERROR_INVALID_PARAM，很难查。

6.4 同步 vs 异步对照 #

维度 同步 API 异步 API
入口 libusb_bulk_transfer / interrupt_transfer / control_transfer libusb_submit_transfer
阻塞 阻塞到传输完成 立即返回
完成通知 函数返回值 回调函数
数据放哪 调用者的 buffer，返回即可用 堆上长期存活，回调里才可用
事件循环 不需要 必须有人跑 libusb_handle_events
并发传输 一个线程一次一个 可同时挂几十个
吞吐 受线程调度限制，够用 高，能打满端点带宽
延迟 一次传输的 RTT 低，多个 transfer 排队填满流水线
代码复杂度 低，串行思路 高，要管状态、生命周期、取消
适合 命令应答、配置读写、调试 高速采集、音频流、持续上报

决策一句话：一秒钟只发几条命令，用同步；设备一直往外吐数据，用异步。

6.5 用多个 transfer 填满流水线 #

异步值钱的地方在这。同步一次读 4KB，读完再提交下一次，中间的往返延迟是浪费的。开 8 个 4KB 的 transfer 同时在飞，主机侧的 URB 队列始终是满的，吞吐就上去了。异步快的不是单个传输，而是永远不空窗。

c
static void LIBUSB_CALL stream_cb(libusb_transfer *t)
{
    if (t->status == LIBUSB_TRANSFER_COMPLETED) {
        consume(t->buffer, t->actual_length);
        libusb_submit_transfer(t);       /* 立刻补位，流水线不空 */
        return;
    }
    if (--g_inflight == 0)
        /* 全部收摊 */;
}

timeout 填 0：持续流用超时没意义。真要看门狗，用独立定时器检查「最近一次收到数据是多少毫秒前」。

6.6 取消 #

c
int r = libusb_cancel_transfer(t);
if (r == 0) {
    /* 请求已接受，但回调还没跑 */
    while (!cancelled)
        libusb_handle_events(NULL);
}

这一步没法省。libusb_cancel_transfer 只是「请取消」，内核把 URB 撤回来的过程中还会回调一次，status = LIBUSB_TRANSFER_CANCELLED。在回调之前就 libusb_free_transfer 是经典 use-after-free。退出前把在飞的 transfer 都取消、都等回调、再释放，顺序不能变。

七、异步的回调与事件循环 #

7.1 libusb_handle_events 做什么 #

它不是「处理一次传输」。它把库内部维护的 fd 集合扔给 poll()，等某个 fd 可读，去读内核给的完成事件，然后逐个调用你注册的回调。没有 fd 就绪就一直等。

推论三条：事件循环必须持续跑，跑一次只处理掉一批；回调里别干重活，那等于卡住整个事件分发；一处线程跑循环就够，多个线程同时跑合法（库内部有锁）但没必要。

函数 行为
libusb_handle_events(ctx) 阻塞，直到有事件
libusb_handle_events_timeout(ctx, &tv) 最多阻塞 tv
libusb_handle_events_completed(ctx, &completed) 阻塞到 *completed 非 0，或有事件
libusb_handle_events_timeout_completed(ctx, &tv, &completed) 上面两个的结合
libusb_get_next_timeout(ctx, &tv) 问库「下一个内部定时器多久到期」

最常用的是 completed 版：

c
int completed = 0;
static void LIBUSB_CALL cb(libusb_transfer *t)
{
    (*(int *)t->user_data)++;           /* 回调里加计数 */
}
while (completed < N) {
    int r = libusb_handle_events_completed(ctx, &completed);
    if (r < 0) break;
}

completed 由回调去加，循环每次先检查它。既不空转，也不提前退出。

7.2 接进外部事件循环 #

程序本身已经有事件循环（glib 的 GMainLoop、libevent、Qt 的 QEventLoop）时，别再多起一个线程，把 libusb 的 fd 塞进你的循环就行。

c
const struct libusb_pollfd **fds = libusb_get_pollfds(ctx);
for (int i = 0; fds[i]; i++)
    printf("fd %d events %x\n", fds[i]->fd, fds[i]->events);

拿到 fd 和关心的事件（POLLIN/POLLOUT），注册进你的 poll 集合。检测到事件发生时，调一次 libusb_handle_events_completed 让库去读完成队列。

设备接入/移除会让 fd 列表变化，所以还得注册通知器：

c
static void LIBUSB_CALL pollfd_added(int fd, short events, void *user_data)
{
    /* 把 fd 加进自己的 poll 集合 */
}
static void LIBUSB_CALL pollfd_removed(int fd, void *user_data)
{
    /* 从 poll 集合里摘掉 fd */
}
libusb_set_pollfd_notifiers(ctx, pollfd_added, pollfd_removed, NULL);

这两个回调跟热插拔回调不是一回事。

7.3 热插拔 #

1.0.16 之后支持热插拔事件，不用轮询设备列表。

c
static int LIBUSB_CALL hotplug_cb(libusb_context *ctx, libusb_device *dev,
                                  libusb_hotplug_event event, void *user_data)
{
    struct libusb_device_descriptor d;
    libusb_get_device_descriptor(dev, &d);
    if (event == LIBUSB_HOTPLUG_EVENT_DEVICE_ARRIVED)
        printf("arrived %04x:%04x\n", d.idVendor, d.idProduct);
    else if (event == LIBUSB_HOTPLUG_EVENT_DEVICE_LEFT)
        printf("left %04x:%04x\n", d.idVendor, d.idProduct);
    return 0;
}
libusb_hotplug_register_callback(ctx,
                                 LIBUSB_HOTPLUG_EVENT_DEVICE_ARRIVED |
                                 LIBUSB_HOTPLUG_EVENT_DEVICE_LEFT,
                                 LIBUSB_HOTPLUG_ENUMERATE,   /* 已插着的也回调一遍 */
                                 VENDOR_ID, PRODUCT_ID,
                                 LIBUSB_HOTPLUG_MATCH_ANY,   /* dev_class */
                                 hotplug_cb, NULL, &hp_handle);

三个过滤器分别管 vendor_id、product_id、dev_class。任意一个填 LIBUSB_HOTPLUG_MATCH_ANY 就是不限，三个都填具体值就是「与」的关系。只按类匹配时，vid/pid 填 MATCH_ANY，dev_class 填 0x03。

LIBUSB_HOTPLUG_ENUMERATE 很实用：注册那一刻会把当前已插着的设备也回调一遍，省了「先枚举再注册」。

接入与移除的完整时序：

text
接入：hotplug 回调 → libusb_open → (可选) libusb_reset_device
                  → detach_kernel_driver / set_auto_detach_kernel_driver
                  → (可选) libusb_set_configuration
                  → libusb_claim_interface
                  → alloc_transfer + fill + submit
移除：hotplug 回调 → 取消在飞的 transfer，等回调
                  → release_interface → close → 释放 buffer

libusb_reset_device 可选，用来把设备恢复到干净状态（上次异常断开时端点还挂着 halt）。它会让设备重新枚举，地址变了、旧 handle 失效，所以要在 open 之后、claim 之前做。

7.4 事件循环与线程 #

单线程全异步：一个循环，所有设备的所有 transfer 都挂在里面，回调里只做搬运。没锁，时序可控。

一线程一设备：每设备一个线程各跑 libusb_handle_events，代码直白，但线程多了麻烦，并发效率不如单线程。一两个设备随便选，十几个设备一律单线程。

八、设备断开与资源释放 #

USB 设备随时会被拔。桌面上是意外，工业现场是日常。代码必须按「随时会断」来写。

8.1 断开时的返回值 #

场景 同步 API 返回 异步 status
传输中途拔出 LIBUSB_ERROR_NO_DEVICE LIBUSB_TRANSFER_NO_DEVICE
接口被别的进程占 LIBUSB_ERROR_BUSY ——
端点 stall LIBUSB_ERROR_PIPE LIBUSB_TRANSFER_STALL
超时 LIBUSB_ERROR_TIMEOUT LIBUSB_TRANSFER_TIMED_OUT
句柄已关 LIBUSB_ERROR_NO_DEVICE ——
传输被取消 —— LIBUSB_TRANSFER_CANCELLED

LIBUSB_ERROR_NO_DEVICE 是终结信号，不是可重试错误。收到就往上报，别在循环里死磕——重试只会立刻再失败一次。

8.2 释放顺序 #

顺序和申请完全相反：

c
/* 1. 先让在飞的传输落地 */
for (int i = 0; i < N_XFER; i++)
    libusb_cancel_transfer(g_t[i]);
while (inflight > 0)
    libusb_handle_events(ctx);       /* 等 CANCELLED 回调到齐 */
/* 2. 释放 transfer 和它引用的 buffer */
for (int i = 0; i < N_XFER; i++) {
    libusb_free_transfer(g_t[i]);    /* 只释放 transfer 本身 */
    free(g_buf[i]);                  /* buffer 是你 malloc 的，自己 free */
}
/* 3. 还接口 */
libusb_release_interface(h, 0);
libusb_attach_kernel_driver(h, 0);   /* 摘过就挂回去 */
/* 4. 关句柄 */
libusb_close(h);
/* 5. 释放设备列表 */
libusb_free_device_list(list, 1);
/* 6. 退库 */
libusb_exit(ctx);

两个反复出现的错误：

  • libusb_free_transfer 之后还访问 t->buffer。free_transfer 只释放 transfer 结构，buffer 是独立分配的，所以要分开处理，顺序是「先 transfer 后 buffer」。
  • libusb_exit 之前还有 handle 没关。库会尝试清理，但你的 udev 权限、内核驱动挂回、接口状态全都不保证恢复，设备下次插上会变哑巴。

8.3 用统一清理兜住所有出口 #

C 里没有析构函数，只能自己管。把资源集中在一个结构体里，全初始化为 NULL/0，配一个统一清理函数：

c
struct usb_session {
    libusb_context       *ctx;
    libusb_device       **list;
    libusb_device_handle *h;
    int                   claimed;
    int                   detached;
};
static void session_close(struct usb_session *s)
{
    if (!s) return;
    if (s->h) {
        if (s->claimed)  libusb_release_interface(s->h, 0);
        if (s->detached) libusb_attach_kernel_driver(s->h, 0);
        libusb_close(s->h);
    }
    if (s->list) libusb_free_device_list(s->list, 1);
    if (s->ctx)  libusb_exit(s->ctx);
    memset(s, 0, sizeof(*s));
}

每个失败分支都 goto fail;，fail: 标签只有一句 session_close(&s);。新增错误路径时不会忘记补清理。

8.4 信号处理 #

Ctrl-C 默认直接杀进程，内核会回收 fd，但设备那头会停在半包状态，内核驱动也没挂回去。要干净退出就得接信号：设一个 volatile sig_atomic_t g_stop，signal(SIGINT, on_sigint) 里只置位，主循环用 libusb_handle_events_timeout_completed 配 200ms 超时轮询它，退出后落回正常清理流程。信号处理函数里只能碰 volatile sig_atomic_t，别在里面调 libusb_*。

九、无驱设计的思路 #

回到最初的问题：为什么要在用户态干这件事。

9.1 内核驱动的三个现实麻烦 #

痛点不是「写不出来」，是「维护不过来」：

  • 版本漂移。客户那边 2.6.18、2.6.32、3.10、4.19 各有一批，每个大版本 API 都有微调，一份驱动得开好几个条件编译分支，Makefile 都得写两份。
  • 移植成本。给嵌入式平台做产品，客户的内核裁剪过，连 insmod 都没移植进去。你想加模块？没门。客户的系统你又不能动。
  • 交付节奏。客户邮件一封接一封：「客户要 2.6.5 的驱动」「要双核 2.6.18-smp 的」「平台是定制的 2.6.12-xxx」。你一部分工作时间全花在编译内核、定制驱动上。

libusb 绕开的正是这三条：一份用户态程序，编出来是普通可执行文件，不依赖内核版本，不需要 root 装模块，拷过去就能跑。

9.2 从 hiddev 到 libusb 的改写路径 #

老办法是走 /dev/usb/hid/hiddevN 加 ioctl。同样「发 72 字节报告再读回 72 字节」，我们的 Device_Report 得这样写：

c
ret = ioctl(fd, HIDIOCINITREPORT, 0);        /* 发送前必须初始化 */
for (index = 0; index < 72; index++) {        /* HID 每次只能操作一个 usage */
    uref.report_type = HID_REPORT_TYPE_FEATURE;
    uref.report_id   = HID_REPORT_ID_FIRST;
    uref.usage_index = index;
    uref.field_index = 0;
    uref.value       = send_data[index];
    ioctl(fd, HIDIOCGUCODE, &uref);
    ret = ioctl(fd, HIDIOCSUSAGE, &uref);
    if (ret != 0) return UNKNOWN_ERROR;
}
rinfo.report_type = HID_REPORT_TYPE_FEATURE;
rinfo.report_id   = HID_REPORT_ID_FIRST;
rinfo.num_fields  = 1;
ret = ioctl(fd, HIDIOCSREPORT, &rinfo);      /* 真正发出去 */
if (ret != 0) return WRITE_REPORT;

读回也是一样 72 次 ioctl（HIDIOCGUSAGE）。一次 72 字节的传输，进出各 72 次系统调用，还得跟 HIDIOCGUCODE 的状态机较劲。

同一个 Device_Report，换成 libusb：

c
usb_claim_interface(Device_handle, 0);       /* 0 = 默认接口 */
/* 一次控制传输把 72 字节发完 */
send_len = usb_control_msg(Device_handle,
                           USB_ENDPOINT_OUT | USB_TYPE_CLASS | USB_RECIP_INTERFACE,
                           HID_REPORT_SET, 0x0300, 0,
                           send_data, 72, USB_TIMEOUT);
if (send_len < 0)   return WRITE_REPORT;
if (send_len != 72) return send_len;
/* 一次控制传输读回来 */
recv_len = usb_control_msg(Device_handle,
                           USB_ENDPOINT_IN | USB_TYPE_CLASS | USB_RECIP_INTERFACE,
                           HID_REPORT_GET, 0x0300, 0,
                           recv_data, 72, USB_TIMEOUT);
if (recv_len < 0)   return READ_REPORT;
if (recv_len != 72) return recv_len;
usb_release_interface(Device_handle, 0);     /* 与 claim 配对 */
memcpy(buffer72, recv_data, 72);
return SUCCESS;

用到的宏在 usb.h 里：USB_ENDPOINT_OUT（0x00）、USB_ENDPOINT_IN（0x80）、USB_TYPE_CLASS（0x01 << 5，即 0x20）、USB_RECIP_INTERFACE（0x01）、HID_REPORT_SET（0x09）、HID_REPORT_GET（0x01）。

0x0300 这个 wValue 是「报告类型 Feature（高字节 0x03）+ 报告 ID 0x00」。这一处最容易填错，查一眼 HID 规范的 wValue 编码表。

144 次 ioctl 变 2 次控制传输。数据在链路上怎么走，两者是一回事——都走控制传输的 SET_REPORT/GET_REPORT，只是 libusb 把协议细节铺好了。

9.3 驱动框架照搬 #

内核驱动那套 probe/read/write/release 结构，用户态一样能照搬。五个接口：Device_Find() 按 VID/PID 枚举并把设备信息存进全局表、Device_Open() 逐句柄 open、Device_Read() / Device_Write() 收发、Device_Close() 关闭回收。

结构与全局表：

c
#include <usb.h>
typedef struct {
    struct usb_device *udev;
    usb_dev_handle    *device_handle;
} device_descript;
#define USB_TIMEOUT   10000
#define VENDOR_ID     0xffff
#define PRODUCT_ID    0xffff
#define DEVICE_MINOR  16          /* 最多同时操作 16 个 */
int             g_num;
device_descript g_list[DEVICE_MINOR];

Device_Find 的骨架就是 2.6 那段双链表遍历，只多一步「把匹配到的 dev 指针存进 g_list[g_num++]」。打开与关闭：

c
int Device_Open(void)
{
    if (g_list[g_num].udev != NULL)
        g_list[g_num].device_handle = usb_open(g_list[g_num].udev);
}
void Device_Close(int handle)
{
    usb_close(g_list[handle].device_handle);
    g_list[handle].device_handle = NULL;
}

设备协议变了只改 Device_Read/Device_Write，枚举和资源管理不动。多个同型号设备挂一台机器，靠 g_list 下标区分，调用者的「句柄」就是那个下标。

十、无驱方案能做什么、不能做什么 #

libusb 不是万能的。它让你能跟设备说话，但不让设备变成系统的一部分。这条线要划清，否则做到一半才发现方向错了。

10.1 能做的 #

能力 说明 实现要点
读写设备数据 批量、中断、控制、同步四种传输全支持 认对端点和传输类型
发厂商自定义命令 bmRequestType 填 0x40/0xC0 wValue/wIndex 自己定义
实现私有协议 固件和主机约定好就行 谁也不管你们怎么编码
取描述符、字符串 枚举设备信息、读序列号 get_descriptor / get_string_descriptor_ascii
热插拔响应 插上就打开，拔掉就清理 libusb_hotplug_register_callback
多设备并发 一个进程管多个同 VID/PID 设备 每设备一 handle，一个事件循环
跨平台 Linux / macOS / Windows（WinUSB）同一套代码 注意后端差异

10.2 不能做的 #

做不到的事 为什么 后果
自动变成串口（/dev/ttyUSB0） 要注册 tty 子系统，只有内核驱动能注册 别的程序看不见这个设备
自动变成网卡 要挂到 net 子系统 只能由你的进程转发数据
自动变成摄像头（V4L2） 要注册 video device 打不开 /dev/video0
让 mount 认出 U 盘 要挂到块设备和文件系统层 只能自己解析文件系统
参与系统电源管理 挂起/唤醒策略归内核管 睡眠唤醒后会丢句柄
被其他程序当标准设备用 设备节点对你私有 你的程序是唯一使用者
独占整台设备做热插拔策略 claim 是按接口的 别的接口仍归系统

这就是「无驱」的代价：你的程序是设备的唯一入口，别的程序想用，得走你的进程。

10.3 什么时候该回到内核驱动 #

  • 设备要出现在系统标准位置（/dev/tty*、/dev/video*、网络接口），让 cat、ffmpeg、iperf 这些现成工具直接用。
  • 要参与系统级电源管理，或者开机就要可用（早于任何用户态进程）。
  • 多个进程要同时访问同一个接口。claim 是独占的，要么用 IPC，要么换驱动。
  • 要与内核里别的子系统协同（比如把 USB 数据直接导进网络栈）。
  • 设备本来就是标准类设备，比如标准 UVC 摄像头、标准 CDC 串口——系统自带驱动就够用，别自己写。

10.4 混合方案 #

有些产品两条路都走：一个极简内核驱动只做枚举和接口转发（暴露 /dev/mydev0 给别的程序用），协议处理全在用户态。代价是代码分两处，好处是既进了系统，又留了灵活性。

十一、一个完整的例子 #

行为：找设备 → 打开 → claim → 发一条厂商命令 → 异步持续读 → Ctrl-C 干净退出。

11.1 上下文与开头 #

c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <signal.h>
#include <libusb.h>
#define VENDOR_ID   0x1234
#define PRODUCT_ID  0x5678
#define IFACE       0
#define EP_IN       0x81
#define PKT_SIZE    4096
#define N_XFER      4
struct app {
    libusb_context       *ctx;
    libusb_device_handle *h;
    libusb_transfer      *t[N_XFER];
    unsigned char        *buf[N_XFER];
    int                   inflight;
    int                   error;
    int                   stopping;
};
static volatile sig_atomic_t g_stop;
static void on_signal(int s) { (void)s; g_stop = 1; }

11.2 找设备并打开 #

c
static int open_device(struct app *a)
{
    libusb_device **list = NULL;
    ssize_t cnt = libusb_get_device_list(a->ctx, &list);
    if (cnt < 0) return (int)cnt;
    libusb_device *dev = NULL;
    for (ssize_t i = 0; i < cnt; i++) {
        struct libusb_device_descriptor d;
        if (libusb_get_device_descriptor(list[i], &d) < 0) continue;
        if (d.idVendor == VENDOR_ID && d.idProduct == PRODUCT_ID) {
            dev = list[i];
            break;
        }
    }
    if (!dev) {
        libusb_free_device_list(list, 1);
        return LIBUSB_ERROR_NO_DEVICE;
    }
    int r = libusb_open(dev, &a->h);
    libusb_free_device_list(list, 1);   /* 数组用完即放，handle 独立存活 */
    if (r < 0) return r;
    /* 被内核驱动绑着就摘掉，否则 claim 会 BUSY */
    if (libusb_kernel_driver_active(a->h, IFACE) == 1)
        libusb_detach_kernel_driver(a->h, IFACE);
    r = libusb_claim_interface(a->h, IFACE);
    if (r < 0) {
        libusb_close(a->h);
        a->h = NULL;
        return r;
    }
    /* 厂商命令：0x40 = OUT + 厂商 + 设备 */
    unsigned char cmd[4] = {0x01, 0x02, 0x03, 0x04};
    r = libusb_control_transfer(a->h, 0x40, 0x01, 0, 0, cmd, sizeof(cmd), 1000);
    if (r < 0) {
        libusb_release_interface(a->h, IFACE);
        libusb_close(a->h);
        a->h = NULL;
    }
    return r;
}

11.3 回调与启动 #

c
static void LIBUSB_CALL read_cb(libusb_transfer *t)
{
    struct app *a = (struct app *)t->user_data;
    switch (t->status) {
    case LIBUSB_TRANSFER_COMPLETED:
        if (t->actual_length > 0)
            printf("rx %d bytes\n", t->actual_length);
        if (!a->stopping) libusb_submit_transfer(t);   /* 补位 */
        else              a->inflight--;
        break;
    case LIBUSB_TRANSFER_CANCELLED:
        a->inflight--;
        break;
    case LIBUSB_TRANSFER_STALL:
        libusb_clear_halt(a->h, t->endpoint);
        if (!a->stopping) libusb_submit_transfer(t);
        else              a->inflight--;
        break;
    case LIBUSB_TRANSFER_NO_DEVICE:
        a->error = LIBUSB_ERROR_NO_DEVICE;
        a->inflight--;
        break;
    default:
        a->error = LIBUSB_ERROR_IO;
        a->inflight--;
        break;
    }
}
static int start_stream(struct app *a)
{
    a->inflight = 0;
    for (int i = 0; i < N_XFER; i++) {
        a->buf[i] = malloc(PKT_SIZE);
        a->t[i]   = libusb_alloc_transfer(0);
        if (!a->buf[i] || !a->t[i]) return LIBUSB_ERROR_NO_MEM;
        libusb_fill_bulk_transfer(a->t[i], a->h, EP_IN, a->buf[i], PKT_SIZE,
                                  read_cb, a, 0);
        int r = libusb_submit_transfer(a->t[i]);
        if (r < 0) return r;
        a->inflight++;
    }
    return 0;
}

11.4 主循环与收尾 #

c
int main(void)
{
    struct app a;
    memset(&a, 0, sizeof(a));
    signal(SIGINT, on_signal);
    signal(SIGTERM, on_signal);
    int r = libusb_init(&a.ctx);
    if (r < 0) return 1;
    if (open_device(&a) < 0 || start_stream(&a) < 0)
        goto cleanup;
    while (!g_stop && a.error == 0) {
        struct timeval tv = {0, 200000};       /* 200ms，保证能看到 g_stop */
        libusb_handle_events_timeout_completed(a.ctx, &tv, NULL);
    }
cleanup:
    a.stopping = 1;
    for (int i = 0; i < N_XFER; i++)
        if (a.t[i]) libusb_cancel_transfer(a.t[i]);
    while (a.inflight > 0) {                   /* 等 CANCELLED 回调到齐 */
        struct timeval tv = {0, 100000};
        libusb_handle_events_timeout_completed(a.ctx, &tv, NULL);
    }
    for (int i = 0; i < N_XFER; i++) {
        if (a.t[i])   libusb_free_transfer(a.t[i]);
        if (a.buf[i]) free(a.buf[i]);
    }
    if (a.h) {
        libusb_release_interface(a.h, IFACE);
        libusb_attach_kernel_driver(a.h, IFACE);
        libusb_close(a.h);
    }
    libusb_exit(a.ctx);
    return a.error ? 1 : 0;
}

十二、易错点速查 #

症状 常见原因 处理
claim 返回 BUSY 内核驱动绑着这个接口 detach_kernel_driver 或 set_auto_detach_kernel_driver
open 返回 ACCESS 设备节点权限不够 加 udev 规则 MODE="0666"
传输随机报 PIPE 端点 stall，上一条命令设备没接住 clear_halt 后重试，检查协议时序
同步读永远超时 端点地址方向填错 查配置描述符的 bEndpointAddress
返回 0 但数据不全 没检查 transferred 按需写凑满循环
异步回调不触发 没人跑 libusb_handle_events 加事件循环，或接进外部 poll
回调里数据是垃圾 buffer 在栈上，函数返回就失效 malloc 到堆上，活到回调之后
偶发段错误 transfer 没取消就 free_transfer 先 cancel，等 CANCELLED 回调，再释放
事件循环空转烧 CPU timeout 传 0 还在循环里转 用 {0, 200000} 这类有限超时
拔掉后程序卡死 同步调用 timeout 设 0 给有限超时，处理 NO_DEVICE
libusb_exit 后崩溃 还有 handle / transfer 没释放 严格按申请的反序释放
拔了再插连不上 没处理热插拔，或旧句柄还占着 注册 hotplug 回调，拔掉时释放干净
中文厂商名变问号 get_string_descriptor_ascii 只转 ASCII 用 get_string_descriptor 拿 UTF-16 自己转
换台机器端点号不对 端点地址由固件定，不是常量 从配置描述符读，别硬编码
多设备数据串了 全局变量被多个 handle 共用 每设备一套 context，用 user_data 传
设了配置接口就失效 set_configuration 会重置所有接口 claim 之前设配置，设完重新 claim

几条不用查表就能记住的规矩：

  • 申请和释放严格反序，claim 配 release，open 配 close，alloc 配 free。
  • 同步 API 的 buffer 可以放栈上，异步 API 的 buffer 必须在堆上。
  • 所有 timeout 都给有限值，除了「设备连续吐数据」的持续流。
  • actual_length 和 transferred 每次都要看，返回 0 不等于传完了。
  • 回调里只做搬运，别做耗时操作，事件循环只有一个。
  • NO_DEVICE 是终点，TIMEOUT 是常态，PIPE 要 clear_halt。

把这些盯住，剩下的基本是设备固件那边的协议问题。协议对不上就抓包，usbmon 那一篇讲怎么抓。
