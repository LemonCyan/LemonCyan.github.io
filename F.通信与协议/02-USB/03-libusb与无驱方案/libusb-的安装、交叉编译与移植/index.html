这篇只讲 libusb 这个库本身：怎么装、怎么交叉编译到开发板、怎么在 Windows 上让它跑起来。不讲 API 怎么调，不讲设备读写的完整例子，也不讲 usbmon 抓包。

三篇同伴：枚举与描述符解析看《libusb 编程》；完整读写例子看《libusb 实战》；总线上的原始数据看《usbmon 抓包》。这篇把环境铺到你 make 能过、file 出来是 ARM、板子上能枚举出设备为止。

一、libusb 是什么 #

Linux 上做 USB 通讯有两条路：写内核驱动，或者用 libusb 做无驱设计。HID 这类设备内核自带驱动，操作设备文件就够了。麻烦出在自己设计的硬件上：没有现成驱动，得从头写。写出来之后问题才刚开始。

三个真实场景。

  • 客户手里有 2.4 内核的平台，也有 2.6 内核的平台，驱动两边都要兼容，连 Makefile 都得写两份。
  • 把 Linux 移植到嵌入平台，内核驱动跟过去体积不小。更难受的是嵌入平台是客户的，客户系统和你环境不一样，没有你要的驱动，程序跑不起来。你想「insmod 一下就行」，结果客户连 insmod 工具都没移植。
  • 驱动写完，客服邮件开始堆：「客户需要 2.6.5 内核的驱动」「客户要双核 2.6.18-smp 的」「客户平台是定制的 2.6.12-xxx」。你的时间全花在编译内核、定制驱动上。

libusb 换了个思路。它是用户空间的库，设计一系列外部 API 给应用程序调用。这些 API 底下调的是内核的底层接口，和内核驱动里那些函数干的事差不多，只是 libusb 更贴近 USB 规范，用起来比写内核驱动容易得多。

一句话：libusb 不让你的程序进内核，它借操作系统的底层接口去跟设备说话。

平台 libusb 底下走什么
Linux usbfs（老内核叫 usbdevfs），节点在 /dev/bus/usb/BBB/DDD
Windows WinUSB 或 libusbK 这类内核态后端
macOS IOKit 的 USB 接口

这个「借道」决定了后面所有麻烦的来源。

  • Linux 上 /dev/bus/usb/* 权限不对，普通用户打不开设备，libusb_open 返回 LIBUSB_ERROR_ACCESS。
  • Windows 上设备没绑到正确的后端，libusb 压根枚举不到，列表是空的。
  • 板子上内核没挂 usbdevfs，usb_find_busses 返回 0，第一层 for 循环都进不去。

所以「无驱」说的是你不用为这台设备写内核驱动。操作系统那一层该有的东西，一样都不能少。

libusb 自己带着一个内核侧的东西。Windows 上是 libusb0.sys，放在 WINDOWS\SYSTEM32\DRIVERS 里，用户程序调 libusb0.dll，dll 把任务交给驱动完成。新版走系统自带的 WinUSB 或 libusbK，道理一样：内核态后端顶住，用户态 API 保持稳定。好处是同一份应用代码，Linux 上编一次、Windows 上编一次，源码不用改。

二、1.0 与 0.1 两个版本线 #

两条互相独立的版本线，API 不一样，头文件不一样，链接的库名也不一样。这不是新版兼容旧版的关系。

  • libusb-0.1：老 API，函数全带 usb_ 前缀，纯同步。
  • libusb-1.0：重写版 API，函数带 libusb_ 前缀，有异步传输、热插拔回调、清楚的错误码。
  • libusb-compat-0.1：桥接库。对外提供 0.1 的 usb.h 和 usb_* 函数，内部转调 libusb-1.0。

素材里那句话写得很实在：libusb 分为 1.0 版和 0.1 版两种版本，1.0 并不向下兼容 0.1，需要 libusb-compat 的支持；因此你可以同时装上 1.0 和 0.1，但不可同时装 0.1 版和 libusb-compat。

最后半句别漏。0.1 本体和 compat 装一起会打架，符号重了。要么用 0.1 本体（只在 2.4 内核上跑的老平台），要么用 1.0 加 compat 走桥接。

对比项 libusb-1.0 libusb-0.1 / compat
函数前缀 libusb_ usb_
主头文件 libusb.h usb.h
链接选项 -lusb-1.0 -lusb
动态库名 libusb-1.0.so.0 libusb-0.1.so.4
设备枚举 libusb_get_device_list usb_find_busses + usb_find_devices
打开设备 libusb_open usb_open
批量传输 libusb_bulk_transfer usb_bulk_write / usb_bulk_read
控制传输 libusb_control_transfer usb_control_msg
异步传输 有 无
谁在用 新项目 老代码、旧 tutorial

结论很干脆：新项目一律用 1.0，老代码继续走 compat，别急着动。

踩坑最多的地方在这：libusb-1.0.9 编译出来的 include 目录里没有以前那些应用程序需要的 usb.h。这不是装错了，1.0 本来就不带它。要 usb.h，必须额外把 compat 包编一遍。

所以一个能让老代码编过的完整工具链是三样东西：libusb-1.0 的库和头、compat 的 usb.h 和 libusb-0.1.so、以及运行时的 libusb-1.0.so。第三章装本机的、第五章交叉编译到板子的，都是这个三件套。

三、Linux 下的安装 #

主流发行版已经把 libusb 收进源里，apt 或 dnf 搜一下就有。开发要用就装 dev 包。

bash
sudo apt-get install libusb-1.0-0-dev   # 1.0 的库和头
sudo apt-get install libusb-dev         # 要 usb.h 再装这个（compat）

libusb-1.0-0-dev 只往 /usr/include/libusb-1.0/ 里放东西，所以源码里要写全路径 #include <libusb-1.0/libusb.h>，或者靠 pkg-config 把 -I 补上。

用 pkg-config 取编译参数 #

别手写 -I 和 -L。.pc 文件就是干这个的。

bash
pkg-config --cflags --libs libusb-1.0

输出类似 -I/usr/include/libusb-1.0 -lusb-1.0。compat 装完之后带的是 libusb.pc（没有版本后缀），走它取旧 API 的参数：

bash
pkg-config --cflags --libs libusb

写进 Makefile：

makefile
CFLAGS  += $(shell pkg-config --cflags libusb-1.0)
LDFLAGS += $(shell pkg-config --libs libusb-1.0)

交叉编译时这两行要换掉，原因在第五章。

从源码编 #

发行版版本太老、或者要自己指定安装前缀，就走源码。SourceForge 上取包：

bash
tar -xzf libusb-1.0.21.tar.bz2
cd libusb-1.0.21
./configure --prefix=/usr/local
make
sudo make install
sudo ldconfig

ldconfig 不能省。装在 /usr/local/lib 下的 .so 不进默认搜索路径，不刷缓存程序启动就报找不到库。

configure 阶段会停在这：

text
configure: error: "udev support requested but libudev not installed"

它默认想带 udev 热插拔支持，但系统里没有 libudev 开发包。装 libudev-dev，或者 ./configure --disable-udev --prefix=/usr/local 关掉。关掉的是热插拔事件那部分，枚举和读写不受影响。交叉编译时更常见，因为板子的 sysroot 里根本没有 libudev。

四、Windows 下的安装 #

Windows 比 Linux 多一层概念。Linux 上装个 .so 就完事，Windows 上 libusb 需要一个内核态驱动把设备接住，接住的方式有三代历史包袱。

后端 出身 驱动文件 现在的定位
libusb-win32 最早的 Windows 无驱方案 libusb0.sys 老项目，配 0.1 API
libusbK libusb-win32 的继任者 libusbK.sys 功能多，1.0 可用
WinUSB 微软自带 winusb.sys 免装第三方驱动，推荐

早期在 Windows 上做 USB 通讯选的是 libusb-0.1 那条线，落到 Windows 就是 libusb-win32。工程上要的是稳，不是新。

原理很简单：libusb-win32 自带内核驱动 libusb0.sys，放在 WINDOWS\SYSTEM32\DRIVERS 里。用户程序调 libusb0.dll，dll 把任务交给驱动去完成，用户态就能把 USB 通讯做完，你不用写 .sys。

现在这三条线已经收敛。libusb-1.0 自己支持多后端，编译时选或者装的时候用驱动安装工具选。你写的还是 libusb_* 那套 API，底下挂 WinUSB 还是 libusbK 是安装时的事。新项目直接上 WinUSB，不装第三方驱动包。

两种安装方式 #

官方文档给了两种装法，含义不一样，别选错。Filter Driver Installation 是过滤驱动方式，挂在设备原有的驱动上面，开发环境用，装完能调试，不改动设备本来的驱动栈。Device Driver Installation 是设备驱动方式，直接替掉设备原来的驱动，发布形态。开发调试选前一种，省得折腾，设备原来的功能还在。要出货、设备就专属你这一个程序用，选后一种。

具体怎么装 #

Zadig 最省事，一个绿色小工具。插上设备，Options → List All Devices 选中它（按 VID/PID 认），右边目标驱动选 WinUSB，点 Replace Driver。

inf-wizard.exe 是 libusb-win32 自带的老工具，走生成 .inf 再装的路子：选择要绑定 VID/PID 的设备，生成 inf 和 cat 文件，安装这个 inf。

装完回设备管理器看，设备应该出现在「libusb-win32 devices」或「Universal Serial Bus devices」下面，不再是带黄色感叹号的未知设备。

Windows 上程序要跑起来，libusb-1.0.dll 必须在 exe 同目录或 PATH 里。32 位和 64 位程序不能混用同一个 dll，位数对不上直接加载失败。

换设备的坑 #

驱动绑在 VID/PID 上，不是绑在「这个 USB 口」上。

  • 换一块同型号的板子，驱动还在，能直接用。
  • 换一个不同 VID/PID 的设备，得重新装一遍驱动。
  • 开发时把 PID 改了一位，设备立刻变成未知设备，别怀疑代码。

卸载也要走驱动这一层。设备管理器里右键卸载，勾上「删除驱动程序软件」，不然下次插上还是旧驱动。

五、交叉编译到开发板 #

前提两条：交叉编译工具链装好了，并且已经 export 到 PATH 里，arm-linux-gnueabihf-gcc -v 能打出 gcc 版本信息才算过。下面命令里的工具链前缀按你实际的换，arm-linux、arm-linux-gnueabi、arm-none-linux-gnueabi、arm-linux-gnueabihf、aarch64-linux-gnu 都是常见写法。

去 SourceForge 的 libusb 项目页取包，libusb-1.0.x 和 libusb-compat-0.1.x 两个都要。素材里一个用的是 libusb-1.0.21 加 libusb-compat-0.1.5，另一个用的是 libusb-1.0.9 加 libusb-compat-0.1.4，步骤完全一样。

bash
tar -xjf libusb-1.0.x.tar.bz2
tar -xzf libusb-compat-0.1.x.tar.gz

第一个包：libusb-1.0 #

bash
cd libusb-1.0.x
mkdir install
CROSS_COMPILE=1 CC=arm-linux-gnueabihf-gcc CXX=arm-linux-gnueabihf-g++ \
./configure --build=i686-linux --host=arm-linux-gnueabihf \
            --prefix=`pwd`/install

--prefix 后面要写成 `pwd`/install，让 shell 先展开成绝对路径，否则安装落到相对路径上，后面找库找头文件全靠猜。

三个参数各管一件事，这是本章最重要的一段：

参数 含义 漏了会怎样
--build=i686-linux 编译这个软件的机器是 x86 自动探测，一般不致命
--host=arm-linux 编出来的东西在 ARM 上跑 编成本机 x86 的库，拷到板子上跑不起来
--prefix=... 装到哪个目录 装进 /usr/local，污染本机，还跟系统库打架

--host 是命门。省略它，configure 认为你在给本机编，工具链还是 gcc，产出的 .so 是 x86 的。你 scp 到板子上，一执行就 cannot execute binary file，排查半天才发现架构错了。

libusb 的 INSTALL 文档对这几个词的定义，抄一遍：host=TYPE 指使用交叉编译工具编译产生目标平台的文件；target=TYPE 指编译出的编译工具链将为目标平台编译产生文件。做应用和库的移植，只关心 host。

工具链前缀不是 arm-linux 的时候别硬套素材里的写法，换成自己的 --host=arm-none-linux-gnueabi。configure 接着会卡在 udev 这步：

text
configure: error: "udev support requested but libudev not installed"

板子的 sysroot 里没有 libudev，交叉编译要显式关掉，关掉之后少了热插拔事件通知，枚举和读写都正常：

bash
./configure --host=arm-linux-gnueabihf --disable-udev --prefix=`pwd`/install
make
make install

make install 会挂在下面这步：

text
../libtool: line 1085: arm-none-linux-gnueabi-ranlib: command not found
make[2]: *** [install-libLTLIBRARIES] Error 127

ranlib 找不到，是安装脚本要用 root 权限、而 root 的 PATH 里没有交叉工具链。素材里的解法是 sudo -i 进 root 再 make install，因为 sudo -i 会继承当前 shell 的环境变量，PATH 还在。sudo make install 有时不行，就是这个原因。更稳的写法是把工具链目录塞进 sudo 的环境：

bash
sudo env PATH=$PATH make install

第二个包：compat #

compat 依赖 1.0 的编译结果，做完第一个包才能做这一步，configure 时还要额外指路。

bash
cd ../libusb-compat-0.1.x
mkdir install
CROSS_COMPILE=1 CC=arm-linux-gnueabihf-gcc CXX=arm-linux-gnueabihf-g++ \
./configure --build=i686-linux --host=arm-linux-gnueabihf \
            --prefix=`pwd`/install \
            PKG_CONFIG_PATH=/home/jerry/libusb-1.0.9/install/lib/pkgconfig
make
make install

那个 PKG_CONFIG_PATH 指向第一个包的 lib/pkgconfig，里面躺着一个 libusb-1.0.pc。写绝对路径，别写 ~，sudo 和环境传递会让它失效。

compat 编完，install/include 里就有 usb.h 了，install/lib 里多出 libusb-0.1.so.4.4.4。这个目录结构就是你要拷到板子上的东西。

验证产物架构 #

别急着拷，先确认编出来的真是 ARM 的。

bash
file install/lib/libusb-1.0.so.0.1.0

text
libusb-1.0.so.0.1.0: ELF 32-bit LSB shared object, ARM, version 1 (SYSV),
dynamically linked, not stripped

关键是 ELF 32-bit 和 ARM 两个词。看见 x86-64 就是 --host 漏了，回去重编。64 位 ARM 板子上应该看到 ELF 64-bit LSB shared object, ARM aarch64。

再看符号，确认导出的是哪套 API：

bash
nm install/lib/libusb-1.0.so.0.1.0

text
00004824 T libusb_lock_event_waiters
00003304 T libusb_open
00003404 T libusb_open_device_with_vid_pid
...

全是 libusb_ 开头，没有 usb_ 开头的。这就对了，1.0 的库不带 0.1 的符号。compat 的库再查一遍：

bash
nm install/lib/libusb-0.1.so.4.4.4

text
U libusb_kernel_driver_active
U libusb_open
U libusb_ref_device
...
00001750 t usbi_log
00002f6c T usb_init
00001f94 T usb_open

U 是未定义符号，靠运行时从 libusb-1.0.so 里解；T 是导出符号，usb_init、usb_open 这些就是 compat 提供的旧 API。一个库同时有 libusb_ 和 usb_ 两套符号，说明它确实是桥接层，编对了。

六、compat 库与旧版本兼容 #

素材开头那句「usb.h 需要编译 libusb-compat-0.1.4」，是这条路上最常被忽略的一句。

有人为了一个嵌入式 Linux 的老应用要访问 Cypress 的 USB 设备，折腾了两天才搞明白：libusb-1.0.9 的版本，编出来的 include 里面没有以前写的应用程序需要的 usb.h。老代码一句 #include <usb.h> 就编不过，补头文件也没用，1.0 根本没有那套函数。

顺序是死的：先编 1.0，再编 compat。倒过来做，compat 的 configure 会直接失败。忘了设 PKG_CONFIG_PATH 时，报错长这样，完整过程在 config.log 里：

text
configure:10684: checking for arm-linux-pkg-config
configure:10717: result: no
configure:10727: checking for pkg-config
configure:10745: found /usr/bin/pkg-config
configure:10757: result: /usr/bin/pkg-config
configure:10769: WARNING: using cross tools not prefixed with host triplet
configure:10782: checking pkg-config is at least version 0.9.0
configure:10785: result: yes
configure:10795: checking for LIBUSB_1_0
configure:10802: $PKG_CONFIG --exists --print-errors "libusb-1.0 >= 0.9.1"
Package libusb-1.0 was not found in the pkg-config search path.
Perhaps you should add the directory containing `libusb-1.0.pc'
to the PKG_CONFIG_PATH environment variable
No package 'libusb-1.0' found

读这段日志能看出三件事。第一，WARNING: using cross tools not prefixed with host triplet 是警告不是错误，说明找不到 arm-linux-pkg-config，退化用了本机的 /usr/bin/pkg-config，嵌入式环境基本都这样。第二，--exists --print-errors "libusb-1.0 >= 0.9.1" 是在问 1.0 的库够不够 0.9.1，问的是 .pc 文件，不是 .so。第三，No package 'libusb-1.0' found 只有一个解法：

bash
export PKG_CONFIG_PATH=/data/libusb-1.0.x/install/lib/pkgconfig:$PKG_CONFIG_PATH

导出之后自己先验一遍，compat 就是照这个结果判断的：

bash
pkg-config --modversion libusb-1.0
pkg-config --cflags libusb-1.0
pkg-config --libs libusb-1.0

输出里带 -I.../install/include 和 -L.../install/lib，指向 ARM 那套，不是 /usr/lib 里的 x86 版。这点特别容易错：pkg-config 默认去系统路径找，系统里装着 x86 的 libusb，它找到了，configure 通过了，你编出来的 compat 就链了 x86 的 1.0。保险起见，PKG_CONFIG_LIBDIR 直接把默认搜索路径掐掉：

bash
export PKG_CONFIG_LIBDIR=/data/libusb-1.0.x/install/lib/pkgconfig

PKG_CONFIG_PATH 是追加，PKG_CONFIG_LIBDIR 是替换。嵌入式场景更推荐后者，不会串味。

链接时要同时带两个库 #

素材的后记写得很实在：应用程序链接的时候，仅链接 libusb compat 0.1.4 的 so 库，说还缺少库函数，又把 libusb 1.0.9 的 so 库加上，才链接成功。

原因是 compat 只提供 usb_* 那层壳，真正干活的 libusb_* 在 1.0 里，那些符号在 compat 里标 U。-lusb 让链接器找到壳，-lusb-1.0 让它找到肉，两个都得给。

bash
arm-linux-gnueabihf-gcc app.c -o app \
    -I/data/libusb-compat-0.1.x/install/include \
    -L/data/libusb-compat-0.1.x/install/lib \
    -L/data/libusb-1.0.x/install/lib \
    -lusb -lusb-1.0

顺序有讲究。-lusb 要写在 -lusb-1.0 前面，链接器从左往右解析，先遇到 usb_* 的引用，再去后面找 libusb_*。顺序反了照样一堆 undefined reference。

写进 Makefile 的形态，素材里给过一个能用的版本：

makefile
CC  = arm-linux-gcc
CPP = arm-linux-g++

LIBUSB_COMPAT = /home/jerry/libusb-compat-0.1.4/install
LIBUSB_10     = /home/jerry/libusb-1.0.9/install

CFLAGS  += -I$(LIBUSB_COMPAT)/include
LFLAGS_APP += -L$(LIBUSB_COMPAT)/lib -L$(LIBUSB_10)/lib \
          -lusb -lusb-1.0

-I 指向 compat 的 include，那里才有 usb.h。-L 两个目录都要给，缺一个就 cannot find -lusb-1.0。两个报错一眼定位：cannot find -lusb 说明只有 libusb-1.0 没有 compat；一屏 undefined reference to 'usb_open' 说明 -I 对了但 -lusb 没加，或者链接顺序反了。

nm 是查这个最快的工具：

bash
nm -D install/lib/libusb-0.1.so.4.4.4 | grep usb_open

T 表示这个库自己实现了，U 表示它要从别处拿。看到 U 就别指望单靠这个库够用。

七、移植到嵌入式系统的注意事项 #

编完库只算拿到半成品。板子上能不能跑起来，另一半取决于内核那边有没有准备好。

内核这几项得开：usb-core、hub、usbdevfs，以及主控那项 OHCI 或 EHCI，看你板子的 USB 控制器。

text
CONFIG_USB=y
CONFIG_USB_DEVICEFS=y
CONFIG_USB_OHCI_HCD=y

老内核里 usbfs 是个要显式打开的可选功能，配置项名字就叫 Preliminary USB Device Filesystem。不打开它，/proc/bus/usb 一直是个空目录。

卡住的那个下午 #

素材里这段过程值得完整走一遍，它踩的恰好是「libusb 到底靠什么找设备」这个点。

库编好了，整个目录拷到 NFS 挂载点，改 /etc/profile 加库路径：

bash
cp -a /usr/local/libusb/libusb-arm /usr/nfs/
export LD_LIBRARY_PATH=/mnt/libusb-arm/.libs:$LD_LIBRARY_PATH

程序在板子上跑起来，只打出 usbtest-arm、bus/device idVendor/idProduct 和一排星号，中间一条记录都没有。第一层 for 循环都没进去，bus 一个都没找到。

回头看 libusb 的源码，linux.c 里的 usb_os_init(void) 是靠环境变量 USB_DEVFS_PATH 决定去哪儿找总线的，默认从 /dev/bus/usb 和 /proc/bus/usb 开始扫。而板子上：没有 /dev/bus；有 /proc/bus/usb，但里面一个文件都没有。

对照 PC。一台 2.4 内核的 Redhat 9.0，也没有 /dev/bus，但 /proc/bus/usb 下面有 001/、002/、devices、drivers 四个东西，能用。一台 2.6 内核的 FC6：

text
$ ls -l /dev/bus/usb/
total 0
drwxr-xr-x 2 root root 60 Feb 27 20:09 001
drwxr-xr-x 2 root root 60 Feb 27 20:09 002

$ ls -l /proc/bus/usb/
total 0
dr-xr-xr-x 2 root root 0 Feb 28 04:09 001
dr-xr-xr-x 2 root root 0 Feb 28 04:09 002
-r--r--r-- 1 root root 0 Feb 28 04:09 devices

两套都有，是同一份总线的两个视图。板子上一份都没有，问题在内核配置或环境，不在 libusb。

想靠 USB_DEVFS_PATH 绕过去也绕不动。插上 U 盘，它出现在 /dev 的某个位置；插上 USB 鼠标，又是另一个位置，路径不统一，设一个统一的查找路径行不通。

真正的答案在 libusb 邮件列表和 linux-usb 官网的一篇文档里：

text
The USB device filesystem is a dynamically generated filesystem, similar to
the /proc filesystem. This filesystem can be mounted just about anywhere,
however it is customarily mounted on /proc/bus/usb ...

You need to select "Preliminary USB Device Filesystem" to make this work.
You also need to enable general /proc support, and to have it mounted
(normally automatic).

To mount the filesystem, you need to be root. Use the mount command:
mount -t usbdevfs none /proc/bus/usb

三句话拆开看，全是关键点。

  • 这个文件系统是内核动态生成的，像 /proc 一样，本身不占磁盘。目录存在不等于内容存在，它得被挂上。
  • 习惯挂载点在 /proc/bus/usb，这个入口节点由 USB 代码本身创建。
  • 挂载要 root。-t usbdevfs 是文件系统类型，none 是设备名占位符，写什么都行。

手动挂一次，不想每次重启都挂就加进 /etc/fstab，放在 /proc 那行后面：

bash
mount -t usbdevfs none /proc/bus/usb

text
none /proc/bus/usb usbdevfs defaults 0 0

挂好之后 /proc/bus/usb 的内容：

text
dr-xr-xr-x 1 root root 0 Jan 26 10:40 001
-r--r--r-- 1 root root 0 Jan 26 10:40 devices
-r--r--r-- 1 root root 0 Jan 26 10:40 drivers

再跑一次那个测试程序，插着 U 盘：

text
usbtest-arm
bus/device idVendor/idProduct
hello,dell 1 !
hello,dell 2 !
001/001 0000/0000
hello,dell 2 !
001/002 0471/0000
*****************************

过了。第一层循环进去了，第二层也进去了，VID/PID 打出来了。

2.6.11 之后的路子换成 devtmpfs 加 udev，内核自己建 /dev/bus/usb/BBB/DDD 节点，不再有人去挂 usbdevfs。板子上如果是这种内核，只要 ls /dev/bus/usb/ 有 001、002 这样的目录、lsusb 能列出设备，就不用管挂载。lsusb 列不出来，先查内核配置和 USB 控制器驱动，别改 libusb。

交叉编译时的报错 #

make 阶段有个常见的拦路虎：

text
cc1: warnings being treated as errors

老代码在新工具链上编，一堆 warning 被 -Werror 提升成 error。Makefile 里把 -Werror 去掉就是了。tests 子目录里还会报一个 uppercase 相关的错误，和主库无关，注释掉那一项或者不进 tests 编译。真正要的是 .libs 里那几个文件。

产物藏在隐藏目录 #

不做 make install、只用源码树里编出来的库时，成品在 .libs 这个隐藏文件夹里：

text
libusb-0.1.so.4.4.4
libusb.a
libusbpp.a
libusbpp-0.1.so.4.4.4

ls 看不见它们，要 ls -a 或者直接 ls .libs。素材里整个目录拷到 NFS，运行时靠 LD_LIBRARY_PATH 指到 .libs，路径里那个点别丢。程序里的编译参数也要跟上：

makefile
LIBUSB = /usr/local/libusb/libusb-arm
CFLAGS  += -I$(LIBUSB)
LDFLAGS += -L$(LIBUSB)/.libs -lusb

拷到板子上之后动态库得能被找到，三种办法：环境变量 export LD_LIBRARY_PATH=/mnt/libusb-arm/.libs:$LD_LIBRARY_PATH 最临时；写进 /etc/profile 开机就有；cp libusb-1.0.so* /usr/lib/ 再 ldconfig 是产品形态。调试用第一种，出货用第三种。

老代码那套 0.1 接口 #

板子上跑的是老应用，用的就是 compat 那层壳。这套函数的全部内容，一张表看完。

分类 函数 一句话说明
初始化 usb_init() 最先调用，无参数，不调后面全废
初始化 usb_find_busses() 找总线，返回总线数
初始化 usb_find_devices() 找设备，必须在 usb_find_busses() 之后
初始化 usb_get_busses() 返回总线链表头，新版本直接读全局 usb_busses
设备 usb_open() 打开设备，返回 usb_dev_handle *
设备 usb_close() 关设备，必须调，返回 0 成功
设备 usb_set_configuration() 设当前 configuration，参数取 bConfigurationValue
设备 usb_set_altinterface() 设 interface 的 bAlternateSetting
设备 usb_claim_interface() 注册接口，必须调，参数取 bInterfaceNumber
设备 usb_release_interface() 注销接口，和 claim 配对
设备 usb_resetep() 复位端点，已被 usb_clear_halt 取代
设备 usb_clear_halt() 复位端点，参数取 bEndpointAddress
设备 usb_reset() 复位设备，复位完还得重新 open，用得少
控制传输 usb_control_msg() 走默认管道收发控制数据
控制传输 usb_get_descriptor() 读描述符
控制传输 usb_get_descriptor_by_endpoint() 按端点读描述符
控制传输 usb_get_string() 读字符串描述符，要指定 langid
控制传输 usb_get_string_simple() 读字符串描述符，语言自动选
批量传输 usb_bulk_write() 批量写，超时单位毫秒
中断传输 usb_interrupt_read() 中断读，超时单位毫秒

这套函数对应的数据结构在 usb.h 和 usbi.h 里。usb_dev_handle 是你的句柄，usb_device 是设备，usb_bus 是总线，三个结构串成链表：

c
struct usb_dev_handle {
    int fd;
    struct usb_bus *bus;
    struct usb_device *device;
    int config;
    int interface;
    int altsetting;
    void *impl_info;
};

struct usb_device {
    struct usb_device *next, *prev;
    char filename[PATH_MAX + 1];
    struct usb_bus *bus;
    struct usb_device_descriptor descriptor;
    struct usb_config_descriptor *config;
    void *dev;
};

struct usb_bus {
    struct usb_bus *next, *prev;
    char dirname[PATH_MAX + 1];
    struct usb_device *devices;
};

usb_dev_handle.fd 是底下的文件描述符，出错时看它是不是 -1，比看返回值快。usb_device.filename 是总线上的编号，001、002 这种东西，和 bus->dirname 拼起来正好是 /dev/bus/usb/001/002 的最后两段。

八、权限与 udev 规则 #

/dev/bus/usb/001/002 这类节点属主是 root，属组是 root，默认 crw-rw-r--。

bash
$ ls -l /dev/bus/usb/001/002
crw-rw-r-- 1 root root 189, 1 Nov 18 12:00 /dev/bus/usb/001/002

普通用户没写权限，libusb_open 就返回 LIBUSB_ERROR_ACCESS，值 -3。程序编过了、设备也枚举出来了，一 open 就失败，八成是这里。先确认 VID/PID，lsusb 的输出形如 Bus 001 Device 002: ID 04b4:8613 Cypress Semiconductor Corp.，04b4 是 idVendor，8613 是 idProduct。

新建规则文件，编号选个不冲突的：

bash
sudo vi /etc/udev/rules.d/99-usb-mydevice.rules

给所有用户读写权限，或者只给组：

text
SUBSYSTEM=="usb", ATTR{idVendor}=="04b4", ATTR{idProduct}=="8613", MODE="0666"

text
SUBSYSTEM=="usb", ATTR{idVendor}=="04b4", ATTR{idProduct}=="8613", GROUP="plugdev", MODE="0660"

plugdev 组在 Debian/Ubuntu 上默认存在，把人加进去，重登一次才生效，groups 里看得到 plugdev 才算：

bash
sudo usermod -aG plugdev $USER

规则写完让 udev 认一下，然后把设备拔了重插，再 ls -l 那个节点，权限应该变了：

bash
sudo udevadm control --reload-rules
sudo udevadm trigger

规则没生效，用 sudo udevadm info -a -n /dev/bus/usb/001/002 查它到底匹配到了什么。-a 打印所有能用来匹配的属性，从上往下依次往规则里加，加得越少匹配越宽，VID/PID 两条就够。

三个细节。文件名前面的数字决定加载顺序，99- 是留给自定义规则的，排在 50- 开头的系统规则后面，能覆盖前面的设置。ATTR{} 和 ATTRS{} 不一样，前者只看当前设备节点这一层，后者搜整条父设备链，USB 设备的 VID/PID 挂在设备本身，用 ATTR{}。别用 chmod 666 手动改节点权限当方案，设备一拔一插节点重建，权限回到默认，下次还得改。

内核驱动抢着用的设备 #

设备已经有内核驱动接管，libusb_claim_interface 会返回 LIBUSB_ERROR_BUSY。1.0 的做法是打开设备之后调一次 libusb_set_auto_detach_kernel_driver(handle, 1)，之后 claim 时库自己帮你 detach，关设备时自动 re-attach。不想用这个开关就手动 libusb_detach_kernel_driver(handle, interface)，0.1 那边是另一套，名字带 _np：usb_detach_kernel_driver_np(handle, interface)。

Windows 上没有这一层。设备绑给 WinUSB 或 libusbK 之后，系统驱动不会占着它，所以 Windows 侧不需要 udev 也不需要 detach。这也是 Windows 上装驱动那一步绕不开的原因。

九、编译产物与集成 #

编完拿到的东西按用途分三类：头文件、动态库、静态库。往工程里放哪个，取决于产品形态。

以 1.0 为例，make install 之后的产物：

text
install/include/libusb-1.0/libusb.h
install/lib/libusb-1.0.a
install/lib/libusb-1.0.so -> libusb-1.0.so.0
install/lib/libusb-1.0.so.0 -> libusb-1.0.so.0.1.0
install/lib/libusb-1.0.so.0.1.0
install/lib/pkgconfig/libusb-1.0.pc

compat 那套多出来 install/include/usb.h、install/lib/libusb.a、install/lib/pkgconfig/libusb.pc，以及 libusb-0.1.so 那一串版本号不同的名字。

符号链接要一起拷，别只拷实文件。程序运行时按 SONAME 找 libusb-1.0.so.0，找不到照样起不来。

静态库还是动态库 #

对比项 动态库 .so 静态库 .a
运行时依赖 要拷 .so 到板子 无
传程序 程序要带着库一起传 一个可执行文件搞定
体积 多个程序共享一份 每个程序各带一份
升级库 换 .so 即生效 要重新链接
板子上要 ldconfig 要 不要
调试 可以单独换库试 只能重编

调试阶段用动态库，改一版库不用重编应用。出货、板子空间紧、或者不想让客户乱动库文件，用静态库。强制链静态库：

bash
arm-linux-gnueabihf-gcc app.c -o app \
    -Iinstall/include -Linstall/lib \
    -Wl,-Bstatic -lusb-1.0 -Wl,-Bdynamic

-Wl,-Bstatic 和 -Wl,-Bdynamic 成对用，中间夹住要静态链的库，换回动态是为了后面链 libc 别也静态了。目录里只有 .a 没有 .so 时，链接器自动选静态，-Linstall/lib -lusb-1.0 就够了。

拷到板子上 #

最直接的办法是整目录拷，靠 LD_LIBRARY_PATH 找：

bash
scp -r install/ root@192.168.1.100:/opt/libusb
export LD_LIBRARY_PATH=/opt/libusb/lib:$LD_LIBRARY_PATH

产品形态别用环境变量，装到系统路径里：

bash
cp /opt/libusb/lib/libusb-1.0.so* /usr/lib/
cp -a /opt/libusb/include/libusb-1.0 /usr/include/
ldconfig

ldconfig 读 /etc/ld.so.conf 和 /etc/ld.so.conf.d/*.conf，把库记进 /etc/ld.so.cache，之后程序启动不用环境变量也能找到。装在 /usr/local/lib 的话，得确认那个目录在 ld.so.conf 里。

把库并进构建系统 #

工程大了换 CMake，用 .pc 文件比自己找路径稳：

cmake
find_package(PkgConfig REQUIRED)
pkg_check_modules(LIBUSB REQUIRED libusb-1.0)

include_directories(${LIBUSB_INCLUDE_DIRS})
link_directories(${LIBUSB_LIBRARY_DIRS})
add_executable(app main.c)
target_link_libraries(app ${LIBUSB_LIBRARIES})

交叉编译时把 PKG_CONFIG_PATH 导给 CMake，.pc 找对了，find_package 就找对了：

bash
PKG_CONFIG_PATH=/opt/libusb/lib/pkgconfig cmake ..

CMake 也能直接指定，不依赖 .pc：

bash
cmake -DCMAKE_C_COMPILER=arm-linux-gnueabihf-gcc \
      -DCMAKE_SYSTEM_NAME=Linux \
      -DCMAKE_SYSTEM_PROCESSOR=arm ..

要更细的控制就写 toolchain 文件，把 sysroot、编译器、查找根目录全钉住。这一步做错的表现和漏 --host 一样：编出来的程序在本机能跑，拷过去跑不了。

十、验证安装是否成功 #

装完别急着写业务代码，按这个顺序验一遍，五分钟能省一下午。

库在不在：pkg-config --modversion libusb-1.0 有版本号输出，说明 .pc 在位；报 No package 'libusb-1.0' found，就是 PKG_CONFIG_PATH 没设或者设错了。交叉编译的产物不用 pkg-config，直接 file install/lib/libusb-1.0.so.0.1.0 看架构。

系统的 USB 栈通不通：lsusb 能列出设备，说明内核的 USB 子系统是好的，/dev/bus/usb 也在；列不出来问题在内核，跟 libusb 无关。lsusb -t 看拓扑，主机控制器、hub、设备挂在哪一级一目了然。

libusb 自己能不能枚举：写个只做枚举的最小程序，不碰设备。

c
#include <stdio.h>
#include <libusb-1.0/libusb.h>

int main(void)
{
    libusb_device **list;
    ssize_t cnt, i;

    if (libusb_init(NULL) < 0) {
        printf("init failed\n");
        return 1;
    }

    cnt = libusb_get_device_list(NULL, &list);
    if (cnt < 0) {
        printf("get_device_list failed\n");
        libusb_exit(NULL);
        return 1;
    }

    printf("found %ld devices\n", (long)cnt);
    for (i = 0; i < cnt; i++) {
        struct libusb_device_descriptor desc;
        if (libusb_get_device_descriptor(list[i], &desc) == 0) {
            printf("%04x:%04x  bus %d  addr %d\n",
                   desc.idVendor, desc.idProduct,
                   libusb_get_bus_number(list[i]),
                   libusb_get_device_address(list[i]));
        }
    }

    libusb_free_device_list(list, 1);
    libusb_exit(NULL);
    return 0;
}

bash
gcc enum.c -o enum $(pkg-config --cflags --libs libusb-1.0)

能打出设备列表，说明 libusb 装好、权限配好、枚举链路全通。这是每次移植完必跑的第一个程序，比任何测试都直接。

打开设备试一次：枚举成功但 libusb_open 返回 -3，是权限问题，回第八章加 udev 规则；返回 LIBUSB_ERROR_NO_DEVICE（-4），是设备被拔了或者句柄失效，重插再试。交叉编译版在板子上跑，记得先把库路径给上，不然程序起不来，报的是 error while loading shared libraries: libusb-1.0.so.0，跟权限一点关系没有。

0.1 的验证程序 #

素材里那个测试程序，直接拿来验证 compat 这条线。它只用 0.1 的 API，正好当冒烟测试：

c
/* testlibusb.c */
#include <stdio.h>
#include <usb.h>

int main(void)
{
    struct usb_bus *bus;
    struct usb_device *dev;

    usb_init();
    usb_find_busses();
    usb_find_devices();

    printf("bus/device idVendor/idProduct\n");

    for (bus = usb_busses; bus; bus = bus->next) {
        printf("hello,dell 1 !\n");
        for (dev = bus->devices; dev; dev = dev->next) {
            printf("hello,dell 2 !\n");
            printf("%s/%s %04X/%04X\n",
                   bus->dirname,
                   dev->filename,
                   dev->descriptor.idVendor,
                   dev->descriptor.idProduct);

            if (!dev->config) {
                printf(" Couldn't retrieve descriptors\n");
                continue;
            }
        }
    }

    printf("*****************************\n");
    return 0;
}

bash
arm-linux-gnueabihf-gcc testlibusb.c -o usbtest-arm \
    -Iinstall/include -Linstall/lib -lusb -lusb-1.0

正常输出：

text
bus/device idVendor/idProduct
hello,dell 1 !
hello,dell 2 !
001/001 0000/0000
hello,dell 2 !
001/002 0471/0000
*****************************

只打出标题和星号、中间一行 hello 都没有，是找不到总线，回去看第七章：挂载有没有做，内核配置有没有开。hello,dell 1 ! 出现、001/001 不出现，是总线上没设备，把目标设备插上。

usb_busses 是个全局变量，老版本靠 usb_get_busses() 取，新一点的版本直接用，两种写法都能编。这是 0.1 时代的一个历史痕迹。

十一、常见编译错误 #

把这条路上真能撞见的错误收一遍，按报错原文查。

阶段 报错原文 原因与解法
configure udev support requested but libudev not installed sysroot 没 libudev，加 --disable-udev
configure Package libusb-1.0 was not found in the pkg-config search path compat 找不到 1.0 的 .pc，设 PKG_CONFIG_PATH
configure C compiler cannot create executables CC 指错或工具链坏，先单跑 gcc -v
configure checking whether we are cross compiling... error --build 和 --host 写成了同一个值
make cc1: warnings being treated as errors 老代码被 -Werror 拦了，Makefile 删掉它
make 'PATH_MAX' undeclared 新工具链不再间接带 linux/limits.h，源码补 #include <limits.h>
make No rule to make target 'xxx' 老 autotools 工程的并行依赖不全，改 make 单线程
make install arm-none-linux-gnueabi-ranlib: command not found root 的 PATH 没工具链，sudo -i 或 sudo env PATH=$PATH
make install cannot create regular file '/usr/local/lib/...': Permission denied --prefix 指到系统目录但没权限，加 sudo 或换前缀
链接 cannot find -lusb 缺 compat 库，或 -L 没指到它的 lib 目录
链接 undefined reference to 'usb_open' 头文件对了但 -lusb 没加，或链接顺序反了
链接 undefined reference to 'libusb_open' 只给了 -lusb，补上 -lusb-1.0
链接 skipping incompatible ./libusb-1.0.so -L 指到了系统的 x86 目录，把自有路径写在 /usr/lib 前面
运行 libusb-1.0.so.0: cannot open shared object file 运行时找不到库，LD_LIBRARY_PATH 或 ldconfig
运行 cannot execute binary file: Exec format error 架构错了，--host 漏了，file 一下重编
运行 LIBUSB_ERROR_ACCESS 设备节点没权限，第八章的 udev 规则
运行 LIBUSB_ERROR_BUSY 内核驱动占着接口，auto detach 或手动 detach

十二、易错点速查 #

现象 根因 一条命令修
板子上跑不了，提示 Exec format error 漏了 --host，编成本机架构 file 查一下，重 configure
.so 里全是 libusb_ 没有 usb_ 只编了 1.0，没编 compat 编 compat，-lusb 补上
老代码报 usb.h: No such file 1.0 的 include 里没有 usb.h 编 compat，-I 指到 compat
cannot find -lusb 缺 compat 库 装 libusb-dev 或编 compat
一屏 undefined reference 两个库只链了一个，或顺序反了 -lusb -lusb-1.0，顺序别动
compat 的 configure 找不到 1.0 PKG_CONFIG_PATH 没设 指向 1.0 的 lib/pkgconfig
configure 报 udev 找不到 板子 sysroot 没 libudev --disable-udev
make install 报 ranlib not found root 的 PATH 丢了工具链 sudo -i 后重装
make 报 warnings as errors -Werror 太严 Makefile 删 -Werror
枚举不到任何设备（老内核） usbdevfs 没挂 mount -t usbdevfs none /proc/bus/usb
枚举不到任何设备（新内核） 内核没开 USB 或控制器驱动 查 config，先 lsusb 证实
libusb_open 返回 -3 /dev/bus/usb/* 没权限 加 udev 规则
libusb_claim_interface 返回 BUSY 内核驱动占着设备 auto detach 或手动 detach
Windows 上设备列表是空的 没给设备绑 WinUSB/libusbK Zadig 走一遍
Windows 上 dll 加载失败 位数不匹配或 dll 不在路径 32/64 位对齐，dll 放同目录
程序启动报 cannot open shared object 运行时找不到 .so LD_LIBRARY_PATH 或 ldconfig
库编过了但 pkg-config 找不到 .pc 不在搜索路径 PKG_CONFIG_PATH 指过去

三条最值钱的，单独拎出来。

--host 是交叉编译的命门。漏了它，一切编译都能成功，make 不报错，make install 也不报错，你以为完事了，拷到板子上才发现跑不了。养成习惯：编完先 file 一下。

-lusb 和 -lusb-1.0 是两个库。compat 是壳，1.0 是肉。壳自己干活干不了，肉没有壳老代码认不出来。两个都要，顺序别反。

老内核要挂 usbdevfs。新内核不用，但你得知道有那么一道挂载存在过，不然在旧板子上看到 /proc/bus/usb 空着，会一直怀疑是库编坏了。

环境到这就齐了。下一步是拿这套库去枚举设备、解析描述符、读数据，接《libusb 编程》。
