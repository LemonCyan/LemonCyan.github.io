这一篇只干一件事：在 RK3399 板子的内核里，把 USB 总线上跑的数据抓下来，然后读懂它。

讲什么：usbmon 在内核的哪一层、debian 11 + linux 4.19.193 上怎么把它启用起来、三种抓包方式怎么取舍、日志里每一列什么意思、S 记录和 C 记录怎么配对、控制传输与中断传输的日志各长什么样、抓不到数据时按什么顺序排查。

不讲什么：用 libusb 在用户态读写设备，看同目录的《RK3399 实战：用 libusb 读写 USB 设备》；libusb 的同步与异步 API 怎么组织，看《libusb 编程：从同步到异步》；libusb 的编译、交叉编译与移植，看《安装与交叉编译》。

两篇的分工摆明：libusb 那篇是「我写代码把数据读出来」，手里有设备句柄、有返回值、有错误码；这一篇是「先不写代码，看清楚总线上到底在跑什么」，手里只有一串十六进制。抓包在前，写码在后，能省掉一大半瞎猜。

运行环境是固定的，后面每条命令输出都来自这一套，换内核版本字段格式会有出入。

一、为什么要在内核里抓 USB 包 #

一个 USB 设备插上板子，内核驱动立刻接管。你在 /dev/input/eventX、/dev/hidrawX 上能拿到数据，但那是驱动处理完之后的结果，不是总线上跑的东西。

驱动把字节嚼碎了 #

以 HID 触摸屏为例。总线上来的是 52 个字节的原始报文，里面有报告 ID、触摸点编号、X 坐标、Y 坐标、接触面积。经过 usbhid → hid-multitouch → input 子系统三层，你最终读到的是一个 input_event 结构：类型 EV_ABS、轴 ABS_MT_POSITION_X、值 2421。

这中间所有信息都还在，但已经不是一个整体了。你没法回答下面这些问题：

  • 报告描述符解析对了吗？那个字节到底该按有符号还是无符号读？
  • 设备是不是真的上报了 6 个触摸点，还是只有 4 个字段有值？
  • 每隔多久上报一次？间隔稳定吗？
  • 有没有 STALL，有没有重试？

用户态读不到原始报文 #

用 libusb 直接在用户态发 URB，能拿到原始 52 字节，这条路解决了一半问题，但仍然看不到下面这些：

  • 内核自己发起的请求。枚举时的那一串 GET_DESCRIPTOR、SET_CONFIGURATION，走的是内核的 usb_control_msg，你在用户态根本碰不到。
  • 驱动和设备之间的空闲轮询。你没发请求的时候，中断端点照样被轮询，数据照样回来。
  • 出错的那一次。libusb 只给你一个 LIBUSB_ERROR_IO，具体是超时、是 STALL、还是校验错，它不告诉你。

这三样全都要在内核里看，usbmon 就是干这个的。

抓包能回答的四类问题 #

问题 抓包能给出的证据
设备到底有没有回数据 有没有 C 记录，C 记录的长度字段是多少
回的字节对不对 = 后面那串十六进制，逐字节对齐报告描述符
传输出没出错 C 记录的 URB status，0 是成功，负数是 errno
一次传输多久 同一个 URB 的 S 与 C 时间戳之差，单位微秒

这四类问题覆盖了调试 USB 设备时的绝大多数场景。电气层信号质量不在此列，那得上示波器。

抓包看不到什么 #

usbmon 挂在 URB 层，不在包层。所以日志里没有这些东西：

  • 令牌包。SETUP、IN、OUT、SOF 这些发起事务的包，一条都看不到。
  • 握手包。ACK、NAK、STALL 这些确认包，同样没有。
  • 总线复位、挂起、恢复的具体时序。这些属于主机控制器层，usbmon 只记 URB 提交和回调。

usbmon 只抓事务里的数据包，不抓令牌包和握手包。你看到的是主机提交的 URB、以及 URB 完成后带回来的数据。

这个限制听起来很致命，实际上不影响排查。绝大多数问题出在「数据不对」和「根本没回」，这两样 URB 层全都有。

什么时候别急着抓包 #

抓包本身有代价，不是所有问题都值得上。

  • 设备枚举失败，先看 dmesg。内核日志里 new full-speed USB device number 4 之后有没有 device descriptor read/64, error -71，一眼就能定性。
  • 权限问题，先看 /dev/bus/usb 的属主。抓包只会告诉你 LIBUSB_ERROR_ACCESS 之前的那部分，帮不上忙。
  • 驱动没加载，先看 lsmod。没驱动就没 URB，抓出来是空的。

这三类问题用常规手段三十秒能定位，抓包反而慢。

二、usbmon 是什么 #

usbmon 就是 usb monitor，Linux 内核自带的 USB 抓包设施，从 2.6.x 就有了，不是什么外挂工具。

一个内核模块加一个 debugfs 接口 #

它由两部分构成：内核模块 usbmon.ko（位置在 /lib/modules/4.19.193/kernel/drivers/usb/mon/usbmon.ko），以及模块加载后通过 debugfs 暴露的字符接口（挂载点在 /sys/kernel/debug/usb/usbmon/）。

模块负责在 USB 核心的几个关键位置挂钩子：URB 提交、URB 完成、URB 提交失败。每命中一次钩子，就往环形缓冲里写一条记录。你 cat 那个文件，就是在读这个缓冲。所以它不是「监听总线电平」，别把它和硬件协议分析仪混为一谈。它拿的是内核自己知道的信息，代价极低，也拿不到内核不知道的东西。

抓的是 URB，不是「包」 #

这一节是本篇的地基，读不懂这里，后面全是天书。

USB 传输在内核里不是一个字节流，是一个个 struct urb。驱动想发数据，就填一个 URB，调 usb_submit_urb 交出去；等传输结束，内核回调 complete，URB 回到驱动手里。

usbmon 就挂在这两个点上：

  • URB 被提交 → 写一条 S 记录（submission）
  • URB 完成回调 → 写一条 C 记录（callback）
  • 提交时出错 → 写一条 E 记录（submission error）

所以日志里同一个 URB 会出现两次。这不是重复，这是它的生命周期两头各留了一个脚印。

看一段真实日志，中间那两行是一条 URB：

text
ffffffc0c88dab00 1925763683 S Ii:1:004:2 -115:1 52 <
ffffffc0c88dab00 1925775309 C Ii:1:004:2 0:1 52 = 01010075 09080930 00000000 00000000 00000000 00000000 00000000 00000000

第一行 S，说「我要读 52 字节」。第二行 C，说「读完了，实际给你 52 字节，内容在这」。两行的第一列完全一样：ffffffc0c88dab00，这就是同一个 URB 的地址。理解这一点，时间线才对得上。把日志当成一包一条来读，永远会疑惑「为什么数据出现两次」。

条数大约是传输次数的两倍 #

一次传输两条记录，这是估算日志规模的基准。10 秒钟的中断轮询、1ms 一次间隔，就是一万次传输、两万行日志，这个量级用 cat 打到屏幕上是灾难。E 记录是个例外，它只在提交失败时出现，而且没有对应的 C，看到它就说明这个 URB 连总线都没上去。

它在 URB 层，所以粒度和包不一样 #

一个常见误解：批量传输把数据拆成多个包发出去，那我应该在日志里看到多条记录。不会。一次批量传输会被拆成十几个包，usbmon 只给你一条 S 和一条 C，拆包是主机控制器干的活。

反过来，一条 C 记录里的数据长度小于请求长度，说明设备只回了一部分。这个信息在日志层面才有，包层面早就丢了。

三种事件的判别方法 #

事件类型 全称 出现时机 有没有对应记录
S submission 驱动调 usb_submit_urb 成功返回 后面会跟一条 C
C callback 传输结束，回调被调用 前面有一条 S
E submission error usb_submit_urb 直接返回错误 孤立一条，没有配对

后面第五、第六两章会把这三者的字段拆开讲，这里先把概念立住：S 是出发，C 是到达，E 是连门都没出。

它和 tcpdump、Wireshark 是什么关系 #

不是竞争关系，是同一份数据的三种读法。usbmon 是数据源，tcpdump 和 Wireshark 是消费者：前者通过 libpcap 的 usbmon 支持去读那个字符设备，后者再读 tcpdump 存下来的 pcap。所以不管用哪种方式，第一件事都是把 usbmon 模块加载起来。

三、启用 usbmon #

启用分两步：挂 debugfs、装模块。debian 11 上前一步多半已经做好了，后一步不一定。

第一步：挂 debugfs #

bash
root@SOM-RK3399v2:/# mount -t debugfs none /sys/kernel/debug
mount: /sys/kernel/debug: none_debugs already mounted or mount point busy.

报这句就对了，说明系统默认已经挂过 debugfs，下次抓包不用再跑这条命令；真没挂的话这条命令会静默成功。

第二步：确认内核支不支持 #

bash
root@SOM-RK3399v2:/# ls /sys/module/usbmon
ls: cannot access '/sys/module/usbmon': No such file or directory

模块还没加载。这里要区分两件事：模块没加载时 /sys/module/usbmon 不存在但 .ko 文件在，modprobe 一下就好；模块根本没编译进内核时 .ko 文件也不存在，那得重新编内核、把 CONFIG_USB_MON 打开。判断方法：

bash
root@SOM-RK3399v2:/# find /lib/modules/$(uname -r) -name 'usbmon*'
/lib/modules/4.19.193/kernel/drivers/usb/mon/usbmon.ko

有这一行就是前者，改配置就能解决。一行都没有就是后者，回去编内核。

要是 usbmon 已经编进内核（配成 =y 而不是 =m），那不需要装模块，/sys/module/usbmon 一开始就在。

第三步：装模块，先撞一次 PATH 的墙 #

bash
root@SOM-RK3399v2:/# modprobe usbmon
bash: modprobe: command not found

这不是模块的问题，是 PATH 的问题。debian 11 的 root 默认 PATH 里没有 /usr/sbin，而 modprobe 就住在那里。

临时绕过去：

bash
root@SOM-RK3399v2:/# export PATH=/usr/sbin:$PATH

关掉终端就没了。要持久得改 /etc/profile：

bash
root@SOM-RK3399v2:/# vim /etc/profile

找到设置 PATH 的那一行，追加：

bash
export PATH=/usr/sbin:$PATH

改完必须 source /etc/profile 才会在当前 shell 里生效。用绝对路径 /usr/sbin/modprobe usbmon 也能绕过 PATH，但每次敲全路径太烦。

第四步：验证加载成功 #

bash
root@SOM-RK3399v2:/# modprobe usbmon
root@SOM-RK3399v2:/# ls /sys/module/usbmon
coresize  holders  initsize  initstate  notes  refcnt  sections  srcversion  taint  uevent

出现这一堆目录就成功了。原理是模块初始化时调用 debugfs 的 API 注册文件，于是在 /sys/kernel/debug/usb/ 下面长出一个 usbmon 目录。

bash
root@SOM-RK3399v2:/# ls /sys/kernel/debug/usb/usbmon
0s  0u  1s  1t  1u  2s  2t  2u  3s  3t  3u  4s  4t  4u  5s  5t  5u  6s  6t  6u

命名规则很直接：

部分 含义
数字 USB 总线号，0 表示所有总线
u 文本格式，给人看的
s 二进制格式，给 Wireshark 这类工具看的
t 二进制格式的另一种变体，带更多元数据

这块板子有 6 条 USB 总线，所以编号 1~6。0u 是「全部总线的文本视图」，调试时最常用。

开机自动加载 #

内核 4.19.193 启动时不会自动去 /lib/modules/4.19.193/ 下面扫模块。要让 usbmon 开机就位，两步。

第一，重建模块依赖：

bash
root@SOM-RK3399v2:/# depmod -a

depmod 分析模块之间的依赖关系，-a 表示探测所有模块，结果写进 modules.dep。少了这一步，modprobe 会找不到目标。

第二，写进 /etc/modules：

text
# /etc/modules: kernel modules to load at boot time.
# This file contains the names of kernel modules that should be loaded
# at boot time, one per line. Lines beginning with "#" are ignored.
usbmon

一个模块一行，# 开头是注释。重启之后验证：

bash
root@SOM-RK3399v2:/# lsmod | grep usbmon
usbmon                 36864  0
root@SOM-RK3399v2:/# ls /sys/module/usbmon
coresize  holders  initsize  initstate  notes  refcnt  sections  srcversion  taint  uevent

完整 lsmod 里有几十个模块，只看 usbmon 这一行就够了。第三列 0 表示当前没有程序在用，正常；你 cat 抓包文件的时候，这一列会变成 1。

别忘了权限 #

/sys/kernel/debug/usb/usbmon/0u 的属主是 root，权限 0400 起步。非 root 用户读会得到 Permission denied。板上直接用 root 最省事，要通过 ssh 转发给别的机器，就得处理权限，这一段放到十一章讲开销时一起说。

四、抓包的三种方式 #

同一份 usbmon 数据，三种读法。选错的代价是浪费半天。

方式一：直接读 debugfs 文本 #

bash
root@SOM-RK3399v2:/# cat /sys/kernel/debug/usb/usbmon/0u

最原始的办法，零依赖。usbmon.ko 一加载，这个文件就在，板上不需要装任何东西。

  • 不需要额外软件。交叉编译环境里经常连 tcpdump 都没有；输出就是文本，可以直接 grep、awk、重定向到文件慢慢看；格式稳定，4.19 内核里所有小版本一致。
  • 没有过滤，全总线数据一起涌出来，只想看一个设备得自己 grep；shell 管道有延迟，高频率轮询时跟不上；数据量大时终端直接卡死。

这块板子上我们用的就是它。理由很实在：板子上没装 tcpdump，也不想为一个抓包去交叉编译一个。

方式二：tcpdump 走 libpcap #

bash
root@SOM-RK3399v2:/# tcpdump -i usbmon0 -w /tmp/usb.pcap

前提是 tcpdump 和 libpcap 都支持 usbmon。libpcap 1.0 以后就支持了，debian 11 源里的版本没问题。

  • BPF 过滤在内核里执行，不匹配的包根本不上来，开销比 grep 低一个量级；直接存 pcap，可以拷回 PC 用 Wireshark 打开；支持 -c 限制包数、-G 按时间切片。
  • 得先装上，板上没有就得 apt 装，离线环境就得交叉编译；过滤能力也有限，只能按地址和传输类型过滤，不能按数据内容过滤，文本输出格式和 debugfs 还不一样。

方式三：usbmon 加 Wireshark #

bash
# 板上先抓成 pcap
root@SOM-RK3399v2:/# tcpdump -i usbmon0 -w /tmp/usb.pcap
# 拷回 PC
$ scp root@192.168.1.100:/tmp/usb.pcap .
# PC 上打开
$ wireshark usb.pcap
  • 能解析协议，这是它唯一真正的优势，也是决定性的优势。控制传输的 bmRequestType、bRequest 会被翻译成 GET_DESCRIPTOR、SET_CONFIGURATION 这样的名字，HID 报文会被拆成字段。
  • 图形界面里 S 和 C 自动配对，点一条 S 就能跳到对应 C。
  • 板上跑不起来，得来回拷文件；装 Wireshark 的机器需要 USB 解析插件，版本太老会解析不出来；数据量大时会卡。

三种方式怎么选 #

维度 debugfs 文本 tcpdump Wireshark
板端依赖 无 tcpdump + libpcap tcpdump + libpcap
过滤能力 shell 管道，事后过滤 BPF，内核态过滤 显示过滤器，事后过滤
协议解析 无 部分 完整
S/C 配对 手动看指针 手动看指针 自动
上手成本 最低 中 中，但需图形界面
适合场景 板上快速看一眼 长时间抓、大数据量 事后深度分析
我们的用法 第一次接触某个设备 抓长时间日志 分析控制传输的具体语义

实操顺序是这样：

  1. 先用 cat 0u | grep 看一眼，确认设备有数据、地址对不对。三十秒的事。
  2. 数据量上来了，换 tcpdump -w 存文件，别在终端里刷。
  3. 要搞清楚某个控制请求到底在问什么，把 pcap 拷回 PC 用 Wireshark 翻。

一开始就上 Wireshark 是浪费时间，最后都不用 Wireshark 是浪费信息。三个工具各有各的位置。

五、怎么读 usbmon 的输出 #

先给一条原始记录，从左到右把每一列拆开。

text
ffffffc0c88dab00 1925775309 C Ii:1:004:2 0:1 52 = 01010075 09080930 00000000 ...

整行的列布局：

text
URB标签            时间戳      事件类型  地址字段    URB状态字段  数据长度  数据标签  数据流

七列空格分隔。前四列位置固定，五到七列在 S 记录里会缺席。逐列拆。

第一列：URB 标签 #

ffffffc0c88dab00 是 struct urb 在内核空间的地址。它的作用是区分不同的 URB：同一个地址的 S 和 C 是一条传输的两头，这是配对唯一的依据，第六章专门讲。长度和系统位数相同，64 位系统上 8 字节、16 个十六进制字符。板子是 aarch64，所以全是 ffffffc0 开头，那是内核空间地址的高位。

第二列：时间戳 #

1925775309，单位微秒。两个特点都得记住：

  • 单增，但不是墙上时间，表示「开机第几微秒」。
  • 会回绕，范围只有 0 ~ 4096 秒，约 68 分钟一圈。

回绕的原因在源码里写得很明白：

c
/* drivers/usb/mon/mon_text.c */
static inline unsigned int mon_get_timestamp(void)
{
        struct timespec64 now;
        unsigned int stamp;

        ktime_get_ts64(&now);
        stamp = now.tv_sec & 0xFFF;  /* 只保留低 12 位，限制在 4096s 内 */
        stamp = stamp * USEC_PER_SEC + now.tv_nsec / NSEC_PER_USEC;
        return stamp;
}

now.tv_sec & 0xFFF 把秒数截到 12 位，过一个多小时归零重来。USEC_PER_SEC 是 1000000，NSEC_PER_USEC 是 1000。

实际影响：抓包超过 68 分钟，时间戳跳回小数值，相邻两行差值变成负数。别当异常，剪掉跨圈那一段就行。算耗时只用同一条 URB 的 C 减 S，两者间隔不会超一圈，不受影响。

第三列：事件类型 #

值 全名 含义 有没有配对
S submission 驱动把 URB 交给 USB 控制器 有，后面跟 C
C callback 传输结束，回调函数被调用 有，前面是 S
E submission error 提交时直接失败，URB 没上总线 无

E 是排查提交层问题的钥匙。它出现说明 usb_submit_urb 返回了非零值，常见原因是端点已禁用、设备已断开、内存不足。

第四列：地址字段 #

text
Ii:1:004:2
|  |  |  |
|  |  |  |__________ 端点号
|  |  |_____________ USB 设备地址
|  |________________ USB 总线号
|___________________ URB 类型及传输方向

第一段：类型加方向。 两个字符，第一个是传输类型，第二个是方向。方向以主机为参照，主机读设备是 IN，主机写设备是 OUT。

前缀 传输类型 方向
Ci / Co 控制传输 IN / OUT
Zi / Zo 等时传输 IN / OUT
Ii / Io 中断传输 IN / OUT
Bi / Bo 批量传输 IN / OUT

第二段：总线号。 1 表示 USB1。每个控制器对应一条总线，板上 6 条总线就是 1 到 6。

第三段：设备地址。 004 是枚举后分配到的地址，不固定，换一次插拔就变。

第四段：端点号。 2 表示走端点 2。这里显示的是端点编号，不带方向位。实际端点地址是 0x82（bit7 为 1 表示 IN，低 4 位是 2），日志只写 2，方向靠第一段的 i / o 表示。

第五列：URB 状态字段 #

最复杂的一列，因为它随传输类型变形。两种大形态：

  • S 记录上的控制传输，这一列是字母 s 后面跟八个十六进制数字。s 不是 status，是 setup，后面跟的是建立阶段主机发出的 8 字节 SETUP 包。
  • 其他所有情况，这一列是一串数字，冒号分隔，依次是 URB status、interval、start frame、error count。

各部分是否出现，取决于传输类型：

传输类型 status interval start frame error count
批量传输 有 无 无 无
中断传输 有 有 无 无
等时传输 有 有 有 有
控制传输（S） 换成 s + 8 字节 SETUP — — —
控制传输（C） 有 无 无 无
  • URB status：对应 struct urb 的 status。0 是成功，负数是 -errno。只在 C 上有意义，S 上是占位符 -115（-EINPROGRESS），意思是「还在进行」。
  • interval：端点轮询间隔，来自描述符的 bInterval。1 对应中断端点每 1 个微帧轮询一次。
  • start frame：等时传输专用，本 URB 起始的帧号。
  • error count：等时传输专用，传输过程中出错的包数。

S 上的 -115 是高频困惑点。看到 -115:1 别慌，那不是错误码，是「尚未完成」。

第六列：数据长度 #

单位字节。S 和 C 上含义不同，这是理解日志的关键：

记录 字段含义
S 主机请求读或写的长度，即 urb->transfer_buffer_length
C 设备实际读或写的长度，即 urb->actual_length

设备不一定满足全部请求。请求 52、只回 32，两条记录就是 52 和 32。此时 C 的数据区只有 32 字节真实内容，后面的补零是格式化输出。这一点在第九章解析多点报文时会再撞上。

第七列：数据标签 #

标签 含义
= 后面跟数据流，是实际的数据内容
< 这是一次 IN 传输，数据从设备到主机
> 这是一次 OUT 传输，数据从主机到设备

< 和 > 后面没有数据内容，因为 S 记录上数据还没来。真数据在配对的 C 里，那里用 =。

一段完整的读传输，两条记录一起看：

text
ffffffc0c88dab00 1925763683 S Ii:1:004:2 -115:1 52 <
                               |        |     |  |___ 数据标签：输入方向，这次要读
                               |        |     |______ 请求读取 52 字节
                               |        |____________ 状态 -115（进行中）+ interval 1
                               |_____________________ 中断 IN，总线 1，设备 4，端点 2

ffffffc0c88dab00 1925775309 C Ii:1:004:2 0:1 52 = 01010075 09080930 ...
                               |        |     |  |___ 数据标签：等号，后面是真实数据
                               |        |     |______ 实际读取 52 字节
                               |        |____________ 状态 0，传输成功
                               |_____________________ 同一个地址，同一条 URB

两行第一列相同，只是事件类型从 S 变 C，状态从 -115 变 0，标签从 < 变 =。时间线就对上了。

第八列：数据流 #

= 后面那一串，每 4 字节一组空格隔开。

text
01010075 09080930 00000000 00000000 00000000 00000000 00000000 00000000

分组只是排版，字节序不变。01010075 是四个字节 01 01 00 75，接着 09080930 是 09 08 09 30，按顺序连成一串。

解析时按位拆，不能按字节对齐。这点在第九章拆触摸点坐标时最要命。数据区实际显示的字节数小于等于第六列的长度值。

一列一表速查 #

列序 名称 示例 关键点
1 URB 标签 ffffffc0c88dab00 配对靠它，同址的 S/C 是一对
2 时间戳 1925775309 微秒，开机起算，68 分钟回绕
3 事件类型 S / C / E E 无配对
4 地址 Ii:1:004:2 类型方向、总线、设备、端点
5 URB 状态 -115:1 或 0:1 或 s... -115 是进行中，不是错误
6 数据长度 52 S 是请求长度，C 是实际长度
7 数据标签 = / < / > 只有 = 后面带数据
8 数据流 01010075 ... 4 字节一组，按位解析

六、URB 的生命周期与抓包对应 #

这一章把 S 和 C 配对的规则讲透，再讲不配对时怎么处理。

一条 URB 的五个阶段 #

阶段 内核动作 usbmon 记录
1. 分配 usb_alloc_urb 无
2. 填充 驱动填端点、缓冲区、长度、回调 无
3. 提交 usb_submit_urb S 记录，成功才有
4. 传输 主机控制器在总线上跑事务 无
5. 完成 回调 complete 被调用 C 记录

usbmon 只覆盖第 3 和第 5 步。这也解释了为什么日志中间那一大段是空的：那段时间物理总线上跑了几十个包、好几次 NAK 重试，URB 层一无所知。

配对规则：靠指针 #

规则只有一条：同一列的 URB 地址相同，且一个是 S、一个是 C，这两条就是一对。

看这段日志，6 条记录，3 对：

text
ffffffc0c88dab00 1925763364 C Ii:1:004:2 0:1 52 = 01010075 09080930 ...
ffffffc0c88dab00 1925763683 S Ii:1:004:2 -115:1 52 <
ffffffc0c88dab00 1925775309 C Ii:1:004:2 0:1 52 = 01010075 09080930 ...
ffffffc0c88dab00 1925775578 S Ii:1:004:2 -115:1 52 <
ffffffc0c88dab00 1925787174 C Ii:1:004:2 0:1 52 = 01010075 09080930 ...
ffffffc0c88dab00 1925787301 S Ii:1:004:2 -115:1 52 <

反直觉的地方：C 出现在 S 之前。第一行那个 C，它的 S 在更早的日志里，被 grep 截掉了。这块屏的中断端点一直在轮询，驱动始终保持一个 URB 在路上，所以任何时候切进去看，第一眼都是「上一轮还没收尾」的 C。配对时不能假设 S 一定在前，要看指针，不要看行序。

耗时就是两个时间戳相减 #

配对之后直接算：C 的时间戳减 S 的时间戳，单位微秒。

text
S: 1925775578
C: 1925787174
差: 1925787174 - 1925775578 = 11596 微秒 ≈ 11.6 毫秒

11.6 毫秒，对 1ms 轮询间隔的中断端点来说偏大。实际情况是驱动提交 URB 之后设备一直没有新数据，URB 就挂在总线上等着，等手指按下才完成。

所以对中断端点来说，S 到 C 的间隔衡量的是「等了多久才有数据」，不是「传输花了多久」。批量传输就不一样，批量 URB 提交后很快完成，时间差接近真实耗时，量级在几百微秒到几毫秒。

为什么同一个指针会出现很多次 #

日志里 ffffffc0c88dab00 反复出现几十次，不是内核复用了地址，是驱动复用了 URB。中断端点的典型写法是：在完成回调里重新填 URB、再提交一次。这样一个 URB 被反复用几千次，地址当然一直是它。

两个影响：地址不是身份，不能说「同一个地址就是同一次传输」，必须靠相邻的 S/C 组合判断；想看不同的 URB 就看去重后的地址数量，一眼看到三个地址说明驱动同时挂了三个 URB。

C 没有对应 S 怎么办 #

三种原因，按概率排：一是 S 在抓包开始之前，你是中途切进去的，那个 URB 早就提交了，这种情况尤其中断端点最多；二是 日志被过滤掉了，grep 条件没匹配上那一条 S；三是 环形缓冲覆盖，usbmon 缓冲有限，高速率下旧记录被冲掉。

处理办法很朴素：抓包时间往前挪，先 cat 起来再触发设备动作。

S 没有对应 C 怎么办 #

两种原因：一是 抓包在传输完成前结束，Ctrl+C 按早了；二是 URB 被取消或者泄漏，驱动没回收，或者设备拔出导致 URB 永远完不成，这是 bug。

第二种在调试驱动时很有价值，判断依据是：正常 URB 完成时间在毫秒级，如果一条 S 之后几十万微秒都没有 C、而同设备其他 URB 在正常滚动，那就是它卡住了。

E 记录单独看 #

text
ffffffc0c88dab00 1925775309 E Ii:1:004:2 -2:1 52 <

E 没有配对，它自己就是完整信息：提交失败，错误码在状态字段，上面这个 -2 是 -ENOENT。这种记录少见但有价值，它意味着问题在提交层面、还没碰到硬件，排查方向立刻收窄到三处：端点是否 enable、设备是否还在线、URB 参数是否合法。

配对的事交给脚本 #

手工配几十行还行，几千行别硬看。一条 awk 足够：

bash
awk '{print $3, $1}' usbmon.log | sort | uniq -c | sort -rn | head

先统计每个地址的 S 和 C 数量，两者不等就是有丢配对，再针对那个地址细看。要算耗时，按地址聚合成对：

bash
awk '$3=="S"{s[$1]=$2} $3=="C" && ($1 in s){print $1, $2-s[$1]; delete s[$1]}' usbmon.log

输出就是「地址 耗时微秒」两列。这套组合比肉眼靠谱得多。

七、控制传输的抓包分析 #

控制传输最值得先啃。设备枚举、读描述符、设置配置、HID 类请求，全是它。看不明白控制传输的日志，等于没抓过包。

控制传输由三个阶段组成 #

阶段 方向 内容 事务数
建立阶段 主机 → 设备 8 字节 SETUP 包，说明「我要干什么」 1
数据阶段 双向或没有 实际的传输数据 0 到多个
状态阶段 设备 → 主机 一个方向相反的零长度包，表示结束 1

usbmon 里这三段合并成两条记录：S 和 C。包层有五六个事务，URB 层只有两条。

S 记录里的那个 s #

普通 URB 的状态字段是数字。控制传输的 S 记录例外，它是字母 s 后面跟 8 个字节的十六进制：

text
ffffffc0c88dab00 1925763683 S Ci:1:004:0 s 80 06 00 01 00 00 40 00

s 后面那 8 个字节就是建立阶段的 SETUP 包，格式固定：

text
bmRequestType(1) + bRequest(1) + wValue(2) + wIndex(2) + wLength(2)

拆 80 06 00 01 00 00 40 00：

字段 字节 值 含义
bmRequestType 80 0x80 IN，标准请求，接收者是设备
bRequest 06 0x06 GET_DESCRIPTOR
wValue 00 01 0x0100 高字节 1 = 设备描述符，低字节 0 = 索引
wIndex 00 00 0 语言 ID 或接口号，设备描述符这里无意义
wLength 40 00 64 最多读 64 字节

注意字节序。wValue 是 16 位小端，00 01 读作 0x0100，不是 0x0001。判断描述符类型看高字节 01。读反了就会把「读设备描述符」误认成「读配置描述符」。

bmRequestType 的三个字段 #

一个字节拆三段，这是读懂控制传输的钥匙：

位 名称 含义
bit7 方向 0 = 主机到设备（OUT），1 = 设备到主机（IN）
bit6:5 类型 0 = 标准，1 = 类，2 = 厂商，3 = 保留
bit4:0 接收者 0 = 设备，1 = 接口，2 = 端点，3 = 其他

常见组合：0x80 是 IN + 标准 + 设备；0x81 是 IN + 标准 + 接口；0xA1 是 IN + 类 + 接口；0x21 是 OUT + 类 + 接口；0xC0 是 IN + 厂商 + 设备。

HID 设备读报告描述符用 0x81，因为描述符挂在接口上，不在设备上。报告描述符挂在接口上而不是设备上，靠的就是 bit4:0 等于 1。

C 记录怎么看结果 #

C 记录的状态字段回到普通数字形态，只含 URB status：

text
ffffffc0c88dab00 1925775309 C Ci:1:004:0 0:1 64 = 12 01 00 02 00 00 00 40 86 1a e3 e5 ...

0:1 里的 0 是成功。数据区就是 64 字节设备描述符，12 01 开头，12 是 bLength，01 是 bDescriptorType。

任一阶段失败，整个 URB 失败。控制传输的状态码：

状态码 errno 常见原因
-32 EPIPE 设备返回 STALL，请求不被支持
-71 EPROTO 协议错误，多是时序或 CRC 问题
-110 ETIMEDOUT 设备没响应，超时
-2 ENOENT 端点不存在或被禁用
-75 EOVERFLOW 设备回的数据比 wLength 多

-32 最常见。控制传输收到 STALL，基本可以断定这个请求设备不支持，或者 bmRequestType 的接收者填错、对着设备发了接口级请求。

枚举过程在日志里长什么样 #

设备插上电，内核发一串控制请求，顺序固定：

顺序 请求 目的
1 GET_DESCRIPTOR(Device) 先读 8 字节，拿到 bMaxPacketSize0
2 SET_ADDRESS 分配设备地址
3 GET_DESCRIPTOR(Device) 用新地址重读完整 18 字节
4 GET_DESCRIPTOR(Config) 读配置描述符，含接口和端点
5 GET_DESCRIPTOR(String) 读厂商、产品、序列号字符串
6 SET_CONFIGURATION 选定配置，设备进入工作状态

日志里的特征很好认：地址字段从 000 开始，然后跳到分配的新地址。所有请求都是 Ci:1:00x:0，端点号都是 0。

设备插拔太快，手工 cat 追不上。要先 cat 起来再插设备：

bash
root@SOM-RK3399v2:/# cat /sys/kernel/debug/usb/usbmon/0u > /tmp/enum.log &
root@SOM-RK3399v2:/# # 这时候插上设备
root@SOM-RK3399v2:/# sleep 3
root@SOM-RK3399v2:/# kill %1
root@SOM-RK3399v2:/# grep "Ci:" /tmp/enum.log | head -40

表层的接口信息 #

接口子类和协议单独读文件，字段名就是描述符字段名：

bash
root@SOM-RK3399v2:/# cd /sys/bus/usb/devices/1-1.2/1-1.2:1.0
root@SOM-RK3399v2:/# cat bInterfaceClass bInterfaceSubClass bInterfaceProtocol
03
00
00
  • bInterfaceClass = 03，HID 类。
  • bInterfaceSubClass = 00，No Subclass，没走键盘或鼠标的标准子类。
  • bInterfaceProtocol = 00，无特定协议。

子类和协议都是 0，说明它是厂商自定义的 HID 设备。hid-multitouch 还是认了它，靠的是报告描述符里 Digitizer 用途页的存在而非接口描述符，这一点直接影响第九章怎么解析报文。

1-1.2 和 1-1.2:1.0 的区别：前者是设备节点，后者是设备第 0 号配置下的第 0 号接口，「1.0」不是版本号而是配置号和接口号的拼接。

urbnum 统计设备累计提交过多少 URB：cat 一次、等几秒再 cat 一次，差值除以间隔就是实际轮询频率，判断「驱动是不是真在轮询」比数日志快得多。

八、批量与中断传输的抓包 #

控制传输只在枚举和配置时出现，设备跑起来之后的常态流量是批量或中断。这块屏走中断，USB 硬盘走批量，两种日志形态不一样。

中断传输：URB 常驻，等数据 #

中断传输的实现方式是：驱动在完成回调里立刻重新提交，保持总有一条 URB 在路上。日志因此呈现固定节奏：

text
ffffffc0c88dab00 1925763364 C Ii:1:004:2 0:1 52 = 01010075 09080930 ...
ffffffc0c88dab00 1925763683 S Ii:1:004:2 -115:1 52 <
ffffffc0c88dab00 1925775309 C Ii:1:004:2 0:1 52 = 01010075 09080930 ...
ffffffc0c88dab00 1925775578 S Ii:1:004:2 -115:1 52 <
ffffffc0c88dab00 1925787174 C Ii:1:004:2 0:1 52 = 01010075 09080930 ...
ffffffc0c88dab00 1925787301 S Ii:1:004:2 -115:1 52 <

节奏是「C 然后立刻 S」交替。两者差 319 微秒，这是回调到重新提交的内核开销，真正等待数据的时间体现在前一个 S 到这个 C 之间。

配对 S 时间戳 C 时间戳 差值
第 1 对 1925763683 1925775309 11626 微秒
第 2 对 1925775578 1925787174 11596 微秒
第 3 对 1925787301 1925800237 12936 微秒

都稳定在 11 到 13 毫秒。手指一直按着，设备一直有数据，URB 完成得快；手指抬起后设备没东西上报，URB 会挂满一个更长的超时周期。所以中断传输的日志读法是：S 到 C 的间隔不是传输耗时，是等到数据的耗时。

中断端点的数据长度可以是可变的 #

上面每次都是 52 字节，因为报告描述符规定报告长度就是 52。但中断端点的 URB 请求长度一般填得比实际报告大，取 wMaxPacketSize 的整数倍，所以驱动缓冲区填大了就会看到 S 请求 64、C 实际回 52——这不代表出错，只是驱动给了设备更多空间。

批量传输：URB 一次一换 #

批量传输的 URB 用完就扔，重新分配。日志特征：

  • URB 地址经常变，不像中断端点那样反复用同一个。
  • S 到 C 的间隔短，几十微秒到几毫秒。
  • 数据长度经常是 wMaxPacketSize 的整数倍，比如 512 的倍数。

看到「地址不断变化 + 间隔短 + 长度整齐」，就是批量。它的状态码含义和中断不同，因为批量有硬件重试机制：

状态码 含义 排查方向
0 成功 —
-71 协议错误 线材、电源、信号质量
-84 校验错误 硬件层问题
-110 超时 设备没响应，查固件
-32 STALL 端点被复位，需要 clear_halt
-2 设备已断开 检查线是否掉了

-71 和 -84 是硬件层信号，软件改不了。usbmon 能看到错误码，但看不到错误发生在哪个包上，那得上协议分析仪。

两种传输的日志对照 #

维度 中断传输 批量传输
URB 复用 高度复用，同一地址反复出现 一次一换，地址不断变
S 到 C 间隔 可长可短，取决于设备有没有数据 短且稳定
C 记录节奏 和 S 交替，形成固定节拍 离散，和业务请求对齐
数据长度 固定，等于报告长度 常为 MPS 整数倍
典型设备 触摸屏、鼠标、键盘 U 盘、移动硬盘、打印机
排查重点 数据内容对不对 有没有出错、速率够不够

过滤一个设备的两种写法 #

看单设备，grep 最直接。三种砸法：

bash
# 整个设备（总线 1，设备 004）
root@SOM-RK3399v2:/# cat /sys/kernel/debug/usb/usbmon/1u | grep "1:004"
# 只看某一个端点
root@SOM-RK3399v2:/# cat /sys/kernel/debug/usb/usbmon/1u | grep "Ii:1:004:2"
# 只看完成记录
root@SOM-RK3399v2:/# cat /sys/kernel/debug/usb/usbmon/1u | grep " C Ii:1:004:2"

1:004 匹配地址字段的第 2、3 段，冒号锚定了分段，所以不会误匹配。" C " 前后各一个空格也是必须的，不然会连 Ci: 前缀的行一起捞进来。

grep 的缓冲问题 #

管道有缓冲。cat 的输出进 grep，grep 再往终端吐，中间隔着两层。结果是：你按下触摸屏，屏幕上要等一秒多才出现日志。

不影响正确性，但影响操作手感。要实时看，把块缓冲关掉：

bash
root@SOM-RK3399v2:/# stdbuf -oL cat /sys/kernel/debug/usb/usbmon/1u | grep --line-buffered "1:004"

stdbuf -oL 让 cat 按行刷，--line-buffered 让 grep 按行刷。两个都要加，只加一个还会有延迟。

没有 stdbuf 的环境（busybox 常见）就先把输出写文件，再 tail -f：

bash
root@SOM-RK3399v2:/# cat /sys/kernel/debug/usb/usbmon/1u > /tmp/usb.log &
root@SOM-RK3399v2:/# tail -f /tmp/usb.log | grep "1:004"

这个写法还有个好处：日志留在文件里，事后可以反复分析。第九章的实录就是靠它抓下来的。

九、一次完整交互的抓包实录 #

前面讲的都是零件，这一章把它们装起来。从读报告描述符开始，到手指按下去、数据回来、把 52 个字节拆成坐标结束。

第一步：先摸清报告描述符 #

不看报告描述符就解析数据，等于闭着眼睛拆包。这块屏的描述符在 debugfs 里，直接读文本版：

bash
root@SOM-RK3399v2:/# cat /sys/kernel/debug/hid/0003:1A86:E5E3.0007/rdesc
05 0d 09 04 a1 01 85 01 09 22 a1 02 09 42 15 00 25 01 75 01 95 01 81 02 95 07 81 01 75 08 09 51 95 01 81 02 05 01 26 00 10 75 10 55 0e 65 11 09 30 35 00 46 79 08 81 02 26 00 10 46 4c 05 09 31 81 02 05 0d 09 48 81 02 c0

目录名 0003:1A86:E5E3.0007 的四段分别是：0003 是接口描述符的 bInterfaceClass（0x03 就是 HID 类），1A86 是 idVendor，E5E3 是 idProduct，0007 是这个 HID 设备在本机的实例序号（插两个同型号设备时靠它区分）。

HID 条目的字节布局 #

每个条目是 key + value，key 一个字节，value 长度由 key 低 2 位决定：

text
bit7:4 = bTag (4 位)
bit3:2 = bType (2 位)
bit1:0 = bSize (2 位)

bSize 决定 value 长度：0 → 0 字节，1 → 1 字节，2 → 2 字节，3 → 4 字节。

bType 决定条目类别：0 → 主条目 Main，1 → 全局条目 Global，2 → 局部条目 Local，3 → 保留。

拆几个关键的：

原始字节 bTag bType bSize 条目 值解读
0x05 0x0d 0 1 Global 1 Usage Page 0x0d = Digitizer
0x09 0x04 0 2 Local 1 Usage 0x04 = Touch Screen
0xa1 0x01 0b1010 0 Main 1 Collection 0x01 = Application
0x85 0x01 0b1000 0 Main 1 Report ID 0x01
0x75 0x01 7 1 Global 1 Report Size 1 位
0x95 0x01 5 1 Global 1 Report Count 1 个
0x81 0x02 0b1000 0 Main 1 Input Data,Var,Abs
0xc0 0b1100 0 Main 0 End Collection 无值

长条目看 bSize=2 就能认出，value 是 2 字节小端：0x26 0x00 0x10 读作 0x1000 = 4096（Logical Maximum），0x46 0x79 0x08 读作 2169，0x46 0x4c 0x05 读作 1356（Y 方向）。0x81 0x02 那个 0x02 的位含义：bit0=0 表示 Data（非 Constant），bit1=1 表示 Variable（非 Array），bit2=0 表示 Absolute（非 Relative），这三个位决定了这个字段怎么读。

三个报告的分工 #

2 FEATURE ContactCountMaximum，最大触点数 10 1 字节 + ID

第三步：对应到物理尺寸 #

坐标是数字，物理意义得算。描述符给了两组边界：Logical 0~4096，Physical X 方向 0~2169。

text
Resolution = (4096 - 0) / ((2169 - 0) * 10^-2) = 188.84 counts per inch

10^-2 来自 UNIT_EXPONENT(-2)，表示物理值以厘米为单位。

同一套公式套在 400DPI 的鼠标上：

text
Resolution = (127 - (-127)) / ((3175 - (-3175)) * 10^-4) = 400 counts per inch

差在单位指数：鼠标那边的 UNIT_EXPONENT 是 -4，单位是米。公式是同一个。dpi 和 cpi 顺手分清：dpi 是 dots per inch，静态指标，适合打印机、扫描仪；cpi 是 counts per inch，动态指标，适合鼠标这类持续移动的设备。鼠标移动一英寸，400cpi 的设备发 400 次信号，800cpi 的发 800 次。

Y 方向 Physical Maximum 是 1356，和 X 的 2169 不同，这不是笔误，是屏幕实际比例：2169:1356 约等于 1.6:1，符合 15.6 英寸屏的常见宽高比。

这块屏的实际行为就是如此：只上报 4 个触摸点的数据，尽管描述符声明了 6 个。长度 52 是驱动请求的，实际回 32 是设备决定的。

32 字节意味着什么 #

两种解释得靠实验区分：设备固件只支持 4 点，描述符是抄来的模板没改；或者设备按需裁短。实测三次不同手指数，长度分别是 52（1 点）、52（2 点）、32（3 点）。1 点和 2 点都回了完整的 52 字节，说明不是按需裁短，而是超过某个阈值才裁。根源在固件，抓包只能把它记下来。

带来一条硬经验：按实际字节数切，不要按描述符声明的长度切。解析代码里写死 52，遇到 32 就会读越界，读出来的是内存残留值，看起来像坐标，实际是垃圾。

保守的切法是：字节 1 开始每 8 字节一个触点，能切出几组就解几个，多出来的当填充丢掉。

实际长度 能解的点数
52 6
33~51 4（实测只出现 32 和 52 两档）
25~32 3~4
17~24 2
9~16 1

换一块同型号但固件版本不同的屏，这些值就会变，代码不该依赖观测结果。

完整交互的时间线 #

把一次「手指按下 → 抬起」的日志按时间排出来：

相对时间 事件 日志特征
T+0 驱动提交轮询 URB S Ii:1:004:2 -115:1 52 <
T+11.6ms 设备回数据，URB 完成 C ... 0:1 52 = 01010075 ...
T+11.9ms 回调里重新提交 S Ii:1:004:2 -115:1 52 <
T+23.5ms 下一包数据 C ... = 01010075 ...
每隔 11~13ms 重复上述循环 直到手指抬起
手指抬起 数据里的按下位清零 C ... = 01000075 ...
抬起后 URB 挂更久才完成 S 到 C 间隔变长

抬起时的关键变化在字节 1：从 01 变成 00，TipSwitch 位清了。日志里正好有这两行对比：

text
ffffffc0c88dab00 1925821178 C Ii:1:004:2 0:1 52 = 01000075 09080930 00000000 00000000 00000000 00000000 00000000 00000000
ffffffc0c88dab00 1925822163 C Ii:1:004:2 0:1 52 = 01000075 09080930 00000000 00000000 00000000 00000000 00000000 00000000

两行数据一样，因为手指抬起后坐标还保留着最后位置。设备上报的是「未按下 + 上次坐标」而不是清零，这符合 HID 触摸屏的常规行为。

描述符里的物理尺寸不可信 #

按 UNIT_EXPONENT(-2)（厘米）解释 Physical Maximum，X 方向就是 2169 厘米，21 米多，一块 15.6 英寸的屏不会是这个尺寸。结论很实际：这块屏的描述符里物理尺寸字段是厂商填的占位值，只能用逻辑坐标 0~4096 做归一化，别指望算出毫米。

这是抓包分析里的常见发现：描述符和数据对不上时，先信数据，描述符当参考。厂商填描述符经常是复制粘贴，改不干净。

十、常见问题的定位方法 #

抓包最大的用处不是「看数据」，是「排错」。这一章把高频故障和对应日志特征列出来，遇到问题按表查。

抓不到任何记录 #

cat 0u 之后屏幕上什么都没有，连别的设备都没有。按顺序查这五项：

检查项 命令 正常表现
模块加载了吗 lsmod | grep usbmon 有一行 usbmon
文件在吗 ls /sys/kernel/debug/usb/usbmon/ 有 0u 等文件
debugfs 挂了吗 mount | grep debugfs 有一行
是不是权限不足 id uid=0
设备真的在动吗 cat /sys/bus/usb/devices/1-1.2/urbnum 前后对比 数值在涨

前四项里任何一项不对，日志就是空的。第五项容易被忽略：设备静止时确实没有 URB，中断端点那条 URB 挂在那里等，不产生新记录。要先动一下设备再看。

抓到了，但全是别的设备 #

grep 的条件错了。地址字段格式是 Ii:1:004:2，三段的冒号匹配必须精确。

写法 问题
grep "1:4" 设备地址是三位补零的 004，不是 4
grep "1:004" 少了锚定，会匹配到 11:004 之类
grep "C" 匹配所有含字母 C 的行，包括 Ci:
grep "4" 匹配一切含 4 的行，全是噪音

正确写法是带上类型定死：grep "Ii:1:004:2"。

有 S 就是没有 C #

URB 提交了但一直没完成，原因有三类：

  • 设备没响应。中断端点无数据时会一直挂着，这是正常状态，不是故障。
  • 设备挂了。检查 dmesg 有没有 reset、disconnect 相关输出。
  • 端点被 halt 了。批量端点收到 STALL 后会 halt，之后的 URB 全部卡住，得 clear_halt。

区分「正常等待」和「真卡死」的方法是看同设备的其他 URB 还在不在滚动：别的 URB 正常、只有这一条不动，就是卡死。

数据长度对不上 #

S 请求 52，C 实际 32，不一定是错误。判断依据在设备特性：

情况 判据 结论
设备只回部分 反复出现同样的 32 设备行为，正常
偶发短包 长度随机变化 检查设备固件
一直是 0 长度恒为 0 但状态 0 零长度包，状态阶段的正常收尾
超长 C 长度大于 S 长度 异常，检查驱动缓冲区

触摸屏那个 32 字节属于第一类，由设备固件决定，可以不管。

状态码不是 0 #

C 记录的状态字段是负数，直接对照 errno：

状态码 名称 含义 处理
-32 EPIPE 端点 STALL clear_halt，或查请求是否合法
-71 EPROTO 协议错误 查线材、供电、信号质量
-84 EILSEQ CRC 校验错 硬件层问题
-110 ETIMEDOUT 超时 设备没响应，查固件
-2 ENOENT 端点不存在 端点地址填错了
-75 EOVERFLOW 溢出 缓冲区比设备回的数据小
-19 ENODEV 设备已断开 查物理连接
-108 ESHUTDOWN 控制器已停 检查主机控制器状态

-71 和 -84 是硬件信号问题，软件层改不了。遇到这两种先换线、换供电、换 USB 口，别在代码里找原因。

枚举卡住 #

设备插上，dmesg 停在 new full-speed USB device number 4 之后没有下文。抓枚举日志看最后一条：

bash
root@SOM-RK3399v2:/# cat /sys/kernel/debug/usb/usbmon/0u > /tmp/enum.log &
root@SOM-RK3399v2:/# sleep 5
root@SOM-RK3399v2:/# kill %1
root@SOM-RK3399v2:/# grep "Ci:1:00" /tmp/enum.log | tail -20

三种典型卡点：

卡在哪 日志表现 原因
读设备描述符 只有一条 s 80 06 00 01 的 S，无 C 设备没响应，或供电不足
读配置描述符 有设备描述符的 C，配置描述符的 S 无 C 描述符长度字段异常，设备回的数据超长
SET_CONFIGURATION C 状态 -32 设备不支持这个配置，或配置值非法

供电不足很常见。RK3399 的 USB 口带载能力有限，接大功率设备要先上带供电的 hub。判断方法：同一个设备插带供电的 hub 能枚举、直插板子不行，就是供电问题。

传输中途断开 #

日志突然中断，之后什么都没有。看 dmesg：

text
[ 1234.567890] usb 1-1.2: USB disconnect, device number 4

看到这行就是物理断开，原因在线、在接口、在设备本身。抓包能确认「断在哪个时刻」，不能确认「为什么断」。

数据内容不对 #

最难的一类。日志有、长度对、状态 0，就是字节解出来不对。按这个顺序查：

  1. 报告描述符读对了吗。cat /sys/kernel/debug/hid/.../rdesc，确认长度和内容。
  2. 字节序搞反了吗。16 位字段是小端，75 09 是 0x0975 不是 0x7509。
  3. 按位还是按字节。1 位的 TipSwitch 和 8 位的 ContactID 混在一起时，偏移算错一位全错。
  4. 有没有报告 ID。描述符里定义了 Report ID，数据第一个字节就是 ID；没定义，第一个字节就是数据。
  5. 长度没检查。实际 32 字节却按 52 解析，后面全是垃圾。

第 5 条是最常见的坑，实际 32 字节却按 52 解析，后面全是垃圾。

高频率下丢记录 #

日志里 S 和 C 数量对不上，缺的总是较早的那些。这是 usbmon 的环形缓冲区满了：缓冲区大小固定，写入速度超过读取速度就会覆盖，而 cat 到终端是最慢的读法。

缓解办法 效果
输出重定向到文件，不刷终端 明显改善
缩小抓包范围，只抓一条总线 减少数据量
用 tcpdump -w 存 pcap 最快，接近零拷贝
缩短抓包时间，只在触发前后抓 根治

最后一条最实在。先准备好 cat，再触发设备动作，抓 2 秒就停，比抓 10 分钟再筛管用得多。

十一、性能与抓包开销 #

抓包不是免费的。搞清楚代价在哪，才知道什么时候该停。

开销的三个来源 #

来源 量级 说明
内核钩子 每次 URB 几百纳秒 复制字段到环形缓冲
文本格式化 每条记录几微秒 mon_text.c 要把二进制转成字符串
用户态读取 取决于消费者 终端渲染远慢于写文件

大头是第三个。内核钩子本身很轻，几条 memcpy 就完了，真正拖慢系统的是你把数据取出来的方式：

读法 相对开销 说明
cat 0u 到终端 最高 终端渲染加滚动缓冲，最慢
cat 0u > file 中 只受磁盘写入限制
grep 管道过滤 中偏高 多了进程间管道和字符串匹配
tcpdump -w 最低 二进制直通，格式化在事后做

「先 cat 到文件，再慢慢分析」这个习惯是对的，它也顺带解决了丢记录的问题。

日志规模估算 #

这块屏的轮询间隔 1ms，每秒 1000 次 URB，每次两条记录，每秒 2000 行；按每行 150 字节算，每秒 300KB，抓 10 分钟就是 180MB，这个量级必须落盘，不能走终端。批量传输设备更凶：USB2.0 高速批量能跑到 40MB/s，如果每次都分成 512 字节的 URB，每秒就是八万次，日志直接爆掉，这种场景必须用 tcpdump，而且得靠 BPF 提前过滤。

对系统的影响 #

抓包对设备时序的影响很小，但不是零：

  • URB 提交和回调多了一层钩子调用，单次开销在纳秒级，相对 USB 的微秒级时间尺度可以忽略；真正的风险是内存，环形缓冲占内核内存，日志量太大时会挤压；极端情况是 CPU 打满，cat 到终端时渲染会吃掉一个核。

判断影响的方法：抓包前后各测一次设备的实际轮询频率。

bash
root@SOM-RK3399v2:/# a=$(cat /sys/bus/usb/devices/1-1.2/urbnum); sleep 5; b=$(cat /sys/bus/usb/devices/1-1.2/urbnum); echo $(( (b-a)/5 )) "URB/s"

正常应该是 1000 左右（1ms 间隔）。抓包时如果掉到 800，说明开销已经影响到设备时序了。

什么时候必须停 #

三种情况：

  • CPU 占用超过 30%，说明格式化开销已经压不住。
  • 日志增长速度超过磁盘写入能力，df 看剩余空间在快速下降。
  • 设备开始报超时错误，说明钩子拖慢了 URB 处理。

前两种降级到 tcpdump，第三种停下来改用别的排查手段。

权限与转发 #

非 root 读不了 usbmon 设备。临时放开：

bash
root@SOM-RK3399v2:/# chmod 644 /sys/kernel/debug/usb/usbmon/0u

重启就失效，长期方案得配合 udev 规则，或者干脆用 root 抓、抓完把文件拷出来。远程抓包有个更省事的办法：ssh 直接把输出重定向回本地。

bash
$ ssh root@192.168.1.100 'cat /sys/kernel/debug/usb/usbmon/0u' > local_usb.log

板上不做任何存储，日志直接落到 PC 硬盘，避免占满 eMMC。要注意网络吞吐：1ms 轮询的日志量是每秒 300KB，千兆网够用，百兆网会丢。

十二、易错点速查 #

把所有坑压缩成表，查的时候不用回头翻。

概念类 #

易错点 正确理解
一条日志是一个包 一条日志是一个 URB 的事件，S 和 C 才凑成一次传输
S 和 C 应该相邻 不一定，中间会插其他 URB，且 C 会出现在 S 之前
同一个 URB 地址是一次传输 地址会被反复复用，要按相邻的 S/C 组合判断
usbmon 能抓到令牌包和握手包 抓不到，URB 层看不见这两类包
S 记录上的 -115 是错误 不是，是 EINPROGRESS，表示还在进行中
E 记录有对应的 C 没有，提交失败就结束了
数据长度字段是实际收到的长度 S 上是请求长度，C 上才是实际长度

命令类 #

易错点 正确写法
modprobe usbmon 报 command not found PATH 里没有 /usr/sbin，export PATH=/usr/sbin:$PATH
ls /sys/module/usbmon 不存在就以为内核不支持 先确认 .ko 文件在不在，在就是没加载
cat 0u 没有输出就以为没数据 设备静止时确实没 URB，先动一下设备
grep "1:4" 匹配不到 设备地址补零到三位，写 1:004
grep "C" 把 Ci: 也捞进来 用 " C " 带前后空格，或写完整地址
cat 完直接分析 先重定向到文件，终端读法会丢记录
管道输出延迟 加 stdbuf -oL 和 --line-buffered

解析类 #

易错点 正确理解
16 位字段按大端读 USB 和 HID 都是小端，75 09 是 0x0975
数据区按 4 字节一组当独立字段 分组只是排版，实际是连续字节流
按描述符声明的 52 字节硬解析 按实际长度切，32 字节时只能解 4 个点
把报告 ID 当第一个触点数据 描述符定义了 Report ID 时，字节 0 是 ID
描述符里的 Physical Maximum 当真实尺寸 厂商常填占位值，不可信
S 记录里的 s 80 06 ... 当成状态码 s 是 setup，后面 8 字节是 SETUP 包
wValue 的字节序读反 00 01 是 0x0100，描述符类型看高字节

时间类 #

易错点 正确理解
时间戳是墙上时间 是开机后的微秒数
时间戳可以跨小时比较 12 位截断，68 分钟回绕一次
S 到 C 的间隔就是传输耗时 中断端点上是「等待数据的时间」
批量传输耗时和中断一样解读 批量 URB 一次一换，间隔接近真实耗时

一条排查流程 #

遇到问题按这个顺序走，几乎不会绕路：

  1. lsmod | grep usbmon，确认模块在。
  2. lsusb 和 cat /sys/kernel/debug/usb/devices，确认设备地址、端点、传输类型。
  3. cat /sys/kernel/debug/usb/usbmon/1u > /tmp/usb.log &，先起抓包。
  4. 触发设备动作，等 2 秒。
  5. kill %1，停抓包。
  6. grep "1:004" /tmp/usb.log，先看有没有记录。
  7. 有记录，看 C 的状态码是不是 0。
  8. 状态码 0，拆数据区，对着报告描述符逐字段核。
  9. 没记录或状态码非 0，回到第十章查表。

排查时最先要能一眼看出来的三个数字：C 记录的状态字段是 0 还是负数，决定了问题在数据内容还是在链路；S 与 C 的长度字段是否相等，决定了是完整包还是短包。这两项定了性，剩下的都是细节。

抓包这件事的价值就在这里：它让你在写下第一行解析代码之前，就已经知道设备会怎么回、回多少、有没有报错。
