这篇只回答一个问题：同样是给闪存用的文件系统，ext4 和 F2FS 的磁盘布局差在哪，谁在为哪条物理特性让路。

讲什么：ext4 的块组布局、超级块与 GDT 备份、位图、inode 与多级间接寻址、extent 树、delalloc 与 journal；F2FS 的六区布局、NAT/SIT/SSA 三张表、六级冷热分离、cleaner 与写放大；两者的正面对照与选型。 不讲什么：VFS 四大对象与路径解析、页缓存与回写、块层 I/O 调度、eMMC/UFS 协议细节。 跨篇指路：inode/dentry/super_block 在内存里长什么样，看「VFS 虚拟文件系统解析」；进程怎么拿着 struct file 访问文件，看「进程与文件系统：fs_struct、files_struct 与打开文件表」；挂载看「2.文件系统简介」；eMMC 侧看「eMMC」。 版本提醒：ext4 部分底稿是 2017-07-17 的翻译文（David Both 著，Linux 中国 chenxinlong 译，linux.cn/article-8685），机制停在 4.x 时代；F2FS 部分底稿是 2020-01 的「F2FS 技术拆解」，讲的是 3.x~4.x 的演进。凡「某版本才支持某特性」的地方都标了内核版本，标不出来的写「原文未标注」。

一、文件系统要解决的三件事：命名、定位、空间管理 #

一个文件系统拆开就干三件事：给数据起名字和组织结构（命名空间）、把名字映射到盘上的位置（定位）、决定哪些块被谁占着（空间管理）。安全模型和系统调用接口是另外两层，跟磁盘布局无关。

前两件事在 ext4 和 F2FS 里差别不大：都有目录项、都有 inode 号、都要靠一层间接结构找到数据块。分歧全在第三件事。

问题 ext4 的答案 F2FS 的答案
新块从哪来 查块位图，找空闲位，就地置 1 往当前活跃日志尾部追加，写完推进指针
旧块怎么改 原地覆写，块号不变 异地写新的，改索引指向它，旧块作废
空闲空间怎么记 位图，一位一个块 SIT 里每段的在用块数 + 位图
空间回收靠什么 删文件就清位图位，没有后台搬移 cleaner 周期性搬移在用块，把段腾空
元数据的锚点 每组的位图和 inode 表，位置固定 NAT 做一次地址转译，node 位置可以漂

这两种答案不是审美差异，是被介质逼出来的。闪存有两个绕不开的事实：擦除单位是块（今天的 NAND 擦除块在 2MB~4MB 量级，看颗粒型号），写之前必须先擦。原地改一个 4KB 页，落到闪存上就是：读出整个擦除块、改其中一页、擦掉整块、把改完的内容写回去。这个动作叫读-改-写，代价是几 MB 的搬运。写放大从这里开始。

厂商的解法是塞一层 FTL（Flash Translation Layer），对上仍然报「512 字节扇区、可以随便覆写」的块设备。文件系统看不见擦除块，闪存也看不见文件。FTL 的问题在于它只有 LBA，没有语义。它不知道这 4KB 是刚 fsync 过的数据库日志，还是三年没动过的一张照片。它只能按地址猜冷热，猜错的成本是搬移和擦除。

ext4 和 F2FS 就是这条链上的两个极端：ext4 顺着块设备抽象走，把随机写原样交给 FTL；F2FS 假设自己知道上层在写什么，用追加写把随机写改造成顺序写，代价是自己养一个 cleaner。

二、从 Minix 到 ext4：一条不断打补丁的路 #

ext 家族不是设计出来的，是补出来的。理解这条补丁链比背特性表有用。

Minix 文件系统出自 Andrew S. Tanenbaum，1987 年发布，比 Linux 早五年。Linus 写第一个内核时不想自己写文件系统，直接把它塞了进去。布局已经很接近后来的 ext：引导块、超级块、inode 位图、inode 区、数据区位图、数据区。inode 里 9 个块指针，7 个直接 + 2 个间接。位图语义也和 ext 一致：0 空闲，1 占用。硬伤是块号 16 位，文件最大 64MB 量级。

EXT（extended）由 Rémy Card 在 1992 年随 Linux 一起发布，目的是解决文件大小限制，元数据结构从 Minix 换到 UFS/FFS 那一套。这一版存在严重问题，很快被 EXT2 取代，可查的发行信息很少。

EXT2 是第一个真正活下来的版本，1993 年问世，一直用到 2000 年代。它和 EXT 的元数据结构基本相同，但设计时留了大量预留空间，后面加特性不用重排版。这个决定救了 ext 家族的命。EXT2 把分区切成块组（原译文写「柱面组」，那是机械盘时代继承下来的叫法，内核文档统一用 block group）。每组开头是超级块、组描述符表、块位图、inode 位图、inode 表，然后才是数据块。

EXT2 真正的问题不是功能，是 fsck。掉电之后 e2fsck 要扫全盘找不一致，没有捷径。原文作者记了一个例子：几百 MB 的盘，崩溃后恢复花了 28 小时。这是他自己的经历，不是 benchmark。

EXT3 就是为这件事生的，作者 Stephen Tweedie，1999 年发布，2001 年进 2.4.15 主线。它对 ext2 的唯一实质改动是日志：把即将执行的操作先写进固定区域，掉电后重放日志回到一致状态。磁盘结构其余部分与 ext2 相同。代价是写入落两遍，一次日志一次原地。升级路径当时很轻：tune2fs -j /dev/sda1 给 ext2 加日志，改 /etc/fstab 里的类型，重新挂载。

EXT4 是性能、容量、可靠性三条线一起动：数据分配从块映射换成 extent，一段连续物理块用一个结构描述；时间戳精度到纳秒，加两个高位把 2038 问题推到 2446 年；元数据和日志加 crc32c 校验和（metadata_csum，3.5 引入）；块号从 32 位扩到 64 位，配 flex_bg 让元数据集中放置。

时间线要说清，原文这里容易读错：

事件 时间 说明
ext4 开发版进内核 2006-10 提出，2.6.19 带入 ext4dev，需要显式指定
ext4 标记为稳定 2008-12-25，2.6.28 补丁进主线，推荐使用
Fedora 设为默认 Fedora 11，2009-06 Fedora 9/10 要加安装参数才开
元数据校验和 3.5，2012 metadata_csum，算法 crc32c

原文说「自 Fedora 14 以来 ext4 是 Fedora 默认」，这条是错的，Fedora 11 就已经是了。

从 ext3 升到 ext4，原译文的建议我认同：备份、mkfs 重做、数据倒回。tune2fs -O extents,uninit_bg,dir_index 能原地打开特性，但旧文件不会被重新分配成 extent，索引块布局还是老的，收益打折。

三、ext4 的磁盘布局：块组 #

ext4 把空间切成等大的块组，边界由 s_blocks_per_group 决定，默认跟块大小绑死：

块大小 每组块数 每组大小 32 位下的最大文件系统
1KiB 8192 8MiB 4TiB
2KiB 16384 32MiB 8TiB
4KiB 32768 128MiB 16TiB
64KiB 524288 32GiB 256TiB

表来自内核文档 filesystems/ext4/blocks.html，它顺手纠正了原译文的一个说法：原文写「每一组大小约为 8MB」，那是 1KiB 块时代的数字。今天 4KiB 块的主流配置，一组 128MiB。块大小在 mkfs 时定死，之后改不了，上限受页大小卡：x86 上页是 4KiB，块就不能大于 4KiB；ppc64 和 aarch64 在特定配置下能到 64KiB。

一个块组的内部顺序固定：

text
块组（block group）
┌───────────────────────────┐
│ 超级块（仅备份组有）        │  组 0 必有；其余按 3/5/7 的幂
├───────────────────────────┤
│ 组描述符表 GDT             │  所有组的描述符，多数挤在组 0
├───────────────────────────┤
│ 保留 GDT 块                │  给 resize2fs 在线扩容用
├───────────────────────────┤
│ 块位图                     │  1 位 = 1 个块
├───────────────────────────┤
│ inode 位图                 │  1 位 = 1 个 inode
├───────────────────────────┤
│ inode 表                   │  每个 inode 128 或 256 字节
├───────────────────────────┤
│ 数据块                     │  剩下的全归这里
└───────────────────────────┘

分区最前面还有引导扇区和一块保留区，填在引导记录和第一个分区之间，GRUB 会往里面塞一部分引导代码。GPT 加 UEFI 之后这块意义小了，老盘的 dd 还是要小心它。

块组这个设计有历史包袱：机械盘上一个组内数据物理聚在一起，磁头寻道短。闪存上没有寻道，这个收益直接消失，只剩「元数据离数据近一点」的好处。

四、超级块、GDT 与位图 #

超级块是文件系统的身份证，固定 1024 字节，从分区偏移 1024 处开始，魔数 0xEF53。关键字段（偏移来自内核文档 filesystems/ext4/super.html）：

偏移 字段 干什么
0x0 s_inodes_count inode 总数
0x4 s_blocks_count_lo 块总数低 32 位
0x18 s_log_block_size 块大小 = 2^(10 + 该值)
0x20 s_blocks_per_group 每组块数
0x28 s_inodes_per_group 每组 inode 数
0x38 s_magic 0xEF53
0x3A s_state 干净卸载 / 有错误 / 孤儿待恢复
0x58 s_inode_size inode 大小，128 或 256
0x5C s_feature_compat 兼容特性位
0x60 s_feature_incompat 不兼容特性位，不认识就拒绝挂载
0xCE s_reserved_gdt_blocks 预留给扩容的 GDT 块数
0x150 s_blocks_count_hi 块总数高 32 位（64bit 特性）
0x274 s_wtime_hi 写时间高 8 位，绕 2038
0x3FC s_checksum 超级块校验和

特性位分三档，这个分级很实用：compat 不认识也能读写，incompat 不认识必须拒绝挂载，ro_compat 不认识只能只读挂载。挂载报 "unknown filesystem features" 时，先看是这三档里的哪一档。

超级块坏了不致命，因为有多份备份。规则由 sparse_super 控制：备份只放在组号是 0、或 3、5、7 的幂的那些组里。不开就每组都备份，浪费空间。更新的 sparse_super2 更省，只留两份，用超级块里的 s_backup_bgs[2] 指出来。查本机备份位置不用猜，让 mke2fs 算：

bash
mke2fs -n /dev/sda1        # -n 只打印不落盘，参数要和当初建 fs 时一致

-n 有坑：块大小、特性、inode 大小必须和建库时一样，否则算出来的组号是错的。从备份恢复，dd 或 e2fsck -b 都行：

bash
# 组 1 的备份超级块在 32768 块，块大小 4K，偏移 = 32768 * 4096
dd if=/dev/sda1 of=/tmp/sb.bak bs=4096 skip=32768 count=1
e2fsck -b 32768 /dev/sda1   # 指定备份超级块位置做检查

组描述符表（GDT）是每组的户口本：块位图在哪、inode 位图在哪、inode 表在哪、空闲块和空闲 inode 还剩多少。32 位布局下每个描述符 32 字节，64bit 打开后换成 64 字节，大小记在 s_desc_size。GDT 跟着超级块一起备份，位置在备份超级块后面。

位图有两个，都是「一位一个对象」：块位图管数据块，inode 位图管 inode 表项。1 表示占用，0 表示空闲，这个约定从 Minix 没变过。位图的问题是它是位图。分配一个块要查位、置位，回收一个块要清位，每次改动都落在同一个 4KB 块上。加 flex_bg 之后更集中，所有组的位图挤在组 0 的头几个块，写起来全砸在同一处。

五、inode 与多级间接寻址 #

inode 是文件的户口本，磁盘上定长，ext2 时代 128 字节，ext4 默认 256 字节。多出来的空间放扩展属性、纳秒时间戳高位、项目 ID。内核文档给的 struct ext4_inode 前半段：

c
struct ext4_inode {
    __le16 i_mode;           /* 文件类型 + 权限位 */
    __le16 i_uid;
    __le32 i_size_lo;        /* 文件大小低 32 位 */
    __le32 i_atime;
    __le32 i_ctime;
    __le32 i_mtime;
    __le32 i_dtime;          /* 删除时间，非 0 就是已删除 */
    __le16 i_gid;
    __le16 i_links_count;    /* 硬链接数 */
    __le32 i_blocks_lo;      /* 占用的 512 字节扇区数，不是块数 */
    __le32 i_flags;          /* 0x80000 = EXT4_EXTENTS_FL */
    __le32 i_block[15];      /* 60 字节：块映射或 extent 树根 */
    /* ... i_generation / i_file_acl_lo / i_size_high / i_extra_isize ... */
};

i_block 那 60 字节是关键。64 位系统上一个块号 4 字节，正好 15 个指针。老方案（ext2/ext3，以及没开 extent 的 ext4）的排布是：前 12 个直接指数据块，第 13 个指间接块，第 14 个指双重间接块，第 15 个指三重间接块。

text
i_block[0..11]  ──► 数据块 ×12
i_block[12]     ──► 间接块 ──► 数据块 ×(块大小/4)
i_block[13]     ──► 双重间接 ──► 间接块 ×(块大小/4) ──► 数据块 ×(块大小/4)²
i_block[14]     ──► 三重间接 ──► 再套两层

4KiB 块下一个指针块装 1024 项，能覆盖 12 + 1024 + 1024² + 1024³，约 10.7 亿块，即 4TiB。

原译文这里有两处算错，我改掉：原文写「4K 的块可以支持 512 个 4 字节的间接节点，允许单个文件有 12 + 512 = 524 个扩展盘区」。512 是 2KiB 块（2048/4）的结果，4KiB 块是 1024 项；而 12 个直接指针和「扩展盘区」不是一回事，前者指块、后者是 extent，混着加没有物理意义。

这套方案的毛病在浪费：文件有 1000 个连续块，就得填满一个 1024 项的间接块。元数据量跟数据量成正比，这就给 extent 让出了位置。

定位一个文件走的是「目录项 → inode 号 → inode 表」：

text
路径 /a/b.txt
  1. 读根目录的 inode（inode 号固定为 2）
  2. 在根目录的数据块里查目录项 "a" → 拿到 a 的 inode 号
  3. 用组号 + 组内偏移算出 a 的 inode 在 inode 表的哪一格
  4. 读 a 的数据块，查目录项 "b.txt" → 拿到 b.txt 的 inode 号
  5. 再算一次偏移，读 b.txt 的 inode
  6. 顺着 i_block 里的指针或 extent 取数据块

第 3 步的算式值得一提：组号 = inode 号 / 每组 inode 数，组内偏移 = inode 号 % 每组 inode 数。这就是 s_inodes_per_group 必须写死在超级块里的原因。目录项本身存「名字 + inode 号 + 类型」，不存 inode 内容。同一个 inode 号可以挂多个名字，这就是硬链接。inode 号只在单个文件系统内唯一，跨分区同一个号指两个不同的文件，这也是硬链接不能跨文件系统建的原因。

六、extent 树：ext4 对间接寻址的改良 #

extent 的思路很直白：与其一个块一个块地记，不如记「从逻辑块 N 开始，连续 L 块，映射到物理块 P」。三个结构，都是 12 字节：

c
struct ext4_extent_header {   /* 每个 extent 节点的开头 */
    __le16 eh_magic;          /* 0xF30A */
    __le16 eh_entries;        /* 后面有几项 */
    __le16 eh_max;            /* 最多能放几项 */
    __le16 eh_depth;          /* 0 = 叶子节点，指向数据 */
    __le32 eh_generation;
};

struct ext4_extent {          /* 叶子节点里的一项 */
    __le32 ee_block;          /* 起始逻辑块号 */
    __le16 ee_len;            /* 覆盖多少块，>32768 表示未初始化 */
    __le16 ee_start_hi;
    __le32 ee_start_lo;       /* 起始物理块号 */
};

struct ext4_extent_idx {      /* 内部节点里的一项 */
    __le32 ei_block;          /* 覆盖到这个逻辑块为止 */
    __le32 ei_leaf_lo;
    __le16 ei_leaf_hi;        /* 下一层节点的物理块号 */
    __le16 ei_unused;
};

eh_depth 最大 5。逻辑块号最多 2^32，每层能放 (块大小 - 12) / 12 项，4KiB 块下是 340 项，340^5 刚过 2^32。根节点直接放在 inode 的 60 字节 i_block 里，减去 12 字节头剩 48 字节，正好 4 个 extent。文件碎片不超过 4 段时，寻址不需要任何额外元数据块。

同一件事在两种方案下的对比（1000 个连续块）：

text
块映射方案
  inode.i_block[12] ──► 间接块（4KiB，1024 项）
                          ├─ 项 0  : 物理块 10000
                          ├─ 项 1  : 物理块 10001
                          ├─ ...
                          └─ 项 999: 物理块 10999
  元数据开销：1 个 4KiB 块 + 1000 个条目

extent 方案
  inode.i_block ──► header + [ ee_block=0, ee_len=1000, ee_start=10000 ]
  元数据开销：12 字节

ee_len 有个顺手的设计：值 ≤ 32768 表示已初始化的 extent，> 32768 表示未初始化，实际长度是 ee_len - 32768。未初始化 extent 是给 fallocate 预分配用的，块已占住但内容没写，读出来是 0，不用真去落盘。extent 树的叶子块有校验和，eb_checksum 是 crc32c(uuid + inode 号 + generation + 整块内容)。inode 里的 4 个 extent 不单独校验，因为 inode 自己已经被校验过。

extent 也是 F2FS 明确不要的东西，理由在第十一章：GC 搬移会改变物理块，extent 的区间范围跟着变，索引块尺寸不可预测，日志结构的原地索引就装不下了。取舍很硬。

七、ext4 的几个标志性特性 #

四件事单独讲，因为它们正是后面「在闪存上难受」的原因。

delayed allocation：先攒够再分配 #

delalloc 从 2.6.30（2009-06）起在 ext4 上默认开启，明显降低碎片率，代价是崩溃窗口：write() 返回了，块还没分配，这时掉电数据就没了。写文件时页缓存只标记脏页，不立刻分配磁盘块，等回写时才一次性分配，此时能看到整个写入区间，容易找到连续空闲块。这个坑 2009 年闹得很大。修法是在 2.6.30 里给 rename、truncate 加隐式 fsync，凡是会让用户以为「数据已落盘」的元数据操作，都先刷一次数据。5.x 上这个坑已经补上，但 nodelalloc 和 delalloc 之间仍要按负载选：

bash
mount -o delalloc    /dev/nvme0n1p1 /data   # 默认，碎片少
mount -o nodelalloc  /dev/nvme0n1p1 /data   # 写即分配，掉电窗口小，碎片多

journal：jbd2 与三种模式 #

日志子系统叫 jbd2，独立的一套代码。三种 data= 的差别在文件数据算不算日志的一部分：

模式 元数据进日志 数据进日志 掉电后的结果
data=journal 是 是 一致，最慢，所有数据写两遍
data=ordered（默认） 是 否，但先于元数据落盘 不会出现「元数据指向垃圾数据」
data=writeback 是 否，顺序不限 读到旧数据塞进新文件

data=ordered 是多数发行版默认，它给的是一个具体保证：不会让 inode 指向还没落盘的数据块。提交间隔由 commit= 控制，默认 5 秒，这个值直接换性能和丢数据窗口：

bash
mount -o data=ordered,commit=30 /dev/nvme0n1p1 /data

30 秒意味着掉电最多丢 30 秒的写入。日志盘、邮件队列这类场景别这么干。日志本身也占空间，原文那个 /boot 是 128MB 的文件系统，日志 32MB，占比不低。

64bit 与 bigalloc #

64bit 把块号从 32 位扩到 64 位，配合 metadata_csum 把文件系统上限从 16TiB 推到 64ZiB 量级（4KiB 块）。它改的是 GDT 描述符大小，从 32 字节变 64 字节。bigalloc 换的是分配单位，从块变簇，默认簇是块的 16 倍，4KiB 块配 64KiB 簇。位图开销降到 1/16，代价是小文件浪费：一个 100 字节的文件占一整个 64KiB 簇。这个特性和 F2FS 的思路正好相反。F2FS 靠段管理空闲空间，不需要大簇省位图；ext4 用位图，就得靠簇来压元数据比例。

flex_bg：把元数据打包 #

flex_bg 是 2.6.28 一带进来的（具体首次可用版本我没逐版本核对）。它把 2 的幂个块组打包成一个逻辑大组，组内所有位图和 inode 表集中放在第一个组里。第四章那段 dumpe2fs 就是它的现场：组 1、组 2 的位图都在组 0。mkfs 的 -G 控制打包几个组。好处是元数据连续，顺序读能一次读一大片。坏处是写入集中：位图全在一个地方，每次分配都要改那几块。机械盘靠缓存扛得住，闪存上这几块被反复擦写。

bash
mke2fs -G 16 /dev/nvme0n1p1                     # 16 个组打一包，默认值
mke2fs -E packed_meta_blocks=1 /dev/nvme0n1p1   # 位图和 inode 表全放盘头

特性清单，按重要程度排：

特性 作用 版本
extent 段式寻址，替代块映射 2.6.19 起
flex_bg 元数据打包 2.6.28 一带（未逐版本核对）
64bit 块号 64 位 原文未标注
dir_index 目录用 htree，大目录查找从 O(n) 到 O(log n) ext3 时代即有
uninit_bg 组未初始化，mkfs 快 2.6.28 一带（未验证）
metadata_csum 元数据 crc32c 校验 3.5（2012）

fast_commit 小改动快提交，缩短 fsync 延迟 5.10 一带（未验证）

八、ext4 在闪存上的痛点 #

把前面的机制摆到一起，闪存上的问题就露出来了。四条。

第一条，原地更新直接把随机写交给 FTL。改一个 4KB 页，FTL 得读出整个擦除块、改、擦、写回。写放大倍数取决于 FTL 的映射粒度，页级映射好一点，块级映射（低端 eMMC 常用的混合映射）差很多。这个倍数跟主控强相关，没有统一数字，我不编。

第二条，元数据热点。flex_bg 让位图和 inode 表挤在一起，每次创建文件都要改位图那几块。这几块的擦写次数明显高于数据区，磨损均衡被迫频繁搬它们。第三条，日志是双写。一次写入至少碰两个地方：日志区和目标块。日志区是固定的一小片，反复覆盖，跟第二条是同一个病。data=journal 下所有数据也进日志，写放大翻倍。

第四条，没有冷热信息。ext4 不知道哪个文件热、哪个冷。分配时有一些启发式（新文件往别的组放、目录和它下面的文件放同组），但这些信息传不到 FTL。FTL 只能看 LBA，谁被写得频繁就当谁热。

结论直说：ext4 在闪存上不难用，是效率不高。同样的写入量，它让 FTL 做更多搬运和擦除，SSD 的寿命和尾延迟都吃这个亏。桌面和服务器上没人计较，是因为 SSD 的 DWPD 和主控缓存把这些抹平了；手机 eMMC 上小文件随机写是常态，就不能不计较。

九、日志结构文件系统：把随机写变成顺序写 #

LFS 的想法 1992 年就有，Rosenblum 和 Ousterhout 的论文《The Design and Implementation of a Log-Structured File System》，SOSP '92。同一个人还是 Tcl 的作者。

别把 LFS 和 journaling 搞混。Journaling 是在盘上划一块区域记操作，用来恢复；LFS 是把整个盘当成一条日志，所有写都是往日志尾部追加。基本动作：要改一个块，不覆盖它，而是在日志尾部写一份新的，更新索引指向新位置，旧块标记作废。顺序写是闪存和机械盘都喜欢的模式，这一条直接换来性能。论文里的 Sprite LFS 数据：小文件随机写比当时的 FFS 快一个数量级；去掉垃圾回收开销后，仍能用掉 70% 的磁盘带宽。这两个数是论文里的，不是现在机器上测的。

顺序写要成立，前提是盘上始终有大片空闲区域。日志被切成固定大小的段（segment），空间不够时把碎片化段里还有用的数据搬出来，腾出连续的段。这个动作就是 cleaner，是 LFS 全部代价的来源。

盘上只有两样东西位置固定：超级块和检查点。检查点（checkpoint）是某个时刻文件系统一致状态的快照，创建分两步：先把所有数据、索引、inode 表、段使用表落盘；再在固定的检查点区记下这些结构的地址和时间戳。掉电保护靠双检查点交替：两个区轮流写，时间戳最后落，重启时选时间戳最新的那个。恢复到这个点之后还能顺着日志前滚（roll-forward）。F2FS 为单个文件的 fsync 实现了前滚：fsync 时只落这个文件的数据和它的直接索引，不落整棵树。

LFS 有两个原生缺陷，F2FS 的全部设计都在对付它们。第一个是滚雪球，英文叫 Wandering Tree。改一个数据块，直接索引要改；直接索引改了位置，上一级间接索引也要改；一路传到 inode、inode map、检查点。

text
写数据块 D（新位置）
   └─► 直接索引块 N1 要改（因为 D 挪了）
         └─► 间接索引块 N2 要改（因为 N1 挪了）
               └─► inode 块要改（因为 N2 挪了）
                     └─► inode map 要改（因为 inode 挪了）
                           └─► 检查点要改（因为 map 挪了）

一次 4KB 写入牵出五个元数据块的重写，写入量放大的倍数跟树高成正比。第二个是清理开销。段里还剩多少在用块，决定搬移成本。空间越满搬得越多，最坏情况是每写一个新块都要搬一个旧块。这个成本随利用率上升不是线性的，第十三章给算式。

十、F2FS 的空间布局：六个区域 #

F2FS（Flash Friendly File System）出自三星，作者 Jaegeuk Kim，2012-10 发到社区，2012-12 进 Linux 3.8 的合并窗口（3.8 在 2013-02 发布）。它和 JFFS2、UBIFS 不一样，不是跑在裸 NAND 上的，走标准块设备接口。所以它跟 ext4 一样面对 FTL，区别在于它假设自己比 FTL 更懂上层。

空间切法跟 ext4 完全不同：段（segment）固定 2MB，若干连续段组成节（section），若干连续节组成区（zone）。section 和 zone 默认都等于一个 segment，mkfs 时可以改。

三个单位用途不同：segment 是空间管理单元（SIT 一位一段），section 是日志写入和清理的单元，zone 对应 FTL 的 GC 单元。F2FS 把 section 大小调到跟 FTL 的 GC 单元一致，就能把「文件系统回收」和「主控回收」对齐，减少互相踩。整卷切成六块：

text
          ← 对齐到 segment →
┌────────┬────────┬──────────┬──────────┬──────────┬──────────────┐
│ 超级块  │ 检查点  │   SIT    │   NAT    │   SSA    │  Main Area   │
│   SB   │   CP   │          │          │          │              │
└────────┴────────┴──────────┴──────────┴──────────┴──────────────┘
                      └── 各占若干 segment ──┘   ↑
                                            对齐到 zone
──────────────────────────────────────────────────────────────────►
Main 内部再切：
   ┌───────┬─────┬───────┐
   │Segment│ ... │Segment│
   └───────┴─────┴───────┘
    └──── Section ────┘
    └───────── Zone ─────────┘

超级块（SB）在分区最开头，两份互为备份，装分区基本信息和 mkfs 时定死、之后不能改的参数。检查点（CP）装文件系统状态、NAT 和 SIT 谁在用哪一份的位图、孤儿 inode 列表、当前活跃段的所有者信息。孤儿 inode 是删了但还有引用、暂时放不掉的 inode，挂在列表里等下次挂载时清。CP 的作用是给出一个「到这一刻为止都对得上」的起点，掉电后从这里往后重放。CP 有两份交替写，靠头尾数据块里的 version 判断哪份新。NAT 和 SIT 也各留两份，CP 里记着该用哪一份。这就是内核文档说的 shadow copy。

段信息表（SIT）记主区每个段里有多少在用块，外加一份标记每个块是否还在用的位图。GC 选哪个段下手、段里哪些块要搬，全靠这张表。

节点地址表（NAT）是关键。F2FS 里 inode、直接节点、间接节点统称 node，每个 node 有个编号，NAT 存「编号 → 实际块地址」。

段摘要区（SSA）是反向索引。主区每个数据块属于哪个 inode、在文件里的偏移是多少，都记在这里。GC 搬一个块之前得先知道它爹是谁，不然改完指针就找不回来了。

主区（Main Area）放真正的数据和索引。一个段要么全是数据段、要么全是索引段，不混。这个约束是冷热分离能成立的前提。默认留 5% 的 overprovision 空间（mkfs.f2fs -o），不对外报，专门留给 GC 周转。空间太满时 GC 没地方放搬移数据，会卡住整个写入。

十一、F2FS 的索引结构：NAT / SIT / SSA #

滚雪球怎么断的？靠 NAT 插进来一次地址转译。ext4 里间接索引块的位置写在上一级索引里，改动会一级一级往上冒。F2FS 里上层只记 node 号，node 号到块地址的映射在 NAT。数据块挪了，改直接节点，再改 NAT 对应那一行，到此为止。间接节点不知道下层挪了。

text
ext4（位置靠上级记）
  inode ──► 间接索引 ──► 直接索引 ──► 数据块
             ↑ 数据块挪了，这一串全要改

F2FS（位置靠 NAT 转译）
  inode ──► 间接节点 ──► 直接节点 ──► 数据块
              │            │            │
              └── NAT 用 node 号查实际地址 ──┘
              ↑ 数据块挪了，只改直接节点 + NAT 那一行

查 /dir/file 比 ext4 多一次 NAT 查表：

text
1. 查 NAT，拿根目录 / 的 node 地址，读出来
2. 在根目录的数据块里找目录项 "dir"，拿它的 inode 号
3. 拿 inode 号查 NAT，得到那个 inode 块的实际地址
4. 读 dir 的 inode 块
5. 在 dir 的数据块里找目录项 "file"，重复 3、4 两步
6. 从 file 的 inode 里顺着索引取数据块

索引结构本身是固定的多级，不是 extent：

text
inode 块（4KiB）
├─ 数据块号 ×923          ← 直接指向数据
├─ 直接节点指针 ×2  ──► 直接节点块（1018 个数据块号）
├─ 间接节点指针 ×2  ──► 间接节点块（1018 个节点指针）
│                        └─► 直接节点块（1018 个数据块号）
└─ 双重间接指针 ×1 ──► 间接节点 ──► 直接节点 ──► 数据块

这组数字来自内核文档 filesystems/f2fs.html：inode 块里 923 个数据块索引、2 个直接节点指针、2 个间接节点指针、1 个双重间接指针，每个直接/间接节点块装 1018 项。算下来单文件上限 3.94TB。923 和 1018 这两个怪数字是这样来的：4KiB 减去头部固定字段，剩下空间除以 4 字节地址，正好这么多，不是设计选出来的整数。

原译文写「最多有 3 级间接索引」，这是口误。按内核文档的结构，最深路径是双重间接（inode → 间接节点 → 直接节点 → 数据），说是 3 级索引可以，但要说清是「双重间接加一个额外层级」，别写成三层间接——那得是三重间接，F2FS 没有那一层。两个上限：单文件 3.94TB（inode 内指针容量限制）；单分区 16TB（块地址 4 字节，2^32 × 4KiB）。第二个是硬限制，卷再大也超不过，手机存储还在 1TB 以内，碰不到。

小文件有个专门优化：inline data，小于 3.4KB 的文件内容直接塞进 inode 块的剩余空间，不占数据块。Android 上小文件极多，这一条省的不只是空间，还有一次寻址和一次 I/O。

bash
mount -o inline_data /dev/mmcblk0p3 /data      # 5.x 起默认开启
mount -o noinline_data /dev/mmcblk0p3 /data    # 关掉

F2FS 不要 extent，理由在日志结构本身：GC 把数据块搬到新位置，extent 的物理起始地址就变了。如果 extent 能合并能分裂，索引块尺寸跟着浮动，而日志结构要求索引块尺寸可预测，不然搬一个索引块就得拆成两个，滚雪球又回来了。固定层级的指针数组尺寸恒定，搬移时原地替换地址就行。

十二、冷热分离：为什么要把数据分段 #

日志结构的老问题是段里冷热混住。一个段里既有每秒改一次的文件，也有三年没动的照片，这个段会一直被前者弄脏，GC 每次都得把照片搬一遍。搬移量跟在用块数成正比，混住就意味着永远搬不完。

F2FS 的解法是开六条日志，按冷热分头写。这就是六级温度：

类型 温度 装什么
node 热 目录的 inode、目录的直接索引块
node 温 普通文件的 inode、直接索引块
node 冷 间接索引块
data 热 目录的数据块（目录项）
data 温 普通文件的数据块
data 冷 多媒体文件数据、GC 搬移过来的块

分头写的效果是每个段里数据的更新频率趋于一致。冷段里的块大多一直有用，GC 扫到它基本不用搬；热段里的块大多已经作废，GC 扫过去只有少量要搬。这就是原文说的 binomial 分布：大部分段要么很空、要么很满，少落在中间那种尴尬状态。

这套分法能调，active_logs 只支持 2、4、6 三个值，默认 6：

bash
mount -o active_logs=6 /dev/mmcblk0p3 /data

6 是热/温/冷 × 节点/数据全开；4 是数据分三级、节点只分热冷；2 只分热/冷两档。底层块设备支持 write streams（NVMe 的 stream 特性、ZNS）时，F2FS 会把热/温/冷数据分别映射到 stream 1/2/3，让主控直接知道冷热，不用猜。

温度判断靠两套启发式，一套是内核按文件类型和操作猜，一套是上层显式指定：

来源 数据温度
元数据（META） WRITE_LIFE_NONE | REQ_META
热节点 WRITE_LIFE_NONE
温节点 WRITE_LIFE_MEDIUM
冷节点 WRITE_LIFE_LONG
冷数据（ioctl 或扩展名命中） WRITE_LIFE_EXTREME
缓冲写产生的热数据 WRITE_LIFE_SHORT
缓冲写产生的温数据 不设

表来自内核文档的 write-hint 一节。WRITE_LIFE_* 是能一路传到块层、再传到支持 stream 的设备上的提示。应用想自己标冷热，用 F2FS_IOC_SET_PIN_FILE 之类的 ioctl，或者让 mkfs 时配好的扩展名列表命中（-e mp3,mp4,jpg）。视频、图片这类一次写入反复读的文件，按扩展名扔进冷数据区划算。

局限要说清：这套冷热是猜的。ext4 上那个三年没动的照片和每秒写一次的日志，到 F2FS 里如果扩展名一样、打开方式一样，还是会被塞进同一个温度档。原文作者自己也承认「冷热分离还较为简单」。真正准的冷热信息只有应用知道，文件系统拿不到。

十三、cleaner：日志结构的垃圾回收代价 #

cleaner 是 F2FS 的 GC 线程，干三件事：挑一个牺牲段、找出里面还在用的块、搬走。内核文档给的流程是四步：

text
1. 查 SIT，挑一个牺牲段（victim）
2. 用 SSA 找出牺牲段里每个数据块的父索引节点
3. 交叉校验「这个块是不是真还被父节点指着」
4. 把确认还在用的块搬走

第 3 步容易漏。SSA 记的是「写入时的归属」，但那个块后来会被覆盖或删掉。SIT 的位图给的是「有没有被释放」，SSA 给的是「当初属于谁」。两者对得上才搬，不然会把作废数据搬到新位置，越搬越乱。

挑牺牲段的算法有两个。贪心（greedy）挑在用块最少的段，实现简单，每次搬得最少，缺点是老段一直不被动，日志块抖动。成本收益（cost-benefit）把段的年龄算进去，老段优先，年龄从 SIT 里记的段更新时间推。热数据马上又要改，搬了白搬；冷数据搬一次能安生很久。分工是：前台 GC 用贪心（要快，别卡住调用者），后台 GC 用成本收益（要准，反正不急）。内核文档写得很明确。搬完的段不是立刻可用，先标记成「预释放」，要等下一个检查点落盘才真正变成空闲。原因是掉电回滚：检查点回退后，那个段在旧检查点里还有在用数据，提前复用就丢数据。

空间不够时 F2FS 也不死守日志写。它会切到 SSR（Slack Space Recycling），也就是 threaded log：直接往碎片化段里的空槽写。这变成随机写，牺牲顺序性，换的是不被前台 GC 卡住。选哪个段做 SSR 也是贪心的，尽量让写入位置还有点连续性。算写放大的账：设一个段里有 u 比例的在用块，要腾出一个空段就得搬 u 份数据，最终只得到 1 - u 份空间。

text
GC 写放大 = 搬移量 / 净腾出量 = u / (1 - u)
叠加一次实际写入，总写放大 ≈ 1 + u/(1-u) = 1/(1-u)
段内使用率 u 总写放大
50% 2.0×
70% 3.3×
80% 5.0×
90% 10.0×
95% 20.0×

这是算式，不是实测数据。它解释了一件事：日志结构文件系统的性能对剩余空间极度敏感。90% 占用时，每写 1 字节实际要写 10 字节到闪存，SSD 寿命按这个倍数消耗。所以 overprovision 不是浪费空间，是买写放大。手机厂商把 /data 留出 10%~20% 不用，就是这个道理。

ext4 没有 cleaner，因为它不搬移。删文件就是清位图位，块立刻进空闲池。代价转移到了 FTL：ext4 那块盘的 GC 是主控在干，你看不见，也调不了。

这是两者最本质的分歧：GC 的活儿要么文件系统干（能看见冷热，但吃 CPU 和带宽），要么 FTL 干（看不见冷热，写放大更高）。没有第三种选择。

十四、F2FS 的发展历程与适用场景 #

F2FS 进主线是 3.8，2013-02 发布。在那之前它在社区里被质疑了很多年，知乎上一批经典问题：三星自己发的文件系统，自家旗舰为什么不用；华为说好用，别人为什么不跟。现在这些问题都有答案了：

时间 事件 来源
2012-10 Jaegeuk Kim 发到 Linux 社区 原文
2012-12 进 Linux 3.8 合并窗口 原文
2018 谷歌 Pixel 3 使用 F2FS，Android Go 推荐用 F2FS 延长器件寿命 原文说法，未独立核实
2019 三星自家旗舰开始用 F2FS 原文说法，未独立核实
2020 前后 多数手机厂商跟进 原文

作者履历也说明问题：Jaegeuk Kim 从三星到摩托罗拉，到华为，到谷歌。人走到哪，F2FS 在 Android 上的推动就到哪。没有历史包袱，可以放手针对 Android 优化——原子写提升 SQLite 在 DELETE 模式下的性能、discard 下发策略减少卡顿，都是从手机场景里长出来的。原子写这块值得单说。SQLite 默认的 rollback journal 模式要「写日志、改数据、删日志」，中间任何一步掉电都靠日志回滚。有了原子写，一次 F2FS_IOC_START_ATOMIC_WRITE 覆盖多块，要么全成要么全不成，不用再靠用户态日志文件兜底。这个特性对手机上的数据库和配置存储收益直接。

适用场景按介质和负载分开说。值的地方：eMMC/UFS 的手机、平板、车机（小文件多、随机写多、容量紧、寿命敏感，F2FS 的设计目标就是这些）；写放大型负载（日志采集、消息队列本地盘、频繁覆盖写的缓存目录，追加写把随机写变成顺序写，主控 GC 压力小）；ZNS/SMR 这类只能顺序写的设备（F2FS 有 blkzoned 支持，ext4 在这个场景基本没得选）；小容量低端设备（Android Go 推荐 F2FS 的理由是延长器件寿命，对小容量 eMMC 站得住）。不值的地方：服务器系统盘和根分区（ext4 的工具链成熟度、恢复流程、发行版默认支持都是实打实的运维成本，fsck.f2fs 能力比 e2fsck 弱一档）；空间长期跑在 90% 以上的盘（写放大按前面的表走，F2FS 在这个区间比 ext4 更难受）；需要精细控制 inode 数量和目录索引行为的场景（ext4 的 -i、-I、dir_index 旋钮更细）；要求快照、在线缩容、成熟 resize 的场景（resize2fs 在线扩容用了二十年，F2FS 的在线 resize 是后来补的）。

十五、ext4 与 F2FS 正面对比 #

前十章讲机制，这一章给结论。同一件事，两边各自付出什么代价，逐项写清。

维度 ext4 F2FS 谁赢，什么条件下
分配方式 位图找空闲位，就地置 1 活跃日志尾部追加，推进指针 闪存上 F2FS，机械盘上 ext4 没对手
空闲空间记账 块位图，flex_bg 下集中在组 0 SIT：每段在用块数 + 位图 平手，都是 O(1) 查询
元数据写入模式 原地改位图、inode 表 异地写节点，靠 NAT 转译 闪存上 F2FS
写放大（文件系统层） 1× 数据 + 日志双写，约 2× 1/(1-u)，u 是段使用率 空盘平手，满盘 ext4 明显更省
写放大（叠加 FTL） 随机写让 FTL 读-改-写，倍数看主控 顺序写让 FTL 一擦块一写，接近 1× 闪存上 F2FS，这是它的主战场
4K 随机写 靠 FTL 的映射粒度兜底 顺序落到日志尾，天然聚合 F2FS，小文件密集时差距最大
顺序大文件写 好，extent 让大文件几乎无元数据 也好，但 GC 会插进来抢带宽 ext4 略稳，F2FS 尾延迟有毛刺
读性能 极好，索引路径短 多一次 NAT 查表，extent cache 能缓解 ext4
空间利用率 高。删除立刻回收，没有预留 要留 5% 以上 overprovision 给 GC ext4，手机上的 10%~20% 是硬成本
碎片 延迟分配 + 预分配，原文实测 1.5%~3.3% 日志写天然顺序，但 GC 会制造碎片 F2FS 布局更整齐，ext4 数值也不高
掉电恢复 jbd2 重放日志，秒级 双检查点 + roll-forward，也是秒级 平手，F2FS 的 fsync 语义更弱
工具成熟度 e2fsck 二十年，问题基本都见过 fsck.f2fs 能力弱一档，修复手段少 ext4
在线扩容 resize2fs 成熟，预留 GDT 块 有 resize.f2fs，历史短 ext4
最大文件 16TiB（4K 块，extent） 3.94TB ext4
最大分区 1EiB 量级（64bit 特性） 16TB（4 字节块地址） ext4
默认发行版采用 几乎所有主流发行版的根分区 Android；部分嵌入式 ext4

挑几项容易被误读的说透。写放大这一行不能只看文件系统层。ext4 自己只写一遍，但它在闪存上引发的 FTL 内部搬运没算进这个 1×。F2FS 自己搬得多（cleaner），但它让 FTL 几乎不用搬。谁的总写放大更低，取决于盘多满、负载多随机：空盘上 ext4 更省，70% 占用的小文件随机写负载上 F2FS 更省。

随机写这一行，ext4 不是做不到顺序。分配器会尽量把连续写放在连续块上，delalloc 也是为这个服务的。问题在「随机」这个前提：应用真随机改 4K 页，ext4 只能原地改，一次一个页，FTL 一次一个擦除块。恢复能力这一行别被「都有日志」骗了。ext4 的 jbd2 保证元数据一致，data=ordered 下还额外保证数据先于元数据落盘。F2FS 的 fsync_mode=posix（默认）语义比 ext4 松，内核文档明写了这一点，要和 ext4 对齐得用 strict，代价是性能退化：

bash
mount -o fsync_mode=strict /dev/mmcblk0p3 /data   # 跑 xfstests generic/342 才过

这一条是选型时最容易翻车的地方。把 ext4 上的数据库直接搬到 F2FS，测试全过，掉电测一次就出事。

结论：这不是谁更好，是两条不同的账。ext4 把 GC 的活儿包给 FTL，自己轻，代价是写放大不可控；F2FS 自己扛 GC，代价是空间预留和 CPU 开销，换来写放大可控和顺序写。

十六、怎么选：按介质与负载 #

决策按介质先分一次，再按负载分一次。

介质 / 场景 选 理由
机械盘（HDD） ext4 F2FS 的顺序写优势在寻道上没意义，GC 白烧 CPU
SATA/NVMe SSD，桌面或通用服务器 ext4 负载杂、盘不易满、工具熟，收益抵不过风险
NVMe SSD，写密集且可测（数据库、日志） 先测，再定 随机写聚合收益真实，但要跑掉电和 fsync 语义测试
eMMC / UFS，手机、平板、车机 F2FS 设计目标就是这个场景，overprovision 和冷热分离刚好对上
小容量低端设备 F2FS 寿命优先，Android Go 的选择
ZNS / SMR F2FS 有 blkzoned 支持；ext4 在只能顺序写的设备上没有对应机制
只读镜像、容器层 两个都不是 看 EROFS，那是另一个话题

三条判断线。盘长期占用超过 85%，别换 F2FS，写放大按 1/(1-u) 走，这时 F2FS 的 cleaner 和 FTL 的 GC 都在满负荷，尾延迟会比 ext4 更难看。负载是「一次写入、反复读」（视频、镜像、备份归档），换 F2FS 收益很小。追加写的好处主要体现在反复覆盖写，读多写少的场景两边差不多，还多个 NAT 查表。跑数据库，先看 fsync 语义。F2FS 默认的 posix 模式比 ext4 松，SQLite、PostgreSQL 这类依赖 fsync 保证的，挂 fsync_mode=strict 再压测。这一条不做，测试环境的结论不能信。

最后一句实话：ext4 是默认答案，因为它不出错。F2FS 换来的是特定负载下的性能和寿命，代价是运维复杂度。你没有明确的写放大痛点，就别换。

十七、mkfs 与挂载参数的实用建议 #

参数名全部对齐 man page 和内核文档，照抄能跑。

ext4 这边 #

bash
mkfs.ext4 -b 4096 \
          -O extent,64bit,metadata_csum,flex_bg,dir_index,sparse_super,large_file \
          -I 256 -m 1 -J size=128 -L data /dev/nvme0n1p1

-m 1 预留块比例，默认 5%。留给 root 的空间用来防碎片和救急，/ 分区留 5%，纯数据盘 1% 够用。-I 256 inode 大小，128 字节的 inode 拿不到 2038 之后的时间戳，也放不下项目 ID 和部分扩展属性，默认已经是 256，写出来是为了提醒你建完就改不了。-J size=128 日志大小，单位 MB，默认按卷大小算，数据库盘给大一点能合并更多事务。-O metadata_csum crc32c 校验，2012 年之后的 e2fsprogs 默认开，老库升级时不带。RAID 上要加 -E stride= 和 stripe_width=，这两个参数影响位图落点，配错会把元数据全压在一块盘上。

bash
mount -t ext4 -o noatime,data=ordered,commit=30,errors=remount-ro /dev/nvme0n1p1 /data

text
# /etc/fstab，第四列是挂载选项
UUID=79fc5ed8-5bbc-4dfe-8359-b7b36be6eed3  /data  ext4  defaults,noatime,commit=30  0 2

noatime 不更新访问时间，读一次写一次元数据，全盘扫描时开销很难看，relatime 是 2.6.30 起的默认。commit=30 放宽日志提交间隔（默认 5 秒），能合并更多写入，代价是掉电最多丢 30 秒。errors=remount-ro 出错就只读挂载，默认是 continue，出错了还继续写，坏块会扩散。

bash
dumpe2fs -h /dev/nvme0n1p1                 # 只看超级块，比全量 dump 快得多
tune2fs -l /dev/nvme0n1p1                  # 同上，另一套工具
e2fsck -fn /dev/nvme0n1p1                  # -n 只检查不修，安全
tune2fs -O metadata_csum /dev/nvme0n1p1    # 老库补开校验和

F2FS 这边 #

bash
mkfs.f2fs -l userdata -s 2 -z 1 -o 8 -e "mp3,mp4,jpg,png" /dev/mmcblk0p3

-s 每个 section 几个 segment，默认 1。设成 2 让 section 变成 4MB，用来对齐主控的 GC 单元，设错了适得其反。-z 每个 zone 几个 section，默认 1。-o overprovision 百分比，默认 5，留给 GC 的周转空间，不报给 df，容量紧的设备别调到 3 以下。-e 扩展名列表，命中的文件写进冷数据区，视频、图片、压缩包这类一次写反复读的适合放进去。

bash
mount -t f2fs -o background_gc=on,gc_merge,discard,noatime,inline_data /dev/mmcblk0p3 /data

text
# /etc/fstab
UUID=xxxx-xxxx  /data  f2fs  defaults,noatime,background_gc=on  0 0

background_gc=on 是默认值，系统空闲时后台 GC，避免前台卡顿，压测时可以设 off，生产别关。gc_merge 让后台 GC 线程接管前台 GC 请求，前台 GC 在 I/O 或 CPU 吃紧的进程里跑会拖很久。discard 段被清理时下发 TRIM，SSD 上开着有用；eMMC 上要测，有些主控的 discard 实现会引入延迟毛刺，可以换成周期性 fstrim。inline_data 小文件塞 inode，5.x 起默认开。

压测时想关检查点，这是危险操作，掉电等于回到挂载时刻：

bash
mount -o checkpoint=disable:10% /dev/mmcblk0p3 /mnt/test

10% 表示最多牺牲 10% 空间来避免 GC，用 /sys/fs/f2fs/<dev>/unusable 看实际被占用了多少。

bash
dump.f2fs -i /dev/mmcblk0p3                       # 打印超级块和布局
fsck.f2fs -f /dev/mmcblk0p3                       # 强制检查，会改盘
cat /sys/fs/f2fs/mmcblk0p3/gc_urgent

换文件系统的流程 #

别原地转，两个方向都没有可靠工具。备份、重建、倒回：

bash
# 1. 备份（保留属性、ACL、稀疏文件）
tar --xattrs --acls --sparse -cpf /backup/data.tar -C /mnt/data .

# 2. 卸载、重建
umount /mnt/data
mkfs.f2fs -l data -o 8 /dev/nvme0n1p1     # 或 mkfs.ext4 ...

# 3. 挂载、倒回
mount /dev/nvme0n1p1 /mnt/data
tar --xattrs --acls --sparse -xpf /backup/data.tar -C /mnt/data

--sparse 别省。没有它，稀疏文件会被展开成实心文件，一个 100GB 的虚拟机镜像能变成 500GB。

十八、易错点速查 #

坑 真相
「ext4 的柱面组约 8MB」 那是 1KiB 块时代的数字。4KiB 块下一组 32768 块，即 128MiB
「ext4 每组都有自己的超级块」 只有 sparse_super 规则的组才有：组号是 0 或 3/5/7 的幂
「4K 块能放 512 个间接指针」 4KiB/4 = 1024 项。512 是 2KiB 块的结果
「12 直接指针 + 512 间接项 = 524 个 extent」 直接指针指块，extent 是区段，不能相加。extent 下 ee_len 上限 32768 块
「inode 是 256 字节的块」 256 是 e2fsprogs 给 ext4 的默认；ext2 时代 128；-I 建完不能改
「ext4 从 Fedora 14 起是默认」 Fedora 11（2009-06）就已经是
「delalloc 只影响碎片」 它开了崩溃窗口。write 返回但块没分配时掉电会丢数据，2.6.30 靠 rename/truncate 隐式 fsync 补上
「ext3 的日志里有文件数据」 只在 data=journal 下。默认的 ordered 不把数据写进日志
「ext4 挂成 ext2 没影响」 日志被绕过，恢复时间回到 fsck 全盘扫描，更容易丢数据
「ext4 碎片率高，要定期 defrag」 原文实测 1.5%~3.3%。e4defrag 有限制，多数场景不值得做
「F2FS 有 3 级间接索引」 内核文档给的是 923 数据块号 + 2 直接 + 2 间接 + 1 双重间接，最深是双重间接
「F2FS 用 extent 会更省」 不会。GC 搬移改变区间，extent 尺寸浮动，日志结构要的是固定尺寸索引
「F2FS 的 16TB 限制是文件大小」 是分区大小。单文件上限 3.94TB
「F2FS 的 CP 和 NAT/SIT 一样只有一份」 都留两份，靠 CP 里记的位图指定用哪一份
「F2FS 删文件就释放空间」 段要先被 cleaner 腾空，df 看到的空间和实际可写空间不是一回事
「F2FS 在满盘上和 ext4 一样」 写放大 1/(1-u)，90% 占用是 10×。满盘时 F2FS 更吃亏
「F2FS 的 fsync 和 ext4 等价」 默认 fsync_mode=posix 比 ext4 松。要对齐得挂 strict，性能退化
「段里在用块越少越好搬」 搬移量按在用块算，但选段还要看年龄。热段搬了白搬，这是 cost-benefit 存在的理由

② 修正的错误 #

  1. 「柱面组大小约 8MB」不成立。 原译文第 66–68 行说每组「约为 8MB」。8MiB 是 1KiB 块下的块组大小；4KiB 块下 s_blocks_per_group = 32768，一组 128MiB。数据出自内核文档 filesystems/ext4/blocks.html。
  2. 「柱面组」这个术语该换成「块组」。 内核文档统一用 block group。原译文在图 1 处写「柱面组」，在 dumpe2fs 处写「Group」，两个概念混用。cylinder group 是 BSD FFS 的术语，ext 家族从 ext2 起就是 block group。
  3. 「inode 是 256 字节的块」放错了位置。 原译文第 36 行讲 Minix 时就说 inode 是 256 字节，那是 ext4 时代的默认值。128 字节是 ext2 的默认，e2fsprogs 现在给 ext4 的默认是 256，-I 可改，建完不能改。
  4. 「4K 的块支持 512 个 4 字节间接节点，允许单个文件有 12 + 512 = 524 个扩展盘区」两处错。 一，4KiB 块能装 1024 个 4 字节指针，512 是 2KiB 块的结果。二，12 个直接指针指向数据块，不是 extent，两者不能相加。
  5. 「EXT3 的日志会将文件数据随同元数据写入指定区域」过度概括。 只有 data=journal 把数据写进日志。默认的 data=ordered 不写数据，只保证数据先于元数据落盘。原译文把三种模式混成了一种。
  6. 「自 Fedora 14 以来，EXT4 一直是 Fedora 的默认文件系统」错误。 Fedora 11（2009-06）就已把 ext4 设为默认；Fedora 9 要加 ext4dev 安装参数，Fedora 10 要加 ext4 参数。依据是 Fedora 官方 wiki 的 Ext4 in Fedora 11 页面。
  7. dumpe2fs 输出里大量字段值为空。 原译文第 91–128 行的 Inode count、Block count、Group descriptor size、Journal inode 等字段冒号后什么都没有。这是抓取或排版时丢了值，不是文件系统没这些字段。本文按 dump 的实际格式把关键字段补成有值的形态，保留原输出的结构与顺序。
  8. 「EXT2/EXT3 挂成 EXT4 会有小幅性能提升」要加条件。 老布局挂上去不会自动变成 extent，索引块还是块映射。只有 tune2fs -O extents,uninit_bg,dir_index 之后再新建的文件才走新路径。
  9. 「F2FS 最多有 3 级间接索引」是口误。 内核文档给的结构是 923 个数据块号 + 2 个直接节点 + 2 个间接节点 + 1 个双重间接，最深路径是双重间接。写成「3 级间接」会让人以为是三重间接，F2FS 没有那一层。
  10. 「F2FS 的两个检查点各占一个 Segment」需要限定。 内核文档只说明 CP 有两份、用 shadow copy 机制。CP 区大小按卷大小算，不是恒定两个 segment。原译文这句在多数小卷上成立，作为通用结论不成立。
  11. 「数据块地址 4 字节，最大分区 16TB」只在 4KiB 块下成立。 2^32 × 4KiB = 16TiB 的算式没错，块大小不是 4KiB 时结果不同，原文没写这个前提。
