本文只回答一个问题：一个进程要访问文件时，内核替它记住了哪些状态。讲什么：task_struct 里的 fs_struct、files_struct、fd 数组、struct file、open() 链路、fork/exec 下 fd 表的三种走向、fd 上限、/proc/pid/fd。不讲什么：inode/dentry/super_block 内部布局，页缓存回写，ext4 磁盘格式。跨篇指路：VFS 四大对象看「VFS 虚拟文件系统解析」；ext4 磁盘结构看「Linux 的 EXT4 文件系统的历史、特性以及最佳实践」；挂载本身看「2.文件系统简介」。

版本提醒：素材的结构体跨三个版本层——2.4 的 fs_struct、2.4 的 files_struct，以及一段没标版本、字段拼合过的 struct file。本文三套都写全，逐字段标出现代内核（5.x）的差异。你拿着 2.4 的 struct dentry *root 去 5.x 源码里搜，是搜不到的。

一、一个进程要访问文件，需要记住哪几件事 #

task_struct 是进程的身份证，current 宏拿到当前跑着的那个。它在文件系统这块只挂两个指针——struct fs_struct *fs; 和 struct files_struct *files;。

fs 管路径的坐标系：我站在哪个目录、根在哪、建文件时默认扣掉哪些权限位。它跟「打开」无关，只跟「找名字」有关。files 管已经打开的东西：哪些文件被打开了、每个打开实例读到第几个字节、哪些 fd 会在 exec 时被关掉。

层 结构 生命周期 一句话
路径上下文 fs_struct 跟进程同生共死，线程间可共享 我在文件系统树的哪儿
打开文件表 files_struct → fdtable → fd 数组 跟进程同生共死，线程间可共享 我手里有哪些打开的文件
打开实例 struct file 引用计数归零才释放，可跨进程共享 这一次打开的具体状态
文件本体 inode + dentry 由 dcache/inode 缓存管，跟进程无关 磁盘上那个东西

边界分清楚，后面很多现象就顺了：dup() 复制的是 fd 号不是 struct file；两次 open() 同一路径得到两个 struct file，两个独立偏移；fork() 子进程拿到新 fd 表，但表里每项还指着同一个 struct file。内核里没有「系统打开文件表」这种全局表，打开文件是纯 per-process 的，全局只维护一个文件对象计数（fs.file-nr）。教科书说的「系统打开文件表」在源码里找不到对应结构，以源码为准。

二、fs_struct：进程与文件系统树的绑定点 #

素材给的 2.4 定义，逐行都有用：

c
/* include/linux/fs_struct.h, Linux 2.4 */
struct fs_struct {
    atomic_t count;                  /* 共享本结构的进程数 */
    rwlock_t lock;                   /* 保护下面所有字段 */
    int umask;                       /* umask() 系统调用写这里 */
    struct dentry *root, *pwd, *altroot;
    struct vfsmount *rootmnt, *pwdmnt, *altrootmnt;
};

注意 2.4 里目录和挂载点是分开两个字段存的。root 是 dentry 指针，rootmnt 是 vfsmount 指针，凑成一条完整路径必须两个都在手。这种「dentry + vfsmount 成对出现」的写法后来被打包成一个结构体。现代内核（5.x）：

c
/* include/linux/fs_struct.h */
struct fs_struct {
    int users;
    spinlock_t lock;
    seqcount_spinlock_t seq;
    int umask;
    int in_exec;
    struct path root, pwd;
} __randomize_layout;

/* include/linux/path.h */
struct path {
    struct vfsmount *mnt;
    struct dentry *dentry;
} __randomize_layout;
2.4 字段 现代（5.x） 差异说明
atomic_t count int users 改名。语义没变：共享同一个 fs_struct 的任务数
rwlock_t lock spinlock_t lock + seqcount_spinlock_t seq 读写锁换成自旋锁加顺序锁。读侧走 seqlock 不加锁，写侧（chdir/chroot/umask）加自旋锁
int umask int umask 没变
—— int in_exec 新增。exec 过程中标记「正在换 fs」，配合 unshare_fs 用
struct dentry *root struct path root dentry 和 vfsmount 合进 path
struct vfsmount *rootmnt 并入 root.mnt 字段消失
struct dentry *pwd struct path pwd 同上
struct vfsmount *pwdmnt 并入 pwd.mnt 字段消失
struct dentry *altroot 已删除 见下一节
struct vfsmount *altrootmnt 已删除 同上

__randomize_layout 是结构体布局随机化（CONFIG_RANDSTRUCT），跟语义无关，但会让按固定偏移在内存里找字段的调试手法失效。两个改名值得单记：count → users，rwlock_t → spinlock_t + seqcount。前者搜 fs->count 一无所获，后者让你在 5.x 里找不到 read_lock(&fs->lock)。

共享 fs_struct 靠 CLONE_FS。fork() 不带这个标志，子进程走 copy_fs() 复制一份；带 CLONE_FS 就 count++ 指向同一个。pthread_create() 建线程时带 CLONE_FS，所以一个线程 chdir("/tmp")，同进程所有线程的当前目录一起变——不是 bug，是共享结构的必然结果。

三、root、pwd 与 altroot 分别用在什么场景 #

字段 语义 谁在用 现代内核
root 根目录，绝对路径解析的起点，.. 走到这里停 chroot() 改它、路径解析用它、/proc/pid/root 读它 保留，类型变 struct path
pwd 当前工作目录，相对路径解析的起点 chdir() 改它、getcwd() 从它往上拼、/proc/pid/cwd 读它 保留，类型变 struct path
altroot 2.4 里给 .. 用的第二个根（AltRoot） 极少数场景，实际用处很小 已删除

cd /var/log 改的是 pwd；之后 cat syslog 走相对路径，从 pwd 开始；cat /var/log/syslog 走绝对路径，从 root 开始。

/ 打头一律从 fs->root 起步，其余从 fs->pwd 起步（*at 系列从 dirfd 指定目录起步，dirfd 为 AT_FDCWD 时同样落到 fs->pwd）。规则写在 fs/namei.c 的 path_init() 里，路径解析第一件事就是把 fs->root / fs->pwd 拷进 nameidata，之后所有 walk 基于这份快照。

altroot 在 2.4 之后被删了。它当初的设想是给「换一个 .. 的解析根」留后门，实际没派上用场。具体删除版本号未验证，只知道 2.6 早期还在、5.x 一定没有。getcwd() 反过来依赖 root 和 pwd：从 fs->pwd 的 dentry 起步，用 d_parent 一路往上走到 fs->root，把每级名字塞进 buffer 再倒过来。所以 pwd 一旦异常（比如被 chdir 进一个已 rmdir 的目录），getcwd() 不会失败，而是会拼出一条带 (deleted) 或干脆是 / 的路径。

四、umask：为什么它是个「减法」 #

umask 存在 fs_struct 里，不在 files_struct，也不在 inode 上。这个位置说明了作用域：per-process（线程间共享），跟具体文件无关。系统调用 SYSCALL_DEFINE1(umask)（fs/open.c）只做一件事：xchg(&current->fs->umask, mask & S_IRWXUGO)，把 mask & 0777 换进去，返回旧值。不加锁——单个 int 的写是原子的，冒这点风险换掉一次锁开销。现代内核里 fs->lock 只护 chdir/chroot 这种成对改 root/pwd 的操作。它在创建路径上是减法：mode & ~umask。内核侧对应 vfs_prepare_mode()，传入的 mask 就是 current_umask()：

c
static inline umode_t vfs_prepare_mode(struct user_namespace *mnt_userns,
                                       struct inode *inode, umode_t mode,
                                       umode_t mask)
{
    mode = (mode & S_IALLUGO) | (inode->i_mode & S_IFMT);
    return mode & ~mask;
}

所以 open(..., 0666) 拿到的不是 0666：

umask 普通文件（请求 0666） 目录（请求 0777） 典型场景
022 0644 0755 默认，多数发行版
002 0664 0775 多人协作目录
077 0600 0700 私有
027 0640 0750 组可读、外人无权限

三个要点。只在创建时生效：chmod 完全不受影响，open() 打开已存在的文件也不受影响，umask 只出现在 open(O_CREAT)、mkdir()、mknod()、creat() 这些会新建 inode 的路径上。它是进程状态，不是 shell 状态：umask 022 是 shell 内建命令，改的是 shell 自己的 fs->umask，然后被 fork+exec 继承，父 shell 设的值影响所有子进程，子进程里改不影响父进程。线程间共享：fs_struct 带 CLONE_FS，一个线程改 umask，整个进程一起变，「process」在这里等于「共享 fs_struct 的那组线程」。

fork() 时 copy_fs() 连 umask 一起复制，exec() 不清 fs_struct，所以 umask 一路继承。这就解释了为什么 cron 里跑出来的文件权限经常跟交互式 shell 里不一样——取决于 crond 怎么起的。

五、files_struct：打开文件表的容器 #

素材给的 2.4 定义：

c
/* include/linux/sched.h, Linux 2.4 */
struct files_struct {
    atomic_t count;              /* 共享本表的进程数 */
    rwlock_t file_lock;          /* 保护下面所有字段 */
    int max_fds;                 /* fd 数组当前容量 */
    int max_fdset;               /* 位图容量，单位 bit */
    int next_fd;                 /* 下一个候选 fd，加速分配 */
    fd_set *close_on_exec;       /* CLOEXEC 位图 */
    fd_set *open_fds;            /* 已打开位图 */
    struct file **fd;            /* 指向动态 fd 数组 */
    struct file *fd_array[32];   /* 内嵌的初始 fd 数组 */
};

现代定义换了一层间接：

c
/* include/linux/fdtable.h, Linux 5.x */
struct files_struct {
    atomic_t count;
    bool resize_in_progress;             /* 扩容进行中，防并发扩容 */
    wait_queue_head_t resize_wait;       /* 等扩容结束的队列 */
    struct fdtable __rcu *fdt;           /* 当前生效的 fd 表 */
    struct fdtable fdtab;                /* 内嵌的初始 fd 表 */
    spinlock_t file_lock ____cacheline_aligned_in_smp;
    unsigned int next_fd;
    unsigned long close_on_exec_init[1]; /* 内嵌位图，容量 1 个 long */
    unsigned long open_fds_init[1];
    unsigned long full_fds_bits_init[1];
    struct file __rcu *fd_array[NR_OPEN_DEFAULT];
};

struct fdtable {
    unsigned int max_fds;
    struct file __rcu **fd;       /* 当前 fd 数组 */
    unsigned long *close_on_exec;
    unsigned long *open_fds;
    unsigned long *full_fds_bits; /* 按 64 位一组标记「这组全满」 */
    struct rcu_head rcu;
};

NR_OPEN_DEFAULT 是 BITS_PER_LONG——64 位机器上为 64，2.4 时代硬编码 32。这个数决定「小进程永不 malloc」的边界。

关注点 2.4 5.x
整体形态 一个大结构装齐所有字段 files_struct 常驻 + fdtable 可整体替换
fd 数组 struct file **fd 直接挂 files_struct fdtable.fd，fdtable 可整体换掉
容量字段 max_fds 与 max_fdset 分开管数组和位图 合并成 fdtable.max_fds
扩容锁 rwlock_t file_lock spinlock_t + resize_in_progress + resize_wait
释放 直接 kfree call_rcu，靠 RCU 让读侧无锁
内嵌位图 无，初始就 malloc open_fds_init/close_on_exec_init 内嵌，不 malloc

count 语义跟 fs_struct 一样：多少个任务共享这张表。CLONE_FILES 决定它是不是 1。fork() 之后 count 是 1（表复制了），pthread_create() 之后也是 1（表被共享，count++ 但被多任务引用）。

六、fd 数组与 struct file #

fd 是个小整数，从 0 开始连续分配。它唯一的作用就是数组下标——这是全篇最该记住的一句。fd 不是文件，不是 inode，不是句柄对象，就是个索引。fd[fd] 拿到 struct file *，就这么一步。分配逻辑（现代内核 fs/file.c）：

c
static int alloc_fd(unsigned start, unsigned end, unsigned flags)
{
    fd = find_next_fd(fdt, start);          /* 从 next_fd 开始扫 open_fds 位图 */
    if (fd < end) { /* 有空位，直接用 */ }
    error = expand_files(files, fd);        /* 不够就翻倍，受 nr_open 卡 -EMFILE */
    if (flags & O_CLOEXEC) __set_close_on_exec(fd, fdt);
    else                   __clear_close_on_exec(fd, fdt);
    __set_open_fd(fd, fdt);
    if (start == 0) files->next_fd = fd + 1; /* 只是缓存，真相在位图里 */
    return fd;
}

next_fd 记住「上次分配到的下一个位置」，下次从这儿开始找空位，避免每次从 0 扫。它只是缓存，不是真相——真相永远在 open_fds 位图里。所以「next_fd 没更新就会漏 fd」这种担心不成立。扩容走翻倍：fd_array[64] 内嵌档不够，就 kmalloc(128 * 8) 拷贝旧内容、RCU 释放旧的，仍不够翻到 256、512…… 一直到 RLIMIT_NOFILE 或 fs.nr_open 卡住。

full_fds_bits 是 5.x 加的优化：按 64 个 fd 一组，整组满就在这个位图上标记，find_next_fd 直接跳过整组。几万 fd 的进程分配时这个优化很实在。0/1/2 是约定不是内核强制，但 shell 会替你铺好：

fd 名字 谁负责
0 stdin shell，exec 前 dup2 到 0
1 stdout 同上
2 stderr 同上

dup() 和 dup2() 让两个 fd 指向同一个 struct file。ls -l 2>&1 做的事是 dup2(1, 2)——把「1 号 fd 指向的 struct file」也塞到 2 号位置，f_count 从 1 变 2。此后 fd 1 和 fd 2 是同一个 struct file 的两个引用，共享 f_pos、共享 f_flags。>file 2>&1 能生效而 2>&1 >file 不能，根子在这里：前者先把 1 改成文件再复制给 2，后者先把 2 复制成「当时的 1」（还是终端）再改 1。

七、struct file 与 inode：一次打开 vs 一个文件 #

素材给的 struct file（未标版本），先原样保留：

c
struct file {
    struct list_head f_list;
    struct dentry *f_dentry;
    struct vfsmount *f_vfsmnt;
    struct file_operations *f_op;
    mode_t f_mode;
    loff_t f_pos;
    unsigned short f_flags;
    unsigned short f_count;
    int f_owner;
    uid_t f_uid;
    gid_t f_gid;
    unsigned long f_version;
    void *private_data;
};

这段有问题，附录逐条说。2.4 的实际定义：

c
/* include/linux/fs.h, Linux 2.4 */
struct file {
    struct list_head        f_list;      /* 挂到 super_block->s_files */
    struct dentry           *f_dentry;
    struct vfsmount         *f_vfsmnt;
    struct file_operations  *f_op;
    atomic_t                f_count;
    unsigned int            f_flags;
    mode_t                  f_mode;
    int                     f_error;
    loff_t                  f_pos;
    struct fown_struct      f_owner;
    unsigned int            f_uid, f_gid;
    struct file_ra_state    f_ra;
    size_t                  f_maxcount;
    unsigned long           f_version;
    void                    *private_data;
};

现代内核（5.10 一带）：

c
/* include/linux/fs.h */
struct file {
    union {
        struct llist_node   fu_llist;
        struct rcu_head     fu_rcuhead;
    } f_u;
    struct path             f_path;
    struct inode            *f_inode;    /* cached value */
    const struct file_operations *f_op;
    spinlock_t              f_lock;
    atomic_long_t           f_count;
    unsigned int            f_flags;
    fmode_t                 f_mode;
    struct mutex            f_pos_lock;
    loff_t                  f_pos;
    struct fown_struct      f_owner;
    const struct cred       *f_cred;
    struct file_ra_state    f_ra;
    u64                     f_version;
    void                    *f_security;
    void                    *private_data;
    struct list_head        f_ep_links;
    struct address_space    *f_mapping;
    errseq_t                f_wb_err;
} __randomize_layout;
2.4 5.x 说明
f_list f_u（union） 不再挂进 s_files 链表。f_count 归零时用 f_u 里的 llist/rcu_head 做延迟释放
f_dentry + f_vfsmnt f_path 老规矩，两件套打包成 struct path
—— f_inode 新增缓存，省一次 d_inode(f_path.dentry)
f_op f_op 变成 const
f_count（atomic_t） f_count（atomic_long_t） 32 位原子换 64 位，海量 fd 场景不再担心计数溢出
f_flags（unsigned int） f_flags 新版把内部标志存进高位，用户态给的 flags 被重新编码
f_mode（mode_t） f_mode（fmode_t） 语义换成 FMODE_READ/FMODE_WRITE/FMODE_EXEC 等内部位
f_pos f_pos + f_pos_lock 加锁。共享 struct file 的并发读写靠它保护偏移
f_error 已删除 2.6 后没有这个字段
f_owner（struct fown_struct） 同 + f_cred SIGIO 异步通知的接收者；f_cred 是打开那一刻的凭证快照
f_uid / f_gid 已删除 权限判定统一走 f_cred，不再单独存 uid/gid
f_maxcount 已删除 单次读写上限改由别处约束
f_ra / f_version / private_data 保留 预读状态 / NFS 缓存判新旧 / 驱动自用
—— f_mapping 指向 inode 的 address_space，页缓存入口
—— f_security / f_wb_err LSM 挂钩（受 CONFIG_SECURITY 控制）/ 写回错误序列号

「一次打开 vs 一个文件」这个点最容易绕晕：

操作序列 struct file 个数 f_pos 共享
fd1 = open(p); fd2 = open(p); 2 个，各自独立 不共享
fd1 = open(p); fd2 = dup(fd1); 1 个，f_count == 2 共享
fork() 后父子各持 fd1 1 个，f_count == 2 共享
同进程两线程各 open(p) 2 个 不共享 
bash
tail -f /var/log/syslog & tail -f /var/log/syslog &   # 两个进程各读各的，互不影响
exec 3</var/log/syslog && head -c 10 <&3 && cat <&3   # 同一个 file，偏移被两次读共同推走

O_APPEND 是另一回事：它让每次 write() 原子地把位置挪到文件末尾再写，绕过 f_pos。多个进程用 O_APPEND 往同一日志写不会互相覆盖，不带 O_APPEND 的并发写会丢数据——不是因为 f_pos 不共享，是因为它们的 f_pos 根本没在共享。

八、CLONE_FILES：fork 与 exec 时 fd 表的三种命运 #

场景 内核路径 fd 表本身 表里的 struct file f_pos
fork()（不带 CLONE_FILES） copy_files() → dup_fd() 复制一份，完全独立 不复制，只 f_count++ 父子共享
clone(CLONE_FILES) / pthread_create() copy_files() 里 atomic_inc(&oldf->count) 共享同一张，count 加一 同一个 共享
exec() unshare_files() + do_close_on_exec() 先 unshare 成私有（若原为共享），再按位图关 fd 被关的 f_count-- 留下来的继续共享

区别在于表和项是不是同一份：fork() 复制「表」不复制「项」，子进程 close(3) 不影响父进程 fd 3，但 read(3) 会把父进程看到的偏移也推走；CLONE_FILES 连表都不复制，一个线程 close(3)，同进程所有线程的 fd 3 立刻 EBADF，这是线程里共享 fd 表最常踩的坑；exec() 不动表里的项，只清「标了 CLOEXEC 的」，这就是 shell 重定向能延续到 exec 之后的原因。

exec 前先 unshare_files() 的理由：当前 files_struct 若跟别人共享（多线程进程 exec），直接关 CLOEXEC 的 fd 会波及别的线程。先 dup_fd() 出一份私有表再动手：

c
/* fs/exec.c, do_execveat_common() 里 */
retval = unshare_files();

unshare_files() 在 5.x 里带 int *displaced 出参，把「被替换掉的那张表」交回来，调用者负责 put_files_struct()。copy_files() 另有小优化：新进程的表没被共享且是新建的，判断 atomic_read(&oldf->count) == 1 走快速路径。

九、close_on_exec 与 FD_CLOEXEC #

close_on_exec 是一张位图，跟 open_fds 同尺寸，一位一个 fd。2.4 是 fd_set *close_on_exec，5.x 是 close_on_exec_init 内嵌加 fdtable.close_on_exec 指针。

途径 写法 特点
open() 带标志 open(p, O_RDONLY | O_CLOEXEC) 原子。fd 一分配就带位，中间没有窗口
fcntl 事后改 fcntl(fd, F_SETFD, FD_CLOEXEC) 非原子。open 和 fcntl 之间有窗口
fcntl 读 fcntl(fd, F_GETFD) 返回位里 FD_CLOEXEC 就是这一位

FD_CLOEXEC 是用户态位名（值为 1），内核态对应 close_on_exec 位图里的一位。fcntl(F_SETFD) 只认这一位，其余忽略。O_CLOEXEC 存在的唯一理由是堵竞态：

c
int fd = open("/path", O_RDONLY);   /* ← 这里若另一线程 fork+exec，fd 会泄漏到新程序 */
fcntl(fd, F_SETFD, FD_CLOEXEC);

多线程进程里，open 返回和 fcntl 之间是有窗口的。另一线程此刻 fork() 再 exec()，新程序就白捡一个不该有的 fd。O_CLOEXEC 把「分配」和「标记」压进同一个原子操作（alloc_fd() 里直接 __set_close_on_exec），窗口消失。现代代码里 O_CLOEXEC 该是默认动作。

exec 时的清理是遍历位图：对每个 test_bit(i, fdt->close_on_exec) 命中的 fd 调 __close_fd()。代价跟 max_fds 成正比，不是跟实际打开的 fd 数成正比——一个开了几十万 fd 的进程 exec，这一步会有可见开销。函数名 do_close_on_exec 在 fs/file.c、调用点在 fs/exec.c 的 exec 路径上，具体行号未逐一验证。

FD_CLOEXEC 跟 O_APPEND、O_NONBLOCK 不是一类：后两者在 f_flags 里，是「打开实例」的属性；FD_CLOEXEC 在 fd 表里，是「这个槽位」的属性。dup() 出来的新 fd，FD_CLOEXEC 位是清掉的（POSIX 规定 dup 不复制它，要保留得用 dup3/F_DUPFD_CLOEXEC）。这点经常被记错。

十、fd 的上限：RLIMIT_NOFILE 与 file-max #

层次 名字 查/改 默认值 撞上时的错误
全系统文件对象总数 fs.file-max /proc/sys/fs/file-max 按内存算，公式随版本变动，未验证 ENFILE（23）
单进程 fd 号上限 fs.nr_open /proc/sys/fs/nr_open 1048576 EMFILE（24）
单进程软限制 RLIMIT_NOFILE soft ulimit -n、prlimit 内核默认 1024，发行版常调到 65535 以上 EMFILE（24）
单进程硬限制 RLIMIT_NOFILE hard prlimit --nofile 1048576 改软限制超硬限 → EPERM

依赖顺序：RLIMIT_NOFILE 不能超过 fs.nr_open。想把 soft 提到 200 万，得先把 fs.nr_open 提上去，否则 setrlimit 直接 EPERM。

bash
ulimit -n                              # soft
ulimit -Hn                             # hard
cat /proc/sys/fs/file-nr               # 已分配 / 恒 0 / file-max

/proc/sys/fs/file-nr 三列常被搞错：第一列是当前已分配的 struct file 数量，第二列在现代内核里恒为 0（历史遗留，早期是「已分配但未使用」），第三列是 file-max。EMFILE 和 ENFILE 分清楚：前者是「你这个进程 fd 用光了」，后者是「整个系统 struct file 用光了」。前者查 lsof -p，后者查 file-nr。

RLIMIT_NOFILE 同时是单次 select()/poll() 能处理的 fd 上限。老代码里 select(fd + 1, ...) 在 fd 超过 1024 时会静默出错，就是这个原因。epoll 不受这条约束，这也是它取代 select 的原因之一。

十一、从 open() 到拿到一个 fd 的完整链路 #

text
用户态: open("/etc/hosts", O_RDONLY)
  │
  ▼
sys_openat → do_sys_open → do_sys_openat2              fs/open.c
  │
  ├─ getname()                    拷贝用户态路径到内核 buffer
  │
  ├─ get_unused_fd_flags(flags)   先在 fd 表里占一个号    ← fd 先出生
  │     └─ __alloc_fd → alloc_fd
  │           ├─ find_next_fd()   从 next_fd 开始扫 open_fds 位图
  │           ├─ expand_files()   不够就翻倍（受 nr_open 卡 -EMFILE）
  │           └─ O_CLOEXEC 在这里设 close_on_exec 位
  │
  ├─ do_filp_open(dfd, path, &op) → path_openat
  │     ├─ path_init       把 fs->root / fs->pwd 拷进 nameidata
  │     ├─ link_path_walk  逐级 walk_component，查 dcache
  │     ├─ do_last         最后一段，拿 dentry + inode，判权限
  │     └─ vfs_open → do_dentry_open
  │           ├─ alloc_empty_file()  分配 struct file，f_count = 1
  │           ├─ f->f_op = fops_get(inode->i_fop)
  │           └─ f_op->open()        调具体文件系统的 open
  │
  └─ fd_install(fd, f)            把 struct file 写进 fd 数组
        └─ 此时 fd 才真正可见，此前 open_fds 位已置但槽位为空
  1. fd 先分配，struct file 后创建。get_unused_fd_flags() 在 do_filp_open() 之前。路径解析失败时要 put_unused_fd(fd) 把刚占的号还回去，还原动作在 do_sys_openat2() 的错误分支里。
  2. fd_install() 是最后一步。在它之前，即使 open_fds 位已置上，fd[fd] 还是 NULL。所以别的线程在这个窗口里看不到这个 fd——靠的是「位图先置、槽位后填」的顺序，加上 fd_install 里的 WRITE_ONCE 配对 fdget 读侧屏障，不是靠锁。
  3. f_op->open() 是文件系统的入口。到这里 dentry、inode 都已就绪，剩下的具体工作（ext4 分配 inode 块、设备驱动初始化）交给它。

O_PATH 是特例：它跳过 f_op->open()，只拿路径不拿读写能力，f_mode 里没有 FMODE_READ/FMODE_WRITE，这种 fd 只能用于 *at() 当 dirfd、fstat、readlink 这几类操作。

2.4 里没有 do_sys_open 这一层，sys_open() 是个大函数一把梭；do_sys_openat2 要到 5.6 才出现。看老版本源码别照现在的调用树去找。

十二、路径解析为什么需要 fs_struct #

路径解析入口在 fs/namei.c，第一件事就是把「坐标系」从 fs_struct 拷出来：

c
/* fs/namei.c, path_init() 一带（5.x） */
if (*s == '/') {
    nd->path = nd->root;    /* 绝对路径：从 fs->root 起步 */
} else {
    nd->path = nd->pwd;     /* 相对路径：从 fs->pwd 起步 */
}

为什么要走快照：解析过程中会睡眠（等 IO、等锁），醒来后 current 指向的任务换过，root/pwd 也会被 chdir 改，快照保证整条解析走同一套坐标系。另外 openat(dirfd, "x", ...) 的相对路径从 dirfd 指向的目录起步，nd->path 来自文件表，但 nd->root 仍来自 fs_struct——因为 .. 爬到根还得停。

.. 的终止条件就挂在 fs_struct->root 上。follow_dotdot() 判断：当前已在 nd->root 上时，.. 原地不动，不再往上。所以 chroot /srv/jail /bin/sh 之后 cd / 落在 /srv/jail，再 cd .. 还是 /srv/jail，出不去。

跨挂载点也靠同一套机制。path 是 {vfsmount, dentry} 两件套，走 .. 时要判断「这一级 dentry 是不是某个挂载点的根」，是的话先 follow_down/follow_up 跳到父挂载。这就是 2.4 里 rootmnt/pwdmnt 必须跟 root/pwd 成对存在的原因——只拿 dentry 无法判断跨没跨挂载点。现代内核打包成 struct path 是必然结果。

十三、chroot、pivot_root 与 mount namespace 的关系 #

机制 改的是什么 需要权限 影响范围 能逃逸吗
chroot() current->fs->root 和 fs->pwd CAP_SYS_CHROOT 只影响调用者自己的 fs_struct（CLONE_FS 的话连同组线程） 能。持有旧 root 的 fd 就能 fchdir 出去
pivot_root() 把当前 mount namespace 的根挂载换成新挂载 CAP_SYS_ADMIN 整个 mount namespace 要配合 mount ns 才有意义
unshare(CLONE_NEWNS) 复制一份 mount namespace CAP_SYS_ADMIN 调用者之后的所有挂载操作 ——

chroot() 的实体只有两行：

c
/* fs/open.c */
set_fs_root(current->fs, &path);
set_fs_pwd(current->fs, &path);

就改 fs_struct 两个字段，不动 mount 表，不动任何全局结构。所以 chroot 之前 open("/", O_PATH) 留一个 fd，之后 fchdir(fd) 再 chdir("..") 就出来了。这不是漏洞，是 chroot 从来没打算当安全边界。想真隔离，得 chroot + 丢权限 + 清 fd，或者直接上 mount namespace + pivot_root。后者的典型姿态是 initramfs 交接：mount /dev/sda1 /newroot、mkdir -p /newroot/oldroot、pivot_root /newroot /newroot/oldroot、exec chroot . /sbin/init（switch_root 是 busybox 的封装）。

跟 fs_struct 的关系要说清：即使有 mount namespace，fs->root 仍然是 per-task 的。两个任务在同一 mount namespace 里，可以有不同 fs->root（一个 chroot 了一个没有）。mount namespace 隔离的是「我能看见哪些挂载」，fs_struct 决定的是「我这条路径从哪儿起步」。两者正交。容器运行时把这个组合用满：新建 mount namespace、pivot_root 到镜像根、丢 CAP_SYS_CHROOT、清掉继承的 fd。少做一步都会被逃。

十四、/proc/pid/fd 与 lsof 看到的是什么 #

/proc/<pid>/fd/ 下每个 fd 是一个符号链接，内容就是那个 struct file 反查出来的路径（ls -l /proc/self/fd 能看到 0 -> /dev/pts/0 这类结果）。

显示 含义
/path/to/file 普通文件，从 f_path 反推的路径
/path (deleted) 文件已 unlink，但还有 fd 引用 inode，空间没释放
pipe:[12345] 管道，方括号里是 pipe inode 编号
socket:[67890] socket，编号对应 /proc/net/* 里的 inode
anon_inode:[eventfd] eventfd/timerfd/signalfd 这类匿名 inode
/memfd:name (deleted) memfd_create() 创建的匿名内存文件

/proc/<pid>/fdinfo/<fd> 给打开实例的细节，四个字段：pos（就是 f_pos）、flags（f_flags 的八进制）、mnt_id（对应 /proc/pid/mountinfo，判断是否同一挂载）、ino。其中 pos 是所有共享这个 struct file 的 fd 共用的那一个值，所以 fork 出来的子进程 /proc/child/fdinfo/3 和 /proc/parent/fdinfo/3 看到的 pos 永远一致。

路径 指向 对应 fs_struct 字段
/proc/<pid>/cwd 当前工作目录 pwd
/proc/<pid>/root 进程的根 root
/proc/<pid>/exe 可执行文件 跟 fs 无关，来自 mm

lsof 做同一件事，把 /proc/*/fd、/proc/*/maps、/proc/*/cwd、/proc/*/root 全扫一遍再拼成表。所以 lsof 慢、要 root（读别人的 /proc/<pid>/fd 要 ptrace 级别权限）、看到的路径未必是打开时的路径（拿的是当前反查结果）。

bash
lsof +D /var/log               # 慢，遍历目录再比对
lsof -p 1234                   # 单进程
fuser -v /var/log/syslog       # 轻量版
ls -l /proc/1234/fd | awk '{print $NF}' | sed 's/[0-9]\+//g' | sort | uniq -c | sort -rn

最后一行是查 fd 泄漏最快的一招：按类型数分布，pipe: 或 socket: 某一类数字疯涨，方向就定了。

十五、易错点速查 #

坑 真相
「fd 是文件句柄」 fd 只是数组下标。struct file 才是打开实例，dup 之后变成多对一
「fork 后子进程拿到文件副本」 表复制了，struct file 没复制。父子共享 f_pos，这是「日志串行错乱」的根因
「close(fd) 就释放了文件」 只是 f_count--。别处还有引用（dup、fork、SCM_RIGHTS 传递）时 inode 和磁盘空间都不放
「unlink 后空间立刻回收」 有 fd 开着就不放。df 满了但 du 对不上，先查 lsof +L1
「FD_CLOEXEC 是文件属性」 是 fd 槽位的属性，在 fd 表的位图里，不在 struct file 里
「dup 会继承 FD_CLOEXEC」 不会。POSIX 规定清掉，要保留得用 F_DUPFD_CLOEXEC
「umask 影响 chmod」 不影响。umask 只在新建 inode 时做减法
「chroot 是安全边界」 不是。拿着旧 root 的 fd 就能出去。要隔离得配 mount ns 加丢权限
「RLIMIT_NOFILE 改到多大都行」 受 fs.nr_open 卡，超了 setrlimit 直接 EPERM
「EMFILE 和 ENFILE 是一回事」 前者进程级 fd 用光，后者系统级 struct file 用光。修法完全不同
「线程和进程的 fd 表是分开的」 CLONE_FILES 一下就是同一张。一个线程 close，全进程跟着 EBADF
「/proc/pid/fd/N 里的路径就是打开时的路径」 是现在反查出来的。文件被 rename 过，这里显示新名字
「2.4 的 fs_struct 能直接对着 5.x 读」 不能。root/pwd 已从裸 dentry* 变成 struct path，altroot 没了，count 改名 users
「2.4 的 f_dentry+f_vfsmnt 在 5.x 里还在」 合并成 f_path。f_count 从 atomic_t 变 atomic_long_t，f_uid/f_gid 没了

② 修正的错误 #

  1. fd_set 不是「指向打开文件描述符的指针数组」。原文第 45 行把 fd_set 说成指针数组、长度为 32。fd_set 是位图类型（unsigned long 数组），指针数组是 struct file **fd 或内嵌 fd_array[32]。原文把两个字段混成一个。
  2. 32 不是 fd_set 的长度。32 是 NR_OPEN_DEFAULT 在 2.4 的取值，指内嵌 fd 数组槽数。5.x 里 NR_OPEN_DEFAULT 是 BITS_PER_LONG（64 位机器上 64）。
  3. open_fds 位数不由「1024」决定。原文说位数取决于 max_fdset，位图「包含 1024 位」——前半句对、后半句误导。1024 是 __FD_SETSIZE，只是 2.4 的初始值，max_fdset 会随需求翻倍扩张，上限受 RLIMIT_NOFILE 与 fs.nr_open 约束。现代内核里 max_fdset 已并入 fdtable.max_fds。
  4. f_list 不是「指向所有已打开文件的链表」。它是 struct list_head 节点，2.4 里挂进 super_block->s_files，作用域是单个文件系统而非全局；5.x 里已换成 f_u union，用途变成延迟释放。内核从来就没有一张「所有打开文件」的链表。
  5. 素材的 struct file 字段与 2.4 实际定义不符。原文第 55–71 行标「在 include/linux/fs.h 中定义」但没给版本：f_count 写成 unsigned short（2.4 是 atomic_t，5.x 是 atomic_long_t）；f_owner 写成 int（2.4 起是 struct fown_struct）；f_flags 写成 unsigned short（2.4 是 unsigned int，高位标志塞不进 16 位）；缺 f_error、f_ra、f_maxcount 三个 2.4 实有字段；顺序也与 2.4 实际定义不同。
  6. fs_struct 没标版本差异会误导。原文给的定义本身是准确的 2.4 版，但通篇没提「现代内核 root/pwd 已是 struct path」。照原文去 5.x 源码找 struct dentry *root，找不到。
  7. 「前 3 个文件描述符」的因果反了。原文说它们「用作标准输入、标准输出和标准错误」——0/1/2 是用户态约定，由 shell 在 exec 前 dup2 铺好，内核不强制。进程完全可以一启动就 close(0)，也可以让 fd 0 指向一个 socket。
