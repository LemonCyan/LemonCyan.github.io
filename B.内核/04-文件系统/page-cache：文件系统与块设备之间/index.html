一、页缓存与块缓存：从两套缓存到一套 #

3.18 里只有一套缓存。文件的数据页挂在文件 inode 的 address_space 上，块设备的数据页挂在 bd_inode 的 address_space 上，buffer_head 退化成挂在 page 上的附属结构，自己不再持有数据。

再往前是两套。buffer cache 按「设备号 + 块号」索引，page cache 按「inode + 页号」索引。同一份磁盘数据在内存里存两份，读一次拷两遍，改一处还得同步另一处。合并发生在 2.4/2.5 开发期（具体版本未验证），做法就是让 buffer_head 指向 page，而不是自己分配一块内存。

维度 块缓存（buffer cache） 页缓存（page cache）
索引 key 设备号 + 块号（sector_t） address_space + 页号（pgoff_t）
归属对象 block_device 的 bd_inode 文件 inode
数据实体 早期是独立内存块 struct page
3.18 的形态 已并入页缓存，只剩 bh 描述「块 ↔ 页」 唯一的数据缓存
分配入口 文件系统/块层经 __getblk 一类接口 read / write / 缺页路径
回写方式 随所属 page 一起回写 writeback 线程 + a_ops->writepages

表里「3.18 的形态」那行是本文立足点。合并之后，按块号找块这件事没变，但底层变成「先把块号换算成页号，再去块设备的 address_space 里找 page」。等下在第十四节看到 __find_get_block_slow() 时，注意它开头那行 index = block >> (PAGE_CACHE_SHIFT - bd_inode->i_blkbits);，就是这个换算。

二、address_space：一个文件在内存里的映射视图 #

一次 read() 走到底，最核心的对象是 struct address_space。它不是缓存本身，是缓存的容器：一棵按页号索引的树，加上一套操作函数表。每个 inode 有一个，块设备的 inode 也有一个。

字段 3.18 中的含义 用在哪
host struct inode * 反指拥有者，读取路径靠它拿 i_size
page_tree struct radix_tree_root 存本 mapping 所有 page，key = 页号
tree_lock spinlock_t 保护树的插入、查找、打 tag
nrpages unsigned long 当前缓存了多少页
a_ops struct address_space_operations * readpage / readpages / writepages / write_begin / direct_IO 从这里分发
i_mmap 区间树 映射了这些 page 的 VMA，mmap 相关
private_lock / private_list spinlock / list_head buffer_head 的挂靠链表
backing_dev_info 回写队列归属 writeback 线程按它排队

page_tree 是理解全文的钥匙。一个文件在内存里长什么样，就是这棵树长什么样。文件多大、读到哪、哪些页是脏的，全在树上。

现代内核这块改了名字：page_tree 换成 i_pages，类型是 struct xarray。注释里经常还能看到「radix tree」的残留说法，别被绕晕。backing_dev_info 在 4.2 之后的 per-memcg writeback 里也有调整（字段名未验证）。

三、mapping 与 host：address_space 属于谁 #

do_generic_file_read() 开头两行就把这层关系摆明了：

c
struct address_space *mapping = filp->f_mapping;
struct inode *inode = mapping->host;

第一行：从打开的文件拿到 mapping。f_mapping 在 open() 时挂上去，普通文件就指向 inode->i_mapping，正常情况下就是 inode 自己那个。

第二行：从 mapping 反查 inode。注意这里的依赖关系是单向的，mapping 里存了 host 指针，所以只凭一个 mapping 就能找到 inode、拿到 i_size、拿到 i_blocks。

块设备走的是另一条入口。没有 struct file 打开某个文件，而是打开 /dev/sda2，拿到的是 struct block_device，它的 inode 叫 bd_inode，bd_inode->i_mapping 就是块设备自己的 address_space。素材第二段代码开头正是这么写的：

c
struct inode *bd_inode = bdev->bd_inode;
struct address_space *bd_mapping = bd_inode->i_mapping;

于是同一块硬盘上，一份数据会同时挂在两棵树里：文件树里它是「read.c 的第 0 页」，设备树里它是「sda2 的第 2681460 块所在的页」。两棵树互不知道对方存在。

四、radix tree / xarray：页在文件内的索引 #

树是稀疏数组，不是红黑树。key 是页号，pgoff_t，无符号长整型。查一个页号就是按位往下走，层数随最大页号增长，几十 G 的文件也就多几层。

3.18 用的 radix tree 每个节点固定槽位数，靠 RADIX_TREE_MAP_SHIFT 决定分支因子。现代内核换成 xarray，接口从「insert / delete」变成「load / store」，address_space 里的字段也随之改名成 i_pages。转换合入在 4.20，patchset 作者是 Matthew Wilcox，LWN 上有原文。

树上有 tag，用来快速捞出某一类页：

tag 含义 谁打
PAGECACHE_TAG_DIRTY 页内容已被改，磁盘上是旧的 写路径、mmap 脏页处理
PAGECACHE_TAG_WRITEBACK 正在回写 writeback 线程
PAGECACHE_TAG_TOWRITE 回写扫描时标记本轮目标 writeback 线程

查找一个页不需要遍历链表，直接 find_get_page(mapping, index)。这也是这套结构比早期「哈希表 + LRU 链表」强的地方：既要按页号随机命中，又要能顺序扫描，一棵树全办了。

六、第一步：算 index、offset、last_index #

对应源码的第 2 段，五行全是位运算：

c
index = *ppos >> PAGE_CACHE_SHIFT;
prev_index = ra->prev_pos >> PAGE_CACHE_SHIFT;
prev_offset = ra->prev_pos & (PAGE_CACHE_SIZE-1);
last_index = (*ppos + iter->count + PAGE_CACHE_SIZE-1) >> PAGE_CACHE_SHIFT;
offset = *ppos & ~PAGE_CACHE_MASK;

index 是本次读的起始页号，offset 是页内偏移，last_index 是本次读要覆盖的最后一页的下一页。拿个具体数走一遍：页大小 4096，*ppos = 5000，iter->count = 8192。

表达式 结果 含义
5000 >> 12 1 从第 1 页开始
5000 & 4095 904 第 1 页内偏移 904
(5000 + 8192 + 4095) >> 12 4 循环要在 index 到 4 之前停下
实际覆盖 页 1、2、3 字节 5000~13191

offset = *ppos & ~PAGE_CACHE_MASK; 这一行容易被当成笔误，看着像「与上掩码的反」。其实 PAGE_CACHE_MASK 就是 PAGE_MASK，等于 ~(PAGE_SIZE-1)，再取反正好是页内偏移掩码 PAGE_SIZE-1。写惯了 & (PAGE_SIZE-1) 再看这行会愣一下，实际等价。

prev_index / prev_offset 来自 ra->prev_pos，是上一次读结束的位置。这两个值不参与寻址，只喂给预读算法：判断这次读是不是接着上次往后走。顺序读、随机读、倒着读，预读窗口大小完全不一样。ra->prev_pos 在函数末尾更新，落在素材省略的第 5 段里，原文未给出该段实现。

七、第二次读同一个文件：缓存的命中路径 #

对应源码的第 4 段。这里是整个函数最热的地方：

c
find_page:
        page = find_get_page(mapping, index);
        if (!page) {
            page_cache_sync_readahead(mapping,
                    ra, filp,
                    index, last_index - index);
            page = find_get_page(mapping, index);
            if (unlikely(page == NULL))
                goto no_cached_page;
        }

只有三条路：

情况 走法 开销
页在树里 find_get_page 直接返回，跳过整个 if 一次树查找，纳秒级
页不在，预读把它捞回来 同步预读发起 IO，回来后再查一次，命中 一次磁盘 IO，但要等
页不在，重查还不在 goto no_cached_page，走单页回填 锁 page、readpage、再判断

第二次读同一个文件，走的是第一行。文件内容已经在 page_tree 里，find_get_page 命中，if (!page) 不成立，page_cache_sync_readahead() 根本不会被调用。预读只在缓存缺失时才启动，它不是每次读都跑。

这也解释了 vmtouch 那个 100% 的意义。vmtouch 干的事就是遍历文件每一页、mincore() 一遍，告诉你哪些页已经在 cache 里。100% 意味着下面每次 read() 都走第一条路。

第三条路的 no_cached_page 分支在素材省略的第 5 段里。语义上是「分配一个新 page、加锁、调 a_ops->readpage() 从磁盘读、等 PG_uptodate」，原文未给出该分支实现，我不补代码。

八、find_get_page 与 page 的引用计数 #

find_get_page() 返回的 page 带着一个引用。拿到就得还，put_page()。这点在循环里尤其要紧：每轮 find_page: 都会重新拿一次，用完必须放，否则 page 永远回收不掉。

返回 NULL 的含义很干净：这个页号不在 mapping 的树里。不是「IO 失败」，也不是「页被锁着」，就是没有。

为什么明明刚查过一次，page_cache_sync_readahead() 之后还要再查一次？因为预读会睡眠。睡着的时候别的路径能把这个页加进来，也能把刚加进来的页又回收掉。所以醒来必须重查，不能拿旧结论继续。

围绕一个 page 有几个状态位在转，别混：

状态 含义 谁设
引用计数 _refcount 有多少人在用，0 才可回收 find_get_page 加一，put_page 减一
PG_locked 正在被某人独占，别人睡等 lock_page / unlock_page
PG_uptodate 页内容与磁盘一致，可以直接用 读盘完成后由 SetPageUptodate
PG_dirty 内容改过，磁盘是旧的 写路径、mmap

三个位管三件事：引用计数管生命周期，PG_locked 管并发，PG_uptodate 管内容对不对。看到一页缓存页，先问自己它在哪个状态上。

find_get_page() 自身的实现，原文未给出。行为上就是「在 mapping->page_tree 里按 index 查，查到就把引用计数加一返回」。

九、缺页与预读：page_cache_sync_readahead #

page_cache_sync_readahead(mapping, ra, filp, index, last_index - index) 五个参数：缓存归属、预读状态、文件、起始页号、本次要多少页。

「同步」的意思是这次读必须等。它从 index 起按预读窗口发起一批 IO，然后阻塞到 index 这一页可用为止。名字里的 sync 对着的是另一个 page_cache_async_readahead()，后者在命中 PG_readahead 标记时触发，只发起 IO 不等待。

预读窗口大小由 struct file_ra_state 决定。字段大致是 start、size、async_size、ra_pages、mmap_miss、prev_pos。ra_pages 上限来自块设备的 bdi->ra_pages，也就是 read_ahead_kb 那个 sysfs 旋钮。顺序读会把 size 翻倍往上顶，随机读会把它拍回初始值，倒着读直接把窗口打回 0。

这里容易以为预读是 mm 那边的事，其实 read 和缺页共用一套：filemap_fault() 撞到页不在，也走同一套预读逻辑，只是入口函数不同。两个路径最后都落到「发起 readpages、等 uptodate」。

page_cache_sync_readahead() 的具体实现，原文未给出。素材里只出现调用点。

十、拷贝到用户态：从 page 到 iov_iter #

数据读进 page 之后，还得搬到用户的 buffer 里。3.18 里这个动作是 copy_page_to_iter()，参数是 page、页内偏移、长度、iov_iter。用户 buffer 能跨好几个 iovec，iov_iter 负责把「散」的用户空间拼起来，内核只管按页喂。

这段落在素材省略的第 5 段，原文未给出代码，只讲三个要点。

第一个是长度。拷贝多少字节由 PAGE_SIZE - offset 和剩余请求量取小，nr 就这么来的。

第二个是文件尾。最后一页往往没填满，i_size 之后的部分是零。直接拷整页会把内核页的残留数据漏给用户，所以要用 i_size 算 end_index，对最后一页单独截断。这也是 end_index 和 isize 两个局部变量在循环里出现的原因。

第三个是失败。copy_page_to_iter() 返回的实际拷贝字节数会小于 nr，用户 buffer 不合法时返回 0 或者错误。这时要扣掉已拷贝的量、置 error，然后跳出循环，不能当作全成功。

拷贝本身会睡眠（用户页不在内存里时触发缺页）。所以拷贝完不能假设 page 还在原地，这也是循环里每轮重查的原因。

iov_iter 的内部布局在后续版本改过多轮（3.19 之后把 iocb 从 iter 里拆出去，再往后字段又有调整），具体到哪个版本改了哪个字段，未验证。

十一、一块页缓存怎么被标记为脏 #

页缓存变脏只有一条路：有人往 page 里写了数据。入口分两大类。

走 write() / writev() 的缓冲写：文件系统提供 write_begin / write_end，中间用 copy_from_user 把用户数据抄进 page，然后在 write_end 里调 set_page_dirty()。

走 mmap 的写：CPU 直接写内存，第一次写触发缺页，page_mkwrite 把页变成可写，同时标脏。后面的写就是纯内存操作，内核靠页表上的 dirty 位在 msync / 回写扫描时把它捡回来。

两条路最后都落到同一处：在 mapping->page_tree 上给这个页号打 PAGECACHE_TAG_DIRTY 标记，并递增 inode 的脏页计数。

3.18 里还有一层 buffer_head。一个 page 的每个块对应一个 bh，bh 有自己的 dirty 位。页级的脏标记和 bh 的脏标记要配合，回写时按 bh 逐块下发，一套页缓存要伺候多个块大小，就靠这一层。等文件系统只用一个块大小、走 writepages 大块回写时，bh 这层基本被绕过。

脏页不能无限攒。balance_dirty_pages() 会按比例卡住写者：脏页超过 dirty_ratio 就阻塞，超过 dirty_background_ratio 就只唤醒回写线程。这两个值在 /proc/sys/vm/ 下可调。

十二、回写：从脏页到 bio 到块设备 #

回写是异步的。write() 返回只保证数据进了页缓存，不保证进了磁盘。链条大致这么走：

步骤 动作 归属
1 页被标脏，打 PAGECACHE_TAG_DIRTY 写路径
2 脏页超阈值，唤醒 flusher balance_dirty_pages()
3 flusher 扫描脏 inode，按 wb 排队 3.18 是 per-bdi 内核线程 bdi_writeback
4 对每个 inode 调 do_writepages() VFS
5 分发到 mapping->a_ops->writepages() 文件系统，ext4 是 ext4_writepages()（本篇素材未涉及，未验证）
6 文件系统查块映射，组 bio ext4 extent 树
7 submit_bio() 交给块层 块层
8 设备完成，清 PG_writeback，清脏标记 中断/软中断

fsync() 是另一条路，同步的：filemap_write_and_wait_range() 把指定范围刷下去，然后等。它比 write() 贵得多，因为要真的等盘。

这里有个和后面实验直接相关的细节：/proc/sys/vm/drop_caches 只回收干净页。脏页不会被丢，丢了就是数据丢失。所以「drop cache」这个动作对脏页无效，脏页只能等回写。

3.18 的回写线程是 per-bdi 的，5.x 之后按 memcg 拆成 per-wb，一个设备上会有多个回写队列。结构变了，路径没变。

十三、直接 IO 为什么绕开页缓存 #

O_DIRECT 打开的文件，读写不进页缓存。数据在用户 buffer 和磁盘之间直接搬，只在中间组 bio。

generic_file_read_iter() 顶上就分了叉：看到 O_DIRECT 标志，直接调 a_ops->direct_IO()，根本不进 do_generic_file_read()。所以本文前面讲的 find_get_page、预读、拷贝到用户态，直接 IO 一条都不走。

维度 缓冲 IO 直接 IO
走不走 page cache 走，数据先落页缓存 不走，用户 buffer 直接对接 bio
对齐要求 无 buffer 地址、长度、文件偏移都要按逻辑块大小对齐
写完何时可见 立即可见（在内存里） 立即可见（已经下发）
与别的读者共享 是，同一份 page 否，绕开共享层
一致性责任 内核管内存，fs 管磁盘 全在应用身上
典型用途 绝大多数场景 数据库自管缓存、大文件流式拷贝

绕开缓存省了一次内存拷贝，代价是失去缓存。每次读都得真去盘上拿，除非自己在上层做缓存。对齐要求也是硬伤：不对齐直接 EINVAL，不是慢一点的问题。

还有一点容易忽略：直接 IO 仍然要进文件系统。它得查块映射（ext4 的 extent 树）、要拿 inode 的读写锁、要遵守 i_size。绕开的是数据缓存，不是元数据。

十四、裸块设备与文件系统：两条不同的路径 #

前面讲的都是正常流程：文件的数据页放文件的 address_space，元数据页放块设备的 address_space，井水不犯河水。有人偏要绕过文件系统，直接写块设备上属于某个文件的数据块——事情就来了。

素材给了 __find_get_block_slow() 的开头，正好展示块设备那条路怎么定位页：

c
static struct buffer_head *
__find_get_block_slow(struct block_device *bdev, sector_t block)
{
    struct inode *bd_inode = bdev->bd_inode;
    struct address_space *bd_mapping = bd_inode->i_mapping;
    struct buffer_head *ret = NULL;
    pgoff_t index;
    struct buffer_head *bh;
    struct buffer_head *head;
    struct page *page;
    int all_mapped = 1;

    index = block >> (PAGE_CACHE_SHIFT - bd_inode->i_blkbits);
    page = find_get_page_flags(bd_mapping, index, FGP_ACCESSED);
    if (!page)
        goto out;
    ......//此处省略几十行
}

关键在 index = block >> (PAGE_CACHE_SHIFT - bd_inode->i_blkbits);。block 是块号，i_blkbits 是块大小的 log2（4096 字节块就是 12），PAGE_CACHE_SHIFT 是页大小的 log2（4096 页也是 12）。所以这行在 4K 块 + 4K 页时等于不移位，块号就是页号；块大小 1K 时右移 2 位，四个块挤一页。

后面 find_get_page_flags(bd_mapping, index, FGP_ACCESSED) 就是在块设备的树里找页。注意这个查找和第七节讲的 find_get_page(mapping, index) 长得一样，区别只在传进去的 mapping 是块设备的，不是文件的。FGP_ACCESSED 这个标志顺手把页标成「刚访问过」，给回收算法用。

两条路摆一起看：

维度 打开文件读（/root/read.c） 打开设备读（/dev/sda2）
打开对象 struct file struct block_device
mapping 来源 inode->i_mapping bd_inode->i_mapping
树的 key 文件页号 设备内的页号（由块号换算）
a_ops ext4 的 ext4_aops def_blk_aops
上层知不知情 文件系统全程参与 块层，文件系统完全不参与
写完谁负责一致 fs 的 writeback 自己，或者根本没有

同一个物理块，在两棵树里各有一个 page。改了设备树里那份，文件树里那份完全不知情。

素材接下来的实验就是证明这件事。先确认文件在缓存里：

bash
vmtouch read.c

text
           Files: 1
     Directories: 0
  Resident Pages: 1/1  4K/4K  100%
         Elapsed: 0.000133 seconds

然后用 debugfs 查 inode 的数据块位置，再用 dd 直接捅设备：

bash
debugfs -R 'stat /root/read.c' /dev/sda2
dd if=/dev/zero of=/dev/sda2 seek=2681460 bs=4096 count=1

text
Inode: 3945394   Type: regular    Mode:  0644   Flags: 0x80000
Size: 386
Links: 1   Blockcount: 8
EXTENTS:
(0):2681460
1+0 records in
1+0 records out
4096 bytes (4.1 kB, 4.0 KiB) copied, 0.000323738 s, 12.7 MB/s

Blockcount: 8 是 512 字节扇区数，386 字节的文件占一个 4K 块，所以文件系统块大小是 4096。extent 起点 2681460 是 4K 块号，dd 用 bs=4096 加 seek=2681460，偏移正好对上。换成 1K 块的文件系统，这个 seek 要除以 4，不然捅歪。

改完再 cat，内容还在。因为读的是内存里那份，设备那份改动压根没进文件树。再 drop cache 重读：

bash
echo 3 > /proc/sys/vm/drop_caches
vmtouch read.c
cat read.c

text
  Resident Pages: 0/1  0/4K  0%
         Elapsed: 0.000679 seconds

cat 没有任何输出，文件变空了。这时读下去是磁盘上的 0，不是缓存里的旧内容。

这里补一个坑：drop_caches 不回收脏页。dd 写 /dev/sda2 走的是块设备的缓冲写，那份页先脏在设备树里，得等回写才真落到盘上。如果回写还没发生就 cat，读到的仍是旧数据，实验会「不成立」。所以这个实验要等一会儿，或者 dd 之后 sync 一下。

十五、mmap 与页缓存是同一份数据 #

mmap() 一页文件，缺页时走 filemap_fault()。它做的事和 read() 高度重合：拿 mapping、按页号找 page、PG_uptodate 不够就从盘上读回来，然后把 page 的物理地址填进进程页表。

填进去之后，进程看到的内存就是 page cache 里那个 page，没有任何拷贝。read() 读到的是同一份，write() 改的也是同一份。

所以有这么个现象：mmap 写了一段，另一个进程 read() 立刻能看到，不需要 msync()。msync() 管的是「刷到磁盘」，不是「让别的进程看见」。「让别的进程看见」在页缓存这一层天然成立，因为只有一份。

反过来，msync() 之后也不是「数据一定在盘上」，它只保证脏页被下发了。要真等，得 fsync() 或者 O_SYNC。

但注意：mmap 和「裸块设备直接写」还是两份。第十四节那个实验，换成 mmap 读一样白搭。共享的前提是「同一个 address_space」，设备树和文件树不是一个。

十六、一致性：谁负责保证磁盘和内存对得上 #

一致性分三层，责任归属完全不同：

层次 谁负责 怎么保证 不做会怎样
同一文件的内存视图 内核，靠「只有一份 page」 天然一致，read / write / mmap 同一个 page 不需要保证
内存与磁盘 文件系统 + 回写线程 writeback、fsync、ext4 的日志 掉电丢数据，或元数据不一致
文件系统与裸设备 没人 无 两份缓存各说各话，直到 drop cache

第三层是本文的重点。内核为什么不给文件树和设备树做同步？因为那是为非法访问买单。正常路径下没人会绕过文件系统去写已挂载文件系统的块，为极小概率的误操作在每次 IO 上挂一个同步检查，代价远超收益。

素材的结论说得准：这两份缓存相互独立，kernel 并不会为这种非正常访问同步两份缓存，从而避免了同步的开销。

工程上的正确处理只有三种。一，别在已挂载的文件系统上直接写块设备，要写先 umount。二，写完了 drop_caches 或者重启，把文件树里那份脏的/旧的清掉。三，真要读写裸设备，用 O_DIRECT，绕开两边的缓存。第三种也不是万灵药，它绕开的是自己那份，别人缓存里的旧数据还在。

十七、易错点速查 #

  1. find_get_page() 返回的 page 带引用，必须 put_page()。循环里漏一次就是内存泄漏。
  2. find_get_page() 返回 NULL 只表示「不在树里」，不表示出错。出错要看后面的 error。
  3. offset = *ppos & ~PAGE_CACHE_MASK; 不是笔误，PAGE_CACHE_MASK 等于 PAGE_MASK，取反就是页内偏移掩码。
  4. last_index 是开区间上界，循环条件是 index < last_index，别当闭区间用。
  5. 预读不在每次读都触发。命中缓存时 page_cache_sync_readahead() 一次都不调。
  6. 拷贝到用户态会睡眠，醒来后 page 已经不在原地，不能拿旧指针继续。
  7. write() 返回不代表落盘。要落盘得 fsync()，或者用 O_SYNC。
  8. drop_caches 只丢干净页，脏页不会被动。
  9. 直接 IO 不对齐是 EINVAL，不是「慢一点」，别指望它自动降级成缓冲 IO。
  10. 裸设备写和文件缓存是两份数据。同物理块，两个 page，改一个另一个不知道。
