这篇只回答一个问题：内核代码里要读写一个文件，现在该用哪几个函数。 场景很窄：调试用的日志落盘、驱动 probe 里读一段配置/校准数据、内核里塞一小段状态。 不覆盖：正常驱动不该走这条路（数据该由用户态给），open() 系统调用的完整路径在 VFS 虚拟文件系统：抽象层与三大操作表，struct file 的引用计数与 fd 分配在 进程与文件系统：fs_struct、files_struct 与打开文件表，页缓存命中与回写在 page cache：文件系统与块设备之间。 版本口径：5.10 及以后为主线。set_fs() 在 5.10 被删除，vfs_read / vfs_write 在 4.14 就不再导出给模块用。网上 2017 年前后那些「get_fs + set_fs(KERNEL_DS) + vfs_write」的写法，在新内核上编译或加载直接失败，第九章给出对照表。

一、先说结论：该用哪个 #

需求 用什么 版本
读/写一个已经打开的文件，偏移自己管 kernel_read() / kernel_write() 4.14 起是新签名
读整个文件到内核 buffer kernel_read_file() / kernel_read_file_from_path() 4.7 起
打开一个文件 filp_open() 一直可用，但只有它没被淘汰
关闭 filp_close() 一直可用
写文件 kernel_write() 4.14 起

反过来说，不要用这些：

别用 为什么
vfs_read() / vfs_write() 4.14 起不再 EXPORT_SYMBOL，模块里调它链接期报 Unknown symbol vfs_read
set_fs() / get_fs() / KERNEL_DS 5.10 起整个机制被删掉，连符号都不存在
sys_read() / sys_open() 2.6.30 之后就被 SYSCALL_DEFINE 宏包起来，不再是可链接的符号

这一节就是全文的答案。下面几节解释为什么，以及每一行代码怎么写。

二、为什么内核里读写文件是个「不该做但有时必须做」的事 #

内核社区的态度一直很明确：不要在核心里自己开文件读写。

理由三条，都不是教条：

策略进了内核。 用哪个路径、什么权限、跟 SELinux/AppArmor 的策略怎么配合，这些本该是用户态决定的。内核硬编码一个 /etc/myapp.conf，等于把一条策略埋进了二进制。

执行上下文不保证。 filp_open 内部要走路径解析，路径解析可能触发文件系统 I/O，I/O 可能睡眠。中断上下文、持有自旋锁时调它，轻则 might_sleep 警告，重则死锁。这类 bug 只在压力下复现。

安全面扩大。 一个能被任意路径打开的接口，就是一条攻击路径。5.x 之后内核推 kernel_read_file() 一族，核心动机之一就是把「内核读文件」这件事收进一个可以挂 LSM 钩子的入口。

那什么时候必须做？实践中就三类：

  • 调试：驱动里临时打个日志到文件，比配 pstore 或改 printk 目标快。
  • probe 时读校准/配置数据：设备的 MAC 地址、RF 校准参数存在 eMMC 某个文件里，驱动启动时要读。
  • 内核内部模块间传数据：少见，但存在。

除了这三类，正确的做法都是让用户态把数据通过 ioctl / sysfs / configfs 送进来。Linux 设备驱动的固件加载 里的 request_firmware() 就是这套思路的标准范例：内核不自己开文件，而是向用户态要数据。

三、打开文件：filp_open #

c
#include <linux/fs.h>

struct file *filp_open(const char *filename, int flags, umode_t mode);

返回 struct file *，失败时返回错误指针，不是 NULL。所以判等必须用 IS_ERR()：

c
struct file *fp;

fp = filp_open("/tmp/mylog", O_WRONLY | O_CREAT | O_APPEND, 0644);
if (IS_ERR(fp)) {
    int err = PTR_ERR(fp);
    pr_err("open failed: %d\n", err);
    return err;          /* 注意：要返回 PTR_ERR，不要返回 -1 */
}

三个参数：

参数 说明
filename 完整路径。内核没有「当前工作目录」的概念（严格说 current->fs->pwd 存在，但依赖它是错的）
flags 与用户态 open(2) 的 flag 一致：O_RDONLY / O_WRONLY / O_RDWR / O_CREAT / O_APPEND / O_TRUNC
mode 只在带 O_CREAT 时有意义，是新建文件的权限位

3.1 三个必踩的坑 #

坑一：IS_ERR 不是 == NULL。 这条原文没写清，但它是模块里最常见的崩溃点。内核里大量函数用「错误指针」这个约定（ERR_PTR(-ENOENT) 之类），直接 if (!fp) 判断等于没判，后面 filp_close(fp) 就去解引用一个 0xfffffffffffffffe 这样的地址。

坑二：打开时机。 如果模块在 module_init 里就 filp_open("/etc/config")，而 rootfs 还没挂载完，会拿到 -ENOENT。嵌入式上这个现象特别常见，因为 insmod 往往发生在 initramfs 阶段。解法是延后到 late_initcall 或者等到设备实际被使用时再打开。

坑三：路径在 initramfs 和真实 rootfs 之间会变。 上一条的变体。switch_root 之后 /etc/config 指向的文件和 switch 之前可能根本不是同一个，即使路径字符串一样。

3.2 权限与凭证 #

filp_open 用的凭证是当前进程的。在 probe() 里调它，用的是触发 probe 的那个上下文（内核线程的话是 kthreadd 改的凭证）。如果需要 root 权限打开，得确保上下文有；否则用 override_creds() 临时提权，用完记得还原。

这也是一个「不该做」的理由：驱动为了一行配置去提权，权限模型就乱了。

四、读写：kernel_read 与 kernel_write #

这两个是现在唯一该用的组合。

c
#include <linux/fs.h>

ssize_t kernel_read(struct file *file, void *buf, size_t count, loff_t *pos);
ssize_t kernel_write(struct file *file, const void *buf, size_t count, loff_t *pos);

四个参数：

参数 说明
file filp_open 返回的那个
buf 内核空间的 buffer。传普通 char buf[] 就行，不需要 __user
count 字节数
pos 偏移指针。必须初始化；读写完成后它会被更新到新位置

返回值是实际读写的字节数，出错返回负错误码。注意「实际字节数小于 count」不是错误，可能读到文件末尾，也可能被信号打断。

c
static int read_and_log(const char *path)
{
    struct file *fp;
    char buf[256];
    loff_t pos = 0;
    ssize_t n;
    int ret = 0;

    fp = filp_open(path, O_RDONLY, 0);
    if (IS_ERR(fp))
        return PTR_ERR(fp);

    n = kernel_read(fp, buf, sizeof(buf) - 1, &pos);
    if (n < 0) {
        ret = n;
    } else {
        buf[n] = '\0';
        pr_info("first %zd bytes: %s\n", n, buf);
    }

    filp_close(fp, NULL);
    return ret;
}

4.1 为什么不用 vfs_read #

原文的核心写法就是这个，也是它最过时的地方。

vfs_read() / vfs_write() 本身还在 fs/read_write.c 里，但 4.14 起不再导出给模块。在模块里调用它，编译能过（有声明），insmod 时报：

text
ERROR: modpost: "vfs_read" [.../my_module.ko] undefined!

或者加载期 Unknown symbol vfs_read (err -2)。

更重要的是，vfs_read 的 buf 参数带 __user 修饰：

c
ssize_t vfs_read(struct file *file, char __user *buf, size_t count, loff_t *pos);

__user 是个给 sparse 看的标记，含义是「这个指针指向用户地址空间」。传内核指针进去，access_ok() 检查会失败，返回 -EFAULT。这就是原文为什么要 set_fs(KERNEL_DS) 绕过去。

kernel_read() 做的正是同一件事，只是把 set_fs 的活收进函数内部。所以用 kernel_read 就别再碰 set_fs，两个一起用反而会出问题。

4.2 kernel_read 的签名变过一次 #

这条非常容易踩，因为大量 2017 年的文章贴的是旧签名：

c
/* 4.13 及以前，定义在 fs/exec.c */
int kernel_read(struct file *file, loff_t offset, char *addr, unsigned long count);

c
/* 4.14 及以后，移到 fs/read_write.c */
ssize_t kernel_read(struct file *file, void *buf, size_t count, loff_t *pos);

差别不只是参数顺序：返回值从 int 变成 ssize_t，最后一个参数从「传入偏移」变成「传入出参指针」。旧代码照抄到新内核，编译期报参数类型不符，或者更糟：编译通过但偏移语义错了（旧版是传值，新版期望传地址，把 0 当指针传进去就是空指针解引用）。

kernel_write() 同理。原文没提这个函数，因为 2017 年那篇文章写的时候它还没成为通用接口。

4.3 set_fs 为什么必须消失 #

理解这段历史能帮你认出哪些资料是过时的。

set_fs(KERNEL_DS) 的作用是把「用户空间和内核空间的分界线」挪到顶，于是所有针对用户指针的地址检查全部放行。这样 vfs_read 拿到一个内核指针也不会报 -EFAULT。

问题在于这是个进程级的全局状态。忘了还原（异常路径、return 提前退出）就会让后续代码在一个错误的地址空间假设下运行。内核历史上出过一批由此引发的安全漏洞。

Christoph Hellwig 从 5.9 开始系统性清理，到 5.10 把 set_fs() 整个删掉。清理办法是把「需要读写内核 buffer」的场景全部改成专门的接口：kernel_read / kernel_write 内部走 iov_iter，iov_iter 自己知道 buffer 在内核还是在用户空间（ITER_KVEC vs ITER_IOVEC），不需要全局状态。

所以 set_fs 不是「不推荐」，是符号已经不存在。在 5.10+ 的内核上写 set_fs(KERNEL_DS)，报的是 implicit declaration of function 'set_fs' 加链接失败。

五、读整个文件：kernel_read_file 一族 #

如果需求是「把这个文件整个读进来」，别自己 filp_open + 循环 kernel_read + 算大小，用现成的：

c
#include <linux/kernel_read_file.h>

int kernel_read_file_from_path(const char *path, loff_t offset,
                               void **buf, size_t buf_size,
                               size_t *file_size,
                               enum kernel_read_file_id id);

int kernel_read_file(struct file *file, loff_t offset,
                     void **buf, size_t buf_size,
                     size_t *file_size,
                     enum kernel_read_file_id id);

它会自己分配 buffer（vmalloc）、自己读满、自己返回大小。用完必须 vfree()。

id 这个参数是关键，不是装饰：

c
enum kernel_read_file_id {
    READING_UNKNOWN = 0,
    READING_FIRMWARE,
    READING_MODULE,
    READING_KEXEC_IMAGE,
    READING_KEXEC_INITRAMFS,
    READING_POLICY,
    READING_X509_CERTIFICATE,
    ...
};

它的作用是告诉 LSM 你在读什么类型的文件，于是 IMA（Integrity Measurement Architecture）可以按类型决定要不要做完整性校验，SELinux 可以按类型放行或拒绝。这正是第二章说的「把内核读文件收进可挂钩子的入口」。

自己 filp_open + kernel_read 就绕过了这一层，安全模块看不见你在读什么。要是这段代码要进主线，reviewer 会要求改成 kernel_read_file。

头文件位置有个版本变化：早期 kernel_read_file* 声明在 <linux/fs.h>，后来（5.11 前后）拆到独立的 <linux/kernel_read_file.h>。只 #include <linux/fs.h> 在旧版能过、新版报隐式声明，两个都 include 最稳。

六、关闭：filp_close #

c
int filp_close(struct file *filp, fl_owner_t id);

第二个参数是「文件所属的 owner」，常规传 NULL。原文说「也有用 current->files 作为实参的」，这在你要模拟当前进程关文件时才有意义。绝大多数场景传 NULL。

c
filp_close(fp, NULL);

这里没有 IS_ERR 的判断必要（前面已经判过），但必须确保每条错误路径都调用了它。filp_open 拿到的 struct file 带引用计数，不关就是泄漏，泄漏的是 struct file 和它引用的 dentry / inode。表现是 slabtop 里 filp 缓存一直涨。

用 goto 风格的清理比每个分支手写 filp_close 可靠：

c
fp = filp_open(path, O_RDONLY, 0);
if (IS_ERR(fp))
    return PTR_ERR(fp);

n = kernel_read(fp, buf, size, &pos);
if (n < 0) {
    ret = n;
    goto out_close;
}
/* ... 用数据 ... */

out_close:
    filp_close(fp, NULL);
    return ret;

七、上下文约束：哪些地方不能调 #

这一节原文提了（第 71~74 行），但说得很含糊，这里说清。

上下文 能调 filp_open / kernel_read 吗 原因
进程上下文，可睡眠（probe、write 回调、工作队列） 能 正常路径
软中断 / tasklet / 定时器回调 不能 这些函数会睡眠，而在中断上下文睡眠是致命错误
持有自旋锁期间 不能 同上，且 spin_lock 期间禁止睡眠
持有 mutex 但上下文可睡眠 能，但要评估锁持有时间 文件 I/O 可能几十毫秒，持锁期间别人全堵着
module_init（早期） 能，但可能因 rootfs 未就绪而失败 见坑二

原文的建议是「可以创建内核线程，把这些函数放在线程环境下执行」。这个建议本身没错，但现代做法更简单：

  • 一次性任务用 schedule_work() / queue_work()，工作队列天然跑在进程上下文。
  • 周期性任务用 kthread_run()。
  • 内核线程默认没有用户态凭证，filp_open 权限判定会走 kthreadd 的 creds；需要特定权限时用 override_creds()。

原文提到的 kernel_thread() 这个函数已经被 kthread_run() 取代，别照着用。

八、一个完整例子（能在 5.10+ 编译） #

原文的例子有几处编译不过的地方，重写一版：

c
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/version.h>

#define LOG_PATH "/tmp/kernel_rw_demo.txt"

static int __init krw_init(void)
{
    struct file *fp;
    loff_t pos = 0;
    ssize_t n;
    static const char msg[] = "hello from kernel\n";
    char rbuf[64];
    int ret = 0;

    pr_info("krw: enter\n");

    fp = filp_open(LOG_PATH, O_RDWR | O_CREAT | O_TRUNC, 0644);
    if (IS_ERR(fp)) {
        pr_err("krw: open %s failed: %ld\n", LOG_PATH, PTR_ERR(fp));
        return PTR_ERR(fp);
    }

    n = kernel_write(fp, msg, sizeof(msg) - 1, &pos);
    if (n < 0) {
        pr_err("krw: write failed: %zd\n", n);
        ret = n;
        goto out;
    }
    pr_info("krw: wrote %zd bytes, pos now %lld\n", n, pos);

    /* 回到文件开头再读一遍 */
    pos = 0;
    n = kernel_read(fp, rbuf, sizeof(rbuf) - 1, &pos);
    if (n < 0) {
        pr_err("krw: read failed: %zd\n", n);
        ret = n;
        goto out;
    }
    rbuf[n] = '\0';
    pr_info("krw: read back (%zd bytes): %s", n, rbuf);

out:
    filp_close(fp, NULL);
    pr_info("krw: leave, ret=%d\n", ret);
    return ret;
}

static void __exit krw_exit(void)
{
    pr_info("krw: exit\n");
}

module_init(krw_init);
module_exit(krw_exit);
MODULE_LICENSE("GPL");

原例子对照着改的地方：

原例子 改成 原因
缺 #include <linux/kernel.h> 补上 pr_info / pr_err 在这
printk("hello enter\n") pr_info("krw: ...") 加模块前缀，方便 dmesg | grep
IS_ERR(fp) 后 return -1 return PTR_ERR(fp) 把真实错误码传出去
fs = get_fs(); set_fs(KERNEL_DS); 全部删掉 5.10 起不存在，kernel_read/write 不需要
vfs_write / vfs_read kernel_write / kernel_read 4.14 起 vfs_* 不导出
set_fs(fs) 放在 filp_close 之后 一并删除 顺序问题随 set_fs 消失
全篇无错误路径清理 加 goto out 统一 filp_close 防 struct file 泄漏
sizeof(buf) 当读长度（含 \0） sizeof(buf) - 1 再补 \0 读满就没有位置放终止符了

特别说明第 5 条：原例子 static char buf[] = "你好"; 然后 vfs_write(fp, buf, sizeof(buf), &pos)，sizeof 包含结尾的 \0，所以会把 7 个字节（UTF-8 的「你好」是 6 字节加 \0）写进文件。这个细节在调试日志场景下无所谓，但如果文件格式有约定，多写一个 \0 就是 bug。

九、从 2017 年到 5.10+：对照表 #

老写法 现状 变更
vfs_read() / vfs_write() 不再导出给模块 4.14，Christoph Hellwig 的「switch in-kernel read/write calls to kernel_read/write」系列
get_fs() / set_fs() / KERNEL_DS / USER_DS 已删除 5.10（清理从 5.9 开始）
kernel_read(file, offset, addr, count) 返回 int kernel_read(file, buf, count, &pos) 返回 ssize_t 4.14，从 fs/exec.c 移到 fs/read_write.c
sys_read() / sys_open() 被 SYSCALL_DEFINE 宏包起来，无导出符号 2.6.30
kernel_thread() 用 kthread_run() / kthread_create() 2.6 后期
自建 buffer + 循环读整个文件 kernel_read_file() 一族 4.7
strcut file* / -EFALUT struct file * / -EFAULT 原文错字

还有一条原文提到但结论需要修正的：

原文：「在可加载的 kernel module 中使用这种方式读写文件可能使模块加载失败，原因是内核可能没有 EXPORT 你所需要的所有这些函数。」

这句话在 2017 年是对的（说的正是 vfs_read 不导出）。但准确的因果是：不是「可能没有导出」，而是 4.14 之后确定不导出。原文把一条确定的版本变更写成了不确定的可能性，读者会误以为「换个内核版本也许就行」。实际情况是：4.14 之前能跑，4.14 之后必须改代码。

十、调试期的替代方案 #

既然是「调试时想在核心里写文件」，先说几条比这更省事的路：

方案 适用 代价
printk + dmesg 默认选择 日志在内存环形缓冲区，重启就没了
pstore / ramoops 崩溃现场要留存 要预留内存，配 dts
debugfs 要暴露结构化数据给用户态 要写一套 file_operations
trace_printk + tracefs 高频事件，要时间戳 走 ftrace，开销比 printk 低
relay 大量数据，要低开销 接口重，值得单独学

判断标准很简单：日志要在重启后还在吗？ 不在，printk 就够。要在，pstore 比往文件里写靠谱，因为它不依赖文件系统和挂载时序。

只有在「必须写进某个具体的文件，且用户态不方便参与」时，才轮到本文这些函数。
