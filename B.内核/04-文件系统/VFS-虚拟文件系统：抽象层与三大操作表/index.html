这篇讲两件事：VFS 这层抽象凭什么立得住，以及它的三张操作表——super_operations、inode_operations、file_operations——每个字段什么时候被谁调用。

一、VFS 存在的理由：一份系统调用，多种文件系统 #

Linux 允许众多不同的文件系统共存，还支持跨文件系统的文件操作。这不是白来的，靠的是中间那层虚拟文件系统——VFS（Virtual File System）。它是内核里的一个软件抽象层，通过一组数据结构，以及挂在这些结构上的方法，向 ext2、vfat 这类实际文件系统提供统一的接口机制。

原文拿 Linux 的两个特性当引子，摆得对：

跨文件系统的文件操作。ext2、ext3、vfat 可以同时挂在系统里，你用同一套文件 I/O 系统调用去操作任意文件，不用管它躺在哪种格式的磁盘上。再往下一层，操作还能跨文件系统执行。cp 把 vfat 分区上的一个文件拷到 ext3 分区，一次命令里就套了两个文件系统。

一切皆是文件。普通文件、目录、字符设备、块设备、套接字，在 Unix/Linux 里都当文件对待。类型不同，对外给的却是同一套操作界面。

VFS 就是这两点的实现者。它给用户空间程序提供文件系统接口，同时在内核里提供一层抽象，让不同文件系统共存。所有文件系统不但依赖 VFS 共存，也依靠 VFS 协同工作。

要让各种实际文件系统都能接进来，VFS 定义了所有文件系统都得支持的基本概念接口和数据结构；反过来，实际文件系统也要提供 VFS 期望的抽象接口和数据结构，把自己的「文件」「目录」对齐到 VFS 的定义。一个文件系统想被 Linux 支持，就得交出一份符合 VFS 标准的接口。原文在这里引了《老炮儿》那句「要有规矩」——想在 Linux 下混，就按 Linux 定的规矩办事。实现细节藏在统一接口后面，所以站在 VFS 层和内核其他部分看过去，所有文件系统长一个样。

落到收益上：应用通过统一系统调用访问各种介质，换文件系统不改代码；新文件系统只要实现 VFS 的各接口，不用动内核其他部分。

这里有个容易滑过去的点：VFS 抽象掉的不是「存储」，是调用约定。它没规定数据怎么落到磁道上，只规定了「要读一个文件时，内核调哪个函数指针，参数是什么，返回什么」。所以第四节到第十一节那些结构体，本质都是一张张函数指针表。

二、一切皆文件：这句话到底省掉了什么 #

这句话常被当口号念，念多了就失真。它说的不是「所有东西都是普通文件」——字符设备和普通文件的差别大得很；它说的是「所有东西都挂同一套操作界面」。

省掉的是用户态的枚举。你写 open / read / write / close，不用先判断这是设备还是普通文件，再决定调 ioctl 还是 read。判断被下沉到内核，由实际文件系统在打开那一刻做一次。

下沉点很具体，就在 ext3_read_inode() 里：

c
void ext3_read_inode(struct inode * inode)
{
    ……
    // 是普通文件
    if (S_ISREG(inode->i_mode)) {
        inode->i_op  = &ext3_file_inode_operations;
        inode->i_fop = &ext3_file_operations;
        ext3_set_aops(inode);
    } else if (S_ISDIR(inode->i_mode)) {
        // 是目录文件
        inode->i_op  = &ext3_dir_inode_operations;
        inode->i_fop = &ext3_dir_operations;
    } else if (S_ISLNK(inode->i_mode)) {
        // 是符号链接
        ……
    } else {
        // 前三种都排除了，剩下的是设备文件
        // 这里的设备还包括套接字、FIFO 等伪设备
        ……
    }
}

按 i_mode 分流，给同一个 struct inode 挂不同的 i_op 和 i_fop。往后不管谁来读这个 inode，read 走的都是挂上去的那套函数。用户态看到的界面一模一样，内核里走的分支完全不同。

对象 用户态看到的 谁在最后做区分 区分依据
普通文件 read / write ext3_file_operations S_ISREG
目录 readdir / lookup ext3_dir_operations S_ISDIR
符号链接 readlink 或自动跟随 i_op->follow_link / get_link S_ISLNK
字符设备 read / write / ioctl def_chr_fops → 驱动自己的表 S_ISCHR
套接字、FIFO 各自一套 sockfs / pipefs 的 fops S_ISSOCK / S_ISFIFO

字符设备那一行是本文后半段的主线，第十七节展开。

三、VFS 的四层对象模型总览 #

VFS 依靠四个主要数据结构和一些辅助结构来描述状态。这几个结构体被当对象用：每个对象里都嵌着一张操作函数表，表里描述内核能对这个对象做什么。原文有句话说得准——它们「表现得就像是对象」。没走 C++ 那套虚函数，用的是「结构体 + 函数指针表」，效果一样，成本更低。

对象 代表什么 存在磁盘上吗 什么时候产生 操作表
struct super_block 一个已挂载的文件系统 磁盘上有控制信息，内存里是实例 挂载时填充 s_op
struct inode 一个文件（含目录、设备节点） 是，磁盘上有索引节点 首次访问时组装 i_op，另有默认的 i_fop
struct dentry 路径里的一个组成部分 否，纯内存 路径解析中创建 d_op
struct file 一次打开（open file description） 否，纯内存 open() 创建，close() 销毁 f_op

前两个是「真实存在」的：超级块和索引节点都在磁盘上有对应物，即便基于内存的文件系统（tmpfs、ramfs）也算一种抽象意义上的实际物理文件。后两个是运行时才造出来的，掉电就没了。

四张 ops 表的分工，先立个骨架，后面逐节填肉：

操作表 挂在谁身上 回答什么问题 谁填
super_operations sb->s_op 整个文件系统怎么初始化、同步、卸载 文件系统作者
inode_operations inode->i_op 目录里怎么查名字、怎么建删文件、怎么改大小 文件系统作者
dentry_operations dentry->d_op 名字怎么比较、哈希、校验 少数文件系统
file_operations file->f_op 已打开的文件怎么读写 文件系统与驱动作者

四层对象之外还有辅助结构：address_space（页缓存与地址映射）、vfsmount（挂载点信息）、file_system_type（文件系统类型注册）、nameidata（路径查找上下文）。用到再讲。

记住这个模式：每个对象带一张表，表里的函数由具体文件系统填，VFS 负责在正确时机调正确的槽位。

四、super_block：一个已挂载文件系统的身份 #

超级块对象存储一个已安装文件系统的控制信息，代表一个已安装的文件系统。每次一个实际文件系统被安装，内核从磁盘的特定位置读控制信息，填充内存里的超级块对象。一个安装实例对应一个超级块对象。超级块通过 s_type 记录自己属于哪种文件系统。

定义在 <linux/fs.h>。以下节选出自 2.6.x，是原文摘出的重要字段，不是全量：

c
/*
 * 超级块结构中定义的字段非常多，
 * 这里只介绍一些重要的属性
 */
struct super_block {
    struct list_head              s_list;    /* 指向所有超级块的链表 */
    const struct super_operations *s_op;     /* 超级块方法 */
    struct dentry                *s_root;    /* 目录挂载点 */
    struct mutex                  s_lock;    /* 超级块互斥锁 */
    int                           s_count;   /* 超级块引用计数 */
    struct list_head              s_inodes;  /* inode 链表 */
    struct mtd_info              *s_mtd;     /* 存储磁盘信息 */
    fmode_t                       s_mode;    /* 安装权限 */
};

两个必须点出来的问题。第一，s_lock 的注释。原两版都写「超级块信号量」，但字段类型是 struct mutex——互斥锁，不是信号量。2.4 时代 s_lock 是自旋锁，那时候的说法更乱。看到「信号量」三个字，按「互斥锁」理解。第二，这段是节选。2.6.17 的 struct super_block 实际字段远不止八个，s_type（文件系统类型）、s_flags（挂载标志）、s_dev（设备号）、s_blocksize、s_maxbytes、s_dirt、s_d_op 都没列进来。原文写明「只介绍一些重要的属性」，这是取舍不是错。但你拿它当字段对照表用，会缺一半。到 5.x 更明显，struct super_block 已经涨到五六十个字段，未逐一验证每个字段的存废，用之前直接翻手上那版内核的 include/linux/fs.h。

五、super_operations：文件系统级操作 #

s_op 指向的这张表定义文件系统级操作。以下结构体出自 2.6.x，13 个字段，一个不少：

c
/*
 * 其中的 s_op 中定义了超级块的操作方法
 * 这里只介绍一些相对重要的函数
 */
struct super_operations {
    /* 创建和初始化一个索引节点对象 */
    struct inode *(*alloc_inode)(struct super_block *sb);
    /* 释放给定的索引节点 */
    void (*destroy_inode)(struct inode *);

    /* VFS 在索引节点被修改时会调用这个函数 */
    void (*dirty_inode) (struct inode *);
    /* 将索引节点写入磁盘，wait 表示写操作是否需要同步 */
    int (*write_inode) (struct inode *, int);
    /* 最后一个指向索引节点的引用被删除后，VFS 会调用这个函数 */
    void (*drop_inode) (struct inode *);
    /* 从磁盘上删除指定的索引节点 */
    void (*delete_inode) (struct inode *);

    /* 卸载文件系统时由 VFS 调用，用来释放超级块 */
    void (*put_super) (struct super_block *);
    /* 用给定的超级块更新磁盘上的超级块 */
    void (*write_super) (struct super_block *);
    /* 使文件系统中的数据与磁盘上的数据同步 */
    int (*sync_fs)(struct super_block *sb, int wait);
    /* VFS 调用该函数获取文件系统状态 */
    int (*statfs) (struct dentry *, struct kstatfs *);

    /* 指定新的安装选项重新安装文件系统时，VFS 会调用该函数 */
    int (*remount_fs) (struct super_block *, int *, char *);
    /* VFS 调用该函数释放索引节点，并清空包含相关数据的页面 */
    void (*clear_inode) (struct inode *);
    /* VFS 调用该函数中断安装操作 */
    void (*umount_begin) (struct super_block *);
};

什么时候被谁调：

回调 触发时机 典型实现里干什么
alloc_inode 分配新 inode 时 分配一个包住 inode 的私有结构体；不实现就分配裸 struct inode
destroy_inode 释放 inode 内存时 释放私有结构体，与 alloc_inode 配对
dirty_inode inode 被标脏时 日志文件系统把元数据变更塞进日志
write_inode 需要把 inode 写回磁盘 组装磁盘索引节点、落盘，wait 非 0 表示同步
drop_inode 最后一个引用被丢弃 决定是否还缓存这个 inode
delete_inode 从磁盘删除 inode 释放磁盘块、更新位图
put_super 卸载文件系统 释放内存超级块的私有数据
write_super 需要更新磁盘超级块 把内存与磁盘的差异写回
sync_fs 同步整个文件系统 刷元数据，wait 非 0 时等完成
statfs statfs(2) / statvfs(3) 填 struct kstatfs
remount_fs 重新挂载 解析新选项并应用
clear_inode 清空 inode 清理内存状态
umount_begin 开始卸载 中断未完成的安装操作，网络文件系统用得多

现代内核差异（依据 6.6 内核文档 filesystems/vfs.html 与 porting.html）：

2.6.x 的字段 现状 变化说明
delete_inode 已删除 与 clear_inode 一起被 evict_inode() 取代
clear_inode 已删除 不再由文件系统实现；页缓存要用 truncate_inode_pages_final() 自己清
write_super 已删除 6.6 的 super_operations 里没有这个槽位
drop_inode 保留，签名变了 返回 int，true 表示希望丢弃；调用时持有 i_lock
dirty_inode 签名变了 多一个 int flags，会带 I_DIRTY_DATASYNC / I_DIRTY_TIME
write_inode 签名变了 第二个参数从 int 换成 struct writeback_control *
其余七个 保留 sync_fs、statfs、remount_fs、umount_begin、put_super、alloc_inode、destroy_inode
—— 新增 free_inode 在 RCU 回调里释放 inode 内存，配合 destroy_inode
—— 新增 evict_inode 语义是「inode 要被逐出缓存」，不管还有没有硬链接
—— 新增 freeze_super / freeze_fs / thaw_super / unfreeze_fs 文件系统冻结，LVM 与 ioctl(FIFREEZE) 用
—— 新增 show_options / show_devname / show_path / show_stats 给 /proc/self/mounts、mountinfo、mountstats 供数
—— 新增 quota_read / quota_write / get_dquots 配额文件读写
—— 新增 nr_cached_objects / free_cached_objects 配合内存回收，报告并释放可回收对象

evict_inode 的来龙去脉值得多一句。porting.rst 写得很明确：clear_inode() 和 delete_inode() 都没了，改用 evict_inode()；调用方不负责逐出页缓存和 inode 关联的元数据缓冲区，实现方得自己调 truncate_inode_pages_final()。这句话把 2.6.x 里 clear_inode 注释写的「清空包含相关数据的所有页面」直接推翻了——清页面不是它的活。按新内核理解那条注释去写代码，会写错。

另外，原文这张表本身也是节选（注释里写了「只介绍一些相对重要的函数」），别把节选当全量。

六、inode：一个文件在磁盘上的身份 #

索引节点对象存文件的相关信息，代表存储设备上一个真实的物理文件。文件第一次被访问时，内核在内存里组装对应的索引节点对象，把操作这个文件必需的信息凑齐。这些信息一部分存在磁盘的特定位置，另一部分在加载时动态填充。

定义在 <linux/fs.h>，节选出自 2.6.x：

c
/*
 * 索引节点结构中定义的字段非常多，
 * 这里只介绍一些重要的属性
 */
struct inode {
    struct hlist_node              i_hash;     /* 散列表，用于快速查找 inode */
    struct list_head               i_list;     /* 索引节点链表 */
    struct list_head               i_sb_list;  /* 超级块链表 */
    struct list_head               i_dentry;   /* 目录项链表 */

    unsigned long                  i_ino;      /* 节点号 */
    atomic_t                       i_count;    /* 引用计数 */
    unsigned int                   i_nlink;    /* 硬链接数 */

    uid_t                          i_uid;      /* 使用者 id */
    gid_t                          i_gid;      /* 使用组 id */

    struct timespec                i_atime;    /* 最后访问时间 */
    struct timespec                i_mtime;    /* 最后修改时间 */
    struct timespec                i_ctime;    /* 最后改变时间 */

    const struct inode_operations *i_op;       /* 索引节点操作函数 */
    const struct file_operations  *i_fop;      /* 缺省的文件操作函数 */
    struct super_block            *i_sb;       /* 相关的超级块 */
    struct address_space          *i_mapping;  /* 相关的地址映射 */
    struct address_space           i_data;     /* 设备地址映射 */

    unsigned int                   i_flags;    /* 文件系统标志 */
    void                          *i_private;  /* fs 私有指针 */
};

按用途分组看：

分组 字段 你要关心的点
身份 i_ino、i_sb、i_hash i_ino 在单文件系统内唯一；i_sb 指回超级块，是判断「属于哪个文件系统」的唯一线索
引用与链接 i_count、i_nlink、i_dentry i_count 是内存引用，i_nlink 是磁盘硬链接数。删了文件但进程还开着，i_nlink 为 0 而 i_count 不为 0，就是「已删除但空间没释放」的来源
属主与权限 i_uid、i_gid、i_flags i_flags 装 S_APPEND、S_IMMUTABLE 这类 inode 级标志
时间戳 i_atime、i_mtime、i_ctime ctime 是状态变更时间，不是创建时间，别混
操作表 i_op、i_fop i_op 是 inode 级操作；i_fop 是「这个 inode 被打开后默认给哪张 file_operations」
数据 i_mapping、i_data 两者多半相同，但块设备会把 i_mapping 指到别处
私有 i_private 文件系统自己的挂载点，VFS 不碰

i_fop 的名字值得停一下。原文注释写「缺省的索引节点操作」，翻错了。它是默认的文件操作表——open() 时如果没有别的来源，struct file 的 f_op 就取 inode->i_fop。2.6.17 的头文件里这行注释更直白：/* former ->i_op->default_file_ops */，早期它挂在 i_op 下面，后来被提到 inode 上。同样在 2.6.17 的 include/linux/fs.h 里，i_op 是 struct inode_operations *i_op;，没有 const；有 const 的是 i_fop。上面这段给 i_op 加了 const，是后来的写法。不影响理解，但拿旧代码去编译新内核，加不加 const 会报错。

节选漏掉的还有 i_mode（文件类型与权限位，S_ISREG 那一串宏全靠它）、i_size（文件长度）、i_rdev（设备号，字符设备靠它）、i_cdev（指向字符设备的 struct cdev）、i_blkbits / i_blksize（块大小）。第十七节回到 i_rdev 和 i_cdev。

七、inode_operations：inode 级操作 #

i_op 指向的这张表定义 inode 级操作。以下结构体出自 2.6.x，6 个字段：

c
/*
 * 其中的 i_op 中定义了索引节点的操作方法
 * 这里只介绍一些相对重要的函数
 */
struct inode_operations {
    /* 为 dentry 对象创建一个新的索引节点 */
    int (*create) (struct inode *, struct dentry *, int, struct nameidata *);
    /* 在特定文件夹中寻找索引节点，该索引节点要对应于 dentry 中给出的文件名 */
    struct dentry * (*lookup) (struct inode *, struct dentry *, struct nameidata *);
    /* 创建硬链接 */
    int (*link) (struct dentry *, struct inode *, struct dentry *);
    /* 从一个符号链接查找它指向的索引节点 */
    void * (*follow_link) (struct dentry *, struct nameidata *);
    /* 在 follow_link 调用之后，由 VFS 调用进行清除工作 */
    void (*put_link) (struct dentry *, struct nameidata *, void *);
    /* 该函数由 VFS 调用，用于修改文件的大小 */
    void (*truncate) (struct inode *);
};

逐个说清触发点：

回调 谁触发 干什么
create open(2) / creat(2) 带 O_CREAT 给还没有 inode 的 dentry 造出 inode，紧接着调 d_instantiate()
lookup 路径解析时在父目录里找名字 返回 dentry，找不到返回负目录项；实现里要调 d_add() / d_splice_alias()
link link(2) 建硬链接，增加 i_nlink
follow_link 解析到符号链接 把链接体交给 VFS 继续走，返回一个 cookie
put_link follow_link 之后 收拾 follow_link 留下的现场
truncate truncate(2) / ftruncate(2) 改文件大小，增删磁盘块

现代内核差异（依据 porting.rst 与 6.6 的 VFS 文档）：

2.6.x 现状 依据
truncate 已删除 「->truncate is gone. The whole truncate sequence needs to be implemented in ->setattr」
follow_link / put_link 被 get_link 取代 「->follow_link() is replaced with ->get_link()」；put_link 已删除
create 带 struct nameidata * 无 nameidata，改成 (mnt_idmap, inode, dentry, umode_t, bool excl) 「->create() doesn't take struct nameidata *」；后来连 excl 也去掉了
lookup 带 struct nameidata * 只带 unsigned int flags 「->d_revalidate() and ->lookup() do not take struct nameidata anymore」
—— 新增 unlink / mkdir / rmdir / mknod / symlink / rename / readlink / permission / setattr / getattr / atomic_open / tmpfile / get_acl / set_acl / listxattr 等 6.6 文档列出的全量

get_link 的换法要留意语义：老接口用 nd_set_link() 把链接体塞进 nameidata，新接口直接返回链接体字符串，cookie 走显式的 void ** 参数。再往后 get_link 又加了 struct delayed_call *done，用 set_delayed_call() 收尾。

lookup 在 2.6.x 里返回 struct dentry *，语义是「找到了就返回，负目录项也算找到」。这条路径上的并发规则后来改得很凶，RCU 走查（第十六节）就是从这儿切进去的。

八、dentry：路径解析的中间产物 #

目录项和超级块、索引节点不一样——它不存在于磁盘上，纯内存对象。

既然靠索引节点就能定位文件，为什么还要插一层？原文的理由很实在：索引节点属性太多，查找、比较文件时直接拿 inode 效率不高，所以引入目录项当抽象层。目录项是对索引节点的抽象。

路径里每一部分都是一个目录项。/mnt/cdrom/foo/bar 包含 5 个目录项：/、mnt、cdrom、foo、bar。

每个目录项有三种状态：

状态 含义
被使用 对应一个真实存在的 inode，且有一个或多个使用者在引用
未使用 对应一个真实存在的 inode，但 VFS 当前没在用，放在 LRU 上等回收
负状态 没有指向任何 inode——inode 被删了，或者这条路径本来就不存在

负状态最容易被低估。它的价值在于把「不存在」也缓存起来：反复 stat 一个不存在的路径，不用每次都穿透到磁盘。代价是文件被创建时必须让负目录项失效，否则你会撞上「明明创建了却说没有」。

c
/* 目录项对象结构 */
struct dentry {
    atomic_t               d_count;     /* 使用计数 */
    unsigned int           d_flags;     /* 目录项标识 */
    spinlock_t             d_lock;      /* 单目录项锁 */
    int                    d_mounted;   /* 该目录项是否是一个挂载点 */
    struct inode          *d_inode;     /* 相关联的索引节点 */
    struct hlist_node      d_hash;      /* 散列表 */
    struct dentry         *d_parent;    /* 父目录的目录项对象 */
    struct qstr            d_name;      /* 目录项名称 */
    struct list_head       d_lru;       /* 未使用的链表 */

    /*
     * d_child 和 d_rcu 共享内存
     */
    union {
        struct list_head   d_child;     /* 挂在父目录的子链表上 */
        struct rcu_head    d_rcu;
    } d_u;

    struct list_head       d_subdirs;   /* 子目录链表 */
    struct list_head       d_alias;     /* 索引节点别名链表 */
    unsigned long          d_time;      /* 重置时间 */
    const struct dentry_operations *d_op; /* 目录项操作相关函数 */
    struct super_block    *d_sb;        /* 文件所属的超级块 */
    void                  *d_fsdata;    /* 文件系统特有数据 */
    unsigned char          d_iname[DNAME_INLINE_LEN_MIN]; /* 短文件名 */
};

几组字段的设计意图：d_count 落到 0 就进 LRU；d_mounted 非零表示路径走到这里要「跳」到另一个文件系统的根；d_alias 把一个 inode 的多个 dentry（硬链接）串起来；d_parent 向上、d_subdirs / d_u.d_child 向下，目录项自己组成一棵树，和 inode 那边的视图是两套；d_name + d_iname 让短名字直接内嵌在结构体里，省一次分配。

d_mounted 的注释原文写「是否登录点的目录项」，「登录点」是 mount point 的误译，统一按「挂载点」读。

d_u 那个 union 是省内存的经典手法：一个目录项不会同时既挂在父目录的子链表上、又已经被 RCU 回收，所以两块指针共用一片内存。注释写得很清楚：d_child and d_rcu can share memory。

九、dentry_operations 与 dcache #

d_op 指向的这张表让文件系统覆盖目录项的默认行为。原文的 7 个字段：

c
/* 目录项相关操作函数 */
struct dentry_operations {
    /* 判断目录项对象是否过期。VFS 准备从 dcache 中使用一个目录项时会调用 */
    int (*d_revalidate)(struct dentry *, struct nameidata *);
    /* 为目录项对象生成 hash 值 */
    int (*d_hash) (struct dentry *, struct qstr *);
    /* 比较 qstr 类型的 2 个文件名 */
    int (*d_compare) (struct dentry *, struct qstr *, struct qstr *);
    /* 当目录项对象的 d_count 为 0 时，VFS 调用这个函数 */
    int (*d_delete)(struct dentry *);
    /* 当目录项对象将要被释放时，VFS 调用该函数 */
    void (*d_release)(struct dentry *);
    /* 当目录项对象丢失其索引节点时（磁盘索引节点被删除了），VFS 会调用该函数 */
    void (*d_iput)(struct dentry *, struct inode *);
    /* 生成目录项的路径名，伪文件系统用 */
    char *(*d_dname)(struct dentry *, char *, int);
};
回调 触发点 本地文件系统要不要写
d_revalidate 从 dcache 命中一个 dentry 时 不写。本地盘上的 dentry 一直是对的
d_hash 把 dentry 加进哈希表时 文件名有大小写折叠、编码转换时才写
d_compare 比较文件名时 同上，FAT 的大小写不敏感就得自己实现
d_delete d_count 落到 0，dcache 决定要不要缓存它 返回 1 立即删，返回 0 就缓存
d_release dentry 真正被释放 有私有数据要清就写
d_iput dentry 丢掉 inode 写了就必须自己调 iput()，否则默认行为被顶掉
d_dname 需要给 dentry 生成路径名 只有 sockfs、pipefs 这类伪文件系统用

dcache 归 VFS 管。原文有句话说得直接：目录项和 dcache 归 VFS 与具体文件系统管，设备驱动没资格碰。驱动只要知道「路径解析快是因为有 dcache」就够了。

维护 dcache 的 API：dget 加引用；dput 减引用，落到 0 且还在父目录哈希里时调 d_delete 决定缓存还是删；d_drop 从父目录哈希表摘掉；d_delete 删 dentry，没有别的引用就变负目录项（触发 d_iput），有引用就退化成 d_drop；d_add 加进哈希表再调 d_instantiate；d_instantiate 把 inode 挂到 dentry 上并加 i_count，传 NULL 就是造负目录项；d_lookup 给定父目录和名字查 dcache。

现代内核差异：

2.6.x 现状
d_revalidate(dentry, nameidata) 签名换成 (dentry, unsigned int flags)，之后又加了父目录 inode 和名字两个参数
—— 新增 d_weak_revalidate，处理跳转来的 dentry（/、.、..、挂载点穿越）
—— 新增 d_init、d_automount、d_manage、d_real
d_hash / d_compare 的调用约定 改了，要能在 rcu-walk 下跑，不能拿锁、不能写 dentry
d_delete 语义 只在引用计数到 0 时调用，必须是常量且幂等

d_revalidate 在 rcu-walk 模式下被调用时，得能在不阻塞、不写 dentry 的前提下判断 dentry 还成不成立；搞不定就返回 -ECHILD，VFS 退回 ref-walk 再来一次。这条规则是后加的，2.6.17 时代还不存在。

十、file：一次打开的文件描述 #

文件对象是已打开的文件在内存中的表示，用来建立进程和磁盘文件之间的对应关系。原文这个类比我认：文件对象不是一个文件，只是抽象地表示「一个打开的文件对」；它和物理文件的关系，有点像进程和程序。它由 open 现场创建，由 close 销毁。站在用户空间看 VFS，你像是在只跟文件对象打交道，不用关心超级块、索引节点和目录项。

多个进程可以同时打开同一个文件，所以同一个文件会有多个对应的文件对象。文件对象只在「进程观点」上代表已打开的文件，它反过来指向目录项，目录项再指向索引节点。一个文件对应的文件对象可以不唯一，但它对应的索引节点和目录项是唯一的。 这句话是第十节和第十二节之间的接缝，记牢。原文给出的节选：

c
/*
 * 文件对象结构中定义的字段非常多，
 * 这里只介绍一些重要的属性

struct file {
    union {

十一、file_operations：最常被驱动实现的那张表 #

f_op 指向的表，是驱动开发者打交道最多的一张。原文的 8 个字段：

c

 * 其中的 f_op 中定义了文件对象的操作方法
 * 这里只介绍一些相对重要的函数

    /* 由系统调用 write(2) 触发 */
    ssize_t (*write) (struct file *, const char __user *, size_t, loff_t *);
    /* 由异步 I/O 接口 io_submit(2) 提交的读请求触发 */
    ssize_t (*aio_read) (struct kiocb *, const struct iovec *, unsigned long, loff_t);
    /* 由异步 I/O 接口 io_submit(2) 提交的写请求触发 */

这里修了两处原文的错：llseek 的注释原文写成「由系统调用 lleek() 调用它」——拼写错，是 lseek(2)；aio_read / aio_write 原文写成「由系统调用 aio_read() 调用」，内核里没有叫 aio_read 的系统调用，异步 I/O 由 io_submit(2) 提交、io_getevents(2) 收割。

直接调 ->read / ->write 禁止 「never call ->read() and ->write() directly; use __vfs_{read,write}」；判断可读性看 FMODE_CAN_READ，不再看函数指针是否为 NULL

最后一行对驱动作者有实际影响：以前判「这个文件能不能读」是看 file->f_op->read 是不是 NULL，现在看 file->f_mode & FMODE_CAN_READ。你自己写驱动时不用管这层，但看内核代码时要认得出两种写法。

驱动侧最小可用集合，按这个顺序填：

场景 必须实现
只读字符设备 owner、open、read、release
读写字符设备 再加 write
要支持定位 llseek
要支持非阻塞 poll
要下发命令 unlocked_ioctl（32 位兼容再加 compat_ioctl）
要 mmap 到用户空间 mmap

flush 和 release 别混：flush 每次 close 都会被调（dup 出来的 fd 关一个就一次），release 只在最后一个引用消失时调一次。要释放资源，放 release。

十三、open() 的完整调用链 #

理论讲完，进源码。原文挑 sys_open() 和 sys_read() 当样本，理由是它们有代表性。源码版本 linux-2.6.17，只列关键代码。

sys_open() 打开或创建一个文件，成功返回文件描述符。整条链分三段，do_filp_open() 里先找文件再打开，open_namei() 里分四步：

在哪个函数里 函数 干了什么
sys_open get_unused_fd() 拿一个空闲 fd。这说明 fd 本质上是「进程打开文件表里对应某个 file 对象的索引值」
sys_open do_filp_open() 打开文件，返回 struct file，代表该进程打开的这个文件
sys_open fd_install() 把 fd 和 file 对象绑上。以后进程对文件的所有读写都靠这个 fd
do_filp_open open_namei() 按路径名查文件，靠 struct nameidata 这个持有路径信息的结构体
do_filp_open nameidata_to_filp() 拿填好的 nameidata 得到最终的 struct file；目的达到后 nameidata 立刻释放
open_namei path_lookup_open() / path_lookup_create() 路径查找。文件不存在且要新建时走后者；两者封装同一个查找函数，参数不同导致细节偏差
open_namei vfs_create() 带 O_CREAT 时造新 inode，核心一句 dir->i_op->create(dir, dentry, mode, nd)
open_namei path_to_nameidata() 填充 nameidata
open_namei may_open() 检查能不能打开：符号链接、只有写权限的目录不能打开；不支持 O_TRUNC 的文件要把 TRUNC 标志位显式关掉；允许 O_TRUNC 的则更新 inode 信息

vfs_create() 那一行值得单独说。这里造出来的 inode 只在内存里，它和磁盘上的 inode 的关系，就像内存里的文件和磁盘上的文件。此时它还不足以标志「物理文件创建成功」——只有 inode 回写到磁盘，才算真创建。想想自己以新建方式打开一个文件、写了一堆、最后没保存就关了：内存里的 inode 从新生到消失走了一遍，磁盘始终不知道有人动过创建文件的念头。原因就是 inode 没回写。

__path_lookup_intent_open() 是 path_lookup_open() 和 path_lookup_create() 的共同终点。遍历路径时逐层把每个组成部分解析成目录项：在 dcache 里就直接取，不在就实际读盘，从磁盘读出该目录项对应的索引节点，再建立 inode 和 dentry 的联系。循环到目标文件为止。拿到 inode，再由 inode 找到超级块，就知道这个文件在哪种文件系统上。读 inode 这一步会引发 VFS 和实际文件系统的一次交互：读 inode 的方法由超级块提供，而挂载时内存超级块的信息就是用实际文件系统的信息填的，其中包含实际文件系统定义的超级块操作函数表。顺着追到 ext3 的 ext3_read_inode()，会发现它一项重要工作就是按文件类型挂不同的 i_op / i_fop——就是第二节那段代码。

最后一步落在 nameidata_to_filp() 的子函数 __dentry_open：

c
static struct file *__dentry_open(struct dentry *dentry, struct vfsmount *mnt,
                                  int flags, struct file *f,
                                  int (*open)(struct inode *, struct file *))
{
    struct inode *inode;
    ……
    // 整个函数的工作在于填充一个 file 对象
    ……
    f->f_mapping = inode->i_mapping;
    f->f_dentry  = dentry;
    f->f_vfsmnt  = mnt;
    f->f_pos     = 0;
    // 把对应索引节点的文件操作函数集赋予文件对象的操作列表
    f->f_op      = fops_get(inode->i_fop);
    ……
    // 若文件自己定义了 open 操作，则执行这个特定的 open 操作
    if (!open && f->f_op)

    if (open) {
        error = open(inode, f);
        if (error)
            goto cleanup_all;
    }
    ……
    return f;
}

这段是 VFS 和实际文件系统交接的关键点。查 inode 时，实际文件系统按文件类型给了不同的 i_fop：普通文件一套，设备文件一套。__dentry_open 把这套东西赋给 f_op，往后读文件时 VFS 还是执行同一个 read 界面，但真正读的时候内核知道怎么区别对待。

注意 f->f_dentry / f->f_vfsmnt 这两行——它们反过来印证了第十节的判断：这段代码确实是 2.6.17 的，那时还没有 f_path。

现代内核差异：入口从 sys_open() 变成 SYSCALL_DEFINE3(open, ...)（具体在哪个版本完成宏化，未验证）；do_filp_open() 还在，内部走 path_openat() 和 open_last_lookups()；path_lookup_open / __path_lookup_intent_open 这套名字已经不在现代内核里；nameidata 内部结构大改，概念还在。

十四、一次 read() 走过了哪些层 #

sys_read() 从已打开的文件读数据。成功返回字节数，到文件尾返回 0。

前置条件是文件已经打开了。从第十三节可知，打开时内存里已经组装好一个 struct file，要对该文件执行的操作方法早已填进 f_op。所以读的时候 VFS 只做一点转换——由 fd 拿到对应的 file 对象，核心是一句 current->files->fd[fd]——然后就是这句：

c
file->f_op->read(file, buf, count, pos);

一层抽象，一个函数指针，把控制权交给实际文件系统。

层 代码 谁实现
用户空间 read(fd, buf, count) 应用程序
系统调用入口 sys_read() 内核，通用
fd → file current->files->fd[fd] 内核，通用
分发 file->f_op->read(...) 由 f_op 指向谁决定
普通文件 generic_file_read() → 页缓存 → a_ops->readpage() 文件系统 + 块层
字符设备 驱动自己的 read 你
块设备 def_blk_fops.read 块层

几条路径在这里分岔，分岔点是 f_op 里那个 read 指针到底指向谁。普通文件走页缓存（命中直接拷，不命中才触发 readpage 读盘）；字符设备一头扎进驱动；块设备走块层。同一个 read(2)，快慢和语义可以差很远。2.6.x 的 vfs_read() 里有个判断：f_op->read 为空就返回 -EINVAL。现代内核改成看 FMODE_CAN_READ，理由在 porting.rst 里写明了——不能直接调 ->read / ->write，要走 __vfs_read / __vfs_write 这类封装。

顺带回答原文留的问题：为什么能跨文件系统复制？把 vfat 上的 a.txt 拷成 ext3 上的 b.txt，是「读 a + 写 b」两个过程。打开文件时 VFS 已经知道各自属于哪个文件系统，操作时调各自的方法：VFS 用 vfat 的读方法把 a.txt 读进内存，把内存里的数据映射到 b.txt 的地址空间，再用 ext3 的写方法落盘。跨文件系统复制就是这么完成的，没有谁在做格式转换。

十五、注册一个文件系统：file_system_type 与 mount #

写字符设备不需要注册文件系统。但你要理解「一次 open 是怎么找到你的驱动的」，就得知道这层怎么进来的。

注册和注销的 API 只有两个：

c
#include <linux/fs.h>

extern int register_filesystem(struct file_system_type *);
extern int unregister_filesystem(struct file_system_type *);

传进去的 struct file_system_type 描述你的文件系统。往某个目录上挂文件系统时，VFS 会调该文件系统对应的 mount() 方法。mount() 返回的树的新 vfsmount 会被挂到挂载点上，此后路径解析走到这个挂载点就跳进那棵树的根。系统里注册了哪些文件系统，看 /proc/filesystems。

struct file_system_type 的现代形态（依据 6.6 的 VFS 文档）：

c
struct file_system_type {
    const char *name;
    int fs_flags;
    int (*init_fs_context)(struct fs_context *);
    const struct fs_parameter_spec *parameters;
    struct dentry *(*mount) (struct file_system_type *, int,
                             const char *, void *);
    void (*kill_sb) (struct super_block *);
    struct module *owner;
    struct file_system_type *next;
    struct hlist_head fs_supers;

    struct lock_class_key s_lock_key;
    struct lock_class_key s_umount_key;
    struct lock_class_key s_vfs_rename_key;
    struct lock_class_key s_writers_key[SB_FREEZE_LEVELS];
    struct lock_class_key i_lock_key;
    struct lock_class_key i_mutex_key;
    struct lock_class_key invalidate_lock_key;
    struct lock_class_key i_mutex_dir_key;
};

name 是文件系统名；fs_flags 装 FS_REQUIRES_DEV 这类标志；init_fs_context / parameters 属于新挂载 API；mount 挂新实例；kill_sb 关实例；owner 填 THIS_MODULE；next 填 NULL；fs_supers 是本类型所有 super_block 的 hlist；一堆 lock_class_key 只给 lockdep 用。

mount() 的契约得说清，写错了会挂死：参数 (fs_type, flags, dev_name, data) 和 mount(2) 对得上；返回所请求那棵树的根 dentry，失败返回 ERR_PTR(error)；必须拿到 superblock 的活跃引用，并且 superblock 处于锁定状态；常见副作用是创建新 superblock，但也可以返回已有文件系统的一棵子树。

fill_super() 才是多数文件系统真正写的地方。VFS 提供三个通用 mount() 实现：mount_bdev（住块设备上的）、mount_nodev（不依赖设备的，tmpfs 这类）、mount_single（所有挂载点共享同一实例）。fill_super() 要填的最要紧字段是 sb->s_op——那张 super_operations，它描述下一层实现。时序上这样走：模块 init 里 register_filesystem(&my_fs_type)；用户 mount 时 VFS 按名找到 file_system_type 调 ->mount()；fill_super 读磁盘超级块、初始化 s_op 和 i_op 模板、建根 inode；sb->s_root 就位，s_type 指回自己的 file_system_type；挂载点挂上后路径解析走到这里就跳进新文件系统；卸载走 ->kill_sb()，再到 put_super。

版本差异：2.6.x 用的是 ->get_sb()，porting.rst 记录「->get_sb() 和 ->mount() are gone. Switch to using the new mount API」——这句是分阶段写的，get_sb 先被 mount 取代，之后 mount 又被 fs_context 体系取代，6.6 里 mount 作为兼容路径还在。

十六、路径解析：link_path_walk 与 RCU 走查 #

open("/mnt/cdrom/foo/bar") 这一串字符怎么变成一个 struct dentry，是理解 dcache 的最佳入口。主循环是 link_path_walk()（2.6.x 语境，现代内核同名函数仍在，内部逻辑改过，未验证）。它按 / 切开路径一段段往下走：

情况 处理
段是 . 原地不动
段是 .. d_parent 上移一层；当前若是某个文件系统的根，要跳回挂载点所在的父文件系统
段命中 dcache 直接取，d_count 加一
段未命中 dcache 调当前目录 inode 的 i_op->lookup()，让实际文件系统去磁盘上找
lookup 找到 文件系统调 d_add() / d_instantiate() 建立联系，VFS 拿到 dentry
lookup 没找到 返回负目录项；要创建就交给后面的 create
走到的 dentry 是挂载点 d_mounted 非空，跳到那个 vfsmount 的根

这条循环把「路径字符串」和「四层对象」接上了：字符串 → dentry 链 → inode → super_block。走到最后一段，你就同时拿到了 dentry 和 inode，open 剩下的工作只是造 struct file。

现代内核在这条路上做了一个很重要的改造：rcu-walk。porting.rst 写得很清楚——VFS 现在会尝试用 rcu-walk 模式走路径，避免在 dentry 和 inode 上做原子操作、避免扩展性风险。

模式 拿锁吗 能阻塞吗 出问题怎么办
rcu-walk 不拿引用、不拿锁，只靠 RCU 保护 不能 返回 -ECHILD，退回 ref-walk 重来
ref-walk 拿引用、按需加锁 能 正常执行

这就是为什么 d_revalidate、d_hash、d_compare、permission 这些回调都被要求「rcu-walk 感知」：d_revalidate 在 flags & LOOKUP_RCU 时不能阻塞、不能写 dentry，搞不定就返回 -ECHILD；permission 看到 MAY_NOT_BLOCK 就知道自己在 rcu-walk 里，不许睡。2.6.17 时代没有这套东西。原文讲的「在 dcache 里就直接取，不在就实际读盘」是 ref-walk 语义，理解主干没问题，但别拿它解释现代内核里那些 -ECHILD 返回值。

十七、字符设备驱动的接入点：cdev 与 VFS 的关系 #

回到驱动作者最关心的问题：我只写了个 file_operations，凭什么 open("/dev/mydev") 会调到我的 .open？

步 发生什么 谁做的
1 设备节点在某个文件系统里，inode 是 S_ISCHR，i_rdev 记着主次设备号 mknod / devtmpfs / udev
2 该文件系统给设备节点挂的是 VFS 的 def_chr_fops，不是你的表 文件系统（init_special_inode）
3 open 走到 def_chr_fops.open，也就是 chrdev_open() VFS
4 chrdev_open() 用 inode->i_rdev 在字符设备表里查 struct cdev，记到 inode->i_cdev VFS（fs/char_dev.c）
5 用 cdev 里的 ops 替换掉 filp->f_op VFS
6 调你的 .open(inode, filp) 你的驱动
7 后续 read / write / ioctl 全部走你的表 你的驱动

第 2 步是很多人想不通的地方：设备节点的 file_operations 一开始不是你的。VFS 先用一张自己的 def_chr_fops 兜住，等 chrdev_open() 拿到设备号，才把 f_op 换成驱动的。6.6 的 VFS 文档原话是：打开字符设备或块设备节点时，多数文件系统会调 VFS 里的支撑函数，这些函数定位到需要的驱动信息，把文件系统的 file_operations 换成驱动的，然后再调新的 open()。

所以字符设备驱动的注册动作和文件系统注册完全无关：

你要做的 用的 API 说明
拿设备号 alloc_chrdev_region() 或 register_chrdev_region() 动态分配优先，别硬编码
初始化 cdev cdev_init(&my_cdev, &my_fops) 把 file_operations 挂到 cdev 上
加进内核 cdev_add(&my_cdev, dev, count) 从此设备号能查到你的 cdev
老接口一把梭 register_chrdev(major, name, &my_fops) 内部帮你做完上面三步，但占满整个主设备号
卸载 cdev_del() + unregister_chrdev_region() 顺序别反

对照一下文件系统作者和字符设备驱动作者各自要填什么：

你写的 文件系统作者 字符设备驱动
super_operations 必填 不填
inode_operations 必填 不填
dentry_operations 少数要填 不填
file_operations 填 填，这是唯一的主战场
file_system_type 必填 不填

一个能跑的最小骨架，到「注册成功、能 open」为止：

c
static int mydev_open(struct inode *inode, struct file *filp)
{
    /* 把私有结构挂到 filp->private_data，release 里取回并释放 */
    filp->private_data = ...;
    return 0;
}

static ssize_t mydev_read(struct file *filp, char __user *buf,
                          size_t count, loff_t *ppos)
{
    /* 返回实际拷贝的字节数；出错返回负 errno */
    return 0;
}

static int mydev_release(struct inode *inode, struct file *filp)
{
    return 0;
}

static const struct file_operations mydev_fops = {
    .owner   = THIS_MODULE,
    .open    = mydev_open,
    .read    = mydev_read,
    .release = mydev_release,
};

.owner = THIS_MODULE 不是可选项。少了它，模块卸载后内核里还留着指向已释放代码段的函数指针，下一次 read 就是一次野跳。
