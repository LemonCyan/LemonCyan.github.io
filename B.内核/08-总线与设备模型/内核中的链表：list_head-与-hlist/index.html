Linux 内核里链表无处不在。struct device 挂在总线的设备链上，struct task_struct 挂在进程表里，struct inode 挂在超级块的 inode 链上，协议栈的哈希桶里挂着一堆 struct sock。这些表全由两套结构撑起来：list_head 和 hlist。两者都在 include/linux/list.h，代码加起来不到一千行，是读内核源码的前置条件。

本文讲四件事：这两个结构长什么样，为什么非得长这样，list.h 里那些接口的真实实现，以及怎么写出一个能编译加载的内核模块去用它们。

不谈的：RCU 版接口（list_for_each_entry_rcu、hlist_for_each_entry_rcu）在第十一章只划一条边界线；不讲 klist、slist、红黑树、XArray；不讲自旋锁与 RCU 的内部机制，并发只说「该加锁的地方要加锁」。

要往下读的：设备模型怎么把 struct device 挂进 list_head，看本目录的「总线、设备与驱动模型」；hlist 在网络栈里的实际用法，看 F.通信与协议/01-TCPIP与套接字 下的协议栈分层几篇。

前置：会读 C 的结构体指针，知道 offsetof 在算什么，见过 module_init / module_exit。

一、内核为什么需要自己的链表 #

链表是物理存储上不连续的结构。元素的逻辑顺序不靠地址相邻，靠指针串起来。结点在运行时动态生成，用完就放。

它换掉的是「必须预先知道数据规模」这个约束，内存按需分配。付出的代价有两个：丢掉随机访问，每次定位都得从头走指针；多出指针域的空间开销，一个结点存两个指针是常事。

按指针域的组织方式，链表分三种形态。

形态 指针域 遍历方向 尾结点特征 判空方式
单链表 next 只能从头向后 next == NULL head == NULL
双向链表 next + prev 双向 next == NULL head == NULL
双向循环链表 next + prev 双向 绕回第一个结点 head->next == head

单链表只有 next，走到尾就停。双向链表加了 prev，能从两头走。把首结点的 prev 指到尾结点、尾结点的 next 指回首结点，就成了双向循环链表——从任意一个结点出发，沿任一方向都能走遍全表，空表则退化成一个自己指向自己的环。

内核选了第三种。原因是循环结构让「插入」和「删除」不需要对首尾做特判：头结点永远存在，谁都有前驱和后继，边界条件被吃掉了一整类。

这三个形态本身没什么稀奇，教材上都有。内核动手改的是另一个地方。

数据组织方式的翻转 #

课本上的链表定义长这样（单链表为例）：

c
struct list_node {
	struct list_node *next;
	ElemType data;
};

要串 ElemType A，写一套；要串 ElemType B，再写一套。节点类型里写死了数据域的类型，链表代码和数据强绑定。

内核面对的场景是：同一套「把东西串起来」的需求，出现在几百个结构上。设备、驱动、inode、socket、路由表项、挂载点……如果每个类型自带一套 xxx_list_add / xxx_list_del / xxx_list_for_each，drivers/ 和 net/ 会膨胀到没法维护。

内核的解法是：链表节点不带数据。

c
struct list_head {
	struct list_head *next, *prev;
};

两个指针，都指向同类型。没有数据域，没有类型标记，没有任何业务语义。

需要链表的数据结构，在自己的定义里塞一个 struct list_head 成员。链表代码只认这个成员，不认宿主是谁。于是同一份 list_add() 能往设备表里插设备，也能往 inode 链上插 inode。

这就是 C 语言里做出「泛型 + 复用」的经典手法。C++ 用模板让容器对任意类型实例化，内核用「把节点嵌进宿主 + 从节点地址反算宿主地址」达到同样的效果，只是反算那一步得手工做——用 container_of，第四章细讲。

3.14 版本的 list_head 定义在 include/linux/types.h 里，后来的版本挪到了 include/linux/list.h 顶部。本文的代码以现在的 list.h 为准，涉及旧版本差异的地方会单独标出来。

二、list_head：双向循环链表 #

结构定义只有两行：

c
struct list_head {
	struct list_head *next, *prev;
};

next 指向后一个结点，prev 指向前一个结点。两个指针的类型都是 struct list_head *，不是 void *，也不是宿主类型。这个选择很重要——它让链表操作完全不依赖宿主类型，代价是把类型恢复的责任推给了调用方。

它被数据包含，而不是包含数据 #

list_head 不是拿来单独用的。它必须嵌进某个宿主结构：

c
struct file_node {
	char c;
	struct list_head node;
};

对比两种组织方式：

c
/* 课本式：链表结点包住数据 */
struct list_node {
	struct list_node *next;
	ElemType data;
};

/* 内核式：数据包住链表结点 */
struct file_node {
	struct list_head list;
	ElemType data;
};

list_head 最精妙的地方就是这一句：它不包含数据，而是被数据包含。

由此带来的直接后果是：链表里存的地址不是宿主结构的地址，而是宿主中那个 list_head 成员的地址。

text
        struct file_node（宿主，编译器会插入填充字节）
        +-------------------------------+
        |  char c;                      |  offset 0
        |  ...padding...                |
        |  struct list_head list;       |  offset 8（举例）
        |    +------------------------+ |
        |    | next ----------------------> 下一个宿主的 list
        |    | prev ----------------------> 上一个宿主的 list
        |    +------------------------+ |
        |  ElemType data;               |
        +-------------------------------+
                 ^
                 |
        head->next 指向这里，不是指向宿主首地址

想拿到 struct file_node *，得把 list 的地址往回减掉 list 在结构里的偏移量。这一步由 container_of 完成，第四章展开。

这个设计的收益是彻底的解耦：list.h 不需要知道 struct file_node 存在，struct file_node 也不需要为链表写任何专属函数。同一个宿主还能同时挂进多条链表——只要嵌多个 list_head 成员，比如 struct sock 就有 sk_node、sk_bind_node、sk_null_node 等多套挂载点，同时被哈希表、绑定链、NULL 链引用。

空链表：自己指向自己 #

内核没有专门的链表头类型。链表头就是一个 list_head，它不承载数据，只当哨兵。

初始化有三个入口：

c
#define LIST_HEAD_INIT(name) { &(name), &(name) }

#define LIST_HEAD(name) \
	struct list_head name = LIST_HEAD_INIT(name)

static inline void INIT_LIST_HEAD(struct list_head *list)
{
	list->next = list;
	list->prev = list;
}

LIST_HEAD(my_list); 展开后是：

c
struct list_head my_list = { &my_list, &my_list };

next 和 prev 都指向自己。这就是空链表——一个长度为 1 的环，只含哨兵。

INIT_LIST_HEAD() 做同一件事，区别在运行期可用：

c
struct list_head head;

INIT_LIST_HEAD(&head);        /* 栈上或 kmalloc 出来的头，运行期初始化 */

LIST_HEAD() 是声明并初始化，只能用在定义处；INIT_LIST_HEAD() 是赋值，可以重复调用。搞混这两个是最常见的编译错误来源之一：把 LIST_HEAD(&head) 写进函数体，会得到一个「声明了一个叫 &head 的变量」之类的报错。

判空直接用「next 是否指回自己」：

c
static inline int list_empty(const struct list_head *head)
{
	return head->next == head;
}

空表只有哨兵一个结点，head->next == head 成立。表里有一个元素时，head->next 指向那个元素的 list 成员，head->prev 也指向同一个成员，此时 head->next == head->prev 但都不等于 head。

头结点自身不存数据。遍历时要跳过它——所有遍历宏的终止条件都写成「pos 又回到了 head」，靠的就是这一点。

内存布局：头结点和第一个元素 #

往空表里插第一个元素，__list_add(new, head, head->next) 会让：

text
插入前（空表）：
    head.next ──┐
    head.prev ──┴──> &head

插入 A 之后：
    head.next ──> &A.list
    head.prev ──> &A.list
    A.list.next ──> &head
    A.list.prev ──> &head

再插 B 到表尾（list_add_tail）：

text
    head.next ──> &A.list ──> &B.list ──┐
         ^                              │
         └──────────────────────────────┘
    head.prev ──> &B.list

环闭合。最后的 &B.list.next 指回 &head，&head.prev 指回 &B.list。

这里要记住一个容易翻车的点：链表头本身也是一个结点，它参与链接。所以「长度为 N 的链表」在结构上是 N+1 个 list_head 串成的环。写 while (pos->next) 这种判空是错的，因为环里永远没有 NULL，只有回到哨兵。

三、list_head 的几个精妙之处 #

把前面几段拆开看，这个设计有四个值得单独拎出来的点。

第一，节点与数据彻底分离。 链表代码只认 struct list_head，宿主是什么类型它不知道也不关心。加一个新型号的数据结构要挂链，只需在结构体里加一行 struct list_head list;，一行代码都不用多写。这是「复用」在 C 里的最高效形态——不是靠语言机制，靠数据布局。

第二，一个对象可以同时属于多条链。 因为挂载点是宿主的成员，而宿主可以有多个成员。struct sock 同时挂在协议栈的 established 哈希表、bind 哈希表、监听队列上，各自用一个 hlist_node / list_head。一个对象进几个容器，就嵌几个节点，容器之间互不干扰。

第三，哨兵头结点吃掉边界的特判。 双向循环链表里没有 NULL，每个结点都有前驱和后继。插入不用判「是不是第一个」，删除不用判「是不是最后一个」。__list_add() 四行代码就能覆盖所有位置。

第四，接口全是 static inline。 没有函数调用开销，编译器直接内联展开。代价是代码体积，好处是这些操作能出现在内核最热的路径上而不心疼。

用宏而不是函数来做遍历，是被类型逼的。list_for_each_entry() 需要在循环里把 list_head * 转成宿主指针，转换目标类型由调用方传入，函数做不到这件事（typeof 推导和结果类型都要在调用点确定），只能写成宏。

四、container_of：从成员反推宿主 #

链表中存的是 list_head 成员地址。要拿到宿主，得做一次地址反算。这个转换是整篇文章的技术核心，理解它，剩下的都是背接口。

入口是先有的 list_entry 宏：

c
#define list_entry(ptr, type, member) \
	container_of(ptr, type, member)

三个参数：ptr 是链表里存的地址，也就是宿主中 list_head 成员的地址；type 是宿主类型；member 是 list_head 成员在宿主里的变量名。

container_of 定义在 include/linux/kernel.h，offsetof 定义在 include/linux/stddef.h。这两个宏不只服务链表，内核里凡是要「从成员反推宿主」的地方都用它们。

第一步：offsetof 算偏移量 #

c
#define offsetof(TYPE, MEMBER) ((size_t) &((TYPE *)0)->MEMBER)

拆开看。(TYPE *)0 把 0 地址强制转成 TYPE * 类型的指针，得到一个「指向地址 0 的 TYPE 结构」的指针。->MEMBER 访问它的成员。& 取这个成员的地址。最后 (size_t) 转成整数。

0 地址的内容不能读，但 0 地址的地址可以取。整个表达式里没有任何访存——编译器在编译期就算完了，结果是一个常量：MEMBER 在 TYPE 里的字节偏移。

代入具体结构：

c
struct file_node {
	char c;
	struct list_head node;
};

offsetof(struct file_node, node) 展开成：

c
((size_t)&((struct file_node *)0)->node)

换个写法更直白：

c
struct file_node *p = NULL;

&p->node;   /* 就是 node 相对结构体首地址的偏移 */

p 是 0，p->node 的地址自然就是 node 相对 0 的偏移量。offsetof 做的就是这个。

对上面的结构，假设 char 占 1 字节、指针占 8 字节、list_head 对齐到 8，那么 c 在 offset 0，填充 7 字节，node 在 offset 8。offsetof(struct file_node, node) 返回 8。

第二步：地址减去偏移量 #

c
#define container_of(ptr, type, member) ({ \
	const typeof( ((type *)0)->member ) *__mptr = (ptr); \
	(type *)( (char *)__mptr - offsetof(type,member) );})

两个语句，用 GCC 的语句表达式 ({ ... }) 包起来，整个宏的值是最后一个表达式的值。

第一个语句声明中间变量 __mptr，类型是「宿主中 member 成员的类型」的指针，也就是 struct list_head *，初始化为传进来的 ptr。typeof( ((type *)0)->member ) 靠的又是 0 地址技巧：不访问数据，只借编译器推导出成员的类型。

第二个语句做减法。(char *)__mptr 把地址转成字节指针，减去偏移量，再 (type *) 转回宿主指针。

为什么必须转成 char * #

指针算术以「所指类型的大小」为单位。如果直接写 __mptr - offsetof(...)，而 __mptr 是 struct list_head *，编译器会按 sizeof(struct list_head) 即 16 字节为单位去减——偏移 8 会被理解成减掉 8 个结点，也就是 128 字节，地址飞到天上去。

char 的大小定义为 1 字节，转成 char * 之后，减法就按字节算，偏移量是多少就减多少。

text
      宿主首地址                     list_head 成员地址
          |                                 |
          v                                 v
    +-----+---------------------------------+-----------+
    | c   | padding | struct list_head node |   data    |
    +-----+---------------------------------+-----------+
          |<------ offsetof(...) = 8 ------->|
                                          ^
                                          |
                            __mptr 在这里，减去 8 得到宿主首地址

为什么要中间变量 #

ptr 在表达式里只出现一次，那为什么还要绕一道 __mptr？

因为传进来的实参允许带副作用。如果写成

c
#define BAD_CONTAINER_OF(ptr, type, member) \
	(type *)((char *)(ptr) - offsetof(type, member))

调用方传 container_of(p++, ...)，p++ 在展开后只出现一次，看着没事。但更复杂的表达式比如 (type *)((char *)(ptr) - offsetof(type, member)) 里如果 ptr 出现两次（老版本的某些实现确实这样），副作用就会被求值两次，自增跑两遍。

先把 ptr 落到一个局部变量里，副作用只发生一次，后面怎么用都安全。

现代内核的 container_of 还加了一道编译期类型检查：

c
#define container_of(ptr, type, member) ({				\
	void *__mptr = (void *)(ptr);					\
	static_assert(__builtin_types_compatible_p(typeof(*(ptr)),	\
			 typeof(((type *)0)->member)),			\
		      "pointer type mismatch in container_of()");	\
	((type *)(__mptr - offsetof(type, member))); })

传错的指针类型在编译期就报出来，不用等到运行时地址错乱才发现。

完整链条 #

把三个宏串起来看，一次 list_entry 调用实际发生的事：

text
head->next  ──> 某个宿主里的 &item->list
                     │
                     │  typeof 推导出成员类型为 struct list_head
                     │  减去 offsetof(宿主, list)
                     ▼
                &item（宿主首地址）
                     │
                     │  (type *) 转换
                     ▼
                struct demo_item *

用法：

c
struct list_head *pos;
struct demo_item *item;

list_for_each(pos, &my_list) {
	item = list_entry(pos, struct demo_item, list);
	/* 现在 item 是完整的宿主，item->id、item->name 都能访问 */
}

写 list_entry(pos, struct demo_item, list) 时，第三个参数 list 必须是宿主里那个 list_head 成员的真实名字。写错成别的成员名，编译能过（只要那个成员也是 list_head 类型），运行起来地址全错——这是排查起来最费时间的一类 bug。

list_entry 和 list_for_each() 几乎总是成对出现。内核干脆把这个组合封成了一个宏，见第五章。

五、list_head 的常用接口 #

所有接口都在 include/linux/list.h，全部 static inline。分成插入、删除、判空、取宿主、遍历五组。

插入：两个公开接口，一个内部实现 #

真正干活的只有 __list_add()。它把 new 插进 prev 和 next 这两个已知相邻结点之间：

c
static inline void __list_add(struct list_head *new,
			      struct list_head *prev,
			      struct list_head *next)
{
	next->prev = new;
	new->next = next;
	new->prev = prev;
	prev->next = new;
}

四行赋值，没有循环，没有判断。前后两个结点由调用者保证相邻。

两个公开接口都是它的薄包装：

c
/* 插在 head 之后，即表头（LIFO，适合栈） */
static inline void list_add(struct list_head *new, struct list_head *head)
{
	__list_add(new, head, head->next);
}

/* 插在 head 之前，即表尾（FIFO，适合队列） */
static inline void list_add_tail(struct list_head *new, struct list_head *head)
{
	__list_add(new, head->prev, head);
}

因为链表是环，head->prev 就是尾结点，head->next 就是首结点。所以「表头插入」= 插在 head 和 head->next 之间，「表尾插入」= 插在 head->prev 和 head 之间。两者的区别只在这两个实参。

看一次实际调用：

c
struct demo_item *item = kzalloc(sizeof(*item), GFP_KERNEL);

list_add(&item->list, &my_list);        /* item 成为首元素 */
list_add_tail(&item->list, &my_list);   /* item 成为尾元素 */

注意传的是 &item->list，不是 item。链表只接收成员地址。

删除：list_del 与 list_del_init #

c
static inline void __list_del(struct list_head *prev, struct list_head *next)
{
	next->prev = prev;
	prev->next = next;
}

static inline void list_del(struct list_head *entry)
{
	__list_del(entry->prev, entry->next);
	entry->next = LIST_POISON1;
	entry->prev = LIST_POISON2;
}

__list_del() 让前驱和后继互相指过去，把 entry 从环里摘出来。摘完之后 entry 的两个指针还指着原来的邻居，那对邻居已经不认它了。

list_del() 多做一步：把 entry->next / entry->prev 写成 LIST_POISON1 / LIST_POISON2。这两个是内核故意选的非法地址（0x00100100 和 0x00200200 加上 POISON_POINTER_DELTA 偏移）。

3.14 时代的代码里它们叫 LIST_POSITION1 / LIST_POSITION2，作用一样。

为什么要毒化？为了让「删完还用」立刻崩。节点被摘下来后如果代码还顺着 entry->next 走，访问 0x00100100 会直接触发页故障，现场就在出问题的那一行。如果不毒化，指针指向一块仍然可读的邻居内存，程序会安静地跑下去，等到别处才炸，排查成本高一个量级。

list_del_init() 是另一条路：

c
static inline void list_del_init(struct list_head *entry)
{
	__list_del(entry->prev, entry->next);
	INIT_LIST_HEAD(entry);
}

摘下来之后把节点重新初始化成「自己指向自己」的空环。这样它还是一个合法结点，可以再用 list_add() 挂到别处，也可以用 list_empty() 判断它当前没挂在任何表上。

选哪个？节点删完就 kfree()，用 list_del()；节点还要复用或者你不知道它挂在哪条表上，用 list_del_init()。

判空：list_empty 与 list_empty_careful #

c
static inline int list_empty(const struct list_head *head)
{
	return head->next == head;
}

static inline int list_empty_careful(const struct list_head *head)
{
	struct list_head *next = head->next;

	return (next == head) && (next == head->prev);
}

list_empty() 只看 next。单线程下够用。

list_empty_careful() 把 next 先存到局部变量，再判断 next == head && next == head->prev。它防的是另一个 CPU 正在改同一条链，导致 next 和 prev 短暂不一致的窗口。

但代码注释自己承认这个保护能力有限：只有对方也走 list_del_init() 这类「一次写两边」的路径才成立。别的 CPU 要是先改了 next 再改 prev，读到的中间态照样骗人。并发访问链表要加锁，list_empty_careful() 不能替代锁。

取宿主：list_entry 的四个常用封装 #

c
#define list_first_entry(ptr, type, member) \
	list_entry((ptr)->next, type, member)

#define list_last_entry(ptr, type, member) \
	list_entry((ptr)->prev, type, member)

#define list_next_entry(pos, member) \
	list_entry((pos)->member.next, typeof(*(pos)), member)

#define list_prev_entry(pos, member) \
	list_entry((pos)->member.prev, typeof(*(pos)), member)

list_first_entry() / list_last_entry() 的入参是链表头，返回第一个/最后一个宿主。空表上调用它们是错的——空表的 head->next 就是 head 自己，转出来的「宿主」是哨兵前面的一块内存。调之前先 list_empty()。

list_next_entry() / list_prev_entry() 的入参是宿主指针，返回相邻宿主。它们内部靠 typeof(*(pos)) 自动拿到宿主类型，不用再手写 type。

遍历：list_for_each 与 list_for_each_entry #

c
#define list_for_each(pos, head) \
	for (pos = (head)->next; pos != (head); pos = pos->next)

就一个 for 循环。pos 是 struct list_head *，从哨兵的后继开始，每轮走一步 next，走回哨兵就停。

老版本的写法带 prefetch：

c
#define list_for_each(pos, head) \
	for (pos = (head)->next; prefetch(pos->next), pos != (head); \
	     pos = pos->next)

prefetch() 是 GCC 的 __builtin_prefetch()，提前把下一个结点的缓存行拉进来，属于纯性能优化，去掉不影响正确性。

list_for_each() 只给你 list_head *，想访问数据还得套一层 list_entry()：

c
struct list_head *pos;
struct demo_item *item;

list_for_each(pos, &my_list) {
	item = list_entry(pos, struct demo_item, list);
	printk("id=%d\n", item->id);
}

这个组合太常见，内核封成了 list_for_each_entry()：

c
#define list_for_each_entry(pos, head, member)				\
	for (pos = list_entry((head)->next, typeof(*pos), member);	\
	     &pos->member != (head);					\
	     pos = list_entry(pos->member.next, typeof(*pos), member))

三处变化：pos 变成宿主指针类型（靠 typeof(*pos) 推出来）；终止条件从 pos != head 变成 &pos->member != head，因为 pos 现在是宿主指针，要拿它的成员地址去和哨兵比；步进改成从 pos->member.next 反推下一个宿主。

用起来干净得多：

c
struct demo_item *item;

list_for_each_entry(item, &my_list, list)
	printk("id=%d name=%s\n", item->id, item->name);

type 参数消失了，因为 typeof(*pos) 能从 pos 的声明里推出来。这也是这类遍历只能写成宏的原因——函数没法凭空知道调用方想要的类型。

六、list_head 的变体操作 #

基础接口之外，list.h 还提供一批「一步到位」的变体。它们内部都是 __list_del() / __list_add() 的组合，理解原理之后不用背。

搬移：list_move 与 list_move_tail #

把一个节点从当前链表摘下来，挂到另一条链表上：

c
static inline void list_move(struct list_head *list, struct list_head *head)
{
	__list_del(list->prev, list->next);
	list_add(list, head);
}

static inline void list_move_tail(struct list_head *list, struct list_head *head)
{
	__list_del(list->prev, list->next);
	list_add_tail(list, head);
}

list_move(&item->list, &other_list) 的效果是：item 从原表消失，成为 other_list 的首元素。两条链表的哨兵不用变。

两个调用都省掉了「先 list_del() 再 list_add()」的中间状态，也不会误用毒化指针。

替换：list_replace #

把一个节点就地换成另一个：

c
static inline void list_replace(struct list_head *old,
				struct list_head *new)
{
	new->next = old->next;
	new->next->prev = new;
	new->prev = old->prev;
	new->prev->next = new;
}

static inline void list_replace_init(struct list_head *old,
				     struct list_head *new)
{
	list_replace(old, new);
	INIT_LIST_HEAD(old);
}

接替 old 的位置，前后邻居的指针改指 new。list_replace_init() 额外把 old 重置成空环。

这组接口在「热替换」场景里用：要换一个配置项，但它在链表里的位置有意义，不能摘了再插到表尾。

合并：list_splice 系列 #

把整条 list 挂到 head 上。先看内部实现：

c
static inline void __list_splice(struct list_head *list,
				 struct list_head *head)
{
	struct list_head *first = list->next;
	struct list_head *last = list->prev;
	struct list_head *at = head->next;

	first->prev = head;
	head->next = first;

	last->next = at;
	at->prev = last;
}

四步：list 的首元素的前驱改指 head；head->next 改指 list 的首元素；list 的尾元素的后继改指 head 原来的首元素；那个首元素的前驱改指 list 的尾元素。

结果是 list 的全部内容被塞进 head 和它原来的首元素之间，新表以 list 的首元素打头，list 的尾元素接上 head 原来的首元素。

c
static inline void list_splice(struct list_head *list, struct list_head *head)
{
	if (!list_empty(list))
		__list_splice(list, head);
}

static inline void list_splice_init(struct list_head *list,
				    struct list_head *head)
{
	if (!list_empty(list)) {
		__list_splice(list, head);
		INIT_LIST_HEAD(list);
	}
}

list_splice() 只搬内容，搬完 list 这个哨兵的 next / prev 还指着原来的结点——它变成了一个悬空的、指向别人家元素的头，误用会出事。list_splice_init() 多调一次 INIT_LIST_HEAD(list)，把源表重置成合法空表。

除了明确要靠源表指针做点什么的场合，一律用 list_splice_init()。

新版本内核把 __list_splice() 拆成了三参数形式 __list_splice(list, prev, next)，为了支持挂到表尾：

c
static inline void list_splice_tail(struct list_head *list,
				    struct list_head *head)
{
	if (!list_empty(list))
		__list_splice(list, head->prev, head);
}

list_splice_tail() 把 list 挂到 head 的尾部。看到三参数版本不用奇怪，原理和两参数的一样，只是把「插入点」从单一 head 扩成了 prev 和 next 两个已知相邻结点。

截断：list_cut_position #

把一条链从中间切开，前半段搬到新表：

c
static inline void __list_cut_position(struct list_head *list,
		struct list_head *head, struct list_head *entry)
{
	struct list_head *new_first = entry->next;
	list->next = head->next;
	list->next->prev = list;
	list->prev = entry;
	entry->next = list;
	head->next = new_first;
	new_first->prev = head;
}

切点在 entry：head 到 entry（含）留在原表，entry 之后的元素搬到 list。

外面包一层边界处理：

c
static inline void list_cut_position(struct list_head *list,
		struct list_head *head, struct list_head *entry)
{
	if (list_empty(head))
		return;
	if (list_is_singular(head) &&
		(head->next != entry && head != entry))
		return;
	if (entry == head)
		INIT_LIST_HEAD(list);
	else
		__list_cut_position(list, head, entry);
}

空表直接返回；只有一个元素且切点不是它，返回；切点就是哨兵本身，说明要搬的是空集，把目标初始化成空表。

反向与接续遍历 #

从尾往头走：

c
#define list_for_each_prev(pos, head) \
	for (pos = (head)->prev; pos != (head); pos = pos->prev)

#define list_for_each_entry_reverse(pos, head, member)			\
	for (pos = list_last_entry(head, typeof(*pos), member);		\
	     &pos->member != (head);					\
	     pos = list_prev_entry(pos, member))

早期的内核把 list_for_each_entry_reverse 直接写成 list_entry((head)->prev, typeof(*pos), member) 和 list_entry(pos->member.prev, typeof(*pos), member)，语义完全一致，只是没用 list_last_entry() / list_prev_entry() 这两个封装。看到老代码不用困惑。

从中间某个位置接着往后走：

c
#define list_for_each_entry_continue(pos, head, member)		\
	for (pos = list_next_entry(pos, member);		\
	     &pos->member != (head);				\
	     pos = list_next_entry(pos, member))

注意它是从 pos 的下一个开始，不是从 pos 本身。想包含当前节点，得用 list_for_each_entry_from()（新版本才有）。

还有一种常见写法：某个游标允许为空，第一次调用从表头开始，之后从游标继续。内核给了 list_prepare_entry()：

c
#define list_prepare_entry(pos, head, member) \
	((pos) ? : list_entry(head, typeof(*pos), member))

?: 是 GNU 扩展，pos 非空就取 pos，否则取 list_entry(head, ...)——把哨兵地址当成宿主地址用，这样下一轮 continue 里的 list_next_entry() 正好落到第一个真实元素上。

配合起来是标准写法：

c
pos = list_prepare_entry(pos, &my_list, list);
list_for_each_entry_continue(pos, &my_list, list) {
	/* 处理 pos */
}

pos 为 NULL 时从表头开始，非空时从 pos 之后开始。

位置判断 #

c
static inline int list_is_last(const struct list_head *list,
			       const struct list_head *head)
{
	return list->next == head;
}

static inline int list_is_singular(const struct list_head *head)
{
	return !list_empty(head) && (head->next == head->prev);
}

list_is_last() 判断给定节点是不是最后一个——它的 next 指向哨兵。list_is_singular() 判断链表是否只有一个元素——首尾指向同一个节点。

七、hlist：哈希链表 #

hlist 是内核里另一套链表，专门给哈希表用。它同样定义在 include/linux/list.h，同一份头文件里两套结构并存。

它由两个结构配合：

c
/* 哈希桶的头结点 */
struct hlist_head {
	struct hlist_node *first;   /* 指向该桶的第一个结点 */
};

/* 哈希桶的普通结点 */
struct hlist_node {
	struct hlist_node *next;    /* 指向下一个结点，末尾为 NULL */
	struct hlist_node **pprev;  /* 指向前一个结点的 next 指针的地址 */
};

两套结构，而不是一套。这就是 hlist 和 list_head 最根本的分歧。

为什么会多出一个 hlist_head？因为哈希表的桶数量大。内核里一张哈希表的桶数动辄几千上万（struct sock 的 established 表按内存规模伸缩，inode 哈希表按页数算）。如果每个桶都用 struct list_head 做哨兵，光桶头就吃掉 16 字节 × 桶数；而桶里大多数时候是空的，这 16 字节基本白扔。

hlist_head 只有一个 first 指针，8 字节，正好省一半。桶越多，省得越明显。

代价是：桶头和普通结点类型不同，不再是同一个类型，list_head 那套「哨兵也是结点」的对称性没了。hlist 的全部复杂度都来自这个不对称。

text
     hlist_head（桶头，8 字节）
     +-----------+
     | first ----+----+
     +-----------+    |
                      v
     hlist_node（普通结点，16 字节）
     +-----------+     +-----------+     +-----------+
     | next -----+---->| next -----+---->| next =NULL|
     | pprev ----+--+  | pprev ----+--+  | pprev ----+--+
     +-----------+  |  +-----------+  |  +-----------+  |
          ^         |       ^         |        ^        |
          |         |       |         |        |        |
          +---------+-------+---------+--------+--------+
            pprev 指向前一个 next 的地址

八、hlist_head 与 hlist_node 的不对称设计 #

先把「不对称」这件事讲明白。

hlist_head 里只有 first，没有 next，没有 prev。hlist_node 里有 next，还有一个二级指针 pprev。

next 好理解，指向下一个兄弟，末尾是 NULL，不绕环。

pprev 是关键。它不是指向前一个结点，而是指向前一个结点的 next 指针的地址。

对第一个结点来说，前一个「结点」其实是桶头 hlist_head，而桶头没有 next 域，只有 first 域。pprev 就指向 &h->first。因为 first 和 next 都是 struct hlist_node * 类型，取它们的地址得到的都是 struct hlist_node **，类型上完全一致。

这一步类型上的凑合，换来了代码路径上的统一。

删除：一条路径通吃 #

c
static inline void __hlist_del(struct hlist_node *n)
{
	struct hlist_node *next = n->next;
	struct hlist_node **pprev = n->pprev;

	*pprev = next;
	if (next)
		next->pprev = pprev;
}

*pprev = next 这一句同时覆盖两种情况：

  • 删的是桶里第一个结点：pprev == &h->first，*pprev = next 就是 h->first = next，桶头指向第二个结点。
  • 删的是中间或末尾结点：pprev == &prev->next，*pprev = next 就是 prev->next = next，前驱跨过它。

后面那个 if (next) 也是必需的：删的是最后一个结点时 next 是 NULL，没有下一个结点可以改 pprev。

删除第一个普通结点和删除非第一个普通结点，代码完全一样。 没有 if (this is the first) 分支。

反证：如果用 next/prev #

假设 hlist_node 老老实实写成双向链表：

c
struct hlist_node_bad {
	struct hlist_node_bad *next;
	struct hlist_node_bad *prev;
};

删除一个普通结点的标准写法是：

c
n->next->prev = n->prev;
n->prev->next = n->next;

删中间结点没事。删桶里第一个结点就出问题：它的 prev 得指向桶头，可桶头是 hlist_head 类型，里面没有 next 域，n->prev->next 这一句访问不到任何合法字段。

要么给桶头加一个 next 域（那就退化成 16 字节，省内存的初衷没了），要么在删除处加一句 if (n->prev == NULL) h->first = n->next; else ... 的特判（每个删除点都得判，还容易漏）。

插入同理。往空桶里插第一个结点时，要改的是 h->first；往非空桶里插，要改的是某个结点的 next。两处代码不同，就得两套分支。

pprev 把「改谁的指针」这件事抽象成了一个指针的指针，两种情况都是「往 *pprev 里写」，于是分支消失。

插入：pprev 的两行赋值 #

c
static inline void hlist_add_head(struct hlist_node *n, struct hlist_head *h)
{
	struct hlist_node *first = h->first;

	n->next = first;
	if (first)
		first->pprev = &n->next;
	h->first = n;
	n->pprev = &h->first;
}

n->pprev = &h->first 是整段的关键。新结点成为桶里第一个，它的前驱「指针槽位」就是桶头的 first 域。

first ? first->pprev = &n->next : ... 这半句也要注意顺序：先把 n->next 赋成 first，才能取 &n->next 交给 first->pprev。顺序反过来，first->pprev 就指向了错误的槽位。

九、hlist 的常用接口 #

初始化有四个入口，两两配对。

c
/* 桶头 */
#define HLIST_HEAD_INIT { .first = NULL }
#define HLIST_HEAD(name) struct hlist_head name = { .first = NULL }
#define INIT_HLIST_HEAD(ptr) ((ptr)->first = NULL)

/* 普通结点 */
static inline void INIT_HLIST_NODE(struct hlist_node *h)
{
	h->next = NULL;
	h->pprev = NULL;
}

INIT_HLIST_NODE() 把 pprev 置 NULL，这里有个约定：pprev == NULL 就表示这个结点不在任何桶里。判断函数就是靠它：

c
static inline int hlist_unhashed(const struct hlist_node *h)
{
	return !h->pprev;
}

static inline int hlist_empty(const struct hlist_head *h)
{
	return !h->first;
}

hlist_unhashed() 判结点，hlist_empty() 判桶。

删除接口：

c
static inline void hlist_del(struct hlist_node *n)
{
	__hlist_del(n);
	n->next = LIST_POISON1;
	n->pprev = LIST_POISON2;
}

static inline void hlist_del_init(struct hlist_node *n)
{
	if (!hlist_unhashed(n)) {
		__hlist_del(n);
		INIT_HLIST_NODE(n);
	}
}

hlist_del() 走毒化路线，删完即废。hlist_del_init() 先查 hlist_unhashed()，已经不在桶里就什么都不做——这让它可以被重复调用而不出错，清理路径上特别好用。

插入三个位置：

c
/* 插到桶头，成为第一个结点 */
static inline void hlist_add_head(struct hlist_node *n, struct hlist_head *h);

/* 插到 next 之前 */
static inline void hlist_add_before(struct hlist_node *n,
				    struct hlist_node *next)
{
	n->pprev = next->pprev;
	n->next = next;
	next->pprev = &n->next;
	*(n->pprev) = n;
}

/* 插到 n 之后 */
static inline void hlist_add_after(struct hlist_node *n,
				   struct hlist_node *next)
{
	next->next = n->next;
	n->next = next;
	next->pprev = &n->next;
	if (next->next)
		next->next->pprev = &next->next;
}

hlist_add_before() 能直接插到第一个位置，因为它先把 next->pprev（此时指向 &h->first）抄进自己的 pprev，最后一句 *(n->pprev) = n 就自动改对了那个槽位。

hlist_add_after() 在 4.x 之后改了名字，现在的内核里叫 hlist_add_behind(n, prev)，语义是「把 n 插到 prev 之后」。看到老代码里的 hlist_add_after 不用当回事，那是同一个函数。

整表搬移：

c
static inline void hlist_move_list(struct hlist_head *old,
				   struct hlist_head *new)
{
	new->first = old->first;
	if (new->first)
		new->first->pprev = &new->first;
	old->first = NULL;
}

只改三处：目标桶的 first 接管整条链，链首结点的 pprev 改指新桶的 first 槽位，源桶清空。O(1)，不碰任何中间结点。

取宿主和遍历：

c
#define hlist_entry(ptr, type, member) container_of(ptr, type, member)

#define hlist_for_each(pos, head) \
	for (pos = (head)->first; pos && ({ prefetch(pos->next); 1; }); \
	     pos = pos->next)

#define hlist_for_each_safe(pos, n, head) \
	for (pos = (head)->first; pos && ({ n = pos->next; 1; }); \
	     pos = n)

#define hlist_for_each_entry(tpos, pos, head, member)			\
	for (pos = (head)->first;					\
	     pos && ({ prefetch(pos->next); 1;}) &&			\
		({ tpos = hlist_entry(pos, typeof(*tpos), member); 1;}); \
	     pos = pos->next)

({ ...; 1; }) 这个写法是 GCC 语句表达式，把「干事」和「产出 1」塞进同一个条件里。pos && 保证结点非空才取 pos->next，否则末尾那个 NULL 会直接解引用崩掉。

hlist_for_each_entry() 比 list 版本多一个 pos 参数——它需要一个 struct hlist_node * 类型的游标。原因在第十一章说。

hlist_for_each_entry_safe()：

c
#define hlist_for_each_entry_safe(tpos, pos, n, head, member)		\
	for (pos = (head)->first;					\
	     pos && ({ n = pos->next; 1; }) &&				\
		({ tpos = hlist_entry(pos, typeof(*tpos), member); 1;}); \
	     pos = n)

safe 版本把 pos->next 提前存进 n，步进时用 pos = n 而不是 pos = pos->next。这样删掉当前结点后，循环还能继续。

接续遍历还有两个变体：hlist_for_each_entry_continue(tpos, pos, member) 从 pos->next 开始；hlist_for_each_entry_from(tpos, pos, member) 从 pos 本身开始。前者要求 pos 已知非空，后者不需要。

十、list 与 hlist 的取舍 #

两套结构并存不是历史包袱，是各管一段。

维度 list_head hlist
头结点大小 16 字节（next + prev） 8 字节（first）
普通结点大小 16 字节 16 字节
涉及的结构体数 1 个 2 个
判空 head->next == head !h->first
尾结点的后继 绕回哨兵 NULL
删除首元素 无需特判 无需特判（靠 pprev）
反向遍历 支持 不支持
典型用途 设备表、进程表、队列、挂载链 哈希桶

关键一点：两套结构的普通结点都是 16 字节，hlist 省的是头，不是结点。

这条决定了选择标准。看「容器个数」和「容器里的元素个数」的比值：

  • 容器多、元素少——哈希表。桶数上千，每桶平均一两个结点。头像数才是内存大头，hlist 每桶省 8 字节，一千个桶就是 8 KB。
  • 容器少、元素多——普通链表。一张设备总表挂几十上百个设备，头结点那 16 字节根本不用算。用 list_head，换来反向遍历和统一的类型。

另一条标准是需求。要 list_for_each_entry_reverse() 往回走，要 list_splice() 合并，要当队列用，选 list_head。只在桶里从头往后扫、插入后顺序不重要，选 hlist。

网络栈的用法正好落在两边：struct sock 的 established 表用 hlist（桶多、只按哈希值扫）；struct net_device 的 dev_base_head 用 list_head（一条总表、要遍历全部、偶尔要反向）。

十一、遍历时的删除与安全性 #

这一章讲一个必须踩过一次才能记住的坑。

list_for_each_entry() 的步进表达式是：

c
pos = list_entry(pos->member.next, typeof(*pos), member)

每轮结束前，它要读 pos->member.next 才能算出下一个宿主。

循环体里如果删掉当前项：

c
list_for_each_entry(item, &my_list, list) {
	if (item->id == 3) {
		list_del(&item->list);
		kfree(item);
	}
}

这一轮结束时，pos->member.next 已经在 list_del() 里被写成 LIST_POISON1，而 item 本身已经被 kfree() 掉。下一轮要读的地址要么是 0x00100100（立刻页故障），要么是一块已经还给 slab 的内存（use-after-free，问题延后爆发，更难查）。

只 list_del() 不 kfree() 同样错：毒化指针还在，读它照样崩。

解法是 list_for_each_entry_safe()，多传一个同类型指针 n：

c
#define list_for_each_entry_safe(pos, n, head, member)			\
	for (pos = list_entry((head)->next, typeof(*pos), member),	\
	     n = list_entry(pos->member.next, typeof(*pos), member);	\
	     &pos->member != (head);					\
	     pos = n, n = list_entry(n->member.next, typeof(*n), member))

初始化时同时算出 pos 和 n（pos 的下一个）。步进是 pos = n —— n 早在上一轮就存好了，跟 pos 现在是什么状态无关；然后再从 n 算下一轮的 n。

就算 pos 在这一轮里被删掉、被释放，n 还活着，循环能继续。

c
list_for_each_entry_safe(item, next, &my_list, list) {
	if (item->id == 3) {
		list_del(&item->list);
		kfree(item);
	}
}

list_for_each_safe(pos, n, head) 同理，只是操作的是裸 list_head *。

hlist 的对应版本：

c
hlist_for_each_entry_safe(tpos, pos, n, head, member)

它比 list 版本多一个参数，因为需要一个 struct hlist_node * 游标 pos。原因就在终止条件：hlist 的末尾是 NULL，而 NULL 不包含在任何宿主结构里，没法通过 &tpos->member 这种地址比较来判断结束，只能直接判 pos 本身是否为空。所以 pos 必须单独拎出来当循环变量。

list 版本没这个问题——它的终止条件是「回到哨兵」，哨兵地址是真的，能参与比较。

安全版不等于线程安全。这套 _safe 宏只解决「单线程里边遍历边删」，不解决并发。链表接口本身一把锁都不加，两个 CPU 同时 list_add() 到同一条链，指针必然写乱。要并发就自己加锁：

c
spin_lock(&my_lock);
list_for_each_entry_safe(item, next, &my_list, list) {
	if (should_remove(item)) {
		list_del(&item->list);
		kfree(item);
	}
}
spin_unlock(&my_lock);

list_empty_careful() 顶不住这个场景，它只是安慰剂。要无锁读，得用 RCU 版接口（list_for_each_entry_rcu()、hlist_for_each_entry_rcu()）配合 call_rcu() 延迟释放，那是另一套机制，不在本篇范围。

十二、实战：自己写一个用链表的模块 #

下面这个模块同时用上了 list_head 和 hlist：一条有序的设备链，一张 8 个桶的哈希表，两种遍历方式，以及一次安全的批量删除。

c
// SPDX-License-Identifier: GPL-2.0
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/slab.h>
#include <linux/list.h>

#define DEMO_BUCKETS 8
#define DEMO_ITEMS   6

struct demo_item {
	int id;
	char name[24];
	struct list_head list;    /* 挂进 demo_list */
	struct hlist_node hnode;  /* 挂进 demo_hash[] */
};

static LIST_HEAD(demo_list);
static struct hlist_head demo_hash[DEMO_BUCKETS];

static unsigned int demo_bucket(int id)
{
	return id & (DEMO_BUCKETS - 1);
}

static void demo_purge(void)
{
	struct demo_item *pos, *next;

	list_for_each_entry_safe(pos, next, &demo_list, list) {
		list_del(&pos->list);
		hlist_del_init(&pos->hnode);
		kfree(pos);
	}
}

static int __init demo_init(void)
{
	int i, left = 0;
	struct demo_item *pos, *next, *hit;
	struct hlist_node *cur;

	for (i = 0; i < DEMO_BUCKETS; i++)
		INIT_HLIST_HEAD(&demo_hash[i]);

	/* 建表：链按 id 顺序追加，哈希按桶插入 */
	for (i = 0; i < DEMO_ITEMS; i++) {
		pos = kzalloc(sizeof(*pos), GFP_KERNEL);
		if (!pos) {
			demo_purge();
			return -ENOMEM;
		}
		pos->id = i;
		snprintf(pos->name, sizeof(pos->name), "item-%d", i);
		INIT_LIST_HEAD(&pos->list);
		INIT_HLIST_NODE(&pos->hnode);
		list_add_tail(&pos->list, &demo_list);
		hlist_add_head(&pos->hnode, &demo_hash[demo_bucket(i)]);
	}

	pr_info("demo: list, head -> tail\n");
	list_for_each_entry(pos, &demo_list, list)
		pr_info("demo:   id=%d name=%s\n", pos->id, pos->name);

	pr_info("demo: list, tail -> head\n");
	list_for_each_entry_reverse(pos, &demo_list, list)
		pr_info("demo:   id=%d name=%s\n", pos->id, pos->name);

	/* 哈希查找：只扫目标桶 */
	hit = NULL;
	hlist_for_each_entry(pos, cur, &demo_hash[demo_bucket(3)], hnode) {
		if (pos->id == 3) {
			hit = pos;
			break;
		}
	}
	pr_info("demo: lookup id=3 -> %s\n", hit ? hit->name : "miss");

	/* 遍历中删除：必须用 _safe */
	pr_info("demo: drop even ids\n");
	list_for_each_entry_safe(pos, next, &demo_list, list) {
		if (pos->id & 1)
			continue;
		list_del(&pos->list);
		hlist_del_init(&pos->hnode);
		kfree(pos);
	}

	list_for_each_entry(pos, &demo_list, list)
		left++;
	pr_info("demo: %d item(s) left\n", left);

	return 0;
}

static void __exit demo_exit(void)
{
	demo_purge();
	pr_info("demo: exit\n");
}

module_init(demo_init);
module_exit(demo_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("list_head and hlist demo");

几个要盯住的细节。

struct demo_item 里同时嵌了 list 和 hnode。删除时必须两个都摘：只 list_del() 就 kfree()，哈希桶里还留着 hnode 的地址，下次哈希查找会读到已释放内存。

错误路径调 demo_purge()。它从 demo_list 上摘，对已挂过的项逐个释放，半成品状态也能清干净。

hlist_del_init() 而不是 hlist_del()，因为 demo_purge() 会在 hlist_add_head() 之前被调用（kzalloc 失败时），此时 hnode 还没进桶。hlist_del_init() 内部的 hlist_unhashed() 判断让这次调用变成空操作。

demo_init() 里那段 list_for_each_entry_reverse() 能验证 prev 指针真被维护对了——正向能走通、反向也能走通，说明双向链接没断。

PWD  := $(shell pwd)

	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

想先在用户态跑一遍，把 include/linux/list.h 拷出来做点减法：删掉 prefetch() 的定义或改成空宏，去掉对 linux/kernel.h、linux/poison.h 的依赖，把 LIST_POISON1/2 换成 NULL 或 (void *)0xdeadbeef，container_of / offsetof 用 GCC 的就能编译。typeof 是 GCC 扩展，-std=gnu99 以上可用。

用户态验证代码和内核模块的逻辑一样，把 pr_info 换成 printf、kzalloc/kfree 换成 malloc/free 即可：

c
#include <stdio.h>
#include <stdlib.h>
#include "list.h"

struct test_struct {
	int test_a;
	char test_b;
	struct list_head list;
};

int main(void)
{
	int i;
	struct test_struct *p, *next;
	struct list_head *ptr;
	LIST_HEAD(head);

	for (i = 0; i < 10; i++) {
		p = malloc(sizeof(*p));
		p->test_a = i;
		p->test_b = i + 1;
		list_add(&p->list, &head);
	}

	list_for_each(ptr, &head) {
		p = list_entry(ptr, struct test_struct, list);
		printf("%d %d\n", p->test_a, p->test_b);
	}

	list_for_each_entry_safe(p, next, &head, list) {
		list_del(&p->list);
		free(p);
	}

	return 0;
}

_safe 系列必须传两个独立指针。把同一个变量同时交给 pos 和 n，n = pos 之后 pos = n 永远不动，循环要么卡死要么只删一个，编译器不管这事。

十三、易错点速查 #

# 症状 原因 正确处理
1 编译报参数类型不符 list_add(item, &head) 传了宿主指针 传 &item->list
2 编译报声明错误 函数体里写了 LIST_HEAD(&head) 用 INIT_LIST_HEAD(&head)
3 遍历时页故障或静默 UAF list_for_each_entry 里删当前项 换 list_for_each_entry_safe
4 编译通过、运行地址错乱 list_entry() 的 member 写错成别的成员 核对宿主里 list_head 成员的变量名
5 拿到野指针 空表上调用 list_first_entry 先 list_empty() 判断
6 list_empty() 结果反常 对 list_del() 摘下的节点判空 用 list_del_init()，或用 list_empty_careful 的语义重新审视
7 源链表头指向别人的元素 用了 list_splice() 换 list_splice_init()
8 指针字段随机损坏 两条线程同时改同一条链 自己加锁；读多写少用 RCU 版接口
9 编译报参数个数不符 hlist_for_each_entry 少传游标 补上 struct hlist_node * 参数
10 二次删除崩在 0x00200200 hlist_del() 后重复删除 换 hlist_del_init()，它有 hlist_unhashed 保护
11 哈希桶里出现重复项 同一个 hnode 插进两个桶 一个节点只进一个桶；要进多个就嵌多个 hlist_node
12 释放后哈希查找读到脏数据 只摘了 list 没摘 hnode 就 kfree() 每个挂载点都要摘干净
13 _safe 循环只删一个或卡死 pos 和 n 传了同一个变量 声明两个独立指针
14 反向遍历拿到垃圾 在 hlist 上找 _reverse 版本 hlist 没有 prev，不支持反向遍历

最后一条要单独记一下：hlist_node 里那个二级指针叫 pprev，不是 prev。它指向前驱的 next 槽位，不是前驱结点本身。想顺着它往回走，得先 *(n->pprev) 拿到前驱结点，但这一步只对「前驱是 hlist_node」的情况成立——桶里第一个结点的前驱是 hlist_head，解引用得到的是另一层含义。所以 hlist 干脆不提供反向遍历，写代码时也别自己绕。
