一、三个框架的共同模式：抽象 + 注册 + 查找 #

一根引脚、一组复用寄存器、一条两线总线，硬件上都简单。麻烦来自差异：同样是「点灯」，SOC 片内的 GPIO 是写一个 memory map 寄存器，挂在 I2C 上的 IO expander 却要先发一帧 I2C 事务；同样是 SDA，这块板子上是 pin 12，换块板子可能是 pin 69。

把这些差异挡在驱动之外，内核用的办法是同一套：定义抽象结构体，provider 填充并注册，consumer 按名字或编号查找。

维度 GPIO 子系统 pinctrl 子系统 I2C 子系统
抽象的硬件对象 一根引脚（可控电平） 一根引脚的复用与电气属性 一条总线和挂在上面的从设备
provider 侧结构体 struct gpio_chip struct pinctrl_desc struct i2c_adapter
provider 注册函数 gpiochip_add() / devm_gpiochip_add_data() pinctrl_register() i2c_add_adapter() / i2c_add_numbered_adapter()
consumer 侧句柄 struct gpio_desc * struct pinctrl * + struct pinctrl_state * struct i2c_client * / struct i2c_adapter *
consumer 主接口 gpiod_get() / gpiod_set_value() pinctrl_select_state() i2c_transfer()
编号空间 全局 gpio 编号 全局 pin 编号 7 bit 从地址
硬件无关核心 gpiolib（drivers/gpio/gpiolib.c） pinctrl core（drivers/pinctrl/core.c） I2C core（drivers/i2c/i2c-core.c）

三个 provider 结构体长一个样：名字 + 资源范围 + 一组回调指针。core 只认回调，不认寄存器。共同的好处是 core 里没有一行代码知道底层是 SOC 片内控制器还是 I2C 挂的 expander；共同的代价是 core 必须维护编号空间（gpio ID、pin ID、总线号）、必须处理「provider 还没注册好」的时序、必须给 consumer 一个能自动清理的句柄（devres）。

三个框架的耦合程度不一样，先记住这张图，后面会反复回到这里：

text
GPIO ─────── 强耦合 ───────> pinctrl       复用状态由 pinctrl 管，走 pinctrl_request_gpio 这条「后门」
I2C  ─────── 弱耦合 ───────> pinctrl、GPIO  控制器引脚靠 pinctrl 配，复位脚/中断脚靠 GPIO 拉

二、GPIO 子系统要解决什么 #

刚入行的嵌入式工程师拿到的第一个任务往往是 GPIO driver 或者 LED driver。CPU datasheet 里关于 GPIO / I/O ports 的那一章也确实简单：一堆寄存器，几位控制方向，几位控制电平，读一个寄存器拿输入状态。看起来一个下午就能写完。

真正动手才发现，一个能用的 GPIO driver 远不止读写那几个寄存器。硬件简单不等于软件抽象简单，这个领域恰好是理解 Linux 分层思想最好的入口。先把边界划清：

内容 属于 GPIO driver 吗 说明
pin signal 状态控制与读取 是 配方向、输出高低、读输入电平
pin multiplexing（引脚复用） 否 同一个引脚是 GPIO 还是 I2C SCL，由 pin controller 决定
pin configuration（引脚特性） 否 pull-up/down、tri-state、drive-strength
GPIO interrupt control 否 边沿/电平触发、mask/unmask、状态清除

后三项落在另外两个子系统里：复用与电气属性归 pinctrl，中断归 interrupt subsystem 里的一个底层 irqchip。这也是本篇要把 GPIO 和 pinctrl 放在一起讲的原因——它们被硬件的物理约束绑死。

三、为什么需要「GPIO 系统」而不是「GPIO driver」 #

嵌入式工程师总要面对各种 target board，每块板子上的 GPIO 都不一样。把差异归类，才能看清内核为什么设计了这么一层抽象。

3.1 与 CPU 的连接方式不同。ARM 平台上 SOC 提供大量 IO port，SOC 内的 GPIO controller 通过 SOC 总线（AMBA）连到 CPU，访问它就是写一个 memory map 寄存器，非常快。SOC 之外还可能有别的 IO：key controller、codec、PMU 芯片顺带提供的几个 I/O port；专用 IO expander 能扩出 16 或 32 个 GPIO——这些 CPU 要通过 I2C（也可能是 SPI）才能访问。

❢重要

这个差异直接决定同步机制的选择。写 SOC 寄存器是纯内存操作，可以用 spinlock；I2C 传输可能阻塞当前进程（总线繁忙时还会睡更久），这条路径上不能用 spinlock，必须用 mutex。GPIO 子系统因此把「可能睡眠」当作抽象的一部分，而不是让每个驱动自己猜。

3.2 访问方式不同。有的 SOC 用一个寄存器控制输出电平：写 1 是 set high，写 0 是 set low；有的用两个寄存器，一个管置高一个管置低。前者读-改-写要小心并发，后者是原子操作——直接影响是否需要额外的锁。

3.3 配置方式不同。同一款 SOC 装在不同板子上，引脚用途不同：这个系统配成输入，那个系统配成输出；这块板接按键，那块板接 LED。引脚配置信息因此不能写死在 driver 里，必须由板级描述（machine driver 的静态表，或者 device tree）提供。

3.4 GPIO 特性不同。这组差异决定驱动能不能对外宣称某项能力：能不能触发中断（有些处理器只有一两组 GPIO 有中断功能）、能不能把 CPU 从 sleep 唤醒、有没有软件可控的上拉/下拉、配成输入时能不能做 debounce。

3.5 多功能复用。IO expander 上的引脚基本都是单纯 GPIO，而 SOC 上的某个引脚除了做普通 IO，还可能是 SPI 的 clock 线。硬件信号只有一条，功能只能二选一——这就是 pin multiplexing 的物理根源，也是第十六章那个「后门」存在的原因。

3.6 硬件功能三分，软件三个模块 #

datasheet 里那一章塞满寄存器描述，按功能归纳只服务三块硬件逻辑：pin controller（引脚功能配置 + 引脚特性配置）、GPIO controller（配方向、设输出高低、读输入电平）、GPIO 中断控制器（mask/unmask、设触发方式、清状态）。传统 GPIO driver 一个模块全包，新内核拆成三个软件模块：

软件模块 驱动的硬件 所属子系统
pin control subsystem pin controller 独立子系统，第十一章起
GPIO subsystem GPIO controller 独立子系统，第四至十章
GPIO interrupt chip driver GPIO 中断控制器 interrupt subsystem 中的一个底层驱动

第三项本篇不展开，它属于 irqchip 那一套，只是寄存器恰好长在 GPIO 的地址空间里。GPIO 子系统与 pin control 子系统的结构完全一致：底层 driver 与硬件相关，初始化时向 core 注册自己（pin controller 的注册接口是 pinctrl_register()，bottom level interface）；core 模块与硬件无关（pinctrl core / gpiolib），抽象掉所有控制器差异，只暴露 top level 接口。这样各个 driver 用 pin 或 GPIO 时，不需要关心控制器是 SOC 片内的还是 I2C 挂的。

四、gpio_chip：一个控制器怎么被抽象 #

gpiolib 对 GPIO controller 的全部认知，都在 struct gpio_chip 里（include/linux/gpio/driver.h，3.x）：

c
struct gpio_chip {
    const char              *label;        /* 唯一名字，出现在 sysfs 和 debugfs 里 */
    struct device           *dev;          /* 父 device，devm 管理靠它 */
    struct module           *owner;

    int                     (*request)(struct gpio_chip *chip, unsigned offset);
    void                    (*free)(struct gpio_chip *chip, unsigned offset);
    int                     (*get_direction)(struct gpio_chip *chip, unsigned offset);
    int                     (*direction_input)(struct gpio_chip *chip, unsigned offset);
    int                     (*direction_output)(struct gpio_chip *chip,
                                                unsigned offset, int value);
    int                     (*get)(struct gpio_chip *chip, unsigned offset);
    void                    (*set)(struct gpio_chip *chip, unsigned offset, int value);
    void                    (*set_multiple)(struct gpio_chip *chip,
                                            unsigned long *mask, unsigned long *bits);
    int                     (*set_debounce)(struct gpio_chip *chip,
                                            unsigned offset, unsigned debounce);
    int                     (*to_irq)(struct gpio_chip *chip, unsigned offset);
    void                    (*dbg_show)(struct seq_file *s, struct gpio_chip *chip);

    int                     base;          /* 起始 gpio 编号；负数表示动态分配 */
    u16                     ngpio;         /* 本 chip 管多少个 gpio */
    const char              *const *names; /* 每根引脚的友好名，可为 NULL */
    bool                    can_sleep;     /* 访问这些寄存器会不会睡眠 */
    bool                    irq_not_threaded;

    int                     (*of_xlate)(struct gpio_chip *gc,
                                        const struct phandle_args *gpiospec, u32 *flags);
#if defined(CONFIG_OF_GPIO)
    struct device_node      *of_node;
    int                     of_gpio_n_cells;
    int                     (*of_gpio_simple_xlate)(struct gpio_chip *gc,
                                                    const struct phandle_args *gpiospec,
                                                    u32 *flags);
#endif
};

字段多，按用途归成六组：

组 字段 说明
身份 label、dev、owner sysfs 里的 gpiochipN 用 label 做别名
编号范围 base、ngpio、names base 为负时由 core 动态分配，从 0 往上找空位
引脚操作 direction_input/output、get、set、set_multiple、get_direction 真正碰寄存器的那几个
资源管理 request、free 可为 NULL，core 会填默认实现
特性声明 can_sleep、set_debounce、to_irq、dbg_show 决定上层能做什么操作
OF 支持 of_node、of_gpio_n_cells、of_xlate 从设备树取 GPIO 靠这一组

两个字段值得单独说。can_sleep 不描述功能，描述访问代价：SOC 片内 GPIO 填 false，I2C/SPI expander 必须填 true。gpiolib 用它拒绝在原子上下文里访问这类 chip（直接报错而不是悄悄睡死），也用它决定 gpiod_set_value() 走 mutex 版本还是自旋锁版本。base 决定全局编号怎么拼：第一个 chip 占 0~ngpio-1，第二个接着往下；填负数表示「你帮我挑」，gpiolib 从 0 向上找第一个够长的空隙。所以用户空间的 gpio 编号在不同板子上完全不一样——它取决于 chip 的注册顺序。

request / free 可选。不填时 gpiolib 只做「这根线有没有被别人占」的标记；填了则 driver 可以在这里做额外动作，典型就是向 pinctrl 申请引脚复用（第十六章那条链路）。

五、gpio_desc 与 gpiolib 的分层 #

gpio_chip 是 provider 侧的抽象，consumer 侧看到的是 struct gpio_desc：

c
/* drivers/gpio/gpiolib.h，3.13 之后的形态 */
struct gpio_desc {
    struct gpio_chip        *chip;     /* 这根线属于哪个 controller */
    unsigned long           flags;     /* 状态位：REQUESTED / IS_OUT / ACTIVE_LOW ... */
    const char              *label;    /* 谁申请的 */
    const char              *name;     /* 这根线的名字 */
#ifdef CONFIG_DEBUG_FS
    const char              *dbg_name;
    ...
#endif
};

gpiolib 为每一根受管的引脚预分配一个 gpio_desc，挂在一张全局表里（3.x 是 radix tree，3.13 之后改为按 chip 分组的数组 + 全局数组，具体形态逐版有变动，未验证到具体 tag）。编号 n 的 desc 就是全局表里第 n 项。

text
consumer（外设驱动）      只用 gpiod_* 或 legacy 的 gpio_* 接口，拿到的都是 gpio_desc
    ▼
gpiolib（硬件无关）       编号分配、占用标记、极性处理、设备树解析、sysfs/debugfs、devres
    ▼
gpio_chip 回调（硬件相关） direction_input / direction_output / get / set
    ▼
寄存器（memory map 或 I2C 事务）

分层的收益在 flags 里看得最清楚。ACTIVE_LOW 让逻辑电平和物理电平分离：设备树里写 GPIO_ACTIVE_LOW，之后 gpiod_set_value(desc, 1) 会让 gpiolib 自动往硬件写 0，驱动代码里不必再出现 !。同一层还吃掉两件事：方向跟踪（IS_OUT 记住这根线配成什么方向）；占用标记（REQUESTED 加 label，让 cat /sys/kernel/debug/gpio 能列出每根线被谁占了，两个驱动抢同一根线时第二个直接失败）。

六、gpio 的申请与释放 #

6.1 legacy 路径 #

c
/* include/linux/gpio.h，3.x 时代 */
int gpio_request(unsigned gpio, const char *label);
void gpio_free(unsigned gpio);
int gpio_request_one(unsigned gpio, unsigned long flags, const char *label);
int gpio_request_array(const struct gpio *array, size_t num);
void gpio_free_array(const struct gpio *array, size_t num);

label 就是 gpio_desc.label，纯粹为了 debugfs 好看，但排查「引脚被谁占了」时价值极高——没填 label 的驱动事后只能对着编号猜。gpio_request_one() 把「申请 + 配方向 + 设初值」合成一步，flags 是 GPIOF_* 位或：

标志 含义
GPIOF_DIR_IN / GPIOF_DIR_OUT 申请后立刻设方向
GPIOF_INIT_LOW / GPIOF_INIT_HIGH 输出时的初始电平
GPIOF_OPEN_DRAIN / GPIOF_OPEN_SOURCE 开漏 / 开源输出
GPIOF_ACTIVE_LOW / GPIOF_ACTIVE_HIGH 极性
GPIOF_EXPORT / GPIOF_EXPORT_DIR_FIXED 导给用户空间，并锁定方向

GPIOF_EXPORT 这一族是另一条边界：3.x 允许驱动把引脚导到 /sys/class/gpio，用户空间 echo N > export 再操作。新内核已弃用这条路径，改用 /dev/gpiochipN 字符设备（4.8 引入的 gpio chardev，具体版本未逐一验证）。

6.2 描述符路径 #

c
/* include/linux/gpio/consumer.h，3.13+ */
struct gpio_desc *gpiod_get(struct device *dev, const char *con_id,
                            enum gpiod_flags flags);
struct gpio_desc *devm_gpiod_get(struct device *dev, const char *con_id,
                                 enum gpiod_flags flags);
void gpiod_put(struct gpio_desc *desc);
void devm_gpiod_put(struct device *dev, struct gpio_desc *desc);

GPIOD_ASIS / GPIOD_IN / GPIOD_OUT_LOW / GPIOD_OUT_HIGH   /* 常见 flags */

gpiod_get() 的参数里没有编号，只有 dev 和 con_id。con_id 是设备树里属性名的前缀，不是引脚编号——这个设计是整套描述符接口的核心，第八章展开。两条路径的对照：

维度 legacy gpio_request 描述符 gpiod_get
引入时间 早期内核就有 3.13 引入，之后逐版扩充
定位引脚 直接用全局 gpio 编号 用「device + 连接名」，编号在 core 内部解析
引脚从哪来 调用者自己算/查 of_get_named_gpio core 自己查设备树
极性处理 调用者自己关心 GPIOF_ACTIVE_LOW desc 记住极性，gpiod_set_value 自动换算
睡眠约束 无自动检查 gpiod_set_value() 与 _cansleep 分开，误用会报错
资源回收 手动 gpio_free devm_ 版本随 device detach 自动释放
现状 legacy，新代码不该用 推荐路径（4.x 之后，未验证具体弃用版本）

结论直白：能写描述符接口就写描述符接口。legacy 接口留在老 BSP 和老驱动里，读代码时必须认识，但不要在新代码里用。

6.3 释放 #

gpio_free() 与 gpiod_put() 都做同一件事：清 REQUESTED 标志，把 desc 还回池子。顺序有讲究——先停用，再释放。若这根线还挂着中断，必须先 free_irq()；若是输出，最好在释放前给它一个确定电平，否则释放瞬间保持的电平取决于最后一个写寄存器的动作。

devm_ 版本把这一步交给驱动模型：devm_gpiod_get() 拿到的句柄在 device detach 时（probe 失败回滚、驱动 unbind、模块卸载）自动释放，所以 probe 里除了错误分支基本不用写释放代码。机制见同批 platform 设备与 devres：平坦总线与资源自动回收。

七、方向、值、以及原子上下文中的 GPIO #

c
int gpiod_direction_input(struct gpio_desc *desc);
int gpiod_direction_output(struct gpio_desc *desc, int value);
int gpiod_direction_output_raw(struct gpio_desc *desc, int value);
int gpiod_get_direction(struct gpio_desc *desc);   /* 返回 0=out, 1=in, 负=错误 */

int gpiod_get_value(struct gpio_desc *desc);
int gpiod_get_value_cansleep(struct gpio_desc *desc);
void gpiod_set_value(struct gpio_desc *desc, int value);
void gpiod_set_value_cansleep(struct gpio_desc *desc, int value);

_cansleep 后缀不是风格选择，是硬约束：

接口 能用在哪 用在错的地方会怎样
gpiod_get_value() / gpiod_set_value() 任意上下文（包括中断里） 若 chip 声明了 can_sleep，gpiolib 打印警告并拒绝执行
gpiod_get_value_cansleep() / gpiod_set_value_cansleep() 只能进程上下文，可睡眠 在中断上下文调用，可能在 mutex 上睡死

这套区分随 3.13 描述符接口一起成型。legacy 的 gpio_get_value() / gpio_set_value() 没有上下文检查，调用者必须自己翻 chip 的 can_sleep——这也是 legacy 难用的原因之一。细节：gpiod_direction_output() 会先设值再切方向（避免切换瞬间出现毛刺），gpiod_direction_output_raw() 不经过极性换算，直接写物理电平，做时序敏感的复位信号时更可控。

读回：gpiod_get_value() 在输出方向下的返回值取决于 chip 的 get 回调，多数 SOC 返回输出寄存器的内容（也就是你写下去的值），个别返回引脚真实电平。被外部拉低的输出脚，这两者不同。要读真实电平，唯一可靠的办法是先切成输入。

原子上下文：中断处理里想点灯（调试常用），只能用 gpiod_set_value()，且只有 chip 是 can_sleep = false 才可以。I2C expander 上的引脚在硬中断里根本不能动——一次 I2C 事务要走完整总线时序，还可能等 mutex。这条限制会反向影响板级设计：如果某个信号必须在硬中断里翻转，就别把它接到 expander 上。

八、从设备树拿 GPIO：gpiod_get 与 of_get_named_gpio #

属性名构词规则是 con_id + "-gpios"（3.x 早期写成 con_id + "-gpio"，单数形式的兼容写法仍在用）。每个 phandle 后面跟几个 cell 由目标 controller 的 #gpio-cells 决定——前面 gpf 写的是 <2>，所以是「编号 + 标志」两个 cell。标志位定义在 include/dt-bindings/gpio/gpio.h：

标志 值 含义
GPIO_ACTIVE_HIGH 0 高电平有效
GPIO_ACTIVE_LOW 1 低电平有效
GPIO_OPEN_DRAIN 2 开漏
GPIO_OPEN_SOURCE 4 开源

两条取值路径：

c

reset = devm_gpiod_get(&pdev->dev, "reset", GPIOD_OUT_LOW);
if (IS_ERR(reset))
    return PTR_ERR(reset);
gpiod_set_value(reset, 1);      /* 拉高，极性由 desc 里的 ACTIVE_LOW 处理 */

data = devm_gpiod_get_array(&pdev->dev, "data", GPIOD_IN);
/* data->ndescs 是实际拿到的条数，data->desc[i] 逐根访问 */

/* legacy 路径：先解析出全局编号，再申请 */
int of_get_named_gpio(struct device_node *np, const char *propname, int index);
int of_get_named_gpio_flags(struct device_node *np, const char *propname,
                            int index, enum of_gpio_flags *flags);

gpio = of_get_named_gpio(np, "reset-gpios", 0);

    return gpio;

"reset" 就是 con_id，core 拼成 reset-gpios 去设备树里查。con_id 为 NULL 时有一堆回退规则（依次尝试 <devname>-gpios、gpios 等），这种写法只适合设备真的只有一根线的情况。两条路径的差别集中在「谁处理极性」：

环节 gpiod_get of_get_named_gpio + gpio_request
找属性名 core 内部拼 con_id-gpios 调用者自己写属性名
解析 cell 数 core 按 of_gpio_n_cells 处理 core 内部同样处理
极性标志 存进 desc，后续自动换算 交给调用者的 flags，容易忘
结果 不透明句柄 一个整数编号

of_get_named_gpio() 返回的是全局 gpio 编号，所以老代码里到处是「int gpio 全局变量 + gpio_set_value()」，C.驱动/06-I2C子系统 里的移植文章还常能看到。

-EPROBE_DEFER：设备树里引用了某个 GPIO controller 但它还没注册好（比如它自己挂在 I2C 上，而 I2C 控制器还在 probe），gpiod_get() 返回 -EPROBE_DEFER。驱动必须原样往上传，不能吞掉、不能改成 -EINVAL。设备模型收到它会把这次 probe 排到队列末尾重试（机制见 device、driver、bus、class：四个注册表）。吞掉它的后果是设备永远起不来，日志里还看不出原因。

九、gpio 与中断的结合：gpio_to_irq #

GPIO 能触发中断时，它同时是 input 和 irq source。把两者接起来的是 gpio_to_irq()：

c
int gpio_to_irq(unsigned gpio);

/* 实现上直接转给 chip 的 to_irq 回调 */
int gpiod_to_irq(const struct gpio_desc *desc)
{
    struct gpio_chip *chip = desc->chip;
    int offset = gpio_chip_hwgpio(desc);
    int ret;

    if (!chip->to_irq)
        return -ENXIO;
    ret = chip->to_irq(chip, offset);
    ...
    return ret;
}

c
gpio = of_get_named_gpio(np, "irq-gpios", 0);
gpio_request_one(gpio, GPIOF_IN, "dev-irq");
irq = gpio_to_irq(gpio);
ret = request_threaded_irq(irq, NULL, dev_irq_thread,
                           IRQF_TRIGGER_FALLING | IRQF_ONESHOT, "dev", priv);

to_irq 回调返回的是一段连续 irq 号里的偏移，背后是 GPIO 型中断控制器注册的 irq domain。所以 gpio_to_irq() 拿到的号可以被 request_irq() 正常使用，中断到来时走标准中断链路。几个绕不开的点：

  • to_irq 可能为 NULL，表示该 chip 的引脚没有中断能力（第三章那组特性差异之一）。调用前要判断，或让 probe 返回明确错误。
  • 触发器要跟硬件对上。IRQF_TRIGGER_FALLING 写在 request_irq 里只是「要求」，真正配寄存器的是链路另一端。设备树里若写了 interrupts 也会产生触发器信息，两处冲突时行为不好预测。选一处写。
  • 去抖。按键类常配 set_debounce 回调或 gpiod_set_debounce()；硬件不支持时只能在软件里做定时器去抖。
  • 唤醒。想用 GPIO 中断把系统从 suspend 唤醒，除了 enable_irq_wake()，设备树里还要有 wakeup-source。

十、legacy 接口 gpio_request 与现代描述符接口的区别 #

第九章那套「of_get_named_gpio + gpio_request + gpio_to_irq」就是完整的 legacy 链路。并排放一次：

c
/* legacy：编号在驱动里流转 */
gpio = of_get_named_gpio(pdev->dev.of_node, "reset-gpios", 0);
if (gpio < 0)
    return gpio;
ret = devm_gpio_request_one(&pdev->dev, gpio, GPIOF_OUT_INIT_LOW, "foo-reset");
priv->reset_gpio = gpio;              /* 存一个 int */
gpio_set_value(priv->reset_gpio, 1);  /* 极性自己记着 */

/* 描述符：句柄在驱动里流转 */
priv->reset = devm_gpiod_get(&pdev->dev, "reset", GPIOD_OUT_LOW);
if (IS_ERR(priv->reset))
    return PTR_ERR(priv->reset);
gpiod_set_value(priv->reset, 1);      /* 极性在 desc 里 */
差异点 legacy 描述符
驱动里存什么 int 编号 struct gpio_desc *
对象边界 「全局编号」和「引脚」混为一谈 编号序列只存在于 core 内部
极性 靠 GPIOF_ACTIVE_LOW 或调用者手动取反 存进 desc，自动换算
上下文安全 无检查 _cansleep 变体强制作者做选择
批量操作 逐根调用 gpiod_get_array / gpiod_set_array_value 一次搞定
测试与 mock 难，编号是全局状态 可替换 gpio_chip，desc 是普通指针
非 DT 平台 各写一套 gpiod_get 统一走固件描述

最后一行值得多说。gpiod_get() 的查找后端不只有设备树，还有 ACPI 和板级查找表（gpiod_add_lookup_table()）。同一份驱动能在 DT 平台和 ACPI 平台跑，这是 legacy 做不到的——老代码里 of_get_named_gpio 和 gpio_request 一搭上，就绑死在设备树上了。

迁移的实际经验：把 int gpio 换成 struct gpio_desc *，去掉所有 !value 取反，把 gpio_set_value 换成 gpiod_set_value，再逐个确认调用上下文用不用 _cansleep。四步做完，行为不变而代码短一半。

十一、pinctrl 要解决什么：复用与电气属性 #

GPIO 子系统管「一根引脚输出什么电平」。引脚还有两个属性它管不了：这根线现在归哪个功能用，以及这根线的电气参数是什么。

2.6 时代做 pin control 的工程师都遇到过这些状况：新项目上手要在 bootloader 里建一张巨大的 table 描述每个引脚的配置和缺省状态，各 driver 里还要再配一遍；某个 driver 不工作，debug 半天发现是别的 driver 初始化时改了引脚配置；主 CPU 相同的两个项目因为外设不同不能共用一个 kernel image；cut-and-paste 满天飞。ARM SOC 表面各不相同，在 pin control 上却共通之处很多，于是可以抽象。功能规格三条：管理系统中所有可控的 pin；管理 pin 的复用（若干引脚组成 pin group 形成特定功能，例如 pin number 为 {0, 8, 16, 24} 的四个引脚组合成一组提供 SPI）；配置 pin 的特性（pull-up/down、drive strength）。

文件组织印证了分层。drivers/pinctrl/ 下以 S3C2416 为例是 pinctrl-samsung.c / pinctrl-samsung.h / pinctrl-s3c24xx.c；include/linux/pinctrl/ 下分两类，consumer.h / machine.h / pinconf.h / pinmux.h / pinctrl.h 暴露给其他内核模块，pinctrl-desc.h 之类提供给底层 driver。靠文件名区分给使用者还是给实现者，是这个子系统最容易识别的设计痕迹。对外有四个方向的接口：

接口方向 对端 内容 所在章节
pinctrl → 普通 driver UART、SPI 等 consumer pin config 与 pin mux 的设定 第十五章
pinctrl ↔ GPIO subsystem gpio controller driver gpio 与 pin 编号的映射与申请 第十六章
pinctrl ↔ driver model 统一设备模型 probe 前自动绑定 pin state 第十五章
pinctrl ← DT / machine driver device tree、板级代码 pin mapping database 第十四、十五章

理想状态是 GPIO controller driver 也像 UART、SPI 那样作为普通 consumer 和 pinctrl 打交道。实际并非如此，第十六章解释为什么必须打个洞。

十二、pin、group、function 三个概念 #

pinctrl 子系统的 entry point 是一个结构体：

c
struct pinctrl_desc {
    const char *name;
    struct pinctrl_pin_desc const *pins;   /* 指向 npins 个 pin 描述符 */
    unsigned int npins;                    /* 本控制器有多少个可控 pin */
    const struct pinctrl_ops *pctlops;     /* 全局控制：group 枚举、debug、DT 解析 */
    const struct pinmux_ops  *pmxops;      /* 复用相关操作 */
    const struct pinconf_ops *confops;     /* 电气特性配置 */
    struct module *owner;
};

三个 ops 指针就是 core 与底层 driver 之间的全部契约：core 负责抽象与流程，driver 负责把三个 ops 填满。pins 与 npins 界定控制器的管辖范围。

pin。core 只关心有多少个 pin，用自然数编号，后续所有操作都以这些编号为对象；至于编号怎么对应到具体物理引脚，完全是 driver 自己的事。

c
/**
 * struct pinctrl_pin_desc - boards/machines provide information on their
 * pins, pads or other muxable units in this struct
 * @number: unique pin number from the global pin number space
 * @name: a name for this pin
 * @drv_data: driver-defined per-pin data. pinctrl core does not touch this
 */
struct pinctrl_pin_desc {
    unsigned number;
    const char *name;
    void *drv_data;
};
字段 谁来定 用途
number driver 全局 pin 编号空间中的唯一 ID，给机器用
name driver user friendly name，ASCII 字符，给人看
drv_data driver 每 pin 私有数据，core 完全不碰；可放寄存器偏移、所属 bank 指针

取值有两个原则：有利于代码编写，有利于理解。Samsung 取 bank名-pin号（如 gph-0），编号从本控制器的 pin base 起连续分配。

group。SPI、I2C 这类功能必须同时控制多个 pin，所以 pin controller 需要以 group 为单位访问。子系统要能回答：有多少个 group、每个叫什么、每个包含哪些 pin。答案都落在 struct pinctrl_ops 里：

c
struct pinctrl_ops {
    int (*get_groups_count) (struct pinctrl_dev *pctldev);
    const char *(*get_group_name) (struct pinctrl_dev *pctldev, unsigned selector);
    int (*get_group_pins) (struct pinctrl_dev *pctldev, unsigned selector,
                           const unsigned **pins, unsigned *num_pins);
    void (*pin_dbg_show) (struct pinctrl_dev *pctldev, struct seq_file *s,
                          unsigned offset);
    int (*dt_node_to_map) (struct pinctrl_dev *pctldev,
                           struct device_node *np_config,
                           struct pinctrl_map **map, unsigned *num_maps);
    void (*dt_free_map) (struct pinctrl_dev *pctldev,
                         struct pinctrl_map *map, unsigned num_maps);
};
回调 作用
get_groups_count 返回 group 个数。后续以索引（类似数组下标）为单位操作，个数即数组大小
get_group_name 返回指定 selector 的 group 名字
get_group_pins 返回指定 group 的所有 pin，结果写进 pins（指针数组）和 num_pins
pin_dbg_show debugfs 输出每个 pin 的当前状态，只在调试时有用
dt_node_to_map 把 DT 中的 pin state 节点转成 pin map 数组
dt_free_map 释放上面生成的 map 数组

group 怎么组织是 driver 的事。Samsung 把 DT 里每个 pin configuration child node 变成一个 group，名字取「节点名 + -grp」后缀。

ℹ笔记

group 与「bank」是两个层次。bank 是硬件上的寄存器分块（同一组引脚共用一套寄存器，特性相同），group 是功能上的一组引脚（可能跨 bank）。Samsung 2416 有 138 个 IO 分成 11 个 bank，但 group 跟着功能走，数量远多于 11。

function。function 表示一个功能，对应一个 HW 逻辑 block，例如 SPI0、I2C0、UART5；一经确定，其占用的 pin（或 pin group）的功能状态也就确定了。core 不关心 function 的具体形态，只要求 driver 把所有可能的 function 枚举出来（格式自定，但要有编号和名称）注册给 core。同一个 function 可能映射到不同的 pin group：SPI0 可能引出到 group {A8, A7, A6, A5}，也可能引出到 {G4, G3, G2, G1}，这两个 group 不能同时 active——芯片里 SPI0 的逻辑电路只有一个。所以做功能设定时必须同时给出 function selector 和该 function 的 pin group selector。

概念 是什么 谁定义 数量级 DT 里的形态
pin 一根物理引脚 driver 用 pinctrl_pin_desc 描述 几十到几百 引用的最小单位，samsung,pins = "gph-0"
group 要一起操作的一组 pin driver 通过 pctlops 枚举 多于 bank 数 一个 pin configuration child node
function 一个硬件功能块 driver 通过 pmxops 枚举 与 SoC 型号相关 一个 node 上的 samsung,pin-function

分组的意义：SPI 用四根线，你不能只把其中一根切过去，group 就是「要么全切，要么不切」的单位。

十三、pinctrl_desc 与 pinctrl_ops #

三个 ops 分工明确：

ops 回答的问题 数量相关的回调 真正改硬件的回调
pinctrl_ops 这个控制器里有哪些 group？DT 怎么解析？ get_groups_count、get_group_name、get_group_pins dt_node_to_map（只解析，不写寄存器）

struct pinmux_ops {
    int (*request) (struct pinctrl_dev *pctldev, unsigned offset);
    int (*free) (struct pinctrl_dev *pctldev, unsigned offset);
    int (*get_functions_count) (struct pinctrl_dev *pctldev);
    const char *(*get_function_name) (struct pinctrl_dev *pctldev, unsigned selector);
    int (*get_function_groups) (struct pinctrl_dev *pctldev, unsigned selector,

    int (*gpio_request_enable) (struct pinctrl_dev *pctldev,

    void (*gpio_disable_free) (struct pinctrl_dev *pctldev,
                               struct pinctrl_gpio_range *range, unsigned offset);
    int (*gpio_set_direction) (struct pinctrl_dev *pctldev,
                               struct pinctrl_gpio_range *range,
                               unsigned offset, bool input);

回调 / 字段 作用
get_functions_count 系统中 function 的个数
get_function_name 指定 function 的名称
get_function_groups 指定 function 占用的 pin group（可有多个）
set_mux 把指定 group 配成指定 function，真正改寄存器的动作

pinctrl_dev 是 core 侧的实例，provider 注册后得到的就是它：

十四、pinmux 与 pinconf 的分工 #

pin 和 group 只是操作对象，接下来是两组操作：改电气特性、改功能。pinconf_ops 管上拉、下拉、高阻（tri-state）、驱动能力（drive-strength）：

回调 作用
pin_config_get 读取指定 pin 当前配置，保存在 config 指针中
pin_config_set 设置指定 pin 的配置，可一次配多个 config
pin_config_group_get 读取指定 pin group 的配置项
pin_config_group_set 设置指定 pin group 的配置项

其余是 debug 用接口，用到时再看。

❢重要

必须想明白的一点：pinctrl core 完全不关心 configuration 的具体内容是什么。它只提供 get/set 的通用机制；get 到的东西、set 的东西到底是什么含义、什么数值，是 pinctrl driver 自己的事。整个子系统贯彻「参数是不透明整数」这个原则。

这不是偷懒。电气参数在不同厂商的编码方式千差万别（有的是位域，有的是编码表），core 若想统一解释，就得为每个厂商写转换逻辑，那才是真正的灾难。

pinmux_ops 管功能：A2 和 B5 两个管脚既能当普通 GPIO，也能配成 I2C0 的 SCL/SDA，还能配成 UART5 的 TX/RX。两个 ops 的分界：

维度 pinmux pinconf
管的是 「这根线归谁」 「这根线电气上长什么样」
操作单位 function + group pin 或 group
参数形态 两个 selector（func、group） 不透明整数数组
冲突语义 有，一个 pin 同刻只能给一个 function（strict 决定是否强制） 无冲突概念，后写覆盖前写
典型寄存器 MUX 选择寄存器 PUD / DRV / SMT 寄存器
顺序重要性 必须先定功能再设电气属性 相对独立

最后一行在实践中很关键：如果先把某根线的驱动强度配好，再把它的功能从 GPIO 切成 I2C，某些 SoC 会在切换时把电气配置寄存器复位掉。所以 dts 里的 pin configuration 顺序习惯写成「先 mux，后 conf」，而 map 数组的顺序正好承载这个语义。

十五、设备树里的 pinctrl 绑定 #

15.1 pin state 与 pin map #

把「pin（或 group）+ function + configuration 的组合」反过来读：这个组合可以确定设备的一个状态，在子系统里就叫 pin state。consumer 只发号施令「帮我把 xxx state 激活」，怎么激活是 pinctrl driver 的事。pin state 之上还有一个「状态持有者」，管一个设备的所有状态：

c
/* 一个设备的 pin control state holder，每个需要 pin 的设备都有一个 */
struct pinctrl {
    struct list_head node;      /* 挂进全局链表 pinctrl_list */
    struct device *dev;         /* 对应的 device */
    struct list_head states;    /* 本设备的全部 state 挂在这里 */
    struct pinctrl_state *state;/* 当前生效的 state */
    struct list_head dt_maps;   /* 从 DT 解析出的 mapping table */
    struct kref users;          /* 引用计数，get/put 配对着增减 */
};

/* 一个状态 */
struct pinctrl_state {
    struct list_head node;      /* 挂进 holder 的 states 链表 */
    const char *name;           /* 状态名，如 default / idle / sleep */
    struct list_head settings;  /* 本状态由若干 setting 组成 */
};

/* 一个 setting：真正可执行的最小单元 */
struct pinctrl_setting {
    struct list_head node;
    enum pinctrl_map_type type;
    struct pinctrl_dev *pctldev;
    const char *dev_name;
    union {
        struct pinctrl_setting_mux mux;
        struct pinctrl_setting_configs configs;
    } data;
};

设定某个 state 时，子系统遍历该 state 的 settings 链表逐条执行，按类型分派：

c
enum pinctrl_map_type {
    PIN_MAP_TYPE_INVALID,
    PIN_MAP_TYPE_DUMMY_STATE,        /* 空状态，只为表示 state 存在 */
    PIN_MAP_TYPE_MUX_GROUP,          /* 功能复用：把某 group 配成某 function */
    PIN_MAP_TYPE_CONFIGS_PIN,        /* 配置单个 pin 的电气特性 */
    PIN_MAP_TYPE_CONFIGS_GROUP,      /* 配置整个 pin group 的电气特性 */
};

struct pinctrl_setting_mux { unsigned group; unsigned func; };
struct pinctrl_setting_configs { const char *group_or_pin;
                                 unsigned long *configs; unsigned num_configs; };
ℹ笔记

有 group selector 和 func selector，才能唯一确定设备与 pin mux 的关系（同一个 function 可能对应多个 group）。这两个数字就是 set_mux 的两个入参。

pin state 的信息通过 pin map 收集，一个 map entry 就是一条「某设备的某状态需要做某件事」的记录：

c
/* include/linux/pinctrl/machine.h */
struct pinctrl_map {
    const char *dev_name;       /* 使用本 entry 的设备名 */
    const char *name;           /* 本 entry 所属的 state 名 */
    enum pinctrl_map_type type; /* entry 类型 */
    const char *ctrl_dev_name;  /* pin controller 设备名 */
    union {
        struct pinctrl_map_mux mux;
        struct pinctrl_map_configs configs;
    } data;
};

struct pinctrl_map_mux { const char *group; const char *function; };
struct pinctrl_map_configs { const char *group_or_pin;
                             unsigned long *configs; unsigned num_configs; };

一个设备的某个 state 可以由多个不同类型的 map entry 组合而成。

c
static struct pinctrl_map mapping[] __initdata = {
    PIN_MAP_MUX_GROUP("foo-i2c.0", PINCTRL_STATE_DEFAULT, "pinctrl-foo",
                      "i2c0", "i2c0"),
    PIN_MAP_CONFIGS_GROUP("foo-i2c.0", PINCTRL_STATE_DEFAULT, "pinctrl-foo",
                          "i2c0", i2c_grp_configs),
    PIN_MAP_CONFIGS_PIN("foo-i2c.0", PINCTRL_STATE_DEFAULT, "pinctrl-foo",
                        "i2c0scl", i2c_pin_configs),
    PIN_MAP_CONFIGS_PIN("foo-i2c.0", PINCTRL_STATE_DEFAULT, "pinctrl-foo",
                        "i2c0sda", i2c_pin_configs),
};

四个 entry 描述同一个 state（foo-i2c.0 的 default）：一个 MUX_GROUP 把 i2c0 组切到 i2c0 功能，一个 CONFIGS_GROUP 配整组电气参数，两个 CONFIGS_PIN 分别微调 SCL 和 SDA。

15.2 设备树写法与解析链路 #

旧时代 bsp 要在 machine 代码里静态定义 pin map 数组。引入 device tree 之后，map 的建立分落到两处：pin controller 的 dts node 里定义各设备的 pin state（作为 child node），格式完全由 pinctrl driver 决定，因为解析也是它自己做（dt_node_to_map）；consumer 自己的 dts node 里用 pinctrl-names 加 pinctrl-0/pinctrl-1…… 引用这些 state。

dts
device-node-name {
    pinctrl-names = "sleep", "active";        /* state 名字列表，下标即 ID */
    pinctrl-0 = <&pin_config_0_a>;             /* 名字 sleep 对应 ID 0 */
    pinctrl-1 = <&pin_config_1_a>, <&pin_config_1_b>;  /* active 对应 ID 1，可含多个 */
};

pinctrl-names 定义 state 名列表，ID 从 0 开始递增，名字与 pinctrl-N 按下标对应。state 的划分和电源管理关系紧密：设备 active 时把一组 pin 设成设备功能，进 sleep 时把这组 pin 设成普通 GPIO 并精确控制电平以省功耗。pinctrl-N 是 phandle 列表，指向 pin controller node 下的 pin configuration；一个 state 可以含多个配置——I2C 功能在工作状态下既可能从 pin {7,8} 引出，也可能从 pin {69,103} 引出。consumer 驱动调 pinctrl_get()（或 devm_pinctrl_get()）拿 holder 时，如果这是第一次，子系统会现场把 dts 解析成 map：

text
pinctrl_get / devm_pinctrl_get
    create_pinctrl(drivers/pinctrl/core.c)
        pinctrl_dt_to_map(drivers/pinctrl/devicetree.c)
            dt_to_map_one_config
                pctlops->dt_node_to_map      /* 底层 driver 解析自己的格式 */

pinctrl_dt_to_map() 的循环就是「DT 属性名 → state 名 → phandle 数组 → map 数组」这条链路的全部：

c
int pinctrl_dt_to_map(struct pinctrl *p)
{
    for (state = 0; ; state++) {
        /* 拼出 pinctrl-0、pinctrl-1 …… 属性名，没有就是 state 到头了 */
        propname = kasprintf(GFP_KERNEL, "pinctrl-%d", state);
        prop = of_find_property(np, propname, &size);
        kfree(propname);
        if (!prop)
            break;

        list = prop->value;
        size /= sizeof(*list);        /* size = 本 state 的 phandle 个数 */

        /* 从 pinctrl-names 取 state 名；没写就用属性名里的数字当名字 */
        if (of_property_read_string_index(np, "pinctrl-names",
                                          state, &statename) < 0)
            statename = prop->name + 8;   /* strlen("pinctrl-") == 8 */

        for (config = 0; config < size; config++) {
            phandle = be32_to_cpup(list++);
            np_config = of_find_node_by_phandle(phandle);
            ret = dt_to_map_one_config(p, statename, np_config);
            of_node_put(np_config);
            if (ret < 0)
                goto err;
        }

        /* 该 state 一个 pin configuration 都没写，也要造个 dummy state */
        if (!size && dt_remember_dummy_state(p, statename) < 0)
            goto err;
    }
    return 0;
err:
    pinctrl_dt_free_maps(p);
    return ret;
}

static int dt_to_map_one_config(struct pinctrl *p, const char *statename,
                                struct device_node *np_config)
{
    /* 1. 顺 parent 向上找，直到命中某个 pin controller 的 node */
    for (;;) {
        np_pctldev = of_get_next_parent(np_pctldev);
        if (!np_pctldev || of_node_is_root(np_pctldev))
            return -EPROBE_DEFER;          /* 控制器还没注册，稍后重试 */
        /* 2. 由 node 拿到 struct pinctrl_dev */
        pctldev = get_pinctrl_dev_from_of_node(np_pctldev);
        if (pctldev)
            break;
        /* 设备自己就是 pin controller（hogs 场景），defer 会死循环 */
        if (np_pctldev == p->dev->of_node)
            return -ENODEV;
    }

    /* 3. 交给底层 driver 解析它自己的 binding */
    ops = pctldev->desc->pctlops;
    ret = ops->dt_node_to_map(pctldev, np_config, &map, &num_maps);
    if (ret < 0)
        return ret;

    /* 4. 把解析出的 map 存起来备用 */
    return dt_remember_or_free_map(p, statename, pctldev, map, num_maps);
}

两条边界值得记住：-EPROBE_DEFER 表示 pin controller 还没注册好，稍后重试；-ENODEV 是因为设备自己就是 pin controller（pin controller 也可以给自己定义 pin state，叫 hogs），defer 会变成死循环。

15.3 consumer 接口与驱动模型代劳 #

c
struct pinctrl *pinctrl_get(struct device *dev);
struct pinctrl *devm_pinctrl_get(struct device *dev);   /* 随 device detach 自动释放 */
void pinctrl_put(struct pinctrl *p);
struct pinctrl_state *pinctrl_lookup_state(struct pinctrl *p, const char *name);
int pinctrl_select_state(struct pinctrl *p, struct pinctrl_state *state);

三个必须知道的细节：holder 第一次 get 时动态创建，要读 dts、建 map、逐条 add_setting，代价不小；多次 get 不会重复分配，只把 users 引用计数加一，put 减一，减到 0 才释放全部资源，所以 get/put 必须配对；pinctrl_select_state() 是唯一真正碰硬件的接口，它遍历 settings 调 driver 的 set_mux / pin_config_set。子系统还预定义了三个标准 state 名（include/linux/pinctrl/pinctrl-state.h）：

c
#define PINCTRL_STATE_DEFAULT "default"
#define PINCTRL_STATE_IDLE    "idle"
#define PINCTRL_STATE_SLEEP   "sleep"

既然每个驱动都要写 get、lookup、select 三行，不如让统一设备模型处理。driver 和 device 匹配成功、调 probe 之前，核心已经替你把 pin 配好了：

c
static int really_probe(struct device *dev, struct device_driver *drv)
{
    ...
    ret = pinctrl_bind_pins(dev);   /* 先配 pin，再 probe */
    ...
}

int pinctrl_bind_pins(struct device *dev)
{
    /* (1) 给 dev->pins 分配空间 */
    dev->pins = devm_kzalloc(dev, sizeof(*(dev->pins)), GFP_KERNEL);

    /* (2) 拿 holder */
    dev->pins->p = devm_pinctrl_get(dev);

    /* (3) 找三个标准 state */
    dev->pins->default_state = pinctrl_lookup_state(dev->pins->p,
                                     PINCTRL_STATE_DEFAULT);
    dev->pins->sleep_state   = pinctrl_lookup_state(dev->pins->p,
                                     PINCTRL_STATE_SLEEP);
    dev->pins->idle_state    = pinctrl_lookup_state(dev->pins->p,
                                     PINCTRL_STATE_IDLE);

    /* (4) 立刻切到 default 状态 */
    ret = pinctrl_select_state(dev->pins->p, dev->pins->default_state);
    return 0;
}

struct dev_pin_info {
    struct pinctrl *p;                       /* 本设备的 state holder */
    struct pinctrl_state *default_state;     /* default 状态 */
    struct pinctrl_state *sleep_state;       /* 电源管理用 */
    struct pinctrl_state *idle_state;        /* 电源管理用 */
};
✦提示

这条机制的实际含义：只要 consumer 在 dts 里写了 pinctrl-names = "default" 和 pinctrl-0，它的驱动一行 pinctrl 代码都不用写，probe 时引脚已经配好了。只有设备需要在运行中切换状态（比如音频 codec 进出低功耗）才需要自己调 pinctrl_select_state()。这也解释了一个常见困惑：明明驱动里搜不到 pinctrl 调用，引脚却是对的——功劳在 pinctrl_bind_pins()。

两种建 map 的方式：machine driver 静态定义（一个巨大的 mapping table，初始化时调 pinctrl_register_mappings() 注册，用于 DT 普及之前的 BSP），或者 device tree（信息分两处写，运行时由 pinctrl_dt_to_map() 合成）。DT 方式的好处是 pinctrl driver 只要定好格式，板级差异全在 dts 里，换板子不用改 C 代码。

15.4 实例：S3C2416 的 dts 与注册动作 #

每个 pin configuration 都是 pin controller node 的 child node，格式与具体控制器相关，只有对应的 pinctrl driver 知道怎么解析。配置信息属于控制器（它知道寄存器怎么写），但需要被 client 引用，client 通过属性指向某个 child node 就把两者连起来了。Samsung 24xx 系列的 pin configuration 分两类：

dts
pinctrl@56000000 {
    /* 第一类：pin bank，描述一个 GPIO 控制器 */
    gpf: gpf {
        gpio-controller;              /* 本节点是一个 GPIO controller */
        #gpio-cells = <2>;            /* 描述一个 GPIO 需要 2 个 cell */
        interrupt-controller;         /* 本节点同时是中断控制器 */
        #interrupt-cells = <2>;
        phandle = <0xc>;
    };

    /* 第二类：功能复用配置，描述某功能用哪些引脚、写什么值 */
    uart0-data: uart0-data {
        samsung,pins = "gph-0", "gph-1";   /* 涉及 gph bank 的第 0、1 号引脚 */
        samsung,pin-function = <2>;         /* 向功能选择寄存器写 2 = UART */
        phandle = <0x2>;
    };

    uart0-fctl: uart0-fctl {
        samsung,pins = "gph-8", "gph-9";   /* 同一个 UART0，另一组可用引脚 */
        samsung,pin-function = <2>;
        phandle = <0x3>;
    };
};

serial@50000000 {
    ...
    pinctrl-names = "default";                 /* 只定义一个状态 */
    pinctrl-0 = <&uart0_data>, <&uart0_fctl>;  /* 该状态可含多个配置 */
};

S3C2416 定义了 gpa 到 gpm 共 11 个 bank node，138 个 I/O 端口（也叫 pin、finger、pad）分成 11 个 bank——这里刻意不用 group 这个术语，是为了和 pin group 区分开。分 bank 的理由是把特性相同的 GPIO 归到一起：这 11 个 bank 中只有 GPF 和 GPG 两个 bank 上的引脚有中断功能。gpio-controller 声明这是 GPIO 控制器；#gpio-cells 说明用几个 cell 描述一个 GPIO；#interrupt-cells 概念类似；phandle 定义句柄供其他节点引用（linux,phandle 是 old-style 同义属性，两个都写是为了兼容）。uart0-data 与 uart0-fctl 是同一个 UART0 的两种引出方式——「一个 function 可能对应多个 pin group」的实例。

ℹ笔记

2416 的 dts 里 pinctrl-0 同时引用两组是历史写法习惯（老 dts 常把候选都写上）。严格讲一个 state 应该只包含该板实际使用的那一组。读老 dts 看到这种写法不必奇怪，能跑是因为底层只把能生效的那一组配上了。

provider 侧初始化两件事：注册 platform driver，在 probe 里注册 pin control device。compatible = "samsung,s3c2416-pinctrl" 与 of_match_table 对上就匹配了；统一设备模型的匹配顺序是先 OF style（of_driver_match_device），再 ACPI style，再 id_table，最后 fallback 到比较名字。

c
static const struct of_device_id samsung_pinctrl_dt_match[] = {
    { .compatible = "samsung,s3c2416-pinctrl",
      .data       = s3c2416_pin_ctrl },   /* 指向该 SoC 的 pin bank 静态描述 */
    {},
};

static int samsung_pinctrl_probe(struct platform_device *pdev)
{
    /* (1) 私有数据，devm 分配随 detach 自动释放 */
    drvdata = devm_kzalloc(&pdev->dev, sizeof(*drvdata), GFP_KERNEL);

    /* (2) 按 DT 信息 + 静态表初始化 SoC 描述符，ioremap 寄存器 */
    ctrl = drvdata->ctrl = samsung_pinctrl_get_soc_data(drvdata, pdev);
    drvdata->dev = &pdev->dev;
    res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
    drvdata->virt_base = devm_ioremap_resource(&pdev->dev, res);

    ret = samsung_gpiolib_register(pdev, drvdata);      /* (3) 各 bank 注册成 gpio chip */
    ret = samsung_pinctrl_register(pdev, drvdata);      /* (4) 注册 pin control device */

    /* (5) GPIO 型中断控制器（只有 gpf / gpg 两个 bank 有） */
    if (ctrl->eint_gpio_init)
        ctrl->eint_gpio_init(drvdata);

    platform_set_drvdata(pdev, drvdata);
    list_add_tail(&drvdata->node, &drvdata_list);
    return 0;
}

驱动私有的 drv_data 把硬件相关和框架无关的信息收在一起，而 ctrl 装的是纯硬件知识——那些内容不可能出现在 core 里，因为不是所有 pin controller 都分 bank：

c
struct samsung_pinctrl_drv_data {
    struct list_head        node;        /* 多个 pin controller 可形成链表 */
    void __iomem            *virt_base;  /* 寄存器基地址 */
    struct device           *dev;        /* 对应的 platform device */
    int                     irq;         /* 2416 的 pin controller 本身不需要 irq */
    struct samsung_pin_ctrl *ctrl;       /* 硬件相关的 SoC 描述符 */
    struct pinctrl_desc     pctl;        /* 硬件无关的 pin controller 描述符 */
    struct pinctrl_dev      *pctl_dev;   /* core 中的 pin controller class device */
    const struct samsung_pin_group *pin_groups;   /* group 信息 */
    unsigned int            nr_groups;
    const struct samsung_pmx_func  *pmx_functions;/* function 信息 */
    unsigned int            nr_functions;
};

struct samsung_pin_ctrl {
    struct samsung_pin_bank *pin_banks;   /* 名字、引脚数、寄存器偏移 */
    u32                     nr_banks;
    u32                     base;         /* 本控制器在全局 pin ID 空间中的起始编号 */
    u32                     nr_pins;      /* 本控制器可控 pin 总数 */
    /* 其余成员与 GPIO 型中断控制器有关 */

base 解决全局编号问题。系统可能有多个 pin controller：A 控制 32 个 pin，B 控制 64 个，统一编号后 A 占 0~31，B 占 32~95，B 的 pin base 就是 32。samsung_pinctrl_register() 把硬件描述变成 core 认识的 struct pinctrl_desc，六步：

c
static int samsung_pinctrl_register(struct platform_device *pdev,
                                    struct samsung_pinctrl_drv_data *drvdata)
{
    struct pinctrl_desc *ctrldesc = &drvdata->pctl;
    struct pinctrl_pin_desc *pindesc;
    struct samsung_pin_bank *pin_bank;
    int pin, bank, ret;

    /* A. 填硬件无关的 pinctrl_desc：三个 ops 表是 core 唯一的调用入口 */
    ctrldesc->name    = "samsung-pinctrl";
    ctrldesc->owner   = THIS_MODULE;
    ctrldesc->pctlops = &samsung_pctrl_ops;    /* group 枚举 + DT 解析 */
    ctrldesc->pmxops  = &samsung_pinmux_ops;   /* 复用 */
    ctrldesc->confops = &samsung_pinconf_ops;  /* 电气特性 */

    /* B. 一次分配全部 pin 描述符，ctrldesc->pins 指向它 */
    pindesc = devm_kzalloc(&pdev->dev, sizeof(*pindesc) * drvdata->ctrl->nr_pins,
                           GFP_KERNEL);
    ctrldesc->pins  = pindesc;
    ctrldesc->npins = drvdata->ctrl->nr_pins;

    /* C. 逐个填 number（pin + ctrl->base，全局唯一）与 name（"gph-0" 形式） */
    ...

    /* D. 从 DT 解析出 group 和 function */
    ret = samsung_pinctrl_parse_dt(pdev, drvdata);

    /* E. 注册到 pinctrl core —— 这里的核心动作 */
    drvdata->pctl_dev = pinctrl_register(ctrldesc, &pdev->dev, drvdata);

    /* F. 为每个 bank 建 gpio range，供 GPIO 子系统反查 pin，见第十六章 */
    for (bank = 0; bank < drvdata->ctrl->nr_banks; ++bank)
        pinctrl_add_gpio_range(drvdata->pctl_dev,
                               &drvdata->ctrl->pin_banks[bank].grange);
    return 0;
}

步骤 C 两件事：number 用 pin + ctrl->base 保证全局唯一；name 用 "<bank>-<pin>" 格式（gph-0），与 DT 里 samsung,pins 的写法对应。步骤 F 里 grange 的 base/pin_base/npins/gc 四个字段就是第十六章那个映射表的全部内容。直接在 pin controller driver 里调 pinctrl_add_gpio_range() 是不推荐的，规范做法是在 GPIO controller 的 DT 节点里用 gpio-ranges 属性描述，让 gpiolib 自己建。

DT 解析那一步，samsung_pinctrl_parse_dt() 把每个 child node 解析成两个描述符：用 samsung,pins 是否存在判断「这是不是 pin configuration」（跳过 bank node），只有带 samsung,pin-function 的节点才额外生成 function：

c
struct samsung_pin_group {
    const char        *name;      /* DT node name + "-grp" */
    const unsigned int *pins;     /* pin list */
    u8                num_pins;
    u8                func;       /* samsung,pin-function 的值，写入功能选择寄存器 */
};

struct samsung_pmx_func {
    const char        *name;      /* DT node name + "-mux" */
    const char        **groups;   /* 属于本 function 的 group 指针数组 */
    u8                num_groups; /* 实现中恒为 1 */
};
✦提示

名字后缀（-grp / -mux）不是装饰。DT 里同一个 node 同时描述「哪些引脚」（group）和「配成什么功能」（function），一个 node 被解析成两个对象，自然需要两个不同的名字，否则在 sysfs 和 debugfs 里就分不清了。

三个查询回调几乎是纯 getter，因为它们只是把 driver 私有数据里的数组按 selector 下标取出来：

c
static int samsung_get_group_count(struct pinctrl_dev *pctldev)
{
    struct samsung_pinctrl_drv_data *drvdata = pinctrl_dev_get_drvdata(pctldev);
    return drvdata->nr_groups;
}
/* get_group_name / get_group_pins 同一路子：取回私有数据，再按 selector 下标取数组元素 */

pinctrl_dev_get_drvdata() 是这三行代码的共同起点：从 core 的 class device 拿回 driver 注册时传入的私有数据。这正是「core 完全不知道 pins 数组内容」的具体体现——core 只存指针，解释权归 driver。pmxops 里真正干活的是 set_mux（定位 group 的引脚列表和 func 值，批量写功能选择寄存器），confops 里真正干活的是 pin_config_set（把不透明的 config 值翻译成寄存器位域）。两个函数都涉及寄存器细节，本节不展开——理解了数据结构，剩下的就是照 datasheet 写位域。

十六、pinctrl 与 GPIO 的关系：两个框架怎么协作 #

16.1 逻辑上很清楚，实际不是 #

按理说关系应该非常清楚：pinctrl 管理系统的所有管脚，GPIO 是这些管脚的用途之一，因此 GPIO 子系统应该是 pinctrl 子系统的 client（也叫 backend、consumer），基于 pinctrl 提供的功能处理 GPIO 相关逻辑。从逻辑上讲这一点很明确：gpio subsystem 永远是 pinctrl 的 backend。据此，规范做法是：任何一个 gpio chip 在使用 GPIO 时（也就是 gpio 子系统的 consumer 申请 GPIO 资源时），都要向 pinctrl 子系统申请管脚，并把管脚配置为 GPIO 功能。但实际情况不是这么简单，两者有着相当紧密的耦合。

16.2 规范做法的困难 #

用一个最简单的例子说明。假设某个 gpio chip 只包含 2 个 gpio，分别和 uart 功能复用。

  • 如果这两个管脚是同时控制的（要么都是 gpio，要么都是 uart），很好处理。按 pinctrl 的精神抽象出两个 function：gpio 和 uart，要用 gpio 功能时调 set state 切过去。
  • 但很多硬件支持分开控制，麻烦就来了。每个 gpio 都要单独抽象成一个 function，于是得到 3 个：gpio1、gpio2、uart。

再往前推一步：考虑一个包含 32 个 gpio 的 chip（一般硬件的 gpio bank 就是 32 个）。如果它们都能单独控制，就会出现 32 个 function。系统里不止一个 chip，于是 device tree 会被一坨坨的 gpio functions 撑爆。这是典型的「抽象纯度」与「可用性」的冲突：规范是追求的目标，但有限度。于是做法是：在 pinctrl 子系统的标准框架上打个洞，碰到这种情况直接走后门。

❢重要

这个「洞」不是设计失误，而是显式承认的例外。边界很清楚：标准路径仍然是 pinctrl function/group 模型；只有在「一个 bank 内每个 gpio 都能独立控制」这种粒度细到无法用 function 表达时，才走后门。后门的入口只有 gpio 子系统能用，其他 consumer 一律走标准接口。

16.3 后门：pinctrl_request_gpio #

当 gpio driver 需要使用某个管脚时，直接调 pinctrl_request_gpio() 向 pinctrl 子系统申请：

c
int pinctrl_request_gpio(unsigned gpio);

pinctrl 子系统维护一个 gpio number 到 pin number 的 map，把 gpio number 转成 pin number 之后，调 struct pinmux_ops 中有关的回调（字段定义见第十三章）：

c
struct pinmux_ops {
    ...
    int (*gpio_request_enable) (struct pinctrl_dev *pctldev,
                                struct pinctrl_gpio_range *range, unsigned offset);
    void (*gpio_disable_free) (struct pinctrl_dev *pctldev,
                               struct pinctrl_gpio_range *range, unsigned offset);
    int (*gpio_set_direction) (struct pinctrl_dev *pctldev,
                               struct pinctrl_gpio_range *range,
                               unsigned offset, bool input);
};

分工因此清晰：gpio driver 要做的事，就是提供 gpio number 到 pin number 的 map；pinctrl 子系统做自己分内的事——管理系统 pin 资源，并根据 gpio 子系统的请求把某些 pin 配成 GPIO 功能。看 pinctrl_request_gpio() 的实现，能看清后门的完整代价：

c
int pinctrl_request_gpio(unsigned gpio)
{
    /* A. 按 gpio 编号找到对应的 pin controller 和 gpio range */
    ret = pinctrl_get_device_gpio_range(gpio, &pctldev, &range);
    if (ret)
        return pinctrl_ready_for_gpio_range(gpio) ? 0 : ret;

    mutex_lock(&pctldev->mutex);
    pin = gpio_to_pin(range, gpio);                        /* gpio ID -> pin ID */
    ret = pinmux_request_gpio(pctldev, range, pin, gpio);   /* B */
    mutex_unlock(&pctldev->mutex);
    return ret;
}

申请 GPIO 资源本应是 GPIO 子系统的责任，但受硬件所限，pinctrl 提供了这个函数供 gpio driver 使用。其他内核 driver 不应该调它，它们应该走 GPIO 子系统提供的接口。代价是显式的：pinctrl 作为 pin 空间的管理者，除了维护 pin ID，还要维护 gpio ID 以及两者的关系。这个函数在子系统边界上并不好看，但它解决的问题（16.2 的 32 个 function）比难看严重得多。

A、B 两步各有含义：A 按 gpio ID 找到对应的 struct pinctrl_dev 和 pinctrl_gpio_range。core 中每个 low level pin controller device 都映射成一个 struct pinctrl_dev 并形成链表（表头 pinctrldev_list）。实际硬件常把 GPIO 分成若干 bank（每个 bank 是一个 HW GPIO controller block），一个 pin controller 管理的 gpio ID 是分区域的，每个区域用一个 pinctrl_gpio_range 抽象。B pinmux_request_gpio() 做两件事：在 core 中标记该 pin 已被用作 GPIO，后续若有模块再申请该资源 core 可以拒绝；调底层 driver 的回调 gpio_request_enable，做真正的寄存器操作。

配套还有三个接口：pinctrl_free_gpio() 是 pinctrl_request_gpio() 的逆操作；pinctrl_gpio_direction_input() 和 pinctrl_gpio_direction_output() 为已指定为 GPIO 功能的引脚设定方向。

16.4 gpio range：那个 map #

c
/* include/linux/pinctrl/pinctrl.h */
struct pinctrl_gpio_range {
    struct list_head node;
    const char *name;          /* 本 range 对应的 chip 名 */
    unsigned int id;           /* 本 range 的编号 */
    unsigned int base;         /* GPIO 编号空间的起始 */
    unsigned int pin_base;     /* pin 编号空间的起始（pins 为 NULL 时有效） */
    unsigned const *pins;      /* 非线性映射的查找表，NULL 表示线性映射 */
    unsigned int npins;        /* 本 range 覆盖的引脚数（含 base） */
    struct gpio_chip *gc;      /* 对应的 gpio chip，可选 */
};

核心对应关系一句话：

gpio controller（gc）中的 gpio(base) 到 gpio(base + npins - 1)，与 pin controller 中的 pin(pin_base) 到 pin(pin_base + npins - 1) 一一对应。

有了它，pinctrl 就能把任意一个 gpio controller 中的 gpio number 转成相应 pin controller 中的 pin number。两种映射由 pins 是否为 NULL 区分：

映射方式 判据 转换规则
线性映射 pins == NULL，pin_base 有效 gpio base 为 a、pin base 为 b，则 a↔b、a+1↔b+1、a+2↔b+2……
非线性映射 pin_base 无效，pins 有效 以 gpio ID 为索引查 lookup table（pins 数组）得 pin ID

gc 字段说明一个事实：每个 GPIO bank 都是一个 gpio chip，对应一个 gpio range，这也是 range 要带 id、base 这些分区域字段的原因。low level pin controller 初始化时（samsung_pinctrl_register 的步骤 F）会把每个 bank 表示的 range 用 pinctrl_add_gpio_range() 挂进 pin control device 的 gpio_ranges 链表。

16.5 通过 device tree 提供 gpio range #

dts
qe_pio_e: gpio-controller@1460 {
    #gpio-cells = <2>;
    compatible = "fsl,qe-pario-bank-e", "fsl,qe-pario-bank";
    reg = <0x1460 0x18>;
    gpio-controller;
    gpio-ranges = <&pinctrl1 0 20 10>, <&pinctrl2 10 50 20>;

gpio-ranges 每个 cell 组是四元组 <&控制器 gpio起始 pin起始 个数>。上面例子声明两个 range：gpio@1460 的 gpio0~9 对应 pinctrl1 的 pin20~29；同一个 controller 的 gpio10~29 对应 pinctrl2 的 pin50~69。一个 gpio chip 的编号空间可以被切分到多个 pin controller 上——只要 pin 的物理归属确实如此。手工调 pinctrl_add_gpio_range() 的方式已经过时，解析链路由 gpiolib 接管：

text
devm_gpiochip_add_data(drivers/gpio/gpiolib.c)
    gpiochip_add_data
        of_gpiochip_add(drivers/gpio/gpiolib-of.c)
            of_gpiochip_add_pin_range
                gpiochip_add_pin_range(drivers/gpio/gpiolib.c)
                    pinctrl_find_and_add_gpio_range(drivers/pinctrl/core.c)

这一串调用的结果是在对应 pin controller 的数据结构里长出一条 gpio range 链表。pinctrl_dev 里同时有 pin_desc_tree（pin 编号到描述符的 radix tree）和 gpio_ranges（gpio 到 pin 的映射区段链表）。同一个控制器要维护两套编号空间，这就是 16.3 说的那个代价的具体形态。

16.6 使用路径：一次 gpio_request 走到哪 #

  1. gpio 子系统的 consumer 调 gpio_request()（或 gpiod_get()）；
  2. 该请求落到具体 gpio chip 的 request 回调（或 gpiolib 默认实现）里；
  3. 那里调 pinctrl core 提供的 pinctrl_request_gpio(gpio)，参数是 gpio 编号；
  4. pinctrl core 遍历 gpio_ranges 链表找到匹配的 range，把 gpio 编号转成 pin 编号；
  5. 调 pin controller driver 的 gpio_request_enable()，用 pin 编号申请该 pin 并配成 GPIO 功能；
  6. 返回。此后方向设置走 pinctrl_gpio_direction_input/output()，释放走 pinctrl_free_gpio()。

至此耦合完整了：标准路径是 consumer 告诉 pinctrl 自己要什么 state；后门路径是 gpio 子系统告诉 pinctrl 自己要哪根 pin。两条路径共用同一套底层回调，差别只在谁发起、粒度多细。

十七、I2C framework 的整体结构 #

I2C 是主从式两线总线。硬件上一条总线由四样东西组成：一个主控端（SoC 里的 I2C controller），一个或多个从设备（PMIC、codec、EEPROM、触摸屏），两根信号线 SDA（数据）和 SCL（时钟），以及两根线上各一只上拉电阻。SDA 与 SCL 都是开漏结构，靠上拉电阻把总线拉到高电平，任何一端拉低就把线拉低——这是「线与」语义，也是 I2C 支持多主控与时钟拉伸的物理基础。总线上每个从设备有一个 7 bit 地址，主控通过地址选择对话对象。

内核只抽象了一半：

所有运行 linux kernel 的设备，在 I2C 总线里面，都是 I2C master（至于 I2C slave，kernel 不管）。

正是基于这个假设，Linux I2C framework 才成为现在这个样子。I2C slave 模式在 3.x 只有零散的厂商补丁，没有进框架主干（具体进主线的版本未验证）。软件拓扑用设备模型的那一套映射：

text
/sys/bus/platform                 /sys/bus/i2c
   │                                 │
   └── i2c controller (platform dev) ──> I2C adapter（虚拟实体，挂在 i2c bus 上）
                                            ├── i2c client（pmic@08）
                                            ├── i2c client（codec@1a）
                                            └── ...
  1. platform bus 挂的是和 CPU 通过系统总线相连的外设。I2C 控制器直接从属于 platform bus；我们常说的「I2C driver」都是指 I2C controller driver，都以 platform driver 的形式存在，对应的控制器是 platform device。
  2. 同时 kernel 抽象出 I2C bus（/sys/bus/i2c），用于挂载通过 I2C 总线连接的各个 slave device。
  3. 特殊之处：I2C core 用一个虚拟实体——I2C adapter——抽象 controller 的有关功能（主要是数据收发），adapter 也挂在 I2C bus 上。
  4. 两者都挂在 I2C bus 上，master 与 slave 的匹配就能按设备模型的常规套路做，访问 slave 走 I2C core 提供的统一接口。

在这个拓扑上搭出来的软件框架有四块：

模块 位置 干什么
I2C core drivers/i2c/i2c-core.c 硬件无关核心：adapter/client 注册、匹配、传输分发
I2C busses drivers/i2c/busses/ 各家的 controller driver，工程师嘴里的「I2C driver」
I2C algos drivers/i2c/algos/ 协议包生成方法（algorithm）；多数由硬件实现，一般不用看
I2C muxes drivers/i2c/muxes/ 总线多路复用，冷门功能

I2C core 内部再分两对抽象：用 adapter + algorithm 抽象 I2C controller，用 client + driver 抽象 I2C slave device（对应设备模型里的 device 和 driver）。在这之上按 I2C 协议又长出一层 SMBus（System Management Bus）兼容接口。框架的最终目标只有一个：提供「访问 I2C slave device」的方法。consumer 不用关心总线时序，只调几个 API 就能和 slave 交换数据；内核态 consumer 大多是别的驱动（HDMI、触摸屏、PMIC 的 regulator 子驱动），用户空间则通过 /dev/i2c-N 字符设备访问同一个 adapter。

一条边界要记住：I2C controller 是 platform device，I2C slave 是 i2c device。同一颗芯片若既是控制器又是从设备，就得在两个 bus 上各出现一次，这是设备模型的常态，不是框架的缺陷。

十八、adapter 的注册 #

controller driver 的活是「把寄存器操作包装成 algorithm，然后注册成 adapter」。生产者侧的完整写法在 D 目录的 I2C controller driver：怎么写适配器驱动，这里只看框架侧的契约。

c
/* include/linux/i2c.h，3.x */
struct i2c_algorithm {
    /* master_xfer 是必须实现的：一次传输若干条 msg */
    int (*master_xfer)(struct i2c_adapter *adap, struct i2c_msg *msgs, int num);
    /* smbus_xfer 可选：SMBus 协议族的实现 */
    int (*smbus_xfer)(struct i2c_adapter *adap, u16 addr, unsigned short flags,
                      char read_write, u8 command, int size,
                      union i2c_smbus_data *data);
    u32 (*functionality)(struct i2c_adapter *);
#if defined(CONFIG_I2C_SLAVE)
    int (*reg_slave)(struct i2c_client *client);
    int (*unreg_slave)(struct i2c_client *client);
#endif
};

struct i2c_adapter {
    struct module *owner;
    unsigned int class;                /* 允许绑定的驱动类型，如 I2C_CLASS_HWMON */
    const struct i2c_algorithm *algo;  /* 干活的那一组回调 */
    void *algo_data;

    int nr;                            /* 总线号，决定 /dev/i2c-N 和 sysfs 里的 i2c-N */
    char name[48];
    struct completion dev_released;

    struct mutex userspace_clients_lock;
    struct list_head userspace_clients; /* 用户空间 new_device 建出来的 client */

    struct i2c_bus_recovery_info *bus_recovery_info;
    struct device dev;                 /* 嵌进去的设备模型对象 */
    ...
};
  • 最终干活的是 master_xfer。整条 I2C 栈到了最底下就是把 struct i2c_msg 数组翻译成总线上的 START / 地址 / 数据 / STOP 时序。
  • nr 是总线号，一旦分配就决定了 /dev/i2c-N 的 N。i2c_add_adapter() 让 core 动态挑一个，i2c_add_numbered_adapter() 用 driver 填好的 nr，冲突就注册失败。用户空间脚本硬编码 /dev/i2c-1 在动态分配下不牢靠。
  • class 是给旧式 detect 用的位掩码。3.x 时代 i2c_new_probed_device() 会按 class 探测总线上的设备，i2c_detect() 让一个驱动监视整条总线。这套机制在 DT 普及后基本退场，新驱动不要碰。
  • dev 是内嵌的 struct device，adapter 在设备模型里是真设备，有 of_node、有 parent（也就是它那个 platform device）。
text
i2c_add_adapter / i2c_add_numbered_adapter
    i2c_register_adapter
        device_register / of_i2c_register_devices   /* 触发 client 创建 */

i2c_register_adapter() 里有一步是这里的重点：注册 adapter 时会顺带把它下面的 slave 都实例化出来（具体是 of_i2c_register_devices() 扫 adapter->dev.of_node 的 child node）。所以「先有 adapter，后有 client」是框架的固定顺序，consumer 拿不到 adapter 时唯一正确的反应就是 -EPROBE_DEFER。

十九、client 的注册与匹配 #

struct i2c_client 抽象一个从设备，对应设备模型里的 struct device：

c
/* include/linux/i2c.h */

/**
 * struct i2c_client - represent an I2C slave device
 * @flags: I2C_CLIENT_TEN indicates the device uses a ten bit chip address;
 *      I2C_CLIENT_PEC indicates it uses SMBus Packet Error Checking
 * @addr: Address used on the I2C bus connected to the parent adapter.
 * @name: Indicates the type of the device, usually a chip name that's
 *      generic enough to hide second-sourcing and compatible revisions.
 * @adapter: manages the bus segment hosting this I2C device
 * @dev: Driver model device node for the slave.
 * @irq: indicates the IRQ generated by this device (if any)
 * @detected: member of an i2c_driver.clients list or i2c-core's
 *      userspace_devices list
 *
 * An i2c_client identifies a single device (i.e. chip) connected to an
 * i2c bus. The behaviour exposed to Linux is defined by the driver
 * managing the device.
 */
struct i2c_client {
        unsigned short flags;           /* div., see below              */
        unsigned short addr;            /* chip address - NOTE: 7bit    */
                                        /* addresses are stored in the  */
                                        /* _LOWER_ 7 bits               */
        char name[I2C_NAME_SIZE];
        struct i2c_adapter *adapter;    /* the adapter we sit on        */
        struct device dev;              /* the device structure         */
        int irq;                        /* irq issued by device         */
        struct list_head detected;
};
  1. flags 指示该 slave device 的一些特性：I2C_CLIENT_PEC（用 SMBus Packet Error Checking）、I2C_CLIENT_TEN（用 10 bit 从地址）、I2C_CLIENT_WAKE（具备 wakeup 能力）。
  2. addr 是 7 bit 的 slave 地址。注意注释那句话——7 bit 地址存在低位那 7 位里，所以读方向位要用 addr << 1，不是在 addr 上或 1。
  3. adapter 是该设备所在的 I2C controller；irq 是 irq number（如果有）；dev 是嵌进来的设备模型对象，client->dev.of_node 走的是通用设备模型路径。

struct i2c_client 由 I2C core 在注册 adapter 时解析其 child node 自行创建，有些字段可通过 DTS 配置：

dts
xxx:xxx@08 {
	reg = <0x08>;                               /* 对应struct i2c_client中的‘addr’*/
	interrupts = <16 8>;                       /* 对应struct i2c_client中的‘irq’*/
	wakeup-source;                             /* 对应flags中的I2C_CLIENT_WAKE */
};

三个绑定关系要背下来：节点名的 @ 后缀必须等于 reg 的值（I2C core 用 reg 当 slave 地址，后缀只是给人看的）；reg 写 7 bit 地址，不写移位后的 8 bit 值；interrupts 走标准 interrupt 绑定，解析结果存进 client->irq。匹配是设备模型的标准流程，i2c_device_match() 依次比三样东西：

顺序 比什么 说明
1 of_driver_match_device() DT 的 compatible 对 of_match_table
2 acpi_driver_match_device() ACPI 平台
3 i2c_match_id() id_table 里的名字对 client->name 
c
static struct i2c_driver foo_driver = {
    .driver = {
        .name           = "foo",
        .owner          = THIS_MODULE,
        .of_match_table = foo_of_match,   /* compatible 列表 */
        .pm             = &foo_pm_ops,    /* 可选：suspend/resume */
    },
    .probe    = foo_probe,     /* 3.x 签名：int (*)(struct i2c_client *, const struct i2c_device_id *) */
    .remove   = foo_remove,
    .id_table = foo_id_table,
};
module_i2c_driver(foo_driver);

probe() 的签名在 3.x 和 4.x 之间变过：老的是 (struct i2c_client *client, const struct i2c_device_id *id)，新的只收 client（id 可以用 i2c_client_get_device_id() 反查）。写 3.x 代码就按前者。module_i2c_driver() 是 3.3 之后引入的宏，展开成 init/exit 两个函数，替掉手写 i2c_add_driver()/i2c_del_driver()。

二十、i2c_transfer 与 SMBus 接口 #

I2C 传输的最小单位不是字节，是一条消息：

c
/* include/linux/i2c.h */
struct i2c_msg {
    __u16 addr;     /* slave address                        */
    __u16 flags;
#define I2C_M_TEN       0x0010  /* this is a ten bit chip address */
#define I2C_M_RD        0x0001  /* read data, from slave to master */
#define I2C_M_NOSTART   0x4000  /* if I2C_FUNC_PROTOCOL_MANGLING */
#define I2C_M_REV_DIR_ADDR  0x2000
#define I2C_M_IGNORE_NAK    0x1000
#define I2C_M_NO_RD_ACK     0x0800
#define I2C_M_RECV_LEN      0x0400
    __u16 len;      /* msg length，u16 所以单条消息 < 64K */
    __u8 *buf;      /* pointer to msg data */
};

一条 msg 对应一段「START + 地址 + 若干字节 + （可选）STOP」。i2c_transfer() 一次传多条，相邻两条之间的行为由 I2C_M_NOSTART 之类标志决定——这是 I2C 世界的核心概念 repeated START：读寄存器时先用写方向发寄存器地址，再在不发 STOP 的情况下切换成读方向继续读，中间那个重复的 START 靠的就是 msg 之间没有 STOP。

c
/* include/linux/i2c.h */

/*
 * The master routines are the ones normally used to transmit data to devices
 * on a bus (or read from them). Apart from two basic transfer functions to
 * transmit one message at a time, a more complex version can be used to
 * transmit an arbitrary number of messages without interruption.
 * @count must be be less than 64k since msg.len is u16.
 */
extern int i2c_master_send(const struct i2c_client *client, const char *buf,
                           int count);
extern int i2c_master_recv(const struct i2c_client *client, char *buf,
                           int count);

/* Transfer num messages.
 */
extern int i2c_transfer(struct i2c_adapter *adap, struct i2c_msg *msgs,
                        int num);
/* Unlocked flavor */
extern int __i2c_transfer(struct i2c_adapter *adap, struct i2c_msg *msgs,
                          int num);

一类以 i2c client 为参数做简单的数据收发，包括 i2c_master_send / i2c_master_recv，只能通过标准方式发送或接收一定数量的数据。另一类以 i2c adapter 和 i2c msg 为参数，可以更灵活地读写，包括 i2c_transfer——以 struct i2c_msg 为参数，一次可以只读、只写，或者读加写。

维度 i2c_master_send / i2c_master_recv i2c_transfer SMBus 一族

SMBus 一族在 3.x 是完整的一套（i2c_smbus_read_byte_data()、i2c_smbus_write_word_data() 等等）。不要把它当成 I2C 的方便封装：SMBus 只支持 7 bit 地址、有时限要求、还规定了数据传输格式。I2C 设备不一定是 SMBus 设备，反过来也一样。

i2c_transfer() 是整条栈的收口：

c
int i2c_transfer(struct i2c_adapter *adap, struct i2c_msg *msgs, int num)
{
    int ret;

    /* ① adapter 必须支持 I2C 功能 */
    if (!adap->algo->master_xfer) {
        dev_dbg(&adap->dev, "I2C level transfers not supported\n");
        return -EOPNOTSUPP;
    }

    /* ② 同一时刻一条总线只允许一次传输，先上锁 */
    i2c_lock_adapter(adap);

    /* ③ 有 mux 的走 mux 路径，普通路径直发 */
    if (adap->muxc) {
        ret = i2c_mux_master_xfer(adap, &msgs[0], num);
    } else {
        ret = __i2c_transfer(adap, msgs, num);
    }

    i2c_unlock_adapter(adap);
    return ret;
}

{

这段是按 3.x 行为的重构写法，不是逐字复制——i2c_lock_adapter() 这个封装是 3.10 之后才有的，之前的版本直接 mutex_lock(&adap->bus_lock)（具体版本未验证）。三个要点：

  1. master_xfer 缺席就没有 I2C 传输可谈。adapter 只实现了 SMBus 时，i2c_transfer() 直接返回 -EOPNOTSUPP。
  2. 锁的粒度是整条 adapter。同一时刻一条总线只能有一次传输，这是物理约束。要连续发多段且不许别人插进来，把多段都放进同一次 i2c_transfer() 的 msgs 数组，不要分两次调用。
  3. adap->quirks 描述控制器的怪癖，I2C_AQ_NO_CLK_STRETCH 之类标志会影响 core 的行为，写 controller driver 时才需要关心。

返回值是成功传输的 msg 条数，不是字节数。这个差别坑过很多人：

c
struct i2c_msg msgs[2];

msgs[0].addr = client->addr;
msgs[0].flags = 0;                 /* 写：发寄存器地址 */
msgs[0].len = 1;
msgs[0].buf = &reg;

msgs[1].addr = client->addr;
msgs[1].flags = I2C_M_RD;          /* 读：收数据 */
msgs[1].len = 2;
msgs[1].buf = buf;

ret = i2c_transfer(client->adapter, msgs, 2);
if (ret == 2)                       /* 不是 ret == 2 字节 */
    ...;                           /* 两段都成功了 */

这一段就是「读一个 16 bit 寄存器」的标准写法，等价于 i2c_smbus_read_word_data() 在多数设备上的效果。串行 EEPROM 那种「先写地址、再读数据」的时序也靠它——C.驱动/06-I2C子系统 里的 I2C 设备驱动实战：OLED 与 AT24C08 和 I2C 设备驱动实战：OLED 与 AT24C08 都在用这个模型。

用户空间接口是 /dev/i2c-N 字符设备，ioctl 一套：I2C_SLAVE（设从地址）、I2C_RDWR（直接传 i2c_msg 数组）、I2C_SMBUS（SMBus 一族）。I2C_RDWR 对应的正是 i2c_transfer()，所以用户空间能做内核空间的所有传输动作。3.x 时代 i2c-dev 有个约束：一个打开的 fd 只能绑一个从地址，要访问多个设备就 open() 多个 fd。

二十一、consumer 侧怎么用：i2c_get_adapter 与 i2c_new_device #

consumer 有两种形态，这是 I2C 世界里最容易搞混的一处分叉。

21.1 形态 1：设备就是 I2C bus 上的设备 #

CPU 和设备的全部数据交互都走 I2C，没有别的路径。PMIC、Audio codec、EEPROM 都是这一类，在设备模型里的位置很干净——就是 i2c bus 上的一个设备。DTS 写法：设备 node 是 I2C 控制器 node 的 child：

dts
/* arch/arm/boot/dts/imx6dl-riotboard.dts */
&i2c1 {
	clock-frequency = <100000>;
	pinctrl-names = "default";
	pinctrl-0 = <&pinctrl_i2c1>;
	status = "okay";
	…
	pmic: pf0100@08 {
		compatible = "fsl,pfuze100";
		…
	};
	...
};

驱动三步：定义一个 struct i2c_driver 变量并用 module_i2c_driver 注册到 I2C core；这个变量要包含和 DTS 里 compatible 一致的 of_match_table 以及一个 probe 接口；probe 的入参是 struct i2c_client *，以它为参数调 i2c_master_send / i2c_master_recv 做简单传输，也可以从它拿到所属 adapter 再调 i2c_transfer 做复杂读写（drivers/base/regmap/regmap-i2c.c 的 regmap_i2c_read 就是这样）。这一类不用 i2c_get_adapter，也不用 i2c_new_device——client 由 core 建好递到你手上，你只负责花它。

21.2 形态 2：设备是 platform device，借用 I2C adapter #

设备的次要功能和 CPU 之间走 I2C，主要功能走别的总线。典型是 HDMI：音视频数据走 TMDS，EDID 走 I2C（HDMI 协议里叫 DDC）。这类设备在设备模型里的位置以主要功能为准，HDMI 显然是 platform 设备，于是 DTS 里它挂在根节点下，用一个 phandle 指向要用的 I2C 控制器：

dts
/* arch/arm/boot/dts/imx6dl-riotboard.dts */
&hdmi {
	ddc-i2c-bus = <&i2c2>;
	status = "okay";
};

probe 时按属性名取 adapter，拿到 struct i2c_adapter * 后用 i2c_transfer() 收发——这条路径上没有 i2c_client，要自己填 i2c_msg.addr。

c
/* drivers/gpu/drm/panel/panel-simple.c */
ddc = of_parse_phandle(dev->of_node, "ddc-i2c-bus", 0);
if (ddc) {
	panel->ddc = of_find_i2c_adapter_by_node(ddc);
	of_node_put(ddc);

	if (!panel->ddc) {
		err = -EPROBE_DEFER;
		goto free_backlight;
	}
}

注意那个 -EPROBE_DEFER：I2C 控制器还没注册好时 of_find_i2c_adapter_by_node() 返回 NULL，原样上报等下次 probe。两种形态的对照：

21.3 运行时构造与销毁 client #

内核里还有一批「不是 DT 描述出来的从设备」：临时设备、光模块、检测出来的器件。它们靠运行时 API 建 client：

c
/* 3.x 时代：按名字和地址建，跑探测 */
struct i2c_client *i2c_new_probed_device(struct i2c_adapter *adap,
                                         struct i2c_board_info *info,
                                         unsigned short const *addr_list,
                                         int (*probe)(struct i2c_adapter *,
                                                      unsigned short addr));
/* DT 普及后的主路径：info->of_node 指定设备树节点 */
struct i2c_client *i2c_new_device(struct i2c_adapter *adap,
                                  struct i2c_board_info *info);
/* 4.x 之后推荐的新接口 */
struct i2c_client *i2c_new_client_device(struct i2c_adapter *adap,
                                         struct i2c_board_info *info);

void i2c_unregister_device(struct i2c_client *client);
void i2c_put_adapter(struct i2c_adapter *adap);

i2c_get_adapter() 与配套的 i2c_put_adapter() 是引用计数对，从总线号拿 adapter。i2c_new_probed_device() 在 4.x 之后被标记为 deprecated 并最终移除（具体版本未验证）——直接按设备真实地址建 client 更可靠，探测在多设备总线上有风险。

二十二、从设备树实例化 I2C 设备 #

设备树里 I2C 设备的创建链路，它把本篇三个框架全串起来了：

text
i2c_add_adapter
    i2c_register_adapter
        of_i2c_register_devices(&adap->dev)
            for_each_available_child_of_node(adap->dev.of_node, node)
                of_i2c_register_device(adap, node)
                    of_property_read_u32(node, "reg", &addr)   /* 拿 slave 地址 */
                    info.addr    = addr;
                    info.of_node = of_node_get(node);
                    info.irq     = of_irq_get(node, 0);        /* 拿 irq */
                    i2c_new_device(adap, &info)
                        /* 建 i2c_client，注册到 i2c bus，触发匹配 */

四步里每一步都有可见的约束：

  1. reg 是必须的。没有 reg 的 child node 会被跳过，设备永远不会被创建。reg 放的是 7 bit 地址。
  2. status 不是 okay 的 node 会被跳过。for_each_available_child_of_node 只遍历可用的节点，这就是改设备树里的 status = "disabled" 能彻底关掉一颗芯片的原因。
  3. interrupts 解析成 client->irq。probe 里直接 client->irq 就能用，不用再 of_irq_get()。这类中断几乎总是要低电平触发（I2C 设备的 INT 脚多为开漏低有效）。
  4. 创建之后立刻匹配。client 注册到 i2c bus 时就尝试和已注册的 i2c_driver 匹配；driver 后注册时反过来扫一遍已有 client。两个方向都支持，加载顺序不强制。

从 DTS 节点反查已存在的对象：

c
/* include/linux/i2c.h */

/* must call put_device() when done with returned i2c_client device */
extern struct i2c_client *of_find_i2c_device_by_node(struct device_node *node);

/* must call put_device() when done with returned i2c_adapter device */
extern struct i2c_adapter *of_find_i2c_adapter_by_node(struct device_node *node);

两者的引用释放都走 put_device(&xxx->dev)，不是 kfree()，这是设备模型的通用规矩。

❢重要

一个常见的误解：以为设备树里写了 node，设备就一定会被探测到。从 node 到 client 要过 status、reg、以及 adapter 是否先注册这三道关。/sys/bus/i2c/devices/ 下没有 N-00XX 目录，就说明卡在某一关，dmesg 里回回有一行对应的报错。

二十三、GPIO / pinctrl / I2C 三者在一份设备树里的协作 #

把三个框架放进同一份 dts，关系就清楚了。下面是典型 SoC 上的 I2C1 + 一颗 PMIC + 一个中断脚：

dts
/* 1. pinctrl provider：引脚复用与电气属性 */
pinctrl@11000000 {
    compatible = "vendor,foo-pinctrl";
    reg = <0x11000000 0x1000>;

    i2c1_bus: i2c1-bus {
        vendor,pins = "gpb-2", "gpb-3";
        vendor,pin-function = <2>;        /* 2 = I2C1 */
        vendor,pin-pud = <3>;             /* 上拉，值由 datasheet 定 */
        vendor,pin-drv = <0>;
    };

    pmic_irq: pmic-irq {
        vendor,pins = "gpa-5";
        vendor,pin-function = <0>;        /* 0 = GPIO */
        vendor,pin-pud = <0>;             /* 无上下拉，外部已接 */
    };
};

/* 2. gpio provider：就是 pinctrl 节点下的某个 bank */
gpio1: gpio1 {
    gpio-controller;
    #gpio-cells = <2>;
    interrupt-controller;
    #interrupt-cells = <2>;
    gpio-ranges = <&pinctrl 0 0 32>;      /* 本 chip 的 gpio0..31 → pin0..31 */
};

/* 3. I2C controller：platform device，同时是 pinctrl consumer */
i2c1: i2c@11001000 {
    compatible = "vendor,foo-i2c";
    reg = <0x11001000 0x1000>;
    interrupts = <0 30 4>;
    clock-frequency = <400000>;
    pinctrl-names = "default";
    pinctrl-0 = <&i2c1_bus>;              /* 引用上面的 pin state */
    status = "okay";

    /* 4. I2C client：由 core 按此 node 创建 */
    pmic@08 {
        compatible = "vendor,fp0100";
        reg = <0x08>;
        interrupt-parent = <&gpio1>;
        interrupts = <5 IRQ_TYPE_LEVEL_LOW>;   /* 对应 pmic_irq 那组引脚 */
        wakeup-source;

        /* 5. 同一颗 chip 上的复位脚，用 gpio 描述符接口取 */
        reset-gpios = <&gpio1 12 GPIO_ACTIVE_LOW>;
    };
};

三个框架的分工：

事件 谁在处理 具体动作
i2c@11001000 probe 前 设备模型 调 pinctrl_bind_pins()，按 pinctrl-0 把 gpb-2/3 切成 I2C1 并配上拉
i2c@11001000 probe 中 I2C controller driver 填 i2c_adapter、指 algo->master_xfer、i2c_add_adapter()
adapter 注册后 I2C core 扫 child node，为 pmic@08 建 i2c_client，解析出 addr 与 irq
client 匹配到驱动 设备模型 + I2C core 调 fp0100 的 i2c_driver.probe(client)
probe 里取复位脚 gpiolib gpiod_get() 解析 reset-gpios，必要时走 pinctrl_request_gpio() 把 gpio12 从别的功能抢回来
中断到来 irqchip + GPIO gpio1 的 to_irq 给出 irq 号，链路走到 PMIC 驱动

三个容易出错的耦合点：

  1. i2c1_bus 里的上拉配置和板上的实际电阻。SoC 内部上拉往往是弱上拉，400 kHz 下未必够，很多板子靠外部 2.2k 电阻。两处都开也不冲突（并联变小），但内部上拉不够时不能指望它。
  2. 中断脚的复用必须是 GPIO 模式。若 pmic_irq 里写错了 pin-function，中断永远不来而 I2C 通信一切正常——这种故障最容易骗人。
  3. interrupt-parent 和 gpio-ranges 必须指向同一套编号空间。gpio1 的 gpio-ranges 写错，gpiod_to_irq() 给出的号就对不上，request_threaded_irq() 会返回 -EINVAL。
