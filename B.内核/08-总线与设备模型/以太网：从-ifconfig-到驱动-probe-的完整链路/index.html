一、一条命令背后的四层：ifconfig → netlink → 网络栈 → 驱动 #

先把地图摊开。你在 shell 里敲的每个网络配置命令，背后只有两条路：一条老的 ioctl，一条新的 netlink。ifconfig 属于前者。

从你敲回车到寄存器被写，一共四层：

层 你看到的东西 内核里对应的东西 属于哪套模型
用户态 ifconfig、ip、busybox SIOCSIFFLAGS + struct ifreq 无，纯 libc 系统调用
文件系统抽象 socketfd sockfs + socket_file_ops VFS 的字符/伪文件子系统
网络栈 设备无关层 dev_ioctl() → dev_ifsioc() → dev_change_flags() net/core/dev.c，全局网络设备表
设备模型 + 驱动 网卡的 probe ndo_open 回调、net_device_ops platform_bus_type + driver_register
硬件 PHY 芯片、MAC 寄存器 mii_bus → MDC/MDIO → PHY 寄存器 mdio_bus_type

四层里最容易忽视的是第三层和第四层的接缝：网络栈对网卡的全部认知只有一个 struct net_device，网卡驱动挂在 platform 总线上，两者靠 net_device_ops 这张函数表对上。这条接缝就是本章要挖的东西。

二、ifconfig 到底做了什么：ioctl 还是 netlink #

先别急着进内核。ifconfig 在用户态做的三件事：

  1. 打开一个 AF_INET / SOCK_DGRAM 的 socket，这个 socket 不用于收发数据，只借用它的 ioctl 通道。
  2. 把接口名 eth0 拷进 struct ifreq.ifr_name，把要设的 flag 位塞进 ifr_flags。up 对应 IFF_UP。
  3. 调 ioctl(fd, SIOCSIFFLAGS, &ifr)。

没有 netlink。这是第一个要纠正的直觉偏差：新工具 ip link set eth0 up 走的是 netlink 的 RTM_NEWLINK 消息，ifconfig 走的是 ioctl，两条路在 dev_change_flags() 附近才会汇合。至于 busybox ifconfig 与 net-tools ifconfig 是否都这样，未验证，但两者都用 SIOCSIFFLAGS 这一点是原文 strace 出来的结论。

SIOCSIFFLAGS 的值是 0x8914，属于内核里那批 0x89xx 的 socket 配置控制命令，原文照录了整段宏定义里比较关键的部分：

c
/* Socket configuration controls. */
#define SIOCGIFNAME	0x8910		/* get iface name		*/
#define SIOCSIFLINK	0x8911		/* set iface channel		*/
#define SIOCGIFCONF	0x8912		/* get iface list		*/
#define SIOCGIFFLAGS	0x8913		/* get flags			*/
#define SIOCSIFFLAGS	0x8914		/* set flags			*/
#define SIOCGIFADDR	0x8915		/* get PA address		*/
#define SIOCSIFADDR	0x8916		/* set PA address		*/
#define SIOCGIFHWADDR	0x8927		/* Get hardware address		*/
#define SIOCGIFINDEX	0x8933		/* name -> if_index mapping	*/
#define SIOCSIFMTU	0x8922		/* set MTU size			*/

真实 ifconfig 干一次 up 不止一个 ioctl：设地址、设掩码、设广播地址、最后设 flag。原文的 strace 只关注 SIOCSIFFLAGS，其他命令只是沿途路过。SIOCSIFMTU、SIOCSIFHWADDR 这些走的是同一个 sock_ioctl() 入口，只是 case 分支不同。

判断走 ioctl 还是 netlink，一条命令就够：

bash
strace -e trace=ioctl,sendto,recvmsg ifconfig eth0 up 2>&1 | head -40
# 只看到 ioctl(4, SIOCSIFFLAGS, ...)                  -> 老路
# 看到 socket(AF_NETLINK, ...) + sendto(..., RTM_NEWLINK ...) -> 新路

ip 那条路本文不追。理由是两条路最终都在 dev_change_flags() 附近落到同一个 net_device 上，摸清 ioctl 这一条，ip 那条的终点是一样的。

三、从 ifconfig 到内核的第一跳 #

ioctl 是标准系统调用。ARM 上走 swi 指令陷内核，查 sys_call_table 拿到 sys_ioctl，返回时走 ret_fast_syscall。原文给了这段汇编，它解释的是「为什么 trace 里看见 SyS_ioctl 之后又跳回用户态」：

armasm
ret_fast_syscall:
  UNWIND(.fnstart	)
  UNWIND(.cantunwind	)
	disable_irq				@ disable interrupts
	ldr	r1, [tsk, #TI_FLAGS]		@ re-check for syscall tracing
	tst	r1, #_TIF_SYSCALL_WORK
	bne	__sys_trace_return
	tst	r1, #_TIF_WORK_MASK
	bne	fast_work_pending
	asm_trace_hardirqs_on
	/* perform architecture specific actions before user return */
	arch_ret_to_user r1, lr
	ct_user_enter
	restore_user_regs fast = 1, offset = S_OFF
  UNWIND(.fnend		)

入口在 fs/ioctl.c：

c
SYSCALL_DEFINE3(ioctl, unsigned int, fd, unsigned int, cmd, unsigned long, arg)
{
	int error;
	struct fd f = fdget(fd);

	if (!f.file)
		return -EBADF;

	error = security_file_ioctl(f.file, cmd, arg);
	if (!error)
		error = do_vfs_ioctl(f.file, fd, cmd, arg);

	fdput(f);
	return error;
}

do_vfs_ioctl() 是一张巨大的 switch，但里面一个网络命令都没有。它只处理 FIOCLEX、FIONBIO、FIOASYNC、FIFREEZE 这类通用文件 ioctl，其余全部落到 default:：

调用链到这里是干净的：

text
ifconfig → socket(AF_INET, SOCK_DGRAM, 0)
         → SYSCALL_DEFINE3(socket)
         → sock_create()
         → sock_map_fd()
         → sock_alloc_file()          （f_op = socket_file_ops）
         → 返回 fd

ifconfig → ioctl(fd, SIOCSIFFLAGS, &ifr)
         → SYSCALL_DEFINE3(ioctl)
         → do_vfs_ioctl()

调试时想知道 fd 属于哪个文件系统，原文的做法是在 vfs_ioctl() 里打一行 filp->f_path.dentry->d_sb->s_type->name，打印出来是 sockfs。这招对所有「匿名 fd」都管用，留着。

四、dev_ifsioc：设备无关层 #

sock_ioctl() 是网络命令的总分流器。它先挡掉 WiFi 扩展命令（SIOCIWFIRST～SIOCIWLAST）和 SIOCDEVPRIVATE 私有段，再把 bridge、vlan、dlci 这些没编进内核的模块用 request_module() 拽进来，剩下的全扔给 sock_do_ioctl()。骨架就三个分支：

c
	if (cmd >= SIOCDEVPRIVATE && cmd <= (SIOCDEVPRIVATE + 15))
		err = dev_ioctl(net, cmd, argp);
	else if (cmd >= SIOCIWFIRST && cmd <= SIOCIWLAST)
		err = dev_ioctl(net, cmd, argp);
	else
		err = sock_do_ioctl(net, sock, cmd, arg);

sock_do_ioctl() 的注释把这层的设计意图写得很直白：先问协议栈，协议栈说不认识，再往下交给网卡驱动。

c
static long sock_do_ioctl(struct net *net, struct socket *sock,
				 unsigned int cmd, unsigned long arg)
{
	int err;
	void __user *argp = (void __user *)arg;

	err = sock->ops->ioctl(sock, cmd, arg);
	/*
	 * If this ioctl is unknown try to hand it down
	 * to the NIC driver.
	 */
	if (err == -ENOIOCTLCMD)
		err = dev_ioctl(net, cmd, argp);
	return err;
}

sock->ops 是 struct proto_ops，AF_INET 的 SOCK_DGRAM socket 挂的是 inet_dgram_ops，它的 .ioctl 就是 inet_ioctl()（原文说「回调的是 inet_ioctl」，路径 net/ipv4/af_inet.c；具体是 inet_dgram_ops 还是 inet_stream_ops 由 socket 类型决定，ifconfig 用 dgram，未逐一验证两者都指向 inet_ioctl）。

inet_ioctl() 是一张 switch 表，把命令分给三个不同的处理者：

c
	switch (cmd) {
	case SIOCGSTAMP:
		err = sock_get_timestamp(sk, (struct timeval __user *)arg);
		break;
	case SIOCADDRT:
	case SIOCDELRT:
	case SIOCRTMSG:
		err = ip_rt_ioctl(net, cmd, (void __user *)arg);
		break;
	case SIOCDARP:
	case SIOCGARP:
	case SIOCSARP:
		err = arp_ioctl(net, cmd, (void __user *)arg);
		break;
	case SIOCGIFADDR:
	case SIOCSIFADDR:
	/* ... SIOCGIFBRDADDR / SIOCGIFNETMASK / SIOCSIFPFLAGS ... */
	case SIOCSIFFLAGS:
		err = devinet_ioctl(net, cmd, (void __user *)arg);
		break;
	default:
		if (sk->sk_prot->ioctl)
			err = sk->sk_prot->ioctl(sk, cmd, arg);
		else
			err = -ENOIOCTLCMD;
		break;
	}

注意 default: 分支返回 -ENOIOCTLCMD，这正是 sock_do_ioctl() 里那个「交给驱动」的开关。SIOCSIFFLAGS 不在 default 里，所以它不会走到驱动，而是走 IPv4 的设备配置入口 devinet_ioctl()。如果你的命令是驱动私有的（比如某个自定义 SIOCDEVPRIVATE），那才会一路下到 dev_ioctl() 再去驱动 ndo_do_ioctl。

devinet_ioctl() 里 case SIOCSIFFLAGS 出现两次：第一次在命令预处理段，只做 ns_capable(net->user_ns, CAP_NET_ADMIN) 检查，不过就 -EPERM 走人；第二次才真正干活，colon 为真时进别名接口分支（inet_del_ifa），否则 ret = dev_change_flags(dev, ifr.ifr_flags);。

三个关键点：

  • 权限。没有 CAP_NET_ADMIN 直接 -EPERM。这就是为什么普通用户 ifconfig eth0 up 报的是 Operation not permitted 而不是 No such device。
  • 正常接口，一行 dev_change_flags(dev, ifr.ifr_flags)。

这里 dev 是从哪来的？devinet_ioctl() 开头已经把 ifr.ifr_name 拷了出来，用 __dev_get_by_name(net, ifr.ifr_name) 拿到 net_device。原文在第二篇里略过了这一步，直接跳到 dev_change_flags，这是素材里的一处跳步，第九章会补全。

devinet_ioctl() 返回 -19 这一点，原文是用加 printk 的方式确认的：ret 打印出来是 -19。这一步别省，内核里搜 SIOCSIFFLAGS 能搜出十几处，不确认入口函数，后面全白追。

五、SIOCSIFFLAGS 与 IFF_UP 的语义 #

flag 在用户态和内核态是同一套值，但语义要分清三组：

flag 值 谁维护 语义 谁真正干活
IFF_UP 0x1 __dev_open / __dev_close 接口管理态 up ndo_open / ndo_stop
IFF_RUNNING 0x40 dev_activate() 收发队列已启动 协议栈，不是驱动
IFF_PROMISC 0x100 __dev_set_promiscuity() 混杂模式 ndo_set_rx_mode
IFF_ALLMULTI 0x200 __dev_set_allmulti() 收全部组播 ndo_set_rx_mode
IFF_MULTICAST 0x1000 dev_change_rx_flags() 支持组播 ndo_change_rx_flags
IFF_NOARP 0x80 __dev_change_flags 不发 ARP 协议栈
IFF_DEBUG 0x2 同上 调试开关 无人管
IFF_DYNAMIC 0x8000 同上 动态分配地址 无人管
IFF_LOOPBACK 0x8 驱动设置，用户不可改 环回 —
IFF_POINTOPOINT 0x10 驱动设置 点对点 —

表格里的关键是第 1 行和第 2 行的区别：IFF_UP 不等于 IFF_RUNNING。ifconfig 里 UP 和 RUNNING 是两个词，很多人混着读。IFF_UP 是「你让内核把这块网卡打开」，IFF_RUNNING 是「内核的收发队列真的跑起来了」；IFF_RUNNING 在 __dev_open() 里由 dev_activate() 设置，不在驱动里。

__dev_change_flags() 对 flag 的处理是「分类信任」：一部分位完全由用户态说了算，一部分位由用户态和当前值共同决定，IFF_UP 干脆不让用户态直接写，只当它是个边缘触发信号。

c
	dev->flags = (flags & (IFF_DEBUG | IFF_NOTRAILERS | IFF_NOARP |
			       IFF_DYNAMIC | IFF_MULTICAST | IFF_PORTSEL |
			       IFF_AUTOMEDIA)) |
		     (dev->flags & (IFF_UP | IFF_VOLATILE | IFF_PROMISC |
				    IFF_ALLMULTI));

第一组是「用户说什么就是什么」，第二组是「保留原值」。你要是把 IFF_UP 写进请求里，它也不会被这行代码置上，真正的置位在 __dev_open() 成功之后那一行 dev->flags |= IFF_UP;。

这里有个容易想错的点：ifconfig eth0 up 传的 ifr_flags 不是「只有 IFF_UP」，而是 ifconfig 当前认为这个接口应有的全部 flag。所以 ifconfig 内部对 flags 的拼装逻辑会直接影响内核看到什么。原文未展开这块，这里也不编。

六、dev_open 与 ndo_open 的分工 #

dev_change_flags() 只是一层壳：

c
int dev_change_flags(struct net_device *dev, unsigned int flags)
{
	int ret;
	unsigned int changes, old_flags = dev->flags, old_gflags = dev->gflags;

	ret = __dev_change_flags(dev, flags);
	if (ret < 0)
		return ret;

	changes = (old_flags ^ dev->flags) | (old_gflags ^ dev->gflags);
	__dev_notify_flags(dev, old_flags, changes);
	return ret;
}

壳里面装了两件事：真干活的是 __dev_change_flags()，__dev_notify_flags() 负责把「变了什么」广播出去（inetdev_event、addrconf_notify 这些 notifier 会收到）。__dev_change_flags() 里真正决定 up/down 的只有一段：

c
int __dev_change_flags(struct net_device *dev, unsigned int flags)
{
	unsigned int old_flags = dev->flags;
	int ret;

	ASSERT_RTNL();

	dev->flags = (flags & (IFF_DEBUG | IFF_NOTRAILERS | IFF_NOARP |
			       IFF_DYNAMIC | IFF_MULTICAST | IFF_PORTSEL |
			       IFF_AUTOMEDIA)) |
		     (dev->flags & (IFF_UP | IFF_VOLATILE | IFF_PROMISC |
				    IFF_ALLMULTI));

	if ((old_flags ^ flags) & IFF_MULTICAST)
		dev_change_rx_flags(dev, IFF_MULTICAST);

	dev_set_rx_mode(dev);

	/*
	 *	Have we downed the interface. We handle IFF_UP ourselves
	 *	according to user attempts to set it, rather than blindly
	 *	setting it.
	 */
	ret = 0;
	if ((old_flags ^ flags) & IFF_UP)
		ret = ((old_flags & IFF_UP) ? __dev_close : __dev_open)(dev);

三个细节值得停一下：

  • (old_flags ^ flags) & IFF_UP 是边缘触发。接口已经 up 了，你再 up 一次，这里为假，ndo_open 不会再被调。所以「我 up 了两遍还是不通」这种说法本身就是错的，第二遍什么都没做。
  • ASSERT_RTNL() 说明这整条路径被 RTNL 锁保护。net_device 的 up/down、注册销毁、重命名全在 RTNL 下串行，驱动 ndo_open 里的睡眠、msleep、wait_for_completion 是允许的，前提是你不自己乱抢锁。
  • ret 从 __dev_open 出来直接返回给用户态。-ENODEV 就是这么从驱动一路冒到 ifconfig 的 stderr 上的。

__dev_open() 是设备无关层对驱动的最后一次「准备」，核心顺序是：

c
	ASSERT_RTNL();

	if (!netif_device_present(dev))
		return -ENODEV;

	netpoll_poll_disable(dev);

	ret = call_netdevice_notifiers(NETDEV_PRE_UP, dev);
	ret = notifier_to_errno(ret);
	if (ret)
		return ret;

	set_bit(__LINK_STATE_START, &dev->state);

	if (ops->ndo_validate_addr)
		ret = ops->ndo_validate_addr(dev);

	if (!ret && ops->ndo_open)
		ret = ops->ndo_open(dev);

	netpoll_poll_enable(dev);

	if (ret)
		clear_bit(__LINK_STATE_START, &dev->state);
	else {
		dev->flags |= IFF_UP;
		dev_set_rx_mode(dev);
		dev_activate(dev);
		add_device_randomness(dev->dev_addr, dev->addr_len);
	}

	return ret;

分工原则：能由框架统一判的就别让每个驱动自己写。所以 __dev_open 管设备模型与状态位那一半（netif_device_present、netpoll_poll_disable、NETDEV_PRE_UP notifier、__LINK_STATE_START、IFF_UP、dev_activate），驱动只管 ndo_validate_addr 和 ndo_open。

__LINK_STATE_START 这个位有个隐含约定：它在 ndo_open 之前就被置上，失败了才清掉。所以驱动在 ndo_open 里调 netif_running() 会返回真。FEC 驱动正好用到了这一点，后面 fec_set_mac_address() 里那句 if (!netif_running(ndev)) return 0; 就是靠它判断的。

netif_device_present 那行是第二个 -ENODEV 的来源：设备被热拔或者被 device_del 之后，这个位为假，__dev_open() 自己就返回 -ENODEV，根本不进驱动。原文这个 case 没遇到，实测时如果 dmesg 里连驱动的 ndo_open 都没有打印，就往这儿查。

七、drivers/net 里一次 open 的完整代码流程 #

ops->ndo_open 在 FEC 驱动里就是 fec_enet_open()：

c
static const struct net_device_ops fec_netdev_ops = {

按顺序拆：

  1. fec_restart(ndev)：复位 MAC、重写 MAC 地址寄存器、配 MII 速率、开中断。注释写得很明确，放在 mii_probe 之前。

  3. napi_enable() + phy_start() + netif_tx_start_all_queues()：收发通道正式放开。
  4. pm_runtime_get_sync() + pm_qos_add_request()：运行时 PM 和延迟约束。

九、往底层追：从 dev_get_by_name 到设备查找 #

-19 出现在 of_phy_connect() 里，那就进去。先看这个函数的注释，它把意图讲全了：

c
struct phy_device *of_phy_connect(struct net_device *dev,
				  struct device_node *phy_np,
				  void (*hndlr)(struct net_device *), u32 flags,
				  phy_interface_t iface)
{
	struct phy_device *phy = of_phy_find_device(phy_np);

	if (!phy)
		return NULL;

	phy->dev_flags = flags;

	return phy_connect_direct(dev, phy, hndlr, iface) ? NULL : phy;
}

phy_device 为空，说明 of_phy_find_device(phy_np) 没找到。继续：

c
struct phy_device *of_phy_find_device(struct device_node *phy_np)
{
	struct device *d;

	if (!phy_np)
		return NULL;

	d = bus_find_device(&mdio_bus_type, NULL, phy_np, of_phy_match);
	return d ? to_phy_device(d) : NULL;
}

这一行是整条链的枢纽：bus_find_device(&mdio_bus_type, NULL, phy_np, of_phy_match)。

它说明 PHY 是一个挂在总线上的设备。总线的名字叫 mdio_bus_type，不是凭空一个「PHY 对象」。

总线查找的骨架：bus_find_device(bus, start, data, match) 沿 bus->p->klist_devices 链表逐个调 match()，命中且 get_device() 成功就停，返回那个 struct device *。匹配规则由调用者给：

c
static int of_phy_match(struct device *dev, void *phy_np)
{
	return dev->of_node == phy_np;
}

规则是两个 of_node 指针相等。这个判断非常强：它比的是设备树节点的地址，不是名字、不是 compatible、不是 PHY 地址。也就是说，设备树里 phy-handle = <&ethphy0> 拿到的 node，和 mdio 下面 ethernet-phy@0 注册 phy_device 时用的 node，必须是同一个 node 对象。名字写得再对，node 不一致也找不到。

找到之后转回 phy_device：

c
#define to_phy_device(d) container_of(d, struct phy_device, dev)

struct phy_device 内嵌了一个 struct device，所以 container_of 能从总线上的 device 反推出 phy_device。这套 container_of 反推是全篇的通用手法：总线链表上只有 struct device 这种「基类」指针，要拿派生结构体就靠它。

装 PHY 的那条总线：

c
struct bus_type mdio_bus_type = {
	.name		= "mdio_bus",
	.match		= mdio_bus_match,
	.pm		= MDIO_BUS_PM_OPS,
	.dev_groups	= mdio_dev_groups,
};
EXPORT_SYMBOL(mdio_bus_type);

sysfs 里能看到的对应目录是 /sys/bus/mdio_bus/，下面 devices/ 和 drivers/ 两张子表，和 platform、PCI 的排布完全一样。PHY 的 probe 和网卡控制器的 probe 走的是同一套 device/driver/bus 机制，只是总线名字不同。

结论落在这里：-ENODEV 的真实含义是「mdio_bus_type 上没有任何一个 device 的 of_node 等于 DTS 里那个 PHY 节点」。只有两种情形：

  • 那个 phy_device 从来没被注册进 mdio_bus_type。
  • 它注册过，但后来从总线上消失了（phy_device_free() 或 device_del()）。

原文到这里提了两个猜想，然后转向 probe 流程去验证。这个方向是对的：phy_device 的创建发生在网卡控制器驱动的 probe 里，不在 ndo_open 里。所以要看 fec_probe()。

补充另一条 -ENODEV 的路，也就是第一章提到、实栈里没出现的那条。ifconfig 的另外一些命令（比如 SIOCSIFMTU、SIOCSIFADDR）走的是 dev_ioctl()：

dev_ioctl() 的路径是：先 dev_load() 按需 request_module() 加载驱动，再按 ifr_name 查 dev，然后进 dev_ifsioc() 走 SIOCSIFFLAGS 之外的分支。拿不到 dev 时同样返回 -ENODEV。所以看到 -19，第一件事要看报错命令是哪个 ioctl：SIOCSIFFLAGS 走 devinet_ioctl()，其他多半走 dev_ioctl()，两条路的 -19 含义不同。原文只处理了前者，后者本文标为「未逐行验证」。

十、为什么错误会在最底层才暴露 #

这个问题比错误本身有价值。-19 没有在 devinet_ioctl()、dev_change_flags()、__dev_open() 这几层被拦下来，而是一路穿到驱动最深处才出现，原因有四条，缺一不可：

  1. 接口本身是注册好了的。register_netdev() 跑完了，net_device 在全局表里，devinet_ioctl() 能按名字查到它，__dev_open() 的 netif_device_present() 也为真。设备在，只是它背后的硬件不通。
  2. IFF_UP 的检查在 __dev_open() 里只是「有没有 ndo_open」，有就调。协议栈不验硬件状态。
  3. 网络栈把 PHY 的事完全当成驱动私事。net_device 里没有一个字段表示「PHY 就绪」，协议栈也无从检查。
  4. FEC 驱动把 PHY 探测放在了 ndo_open 而不是 probe。这是设计选择：注释写着 Probe and connect to PHY when open the interface，理由是省电（不开接口就不给 PHY 供电）。代价是 register_netdev() 成功不代表网卡能用。

这四条合起来，-19 只能在 fec_enet_mii_probe() 里爆。

有一条判据可以直接判断「是不是这个模式」：

bash
ip link show eth0          # 能看到 eth0，state DOWN，没有 NO-CARRIER 之外的异常
ip link set eth0 up        # 失败
dmesg | grep -i fec        # 没有 "Freescale FEC PHY driver [...]" 那行

三条对上了，就是 PHY 没连上，不是网卡没注册。

再往下看，故障和 MAC 地址有关这个现象，原文的解释是时序。这套环境里 fec_get_mac() 的取值顺序是五级瀑布，第 4 级和第 5 级走的代码路径不同，耗时就不同：

级 来源 命中条件 附带动作
1 模块参数 fec.macaddr= 命令行给了 直接用它
2 设备树 local-mac-address DTS 里有 of_get_mac_address()
3 flash / fuse / platform data pdata 非空 读平台数据
4 bootloader 写进 FEC 寄存器 前三级都不合法 读 FEC_ADDR_LOW/HIGH
5 内核随机生成 前四级都不合法 eth_hw_addr_random()

用 USB 工具烧了 MAC 的机器命中第 4 级，代码路径短，fec_reset_phy() 到 fec_enet_mii_init() 之间隔得太近，PHY 还没从复位里缓过来，MDIO 读回来是垃圾，phy_id 拿不到，phy_device 不创建，of_phy_find_device() 找不到，-ENODEV。

没烧 MAC 的机器命中第 5 级，多跑了 eth_hw_addr_random() → eth_random_addr() → get_random_bytes()，多花的那点时间恰好凑够了 PHY datasheet 要求的复位等待窗口，于是正常。

原文给的具体时序数字是：硬件复位脚方案下，reset 保持住电平 10ms 后，还要再维持至少 150ms 才能访问 PHY 寄存器；软件复位方案下，10ms 后至少再等 3.5 个 MDC 时钟。这两个数字来自该 PHY 的 datasheet 要求，原文没标具体页码，本文照录，标为「未逐条核对 datasheet」。

用 printk 能让故障机变好，原理就是拖时间：printk 走串口，一行几十微秒到几毫秒，加在不同的位置，凑出的延迟不同，所以「有时好有时坏」。这个现象本身是时序问题的强证据，不是玄学。

修法有三条，按侵入性从低到高：

  • DTS 加 phy-reset-duration / phy-reset-gpios 之类属性，让框架自己等（具体属性名随内核版本变化，未验证）。
  • 驱动里 fec_reset_phy() 之后补 msleep(150)，简单粗暴，能过认证。
  • 硬件上把复位脚的 RC 加大，或者干脆改成上电复位，软件不参与。

fec_get_mac() 就是按上表五级依次 if (!is_valid_ether_addr(iap))，一级不命中就往下一级走，最后 memcpy(ndev->dev_addr, iap, ETH_ALEN)。第 4 级从寄存器读的写法是：

	 * 4) FEC mac registers set by bootloader

		*((__be32 *) &tmpaddr[0]) =

判别「地址合法」的是 is_valid_ether_addr()：

c
static inline bool is_valid_ether_addr(const u8 *addr)
{
	/* FF:FF:FF:FF:FF:FF is a multicast address so we don't need to
	 * explicitly check for it here. */
	return !is_multicast_ether_addr(addr) && !is_zero_ether_addr(addr);
}

全 0 和全 FF 都不合法，组播位为 1 也不合法。所以「MAC 没烧」在这个驱动里的表现就是全 0，走第 5 级。

随机 MAC 的生成两级：

c
static inline void eth_hw_addr_random(struct net_device *dev)
{
	dev->addr_assign_type = NET_ADDR_RANDOM;
	eth_random_addr(dev->dev_addr);
}

static inline void eth_random_addr(u8 *addr)
{
	get_random_bytes(addr, ETH_ALEN);
	addr[0] &= 0xfe;	/* clear multicast bit */
	addr[0] |= 0x02;	/* set local assignment bit (IEEE802) */
}

get_random_bytes() 从内核随机池取字节，这一步的耗时是不可控的，取决于熵池状态。原文说「刚好满足了 150ms」，字面上是「恰好凑够」，实际含义是「这一步有不确定性」，所以故障表现才会「有时好有时坏」。把因果关系说成「随机数函数耗时正好 150ms」是不严谨的，这里修正为：第 5 级路径比第 4 级多了一次熵池提取，多出来的延迟在临界值附近，导致行为呈现概率性。

这套「靠延迟碰运气」的代码根本不该存在。正确的写法是显式等待复位时序，别让 MAC 地址来源影响 PHY 访问。这是本文对原文的一点批评。

register_netdev(ndev)
 -> register_netdevice(ndev)          拿 RTNL
     -> dev->netdev_ops->ndo_init()   一次，失败则注册失败
     -> dev_get_valid_name()          定名字
     -> dev_new_index()               分配 ifindex
     -> netdev_register_kobject()     在 sysfs 里建 /sys/class/net/eth0
     -> call_netdevice_notifiers(NETDEV_REGISTER)
     -> list_netdevice()              挂进全局设备表
 -> rtnl_unlock()

三个必须记住的点：

  • ndo_init 在注册时调一次，在 net_device 被正式公开之前。FEC 的 fec_netdev_ops 里没有 .ndo_init，所以这个钩子对它为 NULL，跳过。
  • register_netdev() 返回 0 只代表设备进了表，不代表硬件能用。fec_probe() 里 register_netdev() 之前已经 netif_carrier_off(ndev)，register_netdev() 之后也没有 ndo_open 调用。第二章那条「设备在、硬件不通」的结论，地基就在这儿。
  • 名字不是 eth0 时（比如 eth%d 这种格式串），名字的最终确定发生在 register_netdev() 内部。DTS 里的 aliases 会影响顺序，具体机制见《设备树》。

配套的注销是 unregister_netdev()，会先 dev_close() 再摘表。驱动出错路径里，fec_probe() 用的是 free_netdev(ndev) 而不是 unregister_netdev()，因为在 failed_register 标签之前它还没注册成功。

十二、net_device 的分配与初始化 #

net_device 的分配在 fec_probe() 的第一行：

c
	ndev = alloc_etherdev_mqs(sizeof(struct fec_enet_private),
				  num_tx_qs, num_rx_qs);
	if (!ndev)
		return -ENOMEM;

	SET_NETDEV_DEV(ndev, &pdev->dev);

	fep = netdev_priv(ndev);

alloc_etherdev_mqs() 一次调用干三件事：分配 sizeof(struct net_device) + priv_size 的连续内存（私有数据和 net_device 同块，共生命周期）；按 num_tx_qs/num_rx_qs 分配队列数组；设好 dev_addr、addr_len = ETH_ALEN、type = ARPHRD_ETHER。

netdev_priv() 是这块内存的「后半截」指针：

c
static inline void *netdev_priv(const struct net_device *dev)
{
	return (char *)dev + ALIGN(sizeof(struct net_device), NETDEV_ALIGN);
}

NETDEV_ALIGN 的对齐保证 fep 的起始地址满足 DMA 和缓存行要求。这就是为什么驱动可以把 fep 当 ndev 的附属物随意取用，而不用管释放：一块 kfree() 一起走。

SET_NETDEV_DEV(ndev, &pdev->dev) 是本章最容易被忽略、但对设备模型最要紧的一行：它把 net_device 内嵌的 struct device 的 parent 指向 platform device。于是 /sys/class/net/eth0/device 能链回 /sys/devices/.../2188000.ethernet，pm_runtime_get_sync(ndev->dev.parent) 能拿到 platform device 做电源管理，devm_* 分配的资源也和 net_device 的上层设备是同一个。没有这一行，网卡在 sysfs 里就是孤儿，电源管理和热插拔全断。

分配完立刻 netdev_priv() 取 fep，然后把 pdev 存的 quirks、队列数、netdev 反向指针填进去：

c
	of_id = of_match_device(fec_dt_ids, &pdev->dev);
	if (of_id)
		pdev->id_entry = of_id->data;

	fep->quirks = pdev->id_entry->driver_data;
	fep->netdev = ndev;
	fep->num_rx_queues = num_rx_qs;
	fep->num_tx_queues = num_tx_qs;

fep->quirks 是从 DTS 的 compatible 匹配出的 driver_data 来的，后面整个 probe 到处在查这个位图（FEC_QUIRK_HAS_GBIT、FEC_QUIRK_HAS_CSUM、FEC_QUIRK_ENET_MAC……）。一句话：同一个驱动源码，不同 SoC 靠 quirks 位图分流。这是 Freescale 这类「一个驱动管一个家族」的写法，代价是几十个 if (fep->quirks & ...)。

net_device 的完整初始化散在两个函数里：fec_probe() 负责设备模型那一半（分配、parent、drvdata），fec_enet_init() 负责网络栈那一半（ops、features、NAPI、buffer）。后面第十五、十六章拆。

十三、设备模型视角：net 设备挂在哪 #

把网卡放进设备模型的坐标系，是本文和同批那两篇的接缝。一句话：网卡在设备模型里是「platform 设备 + 两个内嵌 device」，网络栈只认其中一个。

text
/sys/devices/soc0/2188000.ethernet/     platform_device 的 dev
├── net/eth0        -> class/net/eth0        net_device 内嵌 dev（SET_NETDEV_DEV）
├── mdio/          mii_bus 内嵌 dev
│    └── 0:00/     phy_device 内嵌 dev
│         └── driver -> bus/mdio_bus/drivers/RTL8201F
└── driver -> bus/platform/drivers/fec

/sys/class/net/eth0/     class=net，纯入口
├── address / flags / mtu / operstate
└── device -> ../../../2188000.ethernet

这张树说明三件事：三个内嵌 device（net_device、mii_bus、每个 phy_device）都靠 parent 串回同一个 platform device；/sys/class/net/ 是 class 层，和 /sys/bus/platform/、/sys/bus/mdio_bus/ 正交指到同一批实体；phy_device 在 mdio_bus_type 上而不是 platform_bus_type 上，这才是 of_phy_find_device() 能按 of_node 找它的原因。

十四、驱动的 probe 流程总览 #

fec_probe() 是驱动入口，也是 net_device 和 mii_bus 的出生地。全文照录：

c
static int fec_probe(struct platform_device *pdev)
{
	struct fec_enet_private *fep;
	struct fec_platform_data *pdata;
	struct net_device *ndev;
	int i, irq, ret = 0;
	struct resource *r;
	const struct of_device_id *of_id;
	static int dev_id;
	struct device_node *np = pdev->dev.of_node, *phy_node;
	int num_tx_qs;
	int num_rx_qs;

	fec_enet_get_queue_num(pdev, &num_tx_qs, &num_rx_qs);

	ndev = alloc_etherdev_mqs(sizeof(struct fec_enet_private),
				  num_tx_qs, num_rx_qs);
	if (!ndev)
		return -ENOMEM;

	SET_NETDEV_DEV(ndev, &pdev->dev);
	fep = netdev_priv(ndev);

	of_id = of_match_device(fec_dt_ids, &pdev->dev);
	if (of_id)
		pdev->id_entry = of_id->data;
	fep->quirks = pdev->id_entry->driver_data;

	/* Select default pin state */
	pinctrl_pm_select_default_state(&pdev->dev);

	r = platform_get_resource(pdev, IORESOURCE_MEM, 0);
	fep->hwp = devm_ioremap_resource(&pdev->dev, r);
	if (IS_ERR(fep->hwp)) {
		ret = PTR_ERR(fep->hwp);
		goto failed_ioremap;
	}

	phy_node = of_parse_phandle(np, "phy-handle", 0);
	fep->phy_node = phy_node;

	ret = of_get_phy_mode(pdev->dev.of_node);
	if (ret < 0)
		fep->phy_interface = PHY_INTERFACE_MODE_MII;
	else
		fep->phy_interface = ret;

后面是资源与硬件初始化，原文三百多行，逐段顺序见第十五章那张 25 步表。这里只留 E 段的 关时钟 → sleep → register_netdev 三行，因为它是「probe 成功但硬件还没开」的关键：

c
	ret = fec_enet_mii_init(pdev);
	if (ret)
		goto failed_mii_init;

	/* Carrier starts down, phylib will bring it up */
	netif_carrier_off(ndev);
	fec_enet_clk_enable(ndev, false);
	pinctrl_pm_select_sleep_state(&pdev->dev);

	ret = register_netdev(ndev);
	if (ret)
		goto failed_register;

骨架分五段：A 分配（ndev/fep）、B 取资源（ioremap、phy-handle、phy-mode、clk、regulator）、C 硬件初始（fec_reset_phy、fec_enet_init、IRQ）、D 建 MDIO（fec_enet_mii_init）、E 挂网络栈（netif_carrier_off、关时钟、register_netdev）。每段的顺序约束在第十五章展开。

值得单独指出的是 E 段那三行连招：netif_carrier_off() → fec_enet_clk_enable(ndev, false) → pinctrl_pm_select_sleep_state() → register_netdev()。probe 结束时，时钟是关的、引脚是 sleep 的、carrier 是 down 的，只有 net_device 在表里。这是省电设计，也正是第十章那四条成立的技术基础。

注意 FEC 驱动在这里没用 devm_* 管时钟：devm_clk_get() 拿了句柄，但 fec_enet_clk_enable() 是手动开关。devm 只保证句柄随设备销毁释放，不保证时钟状态。混淆这两件事是常见误解，platform 与 devres 的机制见同批《platform 设备与 devres》。

失败路径用的是教科书式的级联 goto：每个标签只回滚自己那一层的资源，failed_ioremap 兜底 free_netdev()。devm_* 分配的东西（ioremap、clk 句柄、IRQ）不需要在这里释放，driver_detach 时自动回收。

十五、probe 里的资源获取顺序 #

probe 里三十多个步骤的顺序不是随便排的，每一步都卡在前一步的产物上。这张表是全章的压缩版，硬件细节只留「为什么在这个位置」：

步 动作 依赖什么 提供什么给后面的步骤
1 fec_enet_get_queue_num() DTS 的 fsl,num-tx-queues 之类 队列数，决定 alloc_etherdev_mqs 的大小
2 alloc_etherdev_mqs() 队列数 ndev + 私有内存
3 SET_NETDEV_DEV() pdev->dev ndev 的 parent，后面 ndev->dev.parent 能用

7 platform_get_resource + devm_ioremap_resource DTS reg fep->hwp，所有 writel/readl 的基址
8 platform_set_drvdata() ndev 从 pdev 反查 ndev 的通道
9 of_parse_phandle(np, "phy-handle") DTS fep->phy_node，决定 ndo_open 走分支 A 还是 B
10 of_get_phy_mode() DTS phy-mode fep->phy_interface，决定 MII/RMII/RGMII 位
11 devm_clk_get() × 4 DTS clocks ipg/ahb/enet_out/enet_clk_ref/ptp 句柄

关键的顺序约束有四个，写错必挂：

  • 步 7 必须在步 16 之前。fec_reset_phy()、fec_enet_init()、fec_restart() 全都在写 fep->hwp，基址没映射好就硬件异常。
  • 步 13 必须在步 19 之前。MDIO 的 MDC 时钟来自 AHB/ipg，时钟关着，MDIO 读写就是超时。原文没点破，但 fec_enet_mii_init() 的位置在 fec_enet_clk_enable(ndev, true) 之后，顺序本身就是证据。
  • 步 15 必须在步 19 之前，而且中间要有足够的等待时间。这就是第十章的时序问题：fec_reset_phy() 拉完复位脚就立刻进 fec_enet_mii_init()，PHY 没缓过来。
  • 步 21、步 22 必须在步 19 之后、步 23 之前。MDIO 要时钟，注册完就不需要了，所以关时钟放在最后。有人图省事关早了，probe 能过，ifconfig up 时 fec_enet_clk_enable(ndev, true) 会再开一次，看起来也能用，但 phy_device 已经建好了，不重扫，问题会以「PHY 参数不对」的形式延后出现。这条是本文的推断，标未验证。

fec_reset_phy() 具体怎么做，原文没贴源码。按 i.MX 系列的常见写法，它按 DTS 里的 phy-reset-gpios 和 phy-reset-duration 拉脚、等时间、放开，没有 GPIO 时靠 fec_restart() 里的 MAC 复位间接影响 PHY。确切实现未验证。

十六、net_device_ops 的装配 #

netdev_ops 是网络栈和驱动之间的唯一接口表。它是在 fec_enet_init() 里挂上的：

	ndev->watchdog_timeo = TX_TIMEOUT;
	ndev->netdev_ops = &fec_netdev_ops;
	ndev->ethtool_ops = &fec_enet_ethtool_ops;

fec_netdev_ops 的关键成员，逐个说明协议栈什么时候会调它：

ndo_init 为 NULL 这件事值得说清楚：net_device_ops 里所有钩子都是可选的，netdev_ops 里没实现的就是 NULL，调用点上都会先判空。__dev_open() 里 if (!ret && ops->ndo_open) 这一句就是判空的写法，但它是「有就调」，没 ndo_open 的网卡照样能 up，只是什么硬件动作都不做。这对虚拟设备（veth、dummy）是正常设计，对真网卡就是驱动没写完。

ndo_do_ioctl 这个名字在 4.x 之后被拆成了 ndo_do_ioctl + ndo_siocdevprivate，mii-tool、ethtool -d 这类工具就是靠它下到驱动的。FEC 的 fec_enet_ioctl 处理 SIOCDEVPRIVATE 和 MDIO 读写透传，mii-tool -v 能读 PHY 寄存器就是因为有它。

ethtool_ops 是另一张表，走 SIOCETHTOOL 这个命令进 dev_ethtool()，和 net_device_ops 平行。FEC 的 fec_enet_ethtool_ops 里填了 get_settings、set_settings、get_drvinfo、get_regs、nway_reset、get_link、get_coalesce、get_pauseparam、get_ethtool_stats、get_ts_info、get/set_tunable、get/set_wol 这些成员（原文有全文，此处按功能归类）。

所以同一个 ethtool 命令在 A 板子好用、B 板子报 Operation not supported，不是工具的问题，是驱动没实现对应成员，缺哪个退哪个。

十七、从 probe 到设备可以被 open #

probe 成功返回 0，eth0 出现在 /sys/class/net/，但硬件是「关机」状态。要让它能收发，还必须走一次 ndo_open。这两段的关系要理清：

项目 probe 做的事 open 做的事
时钟 开一次 → 关掉 再开
引脚 default → sleep 切回 default
DMA 描述符 fec_enet_init() 分配 fec_enet_alloc_buffers() 分配 skb 缓冲
PHY fec_enet_mii_init() 建 mii_bus + phy_device fec_enet_mii_probe() 才 phy_connect()
中断 devm_request_irq() 注册 napi_enable() 打开
carrier netif_carrier_off() phy_start() 后由 PHY 状态机决定

这张表是全文的总结：probe 建好了「设备」，open 才建立「连接」。PHY 的 phy_connect() 在 open 里而不是 probe 里，是 FEC 驱动的选择，代价就是第十章那个「注册成功但打不开」的坑。

ndo_open 之后，__dev_open() 还要补上网络栈那一半：置 IFF_UP、再走一次 dev_set_rx_mode()、dev_activate() 建 qdisc 并置 IFF_RUNNING、把 MAC 混进熵池。dev_activate() 那一步是驱动完全看不见的，协议栈真正开始排队发包在它之后。所以 ifconfig 显示 UP RUNNING 说明 ndo_open 和 dev_activate 都成了；只显示 UP 说明队列没起来或者 carrier 为 down。

fec_enet_close() 是对称的回滚：__dev_close() 先发 NETDEV_GOING_DOWN notifier，再清 __LINK_STATE_START，然后调 ops->ndo_stop，最后 dev_deactivate()。原文没贴它的源码，从 fec_enet_open() 的失败路径反推，它至少要做：phy_stop()、phy_disconnect()、napi_disable()、netif_tx_stop_all_queues()、fec_enet_free_buffers()、关时钟、切 sleep 引脚。具体顺序未验证。

十八、mii_bus：PHY 的总线抽象 #

PHY 不是一根线，是一条总线上的设备。硬件上这条总线叫 MDIO：两根线，MDC 是时钟，MDIO 是双向数据。MAC 通过它读写 PHY 的标准寄存器。

MII 是 IEEE 802.3 定义的那套接口总称，包含两部分：MAC 和 PHY 之间的数据接口（MII_TXD[3:0]、MII_RXD[3:0]、MII_TX_CLK、MII_RX_CLK、MII_CRS、MII_COL 这些），和管理接口（MDC/MDIO）。RMII 是精简版，引脚从 16 根压到 7 根，时钟提到 50MHz，MAC 和 PHY 必须同源时钟。这一段出自素材里转引的硬件说明，细节以 IEEE 802.3 原文为准，未逐条核对。

软件上，这条总线就是一个 struct mii_bus，字段逐个说（结构体全文见素材，此处按字段拆）：

字段 类型 干什么 谁填
name const char * 总线名字，日志里能看到 驱动
id char[MII_BUS_ID_SIZE] 唯一标识，拼进 PHY_ID_FMT 驱动
priv void * 反推控制器私有数据的钩子 驱动，填 fep
read 函数指针 读一个 PHY 寄存器 驱动实现
write 函数指针 写一个 PHY 寄存器 驱动实现
reset 函数指针 复位整条总线 驱动实现，可空
mdio_lock struct mutex 串行化同一条总线上的访问 框架初始化
parent struct device * 指向上层，串起 sysfs 驱动填 &pdev->dev
state 枚举 生命周期四态 mdiobus_alloc/register
dev struct device 它在 mdio_bus_type 上的身份 框架
phy_map[PHY_MAX_ADDR] phy_device * 数组 地址 → 设备的直接索引 扫描时填
phy_mask u32 哪些地址不要扫，1 表示跳过 of_mdiobus_register 或驱动
irq[] int * 每个地址对应的中断号 驱动填 PHY_POLL

phy_map 是这张结构里最有用的字段：它是「PHY 地址 → phy_device 指针」的定长数组，fec_enet_mii_probe() 的分支 B 就是直接扫它。PHY_MAX_ADDR 是 32，所以一个 MDIO 总线最多挂 32 个 PHY。

上层封装只有两个函数：mdiobus_read(bus, addr, regnum) 和 mdiobus_write(bus, addr, regnum, val)。两者都是先 BUG_ON(in_interrupt())，再 mutex_lock(&bus->mdio_lock)，调 bus->read / bus->write，然后解锁、返回。

三个设计点：BUG_ON(in_interrupt()) 保证 MDIO 传输可以在里面睡觉等完成（所以 fec_enet_mdio_read() 里能 wait_for_completion_timeout()）；mdio_lock 在框架层，驱动实现 read/write 时不用自己加锁；框架只做转发和加锁，真正碰硬件的是 bus->read / bus->write，所以 phy_device 不关心底下是 FEC 的 MDIO 还是 bit-bang 的 GPIO MDIO。

十九、mii_bus 的初始化流程 #

fec_enet_mii_init() 第一步是 mdiobus_alloc() 填字段：name = "fec_enet_mii_bus"、read = fec_enet_mdio_read、write = fec_enet_mdio_write、id 用 snprintf("%s-%x", pdev->name, fep->dev_id + 1) 拼成、priv = fep、parent = &pdev->dev，再把 irq[] 全填 PHY_POLL。

注意 irq[] 全填 PHY_POLL，意思是「轮询」而不是中断。所以成功日志里那行是 irq=-1：PHY 用轮询状态机检测 link 变化，不用中断。这也是为什么这类板子拔网线后 carrier 变化有几秒延迟。

第二步是注册。有 DTS 子节点 mdio 就走 of_mdiobus_register()，否则走裸的 mdiobus_register()：

c
	node = of_get_child_by_name(pdev->dev.of_node, "mdio");
	if (node) {
		err = of_mdiobus_register(fep->mii_bus, node);
		of_node_put(node);
	} else {
		err = mdiobus_register(fep->mii_bus);
	}

本环境 DTS 里有 mdio 子节点，所以走前者。它先 mdio->phy_mask = ~0 把 32 个地址全部屏蔽（禁止 mdiobus_register() 内部自动扫描），再 mdiobus_register() 把总线挂进 mdio_bus_type，最后 for_each_available_child_of_node() 逐个子节点读 reg 并调 of_mdiobus_register_phy()。这样做的理由在注释里写着：DTS 里列了哪些 PHY，就只认哪些。

本环境的 DTS 片段：

c
	mdio {
		#address-cells = <1>;
		#size-cells = <0>;
		ethphy0: ethernet-phy@1 {
			compatible = "ethernet-phy-ieee802.3-c22";
			reg = <0>;
		};
	};

这段原文有内部矛盾，得指出来：节点名写的是 ethernet-phy@1，但 reg = <0>。按 DTS 规范，节点名里的 @1 是 unit-address，必须和 reg 一致，不一致会被 dtc 报警告。真正生效的是 reg = <0>，所以日志里的地址是 :00，和实际行为对得上。节点名那个 @1 是笔误，本文以 reg 为准。

软件层的注册链：

最后一行 phy_device_register() 是整个问题的落点：只有它成功，mdio_bus_type 的 device 链表上才会出现那个 of_node 匹配得上的 phy_device。of_phy_find_device() 找的就是这个链表。

fec_enet_mdio_read() 是真正碰硬件的最后一层，只有几步：

c
static int fec_enet_mdio_read(struct mii_bus *bus, int mii_id, int regnum)
{
	struct fec_enet_private *fep = bus->priv;
	unsigned long time_left;

	fep->mii_timeout = 0;
	init_completion(&fep->mdio_done);

	/* start a read op */
	writel(FEC_MMFR_ST | FEC_MMFR_OP_READ |
		FEC_MMFR_PA(mii_id) | FEC_MMFR_RA(regnum) |
		FEC_MMFR_TA, fep->hwp + FEC_MII_DATA);

	/* wait for end of transfer */
	time_left = wait_for_completion_timeout(&fep->mdio_done,
			usecs_to_jiffies(FEC_MII_TIMEOUT));

	if (time_left == 0) {
		fep->mii_timeout = 1;
		netdev_err(fep->netdev, "MDIO read timeout\n");
		return -ETIMEDOUT;
	}

	/* return value */
	return FEC_MMFR_DATA(readl(fep->hwp + FEC_MII_DATA));
}

fec_enet_mdio_write() 结构一样，区别是 FEC_MMFR_OP_WRITE 和多带了 FEC_MMFR_DATA(value)，超时后同样返回 -ETIMEDOUT。

这是理解第十章故障的关键：MDIO 读超时时返回 -ETIMEDOUT，不返回 -ENODEV。所以如果你在 dmesg 里看到 MDIO read timeout，那是时钟/供电/复位的问题，直接指向硬件时序。相反，如果 dmesg 里什么 MDIO 报错都没有，却仍然 -ENODEV，说明读是成功的，只是读回来的 phy_id 全是 F（见第二十章）。

fec->miibus_up_failed、fep->mii_timeout 这两个标志是给 ndo_open 失败后做二次判断用的，原文没展开。

本环境的 DTS 里没有 phy_id 属性，of_get_phy_id() 失败，所以走 get_phy_device()。这是唯一一次真正去读 PHY 寄存器的地方，也是时序问题暴露的地方。

c
struct phy_device *get_phy_device(struct mii_bus *bus, int addr, bool is_c45)
{
	struct phy_c45_device_ids c45_ids = {0};
	u32 phy_id = 0;
	int r;

	r = get_phy_id(bus, addr, &phy_id, is_c45, &c45_ids);
	if (r)
		return ERR_PTR(r);

	/* If the phy_id is mostly Fs, there is no device there */
	if ((phy_id & 0x1fffffff) == 0x1fffffff)
		return NULL;

	return phy_device_create(bus, addr, phy_id, is_c45, &c45_ids);
}

get_phy_id() 只做两次 mdiobus_read()，把高 16 位和低 16 位拼起来：

c
	/* Grab the bits from PHYIR1, and put them in the upper half */
	phy_reg = mdiobus_read(bus, addr, MII_PHYSID1);
	if (phy_reg < 0)
		return -EIO;
	*phy_id = (phy_reg & 0xffff) << 16;

	/* Grab the bits from PHYIR2, and put them in the lower half */
	phy_reg = mdiobus_read(bus, addr, MII_PHYSID2);
	if (phy_reg < 0)
		return -EIO;
	*phy_id |= (phy_reg & 0xffff);

两个寄存器，都是 IEEE 802.3 规定的通用寄存器：MII_PHYSID1 = 0x02、MII_PHYSID2 = 0x03。PHYSID1 是 ID 高 16 位，PHYSID2 是低 16 位，合成一个 32 位 phy_id。

get_phy_device() 里那行判据是本章的第二个落点：

c
	if ((phy_id & 0x1fffffff) == 0x1fffffff)
		return NULL;

读回来全是 1（0x1fffffff），说明这个地址上没有任何 PHY 应答，MDIO 被上拉电阻拉成了高电平。这是标准的硬件判断，不是软件 bug。

get_phy_device() 随后返回 ERR_PTR(r) / NULL，of_mdiobus_register_phy() 里 if (!phy || IS_ERR(phy)) return 1;，直接放弃，phy_device_register() 根本没被调用。

二十一、PHY 驱动怎么与 PHY 设备匹配 #

phy_device 在 mdio_bus_type 上，就要有对应的 driver 在总线上，匹配规则由 mdio_bus_type.match 给出：

c
static int mdio_bus_match(struct device *dev, struct device_driver *drv)
{
	struct phy_device *phydev = to_phy_device(dev);
	struct phy_driver *phydrv = to_phy_driver(drv);

	if (of_driver_match_device(dev, drv))
		return 1;

	if (phydrv->match_phy_device)
		return phydrv->match_phy_device(phydev);

	return (phydrv->phy_id & phydrv->phy_id_mask) ==
		(phydev->phy_id & phydrv->phy_id_mask);
}

三层依次尝试：

顺序 判据 说明
1 of_driver_match_device() DTS 里 compatible 直接指驱动，优先级最高
2 phydrv->match_phy_device() 驱动自己写的匹配函数，可处理 ID 不规则的特例
3 (drv->phy_id & mask) == (dev->phy_id & mask) 标准做法：ID 按掩码比较

第三条是常规路径。phy_id_mask 决定比较哪几位：高 5 位是 OUI 之外的厂商/型号编码，各家掩码不同，比如 0x001fffff 表示只比低 21 位。

PHY 驱动的注册表，本环境用的是 Realtek RTL8201F：

这里有一处原文没说清、值得补充的地方：0x001cc816 和 0x001cc912 在 0x001fffff 掩码下不同（差在低 9 位），所以两者不会互相误匹配。但 realtek_tbl[] 少了 RTL8201CP 那一项（0x00008201），这个表是给模块自动加载用的别名表，缺一项只影响 modprobe 自动加载，不影响已经编进内核的 realtek_drvs 匹配。原文没解释这个区别。

二十二、phy_connect 与 link 状态上报 #

fec_enet_mii_probe() 拿到 phy_device 之后要做绑定，走 phy_connect()：phy_attach() 按 PHY_ID_FMT 拼出的名字（如 2188000.ethernet:00）查 phy_device，再 phy_attach_direct() 把 attached_dev、interface、adjust_link 填进 phydev，跑一遍驱动自己的 config_init，最后 phy_start_machine() 启动状态机。

分支 A 走 of_phy_connect()，它先 of_phy_find_device() 拿到 phy_device，再 phy_connect_direct()，跳过按名字查那一步。这里就是 -ENODEV 的另一个入口：phy_connect() 查不到设备返回 ERR_PTR(-ENODEV)，然后 fec_enet_mii_probe() 的 IS_ERR(phy_dev) 分支 return PTR_ERR(phy_dev) 也是 -19。两条分支殊途同归，最终都给用户态一个 -19。

fec_enet_adjust_link 是驱动给 PHY 层的回调，link 状态变化时由 PHY 状态机调：

text
phy_state_machine()（内核定时器，默认轮询）
 ├── 读 PHY 状态寄存器
 ├── link 变了
 │    ├── phydev->link = 0/1
 │    ├── 调 phydev->adjust_link(phydev->attached_dev)
 │    │      → fec_enet_adjust_link(ndev)
 │    │           ├── 读 fep->phy_dev->speed / duplex
 │    │           ├── 更新 fep->link / fep->full_duplex
 │    │           ├── fec_restart(ndev)            重配 MAC 速率位
 │    │           └── phy_print_status(phydev)
 │    └── phydev->state = PHY_RUNNING / PHY_NOLINK
 └── netif_carrier_on/off(attached_dev)             协议栈层

fec_enet_adjust_link() 的关键动作和 fec_restart() 里的速率位对得上：probe 阶段 fec_restart() 配的速率位是「还不知道」的默认值，link up 之后要靠这个回调重写一遍。fep->phy_dev->speed == SPEED_1000 / SPEED_100 / 其他，分别对应 ecntl |= (1 << 5)、rcntl &= ~(1 << 9)、rcntl |= (1 << 9)。

irq = -1（PHY_POLL）意味着这个回调由内核定时器驱动，不是中断驱动。所以插拔网线后 ip link 的 state 变化有几秒延迟，不是故障。

phy_start() 在 fec_enet_open() 里调，位置在 fec_enet_mii_probe() 之后、netif_tx_start_all_queues() 之前。顺序有意义：phy_start() 之后 PHY 状态机开始跑，会立刻触发 adjust_link，而 adjust_link 会调 fec_restart() 重配 MAC。所以 fec_restart() 必须在 PHY 连上之后至少还能再跑一次，napi_enable() 也得在它之前，否则回调里会碰上未启用的 NAPI。

netif_carrier_off/on 是 PHY 层调的，不是驱动调的。probe 里那次 netif_carrier_off() 只是给个初值。最终 carrier 状态由 phydev->link 决定。ifconfig 里的 RUNNING 和 carrier 是两回事：RUNNING 看 IFF_RUNNING（dev_activate 置的），carrier 看 netif_carrier_ok()。两者都为真，才说明链路真的通了。

bash

四、能用但速率/双工不对

落点在 fec_enet_adjust_link() 和 fec_restart() 的速率位。查 PHY 的 advertising、MAC 的 fep->phy_dev->speed、DTS 的 phy-mode 是否和硬件接法一致（RGMII 接成 RMII 就是这类）。

连载指代清理 #

素材五篇每篇开头都有「我们继续沿着上一篇的以太网思路来继续分析」这类句子，以及「之前有讲过流程，我这里再提一下」「大家还记得我们要分析什么吧」「以上五篇文章就是我个人的记录」等连载专属表述，全部删除或改写为中性的「这套环境」「本章」。原文里的「我们继续」「接着看」「跟入看下」保留为叙述语气，不指代具体篇目。

修正的错误 #

  1. -19 的推断链少了两步。连载五写「既然没有从寄存器中获取到 phy_id，因此 phy_device_create 也不会在 mii bus 数据结构中创建 phy_device」，跳过了 get_phy_device() 里 (phy_id & 0x1fffffff) == 0x1fffffff 的全 F 判据，以及 of_mdiobus_register_phy() 里 return 1 放弃注册。本文第二十章补齐，补成完整的十一环。
  2. ifconfig 与 dev_ifsioc 的关系。连载一写「一路走到 dev_ifsioc」，连载二的 dump_stack 实栈里没有 dev_ifsioc()。SIOCSIFFLAGS 是从 devinet_ioctl() 直接调 dev_change_flags()，不过 dev_ifsioc()。本文第四章按实栈写，并说明 dev_ifsioc() 那条路留给其他 ioctl 命令。
  3. 「随机数函数刚好满足 150ms 时序」是伪因果。连载一说第 5 级路径「刚刚好好在这个硬件条件下，恰巧满足了 150ms 的 reset 时序要求」。get_random_bytes() 的耗时不可控，真实机制是「多了一次熵池提取，延迟落在临界值附近，行为呈概率性」。本文第十章改写为概率性解释，并指出这套「靠延迟碰运气」的代码本身不该存在。
  4. DTS 节点名与 reg 不一致。连载五贴的 DTS 里节点名是 ethernet-phy@1，reg = <0>，但日志里是 phy_addr=2188000.ethernet:00。生效的是 reg，节点名的 @1 是笔误，dtc 会报警告。本文第十九章指出，以 reg 为准。
  5. realtek_tbl[] 与 realtek_drvs[] 的作用被混同。连载五把两张表并列贴出，没区分。realtek_drvs[] 决定总线匹配，realtek_tbl[] 只影响模块自动加载别名。本文第二十一章分开说明，并指出 tbl 里缺了 RTL8201CP 项，不影响已经编进内核的匹配。
  6. fec_enet_mii_probe() 两条分支的错误码差异。连载三只讲了 of_phy_connect() 返回 NULL 的 -ENODEV。分支 B 走 phy_connect()，失败时是 ERR_PTR + could not attach to PHY，能看到真实 errno。of_phy_connect() 把错误全吞成 NULL，所以分支 A 永远只有 -19。本文第八章补了这张对照表。
  7. 代码围栏语言标错。素材里大量 C 代码块被标成 makefile 或 text 当作语言标记（尤其 __dev_change_flags、fec_get_mac 的片段）。本文统一改为 c。
  8. 重复粘贴的代码合并。__dev_change_flags() 在连载一、连载二各贴一遍，eth_hw_addr_random() / eth_random_addr() 在连载一、连载四共出现四次，fec_restart() 在连载四贴全文后又用 11 行文字把注释重述一遍，sock_map_fd() 在连载二连贴两遍。全部合并为一次，保留完整代码，删掉重复。
  9. 第一段汇编的 kill() 流程是错置。连载一在讲 ioctl 的段落里插了一句「总体流程：kill() → swi陷入内核态 → sys_call_table 查 sys_kill」，这是另一个系统调用的例子，和 ioctl 无关。本文第三章只保留 ret_fast_syscall 返回路径，删掉 kill 那段，改为 ioctl 的真实路径。
