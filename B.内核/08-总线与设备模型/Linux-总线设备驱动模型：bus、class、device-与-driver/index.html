这篇只做一件事：把设备模型的四个核心结构体 bus_type、class、device、device_driver 逐字段讲清楚，外加它们共享的 subsys_private 和 class_interface。

不覆盖：bus_register / device_register / driver_register 的完整调用链、bus_type->match 的匹配规则、id_table、deferred probe、设备生命周期与引用计数、四个结构体在 sysfs 里的完整位置表。这些在 device、driver、bus、class：四个注册表，那篇讲流程，这篇讲结构。

更底层的东西：kobject / kset / sysfs 的实现见 kobject 与 sysfs：设备模型的底座；platform 总线与 devres 见 platform 设备与 devres：平坦总线与资源自动回收。

版本口径：Linux 5.2.8（原文标注的版本）。文中结构体定义与字段注释来自该版本 include/linux/device.h 与 drivers/base/base.h。6.x 之后有变动的地方逐处标出。

一、四个结构体在设备模型里的位置 #

Linux 是宏内核，它得支持世界上几乎所有能跑的硬件。代价是驱动代码占了内核的大半，而且随硬件换代还在涨。设备模型（Driver Model）就是从 2.6 开始引入的一套统一抽象：把硬件归纳成「总线」「设备」「驱动」「类」四个概念，驱动开发从论述题变成填空题。

四个结构体的分工：

结构体 回答什么问题 关键字段
struct bus_type 这些设备和驱动通过什么通道通信？ name、match、probe、p
struct device 这个具体设备是什么、挂在哪、谁来管？ kobj、parent、bus、driver、class、release
struct device_driver 这段代码能驱动哪些设备？ name、bus、probe、remove、of_match_table
struct class 从「功能」角度看，它属于哪一类？ name、dev_uevent、devnode、dev_groups

关键点在于这四者不是并列的四个类别，而是四个维度的描述：

text
              ┌─────────────────────────────┐
              │        struct bus_type      │  通道
              │   （i2c / spi / platform）   │
              └──────────┬──────────────────┘
                         │ 挂载
        ┌────────────────┴────────────────┐
        │                                 │
┌───────▼────────┐              ┌─────────▼──────────┐
│  struct device │◄────绑定────►│ struct device_driver│
│   （一个实例）  │   match()    │    （一段代码）     │
└───────┬────────┘              └────────────────────┘
        │ 归类（正交，可空）
┌───────▼────────┐
│  struct class  │  /sys/class/net、/sys/class/tty …
└────────────────┘

两条读图要点：

一、bus 决定「能不能绑」。 设备注册到哪条总线，就在这条总线的设备链表里等；驱动注册到哪条总线，就在这条总线的驱动链表里找。跨总线的设备和驱动永远不会匹配。

二、class 与 bus 正交。 一个 device 可以既挂 i2c 总线、又属于 hwmon 类。bus 描述「怎么连的」，class 描述「是干什么的」。这也是为什么 /sys/class/ 下的条目全是符号链接。实体在 /sys/devices/，/sys/class/ 只是按功能重新排了一次索引。

二、struct bus_type：总线怎么描述自己 #

定义在 include/linux/device.h。原样的 kerneldoc 加字段：

c
struct bus_type {
        const char              *name;
        const char              *dev_name;
        struct device           *dev_root;
        const struct attribute_group **bus_groups;
        const struct attribute_group **dev_groups;
        const struct attribute_group **drv_groups;

        int (*match)(struct device *dev, struct device_driver *drv);
        int (*uevent)(struct device *dev, struct kobj_uevent_env *env);
        int (*probe)(struct device *dev);
        int (*remove)(struct device *dev);
        void (*shutdown)(struct device *dev);

        int (*online)(struct device *dev);
        int (*offline)(struct device *dev);

        int (*suspend)(struct device *dev, pm_message_t state);
        int (*resume)(struct device *dev);

        int (*num_vf)(struct device *dev);

        int (*dma_configure)(struct device *dev);

        const struct dev_pm_ops *pm;

        const struct iommu_ops *iommu_ops;

        struct subsys_private *p;
        struct lock_class_key lock_key;

        bool need_parent_lock;
};

2.1 标识与属性组 #

字段 含义 填不填
name 总线名，决定 /sys/bus/<name>/ 的目录名 必填
dev_name 子系统给设备做简单枚举时用的名字模板，如 "foo%u" 很少填
dev_root 默认父设备 现代几乎不用（靠 device->parent 逐级指定）
bus_groups 总线自身的属性组，出现在 /sys/bus/<name>/ 下 按需
dev_groups 该总线上所有设备默认带的属性组 按需
drv_groups 该总线上所有驱动默认带的属性组 按需

三个 groups 字段是「批量挂属性」的机制。设备驱动里也可以给单个设备加属性（device->groups），总线上这三个管的是「这条总线上的所有成员都要有的属性」，典型例子是 i2c 总线上所有设备都带一个 name 属性。

2.2 五个生命周期回调 #

回调 何时调用 现状
match 总线上有新设备或新驱动加入时，逐个尝试配对 核心，必填
probe 匹配成功后初始化设备 已废弃，见下
remove 设备移除时 已废弃
shutdown 关机时静默设备 已废弃
uevent 设备增删时补充环境变量 按需

probe / remove / shutdown 三个标「已废弃」，原因在 driver_register() 里写得很明白：

c
if ((drv->bus->probe && drv->probe) ||
    (drv->bus->remove && drv->remove) ||
    (drv->bus->shutdown && drv->shutdown))
        printk(KERN_WARNING "Driver '%s' needs updating - please use "
                "bus_type methods\n", drv->name);

同一件事既能在 bus_type 里实现、又能在 device_driver 里实现，实际只会执行一个，所以内核看到两边都填就告警。正确做法是用 device_driver 里的那份。因为不同设备需要不同的 probe 逻辑，放在驱动里才合理；放在总线上等于逼所有驱动写同一套。

bus_type 里的这三个回调保留至今只为兼容极老的驱动，新代码不要填。

2.3 match 的返回值 #

match 是四个回调里唯一必须写对的。三条约定：

返回值 含义
正数 匹配成功
0 不匹配
-EPROBE_DEFER 暂时无法判断，把设备挂到 deferred probe 队列，稍后重试

这条要专门强调，因为很多中文资料写反了。返回 0 表示「不匹配」，不是「匹配」。 如果写成「匹配返回 0」，结果是全部设备都配不上任何驱动，或者反过来，取决于你怎么读那段代码。

-EPROBE_DEFER 是延迟探测机制：驱动依赖的资源（比如时钟、regulator、另一个还没加载的模块）还没就绪时，返回它，内核不会报错，而是把设备放进 deferred_probe_pending_list，等有驱动注册或设备注册时再重试一遍。这套机制解决的是「probe 顺序不可控」这个启动期顽疾。

2.4 电源、热插拔与其他 #

字段 用途
online / offline 设备在线/离线切换（内存热插拔场景），可失败
suspend / resume 老的 PM 回调，已被 pm（struct dev_pm_ops）取代
pm 总线级电源管理操作，会回调具体驱动的 pm 操作
num_vf 该总线上的设备支持几个虚拟功能（SR-IOV）
dma_configure 给设备配置 DMA（IOMMU 相关）
iommu_ops 该总线的 IOMMU 特定操作
p 驱动核心私有数据，见第三章
lock_key 锁调试用的锁类 key
need_parent_lock probe/remove 设备时是否要锁住父设备

need_parent_lock 是 5.x 新增的，处理的是「子设备 probe 时父设备正在被移除」的竞态。

2.5 一个最小的 bus_type #

大部分字段都不用填。一个能工作的最小总线：

c
static int my_bus_match(struct device *dev, struct device_driver *drv)
{
    /* 返回正数 = 匹配；0 = 不匹配 */
    return !strcmp(dev_name(dev), drv->name);
}

static int my_bus_uevent(struct device *dev, struct kobj_uevent_env *env)
{
    return add_uevent_var(env, "MODALIAS=mybus:%s", dev_name(dev));
}

struct bus_type my_bus_type = {
    .name   = "mybus",
    .match  = my_bus_match,
    .uevent = my_bus_uevent,
};

注册用 bus_register(&my_bus_type)，注销用 bus_unregister()。注册链路见 device、driver、bus、class：四个注册表 第四章。

注册成功后的目录结构：/sys/bus/mybus/ 下会有 devices/、drivers/、drivers_probe、drivers_autoprobe、uevent，以及 bus_groups 带来的属性。

三、struct subsys_private：bus 和 class 共用的私有数据 #

bus_type 和 class 各有一个 struct subsys_private *p 字段。这不是巧合。

定义在 drivers/base/base.h：

c
struct subsys_private {
        struct kset subsys;                  /* 代表 bus/class 在 sysfs 里的这层 kset */
        struct kset *devices_kset;           /* bus 目录下的 devices 子目录 */
        struct list_head interfaces;         /* 接口链表，class_interface 挂这 */
        struct mutex mutex;

        struct kset *drivers_kset;           /* bus 目录下的 drivers 子目录 */
        struct klist klist_devices;          /* 该总线上的设备链表 */
        struct klist klist_drivers;          /* 该总线上的驱动链表 */
        struct blocking_notifier_head bus_notifier;
        unsigned int drivers_autoprobe:1;    /* 增删时是否自动匹配，默认 1 */
        struct bus_type *bus;

        struct kset glue_dirs;
        struct class *class;
};

3.1 为什么要这个结构 #

直接看 struct bus_type 的字段会发现，里面没有任何「链表头」「kset」这类运行时状态。全部塞进 p 里了。

理由有三条：

一、让 bus_type 可以静态分配。 驱动写 struct bus_type my_bus = {...} 放在 .data 段，编译期就定好了。而链表头、mutex 这些东西必须在运行时初始化。如果它们直接放在 bus_type 里，每个驱动都得自己调一堆 INIT_LIST_HEAD，漏一个就是野指针。

二、屏蔽内部细节。 subsys_private 的注释写得很直白：「Nothing outside of the driver core should ever touch these fields」。子系统作者只需要填 match/uevent 这些回调，运行时状态由核心管。

三、bus 和 class 的结构高度相似。 两者在 sysfs 里都是「一个目录 + 一个 devices 子目录 + 一堆成员」，都要维护成员链表、都要发 uevent。所以 3.x 后期把两份私有数据合并成了一个 subsys_private。

最后这条有个历史痕迹：内核早期它叫 bus_type_private，只给 bus_type 用。后来发现 class 需要一模一样的东西，就改名合并了。原文说「命名为 bus_private 会好点」，这个说法不准确。它没有改叫 bus_private，而是直接叫 subsys_private，因为已经不是 bus 专属了。

3.2 字段怎么用 #

自己写总线驱动时，一般只会用到两个：

字段 什么时候碰
p->klist_devices 遍历该总线上的所有设备
p->bus_notifier 注册总线事件回调（bus_register_notifier）
p->drivers_autoprobe 通过 /sys/bus/<name>/drivers_autoprobe 读写，控制是否自动匹配

遍历所有设备的典型写法（内核里有宏封装）：

c
/* drivers/base/bus.c 里的 bus_for_each_dev 精简化 */
int bus_for_each_dev(struct bus_type *bus, struct device *start,
                     void *data, int (*fn)(struct device *, void *))
{
        struct klist_iter i;
        struct device *dev;
        int error = 0;

        if (!bus || !bus->p)
                return -EINVAL;

        klist_iter_init_node(&bus->p->klist_devices, &i,
                             (start ? &start->p->knode_bus : NULL));
        while ((dev = next_device(&i)) && !error)
                error = fn(dev, data);
        klist_iter_exit(&i);
        return error;
}

klist 而不是普通 list_head 的原因：遍历期间可能会有设备被并发摘除，klist 带引用计数，能保证遍历到一半节点被删也不会踩空。

四、struct class：分类的抽象 #

class 解决的是另一个维度的问题。同一类设备（所有网卡、所有串口、所有输入设备）在功能上是相似的，用户态希望按功能而不是按连接方式来访问它们。class 就是这个「功能视角」。

c
struct class {
        const char              *name;
        struct module           *owner;

        const struct attribute_group    **class_groups;
        const struct attribute_group    **dev_groups;
        struct kobject                  *dev_kobj;

        int (*dev_uevent)(struct device *dev, struct kobj_uevent_env *env);
        char *(*devnode)(struct device *dev, umode_t *mode);

        void (*class_release)(struct class *class);
        void (*dev_release)(struct device *dev);

        int (*shutdown_pre)(struct device *dev);

        const struct kobj_ns_type_operations *ns_type;
        const void *(*namespace)(struct device *dev);

        void (*get_ownership)(struct device *dev, kuid_t *uid, kgid_t *gid);

        const struct dev_pm_ops *pm;

        struct subsys_private *p;
};

4.1 字段逐个说 #

字段 含义 备注
name 类名，决定 /sys/class/<name>/ 必填
owner 所属模块，一般 THIS_MODULE 6.4 起删除，见 4.4
class_groups 类自身的属性组 按需
dev_groups 该类下所有设备的默认属性组 按需
dev_kobj 该类设备在 /sys/dev/ 下的目录，一般是 char 或 block；NULL 时默认 char 内核填，驱动不管
dev_uevent 设备进出该类时补充 uevent 环境变量 按需
devnode 返回设备节点的相对路径，供 devtmpfs 建节点 按需
class_release 类销毁时的回调 由 class_create 填
dev_release 该类下设备销毁时的回调 按需
shutdown_pre 关机前、驱动 shutdown 之前的回调 少见
ns_type / namespace sysfs 命名空间支持（网络命名空间等） 少见
get_ownership 指定 sysfs 目录的 uid/gid 少见
pm 该类的默认电源管理操作 按需
p subsys_private，与 bus_type 共用 驱动核心填

devnode 是字符设备驱动最常用的一个。它和 devtmpfs_create_node() 配合，让内核直接建 /dev 节点，不依赖 udev：

c
static char *my_devnode(struct device *dev, umode_t *mode)
{
    if (mode)
        *mode = 0666;          /* 顺手把权限改掉，省得用户态再 chmod */
    return NULL;               /* NULL 表示用默认名字 dev_name(dev) */
}

注意 mode 参数是出参：传入一个指向 umode_t 的指针，你往里写权限值，内核拿它当节点权限。这一点很多人以为是入参。

4.2 class_interface：设备进出类的钩子 #

class 有一个其他地方找不到的机制：接口。它是一组「当设备加入或离开这个类时会被调用」的回调。

c
struct class_interface {
        struct list_head        node;
        struct class            *class;

        int (*add_dev)     (struct device *, struct class_interface *);
        void (*remove_dev) (struct device *, struct class_interface *);
};

int class_interface_register(struct class_interface *class_intf);
void class_interface_unregister(struct class_interface *class_intf);

一个类可以挂多个接口，调用发生在 device_add() 的末尾：

c
    if (dev->class) {
        mutex_lock(&dev->class->p->mutex);
        /* 把设备挂进 class 的设备链表 */
        klist_add_tail(&dev->knode_class,
                       &dev->class->p->klist_devices);

        /* 通知所有已注册的接口：这个设备来了 */
        list_for_each_entry(class_intf,
                            &dev->class->p->interfaces, node)
                if (class_intf->add_dev)
                        class_intf->add_dev(dev, class_intf);
        mutex_unlock(&dev->class->p->mutex);
    }

这套机制解决什么问题？ 想象一个子系统想「接管所有属于某个类的设备」，但它不可能是这些设备的驱动，设备有自己的驱动。class_interface 让它能旁听：设备一进这个类，就拿到通知。

典型用法是 input 子系统、tty 子系统这类「汇聚型」子系统。它们不实现具体设备的驱动，但要在设备注册时建立自己的数据结构。

三个使用要点：

一、add_dev 的返回值有语义。 返回非 0 会让 device_add() 失败并回滚。所以不要在里面做可能失败的重量级操作。

二、回调在 class->p->mutex 保护下执行。 里面不能再获取同一个锁，也不能长时间阻塞。

三、注册顺序有影响。 class_interface_register 时会遍历已存在的设备，对每个都调一次 add_dev。所以「注册接口」这个动作本身就会触发一堆回调，别在 add_dev 里假设「这是第一个设备」。

4.3 class 与 bus 的正交性 #

这是最容易搞混的一点。用网卡举例：

text
PCI 总线上的网卡：
  /sys/devices/pci0000:00/0000:00:1f.6/     ← 实体，挂在 PCI 总线下
  /sys/bus/pci/devices/0000:00:1f.6        ← PCI 总线的设备索引（符号链接）
  /sys/class/net/eth0                      ← 网络类的功能索引（符号链接）

一个 struct device 同时出现在三个位置。bus 那两条是「怎么连的」，class 那条是「干什么的」。

所以：

  • 同一条总线上的设备可以属于不同类（PCI 总线上有网卡、显卡、声卡）
  • 同一个类下的设备可以来自不同总线（/sys/class/net/ 下有 PCI 网卡、USB 网卡、虚拟的 lo）

这也解释了 /sys/class/ 里为什么全是符号链接：实体只能有一份，就是 /sys/devices/ 下那棵物理树；bus 和 class 都是索引。

4.4 class_create 的签名变过 #

5.2.8 时代：

c
/* include/linux/device.h，是个宏 */
#define class_create(owner, name)               \
({                                              \
        static struct lock_class_key __key;     \
        __class_create(owner, name, &__key);    \
})

struct class *__class_create(struct module *owner, const char *name,
                             struct lock_class_key *key);

__class_create 的实现很短：

c
struct class *__class_create(struct module *owner, const char *name,
                             struct lock_class_key *key)
{
        struct class *cls;
        int retval;

        cls = kzalloc(sizeof(*cls), GFP_KERNEL);
        if (!cls) {
                retval = -ENOMEM;
                goto error;
        }

        cls->name = name;
        cls->owner = owner;
        cls->class_release = class_create_release;

        retval = __class_register(cls, key);
        if (retval)
                goto error;

        return cls;

error:
        kfree(cls);
        return ERR_PTR(retval);
}

6.4 起这个宏被删掉了，变成：

c
struct class *class_create(const char *name);

owner 参数没了。原因是 owner 本来用于「模块引用计数，防止类还在用的时候模块被卸载」，但类的生命周期已经由 kobject 引用计数管住，owner 变成了冗余。所以现在写 class_create(THIS_MODULE, "mycls") 编译不过，按你的内核版本二选一。

对应的 class_destroy() 一直没变。

五、struct device：设备的全部字段 #

系统里每一个设备都是 struct device 的一个实例。这是四个结构体里最大的一个，因为它要承载所有子系统可能需要的信息。

c
struct device {
        struct kobject kobj;
        struct device           *parent;

        struct device_private   *p;

        const char              *init_name;
        const struct device_type *type;

        struct bus_type *bus;
        struct device_driver *driver;
        void            *platform_data;
        void            *driver_data;
        struct mutex            mutex;

        struct dev_links_info   links;
        struct dev_pm_info      power;
        struct dev_pm_domain    *pm_domain;

#ifdef CONFIG_GENERIC_MSI_IRQ_DOMAIN
        struct irq_domain       *msi_domain;
#endif
#ifdef CONFIG_PINCTRL
        struct dev_pin_info     *pins;
#endif
#ifdef CONFIG_GENERIC_MSI_IRQ

5.1 骨架：身份与层级 #

字段 作用
kobj 内嵌的 kobject，必须在第一个位置。设备在 sysfs 里的目录、引用计数、生命周期都靠它
parent 父设备。决定 sysfs 里的目录层级，也决定电源管理、DMA 域的继承关系
p device_private，驱动核心私有。包含 knode_parent（挂进父设备子链表）、knode_bus（挂进总线设备链表）、knode_driver（挂进驱动设备链表）
init_name 初始名字。device_add() 会把它搬进 kobj.name 然后置 NULL
type struct device_type，用于给一类设备挂统一的属性和 uevent 处理
id 设备实例编号，配合 bus->dev_name 生成默认名字
release 设备释放回调，必填。引用计数归零时调用，负责 kfree

kobj 必须在第一个字段，这是硬要求。device 是一堆 kobject 派生结构之一，内核里有大量 container_of / 直接强转在 struct kobject * 和 struct device * 之间来回转。如果 kobj 不在首位，这些转换全错。

release 这条要单独强调。不填 release 的设备，在 put_device() 时不会释放，直接泄漏；更糟的是内核会打印 Device 'xxx' does not have a release() function, it is broken and must be fixed，然后拒绝销毁。这是设备模型里最常见的崩溃/泄漏来源。

c
static void my_dev_release(struct device *dev)
{
    struct my_device *md = container_of(dev, struct my_device, dev);
    kfree(md);
}

5.2 绑定关系：bus / driver / class #

字段 作用
bus 该设备所在的总线。device_add() 时由驱动或 device_create 填
driver 当前绑定到这个设备的驱动。匹配成功后由核心填，驱动代码不要自己改
class 所属的类，可以为 NULL
groups 单个设备的属性组，会叠加到 class->dev_groups 和 bus->dev_groups 之上

driver 的处理要小心。它由 device_bind_driver() / driver_probe_device() 在匹配成功时设置，驱动自己改这个字段会导致 sysfs 链接错乱和引用计数失衡。想知道「我绑定到哪个驱动了」，用 dev->driver 读，别写。

5.3 数据挂载：platform_data 与 driver_data #

这两个字段经常被混用，区别很清楚：

字段 谁写 谁读 用途
platform_data 板级代码（BSP） 驱动 描述「这块板子上这个设备是怎么接的」
driver_data 驱动自己 驱动自己 驱动运行时的私有状态 
c
/* platform_data：板级描述，编译期定死 */
static struct my_led_pdata led_pdata = {
    .gpio = 42,
    .active_low = true,
};
/* 板级代码里：platform_device_add_data(pdev, &led_pdata, sizeof(led_pdata)); */

/* driver_data：驱动运行时状态，probe 里创建 */
static int my_probe(struct platform_device *pdev)
{
    struct my_led *led = devm_kzalloc(&pdev->dev, sizeof(*led), GFP_KERNEL);

    led->pdata = dev_get_platdata(&pdev->dev);   /* 取板级数据 */
    platform_set_drvdata(pdev, led);             /* 存驱动私有数据 */
    ...
}

static ssize_t my_show(struct device *dev, ...)
{
    struct my_led *led = dev_get_drvdata(dev);   /* 取回自己的数据 */
    ...
}

driver_data 的读写要用 dev_set_drvdata() / dev_get_drvdata() 这组封装，别直接访问字段，它们在不同版本里可能带类型检查。

设备树的冲击：有了设备树之后，platform_data 的地位下降了很多，硬件描述搬进了 dts。但 driver_data 依旧不可替代。板级数据现在常从 of_property_read_* 取，而不是 platform_data。

5.4 设备树与固件接口 #

字段 作用
of_node 关联的设备树节点。of_* 系列 API 全靠它
fwnode 统一的固件节点抽象（DT / ACPI / 其他）
of_node_reused 该 dts 节点被父设备共享

fwnode 是 4.x 之后引入的抽象层。of_node 和 fwnode 共存是为了兼容：老代码继续用 dev->of_node，新代码用 device_property_read_*() 这类走 fwnode 的通用接口。这样同一份驱动不用改就能在 ACPI 和 DT 平台上工作。

判断「有没有设备树信息」不要再用 if (dev->of_node)，用 device_property_present() 或 is_of_node(dev_fwnode(dev))。

5.5 DMA 相关 #

这一组字段数量多，但驱动作者真正需要碰的只有一两个。

字段 作用
dma_mask 该设备能寻址的 DMA 地址位宽掩码，如 DMA_BIT_MASK(32)
coherent_dma_mask 一致性 DMA 分配时用的掩码，可能比 dma_mask 更严格
bus_dma_mask 上游桥/bus 施加的更小限制
dma_pfn_offset DMA 地址与物理地址的偏移
dma_parms 段限制描述（最大段大小等），供 IOMMU 用
dma_ops 该设备的 DMA 映射操作集
dma_pools / dma_mem / cma_area 一致性内存池、CMA 区域

典型设置（在 probe 里）：

c
ret = dma_set_mask_and_coherent(&pdev->dev, DMA_BIT_MASK(64));
if (ret)
    ret = dma_set_mask_and_coherent(&pdev->dev, DMA_BIT_MASK(32));

这几个字段必须在设备 probe 期间设置完，且要在任何 DMA 分配之前。 之后再改，之前分配出去的 buffer 的地址空间假设就错了。

5.6 资源与生命周期 #

字段 作用
devt 设备号。MAJOR(devt) 非 0 时 device_add 会在 /sys/dev/ 下建链接并触发 devtmpfs 建节点
devres_lock / devres_head devres 托管资源的锁与链表头
links 设备间依赖关系（supplier/consumer）
power / pm_domain 运行时 PM 状态与 PM 域
iommu_group / iommu_fwspec IOMMU 分组与固件描述
offline_disabled / offline 热插拔（内存）相关状态

devres_head 就是把「所有 devm_* 申请的资源」串起来的链表头，设备销毁时沿链表逐个释放。这套机制详见 platform 设备与 devres：平坦总线与资源自动回收。

5.7 device_register 与前后的分工 #

原文提到「注册 struct device 前最少要设置 parent、bus_id、bus 和 release」。这句话里的 bus_id 是错的。那是 2.6.25 之前的字段名，之后改叫 init_name，再后来连 init_name 都建议用 dev_set_name() 替代。

5.2.8 里注册的实际要求：

必须做的 说明
设 parent 或者接受它成为顶层设备（一般不是你想要的）
设 bus 或 class 至少一个，否则设备在 sysfs 里没有归属
设 release 不设会泄漏，且内核会报错
设名字 dev_set_name() 或通过 init_name 
c
int device_register(struct device *dev)
{
        device_initialize(dev);
        return device_add(dev);
}

两段的分工：

  • device_initialize()：初始化 kobj、mutex、devres 链表、PM 状态。这一步之后就可以用 get_device() / put_device() 了
  • device_add()：建 sysfs 目录、挂进各级链表、发 uevent、触发 probe

device_add() 内部顺序值得记一下，因为出问题时 dmesg 里的报错位置能对上：

text
kobject_add()                  建 /sys/devices/... 目录
device_create_file(uevent)     建 uevent 属性
[MAJOR(devt) 非 0 时]
  device_create_file(devt)     建 dev 属性（显示 主:次）
  device_create_sys_dev_entry() 建 /sys/dev/char|block/M:m 链接
  devtmpfs_create_node()       建 /dev/xxx 节点
device_add_class_symlinks()    class 下的符号链接
device_add_attrs()             设备属性
bus_add_device()               挂进总线设备链表
dpm_sysfs_add() / device_pm_add()  电源管理
kobject_uevent(KOBJ_ADD)       发 uevent
bus_probe_device()             找驱动、probe

bus_probe_device() 是最后一步，所以在 probe 函数里，前面那些 sysfs 节点都已经存在了，可以放心在 probe 里写属性。

六、struct device_driver：驱动的全部字段 #

c
struct device_driver {
        const char              *name;
        struct bus_type         *bus;

        struct module           *owner;
        const char              *mod_name;

        bool suppress_bind_attrs;
        enum probe_type probe_type;

        const struct of_device_id       *of_match_table;
        const struct acpi_device_id     *acpi_match_table;

        int (*probe) (struct device *dev);
        int (*remove) (struct device *dev);
        void (*shutdown) (struct device *dev);
        int (*suspend) (struct device *dev, pm_message_t state);
        int (*resume) (struct device *dev);
        const struct attribute_group **groups;

        const struct dev_pm_ops *pm;
        void (*coredump) (struct device *dev);

        struct driver_private *p;
};

6.1 字段逐个说 #

字段 含义 备注
name 驱动名，决定 /sys/bus/<bus>/drivers/<name>/ 必填
bus 所属总线 必填
owner 模块持有者，THIS_MODULE。防止驱动方法被调用时模块被卸载 必填
mod_name 内建（非模块）驱动的名字 少见
suppress_bind_attrs 不在 sysfs 里生成 bind / unbind 属性 按需
probe_type 同步还是异步 probe 按需
of_match_table 设备树匹配表 DT 平台必填
acpi_match_table ACPI 匹配表 ACPI 平台必填
probe 匹配成功后的初始化 必填
remove 解绑时的清理 有资源就要填
shutdown 关机时静默设备 按需
suspend / resume 老的 PM 回调，被 pm 取代 不用
groups 驱动自己的属性组 按需
pm dev_pm_ops 电源管理操作集 需要休眠支持时填
coredump 用户态写某个 sysfs 时触发，用于导出设备固件/崩溃转储 少见
p driver_private 核心填

owner 和 suppress_bind_attrs 两处细节：

owner 不填的后果很实际。驱动模块在 probe 执行期间被 rmmod，会导致跳到已经释放的代码段。THIS_MODULE 让核心在调用驱动方法期间临时递增模块引用计数，从根上堵住这个洞。

suppress_bind_attrs 是给「绑定关系由硬件决定、不允许用户态干预」的驱动用的。设成 true 后 /sys/bus/<bus>/drivers/<drv>/bind 和 unbind 就不生成，用户没法手写这两文件强制解绑。

查看效果：

bash
ls /sys/bus/platform/drivers/mydriver/
# 有 suppress_bind_attrs：driver  module  uevent
# 没有：driver  module  bind  unbind  uevent

6.2 probe 和 remove 的语义 #

原文用 PC 程序的 main 函数类比 probe，这个类比不太准。更贴切的说法是：

probe 是「设备到货时执行一次」，remove 是「设备撤走时执行一次」。 驱动代码本身就是一段被注册进去的回调集合，它没有「开始」和「结束」，只有「匹配上了」和「解绑了」。

这个区别决定了两件事：

  • probe 可能被调用多次：同一个驱动可以绑定多个设备实例，每个实例调用一次
  • probe 可能不被调用：没有任何设备匹配这个驱动时，probe 永远不执行

probe 的返回值有语义：

返回值 结果
0 绑定成功
-EPROBE_DEFER 资源未就绪，放进延迟队列稍后重试
其他负数 绑定失败，记录到 dmesg

-EPROBE_DEFER 用得很多。比如驱动要拿一个 clk，但提供这个 clk 的另一个驱动还没 probe：

c
clk = devm_clk_get(dev, "core");
if (IS_ERR(clk)) {
    if (PTR_ERR(clk) == -EPROBE_DEFER)
        return -EPROBE_DEFER;      /* 让核心稍后重试 */
    return PTR_ERR(clk);
}

注意 devm_ 系列会自动把 -EPROBE_DEFER 的语义保留下来，dev_err_probe() 这个辅助函数能一行搞定「打印或延迟」的逻辑：

c
clk = devm_clk_get(dev, "core");
if (IS_ERR(clk))
    return dev_err_probe(dev, PTR_ERR(clk), "failed to get clk\n");

6.3 匹配表怎么排 #

一个驱动可能有多个匹配路径，按顺序：

text
① of_match_table      设备树 compatible 匹配
② acpi_match_table    ACPI _HID 匹配
③ id_table            总线私有的 ID 表（i2c_device_id、spi_device_id…）
④ name                直接用 name 和 dev_name 比

具体顺序由总线的 match 回调决定，不是内核统一规定的。以 platform_bus_type 为例，它是先比 id_table / of_match_table，最后兜底比 name。i2c 总线则优先 of_match_table。

of_match_table 必须带哨兵项：

c
static const struct of_device_id my_of_match[] = {
    { .compatible = "vendor,my-device" },
    { /* sentinel */ }
};

漏了 { } 结尾，遍历时就会越界读 of_match_table 后面的内存，运气好是匹配失败，运气不好是随机崩溃。这个坑在新手里出现率极高。

七、四个结构体怎么串起来 #

把前面几章的信息拼成一张图。以「一个通过 i2c 连接的温湿度传感器，同时属于 hwmon 类」为例：

text
注册时：
  i2c_add_driver(&my_driver)
    └─ driver_register(&my_driver.driver)
         ├─ driver->bus = &i2c_bus_type          ← 挂到 i2c 总线
         ├─ bus->p->klist_drivers 加节点          ← 进驱动链表
         └─ driver_attach() 遍历该总线所有设备，调 bus->match

  i2c_new_device(adapter, &info)
    └─ device_register(&client->dev)
         ├─ dev->bus   = &i2c_bus_type
         ├─ dev->class = &hwmon_class（由驱动在 probe 里设）
         ├─ dev->release = i2c_client_dev_release
         └─ device_add()
              ├─ bus->p->klist_devices 加节点
              ├─ class->p->klist_devices 加节点
              ├─ /sys/devices/.../1-0048/ 目录建好
              ├─ /sys/bus/i2c/devices/1-0048 → 符号链接
              ├─ /sys/class/hwmon/hwmonX → 符号链接
              └─ bus_probe_device() → match 成功 → my_probe()

四条结论：

一、每个实体只有一个 struct device。 它在 sysfs 里有多个位置，但除 /sys/devices/ 之外全是链接。

二、bus 和 class 是两条独立索引。 同一个设备可以同时挂在两者下面，互不影响。

三、subsys_private 是 bus 和 class 共用的运行时容器。 链关系、锁、kset 都在里面，bus_type 和 class 本身保持「可静态初始化」的干净状态。

四、class_interface 是 class 侧的旁听机制。 设备进出类时通知订阅者，用于汇聚型子系统。

八、易错点速查 #

现象 原因 检查
Device 'xxx' does not have a release() function struct device 没填 release probe 里设 dev->release
驱动完全不 probe，dmesg 无任何报错 bus_type->match 返回值写反（匹配返回 0） match 返回正数表示匹配
of_match_table 匹配随机失败 漏了哨兵项 { } 表末尾加空项
/sys/class/xxx/ 下没有设备 dev->class 没设，或设得太晚 在 device_register 之前设
类销毁后访问崩溃 设备还引用着已 class_destroy 的 class 先销毁所有设备再销毁类
probe 里读不到 platform_data 板级数据没传，或设备树方案下本就没有 用 dev_get_platdata() 判 NULL
dev_get_drvdata() 返回 NULL 忘了 platform_set_drvdata() probe 开头设
内核报 needs updating - please use bus_type methods bus_type 和 driver 里同时填了 probe/remove 只保留 driver 侧的那份
引用计数泄漏 用 kfree(dev) 而不是 put_device(dev) 一切释放走 put_device
class_create(THIS_MODULE, "x") 编译报参数过多 6.4 起 owner 参数被删 新版写 class_create("x")
