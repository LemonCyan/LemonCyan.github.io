一、设备树要在启动链的哪个位置被用上 #

先把时间线拉出来。设备树不是内核的发明，它是「硬件描述从 C 代码里搬出去」的结果。搬出去以后，链路上多了一个交接点：谁生产这个二进制块，谁消费它。

text
BootROM → bootloader(uboot) → [dtb 在内存里] → kernel decompress → start_kernel
                                    ↑                  ↑
                              放在某个地址          boot_params / x0 / r2 传参

各阶段分工：

阶段 对设备树做了什么 交给下一棒
bootloader 从 flash / 分区 / 网络把 dtb 读到内存，按需做 fixup（改 bootargs、塞 memory 节点） dtb 的物理首地址
内核解压器 原样搬（arm 上会把 dtb 挪到解压输出之后，避免被覆盖） 地址不变，记录在 initial_boot_params
setup_arch setup_machine_fdt() 校验 magic、扫根节点 compatible 选 machine desc machine_desc
early_init_dt_scan_nodes 扫 /chosen 拿 bootargs、扫根节点拿 #address-cells / #size-cells、扫 memory 拿物理内存 boot_command_line、dt_root_addr_cells、meminfo
unflatten_device_tree 把扁平块摊成 device_node 树 of_root
of_platform_populate 树上的节点变成 platform_device 注册到 platform bus

一句话记住位置：dtb 在 start_kernel 之前就已经是内核眼里的唯一硬件事实来源，unflatten_device_tree 只是把它从字节流翻译成指针树。前者是格式问题，后者是数据结构问题，本篇两头都讲。

二、DTS / DTSI / DTB 三者的关系 #

三个后缀，一件事的三副面孔。

形态 后缀 谁读得懂 在哪
源文件 .dts 人 内核源码 arch/*/boot/dts/
被包含的源片段 .dtsi 人（dtc 的 C 预处理器） 同上，i = include
二进制块 .dtb bootloader、内核 flash 分区、boot 分区、/boot

dtsi 存在的理由很朴素：同一颗 SoC 上跑十几块板子，SoC 内部那些 controller 的地址、中断号完全一样，抄十几遍只会抄出十几份不一致的笔误。所以分三层：soc-common.dtsi 给全部用这颗 SoC 的板子共享，board-soc.dtsi 给同系列变种共享，board.dts 放这块板子独有的外设。dtc 自带精简版 C 预处理器，#include、#define、#ifdef 都能用，所以 .dts 里可以直接 #include <dt-bindings/gpio/gpio.h> 拿宏。

以 linux-3.14 的 arch/arm/boot/dts 为例（素材原文所用版本），分层长这样：

dts
/* skeleton.dtsi —— 最小骨架 */
/ {
	#address-cells = <1>;
	#size-cells = <1>;
	chosen { };
	aliases { };
	memory { device_type = "memory"; reg = <0 0>; };
};

dts
/* s3c24xx.dtsi —— SoC family 公共部分 */
#include "skeleton.dtsi"

/ {
	compatible = "samsung,s3c24xx";
	interrupt-parent = <&intc>;

	intc: interrupt-controller@4a000000 {
		compatible = "samsung,s3c2410-irq";
		reg = <0x4a000000 0x100>;
		interrupt-controller;
		#interrupt-cells = <4>;
	};
};

dts
/* s3c2416.dtsi —— 具体 SoC，覆盖 family 里不成立的部分 */
#include "s3c24xx.dtsi"

/ {
	model = "Samsung S3C2416 SoC";
	compatible = "samsung,s3c2416";

	interrupt-controller@4a000000 {
		compatible = "samsung,s3c2416-irq";
	};
};

两处细节，都是新手容易翻车的：

  1. 每个 .dtsi 都写了一遍 / { ... }，看着像「两个根节点」。dtc 会把同名节点合并，最终 dtb 里只有一个根。那个「第二个根」的说法是误解，源码里看到的只是同一路径的多次定义。
  2. s3c2416.dtsi 里重复定义了 compatible。反编译 dtb 只剩 samsung,s3c2416：后定义的覆盖先定义的。合并规则是「属性按名覆盖，子节点按名递归合并」，不是追加。

A.硬件与固件/05-设备树 对这套包含关系讲得更细，这里只当它理解后面编译流程的前提。

三、DTS 的基本语法：节点与属性 #

节点骨架只有这几样：

text
[label:] node-name[@unit-address] {
    [property = value;]
    [child node]
};

[] 表示可选。label 给源码内部引用用，不直接进 dtb 的字符串表（它演化成 phandle）。属性值五种形态：

写法 类型 例子 dtb 里的样子
"..." 字符串 status = "okay"; 6f 6b 61 79 00
".." , ".." 字符串列表 compatible = "arm,pl011", "arm,primecell"; 两个 NUL 结尾的串首尾相接
< ... > 32 位 cell 数组 reg = <0x101f1000 0x1000>; 大端 u32 原样序列
[ ... ] 裸字节 mac-address = [00 11 22 33 44 55]; 原样字节
只有名字 空属性（布尔） interrupt-controller; len = 0

cell 单独记住：1 cell = 32 bit。#address-cells = <2> 的意思是「我的子节点用 2 个 cell 描述地址，也就是 64 位」。# 读作 number，不是注释。尖括号里能混写引用，clocks = <&clk24m 0>; 里 &clk24m 被 dtc 换成 phandle 数值，0 是 clock specifier，含义由 #clock-cells 决定，编译后形如 <0x00000001 0x00000000>。

什么该写进设备树：能被动态探测的（USB device、PCI device）不写，探测不到的（SoC 上的 USB host controller、PCI bridge）必须写。它描述的是内核没法自己发现的东西，不是系统里所有的东西。

四、节点命名与 unit-address #

节点名合法字符集 [0-9a-zA-Z,._+-]，@ 只用来分隔 unit-address。

规则：

  • 有 reg 属性 → 名字必须是 node-name@unit-address
  • 没有 reg 属性 → 名字里不许出现 @
  • 同一个父节点下，node-name@unit-address 组合必须唯一；同名不同 unit-address 是合法的兄弟
  • 根节点的名字固定是 /

unit-address 的格式跟着总线走，不是固定长度：

节点 unit-address 取什么 reg 里几对
cpu@0 CPU 序号 1
memory@80000000 物理起始地址 1
serial@101f1000 寄存器基址 1
i2c@13860000 下的 eeprom@50 I2C 从机地址 1（父节点 #size-cells = <0>）

关键点：unit-address 只是名字的一部分，不参与地址解码，内核认地址看 reg。@ 后面写错而 reg 正确，硬件照样能工作，但你会得到两个名字不同的节点指向同一段寄存器，调试时够喝几壶。几位十六进制没有硬性规定，@0 还是 @00000000 都行，同一份 dts 里统一即可，dtc 的 -Wunit_address_format 会就此报警告。

五、标准属性：compatible、reg、interrupts、status #

这四个属性覆盖九成以上的节点。下面各节都是 ```dts 片段，不单独标注。

compatible #

字符串列表，从具体到通用，内核按顺序匹配，先命中的胜出。对普通设备节点它匹配驱动；对根节点它匹配 machine desc，也就是「这块板子是谁」，根节点还要配一个给人看的 model。

dts
/*
 * 列表形式：compatible = "vendor,device", "vendor,family";
 * 根节点用法：
 */
/ {
	model = "Snail S3C2416 Board";
	compatible = "snail,s3c2416", "samsung,s3c2416";
};

匹配是逗号前的厂商部分逐字符比，逗号后的部分允许通配后缀，不是全文相等，这是 of_device_is_compatible 的行为。

reg #

语法是 reg = <base size base size ...>;。值是一组 (address, size) 对，每对里 address 占几个 cell、size 占几个 cell，由父节点的 #address-cells 和 #size-cells 决定。这一点反直觉但必须记住：reg 的解析规则在父亲身上。

#address-cells = <1>、#size-cells = <1> 时：

dts
reg = <0x101f1000 0x1000>;                /* 一对：base=0x101f1000, size=0x1000 */
reg = <0x0 0x100 0x1000 0x200>;           /* 两对 */

64 位系统，根节点 #address-cells = <2>、#size-cells = <2>，描述 0x0/2GB 与 0x100000000/4GB 两段内存，两种写法内核都认：

dts
/* 方法 1：一个节点，reg 里放两对 */
memory@0 {
	device_type = "memory";
	reg = <0x00000000 0x00000000 0x00000000 0x80000000
	       0x00000001 0x00000000 0x00000001 0x00000000>;
};

/* 方法 2：两个节点，各一对 */
memory@0 {
	device_type = "memory";
	reg = <0x00000000 0x00000000 0x00000000 0x80000000>;
};

memory@100000000 {
	device_type = "memory";
	reg = <0x00000001 0x00000000 0x00000001 0x00000000>;
};

early_init_dt_scan_memory 会遍历所有 device_type = "memory" 的节点。方法 1 紧凑，方法 2 便于单独把某一段 status = "disabled" 掉。

interrupts #

dts
interrupts = <12>;                       /* 1 cell 的 specifier */
interrupts = <1 0 4 28>, <1 1 4 28>;     /* 4 cell 的 specifier，两个中断 */

每个中断占几个 cell 由中断控制器的 #interrupt-cells 决定。S3C24xx 用 4 个 cell，具体每一位的含义的解释权在中断控制器驱动手里，不在设备树规范里。属性名是复数 interrupts，单数 interrupt 是老写法，别用。

status #

取值有明确语义：

值 含义
"okay" / "ok" 可用
"disabled" 存在但不可用，驱动不该 probe
"reserved" 可用，但不该被这个 OS 使用（留给协处理器等）
"fail" / "fail-sss" 探测到严重错误，不启动

of_platform_populate 那一层会跳过非 okay 的节点，不给它生成 platform_device。这一点在第十八章会再看到。

六、phandle 与中断、时钟的引用方式 #

节点之间要互相指——串口的时钟源是哪个、网卡的中断接到哪个控制器——写完整路径太难读，于是有了 label 和引用。

dts
uart0: serial@101f1000 {
	clocks = <&clk24m>;
};

clk24m: clock@10000000 {
	#clock-cells = <0>;
};

dtc 给每个被引用的节点分配一个全局唯一的 u32 编号，写进该节点的 phandle 属性，再把所有 <&clk24m> 换成这个数字：

dts
clock@10000000 {
	...
	phandle = <0x00000001>;
};

serial@101f1000 {
	...
	clocks = <0x00000001>;
};

反编译 dtb 就能验这个等价。老版本 dtc 会同时吐 linux,phandle 和 phandle：前者是内核私有时代的老名字，后者是 ePAPR / Devicetree Specification 转正后的名字。现在只要 phandle，留 linux,phandle 是为了兼容老 dtb。两个都在且值不同，内核行为按版本而异，别造这种 dtb。

引用属性必须分清：

属性 位置 指向什么 解释者
interrupt-parent 能出中断的节点 中断控制器节点 中断子系统
interrupts 设备节点 中断号等 specifier 上一条指向的控制器
interrupts-extended 设备节点 <&intc spec...> 成对出现，自带父指针 中断子系统
clocks + clock-names 设备节点 时钟源节点 + 序号 时钟框架
gpios / *-gpios 设备节点 GPIO 控制器 + 线号 + flag gpiolib

interrupt-parent 的继承规则是子节点没写就顺着父节点向上找，所以 s3c24xx.dtsi 只在根节点写一次，下面所有设备自动继承。你在根节点看到这个属性别觉得奇怪，它不是根节点要出中断。控制器级联时，没写 interrupt-parent 的那个控制器就是根，of_irq_init 靠「找不到 parent」定位它。interrupt nexus（需要 interrupt-map 做 domain 翻译，PCI 是典型）属于中断子系统，本篇不展开。

aliases 是另一条引用路线：

dts
aliases {
	serial0 = &uart0;
};

这里的值不是 phandle，而是完整路径字符串。编进 dtb 后是 "/serial@101f1000"，带引号带 NUL，占 strlen + 1 字节，再按 4 字节对齐补零。of_alias_scan 会把这些别名缓存成 device_node 指针，of_find_node_by_alias 直接查。

一个 phandle 相关的坑：0xffffffff 是保留值，不能分配给任何节点，它表示「无引用」。0 也不该用，device_node->phandle == 0 在内核里表示「这个节点没有 phandle」。

七、编译：dtc 怎么把 dts 编成 dtb #

dtc 源码在内核树 scripts/dtc/，双向转。

bash
sudo apt-get install device-tree-compiler

dtc -I dts -O dtb -o board.dtb board.dts     # dts → dtb
dtc -I dtb -O dts -o board.dts board.dtb     # dtb → dts，调试主力
dtc -I dts -O dtb -o /dev/null board.dts     # 只做语法检查
dtc -I fs  -O dts /proc/device-tree          # 直接读运行中的树
dtc --version

-I 输入格式，-O 输出格式，取值 dts、dtb、fs（/proc/device-tree 那种目录树形态）。不写 -I 时 dtc 自己嗅探。内核构建里不直接调 dtc，Makefile.lib 把 %.dts → %.dtb 串起来，中间产物是 %.dtb.d.dtc.tmp 之类：

bash
make ARCH=arm dtbs
make ARCH=arm s3c2416-snail.dtb        # 单块板

常用选项：

选项 作用
-@ 生成 __symbols__ 节点，供运行时 overlay（/plugin/）用
-H epapr / -H both 头部格式，epapr 就是现在的标准 fdt header
-p <n> structure block 里塞 n 字节 padding
-R <n> 预留 n 字节空余，给 uboot fixup 用
-s 排序，输出可复现
-W<warning> / -Wno-<warning> 开关告警，-Wno-unit_address_vs_reg 最常关

dtc 会补上 memreserve 里预留的空间和 -R 的空余，那些零就是这么来的。想看原始结构用 fdtdump，它不做解析，直接把头部和结构打出来：

bash
fdtdump board.dtb
fdtdump -sd board.dtb > board.txt   # -s 扫描内嵌 fdt，-d 打调试信息

用法输出：

text

八、DTB 的整体布局：四个区块 #

dtb 就是一段连续内存，分四个区：

区块 偏移来源 长度来源 内容
header 固定 0x00 固定 0x28（v17） 10 个 u32
memory reservation block off_mem_rsvmap 变长，靠零项结束 (addr, size) u64 对
structure block off_dt_struct size_dt_struct token 流
strings block off_dt_strings size_dt_strings 属性名池，NUL 分隔 
text
offset 0x00  ┌──────────────────────────────┐
             │  fdt_header   (40 字节)       │  magic / totalsize / 四个偏移 / 版本
offset 0x28  ├──────────────────────────────┤
             │  memory reservation block     │  (u64 addr, u64 size) × n，全零项收尾
             ├──────────────────────────────┤
off_dt_struct├──────────────────────────────┤
             │  structure block              │  FDT_BEGIN_NODE / FDT_PROP / FDT_END_NODE / FDT_END
             ├──────────────────────────────┤
off_dt_strings├─────────────────────────────┤
             │  strings block                │  "compatible\0reg\0status\0..."
total ───────└──────────────────────────────┘

三条硬约束，写解析器时会一条一条撞上：

  1. totalsize 是整个块的长度，含末尾 padding。
  2. 三个偏移都是相对 dtb 起始地址的，绝对地址 = dtb 基址 + 偏移，不是相对上一个区块。
  3. off_dt_struct 和 off_mem_rsvmap 要 4 字节对齐，off_dt_strings 跟着前面的区块自然对齐。四个区块的物理顺序没有强制，偏移字段说了算，解析器不能假设「header → rsvmap → struct → strings」永远成立。

素材原文把这四区叫 header、fill_area、dt_struct、dt_string。fill_area 不是独立的语义区块，它就是 off_dt_struct - sizeof(struct fdt_header) 那段零——也就是 memory reservation block 加对齐余量。这个命名混淆点记在附录。

九、header 区逐字节解析 #

内核里描述它的是 struct fdt_header，定义在 scripts/dtc/libfdt/fdt.h：

c
struct fdt_header {
	fdt32_t magic;               /* magic word FDT_MAGIC */
	fdt32_t totalsize;           /* total size of DT block */
	fdt32_t off_dt_struct;       /* offset to structure */
	fdt32_t off_dt_strings;      /* offset to strings */
	fdt32_t off_mem_rsvmap;      /* offset to memory reserve map */
	fdt32_t version;             /* format version */
	fdt32_t last_comp_version;   /* last compatible version */

	/* version 2 fields below */
	fdt32_t boot_cpuid_phys;     /* Which physical CPU id we're booting on */
	/* version 3 fields below */
	fdt32_t size_dt_strings;     /* size of the strings block */

	/* version 17 fields below */
	fdt32_t size_dt_struct;      /* size of the structure block */
};

10 个 u32，全部大端存放：

偏移 字段 含义 起始版本
0x00 magic 固定 0xd00dfeed v1
0x04 totalsize 整块长度，含尾部 padding v1
0x08 off_dt_struct structure block 偏移 v1
0x0c off_dt_strings strings block 偏移 v1
0x10 off_mem_rsvmap memory reservation block 偏移 v1
0x14 version 格式版本，当前 17 v1
0x18 last_comp_version 向后兼容的最低版本，v17 写 16 v1
0x1c boot_cpuid_phys 启动 CPU 物理 ID，SMP bring-up 用 v2
0x20 size_dt_strings strings block 长度 v3
0x24 size_dt_struct structure block 长度 v17

版本演进：v1 定 header 骨架，v2 加 boot_cpuid_phys，v3 加 size_dt_strings，v16 把节点名从完整路径改成单段名字并改掉 boot_cpuid_phys 的语义，v17 加 size_dt_struct。写解析器前先读 version 定 header 长度，老 dtb 的 header 只有 28 字节或更短，硬读 0x28 会踩到后面的数据。

magic 的字节序是最常被问的点：文件开头 d0 0d fe ed，按大端读是 0xd00dfeed。十六进制编辑器里看到 ed fe 0d d0，那是有人按小端存的，内核直接 -EINVAL。

fdtdump 打出的头部和这张表一一对应：

text
// magic:  0xd00dfeed
// totalsize:  0xce4 (3300)
// off_dt_struct: 0x38
// off_dt_strings: 0xc34
// off_mem_rsvmap: 0x28
// version: 17

十、memory reservation block #

这块回答一个问题：dtb 之外，还有哪些内存是运行时不能碰的。

格式极简：一串 (address, size) u64 对，一个全零项收尾。没有长度字段也没有条目数，size_dt_rsvmap 这种东西不存在，解析器只能一项一项往下读，撞上全零为止。

c
struct fdt_reserve_entry {
	fdt64_t address;
	fdt64_t size;
};

源文件里对应 /memreserve/ 语句，/memreserve/ 0x80000000 0x0000000000004000; 编出来是：

text
00 00 00 00 80 00 00 00   00 00 00 00 00 00 40 00   ← addr=0x80000000, size=0x4000
00 00 00 00 00 00 00 00   00 00 00 00 00 00 00 00   ← 结束标记

场景很具体：bootloader 在 0x80000000 放了自己的数据或一块共享缓冲区，内核要保证不给这段地址分配页。写进 memreserve，early_init_dt_reserve_memory_arch 就会在 buddy 初始化之前把它 reserve 掉。

address 是物理地址，size 是字节数，不是结束地址，写成 (start, end) 会多保留出一大段。dtc 自己还会塞一条 (dtb 物理地址, dtb 大小) 进去，所以反编译普通 dtb 时常看到一条不认识的 memreserve，那是工具加的。

十一、structure block：节点与属性的紧凑编码 #

dtb 的心脏。整个区块是一串 token + 数据 的流，没有长度前缀、没有索引，只能从前往后顺次读。五种 token 全是 32 位大端整数：

c
#define FDT_BEGIN_NODE  0x1    /* Start node: full name */
#define FDT_END_NODE    0x2    /* End node */
#define FDT_PROP        0x3    /* Property: name off, size, content */
#define FDT_NOP         0x4    /* nop */
#define FDT_END         0x9
token 值 后面跟什么 对齐
FDT_BEGIN_NODE 0x00000001 节点名（UTF-8 + \0），根节点空串 名字后补零到 4
FDT_END_NODE 0x00000002 无 —
FDT_PROP 0x00000003 u32 len + u32 nameoff + len 字节值 值后补零到 4
FDT_NOP 0x00000004 无，解析器跳过 —
FDT_END 0x00000009 无，整块结束 —

一个节点的编码顺序固定：

text
FDT_BEGIN_NODE
  name + '\0' + padding
  FDT_PROP, len, nameoff, value + padding    ← 属性，0..n 个
  FDT_BEGIN_NODE ... FDT_END_NODE            ← 子节点，0..n 个
FDT_END_NODE

FDT_NOP 是给 fixup 用的。uboot 或者 overlay 想删一个属性，不用搬动后面所有字节，把那个 FDT_PROP 的 tag 改成 FDT_NOP 就完事，长度不变，偏移全不变。新增属性靠 -R 预留的尾部空余加 FDT_NOP 复用。.dtbo overlay 能在 bootloader 里原地做而不重新编译，根子就在这儿。

一个反直觉的细节：根节点也有自己的 FDT_BEGIN_NODE / FDT_END_NODE，而且根节点的名字是空字符串（只有一个 \0 加 3 字节 padding），不是 "/"。v16 改格式之后就一直是这样，更早的格式里根节点名字是完整路径。素材里 unflatten_dt_node 的注释说得很清楚：

c
/* version 0x10 has a more compact unit name here instead of the full
 * path. we accumulate the full path size using "fpsize", we'll rebuild
 * it later. We detect this because the first character of the name is
 * not '/'.
 */
if ((*pathp) != '/') {
	new_format = 1;
	...
}

这段检测是为兼容老 dtb 留的：新格式下名字第一个字符不会是 /（根节点是空串，其他节点名不带前导斜杠），老格式下名字是 /xxx/yyy 这样的完整路径。一个字符分辨两代格式。

读 structure block 的伪代码就这几行：

c
off = off_dt_struct;
while (off < off_dt_struct + size_dt_struct) {
	tag = be32_to_cpu(*(u32 *)(base + off));
	off += 4;
	switch (tag) {
	case FDT_BEGIN_NODE:  /* 读名字，对齐，压栈 */ break;
	case FDT_END_NODE:    /* 弹栈 */ break;
	case FDT_PROP:        /* 读 len/nameoff/value，对齐 */ break;
	case FDT_NOP:         break;
	case FDT_END:         /* 结束 */ break;
	}
}

内核不这么写，它用的是 libfdt 封装的 fdt_next_node / fdt_first_property_offset，逻辑一样。

十二、节点起始与结束标记 FDT_BEGIN_NODE / FDT_END_NODE #

三个名字长度不同的例子：

text
00 00 00 01                          ← FDT_BEGIN_NODE
00                                   ← 空名字（根节点）
00 00 00                             ← 3 字节 padding

00 00 00 01                          ← FDT_BEGIN_NODE
63 68 6f 73 65 6e 00                 ← "chosen"，7 字节
00                                   ← 1 字节 padding

00 00 00 01                          ← FDT_BEGIN_NODE
73 65 72 69 61 6c 40 31 30 31 66 31 30 30 30   ← "serial@101f1000"，15 字节
00                                   ← NUL，正好凑到 16，无 padding

对齐规则一句话：sizeof(u32) + strlen(name) + 1 向上取整到 4 的倍数，名字长度含结尾 NUL。内核里的结构体：

c
struct fdt_node_header {
	fdt32_t tag;
	char name[0];
};

name 是柔性数组，指向 tag 后面紧跟的名字首字节，名字后面那段 padding 不属于结构体，是外部对齐。FDT_END_NODE 没有负载，就 4 个字节 00 00 00 02。树形全靠这两个 token 的嵌套表达，不需要记录子节点数：

text
BEGIN_NODE ""                     ← 根
  PROP #address-cells
  PROP #size-cells
  BEGIN_NODE "interrupt-controller@10140000"
    PROP compatible
    PROP reg
    PROP interrupt-controller
    PROP #interrupt-cells
    PROP phandle
  END_NODE
  BEGIN_NODE "chosen"
    PROP bootargs
  END_NODE
END_NODE                          ← 根结束
END                               ← 整块结束

FDT_END 是最后一个 token，占 4 字节，所以 off_dt_struct + size_dt_struct 等于 FDT_END 起始偏移加 4。第十五章的算术能对上。

十三、属性编码 FDT_PROP 与它的对齐规则 #

FDT_PROP 是唯一带负载的 token，也是最容易写错对齐的地方。

c
struct fdt_property {
	fdt32_t tag;
	fdt32_t len;
	fdt32_t nameoff;
	char data[0];
};
字段 偏移（相对 tag） 含义
tag +0x00 固定 0x00000003
len +0x04 属性值字节数，不含对齐 padding
nameoff +0x08 属性名在 strings block 里的偏移，相对于 off_dt_strings
data +0x0c len 字节的值

nameoff 是相对偏移，拿到属性名得算 base + off_dt_strings + nameoff，素材原文写的就是这个关系。

len 的语义有两条要钉死：它是值本身的字节数，不含 padding，按 len 取值不会把补的零读进来；对字符串属性它还包含结尾的 NUL，status = "okay"; 的 len 是 5 不是 4，字符串列表包含每一个 NUL。

拿素材例子验：compatible = "samsung,goni", "samsung,s5pv210"; 两个串长度 12 和 16，各带一个 NUL，总 len = 12 + 1 + 16 + 1 = 30。素材原文写 29，只算了一个 NUL。照 29 截断，第二段字符串少掉最后一个字符，附录记了这一笔。

对齐规则：data 从 tag 算起偏移 0x0c，之后补零到 4 字节边界。下一个 token 的偏移 = 当前 FDT_PROP 起始偏移 + 0x0c + ALIGN(len, 4)。

拿第十五章 dump 里 len = 10 的 compatible 验：起始 0x00a8，data 起点 0x00b4，下一个 token 在 0x00b4 + ALIGN(10,4) = 0x00c0，dump 里 0x00c0 确实是下一个 FDT_PROP 的 tag。

空属性 len = 0，data 一个字节都不占，下一个 token 紧接在 nameoff 之后：

text
00 00 00 03        ← FDT_PROP
00 00 00 00        ← len = 0
00 00 00 2c        ← nameoff = 0x2c，指向 "interrupt-controller"
                   ← 没有 data，没有 padding

interrupt-controller; 就这么存，只占 12 字节。

十四、strings block 与属性名的去重 #

属性名在 structure block 里只存偏移，真字符串全在 strings block。原因很简单：compatible 出现在几十个节点里，reg 几乎每个有地址的节点都有，每个存一份纯属浪费。格式：一串以 NUL 结尾的字符串首尾相接，没有数量字段，没有索引表。

text
23 61 64 64 72 65 73 73 2d 63 65 6c 6c 73 00   "#address-cells\0"   ← 偏移 0x00
23 73 69 7a 65 2d 63 65 6c 6c 73 00            "#size-cells\0"      ← 偏移 0x0f
6d 6f 64 65 6c 00                              "model\0"            ← 偏移 0x1b
63 6f 6d 70 61 74 69 62 6c 65 00               "compatible\0"       ← 偏移 0x21

取属性名只能从 off_dt_strings + nameoff 开始读到下一个 \0。没有长度表，读到空串就是坏了。

dtc 的策略是全块共享一张表，同一个属性名只存一次。compatible 在 structure block 里出现 3 次，字符串表里只有 1 份，第十五章 dump 里它的 nameoff 三次都是 0x21。后果是属性名按首次出现顺序排列，后面复用；同一个 dts 换个属性书写顺序，strings block 的字节会变但语义不变，这也是 dtc -s 能让输出可复现的原因。

反方向：节点名不在 strings block 里，它直接在 FDT_BEGIN_NODE 后面内联存。每个节点名在树里只出现一次，没有去重的必要。

size_dt_strings 是 v3 之后才有的字段，比这更老的 dtb 得靠 totalsize - off_dt_strings 推长度。

十六、内核怎么读 dtb：unflatten_device_tree #

格式讲完，换到内核侧。入口 unflatten_device_tree()，在 drivers/of/fdt.c：

c
void __init unflatten_device_tree(void)
{
	__unflatten_device_tree(initial_boot_params, &of_root,
				early_init_dt_alloc_memory_arch);

	/* Get pointer to "/chosen" and "/aliases" nodes for use everywhere */
	of_alias_scan(early_init_dt_alloc_memory_arch);
}

initial_boot_params 是 dtb 的虚拟首地址，由 setup_machine_fdt() 从启动参数取出并校验 magic；of_root 是全局根指针；early_init_dt_alloc_memory_arch 是分配器回调，早期只能走 memblock。

__unflatten_device_tree 的关键是两次遍历：

c
static void __unflatten_device_tree(const void *blob,
			     struct device_node **mynodes,
			     void * (*dt_alloc)(u64 size, u64 align))
{
	unsigned long size;
	int start;
	void *mem;

	/* First pass, scan for size */
	start = 0;
	size = (unsigned long)unflatten_dt_node(blob, NULL, &start, NULL, NULL, 0, true);
	size = ALIGN(size, 4);

	/* Allocate memory for the expanded device tree */
	mem = dt_alloc(size + 4, __alignof__(struct device_node));
	memset(mem, 0, size);

	/* Second pass, do actual unflattening */
	start = 0;
	unflatten_dt_node(blob, mem, &start, NULL, mynodes, 0, false);
}

两遍的原因：device_node 和 property 变长（full_name 紧跟在结构体后面），事先不知道总数。第一遍 dryrun = true 只算大小，第二遍才真分配真填。boot 阶段没别的办法，代价是解析逻辑走两遍。

unflatten_dt_node 流程：

text
1. pathp = fdt_get_name(blob, *poffset, &l)                取出本节点名字
2. 名字首字符是不是 '/'                                    新格式 / 老格式
3. np = unflatten_dt_alloc(sizeof(device_node) + allocl)    连 full_name 一起分配
4. of_node_init(np)                                        初始化 kobject
5. np->full_name = (char *)np + sizeof(*np)                柔性尾巴放全路径
6. np->parent = dad; np->sibling = dad->child; dad->child = np
7. 遍历本节点所有属性，逐个 unflatten_dt_alloc(sizeof(property))
8. 顺带抓 phandle：phandle / linux,phandle / ibm,phandle
9. 没有 name 属性就用 unit-name 造一个
10. np->name / np->type 分别取 name / device_type 属性
11. 递归处理子节点，靠 depth 变化判断边界
12. 反转 child 链表，恢复 dts 书写顺序

几个值得停下来的点。

full_name 是内存布局的一部分。它不是单独 kmalloc 的，而是指向 struct device_node 后面紧跟的那段空间，allocl 就是那段长度。unflatten_dt_alloc 是「一次分配，结构体加字符串连成一块」，所以 kfree(np) 就够。新老格式的判断只有一个字符：v16 之后节点名是单段名字要重建全路径，v16 之前名字本身就是全路径。

c
if ((*pathp) != '/') {
	new_format = 1;
	if (fpsize == 0) {
		/* root node: special case. ... */
		fpsize = 1;
		allocl = 2;
		l = 1;
		pathp = "";
	} else {
		fpsize += l;
		allocl = fpsize;
	}
}

根节点特殊处理成 fpsize = 1、allocl = 2，因为根的全路径就是 /，占两个字节（/ 加 NUL）。其他节点的 full_name 由父节点的 full_name 加 / 加自己的名字拼出来：

c
if (new_format) {
	/* rebuild full path for new format */
	if (dad && dad->parent) {
		strcpy(fn, dad->full_name);
		fn += strlen(fn);
	}
	*(fn++) = '/';
}
memcpy(fn, pathp, l);

dad && dad->parent 是给「根的直接子节点」留的：父节点是根，dad->parent == NULL，dad->full_name 已经是 /，再拷一遍就成 //serial@... 了。

phandle 三种名字都要认：

    (strcmp(pname, "linux,phandle") == 0)) {
	if (np->phandle == 0)
		np->phandle = be32_to_cpup(p);

	np->phandle = be32_to_cpup(p);

ibm,phandle 是 pSeries 动态设备树用的，优先级最高，直接覆盖。前两个先到先得，np->phandle == 0 才写。

name 属性是造出来的。上游 dts 一般不写 name，内核需要它。遍历下来没有就按「最后一个 / 之后、@ 之前」切一个出来：

	const char *p1 = pathp, *ps = pathp, *pa = NULL;
	int sz;

/serial@e2900800 切出来是 serial，长度 7（含 NUL）。这个 name 属性在内核里有实体，所以 /proc/device-tree/serial@e2900800/ 下面能看到一个 name 文件。

child 链表倒着接再翻回来。挂接时 np->sibling = dad->child; dad->child = np; 是头插，结果是逆序，所以末尾有一段反转：

c
if (!dryrun && np->child) {
	struct device_node *child = np->child;
	np->child = NULL;
	while (child) {
		struct device_node *next = child->sibling;
		child->sibling = np->child;
		np->child = child;
		child = next;
	}
}

注释写得很直白：「Some drivers assumes node order matches .dts node order」。有驱动依赖 dts 书写顺序，必须翻回来。

递归边界靠 depth：fdt_next_node 遇到 FDT_BEGIN_NODE 给 depth 加一，遇到 FDT_END_NODE 减一。深度比进入时大，说明后面还有自己的子节点；回到进入时的值，自己的子树处理完了。

c
old_depth = depth;
*poffset = fdt_next_node(blob, *poffset, &depth);
if (depth < 0)
	depth = 0;
while (*poffset > 0 && depth > old_depth)
	mem = unflatten_dt_node(blob, mem, poffset, np, NULL,
				fpsize, dryrun);

版本标注：这段带 fpsize / dryrun / 手写 device_node 分配的写法，对应大约 3.14 ~ 4.x 早期。5.x 之后这块重构过：分配改成内存池 + struct device_node 加了 fwnode_handle，fpsize 从 unsigned long 变成 unsigned long *，两遍遍历的思路保留。要读新代码，git log --oneline drivers/of/fdt.c 追 unflatten_dt_node。素材原文基于 3.14，这一段的实现到 4.x 之后已不适用。

十七、device_node：dtb 在内核里的对应物 #

dtb 的字节流到了内核里变成三样东西：device_node 树、每个节点下的 property 单链表、节点尾部的路径字符串。

c
struct device_node {
	const char *name;              /* node 名称，取最后一个 "/" 和 "@" 之间的子串 */
	const char *type;              /* device_type 属性值，没有则为 <NULL> */
	phandle phandle;               /* phandle 属性值 */
	const char *full_name;         /* 指向结构体结束处，存放节点全路径，如 /chosen */
	struct fwnode_handle fwnode;

	struct property *properties;   /* 本节点第一个属性 */
	struct property *deadprops;    /* removed properties */
	struct device_node *parent;    /* 父节点 */
	struct device_node *child;     /* 第一个子节点 */
	struct device_node *sibling;   /* 同级下一个节点 */
	struct kobject kobj;           /* 对应 sysfs 目录 */
	unsigned long _flags;          /* 状态标志 */
	void *data;
};

字段对照 dtb：

字段 来自 dtb 的哪里 怎么来的
name name 属性（多数由内核合成） 最后一个 / 后、@ 前
type device_type 属性 of_get_property 读
phandle phandle / linux,phandle / ibm,phandle 遍历属性时顺手抓
full_name FDT_BEGIN_NODE 的名字 + 父节点路径 解析时重建
properties 本节点全部 FDT_PROP 按出现顺序串成单链表
parent / child / sibling FDT_BEGIN_NODE / FDT_END_NODE 的嵌套 解析时挂接，child 最后反转回原序
kobj 无 运行时建 sysfs
_flags 无 运行时状态
fwnode 无 ACPI / DT 统一抽象层，后期内核才有

property 结构：

c
struct property {
	char *name;                        /* property full name */
	int length;                        /* property value length */
	void *value;                       /* property value */
	struct property *next;             /* next property under the same node */
	unsigned long _flags;
	unsigned int unique_id;
	struct bin_attribute attr;         /* 属性文件，与 sysfs 挂接 */
};

对照关系：

dtb 里的 struct property 里
strings block 里那段 "compatible\0" name（直接指过去，不拷贝）
FDT_PROP 的 len length
FDT_PROP 的 data value（直接指过去，不拷贝）
下一个 FDT_PROP next

两个「不拷贝」是关键：pp->name = (char *)pname; 和 pp->value = (__be32 *)p; 都直接指向 dtb 里的原始位置。前提是 dtb 内存不能释放、不能覆盖，这就是 early_init_dt_reserve_memory_arch 要 reserve dtb 本身的原因。

_flags 状态位：

c
#define OF_DYNAMIC        1 /* node and properties were allocated via kmalloc */
#define OF_DETACHED       2 /* node has been detached from the device tree */
#define OF_POPULATED      3 /* device already created for the node */
#define OF_POPULATED_BUS  4 /* of_platform_populate recursed to children */

后两个是防止重复创建 platform_device 的闸门，第十八章用到。

内存布局：节点和属性各是一块，节点那块把 full_name 塞在自己的尾巴上：

text
┌──────────────────────────┐      ┌──────────────────────────┐
│ struct device_node      │      │ struct property          │
├──────────────────────────┤      ├──────────────────────────┤
│ full_name 字符串（含 NUL）│      │ 合成的 name 属性值副本    │
└──────────────────────────┘      └──────────────────────────┘

所以 unflatten_dt_alloc(&mem, sizeof(struct property) + sz, ...) 才有那个 + sz，普通属性只有 sizeof(struct property)。

十八、从 device_node 到 platform_device #

树建好了，接下来让驱动能找到设备。ARM 上的入口是 customize_machine()（arch/arm/kernel/setup.c），最终调到 of_platform_populate()：它从根节点开始，对每个子节点调 of_platform_bus_create()，完了给根节点打上 OF_POPULATED_BUS。

c
int of_platform_populate(struct device_node *root,
			const struct of_device_id *matches,
			const struct of_dev_auxdata *lookup,
			struct device *parent)
{
	struct device_node *child;
	int rc = 0;

	root = root ? of_node_get(root) : of_find_node_by_path("/");
	if (!root)
		return -EINVAL;

	for_each_child_of_node(root, child) {
		rc = of_platform_bus_create(child, matches, lookup, parent, true);
		if (rc) {
			of_node_put(child);
			break;
		}
	}
	of_node_set_flag(root, OF_POPULATED_BUS);

	of_node_put(root);
	return rc;
}

真正的判断在 of_platform_bus_create()：

c
static int of_platform_bus_create(struct device_node *bus,
				  const struct of_device_id *matches,
				  struct of_dev_auxdata *lookup,
				  struct device *parent, bool strict)
{
	...
	/* Make sure it has a compatible property */
	if (strict && (!of_get_property(bus, "compatible", NULL))) {
		return 0;
	}
	...
	dev = of_platform_device_create_pdata(bus, bus_id, platform_data, parent);
	if (!dev || !of_match_node(matches, bus))
		return 0;

	for_each_child_of_node(bus, child) {
		rc = of_platform_bus_create(child, matches, lookup, &dev->dev, strict);
		if (rc) {
			of_node_put(child);
			break;
		}
	}
	of_node_set_flag(bus, OF_POPULATED_BUS);
	return rc;
}

三条规则：

  1. 没有 compatible 的节点直接跳过，不生成 platform_device（strict = true 时生效）。
  2. status 不是 okay / ok 或干脆没写的节点，of_platform_device_create_pdata 内部会判，disabled 的不建。
  3. 只有 compatible 命中 of_default_bus_match_table 的节点才递归，把子节点也变成 platform_device，否则到此为止。

递归的判据在 of_default_bus_match_table 里，三样：simple-bus、simple-mfd、arm,amba-bus（后两个按配置和版本取舍）。总线节点的语义是「这里面都是内存映射设备，没有自己的探测机制，把子节点直接当 platform device 注册」，所以 dts 里爱写 simple-bus：

dts
soc {
	compatible = "simple-bus";
	#address-cells = <1>;
	#size-cells = <1>;
	ranges;
	...
};

字段搬运：

platform_device 来源
.name of_node->name 或 compatible 的 model 部分
.dev.of_node 直接指回 of_node
.dev.parent 父节点的 device
.resource[] reg 翻译来的（of_address_to_resource）
.num_resources reg 里 (addr, size) 对的个数
.id of_alias_get_id 的序号，拿不到用 -1

.dev.of_node 是绑定的关键：驱动 probe 拿到的 pdev->dev.of_node 能反查整个 dts 子树，of_property_read_u32() 这些接口全靠它。&pdev->dev 里的 device 拥有一整个 kobject，在 sysfs 落成 /sys/devices/platform/<name>/；设备树节点本身另有一份 /sys/firmware/devicetree/base/...。两份目录指向同一份数据，一个是设备视角，一个是原始描述视角，kobject 与 sysfs：设备模型的底座 讲的就是这条链的另一头。

I2C 支线略有不同：i2c adapter 自己是 platform device，probe 里注册 adapter，of_i2c_register_devices() 遍历子节点，给每个非 disabled 的造一个 i2c_client，名字取 compatible 逗号后的部分。compatible = "maxim,ds1338" 得到 i2c_client->name = "ds1338"，和 platform device 那边的命名规则不一样，别混。

bash
dmesg | grep -i -E 'OF:|fdt|device tree'

OF: fdt: Machine model: ... 这行由 setup_machine_fdt() 打出，出现它就说明 magic 校验过了、根节点的 model 和 compatible 读到了。没有这行，问题在 bootloader 或 dtb 本身。

20.2 /proc/device-tree 与 sysfs #

bash
ls /proc/device-tree/
ls /sys/firmware/devicetree/base/

两个入口同一份数据，结构完全对应 dts：

text
/sys/firmware/devicetree/base/
├── #address-cells          ← 二进制文件，4 字节
├── compatible              ← 文本，末尾带 NUL
├── model
├── chosen/bootargs
├── serial@101f1000/
│   ├── compatible / reg / status
│   └── name                ← 内核造的那个
└── ...

节点是目录，属性是文件，文件类型 bin_attribute，就是 struct property 里那个 attr 字段。of_core_init() 建的，调用链：

text
start_kernel() → rest_init() → kernel_init() → do_basic_setup()
  → driver_init() → of_core_init()

读法有讲究，因为它们是二进制：

bash
cat /proc/device-tree/model; echo                      # 字符串属性
hexdump -C /proc/device-tree/serial@101f1000/reg       # cell 属性
dtc -I fs -O dts /proc/device-tree                     # 整棵树转回 dts

dtc -I fs 把 /proc/device-tree 目录树当输入格式，直接出可读 dts。排查「内核看到的树和我编的不一样」，这一步最直接。

20.3 从设备侧反查 #

bash
ls /sys/bus/platform/devices/            # 有哪些 platform device
ls /sys/bus/platform/drivers/            # 有哪些驱动，谁绑上了谁
ls -l /sys/devices/platform/*/driver     # 软链接指向已绑定驱动
ls /sys/firmware/devicetree/base/soc/    # 原始描述

两份列表对着看，差集就是「dts 里有但没建成设备」的节点，八成是 status 或 compatible 的问题。

20.4 反编译与对比 #

bash
dtc -I dtb -O dts -o /tmp/running.dts /sys/firmware/fdt
dtc -I dtb -O dts -o /tmp/source.dts arch/arm/boot/dts/board.dtb
diff -u /tmp/source.dts /tmp/running.dts

/sys/firmware/fdt 是内核留的原始 dtb 副本，可读。这份 diff 直接暴露 bootloader fixup 干了什么——改 bootargs、删 memory 节点、加 linux,initrd-start，全在里面。

20.5 早期启动崩溃时 #

要在 unflatten_device_tree 之前看，只能靠静态手段：

bash
make ARCH=arm board.dtb
fdtdump board.dtb | head -50

cat /sys/kernel/debug/device-tree | head   # 需 CONFIG_DEBUG_FS + CONFIG_OF

CONFIG_OF_UNITTEST 打开后能跑 of_unittest，在 QEMU 上验解析逻辑。它是测试套件不是调试器，但验证「内核的 libfdt 能不能吃我的 dtb」比手工 dump 靠谱。

二十一、易错点速查 #

按踩坑频率排。

# 症状 原因 修法
1 FDT_ERR_BADMAGIC，内核不认 dtb 文件按小端存的，开头是 ed fe 0d d0 重新用 dtc 编，别手搓
2 内核能起但设备全没有 根节点 compatible 和 machine desc 对不上 dmesg 看实际读到的 model
3 某个设备没生成 platform_device 节点缺 compatible，或 status = "disabled" 补属性，或改 okay
4 platform_device 有了但驱动不 probe compatible 和驱动 .of_match_table 大小写或拼写不一致 两边逐字符对
5 reg 读出来的地址不对 父节点 #address-cells / #size-cells 写错 顺着父节点往上核
6 中断号解析成非法值 控制器 #interrupt-cells 和 interrupts 的 cell 数不匹配 数 cell
7 节点名带 @ 但没 reg 违反命名规则 dtc -Wunit_address_vs_reg 会报
8 clocks 拿不到 &label 引用的节点没有 #clock-cells 补上
9 反编译出来多出一堆 linux,phandle 老 dtc 的遗留 无害，新 dtc 只出 phandle
10 改了 dts 但行为没变 编出来的 dtb 不是 boot 用的那份 diff /sys/firmware/fdt 和源码 dtb
11 memreserve 保留过多 把 (start, end) 当成 (addr, size) 第二个数是长度不是结束地址
12 dtb 被覆盖、属性读出垃圾 dtb 内存没被 reserve 检查 early_init_dt_reserve_memory_arch
13 full_name 打印成 //serial@... 手工构造树时没按新格式重建路径 别手搓，用 unflatten_device_tree
14 子节点顺序和 dts 不一致 头插链表没反转 老代码的 bug 已修，别自己重写这段
15 overlay 加载失败 主 dtb 编的时候没加 -@，没有 __symbols__ 重编主 dtb

再补几条语义层面的：

  • compatible 列表有序，第一个是具体型号，最后一个是通用回退。写成「通用在前」会永远匹配不到特定驱动。
  • #size-cells = <0> 合法，I2C 从设备就这样：只有地址没有长度。
  • ranges 缺省不等于空。没写 ranges 的总线节点，子节点地址翻译不到父总线；写了空的 ranges; 才是 1:1 映射。
  • chosen 只能有一个，且必须挂在根节点下。bootargs、linux,initrd-start 都在这儿。
  • aliases 的值是路径字符串，不是 phandle。这是唯一的例外，别被 &label 的惯性带偏。
  • memory 节点的 device_type 必须是 "memory"，只有带这个属性的节点会被 early_init_dt_scan_memory 当成物理内存。
