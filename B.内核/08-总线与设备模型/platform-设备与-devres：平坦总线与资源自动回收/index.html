本篇讲什么：platform 总线，以及和它绑在一起用的 devres（device resource management）。前者解决「SoC 内部那些无法自动探测的控制器怎么挂进设备模型」，后者解决「probe 里申请的一堆资源谁来释放」。

本篇不讲什么：kobject / sysfs 底层、bus_type 与 struct device 全字段、class 子系统（见《kobject 与 sysfs》《device、driver、bus、class：四个注册表》）；设备树语法与 of_* 全表（见《设备树》）；GPIO/pinctrl 与 I2C 驱动写法（见《GPIO/pinctrl 与 I2C》）；DMA 与 PCIe（见《DMA 与 PCIe》）；以太网（见《以太网》）。

版本基准：素材是 3.x 形态（作者参考 linux3.10.29，可见 .dev_attrs、pdev->archdata、devm_gpio_request 这些 3.x 写法）。4.x / 5.x 有变动处逐处标注；标「未验证」的，是没拿到对应版本源码逐行核对。

一、platform 总线为什么存在：SoC 内部那些探测不到的设备 #

USB 和 PCI 是好总线。插一个 U 盘，主机控制器发 GET_DESCRIPTOR，设备自己报出厂商 ID、产品 ID、接口类型。内核拿这些 ID 去 id_table 里查，查到就绑驱动。你不需要告诉内核「这里插了个东西」——硬件自己会自我介绍。PCI 更彻底：配置空间是协议规定死的，每个 function 有 vendor/device/class 三个码，扫一遍总线就能列清单。

SoC 内部不是这样。一块 ARM SoC 里挂着 GPIO 控制器、I2C 控制器、SPI 控制器、UART、DMA 引擎、定时器、看门狗、以太网 MAC、USB 控制器、显示控制器——这些东西全都焊在硅片上，永远不会插拔，也没有统一的自我介绍协议。GPIO 控制器不会主动说「我是 0x1234 厂商的 0x5678 型号」，它连一个能报 ID 的寄存器都没有。

那内核怎么知道系统里有几个 GPIO 控制器、每个的基地址是多少？两个来源：

  1. 板级代码硬编码。arch/arm/mach-xxx/board-yyy.c 里一长串 static struct platform_device，把名字、寄存器地址、中断号、时钟名全写死，启动时逐个注册。
  2. 设备树。.dts 里写 compatible = "vendor,model"，启动时 of_platform_populate() 遍历节点，动态生成 platform_device。

两条路终点一样：把设备信息变成 struct platform_device，再让 platform_driver 认领。这就是 platform 总线的全部意义：它是「注册用的容器」，不是一根线。没有电气信号，没有枚举协议，没有热插拔。设备必须由板级代码或 DT 主动告知内核。

原文引了 Documentation/driver-model/platform.txt 的定义：

Platform devices are devices that typically appear as autonomous entities in the system. This includes legacy port-based devices and host bridges to peripheral buses, and most controllers integrated into system-on-chip platforms. What they usually have in common is direct addressing from a CPU bus. Rarely, a platform_device will be connected through a segment of some other kind of bus; but its registers will still be directly addressable.

拆成四类：

类别 例子 为什么归 platform
传统 port-based 设备 老式串口、并口 只为兼容保留，不该再用（legacy）
物理总线的桥 PCI host bridge、USB host controller 桥挂在 CPU 总线上，CPU 直接寻址
SoC 内部控制器 GPIO、I2C、SPI、UART、DMA、timer 数量不固定、无法枚举，只能靠描述
挂在别的总线上的设备 少数例外 寄存器仍可 CPU 直接寻址

四类能凑一张表，靠的是同一个共同点：寄存器可被 CPU 总线直接寻址。拿到物理地址 ioremap 一下就能读写。这决定了 platform 的资源描述核心是「一段内存 + 一个中断号」，而不是 USB 那种「端点 + 传输类型」。

判断一个设备该不该写成 platform 设备，问一句就够：它能不能自己告诉内核它存在？ 能，用 USB/PCI/I2C/SPI；不能而寄存器可直接寻址，就是 platform。层次也要分清：一个 GPIO 扩展芯片挂在 I2C 上，那个芯片的驱动是 I2C 驱动；而 SoC 的 I2C 控制器本身，是 platform 驱动。

实现只有两个文件：include/linux/platform_device.h（声明）和 drivers/base/platform.c（实现）。架构分三块，全部建立在原有设备模型之上：

text
struct bus_type platform_bus_type  ← 基于 bus 模块，虚拟总线
   ├─ struct platform_device       ← 基于 device，内嵌 struct device
   │     └─ struct resource        ← 资源描述
   └─ struct platform_driver       ← 基于 device_driver，内嵌 device_driver

注意「内嵌」二字。platform_device 的核心成员就是 struct device dev，platform_driver 里就是 struct device_driver driver。所有平台设备最终都是设备模型里的普通设备，都走 device_register → kobject_add → sysfs，都出现在 /sys/devices/platform/ 下。platform 只是套了一层约定：这类设备长什么样、资源怎么拿、名字怎么匹配。

二、platform_device 与 platform_driver 的结构 #

c
/* include/linux/platform_device.h（3.x 形态） */
struct platform_device {
        const char      *name;
        int             id;
        bool            id_auto;
        struct device   dev;
        u32             num_resources;
        struct resource *resource;
        const struct platform_device_id *id_entry;
        struct mfd_cell *mfd_cell;      /* MFD cell pointer */
        struct pdev_archdata    archdata;  /* arch specific additions */
};

name：设备名，和 struct device 的 init_name 同义——注册时拷贝到 dev.init_name。这是名字匹配的唯一依据。

id：同类设备编号。内核允许同名设备存在多个，靠 id 区分；-1 表示「就一个，不用编号」。

id_auto：注册时是否自动分配 id。3.x 及以前没有这个字段，platform_device_register_simple() 里写死 id = -1。

dev：真正的设备对象。platform 的全部设备模型能力（parent、bus、driver 绑定、sysfs、PM、devres 链表）都来自这里。驱动里拿到的 struct device * 基本都是 &pdev->dev。

num_resources / resource：资源数组和长度，元素是 struct resource。这是 platform 设备最关键的数据——声明「我占了哪段地址、哪个中断、哪条 DMA 通道」。只是声明，注册时才登记进资源树（第三章）。

id_entry：匹配成功后指向 platform_driver 的 id_table 里命中的那一项。原文说「和内核模块相关，暂不说明」，不准确——它和模块加载无关，是驱动拿到的「我按哪条 id 匹配上」的凭据。

mfd_cell：MFD 框架里指向 cell 的指针。一个芯片塞了多个功能块（电源管理芯片里的 RTC + ADC + regulator + GPIO），MFD 把每块拆成一个 platform_device。

archdata：体系结构相关数据。原文吐槽得直接（「去看看 arch/arm/include/asm/device.h 中 struct pdev_archdata 的定义，就知道这种放纵的设计有多么垃圾」），有道理——ARM 的 pdev_archdata 长时间就一个 dma_ops 指针，为它开一个 arch 钩子纯属历史包袱。

版本差异：archdata 在 5.x 已被清掉，DMA ops 整合进 struct device 的通用字段（删除版本未验证，5.15 头文件里已无此成员）。mfd_cell 的职责也部分被 platform_device_info 机制替代（未验证具体版本）。

驱动侧：

c
struct platform_driver {
        int (*probe)(struct platform_device *);
        int (*remove)(struct platform_device *);
        void (*shutdown)(struct platform_device *);
        int (*suspend)(struct platform_device *, pm_message_t state);
        int (*resume)(struct platform_device *);
        struct device_driver driver;
        const struct platform_device_id *id_table;
};

五个回调把 struct device * 换成 struct platform_device *，其余和 device_driver 一致。这个替换是 platform 层做的，底层 driver->probe 签名永远是 int (*probe)(struct device *)，转换发生在 platform_drv_probe()。

platform_device_id 长这样：

c
struct platform_device_id {
        char name[PLATFORM_NAME_SIZE];      /* PLATFORM_NAME_SIZE == 20 */
        kernel_ulong_t driver_data;
};

driver_data 是一根随你用的 kernel_ulong_t，常放「这个变体的寄存器偏移」「这个型号的 quirk 标志」。这个字段被大量滥用——有人塞指针，有人塞枚举值，上限就是 unsigned long 的宽度。

版本差异：remove 回调的签名变过。5.18 起拆出 void (*remove_new)(struct platform_device *)（返回 void），6.3 前后又改名回 remove 并彻底改成 void 返回（具体版本号未验证，按你手上的 platform_device.h 核对）。suspend / resume 这两个老式 PM 回调很早就废弃，实际走 driver.pm 指向的 dev_pm_ops。

一句话总结两边关系：platform_driver 里那个 struct device_driver driver 才是拿去注册的东西，platform 层的回调是给驱动作者看的门面。

platform_device_register_simple() 展开就是三步：alloc → add_resources → add，出错时依次 platform_device_put() 回退。platform_device_register_full() 的参数结构（3.x 形态，5.x 另有 fwnode / properties）：

struct platform_device_info { struct device *parent; const char *name; int id; const struct resource *res; unsigned int num_res; const void *data; unsigned int size_data; u64 dma_mask; };

核心是 platform_device_add()，五步，顺序关键：

text
1. 没有 parent 就设为 &platform_bus → sysfs 路径变成 /sys/devices/platform/xxx
2. pdev->dev.bus = &platform_bus_type
3. 按 id 修正设备名，变成 "name.id" 形式（id < 0 时保持 name）
4. insert_resource()：把 resource 数组登记进全局资源树
   （在此之前 resource 只是声明，资源模块并不知情）
5. device_add(&pdev->dev)：把内嵌 device 加进内核

第 4 步值得多说。insert_resource() 做的是冲突检测：两段设备声明重叠的 MEM 区间时，后注册的失败（-EBUSY）。所以两个驱动抢同一段寄存器时，报错发生在 platform_device_register 里，不是 probe 里。第 3 步的效果在 sysfs 里最清楚：有 id 的设备名形如 name.id（serial8250.0、s3c64xx-spi.1），id = -1 的不带后缀。

platform_device_unregister() 反着来：platform_device_del() + platform_device_put()。所以 alloc 之后如果 add 失败，你得自己 put，否则泄漏。

驱动侧：

c

platform_driver_register() 三步：

text
1. drv->driver.bus = &platform_bus_type
2. 若提供了 probe/remove/shutdown，塞进 drv->driver 对应位置，
   但填的是 platform 层转接函数 platform_drv_probe / _remove / _shutdown
3. driver_register(&drv->driver)

第 2 步是整个设计的关键。设备模型只认 int (*probe)(struct device *)，而驱动作者想写 int (*probe)(struct platform_device *)，中间必须有转换层：

c
static int platform_drv_probe(struct device *_dev)
{
        struct platform_driver *drv = to_platform_driver(_dev->driver);
        struct platform_device *dev = to_platform_device(_dev);
        return drv->probe(dev);
}

to_platform_device() 就是 container_of(dev, struct platform_device, dev)——dev 是成员，知道成员地址反推结构体首地址是合法的。这套手法在设备模型里到处都是。

platform_driver_probe() 是特殊版本：不走正常 match 流程，注册后主动调用一次传入的 probe，失败就注销 driver。好处是 probe 可以放 __init 段省内存；代价是不能 defer probe（-EPROBE_DEFER 没地方重试），也不支持热插拔。老 SoC 板级代码用得多，DT 代码基本不用。

platform_set_drvdata() 本质是 dev_set_drvdata(&pdev->dev, data)，写 dev->p->driver_data。probe 里存、remove 里取、PM 回调里取，是标准动作。

懒人接口 platform_create_bundle(driver, probe, res, n_res, data, size) 一次完成「建 device + 注册 driver + probe」，只适合一辈子出现一次、不需要热插拔的设备。probe 要显式当参数传，因为它绕开了 driver_register 的匹配流程。

四、platform_bus_type：一个几乎不做匹配的总线 #

c
int __init platform_bus_init(void)
{
        int error;
        early_platform_cleanup();
        error = device_register(&platform_bus);
        if (error)
                return error;
        error =  bus_register(&platform_bus_type);
        if (error)
                device_unregister(&platform_bus);
        return error;
}

三件事，各有目的：

  1. early_platform_cleanup()：走到这里说明早期启动结束了，早期平台设备那一套可以扔，__init 段的内存可以还。
  2. device_register(&platform_bus)：注册一个名叫 platform 的普通设备，定义极简，只有 init_name = "platform"。它创出 /sys/devices/platform/，所有 platform 设备的父设备默认就是它。
  3. bus_register(&platform_bus_type)：创出 /sys/bus/platform/，按 bus 模块的规矩挂上 uevent、devices/、drivers/、drivers_probe、drivers_autoprobe。
c
struct bus_type platform_bus_type = {
        .name = "platform", .dev_attrs = platform_dev_attrs,
        .match = platform_match, .uevent = platform_uevent,
        .pm = &platform_dev_pm_ops,
};

五个字段逐个说：

  • .name：sysfs 目录名，/sys/bus/platform。
  • .dev_attrs：给总线上每个设备自动加的默认 attribute。3.x 里装的是 modalias 和 uevent，所以能在 /sys/devices/platform/*/modalias 看到形如 platform:xxx 的字符串。5.x 删了这个字段，默认属性改用 device_type 或直接在 device_add 里处理（platform_dev_attrs 在 5.x 的 platform.c 里已不存在，4.20 前后还在，删除版本未验证）。
  • .match：唯一真正干活的函数，第五章展开。platform 总线的「智能」全在这里。
  • .uevent：往 uevent 环境变量塞 MODALIAS=platform:<name>，供 udev 加载模块。
  • .pm：PM 回调链，platform_pm_* 再转到 dev_pm_ops。

没有 probe / remove 回调。Bus 那篇点过：bus_type 的 probe/remove 是为了保证「总线自己能工作之后才让设备 probe」，而 platform 总线是虚构的，无所谓初始化，留空。这不是设计取舍，是它不需要。

四种总线对照，platform 的特殊性一目了然：

维度 platform USB PCI I2C
物理形态 无 有（差分线） 有 有（两线）
设备发现 靠人告知（板级代码 / DT） 枚举，设备自报 descriptor 扫配置空间 vendor/device/class 地址探测或 DT 声明
匹配依据 名字 + id_table + of/acpi 表 idVendor/idProduct/class vendor/device/class 三元组 地址 + id_table
热插拔 不支持 支持 部分支持 不支持（设计如此）
sysfs 路径 /sys/devices/platform/ /sys/devices/pci.../usbN/ /sys/devices/pci0000:00/ /sys/devices/.../i2c-N/
bus_type->probe 无 有 有 有
资源来源 struct resource 数组 设备 descriptor BAR + 配置空间 无独立资源，靠地址

最后一行是重点。platform 设备带 struct resource 数组，这是它跟其他总线设备最大的形态差别；USB/PCI 的信息在硬件描述符里，读到就知道；platform 的信息只能整段搬进数组等你来取。

注册完成后的系统形状：

text
/sys/devices/platform/            ← platform_bus 设备
/sys/bus/platform/{devices,drivers,drivers_autoprobe,drivers_probe,uevent}

drivers_autoprobe 是调试时最该先想到的开关。probe 崩内核时，echo 0 > /sys/bus/platform/drivers_autoprobe 后重启，驱动不会自动绑定，先看 sysfs 状态，再手动 echo xxx > drivers_probe 逐个触发。

五、id_table 与 name 匹配两种方式 #

platform_match() 是 platform 总线的核心，3.x 形态大致如下（按原文与内核通行实现整理）：

c
static int platform_match(struct device *dev, struct device_driver *drv)
{
        struct platform_device *pdev = to_platform_device(dev);
        struct platform_driver *pdrv = to_platform_driver(drv);
        if (of_driver_match_device(dev, drv))        /* 1. 设备树 compatible */
                return 1;
        if (acpi_driver_match_device(dev, drv))      /* 2. ACPI 的 _HID */
                return 1;
        if (pdrv->id_table)                          /* 3. 比 id_table */
                return platform_match_id(pdrv->id_table, pdev) != NULL;
        return (strcmp(pdev->name, drv->name) == 0); /* 4. 兜底：比名字 */
}

四条路径，严格按顺序短路。 这一句就是「platform 总线几乎不做匹配」的答案：四次比较里三次是字符串比对，一次是查表，没有任何硬件查询。

第一条 of_driver_match_device()：设备有 DT 节点（dev->of_node 非空）就拿节点里的 compatible 去 of_match_table 里比。of_match_table 是 struct device_driver 的成员，类型 const struct of_device_id *。每条 of_device_id 是 { .compatible = "vendor,model", .data = ... }，data 是 const void *，指向驱动自己定义的变体描述，作用和 id_table 的 driver_data 一样。

第二条 acpi_driver_match_device()：x86 上 ACPI 描述设备，比 _HID/_CID。

第三条 id_table：platform_match_id() 返回命中的那一项指针，随后塞进 pdev->id_entry。匹配规则是 strcmp(pdev->name, id->name) == 0。

第四条名字兜底：strcmp(pdev->name, drv->name)，注意比的是 drv->name，即 platform_driver.driver.name。

两条路差别：

name 匹配 id_table 匹配
数据在哪 pdev->name vs drv->driver.name pdev->name vs 每条 id.name
能带变体数据吗 不能 能，id->driver_data
命中后拿到什么 什么都没有 pdev->id_entry 指向命中项

id_table 的价值是同族设备差异化驱动。一颗 SoC 的 UART 有四个控制器、两代寄存器布局：

c
static const struct platform_device_id myuart_ids[] = {
        { .name = "myuart-v1", .driver_data = (kernel_ulong_t)&myuart_v1_data },
        { .name = "myuart-v2", .driver_data = (kernel_ulong_t)&myuart_v2_data },
        { }
};
MODULE_DEVICE_TABLE(platform, myuart_ids);

probe 里用 platform_get_device_id(pdev)->driver_data 取变体数据。一个驱动代码，四份设备实例，两代硬件，全搞定。

MODULE_DEVICE_TABLE(platform, ...) 不能忘。它生成 __mod_platform_device_table 段，供 depmod 建「modalias → 模块」映射。缺了它，/sys/devices/platform/xxx/modalias 匹配不到模块，udev 冷启动时不会自动 modprobe。这个 bug 很难查——热插拔场景下模块已经加载了，问题只在开机阶段出现。

版本差异：5.x 的 platform_match() 多了 device_links / fw_devlink 相关的前置检查（见第二十一章），fw_devlink 是 5.2 引入的，函数体比 3.x 长了。具体加在哪、不同小版本的调整，未验证。

一个容易忽略的点：platform_match 返回非零只是「匹配成功」，不代表 probe 一定执行。设备模型还会检查 dev->driver 是否已绑定。原文讲 Bus 时强调过：

在 bus 的设备链表中查找 device，和对应的 device_driver 比对 name，如果相同，则查看该设备是否已经绑定了 driver（查看其 dev->driver 指针是否为空），如果已绑定，则不会执行 probe 动作；如果没有绑定，则以 device 的指针为参数，调用 driver 的 probe 接口。

这条规则带来一个很有用的能力：一个 platform_driver 可以驱动多个同名设备。四个 serial8250 实例，一个驱动，四次 probe，每次 pdev->id 不同。

匹配成功后 probe 的完整链路：

设备先到走 platform_device_register() → device_add() → bus_probe_device() → device_attach() → __device_attach；驱动先到走 platform_driver_register() → driver_register() → driver_attach() → __driver_attach。两条路都汇到 really_probe()，这一段在第十五章还会再出现，因为它是 devres 自动回收的两个触发点之一。

六、从设备树生成 platform_device：of_platform_populate #

板级代码硬编码 platform_device 数组的日子在 ARM 上基本结束了。主流做法是 DTS 写节点，启动时由 of_platform_populate() 把节点变成 platform_device。调用点在 ARM 的 arch_initcall 级别：

text
start_kernel
  └── setup_arch → unflatten_device_tree()      （展开 DTB）
  └── arch_initcall 级别：
        of_platform_default_populate_init / machine_desc->init_machine
          └── of_platform_populate(NULL, of_default_bus_match_table, NULL, NULL)

签名（4.x 形态）：

int of_platform_populate(struct device_node *root, const struct of_device_id *matches, const struct of_dev_auxdata *lookup, struct device *parent);

四个参数：

  • root：从哪个节点开始。传 NULL 从根开始。
  • matches：判断「哪些子节点该继续递归」。of_default_bus_match_table 是内核默认表，列出所有总线型节点的 compatible（simple-bus、simple-mfd、isa、arm,amba-bus 等）。
  • lookup：struct of_dev_auxdata 数组，给指定节点补 platform_data/资源。老驱动迁移期用，新驱动别用。
  • parent：生成出来的 platform_device 的父设备，传 NULL 就是 platform_bus。

流程：

text
of_platform_populate(root, matches, lookup, parent)
  └── 对 root 的每个子节点 child：
        ├── of_device_is_available(child) 为假 → 跳过（status = "disabled"）
        ├── of_platform_bus_create(child, matches, lookup, parent, true)
        │     ├── of_platform_device_create_pdata()
        │     │     ├── 检查 compatible 非空
        │     │     ├── 分配 platform_device（名字取节点名去掉单位地址）
        │     │     ├── of_device_make_bus_id()：处理重名，编出 name.N
        │     │     ├── pdev->dev.of_node = child        ← 关键
        │     │     ├── of_irq_to_resource 等：regs/interrupts/dma → resource
        │     │     └── platform_device_add()
        │     └── 若节点本身是「总线」（compatible 命中 matches）：
        │           of_platform_bus_create(child, matches, lookup, &dev->dev, false)
        └── 继续下一个子节点

几个要点。

设备名从哪来：DT 节点名形如 serial@1c28000，取 @ 之前的部分，pdev->name 是 serial。同名节点被 of_device_make_bus_id() 编成 serial.0、serial.1。DT 场景下这个命名在生成 platform_device 时就完成，而板级硬编码场景是 platform_device_add() 里按 id 字段拼——两处逻辑，效果类似。

matches 决定递归边界。这个参数很反直觉：它不控制「哪些节点生成设备」，而是控制「哪些节点被当成总线继续往下钻」。不带 matches 的话只处理 root 的直接子节点，不往 simple-bus 里钻。DTS 里那段 simple-bus 就是为这个存在的：

dts
/ {
        compatible = "vendor,myboard";
        #address-cells = <1>;
        #size-cells = <1>;

        soc {
                compatible = "simple-bus";              /* ← 递归边界 */
                #address-cells = <1>;
                #size-cells = <1>;
                ranges;

                uart0: serial@1c28000 {
                        compatible = "vendor,myuart";
                        reg = <0x1c28000 0x400>;
                        interrupts = <0 5 4>;
                        clocks = <&ccu 12>;
                };
                i2c0: i2c@1c2b000 {
                        compatible = "vendor,myi2c";
                        reg = <0x1c2b000 0x400>;
                        interrupts = <0 8 4>;
                        #address-cells = <1>;
                        #size-cells = <0>;
                        eeprom@50 {                      /* ← i2c_client */
                                compatible = "atmel,24c02";
                                reg = <0x50>;
                        };
                };
        };
};

soc 是 simple-bus，被 matches 命中，于是递归进去，uart0 和 i2c0 各生成一个 platform_device。i2c0 下面的 eeprom@50 不是 platform 设备——i2c0 的 compatible 不是 simple-bus，递归到此为止，eeprom 由 I2C 子系统在 i2c0 驱动 probe 时用 of_i2c_register_devices() 实例化成 i2c_client。

这个边界是 DT 驱动模型的核心分工：platform 只管「CPU 能直接寻址的控制器」，控制器下面挂的设备归各自子系统管。

资源是自动转出来的。reg 变 IORESOURCE_MEM，interrupts 变 IORESOURCE_IRQ，dmas 变 IORESOURCE_DMA（of_address_to_resource / of_irq_to_resource）。这就是为什么 DT 驱动的 probe 里可以直接 platform_get_resource(pdev, IORESOURCE_MEM, 0)——那份数组是 DT 生成的。

pdev->dev.of_node 是连接 DT 和驱动的唯一绳索。of_driver_match_device() 拿的就是 dev->of_node，它挂在 struct device 上，不是 platform 特有的。子节点必须有 compatible，否则不生成 platform_device，也不递归（除非父节点是总线型）。

两种来源对照：

板级代码（legacy） 设备树
设备定义位置 board-xxx.c 静态数组 .dts 节点
资源来源 手写 struct resource reg / interrupts 自动转换
设备名 name 字段 节点名去 @ 后缀，重名编 .N

现状 仅留给极老平台 主流

版本差异：of_platform_bus_probe() 在 4.4 前后与 of_platform_populate() 合并（未验证具体版本）；5.2 引入 fw_devlink 后，这条路径上多了「从 DT 的 power-domains/suppliers 建 device link」这一步，of_platform_default_populate() 成为默认入口；of_dev_auxdata 在 5.x 基本只服务极老板级驱动。DT 语法细节见《设备树》，这里只讲「它怎么变成 platform_device」。

七、platform_get_resource：资源是怎么描述的 #

struct resource 是所有 platform 资源的通用容器（include/linux/ioport.h）：

c
struct resource {
        resource_size_t start, end;
        const char *name;
        unsigned long flags;
        struct resource *parent, *sibling, *child;
};
  • start / end：起止，end 是闭区间。reg = <0x1c28000 0x400> 对应 start = 0x1c28000、end = 0x1c283ff，长度 end - start + 1。所以永远不要写 size = end - start，用 resource_size(res)（实现就是 res->end - res->start + 1）。少算一个字节的后果是最后一个寄存器写不进去，而且不报错，行为诡异。
  • name / flags：name 是资源名（DT 下来自 reg-names 或节点名），platform_get_resource_byname() 靠它找；flags 高 8 位是类型（IORESOURCE_MEM / IO / IRQ / DMA / BUS），低位是修饰标志（READONLY / CACHEABLE / SHARED 等）。
  • parent / sibling / child：组成资源树，insert_resource() 把资源插进 /proc/iomem 背后的那棵树。同一时刻树上不能有两个区间重叠，/proc/iomem 的缩进层级就是这棵树。

resource_size_t 在 32 位上是 u32、64 位上是 u64，由 CONFIG_PHYS_ADDR_T_64BIT 决定。跨平台驱动别把 phys_addr_t 和它混用。

取资源：

platform_get_resource(struct platform_device *pdev, unsigned int type, unsigned int num) 与 platform_get_resource_byname(struct platform_device *pdev, unsigned int type, const char *name)。

语义：按 type 过滤 pdev->resource[]，数第 num 个（从 0 起）返回；越界或没匹配返回 NULL。_byname 把 num 换成 name。DT 侧：

dts
usb0: usb@1c13000 {
        compatible = "vendor,myusb";
        reg = <0x1c13000 0x400>, <0x1c14000 0x800>;  /* ctrl / phy */
        reg-names = "ctrl", "phy";
        interrupts = <0 12 4>, <0 13 4>;
        interrupt-names = "usb", "phy";
};

c
ctrl = platform_get_resource_byname(pdev, IORESOURCE_MEM, "ctrl");
phy  = platform_get_resource_byname(pdev, IORESOURCE_MEM, "phy");

_byname 比按索引取值更值得用。原因不是可读性，而是 reg 里多个区间的顺序在不同 SoC 版本上会变，用索引写的驱动换个片子就错位。

版本差异（必需标注）：platform_get_resource() 的签名从 3.x 到 6.x 没变过，一直是 (pdev, type, num) 返回 struct resource *。原文第 8 篇列出的声明在 5.x 头文件里仍然一模一样。签名变过的是它的兄弟 platform_get_irq()（第九章）。

返回裸指针这件事不用担心——pdev->resource 数组的生命周期完全覆盖 probe 到 remove，不需要拷贝。但不要改它，struct resource 是共享数据，改了会影响资源树。

「DT 属性 → resource」的对应关系，调试时特别有用：

DT 属性 生成的 resource flags 类型位 备注
reg 一项或多项 IORESOURCE_MEM 解析方式由 #address-cells/#size-cells 决定
reg + 父节点有 IO 空间 IORESOURCE_IO x86/PCI 常见
interrupts 一项或多项 IORESOURCE_IRQ 规格由控制器的 #interrupt-cells 决定
interrupts-extended 多项，可跨控制器 IORESOURCE_IRQ 一个节点挂多个中断控制器

最后三行是关键认知：不是 DT 里写的都变成 struct resource。只有「一段地址」「一个中断号」「一条 DMA 通道」进数组，时钟、GPIO、reset、regulator、pinctrl 全走各自 framework，用 devm_clk_get() / devm_gpiod_get() 去拿（第十八章）。

这也是 devres 存在的必要性：resource 里的东西是「描述」，真正申请（request_mem_region / request_irq）由驱动在 probe 里做，所以释放也得驱动负责——除非用 devm_ 版本。

八、IORESOURCE_MEM / IRQ / DMA 三类资源 #

flags 的位布局：

c
#define IORESOURCE_TYPE_BITS  0x00001f00     /* 类型位 */
#define IORESOURCE_IO   0x00000100   IORESOURCE_MEM  0x00000200
#define IORESOURCE_REG  0x00000300   IORESOURCE_IRQ  0x00000400
#define IORESOURCE_DMA  0x00000800   IORESOURCE_BUS  0x00001000
#define IORESOURCE_READONLY  0x1     IORESOURCE_CACHEABLE  0x2   /* 修饰位 */
#define IORESOURCE_DISABLED  0x4     IORESOURCE_PREFETCH   0x2000
#define IORESOURCE_SHARED    0x4000

判断类型用 resource_type(flags)（先按 IORESOURCE_TYPE_BITS 掩码），不要写 flags & IORESOURCE_MEM——低位修饰标志会让这个位判断意外成立。

8.1 IORESOURCE_MEM：寄存器的物理地址 #

DT 里 reg = <0x1c28000 0x400> 对应一个 IORESOURCE_MEM 资源。驱动里标准处理分两步，不能混：

c
res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
if (!res)
        return -ENODEV;
/* 第一步：向资源树登记，防冲突 */
if (!request_mem_region(res->start, resource_size(res), dev_name(&pdev->dev)))
        return -EBUSY;
/* 第二步：映射成虚拟地址 */
base = ioremap(res->start, resource_size(res));
if (!base) {
        release_mem_region(res->start, resource_size(res));
        return -ENOMEM;
}

一步到位则是 base = devm_ioremap_resource(&pdev->dev, res);，内部依次 devm_request_mem_region() + devm_ioremap()（第十七章）。

为什么需要 request_mem_region：ioremap 本身不检查冲突。两个驱动 ioremap 同一段地址都能成功，然后互相踩。request_mem_region 才是「向资源树占座」的动作，冲突时返回 NULL。区别在 /proc/iomem 里看得见——没占座的设备那一行不显示名字。

记住顺序：platform_get_resource 拿描述 → request_mem_region 占座 → ioremap 映射。三步三份责任，缺一步留隐患。

8.2 IORESOURCE_IRQ：中断号 #

DT 里 interrupts = <0 5 4>，三项一般是「控制器内序号 / 类型 / 触发方式」，具体含义由控制器的 #interrupt-cells 决定，转换后 resource.start 是 Linux 虚拟中断号。platform_get_resource(pdev, IORESOURCE_IRQ, 0)->start 和 platform_get_irq(pdev, 0) 拿的是同一个值，但后者多做了一件事：IRQ domain 映射。3.x 里它就是 r ? r->start : -ENXIO；带 DT 的版本会先试 irq_of_parse_and_map() / of_irq_get()：

c
        if (IS_ENABLED(CONFIG_OF_IRQ) && dev->dev.of_node) {
                int ret = of_irq_get(dev->dev.of_node, num);
                if (ret > 0 || ret == -EPROBE_DEFER)
                        return ret;
        }

这个顺序很重要：DT 场景下中断号不是 reg 那种静态数字，要经过 irq_domain 转换。同一个硬件 IRQ 在不同内核里拿到的虚拟号不一样，永远不要硬编码。

IRQ 资源的 flags 低位在旧内核里用来传触发方式（IORESOURCE_IRQ_HIGHEDGE 等），4.x 基本废弃，改由 irq_domain / irq_chip 从 DT 解析（5.x 的 ioport.h 里已找不到这些宏，废弃版本未验证）。

8.3 IORESOURCE_DMA：DMA 通道 #

这一类最容易误解。DT 里 dmas = <&dma0 5 0x1>, <&dma0 6 0x1>; 生成的 IORESOURCE_DMA 资源，start 不是物理地址，而是一个不透明编码——形如 (控制器 << 16) | 通道号，编码方式由 DMA controller 驱动自己定义。所以 dma_res->start 不要当地址用。

老式 SoC（IMX、S3C）用这套「通道号」模型，直接 xxx_dma_request_by_prio()。新式做法是 dmaengine API，不从 resource 取，按名字从 DT 拿：

c
struct dma_chan *chan = dma_request_chan(&pdev->dev, "rx");
if (IS_ERR(chan))
        return PTR_ERR(chan);
/* 用完 */
dma_release_channel(chan);

dma_request_chan() 自己解析 dmas / dma-names，不需要碰 IORESOURCE_DMA。5.x 里老接口 dma_request_channel() 已不建议用（要自己传 dma_cap_mask）。

九、platform_get_irq 系列 #

c
int platform_get_irq(struct platform_device *dev, unsigned int num);
int platform_get_irq_byname(struct platform_device *dev, const char *name);
int platform_irq_count(struct platform_device *dev);
int platform_get_irq_optional(struct platform_device *dev, unsigned int num);

platform_get_irq() 的错误返回约定是这个家族最大的坑。 3.x 及更早返回 -ENXIO（-6），所以老代码常见：

c
irq = platform_get_irq(pdev, 0);
if (irq <= 0) {
        dev_err(&pdev->dev, "no irq\n");
        return -ENODEV;
}

用 <= 0 而不是 IS_ERR()，因为返回的是 int，而中断号 0 在 Linux 里非法（合法中断从 1 开始）。原文的示例就是 if (!res || (int)irq <= 0) { err = -ENODEV; goto exit; }。(int)irq 这个强转说明了年代——更早版本返回 unsigned int，没有负数，必须先转有符号才能判 < 0。

5.x 之后统一了：资源获取接口一律「返回 int，成功给非负值，失败给负数 errno」，推荐用 platform_get_irq_optional() 处理「中断可选」的情形——设备确实没有中断时它不打日志、不报错，而 platform_get_irq() 会打一条错误（引入版本未验证，5.10 已存在）。

platform_get_irq_byname() 按 interrupt-names 找（DT 写法见第七章）。platform_irq_count() 数一数声明了几个中断，用于「必须有 N 个否则报错」的检查（5.x 才有）。

拿到 IRQ 要申请才能用：

c
ret = devm_request_irq(&pdev->dev, irq, my_handler, IRQF_SHARED,
                       dev_name(&pdev->dev), priv);

dev_id 的规矩：非共享中断传什么都行（建议传 priv）；IRQF_SHARED 时必须唯一且能反查到设备，因为 free_irq(irq, dev_id) 靠它精确匹配。共享中断上 dev_id 传 NULL 或两个设备传同一个值，会让 free_irq 释放错对象。

十、probe 里的典型流程 #

把前九章拼起来，一个典型 platform 驱动的 probe（托管版）：

c
static int mydrv_probe(struct platform_device *pdev)
{
        struct mydrv *priv;
        struct resource *res;
        int irq, ret;

        res = platform_get_resource(pdev, IORESOURCE_MEM, 0);   /* 1. 取资源描述 */
        if (!res)
                return -ENODEV;
        irq = platform_get_irq(pdev, 0);
        if (irq < 0)
                return irq;

        priv = devm_kzalloc(&pdev->dev, sizeof(*priv), GFP_KERNEL);  /* 2. 私有数据 */
        if (!priv)
                return -ENOMEM;
        priv->dev = &pdev->dev;
        platform_set_drvdata(pdev, priv);

        priv->base = devm_ioremap_resource(&pdev->dev, res);     /* 3. 寄存器映射 */
        if (IS_ERR(priv->base))
                return PTR_ERR(priv->base);

        priv->clk = devm_clk_get(&pdev->dev, "apb");             /* 4. 时钟/复位/供电 */
        if (IS_ERR(priv->clk))
                return PTR_ERR(priv->clk);
        ret = clk_prepare_enable(priv->clk);
        if (ret)
                return ret;
        priv->rst = devm_reset_control_get(&pdev->dev, NULL);
        if (IS_ERR(priv->rst))
                return PTR_ERR(priv->rst);
        ret = reset_control_deassert(priv->rst);
        if (ret)
                return ret;
        priv->vdd = devm_regulator_get(&pdev->dev, "vdd");
        if (IS_ERR(priv->vdd))
                return PTR_ERR(priv->vdd);
        ret = regulator_enable(priv->vdd);
        if (ret)
                return ret;

        ret = devm_request_irq(&pdev->dev, irq, mydrv_isr, 0,     /* 5. 中断 */
                               dev_name(&pdev->dev), priv);
        if (ret)
                return ret;
        ret = mydrv_register(priv);                              /* 6. 对外注册 */
        if (ret)
                return ret;
        dev_info(&pdev->dev, "probed, irq=%d\n", irq);
        return 0;
}

对应的 remove 短得离谱：

c
static int mydrv_remove(struct platform_device *pdev)
{
        struct mydrv *priv = platform_get_drvdata(pdev);

        mydrv_unregister(priv);
        /* 硬件收尾：先停硬件，再让 devres 撤软件资源 */
        clk_disable_unprepare(priv->clk);
        regulator_disable(priv->vdd);
        reset_control_assert(priv->rst);
        return 0;
}

注意最后三行——devm_ 只管「申请」的配对释放，不管「使用」的配对动作。devm_clk_get() 会在 remove 后自动 clk_put()，但不会替你 clk_disable()。clk_prepare_enable() 是你自己调的，就得自己 clk_disable_unprepare()。这个区分是 devres 理解的分水岭，第十九章再展开。

把托管全换成非托管，probe 会变成这样（省略前半段，重点看错误路径）：

c
        priv = kzalloc(sizeof(*priv), GFP_KERNEL);
        if (!priv) { ret = -ENOMEM; goto err_none; }
        if (!request_mem_region(res->start, resource_size(res), DRIVER_NAME))
                { ret = -EBUSY; goto err_free_priv; }
        priv->base = ioremap(res->start, resource_size(res));
        if (!priv->base) { ret = -ENOMEM; goto err_release_region; }
        priv->clk = clk_get(&pdev->dev, "apb");
        if (IS_ERR(priv->clk)) { ret = PTR_ERR(priv->clk); goto err_iounmap; }
        ret = clk_prepare_enable(priv->clk);
        if (ret) goto err_put_clk;
        ret = request_irq(irq, mydrv_isr, 0, DRIVER_NAME, priv);
        if (ret) goto err_disable_clk;
        ret = mydrv_register(priv);
        if (ret) goto err_free_irq;
        platform_set_drvdata(pdev, priv);
        return 0;

err_free_irq:       free_irq(irq, priv);
err_disable_clk:    clk_disable_unprepare(priv->clk);
err_put_clk:        clk_put(priv->clk);
err_iounmap:        iounmap(priv->base);
err_release_region: release_mem_region(res->start, resource_size(res));
err_free_priv:      kfree(priv);
err_none:           return ret;

七个 goto 标签，每个都要「从正确位置开始回滚」，顺序必须是申请的逆序。这就是第十一章要说的问题。

十一、为什么错误处理会写成 goto 森林 #

原文给了一个真实案例，drivers/media/platform/soc_camera/mx1_camera.c 的 mx1_camera_probe()（3.x 时代代码，该驱动在后续内核里已被移除）：

c
static int __init mx1_camera_probe(struct platform_device *pdev)
{
        ...
        res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
        irq = platform_get_irq(pdev, 0);
        if (!res || (int)irq <= 0) { err = -ENODEV; goto exit; }
        clk = clk_get(&pdev->dev, "csi_clk");
        if (IS_ERR(clk)) { err = PTR_ERR(clk); goto exit; }
        pcdev = kzalloc(sizeof(*pcdev), GFP_KERNEL);
        if (!pcdev) {
                dev_err(&pdev->dev, "Could not allocate pcdev\n");
                err = -ENOMEM; goto exit_put_clk;
        }

        /* Request the regions. */
        if (!request_mem_region(res->start, resource_size(res), DRIVER_NAME)) {
                err = -EBUSY; goto exit_kfree;
        }
        base = ioremap(res->start, resource_size(res));
        if (!base) { err = -ENOMEM; goto exit_release; }

        /* request dma */
        pcdev->dma_chan = imx_dma_request_by_prio(DRIVER_NAME, DMA_PRIO_HIGH);
        if (pcdev->dma_chan < 0) {
                dev_err(&pdev->dev, "Can't request DMA for MX1 CSI\n");
                err = -EBUSY; goto exit_iounmap;
        }

        /* request irq */
        err = claim_fiq(&fh);
        if (err) {
                dev_err(&pdev->dev, "Camera interrupt register failed\n");
                goto exit_free_dma;
        }
        err = soc_camera_host_register(&pcdev->soc_host);
        if (err) goto exit_free_irq;

        dev_info(&pdev->dev, "MX1 Camera driver loaded\n");
        return 0;

exit_free_irq:
        disable_fiq(irq);  mxc_set_irq_fiq(irq, 0);  release_fiq(&fh);
exit_free_dma:
        imx_dma_free(pcdev->dma_chan);
exit_iounmap:
        iounmap(base);
exit_release:
        release_mem_region(res->start, resource_size(res));
exit_kfree:
        kfree(pcdev);
exit_put_clk:
        clk_put(clk);
exit:
        return err;
}

七个标签，对应关系一目了然：

# 申请动作 失败时跳去 该标签释放什么
① platform_get_resource / platform_get_irq / clk_get exit 什么都还没申请
② kzalloc(pcdev) exit_put_clk clk_put(clk)
③ request_mem_region exit_kfree kfree(pcdev)
④ ioremap exit_release release_mem_region
⑤ imx_dma_request_by_prio exit_iounmap iounmap(base)
⑥ claim_fiq exit_free_dma imx_dma_free
⑦ soc_camera_host_register exit_free_irq disable_fiq + release_fiq

这个函数不算长，已经七个标签。为什么非得这么写？因为 C 没有 RAII、没有 defer、没有析构函数。每个资源的释放点必须在申请点的作用域之外，才能被多个失败路径共享。goto 到函数尾部的公共出口是这个约束下唯一还不算太难看的解法。

问题在哪：

一、标签顺序是手写的逆序，漏一个就泄漏。 七个标签严格对应申请的逆序（mem_region → ioremap → dma → irq）。哪天有人在中间插第八个资源申请，他必须记得在正确位置插第八个标签，并检查前面七个 goto 有没有跳到会越界释放的地方。

二、goto 目标容易跳错。 claim_fiq 失败处跳 exit_free_dma——因为 FIQ 没申请成功，不能释放它。这种「跳一个、跳过几个」的判断全靠人对依赖关系心里有数。claim_fiq 和 disable_fiq / release_fiq 这种不对称命名更深一层放大了出错率。

三、成功路径和失败路径不对称。 return 0 从函数中间直接走，跳过所有标签；return err 在 exit: 处。两套出口，任何新增清理动作都要同时考虑两条路。

四、函数越长越是灾难。 10 类资源、15 个申请点，标签数量会到二十几个。读代码的人要在脑子里维护一份栈。

原文的吐槽：

整个函数被大段的、重复的「if (condition) { err = xxx; goto xxx; }」充斥，浪费精力，容易出错，不美观。

这不是风格问题，是结构性重复。每次资源申请都重复了「检查、记录错误码、跳转」这个三元组，而跳转目标的选择依赖前面的顺序。任何一处重复都会出错，而错误的表现是「某种失败情况下资源没释放」——一个你几乎测不到的 bug。

内核社区对这个问题的标准解不是「写得更小心」，而是把释放动作变成数据的属性，而不是控制的属性。

一个澄清：goto 在内核里不是坏东西。Documentation/process/coding-style.rst 专门有一节说「集中式退出」比「多个 return」好。devres 没有消灭 goto 的必要性——在结构体初始化、资源释放混杂的场景下它依然是最佳实践。devres 只是把「资源释放」这一类 goto 的职责接过去了。你去看看 drivers/base/devres.c 自己，照样在用 goto。

十二、devres 要解决什么 #

devres = device resource management，在 drivers/base/devres.c 里。原文开头那句值得复述：

driver 你只管申请就行了，不用考虑释放，我设备模型帮你释放。

实现层面的话：把资源的所有权从「函数的控制流」转移到「设备对象的生命周期」。

用 devres 改写第十一章那个 probe（原文给的版本）：

c
static int __init mx1_camera_probe(struct platform_device *pdev)
{
        ...
        res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
        irq = platform_get_irq(pdev, 0);
        if (!res || (int)irq <= 0)
                return -ENODEV;

        clk = devm_clk_get(&pdev->dev, "csi_clk");
        if (IS_ERR(clk))
                return PTR_ERR(clk);
        pcdev = devm_kzalloc(&pdev->dev, sizeof(*pcdev), GFP_KERNEL);
        if (!pcdev) {
                dev_err(&pdev->dev, "Could not allocate pcdev\n");
                return -ENOMEM;
        }

        /* Request the regions. */
        if (!devm_request_mem_region(&pdev->dev, res->start,
                                     resource_size(res), DRIVER_NAME))
                return -EBUSY;
        base = devm_ioremap(&pdev->dev, res->start, resource_size(res));
        if (!base)
                return -ENOMEM;

        /* request dma */                       /* ← 没有 devm 版本，得自己管 */
        pcdev->dma_chan = imx_dma_request_by_prio(DRIVER_NAME, DMA_PRIO_HIGH);
        if (pcdev->dma_chan < 0)
                return -EBUSY;
        /* request irq */                       /* ← FIQ 同理 */
        err = claim_fiq(&fh);
        if (err)
                return err;
        err = soc_camera_host_register(&pcdev->soc_host);
        if (err)
                return err;
        return 0;
}

函数从 84 行降到 60 行，标签从 7 个降到 0 个，每个 if 后面只剩一句 return。

注意这个改写里藏着一个陷阱：imx_dma_request_by_prio() 和 claim_fiq() 没有 devm 版本（DMA 是私有接口，FIQ 更是特例）。所以这两处失败时，前面三个 devm 资源由框架回收，但这两者得靠自己——上面这段代码实际有 bug（claim_fiq 失败时 DMA 通道没释放，soc_camera_host_register 失败时两者都没释放）。这个例子恰好说明了第二十章的论点：devres 只能管它认识的那部分资源。

改写的机理：

text
devres_alloc(release_fn, size, gfp) → [ struct devres | 私有资源结构 ]
  申请资源失败 → devres_free(drv)，什么都不留
  成功 → devres_add(dev, drv)，挂到 &dev->devres_head 链表尾
remove / probe 失败 / driver unbind → devres_release_all(dev)
  → 逆序遍历链表，逐个调 release_fn，然后 kfree

devres 能做和不能做的事，原文划得很清楚：

资源的种类有很多，表现形式也多种多样，而 devres 没法一一知情，也就不能进行具体的分配和回收。因此，devres 能做的（也是它的唯一功能），就是：提供一种机制，将系统中某个设备的所有资源，以链表的形式，组织起来，以便在 driver detach 的时候，自动释放。

devres 本身不释放任何具体资源。 它只做三件事：分配一块「头部 + 数据」连续内存并记下 release 回调；把这块内存挂到设备链表上；设备解绑时逆序调用回调、释放内存。真正「释放 IRQ / 解除映射 / 归还时钟」的动作，全在上层 framework 的 release 回调里。这种「机制在下、策略在上」的分层，是它能同时服务 IRQ、clock、regulator、gpio、pwm、reset、pinctrl、regmap、ioremap 二十几个 framework 的原因。

哪些东西被抽象成「资源」：

类别 说明 管它的 framework
power 供电 regulator framework
clock 时钟 clock framework
memory 内存，用 kzalloc 分配 内核内存分配器
GPIO 用户和 CPU 交换简单控制/状态 gpiolib
IRQ 触发中断 interrupt framework
DMA 无 CPU 参与的数据传输 dmaengine
虚拟地址空间 ioremap / request_region resource 子系统
其它 PWM / RTC / Reset / pinctrl 各自的 framework

原文还提了一段历史背景，是理解设计动机的关键：

在较早的 kernel 中，系统还不是特别复杂，且各个 framework 还没有成型，因此大多的资源都由 driver 自行维护。但随着系统复杂度的增加，driver 之间共用资源的情况越来越多，同时电源管理的需求也越来越迫切。于是 kernel 就将各个 resource 的管理权收回，基于「device resource management」的框架，由各个 framework 统一管理，包括分配和回收。

注意「电源管理的需求」这半句。资源自动回收的第一驱动力不是省事，而是运行时电源管理。设备 suspend 时要释放非必需资源、resume 时重新申请，如果每次都走一遍完整的申请/释放路径，出错概率乘以挂起/唤醒次数。把释放挂在设备生命周期上，才让电源状态切换在框架层变成可控操作。

十三、devm_ 系列的组织：struct devres 与 devres_head #

资源挂在设备上。struct device 里有两个成员专门给 devres 用：

c
struct device {
        ...
        spinlock_t              devres_lock;
        struct list_head        devres_head;
        ...
}

一个链表头、一把自旋锁。每个设备一条资源链表，这是整个设计的基石：资源的归属是「设备」而不是「驱动」，所以驱动解绑时不需要自己清账。用 spinlock_t 而不是 mutex，因为 devres_release_all() 会在各种上下文被调。

资源节点定义在 drivers/base/devres.c 里（C 文件里，不是头文件）：

c
struct devres {
        struct devres_node              node;
        /* -- 3 pointers */
        unsigned long long              data[]; /* guarantee ull alignment */
};
struct devres_node {
        struct list_head                entry;
        dr_release_t                    release;
#ifdef CONFIG_DEBUG_DEVRES
        const char *name;  size_t size;
#endif
};
typedef void (*dr_release_t)(struct device *dev, void *res);

三个字段：

  • entry：挂到 dev->devres_head 的链表节点
  • release：释放这个资源的回调。devres 不知道资源长什么样，只能回调上层
  • name / size：只在 CONFIG_DEBUG_DEVRES 打开时存在，配合 devres_log() 打日志、检查资源类型

struct devres 定义在 .c 里，这个选择值得学——原文的说法是「尽量屏蔽细节」。翻译成工程语言：这个结构对全内核不可见，所以谁都不能直接 kzalloc(sizeof(struct devres))，头部布局可以随便改，上层 framework 只需要知道「我要一块 size 那么大的地方放我的资源」。对比公开在 ioport.h 里的 struct resource，能看出内核在「什么该暴露」上的判断标准：要被多方读写的结构公开，只被框架自己操作的结构私有。

零长度数组 data[] 是奥妙所在。原文给了一句精准的说明：

node 变量的长度为 3 个指针的长度，而 struct devres 的长度也是 3 个指针的长度。而 data 只是一个标记，当有人分配了大于 3 个指针长度的空间并把它转换为 struct devres 类型的变量后，我们就可以通过 data 来访问多出来的 memory。

sizeof(struct devres) 不含 data，data 是「结构体末尾之后那块内存」的入口。分配时 tot_size = sizeof(struct devres) + size，资源占的空间正好是 tot_size - sizeof(struct devres)，从 dr->data 开始。

为什么不用两块 kmalloc？因为释放只需要一次 kfree(dr)。整个 [头部 | 资源数据] 是一块，dr 指针既是链表载体也是内存分配单位。分成两次分配就多一个出错点。unsigned long long data[] 里的 ull 保证 data 起始地址按 8 字节对齐，往里放任何类型（包括要求 8 字节对齐的 u64、dma_addr_t）都不踩对齐要求。

零长度数组的语法沿革：

写法 年代 说明
data[0] 早期 GNU C GCC 扩展，C99 之前
data[1] 过渡期 hack 浪费一个元素但可移植性好
data[] C99 起标准 flexible array member，现在的正规写法

struct devres 用第三种，sizeof 不含它。

还有 struct devres_group，作用是把一组资源打成可整体释放的单元：

c
struct devres_group { struct devres_node node[2]; void *id; int color; };

关键点：里面有两个 devres_node。挂在链表上时占两个链表项（首尾各一个，中间夹着组内资源），释放时靠这两端标记识别组边界，把中间那一段整体释放。id 是调用方给的组标识，color 用于 WARN 时的诊断输出。

c
struct devres_group *devres_open_group(struct device *dev, void *id, gfp_t gfp);
void devres_close_group(struct device *dev, struct devres_group *group);
void devres_remove_group(struct device *dev, struct devres_group *group);
int devres_release_group(struct device *dev, void *id);

open / close 包住的区间内所有 devres_add 的资源都归到这个组，release_group 整体回滚。典型用法是 probe 的阶段式初始化：中途失败就把这一阶段整个扔掉，不留半成品。

devres_group 很少见，绝大多数驱动作者一辈子不会用。它的存在说明 devres 设计时考虑了「部分回滚」，不只是全清。签名到 6.x 没变（6.1 仍是 devres_open_group(dev, id, gfp)，更新版本未验证）。

十四、devres_add / devres_remove 的机制 #

原文用 IRQ 的实现当样板，这是最好懂的入口。头文件里一个 static inline 转发：

c
/* include/linux/interrupt.h */
static inline int __must_check
devm_request_irq(struct device *dev, unsigned int irq, irq_handler_t handler,
                 unsigned long irqflags, const char *devname, void *dev_id)
{
        return devm_request_threaded_irq(dev, irq, handler, NULL, irqflags,
                                         devname, dev_id);
}

/* kernel/irq/devres.c */
int devm_request_threaded_irq(struct device *dev, unsigned int irq,
                              irq_handler_t handler, irq_handler_t thread_fn,
                              unsigned long irqflags, const char *devname,
                              void *dev_id)
{
        struct irq_devres *dr;
        int rc;

        dr = devres_alloc(devm_irq_release, sizeof(struct irq_devres),
                          GFP_KERNEL);
        if (!dr)
                return -ENOMEM;
        rc = request_threaded_irq(irq, handler, thread_fn, irqflags, devname,
                                  dev_id);
        if (rc) {
                devres_free(dr);
                return rc;
        }
        dr->irq = irq;
        dr->dev_id = dev_id;
        devres_add(dev, dr);
        return 0;
}
EXPORT_SYMBOL(devm_request_threaded_irq);

__must_check 别忘——它让编译器在你忽略返回值时警告。上面这个是所有 devm_* 实现的模板，记住五步，你就能读懂任何一个 devm 接口：

text
① devres_alloc(release_fn, size, gfp)：分配 [devres 头 | 资源结构]，失败返回 -ENOMEM
② 调原来的非托管接口申请资源；失败 → devres_free(dr) 还内存并返回错误
③ 把「释放时需要的信息」填进资源结构（dr->irq、dr->dev_id）
④ devres_add(dev, dr) 挂到设备的资源链表
⑤ 返回 0

第 ③ 步是「资源」的本质。 devres 不知道怎么释放 IRQ，它只会在解绑时调 devm_irq_release(dev, res)，而这个回调需要知道「哪个 irq、哪个 dev_id」才能调 free_irq：

c
/* Device resource management aware IRQ request/free implementation. */
struct irq_devres { unsigned int irq; void *dev_id; };

static void devm_irq_release(struct device *dev, void *res)
{
        struct irq_devres *this = res;
        free_irq(this->irq, this->dev_id);
}

devm_irq_release 只有两行。参数是 void *res 不是具体类型，因为 devres 不知道资源形态——这也是它通用性的来源。回调内部立刻转回具体类型。

第 ② 步的失败处理是关键。 顺序必须是「先 devres_alloc，后申请资源」。反过来的话，资源申请成功而 devres_alloc 失败，你还得单独释放。现在的顺序下，任何一步失败都只需 devres_free()。

c
void * devres_alloc(dr_release_t release, size_t size, gfp_t gfp)
{
        struct devres *dr = alloc_dr(release, size, gfp);
        if (unlikely(!dr))
                return NULL;
        return dr->data;
}
static __always_inline struct devres * alloc_dr(dr_release_t release,
                                                size_t size, gfp_t gfp)
{
        size_t tot_size = sizeof(struct devres) + size;
        struct devres *dr = kmalloc_track_caller(tot_size, gfp);
        if (unlikely(!dr))
                return NULL;
        memset(dr, 0, tot_size);
        INIT_LIST_HEAD(&dr->node.entry);
        dr->node.release = release;
        return dr;
}

kmalloc_track_caller 而不是 kmalloc，是为了让内存追踪报告「调用方」而不是 devres 内部——CONFIG_DEBUG_DEVRES 和 slub debug 才能指出是谁申请的资源。memset 清零保证资源结构初值为 0，INIT_LIST_HEAD 让 devres_add 里的 BUG_ON 能正常工作。

c
void devres_add(struct device *dev, void *res)
{
        struct devres *dr = container_of(res, struct devres, data);
        unsigned long flags;
        spin_lock_irqsave(&dev->devres_lock, flags);
        add_dr(dev, &dr->node);
        spin_unlock_irqrestore(&dev->devres_lock, flags);
}
static void add_dr(struct device *dev, struct devres_node *node)
{
        devres_log(dev, node, "ADD");
        BUG_ON(!list_empty(&node->entry));
        list_add_tail(&node->entry, &dev->devres_head);
}

container_of(res, struct devres, data) 从资源指针反推头部。因为 data 是零长度数组，&dr->data 恰好等于 (char *)dr + sizeof(struct devres)，反推是精确的。

list_add_tail——插到链表尾部。这一行就是第十五章 LIFO 顺序的成因。 BUG_ON 是不变量检查：同一个 devres 不能 add 两次，否则链表就坏了。

移除侧，devm_free_irq 展示了手动释放的做法：

c
void devm_free_irq(struct device *dev, unsigned int irq, void *dev_id)
{
        struct irq_devres match_data = { irq, dev_id };
        WARN_ON(devres_destroy(dev, devm_irq_release, devm_irq_match,
                               &match_data));
        free_irq(irq, dev_id);
}
EXPORT_SYMBOL(devm_free_irq);

三步：构造「待查找的资源」match_data → devres_destroy 从链表里找到并移除对应 devres（找到的话它会调 release 并 kfree）→ 手动 free_irq。

c
void *devres_remove(struct device *dev, dr_release_t release,
                    dr_match_t match, void *match_data);
int devres_destroy(struct device *dev, dr_release_t release,
                   dr_match_t match, void *match_data);

devres_destroy 需要两个函数指针：release 匹配「这是哪类资源」（比函数指针），match 匹配「这是哪一个实例」。devres_remove 只摘链、返回指针；devres_destroy 摘链 + 调 release + kfree。devm_irq_match 就是比 irq 和 dev_id 两个字段。

WARN_ON 包住返回值表示：手动释放一个 devm 资源，说明你走了不正常的路径。devm_free_irq() 之后 devres_release_all 不会再碰它（已摘掉），不会 double free，但它意味着驱动清理逻辑和 devres 预期不一致。

devres 的公开接口：

接口 用途
devres_alloc(release, size, gfp) 分配 devres，返回资源区指针
devres_free(res) 释放还没 add 的 devres
devres_add(dev, res) 挂到设备链表尾
devres_remove(dev, release, match, match_data) 摘链并返回
devres_destroy(dev, release, match, match_data) 摘链 + release + free
devres_release(dev, release, match, match_data) 摘链 + release（不 free）
devres_open_group / close_group / release_group 分组管理
devres_release_all(dev) 全清（设备模型内部调用）

remove / destroy / release 三个用一句话记：都是「摘」，差别在摘完之后——remove 什么都不做，destroy 连内存一起还，release 只调回调不还内存。

十五、devres 的释放时机与顺序 #

这是本篇要重点讲清的两个反直觉之一。

15.1 两个触发点 #

原文说得很明确，devres_release_all() 只在两个地方被调：

text
① probe 失败：__driver_attach / __device_attach → driver_probe_device()
   → really_probe() → 调 driver->probe 失败（返回非零）→ devres_release_all()
② driver detach：driver_detach / bus_remove_device → __device_release_driver()
   → 调 driver->remove → devres_release_all()

没有第三个触发点。 设备热插拔摘除、模块卸载、驱动 unbind，最终都汇聚到 __device_release_driver()。只要驱动走标准注册流程，就一定能被兜住。

对照第十一章的 goto 森林，价值立刻显现：devres 精确覆盖了 goto 森林要处理的两种场景——probe 失败回滚、remove 时释放全部。这两件事被框架一次接过去，那七个标签就没有存在理由了。

15.2 释放顺序：LIFO #

c
int devres_release_all(struct device *dev)
{
        unsigned long flags;
        /* Looks like an uninitialized device structure */
        if (WARN_ON(dev->devres_head.next == NULL))
                return -ENODEV;
        spin_lock_irqsave(&dev->devres_lock, flags);
        return release_nodes(dev, dev->devres_head.next, &dev->devres_head,
                             flags);
}

static int release_nodes(struct device *dev, struct list_head *first,
                         struct list_head *end, unsigned long flags)
        __releases(&dev->devres_lock)
{
        LIST_HEAD(todo);
        int cnt;
        struct devres *dr, *tmp;
        cnt = remove_nodes(dev, first, end, &todo);
        spin_unlock_irqrestore(&dev->devres_lock, flags);
        /* Release.  Note that both devres and devres_group are
         * handled as devres in the following loop.  This is safe. */
        list_for_each_entry_safe_reverse(dr, tmp, &todo, node.entry) {
                devres_log(dev, &dr->node, "REL");
                dr->node.release(dev, dr->data);
                kfree(dr);
        }
        return cnt;
}

release_nodes 做三件事，顺序不能换：① remove_nodes() 持锁把整段搬到局部链表 todo 并从 dev->devres_head 摘掉（缩小持锁时间，也防回调里再注册资源）→ ② spin_unlock_irqrestore 先解锁 → ③ list_for_each_entry_safe_reverse 遍历 todo，_reverse 反向，每个节点调 release 回调再 kfree。

先摘链再释放，先解锁再回调。 两个顺序都为安全：

  • 先摘链：release 回调里若调用 devres_add，还在遍历原链表会把链表改坏
  • 先解锁：release 回调里会 sleep（clk_disable 要等硬件，free_irq 要等正在执行的中断处理完），持自旋锁调用会死

list_for_each_entry_safe_reverse 拆开看：list_for_each_entry 遍历链表项并反推结构体；_safe 多存一个 tmp，允许遍历中 kfree 当前项；_reverse 从尾往头走。

结尾那句注释也值得注意：「both devres and devres_group are handled as devres in the following loop. This is safe.」组的两端标记也被当普通 devres 处理，释放循环只需要一份代码。

15.3 为什么必须是 LIFO #

理由一：构造顺序决定依赖顺序，释放必须逆着来。

probe 里的申请顺序不是乱的，是按依赖排的：

text
申请顺序（依赖层层递进）：           释放顺序（LIFO，依赖的反序）：
1 devm_kzalloc                       mydrv_unregister  ← 先撤对外接口
2 devm_ioremap_resource              free_irq          ← 再撤中断
3 devm_clk_get                       clk_disable       ← 再关时钟
4 clk_prepare_enable                 clk_put
5 reset_control_deassert             iounmap           ← 再解映射
6 devm_request_irq                   kfree(priv)       ← 最后还内存
7 mydrv_register

每个都依赖前一个，释放必须逆着来——这不是「看起来对称」，是正确性的必要条件。 先 kfree(priv) 再 free_irq，中断处理函数里访问 priv 就是 use-after-free。先 iounmap 再 free_irq，ISR 读寄存器会触发总线错误。LIFO 恰好就是「依赖的反序」——依赖按顺序建立，反向就自动满足。这是结构性正确，不依赖作者记性好。

理由二：list_add_tail + 反向遍历 = 自动逆序。

text
devres_head → [A kzalloc] → [B ioremap] → [C clk] → [D irq] → （尾）
_reverse 遍历：D → free_irq, C → clk_put, B → iounmap, A → kfree

如果 add_dr 用 list_add（插头部），链表变成 D → C → B → A，那正序遍历就是正确顺序，代码里就不需要 _reverse。两种写法等价。内核选了「尾部插入 + 反向遍历」，我理解的好处是链表本身保持「申请顺序」这个语义——调试时 devres_log 打印的 ADD 和 REL 顺序一比，就能看出谁先申请谁先释放；头部插入的话链表自然顺序和申请顺序反着，读日志会绕。这个选择属于工程偏好，不影响正确性。

理由三：goto 森林本来就是逆序的。

第十一章那个函数，标签 exit_free_irq → exit_free_dma → exit_iounmap → exit_release → exit_kfree → exit_put_clk → exit，严格逆着申请顺序。devres 的 LIFO 不是新规矩，它只是把 goto 森林里本来就有的隐含规则显式化了。

理由四：devres_group 的存在证明顺序被刻意设计过。 如果释放顺序无关紧要，就不需要「组」这种按区间整体回滚的机制了。

15.4 LIFO 释放顺序示例 #

时刻 动作 devres_head 链表状态（头 → 尾 = 申请顺序）
probe 开始 — 空
① devm_kzalloc 成功 [kzalloc]
② devm_ioremap_resource 成功 [kzalloc] → [ioremap]
③ devm_clk_get 成功 [kzalloc] → [ioremap] → [clk]
④ devm_request_irq 成功 [kzalloc] → [ioremap] → [clk] → [irq]
⑤ mydrv_register 失败 return -EIO
⑥ really_probe 检测到非零返回 调 devres_release_all(dev)
⑦ remove_nodes 整段搬到 todo，devres_head 变空
⑧ 解锁，_reverse 遍历 见下表
步骤 处理节点 release 回调 实际动作 为什么此时能做
1 [irq] devm_irq_release free_irq(irq, dev_id) 驱动还没注册成功，没有外部调用者；中断表里还在，得先撤
2 [clk] devm_clk_release clk_put(clk) 中断已撤，不会再有代码去开时钟
3 [ioremap] devm_ioremap_release iounmap(base) 中断和时钟都撤了，不会再有人读寄存器
4 [kzalloc] devm_kmalloc_release kfree(priv) 最后一步，所有引用者都已停止

顺序反了会怎样：

错误顺序 后果
先 kfree(priv) 后 free_irq ISR 拿 dev_id = priv 访问已释放内存 → use-after-free，小概率 Oops
先 iounmap 后 free_irq ISR 读寄存器时页表已撤 → 外部中止 / Oops
先 clk_put 后 free_irq ISR 触发时时钟已关，读寄存器会挂总线
先 kfree 后 iounmap 多半没事（iounmap 不需要 priv），但 release 回调若要用其他数据就出问题

前三条不是理论风险。这类 bug 在你压力测试里不出现，在客户现场跑两个月才 Oops 一次，因为需要恰好命中「ISR 正在执行的那一刻资源被释放」。LIFO 把这些都消掉了。

remove 路径顺序完全一样，只是触发点在 __device_release_driver()。注意它是先调 drv->remove()，再调 devres_release_all()——你写在 remove 里的清理代码先跑，然后框架兜底释放剩余的 devm 资源。

15.5 版本差异（必需标注） #

改动一：devres_head 初始化检查。 3.x 里那个 if (WARN_ON(dev->devres_head.next == NULL)) 依赖 kzalloc 全零初值，属于脆弱假设。4.x 换成了 list_empty() 之类的判法（4.19 的 devres.c 已不是这种写法，替换版本与写法未验证）。

改动二：release_nodes 的签名与加解锁位置。 3.x 的 release_nodes(dev, first, end, flags) 带 __releases(&dev->devres_lock) 注解，意思是「调用时持锁、返回时已解锁」，因此调用方不能再解锁。4.x 之后把「解锁」挪到了更靠前的位置，devres_release_all 的返回值处理也有微调。语义没变：先摘链、再解锁、后回调。代码级 diff 未验证。

改动三：返回值的用法。 返回被释放的节点数 cnt。3.x 调用方基本不看；5.x 之后 __device_release_driver 对返回值有一处日志处理，未验证细节。

改动四：与 PM 的关系。 5.x 之后 devm_ 资源在 runtime_suspend / system_suspend 路径上不会被释放——devres_release_all 只在 detach 时调，到 6.x 都没变。别指望 devres 帮你做 suspend 时的资源回滚，那是 dev_pm_ops 的活。

十六、devm_kzalloc 与它的兄弟 #

c
void *devm_kzalloc(struct device *dev, size_t size, gfp_t gfp);
void *devm_kmalloc(struct device *dev, size_t size, gfp_t gfp);
void *devm_kmalloc_array(struct device *dev, size_t n, size_t size, gfp_t flags);

和非托管版一一对应：

非托管 托管版本 行为差异
kzalloc(size, gfp) devm_kzalloc(dev, size, gfp) 清零；设备 detach 时自动 kfree
kmalloc(size, gfp) devm_kmalloc(dev, size, gfp) 不清零
kmalloc_array(n, size, gfp) devm_kmalloc_array(dev, n, size, gfp) 带乘法溢出检查
kcalloc(n, size, gfp) devm_kcalloc(dev, n, size, gfp) 清零 + 溢出检查（5.x 才有，版本未验证）
kmemdup(src, len, gfp) devm_kmemdup(dev, src, len, gfp) 拷贝一份

实现非常薄：

c
static void devm_kmalloc_release(struct device *dev, void *res) { /* noop */ }

void *devm_kmalloc(struct device *dev, size_t size, gfp_t gfp)
{
        struct devres *dr = alloc_dr(devm_kmalloc_release,
                      size + sizeof(struct devres) - sizeof(*dr), gfp);
        if (unlikely(!dr))
                return NULL;
        devres_add(dev, dr->data);
        return dr->data;
}
static inline void *devm_kzalloc(struct device *dev, size_t size, gfp_t gfp)
{
        return devm_kmalloc(dev, size, gfp | __GFP_ZERO);
}

devm_kmalloc_release 是空的（/* noop */）。因为内存释放就是 kfree(dr)，而那一步已经在 release_nodes 的循环里做了。mem 类是唯一「release 回调为空」的一类资源。

存疑点：devm_kmalloc 传的 size + sizeof(struct devres) - sizeof(*dr) 和 alloc_dr 内部的 sizeof(struct devres) + size 之间的平衡关系，不同版本写法不同（有些版本直接传 size）。读源码时以你手上的版本为准，这里给的是常见形态，不保证逐字一致（未验证）。 行为等价：最终分配 sizeof(struct devres) + size。

devm_kzalloc 的两个限制。

限制一：释放时机是整个设备生命周期，不是函数作用域。 在 probe 里 devm_kzalloc 一块临时缓冲区，指望出了函数自动释放——不会，它一直活到 remove。

限制二：devm_kfree 能用，但少用。 void devm_kfree(struct device *dev, const void *p); 会找到对应 devres 节点并释放。问题是：用了 devm_kfree 就说明你的资源生命周期和设备不一致，这基本是设计问题的信号。常见场景是「probe 里为探测硬件分配了临时 buffer，探测完就还」，这时更清晰的做法是用非托管 kzalloc + kfree 包在局部。

一个真实驱动里很常见的反模式：

c
/* 错误示范：probe 里用 devm_kzalloc 分配固件缓冲区 */
fw = devm_kzalloc(&pdev->dev, fw_size, GFP_KERNEL);
ret = request_firmware_into_buf(&fw_desc, name, fw, fw_size);
if (ret)
        return ret;
parse_hw(fw);
/* 忘了释放，fw 一直占着，直到 remove */

几百 KB 的固件缓冲区在整个设备生命周期里白占着，只因为用了 devm_ 觉得「不用管」。托管不等于免费。

十七、devm_request_irq / devm_ioremap_resource #

17.1 devm_request_irq #

c
static inline int __must_check
devm_request_irq(struct device *dev, unsigned int irq, irq_handler_t handler,
                 unsigned long irqflags, const char *devname, void *dev_id);

六个参数和非托管版完全一致，只在前面多了 dev。这是 devm 系列的统一设计原则，原文说得很清楚：

为了保持兼容，这些新接口和旧接口的参数保持一致，只是名字前加了「devm_」，并多加一个 struct device 指针。

所以不需要记两套 API，把 devm_ 剥掉就是熟悉的老接口。dev_id 的选择再强调：共享中断必须能反查设备，非共享建议传 priv（ISR 要用）。release 回调最终调 free_irq(this->irq, this->dev_id)，和手动 free_irq 是同一个释放路径，没有额外开销。

中止某个阶段时，直接 return 而不是手动 devm_free_irq，理由：返回错误后 really_probe 会调 devres_release_all()，按 LIFO 顺序释放全部资源，顺序自动正确。手动 devm_free_irq 先释放了 IRQ，LIFO 顺序就断了，后面的资源若有依赖，你得自己保证顺序没问题。只有「probe 后续还要继续跑、只是某一部分要回退」时才需要手动释放。

17.2 devm_ioremap 与 devm_ioremap_resource #

devm_ioremap_resource 一个 struct resource * devm_request_mem_region + devm_ioremap 首选，DT 驱动标准写法

c
void __iomem *devm_ioremap_resource(struct device *dev, struct resource *res)
{
        void __iomem *dest_ptr;

        if (!res) {
                dev_err(dev, "invalid resource\n");
                return ERR_PTR(-EINVAL);
        }
        if (!devm_request_mem_region(dev, res->start, resource_size(res),
                                     dev_name(dev))) {
                dev_err(dev, "can't request region for resource %pR\n", res);
                return ERR_PTR(-EBUSY);
        }
        dest_ptr = devm_ioremap(dev, res->start, resource_size(res));
        if (!dest_ptr) {
                dev_err(dev, "ioremap failed for resource %pR\n", res);
                return ERR_PTR(-ENOMEM);
        }
        return dest_ptr;
}

（常见形态，5.x 里加了 IORESOURCE_MEM 类型检查和 IORESOURCE_REG 特殊处理，逐字未验证。）

三个要点：

返回值是 ERR_PTR，不是 NULL。 必须用 IS_ERR() 判断：

c
priv->base = devm_ioremap_resource(&pdev->dev, res);
if (IS_ERR(priv->base))
        return PTR_ERR(priv->base);

对比 ioremap() 返回 NULL、request_mem_region() 返回 NULL，三种错误约定混在一起，那是 API 不统一的年代。devm_ioremap 返回的还是 NULL，只有 devm_ioremap_resource 用 ERR_PTR，这两个别搞混。 写 if (!base) 判断 devm_ioremap_resource 的结果，会把 ERR_PTR(-EBUSY) 那个非零指针当成成功。

它内部已经做了 devm_request_mem_region。 用它之后不要再来一次，否则第二次会因第一次已占座而返回 NULL，你以为是冲突其实是重复申请。

%pR 是 struct resource 的专用格式符，打印形如 [mem 0x1c28000-0x1c283ff]，比手写 0x%x-0x%x 安全（能处理 64 位地址和未知 resource）。

什么时候用 devm_ioremap 而不是 devm_ioremap_resource？同一物理区间被多个设备共享映射时（一个 syscon 寄存器块被三个功能块各映射一部分）——只能有一个设备去 request_mem_region，其他用 devm_ioremap。更规范的新做法是 syscon_regmap_lookup_by_phandle() + regmap，不自己 ioremap。

regmap 的地位：4.x 之后，SoC 驱动写寄存器的标准做法不再是裸 ioremap + readl/writel，而是 devm_regmap_init_mmio()。它把位域读写、缓存、锁、debugfs（/sys/kernel/debug/regmap/ 能看到所有寄存器）全包了。本篇的 ioremap 路径是为讲清资源获取，真实驱动该用 regmap，它自己也有 devm 版本，同样挂在 devres 上。

十八、devm_clk_get / devm_regulator_get 这类托管 #

原文给的接口清单，按 framework 归类并补齐用法。

18.1 时钟 #

devm_clk_get(dev, id)、devm_clk_get_optional(dev, id)、devm_clk_put(dev, clk)、devm_clk_prepare_enable(dev, clk)。

id 是 DT 里 clock-names 中的名字。clocks = <&ccu 12>, <&ccu 13>; clock-names = "apb", "axi"; 对应 devm_clk_get(&pdev->dev, "apb")。

devm_clk_get 的托管范围只有 clk_put：

text
devm_clk_get()       → 拿到句柄，自动配 clk_put()
clk_prepare_enable() → 开启时钟，需要你手动 clk_disable_unprepare()

c
priv->clk = devm_clk_get(&pdev->dev, "apb");
if (IS_ERR(priv->clk))
        return PTR_ERR(priv->clk);
ret = clk_prepare_enable(priv->clk);
if (ret)
        return ret;

/* remove 里 */
clk_disable_unprepare(priv->clk);
/* 不用 clk_put，devm 会做 */

devm_clk_prepare_enable() 把 prepare + enable 也托管，失败时自动 clk_disable_unprepare（5.x 引入，版本未验证）。devm_clk_get_optional() 用于「时钟可有可无」的情形——DT 里没写 clocks 时返回 NULL 而不是 -ENOENT（5.x 引入，版本未验证）。

18.2 regulator #

devm_regulator_get(dev, id)、devm_regulator_get_optional(dev, id)、devm_regulator_put(regulator)、devm_regulator_bulk_get(dev, num_consumers, consumers)。

DT 里 vdd-supply = <&reg_1v8>; 对应 devm_regulator_get(&pdev->dev, "vdd")。命名约定要记：DT 属性名是 <id>-supply，devm_regulator_get(dev, "vdd") 找的就是 vdd-supply。传 "vdd-supply" 反而找不到——-supply 后缀是框架自动加的。

同样只托管 regulator_put，enable / disable 要自己配对。devm_regulator_bulk_get() 一次拿一组，配合 struct regulator_bulk_data { .supply = "vdd" } 数组使用。

18.3 GPIO #

devm_gpio_request(dev, gpio, label) / devm_gpio_free(dev, gpio) 是老接口；5.x 起推荐描述符版 devm_gpiod_get(dev, con_id, flags)、devm_gpiod_get_optional(dev, con_id, flags)、devm_gpiod_put(dev, desc)。

原文列的是 devm_gpio_request()，那是老的整数 GPIO 接口，5.x 起需 CONFIG_GPIOLIB_LEGACY。新代码用描述符接口：

c
priv->reset_gpio = devm_gpiod_get(&pdev->dev, "reset", GPIOD_OUT_LOW);
if (IS_ERR(priv->reset_gpio))
        return PTR_ERR(priv->reset_gpio);
gpiod_set_value(priv->reset_gpio, 1);

con_id 对应 DT 里 <name>-gpios 或 <name>-gpio。GPIOD_OUT_LOW 表示申请时配置为输出并拉低。devm_gpiod_get 只是拿描述符，占引脚的动作在 gpiod_get 内部已经做了；但你拉高的那个电平，框架不管，remove 里要自己拉回安全状态。GPIO 细节见《GPIO/pinctrl 与 I2C》。

18.4 pinctrl #

devm_pinctrl_get(dev)、devm_pinctrl_put(p)、devm_pinctrl_lookup_state(p, name)、devm_pinctrl_select_state(p, s)，以及内联包装 devm_pinctrl_get_select(dev, name)。

原文列的是 devm_pinctrl_get_select，这是「get + 找状态 + select」三步合一的内联包装，多数 SoC 驱动用它（或 devm_pinctrl_get_select_default）。

pinctrl 的特殊情况：DT 里没写 pinctrl-* 属性时，devm_pinctrl_get 返回 -ENODEV。「没有 pinctrl 配置」是合法状态（引脚已由 bootloader 配好），应该把 -ENODEV 当成功处理。写 if (IS_ERR(p)) return PTR_ERR(p); 会让一批本来能跑的设备 probe 失败。

18.5 reset 与 PWM #

devm_reset_control_get / _optional / _exclusive / _shared，签名都是 (struct device *dev, const char *id)；devm_pwm_get(struct device *dev, const char *consumer) 与 devm_pwm_put(struct device *dev, struct pwm_device *pwm)。

devm_reset_control_get() 在 5.x 被拆成 _exclusive / _shared 两版，老名字保留为兼容包装（版本未验证，5.10 已是新名字为主）。assert() / deassert() 依然要自己配对。pwm_enable() / pwm_disable() 同理。

18.6 汇总表 #

资源 取用接口（devm） 托管了什么 没托管什么（要自己配对）
内存 devm_kzalloc / devm_kmalloc 内存释放 —
寄存器映射 devm_ioremap_resource request_mem_region + ioremap —
中断 devm_request_irq free_irq —
时钟 devm_clk_get clk_put clk_disable_unprepare
供电 devm_regulator_get regulator_put regulator_disable
GPIO devm_gpiod_get gpiod_put（含释放引脚） 引脚电平状态
pinctrl devm_pinctrl_get pinctrl_put 恢复默认状态的时机

最后两行是重点，也是第二十章的铺垫。「资源」和「对象注册」是两回事：devm_clk_get 拿的是资源句柄，句柄本身归框架回收；而 devm 世界里没有 devm_register_netdev、devm_register_cdev、devm_register_input_device 这类接口，因为你把对象暴露给了外部，外部就有引用，框架无法单方面撤销。所以 mydrv_register(priv) 永远要自己写 unregister，而且必须放在 remove 最前面。

中间那一列有个共同模式：「拿句柄」是资源，「改变状态」是动作。句柄的生命周期能挂在设备上，状态的生命周期必须由驱动管，因为「什么时候该开时钟」「什么时候该拉 GPIO」是业务逻辑，框架无从知道。

十九、能不能在 devres 里放自己的东西：devm_add_action #

能。这是 devres 最实用的扩展点。

c
int devm_add_action(struct device *dev, void (*action)(void *), void *data);
int devm_add_action_or_reset(struct device *dev,
                             void (*action)(void *), void *data);
void devm_remove_action(struct device *dev, void (*action)(void *), void *data);

这三个接口在 3.13 前后引入（未验证具体版本），作用是把任意函数注册成「设备 detach 时调用」。devm_add_action 干的活：分配一个 devres，资源结构里存 action 和 data 两个指针，release 回调是内部的 devm_action_release()，它取出 action 和 data 调用 action(data)。

这个接口把 devres 从「框架专用的内部机制」变成了「所有驱动可用的通用工具」。 原文（成文于 2014 年）没有提到它，但它是理解 devres 完整能力的关键：任何「申请-释放」配对，都能用 devm_add_action 包装成托管资源。

c
static void mydrv_dma_release(void *data)
{
        struct mydrv *priv = data;
        if (priv->dma_chan)
                dma_release_channel(priv->dma_chan);
}
/* probe 里： */
        priv->dma_chan = dma_request_chan(&pdev->dev, "rx");
        if (IS_ERR(priv->dma_chan))
                return PTR_ERR(priv->dma_chan);
        ret = devm_add_action_or_reset(&pdev->dev, mydrv_dma_release, priv);
        if (ret)
                return ret;
        /* 之后任何一处失败 return，DMA 通道都会被自动释放 */

devm_add_action_or_reset 比 devm_add_action 好用，区别在注册失败时：

  • devm_add_action 失败 → 你自己回滚（action 没注册上，不会自动调）
  • devm_add_action_or_reset 失败 → 框架立即调用一次你的 action，替你把刚申请的资源还掉

所以上面那段里 devm_add_action_or_reset 返回错误时 return ret 是安全的。用 devm_add_action 就得手动补一个 dma_release_channel()。新代码一律用 _or_reset。

devm_remove_action() 用于「我提前手动释放了，把登记撤销掉」，action 和 data 两个参数都要精确匹配。

把 devm_add_action 用起来，第十一章那个例子就能彻底清干净（原文那个 devm 版本漏了 DMA 和 FIQ）：

c
static void mx1_release_dma(void *data)
{
        struct mx1_camera_dev *pcdev = data;
        imx_dma_free(pcdev->dma_chan);
}
static void mx1_release_fiq(void *data)
{
        struct mx1_camera_dev *pcdev = data;
        disable_fiq(pcdev->fiq_irq);  mxc_set_irq_fiq(pcdev->fiq_irq, 0);
        release_fiq(&pcdev->fh);
}
/* probe 里：先 devm_kzalloc 拿到 pcdev，后面每一步都只需 return err */
        pcdev->dma_chan = imx_dma_request_by_prio(DRIVER_NAME, DMA_PRIO_HIGH);
        if (pcdev->dma_chan < 0)
                return -EBUSY;
        err = devm_add_action_or_reset(&pdev->dev, mx1_release_dma, pcdev);
        if (err)
                return err;
        err = claim_fiq(&pcdev->fh);
        if (err)
                return err;                    /* DMA 会被自动释放 */
        pcdev->fiq_irq = irq;
        err = devm_add_action_or_reset(&pdev->dev, mx1_release_fiq, pcdev);
        if (err)
                return err;
        err = soc_camera_host_register(&pcdev->soc_host);
        if (err)
                return err;                    /* FIQ 和 DMA 都被自动释放 */

七个标签彻底消失。逐项对照：

原 goto 标签 替代方案 LIFO 释放位置
exit_put_clk devm_clk_get 1（最先申请，最后释放）
exit_kfree devm_kzalloc 2
exit_release devm_request_mem_region 3
exit_iounmap devm_ioremap 4
exit_free_dma devm_add_action_or_reset(mx1_release_dma) 5
exit_free_irq devm_add_action_or_reset(mx1_release_fiq) 6（最后申请，最先释放）
exit return err 直接退出 —

注意 LIFO 自动给出的顺序恰好和原 goto 标签顺序一致：FIQ 先释放、然后 DMA、ioremap、mem_region、kfree、clk_put。不是巧合——手写 goto 的标签顺序本来就是「申请逆序」，LIFO 就是这个顺序。

上面代码有个细节：devm_add_action 的 data 指针必须指向 detach 时还活着的内存。如果你传 probe 里的栈上局部变量，probe 返回后栈就没了，detach 时回调访问它是野指针。这是 devm_add_action 最危险的用法错误。正确做法二选一：

c
/* 方案 A：状态放进 devm 分配的结构体 */
struct mx1_fiq_ctx *fctx = devm_kzalloc(&pdev->dev, sizeof(*fctx), GFP_KERNEL);
devm_add_action_or_reset(&pdev->dev, mx1_release_fiq, fctx);

/* 方案 B：状态放进驱动私有数据（本身是 devm 分配的） */
struct mx1_camera_dev *pcdev = devm_kzalloc(...);
pcdev->fiq_irq = irq;
pcdev->fh = fh;
devm_add_action_or_reset(&pdev->dev, mx1_release_fiq, pcdev);

方案 B 有顺序耦合：devm_add_action 必须在 devm_kzalloc(priv) 之后注册，才能保证 detach 时「action 先跑，priv 后释放」（LIFO）。先 devm_add_action(priv) 再 devm_kzalloc(priv)，priv 会先被 kfree，然后回调访问野指针。

LIFO 在这里既救你也害你——顺序对了它保你，顺序错了它坑你。规矩记死：devm_add_action 的 data 若指向某个 devm 资源，必须在该资源申请之后注册 action。

二十、devres 的局限：不是所有资源都能托管 #

devres 看起来万能，实际有一堆明确的边界。

局限一：只覆盖设备生命周期，不覆盖函数作用域。 devm_kzalloc 的内存活到 remove，不是活到 probe 结束。

局限二：对已暴露给外部的对象无能为力。 net_device、cdev、input_dev、i2c_adapter、spi_master、backlight_device、device_create 创建的字符设备——这些都注册进了内核全局表，有别的模块、别的进程持有引用，框架不能单方面删掉。所以 remove 里的手工清理一样都不能少：

c
static int mydrv_remove(struct platform_device *pdev)
{
        struct mydrv *priv = platform_get_drvdata(pdev);

        unregister_chrdev_region(priv->devt, 1);   /* 先撤对外 */
        cdev_del(&priv->cdev);
        del_timer_sync(&priv->timer);              /* 停定时器 */
        cancel_work_sync(&priv->work);             /* 停工作队列 */
        return 0;
}

devm 只帮你省掉「资源句柄」那一半。

局限三：顺序由 LIFO 决定，无法干预。 有些资源的释放顺序不能只靠申请的逆序（A→B 申请，但 C 必须在 A 之前释放，而 C 申请得更早）。这时只能用 devres_open_group / release_group 手动划分阶段，或者退回非托管接口加显式 remove。

局限四：不能做 probe 中段回滚（除非用 group）。 devres_release_all 是全清。devres_open_group + devres_release_group 能做到阶段回滚，但用的人不多，因为它把「阶段划分」这个隐式信息显式化了，可读性反而下降。

局限五：release 回调会被调在不合适的上下文。 devres_release_all() 除了 detach 路径，还会从 driver unbind（echo xxx > /sys/bus/platform/drivers/xxx/unbind）触发，那是进程态、可以 sleep。但某些框架会在原子路径上触发 detach，你的回调里如果调了会 sleep 的函数（kmalloc(GFP_KERNEL)、clk_prepare）就出问题。规矩：release 回调里只用不会 sleep 的操作。

局限六：没有编译期检查。 devm_request_irq 有 __must_check，很多 devm 接口没有。忘了检查返回值，编译不报错，运行时拿着 ERR_PTR 当正常指针用，报错位置离出错点很远。

局限七：probe 必须可重入。 用 devres 之后 probe 失败一定是 return 负数。返回 -EPROBE_DEFER 时 really_probe 会调 devres_release_all 把这一轮申请的资源清干净，等依赖就绪后重新 probe。这意味着每次进来状态都得是干净的，不能依赖「上次执行到哪」的残留。不能重入的 probe 在 defer 场景下会出各种诡异问题（资源泄漏、重复注册），这是 4.x 之后大量驱动被重构的原因。

局限八：不解决硬件状态。 devres 释放的只是软件资源：内存、映射、句柄、中断。硬件的物理状态（GPIO 电平、复位线、电源输出、外设内部寄存器）不归它管。reset_control_deassert(priv->rst) 拉高复位后，devm_reset_control_get 会在 detach 时 reset_control_put，但不会 reset_control_assert。不手动 assert 的话，设备 remove 之后硬件还活着：中断没关的话还在产生、DMA 还在搬数据、时钟还在供给。再 probe 一次时硬件不是从复位态起步，会读到脏状态。

remove 里必须做的硬件收尾：

c
/* 1. 先让硬件停止活动 */
writel(0, priv->base + REG_CTRL);
reset_control_assert(priv->rst);

/* 2. 再撤软件资源（这几项 devm 会做） */

顺序不能反。先撤软件再停硬件，硬件还在活动时它的中断会打到已释放的句柄上。

局限九：老接口已被废弃。 devm_gpio_request 需 CONFIG_GPIOLIB_LEGACY；devm_request_and_ioremap() 被 devm_ioremap_resource 取代（3.12 前后废弃，版本未验证）。看老代码遇到不认识的 devm 接口，先在 include/linux/*.h 里 grep 它还在不在。

局限十：devres 内部结构不能直接用。 struct devres 定义在 .c 里，没法继承、没法外部 kzalloc、没法直接操作 node.entry。所有对 devres 的操作必须走 devres_* 接口，包括 devm_add_action 这条通用通道。发现自己在想办法绕过这些接口，说明框架没提供你要的功能，应该提 patch。

汇总：

情况 devm 可用 该用什么
内存分配 是 devm_kzalloc
寄存器映射 是 devm_ioremap_resource
中断 是 devm_request_irq
时钟/电源/reset/pwm 句柄 是 devm_clk_get 等
时钟使能/电源使能等状态 否 手动配对（或 devm_clk_prepare_enable）
自建资源的释放 是 devm_add_action_or_reset
子系统对象注册（netdev/cdev/input） 否 手动 unregister，放 remove 最前
硬件寄存器状态 否 手动写寄存器
GPIO 电平 否 手动设回安全值
probe 中段局部临时内存 不建议 非托管 kzalloc/kfree

二十一、platform 与设备树的配合 #

21.1 完整链路 #

text
DTS → dtc 编译 → DTB → bootloader 加载，把地址传给内核
  → unflatten_device_tree()  建立 device_node 树
       （/sys/firmware/devicetree/base 可见）
  → of_platform_populate(NULL, of_default_bus_match_table, NULL, NULL)
  → platform_device 数组（每个有 of_node 指针 + resource 数组）
  → platform_device_add() → device_add()
  → /sys/devices/platform/<name>/   设备已在设备模型里，等驱动
  → platform_driver_register() → driver_register() → driver_attach()
  → platform_match(dev, drv)：of_driver_match_device() 比 compatible
  → really_probe() → platform_drv_probe() → 你的 mydrv_probe(pdev)
  → probe 里 devm_* 申请资源，挂到 dev->devres_head

/sys/firmware/devicetree/base 值得记：整个 DT 以目录树形式暴露，每个节点一个目录，每个属性一个文件。compatible 是字符串数组、用 \0 分隔，直接 cat 会连成一片，要用 hexdump -C。老内核里这个路径是 /proc/device-tree。

21.2 从 DT 拿数据的接口 #

platform 设备进到 probe 后，除 resource 和中断之外的数据都得自己从 of_node 读：

数据类型 接口 例子
单个整数 of_property_read_u32(np, "prop", &val) <prop = <0x100>>;
整数数组 of_property_read_u32_array <prop = <1 2 3>>;
字符串 of_property_read_string <prop = "abc">;
布尔标志 of_property_read_bool(np, "prop") <prop;>
子节点 of_get_child_by_name / for_each_child_of_node 嵌套节点
phandle 引用 of_parse_phandle / of_parse_phandle_with_args <prop = <&other 12>>;

21.3 两种来源共存的判断 #

c
        if (pdev->dev.of_node) {
                ret = of_property_read_u32(pdev->dev.of_node, "vendor,freq", &freq);
                if (ret)
                        return ret;
        } else {
                pdata = dev_get_platdata(&pdev->dev);

dev_get_platdata() 拿的是 dev->platform_data。这个字段在 5.x 之后只允许板级代码用，DT 驱动不许碰（Documentation/driver-api/driver-model/platform.rst 明确写了新驱动不要用 platform_data）。上面那个 else 分支是历史包袱，新驱动只留 DT 路径。

21.4 fw_devlink：5.2+ 的时序变化 #

3.x 的 probe 时序是「谁先注册谁先 probe」，没有依赖概念。你的驱动依赖一个 regulator 而它的驱动还没 probe，只能靠 -EPROBE_DEFER 反复重试。复杂的 SoC 启动时能看到几十次 defer。

5.2 引入了 fw_devlink（CONFIG_FW_DEVLINK），从 DT 的依赖关系（clocks、power-domains、*-supply、phys 等属性）自动建立 device_link，让 driver core 按依赖顺序 probe，把大部分 defer 消掉：

c
int device_link_add(struct device *consumer, struct device *supplier, u32 flags);
void device_link_del(struct device_link *link);

flags 里有 DL_FLAG_AUTOREMOVE_CONSUMER、DL_FLAG_AUTOREMOVE_SUPPLIER 等，控制 consumer/supplier 销毁时机如何联动。

对写 platform 驱动的影响：

  • 5.2+ 里 DT 写得正确的话，probe 顺序基本不用管了
  • DT 漏写依赖（clocks 没写而代码却 clk_get 了）会导致依赖建立不起来，又退回靠 defer 重试
  • -EPROBE_DEFER 依然要正确处理，fw_devlink 只是减少次数，不是消灭
  • 5.x 的 platform_match() 因此多了前置检查（具体代码未验证）

fw_devlink 的完整行为（5.2 引入、后续小版本多次调整默认值、6.x 的 fw_devlink.strict 等）未验证，展开需要单独一篇。只提醒：升到 5.2+ 后 probe 顺序和 3.x 行为不同，遇到时序问题先看 /sys/kernel/debug/devices_deferred 和 dmesg | grep -i devlink。

21.5 platform 和别的总线在 DT 里的分工 #

dts
soc {
        compatible = "simple-bus";         /* ← 递归边界，platform 继续往下 */
        ranges;

        i2c0: i2c@1c2b000 {
                compatible = "vendor,myi2c";    /* ← platform_device */
                reg = <0x1c2b000 0x400>;

                eeprom@50 {
                        compatible = "atmel,24c02";  /* ← i2c_client，不是 platform */
                        reg = <0x50>;
                };
        };

        gpio0: gpio@1c20800 {
                compatible = "vendor,mygpio";   /* ← platform_device */
                gpio-controller;
                #gpio-cells = <2>;
                interrupt-controller;
                #interrupt-cells = <2>;
        };
};
DT 节点类型 变成什么 谁负责创建 匹配依据
simple-bus 下的普通节点 platform_device of_platform_populate compatible → of_match_table
I2C 控制器下的节点 i2c_client I2C 控制器驱动 probe 时 of_i2c_register_devices compatible → i2c_device_id
SPI 控制器下的节点 spi_device SPI 控制器驱动 of_register_spi_devices compatible → spi_device_id
GPIO 控制器 platform_device of_platform_populate compatible
interrupt-controller irq_domain 的提供者 驱动自己 irq_domain_add_* compatible
gpio-controller gpiochip 驱动自己 devm_gpiochip_add_data —
phy 节点 phy_device phy framework compatible

判据始终是那一条：CPU 能不能直接寻址它的寄存器。 I2C 上的 EEPROM 不能（要经过控制器发时序），所以不是 platform；gpio0 的寄存器 0x1c20800 直接映射，所以是。

四、写作取舍 #

优先信源码，不神化原文。 素材给了结构体和函数的原文片段（struct platform_device、struct platform_driver、struct devres、devres_release_all、release_nodes、alloc_dr、devres_add、devm_request_threaded_irq、platform_bus_init、platform_bus_type、early platform 接口全表），这些按原样保留并注明出处。原文没给的（struct resource 全字段、platform_match 四条路径、of_platform_populate 流程、devm_add_action 语义、各 framework 的 devm 变体）按通行实现补齐，并在「未验证项」表登记。

两个「反直觉」是这篇文章的主干。 第五章讲第一个：platform_bus 的 match 只比字符串和查表，四次比较里没有一次碰硬件，这和 USB/PCI「枚举后比对描述符」是两种完全不同的范式。第十五章讲第二个：devres 的 LIFO 释放不是「顺手写成这样」，而是「构造顺序 = 依赖顺序，释放必须反序」这个正确性约束在数据结构上的体现——list_add_tail + _reverse 遍历这两行代码，是整个 devres 能成立的前提。理解这两点，platform 和 devres 就不需要背 API 了。
