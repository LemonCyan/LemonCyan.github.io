这里讲两段：软件侧的 DMA 子系统，硬件侧的 PCIe 总线；加上一条把两者串起来的完整链路。不涉及 dmaengine 的 provider/consumer 编程、设备树 dmas 属性、probe() 的 devres 生命周期，这些各有专篇。内核版本按 4.20+ 为准，dma-direct 是 4.20 才引入的架构。

一、DMA 是什么：让外设绕开 CPU 搬数据 #

DMA 是 Direct Memory Access，直接内存访问。它指绕开 CPU，在 memory 与 memory、memory 与设备之间直接搬运数据。它不提升算力，只是把「搬数据」这件事从 CPU 手里拿走。这个定义有个容易忽略的后果：DMA 搬运的发起者是设备，不是 CPU。CPU 只负责在开工前把地址和长度写进某个寄存器，写完就退场。所有「设备能不能访问这块内存」「设备看到的是哪个地址」的问题，都在这一刻之前定死了，搬起来之后软件已经没有插手余地。

二、为什么需要 DMA：一次拷贝的开销 #

CPU 与外设的速度差着几个数量级。串口每毫秒才来一个字节，而 CPU 在这 1ms 里能执行上百万条指令。若由 CPU 逐字节搬 1KB，绝大部分时间都耗在轮询状态寄存器和读写数据寄存器上。这些等待还是不可抢占的，实时任务会被直接拖垮。

DMA 控制器的做法是：CPU 只下达一条「把 A 搬到 B，共 N 字节」的指令，然后立刻返回干别的；控制器自己在总线上完成搬运，结束时用中断通知 CPU。搬 4KB 数据对 CPU 的占用从数万条指令降到一次配置加一次中断处理。把这笔开销摊开看：非 DMA 路径每个字节要付「读状态寄存器、读数据寄存器、写目标、更新指针、循环」，每条指令都是一次访存；DMA 路径的成本是固定的，一次寄存器写入序列加一次中断。

三、DMA 控制器的硬件模型 #

各个厂商的 DMA 控制器细节不同，但职责高度一致，正是这种一致性让内核能用一套 dmaengine framework 去抽象它们。

职责 说明
通道管理 维护若干 channel，给发起方分配与仲裁
地址生成 每个传输周期推进源/目的地址，按 width 增减
突发组织 把多个小传输合成一次总线事务，减少仲裁开销
传输计数 搬够 size 个字节自动停止，或按周期循环
完成通知 传输结束（或每传一个 period）产生中断

控制器不参与数据内容，它只认地址与长度。所有「搬什么、搬到哪、搬多少」都由软件在发起前写进控制器寄存器或描述符。

两种触发方式。 软件请求：进程 read() 时驱动分配一个 DMA buffer，把它的总线地址写进控制器并启动，随后进程睡眠；硬件搬完产生中断，中断处理程序应答中断、唤醒进程——这是块设备、网卡发送方向的常见形态。硬件异步：数据什么时候到达由设备决定，CPU 无法预知，流程是设备产生中断、处理程序分配 buffer 告诉设备往这写、设备写完再中断、程序把数据分发出去并唤醒等待者。网卡是后者的典型实现：驱动在初始化时分配一圈 buffer 组成环形缓冲区（DMA ring buffer），放在与处理器共享的内存里；每个输入包进入环中下一个可用 buffer 后产生中断，驱动把包交给协议栈，再往环里补一个新的 DMA buffer。整圈 buffer 从驱动加载一直用到卸载，不在收包路径上分配内存，这是高吞吐的前提。

channel：逻辑概念，不是物理并行通道 #

一个 DMA 控制器能「同时」进行的传输个数叫作 DMA channel。这个「同时」要打引号。总线访问存在冲突，加上内存一致性的要求，物理上并不真的并行跑两个 DMA 传输；channel 大多是控制器为了方便抽象出来的概念，所有 channel 的请求都要在控制器内部仲裁，然后串行执行；软件也可以基于物理 channel 自行抽象出更多逻辑 channel，由软件调度其上的请求，dmaengine framework 不区分两者。驱动里看到 max_channels = 8，不代表带宽是单通道的 8 倍，只代表可以挂 8 个互不阻塞的传输请求队列。

request line：为什么需要一根物理连线 #

CPU 发起 DMA 时只说了「从哪搬到哪」，但它并不知道此刻是否具备传输条件：源设备 FIFO 里有没有数据、目的设备 FIFO 有没有空位。这些信息只有设备自己知道。于是设备与 DMA 控制器之间连了几根物理线，叫作 DMA request（DRQ，DMA 请求线），设备用它告诉控制器「现在可以搬了」。控制器收到拉高电平才发起总线事务，否则等待——没有这条线，控制器只能盲目地按节拍搬运，搬到空 FIFO 就是读到垃圾数据。每个数据收发的节点（endpoint）都对应一条 request line，memory 除外——memory 永远就绪，不需要申请。

维度 DMA channel DMA request line
角色 Provider，提供传输服务 Consumer，消费传输服务
归属 DMA 控制器内部资源 设备与控制器之间的物理连线
数量关系 少 多，因为不是每条线每一刻都在传
解决的问题 谁来搬 什么时候能搬

这也是 struct dma_slave_config 里 slave_id 字段存在的原因：控制器要知道这次传输对应哪条 request line，才能正确地等待与响应。不区分 slave 的控制器可以忽略它。

传输参数：size、width、burst #

DMA 传输参数是逐步演进出来的，三个参数各解决一类问题。

参数 含义 不设它会怎样
transfer size 本次要搬多少字节 无此参数无法启动，但只有它时控制器只能每个时钟搬 1 byte
transfer width 每个时钟搬多少 bit 无法利用 32/64-bit 总线宽度；音频会对不齐 16/24-bit 采样
burst size 控制器内部 buffer 一次缓存多少 每个 beat 都去访问一次 memory，效率极低

transfer width 的必要性来自两类矛盾需求：memory 之间传输希望用总线最大宽度（32-bit、64-bit）拉满带宽；音频设备则要求每次精确写入 16-bit 或 24-bit，多一个字节就是噪音。burst size 解决的是 memory 访问效率：控制器内部有一小块 buffer，memory 作源时一次读出一批数据存在 buffer 里再按节拍一点点送给目的设备，memory 作目的时先把源数据攒够一批再一次性写回 memory，这块 buffer 的容量就是 burst size。

三者关系是：总字节数 = burst 次数 × burst size，而 burst size 的单位是 transfer width 的个数，不是字节。这一点在 dma_slave_config 里体现得很直接：src_maxburst 的单位是 src_addr_width，写错就会得到 4 倍或 8 倍的突发长度。burst 的上界由 dma_device->max_burst 兜底，单次传输的 maxburst 不能超过它。一次传输的完整分工是这样的：CPU 写控制器寄存器（源、目的、宽度、突发、总字节数、对应哪条 request line）→ 控制器挂起等到 request line 拉高 → 控制器发起总线读/写，按 width 逐个 beat 搬、按 burst 组织成事务 → 字节数归零或线路无效时停止并产生中断 → 中断程序解除映射、唤醒等待者、必要时重新挂 buffer。

到这里讲的还是个独立的 DMAC：CPU 配寄存器、DRQ 拉起来、控制器抢总线。第二十一章会看到 PCIe 设备根本不走这套——它自己就是总线主设备，没有中央 DMAC 什么事。两套模型都要认。

四、三种地址：虚拟、物理、总线 #

驱动里最容易混淆的就是「地址」这个词。Linux 驱动开发涉及三种地址，混用其中两个基本必出 bug。

类型 典型类型 谁使用 怎么得到
虚拟地址 void * CPU kmalloc()、vmalloc()、ioremap() 返回
物理地址 phys_addr_t / resource_size_t CPU 通过 MMU 间接用 页表翻译得到；/proc/iomem 可看；驱动不能直接用，需 ioremap()
总线地址 dma_addr_t 设备 设备在总线上看到的地址，MMIO 寄存器或 DMA 读写内存时使用

典型 PCI 场景最能说明三者的关系：设备用 BAR 声明自己在总线上占用的地址区间 A；CPU 不能直接访问总线地址 A，PCI host bridge 会把总线地址 A 映射到一段物理地址 B；驱动 ioremap(B) 拿到虚拟地址 C，之后 ioread32(C) 实际访问的就是总线地址 A 上的寄存器。

text
虚拟 ──MMU 页表──► 物理 ──host bridge──► 总线
  ▲                  │                    │
  └── ioremap ───────┴────────────────────┘

CPU 只认虚拟地址。设备只认总线地址。
物理地址是内核代管的中间产物，驱动不该直接拿去用。

五、DMA 地址不等于物理地址 #

这一节是全文最该记住的一条。假设驱动 kmalloc() 得到虚拟地址 X，MMU 把它映射到物理地址 Y。此时设备看不到 X——MMU 只对 CPU 起作用，对挂在总线上的设备完全不可见。而且系统内存总线与 PCI 总线是两个不同的地址空间，Y 未必是设备能用的地址。

简单系统里设备可以直接访问 Y，事情到此为止。但多数现代系统中间还有一层 IOMMU：它把设备发出的总线地址 Z 翻译成物理地址 Y。于是 dma_map_single() 干的事就清楚了：它先接收虚拟地址 X，再建立 IOMMU 页表项把 X 所在的物理页 Y 映射到总线地址 Z，最后返回 Z。此后设备对 Z 发起 DMA，IOMMU 把它翻译成 Y，落到驱动申请的那块 buffer 上。

text
        ┌──────────┐   dma_map_single()   ┌──────────┐
        │ 驱动持有 │ ───────────────────► │ 设备持有 │
        │ 虚拟 X   │                      │ 总线 Z   │
        └────┬─────┘                      └────┬─────┘
             │ MMU                             │ IOMMU
             ▼                                 ▼
        ┌──────────┐                      ┌──────────┐
        │ 物理 Y   │ ◄────────────────────│ 物理 Y   │
        └──────────┘       (同一块页)      └──────────┘

dma_address 不等于物理地址，这是原文反复强调、也最容易出错的一点。有 IOMMU 时，dma_addr_t 是 IOVA（I/O Virtual Address），一个和设备绑定、和物理页没有固定偏移关系的编号，同一个物理页被两个设备分别映射会拿到两个不同的 IOVA。没有 IOMMU 时，dma_addr_t 才等于 PA（物理地址），但也只是当前平台的实现恰好如此，不是 API 的承诺。有 SWIOTLB（bounce buffer）时，dma_addr_t 指向 bounce buffer 的物理地址，和原 buffer 毫无关系，数据靠软件拷贝。所以这三件事都不能做：

c
/* 错 1：拿 virt_to_phys 的结果当 DMA 地址——有 IOMMU 时是彻底错误的编号 */
dma_addr_t bad = virt_to_phys(buf);

/* 错 2：拿 dma_handle 去 kmap / 解引用——那是设备侧编号，CPU 无法解引用 */
void *p = phys_to_virt(dma_handle);

/* 错 3：比较两个设备的 dma_handle 判断是否同一块内存 */
if (dev_a_handle == dev_b_handle) { /* 永远不要这么想 */ }

virt_to_bus() / bus_to_virt() 在现代内核里基本已不可用。唯一正确的总线地址来源是 dma_map_*() 的返回值——它会考虑 IOMMU、bounce buffer、非一致性架构的缓存维护，而 virt_to_bus() 一个都不管。整个过程驱动只碰 X 和 Z，Y 由内核代管。这就是驱动永远不应该 virt_to_phys() 再拿去给设备用的原因。没有 IOMMU 的平台（大量嵌入式 SoC）上，Z 等于 Y，看起来「不需要翻译」，但代码不能依赖这一点，否则移植到有 IOMMU 的平台上必然失效。

动态映射到底「动态」在哪 #

动态 DMA 映射指只在要用的时候建立 buffer 的虚拟地址到总线地址的映射，传输一结束就销毁。这也解释了 API 为什么叫 map / unmap——它是一次性的租借，不是永久绑定。与之相对的是第十章的一致性映射：初始化时建立，整个驱动生命周期内都在。写驱动应该用通用 API 而不是总线专有 API：用 dma_map_*() 而不是 pci_map_*()，头文件包含 <linux/dma-mapping.h>。通用 API 内部会处理 IOMMU、SWIOTLB、地址限制等平台差异，dma_addr_t 可以保存任何总线与架构上的 DMA 地址。

哪些内存能做 DMA #

分配方式 能否直接 DMA 映射 原因
__get_free_page*()（伙伴系统） 可以 物理页连续
kmalloc() 可以 保证物理连续
kmem_cache_alloc() 可以 底层是 slab，物理连续
vmalloc() 不要用 页帧不连续，且虚拟/物理地址无线性关系，映射时要遍历页表才能得到物理地址
kmap() 不要用 同上，且属临时映射
编译进内核的全局变量 可以 内核初始化时建立的 image mapping 使其连续且虚实偏移固定
编译成模块的全局变量 不行 模块加载时用 vmalloc 分配，超过 1 页就无法保证物理连续
块设备 I/O buffer、网络收发 buffer 可以 由对应子系统在分配时就保证了 DMA 要求

最后一行是条重要经验：驱动不该自己为收发数据造 buffer，而应使用子系统提供的（bio 的页、sk_buff 的数据区），因为它们已经把 DMA 约束考虑进去了。用全局变量做 DMA 还要额外注意两点：一是 cacheline 对齐，避免与相邻变量共享 cacheline 导致伪共享与一致性失效；二是如果平台不是全面 DMA coherent，写回操作必须自己保证。

⚠警告

栈上变量永远不能做 DMA buffer。栈内存的物理页不保证连续，栈溢出后地址更是完全不可控。CONFIG_DMA_API_DEBUG 会专门抓这一条。

六、IOMMU 在这里扮演什么角色 #

IOMMU 不是可选加速器。它在四个地方起作用，每一个都能改变驱动的正确性要求。

一、地址翻译。 设备发总线地址，IOMMU 按页表翻成物理地址，这就是上节 Z→Y 那一层。IOVA 空间可以做到和设备的 dma_mask 一样窄（32 位就够），于是 32 位设备能塞进一台装着大内存的机器里正常工作。

二、地址隔离与保护。 设备只能访问被显式映射过的页。驱动把错误地址写进寄存器，DMA 打到未映射区间会被 IOMMU 直接拒绝并报错（x86 上是 DMAR: [DMA Write] Request device ... fault），而不是悄悄踩坏别人的内存。没有 IOMMU 时同一个 bug 的表现是「几小时后系统在无关位置 panic」。

三、把分散的页聚成连续的 IOVA。 这是 dma_map_sg() 能被软件「合并」的基础。物理页散在四处，IOMMU 可以把它们映射成一段首尾相接的 IOVA 区间，设备只需要一个基址就能连续访问。这就是「不支持 SG 的控制器也能工作」的实现原理。

四、扮演历史遗留物里「映射寄存器」的角色。 在支持映射寄存器的系统上，每个 DMA 映射都要占用总线上一个或多个映射寄存器；寄存器数量有限，而一致性映射生命周期很长，会长期独占这些资源，即使它根本没在传输。耗尽后新的映射只能失败或退化成 bounce buffer，吞吐直接崩掉。现代平台上这个角色由 IOMMU 承担，问题本质没变——IOMMU 的地址转换条目同样是稀缺资源。判断标准因此很简单：这块内存是不是长期被 CPU 与设备交替访问？是才用一致性映射，否则用流式。

ℹ笔记

内核里 IOMMU 的抽象是 struct iommu_domain 与 ->dma_map_ops。dma-direct 是 4.20 引入的直通路径：没有 IOMMU 时 dma_map_ops 指向 dma_direct_ops，有 IOMMU 时指向厂商的 *_iommu_ops（Intel 的 intel_iommu_ops、AMD 的 amd_iommu_ops、ARM 的 iommu_dma_ops）。4.20 之前这套分层散在 arch/*/kernel/dma-mapping.c 和各架构的 struct dma_map_ops 里，读旧代码时别套新结构。

七、哪些内存能做 DMA：一致性内存与流式内存 #

内核把 DMA 映射分成两类，区别在生命周期和谁负责维护 cache 一致性。

维度 一致性内存（coherent） 流式内存（streaming）
建立时机 驱动 init 时，贯穿驱动生命周期 每次传输前 map，传完 unmap
生命周期 等于驱动生命周期 等于一次传输
是否需要方向 不需要（隐含 DMA_BIDIRECTIONAL） 必须指明 enum dma_data_direction
Cache 维护 由平台硬件/内核保证，无需 sync 由 map/unmap/sync 按方向处理
CPU 访问限制 可随时读写 map 之后默认不该碰，要碰必须 sync
主要 API dma_alloc_coherent() dma_map_single() / dma_map_page() / dma_map_sg()
资源占用 长期占用 IOMMU 条目 用完即还
典型场景 描述符环、mailbox、固件 microcode 网卡收发的数据 buffer、块设备数据页

一句话选型：长期被 CPU 与设备交替访问的用一致性，一次性的顺序数据用流式。 不要因为「一致性内存省事」就全用它，它的成本是隐性的：占地址空间、占 IOMMU 条目、小块场景下每块至少一页。

八、dma_mask 与寻址限制 #

设备能访问的地址范围由它自己的地址线决定，不由系统内存大小决定。一块只能驱动低 24 位地址的设备，物理上就只能访问 16MB 以下的内存；给它一个 0x80000000 的地址，DMA 会打到完全不相干的地方，症状是内存被随机踩坏、系统在毫无关联的地方 panic。

驱动必须把设备的限制告诉内核，否则内核默认设备能访问全部 32 bit 地址，分配 buffer 时就不会做特殊处理。这个告知动作在 probe() 里完成。

c
int dma_set_mask_and_coherent(struct device *dev, u64 mask);
int dma_set_mask(struct device *dev, u64 mask);            /* 只设 streaming */
int dma_set_coherent_mask(struct device *dev, u64 mask);   /* 只设 coherent */

int using_dac;
if (!dma_set_mask(dev, DMA_BIT_MASK(64)))          /* 64 位设备：先试 64，再退 32 */
    using_dac = 1;
else if (!dma_set_mask(dev, DMA_BIT_MASK(32)))
    using_dac = 0;
else
    goto ignore_this_device;

mask 表示设备支持的地址位，写 DMA_BIT_MASK(32)、DMA_BIT_MASK(64) 这种形式。返回 0 表示从设备到该 mask 范围内内存的 DMA 可以被系统支持（包括控制器与总线层）；返回非 0 表示这样的 DMA 无法正确完成，强行做后果不可预知。失败后有三个选择：换一个更小的 mask；放弃 DMA 改用普通 PIO；忽略这个设备不初始化。64 位失败并不等于平台不能做 64 位寻址。很多平台上 32 位寻址更快——例如 SPARC64 上 PCI 的 SAC（32 位）比 DAC（64 位）性能更好，内核会主动让 64 位设定失败，把设备压回 32 位窗口。所以这个降级链条是常态而非异常。

struct device 上与 DMA 相关的字段 #

dma_mask 不是孤立的一个值，struct device 里跟 DMA 相关的字段有一组：

字段 类型 语义
dma_mask u64 * 指向设备可寻址位宽掩码的指针，streaming DMA 用
coherent_dma_mask u64 coherent DMA 的寻址掩码，是值不是指针
dma_range_map const struct bus_dma_region * 总线地址与物理地址之间的偏移表（dma-ranges 解析结果）
dma_ops const struct dma_map_ops * 该设备实际使用的映射操作集，dma-direct 也挂这里
dma_coherent bool 该设备是否为硬件一致（非一致设备需要显式 cache 维护）
dma_parms struct device_dma_parameters * 段的边界与大小约束，见下文

dma_mask 是指针。历史上有些架构允许同一总线上的设备共享一个 mask 变量，所以设成了指针。写驱动时用 dma_set_mask() 就够了，不要直接碰这个字段。dma_parms 里的约束比 dma_mask 更细：max_segment_size 是一次 DMA 传输的段最大字节数，segment_boundary_mask 是段边界的位掩码，结构体就这两个字段。max_segment_size 解决的是「设备一次只能搬这么多，超过就必须拆成多段」。典型例子是 32 位 PCI 设备上的 max_segment_size = 65536 - 1——地址跨过 64KB 边界时硬件高位不进位，跨界的传输会回卷到段首。这两个值由总线层在 probe() 时按设备类代码与厂商信息设好，驱动一般不用自己写。

coherent mask 与 streaming mask 的关系 #

一致性与流式两类 DMA 的寻址限制可以不同，也可以相同。相同时用 dma_set_mask_and_coherent() 一次设完，不同时分开设。有一条恒成立的约束：coherent mask 总是小于或等于 streaming mask。因此只要 streaming 设定成功，再用同样或更小的 mask 去设 coherent 必然成功，实践中往往不检查 dma_set_coherent_mask() 的返回值。例外是只支持 coherent DMA 的怪设备，这时必须检查。

❢重要

一个反直觉的坑：即使驱动把 streaming mask 设成了 64 位，只要没有显式调用 dma_set_coherent_mask()，dma_alloc_coherent() 一般仍然只返回 32 位可寻址的地址。dma mask 与 coherent dma mask 是两套独立的限制，不要以为设了一个另一个就跟着变。

九、coherent DMA：dma_alloc_coherent #

一致性映射（consistent / coherent DMA mapping）在驱动初始化时建立，整个生命周期内都在，CPU 与设备看到的内存始终一致，中间不需要软件做任何 cache 操作。两个特征：一是长期存在，init 时 map、shutdown 时 unmap，中间不反复建立销毁；二是自动一致，CPU 写完内存设备立刻能看到，设备写完 CPU 立刻能读到，不需要 dma_sync_*()。「consistent」这个名字其实名不副实，它保证的是 coherent（一致性），不是别的什么。

典型场景的共性是「CPU 与设备会反复交替读写同一块内存，且读写时机无法预判」：网卡描述符环/链（驱动写描述符、设备读；设备状态回写、驱动读，全程反复）；SCSI 适配器的 mailbox command（命令与状态在同一块内存来回传递）；外设执行的固件 microcode（设备自行取指，CPU 无法预知访问时机）；DMA controller 的传输描述符数组（控制器随时会回读描述符）。这些场景改用流式映射，每次 CPU 改完都要 sync for device、每次设备写完都要 sync for cpu，且必须精确插在访问点之间，漏一次就是偶发的数据错乱。

两个地址、页对齐 #

c
void *dma_alloc_coherent(struct device *dev, size_t size,
                         dma_addr_t *dma_handle, gfp_t gfp);
void dma_free_coherent(struct device *dev, size_t size,
                       void *cpu_addr, dma_addr_t dma_handle);

返回值是 CPU 侧的虚拟地址，通过 dma_handle 带回 设备侧的总线地址。两个地址指向同一块内存，绝不能互相替代：CPU 只能用前者解引用，设备寄存器里只能写后者。几条容易踩的性质：起始地址与 size 都按 page 对齐，行为类似 __get_free_pages()，所以申请 100 字节也会占一页；buffer 不会跨越 page 边界，天然满足「DMA buffer 物理连续」的要求；可以在中断上下文调用，但此时 gfp 必须传 GFP_ATOMIC；即使设备的 streaming mask 支持 64 位，只要没显式设过 coherent mask，返回地址一般仍在 32 位窗口内。

⚠警告

dma_free_coherent() 不能在中断上下文调用。某些平台上释放一致性内存会触发 TLB 维护，进而需要核间通信（IPI）；在关中断的上下文里调用会直接死在 SMP 的 IPI 代码中（BUG: scheduling while atomic 或更难查的挂死）。中断里只能释放用 dma_pool 分配的小块，或把释放动作丢到 workqueue。

dma pool：大量小块一致内存 #

驱动经常需要成千上万个又小又多的一致映射块：USB 的传输请求、网络的小描述符、块设备的命令块。直接对每个小块调 dma_alloc_coherent() 会浪费得离谱——每块至少占一页，还会在 IOMMU 里占掉一个映射项。DMA pool 的思路与 kmem_cache 一样：先从 dma_alloc_coherent() 拿一大块，再从中零售小块。

c
struct dma_pool *dma_pool_create(const char *name, struct device *dev,
                                 size_t size, size_t align, size_t boundary);
void *dma_pool_alloc(struct dma_pool *pool, gfp_t mem_flags, dma_addr_t *handle);
void dma_pool_free(struct dma_pool *pool, void *vaddr, dma_addr_t dma);
void dma_pool_destroy(struct dma_pool *pool);

boundary 是关键参数：分配到的小块不会跨越 boundary 边界（传 4096 就不会跨 4K 页）。这对地址受限的设备很有用——某些老设备要求一次 DMA 不跨页，边界约束能在分配时就保证，而不是运行期再拆。池的 size 一旦定下就不可变，所以要把结构体大小算准并留出对齐余量；实际分配到的块大小会被向上取整，align 取 cacheline 大小或硬件要求的最小对齐。

一致性内存仍需内存屏障 #

「一致」只保证 cache 层面的可见性，不保证访问顺序。CPU 和编译器都会重排对一致性内存的访问指令。如果硬件要求 word0 必须先于 word1 更新（典型的描述符「先填内容、最后置 valid 位」），必须显式加屏障：

```c`c desc->addr = dma_handle; desc->len = size; wmb(); /* 保证前两条写入对设备可见后，才写下面的 valid 位 */ WRITE_ONCE(desc->valid, 1);


有些平台上，修改一致性 buffer 后还需要 flush write buffer（`mb()` 或平台特有的 flush），设备才能看到，这类需求写在 SoC 手册里。cache 同步与顺序屏障是两件事，`wmb()` 只解决后者。

## 十、streaming DMA：dma_map_single / dma_map_page

流式映射（streaming DMA mapping）是一次性的：要传的时候才 map，传完立刻 unmap。硬件可以针对这种顺序访问做优化，因此它是数据面（收发路径）的默认选择。使用约束有四条：生命周期等于一次传输，map 与 unmap 之间才是设备可访问的窗口；需要指明方向，因为方向决定了要 flush 还是 invalidate，方向错就是数据错；默认情况下 map 之后 CPU 不应碰 buffer，确实要在中间读写必须用 `dma_sync_*()` 交还控制权；这些接口是按性能优先设计的，**调用前必须清楚知道它做了什么**，不能靠猜。典型场景是网卡收发的数据 buffer、文件系统的数据 buffer（最终交给 SCSI 设备）。

### 方向参数

```c
enum dma_data_direction {
    DMA_BIDIRECTIONAL,
    DMA_TO_DEVICE,
    DMA_FROM_DEVICE,
    DMA_NONE,
};
方向 含义 典型场景
DMA_TO_DEVICE 数据从内存流向设备 网卡发送、写块设备
DMA_FROM_DEVICE 数据从设备流向内存 网卡接收、读块设备
DMA_BIDIRECTIONAL 双向 控制块与状态块放在一起的设备
DMA_NONE 仅用于调试 不要在生产代码里用

方向一定要写准，不要图省事全写 DMA_BIDIRECTIONAL。准确的方向有两重收益：一是实现可以在 DMA_TO_DEVICE 时只 flush、DMA_FROM_DEVICE 时只 invalidate，省掉一半 cache 操作；二是调试价值——某些平台的页表里带写权限位，控制器违反方向去写只读的 DMA_TO_DEVICE buffer 时会打内核日志，方向写错能被抓出来。只有流式映射需要指明方向，一致性映射隐含 DMA_BIDIRECTIONAL，因为 CPU 与设备都会随时读写它。

map_single 与 map_page #

c
dma_addr_t dma_map_single(struct device *dev, void *ptr, size_t size,
                          enum dma_data_direction dir);
void dma_unmap_single(struct device *dev, dma_addr_t dma_handle,
                      size_t size, enum dma_data_direction dir);

dma_addr_t dma_map_page(struct device *dev, struct page *page,
                        unsigned long offset, size_t size,
                        enum dma_data_direction dir);
void dma_unmap_page(struct device *dev, dma_addr_t dma_handle,
                    size_t size, enum dma_data_direction dir);

dma_map_single() 传进去的是 CPU 指针，返回设备侧总线地址。它有一个硬限制：不能映射 HIGHMEM，因为它需要虚拟地址，而 HIGHMEM 在没有 kmap() 的情况下没有固定虚拟地址。需要映射 HIGHMEM 上的页时，改用 page 加页内偏移的版本：

c
/* page + offset 形式：块设备、网络收包这类拿到 struct page 的场景 */
dma_handle = dma_map_page(dev, buffer->page, buffer->offset, buffer->len,
                          DMA_FROM_DEVICE);
if (dma_mapping_error(dev, dma_handle))
    goto map_error_handling;

/* ... 启动传输 ...

   传输完成后 */
dma_unmap_page(dev, dma_handle, buffer->len, DMA_FROM_DEVICE);

dma_mapping_error：必须用它判断 #

映射会失败（IOMMU 表项不足、地址超出设备窗口等），失败时返回值不是 NULL 而是某个特定标记。判断失败必须调用 dma_mapping_error(dev, dma_handle)，不要自己拿返回值做比较。两种典型错误写法：

c
/* 错误示例 1：假设失败地址一定在前 16MB 之外，或低位有标志 */
if ((dma_handle & 0xffff != 0) || (dma_handle >= 0x1000000))
    goto map_error;

/* 错误示例 2：假设失败地址一定等于 DMA_ERROR_CODE */
if (dma_handle == DMA_ERROR_CODE)
    goto map_error;

/* 正确写法 */
dma_handle = dma_map_single(dev, addr, size, DMA_TO_DEVICE);
if (dma_mapping_error(dev, dma_handle)) {
    /* 回滚：释放自己的资源，不要继续启动传输 */
    goto map_error_handling;
}

两种错误写法都对底层实现做了假设，换个架构就失效。不检查错误的后果更严重：把无效地址写进设备寄存器，轻则数据悄悄写错位置（损坏无关内存），重则直接 kernel panic。

unmap 元数据的零成本抽象 #

很多平台上 unmap 是空操作，根本不需要地址和长度，那么在数据结构里为它们各留一个字段就是纯浪费内存。内核为此提供了宏，视 CONFIG_NEED_DMA_MAP_STATE 决定这些字段是真成员还是一无所有：

c
/* before：无条件占内存 */
struct ring_state {
    struct sk_buff *skb;
    dma_addr_t mapping;
    __u32 len;
};

/* after：平台不需要时字段消失，代码不变 */
struct ring_state {
    struct sk_buff *skb;
    DEFINE_DMA_UNMAP_ADDR(mapping);
    DEFINE_DMA_UNMAP_LEN(len);
};

/* 赋值与访问也必须换成宏 */
dma_unmap_addr_set(ringp, mapping, FOO);
dma_unmap_len_set(ringp, len, BAR);

dma_unmap_single(dev, dma_unmap_addr(ringp, mapping),
                 dma_unmap_len(ringp, len), DMA_FROM_DEVICE);

地址和长度分开处理是有原因的：某些实现里 unmap 只需要 dma address，长度完全用不上，能给一个字段是一份。

unmap 与 DMA 地址空间耗尽 #

DMA 地址空间是共享资源，IOMMU 表项数量有限。每次 dma_map_single() / dma_map_sg() 都必须有严格配对的 unmap。只分配不回收，最终会耗尽可用 DMA 地址，整个系统里所有设备的 DMA 一起失败——症状是运行几小时后网卡开始丢包、磁盘报 I/O 错误，而内存和 CPU 看起来都正常。有几条路径特别容易漏 unmap：错误处理分支、设备拔出的清理路径、中断里提前 return 的分支。写驱动时把 map/unmap 当作 kmalloc/kfree 一样严格对待。

多段映射中途失败必须把已经映射成功的那些 unmap 掉。固定两段时用 goto 链条逐级回滚（err_unmap1 里 dma_unmap_single(dev, dma_handle1, len1, DMA_TO_DEVICE)），循环映射时用索引记住成功到哪一段，失败时把 0..i-1 全部 unmap：

c
for (i = 0; i < nents; i++) {
    sg_dma_address(&sgl[i]) = dma_map_single(dev, sg_virt(&sgl[i]),
                                             sgl[i].length, dir);
    if (dma_mapping_error(dev, sg_dma_address(&sgl[i]))) {
        for (j = 0; j < i; j++)
            dma_unmap_single(dev, sg_dma_address(&sgl[j]),
                             sgl[j].length, dir);
        return -EIO;
    }
}

上层回调里的错误语义 #

映射失败不仅要回滚资源，还要按调用它的子系统约定返回，否则会造成上层无限重试或统计错乱：

c
/* 网卡发送路径：map 失败必须释放 skb 并返回 NETDEV_TX_OK */
static netdev_tx_t my_xmit(struct sk_buff *skb, struct net_device *ndev)
{
    dma_addr_t mapping = dma_map_single(dev, skb->data, skb->len, DMA_TO_DEVICE);

    if (dma_mapping_error(dev, mapping)) {
        dev->stats.tx_dropped++;
        dev_kfree_skb(skb);
        return NETDEV_TX_OK;   /* 表示这个 skb 已被处理（丢弃），不是失败 */
    }
}

SCSI 路径的约定不同：queuecommand 里 map 失败要返回 SCSI_MLQUEUE_HOST_BUSY，让 SCSI 中间层稍后重传。

NETDEV_TX_OK 这个返回值最容易搞错：它的语义是「该 skb 的发送流程到此结束」，不是「发送成功」。返回 NETDEV_TX_BUSY 会让重传逻辑介入，而我们并没有把 skb 排队，重传必然再次失败。

bounce buffer 与 ARCH_DMA_MINALIGN #

bounce buffer：驱动要在设备访问不到的地址上做 DMA 时（典型是 HIGHMEM，或者超出设备地址窗口的内存），内核另建一块设备能访问的 buffer，数据按需在原 buffer 与 bounce buffer 之间复制。有的架构直接让映射失败，有的架构会悄悄建 bounce buffer 并把请求成功返回——所以同一个驱动在不同平台上表现会完全不同，这也是为什么必须设对 mask。

ARCH_DMA_MINALIGN：kmalloc() 出来的 buffer 也会用于 DMA。如果架构不是全面 DMA coherent，就必须定义这个宏，保证 kmalloc 返回的地址对齐到它，从而不与相邻的 buffer 共享 cacheline——否则一次 cache 回写会覆盖掉设备刚写进邻居 buffer 的数据，这类 bug 极难查。

⚠警告

ARCH_DMA_MINALIGN 是 DMA buffer 的对齐约束，不是 CPU 的数据对齐约束。它只要求那些会被 DMA 访问的 buffer 满足，并不意味着所有内存访问都要按它对齐。移植时漏定义它，症状是「小 buffer 偶发数据错乱、大 buffer 正常」。

平台移植还有一条：架构若支持 IOMMU（含软件模拟的 IOMMU），需要打开 CONFIG_NEED_SG_DMA_LENGTH。

十一、scatter-gather：dma_map_sg 与 struct scatterlist #

DMA 只能处理物理连续的 buffer，但上层拿到的数据往往是散的：一个 sk_buff 的线性区会跨页，一个文件读请求的目标页更是完全分散。把这些非连续的块拼成一段连续内存再交给 DMA，这个操作叫 scatter gather。多数情况下这靠软件完成：驱动自己维护一个描述符数组，每项记录一段连续区域的地址与长度，控制器逐个执行。真正在硬件层面支持 SG 的控制器（图像、视频、网络这些高吞吐场景常见）可以直接按描述符链遍历，省掉中间拷贝。

struct scatterlist 的字段 #

c
struct scatterlist {
    unsigned long   page_link;     /* struct page 指针；低 2 位被征用为标志 */
    unsigned int    offset;        /* 页内偏移 */
    unsigned int    length;        /* 本段长度 */

    dma_addr_t      dma_address;   /* 映射后的设备侧总线地址（不是物理地址） */
#ifdef CONFIG_NEED_SG_DMA_LENGTH
    unsigned int    dma_length;    /* 映射后的设备侧长度 */
#endif
};
字段 语义 要点
page_link 指向 struct page 低 2 位是两个标志：SG_END（最后一段）与 SG_CHAIN（下一段是链式列表）。所以取页指针必须用 sg_page(sg)，不能直接读字段
offset 段在页内的起始偏移 用 sg_set_page(sg, page, len, offset) 设置，不要手写
length 本次映射前的实际长度 由 CPU 侧填写
dma_address dma_map_sg() 填进去的设备侧地址 只能通过 sg_dma_address(sg) 读
dma_length 映射后会被合并变长的长度 只能通过 sg_dma_len(sg) 读；宏关闭时不占空间

dma_address 和 length 是两个独立的槽位：map 之前 length 有意义、dma_address 无意义；map 之后 dma_length 会大于 length（段被合并），设备侧必须用 dma_length。

dma_map_sg 的完整流程 #

c
int dma_map_sg(struct device *dev, struct scatterlist *sglist,
               int nents, enum dma_data_direction dir);
void dma_unmap_sg(struct device *dev, struct scatterlist *sglist,
                  int nents, enum dma_data_direction dir);

返回值是成功映射的段数，这个值会小于传入的 nents。 返回 0 表示失败。少掉的那几段是被合并了。内部到底做了什么，按 dma-direct（4.20+）的路径展开：

  │    ├─ 建 IOMMU 页表项：IOVA → 各物理页
  │    ├─ 相邻的物理连续页被合并成一个 IOVA 段
  │    └─ 超额时触发 IOVA 空间回收后再试
  │
  └─ __dma_map_sg_attrs() 收尾：写回 sg->dma_address / sg->dma_length，
     返回段数（≤ nents）

返回段数变小的原因有两处：iommu_dma_map_sg() 里物理相邻的页被压成一个 IOVA 段，以及 bounce 区的合并。这个性质正是「不支持或只支持有限 scatter-gather 的控制器也能工作」的原因——内核在映射阶段就把分散的 buffer 整理成了设备能接受的形态。映射成功后遍历用 for_each_sg()，通过 sg_dma_address() 与 sg_dma_len() 取设备侧地址。是否支持硬件 SG 由 dma_device 的 cap_mask 里有没有 DMA_SG、DMA_INTERLEAVE 决定。

sg 初始化与常见错误 #

c
sg = kmalloc_array(page_count, sizeof(*sg), GFP_KERNEL);
if (!sg)
    return -ENOMEM;

sg_init_table(sg, page_count);          /* 必须：清标志位、把最后一段标 SG_END */
for (i = 0; i < page_count; i++)
    sg_set_page(&sg[i], pages[i], PAGE_SIZE, 0);

if (!count) {                           /* 返回 0 即失败，没有别的判据 */

}

for_each_sg(sg, s, count, i)            /* 注意遍历用 count，unmap 用 page_count */
    load_descriptor_to_device(sg_dma_address(s), sg_dma_len(s));

trigger_dma_hardware_sg();

c
/* 错 1：前面没调 sg_init_table，SG_END 没置位，遍历越界 */

/* 错 2：unmap 时传 count 而不是原始 nents —— IOMMU 表项泄漏 */

/* 错 3：设备侧用 sg->length 而不是 sg_dma_len(sg)，合并后的段被截断 */
❢重要

dma_unmap_sg() 的 nents 参数必须传当初传给 dma_map_sg() 的那个 nents，不是返回的 count。传 count 会让那些被合并掉的段得不到清理，IOMMU 表项泄漏，跑一段时间后 DMA 开始莫名其妙失败。dma_sync_sg_*() 同理。

十二、映射方向与 dma_sync 的语义 #

如果一次 map 与 unmap 之间 CPU 从不触碰 buffer，那根本不需要任何 sync 操作。只有在同一块 buffer 上做多次访问、且要在两次 DMA 之间读写它时才需要：DMA 传完 CPU 要读 buffer，调 dma_sync_single_for_cpu() / dma_sync_sg_for_cpu()；CPU 改完要把控制权交还设备，调 dma_sync_single_for_device() / dma_sync_sg_for_device()。

c
void dma_sync_single_for_cpu(struct device *dev, dma_addr_t dma_handle,
                             size_t size, enum dma_data_direction dir);
void dma_sync_single_for_device(struct device *dev, dma_addr_t dma_handle,
                                size_t size, enum dma_data_direction dir);
void dma_sync_sg_for_cpu(struct device *dev, struct scatterlist *sglist,
                         int nents, enum dma_data_direction dir);
void dma_sync_sg_for_device(struct device *dev, struct scatterlist *sglist,
                            int nents, enum dma_data_direction dir);

名字里的 owner 视角 #

for_cpu / for_device 描述的是交接给谁，不是「谁需要同步」。for_cpu 把所有权从设备收回来交给 CPU，要保证 CPU 接下来读到的是 RAM 里的最新值；for_device 把所有权交出去给设备，要保证设备接下来读到的是 CPU 写过的最新值。方向参数依然要传对，因为同一个 for_device 在 DMA_FROM_DEVICE 与 DMA_TO_DEVICE 下做的事不一样：DMA_FROM_DEVICE 的 for_device 需要先把脏行写回（否则设备写 RAM 时脏行还在 cache 里，之后被回写覆盖），DMA_TO_DEVICE 的 for_device 只需要写回。

完整往返示例 #

网卡收包，这段是理解 sync 时机最好的材料：

c
/* 准备阶段：映射一块 buffer 交给硬件，此后 CPU 不应再碰它 */
static void my_card_setup_receive_buffer(struct my_card *cp, char *buffer, int len)
{
    dma_addr_t mapping;

    mapping = dma_map_single(cp->dev, buffer, len, DMA_FROM_DEVICE);
    if (dma_mapping_error(cp->dev, mapping))
        goto map_error_handling;

    cp->rx_buf = buffer;
    cp->rx_len = len;
    cp->rx_dma = mapping;

    give_rx_buf_to_card(cp);          /* 把总线地址写进网卡 DMA 寄存器 */
}

/* 中断里：硬件已把数据写进 buffer */
static irqreturn_t my_card_interrupt_handler(int irq, void *devid)
{
    struct my_card *cp = devid;
    struct my_card_header *hp;

    if (read_card_status(cp) != RX_BUF_TRANSFERRED)
        return IRQ_NONE;

    /* 关键一步：先 sync for cpu，否则读到的是 cache 里的旧数据 */
    dma_sync_single_for_cpu(cp->dev, cp->rx_dma, cp->rx_len, DMA_FROM_DEVICE);

    hp = (struct my_card_header *)cp->rx_buf;
    if (header_is_ok(hp)) {
        dma_unmap_single(cp->dev, cp->rx_dma, cp->rx_len, DMA_FROM_DEVICE);
        pass_to_upper_layers(cp->rx_buf);
        make_and_setup_new_rx_buf(cp);
    } else {
        /* 头部不合法但 buffer 还要继续用：sync for device 后重新交给网卡 */
        dma_sync_single_for_device(cp->dev, cp->rx_dma, cp->rx_len, DMA_FROM_DEVICE);
        give_rx_buf_to_card(cp);
    }
    return IRQ_HANDLED;
}

两个分支的区别：走 unmap 的路径已经把 buffer 还给上层，不再需要交还设备；继续复用的路径必须 sync for device，否则 CPU 读操作会让 cache 里留下脏行，设备下次 DMA 写入时数据被 cache 回写覆盖。

十三、DMA 与 cache 一致性：什么时候要 sync #

CPU 读内存走 cache，DMA 设备读写内存绕过 cache 直接到 RAM。两条路径看到的内存不是同一份：

text
                ┌──────────────────┐
                │      CPU 核心     │
                └────────┬─────────┘
                         ▼▲
                ┌──────────────────┐
                │   Cache 缓存      │ ◄── ① CPU 写入的脏数据停在这里没下去
                └────────┬─────────┘
                         ▼▲
  ┌──────────┐  DMA 写  ┌──────────┐
  │ DMA 设备  ├─────────►│ RAM 内存  │ ◄── ② 设备直接写 RAM，cache 里还是旧值
  └──────────┘           └──────────┘

有两种错法：写丢——CPU 写了数据在 cache 里标脏，设备读 RAM 读到旧值，需要在设备读之前 flush（clean / writeback）；读旧——设备往 RAM 写了新数据，CPU 从 cache 读到旧值，需要在 CPU 读之前 invalidate。DMA_FROM_DEVICE 的缓冲有个陷阱：invalidate 之前必须先 clean。否则 cache 里有脏行，设备已经按 RAM 的旧内容写完，clean 会把脏行覆盖回去，设备写的数据就没了。这就是方向必须传对的原因——方向决定了实现做哪几件事。

硬件兜底：MESI 与总线监听 #

x86 与多数 ARM 服务器 SoC 在硬件层面解决了这个问题。MESI 协议里 cache 块有四个状态：M（Modified） 脏、只在本核、与 RAM 不一致；E（Exclusive） 与 RAM 一致、只在本核；S（Shared） 与 RAM 一致、在多个核；I（Invalid） 已失效，需要从 RAM 重新加载。设备发起写事务抵达一致性互联（coherent interconnect）时，内存控制器会向所有核心广播监听请求（snoop）：若某核里是 S 或 E 状态，硬件立刻把它置为 I；若是 M 状态，硬件会拦住这次 DMA 写，先逼该核把 M 数据写回 RAM，再让设备写。

有这套机制的平台上，dma_map_* 与 dma_sync_* 在不少架构上是空操作（CONFIG_ARCH_HAS_SYNC_DMA_FOR_DEVICE 未定义时的默认实现）。这就是同一份驱动在 x86 上跑得好好的、搬到某个 ARM 板上就开始丢包的原因。低阶 MCU（部分 Cortex-M 类）、MIPS、以及不少低成本 ARM SoC 没有完整的硬件 snooping 互联，这类非一致性平台上 cache 维护必须由驱动经 dma_sync_*() 显式完成，一次都不能漏。同一块 SoC 上，有的设备一致有的不一致，所以 dev->dma_coherent 是设备级属性，不能按平台一概而论。判断方法看两处：编译期的 CONFIG_ARCH_DMA_DEFAULT_COHERENT（架构是否默认一致），以及运行期的 dev->dma_coherent（这个设备是否一致，由固件或 DT 的 dma-coherent 属性决定）。

什么时候必须 sync #

十五、PCIe 是什么：从并行总线到串行链路 #

PCIe 是 PCI Express，一种高带宽、低延迟、端到端（Point-to-Point）的同步串行差分总线。它彻底放弃了 PCI 共享总线的拓扑，改用类似交换式以太网的点对点路由。一条 Link 只能连两个端口：一个 TX，一个 RX；一条链路由若干条 Lane 组成，每条 Lane 是一对差分线。

text
        【 PCIe 物理单通道 (Lane) 差分走线 】

+------------------+                    +------------------+
|  发送端 (TX)     |                    |  接收端 (RX)     |
|      [驱动器]    |                    |     [比较器]     |
|       (D+)  ○────┼───||─── 差分线 ────┼────►○           |
|                  |    AC 耦合电容     |   比较器求差     |
|       (D-)  ○────┼───||─── 差分线 ────┼────►○           |
+------------------+                    +------------------+

一条 Lane 由两向共 4 根差分信号线组成，发送端正负极经差分线连到接收端，反方向同理；电气规范要求发送端串接 AC 耦合电容，用于消除直流偏移并保护输入电路。接收端比较 D+ 与 D- 的电压差判定逻辑值，外部噪声同时同值加载在两根线上，求差后被抵消；两根线电流大小相等方向相反，电磁场近乎抵消，对外的辐射小。链路宽度支持 x1、x2、x4、x8、x12、x16、x32，芯片组（PCH）给低速外设留 x1，x16 留给显卡或高速网卡。

PCIe 2.x 2.5 5.0 8b/10b（20% 开销） 500 MB/s

3.0 的频率只有 2.0 的 1.6 倍，带宽却翻了一倍，原因在编码：8b/10b 为在没有时钟线的串行流里恢复时钟，每发 8 位净荷要夹带 2 位同步码，浪费 20%；3.0 改用加扰（scrambling）加 128b/130b 编码，额外开销降到 1.5%。

插槽上除了差分收发线，还有几根关键引脚：PERST# 是复位（低电平触发，主机电源稳定后拉高，释放外设做内部状态机复位）；REFCLK+/REFCLK- 是 100 MHz 差分参考时钟，让插槽上的卡与主板时钟同相、减小 PLL 抖动；Vaux 是 3.3V 辅助供电，系统休眠时维持卡上的 sticky 寄存器状态，支持 Wake-on-LAN；WAKE# 用于卡向主机申请唤醒；PRSNT1#/PRSNT2# 是存在检测，按接法区分链路宽度。

十六、PCIe 的分层结构：事务层 / 数据链路层 / 物理层 #

PCIe 的数据流分层和 TCP/IP 协议栈是同一种思路：每层只做自己那件事，把对端的同层当成语义上的直接通信方。

text
             【 PCIe 三层协议栈数据流 】

  +------------------+                   +------------------+
  |  事务层 (TLP)    | ◄─── 组包/拆包 ──►|  事务层 (TLP)    |
  +--------▲---------+                   +--------▲---------+
           │                                      │
  +--------▼---------+                   +--------▼---------+
  | 数据链路层 (DLLP)| ◄─── CRC/ACK ────►| 数据链路层 (DLLP)|
  +--------▲---------+                   +--------▲---------+
           │                                      │
  +--------▼---------+                   +--------▼---------+
  |   物理层 (PL)    | ◄── 编码/串并转换 ─►|   物理层 (PL)    |
  +--------▲---------+                   +--------▲---------+
           │                                      │
  =========┴─────────── 物理差分走线 ─────────────┴==========
层 主要职责 关键概念 加的开销
事务层 组装/解析 TLP，端到端路由，流控 Memory Read/Write、Configuration Read/Write、IO Read/Write、Message、Completion；Flow Control Credits TLP 头 12~16 字节 + 可选数据
数据链路层 保证相邻两端口间可靠传输 序列号（12 位）、LCRC（32 位）、ACK/NAK、重传 序列号 + LCRC，共 4+4 字节
物理层 电气传输、编码、串行化 8b/10b 或 128b/130b、加扰、CDR、有序集（TS1/TS2/Electrical Idle） 编码开销 20% 或 1.5%

三层的分工可以从「谁负责什么可靠性」来记：事务层管语义（这个包是读还是写、读哪个地址、要不要回应），数据链路层管相邻两跳的完整性（包丢了错了靠 LCRC + ACK/NAK 重传补回来，它不关心包里装的是什么），物理层管电压和时序（把字节序列变成线上能恢复出时钟的比特流）。

这个分工带来一个推论：数据链路层的重传对事务层是透明的。驱动看到的 DMA 数据不会因为线上一次 LCRC 错就出错，只会慢一点。但链路彻底断了就是另一回事，见 AER。

ℹ笔记

AER（Advanced Error Reporting）把错误分两类。可纠正错误（Correctable）如 LCRC 错、输入缓冲区瞬时溢出，由物理层/链路层的重传机制在硬件上自行消化，软件看不到。不可纠正错误（Uncorrectable）分非致命（Non-fatal，如投毒 TLP Poisoned TLP、目的地址不存在）与致命（Fatal，如链路断开）。非致命错误会触发内核 AER 服务调用 pci_driver 的 struct pci_error_handlers 回调链：error_detected → slot_reset → resume，对应返回值是 PCI_ERS_RESULT_NEED_RESET、PCI_ERS_RESULT_RECOVERED 等。这里只标出它与 DMA 的关系：error_detected 里必须停掉设备的 DMA 通路，否则复位期间设备还在往已释放的 buffer 里写。

十七、TLP 包格式与常见事务类型 #

TLP（Transaction Layer Packet）由四段组成，前后顺序固定：

text
+---------+---------+--------------+-----------+-------------+-----+
| Header  |  Data   |  ECRC(可选)  |  LCRC     |  Framing    |     |
| 12/16 B | 0~4096B |   4 Bytes    |  4 Bytes  |  STP/END    |     |
+---------+---------+--------------+-----------+-------------+-----+
   事务层生成           │           数据链路层加          物理层加
                        └── 数据载荷，长度由 Length 字段与 TC 决定

能不能带数据由事务类型决定，读请求与不带数据的写请求后面没有 Data 段。以 32 位 Memory 请求头（Fmt=10，3DW）为例，前几个双字承载所有路由信息：

字段 位宽 作用 与驱动的关联
Fmt 2 bit 头长度（3DW / 4DW）+ 是否带数据 64 位地址的请求必须用 4DW
Type 5 bit 事务类型，见下表 决定对端怎么处理
TC 3 bit Traffic Class，流量类别 QoS 分级用
Attr 3 bit 属性（Relaxed Ordering、ID-based Ordering） 影响重排与一致性

0_1101 CompareAndSwap（原子操作） 是 同上

Fmt 与 Type 的位编码请以 PCIe 基础规范为准，上表是讲解级近似。若要写硬件仿真或抓包工具，请对照规范原文核对。

Completion 有三个状态位值得记：SC（Successful Completion）、UR（Unsupported Request）、CRS（Configuration Request Retry Status）。配置空间读回全 1 且 UR 置位，往往意味着这个设备或功能号不存在。

十八、配置空间与 BAR #

为了让设备可自动识别（PnP），每个 PCIe 设备都提供一块配置空间。传统 PCI 只有 256 字节，PCIe 扩到 4 KB：前 256 字节与 PCI 2.3 规范严格兼容，含厂商 ID（Vendor ID）、设备 ID（Device ID）、类代码、BAR、中断引脚等；后 3840 字节是 PCIe 扩展配置空间，挂 MSI/MSI-X、电源管理、链路控制与状态、AER 寄存器。

x86 与多数 ARM 服务器把整片配置空间以 MMIO 方式映射进 CPU 物理地址空间，这种访问方式叫 ECAM（Enhanced Configuration Access Mechanism）：

text
MMIO 地址 = ECAM 基址 + (总线号 << 20) + (设备号 << 15) + (功能号 << 12) + 寄存器偏移

每个功能号占 4 KB，8 个功能号占 32 KB（即 1<<15），256 个总线号整体占 256 MB。另一条路是 CAM：老 x86 用 0xCF8/0xCFC 两个 IO 端口间接访问，每次只能读一个 DW，慢但兼容性极好，内核在 pci_mmcfg 不可用时退回这条路径。

BAR（Base Address Register） 是配置空间首部里的寄存器，用来协商设备要占多大一段 MMIO（或 IO）空间：上电时 BAR 里存的是设备申请的大小与类型编码，低位属性位说明是内存空间还是 IO 空间、是否可预取（prefetchable）、是 32 位还是 64 位，高处一串 0 的个数说明对齐要求，也就是空间大小；系统 BIOS 或内核枚举设备时读 BAR，算出需要多大空间，在物理地址空间里找一段空闲的写回去；此后 CPU 访问这段 MMIO 地址，就被主桥重定向到该设备内部的寄存器。

探测大小的经典手法（写全 1 再读回）在驱动里不用手写，pci_resource_len() 已经算好了：

c
resource_size_t start = pci_resource_start(pdev, bar);
resource_size_t len   = pci_resource_len(pdev, bar);
unsigned long   flags = pci_resource_flags(pdev, bar);

if (!(flags & IORESOURCE_MEM))
    return -ENODEV;                 /* 这个 BAR 不是内存空间 */

BAR 的几条硬事实：一个设备最多 6 个 BAR（PCI_STD_NUM_BARS）；64 位 BAR 要占两个相邻的槽位（低 32 位 + 高 32 位），所以设了 64 位 BAR 之后可用槽位数会减少；PCIe 端点一般不用 IO BAR，老设备才用，现代驱动应一律假设内存空间；BAR 里给的是总线地址，CPU 要访问它必须先 ioremap()。

十九、MMIO 与 PIO：驱动怎么访问设备寄存器 #

方式 谁发起 用在什么上 内核接口
MMIO CPU 设备寄存器、配置空间（经 ECAM） ioremap() + readl() / writel()
PIO（端口 IO） CPU x86 的 IO 空间、老 ISA 设备 inb() / outb() / ioread8() 系列
DMA 设备 大批量数据搬运 dma_map_*()

口诀是「寄存器走 MMIO，数据走 DMA」。用 CPU 一个字节一个字节地读设备数据寄存器搬大数据，就是第二章算过的那笔亏本账。

c
void __iomem *base = ioremap(pci_resource_start(pdev, 0),
                             pci_resource_len(pdev, 0));
if (!base)
    return -ENOMEM;

u32 id = readl(base + REG_ID);        /* 读寄存器 */
writel(val, base + REG_CTRL);         /* 写寄存器 */

__iomem 这个地址空间标注不是装饰：它让 sparse 能在编译期抓出「把 MMIO 指针当普通指针解引用」这类错。

readl()/writel() 是小端并隐含 mb() 级屏障；ioread32()/iowrite32() 用原生字节序、不隐含屏障；ioread32be()/iowrite32be() 强制大端；readl_relaxed()/writel_relaxed() 是小端但无屏障，需要自己加。PCI 设备的寄存器按规范是小端，所以 x86 和 ARM 小端平台上 writel() 就是正确选择，用 iowrite32() 在 BE 平台上会写出字节序反了的值。

寄存器写入的完成时机。 writel() 返回不代表设备收到了。写操作在 PCIe 上是 Posted Write（不带 Completion 的写），CPU 侧写进写合并缓冲就算完成。要确认设备真看到了，得读回同一个寄存器（读操作会强制前面的写刷新出去）：writel(val, base + REG_DOORBELL); 之后跟一句 readl(base + REG_DOORBELL);。门铃之后最好不要马上做别的事——有些设备的门铃语义是「一拍即发」，读回会让同一个命令触发两次，具体看设备手册。

二十、MSI / MSI-X 中断 #

传统并行总线用专用物理引脚（INTA# ~ INTD#）做「带外」中断，一个插槽只有 4 根线，多个设备共享。中断处理程序进来后必须挨个读设备寄存器判明中断源，延迟高、开销大，对高位速网卡是硬瓶颈。PCIe 把中断搬进了数据流本身：带内（in-band）消息。设备发一个写事务 TLP，往中断控制器的地址写一个特定值，硬件把它翻译成一条中断。

MSI（Message Signaled Interrupts）要求设备发一个 Memory Write TLP，写指定地址、携带指定数据：地址是目标 CPU 的 APIC 中断控制器映射区（x86 上由 0xFEE00000 一带的 LAPIC 地址加字段拼成），数据是中断向量号（含投递模式、触发方式等位）；一个功能最多申请 32 个向量，都写在同一个 MSI Capability 里（一个地址 + 至多 32 个数据值）。内核侧接口是 pci_alloc_irq_vectors(pdev, min_vecs, max_vecs, PCI_IRQ_MSI)。

MSI-X 是扩展版，向量数上限从 32 提到 2048，地址与数据不再放配置空间，而是放在 BAR 里的一张表（MSI-X Table，由 BIR 字段指定落在哪个 BAR），每个表项各自有地址、数据、掩码位，另外还有 Per-vector Pending Bit Array（PBA）记录挂起状态。MSI 只有整体掩码，MSI-X 能逐向量掩码。MSI-X 每个表项 16 字节：Message Address 低 32 位、高 32 位、Message Data、Vector Control（含掩码位）。表项就在设备 BAR 的 MMIO 里，设备也能读，所以掩码状态双方可见。

多队列网卡的用法是给每个 RX/TX 队列绑一个独立向量，再把向量绑到不同 CPU 上（中断亲和性，写 /proc/irq/<n>/smp_affinity）：

c
int nvec = pci_alloc_irq_vectors(pdev, 1, num_queues,
                                 PCI_IRQ_MSIX | PCI_IRQ_MSI | PCI_IRQ_LEGACY);
if (nvec < 0)
    return nvec;

for (i = 0; i < nvec; i++)
    request_irq(pci_irq_vector(pdev, i), my_queue_isr, 0,
                dev_name(&pdev->dev), &priv->queue[i]);

PCI_IRQ_AFFINITY 标志会让内核自动把向量分摊到各 CPU 上，省掉手工设亲和性。

DMA 完成通知走的就是这条路。 一次传输结束的完整路径是：设备 DMA 引擎搬完 → 内部状态机置完成位 → 设备发 Memory Write TLP（MSI-X 表项里的地址与数据）→ 根复合体收到并路由到对应 CPU 的 LAPIC → CPU 进中断执行 request_irq 注册的处理函数 → 处理函数确认完成、unmap buffer、唤醒等待者。没有中断线，没有共享冲突，中断源天然确定。

二十一、PCIe 上的 DMA 事务怎么走 #

第三章讲的是 SoC 内部那种独立 DMAC：CPU 配寄存器、DRQ 拉起来、控制器抢总线。PCIe 上不是这样。

主板上没有统一的中央 DMA 控制器指挥所有设备。每个 PCIe 端点（千兆网卡、M.2 固态硬盘、GPU）内部都集成了自己的 DMA 引擎，这个能力叫 Bus Mastering（总线主控）：

环节 谁做 怎么体现
分配缓冲区 CPU 上的驱动 在 RAM 里分配描述符环与数据 buffer
写描述符 CPU 上的驱动 把 dma_addr_t 与长度填进描述符
通知设备 CPU 上的驱动 MMIO 写门铃（doorbell）寄存器
发起总线读/写 设备的 DMA 引擎 主动发 Memory Read / Memory Write TLP
通知完成 设备 发 MSI/MSI-X 消息 TLP

设备充当总线 Master，自己往系统 RAM 吐数据或拉数据，CPU 全程不参与地址运算。这和第三章的 DRQ 模型是两套东西：DRQ 是外设「请求」控制器来搬，PCIe 是设备自己搬，控制器就长在设备里。

描述符环与门铃 #

text
   RAM 里的描述符环（device 与 CPU 共享，用 dma_alloc_coherent 分配）
   ┌──────┬──────┬──────┬──────┬──────┬──────┐
   │ desc0│ desc1│ desc2│ desc3│ desc4│ ...  │
   │addr  │addr  │addr  │addr  │addr  │      │
   │len   │len   │len   │len   │len   │      │
   │flags │flags │flags │flags │flags │      │
   └──┬───┴──┬───┴──────┴──────┴──────┴──────┘
      │      │
      ▼      ▼
   数据 buf 数据 buf ...（每个 buffer 一次 dma_map_single / dma_map_page）

   CPU 写 tail 指针 ──► 门铃寄存器 ──► 设备读 tail，开始按环取描述符
   设备写 head 指针 ──► MSI-X ──► CPU 中断，回收已完成的描述符

几个设计要点，全部由「设备在另一侧并发读写」这个事实推出来：描述符环本身必须一致（dma_alloc_coherent()），因为 CPU 与设备交替读写同一块内存；数据 buffer 用流式映射，因为每个 buffer 一次用完就还；描述符里的 flags（含 valid 位）必须最后写，前面要 wmb()，设备只看 valid 位决定这个描述符能不能用；tail/head 的内存语义必须是单写者——CPU 只写 tail，设备只写 head。

一次 DMA 写事务在线上长什么样 #

假设驱动已经 map 好一块 buffer，拿到 dma_addr_t = 0x8000_2000，长度 4 KB，交给设备让设备把数据写进内存。线上发生的是：

text
   ① 驱动：writel(desc_idx, base + REG_TX_DOORBELL)
     → MMIO 写，Posted Write 到设备 BAR 里的寄存器

   ② 设备：读描述符 → 发 Memory Read TLP（64 位地址，读 desc[desc_idx]）
     → 根复合体转成对物理内存的读 → 返回 Completion with Data（CplD）

   ③ 设备：搬数据 → 发一串 Memory Write TLP（目标 0x8000_2000 起的各段）
     → Length 单位是 DW，一个 TLP 至多 4 KB，超出则拆多个
     → Posted Write，没有 Completion 回来
     → IOMMU 若在，把 0x8000_2000 翻成物理地址 Y

   ④ 设备：发 MSI-X 消息 TLP（Memory Write 到 LAPIC 地址），通知完成
   ⑤ CPU：进中断，dma_unmap_single() / dma_unmap_sg() 收回映射

注意第 ② 步：设备要读描述符，本身就是一次 DMA 读，代价算在 DMA 带宽里。所以描述符环的布局对性能有直接影响——紧凑、cacheline 对齐、不跨页的环比散着放快得多。第 ③ 步里那些 Write TLP 的数据来自设备内部 FIFO 或设备自己的一片内存，CPU 完全看不到。TSO/GSO 之类的卸载功能就是在设备内部完成分段，把多个小包合成一两个大 TLP 发出去。

DMA 方向 设备发的 TLP Completion
DMA_TO_DEVICE（内存→设备） Memory Read Request，读 RAM 有，CplD 带回数据
DMA_FROM_DEVICE（设备→内存） Memory Write Request，写 RAM 无，Posted
DMA_BIDIRECTIONAL 两者都有 混合

这个对应关系解释了一个常见现象：同样的字节数，收方向的 CPU 占用往往比发方向低。收方向全是 Posted Write，设备尽管发；发方向每个读请求都要等一次 Completion 往返，延迟敏感，需要靠增加 outstanding 请求数（更多 Tag）来填满流水。

P2P：设备到设备 #

PCIe 上两个设备之间可以直接搬数据，不必绕回 RAM，这叫作 P2P DMA（Peer-to-Peer）。典型场景是 GPU 直接读 NVMe，或者网卡直接写板卡的显存。驱动侧把设备的 BAR 地址映射成可 DMA 的地址即可：dma_map_resource(dev, peer_bar_phys, len, DMA_FROM_DEVICE, 0)，判断失败依然用 dma_mapping_error()。P2P 能不能走通取决于拓扑：两个设备在同一 PCIe Switch 下可以，跨根复合体的路径由硬件与 IOMMU 配置决定。测试前先确认拓扑，不要假设它能用。

二十二、从 dma_map 到设备收到 TLP 的完整链路 #

把全文的链子接起来。一次网卡发送，从驱动到线上：

text
[驱动侧]
  1. dma_map_single(dev, skb->data, skb->len, DMA_TO_DEVICE)
       ├─ 有 IOMMU：建立 IOVA → 物理页的页表项，返回 IOVA
       ├─ 无 IOMMU：返回 phys_to_dma(dev, pa)，也就是 PA
       ├─ 地址超出 dma_mask：走 SWIOTLB bounce，返回 bounce 的地址
       └─ 非一致架构：按 TO_DEVICE 做 cache clean → 返回 dma_addr_t Z

  2. 把 Z 与长度写进描述符环（这块环是 dma_alloc_coherent 来的），wmb() 后置 valid 位
  3. writel(idx, base + REG_DOORBELL) —— MMIO 写，经 BAR 到设备寄存器，Posted

[总线侧]
  4. 设备 DMA 引擎读描述符：Memory Read TLP，Requester ID = 设备，Tag = n
  5. 根复合体转发 → 内存控制器返回 Completion with Data
  6. 设备按描述符里的 Z 拼 Memory Write TLP
       ├─ Header 里 Address 字段 = Z（IOVA）
       ├─ IOMMU 把 Z 翻成物理地址 Y
       └─ 数据落到驱动当初 kmalloc 的那块页上
  7. 设备发 MSI-X 消息 TLP

[驱动侧]
  8. 中断处理：确认完成 → dma_unmap_single() → 释放 skb

两个必须看清的点。第一，第 3 步和第 6 步的目标地址是两种不同的东西。 第 3 步写的是 BAR 里的寄存器，那是总线地址，由 BAR 协商得来，CPU 通过 ioremap 的虚拟地址访问；第 6 步写的是 dma_addr_t，那是内存侧的总线地址，由 dma_map_* 生成。两者都被叫「总线地址」，但一个指向设备内部空间，一个指向系统内存。搞混的症状是「把 BAR 地址当 DMA target 去做 P2P，结果设备往自己的寄存器空间写数据」。

第二，第 6 步能成功的前提全在第 1 步就定好了。 mask 设小了、IOMMU 域建错了、buffer 是 vmalloc 的、方向传反了，都在这里静默出错，事后很难从症状反查回原因。

二十三、PCIe 驱动 probe 里的资源获取 #

一个 PCIe 驱动的 probe() 有一串固定动作，顺序有讲究。这是「DMA 子系统」和「PCIe 总线」真正碰面的一刻。

c
static int my_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
    int ret;
    void __iomem *base;

    ret = pci_enable_device(pdev);              /* 1. 使能设备与 BAR 背后的地址空间 */
    if (ret)
        return ret;

    ret = pci_request_regions(pdev, "mydev");   /* 2. 独占 BAR 区域 */
    if (ret)
        goto err_disable;

    /* 3. 设 DMA mask —— 必须在任何 dma_map / dma_alloc 之前 */
    ret = dma_set_mask_and_coherent(&pdev->dev, DMA_BIT_MASK(64));
    if (ret && dma_set_mask_and_coherent(&pdev->dev, DMA_BIT_MASK(32))) {
        dev_err(&pdev->dev, "no usable DMA mask\n");
        goto err_release;
    }

    pci_set_master(pdev);                       /* 4. bus master 位，不开 DMA 被丢弃 */

    base = pci_iomap(pdev, 0, 0);               /* 5. 映射 BAR */
    if (!base) {
        ret = -ENOMEM;
        goto err_release;
    }

    /* 6. 申请 MSI-X 向量 */
    ret = pci_alloc_irq_vectors(pdev, 1, MY_MAX_QUEUES,
                                PCI_IRQ_MSIX | PCI_IRQ_MSI | PCI_IRQ_LEGACY);
    if (ret < 0)
        goto err_unmap;

    /* 7. 一致内存：描述符环 */
    ring = dma_alloc_coherent(&pdev->dev, MY_RING_BYTES, &ring_dma, GFP_KERNEL);
    if (!ring) {
        ret = -ENOMEM;
        goto err_vectors;
    }
    return 0;

err_vectors:
    pci_free_irq_vectors(pdev);
err_unmap:
    pci_iounmap(pdev, base);
err_release:
    pci_release_regions(pdev);
err_disable:
    pci_disable_device(pdev);
    return ret;
}
步骤 接口 漏掉会怎样
1 pci_enable_device() 设备内存空间未使能，ioremap 到的地址读回全 1
2 pci_request_regions() 两个驱动同时映射同一段 BAR，互相踩寄存器
3 dma_set_mask*() 内核按默认 32 位规划 buffer，超出设备窗口就打到错地方
4 pci_set_master() Command 寄存器的 Bus Master 位为 0，设备的 Memory 请求被根复合体丢弃（x86 上会报 Unsupported Request）
5 pci_iomap() 没有虚拟地址就碰不到寄存器
6 pci_alloc_irq_vectors() 没有中断就没有完成通知，只能靠轮询
7 dma_alloc_coherent() 描述符环没有设备侧地址

第 4 步是新手最容易漏的一步，也是症状最迷惑的一步：寄存器读写都正常，门铃也写进去了，设备状态位也动了，但数据就是不出现。因为它自己发起的 TLP 没有被主机接收——pci_set_master() 之前，这个功能在总线上的身份只是「能应答配置访问的从设备」。

用 devres 可以省掉上面那串 goto：pcim_enable_device()、pcim_iomap()、pcim_request_all_regions()（名称以本机头文件为准）。pcim_* 系列在没有 probe 成功时自动回滚，退出时自动释放，细节见《platform 设备与 devres》。remove() 里的顺序反过来：先 free_irq()，再写寄存器停掉设备，然后 dma_free_coherent()，最后 pci_free_irq_vectors()、pci_iounmap()、pci_release_regions()、pci_disable_device()。先关中断与 DMA 引擎，再释放 buffer，最后拆映射。顺序写反就会踩到「设备还在往已释放的 buffer 里写」——这类 bug 的现场是一块被复用的内存莫名其妙变成全 0xFF。

DMA 打到完全不相干的内存，系统在无关位置 panic 自己用 virt_to_phys() 或 virt_to_bus() 算地址 全仓 grep virt_to_phys 与 virt_to_bus
dma_map_single() 在 HIGHMEM 页上行为异常 该接口不能映射 HIGHMEM 改成 dma_map_page()
中断里 dma_free_coherent() 挂死或 BUG: scheduling while atomic 释放触发 TLB flush + IPI，不能在关中断上下文做 把释放丢到 workqueue
描述符的 valid 位比内容先到设备，设备读到半新半旧 缺 wmb()，CPU 或编译器重排了写序列 在置 valid 之前加 wmb()，用 WRITE_ONCE
一致内存上 CPU 与设备仍看到不一致 一致只保证 cache 层，不保证顺序，也不保证写缓冲已刷 加 mb() 或按 SoC 手册做 write flush
栈上 buffer 做 DMA，偶发内核栈损坏 栈页不保证物理连续 CONFIG_DMA_API_DEBUG 会直接报
模块加载后全局变量做 DMA 失败 模块数据段是 vmalloc，超一页就不连续 用 dma_alloc_coherent() 或 kmalloc
dma_mask 设了 64 位却仍然失败 平台主动拒绝（如 SPARC64 上 SAC 更快） 这是预期行为，走降级链
设备被 AER 复位后驱动仍在收数据 error_detected 里没停 DMA 通路 回调里关设备、停队列
lspci 里 BAR 全 0 该设备或功能号不存在，或配置空间访问返回 UR lspci -vv 看能力链表是否可读
两个功能抢同一段 BAR 只调了 pci_enable_device() 没调 pci_request_regions() 查 probe 的资源申请链

修正的错误 #

原文表述 问题 本文的处理方式
PCIe 篇：「一致性 DMA 映射……自动关闭这块内存的 Cache 缓存功能」 只在「关 cache」这一种实现下成立。现代平台多数靠硬件一致性（snooping）或按需 cache 维护达成，dma_alloc_coherent() 返回的内存并不一定被设成非 cacheable。原文把一种实现当成了定义 改为「由平台硬件/内核保证一致，无需 sync」，并在第十三章说明两种实现路径
PCIe 篇：「流式 DMA……映射的物理内存默认是开启 Cache 缓存的，传输结束后再手动解映射」 「结束之后」这个时机偏了。DMA_FROM_DEVICE 的 invalidate 必须发生在 CPU 读取之前，不是 unmap 之后 第十二章按 ownership（for_cpu / for_device）重建时序，明确 invalidate 在 CPU 读之前
PCIe 篇代码：dma_map_single(..., DMA_BIDIRECTIONAL) 之后在 DMA_FROM_DEVICE 与 DMA_TO_DEVICE 之间来回切换 sync 方向 方向在 map 与 sync 之间不一致。多次 sync 允许，但方向必须与 buffer 的实际用途一致，混用会让实现做错 cache 操作 本文的 sync 示例统一为 DMA_FROM_DEVICE（收包场景），并明确方向必须固定
PCIe 篇：「MSI 报文……CPU 收到此写事件后，硬件自动将其翻译为对应的软中断」 不是软中断。MSI 落到 LAPIC 上产生的是一条硬件中断（经 APIC 投递到某个 CPU 的向量），和 softirq 是两套机制 第二十章改为「翻译成一条中断」
PCIe 篇：s3c2410_dma_enqueue() / s3c2410_dma_config() 示例 这是 2.6.18 之前的平台私有 API，早已被 dmaengine 取代；示例里 dma_alloc_coherent(NULL, ...) 传空 dev 也不合规范 删掉该示例，在易错点里提示这类接口已废弃；dma_alloc_coherent() 需要传入一个真实的 dev
PCIe 篇 §1.5：ECAM 公式写成 (功能号 << 12) 公式本身对（每个功能 4KB），但原文未说明前提是 (设备号 << 15) 覆盖 8 个功能，读者容易漏乘 第十八章保留公式并加了展开说明
DMA 篇 §6.4：错误示例 (dma_handle & 0xffff != 0) 运算符优先级陷阱，!= 先于 &。这是原文引自旧文档的经典错例，本身没错 原样保留在「错误写法」里，只作反例出现
DMA 篇 §5.4：「一致内存仍需内存屏障」给出的 wmb() 本身正确，但原文未提 dma_alloc_coherent 在不同架构上返回的会是写合并内存，需要 mb() 而不是 wmb() 第十三章表格单列一行「顺序屏障与 cache 同步是两件事」
DMA 篇 §3.3：dma_map_* 与 pci_map_* 的关系 原文说「用通用 API 而不是总线专有 API」，方向对，但没说 pci_map_single() 在 PCI 设备上与 dma_map_single() 等价 第十四章表格标注为「不要在新代码里用」，原因补充为可移植性
DMA 篇 §2.3 表格：「不设它会怎样」列对 burst size 的描述 描述正确但没提 burst 的上界由 dma_device->max_burst 兜底 第三章末尾补了这一句
