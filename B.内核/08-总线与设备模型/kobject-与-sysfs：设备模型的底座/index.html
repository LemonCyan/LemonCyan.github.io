一、设备模型要解决什么问题 #

Linux 是宏内核，它得支持世界上几乎所有能跑的硬件。代价很直接：内核里一大半代码是驱动，而且随硬件换代还在涨。这部分代码让内核看起来臃肿、杂乱、不好维护。这不是设计失误，是宏内核必须付的账。

设备模型（Driver Model）是从 2.6 开始引入的统一抽象。它的做法是把硬件设备归纳、分类，抽出一套标准的数据结构和接口。驱动开发就从「论述题」变成「填空题」：你只需要把内核规定的结构体填好，实现规定的回调。

先看四个概念，它们是设备模型的骨架：

  • Bus（总线）：CPU 和一个或多个设备之间信息交互的通道。include/linux/device.h 里 struct bus_type 的注释就是这个口径。设备模型要求所有设备都挂在某条总线上，CPU 内部总线、虚拟总线、platform 总线都算。
  • Class（分类）：把功能或属性相似的设备集合到一起，抽出一套可共用的数据结构和接口。同类设备的驱动不必重复定义公共部分，直接从 Class 继承即可。
  • Device（设备）：抽象系统中所有硬件设备，描述它的名字、属性、从属的 Bus、从属的 Class。
  • Device Driver（驱动）：抽象设备的驱动程序，包含设备初始化、电源管理相关的接口实现。

另有一个特例：有类设备通过自己的设备控制器直接连 CPU，CPU 用常规寻址访问它们，这种连接不属于传统总线。为了让模型普适，内核虚构了一条 Platform Bus 给它们挂。

设备模型的核心思想有四条，用一句话概括就是「用统一的数据结构换取统一的处理流程」：

  1. 统一驱动编写格式。用 struct device 和 struct device_driver 分别描述「有什么用」和「怎么用」。
  2. 实现即插即用。Device 和 Driver 同名（严格说是匹配成功）时，内核调用 Driver 的 probe 初始化设备。热拔插设备拔出时 Device 结构不存在，Driver 就不执行初始化；插入时内核创建 Device，触发 probe。
  3. 解决设备间依赖。Bus → Device 的树状结构表达了「启动设备前必须先启动它挂的总线」这类依赖，电源管理和开关机流程靠这棵树自动定序，不用驱动作者手工维护。
  4. 引入面向对象。Class 结构把共性抽到一层，减少重复劳动。

下面这条线是本文的主线：四个核心结构体都不是凭空长出来的，它们各自内嵌一个 kobject，靠 kobject 拿到引用计数、层次结构、sysfs 投影这三样能力。

text
struct bus_type        -> 内嵌 kobject（早期经 subsys_private）-> /sys/bus/<name>/
struct class           -> 内嵌 kobject（早期经 subsys_private）-> /sys/class/<name>/
struct device          -> 内嵌 kobject                       -> /sys/devices/...
struct device_driver   -> 内嵌 kobject                       -> /sys/bus/<bus>/drivers/<drv>/

这条线往下的东西，就是本篇的全部内容。

二、kobject 是什么：一个能自我管理的对象基类 #

kobject 是设备模型的基础，也是这一层里最难啃的一块。Documentation/kobject.txt 那份文档本身就是内核里少数几个作者承认「不好读」的文档。

它诞生的理由很朴素：设备数量、种类太多，内核里会有海量的设备模型数据结构。这些结构体一定有共同功能，不抽出来就会产生大量冗余代码。抽出来之后，公共部分就是 kobject。

到目前为止，kobject 提供三样东西：

  1. 层次结构。通过 parent 指针把所有 kobject 串成一棵树，这棵树在 sysfs 里就是目录树。
  2. 引用计数。记录自己被引用多少次，归零时释放。这是 kobject 诞生时的唯一功能，也是最本质的那个。
  3. 用户空间投影。和 sysfs 配合，把每个 kobject 及其特性以文件形式暴露给用户空间。

两个必须先记住的前提：

  • kobject 几乎不会单独存在。它的正经用法是内嵌在一个更大的结构体里，为宿主提供底层能力。谁内嵌谁负责生命周期，kobject 只负责计数和释放时机。
  • 驱动作者很少直接调 kobject 接口，用的是构建在它上面的设备模型接口（device_register、device_create 之类）。但接口下面发生了什么，你得知道，否则 release 写错、put 多一次少一次这类问题根本查不出来。

实现文件就两个：

文件 内容
include/linux/kobject.h 所有数据结构定义、接口声明
lib/kobject.c 核心功能实现

4.x 之后这层仍在 lib/kobject.c，但 kset 相关结构与 subsys_private 的重构把不少逻辑挪了位置，具体分界点未验证。

kobject、kset、kobj_type 三个概念先摆清楚，后面所有代码都围绕它们：

概念 一句话定义 在 sysfs 中的形态
kobject 基本数据类型，自带引用计数与父子关系 一个目录
kset 一个特殊的 kobject，用来集合相似的 kobject 一个目录
kobj_type 同一类 kobject 的属性操作集合 不直接出现，决定目录下文件的读写行为

kobj_type 之所以要独立出来，是因为大量 kobject 共用同一套属性操作集。把它放进 kobject 里就是每个对象存一份重复的指针表，独立出来只存一个指针。这个设计在源码里的命名和解释都非常抽象，第七章之后会一点点拆。

三、struct kobject 的字段 #

2.6.x 到 3.x 的形态，注释标注 include/linux/kobject.h 第 60 行附近：

c
/* Kobject: include/linux/kobject.h line 60 */
struct kobject {
    const char *name;
    struct list_head    entry;
    struct kobject      *parent;
    struct kset     *kset;
    struct kobj_type    *ktype;
    struct sysfs_dirent *sd;
    struct kref     kref;
    unsigned int state_initialized:1;
    unsigned int state_in_sysfs:1;
    unsigned int state_add_uevent_sent:1;
    unsigned int state_remove_uevent_sent:1;
    unsigned int uevent_suppress:1;
};

字段逐个过：

字段 类型 作用 谁能改
name const char * 该 kobject 的名字，同时是 sysfs 里的目录名 只能在 add 时由格式化参数生成，改名走 kobject_rename
entry struct list_head 挂进 kset 链表的钩子 由 kobj_kset_join 处理
parent struct kobject * 父对象，决定 sysfs 树位置 add 时确定，未指定则取 kset
kset struct kset * 所属集合，可为 NULL 由上层结构体初始化时设定
ktype struct kobj_type * 属性操作集，必须非空 kobject_init 时设定
sd struct sysfs_dirent * 该对象在 sysfs 里的表示 由 sysfs_create_dir 回填
kref struct kref 原子引用计数 只能通过 kobject_get/kobject_put
state_initialized 位域 1 bit 是否已初始化，用于 Init/Put/Add 的异常校验 内部
state_in_sysfs 位域 1 bit 是否已在 sysfs 中呈现，决定自动注销时要不要摘目录 内部
state_add_uevent_sent 位域 1 bit 是否已发过 ADD uevent 内部
state_remove_uevent_sent 位域 1 bit 是否已发过 REMOVE uevent 内部
uevent_suppress 位域 1 bit 置 1 则忽略所有上报的 uevent 驱动可写，见第十六章

几个要注意的点：

  • name 不能随便改。kobject 加进内核时要按名字注册到 sysfs，之后这个字段就不该再动。要改名调 kobject_rename，它会主动处理 sysfs 那边的事。默认 name 指向 kobject_add 传进来的格式化字符串生成的堆内存，由 kobject_cleanup 负责释放。
  • kset 存在而 parent 未指定时，parent 会被设成 kset。别忘了 kset 本身就是个 kobject，所以这在类型上是自洽的。
  • ktype 是强制的。每个 kobject 必须有一个 ktype，没有的话内核会提示错误。kobject_cleanup 里会拿这一点做检查，sysfs_open_file 里也会因为缺 sysfs_ops 直接拒绝注册 attribute。
  • 三个 state_*_uevent_sent 是配套的：发过 ADD 但没发 REMOVE，注销时会补发 REMOVE，否则用户空间会残留一个已经不存在的设备。
  • sd 是 sysfs 的内部节点指针，是 struct sysfs_dirent 类型。4.x 之后 sd 的具体类型和用法有变，字段是否仍名为 sd、其尖层是否改为 kernfs_node，请以你手上的源码为准，本文不保证。

版本对照（重要）：

变化点 2.6.x ~ 3.x 4.x 之后 说明
name 类型 素材写作 const char * 4.x 改为 const char * 早期 2.6 版本是 char *，后来加 const。见下方勘误
引用计数 struct kref kref 仍为 struct kref 更早的原型里出现过 struct kref 之外的直接计数字段，kref 是定形后的结果

四、引用计数：kref 与 kobject_get/put #

kref 定义在 include/linux/kref.h，是一个可用于原子操作的引用计数封装。kobject 把「什么时候可以释放」这件事完全交给了它。

c
/* include/linux/kobject.h, line 103 */
extern struct kobject *kobject_get(struct kobject *kobj);
extern void kobject_put(struct kobject *kobj);

两个接口的行为：

  • kobject_get：调 kref_get，计数加一，返回 kobj 本身，方便链式使用。
  • kobject_put：以内部接口 kobject_release 为参数调 kref_put。kref 模块在计数归零时调 kobject_release。

也就是说，kobject_put 返回时对象是否还在，取决于计数是否归零。这个语义是所有后续 bug 的来源：put 之后不要再碰 kobj，除非你手上还另有引用。

用引用计数的规矩只有两条，但必须当纪律执行：

  1. 拿到一个指向含 kobject 的结构体的指针，并且要跨过当前栈帧继续用它，就 get 一次；用完了 put。
  2. get 和 put 必须配对，且配对要在一个函数里能看出来。跨函数传递的所有权要在函数注释里写清楚。

kref 在 3.x 到 4.x 之间有过一次接口口径调整（kref_get 之前不做零值检查这件事被反复讨论，后来出现过 kref_get_unless_zero 这类辅助），kobject_get 的语义保持不变：无条件加一。这一点在 4.x 上仍是如此，「未验证」范围的只是内部断言细节。

五、生命周期：release 回调与 kobject 的销毁时机 #

先看 kobject_init 对计数的影响：初始化为 1。也就是说 kobject 一出生就自带一个引用，这个引用由「创建者」持有。创建者 put 掉它，才算交出所有权。

kobject_put 到零之后的路径：

text
kobject_put
  -> kref_put(&kobj->kref, kobject_release)
       -> 计数归零时回调
  -> kobject_release(kref)
       -> 由 kref 反推回 kobject 指针
  -> kobject_cleanup(kobj)

kobject_cleanup 是真正干活的地方，顺序如下：

  1. 检查该 kobject 有没有 ktype。没有就打印警告。这一步是为了让「忘了设 ktype」在开发期就暴露。
  2. 如果发过 ADD uevent 却没发 REMOVE uevent，补发 REMOVE。
  3. 如果 state_in_sysfs 表明它注册在 sysfs 里，调 kobject_del 摘掉目录。
  4. 调 ktype->release，释放宿主结构体的内存。这一步是唯一的释放点，也是唯一的机会。
  5. 释放 name 占用的内存。

release 回调是这套机制里最容易被写错的一环。它在引用计数归零时被调用，不是在 kobject_del 时，不是在 device_unregister 返回时。因此：

  • release 里必须释放宿主结构体本身（用 container_of 反推），kobject 只是它的一部分，单独 kfree(kobj) 在嵌入式用法下是错的。
  • release 里不能调用任何会再次访问该对象的接口。此时对象已经逻辑死亡。
  • release 里可以睡眠（它跑在进程上下文），但不要在里面做会 get 自己的事。

只有一种情况 kfree(kobj) 是对的：kobject 是自己分配的，宿主就是 kobject 本身。这条路径是第十八章会讲的 dynamic_kobj_ktype。

c
/* lib/kobject.c, line 605 */
static void dynamic_kobj_release(struct kobject *kobj)
{
    pr_debug("kobject: (%p): %s\n", kobj, __func__);
    kfree(kobj);
}

static struct kobj_type dynamic_kobj_ktype = {
    .release    = dynamic_kobj_release,
    .sysfs_ops  = &kobj_sysfs_ops,
};

dynamic_kobj_release 直接 kfree，因为这种 kobject 是 kobject_create 用 kmalloc 单独分配的。dynamic_kobj_ktype 就是模块自带的 ktype。这个 ktype 只有 release 和 sysfs_ops 两项，default_attrs 为空，说明它自己不预设任何 attribute 文件。

六、parent 与 kset：kobject 的树形组织 #

kobject 的层次结构只有一根指针：parent。但实际建树时有两个来源，parent 和 kset，关系要理清。

kobject_add_internal 里的处理顺序：

  1. 校验 kobj 和 kobj->name 合法性，不合法打印错误退出。
  2. 有 parent 就给 parent 加一次引用（kobject_get）。子对象存活期间，父对象不能先死，靠的是这次加引用。
  3. kobj->kset 非空则调 kobj_kset_join 把它挂进 kset 链表。
  4. 如果此时 parent 仍为空，而 kset 存在，就把 parent 设成 kset 的 kobject（&kset->kobj），并给 kset 加引用。
  5. 调 create_dir 在 sysfs 里建目录。失败则回滚前面几步，成功则置 state_in_sysfs = 1。

由此得出的定位规则（这也是最实用的一张表）：

情况 parent 取谁 sysfs 位置
显式给了 parent 该 parent parent 目录下
没给 parent，有 kset kset 的 kobject kset 目录下
没给 parent，也没 kset 无（挂在 sysfs 根） /sys/ 下
kset 的 kobject 自己 由注册时的 parent_kobj 决定 /sys/ 或指定目录下

两个反直觉的推论：

  • kset 的 kobj.parent 和 kset 的成员关系是两件不同的事。成员在 kset->list 里，而 sysfs 位置由 parent 决定。二者一致只是常见情况，不是硬绑定。
  • 删除一个 kobject 不会顺手删掉它的子对象。子对象因为持有父的引用而让父活得更久，但父的 del 不会递归。想让子树整体消失，得自己遍历。这也是为什么 device_unregister 之前要先确保子设备已经处理干净。

七、kobject 的名字与它在 sysfs 里的位置 #

名字是 kobject 在 sysfs 里的身份。生成路径有两条：

c
/* include/linux/kobject.h, line 85 */
extern void kobject_init(struct kobject *kobj, struct kobj_type *ktype);
extern __printf(3, 4) __must_check
int kobject_add(struct kobject *kobj, struct kobject *parent,
                const char *fmt, ...);
extern __printf(4, 5) __must_check
int kobject_init_and_add(struct kobject *kobj,
            struct kobj_type *ktype, struct kobject *parent,
            const char *fmt, ...);

kobject_add 的第三个参数是 printf 风格的格式化字符串，不是裸名字。kobject_add_varg 解析它，把结果写进 kobj->name，然后调 kobject_add_internal。所以名字是在 add 时按需分配的。

三个接口的分工：

接口 做什么 何时用
kobject_init 填 ktype、初始化计数/链表/标志 宿主结构体已分配好，kobject 是其中一个成员
kobject_add 生成 name，加入 parent/kset，建 sysfs 目录 紧接着 kobject_init
kobject_init_and_add 上面两步合一 绝大多数场景

kobject_init 的执行逻辑，逐条：

  • 确认 kobj 和 ktype 非空。
  • 若 state_initialized 已置位，说明这个指针被重复初始化，打印错误提示和堆栈信息。这不是致命错误，流程继续。内核在这里选择「吵但你继续说」，所以重复初始化不会立刻炸，但后果是计数被重置，之后必然出现提前释放或泄漏。
  • 初始化内部参数：引用计数、list_head、各种标志位清干净。
  • 把 ktype 赋给 kobj->ktype。

kobject_add 的逻辑：

  • 确认 kobj 非空且已初始化，否则错误退出。
  • 转 kobject_add_varg 完成添加。

名字相关的坑，三个：

  1. 名字里出现 / 会让 sysfs 目录层级错乱。内核在 sysfs_create_dir 一带有校验，但别指望它帮你挡所有输入。
  2. 名字是全局可见的，同一个 parent 下重名会失败。kobject_add 返回负值，且带 __must_check，你必须检查返回值。
  3. 改名不能直接写 kobj->name。用 kobject_rename，它负责 sysfs 那边的目录迁移；迁移完还要考虑是否发 KOBJ_MOVE uevent。

八、ktype 与 attribute 组 #

kobj_type 的原型，注释标注 include/linux/kobject.h 第 108 行附近：

c
/* include/linux/kobject.h, line 108 */
struct kobj_type {
    void (*release)(struct kobject *kobj);
    const struct sysfs_ops *sysfs_ops;
    struct attribute **default_attrs;
    const struct kobj_ns_type_operations *(*child_ns_type)(struct kobject *kobj);
    const void *(*namespace)(struct kobject *kobj);
};
字段 作用
release 释放宿主结构体内存。唯一释放点，见第五章
sysfs_ops 该类型 kobject 的 sysfs 读写回调，即 show/store 的入口
default_attrs 该类型默认的 attribute 列表，kobject_add 时一并注册成文件
child_ns_type 与 sysfs 命名空间相关，返回子对象的命名空间类型操作集
namespace 返回该 kobject 所属命名空间

default_attrs 是 struct attribute **，以 NULL 结尾的指针数组。这批 attribute 是「自动打折」的：create_dir 建完目录后调 populate_dir，遍历这个数组逐个建文件。所以你在 ktype 里列出的属性，驱动作者什么都不用写，对象一注册文件就在。

default_attrs 的实际写法：

c
static struct attribute *my_obj_attrs[] = {
    &dev_attr_foo.attr,
    &dev_attr_bar.attr,
    NULL,   /* 必须以 NULL 结尾 */
};

static struct kobj_type my_obj_ktype = {
    .release    = my_obj_release,
    .sysfs_ops  = &my_obj_sysfs_ops,
    .default_attrs  = my_obj_attrs,
};

default_attrs 的类型在后续内核里出现过 const struct attribute_group **default_groups 的替代（把散装数组升级成 attribute group 数组），但 default_attrs 本身在 4.x 相当长一段时间里还在。具体切换版本未验证。

child_ns_type 和 namespace 这两个字段，是给网络命名空间这类场景用的：sysfs 里同名目录在不同命名空间下指向不同对象。日常驱动开发碰不到，看到时知道它是命名空间钩子就够了，本篇不展开。

九、state_initialized / state_in_sysfs 这些位 #

五个 1-bit 标志，看着琐碎，每一个都对应一处「内核帮你兜底」的逻辑。把它们的作用、谁置位、谁清位、清错会怎样列出来：

标志位 置位时机 清位时机 谁读它 错了会怎样
state_initialized kobject_init 不主动清 kobject_init（查重复初始化）、kobject_add（查未初始化） 重复 init 只警告不中止，计数被重置，后续提前释放
state_in_sysfs create_dir 成功 kobject_del kobject_cleanup、kobject_del 漏置位则清理时不摘目录，残留空目录；多置位则重复摘
state_add_uevent_sent 发送 KOBJ_ADD 成功后 不主动清 kobject_cleanup 判断是否补发 REMOVE 未置位则不补发 REMOVE，用户空间残留设备
state_remove_uevent_sent 发送 KOBJ_REMOVE 成功后 不主动清 同上 提前置位会吞掉该补发的 REMOVE
uevent_suppress 驱动显式写入 驱动显式清除 kobject_uevent_env 忘了清则该对象一生都不再上报事件

state_initialized 的检查方式值得单独说一句。kobject_init 里判断这个位已经置位时会打印错误和堆栈，但流程继续。这是内核在「帮开发者」和「不破坏现场」之间的取舍：早期发现比硬崩强，可硬崩会掩盖真正的调用路径。代价是重复初始化的 bug 会以「引用计数莫名归零」的形态在很远的地方爆发。

state_in_sysfs 是自愈逻辑的开关。宿主的 release 里不需要手动 sysfs_remove*，kobject_cleanup 会替你做。前提是 state_in_sysfs 准确，而这个位由 create_dir 和 kobject_del 维护，正常路径不会错。手工在别处 kfree 掉 kobject 或直接 memset 宿主结构体，才会把它搞脏。

uevent_suppress 是唯一给驱动准备的可写位。用它临时静音某个对象的事件，比在 kset 的 filter 里加特判更直接。

十、kset：kobject 的集合 #

struct kset 的原型，注释标注 include/linux/kobject.h 第 159 行附近：

c

    struct list_head list;
    spinlock_t list_lock;
    struct kobject kobj;
    const struct kset_uevent_ops *uevent_ops;
};
字段 作用

kset 在设备模型里扮演「同类对象的目录」这个角色。/sys/class/net、/sys/bus/pci、/sys/block 这些目录背后都有对应的 kset。

uevent_ops 是 kset 存在感最强的地方。任何 kobject 上报 uevent 时，都要走它所属 kset 的 uevent_ops，由 kset 统一加环境变量或过滤事件。反过来说，一个不属于任何 kset 的 kobject 不允许上报 uevent，这条在第十七章会看到具体的校验位置。

kset 的四个接口：

extern void kset_unregister(struct kset *kset);

接口 逻辑

kset_unregister 直接 kobject_put 释放内部 kobj，计数归零时由 ktype 的 release 释放整个 kset
kset_create_and_add 内部调 kset_create 用 kzalloc 分配一个 kset，再 kset_register

kset_create 用 kzalloc 分配时，会配一个 kset_ktype 类型的 ktype，专门用来释放「由 kset 模块自己分配」的空间。这就是「谁分配谁释放」的落地方式：外部 kmalloc 的 kset 用外部提供的 ktype，模块分配的 kset 用 kset_ktype。

一个常见误解：kset 不是「kobject 的数组」，它只是链表加一个 kobject 头。成员容量没有上限，顺序也不保证。遍历 kset 成员时要拿 list_lock，或者用 kset_find_obj 这类封装。

十一、sysfs 是什么：把内核数据结构投影成文件树 #

sysfs 是一个基于 RAM 的文件系统。它和 kobject 一起，把内核的数据结构导出到用户空间，用文件目录树的形式提供对这些数据结构及其属性的访问。

它有文件系统的全部属性，但本篇只谈它在设备模型里的角色，不谈 fs/sysfs 的实现细节。要看清三件事：sysfs 与 kobject 的关系、attribute 的概念、sysfs 的文件操作接口。

几个定性描述值得先钉住：

  • sysfs 是纯虚拟的，没有一个实际存文件的介质。读一个 sysfs 文件，就是动态地从 kobject 层次结构里提取信息、现生成内容。重启后里面的东西自然没了。
  • sysfs 的信息源就是 kobject 层次结构本身。每个在内核里注册的 kobject 都对应 sysfs 里一个目录。
  • sysfs 用 VFS 接口去读写 kobject 层次，它是 VFS 上的一个文件系统实现，因此要实现 file_operations、dentry_operations、inode_operations 这一套。

三个 VFS 概念在 sysfs 里的对应关系，是理解「为什么 open 一个 sysfs 文件会跑到驱动的 show 函数」的关键：

内核对象 在 sysfs 中的含义 实现方式
kobject 目录 sysfs_create_dir 建 sysfs_dirent，类型为目录
attribute 文件 sysfs_create_file，sysfs_dirent 类型为普通/二进制文件
对象关系 符号链接 sysfs_create_link

VFS 的调用链走一遍，比看十遍结构体定义有用：

text
open("hello.c", O_RDONLY)
  -> sys_open()
  -> filp_open()
  -> dentry_open()
  -> file->f_op->open()

不同文件系统的 f_op->open 不同，sysfs 下就是 sysfs_open_file()。各文件系统把信息都抽象到 dentry 和 inode 里，上层就不必关心底层实现。这就是 VFS 的做法，本质是面向对象。

sysfs 有自己的内存节点层，2.6.x ~ 3.x 形态下是 struct sysfs_dirent。它是 sysfs 里文件或目录在内存中的代表，只表示类型（目录/普通文件/二进制文件/链接）和层级关系，其余信息放在对应 inode 里。创建或删除一个 sysfs 文件，实际动作就是在这棵 sysfs_dirent 树上增删节点。

sysfs_dirent 的关键字段（2.6.x 形态，抓取件有排版损坏，字段顺序按语义整理）：

字段 作用
s_count 引用计数
s_active 激活状态，配合 sysfs_get_active 使用
s_parent 父节点
s_sibling 兄弟节点，按 s_ino 大小顺序串起
s_name 节点名称
s_dir / s_symlink / s_attr / s_bin_attr 联合体，按类型分别记录目录的 kobj、链接目标、普通属性、二进制属性
s_flags 类型与状态标志
s_ino inode 索引，创建节点时动态申请
s_mode 权限模式
s_iattr 临时属性（chmod/chown 用）

inode 那侧存的是主从设备号、一组 file_operations、一组 inode_operations。inode_operations 在 sysfs 里只对目录实现了两个：.lookup = sysfs_lookup（找不到 inode 就创建一个，用 sysfs_init_inode 赋值）、.setattr = sysfs_setattr（改权限用）。

再往下的 dentry 是目录项，是 inode 的链接。它存在的目的是加快访问。三者关系拉直说：

  • sysfs_dirent 是 sysfs 自己的节点树，d_fsdata 从 dentry 指回它。
  • inode 由 sysfs_get_inode(sd) 按需创建，从 s_ino 和 sysfs_sb 算散列位置。
  • dentry 也是按需创建。open 时 path_walk 逐层查找，找不到就由父 dentry 的 inode lookup（即 sysfs_lookup）创建。

sysfs_lookup 的主体逻辑，2.6.x 形态：

c
static struct dentry *sysfs_lookup(struct inode *dir, struct dentry *dentry,
                                   struct nameidata *nd)
{
    struct dentry *ret = NULL;
    struct sysfs_dirent *parent_sd = dentry->d_parent->d_fsdata;
    struct sysfs_dirent *sd;
    struct inode *inode;

    mutex_lock(&sysfs_mutex);
    /* 在父节点下找名字为 dentry->d_name.name 的子节点 */
    sd = sysfs_find_dirent(parent_sd, dentry->d_name.name);
    if (!sd) {
        ret = ERR_PTR(-ENOENT);
        goto out_unlock;
    }
    inode = sysfs_get_inode(sd);
    if (!inode) {
        ret = ERR_PTR(-ENOMEM);
        goto out_unlock;
    }
    dentry->d_op = &sysfs_dentry_ops;   /* 只提供 sysfs_d_iput */
    dentry->d_fsdata = sysfs_get(sd);
    d_instantiate(dentry, inode);
    d_rehash(dentry);
out_unlock:
    mutex_unlock(&sysfs_mutex);
    return ret;
}

这段代码解释了「sysfs 不存内容」这句话的具体含义：

  • sysfs_create_dir / sysfs_create_file 只往 sysfs_dirent 树上加节点并申请 s_ino，此时不建 inode。
  • 真正用到时才建 inode、才建 dentry。
  • 因此一个从未被访问过的 sysfs 文件，在内存里只是一个 sysfs_dirent 节点，没有 inode，也没有 dentry。

sysfs 初始化时一次创建三样东西：超级块 sysfs_sb、根目录 dentry root、根 sysfs_dirent 节点 sysfs_root。sysfs_root 下的子节点由后续的设备/属性注册逐步挂上来。

sysfs_dirent 这一整套在 3.14 前后被 kernfs 取代（fs/kernfs/），struct kernfs_node 顶替 sysfs_dirent，s_name/s_parent/s_sibling 变成 name/parent/rb（红黑树）一类的新形态。这段迁移的准确版本边界我未逐一核对，写「未验证」。你在 4.x 源码里搜不到 struct sysfs_dirent 就是这个原因。

十三、attribute：kobj_attribute 与 device_attribute #

sysfs 目录描述的是 kobject，而 kobject 是某个具体类型变量（如 struct device）的一部分。所以「kobject 的属性」实际是宿主变量的属性：可以是名字、一个内部变量、一个字符串，随便什么。这些属性在 sysfs 里以文件形式提供，文件的读写由定义了该属性的模块负责记录和返回。

一句话概括：attribute 是内核空间和用户空间交换信息的方法。某个驱动有个变量，希望用户空间能改它来控制行为，就把它以 sysfs attribute 的形式开放出去。

attribute 分两类。基础定义在 include/linux/sysfs.h：

/* include/linux/sysfs.h, line 100 */

    struct attribute    attr;
    size_t          size;

    ssize_t (*write)(struct file *, struct kobject *, struct bin_attribute *,

看到 struct attribute 会犯嘀咕：就 name 和 mode 两个真正有用的字段，剩下的都是内核查锁用的调试字段，那文件操作接口在哪？

答案是 attribute 本身不带操作函数。它只是一张「文件名片」，操作函数统一由 kobj_type->sysfs_ops 提供，再由 sysfs_ops 用 container_of 转发到具体类型。这一层转接是 sysfs 设计的精髓，也解释了为什么 struct attribute 要设计得这么空。

于是就有了「每种设备模型结构体都有一套自己的 xxx_attribute」这个模式。本篇涉及的两种，以及工程里最常见的第三种：

类型 定义位置 内嵌 回调签名 对应 sysfs 层级

struct bin_attribute include/linux/sysfs.h struct attribute attr read/write/mmap，带 loff_t 偏移 二进制文件
struct kobj_attribute include/linux/kobject.h struct attribute attr show(struct kobject *, struct kobj_attribute *, char *)
store(struct kobject *, struct kobj_attribute *, const char *, size_t)		 裸 kobject 目录
struct device_attribute include/linux/device.h struct attribute attr show(struct device *, struct device_attribute *, char *)

struct class_attribute include/linux/device.h struct attribute attr show(struct class *, struct class_attribute *, char *)
store(struct class *, struct class_attribute *, const char *, size_t)		 /sys/class/<name>/ 下

关键差别只在第一个参数的类型：kobject / device / class / device_driver。sysfs_ops 拿到的永远是最原始的 struct kobject *，各模块用自己的宏把它转回具体指针。device 那套用的是 to_dev_attr + dev_get_drvdata，class 那套用的是 to_class_attr 加 to_subsys_private。

kobj_attribute 是本文这一层的原配。它的定义形态和配套宏：

c
/* include/linux/kobject.h 附近，2.6.x ~ 3.x 形态 */

    struct attribute attr;
    ssize_t (*show)(struct kobject *kobj, struct kobj_attribute *attr,
                    char *buf);
    ssize_t (*store)(struct kobject *kobj, struct kobj_attribute *attr,
                     const char *buf, size_t count);
};

#define __ATTR(_name, _mode, _show, _store) {               \
    .attr = {.name = __stringify(_name), .mode = _mode },   \
    .show = _show,                                          \
    .store = _store,                                        \
}

    .attr = { .name = __stringify(_name), .mode = 0444 },   \
    .show = _name##_show,                                   \
}

__ATTR 和 __ATTR_RO 是套路化写法，省掉重复的 .attr = {...}。__ATTR_RO 只给 show，权限 0444，写操作在 VFS 层就被挡掉。这几个宏在各内核版本里形态稳定，但宏的可写变体（__ATTR_WO、__ATTR_RW）是在较晚版本才补齐的，具体版本未验证。

device_attribute 的写法与之平行，多一个 DEVICE_ATTR 宏家族，且它的 store 返回 count，show 返回写入 buf 的字节数。两种类型的 show/store 内部都要用 container_of 宏，别手写 (struct device_attribute *)attr，那在属性作为更复杂结构体的成员时会错。

十四、文件的创建与删除 #

attribute 变文件的第一步在 system_create_file 这一族接口里。核心是 sysfs_create_file，实现在 fs/sysfs/file.c。它的实现大多是文件系统层面的操作，和设备模型关系不大，此处不展开实现细节，只给契约：

接口 作用 失败返回
sysfs_create_file(kobj, attr) 在 kobj 目录下建一个属性文件 负 errno，目录不存在时为 -ENOENT
sysfs_create_files(kobj, attrs) 批量建，attrs 以 NULL 结尾 同上，部分成功会回滚
sysfs_remove_file(kobj, attr) 删一个属性文件 无返回值
sysfs_create_bin_file(kobj, bin_attr) 建二进制属性文件 负 errno
sysfs_remove_bin_file(kobj, bin_attr) 删二进制属性文件 无返回值
sysfs_create_link(kobj, target, name) 建符号链接 负 errno
sysfs_remove_link(kobj, name) 删符号链接 无返回值

几条创建规则，记牢能省很多调试时间：

  1. 目录必须先存在。sysfs_create_file 不帮你建父目录，kobject_add 成功之后才能建属性文件。
  2. kobj 的方向别搞反：是「attribute 属于哪个 kobject」，不是「kobject 属于哪个 attribute」。参数顺序是 (kobj, attr)。
  3. 同一目录下属性名不能重复。重名返回 -EEXIST。
  4. 属性文件的 mode 只在创建时生效。运行中 echo 444 > .../ 之类不改变内核里的 attr->mode。
  5. 删除文件不会同步等待所有打开的 fd 关闭。内核侧 sysfs_remove_file 会置 s_active 为 0，新的 open 直接被拒，已打开的 fd 在 close 前仍可读（行为细节各版本有差异，未验证）。

自动创建与手动创建的分界：

方式 谁建文件 注销时谁删
ktype->default_attrs populate_dir 在建目录时自动建 kobject_del 连带处理
显式 sysfs_create_file 驱动自己调 驱动自己调 sysfs_remove_file

第二种方式多了「必须记得删」的责任。忘了删的后果是：kobject 退场时，属性文件指向的 attr 所在的模块内存已经释放，用户读文件就踩到已释放内存。这类 crash 的堆栈大多落在 sysfs_read_file，但根因在你忘了 remove。

另一个方向的问题：sysfs_remove_file 之后紧接着 kobject_put，看着安全，实测仍会触发访问已释放内存（打开着的 fd 还在等 s_active）。正规做法是先 kobject_del 再 put，让 sysfs 侧确认不再有活跃访问。这个顺序在 kobject_cleanup 里也是这个序。

整个模式一次说清，这个模式在所有 *_attribute 上都成立：

  1. 模块定义自己的 xxx_attribute，第一个成员必须是 struct attribute（或 bin_attribute 里第一个成员是 attribute）。
  2. 模块在 ktype 的 sysfs_ops 里实现本模块整体的 show/store。
  3. 被调用时用 container_of 从 struct attribute * 反推出 xxx_attribute *，再从 kobject * 反推出宿主（device/class/driver）。
  4. 转接到 xxx_attribute 里挂的 show/store。

十六、uevent：内核事件怎么通知到用户态 #

uevent 属于 kobject，职责单一：kobject 状态变化（增加、移除等）时通知用户空间程序。

典型用途就是热拔插。U 盘插上，USB 驱动动态创建表示它的 device 结构（连同其中的 kobject），告知用户空间；用户空间为该盘创建 /dev/ 下的设备节点，再通知其他程序把它 mount 上来。整条链路里，驱动只负责「发事件」，剩下的全在用户态。

机制本身不复杂：设备模型里任何设备有事要上报，就调 uevent 提供的接口。uevent 模块把事件格式准备好，然后走两条路送到用户空间：

通道 机制 是否需要用户态常驻进程
netlink NETLINK_KOBJECT_UEVENT 组播，udev/mdev 订阅 需要，订阅者
kmod call_usermodehelper 直接执行 uevent_helper 需要，一个可执行文件/脚本

两条路可以同时走，现代系统主要靠 netlink。kmod 那条路在内核配置里能关掉（CONFIG_UEVENT_HELPER）。

代码只涉及两个文件：

  • include/linux/kobject.h
  • lib/kobject_uevent.c

KOBJ_MOVE 只有在 kobject 真的改变了 sysfs 位置时才该发。先 kobject_rename 再发 MOVE 是正确顺序，反了用户空间拿到的路径已经失效。

十七、kobject_uevent 的调用链 #

kobject_uevent_env 是主实现，步骤按顺序走完：

  1. 查找 kobj 本身或其 parent 是否从属于某个 kset。找不到就报错返回。这就是「不属于 kset 的 kobject 不许发 uevent」的落地位置。
  2. 查 kobj->uevent_suppress，置位则直接返回，什么都不发。
  3. 所属 kset 有 uevent_ops->filter 就调它，非 0 则丢弃本次上报。
  4. 判断所属 kset 是否有合法名称（叫声 subsystem，早期内核版本的叫法有差异），没有就不许上报。
  5. 分配本次上报用的环境变量 buffer（结果存在 env 指针里），同时取该 kobject 在 sysfs 里的路径信息。用户空间程序要靠这个路径回去访问对象。
  6. 调 add_uevent_var 把 ACTION、路径、SUBSYSTEM 等信息塞进 env。
  7. 传入的 envp 不空，就解析它，同样用 add_uevent_var 逐个追加。
  8. kset 有 uevent_ops->uevent 就调它，把 kset 统一的环境变量加进 env。
  9. 按 action 类型设置 kobj->state_add_uevent_sent / state_remove_uevent_sent，记录正确状态。
  10. 用 add_uevent_var 加一行 SEQNUM=%llu 的序列号。
  11. 若定义了 CONFIG_NET，走 netlink 发送。
  12. 以 uevent_helper、subsystem、加上标准环境变量（HOME=/、PATH=/sbin:/bin:/usr/sbin:/usr/bin）的 env 为参数，调 kmod 的 call_usermodehelper 上报。

uevent_helper 的内容由内核配置项 CONFIG_UEVENT_HELPER_PATH 决定（配置项定义在 drivers/base/Kconfig，取值在 lib/kobject_uevent.c 第 32 行附近），它指定一个用户空间程序或脚本来解析上报的 uevent，例如 /sbin/hotplug。call_usermodehelper 做的事就是 fork 一个进程，以 uevent 为参数执行这个 helper。

两个状态位的更新放在第 9 步而不是发完之后，是刻意的：事件一旦进入「已准备发送」阶段，就认为它已经发生。所以即使 netlink 发送失败，state_add_uevent_sent 也是置位的，kobject_cleanup 仍会补发 REMOVE。

用户空间收到的标准环境变量，最少是这几项：

变量 含义 备注
ACTION 事件类型字符串，如 add/remove/change 由 kobject_action 转换
DEVPATH 对象在 sysfs 下的路径 如 /devices/pci0000:00/...，不含 /sys 前缀
SUBSYSTEM 所属 kset 的名字 来自 uevent_ops->name
SEQNUM 单调递增序号 用户态用来检测事件丢失/乱序
MAJOR/MINOR 主次设备号 设备类对象才有
DEVNAME 设备名 由 devtmpfs/驱动补

MAJOR/MINOR/DEVNAME 不是 uevent 核心补的，是设备模型层（device_uevent 那一层）加的。这也说明：uevent 是机制，具体填什么由上层决定。

十八、/sys 目录树的结构 #

/sys 的顶层目录不是随便排的，每一层对应设备模型的一个概念。

子目录 内容 内核侧主要结构
/sys/devices 内核把所有设备按连接关系组织的分层表达，是 /sys 里最核心的目录结构 struct device
/sys/dev 按字符/块设备的主次设备号（major:minor）链接到 /sys/devices 下真实设备的符号链接 devtmpfs，2.6.32 起
/sys/bus 按总线类型分层。/sys/devices 里的设备都能在所属总线目录下找到符号链接 struct bus_type
/sys/class 按设备功能分类。无论设备挂在哪种总线上，功能同类就出现在同一目录 struct class
/sys/block 块设备入口（现代内核），多数条目是指向 /sys/devices 的链接 早期是 /sys/block，后来并入 /sys/class/block
/sys/firmware 固件相关接口，如 dmi、acpi、efi 各固件子系统
/sys/kernel 内核可调参数。早期只有 uevent_helper、kexec_loaded、mm、新式 slab 分配器等少数几项在此，其余可调参数仍走 sysctl（/proc/sys/kernel） 各子系统
/sys/module 系统中所有模块的信息，内联进 vmlinuz 的和编译成 .ko 的都会出现 struct module
/sys/power 电源选项，可写控制命令让机器关机、重启、休眠 电源管理
/sys/fs 各文件系统的可调参数（/sys/fs/cgroup 等） 较晚引入，未验证具体版本

/sys/module 的规则值得细写，因为行为不直观：

  • 编译为外部模块（.ko）的，加载后一定出现 /sys/module/<name>/，其下有属性文件和属性目录，表示版本号、加载状态、提供的驱动等。
  • 编译为内联的（=y），只有存在非 0 值的模块参数时才出现 /sys/module/<name>/。参数放在 /sys/module/<name>/parameters/ 下，例如 /sys/module/printk/parameters/time，可读写，控制内联 printk 打印时是否加时间前缀。
  • 内联模块的参数也能写在启动参数上，形态是 <module>.<param>=<value>，例如启动时加 printk.time=1，与向 /sys/module/printk/parameters/time 写 1 等价。
  • 没有非 0 参数的内联模块不会出现在 /sys/module。

/sys/module 这条规则背后的实现理由是：sysfs 目录由 kobject_add 创建，内联模块的 kobject 只有在需要暴露参数时才会被创建，不创建就没有目录。这也侧面印证了「sysfs 目录 = kobject」这条主线。

三层映射一句话记：kobject → 目录，attribute → 文件，对象关系 → 符号链接。

十九、/sys/devices 与 /sys/class 的区别 #

这两个目录最常被混用，但它们回答的是两个不同问题。

维度 /sys/devices /sys/class
组织的维度 物理拓扑：设备挂在哪条总线、父设备是谁 功能分类：这个设备干什么用
是否唯一 每个设备只出现一次 同一设备可以出现在多个 class 下（多功能设备）
目录类型 实体目录 实体目录 + 大量符号链接
稳定性 路径随硬件拓扑变化 路径稳定，适合用户态长期依赖
典型路径 /sys/devices/pci0000:00/0000:00:1d.0/usb1/1-1 /sys/class/net/eth0、/sys/class/input/input3

判断一个设备的位置，用 /sys/devices。写用户态程序找设备，用 /sys/class。

设备出现在 /sys/class/<name>/ 下的机制：class 本身就是个 kset，device_add 时若设备设置了 dev->class，会在该 class 目录下建一个指向设备在 /sys/devices 下位置的符号链接。所以 /sys/class/net/eth0 是个链接，readlink -f 之后指向 /sys/devices/...。

举个抓取件里的原话场景：USB 接口的鼠标和 PS/2 接口的鼠标，都出现在 /sys/class/input/ 下，因为它们功能同类，尽管总线完全不同。这正是 class 存在的意义。

/sys/bus 与 /sys/devices 的关系也是链接关系，但方向不同：/sys/bus/<bus>/devices/<dev> 是指向 /sys/devices/... 的链接，由总线层在设备注册时创建。

三种目录类型的判别方法，一条命令就能分开：

bash
  # /sys 下哪些是链接，哪些是实体目录
ls -l /sys/class/net/eth0        # l 开头 = 链接
ls -ld /sys/devices/pci0000:00   # d 开头 = 实体目录

# 顺着链接找到物理位置
readlink -f /sys/class/net/eth0

二十、/sys/bus 与 /sys/drivers #

/sys/bus 是早期内核（2.6.x）的总线入口，每个总线一个目录。在 3.x 之前，/sys/bus/<bus>/ 下内容是「本总线上的一切」。3.x 之后总线属性逐步拆到 /sys/devices 与 class 体系，/sys/bus 演变成了一个「索引+注册表」视图。

/sys/bus/<bus>/ 的典型内容：

子项 类型 内容
devices/ 目录 本总线上所有设备的符号链接，指向 /sys/devices/...
drivers/ 目录 本总线上所有已注册驱动的目录
drivers_probe 文件 写设备名，让总线为指定设备重新 probe
drivers_autoprobe 文件 读写开关，控制新设备是否自动 probe
uevent 文件 可写，手工触发总线 uevent
属性文件 文件 总线自身属性，由 bus_type 的 attribute group 提供

/sys/bus/<bus>/drivers/<drv>/ 的内容：

子项 内容
bind 写设备名，把该设备绑到这个驱动
unbind 写设备名，解绑
uevent 手工触发
属性文件 驱动自身属性，以及驱动暴露的模块参数（module/parameters/）

bind/unbind 是实战里最有用的两个文件。驱动 probe 出问题时，你可以手工 unbind 再 bind，看完整的内核日志，不必重载模块。

bash
# 解绑再绑定，观察 probe 日志
echo 0000:00:1f.2 | sudo tee /sys/bus/pci/drivers/ahci/unbind
echo 0000:00:1f.2 | sudo tee /sys/bus/pci/drivers/ahci/bind

# 看某总线上所有设备的链接
ls -l /sys/bus/pci/devices/ | head -5

/sys/bus/<bus>/drivers 与 /sys/class 的差别在于对象类型：drivers 下是 struct device_driver 的 kobject，class 下是设备。驱动对象的 sysfs 位置由 bus 决定（挂在总线的 drivers kset 下），设备的 sysfs 位置由拓扑决定。这条规则的代码依据在《device、driver、bus、class：四个注册表》，本篇只管它们最终都落成 kobject 目录这一层。

二十一、sysfs 的读写与内核代码的对应关系 #

把前面几章串起来，从用户在 shell 里 cat 一个文件，到驱动的 show 被调用，完整链路是：

text
cat /sys/class/foo/bar
  -> VFS: 路径解析，open
  -> sysfs_lookup 建 dentry / inode（首次访问）
  -> inode->i_fop->open = sysfs_open_file
       -> 从 dentry->d_fsdata 取 sysfs_dirent
       -> 父节点拿 kobject
       -> kobj->ktype->sysfs_ops 存进 sysfs_buffer
       -> file->private_data = sysfs_buffer
  -> read -> sysfs_read_file
       -> fill_read_buffer
            -> ops->show(kobj, attr, page)
                 -> 模块的 xxx_attr_show
                      -> container_of 转出 xxx_attribute
                      -> container_of 转出宿主结构体
                      -> 模块自己的 show，往 page 里写
       -> copy_to_user
  -> release -> sysfs_release

对应关系整理成一张表，反向查也有用：

用户动作 VFS 入口 sysfs 处理 最终落到
cat /sys/x/y sysfs_read_file fill_read_buffer → ops->show 宿主的 show 回调
echo v > /sys/x/y sysfs_write_file fill_write_buffer → ops->store 宿主的 store 回调
ls /sys/x sysfs_readdir 遍历 sysfs_dirent 子节点 无宿主参与
ls -l /sys/x/y sysfs_getattr 取 s_mode/s_iattr 无宿主参与
readlink 链接节点直接解析 sysfs_dirent 类型为 symlink 无宿主参与
cat /sys/x/uevent sysfs_read_file 由设备模型层的 show 返回 dev_uevent()

ls 不触发宿主代码，这一点经常被误解。列目录只是走 sysfs_dirent 树；只有读写属性文件才会进驱动。

内存占用也是这条链的结果：sysfs 不为文件内容预分配内存。不对文件操作时，内容不存在。只有用户读写时，才申请一页（PAGE_SIZE）内存存放本次内容。这就是为什么 show 的返回值不能超过一页，也是为什么两次读之间内容可以完全不同。

写方向的拷贝方向相反：先 copy_from_user 到内核页，再交给 store。这一层拷贝是必须的，保护内核空间不被用户态直接改写。

调试 sysfs 属性的几个固定动作：

bash
  # 1. 确认属性文件的来源
ls -l /sys/class/net/eth0/mtu

  # 2. 读
cat /sys/class/net/eth0/mtu

  # 3. 写并检查返回值
echo 1400 | sudo tee /sys/class/net/eth0/mtu
  # tee 会把内核返回的 errno 打出来，比重定向更直观

  # 4. 找不到属性时，看它是不是在另一个层级
find /sys -name 'mtu' 2>/dev/null

tee 比 > 好的地方在于：写失败时 tee 会把 tee: /sys/...: Invalid argument 打出来，而 > 只有一句 Permission denied 或静默无事。

二十二、易错点速查 #

这一节是给返工时用的。每条都写清「错在哪 → 现象 → 怎么改」。

# 易错点 现象 正确做法
1 ktype->release 里 kfree 错了对象 嵌入式 kobject 场景下 kfree(kobj) 释放的只是宿主结构体开头几个字节，后续访问即崩 用 container_of(kobj, struct xxx, kobj) 反推宿主，kfree 宿主
2 完全没写 release 计数归零时 kobject_cleanup 打印警告，对象永远不释放 每个 ktype 必须有 release
3 release 里再次 kobject_put 或访问 sysfs 递归进 cleanup，或访问已释放内存 release 只做释放，不做别的
4 kobject_get/kobject_put 不配对 泄漏（对象永不释放，sysfs 目录残留）或提前释放（use-after-free） 同一函数内配对；跨函数要写明所有权
5 kobject_put 之后继续用 kobj 计数归零时对象已释放，读的是野指针 put 之前先决定还要不要用；要就 get
6 kobject 静态定义或放栈上 内核直接报错或后续 crash kobject 必须动态分配（跟随宿主 kmalloc，或 kobject_create）
7 重复调 kobject_init 打印错误和堆栈但不中止，引用计数被重置，之后提前释放 保证 init 只调一次；用 state_initialized 自查
8 忘了检查 kobject_add 返回值 __must_check 会有编译警告，运行期目录没建上，后续 sysfs_create_file 全返回 -ENOENT 检查返回值，失败就回滚已做的初始化
9 直接改 kobj->name sysfs 目录名和 name 不一致，用户态路径全错 用 kobject_rename，它处理 sysfs 迁移；是否补发 KOBJ_MOVE 要自己确认
10 name 里带 / sysfs 目录层级错乱或创建失败 做输入校验，路径分隔符换掉
11 ktype 没设或 ktype->sysfs_ops 没设 open 时 WARN，返回 -ENODEV，属性文件全都打不开 ktype 必填，带 attribute 就必填 sysfs_ops
12 先 sysfs_create_file 后 kobject_add sysfs_create_file 返回 -ENOENT（父目录还不存在） 顺序固定：kobject_add → sysfs_create_file
13 手工建的属性文件忘了 sysfs_remove_file 对象退场后属性文件仍指向已释放模块内存，读它即 crash default_attrs 走自动，手工创建的必须在卸离路径上删
14 sysfs_remove_file 后立刻 kobject_put 仍有打开的 fd 时会访问到已释放内存 先 kobject_del 再 put，让 sysfs 确认无活跃访问
15 show 返回超过 PAGE_SIZE 的字节数 触发 WARN，用户态读到截断内容 用 scnprintf 而不是 sprintf，控制在一页内
16 show/store 返回值写成 0 或 -1 用户态读到空内容，或写操作永远报错 show 返回写入字节数，store 返回 count；错误返回负 errno
17 store 里直接信 buf 是 \0 结尾 sysfs 的 store 不保证 buf 有终止符（部分属性类型例外） 用 count 做边界，必要时自己补 \0
18 kobject 不属于任何 kset 就发 uevent kobject_uevent_env 直接报错返回，用户态收不到任何事件 先 join 一个 kset，或让 parent 属于 kset
19 kset 的 uevent_ops->name 返回 NULL 该 kset 下所有对象的事件都不上报，且无报错 确保 name 回调在所有分支返回非 NULL 字符串
20 用 uevent_suppress 静音后忘了清 该对象此后所有事件都不上报 只在明确的时间窗口内用它，窗口结束清零
21 环境变量塞太多 add_uevent_var 失败（上限 32 个 / 2048 字节），事件缺字段 精简变量，通用项交给 kset 的 uevent 回调统一加
22 在 release 之后才想起要发 REMOVE state_add_uevent_sent 已错过清理窗口 kobject_cleanup 会自动补发，前提是别提前手工把状态位搞乱
23 以为删父 kobject 会连带删子对象 子对象的 sysfs 目录残留 父的 del 不递归，子对象要自己逐个处理
24 以为 ls 一个 sysfs 目录会跑驱动代码 列目录看不到属性值，察觉不到问题 ls 只走 sysfs_dirent 树，只有读写文件才进 show/store
25 在 /sys/class 下找设备的物理路径 拿到的是符号链接，没有父设备信息 用 readlink -f 转到 /sys/devices 下再看
26 把 /sys/bus/<bus>/devices 当实体目录 只看到链接，误以为设备找不到 那是符号链接集合，真实目录在 /sys/devices
27 遍历 kset->list 不拿锁 并发增删时链表遍历崩 拿 list_lock，或用 kset_find_obj 这类封装
28 假定 /sys/module 里一定能找到内联模块 ls /sys/module/<builtin> 报不存在 内联模块只有带 kobject（有参数要暴露）时才有目录
29 用 struct attribute 当唯一的属性定义就完事 没有 show/store，文件读出来是空的或直接失败 用 kobj_attribute/device_attribute 等派生类型，attribute 必须是第一个成员
30 手写 (struct device_attribute *)attr 强转 属性作为更复杂结构体成员时偏移算错 用 container_of 宏，别手算

几条补充的定性判断：

  • kobject 的生命周期问题，和引用计数的语义问题永远纠缠在一起。查这类 bug 的入口是 release：在 release 里打一行 pr_debug 带 kobject_name，看它是在什么时候被调的，和预期差多远。
  • sysfs 目录残留（/sys 下有目录但设备已不存在）几乎总是「漏了 kobject_del」或「漏了 put」。前者查注册/注销路径是否成对，后者查是否某处多了一次 get。
  • 事件收不到，三件事按序查：设了 uevent_suppress 吗？所属 kset 的 name 回调返回的是非 NULL 吗？filter 放行了吗？这三处全是静默失败，不会有日志。
  • PAGE_SIZE 的限制比想象中更容易碰到。一个把缓冲区内容全量 dump 出来的 show，在有几十条记录的设备上就会超。
