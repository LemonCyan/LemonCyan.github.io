一、四个注册表：Bus / Device / Driver / Class #

内核里注册设备的代码成千上万，但真正被「登记」的地方只有四类表。你写驱动时干的所有事，最后都落在这四张表上。

注册表 结构体 表里的一条是什么 注册入口 sysfs 根
总线类型 struct bus_type USB、PCI、I2C、platform 这类「通道类型」 bus_register() /sys/bus/<name>/
设备实例 struct device 一块具体的硬件，或一个虚拟设备 device_register() /sys/devices/...
驱动 struct device_driver 一段能驱动某类设备的代码 driver_register() /sys/bus/<bus>/drivers/<drv>/
功能类 struct class input、tty、block 这类「按功能归类」 __class_register() /sys/class/<name>/

三句话记住关系：

  • device 和 device_driver 都挂在同一个 bus_type 上，bus 是唯一有权判定「谁能配谁」的角色。
  • class 与 bus 正交：一个设备只能在一个 bus 上，但可以同时属于一个 class。class 只负责按功能给用户空间一个统一入口。
  • 四张表都靠内嵌的 kobject 出现在 sysfs 里，但表的语义各管各的。

把 bus/device/driver 画成三角形，是理解后面所有流程的地图：

text
                 struct bus_type
                （USB / PCI / I2C / platform）
                  /                \
        klist_devices          klist_drivers
                /                    \
      struct device  <---- 匹配 ---->  struct device_driver
      （具体硬件）      match/probe      （驱动代码）
             \                          /
              \____ class 正交挂在旁边 _/
                    （input / tty / block）

bus_match() 一次调用拿到两个参数：struct device *dev 和 struct device_driver *drv。这两个指针分别来自 bus 的两条链表，所以匹配一定是「一边已存在，另一边新来」。这条事实直接推出本章最容易被漏掉的一点：匹配是双向触发的，第八章讲透。

二、为什么需要「总线」这层抽象 #

在没有设备模型的年代，驱动自己去扫硬件、自己对寄存器地址、自己判断「这块板子上有没有我」。板子一换，驱动就废。内核要支持成千上万的硬件平台，这套写法会变成无组织的代码泥潭。

bus 这层抽象解决三件事：

  1. 解耦「有什么设备」和「拿什么代码驱动它」。设备信息（地址、中断、GPIO）由板级代码或设备树提供，驱动代码与板级无关。两边各自注册，由 bus 配对。
  2. 统一生命周期。设备什么时候可用、驱动什么时候加载、谁先谁后，交给 bus 的链表和回调管，不用各个子系统自己发明顺序。
  3. 统一用户空间视图。所有设备最终都出现在 /sys/devices 下的一棵树里，按 bus 和 class 各有索引目录。

内核对 bus 的规定很硬：系统中的每个设备都要连接在一个 bus 上。这个 bus 可以是真实总线（USB、PCI、I2C），也可以是内部总线、虚拟总线或 platform 总线。没有例外，只是有的 bus 是编出来的。

配合「名字」这条规则一起看：

  • 任何注册到内核的设备都必须有合法名称，可以初始化时给出，也可以由内核按「bus name + device ID」造出来（bus_type->dev_name 就是干这个的）。
  • 同名匹配的作用范围是同一个 bus 下的所有 device 和 device_driver。不同 bus 上同名的两个 device 互不干扰。
  • device_driver->bus 必须记录它所属的 bus。原因很实际：内核要保证 driver 运行前，它依赖的总线已经被正确初始化。

特殊 bus 有三种，都是编出来的：

bus 抽象对象 现状
system bus CPU、Timer 这类系统设备 旧版概念，新版内核认为它是坏点子，仅保留兼容
virtual bus 软件模拟的设备，如虚拟机网卡 较新的 bus，/sys/devices/virtual/*
platform bus 集成在 SoC 里的设备 最常见，无所谓初始化，probe/remove 可以留空

三、struct bus_type 的字段 #

定义在 include/linux/device.h（素材取自 3.10 前后，注释标 line 93）。

c
/* include/linux/device.h, line 93（3.x 形态） */
struct bus_type {
    const char *name;
    const char *dev_name;
    struct device       *dev_root;
    struct bus_attribute    *bus_attrs;
    struct device_attribute *dev_attrs;
    struct driver_attribute *drv_attrs;

    int (*match)(struct device *dev, struct device_driver *drv);
    int (*uevent)(struct device *dev, struct kobj_uevent_env *env);
    int (*probe)(struct device *dev);
    int (*remove)(struct device *dev);
    void (*shutdown)(struct device *dev);

    int (*suspend)(struct device *dev, pm_message_t state);
    int (*resume)(struct device *dev);

    const struct dev_pm_ops *pm;

    struct iommu_ops *iommu_ops;

    struct subsys_private *p;
    struct lock_class_key lock_key;
};

逐字段说：

  • name，bus 名称，在 sysfs 里就是目录名。platform bus 表现为 /sys/bus/platform。
  • dev_name，给懒得起名的设备用的名字前缀。USB 这类批量设备经常留空 init_name，核心逻辑就用「bus->dev_name + device ID」生成名称。
  • dev_root，注释说它是 bus 的默认父设备，但实际实现里只和一个叫 subsystem 的功能有关，别按注释想当然。
  • bus_attrs、dev_attrs、drv_attrs，三组默认属性，分别在 bus、device、driver 加入内核时自动建文件。这里是 3.x 写法，新内核改成 bus_groups、dev_groups、drv_groups 三个 const struct attribute_group **，旧的单指针并入了属性组模型（4.x 起，具体版本未验证）。
  • match，具体 bus 实现的核心回调。任何属于该 bus 的 device 或 device_driver 加入内核时，核心都会调它。配上了返回非零，bus 模块接着做后续处理。这是全文的主轴。
  • uevent，设备发生添加、移除或其它动作时调用，bus 驱动借此修改环境变量。
  • probe、remove，bus 级别的初始化与收尾。存在意义是顺序保证：driver 的 probe 之前要先跑 bus 的 probe，remove 反着来。platform bus 本身是虚拟的，直接留空。
  • shutdown、suspend、resume、pm，电源管理，原理与 probe/remove 类似，本文不展开。
  • iommu_ops，IOMMU 相关，本文不展开。
  • p，struct subsys_private 私有数据，下一节细看。
  • lock_key，lockdep 用的锁类键，防止同一把锁在不同 bus 上被误报。

p 指向的 struct subsys_private 才是真正装表的地方：

c
/* drivers/base/base.h, line 28（3.x 形态） */
struct subsys_private {
    struct kset subsys;
    struct kset *devices_kset;
    struct list_head interfaces;
    struct mutex mutex;

    struct kset *drivers_kset;
    struct klist klist_devices;
    struct klist klist_drivers;
    struct blocking_notifier_head bus_notifier;
    unsigned int drivers_autoprobe:1;
    struct bus_type *bus;

    struct kset glue_dirs;
    struct class *class;
};

名字起得烂，但看懂字段就清楚了：

  • subsys，代表本 bus 的 kset，落在 /sys/bus/spi。
  • devices_kset、drivers_kset，bus 下两个子 kset，即 /sys/bus/spi/devices 和 /sys/bus/spi/drivers。
  • interfaces 与 struct list_head，保存该 bus 下所有 interface（第四节末尾的 subsys_interface）。
  • klist_devices、klist_drivers，两条链表，装着本 bus 下全部 device 和 device_driver 的指针。匹配就是遍历它们。
  • drivers_autoprobe，控制本 bus 下设备/驱动注册时是否自动 probe，默认 1，开放到 sysfs 可改。
  • bus 和 class，回指上层的 bus 或 class。class 里挂着同一个结构，这就是为什么它命名成 subsys 而不是 bus_private：bus 和 class 都是「子系统」，形态都是 /sys/bus/* 或 /sys/class/* 下的一个子目录，像一个个独立小王国。
  • glue_dirs、bus_notifier，粘连目录和 notifier 通知链，本文不展开。

bus 模块干五件事：bus 的注册与注销；本 bus 下 device/driver 注册时的处理；注销时的处理；device_driver 的 probe 处理；管理 bus 下所有 device 和 device_driver。

四、bus_register 做了什么 #

原型在 include/linux/device.h 声明、drivers/base/bus.c 实现：

c
/* include/linux/device.h, line 118 */
extern int __must_check bus_register(struct bus_type *bus);

__must_check 不是装饰。注册失败必须处理，否则后面 bus->p 是空的，任何 bus_add_device 都会崩。执行逻辑按顺序：

  1. 为 bus->p（struct subsys_private）分配空间，回填 priv->bus 和 bus->p。
  2. 初始化 priv->subsys.kobj 的 name、kset、ktype。name 就是 bus 的 name（会变成 sysfs 目录名），kset 和 ktype 由 bus 模块提供，分别是 bus_kset 和 bus_ktype。
  3. 调 kset_register 把 priv->subsys 注册进内核，同时向 sysfs 添加目录，如 /sys/bus/spi。
  4. 调 bus_create_file 在 bus 目录下加一个 uevent 属性，如 /sys/bus/spi/uevent。
  5. 调 kset_create_and_add 分别添加 devices 和 drivers 两个 kset，同时体现在 sysfs。
  6. 初始化 priv 里的 mutex、klist_devices、klist_drivers。
  7. 调 add_probe_files，在 bus 下加 drivers_probe 和 drivers_autoprobe 两个属性。前者允许用户空间主动触发指定 bus 下某个 device_driver 的 probe，后者控制注册时是否自动 probe。
  8. 调 bus_add_attrs，添加 bus_attrs 定义的默认属性，落在 /sys/bus/<name>/ 下。

注册完，sysfs 长这样（以 spi 为例）：

text
/sys/bus/spi/
├── uevent                 # bus_create_file 建的
├── drivers_probe          # add_probe_files 建的
├── drivers_autoprobe      # add_probe_files 建的
├── devices/spi1.0 -> ../../../devices/.../spi1.0
└── drivers/spidev/{uevent, bind, unbind}

关于「子系统注册」的版本差异要标清楚。素材里 2.6.23 的内核，/sys/bus/、/sys/devices/、/sys/block、/sys/kernel/、/sys/slab/ 这些顶层目录都是走 subsystem_register，实现就是调一次 kset_register 建个 kset。3.10 前后改了两条路：

  • 方式一：各模块初始化函数里调 kset_create_and_add 建子系统。/sys/bus/ 由 buses_init()（drivers/base/bus.c）建；/sys/class、/sys/kernel、/sys/firmware 同理。subsystem_register 接口被去掉，为了兼容 /sys/devices/system 才在 bus.c 里留了个内部 subsys_register。
  • 方式二：在 bus 模块里用 subsys_register 封装出 subsys_system_register 和 subsys_virtual_register，分别注册 /sys/devices/system/* 和 /sys/devices/virtual/*。与方式一的区别是：不只建 sysfs 目录，还注册同名的 bus 和 device。

五、device 与 device_driver 的结构 #

struct device 是四个注册表里最大的一个。字段多不代表逻辑复杂，很多是 DMA、电源、NUMA 的挂载点。

c
/* include/linux/device.h, line 660（3.x 形态） */
struct device {
    struct device       *parent;

    struct device_private   *p;

    struct kobject kobj;
    const char *init_name; /* initial name of the device */
    const struct device_type *type;

    struct mutex        mutex; /* mutex to synchronize calls to its driver. */

    struct bus_type *bus; /* type of bus device is on */
    struct device_driver *driver; /* which driver has allocated this device */
    void *platform_data; /* Platform specific data, device core doesn't touch it */
    struct dev_pm_info  power;
    struct dev_pm_domain    *pm_domain;

#ifdef CONFIG_PINCTRL
    struct dev_pin_info *pins;
#endif

#ifdef CONFIG_NUMA
    int numa_node; /* NUMA node this device is close to */
#endif
    u64     *dma_mask; /* dma mask (if dma'able device) */
    u64     coherent_dma_mask;/* Like dma_mask, but for alloc_coherent mappings
                                 as not all hardware supports 64 bit addresses
                                 for consistent allocations such descriptors. */

    struct device_dma_parameters *dma_parms;
    struct list_head    dma_pools; /* dma pools (if dma'ble) */
    struct dma_coherent_mem *dma_mem; /* internal for coherent mem override */
#ifdef CONFIG_CMA
    struct cma *cma_area; /* contiguous memory area for dma allocations */
#endif
    /* arch specific additions */
    struct dev_archdata archdata;

    struct device_node  *of_node; /* associated device tree node */
    struct acpi_dev_node    acpi_node; /* associated ACPI device node */

    dev_t           devt; /* dev_t, creates the sysfs "dev" */
    u32         id; /* device instance */

    spinlock_t      devres_lock;
    struct list_head    devres_head;

    struct klist_node   knode_class;
    struct class *class;
    const struct attribute_group **groups; /* optional groups */

    void (*release)(struct device *dev);
    struct iommu_group  *iommu_group;
};

字段说明只保留设备模型相关的：

  • parent，父设备，一般是该设备从属的 bus 控制器或上游设备。/sys/devices 那棵树的层级就由它决定。
  • p，struct device_private 私有数据。子设备链表、挂到 bus/driver/parent 上的链表头都塞在这里，具体看源码。
  • kobj，对应的 struct kobject。设备在 sysfs 里的身份来自它。
  • init_name，设备名。名称的重要性前面说过：注册必须有合法名称，可初始化时给，也可由内核用「bus name + device ID」造。新版内核把 init_name 在 device_add 之后置空，名字改存 kobj.name，所以运行期读名字要用 dev_name()（4.x 起的行为，具体版本未验证）。
  • type，struct device_type，和 kobj_type 对 kobject 的关系一样。
  • mutex，保护对该设备及其驱动的调用，probe 期间也靠它串行化。
  • bus，设备属于哪个总线。
  • driver，已经绑定的驱动指针。匹配成功就是写这个字段，空着就表示没驱动。
  • platform_data，平台相关私有数据的暂存处，驱动模块自己往里塞、自己往外取，设备模型不管它含义。
  • devt，32 位 dev_t，由主设备号和次设备号组成。有设备号的设备靠它生成 /sys/dev/char/、/sys/dev/block/ 下的入口。
  • id，设备实例号。
  • class，属于哪个 class。
  • groups，默认属性集，注册时自动在 sysfs 建文件。
  • release，引用计数归零后的释放回调。这个字段必须有，device_release 会依次查 device、device_type、device 所属 class 是否有 release。
  • devres_lock/devres_head，devres 资源链表，见《platform 设备与 devres》。

struct device_driver 简单得多（早期内核叫 struct driver，改名版本未验证）：

c
/* include/linux/device.h, line 213（3.x 形态） */
struct device_driver {
    const char *name;
    struct bus_type     *bus;

    struct module       *owner;
    const char *mod_name; /* used for built-in modules */

    bool suppress_bind_attrs; /* disables bind/unbind via sysfs */

    const struct of_device_id   *of_match_table;
    const struct acpi_device_id *acpi_match_table;

    int (*probe) (struct device *dev);
    int (*remove) (struct device *dev);
    void (*shutdown) (struct device *dev);
    int (*suspend) (struct device *dev, pm_message_t state);
    int (*resume) (struct device *dev);
    const struct attribute_group **groups;

    const struct dev_pm_ops *pm;

    struct driver_private *p;
};
  • name，驱动名，与设备名匹配的关键依据。
  • bus，该驱动所驱动设备的总线。
  • owner、mod_name，模块相关。
  • suppress_bind_attrs，为真时不在 sysfs 里建 bind/unbind。默认会建，ls /sys/bus/platform/drivers/switch-gpio/ 能看到 bind uevent unbind。这两个属性是用户空间手动绑定/解绑设备的入口，逻辑在 bus.c 里。
  • of_match_table、acpi_match_table，设备树与 ACPI 的匹配表。名字匹配退居二线之后，这两张表才是主流。
  • probe、remove，驱动逻辑的开头与结尾。名字的由来很直白：检测到设备叫 probe，检测到设备被移除叫 remove，一开始就是为了热插拔起的名字。
  • suspend、resume、shutdown、pm，电源管理。
  • groups，驱动的默认属性，注册时由 drivers/base/driver.c 自动加到 sysfs。
  • p，struct driver_private，driver core 私有，其它模块不许碰。

两边字段的对照：

关注点 struct device struct device_driver
名字 init_name（运行期在 kobj.name） name
所属总线 bus bus
配对结果 driver（指向已绑定驱动） 无反向指针，靠 p->klist_devices 反查
匹配依据 of_node、id、type、class of_match_table、acpi_match_table、bus 提供的 id_table
生命周期入口 probe 由驱动的实现承担 probe、remove、shutdown、suspend、resume
默认属性 groups（const struct attribute_group **） groups（同上）
私有数据 platform_data（驱动自己管） p（core 私有，别人不能碰）
释放 release 必填 无
私有结构 struct device_private struct driver_private

六、设备注册：device_register 的完整链路 #

设备模型框架下开发驱动的步骤就两步：分配并填充 struct device 后注册；分配并填充 struct device_driver 后注册。两步做完，内核在合适时机调回调函数。之后驱动开发者眼里就不再有「设备模型」，只有自己的实现。

实际开发很少直接摸 struct device/struct device_driver，内核在上面又包了一层（soc device、platform device 等），接口更简单。但下面这条链路你必须知道，因为所有封装最后都汇到它。

device_register 的定义很短，展开的链路却很长：

c
/* drivers/base/core.c（3.x 形态） */
int device_register(struct device *dev)
{
    device_initialize(dev);
    return device_add(dev);
}

device_initialize 干的是「把这坨内存变成合法对象」：

c
/* drivers/base/core.c（3.x 形态，示意） */
void device_initialize(struct device *dev)
{
    dev->kobj.kset = devices_kset;          /* 所有 device 的 kset */
    kobject_init(&dev->kobj, &device_ktype);
    INIT_LIST_HEAD(&dev->dma_pools);
    mutex_init(&dev->mutex);
    lockdep_set_novalidate_class(&dev->mutex);
    spin_lock_init(&dev->devres_lock);
    INIT_LIST_HEAD(&dev->devres_head);
    device_pm_init(dev);
    set_dev_node(dev, -1);
}

device_add 是主链路：

text
device_add(dev)
├── dev->p = kzalloc(device_private)           # 私有数据：子设备链表、knode_*
├── dev_set_name(dev, "%s", dev->init_name)    # 没名字就报错，必须先有名字
├── device_private_init(dev)                   # 初始化 knode_class / knode_bus / knode_parent
├── dev->kobj.parent = parent 的 kobj          # /sys/devices 下的父子目录靠这个
├── kobject_add(&dev->kobj, ...)               # sysfs 里出现目录
├── device_create_file(dev, &dev_attr_uevent)  # 建 uevent 属性
├── device_add_class_symlinks(dev)             # 建 class 相关符号链接（见第十五章）
├── device_add_attrs(dev)                      # 建默认属性
├── bus_add_device(dev)                        # 挂到 bus 的 devices 链表 + 建链接
├── dpm_sysfs_add(dev)
├── device_pm_add(dev)                         # 电源管理
├── kobject_uevent(&dev->kobj, KOBJ_ADD)       # 广播 udev，用户空间看到新设备
└── bus_probe_device(dev)                      # ★ 触发匹配

倒数第二步和最后一步的顺序值得盯一眼：先广播 uevent，再 probe。用户空间先于驱动 probe 看到设备目录，所以脚本别指望 uevent 一到设备就能用。

bus_add_device 是 bus 模块负责的部分（drivers/base/base.h 声明、drivers/base/bus.c 实现）：

c
/* drivers/base/base.h, line 106 */
extern int bus_add_device(struct device *dev);

四步：调内部 device_add_attrs，把 bus->dev_attrs 的默认属性加到设备目录下（/sys/devices/xxx/xxx_device/）；sysfs_create_link 把设备的真实目录链接进 bus 的 devices 目录，得到 /sys/bus/spi/devices/spi1.0 -> ../../../devices/platform/s3c64xx-spi.1/spi_master/spi1/spi1.0；sysfs_create_link 在设备目录里建一个名为 subsystem 的链接指向 bus 目录，得到 /sys/devices/platform/alarm/subsystem -> ../../../bus/platform；把设备指针塞进 bus->priv->klist_devices。

最后一步是整个设备模型的关键动作之一：这条 klist 就是后面 driver_attach 遍历的对象。设备进了链表，新驱动注册时才能找到它。

dev_set_name 那里有个坑：3.x 里 init_name 一直可用，4.x 之后 device_add 结束时会把 init_name 置为 NULL，此后名字只能从 kobject 里取。你在驱动里缓存 dev->init_name 指针会在 4.x 上拿到 NULL（具体重构版本未验证）。

设备注册还有个变体 device_create，把分配、初始化、注册打包：

c
/* include/linux/device.h（3.x 形态，原型示意） */
struct device *device_create(struct class *class, struct device *parent,
                             dev_t devt, void *drvdata, const char *fmt, ...);

需要设备号、需要 drvdata 的设备（字符设备居多）用它最省事。device_create_vargs 是它的 va_list 版本。

七、驱动注册：driver_register 的完整链路 #

driver_register 同样是一行分两段：

c
/* drivers/base/driver.c（3.x 形态） */
int driver_register(struct device_driver *drv)
{
    int ret;

    ret = bus_add_driver(drv);      /* 挂进 bus，并触发匹配尝试 */
    if (ret)                        /* 失败直接返回 */
        return ret;
    ret = driver_add_groups(drv, drv->groups);   /* 默认属性组 */
    if (ret) {
        bus_remove_driver(drv);
        return ret;
    }
    kobject_uevent(&drv->p->kobj, KOBJ_ADD);     /* 广播，用户空间看到新驱动 */
    return ret;
}

顺序上有个硬结论：bus_add_driver 在广播 uevent 之前就跑完了，而 bus_add_driver 里会调 driver_attach。也就是说驱动注册那次 uevent 发出时，probe 已经结束。这与设备侧「先 uevent 再 probe」正好相反。

bus_add_driver（drivers/base/bus.c）的逻辑按顺序：为 drv->p（struct driver_private）分配空间，初始化 priv->klist_devices、priv->driver、priv->kobj.kset 并回填 device_driver->p；把驱动 kobject 的 kset 设成 bus->p->drivers_kset，所有驱动都落在这个 kset 下；以驱动 name 调 kobject_init_and_add，在 sysfs 建 /sys/bus/xxx/drivers/<drv>/；把驱动存进 klist_drivers，并根据 drivers_autoprobe 决定是否调 driver_attach；driver_create_file 建 uevent；driver_add_attrs 建 bus->drv_attrs 的默认属性；按 suppress_bind_attrs 决定是否建 bind 和 unbind。

第 4 条就是双向匹配里的「驱动侧触发」。

driver_register 有一个前置动作不太显眼，但真写过驱动都会碰到：模块里那段

c
/* 典型写法（platform 由 bus 自己提供 id_table 与 match） */
static struct platform_driver xxx_driver = {
    .probe  = xxx_probe,
    .remove = xxx_remove,
    .driver = {
        .name           = "xxx",
        .of_match_table = xxx_of_match,   /* compatible 表 */
    },
};

static int __init xxx_init(void)
{
    return platform_driver_register(&xxx_driver);
}

platform_driver_register 做的事是填好内嵌的 struct device_driver 的 bus 指针（指向 platform_bus_type），然后调 driver_register。bus 指针必须在 driver_register 之前设好，因为 bus_add_driver 第一件事就是解引用 drv->bus->p。自己手写裸 device_driver 忘了填 bus，会在 bus_add_driver 里直接崩。

driver_register 的返回值只反映「驱动对象是否注册成功」，不反映「有没有配到设备」：driver_attach 的返回值被丢弃，连 -EPROBE_DEFER 都传不出来。判断配没配到，看 sysfs 里那条符号链接，或者在自己 probe 里打日志。第十二章展开。

八、匹配的核心：bus_type->match #

匹配的全部逻辑可以压成一句话：遍历对方那条 klist，对每个候选调一次 bus->match(dev, drv)，返回非零就 bind。

所谓双向，是两个入口各走一遍：

text
方向 A：设备先到，驱动后到
  device_register → device_add → bus_probe_device(dev) → device_attach(dev)
      └─ bus_for_each_drv(bus, NULL, dev, __device_attach)
            └─ 对 bus->p->klist_drivers 里每个 drv：
                  bus_match(dev, drv)  → 命中则 really_probe(dev, drv)

方向 B：驱动先到，设备后到
  driver_register → bus_add_driver(drv) → driver_attach(drv)（受 drivers_autoprobe 控制）
      └─ bus_for_each_dev(bus, NULL, drv, __driver_attach)
            └─ 对 bus->p->klist_devices 里每个 dev：
                  bus_match(dev, drv)  → 命中则 really_probe(dev, drv)

两个方向最终汇到同一个 really_probe，但遍历的对象不同。写驱动最常见的错判就是「我的驱动 register 返回 0，怎么 probe 没跑」——因为设备还没注册，方向 A 没触发，方向 B 又在那时没找到对象。反过来，设备注册时驱动模块还没 insmod，那一次 device_attach 也没配到。两边必须都到齐。

bus_match 本身的实现很薄：它加锁、在驱动的设备链表和 bus 之间做一致性检查，然后转手调 bus->match。真正决定成败的是各 bus 自己的 match 实现。以素材里 platform bus 的形态为例：

c
/* drivers/base/platform.c（3.x 形态，示意） */
static int platform_match(struct device *dev, struct device_driver *drv)
{
    struct platform_device *pdev = to_platform_device(dev);
    struct platform_driver *pdrv = to_platform_driver(drv);

    /* 设备树 / ACPI 优先 */
    if (of_driver_match_device(dev, drv))
        return 1;
    if (acpi_driver_match_device(dev, drv))
        return 1;

    /* 然后是已经转换过的 id_table */
    if (pdrv->id_table)
        return platform_match_id(pdrv->id_table, pdev) != NULL;

    /* 兜底：名字 */
    return (strcmp(pdev->name, drv->name) == 0);
}

注意最后一行是 strcmp 全等，不是前缀，不是模糊。"xxx" 和 "xxx.0" 配不上，但 platform device 的 name 字段（pdev->name）保留的是原始名，所以比较用的是它而不是 sysfs 目录名。

match 的返回值语义很简单：0 不匹配，继续遍历下一个候选；非零匹配，进入 really_probe。-EPROBE_DEFER 不要塞进 match 的返回值，它按 != 0 会被判成匹配，与你的本意相反。这个错误码是驱动从自己的 probe 里返回的，别把两件事混起来。

两边的匹配依据对照：

bus 主依据 兜底 备注
platform of_match_table（compatible） id_table、再 name 全等 SoC 内设，见《设备树》
PCI 厂商/设备 ID 表 无 struct pci_device_id
USB id_table（VID/PID/class） 无 热插拔主力
I2C of_match_table / i2c_device_id name 见《GPIO/pinctrl 与 I2C》
SPI of_match_table / spi_device_id name 同 I2C
自定义 bus 自己写 自己写 必须实现 match，不能为空

九、匹配中的 id_table：以 platform 为例 #

bus 的 match 里，id_table 是介于「名字匹配」和「设备树匹配」之间的那一档。它比名字灵活，又不需要设备树。

platform 的具体实现在 drivers/base/platform.c：

c
/* include/linux/platform_device.h（3.x 形态） */
struct platform_device_id {
    char name[PLATFORM_NAME_SIZE];
    kernel_ulong_t driver_data;
};

struct platform_device 里有一个 id_entry 字段，指向匹配上的那一条 platform_device_id。platform_match_id 遍历 id_table，strcmp(pdev->name, id->name) == 0 命中就把 pdev->id_entry = id 回填，然后返回该条。这个回填动作是关键。

driver_data 是 kernel_ulong_t，常见用法是存一个指向配置结构体的指针，或存一个枚举值。驱动在 probe 里这样取：

c
static int xxx_probe(struct platform_device *pdev)
{
    const struct platform_device_id *id = platform_get_device_id(pdev);
    if (id)
        variant = id->driver_data;      /* 板型差异靠这个分叉 */
    ...
}

同一份驱动代码服务多个板型，靠的就是这张表。名字匹配做不到这件事，因为名字只告诉你「配上了」，不告诉你「配上了哪一档」。

id_table 与 of_match_table 的优先级是明确的：设备树在前，id_table 在后。platform_match 里 of_driver_match_device 先跑，命中就直接返回 1，根本不看 id_table。后果是：设备树描述的设备，id_table 里写错了也不会报错，只是走 OF 分支。

id_table 的收尾必须用空项，因为 platform_match_id 靠 name[0] == '\0' 判断结束：

c
static const struct platform_device_id xxx_id_table[] = {
    { "xxx-v1", (kernel_ulong_t)&variant_v1 },
    { "xxx-v2", (kernel_ulong_t)&variant_v2 },
    { }     /* 必须以全零项结尾 */
};

漏了结尾项，platform_match_id 会走出数组，读到的内容碰巧和 pdev->name 相等就误匹配，或者读越界。这个错误不崩、只在个别板子上「随机偶发」，查起来很费时间。

十、probe 的调用时机与上下文 #

「probe」指：内核发现存在匹配的 device 与 device_driver，就执行 driver->probe。这个回调是所有驱动的入口，在里面做硬件初始化、注册字符设备、注册 ops。remove 是它的反操作，发生在 device 或 driver 任一方从内核注销时。

probe 的触发时机一共五种，分自动与手动：

触发方式 入口 说明
设备注册时自动 device_register、device_add、device_create_vargs、device_create 方向 A
驱动注册时自动 driver_register 方向 B
手动找 driver device_attach(dev) 遍历同 bus 的驱动
手动找 device driver_attach(drv) 遍历同 bus 的设备
自行绑定 device_bind_driver(dev) 直接把 dev->driver 设好，不查 bus

最后一种很特殊：它跳过 match，直接把驱动绑上去。device_bind_driver 只做绑定和 probe，不做任何匹配判定。自己写虚拟总线或做兼容适配时才会用，普通驱动别用。

为什么 probe 是 bus 模块实现的？因为 device 和 device_driver 都挂 bus 上，只有 bus 知道该给谁配谁。这个解释在素材里就一句话，但它决定了代码归属：really_probe、driver_probe_device、device_attach、driver_attach 全在 drivers/base/dd.c（dd = driver/driver binding & device driver），不在 core.c 也不在 bus.c。

drivers_autoprobe 是唯一的全局开关。每个 bus 一个，默认 1，开放到 /sys/bus/<bus>/drivers_autoprobe。置 0 之后新注册的设备和驱动都不会自动 probe，得手动触发：

text
echo 0 > /sys/bus/platform/drivers_autoprobe
echo xxx_device > /sys/bus/platform/drivers_probe      # 手动触发某设备的匹配

drivers_probe 的属性实现是 drivers_probe_store，按设备名找设备再调 device_attach。名字里带 drivers_ 但干的是「给设备找驱动」，容易误导。

probe 的执行上下文有三条：

  • 进程上下文，不是中断。上下文来自内核线程（kworker）时，是 uevent 和延时工作触发的注册路径。
  • dev->mutex 被持有，所以 probe 内部不能再对同一个 dev 调需要这把锁的接口。
  • 「probe 里不能睡眠」是误解。可以 msleep、可以 request_irq、可以 regulator_get。真正的限制是不能长时间阻塞，因为 probe 期间这把锁持有，同一设备的并发访问会被挡住。

从 bus_probe_device 进来的路径，probe 在 device_add 的尾部同步执行，也就是在调用 device_register 的那个进程上下文里。

十一、匹配成功的完整时序 #

really_probe 是最终的绑定动作。素材给的是 3.x 形态：

text
really_probe(dev, drv)
├── dev->driver = drv                       # 先把指针挂上
├── driver_sysfs_add(dev)                   # 建 dev/driver 双向符号链接
├── bus->probe(dev)（非空时）                # 总线级初始化，失败回滚
├── drv->probe(dev)                         # ★ 真正的驱动入口
├── 成功：dev->driver 保持不变，返回 0
└── 失败：devres_release_all / drv->remove / pm 清理 → dev->driver = NULL

几处版本差异必须逐处标：

  • driver_sysfs_add 的位置在 4.x 被重构过。3.x 里它紧跟在 dev->driver = drv 之后、bus->probe 之前；4.x 之后挪到了 call_driver_probe 之后（4.21 附近，版本未完全验证）。后果是 sysfs 里 driver 符号链接出现的时机变了。
  • really_probe 的签名保留 (dev, drv)，但 4.x 末/5.x 起内部多了 dev->links 的遍历（device_links 见第十二章）。
  • devres_release_all 的失败清理在 3.x 里只做 dev->driver = NULL；drv->remove 的调用条件在 4.x 后变过。写驱动时按「失败清理会发生」来假设，别依赖具体调了几次。

driver_sysfs_add 建的两条链接长这样：/sys/bus/platform/drivers/xxx/a010000.serial -> ../../../../devices/platform/a010000.serial，反过来设备目录下有 /sys/devices/platform/a010000.serial/driver -> ../../../bus/platform/drivers/xxx。两条链接互为证据。判断一个设备是否绑上驱动，看设备目录下有没有 driver 链接就够了。

完整时序串起来（假设驱动模块先 insmod、设备后注册）：

text
[1] insmod xxx.ko
      module_init → platform_driver_register(&xxx_driver)
        → 填 drv->driver.bus = &platform_bus_type
        → driver_register → bus_add_driver
            → 分配 driver_private，kset = platform_bus->p->drivers_kset
            → kobject_init_and_add → /sys/bus/platform/drivers/xxx/
            → 塞进 klist_drivers
            → drivers_autoprobe ? driver_attach() : 跳过
                → bus_for_each_dev 遍历 klist_devices（此时为空）→ 无匹配
        → driver_add_groups → kobject_uevent(KOBJ_ADD)   # 用户空间看到新驱动

[2] 设备出现（.dts 展开 / 枚举 / 板级代码）
      platform_device_register → device_add
        → kobject_add → /sys/devices/platform/a010000.serial/
        → bus_add_device → 塞进 klist_devices，建 devices/ 和 subsystem 链接
        → kobject_uevent(KOBJ_ADD)                       # 先广播
        → bus_probe_device → device_attach
            → bus_for_each_drv 遍历 klist_drivers
                → bus_match → platform_match → of_driver_match_device 命中
                    → really_probe
                        → dev->driver = drv → driver_sysfs_add（两条链接出现）
                        → bus->probe（platform bus 为空）
                        → drv->probe(dev)   # ★ xxx_probe：初始化硬件、request_irq、注册 cdev

换成设备先到（热插拔）时序完全对称，只是 device_attach 那一刻遍历到空链表，什么都没发生，等模块加载时由 driver_attach 补上。

十二、不匹配时会发生什么：deferred probe 初探 #

不匹配有四种情况，后果完全不同：

情况 现象 处理
对端根本不存在 无日志，dev->driver 为空 等对端注册，届时自动重试
名字/id 对不上 无日志 检查 name、id_table、compatible
匹配上了但 probe 返回 -ENODEV 之类的错误 打印一条 probe 失败日志，dev->driver 被清空 修驱动
匹配上了但依赖还没就绪，probe 返回 -EPROBE_DEFER 打印 probe deferral，设备进 deferred 链表 等依赖注册后重试

第四种是 deferred probe，Linux 3.4 前后引入（具体引入版本未验证，driver_deferred_probe_init 在 drivers/base/dd.c）。机制：really_probe 里检测到 drv->probe(dev) 返回 -EPROBE_DEFER，就把这次尝试挂到全局的 deferred_probe_pending_list 并返回。之后每次有设备成功 probe，driver_deferred_probe_trigger() 调度 deferred_probe_work，把 pending 列表里的设备全再试一遍。

text
probe 返回 -EPROBE_DEFER
  → 挂进 deferred_probe_pending_list
  → 有设备 probe 成功 → driver_deferred_probe_trigger()
      → 调度 deferred_probe_work → 对 pending 里每个 dev 重跑 device_attach

要点三个：重试次数无上限，deferred_probe_timeout 可配（debugfs 下）；超时后打一条 probe deferral 警告并把 pending/active 列表 dump 到 dmesg，这是排查「某设备一直没起来」的第一手材料。返回 -EPROBE_DEFER 是驱动自己的决定，不是 bus 的，典型场景是 regulator_get、clk_get、reset_control_get、gpiod_get 拿不到资源。3.x 之前没有这套机制，代码要么靠 initcall 顺序硬凑，要么在 probe 里返 -ENODEV 让设备彻底失败——读老代码看到「靠 link order 保证 probe 顺序」的注释，那就是 pre-deferred-probe 时代的遗留。

deferred probe 与 device_links 的关系：device_links（设备间显式依赖，consumer/supplier）是 5.x 才引入的（5.0 附近的 struct device_link，版本未验证）。3.x 没这个概念，deferred probe 只靠重试而不是依赖图。所以老内核上依赖环表现为无限重试加超时警告，新内核上 device_links 能把环检测出来。

driver_register 与 deferred 的关系说全：driver_attach 内部对每个设备的尝试是串行 driver_probe_device，返回值（包括 -EPROBE_DEFER）在 bus_for_each_dev 回调里被当作「继续下一个」，最终 driver_attach 返回 0。从 driver_register 的返回值永远看不出 defer 发生过。要判断，只能看 /sys/devices/.../driver 链接在不在，或者 dmesg 里的 probe deferral。

十三、驱动的注销与设备的移除 #

这两个动作是 register 的镜像，但顺序与对称性不同。

驱动的注销：

c
/* drivers/base/driver.c（3.x 形态，示意） */
void driver_unregister(struct device_driver *drv)
{
    if (!drv || !drv->p) {
        WARN(1, "Unexpected driver unregister!\n");
        return;
    }
    driver_remove_groups(drv, drv->groups);
    bus_remove_driver(drv);
}

bus_remove_driver 的步骤：从 bus 的 klist_drivers 里摘掉；遍历这个驱动已绑上的所有设备（driver_private->klist_devices），对每个调 device_release_driver(dev)，最终 drv->remove(dev) 并清 dev->driver；删除 sysfs 里的 driver 目录以及 bind/unbind/uevent；释放 driver_private。

顺序上有个细节：驱动注销时先解绑所有设备，再删自己的目录。所以 remove 回调执行时，sysfs 里驱动目录还在，设备目录里的 driver 链接也还在。在 remove 里靠这两条链接判断状态的代码是安全的。

设备的移除：

c
/* drivers/base/core.c（3.x 形态，示意） */
void device_del(struct device *dev)
{
    kobject_uevent(&dev->kobj, KOBJ_REMOVE);   /* 1. 先通知，后干活 */
    ...
    device_release_driver(dev);          /* 2. 解绑，内部调 drv->remove(dev) */
    bus_remove_device(dev);              /* 摘 bus 链表、删 devices 链接 */
    device_remove_class_symlinks(dev);   /* 删 class 链接 */
    device_remove_file(dev, &dev_attr_uevent);   /* 3. 撤 sysfs 属性与目录 */
    device_remove_attrs(dev);
    dpm_sysfs_remove(dev);
    device_pm_remove(dev);
    kobject_del(&dev->kobj);             /* /sys/devices 下目录消失 */
    ...
}

void device_unregister(struct device *dev)
{
    device_del(dev);
    put_device(dev);                     /* 引用计数减一，归零走 release */
}

顺序上和 device_add 相反，但有个不对称必须记住：device_del 先发 KOBJ_REMOVE 再解绑。用户空间收到「设备消失」通知时，drv->remove 还没跑。udev 规则里做卸载清理的脚本要预期这个窗口。

device_release_driver 内部对 dev->mutex 加锁，再调 drv->remove。所以 remove 回调的上下文与 probe 一致：进程上下文、持 dev->mutex。

注销路径最容易踩的两个坑：

  • 驱动的 remove 里访问已经在 probe 里 unregister 的东西。顺序错会 double free 或空指针。
  • 模块 exit 里直接 kfree 驱动结构体，而没先 driver_unregister。bus_remove_driver 会去读 driver_private，读到已释放内存。

十四、struct class 的字段与作用 #

前三个注册表都对应实实在在的东西，class 是虚拟的，纯粹为了抽象设备共性。

用班级打比方：一群知识需求相似的人聚在一起就是个班。班级有自己的名称（比如 295），但离开学生（device）就没有存在意义。班级存在的最大意义是课程——老师讲一遍，全班都听到。如果每个学生各自在家学，就要为每人请一个老师讲一遍相同内容。

设备模型里的 class 提供的就是这个：相似的 device（学生）需要向用户空间提供相似的接口（课程）。每个设备的驱动自己实现一遍，内核就有大量冗余代码。class 说，我来实现，你们会用就行。内核注释写得很清楚：A class is a higher-level view of a device that abstracts out low-level implementation details（include/linux/device.h，素材标 line 326）。

c
/* include/linux/device.h, line 332（3.x 形态） */
struct class {
    const char              *name;
    struct module           *owner;

    struct class_attribute          *class_attrs;
    struct device_attribute         *dev_attrs;
    struct bin_attribute            *dev_bin_attrs;
    struct kobject                  *dev_kobj;

    int (*dev_uevent)(struct device *dev, struct kobj_uevent_env *env);
    char *(*devnode)(struct device *dev, umode_t *mode);

    void (*class_release)(struct class *class);
    void (*dev_release)(struct device *dev);

    int (*suspend)(struct device *dev, pm_message_t state);
    int (*resume)(struct device *dev);

    const struct kobj_ns_type_operations *ns_type;
    const void *(*namespace)(struct device *dev);

    const struct dev_pm_ops *pm;

    struct subsys_private *p;
};

和 struct bus_type 几乎同构，逐字段：

  • name，class 名称，体现在 /sys/class/ 下。
  • class_attrs，class 的默认属性，class 注册时自动在 /sys/class/xxx_class/ 下建文件。
  • dev_attrs，该 class 下每个设备的属性，设备注册时自动在设备自己的 sysfs 目录下建文件。这是 class 最实用的一格：同一类设备共用的属性只写一份。
  • dev_bin_attrs，同上，二进制属性版本（固件、eeprom 这类）。
  • dev_kobj，该 class 下设备在 /sys/dev/ 下的目录。现在一般就 char 和 block 两个，为 NULL 时默认选 char（3.x 行为，见附录）。
  • dev_uevent，class 下设备发生变化时的回调。
  • devnode，devtmpfs 节点创建回调，决定 /dev 下节点的名字和权限。
  • class_release，释放 class 自身。
  • dev_release，释放 class 内设备。device_release 会依次检查 device、device_type、device 所属 class 是否提供 release，有就调。
  • suspend、resume、pm，电源管理。
  • ns_type、namespace，命名空间相关（网络设备分 netns 就靠这个）。
  • p，和 bus 里一模一样的 struct subsys_private。这就是前面说的：class 和 bus 都是子系统。

三个注册表的字段侧重点对比：

结构 表里有什么 靠什么进 sysfs 是否参与匹配
bus_type 设备链表 + 驱动链表 subsys_private->subsys kset 是，提供 match
class 设备链表（单向）+ interface 链表 subsys_private->subsys kset 否，不参与 bind
device_driver 自己绑过的设备链表 driver_private->kobj 是被匹配方

class 里没有驱动链表，所以 class 从来不决定「谁驱动谁」。这是 class 与 bus 最本质的区别，第十六章展开。

十五、class_register 与 class_interface #

class 的注册由 __class_register 实现（素材标 drivers/base/class.c，line 609）。逻辑与 bus 注册对齐：为 class->p（struct subsys_private）分配空间，初始化 cp->subsys.kobj.kset、cp->subsys.kobj.ktype；调 kset_register 注册该 class（一个 class 就是一个子系统，注册完 /sys/class/ 下出现对应目录）；调 add_class_attrs 把 class->class_attrs 指向的属性加进去，完成后 /sys/class/xxx_class/ 下能看到这些文件。

class_register 是包了一层锁的宏或内联：

c
/* include/linux/device.h（3.x 形态，示意） */
int __class_register(struct class *cls, struct lock_class_key *key);
#define class_register(cls)                         \
({                                                  \
    static struct lock_class_key __key;             \
    __class_register(cls, &__key);                  \
})

锁类键用宏传，是为了让每个调用点拿到独立的锁类，lockdep 才能区分不同 class 的锁。

struct class_interface 是 class 上的挂载点：

c
/* include/linux/device.h, line 434（3.x 形态） */
struct class_interface {
    struct list_head        node;
    struct class            *class;

    int (*add_dev)          (struct device *, struct class_interface *);
    void (*remove_dev)      (struct device *, struct class_interface *);
};

它允许 class 的使用方在「该 class 下有设备添加或移除」时收到通知。回调里做什么都行，例如改名、补节点，由具体实现决定。add_dev 返回 int、remove_dev 返回 void，两个签名不对称，写的时候别照抄错。

设备注册时与 class 相关的动作，全部在 device_add（drivers/base/core.c）里：调 device_add_class_symlinks 建符号链接（class 目录下指向设备的链接，设备目录下名为 subsystem 指向 class 的链接）；调 device_add_attrs 添加 class->dev_attrs 指定的属性；该 class 若有 add_dev 回调就调它。

第三条要盯一眼：class_interface 的回调在设备注册路径上同步调用，不在独立工作队列里。add_dev 里做耗时操作会拖慢 device_register。

class 注册的完整用法，写到驱动里就三段：

c
static struct class *xxx_class;

static int __init xxx_init(void)
{
    xxx_class = class_create(THIS_MODULE, "xxx");   /* 内部调 __class_register */
    if (IS_ERR(xxx_class))
        return PTR_ERR(xxx_class);
    return 0;
}

/* 创建设备时挂上 class */
dev = device_create(xxx_class, parent, MKDEV(major, minor), drvdata, "xxx%d", i);

static void __exit xxx_exit(void) { class_destroy(xxx_class); }   /* 按反序拆 */

class_create 是 __class_register 的包装，同时把 owner（模块引用）设好。少了 owner，设备还活着时 class 的代码段就有被卸载的风险。

class_interface 的真实用例在输入子系统：input class 注册时挂了一堆 interface，键盘、鼠标、触摸屏各有自己的 add_dev 逻辑，靠它把设备分派到不同的事件处理器。这也是为什么 class 能承载「功能」而不是「传输」。

十六、class 与 bus 的正交关系 #

「正交」不是修辞，是结构上的事实：

维度 bus_type class
表达什么 传输通道 功能类别
一个设备能属于几个 只有一个（dev->bus） 只有一个（dev->class），但同类设备可跨 bus
决定绑定吗 决定，match + probe 不决定，完全不参与
名字来源 USB、PCI、I2C、platform input、tty、block、net、rtc
sysfs 根 /sys/bus/<name>/ /sys/class/<name>/
设备下的链接名 subsystem → /sys/bus/<name> subsystem → /sys/class/<name>

两个维度各只有一个指针，但同一个设备在两个维度上各占一格。举实例：

text
一块接在 I2C 上的触摸屏
  bus   = i2c        （它是怎么连到 CPU 的）
  class = input      （它对外提供什么功能）

同一个 class = input 的目录下，能看到来自 platform/i2c、gpio-keys、virtual 三类来源的设备链接：

text
root@android:/ # ls /sys/class/input/ -l
event0  -> ../../devices/platform/i2c-gpio.17/i2c-17/17-0066/max77693-muic/input/input0/event0
event1  -> ../../devices/platform/gpio-keys.0/input/input1/event1
event2  -> ../../devices/platform/s3c2440-i2c.3/i2c-3/3-0048/input/input2/event2
event8  -> ../../devices/platform/soc-audio/sound/card0/input8/event8
event9  -> ../../devices/platform/i2c-gpio.8/i2c-8/8-0020/input/input9/event9
event10 -> ../../devices/virtual/input/input10/event10
mice    -> ../../devices/virtual/input/mice

从路径能读出物理拓扑：platform/i2c-gpio.17/i2c-17/17-0066/max77693-muic/input/input0/event0 表示「SoC 的 i2c-gpio 控制器 → i2c-17 总线 → 地址 0x66 的 max77693 设备 → 它的 muic 子功能 → input 层 → input0 → event0 节点」。这整条链是设备树里的父子关系，不是 class 关系。class 只提供一条快捷入口。

设备目录下的 subsystem 链接指向 class 时，说明这个设备挂的是 class：

text
/ # ls /sys/devices/platform/s3c2440-i2c.3/i2c-3/3-0048/input/input2/event2/ -l
-r--r--r-- root root  dev
lrwxrwxrwx root root  device -> ../../input2
drwxr-xr-x root root  power
lrwxrwxrwx root root  subsystem -> ../../../../../../../../class/input
-rw-r--r-- root root  uevent

对比纯 bus 场景（platform 设备），同一文件名指向完全不同：

text
/sys/devices/platform/alarm/subsystem -> ../../../bus/platform

subsystem 这个链接指向 bus 还是 class，取决于设备有没有挂 class：挂了就指 class，没挂就指 bus。查设备属于哪个 bus 时不要只 readlink subsystem，去看 /sys/bus/*/devices/ 下有没有它更可靠。

class 的功能说到底就三件：在 /sys/class/ 下建一个 class 目录；在该目录下为每个属于本 class 的设备建符号链接，可从这里直达设备全部属性；在设备自己的目录下建 subsystem 链接指回来。

就这些。input class 本身没做任何「实实在在的事」，只是索引。但这个索引在用户空间是决定性的：你不需要知道设备挂在哪条总线上，只要 ls /sys/class/input/；udev 规则也更愿意按 class 写，SUBSYSTEM=="input" 比 SUBSYSTEM=="i2c" 稳定得多。另一个用途更隐蔽：dev_attrs 让属性只写一份。input class 定义了 name、phys、uniq、prop、capabilities 之后，每个输入设备的 sysfs 目录里都有这些文件，各自的驱动不用重写。

十七、device / driver / bus / class 在 sysfs 里的位置 #

四个注册表在 sysfs 里的落点，一张表看完：

注册表 主目录 它的子目录/文件 被链接到哪里
bus_type /sys/bus/<bus>/ devices/、drivers/、uevent、drivers_probe、drivers_autoprobe —
device /sys/devices/<拓扑路径>/ uevent、subsystem、driver、power/、dev、属性文件 /sys/bus/<bus>/devices/、/sys/class/<class>/、/sys/dev/char|block/<maj:min>/
device_driver /sys/bus/<bus>/drivers/<drv>/ uevent、bind、unbind、属性文件 /sys/bus/<bus>/devices/<dev>/driver
class /sys/class/<class>/ 各设备链接、uevent、class_attrs 文件 设备的 subsystem 链接指向它

一个真实的完整树（以 serial 设备为例，路径按常见 ARM SoC 形态写，具体名字随平台变）：

text
/sys/bus/platform/
├── devices/a010000.serial -> ../../../devices/platform/a010000.serial
├── drivers/serial8250/
│   ├── uevent, bind, unbind
│   └── a010000.serial -> ../../../../devices/platform/a010000.serial
├── drivers_autoprobe
├── drivers_probe
└── uevent

/sys/devices/platform/a010000.serial/
├── driver -> ../../../bus/platform/drivers/serial8250
├── subsystem -> ../../../bus/platform
├── uevent
├── power/{control, runtime_status, ...}
└── tty/ttyS0 -> ../../../../class/tty/ttyS0

/sys/class/tty/ttyS0 -> ../../devices/platform/a010000.serial/tty/ttyS0
/sys/dev/char/4:64   -> ../../devices/platform/a010000.serial/tty/ttyS0

三条路径指向同一个设备目录。这不是冗余，是三个索引，服务三种查法：按总线找（ls /sys/bus/platform/devices/）、按功能找（ls /sys/class/tty/）、按设备号找（ls /sys/dev/char/）。4:64 就是 devt 字段，主 4 次 64。

三个容易搞混的地方：

  1. 真实目录只有一个。设备在 /sys/devices/... 下是实体目录，在 /sys/bus/*/devices/ 和 /sys/class/*/ 下都是符号链接。ls -l 一看就明白，ls -L 会掩盖这一点。
  2. /sys/bus/<bus>/drivers/<drv>/<dev> 和 /sys/bus/<bus>/devices/<dev> 是两条不同的链接，一条按驱动名索引，一条按设备名索引。前者的存在等于「这个驱动绑了这个设备」。
  3. bus 目录和 class 目录本身是 kset 建的实体目录，不是链接。/sys/bus/platform 是目录，/sys/class/tty 也是目录。

十八、设备的生命周期：get_device / put_device #

struct device 是引用计数的。计数藏在 kobj->kref 里，四个注册表里只有 device 需要关心它。

c
/* include/linux/device.h（3.x 形态） */
struct device *get_device(struct device *dev);
void put_device(struct device *dev);

规则三条：

  1. device_initialize 之后，引用计数是 1。
  2. device_register 只是把对象挂进 sysfs 和 bus，不增加你的引用。注册成功后，内核的链表、kobject、class 链接各自持有引用（它们通过 kobject_get 增加）。
  3. device_unregister 做 device_del + put_device，消费掉你那一份。之后 dev 指针就悬空，不要再用。

put_device 走到 0 时调 device_release，它按 dev->release → dev->type->release → dev->class->dev_release 的顺序找，三级都没有就打印 Device '...' does not have a release() function, it is broken and must be fixed 并 WARN。

这条链说明两件事：

  • struct device 的 release 字段必须由你自己提供，或者保证 device_type/class 提供了。用 kzalloc 分配 struct device 之后不填 release 就注册，卸载时必然 WARN 并泄漏。
  • 正确写法是让驱动分配一个包含 struct device 的结构体，release 里对该结构体 kfree：
c
struct xxx_dev {
    struct device dev;
    void __iomem *base;
    int irq;
};

static void xxx_dev_release(struct device *dev)
{
    kfree(container_of(dev, struct xxx_dev, dev));
}

struct xxx_dev *x = kzalloc(sizeof(*x), GFP_KERNEL);
x->dev.release = xxx_dev_release;
x->dev.parent  = &pdev->dev;
dev_set_name(&x->dev, "xxx%d", id);
device_register(&x->dev);        /* 内部含 device_initialize */

在 probe 里拿到 struct device *dev 之后要跨出一个作用域使用的，必须 get_device(dev)，用完 put_device(dev)。sysfs 属性回调、中断处理、工作队列回调都属于这类。

device_register 失败时，对象已经被 device_initialize 过，必须补一个 put_device，否则泄漏。这是 device_register 分支上最常漏的一句。device_create 失败时返回 ERR_PTR，内部已经处理过引用，不需要你再 put。

十九、热插拔与设备发现 #

设备从哪来？三条路，都最终汇到 device_register：

来源 机制 典型场景
静态描述 板级代码 platform_device_register，或设备树展开 SoC 内设、固定接线的外设
总线枚举 bus 自己的探测流程发现设备后注册 PCI 配置空间扫描、USB 枚举
运行时热插拔 用户空间写入触发的探测，或硬件中断 USB 插入、SD 卡插入、雷电

「设备发现」这部分每一层的实现都在各自的 bus 里，本文只讲它们和四个注册表的交界：

  • PCI：pci_scan_bus 走配置空间，每个 function 建一个 struct pci_dev（内嵌 struct device），最后 pci_bus_add_devices 逐个 device_register。bus 是 pci_bus_type，match 用 pci_device_id 表。
  • USB：usb_new_device 读设备描述符，usb_set_configuration 里为每个 interface 建 struct usb_interface，然后 device_add。bus 是 usb_bus_type，match 先比 id_table 的 VID/PID/class，再比 device class。
  • 平台设备：设备树在 of_platform_populate 时把每个 compatible 节点展开成 platform_device；老写法靠板级文件里一张表。细节见《设备树》。

热插拔的用户空间侧靠 uevent：

text
device_add → kobject_uevent(KOBJ_ADD)
  → kset 的 uevent_ops 组装环境变量：ACTION=add、DEVPATH=/devices/platform/...、
    SUBSYSTEM=platform、MODALIAS=platform:xxx
  → netlink 广播
      → udevd 按规则建 /dev 节点（devtmpfs 已建的话只调权限）
      → 按 MODALIAS 调 modprobe 加载驱动

MODALIAS 是自动加载的钩子。modprobe 读 /lib/modules/$(uname -r)/modules.alias，里面是 alias platform:xxx xxx_driver 这样的行，由 MODULE_DEVICE_TABLE(platform, xxx_id_table) 生成。所以驱动里漏了这个宏，热插拔时设备永远等不到驱动，只能手动 insmod，而且表面上看不出任何错误。

uevent 的回调链有三层，按顺序叠加：bus_type->uevent（bus 特有变量）→ device_type->uevent（类型特有）→ class->dev_uevent（功能特有）。三层都能往 env 里加键值，冲突时后者覆盖前者（具体顺序见 drivers/base/core.c 的 dev_uevent，此处未逐行验证）。

热插拔排查的四步：设备有没有被发现（dmesg 里有枚举日志吗）→ 注册成功了吗（/sys/devices/... 目录在吗）→ 配到驱动了吗（/sys/devices/.../driver 链接在吗）→ 用户空间收到通知了吗（udevadm monitor 里有没有 KOBJ_ADD）。第 3 步失败最常见，原因就三类：name/id_table 写错、MODULE_DEVICE_TABLE 漏了、驱动模块没装进 initramfs。

二十、易错点速查 #

按踩坑频率排，每条都对应前面某一章。

# 现象 原因 解法
1 driver_register 返回 0，但 probe 没跑 设备还没注册，方向 B 遍历到空链表 确保设备先或后都注册；查 /sys/devices/.../driver
2 设备注册了，driver 链接不存在 驱动在另一个 bus 上，或 name 不匹配 确认两边 bus 指针指向同一个 bus_type
3 bus_add_driver 里 oops 裸 device_driver 没填 bus 用 platform_driver_register 之类封装，或手填
4 卸载时 WARN does not have a release() struct device 没设 release，也没 device_type/class 提供 自己实现 release 并在里面 kfree 宿主结构
5 device_register 失败后内存泄漏 失败分支没 put_device 失败就 put_device，别直接 kfree
6 probe 里读 dev->init_name 是 NULL 4.x 起 device_add 结束时置空 用 dev_name(dev)
7 设备一直不 probe，dmesg 有 probe deferral 依赖的资源拿不到，probe 返回 -EPROBE_DEFER，重试超时 查依赖的 clock/regulator/gpio 驱动是否加载
8 热插拔后设备起来了但驱动不自动加载 漏 MODULE_DEVICE_TABLE 补宏并重新 depmod
9 同一驱动只驱动了第一个设备 以为 match 有排他性 match 不排他，一个驱动可绑多个设备；看是否在 probe 里设了全局标志
10 readlink subsystem 结果不是预期的 bus 设备挂了 class，subsystem 指向 class 要查 bus 就用 /sys/bus/*/devices/ 反查
11 id_table 漏结尾空项，个别板子误匹配 platform_match_id 靠 name[0]=='\0' 判结束 最后一项写 { }
12 class_interface->add_dev 里做耗时操作，开机变慢 回调在 device_add 同步路径上 把耗时活甩到工作队列
13 drivers_autoprobe 被设为 0，新设备不 probe 现场被人改过 cat /sys/bus/<bus>/drivers_autoprobe 确认
14 remove 里访问已释放的 drvdata device_del 先发 KOBJ_REMOVE 再解绑，用户空间与 remove 并发 清理逻辑按「随时被调」写；用 devm_* 管资源
15 自定义 bus 的 match 返回非零但 probe 不跑 bus->probe 存在且返回失败 虚拟 bus 就把 bus->probe/remove 留空

最后一条要展开一句：really_probe 里 bus->probe(dev) 是先于 drv->probe(dev) 的，bus 的 probe 失败会直接回滚，drv->probe 根本不会被调用。自定义虚拟总线时如果随手写了 bus->probe 又没写好返回值，会出现「匹配成功但驱动不执行」的怪现象。
