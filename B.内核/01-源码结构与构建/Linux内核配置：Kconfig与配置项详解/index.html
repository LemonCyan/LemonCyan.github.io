一、为什么从配置项读内核 #

刚接触内核时最常问的是「从哪儿入手」。能走的路不止一条，配置项是其中认知成本最低、覆盖面最广的一条。

1.1 四条入门路线的定位 #

路线 起点 先建立什么 代价
设备驱动入手 写一个 .ko 与硬件打交道的具体手感 长期停在驱动层，看不见调度、内存、VFS
源码目录入手 顶层二十来个子目录 代码在哪 只知道「在哪」，不知道「做什么」
启动流程入手 head.S / start_kernel 时序与初始化依赖 链条极长，前面一段看不懂就断线
配置项入手 make menuconfig 内核的功能清单与依赖关系 只看到「有什么」，看不到「怎么实现」

配置路线值得作为第一站，理由有两条：一是配置项多到让人一看 menuconfig 就发怵，而这种「多」恰恰把内核的功能边界画了出来；二是配置项的本质是功能开关，Kconfig 呈现的树状结构，从功能划分的角度看比源码目录还清晰。

源码目录回答「代码放在哪」，Kconfig 回答「这个功能叫什么、依赖谁、被谁依赖」。移植一块新板子时真正要动的往往只有几十个开关，其余上千项都是默认值——所以先认门，比先认路更划算。

1.2 Kconfig 树与源码目录的对照 #

功能域 源码目录 对应的 Kconfig 位置 差异说明
进程调度与抢占 kernel/sched/ kernel/Kconfig.preempt、init/Kconfig 菜单里没有单独的「调度」一级项，抢占模型藏在「Processor type and features」或「Kernel Features」
内存管理与分配器 mm/ mm/Kconfig、init/Kconfig 源码目录一目了然，配置项却分散在「General setup」与架构菜单里
块层与 IO 调度 block/ block/Kconfig、block/Kconfig.iosched 一致，菜单名就是「Enable the block layer」
文件系统 fs/ fs/Kconfig 一致
网络协议栈 net/ net/Kconfig 一致，且按协议族逐层展开
设备驱动 drivers/ drivers/Kconfig 菜单按总线再分一层，比 drivers/ 的目录更粗也更像分类树
安全 security/ security/Kconfig 一致
加密 crypto/ crypto/Kconfig 目录叫 crypto，菜单叫「Cryptographic API」
库函数 lib/ lib/Kconfig 一致
调试设施 lib/Kconfig.debug、kernel/trace/ lib/Kconfig.debug Kconfig 把 trace、kprobe、lockdep、fault-injection 全收在「Kernel hacking」一处，源码目录是散的
架构特有 arch/$ARCH/ arch/$ARCH/Kconfig 只有这一类「菜单跟着架构变」，其余各架构共用

一句话结论：除「架构特有功能」和「库/调试设施」这两类，其余配置域与源码目录基本一一对应，所以 Kconfig 树可以当作源码目录的功能化索引来读。

二、Kconfig 语言与入口 #

2.1 入口随架构而变 #

内核的配置项以架构为单位、用 Kconfig 语言组织。顶层 Kconfig 只有一行实质内容，把控制权交给 arch/$SRCARCH/Kconfig：

# 顶层 Kconfig（节选）
mainmenu "Linux/$ARCH $KERNELVERSION Kernel Configuration"

source "arch/$SRCARCH/Kconfig"

$SRCARCH 由构建系统按 ARCH 推导出来（arm64 对应 arm64，arm 对应 arm，x86_64 与 i386 都归到 x86）。所以「入口文件随架构而变」是字面意义上的：

架构 入口文件 说明
ARM64 arch/arm64/Kconfig 本篇素材的分析对象，一级菜单里多出「Platform selection」
ARM（32 位） arch/arm/Kconfig 菜单叫「System Type」，里面是各种 ARCH_xxx 板级开关
x86 arch/x86/Kconfig 32/64 位共用一份，靠 64BIT 开关切换
RISC-V arch/riscv/Kconfig 结构同 ARM64，无 ACPI 菜单

以 ARM64 为例，在源码根目录执行（交叉编译必须带 CROSS_COMPILE，否则会用宿主机的 gcc 试探编译器能力）：

bash
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- menuconfig

不带 _defconfig 直接进 menuconfig，看到的是内核内置的默认值（即 Kconfig 里所有 default 展开的结果），不是某块板子的配置。这是新手第一个坑：在空配置上改了一堆开关，最后发现根本没保存到正确的 defconfig。

2.2 六个关键写法 #

读 Kconfig 只需要认六种写法，其余都是它们的组合：

写法 作用 例子
menu "…" / endmenu 建一层菜单分组。它本身不产生配置项，只是把后面的 config 收进一个可折叠的目录里 menu "Boot options"
config SYMBOL 声明一个配置项。符号名就是宏去掉前缀后的部分：config CMDLINE_FORCE 对应 CONFIG_CMDLINE_FORCE config ARM64_ACPI_PARKING_PROTOCOL
depends on 前置依赖。不满足时该项在菜单里根本不出现；写多行是逻辑与 depends on ACPI
select 反向强选。本项被选中时，无视对方的 depends on 直接把目标项置 y select LIBFDT
choice / endchoice 单选组，组内 config 只能选一个，选中值写进组名对应的 CONFIG_… 抢占模型、IO 调度器、页大小
help / ---help--- 帮助正文，menuconfig 里按 ? 显示。缩进必须比 help 更深 见第五章的原文片段

六种之外还有四件「零件」，它们不构成结构，但决定一项的取值与显示：

零件 作用 例子
bool / tristate / string / int / hex 定类型。类型决定菜单里是 [ ] 还是 < > 还是输入框 bool "UEFI runtime support"
prompt 显式给提示语（多数情况下直接跟在类型后面当匿名 prompt 用） bool ＋ prompt "…"
default / def_bool 默认值。可以带条件：default y if ARM64 default y
range 数值范围，配合 int/hex range 0 7

select 与 depends on 的区别值得单独记一句：depends on 是「你有我才活」，select 是「我活你必须活」。前者写在自己身上，后者写在别人身上；前者不满足只是不显示，后者会把一个本来 n 的项硬拉成 y，被拉的项若自身还有依赖没满足，就会出现「配置了但编不过」的诡异状态。

2.3 类型决定菜单里的显示符号 #

类型 未选中 编进内核 编成模块 备注
bool [ ] [*] 不允许 只有 y/n
tristate < > <*> <M> 驱动类配置项几乎都是它
string ( ) 空的 括号内为字符串 — 如 CMDLINE
int / hex (0) 括号内为数值 — 括号里那个数是当前值，不是默认值
强制项 — -*- — 被 select 拉起来的项，用户改不动

识破 -*- 很重要：它意味着「这一项由别人替你选了」，想关掉它必须去关那个「别人」，直接在这里按 n 是无效的——菜单根本不让你动。

2.4 从 Kconfig 到 .config：三阶段 #

配置过程分三段，产物三个文件，各喂给不同的消费者：

text
arch/arm64/configs/defconfig ──make defconfig──▶ .config
                                                        │
arch/arm64/Kconfig（整棵依赖树）──make olddefconfig──▶ .config（补齐新符号）
                                                        │
                                          make syncconfig
                                              │         │
                                              ▼         ▼
                     include/config/auto.conf     include/generated/autoconf.h
                        （给 Makefile 读）            （给 C 源码读）
文件 生成者 内容形态 谁用它
.config make menuconfig / make xxx_defconfig CONFIG_X=y、CONFIG_Y=m、# CONFIG_Z is not set 人；下一次 make 的输入
include/config/auto.conf make syncconfig（旧内核叫 silentoldconfig） 同 .config 但只保留 =y / =m 的行 顶层 Makefile 与各 Kbuild，决定哪些目录、哪些 obj-$(CONFIG_X) 参与编译
include/generated/autoconf.h 同上 #define CONFIG_X 1 / #define CONFIG_Y_MODULE 1 C 预处理，源码里的 #ifdef CONFIG_X 靠它

三个细节值得记住：

  • .config 里的 # CONFIG_Z is not set 不是注释，它是「显式的 n」。删掉这一行等于「没表态」，make oldconfig 会重新按默认值问一遍。
  • 模块 =m 在 C 里变成 CONFIG_Y_MODULE，不是 CONFIG_Y。源码里写 #ifdef CONFIG_Y 判断的是「编进内核」，判断「是否参与编译」要用 #if IS_ENABLED(CONFIG_Y)。
  • 没有 prompt 的项不会出现在 .config 里，它只作为 select 的目标存在；被选中时在 auto.conf 里出现，在 menuconfig 里显示为 -*-。

2.5 常用 make 目标 #

目标 做什么 典型场景
make menuconfig 基于 .config 的图形界面（ncurses），改完写回 .config 日常裁配置
make xxx_defconfig 把 arch/$ARCH/configs/xxx_defconfig 展开成 .config 换板子第一步
make oldconfig 用旧 .config 为基础，对新增符号逐个提问 升级内核版本后
make olddefconfig 同上但不提问，新符号一律取默认值 脚本化、CI
make savedefconfig 反向把 .config 压成最小 defconfig（只留与默认值不同的项） 提交板级配置
make localmodconfig 按当前机器 lsmod 的结果裁掉用不到的模块 瘦身本机内核
make tinyconfig 从全 n 开始，得到一个最小的内核 学习依赖关系
make randconfig 随机配置 编译测试、找隐藏的编译错误

三、分析配置的三种手段 #

3.1 menuconfig 界面 #

最直接的手段，但有三个技巧大多数人不知道：

  • 按 / 打开搜索框，输入符号名或关键字，结果里会给出**「Depends on」与所在菜单路径**。这是排查「为什么我看不到某一项」的唯一正确姿势：看不到就是依赖没满足，搜索会直接告诉你差哪一项。
  • 按 ? 看当前项的帮助正文，里面通常包含作者写的「什么时候该选」。
  • 顶部一行 Arrow keys navigate the menu. <Enter> selects submenus ---> 里的 ---> 表示这是子菜单，不是开关。
bash
# 进界面，搜索某个符号
make ARCH=arm64 menuconfig
# 界面里按 / ，输入 CONFIG_ARM64_ACPI_PARKING_PROTOCOL

3.2 scripts/config：脚本里改配置 #

scripts/config 是内核自带的小工具，可以直接对 .config 做增删改，不必进界面。适合写进构建脚本或 CI：

bash
# 基本语法：--file 指定目标文件，缺省是 .config
./scripts/config --file .config --enable  CONFIG_DEBUG_INFO
./scripts/config --file .config --disable CONFIG_DEBUG_INFO
./scripts/config --file .config --module  CONFIG_EXT4_FS
./scripts/config --file .config --set-str CONFIG_CMDLINE "console=ttyAMA0,115200 root=/dev/mmcblk0p2"
./scripts/config --file .config --set-val CONFIG_NR_CPUS 8

# 查询当前状态：y / m / n / undef
./scripts/config --file .config --state CONFIG_DEBUG_INFO

# 改完必须重新展开依赖，否则 .config 与 Kconfig 不一致
make ARCH=arm64 olddefconfig

只改 .config 不跑 olddefconfig 是最常见的错误：scripts/config 只是改文本，它不知道 depends on；被关掉的项的子项仍然留在文件里，编译时就会出现「依赖不满足却编了」的怪现象。

3.3 grep：从源码侧反查 #

两种用法，分别回答两个不同的问题：

bash
# 问 1：某个 CONFIG_ 在内核里到底被谁用？
grep -rn "CONFIG_ARM64_ACPI_PARKING_PROTOCOL" --include=*.c --include=*.h .

# 问 2：某个功能对应哪个符号？先从 Kconfig 里找提示语
grep -rn "parking protocol" arch/arm64/Kconfig

# 问 3：当前 .config 里到底开了多少项、哪些是模块
grep -c "^CONFIG_" .config
grep "^CONFIG_.*=m" .config | head -20

# 问 4：两个配置的差异（升级内核前后最有用）
diff <(sort .config.old) <(sort .config)

另外，读 .config 时别忽略 # CONFIG_X is not set：grep CONFIG_X .config 能同时命中 y 和 n 两种状态，而 grep "^CONFIG_X=" 只会命中前者，容易误判成「没这个符号」。

3.4 三种手段怎么选 #

手段 回答什么问题 优点 局限
menuconfig 「这个功能在哪个菜单下」「为什么它不显示」 有依赖链与帮助文本，唯一能看清结构 交互式，不能脚本化；远程纯终端要 ncurses
scripts/config 「把这一项改成 y/m/n」 可脚本、可重复、可进 CI 不校验依赖，必须补 olddefconfig
grep 「这个符号被谁用」「两份配置差在哪」 零成本，能直接落到源码 不显示依赖关系

实际排查顺序一般是：grep 找到符号 → menuconfig 里按 / 看依赖 → scripts/config 改 → olddefconfig 校验。

  • 只有第 4、5、6 三项来自 arch/arm64/，其余全部是各子系统 source 进来的公共菜单。移植时真正要动的，绝大多数在这三项里。

五、ARM64 Boot options 详解 #

5.1 菜单全貌 #

ARM64 与启动相关的配置项很少，整个菜单只有五六个符号，位于 arch/arm64/Kconfig。原文片段（去掉了行号与制表符，其余原样）：

menu "Boot options"

config ARM64_ACPI_PARKING_PROTOCOL
    bool "Enable support for the ARM64 ACPI parking protocol"
    depends on ACPI
    help
      Enable support for the ARM64 ACPI parking protocol. If disabled
      the kernel will not allow booting through the ARM64 ACPI parking
      protocol even if the corresponding data is present in the ACPI
      MADT table.

config CMDLINE
    string "Default kernel command string"
    default ""
    help
      Provide a set of default command-line options at build time by
      entering them here. As a minimum, you should specify the the
      root device (e.g. root=/dev/nfs).

config CMDLINE_FORCE
    bool "Always use the default kernel command string"
    help
      Always use the default kernel command string, even if the boot
      loader passes other arguments to the kernel.
      This is useful if you cannot or don't want to change the
      command-line options your boot loader passes to the kernel.

config EFI_STUB
    bool

config EFI
    bool "UEFI runtime support"
    depends on OF && !CPU_BIG_ENDIAN
    select LIBFDT
    select UCS2_STRING
    select EFI_PARAMS_FROM_FDT
    select EFI_RUNTIME_WRAPPERS
    select EFI_STUB
    select EFI_ARMSTUB
    default y
    help
      This option provides support for runtime services provided
      by UEFI firmware (such as non-volatile variables, realtime
      clock, and platform reset). A UEFI stub is also provided to
      allow the kernel to be booted as an EFI application. This
      is only useful on systems that have UEFI firmware.

config DMI
    bool "Enable support for SMBIOS (DMI) tables"
    depends on EFI
    default y
    help
      This enables SMBIOS/DMI feature for systems.

      This option is only useful on systems that have UEFI firmware.
      However, even with this option, the resultant kernel should
      continue to boot on existing non-UEFI platforms.

endmenu

菜单里能动的其实只有四个开关，其余都是被 select 拉起来的配套项：

配置项 类型 用户可见 一句话
ARM64_ACPI_PARKING_PROTOCOL bool 是 允许用 ACPI parking protocol 唤醒从 CPU
CMDLINE string 是 编译期内置的命令行
CMDLINE_FORCE bool 是 忽略 bootloader 传参，只用内置命令行
EFI bool 是 UEFI 运行时服务 ＋ EFI stub
DMI bool 是 SMBIOS/DMI 表支持
EFI_STUB bool 否（无 prompt） 由 EFI select 拉起

5.2 ACPI parking protocol：从 CPU 怎么被叫醒 #

多核启动时，主 CPU（boot CPU）起来后要把其余 CPU 一个个唤醒。ARM64 有两条互斥的路径：

路径 依赖的固件表 唤醒方式
PSCI 设备树里的 psci 节点 通过 SMC/HVC 调用固件标准接口
Parking protocol ACPI MADT 表里的 GIC Structure / Multiprocessor Wakeup Structure 往约定的内存地址写一个「mailbox」值，从 CPU 轮询到后跳转

ARM64_ACPI_PARKING_PROTOCOL 打开的是第二条。它 depends on ACPI——没有 ACPI 就谈不上 MADT，所以纯设备树系统根本看不到这一项。

关掉它的后果写在 help 里：即使 ACPI MADT 表里有对应数据，内核也拒绝用这条路启动。所以判断标准很简单：

  • 服务器/虚拟化平台（QEMU 的 virt 机器、Xilinx/Ampere 等 ACPI 引导的板子）→ 保持默认 y；
  • 纯设备树引导的嵌入式板子 → 该项根本不会出现，无需关心。

5.3 CMDLINE 与 CMDLINE_FORCE：命令行的三个来源 #

内核能收到命令行的位置有三个，优先级从高到低：

来源 配置项/位置 何时生效
bootloader 传参 U-Boot bootargs、EFI 的 Boot#### 变量、设备树 /chosen/bootargs 默认，优先级最高
编译期内置 CONFIG_CMDLINE 只在 bootloader 没传（或传了空串）时用
强制内置 CONFIG_CMDLINE_FORCE=y 无视 bootloader，永远用 CONFIG_CMDLINE

还有一种介于两者之间的行为由 其他架构 提供（ARM64 没有 CMDLINE_EXTEND，ARM 32 位有）：把内置串追加到 bootloader 串后面。ARM64 上想追加只能改 bootloader 或设备树。

典型的两个用法：

text
# 用法 1：板子上电就要有串口输出，先内置一个最简命令行
CONFIG_CMDLINE="console=ttyAMA0,115200 earlycon=pl011,0x9000000"
CONFIG_CMDLINE_FORCE=n

# 用法 2：量产固件不希望被用户改 bootargs（例如固定 rootfs 分区）
CONFIG_CMDLINE="root=/dev/mmcblk1p2 rootwait rw"
CONFIG_CMDLINE_FORCE=y

CMDLINE_FORCE=y 是把双刃剑：调试期一旦打开，你会发现无论怎么改 bootargs 都没反应，很容易怀疑到设备树或 U-Boot 身上去。排障时先 cat /proc/cmdline，再 zcat /proc/config.gz | grep CMDLINE 核对。

5.4 EFI 家族：一个开关拉起五个 #

config EFI 的依赖是 OF && !CPU_BIG_ENDIAN：既要设备树（内核靠它拿到 UEFI 系统表），又不能是大端。选中后它 select 了五个配套项：

被选中的项 作用
LIBFDT 扁平设备树操作库，EFI 从 FDT 取参数时需要
UCS2_STRING UEFI 变量名是 UTF-16（UCS-2），需要转换函数
EFI_PARAMS_FROM_FDT 从设备树 /chosen 里取 EFI 相关参数
EFI_RUNTIME_WRAPPERS 对运行时服务调用的封装层
EFI_ARMSTUB ARM64 专用的 stub 入口代码
EFI_STUB 让内核镜像本身能被固件当成 EFI 应用直接执行（即 BOOTAA64.EFI）

DMI 又 depends on EFI、default y，所以开了 EFI 就顺手有了 /sys/class/dmi/id/ 下的整机信息（厂商、型号、BIOS 版本）。很多运维脚本靠这几个文件识别机型，嵌入式板子上通常是空的。

版本提醒：depends on OF && !CPU_BIG_ENDIAN 是 4.x 的写法。5.x 之后 EFI 的依赖放宽为不再强制 OF（因为出现了纯 ACPI 引导的 ARM64 服务器），本片段按原文的 4.6-rc5 保留。

Paravirtualized guest support 半虚拟化客户机支持 内核跑在虚拟机里时开（本例就是这种情形）

6.15 Library routines #

选项 说明 建议
Library routines（CRC、压缩算法、位操作等） 被其他子系统 select 的公共库 默认即可，不要手改；改动会引起大片连带依赖

七、两平台对照与最小裁剪 #

7.1 必须项对照 #

功能 ARM64 x86_64 说明
体系结构 ARM64 X86_64 由 defconfig 带出，不需要手动改
设备模型 OF（设备树） ACPI ＋ 可选 OF ARM64 靠设备树枚举，x86 靠 ACPI
中断控制器 ARM_GIC / ARM_GIC_V3 PCI_MSI ＋ IO-APIC 选错会导致系统起不来或中断收不到
定时器 ARM_ARCH_TIMER HPET_TIMER 都是「内核时钟源」的提供者
串口控制台 SERIAL_AMBA_PL011 等 SERIAL_8250 早期启动日志全靠它
块设备 MMC / SCSI / ATA ATA ＋ SCSI_DISK ARM64 板子多是 eMMC/SD
文件系统 EXT4_FS、TMPFS、PROC_FS、SYSFS 同左 缺一不可，尤其 DEVTMPFS

类别 ARM64 上通常可裁 x86 上通常可裁 裁掉的代价

7.3 嵌入式裁剪的落地顺序 #

顺序错了会陷入「关一项、编不过、再开回来」的循环。可靠的做法是从「能跑」往「变小」推：

步骤 动作 判据
1 用厂商 defconfig 起一个能启动的基线 串口有 Booting Linux 且能进 shell
2 打开 IKCONFIG_PROC，之后所有对比都有据可查 /proc/config.gz 存在
3 先删明显无关的硬件探针（别的 SoC、别的厂商控制器） 编得过、起得来
4 再删协议族与文件系统（IPv6、ATM、没用到的 FS） 业务功能自测通过
5 最后删调试设施，并保留 EARLY_PRINTK 与一个串口驱动 仍能出启动日志
6 每步 make savedefconfig，把差异压回 defconfig git diff 只看到实质变化
7 收尾量体积：size vmlinux、ls -l arch/arm64/boot/Image 与目标分区容量比对

不要在第 5 步之前删调试设施。裁到一半编不过时，串口日志是你唯一的线索；把它先关掉，等于在雾里改代码。

八、常见坑 #

8.1 启动参数与配置项的配合：pci=realloc=on #

pci=realloc=on 与 CONFIG_PCI_REALLOC_ENABLE_AUTO（菜单名 Enable PCI resource re-allocation detection）是一对：配置项决定内核有没有这套代码，参数决定运行时用不用。

配置项 启动参数 运行时行为
未编译进内核 任何取值 参数被忽略，内核根本不认
=n（默认） 未指定 不重分配；固件分好的 BAR 原样使用
=n pci=realloc=on 强制重分配，即使配置项没开
=y 未指定 检测到资源不足时自动重分配
=y pci=realloc=off 强制关闭，覆盖配置项

什么时候需要它：多块 PCIe 设备（尤其显卡＋多网卡）时，BIOS 分配的 BAR 窗口不够，出现 pci 0000:xx:yy.z: BAR 3: no space for ... 或设备直接没枚举出来。此时临时加 pci=realloc=on 验证——如果能解决，说明是固件分配问题，正确修法是升级固件或改 BIOS 设置，把参数写进 bootargs 只是权宜之计。

（原文标题里的「pci=realloc=on」其实是作者当时的排障线索，正文里对应的配置项叫 Enable PCI resource re-allocation detection，两者不是同一层的东西——这是本篇记的第二条勘误。）

8.2 CONFIG_MODVERSIONS 与模块兼容 #

insmod 失败报 Invalid module format、dmesg 里写着 version magic '…' should be '…'，是版本串不匹配；报 disagrees about version of symbol，是符号 CRC 不匹配。两件事的开关不同：

开关 影响 关掉/打开后的后果
CONFIG_MODVERSIONS 是否给导出符号记录 CRC，并在加载时校验 关掉后不校验 CRC，能加载「同版本但配置不同」编译出的模块，但结构体布局变了会静默崩溃
CONFIG_MODULE_FORCE_LOAD 允许 insmod -f 跳过版本检查 只跳过 vermagic，不跳过 CRC
vermagic（编译期自动生成） 内核版本＋SMP＋抢占模型＋模块卸载等标记拼成的串 不一致必然被拒，除非 -f

结论：模块必须与运行内核同源同配置编译。跨版本加载在二进制层面能硬改通过（改 .modinfo 里的 vermagic、改 __versions 段），但那属于逆向手段，不解决 ABI 变化。

8.3 CONFIG_IKCONFIG：把 .config 编进内核 #

配置项 作用 建议
CONFIG_IKCONFIG 把 .config 压缩后编进内核镜像 开
CONFIG_IKCONFIG_PROC 通过 /proc/config.gz 暴露 开，这是最常用的入口
依赖 CONFIG_PROC_FS ＋ 解压支持 没有 proc 就只能 scripts/extract-ikconfig vmlinux — 
bash
# 方法 1：运行中的系统
zcat /proc/config.gz | grep CONFIG_CMDLINE

# 方法 2：只有内核镜像（没开 IKCONFIG_PROC 也有效）
./scripts/extract-ikconfig arch/arm64/boot/Image | grep CONFIG_CMDLINE

它的价值在于事后可证：拿到别人编的内核或一台运行中的设备，能一次问清「你到底开了哪些项」，不必再猜。反之，如果当初没开，就只能靠 uname -r 和厂商给的 defconfig 反推，经常对不上。

现象 原因 处置

九、小结 #

  • 配置项是功能索引：Kconfig 树除「架构特有」与「库/调试」两类，其余与源码目录基本一一对应，先认门比先认路划算。
  • 入口随架构变：顶层 Kconfig 只有 source "arch/$SRCARCH/Kconfig" 一行，ARM64 的入口是 arch/arm64/Kconfig，交叉编译必须带 CROSS_COMPILE。
  • 六个写法够了：menu 分组、config 声明、depends on 前置、select 反选、choice 单选、help 正文；类型 bool/tristate/string 决定菜单里是 [ ]、< > 还是输入框。
  • 三个文件一条链：.config（人读）→ auto.conf（Makefile 读）→ autoconf.h（C 读）；=m 在 C 里是 CONFIG_X_MODULE。
  • 三种手段分工：menuconfig 看依赖、scripts/config 脚本改、grep 查符号与差异；改完纪律是 olddefconfig。
  • ARM64 只有三个菜单是自己的（Platform selection / Kernel Features / Boot options），其余全是各子系统 source 进来的公共菜单。
  • Boot options 只有四个可动开关：ACPI parking protocol（ACPI 平台唤醒从 CPU）、CMDLINE（编译期内置命令行）、CMDLINE_FORCE（无视 bootloader）、EFI（UEFI 运行时＋stub，select 五个配套项）。
  • x86 十五个一级菜单里真正需要逐项判断的不多，绝大多数保持默认；判断标准是「这块板子上有没有这个硬件」与「这套内核要不要这个功能」。
  • 裁剪顺序：能启动的基线 → 开 IKCONFIG → 删硬件探针 → 删协议与文件系统 → 最后删调试设施 → 每步 savedefconfig。
  • 参数与配置项分层：pci=realloc=on 是运行时覆盖，CONFIG_PCI_REALLOC_ENABLE_AUTO 是编译期能力，两者不能互相替代。
