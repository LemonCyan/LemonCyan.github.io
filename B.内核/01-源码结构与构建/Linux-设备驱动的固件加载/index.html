源码基线：Linux 3.x（drivers/base/firmware_class.c）。4.18 起这个文件被拆成 drivers/base/firmware_loader/ 下五个文件，差异集中在第九章。API 签名与查找顺序按 7.x 官方文档核对过。 相关篇目：模块加载与 vermagic 见 Linux内核模块：编译、加载与调试追踪，/lib/firmware 怎么打进 rootfs 见 根文件系统的制作，WiFi 固件的真实踩坑现场见 RK3399 WiFi AP6356 驱动。

一、驱动和固件不是一回事 #

这两个词在日常语境里被混用得厉害。说「内存」，大部分人指 SDRAM，但也有人把固化的 Flash 叫内存，你没法说他错，那确实是一种「内部存储」。但在内核里，这两个词有明确边界。

驱动 Driver 固件 Firmware
跑在哪 跑在控制处理器上，也就是跑操作系统的那个核 跑在非控制处理器上：外设里自带的小 MCU，或者主处理器里被 bare metal 占用的那几个核
谁调度 内核调度，有进程上下文、能睡眠 没有内核参与，自己的启动流程、自己的中断
指令集 跟内核同一套 经常是完全不同的指令集（一颗 WiFi 芯片里可能是 ARM Cortex-M0）
内核怎么看待 一段要注册到总线上的代码 一段数据，内核不理解内容，只负责搬运

驱动通过 driver_register() 注册到 bus_type 上，代表系统具备了驱动某种设备的能力。设备被枚举到、注册到同一条总线上，总线做匹配，匹配成功调 probe()，把端口、中断号这些信息交给驱动，驱动再去初始化真实硬件、把控制接口挂到字符设备或 v4l2 之类的子系统上。

固件在这个流程里只是个货物。probe() 里调一次固件接口，拿到一段字节，按厂商规定的时序写进设备的 RAM 或 flash，然后设备自己跑起来。

所以「driver 和 firmware 没有直接关系，但 firmware 一般由驱动去加载」这句话是准确的。操作系统不需要理解固件是什么，只有用这段数据的那个设备知道。

二、为什么不把固件塞进驱动源码 #

新手最直觉的做法是这样：

c
static const char my_firmware[] = { 0x34, 0x78, 0xa4, /* ... 几十万字节 ... */ };

这条路基本是错的，四个理由：

问题 具体后果
许可证 厂商发布的固件几乎不可能在 GPL 之下。把二进制 blob 混进 GPL 代码，法律状态说不清，主流内核不会收
体积 一颗 WiFi 芯片的固件动辄几百 KB 到几 MB，全塞进 .c 文件，编译器和编辑器都难受
升级 换个固件版本要重编内核、重刷镜像。而固件升级本来是件很轻的事
颗粒度 同一颗芯片在不同板子上可能要不同固件（校准数据是逐台定制的），编进内核等于给每块板子编一份

正确做法是需要的时候从用户空间取。这里还有一条容易被忽略的纪律：不要在内核里直接 filp_open("/lib/firmware/xxx") 自己读文件。那样做把「用哪个路径」这个策略写进了内核，还要处理 VFS 的种种边界情况，出错面很大。内核专门为这件事提供了一个接口。

例外确实存在：CONFIG_EXTRA_FIRMWARE 允许把固件编进内核，用于「驱动在根文件系统挂载之前就要用固件」的场景（比如某些存储控制器）。第八章讲它。原稿说「包含内嵌固件的驱动不可能被接受进主流内核」，这句话过时了，准确的说法是「第三方二进制 blob 因许可证问题难以进主线，而内核自己提供了 EXTRA_FIRMWARE 这条合法通道」。

三、request_firmware 这一族：六个 API 怎么选 #

现在的接口不止一个函数，是一族。选错了会出现「程序能跑但启动多等 60 秒」这种隐蔽问题。

API 同步/异步 失败时是否等兜底超时 什么时候用
request_firmware() 同步 是 默认选择。固件是必需的，probe() 里可以睡眠
request_firmware_direct() 同步 否 固件是可选的，不想为「文件不存在」白等 60 秒
firmware_request_nowarn() 同步 是（但失败不刷警告） 固件可选，但希望保留兜底路径
firmware_request_platform() 同步 是 需要从 UEFI 固件里找内嵌副本（仅 x86）
request_firmware_into_buf() 同步 是 已经分配好 DMA buffer，不想让内核再分配一份
request_firmware_nowait() 异步 是 probe() 不能睡眠，或者不想阻塞启动

签名（按 7.x 文档核对）：

c
int request_firmware(const struct firmware **firmware_p,
                     const char *name, struct device *device);

int request_firmware_direct(const struct firmware **firmware_p,
                            const char *name, struct device *device);

int firmware_request_nowarn(const struct firmware **firmware,
                            const char *name, struct device *device);

int firmware_request_platform(const struct firmware **firmware,
                              const char *name, struct device *device);

int request_firmware_into_buf(const struct firmware **firmware_p,
                              const char *name, struct device *device,
                              void *buf, size_t size);

int request_firmware_nowait(struct module *module, bool uevent,
                            const char *name, struct device *device,
                            gfp_t gfp, void *context,
                            void (*cont)(const struct firmware *fw, void *context));

三条从文档里抄下来的硬约束，踩过就知道多重要：

  • request_firmware() 必须在允许睡眠的上下文调用，因为它内部要 wait_for_completion。中断上下文里调它直接报错。
  • request_firmware_nowait() 不能在原子上下文调用。它虽然叫 nowait，但内部仍然靠工作队列，gfp 传 GFP_ATOMIC 时不能睡眠。
  • 调用方必须持有 device 的引用计数（get_device() 过）。固件加载完成前设备被释放，fw_priv 就是野指针。

还有一个 name 的坑：不能包含 .. 路径成分。foo/bar..bin 是合法的，foo/../bar.bin 会被拒绝。这是防路径穿越。

四、struct firmware 与正确用法 #

c
struct firmware {
    size_t size;
    const u8 *data;      /* 2008 年起是 const，写它编译器会报错 */
};

data 是 const 这件事有个历史：2008 年 5 月 David Woodhouse 的补丁把 fw->data 改成了 const u8 *。老资料里写的 u8 *data 是 2.6 时代的形态。这个 const 不是装饰，它在告诉你：这块内存不归你管，别改。

标准用法就三行：

c
const struct firmware *fw;
int ret;

ret = request_firmware(&fw, "brcm/brcmfmac4356-sdio.bin", dev);
if (ret) {
    dev_err(dev, "firmware load failed: %d\n", ret);
    return ret;
}
/* 校验 fw->data / fw->size，然后写进硬件 */
ret = my_device_upload_fw(dev, fw->data, fw->size);
release_firmware(fw);        /* 无论 upload 成功还是失败，这里都要调 */
return ret;

四个必须记住的点：

一、fw->data 是用户态来的未校验数据。 内核从 /lib/firmware 读文件，读之前不验签名、不验长度、不验内容。厂商固件一般带标识串和校验和，发送到硬件之前自己全检一遍。长度不够、magic 不对、checksum 不符，全部当场报错退出。真把一段错数据写进设备 RAM，轻则设备不响应，重则上电时序乱掉。

二、release_firmware() 一定要调。 漏掉就是内存泄漏，而且是那种压测才发现的泄漏（每次 resume 重新加载一次固件，几次之后 OOM）。

三、request_firmware 失败时 firmware_p 被置为 NULL，不能对 NULL 调 release_firmware。 所以模板里要先判 ret。

四、固件缓存会自动生效。 用 uevent 路径请求过的固件会被缓存，resume 时不用再去文件系统捞一遍。这条对 suspend/resume 频繁的设备很关键，因为 resume 早期根文件系统可能还没就绪。

五、内核去哪儿找固件：查找顺序与搜索路径 #

请求发出去之后，内核按固定顺序找。这个顺序值得背下来，因为排错时「固件明明在 /lib/firmware 里为什么加载不到」的答案基本都在这个顺序里：

text
① built-in firmware    CONFIG_EXTRA_FIRMWARE 编进 vmlinux 的，最先命中
② firmware cache       上次请求过的，直接返回
③ direct filesystem    按搜索路径直接读文件
④ platform firmware    只有 firmware_request_platform() 走这条，从 UEFI 里挖内嵌副本
⑤ sysfs fallback       前三步都失败且兜底开启，创建 /sys/class/firmware/xxx/，发 uevent 等用户态来喂

第 ③ 步的搜索路径是这四个，按顺序：

顺序 路径 用途
0 fw_path_para 自定义路径，默认空。由 firmware_class.path= 内核参数或 /sys/module/firmware_class/parameters/path 设置，上限 256 字符
1 /lib/firmware/updates/$(uname -r)/ 针对当前内核版本的更新
2 /lib/firmware/updates/ 与版本无关的更新
3 /lib/firmware/$(uname -r)/ 当前内核版本的固件
4 /lib/firmware/ 兜底

updates 这两级是给发行版留的口子：包管理器装新固件放进 updates/，原厂固件留在 /lib/firmware/，出问题时删掉 updates 下的就能回退。

自定义路径的两种设法的写法：

bash
# 内核参数（开机就生效，适合固件在独立分区）
firmware_class.path=/vendor/firmware

# 运行时改（调试用，注意 -n 去掉换行，否则路径里带 \n 匹配不上）
echo -n /vendor/firmware > /sys/module/firmware_class/parameters/path

那个 echo -n 是实践里最容易漏的一步。用 echo 不带 -n 会写入一个尾部换行，路径变成 /vendor/firmware\n，后面所有查找全部失败，而 cat 出来看着完全正常。

嵌入式上还有一个更隐蔽的：/lib/firmware 是符号链接指向别处，或者 rootfs 是只读的 squashfs 而固件放在可写分区。ls 能看到文件，内核走 VFS 时因为挂载点时序问题读不到。诊断方法见第十章。

六、sysfs 兜底加载：loading / data / device #

第 ⑤ 步只在「直接读文件失败」且「兜底机制开着」时才发生。这是理解起来最绕的一环，但它有历史原因：早期内核还没有「直接从文件系统读文件」的能力，固件必须由用户态喂进去。

内核在 /sys/class/firmware/ 下建一个以固件名命名的目录，里面三个文件：

文件 类型 作用
loading 普通属性 写 1 开始加载（会清掉上一次的半成品），写 -1 中止，写 0 表示数据写完了
data 二进制属性 用户态把固件字节写进来。内核按 PAGE_SIZE 增量扩缓冲区
device 符号链接 指回 /sys/devices 下发起请求的那个设备

然后内核发一个 KOBJ_ADD 的 kobject uevent。用户态收到后，环境变量里带着三个值：

text
FIRMWARE=brcm/brcmfmac4356-sdio.bin
TIMEOUT=60
ASYNC=0
DEVPATH=/devices/...            # 内核自动设置

用户态脚本按这个协议喂数据：

bash
# 这两个变量内核已经放在环境里了
FW_DIR=/lib/firmware
echo 1 > /sys/$DEVPATH/loading
cat $FW_DIR/$FIRMWARE > /sys/$DEVPATH/data
echo 0 > /sys/$DEVPATH/loading

三步里任何一步出错都要写 -1 中止，否则内核会一直等到超时。

超时是 60 秒，不是 10 秒。原稿写「10 秒内没有被服务，内核就放弃」，那是 2007 年 2 月之前的值。Dave Jones 因为 ipw 网卡加载固件太慢提了个补丁，把 loading_timeout 从 10 改成了 60，Greg KH 收进了驱动核心。非 uevent 路径（自定义兜底）用的是 MAX_JIFFY_OFFSET，等于不限时。

改超时：

bash
cat /sys/class/firmware/timeout      # 看当前值
echo 120 > /sys/class/firmware/timeout
echo 0 > /sys/class/firmware/timeout   # 0 = MAX_JIFFY_OFFSET，等于不限时

6.1 这套机制现在基本不用了 #

关键在于：udev 在 2014 年就把固件加载功能删了（systemd commit be2ea723b1d0，v217，2014 年 8 月）。同时 CONFIG_FW_LOADER_USER_HELPER_FALLBACK 在主流发行版里是关的。

两个配置的配合关系容易搞错：

CONFIG_FW_LOADER_USER_HELPER ..._FALLBACK 效果
y y 所有请求都允许走 sysfs 兜底（request_firmware_direct() 除外）
y n 只有 request_firmware_nowait() 且 uevent=true 时才可能兜底
n — 完全没有兜底，request_firmware 走不到第 ⑤ 步

y + n 这个组合下，request_firmware() 永远不会触发 kobject uevent 兜底。这就是为什么现代内核上「没有 udev 规则也能加载固件」，因为压根不走兜底，直接从文件系统读到了。

那么原来的 udev 规则长什么样？留个历史存档，读老资料时会碰到：

text
# /etc/udev/rules.d/50-udev-default.rules（2014 年前的形态）
SUBSYSTEM=="firmware", ACTION=="add", RUN+="firmware.sh"

现在的等价物是这两个 sysctl，调试时有用：

bash
# 全局关掉 sysfs 兜底（省掉「文件不存在还要等 60 秒」）
echo 1 > /proc/sys/kernel/firmware_config/ignore_sysfs_fallback

# 强制开启（调试自己的兜底脚本时）
echo 1 > /proc/sys/kernel/firmware_config/force_sysfs_fallback

force_sysfs_fallback=1 效果上等价于把 CONFIG_FW_LOADER_USER_HELPER_FALLBACK 编成 y，而且不用重编内核。

七、源码链路：firmware_class.c 里发生了什么 #

以下基于 3.x 的 drivers/base/firmware_class.c。这段代码是为了看清「一次请求到底经过哪几步」，不是为了记行号。

7.1 入口只有两层 #

c
int request_firmware(const struct firmware **firmware_p, const char *name,
                     struct device *device)
{
    int uevent = 1;
    return _request_firmware(firmware_p, name, device, uevent);
}

那个 uevent = 1 是一个布尔开关，往下传给 _request_firmware，决定「失败后是否允许创建 sysfs 兜底并播 uevent」。request_firmware_direct() 传的是 0，所以它跳过兜底、立刻返回。这就是「可选固件别用 request_firmware」的实现依据。

7.2 _request_firmware 的主干 #

c
static int _request_firmware(const struct firmware **firmware_p, const char *name,
                             struct device *device, int uevent)
{
    struct device *f_dev;
    struct firmware_priv *fw_priv;
    struct firmware *firmware;
    struct builtin_fw *builtin;
    int retval;

    if (!firmware_p)
        return -EINVAL;

    *firmware_p = firmware = kzalloc(sizeof(*firmware), GFP_KERNEL);
    /* 省略出错保护 */

    /* 第一顺位：built-in firmware */
    for (builtin = __start_builtin_fw; builtin != __end_builtin_fw; builtin++) {
        if (strcmp(name, builtin->name))
            continue;
        dev_info(device, "firmware: using built-in firmware %s\n", name);
        firmware->size = builtin->size;
        firmware->data = builtin->data;
        return 0;
    }

    /* 建 sysfs 目录、挂属性文件 */
    retval = fw_setup_device(firmware, &f_dev, name, device, uevent);
    if (retval)
        goto error_kfree_fw;

    fw_priv = dev_get_drvdata(f_dev);

    if (uevent) {
        if (loading_timeout > 0) {
            fw_priv->timeout.expires = jiffies + loading_timeout * HZ;
            add_timer(&fw_priv->timeout);
        }
        kobject_uevent(&f_dev->kobj, KOBJ_ADD);
        wait_for_completion(&fw_priv->completion);
        set_bit(FW_STATUS_DONE, &fw_priv->status);
        del_timer_sync(&fw_priv->timeout);
    } else {
        wait_for_completion(&fw_priv->completion);
    }

    mutex_lock(&fw_lock);
    if (!fw_priv->fw->size || test_bit(FW_STATUS_ABORT, &fw_priv->status)) {
        retval = -ENOENT;
        release_firmware(fw_priv->fw);
        *firmware_p = NULL;
    }
    fw_priv->fw = NULL;
    mutex_unlock(&fw_lock);

    device_unregister(f_dev);       /* 注销 sysfs 目录 */
    goto out;

error_kfree_fw:
    kfree(firmware);
    *firmware_p = NULL;
out:
    return retval;
}

几个设计点：

__start_builtin_fw / __end_builtin_fw 是链接脚本符号。 编进内核的固件通过 __attribute__((section(".builtin_fw"))) 落在同一个段里，两个符号夹住就是数组。struct builtin_fw 里存 name、data、size 三个字段。这套手法和 machine_desc 的 .arch.info.init 段是同一个套路（见 设备树的内核解析与启动流程）。

built-in 命中时直接返回，不建 sysfs 设备。 所以编进内核的固件在 /sys/class/firmware/ 下看不到任何痕迹，这是判断「固件到底走没走 built-in」的唯一线索：dmesg 里找 using built-in firmware。

wait_for_completion 之前先挂定时器、先发 uevent。 顺序不能反：定时器要先就位，否则用户态响应太快、或者在 kobject_uevent 里睡过去，超时就不准了。

-ENOENT 是「用户态没喂数据」，不是「文件不存在」。 看到这个错误码，先查 /sys/class/firmware/ 有没有残留目录，再看 loading 是不是被写了 -1。

7.3 fw_setup_device 与 fw_register_device #

c
static int fw_setup_device(struct firmware *fw, struct device **dev_p,
                           const char *fw_name, struct device *device,
                           int uevent)
{
    struct device *f_dev;
    struct firmware_priv *fw_priv;
    int retval;

    *dev_p = NULL;
    retval = fw_register_device(&f_dev, fw_name, device);
    if (retval)
        goto out;

    fw_priv = dev_get_drvdata(f_dev);
    fw_priv->fw = fw;

    /* 二进制属性 data，负责收字节 */
    retval = sysfs_create_bin_file(&f_dev->kobj, &fw_priv->attr_data);
    /* 省略出错保护 */

    /* 普通属性 loading，负责开关 */
    retval = device_create_file(f_dev, &dev_attr_loading);
    /* 省略出错保护 */

    if (uevent)
        f_dev->uevent_suppress = 0;
    *dev_p = f_dev;
    goto out;

error_unreg:
    device_unregister(f_dev);
out:
    return retval;
}

两个属性文件，两种创建方式，不能混：data 是二进制，用 sysfs_create_bin_file；loading 是普通文本属性，用 device_create_file。

uevent_suppress 默认是 1（抑制），只有在需要播 uevent 时才置 0。这个字段是 device_register() 里不立刻播 KOBJ_ADD 的开关，避免设备刚注册就发事件、此时 fw_priv 还没填完。

c
static int fw_register_device(struct device **dev_p, const char *fw_name,
                              struct device *device)
{
    int retval;
    struct firmware_priv *fw_priv = kzalloc(sizeof(*fw_priv), GFP_KERNEL);
    struct device *f_dev = kzalloc(sizeof(*f_dev), GFP_KERNEL);

    *dev_p = NULL;
    /* 省略出错保护 */

    init_completion(&fw_priv->completion);
    fw_priv->attr_data = firmware_attr_data_tmpl;   /* data 文件的读写函数 */
    strlcpy(fw_priv->fw_id, fw_name, FIRMWARE_NAME_MAX);

    fw_priv->timeout.function = firmware_class_timeout;
    fw_priv->timeout.data = (u_long) fw_priv;
    init_timer(&fw_priv->timeout);

    fw_setup_device_id(f_dev, device);              /* 用设备名生成 fw 设备名 */
    f_dev->parent = device;
    f_dev->class = &firmware_class;
    dev_set_drvdata(f_dev, fw_priv);                /* f_dev->driver_data = fw_priv */
    f_dev->uevent_suppress = 1;
    retval = device_register(f_dev);
    if (retval) {
        dev_err(device, "%s: device_register failed\n", __func__);
        goto error_kfree;
    }
    *dev_p = f_dev;
    return 0;
}

dev_set_drvdata 那一行是全篇的关键索引：设备类不提供自己的私有数据机制，fw_priv 靠 driver_data 这个通用字段挂到 f_dev 上。所以下一层函数拿到 f_dev 之后第一件事就是 dev_get_drvdata(f_dev) 把它取回来。

7.4 两个模板结构 #

c
/* data 文件：模式和读写回调 */
static struct bin_attribute firmware_attr_data_tmpl = {
    .attr = { .name = "data", .mode = 0644 },
    .size = 0,
    .read = firmware_data_read,      /* 测试驱动才用，正常流程不读 */
    .write = firmware_data_write,    /* 用户态写固件字节进来 */
};

/* 设备类：uevent 与释放 */
static struct class firmware_class = {
    .name = "firmware",              /* 决定 /sys/class/firmware/ */
    .dev_uevent = firmware_uevent,   /* 填 FIRMWARE / TIMEOUT / ASYNC 三个环境变量 */
    .dev_release = fw_dev_release,   /* unregister 时释放 fw_priv */
};

.name = "firmware" 这个类名不能改。内核文档明写了：因为属性文件是类名的一部分，改名会破坏老用户态的兼容性，所以 firmware_class 这个模块名会一直留着，尽管它现在只负责兜底这一条路径。

八、把固件编进内核：CONFIG_EXTRA_FIRMWARE #

这条通道是为「驱动在挂载根文件系统之前就要用固件」准备的。典型场景：启动盘控制器需要固件才能工作，但 rootfs 在这个盘上，鸡生蛋问题。

text
CONFIG_EXTRA_FIRMWARE="brcm/brcmfmac4356-sdio.bin i915/skl_dmc_ver1_27.bin"
CONFIG_EXTRA_FIRMWARE_DIR="/lib/firmware"

CONFIG_EXTRA_FIRMWARE 是空格分隔的相对路径，..._DIR 是这些路径的基准目录（注意它指的是编译主机上的目录，不是目标机）。

好处：

  • 快，不用走文件系统
  • 不依赖 rootfs 时序
  • 固件永远在，不会因为误删 /lib/firmware 导致设备起不来

代价（这几条决定了它只能用于少数场景）：

代价 说明
许可证 第三方二进制 blob 进内核镜像，法律状态比放 /lib/firmware 更敏感
必须重编内核 换个固件版本要重编、重刷，升级成本从「scp 一个文件」变成「刷机」
体积 vmlinux 直接变大，所有板子都背着
逐台定制数据不行 WiFi 校准数据每台设备不同，没法编进内核

验证有没有生效：dmesg 里会有 firmware: using built-in firmware xxx，而 /sys/class/firmware/ 下不会有对应目录。

九、版本演进：从 firmware_class.c 到 firmware_loader/ #

原稿全篇基于一个已经消失的文件。drivers/base/firmware_class.c 在 2018 年被 Luis Rodriguez 拆分，现在是五个文件：

text
drivers/base/firmware_loader/
├── main.c        request_firmware 家族、查找顺序、built-in、缓存
├── direct.c      直接文件系统查找
├── fallback.c    sysfs 兜底、uevent、超时
├── sysfs.c       loading / data 属性
└── helper.c      自定义 helper 路径

拆分的原因写在提交信息里：这个文件二十多年堆下来已经难以跟读，不拆开没法维护。模块名仍然是 firmware_class（兼容性），但代码位置全变了。

其它读到老资料时要对上的差异：

3.x 形态 7.x 形态 影响
struct firmware { u8 *data; } const u8 *data 写 fw->data 编译不过，2008 年起就这样
loading_timeout = 10 = 60 2007 年 2 月改的，见第六章
udev 规则 SUBSYSTEM=="firmware" 已从 udev 移除（2014） 现代系统上这套规则不存在了
CONFIG_FW_LOADER 管全部 另有 FW_LOADER_USER_HELPER / _FALLBACK / FW_LOADER_COMPRESS 裁内核时要分开配
无 request_firmware_direct 有 可选固件必用
无 firmware_request_nowarn 有 引入了但版本号未逐一核对
无 firmware_request_platform 有（仅 x86 EFI） 见下一段
无 request_firmware_into_buf 有 DMA 场景

firmware_request_platform() 单独说一句：它允许从 UEFI 的 EFI_BOOT_SERVICES_CODE 里挖出厂商预先烧进去的固件副本，用于「设备固件藏在系统 ROM 里、没有独立文件」的情况。限制有三条：只支持 x86（其它架构在扫描之前就把那段内存释放了）、扫描发生在 start_kernel() 末尾（更早的代码用不了）、优先级低于 /lib/firmware（放一个同名文件就能覆盖）。

十、排错清单 #

按「固件到底卡在哪一步」倒着查：

现象 原因 查什么
Direct firmware load for xxx failed with error -2 文件真的不存在 ls /lib/firmware/xxx；注意 -2 是 -ENOENT
同上但文件明明在 搜索路径没命中 查 fw_path_para 有没有脏值（cat /sys/module/firmware_class/parameters/path | hexdump -C 看有没有 \n）
failed with error -2 后紧跟 Falling back to user helper 进了 sysfs 兜底但没人喂数据 60 秒后失败。ignore_sysfs_fallback=1 可以立刻失败
-ENOENT 但文件存在 用户态写了 loading 又写 -1 中止 dmesg 找 firmware: xxx loading timed out
启动卡住几十秒才继续 可选固件用了 request_firmware，白等兜底 换 request_firmware_direct() 或 firmware_request_nowarn()
驱动编进内核后固件加载失败，编成模块就正常 加载时序早于 rootfs 挂载 改 =m，或 CONFIG_EXTRA_FIRMWARE，或塞 initramfs
firmware: using built-in firmware 但版本不对 EXTRA_FIRMWARE 里有旧副本 它优先级最高，会盖住 /lib/firmware 里的新版
resume 后固件加载失败 缓存失效或根文件系统未就绪 用 uevent 路径请求（能建缓存），或 firmware_request_cache() 提前缓存
加载成功但设备不工作 固件文件对了，但内容不属于这颗芯片 核对厂商型号、固件里的标识串与校验和

最后一条最费时间，也是唯一没法靠 dmesg 解决的：固件文件名对得上不等于固件内容对。同一颗 WiFi 芯片，不同模组厂贴的固件不同（射频校准参数在固件里），拿错文件的现象是「加载成功、初始化也过了、就是扫不到 AP」。判断方法只有一个：看固件里的版本字符串和设备手册里的要求对不对。

真实案例见 RK3399 WiFi AP6356 驱动：brcmfmac 在 5.2 和 6.3 两个版本里要求的文件名不一样，6.3 需要 brcmfmac4356-sdio.rockchip,rk3399-evb.bin，而厂商只提供 brcmfmac4356-sdio.bin，解决办法是复制一份改名。这不是 bug，是 brcmfmac 的板级固件命名规则。
