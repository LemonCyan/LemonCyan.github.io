读内核源码最怕的不是难，是迷路。八百万行的代码树里没有路标，唯一的办法是先有一张地图，再谈细节。本篇就是那张地图：它不打算把你教会写驱动，只打算让你在任何一个 .c 文件里停下时，知道自己站在哪个子系统的哪一层、上下游分别是谁。

按这个定位，阅读顺序建议是：先看第一章建立「内核是宏内核」这个前提，再看第二章的子系统拓扑和第三章的三个结构体（这是内核的骨架），然后拿第四章的目录地图去源码树里对号，最后五、六、七三章各取一条纵向的动线（启动、系统调用、中断）把骨架跑活。第八章不是新知识，是防止你读源码时把老代码当成笔误的一副眼镜。

一、两种内核形态与 Linux 的选择 #

1.1 分界线只有一条：服务跑在谁的地址空间里 #

操作系统教科书把内核实现分成两大流派，讲得很玄。其实分界线只有一条——文件系统、网络协议栈、设备驱动这些服务，是跑在内核地址空间里，还是跑在独立的用户进程里。跑在一起叫宏内核（monolithic kernel），拆出去叫微内核（microkernel）。

维度 宏内核（Linux、传统 Unix） 微内核（Mach、Minix 3、QNX、seL4）
内核里放什么 调度、内存管理、VFS、协议栈、绝大多数驱动 只有调度、IPC、最基本的中断与地址空间管理
服务跑在哪 内核地址空间，和内核同一个页表 独立用户态进程（server），各自一套页表
服务之间的调用 一次 call 指令，参数走寄存器 一次 IPC 消息，涉及陷入、调度、地址空间切换
单次跨服务开销 数十纳秒量级 数微秒量级，随 TLB 与 cache 失效放大
一个驱动崩了 野指针写到哪就崩到哪，通常整机 panic 只死一个 server，微内核可以重启它
扩展方式 重编内核，或加载 .ko 新写一个 server 进程即可
可验证性 代码量巨大，难做形式化 内核小，seL4 做过完整的功能正确性证明
典型代表 Linux、FreeBSD、Solaris Mach（macOS 的 XNU 只吸收了它的消息机制）、QNX、Minix 3

1.2 微内核的性能税从哪里来 #

微内核的理论优势是真的，代价也是真的，而且代价集中在一条路径上：每次跨服务调用都要过一次地址空间。

宏内核里，vfs_read() 调用 ext4_file_read_iter() 是一条 call：同一套页表、同一份 TLB、同一份 L1 缓存，参数在寄存器里就过去了。

微内核里，同样的动作变成：用户进程发 IPC 给文件服务 → 微内核做消息拷贝或页映射 → 调度器切到文件服务进程 → 切页表（TLB 大面积失效）→ 文件服务处理完再 IPC 回来。一次读写要付两到四次上下文切换，每次切换都要重新暖 TLB 和缓存。机械硬盘时代这个开销还能被 I/O 等待掩盖，NVMe 和内存文件系统时代它就是纯损耗。

这就是为什么微内核在实时、安全、可验证场景（QNX 车载、seL4 军用）活得很好，而在通用计算场景反复败给 Linux：通用计算的瓶颈在吞吐，安全关键系统的瓶颈在可证明性，两者对 IPC 开销的容忍度差了两个数量级。

1.3 一句历史 #

1992 年 Tanenbaum 与 Linus 在 Usenet 上就「宏内核是否过时」吵过一轮，结论是两边各对一半：微内核更安全，但 IPC 开销在通用场景下始终是硬伤；宏内核靠 LKM 解决了扩展性，臃肿那一半只能靠 Kconfig 在编译期裁掉。所谓「混合内核」（Windows NT、macOS 的 XNU）本质是宏内核外面加了一层消息机制，文件系统与大部分驱动照样在内核态。

1.4 LKM：把宏内核做出模块化的三个支柱 #

Linux 选了宏内核，但传统宏内核有个致命弱点：内核一旦编好就改不了，加一个驱动要重编整棵树。LKM（Loadable Kernel Module）就是补这个洞的。它靠三个机制成立：

支柱 载体 作用
动态装载 insmod / modprobe + .ko 文件 运行期把一段目标代码搬进内核地址空间
符号解析 EXPORT_SYMBOL / EXPORT_SYMBOL_GPL 生成的 __ksymtab 段 模块里对 printk、kmalloc 的引用在加载时被重定位到内核中的真实地址
统一地址空间 模块加载后被重定位进内核页表 模块调用内核函数是一次普通 call，没有 IPC、没有切换

一个最小的模块构建脚本长这样（注意 M= 指的是模块目录，不是内核树）：

makefile
obj-m += demo.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD  := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

关键认知：LKM 不是微内核。这是最容易混淆的一点，三者对照如下：

对比项 宏内核 LKM 模块 微内核 server
地址空间 内核空间 内核空间（与内核共用） 用户空间，独立页表
是否独立进程 否 否，没有自己的 task_struct 是，是普通进程
崩溃影响 整机 整机（照样 panic） 仅该 server
调用开销 函数调用 函数调用 IPC + 上下文切换
可否卸载 否 是（引用计数归零后） 是（进程退出）
隔离性 无 无 有

所以模块化解决的是发行与裁剪问题，不是隔离与容错问题。想让驱动崩了不拖垮系统，只有微内核或用户态驱动框架（如 UIO、VFIO、DPDK）那条路，代价是把性能让出去。

二、五大子系统与协作拓扑 #

2.1 职责与落点 #

内核按「管什么资源」分成五大子系统。这张表是全篇使用频率最高的一张，建议记住左两列，用时再查右两列：

子系统 缩写 管什么 核心数据结构 源码落点
进程调度 SCHED CPU 时间，决定谁在什么时候跑 task_struct、struct rq、sched_class kernel/sched/（core.c、fair.c、rt.c、deadline.c）
内存管理 MM 物理页与虚拟地址空间，页表、分配器、回收 mm_struct、vm_area_struct、struct page mm/（memory.c、mmap.c、page_alloc.c、slub.c）
虚拟文件系统 VFS 把一切设备抽象成「文件」的统一接口 inode、dentry、file、super_block fs/（namei.c、open.c、read_write.c、dcache.c、inode.c、super.c）
网络 NET 协议栈与网卡收发 sk_buff、sock、net_device net/（core/dev.c、ipv4/tcp.c、socket.c）
进程间通信 IPC 进程之间的数据与事件传递 kern_ipc_perm、msg_queue、shmid_kernel ipc/（util.c、msg.c、shm.c、sem.c）

这张表里 VFS 一行的落点是勘误过的：常见的中文资料（含本篇的素材原文）把它写成 fs/vfs.c 与 fs/inode.c，而内核树里从来没有 fs/vfs.c 这个文件，VFS 是散在 fs/ 顶层的十来个文件里的一组抽象。详见文末的勘误表。

素材里另一组结论带版本号，必须一起记：

指标 Linux 3.10.29（长期支持分支） 5.x / 6.x 时代
分析基准 素材 2 全文按 3.10.29 + ARM 展开 本篇默认按 5.x/6.x 描述，凡涉及版本差异处均标注
drivers/ 占代码量 约 49.4% 约 60%（删掉大量重复驱动后仍过半）
五大子系统的划分 已定型 未变（这是内核架构里最稳定的部分）
体系结构视角 以 ARM（32 位）为主 arm64 成为嵌入式主力，x86 仍作对照

2.2 每个子系统内部还有纵向分层 #

五大子系统是横向切分。纵向看，每个子系统内部都是一条「系统调用接口 → 通用机制 → 体系结构相关 → 硬件」的四层结构。这四层在源码里的对应关系是固定的：

子系统 系统调用接口层 通用机制层 体系结构相关层
SCHED sched_setscheduler() 等（kernel/sched/core.c） 调度策略：CFS/RT/DEADLINE（fair.c、rt.c、deadline.c） 上下文切换 switch_to、CPU 热插拔（arch/*/kernel/）
MM brk()、mmap()、madvise() 页分配、缺页、回收、Slab（mm/） 页表操作、TLB 刷新、cache 维护（arch/*/mm/）
VFS open()、read()、write() 逻辑文件系统（ext4/、fat/、proc/、sysfs/） 设备无关接口、具体设备驱动（drivers/）
NET socket()、sendmsg() TCP/IP、UDP、Netlink 等协议实现（net/ipv4/、net/core/） 网卡驱动与 net_device（drivers/net/）
IPC msgget()、shmat()、semop() 消息队列、共享内存、信号量集（ipc/） 无（IPC 不直接碰硬件）

这张表回答一个很实际的问题：看到一个函数名，怎么判断它属于哪一层。判据是参数和上下文——出现 struct file *、loff_t 的多半在 VFS 通用层；出现 pgd_t、pte_t 的一定在体系结构相关的内存层；出现 struct sock * 而在 net/ipv4/ 下的，是协议实现层。

2.3 依赖拓扑 #

五个子系统不是并列的，而是有明确的上下游：

text
                  +---------------------------+
                  |     进程调度 SCHED        |
                  |  task_struct / rq / 红黑树 |
                  +------+-------------+------+
                         |             |
        切换时换页表/active_mm         | 唤醒、睡眠
                         v             v
        +--------------------+   +--------------------+
        |   内存管理 MM      |   |   进程间通信 IPC   |
        |  页表/页框/回收    |   |  共享内存、消息    |
        +---------+----------+   +---------+----------+
                  |                        |
        页缓存/swap 依赖                   | 共享内存靠 MM 的
                  v                        v  mmap 实现
        +--------------------+   +--------------------+
        |  虚拟文件系统 VFS  |<--+      网络 NET       |
        |  inode/dentry/file |   |  sk_buff/socket    |
        +---------+----------+   +---------+----------+
                  |                        |
                  v                        v
        +------------------------------------------------+
        |        设备模型与具体驱动（drivers/）           |
        +------------------------------------------------+

四条依赖值得单独记住，它们解释了内核里大量「为什么这里要引用那里」的代码：

  1. SCHED → MM：进程切换必须换页表，所以 switch_mm() 在 context_switch() 里；内核线程没有自己的 mm，只能借用上一个进程的 active_mm。
  2. MM ↔ VFS：页缓存（page cache）住在 MM 里，但由 VFS 通过 address_space 组织；内存紧张时回收页缓存要回调文件系统的 writepage；swap 又把匿名页写进块设备。这两个子系统互相咬得最紧。
  3. NET → MM：sk_buff 的 head/data/tail/end 四指针背后是一整块 kmalloc 出来的缓冲区，协议栈每层 skb_push/pull 只改指针不搬数据，靠的就是 MM 给的连续内核虚拟地址。
  4. IPC → MM：System V 共享内存（shmget + shmat）本质是让两个 mm_struct 的 VMA 指向同一批物理页，实现完全落在 MM 里；信号量集和消息队列则真的在 ipc/ 里自己管。

2.4 一次 read() 的跨子系统穿行 #

把上面五张表串起来最有效的办法，是追一次真实的 read()。要分两种走法，因为它们的后半段完全不同。

走法 A：读一个普通文件

步 经过 关键动作 涉及结构
1 VFS ksys_read 用 fd 号在 current->files 里取到 struct file files_struct、file
2 VFS vfs_read → file->f_op->read_iter，多态分派到具体文件系统 file_operations
3 VFS + MM generic_file_read_iter 查页缓存，命中则 copy_page_to_iter 直接拷给用户态 address_space、page
4 MM + 块层 未命中：分配页、发 readahead，走 submit_bio 到块设备队列 bio、request_queue
5 驱动 块设备驱动把请求塞给 eMMC/NVMe 控制器，DMA 完成后中断 gendisk
6 SCHED 等待 I/O 期间进程置 TASK_UNINTERRUPTIBLE，让出 CPU；完成中断把它唤醒 task_struct

走法 B：读一个 socket

步 经过 关键动作
1 VFS read(sock_fd, ...) 照旧先走 VFS，靠 file 找到「文件」
2 VFS → NET 发现该 inode 是 S_IFSOCK，f_op 是 socket_file_ops，read_iter 落到 sock_read_iter
3 NET 取 struct sock 的接收队列，队列空则进入 sk_wait_data 睡眠
4 SCHED 置 TASK_INTERRUPTIBLE、挂到 sk_wq 等待队列、schedule() 让出 CPU
5 驱动 + NET 网卡收到包 → NAPI 轮询 → 协议栈逐层 skb_pull 解析 → 入 sock 接收队列 → wake_up
6 SCHED 唤醒该进程，重新进就绪队列，等调度器选中
7 MM copy_to_user 把 sk_buff 里的数据搬到用户 buf 映射的物理页

两条走法的差异很说明问题：VFS 只负责前两步——把 fd 变成 file、把操作分派到 f_op。之后的活全部由文件系统或协议栈自己干，VFS 不再参与。这就是「接口层」的含义。

素材原文用 socket 举例是对的，但它把「MM 把网卡 DMA 数据拷到用户态」放在唤醒之后一步完成，实际是七步里的最后一步，中间还夹着 NAPI 与协议栈。本书按真实路径拆开了。

2.5 三张操作函数表，是子系统解耦的通用手法 #

整个内核反复用同一招解耦：定一个结构体装函数指针，让上层只认结构体不认实现。认出这三张表，很多代码一眼就通了：

函数表 所在结构 上层看到的行为 由谁实现
file_operations struct file 的 f_op 一次 read/write/ioctl ext4、socket、字符设备、proc……
address_space_operations inode 的 i_mapping->a_ops 页缓存与磁盘之间怎么换 各文件系统
net_device_ops struct net_device 的 netdev_ops 一帧报文怎么发出去 各网卡驱动
sched_class task_struct 的 sched_class 这个任务按什么规则排队 CFS（现为 EEVDF）、RT、DEADLINE

三、三大核心数据结构 #

内核里有一千多个结构体，但撑起「系统」这个概念的是三个：task_struct（谁在跑）、mm_struct（它能看见哪片内存）、inode（它看见的文件是什么）。搞定这三个，剩下的结构体都是它们的零部件。

3.1 task_struct：进程在内核里的全部 #

每个进程（包括线程、内核线程）对应一个 task_struct，由 alloc_task_struct_node() 从 task_struct 专用 slab 里分配，放进全局链表。字段上百个，真正需要先记住的是这十几个：

字段 类型 说明
__state unsigned int 运行状态：TASK_RUNNING / TASK_INTERRUPTIBLE / TASK_UNINTERRUPTIBLE / __TASK_STOPPED / EXIT_ZOMBIE
mm struct mm_struct * 用户地址空间。内核线程为 NULL
active_mm struct mm_struct * 内核线程借用来的地址空间，只为了页表不为空
files struct files_struct * 打开文件表，fd 号就是它的下标
fs struct fs_struct * 根目录与当前工作目录，相对路径解析的起点
nsproxy struct nsproxy * PID/NET/MNT/IPC/UTS 五类命名空间，容器隔离的开关
cred const struct cred *__rcu uid/gid/capability，权限判定的唯一来源
signal struct signal_struct * 信号处理函数、阻塞掩码、待处理队列
sched_class const struct sched_class * 调度类的多态槽，决定它进哪棵队列
se / rt / dl 联合体 各调度类的私有实体，CFS 只看 se.vruntime
pid / tgid pid_t 前者是线程 ID，后者是线程组 ID（即用户眼中的「进程号」）
comm char[16] 进程名，ps 里那一列
parent / children / sibling 指针与链表 亲缘关系的三件套，ps -ef 的树从这里来

精简后的骨架（省略了 __rcu、锁与配置相关字段）：

c
struct task_struct {
    unsigned int      __state;      /* 5.14 起取代 volatile long state */
    void             *stack;        /* 内核栈，THREAD_SIZE 大小 */
    unsigned int      flags;
    int               prio, static_prio, normal_prio;
    const struct sched_class *sched_class;
    struct sched_entity      se;    /* CFS/EEVDF 用它排队 */

    struct mm_struct        *mm;
    struct mm_struct        *active_mm;
    struct files_struct     *files;
    struct fs_struct        *fs;
    struct nsproxy          *nsproxy;
    const struct cred __rcu *cred;
    struct signal_struct    *signal;

    pid_t   pid;
    pid_t   tgid;
    char    comm[TASK_COMM_LEN];    /* 16 */
    struct task_struct *parent;
    struct list_head    children;
    struct list_head    sibling;
};

两个读源码时的提醒，都是版本差异：

  • state 这个字段名在 5.14 之后没有了，代码里写的是 __state，通过 task_state(p)、set_current_state() 之类访问。老文章里 p->state 的写法现在编不过。
  • thread_info 是否内嵌在 task_struct 里取决于 CONFIG_THREAD_INFO_IN_TASK：x86_64 打开它，thread_info 就在 task_struct 内；arm64 把 thread_info 放在内核栈顶端。看到 task_thread_info(p) 别假设它一定是内嵌成员。

3.2 mm_struct：一个进程能看见的世界 #

mm_struct 描述整个用户地址空间。同一个进程的多个线程共享一个 mm_struct，这正是「线程」与「进程」在内核里的唯一实质区别：

字段 说明
mm_mt VMA 的 maple tree 根（6.1 起取代 mmap 链表与 mm_rb 红黑树），按虚拟地址索引 vm_area_struct
pgd 页全局目录的物理基址，写进 CR3（x86）或 TTBR0_EL1（arm64）
mm_users 用户态使用者计数（线程数），归零说明地址空间没人用了
mm_count 内核态引用计数，active_mm 借用会 +1
total_vm / locked_vm 已映射页数 / 已锁定页数（mlock）
start_code / end_code / start_data / … 各段的边界，/proc/pid/maps 的底稿
arg_start / arg_end / env_start / env_end 参数与环境变量区，ps 显示命令行靠它
mmap_lock 保护 VMA 树的读写信号量，旧名 mmap_sem
context 体系结构相关的 mm_context_t，装 ASID、页表基址等

mm_users 与 mm_count 的双计数是内核里少见的「故意复杂」，原因值得记住：内核线程借用 active_mm 但不需要用户态还活着，所以两个计数必须分开——一个管「地址空间还有没有用户」，一个管「还有没有人引用这块结构」。

3.3 inode：三个不同生命周期的对象 #

初学者最容易把 inode、dentry、file 混成一个东西。它们其实是同一个文件在三个不同维度上的投影，生命周期各不相同：

结构 代表什么 生命周期 归谁管
inode 磁盘上的一个文件实体（元数据 + 数据块位置） 与文件同寿，但内存里可以缓存也可以回收 super_block 的 inode 链表 + LRU
dentry 路径中的一节（名字 → inode 的映射） 由 dcache 缓存，可随时回收重建 fs/dcache.c
file 一次 open() 的实例，带偏移量和打开模式 从 open 到 close 进程的 files_struct

inode 的关键成员：

c
struct inode {
    umode_t   i_mode;        /* 类型 + 权限位 */
    kuid_t    i_uid;
    kgid_t    i_gid;
    unsigned long i_ino;     /* inode 号，文件系统内唯一 */
    loff_t    i_size;        /* 字节大小 */
    struct super_block *i_sb;
    struct address_space *i_mapping;   /* 页缓存入口 */
    const struct inode_operations *i_op;
    const struct file_operations  *i_fop;
    union {
        struct block_device *i_bdev;   /* 块设备节点 */
        struct cdev         *i_cdev;   /* 字符设备节点 */
    };
};

两个实操结论：ls -i 看到的数字就是 i_ino，硬链接之所以「共享内容」，是因为两个 dentry 指向同一个 inode；而 df -i 报警（inode 耗尽）和磁盘满（块耗尽）是两回事，因为 inode 与数据块是分开分配的。

把 task_struct 当起点，向左走是文件，向下走是内存：

text
  task_struct
   ├── mm ──────────► mm_struct ──► maple tree ──► vm_area_struct ──► page table ──► struct page
   │                                                                      │
   │                                                                      └──► 物理页（可被 page cache 复用）
   │
   └── files ───────► files_struct ──► fdtable ──► fd_array[fd] ──► struct file
                                                                        │
                                        ┌───────────────────────────────┤
                                        │                               │
                                    f_path.dentry                  f_inode
                                        │                               │
                                        v                               v

                                     (d_name)                         │

注意 file 同时挂着 dentry 和 inode：dentry 决定「这个文件叫什么名字、在哪个目录」，inode 决定「内容在哪、多大、谁能读」。rename 只换 dentry 不动 inode，chmod 只改 inode 不动 dentry——理解了这条，就理解了 VFS 为什么要把它们拆开。

3.5 CFS：让每个进程都觉得自己独占 CPU #

调度器是 task_struct 里 sched_class 指向的那套策略。2.6.23 引入的 CFS（完全公平调度器）彻底替换了 O(1) 调度器，核心思想一句话：不按优先级分时间片，而是按权重分「虚拟运行时间」。

每个可运行任务维护一个 vruntime，每跑一次就按权重累加：

text
vruntime += delta_exec * (NICE_0_LOAD / weight)

NICE_0_LOAD 是 nice=0 时的基准权重（1024）。权重越大，分母越大，vruntime 涨得越慢；调度器永远挑 vruntime 最小的那个跑，于是高权重进程自然分到更多 CPU。

nice 权重 相对 nice=0 的 CPU 份额
-20 88761 约 86.7 倍
-10 9548 约 9.3 倍
0 1024 1 倍
10 110 约 0.107 倍
19 15 约 0.0146 倍

就绪队列 cfs_rq 是一棵以 vruntime 为键的红黑树，最左节点 rb_leftmost 就是下一个该跑的任务——取是 O(1)，插入和删除是 O(log n)。每个 task_struct 里的 struct sched_entity se 就是它在树上的节点。

c
struct sched_entity {
    struct load_weight load;        /* 由 nice 映射来的权重 */
    struct rb_node     run_node;    /* 挂在 cfs_rq 红黑树上 */
    unsigned int       on_rq;
    u64                exec_start;
    u64                sum_exec_runtime;
    u64                vruntime;    /* 排序键 */
    u64                prev_sum_exec_runtime;
};

一处必须标注的版本变化：6.6 起，SCHED_NORMAL 的实现从 CFS 换成了 EEVDF（Earliest Eligible Virtual Deadline First）。fair_sched_class 这个名字还在，struct sched_entity 也还在，但排序键从单纯的 vruntime 变成「合格时间 + 虚拟截止期」，并引入了 slice（请求的时间片长度）。所以本节的公式适用于 6.6 之前；6.6 之后请把 vruntime 理解为「虚拟时间轴」，不要再假定「最左节点就是下一个」。算法细节见 CFS 调度类：源码、组调度与带宽控制。

实时任务（SCHED_FIFO、SCHED_RR）走另一套 rt_sched_class，优先级 0–99 严格高于任何 fair 任务；只有 SCHED_DEADLINE 能压过 RT。这就是为什么一个死循环的 SCHED_FIFO 线程能把系统卡住——它不需要「更多 CPU」，它直接不把 CPU 让出来。

四、源码树目录地图 #

4.1 顶层目录逐条 #

内核树顶层三十来个目录，按性质分四类：与体系结构强相关、子系统实现、基础设施库、构建与文档。逐条职责如下，右列给出它与第二章五大子系统的对应关系：

目录 职责 对应子系统

4.2 按问题定位，比按目录背更快 #

真到改代码时，没有人会从头背目录表。更实用的是这张「问题 → 目录」的反查表：

最后一条最容易踩坑：内核内部头文件不能直接给用户态用。include/linux/ 里的定义会随版本变，只有 include/uapi/（以及 arch/*/include/uapi/）下的才是稳定 ABI。驱动里 #include <linux/xxx.h>，用户态程序 #include <linux/xxx.h> 拿到的是 /usr/include/linux/xxx.h，那是 headers_install 从 uapi 里抽出来的另一份拷贝。

4.3 arch/x86 与 arch/arm64 的差异 #

同一份内核代码，两个架构目录的布局逻辑是一样的：kernel/、mm/、include/asm/、boot/。差别在具体内容：

维度 arch/x86/ arch/arm64/
启动汇编入口 arch/x86/boot/（16 位实模式 stub）+ kernel/head_64.S arch/arm64/kernel/head.S（primary_entry）
内核映像基址 __START_KERNEL_map = 0xffffffff80000000 线性映射区 PAGE_OFFSET = 0xffff000000000000（48 位 VA）
用户态陷入指令 int $0x80（32 位兼容）、syscall（64 位） svc #0
系统调用号表 arch/x86/entry/syscalls/syscall_64.tbl（还有 _32.tbl、x32.tbl） include/uapi/asm-generic/unistd.h（通用表）
硬件描述 ACPI 为主，可叠加 DT 只有 DT，没有 ACPI 的板级路径
中断控制器 APIC / IOAPIC / MSI，arch/x86/kernel/apic/ GIC（v2/v3/v4），drivers/irqchip/irq-gic*.c
页表级数 4 级或 5 级（CONFIG_X86_5LEVEL） 3/4/5 级，由 VA_BITS 决定
板级描述残留 arch/x86/platform/ 少量 arch/arm/mach-* 已大批删除

这张表最有用的一行是「系统调用号表」：它解释了为什么同一个 read 在 x86_64 上是 0 号，在 arm64 上是 63 号——两套号表根本不是同一张。写跨架构代码时，永远用 __NR_xxx 宏，不要硬编码数字。

五、从加电到 start_kernel #

这一章只讲 x86 的一条主线，因为它的每一级台阶都能在源码里指到具体文件。ARM64 的对应路径在 ARM64 内核启动与页表建立，本节末尾只列出差异。

5.1 全景：五个阶段，四个「谁」 #

内核不是自己跳起来的，它是被别人一级一级搬起来、交接过来的。搞混了「谁负责哪一步」，后面所有的汇编都看不懂。

阶段 谁在执行 地址形态 结束时的状态
① 上电自检 固件（BIOS/UEFI） 实模式 16 位，1MB 寻址 选定启动设备，读第一个扇区
② 引导装载 bootloader（GRUB 等） 实模式 → 由 bootloader 自行切保护模式 内核映像进内存，boot_params 填好，跳 bzImage 入口
③ 引导 stub arch/x86/boot/ 16 位实模式起步 探测内存与显示，装好页表，进保护模式
④ 解压 arch/x86/boot/compressed/ 32/64 位保护模式，恒等映射 解出 vmlinux 到 LOAD_PHYSICAL_ADDR，跳 startup_64
⑤ 内核 C 入口 arch/x86/kernel/head_64.S → init/main.c 64 位，__START_KERNEL_map 映射就绪 执行 start_kernel()

5.2 ③ 引导 stub：实模式里最后一公里 #

arch/x86/boot/header.S 的前 512 字节是一个合法的 MBR 引导扇区（末尾 0x55AA），这就是老资料里 bootsect.S 的后代。它只做几件事：把自己从 0x7C00 挪到别处，把 setup 部分读进来，然后跳到 arch/x86/boot/main.c 的 main()。

main() 里全是「在实模式能做的事」，每一条都对应一个老问题：

步骤 函数 解决什么问题
探测低端内存 detect_memory() 用 int 0x15, eax=0xE820 拿到物理内存布局，存进 boot_params.e820_table
探测显示模式 set_video() 决定 earlyprintk 能往哪写、控制台用什么分辨率
准备启动参数 copy_boot_params()、parse_elf() 把 bootloader 传的 boot_params 搬进安全位置，记下内核各段
切保护模式 go_to_protected_mode() 建临时 GDT/IDT，开 CR0.PE，长跳转

切保护模式那一步是全篇最经典的几行汇编，动手前要开 A20 并关掉 NMI，否则现代的南桥会在切换瞬间给你一个惊喜：

c
/* arch/x86/boot/pm.c 的核心动作（简化） */
enable_a20();                    /* 打开第 21 根地址线，否则只能访问 1MB */
mask_nmi();                      /* 切换期间必须屏蔽 NMI */
setup_idt();                     /* 临时 IDT，任何异常都跳到同一个处理函数 */
setup_gdt();                     /* 临时 GDT，含 __BOOT_CS / __BOOT_DS 两个选择子 */
protected_mode_jump(boot_params.hdr.code32_start, (u32)&boot_params + (ds() << 4));

protected_mode_jump 内部把 CR0.PE 置 1 后，紧接一条长跳转刷新流水线——这行不加，CPU 会继续按实模式译码接下来的指令，行为完全不可预测：

armasm
    movl    %cr0, %eax
    orb     $1, %al            /* CR0.PE = 1，进入保护模式 */
    movl    %eax, %cr0
    ljmpl   *(in_pm32)      /* 远跳转进 32 位段，刷新 CS 与流水线 */

注意 A20 这条线：8086 时代地址线只有 20 根，绕回 1MB 是「兼容特性」；保护模式要访问 1MB 以上，必须先打开 A20。今天的机器上 A20 基本恒开，但代码里 enable_a20() 仍然保留，因为它要走一遍 0x92 端口或 BIOS int 0x15, ax=0x2401。

5.3 ④ 解压：内核为什么是个「压缩包」 #

bzImage 里的 vmlinux 是压缩的（gzip/xz/zstd/lz4/lzo，由 CONFIG_KERNEL_* 决定）。压缩不是为了省那几十兆，是因为大内核无法从传统启动方式里原地展开：解压目标地址和压缩源地址会重叠，只能靠一段位置无关的小代码来搬。

arch/x86/boot/compressed/head_64.S（32 位内核走 head_32.S）做三件事：

  1. 建恒等映射的临时页表——虚拟地址等于物理地址，只为让 64 位代码能跑起来；
  2. 调用解压器（extract_kernel()，在 misc.c 里），把 vmlinux.bin 解到 LOAD_PHYSICAL_ADDR（默认 0x1000000，即 16MB）；
  3. 跳转到解压后的 startup_64。

KASLR 打开时（CONFIG_RANDOMIZE_BASE），第 2 步的落点会被随机化，内核在 choose_random_location() 里从设备树或 e820 的空洞里挑一块可用内存。这是「同一台机器每次启动内核地址不同」的来源，也是为什么调试时需要 nokaslr。

5.4 ⑤ startup_64：最后一副页表 #

这一段常被老资料写错，因为它和 32 位内核的做法完全不同。x86_64 上不存在 0xC0000000 这个映射点，内核跑在 __START_KERNEL_map = 0xffffffff80000000 开始的 512MB 里。

步骤 位置 做了什么
startup_64 arch/x86/kernel/head_64.S 计算重定位偏移（__START_KERNEL_map 与实际装载地址之差），修 R_X86_64_32S 类重定位
__startup_64 arch/x86/kernel/head64.c 造 early_top_pgt：__START_KERNEL_map 映到物理 0，同时建立 PAGE_OFFSET 线性映射区
切栈 head_64.S 把 initial_stack 装进 rsp，之后才能调用 C 函数
x86_64_start_kernel arch/x86/kernel/head64.c 清 .bss、拷 boot_params、调 x86_64_start_reservations
start_kernel init/main.c 进入体系无关的 C 世界

「造页表」这个词在这里有个容易被忽略的细节：这份页表是恒等映射加线性映射的组合，只为启动服务。真正的 mem_map、vmalloc 区、fixmap 要等 setup_arch() 里的 init_mem_mapping() 才建立，所以早期启动代码必须自己保证访问的地址在已映射范围内——这也是「启动早期为什么不能用 printk 打太多东西」的技术原因之一。

5.5 start_kernel() 主链 #

init/main.c 的 start_kernel() 是全内核最长的一个函数，几百行全是「初始化某个子系统」。不必背，但要认出顺序里的因果：后面的调用依赖前面建立的设施。

顺序 调用 建了什么 后面谁依赖它
1 set_task_stack_end_magic() 栈底写 STACK_END_MAGIC 栈溢出检测
2 smp_setup_processor_id() 确定当前 CPU 号 所有 per-CPU 访问
3 setup_arch(&command_line) 解析 DT/ACPI、e820、内存布局、init_mem_mapping() 几乎所有后续步骤
4 setup_log_buf() printk 环形缓冲区 后续所有打印
5 setup_command_line()、parse_early_param() 命令行解析框架 驱动与子系统取参数
6 mm_core_init()（旧名 mm_init()） 页分配器、Slab、vmalloc 一切内存分配
7 sched_init() 各 CPU 的 rq、0 号进程（swapper） 进程创建与切换
8 trap_init()、init_IRQ() 异常向量、IDT、中断控制器 中断与系统调用
9 time_init()、tick_init() 时钟源与 tick 设备 定时器、调度器 tick
10 console_init() 控制台，之前攒的 printk 一次性刷出 用户可见的启动日志
11 arch_call_rest_init() 创建 kernel_init（PID 1）与 kthreadd（PID 2） 用户空间

console_init() 是全篇最值得记的一个位置：它之前的所有 printk 都只是写进环形缓冲区，不输出到屏幕。所以「内核启动前几秒没有任何输出」不是卡住了，是控制台还没注册。调试早期启动要靠 earlyprintk（直接往 UART 写），而不是 printk。

arch_call_rest_init() 之后控制权就交给了 kernel_init：它先 do_basic_setup() 跑完所有 __initcall，再 prepare_namespace() 挂根文件系统，最后 execve 到 /sbin/init 变成 1 号进程。从这一刻起，内核退居幕后，只在系统调用和中断里露面。

5.6 ARM64 只要记四行差异 #

项目 x86_64 arm64
入口 arch/x86/kernel/head_64.S 的 startup_64 arch/arm64/kernel/head.S 的 primary_entry
启动参数 boot_params 结构，选填 x0 = DTB 物理地址，必需
页表 early_top_pgt，分阶段反复重建 按 TCR_EL1.TnSZ 与 VA_BITS 一次性建好 swapper_pg_dir
进 C 的跳板 x86_64_start_kernel __primary_switch → start_kernel

arm64 没有实模式，也没有「解压」这一步的架构意义——内核直接从 primary_entry 开始，前提是 MMU 已经配好且 bootloader 保证 CPU 处于 EL2 或 EL1。页表的建立细节（create_idmap、__create_page_tables）见 ARM64 内核启动与页表建立，地址翻译规则与宏定义见 ARM64 地址翻译与页表宏定义。

六、系统调用入口 #

6.1 三种陷入方式，一条分水岭 #

用户态不能直接干活，只能「请求」。请求的方式随架构和年代变化：

方式 指令 架构 入口机制 现状
中断门 int $0x80 i386 / x86_64 兼容 查 IDT 第 0x80 项 仍保留，供 32 位程序用，慢
快速系统调用 sysenter / sysexit 32 位 x86（Intel） MSR IA32_SYSENTER_CS/EIP/ESP 已少用
快速系统调用 syscall / sysret x86_64（AMD 引入） MSR IA32_LSTAR / IA32_STAR x86_64 的默认路径
异常指令 svc #0 arm64 VBAR_EL1 的同步异常向量 arm64 唯一路径
异常指令 swi / svc arm32 向量表 0x08 老平台

分水岭是 syscall 指令的引入：它不再查 IDT，而是由 CPU 直接从 MSR 里取目标 RIP 与段基址，省掉一次内存查表和一次门切换。这也是 5.3 那节说 int $0x80「慢」的量化依据。

6.2 号表怎么挂上去 #

系统调用号本身只是一个整数，真正把它映射到函数的是 sys_call_table——一个函数指针数组。它在现代内核里是生成的，不是手写的：

text
arch/x86/entry/syscalls/syscall_64.tbl       ← 人写的号表（每行：号  ABI  名字  入口）
        │  scripts/syscalltbl.sh + 构建规则
        ▼
arch/x86/include/generated/asm/syscalls_64.h → __SYSCALL(nr, sym) 展开成表项
        │
        ▼
arch/x86/entry/syscall_64.c   const sys_call_ptr_t sys_call_table[] = { ... }

号表文件里的一行长这样，common 表示多个 ABI（64 位、x32、ia32）共用同一个实现：

text
0	common	read			sys_read
1	common	write			sys_write
59	common	execve			sys_execve

而 sys_write 这个名字是宏变出来的。写 SYSCALL_DEFINE3(write, unsigned int, fd, const char __user *, buf, size_t, count)，展开后同时得到：一个 __x64_sys_write 形式的真实符号、一组供 strace / seccomp / ftrace 使用的元数据、以及参数类型检查。这也是为什么加一个系统调用必须同时改 .tbl 和实现文件，只写函数不会自动被调用到。

6.3 一次 write() 的完整穿行 #

以 glibc 的 write(fd, buf, 5) 为例，八步到底：

步 层 动作 关键寄存器/结构
1 用户态 glibc 把 __NR_write（x86_64 上是 1）装进 rax，参数进 rdi/rsi/rdx rax = 1
2 硬件 执行 syscall，CPU 从 IA32_LSTAR 取 entry_SYSCALL_64，CS/SS 切到内核态 rcx 存返回地址，r11 存 rflags
3 汇编入口 entry_SYSCALL_64 建 pt_regs，保存通用寄存器，切内核栈 struct pt_regs
4 汇编入口 校验 rax：≥ NR_syscalls 则走 syscall_return_slowpath 返回 -ENOSYS __NR_syscall_max
5 分派 call sys_call_table(,%rax,8)，跳到 __x64_sys_write 表项 8 字节
6 C 实现 ksys_write → vfs_write：fdget_pos() 取 file，access_ok() 校验 buf files_struct、file
7 逻辑层 file->f_op->write_iter 多态分派到具体实现（ext4_file_write_iter 或 sock_write_iter） file_operations
8 返回 syscall_exit_to_user_mode 检查信号与重调度标志，sysretq 回用户态 rax = 返回值

第 5 步的 8 是 64 位表项宽度，不是 4。老资料里 sys_call_table(,%eax,4) 的写法来自 32 位内核，搬到 x86_64 上会算错一半的表项——这是本篇勘误表里的一条。

6.4 寄存器约定速查 #

写汇编或读 entry_64.S 时最需要的是这张表：

用途 x86_64（syscall） i386（int $0x80） arm64（svc #0）
系统调用号 rax eax x8
参数 1–6 rdi rsi rdx r10 r8 r9 ebx ecx edx esi edi ebp x0–x5
返回值 rax eax x0
被破坏的寄存器 rcx、r11 无特别约定 x0–x18
错误表示 负值（-ENOSYS） 同左 同左

注意 x86_64 用 r10 而不是 rcx 传第 4 个参数：因为 syscall 指令要用 rcx 存返回地址、r11 存 rflags。这是硬件强制的结果，不是设计偏好。

6.5 安全边界：三道检查 #

系统调用是用户态唯一能主动把数据送进内核的地方，所以入口之后必须过三道关：

  1. 地址合法性：access_ok(VERIFY_READ, buf, count) 保证区间落在用户地址空间内（x86_64 上是低于 TASK_SIZE_MAX）。不做这一步，用户传 0xffffffff81000000 就能让内核替它读内核数据。
  2. 拷贝守卫：真正的 copy_from_user / copy_to_user 在 access_ok 之上还会走 stac/clac（配合 SMAP）或 uaccess_begin/end（arm64 清 PAN），拷贝完立刻恢复。
  3. 指针来源校验：__user 标注的指针在 sparse 检查下不能直接解引用，必须走 get_user/put_user 系列。开着 CONFIG_DEBUG_STRICT_USER_COPY_CHECKS 时会报出越界大小。

这三道关不是可选的加固，是内核能不被用户态玩坏的前提。读驱动代码时看到有人直接 memcpy(dst, user_ptr, n) 而不经 copy_from_user，那是 bug，不是风格问题。

七、中断下半部 #

7.1 边界：上半部只做「必须立刻做」的事 #

硬中断到达时，CPU 会关中断（至少关本级），此时任何拖延都是系统级延迟。所以处理被切成两段，分界线是一条硬规则：

上半部（top half / 硬中断） 下半部（bottom half）
触发时机 硬件中断立刻进入 稍后，由内核在合适时点调度
中断状态 当前 CPU 关中断（至少关本级与同级） 开中断
能否睡眠 绝对不能 softirq/tasklet 不能；workqueue 能
典型动作 读状态寄存器、清中断标志、ack 中断控制器、把数据搬走或标记 协议栈解析、块 I/O 完成回调、唤醒等待队列
耗时预算 微秒级，越短越好 可以到毫秒级
是否可被抢占 不能 softirq 不可，workqueue 可

写成骨架就是 request_irq 注册的那个函数必须极短，剩下的活必须扔出去。判断标准很实在：任何可能睡眠的调用（kmalloc(GFP_KERNEL)、mutex_lock、copy_to_user、msleep）都只能出现在下半部，而且是 workqueue 那一种下半部。

现代内核里 tasklet 已经不被推荐：它和 PREEMPT_RT 补丁冲突（RT 把软中断全部线程化，tasklet 语义会变），新代码更倾向直接用 workqueue 或线程化中断。看到老驱动里的 DECLARE_TASKLET 不必改，但别在新代码里学它。

线程化中断值得单独说一句：它在 request_threaded_irq() 里把 handler（上半部，快速 ack）和 thread_fn（下半部，跑在 irq/N-name 线程）分开。这样下半部既享受进程上下文的睡眠能力，又享有实时优先级，还不用自己管队列。I2C、SPI 这类慢速总线驱动现在基本都用它。

八、读内核源码必备的惯用法 #

这一章不是新知识，是眼镜。下面五种写法在源码里遍地都是，认不出来就会以为是笔误，甚至照抄进自己的代码。它们有个共同点：都靠「0」或「编译期」做文章。

8.1 0 长数组与柔性数组成员 #

需求很朴素：一个结构体后面跟一段长度在运行期才确定的数据。两种写法，语义一样，标准地位不同。

c
/* 写法 A：GNU C 扩展，零长数组 */
struct line_a {
    int  length;
    char contents[0];       /* GNU 扩展，C89 之外的方言 */
};

/* 写法 B：C99 柔性数组成员，内核现在推荐 */
struct line_b {
    int  length;
    char contents[];        /* C99 标准，必须放最后 */
};
对比项 char contents[0]（GNU 扩展） char contents[]（C99 FAM）
标准依据 GCC 扩展，非 ISO C C99 §6.7.2.1 柔性数组成员
sizeof 不计入，sizeof(struct line_a) == 4 不计入，同样为 4
位置约束 必须在末尾（编译器只警告，不强制） 标准强制：必须是最后一个成员
合法性检查 编译器不检查「后面还有成员」这种错误 有的编译器会直接报错
是否可取地址/自增 沿用老语义，容易误用 语义更严格
内核态度 已列为待淘汰 推荐

内核的 Documentation/process/deprecated.rst 里专门有一节讲「零长数组与单元素数组」，把它们列为应当避免的写法，理由是新编译器（尤其开 -fstrict-flex-arrays=3 后）对越界访问的检查会失效，FAM 能配合 __counted_by 做运行期边界检查。这是本篇对素材 3 的第一条勘误：原文只讲了 [0] 这一种写法，且称之为「推荐用法」；在今天的内核里它已经是被点名淘汰的写法。

两种写法在分配上是同一套：先算总字节数，一次分配，再填长度。手写 sizeof(struct line) + n 有整数溢出风险，内核提供了宏：

c
struct line_b *p = kmalloc(struct_size(p, contents, n), GFP_KERNEL);
if (!p)
    return -ENOMEM;
p->length = n;              /* struct_size() 在 include/linux/overflow.h */

struct_size(p, member, count) 展开成 sizeof(*p) + count * sizeof(p->member[0]) 并带溢出检查（走 __must_check_overflow）。用户态对应的是 malloc(sizeof(struct line_b) + n)，但用户态没有 struct_size，得自己判 n > SIZE_MAX - sizeof(...)。

8.2 offsetof 与 container_of：从成员倒推宿主 #

offsetof 算的是「成员在结构体内的字节偏移」，写法看着吓人：

c
#define offsetof(TYPE, MEMBER) ((size_t)&((TYPE *)0)->MEMBER)

把 TYPE 的地址当成 0，那么成员的地址就是它的偏移。这段代码在 include/linux/stddef.h 里，现代版本已经改成直接用编译器内建：__builtin_offsetof(TYPE, MEMBER)，结果一样但是编译期常量、不依赖「假装有对象」。

这里必须纠正一个流传很广的误解：素材 3 说「宏里访问 0 地址不报错，是因为内核把 0 地址设为只读」。不对。&((TYPE *)0)->MEMBER 只做取地址，不产生任何内存读取，编译器在编译期就把它折叠成常量；就算 0 地址可读可写，这个表达式也不会访问它。如果写成 ((TYPE *)0)->MEMBER（不取址，取值），那才必然出错。

container_of 是它的逆运算，也是内核里出现频率最高的宏之一：

c
#define container_of(ptr, type, member) ({                      \
    void *__mptr = (void *)(ptr);                               \
    ((type *)(__mptr - offsetof(type, member))); })

({ ... }) 是 GNU 语句表达式：最后一句的值就是整个表达式的值。所以 container_of 可以当右值用：

c
/* 从 list_head 找回宿主结构 */
struct my_dev *d = container_of(pos, struct my_dev, list);

/* 从 work_struct 反推宿主，这是 workqueue 回调里的标准动作 */
static void my_work_fn(struct work_struct *work)
{
    struct my_dev *d = container_of(work, struct my_dev, work);
    /* 之后才能访问 d->其它成员 */
}

list_entry、rb_entry、hlist_entry、netdev_priv、dev_get_drvdata 全是它的马甲。认出这一层，list_for_each_entry(pos, head, member) 这类宏就突然能读了——它在循环体里做的就是一次 container_of。

宏 作用 常见使用场景
offsetof(type, m) 成员相对结构体首地址的偏移 手写序列化、调试打印结构布局
container_of(p, type, m) 由成员指针反推宿主指针 所有「挂进通用链表/工作队列」的回调
list_entry(p, type, m) container_of 的链表别名 list_for_each_entry 内部

8.3 do {} while (0)：宏的万能壳 #

内核里几乎每个多语句宏都长这样：

c
#define SET_FLAG(dev) do {          \
    (dev)->flags |= F_READY;        \
    smp_wmb();                      \
} while (0)

为什么不能直接写 { ... } 或者裸语句？因为宏是文本替换，替换后会掉进两个坑：

c
/* 坑 1：裸语句 + if 不带大括号 → 第二条语句逃出 if */
if (ok)
    SET_FLAG(dev);      /* 展开后 do_this(); do_that(); 只有第一条在 if 里 */

/* 坑 2：用 { } 包裹 + if/else → 分号把 else 顶走 */
if (ok)
    SET_FLAG(dev);      /* 展开成 { ... }; 于是 else 找不到 if */
else
    retry();

do { ... } while (0) 一次性解决两个问题：整体是一条语句（if/else 安全），且以分号结束的写法天然合法（调用方照常写 SET_FLAG(dev);）。

写法 if 不带大括号时 if/else 时 调用方加分号 能否 break 跳出
裸语句（无包裹） 只有第一条受控 ✗ 正常 — —
{ ... } 整体受控 ✓ 分号导致问题 ✗ 不自然 可（跳出这个块）
do { ... } while (0) 整体受控 ✓ 正常 ✓ 正常 ✓ 可（跳出宏体）

三条使用限制，都是踩出来的：

  1. 宏里的 return 会从调用者返回。有些宏（如 BUG_ON 系列）故意利用这一点，但普通功能宏这么写就是陷阱。
  2. 宏里不要用 break 表达「跳过剩余语句」以外的语义——它会直接结束 while(0)，看起来像正常但读者要愣一下，用 if/else 更清楚。
  3. 参数带副作用时要小心：#define SQ(x) ((x)*(x)) 在 SQ(i++) 上会自增两次。这不是 do{}while(0) 的问题，但两者经常一起出现在同一份老代码里。

顺带一个判断：如果宏只有一条表达式，内核风格是加括号而不加 do/while，例如 #define GET_FLAG(d) ((d)->flags & F_READY)。看到 do{}while(0) 就知道里面一定是多条语句。

8.4 用 0 触发 panic，再用 0 定位它 #

内核 oops 的 Code: 行会给出一串机器码，其中用尖括号 < > 标出的那一条就是出错指令：

text
Call Trace:
[<c0406081>] show_trace_log_lvl+0x1a/0x2f
Code:
e3 a0 20 01 <e5> 83 20 00 f5 7f f0 4e e3 a0 30 00 e5 c3 20 00

有 vmlinux 时最省事：gdb vmlinux 之后 b *(0xc0406081 + 0x1a)，或者直接 x/4i 0xc0406081+0x1a 看反汇编。

没有 vmlinux 时（客户现场常见），内核自带脚本就是干这个的：把 Code: 那一行抄进文件，跑

bash
./scripts/decodecode < ~/oops.txt

它内部会拼一段汇编、调 objdump 反汇编，再把 < > 标记的那条指令指出来。需要 objdump 且架构对得上（ARM 内核要用 ARM 的 objdump）。注意素材 3 写的是 .scripts/decodecode——少了一个目录斜杠，照抄会报「no such file」。

素材 3 里那个 const char array[] = ...; *(int *)0 = 0; 的小程序，作用是制造一个段错误让 gdb 停在能打印数组地址的那一刻：先 printf 出机器码数组的地址，再故意写 0 地址触发 SIGSEGV，于是在 gdb 里 x/8i 那个地址就能看到对应的反汇编。它本身不「定位」任何东西，只是个取址技巧。用的时候数组要加 volatile，否则 -O2 可能把它整个优化掉。

*(int *)0 = 0 为什么崩、而 offsetof 里的 0 指针不崩，原因在 8.2 已经说过：一个是写，一个是取址。这条区别是整个「0 的巧妙用法」系列的地基。

8.5 乘除法与移位：误差藏在顺序里 #

时间子系统、网络带宽换算、定点标定里到处是 x * mult >> shift。为什么不直接 x * a / b？两个原因：整数除法在多数架构上是几十个周期的慢指令，而移位是一条指令；更重要的是内核里不能有浮点（内核态用 FPU 要手动保存现场，代价大且容易出错），只能用整数近似。

误差从哪来？先看一组数：

text
10 * 12 / 8 = 15        先乘后除，精确
10 / 8 * 12 = 12        先除后乘，(10/8)=1 丢掉 0.25，误差被 12 放大成 3

结论一：先乘后除，误差只丢一次且不放大；先除后乘，误差被乘数放大。

右移 >> shift 等价于「除以 2 的 shift 次方，向零截断」，所以 x * mult >> shift 的误差上限是 1 个输出单位，相对精度约 2^-shift。这里要纠素材 4 的一句表述：它说「shift 是 10 就只能精确到十位」——把二进制位当成了十进制位。右移 10 位丢的是 10 个二进制位，相对误差约 1/1024 ≈ 0.1%，不是「精确到十位」。

结论二：mult 越大、shift 相应越大，近似越精确，但 x * mult 不能溢出。这就是内核里 mult 与 shift 成对出现、且 mult 通常取到「不溢出前提下的最大值」的原因：

约束 后果 内核里的处理
mult 太小 精度差，抖动明显 用 clocks_calc_mult_shift() 自动挑最优 mult/shift
shift 太小 精度差 同上，权衡后取满足溢出约束的最大 shift
x * mult 溢出 结果完全错误，且不报错 64 位乘 mul_u64_u32_shr()，或先转 u64
输入 x 本身很大 溢出边界被压缩 分段处理，或改用 div64_u64() 精算

几条实操规则，写驱动和时间换算时直接用：

需求 写法 说明
除以常数、能整除的 2 的幂 x >> n 编译器本来也会优化，但显式写更明确
定点乘除 (u64)x * mult >> shift 强制 64 位再乘，别让 32 位中间结果截断
需要余数 do_div(n, base) 原地修改 n 并返回余数，一条指令级实现
64 位除 64 位 div64_u64(a, b) 32 位架构上没有硬件 64 位除法，走了软件路径
时间戳换算 clocksource_cyc2ns(cs, cyc) 别自己写 cyc * mult >> shift，多核下要防溢出

最后一条经验值得记住：内核里看到 >> shift，先问 shift 从哪来。如果是硬编码的常量，多半是有人算过溢出边界；如果来自 struct 字段（如 clocksource.mult/shift），那它一定是运行期标定出来的，不能假设具体值。

九、小结 #

  • 形态：Linux 是宏内核。选它不是因为它「更先进」，而是通用计算的瓶颈在吞吐，跨地址空间的 IPC 开销付不起。LKM 只解决发行与裁剪，不解决隔离与容错——模块崩了照样 panic。
  • 骨架：五大子系统（SCHED、MM、VFS、NET、IPC）按「管什么资源」切分，每个内部都是「系统调用接口 → 通用机制 → 体系结构相关 → 硬件」四层。看到函数名，先判断它在哪一层。
  • 对象：task_struct 是「谁在跑」，mm_struct 是「能看见哪片内存」，inode 是「文件是什么」，dentry 是「它叫什么名字」，file 是「这一次打开」。五个对象的生命周期各不相同，这是 VFS 设计的核心。
  • 调度：CFS 用权重分摊 vruntime，红黑树最左节点即下一个任务。6.6 起换成 EEVDF，键不再是纯 vruntime，读新内核时别套老公式。
  • 地图：arch/ 放体系相关，kernel/ 与 mm/ 放机制，fs/ 与 net/ 放子系统实现，drivers/ 占一半以上代码量。改代码按「问题 → 目录」反查，比背目录表快。
  • 启动：BIOS → bootloader → 实模式 stub → 解压 → startup_64 建早期页表 → start_kernel()。记住 console_init() 这条分界线：之前的 printk 都只在环形缓冲区里。
  • 系统调用：syscall（x86_64）或 svc #0（arm64）陷入，号表是构建时从 .tbl 生成的 sys_call_table，表项宽度等于指针宽度。入口之后必须过 access_ok 与 copy_*_user 两道关。
  • 下半部：判据只有一条——能不能睡眠。不能睡选 softirq/tasklet，能睡选 workqueue 或线程化中断。网络收包是 softirq 的教科书用法，慢速总线驱动是线程化中断的教科书用法。
  • 惯用法：[0] 长数组已被柔性数组成员取代；offsetof 不访存所以不崩；container_of 靠偏移反推宿主；do{}while(0) 保证宏是一条语句；* mult >> shift 的误差来自截断与溢出，不是精度不够。
  • 一条读码原则：先把「这个函数在哪个子系统、哪一层」搞清楚，再看它做什么。不懂层次的读码，最后只会记住一堆函数名。
