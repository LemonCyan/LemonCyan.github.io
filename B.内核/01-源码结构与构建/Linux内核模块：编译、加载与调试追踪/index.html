一、LKM 到底解决什么问题 #

内核是可执行代码，改一个字符就要重编、打包、重启。Linux 的出路是把驱动做成独立的 .ko，运行时挂进去。

1.1 整内核重编与模块热插拔的成本对比 #

环节 改内置驱动（=y） 改可加载模块（=m）
编译范围 至少重编该子系统，常触发全量链接 只编这一个目录
典型耗时 5 ~ 40 分钟 数秒
产物与生效 新 zImage，烧写并重启 一个 .ko，insmod 毫秒级
是否中断业务 是，所有进程重启 否，仅加载瞬间短暂停顿
调试迭代 每改一行重启一次板子 改、编、装卸，循环在十秒内
出错后果 板子起不来，拆机重烧 卸掉即恢复，最坏 Oops 重启

1.2 =y 还是 =m：判断表 #

判据 倾向 =y 倾向 =m
启动就必须可用 是（根文件系统所在存储、控制台、时钟） 否
卸载是否合理 不合理（卸了系统就崩） 合理（换设备再挂）
是否允许开源 是 否（闭源只能 =m）
板上有几种同类设备 只有一种 多种，按需挂
是否需要传参 不需要 需要（insmod x.ko param=1）
是否要现场热修 不需要 需要（直接替换 .ko）

一条硬约束容易被忽略：根文件系统所在的块设备驱动，以及它依赖的总线驱动，必须是 =y。做成模块的话内核挂根文件系统时无处去取 .ko，只能停在 VFS: Cannot open root device。

模块也不便宜。它跑在最高特权级：空指针不再是死一个进程而是 Oops 整机，越界写会踩坏别的子系统，栈溢出立即静默损坏，关抢占的自旋锁里死循环就是看门狗复位。这正是内核加载模块时要设三道校验关（第五章）的原因——放进去之后，再也没有中间层能拦住它。

二、最小可运行模块 #

内核模块没有 main()。用户态程序由 C 运行时调用 main，模块则由内核在 insmod 时调用你注册的初始化函数。

2.1 完整源码 #

c
#include <linux/init.h>      /* __init / __exit */
#include <linux/module.h>    /* module_init / module_exit / MODULE_* */
#include <linux/kernel.h>    /* printk 与 KERN_* */
#include <linux/jiffies.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("example");
MODULE_DESCRIPTION("Minimal loadable kernel module");
MODULE_VERSION("1.0.0");

static int __init hello_init(void)
{
    printk(KERN_INFO "hello: init, jiffies=%lu\n", jiffies);
    return 0;
}

static void __exit hello_exit(void)
{
    printk(KERN_INFO "hello: exit\n");
}

module_init(hello_init);
module_exit(hello_exit);

2.2 逐行解释 #

代码 作用 删掉会怎样
#include <linux/module.h> 引入 module_init、MODULE_LICENSE 与 struct module 声明 宏未定义，编译失败
MODULE_LICENSE("GPL") 写入 .modinfo 的 license=GPL 能加载，但标记 Tainted: G，且用不了 GPL-only 符号
MODULE_AUTHOR/DESCRIPTION/VERSION 写入 .modinfo，供 modinfo 读取 无影响，只是元数据缺失
__init 函数放进 .init.text，初始化后释放 代码常驻，白占几 KB
__exit 函数放进 .exit.text，=y 时整段丢弃 内置场景多留一段死代码
module_init(hello_init) 把函数指针填进 struct module 的 init 加载成功但什么都不执行，dmesg 无输出
module_exit(hello_exit) 填进 cleanup 卸载时无清理，资源泄漏
return 0 0 成功，负数为 -errno 返回非 0 时内核立刻回滚

module_init 展开后只是给函数打一个固定别名：

c
/* include/linux/module.h（简化） */
#define module_init(initfn)                                  \
    static inline initcall_t __maybe_unused __inittest(void) \
    { return initfn; }                                       \
    int init_module(void) __attribute__((alias(#initfn)));

模块的入口符号真实名字固定叫 init_module，内核正是按这个名字在符号表里找入口；module_exit 同理，别名是 cleanup_module。这也解释了为什么一个模块里不能有两个 module_init——那会产生两个 init_module 定义，链接期直接冲突。

2.3 __init 与 __exit 的段归宿 #

宏 段名 模块场景 内置（=y）场景
__init .init.text do_init_module() 成功后由 module_free() 释放 启动末尾由 free_initmem() 释放
__initdata .init.data 与 .init.text 一起释放 同左
__exit .exit.text 常驻，rmmod 时调用 编译期丢弃

一个常见混淆：释放模块 init 段的不是 free_initmem()。后者处理 vmlinux 自己的 .init.*；模块的 .init.text 是 vmalloc 出来的独立区域，由 do_init_module() 内部调用 module_free(mod, mod->module_init) 归还。

2.4 编译并加载的最短路径 #

bash
ls /lib/modules/$(uname -r)/build                          # 1. 头文件树存在
make -C /lib/modules/$(uname -r)/build M=$(pwd) modules    # 2. 编译
modinfo hello.ko                                           # 3. 看产物写了什么
sudo insmod hello.ko                                       # 4. 加载
dmesg | tail -n 3                                          # 5. 看 init 输出
lsmod | grep hello                                         # 6. 看模块状态
sudo rmmod hello && dmesg | tail -n 1                      # 7. 卸载

text
$ modinfo hello.ko
license:        GPL
description:    Minimal loadable kernel module
depends:
name:           hello
vermagic:       5.15.0-91-generic SMP mod_unload modversions

$ sudo insmod hello.ko && dmesg | tail -n 1
[ 4213.551820] hello: init, jiffies=4295123456

depends: 为空，说明不引用任何其他模块导出的符号。装载被拒时先看 lsmod 的 Used by 列（读自 /proc/modules），那里写着谁在引用你；引用计数非 0 时 rmmod 返回 -EBUSY。

三、Kbuild 与 Makefile #

模块不能直接 gcc hello.c -o hello.ko：内核代码依赖一整套由 .config 生成的宏、特定的编译选项（-march、-fno-pic、-mno-unaligned-access），还依赖内核树的头文件搜索路径。Kbuild 就是把这些一次性喂给编译器的外壳。

3.1 标准模块 Makefile 模板 #

makefile
# 要编译的模块对象；Kbuild 自动找同名 hello.c 生成 hello.o
obj-m += hello.o

# 当前运行内核的开发目录（含 Makefile 与 .config），可由命令行覆盖
KDIR ?= /lib/modules/$(shell uname -r)/build

# 模块源码目录，必须绝对路径
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

modules_install:
	$(MAKE) -C $(KDIR) M=$(PWD) modules_install
	depmod -a

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

3.2 各元素逐条解释 #

元素 含义 写错会怎样
obj-m += hello.o 声明 hello.o 是模块，最终链成 hello.ko 写成 obj-y 会试图链进内核镜像，构建期报错
KDIR ?= ... ?= 表示「未定义才赋值」，便于 make KDIR=... 覆盖 用 = 使外部覆盖失效；路径错则报找不到 Makefile
PWD := $(shell pwd) 编译时的绝对路径 用相对路径，-C 切目录后 M= 指错位置
all: 默认目标，必须站第一位 放到 clean 之后，直接 make 会执行 clean
$(MAKE) -C $(KDIR) 切到内核树执行其顶层 Makefile 写死 make 会断掉 -j 与 MAKEFLAGS 的传递
M=$(PWD) 告诉 Kbuild「只编这个外部目录」 漏掉就变成编整个内核
modules 内核树里的目标名，产出 .ko 写成 all 会走内核默认目标
modules_install 装到 /lib/modules/$(uname -r)/extra/ 再 depmod -a 不装也能 insmod，但 modprobe 找不到
clean 删 .ko/.o/.*.cmd/modules.order 手写 rm *.o 会漏掉隐藏的 .cmd

3.3 Kbuild 双向调用到底发生了什么 #

text
1. 当前目录输入 make → 命中 all
2. 执行 $(MAKE) -C $(KDIR) M=$(PWD) modules，切换到内核源码树
3. 内核顶层 Makefile 接管，读 .config / auto.conf / autoconf.h，
   初始化 CFLAGS、交叉编译前缀、架构选项
4. 见到 M=$(PWD)：本次任务是外部模块，不编内核本体
5. 回到模块目录，读它的 Makefile，解析 obj-m += hello.o
6. 用内核全套选项编译 hello.c → hello.o → hello.ko，
   同时生成 hello.mod.c 与 .modinfo 段

这套设计的价值是：模块自动继承内核树里的全部平台定义。交叉编译时把 KDIR 指向目标板的内核构建目录，再带上 ARCH 与 CROSS_COMPILE，就不用写任何 -march：

bash
make ARCH=arm CROSS_COMPILE=arm-linux-gnueabihf- \
     KDIR=/home/dev/kernel/linux-3.6.33 M=$(pwd) modules

漏掉 ARCH 是最典型的交叉编译事故：Kbuild 按宿主 x86 生成，e_machine 变成 62，拿到 ARM 板上必然 Invalid module format。

3.4 多文件模块 #

makefile
obj-m += mydrv.o
mydrv-objs := core.o irq.o sysfs.o

obj-m 里写的是链接后的模块名，不是任何源文件名。若同时存在 mydrv.c，Kbuild 会先按单文件编 mydrv.o 再按 -objs 链接，两条路径撞车，报 multiple definition。

四、模块参数与符号导出 #

写死配置是最脆的形态：换一块板子就要重编。参数机制让 insmod 时赋值，导出机制让模块之间互相调用。

4.1 module_param 与 sysfs 自动呈现 #

c
static int  baudrate = 9600;
static char *port_name = "ttyS0";

module_param(baudrate, int, 0644);
MODULE_PARM_DESC(baudrate, "Target serial baudrate (default 9600)");
module_param(port_name, charp, 0644);

bash
sudo insmod my_serial.ko baudrate=115200 port_name=ttyS1

cat /sys/module/my_serial/parameters/baudrate      # 115200
echo 9600 > /sys/module/my_serial/parameters/baudrate

第三个参数是 sysfs 权限位，同时决定「能不能改」和「谁来改」：

权限 sysfs 表现 典型用途
0444 只读 硬件能力、版本号这类不该变的量
0644 读写，仅 root 可写 运行期可调参数
0000 不出现在 sysfs 内部调试开关

类型名必须与变量类型严格对应，写错组合编译期就报错：

类型名 C 类型 解析函数
bool / invbool bool kstrtobool（invbool 语义取反）
int / uint / long / ulong 对应整型 kstrtoint / kstrtouint / kstrtol / kstrtoul
charp char * 分配后拷贝字符串

数组参数用 module_param_array，比标量多一个「实际传了几个」的出参 &nr_pins，由内核回填，超长报 -EINVAL。字符串数组在 5.10 之前不支持。

4.2 EXPORT_SYMBOL 与 EXPORT_SYMBOL_GPL #

模块里非 static 的函数虽然进了 .symtab，但那是模块私有符号表，别的模块看不见。要在模块之间互相调用，必须显式导出：

c
int bus_register_custom(struct custom_bus *bus) { return 0; }
EXPORT_SYMBOL_GPL(bus_register_custom);    /* 核心模块：交给别人用 */

extern int bus_register_custom(struct custom_bus *bus);  /* 子模块：声明后调用 */
宏 谁能用 闭源模块调用时
EXPORT_SYMBOL 任何模块 正常解析
EXPORT_SYMBOL_GPL 仅 GPL 或 GPL 兼容许可 拒载，返回 -EACCES
EXPORT_SYMBOL_GPL_FUTURE 同上，未来转强制 GPL 当前内核仅告警

拒绝时的日志容易误判：

text
hello: module license 'Proprietary' taints kernel.
hello: Unknown symbol bus_register_custom (err -2)

第二行看着像「符号不存在」，实际是「存在但你没资格用」。判据：grep -w bus_register_custom /proc/kallsyms 能搜到，就是许可问题而非依赖问题。

导出在二进制上的落点是两个段：__ksymtab 存 struct kernel_symbol 数组（新版用相对偏移 value_offset/name_offset，老版直接存指针），__ksymtab_strings 存符号名。加载器遍历这张表把偏移换算成绝对地址再登记。

4.3 符号表在 /proc/kallsyms 里的样子 #

text
$ grep -w "bus_register_custom" /proc/kallsyms
ffffffffc02b1000 t bus_register_custom      [custom_bus]
ffffffff8106e4d0 T printk
列 含义 用法
地址 内核地址空间中的绝对地址 全 0 说明 kptr_restrict 生效，需 root
类型 t/T 文本，d/D 数据，b/B bss，r/R 只读数据 大写全局，小写局部（static）
名字 符号名 可与 nm hello.ko 输出对照
模块名 方括号内，来自哪个 .ko 空表示属于 vmlinux 本体

t 与 T 之分是排查「导出了但别人看不见」的第一把尺子：模块里的 static 函数永远是 t，永远不会被别的模块解析到。

五、加载流程与三道关 #

insmod 只是用户态的一层薄壳，真正的工作全在 kernel/module.c 里。

5.1 命令对照 #

命令 解析依赖 查 modules.dep 输入 底层动作
insmod 否 否 .ko 路径 init_module / finit_module
rmmod 不适用 否 模块名 delete_module
modprobe 是，按序自动加载 是 模块名（不带 .ko） 内部循环调用 init_module
modinfo 不适用 否 .ko 或模块名 纯用户态解析 .modinfo
depmod -a 不适用 生成 modules.dep 无参 纯用户态扫描所有 .ko

modprobe 能算依赖，是因为 depmod 提前扫过所有 .ko：读 __ksymtab 得到「我导出什么」，读未定义符号得到「我引用什么」，两者做图写进 modules.dep。这就是新编的 .ko 必须先 depmod -a 才能被 modprobe 认出的原因。

5.2 load_module 的关键步骤 #

c
static int load_module(struct load_info *info, const char __user *uargs, int flags)
{
    /* 1. ELF 头部合法性：魔术、类别、字节序、e_type 必须是 ET_REL */
    err = elf_validity_check(info);
    /* 2. 解析段表，定位 .modinfo / __versions / 符号表 */
    err = setup_load_info(info, flags);
    /* 3. 第一道关：vermagic、模块名、许可检查 */
    err = check_modinfo(info->mod, info, flags);
    /* 4. vmalloc 分配可执行内存，把各段搬进去 */
    mod = layout_and_allocate(info, flags);
    /* 5. 解析未定义符号，填入内核符号地址 */
    err = simplify_symbols(info->sechdrs, info->secstrings, ...);
    /* 6. 重定位：把段内占位地址改写成真实地址 */
    err = apply_relocations(mod, info);
    /* 7. 第二道关：符号 CRC 校验（CONFIG_MODVERSIONS 时生效） */
    err = check_modinfo_version(...);
    /* 8. 建 sysfs 节点，挂入全局链表，跳进 init_module */
    err = mod_sysfs_setup(mod, info, mod->kp, mod->num_kp);
    return do_init_module(mod);
}

第 6、7 步失败都返回 -ENOEXEC，区分靠 dmesg 文本，不靠错误码。

5.3 vermagic 逐字段拆解 #

vermagic 是编译期写进 .modinfo 的一行 ASCII，加载时与运行内核的 VERMAGIC_STRING 做 strcmp：

text
vermagic: 3.6.33-fake SMP preempt mod_unload ARMv5
位置 值 来源宏 变了会怎样
第 1 段 3.6.33-fake UTS_RELEASE（含 EXTRAVERSION） 差一个后缀就拒载
第 2 段 SMP CONFIG_SMP 影响 per_cpu 偏移，单核模块装 SMP 内核必拒
第 3 段 preempt CONFIG_PREEMPT 改变 struct module 部分成员的排布
第 4 段 mod_unload CONFIG_MODULE_UNLOAD 决定 struct module 是否有 exit 成员
第 5 段 ARMv5 CONFIG_CPU_* 决定的 -march 指令集级别，ARMv4 模块装 ARMv5 内核被拒
可选段 modversions CONFIG_MODVERSIONS 出现即意味着还要过 CRC 关
可选段 retpoline CONFIG_RETPOLINE 与间接跳转 thunk 兼容性相关

五段的共同点是它们都会改变内核结构的布局，所以内核不敢放行——放行了就是拿错误偏移去写结构体。

5.4 CONFIG_MODVERSIONS 与符号 CRC #

vermagic 只管「同一版本 + 同一套开关」，管不到「同一个函数签名有没有变」：

环节 机制 产物
编译内核 scripts/genksyms 从 EXPORT_SYMBOL 函数的类型串算出 32 位 CRC __kcrctab 里的 crc_<sym>
编译模块 引用符号时记下 CRC __versions 里的 struct modversion_info 数组
加载校验 check_version() 逐个比名字、比 CRC 不匹配则拒载 
c
struct modversion_info {
    unsigned long crc;          /* 64 位上按 long 对齐，占 8 字节 */
    char name[MODULE_NAME_LEN]; /* 符号名，MODULE_NAME_LEN = 56 */
};

text
hello: disagrees about version of symbol printk
hello: Unknown symbol printk (err -13)

第一行说明内核有这个导出符号但 CRC 对不上；第二行的 -13 是 -EACCES。纯「找不到符号」报的则是 Unknown symbol foo (err -2)。-2 与 -13 之差，正好对应「没导出」与「CRC 不符」。

5.5 CPU 架构与 ABI 校验 #

这只在 elf_validity_check 阶段完成，比 vermagic 更早：

字段 偏移 合法值 不匹配表现
e_ident[0..3] 0x00 7F 45 4C 46 Invalid module format，段表都不解析
e_ident[EI_CLASS] 0x04 1 = 32 位，2 = 64 位 32 位模块装 64 位内核直接拒
e_ident[EI_DATA] 0x05 1 = 小端，2 = 大端 大小端不符，段表全乱
e_type 0x10 必须为 1（ET_REL） 用了可执行文件或共享库
e_machine 0x12 40 = ARM，183 = AArch64，62 = x86-64 架构不符，拒载

注意 AArch64 是 183（EM_AARCH64），62 是 EM_X86_64。把 62 硬改成 183 能骗过头部校验，但 apply_relocations 会按 R_AARCH64_* 解释 R_ARM_* 项，出来是乱码指令，必然 Oops。

5.6 一整套 Invalid module format 的定位顺序 #

这个报错是 -ENOEXEC 的统一文案，返回值里不告诉你哪一关没过。先看内核自己怎么说：

bash
dmesg | tail -n 5
dmesg 关键词 卡在哪一关 下一步
version magic 'A' should be 'B' vermagic 逐字段比对 A 与 B，见 5.3
disagrees about version of symbol X 符号 CRC 查是否开了 CONFIG_MODVERSIONS，比对 CRC
Unknown symbol X (err -2) 未导出/依赖未加载 grep -w X /proc/kallsyms；改用 modprobe
Unknown symbol X (err -13) GPL-only 符号 改 MODULE_LICENSE 或换接口
Exec format error / 无日志 ELF 类别、架构，或文件权限 readelf -h、ls -l、id 
bash
modinfo hello.ko | grep -E "vermagic|name|license|depends"   # 模块自己声明的
uname -r                                                     # 内核期望的版本
zcat /proc/config.gz | grep -E "CONFIG_(SMP|PREEMPT|MODULE_UNLOAD|MODVERSIONS)="
readelf -h hello.ko | grep -E "Class|Data|Machine|Type"       # ELF 类别与架构
grep -w "printk" /proc/kallsyms                               # 符号是否可用
modprobe --show-depends hello                                 # 依赖链

六步结果拼起来，病因基本唯一。多数现场事故在前两步就锁定：modinfo 的 vermagic 与 uname -r 对不上。

六、模块 ELF 与重定位 #

.ko 不是共享库也不是可执行文件，而是 ET_REL 可重定位目标文件——和 .o 同一种。里面所有对外地址都是占位值，等内核把它 vmalloc 到某处之后再填。

6.1 ELF 头部关键字段 #

字段 偏移（32 位） 类型 .ko 中的典型值
e_ident[0..3] 0x00 4 × unsigned char 7F 45 4C 46
e_ident[EI_CLASS] 0x04 unsigned char 1 = 32 位，2 = 64 位
e_ident[EI_DATA] 0x05 unsigned char 1 = 小端
e_type 0x10 Elf32_Half 必须为 1（ET_REL）
e_machine 0x12 Elf32_Half 40 / 183 / 62
e_entry 0x18 Elf32_Addr 0，可重定位文件没有入口
e_shoff 0x20 Elf32_Off 段表起始偏移，改段前先读它
e_shnum 0x30 Elf32_Half 段表项数
e_shstrndx 0x32 Elf32_Half 段名字符串表所在段号

64 位下同名字段偏移会变（e_shoff 挪到 0x28，e_shnum 到 0x3C），写脚本别硬编码。

6.2 核心段及其作用 #

段名 类型 作用 逆向关注点
.text PROGBITS AX 函数机器码 改逻辑就改这里，注意指令长度
.rodata PROGBITS A 字符串常量 打印格式串在此，常用来定位功能
.data / .bss PROGBITS/NOBITS 有初值/无初值的全局变量 存被导出的全局对象
.modinfo PROGBITS A license=、vermagic=、name=、depends= 跨内核装载第一改点
__versions PROGBITS A 被引用内核符号的 modversion_info CRC 校验改点
__ksymtab + __ksymtab_strings PROGBITS A 本模块导出的符号表与名字串 被 depmod 读取建立依赖图
.gnu.linkonce.this_module PROGBITS WA 一个 struct module 实例 模块控制块，存 init/exit 指针与模块名
.init.text / .exit.text PROGBITS AX 初始化/清理函数 .init.text 加载后即释放
.rel.* REL 重定位项数组 由 apply_relocate 消费
.symtab / .strtab SYMTAB/STRTAB 符号表与符号名字符串 objdump -r 的 VALUE 列取自这里
.shstrtab STRTAB 段名字符串 readelf -S 的 Name 列取自这里

linkonce 是链接器的老约定：同名段只保留一份，避免重复定义。模块里它只有一个实例，就是加载后挂进全局链表那个 struct module。

6.3 段表项怎么读 #

定位 .modinfo 走的是「e_shoff → 段表 → 目标段 sh_offset」这条链：

字段 偏移 作用
sh_name 0x00 段名在 .shstrtab 中的偏移
sh_type 0x04 PROGBITS=1、SYMTAB=2、STRTAB=3、NOBITS=8、REL=9
sh_flags 0x08 WRITE=0x1（W）、ALLOC=0x2（A）、EXECINSTR=0x4（X）
sh_addr 0x0C 加载后虚拟地址，文件中通常为 0（与 sh_offset 是两回事）
sh_offset 0x10 该段在文件中的字节偏移
sh_size 0x14 段长度
sh_link / sh_info 0x18 / 0x1C 关联段号 / 重定位段表示「作用于哪个段」
sh_entsize 0x24 每项大小，重定位段是 8

段表项固定 40 字节，所以「第 N 段」在文件里的位置是 e_shoff + N × 40。

6.4 重定位段到底在说什么 #

编译器编 .ko 时不知道自己会被放在哪，也不知道 printk 的地址，于是先填占位值，再在 .rel 段记一行：「加载时，把 .text 内偏移 X 处的 4 字节，加上符号 printk 的运行时地址」。机制与链接期重定位相同，区别只在执行者：可执行文件由 ld 在构建时完成，.ko 由内核在加载时完成。

c
typedef struct {
    Elf32_Addr r_offset;   /* 待修正位置，相对于目标段的偏移 */
    Elf32_Word r_info;     /* 高 24 位符号表索引，低 8 位重定位类型 */
} Elf32_Rel;               /* 共 8 字节 */
类型 编号 语义 内核处理
R_ARM_ABS32 2 32 位绝对地址 loc 处原值加上符号地址
R_ARM_REL32 3 32 位相对地址 加符号地址再减当前位置
R_ARM_CALL / R_ARM_JUMP24 28 / 29 BL / B 改指令低 24 位为新偏移
R_ARM_THM_CALL 10 Thumb BL 拆成两段 11 位分别写入

REL（而非 RELA）意味着加数存在被修正的位置本身，不在重定位项里。这一点在第七章改表时会变成致命细节。

6.5 从 readelf 看到的三层信息 #

arm-linux-readelf -S hello.ko 里三列最关键：Off 给文件偏移，Size 给长度，Flg 里的 A 表示加载时需分配内存。实机输出见 7.3。看不到 .debug_* 段，说明这个 .ko 已被 strip 过，或构建时没开 CONFIG_DEBUG_INFO。

七、跨内核装载的逆向实验 #

这一章做一件违反常识的事：把为 A 内核编译的 .ko 装进 B 内核。目的不是生产使用，而是把三道关的检查点在二进制里逐个指出来。每一步都能改坏系统，先在虚拟机或可复位的开发板上做。

7.1 前置准备与安全边界 #

项目 要求 理由
目标机 可用串口或 ssh 收回日志 改错会 panic，网络直接断
复位手段 有复位按钮或可烧写的 sd 卡 panic 之后没法软件恢复
模块源码 先在能加载的内核上验证通过 排除代码本身的问题
备份与工具 cp hello.ko hello.ko.orig；readelf/objdump/hexdump/python3 二进制改错不可逆，全程在宿主机操作
定位 这是分析手段，不是部署方案 生产上应拿到匹配 headers 重编

7.2 第一步：复现报错 #

目标板跑 3.6.33-now（开了 CONFIG_PREEMPT），而我们误在 3.6.33-fake（关掉抢占）的目录里编译：

text
$ sudo insmod hello.ko
insmod: error inserting 'hello.ko': -1 Invalid module format

$ dmesg | tail -n 1
hello: version magic '3.6.33-fake SMP preempt mod_unload ARMv5'
        should be '3.6.33-now SMP preempt mod_unload ARMv5'

本例两边都有 preempt，差异只在版本后缀。如果连 SMP/preempt 也对不上，说明差异不止版本号，7.6 的结构体偏移问题一定会发生。

7.3 第二步：readelf 定位 .modinfo #

text
$ arm-linux-readelf -x .modinfo hello.ko
Hex dump of section '.modinfo':
  0x00000000 6c696365 6e73653d 47504c00 7665726d license=GPL.verm
  0x00000010 61676963 3d332e36 2e33332d 66616b65 agic=3.6.33-fake
  0x00000020 20534d50 20707265 656d7074 206d6f64  SMP preempt mod
  0x00000030 5f756e6c 6f616420 41524d76 3500     _unload ARMv5.

-x 按十六进制打出段内容，比 -p 更适合找偏移（后者只给字符串不给位置）。定位链条：

要改的东西 命令 得到的值
.modinfo 段起始 readelf -S 的 Off 列 0x000060
vermagic 字符串 readelf -x .modinfo 里搜 vermagic= 段内 0x0b
文件内绝对位置 段起始 + 段内偏移 0x00006b
字符串长度 数到下一个 00 为止 见 7.4

7.4 第三步：改 vermagic 字符串 #

规则只有一条：绝不能改变文件总长度。段表与重定位项全按绝对偏移索引，多一个字节后面全体错位。

原值 新值 长度变化 处理
fake now −1 余下 1 字节补 0x00
fake now2 0 直接覆盖
fake nowww +1 不允许，改用等长或更短的串

为什么可以补 0x00：.modinfo 里是一条条 NUL 结尾的独立字符串，vermagic= 提前结束，后面的空字节只是把原本属于这条串的空间让出来，内核按「下一个字符串头」继续解析。前提是不能把空字节写成别的字符，否则会多出一条非法条目。

7.5 第四步：改架构字符串 #

vermagic 末段的 ARMv5 来自编译时的 -march，改法与 7.4 完全相同。但边界必须知道：

场景 改 vermagic 是否够 说明
同为 ARMv7，仅标记不同 够 指令集兼容，改标记即过
ARMv4 → ARMv7 够但危险 ARMv7 是 ARMv4 超集，旧指令能跑，新指令用不到
ARMv7 → ARMv4 不够 目标 CPU 不认识 v7 才有的指令，第一条就 Undefined Instruction
ARM32 → ARM64 完全不够 e_machine 与 EI_CLASS 都不同，elf_check_arch 直接拒

不要把 e_machine 从 40 改成 183。改完确实能过头部校验，但内核会按 AArch64 的重定位类型表解释 R_ARM_* 项，跳进 init_module 就是 Unable to handle kernel paging request。这属于骗过了门卫，但进去拿错了地图。

7.6 第五步：重定位偏移不一致怎么办 #

过完关之后更麻烦的情况出现：模块加载成功，dmesg 甚至打出一行，随后立刻 panic：

text
Unable to handle kernel paging request at virtual address 0x33f2a8b0
PC is at 0x33f2a8b0

根因是 struct module 的布局在两个内核里不同。.gnu.linkonce.this_module 段存着这个结构体的实例，编译器按编译时的布局把 init 指针写在第 0x58 字节；运行内核按它自己的布局读 mod->init，读到的是 0x5C 处的 4 字节——隔壁字段的值。

配置项 对 struct module 的影响
CONFIG_PREEMPT 改变 percpu 与 refptr 相关分支/对齐，init 之前的成员排布变化
CONFIG_SMP 影响 per-CPU 指针与对齐
CONFIG_MODULE_UNLOAD 决定 exit/refcnt 是否存在
CONFIG_MODULE_SIG / CONFIG_LIVEPATCH 尾部追加签名或 klp 相关成员
编译器版本 / -mabi long 与指针对齐，整体对齐变化 
text
$ arm-linux-objdump -r hello.ko
RELOCATION RECORDS FOR [.gnu.linkonce.this_module]:
OFFSET   TYPE              VALUE
00000058 R_ARM_ABS32       init
000000e4 R_ARM_ABS32       cleanup

OFFSET 00000058 就是编译器认为 init 的位置。运行内核的真实位置要拿目标内核的 vmlinux 反汇编，或者用 pahole 读 BTF：

bash
$ pahole -C module vmlinux | grep -n "init"

两边算出差值后改 .rel.gnu.linkonce.this_module 里那条 r_offset：段文件偏移 0x854，第一条 Elf32_Rel 的 r_offset 位于 0x854 + 0x00，小端 4 字节，把 58 00 00 00 改成 5C 00 00 00。

必须说清：只改 r_offset 治标不治本。init 与 cleanup 能改，但模块代码里每一处 mod->xxx 访问都带着编译期算好的常量偏移，藏在 .text 的 ldr/str 立即数里，改起来没有边界。所以这一步是验证假设：改完能正常加载且 init 被调用，就证明病因在结构体布局，接下来该做的是拿匹配的头文件重编。

7.7 Python 自动改写脚本 #

手改十六进制容易数错位。下面脚本只做一件事：把 vermagic= 后面的串换成新串，长度不足补 0x00，超长直接拒绝。

python
#!/usr/bin/env python3
"""安全改写 .ko 的 vermagic：只允许等长或更短，绝不改变文件大小。"""
import sys

PREFIX = b"vermagic="


def patch_vermagic(src, dst, new_magic):
    with open(src, "rb") as f:
        data = bytearray(f.read())

    idx = data.find(PREFIX)
    if idx < 0:
        raise SystemExit("[-] 未找到 vermagic 标记，确认这是 .ko 而不是 .o")

    start = idx + len(PREFIX)
    end = data.find(b"\x00", start)
    if end < 0:
        raise SystemExit("[-] 字符串缺少 NUL 结尾，文件可能已损坏")

    old = data[start:end]
    new = new_magic.encode("ascii")
    if len(new) > len(old):
        raise SystemExit("[-] 新串 %d 字节 > 原串 %d 字节，会破坏段偏移，拒绝执行"
                         % (len(new), len(old)))

    data[start:start + len(new)] = new
    for i in range(start + len(new), end):
        data[i] = 0x00          # 剩余空间补零，保持总长度不变

    with open(dst, "wb") as f:
        f.write(data)
    print("[+] 原 vermagic: %s" % old.decode("ascii", "replace"))
    print("[+] 新 vermagic: %s" % new_magic)
    print("[+] 写出: %s (%d 字节)" % (dst, len(data)))


if __name__ == "__main__":
    if len(sys.argv) != 4:
        print("用法: python3 patch_vermagic.py <in.ko> <out.ko> <new_vermagic>")
        sys.exit(1)
    patch_vermagic(sys.argv[1], sys.argv[2], sys.argv[3])

bash
$ python3 patch_vermagic.py hello.ko hello_fixed.ko \
    "3.6.33-now SMP preempt mod_unload ARMv7"
[+] 原 vermagic: 3.6.33-fake SMP preempt mod_unload ARMv5
[+] 新 vermagic: 3.6.33-now SMP preempt mod_unload ARMv7
[+] 写出: hello_fixed.ko (3172 字节)

$ cmp -l hello.ko hello_fixed.ko | wc -l     # 只允许改动的那几字节不同
$ arm-linux-readelf -p .modinfo hello_fixed.ko | grep vermagic

脚本刻意不做三件事：不搜 __versions 改 CRC、不改 r_offset、不动 e_machine。这三样都需要目标内核的真实信息，猜不得。另外它只改第一处 vermagic=——一个 .ko 里该串只出现一次，复用到别处时要留意。

7.8 处理 CRC 不符 #

若目标内核开了 CONFIG_MODVERSIONS，改完 vermagic 会撞上第二道关（报 Unknown symbol printk (err -13)）。三条出路，按推荐度排序：

方案 做法 代价
拿目标内核 headers 重编 KDIR 指向目标内核构建目录 最干净，需 headers 或完整源码树
让模块不带版本信息 编译时确保 CONFIG_MODVERSIONS 未定义 仅当目标内核也没开此选项才有效
改 __versions 的 CRC 从目标内核读出正确 CRC 再写回 需逐符号对齐，符号一多不可维护

目标内核的真实 CRC 可以在 /proc/kallsyms 里按 __crc_<sym> 找。改 __versions 时注意 struct modversion_info 在 64 位上 crc 是 unsigned long（8 字节），32 位上才是 4 字节——按固定 -4 偏移写会写错位置。

7.9 剥离调试符号加固 #

选项 删掉什么 是否影响加载
strip（裸用） 全部符号表 .symtab 与调试段 影响，重定位需要 .symtab，加载报 Invalid module format
strip -g / --strip-debug 只删 .debug_* 段 不影响，.symtab 与 .rel.* 保留
objcopy --strip-unneeded 只留重定位需要的符号 多数可用，个别架构失败

所以加固只能用 -g。想再进一步得靠编译期 CONFIG_DEBUG_INFO=n——事后 strip 补不回来。而且 strip -g 只删调试段，符号名与函数边界仍在 .symtab 里，反编译门槛提高有限。

7.10 改完怎么验 #

按顺序验四件事：ls -l 确认字节数未变；readelf -p .modinfo 确认 vermagic 与 uname -r 逐字符一致；readelf -h 确认 Type 仍为 REL 且 Machine 未变；insmod 后 dmesg 里既有 init 的打印、又没有 disagrees about version。逐项判据见 11.4。

八、printk 与动态调试 #

模块一加载就可能 panic，「能看见它在干什么」比什么都重要。最低成本的手段是 printk——但它是被过滤的，不配置好会以为代码没跑。

8.1 八个日志级别 #

级别 宏 字面量 含义
0 KERN_EMERG "<0>" 系统不可用，即将崩溃
1 KERN_ALERT "<1>" 必须立即处置
2 KERN_CRIT "<2>" 临界状态，关键子系统故障
3 KERN_ERR "<3>" 普通错误，功能受影响
4 KERN_WARNING "<4>" 警告，可能有问题
5 KERN_NOTICE "<5>" 正常但值得注意
6 KERN_INFO "<6>" 常规信息（pr_info 默认级别）
7 KERN_DEBUG "<7>" 调试细节

数值越小越紧急，这个方向常被记反：KERN_EMERG 是「最容易被看见」，KERN_DEBUG 是「最容易被过滤」。这些宏在 2.6~4.x 定义于 linux/printk.h，5.x 之后才拆到 linux/kern_levels.h。

8.2 console_loglevel 与过滤规则 #

cat /proc/sys/kernel/printk 输出四个数以 4 4 1 7 为例：

位置 名称 作用
1 console_loglevel 只有数值小于它的消息才打到控制台
2 default_message_loglevel printk 不带 KERN_* 时用这个级别
3 minimum_console_loglevel 第 1 个数能被调到的最小值
4 default_console_loglevel 开机默认值

默认 4 意味着 KERN_INFO(6) 与 KERN_DEBUG(7) 都进不了控制台，但仍进了内核环形缓冲区，所以 dmesg 看得到。「串口没输出」不等于「代码没执行」，先 dmesg | tail。

手段 影响范围 持久性
echo 8 > /proc/sys/kernel/printk / dmesg -n 8 只改第 1 个数 重启失效
sysctl kernel.printk 四个数一起设 写入配置文件才持久
内核 cmdline loglevel=8 开机即生效 需改 bootargs

8.3 pr_fmt：给日志加统一前缀 #

c
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt
#include <linux/module.h>
#include <linux/kernel.h>

static int __init demo_init(void)
{
    pr_info("probe done, irq=%d\n", 42);
    return 0;
}

输出变成 demo: probe done, irq=42。KBUILD_MODNAME 由 Kbuild 自动注入，等于 obj-m 里的模块名。pr_fmt 必须在 #include 之前定义：写在头文件之后对 pr_info 的展开无效，而且不会有任何编译警告，是纯粹的静默失败。

8.4 动态调试的零开销原理 #

pr_debug 与 dev_dbg 在没开 CONFIG_DYNAMIC_DEBUG 时展开成 no_printk，参数都不求值。开了之后也不是「加个 if」，而是 jump label：

阶段 编译器做了什么 运行代价
未启用 函数入口放一条 nop，打印代码挪到 .text.unlikely 一条 nop
启用某个点 把该处 nop 原地改写成 jmp 一次跳转
关闭 再改回 nop 回到一条 nop

所以「零开销」的确切含义是：不是没有代码，而是一个可原地翻转的单字节补丁点。

bash
mount -t debugfs none /sys/kernel/debug                       # 通常已挂载
grep "my_driver.c" /sys/kernel/debug/dynamic_debug/control    # 看可用控制点
echo "file my_driver.c +p" > /sys/kernel/debug/dynamic_debug/control    # 开整文件
echo "file my_driver.c line 120 +p" > .../control             # 只开第 120 行
echo "module my_serial +p" > .../control                      # 按模块
echo "file my_driver.c -p" > .../control                      # 关
标志 含义
p 打开该点的 pr_debug
f / l / m / t 连同函数名 / 行号 / 模块名 / 线程 ID 一起打印

+pflmt 组合是调试驱动的常规配置，能把「谁、哪行、什么上下文」一次打全。更完整的日志体系见 内核调试：printk、动态调试与调试接口。

九、KGDB 与模块符号 #

printk 告诉你「发生了什么」，停在断点上才能告诉你「现场是什么」。KGDB 把目标机内核交给宿主机 GDB，代价是目标机在断点处完全停住——包括看门狗和网络。

要求 配置/动作 缺失后果
内核支持 CONFIG_KGDB=y、CONFIG_KGDB_SERIAL_CONSOLE=y kgdboc 参数被忽略
调试信息 CONFIG_DEBUG_INFO=y，保留未 strip 的 vmlinux 只能看汇编，没有源码行号
串口独占 kgdboc 指定的串口不能再被 console= 抢 输出与调试互相打断
启动参数 console=ttyS0,115200 kgdboc=ttyS0,115200 kgdbwait 无 kgdbwait 时要手动 echo g > /proc/sysrq-trigger

9.1 给动态模块补符号表 #

内置代码的符号在 vmlinux 里，GDB 一 file vmlinux 就认识。模块是 vmalloc 出来的独立区域，GDB 不知道它落在哪，break hello_init 会报 Function not defined。

bash
# 目标机上取各段真实地址（模块已加载成功）
$ cat /sys/module/hello/sections/.text        # 0xbf000000
$ cat /sys/module/hello/sections/.data        # 0xbf000200
$ cat /sys/module/hello/sections/.bss         # 0xbf0002a0
$ cat /sys/module/hello/sections/.init.text   # 0xbf001000

text
(gdb) target remote /dev/ttyUSB0
(gdb) add-symbol-file /path/to/hello.ko 0xbf000000 \
        -s .init.text 0xbf001000 \
        -s .data     0xbf000200 \
        -s .bss      0xbf0002a0
(gdb) break hello_init
(gdb) continue
段 不提供的后果
.text（第一个位置参数） 所有函数断点落在错误地址
.data / .bss 全局变量显示为乱值，未初始化变量读不到
.init.text 断不到 init——它的地址与其他段不连续

.init.text 的时效性必须强调：它只在 init 执行期间有效，do_init_module() 返回后整段被 module_free() 归还。「在 hello_init 第一行下断点」只有在加载之前就准备好符号才做得到。另外注意位宽：ARM32 上模块地址形如 0xbf000000，ARM64 才是 0xffffffffc0xxxxxx，两者不要混用。

9.2 用 Oops 地址反查源码行 #

bash
# dmesg 里的调用栈：PC is at hello_init+0x24/0x3c
$ arm-linux-gdb hello.ko
(gdb) list *(hello_init+0x24)

+0x24 是函数内偏移，不依赖加载地址。前提是 .ko 与出问题那次是同一份二进制、且没被 strip 掉调试信息，否则 list 会报 No symbol table。

十、ftrace 与 kprobes #

KGDB 让整机停住，生产环境用不了。ftrace 与 kprobes 思路相反：只记录，不停机。

10.1 function_graph 完整操作序列 #

bash
sudo mount -t debugfs nodev /sys/kernel/debug    # 1. 挂 debugfs
cd /sys/kernel/debug/tracing                     # 2. 进 tracing 目录
echo function_graph > current_tracer             # 3. 选追踪器
echo ':mod:hello' > set_ftrace_filter            # 4. 只追本模块的函数
echo > trace && echo 1 > tracing_on              # 5. 清历史，开开关
sudo insmod hello.ko                             # 6. 触发一次加载
echo 0 > tracing_on && cat trace | head -n 40    # 7. 关开关，读结果

text
 3)               |  hello_init() {
 3)   0.125 us    |    _raw_spin_lock();
 3)   1.218 us    |    printk();
 3)   4.821 us    |  }

左列是 CPU 号，中间是耗时，{ / } 表示进入与退出，缩进体现调用深度。

文件 作用 常用写法
current_tracer 选追踪器 function / function_graph / nop
set_ftrace_filter 只追哪些函数 ':mod:hello'、函数名通配
set_ftrace_notrace / set_graph_function 排除哪些 / 从哪个函数开始画图 排掉 printk 这类高频函数；hello_init
tracing_on 总开关 1 开，0 关
trace / trace_pipe 结果快照 / 流式读取 cat trace，或 cat trace_pipe 边读边流

顺序不能乱：部分文件只在选定追踪器后才出现。直接往 set_ftrace_filter 写而 current_tracer 还是 nop，写入会被忽略。:mod:hello 这种过滤语法的价值在于不写它就要追整个内核的所有函数，缓冲区几毫秒就滚过去了。

10.2 kprobes 原理 #

步骤 内核动作
1 拷贝目标地址处首条指令到影子区
2 把该地址首字节改成断点指令（x86 是 int3，ARM 是 brk）
3 CPU 执行到此处触发异常，进入 kprobes 异常处理
4 调用 pre_handler，此时寄存器上下文完整可读
5 单步执行影子区里那条原始指令
6 跳回原指令流下一条，调用 post_handler 
c
#include <linux/module.h>
#include <linux/kprobes.h>

static struct kprobe kp = {
    .symbol_name = "do_sys_open",   /* 用符号名定位，避免硬编码地址 */
};

static int handler_pre(struct kprobe *p, struct pt_regs *regs)
{
    pr_info("kprobe hit at %pS\n", p->addr);
    return 0;
}

static int __init kp_init(void)
{
    kp.pre_handler = handler_pre;
    return register_kprobe(&kp);
}

static void __exit kp_exit(void) { unregister_kprobe(&kp); }

module_init(kp_init);
module_exit(kp_exit);
MODULE_LICENSE("GPL");

打印寄存器时注意 pt_regs 的成员名随架构不同：x86 是 ip，ARM32 是 ARM_pc，ARM64 是 pc。照抄 regs->ip 在 ARM 上编译不过。

限制 表现 规避
不能探测 __kprobes 标注函数 注册返回 -EINVAL 换目标，或改用 ftrace
同一地址注册冲突探针 第二个注册失败 用批量接口或错开地址
.init.text 里的地址加载后失效 命中一次后崩溃 只探测常驻代码

kretprobe 是变体，专门在函数返回时回调：把 .kp.symbol_name 与 .handler 换成返回处理函数，并给出 .maxactive（同时未返回的最大实例数）。maxactive 必须给足，否则并发高时漏抓，并打印 kretprobe - maxactive exceeded 警告。

10.3 eBPF / SystemTap / LTTng 定位对比 #

维度 LKM（自己写驱动） eBPF SystemTap LTTng
运行形态 直接进内核 内核内虚拟机执行 脚本编译成临时 .ko 内核追踪点 + 用户态消费
安全性 最差，一处越界即 panic 最好，验证器静态检查后才加载 等同 LKM 高，不改内核代码
版本依赖 强（vermagic + CRC） 弱，CO-RE + BTF 可跨版本 需匹配 debuginfo 需匹配内核模块
开发成本 高，写 C + 编译 + 加载 中，C 或 bpftrace 脚本 低，类 awk 脚本 中，需配 lttng-tools
开销 取决于实现 低，JIT 后接近原生 中 最低，无锁环形缓冲
典型场景 真实硬件驱动 系统调用审计、网络、性能剖析 一次性探针 高频长时间录制

选择逻辑很简单：要改内核行为就写 LKM，只想观察就用 eBPF 或 ftrace。SystemTap 的价值在脚本化的一次性探针，LTTng 的价值在长时间、高频、低扰动地录下来再离线分析。

十一、故障排查清单 #

两篇素材各有一份 Checklist，合成原则是「一个现象只出现一次，原因写到最细」。

11.1 编译期 #

现象 原因 处置
No such file or directory: .../build/Makefile KDIR 路径不存在，或没装 headers ls $(KDIR) 确认，装对应版本 headers

multiple definition 同时存在 mydrv.c 与 mydrv-objs 二者只留一个
'pr_info' undeclared 漏了 #include <linux/kernel.h> 补头文件

十二、小结 #

  • 模块的意义是把「编译-部署-重启」压缩成「编译-装-卸」。开发期一律 =m，只有根文件系统所在的存储链路和「卸了系统就崩」的代码才写 =y。
  • 模块没有 main。module_init 展开成 init_module 的别名，内核靠这个固定符号名找入口；__init 段初始化后即释放，__exit 在 =y 时被整段丢弃。
  • Kbuild 的 $(MAKE) -C $(KDIR) M=$(PWD) modules 是双向调用：先进内核树拿全套编译选项，再回模块目录按 obj-m 编译。漏写 ARCH 会产出宿主架构的 .ko。
  • 模块参数通过 sysfs 暴露在 /sys/module/<name>/parameters/，权限位同时决定可见性与可写性；符号导出分普通与 GPL-only 两档，后者拒绝时的错误码是 -13（-EACCES）而非 -2（-ENOENT）。
  • 加载要过三道关：vermagic 逐字段比对、CONFIG_MODVERSIONS 的符号 CRC、ELF 架构与 ABI。共同理由是它们都会改变内核结构的布局。
  • .ko 是 ET_REL，地址全占位，由 apply_relocate 在加载期修正。REL（非 RELA）意味着加数存在被修正的位置本身，这个细节决定了改重定位表时不能只看重定位项。
  • 跨内核装载的改法有明确边界：改 vermagic 可行且安全（等长或更短 + 补零），改 r_offset 只能用于验证假设，改 e_machine 是纯骗门卫，进去必崩。
  • strip -g 能删调试段且不影响加载，裸用 strip 会删掉 .symtab 导致重定位失败。
  • 调试手段按「是否停机」排序：printk 不停机但只能看预先埋的点；dynamic debug 用 jump label 做到零开销可开关；ftrace 只记录不停机；kprobes 能在任意指令插桩；KGDB 能看现场但整机停住。
  • 模块符号在 GDB 里是空的，必须用 add-symbol-file 配 /sys/module/<name>/sections/.text 手动补，且 .init.text 的地址只在 init 执行期间有效。
