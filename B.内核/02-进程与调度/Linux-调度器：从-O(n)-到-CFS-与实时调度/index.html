一、调度器要同时满足的四件事 #

调度器的活是把 task 铺到 CPU 上，同时满足四类互相打架的需求：

需求 谁最在意 调的旋钮 调坏的后果
公平 time-sharing 的普通进程 权重、vruntime 有人吃撑有人饿死
响应 交互式进程、实时进程 调度延迟、抢占粒度 用户能摸到卡顿
吞吐 批处理进程 时间片长度、cache 亲和 CPU 时间全花在切换上
功耗 手持设备 任务放置、频率 电池和温度

先说称呼。进程是资源管理单位，线程才是调度单位。叫「线程调度器」读着别扭，本文沿用「任务调度器」，简称调度器。文中的「进程」指 task_struct 代表的实体。

需求先按任务类型切开。实时进程只认一条：deadline 之前跑完。普通进程要兼顾公平、响应、吞吐，三样互相冲突，于是再切一刀：交互式进程（等用户输入，对延迟敏感，CPU 占用低）和批处理进程（后台闷头干活，只看吞吐）。

这一刀还不够。有些批处理进程是 IO-bound 的，比如数据库服务进程，天生对延迟不敏感却频繁阻塞在 disk IO 上。看到它老睡就抬动态优先级，纯属浪费——受害的是等 CPU 的交互式进程。反过来，交互进程也时常突然变成 CPU-bound，调度器却判断不出它需要补偿。

落到实现上只有两把刷子：优先级（大量 RTOS 是 priority-based，官大一级压死人）和时间片（切大了响应烂，切小了切换开销吃掉吞吐）。功耗这条早期没进视野，Linux 铺到手机上才不得不面对，本文不展开。

二、调度类与调度器：sched_class 的分层 #

Linux 里同时存在 RT scheduler、Deadline scheduler、CFS scheduler、Idle scheduler。它们分层共存，不是互斥的。2.6.23 引入 sched_class 做模块化：核心调度代码只认这个结构体，具体策略由各调度类自己实现。

c
struct sched_class {
	const struct sched_class *next;
	void (*enqueue_task) (struct rq *rq, struct task_struct *p, int flags);
	void (*dequeue_task) (struct rq *rq, struct task_struct *p, int flags);
	void (*check_preempt_curr)(struct rq *rq, struct task_struct *p, int flags);
	struct task_struct * (*pick_next_task)(struct rq *rq, struct task_struct *prev, struct rq_flags *rf);
	/* ... */
};
  • next：指向低一档优先级的调度类。整条链就是优先级顺序。
  • enqueue_task / dequeue_task：入队、出队。
  • check_preempt_curr：task 被唤醒或新建时，判断它能否抢占当前 task，能就置 TIF_NEED_RESCHED。
  • pick_next_task：挑最该跑的那个。这是每个调度类真正见功底的地方。

选择逻辑顺着链走，谁先给出结果用谁：

c
for_each_class(class) {   /* 按优先级顺序遍历，顺着 next 走单链表 */
	p = class->pick_next_task(rq, prev, rf);
	if (p)
		return p;
}

Linux 4.18（CONFIG_SMP）：
stop_sched_class -> dl_sched_class -> rt_sched_class -> fair_sched_class -> idle_sched_class -> NULL

版本账要记清楚：

调度类 管什么策略 出现版本
stop_sched_class 停机/迁移线程，最高档 2.6 后期，仅 SMP
dl_sched_class SCHED_DEADLINE 3.14
rt_sched_class SCHED_FIFO、SCHED_RR 2.6 起
fair_sched_class SCHED_NORMAL、SCHED_BATCH、SCHED_IDLE 2.6.23 起
idle_sched_class 空闲线程 2.6 起

2.6.23 刚并主线时链条只有三节：rt_sched_class → fair_sched_class → idle_sched_class，dl_sched_class 还不存在。拿 2.6.23 的代码去找 deadline 调度类的，找不着。

分层带来一个实质好处：SCHED_FIFO 的实时进程永远排在 SCHED_NORMAL 前面，不是因为 CFS 内部礼让，而是核心调度器压根还没轮到 fair_sched_class。普通进程再多也碍不着实时进程——这一点在 O(n) 时代做不到。

三、2.4 的 O(n) 调度器怎么做 #

考古范围定在 2.4.18。代码短到可以整段读完，是理解后续所有改进的基线。

c
struct task_struct {
	volatile long need_resched;      /* 该让出 CPU 了 */
	long counter;                    /* 本周期还剩多少 tick 额度 */
	long nice;
	unsigned long policy;
	int processor;
	unsigned long cpus_runnable, cpus_allowed;
	struct list_head run_list;
	unsigned long rt_priority;
	/* ...... */
};

切换有两条路径。一条是等不到资源，自己调 schedule 挂起。另一条是跑得正欢被时间片耗尽打断，被迫让出。第二条不立刻切，只把 need_resched 置 1，等最近的调度点到——2.4 不是抢占式内核，调度点基本只在返回用户空间那一刻出现。

1、全局就绪队列 #

整个系统一个 runqueue_head 链表头。不管普通还是实时进程，状态变成可运行就挂进去；fork 挂入，阻塞或退出摘出。所有 CPU 共享这条链，同步靠一把自旋锁——这是后来所有 SMP 问题的根。链路外还有一条包含所有 task 的链（表头 init_task），周期结束重算时间片时用。

2、静态优先级与动态优先级 #

静态优先级是 task 固有的：实时进程看 rt_priority，普通进程看 20 - nice。真正决定谁跑的是 goodness 算出的动态优先级。实时进程直接加固定偏移，好让实时段整体压在普通段之上：

c
weight = 1000 + p->rt_priority;          /* 实时进程 */

weight = p->counter;                     /* 普通进程 */
if (!weight)
	goto out;
weight += 20 - p->nice;

规则两条：时间片耗尽则动态优先级为 0，本轮彻底没戏；时间片有剩则等于剩余 tick 加静态优先级。用 20 - nice 是为了让静态优先级单调上升。第二条的「剩余时间片」是给睡眠进程的奖励——睡得久、剩得多，回来优先级就高。机制粗糙，意图明确：猜谁是交互式进程。

调度器还顺手照顾 cache 和 TLB。A、B 优先级相同、剩余都是 3 tick，但 A 上次就跑在本 CPU 上，命中率更好，就把 A 抬一点。备选进程和当前进程共享地址空间时（同线程组两个线程，或借用上个进程地址空间的内核线程），切换不用换地址空间，也做些倾斜。

几个具体情形：优先级高且剩余多，必定先跑；优先级高但只剩几 tick，会让位给优先级中等、剩得多的人；优先级低是双重打击。但不管优先级多高，时间片用完就得下台——低优先级进程因此总有出头机会，这是 O(n) 唯一的兜底。

3、时间片怎么发 #

规则三条：按静态优先级固定分配缺省时间片，优先级越高分得越多；被调度后每 tick 递减，耗尽失去本轮资格；runqueue 里额度全用完 = 一个周期结束，全体重新充值。

tick 是最小单位，所以 nice=19 的缺省时间片就是 1 个 tick。中间的 nice=0 落在 60ms（HZ=100）或 41ms（HZ=1000），跟着 HZ 漂——同一个 nice 在不同 HZ 下拿到的时间片不一样，调度行为跟 HZ 绑死。

nice HZ=100（tick） HZ=100（时间） HZ=1000（tick） HZ=1000（时间）
-20 11 110ms 81 81ms
-10 8 80ms 61 61ms
0 6 60ms 41 41ms
10 3 30ms 21 21ms
19 1 10ms 3 3ms

周期结束时的充值：

c
if (unlikely(!c)) {
	struct task_struct *p;
	for_each_task(p)
		p->counter = (p->counter >> 1) + NICE_TO_TICKS(p->nice);
	goto repeat_schedule;
}

c 是扫完 runqueue 拿到的最大动态优先级。等于 0 意味着两件事同时成立：没有可运行的实时进程，普通进程的额度也全耗光。

for_each_task 遍历系统里所有进程，不区分状态。runqueue 上的普通进程 counter 已是 0，新额度就是 NICE_TO_TICKS(p->nice)。睡在等待队列里的进程还有余量，会带进新周期——这就是对睡眠进程的奖励。为防止老是睡醒的交互式进程攒出巨额时间片，余量只带一半（>> 1）。

tick 到来时的扣减，扣到 0 就置 need_resched，等调度点剥夺执行权：

c
if (--p->counter <= 0) {
	p->counter = 0;
	p->need_resched = 1;
}

4、调度时机 #

场景 说明
进程主动调度 等不到资源，自己调 schedule
timer 中断 发现当前进程时间片耗尽
进程唤醒 比如唤醒一个 RT 进程
fork 父进程时间片与子进程均分；只剩 1 tick 时全给子进程
进程切换 某 CPU 发生切换，别的 CPU 上也许还有更该跑的
主动让出 用户进程放弃 CPU
改调度参数 用户进程调 nice 等接口

除主动调度外，其余都只置 need_resched，等调度点。拿唤醒场景细看，后面的演进都绕不开它，唤醒方是 waker，被唤醒方是 wakee。

sync wakeup 指 waker 知道自己马上要睡，调 try_to_wake_up 时最好不要抢占——它很快就主动让出；两者往往有亲和性（比如共享内存通信），放同一 CPU 上性能更好，此时抢占反而把 wakee 甩到别的空闲 CPU 上，白白 CPU bouncing。non-sync wakeup 指两者没有同步关系，唤醒后各干各的，可以尝试触发调度。sync 也不是绝对不调度：waker 在 CPU A 上唤醒 wakee，但 wakee 的 cpus_allowed 说明它压根不能在 CPU A 上跑，那就别管 sync 不 sync，直接调 reschedule_idle。

UP 场景没花样，就一个 CPU，谁抢到取决于动态优先级，wakee 更高就置 need_resched。SMP 场景里 CPU 多，不必拼个你死我活：

  1. 优先把 wakee 放到空闲 CPU 上。上次跑的 CPU 正好 idle 就优先它；否则扫所有 CPU，挑最近刚进 idle 的（cache 更热）。
  2. 全都 busy，遍历各 CPU 当前 task，比动态优先级，找最低的。
  3. 最低的仍比 wakee 高，算了，继续排队。wakee 更高就置对方 need_resched；不抢 waker 本身的话，发 IPI 踢一脚。

这套设计把「选 runqueue」和「选 task」搅在一起，后来的负载均衡模块独立出去就是为了解这个结。

5、主调度器 #

c
list_for_each(tmp, &runqueue_head) {
	p = list_entry(tmp, struct task_struct, run_list);
	int weight = goodness(p, this_cpu, prev->active_mm);
	if (weight > c)
		c = weight, next = p;
}

扫全链，动态优先级最大的上台。就看这一段——哪怕链表第一个节点恰好就是最优解，它照样把整条链扫完，所以复杂度是 O(n)。

SCHED_RR 还得在扫之前先处理时间片轮转：

c
if (unlikely(prev->policy == SCHED_RR))
	if (!prev->counter) {
		prev->counter = NICE_TO_TICKS(prev->nice);
		move_last_runqueue(prev);
	}

时间片用光的 RR 进程被挪到链尾，下一轮扫到同优先级时命中的就是链表第一个，轮转就这么实现。古怪之处在于：RR 的时间片按 nice 算，而 nice 本该只对普通进程有意义。

四、O(n) 的三个死穴 #

如果「简单」是唯一标准，O(n) 天下无敌。问题在于它不是。三个死穴是遍历复杂度、全局锁的扩展性、周期同步导致的空转。原稿列了七条，剩下四条放在本节末尾。

1、死穴一：select next 是线性扫描 #

runqueue 上可运行进程一多，select next 的运算量线性上涨，这就是「O(n)」的由来。更糟的是周期结束后的充值：大型系统里同时存在的进程（含睡着的）数以千计，给每个算一遍时间片的代价太高。

2、死穴二：一把全局锁掐死 SMP #

访问 runqueue 的地方多得离谱：调度时要遍历找 next，wakeup 或 block 时要加删节点。每次都得先上自旋锁、关本地中断，做完再放锁开中断。CPU 少时还能忍，一多，runqueue 自旋锁就成了系统瓶颈——所有 CPU 排在同一把锁后面。

3、死穴三：时间片重算把 L1 打成筛子，还让 CPU 空转 #

全体时间片耗尽就得为系统里所有进程重算额度。这个操作足以把该 CPU 的 L1 cache 全部干掉——重算完，你面对一堆毫无意义的 cache 行，命中率断崖式下跌。

浪费的不只是 cache。4 个 CPU，T0~T3 分别跑在 CPU0~CPU3 上，T2 先耗尽，但 CPU2 无法调度——扫遍 runqueue 找不到有额度的进程，只能 idle。随后 T0、T3 也耗尽，只剩 T1 还在 CPU1 上跑，另外三个 CPU 干看着烧电。唯一能破局的是 T1 也耗尽。CPU 越多，这个窗口浪费的算力越多。

4、剩下的四条 #

（1）task bouncing。理想情况下进程该从一而终。O(n) 下进程在 CPU 间跳来跳去是常态，根子还是时间片算法：新周期开始时额度满满、可选对象多，加上调度器偏向上次跑本 CPU 的进程，多数能落回原地；可随着额度一个个耗光，可选项被压缩，进程就被挤到亲和性差得多的 CPU 上——上次在 CPU0，这次落到 CPU1，cache 全在 CPU0。

（2）RT 和普通进程混排。两者挂同一条链，调实时进程时得把整条链扫一遍，算完所有进程的调度指数，包括跟实时性毫无关系的普通进程。更根本的是 2.4 不是抢占式内核，几毫秒的系统调用或中断处理必须返回用户空间才能调度。优先级反转也能要命：RT 进程变成 runnable 了，却只能看着低优先级进程跑，直到后者释放资源。

（3）交互式判断失准。O(n) 不区分交互式和批处理，只是给爱睡的进程发奖励。IO-bound 的批处理进程（数据库服务是典型）也老睡，奖励它纯属无效，还推高其他交互式进程的延迟。反过来，CPU-bound 的交互式进程得不到补偿。

（4）时间片粒度跟着负载漂。HZ=100、5 个 nice=0 的可运行进程、每人 60ms，一个周期就是 300ms。进程耗尽后只能等下个周期，周期越长响应越差。负载越高响应越烂，这是结构性的。

社区当时基本认可这套算法，所以新调度器不是推翻重来，而是对症下药。2.6 的 O(1) 只改痛点，不动哲学。

五、2.6 的 O(1) 调度器：prio_array 与两张 bitmap #

O(1) 调度器以 2.6.11 为准。它和 O(n) 没有本质区别，还是「把 CPU 切成时间片分给可运行进程，用完被抢，等下个周期」，改的是数据结构和同步粒度。

第一刀砍在全局 runqueue 上：改成 per-CPU runqueue。所有可运行进程先经负载均衡模块挂到各 CPU 的 runqueue，再由主调度器和 tick 调度器驱动本 CPU 的调度行为。全局锁随之消失，换成 per-CPU runqueue 内部的一把锁（rq->lock）——一把大锁拆成多把小锁，调度延迟降下来。结构调整顺手解决了 SMP 扩展性和 CPU 空转，task bouncing 则交给好的负载均衡算法去治。

1、prio_array：140 个链表 + 一张 bitmap #

基本思路是把一条单链拆成多条：每个优先级一条链表。

c
struct prio_array {
	unsigned int nr_active;              /* 队列里有多少 task */
	unsigned long bitmap[BITMAP_SIZE];   /* 每个 bit 标记该优先级链表空不空 */
	struct list_head queue[MAX_PRIO];     /* 140 个链表头 */
};

优先级 0~99 归实时进程，100~139 归普通进程。RT 与普通进程从此分居两个空间，普通进程再多也污染不到 RT 的调度。runqueue 里有两个 prio_array，一个管 active（时间片还有剩），一个管 expired（已耗尽），runqueue 上有两个指针分别指着它们。

运行中 active 上的 task 一个个耗尽额度被挂进 expired。active 空了就交换两个指针，新一轮开始——交换是常数时间，没有任何遍历。

2、主调度器算法 #

c
idx = sched_find_first_bit(array->bitmap);
queue = array->queue + idx;
next = list_entry(queue->next, task_t, run_list);

在当前 active 队列的 bitmap 上找第一个非空的优先级链表，取该链表的第一个节点。没有遍历，复杂度是常量。active 空了就换指针：

c
if (unlikely(!array->nr_active)) {
	rq->active = rq->expired;
	rq->expired = array;
	array = rq->active;
}

对比 O(n) 那次遍历全系统重算时间片，这里只是两次指针赋值。runqueue 临界区被大幅压缩，前面三个死穴都被绕开。

3、静态优先级与动态优先级 #

「优先级队列」里的优先级指动态优先级，不是静态优先级。这一点上 O(1) 和 O(n) 反而统一了。

类型 字段 范围 含义
实时进程 rt_priority 1（最低）~ 99（最高） 越大越高
普通进程 static_prio 100（最高）~ 139（最低） 对应 nice -20 ~ 19

静态优先级数轴上有个尴尬：RT 段单调上升，普通段 100~139 单调下降。而实际调度用的动态优先级（prio）必须整体单调。RT 侧用一次映射抹平：p->prio = MAX_USER_RT_PRIO-1 - p->rt_priority;，翻转之后在数轴上也单调下降了。普通进程麻烦得多：除了静态优先级，还要看平均睡眠时间 sleep_avg，据此奖惩，实现在 effective_prio，最终落在 100~139。

和 O(n) 的对比很说明问题。两者思路一致：拿静态优先级做底，再评估「用户交互指数」，交互性强的抬、弱的压。差别在评估质量：

维度 O(n) O(1)
评估输入 仅睡眠进程的剩余时间片 平均睡眠时间，含 CPU 执行时间、runqueue 等待时间、睡眠时长、睡眠时是否可被信号打断、唤醒发生在中断还是进程上下文
交互式识别 隐式（剩余时间片多者胜） 显式（TASK_INTERACTIVE 宏）
结果 粗糙，误伤 IO-bound 批处理进程 判断更准，但常数全是实验凑出来的

4、时间片 #

缺省时间片由 task_timeslice 算，已和 HZ 解绑。不管 HZ 怎么设，nice 从 -20 到 0 到 19，缺省时间片就是 800ms → 100ms → 5ms。

tick 到来时扣减，扣到 0 就摘出 active、置 resched、就地重置额度：

c
dequeue_task(p, rq->active);
set_tsk_need_resched(p);
p->time_slice = task_timeslice(p);

关键在于「就地重置、分散处理」：每个 task 耗尽时立刻补，不再有一次遍历全系统所有进程的重算。这就是第三死穴的解药。

5、交互式进程的特殊照顾 #

正常路径是耗尽 → 挂进 expired → 等下次交换。有些场景要开小灶：

c
if (!TASK_INTERACTIVE(p) || EXPIRED_STARVING(rq)) {
	enqueue_task(p, rq->expired);
	if (p->static_prio < rq->best_expired_prio)
		rq->best_expired_prio = p->static_prio;
} else
	enqueue_task(p, rq->active);

TASK_INTERACTIVE 判断是不是交互式进程——依据还是平均睡眠时间。是的话重新塞回 active，让它接着有机会跑。但也不能太过分：EXPIRED_STARVING 就是那道闸，expired 里的进程等太久了说明不公平已严重，此时哪怕当前是交互式的，也照丢 expired，尽快让两边交换。

判断交互指数那套算法极度复杂，hardcode 了一堆不知所以然的常数，估计是拿大量实验场景凑出来的。它的价值在于比只看睡眠时间的 O(n) 强，代价是没人敢动。

6、抢占式内核 #

2.4 时代主战场是服务器，非抢占内核的选择无可厚非。往桌面和嵌入式渗之后，响应成了投诉重灾区。2.5 开发期引入 CONFIG_PREEMPT：不配，行为与 2.4 一致；配了，大部分内核执行路径可被抢占，不必苦等调度点。

六、O(1) 解决了什么，又留下了什么 #

2.5 开发期 Ingo Molnar 用 O(1) 替换掉简陋的 O(n)，扩展性和性能问题都治好了。商用 2.4 发行版里不少厂商把 O(1) 反向移植回去，可见性能确实能打。

O(1) 没解决的那件事恰恰最要命：桌面卡顿。只要跑起吃 CPU 的进程，现存的交互式程序（比如你在浏览器里翻网页）就能感到明显延迟。一堆工程师试图靠改交互指数算法解决，Con Kolivas 也在其中。可无论怎么调都像拆东墙补西墙：这个场景修好了，那个场景又冒出来。

调这类参数的人容易烦躁，这时候最需要的是停下想清楚。Con Kolivas 看了一遍代码，发现出问题的是评估交互指数那段。为什么调度器要根据进程行为猜它对交互性的需求？这活根本干不对——你永远猜不准，跟猜喜欢的人在想什么一样：性格、爱好、做事风格、逻辑水平、星座、生理周期全收集一遍，照样猜错。

进程调度凭什么不能按确定的东西来？静态优先级已经把调度需求说完了。不猜，只维持公平。所谓公平，就是进程拿到和静态优先级匹配的 CPU 时间。

七、公平调度思想的引入：从「分时间片」到「分权重」 #

顺着这条思路，Con Kolivas 提出 RSDL（Rotating Staircase Deadline）。

1、固定时间片的悖论 #

O(n) 和 O(1) 都固定分配时间片，静态优先级越高片子越大。直觉上没毛病——优先级高就该多跑。潜台词是：高优先级进程会拿到更多连续执行机会，这正是 CPU-bound 进程想要的。可现实里 CPU-bound 进程多在后台跑，优先级恰恰偏低。于是两难：

  • 想给交互式进程高优先级改善体验，可给它大时间片毫无意义——它大部分时间在阻塞等输入。
  • 后台进程优先级低，按优先级分到的小时间片反而伤它性能。这类进程最该趁 cache hot 一口气狂奔。

结论刺耳：固定分配时间片这个设计概念，本身就是错的。

2、RSDL 的三个词 #

RSDL 沿用 O(1) 的数据结构和软件结构，只把评估交互指数那段删干净。

Staircase（优先级楼梯）：进程的时间片不再集中在一个优先级上，而是散布在一串优先级里。静态优先级 120 的进程，时间片摊在 120~139 上。周期开始挂在 120 队列，跑满一个级别的时间配额（假设每级 6ms），降到 121，这就是一次 priority minor rotating。一路下楼梯，到 139 还耗尽，全部额度用完，挂进 expired 等下一个周期——这次叫 major rotating。

Rotating：上面那个逐级下沉的动作。

Deadline：任何进程都能精确预估自己的调度延迟。runqueue 里两个 task，A 是 130，B 是 139。A 只有沿着楼梯从 130 走到 139，B 才有机会跑，延迟是 9 × 6ms = 54ms。

算法就这么干净：只维持公平，不统计睡眠/运行时间，不算交互指数，不藏常数。

3、为什么进不了主线 #

RSDL 始终没进 mainline，取而代之的是同样基于公平思想的 CFS。CFS 并入主线时保留了模块化设计，理论上给 RSDL 或其他调度器留了进门的路。Con Kolivas 后来带着对内核开发模式的不满退出社区——技术之外的事，留给后人评说。

CFS 的设计理念一句话：在真实硬件上实现理想的、精确的完全公平多任务调度。这样的调度器不存在，实现时必须折衷。

4、公平的度量：分权重，不分时间片 #

CFS 追求的是 CPU 运算资源分配的公平：资源被精确地按比例分给在其上运行的 task。2 个静态优先级相同的 task 跑在一颗 CPU 上各拿 50%；优先级不同就按比例分。

text
分配给进程的时间 = 总的 CPU 时间 * 进程的权重 / 就绪队列所有进程权重之和

3 个可运行线程 A、B、C，权重 a、b、c，A 该拿 a/(a+b+c)。

CPU 资源分配是抽象概念，实现时必须落地，最省事的落地方式还是切成时间片。看到「时间片」三个字，你八成会本能地觉得 CFS 和 O(1) 没区别。不是。O(1) 给每个进程一个缺省时间片，用完挂 expired，全体耗光就整体重置回 active。CFS 没有静态时间片概念，它的时间片是动态的，取决于当前 CPU 上可运行进程的数量和它们的优先级。

用观察窗口理解：以 100ms 粒度看，两个同优先级进程 A、B 各分 50ms——不一定是 A 跑满 50ms 再切 B，期间切换了无数次，但 A 总共占 50ms。以 1ms 粒度看，是否各跑 500us？继续缩到 1us 呢？显然做不到每进程 500ns——那样 CPU 时间几乎全耗在切换上。所以 CFS 有个时间粒度，即调度周期。

八、CFS 的三块基石：权重、虚拟时间、红黑树 #

权重代表优先级，进程之间按权重比例分 CPU。A 权重 1024，B 权重 2048：A 拿 1024/(1024+2048) = 33.3%，B 拿 66.7%。权重越大分到的时间越多，等价于优先级越高。nice 值与权重一一对应，范围 [-20, 19]，数值越小优先级越大、权重越大。

1、虚拟时间 #

CFS 像一位母亲，手里只有一个玩具（CPU），要公平分给一群孩子（进程）。两个孩子就轮流各玩 10 分钟。落到调度器上，就是记录每个进程的执行时间，谁跑得少让谁跑。

问题是权重不同，物理时间本来就不该相等。调度周期 6ms，A、B 权重分别是 1024 和 820（nice 0 和 1）：A 跑 6 × 1024/(1024+820) = 3.3ms，占 55%；B 跑 2.7ms，占 45%。两个进程实际执行时间不等，可 CFS 要的是「虚拟时间相等」，于是把它们各过一个公式，得到同一个值：

text
              NICE_0_LOAD                    NICE_0_LOAD * 2^32
vruntime = wall_time * ---------------- = (wall_time * ---------------------) >> 32
                 weight                              weight

         = (wall_time * NICE_0_LOAD * inv_weight) >> 32    (inv_weight = 2^32 / weight)

A：3.3 × 1024/1024 = 3.3ms，nice=0 的进程虚拟时间等于实际时间。B：2.7 × 1024/820 = 3.3ms。权重不同，虚拟时间相同。于是 CFS 只需保证每个进程的虚拟时间一致，选 next 时找最小的即可。

浮点数不能用，内核用「先放大再缩小」保精度。inv_weight 预先算好存进 sched_prio_to_wmult，即 2^32 / sched_prio_to_weight[i]。权重信息用 struct load_weight 描述，两个字段：weight 和 inv_weight。实际时间转虚拟时间的实现是 calc_delta_fair()：

c
static inline u64 calc_delta_fair(u64 delta, struct sched_entity *se)
{
	if (unlikely(se->load.weight != NICE_0_LOAD))             /* 1 */
		delta = __calc_delta(delta, NICE_0_LOAD, &se->load);  /* 2 */
	return delta;
}

权重等于 NICE_0_LOAD 时虚拟时间就是实际时间，不用算；否则调 __calc_delta()，它算的是 delta_exec * weight / lw->weight，用 (u64)(u32)fact * lw->inv_weight 加移位把除法换成乘法。

2、红黑树 #

有了 vruntime 这个一维标量就能排序。二维的（权重，物理时间）被压成一维的虚拟时间轴：权重高的进程虚拟时间轴走得慢，权重低的走得快。

操作 频次 红黑树代价
插入调度实体 每次入队 O(log n)
删除调度实体 每次出队 O(log n)
取最小 vruntime 每次调度 O(1)（缓存最左节点）

CFS 怎么保证公平：每个进程的 vruntime 追平了最左节点就让它上。跑过的进程 vruntime 变大，慢慢往树右边挪；原来在右边的迟早跑到最左边。

3、2.6.23 和 2.6.24 不是一回事 #

这里必须点明一个容易搞错的细节，因为大量二手资料写反了。

版本 排序键 说明

2.6.24 起 se->vruntime 引入 min_vruntime、entity_key()，取代 fair_clock + wait_runtime

2.6.23 的 sched_fair.c 里根本没有 vruntime 这个字段。它是靠 fair_clock（按 runqueue 总负载缩放的虚拟时钟）和每个实体的 wait_runtime（欠账）算出一个 fair_key 当树键：

	key -= se->wait_runtime;

九、权重表 prio_to_weight 与 nice 的换算 #

先把虚拟时间为什么必须存在讲透，这是所有后续机制的起点。

假设进程之间没有优先级差别，问题简单到不用想：记录每个进程的实际运行时间，每次挑跑得最少的那个上。现实是进程有轻重，用户认为重要的进程就该跑得更久。这时候「谁跑得少」这个判据失效了——不同进程的运行时间本来就该不一样，拿什么比？

所以造一把尺子：让不同优先级按各自比例分到的物理时间，经过一个公式换算后得到同一个值。这个值就是虚拟时间。选 next 时挑最小的即可。这就是 vruntime 存在的全部理由——不是为了好看，是为了把「多目标」压成「单目标」。

十、调度延迟、调度周期与最小粒度 #

物理时间怎么换成虚拟时间讲完了，接下来是「一个进程该跑多久」。CFS 的答案是：不预设，现场算。

调度延迟就是保证每个可运行进程至少跑一次的时间间隔。每进程跑 10ms、2 个进程 → 20ms；5 个进程 → 50ms。硬把延迟钉死在 6ms 会怎样：

可运行进程数 每进程分到的时间
2 3ms
6 1ms
100 0.06ms

进程越多，每人分到的时间越少，切换越频繁，开销吃掉越来越多。所以 CFS 的调度延迟不是定值。规则两条：就绪进程数不超过阈值（4.18 里是 sched_nr_latency，默认 8）时，调度周期固定为 sysctl_sched_latency（4.18 默认 6ms）；超过阈值就保证每个进程至少跑 sysctl_sched_min_granularity（4.18 默认 0.75ms）才让出 CPU。

那个「至少跑多久」就是最小粒度时间。于是调度周期是动态的：

c
static u64 __sched_period(unsigned long nr_running)
{
	if (unlikely(nr_running > sched_nr_latency))
		return nr_running * sysctl_sched_min_granularity;
	else
		return sysctl_sched_latency;
}

1、参数在版本之间变过 #

这些数字不能张冠李戴：

2.6.23 20ms 2ms 未单独定义 period × nr / nr_latency
2.6.24 20ms 4ms 5 period × nr / nr_latency

2.6.23 是「延迟 × 进程数 / 阈值」，4.18 是「进程数 × 最小粒度」，后者更直接地表达「每人至少拿最小粒度」。

4.18 还有个容易忽略的点：这几个值会按 CPU 数放大。get_update_sysctl_factor() 用 1 + ilog2(min(ncpus, 8)) 做因子，CPU 越多颗粒越粗，理由是 CPU 多了之后用户能感知到的延迟会变小。这个点子的来源是 Con Kolivas 的 SD 调度器。所以 8 核机器上的 sysctl_sched_latency 是 6ms × 4 = 24ms。

2、最小粒度不总成立 #

先看一个反例。所有进程优先级都一样时，nr × min_granularity 确实能保证每人至少跑 min_granularity。可一旦优先级不同且进程数超过阈值，nice 值高的进程就未必能跑满最小粒度——它在一个周期内分到的总时间本来就不足 sysctl_sched_min_granularity。这是公式的边界，不是 bug。

分到的份额大于最小粒度时才能保证。看 check_preempt_tick()：

c
	ideal_runtime = sched_slice(cfs_rq, curr);
	delta_exec = curr->sum_exec_runtime - curr->prev_sum_exec_runtime;
	if (delta_exec > ideal_runtime) {                     /* 1 跑超了，直接抢 */
		resched_curr(rq_of(cfs_rq));
		clear_buddies(cfs_rq, curr);                       /* 清 buddy，否则它又被选回来 */
		return;
	}
	if (delta_exec < sysctl_sched_min_granularity)         /* 2 没跑够最小粒度，不抢 */
		return;
	se = __pick_first_entity(cfs_rq);
	delta = curr->vruntime - se->vruntime;
	if (delta < 0)
		return;
	if (delta > ideal_runtime)                             /* 3 落后够多才抢 */
		resched_curr(rq_of(cfs_rq));

第 2 句挡在前面，意味着「跑够最小粒度」是抢占的必要条件——只要不满足，后面 vruntime 差多少都不抢。

3、和传统调度器的对比 #

传统调度器保证不了有界延迟。两个 nice=0 的 A、B，各分 100ms 固定时间片，A 先跑到耗尽再换 B，延迟 100ms。再挂进 C、D，四个交替，延迟变 300ms。负载一涨延迟跟着涨。

CFS 从设计之初就把延迟参数定下来了，叫 targeted latency，概念上类似传统调度器的调度周期。区别在于：过去一个周期里的时间片是固定分给各进程的；CFS 是在一个 targeted latency 内不停检查公平性有没有被破坏。sysctl_sched_min_granularity 的作用就是防止 overscheduling——一个进程被调度上 CPU 后至少跑这么久，不许刚上来就被踢下去。

所以 CFS 保证的是：一个 targeted latency 内，所有可运行进程至少执行一次。延迟因此有界、可预测。

4、调度器怎么运作 #

CFS 里没有「固定分配时间片」，只有「固定权重」。选一个进程上 CPU 后立刻开始跟踪 virtual runtime，tick 到来时更新。有了 vruntime，调度器检查的不是「时间片用完没」，而是「公平性还在不在」：算 targeted latency，算出当前进程应得的物理时间片，算出它已累积执行的物理时间，超过了就更新 vruntime、置 need_resched。

选 next 就是从红黑树取最左节点。失去 CPU 的进程重新插回树里，位置由它的 vruntime 决定。

计时靠 runqueue 上的两块表：clock 记物理时间，clock_task 记真正执行 task 的时间。为什么要两块？因为 task 执行期间会撞上中断等异步事件，这些时间不该算到它头上。clock_task 把中断处理时间剔掉，只在真正跑任务时累加。于是计时变成：开始时读一次记为 A，需要统计时再读一次记为 B，B-A 就是物理执行时间，再用 calc_delta_fair 转成虚拟时间累加进 se->vruntime——这就是红黑树的键。

十一、调度实体与就绪队列结构 #

调度类管理和调度的单位是调度实体。支持组调度时一个 cgroup 也会抽象成调度实体，它根本不是 task。所以 task_struct 里塞了三个调度类的实体：

c
struct task_struct {
	struct sched_entity    se;   /* CFS */
	struct sched_rt_entity rt;   /* RT */
	struct sched_dl_entity dl;   /* Deadline */
};

struct sched_entity {
	struct load_weight load;          /* 权重，算虚拟时间用 inv_weight */
	struct rb_node     run_node;      /* 挂红黑树的节点 */
	unsigned int       on_rq;         /* 入队 1，出队 0 */
	u64  sum_exec_runtime;            /* 累计实际运行时间 */
	u64  vruntime;                    /* 累计虚拟运行时间 */
};

每颗 CPU 一个全局就绪队列 struct rq（per-cpu 类型），每个调度类在 rq 里有自己的就绪队列：

c
struct rq { struct cfs_rq cfs; struct rt_rq rt; struct dl_rq dl; };

struct rb_root_cached { struct rb_root rb_root; struct rb_node *rb_leftmost; };

struct cfs_rq {
	struct load_weight load;              /* 所有实体权重之和 */
	unsigned int nr_running;              /* 实体个数 */
	u64 min_vruntime;                     /* 最小虚拟时间的单调下界 */
	struct rb_root_cached tasks_timeline; /* 按 vruntime 排序的红黑树 */
};

rb_leftmost 是个缓存。取最左节点本是 O(log n)，缓存之后变 O(1)，而「取最左」是每次调度都要做的事。

1、min_vruntime 到底管什么 #

名义上是「队列上所有实体的最小虚拟时间」，但实际用途有三个，一个比一个重要。

（1）给新建进程定初值。fork 出来的新进程 vruntime 不能是 0。老进程的 vruntime 都已经很大了，新进程从 0 起跑，CFS 会一直挑它，让它疯跑到追平别人。

（2）给唤醒进程定初值。进程睡一觉醒来也是物是人非，处境跟新进程类似，同样要按 min_vruntime 调整。

（3）给迁移进程做换算。每颗 CPU 的 min_vruntime 差得不少。进程从 CPU0 迁到 CPU1，vruntime 必须换算，否则迁移本身就变成奖励或惩罚。做法是减去源 CPU 的 min_vruntime，入队时加上目标 CPU 的。4.18 的 migrate_task_rq_fair() 里就是 se->vruntime -= min_vruntime;——减在迁移时做，加在入队时做，分成两处是因为迁移那一刻还没拿到新 runqueue 的锁。

2、不是所有 vruntime 都大于 min_vruntime #

min_vruntime 的定义听着像一条不变式：任何实体的 vruntime 都 ≥ min_vruntime。不是。至少有一类反例：给唤醒进程做补偿时会把它 vruntime 减一截，减完就掉到下面去了。

所以 min_vruntime 更准确的理解是「一个单调递增的下界参考」，而不是「当前最小值」。4.18 的实现也印证了这点——它只增不减：

c
/* ensure we never gain time by being placed backwards. */
cfs_rq->min_vruntime = max_vruntime(cfs_rq->min_vruntime, vruntime);

3、min_vruntime 的初值 #

c
void init_cfs_rq(struct cfs_rq *cfs_rq)
{
	cfs_rq->min_vruntime = (u64)(-(1LL << 20));
}

这个初值是 2^64 - 2^20，也就是 U64_MAX 往下 2^20 那个位置附近。为什么不用 0？

min_vruntime 单位是 ns。从这么大一个数起跑，系统运行约 2^20 ns（约 1.05ms）就溢出一次。所以初值设在这里，目的多半是为了让溢出问题早点暴露。设成 0 的话，按 nice=0 的进程算得跑 545 年才溢出一次，测试根本等不到。

这是推测，没有 commit message 佐证。原稿也承认没找到答案。真要下定论得去翻 2.6.24 前后的邮件列表。

1、睡眠进程唤醒后的 vruntime #

第 2 问的答案对唤醒进程同样适用：睡久了醒来，vruntime 要按 min_vruntime 重定，具体做法是「在 min_vruntime 的基础上再减一截」。为什么要减？这段时间它本来就没占 CPU，给点补偿说得过去。交互式程序大多是这种模式——睡很久，醒来要立刻响应，减一截正好把响应速度拉起来。

减多少有讲究，看 4.18 的 place_entity()：

c
	u64 vruntime = cfs_rq->min_vruntime;

	if (initial && sched_feat(START_DEBIT))   /* 新进程：往后排，排到周期尾巴的空位 */
		vruntime += sched_vslice(cfs_rq, se);

	if (!initial) {                            /* 唤醒进程：往前排，减掉一个阈值 */
		unsigned long thresh = sysctl_sched_latency;
		if (sched_feat(GENTLE_FAIR_SLEEPERS))  /* 睡眠效果打对折 */
			thresh >>= 1;
		vruntime -= thresh;
	}

	/* 补偿归补偿，不许借补偿把 vruntime 倒推回去 */
	se->vruntime = max_vruntime(se->vruntime, vruntime);

最后一句还有副作用：se->vruntime 只取两者中的较大值，补偿是「有上限的」——如果一个进程的 vruntime 本来就比 min_vruntime - thresh 大，它一点补偿也拿不到。睡得太短就没有干涉的必要。

和第 2 问对照着看就通了：新进程往后排（initial 分支加 vslice），唤醒进程往前排（减阈值）。方向相反，理由一致——都是让它的位置和它「该被对待的样子」匹配。

2、唤醒会不会立刻抢占 #

分两种情况，取决于唤醒抢占特性 sched_feat(WAKEUP_PREEMPTION)。没开的话，后面的话都不用说，插进树里就完事。

开了呢？由于唤醒的进程刚按 min_vruntime 拿过补偿，它的 vruntime 有相当概率小于当前运行进程。那是不是「只要更小就抢」？不是。条件有两个且必须同时满足：差值还必须大于「唤醒粒度时间」。

c
static int
wakeup_preempt_entity(struct sched_entity *curr, struct sched_entity *se)
{
	s64 vdiff = curr->vruntime - se->vruntime, gran;

	if (vdiff <= 0)
		return -1;                  /* 唤醒方更晚，不该抢 */
	gran = calc_delta_fair(sysctl_sched_wakeup_granularity, se);
	if (vdiff > gran)
		return 1;                   /* 差得够远，该抢 */
	return 0;                       /* 可抢可不抢，看调用方 */
}

sysctl_sched_wakeup_granularity 在 4.18 里默认 1ms，和 sched_latency、min_granularity 一样按 1 + ilog2(ncpus) 放大。

注意 wakeup_gran() 里传的是 se（唤醒方）而不是 curr（当前方），这个选择是有意的。代码注释说得明白：用 se 会惩罚轻量级任务，让它们更容易被抢占。gran 越大，vdiff > gran 越难成立，也就不容易被抢。换个角度看，正是「保护重任务不被轻任务频繁打断」。

十三、实时调度：RT 调度器 #

前面十二章讲的全是普通进程。从现在起换赛道。实时任务和普通任务的分界线是 deadline：实时任务有 deadline，超了就不能产生正确的逻辑结果；普通任务没这条线。Linux 给实时任务准备了两套调度器：POSIX realtime scheduler（RT）和 deadline scheduler（DL）。本节讲 RT。

RT 有两种策略：SCHED_FIFO 和 SCHED_RR，都按实时优先级 rt_priority 调，最高优先级的先拿 CPU。在实时理论里这叫固定优先级调度器——每个 rt 任务预先固定一个优先级。优先级不同时，FIFO 和 RR 没有任何区别，区别只在优先级相同时：

策略 同优先级行为
SCHED_FIFO 最先进入 runnable 的任务先拿 CPU，一直占着不放，直到睡眠或阻塞
SCHED_RR 同优先级轮流执行。任务开始跑后若不阻塞，会一直跑到时间片到期，然后被放到链表末尾，调度器再取下一个

RR 的「链表」有前提：只有相同优先级的任务在一条链表上，不同优先级各占一条。这和第五章的 prio_array 是同一套结构。RT 的选择算法是 O(1)：rt_prio_array 里 100 条链表加一张 bitmap，找第一个非空链表，就是少了 expired 那一半。

配置 RT 任务只涉及两个参数：策略和固定实时优先级，chrt -f 10 video_processing_tool 就是让该任务归 RT 调度器管、实时优先级 10、策略 SCHED_FIFO（-f）。

RT 有个绕不开的坑：跑飞的实时任务会把机器锁死。内核给了兜底——RT 带宽控制。默认周期 1s、可用运行时 0.95s，剩下 0.05s 留给 SCHED_OTHER，好让你还能登进去救回来。

参数 默认值 含义
/proc/sys/kernel/sched_rt_period_us 1000000（1s） 等价于 100% CPU 带宽的调度周期
/proc/sys/kernel/sched_rt_runtime_us 950000（0.95s） 实时调度在周期内可用时间的全局上限

设成 -1 就恢复老行为（不限）。开了 CONFIG_RT_GROUP_SCHED 之后，这些值还成了各组带宽的总闸。

RT 的根本问题是优先级得靠人算。每个 rt 任务的优先级都要人配，配完还得验证整个任务集能被调度到，系统一变就得重来。DL 要解决的正是这件事。

十四、DEADLINE 调度器与 EDF 算法 #

DL 调度器不看优先级，看 deadline。调度点到来时，永远挑 deadline 离当前最近的那个任务。

1、三个参数 #

DL 任务要配三个参数：周期（period）、运行时间（runtime）、最后期限（deadline）。拿视频处理任务举例，每秒处理 60 帧，每 16ms 处理一帧，周期就是 16ms。runtime 是一帧处理需要多少 CPU 时间，这个值不能拍脑袋，必须按最坏情况估（worst-case execution time，WCET）——最慢那帧要 5ms，runtime 就得设 5ms。deadline 是处理结果必须交付的最后期限：假定这帧必须在周期的前 10ms 内交给下一个模块，deadline 就是 10ms。于是 5ms 的 runtime 必须落在这个 16ms 周期的前 10ms 里。

text
chrt -d --sched-runtime 5000000 --sched-deadline 10000000 \
     --sched-period 16666666 0 video_processing_tool

-d 说明策略是 deadline；--sched-runtime 是 5ms；--sched-deadline 是 10ms；--sched-period 是 ≈16.67ms；最后的 0 是优先级占位符，DL 不用它。设定之后，DL 保证每 16ms 周期里给这个任务 5ms CPU，并且这 5ms 落在 10ms 的 deadline 之前。

DL 参数看着复杂，其实简单：知道 task 的行为就能推出参数，只跟自己有关，跟系统无关。RT 不一样，它得看整个系统，把合适的 rt priority 分给各个 rt task，才能保证整体能跑。

这个差别还有个直接后果：DL 任务明确告诉了调度器自己要多少 CPU，所以新 DL 任务进来时调度器能判断 CPU 扛不扛得住。空闲就放进来，加进去会超过 100% 就拒之门外。一旦接纳，就必须按参数兑现。

2、EDF 为什么被叫「最优」 #

评估实时调度器性能的方法很朴素：造一组实时任务给调度器跑，看它能不能全部按期完成。

结论：单处理器上 Early Deadline First（EDF）最优。所谓最优，意思是 EDF 调不了的任务集，换别的调度器也调不了。对 periodic 和 sporadic 任务、且 deadline 不大于周期（constrained deadline）的场景，按 deadline 调度的表现最好。对于 deadline 等于周期的情形，只要任务集总利用率不超过 100%，EDF 都能全部满足。Linux 的 DL 调度器实现的就是 EDF。

看一组例子，deadline 等于 period：

任务 runtime period
A 1 4
B 2 6
C 3 8

总利用率 1/4 + 2/6 + 3/8 = 23/24，没到 100%，这组任务 EDF 能全部按期完成。换成固定优先级的调度器（比如内核里的 FIFO）呢？无论怎么调 rt priority，总有一个任务的 job 会拖到 deadline 之后。

3、EDF 的代价 #

好处先说：知道任务集里每个任务的参数，不需要分析其他任务就能判断这组任务能否按期完成；单处理器上按 deadline 调度产生的上下文切换次数往往更少；在同样满足 deadline 的前提下，能调度的任务数比固定优先级多。

缺点三条。

（1）不保证最小响应时间。deadline 调度器保证每个任务在 deadline 前完成，但不保证谁响应最快。固定优先级正好相反——最高优先级的任务永远有最小的响应延迟。

（2）算法本身更贵。固定优先级的复杂度可以是 O(1)（Linux 的 RT 调度器就是），deadline 调度器是 O(log n)（Linux 的 DL 用按 deadline 排序的红黑树）。公平地说，固定优先级的 O(1) 只算了「调度」这一步，它还需要给每个 task 挑一个最合适的优先级，这个最优优先级的计算是 O(N!)，往往离线做。

（3）多米诺效应。系统过载时（新任务加进来，或 WCET 估错），deadline 调度的麻烦会扩散：一个任务因为 runtime 超支而在 deadline 之后才完成，把结果交给下游，下游跟着错过 deadline，一路传下去。固定优先级反过来，一个任务出岔子，受影响的主要是优先级最低的那个。

Linux 的 DL 实现了 CBS（Constant Bandwidth Server）来治多米诺效应，细节不在本文范围。

十五、实时调度的任务模型与 deadline 分类 #

要讲清调度，得先把任务抽象成模型。评估实时调度器性能的标准做法，就是造一组实时任务（实时任务集）让调度器跑，看所有任务的 deadline 能不能都满足。

类型 到达规律 举例
周期性（Periodic） 固定间隔到达 音频处理程序每隔 20ms 压缩一帧
零散（Sporadic） 只定义最小间隔，实际可以更晚 最小间隔 20ms，则两次之间可以是 20ms 也可以是 30ms，但不会小于 20ms
非周期 无固定模式 用户按键触发的处理

一个实时任务的 deadline 有三种：

类型 关系 时间要求
隐含型（implicit） deadline = period 相对宽松，只要在本周期内分到 runtime 的 CPU 时间即可
受限型（constrained） deadline ≤ period 要求高一些，必须在周期结束之前的某个时间窗内分到 CPU
任意型（arbitrary） deadline 与 period 无关 最一般的情形

这三种形态直接决定可调度性分析的难度。EDF 的「最优」结论在 constrained deadline 下最干净；arbitrary deadline 就麻烦得多。

任务模型的意义在于把「实时」这个模糊的词量化成三个数：period、runtime、deadline。有了这三个数才能回答「这组任务能不能跑」。这也是 DL 比 RT 好用的根本原因：RT 只要求你给一个优先级，而优先级是个相对量——你得看全局才知道给得对不对，改动一个任务的优先级，整套分析都得重来。DL 要求的是绝对量，每个任务的参数只描述自己。

十六、多核实时调度器的分类 #

单核只需决定任务先后顺序。多核还得决定任务落在哪颗 CPU 上。

类别 含义 说明
全局类（Global） 一个调度器管所有 CPU，任务可自由迁移 实现简单，分析最难
集群类（Clustered） CPU 分成互不相交的 cluster，调度器管 cluster 内 折衷方案
分区类（Partitioned） 每个 CPU 一个调度器实例，各管自己 分析最简单
任意类（Arbitrary） 每个任务可以跑在任意 CPU 子集上 最一般

partitioned deadline 调度器是最优的——多核的调度问题被严格分解成一个个单核 deadline 调度问题，前面那套单核理论直接可用。global、clustered、arbitrary 三类都不是最优。

这个「不是最优」不是理论上的吹毛求疵。M 个处理器的系统里，有 M 个 runtime 等于 period 的任务，调度器轻松处理——一人一颗 CPU 就行。4 个「大活」，runtime 和 period 都是 1000ms，4 核系统各跑一个，利用率 400%：4 * 1000/1000 = 4，这么重的负载都能扛。

再看轻负载，直觉上更该没问题。4 个「小活」加 1 个「大活」：小活 runtime 1ms、周期 999ms，大活同上。总利用率 4 * (1/999) + 1000/1000 = 1.004，远小于 4，按直觉这套「4 小 1 大」应该轻松拿下。

结果不是。单核上最优的 EDF，到了多核（指 Global EDF）会出问题：所有任务同时释放，4 个小活的 deadline 更早，被分到 4 颗 CPU 上，大活得等它们全跑完才能开始，于是大活的 deadline 满足不了。这就是 Dhall 效应。

它说明一件反直觉的事：把若干任务分配给若干处理器本质上是个装箱问题，NP-hard。既然 NP-hard，就别指望哪个算法能全面压倒其他算法——各种异常场景都会冒出来。多核实时调度因此没有银弹，只能按场景挑合适的那一类。

十七、6.6 之后：EEVDF 替代了 CFS 的排序键 #

前面十六章讲的是 2.4 到 3.14 的演进。这一章讲一件更新的事：从 6.6 起，普通进程的调度算法换成了 EEVDF，CFS 退居二线。

1、为什么换 #

CFS 从 2.6.23 进来，靠 vruntime 排序保证公平，效果不差。但它有个解决不了的短板：没有表达延迟需求的接口。

有些进程不需要很多 CPU，但需要的时候必须马上给。另一些进程可以多跑，等一等也无所谓。nice 值只能表达「多给点 CPU」，表达不了「快点给我 CPU」。能表达延迟的只有实时类，可实时类是特权操作，跑飞的实时任务会拖累整个系统。latency nice 那套补丁试过解决这件事，思路是让对延迟敏感的 CFS 进程插队。补丁能用，但 Peter Zijlstra 认为有更好的办法——换算法。

2、EEVDF 是什么 #

Earliest Eligible Virtual Deadline First，1995 年由 Ion Stoica 和 Hussein Abdel-Wahab 提出。名字长得像 EDF，但 EEVDF 不是实时调度器。三个核心概念：

lag（欠账）：每个进程算出「本该拿到多少 CPU」和「实际拿到多少」的差。lag 为正说明被亏待了，应该早点跑；为负说明超额了。

eligible（合格）：lag ≥ 0 的进程才算合格，lag 为负的不许跑。不合格的进程在未来的某个时刻会被「该拿的时间追平实拿的时间」，那一刻叫 eligible time，从那时起它重新合格。

virtual deadline（虚拟截止期）：合格时刻加上分配给它的时间片。一个 10ms 时间片、eligible time 在 20ms 之后的进程，虚拟截止期是 30ms 之后。

算法就一句话：在合格的进程里，挑虚拟截止期最早的那个。

延迟需求自然就解决了。算时间片时把 latency nice 算进去：延迟要求紧的进程拿更短的时间片，不敏感的拿更长的。时间片短 → 虚拟截止期近 → 先被调度。两个 nice 相同的进程拿到的 CPU 总量一样，只是延迟敏感的进程把它拆成更多更短的片。

3、代码长什么样 #

字段 含义
se->slice 本次时间片，默认取 sysctl_sched_base_slice（750000ns，即 0.75ms）
se->deadline 虚拟截止期
se->vlag 虚拟 lag（省掉权重那一维的 lag）
se->min_deadline 子树内的最小 deadline，红黑树的增强数据

时间片和截止期是这么算的（update_deadline()）：先判 if ((s64)(se->vruntime - se->deadline) < 0) return;，然后 se->slice = sysctl_sched_base_slice;，最后 se->deadline = se->vruntime + calc_delta_fair(se->slice, se);——即 vd_i = ve_i + r_i / w_i，虚拟时间斜率由 nice 决定，请求长度由 base_slice 决定。

sysctl_sched_latency、sysctl_sched_min_granularity、sched_nr_latency 这几个参数在 6.6 里全没了，__sched_period() 也没了。这是换血，不是打补丁。

红黑树还在，但排序键和查找方式都变了。树仍然按 vruntime 排（__entity_less 比的就是 vruntime），同时靠 min_deadline 做增强，让树兼当按 deadline 排的堆：

c
static void __enqueue_entity(struct cfs_rq *cfs_rq, struct sched_entity *se)
{
	avg_vruntime_add(cfs_rq, se);
	se->min_deadline = se->deadline;
	rb_add_augmented_cached(&se->run_node, &cfs_rq->tasks_timeline,
				__entity_less, &min_deadline_cb);
}

4、别再把 rb_leftmost 当成下一个要跑的 #

这是本文最需要记住的一条实践提醒。

5.x 及以前，问「下一个跑谁」，答案就是 tasks_timeline.rb_leftmost。__pick_first_entity() 直接返回它，所有调试技巧、crash 分析、看 /proc/sched_debug 的直觉都建立在这个前提上。

6.6 起不成立了。__pick_eevdf() 从树根开始往下搜索，不是从左端取：

c
	while (node) {
		struct sched_entity *se = __node_2_se(node);

		/* 不合格就只看左子树 */
		if (!entity_eligible(cfs_rq, se)) {
			node = node->rb_left;
			continue;
		}
		/* 在合格的子树里按 min_deadline 找最早的那个 */
		if (!best || deadline_gt(deadline, best, se))
			best = se;
	}

注释把算法交代得很清楚：其一，任务必须合格（must be owed service）；其二，在合格的里面选虚拟截止期最早的；靠 se->min_deadline = min(se->deadline, se->{left,right}->min_deadline) 在子树上做类 EDF 的搜索，代价 O(log n)。

也就是说：最左节点是 vruntime 最小的，但 vruntime 最小 ≠ 该跑，它 lag 为负（不合格）就得跳过。真正决定谁跑的是「合格 + 虚拟截止期最早」，扫的是整棵树。

代码里还留了个兜底，说明「只靠最左」是错的：pick_eevdf() 调 __pick_eevdf()，拿不到结果时才退回 __pick_first_entity()，同时打一条 pr_err("EEVDF scheduling fail, picking leftmost\n")。看到这条报错，说明调度器已经在走异常路径。

rb_leftmost 缓存本身还在，因为入队/删除时维护它仍然有用，update_min_vruntime()、check_spread() 之类的辅助逻辑还在读它。但它不再是「下一个要跑的实体」。写调试脚本、看 sched_debug 输出、读 crash dump 时，这个前提必须换掉。

5、迁移建议 #

你原来的假设 6.6 之后
看 rb_leftmost 就知道下一个跑谁 要跑 __pick_eevdf() 的逻辑：先筛合格，再比 deadline
调 sched_latency_ns 调延迟 该参数已不存在，调 base_slice_ns
算 sched_slice() 得时间片 时间片是 se->slice，默认 sysctl_sched_base_slice
min_vruntime 是最小 vruntime 还是单调递增下界，但语义重心转向 lag 计算（avg_vruntime() 加权平均）
CFS 就是 fair_sched_class fair_sched_class 还在，里面装的是 EEVDF

需要说明的是，6.6 的改动不是「CFS 加了个新特性」，是「fair 调度类换了内核算法」。fair_sched_class 这个名字、sched_entity 这个结构、rbtree 这个载体都保留了，但排序语义、选择逻辑、参数集全变了。看 6.6 之后的 fair.c，按 CFS 的直觉去读会处处不对劲。
