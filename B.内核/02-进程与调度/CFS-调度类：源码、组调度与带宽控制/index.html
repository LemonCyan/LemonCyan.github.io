一、fair_sched_class：六个钩子函数 #

核心层不认识 CFS，只认识 struct sched_class。调度类靠 next 串成链，优先级从高到低：stop → dl → rt → fair → idle。pick_next_task()、enqueue_task()、dequeue_task() 全是调函数指针。

钩子 CFS 实现 什么时候被调 本篇
enqueue_task enqueue_task_fair 任务变成可运行 四
dequeue_task dequeue_task_fair 任务不再可运行 四
check_preempt_curr check_preempt_wakeup 新任务入队后问「能不能抢」 六、八
pick_next_task pick_next_task_fair 挑下一个跑的任务 五、十一
put_prev_task put_prev_task_fair 当前任务让出 CPU 五
task_tick task_tick_fair 每个 tick 七

task_fork → task_fork_fair（二）和 select_task_rq → select_task_rq_fair（三）逻辑量够大，各占一章。

c
const struct sched_class fair_sched_class = {
    .next = &idle_sched_class,
    .enqueue_task = enqueue_task_fair,   .dequeue_task = dequeue_task_fair,
    .check_preempt_curr = check_preempt_wakeup,
    .pick_next_task = pick_next_task_fair, .put_prev_task = put_prev_task_fair,
    .task_tick = task_tick_fair,         .task_fork = task_fork_fair,
    .update_curr = update_curr_fair,     .set_curr_task = set_curr_task_fair,
    /* CONFIG_SMP 下还有 select_task_rq / migrate_task_rq / task_dead 等 */
};

.next = &idle_sched_class：CFS 下面只剩 idle，所以 CFS 队列空时 pick_next_task_fair() 返回 NULL，核心层顺势落到 idle 线程。

二、fork 时的调度初始化：sched_fork / task_fork_fair #

1、sched_fork 做四件事 #

c
int sched_fork(unsigned long clone_flags, struct task_struct *p)
{
    p->state = TASK_NEW;                   /* 1 */
    p->prio = current->normal_prio;        /* 2 */
    /* ...sched_reset_on_fork 的回滚... */
    if (dl_prio(p->prio)) return -EAGAIN;  /* 3：DL 不在 fork 时建 */
    else if (rt_prio(p->prio)) p->sched_class = &rt_sched_class;  else p->sched_class = &fair_sched_class;
    init_entity_runnable_average(&p->se);  /* 4 */
    __set_task_cpu(p, cpu);  if (p->sched_class->task_fork) p->sched_class->task_fork(p);
}
  1. TASK_NEW 不参与任何唤醒路径，是「半成品」保护位：没人能把它跑起来，信号也唤不醒。 2. 优先级继承自父进程，但不许把 PI boosting 漏给子进程。 3. 三分支，不是无条件选 CFS。素材原文压成了 p->sched_class = &fair_sched_class; 一行（勘误 1）。 4. 给 PELT 打初值：任务实体按满权重起步，group 实体按 0 起步。

__set_task_cpu() 先钉在父进程的 CPU 上再调 task_fork。用它而不是 set_task_cpu()，因为任务还没 setup 完，不能触发 migrate_task_rq。

2、task_fork_fair：给新生儿定 vruntime #

c
    cfs_rq = task_cfs_rq(current);
    curr = cfs_rq->curr;                     /* 1 */
    if (curr) {
        update_curr(cfs_rq);                 /* 2 */
        se->vruntime = curr->vruntime;       /* 3 */
    }
    place_entity(cfs_rq, se, 1);             /* 4 */
    se->vruntime -= cfs_rq->min_vruntime;    /* 5 */
  1. curr 是当前在跑的实体。2. update_curr() 先把父进程到此刻的执行时间折算进 vruntime，不更新抄来的就是旧值。3. 子进程从父进程的 vruntime 起步。4. initial=1 表示新建，要受罚。5. 减掉本队列的 min_vruntime，把绝对值换成相对值。

第 5 步是全文最该记住的一处：

CPU0 的 min_vruntime 是 1000000，创建时算出 vruntime 为 1000500。但这进程唤醒后落到 CPU1，CPU1 的 min_vruntime 是 9000000。不做归一化，它一上来就白捡 800 万领先，会疯狂占 CPU。先减后加之后：1000500 − 1000000 + 9000000 = 9000500，位置正常。

「减」在 task_fork_fair() 末尾，「加」在 enqueue_entity() 里（四）。配对出现，缺一半就出大问题。

3、update_curr 与 update_min_vruntime #

c
    delta_exec = now - curr->exec_start;                    /* 1 */
    if (unlikely((s64)delta_exec <= 0)) return;  curr->exec_start = now;
    curr->vruntime += calc_delta_fair(delta_exec, curr);    /* 2 */
    update_min_vruntime(cfs_rq);                            /* 3 */
    account_cfs_rq_runtime(cfs_rq, delta_exec);             /* 4 */
  1. <= 0 直接返回，防止时钟回跳把 vruntime 往回推。 2. calc_delta_fair() 折虚拟时间，实质是 __calc_delta(delta, NICE_0_LOAD, &se->load)：权重越大折出来越小。 3. 推 min_vruntime。 4. 带宽控制的扣账入口。素材原文把这一句删了，导致第十七章讲的「时间从哪扣」在后文凭空出现（勘误 5）。

update_min_vruntime() 在三个候选中取最小：队列自身的 min_vruntime（初值）、当前运行实体的 vruntime（curr 非空且 on_rq）、树最左节点的 vruntime。最后一句 cfs_rq->min_vruntime = max_vruntime(cfs_rq->min_vruntime, vruntime) 保证单调不减——省了它，后面新建的任务会拿到过小的初值，等于集体作弊。

c

    if (leftmost) {                       /* 树非空，取最左 */
        se = rb_entry(leftmost, struct sched_entity, run_node);
        if (!curr) vruntime = se->vruntime;
        else vruntime = min_vruntime(vruntime, se->vruntime);
    }
    cfs_rq->min_vruntime = max_vruntime(cfs_rq->min_vruntime, vruntime);

4、place_entity：罚新人，奖睡神 #

c
    u64 vruntime = cfs_rq->min_vruntime;
    if (initial && sched_feat(START_DEBIT))
        vruntime += sched_vslice(cfs_rq, se);               /* 1 */
    if (!initial) {                                         /* 2 */
        unsigned long thresh = sysctl_sched_latency;
        if (sched_feat(GENTLE_FAIR_SLEEPERS)) thresh >>= 1; /* 睡眠影响减半 */
        vruntime -= thresh;
    }
    se->vruntime = max_vruntime(se->vruntime, vruntime);    /* 3 */
  1. 加一个 sched_vslice()，等于先欠一整个虚拟时间片。vruntime 越小越先跑，加就是罚。 2. 唤醒给补偿，减掉一个 sysctl_sched_latency，开了 GENTLE_FAIR_SLEEPERS 只减一半。 3. 奖励不许超额。睡 1ms 不许奖 3ms——那它睡一觉还赚了 2ms。你睡 100ms，奖你 3ms，没问题。

5、罚多少：sched_vslice 与 sched_slice #

c
static u64 sched_vslice(struct cfs_rq *cfs_rq, struct sched_entity *se)
{ return calc_delta_fair(sched_slice(cfs_rq, se), se); }
/* sched_slice() 的循环体 */
    u64 slice = __sched_period(cfs_rq->nr_running + !se->on_rq);    /* 1 */
    for_each_sched_entity(se) {                                     /* 2 */
        cfs_rq = cfs_rq_of(se);
        load = &cfs_rq->load;                                       /* 3 */
        if (unlikely(!se->on_rq)) {   /* 还没入队的，权重临时补进分母 */
            lw = cfs_rq->load;  update_load_add(&lw, se->load.weight);  load = &lw;
        }
        slice = __calc_delta(slice, se->load.weight, load);         /* 4 */
    }
  1. __sched_period() 按实体个数算周期：不超过 8 个是 sysctl_sched_latency（默认 6ms），超过就 nr_running × sysctl_sched_min_granularity，否则每人的片太小。
  2. for_each_sched_entity(se) 就是 for (; se; se = se->parent)。不开组调度时退化成 for (; se; se = NULL)，一次。
  3. 本层队列的权重和。
  4. __calc_delta() 在这里算占比再乘周期。队列权重 3072、se 权重 1024、周期 6ms，这个实体拿 6 × 1024 / 3072 = 2ms。

sched_vslice() 外层再套 calc_delta_fair()，把实际时间片换成虚拟时间片——树是按 vruntime 排的，罚也得罚虚拟时间。

三、放置策略：select_task_rq_fair 与 wake_affine #

三篇素材都没展开任务放置，只在 wake_up_new_task() 里带了一句。本章按 4.18.0 fair.c 补齐。判定标准和拓扑在 ⑥ 篇，这里只讲到「CFS 这层拿到哪几个 CPU、怎么挑」。 sd_flag 三选一：SD_BALANCE_WAKE（唤醒）、SD_BALANCE_FORK、SD_BALANCE_EXEC。wake_flags 里 WF_SYNC 表示 waker 唤醒后自己就去睡了，WF_FORK 表示 fork 出来的首次唤醒。只会在「配了对应 flag 的 sched domain」里挑 CPU。WF_SYNC 是强提示：调用方马上阻塞，wakee 放到 waker 的 CPU 上不亏，两个进程交替跑还能共享 cache。

c
    if (sd_flag & SD_BALANCE_WAKE) {
        record_wakee(p);
        want_affine = !wake_wide(p) && !wake_cap(p, cpu, prev_cpu)
                  && cpumask_test_cpu(cpu, &p->cpus_allowed);
    }
    for_each_domain(cpu, tmp) {
        if (!(tmp->flags & SD_LOAD_BALANCE)) break;
        if (want_affine && (tmp->flags & SD_WAKE_AFFINE) &&
            cpumask_test_cpu(prev_cpu, sched_domain_span(tmp))) {
            if (cpu != prev_cpu) new_cpu = wake_affine(tmp, p, cpu, prev_cpu, sync);
            sd = NULL;      /* wake_affine 优先于 balance 标志 */
            break;
        }
        if (tmp->flags & sd_flag) sd = tmp;
        else if (!want_affine) break;
    }
    if (unlikely(sd)) new_cpu = find_idlest_cpu(sd, p, cpu, prev_cpu, sd_flag);
    else if (sd_flag & SD_BALANCE_WAKE) {
        new_cpu = select_idle_sibling(p, prev_cpu, new_cpu);   /* 快路径 */
        if (want_affine) current->recent_used_cpu = cpu;
    }

want_affine 三个条件缺一不可：!wake_wide(p)——一个 waker 扇出一堆 wakee 时不许往一个 CPU 堆，否则调度延迟炸；!wake_cap(p, cpu, prev_cpu)——小核算力塞不下这个大任务，别硬留；cpumask_test_cpu(...)——亲和性写死了就不折腾。

c
    if (sched_feat(WA_IDLE)) target = wake_affine_idle(this_cpu, prev_cpu, sync);
    if (sched_feat(WA_WEIGHT) && target == nr_cpumask_bits)
        target = wake_affine_weight(sd, p, this_cpu, prev_cpu, sync);
    return target == nr_cpumask_bits ? prev_cpu : target;

wake_affine_idle()：this_cpu 空闲且与 prev_cpu 共享 cache 就留 this_cpu；sync 且 this_cpu 只有一个任务也留。一次比较，立刻给答案。wake_affine_weight() 管重载场景，关键在交叉相乘——两边负载各乘对端算力再比，等价于比「每单位算力上的负载」。WA_BIAS 给 prev_cpu 额外加 imbalance_pct 那一档，让「留在原 CPU」天生占点便宜，避免来回搬。

c
    this_eff_load = target_load(this_cpu, sd->wake_idx) + task_h_load(p);  if (sched_feat(WA_BIAS)) this_eff_load *= 100;
    this_eff_load *= capacity_of(prev_cpu);          /* 乘对端算力 */
    prev_eff_load = source_load(prev_cpu, sd->wake_idx) - task_h_load(p);
    if (sched_feat(WA_BIAS)) prev_eff_load *= 100 + (sd->imbalance_pct - 100) / 2;  prev_eff_load *= capacity_of(this_cpu);
出口 触发条件 挑谁
快路径 select_idle_sibling() SD_BALANCE_WAKE 且 wake_affine 没给结论 先 target，再 prev（cache affine 且空闲），再 recent_used_cpu，最后扫 LLC 域的 idle core / idle CPU / SMT 兄弟
慢路径 find_idlest_cpu() 不是 wake affine，或 FORK / EXEC 从 waker 往上找配了 sd_flag 的 domain，先找最闲 group，再找组里最闲 CPU
EAS find_energy_efficient_cpu() 5.10 才进这个函数，异构平台按能量模型挑 每个 perf domain 挑空余算力最大的 CPU，再比能量

fork 走慢路径有道理：新生儿没有 util_avg 历史，估不出轻重，EAS 也算不出能量，先找个最闲的放着。5.10 的三处改动：wake_cap() 删了，算力是否塞得下改由 select_idle_sibling() 里的 asym_fits_capacity() 判；target_load(..., sd->wake_idx) 换成 cpu_load(cpu_rq(...))；EAS 进了唤醒分支。

1、enqueue_task_fair 骨架 #

  1. 沿 se->parent 往上，每层都要入队；组调度关掉时一次循环。 2. on_rq 已经是 1 就不必再插——父链上只要有一层在队，上面都不用动。 3. enqueue_entity() 干实事。

2、enqueue_entity 六步 #

4、dequeue_entity #

五、choose_next_task：最左节点与 pick_next_entity #

1、__enqueue_entity 与 u64 溢出 #

c
    while (*link) {
        parent = *link;
        entry = rb_entry(parent, struct sched_entity, run_node);
        if (entity_before(se, entry)) link = &parent->rb_left;
        else { link = &parent->rb_right; leftmost = false; }

    rb_insert_color_cached(&se->run_node, &cfs_rq->tasks_timeline, leftmost);
static inline int entity_before(struct sched_entity *a, struct sched_entity *b)
{ return (s64)(a->vruntime - b->vruntime) < 0; }

tasks_timeline 是 rb_root_cached，多缓存一个最左节点。leftmost 就是告诉插入逻辑「要不要更新缓存」，O(1) 拿到最小值。

entity_before() 不直接比大小，而是先减再强转 s64，为的是让溢出不影响排序。vruntime 是 u64、单位 ns，2^64 ns 约 584 年。素材原文这里写成「264ns」（丢了下标），后面还有「264 + 5」「264 − 2」这种式子，全是 2^64 被吃掉上标（勘误 2、3）。 原文的例子：a 的 vruntime 是 101、b 是 100，entity_before() 返回假。假设 a 溢出，实际值 2^64 + 5，存下来是 5；b 即将溢出，值是 2^64 − 2。无论 a 是 5 还是 2^64 + 5，减法结果当 s64 看都是正数，结论一致。要读懂得知道负数在机器里怎么表示：5 − (2^64 − 2) 在模 2^64 下等于 7，当 s64 就是 +7，说明 a 在 b 之后。模运算把「跨溢出点」自动处理了。max_vruntime() 用同一个套路。

2、wakeup_preempt_entity 与 wakeup_gran #

九、组调度要解决的问题：一个用户开 1000 个进程怎么办 #

两个用户，A 跑 9 个进程，B 跑 1 个。CFS 按调度实体分时间、权重都一样，于是 A 拿 90%，B 拿 10%。A 再开进程，B 继续掉。

场景 用户 A 用户 B
A 9 个、B 1 个 90% 10%
A 99 个、B 1 个 99% 1%

这不是 CFS 的 bug，是它的语义：它保证「实体之间公平」，不保证「用户之间公平」。多用户机器上这个语义要命——一个用户开一堆进程就能把别人的 CPU 挤没。 组调度（Group Scheduling）把「用户组」也做成一个调度实体，让它参与顶层竞争：

层级 竞争单位 份额
顶层 A 组、B 组 各 50%
A 组内 A 的 9 个进程 各 50%/9 ≈ 5.56%
B 组内 B 的 1 个进程 50%

A 再开 100 个进程，B 还是 50%，只是 A 组内每人分得更少。这才是管理员要的语义：按付钱的比例分，不按进程数分。 代价是结构体变多：每个 task_group 在每个 CPU 上各配一个 group se 和一个 group cfs_rq，层级越深、CPU 越多，数量越吓人。每层的 vruntime、min_vruntime、load.weight 都得单独维护，入队出队要沿父链走一遍——这就是前四章那些 for_each_sched_entity() 的来由。

2、双 CPU 单组的账本 #

原文的例子：2 个 CPU、8 个进程，CPU0 上 3 个、CPU1 上 5 个，其中用户组 A 占 5 个。

队列 nr_running h_nr_running 说明
CPU0 根 cfs_rq 3 3 2 个 task se + 1 个 group se A
CPU0 的 group cfs_rq A 1 1 A 在 CPU0 的 1 个进程
CPU1 根 cfs_rq 5 5 1 个 group se A + 4 个组内进程
CPU1 的 group cfs_rq A 4 4 A 在 CPU1 的 4 个进程

一个 group se 在父队列上只算一个实体，背后拖着几十个任务。所以「CPU0 上 group se A 拿到的 CPU 时间，等于它 group cfs_rq 里所有进程拿到的时间之和」——这句是组调度的核心账本。 nr_running 数本队列的实体、不含子队列，给 __sched_period() 和 check_preempt_tick() 用；h_nr_running 数本队列加所有子孙队列，给 throttle/unthrottle 和均衡用。原文 4 CPU 的例子：根 cfs_rq 上 9 个 task se + 1 个 group se，nr_running = 10，h_nr_running = 19（多的 9 个在 group cfs_rq 里）。

十一、组内的进程选择：leaf_cfs_rq_list 与 vruntime 的传递 #

1、递归下降 #

组调度版的 pick_next_task_fair() 不加东西，就把五·4 那个 do-while 转成真循环：

c
    cfs_rq = &rq->cfs;                              /* 1 从根开始 */
    put_prev_task(rq, prev);
    do {
        se = pick_next_entity(cfs_rq, NULL);        /* 2 本层挑最小 */
        set_next_entity(cfs_rq, se);                /* 3 本层上台 */
        cfs_rq = group_cfs_rq(se);                  /* 4 se->my_q */
    } while (cfs_rq);                               /* 5 是 group se 就下钻 */

set_next_entity() 每层都要调一次。group se 被选中只表示「这个组在这层拿到执行权」，它不是一个能跑的上下文，得继续往下找具体任务。从根到叶，路径上每层的 curr 都被设成那条路径上的实体。

2、leaf_cfs_rq_list：为什么要一条叶子链表 #

概念 含义
leaf cfs_rq 直接装任务的队列，层级最底
cfs_rq->on_list 是否已在这条链上
rq->tmp_alone_branch 入队顺序的临时锚点，保证父总在子之后

入队时 enqueue_entity() 末尾有 if (cfs_rq->nr_running == 1) list_add_leaf_cfs_rq(cfs_rq);——队列从空变非空才挂链，出队到空时摘掉。这条链主要给 update_blocked_averages() 用：CPU 上没任务跑的组，它的 load_avg 不会自己衰减，得周期性扫一遍所有叶子 cfs_rq 才更新。没有这条链，就得遍历整棵组树。list_add_leaf_cfs_rq() 那段代码讲究在顺序：必须保证父在子的后面，否则自底向上刷负载时会用到父的旧值，tmp_alone_branch 就是干这个的锚点。

3、vruntime 在层级间怎么传 #

最容易读糊的地方。核心一句：每层有自己的 min_vruntime，se->vruntime 是相对它所在 cfs_rq 的。

动作 位置 对谁做
se->vruntime -= cfs_rq->min_vruntime dequeue_entity() 非睡眠分支、task_fork_fair() 末尾 绝对时间换成相对本队列
se->vruntime += cfs_rq->min_vruntime enqueue_entity() 的 renorm 分支 换回新队列的基准
每层各做一次 for_each_sched_entity() 循环里 从 task se 一路到根 group se

任务从 CPU0 迁到 CPU1，task se 减自己的加新的；它还在组里，group se 也要在各层减一次加一次。少做一层，那层的排序就错位。task_tick_fair() 那层 for_each_sched_entity() 也是这个道理：任务在 leaf cfs_rq 上跑，它的 group se 也在上层占着执行权，两层 entity_tick() 都得跑——每层的 update_cfs_group() 要刷权重，每层的 check_preempt_tick() 要判超支。任何一层超支，整个任务都得下来。

十二、用户组的权重：se->load.weight 从哪来 #

1、task se：nice 查表 #

load.weight 来自 sched_prio_to_weight[]，nice 0 是 1024，每降一个 nice 大约 ×1.25：

nice -20 0 1 5 10 19
weight 88761 1024 820 335 110 15

改 nice 走 set_load_weight() → reweight_task() → reweight_entity()。后者会把实体先从队列摘下来、改权重、再插回去，因为 cfs_rq->load.weight 得跟着变。

2、group se：按负载比例切 #

组有 shares，但一个组在 N 个 CPU 上各有一个 group se，这 N 个 se 的权重加起来不该超过 shares，否则组整体超额。分配依据是每个 CPU 上这个组的负载占比。原文的例子：2 个 CPU，CPU0 组的 group se 下挂 2 个 task se（权重和 3072），CPU1 上挂 3 个（4096），组 shares = 1024：

CPU 组内权重和 group se 权重 算法
CPU0 3072 439 1024 × 3072 / (3072 + 4096)
CPU1 4096 585 1024 − 439
合计 7168 1024 不超过 shares

这是「最简单的方式」，按 cfs_rq->load.weight 的比例切。真代码不这么算——它用 avg.load_avg，十四章。为什么不能按 load.weight 切：它是瞬时值，一入队一出队就变。按它算比例就得遍历所有 CPU 的 group cfs_rq 求和，跨 CPU 访问同一个全局变量，锁竞争能把系统拖死。于是换成 avg.load_avg：变化慢、可近似、每个 CPU 本地维护。代价是边界条件下有瞬变，十四章公式 (5)~(6) 就是补这个洞的。

十三、sched_slice 与组内时间分配 #

不考虑组调度时，time = sched_period * se->load.weight / cfs_rq->load.weight。单核、2 个权重 1024 的进程：周期默认 6ms，每人 6 × 1024 / 2048 = 3ms。一层组调度（shares = 1024，组内 2 个进程也都是 1024）就再乘一个比例：

text
                           se->load.weight            gse->load.weight
time = sched_period * ------------------------- * ------------------------
                         gcfs_rq->load.weight        cfs_rq->load.weight

代进去：6ms × 1024/2048 × 1024/2048 = 1.5ms。每个进程 1.5ms，组整体 3ms。

层级 竞争单位 权重和 分到 折到单进程
根 cfs_rq 组 A 的 group se、另一个普通进程 2048 组 A 3ms —
组 A 的 group cfs_rq 2 个 task se 2048 每个 1.5ms 1.5ms

再嵌一层组就再乘一个比例。这个连乘就是 sched_slice() 里 for_each_sched_entity() 循环干的事（代码见二·5，此处不重复）：按 nr_running 算周期，!se->on_rq 给「马上入队但还没进去」的实体补一位，然后每层乘一次 se->load.weight / cfs_rq->load.weight。 !se->on_rq 那个分支值得留意：实体还没进队列，权重不在 cfs_rq->load.weight 里，得临时补一个 lw 加进去算。不补分母偏小，算出的时间片偏大。task_fork_fair() → place_entity() → sched_vslice() → sched_slice() 这条路上正好是「还没入队」，所以每次 fork 都会走到。

c
static u64 __sched_period(unsigned long nr_running)
{
    if (unlikely(nr_running > sched_nr_latency))
        return nr_running * sysctl_sched_min_granularity;
    else
        return sysctl_sched_latency;
}

nr_running <= 8 时返回 sysctl_sched_latency（6ms），每人至少 0.75ms；超过 8 就按 nr_running × sysctl_sched_min_granularity 拉长周期，保住最小粒度。

参数 默认（单核） 缩放
sysctl_sched_latency 6ms × (1 + ilog2(ncpus))
sysctl_sched_min_granularity 0.75ms 同上
sysctl_sched_wakeup_granularity 1ms 同上

get_update_sysctl_factor() 里 cpus = min(num_online_cpus(), 8)，所以 8 核以上缩放因子固定 4（4.18，SCHED_TUNABLESCALING_LOG）。

十四、update_cfs_group 与 calc_group_shares 的公式来源 #

三处调用：enqueue_entity()、dequeue_entity()、entity_tick()。含义一样——组内成员变了或负载变了，group se 在父队列上的权重得重算。

c
    struct cfs_rq *gcfs_rq = group_cfs_rq(se);              /* 1 */
    if (!gcfs_rq) return;
    if (throttled_hierarchy(gcfs_rq)) return;                /* 2 */
#ifndef CONFIG_SMP
    runnable = shares = READ_ONCE(gcfs_rq->tg->shares);      /* UP 直接就是 shares */
#else
    shares   = calc_group_shares(gcfs_rq);                  /* 3 */
    runnable = calc_group_runnable(gcfs_rq, shares);
#endif
    reweight_entity(cfs_rq_of(se), se, shares, runnable);   /* 4 */
  1. 拿 group se 对应的 group cfs_rq。task se 直接返回，它没组。 2. 组被 throttle 了就不刷——原文没这条，是 4.18 真实代码（勘误 13）。被 throttle 的队列不动权重，免得解锁时账对不上。 3. 算新权重。4. reweight_entity() 落地。

calc_group_runnable() 算 runnable_weight（参与均衡、扣掉阻塞负载），calc_group_shares() 算 load.weight（参与时间片分配）。两个值，两套用途。

c
    tg_shares = READ_ONCE(tg->shares);  load = max(scale_load_down(cfs_rq->load.weight), cfs_rq->avg.load_avg);
    tg_weight = atomic_long_read(&tg->load_avg);
    tg_weight -= cfs_rq->tg_load_avg_contrib;   /* Ensure tg_weight >= load */
    tg_weight += load;  shares = (tg_shares * load);
    if (tg_weight) shares /= tg_weight;  return clamp_t(long, shares, MIN_SHARES, tg_shares);

落成公式（grq := group cfs_rq，ge := group se）：

text
                                tg->shares * load
ge->load.weight = -------------------------------------------------
                   tg->load_avg - grq->tg_load_avg_contrib + load
load = max(grq->load.weight, grq->avg.load_avg)

tg->load_avg 是这个组所有 group cfs_rq 的负载贡献和。grq->tg_load_avg_contrib 是「本队列上次已计入的值」，减掉再加回当前 load，等于用差分更新绕过遍历所有 CPU。clamp_t(...) 卡上下界：MIN_SHARES = 2、MAX_SHARES = 262144，上界必须是 tg_shares——一个 CPU 上的 group se 不许拿到比整个组还多的权重。

公式怎么来的 #

起点是「按 load.weight 比例分」，分母是全局求和，跨 CPU 太贵，换成平均负载近似：

text
                    tg->shares * grq->load.weight
ge->load.weight = -------------------------------               (1)
                      \Sum grq->load.weight
grq->load.weight -> grq->avg.load_avg                           (2)
                  tg->shares * grq->avg.load_avg
ge->load.weight = ------------------------------                (3)
                        tg->load_avg
Where: tg->load_avg ~= \Sum grq->avg.load_avg

avg 变化太慢，边界条件有瞬变。最典型的是空组刚跑起一个进程，avg.load_avg 从 0 慢慢爬，这段时间 group se 权重被严重低估，延迟就出来了。单核就是这种极端情况，按 (1) 直接算应该等于 tg->shares：

text
                    tg->shares * grq->load.weight
ge->load.weight = ------------------------------- = tg->shares     (4)
                        grq->load.weight
             tg->shares * grq->load.weight
ge->load.weight = ---------------------------------------------------  (5)
   tg->load_avg - grq->avg.load_avg + grq->load.weight
                  tg->shares * grq->load.weight
ge->load.weight = -----------------------------                  (6)
                        tg_load_avg'
 Where: tg_load_avg' = tg->load_avg - grq->avg.load_avg +
                       max(grq->load.weight, grq->avg.load_avg)

(5) 是在分母里把本队列的 avg.load_avg 换成 load.weight，让 (3) 在 UP 场景退化成 (4)。但 (5) 在 grq->load.weight == 0 时除零，所以 (6) 拿 avg.load_avg 当 load.weight 的下限兜底。

场景 (6) 退化成 说明
UP（只有一个 cfs_rq 有负载） ≈ (4)，即 tg->shares 边界条件正确
常规（多 CPU 都有负载） ≈ (3)，按 avg.load_avg 比例 近似但开销小

代码里 load = max(scale_load_down(cfs_rq->load.weight), cfs_rq->avg.load_avg) 对应 (6) 的 max(...)；tg_weight -= tg_load_avg_contrib; tg_weight += load; 对应 tg->load_avg - grq->avg.load_avg + load。 tg->load_avg 的差量更新在 update_tg_load_avg() 里，门限是 tg_load_avg_contrib / 64，不是固定值。原文举了「差值到 2000 才更新，tg->load_avg 依次变成 2000、4000」，那个 2000 只是示意，真实门限随 contrib 浮动（勘误 12）。tg->load_avg 是全局共享变量，多 CPU 同时写。靠差分更新把写频率压下来，代价是它只能是「近似」和——这正是 (3) 里那个 ~= 的来源。

        atomic_long_add(delta, &cfs_rq->tg->load_avg);

十五、带宽控制是什么：quota / period / runtime #

单进程系统把某个进程限到 50%，到点就停、CPU 空闲——看着没意义。两种场景是刚需：这个进程属于「只付了这么多 CPU 时间」的客户；或者要保证严格资源隔离，不许某个租户偶尔爆发把别人挤死。付多少钱享受多少服务，这就是带宽控制（CPU bandwidth control）的定位，只管 SCHED_NORMAL 类。要开这个功能需要 CONFIG_FAIR_GROUP_SCHED 和 CONFIG_CFS_BANDWIDTH。

词 含义 存放位置
period 一段周期时间 cfs_bandwidth->period
quota 一个 period 内这个组最多消耗的 CPU 时间 cfs_bandwidth->quota
runtime 全局池子里还剩多少时间可以发 cfs_bandwidth->runtime

超支的动作叫 throttle：把该组实体从队列上摘掉，没机会被选中。到下一个 period、quota 重新填满，叫 unthrottle。 原文这个类比好用：cfs_bandwidth 像内存池管内存一样管时间。每个 group cfs_rq 想让树上的实体被调度，必须先从全局池申请一个固定大小的切片，让进程消耗；耗尽再申请；池子空了就是 throttle 的时刻。

text
        cfs_bandwidth (per task_group)
        | period = 100ms   quota = 50ms |   <- 每 period 重填成 quota
        | runtime = 剩余可发时间         |
        +---------------+---------------+
                        | 申请 5ms 切片
        +---------------+---------------+
        v                               v
  cfs_rq (CPU0)                    cfs_rq (CPU1)
  runtime_remaining = 5ms          runtime_remaining = 5ms
   进程消耗 -> 扣 runtime_remaining

例子：period 100ms、quota 50ms、2 个 CPU。CPU0 先申请 5ms（全局 runtime 50 → 45），跑完再申请 5ms（45 → 40）；CPU1 同样。全局 runtime 不够满足任何一次申请时，throttle 对应 cfs_rq。定时器到点，把所有被 throttle 的 unthrottle。

十七、带宽如何在层级间贡献与下发 #

第二章那个 update_curr() 的最后一句就是扣账入口。两个开关：全局有没有人用（cfs_bandwidth_used()，静态 key，没人用零开销）、本队列有没有开。

c

/* __account_cfs_rq_runtime() */
    cfs_rq->runtime_remaining -= delta_exec;            /* 1 先扣 */
    expire_cfs_rq_runtime(cfs_rq);                       /* 跨 period 的残留清零 */

        resched_curr(rq_of(cfs_rq));                     /* 4 */
  1. 跑多少扣多少，先扣再 expire：这段会跨 period 边界，得按旧 period 记账。 2. 还有剩就走人，绝大多数情况。3. 不够了找全局池要。 4. 要不到置 TIF_NEED_RESCHED。这里不做 throttle——throttle 要等调度发生、put_prev_entity() 里才做，因为此刻还拿着 rq 锁、任务还在 CPU 上跑。

十八、如何 throttle 一个 cfs_rq #

申请失败只置了 TIF_NEED_RESCHED，真 throttle 发生在任务让出 CPU 的时候：

c
/* check_cfs_rq_runtime()：put_prev_entity() 里调 */
    if (!cfs_bandwidth_used()) return false;
    if (likely(!cfs_rq->runtime_enabled || cfs_rq->runtime_remaining > 0)) return false;  /* 1 */
    if (cfs_rq_throttled(cfs_rq)) return true;    /* 2 已经限过，别重复 */
    throttle_cfs_rq(cfs_rq);                      /* 3 */
/* throttle_cfs_rq() */
    se = cfs_rq->tg->se[cpu_of(rq_of(cfs_rq))];              /* 4 要摘的 group se */
    walk_tg_tree_from(cfs_rq->tg, tg_throttle_down, tg_nop, (void *)rq);  /* 5 */
    task_delta = cfs_rq->h_nr_running;
    for_each_sched_entity(se) {
        struct cfs_rq *qcfs_rq = cfs_rq_of(se);
        if (!se->on_rq) break;
        if (dequeue) dequeue_entity(qcfs_rq, se, DEQUEUE_SLEEP);   /* 6 */
        qcfs_rq->h_nr_running -= task_delta;
        if (qcfs_rq->load.weight) dequeue = 0;   /* 7 还有别人，别再往上摘 */
    }
    if (!se) sub_nr_running(rq, task_delta);
    cfs_rq->throttled = 1;                                /* 8 */
    cfs_rq->throttled_clock = rq_clock(rq);
    list_add_rcu(&cfs_rq->throttled_list, &cfs_b->throttled_cfs_rq);   /* 9 */

  1. 两个前置：开了限额、确实没时间了。调用点在 put_prev_entity()（五·3），也就是「当前任务要下台」这一刻。选这里是因为 rq 锁在手、结构稳定，能安全地把它整条父链摘干净。

  2. 找到本 cfs_rq 在本 CPU 上对应的 group se，要摘的就是它。

  3. 顺着 cfs_rq->tg 往下遍历所有子组，对每个调 tg_throttle_down() 增 throttle_count。父组被限，子组自然也跑不了。

  4. 从父队列红黑树摘掉。摘完 pick_next_entity() 顺着树往下钻就碰不到它——这是 throttle 的本质手段。

  5. 父队列只剩它一个实体（load.weight 变 0）时，父层也得摘；某层还有别的实体，再往上就不能摘，那些人还要跑。

  6. 置标志、记时刻。9. 挂进 throttled_cfs_rq 供后续 unthrottle 找到它；链原来是空的就顺手开定时器。

h_nr_running 那串减法容易看漏：task_delta 是「这个 group se 背后实际挂多少任务」，每摘一层，那层的 h_nr_running 就减这么多。tg_throttle_down() 只做两件事：throttle_count 从 0 变 1 时记下 throttled_clock_task，然后 throttle_count++。计数而不是布尔，是因为会有多条路径把它压住（自己被限 + 父组被限），得全部解除才算真能跑。

观察点 throttle 之后的表现
pick_next_task_fair() 顺根 cfs_rq 的红黑树往下，碰不到被 throttle 的 group se
cfs_rq->nr_running 不变，队列里的任务还在，只是整棵子树被摘了
父队列的 h_nr_running 减掉这一支的数量
cpu.stat nr_throttled 加一，throttled_time 累加
任务状态 还是 TASK_RUNNING，只是拿不到 CPU，从 ps 上看不出异常

        cfs_rq = cfs_rq_of(se);
        if (enqueue) enqueue_entity(cfs_rq, se, ENQUEUE_WAKEUP);    /* 7 */
        cfs_rq->h_nr_running += task_delta;
        if (cfs_rq_throttled(cfs_rq)) break;
    }
    if (!se) add_nr_running(rq, task_delta);
    if (rq->curr == rq->idle && rq->cfs.nr_running) resched_curr(rq);   /* 8 */
/* tg_unthrottle_up() */
    cfs_rq->throttle_count--;
    if (!cfs_rq->throttle_count) {          /* 计数回 0 才算真解禁 */
        cfs_rq->throttled_clock_task_time += rq_clock_task(rq) - cfs_rq->throttled_clock_task;
    }
  1. 要重新入队的还是那个 group se。5. 反向遍历组树，递减 throttle_count。 7. 逐层插回红黑树，跟 throttle_cfs_rq() 的摘动作对称。 8. 本 CPU 正闲着，现在有活干了，得踢一脚让它重新调度，不然要等到下个 tick。
字段 统计什么 什么时候累加
cfs_b->throttled_time 本队列自己因超 quota 被停的时长 unthrottle_cfs_rq()，用 rq_clock()
cfs_rq->throttled_clock_task_time throttle_count 从非 0 到回 0 的总时长，含被父组连带停住的时间 tg_unthrottle_up()，用 rq_clock_task()

差别在于：一个队列自己没超 quota（throttled == 0），但父组超了（throttle_count > 0），它一样跑不了。throttled_clock_task_time 抓的就是这种「我没错也停了」。这个值还被 cfs_rq_clock_task() 用来校正队列时钟，避免把停住的时间算成执行时间。

二十、周期性刷新 quota：sched_cfs_period_timer #

c
/* init_cfs_bandwidth()：两个高精度定时器 */
    cfs_b->quota = RUNTIME_INF;   cfs_b->runtime = 0;
    cfs_b->period = ns_to_ktime(default_cfs_period());      /* 100ms */
    hrtimer_init(&cfs_b->period_timer, CLOCK_MONOTONIC, HRTIMER_MODE_ABS_PINNED);
    cfs_b->period_timer.function = sched_cfs_period_timer;  hrtimer_init(&cfs_b->slack_timer, CLOCK_MONOTONIC, HRTIMER_MODE_REL);
/* sched_cfs_period_timer() */
    for (;;) {                         /* 补漏掉的周期 */
        overrun = hrtimer_forward_now(timer, cfs_b->period);
        if (!overrun) break;
        idle = do_sched_cfs_period_timer(cfs_b, overrun);
    }
    return idle ? HRTIMER_NORESTART : HRTIMER_RESTART;
定时器 模式 回调 干什么
period_timer HRTIMER_MODE_ABS_PINNED sched_cfs_period_timer 每 period 重填 quota 并尝试 unthrottle
slack_timer HRTIMER_MODE_REL sched_cfs_slack_timer 有人归还时间片，提前分发

初始 quota = RUNTIME_INF、period = 100ms（100000000ULL ns）。hrtimer_forward_now() 是补漏掉的周期：系统忙、回调被推了 3 个 period，overrun 就是 3，一次把这 3 个 period 的 quota 补上。idle 返回 1 表示「这组没活动了」，直接 HRTIMER_NORESTART 停表省电。

c
    if (cfs_b->quota == RUNTIME_INF) goto out_deactivate;   /* 不限带宽，不跑表 */
    throttled = !list_empty(&cfs_b->throttled_cfs_rq);  cfs_b->nr_periods += overrun;
    if (cfs_b->idle && !throttled) goto out_deactivate;
    __refill_cfs_bandwidth_runtime(cfs_b);      /* 1 runtime = quota */
    if (!throttled) { cfs_b->idle = 1; return 0; }   /* 下个 period 或空闲，可停表 */
    cfs_b->nr_throttled += overrun;
    while (throttled && cfs_b->runtime > 0) {    /* 2 放开锁分发，回来再检查 */
        runtime = cfs_b->runtime;
        raw_spin_unlock(&cfs_b->lock);
        runtime = distribute_cfs_runtime(cfs_b, runtime, runtime_expires);
        raw_spin_lock(&cfs_b->lock);
        throttled = !list_empty(&cfs_b->throttled_cfs_rq);
        cfs_b->runtime -= min(runtime, cfs_b->runtime);
    }
    cfs_b->idle = 0;

为什么要 while？distribute_cfs_runtime() 得放开 cfs_b->lock（它要拿各 CPU 的 rq 锁），空档期会有别的路径往池子里加时间、或又 throttle 了新队列，得重新检查。注释也承认这种竞争会让本 period 稍微超发，但只在这种极端情况、量有限。cfs_b->idle 的语义：本 period 没有任何 cfs_rq 被 throttle，标记「空闲」，下个 period 还这样就停表。

c
    list_for_each_entry_rcu(cfs_rq, &cfs_b->throttled_cfs_rq, throttled_list) {
        rq_lock(rq, &rf);
        if (!cfs_rq_throttled(cfs_rq)) goto next;
        runtime = -cfs_rq->runtime_remaining + 1;    /* 1 补到刚好 > 0 */
        if (runtime > remaining) runtime = remaining;
        remaining -= runtime;
        cfs_rq->runtime_remaining += runtime;
        if (cfs_rq->runtime_remaining > 0) unthrottle_cfs_rq(cfs_rq);  /* 2 */
next:
        rq_unlock(rq, &rf);
        if (!remaining) break;
    }

补到正数才 unthrottle。补了还不够（欠太多）继续挂着，下个 period 再说。remaining 耗完就 break。公平性靠先来先得——被 throttle 早的排在链前面先拿到时间。不保证绝对公平，但保证不饿死。

slack timer：把没用完的还回去 #

cfs_rq 申请了 5ms，上面只有一个进程，跑 0.5ms 就睡了，整个 group se 被 dequeue。剩的 4.5ms 归谁？不还，这 4.5ms 就锁死在这队列里，而别的 CPU 上的 cfs_rq 会因为全局池只剩 4ms 申请不到 5ms、被 throttle——实际可用 8.5ms 却在那干等。

c
    s64 slack_runtime = cfs_rq->runtime_remaining - min_cfs_rq_runtime;   /* 1 */
    if (slack_runtime <= 0) return;
    if (cfs_b->quota != RUNTIME_INF &&
        cfs_rq->runtime_expires == cfs_b->runtime_expires) {
        cfs_b->runtime += slack_runtime;                                 /* 2 */
        /* we are under rq->lock, defer unthrottling using a timer */
        if (cfs_b->runtime > sched_cfs_bandwidth_slice() &&
            !list_empty(&cfs_b->throttled_cfs_rq))
            start_cfs_slack_bandwidth(cfs_b);                            /* 3 */
    }
    cfs_rq->runtime_remaining -= slack_runtime;                          /* 4 */
  1. min_cfs_rq_runtime 是 1ms。留一点在自己手里——队列马上会有任务，全还回去下次还得重新申请，白折腾。剩不到 1ms 就不还。 3. 开 slack_timer 有条件：池子里的时间够发一个最小切片（> 5ms），且确实有被 throttle 的在等。当前持有 rq 锁，不能直接 unthrottle（那要动别的 rq），推给定时器。 4. 无论还成功没有，本地额度都要减掉。注释直白：还不了也别再试第二次。

slack_timer 的回调 do_sched_cfs_slack_timer() 干三件事：runtime_refresh_within(cfs_b, min_bandwidth_expiration) 检查 period 定时器是不是马上到点（2ms 内），是就撒手让它刷；池子里时间够一个切片才继续；然后复用 distribute_cfs_runtime() 尽力而为，最后把实际发出去的量从 cfs_b->runtime 扣掉。

来源 位置 时机 上限
period 刷新 __refill_cfs_bandwidth_runtime() 每 period 重填为 quota
归还 __return_cfs_rq_runtime() cfs_rq 变空 本地余量减 1ms 后全还
分发 distribute_cfs_runtime() period 到点 / slack 到点 受 cfs_b->runtime 限制

5.10 的改动：distribute_cfs_runtime() 换了签名，只收 cfs_b，内部自己拿 cfs_b->lock 扣 cfs_b->runtime，不再传 remaining / expires、不再返回分发量；do_sched_cfs_period_timer() 里的 while 循环改成直接调一次。throttle_cfs_rq() 也从 void 改成返回 bool（勘误 15）。

二十一、用户组层级的限制与继承 #

text
max(c_i) <= C        每个子组不超过父组
\Sum(c_i) >= C        子组总和可以超过父组

第二条容易误解：允许超额配置，是故意的。父组 100%、三个子组各 60%，加起来 180%——只要不同时打满，这就是合理的资源规划。真超了，谁先抢到算谁的。

原因 谁超了 现象
自己超 quota 本组 cfs_rq->throttled = 1，throttle_count 增一
父组超 quota 祖先组 本组 throttled 还是 0，但 throttle_count > 0，一样跑不了

第二种情况下子组自己的 quota 还有富余，却必须等父组的下个 period。校验在 kernel/sched/core.c 的 tg_cfs_schedulable_down()：

c
        quota = normalize_cfs_quota(tg, d);
        parent_quota = parent_b->hierarchical_quota;
        if (cgroup_subsys_on_dfl(cpu_cgrp_subsys)) {
            quota = min(quota, parent_quota);       /* cgroup v2：静默夹紧 */
        } else {
            if (quota == RUNTIME_INF)               /* cgroup v1：继承 */
                quota = parent_quota;
            else if (parent_quota != RUNTIME_INF && quota > parent_quota)
                return -EINVAL;                     /* v1：直接报错 */
        }
    cfs_b->hierarchical_quota = quota;

两个版本语义不同：v1 上子组写超过父组的值直接返回 -EINVAL，写不进去；v2 静默取 min(自己, 父组)。两个版本写 max（不限）都继承父组 quota。v1 报错、v2 静默夹紧，写配置脚本时这个差别会咬人。hierarchical_quota 是算完继承后的最终配额，上层算完下层才能用，所以 walk_tg_tree() 从根往下走。

二十二、一个完整的使用举例（cgroup v1 cpu.max / cpu.cfs_quota_us） #

先纠个容易混的地方：cpu.max 是 cgroup v2 的文件名，v1 里叫 cpu.cfs_quota_us + cpu.cfs_period_us。

v1 文件 含义 默认 合法范围
cpu.cfs_quota_us 一个 period 内的限额 -1（不限） -1 或 ≥1ms
cpu.cfs_period_us 周期 100000（100ms） 1ms ~ 1000ms
cpu.shares 组权重 1024 2 ~ 262144
cpu.stat 统计 — 只读
cpu.rt_runtime_us / cpu.rt_period_us RT 组带宽 — 需 CONFIG_RT_GROUP_SCHED

cgroup v2 对照：cpu.max 收 "quota period" 两个字段（quota 可写 max），单位微秒；cpu.weight 是 1 ~ 10000、默认 100，换算关系 weight = shares × 100 / 1024；cpu.stat 里 throttled_time（ns）变成 throttled_usec（µs）。cpu.shares 的范围来自 MIN_SHARES = 2、MAX_SHARES = 1 << 18 = 262144；v2 的默认 100 对应 shares = 1024，写 10000 对应 shares = 102400——上限比 v1 松，但是另一套刻度。

bash
# 限到 100%（一个 CPU 的算力）
echo 250000 > cpu.cfs_quota_us
echo 250000 > cpu.cfs_period_us

# 限到 200%（多核）
echo 1000000 > cpu.cfs_quota_us
echo 500000 > cpu.cfs_period_us

# 限到 20%
echo 10000 > cpu.cfs_quota_us
echo 50000 > cpu.cfs_period_us

# v2 上写同样的 20%，再取消限制
echo "10000 50000" > cpu.max
echo max > cpu.max
目标 quota period 比例 特点
100%（1 核） 250ms 250ms 1.0 常规
200%（2 核） 1000ms 500ms 2.0 靠 quota > period 实现
20% 10ms 50ms 0.2 周期短，延迟低

两条调参经验，都是原文结论：period 越大，吞吐越高（每次 throttle/unthrottle 都有开销，稀一点开销少），代价是超支时一次被停更久、抖动大；period 越小，延迟越低（任务最多等一个 period 就能重新拿到时间片），代价是切换频繁。

quota 和 period 都能到 1000ms 上限，但 quota 是「每 period 多少时间」，允许超过 period（200% 那个例子），所以两个上限是不同约束：period 卡在 1s，quota 只受「至少 1ms」这一侧限制。 cpu.stat 输出 nr_periods、nr_throttled、throttled_time 三行。nr_throttled / nr_periods 就是超支概率：nr_throttled 接近 nr_periods 说明 quota 设小了，任务长期在限额边缘；只有零星几次，说明是偶发峰值。throttled_time 单位 ns（v1），看趋势。v2 上同一份信息叫 throttled_usec，别拿 ns 的数去跟时间戳比。切片默认 5000 微秒，路径 /proc/sys/kernel/sched_cfs_bandwidth_slice_us。调大，申请次数少、开销低，但粒度粗——一个 cfs_rq 会一次攥住一大块，别的 CPU 上的队列申请不到就被 throttle；调小反之。

检查项 为什么
CONFIG_FAIR_GROUP_SCHED / CONFIG_CFS_BANDWIDTH 都开了 少一个，cpu.cfs_quota_us 文件不存在
quota 单位是微秒 写 1000 是 1ms，不是 1s
quota 绝对值不小于 1ms 小于会被 tg_set_cfs_bandwidth() 拒掉
父组 quota 别比子组还小 v1 报 -EINVAL，v2 静默夹紧
cpu.shares 别写 0 范围 2 ~ 262144，0 不合法

顺带说清一个机制：新任务属于哪个组是 fork 时由 cpu_cgroup_fork() 定的，比 sched_fork() 早。所以「先 echo pid 到 tasks 再让它干活」和「先干活再 echo」效果完全不同——前者能真限住，后者已经被调度过了。

二十三、易错点速查 #

坑 表现 正解
把 vruntime 当实际时间 算出的时间片差几十上百倍 它是权重归一化后的值，跟实际时间差一个 NICE_0_LOAD / weight 的因子
忘了 for_each_sched_entity 是多层 组调度下只处理一层，权重账对不上 宏是 for (; se; se = se->parent)，组开时 N 层，关时退化成 1 层
