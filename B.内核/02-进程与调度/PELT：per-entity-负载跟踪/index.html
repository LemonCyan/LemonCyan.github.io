一、为什么需要 per-entity load tracking #

调度器的约束互相打架：必须公平，响应要快，throughput 要高，功耗要小。用户提需求时不管这些冲突，只要求全满足，而且不管系统负荷多重。所以 Linux 调度器这些年换了好几茬算法——2007 年 2.6.23 引入 CFS 之后相对稳定，最近一次大改是 3.8 合入的 per-entity load tracking。调度器要真做对，前提是能预知未来：只有准确推测出每个任务对系统的需求，才谈得上调度、均衡、算力调整。硬件厂商卖 CPU 不负责预测进程负载，内核只能拿「过去」推「未来」。问题在于：内核一直在精确统计每个任务实际运行了多久，却不知道每个任务对系统负载贡献了多少。Paul Turner 提交 PELT 补丁集时专门回答过：

  • 任务即便没在 CPU 上跑，只是挂在 runqueue 上等，它照样对 CPU 负载有贡献。「负载」是瞬时量，描述当前这一刻施加多大压力。runqueue 挂 10 个待跑任务，压力显然大于只挂 1 个。
  • 「CPU 使用率（usage）」是累积量。一个跑了很久的进程上礼拜占满 CPU，今天几乎不占，它过去的「辉煌」对现在的系统负荷没有半点贡献。

3.8 之前，CFS 算 CPU load 时跟踪的是每个运行队列的负载（per-rq load tracking）。「运行队列」不止一个：至少每个 CPU 一个 rq，开了组调度之后每个 control group 在每个 CPU 上还有自己的 per-CPU rq。per-rq 能让调度器知道每个 rq 对整个系统贡献了多少，这点信息够组调度器在 control group 之间分时间。但站在整个系统角度，我们不知道负载来自哪里。

PELT 把跟踪从 per-rq 推进到 per-entity。「entity」指调度实体，实际是一个进程，或 control group 里的一组进程。跟踪分两个方向：

跟踪对象 用途
CPU / 任务的利用率（util） 给任务找算力匹配的 CPU；按 CPU util 决定升频还是降频
CPU / 任务的负载（load） 负载均衡：让每个 CPU 承担和它算力匹配的负载

手机平台最能说明问题：4 大核 + 4 小核。任务逻辑复杂、执行时间长，util 大，就该安排到算力匹配的大核；CPU 的 util 上来了就该提频。这些决策都要 per-entity 数据撑着，per-rq 的粗粒度数据顶不住。

二、per-rq 跟踪的三个毛病 #

看不到负载来源。 我们知道某个 rq 上负载是 3000，但不知道这 3000 由哪些任务贡献、每个占多少、当前算力撑不撑得住。要不要提频、要不要迁核，无从判断。工作负载稳定，统计值却在抖。 即使负载相对稳定，rq 级别跟踪出来的值波动也很大。rq 只有一个总量，任务进出、睡眠唤醒全砸在这上面，没有衰减也没有平滑，按它决策就会来回横跳。group 场景下 blocked load 无法区分。 开了 cgroup，一个 group se 底下只要有一个 se 是 runnable，group se 的 on_rq 就是 1。于是 rq 负载混进大量已睡眠任务留下的 blocked load，均衡器想均衡真正的 runnable load，却拿不到干净数据。这是 runnable_avg 存在的唯一理由，第七章还会撞上。一句话：per-rq 能告诉你「这口锅有多满」，告诉不了你「锅里都是什么」。而均衡和算力调整恰恰需要后者。

三、1024us 与衰减因子：PELT 的核心公式 #

这一段是三篇旧稿里重复了三次的核心描述，合并后只留这一处。时间被切成 1024us 的序列（物理时间，不是虚拟时间）。每个 1024us 周期里，一个 entity 对系统负载的贡献由它处于 runnable 状态的时间决定——runnable 指「正在 CPU 上跑」加「在 runqueue 里等着跑」。周期内 runnable 时间是 $x$，这一周期的贡献就是 x/1024。单个周期的贡献不超过 1024us，但把历史周期累加就会超过。累加时越久远的历史乘越大的衰减：

L=L0​+L1​y+L2​y2+L3​y3+⋯=n=0∑∞​Ln​yn

Ln​ 是周期 pn​ 的瞬时负载贡献，p0​ 是当前周期，p1​ 约 1ms 前，p2​ 约 2ms 前；$y$ 是衰减因子，$0<y<1$。这个级数的性质决定了整套实现：贡献值是序列之和；最近的负荷权重最大，权重为 1；过去的负荷照样累计，只是以指数递减的方式影响当前值。好处是算起来极便宜：不需要数组记录历史，把上一次的总贡献乘 $y$、加上新的 L0​ 就完事，util 和 runnable 用同一套递推。$y$ 由内核写死，依据是「一次合理调度周期的宽度」：

y32=0.5⇒y=0.51/32≈0.9785720621

32 个窗口之后（$32 \times 1024\text{us} = 32768\text{us} \approx 32.768\text{ms}$），历史贡献衰减到一半。这就是常说的「PELT 半衰期 32ms」——注意是 32.768ms，不是整数 32，算账别按整 32。有了 y32=0.5，任何 yn 都能拆成「折半部分 × 查表部分」：

yn=2−⌊n/32⌋⋅ynmod32

折半用右移，查表用一张 32 项定点数组。这就是第十六章 decay_load() 能做成常数时间的全部秘密。

四、load、利用率、runnable 三个量的区别 #

概念 时间口径 带不带权重 归一化 典型消费者
load（负载） runnable + running + blocked（衰减中） 带，乘 se->load.weight 不归一化到算力 负载均衡、组调度分时间
util（利用率） 只算 running 不带权重 归一到 1024（系统最大算力） schedutil 调频、EAS / 任务放置
runnable（可运行压力） runnable + running，不含 blocked task 不带权重；group 乘 runnable_weight 归一到 1024 判断 rq 是否真的过载

写开就是（$t$ 是周期内时间，1024 是满窗）：

loadi​=w×1024trunnable​​utili​=capmax​×1024trunning​​runnablei​=capmax​×1024trunnable+running​​

load 带权重。 CFS 里高优先级任务在一个调度周期能分到更多执行时间，同样跑满 1ms，权重 2048 施加的压力是权重 1024 的两倍，所以瞬时负载必须乘 load.weight。util 不带权重。 它要和 capacity 直接做减法（还剩多少余量），描述的是「占了多少算力」，跟任务是谁、优先级多少无关。手机环境里大核最高频的算力定义为 1024，其它 CPU 按微架构和最高频折算。util 天然有上限。runnable 是补丁。 load 里混着 blocked load，util 又只认 running，两个都不适合回答「这个 rq 上到底有几份压力在抢」。runnable 把「等着跑」的时间也算进压力，任务互相抢 CPU 时它明显高于 util。再看一个反例，说明为什么必须滑动平均：上个窗口任务满窗运行，瞬时 util 是 1024，调度器一脚把它迁到大核；下个窗口它有 3/4 时间阻塞，瞬时 util 掉到 256，又踢回小核。任务在大核小核间反复横跳，迁移开销比它干的活还多。所以瞬时量只作为 L0​ 喂进级数，给算法看的是级数收敛出的平均值。

五、时间怎么算：四个时钟与 rq_clock_pelt #

时钟 定义 关键行为
rq->clock 基于 sched clock 的时间轴，update_rq_clock() 驱动 物理时间，含 irq 时间
rq->clock_task 类似 clock，但执行 irq 时停走 只随任务执行前进，见 update_rq_clock_task()
rq->clock_pelt PELT 专用的归一化时间轴 按 capacity / freq 折算，rq 进 idle 时同步回 clock_task
cfs_rq_clock_pelt() 在 rq_clock_pelt 上扣掉被 throttle 的时间 5.2 起存在，带 CONFIG_CFS_BANDWIDTH 才有扣减

为什么单独一条归一化时钟：同样任务量在低算力 CPU 上要花更多物理时间。直接拿物理时间算，同一个任务在小核和大核会算出两个 util，EAS 和调频就没法比。所以 PELT 把执行时间归一化到「超大核最高频」上。代价是 idle 时间被压缩——归一化后的时间短，物理时间长，rq 一旦进 idle，clock_pelt 直接同步到 clock_task 抹平差值：

c
static inline void update_rq_clock_pelt(struct rq *rq, s64 delta)
{
	if (unlikely(is_idle_task(rq->curr))) {
		/* The rq is idle, we can sync to clock_task */
		rq->clock_pelt = rq_clock_task(rq);
		return;
	}
	/* Scale the elapsed time to reflect the real amount of computation */
	delta = cap_scale(delta, arch_scale_cpu_capacity(cpu_of(rq)));
	delta = cap_scale(delta, arch_scale_freq_capacity(cpu_of(rq)));
	rq->clock_pelt += delta;
}

cap_scale(v, s) = (v) * (s) >> SCHED_CAPACITY_SHIFT，shift 是 10。所以 capacity 512 的半血 CPU 跑在最高频上，10ms 物理时间只记 5ms 的 PELT 时间。对外的读接口还要再扣 lost_idle_time：

c
static inline u64 rq_clock_pelt(struct rq *rq)
{
	lockdep_assert_held(&rq->lock);
	assert_clock_updated(rq);
	return rq->clock_pelt - rq->lost_idle_time;
}

lost_idle_time 处理「满负载偷 idle」：rq 一直满负荷时归一化时钟会落后 clock_task，多出那段等于偷走了本该 idle 的时间。rq 变 idle 时 update_idle_rq_clock_pelt() 判断 util_sum 是否顶到上限（((LOAD_AVG_MAX - 1024) << SCHED_CAPACITY_SHIFT) - LOAD_AVG_MAX，rt 和 dl 的 util_sum 也算进去），顶到就把 rq_clock_task(rq) - rq->clock_pelt 记进 lost_idle_time。版本上注意三点：4.18 的 update_load_avg() 用 cfs_rq_clock_task()，没有 pelt 时钟，scale invariance 来自 2019-02 的补丁「sched/fair: Update scale invariance of PELT」，我在 v5.2 的 pelt.h 里已能看到完整实现，但没逐版核对 5.0 / 5.1；arch_scale_cpu_capacity() 的参数个数变过（5.2 是 (NULL, cpu)，5.10 是 (cpu)），照抄旧文章会编译不过；5.10 的 cfs_rq_clock_pelt() 扣 throttled_clock_task_time，6.12 里字段名换了一对，带宽节流属于 ③④ 的范围，本篇只到「被 throttle 的时间要从 pelt 时钟扣掉」这一层。

cfs_rq->load 加总有啥用？两个运算靠它：算 se 的时间片（se 时间片 = sched period × se 权重 / cfs rq 权重），以及算 cfs rq 自己的负载——没开组调度时 cfs_rq->load.weight 就等于挂在上面的所有 se 权重之和，跟单个 se 的算法能共用一套逻辑。

3、h_load：把 se 的负载换算成对 CPU 的贡献 #

均衡要在 CPU 之间搬 runnable load，所以得能比较「某个任务对某个 CPU 贡献了多少负载」。问题在于 task se 的 load_avg 是在它自己那一层算的，权重也是那一层的，不能直接反映它对 root cfs rq（也就是这个 CPU）的贡献。为此每个 cfs rq 上引入 hierarchy load：

text
下一层 cfs rq 的 h_load = 上一层 cfs rq 的 h_load × group se 在上一层 cfs 负载中的占比
task se 的 h_load = task se 的 load_avg × cfs rq 的 h_load / cfs rq 的 load_avg

顶层 cfs rq 的 h_load 就等于它自己的 load_avg。这两步把「任务对自己 cfs rq 的贡献」换算成「任务对 CPU runqueue 的贡献」。h_load 靠 h_load_next 串起来的链自顶向下刷新，last_h_load_update 控制频率。均衡算法怎么用这个值，在 ⑥。

4、struct load_weight 与 task group #

c

	unsigned long weight;
	u32 inv_weight;
};

weight 是权重本身，inv_weight 没有语义，纯粹为了把除法变成乘法（WMULT_CONST / weight，WMULT_SHIFT = 32）。load_weight 内嵌在 se 和 cfs rq 里，分别表示两级的权重。cfs rq 的权重会变，所以缓存值要失效——update_load_add/sub/set 每次都把 inv_weight 清 0，下次算时间片时由 __update_inv_weight() 重建（WMULT_CONST / scale_load_down(weight)，权重为 0 时退化成 WMULT_CONST）。task group（需 CONFIG_FAIR_GROUP_SCHED，细节在 ③④）：

成员 描述
css 对应的 control group 状态
se[] / cfs_rq[] 系统有 N 个 CPU，就有 N 个 se、N 个 cfs rq
shares 该 group 能分到的 CPU 比例，和 task se 的权重对等。但 group se 有 N 个，share 得按规律摊到这 N 个上

load_avg 这个成员看着突兀：task group 作为整体参与竞争，但它是一组 se 的集合，没法在单个 CPU 上被调度，所以权重必须摊到各 CPU 的 group se 上。摊法不是平均分——各 CPU 上挂的任务情况不同。直觉是按各 group cfs rq 的权重占比分，calc_group_shares() 干的就是这件事，实际代码里为了少做除法把权重换成了 load_avg，细节自行阅读。

5、两种形态与两个方向的指针 #

不支持组调度时，每个任务内嵌一个 sched_entity，就是 task se；每个 CPU rq 内嵌调度类自己的 rq，CFS 就是 cfs_rq。runnable 的任务按 vruntime 挂进红黑树。任务阻塞后从红黑树摘下来，但从 PELT 的角度看它仍然挂在 cfs rq 上——负载（blocked load）继续累计到原来那个 cfs rq 并按规则衰减。这条虚线关系是理解 blocked load 的关键。支持组调度时，cfs_rq — se 这个基本件拼成层级：task group 整体作为调度实体参与调度，于是对应一个 se。这话对 UP 成立；SMP 下任务组里的任务散落在各 CPU 上，所以 task group 实际对应的是一组 se，叫 group se。顶层是虚拟的 root task group，它没有对应的 group se（都顶层了，不需要挂到别人的 cfs rq 里），它的 cfs rq 内嵌在 CPU rq 中。group se 有两个关联的 cfs rq，这两个取法必须分清，混了就全乱：

c
static inline struct cfs_rq *cfs_rq_of(struct sched_entity *se)
{
	return se->cfs_rq;
}

static inline struct cfs_rq *group_cfs_rq(struct sched_entity *grp)
{
	return grp->my_q;
}

cfs_rq_of(se) 是这个 se 挂入的队列，往上走；group_cfs_rq(se) 是这个 se 拥有的队列，往下走。PELT 的传播就在这两者之间来回：先把负载算到 group_cfs_rq(se)，再同步到 cfs_rq_of(se)。

成员 描述
last_update_time 上次更新时间点，和当前时间一减就是 delta。两种特殊情况清 0：任务迁移到新 CPU（让新 CPU 从零对齐）、新建任务的 se
load_sum 几何级数累加值，1ms 一个周期，越远衰减越狠，32 周期后减半。只考虑时间因素，包含 running + runnable
runnable_load_sum 同上，口径是 running + runnable 且带 runnable 权重（group se 上等于任务个数）。blocked 期间不再累加
util_sum 只统计 running 时间的累加值
period_contrib 中间变量，记录上次更新时没凑满 1024us 的尾巴（d3），下次更新时当 d1 用
load_avg / runnable_load_avg / util_avg 分别由上面三个 sum 算出的平均值
util_est 4.17 引入，见第十八章。记录阻塞前的 util 估值，防睡久了 util 衰减到接近 0 导致误判

2、三个 avg 的公式 #

由 sum 换算成 avg 时分母不是 LOAD_AVG_MAX，而是「当前窗口位置下几何级数的最大值」：

load_avg=Dload⋅load_sum​,runnable_avg=Drunnable⋅runnable_sum​,util_avg=Dutil_sum​

其中 $D = LOAD_AVG_MAX - 1024 + period_contrib$。LOAD_AVG_MAX 是 47742（怎么来的见第十六章），减 1024 得 46718。为什么减：满窗的 sum 上限不是 LOAD_AVG_MAX，而 LOAD_AVG_MAX * y == LOAD_AVG_MAX - 1024，当前窗口还没走完的部分要扣掉，否则会把「还没过去的时间」当 idle，util_avg 会在 1002~1024 之间抖。对 task se 来说 load_avg 和 runnable_load_avg 相等（load_sum == runnable_load_sum，load.weight == runnable_weight），值不超过 se->load.weight。跑得越满越频繁越接近权重上限：权重 1024 长期跑满贴着 1024 收敛，「跑 1ms、睡 9ms」的周期任务卡在高低两个峰值之间来回。这个曲线形状本身就是「任务有多繁重」的刻画，均衡器拿它算迁移收益才有依据。

3、5.7 之后的改名与语义变化 #

照 4.18 的字段名去读 6.x 会直接对不上。核对了 kernel/sched/pelt.c 两个版本：

项目 4.18 / 5.6 5.7 起
结构体字段 runnable_load_sum / runnable_load_avg runnable_sum / runnable_avg
accumulate_sum() 原型 (delta, cpu, sa, load, runnable, running) (delta, sa, load, runnable, running)，cpu 删掉
util 归一化 contrib * scale_cpu，再 cap_scale(contrib, scale_freq) 直接 contrib << SCHED_CAPACITY_SHIFT，归一化交给 rq_clock_pelt
___update_load_avg() (sa, load, runnable) 三个参数 (sa, load) 两个
语义 runnable 带权重，本质还是 load runnable 压力，不带权重，量纲同 util

改动动机写在提交信息里：runnable_load_avg 已在之前的补丁里被删掉，腾出位置放一个「标出 rq 上 runnable 压力」的新信号。当时判断 rq 是否过载只看 util_avg（util 超过约 80% 且任务数大于 1 就算过载），但任务刚迁走时 util_avg 会短暂掉下去，分类就偏了。任务抢 CPU 时 runnable 因含等待时间会高于 util，用它更稳。所以讨论 4.18 必须说 runnable_load_avg（带权重），讨论 5.7 之后必须说 runnable_avg（不带权重、含等待时间）。混着说是这类文章最常见的错法。

八、一个 entity 的负载怎么初始化 #

分两阶段：建 se 时（task 在 fork，group 在创建 cgroup），唤醒新 se 时。group se 不会被唤醒，所以第二阶段只对 task se 适用。

1、第一阶段：init_entity_runnable_average #

c
void init_entity_runnable_average(struct sched_entity *se)
{
	struct sched_avg *sa = &se->avg;
	memset(sa, 0, sizeof(*sa));
	/*
	 * Tasks are intialized with full load to be seen as heavy tasks until
	 * they get a chance to stabilize to their real load level.
	 * Group entities are intialized with zero load to reflect the fact that
	 * nothing has been attached to the task group yet.
	 */
	if (entity_is_task(se))
		sa->runnable_load_avg = sa->load_avg = scale_load_down(se->load.weight);
	se->runnable_weight = se->load.weight;
	/* when this task enqueue'ed, it will contribute to its cfs_rq's load_avg */
}
对象 load_avg / runnable_load_avg 理由
task se scale_load_down(se->load.weight)，即拉到最大 新任务先当重载任务看，跑起来再靠衰减收敛到真实值。初始化为 0 会让它一开始被当轻任务，容易被塞到不合适的小核上
group se 0 表示这个 task group 上还没有任何任务附着

load_sum / util_sum 一律清 0，last_update_time 也是 0——0 是哨兵值，update_load_avg() 靠它判断「这个 se 是新的，需要 attach，不要做常规更新」。

2、第二阶段：post_init_entity_util_avg #

新任务的 util_avg 设成 0 不合适，它该跟挂入的 cfs 队列负载和 CPU 算力挂钩。可建 se 时根本不知道它会挂到哪个 cfs rq，只能挪到唤醒时做：

c
void post_init_entity_util_avg(struct sched_entity *se)
{
	struct cfs_rq *cfs_rq = cfs_rq_of(se);
	struct sched_avg *sa = &se->avg;
	long cap = (long)(SCHED_CAPACITY_SCALE - cfs_rq->avg.util_avg) / 2;
	if (cap > 0) {
		if (cfs_rq->avg.util_avg != 0) {
			sa->util_avg  = cfs_rq->avg.util_avg * se->load.weight;
			sa->util_avg /= (cfs_rq->avg.load_avg + 1);
			if (sa->util_avg > cap)
				sa->util_avg = cap;
		} else {
			sa->util_avg = cap;
		}
	}
	...
	attach_entity_cfs_rq(se);
}

主公式就是老出现的那条，分母 +1 防除零：

text
util_avg = cfs_rq->util_avg / (cfs_rq->load_avg + 1) * se.load.weight

cfs rq 的 util_avg 本身是 0（比如 CPU 刚起来）时算出来也是 0，同样不合理，这时退化成 cap = (1024 - util_avg) / 2，即「剩余算力的一半」。代码里还有一层上限，注释写得很清楚：

text
util_avg_cap = (1024 - cfs_rq->avg.util_avg) / 2^n        n 是第 n 个任务
 task  util_avg: 512, 256, 128,  64,  32,   16,    8, ...
cfs_rq util_avg: 512, 768, 896, 960, 992, 1008, 1016, ...

没这个上限，按公式外推的 util 之和会发散（调和级数就是典型反例），几个任务一叠就把 CPU 顶成 200%。最后 attach_entity_cfs_rq(se) 把 se 塞进 PELT 层级：不只是把 load_avg 加到 cfs rq，还要沿 cfs_rq — se 逐层往上传播，同时计入 task group。

九、tick 中怎么更新 #

tick 命中时任务状态没变，还是 running，但为了让跟踪跟上必须更新。入口是 entity_tick()：

c
static void
entity_tick(struct cfs_rq *cfs_rq, struct sched_entity *curr, int queued)
{
	update_curr(cfs_rq);
	update_load_avg(cfs_rq, curr, UPDATE_TG);
	update_cfs_group(curr);
	...
}

层次递进：从叶子的 task se 往上，每层调 entity_tick()，更新该层的 se 和 cfs rq——更新本层 se 的负载（__update_load_avg_se()）；更新该 se 挂入的 cfs rq 的负载（update_cfs_rq_load_avg()）；如果是 group se 且层级结构有变化（增删 se），处理向上传播（tick 场景没有这步）；更新本层 task group 的负载以及对 tg 负载的贡献（update_tg_load_avg()），算 tg 的 load_avg 是为了后面算 group se 的权重。update_cfs_group() 紧跟其后：找到该 group se 所属的 cfs rq → calc_group_shares() 算权重 → reweight_entity() 重设权重并按新值更新负载。这一步只动 load_sum / load_avg，runnable_sum / util_sum 跟权重无关，不用动——这是「权重只影响 load、不影响 util」的直接体现。

十、任务睡眠时怎么更新 #

睡眠走 dequeue_task_fair()，是 enqueue_task_fair() 的逆过程，同样自叶向根逐层推进，每层调 dequeue_entity()。但不是每层都真调——必须该 group se 底下子树里所有任务都阻塞了才会调到那一层。

c
static void
dequeue_entity(struct cfs_rq *cfs_rq, struct sched_entity *se, int flags)
{
	/*
	 * When dequeuing a sched_entity, we must:
	 *   - Update loads to have both entity and cfs_rq synced with now.
	 *   - Substract its load from the cfs_rq->runnable_avg.
	 *   - Substract its previous weight from cfs_rq->load.weight.
	 *   - For group entity, update its weight to reflect the new share
	 *     of its group cfs_rq.
	 */
	update_load_avg(cfs_rq, se, UPDATE_TG);
	se_update_runnable(se);
	update_stats_dequeue(cfs_rq, se, flags);
	account_entity_dequeue(cfs_rq, se);
	update_cfs_group(se);
}
步骤 干什么 为什么
update_load_avg(cfs_rq, se, UPDATE_TG) 状态变了，更新本层 se 及其 cfs rq 的负载 把最后这段 running 时间记进去
se_update_runnable(se) 更新 group se 的 runnable_weight 有任务阻塞了，group 的 runnable 数量变了
account_entity_dequeue() 把 se 的权重从 cfs_rq->load.weight 里减掉 权重是队列的静态账
update_cfs_group(se) 重算 group se 的权重 队列权重变了，share 摊法跟着变

注意这里没有把 load_avg 从 cfs rq 里扣掉。任务睡了，但它对 cfs rq 的 load_avg 贡献还在，只是随睡眠时间衰减。这就是 blocked load，也是第六章那条「虚线」在代码里的落点。account_entity_dequeue() 的真实实现减的是 runnable 那一份：

c
static inline void
dequeue_runnable_load_avg(struct cfs_rq *cfs_rq, struct sched_entity *se)
{
	cfs_rq->runnable_weight -= se->runnable_weight;
	sub_positive(&cfs_rq->avg.runnable_load_avg, se->avg.runnable_load_avg);
	sub_positive(&cfs_rq->avg.runnable_load_sum,
		     se_runnable(se) * se->avg.runnable_load_sum);
}

sub_positive() 保证减不到负数（饱和减法），这类累计量的标准写法，别拿普通减法去理解。

十一、任务唤醒时怎么更新 #

1、先看要不要迁 #

唤醒后还是 previous CPU 就什么都不用做。换了 CPU 就是一次迁移，走 migrate_task_rq_fair()：

c
static void migrate_task_rq_fair(struct task_struct *p)
{
	...
	if (p->on_rq == TASK_ON_RQ_MIGRATING) {
		lockdep_assert_held(&task_rq(p)->lock);
		detach_entity_cfs_rq(&p->se);
	} else {
		/*
		 * ... we have difficulty in getting what current time is, so simply
		 * throw away the out-of-date time. This will result in the
		 * wakee task is less decayed, but giving the wakee more load
		 * sounds not bad.
		 */
		remove_entity_load_avg(&p->se);
	}
	/* Tell new CPU we are migrated */
	p->se.avg.last_update_time = 0;
	/* We have migrated, no longer consider this task hot */
	p->se.exec_start = 0;
}

两个关键动作：remove_entity_load_avg() 把该任务的负载从旧 CPU 的 cfs rq 摘掉（开组调度时要沿 PELT 层级逐层减；为了不打乱锁顺序，函数只把要减的量记到 cfs_rq->removed，真正的扣减放到该 cfs rq 下次负载更新时做）；last_update_time = 0 是迁移标志位，新 CPU 的 cfs rq 一看这个 0 就知道要 attach，而不是做常规时间差更新。旧 CPU 那段历史已经结清并跟着搬过来了，新 CPU 不用再算一遍。

2、再入队 #

入队走 enqueue_task_fair()，同样自叶向根。中间节点（group se）要判断自己是否已在 rq 上：se->on_rq == 0 才调 enqueue_entity()；se->on_rq == 1 说明子树里至少有一个 runnable 或 running 的 se，不需要入队动作，直接 update_load_avg() + update_cfs_group()（过程和 tick 一样）。

c
static void
enqueue_entity(struct cfs_rq *cfs_rq, struct sched_entity *se, int flags)
{
	/*
	 * When enqueuing a sched_entity, we must:
	 *   - Update loads to have both entity and cfs_rq synced with now.
	 *   - Add its load to cfs_rq->runnable_avg
	 *   - For group_entity, update its weight to reflect the new share of
	 *     its group cfs_rq
	 *   - Add its new weight to cfs_rq->load.weight
	 */
	update_load_avg(cfs_rq, se, UPDATE_TG | DO_ATTACH);
	se_update_runnable(se);
	update_cfs_group(se);
	account_entity_enqueue(cfs_rq, se);
}

跟 tick 比多了 DO_ATTACH：这次入队会伴随 PELT 层级结构变化（迁移），需要触发负载传播。

3、attach_entity_load_avg #

last_update_time == 0 且带 DO_ATTACH 就进 attach 分支：

c
static void attach_entity_load_avg(struct cfs_rq *cfs_rq, struct sched_entity *se, int flags)
{
	u32 divider = LOAD_AVG_MAX - 1024 + cfs_rq->avg.period_contrib;
	se->avg.last_update_time = cfs_rq->avg.last_update_time;
	se->avg.period_contrib = cfs_rq->avg.period_contrib;
	se->avg.util_sum = se->avg.util_avg * divider;
	se->avg.load_sum = divider;
	if (se_weight(se)) {
		se->avg.load_sum =
			div_u64(se->avg.load_avg * se->avg.load_sum, se_weight(se));
	}
	se->avg.runnable_load_sum = se->avg.load_sum;
	enqueue_load_avg(cfs_rq, se);
	cfs_rq->avg.util_avg += se->avg.util_avg;
	cfs_rq->avg.util_sum += se->avg.util_sum;
	add_tg_cfs_propagate(cfs_rq, se->avg.load_sum);
	cfs_rq_util_change(cfs_rq, flags);
}

这其实是「反解」：手上只有 load_avg / util_avg（迁移带过来的或第一阶段初始化好的），要反算回 *_sum。路径是先用 cfs rq 的窗口位置对齐（把 last_update_time 和 period_contrib 抄过来），再乘 divider——代码里写成先令 load_sum = divider 再乘 load_avg / weight，避免直接做除法。

c
static inline void
enqueue_load_avg(struct cfs_rq *cfs_rq, struct sched_entity *se)
{
	cfs_rq->avg.load_avg += se->avg.load_avg;
	cfs_rq->avg.load_sum += se_weight(se) * se->avg.load_sum;
}

static inline void
enqueue_runnable_load_avg(struct cfs_rq *cfs_rq, struct sched_entity *se)
{
	cfs_rq->runnable_weight += se->runnable_weight;
	cfs_rq->avg.runnable_load_avg += se->avg.runnable_load_avg;
	cfs_rq->avg.runnable_load_sum += se_runnable(se) * se->avg.runnable_load_sum;
}

load_avg 入队加、出队不减，所以 cfs rq 的 load_avg 是 runnable + blocked 之和。runnable_load_avg 入队加、出队减，只含 runnable 那部分。这一加一减的差别，就是第七章那三个量在代码里的分界线。se_runnable() / se_update_runnable() 是 5.7 一并加进来的：

c
static inline void se_update_runnable(struct sched_entity *se)
{
	if (!entity_is_task(se))
		se->runnable_weight = se->my_q->h_nr_running;
}

static inline long se_runnable(struct sched_entity *se)
{
	if (entity_is_task(se))
		return !!se->on_rq;
	else
		return se->runnable_weight;
}

只有 group se 需要 runnable_weight，值就是它拥有的那个 cfs rq 上的任务数。task se 的 runnable 退化成 !!on_rq（0 或 1），因为一个任务要么在跑/等，要么不在。

十二、负载与利用率怎么从叶子传播到根 #

新 task se 加入层级，负载要逐层累计到各级 group se 直到顶层 cfs rq。任务跨 CPU 迁移、跨 cgroup 移动，PELT 层级变了，同样要传播。触发点在 update_load_avg() 里那段 if (!se->avg.last_update_time && (flags & DO_ATTACH))：attach_entity_load_avg() 把 se 的 load / runnable / util 加到 cfs rq 上，再调 add_tg_cfs_propagate() 启动传播。完整路径：

  1. 确定 task se 的负载（唤醒迁移场景不需要再更新）；
  2. 找到该 se 挂入的 cfs rq，把负载计入，并把「待向上传播的量」记进 prop_runnable_sum；
  3. 把负载计入它所属的 task group（update_tg_load_avg()）；
  4. 底层的账平了，往上走一层，先更新 group se 的负载；
  5. 更新上一层 cfs rq 的负载，同时把下一层记下的传播量搬上来；
  6. 子 cfs rq 和父 group se 是「同一个东西的两个视角」，两者的值必须对齐。
c
static inline int propagate_entity_load_avg(struct sched_entity *se)
{
	...
	add_tg_cfs_propagate(cfs_rq, gcfs_rq->prop_runnable_sum);
	update_tg_cfs_util(cfs_rq, se, gcfs_rq);
	update_tg_cfs_runnable(cfs_rq, se, gcfs_rq);
	update_tg_cfs_load(cfs_rq, se, gcfs_rq);
	...
}

第 6 步有个已知的近似：group entity 和 group rq 的 PELT 窗口并不严格对齐，所以三个 update_tg_cfs_* 都是「拷贝 + 差值补偿」，不是精确同步：

函数 做的事
update_tg_cfs_util() group se 的 util 跟随其子 cfs rq 的 util，差值加到 group se 挂入的 cfs rq
update_tg_cfs_runnable() 同上，处理 runnable（5.7 起是 runnable_avg；4.18 是 runnable_load_avg）
update_tg_cfs_load() 同上，处理 load。这个最复杂，load 带权重、父子两级权重不同，要按比例换算

第 7 步更新上一层 task group 的负载，然后重复 4~7 直到顶层。prop_runnable_sum 这名字有点误导：它搬的不只是 runnable，是「这一层需要往上传的负载总和」。往上传的量最终进入 task group 的 load_avg，后者又回头决定各 CPU 上 group se 的权重——一个环。遇到看不懂的权重变化，先看是不是 update_cfs_group() 被传播触发了。

十三、update_load_avg 的完整流程 #

c
static inline void update_load_avg(struct cfs_rq *cfs_rq, struct sched_entity *se, int flags)
{
	u64 now = cfs_rq_clock_pelt(cfs_rq);
	int decayed;
	if (se->avg.last_update_time && !(flags & SKIP_AGE_LOAD))
		__update_load_avg_se(now, cfs_rq, se);          /* A */
	decayed  = update_cfs_rq_load_avg(now, cfs_rq);         /* B */
	decayed |= propagate_entity_load_avg(se);
	if (!se->avg.last_update_time && (flags & DO_ATTACH)) { /* C */
		attach_entity_load_avg(cfs_rq, se);
		update_tg_load_avg(cfs_rq);
	} else if (decayed) {                                   /* D */
		cfs_rq_util_change(cfs_rq, 0);
		if (flags & UPDATE_TG)
			update_tg_load_avg(cfs_rq);
	}
}

A：last_update_time 为 0 就跳过 se 的更新，因为值已设定好。两种 0：新 fork 的 task se（init_entity_runnable_average() 设成 0，缺省值就是对的）；刚迁移来的 se（旧负载已在旧 CPU 结清，新 CPU 只需 sync）。SKIP_AGE_LOAD 是「丢掉旧账」的开关——CFS 任务短暂切成 RT 又切回来，原来的负载认不认，这个 flag 说了算。B：更新 cfs rq 的负载，再把新 se 带来的负载在整个层级传播。C：enqueue_entity() 会带 DO_ATTACH。同时 last_update_time == 0 就是迁移场景，执行 attach：把 se 的平均负载加进 cfs rq 并向上传播。D：decayed 为真说明这次跨过了至少一个 1ms 的 PELT 窗口，*_avg 真的变了（没跨窗口时只更新 *_sum）。只有 avg 真变了才需要通知 cpufreq，cfs_rq_util_change() 会拉起 cpufreq_update_util()。UPDATE_TG 控制要不要顺手更新 task group 的负载——调用方在外面自己会调的话这里就不重复做。

4.18 的同名函数只差三处：now 用 cfs_rq_clock_task(cfs_rq)、__update_load_avg_se() 多传一个 cpu、___update_load_avg() 多一个 runnable 参数，分支结构一致。这一行就是 scale invariance 引入前后的分水岭：4.18 靠 accumulate_sum() 里的 cap_scale() 做容量归一化，5.10 把这活儿挪到了时钟里。

什么时候会调到 update_load_avg #

调用点 flag 场景

十四、__update_load_avg_se 与 __update_load_avg_cfs_rq #

两个函数逻辑基本一致：先 ___update_load_sum() 求 sum，跨窗口了再 ___update_load_avg() 求 avg，差别全在传参。

c
static int
__update_load_avg_se(u64 now, int cpu, struct cfs_rq *cfs_rq, struct sched_entity *se)
{
	if (entity_is_task(se))
		se->runnable_weight = se->load.weight;
	if (___update_load_sum(now, cpu, &se->avg, !!se->on_rq, !!se->on_rq,
				cfs_rq->curr == se)) {

		return 1;
	}
	return 0;
}

				scale_load_down(cfs_rq->runnable_weight),

十五、accumulate_sum：三个区间与累计 #

这个函数算三样东西：调度实体（task se / group se）的 *_sum、cfs rq 的 *_sum、rt / dl / irq / thermal pressure 的 *_sum。逻辑一样，拿 se 举例：一个 se 经历了 delta 时间，这段时间里它的状态（load / runnable / running）决定怎么累计。

1、delta 切成三段 #

text
      d1          d2           d3
      ^           ^            ^
      |           |            |
    |<->|<----------------->|<--->|
|---x---|------| ... |------|-----x (now)
                           p-1
 u' = (u + d1) y^p + 1024 \Sum y^n + d3 y^0
                           n=1
    = u y^p +                              (Step 1)
                     p-1
      d1 y^p + 1024 \Sum y^n + d3 y^0      (Step 2)
                     n=1
段 含义
d1 上次更新时没凑满一个周期的剩余时间，也就是上次的 d3。它加上本次的一小段，正好拼成完整窗口
d2 本次跨越的整数个周期
d3 本次最后没凑满一个周期的剩余，写回 period_contrib，留给下一次当 d1
u′=(u+d1​)yp+1024n=1∑p−1​yn+d3​,p=1+1024d2​​

没跨窗口：delta 加 period_contrib 连 1024us 都不到，只把 delta 累到 period_contrib 上，返回 0，*_avg 不更新——*_sum 也不衰减，还没到该衰减的时候。跨一个窗口：decay_load() 把旧 sum 衰减 1 个窗口（Step 1），__accumulate_pelt_segments() 处理 d1​+d3​（Step 2）。跨 n 个窗口：旧 sum 衰减 n 个窗口，d1 衰减 n 个窗口，d2 折算成 (n−1) 个满窗的 sum。

2、代码 #

4.18 / 5.6 的实现（带 cpu，容量归一化在函数内做）：

c
static __always_inline u32
accumulate_sum(u64 delta, int cpu, struct sched_avg *sa,
	       unsigned long load, unsigned long runnable, int running)
{
	unsigned long scale_freq, scale_cpu;
	u32 contrib = (u32)delta; /* p == 0 -> delta < 1024 */
	u64 periods;
	scale_freq = arch_scale_freq_capacity(cpu);
	scale_cpu = arch_scale_cpu_capacity(NULL, cpu);
	delta += sa->period_contrib;                                 /* 1 */
	periods = delta / 1024; /* A period is 1024us (~1ms) */      /* 2 */
	/*
	 * Step 1: decay old *_sum if we crossed period boundaries.
	 */
	if (periods) {
		sa->load_sum = decay_load(sa->load_sum, periods);        /* 3 */
		sa->runnable_load_sum = decay_load(sa->runnable_load_sum, periods);
		sa->util_sum = decay_load((u64)(sa->util_sum), periods);
		/*
		 * Step 2
		 */
		delta %= 1024;
		contrib = __accumulate_pelt_segments(periods,            /* 4 */
				1024 - sa->period_contrib, delta);
	}
	sa->period_contrib = delta;                                  /* 5 */
	contrib = cap_scale(contrib, scale_freq);
	if (load)
		sa->load_sum += load * contrib;
	if (runnable)
		sa->runnable_load_sum += runnable * contrib;
	if (running)
		sa->util_sum += contrib * scale_cpu;
	return periods;
}
  1. 先把 period_contrib 补进 delta，这样「上次的尾巴 + 这次的头部」能拼成完整窗口；
  2. 算出跨了几个窗口；
  3. 有跨窗口才衰减旧 sum（Step 1）；
  4. 算 Step 2：d1 = 1024 - period_contrib（上次剩下的那段），d3 = delta % 1024（本次剩下的那段）；
  5. period_contrib 更新为本次的 d3，留给下一次。

最后三行按状态累加，contrib 先按 freq 归一化，util 再按 CPU 算力归一化。这三个 if 是 PELT 里「状态 → 数量」的唯一入口：load 有值才累 load，runnable 有值才累 runnable，running 有值才累 util。任务睡着时三个都不为真，sum 只衰减不增长。

5.7 起的版本：签名去掉 cpu，字段改名 runnable_sum，contrib 只在 load 非 0 时才计算（!load 时 runnable 和 running 都被清 0，算了白算），归一化从 cap_scale 换成 contrib << SCHED_CAPACITY_SHIFT——具体缩放已由 rq_clock_pelt 在时间轴上做完。

十六、decay_load：衰减怎么算 #

1、先看 ___update_load_sum #

c
static __always_inline int
___update_load_sum(u64 now, int cpu, struct sched_avg *sa,
		  unsigned long load, unsigned long runnable, int running)
{
	u64 delta;
	delta = now - sa->last_update_time;
	delta >>= 10;                                                       /* 1 */
	if (!delta)
		return 0;
	sa->last_update_time += delta << 10;                                /* 2 */
	if (!load)
		runnable = running = 0;
	if (!accumulate_sum(delta, cpu, sa, load, runnable, running))       /* 3 */
		return 0;
	return 1;
}
  1. delta 单位是 ns，右移 10 位转成约 us（1024ns）。PELT 最小计量单位是 us，差不到 1us 直接返回；
  2. last_update_time 按量化后的粒度推进（delta << 10）而不是直接赋 now——时间轴不会被零头污染，多次调用能对齐到同一粒度；
  3. 返回跨过的周期数，0 表示没跨窗口，*_avg 不需要更新。

if (!load) runnable = running = 0; 有故事：runnable 是 running 的超集，runnable 为 0 时 running 不该为真。但存在「cfs_rq->curr 已 dequeue、却还指着它」的边界情况（比如 idle_balance() 里调 update_blocked_averages()），这时 weight 是 0 但 running 标志还在。这行把脏状态清掉。

2、再算平均 #

c
static __always_inline void
___update_load_avg(struct sched_avg *sa, unsigned long load, unsigned long runnable)
{
	u32 divider = LOAD_AVG_MAX - 1024 + sa->period_contrib;
	/*
	 * Step 2: update *_avg.
	 */
	sa->load_avg = div_u64(load * sa->load_sum, divider);
	sa->runnable_load_avg =	div_u64(runnable * sa->runnable_load_sum, divider);
	WRITE_ONCE(sa->util_avg, sa->util_sum / divider);
}

5.10 里 divider 抽成了 get_pelt_divider(sa)（就是 LOAD_AVG_MAX - 1024 + period_contrib），runnable_avg 不再乘 runnable 权重。

3、decay_load #

c
/*
 * Approximate:
 *   val * y^n,    where y^32 ~= 0.5 (~1 scheduling period)
 */
static u64 decay_load(u64 val, u64 n)
{
	unsigned int local_n;
	if (unlikely(n > LOAD_AVG_PERIOD * 63))                              /* 1 */
		return 0;
	/* after bounds checking we can collapse to 32-bit */
	local_n = n;
	/*
	 * As y^PERIOD = 1/2, we can combine
	 *    y^n = 1/2^(n/PERIOD) * y^(n%PERIOD)
	 * With a look-up table which covers y^n (n<PERIOD)
	 *
	 * To achieve constant time decay_load.
	 */
	if (unlikely(local_n >= LOAD_AVG_PERIOD)) {                           /* 2 */
		val >>= local_n / LOAD_AVG_PERIOD;
		local_n %= LOAD_AVG_PERIOD;
	}
	val = mul_u64_u32_shr(val, runnable_avg_yN_inv[local_n], 32);         /* 3 */
	return val;
}
  1. LOAD_AVG_PERIOD 是 32。超过 32 × 63 = 2016 个周期直接返回 0——每 32 周期折半一次，折 63 次只剩 0.563≈1.08×10−19，可以当 0 扔。2016 个周期约 2.06s，任何任务睡够两秒，PELT 上就干净了；
  2. 每 32 个周期一次折半，用右移实现，余数留给查表；
  3. mul_u64_u32_shr(val, table, 32) 就是 val × table >> 32，一次 64×32 乘法，不碰浮点。

4、查表从哪来 #

text
runnable_avg_yN_inv[n] = y^n * 2^32,  n > 0 && n < 32

生成逻辑在 Documentation/scheduler/sched-pelt.c 的 calc_runnable_avg_yN_inv()，即 runnable_avg_yN_inv[i] = ((1UL << 32) - 1) * pow(0.97857206, i)。因为 y32=0.5，只需算 y0 到 y31 共 32 项；n≥32 靠折半推（$y^{33} \cdot 2^{32} = 0.5 \cdot y \cdot 2^{32} = 0.5 \times \text{table}[1]$）。生成的表在 kernel/sched/sched-pelt.h：

5、__accumulate_pelt_segments 与 c2 的化简 #

c
static u32 __accumulate_pelt_segments(u64 periods, u32 d1, u32 d3)
{
	u32 c1, c2, c3 = d3; /* y^0 == 1 */
	/* c1 = d1 y^p */
	c1 = decay_load((u64)d1, periods);
	/*
	 *            p-1
	 * c2 = 1024 \Sum y^n
	 *            n=1
	 *
	 *              inf        inf
	 *    = 1024 ( \Sum y^n - \Sum y^n - y^0 )
	 *              n=0        n=p
	 */
	c2 = LOAD_AVG_MAX - decay_load(LOAD_AVG_MAX, periods) - 1024;
	return c1 + c2 + c3;
}

c1 和 c3 好懂，c2 是重点：本是 p−1 项多项式求和，硬被化成两次查表。推导：

text
                       p-1
            c2 = 1024 \Sum y^n
                       n=1
                        inf               inf        p-1
            max = 1024 \Sum y^n = 1024 ( \Sum y^n + \Sum y^n + y^0 )
                        n=0               n=p        n=1
               inf                inf
            ( \Sum y^n ) y^p =   \Sum y^n            （等比级数平移不变）
               n=0                n=p
                         inf        inf
            c2 = 1024 ( \Sum y^n - \Sum y^n - y^0 ) = max - (max y^p) - 1024
                         n=0        n=p

关键是等比级数的平移不变性：$\left(\sum_{n=0}^{\infty} y^n\right) y^p = \sum_{n=p}^{\infty} y^n$。于是「前 p-1 项」等于「无穷项减去第 p 项之后的所有项，再减去第 0 项」，尾部那串就是 max 乘 yp。O(p) 的循环变成两次 decay_load()。

6、LOAD_AVG_MAX 是 47742 #

递推怎么看 #

旧稿给过一个看着省事的递推 L1 = 1023 + (L0 + 1) * y。这式子只在第一个点成立，因为 L0​=1023 刚好让 $L_0 + 1 = 1024$，看起来像「衰减上一次的值再加一个满窗」。换成 L1​=2025，$L_1+1 = 2026 \neq 2048$，就对不上物理意义了。正确递推是：

text
满窗时：      L' = L * y + 1024 * y
当前窗口不满：L' = L * y + t          （t 是当前窗口已 runnable 的时间）

也就是「上一次的总贡献整体衰减一格，再加上本窗口新产生的贡献」——这正是 $L = L_0 + L_1y + L_2y^2 + \cdots$ 逐项平移的结果，也是内核里 decay_load(old_sum, periods) 之后 += load * contrib 干的事。

再验一次非整窗的例子 #

旧稿这个例子正好演示 d1/d2/d3 怎么工作。设 task 从 0 时刻开始运行，1022us 时负载就是 1022。再走 10us 到 1032us：

text
现在的负载 = (1024 - 1022 + 1022) * y + 10 - (1024 - 1022)
           = 1022y + 2y + 8
           ≈ 1002.1 + 1.96 + 8
           ≈ 1010

1022 是上一时刻的贡献，过了一个周期要乘一次 $y$；2us 是上次距离 1024us 的缺口，属于上个周期，也要乘 $y$；8us 是当前周期新产生的，不衰减。旧稿写「1022y + 2y + 8 = 1010」，我复算 1010.06，取整一致。再走 2124us 到 3156us：

text
d1 = 1016us（补齐上一时刻不足 1024us 的部分）
d2 = 1024us（一个完整周期）
d3 =   84us（当前时刻不足一个周期）
u' = 1010*y^2 + 1016*y^2 + 1024*y + 84
   ≈ 967.2 + 973.0 + 1002.1 + 84
   ≈ 3026

旧稿写 3024，我复算 3026.16。差别还是 $y$ 的精度：用 y=0.9785 得 3025.7，用 y=0.978 得 3022.5，旧稿的 3024 落在中间，属于口径不统一。要基准就按 y=0.97857206 自己算。这个例子真正要说明的是：经过 2124us 要衰减几次，取决于每一段相对当前位置的周期距离。d1 要补齐上个窗口，跟着旧值一起衰减 2 次；d2 是整数周期，正好在 1 个周期之外，衰减 1 次；d3 就在当下，不衰减。这就是 __accumulate_pelt_segments(periods, d1, d3) 三个参数的来历。

十八、与 util_est、EAS、schedutil 的接口 #

1、util_est：治「睡久了 util 归零」 #

util_avg 有个毛病：任务睡够久，util 衰减到接近 0。一个大任务刚被唤醒时，PELT 认为它几乎是空的，于是引出两种误判：调度器把它塞到一个其实马上就要满载的 CPU 上，或者调频器按 0 负载给了最低频。4.17 合入的 util_est 就是补这个（提交 7f65ea42，作者 Patrick Bellasi，2018-03-20 进 mainline）：dequeue 时把 util_avg 存一份，唤醒时取「当前 PELT 值」和「上次激活时的值」中较大者：

text
util_est(task) = max(task::util_avg, f(task::util_avg@dequeue))

它跟 PELT 是「叠在上面」而不是替代：PELT 仍是唯一的 estimator，util_est 只是在下发决策的时机上取个更保守的值。

c
struct util_est {
	unsigned int			enqueued;
	unsigned int			ewma;
#define UTIL_EST_WEIGHT_SHIFT		2
} __attribute__((__aligned__(sizeof(u64))));
成员 含义
enqueued 对 task 是「上次 dequeue 时的 util_avg」；对 cfs rq 是该 CPU 上所有 RUNNABLE 任务 util_est.enqueued 之和
ewma 只有 task 维护，按激活次数做的指数滑动平均，w = 1/4（>> UTIL_EST_WEIGHT_SHIFT）

版本上注意：4.17 引入时默认关闭（SCHED_FEAT(UTIL_EST, false)），cfs_rq.util_est 只在 root cfs rq 上有意义；5.10 里 UTIL_EST 和 UTIL_EST_FASTUP 都是 true（已核对 v5.10 的 kernel/sched/features.h），即 5.10 起默认开启，中间哪一版翻的默认值没逐个核对，未验证；4.18 的 struct sched_avg 里已有 struct util_est util_est（已核对 v4.17 / v4.18 的 include/linux/sched.h），所以讲 4.18 的 PELT 却把它漏掉是错的——旧稿 CFS调度器4 就漏了。

2、task_util / cpu_util：把数字喂给决策 #

c
static inline unsigned long task_util(struct task_struct *p)
{
	return READ_ONCE(p->se.avg.util_avg);
}

static inline unsigned long task_util_est(struct task_struct *p)
{
	return max(task_util(p), _task_util_est(p));
}

static inline unsigned long cpu_util(int cpu)
{
	struct cfs_rq *cfs_rq = &cpu_rq(cpu)->cfs;
	unsigned int util = READ_ONCE(cfs_rq->avg.util_avg);
	if (sched_feat(UTIL_EST))
		util = max(util, READ_ONCE(cfs_rq->avg.util_est.enqueued));
	return min_t(unsigned long, util, capacity_orig_of(cpu));
}

三个点：cpu_util() 对 util_est 取 max 再按 capacity_orig_of(cpu) 截顶——不截顶的话，任务刚迁移、外推值叠加时 util 会超 1024，均衡器会以为 CPU 过载；cfs rq 的 util_avg 里含 blocked util，这对「预测马上要唤醒的任务」是好事，对「这个 CPU 现在多闲」是坏事，所以 cpu_util_wake() 要先把唤醒任务自己那份减掉（util -= min_t(unsigned int, util, task_util(p))）；sync_entity_load_avg() / task_h_load() 这类函数在做跨 CPU 比较前会把 se 的负载同步到当前时钟，否则拿两个不同时刻的值相减结论没意义，这类同步在 ⑥ 出现频率很高。

3、schedutil：调频的唯一上游 #

cfs_rq_util_change() 是少数几个「PELT 主动通知别人」的出口：只有 root cfs rq 的变化才需要通知 cpufreq，非 root 的（组调度里的子 cfs rq）会沿传播链汇总到 root。flags 里带 SCHED_CPUFREQ_MIGRATION 这类标记，schedutil 用它区分「负载真的变了」和「任务刚搬过来还要再等一拍」。schedutil 拿到的是 cpu_util(cpu) 与 capacity 的比值，再乘到 cpuinfo.max_freq 上。EAS（CONFIG_ENERGY_MODEL，sched_energy_aware 控制）则拿 task util 和 CPU util 去匹配能耗模型，决定任务放哪个核。两者都只读 PELT 的输出，不写。这条链上最容易出问题的地方是时间口径：schedutil 的采样、均衡器的判定、PELT 的窗口三者不同步，读到的是三个不同瞬间的值。这也是为什么 5.x 之后一直有人在折腾 util 的稳定化（util_est、uclamp、schedutil 的 rate limit），而不是等 PELT 自己收敛。

十九、可调的 sysctl 与常见误用 #

PELT 本身几乎没有运行时旋钮：$y$、1024us、LOAD_AVG_MAX 全是编译期常量。能调的都在周边。

旋钮 默认 作用 版本
sched_util_clamp_min 1024 uclamp.min 的上限，任务的 min 请求被限制在 [0, 该值] 5.x 起
sched_util_clamp_max 1024 uclamp.max 的上限，同理限制在 [0, 该值] 同上
sched_util_clamp_min_rt_default 1024 RT 任务默认 uclamp.min，控制 RT 是否无条件顶到最高频 / 最大核 同上
sched_energy_aware 由平台决定 关掉 EAS。只有非对称拓扑且带 energy model 的平台才有这个文件 5.x
sched_schedstats 0 调度统计开关，开了有额外开销，调 PELT 行为时用来观察 长期存在

几条纪律：uclamp 是在 PELT 之上做钳位，不是改 PELT 的计算，设 sched_util_clamp_max 不会让 util_avg 变小，只是让下游按钳过的值做决策，别指望靠它「修正」util 偏高；sched_energy_aware 在非 EAS 平台上写不进去，读也读不到东西（6.x 文档写明），判断平台支不支持 EAS 看有没有 energy model，不是看文件在不在；sched_schedstats 有开销，生产环境别常开，要看负载用 /proc/sched_debug 或 tracepoint（pelt_se_tp / pelt_cfs_tp）现取。还有个很多人以为存在的旋钮：sched_pelt_multiplier。我在 Android common kernel 里查到过 ANDROID: sched: Introducing PELT multiplier，它把 PELT 衰减速度按倍数加快（打印 4 就表示半衰期从 32ms 缩到 8ms，跟负载变化更快，代价是更容易被瞬时抖动带着跑）。但 v6.12 的 Documentation/admin-guide/sysctl/kernel.rst 里没这个条目，kernel/sched/pelt.c 里也没 multiplier 的痕迹。所以它属于厂商 / Android 内核自加，主线（至少到我核对的 6.12）没有。手机项目上看到它别惊讶，也别写进通用排查文档。

二十、易错点速查 #

  1. 把 runnable_load_avg 和 runnable_avg 当同一个东西。 前者 5.7 已删，带 runnable 权重，量纲是 load；后者 5.7 起，不带权重，量纲是 util。6.x 代码里出现 runnable_load_avg 一定是记错了版本。
  2. 以为 load_avg 只统计 runnable。 出队时不减 load_avg，所以它含 blocked load。只有 runnable_avg（旧名 runnable_load_avg）才是入队加、出队减。
  3. 把 cfs_rq_of() 和 group_cfs_rq() 搞混。 一个是 se 挂入的队列（往上），一个是 se 拥有的队列（往下）。传播方向搞反，整段代码都读不通。
  4. 以为分母是 LOAD_AVG_MAX。 是 LOAD_AVG_MAX - 1024 + period_contrib。少了 period_contrib 会让 util 在 1002~1024 之间抖出锯齿。
  5. 以为半衰期是整 32ms。 是 32 × 1024us = 32.768ms。算「4096us 之后还剩多少」这类问题时，24us 的差别会体现出来。
  6. 把 y^32 = 0.5 理解成「32ms 后负载归零」。 是减半。真归零要 2016 个周期（约 2.06s），因为 decay_load() 在 n > 2016 时直接返回 0。
  7. 以为 period_contrib 是「本周期已过去的时间」。 它是「上次没凑满的尾巴」，也就是下一次的 d1。方向是往回看。
  8. 以为 last_update_time == 0 是 bug。 那是哨兵值：新 se 和刚迁移的 se 都是 0，update_load_avg() 靠它决定走 attach 还是常规更新。
  9. ___update_load_avg() 传 load = 1 以为是偷懒。 cfs rq 的 load_sum 累加时已乘过 cfs_rq->load.weight，再乘一次就重复了。
  10. 以为 sum 没变 avg 也不变。 反了：跨窗口才更新 avg；没跨窗口只累 sum，avg 保持上次的值。decayed 返回值就是这个信号。
  11. 拿 util_avg 当「这个 CPU 现在多闲」。 它含 blocked util。判断多闲得用 cpu_util_wake() 那套，把唤醒任务自己的贡献先扣掉。
  12. 在 4.18 的代码上套 5.7 的字段名，或者反过来。 两条基线在 accumulate_sum() 签名、util 归一化方式、___update_load_avg() 参数个数上全都不同，混着读一定卡住。
