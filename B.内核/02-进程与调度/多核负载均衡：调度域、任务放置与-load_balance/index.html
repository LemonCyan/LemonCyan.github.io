代码基线 Linux 5.10.61。引用时对源码做了删减，NUMA 相关的代码整块拿掉了——手机平台上我们暂时不关注这个特性，所以本篇不覆盖 NUMA balancing。task placement 和 EAS 那几节素材基于 linux-5.4.24，两版在这几个函数上行为一致，有差别我会点出来。

一、什么是 CPU 负载，什么是均衡 #

1、load 和 usage、utility 不是一回事 #

CPU usage 是忙闲比例：1000ms 窗口里 500ms 跑任务、500ms 空转，usage 就是 50%。它直观，但没法跨 CPU 比。同一个任务在小核 300MHz 上跑 1000ms，usage 100%；搬到大核 3GHz 上跑 50ms，usage 只有 5%——任务负载一样，usage 差一个量级。

utility（利用率）也看 running time，区别是做了归一化：把 running time 折算到系统最大算力（超大核最高频），再归一化到 1024，这样能直接和 capacity 做运算。load 也归一化，但和 utility 是两个量：utility 只跟 busy time 走，CPU 没跑满时两者差不多同步；一旦跑满，utility 就废了——大家都是 100%，可 runqueue 上挂 10 个任务的 CPU 和挂 5 个的，承压显然不一样。所以早期直接用 runqueue 深度描述负载。 深度太粗。CPU A、B 各挂 1 个任务，A 上是重载任务，B 上是个一会儿就 sleep 的轻载任务，深度一样，压力差远了。现代调度器改用 runqueue 上所有 task load 之和表示 CPU load，CPU 负载的跟踪就变成任务负载的跟踪。Linux 3.8 引入 PELT，把负载跟踪从 per-CPU 推进到 per-entity：好处不只是「知道 CPU 多忙」，而是「知道负载来自哪个调度实体」，均衡才做得准。

2、capacity：算力是会变的值 #

均衡的目标不是把负载平均摊给每个 CPU，而是让每个 CPU 拿到和算力匹配的负载。6 小核 + 2 大核，总负载 800，每个 CPU 摊 100 不叫均衡，大核能扛的比小核多。算力（capacity）指 CPU 能提供的计算能力：同频下 A77 强于 A57；微架构相同，最高频 2.2GHz 强于 1.1GHz。微架构和最高频一确定，算力基本就定了。struct rq 里有两个相关成员：

成员 描述
unsigned long cpu_capacity; 可以用于 CFS 任务的算力
unsigned long cpu_capacity_orig; 该 CPU 的原始算力，和微架构及其最高频率相关

cpufreq 会按当前 util 调频，温控也会压最高频，但这些都改不了 cpu_capacity_orig。CFS 均衡看 cpu_capacity：扣掉 RT、DL、IRQ 占掉的算力和温控损失，剩下的才给 CFS。所以这个值一直在动，得经常重算（update_cpu_capacity()）。为了和 utility 直接比，算力同样归一化：最强的 CPU 跑满最高频是 1024，其余按微架构和最高频折算。到这里好像齐了：任务有 load，CPU 有 capacity，不均衡就搬任务。但搬任务的代价跟拓扑强相关——小核 cluster 内搬一次，和小核搬大核，差一个量级。所以才要调度域和调度组。

3、均衡不是把负载平分 #

均衡要保吞吐，别让「一核有难、七核围观」。但均衡本身要花算力：找最忙的 group、比负载、抢 rq lock、搬任务。于是有两条约束——间隔：不同 level 的 domain 有自己的均衡间隔，不许每个 tick 都撸一遍；门限：group 差距没到 imbalance_pct 就忍着，level 越高门限越高，因为跨 cluster 搬代价更大。 异构系统还多一层：任务轻或对延迟不敏感，放小核；任务重或跟用户体验相关，就希望它上大核。内核用 misfit task 表达——任务一旦被标成 misfit，均衡得尽快把它往上搬（upmigration），让重载任务早点跑完，或者让前台任务响应快一点。均衡还省电：4 个 CPU、8 个等负载任务，全塞一个 CPU 时那个忙的得跑高频，摊开之后每个 CPU 跑低频，整机功耗更低。

二、为什么只 pull 不 push：Linux 均衡的单向语义 #

看 load_balance() 的骨架只有一个方向：从 src_rq 把任务摘下来（detach_tasks），挂到 dst_rq 上（attach_tasks）。发起均衡的 CPU 是 dest，它主动去别人队列里拉。CFS 这一层没有「把本 CPU 的任务推给别人」这条路径。单向有三个后果，都是设计取舍：

  1. 谁空谁去拉。本 CPU 有活干、别人空着，它不会主动分出去——连别人空不空都懒得看。空闲的 CPU 得自己发起，这就是 new idle balance 存在的理由。
  2. idle 的 CPU 不会自己醒。进了 idle、tick 也停了（NO_HZ），就彻底没机会发起均衡。必须有人踢一脚，于是有 nohz idle balance 的 IPI。
  3. running 的任务搬不动。均衡搬的是 runqueue 上的任务，正在跑的不在队列里。想搬它只能走 stop machine，即 active balance。

push 语义内核里确实有，但不在 CFS 的常规均衡路径上：一个是 active balance 用 stop_one_cpu_nowait() 让目标 CPU 停下来再挪 running task；另一个是 CPU hotplug 时的 migration_call。把这两条和 pull 混为一谈，读代码时会一直觉得「哪里少了一段」。

三、调度域 sched_domain 与调度组 sched_group #

1、为什么要造这两个概念 #

复杂度全在拓扑上。CPU 很忙，把任务挪走：跨 cluster 挪，cache 冷掉；SMT 的两个硬件线程共享 cache，互相挪基本无感；NUMA node 之间挪，代价又是另一个量级，除非不均衡严重到没法看。算法必须能表达这些差异，解法就是 struct sched_domain：按拓扑分层，每层一个 domain，均衡在各自内部判定。

成员 描述
parent / child sched domain 形成层级结构，parent 和 child 建立父子关系。base domain 的 child 为 NULL，top domain 的 parent 为 NULL
groups 一个调度域里有若干调度组，形成环形链表，groups 是链表头
min_interval / max_interval 做均衡有开销，无法时刻盯着。这两个值定义检查该 domain 均衡状态的时间间隔范围
busy_factor 正常情况下 balance_interval 就是间隔；CPU 繁忙时间隔拉长为 busy_factor × balance_interval
imbalance_pct 域内不均衡到什么程度才动手，这个成员是判定门限
cache_nice_tries 和 nr_balance_failed 配合控制迁移力度。失败次数超过它，均衡更激进，连 cache hot 的任务也搬
nohz_idle 每个 CPU 都有对应的 LLC sched domain，LLC SD 记录该 CPU 的 idle 状态（tick 是否已停），进而统计 domain 中 busy CPU 的个数，落在 sd->shared->nr_busy_cpus
flags 调度域标志，见下一章的表
level 该 domain 在层级中的位置。base domain 的 level 为 0，向上依次加一
last_balance 上次做均衡的时间点。由基础间隔（get_sd_balance_interval()）和当前 sd 状态算出最终间隔，last_balance + interval 就是下次均衡时间
balance_interval 该 domain 均衡的基础时间间隔
nr_balance_failed 该 domain 上均衡失败的次数。超过 cache_nice_tries 就开始搬 cache hot 的任务
max_newidle_lb_cost 该 domain 上 newidle balance 的最大耗时，最小值被 sysctl_sched_migration_cost 兜住
next_decay_max_lb_cost max_newidle_lb_cost 会衰减，这个成员控制衰减节奏，每秒一次
avg_scan_cost 平均扫描成本
struct sched_domain_shared *shared 为降低锁竞争，sched domain 是 per-CPU 的，但有些信息必须在 per-CPU domain 之间共享：1、该 domain 中 busy CPU 的个数；2、该 domain 中是否有 idle 的 CPU
span_weight / span 该 domain 的跨度。手机场景下 span 就是该 domain 中所有 CPU core 形成的 cpu mask，span_weight 是其中的 CPU 个数

一句话记住 shared：per-CPU 的东西放 per-CPU domain，跨 CPU 要看的汇总数扔进 shared，省得每个 CPU 都算一遍还要抢锁。

2、调度组 #

均衡不在 CPU 之间直接做，而是在 group 之间做。domain 是「比什么范围」，group 是「范围内的参赛选手」。base domain 每个 group 只有一个 CPU；往上走 group 里会有多个 CPU core。

成员 描述
next domain 中所有 sched group 形成环形链表，next 指向下一个节点
ref 该 sched group 的引用计数
group_weight 该调度组中有多少个 CPU
sgc 该调度组的算力信息（struct sched_group_capacity）
cpumask 该调度组包括哪些 CPU

group 是环形链表，每个 CPU 的 domain 里链表头的 group 就是自己。这样「local group」的定位变成一次比较，遍历也天然不抢锁。

四、调度域的层级与 sd flag #

domain 按 CPU 拓扑搭成树，均衡不是一把梭，而是从某个 level 起逐级往上。从哪起、走几层，由均衡类型和各级 flag 决定。在某个指定 domain 里均衡时，不看系统其他 domain 的 CPU 负载，只看本 domain 内各 group 是否均衡——这就是分层的意义：把 N 个 CPU 的全局问题拆成若干个局部问题。

调度域标记 描述
SD_BALANCE_NEWIDLE 该 domain 是否支持 newidle balance
SD_BALANCE_EXEC / SD_BALANCE_FORK / SD_BALANCE_WAKE exec、fork、wake 时该 domain 是否参与对应类型的均衡。这三个 flag 主要用来圈定 exec、fork、wakeup 场景下选核的范围
SD_WAKE_AFFINE 该 domain 上是否考虑 wake affine，即满足条件时让 waker 和 wakee 靠近
SD_ASYM_CPUCAPACITY 该 domain 上的 CPU 是否具有不一样 capacity。MC domain 上各 CPU 算力相同，DIE domain 会设这个 flag
SD_SHARE_CPUCAPACITY 该 domain 上的 CPU 是否共享计算单元。SMT 下两个硬件线程被看作两个 CPU core，但会争抢硬件计算单元。手机上未使用该 flag
SD_SHARE_PKG_RESOURCES domain 中的 CPU 是否共享 SoC 资源（例如 cache）。手机平台上 MC domain 会设这个 flag

SD_SHARE_PKG_RESOURCES 后面反复出现，它是一条分界线：设了它的（MC）用 nr_running/idle CPU 数指导均衡，没设的（DIE）才允许用 util。原因在二十二章。

五、一个 CPU 拓扑示例（big.LITTLE 与 SMT） #

4 小核 + 4 大核：cpu0-3 组成 little cluster，cpu4-7 组成 big cluster，同 cluster 内微架构相同、共用一套调频策略、频率一致。

domain group 数量 每个 group 里的 CPU
小核 MC 4 cpu0 / cpu1 / cpu2 / cpu3，各一个
大核 MC 4 cpu4 / cpu5 / cpu6 / cpu7，各一个
DIE 2 (0,1,2,3) 和 (4,5,6,7)

base domain 叫 MC domain（multi core domain），顶层叫 DIE domain，覆盖全部 8 个 CPU。group 链表是环形的，入口因 CPU 而异：cpu0 的 MC domain 顺序是 0-1-2-3，cpu1 的是 1-2-3-0；DIE 同理，cpu0 是 (0,1,2,3)→(4,5,6,7)，cpu6 是 (4,5,6,7)→(0,1,2,3)。每个 CPU 都有自己的 MC 和 DIE domain，靠 parent/child 串成层级，锁的粒度是 per-CPU 的。非 base domain 的 group 覆盖其 child domain 的全部 CPU：DIE 有两个 child，所以 group 链表只有两个元素。

SMT 是另一回事。两个硬件线程在 topology 眼里是两个 CPU core，能各自跑任务，但共享执行单元，一个线程的负载会拖慢另一个。内核用 SD_SHARE_CPUCAPACITY 表达这层关系。手机 SoC 上没有 SMT，这个 flag 在手机场景不会出现。

六、负载均衡的软件架构：三个入口 #

均衡模块分两层：核心均衡模块（core.c 里的框架、softirq、domain 遍历）和 class-specific 均衡模块（fair.c 里的具体策略）。RT、DL 和 CFS 各走各的，这里只讲 CFS。

入口 触发时机 主要函数
唤醒/创建/exec 任务要选一个 CPU select_task_rq() → select_task_rq_fair()
tick 时间片流逝，周期性检查 scheduler_tick() → trigger_load_balance() → SCHED_SOFTIRQ
进 idle 前 本 CPU 马上没活干 newidle_balance() → load_balance()

三个入口对应三种语义：放置是把还没上 CPU 的任务放到合适的核上，周期均衡是在忙 CPU 之间重新分配，idle 均衡是把任务往空 CPU 上摊。基础设施只有三样，缺一不可：任务负载跟踪（判断任务是否适合当前算力、要搬多少才平）、domain 层级（把全局均衡拆成局部）、算力跟踪（RT/DL/IRQ 的占用和温控损失都得从 cpu_capacity 扣掉，否则均衡会朝一个不存在的目标搬）。手机场景基本两级：MC domain 追每个 CPU 的负载和算力，DIE domain 追每个 cluster 的总负载和总算力、做 inter-cluster 迁移。

七、三类均衡器总览（periodic / nohz / new idle） #

为忙 CPU 准备的是 periodic balancer，为 idle CPU 准备的是 idle balancer，后者又分 nohz idle 和 new idle。别被三个名字骗了，它们最后都落到同一个函数——留到第十七章。

维度 periodic（tick） nohz idle new idle
发起者 任意忙 CPU 忙 CPU 经 IPI 指定的代表 CPU 即将进 idle 的本 CPU
触发点 scheduler_tick() → trigger_load_balance() 同一个 trigger_load_balance() 里的 nohz_balancer_kick() pick_next_task() 挑不到 CFS 任务时
处理函数 run_rebalance_domains() 同一个 handler，先走 nohz_idle_balance() 直接调 newidle_balance()
覆盖范围 本 CPU 的各级 domain 系统里所有 idle CPU 的各级 domain 本 CPU 的各级 domain
均衡方向 从 busiest group 拉到本 CPU 从忙 CPU 拉到各个 idle CPU 从忙 CPU 拉到本 CPU
依赖特性 无 必须有 NO_HZ（tickless），否则 tick 会把 idle CPU 叫醒 无
频次控制 rq->next_balance + domain 间隔 nohz.next_balance + nohz.nr_cpus avg_idle + max_idle_balance_cost

共同点：都只搬 runnable 任务，都自底向上逐级走，都想少干活——每级 domain 都有自己的间隔和门限。

八、任务放置 task placement：什么是放置 #

每个 CPU 一个 runqueue。任务挂在队列上等着是就绪态，负载不匹配靠 load balance 调整；任务正在跑是运行态，超出 CPU 承受能力时被标成 misfit，交给 active upmigration。这两种场景的前提都是「任务已经落在某个 CPU 上，而且负载数据可信」。那还没落位的呢？刚 fork 的、刚 exec 的、刚从阻塞被唤醒的——没有 runqueue，也没有负载历史。给它们挑一个 CPU，就是 task placement。

场景 入口
fork 创建子进程 wake_up_new_task() → select_task_rq()
exec 开始执行 sched_exec() → select_task_rq()
阻塞进程被唤醒 try_to_wake_up() → select_task_rq()

三条路都进 core.c 的 select_task_rq()，再按调度类分发，CFS 这一支跳 select_task_rq_fair()。放置为什么值得单独讲：任务刚被唤醒时，负载信息要么是历史值（唤醒），要么根本没有（fork/exec），决策必须在信息不足时做，而且要快——唤醒路径在等这把决策，慢了就是调度延迟。所以这里的算法全是启发式，全是猜。

九、select_task_rq_fair 的决策路径 #

c
static int select_task_rq_fair(struct task_struct *p, int prev_cpu,
                               int sd_flag, int wake_flags)

sd_flag 是 sched domain 标志位，一共三种——SD_BALANCE_WAKE、SD_BALANCE_FORK、SD_BALANCE_EXEC，对应三个放置场景，调度器只在设了相应 flag 的 domain 里选核。wake_flags 专给 SD_BALANCE_WAKE 用：

标志 含义
WF_FORK 该任务是 fork 出来的，不是从阻塞里被唤醒的
WF_SYNC waker 唤醒 wakee 之后自己就要睡，即同步唤醒
WF_TTWU 唤醒路径进入，给唤醒侧的痕迹采集用

函数内部只处理 WF_SYNC。传了这个标志说明 waker 唤醒 wakee 之后马上要进阻塞态，那把 wakee 放到 waker 的 CPU 上不会挤到谁——waker 立刻让位。这场景用得极多，比如用户态两个进程做非异步 binder 通信，Server 端唤醒一个 binder 线程处理事务。

路径 函数 进入条件 选核思路
EAS 路径 find_energy_efficient_cpu() sd_flag == SD_BALANCE_WAKE，且 sched_energy_present 为真 在能跑得动的前提下，挑让整机能耗最低的 CPU
快速路径 select_idle_sibling() sd_flag == SD_BALANCE_WAKE，EAS 用不上，任务是 wake affine 类型 优先 prev_cpu，其次 wake_cpu，再看它们的 LLC 里有没有 idle CPU
慢速路径 find_idlest_cpu() sd_flag == SD_BALANCE_WAKE 但 EAS 没使能或返回 -1，且不是 wake affine 任务；或 sd_flag 为 SD_BALANCE_FORK/SD_BALANCE_EXEC 在 target domain 里找最闲的 group，再找最闲的 CPU

优先级是硬的：EAS 有条件先试，失败看任务类型，wake affine 走快速路径，其余走慢速路径。 慢速路径多说一句。fork 和 exec 进来的任务负载不可信——新任务的 util 从父进程继承再打折，exec 之后更是换了个人。拿这种数算能耗没意义，所以 EAS 直接不接，只能退到「找最闲的 CPU」。target domain 怎么定：从 waker 的 base domain 往上找最底层配了相应 sd_flag 的 domain，然后在里面找负载最小的 group，再找 group 里负载最小的 CPU。这套「新任务往最闲处塞」对刚创建的任务算稳妥；开发者也提过别的思路（放到特定类型的 CPU 上，或者根据父进程负载推断新任务走向），这些启发式在某些场景会引出别的问题，所以一直没成为默认。

十、wake_affine 与唤醒时的就近选择 #

waker 唤醒 wakee 时把 wakee 放附近有收益：cache 命中率高，还不用叫起别的 idle CPU。但得有条件，无脑打包会把 CPU 挤爆。

函数 看什么 结论
wake_wide() wakee 的数量 waker 唤醒的 wakee 太多就不再做 affine，否则一群 wakee 挤一个 CPU
wake_cap() 目标 CPU 的算力 目标 CPU 算力撑不住 wakee 的 util 就不做 affine，得往大核找

wake_wide() 记录 waker 最近唤醒过几个不同的 wakee。一个主任务唤醒多个子任务时全贴在 waker 身边，调度延迟立刻起飞——想省的那点 cache 和功耗，换来整队任务响应变慢，不划算。wake_cap() 更直接：算力不够别硬塞，小核的 cpu_capacity 装不下 wakee 的 util，affine 到小核等于让它慢慢跑。 两道门都过了才走快速路径 select_idle_sibling()：先看 prev_cpu（任务上次跑的 CPU，hot cache，wake affine 任务最想要它）；再看 wake_cpu（waker 所在 CPU）；都不合适就扫它们的 LLC domain 找 idle CPU。WF_SYNC 在这里会放宽判定：waker 是 wake_cpu 上唯一的任务时，wake_cpu 也算 idle。理由是同步唤醒下 waker 马上要睡，等于给 wakee 腾了位置。

十一、Active upmigration：把任务从冷核搬走 #

常规均衡有个盲区：只搬 runqueue 上的任务。正在跑的那个不在队列里，detach_tasks() 扫不到。小核上跑着一个明显超算力的任务，它一直在 running，均衡器反复扫也搬不走。

active upmigration 就是解这个：把 running 的 misfit task 往上搬。实现靠 stop machine——load_balance() 发现 runnable 任务搬不动、同时 need_active_balance() 判定该动手，就在 busiest rq 上打标记，然后 stop_one_cpu_nowait() 让 busiest CPU 停下来，在 stop 上下文里把当前任务迁走，走 fair.c 的 active_load_balance_cpu_stop()。

三点注意：开销大，要让目标 CPU 停一下，stop 上下文延迟是微秒级的，所以它只做兜底；触发条件是搬不动，常规轮次一个任务都没搬成（ld_moved == 0），nr_balance_failed 累加到超过 cache_nice_tries 才允许动 running 任务；上游原生内核没有独立的 upmigration 框架，手机厂商的 kernel 里 misfit 判定和主动迁移往往有自己的补丁，标准内核只给了 misfit 标记（rq->misfit_task_load）和 active balance 机制。

十二、Energy Aware Scheduling：Energy Model 与 EAS #

1、Energy Model 是什么 #

EAS 在选核时多算一个维度：能耗。输入是 Energy Model（EM），理解 EM 的入口是性能域（performance domain）。perf domain 用 struct perf_domain 描述，同一微架构的 CPU 归到同一个 perf domain，因为它们共享一套调频策略、频率必须一致。4 大核 + 4 小核的拓扑下，小核 4 个 CPU 组成一个 perf domain，大核 4 个组成另一个。同 domain 内所有 CPU 同频。频点是分级的，每级频点和 capacity、power 一一映射：小核 4 个 CPU 最大 capacity 都是 512，对应最高频 1GHz，那 500MHz 对应的 capacity 就是 256。为把这些信息组织起来，EM 加了两个结构体：struct em_perf_domain 和 struct em_cap_state，都能从 perf domain 拿到。

2、energy 怎么估 #

energy 是资源，单位焦耳；power 是每秒的能量损耗，单位瓦特。某个 perf domain 的 energy 由 em_pd_energy() 给出，max_util 是该 domain 各 CPU 中的最高负载，sum_util 是总负载：

c
static inline unsigned long em_pd_energy(struct em_perf_domain *pd,
                                unsigned long max_util, unsigned long sum_util)

同 domain 同频，所以选哪个频点取决于最忙的 CPU。EM 先拿到当前 domain 的最高频点和最大算力，把 max_util 映射到对应频点，找到能覆盖它的最低频点及该频点下的算力 cs_capacity——得保证任务跑得动。频点定了，cs_power 就是现成的，domain 下所有 CPU 共用。还差一个跟运行时间相关的量：CPU 不是满载的（EAS 在超载时不使能），idle 的时间要剔掉，用 util 与 capacity 的比值来估——util 本身就体现窗口内的执行时间，窗口全在跑任务时 util 会顶到 capacity。数据齐了，把 domain 内所有 CPU 的 energy 加起来就是估计能量。

3、EAS 什么时候不工作 #

两种情况直接退出：系统不是异构的（所有 CPU 算力一样，没得挑）；系统里有超载（over-utilized）的 CPU——判定很严格，只要 root domain 里有 CPU 负载达到该 CPU 算力的 80% 以上就算。第二条值得说清。假设小核 cluster 的 cpu3 超载了，那不管你把任务放哪个 CPU，小核 cluster 都得维持最高频点。此时「domain 里空余算力最大的 CPU」这个标准就没意义了——预估的 energy 不公平，EAS 的设计前提（靠放置任务把 cluster 频点压下来省电）直接失效。

十三、EAS 的 task placement 流程 #

find_energy_efficient_cpu() 四步：一是用 em_pd_energy() 算出各个 perf domain 在不放任务时的基础能量；二是遍历各个 perf domain，找出该 domain 下空余算力最大的 CPU，加上 prev_cpu 一起作为备选；三是用 em_pd_energy() 算出把任务放到各备选 CPU 后，对应 perf domain 的能量变化；四是挑能量变化最小的那个，但如果相对放到 prev_cpu 的收益不到 6%，还是回 prev_cpu。 为什么挑空余算力最大的 CPU 当备选：这样不会把某个 CPU 顶到高频，进而把整个 cluster 的频点抬上去。cluster 同频，一个 CPU 冒头，全 cluster 陪跑。为什么舍不得 prev_cpu：hot cache 对执行效率有实打实的好处，所以给它留了 6% 的优惠——节能收益要超过这条线，才允许放弃 cache 亲和性。

十四、周期性负载均衡：tick 触发路径 #

1、触发 #

tick 到来时 scheduler_tick() 调 trigger_load_balance()：

c
void trigger_load_balance(struct rq *rq)
{
    /* Trigger the SCHED_SOFTIRQ if it is time to do periodic load balancing. */
    if (time_after_eq(jiffies, rq->next_balance))
        raise_softirq(SCHED_SOFTIRQ);   /* 触发 periodic balance */
    nohz_balancer_kick(rq);             /* 触发 nohz idle balance */
}

逻辑就一句：到点发软中断。nohz_balancer_kick() 管 nohz idle balance，下一章拆。函数上方那行注释看着不对——它说触发周期性均衡，可这函数顺手也把 nohz idle 触发了。注释没错：nohz idle balance 本质是另一种周期性均衡，只是 idle CPU 产生不了 tick，只好让能产生 tick 的忙 CPU 代劳。两者最后都走 SCHED_SOFTIRQ，都由 run_rebalance_domains() 处理。均衡不是每个 tick 都做：各级 domain 的下次均衡时间点记在 last_balance 里，rq->next_balance 取其中最近的，jiffies 没过线就不发软中断。

2、软中断处理：先 nohz，后 periodic #

c
static __latent_entropy void run_rebalance_domains(struct softirq_action *h)
{
    struct rq *this_rq = this_rq();
    enum cpu_idle_type idle = this_rq->idle_balance ?
                              CPU_IDLE : CPU_NOT_IDLE;
    if (nohz_idle_balance(this_rq, idle))   /* nohz idle balance */
        return;
    update_blocked_averages(this_rq->cpu);
    rebalance_domains(this_rq, idle);       /* 周期性均衡 */
}

顺序有讲究。nohz idle balance 是全局的事——被选中的 CPU 代表所有 idle CPU 做均衡；periodic 只管自己那套 domain。先做后者会怎样？rebalance_domains() 一旦把任务拉到 this CPU 上，this CPU 就不 idle 了，接着 nohz_idle_balance() 一看代表不 idle 直接退出，其他 idle CPU 白等。所以先 nohz；nohz 干成了本 CPU 这轮就不用再做（返回 true，直接 return）。

3、rebalance_domains 主循环 #

c
for_each_domain(cpu, sd) {
    if (time_after(jiffies, sd->next_decay_max_lb_cost)) {          /* A */
        sd->max_newidle_lb_cost = (sd->max_newidle_lb_cost * 253) / 256;
        sd->next_decay_max_lb_cost = jiffies + HZ;
        need_decay = 1;
    }
    max_cost += sd->max_newidle_lb_cost;
    if (!continue_balancing) {                                      /* B */
        if (need_decay)
            continue;
        break;
    }
    interval = get_sd_balance_interval(sd, busy);
    if (time_after_eq(jiffies, sd->last_balance + interval)) {       /* C */
        if (load_balance(cpu, rq, sd, idle, &continue_balancing)) {
            idle = idle_cpu(cpu) ? CPU_IDLE : CPU_NOT_IDLE;
            busy = idle != CPU_IDLE && !sched_idle_cpu(cpu);
        }
        sd->last_balance = jiffies;
        interval = get_sd_balance_interval(sd, busy);
    }
    if (time_after(next_balance, sd->last_balance + interval)) {     /* D */
        next_balance = sd->last_balance + interval;
        update_next_balance = 1;
    }
}

A：max_newidle_lb_cost 是该 domain 上 newidle balance 的最大开销，随时间衰减，每秒乘一次 253/256；这里顺手把各级值累加成 max_cost，最后写进 rq->max_idle_balance_cost，用来控制 new idle balance 的深度。B：循环从 base domain 往上一路走，但上层 domain 覆盖的 CPU 多，如果每个 CPU 的周期均衡都去撸顶层，顶层被撸的遍数太多，continue_balancing 是刹车；例外是需要更新 max_idle_balance_cost（need_decay 为真）时，即使不做均衡也要把各级 domain 走完，否则累加不全。C：到间隔就调 load_balance()，搬成功后要重判本 CPU 忙闲——因为 load_balance() 会改掉 dest CPU，或者说这轮压根不是往本 CPU 拉任务，busy 跟着变，间隔得重算。D：每级 domain 各自算下次均衡点，next_balance 留最近的（偏性能，尽快均衡），后面赋给 rq->next_balance，下一次 tick 靠它判断要不要发软中断。

c
if (need_decay) {                                        /* A */
    rq->max_idle_balance_cost =
        max((u64)sysctl_sched_migration_cost, max_cost);
}
if (likely(update_next_balance)) {                       /* B */
    rq->next_balance = next_balance;
    if ((idle == CPU_IDLE) && time_after(nohz.next_balance, rq->next_balance))
        nohz.next_balance = rq->next_balance;            /* C */
}

A：任何一级 domain 衰减过 cost，就把汇总值刷进 rq->max_idle_balance_cost，并保证不低于 sysctl_sched_migration_cost。B：rq->next_balance 取各级 domain 里最近的均衡点。C：本 CPU 处于 idle 时顺带更新 nohz.next_balance——它是触发 nohz idle balance 的时间锚点，取更近的那个。

4、均衡间隔怎么定 #

均衡频次是在延迟和开销之间找平衡。MC domain 在 cluster 内搬，影响小；DIE domain 跨 cluster 搬，cache 命中率、把深度睡眠的大核叫醒，代价都大，所以间隔必须跟层级挂钩。负载重时还得再拉长——大家都忙，让子弹先飞一会。

成员 描述
last_balance 最近在该 domain 上做均衡的时间点。判定是否该均衡，比的是 jiffies 和 last_balance + interval，interval 由 get_sd_balance_interval() 实时算
min_interval / max_interval 检查该 domain 均衡状态的时间间隔范围。min_interval 默认取 sd weight，即 domain 内 CPU 个数；max_interval 是它的 2 倍
balance_interval 该 domain 均衡的基础间隔。跟层级有关，层级越高、覆盖 CPU 越多，值越大。load_balance() 执行时按实际结果把它加倍或保持原值
busy_factor CPU 繁忙时的间隔放大系数，间隔变成 busy_factor × balance_interval，默认 32 
c
static inline unsigned long
get_sd_balance_interval(struct sched_domain *sd, int cpu_busy)
{
    unsigned long interval = sd->balance_interval;   /* A */
    if (cpu_busy)                                    /* B */
        interval *= sd->busy_factor;
    interval = msecs_to_jiffies(interval);
    if (cpu_busy)                                    /* C */
        interval -= 1;
    return clamp(interval, 1UL, max_load_balance_interval);
}

A：balance_interval 跟着不均衡程度走。初值从 min_interval 起，还不均衡就停在 min_interval；随着不均衡缓解、没任务可搬、需要靠 active balance 收尾，它逐次变大直到 max_interval。4+4 平台上 MC domain 是 4ms/8ms，DIE domain 有 8 个 CPU，是 8ms/16ms。B：各 CPU 的 tick 大致同步，自底向上的均衡几乎同时触发，覆盖 CPU 多的 domain 收集信息慢一点，于是「低阶 domain 刚搬完的任务被高阶立刻又搬走」；busy_factor 放大间隔，缓解这种同步踩踏。C：减 1 让高阶和低阶的间隔不成整数倍关系，把同步再打散一层，上限由 max_load_balance_interval 卡住，100ms。 这套间隔控制对 periodic 和 nohz idle 都生效，因为两者共用 rebalance_domains()。

十五、NOHZ idle balance：为什么需要 IPI 踢醒 #

1、为什么要有它 #

CPU 进了 idle、tick 也停了（NO_HZ），就再没机会发起均衡。别的 CPU 任务堆成山，这边空着——纯 pull 语义下没人能救它。所以忙 CPU 得主动踢一脚：选一个 idle CPU 当代表，发 IPI 把它唤醒，让它代表系统里所有 idle CPU 做一遍均衡。名字里的 NOHZ 就是这个意思：只有配了 tickless 才用得上。没有 dynamic tick 的话 tick 会周期性叫醒 idle CPU，periodic balance 已经覆盖，不需要额外 IPI。被踢醒的 CPU 不是「只把任务拉到我自己队列上」就完事，它是全体 idle CPU 的代表。

2、触发条件 #

c
if (unlikely(rq->idle_balance))                    /* A */
    return;
nohz_balance_exit_idle(rq);                        /* B */
if (likely(!atomic_read(&nohz.nr_cpus)))           /* C */
    return;
if (READ_ONCE(nohz.has_blocked) &&
    time_after(now, READ_ONCE(nohz.next_blocked)))
    flags = NOHZ_STATS_KICK;                       /* D */
if (time_before(now, nohz.next_balance))           /* E */
    goto out;

A：nohz idle balance 是「本 CPU 忙、求别人帮忙」，本 CPU 自己 idle 就没必要发起。B：CPU 从 idle 醒来，第一个 tick 要把全局 nohz 状态和 domain 的 CPU busy 状态刷一遍；nohz idle 本质是 tick balance，但要发 IPI、要叫醒睡着的 CPU，代价不低，频次必须控住，控制手段是全局 nohz 变量（nohz_balance_exit_idle() 负责维护其中的 nr_cpus 和 idle_cpus_mask）：

成员 描述
idle_cpus_mask 系统中哪些 CPU 进入了 idle 状态
nr_cpus 多少个 CPU 进入了 idle 状态
has_blocked 这些 idle CPU 是否需要更新 blocked load
next_balance 下一次触发 nohz idle balance 的时间
next_blocked 下一次更新 blocked load 的时间点

C：系统里一个 idle CPU 都没有，踢谁去？直接返回。D：nohz idle balance 干两件事——更新 idle CPU 的 blocked load，以及负载均衡；可以只更新 blocked load，但做均衡时必须连 blocked load 一起更，有需要衰减的负载就打个标记（blocked load 属于 PELT 的话题，这里不展开）。E：next_balance 控制触发时间点，跟所有 idle CPU 的 rq->next_balance 有关，idle CPU 都没到均衡时间点就没必要触发；执行时遍历 idle CPU，把最小的 rq->next_balance 赋给它。

c
if (rq->nr_running >= 2) {                                    /* A */
    flags = NOHZ_KICK_MASK;
    goto out;
}
sd = rcu_dereference(rq->sd);                                 /* B */
if (sd) {
    if (rq->cfs.h_nr_running >= 1 && check_cpu_capacity(rq, sd)) {
        flags = NOHZ_KICK_MASK;
        goto unlock;
    }
}
sd = rcu_dereference(per_cpu(sd_asym_cpucapacity, cpu));      /* C */
if (sd) {
    if (check_misfit_status(rq, sd)) {
        flags = NOHZ_KICK_MASK;
        goto unlock;
    }
    goto unlock;                                             /* D */
}
sds = rcu_dereference(per_cpu(sd_llc_shared, cpu));
if (sds) {
    nr_busy = atomic_read(&sds->nr_busy_cpus);                /* E */
    if (nr_busy > 1) {
        flags = NOHZ_KICK_MASK;
        goto unlock;
    }
}

A：踢人之前得确认自己有货可被拉，runqueue 上挂 2 个以上任务基本可以确定值得踢。B：只有一个 CFS 任务，但 CPU 能给 CFS 用的算力已经被压下去了（RT 任务或 IRQ 占掉），也要发起。C：异构系统还得看 misfit，本 CPU 上有 misfit task，哪怕只有一个任务也要发起——它是搬去更大核的候选。D：异构系统到此为止，不查 LLC，功耗考量——小核 cluster 里有 busy 的 CPU 不代表需要均衡，只要小核算力还够扛住当前任务，就没必要把大核叫起来。E：同构系统反过来，期望负载在 LLC domain 之间也均一（cache 利用率更高），LLC 内部也要摊开；但本 CPU 看不到别的 LLC，只能退一步：只要有 2 个及以上 CPU 在忙就发起。

3、选哪个 CPU 当代表 #

c
if (flags & NOHZ_BALANCE_KICK)
    nohz.next_balance = jiffies + 1;                        /* A */
ilb_cpu = find_new_ilb();                                   /* B */
if (ilb_cpu >= nr_cpu_ids)
    return;
flags = atomic_fetch_or(flags, nohz_flags(ilb_cpu));        /* C */
if (flags & NOHZ_KICK_MASK)
    return;
smp_call_function_single_async(ilb_cpu, &cpu_rq(ilb_cpu)->nohz_csd);  /* D */

A：要做均衡（不只是更负载）就把 nohz.next_balance 推到下一个 jiffy，这样同一 jiffy 里其他 CPU 的 tick 不会再触发一遍检查；顺利完成的话它会正常更新，被打断的话（下一节 B 段）这个值保证下个 tick 能接着干。B：不在乎功耗的话从所有 idle CPU 里随便挑一个就行，异构系统（手机）得想更多——大核小核都 idle 叫谁？叫大核算力足但费电，叫小核省电但算力够不够？发起请求的 CPU 在哪个 cluster？idle 深度如何？标准内核选的是最省事的算法：取 nohz.idle_cpus_mask 里的第一个。C：确保选中的 CPU 没有正在做 nohz idle balance，已经有 pending 请求就不重复发 IPI。D：发起方叫 kicker，执行方叫 kickee，交互三步——kicker 先设 kickee rq 的 nohz_flags（你被选中了），然后发 IPI 叫醒它，kickee 在中断里跑 scheduler_ipi() 看到标记，走和 periodic balance 一样的路，触发一次 SCHED_SOFTIRQ。

4、均衡处理 #

软中断 handler 还是 run_rebalance_domains()，这里进的是 nohz_idle_balance()：遍历系统里所有 idle CPU，对每个 CPU 调 rebalance_domains()。

c
WRITE_ONCE(nohz.has_blocked, 0);                            /* # */
for_each_cpu(balance_cpu, nohz.idle_cpus_mask) {
    if (balance_cpu == this_cpu || !idle_cpu(balance_cpu))
        continue;                                           /* A */
    if (need_resched()) {                                   /* B */
        has_blocked_load = true;
        goto abort;
    }
    rq = cpu_rq(balance_cpu);
    has_blocked_load |= update_nohz_stats(rq, true);         /* C */
    if (time_after_eq(jiffies, rq->next_balance)) {          /* D */
        if (flags & NOHZ_BALANCE_KICK)
            rebalance_domains(rq, CPU_IDLE);
    }
    if (time_after(next_balance, rq->next_balance)) {        /* E */
        next_balance = rq->next_balance;
        update_next_balance = 1;
    }
}

A：先跳过本 CPU，遍历完其他 idle CPU 之后再处理自己，已经不 idle 的也跳过。B：本 CPU 有活了就赶紧放弃这轮——后面还有好几个 idle CPU、好几级 domain 要扫，全是耗时活，硬撑下去自己队列上的任务就要等，调度延迟立刻爆；放弃的代价是有些 idle CPU 的 blocked load 没更新，所以进来时先假定全更完（# 处清 has_blocked），半路退出只能标回 1。C：给这个 idle CPU 更新 blocked load。D：到了均衡间隔就调 rebalance_domains() 干活。E：跟踪各 idle CPU 里最近的 next_balance，最后写回 nohz.next_balance 管住触发频次。 遍历完其他 CPU 之后，_nohz_idle_balance() 第二段处理本 CPU（被选中的代表）自己的均衡，逻辑一样。

十六、New idle balance：进 idle 前的最后一次检查 #

1、触发 #

入口是 newidle_balance()，pick_next_task_fair() 挑不到 CFS 任务、CPU 要进 idle 时调它。第一段先过滤掉不该做的场景：

c
if (this_rq->avg_idle < sysctl_sched_migration_cost ||        /* A */
    !READ_ONCE(this_rq->rd->overload)) {                      /* B */
    sd = rcu_dereference_check_sched_domain(this_rq->sd);
    if (sd)
        update_next_balance(sd, &next_balance);               /* C */
    nohz_newidle_balance(this_rq);                            /* D */
    goto out;
}

A：要不要做，先看两件事——本 CPU 的 cache 冷热，和整机负载。平均 idle 时间极短说明它很快回来干活，cache 还热；这时候从别的 CPU 拉任务过来，新任务会把老任务的 cache 挤掉，等老任务回来执行，性能掉、功耗涨，两头亏。B：整机 overload 状态记在 root domain 的 overload 成员里，单个 CPU overload 的条件是下面两条之一；系统里只要有一个 CPU overload，就认为整机 overload，整机都不 overload 说明没任务可拉，做均衡纯属浪费。

条件 说明
runnable 任务大于 1 该 CPU 上有排队等执行的任务
只有一个 running 任务，但它是 misfit task 任务跑得动，但当前 CPU 算力不够

C：不适合做均衡，只更新 blocked load；本 CPU 马上进 idle，忙闲状态变了，base domain 的均衡间隔要跟着调。D：new idle balance 也要管 blocked load 更新，条件不满足、本 CPU 不均衡时，还得看看系统里哪些 idle CPU 的 blocked load 该更了，顺手替它们更掉。逻辑是：与其在 nohz idle balance 里遍历挑一个 idle CPU 来更负载，不如让这个马上进 idle 的 CPU 直接干。注意 5.10 的代码这里仍然用 kick_ilb() 选一个 CPU 去发仅负载更新的均衡请求，这个 issue 在后来的版本里修掉了。

c
update_blocked_averages(this_cpu);                            /* A */
for_each_domain(this_cpu, sd) {
    if (this_rq->avg_idle < curr_cost + sd->max_newidle_lb_cost) {
        update_next_balance(sd, &next_balance);
        break;                                                /* B */
    }
    if (sd->flags & SD_BALANCE_NEWIDLE) {
        t0 = sched_clock_cpu(this_cpu);
        pulled_task = load_balance(this_cpu, this_rq,
                                   sd, CPU_NEWLY_IDLE,
                                   &continue_balancing);       /* C */
        domain_cost = sched_clock_cpu(this_cpu) - t0;
        if (domain_cost > sd->max_newidle_lb_cost)
            sd->max_newidle_lb_cost = domain_cost;             /* D */
        curr_cost += domain_cost;                              /* E */
    }
    update_next_balance(sd, &next_balance);
    if (pulled_task || this_rq->nr_running > 0)
        break;                                                 /* F */
}

A：遍历本 CPU 各级 domain 做均衡，做之前先更负载。B：上一段是从 CPU 视角（cache 冷热）降低 new idle balance 次数，这里再从 domain 视角卡一层。做均衡有开销，辛辛苦苦找到忙 CPU、把任务拉过来，结果自己其实没那么闲，马上又有任务落上来，那些 CPU 时间全白费。所以要两个数——平均 idle 时间和历史最大开销 max_newidle_lb_cost，平均 idle 时间不够覆盖「已花的开销 + 这一级的最大开销」就别启动。C：该 domain 支持 newidle balance 才调 load_balance()。D：记录该 domain 上 newidle balance 的最大耗时。E：累计各级 domain 的花销，控制 new idle balance 的深度。F：任何一级 domain 拉到了任务，立刻收手，不再往更高层级走，同样是控开销。E 和 F 是两个不同的标注点：curr_cost += domain_cost 是 E，break 是 F，别看串。

2、开销是怎么记的 #

其他均衡方式都由 tick 驱动，次数天然可控。new idle balance 不一样——每次 CPU 进 idle 都会触发，所以必须谨慎。内核用两个参数控频次：CPU 的平均 idle 时间，和 new idle balance 的最大开销。

成员 描述
u64 max_newidle_lb_cost（sched_domain） 该 domain 上 newidle balance 的最大耗时。每次做都记时长，取最大值存这里。这个值随时间衰减，防止一次极值造成永久影响
unsigned long next_decay_max_lb_cost（sched_domain） 控制衰减节奏。max_newidle_lb_cost 每秒乘一次 253/256，约每秒衰减 1.2%
idle_stamp（rq） 记录 CPU 进 idle 的时间点，用来算 avg_idle。CPU 执行任务期间该值为 0
avg_idle（rq） CPU 的平均 idle 时间
max_idle_balance_cost（rq） 该 CPU 做 new idle balance 的最大开销。它是各级 domain max_newidle_lb_cost 之和，下限被 sysctl_sched_migration_cost 兜住

avg_idle 的算法：newidle_balance() 时记下 idle_stamp，第一次调 ttwu_do_wakeup() 时算两者之差，得到本次 idle 时长，然后滑动平均：

text
avg_idle = avg_idle + (本次 idle 时长 - avg_idle) / 8

CPU 一次 idle 太久会把平均值带偏，所以 avg_idle 的上限被压在 2 倍的 max_idle_balance_cost。

十七、三条路径如何万法归宗到 load_balance #

路径 到 load_balance 的路 idle 参数取值
periodic trigger_load_balance() → SCHED_SOFTIRQ → run_rebalance_domains() → rebalance_domains() → load_balance() CPU_NOT_IDLE（本 CPU 有活）
nohz idle nohz_balancer_kick() → IPI → scheduler_ipi() → SCHED_SOFTIRQ → run_rebalance_domains() → nohz_idle_balance() → rebalance_domains() → load_balance()（在代表 CPU 上、对每个 idle CPU 各来一遍） CPU_IDLE
new idle pick_next_task_fair() → newidle_balance() → 遍历 domain → load_balance() CPU_NEWLY_IDLE

共性三条：入口都是 domain 遍历，都从 base domain 往上走，逐级判间隔、逐级调 load_balance()；只有 load_balance() 真的搬任务，触发层只负责「该不该在这个时间点检查」；idle 参数是行为开关，它一路传到 struct lb_env.idle，决定要不要搬 src 上最后一个任务、要不要等备选 dest、要不要一看 local 更忙就收手。读完三层触发只是拿到了「何时」，「怎么搬」全在下面十章。

1、第一段：参数与上下文 #

c
static int load_balance(int this_cpu, struct rq *this_rq,
                        struct sched_domain *sd, enum cpu_idle_type idle,
                        int *continue_balancing)              /* A */
{
    struct lb_env env = {                                     /* B */
        .sd            = sd,
        .dst_cpu       = this_cpu,
        .dst_rq        = this_rq,
        .dst_grpmask   = sched_group_span(sd->groups),
        .idle          = idle,
        .loop_break    = sched_nr_migrate_break,
        .cpus          = cpus,
        .fbq_type      = all,
        .tasks         = LIST_HEAD_INIT(env.tasks),

参数/返回值 描述
this_cpu 本次做均衡的 CPU。new idle balance 和 tick balance 下 this_cpu 就是 current cpu；nohz idle balance 下未必
this_rq 该 CPU 对应的 runqueue

env 的初始化就是填第一轮均衡的上下文，字段含义见上一章。

3、第三段：detach / attach 循环 #

c

more_balance:                                                 /* C */

        update_rq_clock(busiest);

A：要从 busiest CPU 拉任务，至少得有一个可拉的（nr_running > 1，得留一个继续跑）；拉之前先把 LBF_ALL_PINNED 立起来，后面发现不是全 pinned 再清掉。B：loop_max 是扫描 src rq 上 runnable 任务的次数，默认取 busiest runqueue 的任务数，保证每个任务都被扫到；但要压关中断时长，单次迁移不超过 sysctl_sched_nr_migrate（32 个）。C：跳 more_balance 和跳 redo 不同——新一轮只是接着扫 busiest rq 的任务链表，不重新找 busiest CPU，目的是压关中断时长。D：detach_tasks() 从 busiest rq 上摘出适合迁移的任务，同样受关中断时长限制。E：把摘下来的任务挂到 dest rq；detach_tasks() / attach_tasks() 会跑多轮，ld_moved 累计总数，cur_ld_moved 是本轮数量。F：迁移期间 src CPU 关中断，任务量大时要 break 一下放点时间出去。

1、先更新统计，再问 EAS #

2、几个能一眼判定的场景 #

3、两边都 overloaded 与 busiest 没 overloaded #

A：local 和 busiest 都 overloaded 时，用 avg_load 比拼。B：local 的平均负载比 busiest 还高，不动。C：local 的平均负载高过 domain 平均水平，不动。D：busiest 确实比 local 高，但高得不够多，还是不动——均衡要花开销，差距得到 imbalance_pct 才算事。E：busiest 没 overloaded，说明这个 domain 里各 group 的算力都能 cover 各自的任务，要不要均衡看 idle CPU 分布。F：busiest 都扛得住，而本 CPU 又是 active 的，就没必要均衡——这类均衡的目标是把 idle CPU 用起来，本 CPU 不 idle，凑什么热闹。G：busiest group 里的 idle CPU 不比 local 少（+1 是容忍度），搬过去没意义。H：busiest group 里只有一个 CFS 任务，不动。I：其余情况都要均衡，calculate_imbalance() 算不均衡度，返回 0 表示算完发现不值得搬。

4、决策矩阵 #

行是 busiest group 的状态，列是 local group 的状态：

busiest \ local has_spare fully_busy misfit imbalanced overloaded
has_spare nr_idle balanced N/A balanced balanced
fully_busy nr_idle nr_idle N/A balanced balanced
misfit force N/A N/A force force
imbalanced force force N/A force force
overloaded force force N/A force avg_load
结论 含义
balanced 该 domain 处于均衡状态，不用动
force 不均衡，calculate_imbalance() 算不均衡指数，然后尝试搬任务
avg_load 用 group 平均负载判断。尽量不动，除非差得很多（门限是 imbalance_pct）
nr_idle dest CPU 得是 idle 的，而且 local group 的 idle CPU 数多于 busiest group 的 idle CPU 数，才做均衡

N/A 那几格是拓扑上不会出现的组合，比如 local group 自己不会被判成 misfit 或 imbalanced。

二十一、更新 sched_domain 与 sched_group 的负载统计 #

1、update_sd_lb_stats：遍历 group #

c
    do {
        local_group = cpumask_test_cpu(env->dst_cpu, sched_group_span(sg));
        if (local_group) {                                    /* A */
            sds->local = sg;
            sgs = local;
            if (env->idle != CPU_NEWLY_IDLE ||
                time_after_eq(jiffies, sg->sgc->next_update))
                update_group_capacity(env->sd, env->dst_cpu);

        update_sg_lb_stats(env, sg, sgs, &sg_status);          /* B */
        if (local_group)
            goto next_group;                                   /* C */
        if (update_sd_pick_busiest(env, sds, sg, sgs)) {       /* D */
            sds->busiest = sg;
            sds->busiest_stat = *sgs;
        }
next_group:
        sds->total_load += sgs->group_load;                    /* E */
        sds->total_capacity += sgs->group_capacity;
        sg = sg->next;
    } while (sg != env->sd->groups);
    if (!env->sd->parent) {                                    /* F */
        struct root_domain *rd = env->dst_rq->rd;
        WRITE_ONCE(rd->overload, sg_status & SG_OVERLOAD);
        WRITE_ONCE(rd->overutilized, sg_status & SG_OVERUTILIZED);
    } else if (sg_status & SG_OVERUTILIZED) {
        struct root_domain *rd = env->dst_rq->rd;
        WRITE_ONCE(rd->overutilized, SG_OVERUTILIZED);

这段遍历 domain 的所有 group，刷完统计后选出两个 group：local group 和最忙的非 local group。A：更算力。base domain（手机上是 MC）只更新发起均衡那个 CPU 的算力，这里说的算力是能用于 CFS 的，要扣掉 thermal pressure 的损失、RT/DL/IRQ 的占用，见 update_cpu_capacity()；非 base domain（DIE）更本地 group 的算力，做法简单——把 child domain（MC）所有 group 的算力加起来，结果存在 group 的 sgc 里。算力不能更太勤，这里卡了两道：只有 local group 才更；new idle 时还要看时间间隔。B：更新该 group 的负载统计，下一节拆。C：local group 不参与「谁最忙」的比拼，直接跳过。D：在非 local group 里挑最忙的。E：累加 domain 的总负载和总算力。F：刷 root domain 的 overload / overutilized 状态——顶层 domain 要把各 group 的状态汇总进 root domain，非顶层 domain 只在出现 overutilized 时往上写。

2、update_sg_lb_stats 第一段：逐 CPU 累加 #

c
    for_each_cpu_and(i, sched_group_span(group), env->cpus) {
        struct rq *rq = cpu_rq(i);
        sgs->group_load    += cpu_load(rq);
        sgs->group_util    += cpu_util(i);
        sgs->group_runnable += cpu_runnable(rq);
        sgs->sum_h_nr_running += rq->cfs.h_nr_running;
        nr_running = rq->nr_running;
        sgs->sum_nr_running += nr_running;                     /* A */
        if (nr_running > 1)
            *sg_status |= SG_OVERLOAD;                         /* B */
        if (cpu_overutilized(i))
            *sg_status |= SG_OVERUTILIZED;                     /* C */
        if (!nr_running && idle_cpu(i)) {                      /* D */
            sgs->idle_cpus++;
            continue;
        }
        if (local_group)                                       /* E */
            continue;
        if (env->sd->flags & SD_ASYM_CPUCAPACITY &&
            sgs->group_misfit_task_load < rq->misfit_task_load) {
            sgs->group_misfit_task_load = rq->misfit_task_load;
            *sg_status |= SG_OVERLOAD;                         /* F */
        }
    }

A：group 负载有三个——load、runnable load、util，把 group 内所有 CPU 的三个值各自累加；除了 PELT 跟踪的 load avg，还统计了 group 里 CFS 任务数和总任务数。B：group 里有任何一个 CPU 挂着 1 个以上任务，整个 group 标 overload。C：group 里有任何一个 CPU overutilized（util 顶到算力的 80%），整个 group 标 overutilized。D：统计 idle CPU 个数，注意这个 continue——idle CPU 不参与后面的 misfit 检测。E：local group 不检测 misfit，同 group 内算力相同，不会把 misfit 任务从 local group 拉到 local group。F：domain 覆盖了不同算力的 CPU（比如 DIE）时，即便某个 CPU 上只有一个任务，只要它是 misfit task，group 也标 overload，并记录 group 内最大的 misfit task load。

3、update_sg_lb_stats 第二段：定 group_type #

c
    sgs->group_capacity = group->sgc->capacity;                /* A */
    sgs->group_weight   = group->group_weight;
    sgs->group_type = group_classify(env->sd->imbalance_pct, group, sgs);  /* B */
    if (sgs->group_type == group_overloaded)                   /* C */
        sgs->avg_load = (sgs->group_load * SCHED_CAPACITY_SCALE) /
                        sgs->group_capacity;

A：更 group 总算力和 CPU 个数，capacity 是可用于 CFS 任务的算力。B：判定 group 当前的负载状态。C：平均负载只在 overloaded 状态才算，靠它识别谁更忙。group 状态按负载从重到轻排，括号里是 group_type 的数值，越大越忙：

group_type 描述
group_overloaded（5） group 已过载，给不出算力。要同时满足两条：1、group 上总任务数（不只 CFS）大于 group 内 CPU 数，即至少有一个任务在 runnable；2、group 总 util 或总 runnable load 大于 group 总算力。判过载得留 margin，不能等 util 顶到 capacity 才动手，margin 和 imbalance_pct 相关。注意任务跑起来之后 runnable load 总大于 util：runnable load 记 running + runnable，util 只算 running time，所以 util 对 capacity 用一套 margin，runnable load 对 runnable load 用另一套
group_imbalanced（4） 因 task affinity 导致该 group 不均衡
group_misfit_task（2） group 里有 misfit task，要迁到算力更强的 CPU
group_fully_busy（1） group 没有空闲算力
group_has_spare（0） group 还有空闲算力，能接别的 group 的任务。满足任一条即此状态：1、group 总任务量小于 CPU 个数，即至少有一个 CPU idle；2、group 总算力能承载当前任务量。这里的「任务量」要同时考虑 group util 和 group runnable load

判 group 忙闲的函数是 group_classify()，对着代码看这张表最省事。先比 group_type 数值，大的更忙；相等时另有一套规则：

group_type 等值时的判断
group_overloaded 平均负载高的更忙
group_imbalanced 第一个找到的最忙
group_misfit_task 比 misfit task load，大的更忙
group_fully_busy 第一个找到的最忙
group_has_spare idle CPU 少的更忙；idle CPU 数相等时比 group 任务数

group_imbalanced 和 group_fully_busy 用「第一个找到的」是有意的：这两种状态本身已经代表有问题，谁先谁后不影响结论，省掉比较。

二十二、不均衡程度怎么算 #

calculate_imbalance() 决定两件事：用哪种迁移方式（migration_type），以及搬多少（imbalance）。

1、两个特殊状态直接给答案 #

c
    if (busiest->group_type == group_misfit_task) {
        env->migration_type = migrate_misfit;
        env->imbalance = 1;
        return;                                                /* A */
    }
    if (busiest->group_type == group_imbalanced) {
        env->migration_type = migrate_task;
        env->imbalance = 1;
        return;                                                /* B */
    }

A：busiest group 上有 misfit task，优先做 misfit 迁移，一次一个。B：busiest group 是 affinity 造成的不均衡，靠迁移任务解决，一次一个。

2、local group 有空闲算力：用 util 指导 #

c
    if (local->group_type == group_has_spare) {                /* A */
        if ((busiest->group_type > group_fully_busy) &&
            !(env->sd->flags & SD_SHARE_PKG_RESOURCES)) {      /* B */
            env->migration_type = migrate_util;
            env->imbalance = max(local->group_capacity, local->group_util) -
                             local->group_util;                /* C */
            if (env->idle != CPU_NOT_IDLE && env->imbalance == 0) {
                env->migration_type = migrate_task;
                env->imbalance = 1;                            /* D */
            }
            return;
        }
    }

A：local group 有空闲算力就尽量用起来，前提是搬过来的量既不把 local 压成 overload，也不让 busiest 没活干。B：SD_SHARE_PKG_RESOURCES 是分水岭——设了这个 flag 的 domain（MC）在 placement 阶段尽量挑 idle CPU，均衡路径得跟 placement 对齐，用 nr_running 而不是空闲算力；没设的（DIE）才走 migrate_util。C：local 有空闲、busiest 又忙（比 fully_busy 更重），用 util 指导均衡，迁的量等于 local group 当前空出来的算力。D：有些场景 local group 的 util 已经超过自己的 capacity，按 C 算出来的 imbalance 是 0，等于不搬；可如果 local CPU 是 idle 的，还是得从 busiest 搬一个 runnable 任务过来，不然性能白丢。

3、local group 有空闲算力：用 idle CPU 数指导 #

c
    if (local->group_type == group_has_spare) {
        if (busiest->group_weight == 1 || sds->prefer_sibling) {  /* A */
            unsigned int nr_diff = busiest->sum_nr_running;
            env->migration_type = migrate_task;
            lsub_positive(&nr_diff, local->sum_nr_running);
            env->imbalance = nr_diff >> 1;
        } else {                                                  /* B */
            env->migration_type = migrate_task;
            env->imbalance = max_t(long, 0, (local->idle_cpus -
                                            busiest->idle_cpus) >> 1);
        }
        return;
    }

代码走到这里，说明 busiest group 也有空闲算力，这时主要考虑搬任务，让 domain 里的 idle CPU 尽量均匀。另一种情况是 busiest 明明很忙（比 fully_busy 重），但均衡发生在 MC domain 内，处理方式一样看 idle CPU。A：base domain（group 只有一个 CPU）的目标是让任务散在各个 group（CPU）上，所以搬完之后 local 和 busiest 的任务数要相等，nr_diff >> 1 就是差一半；prefer_sibling 为真时走同一条分支——拓扑希望 sibling group 之间摊匀。B：group 里有多个 CPU，目标是 local 和 busiest 的 idle CPU 数相等。

4、local group 没有空闲算力 #

c
    if (local->group_type < group_overloaded) {                /* A */
        local->avg_load = (local->group_load * SCHED_CAPACITY_SCALE) /
                          local->group_capacity;
        sds->avg_load = (sds->total_load * SCHED_CAPACITY_SCALE) /
                        sds->total_capacity;
        if (local->avg_load >= busiest->avg_load) {
            env->imbalance = 0;
            return;
        }
    }

local 没空闲算力，但也没 overloaded，能从 busiest 搬点负载过来，代价是 local 有进入 overloaded 的风险，所以用 avg_load 再确认一次：local 的平均负载高过 busiest 就不搬。如果两边都 overloaded 且已经走进 calculate_imbalance()，说明前面比过了，busiest 的平均负载必然高于 local。两边都（或即将）overloaded，就按负载迁：

c
    env->migration_type = migrate_load;
    env->imbalance = min(
        (busiest->avg_load - sds->avg_load) * busiest->group_capacity,
        (sds->avg_load - local->avg_load) * local->group_capacity
    ) / SCHED_CAPACITY_SCALE;

取两者中的小值，保证搬完之后 local 和 busiest 都朝 domain 平均负载靠，不会矫枉过正。

migration_type 什么时候出现 imbalance 的含义
migrate_misfit busiest 是 group_misfit_task 固定 1，一次搬一个 misfit task
migrate_task busiest 是 group_imbalanced；或 local 有空闲算力但 domain 设了 SD_SHARE_PKG_RESOURCES；或 local idle 且 util 算出来是 0 要搬的任务个数
migrate_util local 有空闲算力、busiest 更忙、domain 没设 SD_SHARE_PKG_RESOURCES（DIE） 要搬的 utility 总量
migrate_load local 和 busiest 都接近或已经 overloaded 要搬的负载量

二十三、寻找 busiest group 里最忙的 CPU #

find_busiest_queue() 挑最忙的 CPU，挑法跟着 migration_type 走：

migration_type 找最忙 CPU 的方法
migrate_load cpu load / cpu capacity 最大的那个
migrate_util utility 最大的那个
migrate_task 任务最多的那个
migrate_misfit misfit task load 最重的那个

再往下有一层过滤：同一个 group 里的 CPU 会因为 affinity 完全没法接受任务，fbq_type 控制要不要跳过这类 CPU（regular 只看本地、remote 只看远端、all 都看，第一轮是 all）。最忙 CPU 一定，source 和 dest 都齐了，剩下就是搬：detach_tasks() 摘，attach_tasks() 挂。

二十四、detach_tasks 与 attach_tasks #

1、第一段：从队尾摘 #

c
    while (!list_empty(tasks)) {                              /* A */
        if (env->idle != CPU_NOT_IDLE && env->src_rq->nr_running <= 1)
            break;                                            /* B */
        p = list_last_entry(tasks, struct task_struct, se.group_node);  /* C */
        env->loop++;
        if (env->loop > env->loop_max)
            break;                                            /* D */
        if (env->loop > env->loop_break) {
            env->loop_break += sched_nr_migrate_break;
            env->flags |= LBF_NEED_BREAK;
            break;                                            /* E */
        }
        if (!can_migrate_task(p, env))
            goto next;                                        /* F */
next:
        list_move(&p->se.group_node, tasks);
    }

A：tasks 是传进来的 busiest->cfs_tasks，就是这个 rq 上全部 CFS 任务，主循环遍历它，把适合迁到目标 CPU 的任务挂进 env->tasks。B：idle balance 下没必要把 src 上唯一那个任务也拉走，拉走之后任务会一直在两边来回拉扯。C：从 cfs_tasks 队尾摘任务，链表头是最近入队的，从尾部摘能保证拿到的是 cache cold 的。D：扫完一遍或者到了循环上限（sysctl_sched_nr_migrate）就退出。E：任务多、要搬的量大的时候关中断区间太长，得分段——每 sched_nr_migrate_break 个任务标一次 LBF_NEED_BREAK 退出去，回来接着扫，把一个大临界区切成几个小的，延迟才控得住。F：不适合迁移的任务走 next，list_move() 把它挪到 cfs_tasks 头部——从队尾摘、挪到头部，等于把它排到后面再考察，不会卡住循环。

2、第二段：按 migration_type 定量 #

c
    switch (env->migration_type) {
    case migrate_load:
        load = max_t(unsigned long, task_h_load(p), 1);        /* A */
        if (sched_feat(LB_MIN) &&
            load < 16 && !env->sd->nr_balance_failed)
            goto next;                                        /* B */
        if (shr_bound(load, env->sd->nr_balance_failed) > env->imbalance)
            goto next;
        env->imbalance -= load;                               /* C */
        break;
    case migrate_util:
        util = task_util_est(p);
        if (util > env->imbalance)
            goto next;
        env->imbalance -= util;                               /* D */
        break;
    case migrate_task:
        env->imbalance--;                                     /* E */
        break;
    case migrate_misfit:
        if (task_fits_capacity(p, capacity_of(env->src_cpu)))
            goto next;
        env->imbalance = 0;                                   /* F */
        break;
    }

A：算任务负载，最小值兜到 1。B：LB_MIN 特性用来拦住小任务——LB_MIN 为真时 task load 小于 16 的任务不参与均衡，默认是 false。C：不要把超过 imbalance 的负载搬走，这里用 shr_bound() 按 nr_balance_failed 做了放宽：失败次数越多，限制越松。D：migrate_util 用任务的 util 和 imbalance 比，用的是估算后的 util（task_util_est()），不是原始值。E：migrate_task 不看 load 也不看 util，只数任务个数。F：misfit 迁移找到就跑——task_fits_capacity() 为真说明这任务在 src CPU 上跑得动，不是 misfit，跳过；是 misfit，搬走它就够，imbalance 清零。

3、摘下来之后 #

c
        detach_task(p, env);                                  /* A */
        list_add(&p->se.group_node, &env->tasks);
        detached++;
#ifdef CONFIG_PREEMPTION
        if (env->idle == CPU_NEWLY_IDLE)                      /* B */
            break;
#endif

            break;

A：走到这里说明 p 该搬（不该搬的都跳 next 了），从 src rq 上摘下来，挂进 env->tasks。B：new idle balance 是调度延迟的主要来源，所以这种均衡一次只迁一个任务。C：imbalance 搬完就退出遍历。attach_tasks() 反过来做：遍历 env->tasks，把任务一个个摘下来挂到目标 CPU 的队列上。

二十五、can_migrate_task：什么样的任务不能搬 #

第一段处理硬约束：

c
    if (throttled_lb_pair(task_group(p), env->src_cpu, env->dst_cpu))
        return 0;                                             /* A */
    if ((p->flags & PF_KTHREAD) && kthread_is_per_cpu(p))
        return 0;                                             /* B */
    if (!cpumask_test_cpu(env->dst_cpu, p->cpus_ptr)) {        /* C */
        int cpu;
        env->flags |= LBF_SOME_PINNED;
        if (env->idle == CPU_NEWLY_IDLE || (env->flags & LBF_DST_PINNED))
            return 0;                                         /* D */
        for_each_cpu_and(cpu, env->dst_grpmask, env->cpus) {   /* E */
            if (cpumask_test_cpu(cpu, p->cpus_ptr)) {
                env->flags |= LBF_DST_PINNED;
                env->new_dst_cpu = cpu;
                break;
            }
        }
        return 0;
    }

A：任务 p 所在的 task group 在 src 或 dest CPU 上被限流（bandwidth throttled），不能迁，否则限流逻辑会算错。B：per-CPU 内核线程不能迁。C：任务的 affinity 不允许它在 dest CPU 上跑，置 LBF_SOME_PINNED——至少有一个任务因 affinity 搬不了。D：已经选好备选 dest（LBF_DST_PINNED），或者是 new idle balance，直接返回；new idle 不设备选 CPU，它的目标就是往本 idle CPU 搬一个任务，搬不了就算了。E：在 dst_grpmask 和 env->cpus 的交集里给任务找个能跑的 CPU 当备选，供第二轮使用。

第二段处理软约束：

c
    env->flags &= ~LBF_ALL_PINNED;                            /* A */
    if (task_running(env->src_rq, p))
        return 0;                                             /* B */
    tsk_cache_hot = task_hot(p, env);                          /* C */
    if (tsk_cache_hot <= 0 ||
        env->sd->nr_balance_failed > env->sd->cache_nice_tries) {
        return 1;                                             /* D */
    }

A：至少有一个任务在 affinity 层面可以跑在 dest 上，LBF_ALL_PINNED 摘掉。B：正在 running 的任务不参与迁移，搬 running task 是 active balance 的活。C：判 cache hot，主要看任务上次在 src CPU 上开始执行的时间点：离现在够久（门限是 sysctl_sched_migration_cost，0.5ms），它留在 cache 里的东西早被刷掉了，算 cache cold；另外，如果 p 是 src CPU 的 next buddy 或 last buddy，直接算 cache hot。D：常规情况下只搬 cache cold 的任务，但 nr_balance_failed 超过 cache_nice_tries 之后，cache hot 的也搬——均衡做不下去的时候，cache 亲和性得给吞吐让路。

判据 结论 依据
task group 在 src/dest 上被限流 不搬 throttled_lb_pair()
per-CPU 内核线程 不搬 kthread_is_per_cpu()
affinity 不含 dest CPU 不搬，并找备选 dest p->cpus_ptr
任务正在 running 不搬 task_running()，交给 active balance
cache hot 且失败次数未超限 本轮不搬 task_hot() + cache_nice_tries
以上都不成立 可搬 ——

二十六、均衡失败与 active balance 的兜底 #

runnable 任务扫完，一个都没搬成，还有最后一手：

    } else
        sd->nr_balance_failed = 0;                            /* F */

A：没搬成，累加失败次数；这里把 new idle balance 的失败排除掉了——系统里 new idle 次数太多，累加它的失败次数会让 nr_balance_failed 虚高，容易误触发激进均衡。B：need_active_balance() 判断值不值得动 running 任务——runnable 的都搬不动了，只能看这个。C：动手之前先确认 busiest CPU 上正在跑的那个任务能不能跑在 dest 上，不能就收手，跳 out_one_pinned。D：在 busiest rq 上打 active balance 标记，记下 push_cpu。E：stop_one_cpu_nowait() 让 busiest CPU 停下来，在 stop 上下文里把任务挪到 push_cpu。F：至少搬成了一个，失败计数清零。 need_active_balance() 的门槛有三层：idle != CPU_NOT_IDLE（只有 idle 类均衡才允许）、nr_balance_failed > cache_nice_tries（失败次数够多）、src rq 上只剩一个任务（没有别的可搬）。三层都过，才动 running 任务。最后一段是收尾，主要清环境、设 balance_interval：搬成功了就调小（说明还有不均衡，尽快再来一次），没搬成就调大（别再白跑）。

二十七、易错点速查 #

  • percent 和 pct 混着用。imbalance_pct 基准是 100，但一处写成 100 * busiest->avg_load <= imbalance_pct * local->avg_load，另一处在 group_classify() 内部用 margin。别看串，两处比较对象不一样。
  • group_weight 是 CPU 个数，sum_nr_running 是任务数。busiest->group_weight == 1 判的是「group 只有一个 CPU」（base domain），不是「只有一个任务」，后者看 sum_h_nr_running。
  • sum_nr_running 含 RT/DL，sum_h_nr_running 只算 CFS。判 overload 用前者（体现 CPU 被占满），判「还有没有 CFS 任务可拉」用后者。
  • idle 参数的三种取值决定行为。CPU_NOT_IDLE 下不会搬 src 上最后一个任务，CPU_NEWLY_IDLE 一次只搬一个，CPU_IDLE 介于两者之间。同一个 load_balance()，三种行为。
  • EAS 生效期间 load_balance() 直接认输。rd->overutilized 没置位时，find_busiest_group() 第一段就 goto out_balanced。调功耗策略时发现均衡器不动，先查这个。
  • rq->next_balance 和 nohz.next_balance 不是一回事。前者管本 CPU 的 periodic 触发，后者管 nohz idle 的 IPI 触发。rebalance_domains() 里两者会同台更新，看住条件。
  • max_newidle_lb_cost 会衰减。系数 253/256，每秒一次。看到这个值很小别惊讶，那是衰减下来的。
  • LBF_ALL_PINNED 的清除位置。它在 can_migrate_task() 第二段开头被清，而判定全 pinned 是在 detach_tasks() 之后。顺序搞反会以为 affinity 判定有 bug。
  • NUMA 代码不在本篇范围内。fbq_type 的 remote 取值和 NR 相关字段都是 NUMA 场景的东西，本篇只保留 all 这条路径。
  • task placement 那几节基于 5.4.24。select_task_rq_fair() 在 5.10 里被拆得更细（wake affine 和 EAS 的边界调整过），对着 5.10 源码读放置逻辑会有出入，别以为是笔误。
