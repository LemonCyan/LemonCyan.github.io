一、一次切换到底换了什么 #

1、三种「切换」先拆开 #

很多人把「系统调用慢」和「进程切换慢」混成一笔账。它们是三件不同的事，代价差两个数量级。

类型 换的是什么 代价量级 触发者
模式切换 特权级（EL0↔EL1、ring3↔ring0）、栈指针、少量通用寄存器 数百纳秒 svc / syscall 指令
进程切换 通用寄存器、FPSIMD、TLS、栈指针、current 微秒级 schedule()
地址空间切换 TTBR0_EL1（x86 是 CR3）+ 一堆 TLB 语义 直接部分很小，间接部分很大 switch_mm()

三句话记住区别：模式切换不动 current；进程切换一定动 current；地址空间切换只是进程切换里的一步，而且切到内核线程时它根本不发生。

2、一次切换动到的全部东西 #

组件 硬件载体 保存/恢复位置 谁动手
通用寄存器 x19~x28、SP、PC、FP GPR thread.cpu_context cpu_switch_to
FPSIMD 寄存器组 v0~v31 + FPCR/FPSR thread.fpsimd_state fpsimd_thread_switch
TLS 寄存器 TPIDR_EL0、TPIDRRO_EL0 thread.tp_value tls_thread_switch
硬件断点寄存器 调试寄存器 thread.debug 一系 hw_breakpoint_thread_switch
用户页表基址 TTBR0_EL1 mm->pgd switch_mm → cpu_do_switch_mm
内核页表基址 TTBR1_EL1 全局共享，所有进程同一份 不换
地址空间标识 TTBR0_EL1 高位 mm->context.id check_and_switch_context
TLB 内容 TLB 硬件 靠 ASID 撑，或显式 flush
内核栈 SP 指向的物理页 task_struct 内的栈指针 cpu_switch_to 换 SP
lazy TLB 状态 纯软件 rq->prev_mm、x86 的 cpu_tlbstate context_switch

表里有一格最容易被误读：CR3 不是「硬件上下文」，它属于地址空间切换，和 x19~x28 那一类寄存器不是一回事——素材第 4 篇把 cr3 列进「切换硬件上下文」的清单里，那是错的，附录单列了这条。还有一处细节：换掉 TTBR0_EL1 的那一刻，进程还没换。switch_mm() 在 switch_to() 之前跑，有一小段窗口 CPU 上跑的是 A 的代码（内核态），用的却是 B 的用户页表。这不炸，因为这段代码全程在内核空间，而内核空间（TTBR1_EL1 那一半）对所有进程是同一份。

3、直接开销与间接开销 #

开销类型 具体内容 量级
直接开销 切页表基址、切内核栈、保存恢复寄存器、刷 TLB、跑调度器代码 与切换次数成正比，可测
间接开销 新进程的代码和数据不在 L1/L2 里，TLB 也变冷，头几万条指令全程 memory stall 与工作集大小相关，难测

直接开销是常数项，间接开销才是大头，而且它跟「切换前那个进程把 cache 用得多满」直接相关。跨核切换比同核更贵，原因就在这里：L1/L2 是核私有的，跨核一跳，之前暖的全没了。

二、context_switch：从 schedule 到 switch_to #

1、函数本体 #

schedule() 是壳，真正干活的是 __schedule()，它拿到 next 之后的最后一步就是 context_switch()。函数在 kernel/sched/core.c，4.4.6 的实现（素材删掉了 prepare_task_switch 那行，这里补回来）：

c
static inline struct rq *
context_switch(struct rq *rq, struct task_struct *prev,
	       struct task_struct *next)
{
	struct mm_struct *mm, *oldmm;

	prepare_task_switch(rq, prev, next);

	mm = next->mm;			/* (1) */
	oldmm = prev->active_mm;

	if (!mm) {			/* (2) next 是内核线程 */
		next->active_mm = oldmm;
		atomic_inc(&oldmm->mm_count);
		enter_lazy_tlb(oldmm, next);	/* (3) */
	} else {
		switch_mm(oldmm, mm, next);	/* (4) next 是普通进程 */
	}

	if (!prev->mm) {		/* (5) prev 是内核线程 */
		prev->active_mm = NULL;
		rq->prev_mm = oldmm;
	}

	switch_to(prev, next, prev);	/* (6) 一去不回 */
	barrier();

	return finish_task_switch(prev);
}

2、六个动作逐条过 #

rq 是本次切换发生的那个 CPU 的 run queue，prev 是被剥夺执行权的进程（下文叫 A），next 是被切入的进程（下文叫 B）。

# 动作 要点
1 取 mm、oldmm mm = next->mm，oldmm = prev->active_mm。一个取 mm 字段，一个取 active_mm 字段，这个不对称是第四章全部麻烦的源头
2 !mm ⇒ B 是内核线程 只能借 prev->active_mm，不能借 prev->mm：A 自己就可能是内核线程，mm 是 NULL
3 enter_lazy_tlb() 内核线程不碰用户地址，A 的用户空间 entry 对 B 无害，这次不刷 TLB，只打标记
4 普通进程走 switch_mm() 返回时地址空间已是 B 的，而 CPU 上跑的仍是 A 的内核态代码
5 !prev->mm ⇒ A 是内核线程 prev->active_mm = NULL 表示 A 挂起后不再占地址空间；rq->prev_mm = oldmm 把归还甩给后面的人
6 switch_to() 表面两个进程，实际三个。这句在 A 里进去，不在 A 里出来

atomic_inc(&oldmm->mm_count) 加的是 mm_count 不是 mm_users，理由在第四章。普通进程的 mm 和 active_mm 指向同一个 mm_struct；内核线程的 mm 是 NULL，但跑起来时总得有一份页表在 TTBR0_EL1 上，那份借来的就是 active_mm。素材把小标题（5）挂在 else 分支上，却说「如果 B 是内核线程就不必调用 switch_mm」，标注错位了：挂在 else 上要讲的是「B 是普通进程才走 switch_mm」。附录记了这条。

三、switch_to 为什么需要三个参数 #

c
#define switch_to(prev, next, last)			\
	do {						\
		((last) = __switch_to((prev), (next)));	\
	} while (0)

第三个参数是个左值，右边是 __switch_to() 的返回值。这一点决定了它只能写成宏，写成函数就没法回填。

c
AAA
switch_to(prev, next, prev);
BBB

A 调用这一句从 A 切到 B，此时 prev = A、next = B。A 什么时候回来、从谁的上下文里回来，A 在 AAA 那一刻不知道。

站在哪个点 prev next last 对应哪个 rq
AAA（A 切出时） A B 未知，A 不关心 CPUa 的 rq
BBB（A 切回时） A（形参） B（形参） X——把 A 切进来的那个进程 CPUx 的 rq

last 的意义就一句话：我这次是被谁换下来的。CPUa 和 CPUx 未必是同一个核，A 完全可以在另一个核上被唤醒。

finish_task_switch(prev) 要拿 prev 做善后：prev->mm 是否为空决定要不要 mmdrop(rq->prev_mm)，on_cpu 要清，state 要检查。last 传错了，善后就会善到一个跟本次切换无关的 task 头上，mm_count 直接漏掉或者多减一次。所以那个 barrier() 不是装饰：它挡在 switch_to 和 finish_task_switch 之间，保证编译器不把后面的读取提到前面去——switch_to 之后，当前栈已经换人了。

四、内核线程切换时 mm 的处理：active_mm 与 lazy TLB 的由来 #

1、两个引用计数别混 #

计数 含义 谁加减
mm_users 有多少个用户态地址空间使用者在用（线程数） mmget / mmput
mm_count 这个 mm_struct 本身有没有人引用（含「借」） mmgrab / mmdrop（4.4 直接 atomic_inc 掉 mm_count）

内核线程借一个 mm，借的是「这块 mm_struct 内存别被 free 掉」，不是「这个地址空间还有人跑用户代码」。用 mm_users 的后果：最后一个用户态线程退出时它归零，地址空间被拆，那个还在借用的内核线程手里的指针就成了野的。

2、借与还的时序 #

场景 … A ---> B(内核线程) ---> C …：

阶段 代码跑在谁的上下文 动作 mm_count
1 A 调 context_switch next->active_mm = oldmm、atomic_inc +1
2 A 调 switch_to，A 挂起 无 不变
3 B 跑起来 用的就是 A 的那份页表，TTBR0_EL1 没换 不变
4 B 被切出，进 context_switch !prev->mm 成立，rq->prev_mm = oldmm，prev->active_mm = NULL 不变
5 C 跑 finish_task_switch(B) 读 rq->prev_mm，mmdrop -1

第 4 步的判断是 if (!prev->mm)，不是 if (!prev->active_mm)。判据是「被切出的这个是不是内核线程」，而内核线程的标志就是 mm == NULL。

3、finish_task_switch 里的归还 #

c
static struct rq *finish_task_switch(struct task_struct *prev)
{
	struct rq *rq = this_rq();
	struct mm_struct *mm = rq->prev_mm;

	rq->prev_mm = NULL;

	/* ……省略 on_cpu 清理、state 检查、rq_unlock 等…… */

	if (mm)
		mmdrop(mm);

	return rq;
}

rq->prev_mm 读出来立刻清空，因为它是一次性的：一个 rq 上同时只有一次待归还的借用。这里有个「悖论」要说清：引用计数在 A 里加、在 C 里减，加和减都不在 B 里。为什么不能由 B 自己减？因为 B 从 switch_to 返回时，代码路径上已经没有「我是被谁借来的」这个信息了——switch_to 的 last 给的是「谁把我换进来」，不是「我借了谁的 mm」。这份信息只能挂在 rq 上，由下一个上场的进程代劳。

五、ARM64 的地址空间切换（TTBR0/TTBR1、ASID） #

地址空间听着玄，落到地上就是内存里的若干张 translation table。每张表的根在 mm_struct->pgd 里，从 pgd 出发能走遍这个进程的全部用户空间页表。

寄存器 管哪半 切换吗
TTBR0_EL1 用户空间（低位地址） 每次普通进程切换都要换
TTBR1_EL1 内核空间（高位地址） 全局一份，从不换 
c
static inline void switch_mm(struct mm_struct *prev, struct mm_struct *next,
			     struct task_struct *tsk)
{
	unsigned int cpu = smp_processor_id();

	if (prev == next)		/* (1) */
		return;

	if (next == &init_mm) {		/* (2) */
		cpu_set_reserved_ttbr0();
		return;
	}

	check_and_switch_context(next, cpu);	/* (3) */
}

(1) 同一个地址空间，白切。 同一进程的两个线程来回切，prev == next 时连 ASID 都不用重设。

(2) init_mm 是 swapper 的地址空间。 它的用户空间没有任何映射，把 TTBR0_EL1 指过去没有意义，所以设成「保留页表」。4.4 的实现是把 empty_zero_page 的物理地址填进 TTBR0_EL1，后来的版本换成专门的 reserved_pg_dir——版本差异，我没逐版本核对。swapper（idle）是唯一一个「不属于任何进程」的调度实体：它需要页表来跑内核代码，但不能有任何用户空间映射，否则 idle 期间一个野指针就能摸到别人的用户页。用一张空的保留页表当挡箭牌，比给它一份 init_mm 的真实用户页表更便宜也更安全。

(3) 真正干活的是 check_and_switch_context。 它处理 ASID 分配、generation 版本、pending flush，最后调 arch/arm64/mm/proc.S 里的 cpu_do_switch_mm，把 mm->pgd 的物理地址（连同 ASID）写进 TTBR0_EL1。第十、十一章展开。

六、ARM64 的 cpu_context 与 switch_to 汇编 #

1、__switch_to #

c
struct task_struct *__switch_to(struct task_struct *prev,
				struct task_struct *next)
{
	struct task_struct *last;

	fpsimd_thread_switch(next);		/* (1) */
	tls_thread_switch(next);		/* (2) */
	hw_breakpoint_thread_switch(next);	/* 与硬件断点相关 */
	contextidr_thread_switch(next);		/* 与跟踪相关 */

	dsb(ish);
	last = cpu_switch_to(prev, next);	/* (3) */

	return last;
}

(1) FPSIMD。 FP 是 float-point，SIMD 是 Single Instruction Multiple Data。它把当前 FP/SIMD 状态存回 task.thread.fpsimd_state，再把 next 的那份装进硬件。4.4 上是无条件存取的，TIF_FOREIGN_FPSTATE 那套懒加载优化是后面版本才完善的。

(2) TLS。 涉及 TPIDR_EL0、TPIDRRO_EL0 和 task.thread.tp_value。线程库的 thread pointer、errno 的实现、栈保护金丝雀，都靠它。

(3) dsb(ish)。 之前那些写寄存器的动作，在下一条指令之前必须对 inner shareable domain 可见。少了它，cpu_switch_to 里的内存访问会看到旧状态。

2、cpu_context 布局与 cpu_switch_to #

thread.cpu_context 是一块连续的 13 个 8 字节槽位，THREAD_CPU_CONTEXT 是它相对 task_struct 的偏移（offsetof 算出来）：

槽位 内容 槽位 内容
+0 x19 +56 x26
+8 x20 +64 x27
+16 x21 +72 x28
+24 x22 +80 x29（FP）
+32 x23 +88 SP
+40 x24 +96 PC（LR/x30）
+48 x25 — —

代码在 arch/arm64/kernel/entry.S：

armasm
ENTRY(cpu_switch_to)
	mov	x10, #THREAD_CPU_CONTEXT	// (1) 取 thread.cpu_context 偏移
	add	x8, x0, x10			// (2) x8 = &prev->thread.cpu_context
	mov	x9, sp
	stp	x19, x20, [x8], #16		// (3) 存 prev 现场
	stp	x21, x22, [x8], #16
	stp	x23, x24, [x8], #16
	stp	x25, x26, [x8], #16
	stp	x27, x28, [x8], #16
	stp	x29, x9,  [x8], #16
	str	lr, [x8]			// PC 落到最后一个槽

	add	x8, x1, x10			// (4) x8 = &next->thread.cpu_context
	ldp	x19, x20, [x8], #16		// (5) 恢复 next 现场
	ldp	x21, x22, [x8], #16
	ldp	x23, x24, [x8], #16
	ldp	x25, x26, [x8], #16
	ldp	x27, x28, [x8], #16
	ldp	x29, x9,  [x8], #16
	ldr	lr, [x8]			// PC 进 lr
	mov	sp, x9				// (6) 换栈
	ret					// (7) PC ← lr

3、为什么只存 11 个寄存器 #

因为 cpu_switch_to 在 ABI 眼里就是个普通函数。AAPCS64（ARM 标准过程调用文档 IHI0056）规定：x19~x28 是 callee-saved，x29(FP)、x30(LR)、SP 也是现场的一部分；x0~x18 是 caller-saved，函数调用前后本来就不保证不变，被调函数没有义务保存。

寄存器组 ABI 约定 cpu_switch_to 要存吗
x0~x18 caller-saved 不存，调用者自己负责（要留的已由编译器压在栈上）
x19~x28 callee-saved 存，11 个槽里占 10 个
x29(FP)、x30(LR)、SP 现场的一部分 全存，LR 就是 PC

于是「保存上下文」被 ABI 白送了一半：编译器已经在调用点把要留的 caller-saved 寄存器压到栈上了，cpu_switch_to 只要存 callee-saved 那批。栈指针一换，整条栈就是另一个进程的了。

ret 把 x30（从 next 的槽位里 ldr 出来的那份 LR）装进 PC。那份 LR 是 next 当初调 cpu_switch_to 时留下的返回地址，指向 next 的 __switch_to 里调用点之后。所以「返回到调用者」这句话是对的，只是返回到的不是同一个调用者——switch_to 一去不回，直到某个 CPU 从别的进程切回 A。

七、TLB 是什么、为什么切换会伤它 #

MMU 每次访存都要走一遍页表：pgd → pud → pmd → pte → 物理地址，每一级都要读内存。为了不每次都走，CPU 把最近用过的翻译结论塞进一个小而快的表里，这就是 TLB（Translation Lookaside Buffer——素材写成了 "Translation lookasid buffer"，拼错了）。一个 entry 里装着 VA tag、PA、页大小（4KB/16KB/64KB，大页还有 2MB/1GB 级）、权限位、global/local 标志，支持 ASID 时还有「这份翻译属于哪个地址空间」。

形态 命中条件 进程切换要做什么
无 ASID 只看 VA + 权限 必须让旧 entry 全失效，否则同 VA 撞出新 PA
有 ASID VA + ASID 一起比 换 ASID 即可，旧 entry 留着无害

「撞出」得说清。进程 A 里虚拟地址 0x400000 映射到物理页 Pa，进程 B 里同一个 0x400000 映射到 Pb。TLB 里要是同时留着两条 0x400000 的 entry 而硬件分不清它们属于谁，B 就会读到 Pa——这不是性能问题，是数据错乱。

页表描述符里有个 bit 标「这份翻译是否全局」。内核空间的映射对所有进程一样，标 global；用户空间的映射随进程走，标 local。硬件把那个 bit 一起缓存进 TLB entry，于是 flush 就能分粒度：flush all 和 flush local only。这个区分是第八章「暴力 flush 不行」的破题点。

八、单核场景：暴力 flush 为什么不行 #

A 切到 B 时把整个 TLB 和 cache 刷干净，正确性 100%，B 面对的是一台刚从产线下来的机器。代价：B 一开跑，取指 miss、取数 miss、翻译 miss 三连，前几十万条指令全在等内存。切换越频繁，这个冷启动成本被乘的次数越多。

方案 正确性 性能 代价
flush all 对 差 每次切换 B 全冷，内核映射也白刷
flush local only（保留 global） 对 中 内核映射保住，进程 entry 全丢
ASID，不 flush 对（硬件分得清） 好 需要 ASID 分配与回收机制

第二行是 Linux 在支持 global bit 之后的常规做法：切进程时只清 local entry。第三行是 ARM64 的选择，原因在第十章。

1、两个可以不刷的场景 #

(1) A 切到内核线程 K。 地址空间没换，K 只碰内核地址，A 留下的用户 entry 对 K 无影响。这就是 lazy TLB 的物理理由。(2) 同一进程的两个线程互切。 同一个 mm，switch_mm() 里 prev == next 直接 return，TLB 一点不动。

2、A→K→A 的收益 #

时刻 CPU 上跑的 TTBR0_EL1 TLB 里的 A entry
t0 A A 的 pgd 热
t1 K（内核线程） 仍是 A 的 pgd 保留，没刷
t2 A A 的 pgd 还是热的

t2 时 A 醒来，TLB 直接命中。要是 t1 按「进程切换必刷」办，A 醒来得先花几万纳秒把 TLB 重新焐热。在 I/O 密集的负载里，A→kworker→A 这种三明治一秒能出现上万次。

九、多核场景：TLB shootdown 与 IPI #

两个变化：每个核有自己的 TLB，所以「刷 TLB」要指定范围；进程能被调度到任何核上，所以同一个进程的 entry 会散落在多个核的 TLB 里。

维度 单核 多核
TLB 归属 一份，本核 每核一份，互不可见
flush 范围 本核就够 分「本核 local」与「全系统」两种操作
进程残留 一处 到处留情
一致性手段 无 IPI（x86）或 tlbi ...is（ARM64）
lazy TLB 的意义 省一次重建 省一次 IPI + 一次重建

1、一个 4 核的例子 #

CPU 跑什么 当前 active 的 mm
CPU_0 A0（进程 A 的线程） A
CPU_1 一个内核线程，借用了 A1 的地址空间 A（lazy）
CPU_2 A2（进程 A 的线程） A
CPU_3 B（不相关进程） B

A0 改了自己的页表（比如 mmap 之后第一次写触发了 COW），CPU_0 上那份 A 的 entry 失效了，得刷。但 CPU_1 和 CPU_2 上也有 A 的 entry，同样失效了，也得刷。CPU_3 不用管，它的 active mm 是 B。结论：shootdown 的目标集合 = 所有「当前 active mm 等于目标 mm」的核。这个集合要靠 mm_cpumask 一类的记账维护，核越多，集合越大，IPI 越多。

2、两条硬件路线 #

架构 全系统 flush 怎么做 说明
x86 只能发 IPI，让每个核自己执行 invlpg / 重载 CR3 一次 shootdown 就是一轮核间通信
ARM64 tlbi vmalle1is 之类的 ...is 指令，一条指令广播到 inner shareable domain 不用 IPI，但要配 dsb/isb 才生效

is 后缀是 inner shareable。这条指令省掉了 IPI 的分发和等待，但没省掉「所有核的 TLB 都变冷」这件事本身。

回到上表里的 CPU_1。它跑的是内核线程，借 A 的地址空间。收到「刷 mm A」的 IPI 时，它其实可以不刷：内核线程不碰用户地址，A 的 entry 留在 TLB 里对它是死数据。等这个内核线程被切出、切进新进程 C 时，switch_mm() 会换 TTBR0_EL1（x86 是重载 CR3），那一下就把残留全带走了。于是 lazy TLB 模式下的处理变成「记一笔，不执行」——这就是第十一章 tlb_flush_pending 那个 cpumask 的用途。

十、ARM64 的 ASID 管理：版本号与 rollover #

ARM64 在指令集里给了广播式 TLB 维护，shootdown 的分发成本比 x86 低。有了这个前提，支持 ASID 就划算：进程切换时干脆不碰 TLB，让硬件按 ASID 区分。代价从「刷 TLB」转移到「管 ASID」——硬件给的位数有限，用完了得回收，而回收必然要刷。

ASID 宽度 编码空间 由谁报告
8 bit 2^8 = 256 个 ID_AA64MMFR0_EL1.ASIDBits
16 bit 2^16 = 65536 个 同上

素材写「最大 256 或者 65535 个 ID」，16 bit 那半差了一个：编码空间是 65536。内核另有一部分值不参与用户 ASID 分配（0 有特殊含义、generation 编码要留位），所以「可用数」小于编码空间，但这跟 65535 不是一回事。

1、software ASID：一个 64 位字段装两样东西 #

位段 内容 作用
低 asid_bits 位（8 或 16） HW ASID 真正写进 TTBR0_EL1 的那部分
其余高位 generation（版本号） 标识这个 HW ASID 属于哪一批

命中判断就变成一次异或，同 generation 且 HW ASID 非零 ⇒ 高位全等 ⇒ 整个 ! 取反后为真 ⇒ 走快路径。一次异或加一次移位，不用比对两个字段：

c
!((asid ^ atomic64_read(&asid_generation)) >> asid_bits)

2、new_context：分配与 rollover #

c
static u64 new_context(struct mm_struct *mm, unsigned int cpu)
{
	static u32 cur_idx = 1;
	u64 asid = atomic64_read(&mm->context.id);
	u64 generation = atomic64_read(&asid_generation);

	if (asid != 0) {			/* (1) 老 mm，已有 software asid */
		u64 newasid = generation | (asid & ~ASID_MASK);

		if (check_update_reserved_asid(asid, newasid))
			return newasid;

		asid &= ~ASID_MASK;
		if (!__test_and_set_bit(asid, asid_map))
			return newasid;
	}

	asid = find_next_zero_bit(asid_map, NUM_USER_ASIDS, cur_idx);	/* (2) 找空闲 HW asid */
	if (asid != NUM_USER_ASIDS)
		goto set_asid;

	generation = atomic64_add_return_relaxed(ASID_FIRST_VERSION,	/* (3) 满了，换代 */
						 &asid_generation);
	flush_context(cpu);

	asid = find_next_zero_bit(asid_map, NUM_USER_ASIDS, 1);		/* (4) 新代里重找 */

set_asid:
	__set_bit(asid, asid_map);
	cur_idx = asid;

	return asid | generation;
}

(1) 老 mm 的处理。 新建 mm 时 mm->context.id 是 0。非 0 说明它以前拿过 software ASID，那就把高位换成当代 generation；如果这个 HW ASID 在 asid_map 里还保留给它，直接返回。__test_and_set_bit 返回 0 表示这一位原来是 0，抢到了。(2) 真需要新 HW ASID。 从 cur_idx 往后找第一个零位，找到就跳 set_asid 收工。(3) 找不到 ⇒ HW ASID 用光 ⇒ 换代。 ASID_FIRST_VERSION 加一次，asid_generation 前进，flush_context() 把 asid_map 清空。(4) 新代里重新分配。 asid_map 已经全零，这次从 1 开始找必然能找到。

3、rollover 的账 #

事件 asid_generation asid_map 各核 TLB
系统启动 ASID_FIRST_VERSION 全 0 空
分配 N 个 mm（N < 容量） 不变 N 位置 1 逐渐填充
第 N+1 个 mm 来了 加一个 ASID_FIRST_VERSION 全清 0 全部作废（旧代）
此后每个核切入新一代 mm 不变 重新填 该核执行 local_flush_tlb_all

关键点：换代那一刻，全系统的旧 ASID 立刻失效，但没有主动去刷每个核。每个核要等到自己第一次切入「新一代」的地址空间时，才在 check_and_switch_context 里发现自己拿着旧代的 ASID，顺手刷一次本核。刷得晚，但刷得省——flush_context() 只把软件侧的 asid_map 归零，硬件侧的清理交给各核自理。

十一、切换过程中的 TLB 与 ASID 代码走读 #

代码在 arch/arm64/mm/context.c：

c
void check_and_switch_context(struct mm_struct *mm, unsigned int cpu)
{
	unsigned long flags;
	u64 asid;

	asid = atomic64_read(&mm->context.id);			/* (1) */

	if (!((asid ^ atomic64_read(&asid_generation)) >> asid_bits)	/* (2) */
	    && atomic64_xchg_relaxed(&per_cpu(active_asids, cpu), asid))
		goto switch_mm_fastpath;

	raw_spin_lock_irqsave(&cpu_asid_lock, flags);
	asid = atomic64_read(&mm->context.id);
	if ((asid ^ atomic64_read(&asid_generation)) >> asid_bits) {	/* (3) */
		asid = new_context(mm, cpu);
		atomic64_set(&mm->context.id, asid);
	}

	if (cpumask_test_and_clear_cpu(cpu, &tlb_flush_pending))	/* (4) */
		local_flush_tlb_all();

	atomic64_set(&per_cpu(active_asids, cpu), asid);
	raw_spin_unlock_irqrestore(&cpu_asid_lock, flags);

switch_mm_fastpath:
	cpu_switch_mm(mm->pgd, mm);
}

(1) 拿这份地址空间的 software ASID。(2) 快路径。 同一个 generation 且本核 active_asids 原来非零，直接跳到 cpu_switch_mm——只写寄存器，一次 TLB 操作都没有。这是常态。(3) 慢路径。 generation 对不上，说明这份 mm 拿到的是旧代的 ASID，要重新分配。加锁是必须的：asid_map 是全局的（4.4 时期；后面版本改成 per-CPU 的 asid_map，锁粒度跟着变，这点我没逐版本跟）。(4) 补上欠着的 flush。 tlb_flush_pending 是一个 per-CPU 的 cpumask，标记「本核欠一次全刷」，test_and_clear 既判断又清除，保证只刷一次。

atomic64_xchg_relaxed 那步要单说：它在同一个原子操作里读旧值、写新值。旧值为 0 表示本核还没跑过任何带 ASID 的地址空间，快路径就不成立（&& 左边为真、右边为假），必须走慢路径把 active_asids 填上。

1、x86 的 lazy TLB 长什么样 #

ARM64 的 enter_lazy_tlb() 是空的，要看 lazy TLB 的实现只能看 x86：

c
static inline void enter_lazy_tlb(struct mm_struct *mm, struct task_struct *tsk)
{
#ifdef CONFIG_SMP
	if (this_cpu_read(cpu_tlbstate.state) == TLBSTATE_OK)
		this_cpu_write(cpu_tlbstate.state, TLBSTATE_LAZY);
#endif
}

就一句软件状态写入，不碰任何硬件寄存器。#ifdef CONFIG_SMP 是因为单核上 lazy 模式省不出东西——没有别的核会给你发 shootdown。

2、ARM64 与 x86 的 TLB 策略对照 #

维度 ARM64（4.4） x86-64（4.4）
地址空间寄存器 TTBR0_EL1 CR3
标识符 ASID 无（PCID 未进主线）
谁处理 TLB 软件负责，配 ASID 后可免刷 硬件在写 CR3 时自动刷本核 local entry
全系统刷 tlbi ...is 一条指令 IPI 逐核
lazy TLB 空函数 TLBSTATE_LAZY
延迟 flush 的载体 tlb_flush_pending cpumask cpu_tlbstate + lazy 检查

x86 那条「写 CR3 = 自动刷」既是历史包袱也是省事的设计，副作用是每次进程切换都强制一次本地 TLB 冷启动。ARM64 把决定权交给软件，才有了「配 ASID ⇒ 可以不刷」这条路。PCID 在 4.4 时期的 x86 主线上不支持（KVM 里有用），所以上表那行「无 PCID」是当时的事实；PCID 进主线是后来的事，具体版本我没核对。

十二、schedule() 里的同步语义（preempt_count、中断、need_resched） #

1、两种切换与骨架 #

主动让出：进程等资源等不下去，自己调 schedule()。被动抢占：别人把你换掉。抢占有五个常见触发点——时间片用完、中断上下文里唤醒了更高优先级的任务、别的进程上下文里唤醒了更高优先级的任务、别的进程上下文里改了调度参数、还有一堆别的。

抢占不是立刻发生的。设置 need_resched = 1，然后等最近的调度点，调度点到了才真正进 schedule()。这个「延迟」是整个同步机制成立的前提。

c
asmlinkage __visible void __sched schedule(void)
{
	do {
		preempt_disable();			/* a */
		raw_spin_lock_irq(&rq->lock);		/* b */
		/* 选择 next task */
		/* 切到 next task 执行 */
		raw_spin_unlock_irq(&rq->lock);		/* c */
		sched_preempt_enable_no_resched();	/* d */
	} while (need_resched());			/* e */
}

2、preempt_count 的位域 #

thread_info 里那个 preempt_count 是一个 32 位整数，切成几段。4.4 的布局：

位段 字段 偏移 宽度 含义
bit 0~7 preempt counter 0 8 显式 preempt_disable 的嵌套深度
bit 8~15 softirq counter 8 8 关下半部的嵌套深度
bit 16~19 hardirq counter 16 4 中断嵌套深度
bit 20 NMI_MASK — 1 NMI 中
bit 21~ 各种 *_OFFSET 标志 — — PREEMPT_ACTIVE 等

三段里任何一段非零，内核就不许调度。这就是「原子上下文」的定义。

3、从 X 切到 Y 的计数变化 #

位置 谁在跑 动作 谁的 preempt_count 变了
进入前 X 调用者保证为 0 X，值 0
a X preempt_disable() X，值 1
b X raw_spin_lock_irq()：持 rq 锁 + 关本核中断 X，值 2
切换 X → Y switch_to 换栈，current 变 Y X 停在 2，没人管
c Y raw_spin_unlock_irq()：放 rq 锁 + 开中断 Y，值 1
d Y sched_preempt_enable_no_resched() Y，值 0
e Y 检查 need_resched() Y，值 0

注意 c、d 两步操作的是谁的计数：switch_to 之后 current 已经指到 Y，所以减的是 Y 的。X 的那份停在 2，躺在 X 的内核栈和 thread_info 里，等 X 下次被调度回来，从 switch_to 之后接着执行，继续 raw_spin_unlock_irq，把 2 减回 1、再减回 0。栈换了，所以「同一个函数里的两句代码，跑在两个不同的进程上」。这是理解 schedule() 同步语义的唯一钥匙。

4、rq 锁跨进程释放 #

b 点在 X 上加锁，c 点在 Y 上解锁，中间没有「同时持有」的窗口——锁一直是被持有的，只是持有者换人了。所以这把锁保护的不是「某个进程」，而是「run queue 这个数据结构」。raw_spin_lock_irq 里的「关中断」有个陷阱：它不记录关之前中断是什么状态，c 点的 raw_spin_unlock_irq 会无条件打开中断。这个问题在第十四章展开。

十三、为什么禁止抢占时不能调 schedule #

text
preempt_disable
……schedule……
preempt_enable

你已经禁止抢占了，又主动调 schedule()，逻辑上确实拧巴。但内核不能崩，得有个说得过去的处理。

schedule() 期待 caller 的 preempt_count 等于 0——只有 0 才说明「当前任务可以被换掉」。而 schedule() 自己在 a 点会 preempt_disable()，那一刻它需要「CPU 与当前 task 的绑定不变」：cpu 不变、current 不变、rq 不变。所以 a 点之后、b 点之前这段窗口，preempt_count 的正确值应该是 1。

c
static inline void schedule_debug(struct task_struct *prev)
{
	if (unlikely(in_atomic_preempt_off())) {
		__schedule_bug(prev);
		preempt_count_set(PREEMPT_DISABLED);
	}
	/* ……省略 lockdep、rcu、state 检查等…… */
}

in_atomic_preempt_off() 在 a 点之后被调用，它期待的是「preempt counter == 1，softirq/hardirq == 0，PREEMPT_ACTIVE 未置」。对不上就说明在原子上下文里调度了，__schedule_bug() 打印诊断信息——那句 BUG: scheduling while atomic 加一串栈回溯就是它。

打完诊断，内核把 preempt_count 硬写成 PREEMPT_DISABLED，也就是「进入 schedule() 的正确姿势」，然后继续调度。这个选择很能说明 Linux 的取舍：宁可在半错的状态下往前爬，也不要为了一个可以诊断的错把机器停掉。厂商内核常见的做法相反——检测到就 panic()，理由是「早死早修」。

十四、为什么关中断也不能随便调 schedule #

text
local_irq_disable
……schedule……
local_irq_enable

这段往往不是你直接写的——很多内核 API 会隐含睡眠，你随手一调，形态就成了上面这样。从 X 切到 Y 时，如果 X 关着中断就切过去、而中断一直不恢复，Y 会一路裸奔直到自己主动让出 CPU，这不能容忍。所以 b 点的 raw_spin_lock_irq 无条件关中断，c 点的 raw_spin_unlock_irq 无条件开中断：不管 caller 关没关，进的时候关掉，切完之后打开。

1、素材漏掉的那半个代价 #

「不影响调度」这话只对了一半。真正被破坏的是 caller 的临界区语义。如果 Y 就是 X（a~d 转一圈又切回来），那 X 的临界区在 schedule() 里被提前打开了：

你以为的 实际的
local_irq_disable → 临界区全程关中断 临界区在 schedule() 的 c 点被提前开了一次
local_irq_enable 才恢复 恢复是第二次开，local_irq_enable 变成假保证

后果是「关中断保护的那个数据结构」会被中断处理程序摸到。这条比「调度被打乱」隐蔽得多，也危险得多。

2、关中断 ≠ 禁抢占 #

方向是对的：关了中断确实不会被抢占。但两者不等价，差别在抢占点。

保护区写法 退出时有没有抢占检查 高优先级任务何时能上
preempt_disable() … preempt_enable() 有。preempt_enable() 里检查 need_resched 退出那一刻立刻
local_irq_disable() … local_irq_enable() 没有，只恢复中断 拖到下一个抢占点

中断那条有个补偿：一旦开中断，pending 的中断会进来，中断返回路径上会检查抢占。所以「关中断期间被唤醒的高优先级任务」能在中断返回时被换上。

3、补偿不到的那个场景 #

text
（1）local_irq_disable
（2）wake_up_process(高优先级任务)      ← 本核上唤醒
（3）local_irq_enable

try_to_wake_up() 里会设 need_resched 并检查抢占，但此刻中断关着，检查不成立，不调度。等到了（3），local_irq_enable() 里没有抢占检查点，于是这个本该立刻抢占的高优先级任务被硬生生拖到下一个调度点。拖多久？取决于这段代码后面还有多长、下一个抢占点（preempt_enable()、中断返回、cond_resched()）什么时候来。在实时性敏感的路径上，这就是延迟抖动的来源。

十五、中断上下文中睡眠会怎样：一次真实实验 #

1、实验设定与驱动 #

准则人人都背得出来：中断上下文里不能睡眠。可「不能」到底会怎样？我们写了个专门在中断上下文里调 schedule() 的驱动，看真实后果。实验平台：x86-64 + 标准 4.4 内核（素材没给发行版与具体小版本）。

Makefile（M= 指模块目录，不是内核树；两条 recipe 行必须是 tab），Kbuild 只有一行 obj-m := cst.o：

xxxx 是原作者的用户名，换成你的。驱动本体（素材的多行 #include 在抓取时丢了，这里按用到的符号补齐）：

c
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/timer.h>
#include <linux/sched.h>
#include <linux/preempt.h>

#define DRIVER_DESC "context schedule test driver"

static struct timer_list cst_timer;

static void cst_timer_handler(unsigned long data)
{
	struct task_struct *p = current;

	pr_info("=====in timer handler=====\n");
	pr_info("cst shoot %16s [%x] task:\n", p->comm, preempt_count());

	mod_timer(&cst_timer, jiffies + HZ);

	schedule();		/* 故意在中断上下文里睡眠 */
}

static int __init cst_init(void)
{
	init_timer(&cst_timer);
	cst_timer.function = cst_timer_handler;
	cst_timer.expires = jiffies + HZ;
	add_timer(&cst_timer);

	pr_info(DRIVER_DESC " : init on cpu:%d\n", smp_processor_id());

	return 0;
}
module_init(cst_init);

static void __exit cst_exit(void)
{
	del_timer_sync(&cst_timer);
	pr_info(DRIVER_DESC " : exit\n");
}
module_exit(cst_exit);

MODULE_DESCRIPTION(DRIVER_DESC);
MODULE_AUTHOR("linuxer");
MODULE_LICENSE("GPL");

init_timer() / timer_list.function 是 4.4 的写法；5.x 换成 timer_setup() 加 from_timer()，直接照抄编不过。

素材里的 ps –eo 和 tail –f 用的是 en dash（U+2013），抄下来会报 command not found，这里改成了 ASCII 连字符。

3、结果 #

系统没死，模块正常跑，靶机一直 alive，平方根照算。唯一异常是日志：每隔 1 秒 dump 一次栈。按驱动的格式串加 4.4 的位域重建日志骨架（素材只描述了「dump stack 一次」，没贴原始日志，下面是骨架不是原文，省略的栈回溯约 15~25 帧）：

text
=====in timer handler=====
cst shoot          cst_test [100] task:
BUG: scheduling while atomic: cst_test/0x00000100/<pid>, CPU: 2
Call trace: ... 省略 素材未贴出的栈回溯，约 15~25 帧 ...
...
=====in timer handler=====
cst shoot          cst_test [100] task:
BUG: scheduling while atomic: cst_test/0x00000100/<pid>, CPU: 2   ← 一秒一次，重复

[100] 这个值不是抄的，是按第十二章那张位域表推的：softirq 段非零、其它段为零，SOFTIRQ_SHIFT = 8，所以是 0x100。要是在硬中断里跑同样的实验，这里会变成 0x10000。那句 BUG: scheduling while atomic 就是第十三章 __schedule_bug() 的输出。

素材说「每隔 1 秒随机命中一个进程」，这个说法得改。add_timer() 把定时器挂到当前 CPU 的 timer base 上，之后（除非被 timer migration 搬走）回调就在那个 CPU 的 timer softirq 里跑，命中的是那一刻该 CPU 上的 current。所以它不是全系统随机挑，而是「钉在 init 那个核上，撞谁算谁」。这也是为什么素材要多开几个靶机——让 4 个核都别闲着，免得永远撞上 idle。

顺带一个精度问题：这个回调在 softirq 上下文里跑，不是硬中断。定时器到期在硬中断里标记，cst_timer_handler() 本身在 TIMER_SOFTIRQ 里执行。所以 preempt_count() 打出来的是 SOFTIRQ_OFFSET（0x100），不是硬中断的 0x10000 那一档。素材通篇说「中断上下文」，严格说是「软中断上下文」。

4、为什么没死 #

命中时 内核栈上已有什么 中断压入后
用户态 空的（只有入口帧） 中断现场 + 中断处理各帧 + cst_timer_handler 帧
内核态 系统调用进来的一串 stack frame 在其上继续压中断现场 + 处理帧 + handler 帧

schedule() 一调，靶机的现场继续往下压，调度器挑下一个。靶机还在 runqueue 里，早晚被调度回来。回来之后，CPU 从 cst_timer_handler 里 schedule() 后面那行继续，中断处理收尾，从内核栈恢复中断现场，原路返回。

一切看着都对。但这个实验证明不了「中断上下文能睡眠」，它只证明「这一次运气好」。反例很好造：在内核态持锁时被中断命中，然后调度走，锁没放，下一个想拿这把锁的进程就死等。素材建议读者自己改代码试，这个建议照做——你会看到真正的 hang 或者 lockdep 报错。

5、根本原因 #

调度器的调度实体是线程。一个调度实体得有 task_struct，有栈，有状态（runnable / sleeping），能进 runqueue，能被 switch_to 换进换出。中断上下文不是调度实体——它没有自己的 task_struct，内核没法「调度它」。这是设计者的选择，也让调度器保持简单：只有一种实体要排队。

# 规则
1 中断上下文不是调度实体
2 中断上下文的优先级高于任何进程上下文

第二条是第一条的推论：既然中断上下文不排队、不参与调度，那它只能是「插队」的——一旦中断到达，除非本地中断被关掉，任何进程（用户态或内核态）或内核线程都挡不住它。在中断上下文里睡眠，同时破坏了这两条：一个非调度实体去请求调度，一个最高优先级的执行流去排队等别人。内核检测到了也不 panic，是想尽量爬完；厂商内核直接 panic，是想尽早暴露。

十六、切换开销：实测法与工具 #

1、令牌往返法 #

两个进程互为令牌的收发方。A 收到令牌后阻塞，B 发出令牌后等接收也阻塞。跑 N 次往返取平均。编译运行（源码素材没附，只给了这两条命令）：

bash
gcc main.c -o main
./main

text
Before Context Switch Time: 1565352257 s, 774767 us
After Context Switch Time: 1565352257 s, 842852 us
项目 数值 说明
起始时间戳 1565352257 s + 774767 µs 原文数据，未复现
结束时间戳 1565352257 s + 842852 µs 原文数据，未复现
时间差 68085 µs（68.085 ms） 本文按两行相减得出
素材结论 平均每次约 3.5 µs 原文数据，未复现
反推次数 68085 / 3.5 ≈ 19453 次 素材没给循环次数，这是从结论倒推

这个 3.5 µs 有个含糊处，得说破：素材既没给 N，也没说「一次」指单次切换还是一次往返。按往返算，单次切换是 1.75 µs；按单次算，就是 3.5 µs。两种读法差一倍，而你拿不到 N 就没法判定。原文数据，未复现，就这么标。素材还有一句对照：之前测系统调用时最低值是 200 ns。这个对比站得住——系统调用只跨一次特权级，进程切换要换栈、换页表、跑调度器。

2、直接开销与间接开销 #

动作 是否每次必做
切换页表基址（TTBR0_EL1 / CR3） 普通进程间必做，切内核线程不做
切换内核栈 必做
保存恢复硬件上下文（通用寄存器、FPSIMD、TLS） 必做
刷 TLB 看架构：x86 靠写 CR3 带出来，ARM64 靠 ASID 免掉
执行调度器代码（选 next、记账、负载更新） 必做

素材把 ip / bp / sp / cr3 一起列成「硬件上下文」，cr3 混进去了。ip（ARM64 的 PC/LR）、bp（x29）、sp 是寄存器现场，cr3 是地址空间寄存器，在 ARM64 上对应 TTBR0_EL1。归错类别会让人以为「切页表 = 切寄存器」，两者代价差一个量级。

间接开销那半素材认了它测不准：切到新进程，L1/L2 里热的代码和数据全废了，头几万条指令一路 memory stall；跨核切换更狠，因为 L1/L2 是核私有的。令牌实验里两个进程在同核上互切，cache 还是热的，量出来的只是下界。

3、lmbench #

lmbench 是开源基准测试工具，覆盖文档读写、内存操作、进程创建销毁、网络性能。对切换开销，它测的是 lat_ctx：用 2、8、16 个进程，配 0K/16K/64K 三档数据量，故意把 cache footprint 撑大。素材输出（表格是原文数据，我只重排了列对齐，值没动）：

Host OS 2p/0K 2p/16K 2p/64K 8p/16K 8p/64K 16p/16K 16p/64K
bjzw_46_7 Linux 2.6.32- 2.7800 2.7800 2.7000 4.3800 4.0400 4.7500 5.4800

单位按 lmbench lat_ctx 的惯例是微秒（素材没标单位，这是推定）。怎么读这张表：

对比 数字变化 结论
2p/0K → 2p/16K 2.78 → 2.78 数据量小到 16K，还没把 cache 撑爆
2p/16K → 2p/64K 2.78 → 2.70 基本持平，甚至略降（噪声量级）
2p → 8p 2.78 → 4.38 进程数上去了，切换开销翻近一倍
8p → 16p 4.38 → 4.75 继续涨，但增幅变小

2p 那三列几乎不动，说明进程数比数据量更影响切换开销——进程多了，每个进程的 cache 份额被摊薄，跨进程的 cache 冲突变多。这个结论比单看一个数字有用。

素材这里写「从 rsyslog 的数据来看」，是笔误：这张表是 lmbench 的输出，跟 rsyslog 没关系。OS 列的 Linux 2.6.32- 是截断的，完整版本号在 lmbench 原始输出里被列宽吃掉了，这里照抄截断形态，没有补全——补了就是编数据。

4、线程版 #

Linux 里没有「真正的」线程，只有轻量级进程：有独立的 task_struct 和 pid，但共享 mm、代码段、全局变量、打开的文件。getpid() 在同进程的两个线程里返回同一个值，因为它返回的是 tgid，不是 pid。

素材实验（test06）：20 个线程，用管道互传信号，收到就唤醒下一个、自己睡。编译与输出：

bash
gcc -lpthread main.c -o main

text
0.508250 4.363495

素材结论：平均一次线程切换约 3.8 µs，和进程切换差别不大。这两列是什么单位、各代表什么、N 是多少，素材都没写。原文数据，未复现。结论本身合理：线程切换虽然省掉 switch_mm（prev == next 直接 return），但寄存器保存恢复、调度器代码一样不少，省下来的那点占比不大。

6、一次真实负载的账 #

素材的实验环境：8 核 8G 的 KVM 虚拟机，上面跑 nginx + php-fpm（fpm 数量 1000），每秒约 100 个请求，cswch 列显示每秒约 4 万次切换。把数字摊开：

项目 计算 结果
全系统每秒切换 素材观测 约 40000 次
单核每秒切换 40000 / 8 约 5000 次
单核每秒耗在切换上 5000 × 3.5 µs 17.5 ms
单核占比 17.5 ms / 1000 ms 1.75%
全系统每秒总耗时 40000 × 3.5 µs 140 ms

素材写「每秒消耗近 20 毫秒用于上下文切换」，口径是单核，和算出来的 17.5 ms 对得上。不指明单核，读者容易误以为全系统只花 20 ms——那反而显得切换很便宜。

再看 pidstat 那几行：fpm 跑在阻塞模式，每次访问 Redis / Memcached / MySQL 都要等，所以自愿切换占绝大多数（160 vs 34、131 vs 8）。非自愿切换只在时间片耗尽时发生，占比小——这台机器的问题不在抢占，在等待。

7、结论 #

结论 数值 可信度
进程切换耗时 2.7 ~ 5.48 µs（lmbench） 原文数据，未复现
单次切换（令牌法） 约 3.5 µs 原文数据，未复现；N 未知
线程切换 约 3.8 µs 原文数据，未复现；单位与 N 不明
系统调用 最低 200 ns 原文数据，未复现
lmbench 比令牌法可信 — 因为它把 cache footprint 也算进去了

想在自己机器上复现，令牌法最快，但一定要把两个进程绑到不同核上再跑一次，否则你测的只是同核切换的下界。

十七、易错点速查 #

现象 / 说法 实际 定位
「切 cr3 是保存硬件上下文」 cr3/TTBR0_EL1 属于地址空间切换，不是寄存器现场 一、十六
「内核线程切换要 switch_mm」 不切。借 prev->active_mm，走 enter_lazy_tlb 二、四
「内核线程借 prev->mm」 借 prev->active_mm。prev 自己是内核线程时 mm 为 NULL 二
「借 mm 时加 mm_users」 加 mm_count。借的是内存，不是用户态使用者 四
「B 自己归还借来的 mm」 由下一个上场的 C 在 finish_task_switch 里 mmdrop 四
「switch_to 返回就是切回自己」 返回到的是被别的进程切回来的那个点，所以要三个参数 三
「ARM64 切换要存全部寄存器」 只存 callee-saved：x19~x28 + FP + SP + PC 六
「ARM64 切地址空间会刷 TLB」 配了 ASID 就不刷，快路径只写寄存器 十一
「ASID 16 bit 能编 65535 个」 编码空间 2^16 = 65536 十
「tlbi vmalle1is 一条指令就完事」 要配 dsb / isb 才真正生效 九
「关中断调 schedule 无害」 调度不乱，但 caller 的临界区在 c 点被提前开中断 十四
「关中断等于禁抢占」 不等价：preempt_enable 有抢占点，local_irq_enable 没有 十四
「定时器回调在硬中断里」 在 TIMER_SOFTIRQ 软中断里，preempt_count 是 0x100 十五
「context_switch 不调 prepare_task_switch」 4.4 在 context_switch 里调，素材把它删了 二
「init_timer 现在还能用」 4.4 能用，5.x 换成 timer_setup 十五
