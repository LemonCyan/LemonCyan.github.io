进程标识和进程凭证本来是两条线，但在内核里交汇在同一处：copy_process()。前半程从 ID 讲到 struct pid，再讲 pid namespace 怎么把「一个整数」变成「一个二元组」；中间插进凭证，说清 uid/euid/suid/fsuid 各管什么；最后回到 fork，看这些字段怎么被复制、被清掉、被延迟检查。原稿有几处口径是 2.6 甚至 2.6.29 之前的，我没整段删，而是就地标注「旧口径 → 现行实现」，你翻老代码时能立刻知道那份材料的年代。

一、进程在内核里长什么样：task_struct 与 thread_info #

内核不区分进程和线程，都用 task_struct 抽象。区别只在共享了多少东西：共享 mm、files、sighand 和同一个 tgid 的一组 task_struct，用户空间看就是一个多线程进程。4.18 起（基于 4.18 源码）它被显式切成两段：

c
struct task_struct {
#ifdef CONFIG_THREAD_INFO_IN_TASK
    struct thread_info    thread_info;
#endif
    volatile long         state;
    randomized_struct_fields_start
    void                  *stack;
    atomic_t              usage;
    unsigned int          flags;
    ...
    randomized_struct_fields_end
    struct thread_struct  thread;   /* 必须在最后，大小随架构变 */
};

randomized_struct_fields_start/end 之间的成员编译期随机排布，让针对结构体偏移的 exploit 不好写。代价是这段里不能指望稳定偏移，硬编码 offsetof 的代码会挂。

thread_info 与内核栈的关系按版本和架构分三种：

版本 / 架构 thread_info 位置 THREAD_SIZE 怎么拿 current
2.6.x / 3.14 x86-32 内核栈低地址端，与栈共用 8K esp & ~(THREAD_SIZE - 1)
3.14 x86-64 同上 THREAD_SIZE_ORDER = 1，2 页 per_cpu(kernel_stack) + KERNEL_STACK_OFFSET - THREAD_SIZE
4.9 起 CONFIG_THREAD_INFO_IN_TASK task_struct 第一个成员 栈里不再放元数据 直接 current->thread_info

3.14 x86-64 不再从 rsp 掩码算，改用 per-cpu 变量：

c
/* arch/x86/include/asm/thread_info.h, 3.14, x86-64 */
DECLARE_PER_CPU(unsigned long, kernel_stack);

static inline struct thread_info *current_thread_info(void)
{
    return (void *)(this_cpu_read_stable(kernel_stack) +
                    KERNEL_STACK_OFFSET - THREAD_SIZE);
}

3.14 的 thread_info 本体（x86）字段少但都有用：task 指回进程描述符，exec_domain 是执行域（第十一节用到），flags/status 放 TIF_* 这种汇编层要立刻访问的标志，addr_limit 是内核态能碰的用户地址上界（set_fs() 改的就是它，5.10 后整个删掉）。两边指针互指：thread_info->task → task_struct，task_struct->stack → 这块栈；task_thread_info() 就是一次强转（有这个配置项时返回 &task->thread_info，否则是老写法 (struct thread_info *)(task)->stack）。x86-32 上 thread_info 和栈往中间长：栈从高往低，thread_info 在最底，中间隔一个 STACK_WARN（THREAD_SIZE/8）告警线。所以老内核「栈溢出」表现千奇百怪——它往往先踩掉 thread_info，然后 current 就是个垃圾指针。

二、四种 ID 与它们的语义（POSIX 视角与 Linux 线程组模型） #

1、POSIX 的四个层次 #

进程是资源分配单位；线程是调度单位，同进程内线程共享地址空间、fd、信号处理；多个进程组成进程组（job control）；多个进程组组成会话（一次登录）。用户态接口对得上：getpid/getppid、gettid（Linux 专有，glibc 2.30 才给同名包装，之前只能 syscall(SYS_gettid)）、getpgid/setpgid/getpgrp/setpgrp、getsid/setsid。

2、Linux 的映射 #

内核给每个执行实体都分一个 task_struct、都有自己的 ID，于是 POSIX 的「进程 ID」在 Linux 里变成了「线程组 ID」：

POSIX 概念 接口 内核名 4.4 里实际存在哪
进程 ID getpid tgid task->group_leader->pids[PIDTYPE_PID].pid，另有缓存字段 task->tgid
线程 ID gettid pid task->pids[PIDTYPE_PID].pid，另有缓存字段 task->pid
进程组 ID getpgid pgrp task->group_leader->pids[PIDTYPE_PGID].pid
会话 ID getsid session task->group_leader->pids[PIDTYPE_SID].pid

三个结论记住省很多事：leader 的 pid 等于 tgid，非 leader 线程的 pid 与 tgid 不同但 tgid 与 leader 一致；POSIX 只要求线程 ID 在进程内唯一，Linux 给的是全系统唯一，所以 gettid() 的值能直接扔进 /proc 查；task->pid、task->tgid 是缓存值，权威来源是 pids[] 里的 struct pid，copy_process() 里 p->pid = pid_nr(pid) 就是在填缓存。

3、旧口径：2.6 早期是怎么取的 #

process identification.md 基于 2.6 早期，路径和现在不同：

c
/* 2.6 早期，来源：process identification.md */
asmlinkage long sys_getpid(void)  { return current->tgid; }
asmlinkage long sys_gettid(void)  { return current->pid; }
static inline pid_t process_group(struct task_struct *tsk)
{ return tsk->signal->pgrp; }
static inline pid_t process_session(struct task_struct *tsk)
{ return tsk->signal->__session; }

那个年代 pgid 和 sid 就是 signal_struct 里两个 pid_t，因为它们天然是整个线程组共享的属性。后来变了：2.6.19 引入 pid_link 和 pids[]，把 pgid/sid 也统一成 struct pid *；pid namespace 合入后 struct pid 又长出 upid 数组。2.6.28 的 signal_struct 还留着这两个字段，但已标 __deprecated：

c
/* include/linux/sched.h, 2.6.28 —— 旧字段已弃用，新路径走 pids[] */
union { pid_t pgrp __deprecated; pid_t __pgrp; };
union { pid_t session __deprecated; pid_t __session; };

static inline struct pid *task_pgrp(struct task_struct *task)
{ return task->group_leader->pids[PIDTYPE_PGID].pid; }

所以「signal->pgrp 表示进程组 ID」只在 2.6.19 之前成立。手上材料带这个说法，直接按年份排除。

4、getsid 的一处 POSIX 偏离 #

POSIX 要求 getsid(pid) 在 pid 不是 session leader 时报错，Linux 不干，总是返回该进程所在会话 ID。2.6 的代码一眼看穿——find_task_by_pid() 找到就 process_session(p) 返回，根本没有 leader 检查：

c
/* 2.6 早期，来源：process identification.md —— 没有 leader 检查 */
if (!pid) { return process_session(current); }
read_lock(&tasklist_lock);
p = find_task_by_pid(pid);
retval = -ESRCH;
if (p) { retval = security_task_getsid(p);
         if (!retval) retval = process_session(p); }
read_unlock(&tasklist_lock);

这个偏离一直保留。写可移植代码时别假设非 leader 会返回 -EPERM。

三、内核怎么抽象这些 ID：struct pid 与 upid #

1、struct upid #

用户空间一个正整数够，内核不够：同一个数字在不同 pid namespace 里指不同进程，所以必须是「namespace + 数字」二元组。

c
/* include/linux/pid.h, 4.4 */
struct upid {
    /* Try to keep pid_chain in the same cacheline as nr for find_vpid */
    int nr;
    struct pid_namespace *ns;
    struct hlist_node pid_chain;
};

nr 是本 ns 里的号，ns 是这个 namespace，pid_chain 是全局哈希表 pid_hash 的链表节点——用户态传个整数进来（比如 kill），内核靠它快速定位 upid。哈希把 nr 和 ns 指针一起搅进去（hash_long((unsigned long)nr + (unsigned long)ns, pidhash_shift)），pid_hash 槽数按内存伸缩，16 到 4096，由 pidhash_init() 里的 alloc_large_system_hash 决定。

2、struct pid #

c
/* include/linux/pid.h, 4.4 */
struct pid
{
    atomic_t count;
    unsigned int level;
    /* lists of tasks that use this pid */
    struct hlist_head tasks[PIDTYPE_MAX];
    struct rcu_head rcu;
    struct upid numbers[1];
};

count 是引用计数——一个 session 里所有 task 的 pids[PIDTYPE_SID].pid 都指向同一个 struct pid，不共用计数就乱。level 是这个 ID 所属 ns 在树上的层级，同时等于 numbers[] 有效元素个数减一。tasks[PIDTYPE_MAX] 是三个链表头，把「用这个 ID 的 task」串起来，是从 ID 反查 task 的快路径。rcu 给 call_rcu(&pid->rcu, delayed_put_pid) 用，等宽限期过了再真释放。numbers[1] 是变长数组写法，分配时按 level 一次性拿 level + 1 个 upid。

这里有个极易踩的索引约定：numbers[0] 是 root ns 的号，numbers[pid->level] 才是这个 ID 所属（最内层）ns 的号。新手容易反着理解。

为什么值得为它单独抽个对象，pid.h 注释讲得比大部分文章清楚：光存 pid_t 有「PID 回绕后指错进程」的问题，存 task_struct * 有「进程退了但 10K 内核内存被钉住」的问题（THREAD_SIZE + sizeof(struct task_struct)），存 struct pid 两个一起解决——它只有 64 字节左右。

3、pid_link 与 pids[] #

前面提了两个方向的需求：从 task 找 struct pid，从 struct pid 找回所有 task。前者靠 pid_link（struct hlist_node node; struct pid *pid;），pid 指向具体 struct pid，node 是这个 task 挂到 pid->tasks[type] 上的钩子。task_struct 里放个数组 struct pid_link pids[PIDTYPE_MAX]; 再加一条 struct list_head thread_group;——后者是另一条线索：同线程组的 task 挂在 leader 的 thread_group 链上，遍历线程组走它，不走 pids[]。

enum pid_type 只有三种（4.4）：PIDTYPE_PID、PIDTYPE_PGID、PIDTYPE_SID。tid 和 tgid 共用 PIDTYPE_PID：一个 task 指向自己作为线程的 ID；它作为线程组成员的进程 ID 要靠 group_leader 绕一下。对 leader 自己，两个指针指同一个 struct pid；对普通线程，指两个不同的 struct pid。

三个链表分别挂谁：

这个 struct pid 的身份 tasks[PIDTYPE_PID] tasks[PIDTYPE_PGID] tasks[PIDTYPE_SID]
只当线程 ID 1 个 task 空 空
当进程 ID（leader 的 pid） 该线程组全部 task 空 空
当进程组 ID 空 组内所有 leader 空
当会话 ID 空 空 会话内所有 leader

pgid/sid 链表挂的是各线程组 leader，不是每个线程——原因很简单，pgid 和 sid 是线程组级属性，copy_process() 里只对 thread_group_leader(p) 才 init_task_pid(p, PIDTYPE_PGID, ...) 并 attach_pid(p, PIDTYPE_PGID)。4.19 起 enum pid_type 变四个，多一个显式 PIDTYPE_TGID，让「按线程组 ID 找 task」不必再走 group_leader 那一跳；pids[] 也拆成了各自独立的 pid_links[]。

四、pid namespace：level 与可见性 #

pid namespace 就是 pid 的地址空间隔离，容器 A 和 B 里可以同时存在 pid 等于 1 的进程，它们在 root ns 里是两个不同数字。struct pid_namespace（4.4）里关心三个：level（自己是第几层，root 是 0）、parent（父 ns）、child_reaper（本 ns 的 init，负责收尸）；pidmap + last_pid 是编号分配器，hide_pid 对应 hidepid 挂载项。

层级与 ID 个数，按源码索引约定：

ns level 需要几个 upid numbers[] 有效下标 这个进程在哪些 ns 可见
0（root） 1 0 只有 root ns
1 2 0, 1 root ns 与自己
2 3 0, 1, 2 root、父、自己

规律：位于 level x 的进程需要 x + 1 个号，因为每往上一层还有一个。可见性单向：外层能看到内层的号，内层看不到外层。alloc_pid() 从内层往外层逐个要号，把层次落到了实现上：

c
/* kernel/pid.c, 4.4 */
tmp = ns;
pid->level = ns->level;
for (i = ns->level; i >= 0; i--) {
    nr = alloc_pidmap(tmp);
    if (IS_ERR_VALUE(nr)) { retval = nr; goto out_free; }
    pid->numbers[i].nr = nr;
    pid->numbers[i].ns = tmp;
    tmp = tmp->parent;
}

i 从 ns->level 递减到 0，tmp 顺 parent 往上爬，所以 numbers[0] 天然是 root ns 的号。由此也有了 ns_of_pid()：

c
/* include/linux/pid.h, 4.4 */
static inline struct pid_namespace *ns_of_pid(struct pid *pid)
{
    struct pid_namespace *ns = NULL;
    if (pid)
        ns = pid->numbers[pid->level].ns;   /* 最内层那个 */
    return ns;
}

两个实操坑：CLONE_NEWPID 不影响调用者自己的 ns，copy_process() 给子进程分号用的是 p->nsproxy->pid_ns_for_children，新 ns 从子进程开始生效，所以经典写法是先 unshare(CLONE_NEWPID) 再 fork()；ns 里的 pid 1 死了整个 ns 的进程都被内核杀掉，它的 signal_struct->flags 上打了 SIGNAL_UNKILLABLE，除内核自己发的信号，普通 SIGKILL 也杀不掉。

五、从代码看取值路径 #

1、四个 helper（4.18 源码） #

c
/* include/linux/sched.h, 4.18 */
static inline struct pid *task_pid(struct task_struct *task)
{ return task->pids[PIDTYPE_PID].pid; }
static inline struct pid *task_tgid(struct task_struct *task)
{ return task->group_leader->pids[PIDTYPE_PID].pid; }
/* Without tasklist or RCU lock it is not safe to dereference
 * the result of task_pgrp/task_session even if task == current,
 * we can race with another thread doing sys_setsid/sys_setpgid. */
static inline struct pid *task_pgrp(struct task_struct *task)
{ return task->group_leader->pids[PIDTYPE_PGID].pid; }
static inline struct pid *task_session(struct task_struct *task)
{ return task->group_leader->pids[PIDTYPE_SID].pid; }

task_pid/task_tgid 可以直接读，线程组归属不会变；task_pgrp/task_session 会变（setpgid、setsid 会改），注释明说要加锁。写模块时读到 NULL 直接 oops。

2、getpid / gettid / getppid #

4.4 的本体只有一行，getppid 多一层 RCU：

c
/* kernel/sys.c, 4.4 */
SYSCALL_DEFINE0(getpid)  { return task_tgid_vnr(current); }
SYSCALL_DEFINE0(gettid)  { return task_pid_vnr(current); }
SYSCALL_DEFINE0(getppid)
{
    int pid;
    rcu_read_lock();
    pid = task_tgid_vnr(rcu_dereference(current->real_parent));
    rcu_read_unlock();
    return pid;
}

getppid 要 RCU，因为 real_parent 会被 reparent 改掉（父进程退出时子进程过继给 init 或 subreaper）；getpid 不用，current 的线程组不会变。task_tgid_vnr() 是包装，ns == NULL 表示「用 current 的 ns」，落到下面这个函数：

c
/* kernel/pid.c, 4.4 */
pid_t __task_pid_nr_ns(struct task_struct *task, enum pid_type type,
                       struct pid_namespace *ns)
{
    pid_t nr = 0;
    rcu_read_lock();
    if (!ns) ns = task_active_pid_ns(current);
    if (likely(pid_alive(task))) {
        if (type != PIDTYPE_PID) task = task->group_leader;
        nr = pid_nr_ns(rcu_dereference(task->pids[type].pid), ns);
    }
    rcu_read_unlock();
    return nr;
}

3、pid_nr_ns：翻译成某个 ns 里的号 #

c
/* kernel/pid.c, 4.4 */
pid_t pid_nr_ns(struct pid *pid, struct pid_namespace *ns)
{
    struct upid *upid;
    pid_t nr = 0;
    if (pid && ns->level <= pid->level) {
        upid = &pid->numbers[ns->level];
        if (upid->ns == ns) nr = upid->nr;
    }
    return nr;
}
pid_t pid_vnr(struct pid *pid)
{ return pid_nr_ns(pid, task_active_pid_ns(current)); }

两道检查各有含义。ns->level <= pid->level 挡「从内层看外层」，直接返回 0；upid->ns == ns 挡「同 level 的兄弟 ns」——两个容器同层，一个容器的进程在另一个里必须查不到。pid_vnr() 用 task_active_pid_ns(current)，关键就在这：返回的号是「以调用者所在 ns 的视角」看到的号。容器里 ps 显示 1，宿主机显示 12345，差别只在这一个参数。

4、find_task_by_vpid：从号反查 task #

号 + ns → struct pid，再 struct pid → task：

c
/* kernel/pid.c, 4.4 */
struct pid *find_pid_ns(int nr, struct pid_namespace *ns)
{
    struct upid *pnr;
    hlist_for_each_entry_rcu(pnr, &pid_hash[pid_hashfn(nr, ns)], pid_chain)
        if (pnr->nr == nr && pnr->ns == ns)
            return container_of(pnr, struct pid, numbers[ns->level]);
    return NULL;
}

struct task_struct *pid_task(struct pid *pid, enum pid_type type)
{
    struct task_struct *result = NULL;
    if (pid) {
        struct hlist_node *first;
        first = rcu_dereference_check(hlist_first_rcu(&pid->tasks[type]),
                          lockdep_tasklist_lock_is_held());
        if (first) result = hlist_entry(first, struct task_struct, pids[(type)].node);
    }
    return result;
}
struct task_struct *find_task_by_vpid(pid_t vnr)
{ return find_task_by_pid_ns(vnr, task_active_pid_ns(current)); }

container_of 那句是这套设计的精髓：只知道 upid 地址，靠 numbers[ns->level] 的偏移把 struct pid 的头算出来。这也是为什么 numbers[] 必须按 ns level 有序放。pid_task 只取链表第一个元素：对 PIDTYPE_PID 链表长度恒为 1 没问题，对 pgid 取到的是进程组某个 leader，够用。hlist_entry(..., pids[(type)].node) 依赖「三个 pid_link 在数组里、节点偏移随 type 变」，4.19 改成独立 pid_links[] 后写法也跟着变了。

5、getpgid 的完整路径 #

c
/* kernel/sys.c, 4.4 */
SYSCALL_DEFINE1(getpgid, pid_t, pid)
{
    struct task_struct *p; struct pid *grp; int retval;
    rcu_read_lock();
    if (!pid) grp = task_pgrp(current);
    else {
        retval = -ESRCH;
        p = find_task_by_vpid(pid);
        if (!p) goto out;
        grp = task_pgrp(p);
        if (!grp) goto out;
        retval = security_task_getpgid(p);
        if (retval) goto out;
    }
    retval = pid_vnr(grp);
out:
    rcu_read_unlock();
    return retval;
}

三条路径：pid == 0 直接 task_pgrp(current)；非 0 先 find_task_by_vpid（进入当前 ns 视角）再取对方 task_pgrp；无论哪条，最后都 pid_vnr() 换算成当前 ns 的号。中间的 security_task_getpgid() 是 LSM 钩子。getpgrp() 就是 return sys_getpgid(0);，四个接口结构完全一样，只有取哪个 helper 不同：

接口 取哪个 helper 换算 版本注意
getpid task_tgid task_tgid_vnr 2.6 直接返回 current->tgid
gettid task_pid task_pid_vnr 2.6 直接返回 current->pid
getppid task_tgid(real_parent) task_tgid_vnr 4.x 起必须 RCU
getpgid task_pgrp pid_vnr 2.6.19 前读 signal->pgrp
getsid task_session pid_vnr 2.6.19 前读 signal->__session

六、进程凭证：从 UID/GID 到 struct cred #

进程要访问文件、给别的进程发信号、申请 IPC 对象，内核得先答「你是谁，你凭什么」。五个 ID 的全家桶：

类别 成员 管什么
real uid / gid 你到底是谁。记账、/proc/pid/status 用它
effective euid / egid 你此刻以谁的身份行动，绝大多数判权的依据
saved suid / sgid 你曾经是谁，给「临时降权再升回来」留后路
file-system fsuid / fsgid 只用于文件访问判定，Linux 特有
supplementary group_info 你还在哪些组里

1、2.6.29 之前：字段直接躺在 task_struct 里 #

c
/* include/linux/sched.h, 2.6.11 —— 直接躺在 task_struct 里 */
uid_t uid,euid,suid,fsuid;
gid_t gid,egid,sgid,fsgid;
struct group_info *group_info;
kernel_cap_t   cap_effective, cap_inheritable, cap_permitted, cap_bset;

/* include/linux/cred.h, 2.6.28 —— 只剩一堆宏 */
#define current_uid()   (current->uid)
#define current_fsuid() (current->fsuid)
#define current_cap()   (current->cap_effective)

/* include/linux/sched.h, 3.14 —— 2.6.29 起抽成独立对象 */
const struct cred __rcu *real_cred;  /* objective and real subjective (COW) */
const struct cred __rcu *cred;       /* effective (overridable) subjective (COW) */

三个版本并排看很清楚。旧做法的毛病：改一个字段就原地改 task_struct，做不到写时复制，也没法让 struct file、struct socket 各持一份凭证。新做法挂在 task_struct 上的只剩两个 const 指针（还有一个 ptracer_cred 记录 tracer 的凭证）。const 是有意的：凭证一旦提交就不可变，要改只能 prepare_creds() 复制、改完 commit_creds() 换上，RCU 读者天然安全。

2、struct cred 全貌 #

c
/* include/linux/cred.h, 3.14 */
struct cred {
    atomic_t    usage;
    kuid_t      uid;   kgid_t gid;    /* real UID/GID of the task */
    kuid_t      suid;  kgid_t sgid;   /* saved UID/GID of the task */
    kuid_t      euid;  kgid_t egid;   /* effective UID/GID of the task */
    kuid_t      fsuid; kgid_t fsgid;  /* UID/GID for VFS ops */
    unsigned    securebits;
    kernel_cap_t cap_inheritable, cap_permitted, cap_effective, cap_bset;
    struct user_struct    *user;       /* real user ID subscription */
    struct user_namespace *user_ns;    /* caps/keyrings 相对哪个 userns */
    struct group_info     *group_info; /* supplementary groups */
    struct rcu_head        rcu;
};

容易看漏的：user 是 user_struct，RLIMIT_NPROC 和打开文件数这类按用户统计的资源就记在它的 processes、files 上；user_ns 决定这些 capability 相对哪个 user namespace 有意义；security 是 LSM 私有指针（SELinux label 挂这里）。

3、subjective 与 objective #

cred.h 的注释把设计讲得最清楚：objective context 是「别的 task 想影响我时」用的，subjective context 是「我去操作别的对象时」用的。落到字段上：

指针 语义 谁用它 举例
task->cred subjective 本进程去操作别人时 打开文件、kill 别人
task->real_cred objective 别人来操作本进程时 别人 kill 我、异步 I/O 完成后文件给我发信号

绝大多数时候两者指同一个 struct cred。分开的场合是 override_creds()——内核里「临时借别人身份干一件事」，改的只是 subjective 那一半。

七、real/effective/saved 与 file-system ID 的区别与用途 #

1、real 与 effective #

real ID 决定「你是谁的进程」：/proc/pid/status 里 Uid: 第一列，RLIMIT_NPROC 也按 real uid 算。effective ID 决定「你此刻能干什么」，创建时两者相同，除非可执行文件带 Set-User-ID 位——/usr/bin/passwd 那种权限位是 rwsr-xr-x，那个 s 就是。张三执行它：real uid 是张三，euid 是 root，suid 是 root。

2、saved 保存的是 effective，不是 real #

变量名 suid 极其误导，process credentials.md 那句提醒有价值，我加重搬过来：它保存的是 effective ID。为什么保存？因为进程该以尽可能小的权限运行，以 root 起的 passwd 只在写 /etc/shadow 那几行需要特权：

c
uid_t saved = geteuid();   /* root —— 内核里的 suid 此时也是 root */
seteuid(getuid());         /* 降到张三：euid=张三，suid 仍是 root */
/* ... 干不敏感的活 ... */
seteuid(saved);            /* 靠 suid 还在，升回去 */

非特权进程的 euid 只能在 real 和 saved 之间切，第三个值一律 EPERM。这就是「降权后还能爬回来」的全部机制，也是 setuid 程序被打穿后危害这么大的原因。

3、fsuid：只给文件系统看的那一份 #

传统 UNIX 文件访问按 euid 判，Linux 多一个 fsuid，VFS 只用它：

c
/* fs/namei.c, 3.14 */
static int acl_permission_check(struct inode *inode, int mask)
{
    unsigned int mode = inode->i_mode;
    if (likely(uid_eq(current_fsuid(), inode->i_uid)))
        mode >>= 6;
    else {
        ...
        if (in_group_p(inode->i_gid))
            mode >>= 3;
    }
    ...
}

为什么需要？NFS。B 主机进程要访问 A 主机文件，实际读写的是 A 上的 nfsd。如果改 nfsd 的 euid，那用户态任意进程都能给 nfsd 发信号搞事（信号判权也看 euid）。所以单独留一个只影响文件判定的 ID。process credentials.md 在这里下的结论我要纠正：它说「2.0 之后采用了方案二，因此 file-system ID 应该是被废弃的」。事实是两条路都走了——信号判权改成了基于 real/effective ID（跟 fsuid 无关），同时 fsuid 没废，还成了 VFS 判权的正式入口。4.4 的 kernel/sys.c 里 setfsuid() 活得很好：

c
/* kernel/sys.c, 4.4 —— setfsuid() 的判权与返回值 */
if (uid_eq(kuid, old->uid)  || uid_eq(kuid, old->euid)  ||
    uid_eq(kuid, old->suid) || uid_eq(kuid, old->fsuid) ||
    ns_capable(old->user_ns, CAP_SETUID)) {
    if (!uid_eq(kuid, old->fsuid)) {
        new->fsuid = kuid;
        if (security_task_fix_setuid(new, old, LSM_SETID_FS) == 0)
            goto change_okay;
    }
}
abort_creds(new);
return old_fsuid;     /* 注意：返回旧的 fsuid，不是错误码 */

顺带记住这个设计失误：setfsuid() 返回旧值而非错误码，失败时返回值等于原值，所以「成功没有」在 API 层面不可判定。POSIX 里根本没这个函数。

4、四个 ID 的联动规则 #

setuid() 系列改的不是一个 ID，是一组。4.4 kernel/sys.c 的规则：

调用 有 CAP_SETUID 无 CAP_SETUID fsuid 怎么变
setuid(uid) uid/euid/suid 全设成新值 只能是 real 或 saved 的值，否则 EPERM 跟 euid
setreuid(r, e) 三个都能改 每个值只能落在 {real, euid, suid} 跟 euid
setresuid(r, e, s) 三个都能改 同上 跟 euid
setfsuid(uid) 随便设 只能是 {real, euid, suid, fsuid} 之一 只改 fsuid

「fsuid 跟 euid」在代码里就是一句 new->fsuid = new->euid;，setuid/setreuid/setresuid 末尾都有。唯一例外是 setfsuid()，它单独改 fsuid。execve 是凭证变化最剧烈的地方，3.14 的 prepare_binprm() 先无条件把 euid/egid 拉回当前值，再看 setuid 位：

c
/* fs/exec.c, 3.14 —— prepare_binprm()：先复位，再看 setuid 位 */
bprm->cred->euid = current_euid();
bprm->cred->egid = current_egid();
if (!(bprm->file->f_path.mnt->mnt_flags & MNT_NOSUID) &&
    !current->no_new_privs &&
    kuid_has_mapping(bprm->cred->user_ns, inode->i_uid) &&
    kgid_has_mapping(bprm->cred->user_ns, inode->i_gid)) {
    if (mode & S_ISUID) {
        bprm->per_clear |= PER_CLEAR_ON_SETID;
        bprm->cred->euid = inode->i_uid;
    }
    ...
}

注意 MNT_NOSUID 和 no_new_privs 两个闸门：挂载点带 nosuid 时 setuid 位无效，进程打了 PR_SET_NO_NEW_PRIVS 后也无效。容器运行时大量靠这两条关掉宿主机的 setuid 提权面。真正安装新凭证是 install_exec_creds() 里的 commit_creds(bprm->cred)，同时把 suid 设成新 euid，完成「saved = 当前 effective」的复制。

八、supplementary groups #

一个用户可以在多个组里，uid/gid 只能表示主组，附属组是另一套结构：

c
/* include/linux/cred.h, 3.14 */
#define NGROUPS_SMALL        32
#define NGROUPS_PER_BLOCK    ((unsigned int)(PAGE_SIZE / sizeof(kgid_t)))
struct group_info {
    atomic_t    usage;
    int         ngroups, nblocks;
    kgid_t      small_block[NGROUPS_SMALL];
    kgid_t      *blocks[0];
};
#define GROUP_AT(gi, i) \
    ((gi)->blocks[(i) / NGROUPS_PER_BLOCK][(i) % NGROUPS_PER_BLOCK])

设计上是个二维结构：前 32 个组内嵌在 small_block[]，不额外分配（绝大多数用户不需要 32 个组）；超过了才申请整页的 blocks[]。访问一律走 GROUP_AT()，别自己算下标。

group_info 是独立对象、带引用计数，所以 struct cred 复制时只 get_group_info() 共享它——这是抽成独立对象的直接好处，prepare_creds() 里就是 memcpy(new, old, sizeof(struct cred)) 之后 get_group_info()、get_uid()、get_user_ns() 各加一次引用。判权函数两个：

函数 比什么 用在哪
in_group_p(gid) fsgid + 附属组 文件 / 目录访问
in_egroup_p(gid) egid + 附属组 非文件类判定（IPC 等）

process credentials.md 末句「supplementary group IDs 会配合 file-system ID 和 effective ID 判定」要拆开看：文件访问用的是 fsuid + fsgid + 附属组（in_group_p），不是 effective ID。模块里拿 in_egroup_p() 判文件权限，结论会和用户态 open() 不一致。登录流程里的来源：login 从 /etc/passwd 拿主组、从 /etc/group 扫附属组，然后 setgroups() 写进去；之后 fork 出来的子进程共享同一个 group_info，直到某个进程再调 setgroups()。

九、从 _do_fork 到 copy_process：一次 fork 都做了什么 #

1、用户空间的三条路 #

接口 clone flags 父进程阻塞吗 用途
fork() SIGCHLD 不 常规创建进程，COW
vfork() CLONE_VFORK | CLONE_VM | SIGCHLD 阻塞到子进程 exec/exit 省掉页表复制
clone() 用户指定 看 flags 线程、namespace 隔离

3.14 的三个入口：

c
/* kernel/fork.c, 3.14 —— 三入口，clone 另有 CLONE_BACKWARDS{2,3} 变体 */
SYSCALL_DEFINE0(fork)
{
#ifdef CONFIG_MMU
    return do_fork(SIGCHLD, 0, 0, NULL, NULL);
#else
    return -EINVAL;   /* can not support in nommu mode */
#endif
}
SYSCALL_DEFINE0(vfork)
{ return do_fork(CLONE_VFORK | CLONE_VM | SIGCHLD, 0, 0, NULL, NULL); }
SYSCALL_DEFINE5(clone, unsigned long, clone_flags, unsigned long, newsp,
         int __user *, parent_tidptr, int __user *, child_tidptr, int, tls_val)
{ return do_fork(clone_flags, newsp, 0, parent_tidptr, child_tidptr); }

fork 在 nommu 上直接 -EINVAL：没有 MMU 就没有页表，也就没有 COW 版 fork。要跑只能完整复制地址空间，或者用 vfork + exec 模拟，内核选了后者。vfork 为什么必须阻塞父进程？它和子进程共用同一个 mm_struct，连栈都一样；两个执行流在同一个栈上跑，栈帧立刻互踩。所以父进程必须挂起，等子进程 exec（换掉 mm）或 exit（mm_release()）才唤醒。衔接点是 vfork_done 这个 completion：

c
/* kernel/fork.c, 3.14 */
p = copy_process(clone_flags, stack_start, stack_size, child_tidptr, NULL, trace);
if (!IS_ERR(p)) {
    struct completion vfork;
    nr = task_pid_vnr(p);
    if (clone_flags & CLONE_VFORK) {
        p->vfork_done = &vfork;
        init_completion(&vfork);
        get_task_struct(p);
    }
    wake_up_new_task(p);
    if (clone_flags & CLONE_VFORK) {
        if (!wait_for_vfork_done(p, &vfork))
            ptrace_event(PTRACE_EVENT_VFORK_DONE, nr);
    }
}

顺序不能反：得先装好 vfork_done 再 wake_up_new_task()，否则子进程瞬间跑完退出，mm_release() 找不到 completion，父进程永远醒不来。

2、do_fork 的第一件事：要不要通知 tracer #

c
/* kernel/fork.c, 3.14 */
if (!(clone_flags & CLONE_UNTRACED)) {
    if (clone_flags & CLONE_VFORK)
        trace = PTRACE_EVENT_VFORK;
    else if ((clone_flags & CSIGNAL) != SIGCHLD)
        trace = PTRACE_EVENT_CLONE;
    else
        trace = PTRACE_EVENT_FORK;
    if (likely(!ptrace_event_enabled(current, trace)))
        trace = 0;
}

判据是 flags 本身，不用问用户态：带 CLONE_VFORK 就是 vfork 事件，退出信号不是 SIGCHLD 就是 clone 事件，剩下的是 fork 事件。内核线程创建时都带 CLONE_UNTRACED，所以内核线程天生不可被 trace——strace -f 抓不到内核线程的「创建」动作。tracer 没开对应事件时 trace = 0，后续 ptrace_event() 全是空操作，未 trace 时 fork 不付代价。

3、copy_process 开头的六道 flag 检查 #

c
/* kernel/fork.c, 3.14 —— 前六道是 flag 互斥检查，第七道是 LSM 钩子 */
if ((clone_flags & (CLONE_NEWNS|CLONE_FS)) == (CLONE_NEWNS|CLONE_FS))
    return ERR_PTR(-EINVAL);
if ((clone_flags & (CLONE_NEWUSER|CLONE_FS)) == (CLONE_NEWUSER|CLONE_FS))
    return ERR_PTR(-EINVAL);
/* Thread groups must share signals as well */
if ((clone_flags & CLONE_THREAD) && !(clone_flags & CLONE_SIGHAND))
    return ERR_PTR(-EINVAL);
/* Shared signal handlers imply shared VM */
if ((clone_flags & CLONE_SIGHAND) && !(clone_flags & CLONE_VM))
    return ERR_PTR(-EINVAL);
/* Siblings of global init remain as zombies on exit */
if ((clone_flags & CLONE_PARENT) &&
            current->signal->flags & SIGNAL_UNKILLABLE)
    return ERR_PTR(-EINVAL);
if (clone_flags & CLONE_SIGHAND) {
    if ((clone_flags & (CLONE_NEWUSER | CLONE_NEWPID)) ||
        (task_active_pid_ns(current) !=
            current->nsproxy->pid_ns_for_children))
        return ERR_PTR(-EINVAL);
}
retval = security_task_create(clone_flags);
if (retval) goto fork_out;

逐条说明：

检查 为什么禁 用户态会看到
CLONE_NEWNS + CLONE_FS 新 mount ns 必然要独立 fs_struct（里面存 root 和 pwd 的 vfsmount） clone 返回 -EINVAL
CLONE_NEWUSER + CLONE_FS 同上，且这组合历史上出过提权漏洞 -EINVAL
CLONE_THREAD 缺 CLONE_SIGHAND 线程组必须共享信号处理表，否则一个线程改 handler 别人看不见 -EINVAL
CLONE_SIGHAND 缺 CLONE_VM handler 是代码地址，不共享地址空间没法共享 handler -EINVAL
CLONE_PARENT + init init 不能造兄弟，否则父进程是 swapper，没人收尸 -EINVAL
CLONE_SIGHAND + 换 ns 换 pid/user ns 的进程不能留在原线程组，否则 ID 语义乱 -EINVAL

CLONE_NEWNS 与 CLONE_FS 排他的原因：fs_struct 里带着 mount namespace 信息，共享 fs_struct 等于共享 mount ns，拆不开。CLONE_NEWUSER + CLONE_FS 的历史漏洞可以顺着 2013 年那份公开说明看：http://www.openwall.com/lists/oss-security/2013/03/13/10。最后一道里 task_active_pid_ns(current) != current->nsproxy->pid_ns_for_children 抓的是「已经 unshare(CLONE_NEWPID) 之后的第一次 fork」：此时 current 还在老 ns，但 pid_ns_for_children 已指向新 ns，两者不等，于是禁止这个 fork 出来的进程再共享 signal handler。前面说「新 ns 从子进程开始生效」，在这里落了地。

十、复制内核栈与 creds、RLIMIT_NPROC 与 PF_NPROC_EXCEEDED #

1、dup_task_struct #

c
/* kernel/fork.c, 3.14 —— dup_task_struct() 的主体动作 */
tsk = alloc_task_struct_node(node);
if (!tsk) return NULL;
ti = alloc_thread_info_node(tsk, node);
if (!ti) goto free_tsk;
err = arch_dup_task_struct(tsk, orig);      /* 弱符号，默认 *dst = *src */
if (err) goto free_ti;
tsk->stack = ti;
setup_thread_stack(tsk, orig);
clear_user_return_notifier(tsk);
clear_tsk_need_resched(tsk);
*end_of_stack(tsk) = STACK_END_MAGIC;       /* for overflow detection */
/* One for us, one for whoever does the "release_task()" (usually parent) */
atomic_set(&tsk->usage, 2);

四个动作逐条对。分配：task_struct 和「内核栈 + thread_info」是两次分配，走不同分配器；x86 上 THREAD_SIZE >= PAGE_SIZE，alloc_thread_info_node() 直接 alloc_pages_node(..., THREAD_SIZE_ORDER) 拿连续两页。搭关系：tsk->stack = ti 加 setup_thread_stack()，后者是 *task_thread_info(p) = *task_thread_info(org); task_thread_info(p)->task = p;——整块 memcpy 父进程的 thread_info 再把自己的 task 指回去，就这一句决定了子进程的 TIF_* 初值和父进程一样，后面那些 clear_tsk_need_resched() 都在这基础上做减法。完整复制：arch_dup_task_struct() 默认实现一句 *dst = *src，整个 task_struct 拷过来，所以「fork 复制了几乎全部东西」在代码上就是一次结构体赋值，后面的 copy_* 系列都在逐项修正这份拷贝。计数置 2：一个给「正在 fork 的这条路径」，一个给将来 release_task() 的调用者（一般是父进程）；置 1 会让 free_task() 提前跑掉，置 3 就是泄漏。

STACK_END_MAGIC 是栈溢出哨兵：栈长过头把 magic 覆掉，异常路径检查一次就报 kernel stack overflow。CONFIG_VMAP_STACK（4.9 起）改成栈两端放 guard page 靠缺页抓，比哨兵可靠。

2、RLIMIT_NPROC 的检查 #

c
/* kernel/fork.c, 3.14 */
retval = -EAGAIN;
if (atomic_read(&p->real_cred->user->processes) >=
        task_rlimit(p, RLIMIT_NPROC)) {
    if (p->real_cred->user != INIT_USER &&
        !capable(CAP_SYS_RESOURCE) && !capable(CAP_SYS_ADMIN))
        goto bad_fork_free;
}
current->flags &= ~PF_NPROC_EXCEEDED;
retval = copy_creds(p, clone_flags);
if (retval < 0)
    goto bad_fork_free;

它查的是 p->real_cred->user->processes。此刻 p 还是父进程的拷贝，real_cred 指的也是父进程凭证，所以等价于查「当前用户已经有几个进程」。三个豁免：INIT_USER（root 的 user_struct）、CAP_SYS_RESOURCE、CAP_SYS_ADMIN。所以 root 不管 RLIMIT_NPROC 设多小都能继续 fork，想卡 root 得靠 nr_threads >= max_threads 那条全局限制。

current->flags &= ~PF_NPROC_EXCEEDED; 这句看着莫名，其实是给 set*uid() 擦屁股。set_user() 在 setuid 路径上有意不因 RLIMIT_NPROC 失败（太多程序不检查返回值），改用 flag 记账把失败推迟到 execve()：

c
/* kernel/sys.c, 4.4 —— set_user() 里的延迟记账 */
if (atomic_read(&new_user->processes) >= rlimit(RLIMIT_NPROC) &&
        new_user != INIT_USER)
    current->flags |= PF_NPROC_EXCEEDED;
else
    current->flags &= ~PF_NPROC_EXCEEDED;

execve 那端补刀：do_execve_common() 开头一看 PF_NPROC_EXCEEDED 还在、current_user()->processes 仍超限，就返回 -EAGAIN；没超则清掉 flag，让后续 execve 不再失败。这条链路解释了一类很费解的现象：setuid 成功但 fork 失败，或者 setuid 成功但 execve 返回 EAGAIN。看到 fork: Resource temporarily unavailable 时，先查 ulimit -u 和 /etc/security/limits.conf，别急着怀疑内存。

3、全局线程数上限 #

nr_threads 是全系统 task 数（idle 不算），max_threads 在 fork_init() 里按内存算，copy_process() 里只做一次比较。物理含义：每个 task 保底要一个内核栈（THREAD_SIZE），8 * THREAD_SIZE / PAGE_SIZE 是「8 个 task 的栈折算成多少页」，除一下就是「内存全给栈能塞多少」，再除 8 表示「最多占八分之一」。跑起来还能改：

限制 位置 默认值 超了会怎样
max_threads /proc/sys/kernel/threads-max 上面的公式，下限 20 fork 返回 EAGAIN
RLIMIT_NPROC ulimit -u / setrlimit(2) max_threads / 2 fork 返回 EAGAIN；setuid 路径会把失败推迟到 execve
单 user 进程数 user_struct->processes 由 RLIMIT_NPROC 卡 同上

RLIMIT_NPROC 默认取 max_threads/2 是同一套思路：root 一个人最多占一半，剩下的留给别人。

4、copy_creds #

c
/* kernel/cred.c, 3.14 */
if (
#ifdef CONFIG_KEYS
    !p->cred->thread_keyring &&
#endif
    clone_flags & CLONE_THREAD
    ) {
    p->real_cred = get_cred(p->cred);
    get_cred(p->cred);
    alter_cred_subscribers(p->cred, 2);
    atomic_inc(&p->cred->user->processes);
    return 0;
}
new = prepare_creds();
if (!new) return -ENOMEM;
if (clone_flags & CLONE_NEWUSER) {
    ret = create_user_ns(new);
    if (ret < 0) goto error_put;
}
atomic_inc(&new->user->processes);
p->cred = p->real_cred = get_cred(new);
alter_cred_subscribers(new, 2);

两条分支，差别就是共享还是复制。创建线程（CLONE_THREAD）：不复制 struct cred，只加引用计数；get_cred(p->cred) 调两次是因为 real_cred 和 cred 会成为两个独立引用，后面 exit_creds() 也 put_cred 两次；条件里那个 !p->cred->thread_keyring 是 3.14 才有的，带 thread keyring 的线程不能共享 cred，必须复制。创建进程：prepare_creds() 复制一份，p->cred = p->real_cred = get_cred(new)；如果带 CLONE_NEWUSER，还要 create_user_ns(new) 把新凭证挂到新 user namespace 上——这就是容器里 uid 0 只在容器内是 root 的机制。

顺带把 objective/subjective 在 fork 里的落点说清：注释那句 "The new process gets the current process's subjective credentials as its objective and subjective credentials" 就是 p->cred = p->real_cred 这一行——父进程的 subjective 成了子进程的 objective，因为从此刻起父进程是「别人」了。

十一、模块回调、delay accounting 与 flag 复制 #

1、rt_mutex_init_task #

c
/* kernel/fork.c, 3.14 */
static void rt_mutex_init_task(struct task_struct *p)
{
    raw_spin_lock_init(&p->pi_lock);
#ifdef CONFIG_RT_MUTEXES
    p->pi_waiters = RB_ROOT;
    p->pi_waiters_leftmost = NULL;
    p->pi_blocked_on = NULL;
    p->pi_top_task = NULL;
#endif
}

pi 是 priority inheritance（优先级继承），为实时互斥量解决优先级翻转而生。假设低、中、高三个优先级的 task 都要一把 mutex：

时刻 事件 结果
T0 只有低优先级在跑 正常
T1 低优先级拿到 mutex 持锁运行
T2 中优先级被外部事件唤醒 抢占低优先级，低优先级拿着锁被挂起
T3 高优先级被外部事件唤醒 抢占中优先级
T4 高优先级去要那把 mutex 拿不到，挂起等低优先级
T5 中优先级继续跑 高优先级被中优先级间接阻塞

问题不在 T4 的等待，在 T5：高优先级要等「中优先级跑完 + 低优先级跑完」，等待时间完全不受自己控制，实时系统里就是致命的。优先级继承的做法：高优先级等一把被低优先级持有的锁时，内核临时把低优先级提到高优先级那一档，让它赶紧跑完释放；锁一放，优先级回落。pi_lock 保护的就是这套状态：pi_waiters 是等这把锁的 task 红黑树（按优先级排序），pi_waiters_leftmost 缓存树里最高优先级那个，pi_blocked_on 记录自己卡在哪个 rt_mutex_waiter 上，pi_top_task 记录「谁把我提上来的」。用户态互斥量想避免优先级翻转必须用 pthread_mutexattr_setprotocol(PTHREAD_PRIO_INHERIT)，底层通过 FUTEX_LOCK_PI 落到这里。

2、exec_domain 的模块引用 #

c
/* kernel/fork.c, 3.14 */
if (!try_module_get(task_thread_info(p)->exec_domain->module))
    goto bad_fork_cleanup_count;

exec_domain 是执行域，让在别的 UNIX 上编译的程序在 Linux 上跑：系统调用号、信号编号、ioctl 编码这些 ABI 差异全在这里对齐。DOS/Windows 那种差异太大只能靠用户态模拟，POSIX 系只需微调。子进程的 exec_domain 在 dup_task_struct 里已经跟着 thread_info 整块拷过来了，所以这里只给它的模块加引用计数——模块不能在被引用期间卸载；对应的 module_put() 在 bad_fork_cleanup_policy 和进程退出路径上。这个字段后来整块删掉了，只剩 task_struct->personality 记录 PER_LINUX 这类 personality 位。

3、per-task delay accounting #

delayacct_tsk_init(p) 那句 /* Must remain after dup_task_struct() */ 很重要：它给 p->delays 分配并初始化统计结构，必须在 dup_task_struct() 之后——否则指针会被那次整块结构体拷贝覆盖掉。这个 feature 统计 task 等资源的时间，四类：

等待类型 场景 统计字段（2.6.28 的 task_delay_info）
CPU runnable 但没被调度上 sched_info 里另算
同步块 I/O 发起 sync I/O 后阻塞 blkio_delay / blkio_count
swap in 访问被换出的页（capacity miss） swapin_delay / swapin_count
内存回收 申请内存触发 reclaim freepages_delay / freepages_count 
c
/* include/linux/sched.h, 2.6.28 */
struct task_delay_info {
    spinlock_t      lock;
    unsigned int    flags;
    struct timespec blkio_start, blkio_end;   /* Shared by blkio, swapin */
    u64 blkio_delay;        /* wait for sync block io completion */
    u64 swapin_delay;       /* wait for swapin block io completion */
    u32 blkio_count, swapin_count;
    struct timespec freepages_start, freepages_end;
    u64 freepages_delay;    /* wait for memory reclaim */
    u32 freepages_count;
};

统计出来干什么？调优先级。等 CPU 久的，调度器可以给更多权重；等 I/O 久的，I/O 调度器可以调它的 I/O 优先级；freepages_delay 高的说明内存吃紧，该压它的 RSS 上限。数据出口在 taskstats，getdelays 那个工具读的就是它。delayacct_on 关掉时 delayacct_tsk_init() 是空函数，一点开销都没有——内核处理统计类功能的通用做法：编译进来，运行时按开关走。

4、copy_flags #

c
/* kernel/fork.c, 3.14 */
static void copy_flags(unsigned long clone_flags, struct task_struct *p)
{
    unsigned long new_flags = p->flags;
    new_flags &= ~(PF_SUPERPRIV | PF_WQ_WORKER);
    new_flags |= PF_FORKNOEXEC;
    p->flags = new_flags;
}
flag 处理 理由
PF_SUPERPRIV 清 它记录的是「这个 task 曾经用过特权」，不是「有特权」。子进程还没有任何特权使用记录，继承父进程的标记是错的
PF_WQ_WORKER 清 标识「我是 workqueue worker」。新 task 要真成了 worker，会在 worker_thread() 里自己打上
PF_FORKNOEXEC 置 表示「fork 了但还没 exec」。setpgid() 的检查里就用它判断这个进程是不是还没 exec 过

PF_SUPERPRIV 的语义值得单独强调，因为网上大量代码解析在这句上出错。它由 capability 检查路径打上：capable() 成功返回时 current->flags |= PF_SUPERPRIV。所以它是「用过特权」的历史记录，不是「有特权」的能力标志。父进程有特权，子进程靠 copy_creds 拿到同样的 struct cred，capability 集合完整继承，清的只是那个历史位。这 flag 的用途是审计：进程退出时被检查，决定要不要记一条「特权使用」的账。它跟权限判定毫无关系——判有没有权限，永远看 cap_effective 和 euid。

十二、易错点速查 #

现象 原因 怎么确认
单线程进程 getpid() 和 gettid() 相等，多线程不等 Linux 把 POSIX 进程 ID 映射成 tgid，线程 ID 映射成 task 自己的 pid ps -eLf 看 LWP 列，等于 PID 的那行是 leader
线程里 getpid() 拿到的不是自己「进程号」 同上，getpid 返回 tgid 用 syscall(SYS_gettid) 取自己的
容器里 ps 看到 pid 1，宿主机看到别的号 pid_nr_ns() 用 task_active_pid_ns(current) 换算 nsenter -t <pid> -p ps 对比
容器里 pid 1 kill -9 杀不掉 SIGNAL_UNKILLABLE 只放行内核发的信号 看 p->signal->flags，或直接杀整个 ns
unshare(CLONE_NEWPID) 后当前进程 pid 没变 新 pid ns 只对子进程生效 再 fork() 一次，子进程才是 1
fork() 返回 EAGAIN RLIMIT_NPROC 或 nr_threads >= max_threads 查 ulimit -u、/proc/sys/kernel/threads-max
setuid() 成功但 execve() 返回 EAGAIN PF_NPROC_EXCEEDED 把失败推迟到了 execve 查 ulimit -u，比对 /proc/pid/status
setfsuid() 无法判断成功失败 它返回旧 fsuid，失败时返回值等于原值 调完再 setfsuid(-1) 读一次
access() 和 open() 结论不一致 access() 用 real uid，open() 用 fsuid 用 faccessat(AT_EACCESS) 才按 euid 判
setuid 程序降权后再也升不回去 用了 setuid() 而不是 seteuid()，前者在 root 下会把 suid 一起改掉 看 /proc/pid/status 的 Uid: 四列
clone 返回 -EINVAL flag 组合非法，见第九节那张表 逐条排查 CLONE_THREAD/CLONE_SIGHAND/CLONE_VM/CLONE_FS
vfork 之后父进程卡住不动 子进程既没 exec 也没 exit，vfork_done 没被 complete ps 看父进程状态，别在子进程里改栈
模块里读 task_pgrp() 偶发 oops 没加 tasklist_lock 或 RCU，撞上 setsid/setpgid 照 sched.h 注释加锁
/proc/pid/status 的 Uid: 有四列 分别是 real / effective / saved / fsuid 和 getresuid() 对照
线程崩溃带崩整个进程 CLONE_SIGHAND 语义，信号处理表共享 这本来就是这个模型的行为，不是 bug
升级内核后 task_struct 偏移变了 4.18 起有 randomized_struct_fields_start/end 区段 别靠硬编码偏移，用 offsetof 加运行时校验
