一、2.4 时代：tick 驱动一切的旧架构 #

先回到 2.4 内核。那时候没有 clocksource、没有 clockevent、也没有 hrtimer。整个时间子系统的骨架只有一根：周期性 tick。

每个 architecture 的 arch/ 目录下自己写两样东西，名字上借用了新架构的词，实际内容很朴素：

  • 一个 timer 硬件的中断处理函数。这就是「clock event」的全部内容。
  • 一个能返回「上个 tick 到现在的偏移」的接口函数。这就是「clock source」的全部内容。

在这两块之上堆出 tick 模块。tick 模块维护系统的 tick 计数，假设配置是 10ms 一个 tick，每次 tick 中断到来，timekeeping 就把系统时间往前推 10ms。如果 timekeeping 完全靠 tick 驱动，它的精度就锁死在 10ms。偏移接口函数的唯一作用是把这个 10ms 的台阶再细分一点，让读时间的误差小于一个 tick。

整套东西摊开看是这样的：

text
 arch/<platform>/                      arch-independent
 ─────────────────────────────         ─────────────────────────────
 timer 中断处理函数 ────────────────►  tick 模块（维护系统 tick）
 gettimeoffset() 偏移函数 ─────────►  timekeeping（每 tick 加一个 tick 的时长）
                                      │
                                      ├──► 低精度 timer（定时器软中断里跑）
                                      ├──► 进程时间统计（utime / stime）
                                      ├──► 调度器（时间片记账）
                                      ├──► System Load 计算
                                      └──► Kernel Profiling

最初的 Linux kernel 只支持低精度 timer，也就是基于 tick 的 timer。10ms 的 tick，低精度 timer 的最高精度也只有 10ms。想要 µs 甚至 ns 级别，做不到。内核里所有驱动模块要定时，都调低精度 timer 的接口。进程的时间统计基于 tick，调度器拿这批数据做决策。System Load 和 Kernel Profiling 也基于 tick，一个算系统负荷，一个做内核性能剖析。整棵树都挂在 tick 上。

从用户空间看，需求只有两类：

  • 拿时间、设时间。time、stime、gettimeofday、settimeofday。
  • 定时器。setitimer、alarm，到期后给进程发信号。

这两类需求在 2.4 的架构下都够用，因为没人要求精度超过一个 tick，也没人要求系统空闲时别醒。

二、旧架构的两个问题：功耗与精度 #

技术往前走，冒出来两个旧架构接不住的需求。

问题一：功耗。 嵌入式设备要好用的电源管理策略。传统 Linux 有一个雷打不动的周期性时钟，系统无事可做的时候照样醒，醒了就得从低功耗 idle 状态爬回高功耗状态。CPU 一直在 idle 和 run 之间来回摩擦，电池吃不消。这个设计和现代电源管理思路直接冲突。

问题二：精度。 多媒体应用需要精确的 timer。视频要避免跳帧，音频回放要避免抖动，10ms 的粒度盖不住这些场景。这是 tick 这个单位本身的问题。

低精度 timer 用 tick 计量，而 tick 的长度跟内核配置绑死，不是一个人能直观理解的时间单位。高精度 timer 用 ns，这是人最直观的单位。两者摆在一起，前者明显该退场。

但「该退场」不等于「能退场」。hrtimer 落地之后，内核其实不再需要低精度 timer 了，可是低精度 timer 已经存在很多年，渗透进内核各个角落，拔掉它很容易引出稳定性和健壮性问题。于是内核保持两种 timer 并存。内核开发人员试过把两者整合，没成，整合的尝试失败了，目前的实现就是两套并存。

这条经验值得记住：软件框架演化时，一个组件被大量其他模块依赖，你没法推倒重来，只能留兼容路径。负担很重，但只能这么干。第7节的 CONFIG_ARCH_USES_GETTIMEOFFSET 就是这条经验留下的化石。

四层抽象各管一段，分工如下：

层 管什么 和硬件的关系 关键约束
clock source layer 硬件 free running counter 的抽象，提供读「当前第几个 cycle」的接口，构成全局 timeline 硬件无关 有溢出问题，取决于 counter 位宽和输入频率
clock event layer 在 timeline 上的指定点产生事件的设备抽象，依靠中断子系统实现异步 硬件无关 一个硬件 timer 就是一个 device，可以有很多个
tick device layer 在 clock event 之上建 tick，每 CPU 一个 local tick device，其中选一个当 global tick 硬件无关 每 CPU 有且只有一个 tick device；可周期性可 oneshot
timekeeping 把 cycle 差值积分成人类可用的时间（monotonic / boot / real） 硬件无关 精度取决于 clock source，推进节奏取决于 tick

几个要点按原文说清楚：

clocksource 对应硬件的 system free running counter，提供一条基础 timeline。真实的 timeline 是一条无限延伸的直线，对内核而言 timeline 构建在 counter 之上，所以 clocksource 的 timeline 必然有溢出问题。这是数学上的必然，不是实现缺陷。如果选 64bit 的硬件 counter、输入频率又不那么高，溢出时间能长达 50 年甚至更多。从应用角度看，一条能维持 50 年的 timeline 可以接受。

如果 clocksource 是「一条 timeline」，clock event 就是「在这条 timeline 上的指定点产生事件的设备」。它能产生异步事件，靠的是中断子系统。所以 clock source chip driver 要申请中断，中断来了再调用通用 clock event 模块的 callback，把这个异步事件通知上去。

tick device layer 建在 clock event 设备之上。每个 CPU 形成自己的一个小系统，有自己的调度、自己的进程统计，这个小系统需要自己的 tick 设备，而且是唯一的。clock event 设备不是这样，硬件有多少个 timer 就注册多少个 clock event device，每个 CPU 的 tick device 从里面挑最适合自己的那个。tick device 可以跑 periodic mode 也可以跑 one shot mode，具体哪种跟系统配置有关。所以 tick device layer 里，有多少 CPU 就有多少 tick device，我们叫它 local tick device。有些事不适合在 local tick 下做，比如整个系统的负荷计算，于是所有 local tick device 里会选一个当 global tick device，由它维护整个系统的 jiffies、更新 wall clock、算全局负荷。

高精度 timer 需要高精度的 clock event，工作在 one shot 模式的 tick device 就能提供高精度 clock event。所以高精度 timer 建在 oneshot 模式的 tick device 之上，内核各个模块调高精度 timer 的接口就能拿到 ns 级的定时服务。

第2节说过高精度和低精度并存。具体怎么并存的：系统跑在高精度模式时（tick device 处于 one shot 模式），内核会 setup 一个特别的高精度 timer，可以叫它 sched timer，让它周期性触发，从而模拟出传统的 periodic tick，靠它推动低精度 timer 的运转。于是那些还抱着经典低精度 timer 接口不放的模块，照样能用。

四、一个 hardware 拆成两半：free running counter 与 CPU local timer #

引入 multi-core 之后，过去「一个 HW timer 干所有事」的局面变了。原来那个硬件模块的功能被拆成两部分。

第一半：free running 的 system counter。 它是全局的，不属于任何一个 CPU。它只做一件事，不停地数 cycle。所有时间计算的基准都在它身上。

第二半：产生定时事件的 HW block。 我们叫它 timer。timer 硬件被嵌进各个 CPU core 里，所以更准确的叫法是 CPU local Timer。这些 timer 全都基于那一个 global counter 运作：counter 负责「现在是第几个 cycle」，local timer 负责「到第 N 个 cycle 时给我一个中断」。

拆开之后，驱动层的组织方式也跟着变。我们提供一个 clock source chip driver 模块去驱动硬件，这个模块和硬件体系结构有关。如果系统里存在多个 HW timer 和 counter block，系统里就会存在多个 clock source chip driver。

五、通用层与芯片驱动：谁依赖谁 #

面对形形色色的 timer 和 counter 硬件，内核抽出了通用 clock event layer 和通用 clock source 模块，这两个模块和硬件无关。底层的 clock source chip driver 调这两个通用模块的接口函数，把 clock source 设备和 clock event 设备注册上去。

依赖方向是从下往上的，写驱动的人必须清楚这一点：

text
   ┌───────────────────────────────────────────────┐
   │  内核使用方：hrtimer、timer wheel、tick、       │
   │  timekeeping、进程统计                          │
   └───────────────────▲───────────────────────────┘
                       │ 只用通用 API
   ┌───────────────────┴───────────────────────────┐
   │  通用层：clocksource + clockevent（硬件无关）    │
   │  clocksource_register_khz()
   │  clockevents_config_and_register()
   │  clockevents_register_device()
   └───────────────────▲───────────────────────────┘
                       │ 驱动调通用层注册自己，不反向调用使用方
   ┌───────────────────┴───────────────────────────┐
   │  chip driver：和 arch / SoC 绑定                │
   │  申请中断 → 中断里回调通用层                     │
   └───────────────────────────────────────────────┘

一句话：驱动只负责「把硬件能力登记到通用层」和「中断来了通知通用层」，不做任何时间语义的决策。时间的语义（monotonic 还是 real、要不要 NTP 调整、精度多少）全在 timekeeping 那一侧。这条边界划清楚了，同一份通用层代码才能喂给几十种不同的 SoC。

六、文件汇整：kernel/time/ 目录下都有谁 #

Linux kernel 时间子系统的源文件位于 kernel/time/ 目录下。素材这里原本有一份文件清单，抓取时和示意图一起丢了。下面这份清单是按内核中该目录的公知内容补的，补的内容标注为待核对，你对照自己手上的内核版本再看一眼：

文件 职责 备注

hrtimer.c 高精度 timer 红黑树、hrtimer_start_range_ns、hrtimer_run_queues 待核对
itimer.c setitimer / getitimer 的 interval timer 实现 待核对

posix-clock.c POSIX clock 调优，clock_adjtime 走这里 待核对
clocksource.c 通用 clocksource 层，注册、rating 选择、读 cycle 待核对
clockevents.c 通用 clockevent 层，设备注册与 mode 管理 待核对
tick-common.c tick device 通用逻辑，tick_setup_device 等 待核对

真正能从素材里硬拿到的证据只有一条，就是 kernel/time/Makefile 里这行：

makefile
obj-y += time.o timer.o hrtimer.o itimer.o posix-timers.o posix-cpu-timers.o

这行的看点在 obj-y。obj-y 意味着无条件编进内核 image，不受任何 CONFIG_ 控制。所以就算关掉高精度 timer，hrtimer.o 照样进内核。这一点在第9节讲低精度路径时会再翻出来用，它是理解「hrtimer 的双模式」的关键。

七、内核配置项与它们的组合 #

配置项分四组看，别混在一起记。

第一组：通用 clock source 与 clock event。

配置项 含义 依赖与现状
CONFIG_GENERIC_CLOCKEVENTS 打开新的时间子系统架构 不配就用第1节描述的旧架构
CONFIG_GENERIC_CLOCKEVENTS_BUILD 配合上一项，构建通用 clockevent 代码 与 CONFIG_GENERIC_CLOCKEVENTS 一起用
CONFIG_GENERIC_TIME 曾经对应 clocksource 的配置项 已在某个版本中删除，具体版本号素材未说明
CONFIG_ARCH_USES_GETTIMEOFFSET 为兼容旧风格 timekeeping 接口而保留 现代内核仍提供，用来接旧 arch 代码

CONFIG_GENERIC_TIME 被删这件事值得单独说。删掉的意思很清楚：现在的内核一律走通用 clocksource 模块，没办法退回过去那种 arch 自带 clocksource 的时代。可为了兼容旧风格的 timekeeping 接口，CONFIG_ARCH_USES_GETTIMEOFFSET 还留着。一个删掉一个保留，正好是第2节那条经验的两面。

第二组：tick 相关的三选一。 前提是配了 CONFIG_GENERIC_CLOCKEVENTS，之后内核会打开 Timers subsystem 的配置选项，主要和 tick 以及高精度 timer 有关。tick 相关有三种，只能配其中一个：

配置项 行为 附带效果
CONFIG_HZ_PERIODIC 任何时候都启用周期性 tick，系统 idle 时照样醒 无
CONFIG_NO_HZ_IDLE 系统 idle 时停掉周期性 tick 同时 enable NO_HZ_COMMON
CONFIG_NO_HZ_FULL 非 idle 状态、CPU 上还跑着 task，也会停 tick，和实时应用相关 同时 enable NO_HZ_COMMON

旧内核用 CONFIG_NO_HZ 配 dynamic tick（也叫 tickless idle：非 idle 时有周期性 tick，idle 状态下 timer 中断不再周期性触发，只按需要触发）。新内核为了兼容旧系统，CONFIG_NO_HZ 仍然支持。所以你在老 defconfig 里看到 CONFIG_NO_HZ=y，别以为它和 CONFIG_NO_HZ_FULL 是一回事。

第三组：timer 模块。 和高精度 timer 相关的配置很简单，只有一个 CONFIG_HIGH_RES_TIMERS。另外一条强依赖：如果配了高精度 timer，或者配了 NO_HZ_COMMON，那就一定得配 CONFIG_TICK_ONESHOT，意思是系统支持 one-shot 类型的 tick device。反过来说不通：配了 CONFIG_TICK_ONESHOT 不代表硬件真有 one shot 能力，第9节会讲这种「配了但硬件没有」的情况。

第四组：架构层面的二选一。 两条路：

  1. 新的通用时间子系统框架：配 CONFIG_GENERIC_CLOCKEVENTS。
  2. 传统时间子系统框架：不配 CONFIG_GENERIC_CLOCKEVENTS，配 CONFIG_ARCH_USES_GETTIMEOFFSET。

除非你在维护一套旧系统，否则走第一条。走第一条之后，还有四种配置组合可选，见第8节。

八、CONFIG_HZ_PERIODIC / NO_HZ_IDLE / NO_HZ_FULL 三选一 #

新框架下的四种组合，都建立在「低精度/高精度」与「周期 tick / dynamic tick」两个维度上：

组合 tick 配置 timer 精度 场景
低精度 timer + 周期 tick CONFIG_HZ_PERIODIC 一个 tick（如 10ms） 保持和传统 Unix 的一致性，传统 linuxer 熟悉的味道
低精度 timer + dynamic tick CONFIG_NO_HZ_IDLE 一个 tick 移动端、嵌入式省电
高精度 timer + 周期 tick CONFIG_HZ_PERIODIC + CONFIG_HIGH_RES_TIMERS ns 少见，多半是硬件不支持 one shot
高精度 timer + dynamic tick CONFIG_NO_HZ_IDLE + CONFIG_HIGH_RES_TIMERS + CONFIG_TICK_ONESHOT ns，空闲不醒 现代通用发行版的常见形态

第三种组合要单独解释。为什么高精度 timer 配周期 tick 会少见？因为高精度 timer 要的是「在任意时刻点设一个触发点」，这需要能随意 reprogram 的 one shot clock event。硬件只能周期性触发，就没有任意触发点的能力，系统只能退回周期 tick，高精度能力发挥不出来。所以这种组合出现的原因多是硬件限制，不是软件选择。

CONFIG_NO_HZ_FULL 这条路（full dynticks system）本篇不展开，它和实时应用相关，细节去看《tick 机制》那一篇。

九、数据流：从硬件中断到 timekeeping 更新 #

四种配置下，数据流的差别集中在「谁去 reprogram 硬件」以及「tick 从哪儿来」。逐条走。

9.1 低精度 timer + 周期 tick #

起点一定是底层的 clock source chip driver。这个 driver 调注册 clock event 的接口，二选一：

c
clockevents_config_and_register(dev, freq, min_delta, max_delta);
/* 或者 */
clockevents_register_device(dev);

一旦新增了一个 clock event device，就得通知上层 tick device layer。理由很直接：新注册的这个 device 更好用、更适合某个 tick device。通知的动作是调 tick_check_new_device()。

如果这个 clock event device 被某个 tick device 收留了（两种情况：该 tick device 之前没有匹配的 clock event device，或者新 device 比原来那个更合适），就启动对该 tick device 的配置，参考 tick_setup_device()。

在当前配置下（周期性 tick），走 tick_setup_periodic()。这时候该 tick device 对应的 clock event device 的 event handler 被设成 tick_handle_periodic。底层硬件周期性地产生中断，从而周期性地调 tick_handle_periodic，驱动整个系统运转。

text
 chip driver: clockevents_register_device()
        │
        ▼
 clockevents 通用层：登记 device
        │
        ▼
 tick_check_new_device()   ← 问：有 tick device 要收留它吗
        │  收留
        ▼
 tick_setup_device()
        │  当前是周期 tick 配置
        ▼
 tick_setup_periodic()
        │
        ▼
 dev->event_handler = tick_handle_periodic
        │
        ▼
 硬件每 tick 中断一次 ──► tick_handle_periodic() ──► 推进 jiffies / timekeeping

这里有个容易踩的坑：即便配了 CONFIG_NO_HZ 和 CONFIG_TICK_ONESHOT，只要系统里没有提供 one shot 的 clock event device，整个系统仍然是跑在周期 tick 模式下。配置项只表达「软件支持」，不保证「硬件具备」。

接着看低精度 timer。即便没使能高精度 timer，内核也会把高精度 timer 模块的代码编进 image，第6节那行 obj-y 就是证据。在这种架构下，内核模块调 hrtimer 接口也能调通，但 hrtimer 跑在低精度模式：这些 hrtimer 仍按高精度 timer 的红黑树组织，可系统只在每一个周期性 tick 到来时调一次 hrtimer_run_queues()，检查有没有 expire 的 hrtimer。

c
/* 低精度模式下的 hrtimer：不做 reprogram，只在 tick 到来时扫一遍 */
void hrtimer_run_queues(void);

扫一遍的粒度就是一个 tick。所以此时的 hrtimer 精度等同 tick，高精度的名义没有实际意义。理解这点，你就不会困惑为什么「只设了 CONFIG_HIGH_RES_TIMERS 却感觉定时不准」——还得看 tick 能不能进 oneshot。

周期 tick 存在，低精度 timer 的运作毫无压力，和过去一样。

9.2 低精度 timer + dynamic tick #

系统不是一启动就进 dynamic tick 模式的，中间有个切换过程。

第一阶段，系统跑在周期 tick 模式，每个 CPU 的 tick device 对应的 clock event device 的 event handler 是 tick_handle_periodic。

第二阶段，在 timer 的软中断上下文里会调 tick_check_oneshot_change() 做检查，判断要不要切到 one shot 模式。切换的条件是：系统里有支持 one-shot 的 clock event device，并且没有配高精度 timer。两个条件都满足，就发生 tick mode 切换，调 tick_nohz_switch_to_nohz()。

切换之后：

text
 tick device 模式：periodic ──► oneshot
 event_handler：tick_handle_periodic ──► tick_nohz_handler

因为此时 clock event device 工作在 one shot 模式，系统正常运行时，event handler 每次都得 reprogram clock event，才能正常产生下一次 tick。等 CPU 跑 idle 进程时，clock event device 不再 reprogram 下一次 tick，整个系统的周期性 tick 就停下来了。这就是 tickless idle 的实现要点：不停 reprogram，tick 自然消失。

这个模式下高精度 timer 和低精度 timer 的工作原理和第9.1节相同，因为它们本来就没进 hrtimer 的高精度路径。

9.3 高精度 timer + dynamic tick #

同样有个切换过程。起点一样：系统跑在周期 tick 模式，event handler 是 tick_handle_periodic。

在周期 tick 的软中断上下文里（参考 run_timer_softirq），满足条件就调 hrtimer_switch_to_hres()，把 hrtimer 从低精度模式切到高精度模式。这一步做三件事：

  1. tick device 的 clock event 设备切到 oneshot mode，参考 tick_init_highres()。
  2. tick device 的 clock event 设备的 event handler 更新成 hrtimer_interrupt，参考 tick_init_highres()。
  3. 设定 sched timer，也就是那个用来模拟周期 tick 的高精度 timer，参考 tick_setup_sched_timer()。

之后下一次 tick 到来时，系统调 hrtimer_interrupt() 处理这个 tick，而这个 tick 是由 sched timer 产生的。

dynamic tick 模式下，各 CPU 的 tick device 工作在 one shot 模式，对应的 clock event 也工作在 one shot，硬件 timer 的中断不再周期性产生。可内核里很多模块依赖周期性 tick。解法是用 hrtimer 模拟一个周期性 tick：切到 dynamic tick 模式时初始化这个高精度 timer，回调函数是 tick_sched_timer。

tick_sched_timer 干的事和周期 tick 里 event handler 干的事类似，区别在最后——它会 reprogram 这个高精度 timer，以便周期性产生 clock event。系统进 idle 时停掉这个高精度 timer，没有用户事件时 CPU 就能持续待在 idle，功耗降下来。

text
                 周期 tick 模式                    dynamic tick 模式
                 ─────────────                    ───────────────────
 tick device      periodic                         oneshot
 event_handler    tick_handle_periodic             hrtimer_interrupt
 tick 来源         硬件周期中断                     sched timer（hrtimer）
                                                  ↓
                                                  回调 tick_sched_timer
                                                  ├─ 干活（同周期 tick）
                                                  ├─ reprogram 自己（忙）
                                                  └─ 进 idle 时停掉（闲）

注意 hrtimer_interrupt 这个名字：它挂在了 clock event 设备上，但它不处理业务，它负责分派 expired hrtimer，其中就包含 sched timer 自己。这条自举链是理解高精度模式的关键。

9.4 高精度 timer + 周期 tick #

这种配置不多见，原因第8节说过，多半因为硬件无法支持 one shot 的 clock event device。这种情况下整个系统仍然跑在周期 tick 模式，第9.1节的流程原样生效，高精度能力被硬件封死。

9.5 四种配置一览 #

配置 tick device 模式 clock event 的 event handler tick 由谁产生
低精度 + 周期 tick periodic tick_handle_periodic 硬件周期中断
低精度 + dynamic tick 先 periodic 后 oneshot 先 tick_handle_periodic 后 tick_nohz_handler 正常情况下每次 reprogram，idle 时停止
高精度 + dynamic tick 先 periodic 后 oneshot 先 tick_handle_periodic 后 hrtimer_interrupt sched timer（tick_sched_timer），idle 时停
高精度 + 周期 tick periodic tick_handle_periodic 硬件周期中断

十、控制流：一条从申请到注销的时序 #

数据流讲的是「中断来了往哪儿走」，控制流讲的是「谁来装、谁来拆」。以 clocksource 为例，一条完整的生命周期是这样的：

text
 probe / init
   │
   ├─ 读硬件、确定 counter 位宽和输入频率
   │
   ├─ 分配 struct clocksource，填 read 回调、mask、mult、shift、rating
   │
   ├─ clocksource_register_khz() / clocksource_register_hz()
   │        │
   │        └─ 通用层按 rating 排序，选出当前最优 source
   │
   ├─ （可选）同时注册 clock event：
   │     clockevents_config_and_register(dev, freq, min, max)
   │        │
   │        ├─ tick_check_new_device()   ← tick device 来挑
   │        └─ tick_setup_device()       ← 被收留后配置
   │
   └─ request_irq()  ← clock event 侧必须申请中断，否则无法通知上层
            │
            └─ 中断到来 ──► 调通用 clock event 的 callback ──► event_handler

 remove / suspend
   │
   ├─ 停止硬件、关中断
   ├─ tick device 换一个 clock event device 顶上（或切 broadcast）
   └─ 注销 clocksource，通用层重新按 rating 选 source

三个节点必须盯住：

  1. clocksource_register_khz() 之后，通用层凭 rating 决定谁是当前 source，驱动改不了这个决定。选 source 的规则去看《clocksource 与 clockevent》。
  2. clockevents_config_and_register() 之后，设备进了一个池子，等 tick device 来挑。这不等于它马上成为某个 CPU 的 tick 源。
  3. 中断必须申请。clock event 的异步性完全依赖中断，没中断就没有事件。

十一、用户态看得见的那一面：系统时间服务 #

上面九节讲的是内核里怎么组织。现在换到应用视角。内核要提供的和时间相关的服务只有三种：

  1. 和系统时间相关的服务。往数据库写一条记录时，得记下操作时间：何年何月何日何时。
  2. 让进程睡眠一段时间。
  3. 和 timer 相关的服务。一段指定时间过去后，内核要 alert 用户进程。

这三类需求对应两组 API，加起来覆盖了你在 man 手册里能翻到的全部时间函数。先给总表，后面逐节展开：

精度档 取时间 设时间 睡眠 定时
秒 time() stime() sleep() alarm()
微秒 gettimeofday() settimeofday() usleep() setitimer()
纳秒 clock_gettime() clock_settime() nanosleep() / clock_nanosleep() timer_create() 系列

这张表有个规律：精度越高的那一档，功能也越全。秒和微秒那两档全部被标注为被取代（gettimeofday / settimeofday 和 interval timer 在新 POSIX 标准里标为 obsolescent），纳秒这一档是现在的正确选择。原因不复杂：秒和微秒两档的语义被硬编码成了 CLOCK_REALTIME，你想基于别的 clock 干活就没接口了。

十二、秒级、微秒级、纳秒级的时间函数 #

12.1 秒级：time 和 stime #

c
#include <time.h>

time_t time(time_t *t);
int stime(time_t *t);

time() 返回当前时间点到 Linux epoch 的秒数。这个值由 timekeeper 模块保存，具体字段是 timekeeper->xtime_sec。stime() 设定当前时间点到 Linux epoch 的秒数。

设定时间要权限：调用进程必须持有 CAP_SYS_TIME，否则失败。这条权限检查贯穿本篇所有设时间的接口，后面不再重复。

内核用系统调用 sys_time 和 sys_stime 支持这两个函数。但注意，引入更高精度的系统调用（例如 sys_gettimeofday）之后，这两个系统调用完全可以在用户空间用新系统调用实现 time 和 stime。内核里只有定义了 __ARCH_WANT_SYS_TIME 这个宏，系统才提供这两个系统调用。留着它们的主要目的是兼容旧应用。

配套还有一串把「到 epoch 的秒数」转成人能读的形式的函数：asctime、ctime、gmtime、localtime、mktime，以及线程安全版本 asctime_r、ctime_r、gmtime_r、localtime_r。它们的作用是把 time_t 转成 break-down time 或者字符串。

12.2 微秒级：gettimeofday 和 settimeofday #

c
#include <sys/time.h>

int gettimeofday(struct timeval *tv, struct timezone *tz);
int settimeofday(const struct timeval *tv, const struct timezone *tz);

和上一小节类似，只是精度到微秒。gettimeofday() 拿到从 epoch 到当前时间点的秒数加微秒数。

内核态的实现值得一提：这个值仍然由 timekeeper 提供，具体接口是 getnstimeofday64()，它给的是纳秒精度。微秒级的接口只是把你拿到的纳秒值除以 1000 而已。也就是说，底层精度比接口宣称的高一个数量级，除以 1000 不损失任何精度。

settimeofday() 设定从 epoch 到当前时间点的秒数和微秒数，同样要 CAP_SYS_TIME。

tz 参数纯属历史遗留，内核实际并没有对 timezone 做支持。传 NULL 就行。

sys_gettimeofday 和 sys_settimeofday 这两个系统调用支撑上面两个函数。但新 POSIX 标准把 gettimeofday 和 settimeofday 标为 obsolescent，取而代之的是 clock_gettime 和 clock_settime。

12.3 纳秒级：clock_gettime 和 clock_settime #

c
#include <time.h>

int clock_getres(clockid_t clk_id, struct timespec *res);
int clock_gettime(clockid_t clk_id, struct timespec *tp);
int clock_settime(clockid_t clk_id, const struct timespec *tp);

把 clk_id 这个参数摘掉，这三个函数和 gettimeofday / settimeofday 完全类似，区别只在精度是纳秒。clock 就是时钟，记录时间的流逝；clock ID 就是识别 system clock（系统时钟）的 ID。标准里定义的 ID：

text
CLOCK_REALTIME
CLOCK_MONOTONIC
CLOCK_MONOTONIC_RAW
CLOCK_PROCESS_CPUTIME_ID
CLOCK_THREAD_CPUTIME_ID

按应用需求，内核维护了几个不同的系统时钟。语义如下（完整版见《时间的基本概念与 11 种 clock》）：

clock ID 是不是墙上时钟 谁能改 有 NTP 调整吗 典型用途
CLOCK_REALTIME 是 有 CAP_SYS_TIME 的进程 + NTP 有 记录事件发生时刻
CLOCK_MONOTONIC 是，但基准点不一定是 epoch，多半是系统启动 只有 NTP，其他程序不允许设 有 测量时间间隔
CLOCK_MONOTONIC_RAW 是，纯本地晶振 谁都不能设，连频率都不能调 无 自己实现时间调整
CLOCK_PROCESS_CPUTIME_ID 不是，进程 CPU 时间 — — 进程级性能统计
CLOCK_THREAD_CPUTIME_ID 不是，线程 CPU 时间 — — 线程级性能统计

逐条补几句。

CLOCK_REALTIME 是大家最熟悉的系统时钟，因为它表示真实世界的墙上时钟。前面两节的接口函数都没有指定 clock ID，实际拿到的就是它的值。它允许用户设定（当然要有 CAP_SYS_TIME），这也就意味着用户空间能把它改出不连续的时间间断点。除此之外，它也能被 NTP 调整，NTP 那条路径不产生间断点，它调的是本地振荡器和上游服务器之间的频率误差而已。

CLOCK_MONOTONIC 从名字看就是单调递增的。它也是真实世界的墙上时钟，只是基准点不一定是 epoch（当然也可以是），一般把系统启动的时间点设成基准点，然后一直往上增。除了 NTP，任何程序都不允许设定它，这样就保证了单调性。

为什么要有 CLOCK_MONOTONIC？举个具体的：你设定「事件 A 之后 5 秒执行动作 B」。用 MONOTONIC 就没问题。用 REALTIME，用户在这 5 秒里插一次设时间，B 就永远等不到。这是个纯逻辑的洞，不是实现缺陷。

MONOTONIC 类型的时钟不是绝对时间的概念，多半是算两个采样点之间的时间，并保证采样点之间时间的单调性。另一个常见需求是知道系统启动时间，也需要 MONOTONIC 类型的时钟。

CLOCK_MONOTONIC_RAW 具备 CLOCK_MONOTONIC 的全部特性，除了 NTP 调整。它是一个完全基于本地晶振的时钟，不能设，也不能调晶振频率。它是个底层工具，程序员多半不会直接操作它，用 MONOTONIC 就够。高级场合除外，比如你想用 NTP 以外的方法来调整时间，那就用它。

最后两个 CPU 时钟。有些场景用 real time 的墙上时钟不合适，比如做系统里各个应用的性能分析和统计，墙上时钟会被 NTP 掰来掰去，你算出来的 CPU 时间会漂。所以内核提供了基于进程或线程的系统时钟。要用它们，先拿 clock id：

c
#include <time.h>

int clock_getcpuclockid(pid_t pid, clockid_t *clock_id);

线程版走 pthread：

c
#include <pthread.h>
#include <time.h>

int pthread_getcpuclockid(pthread_t thread, clockid_t *clock_id);

这组接口的精度能到 ns，但实际能达到多少是实现相关的。所以有了 clock_getres()：用它问系统时钟的实际精度，别假设。

三档 API 摆在一起对比：

维度 秒级 微秒级 纳秒级
取时间 time() gettimeofday() clock_gettime()
设时间 stime() settimeofday() clock_settime()
内核取值接口 timekeeper->xtime_sec getnstimeofday64() 后除以 1000 直接纳秒
可选 clock 无，硬编码 REALTIME 无，硬编码 REALTIME 任意 clock ID
权限 设时间要 CAP_SYS_TIME 同左 同左
POSIX 状态 靠 __ARCH_WANT_SYS_TIME 才提供，为兼容 obsolescent 现行

十三、系统时钟的调整：step 与 slewed #

设定系统时间是比较粗暴的做法。你一改，系统里依赖绝对时间的进程就会有各种奇奇怪怪的行为。所以内核另外提供了时间同步接口，让外部的精准计时服务器持续修正系统时钟。

这里有两种调整哲学，术语上是硬性和柔性：

  • step（步进）：直接跳一下，时间轴出现间断点。settimeofday / clock_settime 干的就是这个。
  • slewed（渐进调整）：不跳，慢慢把偏差吃掉，时间轴连续。adjtime / adjtimex 干的是这个。

13.1 adjtime #

c
int adjtime(const struct timeval *delta, struct timeval *olddelta);

按 delta 缓慢修正系统时钟（就是 CLOCK_REALTIME 那个）。olddelta 返回上一次调整里还没走完的 delta。

关键在「缓慢」。它不会让时间跳。比如系统时间比正确时间快了 100ms，adjtime 不会把时钟往回拨 100ms，而是让时钟稍微慢一点走，过一段时间自然对齐。依赖绝对时间的进程感觉不到任何突变。

13.2 adjtimex #

c
#include <sys/timex.h>

int adjtimex(struct timex *buf);

RFC 1305 定义了更复杂更完备的时间调整算法，Linux kernel 通过 sys_adjtimex 支持这套算法，用户空间的接口函数就是 adjtimex。这套算法本身是另一个话题，素材在这里明确留了白，本篇不替它补内容。

内核提供 sys_adjtimex 支持上面两个接口函数。同一个方向上还有 sys_clock_adjtime，用来支持 POSIX clock tunning，实现走 posix-clock.c，细节见《POSIX timer 与 ARM Generic Timer 驱动》那一篇里 timer 相关的部分。

十四、进程睡眠：sleep / usleep / nanosleep / clock_nanosleep #

四个睡眠接口，按精度和责任划分。

14.1 秒级：sleep #

c
#include <unistd.h>

unsigned int sleep(unsigned int seconds);

让当前进程睡眠，seconds 之后（基于 CLOCK_REALTIME）返回继续执行。

返回值有含义：它告诉你进程没睡够的那部分时间。想睡 8 秒，被 signal 打断只睡了 5 秒，返回值就是 3，表示还有 3 秒没睡。所以正确用法是检查返回值，非零就再睡一轮。

14.2 微秒级：usleep #

c
#include <unistd.h>

int usleep(useconds_t usec);

概念和 sleep 一样，返回值的定义不同。返回 0 表示成功，返回 -1 表示失败，错误码在 errno 里。它不告诉你剩余时间。这也是它不好用的地方：被 signal 打断时你拿不到还差多少。

14.3 纳秒级：nanosleep #

c
#include <time.h>

int nanosleep(const struct timespec *req, struct timespec *rem);

usleep 已经是过去式，不建议使用，取而代之的是 nanosleep。req 里设你要睡的秒和纳秒，然后调它让当前进程睡。

返回值：0 成功，-1 失败，错误码在 errno。EINTR 表示被 signal 打断。rem 是 remaining time，告诉你还有多少没睡完。这就把 sleep 的「剩余时间靠返回值」和 usleep 的「errno 报错」两种风格合到一处了。

一个重要事实：内核没有提供 sleep 和 usleep 对应的系统调用，这两个函数的实现位于 C 库。有的系统里这些实现依赖信号，也有的系统用 timer 实现。对 GNU 系统而言，sleep 和 usleep 跟 nanosleep 一样，最终都通过内核的 sys_nanosleep 系统调用实现，底层基于 hrtimer。

这条链路值得追一遍，因为它把本篇上下两半缝到了一起：

text
 sleep(8)          usleep(usec)        nanosleep(req, rem)
    │                   │                    │
    └─────── glibc 封装，最终归一 ────────────┘
                        │
                        ▼
              sys_nanosleep（系统调用）
                        │
                        ▼
                 基于 hrtimer
                        │
                        ▼
         hrtimer 挂在能 reprogram 的 tick device 上
                        │
                        ▼
              回到第9节的高精度 data flow

所以 sleep 的真实精度不由 sleep 这个接口决定，而由第9节里 tick 能不能进 oneshot 决定。跑在 CONFIG_HZ_PERIODIC 的内核上，nanosleep 喊的是纳秒，实际落地精度是一个 tick。

14.4 更高级的：clock_nanosleep #

c
#include <time.h>

int clock_nanosleep(clockid_t clock_id, int flags,
                    const struct timespec *request,
                    struct timespec *remain);

参数多了，功能也就更强。多出来的两个参数各管一件事：

  • clock_id：这个接口不仅能基于 real time clock 睡眠，还能基于其他系统时钟睡。想睡一个「绝对时刻」且不受用户改时间影响，就用 CLOCK_MONOTONIC。
  • flags：等于 0 或 TIMER_ABSTIME，分别指明 request 里给的是相对时间还是绝对时间。素材里的表述是「flag 等于 0 或者 1」，这里的 1 即 TIMER_ABSTIME。

sleep 和 clock_nanosleep 的差别是实质性的：sleep 永远基于 CLOCK_REALTIME，用户一改时间，你的睡眠时长就不可控。要写不受时间调整影响的代码，只能用 clock_nanosleep 配 CLOCK_MONOTONIC。

十五、用户态 timer 服务的三种形态 #

定时器接口有三代，功能一代比一代全。

15.1 alarm：最简单的一代 #

c
#include <unistd.h>

unsigned int alarm(unsigned int seconds);

用 timer 最简单的接口。指定秒数（基于 CLOCK_REALTIME）过去后，向该进程发 SIGALRM。调这个接口的程序得自己设 signal handler，否则 SIGALRM 的默认动作会杀掉进程。

一个进程只能有一个 alarm，重复调用会覆盖前一个，返回值是上一个 alarm 还剩多少秒。

15.2 interval timer：一代半 #

c
#include <sys/time.h>

int getitimer(int which, struct itimerval *curr_value);
int setitimer(int which, const struct itimerval *new_value,
              struct itimerval *old_value);

行为和 alarm 类似，功能更强。每个进程支持 3 种 timer，不同的 timer 定义了怎么计时和发什么信号，which 指明用哪个：

which 计时依据 超时信号
ITIMER_REAL 基于 CLOCK_REALTIME SIGALRM，同 alarm
ITIMER_VIRTUAL 只在该进程用户空间代码执行时计时 SIGVTALRM
ITIMER_PROF 该进程执行时计时，用户空间和陷入内核（如系统调用）都算 SIGPROF

数据结构：

c
struct itimerval {
    struct timeval it_interval; /* next value */
    struct timeval it_value;    /* current value */
};

两个成员分别指明本次和下次（超期后如何设定）的时间值。

靠这个定义，interval timer 能同时表达 one shot 和 periodic 两种形态：

  • it_value 设 5 秒、it_interval 设 3 秒。设定后 it_value 不断递减，5 秒后触发；随后 it_value 被重新加载成 it_interval 的值（3 秒），之后按 3 秒为周期不断触发。
  • it_interval 设 0，就是 one shot，触发一次就完。

old_value 返回上次 setitimer 的设定值。getitimer 拿当前状态，其中 it_value 成员是当前时刻到下一次触发点的时间信息，it_interval 保持不变，除非你重新调 setitimer。

interval timer 也是 POSIX 标准的一部分，但新 POSIX 标准把它标为 obsolescent，取而代之的是 POSIX timer 接口。

15.3 POSIX timer：现行方案 #

interval timer 的不足有明确的四条：

  1. 一个进程只有 ITIMER_REAL、ITIMER_VIRTUAL、ITIMER_PROF 三个 timer。连续设定同一种（例如 ITIMER_REAL），第二次设定会覆盖第一次。
  2. 超时处理永远走信号，而且发哪个信号不能改。
  3. 信号被 mask 时，虽然 timer 多次超期，signal handler 只会被调一次，拿不到更详细的信息。
  4. 精度是微秒级，还有提升空间。

针对这四条，POSIX 标准定义了更灵活的一套接口。它把「定时器」从「进程的三个槽位」变成了「可以任意创建的对象」，通知方式也从「只能发信号」变成了「可以坐下来跟你商量」。

创建：

c
#include <signal.h>
#include <time.h>

int timer_create(clockid_t clockid, struct sigevent *sevp, timer_t *timerid);

clockid 不陌生了。timerid 是返回的 timer 句柄，地位跟 open() 返回的文件描述符一样。重点在 struct sigevent：

c
union sigval {              /* Data passed with notification */
    int     sival_int;      /* Integer value */
    void   *sival_ptr;      /* Pointer value */
};

typedef struct sigevent {
    sigval_t sigev_value;
    int sigev_signo;
    int sigev_notify;
    union {
        int _pad[SIGEV_PAD_SIZE];
        int _tid;
        struct {
            void (*_function)(sigval_t);
            void *_attribute;   /* really pthread_attr_t */
        } _sigev_thread;
    } _sigev_un;
} sigevent_t;

sigev_notify 定义 timer 超期后怎么通知进程，四种取值：

sigev_notify 通知方式 关键字段
SIGEV_NONE 不做异步通知，程序自己调 timer_gettime 轮询状态 无
SIGEV_SIGNAL 发信号这种异步通知方式 sigev_signo 指定信号；发 realtime signal 时附加数据由 sigev_value 给
SIGEV_THREAD 创建一个线程执行超期 callback _attribute 定义该线程属性
SIGEV_THREAD_ID 行为类似 SIGEV_SIGNAL，但信号只送到进程内指定的 thread _tid 标识那个 thread

SIGEV_THREAD_ID 是 Linux 特有的扩展，不在原版 POSIX 里，写可移植代码时留意。

设定：

c
#include <time.h>

int timer_settime(timer_t timerid, int flags,
                  const struct itimerspec *new_value,
                  struct itimerspec *old_value);
int timer_gettime(timer_t timerid, struct itimerspec *curr_value);

timerid 是 timer_create 创建的 timer。new_value 和 old_value 的语义类似 setitimer，不重复。flags 等于 0 或 TIMER_ABSTIME，指明 new_value 里给的是相对时间还是绝对时间。

启停全靠 new_value.it_value：

  • it_value 非 0：调 timer_settime 启动该 timer。
  • it_value 为 0：调 timer_settime 停止该 timer。

timer_gettime 类似 getitimer。

删除：

c
#include <time.h>

int timer_delete(timer_t timerid);

有创建就有删除，timer_delete 删掉指定的 timer，释放资源。不删也行，进程退出时会回收，但长寿命进程里这就是泄漏。

三代 timer 的对比：

维度 alarm setitimer POSIX timer
数量上限 进程 1 个 每类 1 个，共 3 个 任意个，自己持有句柄
可选 clock 无，硬编码 REALTIME 无 任意 clock ID
通知方式 只能 SIGALRM 固定信号，不能改 信号 / 线程 / 不通知，可选
多次超期 会丢 信号被 mask 时只调一次 SIGEV_SIGNAL 配 realtime signal 可排队
精度 ms 级，实际按 tick 微秒 ns 接口
POSIX 状态 保留 obsolescent 现行

十六、从系统调用看内核对齐 #

把用户态函数和内核模块对上，整篇就收口了：

用户态函数 系统调用 内核模块 底层依赖
time() sys_time time.c + timekeeper->xtime_sec clock source
stime() sys_stime time.c 要 CAP_SYS_TIME
gettimeofday() sys_gettimeofday getnstimeofday64() timekeeper
settimeofday() sys_settimeofday do_sys_settimeofday 要 CAP_SYS_TIME
clock_gettime() sys_clock_gettime posix-timers.c clock source + timekeeper
clock_settime() sys_clock_settime posix-timers.c 要 CAP_SYS_TIME
clock_getres() sys_clock_getres posix-timers.c clock source 频率
nanosleep() sys_nanosleep hrtimer.c tick device 能否 oneshot
clock_nanosleep() sys_clock_nanosleep hrtimer.c + clock 选择 同上
sleep() / usleep() 无（glibc 转 sys_nanosleep） glibc + hrtimer.c 同上
alarm() sys_alarm alarmtimer.c 要 CONFIG_RTC_CLASS 才能唤醒（未验证）
setitimer() sys_setitimer itimer.c tick 或 hrtimer
timer_create() 系列 sys_timer_create / sys_timer_settime / sys_timer_delete posix-timers.c hrtimer
adjtime() / adjtimex() sys_adjtimex ntp.c slewed 调整
clock_adjtime() sys_clock_adjtime posix-clock.c POSIX clock tunning

两条规律：

第一，所有「取时间」的路径最终都归到 timekeeper，而 timekeeper 的数来自 clock source 的 cycle 差值。所以用户态读时间的精度上限，是 clock source 的精度。

第二，所有「等一段时间」的路径最终都归到 hrtimer（除了周期 tick 模式下的低精度 timer），而 hrtimer 能不能精确，取决于 tick device 能不能进 oneshot。所以用户态睡眠和定时的精度上限，是时钟事件硬件的精度。

这两条把第3节那张分层图和本章的表串起来了。你在用户态遇到的所有时间精度问题，答案都在这两条链上的某一环。

十七、易错点速查 #

  • 以为配 CONFIG_NO_HZ 就是 tickless。新内核里 CONFIG_NO_HZ 是为兼容旧系统留的，新写法是三选一：CONFIG_HZ_PERIODIC / CONFIG_NO_HZ_IDLE / CONFIG_NO_HZ_FULL，且只能选一个。
  • 以为配了 CONFIG_TICK_ONESHOT 就有 one shot 能力。配置项只表达软件支持，硬件没有 one shot 的 clock event device，系统还是跑周期 tick。
  • 以为配了 CONFIG_HIGH_RES_TIMERS 就必然高精度。还得 tick device 能进 oneshot，否则 hrtimer 只在每个 tick 扫一次 hrtimer_run_queues()，精度等于 tick。
  • 找 CONFIG_GENERIC_TIME 找不到。它已经在某个版本里删了（具体版本未验证），现在一律走通用 clocksource。
  • 拿 gettimeofday 的 tz 参数当真的用。内核没做 timezone 支持，这个参数是历史遗留，传 NULL。
  • 用 CLOCK_REALTIME 测时间间隔。用户改一次时间，你的间隔就废了。测间隔用 CLOCK_MONOTONIC。
  • 用 CLOCK_MONOTONIC 记事件发生时刻。它的基准点多半是系统启动，不是 epoch，和数据库里的 timestamp 对不上。记时刻用 CLOCK_REALTIME。
  • 用 sleep() 做精确延时。它基于 CLOCK_REALTIME，受设时间影响，而且被信号打断时只返回剩余秒数。要精确用 clock_nanosleep() 配 CLOCK_MONOTONIC。
  • 忽略 nanosleep 的 rem。被 EINTR 打断时不知道还剩多少，只能从头再睡一遍，累计误差越滚越大。
  • 连续调用 setitimer(ITIMER_REAL, ...) 以为自己有两个 timer。同一种 which 只有一份，第二次覆盖第一次。
  • 信号被 mask 时指望 interval timer 多触发几次。信号不会排队，handler 只被调一次。需要排队语义得上 POSIX timer 的 realtime signal。
  • 调 stime / settimeofday / clock_settime 没给 CAP_SYS_TIME，然后怀疑内核有 bug。先查权限。
  • 以为 time() 和 stime() 一定是系统调用。只有定义了 __ARCH_WANT_SYS_TIME 的架构才提供，其他架构上是 libc 用新系统调用拼出来的。
  • 拿 clock_gettime 的返回精度当实际精度。接口精度是 ns，实际精度用 clock_getres() 问。
  • 改系统时间期望所有进程无感。step 式调整（settimeofday / clock_settime）一定有间断点，要无感只能用 adjtime / adjtimex 做 slewed 调整。
