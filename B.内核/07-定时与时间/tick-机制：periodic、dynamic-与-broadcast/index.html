一、tick 是什么：内核的心跳 #

操作系统有一堆日常事务要做：更新系统时间、处理低精度 timer、维护正在运行进程的时间片。这些事最省事的做法是轮询——按固定频率去做。轮询需要一个节拍源，硬件上有 HW timer 能周期性地打中断，这就是 tick 的物理来源。

1、tick 的设备侧定义 #

内核里把这项工作抽象成两层：

  • tick：周期性产生的 timer 中断事件
  • tick device：能源源不断产生 tick event 的设备
c
struct tick_device {
	struct clock_event_device *evtdev;
	enum tick_device_mode mode;
};

一句话拆开：tick device 就是「工作在某种模式下的 clock event 设备」。工作模式在 mode 里，具体硬件在 evtdev 里。

c
enum tick_device_mode {
	TICKDEV_MODE_PERIODIC,
	TICKDEV_MODE_ONESHOT,
};

只有两种模式。periodic 是硬件按固定间隔自己打中断；oneshot 是设一次打一次，想要连续 tick 就得每次重新设。

2、为什么心跳频率要权衡 #

HZ 不是随便定的，它在三个方向上拉扯：

方向 HZ 调高的结果 HZ 调低的结果
低精度 timer 精度 精度变好，10ms 周期下 3ms 的 timer 没有意义 精度变差，深睡的设备醒不过来
中断开销 CPU 更多时间花在中断处理上 中断开销小
调度器时间片 刻度更细，响应更快 时间片粒度粗，响应慢
功耗 空转的 tick 越多，越费电 空转少，但唤醒粒度粗

注意低精度 timer 那一行的机制：低精度 timer 挂在 timer wheel 上，wheel 的推进靠 tick，所以定一个比 tick 周期还短的超时，实际触发时间还是被拉到下一个 tick。这不是精度损失一点点，而是物理上不可能更准。

嵌入式设备对周期性 tick 更敏感：待机时长是硬指标，而周期性 tick 意味着 CPU 永远不可能真的睡下去，会按 HZ 的频率被叫醒，电池就这么没了。

二、tick 驱动了哪些子系统 #

tick 不是一个孤立的时钟功能，它是一条驱动总线。搞清「tick 到期后谁被叫醒」，比背结构体有用得多。

1、periodic 模式的驱动链 #

text
HW timer 中断
  → clock_event_device->event_handler
      → tick_handle_periodic()
          → tick_periodic(cpu)
              → [global tick 那台 CPU] do_timer(1)  → 更新 jiffies + 计算全局平均负载
              → [global tick 那台 CPU] update_wall_time()
              → update_process_times(user_mode(get_irq_regs()))
                  → account_process_tick()   进程/系统/空闲时间统计
                  → run_local_timers()       推进 timer wheel，触发 TIMER_SOFTIRQ
                  → rcu_check_callbacks()    RCU 状态机推进
                  → irq_work_tick()          irq_work 队列（含 NOHZ_FULL 的 kick）
                  → scheduler_tick()         调度器 tick，抢占点
                  → run_posix_cpu_timers()   POSIX CPU timer
              → profile_tick(CPU_PROFILING)  采样剖析

（update_process_times 的这一串调用顺序来自 4.20 的 kernel/time/timer.c，6.1 同一函数仍是这个骨架，成员细节有增删。）

2、逐项看影响面 #

被驱动的东西 断 tick 之后的后果 内核怎么补
jiffies 停跳不动，读到的是旧值 tick_do_update_jiffies64() 在 irq_enter / 恢复时按时间戳补齐
wall time 不更新，clock_gettime 变成采样值 退出 idle 时统一 update_wall_time()
timer wheel 不推进，超时不来 直接算出最近的到期点，设给硬件
调度器 不给 TIF_NEED_RESCHED，同优先级不抢占 只允许在「单任务」或「idle」时断 tick
负载统计 采样点缺失，loadavg 失真 calc_load_nohz_start/stop 折算
RCU 回调无法推进，grace period 卡住 rcu_need_cpu 一票否决
POSIX CPU timer 进程级 CPU 时间计时不走 tick_dep 依赖位强制保留 tick
perf 采样 采样频率失控 perf_events 依赖位强制保留 tick
soft lockup 检测 长时间无 tick，误报 tick 处理函数里 touch_softlockup_watchdog_sched()

最后两行是实战里最容易踩的：一台开了 perf 采样的机器上，NOHZ_FULL 那台 CPU 永远不会真的停 tick，因为它一直有 perf 依赖；反过来，停 tick 期间如果 watchdog 没被 touch，就会刷一堆假 lockup 日志。

三、tick device layer 的三层结构 #

kernel/time/tick-*.c 这几个文件各自管一件事，分层比想象中清楚。

1、文件分工 #

文件 职责 关键符号
tick-common.c tick device 通用操作 + periodic tick tick_cpu_device、tick_setup_device、tick_setup_periodic、tick_handle_periodic、tick_periodic、tick_check_new_device
tick-oneshot.c oneshot 模式的接口 tick_switch_to_oneshot、tick_setup_oneshot、tick_program_event、tick_oneshot_mode_active、tick_init_highres
tick-sched.c tick 的调度：产生 tick、停 tick、恢复 tick tick_cpu_sched、tick_nohz_*、tick_sched_timer、tick_do_update_jiffies64
tick-broadcast.c tick 广播 tick_broadcast_device、tick_broadcast_mask、tick_handle_oneshot_broadcast

2、三层抽象 #

层 抽象对象 单位 谁填 谁读
硬件层 HW timer + 中断 寄存器/PPI/SPI SoC 厂商 clockevent 驱动
clockevent layer struct clock_event_device 设备 驱动注册 tick layer
tick device layer struct tick_device CPU（加一个 broadcast） tick_setup_device 时间子系统各模块

一句话说明三者的关系：clockevent layer 管「有哪些 timer 可用、精度多少」；tick layer 管「每个 CPU 用哪个 timer，用什么模式，中断里跑什么 handler」；tick-sched 管「什么时候停，什么时候恢复」。

从设备数量的角度再看一遍，这四个对象的数量关系是 tick 层最容易记错的地方：

对象 定义位置 数量 备注
tick_cpu_device tick-common.c，DEFINE_PER_CPU 每 CPU 一个 local tick device
tick_cpu_sched tick-sched.c，DEFINE_PER_CPU 每 CPU 一个 tick 停止状态与空闲统计
tick_broadcast_device tick-broadcast.c，单个全局变量 1 个 global 视图的 tick device
clock_event_device 由驱动提供 N 个 全局链表管理，不按 CPU 平摊

注意最后一行：clock_event_device 不是 per cpu 的。一个 CPU 可以有多个 local timer，一个全局 timer 也可以服务多个 CPU。每个 CPU 只是从这堆设备里挑一个最适合自己的做 local tick device。

四、tick_device 与 clock_event_device 的关系 #

理解这一层，关键是分清「谁的字段被谁改」。event_handler 和 broadcast 这两个函数指针是焦点。

3、两个函数指针的归属 #

函数指针 谁来写 指向谁 什么时候被调
event_handler tick layer tick_handle_periodic（periodic） / hrtimer_interrupt 或 tick_nohz_handler（oneshot） / tick_handle_periodic_broadcast、tick_handle_oneshot_broadcast（broadcast） 该设备的硬件中断处理函数里

broadcast 回调的架构相关性：include/linux/clockchips.h 里写的是 #ifdef CONFIG_ARCH_HAS_TICK_BROADCAST 才有 tick_broadcast()，否则 #define tick_broadcast NULL，此时 tick_device_setup_broadcast_func 会退化成 err_broadcast，只打一条 pr_crit_once("Failed to broadcast timer tick. Some CPUs may be unresponsive.\n")。也就是说，架构没实现 broadcast 回调时并不是编译失败，而是运行期发一条 crit 日志然后一路错下去。

五、local tick 与 global tick #

1、local tick device #

c
DEFINE_PER_CPU(struct tick_device, tick_cpu_device);

单核时代只有一个 tick，多核以后每个 CPU 各有一个。想当某个 CPU 的 local tick device，要满足两条：

  • 硬件 timer 的中断能送到这个核。clock_event_device->cpumask 表示它能服务哪些核。ARM generic timer 的 timer 基本是 per cpu 的（PPI 中断），这类叫 per cpu timer。
  • 支持 oneshot，并且 rating 最高。前者是 dynamic tick 的门票，后者决定「多个候选时选谁」。

2、global tick 的指针 #

c
int tick_do_timer_cpu __read_mostly = TICK_DO_TIMER_BOOT;

有些工作天生不适合在每个核上都做一遍：更新 jiffies、更新 wall time、更新全系统平均负载。这些只需要一个核来做，那个核上的 local tick 就兼职 global tick。

tick_do_timer_cpu 的取值有三种状态：

值 含义 谁设
>= 0 具体某个 CPU 在干 do_timer tick_setup_device 首次分配
TICK_DO_TIMER_NONE（-1） 没人干，谁看到谁接 停 tick 的 CPU 主动让出
TICK_DO_TIMER_BOOT（-2） 还没分配 静态初始化

这个变量同时干两件事（注释就写在 tick-common.c 里）：

  1. 防止一堆 CPU 同时抢 timekeeping 锁造成惊群，只有被指定的那个核去更新；
  2. 在 NOHZ 场景做责任交接——把值设成 TICK_DO_TIMER_NONE，下一个看到它的 CPU 就接手，保证时间不停止推进。热插拔也走同一套交接逻辑。

3、责任交接的实现（4.20 / 6.1） #

c
/* tick_nohz_stop_tick() 里，停 tick 前主动交出 do_timer 职责 */
if (cpu == tick_do_timer_cpu) {
	tick_do_timer_cpu = TICK_DO_TIMER_NONE;
	ts->do_timer_last = 1;
} else if (tick_do_timer_cpu != TICK_DO_TIMER_NONE) {
	ts->do_timer_last = 0;
}

/* tick_sched_do_timer() 里，跑 tick 的 CPU 发现没人接就自己接 */
if (unlikely(tick_do_timer_cpu == TICK_DO_TIMER_NONE) && !tick_nohz_full_cpu(cpu))
	tick_do_timer_cpu = cpu;

6.1 这一段与 4.20 有一处不同：4.20 在 tick_nohz_full_cpu(cpu) 处是 !tick_nohz_full_cpu(cpu)，6.1 简化成 if (unlikely(tick_do_timer_cpu == TICK_DO_TIMER_NONE))，并加上了 WARN_ON_ONCE(tick_nohz_full_running)，因为开了 NOHZ_FULL 之后 timekeeper 是被明确指定的，不该出现没人接的情况。

4、NOHZ_FULL 下的 do_timer 归属 #

开了 CONFIG_NO_HZ_FULL 之后，规则变了：某个核要被指定为 timekeeper，不能随便交给 nohz_full 集合里的核。5.15 / 6.1 的 tick_setup_device 里有这么一段：

c
if (tick_do_timer_cpu == TICK_DO_TIMER_BOOT) {
	tick_do_timer_cpu = cpu;
	tick_next_period = ktime_get();
#ifdef CONFIG_NO_HZ_FULL
	if (tick_nohz_full_cpu(cpu))
		tick_do_timer_boot_cpu = cpu;
} else if (tick_do_timer_boot_cpu != -1 && !tick_nohz_full_cpu(cpu)) {
	tick_take_do_timer_from_boot();
	tick_do_timer_boot_cpu = -1;
	WARN_ON(tick_do_timer_cpu != cpu);
#endif
}

含义：boot CPU 先临时接管 do_timer，如果有 housekeeping 核上线，就把职责要过去。tick_nohz_init() 里还会拦住 nohz_full 集合里的核下线（tick_nohz_cpu_down 返回 -EBUSY），因为 timekeeper 必须在位。

要点只有一条：nohz_full 集合里的核不能当 timekeeper。do_timer 的归属因此从「谁先注册谁拿」变成了「必须落在 housekeeping 核上」，交接发生在二级 CPU 上线的时刻，不在停 tick 的时刻。

六、tick device 的注册与选择 #

故事的起点在 clockevent layer：驱动初始化时调 clockevents_register_device() 或 clockevents_config_and_register()，里面会回头调 tick_check_new_device()，问 tick layer「这个新设备你要不要」。

1、tick_check_new_device 的判定流程 #

c
void tick_check_new_device(struct clock_event_device *newdev)
{
	struct clock_event_device *curdev;
	struct tick_device *td;
	int cpu;

	cpu = smp_processor_id();
	if (!cpumask_test_cpu(cpu, newdev->cpumask))
		goto out_bc;

	td = &per_cpu(tick_cpu_device, cpu);
	curdev = td->evtdev;

	if (!tick_check_percpu(curdev, newdev, cpu))
		goto out_bc;

	if (!tick_check_preferred(curdev, newdev))
		goto out_bc;

	if (!try_module_get(newdev->owner))
		return;

	if (tick_is_broadcast_device(curdev)) {
		clockevents_shutdown(curdev);
		curdev = NULL;
	}

	clockevents_exchange_device(curdev, newdev);
	tick_setup_device(td, newdev, cpu, cpumask_of(cpu));

	if (newdev->features & CLOCK_EVT_FEAT_ONESHOT)
		tick_oneshot_notify();

	return;

out_bc:
	tick_install_broadcast_device(newdev);
}

三道关卡，加一个收尾：

关卡 函数 干什么
1 cpumask_test_cpu 这个设备根本不服侍本核，直接去 broadcast 那边排队
2 tick_check_percpu 本核和它「有没有缘分」：亲和性能不能设、原配是不是本地专用
3 tick_check_preferred 新欢比原配「优秀」吗：oneshot 能力、rating、本地性
收尾 tick_install_broadcast_device 落选的进 broadcast 候选池

2、tick_check_percpu：偏爱专情 #

c
static bool tick_check_percpu(struct clock_event_device *curdev,
			      struct clock_event_device *newdev, int cpu)
{
	if (!cpumask_test_cpu(cpu, newdev->cpumask))
		return false;

	if (cpumask_equal(newdev->cpumask, cpumask_of(cpu)))
		return true;

	if (newdev->irq >= 0 && !irq_can_set_affinity(newdev->irq))
		return false;

	if (curdev && cpumask_equal(curdev->cpumask, cpumask_of(cpu)))
		return false;

	return true;
}

逐条翻译：

  • 新设备的 cpumask 里没有本核，没戏。
  • 新设备只服务本核——本地 timer，直接通过，后面不用看了。
  • 新设备服务多个核，那就看它的中断能不能改亲和性。不能改就意味着没法把它钉到本核，放弃。
  • 能改亲和性，但本核现役设备已经是本地专用的了。现役设备这么专情，就不要动它了，拒掉新的。

读到第四条的判断可能觉得别扭，这正是原文作者自己标了 TODO 的地方（详见附录勘误）。

3、tick_check_preferred：偏爱优秀 #

c
static bool tick_check_preferred(struct clock_event_device *curdev,
				 struct clock_event_device *newdev)
{
	if (!(newdev->features & CLOCK_EVT_FEAT_ONESHOT)) {
		if (curdev && (curdev->features & CLOCK_EVT_FEAT_ONESHOT))
			return false;
		if (tick_oneshot_mode_active())
			return false;
	}

	return !curdev ||
		newdev->rating > curdev->rating ||
	       !cpumask_equal(curdev->cpumask, newdev->cpumask);
}

先比 oneshot 能力，再比 rating，最后比本地性：

情况 结论
新的没 oneshot，原配有 新的出局
两个都没 oneshot，但系统已经切到 oneshot 模式 新的出局
原配为空 新的直接上
新 rating 更高 新的上
rating 更低但新的是本地 timer、原配不是 新的上

最后一条是硬倾斜：本地 timer 的价值高于 rating 上差一点点。理由很实际——远程 timer 需要额外的 IPI 才能把事件送到本核，这个代价不止一个 rating 点。

4、tick_setup_device：把设备装上去 #

c
static void tick_setup_device(struct tick_device *td,
			      struct clock_event_device *newdev, int cpu,
			      const struct cpumask *cpumask)
{
	void (*handler)(struct clock_event_device *) = NULL;
	ktime_t next_event = 0;

	if (!td->evtdev) {
		if (tick_do_timer_cpu == TICK_DO_TIMER_BOOT) {
			/* 见第五章第 4 节的版本差异 */
			tick_do_timer_cpu = cpu;
			tick_next_period = ktime_get();
		}
		td->mode = TICKDEV_MODE_PERIODIC;
	} else {
		handler = td->evtdev->event_handler;
		next_event = td->evtdev->next_event;
		td->evtdev->event_handler = clockevents_handle_noop;
	}

	td->evtdev = newdev;

	if (!cpumask_equal(newdev->cpumask, cpumask))
		irq_set_affinity(newdev->irq, cpumask);

	if (tick_device_uses_broadcast(newdev, cpu))
		return;

	if (td->mode == TICKDEV_MODE_PERIODIC)
		tick_setup_periodic(newdev, 0);
	else
		tick_setup_oneshot(newdev, handler, next_event);
}

四个要点：

  • 第一次安装时顺带解决 global tick 的归属，顺便初始化 tick_next_period（ktime_get()）和 tick_period（NSEC_PER_SEC / HZ）。注意 tick_period 在 6.1 里已经不在 tick-common.c 中定义了，统一用 TICK_NSEC 宏。
  • 模式永远从 periodic 起步。哪怕硬件有 oneshot，哪怕配了 NO_HZ，第一脚也是 periodic。这是后面「注册期间为什么有 periodic tick」的根源。
  • 换设备时老设备的 event_handler 被改成 clockevents_handle_noop，相当于让它退休。老 handler 和 next_event 被保存下来，oneshot 模式下会传给新设备继续用。
  • 非本地设备要 irq_set_affinity() 钉到本核。

5、谁来交接 period：tick_setup_oneshot #

被替换下来的老设备如果原来是 oneshot，它的 next_event 就是全系统最近的到期点之一。不能丢，所以：

c
void tick_setup_oneshot(struct clock_event_device *newdev,
			void (*handler)(struct clock_event_device *),
			ktime_t next_event)
{
	newdev->event_handler = handler;
	clockevents_switch_state(newdev, CLOCK_EVT_STATE_ONESHOT);
	clockevents_program_event(newdev, next_event, true);
}

tick_setup_oneshot 只在 td->mode 已经是 TICKDEV_MODE_ONESHOT 时才走（见 tick_setup_device 的尾部分支），调用前 handler 和 next_event 是从老设备上抢救下来的。next_event 用 0 初始化、handler 用 NULL 初始化，所以「老设备本来就没有」的场合，这两个值也会原样传下去——tick_setup_oneshot 自己不做判空，靠的是调用者只在该走的路径上调用它。

七、periodic 模式：每个 tick 都中断一次 #

1、从中断到 event_handler #

底层驱动的活儿很单调：注册中断，中断里转头调 clock_event_device->event_handler。以 ARM generic timer 为例（这段来自原文引用的驱动）：

c
err = request_percpu_irq(ppi, arch_timer_handler_phys, "arch_timer", arch_timer_evt);

原文给出的中断处理函数名是 arch_timer_handler_phys_mem，函数体是空壳。真实实现（drivers/clocksource/arm_arch_timer.c）会先读 evt->event_handler 判空再调它，失败时打印 %s: event_handler called without a reason，然后 pr_warn_once("%s: spurious interrupt\n", evt->name)。原文的空壳只能说明这个函数本体没内容，不要把它当真实代码抄。

periodic 场景下，这个 event_handler 被设成 tick_handle_periodic。至此，硬件中断和内核逻辑接上了。所以「tick 是在哪里进入内核」的答案不是 arch_timer 驱动，而是 clock_event_device->event_handler 这条通用指针——换一个 SoC，驱动名和 IP 全变，这行调用不变。

2、tick_setup_periodic #

c
void tick_setup_periodic(struct clock_event_device *dev, int broadcast)
{
	tick_set_periodic_handler(dev, broadcast);

	if (!tick_device_is_functional(dev))
		return;

	if ((dev->features & CLOCK_EVT_FEAT_PERIODIC) &&
	    !tick_broadcast_oneshot_active()) {
		clockevents_set_mode(dev, CLOCK_EVT_MODE_PERIODIC);
	} else {
		unsigned long seq;
		ktime_t next;

		do {
			seq = read_seqbegin(&jiffies_lock);
			next = tick_next_period;
		} while (read_seqretry(&jiffies_lock, seq));

		clockevents_set_mode(dev, CLOCK_EVT_MODE_ONESHOT);

		for (;;) {
			if (!clockevents_program_event(dev, next, false))
				return;
			next = ktime_add(next, tick_period);
		}
	}
}

（4.20 / 6.1 版本里 clockevents_set_mode(dev, CLOCK_EVT_MODE_PERIODIC) 对应改成 clockevents_switch_state(dev, CLOCK_EVT_STATE_PERIODIC)，ktime_add(next, tick_period) 对应 ktime_add_ns(next, TICK_NSEC)，循环里的 next 挪到循环体里自增。）

分支逻辑只有两条路：

条件 做法 代价
硬件支持 periodic，且 broadcast 没在 oneshot 模式 直接设 periodic，硬件自己按周期打 零软件开销
否则 把硬件设成 oneshot，软件在 loop 里一帧一帧地续 每个 tick 一次 clockevents_program_event

第二条路为什么要 for (;;)：clockevents_program_event 可能失败，失败说明目标时间太近（已经过去或离 min_delta 不够），这时候直接挪到下一个周期再设，而不是死等或报错。

第二条路还有个细节容易忽略：next 的初值来自 tick_next_period，读取时用 seq lock 保护。这意味着用 oneshot 模拟 periodic 的 tick 是对齐到全系统的 tick 网格的，不是从设设备那一刻自由起算。多核系统里这很重要，否则各核的 tick 会互相错开，jiffies 的推进步调就乱了。

3、softirq 里的模式切换检查 #

periodic 模式不会自己退出。想要切到 oneshot，得靠周期性检查：每个 tick 会拉起 TIMER_SOFTIRQ，最终跑到 hrtimer_run_pending()：

c
void hrtimer_run_pending(void)
{
	if (tick_check_oneshot_change(!hrtimer_is_hres_enabled()))
		hrtimer_switch_to_hres();
}

c
int tick_check_oneshot_change(int allow_nohz)
{
	struct tick_sched *ts = this_cpu_ptr(&tick_cpu_sched);

	if (!test_and_clear_bit(0, &ts->check_clocks))
		return 0;

	if (ts->nohz_mode != NOHZ_MODE_INACTIVE)
		return 0;

	if (!timekeeping_valid_for_hres() || !tick_is_oneshot_available())
		return 0;

	if (!allow_nohz)
		return 1;

	tick_nohz_switch_to_nohz();
	return 0;
}

四道闸依次是：有没有人通知过（check_clocks 位）、当前是不是还没进任何 nohz 模式、timekeeping 和 tick device 是否都准备好了、要不要走低精度 nohz 分支。allow_nohz 是 !hrtimer_is_hres_enabled() 传进来的，意思是没有高精度 timer 时才轮到 lowres nohz。

八、periodic 模式下的 handler 链 #

1、tick_handle_periodic #

c
void tick_handle_periodic(struct clock_event_device *dev)
{
	int cpu = smp_processor_id();
	ktime_t next = dev->next_event;

	tick_periodic(cpu);

#if defined(CONFIG_HIGH_RES_TIMERS) || defined(CONFIG_NO_HZ_COMMON)
	/*
	 * The cpu might have transitioned to HIGHRES or NOHZ mode via
	 * update_process_times() -> run_local_timers() ->
	 * hrtimer_run_queues().
	 */
	if (dev->event_handler != tick_handle_periodic)
		return;
#endif

	if (!clockevent_state_oneshot(dev))
		return;
	for (;;) {
		next = ktime_add(next, tick_period);

		if (!clockevents_program_event(dev, next, false))
			return;

		if (timekeeping_valid_for_hres())
			tick_periodic(cpu);
	}
}

这个函数有两个坑点值得单独拎出来。

坑点一：中间可能被切走。 tick_periodic() 里会调 update_process_times()，里面跑 run_local_timers()，再里面是 hrtimer_run_queues()，这条链上可能触发 tick_switch_to_oneshot() 把本核的 tick 切到 oneshot。切完之后 dev->event_handler 已经不是 tick_handle_periodic 了，所以必须早退，不能拿旧的 periodic 逻辑继续往下走。原始素材的 3.x 版本没有这个检查，4.20 才补上。

坑点二：oneshot 模拟 periodic 时的死循环防护。 循环里 clockevents_program_event 失败会一路把 next 往后推，同时条件性地调 tick_periodic。为什么调之前要判 timekeeping_valid_for_hres()？注释写得很清楚：tick_periodic 会推进 jiffies，jiffies 推进会让时间变大，时间变大又可能让下一个 program 失败，于是滚成死循环。要求 clocksource 是真正靠得住的硬件源，才敢在循环里继续推进时间。坑点一的版本差异这里同样适用：3.x 的 tick_handle_periodic 没有 handler 早退检查，也没有 for (;;) 那种带防护的补帧循环，是「失败就 return」的简化形态。

2、tick_periodic：干活的实体 #

c
static void tick_periodic(int cpu)
{
	if (tick_do_timer_cpu == cpu) {
		write_seqlock(&jiffies_lock);
		tick_next_period = ktime_add(tick_next_period, tick_period);

		do_timer(1);
		write_sequnlock(&jiffies_lock);
		update_wall_time();
	}

	update_process_times(user_mode(get_irq_regs()));
	profile_tick(CPU_PROFILING);
}

职责划分很清晰：

分支 谁执行 做什么
tick_do_timer_cpu == cpu 只有 global tick 那个核 推进 tick_next_period、do_timer(1)（jiffies + 全局平均负载）、update_wall_time()
无条件执行 每个核 update_process_times()、profile_tick()

3、三种模式下的 handler 对照 #

模式 硬件状态 event_handler 谁产生周期性 tick

九、jiffies 在 periodic 模式下的推进 #

1、periodic 模式：加一 #

periodic 模式下 jiffies 的推进简单到没什么可讲：do_timer(1)，一次加一。这段代码在 3.x 里是在 jiffies_lock 的 seqlock 保护下做的。

2、切到 oneshot 之后：按时间差补 #

一旦不再有周期性中断，jiffies 就不能靠「加一」了，得按流逝的真实时间补：

c
static void tick_do_update_jiffies64(ktime_t now)
{
	unsigned long ticks = 0;
	ktime_t delta;

	delta = ktime_sub(now, last_jiffies_update);
	if (delta < tick_period)
		return;

	write_seqlock(&jiffies_lock);
	delta = ktime_sub(now, last_jiffies_update);
	if (delta >= tick_period) {
		delta = ktime_sub(delta, tick_period);
		last_jiffies_update = ktime_add(last_jiffies_update, tick_period);

		if (unlikely(delta >= tick_period)) {
			s64 incr = ktime_to_ns(tick_period);
			ticks = ktime_divns(delta, incr);
			last_jiffies_update = ktime_add_ns(last_jiffies_update, incr * ticks);
		}
		do_timer(++ticks);
		tick_next_period = ktime_add(last_jiffies_update, tick_period);
	} else {
		write_sequnlock(&jiffies_lock);
		return;
	}
	write_sequnlock(&jiffies_lock);
	update_wall_time();
}

（4.20 源码形态。6.1 改成用 jiffies_seq 的 seqcount 加 jiffies_64 += ticks 直接推进，并加入了 64 位平台的 smp_load_acquire 快速路径——先不加锁看一眼 tick_next_period，没到期就直接返回。ticks 的初值也从 0 改成 1。）

这段代码的核心是两级推进：

  • 进程了常规的一帧：ticks = 0，do_timer(++ticks) 即 do_timer(1)
  • 一次醒得太晚，跨了好几帧：用 ktime_divns 算出跨了几帧，一次性补上

last_jiffies_update 的语义是「上一次 jiffies 更新对应的单调时间」。它不是 now，是累加出来的，这样多次零碎的补帧不会累积误差，jiffies 与真实时间不会漂。

3、tick 停着不动时谁补 jiffies #

这就引出一个问题：CPU 已经睡了 500ms，没有任何 tick，这期间的 jiffies 谁来推进？答案是任何一个被中断叫醒的时点：

c
void tick_irq_enter(void)
{
	tick_check_oneshot_broadcast_this_cpu();
	tick_nohz_irq_enter();
}

tick_nohz_irq_enter() 里如果发现本核 tick_stopped 为真，就调 tick_nohz_update_jiffies(now)，进而走上面那个 tick_do_update_jiffies64()。所以 jiffies 的语义在 NOHZ 系统里是「最近一次有理由更新它时的值」，而不是「此刻精确值」。这是读到 jiffies 必须谨慎的根本原因——中断处理函数里读到的是个旧值，够用，但不精确。

十、oneshot 模式与 dynamic tick #

这一章开始进入补写区。原文（之十二、之十三）只给了结论性描述，实现细节几乎没有。

1、两种入口 #

切到 oneshot 有两条完全不同的路，都不是「用户态开关」：

入口 触发条件 handler nohz_mode
高精度 timer CONFIG_HIGH_RES_TIMERS 且 clocksource 满足 timekeeping_valid_for_hres() hrtimer_interrupt NOHZ_MODE_HIGHRES
低精度 dynamic tick 没有高精度 timer，但硬件支持 oneshot tick_nohz_handler NOHZ_MODE_LOWRES

高精度那条路：

c
int tick_init_highres(void)
{
	return tick_switch_to_oneshot(hrtimer_interrupt);
}

低精度那条路：

c
static void tick_nohz_switch_to_nohz(void)
{
	struct tick_sched *ts = this_cpu_ptr(&tick_cpu_sched);
	ktime_t next;

	if (!tick_nohz_enabled)
		return;

	if (tick_switch_to_oneshot(tick_nohz_handler))
		return;

	hrtimer_init(&ts->sched_timer, CLOCK_MONOTONIC, HRTIMER_MODE_ABS);
	next = tick_init_jiffy_update();
	hrtimer_set_expires(&ts->sched_timer, next);
	hrtimer_forward_now(&ts->sched_timer, tick_period);
	tick_program_event(hrtimer_get_expires(&ts->sched_timer), 1);

	tick_nohz_activate(ts, NOHZ_MODE_LOWRES);
}

两条路都要用 ts->sched_timer 这个 hrtimer 来产生周期性 tick。区别在 handler 不同：低精度用 tick_nohz_handler，它内部直接 tick_program_event()；高精度用 tick_sched_timer，它是标准的 hrtimer 回调，返回 HRTIMER_RESTART 让 hrtimer 框架自己续。

2、tick_switch_to_oneshot：模式切换的守门人 #

c
int tick_switch_to_oneshot(void (*handler)(struct clock_event_device *))
{
	struct tick_device *td = this_cpu_ptr(&tick_cpu_device);
	struct clock_event_device *dev = td->evtdev;

	if (!dev || !(dev->features & CLOCK_EVT_FEAT_ONESHOT) ||
	    !tick_device_is_functional(dev)) {
		pr_info("Clockevents: could not switch to one-shot mode:");
		if (!dev)
			pr_cont(" no tick device\n");
		else if (!tick_device_is_functional(dev))
			pr_cont(" %s is not functional.\n", dev->name);
		else
			pr_cont(" %s does not support one-shot mode.\n", dev->name);
		return -EINVAL;
	}

	td->mode = TICKDEV_MODE_ONESHOT;
	dev->event_handler = handler;
	clockevents_switch_state(dev, CLOCK_EVT_STATE_ONESHOT);
	tick_broadcast_switch_to_oneshot();

	return 0;
}

四个动作，最后一个才是联动：本核 tick device 切模式 → 换 handler → 硬件切 oneshot → broadcast 设备也切。broadcast 跟着切是必须的，否则一个核在 oneshot、broadcast 还在 periodic，语义就打架了。

tick_oneshot_mode_active() 则是一个纯查询，读的只是 tick_cpu_device.mode，不碰硬件：

c
int tick_oneshot_mode_active(void)
{
	unsigned long flags;
	int ret;

	local_irq_save(flags);
	ret = __this_cpu_read(tick_cpu_device.mode) == TICKDEV_MODE_ONESHOT;
	local_irq_restore(flags);
	return ret;
}

用的是 __this_cpu_read 加关中断，说明它期待在中断关闭的上下文里被调用，不打算做跨核同步。

3、tick_sched_timer：把 tick 变成一个 hrtimer #

c
static enum hrtimer_restart tick_sched_timer(struct hrtimer *timer)
{
	struct tick_sched *ts = container_of(timer, struct tick_sched, sched_timer);
	struct pt_regs *regs = get_irq_regs();
	ktime_t now = ktime_get();

	tick_sched_do_timer(ts, now);

	if (regs)
		tick_sched_handle(ts, regs);
	else
		ts->next_tick = 0;

	if (unlikely(ts->tick_stopped))
		return HRTIMER_NORESTART;

	hrtimer_forward(timer, now, TICK_NSEC);
	return HRTIMER_RESTART;
}

这个函数是整个 dynamic tick 的心脏，四步：

  1. tick_sched_do_timer()：承担 do_timer 职责（如果本核是 global tick），然后 tick_do_update_jiffies64()。
  2. tick_sched_handle()：跑 update_process_times() + profile_tick()，等于原来 periodic tick 的第二个分支。
  3. 如果 tick 已经被停掉（tick_stopped），返回 HRTIMER_NORESTART，不再续期。
  4. 否则 hrtimer_forward() 往前推一个周期，返回 HRTIMER_RESTART。

「tick_stopped 与 handler 返回值联动」这个设计很省心：停 tick 的动作不需要真的去 cancel 这个 hrtimer 的每一次实例，只要设了 tick_stopped，下一次触发就自己不再续了。

4、tick_sched_do_timer 里的两个细节 #

c
static void tick_sched_do_timer(struct tick_sched *ts, ktime_t now)
{
	int cpu = smp_processor_id();

	if (unlikely(tick_do_timer_cpu == TICK_DO_TIMER_NONE) && !tick_nohz_full_cpu(cpu))
		tick_do_timer_cpu = cpu;

	if (tick_do_timer_cpu == cpu)
		tick_do_update_jiffies64(now);

	if (ts->inidle)
		ts->got_idle_tick = 1;
}
  • do_timer 责任交接就在这里发生。
  • got_idle_tick 标记「idle 期间 tick 来过」。tick_nohz_idle_got_tick() 会读它并清零，cpuidle 的 governor 用这个判断 idle 是不是被 tick 打断的，从而调整状态选择的激进程度。

5、jiffies 补帧的另一个守卫 #

tick_sched_do_timer() 里还有一段 6.1 才有的逻辑（4.20 没有）：

c
if (ts->last_tick_jiffies != jiffies) {
	ts->stalled_jiffies = 0;
	ts->last_tick_jiffies = READ_ONCE(jiffies);
} else {
	if (++ts->stalled_jiffies == MAX_STALLED_JIFFIES) {
		tick_do_update_jiffies64(now);
		ts->stalled_jiffies = 0;
		ts->last_tick_jiffies = READ_ONCE(jiffies);
	}
}

MAX_STALLED_JIFFIES 是 5。连续 5 次 tick 处理时 jiffies 都没动，说明 timekeeper 那台 CPU 卡住了（比如在 stop_machine() 里，或者被虚拟化 VMEXIT 扣了很久），这时本核强制自己去更新一次 jiffies 兜底。这个坑在虚拟化环境里很常见：vCPU 被宿主机扣住不放，guest 的 timekeeper 就"消失"了一段时间，jiffies 冻住。

6、切换时序：从 time_init 到第一帧 #

把前面的碎片按时间串起来，启动过程大致是这样：

text
start_kernel()
  → time_init()                  clocksource 初始化，local timer 驱动 probe
      → clockevents_register_device()
          → tick_check_new_device()
              → tick_setup_device() → tick_setup_periodic()
                  此时 BSP 上第一帧 periodic tick 开始跑，BSP 兼任 global tick
  → 各 secondary CPU 上线
      → 各自注册 local timer → tick_setup_device() → tick_setup_periodic()
  → 第一个 tick 的 softirq
      → run_local_timers() → hrtimer_run_queues() → hrtimer_run_pending()
          → tick_check_oneshot_change() 通过 → hrtimer_switch_to_hres()
              → tick_init_highres() → tick_switch_to_oneshot(hrtimer_interrupt)
                  → tick_setup_sched_timer()  创建 sched timer
  → 系统进入 oneshot，tick 由 hrtimer 驱动
  → cpuidle 初始化，发现 idle state 有 CPUIDLE_FLAG_TIMER_STOP
      → CLOCK_EVT_NOTIFY_BROADCAST_ON → broadcast 上线（详见第十四章）

这条链里有两处容易看错的细节：hrtimer_switch_to_hres() 本身并不建 timer，建 timer 的是它内部调用的 tick_setup_sched_timer()；而 tick_switch_to_oneshot(hrtimer_interrupt) 换的是本核的 handler，跟 broadcast 设备如何切模式是两件事（broadcast 的切换在第十四章）。

注意时序上的一个硬约束：在 tick_setup_sched_timer() 执行之前，哪怕已经决定要 oneshot，系统里也还没有任何一个 hrtimer 负责产生周期性 tick。这中间有个真空期，靠的是「还没切换」——tick_switch_to_oneshot() 换 handler 和 tick_setup_sched_timer() 建 timer 是紧挨着的两步，都在 hrtimer_run_pending() 的上下文里完成，不会跨 tick。

3、真正停 tick：tick_nohz_idle_stop_tick #

c
static void __tick_nohz_idle_stop_tick(struct tick_sched *ts)
{
	ktime_t expires;
	int cpu = smp_processor_id();

	if (ts->timer_expires_base)
		expires = ts->timer_expires;
	else if (can_stop_idle_tick(cpu, ts))
		expires = tick_nohz_next_event(ts, cpu);
	else
		return;

	ts->idle_calls++;

	if (expires > 0LL) {
		int was_stopped = ts->tick_stopped;

		tick_nohz_stop_tick(ts, cpu);
		ts->idle_sleeps++;
		ts->idle_expires = expires;

		if (!was_stopped && ts->tick_stopped) {
			ts->idle_jiffies = ts->last_jiffies;
			nohz_balance_enter_idle(cpu);
		}
	} else {
		tick_nohz_retain_tick(ts);
	}
}

谁调用它：cpuidle_idle_call() 在真正进 idle 之前调 tick_nohz_idle_stop_tick()。这一步才是「停 tick」。

4、能不能停：can_stop_idle_tick 的四道否 #

c
static bool can_stop_idle_tick(int cpu, struct tick_sched *ts)
{
	if (unlikely(!cpu_online(cpu))) {
		if (cpu == tick_do_timer_cpu)
			tick_do_timer_cpu = TICK_DO_TIMER_NONE;
		ts->next_tick = 0;
		return false;
	}

	if (unlikely(ts->nohz_mode == NOHZ_MODE_INACTIVE))
		return false;

	if (need_resched())
		return false;

	if (unlikely(local_softirq_pending())) {
		/* 有未处理的 softirq，不能停，且有 ratelimit 日志 */
		return false;
	}

	if (tick_nohz_full_enabled()) {
		if (tick_do_timer_cpu == cpu)
			return false;
		if (tick_do_timer_cpu == TICK_DO_TIMER_NONE)
			return false;
	}

	return true;
}

四个否决条件，都直白：

条件 原因
CPU 已离线 顺手交出 do_timer，清 next_tick 防止下次上线被旧值坑
还没进任何 nohz 模式 硬件或配置不支持
有 need_resched 马上要走，停 tick 纯属浪费
有 pending softirq softirq 要靠 tick 之外的东西推动，停了怕卡住
（开了 full dynticks 时）本核是 timekeeper 或职责悬空 必须有核在计时

第四条在新版本里的形态变了：6.1 用 report_idle_softirq() 做了更精细的处理——先剔掉 SOFTIRQ_HOTPLUG_SAFE_MASK，再排除 RT 上 local_bh_blocked() 的情况，剩下的才真正拒绝停 tick，并打一条 pr_warn("NOHZ tick-stop error: local softirq work is pending, handler #%02x!!!\n")。这个日志在调试 tickless 卡死时非常有用。

5、算出能睡多久：tick_nohz_next_event #

c
static ktime_t tick_nohz_next_event(struct tick_sched *ts, int cpu)
{
	u64 basemono, next_tick, next_tmr, next_rcu, delta, expires;
	unsigned long seq, basejiff;

	do {
		seq = read_seqbegin(&jiffies_lock);
		basemono = last_jiffies_update;
		basejiff = jiffies;
	} while (read_seqretry(&jiffies_lock, seq));

	ts->last_jiffies = basejiff;
	ts->timer_expires_base = basemono;

	if (rcu_needs_cpu(basemono, &next_rcu) || arch_needs_cpu() ||
	    irq_work_needs_cpu() || local_timer_softirq_pending()) {
		next_tick = basemono + TICK_NSEC;
	} else {
		next_tmr = get_next_timer_interrupt(basejiff, basemono);
		ts->next_timer = next_tmr;
		next_tick = next_rcu < next_tmr ? next_rcu : next_tmr;
	}

	delta = next_tick - basemono;
	if (delta <= (u64)TICK_NSEC) {
		timer_clear_idle();
		if (!ts->tick_stopped) {
			ts->timer_expires = 0;
			goto out;
		}
	}

	delta = timekeeping_max_deferment();
	if (cpu != tick_do_timer_cpu && (tick_do_timer_cpu != TICK_DO_TIMER_NONE || !ts->do_timer_last))
		delta = KTIME_MAX;

	if (delta < (KTIME_MAX - basemono))
		expires = basemono + delta;
	else
		expires = KTIME_MAX;

	ts->timer_expires = min_t(u64, expires, next_tick);
out:
	return ts->timer_expires;
}

这段是「能睡多久」的完整算法，四层取 min：

层 来源 约束什么
1 rcu_needs_cpu / arch_needs_cpu / irq_work_needs_cpu / timer softirq pending 有这些就得下一帧就醒，next_tick = basemono + TICK_NSEC
2 get_next_timer_interrupt() 下一个 timer wheel 到期点
3 next_rcu 下一个 RCU 需要 CPU 的时点
4 timekeeping_max_deferment() 只有 timekeeper 那台才受限——它要负责别让时间统计停太久

第 4 层是最容易漏掉的：if (cpu != tick_do_timer_cpu && ...) delta = KTIME_MAX; 意思是「不是 timekeeper 的核，可以睡到天荒地老，不用管 max_deferment」。所以 timekeeping_max_deferment() 只对 timekeeper 起作用，这个值来自 clocksource 的能力（能回溯多久不漂），不是 tick 层的选择。

arch_needs_cpu() 是个架构钩子，默认 (0)（在 include/linux/tick.h 里用 #ifndef arch_needs_cpu 兜底），架构不实现它就等于「永远不需要因为架构原因保留 tick」。

6、真的停：tick_nohz_stop_tick #

c
static void tick_nohz_stop_tick(struct tick_sched *ts, int cpu)
{
	struct clock_event_device *dev = __this_cpu_read(tick_cpu_device.evtdev);
	u64 basemono = ts->timer_expires_base;
	u64 expires = ts->timer_expires;
	ktime_t tick = expires;

	ts->timer_expires_base = 0;

	if (cpu == tick_do_timer_cpu) {
		tick_do_timer_cpu = TICK_DO_TIMER_NONE;
		ts->do_timer_last = 1;
	} else if (tick_do_timer_cpu != TICK_DO_TIMER_NONE) {
		ts->do_timer_last = 0;
	}

	if (ts->tick_stopped && (expires == ts->next_tick)) {
		/* 已经停过且目标时间没变，不重复 reprogram */
		if (tick == KTIME_MAX || ts->next_tick == hrtimer_get_expires(&ts->sched_timer))
			return;
		WARN_ON_ONCE(1);
		/* 打一条诊断日志，说明 clockevent 的编程状态和 sched timer 不一致 */
	}

	if (!ts->tick_stopped) {
		calc_load_nohz_start();
		cpu_load_update_nohz_start();
		quiet_vmstat();
		ts->last_tick = hrtimer_get_expires(&ts->sched_timer);
		ts->tick_stopped = 1;
		trace_tick_stop(1, TICK_DEP_MASK_NONE);
	}
	ts->next_tick = tick;

	if (unlikely(expires == KTIME_MAX)) {
		if (ts->nohz_mode == NOHZ_MODE_HIGHRES)
			hrtimer_cancel(&ts->sched_timer);
		return;
	}

	if (ts->nohz_mode == NOHZ_MODE_HIGHRES) {
		hrtimer_start(&ts->sched_timer, tick, HRTIMER_MODE_ABS_PINNED);
	} else {
		hrtimer_set_expires(&ts->sched_timer, tick);
		tick_program_event(tick, 1);
	}
}

停 tick 对 tick 本身的操作只有一句：把 sched timer 的下次到期时间设成「能睡到的那一刻」，而不是下一个 tick 周期。tick_stopped = 1 之后，tick_sched_timer() 下次被调时会返回 HRTIMER_NORESTART，周期性 tick 就此终止。

还有三件顺带的事，都是因为「这期间没人统计了」：

  • calc_load_nohz_start() / cpu_load_update_nohz_start()：记下停 tick 时的负载采样状态，醒来时换算。
  • quiet_vmstat()：把 per-cpu 的 vmstat 差值折叠进全局计数，避免停 tick 期间数据越积越多。
  • trace_tick_stop(1, TICK_DEP_MASK_NONE)：tracepoint，抓 tickless 问题第一手资料。

expires == KTIME_MAX 那一支是「可以永久睡」的场景，直接把 sched timer 取消掉，连 hrtimer 都不留。整个系统的所有 CPU 都处于这个状态时，系统里就没有任何 tick 在跑，只有真实中断能唤醒。

7、恢复：tick_nohz_idle_exit #

c
void tick_nohz_idle_exit(void)
{
	struct tick_sched *ts = this_cpu_ptr(&tick_cpu_sched);
	bool idle_active, tick_stopped;
	ktime_t now;

	local_irq_disable();
	WARN_ON_ONCE(!ts->inidle);
	WARN_ON_ONCE(ts->timer_expires_base);

	ts->inidle = 0;
	idle_active = ts->idle_active;
	tick_stopped = ts->tick_stopped;

	if (idle_active || tick_stopped)
		now = ktime_get();

	if (idle_active)
		tick_nohz_stop_idle(ts, now);

	if (tick_stopped)
		__tick_nohz_idle_restart_tick(ts, now);

	local_irq_enable();
}

（4.20 形态。6.1 把 if (tick_stopped) 那一支换成了 tick_nohz_idle_update_tick(ts, now)，内部再分 tick_nohz_full_cpu 走 full 路径还是普通路径，最后都调 tick_nohz_account_idle_time()。）

「退 idle」内部按顺序做四件事：

  1. tick_nohz_stop_idle()：结算 idle 时长，写进 idle_sleeptime 或 iowait_sleeptime（看 nr_iowait_cpu()）。
  2. tick_nohz_restart_sched_tick()：先 tick_do_update_jiffies64(now) 把 jiffies 补齐，再 timer_clear_idle()、calc_load_nohz_stop()、touch_softlockup_watchdog_sched()，清 tick_stopped，最后 tick_nohz_restart() 把 sched timer 往前对齐重挂。
  3. tick_nohz_account_idle_ticks()：按 jiffies - ts->idle_jiffies 一次性补记 idle 时间，让 update_process_times() 那一格 tick 的记账不至于把整段睡眠算成 busy。
  4. 恢复后 tick_stopped = 0，下一次 tick_sched_timer() 触发时会正常返回 HRTIMER_RESTART，周期性 tick 回来了。

tick_nohz_restart() 的关键在于顺序：先 hrtimer_cancel()，把到期时间拨回 ts->last_tick，再 hrtimer_forward(&ts->sched_timer, now, tick_period) 往前推。last_tick 是停 tick 之前的最后一帧时间，用它做基准往前 forward，保证恢复后的 tick 序列仍然对齐在原来的网格上——不是从「现在」重新起算。

8、中断来了但没要重新调度 #

CPU 睡下去以后被一个与调度无关的中断叫醒（网卡收包、GPIO、IPI），这个中断可能改了 timer wheel、加了 RCU 回调。如果就这么睡回去，这些新情况就丢了。tick_nohz_irq_exit() 就是补这一步：还在 idle 里（ts->inidle）就把 idle 计时起点重置一下，等下一轮 cpuidle_idle_call() 重新算睡多久；不在 idle 里（NOHZ_FULL 那个场景），调 tick_nohz_full_update_tick() 走 full 的重新评估。

十二、NO_HZ_FULL：连忙碌的 CPU 也停 tick #

1、它要解决什么 #

NO_HZ_IDLE 只在 CPU 空闲时停 tick。可如果一台 CPU 上跑着一个长时间死循环的 HPC 进程，或者一个实时线程，那么即使它 99% 的时间在用户态、完全不需要内核介入，tick 依然每秒打进来 HZ 次。每一次都是一次用户态到内核态再回来的往返，cache 被污染的代价在 HPC 场景里非常真实。

NO_HZ_FULL 的目标就是这个：让一个「只有一个任务在跑、且那个任务主要在用户态」的 CPU 也能把 tick 停掉。

2、配置与启动参数 #

依赖列表在第十一章第 1 节已列出。运行期靠启动参数激活：

text
nohz_full=<cpu list>     # 比如 nohz_full=2-7

tick_nohz_full_setup() 只做两件事：把参数里的 CPU 拷进 tick_nohz_full_mask，把 tick_nohz_full_running 置真。真正干活的是 tick_nohz_init()：

c
void __init tick_nohz_init(void)
{
	int cpu, ret;

	if (!tick_nohz_full_running)
		return;

	if (!arch_irq_work_has_interrupt()) {
		pr_warn("NO_HZ: Can't run full dynticks because arch doesn't support irq work self-IPIs\n");
		cpumask_clear(tick_nohz_full_mask);
		tick_nohz_full_running = false;
		return;
	}

	/* 各种版本的差异见下文 */
	for_each_cpu(cpu, tick_nohz_full_mask)
		context_tracking_cpu_set(cpu);

	pr_info("NO_HZ: Full dynticks CPUs: %*pbl.\n", cpumask_pr_args(tick_nohz_full_mask));
}

里面那个「把当前 CPU 从 nohz_full 集合里踢出去」的动作，4.20 的写法与 6.1 不同：

版本 判断条件 说明
4.20 if (cpumask_test_cpu(cpu, tick_nohz_full_mask)) 无条件把 boot CPU 踢出去
6.1 if (IS_ENABLED(CONFIG_PM_SLEEP_SMP) && !IS_ENABLED(CONFIG_PM_SLEEP_SMP_NONZERO_CPU)) 只有挂了修眠、且修眠要求 CPU0 在位时才踢

这个变化的原因是对 PM_SLEEP_SMP 之后修眠可以只留某个非零 CPU 在线，不再强制要求 boot CPU。把 4.20 的行为套到 6.1 上会得出错误的结论。

arch_irq_work_has_interrupt() 那个早退很关键：full dynticks 靠 irq_work 的「自发 IPI」来驱动 tick 的重新调度，如果架构不能从 irq_work 自己发中断，整个机制就不成立。这条线不通时不会崩，而是很干净地把 tick_nohz_full_running 置假、清空掩码，整个功能退化成 NO_HZ_IDLE。

3、停机决策：can_stop_full_tick #

跟 idle 那条路完全不同的一套判断：

c
static bool can_stop_full_tick(int cpu, struct tick_sched *ts)
{
	if (unlikely(!cpu_online(cpu)))
		return false;

	if (check_tick_dependency(&tick_dep_mask))
		return false;
	if (check_tick_dependency(&ts->tick_dep_mask))
		return false;
	if (check_tick_dependency(&current->tick_dep_mask))
		return false;
	if (check_tick_dependency(&current->signal->tick_dep_mask))
		return false;

	return true;
}

四级依赖检查，从全局到线程组：

层级 谁来设 典型场景
全局 tick_dep_mask tick_nohz_dep_set(bit) perf 事件依赖频率采样、clocksource 不稳定
本核 ts->tick_dep_mask tick_nohz_dep_set_cpu(cpu, bit) 本核上有 RCU 回调积压、调度器需要 tick
当前任务 current->tick_dep_mask tick_nohz_dep_set_task(tsk, bit) 这个进程用了 POSIX CPU timer
线程组 current->signal->tick_dep_mask tick_nohz_dep_set_signal(tsk, bit) 整个进程组用了 POSIX CPU timer

依赖位一共六个（enum tick_dep_bits，include/linux/tick.h）：POSIX_TIMER、PERF_EVENTS、SCHED、CLOCK_UNSTABLE、RCU、RCU_EXP。

TICK_DEP_BIT_RCU_EXP 在 6.1 有定义、有掩码，但 check_tick_dependency() 里并没有检查它——5.x 之后 RCU expedited grace period 不再通过这个位强制 tick。这一点跟具体小版本有关，标未验证。

设了依赖位之后还得把已经睡下去的核叫醒：

c
static void tick_nohz_dep_set_all(atomic_t *dep, enum tick_dep_bits bit)
{
	int prev;

	prev = atomic_fetch_or(BIT(bit), dep);
	if (!prev)
		tick_nohz_full_kick_all();
}

「第一次置位才 kick」这个设计避免了一堆重复 IPI。tick_nohz_full_kick_all() 遍历 tick_nohz_full_mask 与 cpu_online_mask 的交集，逐个 irq_work_queue_on()。被 kick 的 CPU 在 tick_nohz_irq_exit() 里发现依赖位变了，就把 tick 重新起起来。

4、full dynticks 下的 host tick #

__tick_nohz_full_update_tick() 是「重新评估」的总入口：能停就 tick_nohz_stop_sched_tick()，已经停了但依赖来了就 tick_nohz_restart_sched_tick()。往外一层 tick_nohz_full_update_tick() 只做两件事——不是 nohz_full 核直接返回；从没进过 nohz（!tick_stopped 且 nohz_mode == INACTIVE）也直接返回，它还在 periodic 模式，还谈不上停不停。

调用点有两处：tick_nohz_irq_exit()（中断返回且不打算重新调度）和 __tick_nohz_task_switch()（切任务）。

5、任务切换时的重新评估 #

c
void __tick_nohz_task_switch(void)
{
	struct tick_sched *ts;

	if (!tick_nohz_full_cpu(smp_processor_id()))
		return;

	ts = this_cpu_ptr(&tick_cpu_sched);

	if (ts->tick_stopped) {
		if (atomic_read(&current->tick_dep_mask) ||
		    atomic_read(&current->signal->tick_dep_mask))
			tick_nohz_full_kick();
	}
}

一个 nohz_full 的 CPU 上，新切进来的任务如果带了 tick 依赖（比如它开了 POSIX CPU timer），必须立刻把 tick 拉回来，否则那个 timer 的时间永远不往前算。tick_nohz_full_kick() 通过 irq_work_queue() 把自己踢一脚——这里用的是本核的 irq_work 而不是直接起 tick，因为这时候可能还在调度器锁里，不能乱来。tick_nohz_full_kick_cpu() 是跨核版本（irq_work_queue_on()），6.1 的 tick_nohz_kick_task() 在任务换核时会走到它。

6、housekeeping：不能停的核 #

开了 NO_HZ_FULL，有一部分核必须保持「正常」：timekeeper、无绑定定时器的承载者、workqueue 之类。这块由 CONFIG_CPU_ISOLATION 的 housekeeping 框架管。两个入口函数（4.20 形态）：

c
static inline bool is_housekeeping_cpu(int cpu)
{
#ifdef CONFIG_NO_HZ_FULL
	if (tick_nohz_full_enabled())
		return cpumask_test_cpu(cpu, housekeeping_mask);
#endif
	return true;
}

housekeeping_affine(struct task_struct *t) 是它的写侧：nohz_full 生效时直接 set_cpus_allowed_ptr(t, housekeeping_mask)。

（6.1 里 housekeeping_mask 这个全局已不再由 tick.h 直接声明，改由 housekeeping_test_cpu() / housekeeping_cpumask() 之类的接口提供，具体符号名标未验证。）

housekeeping_affine() 的用法很有代表性：内核线程被创建时，如果 nohz_full 生效，就直接把它的 CPU 亲和性钉在 housekeeping 核上，不让它跑到 dynticks 核上去干活。这是一个隐式的后台迁移，调试「为什么我的内核线程从没在 CPU3 上跑过」时经常是它干的。

十三、停止 tick 之前必须做什么 #

这一章是对前两章的收束。停 tick 的瞬间，系统里所有「靠 tick 推动」的东西同时失去动力，所以必须先把账结清。

1、五件事的顺序 #

text
tick_nohz_stop_tick()
  1. 交出 do_timer 职责（tick_do_timer_cpu = TICK_DO_TIMER_NONE）
  2. 记下负载采样起点（calc_load_nohz_start / cpu_load_update_nohz_start）
  3. 折叠 per-cpu vmstat（quiet_vmstat）
  4. 记下 last_tick（= sched timer 的到期时间），置 tick_stopped
  5. 把 sched timer 的下次到期时间改成「算出来的最早醒来点」

顺序不能乱：先算得出「最早醒来点」才能改硬件；先把负载/统计的起点记下来再停，否则醒来时那段区间没有起点可算。

2、为什么不能先停 tick 再补账 #

停 tick 之后 CPU 会进 idle 指令，很快失去执行能力。补账的代码可能在停 tick 之后根本得不到执行机会。所以所有需要 CPU 动手的事都必须在停之前完成，停之后唯一能动的是硬件——那个设过去的唤醒时间点。

4、tick_freeze / tick_unfreeze：系统挂起时的极端情况 #

系统进入 suspend 时不是「个别 CPU 停 tick」，而是全部停，包括 timekeeping 本身。这条路走的是另一套接口：tick_freeze() 把 tick_freeze_depth 加一，加满 num_online_cpus() 的那个 CPU 负责关 timekeeping（置 system_state = SYSTEM_SUSPEND 后调 timekeeping_suspend()），其余 CPU 各自 tick_suspend_local()（内部就是 clockevents_shutdown(td->evtdev)）。tick_unfreeze() 是镜像操作：第一个解冻的 CPU 先 timekeeping_resume()，其余 tick_resume_local()。

（6.1 在 timekeeping_suspend() 前面多了一句 sched_clock_suspend()，恢复侧对称加 sched_clock_resume()。）

tick_freeze_depth 是全局深度计数，用 num_online_cpus() 做门槛，所以「谁最后一个进来、谁第一个出去」完全靠计数，不靠 CPU 编号。

十四、broadcast 框架要解决的问题 #

1、场景：local timer 被 CPU 自己关掉了 #

cpuidle 框架决定 idle 状态深浅。CPU 睡得足够深时，硬件会把本核的 timer 也关掉。这带来一个死结：

text
CPU 进入深 idle → local timer 停止 → 该核上所有 software timer 无法唤醒它

没人能叫醒它，它就永远睡下去。而它睡之前明明还有一堆 timer 等着触发。

2、两条出路 #

方案 做法 代价
独立 HW timer 找一个和 cpuidle 无关、常开、不属于任何 CPU 的 timer（GIC 上是 SPI 类型中断，local timer 是 PPI） 需要额外的硬件资源
借某个 CPU 的 local timer 选一个核不退 idle，用它的 local timer + IPI 唤醒其他核 牺牲一个核的功耗

tick broadcast framework 同时支持这两条路，第二种情况叫 hrtimer based broadcast。

3、它不解决的问题 #

broadcast 只解决「deep idle 期间 tick 从哪来」。它不解决「idle 期间怎么算出该睡多久」（那是 tick_nohz_next_event），也不解决「醒来后怎么补 jiffies」（那是 tick_nohz_idle_exit）。这三个机制各管一段，别混在一起看。

十五、broadcast 的软件结构 #

1、全局 tick device #

c
static struct tick_device tick_broadcast_device;

它就是 struct tick_device，没有专用类型。因为广播设备的本质仍然是「一个 tick device」，只不过它服务的是多个 CPU，而不是本核。这个复用让 periodic 那套 tick_setup_periodic() 可以直接拿来给它用——传 broadcast = 1 就够。

2、四组 mask #

c
static cpumask_var_t tick_broadcast_mask;
static cpumask_var_t tick_broadcast_on;
static cpumask_var_t tmpmask;

c
static cpumask_var_t tick_broadcast_oneshot_mask;
static cpumask_var_t tick_broadcast_pending_mask;
static cpumask_var_t tick_broadcast_force_mask;
mask 什么时候用 谁置位
tick_broadcast_mask periodic 场景 tick_device_uses_broadcast()、tick_broadcast_control()
tick_broadcast_on 记录 cpuidle 的「这个核将来可能需要」声明 tick_broadcast_control() 的 ON 分支
tmpmask 计算用的中间变量 各处临时用
tick_broadcast_oneshot_mask oneshot 场景：这些核的 local timer 已关 tick_broadcast_oneshot_control() 的 ENTER 分支
tick_broadcast_pending_mask 这批核的到期事件已经被处理并发出了 IPI tick_handle_oneshot_broadcast()

两个细节值得单独记：

tick_broadcast_on 是后来加的。早期只有一个 tick_broadcast_mask，引入 dummy timer 之后在某个特定场景下出了问题（tick_broadcast_mask 既承担「谁要周期 broadcast」又承担「谁声明过将来要」，语义被压在一起），于是拆成两个：on 记录声明，mask 记录当前实际需求。原作者给的背景链接是 https://lkml.org/lkml/2013/7/2/272。

tick_broadcast_force 是个单向开关。早期形态是 static int tick_broadcast_force;，一旦置 1，TICK_BROADCAST_OFF 就不再生效，按注释「cannot be undone」。主要用于 x86 平台。4.20 起改名 tick_broadcast_forced，语义不变。

3、两组 handler #

handler 挂给谁 场景
tick_handle_periodic_broadcast broadcast 设备（periodic 模式） 有核用 dummy timer 或整机处于 periodic
tick_handle_oneshot_broadcast broadcast 设备（oneshot 模式） 常规的 idle + broadcast 组合

tick_set_periodic_handler() 按 broadcast 参数二选一：0 挂 tick_handle_periodic，非 0 挂 tick_handle_periodic_broadcast。

4、谁能当 broadcast 设备 #

c
static bool tick_check_broadcast_device(struct clock_event_device *curdev,
					struct clock_event_device *newdev)
{
	if ((newdev->features & CLOCK_EVT_FEAT_DUMMY) ||
	    (newdev->features & CLOCK_EVT_FEAT_PERCPU) ||
	    (newdev->features & CLOCK_EVT_FEAT_C3STOP))
		return false;

	if (tick_broadcast_device.mode == TICKDEV_MODE_ONESHOT &&
	    !(newdev->features & CLOCK_EVT_FEAT_ONESHOT))
		return false;

	return !curdev || newdev->rating > curdev->rating;
}

否决条件里最反直觉的是 C3STOP：broadcast 存在的目的就是解决 C3STOP 问题，如果 broadcast 自己依赖的设备也是 C3STOP 的，那就没意义了。PERCPU 同理——只能服务本核的东西没法广播。最后一条只有在 broadcast 设备已经切到 oneshot 模式之后才生效：此时新的候选设备必须也有 oneshot 能力，一个只会 periodic 的设备接不了这个班。

5、hrtimer based broadcast #

没有全局 HW timer 时的保底方案，在 kernel/time/tick-broadcast-hrtimer.c：

c
static struct clock_event_device ce_broadcast_hrtimer = {
	.name			= "bc_hrtimer",
	.set_state_shutdown	= bc_shutdown,
	.set_next_ktime		= bc_set_next,
	.features		= CLOCK_EVT_FEAT_ONESHOT |
				  CLOCK_EVT_FEAT_KTIME |
				  CLOCK_EVT_FEAT_HRTIMER,
	.rating			= 0,
	.bound_on		= -1,
	.min_delta_ns		= 1,
	.max_delta_ns		= KTIME_MAX,
	.min_delta_ticks	= 1,
	.max_delta_ticks	= ULONG_MAX,
	.mult			= 1,
	.shift			= 0,
	.cpumask		= cpu_possible_mask,

（6.1 形态。注意 features 里带 CLOCK_EVT_FEAT_HRTIMER，这是整套 framework 认出「我不是真硬件」的唯一标记。rating = 0 表示它永远是最差的选择，真有硬件 broadcast 设备时一定被替换掉。）

它怎么模拟硬件 timer：tick_setup_hrtimer_broadcast() 把 bctimer 初始化成 CLOCK_MONOTONIC 的 HRTIMER_MODE_ABS hrtimer，回调挂 bc_handler，然后注册 ce_broadcast_hrtimer；bc_handler() 只做两件事——把事件转给 ce_broadcast_hrtimer.event_handler()，返回 HRTIMER_NORESTART。一个 hrtimer 冒充 HW timer，其余全走 tick broadcast 的通用逻辑。

bc_set_next() 里做的是「在哪个 CPU 上 arm 这个 hrtimer，就把 bound_on 记成哪个 CPU」，这个值后面会被 broadcast_needs_cpu() 用上——持有 broadcast hrtimer 的那个核不能进 deep idle。

这套方案的代价在原文里写得很清楚：

代价 后果
local timer 无法把中断直接送到别的核 只能走 IPI，多一次中断往返
支持 CPU hotplug 时要换核 hotplug_cpu__broadcast_tick_pull() 负责把 broadcast 挪到活着的核上
总有一个核不能 idle 功耗上的直接损失

十六、broadcast mask 与 tick_broadcast_oneshot #

1、谁往 mask 里置位 #

置位的入口有两个，对应两种模式：

c
/* periodic 模式：cpuidle 声明「我将来要 broadcast」 */
int tick_device_uses_broadcast(struct clock_event_device *dev, int cpu)
{
	struct clock_event_device *bc = tick_broadcast_device.evtdev;
	unsigned long flags;
	int ret = 0;

	raw_spin_lock_irqsave(&tick_broadcast_lock, flags);

	if (!tick_device_is_functional(dev)) {
		dev->event_handler = tick_handle_periodic;
		tick_device_setup_broadcast_func(dev);
		cpumask_set_cpu(cpu, tick_broadcast_mask);
		if (tick_broadcast_device.mode == TICKDEV_MODE_PERIODIC)
			tick_broadcast_start_periodic(bc);
		else
			tick_broadcast_setup_oneshot(bc);
		ret = 1;
	} else {
		if (!(dev->features & CLOCK_EVT_FEAT_C3STOP))
			cpumask_clear_cpu(cpu, tick_broadcast_mask);
		else
			tick_device_setup_broadcast_func(dev);

		if (!cpumask_test_cpu(cpu, tick_broadcast_on))
			cpumask_clear_cpu(cpu, tick_broadcast_mask);

		switch (tick_broadcast_device.mode) {
		case TICKDEV_MODE_ONESHOT:
			tick_broadcast_clear_oneshot(cpu);
			ret = 0;
			break;
		case TICKDEV_MODE_PERIODIC:
			if (cpumask_empty(tick_broadcast_mask) && bc)
				clockevents_shutdown(bc);
			if (bc && !(bc->features & CLOCK_EVT_FEAT_HRTIMER))
				ret = cpumask_test_cpu(cpu, tick_broadcast_mask);
			break;
		default:
			break;
		}
	}

	raw_spin_unlock_irqrestore(&tick_broadcast_lock, flags);
	return ret;
}

（tick_device_is_functional(dev) 的定义就一行：!(dev->features & CLOCK_EVT_FEAT_DUMMY)。原文注释说 x86 的 apic local timer 会设 DUMMY，意思是「我是个占位符，别真拿我产生 tick，请 broadcast 来」。）

返回值 ret 的语义要小心：它表示「这个核继续用 broadcast，别初始化本地设备」。所以返回非零时 tick_setup_device() 直接 return，per cpu tick device 留在 shutdown 状态。

注意 bc && !(bc->features & CLOCK_EVT_FEAT_HRTIMER) 这个附加条件——4.20 / 6.1 才有的形态。hrtimer based broadcast 的情况下即使 tick_broadcast_mask 里还有这个核，也不能让 per cpu 设备停在 shutdown，因为 hrtimer broadcast 本身要靠某个核的 local timer 撑起来，那个核的本地设备必须是活的。

2、谁的请求更早听谁的：tick_broadcast_set_event #

这是整个 broadcast 的核心机制：

c
static void tick_broadcast_set_event(struct clock_event_device *bc, int cpu,
				     ktime_t expires)
{
	if (!clockevent_state_oneshot(bc))
		clockevents_switch_state(bc, CLOCK_EVT_STATE_ONESHOT);

	clockevents_program_event(bc, expires, 1);
	tick_broadcast_set_affinity(bc, cpumask_of(cpu));
}

（6.1 形态。3.x / 4.0 的版本还多一个 force 参数并且返回 ret，调用方会检查返回值来决定是否 goto 重来。）三个动作：

  1. 确保设备处于 oneshot 状态。
  2. 把到期时间设到广播硬件上。
  3. 把中断定向到 cpu——就是那个请求最早到期的核。这一步是性能关键：broadcast 中断打在哪台 CPU 上，就由那台 CPU 来跑 tick_handle_oneshot_broadcast()，让它顺便处理自己那份到期事件，省掉一次 IPI。

tick_broadcast_set_affinity() 只在设备带 DYNIRQ 时真的改亲和性，否则直接返回；改的时候还要先比一次 cpumask_equal()，相同就不调 irq_set_affinity()——irq_set_affinity() 不算便宜。

3、为什么「只设最近的一个」不会丢事件 #

原文里用一个例子把这个问题说清楚了：

text
当前时刻 X 秒，broadcast 已设为 X+5 秒
CPU A 申请 X+7 秒 → 不用管，X+5 先到，届时统一扫描
CPU B 申请 X+3 秒 → 立刻改成 X+3 秒，A 的需求被"覆盖"

看起来 A 被忽略了。实际上不会：每次 tick_handle_oneshot_broadcast() 都会遍历 tick_broadcast_oneshot_mask 里所有核的 next_event，把没到期的最近一个重新设进去。所以「覆盖」只是一次临时的重排，A 的 X+7 会在 X+3 那次处理时被重新捡起来。

4、broadcast 触发条件汇总 #

条件 触发点 结果
per cpu 的 clock event 是 DUMMY tick_device_uses_broadcast() broadcast 设备进 periodic，永久服务该核
per cpu 设备带 C3STOP 且 cpuidle 发了 ON tick_broadcast_control() 该核进入 tick_broadcast_mask
该核真要进带 CPUIDLE_FLAG_TIMER_STOP 的 state tick_broadcast_oneshot_control(ENTER) 该核进入 tick_broadcast_oneshot_mask，本地 timer shutdown
该核的 next_event 比 broadcast 现有设置更早 tick_broadcast_oneshot_control(ENTER) tick_broadcast_set_event() 提前
该核被别的东西唤醒，且本地事件已过期 tick_broadcast_oneshot_control(EXIT) 进 tick_broadcast_force_mask，交给 broadcast handler 处理
强制模式 tick_broadcast_control(TICK_BROADCAST_FORCE) tick_broadcast_forced = 1，OFF 不再生效

5、tick_broadcast_control #

c
void tick_broadcast_control(enum tick_broadcast_mode mode)
{
	struct clock_event_device *bc, *dev;
	struct tick_device *td;
	int cpu, bc_stopped;
	unsigned long flags;

	raw_spin_lock_irqsave(&tick_broadcast_lock, flags);
	td = this_cpu_ptr(&tick_cpu_device);
	dev = td->evtdev;

	if (!dev || !(dev->features & CLOCK_EVT_FEAT_C3STOP))
		goto out;

	if (!tick_device_is_functional(dev))
		goto out;

	cpu = smp_processor_id();
	bc = tick_broadcast_device.evtdev;
	bc_stopped = cpumask_empty(tick_broadcast_mask);

	switch (mode) {
	case TICK_BROADCAST_FORCE:
		tick_broadcast_forced = 1;
		fallthrough;
	case TICK_BROADCAST_ON:
		cpumask_set_cpu(cpu, tick_broadcast_on);
		if (!cpumask_test_and_set_cpu(cpu, tick_broadcast_mask)) {
			if (bc && !(bc->features & CLOCK_EVT_FEAT_HRTIMER) &&
			    tick_broadcast_device.mode == TICKDEV_MODE_PERIODIC)
				clockevents_shutdown(dev);
		}
		break;
	case TICK_BROADCAST_OFF:
		if (tick_broadcast_forced)
			break;
		cpumask_clear_cpu(cpu, tick_broadcast_on);
		if (cpumask_test_and_clear_cpu(cpu, tick_broadcast_mask)) {
			if (tick_broadcast_device.mode == TICKDEV_MODE_PERIODIC)
				tick_setup_periodic(dev, 0);
		}
		break;
	}

	if (bc) {
		if (cpumask_empty(tick_broadcast_mask)) {
			if (!bc_stopped)
				clockevents_shutdown(bc);
		} else if (bc_stopped) {
			if (tick_broadcast_device.mode == TICKDEV_MODE_PERIODIC)
				tick_broadcast_start_periodic(bc);
			else
				tick_broadcast_setup_oneshot(bc);
		}
	}
out:
	raw_spin_unlock_irqrestore(&tick_broadcast_lock, flags);
}

这个函数就是 broadcast 的总开关。三个门控条件，缺一不可：

  • 没有本地设备，或者本地设备不带 C3STOP。前者是 dummy 的情况（由 tick_device_uses_broadcast() 那条路处理过了），后者是「我自己能搞定 idle」。
  • 设备不是 functional 的（DUMMY），也不归这里管。
  • 之后才进 switch。

最后那一段「如果 tick_broadcast_mask 空了就 shutdown broadcast 设备；如果从空变非空就启动它」是整个框架的开关逻辑——broadcast 设备本身不常开，只在有客户的时候才启动，没客户就关掉省电。

版本提示：3.x 里没有 !bc->features & CLOCK_EVT_FEAT_HRTIMER 与 bc && 两层判断，注释写的是「只有 broadcast 设备存在且非 hrtimer 时才 shutdown 本地设备」，这两层是 4.x 中期补的（精确到哪个小版本未验证）。

6、broadcast mask 里出现了「不该出现」的核 #

真实调试里最常见的一幕：dump 出 tick_broadcast_oneshot_mask 发现某个核明明在跑用户态，位却被置着。

可能原因 机制
那个核刚出 idle，EXIT 还没走 tick_broadcast_oneshot_control() 里先清 mask 再处理
broadcast_needs_cpu() 返回了 -EBUSY 又没清位 hrtimer broadcast 场景，持有 bctimer 的核
该核被 tick_broadcast_force_mask 兜住了 EXIT 时本地事件已过期，交给 broadcast handler 收尾
cpu hotplug 中途 tick_broadcast_offline() 会清三个 oneshot mask

十七、从 broadcast 唤醒 idle CPU 的全过程 #

这一章把一次完整的「CPU 睡了 → broadcast 把它叫醒 → 它继续干活」从头到尾走一遍。这是 tick broadcast 最值得背下来的一段。

1、进入：tick_broadcast_oneshot_control(ENTER) #

c
int __tick_broadcast_oneshot_control(enum tick_broadcast_state state)
{
	struct clock_event_device *bc, *dev;
	int cpu, ret = 0;
	ktime_t now;

	if (!tick_broadcast_device.evtdev)
		return -EBUSY;

	dev = this_cpu_ptr(&tick_cpu_device)->evtdev;

	raw_spin_lock(&tick_broadcast_lock);
	bc = tick_broadcast_device.evtdev;
	cpu = smp_processor_id();

	if (state == TICK_BROADCAST_ENTER) {
		ret = broadcast_needs_cpu(bc, cpu);
		if (ret)
			goto out;

		if (tick_broadcast_device.mode == TICKDEV_MODE_PERIODIC) {
			if (bc->features & CLOCK_EVT_FEAT_HRTIMER)
				ret = -EBUSY;
			goto out;
		}

		if (!cpumask_test_and_set_cpu(cpu, tick_broadcast_oneshot_mask)) {
			WARN_ON_ONCE(cpumask_test_cpu(cpu, tick_broadcast_pending_mask));

			broadcast_shutdown_local(bc, dev);

			if (cpumask_test_cpu(cpu, tick_broadcast_force_mask)) {
				ret = -EBUSY;
			} else if (dev->next_event < bc->next_event) {
				tick_broadcast_set_event(bc, cpu, dev->next_event);

				ret = broadcast_needs_cpu(bc, cpu);
				if (ret)
					cpumask_clear_cpu(cpu, tick_broadcast_oneshot_mask);
			}
		}
	}
	/* EXIT 分支见第 3 节 */
out:
	raw_spin_unlock(&tick_broadcast_lock);
	return ret;
}

（4.20 / 6.1 形态。函数内部对 bc 的判空是根据调用约定假定的：外层 __tick_broadcast_oneshot_control 与 tick_broadcast_oneshot_control 在进入前已经确认过设备存在。3.x 里这个函数叫 tick_broadcast_oneshot_control()，并且开头先判 tick_broadcast_device.mode == TICKDEV_MODE_PERIODIC 直接返回 0。）

逐段拆开：

第一关：broadcast_needs_cpu()。 见第 5 节。 第二关：broadcast 设备在 periodic 模式。 这种情况下它只会周期性地广播，满足不了「按需在 X 时刻唤醒」，所以返回 -EBUSY 让上层放弃深 sleep。如果广播本身就是 hrtimer 假的，也返回 -EBUSY。 第三关：cpumask_test_and_set_cpu() 返回真。 说明这个核已经在 mask 里了（周期性到 oneshot 的切换中间态），不用再关一次本地 timer，也不用重设 broadcast。 第四关：真的要把本地 timer 关掉。 broadcast_shutdown_local() 有条件。 第五关：决定要不要提前 broadcast。 只有「本地事件比 broadcast 当前设定更早」才值得改，否则白改。

5、投递：tick_do_broadcast #

c
static bool tick_do_broadcast(struct cpumask *mask)
{
	int cpu = smp_processor_id();
	struct tick_device *td;
	bool local = false;

	if (cpumask_test_cpu(cpu, mask)) {
		struct clock_event_device *bc = tick_broadcast_device.evtdev;

		cpumask_clear_cpu(cpu, mask);
		local = !(bc->features & CLOCK_EVT_FEAT_HRTIMER);
	}

	if (!cpumask_empty(mask)) {
		td = &per_cpu(tick_cpu_device, cpumask_first(mask));
		td->evtdev->broadcast(mask);
	}

	return local;
}

两个动作：

  • 本核也在 mask 里，就从 mask 里摘掉，直接调用本核的 event handler。省掉一次 IPI 是一次完整的中断往返，值得。
  • 剩下的核交给 broadcast() 回调。注意它选的是 cpumask_first(mask) 那个核的设备上的回调，随便挑一个——注释说「目前只要在所有设备上的 broadcast 函数相同时是安全的，这个缺陷只存在于 x86 的 lapic 上」。

local 的返回值有个重要用途：hrtimer based broadcast 时不能直接调本核的 handler，否则会递归——本地 timer 中断 → 本地 handler → expire_hrtimers() → bc_handler() → 本地 handler → expire_hrtimers()。注释把这个调用链写得明明白白。

7、一个特例：broadcast_needs_cpu #

c
static int broadcast_needs_cpu(struct clock_event_device *bc, int cpu)
{
	if (!(bc->features & CLOCK_EVT_FEAT_HRTIMER))
		return 0;
	if (bc->next_event == KTIME_MAX)
		return 0;
	return bc->bound_on == cpu ? -EBUSY : 0;
}

只有 hrtimer based broadcast 才有意义：

  • 不是 hrtimer 假的，返回 0，谁都可以睡。
  • broadcast hrtimer 还没挂（next_event == KTIME_MAX），返回 0，可以睡。
  • 本核就是持有 bctimer 的那个核，返回 -EBUSY，不能睡。因为 bctimer 是在这个核的 local timer 上跑的，这个核一睡，broadcast 就死了。

这就是 hrtimer based broadcast 的全部代价所在：总要有一个核陪跑。

十八、broadcast 与 cpuidle 的配合 #

1、三段式握手 #

broadcast 不知道哪个 CPU 会进深 idle，cpuidle 也不知道 broadcast 硬件该怎么设。两者靠三条消息对接：

消息 什么时候发 处理函数 效果
CLOCK_EVT_NOTIFY_BROADCAST_ON cpuidle 初始化时，某个 state 带 CPUIDLE_FLAG_TIMER_STOP tick_broadcast_control(TICK_BROADCAST_ON) 声明「我将来可能要」
CLOCK_EVT_NOTIFY_BROADCAST_ENTER 真要进那个 state 之前 tick_broadcast_oneshot_control(ENTER) 关本地 timer，申请按需唤醒
CLOCK_EVT_NOTIFY_BROADCAST_EXIT 出 state 之后 tick_broadcast_oneshot_control(EXIT) 恢复本地 timer

（3.x 里这三条消息由 tick_broadcast_on_off() 统一分发，ON/OFF 走 tick_do_broadcast_on_off()；4.x 之后 ON/OFF 改由 tick_broadcast_control() 处理，ENTER/EXIT 走 tick_broadcast_oneshot_control()。原来的 tick_broadcast_on_off() 在 4.x 之后被删掉了。）

2、ON 为什么不能省 #

如果只有 ENTER/EXIT，那么每次进深 idle 才去关本地 timer、设 broadcast，开销全落在 idle 路径上，而这正是最不该花时间的地方。ON 提前把「这个核可能需要 broadcast」这件事告诉框架，框架就可以在 cpuidle 初始化完成时就把 broadcast 设备启动起来（periodic 场景）或者准备好 oneshot 状态，把准备工作提前摊平。

3、-EBUSY 的语义：不要进深 idle #

tick_broadcast_oneshot_control() 的返回值不是「成功/失败」，而是「能不能进这个深 idle 状态」：

返回 谁返回 cpuidle 怎么理解
0 一切正常 可以进，本地 timer 已经关了，broadcast 接着
-EBUSY broadcast_needs_cpu()、force mask 命中、无 broadcast 设备、periodic + hrtimer 组合 别进，进来了也叫不醒

cpuidle 拿到 -EBUSY 会退回到更浅的 idle state。所以那些「功耗怎么都降不下去，CPU 老是停在 C1」的现场，查 broadcast_needs_cpu() 附近的返回路径是第一步。

4、怎么拿它排障 #

你想确认的事 看哪一行 期望值
系统进 oneshot 了吗 Tick Device: mode 1
本地 tick 挂了什么 handler event_handler tick_sched_timer（hres）/ tick_nohz_handler（lowres）/ tick_handle_periodic（periodic）
broadcast 有没有启用 tick_broadcast_oneshot_mask 全 0 说明没有核在申请
哪个核在关 local timer 各 CPU 段落的 mode 1（SHUTDOWN）说明它把本地 timer 关了
是不是 hrtimer 假 broadcast Clock Event Device: 名字 bc_hrtimer
设备是不是根本没被 tick 用 event_handler: clockevents_handle_noop 该设备在退休状态
有没有 CPU 反复设过近的时间 retries 保持 0 或很小

static int __init setup_tick_nohz(char *str)

怀疑某个延迟抖动是 tickless 引起的，加 nohz=0 重跑一遍是最快的二分手段。

二十一、易错点速查 #

易错认知 实际情况
「tick device 就是 clock_event_device」 tick device 是 struct tick_device，内含一个 clock_event_device 指针和一个 mode
「每个 CPU 有一个 clock_event_device」 clock_event_device 是全局链表管理的，一个 CPU 可以有多个候选，也可能多个 CPU 共用一个
「tick device 会直接进入 oneshot 模式」 首次安装一律 TICKDEV_MODE_PERIODIC，靠 softirq 里的 tick_check_oneshot_change() 往上切
「切到 oneshot 就没 tick 了」 错了，tick 还在，只是由 sched_timer 这个 hrtimer 产生
「tick_nohz_idle_enter() 会停 tick」 4.9 之后不会，它只置 inidle；真正停 tick 的是 tick_nohz_idle_stop_tick()
「jiffies 永远是当前时间」 NOHZ 下它是「最近一次被更新时的值」，中断里读到的可能是旧值
「broadcast 只服务 idle 的 CPU」 periodic 模式下它也服务 DUMMY 设备的 CPU，那些 CPU 可能正在跑任务
「broadcast 设备一直开着」 只在 tick_broadcast_mask 非空时启动，空了就 clockevents_shutdown()
「broadcast 会漏掉晚到的请求」 不会，每次 handler 都全量扫描 tick_broadcast_oneshot_mask 重设最近的到期点
「tick_broadcast_oneshot_control() 返回 0 是成功」 0 表示「可以进深 idle」，-EBUSY 表示「别进」，语义是决策不是错误码
「hrtimer based broadcast 不花钱」 花的，总有一个核被 broadcast_needs_cpu() 钉在浅 idle
「TICK_BROADCAST_FORCE 可以撤销」 不能，代码注释写着 cannot be undone
「arch_needs_cpu() 在所有架构上都有实现」 默认宏是 (0)，没实现的架构上永远返回 0
「tick_do_timer_cpu 一旦定了就不变」 会变，停 tick 时可能被置成 TICK_DO_TIMER_NONE 等别人接手
「CONFIG_NO_HZ_FULL 开了就全程无 tick」 还需要 nohz_full=<cpulist> 启动参数，且只在单任务、无依赖时停
