一、时间源与事件源：一对必须分清的概念 #

先给结论，一句话切开：

  • clocksource 是一条只增不减的时间轴。它有一个自由运行的计数器，你随时可以读，读到的值（cycles）经过换算就是「从某个基准点起过去了多少纳秒」。
  • clockevent 是一次性（或周期性）的闹钟。你告诉它「再过 N 个 tick 给我一个中断」，它到点触发，然后闭嘴，等你设置下一次。

两者最大的差别不在硬件，而在谁主动。clocksource 是被动的：没人问，它什么都不干，也不产生任何事件。clockevent 是主动的：设了就会响，响了你必须处理，不处理它会一直响（periodic 模式下真的会一直响）。

再看它们和硬件的对应关系，这是本篇后半段的伏笔：

维度 clocksource clockevent
核心硬件资源 一个 free running 的 counter 一个 counter + 一个比较器（comparator）
数据方向 内核去读硬件 内核写硬件，硬件来打断内核
是否需要中断 不需要 必需（否则「到点」无从感知）
数量 全系统可以注册多个，只有一个是 curr_clocksource 每个 CPU 一个本地设备，另有一个全局的
选优标准 rating 越高越好，还要求高精度能力 rating 越高越好，还要求 feature 匹配
失败后果 读出来的时间走歪 该响的没响，或响了没停
典型代表 TSC、HPET、ACPI PM Timer、jiffies local APIC timer、HPET channel 0、PIT

把这张表记住，后面所有细节都是它的展开。

有一个常见的误解要当场拆掉：不是有了 clocksource 就不需要 clockevent。你随时能知道现在几点，不代表你知道什么时候该醒来干活。中断是硬件事件，没有计数器比较器就产生不了。反过来也一样：本地 APIC timer 能在 C3 状态下停摆，它做 clockevent 会有 bug，但也从来不打算做 clocksource。

再补一个方向上的对称：两者用同一套定点换算机制。clocksource_cyc2ns() 把 cycles 换成纳秒，clockevents 用同样的 mult/shift 把纳秒换成 ticks，只是 from 和 to 两个频率参数掉了个方向。这一点到第六章和第十四章还会再撞见。

二、clocksource 要满足什么条件 #

不是随便一个计数器都能当 clocksource。内核隐含要求下面几条，条条都有代价：

一、单调。读数不能倒退。硬件 CRITICAL 的地方在于回绕：一个 32 bit 的计数器，跑到 0xFFFFFFFF 之后回绕到 0。这在数学上是「模 2^32 单调」，只要两次读数的间隔小于半个回绕周期，减法（配合 mask）就不会算错。时间轴因此不是一条无限长的直线，而是一条由首尾相接的线段拼成的线。原文这个比喻是准确的：内核的时间更像不断重复的线段拼出的 timeline。

二、可换算。频率必须已知且稳定。1GHz 的计数器一个 cycle 就是 1ns；10MHz 的一个 cycle 是 100ns。频率如果不稳（比如跟着 CPU 主频变频的早期 TSC），读数就没有固定意义。

三、分辨率够。这是 rating 想表达的东西。10ms 一个 cycle 的计数器拿来做时间源，clock_gettime() 的精度上限就是 10ms，够不够用取决于你在做什么。

四、宽度够。mask 决定了一条线段多长。32 bit 在 1GHz 下只有 4.29 秒就回绕一次；64 bit 的 TSC 在可预见的未来不会回绕。

五、跨核一致。SMP 下多个 CPU 会同时读同一个时间源。若每个核的计数器不同步，读数会互相打架，时间轴上出现跳变。PC 上 TSC 在不同步时由 watchdog 摘掉，就是这条要求的具体体现。

六、不受低功耗状态影响。CPU 进 C3 后计数器若停摆，读数就漏掉了时间。CLOCK_SOURCE_SUSPEND_NONSTOP 这个 flag 就是给「挂起期间不停」的时间源准备的。

这六条之间经常互斥。宽、快、准、跨核同步、低功耗不停摆，很难同时满足。内核的做法是允许注册多个，选一个当前最合适的，剩下的留着当候选与 watchdog 参照。这就是 rating 机制存在的理由。

三、struct clocksource 的核心字段 #

先看 3.x 原文给出的定义，这是素材里最有价值的部分，一字不改照录：

c
struct clocksource {
    cycle_t (*read)(struct clocksource *cs);==============（1）
    cycle_t cycle_last;
    cycle_t mask;
    u32 mult;
    u32 shift;
    u64 max_idle_ns;
    u32 maxadj;

    const char *name;=====================================（2）
    struct list_head list;
    int rating;
    int (*enable)(struct clocksource *cs);
    void (*disable)(struct clocksource *cs);
    unsigned long flags;
    void (*suspend)(struct clocksource *cs);
    void (*resume)(struct clocksource *cs);

#ifdef CONFIG_CLOCKSOURCE_WATCHDOG=======================（3）
    struct list_head wd_list;
    cycle_t cs_last;
    cycle_t wd_last;
#endif

    struct module *owner;
} ____cacheline_aligned;

原文把字段分成三组，这个划分很到位：第一组是计时热路径，第二组是系统操作相关，第三组是 watchdog 私有。我们照这个分组逐条过，同时标出 5.15 的变化。

第一组：热路径字段 #

字段 含义 5.x 变化
read 读当前 counter 值，返回 cycles 返回类型 cycle_t 改名 u64；参数名 cs 保留
cycle_last 上次读到的 cycle 值，用于算差值 已删除，差值状态迁到 timekeeper 的 tkr->cycle_last
mask 回绕掩码，做模减用 保留
mult cycle 到 ns 的乘数因子 保留
shift cycle 到 ns 的右移位数 保留
max_idle_ns 保证 cycles * mult 不溢出的最大空闲纳秒数 保留
maxadj mult 允许被 NTP 调整的最大幅度（约 11%） 保留

cycle_last 的删除值得单说。原文注释讲得很好：热路径字段放在结构体最前面、结构体 ____cacheline_aligned，是为了「访问了 read，后面几个成员就一起进 cacheline」。这个优化在 3.x 成立，因为 timekeeping 每次都要拿 cs->cycle_last。到了 5.x，timekeeper 自己缓存了 mult/shift/mask/cycle_last，struct clocksource 本体不再出现在时间读取热路径上。5.15 的注释明确写了这一点：

text
 * Note: This struct is not used in hotpathes of the timekeeping code
 * because the timekeeper caches the hot path fields in its own data
 * structure, so no cache line alignment is required,

注意最后半句「no cache line alignment is required」。5.x 的 struct clocksource 已经去掉了 ____cacheline_aligned。这与原文（以及很多老教程）的描述不同，是个实打实的行为变化。struct clock_event_device 在 5.15 里则仍然保留了这个属性。

第二组：管理字段 #

字段 含义 5.x 变化
name 名字，sysfs 里看到的、override_name 匹配的就是它 保留
list 挂进全局 clocksource_list 的节点，按 rating 降序 保留
rating 选优权重 保留
enable / disable 启停回调 保留
flags CLOCK_SOURCE_* 位 见下表
suspend / resume 电源管理回调 保留
owner 模块引用 保留

flags 的位定义变化不小，逐位对比：

宏 3.x 5.15 作用
CLOCK_SOURCE_IS_CONTINUOUS 有 有 无空洞、无跳变，高精度 tick 的前提
CLOCK_SOURCE_MUST_VERIFY 有 有 必须被 watchdog 验证过后才敢用
CLOCK_SOURCE_WATCHDOG 有 有 已被 watchdog 采信（内部标志）
CLOCK_SOURCE_VALID_FOR_HRES 有 有 可用于高精度模式
CLOCK_SOURCE_UNSTABLE 有 有 被判定走歪了
CLOCK_SOURCE_SUSPEND_NONSTOP 有 有 挂起期间不停，可用来算睡眠时长
CLOCK_SOURCE_RESELECT 无 有（0x100） 请求重新选举
CLOCK_SOURCE_VERIFY_PERCPU 无 有（0x200） 需要对每个 CPU 单独验同步

后两个是新加的，RESELECT 在 watchdog 里用，VERIFY_PERCPU 对应 clocksource_verify_percpu() 那套跨核比对。

第三组：watchdog 私有 #

wd_list 是挂进 watchdog_list 的节点，cs_last 和 wd_last 分别是被监视时间源与基准时间源在上一次检查时的读数。这三个字段在 5.15 里原样保留，只是类型从 cycle_t 变成 u64。第八章专门讲它们的用法。

5.x 新增的字段 #

5.15 的 struct clocksource 还多出这些：

字段 作用
uncertainty_margin 每半秒允许的不确定度（ns），watchdog 判歪的阈值来源
archdata 架构相关的可选数据（CONFIG_ARCH_CLOCKSOURCE_DATA）
max_cycles 做 cycles * mult 不溢出的最大 cycle 值
id enum clocksource_ids，快照时校验来源
vdso_clock_mode 是否可被 vDSO 直接用
mark_unstable 通知驱动「你的时间源被 watchdog 判歪了」
tick_stable watchdog 周期性提供的稳定同步点回调

max_cycles 是把 max_idle_ns 背后的中间量显式存下来，clocks_calc_max_nsecs() 一次算两个值。mark_unstable 让驱动能自己收拾残局，TSC 的 tsc_cs_mark_unstable() 就是个例子：它会把 sched_clock 切回 jiffies 基准。

四、rating：多个时间源时怎么选 #

rating 是一个整数，越大越优先。原文提到「内核代码的注释已经足够了」，但素材里那张注释表在抓取时丢了。这里补上 3.x 与 5.15 共有的档位说明，原文照译：

区间 代码注释原文 含义
1–99 Unfit for real use. Only available for bootup and testing purposes. 不可用于生产，只给启动和测试用
100–199 Base level usability. Functional for real use, but not desired. 能用，但不想要
200–299 Good. A correct and usable clocksource. 好，正确且可用
300–399 Desired. A reasonably fast and accurate clocksource. 想要，够快够准
400–499 Perfect. The ideal clocksource. A must-use where available. 理想时间源，有就用它

注释还特别写了动机：to avoid rating inflation（防止 rating 通货膨胀）。意思是别都往 400 上堆，否则档位失去区分度。

光有档位不够，还得看真家伙。下面是从 5.15 源码里逐个核出来的实际取值：

时间源 定义位置 rating 备注
tsc arch/x86/kernel/tsc.c 300 带 VALID_FOR_HRES、VERIFY_PERCPU
tsc-early arch/x86/kernel/tsc.c 299 精校前的临时货，校准完成后注销
hpet arch/x86/kernel/hpet.c 250 mask 为 32 bit
acpi_pm drivers/clocksource/acpi_pm.c 200 有缺陷芯片组会被降到 120
jiffies kernel/time/jiffies.c 1 兜底，注释写明「lowest valid rating」
refined-jiffies kernel/time/jiffies.c 2 jiffies 的 rating + 1

tsc 是 300 而不是 400，这个细节很多人记错。400 档在主流 x86 上是空着的。

acpi_pm 的降级逻辑值得抄下来，它是个「硬件有 bug 就自降身价」的示范：

c
static inline void acpi_pm_need_workaround(void)
{
	clocksource_acpi_pm.read = acpi_pm_read_slow;
	clocksource_acpi_pm.rating = 120;
}

PCI fixup 识别到 PIIX4 勘误（计数器自增期间有 3ns 窗口读数不确定）后调用它。读数函数换成三读取中的 acpi_pm_read_verified()，rating 从 200 掉到 120。换实现 + 降 rating 一起做，这是正确姿势：光降 rating 不换实现，等于把慢读留在原地。

rating 还有个隐藏规则：不只是整数大小，还看 flag。clocksource_find_best() 里有个开关：

c
static struct clocksource *clocksource_find_best(bool oneshot, bool skipcur)
{
	struct clocksource *cs;

	if (!finished_booting || list_empty(&clocksource_list))
		return NULL;

	list_for_each_entry(cs, &clocksource_list, list) {
		if (skipcur && cs == curr_clocksource)
			continue;
		if (oneshot && !(cs->flags & CLOCK_SOURCE_VALID_FOR_HRES))
			continue;
		return cs;
	}
	return NULL;
}

oneshot 为真时，没有 CLOCK_SOURCE_VALID_FOR_HRES 的直接跳过。所以「rating 最高」有个前提：在当前 tick 模式下有资格。这解释了一个现象：同一台机器，nohz=off 和 nohz=on 下 /sys/devices/system/clocksource/clocksource0/current_clocksource 会不一样。

五、clocksource 的注册与注销 #

注册接口是给底层 timer 驱动用的。原文介绍了两条路子，我们按 5.x 的实际形态重述。

路子一：驱动自己算好 mult 与 shift #

3.x 有 clocksource_register()，语义是「我自己的 mult/shift 都填好了，你别动」。5.15 这个函数已经不存在，取而代之的是：

c
static inline int __clocksource_register(struct clocksource *cs)
{
	return __clocksource_register_scale(cs, 1, 0);
}

注意 freq 传 0。__clocksource_update_freq_scale() 里有这么一段注释：

text
 * Default clocksources are *special* and self-define their mult/shift.
 * But, you're not special, so you should specify a freq value.

也就是说，只有 jiffies 这种「默认时间源」才走这条特殊路径，传 0 表示「别给我算，我自己有」。头文件里那个函数也明说了：

text
/*
 * Don't call this unless you are a default clocksource
 * (AKA: jiffies) and absolutely have to.
 */

普通驱动不要走这条路。 传 0 会连带跳过 maxadj 溢出收缩循环（那个循环的 while 条件里有 freq &&），只留一个 WARN_ONCE 提醒存在溢出风险。

路子二：驱动给频率（推荐） #

c
static inline int clocksource_register_hz(struct clocksource *cs, u32 hz)
{
	return __clocksource_register_scale(cs, 1, hz);
}

static inline int clocksource_register_khz(struct clocksource *cs, u32 khz)
{
	return __clocksource_register_scale(cs, 1000, khz);
}

__clocksource_register_scale() 是真正干活的，5.15 版本按骨架重写如下（省略日志与 VDSO 校验细节）：

c
int __clocksource_register_scale(struct clocksource *cs, u32 scale, u32 freq)
{
	unsigned long flags;

	clocksource_arch_init(cs);
	/* 校验 id 与 vdso_clock_mode，越界则回落到缺省值 */

	/* 初始化 mult/shift 与 max_idle_ns/max_cycles */
	__clocksource_update_freq_scale(cs, scale, freq);

	mutex_lock(&clocksource_mutex);

	clocksource_watchdog_lock(&flags);
	clocksource_enqueue(cs);
	clocksource_enqueue_watchdog(cs);
	clocksource_watchdog_unlock(&flags);

	clocksource_select();
	clocksource_select_watchdog(false);
	__clocksource_suspend_select(cs);
	mutex_unlock(&clocksource_mutex);
	return 0;
}

和 3.x 原版比，多了三步：clocksource_select_watchdog() 选基准时间源、__clocksource_suspend_select() 选挂起计时用的时间源、以及对 id/vdso_clock_mode 的校验。原文列的六步（算 maxadj、算 max_idle_ns、加锁、入队、处理 watchdog、选举）主线没变。

入队就是按 rating 降序插入有序链表，所以 clocksource_list 从头到尾就是从好到坏：

c
static void clocksource_enqueue(struct clocksource *cs)
{
	struct list_head *entry = &clocksource_list;
	struct clocksource *tmp;

	list_for_each_entry(tmp, &clocksource_list, list) {
		/* Keep track of the place, where to insert */
		if (tmp->rating < cs->rating)
			break;
		entry = &tmp->list;
	}
	list_add(&cs->list, entry);
}

这带来一个副作用，clocksource_find_best() 里直接取第一个满足条件的节点就算最优，不用遍历比较。省事，但前提是链表始终有序，clocksource_change_rating() 必须把节点删掉重插：

c
static void __clocksource_change_rating(struct clocksource *cs, int rating)
{
	list_del(&cs->list);
	cs->rating = rating;
	clocksource_enqueue(cs);
}

注销 #

clocksource_unregister() 只是加锁后调 clocksource_unbind()。原文抄的是 3.x 版，5.15 版多了两段，完整逻辑：

c
static int clocksource_unbind(struct clocksource *cs)
{
	unsigned long flags;

	if (clocksource_is_watchdog(cs)) {
		/* Select and try to install a replacement watchdog. */
		clocksource_select_watchdog(true);
		if (clocksource_is_watchdog(cs))
			return -EBUSY;
	}

	if (cs == curr_clocksource) {
		/* Select and try to install a replacement clock source */
		clocksource_select_fallback();
		if (curr_clocksource == cs)
			return -EBUSY;
	}

	if (clocksource_is_suspend(cs)) {
		clocksource_suspend_select(true);
	}

	clocksource_watchdog_lock(&flags);
	clocksource_dequeue_watchdog(cs);
	list_del_init(&cs->list);
	clocksource_watchdog_unlock(&flags);
	return 0;
}

三处 -EBUSY 的含义：正在当 watchdog 基准且找不到替补、正在当当前时间源且找不到替补（即全系统只剩它）、正在当挂起计时源（这一条不返回错误，只换人）。原文只覆盖了前两条，第三条是 5.x 新加的。

六、mult 与 shift：从 cycles 转换到 ns #

这一章是整篇最硬的部分，慢慢来。

为什么不用除法 #

从 cycles 到纳秒的原始公式：

text
转换后的纳秒数目 = (A / F) x NSEC_PER_SEC

F 是计数器频率。这个式子要做除法。CPU 有乘法器但不一定有除法器，软除法的代价在内核热路径上不能接受，而且 F 是运行期才知道的值，编译器没法优化成常数。用浮点？

内核不用浮点。原因很简单：内核态不保存浮点/SIMD 上下文，用一次就得手动 kernel_fpu_begin() 包起来，代价远大于省下的那条除法指令；中断上下文里更是不许碰。原文那句「请把答案寄到蜗窝科技大厦」是在开玩笑，答案是「上下文保存成本 + 中断上下文禁用」。

解法是定点：把 1/F 放大 2^shift 倍存成整数 mult，乘完再右移回来。

c
static inline s64 clocksource_cyc2ns(u64 cycles, u32 mult, u32 shift)
{
	return ((u64) cycles * mult) >> shift;
}

这个公式 3.x 与 5.15 完全一致，唯一的类型变化是 cycle_t 改成 u64。5.15 的注释还补了一句很重要的限定：

text
 * The code is optimized for performance and is not intended to work
 * with absolute clocksource cycles (as those will easily overflow),
 * but is only intended to be used with relative (delta) clocksource cycles.

只能喂差值，不能喂绝对值。 TSC 读到 10^15 量级的绝对 cycle，乘上 mult 立刻爆 64 bit。这一条是新手最常踩的坑，第二十章还会回到它。

mult 怎么推出来 #

从 ns = (cycles * mult) >> shift 出发，取 cycles 为频率值即一秒的量：

text
根据 ns = (cycles * mult) >> shift，令 cycles = F、ns = 1e9：
    mult = (1e9 << shift) / F

这就是 clocks_calc_mult_shift() 里 tmp = (u64) to << sft; tmp += from / 2; do_div(tmp, from); 三行的来历。to 在 clocksource 场景是 NSEC_PER_SEC（1e9），from 是计数器频率。加 from/2 是做四舍五入。

shift 怎么定：反向搜索 #

shift 越大精度越高，但 cycles * mult 越容易溢出 64 bit。所以有个上限，由「最大需要覆盖的 cycle 数」决定。完整代码：

c
void clocks_calc_mult_shift(u32 *mult, u32 *shift, u32 from, u32 to, u32 maxsec)
{
	u64 tmp;
	u32 sft, sftacc = 32;

	/* 计算限制转换范围的 shift 因子： */
	tmp = ((u64)maxsec * from) >> 32;
	while (tmp) {
		tmp >>= 1;
		sftacc--;
	}

	/* 找到精度最好、且能塞进 maxsec 范围的 shift/mult 组合： */
	for (sft = 32; sft > 0; sft--) {
		tmp = (u64) to << sft;
		tmp += from / 2;
		do_div(tmp, from);
		if ((tmp >> sftacc) == 0)
			break;
	}
	*mult = tmp;
	*shift = sft;
}

逐段拆：

  1. maxsec * from 是「最大需要转换的 cycle 数」。右移 32 位取高位，若不是 0 说明这个数超过 32 bit，需要收紧 sftacc。
  2. sftacc 是 mult 允许占用的可用位数。32 bit 以内的计数器固定给 32；超过 32 bit 的按 tmp 的可用位数递减。
  3. sft 从 32 往下穷举。第一个满足 (tmp >> sftacc) == 0 的（即 mult 的占用位不超过 sftacc）就是答案。
  4. 找到了就 break，同时拿到 mult 和 shift。

这个搜索方向决定了「精度优先」：从大往小试，第一个可行解就是能用的最大 shift。

maxsec 从哪来 #

__clocksource_update_freq_scale() 里：

c
		sec = cs->mask;
		do_div(sec, freq);
		do_div(sec, scale);
		if (!sec)
			sec = 1;
		else if (sec > 600 && cs->mask > UINT_MAX)
			sec = 600;

mask / freq 就是硬件计数器能表示的最大秒数。然后两条修正：不足 1 秒抬到 1 秒；超过 600 秒且 mask 超过 32 bit 时压到 600 秒。

600 秒这个数字是个取舍。原文讲得对：一边要精度（mult 要大 → 覆盖范围要小），一边要 cpuidle 能睡久一点（范围要大）。600 秒（10 分钟）是双方都能接受的值。5.15 的注释还给了量化结果：

text
 * a shift value of 24 for a clocksource with mask >= 40-bit and
 * f >= 4GHz. That maps to ~ 0.06ppm granularity for NTP.

maxadj：11% 的由来 #

c
static u32 clocksource_max_adjustment(struct clocksource *cs)
{
	u64 ret;
	/*
	 * We won't try to correct for more than 11% adjustments (110,000 ppm),
	 */
	ret = (u64)cs->mult * 11;
	do_div(ret, 100);
	return (u32)ret;
}

11%、即 110000 ppm。为什么是 11% 而不是 10%？原文留了个问号（「为何是 11％呢？」）。从代码能确认的只有数值本身是 11，至于当初选 11 而不是 10 的历史理由，源码注释里没有说明，本篇不做推测。

maxadj 的用途是给 NTP 调频留余量。mult 会被 NTP 上下调整以校正计数器频率误差，但调整幅度必须有界，否则 cycles * mult 溢出。算完还要验一遍：

c
	cs->maxadj = clocksource_max_adjustment(cs);
	while (freq && ((cs->mult + cs->maxadj < cs->mult)
		|| (cs->mult - cs->maxadj > cs->mult))) {
		cs->mult >>= 1;
		cs->shift--;
		cs->maxadj = clocksource_max_adjustment(cs);
	}

mult + maxadj < mult 是 u32 加法回绕的判据，mult - maxadj > mult 是减法的。命中任一说明 mult 太大，砍半、shift 减一、重算，直到不溢出。注意这个循环带 freq && 条件：走 __clocksource_register()（freq 为 0）特殊路径的时间源会跳过它，只留个 WARN_ONCE。原文提到「用户设定的 mult 已逼近最大值」，说的就是这个风险，5.x 用 WARN_ONCE 显式化了。

max_idle_ns：不溢出的睡眠上限 #

c
u64 clocks_calc_max_nsecs(u32 mult, u32 shift, u32 maxadj, u64 mask, u64 *max_cyc)
{
	u64 max_nsecs, max_cycles;

	/*
	 * 算不溢出 64 位结果的最大 cycle 数：
	 */
	max_cycles = ULLONG_MAX;
	do_div(max_cycles, mult+maxadj);

	/*
	 * 真正能推迟的上限取 max_cycles 与 mask 的较小者。
	 * 减掉 maxadj 是为了在大的负向调整下也不睡过头。
	 */
	max_cycles = min(max_cycles, mask);
	max_nsecs = clocksource_cyc2ns(max_cycles, mult - maxadj, shift);

	if (max_cyc)
		*max_cyc = max_cycles;

	/* 返回实际最大值的一半，这样能检测坏值 */
	max_nsecs >>= 1;

	return max_nsecs;
}

有几处必须点出来：

第一，maxadj 出现在两个位置，方向相反。 算 max_cycles 时用 mult + maxadj（上界，取最坏情况）；算纳秒时用 mult - maxadj（下界，防止负向调整后睡过头）。这个细节原文没展开，但它是正确性的关键。

第二，「返回 50%」不是 12.5% 的 margin。 素材原文说这里「为了安全还设定了 12.5％的 margin，之所以选择 12.5％，是因为可以通过移位而不是除法完成」。这句话在有 clocks_calc_max_nsecs() 的 5.x 上是错的：代码明写 max_nsecs >>= 1，是 50%，除以 2 确实靠移位，但不是 12.5%。

3.x 的 clocksource_max_deferment() 是否用 12.5%，(mask - (mask >> 3)) 这个算式（即 mask * 0.875）确实出现在 __clocksource_updatefreq_scale() 里，这一点原文没说错。但 5.15 的对应代码已经改成：

c
		sec = cs->mask;
		do_div(sec, freq);
		do_div(sec, scale);

直接就是 mask，那个 12.5% 的减法 5.15 已经没了。 算在附录的勘误里。

第三，max_idle_ns 名字里的 idle 是有来历的。 它限制的是 NO_HZ 下 CPU 最长能睡多久。传统 Unix 有周期性 tick（嵌入式常见 10ms），NO_HZ 去掉 tick 后，CPU 没活干就想一直睡，但 counter 会回绕、换算会溢出，所以必须有个上限。原文这段解释是准确的。

快慢两套换算 #

5.15 里 clocksource_cyc2ns() 是快路径，专门处理「已经保证不溢出」的差值。超出 max_cycles 时走慢路径：

c
static noinline u64 cycles_to_nsec_safe(struct clocksource *cs, u64 start, u64 end)
{
	u64 delta = clocksource_delta(end, start, cs->mask);

	if (likely(delta < cs->max_cycles))
		return clocksource_cyc2ns(delta, cs->mult, cs->shift);

	return mul_u64_u32_shr(delta, cs->mult, cs->shift);
}

noinline 是有意的：把慢路径踢出热路径的指令 cache。mul_u64_u32_shr() 用上 64×32→128 位的乘法指令（x86 的 mulx 之类），中间结果 128 位，不溢出。

clocksource_delta() 顺手处理回绕：

text
delta = (now - last) & mask

一句话：用 mask 把减法结果截到掩码位宽，回绕就变成了正常的正整数差。前提是两次读之间没跨过「半个回绕周期」，超过这个间隔硬件无法自证，这也是 max_idle_ns 存在的另一个理由。

七、clocksource 的读接口与快慢路径 #

「读时间」这件事在用户态看起来是一条 clock_gettime()，落到内核其实分了三条路。我们按从快到慢排。

第一层：vDSO，根本不进内核 #

x86 上主流时间源是 TSC。如果 clocksource 的 vdso_clock_mode 是 VDSO_CLOCKMODE_TSC，用户态的 clock_gettime(CLOCK_MONOTONIC) 可以直接在内核之外算完：读 TSC、套用页面里缓存的 mult/shift/offset，全程没有 syscall。clocksource_tsc.enable 里那行就是点亮它：

c
static int tsc_cs_enable(struct clocksource *cs)
{
	vclocks_set_used(VDSO_CLOCKMODE_TSC);
	return 0;
}

这条路的前提是「读数换算参数可以被用户态安全读到」，即 clocksource 必须能被 vDSO 用。vdso_clock_mode 这个字段在 3.x 还没有，素材原文自然没提。

第二层：timekeeper 缓存的热路径 #

进内核后，ktime_get() 系列走的是 timekeeper 自己缓存的那份参数，不碰 struct clocksource 本体。5.15 注释已经说得很直白（第三章引过），tkr_mono.base、tkr_mono.clock->mult、tkr_mono.cycle_last 都是 timekeeper 结构里的副本。

这带来一个设计后果：clocksource.read() 的返回值必须先和 tkr->cycle_last 做差，不能直接把绝对值交给 clocksource_cyc2ns()。第六章结尾那句「只喂差值」在这里落地。

第三层：clocksource 自己的慢路径 #

就是第六章末尾的 cycles_to_nsec_safe() 和 mul_u64_u32_shr()。只有差值超过 max_cycles 才进来。

读回调本身的代价差异 #

别以为 read() 都是同一种成本。同一个 struct clocksource 抽象下藏着天差地别的实现：

时间源 read 实现 典型代价
tsc rdtsc_ordered() 约几十个周期，lfence 序化后略高
hpet readl() 读 MMIO 计数器 微秒级，且多核并发时会被锁串行化
acpi_pm inl() 读 I/O 端口 微秒级，比 MMIO 还慢
jiffies 直接读全局变量 纳秒级，但精度只有 1/HZ

HPET 在 5.15 上的 read 有一段专门的优化，值得一看：

c
static u64 read_hpet(struct clocksource *cs)
{
	unsigned long flags;
	union hpet_lock old, new;

	/* 在 NMI 里直接读 */
	if (in_nmi())
		return (u64)hpet_readl(HPET_COUNTER);

	/* 原子读出锁状态和已缓存的计数值 */
	old.lockval = READ_ONCE(hpet.lockval);

	if (arch_spin_is_locked(&old.lock))
		goto contended;
	/* ... trylock 成功就读一次硬件并写回共享值 ... */

contended:
	/*
	 * 竞争路径：等到共享值变化或者锁释放
	 */
	do {
		cpu_relax();
		new.lockval = READ_ONCE(hpet.lockval);
	} while ((new.value == old.value) && arch_spin_is_locked(&new.lock));
	return (u64)new.value;
}

代码上方的注释解释了动机：几百个 CPU 同时读 HPET 会让整机慢到 trigger soft lockup。解法是「第一个进锁的核读硬件，其余核复用同一个值」。这是个很实在的 trade-off：牺牲一点精度换可用性。HPET 做默认时间源本来就是不得已，rating 只有 250。

精度上限 #

不管哪条路，clocksource_cyc2ns() 的右移都会丢低位。丢多少由 shift 决定，而 shift 又受 maxsec 约束。这就是原文那句「设计是平衡的艺术」的实际所指。要估个数量级可以用一个简单的近似：

text
相对误差 ~ 1 / 2^shift * mult 的舍入

精确值取决于 mult/shift 的具体组合，这里不给具体数字，避免编数据。想知道自己机器上的真实值，dmesg | grep -i clocksource 里那行 mask: 0x... max_cycles: 0x..., max_idle_ns: ... ns 是起点，mult/shift 本身要从调试器里取。

八、watchdog：怎么发现时间源走歪了 #

原文在第五章只有一行：「呵呵～～～有空再写吧。」这一章就是把它补上。这是 clocksource 里最容易讲错的部分，我们按 5.15 源码一步步来。

核心思路 #

用两个独立的时间源对表。 一个当被测对象（CLOCK_SOURCE_MUST_VERIFY 标志），一个当基准（watchdog）。每隔 0.5 秒，同时读两者的差值，比较差了多少纳秒。差太多就判被测对象走歪，降 rating 到 0，然后重新选举。

谁当基准：clocksource_select_watchdog() #

c
static void clocksource_select_watchdog(bool fallback)
{
	struct clocksource *cs, *old_wd;
	unsigned long flags;

	spin_lock_irqsave(&watchdog_lock, flags);
	old_wd = watchdog;
	if (fallback)
		watchdog = NULL;

	list_for_each_entry(cs, &clocksource_list, list) {
		/* cs is a clocksource to be watched. */
		if (cs->flags & CLOCK_SOURCE_MUST_VERIFY)
			continue;

		/* Skip current if we were requested for a fallback. */
		if (fallback && cs == old_wd)
			continue;

		/* Pick the best watchdog. */
		if (!watchdog || cs->rating > watchdog->rating)
			watchdog = cs;
	}
	if (!watchdog)
		watchdog = old_wd;

	if (watchdog != old_wd)
		clocksource_reset_watchdog();

	clocksource_start_watchdog();
	spin_unlock_irqrestore(&watchdog_lock, flags);
}

规则很清楚：基准必须是不需要被验证的（没有 MUST_VERIFY），且在候选里 rating 最高。所以 TSC 不能既是被测对象又当基准，它带 MUST_VERIFY。

谁入队列：clocksource_enqueue_watchdog() #

c
static void clocksource_enqueue_watchdog(struct clocksource *cs)
{
	INIT_LIST_HEAD(&cs->wd_list);

	if (cs->flags & CLOCK_SOURCE_MUST_VERIFY) {
		/* cs is a clocksource to be watched. */
		list_add(&cs->wd_list, &watchdog_list);
		cs->flags &= ~CLOCK_SOURCE_WATCHDOG;
	} else {
		/* cs is a watchdog. */
		if (cs->flags & CLOCK_SOURCE_IS_CONTINUOUS)
			cs->flags |= CLOCK_SOURCE_VALID_FOR_HRES;
	}
}

注意 else 分支：不需要验证的时间源，如果连续，就直接授予高精度资格，不用等 watchdog 点头。这是 TSC 之外的路径能进 hrtimer 的依据。

吃一颗定心丸：tick_stable #

判断依据从 3.x 到 5.x 有过一次重要修补。3.x 判歪之后直接降 rating，TSC 立刻被摘。但 TSC 在 CPU 热迁移、虚拟化抢占的瞬间读数会落后一点，被摘掉就再也回不来了。

5.15 的补救是交叉验证：watchdog 连续几次结果一致，就调 tick_stable 回调给一次「稳定」的确认，TSC 自己可以把状态扶正。

c
		if (cs == curr_clocksource && cs->tick_stable)
			cs->tick_stable(cs);

TSC 侧的实现：

c
static void tsc_cs_tick_stable(struct clocksource *cs)
{
	if (tsc_unstable)
		return;

	if (using_native_sched_clock())
		sched_clock_tick_stable();
}

反过来，真判歪了走 mark_unstable：

c
static void tsc_cs_mark_unstable(struct clocksource *cs)
{
	if (tsc_unstable)
		return;

	tsc_unstable = 1;
	if (using_native_sched_clock())
		clear_sched_clock_stable();
	disable_sched_clock_irqtime();
	pr_info("Marking TSC unstable due to clocksource watchdog\n");
}

这两个回调字段 mark_unstable / tick_stable 都是 3.x 没有的。

判歪的阈值 #

c
#define WATCHDOG_THRESHOLD (NSEC_PER_SEC >> 5)

NSEC_PER_SEC >> 5 就是 1e9 / 32 = 31.25 ms。这是 uncertainty_margin 未指定时的默认值。

真正判歪的条件：

c
		/* Check the deviation from the watchdog clocksource. */
		md = cs->uncertainty_margin + watchdog->uncertainty_margin;
		if (abs(cs_nsec - wd_nsec) > md) {

两侧的 margin 相加，然后比较纳秒差值。uncertainty_margin 在注册时若没填，按计数器周期算：

c
	if (scale && freq && !cs->uncertainty_margin) {
		cs->uncertainty_margin = NSEC_PER_SEC / (scale * freq);
		if (cs->uncertainty_margin < 2 * WATCHDOG_MAX_SKEW)
			cs->uncertainty_margin = 2 * WATCHDOG_MAX_SKEW;
	} else if (!cs->uncertainty_margin) {
		cs->uncertainty_margin = WATCHDOG_THRESHOLD;
	}

WATCHDOG_MAX_SKEW 是 100 * NSEC_PER_USEC，即 100 μs，是「SMIs、NMIs、vCPU 抢占」造成的干扰下界。

读数本身也得防脏 #

判歪之前得先确认「这一次读数确实是干净的」。cs_watchdog_read() 读三次基准时间源：

c
		local_irq_disable();
		*wdnow = watchdog->read(watchdog);
		*csnow = cs->read(cs);
		wd_end = watchdog->read(watchdog);
		wd_end2 = watchdog->read(watchdog);
		local_irq_enable();

判据有三条：

情况 判据 处理
干净 wd_delay <= WATCHDOG_MAX_SKEW（≤100μs） 采信这次读数
系统太忙 wd_seq_delay > WATCHDOG_MAX_SKEW / 2 跳过本轮，重置，睡 5 分钟再看
一直脏 重试超过 clocksource_get_max_watchdog_retry() 判被测对象不稳定

重试次数不是常数，跟着 CPU 数走：

c

{
	return (ilog2(num_online_cpus()) / 2) + 1;
}

「系统太忙就睡 5 分钟」那段：

c
		if (read_ret == WD_READ_SKIP) {
			clocksource_reset_watchdog();
			extra_wait = HZ * 300;
			break;
		}

300 秒。这条设计值得注意：watchdog 宁可沉默，也不能在高负载下误判。

时间间隔过长也要跳过 #

c
		interval = max(cs_nsec, wd_nsec);
		if (unlikely(interval > WATCHDOG_INTERVAL_MAX_NS)) {
			if (system_state > SYSTEM_SCHEDULING &&
			    interval > 2 * watchdog_max_interval) {
				watchdog_max_interval = interval;
				pr_warn("Long readout interval, skipping watchdog check: cs_nsec: %lld wd_nsec: %lld\n",
					cs_nsec, wd_nsec);
			}
			watchdog_timer.expires = jiffies;
			continue;
		}

WATCHDOG_INTERVAL 是 HZ >> 1（0.5 秒），WATCHDOG_INTERVAL_MAX_NS 是它的两倍对应纳秒。timer softirq 被 ksoftirqd 拖延时，间隔会拉长，此时固定的 margin 就不适用了。注释里点了名：acpi_pm 这类时间源经不起间隔太长。

被判歪之后的连锁反应 #

c
static void __clocksource_unstable(struct clocksource *cs)
{
	cs->flags &= ~(CLOCK_SOURCE_VALID_FOR_HRES | CLOCK_SOURCE_WATCHDOG);
	cs->flags |= CLOCK_SOURCE_UNSTABLE;

	if (list_empty(&cs->list)) {
		cs->rating = 0;
		return;
	}

然后内核线程把 rating 清零并触发重选：

c

			if (cs->flags & CLOCK_SOURCE_UNSTABLE) {
				list_del_init(&cs->wd_list);
				__clocksource_change_rating(cs, 0);
				select = 1;
			}
			...

rating 归零，不是减一点。归零之后就彻底出局，留在链表里只是供参考。

为什么要绕一圈用 kthread 而不是直接在 timer 里做？clocksource_select() 会调 timekeeping_notify()，后者用 stop_machine()。在 workqueue 里用 stop_machine() 会跟 CPU hotplug 形成锁序倒置。所以 5.15 的做法是 kthread_run() 起一个临时线程：

c
static void clocksource_watchdog_work(struct work_struct *work)
{
	/*
	 * We cannot directly run clocksource_watchdog_kthread() here, because
	 * clocksource_select() calls timekeeping_notify() which uses
	 * stop_machine(). One cannot use stop_machine() from a workqueue() due
	 * lock inversions wrt CPU hotplug.
	 */
	kthread_run(clocksource_watchdog_kthread, NULL, "kwatchdog");
}

谁来喂狗 #

两条：

  • 系统挂起/恢复后 clocksource_resume() 会调 clocksource_resume_watchdog()，把 watchdog_reset_pending 加一，表示「时基变了，下一轮重新取样」。
  • kgdb 之类的外部停顿后，clocksource_touch_watchdog() 也走同一条路。

什么情况下干脆不装 watchdog #

TSC 在满足一堆条件时会把 MUST_VERIFY 摘掉，watchdog 对它就不再工作了：

c
	if (boot_cpu_has(X86_FEATURE_CONSTANT_TSC) &&
	    boot_cpu_has(X86_FEATURE_NONSTOP_TSC) &&
	    boot_cpu_has(X86_FEATURE_TSC_ADJUST) &&
	    nr_online_nodes <= 2)
		tsc_disable_clocksource_watchdog();

四个条件：频率恒定、C-state 不停、有 TSC_ADJUST 寄存器、节点数不超过 2。理由见注释：前三条保证 TSC 本身可靠，节点数限制是拿内存节点数近似「插槽数不超过 2」，因为启动早期数不出插槽数。

tsc=nowatchdog 启动参数也能强制关掉（no_tsc_watchdog）。

九、jiffies 与 clocksource 的关系 #

jiffies 在 clocksource 体系里的位置很特殊：它是时间源，也是所有时间源的兜底。

看定义：

c

	.name			= "jiffies",
	.rating			= 1, /* lowest valid rating*/
	.uncertainty_margin	= 32 * NSEC_PER_MSEC,
	.read			= jiffies_read,
	.mask			= CLOCKSOURCE_MASK(32),
	.mult			= TICK_NSEC << JIFFIES_SHIFT,
	.shift			= JIFFIES_SHIFT,
	.max_cycles		= 10,
};

几个要点：

rating = 1，注释写明 lowest valid rating。它是「在所有系统上都能工作」的最小公分母。

read 就是读一个全局变量，代价近乎为零，但精度就是 1/HZ。

mult 和 shift 是编译期写死的，不走 clocks_calc_mult_shift()。TICK_NSEC 是每个 tick 的纳秒数（1e9/HZ），左移 JIFFIES_SHIFT 位就是放大后的乘数。这也是它敢用 __clocksource_register()（freq 传 0）特殊路径的原因。

max_cycles = 10，很小。对应 mask 只有 32 bit 且精度极粗，10 个 tick 之后就超出安全换算范围。

源码注释对它的缺点毫不客气：

text
 * The Jiffies based clocksource is the lowest common
 * denominator clock source which should function on
 * all systems. It has the same coarse resolution as
 * the timer interrupt frequency HZ and it suffers
 * inaccuracies caused by missed or lost timer
 * interrupts and the inability for the timer
 * interrupt hardware to accurately tick at the
 * requested HZ value. It is also not recommended
 * for "tick-less" systems.

「不推荐给 tickless 系统」，这句话是重点。NO_HZ 下没有周期性 tick，jiffies 的推进本身就依赖 tick 或别的机制，拿它做时间源是恶性循环。

它什么时候真的被用上 #

两条路：

其一，启动早期。 clocksource_done_booting() 里有一句：

c
static int __init clocksource_done_booting(void)
{
	mutex_lock(&clocksource_mutex);
	curr_clocksource = clocksource_default_clock();
	finished_booting = 1;
	/* 先跑 watchdog 把不稳定的时间源剔掉 */
	__clocksource_watchdog_kthread();
	clocksource_select();
	mutex_unlock(&clocksource_mutex);
	return 0;
}
fs_initcall(clocksource_done_booting);

clocksource_default_clock() 的弱符号定义就是返回 &clocksource_jiffies。同时把 finished_booting 置 1，这就是原文说的「等尘埃落定再选举」的开关。

其二，真没有别的时间源。 嵌入式板子上没有 TSC、没有 HPET、没有 PM Timer 时，只有它。

refined-jiffies #

register_refined_jiffies() 会基于一个外部已知频率的计数器（比如 PIT 的标定结果）算出更准的每 tick 纳秒数，注册一个 refined-jiffies，rating 比 jiffies 大 1：

c
	refined_jiffies = clocksource_jiffies;
	refined_jiffies.name = "refined-jiffies";
	refined_jiffies.rating++;

只大 1，够用了，因为它俩是同一个东西的两种精度。这个「只加 1 而不跳到 100」的做法，正是 rating inflation 那句警告的正面教材。

sched_clock 那条旁路 #

差点忘了提：sched_clock 不吃 clocksource。x86 上 native_sched_clock() 直接用 rdtsc 加自己的一套 cyc2ns，绕开了 clocksource 抽象：

c
u64 native_sched_clock(void)
{
	if (static_branch_likely(&__use_tsc)) {
		u64 tsc_now = rdtsc();
		return cycles_2_ns(tsc_now);
	}
	/* 没有 TSC 时退回 jiffies 基准 */
	return (jiffies_64 - INITIAL_JIFFIES) * (1000000000 / HZ);
}

注释解释了原因：调度器时钟容忍小误差，但对速度的要求优先于精度，所以 TSC 被判不稳定时它仍然用 TSC，只有完全没 TSC 才退回 jiffies。这个设计取舍值得记住：「时间准」和「时间快」是两个不同的需求，内核用两套代码分别满足。

十、clockevent 要解决什么问题 #

从此章起进入 clockevent。先重申一遍对偶关系，这次从需求侧说。

内核需要「在未来某个时刻被打断」的场景，是下面这一串：

需求 谁在用 特征
周期性 tick 传统调度器、jiffies 推进 固定间隔，频率由 HZ 定
高精度定时器 hrtimer、nanosleep() 单次，精确到纳秒
动态 tick NO_HZ_IDLE / NO_HZ_FULL 单次，间隔可变，可以很久
超时检测 TCP retransmit、poll() 单次，间隔不定
广播唤醒 深 C-state 的 CPU 由另一个设备代打

这些需求的共同点只有一个：都需要硬件在将来某个时刻产生中断。这就是 clockevent 抽象的边界。

和 clocksource 的关系，一句话说透 #

时钟硬件上是一组东西：一个自由运行的计数器，加上若干个比较器。计数器供 clocksource 读，比较器供 clockevent 设。同一个计数器同时服务两边，这不是巧合，是设计上的必然：比较器的匹配值是拿计数器的刻度来写的，两者必须是同一个时基，否则「再过 1000 个 tick 叫我」这个约定就无从谈起。

clocksource_cyc2ns(cycles, mult, shift) 和 clockevents 从纳秒算 tick 的公式，共享同一套定点原理:

text
clocksource: nsec = (cycles * mult) >> shift      /* from=频率, to=1e9 */
clockevent:  latch = (nsec * mult) >> shift       /* from=1e9, to=频率 */

换算方向相反，所以 mult 的算法方向也相反。clocks_calc_mult_shift() 的注释把这件事写明了：

text
 * @to and @from are frequency values in HZ. For clock sources @to is
 * NSEC_PER_SEC == 1GHz and @from is the counter frequency. For clock
 * event @to is the counter frequency and @from is NSEC_PER_SEC.

一个函数，两套用法，参数对调。这是这一对抽象共享的最核心的代码。

逐个过，按功能分四组。

第一组：事件编程 #

字段 含义 谁写

注意 mult/shift 的方向与 clocksource 相反（第六章说过）。这里 from 是 1e9，to 是设备频率。

state_use_accessors 这个名字本身就是警告：字段名带 use_accessors，就是告诉你别裸读。5.15 提供了五个 helper：

static inline bool clockevent_state_detached(struct clock_event_device *dev)
{
	return dev->state_use_accessors == CLOCK_EVT_STATE_DETACHED;
}

配套的状态枚举与状态机：

c

	CLOCK_EVT_STATE_DETACHED,

features 的位定义与含义：

宏 值 含义
CLOCK_EVT_FEAT_PERIODIC 0x000001 支持周期模式

第三组：广播与电源 #

字段 含义

字段 含义 5.x 变化

irq 中断号（非 CPU 本地设备才有意义） 保留
bound_on 绑定在哪个 CPU 上（hrtimer 广播用） 保留

____cacheline_aligned 这个属性在 5.15 仍然保留，和 struct clocksource 不同（第三章说过）。

十二、clockevent 的两种工作模式：periodic 与 oneshot #

这是 clockevent 最重要的一个分叉。两套模式在硬件编程、中断语义、上层用途上全不一样。

维度 periodic 模式 oneshot 模式
硬件配置 一次性写入周期值，硬件自动重装 每次触发后必须重设
中断频率 固定，由 HZ 决定 可变，取决于上层下一个 deadline
内核干预 几乎不需要 每次事件都要进一次编程路径
时间精度 1/HZ 到硬件分辨率
支持者 几乎所有 timer 现代 timer
省电 差，空闲也在响 好，能配合 NO_HZ 停掉
上层用户 传统 tick、jiffies hrtimer、NO_HZ、高精度定时
状态 CLOCK_EVT_STATE_PERIODIC CLOCK_EVT_STATE_ONESHOT

periodic 怎么下去 #

HPET 的实现最典型，一眼能看懂硬件在干什么：

c
static int hpet_clkevt_set_state_periodic(struct clock_event_device *evt)
{
	unsigned int channel = clockevent_to_channel(evt)->num;
	unsigned int cfg, cmp, now;
	uint64_t delta;

	hpet_stop_counter();
	delta = ((uint64_t)(NSEC_PER_SEC / HZ)) * evt->mult;
	delta >>= evt->shift;
	now = hpet_readl(HPET_COUNTER);
	cmp = now + (unsigned int)delta;
	cfg = hpet_readl(HPET_Tn_CFG(channel));
	cfg |= HPET_TN_ENABLE | HPET_TN_PERIODIC | HPET_TN_SETVAL |
	       HPET_TN_32BIT;
	hpet_writel(cfg, HPET_Tn_CFG(channel));
	hpet_writel(cmp, HPET_Tn_CMP(channel));
	udelay(1);
	/*
	 * AMD 81xx 需要第二次写（清掉 SETVAL）才设得上周期
	 */
	hpet_writel((unsigned int)delta, HPET_Tn_CMP(channel));
	hpet_start_counter();

	return 0;
}

三行关键：

  1. delta = ((1e9 / HZ) * mult) >> shift —— 纳秒换 tick，就是第六章那个公式反过来用。
  2. cmp = now + delta —— 比较器基准点选在当前计数上。
  3. 置 HPET_TN_PERIODIC —— 硬件之后自动重装。

注意那个 udelay(1) 和二次写入。代码注释点了名是 AMD 8111 的 bug：SETVAL 位第一次写会自动清，必须再写一次周期值。这类「硬件 quirk」在 timer 驱动里遍地都是，是理解 clockevent 驱动代码时最容易卡住的地方。

oneshot 怎么下去 #

切到 oneshot 只是改配置，真正的编程在 set_next_event：

c
static int hpet_clkevt_set_state_oneshot(struct clock_event_device *evt)
{
	unsigned int channel = clockevent_to_channel(evt)->num;
	unsigned int cfg;

	cfg = hpet_readl(HPET_Tn_CFG(channel));
	cfg &= ~HPET_TN_PERIODIC;
	cfg |= HPET_TN_ENABLE | HPET_TN_32BIT;
	hpet_writel(cfg, HPET_Tn_CFG(channel));

	return 0;
}

只清 PERIODIC 位，不写比较值。 比较值留给 set_next_event 每次单独设。

谁决定用哪种 #

答案在 tick 层，不在 clockevent 层。__clocksource_select() 里那句：

c
	bool oneshot = tick_oneshot_mode_active();

clockevents 只负责「能不能」，tick 层负责「要不要」。决定「要不要」的因素是 CONFIG_NO_HZ_IDLE、CONFIG_HIGH_RES_TIMERS、nohz= 启动参数以及运行时 tick_nohz_enabled。

从 periodic 切到 oneshot 的时机 #

oneshot 一旦被使能，全局都会切，包括广播设备（第十六章）。切的过程在广播代码里有个专门函数 tick_broadcast_switch_to_oneshot()。切的时候要保证「还在等 periodic tick 的 CPU 能在下一个 tick 被唤醒」，否则那些 CPU 会一直睡死过去。这段逻辑在 tick_broadcast_setup_oneshot() 里，用 tick_broadcast_mask 和 tick_broadcast_oneshot_mask 两个 cpumask 做交接。

ONESHOT_STOPPED 的用途 #

第三个状态 ONESHOT_STOPPED 容易漏。它的场景是：省电。单次模式下你已经知道下一个 deadline 在很远的将来，把 timer 临时关掉（不是硬件 shutdown，是真的停表），等到要用了再切回 ONESHOT。

local APIC 的实现直接把 stopped 映射到 shutdown：

c
static struct clock_event_device lapic_clockevent = {
	...
	.set_state_oneshot_stopped	= lapic_timer_shutdown,
	...
};

HPET 没设这个回调，所以对 HPET 来说 ONESHOT_STOPPED 会返回 -ENOSYS：

c
	case CLOCK_EVT_STATE_ONESHOT_STOPPED:
		/* Core internal bug */
		if (WARN_ONCE(!clockevent_state_oneshot(dev),
			      "Current state: %d\n",
			      clockevent_get_state(dev)))
			return -EINVAL;

		if (dev->set_state_oneshot_stopped)
			return dev->set_state_oneshot_stopped(dev);
		else
			return -ENOSYS;

WARN_ONCE 那句「Core internal bug」透露了语义：只能从 ONESHOT 进 STOPPED，从别的状态进来是内核自己的错。

十三、event_handler：到点之后做什么 #

中断响了，硬件里的路径是这么走的：

text
timer IRQ
  -> 驱动的中断处理函数
    -> evt->event_handler(evt)
      -> tick 层 / hrtimer 层

event_handler 这个函数指针不是驱动填的，是 clockevents core 和 tick 层填的。头文件的注释就是这么写的：

text
 * @event_handler:	Assigned by the framework to be called by the low
 *			level handler of the event source

驱动的责任只有一条：中断来了，调它。HPET 的 MSI 中断处理是个干净的范例：

c
static irqreturn_t hpet_msi_interrupt_handler(int irq, void *data)
{
	struct hpet_channel *hc = data;
	struct clock_event_device *evt = &hc->evt;

	if (!evt->event_handler) {
		pr_info("Spurious interrupt HPET channel %d\n", hc->num);
		return IRQ_HANDLED;
	}

	evt->event_handler(evt);
	return IRQ_HANDLED;
}

先判空。event_handler 为空说明这是个 spurious 中断，直接吞掉。

handler 都有谁 #

不同场景挂不同的函数：

handler 挂在什么状态 干什么
tick_handle_periodic periodic，本地设备 推进 jiffies，跑 timer wheel
tick_handle_periodic_broadcast periodic，但走广播 上面那件事，外加给别的 CPU 发包
tick_handle_oneshot_broadcast oneshot 广播设备 扫描各 CPU 的 deadline，给到期的发包
tick_oneshot_wakeup_handler oneshot wakeup 设备 只做 tick_receive_broadcast()
clockevents_handle_noop 被替换下来的旧设备 什么都不做

clockevents_handle_noop 的实现真的什么都没有：

c
void clockevents_handle_noop(struct clock_event_device *dev)
{
}

它是「占位用的哑函数」，作用是把一个还在被硬件驱动着的设备的中断安全地吸收掉。

收广播的那一侧 #

一个 CPU 收到别人发来的广播 IPI 后，走的是 tick_receive_broadcast()：

c
int tick_receive_broadcast(void)
{
	struct tick_device *td = this_cpu_ptr(&tick_cpu_device);
	struct clock_event_device *evt = td->evtdev;

	if (!evt)
		return -ENODEV;

	if (!evt->event_handler)
		return -EINVAL;

	evt->event_handler(evt);
	return 0;
}

它不自己处理，而是借用本 CPU 的 event_handler。这是广播机制的关键设计：接收方的「到点了该怎么办」逻辑完全不变，只是触发源从自己的 timer 换成了别人的 IPI。第十六章会再回到这里。

一个容易看迷糊的地方 #

tick_handle_periodic_broadcast 里面同时做了两件事：给别的 CPU 发包，以及（在设备是 oneshot 时）给自己重新编程：

c
static void tick_handle_periodic_broadcast(struct clock_event_device *dev)
{
	...
	bc_local = tick_do_periodic_broadcast();

	if (clockevent_state_oneshot(dev)) {
		ktime_t next = ktime_add_ns(dev->next_event, TICK_NSEC);

		clockevents_program_event(dev, next, true);
	}
	...
}

clockevents_program_event(dev, next, true) 的第三个参数 force=true，意思是「即使 deadline 已经过去了，也照设不误，设成最小间隔」。这在广播场景下是必要的：广播设备是共享的，不能因为一次迟到就放弃。

十四、clockevent 的注册与 rating 选择 #

注册的两种方式 #

方式一：注册现成设备。

c
void clockevents_register_device(struct clock_event_device *dev)
{
	unsigned long flags;

	/* Initialize state to DETACHED */
	clockevent_set_state(dev, CLOCK_EVT_STATE_DETACHED);

	if (!dev->cpumask) {
		WARN_ON(num_possible_cpus() > 1);
		dev->cpumask = cpumask_of(smp_processor_id());
	}

	if (dev->cpumask == cpu_all_mask) {
		WARN(1, "%s cpumask == cpu_all_mask, using cpu_possible_mask instead\n",
		     dev->name);
		dev->cpumask = cpu_possible_mask;
	}

	raw_spin_lock_irqsave(&clockevents_lock, flags);

	list_add(&dev->list, &clockevent_devices);
	tick_check_new_device(dev);
	clockevents_notify_released();

	raw_spin_unlock_irqrestore(&clockevents_lock, flags);
}

三件事必须记住：状态强制设为 DETACHED、cpumask 必须非空（NULL 且 SMP 会 WARN_ON）、不能是 cpu_all_mask（会被改成 cpu_possible_mask 并告警）。

方式二：带频率一起注册（推荐）。

c
void clockevents_config_and_register(struct clock_event_device *dev,
				     u32 freq, unsigned long min_delta,
				     unsigned long max_delta)
{
	dev->min_delta_ticks = min_delta;
	dev->max_delta_ticks = max_delta;
	clockevents_config(dev, freq);
	clockevents_register_device(dev);
}

clockevents_config() 才是算 mult/shift 的地方：

c
static void clockevents_config(struct clock_event_device *dev, u32 freq)
{
	u64 sec;

	if (!(dev->features & CLOCK_EVT_FEAT_ONESHOT))
		return;

	/*
	 * 算最长能睡多少秒，超过 32bit tick 的硬件压到 10 分钟
	 */
	sec = dev->max_delta_ticks;
	do_div(sec, freq);
	if (!sec)
		sec = 1;
	else if (sec > 600 && dev->max_delta_ticks > UINT_MAX)
		sec = 600;

	clockevents_calc_mult_shift(dev, freq, sec);
	dev->min_delta_ns = cev_delta2ns(dev->min_delta_ticks, dev, false);
	dev->max_delta_ns = cev_delta2ns(dev->max_delta_ticks, dev, true);
}

只有 oneshot 设备才算。 !CLOCK_EVT_FEAT_ONESHOT 直接返回，因为 periodic 模式不需要纳秒换算。还有那个熟悉的 600 秒上限，和 clocksource 那边一模一样，来自同一个设计权衡。

clockevents_calc_mult_shift() 就是参数对调的那次调用：

c
static inline void
clockevents_calc_mult_shift(struct clock_event_device *ce, u32 freq, u32 maxsec)
{
	return clocks_calc_mult_shift(&ce->mult, &ce->shift, NSEC_PER_SEC, freq, maxsec);
}

rating 的实际取值 #

clockevent 的 rating 和 clocksource 完全独立。5.15 源码里的实际值：

设备 定义位置 rating 备注
hpet1…hpetN（每 CPU MSI 通道） arch/x86/kernel/hpet.c 110 hpet_init_clockevent(hc, 110)
lapic / lapic-deadline arch/x86/kernel/apic/apic.c 100 基础值
lapic（有 ARAT） 同上 150 setup_APIC_timer() 里提上去的
hpet（legacy 全局通道） arch/x86/kernel/hpet.c 50 hpet_init_clockevent(hc, 50)

ARAT 那个上调带一行注释，说得很直白：

c
	if (this_cpu_has(X86_FEATURE_ARAT)) {
		lapic_clockevent.features &= ~CLOCK_EVT_FEAT_C3STOP;
		/* Make LAPIC timer preferable over percpu HPET */
		lapic_clockevent.rating = 150;
	}

两件事一起做：摘掉 C3STOP（ARAT 保证 C-state 下不停），rating 提到 150（高于每 CPU HPET 的 110）。这就把「优先用本地的、别用共享的」写成了显式规则。

选择逻辑 #

tick_check_new_device() 是入口，但具体比较逻辑散在两处：

每 CPU 设备的选择在 tick 层，比较 rating，胜者通过 clockevents_exchange_device() 换上去：

c
void __clockevents_exchange_device(struct clock_event_device *old,
				   struct clock_event_device *new)
{
	/*
	 * Caller releases a clock event device. We queue it into the
	 * released list and do a notify add later.
	 */
	if (old) {
		clockevents_switch_state(old, CLOCK_EVT_STATE_DETACHED);
		list_move(&old->list, &clockevents_released);
	}

	if (new) {
		WARN_ON(!clockevent_state_detached(new));
		clockevents_shutdown(new);
	}
}

注意「旧设备进 clockevents_released 而不是直接摘掉」，等通知链跑完再处理，避免在回调中间改链表。

广播设备的选择在 tick_check_broadcast_device()，除了 rating，还有一堆 feature 门槛：

c
static bool tick_check_broadcast_device(struct clock_event_device *curdev,
					struct clock_event_device *newdev)
{
	if ((newdev->features & CLOCK_EVT_FEAT_DUMMY) ||
	    (newdev->features & CLOCK_EVT_FEAT_PERCPU) ||
	    (newdev->features & CLOCK_EVT_FEAT_C3STOP))
		return false;

	if (tick_broadcast_device.mode == TICKDEV_MODE_ONESHOT &&
	    !(newdev->features & CLOCK_EVT_FEAT_ONESHOT))
		return false;

	return !curdev || newdev->rating > curdev->rating;
}

翻译成中文：不能是占位设备、不能是每 CPU 设备、自己不能有 C3STOP（否则自己都会停，怎么给别人打铃）、oneshot 模式下必须支持 oneshot。全过了才比 rating。

注销 #

clockevents_unbind_device() 走 smp_call_function_single() 到目标 CPU 上执行，因为每 CPU 设备的状态只能在它自己的 CPU 上动：

c
int clockevents_unbind_device(struct clock_event_device *ced, int cpu)
{
	int ret;

	mutex_lock(&clockevents_mutex);
	ret = clockevents_unbind(ced, cpu);
	mutex_unlock(&clockevents_mutex);
	return ret;
}

如果目标设备正在被用，clockevents_replace() 会找一个替补顶上，找不到就返回 -EBUSY。

十五、set_next_event 与硬件编程 #

契约 #

c
int (*set_next_event)(unsigned long evt, struct clock_event_device *);

evt 是相对当前时刻的 tick 数，不是绝对值。返回 0 表示设成功，返回非 0（基本是 -ETIME）表示「这个时间点已经过去了，设不上」。

为什么是相对值而不是绝对值？ 因为硬件比较器多数是「计数器 + 偏移」或「倒计数器」形态。绝对值的方案需要硬件有一个和计数器同宽的比较寄存器，而相对值只需要一个能加到当前计数的偏移。HPET 和 APIC 都吃相对值。

谁来调用它 #

只会是 clockevents_program_event() 或 clockevents_program_min_delta()。 驱动不该自己调，也不该在别处写比较寄存器。

clockevents_program_event() 是主角：

c
int clockevents_program_event(struct clock_event_device *dev, ktime_t expires,
			      bool force)
{
	unsigned long long clc;
	int64_t delta;
	int rc;

	if (WARN_ON_ONCE(expires < 0))
		return -ETIME;

	dev->next_event = expires;

	if (clockevent_state_shutdown(dev))
		return 0;

	/* We must be in ONESHOT state here */
	WARN_ONCE(!clockevent_state_oneshot(dev), "Current state: %d\n",
		  clockevent_get_state(dev));

	/* 能直接吃 ktime 的设备走捷径 */
	if (dev->features & CLOCK_EVT_FEAT_KTIME)
		return dev->set_next_ktime(expires, dev);

	delta = ktime_to_ns(ktime_sub(expires, ktime_get()));
	if (delta <= 0)
		return force ? clockevents_program_min_delta(dev) : -ETIME;

	delta = min(delta, (int64_t) dev->max_delta_ns);
	delta = max(delta, (int64_t) dev->min_delta_ns);

	clc = ((unsigned long long) delta * dev->mult) >> dev->shift;
	rc = dev->set_next_event((unsigned long) clc, dev);

	return (rc && force) ? clockevents_program_min_delta(dev) : rc;
}

几步关键：

  1. dev->next_event = expires —— 先记账再编程，即使后面失败了，上层查 next_event 也是对的。
  2. delta <= 0 说明已经迟到。force=false 返回 -ETIME，force=true 强制设最小间隔。
  3. 夹在 [min_delta_ns, max_delta_ns] 之间，防硬件上下溢。
  4. clc = (delta * mult) >> shift —— 纳秒换 tick，和 clocksource 公式反向。
  5. 硬件返回错误且 force=true，退到最小值再试。

clockevents_program_min_delta() 是兜底循环：

c
	for (i = 0;;) {
		delta = dev->min_delta_ns;
		dev->next_event = ktime_add_ns(ktime_get(), delta);

		if (clockevent_state_shutdown(dev))
			return 0;

		dev->retries++;
		clc = ((unsigned long long) delta * dev->mult) >> dev->shift;
		if (dev->set_next_event((unsigned long) clc, dev) == 0)
			return 0;

		if (++i > 2) {
			/*
			 * 用当前 min_delta_ns 试了 3 次还是不行，
			 * 就抬高 min_delta_ns 再试
			 */
			if (clockevents_increase_min_delta(dev))
				return -ETIME;
			i = 0;
		}
	}

clockevents_increase_min_delta() 的策略是「先抬到 5000ns，之后每次乘 1.5」，上限是一个 jiffy：

c
	if (dev->min_delta_ns < 5000)
		dev->min_delta_ns = 5000;
	else
		dev->min_delta_ns += dev->min_delta_ns >> 1;

	if (dev->min_delta_ns > MIN_DELTA_LIMIT)
		dev->min_delta_ns = MIN_DELTA_LIMIT;

MIN_DELTA_LIMIT 是 NSEC_PER_SEC / HZ。抬到一整个 jiffy 还失败，就打 "CE: Reprogramming failure. Giving up"，把 next_event 设成 KTIME_MAX，表示放弃这个设备。

两个真实实现 #

local APIC，TMICT 相对模式：

c
static int lapic_next_event(unsigned long delta,
			    struct clock_event_device *evt)
{
	apic_write(APIC_TMICT, delta);
	return 0;
}

就一行。APIC_TMICT 是倒计数器，写入就开跑，减到 0 触发中断。永远返回 0，因为它没有「设不上」的概念。

local APIC，TSC deadline 模式：

c
static int lapic_next_deadline(unsigned long delta,
			       struct clock_event_device *evt)
{
	u64 tsc;

	/* This MSR is special and need a special fence: */
	weak_wrmsr_fence();

	tsc = rdtsc();
	wrmsrl(MSR_IA32_TSC_DEADLINE, tsc + (((u64) delta) * TSC_DIVISOR));
	return 0;
}

这里就是绝对值了：读当前 TSC，加上换算后的偏移，写 MSR。那句 weak_wrmsr_fence() 是必须的，Intel SDM 明确说这个 MSR 的写入需要序化。

TSC_DIVISOR 是 8，因为 TSC deadline 的频率是 tsc_khz * (1000 / TSC_DIVISOR)，注册时这么传：

c
		clockevents_config_and_register(levt,
						tsc_khz * (1000 / TSC_DIVISOR),
						0xF, ~0UL);

min_delta = 0xF、max_delta = ~0UL，都是 tick 数。

HPET，最麻烦的一个：

c
static int
hpet_clkevt_set_next_event(unsigned long delta, struct clock_event_device *evt)
{
	unsigned int channel = clockevent_to_channel(evt)->num;
	u32 cnt;
	s32 res;

	cnt = hpet_readl(HPET_COUNTER);
	cnt += (u32) delta;
	hpet_writel(cnt, HPET_Tn_CMP(channel));

	/*
	 * 判 ETIME 的依据：写完之后计数器离事件太近，或者已经越过
	 */
	res = (s32)(cnt - hpet_readl(HPET_COUNTER));

	return res < HPET_MIN_CYCLES ? -ETIME : 0;
}

代码上方的长注释解释了为什么要在写完比较值之后再读一次计数器，而不是回读比较寄存器：某些芯片组（ATI、ICH9/10）对比较寄存器的写入有最多两个 HPET 时钟周期的延迟，回读会读到旧值。改成「写完立刻看计数器还差多少」就绕过了这个问题。

HPET_MIN_CYCLES 是 128，而 core 侧的最小编程间隔被设成 HPET_MIN_PROG_DELTA = HPET_MIN_CYCLES + (HPET_MIN_CYCLES >> 1)，即 192 个 cycle（1.5 倍余量）。

这是 clockevent 驱动里最值得学的一段：它示范了「硬件有 quirk 时，判定条件该怎么设计才稳」。

set_next_ktime #

CLOCK_EVT_FEAT_KTIME 这个 feature 意味着设备能直接接受绝对 ktime，跳过「减当前时间 → 算 delta」两步。x86 上没有主流设备用它（TSC deadline 虽然用绝对值，但注册时没置这个 feature，走的是 set_next_event 加 TSC_DIVISOR 换算）。这个 feature 在 ARM 的一些 timer 驱动上更常见。

中断号的意义 #

dev->irq 只对非 CPU 本地设备有意义。local APIC timer 的 irq 填的是 -1：

c
static struct clock_event_device lapic_clockevent = {
	...
	.irq				= -1,
};

HPET 每 CPU 通道填的是 MSI 分配到的真实中断号，这样 tick_broadcast_set_affinity() 才能调 irq_set_affinity()。

十六、clockevent 的广播：单核定时器怎么服务多核 #

这一章是 clockevent 里最绕的部分，也是 CLOCK_EVT_FEAT_C3STOP 存在的全部理由。

问题 #

x86 的 local APIC timer 在 CPU 进 C3（甚至更深）时会停摆。CPU 睡下了，timer 也停了，本来该在 10ms 后叫醒它的事件根本不会发生。而 CPU 这时候已经在 C3 里，自己醒不过来。

单个 CPU 修不了这个问题，因为能救它的硬件恰好是它自己身上那个停了的 timer。

解法 #

找一个在低功耗状态下仍然运行的设备，让它代打。 默认是 HPET，或者 LAPIC 的 broadcast 通道，或者最后兜底的 hrtimer。

这个设备就叫广播设备（broadcast device），在 tick 层有一个独立的结构：

c
static struct tick_device tick_broadcast_device;
static cpumask_var_t tick_broadcast_mask __cpumask_var_read_mostly;
static cpumask_var_t tick_broadcast_on __cpumask_var_read_mostly;

tick_broadcast_mask 是当前需要被代打的 CPU 集合。进 C3 前把自己加进去，出来后摘掉。

广播设备本身是怎么选出来的 #

三个 feature 门槛（第十四章引过 tick_check_broadcast_device()）：不能 DUMMY、不能 PERCPU、自己不能 C3STOP。

x86 上的实际候选：

设备 能不能当广播设备 原因
local APIC timer 不能 带 C3STOP
HPET channel 0（legacy） 能 rating 50，全局共享
HPET 每 CPU MSI 通道 不能 带 PERCPU
hrtimer 广播（无硬件时） 能（兜底） 带 HRTIMER

最后一行的意思是：如果硬件全都不合格，内核用 hrtimer 软件模拟一个广播设备。这在虚拟机和某些裁剪平台上很常见。

怎么代打 #

广播设备是一个，被唤醒的 CPU 会很多。所以它每次到期都要扫描一遍：

c
static void tick_handle_oneshot_broadcast(struct clock_event_device *dev)
{
	struct tick_device *td;
	ktime_t now, next_event;
	int cpu, next_cpu = 0;
	bool bc_local;

	raw_spin_lock(&tick_broadcast_lock);
	dev->next_event = KTIME_MAX;
	next_event = KTIME_MAX;
	cpumask_clear(tmpmask);
	now = ktime_get();
	/* 找出所有已到期的 CPU */
	for_each_cpu(cpu, tick_broadcast_oneshot_mask) {
		td = &per_cpu(tick_cpu_device, cpu);
		if (td->evtdev->next_event <= now) {
			cpumask_set_cpu(cpu, tmpmask);
			cpumask_set_cpu(cpu, tick_broadcast_pending_mask);
		} else if (td->evtdev->next_event < next_event) {
			next_event = td->evtdev->next_event;
			next_cpu = cpu;
		}
	}

	cpumask_clear_cpu(smp_processor_id(), tick_broadcast_pending_mask);

	/* 处理强制广播请求 */
	cpumask_or(tmpmask, tmpmask, tick_broadcast_force_mask);
	cpumask_clear(tick_broadcast_force_mask);

	/* 唤醒所有已到期的 CPU */
	bc_local = tick_do_broadcast(tmpmask);

	/*
	 * 需要重新编程的两种情形：
	 * - 本轮没有 CPU 到期（dyntick 下 PIT 的最大 delta 很小）
	 * - 还有睡着的 CPU 有更晚的 pending 事件
	 */
	if (next_event != KTIME_MAX)
		tick_broadcast_set_event(dev, next_cpu, next_event);

	raw_spin_unlock(&tick_broadcast_lock);

	if (bc_local) {
		td = this_cpu_ptr(&tick_cpu_device);
		td->evtdev->event_handler(td->evtdev);
	}
}

逻辑拆开：

  1. 遍历 tick_broadcast_oneshot_mask，把 next_event <= now 的 CPU 收进 tmpmask。
  2. 顺便记下最近的未来 deadline和它属于哪个 CPU。
  3. 用 tick_do_broadcast(tmpmask) 给这些 CPU 发 IPI。
  4. 如果有下一个 deadline，就把它设给广播设备（tick_broadcast_set_event 会顺便切 affinity）。
  5. 如果自己也在这个集合里，在锁外跑自己的 handler（避免死锁）。

第 5 步的 bc_local 判断在 tick_do_broadcast() 里，还有一段注释解释为什么 hrtimer 模拟的设备要特殊处理：

text
		/*
		 * We only run the local handler, if the broadcast
		 * device is not hrtimer based. Otherwise we run into
		 * a hrtimer recursion.
		 */

递归链条注释里画了出来：local timer_interrupt() → local_handler() → expire_hrtimers() → bc_handler() → local_handler() → expire_hrtimers()。hrtimer 模拟的广播设备本身就活在 hrtimer 里，再回调本 CPU 的 handler 就成了死循环。

怎么发包 #

发包靠 broadcast 回调。local APIC 的实现就是发一个 IPI：

c
static void lapic_timer_broadcast(const struct cpumask *mask)
{
#ifdef CONFIG_SMP
	apic->send_IPI_mask(mask, LOCAL_TIMER_VECTOR);
#endif
}

所以广播在 x86 上的实际效果是：HPET/其他设备到点 → 中断进到某个 CPU → 该 CPU 用 IPI 把 LOCAL_TIMER_VECTOR 打给其余需要唤醒的核 → 那些核的中断处理函数调自己的 event_handler。

如果连 broadcast 都没填，tick 层会塞一个默认的：

c
static void tick_device_setup_broadcast_func(struct clock_event_device *dev)
{
	if (!dev->broadcast)
		dev->broadcast = tick_broadcast;
	if (!dev->broadcast) {
		pr_warn_once("%s depends on broadcast, but no broadcast function available\n",
			     dev->name);
		dev->broadcast = err_broadcast;
	}
}

err_broadcast 只打一句 "Failed to broadcast timer tick. Some CPUs may be unresponsive."。看到这句，说明有 CPU 已经睡死了。

进去和出来 #

时机 谁调 做什么
进 C3 前 cpuidle / tick_broadcast_control(TICK_BROADCAST_ON) 把本 CPU 加进 tick_broadcast_mask，shutdown 本地设备
被唤醒时 tick_check_oneshot_broadcast_this_cpu() 把本地设备切回 ONESHOT
退出 C3 后 TICK_BROADCAST_OFF 从 mask 摘掉，恢复本地设备

periodic 广播模式下，本地设备被显式 shutdown：

c
			if (bc && !(bc->features & CLOCK_EVT_FEAT_HRTIMER) &&
			    tick_broadcast_device.mode == TICKDEV_MODE_PERIODIC)
				clockevents_shutdown(dev);

三个条件缺一不可：广播设备存在、不是 hrtimer 模拟的、当前是 periodic 模式。注释解释了为什么要判 hrtimer：「避免切换到 oneshot 时出现 hiccup」，因为 hrtimer 广播设备本身还没准备好。

一个坑：ping-pong #

oneshot 广播里有一段长注释，讲的是「出口路径上的乒乓」：

text
			 * This can lead to a ping-pong when we return
			 * to idle and therefore rearm the broadcast
			 * timer before the cpu local timer was able
			 * to fire.

场景是：CPU 被别的原因唤醒（不是广播 IPI），退出 idle，重新编程本地 timer；但 pending 的广播还没处理完，于是再次睡下、再次重新编程……来回弹。

解法是 tick_broadcast_force_mask：如果发现本地 next_event 已经过期，就打上 force 标记，不重编程，让广播 handler 来收尾。

十七、clocksource 与 clockevent 的硬件对应关系 #

回到开篇的对偶关系，这次落到具体芯片上。

一颗 HPET 块拆成两半 #

HPET 是最典型的例子：同一个硬件块，同时注册了 clocksource 和 clockevent。

c
	clocksource_register_hz(&clocksource_hpet, (u32)hpet_freq);

	if (id & HPET_ID_LEGSUP) {
		hpet_legacy_clockevent_register(&hpet_base.channels[0]);
		hpet_base.channels[0].mode = HPET_MODE_LEGACY;
		...
	}

hpet_enable() 里这两步隔了几行，但用的是同一组寄存器：

用途 用的寄存器 对应抽象
读当前时间 HPET_COUNTER（主计数器） clocksource read
定周期 HPET_Tn_CMP + HPET_Tn_CFG.PERIODIC clockevent periodic
定单次 HPET_Tn_CMP 写入绝对计数 clockevent oneshot

clocksource_hpet 和 channel 0 的 evt 共享同一个 counter 的时基，这是它们能协调工作的前提。

一颗本地 APIC：只有 clockevent，没有 clocksource #

local APIC timer 的计数器（APIC_TMICT/APIC_TMCCT）是倒计数的，而且进 C3 会停。倒计数不能做单调时间轴，停摆更不能。所以它只注册 clockevent：

c
static struct clock_event_device lapic_clockevent = {
	.name				= "lapic",
	.features			= CLOCK_EVT_FEAT_PERIODIC |
					  CLOCK_EVT_FEAT_ONESHOT | CLOCK_EVT_FEAT_C3STOP
					  | CLOCK_EVT_FEAT_DUMMY,
	.shift				= 32,
	...
	.rating				= 100,
	.irq				= -1,
};

注意 DUMMY 也在 feature 里。注释写了原因：LAPIC timer 在某些配置下会被当作占位设备，真正的定时由广播设备负责。

TSC：只做 clocksource，也做 deadline timer #

TSC 是自由运行的递增计数器，天生物合 clocksource。但它同时被拿来当 clockevent 的时基：TSC deadline timer 不是独立的计数器，而是拿 TSC 的值去比较。

c
static int lapic_next_deadline(unsigned long delta,
			       struct clock_event_device *evt)
{
	u64 tsc;

	weak_wrmsr_fence();
	tsc = rdtsc();
	wrmsrl(MSR_IA32_TSC_DEADLINE, tsc + (((u64) delta) * TSC_DIVISOR));
	return 0;
}

这是两者共用同一硬件的最直接证据：clocksource 读的就是 clocksource_tsc.read() 里的同一个 rdtsc()，clockevent 写的是这个读数的未来值。

汇总表 #

硬件 能做 clocksource 能做 clockevent 原因
TSC 能（rating 300） 间接（TSC deadline） 64 bit 自由计数、跨核同步（条件性）
HPET 能（rating 250） 能（rating 50 / 110） 独立计数器 + 多个比较通道
ACPI PM Timer 能（rating 200） 不能 24 bit 只读计数器，无比比较器
PIT (8254) 一般不用 能（早期/兼容） 16 bit，频率低，已边缘化
local APIC timer 不能 能（rating 100 / 150） 倒计数、C3 停摆
jiffies 能（rating 1） 不能 纯软件

规律很清楚：clocksource 需要「自由运行的计数器」，clockevent 需要「比较器」或「可重装的定时器」。 一个硬件如果两者都有，就能出两个抽象；只有计数器就只能做 clocksource；只有比较器就只能做 clockevent。

十八、一次完整的时间读取与定时设定 #

把前面所有零件串成两条链路。

链路一：读一次时间 #

text
用户态 clock_gettime(CLOCK_MONOTONIC)
  |
  +-- [vDSO 路径] clocksource.vdso_clock_mode 允许
  |     -> 直接读 TSC -> 用页里缓存的 mult/shift/offset 算 -> 返回
  |     （全程不进内核）
  |
  +-- [syscall 路径]
        -> ktime_get() / ktime_get_mono_fast_ns()
           -> timekeeper 读 tkr->clock->read()      <- clocksource.read()
              -> clocksource_delta(now, tkr->cycle_last, mask)
                 -> 差值 < max_cycles ?
                    -> clocksource_cyc2ns(delta, mult, shift)   [快]
                    -> mul_u64_u32_shr(delta, mult, shift)      [慢]
              -> 累加到 tkr_mono.base 上
              -> 加上 NTP 调整量
              -> 返回 ns

三个交接点记住：

  1. read() 只负责给 cycle，不做任何换算。
  2. 减法带 mask，回绕自动处理。
  3. 换算只喂差值，绝对值必溢出。

链路二：设一次定时 #

text
上层设 deadline（hrtimer / timer wheel / NO_HZ 计算）
  -> tick 层选下一个到期时刻
     -> clockevents_program_event(dev, expires, force)
        |
        +-- CLOCK_EVT_FEAT_KTIME ? -> dev->set_next_ktime(expires, dev)
        |
        +-- delta = expires - ktime_get()
            +-- delta <= 0 ?
            |     +-- force ? clockevents_program_min_delta() -> 返回
            |     +-- 否则返回 -ETIME
            |
            +-- delta 夹到 [min_delta_ns, max_delta_ns]
                -> clc = (delta * dev->mult) >> dev->shift
                   -> dev->set_next_event(clc, dev)
                      -> 驱动写硬件比较寄存器
                         -> 硬件到点 -> IRQ
                            -> 驱动中断处理
                               -> evt->event_handler(evt)
                                  -> tick_handle_periodic / hrtimer 中断处理

三个交接点：

  1. program_event 收绝对 ktime，set_next_event 收相对 tick 数。
  2. 夹取在 program_event 里做，驱动不用再做。
  3. 中断里统一走 event_handler，驱动不越权。

两条链路的交点 #

看这两个 mult/shift：clocksource->mult 和 clock_event_device->mult。它们不是同一对数，方向相反。但它们的来源是同一个 clocks_calc_mult_shift()，参数对调。

另一个交点是时基一致。链路二算 delta = expires - ktime_get()，ktime_get() 来自链路一。如果 clocksource 换了（TSC 被判歪换成 HPET），ktime_get() 的基准变了，正在等进行中的 clockevent 依然按绝对 ktime 走，不需要重算。这就是为什么 next_event 存的是绝对 ktime 而不是 tick：换时间源不会打乱已设的定时器。

写 current_clocksource 的两个结果 #

写了名字之后，__clocksource_select() 会把 override_name 和链表里的名字比对。命中还要过一道：

c
		if (!(cs->flags & CLOCK_SOURCE_VALID_FOR_HRES) && oneshot) {
			/* Override clocksource cannot be used. */
			if (cs->flags & CLOCK_SOURCE_UNSTABLE) {
				pr_warn("Override clocksource %s is unstable and not HRT compatible - cannot switch while in HRT/NOHZ mode\n",
					cs->name);
				override_name[0] = 0;
			} else {
				/*
				 * The override cannot be currently verified.
				 * Deferring to let the watchdog check.

					cs->name);
			}
		} else
			best = cs;

两种情况：被判不稳定就清空 override_name 并警告，你的要求被拒绝；只是还没验证就推迟，等 watchdog 点过头再切。原文用「用户是上帝，但用户也许会愚蠢」形容这段，代码的态度确实是这样。

交叉验证时间源 #

clocksource_verify_percpu() 是给 TSC 这类跨核时间源做的核对器，由 CLOCK_SOURCE_VERIFY_PERCPU 标志触发：

c
void clocksource_verify_percpu(struct clocksource *cs)
{
	...
	preempt_disable();
	for_each_cpu(cpu, &cpus_chosen) {
		if (cpu == testcpu)
			continue;
		csnow_begin = cs->read(cs);
		smp_call_function_single(cpu, clocksource_verify_one_cpu, cs, 1);
		csnow_end = cs->read(cs);
		delta = (s64)((csnow_mid - csnow_begin) & cs->mask);
		if (delta < 0)
			cpumask_set_cpu(cpu, &cpus_behind);
		delta = (csnow_end - csnow_mid) & cs->mask;
		if (delta < 0)
			cpumask_set_cpu(cpu, &cpus_ahead);
	}
	...
}

思路：本 CPU 读一次，让目标 CPU 读一次，本 CPU 再读一次。如果目标 CPU 的读数落在两次读之间，说明同步；落在外面就不行，ahead 还是 behind 一目了然。

结果只在 curr_clocksource 被判 UNSTABLE 且带 VERIFY_PERCPU 时才跑（在 watchdog kthread 里）。

二十、易错点速查 #

按踩坑频率排序，每条都是本篇讲过的内容。

# 坑 正确做法 出处
1 把绝对 cycle 喂给 clocksource_cyc2ns() 先减 cycle_last 做差，只喂差值 第六章
2 做差忘了 & mask 用 clocksource_delta()，回绕才对 第六章
3 以为 struct clocksource 还带 cycle_last 5.x 已删，状态在 timekeeper 里 第三章
4 以为 struct clocksource 还是 cacheline 对齐 5.x 已去掉，clock_event_device 才保留 第三、十一章
5 以为 rating 高的就一定被选中 oneshot 模式下没有 VALID_FOR_HRES 的直接跳过 第四章
6 以为 max_idle_ns 是 12.5% margin 5.x 是 >>= 1，50% 第六章
7 驱动自己算 mult/shift 后调 __clocksource_register() 那是 jiffies 专用路径，普通驱动用 clocksource_register_hz() 第五章
8 给 struct clock_event_device 填 event_handler 框架才会填，驱动填了会被覆盖或造成错乱 第十三章
9 在 set_next_event 里收绝对值 收到的是相对 tick 数 第十五章
10 以为 set_next_event 返回 0 就表示一定成功 硬件已经过期，program_event 会再判 第十五章
11 广播设备带 C3STOP 广播设备自己都会停，选不上 第十四章
12 广播设备的 cpumask 填 cpu_all_mask 会被改成 cpu_possible_mask 并告警 第十四章
13 忘了 clockevent_state_*() 直接读 state_use_accessors 字段名就在提示你别裸读 第十一章
14 在 SHUTDOWN 状态下调 program_event 会直接返回 0，事件根本不会发生 第十五章
15 以为 jiffies 能在 NO_HZ 下当时间源 源码注释明确「不推荐给 tickless 系统」 第九章
16 以为 TSC 的 rating 是 400 实际是 300，tsc-early 是 299 第四章
17 看到 available_clocksource 少了某个就慌 oneshot 模式下会按 VALID_FOR_HRES 过滤 第十九章
18 在 NMI 里调 HPET 的 read() 5.15 专门有 in_nmi() 分支绕开锁 第七章
19 以为 watchdog 判歪只是减一点 rating 直接归零，彻底出局 第八章
20 以为时钟源换了对正在等的定时器有影响 next_event 存绝对 ktime，不受影响 第十八章

再补三条不容易用一句话概括的：

关于 mult 的有符号性。 clocksource_cyc2ns() 的返回类型是 s64，中间乘法转成 u64。如果输入的是负的差值（比如时间源倒退了），会得到一个巨大的正数。所以时间倒数与边界检查必须在 timekeeper 层做，不能指望换算函数兜底。

关于 600 秒。 clocksource 和 clockevent 两个方向都有这个上限，含义相同：精度与睡眠时长的折衷。别把它当成硬件能力，它是软件主动设的。

关于「未验证」的部分。 本篇所有代码引用都以 5.15 为基线，逐字核对过。struct clock_event_device.cpumask 在 5.15 之后是否改名、改成什么，我没有逐版核对，标未验证。你手上的内核如果不是 5.15，请先看一眼 include/linux/clockchips.h 和 include/linux/clocksource.h 再对照本文。
