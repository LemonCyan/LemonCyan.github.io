一、POSIX timer 在用户态长什么样 #

先把接口摆出来,不然下面读内核代码没有锚点。

c
#include <signal.h>
#include <time.h>

int timer_create(clockid_t clockid, struct sigevent *sevp, timer_t *timerid);
int timer_settime(timer_t timerid, int flags,
                  const struct itimerspec *new_value, struct itimerspec *old_value);
int timer_gettime(timer_t timerid, struct itimerspec *curr_value);
int timer_getoverrun(timer_t timerid);
int timer_delete(timer_t timerid);

struct itimerspec {
    struct timespec it_interval;  /* timer period */
    struct timespec it_value;     /* timer expiration */
};

union sigval { int sival_int; void *sival_ptr; };

typedef struct sigevent {
    sigval_t sigev_value;
    int sigev_signo;
    int sigev_notify;
    union {
        int _pad[SIGEV_PAD_SIZE];
        int _tid;
        struct {
            void (*_function)(sigval_t);
            void *_attribute;
        } _sigev_thread;
    } _sigev_un;
} sigevent_t;

it_value 是第一个到期点,it_interval 是周期。it_interval 为零就是 one shot,非零就是 periodic;it_value 为零表示停表——这个语义在 common_timer_set 里会变成一句 return 0。

sigev_notify 四个取值,内核里有同名宏:

值 宏 到期之后内核做什么
0 SIGEV_SIGNAL 向进程(缺省)或指定线程发 sigev_signo 信号
1 SIGEV_NONE 什么都不发,用户自己 timer_gettime 轮询
2 SIGEV_THREAD glibc 侧创建线程跑回调,内核看到的仍是 SIGEV_SIGNAL
4 SIGEV_THREAD_ID 向 _sigev_un._tid 指定的线程发信号

SIGEV_THREAD 内核根本不认识。glibc 的 timer_create 在用户态把它翻译成专用 realtime 信号加线程池回调,进内核时 sigev_notify 是 SIGEV_SIGNAL。所以第十章之后讨论内核路径时它不再出现。

和老的 setitimer 比,POSIX timer 解决了四个硬伤:每进程只能 3 个 timer、设定即覆盖、信号不可改、mask 期间多次超期只回调一次拿不到计数。最后那条就是 overrun 的由来,第八章看内核怎么用两个字段记它。

二、如何标识一个 timer：timer_t 与 k_itimer #

timer_t 在 glibc 里是个指针大小的句柄,内核里就是一个小整数。分配算法在 posix_timer_add:

c
static int posix_timer_add(struct k_itimer *timer)
{
    struct signal_struct *sig = current->signal;
    int first_free_id = sig->posix_timer_id;            /* (1) */
    struct hlist_head *head;
    int ret = -ENOENT;

    do {                                                 /* (2) */
        spin_lock(&hash_lock);
        head = &posix_timers_hashtable[hash(sig, sig->posix_timer_id)]; /* (3) */
        if (!__posix_timers_find(head, sig, sig->posix_timer_id)) {     /* (4) */
            hlist_add_head_rcu(&timer->t_hash, head);
            ret = sig->posix_timer_id;
        }
        if (++sig->posix_timer_id < 0)                   /* (5) */
            sig->posix_timer_id = 0;
        if ((sig->posix_timer_id == first_free_id) && (ret == -ENOENT)) /* (6) */
            ret = -EAGAIN;
        spin_unlock(&hash_lock);
    } while (ret == -ENOENT);

    return ret;
}
  1. sig->posix_timer_id 是「上一次分配的 ID + 1」,也就是扫描起点。原文原话:「这个假设不一定成立,但是有很大的机会」。
  2. 线性扫描,从起点往后找第一个空位。
  3. hash key 由「进程 signal descriptor 地址」和「候选 ID」共同决定,所以 ID 只在进程内唯一,跨进程可以撞。
  4. 该 ID 在本进程没被占用,插入 hash 并返回。
  5. 溢出(INT_MAX 之上)回绕到 0。
  6. 扫满一圈还无空位,返回 -EAGAIN。

posix_timer_id 挂在 struct signal_struct 里,不在 task_struct。原因直白:timer 和信号发送强相关,而同进程所有线程共享一个 signal_struct。这意味着一个线程 timer_create 出来的 timer,另一个线程用同一个 ID 也 timer_settime 得动——ID 空间是进程级的。

c
struct signal_struct {
    ...
    int posix_timer_id;
    struct list_head posix_timers;
    ...
};

fork 之后 posix_timer_id 归零,子进程从 0 重新分配,父进程的 POSIX timer 对象不继承。4.x 之后 posix_timer_id 是否仍是 int、是否仍在 signal_struct,未验证。

三、如何组织所有 timer：散列表与 idr #

系统里所有进程的所有 POSIX timer 都在一张全局 hash 表里:

c
static DEFINE_HASHTABLE(posix_timers_hashtable, 9);
static DEFINE_SPINLOCK(hash_lock);

static int hash(struct signal_struct *sig, unsigned int nr)
{
    return hash_32(hash32_ptr(sig) ^ nr, HASH_BITS(posix_timers_hashtable));
}

DEFINE_HASHTABLE(x, 9) 是 2^9 = 512 个桶。key 是 signal_struct 地址和 timer ID 的异或再 hash_32。除全局表外,每个进程还有一条自己的链(struct signal_struct 的 posix_timers 成员),创建时 list_add,删除时摘掉。

结构 作用域 用途 保护
posix_timers_hashtable[512] 全局 从 timer_t 反查 k_itimer hash_lock
signal->posix_timers 链 每进程 遍历/清理本进程所有 timer sighand->siglock
k_itimer.t_hash 节点 挂全局 hash 链表 hash_lock + RCU
k_itimer.list 节点 挂进程链 sighand->siglock

为什么是 hash 而不是 idr?ID 是每进程独立编号、会回绕、不要求全局唯一,而 idr 要的是全局单调可分配的整数空间,不匹配。用 hash 的代价是扫描会线性退化,收益是没有中心分配器、fork/exit 时清理简单。这一段原文只说「global hash table」,没讨论取舍,标「推断」。

锁次序:先拿 hash_lock 查表,再 spin_lock 每个 timer 自己的 it_lock;任何持有 it_lock 的路径都不回头拿 hash_lock。第九章的 unlock_timer() 就是这个次序。

四、如何抽象一个 timer：k_clock 与 k_itimer 的分层 #

1、k_itimer：一个 timer 对象的全貌 #

c
struct k_itimer {
    struct list_head list;                  /* (1) */
    struct hlist_node t_hash;
    spinlock_t it_lock;
    clockid_t it_clock;                     /* (2) */
    timer_t it_id;
    int it_overrun;                         /* (3) */
    int it_overrun_last;
    int it_requeue_pending;                 /* (4) */
#define REQUEUE_PENDING 1
    int it_sigev_notify;                    /* (5) */
    struct signal_struct *it_signal;
    union {                                 /* (6) */
        struct pid *it_pid;
        struct task_struct *it_process;
    };
    struct sigqueue *sigq;
    union {                                 /* (7) */
        struct {
            struct hrtimer timer;
            ktime_t interval;
        } real;
        struct cpu_timer_list cpu;
        struct {
            unsigned int clock;
            unsigned int node;
            unsigned long incr;
            unsigned long expires;
        } mmtimer;
        struct {
            struct alarm alarmtimer;
            ktime_t interval;
        } alarm;
        struct rcu_head rcu;
    } it;
};
字段 类型 语义 谁写
list struct list_head 挂 signal->posix_timers timer_create / timer_delete
t_hash struct hlist_node 挂全局 hash 桶 posix_timer_add
it_lock spinlock_t 保护本对象全部字段 各路径
it_clock clockid_t 时基,决定走哪个 k_clock timer_create
it_id timer_t 进程内唯一 ID timer_create
it_overrun int 本轮累积的 overrun 计数 posix_timer_fn / schedule_next_timer
it_overrun_last int 已递交那一轮的 overrun 快照 schedule_next_timer
it_requeue_pending int LSB 标 pending,高 31 位是信号私有数据 posix_timer_fn
it_sigev_notify int SIGEV_* timer_create
it_signal struct signal_struct * 所属进程的 signal descriptor timer_create
it_pid / it_process 匿名 union 信号目标进程 / clock_nanosleep 用的 task timer_create
sigq struct sigqueue * 预分配的 sigqueue,到期时挂 pending 队列 timer_create 路径
it 匿名 union 按 clock 类型分派的具体实现 各 k_clock 回调

几个点要展开。

(1) 两条链表节点必须分开。 list 和 t_hash 同时在用:反查靠 hash,清理靠进程链。一个对象同时挂两处,缺一不可。

(3) 两个 overrun 字段的来历。 一个 1 秒周期的 timer,信号被 mask 三秒才处理:1s 挂一个 pending 信号,2s 又到期但信号已在队列里,只把 si_overrun 加一,3s 同理。用户在 3.5s 才进 handler,timer_getoverrun 该返回 2。问题是信号递交给进程了,累积计数字段得清掉准备下一轮,但用户随时会来查上一轮的值。所以两个字段:it_overrun 边跑边累,递交那一刻快照进 it_overrun_last,it_overrun 重置。

c
SYSCALL_DEFINE1(timer_getoverrun, timer_t, timer_id)
{
    ...
    overrun = timr->it_overrun_last;
    ...
    return overrun;
}

(4) it_requeue_pending 两用。 LSB(REQUEUE_PENDING = 1)标「该 timer 的信号此刻在 pending 队列」。高位是信号私有数据,写进 siginfo.si_sys_private,用来在 dequeue_signal 时判断「这条是不是新一轮、要不要推周期的下一个到期点」。所以推进周期是 +2:

c
timr->it_requeue_pending = (timr->it_requeue_pending + 2) & ~REQUEUE_PENDING;

加 2 让高位加一(换私有数据),与上 ~REQUEUE_PENDING 清 LSB(不再 pending)。

(7) 那个 union 是分层的核心。 同一个 k_itimer,按 it_clock 走不同成员:real 是真实时间 clock,内部一个 hrtimer 加一个 ktime_t interval,本篇主干;cpu 是 CLOCK_*_CPUTIME_ID,走 cpu_timer_list,由调度器/ tick 侧统计推进,不碰 hrtimer;alarm 是 *_ALARM,内部 alarmtimer,基于 RTC;mmtimer 作者自己说「不知道用在什么场合,也许和 Multimedia Timer 相关」,在 3.10 的树里这一支基本是死代码,是否已被移除未验证;rcu 是删除时复用这块内存等 grace period,避免和正在跑的回调打架。

一个 union 装五种实现,省掉了每种 timer 一个父类指针,代价是字段含义要靠 it_clock 手工解释,编译器帮不上忙。

十个回调分两组:前四个管「时间本身」,后五个管「timer 生命周期」,nsleep 管睡眠。timer 相关只要五个,syscall 层不关心底层是 hrtimer 还是 cpu_timer 还是 alarm,一律 kc->timer_xxx(timr, ...)。

这两层的分工一句话:**`k_clock` 是策略,`k_itimer` 是状态。** 系统调用写一次,`kc->` 一跳,五种 timer 各走各的。

五、timer_create 的完整链路 #

c
SYSCALL_DEFINE3(timer_create, const clockid_t, which_clock,
                struct sigevent __user *, timer_event_spec,
                timer_t __user *, created_timer_id)
{
    struct k_clock *kc = clockid_to_kclock(which_clock);
    struct k_itimer *new_timer;
    int error, new_timer_id;
    sigevent_t event;
    int it_id_set = IT_ID_NOT_SET;

    new_timer = alloc_posix_timer();
    spin_lock_init(&new_timer->it_lock);
    new_timer_id = posix_timer_add(new_timer);            /* (1) */
    it_id_set = IT_ID_SET;
    new_timer->it_id = (timer_t)new_timer_id;
    new_timer->it_clock = which_clock;
    new_timer->it_overrun = -1;                            /* (2) */

    if (timer_event_spec) {
        if (copy_from_user(&event, timer_event_spec, sizeof(event))) {
            error = -EFAULT;
            goto out;
        }
        rcu_read_lock();
        new_timer->it_pid = get_pid(good_sigevent(&event)); /* (3) */
        rcu_read_unlock();
    } else {
        event.sigev_notify = SIGEV_SIGNAL;
        event.sigev_signo = SIGALRM;
        event.sigev_value.sival_int = new_timer->it_id;
        new_timer->it_pid = get_pid(task_tgid(current));    /* (4) */
    }

    new_timer->it_sigev_notify     = event.sigev_notify;
    new_timer->sigq->info.si_signo = event.sigev_signo;
    new_timer->sigq->info.si_value = event.sigev_value;
    new_timer->sigq->info.si_tid   = new_timer->it_id;      /* (5) */
    new_timer->sigq->info.si_code  = SI_TIMER;

    if (copy_to_user(created_timer_id, &new_timer_id, sizeof(new_timer_id))) {
        error = -EFAULT;
        goto out;
    }

    error = kc->timer_create(new_timer);                    /* (6) */

    spin_lock_irq(&current->sighand->siglock);
    new_timer->it_signal = current->signal;
    list_add(&new_timer->list, &current->signal->posix_timers); /* (7) */
    spin_unlock_irq(&current->sighand->siglock);
    return 0;
}

(1) 分配与入表。 alloc_posix_timer() 从 kmem_cache 拿对象并清零,连 sigq 一起预分配。这个细节关键:到期回调在硬中断上下文跑,那时不能 kmalloc,信号载体必须提前备好。posix_timer_add() 同时做两件事:分配 ID、挂全局 hash。原文注释点了 it_id_set 的作用——已经进表了,后面任何一步失败都必须在退出路径上把 t_hash 摘掉,否则 hash 桶里挂着野节点。原文把 goto 之后的出错处理省略了。

(2) it_overrun = -1。 初值不是 0。为什么,原文没写,未验证。从上下文推,it_overrun 是「累积中」的计数器,-1 应是「未开始计数」的哨兵(推断),和第九章 schedule_next_timer() 里那句 timr->it_overrun = -1 是同一个初值。

(3) good_sigevent() 的检查。 用户传了 sigevent 就得验:给了 SIGEV_THREAD_ID 时要能按 tid 找到 task_struct,而且那个线程必须和当前线程同属一个进程组(same_thread_group 一类检查);走信号路径时 sigev_signo 必须是合法的信号号。全过才返回目标 struct pid *。两个分支:指定 tid 一条,否则发给整个线程组。

(4) 不给 sigevent 的缺省。 SIGALRM 发给 task_tgid(current),即线程组 leader。这解释了为什么在子线程里 timer_create(NULL) 之后 SIGALRM 会落在主线程上——信号目标是「进程」,不是「创建 timer 的那个线程」。

(5) si_code = SI_TIMER。 内核靠这个值决定 dequeue_signal 之后干什么。第九章会看到,dequeue_signal 里判断 (info->si_code & __SI_MASK) == __SI_TIMER && info->si_sys_private 来决定是否推进周期。

(6) 落到具体 clock。 对 real time clock 是:

c
static int common_timer_create(struct k_itimer *new_timer)
{
    hrtimer_init(&new_timer->it.real.timer, new_timer->it_clock, 0);
    return 0;
}

这里只是 hrtimer_init,还没开始计时。真正的到期时间在 timer_settime 里设。timer_create 之后、timer_settime 之前,timer 是「存在但停着」。

(7) 挂进进程链。 it_signal 赋值 + list_add 都在 siglock 里。放在 kc->timer_create() 之后的原因:失败时对象还没进进程链,清理只需摘 hash;一旦进了进程链,清理方(比如 exit_itimers)就会并发抓到它。

六、timer_settime：设定第一个到期时间 #

syscall 外壳很短,核心在 common_timer_set:

c
SYSCALL_DEFINE4(timer_settime, timer_t, timer_id, int, flags,

                struct itimerspec __user *, old_setting)
{
    struct k_itimer *timr;
    struct itimerspec new_spec, old_spec;

TIMER_RETRY 很重要。hrtimer_try_to_cancel() 在回调正在执行的瞬间返回负值,common_timer_set 直接 return TIMER_RETRY,外壳重来一遍。所以 timer_settime 是「要么不取消,要么取消成功」,不会和正在跑的回调互相踩。

c
static int common_timer_set(struct k_itimer *timr, int flags,
                            struct itimerspec *new_setting,
                            struct itimerspec *old_setting)
{
    struct hrtimer *timer = &timr->it.real.timer;
    enum hrtimer_mode mode;

    if (old_setting)
        common_timer_get(timr, old_setting);

    timr->it.real.interval.tv64 = 0;                 /* 先清零 interval */

    if (hrtimer_try_to_cancel(timer) < 0)            /* 停表 */
        return TIMER_RETRY;

    timr->it_requeue_pending = (timr->it_requeue_pending + 2) & ~REQUEUE_PENDING;
    timr->it_overrun_last = 0;                       /* (1) */

    if (!new_setting->it_value.tv_sec && !new_setting->it_value.tv_nsec)
        return 0;                                    /* it_value 为 0 => 只停表 */

    mode = flags & TIMER_ABSTIME ? HRTIMER_MODE_ABS : HRTIMER_MODE_REL; /* (2) */

    hrtimer_init(&timr->it.real.timer, timr->it_clock, mode);
    timr->it.real.timer.function = posix_timer_fn;

    hrtimer_set_expires(timer, timespec_to_ktime(new_setting->it_value));

    timr->it.real.interval = timespec_to_ktime(new_setting->it_interval); /* (3) */

    if ((timr->it_sigev_notify & ~SIGEV_THREAD_ID) == SIGEV_NONE) {       /* (4) */
        if (mode == HRTIMER_MODE_REL)
            hrtimer_add_expires(timer, timer->base->get_time());
        return 0;
    }

    hrtimer_start_expires(timer, mode);              /* 真正入红黑树 */
    return 0;
}

(1) 重设就清 overrun。 一次 timer_settime 之后上一轮的 overrun 语义作废,所以 it_overrun_last 归零,it_requeue_pending 加 2 换一轮私有数据。这一手还解决一个隐患:旧信号还在队列里没被 dequeue 时,新设定后那个旧信号被取出来,私有数据已经对不上,dequeue_signal 就不会去 schedule_next_timer() 推一个新周期。

(2) TIMER_ABSTIME 直通 hrtimer mode。 flags & TIMER_ABSTIME 为真就是 HRTIMER_MODE_ABS,否则 HRTIMER_MODE_REL。用户态和内核态的「相对/绝对」在 hrtimer 层已有对应物,不需要额外转换。

(3) interval 换算成 ktime。 3.10 里 ktime_t 还是:

c
union ktime {
    s64 tv64;
#if BITS_PER_LONG != 64 && !defined(CONFIG_KTIME_SCALAR)

所以代码里到处 tv64。这个写法 4.x 之后消失(ktime_t 变成 s64),原文里所有 .tv64 判断在 4.x 上都要重新对一遍,未验证具体提交。

(4) SIGEV_NONE 的偷懒启动。 轮询型 timer 压根不进红黑树,只把 expires 算好放进 hrtimer。等用户 timer_gettime 来问,common_timer_get 自己发现超期、自己 hrtimer_forward、自己补 overrun。省掉的是一次硬件编程和一次中断,代价是 SIGEV_NONE 的精度完全由用户轮询频率决定。原文注释说得客气:「我们并不会真正启动该 timer」,实质是把算账的活推给了读的一方。

相对时间在这里还要手工补一次 hrtimer_add_expires(timer, timer->base->get_time()),因为 hrtimer_start_expires 那个「把 REL 转 ABS」的动作被跳过了。

七、timer_gettime 与 timer_getoverrun #

1、外壳 #

c
SYSCALL_DEFINE2(timer_gettime, timer_t, timer_id,
                struct itimerspec __user *, setting)
{
    struct itimerspec cur_setting;
    struct k_itimer *timr;
    struct k_clock *kc;
    unsigned long flags;
    int ret = 0;

    timr = lock_timer(timer_id, &flags);
    kc = clockid_to_kclock(timr->it_clock);

        ret = -EINVAL;
    else

copy_to_user 放在 unlock_timer 之后,因为 copy 会睡眠(page fault 要拿 mmap 锁)。clockid_to_kclock() 用 WARN_ON_ONCE 而不是直接返回错误:走到这里说明内核自己出了 bug(it_clock 是内核写进去的),但用户态不该因此崩,所以还是给 -EINVAL。

2、common_timer_get：剩余时间怎么算 #

c
static void common_timer_get(struct k_itimer *timr, struct itimerspec *cur_setting)
{
    ktime_t now, remaining, iv;
    struct hrtimer *timer = &timr->it.real.timer;

    memset(cur_setting, 0, sizeof(struct itimerspec));
    iv = timr->it.real.interval;                       /* 周期值 */

    if (iv.tv64)                                       /* (1) */
        cur_setting->it_interval = ktime_to_timespec(iv);
    else if (!hrtimer_active(timer) &&
             (timr->it_sigev_notify & ~SIGEV_THREAD_ID) != SIGEV_NONE) /* (2) */
        return;

    now = timer->base->get_time();                     /* (3) */

    if (iv.tv64 && (timr->it_requeue_pending & REQUEUE_PENDING ||
                    (timr->it_sigev_notify & ~SIGEV_THREAD_ID) == SIGEV_NONE))
        timr->it_overrun += (unsigned int)hrtimer_forward(timer, now, iv); /* (4) */

    remaining = ktime_sub(hrtimer_get_expires(timer), now);

    if (remaining.tv64 <= 0) {                         /* 已经过期 */
        if ((timr->it_sigev_notify & ~SIGEV_THREAD_ID) != SIGEV_NONE)
            cur_setting->it_value.tv_nsec = 1;         /* (5) */
    } else
        cur_setting->it_value = ktime_to_timespec(remaining);
}

(1) it_interval 非零就是 periodic,原样返回周期;内核不做「取模算当前周期进度」这种操作。

(2) one shot 且 hrtimer 已不 active 且不是 SIGEV_NONE:说明这一枪打完了,返回全零。SIGEV_NONE 被排除在外——轮询型 timer 从来不 active,不能因此判成「已结束」。

(3) base->get_time() 而不是 ktime_get()。CLOCK_REALTIME 和 CLOCK_MONOTONIC 用不同 time base,hrtimer 的 base 绑定了时基,取时间必须走 base 自己的 get_time,否则 REALTIME 的 timer 会被拿 MONOTONIC 的「现在」去减,差出一个 uptime。

(4) 这里是 timer_gettime 真正干活的地方。 两种情况要在读的时候把账算掉:

  • it_requeue_pending & REQUEUE_PENDING:周期 timer 的信号还在 pending 没被带走,期间 hrtimer 不会被 restart,停在原地。此时来读就得自己 hrtimer_forward 把到期点往后推 N 个周期,返回值正好是「越过了几个周期」,直接加进 overrun。
  • SIGEV_NONE:同上,本来就没人 restart。

hrtimer_forward(timer, now, iv) 的语义是把 expires 前推最小的整数个 iv,使 expires > now,返回推进的周期数。第九章 schedule_next_timer 里的那次调用是同一个手法。

(5) 一个 nsec = 1 的怪值。 超期了但不是轮询型,it_value 填 tv_nsec = 1 而不是 0。原文这里写 (5)TODO。。我的理解:此时信号已经产生(或即将产生),it_value = 0 在 POSIX 语义里表示「timer 已停止」,1ns 既表达「还剩一点点」又避免用户误判 timer 被停了。属于推断,未验证,原文明确没给答案。

3、timer_getoverrun #

timer_getoverrun 不碰 hrtimer,只读字段:

c
SYSCALL_DEFINE1(timer_getoverrun, timer_t, timer_id)
{
    ...
    overrun = timr->it_overrun_last;
    ...

八、timer_delete 与资源释放 #

c
SYSCALL_DEFINE1(timer_delete, timer_t, timer_id)
{
    struct k_itimer *timer;
    unsigned long flags;

retry_delete:
    timer = lock_timer(timer_id, &flags);

    if (timer->it_sigev_notify == (SIGEV_THREAD_ID | SIGEV_SIGNAL)) {
        /* 目标线程已死,借机清理 */
        unlock_timer(timer, flags);
        goto retry_delete;
    }
    do_timer_delete(timer);           /* kc->timer_del + 摘表 */
    unlock_timer(timer, flags);
    return 0;
}

do_timer_delete() 要做完五件事:

  1. kc->timer_del(timer),对 real time clock 是 hrtimer_cancel() 把高精度 timer 摘出红黑树(3.10 的 common_timer_del 就是把 hrtimer_cancel 包了一层)。
  2. 从 signal->posix_timers 链上 list_del。
  3. 从 posix_timers_hashtable 上 hlist_del。
  4. it_signal = NULL,it_pid 或 it_process 用 put_pid/put_task_struct 放引用。
  5. 对象不能立刻 kmem_cache_free。到期回调在 hrtimer 软中断里跑,此刻正拿 container_of 指着这具尸体。所以走 call_rcu(&timer->it.rcu, itimer_free),那个 rcu 成员复用 it union 的空间。进程退出时的批量清理(exit_itimers)同理。

SIGEV_THREAD_ID | SIGEV_SIGNAL 那个分支值得说:目标线程已经 exit 时,sighand/signal 这套结构在解体,继续往下走会踩空。内核的做法是放锁重来,重来时 lock_timer 会查到一个已被标脏的 timer 并顺手回收。这是 3.10 的形态,4.x 之后这块有调整,未验证。

九、timer 的回调：到期之后发生什么 #

1、posix_timer_fn #

c
static enum hrtimer_restart posix_timer_fn(struct hrtimer *timer)
{
    struct k_itimer *timr;
    unsigned long flags;
    int si_private = 0;
    enum hrtimer_restart ret = HRTIMER_NORESTART;            /* (1) */

    timr = container_of(timer, struct k_itimer, it.real.timer); /* (2) */
    spin_lock_irqsave(&timr->it_lock, flags);

    if (timr->it.real.interval.tv64 != 0)
        si_private = ++timr->it_requeue_pending;             /* (3) */

    if (posix_timer_event(timr, si_private)) {               /* (4) */
        /* 信号被 ignore:在这里补设下一个到期点,返回 RESTART */
    }

    unlock_timer(timr, flags);

    return ret;
}

(1) 缺省 HRTIMER_NORESTART。 连周期 timer 也是。这不是 bug,是设计:周期 timer 的下一个到期点由「信号被取走」那一刻决定,不在回调里。后果是 jitter 取决于信号投递时机,好处是信号堆积时不会把一堆到期点全烧掉。

(2) container_of 把嵌入的 hrtimer 换成外层 k_itimer。 这就是第四章「it.real.timer 嵌在 k_itimer 里」的实际用途。

(3) si_private 挂到 pending 位。 周期 timer 才走这行。++it_requeue_pending 同时做两事:LSB 置 1 表示「信号已在 pending 队列」,高位加一作为这一轮的序号。

(4) posix_timer_event 落到 send_sigqueue:

c
int send_sigqueue(struct sigqueue *q, struct task_struct *t, int group)
{
    ...
    ret = 0;
    if (unlikely(!list_empty(&q->list))) {     /* 已经在 pending 队列 */
        q->info.si_overrun++;                  /* 只加计数 */
        return ret;
    }
    q->info.si_overrun = 0;                    /* 首次挂入,计数归零 */
    pending = group ? &t->signal->shared_pending : &t->pending;
    list_add_tail(&q->list, &pending->list);
    sigaddset(&pending->signal, sig);
    complete_signal(sig, t, group);            /* 置 TIF_SIGPENDING */
    ...
}

list_empty(&q->list) 是 overrun 机制的支点。每个 k_itimer 只带一个 sigqueue,所以同一个 timer 在任一瞬间最多有一个信号在队列里。第二个周期到期时不排队,只把 si_overrun 加一。这就是 POSIX timer 不会把 pending 队列撑爆的原因。

2、周期 timer 的 restart 在哪 #

在 dequeue_signal() 里:

c
int dequeue_signal(struct task_struct *tsk, sigset_t *mask, siginfo_t *info)
{
    ...
    if ((info->si_code & __SI_MASK) == __SI_TIMER && info->si_sys_private) {
        spin_unlock(&tsk->sighand->siglock);
        do_schedule_next_timer(info);
        spin_lock(&tsk->sighand->siglock);
    }
    return signr;
}

信号一旦被取走,si_sys_private 非零说明这是周期 timer 的一轮,于是:

c
static void schedule_next_timer(struct k_itimer *timr)
{
    struct hrtimer *timer = &timr->it.real.timer;

    if (timr->it.real.interval.tv64 == 0)     /* one shot,直接返回 */
        return;

    timr->it_overrun += (unsigned int)hrtimer_forward(timer,
                            timer->base->get_time(),
                            timr->it.real.interval);   /* 推到 now 之后 */
    timr->it_overrun_last = timr->it_overrun;          /* 快照 */
    timr->it_overrun = -1;                             /* 重置 */
    ++timr->it_requeue_pending;                        /* 清 LSB,换私有数据 */
    hrtimer_restart(timer);
}

it_overrun = -1 和第五章 timer_create 的初值一致,佐证 -1 是「重新开始计数」的哨兵。但 hrtimer_forward 的返回值又会加到 -1 上,所以计数是「上次快照 + 本轮新增 - 1」,细读有点绕;原文没解释,我按字面照抄,不动它的语义。

3、信号什么时刻真正投递 #

软中断里只做到「挂进 pending 队列 + 置 TIF_SIGPENDING」。真正调用用户 handler 在返回用户态之前,do_work_pending 检查:

c
#define _TIF_WORK_MASK  (_TIF_NEED_RESCHED | _TIF_SIGPENDING | _TIF_NOTIFY_RESUME)

_TIF_SIGPENDING 置位就 do_signal() → dequeue_signal() → 用户 handler。所以从「硬件中断」到「handler 开始跑」,中间隔着:softirq 排队、调度时机、返回用户态检查。这段延迟就是 SIGEV_SIGNAL 型 POSIX timer 的实际精度上限,和 clock_getres 报的纳秒级没关系。

text
CPU 时钟事件中断
  → clock_event_device->event_handler == hrtimer_interrupt
    → __hrtimer_run_queues(now)
      → 取 base->active 最左节点,到期就 __run_hrtimer
        → timer->function == posix_timer_fn
          → ++it_requeue_pending (周期 timer)
          → posix_timer_event → send_sigqueue
              → 首次:list_add_tail(sigq) + sigaddset + complete_signal
              → 重复:si_overrun++ 仅此而已
          → 返回 HRTIMER_NORESTART
  → softirq/irq 返回路径检查 TIF_SIGPENDING
    → do_signal → dequeue_signal
      → si_code == SI_TIMER && si_sys_private
        → schedule_next_timer → hrtimer_forward + hrtimer_restart
      → 调用用户 signal handler

clockid_t 不是简单枚举。内核拆成「负数走特殊路径,非负数查表」:

c

{

        return (id & CLOCKFD_MASK) == CLOCKFD ?
               &clock_posix_dynamic : &clock_posix_cpu;
    if (id >= MAX_CLOCKS || !posix_clocks[id].clock_getres)
        return NULL;

}

#define CLOCK_MONOTONIC             1
#define CLOCK_PROCESS_CPUTIME_ID    2
#define CLOCK_THREAD_CPUTIME_ID     3
#define CLOCK_MONOTONIC_RAW         4

#define CLOCK_MONOTONIC_COARSE      6

负值那一路:高 29 位放 pid 或 fd,bit 2 区分进程 clock 与线程 clock,bit 1:0 区分 PROF=0 / VIRT=1 / SCHED=2 / FD=3。CPU-time clock 的 pid 存的是反码,保证 clockid 是负数,这样 id < 0 才能一刀切开。

MONOTONIC_RAW 和两个 *_COARSE 最值得警惕:它们根本没有 .timer_create。POSIX Clock 篇的原话是「该 clock 没有 timer 相关的 callback 函数」。所以「任意 clock 都能建 timer」是错的。

CLOCK_BOOTTIME 的 hrtimer base 是专用 base,计数含 suspend 时间;CLOCK_REALTIME 的 base 会被 settimeofday 影响。搞定时器时优先选 MONOTONIC,这是选 clock 的第一条经验。

十一、从 POSIX timer 到 hrtimer（补写） #

本章起四章为补写。 原系列第(十一)篇「高精度 timer / hrtimer」在仓里缺失,我们只从第(二)篇「软件架构」拿到两条事实:hrtimer 按红黑树组织;低精度模式下每个 tick 调 hrtimer_run_queues() 扫过期,高精度模式下 clock event 的 handler 换成 hrtimer_interrupt()。以下按 hrtimer.c 补,3.x/4.x 形态一致的部分不单独标注。

1、hrtimer 是什么形状 #

c
/* 3.x 形态,4.x 之后 ktime_t 变成 s64,.tv64 访问被移除 */
struct hrtimer {
    struct timerqueue_node      node;        /* 红黑树节点 */
    ktime_t                     _softexpires;
    enum hrtimer_restart      (*function)(struct hrtimer *);
    struct hrtimer_clock_base   *base;
    unsigned char               state;
};

三个字段撑起全部语义。node 是红黑树里的位置,键是 node.expires(硬到期时间)。_softexpires 是软到期时间,二者可以不等:expires > _softexpires 时,timer 在 _softexpires 之后、expires 之前的任意时刻被触发都不算错,这是给合并唤醒留的窗口,hrtimer_start_range_ns() 才有这个参数,hrtimer_start() 传 0 表示两者相等。state 低几位是状态位(HRTIMER_STATE_INACTIVE / ENQUEUED / CALLBACK / MIGRATING / PINNED),高位是 base 索引,hrtimer_active() 一行就能判完。

POSIX timer 用的 hrtimer 通过 hrtimer_init(&timr->it.real.timer, timr->it_clock, mode) 初始化,位置在 k_itimer.it.real.timer。它不是独立分配的对象,是 k_itimer 的成员,所以 timer_delete 不能随手 free,第八章那条 RCU 路径就是为此。

2、从「设个时间」到「硬件知道」 #

text
hrtimer_start_range_ns(timer, tim, delta_ns, mode)
  1. 把 REL 转 ABS:tim = ktime_add(tim, base->get_time())
  2. 锁 base->cpu_base->lock
  3. 若已 ENQUEUED:摘下来(顺手 enqueue_hrtimer + reprogram)
  4. 设置 timer->node.expires = tim,_softexpires = tim - delta_ns
  5. 按 base 类型(single/multiple)记下发到哪几个 base
  6. 若新到期点比该 base 当前最早的那个还早:
       - 在 base 所在 CPU 上跑 → 直接 reprogram
       - 不在本 CPU → 发 IPI,让对方 clock event 重新编程
  7. enqueue_hrtimer + hrtimer_reprogram

第 6 步是性能关键,也是「跨 CPU 设 timer 为什么贵」的答案:你在这颗 CPU 上给另一颗 CPU 的 timer 设了更早的到期点,唯一办法是发 IPI 把人叫醒去改自己的硬件寄存器。3.x 的 irq_work 机制就是为「硬中断上下文里不能直接编程硬件、但又必须尽快编程」这类场景准备的。

第 7 步的 hrtimer_reprogram() 是上下半场的接缝:

c
/* 语义示意,非逐字原文 */
static int hrtimer_reprogram(struct hrtimer *timer, bool reprogram)
{
    struct hrtimer_cpu_base *cpu_base = ...;
    struct hrtimer_clock_base *base = timer->base;
    struct clock_event_device *dev = cpu_base->clock_base[...].clock_base...;
    ktime_t expires = ktime_sub(timer->node.expires, base->offset);

    if (expires < cpu_base->expires_next) {          /* 比已编程的还早 */
        ...
        res = tick_program_event(expires, 1);
        if (!res) cpu_base->expires_next = expires;
    }
    return res;
}

tick_program_event(expires, force) 一路跳到 clockevents_program_event() → dev->set_next_event(delta, dev),到这里变成对具体硬件寄存器的写。ARM Generic Timer 的 set_next_event 写 CNTP_TVAL/CNTV_TVAL(第十七章)。这是全篇唯一一个「软件时间」变「硬件比较值」的地方。

base->offset 这个减法要留意:ktime_get() 返回的是统一视角的时间,硬件只认某一个 base 的绝对值,差值就压在这个 offset 里。

3、两种运行模式 #

模式 谁推进 触发点 精度
低精度 hrtimer_run_queues() 每个周期性 tick 的软中断 一个 tick(HZ=100 时 10ms)
高精度 hrtimer_interrupt() clock event 的单次编程中断 硬件分辨率(ns 级)

切换发生在 hrtimer_switch_to_hres(),由周期性 tick 的软中断上下文发起,条件是 clock event 支持 CLOCK_EVT_FEAT_ONESHOT。切换后 tick device 的 event_handler 从 tick_handle_periodic 换成 hrtimer_interrupt,并注册一个 tick_sched_timer 模拟原来的周期 tick——第(二)篇原话是「当下一次 tick 到来的时候,系统会调用 hrtimer_interrupt 来处理这个 tick(该 tick 是通过 sched timer 产生的)」。

对写应用的人,这一小节的实际意义:CLOCK_REALTIME 上 POSIX timer 的精度不是恒定的。没有 one shot clock event 的平台(老硬件、虚拟机上常见)整个系统跑在低精度模式,timer_settime 的精度就是 HZ 的倒数。

十二、hrtimer 的组织：per-CPU 红黑树（补写） #

1、两级结构 #

c

    struct timerqueue_head    active;      /* 红黑树根 + 最左缓存 */
    ktime_t                   (*get_time)(void);
    ktime_t                   offset;
};

struct hrtimer_cpu_base {
    raw_spinlock_t            lock;
    unsigned int              cpu;
    unsigned int              active_bases;  /* 哪些 base 非空,位图 */
    unsigned int              clock_was_set_seq;
    unsigned int              hres_active : 1;
    unsigned int              in_hrtirq : 1;
    unsigned int              hang_detected : 1;
    ktime_t                   expires_next;
    int                       nr_events;
    int                       nr_retries;
    int                       nr_hangs;
    unsigned int              max_hang_time;
    struct hrtimer_clock_base clock_base[HRTIMER_MAX_CLOCK_BASES];
};

static DEFINE_PER_CPU(struct hrtimer_cpu_base, hrtimer_bases);

一个 CPU 一个 hrtimer_cpu_base,里面再按 base 类型分几棵树。每个 base 一棵红黑树,active 是 timerqueue_head,除了树根还缓存最左节点——取「最早到期」是 O(1),插删是 O(log n)。

2、为什么必须有 active_bases #

per-CPU 红黑树设计里最省事的一笔。每个周期 __hrtimer_run_queues() 不必遍历所有 base,只看位图里置位的那些:

c
/* 语义示意 */
if (cpu_base->active_bases & (1 << HRTIMER_BASE_MONOTONIC)) { ... }
if (cpu_base->active_bases & (1 << HRTIMER_BASE_REALTIME))  { ... }
if (cpu_base->active_bases & (1 << HRTIMER_BASE_BOOTTIME))  { ... }
if (cpu_base->active_bases & (1 << HRTIMER_BASE_TAI))       { ... }

空树占的空间是零,跳过的成本是一条 and 加一条分支。系统里绝大多数 hrtimer 挂在 MONOTONIC,TAI 常年为空,位图让这个不对等变得免费。

3、offset 的用处 #

REALTIME 和 TAI 这两个 base 的 offset 不是零,指向 MONOTONIC。理由:settimeofday 一改墙上时间,如果直接把 REALTIME 树上所有 key 重算一遍,代价是 O(n) 且要持锁很久。改成在 base 上记一个偏移量,所有 key 一个动作就整体位移。时间被调整那一下还要 hrtimer_clock_was_set() 把 expires_next 全置失效,让每颗 CPU 重新编程——否则硬件比较值还停在旧时间轴上。

4、timerqueue_node 与「红黑树 + 最左缓存」 #

hrtimer 的 node 类型是 struct timerqueue_node { struct rb_node node; ktime_t expires; },红黑树用 expires 当键。timerqueue_head 除了 rb_root 还带 rb_leftmost。timerqueue_add() 维护 rb_leftmost 的时机只有一种:新节点的键比当前最左还小。

这套实现在内核里出现三次:CFS 调度器的 tasks_timeline、高精度定时器、timerqueue。同一个模式反复出现,是因为它匹配的正是「有序 + 频繁插删 + 频繁取最小」这个负载。

十三、hrtimer 的到期处理与回调分发（补写） #

1、中断入口 #

c
/* 语义示意,非逐字原文 */
void hrtimer_interrupt(struct clock_event_device *dev)
{
    struct hrtimer_cpu_base *cpu_base = this_cpu_ptr(&hrtimer_bases);
    ktime_t expires_next;
    int ret;

    raw_spin_lock(&cpu_base->lock);
    cpu_base->in_hrtirq = 1;
    cpu_base->expires_next = KTIME_MAX;

retry:
    expires_next = __hrtimer_run_queues(cpu_base, ktime_get(),
                                        HRTIMER_ACTIVE_ALL, expires_next);
    ...
    if (expires_next > now) {
        if (expires_next < KTIME_MAX)
            tick_program_event(expires_next, 0);
        ...
    } else {
        /* 到期点已经过了,再跑一轮,防漏 */
        retry++;
        if (retry >= 3) { ... 记录 nr_hangs ... }
        goto retry;
    }

    raw_spin_unlock(&cpu_base->lock);
    cpu_base->in_hrtirq = 0;
}

三点。

重来三轮。 处理完一轮之后如果「下一个到期点」已经过去了(中断处理本身花的时间超过一个周期),不能就这么返回——那样会立刻再次中断,而中间会漏掉好多 timer。所以回到开头再跑一轮,最多三轮,三轮还追不上就记账(nr_hangs、max_hang_time),然后放弃本轮让下一轮中断收尾。

进出锁用 raw 版。 hrtimer 在 -rt 内核里也要保持真正的自旋语义,用 raw_spin_lock 把优先级继承之类的机制挡在外面。

回调不在锁里跑。 __run_hrtimer() 把 timer 从树上摘下来、标成 HRTIMER_STATE_CALLBACK,然后放锁调 fn(timer):

c
/* 语义示意 */
raw_spin_unlock_irq(&base->cpu_base->lock);
restart = fn(timer);
raw_spin_lock_irq(&base->cpu_base->lock);

因为放锁了,回调里可以自由地 hrtimer_start/hrtimer_cancel 自己或其他 timer。也因为放锁了,timer 对象在回调执行期间不能被释放——HRTIMER_STATE_CALLBACK 位就是给 hrtimer_cancel 用的信号:「这个还在跑,等着」。

2、__hrtimer_run_queues 的循环 #

c
/* 语义示意 */
static ktime_t __hrtimer_run_queues(struct hrtimer_cpu_base *cpu_base,
                                    ktime_t now, unsigned int active_mask,
                                    ktime_t expires_next)
{
    struct hrtimer_clock_base *base;
    unsigned int active = cpu_base->active_bases & active_mask;

    for_each_active_base(base, cpu_base, active) {
        ktime_t basenow = ktime_add(now, base->offset);

        while ((timer = timerqueue_getnext(&base->active))) {
            if (basenow < timer->node.expires)
                break;
            __run_hrtimer(cpu_base, base, timer, &basenow);
        }
        /* 更新 expires_next */
    }
    return expires_next;
}

basenow = now + base->offset,第十二章那个 offset 在这里被吃掉。内层 while 是「把这棵树上已经过期的全跑完」——注意 __run_hrtimer 里放过锁,这期间用户回调往树上插了新节点,timerqueue_getnext 每轮重取是对的。

3、低精度模式的分支 #

c
void hrtimer_run_queues(void)
{
    struct hrtimer_cpu_base *cpu_base = this_cpu_ptr(&hrtimer_bases);

    if (__hrtimer_hres_active(cpu_base))
        return;                                   /* 高精度下不归你管 */
    __hrtimer_run_queues(cpu_base, ktime_get(), HRTIMER_ACTIVE_ALL, KTIME_MAX);
}

第一句 return 保证高精度模式下不会有两套路径同时扫队列——重复执行会让 posix_timer_fn 跑两次,overrun 计数直接失真。

4、回调返回值 #

c
enum hrtimer_restart {
    HRTIMER_NORESTART,   /* 不重新入队 */
    HRTIMER_RESTART,     /* 重新入队,用当前 node.expires */
};

__run_hrtimer() 拿到返回值后:NORESTART 什么都不做,state 清回 INACTIVE;RESTART 要检查 timer->state & HRTIMER_STATE_ENQUEUED 并确认 expires 已被推进——如果回调里没调过 hrtimer_forward(),expires 还停在刚才那个过期点,直接重新入队会和当前时间一起再次过期,形成死循环。所以那个检查是硬性的,不通过就报错且不重新入队。

POSIX timer 的 posix_timer_fn 默认返回 HRTIMER_NORESTART,第九章已解释周期由 dequeue_signal 那条路推。正因如此,POSIX timer 永远不踩这个坑——它压根不在这条路上重入队。

5、取消与重编 #

hrtimer_cancel() 的语义是「保证回调已经跑完」:先 hrtimer_try_to_cancel(),失败(说明 CALLBACK 位置位、回调正在别的 CPU 或本 CPU 的软中断里跑)就 wait_for_hrtimer() 等。hrtimer_try_to_cancel() 反过来只试一次。第六章 common_timer_set 用的是后者,所以才有 TIMER_RETRY 这条重试路径——timer_settime 不睡眠等回调,而是让 syscall 层重来。取消之后如果摘掉的是树上最左节点,必须 hrtimer_reprogram() 重新编程硬件,否则硬件还会在那个已经不存在的到期点上来一次中断。

十四、为什么 POSIX timer 最终落在 hrtimer 上 #

把前面十三章拼起来,答案由三个约束推出来。

约束一:精度不能由 tick 决定。 用户填的是 struct timespec,纳秒字段随便写。如果底层是 timer_list(jiffies 精度),it_value.tv_nsec 会被抹成 tick 的倍数——那和 setitimer 就没区别了,POSIX timer 存在的第一个理由就没了。要撑住 ns 级设定,底层必须能吃「绝对时间点」并在任意时刻编程硬件,只有 hrtimer + one shot clock event 这一条路。

约束二:一个进程可以开成百上千个 timer。 固定个数的硬件比较器不够,必须软件排队。hrtimer 的红黑树就是那个队列,插入和取最早都是对数或常数级。it.real.timer 直接嵌在 k_itimer 里,timer_create 只付一次 k_itimer 的分配,timer_settime 只在树上做一次插删。

约束三:到期处理不能睡眠。 POSIX timer 的到期回调要发信号,而 send_sigqueue/complete_signal 全程持 siglock,不能睡。hrtimer 回调在中断上下文、放掉 base 锁之后执行,正好;timer_list 的软中断上下文也能满足,但精度不行。两个约束的交集只剩 hrtimer。

于是整条纵贯线的关键节点固定下来:

十五、ARM Generic Timer 的硬件结构 #

为什么 ARM 要把 timer 做进核里?原文开头那段吐槽值得抄:单核时代各 SOC vendor 自己设计 timer 外设,五花八门,而 Linux 时间子系统对硬件只有两条要求——一个 free running 的 counter,加一个「能在指定 counter 值上产生中断」的能力。有良心的厂商(PXA270)把两条都做齐,没良心的(S3C2451)做得不够,写驱动时恨不得把硬件设计人员拉出来打。多核时代 ARM 在 Cortex A15 的 MPcore 里给了 Generic Timer,取代 A9 的 global timer + private timer。

1、三个 block #

text
        ┌──────────────────────────────────────┐
        │        System Counter (SOC 级)       │
        │  CNTFRQ 定频率, CNTPCT 不断累加      │
        └───────┬──────────────┬───────────────┘
                │ 广播 counter 值 │
        ┌───────▼──────┐  ┌────▼─────────┐
        │ Timer @ CPU0 │  │ Timer @ CPU1 │ …
        │ CompareValue │  │ CompareValue │
        │ TimerValue   │  │ TimerValue   │
        │ 控制寄存器    │  │ 控制寄存器    │
        └───────┬──────┘  └────┬─────────┘
                │ PPI           │ PPI
        ┌───────▼───────────────▼───────────┐
        │              GIC                  │
        └───────────────────────────────────┘

三块各自的职责:System counter 是 SOC 上的一份,多核共享,输入时钟每跳一次加一,初值 0,它的值必须广播到各 CPU 的 timer 上,保证所有 timer 看到同一个时间轴;Timer(per CPU)拿 system counter 的当前值和自己的 CompareValue 比,追上就 assert 一根输出信号,接进 GIC 当 PPI;接口电路 管各个 CPU 的 timer 之间、timer 和 system counter 之间的交互。

2、两个 domain 是设计出来的 #

power domain:System counter 一份,per-CPU timer 一份。省电时可以关掉 CPU 及其 timer 的供电,但保留 system counter——系统时间不会因为 CPU 睡了就丢。这是「counter 是 SOC 级、timer 是 per-CPU 级」的原始动机。

clock domain:system counter 和 processor 跑在不同时钟上。软件改 CPU 频率(DVFS)不影响 system counter 的节奏,也就不会改变 timer 的行为。这条对写驱动的人很实在:你不用在 cpufreq 的 callback 里重算 timer 的 compare value。

3、event stream #

ARMv7 有 wait for event 机制,CPU 可以进低功耗等 event。event 来自另一颗核的 SEV 指令,或来自外部硬件——system counter 就能产生。配置项两个:选哪一位翻转算 event(低 16 位可选),以及 0→1 还是 1→0 翻转算 event。选 bit 0,event stream 频率极高;选 bit 15,得等 15 位翻转才来一次,频率最慢。这个功能在内核里由 CONFIG_ARM_ARCH_TIMER_EVTSTREAM 打开,arch_timer_configure_evtstream() 配置,和第十七章 arch_timer_setup() 末尾两句对得上。

十六、四个系统寄存器：CNTFRQ / CNTPCT / CNTVCT / CNTP_CVAL #

先区分两族:CNTFRQ、CNTPCT、CNTVCT 属于 system counter 侧;CNTP_CVAL/CNTP_TVAL/CNTP_CTL 属于某个 timer 侧(下面以 physical timer 为例,换成 V 就是 virtual timer)。

寄存器 宽度 位置 读/写 作用
CNTFRQ 32 system counter 读写(固件写死后实为只读) counter 的输入时钟频率,Hz
CNTPCT_EL0 64 system counter 只读 physical counter 当前值
CNTVCT_EL0 64 system counter 只读 virtual counter 当前值
CNTP_CVAL 64 per-CPU timer 读写 physical timer 的比较值(绝对)
CNTP_TVAL 32 per-CPU timer 读写 physical timer 的倒计数(相对)
CNTP_CTL 32 per-CPU timer 读写 ENABLE / IMASK / ISTATUS

几点必须说清。

CNTPCT 与 CNTVCT 的关系。 没有 security extension 和 virtualization extension 的系统上,二者就是同一个值。有虚拟化时,hypervisor 通过 CNTVOFF 给 virtual counter 加偏移,让 guest 看到的时间轴从它自己的起点算起。驱动里读 counter 的默认选择是 virtual(arch_counter_get_cntvct()),因为 host 和 guest 都能读它。

CNTP_CVAL 是绝对比较值,不是倒计时。 语义是「counter 追平这个值就触发」,写进去的必须比当前 counter 大。CNTP_TVAL 才是相对量:写 1000 表示「1000 个 tick 之后触发」,硬件内部换算成 CVAL = CNTPCT + 1000。用 TVAL 的好处是不用先读 counter 再加,省一次寄存器访问,而且不会因为读 counter 和写 CVAL 之间的延迟引入误差。

CNTPCT 是 64 位且单调递增,但不是「永不上翻」。 驱动注册 clocksource 时给的是 CLOCKSOURCE_MASK(56),按 56 位算。为什么不是 64:56 位 @ 24MHz 约 87 年,已超过「系统不重启」的实操寿命;而且取 56 位让 mult/shift 的计算落在 u32 * u32 的安全范围内,不必走 128 位中间结果。sched_clock_register(arch_timer_read_counter, 56, arch_timer_rate) 里的 56 是同一个数。

控制寄存器三位。 ENABLE(该 timer 是否工作)、IMASK(输出信号是否被屏蔽)、ISTATUS(当前是否已到期,只读)。set_next_event 完成后要把 ENABLE 置 1、IMASK 清 0,否则比较值追平了也没有中断。

中断号是 PPI。 每个 CPU 的 timer 中断只送达自己那颗核,所以是 PPI 而不是 SPI。Cortex A15 的 PPI 编号在 DT 里是 13/14/11/10 四个(见第十八章的 RK3288 节点),分别对应 secure physical / non-secure physical / virtual / hyp physical timer。

十七、ARM timer 驱动的 probe 与初始化 #

1、入口不在 probe 在 section #

这个驱动没有平台 driver 的 probe,它靠 CLOCKSOURCE_OF_DECLARE 把初始化函数塞进一个专用 section,由 time_init() 主动扫:

c
#define CLOCKSOURCE_OF_DECLARE(name, compat, fn)                    \
    static const struct of_device_id __clksrc_of_table_##name       \
        __used __section(__clksrc_of_table)                         \
        = { .compatible = compat,                                    \
            .data = (fn == (clocksource_of_init_fn)NULL) ? fn : fn }

CLOCKSOURCE_OF_DECLARE(armv7_arch_timer,     "arm,armv7-timer",     arch_timer_init);
CLOCKSOURCE_OF_DECLARE(armv8_arch_timer,     "arm,armv8-timer",     arch_timer_init);
CLOCKSOURCE_OF_DECLARE(armv7_arch_timer_mem, "arm,armv7-timer-mem", arch_timer_mem_init);

原文有个观察值得记:compatible 用的是 armv7/armv8 而不是 Cortex A15,说明 ARM 认为 generic timer 是指令集级别的设施。这也解释了驱动为什么从 arch/arm/ 搬到 drivers/clocksource/——ARM 和 ARM64 共用一份。v7 和 v8 走同一个 arch_timer_init,差别在 PPI 的数量和编号,由 DT 提供,代码不用分叉。

两种访问形态是这篇反复出现的主题:

形态 compatible 初始化函数 访问方式 能力
CP15 timer arm,armv7-timer / arm,armv8-timer arch_timer_init 协处理器 mrc/mcr(ARM64 上 mrs/msr) 只碰 per-CPU timer
MMIO timer arm,armv7-timer-mem arch_timer_mem_init readl_relaxed 等 能碰 system counter

为什么两种都要有?原文给了两条。一,CP15 方式控制不到 system counter——counter 是 SOC 级的,只能 MMIO。而 system counter 有一张 frequency table,能按电源状态切输入频率和每个 clock 的增量,这类配置绕不开 MMIO。二,有些系统根本不允许协处理器访问,那就只能全部走 MMIO,慢一点但至少功能齐。

2、time_init 与 clocksource_of_init #

c
void __init time_init(void)
{
    if (machine_desc->init_time) {
        machine_desc->init_time();
    } else {
#ifdef CONFIG_COMMON_CLK
        of_clk_init(NULL);
#endif

void __init clocksource_of_init(void)
{
    struct device_node *np;
    const struct of_device_id *match;
    clocksource_of_init_fn init_func;
    unsigned clocksources = 0;

    for_each_matching_node_and_match(np, __clksrc_of_table, &match) {
        if (!of_device_is_available(np))
            continue;
        init_func = match->data;
        init_func(np);
        clocksources++;
    }

    if (!clocksources)
        pr_crit("%s: no matching clocksources found\n", __func__);
}

两条路:老式 machine driver 自己提供 init_time,新式走 DT。clocksource_of_init 扫 __clksrc_of_table,逐个拿 compatible 和 DT 里所有节点比对,命中就把节点的 np 传给驱动的初始化函数。这一步发生在 start_kernel 里,比任何驱动的 probe 都早——时间子系统必须先有 clock,别的东西才能用时间。

(2) 四条 PPI 全拿下。 irq_of_parse_and_map(np, i) 按 DT interrupts 属性的索引解析并建立映射,结果存进 arch_timer_ppi[]。四个索引对应 secure physical / non-secure physical / virtual / hyp physical。

(3) 定频率。 见第 5 小节。

(4) 选 physical 还是 virtual。 两个条件任一成立就强制走 physical:is_hyp_mode_available()(系统本身在 HYP 模式,比如 host 上跑了 KVM),或 DT 里没给 virtual PPIs。强制 physical 之后必须保证 secure 和非 secure 两个 physical PPI 都在,缺一个就放弃——这种情况下 timer 起不来,time_init 的 clock 就没了。virtual timer 是留给 guest 的,host 不该抢。

(5) 注册。 见第 4 小节。

(6) 公共部分。 见第 6 小节。

4、arch_timer_register #

c
static int __init arch_timer_register(void)
{
    int err;
    int ppi;

    arch_timer_evt = alloc_percpu(struct clock_event_device);   /* (a) */

    if (arch_timer_use_virtual) {                               /* (b) */
        ppi = arch_timer_ppi[VIRT_PPI];
        err = request_percpu_irq(ppi, arch_timer_handler_virt,
                                 "arch_timer", arch_timer_evt);
    } else {
        ppi = arch_timer_ppi[PHYS_SECURE_PPI];
        err = request_percpu_irq(ppi, arch_timer_handler_phys,
                                 "arch_timer", arch_timer_evt);
        if (!err && arch_timer_ppi[PHYS_NONSECURE_PPI]) {
            ppi = arch_timer_ppi[PHYS_NONSECURE_PPI];
            err = request_percpu_irq(ppi, arch_timer_handler_phys,
                                     "arch_timer", arch_timer_evt);
        }
    }

    err = register_cpu_notifier(&arch_timer_cpu_nb);            /* (c) */
    err = arch_timer_cpu_pm_init();                             /* (d) */
    arch_timer_setup(this_cpu_ptr(arch_timer_evt));             /* (e) */
    return 0;
}

(a) per-CPU 分配。 clock_event_device 不是全局一份,是每核一份。因为硬件也是每核一份,system counter 只有一份。

(b) per-CPU IRQ。 request_percpu_irq 与 request_irq 的差别是前者注册一次、全核生效,handler 里用 this_cpu_ptr() 取本核 context。对 per-CPU timer 这是正确的抽象:中断是 PPI,只落到它自己那颗核。

(c) CPU 热插拔。 BSP 之外的核在 bringup 时才初始化自己的 timer,靠 arch_timer_cpu_nb 这个 notifier。

(d) 电源管理。 进/出低功耗时 reprogram。

(e) BSP 的 setup。 只有这一句立即生效,其余核等 notifier。

5、frequency 从哪来 #

c
static void arch_timer_detect_rate(void __iomem *cntbase, struct device_node *np)
{
    if (of_property_read_u32(np, "clock-frequency", &arch_timer_rate)) {
        if (cntbase)
            arch_timer_rate = readl_relaxed(cntbase + CNTFRQ);
        else
            arch_timer_rate = arch_timer_get_cntfrq();
    }
}

优先级是 DT 属性 > 寄存器。cntbase 非空说明是 MMIO 形态,直接 readl;为空说明 CP15 形态,走 arch_timer_get_cntfrq()。arch_timer_rate 是全局变量,注册 clocksource 和 sched_clock 都要用。为什么优先 DT?有些片上 CNTFRQ 是固件写错的,或者根本没写,DT 里给一个权威值更可靠。

6、arch_timer_common_init #

c
static void __init arch_timer_common_init(void)
{
    unsigned mask = ARCH_CP15_TIMER | ARCH_MEM_TIMER;           /* (a) */

    if ((arch_timers_present & mask) != mask) {
        if (of_find_matching_node(NULL, arch_timer_mem_of_match) &&
            !(arch_timers_present & ARCH_MEM_TIMER))

(a) 这段代码只跑一次,即便系统里两种 timer 都有。理由:system counter 是 system level 的,只有一份,注册一次就够。所以先初始化的那个会「等一下」——DT 里还挂着另一种 timer 节点而它还没 init,就直接 return,让后一个来跑公共部分。

c
/* 语义示意 */
static inline void arch_timer_reg_write_cp15(int access, enum arch_timer_reg reg, u32 val)
{
    if (access == ARCH_TIMER_PHYS_ACCESS) {
        switch (reg) {
        case ARCH_TIMER_REG_CTRL: write_sysreg(val, cntp_ctl_el0); break;
        case ARCH_TIMER_REG_TVAL: write_sysreg(val, cntp_tval_el0); break;
        }
    } else if (access == ARCH_TIMER_VIRT_ACCESS) {
        switch (reg) {
        case ARCH_TIMER_REG_CTRL: write_sysreg(val, cntv_ctl_el0); break;
        case ARCH_TIMER_REG_TVAL: write_sysreg(val, cntv_tval_el0); break;
        }
    }
}

一行 write_sysreg 最终落成一条 msr cntv_tval_el0, x0。从 timer_settime 到这条指令,中间隔了十几次函数调用和一次红黑树插删——这就是第十四章那条链路底部的样子。

1、RK3288 的 CP15 timer 节点 #

四行 interrupts 的顺序就是驱动 arch_timer_ppi[] 的索引顺序:

0 13 secure physical timer
1 14 non-secure physical timer
2 11 virtual timer
3 10 non-secure hyp physical timer

GIC_CPU_MASK_SIMPLE(4) 表示这颗 GIC 有 4 个 CPU interface 都收这个 PPI;IRQ_TYPE_LEVEL_HIGH 是电平触发。clock-frequency = <24000000> 是 24MHz 的 system counter 输入频率——第十六章说 56 位 @ 24MHz 约 87 年,数字就是从这类节点来的。

2、msm8974 的 MMIO timer 节点 #

dts
timer@f9020000 {
    #address-cells = <1>;
    #size-cells = <1>;
    ranges;
    compatible = "arm,armv7-timer-mem";
    reg = <0xf9020000 0x1000>;          /* system counter 的寄存器 */

    clock-frequency = <19200000>;

    frame@f9021000 {                    /* per-CPU timer,最大 8 个 frame */
        frame-number = <0>;
        interrupts = <0 8 0x4>,         /* physical timer 中断 */
                     <0 7 0x4>;         /* virtual timer 中断 */
        reg = <0xf9021000 0x1000>,      /* first view base address */
              <0xf9022000 0x1000>;      /* second view base address */
    };

};

父节点的 reg 指向 system counter,子节点 frame@ 才是 per-CPU timer。每个 frame 两个 view:一个给 physical timer,一个给 virtual timer——MMIO 形态下访问不同 timer 要不同基址,不像 CP15 那样一个 mrc 换寄存器编号就行。frame-number 决定这块 timer 归哪颗 CPU,原文注「目前最大支持 8 个 frame」,对应 8 核上限;这个 8 是 3.14 驱动里的实现上限,新内核改过没有,未验证。

3、freq 的来源与顺序 #

第十八章第一节那两个节点都带 clock-frequency。没带时驱动回落到读 CNTFRQ,顺序就是第十七章第 5 小节那段代码:DT 属性 > 寄存器。CP15 形态的 arch_timer_get_cntfrq() 语义上是一条 mrc p15, 0, %0, c14, c0, 0(ARMv7 写法),ARMv8 换成 mrs %0, cntfrq_el0。对应关系按原文「通过协处理器来获取」理解,具体汇编原文没给,未验证。CNTFRQ 是 32 位,最大 4.29GHz,对 system counter 的输入频率绰绰有余。

4、ACPI 一侧 #

3.14 的 arm_arch_timer.c 只有 OF 匹配路径,没有 ACPI。ARM64 服务器上用 ACPI 的 GTDT 表描述 generic timer 是后来加的。两条路径拿到的信息同构:DT 的 clock-frequency 对应 GTDT 的 CntFrq,DT 的四条 PPI 对应 GTDT 的 SecurePl1TimerGSIV/NonSecurePl1TimerGSIV/VirtualTimerGSIV/NonSecurePl2TimerGSIV。本节属方向性说明,入口函数名与字段名未逐字核对源码。

十九、怎么注册成 clockevent 与 clocksource #

时间子系统对硬件只有两条要求:一个 free running counter(= clocksource),一个能产生中断的 timer(= clockevent)。ARM generic timer 一份硬件同时供两条。

1、clocksource #

c
static struct clocksource clocksource_counter = {
    .name    = "arch_sys_counter",
    .rating  = 400,
    .read    = arch_counter_read,
    .mask    = CLOCKSOURCE_MASK(56),
    .flags   = CLOCK_SOURCE_IS_CONTINUOUS | CLOCK_SOURCE_SUSPEND_NONSTOP,
};
字段 值 含义
name arch_sys_counter 原文顺带吐槽:clocksource_counter 这变量名起得太差,看不出是 counter
rating 400 精度等级,数字越大越优先
read arch_counter_read 读当前 counter 的函数
mask CLOCKSOURCE_MASK(56) 可用位宽 56,上翻按 56 位算
flags IS_CONTINUOUS | SUSPEND_NONSTOP 不停止、suspend 期间也继续计数

CLOCK_SOURCE_SUSPEND_NONSTOP 和第十五章的 power domain 描述对得上:system counter 在 CPU 掉电时仍在跑,系统从 suspend 回来后 counter 没有断点,timekeeping 不需要额外补偿。

c
static void __init arch_counter_register(unsigned type)
{
    u64 start_count;

    if (type & ARCH_CP15_TIMER)                                    /* (1) */
        arch_timer_read_counter = arch_counter_get_cntvct;
    else
        arch_timer_read_counter = arch_counter_get_cntvct_mem;

    start_count = arch_timer_read_counter();

    clocksource_register_hz(&clocksource_counter, arch_timer_rate); /* (2) */

    cyclecounter.mult   = clocksource_counter.mult;                 /* (3) */
    cyclecounter.shift  = clocksource_counter.shift;
    timecounter_init(&timecounter, &cyclecounter, start_count);

    /* 56 bits minimum, so we assume worst case rollover */
    sched_clock_register(arch_timer_read_counter, 56, arch_timer_rate); /* (4) */
}

(1) arch_counter_read 只是跳板,真正的函数指针 arch_timer_read_counter 在这里按访问形态定。CP15 形态读 CNTVCT,MMIO 形态读映射进来的寄存器。

(2) 传 Hz 而不是周期,由 clocksource 层自己算 mult/shift。这两个数把 counter tick 换算成纳秒(ns = (cycles * mult) >> shift),用整数乘移位代替除法,且能在 u64 范围内保持精度。

(3) cyclecounter 是从 clocksource_counter 抄过来的 mult/shift。clocksource 服务于 timekeeping,timecounter 服务于其他想「读一下 counter 换算成纳秒」的驱动,可以通过 arch_timer_get_timecounter() 拿它再 timecounter_read()。

(4) 调度器需要一个「读一下就能拿到 ns」的快速接口,且任何上下文可用。给它 56 位和 24MHz,回绕自己处理。原文这句标了 TODO,注释本身的意思是「56 位是下限,按最坏情况算回绕」。

2、clockevent_device #

c
static int arch_timer_setup(struct clock_event_device *clk)
{
    __arch_timer_setup(ARCH_CP15_TIMER, clk);   /* 填 clock_event_device 并注册 */

    if (arch_timer_use_virtual)                 /* enable timer interrupt */
        enable_percpu_irq(arch_timer_ppi[VIRT_PPI], 0);
    else {
        enable_percpu_irq(arch_timer_ppi[PHYS_SECURE_PPI], 0);
        if (arch_timer_ppi[PHYS_NONSECURE_PPI])
            enable_percpu_irq(arch_timer_ppi[PHYS_NONSECURE_PPI], 0);
    }

    arch_counter_set_user_access();

    if (IS_ENABLED(CONFIG_ARM_ARCH_TIMER_EVTSTREAM))
        arch_timer_configure_evtstream();       /* event stream,见第十五章 */

    return 0;
}

__arch_timer_setup() 里给 clk 填的关键字段:

c
/* 语义示意 */
clk->name           = "arch_timer";
clk->rating         = 400;
clk->cpumask        = cpumask_of(smp_processor_id());  /* per-CPU */
clk->irq            = ppi;
clk->set_next_event = arch_timer_set_next_event_virt 或 _phys;
clk->set_state_shutdown / set_state_periodic / set_state_oneshot = ...;
clk->features       = CLOCK_EVT_FEAT_ONESHOT;          /* 3.14 形态 */
clockevents_config_and_register(clk, arch_timer_rate, 0xf, 0x7fffffff);

四个字段决定它能干什么:cpumask 只含自己那颗核,tick 层会把它当 local tick device 的候选(第(十二)篇);features 带 CLOCK_EVT_FEAT_ONESHOT,具备进高精度模式的前提,第十三章那个 hrtimer_interrupt 才会被装上;set_next_event 的参数是「多少个 counter tick 之后」,和第十六章 TVAL 语义一致;clockevents_config_and_register 的 0xf 是 min delta,0x7fffffff 是 max delta。

每核注册一次。 BSP 在 arch_timer_register() 里直接调 arch_timer_setup(),其余核在 CPU up 的 notifier 里调。这就是第二十二章那条链路里「每颗核都有自己的 clockevent」的来源。注册之后,tick 层的 tick_check_new_device() 检查它是否比当前的更好(one shot 优先、rating 高优先),决定是否换掉。

二十、ARM timer 的中断处理 #

1、handler 只有三步 #

c
static irqreturn_t arch_timer_handler_virt(int irq, void *dev_id)
{
    struct clock_event_device *evt = this_cpu_ptr(arch_timer_evt);

    evt->event_handler(evt);
    return IRQ_HANDLED;
}

static irqreturn_t arch_timer_handler_phys(int irq, void *dev_id)
{
    struct clock_event_device *evt = this_cpu_ptr(arch_timer_evt);

    evt->event_handler(evt);
    return IRQ_HANDLED;
}

this_cpu_ptr(arch_timer_evt) 不是随便取的:PPI 只送到本核,handler 当然要拿本核 context。这也解释了第十九章为什么用 alloc_percpu。

event_handler 是谁,取决于当前 tick device 的模式:

系统状态 event_handler 干的事
周期性 tick tick_handle_periodic 加 jiffies、跑低精度 timer、必要时 reprogram
NO_HZ / one shot tick_nohz_handler 加 jiffies,pending 时 reprogram
高精度模式 hrtimer_interrupt 扫 hrtimer 各 base,跑到期回调
被替换的旧设备 clockevents_handle_noop 什么都不做

第三行就是本篇上下半场的接缝:POSIX timer 的到期,最终通过这个 event_handler 函数指针跳到 hrtimer_interrupt。

2、中断之后必须重新编程 #

one shot 硬件不会自己再来第二次。tick_handle_periodic 里:

c
void tick_handle_periodic(struct clock_event_device *dev)
{
    ...
    if (dev->mode != CLOCK_EVT_MODE_ONESHOT)
        ...
    if (!clockevents_program_event(dev, next, false))   /* 编程下一个 */
        ...
}

CLOCK_EVT_MODE_ONESHOT 下每次中断都得重编,hrtimer_interrupt 里的 tick_program_event(expires_next, 0) 同理。漏一次 reprogram,系统就再也不会 tick——所以第十三章那个「重试三轮」的循环是保命的,不是可选的优化。

3、arch_timer_stop 与 IMASK #

c
arch_timer_set_ctl(clk, ARCH_TIMER_REG_CTRL, 0);

写 0 意味着 ENABLE=0、IMASK=1。两个都关,是因为不同的硬件实现上只关一个会留下边界情况(比如比较值已经追平、pending 的输出信号还挂在那儿)。arch_timer_set_oneshot() 里写 ARCH_TIMER_CTRL_IT_MASK 而不清 ENABLE,是「先屏蔽输出、等 set_next_event 写好再放开」的两段式——否则写 TVAL/CVAL 那一瞬,旧比较值早已过期会立刻误触发。

4、中断到 handler 之间 #

从 GIC 拉高 PPI 到 arch_timer_handler_virt 被调用,中间是通用 ARM 中断入口:异常向量 → 保存现场 → gic_handle_irq() → handle_domain_irq() → per-CPU IRQ 描述符 → generic_handle_irq()。这一段属于中断子系统,不展开。只留一句实用的:arch_timer_register() 用 request_percpu_irq,enable 要在每颗核上分别做(enable_percpu_irq)。少 enable 一颗核,那颗核就永远不会 tick,表现为「某个 CPU 上时间不动、nohz 统计怪异」,查起来很费时间。

二十一、两种 timer：physical 与 virtual #

1、几颗 timer #

SOC 能力 每核 timer 数 具体
无 security + 无 virtualization extension 2 physical timer、virtual timer(行为等价)
有 security、无 virtualization extension 3 Non-secure physical、Secure physical、virtual
有 virtualization extension 4 Non-secure PL1 physical、Secure PL1 physical、Non-secure PL2 physical、virtual

对 Linux 而言,实际用到的只是其中一颗。选择逻辑在第十七章 arch_timer_init() 那段:is_hyp_mode_available() 或没给 virtual PPI,就强制 physical。

2、physical 与 virtual 的正面对比 #

维度 physical timer virtual timer
寄存器 CNTP_CTL / CNTP_TVAL / CNTP_CVAL / CNTPCT CNTV_CTL / CNTV_TVAL / CNTV_CVAL / CNTVCT
时基 physical counter virtual counter = physical counter − CNTVOFF
PPI(A15 例) secure 13 / non-secure 14 / hyp 10 11
谁用 host(非 HYP 模式)、系统本身在 HYP 时 guest OS、非 HYP 模式下的 host
偏移可调 不可 可以(CNTVOFF 由 hypervisor 写)
访问权限 需要相应特权级 EL0/EL1 可读 counter,高于其特权级才能用

驱动里的分叉点就两个:arch_timer_use_virtual 为真就用 arch_timer_handler_virt + arch_timer_set_next_event_virt,否则两个 physical handler 都注册。

3、为什么不是「无脑用 virtual」 #

两个例外都是硬的。系统本身在 HYP 模式(KVM host):virtual timer 的 PPI 已被 hypervisor 占作他用,host 去抢会冲突,强制 physical。DT 没给 virtual PPI:或是 hardware 没做,或是 firmware 故意不给,强制 physical。反过来,普通 guest 里默认 virtual,因为 CNTVOFF 让 guest 的时间轴从它自己的 epoch 开始,hypervisor 迁移 guest 时调整偏移而不需要改 guest 内核里的任何计时数据。

4、physical 下为什么注册两个 PPI #

arch_timer_register() 里 physical 分支把 secure 和 non-secure 两个 PPI 都 request_percpu_irq 了,用同一个 handler。原因:内核在 secure/non-secure 两种世界里都会跑(取决于启动方式和是否有 secure monitor),但 Linux 自己不知道 DT 里哪个 PPI 真正会来中断,注册两个的成本只是多一条 IRQ 描述符,换来的是不管哪种启动方式都能工作。enable 的时候也是两个都 enable。

四件事在这条线上要看明白:

  1. 三次穿越软件/硬件边界:hrtimer_reprogram 写寄存器下去,中断上来,再 reprogram 写下去。一次 timer_settime 触发的不是一次写,而是「设一个」+「每次到期后改下一次」。
  2. posix_timer_fn 不 restart。周期 timer 的下一枪由 dequeue_signal 那条路推,所以信号被 mask 越久,periodic timer 越像「一枪打一次」,中间欠下的次数进 overrun。
  3. it_lock 在回调里拿了又放,hash_lock 一次没碰(unlock_timer 内部次序)。锁的层次从设计上很扁。
  4. 每颗 CPU 各有一份 hrtimer_cpu_base 和一份 clock_event_device。用户在这颗 CPU 上设的 timer,如果落到另一颗 CPU 的 base 上,中间要多一次 IPI。
