一、如何度量时间：从地球自转走到铯原子 #

时间这个东西和变化绑在一起。没有位移、没有能量交换、一切静止，你也就没有参照去谈「过了多久」。所以人类度量时间的思路一直是：找一个有稳定周期的现象，数它重复了多少次。

第一代选的是天体。地球自转一周切 24 份，一份叫小时；一小时再切 3600 份，一份叫秒。这套定义符合所有人的直觉，一天 24 小时、一小时 60 分钟、一分钟 60 秒，写进日历、写进作息、写进你手腕上的表。

问题在于周期本身不稳。地球自转在变慢，公转也不是恒定值。用平均太阳日的 1/86400 定义秒，等于把一颗正在漂移的星球当成尺子。天体尺度上这点漂移不算什么，落到「纳秒级精度」的计算机里就是灾难。

第二代选的是原子。铯 133 原子在特定能级跃迁时辐射的电磁波频率非常稳定，拿它来定义秒，秒就有了一个与地球自转、公转、季节、纬度都无关的恒定长度。这就是原子秒。

两种标准并存，且互相打架：

标准 依据 优点 缺点
地球自转/公转 平均太阳日、公转周期 与日历、昼夜一致 周期不恒定，秒长会漂
铯 133 振荡频率 原子能级跃迁频率 恒定，可复现 与地球自转逐渐脱钩

Linux 内核用的是第二种。参考点（epoch）选的是 UTC 时间，而 UTC 就是走原子秒这条路的时间标准。

定下秒之后，往下细分有毫秒、微秒、纳秒，往上组织有分、时、日、月、年。往下细分是工程问题，往上组织是日历问题，两件事别混。闰秒、闰年这些补丁都属于「往上组织」这一侧，跟秒本身的定义无关。

顺带说一句物理：严格的绝对时空观在狭义相对论下站不住，时间和空间是耦合的四维时空，同时性是相对于参考系的。但内核关心的是单机、低速、非光速运动的场景，牛顿那套框架足够用，狭义相对论在这里是个可以忽略的修正项。搞内核的人不必在总线上的时钟中断里思考洛伦兹变换。

二、Epoch：时间轴的原点是谁定的 #

有了刻度还不够，还得有原点。原点一确定，一个时间点就能退化成一个数字：到原点的距离。

这里有个容易混淆的地方：定义单位是技术活，定义原点是习惯问题。谁都可以选。

系统 Epoch 基准点（UTC） 备注
Unix / Linux 1970-01-01 00:00:00 Unix 在 1970 年前后成型，顺手就定了
NTP 1900-01-01 00:00:00 RFC 5905 的时间戳原点
GPS 1980-01-06 00:00:00 与 UTC 有固定偏移，不含闰秒
你的手表 耶稣诞辰日（习惯上） 那个 tm_year 从 1900 起算

历史上 POSIX 曾把参考点写成 1970-01-01 00:00:00 GMT，后来修正为 UTC。这个修正不是文字游戏，GMT 和 UTC 在闰秒附近不是同一个东西，后面第三章讲。

Linux 的做法很直接：CLOCK_REALTIME 的读数就是当前时刻到 Unix epoch 的秒数（外加纳秒小数）。你在终端里 date +%s 看到的那串数字，就是这块表的读数。作为一个 linuxer，你手上那块「表」上只有这个秒数，年月日时分秒是后来才拆出来的。

除了墙上时间，系统还需要另一个原点：开机时刻。把 epoch 挪到 boot 那一刻，问「系统起来多久了」就变成直接读表。这就是后来 CLOCK_MONOTONIC / CLOCK_BOOTTIME 的由来，第九章、第十一章细讲。

拆成年月日时分秒的那套东西叫 broken-down time。内核里用 struct tm 表示：

c
struct tm {
    /*
     * the number of seconds after the minute, normally in the range
     * 0 to 59, but can be up to 60 to allow for leap seconds
     */
    int tm_sec;
    /* the number of minutes after the hour, in the range 0 to 59*/
    int tm_min;
    /* the number of hours past midnight, in the range 0 to 23 */
    int tm_hour;
    /* the day of the month, in the range 1 to 31 */
    int tm_mday;
    /* the number of months since January, in the range 0 to 11 */
    int tm_mon;
    /* the number of years since 1900 */   /* 以 1900 为基准，不是 Unix epoch */
    long tm_year;
    /* the number of days since Sunday, in the range 0 to 6 */
    int tm_wday;
    /* the number of days since January 1, in the range 0 to 365 */
    int tm_yday;
};

注意 tm_sec 的注释：范围写的是 0~59，但为了容纳闰秒可以到 60。这条注释是 POSIX 里闰秒痕迹最明显的地方。

精度层面，Linux 一路往上堆了三种表示：

c
typedef long time_t;          /* 秒 */

struct timeval {
    time_t      tv_sec;       /* seconds */
    suseconds_t tv_usec;      /* microseconds */
};

struct timespec {
    time_t tv_sec;            /* seconds */
    long   tv_nsec;           /* nanoseconds */
};

tv_sec x 10^6 + tv_usec 就是到 epoch 的微秒数，tv_sec x 10^9 + tv_nsec 是纳秒数。POSIX 规定时间轴上一个时间点用 struct timespec 表示。time_t 如果是 32 位有符号整数，2038 年会溢出，这个问题和本篇的 clock 语义无关，属于 ABI 层面的事。

三、TAI 与 UTC：为什么需要闰秒 #

沿着原子秒一路铺出来的时间轴，叫 TAI（International Atomic Time）。这块表不管日出日落、不管农耕节气，机械地按铯原子定义的那个秒往前走。它精准，冷冰冰，对人类不友好。

人类要的是「太阳在正午最高」这种能对上昼夜的日历时间制度，历史上叫 GMT 那一类。它符合习惯，但不精确。

UTC（Coordinated Universal Time）是个妥协产物：基因来自 TAI（同样用原子秒计时），但身上挂了一个调节器，在合适的时候把秒针拨一下，让它和地球自转保持对齐。这个「拨一下」就是闰秒（leap second）。

三者的关系：

概念 计时依据 是否含闰秒 与地球自转的关系
TAI 原子秒，连续 否 无，纯原子时
UTC 原子秒 + 闰秒微调 是 靠闰秒维持与 GMT 的一致
GMT 天文观测（格林尼治平均太阳时） 不适用 直接依赖地球自转

TAI 和 UTC 在 1972 年做过一次对准，当时相差 10 秒。此后两边各自跑，UTC 每逢闰秒就被拨动一秒，而 TAI 不动。于是差距一路累积：到 2017 年已经有过 27 次闰秒，TAI 比 UTC 快 37 秒（10 + 27 = 37）。

你可以这样理解：两块表的发条一模一样，都是原子秒的滴答（tick）。区别只在于 UTC 那块表上装了个能前后拨一秒的旋钮。所以它们本质上是同一条时间轴加上一个随时间变化的偏移量：

text
TAI = UTC + offset
1972 年：offset = 10 秒
2017 年：offset = 37 秒（27 次闰秒之后）
每次 +1 闰秒：offset 再 +1

地球自转目前一直在变慢，所以现在的闰秒都是往 UTC 里加一秒。哪天自转变快，理论上要减一秒——那才是真正让所有软件集体出事的场景，因为「23:59:60」这种时间点加一秒还能凑合，「23:59:59 之后还是 23:59:58」就让所有假设时间单调的代码全部翻车。目前没有负闰秒发生过。

Linux 内核怎么处理闰秒？答案是：基本不管。内核的 epoch 是 UTC，但内核自己不做闰秒补偿。理由很实在——对一个天文学意义上很短的时间段（比如 15 个月），UTC 和 GMT 的差别可以忽略，绝大多数应用也感觉不到。真在乎这件事的是时间同步服务器和上层应用，内核只负责支持 NTP 协议去和外部服务器对齐，外部服务器怎么处理闰秒，那是它们的事。

这个「甩锅」策略有代价：闰秒的那一刻，如果 NTP 把 CLOCK_REALTIME 往后拨一秒，所有正在跑的定时器都会多睡一秒。所以现实中的 NTP 实现（比如 ntpd 的 slew 模式）更倾向于把这一秒摊开慢慢消耗，而不是一次性跳过去。这就引出了下一章。

顺带把闰年也理一下，它和闰秒是两套补丁。地球公转周期约 365.2564 天，平年取 365 天，每四年补一天，则每四年多算 0.0256 天。四百年累积下来多出约 2.56 天，于是规则再打一层补丁：能被 100 整除的年份不闰，能被 400 整除的年份还是闰。四百年里 100 的倍数有 4 个，其中 400 的倍数 1 个，净少闰 3 天，剩下 0.44 天的残差继续挂着，永远算不完。这套规则在 CLOCK_REALTIME 转 broken-down time 的时候由内核或用户库实现，和 clock 的读数本身无关。

四、时间调整的两种方式：跳变与渐进 #

记住老爸那块机械表的画面：每隔一段时间它就要慢上一分钟，于是他守在 7 点钟的新闻联播前，听到「刚才最后一响」就伸手把表拨正。这个动作在内核里对应 clock_settime（底层是 clock_set 回调）。

计算机的晶振和机械表的发条一个毛病：不够准。UTC 是基于原子钟的，你不会给每台机器装一台铯钟。所以要有时间同步。

同步有两条路，区别是「连续性」：

方式 手段 时间轴行为 连续性 单调性 典型对应
跳变（step） 直接设定当前时间值 向前或向后瞬移 破坏 破坏 clock_settime、do_settimeofday
渐进（slew） 微调本地振荡器的频率 慢慢追上/退后 保持 保持 adjtimex、ntpd slew 模式

跳变的问题很直接：往前跳一秒，所有到期的定时器立刻全部到期；往后跳一秒，所有定时器集体多等一秒。中间那一刻的时间戳还会重复出现，日志里出现两条一模一样的时间戳是家常便饭。

渐进则是对本地振荡器的输出频率做微调，让本地时间以略快或略慢的速率追赶目标值。秒还是那个秒，只是每个秒比标准秒长一点点或短一点点，追平之前系统时间始终是连续的、单调的。代价是你需要一段时间才能完成校正。

内核里这两条路都有：

c
struct k_clock clock_realtime = {
    .clock_getres = hrtimer_get_res,
    .clock_get    = posix_clock_realtime_get,
    .clock_set    = posix_clock_realtime_set,   /* 跳变 */
    .clock_adj    = posix_clock_realtime_adj,   /* 渐进 */
    .nsleep       = common_nsleep,
    .nsleep_restart = hrtimer_nanosleep_restart,
};

clock_set 对应 do_settimeofday，clock_adj 对应 do_adjtimex。上游用户态接口分别是 clock_settime 和 adjtimex。

这就是本篇第一个核心问题的答案。CLOCK_REALTIME 之所以会跳变，是因为它的设计目标就是「和墙上的钟表对齐」，而对齐这件事必然允许被外力直接改写——无论是人工设时间，还是 NTP 校时，甚至闰秒。CLOCK_MONOTONIC 之所以不会跳变，是因为它的 k_clock 结构里根本没有 clock_set 成员，你连改它的入口都没有：

c
struct k_clock clock_monotonic = {
    .clock_getres = hrtimer_get_res,
    .clock_get    = posix_ktime_get_ts,
    .nsleep       = common_nsleep,
    .nsleep_restart = hrtimer_nanosleep_restart,
};

没有 clock_set，没有 clock_adj。两个函数指针的缺失，就是「单调」这两个字在内核代码里的全部体现。

五、计时范围与精度：两个必须一起看的指标 #

有一种表叫秒表：按下 start 开始计时，按住 stop 暂停，再按继续。用它记录一个人睡了多久，睡着的瞬间按下 start，醒来的瞬间暂停。它度量的是「真正发生的那段过程」有多长，而不是「从昨晚到今早墙上钟表走了多少格」。

Linux 里有一模一样的东西：CLOCK_PROCESS_CPUTIME_ID 和 CLOCK_THREAD_CPUTIME_ID。进程被调度出去，表就停；调度回来，表继续走。这是「计时范围」这个维度的第一个分界——有些 clock 只计 CPU 真正在跑的时间，有些 clock 计整个真实时间轴。

那么精度呢？这里要先戳破一个错觉：时间是连续的，但 Linux 里记录的时间值不连续。

系统在每个 tick 到来时更新一次时间（到 epoch 的秒和纳秒）。所以内核手上握着的是一串离散采样点。用户来问「现在几点」，实现可以做两件事：

  • 把最近一个 tick 的采样值返回去，快，但最多差了不到一个 tick；
  • 采样值加上「当前时刻到上一个 tick 的 delta」，准，但要多算一次当前计数值。

两条路各有拥趸。CLOCK_REALTIME_COARSE / CLOCK_MONOTONIC_COARSE 走第一条，精度就是 tick 的纳秒数（KTIME_LOW_RES），换来的是不需要读硬件计数器、不需要序列化计算的性能优势。高精度 clock 走第二条。

c
struct k_clock clock_realtime_coarse = {
    .clock_getres = posix_get_coarse_res,
    .clock_get    = posix_get_realtime_coarse,
};

struct k_clock clock_monotonic_coarse = {
    .clock_getres = posix_get_coarse_res,
    .clock_get    = posix_get_monotonic_coarse,
};

这就是为什么 clock_getres 是 k_clock 的第一个成员：精度不是一个装饰性的返回值。POSIX timer 超时时间会被规整到这个精度允许的粒度上，你设 1 微秒的定时器落在 coarse clock 上，实际粒度是 tick。

精度和范围是两把独立的尺子，混着看会得出错误结论。CLOCK_THREAD_CPUTIME_ID 的 CPUCLOCK_SCHED 变体精度到 1 纳秒，但它只统计一个线程在 CPU 上的时间，范围窄到几乎不能用来测量一段真实耗时。

六、睡觉的时候时间会停止吗 #

在现实世界里问这个问题没什么意义。但对 Linux 的 clock 来说，这是必须回答的工程问题。

原因在于 clock 最重要的派生用途是创建 timer：每个 timer 都挂在某个特定的 clock 上运行。假设你设了一个 5 秒的超时，第 2 秒系统进了 suspend。到第 5 秒，这个 timer 要不要触发？

多数情况下不会触发。因为底层 clock 依赖的是一个持续运转的硬件计数器（free running counter），suspend 之后这个计数器停了，clock 也就不动了。clock 不走，timer 自然不会到期。至于唤醒系统去执行 expired handler，更是无从谈起。

但用户有真实需求，最典型的就是关机闹铃：手机闹钟在系统休眠时必须响。这就需要一类特殊的 clock，在 suspend 期间仍然推进，从而推动 timer 到期，再由 Alarmtimer 这类机制把系统叫醒。

这条线索把 11 种 clock 分成三组，也是后面各章反复出现的三个问题：

  1. 这块表会不会被外力改（跳变）？
  2. 这块表在 suspend 期间走不走？
  3. 这块表只计 CPU 时间，还是计真实时间？

七、Linux 的十一种 clock 总览 #

内核定义了下面这组 clock id：

c
#define CLOCK_REALTIME              0
#define CLOCK_MONOTONIC             1
#define CLOCK_PROCESS_CPUTIME_ID    2
#define CLOCK_THREAD_CPUTIME_ID     3
#define CLOCK_MONOTONIC_RAW         4
#define CLOCK_REALTIME_COARSE       5
#define CLOCK_MONOTONIC_COARSE      6
#define CLOCK_BOOTTIME              7
#define CLOCK_REALTIME_ALARM        8
#define CLOCK_BOOTTIME_ALARM        9
#define CLOCK_SGI_CYCLE            10    /* Hardware specific */
#define CLOCK_TAI                  11

#define MAX_CLOCKS                 16

数一下上面是 12 个宏，但 CLOCK_SGI_CYCLE 是 SGI 平台专有的硬件相关 clock，跟通用内核语义无关，所以讲「Linux 的十一种 clock」时只数 0~9 加 11 这 11 个。这个数法要记住，否则跟别人对不上账。

POSIX 标准只定义了其中 4 种：CLOCK_REALTIME、CLOCK_MONOTONIC、CLOCK_PROCESS_CPUTIME_ID、CLOCK_THREAD_CPUTIME_ID。剩下 7 种都是 Linux 自己加的。

内核用一张静态数组兜住这些 clock：

c
static struct k_clock posix_clocks[MAX_CLOCKS];

init_posix_timers 在系统初始化时把 real time 系列的 clock 注册进 posix_clocks，init_posix_cpu_timers 负责 CPU-time 系列。用户态传下来的 clock id 当成数组下标查表：

c
static struct k_clock *clockid_to_kclock(const clockid_t id)
{
    if (id < 0)
        return (id & CLOCKFD_MASK) == CLOCKFD ?
            &clock_posix_dynamic : &clock_posix_cpu;
    if (id >= MAX_CLOCKS || !posix_clocks[id].clock_getres)
        return NULL;
    return &posix_clocks[id];
}

两个分支值得盯住。id >= 0 是静态 clock，直接查数组，顺手用 clock_getres 是否为空来判定这个下标是不是真的注册过。id < 0 是另一回事：负数 id 要么是 CPU-time clock（带 pid 或线程 id），要么是动态 posix clock（带 fd）。

一个 int 装不下这么多信息，所以 bit 位被切得很细：

text
bit 31 .. bit 3 : pid（CPU-time clock）或 fd（dynamic clock）
bit 2           : 1 = 线程 clock，0 = 进程 clock
bit 1, bit 0    : 类型 PROF=0, VIRT=1, SCHED=2, FD=3

注意 pid 存的是反码（CPUCLOCK_PID(clock) 是 ~((clock) >> 3)），目的就是保证 MSB 为 1，让整个 clock id 落在负数区间，clockid_to_kclock 才能用符号位一步分流。这是内核里「用类型系统省一个判断」的典型手法。

下面八到十四章逐个过这 11 种 clock。每个都按同一套问题去问：定义在哪、怎么取当前值、能不能设、有没有 timer 能力、suspend 期间走不走。

八、real time clock：会跳变的那块表 #

CLOCK_REALTIME 是墙上那块钟。名字里的 realtime 有歧义，既可以指「真实时间」，也可以指「实时性」——这个歧义中英文都有，看上下文判断，这里说的是前者。

它的读数是当前时刻到 Unix epoch 的秒数加纳秒，能读也能设定。你在 date -s 里敲的那些数字，最终就落到这块表上。

内核里的定义：

c
struct k_clock clock_realtime = {
    .clock_getres    = hrtimer_get_res,
    .clock_get       = posix_clock_realtime_get,
    .clock_set       = posix_clock_realtime_set,
    .clock_adj       = posix_clock_realtime_adj,
    .nsleep          = common_nsleep,
    .nsleep_restart  = hrtimer_nanosleep_restart,
};

四个关键回调背后全是 timekeeping 模块的接口：

回调 实际调用 作用
posix_clock_realtime_get ktime_get_real_ts 取当前值，返回 timespec 格式
posix_clock_realtime_set do_settimeofday 直接设定，跳变
posix_clock_realtime_adj do_adjtimex 频率调整，渐进
hrtimer_get_res hrtimer 相关 精度，与 hrtimer 能力相关

common_nsleep / hrtimer_nanosleep_restart 说明纳秒级 sleep 是靠高精度 timer 实现的，这块表只是提供了 time base。

CLOCK_REALTIME 的三个属性：会跳变（clock_set 存在）、suspend 期间「走」但语义上不可靠（suspend 期间 RTC 在走，resume 后靠 RTC 校正，若 RTC 本身不准还得等 NTP）、记录真实世界时间。

用它做超时计算是经典事故：clock_gettime(CLOCK_REALTIME) 取两次值相减算耗时，中间只要发生一次 NTP step，算出来的耗时可以是负数。测耗时请用 monotonic。

九、monotonic clock：只前进的那块表 #

CLOCK_MONOTONIC 是那块不许你调的表。它也是真实世界的时钟（全称 monotonic real time clock），有明确的零点，但零点不是 Unix epoch，而是系统启动那一刻。初始值 0，此后只增不减。

c
struct k_clock clock_monotonic = {
    .clock_getres    = hrtimer_get_res,
    .clock_get       = posix_ktime_get_ts,
    .nsleep          = common_nsleep,
    .nsleep_restart  = hrtimer_nanosleep_restart,
};

取当前值走 ktime_get_ts。结构里没有 clock_set，也没有 clock_adj。这是「单调」的机械保证，不靠约定，靠成员函数缺失。

但「不能被人为设定」不等于「不能被调整」。NTP 对 monotonic 的调整走的是另一条路：它调整的是底层 clocksource 的频率（也就是那个渐进式 slewing），所以 monotonic 仍然会随着 NTP 的频率校正而变化，只是不会出现 step 跳变。语义上它保证连续、保证单调递增，但不保证「每个秒都精确等于原子秒」。

CLOCK_MONOTONIC 在 suspend 期间的读数是内核里最容易踩的坑之一。这块表停在那里不推进，所以 resume 之后 CLOCK_MONOTONIC 少算了整个休眠时长。需要把休眠算进去的场景就用 CLOCK_BOOTTIME，见第十一章。

用它算耗时是对的：两次采样相减，结果一定非负，即使中间 NTP 校时、闰秒、设时间也不会翻车。

十、monotonic raw 与 coarse：两种不同目的的退化 #

monotonic raw #

c
struct k_clock clock_monotonic_raw = {
    .clock_getres = hrtimer_get_res,
    .clock_get    = posix_get_monotonic_raw,
};

CLOCK_MONOTONIC_RAW 取当前值走 getrawmonotonic。raw 这个词说的是它拿的是硬件的原始计数换算结果，不经过 NTP 的频率调整和偏移修正。系统启动时设为 0，此后一直累加，不能设定。

和 CLOCK_MONOTONIC 的区别就一条：不受 NTP 调整影响。你要的是「这块晶振实际跑了多少个周期」，用 raw；你要的是「经过了多久（已校正）」，用 monotonic。

另一个差别在结构体里：raw 没有 nsleep，也没有任何 timer 相关的 callback。它只能读，不能用来挂 timer。这一点比很多人以为的严格。

coarse #

c
struct k_clock clock_realtime_coarse = {
    .clock_getres = posix_get_coarse_res,
    .clock_get    = posix_get_realtime_coarse,
};

struct k_clock clock_monotonic_coarse = {
    .clock_getres = posix_get_coarse_res,
    .clock_get    = posix_get_monotonic_coarse,
};

两个 coarse clock 的行为分别对应 CLOCK_REALTIME 和 CLOCK_MONOTONIC，只是精度降级到 tick。精度值返回 KTIME_LOW_RES，也就是一个 tick 的纳秒数。取值分别走 current_kernel_time 和 get_monotonic_coarse。

这两个 clock 的存在理由纯粹是性能：不需要读硬件计数器、不需要做序列化校正，直接从内存里拿最近的 tick 采样值。适合那些「精度要求不高但调用极其频繁」的场景，比如日志打时间戳、统计埋点、某些 timer 库的 fast path。

注意 coarse 也不能挂 timer，结构体里只有 clock_getres 和 clock_get 两个成员。

三种退化路径放到一张表里看更清楚：

clock 退化方向 精度 受 NTP 影响 能挂 timer
CLOCK_MONOTONIC 无 hrtimer 精度 是（频率层面） 是
CLOCK_MONOTONIC_RAW 去掉 NTP 校正 hrtimer 精度 否 否
CLOCK_MONOTONIC_COARSE 降低精度换性能 tick 是（tick 级） 否
CLOCK_REALTIME 无 hrtimer 精度 是 是
CLOCK_REALTIME_COARSE 降低精度换性能 tick 是（tick 级） 否

十一、boottime：把睡眠时间也算进去 #

CLOCK_BOOTTIME 是 CLOCK_MONOTONIC 的补丁版。也是单调递增，也是启动时置 0，区别只有一条：它把 suspend 的时间也算进去。

text
                 suspend         resume
   -----+----------+---------------+----------+-----> 真实时间
        |                                   |
   CLOCK_MONOTONIC: 前进          停住        继续前进
   CLOCK_BOOTTIME : 前进          继续前进     继续前进

也就是说，不论是 running 还是 suspend，都算在 boottime 里，一直累积到系统 reset 或 shutdown。这正是 alarm 所需的时间基准：定时器要知道「真实世界已经过了 8 小时」，而不关心「CPU 睡了 8 小时」。

内核里 CLOCK_BOOTTIME 的实现很简单，就是在 monotonic 的读数上叠加 suspend 期间累积的时长（源代码中由 timekeeping 模块维护 suspend 时长变量，具体变量名随版本变化，未逐版本核对）。素材原文对此只有一句「实现非常简单，大家自行阅读代码」，本篇按此保留，不做超出原文的断言。

CLOCK_BOOTTIME 是 2.6.39 引入的，在那之前想算「开机以来真实经过时间」只能自己跟踪 suspend 事件。

它也不能被设定。suspend 期间它「走」，但注意这个「走」是由 resume 后用 RTC 差值补偿实现的——RTC 不准，boottime 在跨越 suspend 之后也就不准。

十二、CPU-time clock：per-process 与 per-thread #

这一族 clock 度量的不是真实时间，而是 CPU 时间：进程或线程真正占着 CPU 跑的时间。被调度出去，表就停；调度回来，表继续走。

用户空间有两种用法：

c
/* 用法一：直接用预定义 id */
clock_gettime(CLOCK_PROCESS_CPUTIME_ID, &ts);
clock_gettime(CLOCK_THREAD_CPUTIME_ID, &ts);

/* 用法二：先拿到某个进程/线程的 clock id，再用它 */
clockid_t cid;
clock_getcpuclockid(target_pid, &cid);     /* 进程 */
pthread_getcpuclockid(thread, &cid);       /* 线程 */
clock_gettime(cid, &ts);

用法一对应内核初始化时注册的两个静态 clock：process 和 thread（init_posix_cpu_timers 完成注册）。用法二对应一个通用的 clock_posix_cpu，它接受负数 clock id，从 id 里解出 pid 和 bit 2 的类型位。

c
struct k_clock clock_posix_cpu = {
    .clock_getres    = posix_cpu_clock_getres,
    .clock_set       = posix_cpu_clock_set,
    .clock_get       = posix_cpu_clock_get,
    .nsleep          = posix_cpu_nsleep,
    .nsleep_restart  = posix_cpu_nsleep_restart,
};

（为突出重点，上面省掉了 timer 系列回调。）

clock_posix_cpu 有个 clock_set 成员，看着奇怪——CPU 时间当然没法设。这个回调实际只做一件事：返回 -EINVAL，告诉调用者不支持。

c
struct k_clock process = {
    .clock_getres    = process_cpu_clock_getres,
    .clock_get       = process_cpu_clock_get,
    .nsleep          = process_cpu_nsleep,
    .nsleep_restart  = process_cpu_nsleep_restart,
};

process_cpu_clock_getres 内部就是转调 posix_cpu_clock_getres(PROCESS_CLOCK, tp)，process_cpu_clock_get 转调 posix_cpu_clock_get。线程版同理，素材原文对此就只有「很简单，大家自行学习吧」一句，本篇不额外发挥。

精度：tick 还是 1 纳秒 #

c
static int posix_cpu_clock_getres(const clockid_t which_clock, struct timespec *tp)
{
    int error = check_clock(which_clock);   /* 参数校验 */
    if (!error) {
        tp->tv_sec = 0;
        tp->tv_nsec = ((NSEC_PER_SEC + HZ - 1) / HZ);
        if (CPUCLOCK_WHICH(which_clock) == CPUCLOCK_SCHED) {
            tp->tv_nsec = 1;
        }
    }
    return error;
}

函数分两段：校验，然后返回精度。(NSEC_PER_SEC + HZ - 1) / HZ 是向上取整的 tick 纳秒值。CPUCLOCK_SCHED 类型直接给 1 纳秒。

check_clock 做三件事：

  • 从 clock id 解出 pid（存的是反码，见第七章），确认该 task 存在；
  • 如果 id 指的是进程（clock_getcpuclockid 来的），要求该 pid 对应的 task 是线程组 leader。内核里 pid 是线程 ID，POSIX 意义上的进程 ID 对内叫 tgid，所以「真实的进程 id」意味着 pid == tgid；
  • 如果 id 指的是线程（pthread_getcpuclockid 来的），要求调用者与该线程同属一个线程组。

素材原文对第二条自己标了 TODO「此处理解存疑」，本篇照实标注：这条校验的严格程度随版本有差异，精度查询场景下要求放宽到「有 thread group leader 即可」，源码里的注释与实现是否完全对齐未逐行核对。

取值：三种统计口径 #

c
static int posix_cpu_clock_get_task(struct task_struct *tsk, const clockid_t which_clock,
                    struct timespec *tp)
{
    int err = -EINVAL;
    unsigned long long rtn;

    if (CPUCLOCK_PERTHREAD(which_clock)) {          /* per 线程 */
        if (same_thread_group(tsk, current))        /* 必须同进程 */
            err = cpu_clock_sample(which_clock, tsk, &rtn);
    } else {                                        /* per 进程 */
        if (tsk == current || thread_group_leader(tsk))
            err = cpu_clock_sample_group(which_clock, tsk, &rtn);
    }
    if (!err)
        sample_to_timespec(which_clock, rtn, tp);
    return err;
}

权限模型很简单：进程 clock 只允许进程自己（或线程组 leader）查，线程 clock 只允许同进程的线程查。跨进程偷看别人耗 CPU 多少时间，接口层面就挡掉了。

三种统计口径由 CPUCLOCK_WHICH 分派：

c
static int cpu_clock_sample(const clockid_t which_clock, struct task_struct *p,
                unsigned long long *sample)
{
    switch (CPUCLOCK_WHICH(which_clock)) {
    default:
        return -EINVAL;
    case CPUCLOCK_PROF:
        *sample = prof_ticks(p);          /* 用户态 + 内核态执行时间 */
        break;
    case CPUCLOCK_VIRT:
        *sample = virt_ticks(p);          /* 仅用户态执行时间 */
        break;
    case CPUCLOCK_SCHED:
        *sample = task_sched_runtime(p);  /* 调度器口径 */
        break;
    }
    return 0;
}

CPUCLOCK_PROF 和 CPUCLOCK_VIRT 是「粗估派」，靠周期性 tick 累加：tick 到来时如果正在跑用户态程序，整个 tick 都记成该进程的用户态时间；如果正在内核态且是用户程序陷入系统调用，整个 tick 都记成系统态时间（或反之，依统计对象而定）。精度是 tick，粒度粗，但开销极低。

CPUCLOCK_SCHED 是「精算派」，由调度器以纳秒级精度累加进程 runtime，取 task_sched_runtime。精度高，代价是要在调度路径上做更多记账。process_cpu_clock_getres 里那个「SCHED 精度是 1ns」就来自这里，具体累加算法属于调度器篇章。

cpu_clock_sample_group 逻辑同构，只是把该进程下所有线程的时间加总。

CLOCK_SGI_CYCLE #

posix_clocks[10] 这一格是 CLOCK_SGI_CYCLE，SGI 平台专用的硬件周期计数器，标着 /* Hardware specific */。通用 x86/ARM 内核上不会注册，clockid_to_kclock 查到这里会因 clock_getres 为空返回 NULL。讲 clock 语义时可以跳过它，这也是本篇只数 11 种不数 12 种的原因。

十三、alarm clock：能唤醒系统的那种 #

CLOCK_REALTIME_ALARM 和 CLOCK_BOOTTIME_ALARM 是为 Alarmtimer 准备的。它们和对应的母 clock 读数完全一样，区别在于能力：用它们创建的 timer 挂在 RTC 上，在 suspend 甚至关机状态下也能把系统叫醒。

回答第六章那个闹钟问题，答案就在这里。普通 timer 挂在 CLOCK_MONOTONIC 上，suspend 时底下的硬件计数器停了，timer 永远等不到到期。Alarmtimer 换了个底座——RTC 在 suspend 期间由电池供电继续走，到点产生中断，系统 resume 后处理 expired handler。

组合 时间语义 suspend 期间 能唤醒系统
CLOCK_REALTIME + timer 墙上时间，会跳变 停止 否
CLOCK_MONOTONIC + timer 单调，不含睡眠 停止 否
CLOCK_BOOTTIME + timer 单调，含睡眠 继续 否
CLOCK_REALTIME_ALARM + timer 墙上时间 继续（RTC） 是
CLOCK_BOOTTIME_ALARM + timer 单调，含睡眠 继续（RTC） 是

选哪个取决于你要的是「绝对时刻闹」还是「相对时长闹」。设定「明早 7 点响」用 CLOCK_REALTIME_ALARM，因为 7 点是个绝对时刻，中途时区变了、夏令时变了都要跟着变；设定「8 小时后响」用 CLOCK_BOOTTIME_ALARM，因为你要的是时长。前者在时区被改写时会跟着漂，后者不会。

调用 alarm clock 需要 CAP_WAKE_ALARM 权限（能力宏名来自通用 alarmtimer 实现，本篇未逐版本核对引入版本）。

十四、CLOCK_TAI：去掉闰秒的 UTC #

CLOCK_TAI 是 3.10 引入的，它在 clock id 表里排最后一位，值为 11。

语义上它就是「没有闰秒的 UTC」，也就是 TAI。读数和 CLOCK_REALTIME 之间差一个 TAI - UTC 的偏移量。第三章算过：1972 年是 10 秒，2017 年是 37 秒，每发生一次闰秒再加 1。

text
CLOCK_TAI ≈ CLOCK_REALTIME + offset
offset 随闰秒增加，现在（2017 之后）是 37 秒

为什么需要它？因为有一类应用要的是一条严格连续、绝不回退、绝不重复的时间轴，同时又要和 UTC 保持可换算关系。金融撮合、跨机事务排序、科学数据采集都属于这类。CLOCK_MONOTONIC 单调但不含绝对时刻，跨机器没法比较；CLOCK_REALTIME 有绝对时刻但闰秒时会出怪事。CLOCK_TAI 同时满足两个条件。

代价是：offset 不是内核自己算的，得有人告诉它。系统启动时通过 adjtimex 的 TAI 偏移字段（timex.tai）设定，NTP 服务器在对时的时候顺手把它下发。内核不会自己去查闰秒表。

CLOCK_TAI 能不能被设定？它的语义要求它必须单调，所以不提供 clock_set。素材原文对此只有一句「CLOCK_BOOTTIME 和 CLOCK_TAI 的 clock 实现非常简单，大家自行阅读代码就 OK 了」，本篇按此不作超出原文的实现细节断言——CLOCK_TAI 在 timekeeping 层的具体实现路径未验证。

十五、内核怎么抽象这些 clock：struct posix_clock #

到这里要澄清一件容易搞混的事：内核里有两套 clock 抽象，不要当成一个。

第一套：struct k_clock，静态 clock 的抽象 #

静态 clock 就是 ID 在 0..MAX_CLOCKS-1 范围内、编进内核的那些。它们全放在 posix_clocks 数组里，每个元素是一个 struct k_clock：

c
struct k_clock {
    int (*clock_getres) (const clockid_t which_clock, struct timespec *tp);
    int (*clock_set) (const clockid_t which_clock, const struct timespec *tp);
    int (*clock_get) (const clockid_t which_clock, struct timespec * tp);
    int (*clock_adj) (const clockid_t which_clock, struct timex *tx);
    int (*timer_create) (struct k_itimer *timer);
    int (*nsleep) (const clockid_t which_clock, int flags, struct timespec *, struct timespec __user *);
    long (*nsleep_restart) (struct restart_block *restart_block);
    int (*timer_set) (struct k_itimer * timr, int flags, struct itimerspec * new_setting,
                            struct itimerspec * old_setting);
    int (*timer_del) (struct k_itimer * timr);
    void (*timer_get) (struct k_itimer * timr, struct itimerspec * cur_setting);
};

十个函数指针，可以按职责切成三组：

组 成员 说明
精度与取值 clock_getres、clock_get getres 同时充当「该 clock 是否注册」的哨兵
时间调整 clock_set、clock_adj 前者跳变，后者渐进；都没有的 clock 就是不可调整
睡眠与 timer nsleep、nsleep_restart、timer_create、timer_set、timer_del、timer_get 后四个属于 POSIX interval timer，另有专文

clock_get 拿到的是一个绝对时间值——绝对也是相对的，相对于该 timeline 自己的 epoch（CLOCK_REALTIME 是 Unix epoch，CLOCK_MONOTONIC 是 boot 时刻）。clock_adj 的存在理由是本地晶振不准：随温度漂移、随时间老化，需要外部精确时间信息来矫正。

把本篇出现过的 k_clock 定义并排放，缺哪个成员一目了然：

c
/* 能取能设能调，能挂 timer —— 墙上那块表 */
struct k_clock clock_realtime = {
    .clock_getres   = hrtimer_get_res,
    .clock_get      = posix_clock_realtime_get,
    .clock_set      = posix_clock_realtime_set,
    .clock_adj      = posix_clock_realtime_adj,
    .nsleep         = common_nsleep,
    .nsleep_restart = hrtimer_nanosleep_restart,
};

/* 能取能挂 timer，不能设 —— 单调那块表 */
struct k_clock clock_monotonic = {
    .clock_getres   = hrtimer_get_res,
    .clock_get      = posix_ktime_get_ts,
    .nsleep         = common_nsleep,
    .nsleep_restart = hrtimer_nanosleep_restart,
};

/* 只能读 —— 原始计数 */
struct k_clock clock_monotonic_raw = {
    .clock_getres   = hrtimer_get_res,
    .clock_get      = posix_get_monotonic_raw,
};

/* 只能读，精度是 tick —— 性能优先的降级版 */
struct k_clock clock_realtime_coarse = {
    .clock_getres   = posix_get_coarse_res,
    .clock_get      = posix_get_realtime_coarse,
};

struct k_clock clock_monotonic_coarse = {
    .clock_getres   = posix_get_coarse_res,
    .clock_get      = posix_get_monotonic_coarse,
};

/* CPU-time clock：set 恒返回 -EINVAL */
struct k_clock clock_posix_cpu = {
    .clock_getres   = posix_cpu_clock_getres,
    .clock_set      = posix_cpu_clock_set,
    .clock_get      = posix_cpu_clock_get,
    .nsleep         = posix_cpu_nsleep,
    .nsleep_restart = posix_cpu_nsleep_restart,
};

/* 进程级 CPU-time clock */
struct k_clock process = {
    .clock_getres   = process_cpu_clock_getres,
    .clock_get      = process_cpu_clock_get,
    .nsleep         = process_cpu_nsleep,
    .nsleep_restart = process_cpu_nsleep_restart,
};

读内核代码时，判断一种 clock 的性质不需要翻文档，看它的 k_clock 结构体里有什么成员就够了。有 clock_set 就说明它会跳变，没有就说明它单调。

第二套：struct posix_clock，动态 clock 的抽象 #

有些硬件本身能做精确计时，也想通过 POSIX clock 接口暴露出来。问题是这类硬件像 USB 设备一样可以热插拔，不能静态定义在 posix_clocks 数组里。而且除了标准 clock/timer 操作，它们还需要字符设备那一套控制接口（open、read、write 之类）。

于是有了 dynamic posix clock：

c
struct posix_clock {
    struct posix_clock_operations ops;   /* (1) */
    struct cdev cdev;                    /* (2) */
    struct kref kref;
    struct rw_semaphore rwsem;
    bool zombie;                         /* (3) */
    void (*release)(struct posix_clock *clk);  /* (4) */
};

四个成员分别对应四件事：

  1. ops 是操作函数集，分两组：clock/timer 那一组（clock_gettime、clock_settime、timer_create、timer_delete）和字符设备那一组（open、read、write）。
  2. cdev 是对应的字符设备，让用户空间能用标准文件描述符操作它。
  3. zombie 记录底层硬件状态，热插拔设备会被拔掉；rwsem 保护这个状态。
  4. 引用计数归零时调用 release 释放资源。

素材原文提了一个设计冗余的疑问：posix_clock_operations 里有 owner，cdev 里也有指向 module 的 owner，看着重复；kref 和 cdev 里的 kobject（已经包含名字和引用计数）也有重复。原文的判断是「只要 struct posix_clock 包含了 cdev 成员，ops.owner 和 kref 就没有必要存在」。这是作者的个人观点，不是内核社区的结论，引用时请注意。

注册和注销：

c
int posix_clock_register(struct posix_clock *clk, dev_t devid)
{
    int err;

    kref_init(&clk->kref);
    init_rwsem(&clk->rwsem);

    cdev_init(&clk->cdev, &posix_clock_file_operations);
    clk->cdev.owner = clk->ops.owner;

    err = cdev_add(&clk->cdev, devid, 1);
    return err;
}

VFS 那一侧的 posix_clock_file_operations 很简单，基本就是把字符设备操作转发到 struct posix_clock_operations 上。

从 fd 到 clock id 的转换：

c
#define FD_TO_CLOCKID(fd)  ((~(clockid_t) (fd) << 3) | CLOCKFD)

fd 来自打开那个硬件设备的设备节点。取反左移，保证结果为负数，CLOCKFD 占 bit 0-1，于是 clockid_to_kclock 走 id < 0 分支，再靠 (id & CLOCKFD_MASK) == CLOCKFD 判出这是动态 clock，返回 &clock_posix_dynamic。clock_posix_dynamic 把这个 id 还原成对应的 struct posix_clock，然后调 posix_clock_operations 上的函数。

clock_posix_cpu（CPU-time clock）也走 id < 0 分支，但它不是动态 clock，是静态定义的、专门处理带 pid 的 clock id。所以 id < 0 的三条分支要一起记：CLOCKFD → 动态，否则 → CPU-time。

十六、一张表看懂 11 种 clock 的差异 #

素材里缺失的那张对比表，在这里重建。五个维度：编号、名称、可否被调整（跳变）、是否计入 suspend、典型用途。

编号 名称 会跳变吗 受 suspend 影响 典型用途
0 CLOCK_REALTIME 会，可被 clock_settime / NTP step 直接改写 走，但 resume 后依赖 RTC 校正 取日历时间、date、日志时间戳、绝对时刻定时
1 CLOCK_MONOTONIC 不会，无 clock_set，但受 NTP 频率调整 不走，suspend 期间停止 测耗时、相对超时、epoll 超时基准
2 CLOCK_PROCESS_CPUTIME_ID 不适用，clock_set 返回 -EINVAL 不适用，只计 CPU 在跑的时间 进程 CPU 占用统计、性能剖析
3 CLOCK_THREAD_CPUTIME_ID 不适用，同上 不适用 单线程耗时剖析、锁竞争分析
4 CLOCK_MONOTONIC_RAW 不会，且不受 NTP 调整（纯硬件计数） 不走 晶振漂移测量、raw 时间基准分析
5 CLOCK_REALTIME_COARSE 会，粒度是 tick 走（tick 级） 高频打时间戳、日志、统计埋点

9 CLOCK_BOOTTIME_ALARM 不会 走，RTC 供电维持 相对时长闹铃，可唤醒系统
11 CLOCK_TAI 不会回退，不含闰秒 走 跨机事件排序、金融撮合、需要绝对且单调的时刻

（10 号 CLOCK_SGI_CYCLE 是 SGI 平台专有硬件 clock，不计入这 11 种。）

两个问题的答案落到这张表上：

为什么 CLOCK_REALTIME 会跳变而 CLOCK_MONOTONIC 不会？ 因为前者的 k_clock 里有 clock_set 和 clock_adj，后者的结构体里这两个成员都不存在。设计目标不同：前者要和墙上的钟对齐，对齐就必须允许被改写；后者要保证时间轴单调，单调就绝不能有改写入口。

CLOCK_BOOTTIME 和 CLOCK_MONOTONIC 差在哪？ 只差 suspend 那一段。running 状态下两者读数一致（boottime 在 monotonic 基础上叠加 suspend 累积时长，running 期间该累积量不变）。一旦进过 suspend，boottime 会比 monotonic 大出整个休眠时长。要「真实世界过了多久」用 boottime，要「CPU 醒着跑了多久」用 monotonic。

十七、易错点速查 #

1. 用 CLOCK_REALTIME 算耗时。 中间一次 NTP step 就能算出负数。测耗时一律用 CLOCK_MONOTONIC。

2. 以为 CLOCK_MONOTONIC 完全不受 NTP 影响。 它只免疫 step 跳变，不免疫 slew 频率调整。要纯硬件计数用 CLOCK_MONOTONIC_RAW。

3. 以为 CLOCK_MONOTONIC_RAW 能挂 timer。 不能，结构体里没有 timer 也没有 nsleep。

4. 以为 coarse clock 能挂 timer。 也不能，只有 clock_getres 和 clock_get。

5. 给 CLOCK_BOOTTIME 上的定时器期待它唤醒系统。 不能。它只是把 suspend 时间算进去，硬件计数器照样停了。要唤醒用 _ALARM 系列。

6. 用 CLOCK_MONOTONIC 统计「用户看到的耗时」。 suspend 期间它不走，用户合上笔记本再打开，monotonic 少算了几个小时。要统计真实流逝时间用 CLOCK_BOOTTIME。

7. 用 CLOCK_TAI 却不设 TAI 偏移。 内核不会自己查闰秒表，不设偏移它就是个偏移错误的读数。

8. 把 struct k_clock 和 struct posix_clock 当成同一个东西。 前者是静态 clock 的行为表，后者是动态 clock 设备对象，id 符号位一分流就各走各的。

9. 数 clock 数量时把 CLOCK_SGI_CYCLE 算进去。 那是 SGI 平台专有项，通用内核上 clock_getres 为空，clockid_to_kclock 会返回 NULL。

10. 以为 clock_posix_cpu 的 clock_set 真能设时间。 它恒返回 -EINVAL，存在的意义就是明确拒绝。

11. 拿奇数值得出「内核处理了闰秒」的结论。 内核不做闰秒补偿，只支持 NTP 去和外部服务器对齐。

12. 用 struct timeval 做微秒级长时间计时。 微秒加上 32 位 time_t，溢出窗口比你想的短。新代码用 timespec 加 64 位。
