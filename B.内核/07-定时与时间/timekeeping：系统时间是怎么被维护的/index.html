一、timekeeping 在整条链路上的位置 #

先把责任切干净。整条链路上有三个角色：

层 手里有什么 回答什么问题
clocksource / clockevent 一个会单调递增的硬件计数器 「从上次问你到现在，又过了多少个周期」
timekeeping 计数器值、换算系数、若干条时间轴的基准与偏移 「现在对应哪年哪月哪日几时几分几秒」
tick / hrtimer 定时事件 「多久之后叫醒我」

clocksource 不会告诉你日期。它只会 read() 出 0x1a2b3c4d 这样的值，这个值从哪开始、一秒钟涨多少个、会不会回绕，都是 clocksource 自己的事。timekeeping 拿这个值做两件事：

  1. 算增量。now - cycle_last，再按 clocksource 的 mask 取模，得到一个「自上次更新以来经过的周期数」。
  2. 把周期数换成纳秒，累加到以秒为单位的时间轴上。

周期 → 纳秒这一步是整个模块的心脏，后面第八、九节专门拆。

这个分工带来一个后果：系统时间的精度上限由 clocksource 决定，不由 timekeeping 决定。timekeeping 只做定点换算和累加，换算误差压在亚纳秒量级（推导见第九节）。你主板上是 24MHz 的 ARM Generic Timer 还是 3.5GHz 的 TSC，时钟源的粒度就直接决定了 clock_gettime 最后一位稳不稳。

模块的入口文件和边界：

text
kernel/time/timekeeping.c      timekeeping 主体，本文的主角
include/linux/timekeeper_internal.h
                               struct timekeeper 的定义（3.10 起从 timekeeping.c 里搬出来）
kernel/time/ntp.c              NTP 相位锁定，给 timekeeping 提供 time_offset / time_freq
kernel/time/clocksource.c      提供 clock->mult / shift / mask，以及换源通知
kernel/time/tick-common.c      周期 tick 里调 update_wall_time()

素材是 3.10 时代的写法，struct timekeeper 还是扁平的，全局变量还是 timekeeper + timekeeper_seq。5.10 起这两样都换了壳，但换算公式一寸没动。理解公式比记住变量名值钱。

二、它要维护的不止一条时间轴 #

同一个硬件计数器，要同时喂给好几条语义不同的时间轴。它们在 Posix 里有编号，在内核里有各自的 clockid_t：

clock 语义 会不会被用户改 含不含睡眠时间 含不含 NTP
CLOCK_REALTIME 墙上时间，1970-01-01 起 会（settimeofday） 含 含
CLOCK_MONOTONIC 开机起单调递增 不会 不含 含
CLOCK_MONOTONIC_RAW 开机起单调递增，纯硬件 不会 不含 不含
CLOCK_BOOTTIME 开机起，含睡眠 不会 含 含
CLOCK_TAI 国际原子时 不会（只能由 NTP 设偏移） 含 不受闰秒影响
CLOCK_REALTIME_COARSE 粗粒度墙上时间 会 含 含
CLOCK_MONOTONIC_COARSE 粗粒度单调时间 不会 不含 含

表里「含不含 NTP」这一列，本质是「用 tkr_mono.mult 还是 clocksource->mult」。第十一节讲这两者的差别。

时间轴之间的关系可以写成三条恒等式。3.10 的定义：

text
CLOCK_REALTIME        = xtime_sec + (xtime_nsec >> shift) + 自上次更新以来的增量
CLOCK_MONOTONIC       = CLOCK_REALTIME + wall_to_monotonic
CLOCK_MONOTONIC_RAW   = raw_time + cyc2ns(硬件周期增量, clock->mult, clock->shift)   ← 不经过 NTP
CLOCK_BOOTTIME        = CLOCK_MONOTONIC + total_sleep_time
CLOCK_TAI             = CLOCK_REALTIME + tai_offset

注意 wall_to_monotonic 是负数。CLOCK_MONOTONIC 从 0 起算，而 CLOCK_REALTIME 是一个正的大数字（2026 年约 1.8e9），所以要把它拉回 0，偏移量必须是负的。

timekeeping 只存 CLOCK_REALTIME 和各个偏移量，不直接存 CLOCK_MONOTONIC 的绝对值。这不是设计洁癖，是性能：settimeofday 只改 xtime_sec，然后把差值塞进 wall_to_monotonic，CLOCK_MONOTONIC 就自动纹丝不动。第十四节展开。

5.x 的形状变了，但恒等式没变：

text
CLOCK_MONOTONIC       = tkr_mono.base + 自上次更新以来的增量
CLOCK_REALTIME        = tkr_mono.base_real + 自上次更新以来的增量
CLOCK_BOOTTIME        = CLOCK_MONOTONIC + offs_boot
CLOCK_TAI             = CLOCK_MONOTONIC + offs_tai
CLOCK_MONOTONIC_RAW   = tkr_raw.base + 自上次更新以来的增量

base 和 base_real 这两个 ktime_t 是预先算好的，读路径上只要一次加法。这就是第十节 tk_update_ktime_data 存在的唯一理由。

三、struct timekeeper 的核心字段 #

3.10 的定义（include/linux/timekeeper_internal.h）：

c
struct timekeeper {
    struct clocksource    *clock;            /* 当前使用的 clocksource */
    u32                   mult;              /* NTP 可调的乘数 */
    u32                   shift;             /* 定点小数位数 */
    cycle_t               cycle_interval;    /* 一个 NTP interval 对应多少周期 */
    cycle_t               cycle_last;        /* 上次更新时的周期值 */
    u64                   xtime_interval;    /* 一个 interval 累计多少「左移后的纳秒」 */
    s64                   xtime_remainder;   /* interval 取整后剩下的零头 */
    u32                   raw_interval;      /* 一个 interval 对应多少纳秒（RAW 轴用） */
    s64                   ntp_error;         /* 累计时间与 NTP 目标时间的偏差 */
    u32                   ntp_error_shift;   /* ntp_error 与 xtime_nsec 的定标差 */
    u64                   xtime_sec;         /* CLOCK_REALTIME 的秒 */
    u64                   xtime_nsec;        /* CLOCK_REALTIME 的纳秒，已左移 shift 位 */
    struct timespec       wall_to_monotonic; /* REALTIME → MONOTONIC 的偏移（负值） */
    ktime_t               offs_real;         /* MONOTONIC → REALTIME 的偏移（ktime 形式） */
    struct timespec       total_sleep_time;  /* 累计睡眠时间 */
    ktime_t               offs_boot;         /* MONOTONIC → BOOTTIME 的偏移 */
    struct timespec       raw_time;          /* CLOCK_MONOTONIC_RAW 的基准 */
    s32                   tai_offset;        /* UTC 到 TAI 的秒数差 */
    ktime_t               offs_tai;          /* MONOTONIC → TAI 的偏移 */
};

逐组解释：

换算三件套：mult、shift、clock。 clock 指向当前参与计时的 clocksource，它一定是系统里评级最高的那个。有更好的注册进来，clocksource 模块会通知 timekeeping 换源，换源流程见第五节之外的第（五）条注释。mult / shift 本来和 clock->mult / clock->shift 一样，但 tk->mult 会被 NTP 微调，clock->mult 不会。这个区别很重要，记住。

累计量：xtime_sec + xtime_nsec。 这两个合起来才是 CLOCK_REALTIME。xtime_sec 是整秒部分；xtime_nsec 是秒内的纳秒部分，但它不是真的纳秒，而是纳秒左移了 shift 位。

素材这里容易读错。它写「当前时间点的值应该是 xtime_sec + (xtime_nsec << shift)」，方向反了。正确方向是右移：

c
/* 3.10 的 tk_xtime() */
ts.tv_sec  = tk->xtime_sec;
ts.tv_nsec = (long)(tk->xtime_nsec >> tk->shift);

xtime_nsec 里存的是「纳秒 × 2^shift」，所以要还原成纳秒得右移。写成左移会让数值大出 2^shift 倍，shift 多数落在 20 到 30 之间，直接爆炸。这一处是硬勘误。

为什么要左移存储。 定点运算的精度全靠这个。每次累加不是加「整数纳秒」，而是加「一个周期数 × mult」，结果保留 shift 位小数。这样周期数到纳秒的除法就变成了右移，小数部分一直不丢，一秒钟累加几十次也不会因为四舍五入而累积漂移。

偏移量：wall_to_monotonic / offs_real / offs_boot / offs_tai。 前两个是同一个东西的两种表示，一个 timespec，一个 ktime_t。两份冗余是刻意的：timespec 版用在走 CLOCK_MONOTONIC 的接口里，做加减法不需要额外的类型转换；ktime 版直接喂给 hrtimer，因为 hrtimer 内部全用 ktime_t。tk_set_wall_to_mono() 里有一行 WARN_ON_ONCE，专门校验这两个值是不是始终互为相反数：

c
static void tk_set_wall_to_mono(struct timekeeper *tk, struct timespec wtm)
{
    struct timespec tmp;

    /* 修改之前先验证 offset_real = -wall_to_monotonic */
    set_normalized_timespec(&tmp, -tk->wall_to_monotonic.tv_sec,
                                 -tk->wall_to_monotonic.tv_nsec);
    WARN_ON_ONCE(tk->offs_real.tv64 != timespec_to_ktime(tmp).tv64);
    tk->wall_to_monotonic = wtm;
    set_normalized_timespec(&tmp, -wtm.tv_sec, -wtm.tv_nsec);
    tk->offs_real = timespec_to_ktime(tmp);
    tk->offs_tai = ktime_sub(tk->offs_real, ktime_set(tk->tai_offset, 0));
}

offs_tai = offs_real - tai_offset，所以 CLOCK_TAI = CLOCK_REALTIME + tai_offset 成立。这个减法方向很容易记反：TAI 比 UTC 快，tai_offset 是正数，所以从 monotonic 到 TAI 的偏移比到 REALTIME 的偏移要小。

NTP 相关：ntp_error、ntp_error_shift。 ntp_error 是「timekeeper 已经累加的时间」和「NTP 认为应该累加的时间」的差，单位是「纳秒左移了 NTP_SCALE_SHIFT 位」。ntp_error_shift = NTP_SCALE_SHIFT - clock->shift，就是两种定标之间的转换量。第十一节展开。

cycle_interval。 这是「一个 NTP 间隔」的周期数，不是「一个 tick」的周期数。NTP 每隔 NTP_INTERVAL_LENGTH 纳秒做一次校正，而 update_wall_time() 调进来的频率是 tick 频率。素材在第六节把它说成「周期性 tick 的 cycle interval」，这是错的。源码里判定跳过用的是 offset < real_tk->cycle_interval，而 offset 是自上次更新以来读到的周期增量，跟 tick 一点关系都没有。NO_HZ 下可以一次跨几十万个 tick 才更新一次，cycle_interval 仍然是同一个常量。

全局变量与保护机制 #

3.10：

c
static struct timekeeper timekeeper;
static DEFINE_RAW_SPINLOCK(timekeeper_lock);
static seqcount_t timekeeper_seq;
static struct timekeeper shadow_timekeeper;

5.10：

c
DEFINE_RAW_SPINLOCK(timekeeper_lock);

static struct {
    seqcount_raw_spinlock_t seq;
    struct timekeeper        timekeeper;
} tk_core ____cacheline_aligned = {
    .seq = SEQCNT_RAW_SPINLOCK_ZERO(tk_core.seq, &timekeeper_lock),
};

两件事变了：

  1. timekeeper 和它的 seqcount 被塞进同一个结构体，加上 ____cacheline_aligned。 读路径要同时摸 seq 和数据，如果两者跨 cache line，每次读都是一个额外的 cache miss。塞一起就是一次。这条注释在 5.10 源码里写得很清楚：The most important data for readout fits into a single 64 byte cache line。
  2. seqcount_t 变成 seqcount_raw_spinlock_t。 后者把「序列号 + 关联的自旋锁」绑成一个对象，write_seqcount_begin() 里会顺带断言锁被持有了（seqcount_assert()），调试配置下能抓出「改了数据却没拿锁」的 bug。语义没变，还是写者独占、读者乐观重试。

shadow_timekeeper 在 5.10 里依然存在，位置从「和 timekeeper 并列」变成了 tk_core 之外的独立静态变量：static struct timekeeper shadow_timekeeper;。

shadow 的用途是缩短临界区。update_wall_time() 里所有繁琐的累加都在 shadow 上做，做完再一次 memcpy 回真的 timekeeper，memcpy 放在 write_seqcount_end() 之前。这样读者被卡的窗口就只有这一次内存拷贝，而不是几十轮 logarithmic_accumulation()。

代价是：别的路径改了 timekeeper（比如 settimeofday），必须同步 shadow，否则下一次 update_wall_time() 会把旧数据覆盖回去。这就是 timekeeping_update(tk, ..., mirror=true) 里那个 mirror 参数的作用。5.10 把它换成了 TK_MIRROR 位。

四、base 与 offsets：两条时间轴的换算基础 #

这一节把两套表示法摊开，因为后面的读、更新、NTP 全建立在它上面。

3.10 的表示法：xtime + 偏移 #

3.10 没有 base 这种预计算结果。读 CLOCK_MONOTONIC 的代码（ktime_get()）：

c
ktime_t ktime_get(void)
{
    struct timekeeper *tk = &timekeeper;
    unsigned int seq;
    s64 secs, nsecs;

    WARN_ON(timekeeping_suspended);

    do {
        seq = read_seqcount_begin(&timekeeper_seq);
        secs  = tk->xtime_sec + tk->wall_to_monotonic.tv_sec;
        nsecs = timekeeping_get_ns(tk) + tk->wall_to_monotonic.tv_nsec;
    } while (read_seqcount_retry(&timekeeper_seq, seq));

    return ktime_add_ns(ktime_set(secs, 0), nsecs);
}

secs 是两项之和，nsecs 也是两项之和。timekeeping_get_ns() 给出「墙钟从上次更新到现在的纳秒偏移」，再加上负的 wall_to_monotonic.tv_nsec。

注意这里 nsecs 允许是负数。ktime_add_ns(ktime_set(secs, 0), nsecs) 能处理负的纳秒增量，ktime_set() 建出来的基准加一个负偏移，结果自然归一化。这也是为什么 wall_to_monotonic 的 tv_nsec 那一半被要求「永远保持正的」（见 5.10 头文件注释：we will ALWAYS keep the tv_nsec part positive so we can use the usual normalization），负号全部由 tv_sec 那部分承担。

5.x 的表示法：base + 增量 #

5.10 把上式的两个「常数部分」提前算好：

c
/* 5.10, tk_update_ktime_data() 的核心 */
seconds = (u64)(tk->xtime_sec + tk->wall_to_monotonic.tv_sec);
nsec    = (u32) tk->wall_to_monotonic.tv_nsec;
tk->tkr_mono.base = ns_to_ktime(seconds * NSEC_PER_SEC + nsec);

注释里给了推导：

text
xtime 口径的单调读法是：
    nsec = (xtime_sec + wtm_sec) * 1e9 + wtm_nsec + now();
ktime 口径的单调读法是：
    nsec = base_mono + now();
推出：
    base_mono = (xtime_sec + wtm_sec) * 1e9 + wtm_nsec

于是 5.10 的 ktime_get() 只剩：

c
/* 5.10 简化形式，实际代码走 timekeeping_get_ns(&tk->tkr_mono) */
now = ktime_to_ns(tkr->base) + timekeeping_delta_to_ns(tkr, delta);

一次加法代替两次加法加一次归一化。收益不只在读路径上，更在 VDSO 上：用户态直接读 base 和 mult/shift 自己算，省掉一次系统调用。所以 5.x 愿意付「每次更新时多算一次 base」的代价。

各 clock 的 base / offset 组合 #

这张表是全篇最该记住的一张。左列是你要的 clock，右列是怎么从硬件增量拼出来。

clock 3.10 拼法 5.10 拼法 关键点
CLOCK_REALTIME xtime_sec + timekeeping_get_ns(tk) tkr_mono.base_real + delta_ns base_real = base + offs_real
CLOCK_MONOTONIC xtime_sec + wall_to_monotonic.tv_sec + timekeeping_get_ns(tk) + wall_to_monotonic.tv_nsec tkr_mono.base + delta_ns 时间增量与 REALTIME 完全相同，只是基准不同

CLOCK_REALTIME_COARSE 的拼法值得单独看一眼。3.10：

c
struct timespec current_kernel_time(void)
{
    struct timekeeper *tk = &timekeeper;
    struct timespec now;
    unsigned long seq;

    do {
        seq = read_seqcount_begin(&timekeeper_seq);
        now = tk_xtime(tk);
    } while (read_seqcount_retry(&timekeeper_seq, seq));

    return now;
}

没有 timekeeping_get_ns()。也就是完全没有碰硬件，直接返回上次 update_wall_time() 留下的值。所以它的误差上限是一整个更新间隔（HZ=250 时约 4ms），好处是快，快到你愿意在一个热循环里反复调。

5.10 的对应函数叫 ktime_get_coarse_real_ts64() / ktime_get_coarse_ts64()，逻辑一样，只是返回 timespec64。函数名变了，current_kernel_time() 在 5.x 已被删除，这是移植代码时最常见的编译错误之一。

WARN_ON(timekeeping_suspended) 的来历 #

ktime_get() 开头有一句 WARN_ON(timekeeping_suspended)。suspend 流程里 timekeeping 会把自己标成 suspended = 1（第十五节），这期间 clocksource 或被断电，read() 出来的值毫无意义。这个断言就是在抓「有人在 suspend 中间去读时间」。

__getnstimeofday() 的处理更克制：读完了、算完了，最后才判断，返回 -EAGAIN。源码注释写得很直白：Do not bail out early, in case there were callers still using the value, even in the face of the WARN_ON. 该给的错误码给，但别把半截数据丢给人家。

五、read 路径：为什么读时间不需要锁 #

clock_gettime() 是系统里被调得最频繁的接口之一。如果每次都抢 timekeeper_lock，那么任何一次读时间都会和其它 CPU 上的读时间互相排队，读写对称，扩展性直接归零。timekeeping 的做法是：读路径完全不拿锁，只做乐观重试。

3.10 的 ktime_get() 模式，全模块统一：

c
do {
    seq = read_seqcount_begin(&timekeeper_seq);
    /* ...读 tk 的若干字段，做计算... */
} while (read_seqcount_retry(&timekeeper_seq, seq));

read_seqcount_begin() 干两件事：等这一轮写者结束（判断序列号的奇偶），然后返回当前序列号。read_seqcount_retry() 再看一次序列号，如果变了，说明期间有写者动过，整段重算。

这里有个细节值得强调：重试是整段重算，不是局部修补。ktime_get() 里 secs 和 nsecs 的读取都在 do-while 里面，就是因为这两个值必须来自同一个快照。如果只把 secs 放在循环内、nsecs 放在循环外，就会出现「秒是新的、纳秒是旧的」这种撕裂，时间会倒退或跳跃。

读路径到底读了几次硬件 #

这是理解 timekeeping 性能的关键。ktime_get() 循环体内只有一次硬件访问，藏在 timekeeping_get_ns() 里：

c
static inline s64 timekeeping_get_ns(struct timekeeper *tk)
{
    cycle_t cycle_now, cycle_delta;
    struct clocksource *clock;
    s64 nsec;

    /* read clocksource: */
    clock = tk->clock;
    cycle_now = clock->read(clock);

    /* calculate the delta since the last update_wall_time: */
    cycle_delta = (cycle_now - clock->cycle_last) & clock->mask;

    nsec = cycle_delta * tk->mult + tk->xtime_nsec;
    nsec >>= tk->shift;

    return nsec + get_arch_timeoffset();
}

clock->read(clock) 就是那一次硬件读。对多数现代 clocksource（TSC、ARM 的 CNTVCT_EL0）来说，这是一条读寄存器指令或 rdtsc，几十个周期。如果你在写 seqcount 期间被抢占了、重试了一次，硬件会被再读一遍，多花几十个周期，但不需要拿锁。

没有锁，就不会有优先级反转，也不会有跨 CPU 的 cache line 争用。只要 timekeeper_seq 所在的那条 cache line 是共享状态、写者不频繁，几核同时读就是纯粹的并发读，扩展性接近线性。

5.10 在这条路上做了两处加固，都值一提：

c
/* 5.10: tk_clock_read() */
static inline u64 tk_clock_read(const struct tk_read_base *tkr)
{
    struct clocksource *clock = READ_ONCE(tkr->clock);

    return clock->read(clock);
}

为什么要 READ_ONCE？注释解释得清楚：seqcount 保证你不会读到不一致的值，但不保证不崩。极端情况下 tkr->clock 会在「读到指针」和「拿指针去调 read()」之间被换源改掉，那么一个 clocksource 的 read() 函数就被喂了另一个 clocksource 的指针。轻则算错，重则空指针。READ_ONCE 让编译器只读一次，配合换源时的 stop_machine()（第十节的换源流程），把窗口压死。

第二处是 timekeeping_get_delta()，5.10 里它嵌套了第二次 seqcount：

c
do {
    seq = read_seqcount_begin(&tk_core.seq);
    now  = tk_clock_read(tkr);
    last = tkr->cycle_last;
    mask = tkr->mask;
    max  = tkr->clock->max_cycles;
} while (read_seqcount_retry(&tk_core.seq, seq));

外层已经有一次 seqcount（ktime_get() 的），这里又套一层。注释说明了理由：外面那层本来就允许「算到一半数据变了、最后丢掉重算」，但 timekeeping_get_delta() 里要做溢出和下溢的告警判定，如果它基于撕裂的数据判出个假阳性，这个假警报就留在 overflow_seen 里了。内层 seqcount 把「读这几个值」变成原子的，判定就变准。

还剩下的问题 #

软中断、NMI 里不能睡、不能让读者无限重试。所以除了主路径，5.x 还开了两条快路径：

  • ktime_get_mono_fast_ns() / ktime_get_raw_fast_ns() / ktime_get_real_fast_ns()：读 tk_fast_mono / tk_fast_raw，那是一对 tk_read_base 组成的双缓冲数组，用 raw_write_seqcount_latch() 更新。读者按 seqcount 的最低位选数组下标，写者轮流改另一份。NMI 安全，任何上下文都能调。
  • 代价：快路径不保证跨更新单调。5.10 源码的注释图写得很诚实：如果更新把斜率调小了，被强制切到尚未更新的第二份数组的读者还在用旧斜率，于是 reader 6 will observe time going backwards versus reader 5。调用方得自己扛。

这张图我在下面复刻一下，因为它解释了「为什么 NMI 里的时间戳会大于后面的时间戳」：

text
tmono

只有 NMI 恰好打在更新中间的那次读会看到这个。正常 CPU 上下文不会。

六、seqcount：无锁读的一致性保证 #

上一节讲了「怎么用」，这节讲「为什么够用」。

seqcount 不是 Seqlock 的简写。两者的区别是：Seqlock 带锁，写者需要拿 spinlock_t；seqcount 只是一个计数器，锁要另外配。timekeeping 配的是 timekeeper_lock，3.10 里它们是两个并列的全局量，5.10 里被 seqcount_raw_spinlock_t 绑成了一个。

写者一侧的固定套路：

c
raw_spin_lock_irqsave(&timekeeper_lock, flags);
write_seqcount_begin(&timekeeper_seq);

/* 改 timekeeper 的字段 */

timekeeping_update(tk, clearntp, mirror);

write_seqcount_end(&timekeeper_seq);
raw_spin_unlock_irqrestore(&timekeeper_lock, flags);

write_seqcount_begin() 把序列号加一（变奇数），write_seqcount_end() 再加一（变偶数）。读者看到奇数就说明写者正在改，等到偶数才往下走。看到两个相同的偶数，说明这一轮没有写者动过，读到的数据自洽。

为什么不用锁 #

方案 读开销 多核扩展性 NMI 里能用吗 timekeeping 选了它吗
读也拿 raw_spinlock 一次原子加锁 差，读写互斥 不能 否
RCU + 指针替换 读侧近乎免费 好 能 否（更新太频繁）
seqcount 乐观重试 两次读序列号 好，写者极少 勉强，重试即死 是
seqcount_latch 双缓冲 两次读序列号 + 选下标 好 能 是（fast timer）

选 seqcount 的理由：写者频率是 tick 级别（HZ=250 就是每秒 250 次），读频率是百万级每秒。让稀有的写者去承担「推进序列号 + 让读者重试」的成本，比让海量的读者去抢锁划算得多。

RCU 不行，是因为 timekeeper 是原地修改的，不是指针替换。要做成 RCU 得每次更新分配一份新副本，tick 频率下分配器会被打爆。5.10 的 tk_fast 用双缓冲数组，算是把「指针替换」这条路局部实现了，但只给 NMI 快路径用。

临界区的位置很讲究 #

拿 do_settimeofday() 看一次完整的写者流程：

c
int do_settimeofday(const struct timespec *tv)
{
    struct timekeeper *tk = &timekeeper;
    struct timespec ts_delta, xt;
    unsigned long flags;

    if (!timespec_valid_strict(tv))
        return -EINVAL;

    raw_spin_lock_irqsave(&timekeeper_lock, flags);
    write_seqcount_begin(&timekeeper_seq);

    timekeeping_forward_now(tk);

    xt = tk_xtime(tk);
    ts_delta.tv_sec  = tv->tv_sec  - xt.tv_sec;
    ts_delta.tv_nsec = tv->tv_nsec - xt.tv_nsec;

    tk_set_wall_to_mono(tk, timespec_sub(tk->wall_to_monotonic, ts_delta));

    tk_set_xtime(tk, tv);

    timekeeping_update(tk, true, true);

    write_seqcount_end(&timekeeper_seq);
    raw_spin_unlock_irqrestore(&timekeeper_lock, flags);

    clock_was_set();

    return 0;
}

三段结构值得抄：

  1. 先 timekeeping_forward_now()。把「上次更新到现在」这段还没记账的时间先累加进去。做完之后 cycle_last 等于刚读到的硬件值，xtime_sec/xtime_nsec 精确对应「此刻」。不这么做的话，你设的时间会跟还没累积的那段增量打架，读者会看到一次诡异的跳跃。
  2. 改 wall_to_monotonic 和 xtime_sec 是同一个临界区里的。中间任何时刻读者都不能进来，否则会看到「新墙上时间 + 旧偏移」的组合，CLOCK_MONOTONIC 就跳了。
  3. clock_was_set() 在临界区外面调。它要通知 hrtimer 重算，要唤起点东西，放在 seqcount 里面等于让读者陪着等。

5.10 里 do_settimeofday() 改成了 do_settimeofday64()，收 timespec64，timekeeping_update() 的 bool 参数换成了 TK_CLEAR_NTP | TK_MIRROR | TK_CLOCK_WAS_SET 位掩码。结构没变。

序列号还会被用作版本号 #

clock_was_set_seq（4.4 起）和 cs_was_changed_seq（5.x）是独立的计数器，不参与 seqcount 的奇偶判定，而是当「事件序号」用。hrtimer 在中断里缓存一份偏移量，下次进来先比 cwsseq 有没有变，变了才重新读 offs_real / offs_boot / offs_tai。这样改时间的处理器不会被 hrtimer 中断反复拖进去重读。

c
/* 5.10, ktime_get_update_offsets_now() 节选 */
if (*cwsseq != tk->clock_was_set_seq) {
    *cwsseq    = tk->clock_was_set_seq;
    *offs_real = tk->offs_real;
    *offs_boot = tk->offs_boot;
    *offs_tai  = tk->offs_tai;
}

注意这个读也套在 read_seqcount_begin/retry 里，和 base、nsecs 一起。偏移量和时间基准必须同源。

七、timespec64 与 ktime_t：两种时间表示 #

内核里同一时刻有好几种写法，混用是移植代码时最容易出的错。

类型 定义 精度 适用场合 3.10 5.10
struct timespec time_t tv_sec + long tv_nsec 1ns，32 位机上会退化 用户态接口 有 有（但内核内部已不用）
struct timespec64 time64_t + long 1ns，宽度固定 内核内部统一表示 部分有 全面使用
struct timeval time_t tv_sec + suseconds_t tv_usec 1us gettimeofday 有 有
ktime_t（64 位） s64，直接是纳秒 1ns hrtimer、偏移量运算 有 有
ktime_t（32 位，无 CONFIG_KTIME_SCALAR） union { s64 tv64; struct { s32 sec, nsec; }; } 1ns 同上 有 有

timespec 在 32 位机上的坑 #

struct timespec 的 tv_sec 在 32 位机上是有符号 long，2038 年溢出。所以内核内部用了 timespec64，tv_sec 固定 64 位。3.10 里 timespec64 已经存在，但 struct timekeeper 的大部分字段还在用 struct timespec；4.4 把它们全部换掉了。你那还停留在 3.10 风格的代码，在 32 位 ARM 上是有 2038 隐患的，时间紧可以先不动，但要知道这账迟早得还。

ktime_t 的两种形态 #

KTIME_SEC_MAX 就是给这个类型兜底的：

c
#define KTIME_MAX      ((s64)~((u64)1 << 63))

#if (BITS_PER_LONG == 64)
# define KTIME_SEC_MAX  (KTIME_MAX / NSEC_PER_SEC)
#else
# define KTIME_SEC_MAX  LONG_MAX
#endif

KTIME_MAX 是 s64 的正上限，2^63 - 1，约 9.22e18。除以 1e9 得到约 9.22e9 秒，也就是约 292 年。ktime_t 存的是「自某个基准以来的纳秒数」，一年约 3.15e16 纳秒，292 年就是 s64 的极限。

32 位机上另有讲究。如果 CONFIG_KTIME_SCALAR 没开，ktime_t 用「秒 + 纳秒」两段存，能表示的绝对时间远超 292 年，但每次加减都得分别处理两个域。这也是 ktime_get() 里要写 ktime_add_ns(ktime_set(secs, 0), nsecs) 而不是简单的加法：

c
/*
 * Use ktime_set/ktime_add_ns to create a proper ktime on
 * 32-bit architectures without CONFIG_KTIME_SCALAR.
 */
return ktime_add_ns(ktime_set(secs, 0), nsecs);

源码里这句注释就是答案。ktime_set(secs, 0) 先把秒部建好，ktime_add_ns() 再把纳秒增量加进去，两段域各自归一化。如果图省事直接算 secs * NSEC_PER_SEC + nsecs，在 32 位机上是 s64 乘法，secs 是 2026 年那种量级时，2026 年 × 1e9 不会溢出（才 1.8e18，s64 顶得住），但再过两百年就顶不住了。内核选了从一开始就不给自己埋雷。

timespec_valid_strict() 校验的就是这两条边界：

text
tv_sec  ∈ [0, KTIME_SEC_MAX)
tv_nsec ∈ [0, NSEC_PER_SEC)

timekeeping_init() 里从 RTC 读出时间后第一件事就是校验，不合法就警告并归零（Persistent clock returned invalid value! Check your CMOS/BIOS settings.）。这句 pr_warn 你在板子上遇到过，基本就两种情况：RTC 电池没电，或者 I2C 上那颗 RTC 芯片压根没应答。

什么时候用哪个 #

经验法则：

  • 对外边界（系统调用、/proc、VDSO）用 timespec64 或 timeval。
  • 内部运算（偏移量、hrtimer、超时比较）用 ktime_t，因为它就是一个整数，加减比较都不会有归一化问题。
  • timekeeper 的累计量用「秒 + 左移纳秒」这个自定义形式（xtime_sec / xtime_nsec），因为要保住 shift 位小数。

这三个域之间的转换点，就是 tk_xtime()、ktime_set()、timespec64_to_ktime() 那几个函数。写代码时把转换都收在边界上，中间不要乱换，能省掉很多 tv_nsec >= NSEC_PER_SEC 的诡异 bug。

八、从 cycles 到 nanoseconds：mult 与 shift #

这一节是整篇的技术核心。搞懂了 mult/shift，前面所有「为什么要左移存储」「精度损失从哪来」的问题都会自己解开。

问题 #

clocksource 给你的是周期数。你知道的是一秒对应多少个周期，比如 24MHz 的 ARM Generic Timer，1s = 24,000,000 个周期。要换纳秒：

text
nsec = cycles * 1e9 / 24000000

内核要在一秒钟里做几十万次这种换算（每次 clock_gettime 都来一次），除法太贵。32 位机上更没有 64 位除法指令，只能走 do_div()，几十个周期起步。这条路走不通。

解法：定点数 #

把 1e9 / freq 这个「每周期多少纳秒」的系数，用一个「整数部分 + 小数部分」的定点数表示：

text
nsec ≈ (cycles * mult) >> shift

mult 是 32 位无符号整数，shift 是它作为一个 32.32 定点数时的小数位数。

标准说法是「mult / 2^shift 就是每周期多少纳秒」。更准确的说法：mult 是一个被 shift 位小数扩展过的整数，实际乘数是 mult / 2^shift。当你把 cycles 乘上 mult，再右移 shift 位，等价于：

text
nsec = cycles * (mult / 2^shift)
     = cycles * mult / 2^shift

一次 64 位乘法和一次移位，代替了一次 64 位除法。这是整个时间子系统里最值钱的一个技巧。

「32.32 定点数」这个说法要拆开看。mult 本身只有 32 位，所以它不能同时容纳 32 位整数和 32 位小数。真正的表示范围是「shift 位小数 + (32 - shift) 位整数」。之所以叫 32.32，指的是运算过程中：cycles * mult 这一步，如果 cycles 是 32 位、mult 是 32 位，乘积就是 64 位，正好是一份「32 位整数部分 + 32 位小数部分」的 32.32 数，右移 shift 位就得到纳秒。所以 32.32 描述的是乘积的形态，不是 mult 的形态。

具体数值 #

以 init_tsc_clocksource() 这一类初始化逻辑为例，clocksource 注册时会调：

c
/* 各版本一致的核心表达式，v3.10 ~ v6.x */
clocksource_calc_mult_shift(&cs->mult, &cs->shift, freq, maxsec);

clocksource_calc_mult_shift() 按「mult 不溢出、相对误差最小」两个约束挑参数，挑出来的 shift 大致落在 20 到 30 之间。以 24MHz 为例，每周期 41.666...纳秒，mult/2^shift 要逼近这个值。取 shift = 26，那么 mult ≈ 41.6667 × 2^26 ≈ 2.796e9，塞得进 u32（上限 4.29e9）。取 shift = 28 就溢出了。函数自己会算这个边界，你不用手推。

这个函数的具体选值算法我没逐行核对，标「未验证」。但 shift 的典型取值区间和「乘积 64 位、右移还原纳秒」这个结构是确定的。

clocksource_cyc2ns() #

include/linux/clocksource.h 里的内联函数，3.10 到 6.x 一直是这个形状：

c
/**
 * clocksource_cyc2ns - converts clocksource cycles to nanoseconds
 * @cycles: cycles
 * @mult:   cycle to nanosecond multiplier
 * @shift:  cycle to nanosecond divisor (power of two)
 *
 * Converts cycles to nanoseconds, using the ex and shift mult/shift pair
 */
static inline s64 clocksource_cyc2ns(cycle_t cycles, u32 mult, u32 shift)
{
    return ((u64) cycles * mult) >> shift;
}

三行，没有别的。整个时间换算的全部内容就在这里。

注意几个细节：

  1. (u64) cycles 的强转是必需的。 如果 cycles 是 32 位而 mult 也是 32 位，不转成 64 位就直接乘，乘积截断成 32 位，结果完全错。
  2. >> shift 是逻辑右移，作用在 u64 上。
  3. 函数返回 s64，但中间全是无符号运算。cycles * mult 的最大值：cycles 最大约 2^32，mult 最大约 2^32，乘积能顶到 2^64。右移之后落在 u64 能表示的范围内，再当 s64 用。

和 NTP 结合后的版本 #

timekeeping_get_ns() 用的不是纯 clocksource_cyc2ns()，而是把「累计的小数部分」也加进去了：

c
nsec = cycle_delta * tk->mult + tk->xtime_nsec;
nsec >>= tk->shift;

对比一下：

text
clocksource_cyc2ns(delta, clock->mult, clock->shift)
    = (delta * clock->mult) >> clock->shift          ← 只看增量，不带历史

timekeeping_get_ns(tk)
    = (delta * tk->mult + tk->xtime_nsec) >> tk->shift  ← 增量 + 历史小数

两个差别：

  • tk->mult 而不是 clock->mult。 前者带 NTP 微调，后者是硬件原值。
  • 带上 tk->xtime_nsec。 这是上一次更新时留下的、左移后的纳秒零头。不带它，每次读时间都从零开始算小数，误差会一次次累积。带上它，小数部分就串起来了。

这个式子也解释了 RAW 轴和 MONO 轴的本质差别。5.10 里 tkr_raw 的 xtime_nsec 同样是左移存储的，timekeeping_delta_to_ns() 对两条轴一视同仁。区别在分子上那个 mult：RAW 轴用的是 tkr_raw.mult，NTP 从不碰它。所以 RAW 轴累出来的就是硬件计数器的真实速率，误差只剩定点截断那一项，没有 NTP 的干预痕迹。

常见频率的 mult/shift 对照 #

shift 和 mult 是运行时算出来的。下表按「mult 落进 u32 且相对误差最小」那一档估算，只是示意，实际值以 clocksource_calc_mult_shift() 的输出为准（未验证）：

100 Hz 10,000,000 8 2,560,000,000 约 0.4 ppm jiffies 模拟时钟源（clocksource_default_clock()）
24 MHz 41.6667 26 约 2,796,202,667 约 0.36 ppm ARM Generic Timer 常见频率

1 GHz 1 30 1,073,741,824 约 0.93 ppm 高频 TSC

25MHz 那一档要单独说：每周期 40ns，shift = 27 时 mult = 40 × 2^27 = 5,368,709,120，已经越过 u32 上限 4,294,967,295，只能退到 shift = 26，mult = 2,684,354,560。这一档是「shift 选小了精度掉、选大了溢出」最典型的例子。

最后一行那种情况最值得看：shift = 30 时 mult ≈ 3.07e8，只有 u32 上限的 7%。这说明定点数的小数位还剩很多余量，cycles * mult 的乘积离 64 位上限还远。反过来，24MHz 那一行 mult 已经快到 2.8e9，shift 只要多一位就溢出。频率越低，要用的小数位越多，u32 的余量越紧。 这就是 shift 落在 20~30 这个区间的原因。

九、精度损失从哪来 #

定点换算一定有误差。关键是算清误差有多大、会不会累积、能不能修。

第一处：mult 本身是近似值 #

mult / 2^shift 只能逼近 1e9 / freq，无法精确相等（除非 freq 恰好是 2 的幂且能整除 1e9）。截断到 u32 之后，相对误差的量级是：

text
相对误差 ≈ 1 / mult

mult ≈ 2.8e9 时，相对误差约 3.6e-10，也就是约 0.36 ppm。一秒对应 1e9 纳秒，误差约 0.36 纳秒/秒。一天累积不到 31 微秒。这个量级完全可接受，而且这不是「漂移」，是恒定比例的速度偏差，NTP 一看就能测出来（第十一节）。

mult 越小，相对误差越大。3.5GHz TSC 那一行 mult ≈ 3.07e8，相对误差约 3.3e-9，也就是 3.3 ppm。但这个 3.3ppm 是相对纳秒的，不是相对秒的。cycles = 3.5e9 时，cycles * mult 的量级是 1.07e18，离 2^63 还有 8 倍余量，右移 30 位之后结果的相对误差依然是 1/mult 那一档。

第二处：右移截断，每次读都丢 #

c
nsec = (delta * mult + xtime_nsec) >> shift;

>> 是截断，不是四舍五入。丢掉的是 shift 位以下的小数，最多 2^-shift 个纳秒。

但注意：xtime_nsec 是持久化的，它保留着上次更新时留下的零头。所以这次读丢掉的截断量，下一次计算时还在 xtime_nsec 里参与运算，不会凭空消失。也就是说，读路径上的截断是可恢复的，累加路径才决定长期精度。

真正会累积的是 update_wall_time() 那一侧。3.10 的完整循环：

text
while (offset >= cycle_interval) {
    offset -= cycle_interval;
    xtime_nsec += xtime_interval;     /* 一个 interval 的「左移纳秒」 */
    accumulate_nsecs_to_secs();
}

xtime_interval = cycle_interval * mult，是整数。而「一个 NTP interval 应该对应多少左移纳秒」是 NTP_INTERVAL_LENGTH << shift，这个值一般不能被 cycle_interval * mult 整除。差值就是 xtime_remainder：

c
tk->xtime_interval  = (u64) interval * clock->mult;
tk->xtime_remainder = ntpinterval - tk->xtime_interval;

ntpinterval 就是 NTP_INTERVAL_LENGTH << clock->shift。xtime_remainder 就是「取整取掉的那点零头」。源码把它记下来，后面在 logarithmic_accumulation() 里当误差项扣掉：

c
tk->ntp_error -= (tk->xtime_interval + tk->xtime_remainder) << (tk->ntp_error_shift + shift);

不记这个零头，ntp_error 就测不准，NTP 在校正时会把「本该属于取整误差的部分」当成「晶振真的快了」，然后越校越偏。

第三处：cycle_interval 取整 #

再看 cycle_interval 怎么来的：

c
tmp = NTP_INTERVAL_LENGTH;
tmp <<= clock->shift;
ntpinterval = tmp;
tmp += clock->mult / 2;
do_div(tmp, clock->mult);
if (tmp == 0)
    tmp = 1;
interval = (cycle_t) tmp;

NTP_INTERVAL_LENGTH << shift 除以 mult，得到「这么多纳秒对应多少个周期」。tmp += clock->mult / 2 是四舍五入（加半个除数）。if (tmp == 0) tmp = 1; 是个保护：极慢的 clocksource 会算出来 0 个周期，那就至少算 1 个，不然 cycle_interval 为 0 会让后面的 while (offset >= cycle_interval) 变成死循环。

取整之后，interval * mult 和原来的 ntpinterval 之间又差了一点，这就是上面那个 xtime_remainder。

第四处：NTP_INTERVAL_LENGTH 与 tick 的差异 #

NTP 的校正周期不是 tick 周期。tick 是 4ms（HZ=250），而 NTP_INTERVAL_LENGTH 是另一回事。两者不相等，意味着每次 tick 只是「能凑够一个 interval」才推进，凑不够就跳过：

c
offset = (clock->read(clock) - clock->cycle_last) & clock->mask;

/* Check if there's really nothing to do */
if (offset < real_tk->cycle_interval)
    goto out;

这就是为什么 cycle_interval 不能理解成「tick 的周期数」。tick 频率变了（CONFIG_HZ 不同），cycle_interval 不变。

误差能不能消 #

能，而且是 NTP 在消。第十一节。

小结：损失的量级 #

来源 量级 是否会累积 谁能修
mult 截断 约 0.4~3 ppm 会，但恒定 NTP 的 freq 校正
右移截断（读路径） ≤ 1ns 不会，零头留在 xtime_nsec 不需要
cycle_interval 取整 每 interval 不到 1 个 mult 由 xtime_remainder 记账 ntp_error
晶振本身 几十到几百 ppm 会，随温度变 NTP 的 freq 校正
clocksource 分辨率 1/freq 秒 不会 换更好的 clocksource

最后一行才是多数系统的真瓶颈。24MHz 的 counter，一个周期就是 41.7ns，clock_gettime 的最低位再怎么算也不会比这更准。想再准，只能换硬件或者干脆用 CLOCK_MONOTONIC_RAW 绕开 NTP 自己算。

十、更新路径：tk_update_ktime_data #

这一节拆 update_wall_time() 的全流程。3.10 和 5.10 的结构基本一样，后者多了一个 tk_update_ktime_data() 函数把预计算单独抽出来。

3.10 的完整流程 #

c
static void update_wall_time(void)
{
    struct clocksource *clock;
    struct timekeeper *real_tk = &timekeeper;
    struct timekeeper *tk = &shadow_timekeeper;
    cycle_t offset;
    int shift = 0, maxshift;
    unsigned long flags;

    raw_spin_lock_irqsave(&timekeeper_lock, flags);

    /* 确保已经完成 resume */
    if (unlikely(timekeeping_suspended))
        goto out;

    clock = real_tk->clock;

#ifdef CONFIG_ARCH_USES_GETTIMEOFFSET
    offset = real_tk->cycle_interval;
#else
    offset = (clock->read(clock) - clock->cycle_last) & clock->mask;
#endif

    /* 还没攒够一个 interval，直接走人 */
    if (offset < real_tk->cycle_interval)
        goto out;

    /*
     * NO_HZ 下一次要补很多个 interval。
     * 找出「小于 offset 的最大 2 的幂倍 interval」，一次吃掉一大块，
     * 然后再用更小的块补剩下的。
     */
    shift = ilog2(offset) - ilog2(tk->cycle_interval);
    shift = max(0, shift);
    maxshift = (64 - (ilog2(ntp_tick_length())+1)) - 1;
    shift = min(shift, maxshift);
    while (offset >= tk->cycle_interval) {
        offset = logarithmic_accumulation(tk, offset, shift);
        if (offset < tk->cycle_interval<<shift)
            shift--;
    }

    timekeeping_adjust(tk, offset);
    old_vsyscall_fixup(tk);
    accumulate_nsecs_to_secs(tk);

    write_seqcount_begin(&timekeeper_seq);
    clock->cycle_last = tk->cycle_last;
    memcpy(real_tk, tk, sizeof(*tk));
    timekeeping_update(real_tk, false, false);
    write_seqcount_end(&timekeeper_seq);
out:
    raw_spin_unlock_irqrestore(&timekeeper_lock, flags);
}

逐段拆：

(1) timekeeping_suspended 检查。 suspend 中间不能推进时间。挂了就退出，什么也不做。

(2) 读硬件算 offset。 & clock->mask 处理回绕。CONFIG_ARCH_USES_GETTIMEOFFSET 那条分支是给那些「没法直接读 counter」的老架构留的后路，直接把 offset 设成一个 interval。

(3) 不够一个 interval 就跳过。 这是「timekeeping 按自己的节奏更新」的实现位置。tick 来了但时间不够，就什么也不做。

(4) ilog2 定步长。 这是 NO_HZ 的关键优化。假设系统刚从深度空闲里醒过来，offset 是 100 万个 interval。如果一个个吃，while 循环要转 100 万次，全程握着 timekeeper_lock。用「2 的幂倍」的策略：第一次吃 2^k 个 interval，第二次吃 2^(k-1) 个，……，总共只要大约 k 轮。logarithmic_accumulation 就是这么得名的。

maxshift 那一行是个防溢出保护：保证 xtime_interval << shift 不会超过 s64。

(5) logarithmic_accumulation()。 一次吃掉 shift 级的量：

c
static cycle_t logarithmic_accumulation(struct timekeeper *tk, cycle_t offset,
                                        u32 shift)
{
    cycle_t interval = tk->cycle_interval << shift;
    u64 raw_nsecs;

    /* offset 没有大到这个级别，什么也不做 */
    if (offset < interval)
        return offset;

    offset -= interval;
    tk->cycle_last += interval;

    tk->xtime_nsec += tk->xtime_interval << shift;
    accumulate_nsecs_to_secs(tk);

    /* 累加 RAW 轴 */
    raw_nsecs = (u64)tk->raw_interval << shift;
    raw_nsecs += tk->raw_time.tv_nsec;
    if (raw_nsecs >= NSEC_PER_SEC) {
        u64 raw_secs = raw_nsecs;
        raw_nsecs = do_div(raw_secs, NSEC_PER_SEC);
        tk->raw_time.tv_sec += raw_secs;
    }
    tk->raw_time.tv_nsec = raw_nsecs;

    /* 累加 NTP 偏差 */
    tk->ntp_error += ntp_tick_length() << shift;
    tk->ntp_error -= (tk->xtime_interval + tk->xtime_remainder) <<
                     (tk->ntp_error_shift + shift);

    return offset;
}

三步：推进 xtime、推进 raw_time、记账 ntp_error。三条轴在同一个函数里往前挪，互相之间的相对速率由 cycle_interval 和 raw_interval 决定。

注意 raw_time 在 3.10 里是 timespec，所以这段有 do_div 的秒进位。5.10 把 RAW 轴改成了 tkr_raw.xtime_nsec（左移纳秒），进位逻辑就变成和 mono 轴一样的右移比较了，do_div 消失。

(6) timekeeping_adjust(tk, offset)。 NTP 校正最后一轮，第十一节。offset 是吃完所有整 interval 之后剩下的零头周期。

(7) accumulate_nsecs_to_secs(tk)。 最后把 xtime_nsec 里攒够的整秒挤到 xtime_sec 里，顺带处理闰秒。

(8) 提交。 进 seqcount，把 shadow 拷回真的 timekeeper，再调 timekeeping_update()。注释说得很明确：The memcpy must come last. Do not put anything here!（5.10）——memcpy 之后不能再碰任何东西，否则读者会看到一个半新半旧的 timekeeper。

5.10 的 tk_update_ktime_data() #

5.10 把「算 base」这一步单独抽出来，叫 tk_update_ktime_data()。这是全篇最该逐行读的函数：

c
/*
 * Update the ktime_t based scalar nsec members of the timekeeper
 */
static inline void tk_update_ktime_data(struct timekeeper *tk)
{
    u64 seconds;
    u32 nsec;

    /*
     * The xtime based monotonic readout is:
     *      nsec = (xtime_sec + wtm_sec) * 1e9 + wtm_nsec + now();
     * The ktime based monotonic readout is:
     *      nsec = base_mono + now();
     * ==> base_mono = (xtime_sec + wtm_sec) * 1e9 + wtm_nsec
     */
    seconds = (u64)(tk->xtime_sec + tk->wall_to_monotonic.tv_sec);
    nsec = (u32) tk->wall_to_monotonic.tv_nsec;
    tk->tkr_mono.base = ns_to_ktime(seconds * NSEC_PER_SEC + nsec);

    /*
     * xtime 的纳秒部分和 wall_to_monotonic 的纳秒部分之和
     * 会大于等于一秒。更新 tk->ktime_sec 之前要先考虑这点。
     */
    nsec += (u32)(tk->tkr_mono.xtime_nsec >> tk->tkr_mono.shift);
    if (nsec >= NSEC_PER_SEC)
        seconds++;
    tk->ktime_sec = seconds;

    /* 更新 raw 轴的基准 */
    tk->tkr_raw.base = ns_to_ktime(tk->raw_sec * NSEC_PER_SEC);
}

三个要点：

第一，base 只是「常数部分」的重排，不引入新信息。 推导里那行 nsec = base_mono + now() 中的 now() 就是硬件增量换算后的纳秒。把它挪到读路径上，每次读少一次加法和一次归一化。

第二，ktime_sec 的进位。 wall_to_monotonic.tv_nsec 和 xtime_nsec >> shift 各自都小于 NSEC_PER_SEC，加起来会到 2e9 - 2。所以要判一次 >= NSEC_PER_SEC，进位到 seconds。不做这一步，ktime_sec 会少一秒。这是 5.x 引入 base 时新加的坑，3.10 没有这个问题（3.10 的 ktime_sec 在哪个函数里维护，未验证）。

第三，raw 轴的 base 只取 raw_sec。 tkr_raw.base = ns_to_ktime(tk->raw_sec * NSEC_PER_SEC)，不带任何偏移。因为 CLOCK_MONOTONIC_RAW 就是从 0 起算的纯硬件时间，没有偏移可言。

tk_update_ktime_data() 在哪儿被调？

c
/* 5.10, timekeeping_update() */
static void timekeeping_update(struct timekeeper *tk, unsigned int action)
{
    if (action & TK_CLEAR_NTP) {
        tk->ntp_error = 0;
        ntp_clear();
    }

    tk_update_leap_state(tk);
    tk_update_ktime_data(tk);

    update_vsyscall(tk);
    update_pvclock_gtod(tk, action & TK_CLOCK_WAS_SET);

    tk->tkr_mono.base_real = tk->tkr_mono.base + tk->offs_real;
    update_fast_timekeeper(&tk->tkr_mono, &tk_fast_mono);
    update_fast_timekeeper(&tk->tkr_raw,  &tk_fast_raw);

    if (action & TK_CLOCK_WAS_SET)
        tk->clock_was_set_seq++;

    if (action & TK_MIRROR)
        memcpy(&shadow_timekeeper, &tk_core.timekeeper,
               sizeof(tk_core.timekeeper));
}

顺序有讲究：

  1. 先 tk_update_leap_state()，把待定闰秒换算成单调时间点。
  2. 再 tk_update_ktime_data()，算出 base。
  3. 然后才 base_real = base + offs_real。这个顺序不能反，base_real 依赖 base。
  4. update_vsyscall() / update_pvclock_gtod() 把新的 base、mult、shift 推给用户态可读的页和 KVM 的 pvclock。
  5. update_fast_timekeeper() 刷 NMI 快路径的两份双缓冲。
  6. clock_was_set_seq++ 通知 hrtimer 偏移变了。
  7. TK_MIRROR 的 memcpy 放在最后。注释写得很直白：The mirroring of the data to the shadow-timekeeper needs to happen last here to ensure we don't over-write the timekeeper structure on the next update with stale data. 如果提前镜像，中间几步的修改就没进 shadow，下一轮 update_wall_time() 会用旧的 shadow 覆盖回去。

NTP_INTERVAL_LENGTH #

这个宏决定「多久校正一次」。素材没给值，我查到的定义（3.8 起引入 NTP_INTERVAL_LENGTH 宏，之前是 NTP_INTERVAL_FREQ）在 include/linux/timex.h 或 ntp_internal.h：

c
#define NTP_INTERVAL_FREQ  (HZ << 1)
#define NTP_INTERVAL_LENGTH (NSEC_PER_SEC/NTP_INTERVAL_FREQ)

HZ<<1 就是 tick 频率的两倍，所以 NTP_INTERVAL_LENGTH 是半个 tick 周期。HZ=250 时约 2ms；HZ=1000 时约 0.5ms。这个「取什么值」我标「未验证」，因为不同版本或做过微调，但它和 tick 频率挂钩、不是 tick 周期本身这一点是确定的。

十一、NTP 校正：offset 与 freq #

timekeeping 不懂 NTP 协议，只管收两个数。

两个输入 #

概念 在 ntp.c 里的名字 语义 谁产生
相位偏移 time_offset 「我认为的现在」和「NTP 认为的现在」差多少，单位「纳秒左移 NTP_SCALE_SHIFT 位」 PLL 每次 update 算出来
频率校正 time_freq 晶振快/慢多少 ppm，单位 scaled_ppm PLL 长期收敛出来

time_freq 进到 timekeeping 之后表现成 tk->mult 和 clock->mult 的差。你在 timekeeping_adjust() 里能看到 maxadj 的断言：

c
if (unlikely(tk->clock->maxadj &&
    (tk->mult + adj > tk->clock->mult + tk->clock->maxadj))) {
    printk_once(KERN_WARNING
        "Adjusting %s more than 11%% (%ld vs %ld)\n",
        tk->clock->name, (long)tk->mult + adj,
        (long)tk->clock->mult + tk->clock->maxadj);
}

maxadj 是 clocksource 能接受的最大调整幅度，注释说 11%。NTP 最多只能把 mult 推偏 11%，再多就报警并且不再加重校正。这是防核弹的保险：如果 PLL 因为某种原因（拿到垃圾时间样本、或者对端在骗它）持续往一个方向推，mult 被推到 2.8e9 以上会溢出，时间会突然疯掉。有个 11% 的硬上限，至少能保证时间还在「快一点/慢一点」的量级，而不是「一年后见」。

ntp_error 的记账 #

每推进一个 interval，logarithmic_accumulation() 做两件事：

c
tk->ntp_error += ntp_tick_length() << shift;                 /* NTP 认为该走这么多 */
tk->ntp_error -= (tk->xtime_interval + tk->xtime_remainder) << (tk->ntp_error_shift + shift);
                                                              /* 实际走了这么多 */

两边单位不同，靠 ntp_error_shift 对齐。ntp_error_shift = NTP_SCALE_SHIFT - clock->shift，把 clock->shift 定标换算到 NTP_SCALE_SHIFT 定标。

ntp_error > 0 表示「实际走得比 NTP 要求的多」，也就是时间跑快了，要减速。ntp_error < 0 表示跑慢了，要加速。

timekeeping_adjust() #

3.10 的完整实现（省略 maxadj 断言和末尾的下溢处理，前面贴过）：

c
static void timekeeping_adjust(struct timekeeper *tk, s64 offset)
{
    s64 error, interval = tk->cycle_interval;
    int adj;

    /*
     * error 是 ntp_error 换算到 clocksource 定标后的值。
     * 这里只右移 ntp_error_shift - 1 位，等于 error 被算成了原来 2 倍，
     * 省了一次对 interval 的除法，同时保留「error > interval」
     * 这个比较仍然是在判断「error 是否超过半个 interval」。
     */
    error = tk->ntp_error >> (tk->ntp_error_shift - 1);
    if (error > interval) {
        error >>= 2;
        if (likely(error <= interval))
            adj = 1;
        else
            adj = timekeeping_bigadjust(tk, error, &interval, &offset);
    } else {
        if (error < -interval) {
            error >>= 2;
            if (likely(error >= -interval)) {
                adj = -1;
                interval = -interval;
                offset = -offset;
            } else {
                adj = timekeeping_bigadjust(tk, error, &interval, &offset);
            }
        } else {
            goto out_adjust;         /* 误差在半个 interval 内，不动 */
        }
    }

    tk->mult += adj;
    tk->xtime_interval += interval;
    tk->xtime_nsec -= offset;
    tk->ntp_error -= (interval - offset) << tk->ntp_error_shift;

out_adjust:
    /* xtime_nsec 下溢时，把它推回 0，把差额记进 ntp_error 下次再修 */
    if (unlikely((s64)tk->xtime_nsec < 0)) {
        s64 neg = -(s64)tk->xtime_nsec;
        tk->xtime_nsec = 0;
        tk->ntp_error += neg << tk->ntp_error_shift;
    }
}

这段最绕的是 tk->xtime_nsec -= offset;。源码注释里有一大段推导，值得抄下来：

text
现在的时间（左移纳秒）是：
    now = (offset * adj) + xtime_nsec

我们调了频率，但时间必须连续：不能倒退，也不能突进。
所以相同的 offset 值，调整前后算出来的时间必须相等：
    now = (offset * adj_1) + xtime_nsec_1
    now = (offset * adj_2) + xtime_nsec_2

已知 adj_2 = adj_1 + 1，代入：
    (offset * adj_1) + xtime_nsec_1 = (offset * (adj_1+1)) + xtime_nsec_2
    (offset * adj_1) + xtime_nsec_1 = (offset * adj_1) + offset + xtime_nsec_2
消去两边：
    xtime_nsec_1 = offset + xtime_nsec_2
得到：
    xtime_nsec_2 = xtime_nsec_1 - offset

一句话：把 mult 加一，等于把这段还没累加的 offset 周期的「价值」抬高了一个周期。为了不让时间跳变，必须从累计量里扣掉这个差值。

这个思路 5.10 被抽成了独立函数 timekeeping_apply_adjustment()，逻辑一样，只是多了个 mult_adj == -1 的取反分支和更整齐的溢出检查。

5.10 的 timekeeping_adjust() 换了算法 #

5.10 的 timekeeping_adjust() 变得简短很多：

c
static void timekeeping_adjust(struct timekeeper *tk, s64 offset)
{
    u32 mult;

    /* tick 长度没变就省掉除法 */
    if (likely(tk->ntp_tick == ntp_tick_length())) {
        mult = tk->tkr_mono.mult - tk->ntp_err_mult;
    } else {
        tk->ntp_tick = ntp_tick_length();
        mult = div64_u64((tk->ntp_tick >> tk->ntp_error_shift) -
                         tk->xtime_remainder, tk->cycle_interval);
    }

    /*
     * 如果时钟落后于 NTP 时间，就把 mult 加 1 追上；
     * 如果超前而且 tick 除法有余数，就把 mult 减掉 ntp_err_mult 让它慢下来。
     */
    tk->ntp_err_mult = tk->ntp_error > 0 ? 1 : 0;
    mult += tk->ntp_err_mult;

    timekeeping_apply_adjustment(tk, offset, mult - tk->tkr_mono.mult);

    /* ... maxadj 断言 ... */

    if (unlikely((s64)tk->tkr_mono.xtime_nsec < 0)) {
        tk->tkr_mono.xtime_nsec += (u64)NSEC_PER_SEC << tk->tkr_mono.shift;
        tk->xtime_sec--;
        tk->skip_second_overflow = 1;
    }
}

3.10 那套「误差大于半个 interval 就 bigadjust 大跳一步」的逻辑在 5.10 被删掉了，改成了「每次最多把 mult 调 ±1，靠 tick 长度变化来驱动」。这个改动我是从两个版本的源码对比得出的，具体是哪个 commit 落的、动机是什么，未验证。能确定的是：3.10 允许 adj 一次跨多步（bigadjust 里 *interval <<= adj），5.10 的 mult 增量变成了「新算出来的 mult 减当前 mult」，幅度由 xtime_remainder 和 ntp_tick 决定。

5.10 末尾的下溢处理也更严谨：3.10 是「把 xtime_nsec 归零，差额记进 ntp_error」，5.10 是「补一整个 NSEC_PER_SEC，xtime_sec 减一，然后打 skip_second_overflow 标记，让 accumulate_nsecs_to_secs() 跳过这一秒的 NTP 统计」。后者语义更正确：3.10 归零等于把损失推给了 ntp_error 的符号，5.10 是明确承认「我刚才那一秒算重了，别重复上报」。skip_second_overflow 字段因此是在这一代新增的。

长期行为 #

NTP 的校正回路是：

text
晶振有偏差 → 时间慢慢偏 → PLL 测出 time_offset 涨大
           → time_freq 收敛到一个非零值 → tk->mult 偏离 clock->mult
           → 时间走得跟 NTP 一致 → time_offset 稳定在 0 附近

收敛时间从几分钟到几小时不等，取决于 PLL 的环路参数和晶振稳定性。收敛之后 tk->mult 就停在一个偏离值上，这就是你系统里那个「clock->mult 和 tk->mult 差一点点」的来源。

十二、slew 与 step：两种调整方式的区别 #

「把时间调准」有两条路，语义完全不同，混用会出事。

维度 step（跳变） slew（平滑调整）
效果 时间瞬间跳到目标值 时间以略快/略慢的速率追上去
CLOCK_REALTIME 会跳 不跳，只是速率变
CLOCK_MONOTONIC 不动（靠调 wall_to_monotonic 保住） 不动
用户态感知 能看到时间突变 看不到
典型接口 settimeofday() / clock_settime() / adjtimex(ADJ_SETOFFSET) adjtimex() 的 ADJ_OFFSET + ADJ_FREQUENCY
内核实现 do_settimeofday() 直接改 xtime_sec timekeeping_adjust() 改 tk->mult
适用场景 开机从 RTC 拿到正确时间；用户手动对时 长时间运行中的持续微调
风险 跨进程的时间比较会失效；timerfd / 超时会提前或延后触发 追赶期间时间「不真实」，但对单调性安全

step 的实现 #

3.10 的 do_settimeofday() 前面贴过。核心三行：

c
xt = tk_xtime(tk);
ts_delta.tv_sec  = tv->tv_sec  - xt.tv_sec;
ts_delta.tv_nsec = tv->tv_nsec - xt.tv_nsec;

tk_set_wall_to_mono(tk, timespec_sub(tk->wall_to_monotonic, ts_delta));
tk_set_xtime(tk, tv);

注意 wall_to_monotonic 减掉的那一项。设 wall_to_monotonic 是 W，xtime 是 X，CLOCK_MONOTONIC = X + W。

设前后：X 变成 X + d（d = ts_delta），W 变成 W - d，那么 CLOCK_MONOTONIC = (X + d) + (W - d) = X + W。恒等。 这就是第十四节的答案。

还有个细节：do_settimeofday() 里没有 clock_settime 那种「检查单调性」的逻辑，它接受任何合法的时间值。用户可以往前调，让 CLOCK_REALTIME 倒退。但 CLOCK_MONOTONIC 不受影响，这是 POSIX 要求的：CLOCK_MONOTONIC 不能因为用户改了墙上时间而倒退。

timekeeping_inject_offset() #

adjtimex(ADJ_SETOFFSET) 走这条：

c
int timekeeping_inject_offset(struct timespec *ts)
{
    struct timekeeper *tk = &timekeeper;
    unsigned long flags;
    struct timespec tmp;
    int ret = 0;

    if ((unsigned long)ts->tv_nsec >= NSEC_PER_SEC)
        return -EINVAL;

    raw_spin_lock_irqsave(&timekeeper_lock, flags);
    write_seqcount_begin(&timekeeper_seq);

    timekeeping_forward_now(tk);

    /* 校验加上去之后还合法 */
    tmp = timespec_add(tk_xtime(tk),  *ts);
    if (!timespec_valid_strict(&tmp)) {
        ret = -EINVAL;
        goto error;
    }

    tk_xtime_add(tk, ts);
    tk_set_wall_to_mono(tk, timespec_sub(tk->wall_to_monotonic, *ts));

error:
    /* 就算出错，时间也已经 forward 了，还是要 update */
    timekeeping_update(tk, true, true);

    write_seqcount_end(&timekeeper_seq);
    raw_spin_unlock_irqrestore(&timekeeper_lock, flags);

    clock_was_set();

    return ret;
}

和 do_settimeofday() 的差别在于：它接受负的偏移，而且 ts_delta 就是用户给的那个值，不需要先算差。语义上它是「相对调整」，settimeofday 是「绝对设定」。

error 标签的位置很值得学：校验失败也要 timekeeping_update()，因为前面已经 timekeeping_forward_now() 了，tk 的状态已经改了，得刷出去，不然 vsyscall 页和 shadow 都是旧的。

slew 的实现 #

slew 根本没有专门的函数。它就是第十一节那套「改 tk->mult」。区别在于：

  • step 改 xtime_sec 和 wall_to_monotonic，一次到位。
  • slew 改 tk->mult，每次 update_wall_time() 调一点点，靠时间自己走过去。

slew 期间 CLOCK_REALTIME 的「速率」不再是 1 秒/秒，而是 1 + e 秒/秒。理论上 e 的上限是 maxadj / mult，也就是那个 11%。实际 NTP 用的量级是几十 ppm。

这就是为什么 adjtimex 的两个码 ADJ_OFFSET（slew 追赶）和 ADJ_SETOFFSET（step 跳过去）不能随便换用。如果你的应用依赖时间单调，用 slew；如果你的应用要求「立刻显示正确时间」（比如 NTP 客户端启动时的初次驯服），用 step。

WARN_ON_ONCE 的那条不变量 #

slew 和 step 都能改 wall_to_monotonic，但 offs_real 必须始终等于 -wall_to_monotonic。这个不变量靠 tk_set_wall_to_mono() 里的 WARN_ON_ONCE 守着。所有改 wall_to_monotonic 的代码都必须走这个函数，不允许直接赋值。这也是为什么 3.10 到 5.10 换掉了几乎所有字段类型，tk_set_wall_to_mono() 这个函数名和它的检查却一直没动。

十三、闰秒在 timekeeping 里怎么落地 #

闰秒是个尴尬的东西：它是 UTC 对 TAI 的一次「手动修正」，你没法用晶振周期提前算出来，只能等通知。

时间从哪来 #

UTC 通过 NTP 传下来。IERS 提前半年公告「某月某日 23:59:60 出现」，你的 NTP daemon 调 adjtimex(ADJ_STATUS)，设置 STA_INS（插入）或 STA_DEL（删除），并告诉内核闰秒发生在哪个 UTC 秒。

内核里落成 ntp.c 的 time_status 标志和 time_next_leap_sec 这类变量（字段名按 3.10 语义整理的说明，未逐一核对 ntp.c 内部实现），timekeeping 侧只认 second_overflow() 的返回值。

timekeeping 侧的落地点 #

只有一个地方，accumulate_nsecs_to_secs()：

c
static inline void accumulate_nsecs_to_secs(struct timekeeper *tk)
{
    u64 nsecps = (u64)NSEC_PER_SEC << tk->shift;

    while (tk->xtime_nsec >= nsecps) {
        int leap;

        tk->xtime_nsec -= nsecps;
        tk->xtime_sec++;

        /* 判断这一秒是不是闰秒，是的话应用它 */
        leap = second_overflow(tk->xtime_sec);
        if (unlikely(leap)) {
            struct timespec ts;

            tk->xtime_sec += leap;

            ts.tv_sec = leap;
            ts.tv_nsec = 0;
            tk_set_wall_to_mono(tk,
                timespec_sub(tk->wall_to_monotonic, ts));

            __timekeeping_set_tai_offset(tk, tk->tai_offset - leap);

            clock_was_set_delayed();
        }
    }
}

逐行：

  1. leap = second_overflow(tk->xtime_sec)。告诉 NTP「我又前进了一秒（xtime_sec 是刚进过位的值），顺便问一下这一秒要不要插/删闰秒」。返回值是 +1（插入）、-1（删除）或 0。
  2. tk->xtime_sec += leap。插入时再多加一秒，23:59:59 之后是 23:59:60，形式上是「一秒出现了两次」。删除时减一秒。
  3. tk_set_wall_to_mono(tk, timespec_sub(tk->wall_to_monotonic, ts))。把这一秒从 wall_to_monotonic 里扣掉，于是 CLOCK_MONOTONIC = xtime + wall_to_monotonic 不变。闰秒不污染单调时钟。
  4. __timekeeping_set_tai_offset(tk, tk->tai_offset - leap)。插入一秒，UTC 和 TAI 的差就多一秒，所以 tai_offset 加 1。源码写的是 - leap，因为 leap 是 +1，减一下就是把 tai_offset 减 1。方向要看 tai_offset 的定义：offs_tai = offs_real - tai_offset，tai_offset 增加意味着 TAI 相对 REALTIME 更超前。源码这里实现的符号约定我没完全推透，因为 __timekeeping_set_tai_offset 只在 ntp.c 和 timekeeping.c 两个文件里出现，得连起来读才确定。这块标「未验证」，但你只要记住一点：闰秒会同步调整 tai_offset，让 CLOCK_TAI 不受闰秒影响。
  5. clock_was_set_delayed()。延迟版，因为在 update_wall_time() 的上下文里（中断），直接调会死锁。

为什么用 clock_was_set_delayed() #

accumulate_nsecs_to_secs() 是从 update_wall_time() 调进来的，而 update_wall_time() 运行在 tick 中断里，此时已经持有 timekeeper_lock。clock_was_set() 会去唤醒 hrtimer 的处理，需要别的锁。所以用 _delayed 版本，把工作丢到 irq_work 里稍后做。

5.x 的 next_leap_ktime #

5.10 多了个 next_leap_ktime 字段，语义是「下一个闰秒触发的单调时间点」：

c
static inline void tk_update_leap_state(struct timekeeper *tk)
{
    tk->next_leap_ktime = ntp_get_next_leap();
    if (tk->next_leap_ktime != KTIME_MAX)
        /* 换算成单调时间 */
        tk->next_leap_ktime = ktime_sub(tk->next_leap_ktime, tk->offs_real);
}

为什么需要它？因为 CLOCK_REALTIME 在闰秒时刻会「停一秒」或「跳一秒」，但 hrtimer 是按单调时间排队的，它不知道墙上时间的变化。ktime_get_update_offsets_now() 里有一句：

c
/* 处理闰秒插入时的偏移调整 */
if (unlikely(base >= tk->next_leap_ktime))
    *offs_real = ktime_sub(tk->offs_real, ktime_set(1, 0));

hrtimer 中断里如果发现单调时间已经过了闰秒点，就把给它的 offs_real 减一秒。这样 CLOCK_REALTIME 的绝对时间在那一秒里是「冻结」的，而单调时间继续走。3.10 没有这个字段，闰秒的效果是通过 wall_to_monotonic 和 clock_was_set_delayed() 让 hrtimer 重算来实现的，触发时机没有 5.x 精确。

十四、CLOCK_MONOTONIC 为什么不会跳变 #

这是全篇最该讲清楚的一个问题，因为它是用户态最依赖的性质。

三条理由叠在一起 #

CLOCK_MONOTONIC 不跳，靠三层保护：

第一层：它没有自己的存储，完全由 xtime 和 wall_to_monotonic 相加得到。

text
CLOCK_MONOTONIC = CLOCK_REALTIME + wall_to_monotonic

第二层：每一次外部改时间，改动 xtime 的同时把等量差值反向写进 wall_to_monotonic。

三种改法都遵守这个约定：

场景 对 xtime 的动作 对 wall_to_monotonic 的动作 结果
settimeofday = tv -= ts_delta MONOTONIC 不变
inject_offset += ts -= ts MONOTONIC 不变
注入睡眠时间 += delta -= delta MONOTONIC 不变
闰秒 xtime_sec += leap -= leap MONOTONIC 不变
正常 tick 推进 xtime_nsec += ... 不动 MONOTONIC 与 REALTIME 同步前进

最后一行才是关键：正常走时的时候不去碰 wall_to_monotonic，所以 CLOCK_MONOTONIC 和 CLOCK_REALTIME 是同一个增量。外面改时间的时候才反向补偿。一增必有一减，所以 xtime + wall_to_monotonic 这条和永不变。

第三层：wall_to_monotonic 只在一个地方写。

tk_set_wall_to_mono()。3.10 到 5.10 都是这一个函数，所有路径都走它。函数里那句 WARN_ON_ONCE 校验 offs_real == -wall_to_monotonic，等于给了你一个「谁绕过了这个函数」的探针。这条纪律把「有人直接改字段导致不变量破裂」这条路堵住了。

具体的代码 #

updates 那五种场景的代码我在前面都贴过了。再补一个最容易漏的：__timekeeping_inject_sleeptime()：

c
static void __timekeeping_inject_sleeptime(struct timekeeper *tk,
                                           struct timespec *delta)
{
    if (!timespec_valid_strict(delta)) {
        printk(KERN_WARNING "__timekeeping_inject_sleeptime: Invalid "
                            "sleep delta value!\n");
        return;
    }
    tk_xtime_add(tk, delta);
    tk_set_wall_to_mono(tk, timespec_sub(tk->wall_to_monotonic, *delta));
    tk_set_sleep_time(tk, timespec_add(tk->total_sleep_time, *delta));
}

三行，三个动作，各有分工：

  1. tk_xtime_add(tk, delta)：墙上时间加上睡眠时长。你睡着的时候 RTC 在走，所以醒来墙钟应该往前走那么多。
  2. tk_set_wall_to_mono(tk, ... - delta)：反向补偿，CLOCK_MONOTONIC 不动。
  3. tk_set_sleep_time(tk, ... + delta)：睡眠时长单独记账，这是 CLOCK_BOOTTIME 的原料。

CLOCK_MONOTONIC 不计睡眠时间、CLOCK_BOOTTIME 计，就是这么实现的：两者共用同一个 xtime，差别只在 total_sleep_time 加不加。

唯一的例外 #

CLOCK_MONOTONIC 有一条确实会变：NTP 的 slew 校正。它不改 wall_to_monotonic，改的是 tk->mult，所以 CLOCK_MONOTONIC 的速率会变（快一点点或慢一点点），但值不会跳。

这符合 POSIX 的定义，CLOCK_MONOTONIC 只保证「不回退」，不保证「速率精确等于 SI 秒」。要速率精确，用 CLOCK_MONOTONIC_RAW。

另外 CLOCK_MONOTONIC 在 timekeeping_suspended 期间会「冻结」，resume 之后继续，不补睡眠期间的时间。这不是跳变，是停表。

一个反直觉的结论 #

CLOCK_MONOTONIC 的精度其实比 CLOCK_MONOTONIC_RAW 高。因为 CLOCK_MONOTONIC 被 NTP 校正过，它的长期速率贴近真实秒；CLOCK_MONOTONIC_RAW 是硬件原样，晶振偏 50ppm 它就偏 50ppm，只是它不会有任何"人为干预"。

要「不受干扰的物理时间」，用 RAW；要「准确的流逝时长」，用 MONOTONIC。这两个目标在现实硬件上是矛盾的，内核给了你两个 clock 让你自己选。

十五、CLOCK_BOOTTIME 与挂起时间 #

CLOCK_BOOTTIME 和 CLOCK_MONOTONIC 在醒着的时候完全一样，只有系统睡过去那段时间才有区别。这块时间谁来记？timekeeping 自己记，因为睡过去之后 clocksource 也停了。

三个候选时间源 #

suspend 期间能用的时间源，按优先级排：

优先级 来源 条件 精度
1 当前 clocksource（带 CLOCK_SOURCE_SUSPEND_NONSTOP 标志） 硬件在 suspend 中不停计数 最高，就是 clocksource 本身
2 persistent clock（RTC） read_persistent_clock64() 有可用实现 多为秒级
3 RTC 子系统 前两者都没有 秒级，但要等中断可用

5.10 的源码注释把这三档写得很清楚：

text
We have three kinds of time sources to use for sleep time
injection, the preference order is:
1) non-stop clocksource
2) persistent clock (ie: RTC accessible when irqs are off)
3) RTC

1) and 2) are used by timekeeping, 3) by RTC subsystem.
If system has neither 1) nor 2), 3) will be used finally.

第 3 档不在 timekeeping 里处理，走 timekeeping_inject_sleeptime64()，由 rtc_resume() 调。3.10 的对应函数叫 timekeeping_inject_sleeptime()，还带一个保护：

c
/* 别把时钟设两遍，timekeeping_resume() 已经设过的情况要挡掉 */
if (has_persistent_clock())
    return;

suspend 一侧 #

c
static int timekeeping_suspend(void)
{
    struct timekeeper *tk = &timekeeper;
    unsigned long flags;
    struct timespec     delta, delta_delta;
    static struct timespec  old_delta;

    read_persistent_clock(&timekeeping_suspend_time);

    /* 有些平台的 persistent clock 在 init 阶段探不到，这里再试一次 */
    if (timekeeping_suspend_time.tv_sec || timekeeping_suspend_time.tv_nsec)
        persistent_clock_exist = true;

    raw_spin_lock_irqsave(&timekeeper_lock, flags);
    write_seqcount_begin(&timekeeper_seq);
    timekeeping_forward_now(tk);
    timekeeping_suspended = 1;

    /*
     * 避免反复 suspend/resume 累积漂移（每次都能引入约 1 秒误差）。
     * 让「系统时间和 persistent clock 的差值」保持近似恒定。
     */
    delta = timespec_sub(tk_xtime(tk), timekeeping_suspend_time);
    delta_delta = timespec_sub(delta, old_delta);
    if (abs(delta_delta.tv_sec) >= 2) {
        /* 差得太多，说明期间有人校过时间，把 old_delta 重置 */
        old_delta = delta;
    } else {
        /* 否则调整基准去补偿 */
        timekeeping_suspend_time =
            timespec_add(timekeeping_suspend_time, delta_delta);
    }
    write_seqcount_end(&timekeeper_seq);
    raw_spin_unlock_irqrestore(&timekeeper_lock, flags);

    clockevents_notify(CLOCK_EVT_NOTIFY_SUSPEND, NULL);
    clocksource_suspend();
    clockevents_suspend();

    return 0;
}

几个点：

timekeeping_forward_now(tk) 必须在 timekeeping_suspended = 1 之前。 它要读一次 clocksource，而 suspended = 1 设置完之后，clocksource 已被断电（clocksource_suspend()）。

delta / delta_delta 那段补偿是防累积漂移的。 RTC 只有秒级精度，每次 suspend 读一下，偏个半秒。suspend 十次就偏 5 秒。这段代码的做法是：拿「系统时间 - RTC 时间」当基准差值 delta，每次 suspend 算一下新的 delta 和上次的差 delta_delta，如果这个差小于 2 秒（说明没有人工校时），就把 timekeeping_suspend_time 往前挪 delta_delta，把漂移吸收掉。

素材这里只写到「如果 delta_delta 大于 2 秒，」就断了。完整语义要看 else 分支：差距小于 2 秒时做补偿，大于 2 秒时认为期间有人 settimeofday 过，直接重置基准。

timekeeping_suspended = 1 的作用面。 这个标志被 ktime_get() 的 WARN_ON 检查，也被 update_wall_time() 用来直接退出。suspend 期间时间冻结。

5.10 的写法多了两步：clocksource_start_suspend_timing() 记下当前 clocksource 的周期值，halt_fast_timekeeper() 把 NMI 快路径也冻结住：

c
static void halt_fast_timekeeper(const struct timekeeper *tk)
{
    static struct tk_read_base tkr_dummy;
    const struct tk_read_base *tkr = &tk->tkr_mono;

    memcpy(&tkr_dummy, tkr, sizeof(tkr_dummy));
    cycles_at_suspend = tk_clock_read(tkr);
    tkr_dummy.clock = &dummy_clock;
    tkr_dummy.base_real = tkr->base + tk->offs_real;
    update_fast_timekeeper(&tkr_dummy, &tk_fast_mono);
    /* raw 轴同理 */
}

替换成 dummy_clock，它的 read() 返回固定的 cycles_at_suspend。于是 NMI 快路径在 suspend 期间每次读到的周期增量都是 0，时间戳冻结在挂起那一刻。这比直接让读者访问已断电的硬件安全。

resume 一侧 #

3.10：

c
static void timekeeping_resume(void)
{
    struct timekeeper *tk = &timekeeper;
    struct clocksource *clock = tk->clock;
    unsigned long flags;
    struct timespec ts_new, ts_delta;
    cycle_t cycle_now, cycle_delta;
    bool suspendtime_found = false;

    read_persistent_clock(&ts_new);

    clockevents_resume();
    clocksource_resume();

    raw_spin_lock_irqsave(&timekeeper_lock, flags);
    write_seqcount_begin(&timekeeper_seq);

    cycle_now = clock->read(clock);
    if ((clock->flags & CLOCK_SOURCE_SUSPEND_NONSTOP) &&
        cycle_now > clock->cycle_last) {
        u64 num, max = ULLONG_MAX;
        u32 mult = clock->mult;
        u32 shift = clock->shift;
        s64 nsec = 0;

        cycle_delta = (cycle_now - clock->cycle_last) & clock->mask;

        /*
         * cycle_delta * mult 会 64 位溢出，睡太久就中。
         * 那种情况要拆开算。
         */
        do_div(max, mult);
        if (cycle_delta > max) {
            num = div64_u64(cycle_delta, max);
            nsec = (((u64) max * mult) >> shift) * num;
            cycle_delta -= num * max;
        }
        nsec += ((u64) cycle_delta * mult) >> shift;

        ts_delta = ns_to_timespec(nsec);
        suspendtime_found = true;
    } else if (timespec_compare(&ts_new, &timekeeping_suspend_time) > 0) {
        ts_delta = timespec_sub(ts_new, timekeeping_suspend_time);
        suspendtime_found = true;
    }

    if (suspendtime_found)
        __timekeeping_inject_sleeptime(tk, &ts_delta);

    /* 重设 cycle_last */
    tk->cycle_last = clock->cycle_last = cycle_now;
    tk->ntp_error = 0;
    timekeeping_suspended = 0;
    timekeeping_update(tk, false, true);
    write_seqcount_end(&timekeeper_seq);
    raw_spin_unlock_irqrestore(&timekeeper_lock, flags);

    touch_softlockup_watchdog();

    clockevents_notify(CLOCK_EVT_NOTIFY_RESUME, NULL);

    /* 恢复 hrtimers */
    hrtimers_resume();
}

那个溢出拆分很有意思。 cycle_delta * mult 是 64 位乘，cycle_delta 会很大（睡了一个月，24MHz 的 counter 攒了 6.2e13 个周期），mult ≈ 2.8e9，乘积会破 2^64。

拆法是先算 max = ULLONG_MAX / mult，这是「一次乘法能安全处理的最大周期数」。然后 num = cycle_delta / max 得到要拆几段，每段贡献 (max * mult) >> shift 纳秒，剩下的零头照常算。num 最多能到 2.2e4 这个量级，nsec 用 s64 装得下。

选源顺序在代码里的体现。 先试 non-stop clocksource，cycle_now > clock->cycle_last 这个判断是防回绕的（counter 不要回绕，要求它的溢出周期比任何 suspend 时间都长）；不行再看 persistent clock，ts_new > timekeeping_suspend_time 是防「RTC 被谁调回去了」。

tk->ntp_error = 0;。 睡了一觉，之前的相位误差记录没意义了，清零重来。

5.10 用 clocksource_stop_suspend_timing() 替代了手写的拆分：

c
cycle_now = tk_clock_read(&tk->tkr_mono);
nsec = clocksource_stop_suspend_timing(clock, cycle_now);
if (nsec > 0) {
    ts_delta = ns_to_timespec64(nsec);
    inject_sleeptime = true;
} else if (timespec64_compare(&ts_new, &timekeeping_suspend_time) > 0) {

}

溢出拆分被搬进了 clocksource.c，timekeeping 只看返回的 nsec 是不是正数。职责划分更清楚了：clocksource 模块知道自己能测多长，timekeeping 只负责把测出来的时长注入。

和 tk_set_wall_to_mono() 一样的套路：两个字段必须同步，用一个 WARN_ON_ONCE 盯着。offs_boot 就是 total_sleep_time 的 ktime_t 形式，给 hrtimer 用。

CLOCK_BOOTTIME 的读法 #

3.10：

c
void get_monotonic_boottime(struct timespec *ts)
{
    struct timekeeper *tk = &timekeeper;
    struct timespec tomono, sleep;
    s64 nsec;
    unsigned int seq;

    WARN_ON(timekeeping_suspended);

    do {
        seq = read_seqcount_begin(&timekeeper_seq);
        ts->tv_sec = tk->xtime_sec;
        nsec = timekeeping_get_ns(tk);
        tomono = tk->wall_to_monotonic;
        sleep = tk->total_sleep_time;
    } while (read_seqcount_retry(&timekeeper_seq, seq));

    ts->tv_sec += tomono.tv_sec + sleep.tv_sec;
    ts->tv_nsec = 0;
    timespec_add_ns(ts, nsec + tomono.tv_nsec + sleep.tv_nsec);
}

和 ktime_get_ts() 的唯一区别是多加了个 sleep。seqcount 里读了四项（xtime_sec、timekeeping_get_ns()、wall_to_monotonic、total_sleep_time），每一项都必须同源。

5.10 简化成一次加法：

c
u64 notrace ktime_get_boot_fast_ns(void)
{
    struct timekeeper *tk = &tk_core.timekeeper;

    return (ktime_get_mono_fast_ns() + ktime_to_ns(tk->offs_boot));
}

注意它是 notrace 的，要在 ftrace 里用，不能自己又被跟踪。而且 5.10 的注释承认这条路有两个瑕疵：

text
(1) boot offset 更新之后、timekeeper 更新之前取的时间戳，会「早一点」看到新的 boot offset
(2) 32 位机上 offs_boot 是 64 位，会被读到一半更新

两个都是低概率事件，注释里的态度是「后处理能扛就扛」。

应用侧的实际价值 #

CLOCK_BOOTTIME 是给「超时要跨 suspend 生效」的场景用的。比如：

  • timerfd 的 TFD_TIMER_CANCEL_ON_SET 配合 CLOCK_BOOTTIME，可以让「30 分钟后唤醒」的语义在设备睡眠期间也成立。
  • Android 的 SystemClock.elapsedRealtime() 就是 CLOCK_BOOTTIME。
  • CLOCK_MONOTONIC 的 epoll_wait 超时，睡一觉之后等于白等，因为它的时钟停表了。

用法上记住一条：要跨睡眠计时，用 CLOCK_BOOTTIME；要纯运行时长，用 CLOCK_MONOTONIC。

差别在锁的粒度：5.10 里 update_wall_time() 在 jiffies_lock 外面，因为它自己有 timekeeper_lock，两个锁不该嵌套。3.10 里 update_wall_time() 是 do_timer() 的一部分，而 do_timer() 的调用者已经持有 jiffies_lock（write_seqlock(&jiffies_lock)）。这在我看过的 3.10 源码里是成立的，但锁序容易看错，5.10 的重排就是把这个坑填了。

为什么 timekeeping 要「按自己的节奏」 #

tick_periodic() 每个 tick 都调 update_wall_time()，但 update_wall_time() 会自己判断要不要真干活：

c
offset = (clock->read(clock) - clock->cycle_last) & clock->mask;
if (offset < real_tk->cycle_interval)
    goto out;

两个好处：

  1. tick 频率高于 NTP 校正需要的频率时，不浪费。 HZ=1000 的系统，每秒 1000 个 tick，但 NTP 只需要每 NTP_INTERVAL_LENGTH 校正一次。不判断的话，xtime_nsec 每次只加一点点，还要走一遍 timekeeping_adjust()，纯浪费。
  2. HZ 不影响时间的长期精度。 cycle_interval 是 NTP_INTERVAL_LENGTH 定的，跟 tick 频率无关，所以 HZ=100 和 HZ=1000 的系统，长期时间精度是一致的。tick 只影响「多久更新一次」和「CLOCK_REALTIME_COARSE 的精度」。

第 2 点值得强调：很多人以为 HZ 高时间就更准。不对。HZ 高只是让 CLOCK_*_COARSE 更准、让调度器响应更快。精确时间的精度靠 clocksource 的分辨率和 NTP 的校正，跟 tick 频率无关。

dynamic tick / NO_HZ #

CONFIG_NO_HZ_IDLE 或 CONFIG_NO_HZ_FULL 下，空闲时 tick 会停。那么这段时间的时间推进怎么办？

答案在 update_wall_time() 的 ilog2 那段：

c
shift = ilog2(offset) - ilog2(tk->cycle_interval);
shift = max(0, shift);
maxshift = (64 - (ilog2(ntp_tick_length())+1)) - 1;
shift = min(shift, maxshift);
while (offset >= tk->cycle_interval) {
    offset = logarithmic_accumulation(tk, offset, shift);
    if (offset < tk->cycle_interval<<shift)
        shift--;
}

offset 是「上次更新到现在一共过了多少周期」。NO_HZ 下这个值会是一整个空闲时长的周期数。循环用「2 的幂倍」的步长，用 O(log N) 轮吃完。

这里有个东西必须讲清楚：clock->cycle_last 只有在 logarithmic_accumulation() 里才被推进，而它推进的量是 cycle_interval << shift，不是 offset。所以循环结束之后 cycle_last 和实际读到的 cycle_now 之间还有 offset 的差距，这个差距就是 timekeeping_adjust(tk, offset) 的第二个参数。

3.10 的这个差距就留在那儿，等到下一次 update_wall_time() 时再加进 offset 里一起算。

5.10 的 timekeeping_advance() 有个 TK_ADV_TICK / TK_ADV_FREQ 的模式参数：

c
enum timekeeping_adv_mode {
    /* 一个 tick 过去了，更新 timekeeper */
    TK_ADV_TICK,
    /* 频率被直接改了，要立刻生效 */
    TK_ADV_FREQ
};

do_adjtimex() 里如果看到 ADJ_FREQUENCY | ADJ_TICK，就直接调 timekeeping_advance(TK_ADV_FREQ)：

c
/* Update the multiplier immediately if frequency was set directly */
if (txc->modes & (ADJ_FREQUENCY | ADJ_TICK))
    timekeeping_advance(TK_ADV_FREQ);

为什么要立刻？因为 ADJ_FREQUENCY 是「直接设频率」，用户期望的是「从现在起就是这个频率」，不是「等下一个 tick 才生效」。3.10 里没有这个模式参数，靠 do_adjtimex() 之后的下一轮 update_wall_time() 生效，延迟最多一个 tick。5.10 把这个延迟去掉了。

这是 tick 机制篇的事，这里只给结论：空闲时靠 clock_event_device 的一次性编程（oneshot 模式），下一个事件到期时唤醒。唤醒之后 tick_nohz_restart() 会把 update_wall_time() 该补的时间一次性补上，就是上面那段 ilog2 循环。

十七、一个完整的读时间流程 #

从用户态一次 clock_gettime(CLOCK_MONOTONIC, &ts) 走下去，把前面所有零件串一遍。

第 0 步：VDSO 拦截 #

进入内核之前，glibc 会先看 VDSO（vvar 页）。如果内核在 update_vsyscall() 里把 tkr_mono 的 mult、shift、cycle_last、base 都写好了（5.10 的 struct vdso_data），VDSO 里就有 __vdso_clock_gettime，直接：

text
1. 读 seq 计数（vvar 页里的一份拷贝）
2. 从 vdso_data 里读 mult / shift / cycle_last / base
3. 读一次 TSC 或 CNTVCT（用户态可读的计数器）
4. delta = (now - cycle_last) & mask
5. ns = base + ((delta * mult) >> shift)
6. 再读一次 seq，变了就重来

整个过程没有一次系统调用。这是绝大多数 clock_gettime 的真实路径。

VDSO 的具体数据结构（struct vdso_data、各字段偏移）我没在本轮核对，标「未验证」。但「VDSO 用同一套 mult/shift 自己算」这个机制是确定的，update_vsyscall() 的调用点就在 timekeeping_update() 里。

第 1 步：进内核的路径 #

VDSO 不可用（比如 CLOCK_MONOTONIC_RAW 在某些版本上没有 VDSO 实现，或者 vvar 页被禁用），走系统调用：

text
sys_clock_gettime(CLOCK_MONOTONIC, tp)
  → posix_clock_gettime()          kernel/time/posix-timers.c
    → k_clock->clock_get()         由 clockid 对应的 k_clock 决定
      → posix_get_timespec() / ktime_get_ts()
        → ktime_get_ts()

第 2 步：ktime_get_ts() #

c
void ktime_get_ts(struct timespec *ts)
{
    struct timekeeper *tk = &timekeeper;
    struct timespec tomono;
    s64 nsec;
    unsigned int seq;

    WARN_ON(timekeeping_suspended);

    do {
        seq = read_seqcount_begin(&timekeeper_seq);
        ts->tv_sec = tk->xtime_sec;
        nsec = timekeeping_get_ns(tk);
        tomono = tk->wall_to_monotonic;

    } while (read_seqcount_retry(&timekeeper_seq, seq));

    ts->tv_sec += tomono.tv_sec;
    ts->tv_nsec = 0;
    timespec_add_ns(ts, nsec + tomono.tv_nsec);
}

三件事在 seqcount 里一起做：读 xtime_sec、算 timekeeping_get_ns()（这一次会读硬件）、拷 wall_to_monotonic。

出来之后：tv_sec 是 xtime_sec + tomono.tv_sec，tv_nsec 是 0，然后 timespec_add_ns() 把 nsec + tomono.tv_nsec 加进去并归一化。

nsec 这个变量是 s64。timekeeping_get_ns() 本身非负，tomon.tv_nsec 被要求保持正数，所以整体非负。用 s64 是为了防御 get_arch_timeoffset() 返回负值的那种架构。

第 3 步：timekeeping_get_ns() 里发生了什么 #

c
static inline s64 timekeeping_get_ns(struct timekeeper *tk)
{
    cycle_t cycle_now, cycle_delta;
    struct clocksource *clock;
    s64 nsec;

    /* read clocksource: */
    clock = tk->clock;
    cycle_now = clock->read(clock);                 ← 一次硬件读

    /* calculate the delta since the last update_wall_time: */
    cycle_delta = (cycle_now - clock->cycle_last) & clock->mask;

    nsec = cycle_delta * tk->mult + tk->xtime_nsec;
    nsec >>= tk->shift;

    return nsec + get_arch_timeoffset();
}

clock->read() 是唯一一次硬件访问。对 ARM 的 arch_sys_counter，read 就是一条 mrs x0, cntvct_el0；对 x86 的 TSC，是 rdtsc 加一点序列化。

& clock->mask 处理回绕。clock->mask 由 clocksource 的位宽决定：32 位 counter 是 0xffffffff，64 位是 ~0ULL。

cycle_delta * tk->mult 是 64 位乘，+ tk->xtime_nsec 把历史小数带上，>> tk->shift 还原成纳秒。

第 4 步：timespec_add_ns() 归一化 #

text
ts->tv_nsec = 0
timespec_add_ns(ts, nsec)
  → 把 nsec 加到 tv_nsec 上
  → while (tv_nsec >= NSEC_PER_SEC) { tv_nsec -= NSEC_PER_SEC; tv_sec++; }
  → while (tv_nsec < 0)             { tv_nsec += NSEC_PER_SEC; tv_sec--; }

这两行循环是 3.10 的实现方式（nsec 很大时用循环太慢）。实际实现是按 NSEC_PER_SEC 做一次除法再加一次取模，timespec_add_ns() 内部做了优化。具体实现未验证，但语义就是上面那样。

text

  |     |-- ilog2 定步长
  |     |-- while (offset >= cycle_interval)
  |     |     └-- logarithmic_accumulation()
  |     |           ├-- cycle_last += interval << shift
  |     |           ├-- xtime_nsec += xtime_interval << shift
  |     |           ├-- accumulate_nsecs_to_secs()   ← 闰秒在这里判
  |     |           ├-- raw_time 推进
  |     |           └-- ntp_error 记账
  |     |-- timekeeping_adjust(offset)                ← NTP 在这里动 mult
  |     |-- accumulate_nsecs_to_secs()                ← 收尾归一化
  |     |-- write_seqcount_begin()
  |     |-- memcpy(real_tk, shadow_tk, sizeof)
  |     |-- timekeeping_update()
  |     |     ├-- tk_update_leap_state()
  |     |     ├-- tk_update_ktime_data()              ← 算 base
  |     |     ├-- update_vsyscall()                   ← 用户态可见
  |     |     ├-- update_pvclock_gtod()
  |     |     ├-- base_real = base + offs_real
  |     |     ├-- update_fast_timekeeper()            ← NMI 快路径
  |     |     └-- if (TK_MIRROR) memcpy(shadow_timekeeper, ...)
  |     |-- write_seqcount_end()
  |     └-- raw_spin_unlock_irqrestore()

注意 timekeeping_update() 在 seqcount 之内，而 update_vsyscall() 在里面会写用户态可读的 vvar 页。这一步是在 seqcount 的写保护下做的，读者要么看到旧的 vvar，要么看到新的，不会撕裂。

十八、易错点速查 #

概念层 #

易错点 正确理解
xtime_nsec 是真的纳秒 是纳秒左移 shift 位。还原要右移
cycle_interval 是一个 tick 的周期数 是一个 NTP 校正间隔的周期数，与 tick 频率无关
tk->mult 和 clock->mult 一样 tk->mult 带 NTP 微调，clock->mult 是硬件原值
wall_to_monotonic 是正数 是负数，CLOCK_MONOTONIC 要从一个正的大数拉回 0
CLOCK_MONOTONIC 有自己的存储 没有，它是 xtime + wall_to_monotonic 算出来的
CLOCK_MONOTONIC 比 CLOCK_MONOTONIC_RAW 准 长期速率上 MONOTONIC 更准（有 NTP），物理真实性上 RAW 更纯
读时间要拿锁 读路径完全不拿锁，只有 seqcount 乐观重试
HZ 越高时间越准 HZ 只影响 *_COARSE 的精度和调度响应
CLOCK_BOOTTIME 就是 CLOCK_MONOTONIC 醒着时一样，睡着时前者继续走后者停表

代码层 #

易错点 具体表现
用 3.10 的字段名找 5.10 的代码 tk->clock、tk->mult、tk->shift、tk->xtime_nsec 全搬进了 tkr_mono
找 total_sleep_time 5.x 已删，改用 offs_boot + monotonic_to_boot
找 current_kernel_time() 5.x 已删，改 ktime_get_coarse_real_ts64()
getnstimeofday() 还在 5.x 已废弃，改 ktime_get_real_ts64()（具体删除版本未验证）
do_settimeofday() 收 timespec 5.x 是 do_settimeofday64() 收 timespec64
timekeeping_update(tk, true, true) 5.x 是位掩码 TK_CLEAR_NTP | TK_MIRROR | TK_CLOCK_WAS_SET
write_seqcount_begin(&tk_core.seq) 5.x 的 tk_core.seq 是 seqcount_raw_spinlock_t，必须先持有 timekeeper_lock
从 do_timer() 里找 update_wall_time() 5.x 里在 xtime_update() 里，do_timer() 只剩 jiffies_64 和 calc_global_load()
以为 clocksource_cyc2ns() 用了 tk->mult 它收的是裸参数，timekeeping 用的是自己的 tk->mult + xtime_nsec 版本
在 #include <linux/clocksource.h> 里找不到 timekeeping_get_ns() 那是 timekeeping.c 的 static inline，外部不可见

排障层 #

现象 先看哪里
clock_gettime 偶尔返回比上次小的值 是不是在 NMI 里用了 ktime_get_mono_fast_ns()，它不保证跨更新单调
dmesg 有 Adjusting xxx more than 11% NTP 想调 mult 超过 clock->maxadj，说明 clocksource 或 PTP 有问题
dmesg 有 Persistent clock returned invalid value RTC 没应答或电池没电
dmesg 有 Underflow in clocksource timekeeping_get_delta() 判出了 mask 相对的小负数，counter 读回退了
dmesg 有 Overflow in clocksource delta > clock->max_cycles，计数器转过一圈了
suspend 唤醒后时间慢了几秒 没有 non-stop clocksource，persistent clock 精度不够
CLOCK_TAI 和 CLOCK_REALTIME 差值和预期不一样 查 adjtimex --print 的 tai 字段，或者闰秒表没更新
32 位机上 2038 年之后时间错 用了 struct timespec 而不是 timespec64
换 clocksource 之后时间跳了一下 tk_setup_internals() 的 shift_change 补偿没做对（正常情况不该跳）

python3 - <<'EOF'
import time
prev = None
for _ in range(20):
    t = time.clock_gettime_ns(time.CLOCK_MONOTONIC_RAW)
    print(t, "" if prev is None else t - prev)
    prev = t
EOF
