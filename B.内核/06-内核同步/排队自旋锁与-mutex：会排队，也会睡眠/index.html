一、ticket spinlock 的问题：所有核都在抢同一行 cache #

自旋锁的代数可以用一句话记住：TAS 不公平，ticket 公平但吵，qspinlock 公平且安静。

最早是 TAS 锁：一条原子指令把状态从 unlocked 改成 locked，改成了就进临界区，改不成就重试。原子指令作用于一行 cache，谁先拿到谁赢。这里的不公平来自硬件拓扑，不来自代码。

text
thread4 持锁（在 cpu4）
cpu7 与 cpu4 同一 cluster，thread7 在等
cpu0 在另一个 cluster，thread0 在等
thread4 放锁瞬间：cpu7 的探测更快到达这一行，thread7 大概率抢先

于是有了 ticket lock，用两个号替换一个布尔位。

c
/* 结构示意，具体字段名以各架构的 arch_spinlock_t 为准 */
typedef struct arch_spinlock {
    union {
        __ticket_t     ticket;      /* 已发到几号 */
        __ticketpair_t head_tail;   /* 高半部 owner：当前叫号；低半部 next：下一个要发的号 */
    };
} arch_spinlock_t;

拿锁两步：先对 next 做一次 fetch_add 领号，再在本地反复比较自己的号和 owner。放锁一步：把 owner 加一，等于叫下一个号。

公平性解决了，新问题立刻出现。持锁失败那条路径上还要对 next 做 ++，这是一次写操作；放锁对 owner 加一，也是一次写操作。两处都在同一个 4 字节里。核的数目一大，竞争一激烈，这 4 字节所在的 cacheline 就在各核的 L1 之间来回搬：每次搬都要一个核把行降级、另一个核把行升级，行里的数据没变，搬运动作本身把总线占满了。这就是 cacheline bouncing。

锁 公平性 加锁时触碰的 cacheline 等待者自旋在哪 扩展性
TAS 不公平，受拓扑影响 1 行（锁本身） 锁变量 差
ticket 公平，先来先得 1 行（锁本身），且每次领号都写 锁变量 中等偏差
qspinlock 公平，先来先得 快路径 1 行；排队后队首 1 行，其余人碰自己的行 自己的 mcs 节点 好

关键差别不在「谁先拿到」，而在「等待的人碰哪块内存」。ticket 锁是 N 个核轮着写同一行；qspinlock 是 N 个核各写各的 per-CPU 节点，只有队首去碰那一行共享的。

二、qspinlock 的设计目标 #

qspinlock 不是凭空长出来的，它是把经典的 MCS 锁塞进 4 字节。qspinlock.c 开头的注释把这个妥协写得很直白，翻译过来是三件事。

第一，spinlock_t 必须还是 4 字节。内核里 spinlock 嵌在成千上万个结构体里，锁一变大，宿主结构体跟着变大，缓存占用、内存占用、结构体布局全都要重算。这条约束是硬约束，不是审美偏好。

第二，API 不能变。arch_spin_lock / arch_spin_unlock 的签名、语义、内存序都得和 ticket 时代一致，否则上层几万处调用点要跟着动。传统 MCS 锁要求「加锁时传节点、解锁时传同一个节点」，这个形状和现有 API 不兼容。

第三，只有队首碰共享 cacheline。这是性能目标，也是唯一值得为它付出复杂度的地方。

具体怎么压缩，注释里给了账本：传统 MCS 需要 8 字节的 tail 指针，外加自己节点的 next（又 8 字节）才能通知下一个等待者。qspinlock 把 {tail, next->locked} 压进一个 u32。压缩的支点是嵌套层数有限——自旋锁在同一个上下文里不允许递归（同一个锁递归就是死锁），能嵌套的上下文只有 task、softirq、hardirq、NMI 四层，2 bit 就能编码。于是 tail 变成「2 bit 层号 + CPU 号」，加上 1 字节的锁值，正好 32 位。

还有一处改动值得单独记：qspinlock 让第一个等待者自旋在锁字节上，而不是自旋在自己的节点上。传统 MCS 里每个人（含队首）都自旋在自己的 node->locked，靠前驱写它来传递；qspinlock 把队首改成直接看锁值，好处是「拿到锁之后不需要再回头碰自己的节点」，解锁路径因此变短，而且不用把节点从加锁带到解锁。

c
/* kernel/locking/qspinlock.c，5.10 */
#define MAX_NODES 4

struct qnode {
    struct mcs_spinlock mcs;
#ifdef CONFIG_PARAVIRT_SPINLOCKS
    long reserved[2];
#endif
};

static DEFINE_PER_CPU_ALIGNED(struct qnode, qnodes[MAX_NODES]);

MAX_NODES = 4 对应四层嵌套。5.10 用 struct qnode 把 mcs 节点包了一层，只是为了 paravirt 多塞两个 long 做 padding：64 位平台上 mcs_spinlock 是 16 字节，4 个正好一行 64 字节；开了 paravirt 之后每个撑到 32 字节，一行只放得下 2 个——注释说实际使用中很少出现超过 2 层慢路径嵌套，不值得为罕见情况拖累原生 qspinlock。

4.2 首次引入时没有这层包装，形态是 static DEFINE_PER_CPU_ALIGNED(struct mcs_spinlock, mcs_nodes[MAX_NODES]);，而且 MAX_NODES 在开 paravirt 时是 8。

三、qspinlock 的数据结构：那个 32 位打包字段 #

arch_spinlock_t 就是 struct qspinlock，一个 union 套两种切法。

c
/* include/asm-generic/qspinlock_types.h，5.10 */
typedef struct qspinlock {
    union {
        atomic_t val;

        /* 整个第二字节给 pending，方便 pending 持有者一次写到位 */
#ifdef __LITTLE_ENDIAN
        struct {
            u8  locked;
            u8  pending;
        };
        struct {
            u16 locked_pending;
            u16 tail;
        };
#else
        struct {
            u16 tail;
            u16 locked_pending;
        };
        struct {
            u8  reserved[2];
            u8  pending;
            u8  locked;
        };
#endif
    };
} arch_spinlock_t;

#define __ARCH_SPIN_LOCK_UNLOCKED   { { .val = ATOMIC_INIT(0) } }

为什么要三种切法，注释和田里的活都指向同一件事：不同代码路径需要的粒度不一样。

切法 类型 谁在用 为什么
整体 atomic_t val 快路径 cmpxchg、判断空锁、atomic_cond_read_* 判断「val == 0」只需一次读，不用拼字段
前半 u16 locked_pending clear_pending_set_locked、队首的等待条件 一次 16 位写就把 pending→locked 换完，不会出现中间态
后半 u16 tail xchg_tail tail 是 16 位，用 16 位 xchg 比 32 位 cmpxchg 循环便宜
单字节 u8 locked / u8 pending set_locked、clear_pending、解锁 只动一个字节，减少整字写带来的额外失效

大端机器上 tail 在前、locked 在后，所以多出一组 reserved[2] + pending + locked 的切法来补齐字节序。

位域分配（include/asm-generic/qspinlock_types.h）：

qspinlock 复用的 mcs 节点在两个文件里：

c
/* kernel/locking/mcs_spinlock.h，5.10 */
struct mcs_spinlock {
    struct mcs_spinlock *next;
    int locked;     /* 1 if lock acquired */
    int count;      /* nesting count, see qspinlock.c */
};

count 不是锁状态，是嵌套计数。它每次慢路径入队时自增、出队时自减，同时充当「这一层用哪个 node」的索引。这一点后面讲入队代码时会对上。

四、pending / tail 两个字段怎么配合 #

先说 tail 的编码。tail 是 16 位，装下「2 bit 层号 + CPU 号」。CPU 号要加一，原因写在源码注释里：不加一的话，「队列里有节点在 cpu0 上做第 0 层等待」和「队列为空」在编码上撞车，都是 0。

c
/* kernel/locking/qspinlock.c，5.10 */
static inline __pure u32 encode_tail(int cpu, int idx)
{
    u32 tail;

    tail  = (cpu + 1) << _Q_TAIL_CPU_OFFSET;
    tail |= idx << _Q_TAIL_IDX_OFFSET;   /* assume < 4 */
    return tail;
}

static inline __pure struct mcs_spinlock *decode_tail(u32 tail)
{
    int cpu = (tail >> _Q_TAIL_CPU_OFFSET) - 1;
    int idx = (tail & _Q_TAIL_IDX_MASK) >> _Q_TAIL_IDX_OFFSET;

    return per_cpu_ptr(&qnodes[idx].mcs, cpu);
}

static inline __pure struct mcs_spinlock *grab_mcs_node(struct mcs_spinlock *base, int idx)
{
    return &((struct qnode *)base + idx)->mcs;
}

grab_mcs_node 的写法是个小陷阱：base 拿到的是 qnodes[0].mcs 的地址，而要按 struct qnode 的大小步进，所以先转成 struct qnode * 再加 idx。开了 paravirt 时 qnode 是 32 字节，步进不能按 mcs_spinlock 的 16 字节算。

有了编码，三个域的组合就能穷举。下面这张表把 val 的十六进制值、三个域的取值、以及「谁在干什么」对上，读代码时可以直接查。

val（尾部用 n 表示任意非 0 tail） tail pending locked 场景
0x00000000 0 0 0 空锁，快路径一次 cmpxchg 就进临界区
0x00000001 0 0 1 有人持锁，无 pending、无队列
0x00000101 0 1 1 有人持锁，且已有一个 pending 持有者在等锁字节
0x00000100 0 1 0 owner 已放锁，pending 持有者还没完成交接
0x0000xxxx01 n 0 1 队列非空，队首之外的人在等自己的 mcs 节点
0x0000xxxx00 n 0 0 队首已放锁但 tail 还没清，属于瞬间态
0x000001xx01 且 tail 非 0 n 1 1 队列里有节点，同时还有一个 pending 持有者

pending 位存在的意义是一层「软排队」。它允许一个等待者不挂进 MCS 队列、只自旋在锁字节上，从而避免碰第二条 cacheline（per-CPU 节点所在的那条）。这个位置只有一个，所以它本质上是「队列外的插队名额」，插到就算 pending 持有者，插不到就老老实实入队。

什么时候算「有 contention」，看这一句就够：

c
if (val & ~_Q_LOCKED_MASK)
    goto queue;

只要 locked 之外还有任何一位被置起来（pending 或 tail），直接去排队。这个判断既省事又保守：宁可直接排，不要为了省一次入队去猜。

五、加锁路径：快路径与慢路径 #

快路径在头文件里，一个内联函数，一次 cmpxchg。

c
/* include/asm-generic/qspinlock.h，5.10 */
static __always_inline void queued_spin_lock(struct qspinlock *lock)
{
    u32 val = 0;

    if (likely(atomic_try_cmpxchg_acquire(&lock->val, &val, _Q_LOCKED_VAL)))
        return;

    queued_spin_lock_slowpath(lock, val);
}

atomic_try_cmpxchg_acquire 的语义要记住：拿 val 当输入也当输出。进去时 val == 0，比较 lock->val 是否等于 0，等于就写 _Q_LOCKED_VAL 并返回 true；不等于就把实际值回填进 val 并返回 false。这个回填是后面所有逻辑的起点——慢路径开头那个 val 就是这次失败看到的真实值。

arch_spin_lock 除了这一句还包了抢占控制，那部分在《spinlock：自旋锁的原理、实现与陷阱》里。

慢路径一进来先处理一个过渡态。

c
if (pv_enabled())
    goto pv_queue;

if (virt_spin_lock(lock))
    return;

/*
 * 0,1,0 -> 0,0,1
 */
if (val == _Q_PENDING_VAL) {
    int cnt = _Q_PENDING_LOOPS;
    val = atomic_cond_read_relaxed(&lock->val,
               (VAL != _Q_PENDING_VAL) || !cnt--);
}

/*
 * 只要有竞争，去排队
 */
if (val & ~_Q_LOCKED_MASK)
    goto queue;

这段的意图是「别急着排队」。val == _Q_PENDING_VAL 意味着锁值只有 pending 位被置起来，对应 owner 已经放锁、pending 持有者还没来得及把 pending 换成 locked 的那一瞬。这一瞬很短。如果这时候往下走，下一步那个 val & ~_Q_LOCKED_MASK 一定为真，当前线索会被踢进队列——入队要碰 per-CPU 节点所在的第二条 cacheline，一次冷访问。反过来，如果等一小会儿让 pending 持有者完成交接（它 clear pending、set locked），本线索就能顶替它的位置成为新的 pending 持有者，不排队。

等多久？_Q_PENDING_LOOPS。

c
/* kernel/locking/qspinlock.c，5.10 */
#ifndef _Q_PENDING_LOOPS
#define _Q_PENDING_LOOPS 1
#endif

注释解释得很清楚：设这个上限是因为不保证有前进（forward progress）。理论上交接很快，但竞争激烈时「单 pending 位长时间不动」的情况会出现，死等就变成了给别人做嫁衣。1 的意思是重读一次，读不到就走。

4.2 里没有这个上限，那段是 while ((val = atomic_read(&lock->val)) == _Q_PENDING_VAL) cpu_relax();，无界。加入 _Q_PENDING_LOOPS 与配套的 atomic_cond_read_relaxed 是在 5.x 之前的某个版本（具体版本号未验证）。

接着进 pending 分支。走到这里说明 val 的 locked 之外没有任何位被置起来，也就是「至少看上去我是第一个等待者」。

c
/*
 * 0,0,* -> 0,1,* -> 0,0,1  pending, trylock
 */
val = queued_fetch_set_pending_acquire(lock);

if (unlikely(val & ~_Q_LOCKED_MASK)) {
    /* 撤销我们可能设上的 PENDING */
    if (!(val & _Q_PENDING_MASK))
        clear_pending(lock);
    goto queue;
}

if (val & _Q_LOCKED_MASK)
    atomic_cond_read_acquire(&lock->val, !(VAL & _Q_LOCKED_MASK));

clear_pending_set_locked(lock);
lockevent_inc(lock_pending);
return;

queued_fetch_set_pending_acquire 是一次 atomic_fetch_or_acquire(_Q_PENDING_VAL, &lock->val)，返回旧值。三个结果分支：

第一，旧值里 locked 之外还有位（别人抢先设了 pending，或者别人已经排进队列），那就撤销。撤销前要看清楚 pending 位是谁设的：if (!(val & _Q_PENDING_MASK)) clear_pending(lock); 只有在「旧值里本来没有 pending」时才清——那说明这一位是本次 fetch_or 加的。如果旧值里已经有 pending（别人设的），绝不能清，清了就把别人从 pending 位置上摘掉了。

第二，旧值只有 locked（或者干脆是 0），并且我们成功把 pending 置了起来，就进入等待。注意等待条件是 !(VAL & _Q_LOCKED_MASK)，只看 locked，不看 pending。拿到锁之后 clear_pending_set_locked 一次把 *,1,0 改成 *,0,1。

第三，queued_fetch_set_pending_acquire 之后 val 里 tail 非 0，说明队列已经有人了，回退 pending 并排队。

这里的内存序不能省。源码注释点明：这个等待循环必须是 load-acquire，用来和「清 locked 位的 store-release」配对，从而建立锁的先后顺序；原因不是所有 clear_pending_set_locked 的实现都带完整屏障。

两个辅助函数在 _Q_PENDING_BITS == 8 下是字节/半字操作：

c
/* _Q_PENDING_BITS == 8 分支，5.10 */
static __always_inline void clear_pending(struct qspinlock *lock)
{
    WRITE_ONCE(lock->pending, 0);            /* *,1,* -> *,0,* */
}

static __always_inline void clear_pending_set_locked(struct qspinlock *lock)
{
    WRITE_ONCE(lock->locked_pending, _Q_LOCKED_VAL);   /* *,1,0 -> *,0,1 */
}

static __always_inline void set_locked(struct qspinlock *lock)
{
    WRITE_ONCE(lock->locked, _Q_LOCKED_VAL); /* *,*,0 -> *,0,1 */
}

clear_pending_set_locked 只写 16 位，tail 那半部不受影响，所以不需要 cmpxchg 循环。整套设计里「用一个字节/半字写代替整字 cmpxchg」是反复出现的省法，代价是要有 _Q_PENDING_BITS == 8 这个前提；一旦 CPU 数超过 16384，pending 只剩 1 位，这些操作退化成 atomic_andnot / atomic_add。

六、慢路径里的 MCS 队列 #

到了 queue: 标签，说明 pending 这条路走不通，必须挂进队列。四步准备：

    barrier();
    node->locked = 0;
    node->next   = NULL;
    pv_init_node(node);

四个动作逐一对应：

node = this_cpu_ptr(&qnodes[0].mcs) 拿 per-CPU 数组的基地址。idx = node->count++ 领层号，自增发生在取用之前，所以取到的是「本次要用第几层」。encode_tail(smp_processor_id(), idx) 把 CPU 号加一后左移，和层号拼成 16 位 tail。grab_mcs_node(node, idx) 按 struct qnode 的大小步进，得到本层节点。

那个 barrier() 和上面的注释是整篇里最容易忽略的一处正确性细节：count 的自增必须排在节点初始化的 store 之前。若编译器把 node->locked = 0 提到 count++ 前面，一个恰好在此时进来的中断会认为这一层已经可用，然后覆盖掉我们刚写的值。开了 paravirt 时 pv_init_node 还会再碰节点，顺序要求一样。

idx >= MAX_NODES 是兜底：四层全占满说明出现了预想不到的嵌套深度（比如某些架构上嵌套 NMI 也去拿 spinlock）。这时不排队了，退化成最原始的「直接自旋在锁上」，宁可性能差也不能崩。

节点备好之后还有一次免费的重试机会。

c
    /*
     * 刚碰过一条（大概率是冷的）per-CPU cacheline，
     * 干脆再试一次锁，说不定刚才有人放锁了
     */
    if (queued_spin_trylock(lock))
        goto release;

    smp_wmb();

    old  = xchg_tail(lock, tail);
    next = NULL;

queued_spin_trylock 是「读一次，非 0 就失败，是 0 才 cmpxchg」：

c
static __always_inline int queued_spin_trylock(struct qspinlock *lock)
{
    u32 val = atomic_read(&lock->val);

    if (unlikely(val))
        return 0;

    return likely(atomic_try_cmpxchg_acquire(&lock->val, &val, _Q_LOCKED_VAL));
}

先读一次再决定要不要发原子指令，因为读比 cmpxchg 便宜得多，而失败是常态。

smp_wmb() 与 xchg_tail 的配合也是必需的：节点初始化（locked = 0、next = NULL）必须先于 tail 的发布，否则后面前驱可能拿到一个还没初始化好的 node 并往里写 next。

xchg_tail 在 _Q_PENDING_BITS == 8 下是一次 16 位 xchg：

c
static __always_inline u32 xchg_tail(struct qspinlock *lock, u32 tail)
{
    /* 调用者已保证 mcs node 初始化完毕，可以用 relaxed */
    return (u32)xchg_relaxed(&lock->tail, tail >> _Q_TAIL_OFFSET) << _Q_TAIL_OFFSET;
}

返回值是旧的 16 位 tail，左移回 bit16 对齐的位置，这样和 _Q_TAIL_MASK 比较时不用改口径。CPU 数超过 16384 时 pending 只有 1 位，tail 不落在整字节边界上，没法用 16 位 xchg，退化成对 lock->val 的 cmpxchg 循环（保留 _Q_LOCKED_PENDING_MASK 部分，只换 tail）。

接下来看有没有前驱。

c
    if (old & _Q_TAIL_MASK) {
        prev = decode_tail(old);
        WRITE_ONCE(prev->next, node);

        pv_wait_node(node, prev);
        arch_mcs_spin_lock_contended(&node->locked);

        /*
         * 等 MCS 锁期间，后面可能又排进来人，next 已被填好。
         * 顺手预取一下，减少后面 unlock 的延迟
         */
        next = READ_ONCE(node->next);
        if (next)
            prefetchw(next);
    }

old & _Q_TAIL_MASK 为 0 说明队列原本是空的，本节点就是队首也是队尾，不需要等前驱，直接跳到自旋在锁值上那一步。非 0 说明有前驱：解出前驱地址，把自己挂到 prev->next 上，然后自旋在自己的 node->locked 上。

arch_mcs_spin_lock_contended 的默认实现在 kernel/locking/mcs_spinlock.h：

c
#ifndef arch_mcs_spin_lock_contended
#define arch_mcs_spin_lock_contended(l)                 \
do {                                                    \
    smp_cond_load_acquire(l, VAL);                      \
} while (0)
#endif

#ifndef arch_mcs_spin_unlock_contended
#define arch_mcs_spin_unlock_contended(l)   smp_store_release((l), 1)
#endif

smp_cond_load_acquire 不是裸轮询：ARM64 上它用 wfe 让核进入低功耗等待，前驱的 store-release 会发事件把它叫醒；不支持这类等待的架构上它就是「load + 屏障 + cpu_relax」的循环。同一份 C 代码在不同架构上的功耗表现差别很大，这点在做功耗剖析时要记住（各架构的具体实现未逐个核对）。

到这里，一条线索要么成了 pending 持有者，要么成了队首，要么挂在别人后面等自己的 node->locked 被写成 1。三条路的汇合点是「队首自旋在锁值上」，那是下一章的事。

七、解锁与队列传递 #

队首的自旋条件是「锁值和 pending 都清掉了」。

c
    /*
     * 已经排到队首，等 owner 和 pending 让开
     *
     * *,x,y -> *,0,0
     */
    if ((val = pv_wait_head_or_lock(lock, node)))
        goto locked;

    val = atomic_cond_read_acquire(&lock->val, !(VAL & _Q_LOCKED_PENDING_MASK));

locked:
    /*
     * n,0,0 -> 0,0,1 : 拿锁，无竞争
     * *,*,0 -> *,*,1 : 拿锁，有竞争
     */
    if ((val & _Q_TAIL_MASK) == tail) {
        if (atomic_try_cmpxchg_relaxed(&lock->val, &val, _Q_LOCKED_VAL))
            goto release;   /* No contention */
    }

    set_locked(lock);

    /*
     * 有竞争：等 next 出现，把锁传下去
     */
    if (!next)
        next = smp_cond_load_relaxed(&node->next, (VAL));

    arch_mcs_spin_unlock_contended(&next->locked);
    pv_kick_node(lock, next);

release:
    __this_cpu_dec(qnodes[0].mcs.count);

这段要拆开看，因为它同时处理了「我是队尾」和「我后面还有人」两种情形。

atomic_cond_read_acquire 的等待条件是 !(VAL & _Q_LOCKED_PENDING_MASK)，也就是 locked 和 pending 都清零。为什么队首还得等 pending？因为 pending 持有者排在队首之前。队列是「队首 → 队首之后」，而 pending 持有者站在这两者之外、位置更靠前。pending 位没清掉，说明那位还没进临界区，队首不能抢。

拿锁的判定条件是 (val & _Q_TAIL_MASK) == tail：锁值里记录的 tail 还是我自己，说明我后面没人排队。这种情况下一次 cmpxchg 把整个 val 写成 _Q_LOCKED_VAL，等于顺手把 tail 也清了，队列回到空态。这是最常见的路径，goto release 直接收工。

如果 tail 不是我，两种可能：后面有人排进来了，或者有新的 pending 竞争者出现。这时不能用 cmpxchg 整字写（会把别人的 tail 盖掉），只能用 set_locked 单独置 locked 位——那是 8 位写，tail 那半部不动。

set_locked 之后必须把锁传给下一个人。if (!next) next = smp_cond_load_relaxed(&node->next, (VAL)); 这里 next 可能是入队时顺手读到的那个，也可能为 0：为 0 说明「我读 next 的那一刻后面还没人」；但读完之后、我拿锁之前，很可能又有人挂到我后面了。所以这里要再等一次，等 node->next 变成非 0。这一步不能省，省了就丢唤醒，后面那位永远等不到 locked 被置 1。

arch_mcs_spin_unlock_contended(&next->locked) 就是 smp_store_release(&next->locked, 1)，一次 store-release。它同时完成两件事：告诉下一位「轮到你了」，并用 release 语义保证我在临界区里的写对下一位可见。

__this_cpu_dec(qnodes[0].mcs.count) 在 release 标签，三条路径都会走到它（包括 idx >= MAX_NODES 那条兜底路），嵌套计数必须回到原值，否则这台 CPU 的层号会被永久占掉。

解锁本身只有一行。

c
/* include/asm-generic/qspinlock.h，5.10 */
static __always_inline void queued_spin_unlock(struct qspinlock *lock)
{
    /* unlock() 需要 release 语义 */
    smp_store_release(&lock->locked, 0);
}

一次 8 位 store-release，把 locked 清零。就这么多。tail 不清，pending 不动——因为此刻 tail 里记的是队首，队首要靠它判断「我是不是队尾」；pending 位属于别人。清 tail 的活交给了队首的 cmpxchg，这是设计上的分工。

对比 4.2 的版本，解锁当时也是同一行代码，但它与 5.10 的差别在慢路径末尾：4.2 是 for(;;) 里 if (val != tail) { set_locked(lock); break; } 然后 while (!(next = READ_ONCE(node->next))) cpu_relax();，5.10 换成了 atomic_try_cmpxchg_relaxed 加 smp_cond_load_relaxed。语义一样，后者的等待在 ARM64 上能用 wfe。

把整条状态链串起来，源码注释里那张 ASCII 图值得抄下来当速查表：

text
                            fast     slow      unlock
                              :        :           :
uncontended  (0,0,0) ---------:------> (0,0,1) ----:-------> (*,*,0)
                              :        |  ^--------.------. /
                              :        v  |        |      |
pending      (0,1,1) <-----------------+  |        |      |
                              :        |  ^--'     |      |
                              :        v           |      |
uncontended  (n,x,y) -----------------> (n,0,0) ---'      |

                              :        v                  |
contended    (*,x,y) -----------------> (*,0,0) --> (*,0,1) -'

读法：左边是入口状态，(tail, pending, locked) 三元组；横向是三条路径；(*) 表示 tail 非 0。

顺带说清一个常被问到的点：qspinlock 没有「解锁时唤醒别人」这一步。因为等待者从来没睡下去过（除了硬件级的 wfe），它们一直在自己的节点上自旋。解锁只需把 locked 清零，队首会看见。真正的「传递」发生在队首拿锁之后，用一次 store-release 把下一个人从 MCS 节点自旋里放出来。

八、qspinlock 为什么能减少 cacheline 争抢 #

先给结论，再给账本。

结论：qspinlock 把「N 个核抢同一行」变成「N 个核各碰各的行，只有队首碰共享行」。竞争规模再大，共享行的访问频率也是常数级的（每次锁传递一次），不随等待者数目增长。

账本要按「谁碰哪条 cacheline、碰几次」来算。假设有 N 个等待者，临界区里什么都没干。

事件 ticket spinlock qspinlock
加锁快路径（无竞争） 1 次原子操作，1 行 1 次 cmpxchg，1 行
加锁失败领号 1 次 fetch_add 写共享行（N 次/N 个等待者） 不改锁值，写完 per-CPU 节点后一次 xchg_tail（N 次，但只写 tail 半部）
等待期间 反复读共享行（N 个核都在读） pending 持有者读共享行；队首读共享行；其余读自己的 node->locked
锁传递 放锁者写共享行，所有等待者立即一起重读（一次抖动全员参与） 队首写下一人的 node->locked，只有那一个人被唤醒
放锁 写共享行 写共享行的 locked 字节
共享行总写次数 ~2N（领号 + 放锁） ~N + 1（tail 发布 + 每次传递 1，传递在各自节点上）

有三处值得掰开。

第一处，等待期间读的粒度。ticket 锁所有人都读同一个地址，缓存一致性协议下这是「共享态」，读本身不产生总线流量；但一旦有人写（领号、放锁），所有共享副本全部失效，下一次读要重新取行。qspinlock 把等待者的读分散到各自的 per-CPU 节点上，共享行只在传递瞬间被写一次，失效范围是「一个节点」，不是「全员」。

第二处，写 tail 的代价。qspinlock 入队要写 tail，看起来还是写共享行。区别在于写的大小和频率：tail 是 16 位，用 xchg 一次搞定，而且只在入队那一刻写一次；写完之后这位就不碰共享行了。ticket 锁的领号也是每次一次，但等待期间所有人还在读同一行，每次放锁都要全员重取。省下来的不是写次数，是「等待期间的重取次数」。

第三处，也是最少被提到的一点：qspinlock 里没有「唤醒风暴」。ticket 锁放锁后，N 个等待者同时发现条件满足、同时重读、同时尝试原子指令，只有一个成功，其余全部退回去。这一轮原子指令的争抢是纯粹的浪费。qspinlock 的传递是点对点：队首把 next->locked 置 1，只有那一个人从 wfe 里醒来，其余人还在各自的节点上等着，压根不知道这件事发生过。

pending 那一位是唯一例外，它在共享行上自旋。这是有意留的「特权位」：位置只有一个，成本可控，换来的是省掉一次入队。它同时也是个可调项——_Q_PENDING_LOOPS 控制「等这个位置多久」，调大偏向省入队，调小偏向快落队。

真要在自己的机器上验证，盯三个点：lock_slowpath 与 lock_pending 的计数（qspinlock_stat.h 里的 lockevent_inc 就是给它们用的）、perf 里 cache-misses 在锁函数上的分布、以及 lock_no_node 是否非 0（非 0 说明嵌套超过四层，退化了）。

九、自旋锁的上限：临界区长了怎么办 #

自旋锁的问题不在实现，在模型。它假设了两件事，而这两件事在实际代码里都不总能成立。

假设一：临界区很短。自旋的成本是「白烧 CPU 周期」，只要等待时间短于上下文切换开销，自旋就比睡眠划算。这个不等式一旦反过来，自旋就成了纯亏——CPU 被占着不干活，还可能把持锁者挤下 CPU。

假设二：持锁者一定能跑。这在抢占式内核里并不成立。高优先级任务抢占了持锁者，持锁者没法继续执行、也就没法放锁，而等待者还在自旋，白白耗着。核数少的时候这会演化成死锁式的活锁。

这两条假设失效时的表现，就是本文要说清的「上限」：不是性能上限，是适用范围的上限。

场景 自旋锁能不能用 原因
改几个局部变量、链表插入 能，这是本行 临界区十来个周期
持有期间调用可能睡眠的函数 不能 睡眠时还占着自旋锁，别的核转到死
中断上下文里保护数据 必须用自旋锁 中断上下文不能睡
临界区里有 msleep、copy_from_user、等 I/O 不能 一旦睡下，等待者可能自旋到你回来
临界区里有内存分配（未加 GFP_ATOMIC） 不能 分配器可能睡眠
临界区里再拿同类锁 看顺序 顺序反了就是 ABBA 死锁；同一把锁递归必死
临界区要跑几十微秒 别用 该换 mutex，见第十章

还有一层现实约束：手机这类异构平台上，cluster 之间的拓扑距离不一致，自旋锁的公平设计（先来先得）和「谁该先被满足」的实际需求（响应延迟优先）方向不同。这是设计目标层面的冲突，靠调参解决不了，只能换锁的语义。

所以内核才需要第二条路。自旋锁解决的是「短且不能睡」，剩下的全部交给 mutex。

十、mutex 的设计目标：拿不到就睡 #

mutex 的定位一句话能说完：拿不到锁就把当前任务挂起，等别人放锁时被唤醒。

这个「挂起」不是比喻。它会调 schedule_preempt_disabled()，把 CPU 让出去，任务进入 TASK_UNINTERRUPTIBLE（mutex_lock）、TASK_INTERRUPTIBLE（mutex_lock_interruptible）或 TASK_KILLABLE（mutex_lock_killable）。代价是一次上下文切换，收益是等待期间 CPU 可以去干别的。

代价的量级决定了它的适用边界：临界区越长，一次切换的摊销越划算；临界区越短，切换开销占比越高。

内核把上面这些规矩写成了注释，include/linux/mutex.h 里那段英文，转成中文是这样：

规矩 违反的后果
同一时刻只有一个任务能持有 临界区互斥失效
只有 owner 能解锁 owner 字段错乱，唤醒逻辑失效
不允许多次解锁 同上
不允许递归加锁 自己等自己，死锁
必须用 API 初始化 owner/wait_lock/wait_list 没初始化
不能用 memset 或结构体拷贝初始化 同上，且 wait_list 的自引用会坏
任务退出前必须释放持有的锁 锁永久泄漏
锁所在内存不能在持锁期间释放 解锁写到已释放内存

这些规矩在开了 CONFIG_DEBUG_MUTEXES 时会被真正检查，配合 lockdep 还能查出循环死锁。

一个常被忽略的点：这些都是「mutex 比二值信号量更严格」的地方。二值信号量允许谁 up 都行、允许递归 down（虽然没意义），mutex 一条都不允许。严格换来的是实现可以做优化——知道只有 owner 会解锁，owner 字段就敢拿来塞标志位，也敢做交接（handoff）。这正是后面几章所有优化能成立的前提。

十一、mutex 的数据结构 #

以 5.10 为准。

c

    atomic_long_t           owner;
    spinlock_t              wait_lock;

成员 类型 作用
owner atomic_long_t 两用：高位存持有者的 task_struct *（NULL 表示无人持有）；低 3 位存标志。task_struct 按 L1_CACHE_BYTES 对齐，低位天然是 0，白拿

osq 只有一个 tail：

c
/* include/linux/osq_lock.h，5.10 */
struct optimistic_spin_node {
    struct optimistic_spin_node *next, *prev;
    int locked;    /* 1 if lock acquired */
    int cpu;       /* encoded CPU # + 1 value */
};

struct optimistic_spin_queue {
    /* 编码后的队尾 CPU 号；空队列时是 OSQ_UNLOCKED_VAL */
    atomic_t tail;
};

#define OSQ_UNLOCKED_VAL (0)

tail 不是指针，是 CPU 号加一。节点是 per-CPU 的，拿到 CPU 号就能定位。OSQ_UNLOCKED_VAL 取 0 同样是为了让「空队列」和「队尾在 cpu0」不撞车。

owner 和 osq 的分工要分清：owner 是「谁持锁」，osq 是「谁有资格盯着 owner 看」。前者是锁状态，后者是自旋许可证队列。

MUTEX_FLAG_WAITERS 0x01 __mutex_add_waiter，条件是「我成了队首」 wait_list 非空，解锁时必须走唤醒逻辑 __mutex_remove_waiter 时若链表已空，__mutex_clear_flag(MUTEX_FLAGS) 一起清
MUTEX_FLAG_HANDOFF 0x02 唤醒后的 top waiter 在 first 为真时 下次解锁别广播了，直接把锁交给我 交接完成时 __mutex_handoff 重建 owner 值不带它；__mutex_trylock_or_owner 成功取锁时也显式清
MUTEX_FLAG_PICKUP 0x04 __mutex_handoff，且 task 非 NULL 锁已经写上了你的名字，来取 成功取锁的 __mutex_trylock_or_owner 里清

辅助函数都很短：

{

}

}

__mutex_set_flag / __mutex_clear_flag 是无锁的原子或/与非，不拿 wait_lock。这是有意的：标志位和 owner 指针打包在同一个原子变量里，任何一处改都要走原子操作，否则会撕裂。

这个阶段的 owner 只是个「给乐观自旋看的提示」，真正决定谁能进临界区的是 count。count 的三个取值要记牢：1 空闲、0 被持有、负数表示被持有且有人排队。快路径是 atomic_dec_return 为 0 就走下去，不成则进慢路径；慢路径里用 atomic_xchg(&count, -1) 拿到锁并顺手标记「有人等」。

十二、mutex 的加锁快路径 #

入口只有三行，但每一行都有讲究。

c
/* kernel/locking/mutex.c，5.10 */
void __sched mutex_lock(struct mutex *lock)
{
    might_sleep();

    if (!__mutex_trylock_fast(lock))
        __mutex_lock_slowpath(lock);
}

might_sleep() 不只是个注释性的占位。开了 CONFIG_DEBUG_ATOMIC_SLEEP 时它会检查当前是否处在原子上下文（中断、软中断、持有自旋锁、抢占关闭），命中就打印调用栈。没开这个选项时它退化成 might_resched()；在 CONFIG_PREEMPT_NONE / CONFIG_PREEMPT 下 might_resched() 是空的，在 CONFIG_PREEMPT_VOLUNTARY 下它会调 _cond_resched() 主动让出一次。

快路径：

c
static __always_inline bool __mutex_trylock_fast(struct mutex *lock)
{
    unsigned long curr = (unsigned long)current;
    unsigned long zero = 0UL;

    if (atomic_long_try_cmpxchg_acquire(&lock->owner, &zero, curr))
        return true;

    return false;
}

一次 cmpxchg，把 owner 从 0 换成 current。成功就进临界区，代价和其他任何原子操作一样低；失败说明锁被持有，或者正处在交接过程中（owner 里带着标志位）。

这里有个容易误判的细节：快路径要求 owner 整体等于 0，不只是 task 指针为 NULL。也就是说，哪怕没人持锁，只要 MUTEX_FLAG_* 还有位被置着，快路径一样失败。这正是设计意图——有标志位说明有等待者或正在交接，这种时候不该让新来的插队，得走慢路径按规矩办。

另一个细节：快路径不加 wait_lock。所以两个任务可以同时在同一把 mutex 上做 cmpxchg，硬件保证只有一个赢。owner 用原子变量而不用锁保护，就是为了这个。

解锁快路径是对称的：

c
static __always_inline bool __mutex_unlock_fast(struct mutex *lock)
{
    unsigned long curr = (unsigned long)current;

    if (atomic_long_cmpxchg_release(&lock->owner, curr, 0UL) == curr)
        return true;

    return false;
}

只有当 owner 整体等于 current（说明只被当前任务持有、且没有任何标志位）时，才把它清零。一旦带上任何标志位，这次 cmpxchg 就失败，转慢路径。这个条件同时完成了一件事：验证解锁者确实是 owner。

__mutex_trylock_fast 用 acquire 语义，__mutex_unlock_fast 用 release 语义。这一对把临界区里的读写框住了：拿锁之后的读能看到放锁之前的写，放锁之前的写对下一个拿锁者可见。

mutex_trylock 走的是另一条路，它不碰 wait_list，但要处理交接：

c
/* kernel/locking/mutex.c，5.10 */
static inline struct task_struct *__mutex_trylock_or_owner(struct mutex *lock)
{
    unsigned long owner, curr = (unsigned long)current;

    owner = atomic_long_read(&lock->owner);
    for (;;) {
        /* 必须循环，可能和标志位竞争 */
        unsigned long old, flags = __owner_flags(owner);
        unsigned long task = owner & ~MUTEX_FLAGS;

        if (task) {
            if (likely(task != curr))
                break;                                  /* 别人持有，失败 */
            if (likely(!(flags & MUTEX_FLAG_PICKUP)))
                break;                                  /* 是我但没交接，递归失败 */
            flags &= ~MUTEX_FLAG_PICKUP;                /* 交接给我了，清掉取走 */
        } else {
            DEBUG_LOCKS_WARN_ON(flags & MUTEX_FLAG_PICKUP);
        }

        /*
         * 我们置了 HANDOFF，就必须保证它不会活过取得锁的那一刻。
         * 如果在未上锁的 mutex 上（错误地）置了该位，这里会清掉。
         */
        flags &= ~MUTEX_FLAG_HANDOFF;

        old = atomic_long_cmpxchg_acquire(&lock->owner, owner, curr | flags);
        if (old == owner)
            return NULL;    /* 成功 */
        owner = old;
    }
    return __owner_task(owner);
}

返回值语义要记清楚：成功返回 NULL，失败返回持有者的 task 指针。这个反直觉的约定来自它的主要使用者——乐观自旋需要「失败时顺便拿到 owner 是谁」，省一次读。

三条分支对应三种情形：

task 非 0 且不等于 curr：别人持有，失败返回 owner。

task 等于 curr 且带 PICKUP：交接给我了。清掉 PICKUP 再 cmpxchg，等于「签收」。这是唯一允许「同一个人重复看到自己持有」的场景，也是 handoff 的落地点。

task 等于 curr 但不带 PICKUP：递归加锁，失败。MUTEX_FLAG_HANDOFF 在这里被无条件清掉的理由写在注释里——如果某条路径不小心在未上锁的 mutex 上置了 HANDOFF，取锁时必须把它带走，否则这个位会一直留着，导致后续解锁永远走交接分支。

atomic_long_cmpxchg_acquire 失败要重来，因为 owner 是多个字段打包的，读到和写回之间可能被别人改标志位。整个循环没有任何锁保护，靠 cmpxchg 的重试兜底。

__mutex_trylock 就是它的布尔化包装：

c
static inline bool __mutex_trylock(struct mutex *lock)
{
    return !__mutex_trylock_or_owner(lock);
}

十三、mutex 的慢路径：乐观自旋与睡眠 #

__mutex_trylock_fast 失败就进 __mutex_lock_slowpath，最终落到 __mutex_lock。这条路上有三个阶段，顺序不能乱：先抢占式地乐观自旋一段，再决定要不要睡，睡下去之后靠交接被唤醒。

1、先看 __mutex_lock 的骨架 #

2、乐观自旋要满足五个条件 #

mutex_optimistic_spin 不是无条件自旋，它前面有一串前置检查，任何一个不成立就直接返回 false，去睡。

c
/* kernel/locking/mutex.c，5.10，删减 */
static __always_inline bool
mutex_optimistic_spin(struct mutex *lock, struct ww_acquire_ctx *ww_ctx,
                      struct mutex_waiter *waiter)
{
    if (!waiter) {
        /*
         * 乐观自旋者的工作就是抢 owner，抢到了才走。
         * 这里能成功，说明队列空或者已经轮到我了。
         */
        if (!mutex_can_spin_on_owner(lock))
            goto done;

        /*
         * 如果 OSQ 里已经有人在自旋，让它们先来，避免自己插队。
         */
        if (!osq_lock(&lock->osq))
            goto done;
    }

    for (;;) {
        struct task_struct *owner;

        owner = __mutex_owner(lock);
        if (owner && !mutex_spin_on_owner(lock, owner))
            break;

        /* 也许 owner 刚放锁，再试一次 */
        if (__mutex_trylock(lock)) {
            if (waiter)
                __mutex_remove_waiter(lock, waiter);
            /* osq 里没有 waiter，成功拿到锁 */
            lock_acquired(&lock->dep_map, _RET_IP_);
            ...
            goto done_unlock;
        }

        cpu_relax();
    }
    ...
}

osq_lock 把自旋者排成一队 MCS，和 qspinlock 是同一套思路：每个自旋者在自己的节点上等，队列传递时才被通知。这样避免所有自旋者一起盯着 owner 那一行 cache 猛读。

mutex_can_spin_on_owner 是前置条件，五个都满足才能自旋：

c
static inline bool mutex_can_spin_on_owner(struct mutex *lock)
{
    struct task_struct *owner;
    bool retval = true;

    if (need_resched())
        return false;

    rcu_read_lock();
    owner = __mutex_owner(lock);
    if (owner)
        retval = owner->on_cpu;
    rcu_read_unlock();

    /*
     * 如果 !on_cpu 且 PREEMPT_RCU，owner 可能正在被调度走。
     */
    return retval;
}

拆开看这五个条件：

条件 检查点 不满足时
当前不需要重调度 need_resched() 立刻让出 CPU
owner 存在 __mutex_owner(lock) 直接去 trylock
owner 正在 CPU 上跑 owner->on_cpu 别等了，睡
当前没在关抢占态睡过 preempt_count 检查 不能自旋
ww_ctx 的上下文兼容 ww 相关 走 ww 特殊路径

第五条最关键。owner->on_cpu 是判断「值不值得等」的唯一依据：如果持锁者根本不在 CPU 上跑，自旋就是纯浪费——它可能在等 IO，可能被别的核抢占，可能已经睡了。这时候睡下去比自旋强。

owner->on_cpu 的读取要放在 rcu_read_lock() 里，因为 owner 可能在这期间被释放。这是 RCU 用在「结构体生命周期」上的典型场景。

3、mutex_spin_on_owner：边盯边判断 #

盯住 owner 的那一小段：

c
static noinline
bool mutex_spin_on_owner(struct mutex *lock, struct task_struct *owner)
{
    bool ret = true;

    rcu_read_lock();
    while (__mutex_owner(lock) == owner) {
        /*
         * 确保 owner 还在跑，否则我们白转。
         */
        if (owner->on_cpu) {
            barrier();
            continue;
        }

        /*
         * owner 不在跑了，可能已经释放，也可能被切走。
         * 无论哪种，都不值得再自旋。
         */
        ret = false;
        break;
    }
    rcu_read_unlock();

    return ret;
}

barrier() 的用意：防止编译器把 owner->on_cpu 的检查提到循环外。这是个纯编译器屏障，没有硬件代价。

这个循环里没有任何 cpu_relax()，因为 on_cpu 是读本核缓存。真正的 cpu_relax() 在外层循环里，那是 __mutex_trylock 失败之后的退避。

4、真要睡了：上链表 + 设状态 + 调用 schedule #

乐观自旋失败后进等待链表：

c
static void __mutex_add_waiter(struct mutex *lock, struct mutex_waiter *waiter,
                               struct list_head *list)
{
    debug_mutex_add_waiter(lock, waiter, current);

    list_add_tail(&waiter->list, list);
    if (__mutex_waiter_is_first(lock, waiter))
        __mutex_set_flag(lock, MUTEX_FLAG_WAITERS);
}

list_add_tail 保证 FIFO。只有队首的 waiter 才置 MUTEX_FLAG_WAITERS——这个标志位告诉解锁路径「有活人等着，要走交接流程，别走快路径」。

睡下去的主循环：

c
    set_current_state(state);
    for (;;) {
        if (__mutex_trylock(lock))
            goto acquired;

        raw_spin_unlock(&lock->wait_lock);

        /*
         * 虽然已经被 wake，但还得再检查一次。
         */
        schedule_preempt_disabled();

        if (signal_pending_state(state, current))
            goto err;

        raw_spin_lock(&lock->wait_lock);
    }

注意 set_current_state 在 raw_spin_lock 之后、schedule 之前。这个顺序不能反：

  • 必须在持 wait_lock 时设状态，否则解锁者可能在设状态之前就把 PICKUP 置上了，造成丢失唤醒。
  • schedule_preempt_disabled() 而不是裸 schedule()，因为此时已经 preempt_disable() 了，要让出 CPU 得走这个出口。

被唤醒之后先 __mutex_trylock。这里就是交接落地的地方：如果解锁者置了 MUTEX_FLAG_PICKUP，__mutex_trylock_or_owner 会看见「task == curr 且带 PICKUP」，清掉 PICKUP 并把 owner 取走，返回 NULL，成功。

5、signal_pending_state 的三种状态 #

state 参数决定被信号打断的行为：

c
static inline int signal_pending_state(unsigned int state, struct task_struct *p)
{
    if (!(state & (TASK_INTERRUPTIBLE | TASK_WAKEKILL)))
        return 0;
    if (!signal_pending(p))
        return 0;

    return (state & TASK_INTERRUPTIBLE) || __fatal_signal_pending(p);
}

TASK_UNINTERRUPTIBLE 不在这两个位上，所以 mutex_lock 永远返回不了 -EINTR，也永远响应不了信号——包括 kill -9。这就是它被称为「D 状态」的原因，也是 mutex_lock 在可中断场景下要换用 mutex_lock_interruptible / mutex_lock_killable 的原因。

TASK_KILLABLE 是 TASK_WAKEKILL | TASK_UNINTERRUPTIBLE，只响应致命信号。它比 TASK_UNINTERRUPTIBLE 多了一条活路，又比 TASK_INTERRUPTIBLE 少了被 SIGUSR1 这类无害信号打扰的机会。

6、解锁的慢路径：把锁交给下一个人 #

c
static noinline void __sched __mutex_unlock_slowpath(struct mutex *lock, unsigned long ip)
{
    struct task_struct *next = NULL;
    DEFINE_WAKE_Q(wake_q);
    unsigned long owner;

    mutex_release(&lock->dep_map, ip);

    /*
     * 先尝试快路径：没人等，直接清零。
     */
    owner = atomic_long_read(&lock->owner);
    for (;;) {
        unsigned long old;

        if (owner == (unsigned long)current &&
            !(owner & MUTEX_FLAGS)) {
            /* 无标志位，走快路径 */
            ...
        }

        /*
         * 走交接。把 owner 设成 "0 + HANDOFF"，表示「锁空着，
         * 谁抢到就归谁，但优先给队首」。
         */
        old = atomic_long_cmpxchg_release(&lock->owner, owner,
                                          curr | MUTEX_FLAG_HANDOFF);
        if (old == owner)
            break;
        owner = old;
    }

    raw_spin_lock(&lock->wait_lock);
    /*
     * 有人等着，且有 waiter 被 HANDOFF 标记，交给它。
     */
    if (!list_empty(&lock->wait_list)) {
        struct mutex_waiter *waiter = list_first_entry(&lock->wait_list,
                                        struct mutex_waiter, list);
        next = waiter->task;

        debug_mutex_wake_waiter(lock, waiter);
        wake_q_add(&wake_q, next);
    }

    if (owner & MUTEX_FLAG_HANDOFF)
        __mutex_handoff(lock);

    raw_spin_unlock(&lock->wait_lock);
    wake_up_q(&wake_q);
}

MUTEX_FLAG_HANDOFF 的语义：解锁者声明「我要把锁交接给队首」，它会一直保留到队首拿锁的那一刻。__mutex_handoff 负责置 MUTEX_FLAG_PICKUP 给队首。

为什么要两阶段（HANDOFF → PICKUP）而不是一次性唤醒？因为从「解锁」到「队首真正跑起来」之间有个窗口，新的抢锁者可能在这个窗口里插队。HANDOFF 标志位让这个窗口内的 __mutex_trylock_fast 一律失败——owner 带有标志位就不等于 0，快路径过不去。这样保证了队首不被饿死。

这就是 mutex 的公平性机制：交接优先，插队者被挡在标志位外面。

十四、mutex 的 owner 字段与调试标志 #

owner 用一个字段装两样东西，靠 task_struct 的对齐保证低位可用。

c
/*
 * @owner: 'struct task_struct *' 指向当前持锁者，NULL 表示无人持有。
 *
 * 低两位用作标志：
 */
#define MUTEX_FLAG_WAITERS      0x01
#define MUTEX_FLAG_HANDOFF      0x02
#define MUTEX_FLAG_PICKUP       0x04

#define MUTEX_FLAGS             0x07

三个标志位的含义：

标志 何时置 作用 何时清
WAITERS 有 waiter 上链表 锁空着但有人等着，别让快路径跳过 队列空后
HANDOFF 解锁时决定交接 锁空着但应该给队首，插队者退散 队首取锁时
PICKUP __mutex_handoff 置 告诉队首「锁是你的了，签收吧」 队首取锁时

地址与标志位的分离靠两个宏：

c
static inline struct task_struct *__owner_task(unsigned long owner)
{
    return (struct task_struct *)(owner & ~MUTEX_FLAGS);
}

static inline unsigned long __owner_flags(unsigned long owner)
{
    return owner & MUTEX_FLAGS;
}

task_struct 在 include/linux/sched.h 里声明为 ____cacheline_aligned，指针最低 6 位天然为 0（x86_64 的 L1_CACHE_BYTES 是 64）。所以取低 3 位存标志是安全的。

调试时看这三个位能判断现场：

  • owner 非 0 且无标志：正常持有
  • owner 只有 WAITERS（task 部分为 0）：锁空着，但有 waiter 在排队，正在交接
  • owner 带 HANDOFF：解锁者还在交接中
  • owner 带 PICKUP：已经指定给某个 waiter，等它签收

CONFIG_DEBUG_MUTEXES 打开后，struct mutex 多出 magic 成员：

c
#ifdef CONFIG_DEBUG_MUTEXES
    void *magic;
#endif

magic 指向自己（或一个魔数），mutex_lock / mutex_unlock 前后都会检查。它抓的是「用错了锁对象」——比如 memcpy 把整块结构体复制到别处，magic 会对不上。

CONFIG_DEBUG_LOCK_ALLOC 打开后加 dep_map，给 lockdep 用。lockdep 会记录每把锁的获取顺序，发现「A 锁后拿 B」和「B 锁后拿 A」同时出现时报警——这是排查死锁最有效的工具。

这三个调试选项的代价：

  • CONFIG_DEBUG_MUTEXES：每次加解锁多几次指针比较，代价很小，但 struct mutex 变大
  • CONFIG_DEBUG_LOCK_ALLOC：lockdep 用哈希表记录锁序，开销在几十到几百纳秒量级
  • CONFIG_MUTEX_SPIN_ON_OWNER：加自旋队列，多 4 字节 tail，但能省掉不必要的睡眠

生产内核一般只开 SPIN_ON_OWNER。调试内核三个全开。

拿不到时 原地循环 睡下去让出 CPU
能不能在中斷上下文用 能（spin_lock_irqsave） 不能

最本质的差别在「能不能睡」。这不是性能问题，是正确性问题：

spin_lock 自旋时不让出 CPU。如果持锁者被切走，自旋者在同一个核上转圈，谁也别想跑。所以持 spin_lock 期间禁止抢占（preempt_disable()），也禁止睡眠——睡了没人来唤醒自旋者。

mutex 睡下去靠调度器唤醒。如果持锁者在同一个核上被切走，调度器能切回来；但如果在中断上下文里睡，中断处理是关抢占的，切不回来——所以 mutex_lock 里第一句 might_sleep() 就是用来抓这个的。

十六、自旋还是睡眠：判断依据 #

按顺序问四个问题，第一个命中的就是答案：

1、你在中断上下文吗 #

在硬中断、软中断、tasklet、或者持有 spin_lock、或者 preempt_disable() 的区间里——只能用 spinlock。mutex 会触发 might_sleep() 的警告，开了 CONFIG_DEBUG_ATOMIC_SLEEP 还会直接 dump 栈。

2、临界区里有睡眠操作吗 #

有 kmalloc(GFP_KERNEL)、copy_from_user、wait_for_completion、任何可能阻塞的 IO——只能用 mutex。spin_lock 期间睡下去，CPU 就卡死在那儿。

3、数据会被中断上下文访问吗 #

会被——只能用 spinlock，而且必须是 spin_lock_irqsave 或 spin_lock_bh。裸 spin_lock 在中断上下文访问同一把锁时，本核会自死锁。

不会被——mutex 或 spinlock 都行，往下看第四条。

4、临界区有多长 #

估算一下：几条赋值、一次链表操作——spinlock。有函数调用、有循环、有内存分配——mutex。

有个粗略的经验值：大约 1000 条指令以内用 spinlock，再长就该考虑 mutex。这个数字不是硬指标，但大体上更长的临界区用 spinlock 会让所有竞争核心白转，浪费的 CPU 时间远超睡眠唤醒的代价。

5、一张决策表 #

临界区里有阻塞操作？
├─ 是 → mutex（不管其他条件）
└─ 否
   └─ 在中断上下文 / 关抢占区间？
      ├─ 是 → spinlock + _irqsave / _bh
      └─ 否
         └─ 数据被中断上下文共享？
            ├─ 是 → spinlock + _irqsave / _bh
            └─ 否
               └─ 临界区 > ~1000 指令？
                  ├─ 是 → mutex
                  └─ 否 → 两个都行，选 spinlock（更轻）
