版本与架构照实标：读写锁的通用结构与 ARM 汇编来自 wowotech 那篇基于 ARM32、2.6.x~3.x 时代的分析，本文的汇编已按 linux-3.10 的 arch/arm/include/asm/spinlock.h 逐字核对；seqlock 的分析基于 linux-4.0，接口与屏障位置另按 linux-5.15 的 include/linux/seqlock.h 核对；rwsem 的公平性结论来自 linux-5.15.81。凡是我没有在源码里核到的，正文里标「未验证」。

一、为什么自旋锁不够用：读多写少的场景 #

内核里有一张被反复读、极少被改的表。文件系统类型的链表就是标准样本：

c
static struct file_system_type *file_systems;
static DEFINE_RWLOCK(file_systems_lock);

file_systems 指向链表头，每个 struct file_system_type 描述一种文件系统（ext4、yaffs2 等等）。访问分两类：register_filesystem/unregister_filesystem 改链表，fs_name/fs_index 这类函数只遍历链表找节点。

差别在并发度上。多个遍历者同时进临界区，每个都返回正确结果，互不干扰；只要有人改链表，就必须独占，因为遍历者走到一半看到半个新节点，结果就不可信了。

spinlock_t 把这两种情况一视同仁：管你是读还是写，一次只放一个进去。于是 8 核机器上跑 8 个遍历线程，吞吐不是 8 倍，是 1 倍，另外 7 个核在同一个 cacheline 上打转。ARM 上如果有 WFE 还好，CPU 能进低功耗；用纯轮询实现的自旋锁，这 7 个核就是在烧电。

我们把需求摊开：

访问模式 读者之间 读者与写者 需要的语义
全读 可并行 无写者 无锁即可，或只读快照
读多写少 可并行 互斥 共享读、独占写
读写各半 可并行收益小 互斥 普通互斥锁就够
写多读少 不适用 互斥 写者优先，读者让路

第二行就是要解决的问题。rwlock_t 的答案是把「进入临界区的许可」从一个布尔量扩成一个带读者计数的状态字；seqlock_t 的答案更激进，干脆不给读者发许可，让读者直接读，读完再验证这段时间里有没有人改过。

两个方案都在自旋的范畴里，都不睡眠。区别只在读者那一侧要不要写内存。要不要用睡眠版（rwsem），取决于临界区里能不能睡眠，这条边界放到第七节说。

二、读写锁的核心思想：读者共享、写者独占 #

把规则写成条目，比画状态图好记。

加锁侧：

  1. 临界区空着：任何读者或写者都能进，但只能进一个写者，读者可以进多个。
  2. 已有读者在临界区：新读者随便进，写者不行。
  3. 已有写者在临界区：读者、写者都不行。
  4. 已有读者、写者正在等：写者进不去，新读者照样进得去——它拦不住后来者，只能等所有读者退场。

解锁侧：

  1. 写者退出：写者是排他的，临界区里只有它一个，它一放锁，所有在自旋的读者和写者重新抢。
  2. 读者退出：看情况。临界区还有别的读者，等在门外的写者继续等，而且这期间新读者仍能进；等最后一个读者退出，写者才有机会参与竞争。

第 4 条和第 2 条的解锁规则合起来，就是读写锁最大的性格缺陷：写者没有优先权。读者源源不断地来，写者就源源不断地等。第五节专门算这笔账。

用起来没有新东西，就是把 spin_ 前缀换成 read_/write_：

c
rwlock_t lock;

rwlock_init(&lock);

read_lock(&lock);
/* 只读临界区，多个 CPU 可以同时在这里 */
read_unlock(&lock);

write_lock_irqsave(&lock, flags);
/* 独占临界区 */
write_unlock_irqrestore(&lock, flags);

一句话概括语义：防写不防读。写者永远独行，读者永远成群，两者永不同时在临界区。

三、rwlock_t 的数据结构与状态编码 #

通用结构薄得离谱，就一个架构相关的字段：

c
typedef struct {
    arch_rwlock_t raw_lock;
} rwlock_t;

这是 3.x 的样子。到 6.6，调试字段加进来了，骨架没变：

c
typedef struct {
    arch_rwlock_t raw_lock;
#ifdef CONFIG_DEBUG_SPINLOCK
    unsigned int magic, owner_cpu;
    void *owner;
#endif
#ifdef CONFIG_DEBUG_LOCK_ALLOC
    struct lockdep_map dep_map;
#endif
} rwlock_t;

初始化有三条路，静态、动态、常量赋值：

宏/函数 用途 备注
DEFINE_RWLOCK(x) 定义并静态初始化 展开为 rwlock_t x = __RW_LOCK_UNLOCKED(x)
rwlock_init(&x) 运行动态初始化 对应 __rwlock_init，带 lockdep 校验
RW_LOCK_UNLOCKED 常量初始化 赋给已声明的对象

结构体本身不含状态，状态全在 arch_rwlock_t 里。ARM32 的定义简单到一个字：

c
typedef struct {
    u32 lock;
} arch_rwlock_t;

32 位整数，一个字段。看到这个定义就能下一个判断：ARM32 的读写锁不是 ticket-based 的，它没有 next/owner 两个序号。整个状态空间就是这 32 个 bit。

位怎么分：

位域 含义 说明
bit 31 写者标志 置 1 表示写者持锁。写者排他，只有 0/1 两种取值
bit 0~30 读者计数 每个进入读临界区的 CPU 加 1，退出减 1
全 0 空锁 无读者无写者，任何申请者都能进

编码的关键约束是「符号位就是写者位」。读者加 1 之后如果结果变成负数，说明 bit 31 被人占了，也就是写者持锁，读者必须退让。这套设计把「写者是否存在」的判断压缩成一条 adds 指令的条件码，代价是读者计数只有 31 位可用。

读者上限是多少？计数占 bit 0~30，最大值 0x7FFFFFFF，也就是 2^31-1。再多一个读者，加 1 得到 0x80000000，符号位翻成负，strexpl 不执行，这个读者直接被判失败。所以安全范围是 0 到 0x7FFFFFFF 共 2^31-1 个并发读者。素材原文写的是 2^30-1，少算了一半（见勘误表）。

文件组织跟自旋锁同构，三件套：

文件 内容
include/linux/rwlock_types.h rwlock_t 定义、DEFINE_RWLOCK 等初始化宏
include/linux/rwlock.h read_lock/write_lock/read_unlock/write_unlock 接口声明
include/linux/rwlock_api_smp.h SMP 下的接口实现

使用者不用逐个 include，一个 include/linux/spinlock.h 就够了，普通自旋锁和读写自旋锁共用这一道门。

后端实现后来换了人。6.6 的 include/asm-generic/qrwlock_types.h 里躺着这么一段：

c
typedef struct qrwlock {
    union {
        atomic_t cnts;
        struct {
#ifdef __LITTLE_ENDIAN
            u8 wlocked;   /* Locked for write? */
            u8 __lstate[3];
#else
            u8 __lstate[3];
            u8 wlocked;
#endif
        };
    };
    arch_spinlock_t wait_lock;
} arch_rwlock_t;

外层 rwlock_t 一个字没改，里面从「1 个 u32」换成了「1 个 atomic 计数 + 1 把等待队列锁」。这是队列化读写锁（qrwlock）。它的编码换了一套：

常量 值 含义
_QW_WAITING 0x100 有写者在等，新读者必须走慢速路径
_QW_LOCKED 0x0ff 写者持锁时计数区的值
_QW_WMASK 0x1ff 写者相关位的掩码
_QR_SHIFT 9 读者计数的起始位
_QR_BIAS 1 << 9 读者加一就是加这个偏置

读侧就是一条 atomic_add_return(_QR_BIAS, &lock->cnts)，返回值里写者位干净就算拿到锁；写侧就是 cmpxchg 把 0 换成 _QW_LOCKED。这套接替 ARM32 老编码的具体版本节点我没有逐版本核，标「未验证」；能确认的是 6.6 里 arch_rwlock_t 已经是 struct qrwlock，queued_rwlock_t 这个类型名在源码里不存在，说的是同一件东西。

四、read_lock 与 write_lock 的实现 #

接口家族跟自旋锁一一对应，改的只有前缀：

接口 语义
read_lock(l) / read_unlock(l) 拿不到就自旋；读者之间不互斥
write_lock(l) / write_unlock(l) 拿不到就自旋；写者独占
read_trylock(l) / write_trylock(l) 试一次，成了返回 1，不成返回 0，不等待
read_lock_irq(l) / read_unlock_irq(l) 关本地中断再拿读锁
read_lock_irqsave(l, f) / read_unlock_irqrestore(l, f) 存中断标志再关中断
write_lock_irqsave(l, f) / write_unlock_irqrestore(l, f) 写侧同上
read_lock_bh(l) / read_unlock_bh(l) 关软中断
write_lock_bh(l) / write_unlock_bh(l) 写侧同上

调用链跟自旋锁一模一样，只在最底下那层分叉：

text
read_lock(lock)
  -> _raw_read_lock(lock)            每 CPU 数据、lockdep、抢占计数在这一层
    -> __raw_read_lock(lock)         SMP 版本，处理 CONFIG_ 分支
      -> arch_read_lock(&lock->raw_lock)

write_lock(lock)
  -> _raw_write_lock(lock)
    -> __raw_write_lock(lock)
      -> arch_write_lock(&lock->raw_lock)

这就是素材里那句「实现流程与 spin_lock 几乎完全一致，唯一不同的是最后调用体系结构相关的函数是 arch_read_lock 而不是 arch_spin_lock」的确切含义。自旋锁那篇讲的 ticket 逻辑到这里全部让位给 arch_*，通用层只剩三件事：关抢占、喂 lockdep、把参数搬到 raw_lock 上。这三件事的代码在 rwlock_api_smp.h 里，素材没有贴，我也不在这里补全函数体。

真正有区别的是解锁侧，因为读者不止一个：

写者解锁：写者持锁时临界区里必然只有它一个，读者计数一定是 0。所以释放就是把状态字整体写 0，不需要读改写，也不需要判条件。

读者解锁：读者有 N 个，减 1 之后还剩几个不知道。只有减到 0 的那一个读者才需要唤醒等在门外的写者（它们卡在 WFE 上）。ARM 的实现里就有 if (tmp == 0) dsb_sev() 这一句。

这一处不对称，是读写锁实现的全部难点：

动作 需要读改写吗 需要条件唤醒吗 原因
arch_write_lock 是（独占指令） 否 要确认状态字为 0 才能置写者位
arch_write_unlock 否 是（无条件） 直接写 0，随后必发事件
arch_read_lock 是（独占指令） 否 要确认非负才能加 1
arch_read_unlock 是（独占指令） 是（有条件） 只有最后一个读者退出才唤醒写者

注意 arch_read_unlock 也要独占指令：读者之间虽然不互斥，但它们改的是同一个内存字，减 1 这个读改写必须原子，否则两个读者同时退出会丢计数。

五、读写锁的公平性问题：读者会不会饿死写者 #

把第二节的规则跑一遍，答案很快出来。假设 CPU0 上的读者 A 在临界区，CPU1 上的写者 B 到了门口：

时刻 临界区 门口 结果
t0 A（读） 空 A 进
t1 A（读） B（写） B 自旋
t2 A（读）+ C（读） B（写） C 直接进，B 继续自旋
t3 A 退出，C（读）+ D（读） B（写） B 继续自旋
t4 所有读者退出 B（写） B 终于进

t2 和 t3 两行就是问题所在。读者 A 退出时状态字仍是正数，arch_read_unlock 里那句 if (tmp == 0) 不成立，不会发 SEV，B 连被唤醒的机会都没有，它在 WFE 里睡着，直到最后一个读者退出才被踢醒。

从代码层面看，写者没有任何「声明我要进」的动作。ARM32 的 arch_write_lock 是这么个流程：ldrex 读状态字，teq 判断是否为 0，不为 0 就 WFE 等事件，为 0 才 strexeq 写 0x80000000。它全程只观察，不占据任何位。既然它没有留下「我在等」的痕迹，后来者自然无从知道该让它。

读者侧的逻辑反过来：adds 加 1，结果非负就 strexpl 落盘。只要状态字还是正的，谁都拦不住新读者。这条路径没有「有人在等写者」的检查点。

后果是写者的等待时间没有上界。读者到达率 λ、单个读者持锁时长 T，写者的实际等待就随 λT 增长；负载一上来，写者会被无限推后。这在自旋锁的语义里尤其难受：写者不是睡眠，是在核上烧 CPU 轮询。

后来的队列化实现专门补了这个洞。_QW_WAITING（0x100）就是给写者留的牌子：写者在慢速路径上把这一位置起来，新读者 atomic_add_return 回来发现 _QW_WMASK 非空，就知道有人在排队，乖乖回退并转入 queued_read_lock_slowpath。写者从「只观察」变成「占坑」，读者不能再无脑插队。

睡眠锁那边的解法是另一个思路，名字叫 handoff。5.15.81 的 rwsem 里有这么一套机制：

场景 处理
唤醒 top waiter 时锁被偷 若已等待超过 4ms 且未设 handoff，置 handoff 位，禁止他人再抢
被唤醒的写者试图持锁失败 同上，超 4ms 置 handoff 位
handoff 置位后 快速路径、读者的乐观偷锁、写者的乐观自旋全部失效，锁直接递交给 top waiter
持锁成功 清除 handoff

注意这是 rwsem，是睡眠锁，有等待队列、有 task 结构、能睡。自旋锁玩不了这套：它没有队列，也没有地方挂「我等了 4ms」这个状态。所以读写自旋锁的公平性问题，最终是靠换实现（qrwlock）解决的，不是靠打补丁。

六、读写锁在 ARM 上的实现 #

所有读写锁的细节都在 arch_read_lock/arch_write_lock 这一层。ARM32 的两个文件各管一段：

文件 内容
arch/arm/include/asm/spinlock_types.h arch_rwlock_t 定义、__ARCH_RW_LOCK_UNLOCKED 等初始化
arch/arm/include/asm/spinlock.h arch_read_lock/arch_write_lock/__read_lock_failed 等实现

arch_rwlock_t 就是一个 u32 lock，前文已列。有意思的是素材里那句评价：从定义就能看出 ARM 的读写自旋锁不是 ticket-based。判断依据很直接：ticket 锁需要两个 16 位序号（next/owner），一个 u32 塞不下「读者计数 + 写者标志 + 两个序号」，所以它只能走位域方案。

下面按 3.10 源码讲，缩进和指令原样保留。

写者加锁

armasm
static inline void arch_write_lock(arch_rwlock_t *rw)
{
    unsigned long tmp;

    prefetchw(&rw->lock);

    __asm__ __volatile__(
"1:	ldrex	%0, [%1]\n"
"	teq	%0, #0\n"
    WFE("ne")
"	strexeq	%0, %2, [%1]\n"
"	teq	%0, #0\n"
"	bne	1b"
    : "=&r" (tmp)
    : "r" (&rw->lock), "r" (0x80000000)
    : "cc");

    smp_mb();
}

逐条读：

指令 作用
prefetchw 告诉硬件「马上要写这块」，先预取到 cache
ldrex %0, [%1] 独占读状态字到 tmp
teq %0, #0 判断是否为空锁
WFE("ne") 非 0 就等事件。有读者或有写者，都得让路
strexeq %0, %2, [%1] 为 0 才执行：把 0x80000000 写进去
teq %0, #0 + bne 1b 独占写失败说明中间被人插了，回到 1 重来
smp_mb() 拿到锁后插全屏障，防止临界区访存被重排到加锁之前

WFE 是个宏，不是指令。3.10 里它展开成 ALT_SMP("wfe" cond, "nop")，走 .alt.smp.init 段，UP 内核启动时把 wfe 补成 nop。原因写在注释里：sev 和 wfe 是 ARMv6K 扩展，单核 ARMv6 未必有。Thumb-2 下有额外处理，编译器会因为相邻的条件指令自作主张插一条 16 位 IT 指令，把原本 4 字节的 wfene 挤成别的长度，SMP_ON_UP 的修正代码就对不上了，所以显式写了 it。

写者解锁

armasm
static inline void arch_write_unlock(arch_rwlock_t *rw)
{
    smp_mb();

    __asm__ __volatile__(
    "str	%1, [%0]\n"
    :
    : "r" (&rw->lock), "r" (0)
    : "cc");

    dsb_sev();
}

先 smp_mb() 保证临界区内的写已经落地，再一条 str 把 0 写进去。这里不需要 ldrex/strex，理由前面说过：写者持锁时读者计数必为 0，状态字只会是 0x80000000，直接覆盖成 0 不会丢任何信息。最后 dsb_sev()，数据同步屏障加 sev，把卡在 wfe 上的核叫醒。

dsb_sev() 自身也有版本分支：ARMv7 及以上用 dsb 加 sev；ARMv6 用 mcr p15, 0, %0, c7, c10, 4。两者都套在 ALT_SMP 里，UP 编译时 sev 变成 nop。

读者加锁

armasm
static inline void arch_read_lock(arch_rwlock_t *rw)
{
    unsigned long tmp, tmp2;

    prefetchw(&rw->lock);

    __asm__ __volatile__(
"1:	ldrex	%0, [%2]\n"
"	adds	%0, %0, #1\n"
"	strexpl	%1, %0, [%2]\n"
    WFE("mi")
"	rsbpls	%0, %1, #0\n"
"	bmi	1b"
    : "=&r" (tmp), "=&r" (tmp2)
    : "r" (&rw->lock)
    : "cc");

    smp_mb();
}

这段比写者那段绕，因为它把两个判断塞进了条件码：

指令 作用
ldrex %0, [%2] 独占读状态字
adds %0, %0, #1 tmp = tmp + 1，末尾的 s 更新条件码
strexpl %1, %0, [%2] pl 是 positive or zero：结果为非负才落盘
WFE("mi") mi 是 negative：结果为负说明有写者，等事件
rsbpls %0, %1, #0 结果为非负时算 0 - tmp2，tmp2 是 strex 的返回值，0 表示成功
bmi 1b 上一步结果为负（即独占写失败）就重来

关键在 adds 和 strexpl 的配合。读者加 1 后若结果仍是正的，说明 bit 31 没被占，写者不在，可以落盘；若结果变负，说明写者正持锁，pl 条件不成立，strex 根本不执行，直接进 WFE。一条 adds 同时完成了「计数加一」和「检测写者」两个任务。

strexpl 不执行时 %1 保留旧值。rsbpls %0, %1, #0 只在非负分支执行，等于 0 才继续；bmi 1b 就是靠这个把「写失败」翻译成「重试」。素材里那句「pl 的意思就是 positive or zero，也就是说，如果结果是正数或者 0，该指令都会执行」就是这个意思，只是它把 0 这个边界说成「没有 thread 在临界区或者临界区内有若干 read thread」——准确说，是「结果非负」，包含了读者计数加到某值的全部正常情形。

读者解锁

armasm
static inline void arch_read_unlock(arch_rwlock_t *rw)
{
    unsigned long tmp, tmp2;

    smp_mb();

    prefetchw(&rw->lock);

    __asm__ __volatile__(
"1:	ldrex	%0, [%2]\n"
"	sub	%0, %0, #1\n"
"	strex	%1, %0, [%2]\n"
"	teq	%1, #0\n"
"	bne	1b"
    : "=&r" (tmp), "=&r" (tmp2)
    : "r" (&rw->lock)
    : "cc");

    if (tmp == 0)
        dsb_sev();
}

这是四段里唯一带条件唤醒的。sub 减一，strex 落盘，失败重试；出了汇编之后判 tmp == 0，只有减到 0 的那个读者才 dsb_sev()。其他读者悄悄走人，不惊动任何人。

trylock 和 can_lock 这两组辅助接口也在同一文件里：

接口 实现要点
arch_write_trylock ldrex + teq 0 + strexeq，一次不成就返回 0，不进循环
arch_read_trylock adds + strexpl，失败返回 0；tmp2 初值 1，成功被 strex 置 0
arch_write_can_lock(x) ((x)->lock == 0)
arch_read_can_lock(x) (x)->lock < 0x80000000，即符号位为 0

can_lock 不看独占标记，只看状态字的值，所以它是个有竞态的乐观判断，只适合在「马上要 trylock」之前做一次便宜的预判。

三组 relax 直接复用 cpu_relax()：

c
#define arch_spin_relax(lock)   cpu_relax()
#define arch_read_relax(lock)   cpu_relax()
#define arch_write_relax(lock)  cpu_relax()

ARM32 的 cpu_relax() 是 barrier()，行为上等同编译器屏障，不产生指令。所以 ARM32 上的自旋等待靠的是 wfe 而不是 pause 式的退让提示。这点跟 x86 不同，x86 的自旋路径里会出现 rep; nop，也就是 pause。

七、读写锁的局限：读者多时写者等待过久 #

把第六节的四段代码放一起看，局限就浮出来了。

第一，写者没有等待声明。arch_write_lock 全程只 ldrex 观察，不写任何位。后来者看不到它，自然不会让它。

第二，读者路径没有「有人等写」的检查。adds 加一、非负就落盘，这条快路径没有任何分支去查等待者。

第三，写者的等待是烧 CPU 的。WFE 让核进低功耗，但这是 ARM 的红利；纯轮询实现（比如某些 x86 变体）上，写者会一直占着流水线。x86 那套实现里，读者失败后进 __read_lock_failed，核心是 pause：

armasm
/* 概念示意，非逐字源码 */
1:  pause
    cmpl $1, (%rdi)
    jne  1b

素材对 rep; nop 的解释是对的：rep 是重复串操作前缀，正常跟 movs/stos/lods/ins/outs 搭配，rep; nop 是个特例，被处理器翻译成 pause，提示「我在自旋等待」，让 CPU 避开内存序冲突。至于 __read_lock_failed 里那套「先给 rw 加 1 再比较 1」的循环，它依赖当时 x86 那版读写锁把「写者持锁」编码成 -1 这个约定；我在 3.10/4.9/6.6 的 x86 实现里都没有核到完全一致的函数体（那套编码先后换过几轮），所以这段标「未验证」，只当作理解思路的示意。

第四，也是最要命的一条：读写锁不解决优先级反转，只放大它。写者要等所有读者退场，读者里只要有一个被调度器踢下 CPU（抢占、中断处理、缺页），写者的等待时间就由这个读者决定，而不是由读者的工作量决定。临界区里放页错误、放内存分配、放任何会睡着的调用，都会把写者的等待拉长到毫秒级甚至更久。

第五，它是自旋锁，不能睡。临界区里调 copy_to_user、kmalloc(GFP_KERNEL)、mutex_lock，都会在持锁期间睡眠，而睡眠的持锁者不会主动放锁，等它的写者会把 CPU 烧穿。这条规矩跟普通自旋锁一样，但读写锁的读临界区容易被误认为「只是读，不会有问题」，实际读路径里带着 might_sleep() 的操作一样致命。

同一套编码在 ARM64 上是另一组指令。ARM64 的 arch_rwlock_t 我按 3.10~5.x 的 arch/arm64/include/asm/spinlock_types.h 回忆，结构同样是 u32 lock，位分配也一样，但独占访问指令从 ldrex/strex 换成了 ldaxr/stlxr（带 acquire/release 语义），wfe/sev 还在：

层面 ARM32 ARM64
独占读 ldrex ldaxr（带 acquire）
独占写 strex stlxr（带 release）
等事件 wfe wfe
发事件 sev，配 dsb sev，配 dmb ish
显式全屏障 smp_mb() smp_mb() 或依赖 ldaxr/stlxr 隐含序
自旋提示 barrier()（空） yield

这张表的 ARM64 一列我标「部分未验证」：ldaxr/stlxr 与 yield 出现在 ARM64 的自旋实现里是确定的，但读写锁那四个函数在 6.6 的 ARM64 上是不是已经全部转给 asm-generic qrwlock，我没有逐个文件核对。写代码时以你手上的内核源码为准，别拿这张表当依据。

那什么时候该换成睡眠版？看临界区能不能睡：

判据 用读写自旋锁 用 rwsem
临界区会睡眠 不行 必须
临界区访问用户内存 不行 必须
临界区在中断上下文 必须 不行
临界区极短（几十条指令） 合适 开销过大
需要写者不被饿死 换 qrwlock 用 handoff

rwsem 侧的公平性前面讲过 handoff。它还有一层额外保障：等待超过 4ms 就置 handoff 位，之后快速路径、读者的偷锁、写者的乐观自旋全部失效，锁直接递给队首。这条 4ms 的阈值出现在 5.15.81 的 rwsem_mark_wake 与 rwsem_try_write_lock 里，具体宏名是 RWSEM_WAIT_TIMEOUT（素材正文只给了 4ms 这个数值，宏名我按同版本源码补的）。

至于「rwlock 已经没人用了」这句话，得给个准数：素材原文说的是内核不再鼓励使用读写自旋锁，RCU 是更好的选择。这是 2.6.x~4.x 那个年代的判断，到 5.x 依然成立，Documentation/locking/ 里对 rwlock_t 的定位也是「遗留」。要精确到哪个版本开始不推荐，我没核到，标「未验证」；能确认的是 6.6 里它还在，只是后端换成了 qrwlock。

八、seqlock：让读者彻底无锁 #

读写锁至少让读者写一次状态字。seqlock_t 把这最后一次写也省了。

它的出发点是另一个方向的偏好：不给读者优先权，反过来给写者让路。写者想进就进，不管门口排着多少读者；读者自己负责检测「我读的时候有没有人改」，改过就重读。

规则很干净：

  1. 写者之间仍然互斥，靠内嵌的一把自旋锁保证。
  2. 读者不拿任何锁，直接读。
  3. 读者读完检查序号有没有变，变了就整个重来。

素材里那句总结值得抄下来：临界区只允许一个写者进入；没有写者时读者可以随意进入，读者不阻挡读者；临界区里有读者时，写者可以立刻执行，不等。

跟读写锁对比，差异只有一处，但影响巨大：

维度 rwlock_t seqlock_t
读者进入 原子读改写状态字 读一个序号，不写内存
读者之间 并行 并行
写者等待读者 必须等所有读者退场 不等，直接进
读者读到脏数据 不会 会，靠重试修正
读者侧 cacheline 争抢（同一状态字） 只读共享，几乎无争抢
适合的数据 任意结构 定长、可整体重读的数据

最后一行是硬边界。seqlock 的读者拿到的数据是撕裂的，所以它必须满足「重读一次就能拿到完整正确值」这个条件。

jiffies_64 是内核里的标准用例。它 64 位宽，32 位机器上一次读不完，读完高低两半之间会被时钟中断里的写者改掉，于是用 jiffies_lock 保护：

c
u64 get_jiffies_64(void)
{
    u64 ret;
    unsigned int seq;

    do {
        seq = read_seqbegin(&jiffies_lock);
        ret = jiffies_64;
    } while (read_seqretry(&jiffies_lock, seq));

    return ret;
}

写侧：

c
static void tick_do_update_jiffies64(ktime_t now)
{
    write_seqlock(&jiffies_lock);

    /* 改 jiffies_64 及相关变量，略 */

    write_sequnlock(&jiffies_lock);
}

读侧一个 do-while，没有任何加锁动作。这就是 seqlock 的全部使用成本。

九、seqlock 的序号机制：写入时序号加两次 #

数据结构是把自旋锁和一个序号焊在一起：

c
typedef struct {
    struct seqcount seqcount;    /* 序号 */
    spinlock_t lock;             /* 写者串行化 */
} seqlock_t;

4.0 的直接写作：

c
typedef struct {
    struct seqcount seqcount;
    spinlock_t lock;
} seqlock_t;

struct seqcount 里就一个 unsigned sequence（3.x/4.x 的写法，对应源码里的 sl->sequence）。到 5.15，这个成员换成了带关联锁的变体：

c
typedef struct {
    seqcount_spinlock_t seqcount;
    spinlock_t lock;
} seqlock_t;

seqcount_spinlock_t 是「序号 + 指向关联锁的指针」，作用是让 lockdep 能校验写侧临界区确实被那把锁串行化。字段名也从 sequence 变成了 seqcount.seqcount.sequence。这是纯粹的调试与校验增强，读写逻辑没动。

序号的核心规则一句话：写者进临界区加一，出临界区再加一。4.0 的写法：

c
static inline void write_seqlock(seqlock_t *sl)
{
    spin_lock(&sl->lock);
    sl->sequence++;
    smp_wmb();
}

static inline void write_sequnlock(seqlock_t *sl)
{
    smp_wmb();
    sl->sequence++;
    spin_unlock(&sl->lock);   /* 素材未贴，按同版本源码补 */
}

5.15 的写法换成了宏，语义一一对应：

c
static inline void write_seqlock(seqlock_t *sl)
{
    spin_lock(&sl->lock);
    do_write_seqcount_begin(&sl->seqcount.seqcount);
}

static inline void write_sequnlock(seqlock_t *sl)
{
    do_write_seqcount_end(&sl->seqcount.seqcount);
    spin_unlock(&sl->lock);
}

而 do_write_seqcount_begin 与 do_write_seqcount_end 的肉身，还是那两次自增加屏障：

c
static inline void do_raw_write_seqcount_begin(seqcount_t *s)
{
    s->sequence++;
    smp_wmb();
}

static inline void do_raw_write_seqcount_end(seqcount_t *s)
{
    smp_wmb();
    s->sequence++;
}

于是序号的奇偶成了状态指示器：

序号状态 含义 读者的动作
偶数（含 0） 没有写者在临界区 可以读
奇数 有写者在临界区 等它变偶数再读
读数时偶数、读完变奇数 我读的时候写者插进来了 丢弃重读
读数时偶数、读完成另一个偶数 写者来过了 序号不等，重读

为什么是加两次而不是一次？因为读者要区分「写者来过」和「写者正在写」。加一次的话，读者看到一个变了的值就分不清是写完了还是写一半。加两次让「稳定状态」永远是偶数，「进行中」永远是奇数，读者用一个 & 1 就能判断。

这也解释了素材里那个自问自答：既然 read_seqretry 会比对序号，read_seqbegin 里的奇偶判断是不是多余？不多余。放读者进去再靠 retry 拦下，逻辑上没错，但读者会在写者还在改数据的时候进去读一遍，把写者刚写好的 cacheline 读成共享态，写者后续的写就要多一次 cache 一致性开销。在 read_seqbegin 拦住，代价是一次序号读，收益是写者少受干扰。素材对这点给的理由是 reader 进去读会给 writer 带来额外的开销（cache miss），判断成立。

还有一点是素材没说透的：序号是 32 位无符号数，溢出回绕。两个 reader 在回绕窗口里恰好看到相同序号的窗口存在，但需要中间隔了 2^32 次写者进入，实践里不会发生。这条只做记录，不展开。

写者侧的代价也要说清。write_seqlock 拿的是内嵌的自旋锁，所以写者之间互斥；但它不等读者，读者也不改任何写者要争的变量。这带来一个反直觉的结果：seqlock 的写者进入临界区的成本，跟临界区外面有没有一百个读者无关。读者的存在对写者完全透明。

代价转移到了读者那边。写者密集时读者会反复重试，极端情况下出现活锁：读者刚读完数据，写者进来把序号改成奇数，读者重来，又撞上。5.15 给这类场景留了出口，就是「读锁或乐观读」二选一的那组接口：

c
static inline void read_seqbegin_or_lock(seqlock_t *lock, int *seq)
{
    if (!(*seq & 1))    /* Even */
        *seq = read_seqbegin(lock);
    else                /* Odd */
        read_seqlock_excl(lock);
}

static inline int need_seqretry(seqlock_t *lock, int seq)
{
    return !(seq & 1) && read_seqretry(lock, seq);
}

static inline void done_seqretry(seqlock_t *lock, int seq)
{
    if (seq & 1)
        read_sequnlock_excl(lock);
}

用法是：第一次传一个偶数 seq 进去，走无锁路径；如果 need_seqretry 返回需要重试，把 seq 传回去再来一轮，这次因为 seq 是奇数，读者转成「持锁读者」——read_seqlock_excl 直接抢内嵌自旋锁，把写者挡在外面，读一次就成。done_seqretry 负责把锁放掉。

这套机制的本质是给读者一个逃生通道：重试一次失败就升级成加锁读者，用阻塞换确定性。素材分析的是 4.0，那时还没有这组接口，所以没提；5.15 里它在 seqlock.h 里，是解决读者饥饿的官方答案。

十、read_seqbegin / read_seqretry 的配对 #

读者侧两个函数，一进一出。

4.0 的 read_seqbegin：

c
static inline unsigned read_seqbegin(const seqlock_t *sl)
{
    unsigned ret;

repeat:
    ret = ACCESS_ONCE(sl->sequence);
    if (unlikely(ret & 1)) {
        cpu_relax();
        goto repeat;
    }

    smp_rmb();

    return ret;
}

ACCESS_ONCE 是必须的。它告诉编译器「这个变量会被别人改，不要缓存到寄存器，不要合并读」。少了它，编译器完全可以把 repeat 里的读提到循环外，读者就永远看不到写者动过序号。

smp_rmb() 的位置是关键：在序号快照之后、读数据之前。它保证读数据的访存不会被重排到读序号之前。少了它，CPU 会先把 jiffies_64 读进流水线，再读序号，于是「序号是偶数」这个结论对应的是一个已经过期的数据快照——屏障没配平的后果就是这个。

cpu_relax() 在 ARM64 上是一条 yield：

c
static inline void cpu_relax(void)
{
    asm volatile("yield" ::: "memory");
}

yield 告诉硬件「本核在等，别的线程要用就让出来」。跟 ARM32 的 barrier()（空实现）不是一回事，这属于架构差异，别混着背。

read_seqretry：

c
static inline unsigned read_seqretry(const seqlock_t *sl, unsigned start)
{
    smp_rmb();
    return unlikely(sl->sequence != start);
}

进去先 smp_rmb()，保证读数据的访存不会被重排到读序号之后；然后比对序号。相等说明整个读期间没有写者插入，这次读的结果可以交付；不相等就重来。

read_seqretry 的返回类型在 4.0 里写的是 unsigned，实际当布尔用。素材照抄了源码，保留原样。

到 5.15，两个函数都被拆成了多层宏，但屏障位置没变：

c
static inline unsigned read_seqbegin(const seqlock_t *sl)
{
    unsigned ret = read_seqcount_begin(&sl->seqcount);

    kcsan_atomic_next(0);
    kcsan_flat_atomic_begin();
    return ret;
}

static inline unsigned read_seqretry(const seqlock_t *sl, unsigned start)
{
    kcsan_flat_atomic_end();

    return read_seqcount_retry(&sl->seqcount, start);
}

往下追一层，read_seqcount_retry 最终落到：

c
static inline int do_read_seqcount_retry(const seqcount_t *s, unsigned start)
{
    smp_rmb();
    return unlikely(READ_ONCE(s->sequence) != start);
}

smp_rmb() 还是在比对之前，ACCESS_ONCE 换成了语义相同的 READ_ONCE。多出来的一堆 kcsan_* 是 KCSAN 数据竞争检测用的标注，不参与同步。

四个屏障的位置汇总成一张表，这是本篇最该记住的东西：

位置 屏障 防的是什么
write_seqlock：自增序号之后 smp_wmb() 防止临界区内的写被重排到序号自增之前
write_sequnlock：自增序号之前 smp_wmb() 防止序号自增被重排到临界区写完成之前
read_seqbegin：读序号之后 smp_rmb() 防止读数据被重排到读序号之前
read_seqretry：比对序号之前 smp_rmb() 防止读数据被重排到比对序号之后

四条屏障配成一个完整的传递链：写者的数据写在序号变化之前可见，读者的数据读在序号比对之前完成。

十一、seqlock 的适用条件：读者能重试、数据可重读 #

seqlock 不是通用锁，它挑场景。三个条件同时成立才有意义。

条件一：读远多于写。 读者重试的代价由写者频率决定。写者每秒改一万次，读者每次读都要撞上写者，重试几次是常态，读者侧的性能就塌了。seqlock 的收益全部来自「绝大多数时候序号不变」。

条件二：读者能重试。 读侧代码必须是个循环。如果读操作有副作用（改寄存器、发命令、写日志、申请内存），重试就会重复执行副作用。这类代码不能放进 seqlock 的读侧。

条件三：数据能整体重读。 读者拿到的必须是「完整的一份快照」。数据是定长标量、定长结构体、几个相关的标量，都行；数据是链表、树、动态数组指针，就有大麻烦（下一节展开）。

把条件摊成表：

数据形态 能上 seqlock 吗 卡在哪
u64、ktime_t、几个关联标量 能 无
定长结构体（如 struct timespec64） 能 结构体内不能有指针
链表 / 树 / 哈希桶 不能 写者会释放读者正要访问的节点
变长数组 不能 尺寸本身会变，读者会越界
带引用计数的对象 不能 取引用这一步本身就有竞态

内核文档对这条边界的措辞比我狠：这种机制在受保护数据含指针时不能用，因为写者会让读者正在跟随的指针失效。

还有一个容易漏的条件：写者之间必须串行，且写侧不能被打断。 seqcount 本身只做计数，不提供串行化。裸用 seqcount_t 时，写侧临界区必须是串行的、不可抢占的；如果读者会来自硬中断或软中断，写侧还要相应关中断或关下半部。seqlock_t 好一些，它内嵌了 spinlock_t，把写者串行化和关抢占这两件事包了。

这也是 seqcount_t 和 seqlock_t 的分界：

类型 写者串行化 关抢占 适用
seqcount_t 调用者自己负责 调用者自己负责 已经有别的锁在保护写侧
seqcount_spinlock_t 关联一把自旋锁，由 lockdep 校验 内建 写侧用自旋锁保护
seqlock_t 内嵌自旋锁 内建 独立使用，最省心

5.15 里 seqcount_LOCKNAME_t 这一族就是给「写侧已经有锁」的场景准备的，SEQCOUNT_LOCKNAME 宏一次性生成 seqcount_raw_spinlock_t、seqcount_spinlock_t、seqcount_rwlock_t、seqcount_mutex_t、seqcount_ww_mutex_t 五种。差别只在 __seqprop_*_preemptible() 的返回值：关联自旋锁的不可抢占，关联 mutex 的可以抢占。

十二、seqlock 不能保护什么：指针解引用 #

这是 seqlock 最容易踩的坑，素材里那个链表的例子值得原样复述再拆开。

假设被保护的是链表 header -> A -> B -> C -> null。读者在遍历，把 B 存进临时变量 x，这时候中断来了，读者被抢占——注意读者路径是没有关抢占的，这是 seqlock 的设计前提。其他 CPU 上的写者趁机把 B 摘下来并释放了它的内存。读者恢复执行，通过 x 访问 x->next 想找 C：踩已经还给分配器的内存。

要命的地方在于序号检查兜不住这个错。读者醒来后继续读完，最后 read_seqretry 确实会发现序号变了、返回 true、要求重试。但踩内存这个动作已经发生了，重试是事后补救，访问非法地址时程序已经崩了。

结论得说死：seqlock 只保证读者最终拿到一致的数据，不保证读者在重试期间访问的内存还没被释放。

同样的坑还有几种变体：

场景 后果 为什么序号检查救不了
写者释放链表节点 读者 use-after-free 序号检查在读完之后，踩内存在读之中
写者收缩数组 读者越界读 边界在读者读到时已经变了
写者把指针改成 NULL 读者空指针解引用 同上
读者取引用计数后再用 引用计数本身有竞态 取计数与对象销毁之间没有原子性

那这类场景用什么？RCU。RCU 的读者侧也有「不加锁、允许读到旧版本」的特征，区别是它保证被读对象的生命周期：写者不能立刻释放，得等所有读者退出读侧临界区（宽限期）。这一点是 seqlock 给不了的。

这条对比值得单独列一行，因为很多人把 seqlock 当轻量 RCU 用：

维度 seqlock RCU
读者开销 读序号 + 读数据 + 再读序号 关/开抢占（或标记静默态）
读者需要重试 需要 不需要，读到老版本也算对
数据一致性 保证单次快照一致 保证指针可用，不保证多字段一致
写者能否立即释放 无此概念 要等宽限期
指针结构 不能用 正是它的主场

一句话分界：要「一致的一份数据」用 seqlock，要「安全地遍历指针结构」用 RCU。

十三、三种锁的正面对比：spinlock / rwlock / seqlock #

把三把锁放在同一张表里，差异一眼可见。

维度 spinlock_t rwlock_t seqlock_t
临界区并发度 1 读者 N，写者 1 读者 N（无锁），写者 1
读者是否写共享变量 是（抢锁） 是（改计数） 否
写者是否等读者 是 是 否
读者是否等写者 是 是 只等序号变偶
读者会读到脏数据 不会 不会 会，靠重试
读侧最坏延迟 有界（一次持锁时长） 有界（一次持锁时长） 无界（写者密集时反复重试）
写侧最坏延迟 有界 无界（读者不断） 有界（一次持锁时长）
保护指针结构 能 能 不能
可睡眠临界区 不能 不能 不能
中断上下文可用 能 能 能
典型实现 ticket / qspinlock 位域 / qrwlock seqcount + 自旋锁

注意「读侧最坏延迟」和「写侧最坏延迟」两行是反着来的。选锁时先问自己哪一侧的延迟不能失控，答案就出来了。

再看一组数字上的直觉。假设 4 核、临界区 100 条指令、读者到达率很高：

锁 4 核全读的吞吐 有写者时的写者等待
spinlock_t 串行，约 1 核的量 平均等半个临界区
rwlock_t 接近 4 核 取决于读者，无上界
seqlock_t 接近 4 核，且无 cacheline 争抢 0

这张表只给方向，不给数字，具体倍数取决于 cacheline 争抢和 NUMA 拓扑，各家机器不一样。别拿这类数字当基准测试结论。

十四、怎么选：一张决策表 #

从上往下问，命中就停。

问题 答案 结论
1. 临界区会睡眠？ 是 换 rwsem 或 mutex，别用自旋锁
2. 读者会不会写共享状态以外的变量？ 是 别用 seqlock，用 rwlock_t
3. 受保护数据含指针 / 变长结构？ 是 别用 seqlock，用 rwlock_t 或 RCU
4. 读侧有副作用、不能重试？ 是 别用 seqlock，用 rwlock_t
5. 写者延迟必须可控（不能被读者拖住）？ 是 seqlock_t
6. 读者延迟必须可控（不能被写者拖住）？ 是 rwlock_t，或换成 RCU
7. 读写频率相当、临界区极短？ 是 普通 spinlock_t 就够，读写锁的额外原子操作不划算
8. 全是读，写几乎不发生？ 是 优先 RCU，其次 seqlock_t

配套的场景速查：

场景 选择 理由
文件系统类型链表 rwlock_t（历史代码） 遍历多、注册注销少，但是指针结构，不能用 seqlock
jiffies_64 读取 seqlock_t 定长标量，写者频率低，读侧能重试
时间戳、timespec 快照 seqlock_t 定长结构，无指针
网络协议栈的路由表 RCU 指针结构，读极多写极少
设备寄存器的并发访问 spinlock_t 临界区短，读写都少
需要写者不被饿死的读写场景 qrwlock / rwsem 老 rwlock_t 无公平性保障
配置表的整表替换 RCU 或 seqlock_t 看是否需要读到一致快照

最后补一条实践口径：新代码里，rwlock_t 的出现频率已经很低。要么读写都少用 spinlock_t，要么指针结构用 RCU，要么定长标量用 seqlock_t。真要用 rwlock_t，先想清楚读者和写者哪一侧的延迟不能炸。

十五、易错点速查 #

易错点 错在哪 正确做法
在读写锁的读临界区里调 kmalloc(GFP_KERNEL) 会睡眠，持锁睡眠拖死写者 把分配挪到锁外，或改用 rwsem
认为读锁是「只读所以安全」，在里头调 copy_to_user 缺页会睡眠 同上，读写自旋锁都不能睡
用 seqlock 保护链表 写者释放节点后读者踩空 换 RCU
读侧忘了 do-while，只调一次 read_seqbegin 读到一半被写者改了也不重试 必须配 read_seqretry 循环
读侧把 read_seqretry 写在数据使用之后 序号变了但数据已经用了 先验序号再用数据
用 sl->sequence 直接读写，绕过 API 漏掉屏障，漏掉写者串行化 只用 read_seqbegin/write_seqlock 这一套
写侧只加一次序号 读者分不清「写完了」和「写一半」 进出各加一次
在 read_seqbegin 里删掉 ACCESS_ONCE 编译器把读提到循环外，序号永远不变 保留 ACCESS_ONCE/READ_ONCE
在 read_seqretry 里删掉 smp_rmb() 数据读被重排到序号比对之后 保留屏障
在写侧漏掉 smp_wmb() 序号先变，数据后到，读者读到「新序号 + 旧数据」 两处 smp_wmb() 都要
拿 arch_read_can_lock 当同步手段 它只是读一眼状态字，有竞态 只用它做 trylock 前的预判
在 rwlock_t 上指望写者不被饿死 老实现里写者不占位 换 qrwlock 或 rwsem
把 cpu_relax() 当成跨架构一致的退让指令 ARM32 上是 barrier()，ARM64 上才是 yield 按架构理解，别背结论
读者计数溢出 超过 0x7FFFFFFF 个并发读者会把符号位翻负 实际达不到，但别在理论上假设无限
在持读锁期间调用会触发递归加锁的回调 写锁重入直接死锁 锁外回调，或改设计
