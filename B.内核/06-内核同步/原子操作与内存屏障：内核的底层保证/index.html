一、为什么需要原子操作：一条 C 语句不等于一条指令 #

你写的是一行自增，CPU 执行的是三条：

c
v->counter++;

armasm
ldr     r3, [r2]        @ ① 从内存读到寄存器
add     r3, r3, #1      @ ② 寄存器里加一
str     r3, [r2]        @ ③ 写回内存

三条指令中间，任何东西都可以插进来。这就是全部问题的起点。

多 CPU 上两个核同时跑这段代码，内存里 counter 初始是 5：两个核各自 ldr 拿到 5，各自算出 6，先后写回。两个核各加了一次，结果应该是 7，实际是 6——CPU0 的修改被 CPU1 覆盖了，这叫丢失更新（lost update）。

单 CPU 也一样出错，只是插进来的不是另一个 CPU，是中断。系统调用路径 ldr 拿到 5、算完还没写回，硬件触发中断，handler 把 counter 从 5 加到 6 写回，中断返回，系统调用路径把寄存器里那个陈旧的 6 写回——handler 的那次加一没了。

两件事说的是同一件事：读-改-写（read-modify-write，RMW）不是不可分割的操作。

两个概念要分开，很多混淆都来自没分开。单次访问的原子性指一次对齐的 load 或 store 会不会读到半个值：一个字长对齐的 int 访问，ARM、x86、PowerPC 都不撕裂，硬件保证；但 atomic64_t 在 32 位机器上跨两个字，那就不是单次访问了。复合操作的原子性指 read → modify → write 三步作为一个整体不被插入，这个硬件不白送，要么总线锁，要么独占监视器，要么关中断。内核要的是第二个。

二、原子操作的源由：lock bus 的代价 #

多个 CPU 和内存芯片挂在同一条总线上，任意时刻只能有一个总线 master 访问 RAM 这个 slave。两个 CPU 的读被总线仲裁串行化，各自拿到同样的旧值；两次写也被串行化，一前一后落盘。串行化解决不了丢失更新，因为问题不在「同时」，在「中间被插了」。硬件给了三条路：

手段 做法 代价 适用
关中断 raw_local_irq_save 包住 RMW 本核响应中断变慢；对其它核毫无作用 单核（UP）
总线锁 / lock 前缀 RMW 期间锁总线，别的 master 一律等 阻塞系统里所有总线主设备，几百周期起步 多核，粗粒度
独占监视器 ldrex/strex，只在提交时检查有没人插手 冲突时白干一次，循环重试 多核，细粒度

第三种是现代 ARM 的主流，第六节细讲。先说第二种的代价，因为它是「为什么不要滥用原子操作」的答案。x86 的 lock addl $1, (%rax)，lock 前缀会拉起锁。数据不跨 cacheline 时只锁那条 cacheline（靠 MESI 拉到 exclusive），不真拉总线；跨 cacheline 或访问不可缓存内存（UC）才退化成总线锁。这条细节未逐字核对 SDM，标在勘误。

代价落在同一处：其它核想访问同一条 cacheline 就得等。一条 cacheline 塞多个热点计数器，所有核排队。这推出两条编码习惯：每个 CPU 各自的自增计数器用 per-CPU 变量（this_cpu_inc），不要挤在一个 atomic_t 上；能读到快照就算数的场景用 READ_ONCE，省掉多余动作。还有一条：atomic_t 不是「更快的 int」，是「用原子指令换正确性」的 int，只在真需要 RMW 原子性时用。

三、内核原子操作 API：atomic_t 与 atomic64_t #

内核给原子变量一个专用类型，include/linux/types.h：

c
typedef struct {
    int counter;
} atomic_t;

就一个 int，包了一层 struct。这层不是为了对齐也不是填充，纯粹为了类型检查：拿普通 int * 去调 atomic_inc 编译不过，想混用就得显式强转；声明了 atomic_t 就没法写 v++、v += 2（struct 不能这么算），只能走接口；sparse 这类工具还能顺着类型把直接访问 v.counter 的地方挑出来。

ATOMIC_INIT 在 arch/arm/include/asm/atomic.h，用法 atomic_t canopen = ATOMIC_INIT(1);，定义是 #define ATOMIC_INIT(i) { (i) }。struct 是它必须是聚合类型的第二个理由：可以用初始化列表。

读写这两个最基础的（4.15 的写法）：

c
#define atomic_read(v)  READ_ONCE((v)->counter)
#define atomic_set(v,i) WRITE_ONCE(((v)->counter), (i))

这两行说明一件重要的事：atomic_read 和 atomic_set 不是原子 RMW，只是一次性访问。4.15 起它们直接就是 READ_ONCE/WRITE_ONCE，连指令都没多一条。真正需要独占的是 atomic_add 那一类。

atomic64_t 在旁边，包在 #ifndef CONFIG_GENERIC_ATOMIC64 里——架构没提供原生 64 位原子操作时退回通用实现（#include <asm-generic/atomic64.h>），定义是 typedef struct { long long counter; } atomic64_t;。ARM 的实现分两档，看有没有 LPAE（Large Physical Address Extension，大物理地址扩展，Cortex-A7/A15 起支持，提供 ldrd/strd 双字访问）：

配置 atomic64_read 实现 说明
CONFIG_ARM_LPAE=y ldrd %0, %H0, [%1] 单条双字 load，硬件原子
CONFIG_ARM_LPAE=n ldrexd %0, %H0, [%1] 独占双字 load，配 strexd

没有 LPAE 的 32 位 ARM 上 ldrd/strd 不保证原子，只能走 ldrexd/strexd。这就是 32 位机器上 atomic64_t 明显更贵的原因：每次操作都是一次带重试循环的独占序列。

atomic_inc / atomic_dec 在 4.15 就是宏，展开是那套 ldrex/strex：#define atomic_inc(v) atomic_add(1, v)。

atomic_add_return 和 atomic_fetch_add 是两套不同的东西，ARM 上是两个不同的汇编块（ATOMIC_OP_RETURN 与 ATOMIC_FETCH_OP）。前者返回 result（strex 之后的新值），后者返回 val（strex 之前的旧值）。用错不报错，逻辑错。

4、操作并测试 #

接口 语义 返回值
atomic_inc_and_test(v) v += 1 新值为 0 时真
atomic_dec_and_test(v) v -= 1 新值为 0 时真
atomic_sub_and_test(i, v) v -= i 新值为 0 时真
atomic_add_negative(i, v) v += i 新值小于 0 时真
atomic_add_unless(v, a, u) v 不等于 u 时 v += a 添加发生过时非零
atomic_inc_not_zero(v) v 非零时 v += 1 增加发生过时非零
atomic_dec_if_positive(v) v 大于 0 时减一 旧值减一，减没减都返回

4.15 ARM 上这一组是宏，返回值关系写得直白：

c
#define atomic_inc_and_test(v)  (atomic_add_return(1, v) == 0)
#define atomic_dec_and_test(v)  (atomic_sub_return(1, v) == 0)
#define atomic_sub_and_test(i, v) (atomic_sub_return(i, v) == 0)
#define atomic_add_negative(i,v) (atomic_add_return(i, v) < 0)

注意没有 atomic_add_and_test——只有减法和自增能测零，加法测零没意义。atomic_add_unless 的返回值有个坑，4.15 的 include/linux/atomic.h 这样收口：

c
static inline int atomic_add_unless(atomic_t *v, int a, int u)
{
    return __atomic_add_unless(v, a, u) != u;
}

底层 __atomic_add_unless 返回旧值，上层包装转成布尔。所以它返回非零的意思是「加了」，不是「值是多少」。

atomic_dec_and_test 是这组里用得最多的。它干一件并发代码里反复出现的事：减一，同时判断「我是不是最后一个」。减完是 0 说明我是最后一个持有者，可以释放；否则安静走人。引用计数、kref_put、文件描述符回收全在这个动作上。素材里那个字符设备例子是它的另一个用法——单开限制：

c
static atomic_t canopen = ATOMIC_INIT(1);

int hello_open(struct inode *p, struct file *f)
{
    if (!atomic_dec_and_test(&canopen)) {   /* 自减 1 并判断是否为 0 */
        atomic_inc(&canopen);              /* 恢复原始值 */
        return -EBUSY;
    }
    return 0;
}

int hello_close(struct inode *inode, struct file *file)
{
    atomic_inc(&canopen);
    return 0;
}

第一次打开：1 减到 0，返回真，取反为假，if 不成立，成功。第二次打开：0 减到 -1，返回假，取反为真，进分支，先把值加回去再返回错误。之所以能这样恢复，是因为「减到 -1」这个状态不会让别人误判成功——只有减到 0 的那个线程才拿到。这个模式只在计数值不会被减很深的场景成立，负得越多恢复越粗糙。

6、内存序变体 #

后缀 语义 例子
无后缀 全序（acquire + release 都占） atomic_add_return
_relaxed 不保证顺序，只保证原子 atomic_add_return_relaxed
_acquire 只对 load 部分给 acquire atomic_fetch_add_acquire
_release 只对 store 部分给 release atomic_fetch_add_release

include/linux/atomic.h 说明了构建方式：架构提供了 _relaxed 版本时，_acquire/_release/无后缀就在它外面套屏障：

c
#define __atomic_op_acquire(op, args...)                    \
({                                                          \
    typeof(op##_relaxed(args)) __ret = op##_relaxed(args);  \
    smp_mb__after_atomic();                                 \
    __ret;                                                  \
})

架构没提供 _relaxed 版本时全部别名到全序版本。这条规则的意思是：在弱的架构上用 _relaxed 能省钱，在强的架构上写 _relaxed 不亏，只是省不下来。atomic64_* 与 atomic_* 一一对应，参数换成 long long，初始化用 ATOMIC64_INIT(0)。

五、位操作：set_bit / test_and_set_bit #

整型原子操作管「一个计数器」，位操作管「一个 bit」：

接口 语义 返回值
set_bit(nr, addr) 第 nr 位置 1 —
clear_bit(nr, addr) 第 nr 位清 0 —
change_bit(nr, addr) 第 nr 位取反 —
test_bit(nr, addr) 读第 nr 位 该位值
test_and_set_bit(nr, addr) 置 1 并返回原值 原来的位值
test_and_clear_bit(nr, addr) 清 0 并返回原值 原来的位值
test_and_change_bit(nr, addr) 取反并返回原值 原来的位值
__set_bit / __clear_bit 非原子版本 —

addr 的实际类型是 volatile unsigned long *，nr 是 int。前六个原子，双下划线那批不原子。test_and_xxx_bit 等价于「先 test_bit 再 xxx_bit」，但两步是原子的，中间别人插不进来。test_bit 本身不加任何锁，因为它只是一次 load，没有 RMW。

原子性从哪来 #

arch/arm/include/asm/bitops.h 有两条路径。C 那条：

c
static inline int
____atomic_test_and_set_bit(unsigned int bit, volatile unsigned long *p)
{
    unsigned long flags, mask = BIT_MASK(bit);
    unsigned int res;

    p += BIT_WORD(bit);

    raw_local_irq_save(flags);
    res = *p;
    *p = res | mask;
    raw_local_irq_restore(flags);

    return (res & mask) != 0;
}

靠关中断。前提是单核：关掉本核中断，就没有别的执行流能插进来。多核可用的是汇编那条，_test_and_set_bit 用 ldrex/strex 实现，逻辑和 atomic_add 同构。两条路径怎么选看这个宏：

c
#ifndef CONFIG_SMP
#define ATOMIC_BITOP(name,nr,p)          \
    (__builtin_constant_p(nr) ? ____atomic_##name(nr, p) : _##name(nr,p))
#else
#define ATOMIC_BITOP(name,nr,p)     _##name(nr,p)
#endif

CONFIG_SMP=y 时一律走汇编版本，没有例外；CONFIG_SMP=n 且位号是编译期常量时走关中断的 C 版本，省一次函数调用；CONFIG_SMP=n 且位号是变量时走汇编版本。__builtin_constant_p(nr) 是 GCC 内建，编译期就能判断是不是常量，这是内核里「常量走快路径」的常见套路。

用在哪：bit lock（include/asm-generic/bitops/lock.h 的 bit_spin_lock() 就是 test_and_set_bit 循环，一个 bit 当一把锁，比 spinlock_t 省内存，代价是没调试信息、不能睡眠）；page flags（PG_locked、PG_dirty、PG_writeback，页是全局资源，必须在多核下原子）；cpu_online_mask（一个 cpumask，本质就是位数组）；等待队列标志（wait_queue_head_t 的 flags、工作队列的状态位）。

六、原子操作在 ARM 上的实现 #

以 atomic_add 为例。arch/arm/include/asm/atomic.h 里接口是被宏生成出来的：

c
#define ATOMIC_OPS(op, c_op, asm_op)                    \
    ATOMIC_OP(op, c_op, asm_op)                         \
    ATOMIC_OP_RETURN(op, c_op, asm_op)                  \
    ATOMIC_FETCH_OP(op, c_op, asm_op)

ATOMIC_OPS(add, +=, add)
ATOMIC_OPS(sub, -=, sub)

ATOMIC_OPS(add, +=, add) 一个实参展开出三个函数：atomic_add、atomic_add_return、atomic_fetch_add。c_op 是 C 运算符（只给无独占指令的老架构用），asm_op 是汇编助记符（add/sub/and/orr/eor/bic）。ATOMIC_OP 本体，ARMv6 及以上：

c
#define ATOMIC_OP(op, c_op, asm_op)                             \
static inline void atomic_##op(int i, atomic_t *v)              \
{                                                               \
    unsigned long tmp;                                          \
    int result;                                                 \
                                                                \
    prefetchw(&v->counter);                                     \
    __asm__ __volatile__("@ atomic_" #op "\n"                   \
"1: ldrex   %0, [%3]\n"                                         \
"   " #asm_op " %0, %0, %4\n"                                   \
"   strex   %1, %0, [%3]\n"                                     \
"   teq     %1, #0\n"                                           \
"   bne     1b"                                                 \
    : "=&r" (result), "=&r" (tmp), "+Qo" (v->counter)           \
    : "r" (&v->counter), "Ir" (i)                               \
    : "cc");                                                    \
}

ARMv6 以下（#else 分支）用关中断：raw_local_irq_save(flags); v->counter c_op i; raw_local_irq_restore(flags);。分支开关是 #if __LINUX_ARM_ARCH__ >= 6，老架构分支一开头就写着 #ifdef CONFIG_SMP / #error SMP not supported on pre-ARMv6 CPUs。意思明确：ARMv6 之前没有独占访问指令，原子性只能靠关中断，关中断只对单核成立，所以内核直接拒绝在老 ARM 上编译 SMP。

把宏展开成人能读的汇编 #

ATOMIC_OP(add, +=, add) 展开，%0→R0、%1→R1、%3→R3、%4→R4：

armasm
初始条件：
    R3 = &v->counter         @ 待操作变量地址
    R4 = i                   @ 待加的值
1:  ldrex   R0, [R3]         @ 独占读：R0 = v->counter，并在 [R3] 打独占标记
    add     R0, R0, R4       @ R0 = R0 + R4
    strex   R1, R0, [R3]     @ 独占写：成功则 [R3] = R0，R1 = 0
    teq     R1, #0           @ 测试 R1 是否等于 0
    bne     1b               @ 非 0（写失败）回到标号 1 重来
返回结果：
    result = R0              @ 新值，atomic_add_return 用它
    tmp    = R1              @ strex 的成败标记

ldrex / strex 做了什么 #

ldrex 是 ldr 加独占语义（LDREX <Rt>, [<Rn>]）。<Rn> 是基址寄存器，<Rt> 是目的寄存器。执行时硬件额外放两条「狗」盯着这个地址：local monitor（本核）和 global monitor（全局）。strex 是 str 加条件（STREX <Rd>, <Rt>, [<Rn>]），<Rd> 保存成败，0 成功、1 失败。能不能写取决于监视器状态——狗还盯着这个地址就允许写，写完清标记；标记已经没了就拒绝写，返回 1。

一次失败路径：

序号 进程 1 进程 2
1 ldrex R0, [R3] 置独占标记
2 add R0, R0, R4
3 ldrex R0, [R3] 置独占标记
4 add R0, R0, R4
5 strex 成功，写回，清标记
6 strex 标记已被清，失败
7 teq R1, #0 不等，R1=1 teq R1, #0 相等，R1=0
8 b 1b 重来 继续往下

进程 2 提交成功后清了标记，进程 1 的 strex 必然失败，回到标号 1 重读。整个 RMW 白做一次，这是乐观策略的代价：无冲突时只要四条指令，有冲突时退化成自旋。

exclusive 是 ARMv6 引入的，不是 ARMv7。素材写「是 ARMv7 提供的」不对，内核判断的边界就是 __LINUX_ARM_ARCH__ >= 6，记在勘误。监视器按地址标记而不按值，所以一次 ldrex 之后再 ldrex 别的地址，前一个标记会失效——写内联汇编时，ldrex 和 strex 之间不能插别的独占访问。

约束符逐个说 #

"=&r" 里 = 表示只写，& 是 earlyclobber。& 禁止 GCC 把输出和输入分到同一个寄存器：不加 & 时 GCC 倾向省寄存器让 %0 和 %3 共用，但 %0 在第一条 ldrex 就被写入，此时 %3 还要用，共用直接算错。"+Qo" 里 + 表示读写，Qo 是 ARM 约束，表示可用基址寄存器寻址的内存操作数。"r" 让 GCC 随便挑一个通用寄存器。

"Ir" 里 I 是 ARM 专用约束，要求能编码进 data-processing 指令的立即数——8 位数据配 4 位循环移位凑出的 32 位数。ARM 的 data-processing 指令 32 位里有 12 位表示立即数，8 位真数据、4 位循环量，所以「0~255 经 rotation 得到的数」合法，数值不合适时 GCC 先 mov 到寄存器。"cc" 告诉 GCC 这段改了条件码寄存器（teq 会改），别指望之前的标志位还在。__volatile__ 禁止编译器对这段内联汇编优化、移动、删除，没有它 GCC 可以认为一段「没有输出」的汇编没用直接扔掉。prefetchw(&v->counter) 是可选优化：strex 之前把目标内存预取到 cache，让独占访问更快命中，不是正确性的一部分。

七、从单条指令到多条指令：为什么还需要内存屏障 #

atomic_add 解决了「一条 RMW 不可分割」，不解决另一件事：两条独立访问之间谁先谁后。

c
data = 42;          /* 第一条 store */
ready = 1;          /* 第二条 store */

写代码的人想表达「数据准备好了才置标志」。读的一边 while (!ready) cpu_relax(); use(data);。三种情况下失效：编译器把两条 store 调换顺序（第八章）；CPU 把两条 store 投进不同顺序的 store buffer（第九章）；读的一边，ready 的读先于 data 的读完成（第九章的 invalidate queue）。

atomic_t 对这三种情况一个都不管。atomic_add 保证的是「这一个变量上的这一次 RMW 是独占的」，不保证这条 RMW 和别的访问之间的先后。所以原子操作不够。原子性是水平的（这一条操作不被切开），顺序性是垂直的（多条操作按我的顺序落地），两个维度要两套工具。这两件事在弱内存模型上不能互相替代。

再往下推：为什么 CPU 要乱序？因为它想快。一条 store 等不到 cacheline 所有权就卡住，流水线白等几十上百周期。硬件索性给 store 一个缓冲，先收下，回头再落地。这个缓冲一旦存在，store A; store B 落地成 B; A 就有了物理基础。所以屏障不是「修 bug 的补丁」，它是换性能的付款凭证：你容忍了乱序换吞吐，付出屏障换正确性。

八、编译器优化会做什么 #

编译器只认一件事：单线程语义。它不知道 lock->owner 会被另一个 CPU 改，也不知道某个地址背后是外设寄存器。

1、把循环里的 load 提到循环外 #

kernel/locking/mutex.c 的 __mutex_lock_common 里有这样一段（ACCESS_ONCE 时代，4.15 之前）：

c
for (;;) {
    struct task_struct *owner;

    owner = ACCESS_ONCE(lock->owner);
    if (owner && !mutex_spin_on_owner(lock, owner))
        goto slowpath;
    /* ... */
}

意图是让 mutex 的持锁者还在跑时自旋等一会儿，比直接睡眠便宜。循环里每轮都要重新读 lock->owner。如果写的是裸的 lock->owner，编译器看到的循环体是：读一个循环内没人写的变量，判空，调函数。它完全可以判定「这个读是循环不变量」，把它提到循环外，变成进循环前读一次、之后一直用那个值。对单线程这个变换完全正确，对这段代码是致命的：owner 被另一个 CPU 释放了，循环永远看不到，只能到超时——如果它退得出来的话。

2、把一次 load 拆成多次，或者合并 #

Linus 在邮件里举的例子：

c
if (a > MEMORY) {
    do1;
    do2;
    do3;
} else {
    do2;
}

GCC 可以把公共的 do2 提出来，变成 if (a > MEMORY) do1; do2; if (a > MEMORY) do3;。本身没问题，直到 do2 会改 MEMORY：原来只读一次，现在读两次，结果不一样，分支判断和 C 代码的语义就对不上。反方向也会发生：两次读同一个地址被合并成一次（CSE，公共子表达式消除），等标志位的场景里，等于把「反复看」变成「看一眼」。

3、把相邻的内存访问调换顺序 #

编译器为了减少指令数、改善流水线，会把独立的访问重排。它认为这两条互不相关，因为它们碰的不是同一个对象——共享内存里它们相关不相关，编译器无从知道。

4、对 volatile 的误解 #

volatile 能防住第 1、2 类（不许合并、不许消除、每次访问真的落到内存），但对第 3 类只管一半：GCC 保证 volatile 访问之间保序，但不保证 volatile 与其他访问之间保序。这就是后来内核把 ACCESS_ONCE（本质是 *(volatile T *)&x）换成 READ_ONCE/WRITE_ONCE、并在编译器层面加上依赖屏障的原因。__READ_ONCE 的定义见第十三章，结尾那句 smp_read_barrier_depends() 就是补的这一刀。

READ_ONCE 的作用范围比 ACCESS_ONCE 宽：明确承诺「编译器不许重排相邻的 READ_ONCE/WRITE_ONCE」，而且支持聚合类型，超过字长时退化成 memcpy。这些 ACCESS_ONCE 做不到。

九、CPU 与 cache 的一致性会做什么 #

只交代最必要的背景。MESI 的完整推导、store buffer 与 invalidate queue 的状态迁移、带时序图的四个场景，在 B 目录那篇《内存屏障与乱序》里，这里不复述。记住三个硬件部件，以及每个部件对应的乱序类型：

硬件部件 存在的原因 带来的乱序
cache（多核共享内存的副本） 缩短访存延迟 副本之间要同步，需要一致性协议
store buffer store 不必等 cacheline 所有权到手 StoreStore 重排、StoreLoad 提前可见
invalidate queue 收到 invalidate 不必立刻处理就能回 ack LoadLoad、LoadStore 读到过期副本

三个部件各自堵一个瓶颈，各自开一个乱序的口子，屏障指令就是封这些口子的。

组合 含义 谁造成
LoadLoad 两次读，后一个跑到前一个之前 invalidate queue
LoadStore 读之后的写跑到读之前 invalidate queue / 编译器
StoreStore 两次写，后一个跑到前一个之前 store buffer / 编译器
StoreLoad 写之后的读跑到写之前 store buffer + invalidate queue / 编译器

StoreLoad 最贵也最难：它要求「我写的所有人都看见了，我再去读」。这一条天然要求等对方 ack，x86 上靠 mfence 或带 lock 前缀的指令，ARM 上靠 dmb ish。

另一点必须交代：外设寄存器的内存映射。ARM 上外设寄存器映射到一段内存地址，编译器不知道那块地址背后是硬件：

c
do {
    status = readl(base + TX_STATUS);   /* 读 TX FIFO 状态寄存器 */
    barrier();
} while (status & TX_BUSY);

writel(data, base + TX_FIFO);           /* 写 TX FIFO 寄存器 */

没有 barrier()，编译器可以把 writel 提到循环前面——那就成了往没准备好的 FIFO 里灌数据。ARM 架构对 Device 和 Strongly-ordered 类型的内存访问本身保证 program order（A1 先于 A2，则 A1 先被观察到），所以这里 barrier() 足够，不需要 CPU 屏障。x86 的 IO 端口指令天然有序，同理。

mb() 与 smp_mb() 的分界线必须记清楚，写错就是性能事故：mb() 约束所有 CPU 和所有设备，用于和硬件对话——DMA 描述符、设备寄存器；smp_mb() 只约束其它 CPU，用于纯 CPU 之间的通信——内核数据结构、锁、标志位。UP（CONFIG_SMP=n）编译时 smp_mb() 全部退化成 barrier()，一条指令都不生成；mb() 不退化，因为即使单核，外设和 CPU 之间的可见性仍需处理。分界线的判据是「对面是谁」：对面是设备就是 mb()，对面是另一个 CPU 就是 smp_mb()。

十一、smp_mb / smp_rmb / smp_wmb 的语义与配对 #

Documentation/memory-barriers.txt 用「memory barrier」这个词，但它约束的不是「内存」，是访问的观察顺序。smp_mb() 保证：在它之前的所有 load 和 store，对于其它 CPU 而言，都先于它之后的所有 load 和 store 被观察到。

三个词要抠：「对它之前的/之后的」——屏障有两个方向，不是单向的；「其它 CPU」——不管本核自己看到的顺序，本核永远看到自己的写（store-to-load forwarding），别的核看到的才有乱序问题；「被观察到」——不是「执行完」，是「结果对别人可见」。smp_rmb() 弱一档，只管 load 对 load、load 对 store；smp_wmb() 只管 store 对 store。把「被观察到」读成「执行完」是最常见的理解偏差。

屏障必须成对使用才有意义。这不是形式要求：一半的屏障等于没有屏障。

一侧 另一侧 保证
smp_wmb()（写数据后） smp_rmb()（读标志后） 写侧数据先于标志可见；读侧读到标志后再读数据，读到新数据
smp_mb() smp_mb() 双向全序
smp_store_release() smp_load_acquire() 释放/获取配对，最推荐
smp_wmb() 依赖屏障 写侧写指针 + 初始化，读侧靠指针依赖保序
dma_wmb() dma_rmb() CPU 与 device 之间的描述符顺序

配错是最常见的错误。三个典型错法：写侧 smp_wmb() 读侧什么都不用（写侧保证数据先落地，读侧仍会先读到标志、后读到旧副本）；两侧都用 smp_wmb()（读侧要的是读屏障，wmb 管不了读的顺序）；smp_rmb() 配 smp_rmb()（两边都只管自己内部的读序，跨 CPU 的「数据先于标志」没人保证）。

发布-订阅是所有无锁通信的原型，模板背下来：

c
/* 写侧：发布 */
WRITE_ONCE(desc->data, value);
smp_wmb();                       /* 数据先落地 */
WRITE_ONCE(global_desc, desc);   /* 再发布指针 */

/* 读侧：订阅 */
p = READ_ONCE(global_desc);
smp_rmb();                       /* 读到指针之后，才去读它指向的东西 */
if (p)
    use(p->data);

写成 acquire/release 更省事，语义等价且不容易配错：

c
smp_store_release(&global_desc, desc);      /* 写侧 */
p = smp_load_acquire(&global_desc);         /* 读侧 */

好处是把「屏障 + 一次访问」打包成不可拆的表达式，你没法只写一半。老的 smp_mb() 风格里屏障和访问是两条独立语句，中间插进别的东西就错了。

为什么两边都要加，不是可以省一边的性能问题。屏障约束的是本核把访问投向内存的顺序。A 核把 data 写在 flag 前面投向内存，B 核才会先看到 flag 再看到 data；B 核自己也需要屏障，否则它内部的读会先取 data 后取 flag——即使外部内存的顺序是对的，B 核照样读到旧 data。两侧各管一半，缺一半就漏一半。

smp_mb__before_atomic / smp_mb__after_atomic 是给原子操作补顺序语义的。原子操作本身不带顺序语义，而某些架构上「全屏障」很贵，「相对于原子操作的屏障」可以便宜实现：

c
WRITE_ONCE(count, n);           /* 让前面的 store 先于这次 atomic_inc 可见 */
smp_mb__before_atomic();
atomic_inc(&refcnt);

命名要读准：__before_atomic 的语义是「屏障在原子操作之前，约束的是该原子操作之前的访问」，不是「约束该原子操作之前的原子访问」。

十二、barrier()：只约束编译器 #

2.6 时代直接在头文件里写死 #define barrier() __asm__ __volatile__("": : :"memory")。4.x 改成间接定义（include/linux/compiler.h）：

c
/* Optimization barrier */
#ifndef barrier
#define barrier() __memory_barrier()
#endif

__memory_barrier() 由 compiler-gcc.h 提供，GCC 下展开就是上面那条空汇编。

它一条机器指令都不生成（GCC 会把它优化掉，只留约束效果），但 "memory" 这个 clobber 项让 GCC 做三件事：不许把跨过这条语句的内存访问重排，它像一道栅栏把前后代码分成两段；不许假设寄存器里缓存的内存值仍然成立，GCC 必须重新从内存加载，因为它不知道这段汇编动了什么；不许把这条语句删掉，volatile 保证。

text
[前一段 C 代码]  ← 段内可以随意重排
=== barrier() ===        ← 跨越这条线不行
[后一段 C 代码]  ← 段内可以随意重排

barrier() 管不了段内的顺序，也管不了 CPU 的顺序，只在编译器这一层生效。

用法一：preempt_disable #

c
#define preempt_disable() \
do { \
    preempt_count_inc(); \
    barrier(); \
} while (0)

（2.6 / 3.x 的写法。4.14 起 preempt_count 变成 per-CPU 变量，实现改成 preempt_count_add(1) 一类的形式，barrier() 是否还在请对照你手上的版本，本文未逐版本核验。）

为什么要 barrier()：preempt_count_inc() 只是给当前 task 的 preempt_count 加一。如果 GCC 把临界区第一条指令提到这条加一之前，「先加计数再进临界区」的语义就破了——临界区代码在 preempt_count 还没加的时候就跑了，抢占保护形同虚设。

这个场景不需要 CPU 屏障，理由值得记：preempt_count 只被本核访问（task 调度到哪个核就由哪个核访问它的 preempt_count），不存在跨核通信。本核中断呢？硬件取中断时保证了「PC 之前的指令都执行完、之后的都没执行」，所以关中断/开中断与相邻指令之间不存在乱序，编译器屏障够了。

用法二：外设轮询 #

什么时候 barrier() 不够 #

只要涉及两个 CPU，barrier() 就不够。它只告诉 GCC 别动，没告诉 CPU 别动，CPU 该乱序还是乱序。

场景 需要什么
只防 GCC，不跨 CPU，不跨外设 barrier()
跨 CPU 通信 smp_mb() 系列 / smp_load_acquire 系列
跨 CPU 与设备 mb() 系列 / dma_rmb() 系列
只想让一次访问「真读一次/真写一次」 READ_ONCE / WRITE_ONCE

十三、READ_ONCE / WRITE_ONCE：现代内核的做法 #

READ_ONCE / WRITE_ONCE 在 4.15 前后引入，用来替代 ACCESS_ONCE。职责界定得很窄，只有两条：让这一次访问真的发生一次（不许合并、不许拆分、不许消除、不许用寄存器里的缓存值代替）；让相邻的 READ_ONCE/WRITE_ONCE 之间保持顺序（仅限编译器可判定的情况）。它们不提供任何 CPU 层面的顺序保证，需要 CPU 顺序时另配 smp_mb()，或直接用 smp_load_acquire / smp_store_release。

实现上，读走一条按尺寸特化的路径：1/2/4/8 字节各一条 volatile 访问，超过字长退化到 memcpy 两侧夹 barrier()（4.15 的 __READ_ONCE_SIZE）。

c
#define __READ_ONCE(x, check)                               \
({                                                          \
    union { typeof(x) __val; char __c[1]; } __u;            \
    if (check)                                              \
        __read_once_size(&(x), __u.__c, sizeof(x));         \
    else                                                    \
        __read_once_size_nocheck(&(x), __u.__c, sizeof(x)); \
    smp_read_barrier_depends(); /* 强制 x 的依赖顺序 */     \
    __u.__val;                                              \
})
#define READ_ONCE(x)    __READ_ONCE(x, 1)

#define WRITE_ONCE(x, val)                                  \
({                                                          \
    union { typeof(x) __val; char __c[1]; } __u =           \
        { .__val = (__force typeof(x)) (val) };             \
    __write_once_size(&(x), __u.__c, sizeof(x));            \
    __u.__val;                                              \
})

四个设计细节，每个都有出处。char __c[1] 在 union 里，把任意类型的读写降级成「按字节缓冲区操作」，绕开类型系统的别名分析——-fstrict-aliasing 会认为不同类型指针不指向同一块内存从而做出致命优化，用 union 的字节视图走 memcpy 语义规避掉。__force typeof(x) 里 __force 是 sparse 注解，意思是「我知道这里在做类型转换，别报警」。check 参数：READ_ONCE 传 1 走带 KASAN 检查的版本，READ_ONCE_NOCHECK 传 0 走 __read_once_size_nocheck，用于 KASAN 自己内部读栈的场合——一边检查一边被检查就死循环了。smp_read_barrier_depends() 在 4.15 的 __READ_ONCE 里是硬编码的，给「读指针然后解引用」的依赖链加保序，DEC Alpha 是唯一需要真指令的架构，别的架构上是空的。

回到第三章那两行：atomic_read(v) 展开就是 READ_ONCE((v)->counter)。所以它不是「原子读」，它就是「读一次，别优化」。这个认知能省掉很多乱加屏障的代码。

smp_load_acquire / smp_store_release 是 4.x 之后写无锁代码的首选。smp_load_acquire(p) 等于「READ_ONCE(*p) + 之后的访问不许提前」，smp_store_release(p, v) 等于「之前的访问不许拖后 + WRITE_ONCE(*p)」。ARM 上它们能用上 ldar/stlr 这种专用指令（ARMv8），或者在 ARMv7 上仍比全屏障省：

c
/* 不好：三步，容易漏 */
WRITE_ONCE(data, 1);
smp_wmb();
WRITE_ONCE(flag, 1);

/* 好：一步，成对 */
WRITE_ONCE(data, 1);
smp_store_release(&flag, 1);

十四、ACCESS_ONCE：它解决了什么，又为什么被取代 #

c
#define ACCESS_ONCE(x) (*(volatile typeof(x) *)&(x))

拆开：&(x) 取地址，(volatile typeof(x) *) 强转成 volatile 指针，* 解引用，效果是「对这一块内存做一次 volatile 访问」。volatile 在 GCC 下的含义是「每次访问都真的去内存取/写，不许优化掉，不许合并」，所以 ACCESS_ONCE(x) = 「读一次 x，就一次，别自作聪明」。

4.14 的 compiler.h 有个更绕的版本，为的是绕开 sparse 告警：

c
#define __ACCESS_ONCE(x) ({ \
     __maybe_unused typeof(x) __var = (__force typeof(x)) 0; \
    (volatile typeof(x) *)&(x); })
#define ACCESS_ONCE(x) (*__ACCESS_ONCE(x))

__var 声明了不用，纯粹让 sparse 记住 x 的类型。两个典型场景，一个防「多次读变一次读」，一个防「一次读变多次读」。第一个是轮询一个会被别人改的变量：owner = ACCESS_ONCE(lock->owner); 不加这个宏，GCC 会把读提到循环外（第八章），加了之后每轮都真的去读。第二个是第八章那个 if (a > MEMORY) 的例子：GCC 把 do2 提出来后 a > MEMORY 被求值两次，这两次之间如果 MEMORY 被别人改了，走的分支和 C 代码不一致，对 a 用 ACCESS_ONCE(a) 就能钉住，只读一次，读到的值之后随便用。

一句话：ACCESS_ONCE 让 C 代码能对编译器说「这个地址的访问，就是一次，不许合并、不许拆分、不许省略」。

为什么被取代 #

三个硬伤，全部跟 volatile 这个实现手段有关。

硬伤一：volatile 在这是「恰好管用」，不是「本来正确」。 volatile 的语义是为内存映射 IO 设计的，本意是「这个地址会被硬件改」。拿它约束编译器对普通内存的优化属于借用。内核文档里明确说过，volatile 能少用就少用，因为语义太强、管得太宽，反而妨碍优化。

硬伤二：不保序。 ACCESS_ONCE(a); ACCESS_ONCE(b); 这两句，GCC 有权调换顺序。volatile 的保序范围是「volatile 访问之间」和「volatile 访问与序列点之间」，编译器对两个独立 volatile 访问的交叉重排、以及对 volatile 与普通访问的重排，规则比大家以为的松。READ_ONCE/WRITE_ONCE 的注释把这条明确写下来：编译器不许重排相邻的实例。

硬伤三：只支持标量。 ACCESS_ONCE(struct_foo) 编译不过——__ACCESS_ONCE 里那句 typeof(x) __var = ... 0 的初始化就没法写。4.14 的注释老实承认：

text
 * ACCESS_ONCE will only work on scalar types. For union types, ACCESS_ONCE
 * on a union member will work as long as the size of the member matches the
 * size of the union and the size is smaller than word size.

READ_ONCE/WRITE_ONCE 用 union + memcpy 解决了这条，聚合类型直接能用。

一处遗留：lockless_dereference #

4.14 的 compiler.h 里还有一个：

c
#define lockless_dereference(p) \
({ \
    typeof(p) _________p1 = READ_ONCE(p); \
    typeof(*(p)) *__typecheck_p __maybe_unused; \
    smp_read_barrier_depends(); /* Dependency order vs. p above. */ \
    (_________p1); \
})

用途是「读一个指针，然后安全解引用，这个指针的生命周期不归 RCU 管（归引用计数或永生对象管）」。smp_read_barrier_depends() 保证「先读到指针，再去读指针指向的内容」不被 CPU 重排——否则你读到指针之后，CPU 先把 p->field 读了，才发现 p 是新的，读到的是旧的 field。这个宏在 5.x 被删，等价写法是 smp_load_acquire(p) 或 rcu_dereference。

十五、内存屏障在 ARM 中的实现 #

指令 全称 语义 类比
dmb Data Memory Barrier 保证之前的访问先于之后的被观察到，不等待完成 交警放行，不等到场
dsb Data Synchronization Barrier 保证之前的访问全部完成才继续 交警清场，等到场才放行
isb Instruction Synchronization Barrier 清空流水线，之后的指令重新取指 改页表/开 MMU 之后必须用

dmb 只保证顺序：屏障前的写还在 store buffer 里没落地，只要别人看到它的时间点晚于屏障后的写就行。dsb 保证完成：屏障前的写必须真的到了内存（对设备是到了设备）才执行后面的指令，切换页表、改 TTBR、进 WFI 之前要用它。isb 管取指，和内存顺序无关，处理的是「我改了指令流相关的东西，流水线里预取的旧指令得丢掉」。dsb 能替代 dmb（更强），反过来不行；isb 不能替代任何一个。三条指令里只有 dsb 等真正完成，dmb 只管顺序。

ARMv7+ 的映射（arch/arm/include/asm/barrier.h，4.19）带了个 option 参数，就是共享域（shareability domain）限定词：

c
#if __LINUX_ARM_ARCH__ >= 7
#define isb(option) __asm__ __volatile__ ("isb " #option : : : "memory")
#define dsb(option) __asm__ __volatile__ ("dsb " #option : : : "memory")
#define dmb(option) __asm__ __volatile__ ("dmb " #option : : : "memory")
option 含义
sy 全系统（默认，等于不带参数）
ish Inner Shareable，内部共享域（多核 cluster 内）
ishst 只对 store 生效的 ish
osh Outer Shareable，外部共享域
oshst 只对 store 生效的 osh
nsh Non-shareable

smp_mb() 用 dmb(ish)：只约束本 coherence domain 内所有核的可见性，没必要惊动外系统，这是性能上的精确取舍。ARMv6 没有这几条名前指令，得用 CP15 协处理器操作代替：

c
#elif defined(CONFIG_CPU_XSC3) || __LINUX_ARM_ARCH__ == 6
#define isb(x) __asm__ __volatile__ ("mcr p15, 0, %0, c7, c5, 4" \
                    : : "r" (0) : "memory")
#define dsb(x) __asm__ __volatile__ ("mcr p15, 0, %0, c7, c10, 4" \
                    : : "r" (0) : "memory")
#define dmb(x) __asm__ __volatile__ ("mcr p15, 0, %0, c7, c10, 5" \
                    : : "r" (0) : "memory")
语义 ARMv7+ 指令 ARMv6 CP15 操作 说明
指令同步 isb mcr p15, 0, r0, c7, c5, 4 c7 是 cache 操作寄存器，c5 子操作
数据同步 dsb mcr p15, 0, r0, c7, c10, 4 c10 是 cache 清理/屏障寄存器
数据内存屏障 dmb mcr p15, 0, r0, c7, c10, 5 操作码 5 是 DMB

更老的架构上还有坑：某些核（如 FA526）没有 DMB，dmb() 被定义成空的 __asm__ __volatile__("" ::: "memory")，只剩编译器屏障。这时 smp_mb() 在硬件层不存在，靠单核假设兜底。

mb() / smp_mb() 在 ARM 上的分派：

c
#ifdef CONFIG_ARM_HEAVY_MB
extern void (*soc_mb)(void);
extern void arm_heavy_mb(void);
#define __arm_heavy_mb(x...) do { dsb(x); arm_heavy_mb(); } while (0)
#else
#define __arm_heavy_mb(x...) dsb(x)
#endif

#if defined(CONFIG_ARM_DMA_MEM_BUFFERABLE) || defined(CONFIG_SMP)
#define mb()        __arm_heavy_mb()
#define rmb()       dsb()
#define wmb()       __arm_heavy_mb(st)
#define dma_rmb()   dmb(osh)
#define dma_wmb()   dmb(oshst)
#else
#define mb()        barrier()
#define rmb()       barrier()
#define wmb()       barrier()
#define dma_rmb()   barrier()
#define dma_wmb()   barrier()
#endif

#define __smp_mb()  dmb(ish)
#define __smp_rmb() __smp_mb()
#define __smp_wmb() dmb(ishst)

三个细节值得盯：mb() 用 dsb 而不是 dmb，因为它是给设备用的，要等真正完成，而 smp_mb() 用 dmb(ish)，因为 CPU 之间只需要顺序；rmb() 就是 dsb() 不带 option，老代码的痕迹，没按共享域细分；wmb() 用 __arm_heavy_mb(st)，需要时额外调 soc_mb()——有些 SoC 的 bus fabric 有自己的乱序行为，光靠 dsb(st) 不够，得让平台代码补一刀，这就是 CONFIG_ARM_HEAVY_MB 和 soc_mb 回调存在的理由。

四种架构的屏障指令对照：

语义 ARMv7 ARMv6 x86 PowerPC
mb() 全屏障 dsb mcr p15,0,r0,c7,c10,4 mfence sync
rmb() 读屏障 dsb 同上 lfence lwsync
wmb() 写屏障 dsb st 同上 sfence lwsync
smp_mb() dmb ish mcr p15,0,r0,c7,c10,5 lock; addl $0,0(%rsp) 或 mfence sync
smp_rmb() dmb ish 同上 空 lwsync
smp_wmb() dmb ishst 同上 空 lwsync
编译器屏障 barrier() barrier() barrier() barrier()

两个要点。x86 的 smp_rmb()/smp_wmb() 是空的——x86 的 TSO 模型保证 load-load、load-store、store-store 有序，只允许 store-load 重排，所以只需 smp_mb()，这也解释了为什么在 x86 上开发的无锁代码搬到 ARM 上会挂：你少写的屏障，编译器不报，CPU 不报，ARM 直接给错误结果。PowerPC 的 lwsync 便宜、sync 贵——lwsync 覆盖 load-load、load-store、store-store 但不覆盖 store-load，所以 smp_mb() 用 sync，其余用 lwsync。这张表最该记住的是 x86 那两格是空的。

ARM 两列有源码支撑（arch/arm/include/asm/barrier.h，3.10 与 4.19 对照）。x86 与 PowerPC 两列是通用知识，未逐一对照对应版本的原文，标在勘误。

十六、一个容易写错的例子：无锁标志位 #

场景：生产者往共享缓冲区写数据，写完置「就绪」标志；消费者看到标志就去读数据。不用锁，靠屏障。

c
/* 生产者 */
buf->len = n;
memcpy(buf->data, src, n);
ready = 1;

/* 消费者 */
while (!ready)
    cpu_relax();
consume(buf->len, buf->data);

错在四处：ready = 1 之前没有屏障，CPU 可以把 ready 的写提前到 memcpy 之前（九，StoreStore）；编译器可以把 ready = 1 提到 memcpy 之前（八，编译器重排）；while (!ready) 没有 READ_ONCE，读可以被提到循环外变成死循环（八）；循环退出后没有屏障，读到 ready 之后 buf->len 的读先完成（九，LoadLoad）。

c
/* 生产者 */
buf->len = n;
memcpy(buf->data, src, n);
smp_wmb();              /* 数据先于 flag 可见 */
WRITE_ONCE(ready, 1);

/* 消费者 */
while (!READ_ONCE(ready))
    cpu_relax();
smp_rmb();              /* 读到 flag 之后才读数据 */
consume(buf->len, buf->data);

WRITE_ONCE/READ_ONCE 解决编译器的合并与提升，smp_wmb()/smp_rmb() 解决 CPU 顺序，四处全覆盖，且配对正确（写侧 wmb，读侧 rmb）。换成 acquire/release 写法语义等价，少写两行，不会配错：

c
/* 生产者 */
buf->len = n;
memcpy(buf->data, src, n);
smp_store_release(&ready, 1);

/* 消费者 */
while (!smp_load_acquire(&ready))
    cpu_relax();
consume(buf->len, buf->data);

ARMv8 上 smp_store_release 直接编成 stlr，比 dmb + str 便宜。但这里还有一个坑：memcpy 本身不保证按顺序写，现代 GCC 把它展开成一串 SIMD store，这些 store 之间的顺序在弱内存模型架构上不保证。第三版为什么对：那几条 strd 之间的顺序由硬件保证（同地址序），最后一条和 stlr 之间由 stlr 的 release 语义保证。真正会挂的是把 smp_store_release 换成裸的 WRITE_ONCE(&ready, 1) 再补一个事后 smp_mb()——屏障放在标志写之后，等于没有。

高吞吐场景还有一层优化：消费者不想每次都读 ready，想批量，这就变成环形缓冲区，用 head/tail 两个索引而不是布尔标志。正确性由索引的单调性和配对屏障保证，Documentation/circular-buffers.txt 里有完整推导。

5、三条能背下来的判断 #

  1. 要一条 RMW 不被切开 → atomic_*。要两条访问有先后 → 屏障。
