一、信号量：计数型的同步原语 #

信号量本质就是一个计数器，用来记录某类资源的可用个数。取用资源走四步：读计数；计数为正就减 1 放行；计数为 0 就把当前任务挂进等待队列睡觉，等有人把计数加上去再重试；用完资源把计数加 1。

对计数的操作只有两种，Dijkstra 那套 PV 原语：

  • P(s)：s 大于 0 就减 1；s 等于 0 就把任务置为等待态，排进等待队列。
  • V(s)：有任务因 s 而挂起，就放一个出来跑；没有挂起者，就加 1。

P 对应内核里的 down()，V 对应 up()。名字来源是荷兰语的 proberen / verhogen，读代码时按「申请/释放」理解就行。

关键点在于 count 的初值。初值为 1，它就是二值信号量，等价于一把睡眠锁；初值为 N，它允许 N 个任务同时进入所谓的临界区。这一点把它和 mutex 从根上分开了：mutex 只允许一个持有者，而且带所有权；信号量不认持有者，谁都能 up()。

三套初始化方式，按场景挑：

c
/* 静态定义，count = 1 */
DEFINE_SEMAPHORE(sema);

/* 静态定义，自定义初值，展开后是 __SEMAPHORE_INITIALIZER(name, n) */
struct semaphore sema = __SEMAPHORE_INITIALIZER(sema, 4);

/* 动态定义后初始化，val 即 count 初值 */
struct semaphore sema;
sema_init(&sema, 4);

DEFINE_SEMAPHORE(name) 展开后 count 固定为 1。想要 count 不等于 1 的静态信号量，得手写 __SEMAPHORE_INITIALIZER，或者退回到动态分配 + sema_init。

接口一共五个，先把边界钉住：

接口 是否睡眠 返回值 可用上下文
down(sem) 会，TASK_UNINTERRUPTIBLE 无 进程上下文
down_interruptible(sem) 会，TASK_INTERRUPTIBLE 0 或 -EINTR 进程上下文
down_killable(sem) 会，TASK_KILLABLE 0 或 -EINTR 进程上下文
down_timeout(sem, jiffies) 会，带超时 0 或 -ETIME / -EINTR 进程上下文
down_trylock(sem) 不会 0 成功，非 0 失败 任意上下文
up(sem) 不会 无 任意上下文

down() 上游注释里明写了 deprecated，让改用 down_interruptible() 或 down_killable()。原因后面第五章讲。

二、semaphore 的数据结构 #

结构体在 include/linux/semaphore.h，头上那句注释是硬规矩：

c
/* Please don't access any members of this structure directly */
struct semaphore {
        raw_spinlock_t          lock;
        unsigned int            count;
        struct list_head        wait_list;
};

三个字段，各管一件事：

  • lock：保护 count 和 wait_list 的自旋锁，只在临界区里持有，时间极短。
  • count：剩余可用资源数，就是 PV 里的那个 s。
  • wait_list：等待队列头，睡着等资源的任务都挂在这条双向链表上。

wait_list 挂的是 list_head，内核通用的双向链表节点，next / prev 两个指针，这里不展开。

版本差异在这儿：更早的 2.6 系代码里是 atomic_t count; 加 spinlock_t lock;，计数用原子变量自己保证原子性，锁只保护链表。改成 raw_spinlock_t 之后，count 的读写也一并被锁保护，atomic_t 就多余了。具体切换版本未验证，能确定本篇引的这版是 2.6.33 之后的口径。

初始化宏把三个字段一次性摆平：

c
#define __SEMAPHORE_INITIALIZER(name, n)                                \
{                                                                       \
        .lock           = __RAW_SPIN_LOCK_UNLOCKED((name).lock),        \
        .count          = n,                                            \
        .wait_list      = LIST_HEAD_INIT((name).wait_list),             \
}

#define DEFINE_SEMAPHORE(name)  \
        struct semaphore name = __SEMAPHORE_INITIALIZER(name, 1)

static inline void sema_init(struct semaphore *sem, int val)
{
        static struct lock_class_key __key;
        *sem = (struct semaphore) __SEMAPHORE_INITIALIZER(*sem, val);
        lockdep_init_map(&sem->lock.dep_map, "semaphore->lock", &__key, 0);
}

sema_init 里那句 *sem = (struct semaphore) __SEMAPHORE_INITIALIZER(*sem, val) 值得停一下。宏里有两个 (name).lock、(name).wait_list，它们在这个复合字面量里会被求值，只不过外层是对 *sem 整体赋值，先算右值再落到左值，所以取到的还是旧值。编译器对这种写法不报错，但看起来很像自引用。实际靠的是「先求值后赋值」的顺序。

lockdep_init_map 是给 lockdep 打标签用的。每把锁一个独立的 lock_class_key，锁的依赖图才分得清哪个是哪个。跑生产内核时 lockdep 常常关掉，这段就是空操作。

等待者结构体在 kernel/locking/semaphore.c 里定义：

c
struct semaphore_waiter {
        struct list_head list;
        struct task_struct *task;
        bool up;
};

list 挂进 sem->wait_list；task 记下被唤醒的是谁；up 是交接旗标，__up() 把它置 true，睡眠方醒来看到 true 就知道「资源已经递到我手里了」。素材 3 那份教学版结构体只有 list 和 task 两个字段，少了 up，那是为了讲原理砍掉的，别照着抄。

bool up 这个字段承载的语义很重：它就是「直接交接」的实现手段。谁被唤醒，谁不用再去抢 count，__up() 已经替他把排队资格转成持有了。

三、down / up 的完整实现 #

down() 在 kernel/locking/semaphore.c，函数体短得不像话：

c
/**
 * down - acquire the semaphore
 * @sem: the semaphore to be acquired
 *
 * Use of this function is deprecated, please use down_interruptible() or
 * down_killable() instead.
 */
void down(struct semaphore *sem)
{
        unsigned long flags;

        raw_spin_lock_irqsave(&sem->lock, flags);
        if (likely(sem->count > 0))
                sem->count--;
        else
                __down(sem);
        raw_spin_unlock_irqrestore(&sem->lock, flags);
}

流程就三段。拿锁并关本地中断；likely(count > 0) 走快路径，直接减一；否则进 __down() 慢路径。快路径全程没有调度，只有一次关中断和一次开中断。

__down() 是一层薄壳，把参数摆好就交给通用实现：

c
static noinline void __sched __down(struct semaphore *sem)
{
        __down_common(sem, TASK_UNINTERRUPTIBLE, MAX_SCHEDULE_TIMEOUT);
}

真正的逻辑在 __down_common()，这是本篇最该读懂的一段：

c
static inline int __sched __down_common(struct semaphore *sem, long state,
                                                                long timeout)
{
        struct semaphore_waiter waiter;

        list_add_tail(&waiter.list, &sem->wait_list);
        waiter.task = current;
        waiter.up = false;

        for (;;) {
                if (signal_pending_state(state, current))
                        goto interrupted;
                if (unlikely(timeout <= 0))
                        goto timed_out;
                __set_current_state(state);
                raw_spin_unlock_irq(&sem->lock);
                timeout = schedule_timeout(timeout);
                raw_spin_lock_irq(&sem->lock);
                if (waiter.up)
                        return 0;
        }

 timed_out:
        list_del(&waiter.list);
        return -ETIME;

 interrupted:
        list_del(&waiter.list);
        return -EINTR;
}

这段是经典的「挂队 → 放锁 → 睡 → 醒来重取锁 → 检查旗标」循环。逐点拆：

  1. list_add_tail() 把 waiter 尾插进 wait_list。尾插意味着 FIFO，先等的先醒。
  2. waiter.task = current，把唤醒目标钉在自己身上。waiter 是栈上变量，在函数返回前一直可读，这是它能被 __up() 反向引用的前提。waiter.up = false 把旗标先放下。
  3. 进循环。signal_pending_state() 判「有信号且当前 state 允许被打断」，state 传 TASK_UNINTERRUPTIBLE 时恒为 false。timeout <= 0 判超时，down() 传的是 MAX_SCHEDULE_TIMEOUT，schedule_timeout() 把它当「不设上限」，这条分支对 down() 是死代码，对 down_timeout() 才活。
  4. __set_current_state(state) 改状态，然后**raw_spin_unlock_irq(&sem->lock) 必须在 schedule_timeout() 之前**。锁不放开，up() 永远进不去临界区，谁也叫不醒你。
  5. schedule_timeout(timeout) 交出 CPU，返回剩余 jiffies。回来第一件事是 raw_spin_lock_irq() 重新拿锁，因为接下来要动 wait_list、判旗标，必须在锁里。
  6. if (waiter.up) return 0; 拿到就返回，注意这里 count 没有减。没拿到就继续循环——被信号打醒、被无关唤醒、超时前被假醒，都会回到循环头重判。

第 4、5 步是这个循环的全部技术含量：锁在睡眠前后各放收一次，中间那段不能持锁。持锁睡觉是死锁的标准起手式。

第 6 步的「count 不减」容易被误读成漏了减一。不是。up() 的慢路径根本不加 count，它把排队资格直接交给第一个等待者，所以唤醒路径上 count 天然不需要变。快路径加、慢路径交接，两条路合计守恒。

-ETIME 和 -EINTR 两条错误分支都要 list_del(&waiter.list)。漏了这句，waiter 是栈变量，函数一返回，wait_list 上就挂着一个指向已释放栈帧的节点，后面 __up() 一 deref 就炸。这是信号量代码里最典型的 UAF 形态。

再看释放侧。up() 同样两段式：

c
/**
 * up - release the semaphore
 * @sem: the semaphore to release
 *
 * Release the semaphore.  Unlike mutexes, up() may be called from any
 * context and even by tasks which have never called down().
 */
void up(struct semaphore *sem)
{
        unsigned long flags;

        raw_spin_lock_irqsave(&sem->lock, flags);
        if (likely(list_empty(&sem->wait_list)))
                sem->count++;
        else
                __up(sem);
        raw_spin_unlock_irqrestore(&sem->lock, flags);
}

注释里那句 up() may be called from any context and even by tasks which have never called down() 是信号量和 mutex 的分水岭，第六章还会回来讲。

慢路径 __up()：

c
static noinline void __sched __up(struct semaphore *sem)
{
        struct semaphore_waiter *waiter = list_first_entry(&sem->wait_list,
                                                struct semaphore_waiter, list);
        list_del(&waiter->list);
        waiter->up = true;
        wake_up_process(waiter->task);
}

摘队头、从链表上摘掉、把 up 置 true、唤醒。顺序有讲究：先 list_del() 再置旗标再唤醒。被唤醒的任务重新拿到 sem->lock 时，wait_list 上已经看不到自己了，不会重复摘队。

wake_up_process() 只唤醒一个任务，不是广播。信号量一次 up() 只放一个等待者，靠的就是这一点。

四、信号量与 mutex 的区别：什么时候用哪个 #

两者代码长得像，语义差得远。逐项对比：

维度 semaphore mutex
计数 任意初值 N 二值，隐含 0/1
所有权 无，谁都能 up() 有，只有持锁者能解锁
解锁校验 不校验 owner 字段校验
释放上下文 任意上下文，含中断 只能进程上下文
申请上下文 只能可睡眠的进程上下文 只能可睡眠的进程上下文
快路径 count-- cmpxchg 抢 owner
优先级继承 不支持 支持（CONFIG_MUTEX_SPIN_ON_OWNER 下的乐观自旋另算）
典型用途 资源池计数、生产者消费者 保护一段临界区

选型没有中间地带，按这三条判：

  • 需要「同时最多 N 个」的语义，用信号量。典型是缓冲区空位数、并发 IO 配额。mutex 表达不了 N > 1。
  • 需要在中断上下文里释放，用信号量。up() 的注释明说可以来自任意上下文。中断里给 mutex 解锁是错的，mutex_unlock() 会校验 owner，中断上下文根本没有对应的 owner 概念。
  • 只是保护一段数据和代码，用 mutex。它能查出错用、能配合 lockdep 抓死锁、能在 CONFIG_DEBUG_MUTEXES 下把状态机翻出来。

还有一条实战结论：DEFINE_SEMAPHORE 初值 1 的那种用法，别写。它和 mutex 功能重叠，却丢掉了所有权校验和调试能力。上游把 down() 标 deprecated，方向也是把「二值」场景往 mutex 赶。

信号量在驱动里有个经典用法，open() 里做独占：

c
static DEFINE_SEMAPHORE(sema);

int hello_open(struct inode *p, struct file *f)
{
    if (down_trylock(&sema) > 0) {
        printk("device busy, hello_open failed\n");
        return -EBUSY;
    }
    printk("hello_open\n");
    return 0;
}

int hello_close(struct inode *inode, struct file *file)
{
    up(&sema);
    return 0;
}

down_trylock() 不睡，所以 open() 立刻就返回 -EBUSY，用户态拿到明确的「设备忙」。三个进程同时打开，一个成功、两个失败：

text
[root@zy:/]# ./main &
open success,PID=61
[root@zy:/]# ./main &
can't open!
[root@zy:/]# ./main &
device busy,hello_open failed
can't open!
[root@zy:/]#

这个模式有个坑：open() 里 down_trylock() 成功、后续初始化失败返回错误，release 不会被调用，信号量就漏了。要补 up()。写成 goto 错误路径收口，别在中间 return。

五、可中断的 down：down_interruptible 与 -ERESTARTSYS #

down_interruptible() 就是换个 state 参数再走一遍 __down_common()：

c
int down_interruptible(struct semaphore *sem)
{
        unsigned long flags;
        int result = 0;

        raw_spin_lock_irqsave(&sem->lock, flags);
        if (likely(sem->count > 0))
                sem->count--;
        else
                result = __down_common(sem, TASK_INTERRUPTIBLE, MAX_SCHEDULE_TIMEOUT);
        raw_spin_unlock_irqrestore(&sem->lock, flags);

        if (signal_pending(current))
                return -EINTR;

        return result;
}

差别全在 TASK_INTERRUPTIBLE。任务状态可中断，signal_pending_state() 在循环头就会命中，走 interrupted 分支，摘队、返回 -EINTR。

醒来的路径有两条，得在调用点区分：

  • __up() 唤醒：waiter.up == true，返回 0，拿到资源。
  • 信号唤醒：signal_pending_state() 为真，返回 -EINTR，没拿到资源。

问题出在 -EINTR 上。返回它不代表没拿到，也不代表拿到了，调用者只知道自己被打断了。所以调用点必须处理，而且不能吞掉：

c
if (down_interruptible(&sem))
        return -ERESTARTSYS;

-ERESTARTSYS 是给系统调用层的信号。用户态在 read() 里被 SIGINT 打断，内核返回 -ERESTARTSYS，信号处理函数跑完之后，restart_syscall 机制会把整个系统调用重做一遍。用户态看到的是「read() 慢一点，但没失败」，符合 read() 的 SA_RESTART 语义。如果你返回 -EINTR，用户态直接收到 EINTR，read() 失败了——对某些应用是灾难，SIGALRM 一响，数据读到一半的循环就断了。

所以，down_interruptible() 的返回值原样换成 -ERESTARTSYS 往上返，这是驱动里的正字法。中间绝不能 return 0 装作成功，也绝不能 return -EINTR 自己造错误码。

down_killable() 是同一套壳换成 TASK_KILLABLE。它只响应致命信号（SIGKILL），普通信号打不断。用在「必须睡完，但 kill -9 得能杀掉」的场景。

down_timeout() 多带一个超时参数：

c
int down_timeout(struct semaphore *sem, long jiffies);

超时返回 -ETIME，被信号打断返回 -EINTR，拿到返回 0。-ETIME 和 -EINTR 在 __down_common() 里是两条独立分支，对应两个不同的 errno，别混着判。

末尾那句 if (signal_pending(current)) return -EINTR; 是无条件判的，快路径也过这一关。所以「拿到 count 了但函数返回 -EINTR」在理论上存在，调用方按 errno 判断会误以为没拿到。这是上游的历史包袱，照实标在这里；写新代码时别依赖「返回 -EINTR 就一定没持锁」这个假设。

六、信号量能不能用在中斷上下文：为什么不能 #

不能。原因不是「内核规定」，是物理上做不到。

down() 走慢路径会进 __down_common()，里面必然执行 schedule_timeout()。schedule() 做的事是「从 runqueue 上摘掉当前任务，挑一个别的上来跑」。中断上下文里没有「当前任务」可摘——硬中断挂在被打断的进程栈上，current 还是那个进程，但中断不是它主动让出的，把它的状态改成 TASK_UNINTERRUPTIBLE 再切走，那个进程就凭空消失了，永远没人把它捡回来。

内核对这种事的反应是直接报错。schedule() 开头有 __schedule_bug() 检查，preempt count 非 0 或者 irqs_disabled 的时候打 backtrace 然后 BUG。所以第一层是：不可睡眠上下文里 schedule() 一调就死。第二层是 might_sleep()，down()、down_interruptible() 前面都挂着这个调试钩子，CONFIG_DEBUG_ATOMIC_SLEEP 一开，在中断里调它们会立刻打出「BUG: sleeping function called from invalid context」并附 preempt count 和 irq 状态。

四类上下文，结论一样：

上下文 能 down*() 吗 能 up() 吗 能 down_trylock() 吗
进程上下文（可睡眠） 能 能 能
软中断 / tasklet 不能 能 能
硬中断 不能 能 能
持有 spinlock 期间 不能 能 能

最后一行最容易踩。持有 spinlock 时 preempt 被禁，进 schedule() 同样是 BUG。所以「在锁里 down()」和「在中断里 down()」是同一类错误，代价却不一样：前者是设计失误，后者是物理不允许。

up() 在中断里完全合法，这也是信号量在驱动里的常见形态——中断服务程序 up()，进程上下文 down_interruptible() 等。整条链路不睡眠的只有上半部，睡眠的只有下半部：

c
/* 进程上下文：等数据 */
if (down_interruptible(&sem))
        return -ERESTARTSYS;

/* 中断上下文：数据到了，放行 */
static irqreturn_t my_isr(int irq, void *dev)
{
        up(&sem);
        return IRQ_HANDLED;
}

down_trylock() 是中断里唯一能用的申请接口，因为它不睡，拿不到就立刻返回非 0。代价是得自己处理失败——重试、丢包、还是退回软中断，看你。和 mutex 对比一下就清楚了：mutex 两头都堵死，中断里既不能 mutex_lock() 也不能 mutex_unlock()，因为解锁要校验 owner，而中断上下文没有 owner。spinlock 反过来，两头都能用在中断里，代价是忙等。信号量卡在中间：申请必须在进程上下文，释放随意。

七、completion：只等一个事件，不持有所有权 #

completion 不是锁。这句话得先说死，否则后面全乱。

锁解决的是「同一时刻谁能进这段代码」。completion 解决的是「这件事做完了没有，做完了叫一声」。它不保护任何数据，不表达任何资源数量，也没有「持有者」这个概念。

场景是这样：一个线程必须等某个内核活动走到某个点，或者等某个状态出现。用信号量也能实现——初值 0 的信号量，等的 down()，做的 up()。但那个写法有两个毛病：一是语义错位，down() 看上去像在「抢资源」，而这里根本没有资源；二是容易漏 up()，配对关系靠人记。

completion 把这两点都堵住了。它只暴露两个动作：等用 wait_for_completion() 及其变体，叫用 complete() 或 complete_all()。

叫的人不需要知道自己叫的是谁，等的人不需要知道自己等的是谁。没有配对义务，没有所有权校验，这就是上游注释里说的「无竞争的解决方案」。

一个能立刻看出来的差别：信号量的 up() 在没有等待者时把 count 加 1，那个 1 是「资源多了一个」，后来的 down() 可以立刻拿到。completion 的 complete() 在没有等待者时把 done 加 1，那个 1 是「事件已经发生过一次」，后来的 wait_for_completion() 立刻返回。前者是库存，后者是记账。

记账这个性质很关键。它让 completion 能表达「先发生、后等待」的时序——事件先到，等待者后到，等待者不该白等。信号量初值 0 也能凑出这个效果，但语义上要靠约定，读代码的人得自己脑补。

八、struct completion 与 wait_for_completion #

结构体在 include/linux/completion.h，两个字段：

c
/*
 * struct completion - structure used to maintain state for a "completion"
 *
 * Completions currently use a FIFO to queue threads that have to wait for
 * the "completion" event.
 */
struct completion {
        unsigned int done;
        wait_queue_head_t wait;
};

wait 是等待队列头，等着这个事件的任务排在这里，FIFO 顺序。done 是完成计数，complete() 加、wait_for_completion() 减。所以它内部就是一把等待队列，没有别的魔法。

两种定义方式等效。栈上定义用 DECLARE_COMPLETION_ONSTACK(name)，它给 lockdep 打标记，抓「栈上的 completion 被带出作用域」这种错误；函数内定义就该用它。

c
struct completion mycompletion;
init_completion(&mycompletion);          /* 方式一：先定义，再初始化 */

DECLARE_COMPLETION(mycompletion);        /* 方式二：定义即初始化 */

#define init_completion(x) __init_completion(x)

static inline void __init_completion(struct completion *x)
{
        x->done = 0;
        init_waitqueue_head(&x->wait);
}

done 清零，等待队列头初始化成空链表。就这两件事。

复用同一个 completion 之前必须 reinit_completion()。它不是可选的美化，是正确性要求：上一轮的 done 残值会让这一轮的 wait_for_completion() 直接返回，等的人以为事件到了，其实到的是上一轮的事件。它的实现就一句 x->done = 0;。三者的分工记成一句话：定义时清零用 init_completion，复用时清零用 reinit_completion，栈上用 DECLARE_COMPLETION_ONSTACK。

等待侧的核心在 kernel/sched/completion.c，是 do_wait_for_common()：

c
static inline long __sched
do_wait_for_common(struct completion *x,
                   long (*action)(long), long timeout, int state)
{
        if (!x->done) {
                DECLARE_WAITQUEUE(wait, current);

                __add_wait_queue_entry_tail_exclusive(&x->wait, &wait);
                do {
                        if (signal_pending_state(state, current)) {
                                timeout = -ERESTARTSYS;
                                break;
                        }
                        __set_current_state(state);
                        spin_unlock_irq(&x->wait.lock);
                        timeout = action(timeout);
                        spin_lock_irq(&x->wait.lock);
                } while (!x->done && timeout);
                __remove_wait_queue(&x->wait, &wait);
                if (!x->done)
                        return timeout;
        }
        if (x->done != UINT_MAX)
                x->done--;
        return timeout ?: 1;
}

骨架和信号量的 __down_common() 一模一样：挂队、放锁、睡、醒来重取锁、检查条件。差别在三处：

  1. 判据是 x->done，不是 count > 0。done 非 0 就算条件满足。
  2. 醒来后不做「交接」，直接 x->done-- 消费一次记账。UINT_MAX 是例外，见第九章。
  3. 等待队列项用的是 DECLARE_WAITQUEUE + __add_wait_queue_entry_tail_exclusive，独占唤醒。complete() 只叫一个，靠的就是 exclusive 标记。

__add_wait_queue_entry_tail_exclusive 里的 exclusive 意思是「这个等待项只接受一次唤醒」。__wake_up_locked() 带 nr_exclusive = 1 时，叫到第一个 exclusive 项就停。一堆任务等同一个 completion，complete() 只放一个，符合「一次 complete 对应一次 wait」。

action 是函数指针，指向 schedule_timeout()。超时就是这么插进来的——wait_for_completion_timeout() 传的 action 一样，只是 timeout 有值。返回值那句 return timeout ?: 1; 是 GNU 扩展的三目简写：timeout 非 0 返回剩余 jiffies，否则返回 1。

两个最常用的变体，都在这层壳上面：

c
void __sched wait_for_completion(struct completion *x)
{
        wait_for_common(x, MAX_SCHEDULE_TIMEOUT, TASK_UNINTERRUPTIBLE);
}

int __sched wait_for_completion_interruptible(struct completion *x)
{
        long t = wait_for_common(x, MAX_SCHEDULE_TIMEOUT, TASK_INTERRUPTIBLE);
        if (t == -ERESTARTSYS)
                return t;
        return 0;
}

wait_for_completion() 不可中断、无超时。上游注释写得很直白：It is NOT interruptible and there is no timeout. 一旦进去，只有 complete() 能救它，kill -9 都杀不掉。用在线程里要确认这条路径一定会有人叫醒，否则就是永久 D 状态。

wait_for_completion_interruptible() 返回 0 表示完成，返回 -ERESTARTSYS 表示被信号打断。它把 -ERESTARTSYS 直接透传，没有转成 -EINTR——理由和信号量那章一样，让系统调用层决定是重启还是返回错误。

API 全表：

接口 可中断 超时 返回
wait_for_completion(x) 否 无 无（void）
wait_for_completion_interruptible(x) 是 无 0 / -ERESTARTSYS
wait_for_completion_killable(x) 仅致命信号 无 0 / -ERESTARTSYS
wait_for_completion_timeout(x, t) 否 有 剩余 jiffies / 0
wait_for_completion_interruptible_timeout(x, t) 是 有 剩余 jiffies / 0 / -ERESTARTSYS
completion_done(x) — — 0 有等待者 / 1 无等待者

超时类接口的返回值要看清：返回 0 是超时（没等到），返回正数是「等到了，还剩这么多 jiffies」。所以判断写法是 if (!wait_for_completion_timeout(&c, HZ)) 表示超时，不是相反。

completion_done() 判「有没有人在等」：

c
bool completion_done(struct completion *x)
{
        unsigned long flags;

        if (!READ_ONCE(x->done))
                return false;

        /*
         * If ->done, we need to wait for complete() to release ->wait.lock
         * otherwise we can end up freeing the completion before complete()
         * is done referencing it.
         */
        spin_lock_irqsave(&x->wait.lock, flags);
        spin_unlock_irqrestore(&x->wait.lock, flags);
        return true;
}

返回值方向容易记反：0 表示有等待者（wait_for_completion() 正在进行），1 表示没人在等。函数名问的是「完成了吗」，返回真表示「完成已记账、没人还在等」。

中间那次空转的加解锁不是为了改数据，是为了同步。done 非 0 时，complete() 释放 wait.lock 之后才算真正收工；这里抢一次锁再放开，等于等它收工，否则调用者一 kfree() 掉 completion，complete() 还在用。所以 completion_done() 判完之后 free 的写法仍有竞态，别把它当「安全释放」的许可证，它的正经用途是「还剩多少活没干完」这种统计。

九、complete 与 complete_all #

complete() 负责叫醒一个：

c
void complete(struct completion *x)
{
        unsigned long flags;

        spin_lock_irqsave(&x->wait.lock, flags);

        if (x->done != UINT_MAX)
                x->done++;
        __wake_up_locked(&x->wait, TASK_NORMAL, 1);
        spin_unlock_irqrestore(&x->wait.lock, flags);
}

三步。done 加 1，加之前挡一下 UINT_MAX；__wake_up_locked() 唤醒，最后一个参数 1 是 nr_exclusive，表示「最多叫醒一个独占等待者」；放锁。done 加 1 发生在唤醒之前，这个顺序不能反。先记账再叫人，被叫醒的任务重取锁时能看到 done > 0，条件成立，消费掉。反过来先叫人再记账，醒来的人看到 done == 0，回去接着睡，这次唤醒就丢了。

__wake_up_locked 的 _locked 后缀表示「调用者已经持有 wait.lock」。等待队列那套 API 有无锁版本和持锁版本两套，用混了就是双锁或漏锁。

complete_all() 负责叫醒全部：

c
void complete_all(struct completion *x)
{
        unsigned long flags;

        spin_lock_irqsave(&x->wait.lock, flags);
        x->done = UINT_MAX;
        __wake_up_locked(&x->wait, TASK_NORMAL, 0);
        spin_unlock_irqrestore(&x->wait.lock, flags);
}

两处差别。done 被直接置成 UINT_MAX，不是加 1；nr_exclusive 传 0，表示「独占项也全叫」。

UINT_MAX 是这套机制里的「无穷大」。回看 do_wait_for_common() 里那句 if (x->done != UINT_MAX) x->done--;，饱和了就不再减。效果是：complete_all() 之后，不管是已经在等的、还是之后才来的，wait_for_completion() 都立刻返回，且 done 永远不减到 0。这个 completion 就永久变成「已触发」状态，只能靠 reinit_completion() 复位。

饱和语义换来一个明确后果：complete_all() 之后调 completion_done() 永远返回 1。注释里也写了：Note, this will always return true if complete_all() was called on @X. 因为 done 不为 0，而 completion_done() 第一句就是判 done。

选择规则很短：

语义 用哪个
一次事件对应一个等待者，逐个交付 complete()
广播：所有等待者同时放行 complete_all()
一次性 gate，开了就一直开着 complete_all() + 永不复位
反复使用的循环等待点 complete() + wait_for_completion() 配对

complete() 配 N 个等待者是最容易写错的组合。complete() 只放一个，N 个等待者就得有 N 次 complete()。写成一次 complete() 加 N 个 wait_for_completion()，剩下的 N-1 个会一直睡。这种 bug 在压测里才暴露，靠代码审查很难看出来。

十、completion 的典型场景：驱动 probe 等硬件就绪 #

最典型的形态是「A 路径等 B 路径把事办完」。驱动里到处是这种结构：probe 等硬件上电完成、read 等 DMA 搬运完成、ioctl 等固件加载完成。

举个能跑的最小例子。字符设备，两个 ioctl 命令：命令 0 等，命令 1 叫。

c
#include <linux/module.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/completion.h>

DECLARE_COMPLETION(mycompletion);

static long hello_ioctl(struct file *file, unsigned int cmd, unsigned long arg)
{
        switch (_IOC_NR(cmd)) {
        case 0:
                pr_info("i am waiting\n");
                wait_for_completion(&mycompletion);
                pr_info("haha, i get the message\n");
                break;
        case 1:
                pr_info("complete\n");
                complete(&mycompletion);
                break;
        default:
                pr_info("default\n");
        }
        return 0;
}

用户态两个线程，先起线程 A 发命令 0 阻塞住，sleep(2) 后起线程 B 发命令 1 放行。输出顺序就是时序证据：

text
write start
read start
write end
read end
main exit

write start 之后卡了两秒才出现 read start——那就是 wait_for_completion() 在睡。read start 一到，complete() 立刻把 A 放出来，于是 write end 出现。

这个例子故意用了不可中断版本，因为它把「没人叫就永久 D 状态」的风险摆在明面上。真实驱动里这条路径要加超时：

c
if (!wait_for_completion_timeout(&mycompletion, msecs_to_jiffies(500))) {
        dev_err(dev, "hardware not ready after 500ms\n");
        return -ETIMEDOUT;
}

probe 里的用法更常见。硬件上电、PLL 锁定、固件握手这类事必须等，但等的对象是中断，不是同一个执行流：

c
struct my_dev {
        struct completion hw_ready;
};

static irqreturn_t my_isr(int irq, void *data)
{
        struct my_dev *d = data;

        complete(&d->hw_ready);          /* 硬件就绪，记账 */
        return IRQ_HANDLED;
}

static int my_probe(struct platform_device *pdev)
{
        struct my_dev *d = devm_kzalloc(&pdev->dev, sizeof(*d), GFP_KERNEL);

        if (!d)
                return -ENOMEM;

        init_completion(&d->hw_ready);

        if (devm_request_irq(&pdev->dev, irq, my_isr, 0, "my", d))
                return -EINVAL;

        my_hw_start(d);                  /* 触发硬件，然后等它回话 */

        if (!wait_for_completion_timeout(&d->hw_ready, HZ))
                return -ETIMEDOUT;

        return 0;
}

三个要点。init_completion() 必须在 request_irq() 之前，否则中断先到、complete() 撞上一个没初始化的 wait.lock。等待必须带超时，硬件不回应的时候内核不能陪它一起挂。my_hw_start() 与 wait_for_completion_timeout() 的先后不能反，先起硬件再等回话。

completion 放在 struct my_dev 里而不是全局，是因为它和这个设备实例绑定。全局 completion 在多个设备实例时会串台——设备 A 的中断放行了等设备 B 的线程，这种 bug 极难查。

十一、completion 与信号量的关系 #

两者都是「睡在这里等人叫」，但语义层不同。摆一起看：

维度 semaphore completion
核心字段 count + wait_list done + wait
计数语义 可用资源个数 事件发生次数
有所有权 无 无
一次释放叫几个 1 个 complete() 叫 1 个，complete_all() 叫全部
计数上限 无 UINT_MAX 饱和
可重复使用 是 是，需配对消费或 reinit
典型对象 资源池 事件 / 时序屏障
用在中断里 只能 up() 只能 complete*()
主要接口 down*() / up() wait_for_completion*() / complete*()

一句话分界：问「还有几个」，用信号量；问「好了没有」，用 completion。

把初值 0 的信号量改写成 completion，是纯粹的语义升级，代码量还少一点：

c
/* 旧写法：初值 0 的信号量 */
static DEFINE_SEMAPHORE(done_sem);   /* 注意：DEFINE_SEMAPHORE 初值固定为 1，这里不适用 */

这条注释本身是个坑，值得展开。DEFINE_SEMAPHORE(name) 展开是 __SEMAPHORE_INITIALIZER(name, 1)，初值写死 1。想要初值 0 的静态信号量，得手写：

c
static struct semaphore done_sem = __SEMAPHORE_INITIALIZER(done_sem, 0);

或者退回动态分配加 sema_init(&done_sem, 0)。网上大量示例直接写 DEFINE_SEMAPHORE(done_sem) 当「初值 0 用」，那是错的，那个信号量一上来就能被 down() 拿到。

换成 completion 之后，这段就没有了：

c
static DECLARE_COMPLETION(done_evt);

/* 等的一方 */
wait_for_completion(&done_evt);

/* 叫的一方 */
complete(&done_evt);

不用管初值，不用管配对，不用解释「这个 0 是什么意思」。这就是 completion 存在的理由——它把「等事件」这件事从「抢资源」里摘出来了。

反过来也有一条：completion 不能替代 N > 1 的信号量。done 虽然也是计数，但它没有「取走一个资源就少一个」的库存语义，只有「事件发生过几次」的记账语义。资源池必须用信号量。

十二、Per-CPU 变量：为什么它可以不用锁 #

前面所有机制都在解决同一个问题：多个执行流抢同一份内存。spinlock 让它们排队，信号量让它们睡觉，completion 让它们等事件。Per-CPU 走的完全是另一条路：既然抢是因为共享，那就别共享。

给每个 CPU 一份私有副本，CPU 0 的 counter 和 CPU 1 的 counter 是两个不同的地址，物理上不相邻。CPU 0 改自己的那份，不需要问 CPU 1 的意见，也不需要任何原子指令。多个 CPU 之间的并发在数据层面被消掉了。

这里的分界线要划清：Per-CPU 消掉的是 CPU 之间的并发，不是同一个 CPU 上的并发。同一个 CPU 上被抢占，两个执行流还是会同时碰同一份副本。所以内核在访问 Per-CPU 变量时做的是 preempt_disable()。

素材里的说法很准：preempt disable 也是一种锁，只不过代价比较小。它不碰内存、不发总线事务、不睡眠，只把当前任务的 preempt_count 加 1。任务因此不会被调度到别的 CPU 上去。一旦被调度到别的 CPU，this_cpu_ptr 算出来的地址就变了，你摸到的就是别人家那份副本。这就是为什么 Per-CPU 的「锁」必须锁住的是「CPU 亲和性」，而不是内存。

十三、lock bus 带来的性能问题 #

Per-CPU 的存在理由，得从原子指令的成本说起。

ARMv6 之前，共享内存的原子访问靠 SWP / SWPB：

armasm
SWP <Rt>, <Rt2>, [<Rn>]

Rn 是要操作的内存地址。这条指令把 Rn 指向的内容读进 Rt，同时把 Rt2 的值写回 Rn。从程序员视角看它是原子的——读和写之间不会被任何异步事件打断。

硬件怎么做到的？执行期间给总线发一个 lock signal，告诉总线「这段内存访问不可被中断」，两次内存访问做完再 clear。

问题就在这儿。被 lock 的是总线，不是那块内存。

多核系统里，一个 CPU 锁总线的时候，其他所有 processor 对那条 memory bus 的访问全被 hold 住。哪怕它们访问的是完全无关的地址。这就是 lock bus 的成本：它把并行变成了串行，代价和「有多少个核在同时干活」成正比。

ARMv6 之后改用 LDREX / STREX，软硬件结合，独占监视器只盯一条 cache line，不再锁整条总线。看起来 Per-CPU 的存在基础被抽掉了。

但没抽干净。因为还有 cache。

十四、cache 行争抢：Per-CPU 要解决的第二个问题 #

假设多核系统的 cache 层次是这样：每个 CPU 有自己的 L1（含 data cache 和 instruction cache），所有 CPU 共享 L2，再往下是 main memory。L1/L2/内存的访问速度差距极大，最好的情况永远是 L1 hit。

再看共享内存的情况。CPU 0 改了共享变量，硬件必须把所有其他 CPU 的 L1 上对应的 cache line 置为 invalid，否则它们会读到脏数据。这不是可选的优化，是 cache 一致性的硬要求。

后果是：一个被频繁写的共享变量，会让所有 CPU 上那条 cache line 反复失效、反复回内存重载。变量本身只有 4 字节，被打扰的却是整条 cache line（典型 64 字节）。这叫伪共享（false sharing），比 lock bus 隐蔽，但同样吃性能。

换个角度就明白了：把共享内存变成 Per-CPU 内存，本质是拿内存换性能。一个变量变成 N 份，多占了 (N-1) × sizeof 的内存；换来的是每个 CPU 只碰自己那条 cache line，写操作不会让别人的 line 失效，全程没有总线事务。对现代 CPU 来说这笔交易很划算——内存几条 cache line 不值钱，cache line 来回失效值钱。

有一类变量天然适合这条路：计数器。vmstat 的每一项、网络栈的收发计数、调度器的统计量，全是「每个 CPU 各记各的，要总数的时候加起来」。这类变量没有任何跨 CPU 的因果依赖，是 Per-CPU 的典型用户。

十五、静态声明与访问的 API #

静态声明有一套家族，按「放哪个 section、怎么对齐、SMP 和 UP 怎么处理」分化：

宏 用途
DEFINE_PER_CPU(type, name) 最常用，普通 Per-CPU 变量
DEFINE_PER_CPU_FIRST(type, name) 放在 percpu section 最前面
DEFINE_PER_CPU_SHARED_ALIGNED(type, name) SMP 下按 cache line 对齐
DEFINE_PER_CPU_ALIGNED(type, name) 按 cache line 对齐（UP 也生效）
DEFINE_PER_CPU_PAGE_ALIGNED(type, name) 按 page 对齐
DEFINE_PER_CPU_READ_MOSTLY(type, name) 读多写少，可落独立副本策略

声明侧对应一套 DECLARE_PER_CPU*，只声明不定义，用于跨文件引用，比如 DECLARE_PER_CPU(int, my_counter);。

素材原文里这两张表在网页抓取时丢了，上表按 include/linux/percpu-defs.h 的宏名重建，宏名本身可靠；每个宏对应的 section 名和具体对齐字节数未逐条验证。

分化的四个维度就是素材列的那四条：变量在 section 中的位置、对齐方式、SMP 与 UP 的差异处理、访问形态。举两个用法：要求按 page 对齐，用 DEFINE_PER_CPU_PAGE_ALIGNED；只要求在 SMP 下对齐到 cache line，用 DEFINE_PER_CPU_SHARED_ALIGNED。后者名字里的 SHARED 指「SMP 共享对齐要求」，不是「共享变量」。

静态定义的变量不能当普通变量用。my_counter++ 编译得过，但改的是原始模板，不是任何 CPU 的副本。必须走访问接口：get_cpu_var(var) / put_cpu_var(var)，这两个已经内嵌了 preempt disable/enable，成对使用即可。如果当前环境已经是 preempt disabled（比如持有 spinlock、或者在中断处理里），用无锁版本 __get_cpu_var(var)，它不带 preempt 操作，因为假定调用者已经保证了 CPU 亲和性。

2.6.33 起多了一套 this_cpu_* 接口，这是访问 Per-CPU 变量最省的方式：

接口 作用
this_cpu_read(var) 读本 CPU 副本
this_cpu_write(var, val) 写本 CPU 副本
this_cpu_add(var, val) 加
this_cpu_sub(var, val) 减
this_cpu_inc(var) / this_cpu_dec(var) 自增 / 自减
this_cpu_ptr(ptr) 取本 CPU 副本的指针

this_cpu_* 的关键在于它把「取地址 + 访存」做成了一条指令。x86 上可以编译成带 %gs 段前缀的单条 add，ARM 上也能省掉一次地址计算。所以它是原子的（相对本 CPU 而言），不需要额外的 preempt 包裹。

this_cpu_* 是 2.6.33 引入的，版本点记牢。更早的代码里只有 get_cpu_var / __get_cpu_var 那一套。

十六、动态分配与访问的 API #

静态定义要求编译期知道变量。运行时才知道要多少份、或者要按 CPU 数量分配，走动态接口：

接口 作用
alloc_percpu(type) 分配 type 类型的 Per-CPU 变量，返回指针
alloc_percpu_gfp(type, gfp) 同上，指定分配标志
__alloc_percpu(size, align) 底层接口，指定大小和对齐
free_percpu(ptr) 释放
per_cpu_ptr(ptr, cpu) 取指定 CPU 的副本指针
this_cpu_ptr(ptr) 取本 CPU 的副本指针
get_cpu_ptr(ptr) / put_cpu_ptr(ptr) 带 preempt 保护的本 CPU 指针
per_cpu(var, cpu) 直接取指定 CPU 的副本值

alloc_percpu() 返回的是原始指针，不是任何 CPU 的副本地址。这是最常见的误解。想访问必须再过一层：

c
int __percpu *pc = alloc_percpu(int);
int *p;

if (!pc)
        return -ENOMEM;

p = per_cpu_ptr(pc, 2);          /* 取 CPU 2 的副本 */
*p = 42;

p = this_cpu_ptr(pc);            /* 取本 CPU 的副本 */
free_percpu(pc);

per_cpu_ptr(ptr, cpu) 的 cpu 参数是运行时 CPU 编号，可以来自 smp_processor_id()、get_cpu()，或者遍历 for_each_possible_cpu()。遍历求和是动态 Per-CPU 的典型用法，读的是别人的副本、没有加锁：

c
for_each_possible_cpu(cpu)
        total += *per_cpu_ptr(pc, cpu);

安全性靠的是「计数器只增不减、读到的稍微旧一点无所谓」。如果被统计的量会跨越有意义的边界，这种无锁求和就不成立。

十七、Per-CPU 的实现：段与偏移 #

以 DEFINE_PER_CPU 为例，一层层展开：

c
#define DEFINE_PER_CPU(type, name)                    \
        DEFINE_PER_CPU_SECTION(type, name, "")

#define DEFINE_PER_CPU_SECTION(type, name, sec)                \
        __PCPU_ATTRS(sec) PER_CPU_DEF_ATTRIBUTES            \
        __typeof__(type) name

#define __PCPU_ATTRS(sec)                        \
        __percpu __attribute__((section(PER_CPU_BASE_SECTION sec)))    \
        PER_CPU_ATTRIBUTES

#ifndef PER_CPU_BASE_SECTION
#ifdef CONFIG_SMP
#define PER_CPU_BASE_SECTION ".data..percpu"
#else
#define PER_CPU_BASE_SECTION ".data"
#endif
#endif

结果就是把变量塞进 .data..percpu 段。PER_CPU_DEF_ATTRIBUTES 由 arch 层定义，arch 不定义就为空（include/asm-generic/percpu.h）。

Per-CPU 的软件分三层。include/linux/percpu.h 是 arch-independent 接口，其他模块就 include 它；include/asm-generic/percpu.h 是 arch-general 层，各 arch 长得一样的东西抽出来放这，不直接 include，由上一层带进来；arch/arm/include/asm/percpu.h 是 arch-specific 层，ARM 平台的具体实现。

为什么要分这么多 section？普通变量编译链接后进 .data 或 .bss，初始化时一次搞定。Per-CPU 变量不行，它得先有一份「原始模板」，再给每个 CPU 复制一份。

原始模板落在 __per_cpu_start 和 __per_cpu_end 之间。链接脚本 vmlinux.lds.h 里 PERCPU_INPUT 决定排列：

c
#define PERCPU_INPUT(cacheline)                        \
        VMLINUX_SYMBOL(__per_cpu_start) = .;                \
        *(.data..percpu..first)                        \
        . = ALIGN(PAGE_SIZE);                        \
        *(.data..percpu..page_aligned)                    \
        . = ALIGN(cacheline);                        \
        *(.data..percpu..readmostly)                    \
        . = ALIGN(cacheline);                        \
        *(.data..percpu)                        \
        *(.data..percpu..shared_aligned)                \
        VMLINUX_SYMBOL(__per_cpu_end) = .;

对齐是这里的设计核心。first 段里有东西，后面就得按 PAGE_SIZE 对齐——防止 page_aligned 的变量被 first 段挤到非页边界的偏移上。readmostly 和 shared_aligned 前各插一次 ALIGN(cacheline)，目的是让它们从新 cache line 开始，不和其他变量共用一条 line。这也解释了为什么要有那么多 DEFINE_PER_CPU_* 变体：它们只是选择了不同的 section，而 section 决定了对齐和位置，对齐和位置决定了会不会和邻居抢 cache line。

有了模板，还得建副本。直接静态定义一个 NR_CPUS 长度的数组行不行？不行。NR_CPUS 是「系统支持的最大 processor 数」，不是「实际有几个」，为不存在的 CPU 分配内存是纯浪费。而且 NUMA 下要求更硬：每个 CPU 的副本得放在它访问最快的 memory 上，各 CPU 的副本会散布在整个地址空间、彼此之间有空洞。所以副本的分配归内存管理子系统管：为每个 CPU 分配一大块 memory，UMA 下就是普通内存，NUMA 下挑离该 CPU 最近的那块。

分配动作发生在 setup_per_cpu_areas()，把 __per_cpu_start 到 __per_cpu_end 那段模板按同样大小复制进每个 CPU 的 chunk。

副本和模板之间的地址关系是本篇第二个关键点：它是线性关系，差一个固定偏移。所以访问副本只要「模板地址 + 本 CPU 偏移」：

c
#define SHIFT_PERCPU_PTR(ptr, offset) ((void *)((unsigned long)(ptr) + (offset)))

#define __my_cpu_offset per_cpu_offset(raw_smp_processor_id())

#ifndef __per_cpu_offset
extern unsigned long __per_cpu_offset[NR_CPUS];
#define per_cpu_offset(x) (__per_cpu_offset[x])
#endif

#define this_cpu_ptr(ptr) __this_cpu_ptr(ptr)
/* ARM 平台没定义 __this_cpu_ptr，走 asm-generic 版本 */
#define __this_cpu_ptr(ptr) SHIFT_PERCPU_PTR(ptr, __my_cpu_offset)

#define get_cpu_var(var) (*({                \
        preempt_disable();                \
        &__get_cpu_var(var); }))
#define __get_cpu_var(var) (*this_cpu_ptr(&(var)))

__per_cpu_offset[] 是一张表，下标是 CPU 编号，值是该 CPU chunk 相对模板的偏移。raw_smp_processor_id() 拿到本 CPU 编号，查表，加偏移，得到副本地址。

ARMv6K 和 ARMv7 有专门的 TPIDRPRW 寄存器直接存这个偏移，省掉查表。arch 层如果定义了 __per_cpu_offset 宏，通用版的那张数组就不参与编译。

get_cpu_var 在最外层套 preempt。({ ... }) 是 GCC 的语句表达式扩展，整个块的值是最后一个表达式，所以 get_cpu_var(x) 展开成「关抢占，返回 x 在本 CPU 副本上的左值」。它能当左值用，也能当右值用。

十八、Per-CPU 的边界：什么时候还是得加锁 #

Per-CPU 只解决「不同 CPU 之间」。以下四种情况它管不了。

一、同一 CPU 上的并发。 抢占关了能挡住进程之间的切换，挡不住中断。中断服务程序插进 this_cpu_* 序列中间，摸的是同一份副本。这时候要额外 local_irq_disable()，或者用 local_lock。所以「Per-CPU 不用锁」严格说是「不用跨 CPU 的锁」。

二、要在 CPU 之间迁移数据。 生产者在本 CPU 上产生数据、消费者在另一个 CPU 上取走，这就是跨 CPU 的因果依赖，逃避不了同步。内核里的做法多是「Per-CPU 队列 + 一次真正的跨 CPU 通知」。

三、需要一个全局一致的值。 遍历所有副本求和时，读到的是「各 CPU 在各自时刻的值」，拼起来不一定对应任何一个真实时刻。要做精确快照，还是得加全局锁。

四、指针本身是共享的。 alloc_percpu() 返回的 pc 指针如果被多个 CPU 同时读写（比如重新分配），那个指针就需要保护。被保护的只是指针，不是它指向的 N 份副本。

一句话收口：Per-CPU 把「数据竞争」换成了「数据分布」，但没换来「无条件的并发安全」。它换掉的锁是 CPU 之间的那把，同一 CPU 内部的那把还在。

十九、四种同步机制的横向对比 #

四种机制摆一起。这一节只做对比，实现细节在同批另外三篇。

spin lock：两个计数 next 和 owner，申请时取号，next++ 后再比 owner；释放时 owner++。ARM64 上自旋用 WFE 让核进低功耗，释放用 SEV 广播。特点是不睡、忙等、临界区必须极短、可以在中断里用。用在「等的时间比调度开销还短」的场合。

信号量：一个 count 加一条 wait_list。count > 0 直接减一，否则挂队、schedule_timeout() 睡过去。up() 时若有人在等，直接把资源交接给队头。特点是可以睡、可计数、无所有权、申请只能在进程上下文。用在「资源池」和「等的时间远大于调度开销」的场合。

读写锁：一个 unsigned int，bit31 标记有没有写者，低 31 位统计读者数。读锁加计数，写锁置 bit31。特点是在读多写少时让读者并发进入。坑是写者会饿死——素材里的例子，A、B、C 在读者临界区里，D 等写锁，出去之前又来了 F、G，D 就一直等。

mutex：一个 owner 加一条 wait_list。没有 owner 就抢，有就挂队睡。释放时校验 owner 是当前进程。特点是有所有权、有优先级继承、有 lockdep 加持。用在「保护一段临界区」的绝大多数场合。

二十、怎么选：一张决策表 #

按顺序问自己，第一个「是」就是答案。

顺序 问题 答案
1 数据能按 CPU 切开，各 CPU 各管一份？ Per-CPU
2 只是等某个事件发生，不涉及资源数量？ completion
3 需要「同时最多 N 个」的语义？ 信号量
4 需要在中断上下文里申请？ spin lock
5 读多写少，且写者饿死可接受？ 读写锁
6 以上都不是，就是保护一段临界区？ mutex

补几条判据：

  • 能在中断里用吗：只有 spin lock 和 down_trylock() 能申请。mutex 两头都不行，信号量只有释放侧行。
  • 临界区有多长：比两次上下文切换短，用 spin lock；长了，用 mutex 或信号量。spin lock 在单核上退化成「关抢占」，多核上退化成「烧 CPU」。
  • 要不要睡眠：任何会跑在中断上下文的路径，一律不能睡。这一条比性能优先。
  • 有没有所有权语义：需要「谁锁谁解」的约束，用 mutex。不需要，且要跨上下文释放，用信号量。
  • 是不是纯计数：纯计数且能按 CPU 切，直接 Per-CPU。不能切（比如要精确全局值），退回去用原子变量或 spin lock 保护。

最后一条经验：能用 mutex 就用 mutex。它的调试支持最全，CONFIG_DEBUG_MUTEXES 能抓出「重复解锁」「非持有者解锁」「自己锁自己」。只有在它明确不行的场景（中断上下文、N > 1、跨上下文释放）才换别的。

二十一、易错点速查 #

信号量侧：

  • DEFINE_SEMAPHORE(name) 的 count 固定为 1。想要 0 或 N，手写 __SEMAPHORE_INITIALIZER 或 sema_init()。
  • down() 已 deprecated。新代码用 down_interruptible() 或 down_killable()。
  • down_interruptible() 返回非 0 时，返回 -ERESTARTSYS，不要吞掉，也不要自己转 -EINTR。
  • open() 里 down_trylock() 成功后走错误路径，必须补 up()，因为 release 不会被调用。
  • -ETIME 和 -EINTR 是两个不同的错误，别混判。
  • up() 可以来自任何上下文，包括中断；down() 不行。

completion 侧：

  • completion 不是锁，不保护数据，别拿它当互斥用。
  • 复用前必须 reinit_completion()，残留的 done 会让等待立刻返回假成功。
  • complete() 只叫一个。N 个等待者要 N 次 complete()，或者改用 complete_all()。
  • complete_all() 把 done 置成 UINT_MAX，之后永远饱和，只能靠 reinit_completion() 复位。
  • wait_for_completion() 不可中断、无超时。用在线程里必须确认一定有人叫。
  • 超时类接口返回 0 才是超时，返回正数是「等到了，还剩这么多 jiffies」。别写反。
  • completion_done() 返回 0 表示有等待者，1 表示没有。
  • init_completion() 必须在 request_irq() 之前，否则中断先到会撞未初始化的 wait.lock。
  • 函数内定义 completion 用 DECLARE_COMPLETION_ONSTACK。

Per-CPU 侧：

  • Per-CPU 变量不能直接当普通变量读写，必须走 this_cpu_* / get_cpu_var / per_cpu_ptr。
  • this_cpu_* 是 2.6.33 才有的，更早的内核只有 get_cpu_var 那一套。
  • alloc_percpu() 返回的是原始指针，不是任何 CPU 的副本地址。
  • per_cpu_ptr(ptr, cpu) 要传运行时 CPU 编号，传常量 0 就是只访问 CPU 0。
  • 已经 preempt disabled（持 spinlock、在中断里）时用 __get_cpu_var，别重复关抢占。
  • 关了抢占挡不住中断。中断也会摸同一份副本，必要时补 local_irq_disable()。
  • 遍历所有副本求和不是原子快照，读到的是各 CPU 各自时刻的值。
  • 对齐宏的选择影响 cache line 争抢。SHARED_ALIGNED 里的 SHARED 指对齐要求，不是共享变量。
