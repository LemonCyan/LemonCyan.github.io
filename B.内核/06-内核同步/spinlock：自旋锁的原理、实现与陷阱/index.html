一、自旋锁要解决什么问题 #

内核里最常见的麻烦是这样一屏：一块共享数据，进程上下文在读，中断上下文也在写。

进程上下文之间的互斥好办，semaphore、mutex 都能干，策略是「抢不到就睡，把 CPU 让出去，等人叫醒」。这套策略在中断上下文里直接失效——那儿没有 task 可以挂，没有 schedule() 可以调，睡下去没人唤醒你。于是需要一种「抢不到也不睡，原地重试」的锁。spinlock 就是这个东西。它的特点四条：

  1. 死等。冲突时不挂起当前执行流，而是不停重试，直到持锁者放手。
  2. 只允许一个执行流进入。semaphore 的计数可以大于 1，允许多个执行流同时进入；spinlock 永远只有一个赢家，其余在门口空转。
  3. 临界区必须短。空转是在烧 CPU，几行代码的临界区适合，几百行的循环不适合。ARM 提供了 wfe/sev 这类指令让空转的核进入低功耗等待，能把烧 CPU 的代价压下来，但压不到零。
  4. 能用在中断上下文。因为它不睡。

第 4 条是它存在的全部理由。你只要记住：spinlock 不是「更快的 mutex」，它是「唯一能在中断上下文里用的互斥」。

实现演进的三段 #

余华兵在《Linux内核深度解析》里把这段历史切成三段，我们照抄这个切法，因为它解释了为什么今天的锁长这样：

阶段 策略 问题
无序竞争 一个整数，0/1，CAS 抢 不公平，弱内存序硬件下有人饿死
入场券（ticket） owner / next 双字段排队叫号 所有人在同一个变量上自旋，缓存行反复失效
MCS（qspinlock） 每个 CPU 一个本地节点，在本地变量上自旋 结构变大，后来被压进 4 字节

第一段对应 2.6.23 的 ARM 实现，第二段对应 3.x 之后的 ARM/ARM64，第三段是 4.2 之后 x86 的默认实现。本篇主线走前两段，第三段只交代结论。

「自旋锁有三种实现」这句话的准确含义 #

网上流传一张表，说自旋锁有三种实现。它是从「锁最终编译成什么」这个角度看问题的：

场景 spin_lock() 实际做什么 有自旋吗
单核 + 非抢占（!CONFIG_SMP && !CONFIG_PREEMPT） 空操作 无
单核 + 抢占（!CONFIG_SMP && CONFIG_PREEMPT） 只 preempt_disable() 无
多核（CONFIG_SMP） preempt_disable() + 独占指令忙等 有

三行的差别不是配置差异，是语义差异。第一行连锁变量都不存在，第二行锁变量存在但永远抢得到，第三行才是真锁。后面第四、五、六章分别把这三行摊开。

二、自旋锁与睡眠：为什么它不能睡 #

一句话版本：持锁者睡下去，等锁的人就永远等不到释放。

展开成两条路径。

路径一，不同 CPU。CPU0 上的 A 持锁后睡了，CPU1 上的 B 在自旋。B 不会自己退出（spin_lock 没有超时），它就一直占着 CPU1 空转。等 A 被唤醒后释放锁，B 才能走。这条路只是浪费，不致命。

路径二，同一个 CPU。CPU0 上的 A 持锁后睡了，调度器把 C 换上来，C 也要这把锁。于是 C 在 CPU0 上自旋，而唯一能释放锁的 A 正躺在运行队列里等 CPU0。CPU0 被 C 占着不放，A 永远上不来，这一个 CPU 直接锁死。素材 5 把这个叫「第二种死锁」，描述得很准：

最坏的情况是，那个想获取锁的线程刚好和你的代码运行在同一个处理器上，这时它将一直持有 CPU 进行自旋操作，而你的代码永远得不到 CPU 去释放这个锁。

所以在临界区里，下面这些函数一个都不能碰：

text
copy_from_user() / copy_to_user()   缺页时睡眠
kmalloc(GFP_KERNEL)                 内存回收时睡眠
msleep() / schedule()               主动让出 CPU
mutex_lock()                        拿不到就睡
down()                              信号量，睡
阻塞式 I/O、等待完成量的 read/write

要分配内存就用 GFP_ATOMIC，要拷贝用户数据就挪到临界区外面先拷完。

spin_lock 本身会调 preempt_disable()，所以临界区期间本 CPU 的内核抢占是关的。这挡得住「被更高优先级进程抢走」，挡不住「自己主动调 schedule()」，也挡不住「被中断打断」。前者是你自己写错，后者是第十章要处理的事。

三、spinlock_t 的数据结构 #

spinlock_t 的定义在 include/linux/spinlock_types.h。它是三层套娃，一层比一层接近硬件：

c
typedef struct spinlock {
        struct raw_spinlock rlock;
} spinlock_t;

typedef struct raw_spinlock {
    arch_spinlock_t raw_lock;
} raw_spinlock_t;

3.x 之后实际的 spinlock_t 外面还套了一层 union，因为要放 lockdep 的 dep_map、owner 之类调试字段：

c
typedef struct spinlock {
        union {
                struct raw_spinlock rlock;
                /* debug 字段，CONFIG_DEBUG_* 打开时才有内容 */
        };
} spinlock_t;

arch_spinlock_t 由各架构自己定义，在 arch/*/include/asm/spinlock_types.h。

为什么要有 raw_spinlock 这一层 #

这不是为了好看，是被 PREEMPT_RT 逼出来的。旧内核（比如 2.6.23）命名很直白：通用层叫 spinlock_t，各架构定义自己的 struct raw_spinlock。实时分支（CONFIG_PREEMPT_RT）要求把 spinlock 分成两类：一类在实时内核里可以睡（底层换成带优先级继承的 mutex），一类在任何配置下都必须真自旋。于是定成三个名字：spinlock（配了 PREEMPT_RT 时可以被抢占，底层换成 mutex）、raw_spinlock（即便配了 PREEMPT_RT 也要顽强地自旋）、arch_spinlock（架构相关的实现，永远是最底层）。

主线内核没打 RT 补丁，spinlock 就是 raw_spinlock 的一层空壳，两者行为一致。为了将来兼容 RT，写代码守三条：优先用 spinlock；绝对不能睡、不能被抢占的地方用 raw_spinlock；临界区足够小的地方，raw_spinlock 更省。

UP 上的 arch_spinlock_t 是空结构体 #

include/linux/spinlock_types_up.h：

c
typedef struct { } arch_spinlock_t;

什么都没有，一切皆空。这跟第四章的分析对得上：单核非抢占下根本不需要锁变量。空结构体在 C 里占 1 字节（GCC 扩展），不占实际存储，关键是让 &lock->rlock.raw_lock 这类表达式还能编译通过。

ARM32：ticket 的双字段 #

arch/arm/include/asm/spinlock_types.h（3.x）：

c
typedef struct {
    union {
        u32 slock;
        struct __raw_tickets {
#ifdef __ARMEB__                        /* 大端，高字节在低地址 */
            u16 next;
            u16 owner;
#else                                   /* 小端，低字节在低地址 */
            u16 owner;
            u16 next;
#endif
        } tickets;
    };
} arch_spinlock_t;

owner 是当前叫到的号（服务号），next 是下一个要发的号（排队号）。整个锁就是一个 u32，owner 占低 16 位，next 占高 16 位。TICKET_SHIFT 定义为 16，所以 next++ 在数值上等于 slock += (1 << 16)。__ARMEB__ 那个分支不是装饰：字节序反了，u32 的低 16 位落到 next 上，next++ 会变成 owner++，锁直接失效。

ARM64：4.x 里干脆写成两个裸 u16 #

arch/arm64/include/asm/spinlock_types.h（4.x）：

c
typedef struct {
#ifdef __AARCH64EB__     /* 大端字节序（高位存放在低地址） */
     u16 next;
     u16 owner;
#else                    /* 小端字节序（低位存放在低地址） */
     u16 owner;
     u16 next;
#endif
} __aligned(4) arch_spinlock_t;

ARM64 版本去掉了 union。ARM32 需要 slock 这个 32 位视图，是因为它要用 ldrex/strex 一次性把整个 32 位读出来再写回；ARM64 用 ldaxr/stxr 处理 32 位、ldaxrh 处理 16 位 owner，不需要那个别名。__aligned(4) 保证 4 字节对齐，独占访问指令对非对齐地址会失败。

初始化链 #

spin_lock_init() 是一条四层宏链，逐层剥：

c
/* include/linux/spinlock.h */
#define spin_lock_init(_lock)                           \
do {                                                    \
        spinlock_check(_lock);                          \
        raw_spin_lock_init(&(_lock)->rlock);            \
} while (0)

/* include/linux/spinlock.h */
#define raw_spin_lock_init(lock)                               \
        do { *(lock) = __RAW_SPIN_LOCK_UNLOCKED(lock); } while (0)

/* include/linux/spinlock_types.h */
#define __RAW_SPIN_LOCK_INITIALIZER(lockname)   \
        {                                       \
        .raw_lock = __ARCH_SPIN_LOCK_UNLOCKED,  \
        SPIN_DEBUG_INIT(lockname)               \
        SPIN_DEP_MAP_INIT(lockname) }

#define __RAW_SPIN_LOCK_UNLOCKED(lockname)      \
        (raw_spinlock_t) __RAW_SPIN_LOCK_INITIALIZER(lockname)

/* arch/arm/include/asm/spinlock_types.h */
#define __ARCH_SPIN_LOCK_UNLOCKED       { { 0 } }

落点就是 slock = 0，也就是 owner = 0、next = 0。owner == next 表示空闲。静态定义用 DEFINE_SPINLOCK(x)，编译期就填好；运行时动态初始化用 spin_lock_init(x)，这类锁多嵌在 kmalloc 出来的结构体里。

顺带说说 2.6.23 长什么样 #

那一版 ARM 的 raw_spinlock_t（注意那时还没有 arch_spinlock_t）：

c
typedef struct {
    volatile unsigned int lock;
} raw_spinlock_t;

0 表示未锁，1 表示已锁。__raw_spin_lock 不断读这个值，等于 0 就用独占指令写 1，不等于 0 就继续读。__raw_spin_unlock 就是写 0。

能跑，无冲突时性能还不错，问题是不公平。所有 CPU 都在无序抢，谁手快谁得，不管等了多久。Nick Piggin 当年在提交信息里写过一段：> On an 8 core (2 socket) Opteron, spinlock unfairness is extremely noticable, with a userspace test having a difference of up to 2x runtime per thread, and some threads are starved or "unfairly" granted the lock up to 1 000 000 (!) times.

有线程被饿了一百万次。概率上无序竞争应该均匀，硬件把这事搞坏了：锁在内存里，每个 CPU 的 L1 都缓存了它；持锁者释放锁时执行 smp_mb()，其他自旋 CPU 的 cache line 全部失效，而刚释放锁那个 CPU 的 L1 里数据是热的，它下一次抢到锁的概率就高得多。越抢越热，越热越容易抢到。这就是第十二章 ticket spinlock 要解决的问题。

四、非抢占单核下的自旋锁 #

CONFIG_SMP 没开，CONFIG_PREEMPT 也没开。这种内核里，一个进程进了内核态只要不自己调 schedule()，就一路跑到返回用户态，中间不会被换下去，系统调用的执行完全串行。

推论很直接：共享数据只被进程上下文访问时，根本不需要保护。没有并发，谈何保护。所以这种配置下 spin_lock() 编译出来是空操作，arch_spinlock_t 是空结构体，锁变量连一个字节都不占。

但代码不能这么写 #

「不需要保护」和「你可以不写保护」是两件事。内核代码要跨配置编译，你在自己的单核板子上验证通过，代码挪到 SMP 配置上就散架。驱动里该写的 spin_lock 一个都不能省，它在 UP 上被编译器吃掉，在 SMP 上救你的命。

中断重入是另一码事 #

进程上下文之间没并发，不代表中断上下文和进程上下文之间没并发。中断可以在任何时刻打断内核代码，包括打断那块「反正不需要保护」的共享数据。素材 4 把这个场景追得很细，它问两个问题。

问题一：UP 下持有 spin_lock 的进程会被调度器切走吗？

不会。preempt_disable() 的自增让抢占计数非零，check_preempt_tick() 到点只会调 resched_task() 给当前进程打 TIF_NEED_RESCHED 标记，真正的切换发生在中断返回路径上，而那一步会看抢占计数。计数非零，切换不执行，所以临界区不会被进程上下文重入。

c
static void check_preempt_tick(struct cfs_rq *cfs_rq, struct sched_entity *curr)
{
	ideal_runtime = sched_slice(cfs_rq, curr);

	if (delta_exec > ideal_runtime) {
		/* 实际运行时间超过预期，打个需要重调度的标记 */
		resched_task(rq_of(cfs_rq)->curr);
		clear_buddies(cfs_rq, curr);
		return;
	}

	if (delta_exec < sysctl_sched_min_granularity)
			return;
	...
}

（原文此处写「真正的调度工作交给了中断返回时的 do_work_pending()」。do_work_pending 是 ARM 返回用户态时的收尾路径，处理信号和 TIF_NEED_RESCHED；内核抢占的入口是 preempt_schedule_irq()。方向对，函数名不准，见勘误。）

问题二：中断上下文会重入临界区吗？

会。A 进程拿到锁进临界区，中断来了，ISR 里也要这把锁。UP 上的 spin_lock() 不会失败，因为压根没有锁可以失败，ISR 直接穿过去跟 A 撞在一起，临界变量被改了一半，A 毫不知情。

UP 下的结论：spin_lock() 保护的临界区被 ISR 重入时，结果是数据错乱，不是死锁（没有自旋，没人卡住）。要挡住它只有关本地中断，也就是用 spin_lock_irq() 而不是光秃秃的 spin_lock()。

五、抢占式单核下的自旋锁 #

!CONFIG_SMP，但 CONFIG_PREEMPT 开了。这时一个在内核态跑的进程，会在中断返回时被更高优先级的进程顶掉。

素材 3 把抢占点列得很清楚。抢占式内核里，内核态进程会在四种情况下被切换：运行完成返回用户空间；主动让出 CPU（调 schedule() 或阻塞在某个等待上）；中断处理程序执行完、返回内核空间之前（此时抢占计数要为 0）；内核代码重新变得可抢占的时候，比如解锁、使能软中断。第 3、4 条是抢占内核多出来的，非抢占内核只有 1、2 两条。

这里锁退化成什么 #

raw_spin_lock() 展开到 _raw_spin_lock()，再到 UP 版本的 __LOCK()：

c
/* include/linux/spinlock_api_up.h */
#define _raw_spin_lock(lock)            __LOCK(lock)

#define __LOCK(lock) \
    do { preempt_disable(); ___LOCK(lock); } while (0)

#define ___LOCK(lock) \
  do { __acquire(lock); (void)(lock); } while (0)

#define preempt_disable() \
do { \
         preempt_count_inc(); \
         barrier(); \
  } while (0)

___LOCK() 是空的（__acquire 是 sparse 静态检查用的标注，(void)(lock) 只是压掉「参数未使用」的警告）。真正干活的只有 preempt_disable()。

也就是说，抢占式单核上，spin_lock() 等价于「禁止内核抢占」，没有自旋。锁变量存在，但永远不会被争用，arch_spin_lock() 在 UP 上压根不会被调用。

barrier() 不能省。它挡住编译器把临界区里的访存重排到 preempt_count_inc() 之前，也挡住把锁外的访存挪进临界区。

那个「永久 spin」的场景 #

素材 1 用这个例子说明为什么要禁抢占：进程 A 在系统调用里访问共享资源 R；A 访问到一半中断来了，中断唤醒了沉睡的、优先级更高的 B；中断返回现场时发生进程切换，B 跑起来也要访问 R；B 去拿 spin_lock，锁在 A 手里，B 自旋。如果 A 和 B 在不同 CPU 上，这没问题：A 会继续跑并释放锁，B 转两圈就拿到了。但在单核上，A 被 B 顶掉了，A 跑不了，锁放不掉，B 永远自旋——CPU 卡死。

preempt_disable() 就是切断第 3 步的：A 持锁期间抢占计数非零，中断返回时切不了人，B 只能等 A 出临界区。所以「永久 spin」在本 CPU 上被排除了。

还有一个残留的口子 #

preempt_disable() 只关抢占，不关中断，中断照常进来。如果中断处理程序也要这把锁，第四章分析过：UP 下没有自旋，ISR 直接穿墙，数据错乱。所以「中断会不会碰这块数据」这个问题必须由你自己回答，答案是「会」就得升到 spin_lock_irq()。关抢占只是挡「进程偷进程」，挡不了「中断偷进程」。

六、多核下的自旋锁 #

CONFIG_SMP 开了，这时才有真正的自旋。

持锁的那条路径执行 preempt_disable() 之后，共享数据只剩被别的 CPU 碰这一条路。所以要两件事：preempt_disable() 挡住本 CPU 上的进程抢占自己，独占指令（ARM 上是 ldrex/strex）挡住别的 CPU 同时改锁变量。

第二件事只能用硬件指令做。普通 ldr + cmp + str 会在中间被打断，两个 CPU 同时看到「锁是空的」，同时写 1，双双进入临界区。

把第四、五、六章压成一张表：

spin_lock() 展开 空操作 preempt_disable() preempt_disable() + 自旋

最后一列那句「本 CPU 死锁」是素材 4 追出来的。推理是：SMP 上 ISR 拿不到锁会调 wfe 进入低功耗等待，等的是「持锁者释放锁」这个事件。可持锁者就是被这个中断打断的那条路径，它跑不了，锁放不掉，事件等不到，CPU 卡死在 wfe 上。换个 CPU 执行 ISR 就没事，那个 CPU 等一会儿能等到。

素材 5 的三种死锁，逐条核对 #

第一种：跨 CPU 的持锁休眠。 A 在 CPU-A 上持锁进临界区，B 在 CPU-B 上自旋。A 那边程序阻塞（睡眠）了，CPU-A 切换跑 C，C 也要这把锁，也在 CPU-A 上自旋。于是 A 和 C 死锁：C 占着 A 需要的 CPU，A 占着 C 需要的锁。这是真的，它再次印证第二章那条：持锁期间不能睡。

第二种：同 CPU 的持锁睡眠。 第二章那条路径二，原理一样，不重复。

第三种：同 CPU 的中断重入。 进程 A 调 spin_lock(&lock) 进临界区，中断来了，ISR 里也 spin_lock(&lock)。同一个 CPU，锁在 A 手里，SMP 上 ISR 自旋，A 跑不了，锁放不掉，死锁。反过来，这个中断跑在别的 CPU 上就不死：那个 CPU 自旋一会儿，A 退出临界区放锁，中断拿到锁。

素材 5 这个段落有个说法要改：它写「由于是在同一个 CPU 上被中断，进程 A 会被设置为 TASK_INTERRUPT 状态……由于进程 A 被设置为中断状态，schedule() 进程调度就无法再调度进程 A 运行」。

内核不会因为「被中断」就把 A 设成 TASK_INTERRUPTIBLE（那是进程主动调 set_current_state() 才进的睡眠态）。真因是：A 被本 CPU 的硬中断打断，中断上下文在当前 CPU 上自旋，A 所在的执行流根本没有机会继续跑，所以锁永远不释放。结论对，机制写错了，见勘误。

那现代 CPU 有自旋超时吗 #

素材 5 最后一句写「现代处理器在处理自旋锁时都会设定自旋上限时间以防死锁」。这句是错的，得改。

Linux 的 spinlock 没有自旋超时，没有退避上限，也没有「超时后放弃」。arch_spin_lock() 里的循环是无界的，持锁者不释放，等锁者就一直等。防止「永远等不到」靠的不是锁本身，是外部检测：NMI watchdog、hung_task 检测、CONFIG_DEBUG_SPINLOCK 的持有者记录。它们的作用是「卡住之后报出来」，不是「卡住之后自动解开」。

这一点决定了设计取向：spinlock 的正确性完全依赖你不在临界区里睡、不在持锁时被中断抢走。锁不会救你，它只会把你拖死。

七、spin_lock 的完整实现路径 #

从 API 到汇编隔了六层。每层解决一个独立问题：通用接口、RT 兼容、调试检查、统计、架构抽象。

一路剥下去 #

text
spin_lock(lock)
  └─ raw_spin_lock(&lock->rlock)
       └─ _raw_spin_lock(lock)
            ├─ [UP]   __LOCK(lock)  →  preempt_disable()
            └─ [SMP]  __raw_spin_lock(lock)
                        ├─ preempt_disable()
                        ├─ spin_acquire(&lock->dep_map, 0, 0, _RET_IP_)
                        └─ LOCK_CONTENDED(lock, do_raw_spin_trylock, do_raw_spin_lock)

最上面两层是薄壳，早期 spin_lock 还带 __always_inline，后来为了 lockdep 记录调用点改成普通 static inline：

c
static inline void spin_lock(spinlock_t *lock)
{
    raw_spin_lock(&lock->rlock);
}

#define raw_spin_lock(lock)    _raw_spin_lock(lock)

分叉点在 _raw_spin_lock。它有两个实现，由 spinlock.h 按 CONFIG_SMP 选一个 include 进来：单核用 include/linux/spinlock_api_up.h，多核用 kernel/locking/spinlock.c。这也是为什么不能直接 include spinlock_api_up.h——它依赖外层的配置判断。

UP 分支与 SMP 分支 #

c
/* include/linux/spinlock_api_up.h —— 单核 */
#define _raw_spin_lock(lock)            __LOCK(lock)

#define __LOCK(lock) \
 do { preempt_disable(); ___LOCK(lock); } while (0)

#define ___LOCK(lock) \
  do { __acquire(lock); (void)(lock); } while (0)

___LOCK() 在 non-debug 版本里是空的，__acquire() 只在 sparse 检查时有意义。UP 上整个 spin_lock() 就剩一句 preempt_disable()。素材 3 提到的 debug 版（spinlock_up.h）会在 ___LOCK 里加锁状态校验和持有者记录，依然不加自旋——UP 上没有第二个 CPU 跟你抢。

c
/* kernel/locking/spinlock.c —— 多核 */
void __lockfunc _raw_spin_lock(raw_spinlock_t *lock)
{
    __raw_spin_lock(lock);
}

/* include/linux/spinlock_api_smp.h */
static inline void __raw_spin_lock(raw_spinlock_t *lock)
{
    preempt_disable();
    spin_acquire(&lock->dep_map, 0, 0, _RET_IP_);
    LOCK_CONTENDED(lock, do_raw_spin_trylock, do_raw_spin_lock);
}

__lockfunc 是段属性宏，把这些函数放进 .spinlock.text 段，CONFIG_LOCKDEP 打开时按函数逐个生成，方便定位是哪个锁函数出的问题。三句正文各管一件事：preempt_disable() 挡本 CPU 抢占，spin_acquire() 给 lockdep 记「我在这里拿了这把锁」，LOCK_CONTENDED() 真正去抢。spin_acquire() 展开成 lock_acquire_exclusive() 再展开成 lock_acquire()，没开 CONFIG_LOCKDEP 时它是空函数：

c
/* include/linux/lockdep.h */
#define lock_acquire_exclusive(l, s, t, n, i)           lock_acquire(l, s, t, 0, 1, n, i)
#define spin_acquire(l, s, t, i)                lock_acquire_exclusive(l, s, t, NULL, i)
#define lock_acquire(l, s, t, r, c, n, i) do { } while (0)

LOCK_CONTENDED：先试一次再死等 #

c
#define LOCK_CONTENDED(_lock, try, lock)                        \
do {                                                            \
        if (!try(_lock)) {                                      \
                lock_contended(&(_lock)->dep_map, _RET_IP_);    \
                lock(_lock);                                    \
        }                                                       \
        lock_acquired(&(_lock)->dep_map, _RET_IP_);             \
} while (0)

名字里带 CONTENDED，但没开 CONFIG_LOCK_STAT 时它只是 #define LOCK_CONTENDED(_lock, try, lock) lock(_lock)。开了统计才走上面那个「先 try 一次、失败记一笔 contended、再死等」的版本。所以未开统计时 do_raw_spin_trylock() 根本不会被调用——spin_lock() 一上来就是死等，不是先试后等。lock_contended() / lock_acquired() 只负责记录「这把锁被等过几次、等了多久」。

do_raw_spin_lock：两个版本 #

同名函数有两个实现，取决于 CONFIG_DEBUG_SPINLOCK。non-debug 版本在 include/linux/spinlock.h，是内联的：

c
static inline void do_raw_spin_lock(raw_spinlock_t *lock) __acquires(lock)
{
    __acquire(lock);
    arch_spin_lock(&lock->raw_lock);
}

debug 版本在 kernel/locking/spinlock_debug.c：

c
/*
 * We are now relying on the NMI watchdog to detect lockup instead of doing
 * the detection here with an unfair lock which can cause problem of its own.
 */
void do_raw_spin_lock(raw_spinlock_t *lock)
{
        debug_spin_lock_before(lock);
        arch_spin_lock(&lock->raw_lock);
        mmiowb_spin_lock();
        debug_spin_lock_after(lock);
}

debug_spin_lock_before() 检查锁是不是已经被当前 CPU 持有（递归加锁会直接报错而不是卡死），debug_spin_lock_after() 记下持有者，mmiowb_spin_lock() 处理 MMIO 写序。注释那句值得读：内核靠 NMI watchdog 检测锁死，不再在锁内部做周期性检测，因为在不公平的锁上做检测本身会引入新问题。素材 3 给的是 debug 版，素材 1 给的是 non-debug 版，两份都对，只是配置不同。

八、spin_lock_irqsave 与它的兄弟们 #

基础款 spin_lock 只关抢占。要关中断、关软中断，得另外加料。内核把这几种组合都封好了。

六个组合宏 #

素材 3 给的等价关系是对的，照抄并补上返回值说明：

text
spin_lock_irq()      = spin_lock() + local_irq_disable()
spin_unlock_irq()    = spin_unlock() + local_irq_enable()

spin_lock_irqsave()  = spin_lock() + local_irq_save(flags)
spin_unlock_irqrestore() = spin_unlock() + local_irq_restore(flags)

spin_lock_bh()       = spin_lock() + local_bh_disable()
spin_unlock_bh()     = spin_unlock() + local_bh_enable()

local_irq_save(flags) 多了一个参数：它先把当前 CPU 的中断使能状态读进 flags，再关中断。local_irq_restore(flags) 按 flags 恢复，而不是无脑开中断。这个差别是要命的。如果进临界区之前中断本来就是关的（比如你正处在一段临界区里，外面已经关过），spin_unlock_irq() 会无脑把中断打开，把外层的关中断意图破坏掉；spin_unlock_irqrestore() 会恢复成关的状态，外层的保护还在。

四种变体对照 #

变体 关抢占 关本地硬中断 关软中断 保存/恢复中断状态 典型场景
spin_lock 是 否 否 否 纯进程上下文互斥，确定没有中断/软中断会碰这块数据
spin_lock_bh 是 否 是 否 进程上下文 vs 软中断/tasklet 共享数据
spin_lock_irq 是 是 隐含是 否 确定进入时中断是开着的
spin_lock_irqsave 是 是 隐含是 是 不确定进入时中断状态，或会被别的临界区嵌套调用

spin_lock_irq 和 spin_lock_irqsave 都关了硬中断，软中断自然进不来（软中断只在硬中断退出时或 local_bh_enable() 时跑）。所以「关硬中断」打勾的，软中断那一列不用单独打。

raw_spin_lock_bh()、raw_spin_lock_irq()、raw_spin_lock_irqsave()、raw_spin_trylock() 和对应的 raw_spin_unlock_*()，接口形状完全一致，区别只在操作的是 raw_spinlock_t 而不是 spinlock_t。给 RT 内核准备的逃生门，主线里两者等价。

还有 trylock #

c
int spin_trylock(spinlock_t *lock);

抢到返回 1，抢不到返回 0，不自旋。它同样会 preempt_disable()，但返回 0 时抢占计数已经被减回去了，你不用管；返回 1 就正常走 spin_unlock()。用处是「宁可走备用路径，也不要卡在这里」——比如中断处理程序想拿一把会被长时间持有的锁，拿不到就丢进队列延后处理。

一个容易踩的坑：解锁顺序 #

spin_unlock_irqrestore(lock, flags) 展开到 __raw_spin_unlock_irqrestore() 是先解锁，后恢复中断状态：

c
#define spin_unlock_irqrestore(lock, flags) \
do {                                    \
        raw_spin_unlock_irqrestore(lock, flags); \
} while (0)

这个顺序是必须的。如果先开中断再解锁，中断进来的那一刻你还持着锁，中断里要这把锁就死锁，第六章分析过。先放锁再开中断，中断进来时锁已经是自由的了。

九、为什么要区分 spin_lock / _irq / _irqsave / _bh #

答案只有一个：你要挡住的是谁，就用对应的那一款。挡错了不是性能问题，是死锁或者数据错乱。

判断流程 #

问三个问题，按顺序：

text
1. 这块数据会被硬中断处理程序碰吗？
     会  → 进程上下文用 spin_lock_irqsave（或确定中断开着时用 spin_lock_irq）
            中断上下文里用 spin_lock
     不会 → 下一步

2. 这块数据会被软中断 / tasklet / timer callback 碰吗？
     会  → 进程上下文用 spin_lock_bh
            软中断上下文里用 spin_lock
     不会 → 下一步

3. 只在进程上下文之间共享？
     → spin_lock

第 1 步为什么中断上下文里用裸 spin_lock 就够？因为硬中断处理程序运行时，本 CPU 的中断是关的（新内核不区分 fast/slow handler，所有 handler 都在关中断的上下文里跑），同一个中断不会在同一个 CPU 上嵌套自己，别的 CPU 上的同一个中断由锁本身挡住。所以中断侧不需要再关一次。

为什么进程侧要用 irqsave 而不是 irq #

因为进程上下文的中断状态不可预知。你这段代码会被另一个已经关了中断的临界区调用。这时候 spin_lock_irq() 记不住「进来时是关的」，spin_unlock_irq() 会把中断误开。

spin_lock_irq() 只在你能百分百确定「进这里时中断必然是开的」时才能用。驱动里这种情况少，所以内核代码里 spin_lock_irqsave 的出现频率远高于 spin_lock_irq。

素材 1 那个「牛刀杀鸡」的说法 #

素材 1 讨论 softirq 场景时写：用 spin_lock + 关本地中断当然能保护，但拿牛刀杀鸡，local_bh_disable() 就够了。

这个判断是对的。软中断不会在硬中断上下文之外异步打断你，它只在硬中断退出、或 local_bh_enable()、或 ksoftirqd 调度时执行。关掉 bh 就把它挡在门外了，不需要连硬中断一起关。关硬中断的代价更高——它会让整个系统的中断响应变差。

一个跨平台的反直觉要求 #

素材 3 提了一条，值得单独抄出来：即便你在单核上写代码，也要按多核来想。它的例子是：单核上「进程里用 spin_lock_irqsave，中断里不调 spin_lock」也能工作，因为 spin_lock_irqsave 已经保证本 CPU 的 ISR 跑不了。但换到多核，spin_lock_irqsave 关的是本 CPU 的中断，别的 CPU 上的同一个中断照样能进来，两边同时改数据。所以中断处理程序里也必须调 spin_lock。这条规则不分架构：只要进程和中断共享数据，两侧都要加锁，进程侧加 irqsave。

十、中断上下文里用普通 spin_lock 会死锁的那一幕 #

把这一场完整走一遍，它是最容易犯、后果最重的一个错。

布景 #

一块共享数据 R，被两处访问：进程上下文里 foo() 用 spin_lock(&lock) 保护 R 的读改写，外设 P 的中断 handler 里也要读写 R。

c
static DEFINE_SPINLOCK(lock);
static int counter;

static irqreturn_t p_handler(int irq, void *dev)
{
    spin_lock(&lock);          /* 错在这里：普通 spin_lock */
    counter++;
    spin_unlock(&lock);
    return IRQ_HANDLED;
}

static void foo(void)
{
    spin_lock(&lock);          /* 同一个错 */
    counter++;
    spin_unlock(&lock);
}

走一遍 #

  1. CPU0 上的进程 A 调 foo()，spin_lock() 成功，counter 是 42，A 准备写 43。
  2. A 还没写完，外设 P 的中断来了，落在 CPU0 上。
  3. CPU0 转去跑 p_handler()，它也要 spin_lock(&lock)。
  4. 锁在 A 手里。SMP 上 p_handler() 进 wfe 等待 owner 变化。
  5. 谁能让 owner 变？只有 A。而 A 被这个中断打断了，它的执行流就压在中断栈底下。
  6. 中断不返回，A 不继续；A 不继续，锁不释放；锁不释放，中断不返回。

CPU0 卡在 wfe 上，直到看门狗把它报出来。

换成 irqsave 就没事 #

c
static void foo(void)
{
    unsigned long flags;

    spin_lock_irqsave(&lock, flags);
    counter++;
    spin_unlock_irqrestore(&lock, flags);
}

第 1 步之后 local_irq_save() 把 CPU0 的中断关了。第 2 步的中断落不到 CPU0 上，会被路由到别的 CPU（SMP 下由中断控制器的亲和性设置决定），或者挂起到中断重新使能。A 安稳地把 counter 写完、放锁、恢复中断，中断此时才进来，锁是自由的，p_handler() 一次拿到。

关键在于：关中断这个动作必须和拿锁在一起。分开放（先 local_irq_disable() 再 spin_lock()）功能上等价，但解锁时容易配错——spin_unlock_irqrestore() 会替你按正确顺序做「放锁、恢复中断」两件事。

中断侧为什么用裸 spin_lock #

p_handler() 保持 spin_lock() 就好。它运行时本 CPU 中断是关的，自己不会再被打断（NMI 除外，NMI 不能拿普通 spinlock，这是另一条规矩）。它要防的是别的 CPU 上的进程 A，独占指令已经够了。中断侧写成 spin_lock_irqsave() 不会错，只是白干——白白保存恢复一次中断状态。### 那一幕的变体：软中断

把 handler 换成 tasklet，进程侧用 spin_lock_bh()：

c
static void p_tasklet(unsigned long data)
{
    spin_lock(&lock);
    counter++;
    spin_unlock(&lock);
}

static void foo(void)
{
    spin_lock_bh(&lock);
    counter++;
    spin_unlock_bh(&lock);
}

同样的道理。local_bh_disable() 之后本 CPU 上的软中断被推迟到 local_bh_enable() 之后再跑，那时锁已经放了。不用关硬中断，代价小得多。这里误用 spin_lock() 的话，进程 A 在临界区里被软中断打断，tasklet 里 spin_lock 自旋，A 跑不了——同一个死锁，只是触发源从硬中断换成软中断。

十一、spinlock 在 ARM 上的实现：ldrex/strex 与 wfe #

ARM 的独占访问机制是这套东西的硬件基础，先讲清楚它，后面的 ticket 汇编才读得懂。

ldrex / strex 干了什么 #

ldrex（Load-Exclusive）和 strex（Store-Exclusive）是一对。它们不是原子指令，配对使用才构成原子操作。

armasm
ldrex  r0, [r1]        @ 读 [r1] 到 r0，同时给 [r1] 这块地址打上独占标记
add    r0, r0, #1      @ 中间随便算，可以插任意指令
strex  r2, r0, [r1]    @ 尝试写回：独占标记还在就写成功，r2 = 0
                       @             标记没了就写失败，r2 = 1，[r1] 不变

关键点：ldrex 之后，如果有任何其他 PE（处理单元）对同一地址执行了写，本 PE 的独占标记就被清掉，strex 必定失败并返回 1。软件看到 strex 返回非 0，就知道「我算的这遍白算了」，回到 ldrex 重来。

这就是一个无锁的「读-改-写」原子序列。它比 CAS 灵活（中间可以做任意运算），但要求中间不能有别的写碰这块地址，所以循环是必须的。三条使用铁律：ldrex 和 strex 必须访问同一地址，否则行为未定义；中间的指令数不能太多，独占监视器（exclusive monitor）不是无限的，具体上限「未验证」，实践上都是几条指令；strex 的返回值必须检查，忽略它就是一个静默的错误。

独占监视器与 wfe 的联动 #

ARM ARM 里有一张 global monitor 的状态迁移图（Figure B2-5）：PE(n) 对地址 x 发起 exclusive 操作时，PE(n) 的 global monitor 从 open access 迁移到 exclusive access；此时来自其他 PE 针对 x 的 store 操作会让 PE(n) 的 global monitor 退回 open access，并且把 PE(n) 的 Event register 写上一个 event，把 PE(n) 唤醒。

这条硬件行为有个实际后果：arch_spin_unlock() 里不需要 sev 指令。等锁的 PE 在自旋前都执行过 ldrex（ARM32）或 ldaxrh（ARM64）读 owner，已经把自己设成了「在 x 上等待」，解锁那次 store 会自动给它们发 event。省一条指令，也省一次广播。

wfe / sev / sevl #

wfe（Wait For Event）让 CPU 进入低功耗等待，直到 Event register 收到 event 才继续。它和 wfi（等中断）的区别是 wfe 可以被 sev 唤醒，也可以被硬件事件（上面那条）唤醒，不要求真中断。sev（Send Event）向所有 PE 广播 event，sevl（Send Event Local）只给自己发一个 event，先把 Event register 置位。

sevl 的用处很具体。ARM64 的 arch_spin_lock 在进入 wfe 循环前先 sevl，堵一个窗口：如果解锁恰好发生在「判断 owner 不相等」和「执行 wfe」之间，这个 event 就丢了，wfe 会睡到下一次 event 才醒，白等一个来回。先 sevl 把 register 置位，下一句 wfe 立刻返回，重新读 owner，继续判断。

ARM32 的旧代码没有 sevl，靠的是 wfe 之前那次 ldrex/ldr 建立的监视状态。这个差异在 3.x 的 ARM32 和 4.x 的 ARM64 之间真实存在。

为什么 V6 之后的 ARM 需要内存屏障 #

arch_spin_lock() 结尾有一句 smp_mb()，注释写得明白：

A memory barrier is required after we get a lock, and before we release it, because V6 CPUs are assumed to have weakly ordered memory.

拿到锁之后必须有一条屏障，否则临界区里的访存会被重排到锁之前执行——锁还没真正到手，数据已经被改了。释放锁之前同样需要。

ARMv8 引入的 Load-Acquire / Store-Release 语义可以用指令自带屏障替换显式 dmb：ldaxr 是 load + acquire，保证这条 load 之后的指令在所有 observer 看来都在它之后执行；stlrh / stlr 是 store + release，保证这条 store 之前的指令都在它之前完成。

省一条 dmb 在锁这种每纳秒都在跑的热路径上不是小事。这就是为什么 ARM64 的 arch_spin_lock() 结尾没有 smp_mb()，而 ARM32 有。

十二、ticket spinlock：为什么要排队 #

第三章留下的问题：无序竞争为什么会饿死人。答案在 cache 一致性，解法在排队。

问题重述 #

锁在内存里，每个 CPU 的 L1 都缓存了它。CPU0 持锁、释放（执行 smp_mb() 让别人的 cache line 失效），它自己的 L1 里那份数据还是热的，下一次去抢几乎必然赢。而刚被失效了缓存的 CPU1 得从内存重新取，慢一大截。结果就是「越抢越热、越热越抢」，Nick Piggin 说的「被饿一百万次」就是这么来的。

解法：叫号 #

ticket spinlock 借的是银行柜台的模型。进门先取号，柜台叫号，号对上的人才上前。owner 是当前叫到的号（服务号），next 是下一个要发的号（排队号）。

规则三条：拿锁时原子地把 next 加一，自己留下旧的 next 值作为自己的号；然后轮询 owner 是否等于自己的号，等于就进临界区，不等就继续等；释放锁时 owner 加一，下一个人的号就对上了。因为发号是原子的（ldrex/strex），不会有两个 CPU 拿到同一个号。所以严格先来先得，饿死在这里不存在。

用餐馆讲一遍 #

素材 1 用「九毛九只有一张桌子」打比方，我们沿用。最开始 slock = 0，owner = next = 0，两者相等表示空闲。

第一个人来（thread 调 spin_lock），看到 owner == next，直接入席，同时 next++ 变成 1——「下一个人来，给他 1 号」。这个人吃得快，没人竞争就 spin_unlock，owner++ 变成 1，表示「1 号可以入席了」。

1 号来了，取号拿到 1，next++ 变成 2。1 号吃饭巨慢（thread 不该长期持锁，但存在）。期间 2 号、3 号、4 号陆续来，依次拿到 2、3、4，next 一路涨到 5，owner 停在 1 不动，所有人都在门口等。1 号终于吃完，spin_unlock，owner++ 变成 2，2 号看到号对上了入席，3 号、4 号继续等。owner 一次只加一，所以严格按取号顺序放行。

ARM32 的 arch_spin_lock #

arch/arm/include/asm/spinlock.h（3.x）：

c
static inline void arch_spin_lock(arch_spinlock_t *lock)
{
    unsigned long tmp;
    u32 newval;
    arch_spinlock_t lockval;

    prefetchw(&lock->slock);                          /* (1) */

    __asm__ __volatile__(
"1:    ldrex    %0, [%3]\n"                           /* (2) */
"    add      %1, %0, %4\n"                           /* (3) */
"    strex    %2, %1, [%3]\n"                         /* (4) */
"    teq      %2, #0\n"                               /* (5) */
"    bne      1b"
    : "=&r" (lockval), "=&r" (newval), "=&r" (tmp)
    : "r" (&lock->slock), "I" (1 << TICKET_SHIFT)
    : "cc");

    while (lockval.tickets.next != lockval.tickets.owner) {   /* (6) */
        wfe();                                                /* (7) */
        lockval.tickets.owner = READ_ONCE(lock->tickets.owner); /* (8) */
    }

    smp_mb();                                                 /* (9) */
}

逐条：

  1. prefetchw() 把 cache line 预取成独占状态，纯粹为性能。ARM32 上它展开成 pldw，老核上是空实现。
  2. ldrex 把整个 slock（owner + next 打成 32 位）读进 lockval，同时打独占标记。
  3. newval = lockval + (1 << 16)。因为 next 在高 16 位，这等价于 next++。
  4. strex 写回。成功 tmp = 0，失败 tmp = 1。
  5. 失败就 bne 1b 回去重来。这是「取号」的原子操作。
  6. 取完号，比较自己 lockval 里的 next（自己拿到的号）和 owner（服务号）。相等就直接进临界区，一次也没等——无竞争时零开销。
  7. 不相等就 wfe 睡下等 event。谁发 event？持锁者 spin_unlock 时写 owner，第十一章讲过，硬件会自动给在 slock 上做过 exclusive load 的 PE 发 event。
  8. 被唤醒后重新读 owner（用 READ_ONCE 防止编译器把它提到循环外），回到 6 判断。只读 16 位而非整个 slock，虽然两者同在一个 cache line，终究会失效。
  9. smp_mb()，ARM64 上被 acquire/release 指令代替了，ARM32 上必须有。

三个进程同时抢的一次完整推演 #

slock 初始 0（owner = 0, next = 0），三个 CPU 同时执行到 ldrex。

时刻 CPU0 CPU1 CPU2 lock->slock
起始 — — — owner=0, next=0
CPU0 抢到独占 lockval=0，newval=1<<16，strex 成功 同时 ldrex，标记被抢 同时 ldrex，标记被抢 next=1
CPU0 判断 next(0) == owner(0)，持锁进临界区 strex 失败，bne 1b strex 失败，bne 1b —
CPU1 重来 在临界区 lockval=1<<16，newval=2<<16，成功 又失败 next=2
CPU1 判断 在临界区 next(1) != owner(0)，wfe 重来 —
CPU2 重来 在临界区 睡着 lockval=2<<16，newval=3<<16，成功 next=3
CPU2 判断 在临界区 睡着 next(2) != owner(0)，wfe —
CPU0 解锁 owner++ → 1 被 event 唤醒 睡着 owner=1, next=3
CPU1 判断 出临界区 next(1) == owner(1)，持锁 仍 next(2) != owner(1)，继续睡 —

三个人各自拿到的号是 0、1、2，owner 一次加一，放行顺序 0 → 1 → 2。这就是公平性。

素材 3 那段推演的三个错 #

素材 3 也做了这个推演，写的是：

此时第一个进程释放spinlock，则执行 lock->tickets.owner++，lock->tickets.owner=2； 虽然此时第二个进程和第三个进程都在等待spinlock，但是因为第二个进程的修改了 lockval.tickets.owner，满足了 ...

两处错。owner 从 0 加一得 1，不是 2；真跳到 2，进程 2 的号（1）就被跳过了，进程 3 会先拿到锁，公平性直接消失——而公平性正是 ticket lock 存在的理由。「第二个进程修改了 lockval.tickets.owner」这个说法把方向搞反了：lockval 是每个 CPU 自己的栈上局部变量，别人改不了。进程 2 是在 wfe 循环里重新读了 lock->tickets.owner 并写进自己的 lockval（上面第 8 步），然后重新比较。素材 3 自己给的代码写的就是 lockval.tickets.owner = ACCESS_ONCE(lock->tickets.owner)，是对的，推演段落写岔了。

素材 3 的汇编逐条表也有问题：它有 13 行，里面 ldrex R0, [R3] 出现了三次、strex R1, R0, [R3] 出现一次（这条在源码里不存在）。那张表把三个 CPU 的执行交织错了位。以上面那张表为准。

ARM64 的 arch_spin_lock #

arch/arm64/include/asm/spinlock.h（4.1.10）：

c
static inline void arch_spin_lock(arch_spinlock_t *lock)
{
    unsigned int tmp;
    arch_spinlock_t lockval, newval;

    asm volatile(
    /* Atomically increment the next ticket. */
"    prfm    pstl1strm, %3\n"                      /* (A) */
"1:    ldaxr    %w0, %3\n"                        /* (B) lockval = lock */
"    add      %w1, %w0, %w5\n"                    /* newval = lockval + (1<<16) */
"    stxr     %w2, %w1, %3\n"                     /* lock = newval */
"    cbnz     %w2, 1b\n"                          /* 有其他 PE 插入？重来 */

    /* Did we get the lock? */
"    eor      %w1, %w0, %w0, ror #16\n"           /* 把 next 和 owner 异或到一起 */
"    cbz      %w1, 3f\n"                          /* 相等就是 0，持锁进临界区 */

    /*
     * No: spin on the owner. Send a local event to avoid missing an
     * unlock before the exclusive load.
     */
"    sevl\n"                                       /* (C) */
"2:    wfe\n"                                      /* (D) */
"    ldaxrh   %w2, %4\n"                           /* (E) 读 owner（半字） */
"    eor      %w1, %w2, %w0, lsr #16\n"            /* 自己的号 == owner？ */
"    cbnz     %w1, 2b\n"                           /* 不等，回 2 继续睡 */

    /* We got the lock. Critical section starts here. */
"3:"
    : "=&r" (lockval), "=&r" (newval), "=&r" (tmp), "+Q" (*lock)
    : "Q" (lock->owner), "I" (1 << TICKET_SHIFT)
    : "memory");
}

和 ARM32 的差别，逐条对照：

项目 ARM32 ARM64
预取 prefetchw prfm pstl1strm
独占加载 ldrex（无 acquire） ldaxr（带 acquire）
独占存储 strex stxr
取号后的内存屏障 结尾 smp_mb() 无，acquire 语义已含
比对方式 逐字段 != eor + ror #16 一次算完
进入等待前的防丢事件 无 sevl
读 owner ldr / READ_ONCE 整字后拆 ldaxrh 半字，带 acquire

eor %w1, %w0, %w0, ror #16 这一句干净：把 32 位值循环右移 16 位再和原值异或，若 owner == next 则高低半字抵消，结果为 0。一条指令代替两次取值比较。

ldaxrh 末尾的 h 是 halfword，只读 2 字节的 owner。ARM64 的 arch_spinlock_t 是两个裸 u16，本来就能单独寻址 owner，这是它去掉 union 的收益。

ARM64 的 arch_spin_unlock #

c
static inline void arch_spin_unlock(arch_spinlock_t *lock)
{
    unsigned long tmp;

    asm volatile(ARM64_LSE_ATOMIC_INSN(
    /* LL/SC */
    "    ldrh    %w1, %0\n"
    "    add     %w1, %w1, #1\n"
    "    stlrh   %w1, %0",
   /* 大系统扩展的原子指令 */
    "    mov     %w1, #1\n"
    "    staddlh %w1, %0\n"
    __nops(1))
    : "=Q" (lock->owner), "=&r" (tmp)
    :
    : "memory");
}

主体是「读 owner、加一、写回」，三步。这里不需要 ldrex/strex——一次只有一个执行流在临界区里，只有一个执行流会走到 unlock，owner 的读改写不会被并发。这个推论解释了为什么 unlock 比 lock 短得多。

stlrh 的 l 是 release。它保证临界区里的所有写，在别的 CPU 看来都发生在 owner 更新之前。少了这个，下一个持锁者会先看到 owner 变了、拿锁进临界区，然后才看到上一个持锁者写的数据——数据竞争。ARM64_LSE_ATOMIC_INSN 是个编译期二选一：处理器有 LSE（Large System Extensions，ARMv8.1 引入的原子指令扩展）时用 staddlh（带 release 的原子加）一条搞定，没有就用 ldrh/add/stlrh 三连。前面取号那半段同理，有 LSE 就用 ldadda。

为什么 ARM 至今还是 ticket #

4.2 之后 x86 换成了 qspinlock（MCS 的 4 字节压缩版），ARM 一直留在 ticket。原因不是 ARM 落后，是 qspinlock 依赖 xchg 和 per-CPU 变量布局，在 ARM 上的收益相对小；而 ARM 的 ticket 已经配好了 wfe，空转不烧 CPU，cache 行争用的痛点被削弱了。排队锁的状态机、pending 位、_Q_LOCKED_VAL 那些，本篇不展开，排队锁见同批另一篇。

十三、自旋锁保护的边界：它保护的是数据，不是代码 #

这是误解最多的一条。写下来一句话：锁保护的是数据实例，不是代码段。

一条推论会让人不适应：同一个函数可以在两个 CPU 上同时执行，只要它不碰受保护的数据。spin_lock 不负责「让这个函数串行」，它只负责「让通过这把锁访问这份数据的执行流串行」。举两个写错的样子。

错法一：以为加锁就串行了。

c
static DEFINE_SPINLOCK(lock);

static void update(void)
{
    spin_lock(&lock);
    a++;                 /* 受保护，对的 */
    spin_unlock(&lock);

    b++;                 /* 不受保护，别的 CPU 照样能同时改 b */
}

b++ 在锁外，update() 在两个 CPU 上跑就是数据竞争。要保护 b 就把它挪进临界区，或者给它另一把锁。

错法二：一把全局锁保护所有东西。 static DEFINE_SPINLOCK(big_lock); 能跑，但在多核上是性能灾难，所有 CPU 排队过同一把锁，本来能并行的路径全串起来。

第三层：锁要跟着数据走，不是跟着函数走。

c
struct queue {
    spinlock_t lock;
    struct list_head head;
};

static void queue_push(struct queue *q, struct item *it)
{
    spin_lock(&q->lock);
    list_add_tail(&it->node, &q->head);
    spin_unlock(&q->lock);
}

锁嵌在 queue 里，每个队列一把。一百个队列就是一百把独立的锁，互不干扰。写成函数外的 static DEFINE_SPINLOCK(lock)，一百个队列就抢一把。

临界区的边界怎么划 #

标准是「不变量」：临界区要刚好包住「不变量被破坏」的那段窗口，不多不少。链表插入的不变量是「head 的指针和 it->node 的指针要么都旧、要么都新」，所以 list_add_tail() 整段必须在锁内。插入之后要打印一行日志，那行打印不该在锁内——它不参与不变量，放进去只让临界区变长。

一个反直觉的结论 #

自旋锁不阻止任何代码执行，它只让抢不到锁的执行流原地空转。「加了锁」从来不等于「安全了」。安全的充分条件是：所有访问这份数据的路径，都用了同一把锁。漏掉一条，锁就等于没加。这也是 CONFIG_DEBUG_SPINLOCK 和 lockdep 存在的理由——它们检查的正是「有没有漏」。

十四、嵌套与加锁顺序 #

同一把锁不能嵌套 #

已经持有 spin_lock(&lock)，再 spin_lock(&lock) 一次会怎样？

SMP 上：第二次发现 next != owner，wfe 睡下等自己释放锁，等到天荒地老。这叫自死锁（self-deadlock）。

UP 上更阴：spin_lock 只做 preempt_disable()，第二次调用照样成功返回，抢占计数变成 2，代码一路跑下去看着没事。等第一次 spin_unlock() 把计数减回 1，锁其实已经「放」了，你的代码却以为还持有——保护漏了。UP 上不报错，只是静默失效。

CONFIG_DEBUG_SPINLOCK 的 debug_spin_lock_before() 专门查这个：它记了持有者，发现当前 CPU 已经持有同一把锁就立刻报错，不让你卡死。这是第七章那个 debug 版本存在的最大价值。绝不对同一把锁递归加锁。 需要递归保护的场景说明临界区划分有问题，重新设计。

多把锁必须定序 #

两个临界区各要两把锁，顺序不一致就是 ABBA 死锁：

c
/* CPU0 */                    /* CPU1 */
spin_lock(&a);                spin_lock(&b);
spin_lock(&b);                spin_lock(&a);

CPU0 拿到 a 等 b，CPU1 拿到 b 等 a。两边都在自旋，谁都不放，系统挂死。

规则：给所有锁排一个全局顺序，任何路径都按这个顺序加锁。 顺序怎么定都行，关键是要有，且全代码库一致，用「锁的地址大小」「模块内编号」「数据结构层次」都可以，写进注释。内核里成对使用、顺序已经定死的有 mm->page_table_lock 与 pte_lock、task_struct->alloc_lock 与 signal->siglock，这类顺序在内核文档里有记载，改之前要先查。### 嵌套时的 irqsave 变量

c
static void outer(void)
{
    unsigned long flags;

    spin_lock_irqsave(&a, flags);
    inner();
    spin_unlock_irqrestore(&a, flags);
}

static void inner(void)
{
    unsigned long f2;

    spin_lock_irqsave(&b, f2);     /* 注意：用另一个变量 */
    /* ... */
    spin_unlock_irqrestore(&b, f2);
}

两层各用自己的 flags 变量。图省事共用一个，内层 local_irq_save() 会把「外层已经关了中断」这个事实覆盖掉，外层恢复时就恢复错了。这也是 local_irq_save() 存在的全部理由——它把状态存下来，恢复时按存的值恢复，不是无脑开。

lockdep 能查什么 #

CONFIG_PROVE_LOCKING（lockdep）在运行时记录「谁在持有什么锁的时候申请了什么锁」，维护一张锁依赖图。它抓得住的：ABBA 死锁的潜在顺序（还没真死就报）、持有锁时申请另一把已知会冲突的锁、中断上下文与进程上下文的锁使用不一致（靠 spin_lock_irqsave 与 spin_lock 的类别标记推断）、同一把锁递归申请。它抓不住数据竞争本身。锁用对了，代码照样会漏保护某条路径，那个得靠 KCSAN 这类工具。

十五、几道常见的自旋锁问题 #

素材 4 是问答体，把它的两个问题和另外几个常被问到的合并在这里。

Q1：单核上 spin_lock() 什么都不做，那我写了有什么用？ #

在你自己那块单核板子上，确实什么都没做。但代码不是只为一块板子写的。三个理由：跨配置编译（同一份代码在 SMP 配置下需要它）；关抢占这个副作用真实生效，它挡住了内核态抢占；CONFIG_DEBUG_SPINLOCK / lockdep 打开后它是检查器挂载点，能抓出漏保护的路径。省掉它的代价是「在你的板子上能跑，在别人的板子上炸」。

Q2：持锁期间，我的代码会被打断吗？ #

分三层：被别的进程抢走——不会，preempt_disable() 挡住了；被硬中断打断——会，spin_lock() 不关中断，除非你用 spin_lock_irq / spin_lock_irqsave；被软中断打断——会，除非你用 spin_lock_bh。所以「持锁期间不可打断」这句话只在 spin_lock_irqsave 这个级别成立，裸 spin_lock 只保证「不会被别的进程抢走 CPU」。

Q3：spin_lock 和 spin_lock_irqsave 到底怎么选？ #

回到第九章那三个问题。核心判据只有一条：这块数据会被中断处理程序碰吗？ 会就用 spin_lock_irqsave（进程侧），不会就有机会用便宜的。

不确定的时候选 spin_lock_irqsave。它多一点开销（保存恢复一次中断状态），但错了会死锁，而死锁在现场极难查。

Q4：临界区里能不能 printk？ #

能。printk() 可以在原子上下文调用，它自己处理了重入（用 per-CPU 缓冲和锁的嵌套计数），调试时在锁里打日志不会立刻炸。

printk() 很慢，串口输出一行要几十微秒，在自旋锁里打日志会把临界区拉长几个数量级。调试期可以，提交前删掉。真正不能碰的是 printk 之外那些会睡的：kmalloc(GFP_KERNEL)、copy_from_user()、mutex_lock()，第二章列过清单。

Q5：既然锁里不能睡，那我为什么不用 mutex？ #

因为 mutex 在中断上下文里用不了，而 spinlock 能。这不是偏好问题，是可用性问题。选择标准很硬：临界区会不会在中断上下文（或任何不能调度的上下文）执行？ 会就只能 spinlock，临界区必须做到极短；不会就优先 mutex，抢不到会睡，不烧 CPU，临界区可以长。

spinlock 是给「不能睡」的场景用的，不是给「想快」的场景用的。能睡的地方用它，纯属自找麻烦。

Q6：spin_lock 会一直自旋吗？有没有超时？ #

没有超时，没有退避上限，没有放弃机制。arch_spin_lock() 里的循环是无界的，第六章末尾讲过。

唯一会「退出」的情况是持锁者释放锁。持锁者因为任何原因跑不下去，等锁者就陪它一起卡着，检测交给 NMI watchdog 和 hung_task，它们只报不解。

Q7：为什么不干脆用原子操作代替锁？ #

原子操作只有一条指令的粒度。atomic_inc() 保证加一是原子的，但保证不了「读 A、判断、再改 B」这一串的原子性。

只要能用一个原子操作表达完整的不变量，就用原子操作，比锁便宜得多。一旦需要多条语句共同维持一个不变量，就得上锁。

十六、易错点速查 #

按「症状 → 原因 → 修法」排，方便现场对照。

# 症状 原因 修法
1 单核上数据错乱，多核上直接挂死 中断处理程序也碰这块数据，但进程侧只用了 spin_lock 进程侧换 spin_lock_irqsave，中断侧保持 spin_lock
2 软中断并发下数据错乱 进程侧用 spin_lock，tasklet 里也用它 进程侧换 spin_lock_bh
3 系统偶发整体卡死，无 oops 临界区里调了会睡的函数，持锁者睡下去 找出 copy_from_user/kmalloc(GFP_KERNEL)/msleep，挪出临界区
4 调用某个函数就卡住，栈里停在 wfe 同一把锁递归加锁 拆临界区，绝不对同一把锁嵌套
5 两个线程互相等，各自拿着对方要的锁 加锁顺序不一致（ABBA） 定全局顺序，全库统一
6 spin_unlock_irq() 之后中断状态不对 进入时中断本来就是关的，被无脑打开了 换 spin_lock_irqsave + spin_unlock_irqrestore
7 UP 上验证通过，SMP 上崩 按单核写了锁，或省掉了 spin_lock 一律按 SMP 写；中断里也要加锁
8 解锁后别的 CPU 读到旧数据 缺内存屏障，或用了 _relaxed 变体 用标准 spin_lock/spin_unlock，别自己拼屏障
9 临界区里 printk 后系统变慢 串口输出把临界区拉长几十倍 调试完删掉，或挪出临界区
10 一把锁成了全局瓶颈 用一把模块级锁保护所有数据 按数据实例分锁
11 NMI 里用 spin_lock 卡死 NMI 不能被屏蔽，持锁者永远等不到 NMI 里不能用普通 spinlock，要用 raw_spin_lock 加特殊处理
12 spin_trylock 抢到后忘了 spin_unlock 把它当纯查询用 返回非 0 就必须配对释放

再补三条不属于「误用」但经常被忽略的：

  • 用 DEFINE_SPINLOCK 而不是手写初始化。手写初始化容易漏掉 debug 字段，CONFIG_DEBUG_SPINLOCK 打开后行为异常。
  • 锁变量要跟着数据一起分配和释放。kmalloc 出来的结构体，里面的锁必须 spin_lock_init()，否则是一堆随机字节。
  • 别在持有锁时 return 忘了解锁。这是最常见的泄漏，CONFIG_DEBUG_SPINLOCK 会在释放路径上抓。
