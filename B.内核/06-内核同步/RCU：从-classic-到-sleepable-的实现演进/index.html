一、RCU 实现了什么承诺：读侧零开销 #

先把承诺说清楚，不然下面所有数据结构看起来都是自找麻烦。

RCU 的读侧原语，在 2.6.11 / 2.6.12 的 include/linux/rcupdate.h 里就两行：

c
#define rcu_read_lock()        preempt_disable()
#define rcu_read_unlock()    preempt_enable()

就这样。不配置 CONFIG_PREEMPT 的内核，preempt_disable() 展开成空，进出临界区一条指令都没有。三个后果：读侧不写共享变量；读侧不碰全局 cacheline，多个 CPU 同读一份数据各自的 cache 保持 shared；读侧不需要原子指令，没有 lock 前缀。rcu_dereference 在 x86 上是空的，只在 Alpha 这类弱序机器上补 smp_read_barrier_depends()。

代价全转移到写侧。写侧付出的是时间不是锁：等一个宽限期（grace period，下称 GP），确认所有「在改动之前就已进入读临界区」的读者都走完了，才能回收旧版本。

角色 付出什么 拿到什么
读者 一条 preempt_disable()，不可抢占内核下为 0 免锁、免原子操作、免 cacheline 争用
写者 一次 GP 的等待时间，外加一次 callback 调度 不用管读者是谁、有多少
系统 每 CPU 一份状态，GP 期间一轮扫描 读者再多也不增加开销

这个账能成立，前提是读者守规矩。三条规矩从 2.5.43 起没变过：读侧不能阻塞；读侧临界区不能跨任务传递；写者之间必须自己用别的机制互斥。2.6.12 的 rcupdate.h 里注释写得很直白：「So where is rcu_write_lock()? It does not exist」。

二、2.5.43 的第一次尝试 #

2.5.43 是第一个带 RCU 的内核版本。代码少，结构直白，正因为直白，问题看得清清楚楚。

c
/* 2.5.43 */
struct rcu_head {
    struct list_head list;
    void (*func)(void *obj);
    void *arg;
};

struct rcu_data {
    long            qsctr;          /* 本 CPU 的 QS 计数器，只增不减 */
    long            last_qsctr;     /* GP 起点那一刻记下的值 */
    long            batch;          /* 本 CPU curlist 里那批请求的批次号 */
    struct list_head nxtlist;       /* 新提交的 callback */
    struct list_head curlist;       /* 已分配批次号、正在等 GP 的 callback */
} ____cacheline_aligned_in_smp;

struct rcu_ctrlblk {
    spinlock_t      mutex;
    long            curbatch;       /* 正在检测 GP 的批次号 */
    long            maxbatch;       /* 已分配出去的最大批次号 */
    unsigned long   rcu_cpu_mask;   /* 还没上报 QS 的 CPU 位图 */
};

初始化是 { .curbatch = 1, .maxbatch = 1, .rcu_cpu_mask = 0 }。

qsctr 只增不减，每次本 CPU 离开读临界区就加一。GP 开始时把当前值抄进 last_qsctr，之后只要两个值不等，就说明这个 CPU 至少经历过一次静止状态。注意这是「两个计数器做差」，不是标志位。rcu_cpu_mask 的语义很干脆：GP 开始时置成 cpu_online_map，每个 CPU 上报 QS 就清掉自己那一位，全 0 则 GP 结束。

提交与推进 #

c
/* 2.5.43 */
void call_rcu(struct rcu_head *head, void (*func)(void *arg), void *arg)
{
    int cpu;
    unsigned long flags;

    head->func = func;
    head->arg = arg;
    local_irq_save(flags);
    cpu = smp_processor_id();
    list_add_tail(&head->list, &RCU_nxtlist(cpu));
    local_irq_restore(flags);
}

挂进本 CPU 的 nxtlist，完事。没有批次号，也不启动 GP。struct rcu_head 用双向链表、arg 单独传参，这两处 2.6 都砍了，理由在第三章和第七章。

批次号在 tick 里分配。每个 tick rcu_check_callbacks() 都会 tasklet_schedule(&RCU_tasklet(cpu))，tasklet 里跑 rcu_process_callbacks()：

c
/* 2.5.43，删掉无关代码 */
    local_irq_disable();
    if (!list_empty(&RCU_nxtlist(cpu)) && list_empty(&RCU_curlist(cpu))) {
        list_splice(&RCU_nxtlist(cpu), &RCU_curlist(cpu));
        INIT_LIST_HEAD(&RCU_nxtlist(cpu));
        local_irq_enable();
        spin_lock(&rcu_ctrlblk.mutex);
        RCU_batch(cpu) = rcu_ctrlblk.curbatch + 1;
        rcu_start_batch(RCU_batch(cpu));
        spin_unlock(&rcu_ctrlblk.mutex);
    } else {
        local_irq_enable();
    }

两个条件同时满足才动手：nxtlist 非空（有新请求）、curlist 为空（上一批已经搬走了）。满足就把 nxtlist 整条拼进 curlist，分配批次号 curbatch + 1。

为什么 +1？因为 curbatch 那批的 GP 还在检测中，新来的这批只能排队，它是 pending 批次。maxbatch 就是记账用的：记住最大分配出去的批次号，等 curbatch 那批过了 GP，maxbatch 大于 curbatch 就再启动一批。rcu_start_batch(newbatch) 做两件事——把 maxbatch 抬到 newbatch；如果 maxbatch 不低于 curbatch 且 rcu_cpu_mask == 0，把 rcu_cpu_mask 重置成 cpu_online_map，这就是 GP 的起点。

QS 上报 #

c
/* 2.5.43 */
static void rcu_check_quiescent_state(void)
{
    int cpu = smp_processor_id();

    if (!test_bit(cpu, &rcu_ctrlblk.rcu_cpu_mask))          /* (1) */
        return;
    if (RCU_last_qsctr(cpu) == RCU_QSCTR_INVALID) {         /* (2) */
        RCU_last_qsctr(cpu) = RCU_qsctr(cpu);
        return;
    }
    if (RCU_qsctr(cpu) == RCU_last_qsctr(cpu))              /* (3) */
        return;

    spin_lock(&rcu_ctrlblk.mutex);                          /* (4) */
    if (!test_bit(cpu, &rcu_ctrlblk.rcu_cpu_mask)) {        /* (5) */
        spin_unlock(&rcu_ctrlblk.mutex);
        return;
    }
    clear_bit(cpu, &rcu_ctrlblk.rcu_cpu_mask);              /* (6) */
    RCU_last_qsctr(cpu) = RCU_QSCTR_INVALID;                /* (7) */
    if (rcu_ctrlblk.rcu_cpu_mask != 0) {                    /* (8) */
        spin_unlock(&rcu_ctrlblk.mutex);
        return;
    }
    rcu_ctrlblk.curbatch++;                                 /* (9) */
    rcu_start_batch(rcu_ctrlblk.maxbatch);                  /* (10) */
    spin_unlock(&rcu_ctrlblk.mutex);
}

这段是 2.5.43 的心脏，逐条对：(1) 本 CPU 的位已经清了，这一轮 QS 早报过了；(2) last_qsctr 是 RCU_QSCTR_INVALID，说明这是新一轮 GP 的第一次检查，先记基准值，没有可比的东西；(3) 计数器和基准一样，本 CPU 还没经历过 QS；(4) 到这里说明确实经历过，要改全局位图了，加锁；(5) 拿锁后复查，拿锁期间别的路径先清了位；(6) 清掉自己的位；(7) 把 last_qsctr 打回 INVALID，为下一轮重置基准；(8) 还有别的 CPU 没上报，等它们；(9) 位图全 0，GP 过了，curbatch 加一，等于向全系统宣布「curbatch 那批的 GP 已完成」；(10) 试着启动下一批。

curbatch 这条自增就是广播方式：没有 IPI，没有通知，其他 CPU 下次看 curbatch 自然就知道进度变了。

callback 在哪跑 #

同一个 tasklet 函数里还有另一半：

c
/* 2.5.43 */
    LIST_HEAD(list);
    if (!list_empty(&RCU_curlist(cpu)) &&
        rcu_batch_after(rcu_ctrlblk.curbatch, RCU_batch(cpu))) {
        list_splice(&RCU_curlist(cpu), &list);
        INIT_LIST_HEAD(&RCU_curlist(cpu));
    }
    ...
    if (!list_empty(&list))
        rcu_do_batch(&list);

判定条件是 rcu_batch_after(curbatch, batch)——全局批次号跑到本 CPU 批次号前面去了，说明本 CPU 这批的 GP 已经过了。把 curlist 整条摘到临时链表，一次性跑完。这个「一次性跑完」是 2.5.43 最短的那块板。

三、那次尝试为什么会失败 #

原文开头作者自述「我这篇写得的确不怎么样」。这话说的是文档不是代码，但 2.5.43 的实现在工程上确实站不住。五个问题，一个比一个实。

问题一：rcu_cpu_mask 是全局写热点。 rcu_ctrlblk 是单个全局变量，每个 CPU 每次过 QS 都要 clear_bit 写它的一个 bit，CPU 一多这个 cacheline 就在核间来回弹。

更贵的是读，它出现在五处：rcu_pending() 里一次 test_bit；rcu_check_quiescent_state() 的 A 点 test_bit、B 点拿锁后复查、C 点 clear_bit、D 点判 0；rcu_start_batch() 里的非零判断和赋值。rcu_pending() 那个 test_bit 原本是为省 CPU 加的优化：位已经清了，这个 CPU 这一轮没活干，早点返回。结果就是把一个跨核写的变量变成了每 tick 每 CPU 都要读的变量，省下几条指令，赔进去的是 cache miss。A 点和 B 点是同一句 test_bit，中间夹着 spin_lock，B 点那次复查在只从这里调用的前提下没有意义，作者的评语是「我没有看出有任何的必要」。

问题二：rcu_do_batch() 一次跑完整批，实时性没救。 callback 跑在 tasklet 里，tasklet 是 softirq，softirq 是中断上下文，优先级高于任何进程。2.5.43 的 rcu_do_batch() 没有数量上限，一个批次挂上几千个 callback，全在这一次 softirq 里跑完，跑的过程中高优先级进程一个都调度不上。这不是理论问题，网络收包路径上 kfree_skb 走 RCU 的场合很多，包一多 callback 就堆起来。

问题三：接口把内存屏障甩给调用者。 2.5.43 对外只有四个符号：rcu_read_lock() 就是 preempt_disable()、rcu_read_unlock() 就是 preempt_enable()、call_rcu(head, func, arg)、synchronize_kernel()。rcu_dereference() 和 rcu_assign_pointer() 还没出生。写者发布指针要自己插 smp_wmb()，读者取指针要自己防编译器重排。一个同步机制把内存序的正确性外包给调用者，抽象就漏了。同一个 synchronize_kernel() 还背了太多语义：它不只等 RCU 读者，还要等 NMI handler 跑完、等所有中断 handler 跑完，一个名字干四件事，调用者根本说不清自己在等什么。

问题四：内存浪费。 struct rcu_head 用双向链表，callback 只需要单向遍历，白白多一个指针；arg 也没必要，rcu_head 基本都嵌在业务结构体里，callback 拿到 struct rcu_head * 用 container_of 就还原了。另一处是 qsctr 加 last_qsctr 两个 long——判 QS 只关心「至少经历过一次没有」，经历 3 次和 5 次没区别，两个 long 干一个 bit 的活。

问题五：curbatch / maxbatch 语义糊。 看名字猜不出谁大谁小、谁等谁。读代码读到 maxbatch 那段，作者的评语是「一个 flag 的事，干嘛搞这么复杂」。它全部作用就是回答一个问题：当前这批过了 GP 之后要不要立刻启动下一批？curbatch == maxbatch 就不启动，不等就启动。这就是 2.6 的 next_pending 标志。

附带一个真 bug：

c
/* 2.5.43，有 bug 的版本 */
if (user ||
    (idle_cpu(cpu) && !in_softirq() && hardirq_count() <= 1))
    RCU_qsctr(cpu)++;

hardirq_count() 返回的是被打断的硬中断嵌套层数移位后的值，不是层数本身。判「不在硬中断里」应该写 hardirq_count() <= (1 << HARDIRQ_SHIFT)。写成 <= 1，而这个函数本身就在 timer 的 interrupt handler 里跑，条件永远不成立，idle 分支整条是死代码。2.6.12 的 rcu_check_callbacks() 里已经是 (1 << HARDIRQ_SHIFT)，对得上。

四、2.6.11 classic RCU 的总体设计 #

2.6.11 是重写不是修补。改法一句话：把「全局的 GP 状态」和「本 CPU 的 QS 状态」彻底分开，让每个 CPU 只读自己的 per-CPU 变量，全局位图只在真正要改的时候碰。

c
/* 2.6.12 */
struct rcu_state {
    spinlock_t  lock;       /* 保护本结构和 rcu_ctrlblk 的写 */
    cpumask_t   cpumask;    /* 还没过 QS 的 CPU */
};

struct rcu_ctrlblk {
    long    cur;            /* 当前正在检测 GP 的批次号 */
    long    completed;      /* 最近一个已完成 GP 的批次号 */
    int     next_pending;   /* 下一批是否已经在等 */
} ____cacheline_maxaligned_in_smp;

struct rcu_head {
    struct rcu_head *next;
    void (*func)(struct rcu_head *head);
};

全局状态搬进 struct rcu_state，只留位图和锁；控制块瘦成三个字段。struct rcu_head 砍掉一半——双向链表变单向，arg 没了，func 的入参改成 struct rcu_head *。省 50% 的定义，也顺手把 callback 的写法定死了：要传参数就把 rcu_head 嵌进自己的结构体，用 container_of 取回来。

per-CPU 数据长出 QS 相关的三个新成员：

c
/* 2.6.12 */
struct rcu_data {
    long                quiescbatch;    /* 本 CPU 正在为哪个批次检测 QS */
    int                 passed_quiesc;  /* 自 GP 起点起至少过了一次 QS */
    int                 qs_pending;     /* 还要等本 CPU 上报 QS */
    long                batch;          /* 本 CPU curlist 那批的批次号 */
    struct rcu_head     *nxtlist, **nxttail;
    struct rcu_head     *curlist, **curtail;
    struct rcu_head     *donelist, **donetail;
    int                 cpu;
};

三个批次号同时活着 #

这是最容易读错的地方。系统里同时存在的批次号最多三个：

名字 存在哪 含义
current rcp->cur 正在检测 GP 的那批
last completed rcp->completed 最近完成 GP 的那批
next pending 各个 rdp->batch 已分配号、还没能启动 GP 的那批

cur 和 completed 最多差 1。next_pending 只有 1 bit，记的是「有没有 pending 批次」，具体号在 CPU 自己的 rdp->batch 里。

为什么是三个？因为「分配批次号」和「启动这批的 GP」是两件事。CPU 把 nxtlist 移进 curlist 时就得有个号，但这时候 cur 那批还没过 GP，新批次只能挂着等。这个号就是 next pending。

rdp->quiescbatch 是第四个概念：本 CPU 正在为哪批检测 QS。它和 rcp->cur 不相等，说明新的一批 GP 已经启动、本 CPU 还没跟上，下一次 tick 要做状态重置。这个比较是整套机制的启动开关：

c
/* 2.6.12，rcu_check_quiescent_state() 开头 */
if (rdp->quiescbatch != rcp->cur) {
    rdp->qs_pending = 1;
    rdp->passed_quiesc = 0;
    rdp->quiescbatch = rcp->cur;
    return;
}

批次号比较不用 a < b，用补码溢出的减法：

c
/* 2.6.12，include/linux/rcupdate.h */
static inline int rcu_batch_before(long a, long b) { return (a - b) < 0; }
static inline int rcu_batch_after(long a, long b)  { return (a - b) > 0; }

批次号一路加下去总会回绕，减法在回绕后依然正确，只要两个号相差不超过半个字长。2.6.12 里两个控制块的初值都是 { .cur = -300, .completed = -300 }，也是考虑这个。

五、宽限期的判定：每个 CPU 都经历过静止状态 #

GP 的判定就是一句话：位图全 0。但这个 0 是谁清出来的、谁负责广播，决定了整套机制能不能扩展。

c
/* 2.6.12 */
static void cpu_quiet(int cpu, struct rcu_ctrlblk *rcp, struct rcu_state *rsp)
{
    cpu_clear(cpu, rsp->cpumask);

    if (cpus_empty(rsp->cpumask)) {
        /* batch completed ! */
        rcp->completed = rcp->cur;
        rcu_start_batch(rcp, rsp, 0);
    }
}

cpu_clear 清自己那位，清完非空就返回等着。清完空了，说明自己就是最后一个过 QS 的 CPU，责任重大：它得把「cur 那批过了」告诉全系统。做法不是发 IPI，是 rcp->completed = rcp->cur——把结果写进一个所有人都读的变量，谁需要谁去看。写完立刻 rcu_start_batch(rcp, rsp, 0) 试着启动下一批；这里传的 next_pending 是 0，意思是「我这次调用不新增 pending 请求」，但如果之前已经有 CPU 把 next_pending 置上了，条件照样成立，下一批就地启动。

c
/* 2.6.12 */
static void rcu_start_batch(struct rcu_ctrlblk *rcp, struct rcu_state *rsp,
                            int next_pending)
{
    if (next_pending)
        rcp->next_pending = 1;

    if (rcp->next_pending && rcp->completed == rcp->cur) {
        /* Can't change, since spin lock held. */
        cpus_andnot(rsp->cpumask, cpu_online_map, nohz_cpu_mask);
        rcp->next_pending = 0;
        /* next_pending == 0 必须先于 cur 的新值对
         * __rcu_process_callbacks() 可见 */
        smp_wmb();
        rcp->cur++;
    }
}

四个动作一个都不能少：位图重置成 cpu_online_map 减掉 nohz_cpu_mask（dynamic tick 下已经停 tick 的 CPU），这是 GP 起点，从这一刻起所有还在跑 tick 的 CPU 都欠一次 QS；next_pending = 0，pending 已经扶正成 current；smp_wmb() 保证 next_pending = 0 对其他 CPU 可见在先、cur 的新值在后；cur++ 就是「新一批 GP 已启动」的广播。

那个屏障为什么要？看另一侧：

c
/* 2.6.12，__rcu_process_callbacks() 里 */
rdp->batch = rcp->cur + 1;
smp_rmb();                      /* 见 rcu_start_batch() 里的 wmb() */
if (!rcp->next_pending) {
    spin_lock(&rsp->lock);
    rcu_start_batch(rcp, rsp, 1);
    spin_unlock(&rsp->lock);
}

CPU A 读 cur（拿到 B 加一之后的新值）算新批次号，然后读 next_pending，smp_rmb() 保证这个读发生在读 cur 之后。如果 A 看到 B 的 cur++，屏障保证 A 也一定看到 B 的 next_pending = 0，于是 A 进 rcu_start_batch 把新批次挂上 pending。少了这个屏障，A 看到新 cur 却看到旧的 next_pending == 1，就会跳过这次启动，新批次一直挂着没人管。

谁把 passed_quiesc 变成位图上的 0 #

中间还隔一层。passed_quiesc 是 per-CPU flag，置位它的人在下一章。把它翻译成「清位图」的是：

c
/* 2.6.12 */
static void rcu_check_quiescent_state(struct rcu_ctrlblk *rcp,
                                      struct rcu_state *rsp,
                                      struct rcu_data *rdp)
{
    if (rdp->quiescbatch != rcp->cur) {
        rdp->qs_pending = 1;
        rdp->passed_quiesc = 0;
        rdp->quiescbatch = rcp->cur;
        return;
    }

    /* GP 对本 CPU 已经完成？查 qs_pending 而不是位图，
     * 就是为了避免 cacheline thrashing。 */
    if (!rdp->qs_pending)
        return;
    if (!rdp->passed_quiesc)
        return;

    rdp->qs_pending = 0;
    spin_lock(&rsp->lock);
    /* CPU 上线期间 quiescbatch / cur 和位图会短暂不同步，忽略 */
    if (likely(rdp->quiescbatch == rcp->cur))
        cpu_quiet(rdp->cpu, rcp, rsp);
    spin_unlock(&rsp->lock);
}

第二个 if 是全部改动的核心：qs_pending 是 per-CPU 变量，读它不产生跨核 cacheline 流量。2.5.43 要靠 test_bit 读全局位图来省事，2.6.11 靠一个本地 flag 省事，代价为零。只有确认要上报了，才进临界区改全局位图。全局写得少，读几乎没有。

六、静止状态（quiescent state）与 QS 上报 #

c
/* 2.6.12，include/linux/rcupdate.h */
static inline void rcu_qsctr_inc(int cpu)
{
    struct rcu_data *rdp = &per_cpu(rcu_data, cpu);
    rdp->passed_quiesc = 1;
}

函数名叫 inc，实际只写一个 1。注释写得很直白：「The counter is a bit degenerated: We do not need to know how many quiescent states passed, just if there was at least one since the start of the grace period. Thus just a flag.」

三处调用点：进程切换，schedule() 里对换下来的 CPU 调 rcu_qsctr_inc(task_cpu(prev))——进程切走了，它必然不在读临界区里，因为读临界区里 preempt_disable() 了，切不动；tick 命中用户态，user 为真说明中断打断的是用户态代码，那会儿内核还没回去，读临界区早出了；tick 命中 idle。

第三处为什么必须存在？设想一个 CPU 长期 idle，没有别的进程可切，schedule() 不执行，tick 每次都命中内核态，user 永远是 0。只靠前两处，这个 CPU 的 passed_quiesc 永远不置位，GP 无限长。

c
/* 2.6.12 */
void rcu_check_callbacks(int cpu, int user)
{
    if (user ||
        (idle_cpu(cpu) && !in_softirq() &&
         hardirq_count() <= (1 << HARDIRQ_SHIFT))) {
        rcu_qsctr_inc(cpu);
        rcu_bh_qsctr_inc(cpu);
    } else if (!in_softirq())
        rcu_bh_qsctr_inc(cpu);

    tasklet_schedule(&per_cpu(rcu_tasklet, cpu));
}

最后那个 tasklet_schedule() 是无条件的。tick 一到就把 tasklet 排上，至于里面有没有活干，由 rcu_pending() 判断。它在 TASKLET_STATE_SCHED 上是幂等的，重复调用只置位不重复排队，所以每 tick 排一次的开销很小。这也解释了为什么 rcu_pending() 要写得那么省——它每个 tick 都被调一次，热路径。

QS 判定条件汇总 #

触发场景 判定条件 覆盖哪套 RCU 落在哪
进程切换 schedule() 执行 classic + bh rcu_qsctr_inc / rcu_bh_qsctr_inc
tick 打断用户态 user != 0 classic + bh rcu_check_callbacks
tick 打断 idle idle_cpu() && !in_softirq() && hardirq_count() <= (1 << HARDIRQ_SHIFT) classic + bh rcu_check_callbacks
tick 不在 softirq 里 !in_softirq() 仅 bh rcu_check_callbacks

bh 那套是 2.6 新增的：读者的临界区全在 softirq 上下文时，用 call_rcu_bh 加 rcu_read_lock_bh()（也就是 local_bh_disable()），QS 条件可以放宽到「跑完一个 softirq handler 就算过」。两套各有自己的控制块，互不干扰：

c
/* 2.6.12 */
struct rcu_ctrlblk rcu_ctrlblk    = { .cur = -300, .completed = -300 };
struct rcu_ctrlblk rcu_bh_ctrlblk = { .cur = -300, .completed = -300 };

static void rcu_process_callbacks(unsigned long unused)
{
    __rcu_process_callbacks(&rcu_ctrlblk, &rcu_state,
                            &__get_cpu_var(rcu_data));
    __rcu_process_callbacks(&rcu_bh_ctrlblk, &rcu_bh_state,
                            &__get_cpu_var(rcu_bh_data));
}

tasklet 里做什么 #

c
/* 2.6.12 */
static void __rcu_process_callbacks(struct rcu_ctrlblk *rcp,
                                    struct rcu_state *rsp,
                                    struct rcu_data *rdp)
{
    if (rdp->curlist && !rcu_batch_before(rcp->completed, rdp->batch)) {
        /* 本 CPU 这批的 GP 过了，整条挂到 donelist 尾巴上 */
        *rdp->donetail = rdp->curlist;
        rdp->donetail = rdp->curtail;
        rdp->curlist = NULL;
        rdp->curtail = &rdp->curlist;
    }

    local_irq_disable();
    if (rdp->nxtlist && !rdp->curlist) {
        rdp->curlist = rdp->nxtlist;
        rdp->curtail = rdp->nxttail;
        rdp->nxtlist = NULL;
        rdp->nxttail = &rdp->nxtlist;
        local_irq_enable();

        rdp->batch = rcp->cur + 1;
        smp_rmb();
        if (!rcp->next_pending) {
            spin_lock(&rsp->lock);
            rcu_start_batch(rcp, rsp, 1);
            spin_unlock(&rsp->lock);
        }
    } else {
        local_irq_enable();
    }

    rcu_check_quiescent_state(rcp, rsp, rdp);

    if (rdp->donelist)
        rcu_do_batch(rdp);
}

顺序不能变：先看旧批次能不能转 donelist，再把 nxtlist 提成 curlist 并分配新批次号，然后处理 QS，最后跑 callback。rcu_do_batch() 放最后是因为它最耗时，前面几步都是簿记。if (rdp->nxtlist && !rdp->curlist) 里没有判断「新批次能不能启动」，rcu_start_batch() 内部会判——这是 2.6 的风格，条件判断集中一处，调用方少操心。

tick 之外还有谁推进 GP #

只有 tick 和进程切换，没有专门的内核线程扫位图。直接后果：GP 的长度以 tick 为粒度。一个 CPU 从「欠 QS」到「上报 QS」，最快下一次 tick，最慢要等它真的发生一次进程切换或进 idle。这就是 idle 判定那条不能少的原因——少一条，GP 时长就没有上界。

七、callback 链表的组织 #

2.6 把 list_head 双向链表换成手工单链表，靠尾指针维护。三条链，每条一个头一个尾，nxttail 不是指向最后一个节点，而是指向最后一个节点的 next 字段的地址：

c
/* 2.6.12 */
void fastcall call_rcu(struct rcu_head *head,
                       void (*func)(struct rcu_head *rcu))
{
    unsigned long flags;
    struct rcu_data *rdp;

    head->func = func;
    head->next = NULL;
    local_irq_save(flags);
    rdp = &__get_cpu_var(rcu_data);
    *rdp->nxttail = head;       /* 接到尾巴上 */
    rdp->nxttail = &head->next; /* 尾巴挪到新节点的 next */
    local_irq_restore(flags);
}

空链时 nxttail = &nxtlist，*nxttail = head 等价于 nxtlist = head，同一个写法处理空链和非空链。这里没有任何锁，只有 local_irq_save()——三条链都是 per-CPU 的，只有本 CPU 碰，唯一要防的是本 CPU 的中断抢进来插一刀，用 irq disable 就够。

链表 装什么 谁往里放 谁往外取
nxtlist 刚 call_rcu 提交、还没有批次号的请求 call_rcu，任意上下文 __rcu_process_callbacks，tasklet 里
curlist 已分配批次号、正在等 GP 的请求 上一步整批搬过来 __rcu_process_callbacks，GP 过后搬去 donelist
donelist GP 已过、等着跑 callback 的请求 上一步整批搬过来 rcu_do_batch，tasklet 里

整批搬运用同一个手法，改指针不改节点：*donetail = curlist 接上尾巴，donetail = curtail 挪尾指针，curlist = NULL 清空，curtail = &curlist 回到空链状态。donelist 之所以存在，是因为单轮有数量上限：一批跑不完，剩下的留在 donelist 里，再 tasklet_schedule() 一次，下个 tick 接着跑。

c
/* 2.6.12 */
static void rcu_do_batch(struct rcu_data *rdp)
{
    struct rcu_head *next, *list;
    int count = 0;

    list = rdp->donelist;
    while (list) {
        next = rdp->donelist = list->next;
        list->func(list);
        list = next;
        if (++count >= maxbatch)
            break;
    }
    if (!rdp->donelist)
        rdp->donetail = &rdp->donelist;
    else
        tasklet_schedule(&per_cpu(rcu_tasklet, rdp->cpu));
}

跑满 maxbatch（默认 10）个就收工，剩下的重新排 tasklet。2.5.43 的实时性问题在这里有了答案：把一个不可中断的长操作切成每 tick 一小片。每片 10 个是写死的常量，高负载下偏小——这个问题 2.6.23 用三个旋钮解了，第十章说。

八、call_rcu 的完整流程 #

把上面几节串起来走一遍。假设双 CPU，初始状态：

text
                    全局                CPU0                  CPU1
    cur          5        quiescbatch  5     passed_quiesc 1   0
    completed    4        qs_pending   0     batch         5   5
    next_pending 0        curlist   (==)     curlist   (===)

批次 5 正在检测 GP，批次 4 已完成，没有 pending。CPU0 已上报过 QS，CPU1 还没，两边的 curlist 里都有批次 5 的请求。

第一步：CPU0 的 tick，什么都不做 #

c
/* 2.6.12 */
static inline int __rcu_pending(struct rcu_ctrlblk *rcp, struct rcu_data *rdp)
{
    /* 本 CPU 有请求，且 GP 已经过了 → 要搬到 donelist */
    if (rdp->curlist && !rcu_batch_before(rcp->completed, rdp->batch))
        return 1;
    /* 没有在途批次，但有新请求 → 要分批次号 */
    if (!rdp->curlist && rdp->nxtlist)
        return 1;
    /* donelist 里有活要干 */
    if (rdp->donelist)
        return 1;
    /* 内核在等本 CPU 的 QS，或者新批次已启动而本 CPU 没跟上 */
    if (rdp->quiescbatch != rcp->cur || rdp->qs_pending)
        return 1;
    return 0;
}

对着快照逐条：completed = 4 而 batch = 5，rcu_batch_before(4, 5) 为真，取反为假，第 1 条不成立；curlist 非空，第 2 条不成立；donelist 空；quiescbatch == cur 且 qs_pending == 0。返回 0。这就是 2.6.11 相对 2.5.43 最直接的收益：没有 RCU 活干的 tick，判断过程只读 per-CPU 变量加两个全局 long，不碰位图。

第二步：CPU1 进程切换，然后 tick #

schedule() 里调 rcu_qsctr_inc(task_cpu(prev))，CPU1 的 passed_quiesc 变成 1。下一个 tick __rcu_pending() 第 4 条成立，进 __rcu_process_callbacks()。前面两步都不满足（completed < batch，curlist 非空），只走到 rcu_check_quiescent_state() 的后半段：qs_pending 置 0，拿锁，quiescbatch == cur 成立，调 cpu_quiet()。

cpu_quiet() 清掉 CPU1 那位，位图空了，completed 从 4 跳到 5，再 rcu_start_batch(rcp, rsp, 0)——因为 next_pending == 0，没有新批次可启动，直接返回。GP 过了，但两边的 curlist 都还没搬，搬迁要等各自的 tick。

第三步：CPU0 来新请求，然后 tick #

新 head 挂进 CPU0 的 nxtlist，没批次号，不参与 GP 检测。这次 tick __rcu_pending() 第 1 条成立（completed = 5、batch = 5，rcu_batch_before(5, 5) 为假，取反为真），开头那段先把 curlist 搬到 donelist，curlist 空出来，接着 nxtlist 提成 curlist，分配 rdp->batch = rcp->cur + 1 = 6。

因为 next_pending 还是 0，进 rcu_start_batch(rcp, rsp, 1)：先置 next_pending = 1，然后 completed == cur（5 == 5）成立，位图重置、next_pending 清 0、cur++。批次 5 刚完成，批次 6 又新鲜出炉，就地扶正。这次 tick 的最后，donelist 非空，rcu_do_batch() 跑掉最多 10 个 callback。

text
    cur 6   completed 5   next_pending 0
    CPU0: quiescbatch 6  passed_quiesc 0  qs_pending 1  batch 6  curlist (**)  donelist (==)
    CPU1: quiescbatch 5  passed_quiesc 1  qs_pending 0  batch 5  curlist (===)

容易读错的点：CPU1 的 batch 还是 5、curlist 里还是批次 5 的请求，但批次 5 的 GP 早就过了，只是 CPU1 还没在自己的 tick 里搬。 全局 cur 已经是 6，不影响批次 5 的处理，因为搬迁判定用的是 completed 和 rdp->batch，不是 cur。

第四步：CPU1 的 tick，然后新请求 #

completed = 5、rdp->batch = 5，第 1 条成立，curlist 搬到 donelist。rcu_check_quiescent_state() 发现 quiescbatch(5) != cur(6)，重置本地状态：passed_quiesc = 0、qs_pending = 1、quiescbatch = 6。此时 batch = 5 已经没有意义——curlist 空，不存在「在途批次」。

之后 CPU1 来新请求，下一次 tick 里 nxtlist 提成 curlist，batch = rcp->cur + 1 = 7。但这次 completed(5) != cur(6)，批次 6 的 GP 还没过，rcu_start_batch() 里那个 if 不成立，7 号只能挂着，next_pending 置 1。系统里同时存在三个批次：6 是 current（检测中），5 是 last completed，7 是 pending。这就是第四章那张表的具体形态。

第五步：批次 6 的 GP 过去 #

最后过 QS 的 CPU 在 cpu_quiet() 里做 completed = 6，然后 rcu_start_batch(rcp, rsp, 0)。这次 next_pending 已是 1，completed == cur 也成立，7 号立刻扶正，cur 变 7。

一个批次跑完下一个自动接上，全程没有 IPI，没有专门的 GP 线程。所有协调都通过 cur、completed、next_pending 三个格子加上每 CPU 的 qs_pending 完成。

九、rcu_check_callbacks 与软中断的配合 #

rcu_check_callbacks() 在 tick handler 里被调用，是整套机制的心跳。它做两件事：给 QS 记账，然后无条件排 tasklet。代码在第六章，这里只说它跟软中断的配合。

call_rcu_bh() 的语义是「读侧临界区在 softirq handler 结束时就结束」，对应 rcu_read_lock_bh() 展开成 local_bh_disable()。

一旦读者用 bh 版本，QS 判定可以放宽：不需要等进程切换，只要当前不在 softirq 里，就说明之前那些 softirq handler 已经跑完，它们对应的读临界区自然结束。看最后的 else if (!in_softirq())：tick 不打断 softirq，说明排队都跑干净了，rcu_bh_qsctr_inc(cpu) 成立。而 classic 那一路只在 user 或 idle 时记账。两套 RCU 各有自己的 rcu_ctrlblk、rcu_state、rcu_data，rcu_process_callbacks() 一次 tasklet 里把两套都跑一遍（代码见第六章）。

这也是 2.6.11 新增的两项能力之一：CPU HOTPLUG 支持（rcu_offline_cpu() 把离线 CPU 的三个链表搬到当前 CPU，并替它 cpu_quiet()，否则 GP 会永远等一个不会上报的 CPU），以及 softirq 上下文的 QS 判定。

十、classic RCU 的局限：只能保护不可睡眠的读侧 #

整套 classic RCU 的正确性压在一个假设上：读侧临界区里不会阻塞。

这个假设被用在两个地方，缺一不可：rcu_read_lock() 就是 preempt_disable()，读侧不可抢占，进程被换出去的时候一定不在读临界区里；passed_quiesc 的置位靠进程切换，切走了 → 不在临界区 → 这个 CPU 过了 QS。

一旦允许读侧睡眠，两条同时失效：进程在临界区里主动睡眠让出 CPU，schedule() 照样执行，passed_quiesc 照样置位，但进程还没走完临界区。写者以为安全了，把旧版本释放了，读者醒来访问的就是已释放内存。所以 2.6.11 的 rcu_read_lock() 注释里那句「It is illegal to block while in an RCU read-side critical section」不是建议，是正确性前提。

在 2.6.11 上写「读侧需要睡眠」的场景只有几条路，都不好走：把需要睡眠的部分挪出临界区——而带出去引用就需要引用计数，绕回自己；整段改成 mutex——写少读多的场景性能塌下来；拆成「临界区内只取指针 + 临界区外自己保证生命周期」——等于自己发明一套 RCU 变种。

这个矛盾在 realtime 场景里最尖锐。realtime 内核要求所有不可抢占的临界区尽量短，spinlock 的临界区为此改成可抢占的（只保留 raw spinlock 不可抢占）。RCU 的读临界区如果还坚持不可抢占，就成了这套改造里剩下的硬块。

顺带：2.6.23 还修了 classic 的其余毛病 #

修了 rcu_start_batch() 里的竞态。 2.6.12 的写法是 cpus_andnot() → next_pending = 0 → smp_wmb() → cur++。读 nohz_cpu_mask 在 cur++ 之前，这两步之间如果某个 CPU 进了 idle 并停了 tick，它会被算进 cpumask，但它根本不跑 tick，也就不会上报 QS，GP 被白白拖长。2.6.23 把 cpus_andnot 挪到 cur++ 之后并补一个 smp_mb()：

c
/* 2.6.23 */
rcp->cur++;
smp_mb();
cpus_andnot(rcp->cpumask, cpu_online_map, nohz_cpu_mask);
rcp->signaled = 0;

顺便去掉了 rcu_start_batch() 的 next_pending 参数，改由调用者自己置位。同时把 rcu_ctrlblk 和 rcu_state 合了——两个结构一起看才有意义，分开只让参数传递变长。2.6.23 里 cpumask 和 lock 直接进了 rcu_ctrlblk，初始化写成 { .cur = -300, .completed = -300, .lock = __SPIN_LOCK_UNLOCKED(&rcu_ctrlblk.lock), .cpumask = CPU_MASK_NONE }。

给 callback 加了水位控制。 2.6.11 的 maxbatch = 10 是死的，2.6.23 换成三个旋钮，blimit 是每轮 tasklet 跑多少个，qhimark 是队列上限水位，qlowmark 是下限：

c
/* 2.6.23 */
static int blimit = 10;
static int qhimark = 10000;
static int qlowmark = 100;

/* call_rcu 尾部 */
if (unlikely(++rdp->qlen > qhimark)) {
    rdp->blimit = INT_MAX;
    force_quiescent_state(rdp, &rcu_ctrlblk);
}

/* rcu_do_batch 尾部 */
if (rdp->blimit == INT_MAX && rdp->qlen <= qlowmark)
    rdp->blimit = blimit;

per-CPU 的 qlen 记账，每提交一个 callback 加一、跑一个减一。超上限就双管齐下：blimit 提到 INT_MAX（不再限制单轮跑多少），同时 force_quiescent_state() 逼所有 CPU 快点过 QS——本 CPU set_need_resched()，其他 CPU 发 reschedule IPI（smp_send_reschedule()，用 rcp->signaled 防止重复发）。qlen 回落到 qlowmark 以下，blimit 复位。这是自适应：平静时每轮 10 个保证调度延迟，积压时放开限制并加速 GP，保证不爆内存。

加了 rcu_barrier()。 synchronize_rcu() 只保证 GP 过了，不保证 callback 跑完了。模块卸载和文件系统 umount 必须等 callback 真正执行完——callback 里还要操作这个模块或 super block。做法是每 CPU 一个专用的 rdp->barrier head：

c
/* 2.6.23 */
static void rcu_barrier_func(void *notused)
{
    int cpu = smp_processor_id();
    struct rcu_data *rdp = &per_cpu(rcu_data, cpu);

    atomic_inc(&rcu_barrier_cpu_count);
    call_rcu(&rdp->barrier, rcu_barrier_callback);
}

给每个 CPU 塞一个 barrier callback，用原子计数跟踪执行完的个数，减到 0 就 complete()。等在 wait_for_completion() 上的调用者醒来，说明调用那一刻之前提交的所有 callback 都跑完了。

十一、2.6.23 sleepable RCU 的设计动机 #

SRCU 全称 sleepable RCU，名字就说明了它要干什么：读侧临界区里可以睡眠。一放开这个口子，classic RCU 的两根支柱全断。所以直觉上 SRCU 不能实现，两个理由听起来都成立：读侧一睡眠 GP 就没上界，系统怎么受得了；进程切换判定 QS 的机制直接失效。那为什么还做？因为 realtime 的需求压过来了（上一章末尾）。当所有不可抢占临界区都要变短的时候，RCU 的读侧不能豁免。

既然必须做，先得解决「GP 会很长」这个副作用。2.6.23 的解法两条，都很干脆。

不给异步接口。 只有 synchronize_srcu()，没有 call_srcu()。理由值得记：如果提供 call_srcu()，任何线程都能在循环里提交任意多个 callback，GP 一长队列就失控。而同步接口会阻塞当前线程，一个线程在任一时刻最多一个请求在途，提交速率被线程数天然限住。

GP 细分到子系统。 classic RCU 只有一个全局 GP，一个子系统里某个读者卡住，全系统的 callback 都跟着等。SRCU 允许每个使用方有自己的 struct srcu_struct，各自独立算 GP：一个读者卡住只影响它所属那一个 srcu_struct，副作用是使用方要自己管生命周期。

c
/* 2.6.23，include/linux/srcu.h */
int init_srcu_struct(struct srcu_struct *sp);
void cleanup_srcu_struct(struct srcu_struct *sp);
int srcu_read_lock(struct srcu_struct *sp) __acquires(sp);
void srcu_read_unlock(struct srcu_struct *sp, int idx) __releases(sp);
void synchronize_srcu(struct srcu_struct *sp);
long srcu_batches_completed(struct srcu_struct *sp);

srcu_read_lock() 带返回值，返回的 idx 必须原样传给对应的 srcu_read_unlock()。这是 SRCU 最反直觉的一处，也是它比 classic RCU 贵的根源，下一章讲。

分工上别混：classic RCU 读侧极轻，可以用在中断上下文、NMI 上下文；SRCU 读侧要做 per-CPU 计数，srcu_read_lock() 里带 preempt_disable()，2.6.23 的实现明确要求从进程上下文调用，synchronize_srcu() 更是会睡眠。SRCU 填的是「读侧需要睡眠」这个空档，不是替换 classic RCU。

十二、SRCU 的 per-srcu_struct 计数 #

c
/* 2.6.23，include/linux/srcu.h */
struct srcu_struct_array {
    int c[2];
};

struct srcu_struct {
    int completed;
    struct srcu_struct_array *per_cpu_ref;
    struct mutex mutex;
};

三个字段各管一件事：completed 是 GP 编号，同时它的 LSB 决定当前用 c[0] 还是 c[1]；per_cpu_ref 是 per-CPU 计数器数组，每个 CPU 两个 int；mutex 串行化 synchronize_srcu()。

c[2] 这两个槽位是 SRCU 的全部秘密，轮换使用：completed 是偶数，c[0] 是 current（正在等待清零的那轮），c[1] 是 next pending；completed 是奇数则反过来。

为什么不只用一个计数器？因为一个计数器没法区分「新读者」和「旧读者」。synchronize_srcu() 要等的是「调用那一刻之前进入的读者」，之后进入的不该算进来。混在一起永远等不到 0。两个槽轮换，等 current 槽清零，新读者都进了 next 槽，互不干扰。

c
/* 2.6.23，kernel/srcu.c */
int srcu_read_lock(struct srcu_struct *sp)
{
    int idx;

    preempt_disable();
    idx = sp->completed & 0x1;
    barrier();  /* 确保编译器只读一次 sp->completed */
    per_cpu_ptr(sp->per_cpu_ref, smp_processor_id())->c[idx]++;
    srcu_barrier(); /* 确保编译器不会把临界区重排到计数之前 */
    preempt_enable();
    return idx;
}

三个细节。preempt_disable() 只包住计数，不包住整个临界区——这是 SRCU 和 classic RCU 最本质的区别。classic 的 rcu_read_lock() 本身就是 preempt_disable()，整段临界区不可抢占；SRCU 的计数做完就把抢占打开了，临界区里该睡就睡。preempt disable 在这里只保证「取 idx — 计数 — 记录当前 CPU」这三步原子，不被迁移到别的 CPU 上。barrier() 保证 completed 只读一次。没有它，编译器读两次，一次算 idx、一次干别的；两次之间 completed 若被 synchronize_srcu() 改了，算出的 idx 就和实际加一的槽位对不上。

srcu_barrier() 的作用随配置变：

c
/* 2.6.23 */
#ifndef CONFIG_PREEMPT
#define srcu_barrier()  barrier()
#else
#define srcu_barrier()
#endif

不可抢占内核下退化成编译器屏障；可抢占内核下定义为空，因为编译期重排已被依赖挡住，运行期重排由硬件内存模型保证。这个定义对弱序架构是否成立，我没找到 2.6.23 当时的论证，标为未验证。

c
/* 2.6.23 */
void srcu_read_unlock(struct srcu_struct *sp, int idx)
{
    preempt_disable();
    srcu_barrier();
    per_cpu_ptr(sp->per_cpu_ref, smp_processor_id())->c[idx]--;
    preempt_enable();
}

它减的是 c[idx]，idx 是 srcu_read_lock() 返回的那个值，不是重新算的。源码注释写得很清楚：

Removes the count for the old reader from the appropriate per-CPU element of the srcu_struct. Note that this may well be a different CPU than that which was incremented by the corresponding srcu_read_lock().

为什么必须是返回值？因为临界区里会睡眠，醒来已在别的 CPU 上；更关键的是，临界区里调了 synchronize_srcu() 把某个别的 srcu_struct 的 completed 加了，GP 编号变了。这时重新算 completed & 0x1 会选错槽位，减到不该减的地方去。idx 就是「你进入时用的是哪个槽」的凭据，跨睡眠、跨 CPU 迁移都成立。

计数之所以 per-CPU，是因为 srcu_read_lock() 在热路径上。一个全局计数器的话，所有 CPU 都在同一个 cacheline 上加加减减，CPU 一多就废。per-CPU 数组每个 CPU 独占一个 srcu_struct_array（两个 int 共 8 字节），没有跨核争用。代价是 synchronize_srcu() 要遍历所有 CPU 求和：

c
/* 2.6.23 */
static int srcu_readers_active_idx(struct srcu_struct *sp, int idx)
{
    int cpu, sum = 0;

    for_each_possible_cpu(cpu)
        sum += per_cpu_ptr(sp->per_cpu_ref, cpu)->c[idx];
    return sum;
}

求和不是原子的，源码注释明说了「this is not an atomic primitive, and can therefore suffer severe errors when invoked on an active srcu_struct」。它只适合 GP 判定这种「反复采样直到为 0」的场合。srcu_readers_active() 把两个槽加起来，只在 cleanup_srcu_struct() 里做泄漏检查。

十三、synchronize_srcu 与宽限期判定 #

这是 SRCU 里最需要小心的函数。

c
/* 2.6.23 */
void synchronize_srcu(struct srcu_struct *sp)
{
    int idx;

    idx = sp->completed;
    mutex_lock(&sp->mutex);

    /* 有人替我们干完了？
     * 我们需要计数器走 -两- 步，不是一步。 */
    if ((sp->completed - idx) >= 2) {
        mutex_unlock(&sp->mutex);
        return;
    }

    synchronize_sched();    /* 在所有 CPU 上强制内存屏障 */

    idx = sp->completed & 0x1;
    sp->completed++;

    synchronize_sched();    /* 在所有 CPU 上强制内存屏障 */

    while (srcu_readers_active_idx(sp, idx))
        schedule_timeout_interruptible(1);

    synchronize_sched();    /* 在所有 CPU 上强制内存屏障 */

    mutex_unlock(&sp->mutex);
}

数一下，是三轮 synchronize_sched() 夹一轮轮询，每轮都有不可替代的作用。

第一轮（翻槽之前）：保证「任何看到新 completed 的 CPU，也能看到本 CPU 在此之前做的所有数据结构改动」。没有它，别的 CPU 把它读临界区里的访存重排到 srcu_read_lock() 之前，读到的就是一个还没发布完的版本。

翻槽：idx = sp->completed & 0x1 取出 current 槽，sp->completed++ 让后进来的 srcu_read_lock() 都用另一个槽。翻完之后 current 槽里的计数只减不增。

第二轮（翻槽之后）：保证所有用旧槽的 srcu_read_lock() 调用本身都执行完了。注意这里保证的是「原语执行完」，不是「临界区执行完」——两者差得远，临界区还在睡。但计数已经加上了，所以后面能等到。

轮询等清零：反复读 current 槽的和，非 0 就 schedule_timeout_interruptible(1) 睡一个 jiffy 再来。「等读者走完」就发生在这里。

第三轮（解锁之前）：强制那些和轮询同时进行的 srcu_read_unlock() 执行完。更要紧的是，它顺带保证了对应的读临界区也执行完、引用也放掉了。

常见的说法是「synchronize_srcu 两轮等待」，对不上 2.6.23 源码——代码注释里那个「两轮」说的是 completed 要走两步（见下一节），跟这里的三轮不是一回事。实际是三段 synchronize_sched() 加一轮轮询。

那个 - 2 的判断 #

idx 是拿锁之前读的 completed，所以 completed - idx 是「等锁的这段时间里别人把 GP 推进了几步」。为什么要 2 步不是 1 步？源码注释解释得很细：

We need -two- advances of the counter, not just one. If there was but one, we might have shown up -after- our helper's first synchronize_sched(), thus having failed to prevent CPU-reordering races with concurrent srcu_read_unlock()s on other CPUs.

如果只要 1 步，我们是在别人的第一轮 synchronize_sched() 之后才出现的，那样就漏掉了它提供的那层保护，没法阻止别的 CPU 把 srcu_read_unlock() 重排到临界区之前。注释还给了替代方案：把 2 改成 3 也能保证正确，但批量场景下延迟会变大，所以选了现在这个。

第三轮为什么必须留在 mutex_unlock() 之前？注释专门强调了一整段。假设允许提前退出的路径在解锁之后才做 synchronize_sched()：某个 CPU 上的 srcu_read_unlock() 刚执行过 c[idx]--；我们的 srcu_readers_active_idx() 检查在它之后，看到 0，以为安全了；但那个 CPU 把这条 srcu_read_unlock() 重排到了某个临界区之后，实际上还有一个读者在用旧数据；我们这边释放内存，那边正在访问。第三轮把这种重排全掐掉。

维度 classic RCU（2.6.11/2.6.12） SRCU（2.6.23）
GP 的载体 全局 rcu_ctrlblk.cur / completed 每个 srcu_struct.completed
读者是否被计数 不计数，只看 CPU 是否过了 QS 每 CPU 两个计数器，进临界区加一
判定「读者走完」 位图全 0（每 CPU 上报一次 QS） 遍历所有 CPU 求 current 槽的和，为 0 则过
异步 callback 有（call_rcu → tasklet） 没有，只有同步 synchronize_srcu()
谁来推进 tick + 进程切换 synchronize_srcu() 自己轮询
GP 时长上界 一个 tick 到几个 tick 取决于最慢的读者，可以到秒级
调用上下文 任意 进程上下文

最本质的差别在两行：classic 判断的是「CPU 有没有离开过读侧」，SRCU 判断的是「计数器有没有归零」。前者不需要知道读者是谁，后者必须计数。

十四、SRCU 的代价：为什么它比 classic RCU 慢 #

读侧多了几次操作。 classic 的 rcu_read_lock() 在不可抢占内核下零条指令；SRCU 的 srcu_read_lock() 至少要 preempt_disable()、读 completed、算 idx、c[idx]++、preempt_enable()。多出来的还有一个写动作——写本 CPU 的计数器，虽然不跨核，但也是一次 store。外加 idx 要一路活到 srcu_read_unlock()，宿主的寄存器分配压力上去了，编译器会在别处 spill。

每个 srcu_struct 一份 per-CPU 数组。 for_each_possible_cpu() 个 srcu_struct_array，每个 8 字节。CONFIG_NR_CPUS 大的机器上，一个 srcu_struct 就是几百字节，子系统多了这个数会堆起来。synchronize_srcu() 的等待还是轮询。 睡一个 jiffy 醒来遍历所有 CPU 求和，CONFIG_HZ=250 就是 4ms 一个周期，CONFIG_HZ=100 就是 10ms。读者少的时候这个粒度太粗——GP 明明已经过了，还要多睡最多一个 jiffy。外加三轮 synchronize_sched()，每次都是一轮全局 QS 等待，虽然比 classic 的完整 GP 轻，但也不是免费。

所以 2.6.23 的定位很清楚：SRCU 是给「确实需要睡」的场景用的，不是 classic RCU 的升级版。 能用 classic 的地方别用 SRCU。

十五、RCU 与引用计数的关系：不是一回事 #

这一节压的是 perfbook 第 9.3 节的几小节（9.3.3.2 到 9.3.3.4）。原文论证很长，结论就三句话。

它是「受限的引用计数」 #

perfbook 9.3.3.2 的标题是「RCU is a Restricted Reference-Counting Mechanism」。论点用两段代码就说完：

c
/* perfbook 9.3.3.2 的示例 */
rcu_read_lock();                  /* 获取引用 */
p = rcu_dereference(head);
/* 用 p 干活 */
rcu_read_unlock();                /* 释放引用 */

spin_lock(&mylock);               /* 写侧照样能安全删 */
p = head;
rcu_assign_pointer(head, NULL);   /* 断掉后来者的获取路径 */
spin_unlock(&mylock);
synchronize_rcu();                /* 等已获得的引用全部释放 */
kfree(p);

在 rcu_dereference() 之后才开始的 GP，必须等你走到 rcu_read_unlock() 才能结束。「受限」在两处：读侧不能阻塞；临界区不能从一个任务交给另一个任务。和传统引用计数的本质差别：没有人真的在记账。 rcu_read_lock() 不碰任何计数器，写侧也没有一个地方能读出「现在有几个读者」。所谓「引用」是逻辑上的，由「GP 不会在读者走完之前结束」这条性质保证出来。

它是「批量引用计数」 #

perfbook 9.3.3.3 接着讲。传统引用计数是 per-object 的：一个结构体嵌一个 atomic_t，谁持有谁加一。问题是如果要给一大堆各不相同的结构体维护一个全局计数器，那条 cacheline 会在核间来回弹，性能崩掉。RCU 反过来：读侧太轻，轻到可以给「一大批数据结构」共用同一套保护而不付代价。这就是 bulk reference-counting。

这一节还给了一个 SRCU 的适用边界：单个任务跨一段会阻塞的代码持有一个引用，交给 SRCU 处理。而「引用从一个任务传给另一个任务」的场景（发起 I/O 时取引用、在完成中断里放引用）SRCU 盖不住——理论上能改，实际上权衡没算清。同节还列了 SRCU 自身的两条限制：srcu_read_lock() 的返回值必须传给对应的 srcu_read_unlock()；SRCU 原语不能在硬中断和 NMI handler 里调用。

维度 传统引用计数 classic RCU SRCU
读者是否写共享状态 是，原子加一 否 是，per-CPU 计数
读者开销 一次原子 RMW 0（不可抢占内核） 一次 preempt 开关 + 一次 store
cacheline 争用 有，集中在一个 counter 上 无 无，计数 per-CPU
能否保护任意多个对象 每个对象一个 counter 一套机制保护任意多对象 同左，但要按子系统分 srcu_struct
读者能否睡眠 能 不能 能
引用能否跨任务传递 能 不能 不能（2.6.23 的实现）
谁来定何时释放 计数归零 写侧调 synchronize_rcu / call_rcu 写侧调 synchronize_srcu

一句话收口：RCU 用「等一段时间」换掉了「记一个数」。它不是引用计数的变种，是把「谁还在用」这个问题从空间（计数器）搬到了时间（宽限期）。perfbook 9.3.3.4 还专门批了「RCU 像垃圾回收器」这个比喻：GC 要扫描找出不可达对象，RCU 不扫描、不判断可达性，它只是等。写侧自己决定什么时候释放、释放什么，RCU 只提供「现在安全了」这个时间点。

十六、从 2.6 到现代：这个实现后来怎么变的 #

2.6.11 这套东西的命运一句话：结构留下来了，位图被换掉了。 下面这些版本号里，能确认的写版本，不确定的标未验证。

位图方案撑不住 #

rcu_state.cpumask 是一个 cpumask_t。CPU 数一多问题回来了：每次 GP 起点要 cpus_andnot() 遍历整个位图，每次 GP 结束要 cpus_empty() 判一遍，位图本身占的 cacheline 数随 CPU 数线性增长。4096 核的机器上一个 GP 要扫 64 个 long。这不是理论担忧，是 SGI 那类大机器上的实测问题。

替代方案把「所有 CPU 一个位图」改成「一棵树，叶子是一小组 CPU」：每个内部节点只管它下面那一小撮，聚合上报，根节点空了才算 GP 过。这就是 tree RCU（rcu_node 树）。引入时间在 2.6.16 前后（未验证具体 commit），和 classic 版本并存过一段时间，用 CONFIG_CLASSIC_RCU / CONFIG_TREE_RCU 二选一，后来前者被删掉，只剩 tiny 和 tree 两个实现——tiny 给 UP 和小型 SMP，tree 给其余。「每个 CPU 上报 QS」这一条 tree RCU 保留了，只是上报粒度从「全局位图的一位」变成「叶子节点的一位，然后逐层合并」。

可抢占 RCU：classic 那条假设被正面拆开 #

第十章说 classic RCU 依赖「读侧不可抢占」。realtime 的需求把这条件去掉了，于是需要一套在读侧可抢占时依然正确的 RCU。做法是把「不计数、只看 CPU 过没过 QS」换掉，改成显式跟踪被抢占的读者：读侧进入时记 rcu_read_lock_nesting，如果在临界区里被抢占，把任务挂到一个 per-CPU 链表上，GP 要等这些任务都被恢复并退出临界区。这套叫 RCU-preempt，CONFIG_PREEMPT_RCU，进了主线（2.6.26 前后，未验证具体版本）。

它和 SRCU 的关系：两者都允许读侧睡眠，但 RCU-preempt 只允许被抢占，不允许读者主动 schedule()。要主动睡，还是得 SRCU。

SRCU 本身也在变 #

2.6.23 的做法 后来的做法 为什么改
synchronize_srcu() 用 schedule_timeout_interruptible(1) 轮询 改成等待队列 / completion，读者退出时唤醒 轮询粒度最差一个 jiffy（4~10ms），白等
每个 srcu_struct 一份扁平 per-CPU 数组 引入 srcu_node 树和 per-CPU 的 srcu_data CPU 数大时 for_each_possible_cpu 求和太贵
GP 状态就是一个 int completed 加上 sequence counter 与状态机 支持更复杂的并发与 NMI 场景

现代内核里 srcu_read_lock() 仍然返回 idx，仍然要传给 srcu_read_unlock()——这条接口约束从 2.6.23 至今没变，它已经不是实现细节，是 API 契约。

classic 那套里活下来的东西 #

即使位图没了，2.6.11 定下的几个概念一直用到现在。

三态批次：cur / completed / next_pending 对应现代的 gp_seq 和一批状态位，语义没变——分配批次、启动 GP、广播完成是三件不同的事。

per-CPU 判断优先：先读本地变量决定要不要干活，只在必须改全局时才进临界区。这条是 2.6.11 相对 2.5.43 最大的改进，现在的 RCU 仍照这个原则写。

callback 分批执行加水位数控制：2.6.23 的 blimit / qhimark / qlowmark 演化成现代的 qhimark / qlomark 加 per-CPU callback 链表。

rcu_barrier()：2.6.23 加的那个接口至今还在，语义没动过。
