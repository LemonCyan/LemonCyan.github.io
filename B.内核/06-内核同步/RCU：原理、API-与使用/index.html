一、RCU 要解决的问题：读多写少场景下的免锁读 #

先算锁的账。

spinlock 保护临界区靠 next 和 owner 两个共享变量。线程调 spin_lock 进临界区，动作三步：取自己的号码牌（next 当前值）并读允许进入的那张牌（owner）；把 next 加一写回；判断自己的牌等于 owner 就进，不等就自旋重读 owner（ARM64 上可用 WFE 降功耗）。取值和更新写回必须是原子操作，中间不能插进任何东西。spin_unlock 离开临界区，做一次 owner++。

麻烦出在缓存行。CPU0 操作 lock，其他 CPU 的 L1 里那份 lock 全部失效，随后它们访问 lock 就是 communication cache miss，得从下一级 cache 取；反过来，它们取到新值又让 CPU0 的副本失效。核数越多，这一行抢得越凶。

RW spinlock 和 seqlock 走同一条路：都基于内存里一个共享变量，靠对该变量的原子访问仲裁。只要读侧要碰它，读侧就得吃缓存一致性流量。RCU 把这件事绕过去：读侧压根不访问那个共享变量。

素材 6 引了一张 700MHz 奔腾 II 上的基本操作开销表，并指出在 1.8GHz 至强上原子加指令的开销反而慢 5ns，虽然主频快了两倍多。原因不难推：锁的获取开销跟访存延迟绑在一起，而 CPU 和存储器之间的速度差越拉越大。同一份素材给出的锁扩展性对比（4 CPU 场景，按原文表述）：

机制 相对理论性能 备注
引用计数 refcnt 约 5% 单个原子变量，扩不起来
rwlock 约 9% 2 CPU 时性能还不如 1 CPU
spinlock 约 57% 明显好于前两者，仍然掉一半
brlock（Big Reader Lock） 接近线性扩展 读者开销低，写者开销极大
RCU 读侧不碰共享计数器 读侧开销与核数脱钩

brlock 由 Red Hat 的 Ingo Molnar 实现，读者开销低、写者开销极大；它只为少数几个锁预定了位置，用户没法随便定义，还要为每个 CPU 准备一份锁状态数组，所以只用在少数特定位置。

1.1 适用场景的四条限制 #

RCU 不是 rwlock 的通用品，使用面窄得多。素材 1 列了四条，一条都不能省：

限制 含义 违反的后果
只能保护动态分配的数据结构 结构必须由指针访问，读者通过指针拿到它 栈上或内嵌的静态对象没法延迟释放
读侧临界区里不能睡眠 一睡眠，宽限期判定的前提被破坏 系统进入不稳定状态
读写不对称 写侧性能没有硬要求，读侧要求极高 写多的场景写侧开销白付
读者对拿到新数据还是旧数据不敏感 允许一段窗口内看到旧版本 需要强一致的场景用不了

它落在这几处：路由表查询与更新、设备状态表维护、系统调用审计规则表、SELinux 的 AVC、dcache、System V IPC、多径 I/O 的设备维护。共同点是遍历远多于改。

二、RCU 的核心契约：读侧不阻塞、写侧延迟释放 #

RCU 涉及两种数据：指向被保护数据的指针（RCU protected pointer），和指针指向的共享数据（RCU protected data，必须动态分配）。角色有两种：reader 和 writer。

对传统锁而言，reader 在临界区里访问数据时 writer 就进不来；writer 直接改 data 会破坏 reader 正在看的内容。拆掉这个耦合只有一条路：让 reader 先把活儿干完。RCU 的做法是给 reader 一份永远不被就地修改的数据。

2.1 读侧：rcu_read_lock 根本不是锁 #

rcu_read_lock() 名字里带 lock，实际不做互斥。4.x 的 classic RCU 路径上它是这样（素材 5 引的 <include/linux/rcupdate.h>）：

c
static inline void rcu_read_lock(void)
{
        __rcu_read_lock();
        __acquire(RCU);
        rcu_read_acquire();
}

三个调用里只有第一个干活，其余两个是给 sparse 和 lockdep 看的注解。真正的工作是关内核可抢占性：__rcu_read_lock() 里只有 preempt_disable()，__rcu_read_unlock() 里只有 preempt_enable()。中间允许中断。这就是全部。

读侧不写任何全局计数，不碰写者状态，也不与其他读者争抢同一个变量。reader 之间、reader 与 writer 之间都没有缓存行交互——这是 RCU 读侧便宜的根源。

一个后果要记住：既然它只关抢占，就拦不住中断。读者刚取到指针 p、还没访问 p 里的成员时来了中断，ISR 要改 p 指向的数据，按 RCU 规则它会新分配 new_p、拷贝、在 new_p 上改、把 new_p 赋给 p、注册回调延迟释放旧的 p。中断返回后，被中断的进程继续用旧 p 的数据，这是 RCU 明确允许的。

2.2 写侧：removal 与 reclamation 必须分两步 #

写者的动作拆成两半，中间夹着一段等待。

第一步 removal。 writer 分配一份新版本，在副本上改完，把 RCU protected pointer 指向新版本。指针一换，原来 reader 的引用就被切断（新来的 reader 拿到的是新版本）。指针赋值是原子的，读侧要么看到旧的要么看到新的，不会看到半成品。

第二步 reclamation。 共享数据不能同时存在两个版本，旧版本必须回收。但不能 reader 还在访问旧版本时就硬回收，那会让 reader 崩掉。回收必须发生在「所有还握着旧版本指针的 reader 都离开临界区」之后，这段等待就是宽限期。之后的 free 有时写者自己干（synchronize_rcu 后跟 kfree），有时推给回调（call_rcu 注册，softirq 上下文执行）。

2.3 契约表 #

角色 承诺 代价
reader 只在 rcu_read_lock/rcu_read_unlock 之间用指针；临界区内不睡眠；出了临界区不再碰 有概率读到旧版本
writer 发布新版本用 rcu_assign_pointer；旧版本延迟到宽限期之后释放；多个 writer 之间自己加锁 要等宽限期，内存有延迟释放的峰值
RCU 内核代码 提供宽限期判定，宽限期结束后执行回调 每个 CPU 要维护回调链表

「RCU 是免锁机制」只在 reader 与 writer 之间成立。writer 和 writer 之间不免费——多个 writer 并行改同一份数据，必须自己用 spinlock 之类互斥。素材 6 说得直白：RCU 属于「免锁机制」的说法仅限读取者与写入者之间。

对比 rwlock 还有一个隐藏差别。rwlock 的读者和写者自始至终共用同一份拷贝，读者必须确认没有写者在动它；RCU 把数据在读者和写者之间做了隔离，读者看到的是某一份不会变的版本，代价是写者要负责清理旧版本。

三、宽限期（grace period）到底是什么 #

定义很朴素：从写者开始更新，到所有读者完成访问，这段时间叫宽限期（素材 2 的原话是「等待所有读者访问结束的时间称为宽限期」）。

难点全在「怎么判定所有读者都完成了访问」。内核没法去问每个读者「你还在临界区里吗」——那等于在读者路径上加共享写操作，前功尽弃。RCU 换了个问法：不问读者，问 CPU。

CPU 经历一次上下文切换（或进入用户态、进入 idle），说明它此刻不持有任何 RCU 读侧临界区——因为读侧不允许睡眠，能切换就说明不在临界区里。这个状态叫 quiescent state（QS）。判定条件于是变成一句话：所有 CPU 各经历至少一次 QS，一个宽限期就结束了。

3.1 在时钟中断里判定 #

4.x 的 tree RCU 上，每个 CPU 在时钟中断里判断自己是否度过了 QS（素材 4）：

c
void update_process_times(int user_tick)
{
......
        rcu_check_callbacks(cpu, user_tick);
......
}

void rcu_check_callbacks(int cpu, int user)
{
......
        if (user || rcu_is_cpu_rrupt_from_idle()) {
                /* 在用户态上下文，或者 idle 上下文，说明已经发生过抢占 */
                rcu_sched_qs(cpu);
                rcu_bh_qs(cpu);
        } else if (!in_softirq()) {
                /* 仅仅针对使用 rcu_read_lock_bh 类型 rcu 的读者，
                 * 不在 softirq，说明已经不在 read_lock 关键区域 */
                rcu_bh_qs(cpu);
        }
        rcu_preempt_check_callbacks(cpu);
        if (rcu_pending(cpu))
                invoke_rcu_core();
......
}

细分分支是为减少无谓判断。注意 rcu_sched_qs 与 rcu_bh_qs 是两个不同变体的记账，不是重复动作：用户态和 idle 对两者都算 QS，而非 softirq 上下文只对 RCU-bh 算 QS。

3.2 从叶子报到根 #

每个 CPU 报完 QS 还要往上汇报，直到所有 CPU 报完。这条路径也藏在 softirq 里，RCU_SOFTIRQ 负责汇合，唤醒它的是时钟中断：

text
update_process_times
-> rcu_check_callbacks
-> invoke_rcu_core

rcu_process_callbacks
-> __rcu_process_callbacks
-> rcu_check_quiescent_state
-> rcu_report_qs_rdp
                -> rcu_report_qs_rnp

rcu_report_qs_rdp 报单个 CPU 的 QS；rcu_report_qs_rnp 从叶子往根遍历，同一节点的所有子节点都报过 QS 之后该节点也置为通过。这个树状汇报就是 «Tree RCU» 名字的由来。核数决定层数，宏定义在第十章。

3.3 宽限期不是固定时长 #

长度取决于系统里最慢的那个 CPU 什么时候过 QS。CPU 正忙着跑 softirq、正关着抢占跑一段长代码，宽限期就得等。

这也解释了 RCU-bh 为什么存在。网络栈在软中断里处理报文，如果攻击者疯狂发报文，被打的设备大部分时间在跑软中断，宽限期会拉得极长，一堆延迟执行的销毁操作堵在队列里，内存持续上涨。RCU-bh 把「执行完软中断」也算成一次 QS，宽限期立刻缩短。这是分布式拒绝服务攻击能打出来的内核实测问题，不是纸面推演。

3.4 不需要等全部读者 #

常见的误读是以为宽限期要等所有在更新前进入的 reader 全部离开。写者在 t0 发布新指针，时间轴是这样：

text
时间 -->
read1  [======]                     旧数据，必须等
read2      [========]               旧数据，必须等
write  ----------| t0 发布新指针
read3              [====]           新数据，不用等
read4           [=========]         新数据，不用等

reclamation 不用等 read3 和 read4。指针赋值是原子的，后来的 reader 拿到的一定是新数据。只需等 t0 之前就进入临界区的那些读者。素材 1 点得很明确：RCU 允许有概率读到旧数据，但读到旧数据的读者一定是替换之前进来的，它们总会在有限时间内离开。

3.5 不同变体的判定条件 #

变体 QS 判据 额外条件
classic RCU 每个 CPU 发生一次抢占/切换 无
RCU-bh 每个 CPU 的 softirq 执行完也算 QS 读侧用 rcu_read_lock_bh
RCU-sched 每个 CPU 退出 preempt-disable 区 读侧用 rcu_read_lock_sched
RCU-preempt 每个 CPU 的 nesting 计数归零 还要 !rcu_preempt_blocked_readers_cgp(rnp)

最后一行的额外条件来自素材 4：可抢占 RCU 允许读侧被抢占，光看「每个 CPU 都过了一次 QS」不够，还要检查有没有读者正卡在临界区里睡觉。被抢占的读者进程会挂进 rnp->blkd_tasks 阻塞队列，同时出现在 rnp->gp_tasks 链表上。宽限期结束的条件因此是两项都成立：

text
!(rnp->qsmask) && !rcu_preempt_blocked_readers_cgp(rnp)

前一项表示每个 CPU 都过了一次 QS，后一项表示没有卡住的读者。

四、新老指针替换：RCU 的更新模型 #

RCU 的更新模型只有一句话：改副本，换指针，等宽限期，释放旧的。 素材 5 把它压成六个字：通过新老指针替换的方式来实现免锁方式的共享保护。听上去简单，落到代码层面会撞上一堆细节。

读者的所有访问都从指针出发，这意味着三件事：结构体内部的字段必须在指针发布之前写好；指针赋值本身必须单次、原子、不可拆分；发布之后不能再原地改旧对象。第三条是 RCU 与 rwlock 的分水岭——rwlock 允许原地改，代价是读者和写者不能共存；RCU 不允许原地改，换来读者和写者共存。

4.1 链表删除的一个具体推演 #

以链表中删除元素 B 为例（素材 6）。A、B、C 按序相连，写者要做：遍历拿到指向 B 的指针；改 A 的 next 指向 C；改 C 的 prev 指向 A。

这期间会有读者正在遍历。改指针指向这个动作是原子的，不需要同步；但 B 自己的 next/prev 不能动，因为读者还在用 B 去拿它的前驱或后继。写者做完这两步，注册一个回调，在宽限期之后删除 B，然后返回。垃圾收集器检测到所有 CPU 都不再引用该链表（都经历过 QS，宽限期已过），才去调回调释放 B。

这解释了 list_del_rcu() 的反直觉行为：它把 entry->prev 设成 LIST_POISON2，但不把 entry->next 设成 LIST_POISON1，因为这个指针还要留给读者遍历。同理 hlist_del_rcu() 只毒化 n->pprev。看到这里觉得别扭的，就是还没转到 RCU 的思路上。

4.2 三种更新模型 #

素材 6 把使用情况分成三类，选哪类直接决定写侧要付多少代价：

模型 写侧动作 读者看到旧数据的时间窗 代价
只增删，不修改条目 list_add_rcu / list_add_tail_rcu / list_del_rcu + call_rcu 删除后到宽限期结束 最低，单写者时可不配 spinlock
需要替换条目 拷贝一份、改副本、list_replace_rcu + call_rcu 同上 中，要一次内存分配
修改要立刻可见 给条目加 deleted 标志或每项一把锁，读侧在临界区内校验 无 最高，读侧要额外检查

第一类最省事。路由表维护就是这一类：操作绝大多数是查询，写只有增加和删除，从 rwlock 换成 RCU 非常自然。系统调用审计也是这一类。

第三类要读侧配合。System V IPC 在每个链表条目里加了 deleted 字段，删除时置真，遍历时核对；代价是每个条目要一把 spinlock 保护这个标志，读者在临界区里拿到条目后要立刻检查，否则仍然看到旧数据。

五、读侧原语：rcu_read_lock 与 rcu_read_unlock #

读侧原语不长，但每个变体各有一套，混用是新手最容易踩的坑。

5.1 经典 RCU #

如果不关心底层用的是不可抢占 RCU 还是可抢占 RCU，就用经典 RCU 的编程接口。素材 2 交代了这套接口的来历：最初的经典 RCU 是不可抢占 RCU，后来实现了可抢占 RCU，经典 RCU 的含义就变了——内核编译了可抢占 RCU，经典 RCU 的接口就被实现为可抢占 RCU，否则实现为不可抢占 RCU。

c
rcu_read_lock();          /* 标记进入读侧临界区 */
/* 通过 rcu_dereference 拿指针，再访问数据 */
rcu_read_unlock();        /* 标记退出读侧临界区 */

读侧临界区可以嵌套，rcu_read_unlock() 与最近一次的 rcu_read_lock() 配对。

5.2 可抢占 RCU 下的实现 #

配置了 CONFIG_TREE_PREEMPT_RCU=y 时，读侧不能靠关抢占来标记，改成给当前进程的计数加一（素材 4）：

c
void __rcu_read_lock(void)
{
        current->rcu_read_lock_nesting++;
        barrier();  /* critical section after entry code. */
}

void __rcu_read_unlock(void)
{
        struct task_struct *t = current;

        if (t->rcu_read_lock_nesting != 1) {
                --t->rcu_read_lock_nesting;
        } else {
                barrier();  /* critical section before exit code. */
                t->rcu_read_lock_nesting = INT_MIN;
                barrier();  /* assign before ->rcu_read_unlock_special load */
                if (unlikely(ACCESS_ONCE(t->rcu_read_unlock_special)))
                        rcu_read_unlock_special(t);
                barrier();  /* ->rcu_read_unlock_special load before assign */
                t->rcu_read_lock_nesting = 0;
        }
}

两个细节值得盯住。退出时先把计数写成 INT_MIN 而不是直接减到 0，这样即便此刻被抢占，宽限期也不会认定它已离开临界区，避免误释放；处理完 rcu_read_unlock_special 再归零。三处 barrier() 都不是给 CPU 看的，是给编译器看的——防止编译器把临界区内的访存挪到计数加减之外。

可抢占 RCU 允许读者在临界区里被抢占。发生抢占时 __schedule 调 rcu_note_context_switch 通知 RCU 更新状态；如果当前 CPU 处于 rcu_read_lock 状态，当前进程会被挂进 rnp->blkd_tasks。

5.3 三个变体的读侧原语 #

变体 进入 退出 取指针 对应写侧等待
classic RCU rcu_read_lock() rcu_read_unlock() rcu_dereference(p) synchronize_rcu()
不可抢占 RCU rcu_read_lock_sched() rcu_read_unlock_sched() rcu_dereference_sched(p) synchronize_sched()
加速版不可抢占 RCU rcu_read_lock_bh() rcu_read_unlock_bh() rcu_dereference_bh(p) synchronize_rcu_bh()

三者的读侧临界区都能嵌套。rcu_read_lock_bh() 与 local_bh_disable() 等价，rcu_read_lock_sched() 与 preempt_disable() 等价——素材 6 给的是宏形式：

c
#define rcu_read_lock()        preempt_disable()
#define rcu_read_unlock()      preempt_enable()

#define rcu_read_lock_bh()     local_bh_disable()
#define rcu_read_unlock_bh()   local_bh_enable()

这是 2.6.x 的形态。到 4.x，rcu_read_lock() 已是 include/linux/rcupdate.h 里的 inline 函数，随 CONFIG_PREEMPT_RCU 分叉（见 2.1、5.2）。不要照抄宏定义去推断语义，按配置走。变体必须配对，理由见铁律五。

六、写侧原语：rcu_assign_pointer 与 rcu_dereference #

读写两侧的原语是配套设计的，配错了编译器不一定报错，运行时才炸。

6.1 全套原语对照 #

用途 读侧 写侧 说明
进入/退出临界区 rcu_read_lock / rcu_read_unlock — 只做 preempt_disable/preempt_enable
取指针 rcu_dereference(p) — 封装数据依赖屏障，只有 Alpha 真需要
发布指针 — rcu_assign_pointer(p, v) 保证先初始化结构、后发布指针
同步等宽限期 — synchronize_rcu() 会阻塞，需睡眠上下文
加速等宽限期 — synchronize_rcu_expedited() 发 IPI 强制其他 CPU 过 QS
异步注册回调 — call_rcu(head, func) 立即返回，不阻塞
等回调全部执行完 — rcu_barrier() 会阻塞，需睡眠上下文
延迟释放对象 — kfree_rcu(ptr, rcu_head) 直接按宽限期释放，不必自己写回调

rcu_assign_pointer 为什么不能直接写成 p = v，理由在第七章。

6.2 call_rcu 的签名与 rcu_head #

c
void call_rcu(struct rcu_head *head, rcu_callback_t func);

struct callback_head {
     struct callback_head *next;
     void (*func)(struct callback_head *head);
} __attribute__((aligned(sizeof(void *))));

#define rcu_head callback_head

typedef void (*rcu_callback_t)(struct rcu_head *head);

struct rcu_head 这个形状的原因很实际：next 让它能被挂进 per-CPU 回调链表，func 记住自己的处理函数。#define rcu_head callback_head 是后来重命名留下的别名；2.6.x 源码里写的就是本体，直接是 next 加 func 两个字段，没有 callback_head 这一层。

把 rcu_head 内嵌进被保护的数据结构，是为了省掉单独分配一个节点的内存操作。删除路径不该留下内存分配失败的机会，这点很关键。

6.3 节点结构的三个成员 #

c
typedef struct {
    struct list_head link;   /* 挂链表的钩子 */
    struct rcu_head rcu;     /* 给 call_rcu 用的钩子 */
    int key;
    int val;
} test_entry;

link 是链表结构的一部分，rcu 只在对象被摘下来之后才用，两个钩子互不干扰。分开的理由在于：link 在整个生命周期里都在链表中被改写，而 rcu 一旦挂进回调链，它的 next 就被 RCU 自己接管了。共用一个字段会立刻冲突。

6.4 四种写操作 #

添加、修改、删除的完整可用代码在 14.3，这里只点出与原地修改的差别。

修改必须走「拷贝—改副本—替换—延迟释放」：kmalloc 一块新的、*new_entry = *entry 拷过去、在副本上改、list_replace_rcu 发布、call_rcu 登记旧节点的回收。删掉任何一步都不行——不拷贝就直接改是 rwlock 的写法，在 RCU 下会让正在读的读者看到半更新的数据。

删除是 list_del_rcu 加回收，回收走 call_rcu 或 synchronize_rcu 两条路。多写者时三种操作外层各加一把 spinlock，锁保护写者之间的互斥，读者完全不受影响。

6.5 每个变体的四个写侧函数 #

变体 同步等待 加速等待 异步回调 等回调清空
classic RCU synchronize_rcu() synchronize_rcu_expedited() call_rcu() rcu_barrier()
不可抢占 RCU synchronize_sched() synchronize_sched_expedited() call_rcu_sched() rcu_barrier_sched()
加速版不可抢占 RCU synchronize_rcu_bh() synchronize_rcu_bh_expedited() call_rcu_bh() rcu_barrier_bh()

语义一一对应，只是账本不同。被 expedited 强制加快的叫加速宽限期（expedited grace period），没被强制的叫正常宽限期（normal grace period）。

rcu_barrier() 解决的是另一个问题：call_rcu 注册的回调会在 call_rcu 返回后很久才执行，模块卸载时直接走人，回调就会打在卸载后的代码上。rcu_barrier() 保证已注册的回调全部执行完再返回。它需要睡眠上下文，只能在进程上下文调用。

6.6 synchronize_rcu 与 call_rcu 怎么选 #

维度 synchronize_rcu() call_rcu()
阻塞 阻塞，需睡眠上下文 立即返回
可用上下文 只能在进程上下文 进程上下文、中断上下文、softirq 都能用

素材 5 把这条决策规则说得很干脆：call_rcu 返回后其注册的回调函数未必已被调用，老指针还没被释放；而 synchronize_rcu 返回后老指针一定被释放了。选哪个要看具体需求与当前上下文——中断处理的上下文肯定不能用 synchronize_rcu。

6.7 名字的来历与兼容包袱 #

素材 6 记了一段容易踩坑的历史：synchronize_rcu 在 2.6.11 及以前的 2.6 内核里叫 synchronize_kernel，到 2.6.12 才更名，同一次改动还提供了 synchronize_kernel 和一个新函数 synchronize_sched。

为什么要拆？很多内核开发者用 synchronize_kernel 的本意是「等所有 CPU 都退出不可抢占区」，而 RCU 设计里这个函数只用来「等所有 CPU 都退出读侧临界区」。两个语义会随着 RCU 实现的修改而分岔，为了预先防住这种情况，新代码把两者拆开：非 RCU 的内核代码用 synchronize_sched，RCU 代码用 synchronize_rcu，synchronize_kernel 留着只为源码兼容。

在 2.6.12 这个具体版本里，synchronize_kernel 和 synchronize_sched 都实际调用 synchronize_rcu，所以三者功能当时完全等同；但语义分岔已经埋好，名字该怎么用就怎么用，不要依赖「当前实现恰好一样」。

七、为什么需要 rcu_dereference：编译器与 CPU 的乱序 #

rcu_dereference 名字里带 dereference，但它并没有解引用任何东西。它的全部作用是插一道屏障。

c
#define rcu_dereference(p)     ({ \
                                typeof(p) _________p1 = p; \
                                smp_read_barrier_depends(); \
                                (_________p1); \
                                })

这是 2.6.x 的形态。smp_read_barrier_depends() 在绝大多数架构上是空操作，只在 Alpha 上展开成真正的屏障。

7.1 到底在防什么 #

看写侧。写者初始化新节点的过程是：

c
new->a = 1;
new->b = 2;
rcu_assign_pointer(gp, new);

编译器看到的是一串与「可观察行为」无关的赋值，它有权把 rcu_assign_pointer(gp, new) 挪到前面——这些写指向不同对象，谁先谁后不影响单线程语义。CPU 也会做同样的事：重排写缓存的顺序。

一旦重排发生，读者会先看到 gp 指向新节点，再去读 new->a，此时 a 还没写进去，读到垃圾。rcu_assign_pointer 内部带一道 store-store 屏障，把「初始化完成」和「发布指针」之间的顺序钉死。

7.2 读侧的数据依赖 #

读者这边的问题形态不同。读者先拿指针再取值：

c
p = rcu_dereference(gp);
v = p->a;

这两句构成数据依赖：第二句的地址依赖第一句的结果。x86、ARM 等架构保证地址依赖不被重排，不需要额外屏障；Alpha 的弱内存模型不保证，所以要 smp_read_barrier_depends()。

这就是「只有 Alpha 需要读内存屏障」的由来，素材 1 与素材 6 都这么写。读者不用为此付出跨架构开销，宏在非 Alpha 上编译成空。

7.3 编译期检查 #

rcu_dereference 的另一个价值是给 sparse 看。指针变量标注成 __rcu 之后，直接 *p 会被 sparse 报错，必须经过 rcu_dereference 才能拿到可解引用的指针。这把「忘记加屏障」从运行时事故变成编译期告警。

代价是啰嗦：TEST 之类的东西要写 rcu_dereference(p)->field，不是 p->field。

7.4 链表 API 已经封装好了 #

链表操作不需要手写屏障，_rcu 版本已经封装：

链表类型 遍历 头插 尾插 删除 替换
list_head list_for_each_entry_rcu list_add_rcu list_add_tail_rcu list_del_rcu list_replace_rcu
hlist hlist_for_each_entry_rcu hlist_add_head_rcu hlist_add_tail_rcu hlist_del_rcu hlist_replace_rcu
hlist_nulls hlist_nulls_for_each_entry_rcu hlist_nulls_add_head_rcu hlist_nulls_add_tail_rcu hlist_nulls_del_rcu —
hlist_bl hlist_bl_for_each_entry_rcu hlist_bl_add_head_rcu — hlist_bl_del_rcu —

四种链表的差别：

list_head 标准双向链表
hlist 头节点只有一个指针，省内存
hlist_nulls 结束符是 (1UL | (((long)value) << 1))，最低位为 1，value 是嵌入的值（比如散列桶索引）
hlist_bl 链表头节点的最低位作为基于位的自旋锁

list_for_each_entry_rcu 封装了只有 Alpha 需要的数据依赖屏障，所以遍历必须用它，不能自己写 list_for_each_entry。有一个例外：遍历发生在唯一的删除路径上时可以不用 _rcu 版本，因为那个位置只有写者在跑。内核 audit 代码里就留着这样的注释：Do not use the _rcu iterator here, since this is the only deletion routine.

7.5 list_del_rcu 的不对称行为 #

  • list_del_rcu(entry) 把 entry->prev 设为 LIST_POISON2，不设 entry->next 为 LIST_POISON1；
  • hlist_del_rcu(n) 把 n->pprev 设为 LIST_POISON2，不设 n->next。

原因相同：读者正沿着被删节点继续往后走，next 还得可用。毒化 prev 是因为读者不会再往回退。这种不对称是 RCU 的语义要求，不是实现疏漏。

八、同步等待：synchronize_rcu #

synchronize_rcu() 是写侧最直观的工具：调它，等宽限期过去，返回后旧数据再无引用者，可以直接 free。

c
list_del_rcu(&entry->link);
synchronize_rcu();
kfree(entry);

三句话就是一次完整的安全删除。

8.1 它做了什么 #

素材 5 描述得足够精确：synchronize_rcu 的实现利用了等待队列。它也会像 call_rcu 那样往当前处理器的本地回调链表中加入一个节点，区别在于这个节点里的回调函数是 wakeme_after_rcu。加完节点，synchronize_rcu 在等待队列里睡眠，直到系统里所有处理器都发生过一次进程切换，rcu_process_callbacks 调起 wakeme_after_rcu 把它唤醒。醒来之后它知道自己可以放行后续操作了。

这顺带回答了一个问题：synchronize_rcu 内部就是 call_rcu 加一层睡眠等待。素材 6 有一句话印证：函数 synchronize_rcu 的实现实际上使用函数 call_rcu。两者不是两套机制，是一个机制的两种用法。

8.2 为什么它必须能睡眠 #

synchronize_rcu 要等宽限期。宽限期长度不可预知，短则几微秒，长则毫秒级甚至更久（取决于最慢的那个 CPU）。用自旋等待会关抢占、烧 CPU，还会把宽限期本身拖长——等的人越多，被等的 CPU 越难安心过 QS。

所以它是睡眠等待。随之而来的硬限制：

上下文 能否用 synchronize_rcu
进程上下文 可以
中断处理程序 不能
softirq / tasklet 不能
持有 spinlock 时 不能（关抢占，睡眠即死锁）
关抢占区内 不能

8.3 expedited 版本 #

synchronize_rcu_expedited() 等待的仍是宽限期，区别是会向其他处理器发处理器间中断（Inter-Processor Interrupt，IPI），强制宽限期快速结束。

代价是把「等」的成本转成「打断所有 CPU」的成本。频繁调用会把系统整体性能拉下来，只适合初始化、模块卸载这类一次性路径。

8.4 多个写者同时等，一起醒 #

素材 6 有一句容易被忽略的话：如果有多个 RCU 写端调用该函数，它们将在一个 grace period 之后全部被唤醒。

synchronize_rcu 天然批量。N 个写者几乎同时调用，不会产生 N 个宽限期，而是共用同一个。这对写侧密集的场景是好消息，但别把它当限流手段。

九、异步回调：call_rcu #

call_rcu() 把释放动作推迟给回调，自己立刻返回。

9.1 它的执行路径 #

素材 5 的过程描述：

  1. call_rcu 把释放老指针的回调函数放入一个节点；
  2. 把该节点加入当前正在运行 call_rcu 的处理器的本地链表；
  3. 时钟中断的 softirq 部分（RCU_SOFTIRQ）里，rcu_process_callbacks 检查当前处理器是否经历了一个休眠期；
  4. 确认所有处理器都经历过一次休眠期之后，调起 call_rcu 提供的回调函数。

第 3 步容易被读成「单个 CPU 过 QS 就执行」，不是。要所有 CPU 都过 QS。素材 5 原话：rcu 的内核代码实现在确定系统中所有的处理器都经历过了一个休眠期之后（意味着所有处理器上都发生了一次进程切换，因此老指针此时可以被安全释放掉了），将调用 call_rcu 提供的回调函数。

9.2 回调在什么上下文跑 #

softirq。这一点决定了回调函数的写法限制：

允许 禁止
kfree 睡眠（kmalloc(GFP_KERNEL)、mutex_lock、synchronize_rcu 等）
自旋锁（需用 spin_lock_bh 与 softirq 侧保持一致） 长时间占用 CPU
唤醒等待者 直接操作需要进程上下文的子系统

回调跑在 softirq 里，跑的时候关着下半部，还压着 RCU_SOFTIRQ 这条软中断线。回调写得太重会拖慢整个 softirq 路径。

9.3 kfree_rcu 省掉手写回调 #

针对从通用 slab 缓存用 kmalloc() 分配的对象，内核提供 kfree_rcu(ptr, rcu_head)，把对象延迟释放到宽限期结束。第二个参数是 ptr 指向的结构体里类型为 struct rcu_head 的成员名。

c
test_entry *p;

p = kmalloc(sizeof(test_entry), GFP_KERNEL);
/* ... */
kfree_rcu(p, rcu);

省掉的东西：一个回调函数、一次 container_of 运算、一次 call_rcu 调用。这在删除路径上很值。

9.4 内存峰值与批量执行 #

代价藏在内存账上。回调没执行之前老对象一直占着内存，删除密集时堆积量取决于宽限期长度和删除速率。素材 6 的总结点出了这条：延迟的删除或释放将占用一些内存，尤其是对嵌入式系统，这是很贵的内存开销。另一头是批量执行：宽限期一结束，积压的回调要一口气跑完，形成 CPU 尖峰。2.6.11 引入了 maxbatch 变量限制单批处理量，细节在实现演进篇，结论是 rcu_do_batch 不是无界的。

十、synchronize_rcu 的内部原理 #

把 synchronize_rcu 拆开看，一共四件事：标记读者、让每个 CPU 报 QS、汇总 QS、发起并结束宽限期。以 4.x 的 tree RCU 为主线（素材 4），2.6.x 的形态差异在实现演进篇。

10.1 标记读者 #

读侧实现就是 preempt_disable() / preempt_enable()（代码见 2.1）。于是「是否度过宽限期」的判定变简单了：每个 CPU 都经历过一次抢占即可。因为发生了抢占，就说明它不在 rcu_read_lock 与 rcu_read_unlock 之间，要么已完成访问，要么还没开始。

这个推理是整座大厦的地基。它同时解释了为什么读侧临界区里绝对不能睡眠：一旦睡眠，抢占发生了，RCU 会认为这个 CPU 已过 QS，宽限期会提前结束，旧数据被释放，醒来的读者踩空。

10.2 每个 CPU 上报 QS #

时钟中断里跑 rcu_check_callbacks（代码见 3.1），判定当前 CPU 是否度过 QS，然后 rcu_sched_qs(cpu) / rcu_bh_qs(cpu) 记账。细分场景是为了提高效率：能确定过 QS 的路径走快路，不确定的留给后面的检查。

10.3 汇总 #

text
update_process_times
-> rcu_check_callbacks
-> invoke_rcu_core

invoke_rcu_core 唤起的软中断里做汇合：

text

-> __rcu_process_callbacks
-> rcu_check_quiescent_state

rcu_report_qs_rnp 从叶子往根遍历。同一节点的子节点都过 QS 之后，该节点也置为通过。核数决定树的层数，素材 4 给的宏从 1 层到 4 层（下面只留前两个分支示意，完整四段在《RCU：实现演进》）：

10.4 发起与结束 #

所有宽限期的发起和完成都由同一个内核线程 rcu_gp_kthread 完成。判据两条：

动作 判据
发起一个 GP rsp->gp_flags & RCU_GP_FLAG_INIT 为真
结束一个 GP !(rnp->qsmask) && !rcu_preempt_blocked_readers_cgp(rnp)

发起时 rsp->gpnum++；结束时 rsp->completed = rsp->gpnum。这两个计数器是判断「某个回调属于哪个宽限期」的依据。

把宽限期交给一个内核线程做，好处是把「等」集中到一个可以被调度、被追踪、被 stall 检测抓现行的位置上。宽限期卡住时，你能在 rcu_gp_kthread 的栈上看到它卡在哪一层。

10.5 可抢占 RCU 的额外判据 #

CONFIG_TREE_PREEMPT_RCU=y 时，synchronize_rcu 默认使用 rcu_preempt_state。这类 RCU 的读侧允许被抢占，判定方法不同：

  • 读侧靠 current->rcu_read_lock_nesting 计数，不是靠关抢占；
  • 抢占发生时 __schedule 调 rcu_note_context_switch 通知 RCU 更新状态；
  • 如果当前 CPU 处于 rcu_read_lock 状态，当前进程会被挂进 rnp->blkd_tasks 阻塞队列，同时出现在 rnp->gp_tasks 链表上；
  • 宽限期结束要同时满足 !(rnp->qsmask)（每个 CPU 都过了一次 QS）和 !rcu_preempt_blocked_readers_cgp(rnp)（没有卡住的读者）。

真正被阻塞的读者不会漏，因为它在 blkd_tasks 上挂着，rcu_gp_kthread 会看到它，宽限期不结束。等它退出临界区，rcu_read_unlock_special 把它摘下来，宽限期才能收尾。

十一、等待队列与回调链表 #

call_rcu 注册的回调存哪儿、怎么排序、什么时候被取出执行，这套数据结构决定了 RCU 的写侧行为。

11.1 per-CPU 回调链表 #

每个 CPU 维护自己的回调链表。2.6.x 的形态是每个 CPU 两个结构体：rcu_data 和 rcu_bh_data。call_rcu 注册的回调进 rcu_data，call_rcu_bh 注册的进 rcu_bh_data。每个结构上回调串成链表，先注册的排在前面，后注册的排在末尾。

per-CPU 是必然选择：把所有 CPU 的回调挂到一条全局链表上，call_rcu 就要抢那把全局锁，写侧立刻退化回自旋锁的性能。分开挂，call_rcu 只碰本地数据。

11.2 分段链表 #

回调链表不是一条简单队列，它按「在哪个宽限期结束」分段（素材 4，4.x 形态）：

text
nxtlist
  -> *nxttail[RCU_DONE_TAIL]
  -> *nxttail[RCU_WAIT_TAIL]
  -> *nxttail[RCU_NEXT_READY_TAIL]
  -> *nxttail[RCU_NEXT_TAIL]

nxtlist 是链表头，四个 nxttail[] 指针把链表切成四段。rcu_do_batch 只处理 nxtlist 到 *nxttail[RCU_DONE_TAIL] 之间的回调——这一段的宽限期已经结束，可以安全执行。

每结束一个 GP，段位重新调整：原本 WAIT 段的回调挪进 DONE 段。新注册的回调一律追加到 *nxttail[RCU_NEXT_TAIL]。

分段的意义：注册回调的时刻不确定，回调该由哪个宽限期兜底也不确定。分段把「等哪个 GP」这个判断从执行时刻挪到了注册时刻，执行时只需看段位。

11.3 回调执行路径 #

text
rcu_process_callbacks
-> __rcu_process_callbacks
-> invoke_rcu_callbacks
-> rcu_do_batch
                -> __rcu_reclaim

rcu_do_batch 一次取一段，逐个调 __rcu_reclaim。这一批跑多少受 maxbatch 限制，跑完如果还有剩余，重新挂起软中断接着跑，不会一次霸占 CPU。

11.4 2.6.x 的 tasklet 形态 #

素材 6 描述的是 2.6.x 的实现，路径不同但结构对应：

  1. rcu_check_callbacks 检查完 QS 之后调 tasklet_schedule，为本 CPU 设置 rcu_tasklet；
  2. 时钟中断返回后，rcu_tasklet 在 softirq 上下文运行；
  3. rcu_tasklet 跑 rcu_process_callbacks，后者会做三件事：开始一个新的 grace period（rcu_start_batch）、运行需要处理的回调（rcu_do_batch）、检查该 CPU 是否经历了一次 QS（rcu_check_quiescent_state）。

如果还没有开始 grace period，就调 rcu_start_batch 开一个新的。rcu_check_quiescent_state 确认本 CPU 过了 QS；如果它是最后一个过 QS 的 CPU，就结束当前 grace period 并开始新的一个；如果有已完成 grace period 的段，就调 rcu_do_batch 跑掉那批回调。这一切对 rcu_data 和 rcu_bh_data 各做一遍。

11.5 等待队列 #

call_rcu 的路径里没有等待队列，synchronize_rcu 才有。链条是这样：

text
写者 synchronize_rcu()
  -> 分配/复用一个 rcu_head，回调设为 wakeme_after_rcu
  -> 挂进当前 CPU 的回调链表
  -> 在等待队列上睡眠
  ...
rcu_do_batch 执行到该节点
  -> wakeme_after_rcu(head)
  -> 唤醒睡眠的写者
写者醒来，返回，kfree 旧对象

synchronize_rcu 和 call_rcu 的区别因此可以精确表述成一句话：注入的回调函数不同。一个是 wakeme_after_rcu，一个是用户自己写的 test_free_node。

11.6 排队与内存压力的实测问题 #

回调堆积不是理论问题。RCU-bh 的引入动机就来自堆积：软中断长期占满 CPU 时，普通 RCU 的宽限期无限拉长，写者注册的回调却源源不断，内存只增不减。把「软中断执行完」也算作 QS 之后，宽限期能收敛，堆积才被止住。

这也是理解「宽限期为什么不能太短也不能太长」的关键：太短会误判（读者还在用旧数据），太长会积压。RCU 的所有变体本质上都在调整 QS 的判据，去适配不同上下文的读者。

十二、RCU 的几种变体：RCU-bh / RCU-sched / SRCU / Tasks RCU #

变体的存在理由只有一个：读者的上下文不同，QS 的判据就得跟着不同。

12.1 三种基础变体 #

素材 2 列出的三种，版本号照原文：

12.2 sleepable RCU（SRCU） #

前面所有 RCU 的共同限制是读侧不能睡眠。SRCU 拆掉了这个限制，2.6.23 引入：

维度 普通 RCU SRCU
读侧睡眠 禁止 允许
读者计数 全局/per-CPU 隐式 每个 srcu_struct 各自维护
宽限期 全局共享，开销低 每个 srcu_struct 独立，开销高
写侧等待 synchronize_rcu synchronize_srcu
使用门槛 低 要显式初始化一个 struct srcu_struct

2.6.23 那版的接口只有五个（来自同目录《Linux2623 sleepable RCU的实现.md》）：

c
int init_srcu_struct(struct srcu_struct *sp);
void cleanup_srcu_struct(struct srcu_struct *sp);

int srcu_read_lock(struct srcu_struct *sp) __acquires(sp);
void srcu_read_unlock(struct srcu_struct *sp, int idx) __releases(sp);

void synchronize_srcu(struct srcu_struct *sp);

srcu_read_unlock 要多带一个 idx，这是 SRCU 的设计代价：解锁要告诉内核减哪一个计数器。因为 srcu_read_lock 与 srcu_read_unlock 之间插入一次 synchronize_srcu，把 completed（当前 pending 的 GP ID）加一，sp 自己已经分不清该减哪个了。

那版刻意不提供异步接口（不给 call_srcu 这类 API），只留同步接口。理由很实际：给了异步接口，每个线程就能提交任意多个回调请求；而 synchronize_srcu 会阻塞当前线程，一个线程一次只能挂一个请求，数量被自然压住。call_srcu 是后来才有的，具体版本未验证。

SRCU 的宽限期按实例独立计算，省不掉开销。它适合读侧确实要睡眠、又想避开互斥锁的场景。源码实现见《RCU：实现演进》。

12.3 Tasks RCU #

tasks RCU 保护的是「任务返回用户态之前不会被释放」这类语义，典型用途是可执行代码区域的延迟释放和 BPF 相关路径。引入版本素材没有涉及，未验证；接口名随版本变过，也未验证。用之前查当前内核的 Documentation/RCU/。

十三、使用 RCU 的五条铁律 #

五条从前面所有推演里抽出来。违反任何一条，症状都是「偶发、难复现、栈上看不出原因」的那类崩溃。

铁律一：读侧临界区内不许睡眠 #

rcu_read_lock 在 classic RCU 下就是 preempt_disable()。里面调任何会睡眠的函数，要么立刻触发调度器告警，要么把 QS 判定的前提破坏掉——抢占发生了，RCU 认为该 CPU 已过 QS，宽限期收尾，旧数据被释放，醒来的读者踩到已释放内存。

素材 5 把这句写得很重：如果在内核的临界区中调用了一个函数，该函数会睡眠，那么 RCU 的设计规则就遭到了破坏，系统将进入一种不稳定的状态。要睡眠就用 SRCU，或把睡眠操作挪到临界区之外。

铁律二：出了临界区不许再碰那个指针 #

synchronize_rcu 返回后写者就敢 free，凭的是「没有读者还握着指针」。你如果偷偷把指针存进全局变量或 task_struct，出了临界区再用，那个保证立刻失效。

需要长期持有就加引用计数（atomic_inc_not_zero + 二次校验），那是另一套机制，别指望 RCU 帮你保。14.5 有完整形态。

铁律三：写侧必须延迟释放，不能直接 kfree #

从链表上摘掉节点之后，那个节点的内存还被在临界区里的读者用着。list_del_rcu() 之后直接 kfree() 是最高频的 RCU bug。正确姿势二选一：

c
/* 方式一：同步 */
list_del_rcu(&entry->link);
synchronize_rcu();
kfree(entry);

/* 方式二：异步 */
list_del_rcu(&entry->link);
call_rcu(&entry->rcu, test_free_node);

铁律四：多个写者之间必须自己加锁 #

RCU 的免锁只覆盖读者与写者之间。两个写者同时改同一条链表，照样会把 next 改坏。素材 6 的写法是给每个写操作外层套一把 spinlock，读者不受影响。只有一个写者时才可以省掉——前提是你能证明真的只有一个。

铁律五：变体必须配对 #

写侧用的 读侧必须用
call_rcu / synchronize_rcu rcu_read_lock / rcu_read_unlock
call_rcu_bh / synchronize_rcu_bh rcu_read_lock_bh / rcu_read_unlock_bh
call_rcu_sched / synchronize_sched rcu_read_lock_sched / rcu_read_unlock_sched
synchronize_srcu srcu_read_lock / srcu_read_unlock

配错的后果是保护静默失效：读侧的临界区不在写侧等待的那本账上，宽限期照样结束，旧数据照样被释放，代码看上去一切正常。

# 铁律 违反的典型症状
1 读侧不睡眠 偶发 use-after-free，或 scheduling while atomic
2 出临界区不持有指针 free 之后被访问，栈上指向已释放的 slab
3 写侧延迟释放 高负载下必崩，低负载下测不出来
4 写者之间互斥 链表指针被改坏，遍历时跳到垃圾地址
5 变体配对 保护失效但无任何报错，压力测试才发现

十四、一个完整的例子：链表的免锁遍历与安全删除 #

把前面所有零件拼成一个能跑的骨架。

c
#include <linux/list.h>
#include <linux/rcupdate.h>
#include <linux/slab.h>
#include <linux/spinlock.h>

typedef struct {
    struct list_head link;   /* 挂链表的钩子 */
    struct rcu_head rcu;     /* 给 call_rcu 用的钩子 */
    int key;
    int val;
} test_entry;

static struct list_head test_head;
static DEFINE_SPINLOCK(test_lock);   /* 只在多写者时才需要 */

14.1 读侧：完全不加锁 #

c
int test_read(int key, int *val_ptr)
{
    test_entry *entry;
    int found = 0;

    rcu_read_lock();
    list_for_each_entry_rcu(entry, &test_head, link) {
        if (entry->key == key) {
            *val_ptr = entry->val;
            found = 1;
            break;
        }
    }
    rcu_read_unlock();

    return found;
}

读者没拿任何锁，没碰任何全局计数器，也不阻塞写者。它唯一的假设是：遍历期间拿到的每个节点，内存都还可用——这个假设由写侧的延迟释放保证。必须用 list_for_each_entry_rcu 而非 list_for_each_entry，因为前者封装了数据依赖屏障，且在被删节点上仍能安全取 next。

14.2 写侧：增删改 #

添加。单写者直接调；多写者外面包一层 spinlock：

c
void test_add_node(test_entry *entry)
{
    spin_lock(&test_lock);
    list_add_tail_rcu(&entry->link, &test_head);
    spin_unlock(&test_lock);
}

修改走「拷贝—改副本—替换—延迟释放」，list_replace_rcu 的第二个参数用 &new_entry->link（素材原文写作 &new_entry->list，字段名是错的，见附录）：

c
static void test_free_node(struct rcu_head *head)
{
    test_entry *entry = container_of(head, test_entry, rcu);

    kfree(entry);
}

int test_update_node(int key, int new_val)
{
    test_entry *entry, *new_entry;
    int ret = -ENOENT;

    spin_lock(&test_lock);
    list_for_each_entry(entry, &test_head, link) {
        if (entry->key == key) {
            new_entry = kmalloc(sizeof(test_entry), GFP_ATOMIC);
            if (new_entry == NULL) {
                ret = -ENOMEM;
                break;
            }
            *new_entry = *entry;
            new_entry->val = new_val;
            list_replace_rcu(&entry->link, &new_entry->link);
            call_rcu(&entry->rcu, test_free_node);
            ret = 0;
            break;
        }
    }
    spin_unlock(&test_lock);

    return ret;
}

GFP_ATOMIC 是因为整段在 spinlock 里，不能睡眠。想把分配挪到锁外用 GFP_KERNEL 也行，先分配好再进锁。

删除用异步，回调函数与修改共用同一个 test_free_node：

c
int test_del_node(int key)
{
    test_entry *entry;
    int found = 0;

    spin_lock(&test_lock);
    list_for_each_entry(entry, &test_head, link) {
        if (entry->key == key) {
            list_del_rcu(&entry->link);
            call_rcu(&entry->rcu, test_free_node);
            found = 1;
            break;
        }
    }
    spin_unlock(&test_lock);

    return found;
}

同一场景也可以写成 list_del_rcu() 后跟 synchronize_rcu() 再 kfree()——代码更短，但只能在单写者或外层已有互斥时用，因为 synchronize_rcu() 会睡眠，而写侧遍历链表本身不受 RCU 保护。

14.3 退出：别漏掉 rcu_barrier #

c
static void __exit test_exit(void)
{
    test_entry *entry, *tmp;

    /* 等所有已注册的回调执行完，否则回调会打在已卸载的代码上 */
    rcu_barrier();

    list_for_each_entry_safe(entry, tmp, &test_head, link) {
        list_del(&entry->link);
        kfree(entry);
    }
}

rcu_barrier() 是模块卸载时的标准动作。没有它，卸载完成后 softirq 才来跑 test_free_node，函数指针指向的代码段已经没了。这里的 list_del 用普通版本，因为模块正在退出，没有并发读者要照顾。

14.4 进阶：散列表 + 引用计数 #

如果读者要在临界区之外继续持有对象，RCU 不够，要配引用计数，顺序很讲究。素材 3 给的查找算法：

c
head = &table[slot];
rcu_read_lock();
begin:
hlist_nulls_for_each_entry_rcu(obj, node, head, hash_node) {
    if (obj->key == key) {
        if (!atomic_inc_not_zero(&obj->refcnt))
            goto begin;                /* 对象正在释放，重来 */

        if (obj->key != key) {
            put_ref(obj);              /* 内存已分给别的对象，重来 */
            goto begin;
        }
        goto out;
    }

    if (get_nulls_value(node) != slot) /* 遍历期间有对象迁到别的桶 */
        goto begin;
    obj = NULL;
}

out:
rcu_read_unlock();

三个 goto begin 对应三种竞态：引用计数已归零（对象在释放）、加计数后 key 变了（内存被复用）、链表结束符里的桶索引变了（有对象迁桶）。

这段代码敢在引用计数归零后立刻 kmem_cache_free()，是因为缓存带 SLAB_TYPESAFE_BY_RCU 标志（旧名 SLAB_DESTROY_BY_RCU）。这个标志只延迟释放 slab 页到宽限期结束，不延迟对象释放：kmem_cache_free() 之后对象内存立刻可被分配给下一个对象。所以读者手里的指针永远指向合法内存（页还在），不会 UAF；但内容已是另一个对象，必须二次校验 key；对象还会被分到不同散列桶，必须校验桶索引。这就是「类型安全的 RCU」的含义：保证内存可用，不保证内容还是原来那个。

14.5 一个真实的迁移案例 #

素材 6 完整保留了系统调用审计代码从 rwlock 迁到 RCU 的过程：读侧 read_lock 换 rcu_read_lock、list_for_each_entry 换 list_for_each_entry_rcu，写侧 write_lock 直接消失——因为 audit_netlink_sem 已由调用者持有，写者互斥有人兜底。增删分别换成 list_add_rcu / list_add_tail_rcu 与 list_del_rcu + call_rcu。

删除路径上有个细节值得抄：那条遍历故意用非 _rcu 版本，并留了注释：

c
/* Do not use the _rcu iterator here, since this is the only
 * deletion routine. */
list_for_each_entry(e, list, list) {
    if (!audit_compare_rule(rule, &e->rule)) {
        list_del_rcu(&e->list);
        call_rcu(&e->rcu, audit_free_rule);
        return 0;
    }
}

唯一的写者，不存在并发遍历，用 _rcu 版本只是白付一道屏障。判断依据是「这个位置会不会有别人同时在跑」，不是「RCU 代码就必须全用 _rcu 版本」。

14.6 需要立刻可见怎么办 #

前两类模型都允许读者在一段时间内看到旧数据。业务上不能容忍（比如删除必须立刻生效）时，RCU 单独解决不了，要叠一层标志。素材 6 的方案：每个条目加一个 deleted 字段。删除时先置标志再摘链：

c
spin_lock(&e->lock);
list_del_rcu(&e->list);
e->deleted = 1;
spin_unlock(&e->lock);
call_rcu(&e->rcu, audit_free_rule);

读侧在临界区里核对，且必须在 rcu_read_unlock() 之前完成：

c
spin_lock(&e->lock);
if (e->deleted) {
    spin_unlock(&e->lock);
    rcu_read_unlock();
    return AUDIT_BUILD_CONTEXT;
}
spin_unlock(&e->lock);
return state;

代价很明确：每个条目一把 spinlock，读侧多一次取锁。这已经不是便宜的 RCU 读侧了，只在确实需要强可见性时才这么做。

十五、什么时候不该用 RCU #

RCU 的读侧便宜是靠写侧付账换来的。写侧账付不起的时候，别用。

情形 为什么不行 换什么
写多读少 每次写都要等宽限期，写侧开销压倒收益 mutex / rwlock
读侧需要睡眠 临界区内一睡，QS 判定失效 SRCU 或 mutex
读侧不能容忍旧数据 RCU 天然允许一段窗口内读到旧版本 加 deleted 标志 + 每项锁，或直接上锁
数据不是指针访问的 RCU 靠指针原子替换发布新版本 静态对象改不了指针，没法发布
内存紧张 延迟释放期间新旧两份并存，峰值翻倍 缩短宽限期，或换锁
读侧临界区很长 宽限期被拖长，回调堆积 缩短临界区，或换锁
需要读者阻塞写者 RCU 的读者压根不阻塞写者 rwlock / seqlock
单次访问，没有热点 收益本来就小，复杂度白加 直接上锁

「内存紧张」这条对嵌入式尤其要算。素材 6 的总结很实：延迟的删除或释放会占用内存，尤其对嵌入式系统这是很贵的内存开销。

「读侧临界区很长」容易被忽略。宽限期要等所有 CPU 过 QS，读者临界区越长，它所在的 CPU 越晚过 QS。一个跑 10ms 的读侧临界区，会让这 10ms 内注册的所有回调都等着。

十六、易错点速查 #

# 现象 根因 改法
1 高负载下偶发 use-after-free 摘链后直接 kfree 加 synchronize_rcu() 或 call_rcu()
2 scheduling while atomic 读侧临界区里调了睡眠函数 挪出临界区，或改 SRCU
3 保护看起来没生效 写侧用 call_rcu_bh，读侧用 rcu_read_lock 变体配对
4 链表遍历跳到垃圾地址 多写者没加锁，next 被改坏 写侧加 spinlock
5 模块卸载后崩在回调里 漏了 rcu_barrier() 卸载前先 barrier
6 读者拿到旧值，业务出错 用了「只增删」模型但业务要强一致 加 deleted 标志 + 每项锁
7 出了临界区还用指针 把指针存到了全局或结构体里 加引用计数，或缩短使用范围
8 遍历函数用错 用了 list_for_each_entry 而非 _rcu 版本 换成 list_for_each_entry_rcu
9 反向：唯一的删除路径用了 _rcu 白付屏障开销 确认无并发后用普通版本
10 list_del_rcu 后 next 被判无效 以为它和 list_del 一样毒化两边 记住 next 保留给读者
11 回调里 kmalloc(GFP_KERNEL) 卡死 回调跑在 softirq 上下文 只用 GFP_ATOMIC，或挪到 workqueue
12 宽限期莫名其妙很长 有 CPU 长期跑 softirq 或长临界区 换 bh 变体，或缩短临界区
13 加锁顺序死锁 在 RCU 临界区里拿了会睡眠的锁 RCU 临界区内只拿 spinlock
14 在读侧临界区里等信号量 把 RCU 当互斥锁用 RCU 不提供互斥

第 14 条值得单独说。rcu_read_lock() 名字骗人，它不排除任何其他执行流：两个读者能同时读，写者也能同时写。指望它做互斥，等于什么都没做。
