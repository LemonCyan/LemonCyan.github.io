一、从 API 到内部：一次 clk_set_rate 走过了什么 #

先建立全局的位置感。clk_set_rate 是个很薄的壳，它做三件事：拿锁、算、下发。

c
/* drivers/clk/clk.c，linux-3.10.29 */
int clk_set_rate(struct clk *clk, unsigned long rate)
{
        struct clk *top, *fail_clk;
        int ret = 0;
        /* prevent racing with updates to the clock topology */
        clk_prepare_lock();
        /* bail early if nothing to do */
        if (rate == clk->rate)
                goto out;
        if ((clk->flags & CLK_SET_RATE_GATE) && clk->prepare_count) {
                ret = -EBUSY;
                goto out;
        }
        /* calculate new rates and get the topmost changed clock */
        top = clk_calc_new_rates(clk, rate);
        if (!top) {
                ret = -EINVAL;
                goto out;
        }
        /* notify that we are about to change rates */
        fail_clk = clk_propagate_rate_change(top, PRE_RATE_CHANGE);
        if (fail_clk) {
                pr_warn("%s: failed to set %s rate\n", __func__,
                                fail_clk->name);
                clk_propagate_rate_change(top, ABORT_RATE_CHANGE);
                ret = -EBUSY;
                goto out;
        }
        /* change the rates */
        clk_change_rate(top);
out:
        clk_prepare_unlock();
        return ret;
}

五个阶段，各管一件事：

阶段 代码 干什么 失败返回
1 取锁 clk_prepare_lock() 整个时钟拓扑的全局互斥，防止一边改树一边遍历 —
2 早退 rate == clk->rate；CLK_SET_RATE_GATE 且已 prepare 无事可做；或这个 clock 正被使用，不允许变频 0 / -EBUSY
3 试算 clk_calc_new_rates(clk, rate) 把要改的 rate 写进沿途每个节点的 new_rate，返回「最顶层那个要动的节点」 NULL → -EINVAL
4 通知 clk_propagate_rate_change(top, PRE_RATE_CHANGE) 自顶向下问每个监听者：这个频率你接受吗 返回拒绝者 → -EBUSY
5 落地 clk_change_rate(top) 从最顶层开始一个个写硬件、重算子树 无返回值

clk_round_rate 是同一套计算流程的只读版：走一样的协商逻辑，但不写硬件、不改缓存。

text
CLK_OF_DECLARE(fixed_clk, "fixed-clock", of_fixed_clk_setup)
        │  编译期把 of_device_id 塞进 __clk_of_table section
        ▼  of_clk_init(NULL) 遍历并匹配 DTS 的 compatible
        ▼  of_fixed_clk_setup(np)：读 clock-frequency，注册，再 of_clk_add_provider

核心结论只有一句：一次 clk_set_rate 动的是一个节点还是一条链，取决于 top 指针落在哪里。 clk_calc_new_rates 返回的 top 就是这条链的顶端，clk_change_rate(top) 从 top 往下逐级落地。这条链怎么算出来的，是第三章到第六章的全部内容。

和框架层的接缝： 框架层那把 struct clk 当句柄讲，本章把它当「用户持有的一份引用」讲。4.x 里 clk_set_rate 的写法变成 clk_set_rate(core->clk, rate)，然后落到 clk_core_set_rate_nolock(core, rate)，逻辑顺序完全一样，只是 clk 和 clk_core 拆成了两层。

new_rate 单独存在，是因为变频是个两阶段过程：先全部算完（写 new_rate），全部确认可行之后再一个个落地（读 new_rate，写 rate）。中间任何一步谈崩，new_rate 全部作废，rate 一动没动。这是整个 rate 协商能安全回滚的基础。

parent_names 那一坨 kstrdup 值得单独说：clk_register 先 kcalloc 一个指针数组，再对每一项 kstrdup 一份。注释写得很直白——in case parent_names is __initdata。平台写时钟表常用 static const char * const pname[] __initconst，或者栈上临时数组，free_initmem() 之后全是野指针，所以 CCF 必须自己拷一份。这条约束一直没变过，移植时把父名字数组放 __initdata 的代价就是注册完 clock 名字变乱码。

这次拆层的动机，看一个字段就明白：exclusive_count。clk_core 是硬件节点，全局唯一；struct clk 是一个使用者手里的引用，可以有 N 份。同一个 UART 时钟被两个驱动 clk_get，内核里只有一份 clk_core（计数、频率状态都在这），但有两份 struct clk（各自的 dev / con_id）。3.10 里这两件事是同一个结构体，一旦有人想独占使用（clk_get_exclusive），就没地方记。

本章约定： 3.10 的代码贴原样（字段名 clk->xxx），4.x 的行为用 clk_core->xxx 描述。看到 clk->rate 就知道是 3.10 单层，看到 core->rate 就是 4.x。

三、rate 的传播：父子之间怎么协商 #

问题的本质：clk_set_rate(leaf, 48MHz)，但 leaf 是个 divider，自己不会产生频率，它的频率只由 parent 和分频比决定。要得到 48MHz，要么改分频比，要么改 parent，要么改 parent 的 parent。CCF 的策略是先往上问，问到一个能满足的层级再停下。

这个「能停在哪」由 CLK_SET_RATE_PARENT 决定：

clock 的情况 CCF 的行为
没有 .round_rate，没有 CLK_SET_RATE_PARENT 拒绝，-EINVAL。这个节点自己不会变频，也不许动上层
没有 .round_rate，有 CLK_SET_RATE_PARENT 把请求原样转给 parent，递归
有 .round_rate 就地算，.round_rate 返回它能给的最接近值
有 .round_rate 且 CLK_SET_RATE_PARENT，但算不出 继续往上问 parent

__clk_round_rate 是这套逻辑的只读版，最直白：

c
/* drivers/clk/clk.c，linux-3.10.29 */
unsigned long __clk_round_rate(struct clk *clk, unsigned long rate)
{
        unsigned long parent_rate = 0;
        if (!clk)
                return 0;
        if (!clk->ops->round_rate) {
                if (clk->flags & CLK_SET_RATE_PARENT)
                        return __clk_round_rate(clk->parent, rate);
                else
                        return clk->rate;
        }
        if (clk->parent)
                parent_rate = clk->parent->rate;
        return clk->ops->round_rate(clk->hw, rate, &parent_rate);
}

三个分支对应上表。注意 round_rate 的第三个参数是 unsigned long *——输入输出双向。进去时是 parent 当前频率，出来时可以变成「我觉得 parent 也该改成这个值」。这一个指针就是第五章「round 和 set 为什么要联动」的全部伏笔。

真正改频率时的传播路径长这样：

text
向上协商（calc）：  uart0 ──► gate ──► div_hclk ──► pll
                 走到有 .round_rate（能就地定值）或 CLK_SET_RATE_PARENT（允许往上）为止
向下落地（change）：pll ──► div_hclk ──► gate ──► uart0
                 从 top 开始，逐级 .set_rate + 重算整棵子树

两条铁律：

  1. 向上只走到有 .round_rate 或有 CLK_SET_RATE_PARENT 的节点。 一个纯 gate 节点（只有 .enable / .disable）是透明的，rate 原样透传，既不拦请求也不处理。
  2. 向下必须走完整棵子树。 上层 rate 一变，所有下游的 recalc_rate 都得重跑，因为你不知道别人缓存的那份频率眼下是什么情况。

传播路径上的每个节点会经历三种状态，这是判断 bug 的关键：

状态 rate new_rate 含义
未参与 原值 未定义 这次变频跟它无关，没被 clk_calc_new_rates 访问
已试算未提交 原值 新值 clk_calc_new_rates 走过了，等 clk_propagate_rate_change 的结果
已提交 新值 新值 clk_change_rate 已经落地

中途 abort 时，会有一批节点卡在「已试算未提交」状态，rate 还是旧的，new_rate 是作废的。这不算 bug，new_rate 只是下一次计算会覆盖的临时格。真正要小心的是：任何在 notifier 回调里读 new_rate 的代码，在 abort 之后读到的是垃圾值。

一种要避免的写法： 素材原文注 4 说得很直接——「clock rate set 有 2 种场景，一是只需修改自身的配置，二是需要同时修改 parent 的 rate（可向上递归）。原文建议少用第二种，以保持系统的简洁性。」跨层改 rate 意味着你的驱动在改别人的硬件配置，一旦有两个驱动都这么干，就是经典的「最后写赢」，而且谁都复现不出对方的现场。

四、clk_calc_new_rates 的算法 #

这是 clk_set_rate 的第一个核心函数。名字是 clk_calc_new_rates（3.10），4.x 里叫 clk_calc_new_rates 的已经是 clk_core_calc_rate_up / clk_core_calc_new_rates 一族，函数名和拆分方式都变过，具体对应关系未逐行核对。

3.10.29 的形态：

c
/* drivers/clk/clk.c，linux-3.10.29，函数职责概述 */
static struct clk *clk_calc_new_rates(struct clk *clk, unsigned long rate)
{
        struct clk *top = clk;
        unsigned long best_parent_rate = 0;
        unsigned long new_rate;
        unsigned int flags = clk->flags;
        /* 1. 先问自己能不能给 */
        new_rate = __clk_round_rate(clk, rate);
        if (new_rate == clk->rate && !(flags & CLK_SET_RATE_PARENT))
                return NULL;            /* 值没变，也没权限往上动，退出 */
        /* 2. 处理 parent：要么换父，要么改父的 rate */
        if (new_rate != rate && (flags & CLK_SET_RATE_PARENT)) {
                if (__clk_get_parent(clk) == clk->parent)
                        /* 递归：让 parent 也去算它的 new_rate */
                        top = clk_calc_new_rates(clk->parent, ...);
                else
                        /* 换了父，直接从新父开始 */
                        top = clk_calc_new_rates(clk->new_parent, ...);
        }
        /* 3. 记下中间值 */
        clk->new_rate = new_rate;
        return top;                     /* 返回最顶层那个要动的节点 */
}

勘误说明： 上面这段是按 3.10 源码结构与素材原文描述重写的骨架，素材第 1 篇对 clk_calc_new_rates 只给了 clk_set_rate 的调用点，没有贴函数体全文。本章的形态描述基于 clk_set_rate 的调用契约与其注释「calculate new rates and get the topmost changed clock」，逐行原文未验证。要精确到行，请以手里内核的 drivers/clk/clk.c 为准。

算法骨架 #

不管版本怎么变，骨架是固定四步：① round(clk, rate) 拿最接近值；② 如果它等于 clk->rate 且没有 CLK_SET_RATE_PARENT，返回 NULL（这就是 clk_set_rate 返回 -EINVAL 的那条路）；③ 如果拿不到想要的 rate 又有 CLK_SET_RATE_PARENT，让 parent 用同样的 rate 再算一次；④ 写 clk->new_rate，返回更新过的 top。

为什么返回值是 top 而不是成功/失败 #

因为要改的往往不止一个节点。举个例子：

c
clk_set_rate(uart0, 115200 * 16);

uart0 是个 divider，父是 pclk，pclk 父是 hclk，hclk 父是 mpll。如果 uart0 的 .round_rate 说「我最多只能给到 1.8MHz，再高得改 pclk」，而 pclk 又有 CLK_SET_RATE_PARENT，那么真正要写硬件的就是 hclk 的分频寄存器 + uart0 的分频寄存器两个点。top 指向上层那个（hclk 或更上），clk_change_rate(top) 从它开始往下走，两个点都会被走到。

两个「没变化」的区分 #

代码里有两处判断「值没变」，语义完全不同：

位置 判断 含义
clk_set_rate 入口 rate == clk->rate 用户请求的值和当前值相同，整个流程不用启动
clk_calc_new_rates new_rate == clk->rate round 之后的结果和当前值相同，这个节点不用动

第一处是捷径，第二处是精确判断。区别在于：用户请求 48MHz，实际 round 出来还是 48MHz，但下游有别的节点受牵连（比如 parent 要改）。真正的判断依据永远是「有没有节点的 new_rate != rate」。

支持链上的三类节点 #

节点类型 .round_rate CLK_SET_RATE_PARENT 在计算里的角色
PLL / 可编程时钟 有 一般没有 链的终点，它就是能定值的那层
divider / mux 有 视情况 中间层，能改自己，改不了就把请求往上递
gate 没有 有（透明） 透传，不参与 rate 计算，只在 enable 链上重要
叶子外设时钟 视情况 视情况 链的起点，用户调用的入口

五、determine_rate 与 round_rate 的关系 #

round_rate 老了，determine_rate 是它的替代品，但两者长期并存，原因很实在：round_rate 的表达能力不够。

表达能力的问题 #

round_rate 的签名：

它的签名是 long (*round_rate)(struct clk_hw *hw, unsigned long rate, unsigned long *parent_rate)——第三个参数是输入输出双向。 它只能告诉 CCF 两件事：我能给的最接近值，以及我建议的 parent 频率（通过 *parent_rate 回写）。它没法说：

  • 「我不行，但我的另一个 parent 可以」——换父得在 .set_parent 里单独做。
  • 「我这个值只能在我的第 2 个 parent 上得到」——parent 的索引无处安放。
  • 「我给出这个值的时候，精度（accuracy）是多少」。
  • 「我给出的值和你要的值差多少，这个差值我接受不了」。

determine_rate 换了参数，把这些问题一次性收进一个结构体：

c
/* include/linux/clk-provider.h，4.16 前后的形态 */
struct clk_rate_request {
        unsigned long rate;              /* 请求值 */
        unsigned long min_rate;          /* 可接受下界 */
        unsigned long max_rate;          /* 可接受上界 */
        unsigned long best_parent_rate;  /* 建议的 parent 频率 */
        struct clk_hw *best_parent_hw;   /* 建议的 parent */
};
int (*determine_rate)(struct clk_hw *hw, struct clk_rate_request *req);

对应关系：

能力 round_rate determine_rate
给出最接近值 返回值 req->rate 回写
建议 parent 频率 *parent_rate 输出参数 req->best_parent_rate
建议具体哪个 parent 无法表达 req->best_parent_hw
表达容忍区间 无法表达 req->min_rate / max_rate
表达精度 无法表达 走 .recalc_accuracy（另一条路）

移植时的判断方法 #

不要猜，直接 grep：

bash
grep -n "set_rate" include/linux/clk-provider.h | head -20
grep -rn "determine_rate" drivers/clk/*.c | head

如果头文件里 struct clk_ops 有 determine_rate 成员，你的 provider 就可以实现它；如果只有 round_rate，写了也编译不过。反过来说，一个老 provider 在新内核上继续只实现 round_rate 是合法且能工作的，CCF 会走兼容路径——但会失去「自动选择更优 parent」的能力，多 parent 的 mux 尤其明显：round_rate 版本只能按当前 parent 算，父选错了就只能接受差的结果。

六、冲突处理：谁来否决一次变频 #

clk_calc_new_rates 算完了，但「算得出」不等于「该做」。有些硬件在特定状态下不能变频——比如某个 PLL 正在给 DDR 供时钟，此刻改它会挂；或者某个外设已经准备好了，变频会让它失步。这类否决权交给 clock notifier。

clk_propagate_rate_change 就是收否决票的地方。它从 top 开始自顶向下遍历整棵子树，对每个挂着 notifier 的节点触发一遍：

c
/* drivers/clk/clk.c，linux-3.10.29，函数职责概述 */
static struct clk *clk_propagate_rate_change(struct clk *clk,
                                             unsigned long event)
{
        struct clk *child, *fail_clk = NULL;
        int ret = NOTIFY_DONE;
        if (clk->rate == clk->new_rate && event == PRE_RATE_CHANGE)
                goto skip;            /* 这个节点的频率其实没变，不问 */
        switch (event) {
        case PRE_RATE_CHANGE:
                if (clk->notifier_count)
                        ret = __clk_notify(clk, event, clk->rate, clk->new_rate);
                if (ret & NOTIFY_STOP_MASK)
                        fail_clk = clk;
                break;
        case POST_RATE_CHANGE:
                if (clk->notifier_count)
                        __clk_notify(clk, event, clk->new_rate, clk->rate);
                break;
        case ABORT_RATE_CHANGE:
                if (clk->new_rate == clk->rate)
                        goto skip;
                else if (clk->notifier_count)
                        __clk_notify(clk, event, clk->new_rate, clk->rate);
                break;
        }
skip:
        hlist_for_each_entry(child, &clk->children, child_node) {
                struct clk *tmp = clk_propagate_rate_change(child, event);
                if (tmp)
                        fail_clk = tmp;
        }
        return fail_clk;
}

勘误说明： 这段是按素材原文对 clk_propagate_rate_change 的描述重写的骨架（自顶向下递归、PRE / POST / ABORT 三种 event、NOTIFY_STOP_MASK 判定失败），逐行原文未验证。要点在于三个 event 的语义与「失败后立刻反向广播 ABORT」这一对动作。

三个 event 的时序 #

时序只有一条主线：clk_calc_new_rates 算出 top → 自顶向下 propagate(PRE)，对每个 new_rate != rate 的节点问一遍，任一方返回 NOTIFY_BAD 就记下 fail_clk → 有 fail_clk 就 propagate(ABORT) 撤回并返回 -EBUSY；没有就 clk_change_rate(top) 落地，再 propagate(POST)，返回 0。 关键设计：ABORT 是必须的。已经收到的 PRE 通知是一份承诺——监听者据此做了准备动作（暂停采样、切换时钟源）。如果变频最终失败却不告诉它，监听者会一直停在「准备中」状态。ABORT_RATE_CHANGE 把这笔账结掉。

通知的参数 #

__clk_notify 传给回调的 struct clk_notifier_data：

c
struct clk_notifier_data {
        struct clk              *clk;      /* 被通知的 clock */
        unsigned long           old_rate;  /* 变之前 */
        unsigned long           new_rate;  /* 变之后（PRE 时是预期值） */
};

PRE 事件里 new_rate 是预期值而不是实际值——如果后面 abort 了，它永远没发生。POST 事件里 old_rate 是预期旧值，new_rate 才是从硬件 recalc_rate 读回来的真实值，两者会因硬件精度不一致而有偏差。

两种否决来源 #

来源 触发点 代价
flag 级否决 CLK_SET_RATE_GATE + prepare_count != 0，在 clk_set_rate 入口直接 -EBUSY 最便宜，不进入计算
notifier 级否决 NOTIFY_BAD，在 PRE 阶段 走完了整个计算+广播，abort 时还得再广播一轮

用哪个？flag 能表达的别用 notifier。 CLK_SET_RATE_GATE 是「这个 clock 有人用着就别动」的标准表达，写在 hw->init->flags 里，零运行时开销。notifier 是给「有外部状态需要协商」的场景用的，比如 DPLL 给音频和视频两路供时钟，任一路都要求特定的整数分频比。

七、prepare 的引用计数 #

clk_prepare 背后的实现是 __clk_prepare（3.10），4.x 里是 clk_core_prepare。这段代码很短，但两处细节是 CCF 全部引用计数逻辑的样板：

c
/* drivers/clk/clk.c，linux-3.10.29 */
int __clk_prepare(struct clk *clk)
{
        int ret = 0;
        if (!clk)
                return 0;
        if (clk->prepare_count == 0) {
                ret = __clk_prepare(clk->parent);
                if (ret)
                        return ret;
                if (clk->ops->prepare) {
                        ret = clk->ops->prepare(clk->hw);
                        if (ret) {
                                __clk_unprepare(clk->parent);
                                return ret;
                        }
                }
        }
        clk->prepare_count++;
        return 0;
}

细节一：计数从 0 到 1 的那一次才真正干活。 后续每次 prepare 只是把计数加一，不碰硬件、不碰 parent。这样一对 prepare/unprepare 可以安全地被多层软件栈各调一次（比如平台驱动、子系统核心、设备驱动三层都 prepare 同一个时钟），谁都不用关心别人。

细节二：顺序是「先父后子」，且失败要回滚父。 __clk_prepare(clk->parent) 在前，clk->ops->prepare 在后。物理上锁相环必须先稳定，下游才能准备——顺序不能反。如果子节点 prepare 失败，已经把父节点 prepare 过了，必须 __clk_unprepare(clk->parent) 补偿，否则父节点的 prepare_count 就漏了一个。

这个「操作失败要回滚已做的步骤」的模式，是嵌套型 API 的标准写法，CCF 里每一处递归都这么写。

prepare 的回调语义（来自 clk_ops 注释）：允许睡眠。这是 prepare 存在的核心理由——PLL 上电要等锁定，mdelay 级别的时间，不能让 CPU 空转，得睡。而 enable 的回调不允许睡眠，因为 clk_enable 会在中断上下文里被调用。

八、enable 的引用计数与 prepare 的关系 #

enable 的计数逻辑和 prepare 一模一样，只是多一道前置检查：

c
/* drivers/clk/clk.c，linux-3.10.29，函数职责概述 */
int __clk_enable(struct clk *clk)
{
        int ret = 0;
        if (!clk)
                return 0;
        /* 关键：没 prepare 过就 enable，直接报错 */
        if (WARN_ON(clk->prepare_count == 0))
                return -ESHUTDOWN;
        if (clk->enable_count == 0) {
                ret = __clk_enable(clk->parent);   /* 先父 */
                if (ret)
                        return ret;
                if (clk->ops->enable) {
                        ret = clk->ops->enable(clk->hw);
                        if (ret) {
                                __clk_disable(clk->parent);   /* 回滚 */
                                return ret;
                        }
                }
        }
        clk->enable_count++;
        return 0;
}

对照 __clk_prepare，唯一的结构差异就是开头那个 WARN_ON。这个 WARN 是 CCF 最常被人撞到的一条，BUG: WARN_ON(core->prepare_count == 0) 的 dmesg 基本都来自「只调了 clk_enable，没调 clk_prepare」或者「prepare 和 enable 用的不是同一个 struct clk」。

两个计数的状态组合可以穷举完，一共四种合法、三种非法：

prepare_count enable_count 合法 状态 怎么到这儿
0 0 ✅ 完全关闭 初始状态；clk_disable_unprepare 到底
>0 0 ✅ 已准备未使能 clk_prepare 之后。PLL 已锁定、时钟已配置，但门没开
>0 >0 ✅ 已使能 clk_prepare_enable，正常工作状态
>0 >0（但 enable > prepare 做不到） — — __clk_enable 保证 enable_count <= prepare_count
0 >0 ❌ 非法 只 clk_enable 了没 clk_prepare；或 clk_unprepare 早于 clk_disable
0 0，但硬件开着 ⚠️ 泄漏 上层计数归零了但没走 clk_disable，硬件门忘关
>0 0，但硬件关着 ⚠️ 反泄漏 有人绕过 CCF 直接写了 gate 寄存器

enable_count <= prepare_count 是 CCF 的硬不变量。 它由 __clk_enable 的 WARN_ON 强制。一旦这个不等式被破坏，说明调用方违反了 API 契约，后续所有状态判断都不可信，debugfs 里看到的 enable_cnt / prepare_cnt 也不能再当依据。

两套计数必须成对的地方，还有一个隐性约束：prepare 和 enable 的引用必须来自同一个 struct clk。4.x 拆层之后，两份 struct clk 指向同一个 clk_core，prepare_count 记在 clk_core 上，所以 A 驱动 prepare、B 驱动 enable 在计数上是允许的（物理上确实只需要一个 prepare）——但这会让 devm_clk_get 的自动释放彻底失效：A 驱动 unbind 时 devres 替它 clk_put，B 手里那份引用并没有跟着失效，而 prepare_count 也许已经归零。这类 bug 的现场是「unbind 之后再 bind 一个驱动，时钟状态莫名其妙」。

九、两段式设计的原因 #

为什么不是一个 clk_enable 完事？因为约束不同。

维度 prepare / unprepare enable / disable
上下文要求 可以睡眠 不能睡眠
典型调用点 probe、runtime_resume、打开设备 中断处理、atomic 上下文、dma 回调
典型耗时 毫秒级（等 PLL 锁定、等电源稳定） 微秒级（写一个 bit）
保护用的锁 prepare_lock（mutex） enable_lock（spinlock）
谁定义语义 硬件相关：这一步做什么 硬件相关：开哪个门

clk_ops 的注释把这条讲得很明确：

text
 * The clk_enable/clk_disable and clk_prepare/clk_unprepare pairs allow
 * implementations to split any work between atomic (enable) and sleepable
 * (prepare) contexts.  If enabling a clock requires code that might sleep,
 * this must be done in clk_prepare.  Clock enable code that will never be
 * called in a sleepable context may be implemented in clk_enable.
 *
 * Typically, drivers will call clk_prepare when a clock may be needed later
 * (eg. when a device is opened), and clk_enable when the clock is actually
 * required (eg. from an interrupt). Note that clk_prepare MUST have been
 * called before clk_enable.

素材原文举的例子很好：使能 PLL 要先启动它，再等它稳定。PLL 的锁定时间对音频用的 PLL 是毫秒量级，这段时间 CPU 什么都不做地空转（udelay 循环）是纯粹的浪费。拆成两段，这段等待就可以放在 prepare 里用 msleep，把 CPU 交出去。

反过来说，enable 里面就只能是「写一个寄存器位」这种操作。这也是为什么 clk_gate 这个最基础的时钟类型只实现 .enable / .disable / .is_enabled，不实现 .prepare——它没有可睡眠的事情要做。

两个组合 API 的来历 #

c
static inline int clk_prepare_enable(struct clk *clk)
{
        int ret;
        ret = clk_prepare(clk);
        if (ret)
                return ret;
        ret = clk_enable(clk);
        if (ret)
                clk_unprepare(clk);
        return ret;
}

clk_prepare_enable 就是一个带失败回滚的顺序调用。它的存在理由很朴素：九成的调用场景是「我现在就要这个时钟」，分两步写既啰嗦又容易漏。素材原文的说法是「如果调用者能确保是在 non-atomic 上下文中调用，就可以顺序调用 prepare/enable，为了简单，framework 就帮忙封装了这两个接口」。

但要知道这个便利的代价：clk_prepare_enable 只能在能睡眠的上下文调用，因为它里面含了 clk_prepare。在中断里想开时钟，只能 clk_enable——而这就意味着这个时钟必须在某处已经 prepare 过了。这条约束是移植文件系统、网络这类「中断里要访问硬件」的驱动时最容易踩的地方。

十、时钟门控的硬件实现 #

gate 是 CCF 里最简单也最普遍的一类时钟。硬件上它是一个与门，软件上它就是一个寄存器里的一个 bit。

c
/* include/linux/clk-provider.h */
struct clk_gate {
        struct clk_hw hw;
        void __iomem    *reg;      /* 控制该 clock 开关的寄存器地址（虚拟地址） */
        u8              bit_idx;   /* 控制 clock 开关的 bit 位 */
        u8              flags;     /* gate 专属 flag */
        spinlock_t      *lock;     /* 如果 clock 开关是独享的，可以使用自旋锁 */
};

c
#define CLK_GATE_SET_TO_DISABLE         BIT(0)
#define CLK_GATE_HIWORD_MASK            BIT(1)
#define CLK_GATE_BIG_ENDIAN             BIT(2)

三个 flag 各对应一类真实坑：

flag 硬件长什么样 不加会怎样
CLK_GATE_SET_TO_DISABLE 位写 1 是关，写 0 是开（反相） 逻辑全反，该开的关、该关的开，probe 时外设直接没响应
CLK_GATE_HIWORD_MASK 低 16 位是数据，高 16 位是写使能掩码 写操作被硬件忽略，寄存器值看起来是对的，时钟纹丝不动
CLK_GATE_BIG_ENDIAN 寄存器是大端序访问 在 little-endian SoC 上操作大端寄存器会写错位

CLK_GATE_HIWORD_MASK 这一类最坑。它不是「写错」，是「写了但没生效」，__raw_readl 回去看值还全对。这类 SoC（不少三星、瑞芯微的设计）必须把 (bit << 16) | bit 一起写进去。

clk_register_gate 的签名，从参数就能看出它对硬件的全部假设：

c
struct clk *clk_register_gate(struct device *dev, const char *name,
                const char *parent_name, unsigned long flags,
                void __iomem *reg, u8 bit_idx,
                u8 clk_gate_flags, spinlock_t *lock);
参数 描述的是什么硬件事实
name / parent_name 节点在树里的位置
flags CCF 层的 flag（CLK_IGNORE_UNUSED、CLK_SET_RATE_PARENT 等）
reg + bit_idx 门在哪
clk_gate_flags 门是正相还是反相、要不要 hiword mask、大小端

lock 传 NULL 的后果：clk_gate_ops 里对锁做了判空，NULL 就跳过加锁。如果两个 gate 恰好共享 CLKCON 这种寄存器，无锁的读-改-写序列在 SMP 上会丢写。S3C2440 是单核、老的 ARMv4T，这个坑根本不显现，所以三星那批代码里大量 GATE(..., 0) 最后一位传 0。换到多核平台照抄这个习惯就要出问题。

S3C2440 的实际例子：

c
/* drivers/clk/samsung/clk-s3c2410.c */
static struct samsung_gate_clock s3c2410_common_gates[] __initdata = {
        GATE(PCLK_SPI, "spi", "pclk", CLKCON, 18, 0, 0),
        GATE(PCLK_I2C, "i2c", "pclk", CLKCON, 16, 0, 0),
        ...
        GATE(HCLK_USBH, "usb-host", "hclk", CLKCON, 6, 0, 0),
        ...
};

GATE(HCLK_USBH, "usb-host", "hclk", CLKCON, 6, 0, 0) 读出来是：时钟名叫 usb-host，父是 hclk，门在 CLKCON 寄存器第 6 位，CCF flag 全 0，gate flag 全 0（正相、非 hiword、小端）。这个 clock 后面还会出现——USB 那个案例的一半就在它身上。

gate 在 rate 传播里的角色要记牢：它是透明的。 它没有 .round_rate，CLK_SET_RATE_PARENT 一般会置，于是 clk_set_rate(gate) 会把请求原样递给父。所以对 i2c、uart0 这类「父是 pclk/hclk 的 gate」，调 clk_set_rate 等于调父的 clk_set_rate，会改整条总线的频率。素材原文那句「如果直接调用 clk_set_rate 函数设置频率，clk_set_rate 会向上传递，即设置它的父时钟频率」讲的就是这件事，这也是为什么对 gate 时钟调 set_rate 多半不是你想要的动作。

十一、clock notifier：谁在监听频率变化 #

接口只有两个：

c
int clk_notifier_register(struct clk *clk, struct notifier_block *nb);
int clk_notifier_unregister(struct clk *clk, struct notifier_block *nb);

语义：某个驱动关心某个 clock，希望这个 clock 的 rate 改变时通知到自己，就注册一个 notifier。这是标准的 notifier_block 套路，nb->notifier_call 的返回值决定后续：

返回值 效果
NOTIFY_DONE 我看过了，没问题，继续通知别人
NOTIFY_OK 同 NOTIFY_DONE，语义上表示「明确同意」
NOTIFY_BAD（含 NOTIFY_STOP_MASK） 否决这次变频，clk_propagate_rate_change 返回非空，clk_set_rate 最终返回 -EBUSY

内部维护 clk->notifier_count，注册时加一、注销时减一，clk_propagate_rate_change 就是靠它做快速判断——没有监听者就完全跳过，零开销。这个字段同时出现在 debugfs 的 clk_notifier_count 里，是判断「谁挂在这个 clock 上」的唯一运行时手段。

谁在用 #

实际内核里挂 notifier 的地方不多，但都很典型：

用途 谁挂 关心什么
CPUfreq 的 CPU 时钟 cpufreq 驱动 / clk-cpufreq 频率变了要通知上层更新 OPP 表、重算 loops_per_jiffy
音频子系统 ASoC 的 clk 组件 父时钟变了，采样率跟着变，要重新配置 I2S 分频
显示子系统 DRM/KMS 驱动 像素时钟变了，说明分辨率或刷新率要改，reject 掉意外变更
看门狗 / 定时器 少数平台 时钟源变了会改变超时周期，不能接受
性能监控 平台 DVFS 驱动 记录变频历史，做功耗模型

一个现实约束 #

notifier 回调运行在 clk_prepare_lock（mutex）被持有的上下文里。这意味着：

  • 回调里不能睡眠的假设不成立——它在进程上下文，可以睡眠。但不能反向调用 CCF API，那会重复拿同一把 mutex，直接死锁。
  • 回调里能做的事：读寄存器、记录、设置一个标志、唤醒别的线程。不能做的：clk_set_rate、clk_set_parent、clk_prepare、任何进 clk.c 的调用。

这条约束在框架层第二十五章易错点第 14 条已经点过，这里补上原因：不是因为它是「notifier 就危险」，而是因为 clk_prepare_lock 不可重入。

十二、notifier 的注册与回调时机 #

注册的模板：

c
static int foo_clk_notifier_call(struct notifier_block *nb,
                                 unsigned long event, void *data)
{
        struct clk_notifier_data *ndata = data;
        struct foo_priv *priv = container_of(nb, struct foo_priv, clk_nb);
        switch (event) {
        case PRE_RATE_CHANGE:      /* 变频前，可以说不行 */
                return (ndata->new_rate % priv->sample_base) ? NOTIFY_BAD
                                                              : NOTIFY_DONE;
        case POST_RATE_CHANGE:     /* 变频成功，new_rate 是硬件读回的真实值 */
                foo_recalc(priv, ndata->new_rate);
                break;
        case ABORT_RATE_CHANGE:    /* 被否决，清理 PRE 里做的准备 */
                foo_abort(priv);
                break;
        }
        return NOTIFY_DONE;
}
/* 注册 */
priv->clk_nb.notifier_call = foo_clk_notifier_call;
ret = clk_notifier_register(priv->clk, &priv->clk_nb);

三个事件的精确时序，把前面几章串起来：

text
clk_set_rate(leaf, target)
  ├─ clk_prepare_lock()
  ├─ clk_calc_new_rates  → 算出 top，沿线写 new_rate
  ├─ propagate(PRE)      → 每个 new_rate != rate 的节点问一遍，可被 NOTIFY_BAD 否决
  │     └─ 被否决 → propagate(ABORT) 通知撤回 → 返回 -EBUSY
  ├─ clk_change_rate(top) → 逐级 .set_rate + 重算子树
  ├─ propagate(POST)     → 通知 (old, new_actual)，只告知不可否决
  └─ clk_prepare_unlock()

读到三个关键事实：

  1. PRE 的 new_rate 是承诺值，POST 的 new_rate 是实测值。 两者会不等，因为 .set_rate 之后要 .recalc_rate 回读，硬件精度、分频比取整都会造成偏差。在 POST 里应该用 ndata->new_rate，别用你在 PRE 里记下的那个数。
  2. ABORT 的参数顺序和 PRE 相反。 PRE 是 (old → new)，ABORT 是 (new → old)——表达「从那个没发生的新值，回到原值」。
  3. POST 无否决权。 clk_propagate_rate_change 在 POST 分支里不看返回值。频率已经写进硬件了，你再说「不行」没有意义，只能记录。

一个常被忽略的细节：跳过条件 #

clk_propagate_rate_change 里对每个节点先判断 clk->rate == clk->new_rate，相等就 goto skip——这个节点频率其实没变，不问它。这个优化带来一个副作用：如果一个 clock 在计算过程中 new_rate 被设成了与 rate 相同的值（比如 round 之后恰好回到原值），挂着 notifier 也收不到通知。

调试时的表现是「我给 uart0 设了个新频率，但 uart0 的 notifier 没触发，反而是它父节点的 notifier 触发了」。这不是 bug，是 uart0 的 round 结果没变，真正变的是父。

注销 #

c
clk_notifier_unregister(priv->clk, &priv->clk_nb);

必须在 clk_put 之前。notifier 链表挂在 clk 上（4.x 是 clk_core 上），clock 被释放了再注销就是 use-after-free。用 devm 风格的驱动，要确保退出路径的顺序：先 unregister，再让 devres 回收 clk。

十三、CCF 在 clk 注册时的树构建 #

到这里可以回答一个问题：那棵 clock 树是什么时候、由谁拼起来的？答案是 __clk_init，它在每次 clk_register 的末尾被调用一次。

c
/* drivers/clk/clk.c，linux-3.10.29。长段英文注释压成行内注释，控制流未改 */
int __clk_init(struct device *dev, struct clk *clk)
{
        int i, ret = 0;
        struct clk *orphan;
        struct hlist_node *tmp2;
        if (!clk)
                return -EINVAL;
        clk_prepare_lock();
        /* 查重：clock 以 name 唯一识别 */
        if (__clk_lookup(clk->name)) {
                pr_debug("%s: clk %s already initialized\n",
                                __func__, clk->name);
                ret = -EEXIST;
                goto out;
        }
        /* ops 完整性：set_rate 必须配 round_rate + recalc_rate */
        if (clk->ops->set_rate &&
                        !(clk->ops->round_rate && clk->ops->recalc_rate)) {
                pr_warning("%s: %s must implement .round_rate & .recalc_rate\n",
                                __func__, clk->name);
                ret = -EINVAL;
                goto out;
        }
        /* set_parent 必须配 get_parent */
        if (clk->ops->set_parent && !clk->ops->get_parent) {
                pr_warning("%s: %s must implement .get_parent & .set_parent\n",
                                __func__, clk->name);
                ret = -EINVAL;
                goto out;
        }
        for (i = 0; i < clk->num_parents; i++)
                WARN(!clk->parent_names[i],
                        "%s: invalid NULL in %s's .parent_names\n",
                        __func__, clk->name);
        /* 缓存候选父指针。允许留空洞：early boot 时父还没注册 */
        if (clk->num_parents > 1 && !clk->parents) {
                clk->parents = kzalloc((sizeof(struct clk*) * clk->num_parents),
                                GFP_KERNEL);
                if (clk->parents)
                        for (i = 0; i < clk->num_parents; i++)
                                clk->parents[i] =
                                        __clk_lookup(clk->parent_names[i]);
        }
        clk->parent = __clk_init_parent(clk);
        /* 三种归属 */
        if (clk->parent)
                hlist_add_head(&clk->child_node,
                                &clk->parent->children);
        else if (clk->flags & CLK_IS_ROOT)
                hlist_add_head(&clk->child_node, &clk_root_list);
        else
                hlist_add_head(&clk->child_node, &clk_orphan_list);
        /* 初始 rate：recalc_rate 优先，其次父的 rate，兜底 0 */
        if (clk->ops->recalc_rate)
                clk->rate = clk->ops->recalc_rate(clk->hw,
                                __clk_get_rate(clk->parent));
        else if (clk->parent)
                clk->rate = clk->parent->rate;
        else
                clk->rate = 0;
        /* 认领孤儿：有 get_parent 就问硬件，否则遍历 parent_names */
        hlist_for_each_entry_safe(orphan, tmp2, &clk_orphan_list, child_node) {
                if (orphan->ops->get_parent) {
                        i = orphan->ops->get_parent(orphan->hw);
                        if (!strcmp(clk->name, orphan->parent_names[i]))
                                __clk_reparent(orphan, clk);
                        continue;
                }
                for (i = 0; i < orphan->num_parents; i++)
                        if (!strcmp(clk->name, orphan->parent_names[i])) {
                                __clk_reparent(orphan, clk);
                                break;
                        }
        }
        /* .init 给怪异硬件的逃生口，kernel 明确不建议用 */
        if (clk->ops->init)
                clk->ops->init(clk->hw);
        clk_debug_register(clk);
out:
        clk_prepare_unlock();
        return ret;
}

按行拆，__clk_init 做六件事：

位置 动作 失败后果
查重 __clk_lookup(clk->name) -EEXIST。clock 以 name 唯一识别，不能同名
ops 完整性 set_rate → 必须配 round_rate + recalc_rate；set_parent → 必须配 get_parent -EINVAL
parent_names 空值检查 逐项 WARN 只警告，继续（后面会出问题）
建 parents[] 缓存 num_parents > 1 且未预置时 kzalloc + __clk_lookup 逐个填充 允许失败，后续懒填充
定 parent + 入链 有父 → parent->children；无父但有 CLK_IS_ROOT → clk_root_list；否则 → clk_orphan_list —
定初始 rate 优先 .recalc_rate(parent_rate)；次选父的 rate；兜底 0 —
认领孤儿 遍历 clk_orphan_list，匹配上的 __clk_reparent —

parents[] 懒填充与归属 #

parents[] 允许留空洞：early boot 时 kzalloc 会失败，且父节点还没注册，__clk_lookup 返回 NULL。任何访问 clk->parents[i] 的代码都必须判空并在缺失时补一次 lookup。这个设计是后面所有「注册顺序」问题能自愈的前提。

__clk_init_parent 与孤儿认领 #

父的个数 做法
0 parent = NULL
1 直接用 parent_names[0] 查一次
>1 必须有 .get_parent。回调返回硬件当前选中的 index，用 parents[index] 取出指针

多父必须实现 .get_parent 是硬性要求（Documentation/clk.txt 写明）——内核没法凭空知道硬件此刻选了哪一路，只能问。

末尾那段 hlist_for_each_entry_safe 就是认领机制：有 .get_parent 的问硬件 index 再比名字，没有的遍历 parent_names[] 挨个比，匹配上就 __clk_reparent。这就是注册顺序可以乱的原因；代价是启动阶段有一小段时间 clock 树是破碎的，clk_get_rate 在这些孤儿上返回 0。

全局链表与查找 #

text
clk_root_list     ← 所有 CLK_IS_ROOT 的 clock
clk_orphan_list   ← 无父且非 ROOT 的 clock（等待被认领）
__clk_lookup(name) 搜索：root_list → root → children …，orphan_list → orphan → children …

所以一个 clock 如果父链断在任何一级，它在下游 clk_get 是查不到的（-ENOENT），不是查到但 rate 为 0。两种故障现象完全不同，别混。

十四、of_clk 与 provider 的绑定 #

DTS 声明了 clock 之后，内核怎么把它们和实际的 struct clk 对上？链条是这条：

链条是：DTS clocks = <&clocks HCLK_USBH> → of_clk_get(np, index) 内部 of_parse_phandle_with_args(np, "clocks", "#clock-cells", index, &clkspec) → of_clk_get_from_provider(&clkspec) → provider 的 get 回调 → struct clk *。

of_clk_get_from_provider 的实现只有十几行，但它定义了 provider 的注册契约：

c
/* drivers/clk/clk.c */
struct clk *of_clk_get_from_provider(struct of_phandle_args *clkspec)
{
    struct of_clk_provider *provider;
    struct clk *clk = ERR_PTR(-ENOENT);
    /* Check if we have such a provider in our array */
    mutex_lock(&of_clk_lock);
    list_for_each_entry(provider, &of_clk_providers, link) {
        if (provider->node == clkspec->np)
            clk = provider->get(clkspec, provider->data);
        if (!IS_ERR(clk))
            break;
    }
    mutex_unlock(&of_clk_lock);
    return clk;
}

三个要点：

  1. 匹配靠 device_node 指针相等，不是靠 compatible 字符串。所以一个 provider 只能对应一个 DT node。
  2. 没有按 ID 建索引，是线性扫链表。provider 个数在个位数到几十，这个开销可以忽略。
  3. 找到 provider 之后，具体返回哪个 clock 由 provider->get 决定。clkspec->args[0] 就是 DTS 里写的那个 ID（HCLK_USBH = 33）。

把 HCLK_USBH 翻译成 struct clk * 由 provider 的 get 回调做，三星用 of_clk_hw_onecell_get：先按 clkspec->args[0] 取下标，下标越界 -EINVAL，这一格是 ERR_PTR(-ENOENT) 就 -ENOENT，否则返回 hw_data->hws[idx]。

c
/* include/linux/clk-provider.h */
struct clk_hw_onecell_data {
        unsigned int num;        /* 注册的时钟数量 */
        struct clk_hw *hws[];    /* 存储每一个时钟对应的 struct clk_hw * */
};

hws[] 按平台 ID 直接索引，下标必须和 ID 一一对应。samsung_clk_init 初始化时整片填成 ERR_PTR(-ENOENT)，分配失败直接 panic——clock provider 起不来整个 SoC 都跑不了，比继续跑到某个外设莫名其妙不工作要好定位。

反过来，写端只有一句：

c
if (!IS_ERR(clk))
        of_clk_add_provider(node, of_clk_src_simple_get, clk);

框架层第二十二章已经讲过 of_clk_add_provider 的返回值必须检查（它会先应用 assigned-clocks，失败则撤销注册）。这里补一个跟本章相关的点：of_clk_add_provider 之后的 clock 才能被 clk_get 找到。如果你的 provider 注册了 clock 但在 of_clk_add_provider 之前就让 consumer 去取（比如同一次 init 里同步地初始化了 UART），会拿到 -EPROBE_DEFER。

十五、clk 树的重建与延迟初始化 #

__clk_init 的孤儿机制解决的是「父后注册」的问题。但还有一层：整个 provider 的初始化时机。

of_clk_init 是这层的入口：

c
/* drivers/clk/clk.c */
void __init of_clk_init(const struct of_device_id *matches)
{
        struct device_node *np;
        if (!matches)
                matches = __clk_of_table;
        for_each_matching_node(np, matches) {
                const struct of_device_id *match = of_match_node(matches, np);
                of_clk_init_cb_t clk_init_cb = match->data;
                clk_init_cb(np);
        }
}

它扫的是 __clk_of_table 这个 section，往这个 section 里塞条目的是 CLK_OF_DECLARE：

CLK_OF_DECLARE(tag, compatible, callback) 在 __clk_of_table 里定义一个 struct of_device_id，compatible 填进去，data 填成 callback。

CLK_OF_DECLARE(tag, compatible, callback) 干的事：在 __clk_of_table 里定义一个 struct of_device_id，compatible 填进去，data 填成 callback。

三个关键性质：

  1. CLK_OF_DECLARE 走的是 early init，不是正常的 driver probe。 它在 time_init() 阶段就被调用，早于任何 module_init、早于 driver model。这是有意的：定时器、串口这些要在 driver model 起来之前就能拿到时钟。
  2. __clk_of_table 的顺序就是遍历顺序。 这个顺序由链接器按编译进 vmlinux 的目标文件顺序决定，不是声明顺序。所以「A provider 依赖 B provider 的 clock」这种跨 provider 的父链，会被初始化成孤儿——除非它们本来就在同一个 provider 里。
  3. of_clk_init 只处理 CLK_OF_DECLARE 注册的 provider。 用 platform_driver + of_clk_add_hw_provider 注册的 provider 走正常 probe 路径，顺序由 driver model 的依赖解析决定（-EPROBE_DEFER 兜底）。

孤儿链的最终收敛 #

把三件事串起来看：

text
时刻 T0: of_clk_init 按 __clk_of_table 顺序调用各 provider 的 setup
          每调一次 → clk_register → __clk_init
          父还没注册的 → 进 clk_orphan_list
          父已注册的   → 进 parent->children
时刻 T1: 后续每次 __clk_init 末尾都会扫 clk_orphan_list
          把「父名字 == 我刚注册的名字」的孤儿全部认领
时刻 T2: platform_driver 的 probe 阶段
          跨 provider 的依赖靠 -EPROBE_DEFER 重试
时刻 T3: clk_disable_unused()（late_initcall 之后）
          把没被任何驱动 get 的 clock 关掉（CLK_IGNORE_UNUSED 的除外）

T3 是最后一道坎。一个 clock 如果在整个启动过程里没被任何驱动 clk_get + prepare_enable，clk_disable_unused 会把它关掉。这解释了那个经典现象：bootloader 里开着某个外设的时钟，内核起来后外设不工作了，而 probe 看起来完全正常。因为 probe 没管时钟（靠 assume bootloader did it），而 clk_disable_unused 把那个「没人用」的时钟给关了。

三个应对手段，按推荐度排序：

手段 做法 适用
正确做法 驱动里 devm_clk_get + clk_prepare_enable 永远优先这个
标 flag `hw->init->flags = CLK_IGNORE_UNUSED`
内核参数 bootargs 加 clk_ignore_unused 只用于定位，别带上产线

clk_ignore_unused 的价值在于验证：加上它以后问题消失，就说明是 clk_disable_unused 干的，跟你的驱动逻辑无关。它是排查的第一步，不是修复。

4.x 的重建差异 #

4.x 里 __clk_init 被拆成 clk_core_init + clk_hw_create_clk，孤儿机制保留但实现变了：clk_core->orphan 变成一个显式的 bool 字段，不再靠「挂在哪个链表」来判断；重新认领的函数是 clk_core_reparent_orphans_nolock（函数名未逐行核对）。3.10 的 __clk_reparent(clk, new_parent) 在 4.x 是 clk_core_set_parent_nolock 一族 + clk_reparent。语义没变：换 parent 指针、换链表归属、重算整棵子树的 rate。

十六、reset framework：复位控制 #

CCF 讲完，接着讲 reset。这两套框架在同一个 SoC 的 clock/reset 寄存器块里挨着，driver 里也基本成对出现。

为什么需要它 #

复杂 IC 内部有很多独立功能的硬件模块：CPU core、GPU、USB 控制器、MMC 控制器。为功耗和稳定性，它们各自带一个复位信号，软件通过寄存器（一般 1 bit 控 1 个硬件）控制。驱动作者的需求很单纯：「我只想复位我的硬件，不想知道动的是哪个寄存器的哪个 bit。」这就是封装与抽象——驱动看到「reset」这个通用概念，寄存器细节归平台维护者。

层 提供什么 谁写

consumer 接口 device_reset / reset_control_* 内核
provider 接口 struct reset_controller_dev + struct reset_control_ops 平台 reset 驱动

要自动释放 devm_reset_control_get(dev, id)
多路一起操作 reset_control_get_shared / devm_reset_control_array_get + reset_control_assert_array

句柄拿到后三个动作：reset_control_reset / reset_control_assert / reset_control_deassert，用完 reset_control_put。DTS 侧就两行：

dts

    resets = <&rst 20>;
    reset-names = "reset";
};

resets 字段的具体格式（几个 cell、低位是什么）由 provider 决定，也就是由 provider 的 #reset-cells 决定。上面那个 20 就是一个 cell。

操作结构体只有三个回调：

    int (*reset)(struct reset_controller_dev *rcdev, unsigned long id);
    int (*assert)(struct reset_controller_dev *rcdev, unsigned long id);

一个最小 provider #

三星平台的 reset 控制器实现（drivers/reset/hisilicon/ 或 drivers/reset/reset-samsung.c，具体文件路径未验证）的形态大致是：

c
/* 形态示意：id 拆成"哪个寄存器的哪一位"，这是 provider 的全部核心 */
static int foo_reset_assert(struct reset_controller_dev *rcdev, unsigned long id)
{
        struct foo_reset *rst = to_foo_reset(rcdev);
        unsigned int reg = id / 32;              /* id → 寄存器 */
        unsigned int bit = id % 32;              /* id → bit 位 */
        spin_lock(&rst->lock);
        writel(BIT(bit), rst->base + reg + FOO_RESET_SET);
        spin_unlock(&rst->lock);
        return 0;
}
/* deassert 同理，写 FOO_RESET_CLR。结构体与注册只有这几行： */
static const struct reset_control_ops foo_reset_ops = {
        .assert   = foo_reset_assert,
        .deassert = foo_reset_deassert,
        /* 不实现 .reset：复位脉冲宽度由硬件自动保证 */
};
rcdev->ops = &foo_reset_ops;
rcdev->nr_resets = FOO_NR_RESETS;
rcdev->of_node = pdev->dev.of_node;
rcdev->of_reset_n_cells = 1;
return reset_controller_register(rcdev);

这段骨架里有两个值得注意的实现选择：

  1. .reset 没实现。 因为复位脉冲宽度由硬件自动保证（有些 SoC 的复位寄存器写一次就自动产生固定宽度的脉冲）。这种情况 consumer 必须用 reset_control_assert + reset_control_deassert，不能指望 reset_control_reset。
  2. id 到寄存器/bit 的换算在 provider 里。 这是 of_xlate 或 .assert 回调的职责边界——consumer 只知道「第 20 路」，不知道 20 落在哪个寄存器的哪一位。

reset 的计数语义 #

和 clock 的 prepare_count / enable_count 不同，reset_control 不维护引用计数。assert 两次就是 assert 两次（幂等），deassert 两次也是（幂等）。所以：

  • 两个驱动同时对同一个 reset 说话时，没有「谁先谁后」的保护。
  • devm_reset_control_get 只管句柄释放，不管状态回滚——驱动退出时不会自动把设备复位回默认状态。

这个差异在移植时要留意：clock 有计数，忘了 disable 是资源泄漏；reset 没有计数，忘了 deassert 就是设备永远起不来。

十八、CCF 与 reset 的配套使用 #

两者在真实驱动里的标准用法：

c
static int foo_probe(struct platform_device *pdev)
{
        struct clk *clk;
        struct reset_control *rstc;

        /* 1. 先拿资源 */
        clk  = devm_clk_get(&pdev->dev, "foo_clk");
        rstc = devm_reset_control_get(&pdev->dev, "foo_rst");
        if (IS_ERR(clk) || IS_ERR(rstc))
                return -ENODEV;

        /* 2. 开时钟 —— 复位动作需要时钟配合 */
        clk_prepare_enable(clk);

        /* 3. 复位 —— 在时钟已经跑起来的状态下 */
        reset_control_assert(rstc);
        udelay(1);
        reset_control_deassert(rstc);

        /* 4. 后面才是寄存器初始化、注册子系统 */
}

顺序不是随意的：

顺序 为什么
clock 先于 reset 有些模块的复位逻辑由时钟驱动，没时钟时 assert 不进去（保持状态不生效）
reset 在 clock 之后、寄存器访问之前 模块内部状态要回到初值，否则后续配置会落在脏状态上
deassert 之后留一点延时 复位释放到模块可访问之间有几个周期的同步延迟

反过来的错误顺序，故障现象是「寄存器读写全是 0 或全 1」——因为这根本不是「配置不对」，是模块还没出复位态，总线访问被挡住。

一个易混点：reset 与 clock gate 的关系 #

动作 影响的层次 恢复代价
clk_disable 门控，关掉时钟信号 便宜。再 clk_enable 即可恢复
reset_control_assert 模块内部所有寄存器回初值 贵。要重新配置全部寄存器

很多 SoC 的时钟控制器和复位控制器是同一个寄存器块，CLKCON 旁边就是 SWRST。这让「关时钟省电」和「复位」看起来像同一件事，实际完全不同。误把 reset 当省电手段用，代价是整个模块的配置丢失。

十九、一次真实的 CCF 移植：从 USB 超时说起 #

前面全是机制。现在看一个把 CCF 用到一个真实 bug 上的完整过程。平台是三星 S3C2440（ARM920T，arch/arm/mach-s3c24xx），内核是素材作者手头的 linux-5.2.8。

c
struct clk *devm_clk_get(struct device *dev, const char *id)
{
        struct clk **ptr, *clk;
        ptr = devres_alloc(devm_clk_release, sizeof(*ptr), GFP_KERNEL);
        if (!ptr)
                return ERR_PTR(-ENOMEM);
        clk = clk_get(dev, id);
        if (!IS_ERR(clk)) {
                *ptr = clk;
                devres_add(dev, ptr);
        } else {
                devres_free(ptr);
        }
        return clk;
}

devm 三步全在：devres_alloc 分配记录（devm_clk_release 在设备销毁时做 clk_put）、devres_add 挂到 dev->devres_head、失败路径 devres_free 立刻回收而不留在链表上（漏了就是每次 probe 失败泄漏一条悬空记录）。devres 本身见 Runtime PM 与驱动的电源管理；和 CCF 的交界只有 devm_clk_release → clk_put → 4.x 的 clk_core_put → 引用计数归零才真正释放 clk_core。

二十二、USB 设备识别超时的根因定位 #

回到问题本身。usb-bus-host 拿到了，clk_prepare_enable 也调了，那 UCLK 到底是不是 48MHz？

第一次尝试：在 start_hc 里改 UPLL #

网上流传的方案是在 s3c2410_start_hc 开头重新写 UPLL 配置寄存器：

c
        int rate = clk_get_rate(usb_clk);
        printk("------------------------before %d", rate);
        while (upllvalue != __raw_readl(S3C2410_UPLLCON)) {
                __raw_writel(upllvalue, S3C2410_UPLLCON);
                mdelay(1);
        }
        rate = clk_get_rate(usb_clk);
        printk("--------------------------after %d", rate);

注意这段代码的两个动作：先 clk_get_rate 看当前值，然后直接写硬件寄存器 S3C2410_UPLLCON，再 clk_get_rate 看一次。

实际跑出来是 before 48000000 / after 48000000——一点变化都没有。而设备确实识别到了（后面能看到 usbserial / ftdi_sio / pl2303 的注册日志），但几分钟后掉线。 前 48MHz，后 48MHz，一点变化都没有。 而设备确实识别到了（后面能看到 usbserial / ftdi_sio / pl2303 的注册日志），但几分钟后掉线。

为什么 clk_get_rate 两次都是 48MHz #

这是本章前面所有机制知识的直接应用。clk_get_rate 返回的是 clk->rate 缓存值，只有置了 CLK_GET_RATE_NOCACHE 才重算：

c
/* drivers/clk/clk.c，linux-3.10.29 */
unsigned long clk_get_rate(struct clk *clk)
{
        unsigned long rate;
        clk_prepare_lock();
        if (clk && (clk->flags & CLK_GET_RATE_NOCACHE))
                __clk_recalc_rates(clk, 0);
        rate = __clk_get_rate(clk);
        clk_prepare_unlock();
        return rate;
}

uclk 这个 divider 在注册时没有 CLK_GET_RATE_NOCACHE（对比 PLL() 宏里有 CLK_GET_RATE_NOCACHE，DIV() 宏里没有）。所以：

时刻 clk_get_rate(usb_clk) 实际返回什么
改 UPLL 之前 clk->rate 缓存，由 __clk_init 时 recalc_rate 算出
直接写 UPLLCON 缓存完全没变。这是绕过 CCF 直写寄存器
改 UPLL 之后 同一个缓存值，还是那个数

所以 before 48000000 和 after 48000000 不证明 UPLL 已经是 48MHz，只证明缓存值是 48MHz。这两个 printk 在这个场景下没有任何诊断价值。

这是本篇最想让你记住的一条。 clk_get_rate 是缓存读取，不是硬件回读。任何「改了寄存器再看 clk_get_rate」的验证方式都是无效的，除非那个 clock 有 CLK_GET_RATE_NOCACHE。要验证硬件，得读寄存器原始值自己算。

那 48MHz 是哪来的 #

答案：uboot 阶段配的。S3C2440 的 SoC 手册明确写着，在系统初始化阶段设置 MPLL 和 UPLL 时，必须先设置 UPLL 再设置 MPLL。uboot 按这个顺序做，把 UPLL 配成了 48MHz，CLKDIVN bit[3] 配成 0。

uboot 启动日志只打印三个频率：CPUID: 32440001、FCLK: 400 MHz、HCLK: 100 MHz、PCLK: 50 MHz。没有 UCLK——这是排查卡住的直接原因，你最关心的那个频率恰好在日志里没有。

根因 #

把前面所有碎片拼起来：

根因一句话：UCLK 的频率由 bootloader 决定，内核这一侧不做任何确认。 clk_prepare_enable 只保证「门开了」，不保证「门后面的频率对不对」。mdelay(2) 等的是门后信号稳定，不是 PLL 锁定。整条链路上没有任何一步重新配置 UPLL。

三条对策与实际取舍 #

对策 做法 代价 素材作者的结论
A. 内核里重配 UPLL 在 s3c2410_start_hc 里写 UPLLCON 破坏 CCF 抽象；clk_get_rate 缓存失真；MPLL/UPLL 顺序要求还得手工保证 网上流传最多，无效（那两个 printk 不证明任何事）
B. bootloader 保证 uboot 先配 UPLL 再配 MPLL，CLKDIVN bit[3] 与 UPLL 值匹配 依赖 bootloader，换 bootloader 就崩 作者实际用的是这条。uboot 里 FCLK 400 / HCLK 100 / PCLK 50，UPLL 48MHz / bit3=0
C. 设备树 + assigned-clocks 让 CCF 在 provider 注册后统一配置 需要 DTS 改造，老平台没 DTS 更规范，素材这套老代码没有采用

作者对「A 方案无效」的判断是可信的，理由就在 clk_get_rate 的缓存语义上——两次读到同一个数完全不能说明硬件没变。

但问题没有完全解决 #

原文明说：「控制输出的信息可以看到 usb 设备的确识别到了，不过过了几分钟，usb 设备又会自动断开，因此我怀疑是电源不稳定导致的 usb 断开。」

所以最终状态是：

阶段 现象 判断
初始 插 U 盘无反应 时钟配置问题
加 UPLL 重置代码后 能识别，几分钟后掉线 时钟已经不是主要矛盾，怀疑电源
悬而未决 掉线 供电不足或 VBUS 控制问题，未在原文中结论

这个案例的价值不在于「解决了」，而在于「排除」。 时钟这条线被完整验证过了——读到 48MHz，两条路径（UPLL 48 + bit 0，或 UPLL 96 + bit 1）都推导过，剩下的变量被压缩到电源。原文诚实地停在「我怀疑是电源不稳定」，这比硬编一个「改成 XXX 就好了」的结论要靠得住。

第 5 步为什么失败，第 6 步怎么改进 #

clk_get_rate 的坑前面讲过了。正确的验证方式：

u32 upllcon = __raw_readl(S3C2410_UPLLCON);

       clkdivn, (clkdivn >> 3) & 1);

检查项 期望 说明
CLKDIVN bit[3] 0 UCLK = UPLL，不分频
UPLLCON 的 MDIV/PDIV/SDIV 算出 48MHz 按 S3C2440 手册 UPLL 公式
两者组合的 UCLK 48MHz 唯一合法的组合

UCLK 的两条合法组合，写成表：

UPLLCON 配置的 UPLL CLKDIVN bit[3] UCLK 合法
48MHz 0 48MHz ✅
48MHz 1 24MHz ❌ 慢一半，USB 全崩
96MHz 1 48MHz ✅
96MHz 0 96MHz ❌ 快一倍，同样崩

这四个组合里只有两个能用。DIV() 宏只有 1 bit 宽度，物理上就只支持两种分频比，所以「配错」就是把两个合法组合之一和两个非法组合之一搞混。

5 寄存器也对 那就不是时钟问题，查电源、复位、引脚复用

第 4 步是这个案例的核心教训，第 5 步是它终点的位置。

二十四、CCF 的调试手段：clk_summary 与 ftrace #

框架层第二十四章已经列过 debugfs 的接口。这里补的是「实现层视角」——每个调试接口对应哪个内部机制。

调试接口 反映哪个内部状态 出问题时的判断
clk_summary 整棵树 parent 指针 + children 链表 缩进层级不对 = 父名拼错或父 provider 没注册成功
clk_summary 的 enable_cnt/prepare_cnt enable_count / prepare_count 只涨前者 = 违反 enable_count <= prepare_count；两者不等 = 有驱动漏配对
clk_summary 的 rate 列 core->rate 缓存 为 0 且有子节点 = .recalc_rate 没实现；和手册不符 = 缓存失真或 bootloader 配错
clk_summary 缺某个 clock 还在 clk_orphan_list 父名拼错，或父 provider 没初始化完
clk_orphan_summary（如果挂载） clk_orphan_list 内容 定位「clock 找不到」的第一现场
<clk>/clk_notifier_count notifier_count 非 0 但没人承认 = 有驱动挂了没注销
<clk>/clk_possible_parents parent_names[] + 当前选中项 mux 配错一眼看出来
tracepoint clk_enable/clk_disable/clk_set_rate/clk_set_parent 各 API 入口 clk_summary 是快照，看不出「谁在什么时候改的」

ftrace 抓 rate 变更 #

clk_set_rate 的 tracepoint 在 clk.c 里有，抓下来能看到每一次请求的完整参数：

bash
# 开 tracepoint
echo 1 > /sys/kernel/debug/tracing/events/clk/clk_set_rate/enable
echo 1 > /sys/kernel/debug/tracing/events/clk/enable/enable
echo 1 > /sys/kernel/debug/tracing/events/clk/disable/enable
# 只抓当前 shell
echo $$ > /sys/kernel/debug/tracing/set_ftrace_pid
# 触发一下
cat /sys/kernel/debug/clk/uclk/clk_rate
# 读结果
cat /sys/kernel/debug/tracing/trace

tracepoint 的价值在于时序。clk_summary 是个快照，看不出「是谁在什么时候把频率改掉的」。一次 BOOT 阶段的频率漂移，只有 trace 能抓到。

二十五、易错点速查 #

# 症状 内部机制上的原因 修法
1 clk_set_rate 返回 -EINVAL clk_calc_new_rates 返回 NULL：既没有 .round_rate，也没有 CLK_SET_RATE_PARENT 补 .round_rate，或补 flag
2 clk_set_rate 返回 -EBUSY，日志有 failed to set xxx rate 有 notifier 返回了 NOTIFY_BAD；或 CLK_SET_RATE_GATE 且已 prepare 查 clk_notifier_count；CLK_SET_RATE_GATE 的 clock 要先 unprepare
3 变频返回 0，但 clk_get_rate 没变 new_rate == 当前 rate 被 clk_calc_new_rates 判为无变化 用 clk_round_rate 先看实际能给多少
4 clk_get_rate 前后两次都同一个值，怀疑没生效 clk_get_rate 读的是 clk->rate 缓存（除非有 CLK_GET_RATE_NOCACHE） 直读寄存器自己算。这是第 22 章的核心教训
5 WARN_ON(core->prepare_count == 0) __clk_enable 的硬检查：先 enable 没 prepare 用 clk_prepare_enable
6 enable_count 只涨不落 某个错误路径漏了 clk_disable goto 统一清理，别每个分支手写
7 prepare_count 归零但硬件时钟还开着 上层计数归零却没走 clk_disable（__clk_unprepare 不自动 disable） 检查调用配对；clk_summary 的 enable_cnt 会暴露
8 多父 clock 注册返回 -EINVAL __clk_init 要求有 .set_parent 就必须有 .get_parent 两个成对实现
9 set_rate 有实现但注册报 must implement .round_rate & .recalc_rate __clk_init 的 ops 完整性检查 三个回调都要有
10 注册返回 -EEXIST __clk_lookup 查到同名 clock。clock 以 name 唯一 改名字；检查是不是重复注册了同一个 provider
11 clock 名字变乱码 parent_names 或 name 指向 __initdata 或栈，初始化后内存被回收 CCF 已经 kstrdup 了名字；检查是否绕过了 clk_register
12 某个 clock 在 clk_summary 里层级错位 parent_names 拼错，或父 provider 后注册导致它先进了 orphan，之后没被认领 clk_possible_parents 对照真实名字
13 clk_get 返回 -ENOENT 名字在两条链表里都查不到 看 clk_orphan_summary；检查 provider 有没有走 of_clk_add_provider
14 开机后外设失灵，probe 明明成功 clk_disable_unused 关掉了没被任何驱动 get 的 clock bootargs 加 clk_ignore_unused 验证 → 补 CLK_IGNORE_UNUSED 或修驱动
15 notifier 回调里死锁 回调在持有 prepare_lock 时运行，内部又调 CCF API 回调里只做记录，不碰 clock API
16 notifier 注销后崩溃 先 clk_put 再 clk_notifier_unregister 注销必须在 put 之前
17 devm_clk_get 拿到 clock，但 unbind 后状态诡异 两个 driver 共用同一 clk_core，devres 只回收自己那份引用 独占场景用 clk_get_exclusive（4.x）
18 gate 写了寄存器但时钟不响应 漏了 CLK_GATE_HIWORD_MASK（高 16 位是写使能掩码） 补 gate flag；直读寄存器确认
19 gate 行为全反（该开关的反了） 漏了 CLK_GATE_SET_TO_DISABLE 补 gate flag
20 两个 gate 共用寄存器，偶发丢写 clk_register_gate 的 lock 传了 NULL 传共享的 spinlock_t *
21 对 gate 时钟调 clk_set_rate，改了整条总线 gate 在 rate 传播里透明，CLK_SET_RATE_PARENT 把请求递给父 别对 gate 调 set_rate；要改就改末端的有分频器的节点
22 reset_control_reset 返回错误 provider 没实现 .reset 回调 改用 assert + udelay + deassert
23 reset 之后寄存器读写全 0/全 1 忘了 deassert，模块还在复位态 补 deassert；注意 reset 没有引用计数，不会自动恢复
24 clock 开着但复位无效 复位动作需要时钟才生效 保证 clk_prepare_enable 在 reset_control_assert 之前
25 of_clk_add_provider 之后 consumer 仍 -ENOENT 注册了 clock 但 provider 挂错了 node，或 #clock-cells 不匹配 provider 的 node 必须是 DTS 里被 clocks = <&xxx ...> 引用的那个
