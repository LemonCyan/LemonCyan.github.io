一、Runtime PM 与 System PM 的分工 #

两级目标不同：系统 PM（System PM）回答「整机什么时候睡」，由用户空间写 /sys/power/state 触发，PM core 按固定顺序遍历所有设备，依次调 ->prepare、->suspend、->suspend_late、->suspend_noirq，最后 CPU 进 WFI。整个过程全局、同步、路径固定。

Runtime PM（下文简称 RPM）回答「这个设备现在还需要供电吗」，由驱动自己触发：操作前 get、操作完 put，计数归零后 core 调 ->runtime_idle、->runtime_suspend 挂起设备。只作用于一个设备，与整机是否 suspend 无关。

维度 System PM Runtime PM
触发者 用户空间写 /sys/power/state 驱动调 pm_runtime_get/put
作用范围 整机，所有设备 单个设备（CPU 除外）
时机 显式、一次性 持续、随访问模式变化
判断依据 全局的唤醒事件与冻结状态 每设备的 usage_count 与 child_count
回调链 prepare→suspend→late→noirq runtime_idle→runtime_suspend
状态记录 dev->power.is_suspended 等标志 dev->power.runtime_status
失败代价 整机回滚 单设备，可重试
代码位置 drivers/base/power/main.c drivers/base/power/runtime.c

关键差别在「判断依据」这一行。System PM 要判断整机能不能睡，运行环境太复杂，一个后台线程、一次网络收包都能让判断失效。RPM 只判断一个设备空闲不空闲，边界清楚得多。

两套机制会互相踩。系统 suspend 进行中，某个驱动调 pm_runtime_get 想唤醒设备，会把流程搞乱。所以 PM core 在 device_prepare 阶段就调 pm_runtime_get_noresume 把 API 挡掉——只加引用计数不触发 resume，等于临时冻结该设备的 RPM 行为，等 complete 阶段再放开，细节见第十四章。

代码量上，3.17 时 drivers/base/power/runtime.c 约 1400 行，其中大篇幅在处理同步：多个 runtime_suspend 请求之间、runtime_suspend 与 runtime_resume 之间、RPM 与 system suspend 之间。真正干活的逻辑并不多。

二、Runtime PM 要解决什么：设备级的按需供电 #

设备给用户程序提供服务只有两种方式：接受指令干活（被动），或上报事件（主动，多数走中断）。所以 active 时间段正好两段：从收到指令到完成指令、从事件到达到达驱动把它记下来。剩下的时间——驱动把指令交给硬件前的准备、把事件数据交给应用前的中转——都是 idle。

idle 了是不是马上挂起？看场景：

  • 网卡传输中的连接。下一个包几十微秒后就到，频繁 suspend/resume 更费电（每次都要保存寄存器、关时钟、关电源），性能还掉。
  • 用户按键。突发性极强，按完几小时没动静，挂起。
  • 触摸屏。间歇 report，间隔几十毫秒，这个要试。

get/put 正好是 idle 状态的切换点，所以时机也清楚：主动访问设备时（写寄存器、发起 DMA）get，访问结束 put；设备有事件通知时（多数在中断里）get，处理完 put。

这是理论模型，实际可以放松。一个操作内部做了一堆寄存器读写，没必要每次读写都 get/put，在操作入口 get、出口 put 就够。粒度做大一点，代码清爽，代价是省电效果差一点。

容易踩的坑：RPM 里的「suspend」不等于「进低功耗模式」。它只承诺一件事——设备不处理数据，不和 CPU、RAM 通信，直到 ->runtime_resume 被调用。原因是此刻设备的 parent（bus controller）、CPU、RAM 都已挂起，设备再有动作都会出问题。Documentation/power/runtime_pm.txt 写得很明白：

text
* Once the subsystem-level suspend callback (or the driver suspend callback,
   if invoked directly) has completed successfully for the given device, the PM
   core regards the device as suspended, which need not mean that it has been
   put into a low power state.  It is supposed to mean, however, that the
   device will not process data and will not communicate with the CPU(s) and
   RAM until the appropriate resume callback is executed for it.  The runtime
   PM status of a device after successful execution of the suspend callback is
   'suspended'.

所以写 ->runtime_suspend 时，第一优先级是把设备「静下来」：停 DMA、关中断上报、关时钟。真正掉不掉电，看硬件支持。

usage_count 与 child_count 在 3.x 里是 atomic_t 还是 unsigned int 加锁保护，不同小版本写法不一（见附录「未验证」），语义不变。CONFIG_PM_ADVANCED_DEBUG 打开后多出的那几个调试计数，就是 sysfs 里 runtime_usage、runtime_active_kids 等文件的来源。

字段分五组。系统 suspend：power_state、can_wakeup、async_suspend、is_prepared/is_suspended/is_noirq_suspended/is_late_suspended 四个阶段标志、direct_complete（能否跳过整个流程直接完成）、no_pm、early_init。RPM 计数与开关：usage_count、disable_depth、child_count、ignore_children、runtime_auto（对应 /sys/devices/.../power/control）、runtime_status、runtime_error、idle_notification、request_pending/request、deferred_resume。能力标志：no_callbacks、irq_safe、use_autosuspend、timer_autosuspends、memalloc_noio。autosuspend：timer、timer_expires、rpm_resume_delay、rpm_suspend_delay。统计与等待：total_time、suspend_time、max_time_suspended_ns、wait_queue、work、wakeup。

有一处必须背下来：新设备注册时 pm_runtime_init 把 runtime_status 初始化为 RPM_SUSPENDED，同时把 disable_depth 置 1。内核不知道硬件此刻真实状态，驱动必须先 pm_runtime_set_active() 或 pm_runtime_set_suspended() 修正，再 pm_runtime_enable()。顺序反了就是 bug，见第十一章。

四、Runtime PM 的核心：usage_count 与 child_count #

三个计数器各管一摊，混了就写不出正确的驱动。

usage_count——有几个人在用，语义和 kobject 引用计数类似。pm_runtime_get* 加一，pm_runtime_put* 减一，归零意味着「没有调用者了」。驱动显式维护，每次 get 都要有对应的 put，漏了就是永远不睡。

child_count——有多少个子设备还活着，RPM core 自动维护。任何一个子设备 active，child_count 就大于 0，父设备赖着不睡。子设备 suspend 时 __pm_runtime_suspend 调 __pm_runtime_idle(parent) 把计数往下减，resume 时递归把父设备先拉起来。这是父子依赖传播的基础，第十章细讲。

disable_depth——临时禁止运行时挂起。它和引用计数是两个维度，虽然都会影响「能不能挂起」：usage_count 说的是需求侧（有 N 个调用者在用），disable_depth 说的是机制侧（RPM 功能本身被关掉，任何自动挂起都不生效）。

disable_depth 支持嵌套，pm_runtime_enable 减一、pm_runtime_disable 加一。只要它大于 0，一大批 API 直接返回 -EACCES，回调根本不会被调用。用它可以把一段代码包起来，保证执行期间设备绝对不会被自动挂起：

c
pm_runtime_disable(dev);
/* ... 这段代码里设备绝对醒着 ... */
pm_runtime_enable(dev);

副作用：pm_runtime_enable 只把 disable_depth 减回 0，不会自动触发 idle 检查。想给设备一次睡下去的机会，得再补 pm_request_idle(dev)。

一张表把三者钉死：

计数器 谁维护 含义 归零 / 大于零的效果
usage_count 驱动显式 get/put 有几个人在用 归零→可以走 idle 流程
child_count RPM core 自动 几个子设备还 active 大于零→父设备不能睡
disable_depth enable/disable 配对 RPM 机制被关了几层 大于零→API 直接失败，回调不跑

一个判断要不要挂起的条件，必须同时满足：usage_count == 0、child_count == 0（或 ignore_children 置位）、disable_depth == 0、runtime_status == RPM_ACTIVE。少一个都不行。

五、pm_runtime_get / put 的引用计数 #

正统接口就两个：pm_runtime_get 和 pm_runtime_put。

c
static inline int pm_runtime_get(struct device *dev)
{
        return __pm_runtime_resume(dev, RPM_GET_PUT | RPM_ASYNC);
}

static inline int pm_runtime_put(struct device *dev)
{
        return __pm_runtime_idle(dev, RPM_GET_PUT | RPM_ASYNC);
}

两个都是异步的（RPM_ASYNC）。get 的语义是「我要用这个设备了」——计数加一，设备不是 active 就把 runtime_resume 请求丢到 pm_wq 工作队列排队。put 是「我用完了」——计数减一，减到 0 且没有子设备 active 就丢一个 runtime_idle 请求排队。默认异步是因为这两类调用会出现在中断处理函数里，->runtime_resume 里要 msleep、要等 regulator 稳定，同步调用就把中断处理拖住了。RPM_GET_PUT 的意思很直白：本次操作要顺带改 usage_count，底下的 __pm_runtime_idle / __pm_runtime_resume 靠它区分「改计数」和「只做动作」。

漏 put 的驱动满地都是，症状是设备永远不睡、功耗下不来。排查套路：看 /sys/devices/.../power/runtime_usage，值不是 0 就说明有人借了没还（需要 CONFIG_PM_ADVANCED_DEBUG）。

还有一个「加计数但不触发 resume」的接口：

c
static inline void pm_runtime_get_noresume(struct device *dev)
{
        atomic_inc(&dev->power.usage_count);
}

PM core 内部大量使用，最典型就是 device_prepare 里用来暂时挡掉 RPM。驱动自己也可以用它做「先占位，稍后再真正唤醒」的处理。

六、pm_runtime_get_sync 与异步版本 #

同步版本就是把 RPM_ASYNC 去掉，直接在当前上下文跑回调。

c
static inline int pm_runtime_get_sync(struct device *dev)
{
        return __pm_runtime_resume(dev, RPM_GET_PUT);
}

static inline int pm_runtime_put_sync(struct device *dev)
{
        return __pm_runtime_idle(dev, RPM_GET_PUT);
}

static inline int pm_runtime_put_sync_suspend(struct device *dev)
{
        return __pm_runtime_suspend(dev, RPM_GET_PUT);
}

pm_runtime_get_sync 是驱动里出现频率最高的一个，它保证函数返回时设备已经 active，之后访问寄存器是安全的。代价是会在当前上下文同步执行 ->runtime_resume，会睡，所以只能在可以睡的上下文调用——除非用 pm_runtime_irq_safe() 声明过这个设备。三类接口的定位：

接口 同步性 改 usage_count 典型用途
pm_runtime_get_sync 同步 加一 操作设备前确保已唤醒
pm_runtime_get 异步 加一 中断上下文、不方便睡的路径
pm_runtime_put_sync 同步 减一 用完后立刻放下
pm_runtime_put 异步 减一 中断上下文、性能敏感路径
pm_runtime_put_sync_suspend 同步 减一 放下并直接挂起，跳过 idle
pm_runtime_put_autosuspend 异步 减一 放下并延时挂起
pm_runtime_put_sync_autosuspend 同步 减一 同上，同步版
pm_request_idle / pm_request_resume 异步 不改 只请求一次动作
pm_runtime_idle / pm_runtime_suspend / pm_runtime_resume 同步 不改 直接尝试对应动作
pm_schedule_suspend 异步 不改 延时 ms 级后挂起

最后一行值得单说：pm_schedule_suspend 接受毫秒级 delay，起定时器，到期挂起设备，不动引用计数。放在 ->runtime_idle 里最合适，驱动不用自己维护 timer。

c
static int foo_runtime_idle(struct device *dev)
{
        /* 300ms 内没有新的 get，就挂起 */
        return pm_schedule_suspend(dev, 300);
}

同步版的风险就是「后果自负」：在持有自旋锁、禁中断、或调用链上层有锁时调，会把 ->runtime_resume 里的 msleep 变成死锁或调度崩溃。runtime.c 之所以要用大半篇幅处理同步，源头就在这里。

七、runtime_status 的五个状态 #

enum rpm_status 在 3.x 里是四个值：

c
enum rpm_status {
        RPM_ACTIVE = 0,
        RPM_RESUMING,
        RPM_SUSPENDED,
        RPM_SUSPENDING,
};
状态 含义 进入条件
RPM_ACTIVE 正常工作 ->runtime_resume 执行成功
RPM_RESUMING 正在唤醒 ->runtime_resume 执行中
RPM_SUSPENDED 已挂起 ->runtime_suspend 执行成功
RPM_SUSPENDING 正在挂起 ->runtime_suspend 执行中
RPM_REQ_NONE 无 pending 请求 属 power.request，非设备状态

最后一行的归属要说清：RPM_REQ_NONE、RPM_REQ_IDLE、RPM_REQ_SUSPEND、RPM_REQ_AUTOSUSPEND、RPM_REQ_RESUME 属于 enum rpm_request，记录在 dev->power.request，表示「排队里有个什么请求」，不是设备的电源状态。

两处新手必踩。第一，runtime_status 和 idle 无关：->runtime_idle 只是 suspend 前的一道缓冲，它本身不改变 runtime_status，/sys/.../power/runtime_status 里永远是那四个状态之一，不会出现 idle。第二，初始值是 RPM_SUSPENDED：pm_runtime_init 无论硬件实际状态如何一律设成它。一个上电就活着的设备如果不修正，第一次 pm_runtime_get_sync 会老老实实调一次 ->runtime_resume，而那个回调往往假设设备本来在挂起态（比如重新做一遍初始化），于是出现「设备被二次初始化」的怪问题。

runtime_error 是配套的：回调返回非 0 时错误码记进 dev->power.runtime_error，后续对该设备的 RPM 操作直接返回这个错误，直到驱动调 pm_runtime_set_active() 之类清掉。调试时看到一堆 -EIO 找不到源头，先翻 runtime_error。

八、自动挂起的触发：idle 与 autosuspend #

put 把计数减到 0 后，core 走三条路之一。

路径一，直接 suspend：core 调 ->runtime_idle（如果注册了），返回 0 表示「可以挂」，接着调 ->runtime_suspend；返回负数表示「别挂」。路径二，延时 suspend：回调里调 pm_schedule_suspend(dev, delay)，core 起 timer 到期再挂。路径三，autosuspend：probe 里 pm_runtime_use_autosuspend(dev) 加 pm_runtime_set_autosuspend_delay(dev, delay)，之后所有 pm_runtime_put 都变成「减计数 + 起 autosuspend 定时器」，期间有人 get 就把 timer 取消，设备根本没睡过。

区别就在定时器上。autosuspend 是全局策略（一次设好，所有 put 生效），pm_schedule_suspend 是单次策略（只对这一次 idle 回调生效）。选哪个看设计：访问模式有稳定的「空闲间隔」特征就用 autosuspend，delay 设成那个间隔的两倍左右；只有特定路径需要保护、其他路径希望尽快睡就用 pm_schedule_suspend。

autosuspend 的接口族：

c
static inline void pm_runtime_use_autosuspend(struct device *dev)
{
        dev->power.use_autosuspend = 1;
}

static inline void pm_runtime_dont_use_autosuspend(struct device *dev)
{
        dev->power.use_autosuspend = 0;
}

extern void pm_runtime_set_autosuspend_delay(struct device *dev, int delay);
extern unsigned long pm_runtime_autosuspend_expiration(struct device *dev);

delay 单位毫秒。pm_runtime_autosuspend_expiration 返回距定时器到期还剩多少 jiffies，可以拿来做「快到期了，再 get 一次续命」的判断。use_autosuspend 关掉之后，pm_runtime_put_autosuspend 退化成普通 put，不报错。实在搞不清该用哪条路时，->runtime_idle 干脆不实现，core 直接走 suspend，逻辑最简单。

九、回调链：runtime_suspend / runtime_resume #

RPM core 只有三个回调：int (*runtime_suspend)(struct device *dev);、int (*runtime_resume)(struct device *dev);、int (*runtime_idle)(struct device *dev);，都写在 struct dev_pm_ops 里。

runtime_idle 可省，另两个在启用了 RPM 的设备上必须有——除非调了 pm_runtime_no_callbacks()。runtime_idle 的职责很窄：判断设备现在能不能挂起。标准写法只有两种，返回 0 让 core 接着挂，或者调 pm_schedule_suspend 安排延时；返回负数表示别挂。runtime_suspend 才真正动手：停 DMA、关中断上报、gating 时钟、必要时调 regulator 降档。成功后 core 把 runtime_status 设成 RPM_SUSPENDED，然后调 __pm_runtime_idle(parent) 把父设备的 child_count 减一。runtime_resume 反过来：先确保 parent 醒着，再恢复时钟、恢复寄存器、打开中断，返回 0 后状态变 RPM_ACTIVE。

核心实现在 __pm_runtime_resume，下面按 3.x 结构整理，逻辑是 runtime.c 的真实路径：

c
int __pm_runtime_resume(struct device *dev, int rpmflags)
{
        unsigned long flags;
        int retval;

        might_sleep_if(!(rpmflags & RPM_ASYNC) && !dev->power.irq_safe);

        /* 1. 机制被关了？直接报错 */
        if (dev->power.disable_depth > 0)
                return -EACCES;

        /* 2. 请求计数（供 pm_runtime_barrier 等判断有没有 pending） */
        if (rpmflags & RPM_GET_PUT) {
                if (!atomic_inc_not_zero(&dev->power.usage_count)) {
                        if (!(rpmflags & RPM_ASYNC))
                                return -EACCES;
                }
        }

 retry:
        spin_lock_irqsave(&dev->power.lock, flags);

        /* 3. 已经是 ACTIVE 且没有 pending 请求 → 直接返回，快速路径 */
        if (dev->power.runtime_status == RPM_ACTIVE) {
                retval = 0;
                goto out;
        }

        /* 4. 正在 RESUME → 同步等，异步直接返回 */
        if (dev->power.runtime_status == RPM_RESUMING) {
                if (!(rpmflags & RPM_ASYNC)) {
                        /* 等前一个 resume 完成：sleep 在 wait_queue 上 */
                        ...
                }
                retval = 0;
                goto out;
        }

        /* 5. 异步请求：排进 work，不在这里跑回调 */
        if (rpmflags & RPM_ASYNC) {
                dev->power.request = RPM_REQ_RESUME;
                dev->power.request_pending = true;
                queue_work(pm_wq, &dev->power.work);
                retval = 0;
                goto out;
        }

        /* 6. 同步路径：先拉起 parent，再跑自己的回调 */
        if (dev->parent && dev->parent->power.disable_depth > 0) {
                retval = -EACCES;
                goto out;
        }

        dev->power.runtime_status = RPM_RESUMING;
        spin_unlock_irqrestore(&dev->power.lock, flags);

        if (dev->parent)
                __pm_runtime_resume(dev->parent, RPM_GET_PUT);

        retval = rpm_callback(&dev->pm_domain->ops, RPM_RESUME, dev);

        spin_lock_irqsave(&dev->power.lock, flags);

        if (retval) {
                /* 失败：状态回滚，错误记进 runtime_error */
                dev->power.runtime_status = RPM_SUSPENDED;
                dev->power.runtime_error = retval;
        } else {
                dev->power.runtime_status = RPM_ACTIVE;
                dev->power.runtime_error = 0;
                if (dev->parent)
                        atomic_inc(&dev->parent->power.child_count);
        }
 out:
        spin_unlock_irqrestore(&dev->power.lock, flags);
        return retval;
}

七个要点。一，disable_depth > 0 立刻 -EACCES，这就是为什么 pm_runtime_enable 之前调 get_sync 会失败。二，RPM_GET_PUT 且引用计数非零时只加计数，atomic_inc_not_zero 的用法是「本来是零就不强行从零加到一」，配合异步路径避免「借了不还」。三，快速路径：已经 ACTIVE 无 pending 直接成功，一个寄存器都不碰，绝大多数调用走这里。四，状态是 RPM_RESUMING 时同步调用者挂在 wait_queue 上等前一个 resume 完成，这就是「多个 runtime_resume 请求之间的同步」。五，RPM_ASYNC 走 queue_work(pm_wq, ...)，在当前上下文跑回调的机会都没有。六，同步路径先递归拉起 parent，RPM_GET_PUT 保证 parent 的引用计数也加上去，递归返回后 parent 一定 active。七，回调失败时状态回滚到 RPM_SUSPENDED 并写 runtime_error，成功时给 parent 的 child_count 加一。

第 6 步给 parent 加的计数由谁还？等子设备 suspend 时对应地还回去。__pm_runtime_suspend 就是镜像结构：

c
int __pm_runtime_suspend(struct device *dev, int rpmflags)
{
        unsigned long flags;
        int retval;

        might_sleep_if(!(rpmflags & RPM_ASYNC) && !dev->power.irq_safe);

        if (dev->power.disable_depth > 0)
                return -EACCES;

        spin_lock_irqsave(&dev->power.lock, flags);

        /* 已经是 SUSPENDED → 直接成功 */
        /* 正在 SUSPENDING → 同步等 / 异步返回 */
        /* RPM_ASYNC → 排队 */

        /* 同步路径的前置条件：引用计数必须为 0 */
        if (atomic_read(&dev->power.usage_count) > 0
            || (dev->power.ignore_children ?
                atomic_read(&dev->power.child_count) > 0 : 0)) {
                retval = -EAGAIN;
                goto out;
        }

        dev->power.runtime_status = RPM_SUSPENDING;
        spin_unlock_irqrestore(&dev->power.lock, flags);

        retval = rpm_callback(&dev->pm_domain->ops, RPM_SUSPEND, dev);

        spin_lock_irqsave(&dev->power.lock, flags);

        if (retval == 0) {
                dev->power.runtime_status = RPM_SUSPENDED;
                dev->power.runtime_error = 0;
                /* 父设备少一个 active 的子设备，有资格睡了 */
                if (dev->parent)
                        __pm_runtime_idle(dev->parent, 0);
        } else {
                dev->power.runtime_status = RPM_ACTIVE;
                dev->power.runtime_error = retval;
        }
 out:
        spin_unlock_irqrestore(&dev->power.lock, flags);
        return retval;
}

两处关键差异：suspend 要检查「还有没有人用」，usage_count > 0 或（ignore_children 时）child_count > 0 都直接 -EAGAIN；成功后不是加父计数，而是给父设备一次 idle 机会。第 6 步给 parent 加的计数，由子设备 suspend 时对应还回去，一加一还是一对一的。

__pm_runtime_idle 和 __pm_runtime_suspend 是两个不同入口：idle 先跑 ->runtime_idle 再决定要不要 ->runtime_suspend，suspend 直接跑 ->runtime_suspend。pm_runtime_put_sync_suspend 走的后者，跳过 idle 那道缓冲。代码里的 dev->pm_domain->ops 是为了突出「回调来源」，实际实现走 dev_pm_ops 的优先级查找（第十二章展开）。父设备 disable_depth > 0 时子设备的 resume 直接返回 -EACCES，这个检查在 __pm_runtime_resume 里出现两次，因为 parent 会在中间被 disable 掉。

十、父子设备的依赖传播 #

struct device 的 parent 指针指父设备（一般是 bus controller、host controller），设备要正常工作父设备必须在供电。RPM 对这条依赖的处理有三条规则：父设备下任何一个子设备 active，父设备必须 active；任意子设备 idle 了要通知父设备，父设备据此记录还有几个 active 的子设备；所有子设备都 idle 了，父设备才有资格 idle。

这三条 core 全自动完成，驱动不用写代码。实现就是前面代码里那几个动作：子设备 __pm_runtime_resume 成功时 atomic_inc(&parent->power.child_count)（parent 的 usage_count 也在递归里加一），子设备 __pm_runtime_suspend 成功时 __pm_runtime_idle(parent, 0)（parent 的 usage_count 与 child_count 各减一）。

child_count 和 usage_count 是联动的两层，所以父设备的 usage_count 里始终包含「我的子设备个数」这一份。

有个开关能打破这条链：ignore_children。驱动调 pm_runtime_ignore_children(dev) 之后，父设备忽略 child_count，即使子设备还活着也能挂起。适用场景是「父设备只是总线控制器，子设备各自独立供电，父设备关机不影响子设备」的硬件。用错了就是灾难——父设备挂起后子设备还在工作，访问必然出错。旧接口名 pm_suspend_ignore_children，新内核统一成 dev_pm_suspend_ignore_children / pm_runtime_ignore_children 这一类，具体哪个版本改的名「未验证」。

父子链还有个隐性约束：只有 parent 先睡，child 才能睡。睡眠顺序必然自下而上，唤醒顺序必然自上而下。这个顺序和系统 PM 正好相反（系统 PM 是先 parent 后 child）。

十一、Runtime PM 的典型使用模板 #

把前面讲的串起来，一个正确的 probe：

c
static int foo_probe(struct platform_device *pdev)
{
        struct device *dev = &pdev->dev;
        struct foo_dev *foo = devm_kzalloc(dev, sizeof(*foo), GFP_KERNEL);

        if (!foo)
                return -ENOMEM;

        platform_set_drvdata(pdev, foo);

        /* 1. 先按硬件实际状态修正 runtime_status */
        pm_runtime_set_active(dev);

        /* 2. 打开自动挂起策略（可选） */
        pm_runtime_use_autosuspend(dev);
        pm_runtime_set_autosuspend_delay(dev, 200);

        /* 3. 最后才 enable，让 disable_depth 归零 */
        pm_runtime_enable(dev);

        return 0;
}

三步的顺序有讲究。pm_runtime_set_active() 必须在 enable() 之前：它直接把 runtime_status 写成 RPM_ACTIVE 并清掉 runtime_error。反了的话，设备就有资格在初始化完成前被人挂起。中间一步是策略配置，use_autosuspend 置位后所有 pm_runtime_put 都自动带延时。最后 pm_runtime_enable() 把 disable_depth 从初始的 1 减到 0，RPM 才真正工作。

remove 必须倒着来，pm_runtime_disable 把 disable_depth 加回 1，pm_runtime_dont_use_autosuspend 关策略，pm_runtime_set_suspended 让状态归位防止 remove 后残留。pm_runtime_disable 内部会 flush_work 等待已排队的工作项完成，所以它会睡，别在原子上下文里调。

运行期的典型写法：

c
static ssize_t foo_write(struct file *filp, const char __user *buf,
                         size_t count, loff_t *ppos)
{
        struct foo_dev *foo = filp->private_data;
        struct device *dev = foo->dev;
        int ret;

        ret = pm_runtime_get_sync(dev);
        if (ret < 0) {
                pm_runtime_put_noidle(dev);
                return ret;
        }

        /* 这里随便碰寄存器，设备一定醒着 */
        ret = foo_hw_write(foo, buf, count);

        pm_runtime_mark_last_busy(dev);
        pm_runtime_put_autosuspend(dev);

        return ret < 0 ? ret : count;
}

三个细节。pm_runtime_get_sync 失败时不能只 return，要补 pm_runtime_put_noidle——get_sync 在返回错误前已经把 usage_count 加过了，不还回去就永远差一。pm_runtime_mark_last_busy 更新 dev->power.timer_expires，把 autosuspend 定时器从现在重新算起，没有它延时就从上一次 put 开始算，设备刚 put 就到期。pm_runtime_put_autosuspend 是「减计数 + 按 delay 安排挂起」，前面没启用 autosuspend 时它等价于普通 pm_runtime_put。

中断处理里换成异步版，pm_runtime_get / pm_runtime_put，因为中断上下文不能睡。确实需要在中断里同步唤醒设备的，先调 pm_runtime_irq_safe(dev) 声明这个能力——它会改变 core 的锁策略，runtime.c 里大量 if (!dev->power.irq_safe) 判断就是为它服务的。

还有条经验：pm_runtime_put() 之后的代码会在 runtime_idle 之后才执行，重要的收尾工作放在 put 之前做完，别指望 put 之后的代码还在设备醒着的窗口里。

十二、驱动电源管理的三层回调 #

换掉 runtime 的视角，看整个驱动侧电源管理怎么组织。旧时光里驱动只需要在 struct platform_driver 里填 .suspend / .resume / .shutdown：

c
static int foo_suspend(struct platform_device *pdev, pm_message_t state)
{
        /* ... */
        return 0;
}

static struct platform_driver foo_pdrv = {
        .probe    = foo_probe,
        .suspend  = foo_suspend,
        .resume   = foo_resume,
        .shutdown = foo_shutdown,
        .driver   = {
                .name = "foo",
        },
};

这套现在还能用，但进了「兼容区」。platform.c 会把它翻译成新的 dev_pm_ops 形式，翻译函数名字里就带着 legacy：

c
int platform_pm_suspend(struct device *dev)
{
        struct device_driver *drv = dev->driver;
        int ret = 0;

        if (!drv)
                return 0;

        if (drv->pm) {
                if (drv->pm->suspend)
                        ret = drv->pm->suspend(dev);
        } else {
                ret = platform_legacy_suspend(dev, PMSG_SUSPEND);
        }

        return ret;
}

驱动有 dev_pm_ops 就走新的，没有就退回去调 pdrv->suspend。老驱动不会因为内核升级突然挂掉，但新驱动别再用老路子。shutdown 那条路稍有不同，__platform_driver_register 里做了替换：if (drv->shutdown) 成立时把 drv->driver.shutdown 换成 platform 层的 platform_drv_shutdown，由它再转调驱动自己的回调，reboot 流程就不用关心底下是什么总线。

所谓「三层」指 dev_pm_ops 挂在不同层级上，core 按固定优先级从上往下找：

text
dev->pm_domain->ops   ← 最高优先级
dev->type->pm
dev->class->pm
dev->bus->pm
dev->driver->pm       ← 最低优先级

找到第一个非空的就用它，后面的完全不看。所以你写在 driver 里的 ->suspend，只要 bus 层也有 ->suspend 就不会被直接调到——但 bus 层的实现转手调 pm_generic_suspend(dev)，最终还是回到你的驱动。看 genpd 这个实例：

c
genpd->domain.ops.suspend = pm_genpd_suspend;

static int pm_genpd_suspend(struct device *dev)
{
        struct generic_pm_domain *genpd = dev_to_genpd(dev);

        if (IS_ERR(genpd))
                return -EINVAL;

        return genpd->suspend_power_off ? 0 : pm_generic_suspend(dev);
}

绕一圈，pm_generic_suspend 最终调 dev->driver->pm->suspend，球还是踢回给驱动。这一层的意义是判断设备是否已经掉电（掉电了不能再 suspend，否则会踩未上电的硬件），以及决定整个 domain 要不要 power off——这些是 domain 的职责，单个驱动没有全局视野。bus 层看 platform：

c
struct bus_type platform_bus_type = {
        .name       = "platform",
        .dev_groups = platform_dev_groups,
        .match      = platform_match,
        .uevent     = platform_uevent,
        .pm         = &platform_dev_pm_ops,
};

static const struct dev_pm_ops platform_dev_pm_ops = {
        .runtime_suspend = pm_generic_runtime_suspend,
        .runtime_resume  = pm_generic_runtime_resume,
        USE_PLATFORM_PM_SLEEP_OPS
};

USE_PLATFORM_PM_SLEEP_OPS 把 suspend/resume、freeze/thaw、poweroff/restore 以及它们的 _late、_noirq 变体批量指向 platform_pm_* 系列。platform 是虚拟总线，除了转发没别的事可做；物理总线（I2C、SPI、PCI）就会在 bus 层做真动作——控制器要保存总线状态、处理片选、配置总线电源管理。优先级这么设计的原因也就清楚了：越靠近 domain 的层越知道设备的真实供电状态，越靠近 driver 的层越知道设备该做什么。

按用途只有三大组：

常规路径 suspend / resume STR、Standby 主路径

参与系统 suspend 最低限度实现 suspend / resume 就行，_late、_noirq 只在特定场景需要（下一章讲）。dev_pm_ops 存在于所有和设备模型有关的实体里，下面把结构体主体省略只留关键成员：

c
struct bus_type      { ...  const struct dev_pm_ops *pm;  ... };
struct device_driver { ...  const struct dev_pm_ops *pm;  ... };
struct class         { ...  const struct dev_pm_ops *pm;  ... };
struct device_type   { ...  const struct dev_pm_ops *pm;  };
struct device        { ...  struct dev_pm_info power;
                            struct dev_pm_domain *pm_domain;  ... };
struct dev_pm_domain {      struct dev_pm_ops ops;  ... };

struct dev_pm_domain 里是结构体成员 ops，其余几处都是指针 pm——domain 的 ops 内联在 domain 里，访问不用多一次解引用。power 和 pm_domain 是两回事：前者存状态且每个设备都有，后者存回调整体且可以为 NULL。

回开头那个问题——旧时代为什么要把 suspend/resume 散在 bus_type、class、device_driver、device_type 里？因为没有封装。每加一个阶段（比如后来的 _noirq）就要改这四个结构体，改一处影响全局。抽成 dev_pm_ops 之后，新增阶段只改一个结构体。

十四、suspend / resume / freeze 的回调与时机 #

系统进入 suspend，core 按固定顺序走一遍：

text
prepare → suspend → suspend_late → suspend_noirq ---- 睡眠 ----→
resume_noirq → resume_early → resume → complete

醒来时顺序完全镜像。这条链由 drivers/base/power/main.c 调度，入口是几个 dpm_* 函数。

dpm_prepare 遍历 dpm_list，对每个设备调 device_prepare：看 dev->power.syscore，是 syscore 设备就跳过；调 pm_runtime_get_noresume(dev) 把该设备的 RPM 挡掉（第一章说的解法）；调 device_may_wakeup()，结合 dev->power.wakeup 和 can_wakeup 判断该设备是不是唤醒路径，结果记进 dev->power.wakeup_path；按优先级找到 prepare 回调并调用。成功后 dev->power.is_prepared = true，设备从主链转移到 dpm_prepared_list。这条路径上 suspend_report_result() 用得很多，专门在特定回调失败时打日志（受 CONFIG_PM_DEBUG 控制）：

c
#define suspend_report_result(fn, ret)                                  \
        do {                                                            \
                __suspend_report_result(__func__, fn, ret);             \
        } while (0)

dpm_suspend 同样遍历 dpm_list 调 device_suspend：失败就把错误信息记进 struct suspend_stats 数组并打印（/sys/kernel/debug/suspend_stats 的数据源），成功则把设备转移到 dpm_suspended_list。

dpm_suspend_start = dpm_prepare + dpm_suspend；dpm_suspend_end = 所有设备的 suspend_late + 所有设备的 suspend_noirq。醒来一侧一一对应：dpm_resume_start = 所有 resume_noirq + 所有 resume_early，dpm_resume_end = dpm_resume + dpm_complete。先 noirq 后 early，和睡下去严格镜像——睡眠时最后做的动作必须第一个撤销，否则中断状态不一致。

freeze / thaw 和 suspend / resume 结构一样，语义不同：后者的设备真的进低功耗状态，寄存器内容丢失，resume 要重新初始化硬件；前者的设备状态在内存和硬件里都留着，只是暂停工作。分开是因为 hibernate 要先把内存快照写到 disk，这个过程设备不能真的断电（还要读 disk、还要收 IO），但又必须安静下来不产生新数据。freeze 干这个，真正断电交给 poweroff。

顺序 阶段 回调 中断状态 设备状态
1 prepare ->prepare 开 正常工作
2 suspend ->suspend 开 准备进入低功耗
3 late ->suspend_late 开 平台代码交界处
4 noirq ->suspend_noirq 关 中断已禁，最后收尾
— 睡眠 — 关 CPU 进 WFI
5 noirq ->resume_noirq 关 恢复中断控制器
6 early ->resume_early 关 平台代码交界处恢复
7 resume ->resume 开 设备恢复工作
8 complete ->complete 开 收尾，放开 RPM

第 4 步和第 5 步之间就是真正的睡眠窗口，CPU 在 WFI 里等中断。

十五、late_suspend 与 noirq 阶段为什么需要 #

一个阶段不够用，是因为设备之间的依赖不对称。设备 A 是 I2C 控制器，B 是挂在 A 下面的传感器：suspend 时 B 必须先睡（停止用 A），A 后睡；resume 时 A 必须先醒，B 后醒。这就是「自下而上睡、自上而下醒」。

PM core 靠 dpm_list 的顺序保证这一点。但 dpm_list 只保证设备之间的顺序，不保证设备与中断控制器之间的顺序。中断控制器本身也是设备，suspend 时它必须最后才关中断能力。按普通顺序处理的话，它会在某个设备之前就被关掉，那个设备的 suspend 回调里想用中断就完蛋了。

_noirq 解决这个问题。它发生在所有普通 suspend 完成之后、中断真正关闭之后，此时只能做不需要中断的动作，中断控制器的 suspend_noirq 一定最后跑。醒来时反向，resume_noirq 最先跑。_late 解决另一类问题——设备驱动和平台代码的交界。有些 SoC 平台代码（platform_suspend_ops）需要在「所有设备驱动都处理完、但中断还没关」这个窗口做事，比如配置电源管理 IC 的寄存器、切换外部时钟。一句话：suspend 是驱动的主战场，_late 是驱动与平台代码握手的窗口，_noirq 是中断关掉之后还能做的边角工作。

阶段 能做什么 不能做什么
suspend 睡眠等待、申请内存、收发中断 —
suspend_late 简单 IO、写寄存器 依赖中断的动作
suspend_noirq 纯寄存器操作、忙等 睡眠、依赖中断、申请大块内存

大部分驱动只实现 suspend / resume 就够。需要 _noirq 的典型场景是「中断关闭之后确认中断线没有挂起 pending 中断」，需要 _late 的典型场景是「和平台的时钟/电源切换代码配合，必须卡在所有驱动处理完之后」。

十六、PM OPP：性能点与电压频率配对 #

OPP 是 Operating Performance Point。定义直白：一个 voltage domain 里，设备支持的所有「频率/电压」组合，就是它的 OPP 集合。

为什么一定要配对？频率决定器件能跑多快，功耗和频率成正比（P ∝ f），但和电压是平方甚至立方级（P ∝ C·V²·f）。降频的省电是线性的，降压的省电是平方的。而频率降低之后电路时序余量变大，电压就能跟着降。所以「频率 + 电压」是一个组合动作，降频不降压等于白降。这就构成性能和功耗之间的跷跷板，OPP 库的职责就是把这个跷跷板的所有档位存起来、查出来。

OPP 是一个单纯的软件 library，不碰硬件，没有复杂逻辑，Documentation/power/opp.txt 写得已经很清楚。它的价值在于「所有设备的 OPP 管理方式统一」。需求无非几条：一个数组存下所有 OPP、能增删改、能查设备支持哪些、能按频率/电压/范围查、能临时禁用某一档。

实现在 drivers/base/power/opp.c，头文件 include/linux/pm_opp.h。内部组织方式，opp.txt 给了张图：

text
/*
 * Internal data structure organization with the OPP layer library is as
 * follows:
 * dev_opp_list (root)
 *      |- device 1 (represents voltage domain 1)
 *      |       |- opp 1 (availability, freq, voltage)
 *      |       |- opp 2 ..
 *      ...     ...
 *      |       `- opp n ..
 *      |- device 2 (represents the next voltage domain)
 *      ...
 *      `- device m (represents mth voltage domain)
 * device 1, 2.. are represented by dev_opp structure while each opp
 * is represented by the opp structure.
 */

本来可以在 struct device 里加个字段挂 OPP 链表，但 OPP 在设备模型里地位太边缘，进不了核心结构。所以 OPP 库自己在 opp.c 里维护全局 dev_opp_list，每个设备对应一个 struct device_opp 节点，节点下挂该设备的所有 struct dev_pm_opp。

c
/* 3.x 形态，字段名以 drivers/base/power/opp.c 与 include/linux/pm_opp.h 为准 */
struct dev_pm_opp {
        struct list_head        node;      /* 挂在 device_opp->opp_list 上 */
        struct rcu_head         head;      /* 释放用 */
        bool                    available; /* 该 OPP 是否可用（未被 disable） */
        unsigned long           rate;      /* 频率，单位 Hz */
        unsigned long           u_volt;    /* 电压，单位 uV */
        unsigned long           u_volt_min;/* 电压下限，后续内核加入 */
        unsigned long           u_volt_max;/* 电压上限，后续内核加入 */
        unsigned long           u_amp;     /* 电流，后续内核加入 */
};

struct device_opp 大致是 node（挂在全局 root list）、dev（对应设备指针）、opp_list（该设备的 OPP 链表头）、opp_list_lock，加一个类似 kref 的引用计数管理生命周期。这两个结构只在库内部使用，外部驱动拿到的永远是 struct dev_pm_opp * 这样的不透明句柄，只能通过 dev_pm_opp_get_freq / dev_pm_opp_get_voltage 读值。内部结构随时可以改，接口不用动。

十七、opp table 的注册与查找 #

添加与开关：

c
int dev_pm_opp_add(struct device *dev, unsigned long freq,
                   unsigned long u_volt);
int dev_pm_opp_enable(struct device *dev, unsigned long freq);
int dev_pm_opp_disable(struct device *dev, unsigned long freq);

freq 单位 Hz，u_volt 单位 uV。库里按 rate 排序插入链表，所以添加顺序无所谓。dev_pm_opp_add 加进去的 OPP 默认可用；驱动判断某一档在特定板子上有风险（电压余量不够、散热不行）时可以 dev_pm_opp_disable 关掉，关掉之后除了 dev_pm_opp_find_freq_exact 之外所有查询接口都查不到它。

查询：

c
int dev_pm_opp_get_opp_count(struct device *dev);

struct dev_pm_opp *dev_pm_opp_find_freq_exact(struct device *dev,
                                              unsigned long freq,
                                              bool available);
struct dev_pm_opp *dev_pm_opp_find_freq_floor(struct device *dev,
                                              unsigned long *freq);
struct dev_pm_opp *dev_pm_opp_find_freq_ceil(struct device *dev,
                                             unsigned long *freq);
接口 匹配规则 freq 参数 是否查 disabled 的 OPP
dev_pm_opp_find_freq_exact 精确等于 值传递 由 available 控制
dev_pm_opp_find_freq_floor 小于或等于 指针，回写实际值 不查
dev_pm_opp_find_freq_ceil 大于或等于 指针，回写实际值 不查

floor / ceil 传指针是因为查到的频率一般不等于请求值。你请求 480MHz，硬件只有 400MHz 和 500MHz 两档，floor 返回 400MHz 那档并把 *freq 改成 400000000，ceil 返回 500MHz 那档。dev_pm_opp_find_freq_exact 的 available 参数语义：true 只找可用的，false 只找被 disable 的，不能同时返回，实际读法是「我只要 available == 这个值 的」。

c
unsigned long dev_pm_opp_get_voltage(struct dev_pm_opp *opp);
unsigned long dev_pm_opp_get_freq(struct dev_pm_opp *opp);

从句子柄里读电压和频率，都是纯读。规矩：所有 dev_pm_opp_find_* 返回的句柄，用完必须 dev_pm_opp_put() 还回去。3.x 早期实现靠 RCU 读，句柄不需要立刻还，4.5 之后改成引用计数，漏 put 会泄漏；确切分界版本「未验证」，按有 dev_pm_opp_put 的规则写准没错。

从 DTS 初始化：

c
#if defined(CONFIG_PM_OPP) && defined(CONFIG_OF)
int of_init_opp_table(struct device *dev);
#else
static inline int of_init_opp_table(struct device *dev)
{
        return -EINVAL;
}
#endif

条件编译是必须的：没开 CONFIG_OF 或没开 CONFIG_PM_OPP 时给一个返回 -EINVAL 的空实现，调用方不用再套 #ifdef。DTS 格式以 arch/arm/boot/dts/omap34xx.dtsi 为例：

dts
cpus {
        cpu@0 {
                /* OMAP343x/OMAP35xx variants OPP1-5 */
                operating-points = <
                        /* kHz    uV */
                        125000   975000
                        250000  1075000
                        500000  1200000
                        550000  1270000
                        600000  1350000
                >;
                clock-latency = <300000>; /* From legacy driver */
        };
};

operating-points 是扁平的 <频率 电压> 对数组，单位 kHz 和 uV，of_init_opp_table 解析它并逐个调 dev_pm_opp_add，kHz 会乘 1000 转成 Hz。clock-latency 不是 OPP 属性，是调频时等时钟稳定的时间（纳秒级），cpufreq 用它做过渡延时，放在同一节点是因为「和频率相关的东西放一起」。注意单位不一致：DTS 用 kHz，内核 API 用 Hz，差 1000 倍。调 dev_pm_opp_find_freq_ceil 永远查不到，多半就是这里错了。

十八、dev_pm_opp_set_rate 的链路 #

3.x 时代的 OPP 库是「纯数据」的，只管查表不管设。驱动查到想要的 OPP 之后要自己做三件事：从句柄读 u_volt、调 regulator 设电压、调 clk 设频率。

c
static int foo_set_rate(struct device *dev, unsigned long target_freq)
{
        struct dev_pm_opp *opp;
        unsigned long freq = target_freq;
        unsigned long volt;

        opp = dev_pm_opp_find_freq_ceil(dev, &freq);
        if (IS_ERR(opp))
                return PTR_ERR(opp);

        volt = dev_pm_opp_get_voltage(opp);
        dev_pm_opp_put(opp);

        /* 先升压再升频，先降频再降压 —— 顺序不能反 */
        if (target_freq > current_freq) {
                if (regulator_set_voltage(td->reg, volt, volt))
                        return -EIO;
                if (clk_set_rate(td->clk, freq))
                        return -EIO;
        } else {
                if (clk_set_rate(td->clk, freq))
                        return -EIO;
                if (regulator_set_voltage(td->reg, volt, volt))
                        return -EIO;
        }

        return 0;
}

顺序是关键。升频时先升压，否则新频率下电压不够会跑飞；降频时先降频，否则降压后旧频率跑不动。反过来会死机。

手写流程太容易错，每个驱动都在重复同样的三件事。内核在 4.5 之后加了 dev_pm_opp_set_rate() 把这段逻辑收进库：

c
/* 4.5+ 形态，具体引入版本与签名以新版 pm_opp.h 为准 */
int dev_pm_opp_set_rate(struct device *dev, unsigned long target_freq);

struct opp_table *dev_pm_opp_set_regulators(struct device *dev,
                                            const char * const names[],
                                            unsigned int count);
struct opp_table *dev_pm_opp_set_clkname(struct device *dev, const char *name);
struct opp_table *dev_pm_opp_set_supported_hw(struct device *dev,
                                              const u32 *versions,
                                              unsigned int count);
void dev_pm_opp_put_regulators(struct opp_table *opp_table);
void dev_pm_opp_put_clkname(struct opp_table *opp_table);
void dev_pm_opp_put_supported_hw(struct opp_table *opp_table);

调用 dev_pm_opp_set_rate 之前，设备要先用上面几个接口把依赖绑好。它内部做的事就是把那段伪代码自动化：查表 → 判断方向 → 按正确顺序调 regulator 和 clk → 处理失败回滚。supported_hw 用于同一颗 SoC 的不同速度等级（speed bin），不同 bin 的 OPP 表不同。

这套 API 和 3.x 差别很大。3.x 里没有 opp_table 这个概念，4.x 把它显式化成对象并用引用计数管理生命周期。4.5 到 4.10 之间还改过几轮，具体哪个版本引入了哪个接口，我们没逐版本核对，写「未验证」。唯一确定的是：面对 3.18 及更早的内核，dev_pm_opp_set_rate 不存在，必须手写升压升频逻辑。整条链路：

text
DTS operating-points
    ↓ of_init_opp_table()
OPP 库内部链表 (device_opp → dev_pm_opp...)
    ↓ dev_pm_opp_find_freq_ceil()
struct dev_pm_opp * 句柄
    ↓ dev_pm_opp_get_voltage() / dev_pm_opp_get_freq()
目标电压 + 目标频率
    ↓ regulator_set_voltage() + clk_set_rate()   [3.x 手写]
    ↓ dev_pm_opp_set_rate()                       [4.5+ 库代劳]
硬件实际频率与电压

最后一跳之后硬件是不是真的到位，需要 clk_get_rate() 和 regulator_get_voltage() 回读确认，这属于 cpufreq 或驱动自身的职责，OPP 库不管。

十九、power supply class：供电设备框架 #

前十八节讲「用电的设备」，这一节转过来讲「供电的设备」——电池、充电器、适配器、UPS。

power supply class 有两个目标：抽象 PSY（power supply，下文统一用这个缩写）设备的共性并向用户空间提供统一 API；给底层 PSY 驱动的编写提供统一方式，把公共逻辑封装好，驱动只管硬件相关部分。

PSY 设备明明就是供电的，不用驱动也能供电，内核管它干什么？因为情况比「供电」复杂：电池设备涉及电量检测、充电管理、电池类型识别、健康度评估；系统里有多个 PSY 而且有级联，平板里同时有 DC-charger、USB-charger 和 battery，前两个给 battery 充电，battery 再给系统供电。所以 PSY 驱动真正的职责是向用户空间汇整状态信息，共性就是「属性（properties）」，属性种类有限，个数有限。分工因此很清楚：PSY 驱动负责「这台设备有哪些属性、值是什么、值变了就通知 class」，class 负责「以 sysfs 暴露出去、值变了发 uevent 广播、协助处理级联」。

代码在 drivers/power/ 下拆成三块，具体 PSY 驱动也在这个目录下，只处理平台相关、硬件相关的逻辑：

文件 职责
power_supply_core.c 核心数据结构与公共逻辑
power_supply_sysfs.c sysfs 属性与 uevent
power_supply_leds.c 基于 LED class 的状态指示通用实现

enum power_supply_type 定义设备类型：

        POWER_SUPPLY_TYPE_UNKNOWN = 0,

        POWER_SUPPLY_TYPE_UPS,

BATTERY 是电池，嵌入式最常见；UPS 是不间断电源，交流电和蓄电池组合，断电时电池顶上，多用于服务器；MAINS 是主供电，笔记本适配器那一类，能单独供电，它断了才轮到电池。后面四个 USB 类型的差别全在充电电流限制上，由 USB Battery Charge Spec 规定：SDP 标准下行口、DCP 专用充电口、CDP 充电下行口、ACA 附件充电适配器。这几个类型存在的意义是让用户空间的充电逻辑知道「我现在能拉多大电流」。4.13 前后这个枚举被扩展过，加了 POWER_SUPPLY_TYPE_USB_TYPE_C、POWER_SUPPLY_TYPE_USB_PD 等等，具体加了哪些、哪个版本加的「未验证」，但上面这 8 个在 3.x 里是完整的。

◆4.13 的重构：power_supply_desc #

3.x 那个结构有个设计问题：驱动要初始化的字段（name、type、properties、get_property）和 class 私有的运行时字段（changed_work、changed_lock、dev）混在一起，驱动必须 kzalloc 一整个 power_supply，还得知道哪些字段是「别人的」。4.13 前后做了拆分，静态描述部分抽到 struct power_supply_desc，struct power_supply 只留运行时状态：

c
/* 4.13+ 形态，字段名以新版 power_supply.h 为准，未逐行核对 */
struct power_supply_desc {
        const char *name;
        enum power_supply_type type;
        enum power_supply_property *properties;
        int num_properties;
        int (*get_property)(struct power_supply *psy,
                            enum power_supply_property psp,
                            union power_supply_propval *val);
        int (*set_property)(struct power_supply *psy,
                            enum power_supply_property psp,
                            const union power_supply_propval *val);
        int (*property_is_writeable)(struct power_supply *psy,
                                     enum power_supply_property psp);
        void (*external_power_changed)(struct power_supply *psy);
        void (*set_charged)(struct power_supply *psy);
        bool no_thermal;
        int use_for_apm;
};

配对的 struct power_supply 变成不透明的运行时容器，字段包括 desc（指回描述）、dev、changed_work、changed_lock、initialized、tzd、tcd、of_node、use_for_apm 等。supplied_to / supplied_from 这两个数组在新版里彻底消失了，改成设备树或 device_link 表达供电关系。具体替代机制是 power_supply_get_by_name 加 power_supply_am_i_supplied 的组合，还是完全依赖 fwnode 的 power-supplies 属性，「未验证」——我们只确认这两个字段在 4.13 之后的 power_supply 结构里不再存在。

注册接口也跟着变了，2 参数形式变成接收 desc：

c
/* 4.13+ 形态，未逐版本核对 */
struct power_supply *power_supply_register(struct device *parent,
                                           const struct power_supply_desc *desc,
                                           const struct power_supply_config *cfg);

返回指针而不是 int，失败用 IS_ERR() 判断。配对的是 power_supply_unregister(psy) 和一个新的 power_supply_put(psy)，因为 power_supply_get_by_name 现在也带引用计数了。写驱动的建议：先看手上内核版本。3.x 按老结构写，4.13+ 按 desc 写，中间的 4.0~4.12 两者都有过渡形态（power_supply_register 仍有 2 参数版但内部已经拆了 desc），这一段的准确断代「未验证」，以 include/linux/power_supply.h 的实际定义为准。

二十一、power_supply 的注册与通知 #

c
extern int power_supply_register(struct device *parent,
                                 struct power_supply *psy);
extern int power_supply_register_no_ws(struct device *parent,
                                 struct power_supply *psy);
extern void power_supply_unregister(struct power_supply *psy);

两个注册函数的唯一差别：前者注册的 PSY 具备唤醒系统的能力，会创建一个 wakeup source，后者不具备。选哪个看板级设计——插拔充电器能不能唤醒系统。

power_supply_register 内部做了很多事：创建 struct device、挂到 power_supply class 下、创建 sysfs 属性组（只创建 properties 里声明的那些）、初始化 changed_work、注册 wakeup source、必要时注册 thermal 和 LED。

状态变更通知只有一个函数：

c
extern void power_supply_changed(struct power_supply *psy);

驱动检测到任何属性值变了就调它，class 会做四件事：如果本 PSY 是别人的供电源，遍历所有 supplicant 调它们的 external_power_changed；如果开了 CONFIG_LEDS_TRIGGERS，调 power_supply_update_leds 更新 LED；发 notifier 通知所有注册了 power_supply_reg_notifier 的驱动；按统一格式向用户空间发 uevent。

第一条不递归，只通知直接 supplicant。级联三层的话，中间那层的驱动要自己再调一次 power_supply_changed。

杂项接口：

c
extern struct power_supply *power_supply_get_by_name(const char *name);
extern struct power_supply *power_supply_get_by_phandle(struct device_node *np,
                                                        const char *property);
extern int power_supply_am_i_supplied(struct power_supply *psy);
extern int power_supply_set_battery_charged(struct power_supply *psy);
extern int power_supply_is_system_supplied(void);
extern int power_supply_powers(struct power_supply *psy, struct device *dev);
接口 作用
power_supply_get_by_name 按名字取 PSY 指针
power_supply_get_by_phandle 从 DTS 的 phandle 取 PSY 指针
power_supply_am_i_supplied 查我自己是否由别的 PSY 供电
power_supply_set_battery_charged 转调指定 PSY 的 set_charged
power_supply_is_system_supplied 系统是否有在线 PSY
power_supply_powers 在指定设备 sysfs 目录下建 powers 符号链接

power_supply_is_system_supplied 这个名字骗了不少人。它不是「系统有没有电」，而是「有没有一个在线的外部供电源」。返回值 0 在嵌入式场景意味着「纯电池供电」，在桌面场景意味着「没有电池，只有市电」——两种情况返回值相同但含义相反，调用方必须结合板级配置判断。

notifier 是两个函数：

c
extern int power_supply_reg_notifier(struct notifier_block *nb);
extern void power_supply_unreg_notifier(struct notifier_block *nb);

任何 PSY 状态变了并调了 power_supply_changed，所有注册的 notifier 都被通知。这是「别的驱动跟踪电池状态」的标准做法，比如背光驱动想在电量低时调暗。回调跑在 changed_work 这个 workqueue 上，可以睡，但别做太重的工作。

二十二、/sys/class/power_supply 下的接口 #

class 通过两种形式对用户空间暴露信息。第一种是 uevent，格式为「名字=值」，每条属性一行：

text
POWER_SUPPLY_NAME=xxx                     /* power supply name */
POWER_SUPPLY_xxx1=xxx                     /* property = value */
POWER_SUPPLY_xxx2=xxx
...

uevent 在两个时机发：设备注册进内核时、属性发生改变（power_supply_changed）时。用户空间（udev、Android 的 healthd/health HAL）靠监听它更新电池图标、触发低电量关机。注意 uevent 里的属性名是大写的、带 POWER_SUPPLY_ 前缀，和 sysfs 文件名（小写）不同，解析代码两边要分别处理。

第二种是 sysfs。power_supply_sysfs.c 里定义了一个 device_attribute 数组，和 enum power_supply_property 严格同序：

c
/* Must be in the same order as POWER_SUPPLY_PROP_* */
/* 完整的 65 项与上面的 enum power_supply_property 一一对应，这里只示首尾 */
static struct device_attribute power_supply_attrs[] = {
        POWER_SUPPLY_ATTR(status),
        ...
        POWER_SUPPLY_ATTR(model_name),
        POWER_SUPPLY_ATTR(manufacturer),
        POWER_SUPPLY_ATTR(serial_number),
};

「同序」是硬约束。POWER_SUPPLY_ATTR(status) 之所以能定位到 POWER_SUPPLY_PROP_STATUS，靠的就是数组下标和枚举值一一对应。你在这里插一个、上面漏一个，所有属性都会错位，症状是读 capacity 拿到 temp 的值——这类 bug 排查起来很费劲，因为值本身看起来都是合理数字。

某个 PSY 设备的目录里只会出现它 properties 数组里声明过的文件。电池一般有 capacity、status、health、voltage_now、temp、technology、cycle_count；充电器一般有 online、type、current_max、input_current_limit。

单位约定：voltage_* 是 uV，current_* 是 uA，charge_* 是 uAh，energy_* 是 uWh，capacity 是百分数（0~100），temp 是 0.1 摄氏度（25.3℃ 读出来是 253），time_to_* 是秒。temp 的 0.1 度是踩坑重灾区，直接用会得到「电池温度 253 度」这种荒谬读数。

从 PSY 驱动作者角度看，流程四步：对着硬件 spec 列出特性并映射到 enum power_supply_property；实现这些属性的 get_property / set_property；定义并初始化 struct power_supply，调 power_supply_register 或 power_supply_register_no_ws；启动属性变化的检测（中断或轮询），变了就调 power_supply_changed。框架能提供的就这么多了。

二十四、易错点速查 #

按踩坑频率排序。

1. usage_count 和 disable_depth 当成一回事。 前者是「有几个人在用」，后者是「机制关没关」。pm_runtime_disable 加的是 disable_depth，pm_runtime_get 加的是 usage_count；pm_runtime_enable 之后不自动 idle，要补 pm_request_idle。

2. probe 里忘了 pm_runtime_set_active。 初始状态是 RPM_SUSPENDED，硬件实际却是活的，第一次 get_sync 会多调一次 runtime_resume。

3. get_sync 失败后没补 put_noidle。 计数永久差一，设备永远不睡。

4. pm_runtime_put() 后面的代码以为设备还醒着。 异步 put 之后回调在另一个线程跑完了。

5. 在中断里调同步接口。 除非 pm_runtime_irq_safe() 声明过，否则 might_sleep() 会告警甚至崩。

6. runtime_error 粘住。 一次回调失败后后续所有 RPM 操作都返回同一个错误，要 pm_runtime_set_active 之类清掉。

7. ignore_children 用错。 父设备挂起后子设备还在工作，访问硬件必错。

8. OPP 单位搞混。 DTS 里频率 kHz，API 里 Hz，差 1000 倍。dev_pm_opp_find_freq_ceil 永远查不到就是这里错了。

9. 调频调压顺序反了。 升频先升压，降频先降频，反过来跑飞。

10. OPP 句柄漏 dev_pm_opp_put。 4.x 之后会泄漏。

11. power_supply 属性表和枚举错位。 两边顺序必须严格一致，插一个漏一个就全体错位。

12. temp 属性直接用。 单位是 0.1 摄氏度，25.3℃ 读出来是 253。

13. power_supply_changed 忘了调。 值变了用户空间不知道，电池图标不更新。

14. power_supply_is_system_supplied 返回值理解反。 0 在纯电池板和纯市电板上都会出现。
