一、Suspend 要解决什么：睡下去之后谁负责叫醒 #

Suspend 的语义是「把整台机器塞进一个能恢复的低功耗状态，等一个事件把它拽回来」。它和 idle 的区别只有一条：CPU 停了，上下文还在。所以它从来不是单一动作，而是一串有顺序的让步——进程先停、设备先睡、中断先关，最后才是 CPU 断电。任何一步乱了顺序，恢复时就是死机或者数据损坏。

睡下去之后谁负责叫醒，是第二个问题，也是整个电源管理里最难的部分。按键、充电器插入、RTC 闹钟、网络包，产生的时间点不受控。它们会落在你正在冻结进程的那一毫秒里，也会落在你刚写完 wakeup_count 还没关中断的那一毫秒里。

幼稚的实现会在那种时刻直接睡过去，然后事件已经处理了一半、用户态还没跑完、系统却睡了。醒来后事件丢失，用户看到一个没反应的机器。

wakeup events framework 就是来处理这件事的。它给每个能唤醒系统的设备挂一个 wakeup_source，用两个计数器（已登记事件数、处理中事件数）描述「现在有没有事情在做」，然后在 suspend 路径的关键节点上反复检查：还在处理中就中止挂起。wakeup_count 在此基础上再加一层，解决用户态与内核之间的竞态。

一句话记住分工：Suspend 决定怎么睡，wakeup events 决定能不能睡。

二、Suspend 的三种状态：freeze / standby / mem #

用户态入口只有一个文件，/sys/power/state：

bash
echo freeze  > /sys/power/state
echo standby > /sys/power/state
echo mem     > /sys/power/state

写进内核就是三个枚举值（include/linux/suspend.h，3.x）：

c
typedef int __bitwise suspend_state_t;

#define PM_SUSPEND_ON           ((__force suspend_state_t) 0)
#define PM_SUSPEND_FREEZE       ((__force suspend_state_t) 1)
#define PM_SUSPEND_STANDBY      ((__force suspend_state_t) 2)
#define PM_SUSPEND_MEM          ((__force suspend_state_t) 3)
#define PM_SUSPEND_MIN          PM_SUSPEND_FREEZE
#define PM_SUSPEND_MAX          ((__force suspend_state_t) 4)

PM_SUSPEND_MAX 不是状态，是哨兵值，写 disk 落到 hibernate 分支。state_store 就这么分的：

c
static ssize_t state_store(struct kobject *kobj, struct kobj_attribute *attr,
                           const char *buf, size_t n)
{
        suspend_state_t state;
        int error;

        error = pm_autosleep_lock();
        if (error)
                return error;

        if (pm_autosleep_state() > PM_SUSPEND_ON) {
                error = -EBUSY;
                goto out;
        }

        state = decode_state(buf, n);
        if (state < PM_SUSPEND_MAX)
                error = pm_suspend(state);
        else if (state == PM_SUSPEND_MAX)
                error = hibernate();
        else
                error = -EINVAL;

 out:
        pm_autosleep_unlock();
        return error ? error : n;
}

power_attr(state);

开头两行先拿 pm_autosleep_lock()，autosleep 开着就 -EBUSY。手动挂起和 autosleep 互斥，这是设计。

状态 写入值 平台回调 做了什么 功耗
freeze freeze 不需要 suspend_ops 冻结进程 + 设备 suspend + CPU 进 idle 降低有限
standby standby 要 suspend_ops->valid 认可 上述三项 + 平台 standby 中等
mem（STR） mem 要 suspend_ops->valid 认可 上述三项 + 关非 boot CPU + 关中断 + suspend_ops->enter() 最低，内存只靠自刷新

freeze 是唯一不要平台配合的，valid_state 把这一点写死了：

c
bool valid_state(suspend_state_t state)
{
        if (state == PM_SUSPEND_FREEZE) {
                return true;
        }
        /*
         * PM_SUSPEND_STANDBY and PM_SUSPEND_MEMORY states need lowlevel
         * support and need to be valid to the lowlevel
         * implementation, no valid callback implies that none are valid.
         */
        return suspend_ops && suspend_ops->valid && suspend_ops->valid(state);
}

内核注释给 freeze 的定义最准：PM_SUSPEND_FREEZE equals frozen processes + suspended devices + idle processors。

版本变化：4.x 起 suspend.c 重构，PM_SUSPEND_FREEZE 与 freeze_enter() 从这条路径上消失，freeze 退回 freezer 子系统的语义（写 freeze 仍可用，路径不同）。具体版本点未验证。

三、pm_suspend 的完整入口 #

pm_suspend() 在 kernel/power/suspend.c，薄得像包装：

c
int pm_suspend(suspend_state_t state)
{
        int error;

        if (state <= PM_SUSPEND_ON || state >= PM_SUSPEND_MAX)
                return -EINVAL;

        error = enter_state(state);
        if (error) {
                suspend_stats.fail++;
                dpm_save_failed_errno(error);
        } else {
                suspend_stats.success++;
        }
        return error;
}

只做参数检查和统计。suspend_stats 的 success/fail 加 dpm_save_failed_errno() 记的错误码，在 /sys/power/suspend_stats 下能读。现场查「为什么老挂不下去」，先看这里。

边界是 state <= PM_SUSPEND_ON || state >= PM_SUSPEND_MAX，只放行 1、2、3。传 0（PM_SUSPEND_ON）不会当 no-op，直接 -EINVAL。真正的活全在 enter_state()。

四、enter_state：Suspend 的主流程 #

c
static int enter_state(suspend_state_t state)
{
        int error;

        if (!valid_state(state))
                return -ENODEV;

        if (!mutex_trylock(&pm_mutex))
                return -EBUSY;

        if (state == PM_SUSPEND_FREEZE)
                freeze_begin();

        printk(KERN_INFO "PM: Syncing filesystems ... ");
        sys_sync();
        printk("done.\n");

        pr_debug("PM: Preparing system for %s sleep\n", pm_states[state]);
        error = suspend_prepare(state);
        if (error)
                goto Unlock;

        if (suspend_test(TEST_FREEZER))
                goto Finish;

        pr_debug("PM: Entering %s sleep\n", pm_states[state]);
        pm_restrict_gfp_mask();
        error = suspend_devices_and_enter(state);
        pm_restore_gfp_mask();

 Finish:
        pr_debug("PM: Finishing wakeup.\n");
        suspend_finish();
 Unlock:
        mutex_unlock(&pm_mutex);
        return error;
}

逐条：valid_state() 平台不认就 -ENODEV；mutex_trylock(&pm_mutex) 是 trylock 不是 lock，第二个挂起请求立刻 -EBUSY，不排队——它一阻塞就带着活任务进冻结流程，局面更糟；freeze_begin() 只对 freeze 做；sys_sync() 刷脏页，用户态看到卡在 PM: Syncing filesystems ... 就是卡 IO；suspend_prepare() 失败去 Unlock，收尾由它自己负责；suspend_test(TEST_FREEZER) 是 /sys/power/pm_test 的调试钩子；pm_restrict_gfp_mask() 在挂起期间收紧到 GFP_ATOMIC 级，防止有人做需要回收的分配——回收会唤醒 flusher，而 flusher 正冻着；suspend_devices_and_enter() 是重头戏；suspend_finish() 解冻、发 PM_POST_SUSPEND、还原 console。

pm_mutex 覆盖整段，整个挂起-恢复周期是全局串行的。

五、第一阶段：冻结进程 #

冻结在 suspend_prepare() 里，顺序是死的：pm_prepare_console() → PM_SUSPEND_PREPARE notifier → suspend_freeze_processes()，前两步失败都跳 Finish 回滚。

c
static int suspend_prepare(suspend_state_t state)
{
        int error;

        if (need_suspend_ops(state) && (!suspend_ops || !suspend_ops->enter))
                return -EPERM;

        pm_prepare_console();

        error = pm_notifier_call_chain(PM_SUSPEND_PREPARE);
        if (error)
                goto Finish;

        error = suspend_freeze_processes();
        if (!error)
                return 0;

        suspend_stats.failed_freeze++;
        dpm_save_failed_step(SUSPEND_FREEZE);
 Finish:
        pm_notifier_call_chain(PM_POST_SUSPEND);
        pm_restore_console();
        return error;
}

console 那一步做 VT switch：前台切到 SUSPEND_CONSOLE，kmsg 一并重定向过去。理由是挂起过程中设备逐个下线，你正看的 VT 依赖的设备刚被 suspend，画面就花了。VT switch 很贵，全局开关 pm_vt_switch() 三种情况才开：有 console driver 调 pm_vt_switch_required(true)；系统禁了 suspend console（console_suspend_enabled 为假）；没有任何 driver 表过态。四步操作记住名字：prepare / suspend（hold 住 printk 的 console 互斥锁）/ resume / restore，suspend_console() 在 kernel/printk.c。

PM notifier 是后门。按设备模型，设备 suspend 在冻结之后、resume 在解冻之前。必须在冻结之前 suspend 的设备、resume 要等用户态数据的设备，都被这个顺序坑了——后者会把所有进程一起堵住。notifier 让它们绕过设备模型直接收 PM_SUSPEND_PREPARE / PM_POST_SUSPEND。素材点的实例是 drivers/video/omap2/dss/core.c（3.x 路径）。

suspend_freeze_processes() 在 kernel/power/process.c，完整状态机在《中断唤醒与进程冻结》。这里只记三件事：失败记 suspend_stats.failed_freeze++ 和 dpm_save_failed_step(SUSPEND_FREEZE) 后整条链中止；冻结后用户态不再被调度，这正是「事件已到内核、但没人处理」的来由；冻结期间需要用户态配合的分配会卡死，所以 enter_state 要收紧 gfp mask。

六、第二阶段：设备 suspend（dpm_suspend） #

suspend_devices_and_enter() 是设备阶段的总调度：

c
int suspend_devices_and_enter(suspend_state_t state)
{
        int error;
        bool wakeup = false;

        if (need_suspend_ops(state) && !suspend_ops)
                return -ENOSYS;

        trace_machine_suspend(state);
        if (need_suspend_ops(state) && suspend_ops->begin) {
                error = suspend_ops->begin(state);
                if (error)
                        goto Close;
        }
        suspend_console();
        ftrace_stop();
        suspend_test_start();
        error = dpm_suspend_start(PMSG_SUSPEND);
        if (error) {
                printk(KERN_ERR "PM: Some devices failed to suspend\n");
                goto Recover_platform;
        }
        suspend_test_finish("suspend devices");
        if (suspend_test(TEST_DEVICES))
                goto Recover_platform;

        do {
                error = suspend_enter(state, &wakeup);
        } while (!error && !wakeup && need_suspend_ops(state)
                && suspend_ops->suspend_again && suspend_ops->suspend_again());

 Resume_devices:
        suspend_test_start();
        dpm_resume_end(PMSG_RESUME);
        suspend_test_finish("resume devices");
        ftrace_start();
        resume_console();
 Close:
        if (need_suspend_ops(state) && suspend_ops->end)
                suspend_ops->end();
        trace_machine_suspend(PWR_EVENT_EXIT);
        return error;

 Recover_platform:
        if (need_suspend_ops(state) && suspend_ops->recover)
                suspend_ops->recover();
        goto Resume_devices;
}

按顺序：suspend_ops->begin() 通知平台「要开始了」，可失败，失败直接 Close；suspend_console() 握死 console 互斥锁，printk 从此只进 ring buffer；ftrace_stop() 停 ftrace，理由相同——后端要走设备；dpm_suspend_start() 跑设备第一半；失败走 Recover_platform；suspend_enter() 跑第二半；do/while 里的 suspend_again() 由平台决定要不要再来一轮，返回 true 就再进一次；退出后 Resume_devices 逆序恢复；最后 Close 收平台。

dpm_suspend_start() 展开（drivers/base/power/main.c）：

c
int dpm_suspend_start(pm_message_t state)
{
        int error;

        error = dpm_prepare(state);
        if (error) {
                dpm_save_failed_step(SUSPEND_PREPARE);
                dpm_complete(state);
                return error;
        }
        return dpm_suspend(state);
}

dpm_prepare() 遍历设备调 ->prepare，是预检，顺手把还忙的设备掐到 idle；dpm_suspend() 调 ->suspend，设备真的进入低功耗。注意失败处理不对称：prepare 失败要立刻 dpm_complete，因为它已经对所有设备跑过一遍，complete 得全部收回；dpm_suspend 失败只需回滚已经 suspend 过的，那是 dpm_resume 的事。

suspend_enter() 里还有 dpm_suspend_end()：

c
int dpm_suspend_end(pm_message_t state)
{
        int error = dpm_suspend_late(state);
        if (error)
                return error;
        error = dpm_suspend_noirq(state);
        if (error)
                dpm_resume_early(state);
        return error;
}

late 失败直接退，noirq 失败要把 late 退回来。位置越深，回滚越麻烦。

七、设备 suspend 的顺序与依赖 #

dpm_list 的顺序就是 suspend 顺序，resume 严格逆序，按注册顺序形成（先注册的排前面）。规律是先挂起子系统，后挂起底层控制器：USB 设备先于 USB 控制器，控制器先于电源域，电源域先于时钟控制器。device_pm_move_to_tail() 就是给「我不在 parent 后面就活不了」的驱动留的。

轮次 回调 中断状态 该干什么
1 ->prepare 开 预检，等 runtime PM 落地，失败可中止整个挂起
2 ->suspend 开 主体挂起：存寄存器、关时钟、关电源域
3 ->suspend_late 开，其它设备已 noirq 最后一刻的寄存器与电源操作
4 ->suspend_noirq IRQ 线已被禁用 需要「确定没有中断进来」的动作

resume 侧对称：->resume_noirq → ->resume_early → ->resume → ->complete。反直觉点：->suspend_noirq 的 noirq 不是全局关中断，只是各 IRQ 线被禁用，CPU 照常调度。所以 suspend_enter() 先用 dpm_suspend_end()，不提前 arch_suspend_disable_irqs()。

八、第三阶段：platform suspend 与关中断 #

suspend_enter() 是整条流程里最深的一段：

c
static int suspend_enter(suspend_state_t state, bool *wakeup)
{
        int error;

        if (need_suspend_ops(state) && suspend_ops->prepare) {
                error = suspend_ops->prepare();
                if (error)
                        goto Platform_finish;
        }

        error = dpm_suspend_end(PMSG_SUSPEND);
        if (error) {
                printk(KERN_ERR "PM: Some devices failed to power down\n");
                goto Platform_finish;
        }

        if (need_suspend_ops(state) && suspend_ops->prepare_late) {
                error = suspend_ops->prepare_late();
                if (error)
                        goto Platform_wake;
        }

        if (suspend_test(TEST_PLATFORM))
                goto Platform_wake;

        /*
         * PM_SUSPEND_FREEZE equals
         * frozen processes + suspended devices + idle processors.
         * Thus we should invoke freeze_enter() soon after
         * all the devices are suspended.
         */
        if (state == PM_SUSPEND_FREEZE) {
                freeze_enter();
                goto Platform_wake;
        }

        error = disable_nonboot_cpus();
        if (error || suspend_test(TEST_CPUS))
                goto Enable_cpus;

        arch_suspend_disable_irqs();
        BUG_ON(!irqs_disabled());

        error = syscore_suspend();
        if (!error) {
                *wakeup = pm_wakeup_pending();
                if (!(suspend_test(TEST_CORE) || *wakeup)) {
                        error = suspend_ops->enter(state);
                        events_check_enabled = false;
                }
                syscore_resume();
        }

        arch_suspend_enable_irqs();
        BUG_ON(irqs_disabled());

 Enable_cpus:
        enable_nonboot_cpus();

 Platform_wake:
        if (need_suspend_ops(state) && suspend_ops->wake)
                suspend_ops->wake();

        dpm_resume_start(PMSG_RESUME);

 Platform_finish:
        if (need_suspend_ops(state) && suspend_ops->finish)
                suspend_ops->finish();

        return error;
}

顺序不能换。逐段：

  1. suspend_ops->prepare()，平台最后的一般准备。
  2. dpm_suspend_end()，late + noirq 两轮设备回调。
  3. suspend_ops->prepare_late()，平台在「所有设备已 noirq」之后的准备。
  4. freeze 分支：freeze_enter()，CPU 进 idle 等中断。只在这一支上，因为 freeze 不需要关中断、关 CPU。
  5. disable_nonboot_cpus()，把非 boot CPU 全下线。多核上每个 CPU 都有自己的状态，得先收敛到一个。
  6. arch_suspend_disable_irqs()，关全局中断。紧跟着的 BUG_ON(!irqs_disabled()) 是硬性自检，关不掉就是内核 bug，没有「继续尝试」这一说。
  7. syscore_suspend()，挂起 syscore 设备（时间、中断控制器、时钟事件、DMA 控制器这类「核心中的核心」）。syscore 是一层特殊的设备列表，跑在关中断之后，只能用不睡眠的操作。
  8. pm_wakeup_pending()，睡前的最后一道闸。返回值塞进 *wakeup。
  9. suspend_ops->enter(state)，真正进低功耗。这一句返回，就意味着系统已经被唤醒了。
  10. events_check_enabled = false，醒来后清掉 wakeup count 的检查标志。只在真正 enter 过之后才清，中止路径不清，细节在第十八章。
  11. syscore_resume() → arch_suspend_enable_irqs() → enable_nonboot_cpus()，对称恢复。
  12. suspend_ops->wake() → dpm_resume_start(PMSG_RESUME)，设备从 noirq 层往回收。
  13. suspend_ops->finish()，平台收尾。

几个 goto 标签的落点要分清，回滚深度不一样：

  • Platform_finish：只做了 ->prepare 就失败了，或者 dpm_suspend_end 失败。回滚只需平台 ->finish。
  • Platform_wake：已经 noirq 了，必须先 ->wake() 再 dpm_resume_start() 把设备捞回来。
  • Enable_cpus：CPU 已下线，先 enable_nonboot_cpus() 再往 Platform_wake 落。

九、dpm_suspend_noirq 与中断的关闭时机 #

三层「关中断」必须分开，混在一起是这行代码最常见的误解来源：

阶段 谁在关 关到什么程度 还能调度吗
->suspend_noirq DPM 逐设备禁 IRQ 线 该设备 IRQ 被 disable 能，CPU 正常跑
syscore_suspend 进 syscore 前已关全局中断 中断控制器还在，CPU 本地中断已关 不能睡眠，只能自旋
suspend_ops->enter 平台代码 中断控制器关闭，CPU 断电或进 WFI 全停

dpm_suspend_noirq 的名字是「no IRQ」，不是「no 中断指令」。它的价值在于设备 IRQ 全禁后不会再有新中断打断这一轮遍历，驱动代码本身照常跑在进程或软中断上下文。

arch_suspend_disable_irqs() 之后，中断控制器还没关，只是 CPU 本地中断关闭。真正的「关」在 suspend_ops->enter() 里。这也是 syscore_suspend() 必须排在它之后的原因——syscore 要管的设备包含中断控制器本身，得先保证没有中断在飞。

从 wakeup 角度看，第 6 步之后系统不再产生任何 event，combined_event_count 冻在那一刻。所以 pm_wakeup_pending() 的严格含义是「到关中断为止，有没有未处理完的事件」。

唤醒事件从 IRQ 到 irq_wake 的具体路径在《中断唤醒与进程冻结》，本篇不碰。

十、resume 的逆流程 #

resume 分散在三处，不是一段代码。

第一段在 suspend_enter() 内部，从 suspend_ops->enter() 返回那一刻开始：

text
suspend_ops->enter() 返回
  -> syscore_resume()
  -> arch_suspend_enable_irqs()
  -> enable_nonboot_cpus()
  -> suspend_ops->wake()
  -> dpm_resume_start(PMSG_RESUME)   /* ->resume_noirq + ->resume_early */
  -> suspend_ops->finish()

第二段回到 suspend_devices_and_enter() 的 Resume_devices：dpm_resume_end(PMSG_RESUME)（->resume + ->complete）、ftrace_start()、resume_console()、suspend_ops->end()。 dpm_resume_end 是 dpm_resume() + dpm_complete()，加 might_sleep() 和 dpm_list_mtx 保护。

第三段在 enter_state() 的 Finish：

c
static void suspend_finish(void)
{
        suspend_thaw_processes();
        pm_notifier_call_chain(PM_POST_SUSPEND);
        pm_restore_console();
}

顺序是死的：先解冻进程，再还原 console。反过来，console 切回去了而进程还冻着，用户看到一个死掉的控制台，会以为挂起失败卡住了。

首尾对照：

顺序 suspend resume
1 pm_prepare_console() pm_restore_console()
2 PM_SUSPEND_PREPARE PM_POST_SUSPEND
3 suspend_freeze_processes() suspend_thaw_processes()
4 suspend_console() resume_console()
5 dpm_suspend_start() dpm_resume_end()
6 dpm_suspend_end() dpm_resume_start()
7 disable_nonboot_cpus() enable_nonboot_cpus()
8 arch_suspend_disable_irqs() arch_suspend_enable_irqs()
9 syscore_suspend() syscore_resume()
10 suspend_ops->enter() 平台内部

第 5、6 步之间隔着 suspend_enter() 的开头，别把 dpm_suspend_start 当成「设备全睡完了」，它只睡了一半。

resume 特有的一个坑：唤醒源在 resume 过程中会再次触发。设备刚 ->resume，中断线还没恢复到能处理事件，此时来的事件挂在 pending 上，等 arch_suspend_enable_irqs() 之后才处理。这段窗口里 wakeup_source 的状态一致性由驱动保证，框架只保证计数不丢。

十一、Suspend 失败时的回滚 #

失败分三类，回滚深度完全不同。

准备阶段失败：enter_state 直接 goto Unlock，不调 suspend_devices_and_enter，也不调 suspend_finish。清理责任在 suspend_prepare 自己的 Finish 标签：发 PM_POST_SUSPEND、pm_restore_console()。冻结失败还要记 suspend_stats.failed_freeze++ 和 dpm_save_failed_step(SUSPEND_FREEZE)。

设备 suspend 失败：落点 Recover_platform，先平台 ->recover() 再 Resume_devices。为什么先 recover——suspend_ops->begin() 会改平台状态，->recover() 就是给这种半成品擦屁股的。

suspend_enter 内部失败：最多三级嵌套，看 goto 落点。

text
suspend_ops->prepare()        失败 -> Platform_finish   （只有平台要收尾）
dpm_suspend_end()             失败 -> Platform_finish   （内部已自行 dpm_resume_early）
suspend_ops->prepare_late()   失败 -> Platform_wake     （设备已 noirq，要 ->wake + dpm_resume_start）
disable_nonboot_cpus()        失败 -> Enable_cpus       （CPU 已部分下线）
syscore_suspend()             失败 -> arch_suspend_enable_irqs()
pm_wakeup_pending() 为真      -> syscore_resume + 开中断，原样返回
suspend_ops->enter() 返回     -> 正常退出，见第十章

pm_wakeup_pending() 返回 true 不是「失败」，是「主动中止」。*wakeup 置真后跳过 enter()，也不清 events_check_enabled，然后把 syscore_resume() 跑完、中断打开、设备恢复。对外返回的 error 仍是 0。挂起被唤醒事件中止，pm_suspend() 的返回值是成功。 这就是为什么用户态写入返回 n、却发现自己没睡。

dpm_save_failed_step() / dpm_save_failed_dev() / dpm_save_failed_errno() 三个记录点串起来就是 /sys/power/suspend_stats/last_failed_dev 和 last_failed_step。现场第一站：

bash
cat /sys/power/suspend_stats/success
cat /sys/power/suspend_stats/fail
cat /sys/power/suspend_stats/last_failed_dev
cat /sys/power/suspend_stats/last_failed_step

last_failed_step 取值是 SUSPEND_FREEZE、SUSPEND_PREPARE、SUSPEND_SUSPEND、SUSPEND_SUSPEND_LATE、SUSPEND_SUSPEND_NOIRQ 这一串（命名随版本，未逐一验证）。它直接告诉你卡在第几轮。

/sys/power/pm_test 是另一件工具：写 freezer、devices、platform、processors、core 中任一个，内核会在对应阶段停下、返回，不真正进低功耗。二分定位失败点用它。

十二、唤醒事件框架要解决什么 #

问题一句话：suspend 的过程中来了 wakeup event，怎么办。 答案是终止挂起。麻烦在挂起过程中进程被冻结、设备被挂起，事件不一定能被及时处理。

内核空间同步：事件以中断到达驱动，驱动在处理，处理完前不能睡，计数器能解决。用户空间同步：驱动处理完交给用户态继续，分两种——该进程根本没机会被调度（已冻住），或者被调度了、正在处理且处理完还要决定要不要中止挂起。两个窗口里系统都不能睡。

于是框架拆成四块：内核空间同步用 wakeup_source + in-progress 计数 + pm_wakeup_pending()（drivers/base/power/wakeup.c）；用户空间同步的情境 1 用 wakeup_count；情境 2 用 wakelock（kernel/power/wakelock.c）；「谁来触发挂起」交给 autosleep（kernel/power/autosleep.c）。

裂缝始终存在：kernel 认为电源是核心资源、不该由用户态决定，Android 认为必须由用户态决定。产物就是两个可选配置。从 kernel/power/main.c 的属性数组能看出亲疏：

c

        &wake_unlock_attr.attr,
#endif

state 无条件在，wakeup_count 只要 CONFIG_PM_SLEEP 就在，autosleep 和 wake_lock/wake_unlock 各自被一个额外宏包着。

十三、wakeup_source：一个唤醒源的抽象 #

能唤醒系统的只有设备，但不是每个设备都能。有唤能力的设备称作 wakeup source，它在设备模型里的落脚点是 struct device 的 power 字段：

c
struct device {
        ...
        struct dev_pm_info      power;
        ...
};

struct dev_pm_info {
        ...
        unsigned int            can_wakeup:1;
        ...
#ifdef CONFIG_PM_SLEEP
        ...
        struct wakeup_source    *wakeup;
        ...
#else
        unsigned int            should_wakeup:1;
#endif
};

can_wakeup 说明这台设备硬件上能唤醒。只有它为真，sysfs 里才有 power/ 目录，里面才有 wakeup、wakeup_count 等属性。真正承载信息的是 struct wakeup_source（include/linux/pm_wakeup.h，3.x 形态）：

c
struct wakeup_source {
        const char              *name;
        struct list_head        entry;
        spinlock_t              lock;
        struct timer_list       timer;
        unsigned long           timer_expires;
        ktime_t total_time;
        ktime_t max_time;
        ktime_t last_time;
        ktime_t start_prevent_time;
        ktime_t prevent_sleep_time;
        unsigned long           event_count;
        unsigned long           active_count;
        unsigned long           relax_count;
        unsigned long           expire_count;
        unsigned long           wakeup_count;
        bool                    active:1;
        bool                    autosleep_enabled:1;
};

字段逐个过，这张表是本篇最该记住的一张：

字段 类型 含义 实战用法

prepare 与 create 的分工要记住：前者给内嵌的结构用（struct wakelock 内嵌一个 ws，走 prepare + add），后者自己分配内存。一个设备从零到有唤醒源：

c

十四、wakeup_source 的引用计数 #

pm_stay_awake() 和 pm_relax() 必须成对调用。多个中断源共享同一个唤醒源时，「成对」就变成了计数问题。

activate 是幂等的：

c
static void wakeup_source_activate(struct wakeup_source *ws)
{
        unsigned int cec;

        /*
         * active wakeup source should bring the system
         * out of PM_SUSPEND_FREEZE state
         */
        freeze_wake();

        ws->active = true;
        ws->active_count++;
        ws->last_time = ktime_get();
        if (ws->autosleep_enabled)
                ws->start_prevent_time = ws->last_time;

        /* Increment the counter of events in progress. */
        cec = atomic_inc_return(&combined_event_count);

        trace_wakeup_source_activate(ws->name, cec);
}

重复 activate 一个已 active 的源，只加 active_count，不加 in-progress 计数。in-progress 记的是「多少批事件正在处理」，不是「activate 被调了几次」。

deactivate 有一道防重复的门：

c
static void wakeup_source_deactivate(struct wakeup_source *ws)
{
        unsigned int cnt, inpr, cec;
        ktime_t duration;
        ktime_t now;

        ws->relax_count++;
        /*
         * __pm_relax() may be called directly or from a timer function.
         * If it is called directly right after the timer function has been
         * started, but before the timer function calls __pm_relax(), it is
         * possible that __pm_stay_awake() will be called in the meantime and
         * will set ws->active.  Then, ws->active may be cleared immediately
         * by the __pm_relax() called from the timer function, but in such a
         * case ws->relax_count will be different from ws->active_count.
         */
        if (ws->relax_count != ws->active_count) {
                ws->relax_count--;
                return;
        }

        ws->active = false;

        now = ktime_get();
        duration = ktime_sub(now, ws->last_time);
        ws->total_time = ktime_add(ws->total_time, duration);
        if (ktime_to_ns(duration) > ktime_to_ns(ws->max_time))
                ws->max_time = duration;

        ws->last_time = now;
        del_timer(&ws->timer);
        ws->timer_expires = 0;

        if (ws->autosleep_enabled)
                update_prevent_sleep_time(ws, now);

        /*
         * Increment the counter of registered wakeup events and decrement the
         * couter of wakeup events in progress simultaneously.
         */
        cec = atomic_add_return(MAX_IN_PROGRESS, &combined_event_count);
        trace_wakeup_source_deactivate(ws->name, cec);

        split_counters(&cnt, &inpr);
        if (!inpr && waitqueue_active(&wakeup_count_wait_queue))
                wake_up(&wakeup_count_wait_queue);
}

relax_count != active_count 这个判据值得停一下。内核注释讲的是：定时器路径和直接调用会撞车。定时器到期想 relax，直接调用的 __pm_relax() 也来了，期间又来了一次 __pm_stay_awake()。这时候无脑清 active，就把新事件的状态抹掉了。所以不等就退出：本次 relax 是多余的，撤掉自己加的 relax_count，什么都不做。

三个计数器的实用价值：

  • active_count > relax_count：有事件在处理，或者有驱动漏了 pm_relax。差值不归零，系统再也睡不着。
  • relax_count > active_count：多调了 pm_relax，被上面的判据挡掉。数值本身无害，但说明驱动的配对有问题。
  • expire_count > 0：有人在用 __pm_wakeup_event()，正常用法。

配合 ws->wakeup_count（sysfs 里的 wakeup_abort_count），能在「反复挂起失败」时锁定嫌疑人。

十五、active 与 registered 的区别 #

两个「状态」概念，中文都叫活跃，必须掰开。

ws->active：这个唤醒源当前是否持有一次未归还的唤醒。从设备视角看，由 pm_stay_awake / pm_relax 切换。

registered wakeup events：全局计数器的高位，记录历史上完整处理完的事件总数，只增不减。

先看两个容易混的判定式：

c
bool device_can_wakeup(struct device *dev)   { return dev->power.can_wakeup; }
bool device_may_wakeup(struct device *dev)   { return dev->power.can_wakeup && !!dev->power.wakeup; }

can_wakeup 是硬件能力，may_wakeup 是「有 wakeup_source 挂着」。层次不同，后者为真只说明唤醒源注册了，不代表它现在能让系统睡不着。

概念 载体 变化时机 递减吗
ws->active 每个源一位 wakeup_source_activate / deactivate 会，来回切
ws->event_count 每个源一个 每次 wakeup_source_report_event 不会
in-progress 全局计数低半部分 activate 加 1，deactivate 减 1 会
registered 全局计数高半部分 deactivate 时加 1 不会

pm_wakeup_pending() 判两件事之一：cnt != saved_count（有事件处理完）或 inpr > 0（有事件在处理）。逐源的 active 与全局的 in-progress 是求和关系：in-progress 大于零时，必然存在某个 active 为真的源，所以 print_active_wakeup_sources() 能列出正在拖住系统的嫌疑人。（以上关系来自代码推导，未在运行时验证。）

十六、wakeup events 的统计与上报 #

所有统计都从两个计数器来，它们被合并进一个 atomic_t：

c
/*
 * Combined counters of registered wakeup events and wakeup events in progress.
 * They need to be modified together atomically, so it's better to use one
 * atomic variable to hold them both.
 */
static atomic_t combined_event_count = ATOMIC_INIT(0);

#define IN_PROGRESS_BITS        (sizeof(int) * 4)
#define MAX_IN_PROGRESS         ((1 << IN_PROGRESS_BITS) - 1)

static void split_counters(unsigned int *cnt, unsigned int *inpr)
{
        unsigned int comb = atomic_read(&combined_event_count);

        *cnt = (comb >> IN_PROGRESS_BITS);
        *inpr = comb & MAX_IN_PROGRESS;
}

IN_PROGRESS_BITS 是 sizeof(int) * 4，32 位机上等于 16：低 16 位记 in-progress，高 16 位记 registered。两个方向的更新：

c
cec = atomic_inc_return(&combined_event_count);                   /* in-progress +1 */
cec = atomic_add_return(MAX_IN_PROGRESS, &combined_event_count);  /* in-progress -1，registered +1 */

第二句是这套设计里最值得看的一行。MAX_IN_PROGRESS 是 0xFFFF，往低 16 位加它等价于减 1，同时进位溢出到高 16 位，正好是 registered 加 1。一次 atomic_add_return 完成「一个事件处理完了」，不需要锁，也不需要两次原子操作之间的窗口。分成两个变量的话，inpr-- 和 cnt++ 之间就有窗口，另一个 CPU 读到「in-progress 已 0、registered 还没加」，pm_wakeup_pending() 就误判成「没有新事件」，把系统放睡。

驱动侧的上报接口分两层：

c
/* 直接操作 wakeup_source，驱动里一般不用 */
extern void __pm_stay_awake(struct wakeup_source *ws);
extern void __pm_relax(struct wakeup_source *ws);
extern void __pm_wakeup_event(struct wakeup_source *ws, unsigned int msec);

/* 操作 device，驱动常用 */
extern int  device_wakeup_enable(struct device *dev);
extern int  device_wakeup_disable(struct device *dev);
extern void device_set_wakeup_capable(struct device *dev, bool capable);
extern int  device_init_wakeup(struct device *dev, bool val);
extern int  device_set_wakeup_enable(struct device *dev, bool enable);
extern void pm_stay_awake(struct device *dev);
extern void pm_relax(struct device *dev);
extern void pm_wakeup_event(struct device *dev, unsigned int msec);

三个上层接口都只是加锁转发：

c
void pm_stay_awake(struct device *dev)
{
        unsigned long flags;

        if (!dev)
                return;

        spin_lock_irqsave(&dev->power.lock, flags);
        __pm_stay_awake(dev->power.wakeup);
        spin_unlock_irqrestore(&dev->power.lock, flags);
}

void __pm_stay_awake(struct wakeup_source *ws)
{
        unsigned long flags;

        if (!ws)
                return;

        spin_lock_irqsave(&ws->lock, flags);

        wakeup_source_report_event(ws);
        del_timer(&ws->timer);
        ws->timer_expires = 0;

        spin_unlock_irqrestore(&ws->lock, flags);
}

static void wakeup_source_report_event(struct wakeup_source *ws)
{
        ws->event_count++;
        /* This is racy, but the counter is approximate anyway. */
        if (events_check_enabled)
                ws->wakeup_count++;

        if (!ws->active)
                wakeup_source_activate(ws);
}

__pm_stay_awake() 把 timer 删掉，因为它要求调用者手动 relax，自动超时不该兜底。__pm_wakeup_event() 相反：上报后挂 timer，到期由定时器回调替你 relax，expire_count 加一。wakeup_source_report_event() 里那行注释诚实得可爱——This is racy, but the counter is approximate anyway. ws->wakeup_count 的加一和 events_check_enabled 的判断之间有竞态，但这个计数只用来指认嫌疑人，允许近似。

__pm_relax()：

c
void __pm_relax(struct wakeup_source *ws)
{
        unsigned long flags;

        if (!ws)
                return;

        spin_lock_irqsave(&ws->lock, flags);
        if (ws->active)
                wakeup_source_deactivate(ws);
        spin_unlock_irqrestore(&ws->lock, flags);
}

if (ws->active) 这层门让非 active 的 relax 连 wakeup_source_deactivate() 都不进，不会污染 relax_count。第十四章那个 relax_count != active_count 判据处理的是另一类情况：定时器与直接调用撞车，且期间有新的 activate。

三类事件的典型时序：

text
场景 A：可确定处理时长
  irq → pm_wakeup_event(dev, 500) → in-progress+1, timer 挂 500ms
      → 500ms 到 → timer 回调 → __pm_relax → in-progress-1, registered+1

场景 B：处理时长不定，手动配对
  irq → pm_stay_awake(dev) → in-progress+1
      → 在 threaded irq / work 里处理完
      → pm_relax(dev) → in-progress-1, registered+1

场景 C：驱动漏了 pm_relax
  irq → pm_stay_awake(dev) → in-progress 永远 > 0
      → 系统再也挂不起来，wakeup_count 也不再增长

场景 C 是最常见的一类现场故障。/sys/kernel/debug/wakeup_sources（要 CONFIG_PM_SLEEP_DEBUG）里 active_count 和 relax_count 不等的那一行就是它。

device/.../power/wakeup_count 和 /sys/power/wakeup_count 是两个不同的东西：前者是单设备的 event_count，后者是全局 registered events。

最后是 sysfs 增删的根：

c
void device_set_wakeup_capable(struct device *dev, bool capable)
{
        if (!!dev->power.can_wakeup == !!capable)
                return;

        if (device_is_registered(dev) && !list_empty(&dev->power.entry)) {
                if (capable) {
                        if (wakeup_sysfs_add(dev))
                                return;
                } else {
                        wakeup_sysfs_remove(dev);
                }
        }
        dev->power.can_wakeup = capable;
}

那两个 !! 是把参数压成 0/1 再比较，避免「传 2 当成 true 但和已有的 1 不相等」。返回值是 void，wakeup_sysfs_add 失败直接 return，can_wakeup 保持原值——静默失败的口子，驱动只能事后读 device_can_wakeup() 确认。

十七、wakeup_count：防止挂起过程中的竞态 #

先把竞态说清楚，这是整篇最值得逐字读的部分。

用户态想挂起，流程是「读 count → 写 state」。天真实现如下：

text
t0  用户态: 读 /sys/power/wakeup_count 得到 N
t1  用户态: 做自己的准备（关屏、保存状态、通知 app）
t2  内核:   按键中断到达，wakeup_source_report_event，in-progress+1
t3  内核:   驱动处理完，__pm_relax，in-progress-1，registered+1
            → 全局 count 从 N 变成 N+1
t4  用户态: 写 /sys/power/state = "mem"

t2 到 t3 之间，事件产生并且处理完了。等到 t4 真正开始挂起，in-progress 已经回到 0，registered 是 N+1。只检查 in-progress 的实现会看到 0，放行，系统睡过去。

问题不在「事件丢了」——它在 t3 已经处理完。问题在用户态还没机会处理这个事件的结果：按键要给输入系统，输入系统冻着；电源键服务要知道「有人按了键、这次别睡」，它冻着。用户按下键、看到黑屏，再等两秒机器才醒。

正确做法是给「读 count」和「写 state」之间建立原子关联。wakeup_count 的写操作就是这道关卡：

text
t0  用户态: 读 /sys/power/wakeup_count 得到 N
t1  用户态: 做自己的准备
t2  用户态: 写 /sys/power/wakeup_count = N
           内核: 比较当前 cnt 与 N
           相等且 inpr == 0 → saved_count = N, events_check_enabled = true, 成功
           不等或 inpr != 0 → 失败
t3  失败 → 回 t0 重来；成功 → 写 /sys/power/state = "mem"

关键在于 t2 的写不是把 N 塞进某个变量，而是「用 N 校验当前系统状态」。校验通过才记下 saved_count = N 并打开 events_check_enabled。t1 期间来了事件（哪怕处理完了），cnt 变成 N+1，校验失败，用户态重来。竞态窗口从「读和写之间」压缩到「写成功和关中断之间」，后者由 suspend_enter() 里的 pm_wakeup_pending() 守住。内核注释的原话：

text
If that fails, at least one wakeup event has occurred since
'wakeup_count' was read and 'state' should not be written to.  Otherwise, it
is allowed to write to 'state', but the transition will be aborted if there
are any wakeup events detected after 'wakeup_count' was written to.

写操作会等待、会失败，这是设计意图。 用户态必须写成循环：

c
do {
    ret = read(&cnt, "/sys/power/wakeup_count");
    if (ret) {
        ret = write(cnt, "/sys/power/wakeup_count");
    } else {
        continue;
    }
} while (!ret);
write("mem", "/sys/power/state");
/* goto here after wakeup */

读失败（-EINTR）继续读，写失败继续读写。成功了才能写 state：

bash
while true; do
    cnt=$(cat /sys/power/wakeup_count) || continue
    if echo "$cnt" > /sys/power/wakeup_count; then break; fi
done
echo mem > /sys/power/state

还有一点常被忽略：不碰 wakeup_count，pm_wakeup_pending() 完全不干活。它第一句就是 if (events_check_enabled)，没开直接 ret = false。只写 /sys/power/state 的话，框架退化到只剩 in-progress 检查，而它在「事件已处理完」这个场景下是瞎的。

十八、wakeup_count 的读写语义 #

两个 sysfs 接口都在 kernel/power/main.c：

c
static ssize_t wakeup_count_show(struct kobject *kobj,
                                 struct kobj_attribute *attr,
                                 char *buf)
{
        unsigned int val;
        return pm_get_wakeup_count(&val, true) ?
                sprintf(buf, "%u\n", val) : -EINTR;
}

static ssize_t wakeup_count_store(struct kobject *kobj,
                                  struct kobj_attribute *attr,
                                  const char *buf, size_t n)
{
        unsigned int val;
        int error;

        error = pm_autosleep_lock();
        if (error)
                return error;

        if (pm_autosleep_state() > PM_SUSPEND_ON) {
                error = -EBUSY;
                goto out;
        }

        error = -EINVAL;
        if (sscanf(buf, "%u", &val) == 1) {
                if (pm_save_wakeup_count(val))
                        error = n;
        }

 out:
        pm_autosleep_unlock();
        return error;
}

show 的第二个参数传 true，即阻塞。store 先拿 pm_autosleep_lock()，autosleep 开着就 -EBUSY。和 state_store 里那两行一模一样——用手动 wakeup_count 的方式挂起，和 autosleep 互斥。原因在第二十章。

pm_get_wakeup_count() 在 drivers/base/power/wakeup.c：

c
bool pm_get_wakeup_count(unsigned int *count, bool block)
{
        unsigned int cnt, inpr;

        if (block) {
                DEFINE_WAIT(wait);

                for (;;) {
                        prepare_to_wait(&wakeup_count_wait_queue, &wait,
                                        TASK_INTERRUPTIBLE);
                        split_counters(&cnt, &inpr);
                        if (inpr == 0 || signal_pending(current))
                                break;
                        schedule();
                }
                finish_wait(&wakeup_count_wait_queue, &wait);
        }

        split_counters(&cnt, &inpr);
        *count = cnt;
        return !inpr;
}

block == true 时的行为：

  • 进 TASK_INTERRUPTIBLE 等待队列 wakeup_count_wait_queue。
  • 循环里检查 inpr == 0 或 signal_pending()。前者是目标状态，后者是给 -EINTR 留的出口（show 把它变成返回值）。
  • 两者都不满足就 schedule() 让别人跑。

block == false 时直接读一次，返回 !inpr。这样调用者能区分「读到了且当前干净」和「读到了但有事件在处理」。

唤醒这个等待队列的地方，第十四章那段代码末尾：

c
        split_counters(&cnt, &inpr);
        if (!inpr && waitqueue_active(&wakeup_count_wait_queue))
                wake_up(&wakeup_count_wait_queue);

每次 deactivate 之后，如果 in-progress 归零且有人在等，就唤醒。这是唯一的唤醒点，很干净。

pm_save_wakeup_count()：

c
bool pm_save_wakeup_count(unsigned int count)
{
        unsigned int cnt, inpr;
        unsigned long flags;

        events_check_enabled = false;
        spin_lock_irqsave(&events_lock, flags);
        split_counters(&cnt, &inpr);
        if (cnt == count && inpr == 0) {
                saved_count = count;
                events_check_enabled = true;
        }
        spin_unlock_irqrestore(&events_lock, flags);
        return events_check_enabled;
}

四步：

  1. 先把 events_check_enabled 清成 false。这是无条件的，且发生在加锁之前——意味着上一次挂起遗留的启用状态被彻底作废。
  2. split_counters() 读当前两个值。
  3. cnt == count && inpr == 0 才认账：写入的 N 和当前 registered 一致（说明读之后没有事件处理完），且没有事件正在处理。
  4. 认账时 saved_count = count 并存住，events_check_enabled = true。

返回值就是 events_check_enabled 的最终值，true 表示可以写 state 了。

pm_wakeup_pending() 和这两个接口的收尾关系：

c
bool pm_wakeup_pending(void)
{
        unsigned long flags;
        bool ret = false;

        spin_lock_irqsave(&events_lock, flags);
        if (events_check_enabled) {
                unsigned int cnt, inpr;

                split_counters(&cnt, &inpr);
                ret = (cnt != saved_count || inpr > 0);
                events_check_enabled = !ret;
        }
        spin_unlock_irqrestore(&events_lock, flags);

        if (ret)
                print_active_wakeup_sources();

        return ret;
}

留意 events_check_enabled = !ret 这行。返回 true（要中止）时把它清掉，返回 false（可以睡）时保持置位。所以 pm_wakeup_pending() 被连续调用多次时，只有第一次判定作数，之后 saved_count 已作废。

另外 suspend_enter() 里 suspend_ops->enter(state) 成功返回之后还有一句 events_check_enabled = false，那是「真睡过一次了，这次会话结束」的收尾。

三者的语义，一张表：

sysfs 操作 内核函数 关键行为 返回
读 /sys/power/wakeup_count pm_get_wakeup_count(&v, true) 阻塞等 in-progress 归零；有信号则退出 成功给 N，否则 -EINTR
写 /sys/power/wakeup_count = N pm_save_wakeup_count(N) 校验 cnt == N && inpr == 0，通过则 saved_count = N、置 events_check_enabled 成功给 n，失败 -EINVAL；autosleep 开着给 -EBUSY
写 /sys/power/state = mem pm_suspend(PM_SUSPEND_MEM) 走到 suspend_enter 深处调 pm_wakeup_pending() 成功给 n（包括被 wakeup 中止），失败给错误码

把这三次写操作的时序和 events_check_enabled 的状态串起来：

text
saved_count = 0, events_check_enabled = false

读 count            → N          （阻塞到 inpr==0）
写 count = N        → 成功        （cnt==N && inpr==0）
                    → saved_count = N, events_check_enabled = true
写 state = "mem"
  → suspend_prepare → 冻结进程
  → dpm_suspend_start
  → suspend_enter
      → dpm_suspend_end
      → disable_nonboot_cpus
      → arch_suspend_disable_irqs
      → syscore_suspend
      → pm_wakeup_pending()
          events_check_enabled == true → 比较 cnt 与 saved_count(N)
            相同且 inpr==0 → false，保持 enabled，继续 enter
            不同或 inpr>0  → true，清 enabled，跳过 enter，中止
      → syscore_resume ...
  → suspend_ops->enter() 正常返回后 events_check_enabled = false

情况二和情况三是两道闸，缺一个都不行。只有情况二，事件落在写完之后就漏了；只有情况三，事件落在读完到写之间就漏了。wakeup_count + pm_wakeup_pending() 是一对，不是两个独立功能。 注意中间「冻结进程」那一段没有 pm_wakeup_pending() 调用。suspend_prepare 里只有 suspend_test(TEST_FREEZER)，不是 wakeup 检查。冻结期间产生的事件要等到 suspend_enter 深处的检查点才被发现——这正是它必须存在的原因。

版本变化：wakeup_count 在 3.x 就已经是这个形态。4.x 之后 pm_save_wakeup_count 的接口签名和 events_check_enabled 的清理路径有过调整，pm_get_wakeup_count 的阻塞逻辑也改过（后期版本里加入了 wakeup_count_wait_queue 之外的额外检查）。具体改动点本篇未逐一验证。

十九、autosleep：没人用时自动挂起 #

autosleep 从 Android wakelocks 补丁集演化而来，用来取代 wakelocks 自带的自动休眠。它基于 wakeup source 实现，代码很短，但背后那个问题一直没答案：挂起应该由谁在什么时候触发。

PC 时代答案很直接，用户不想用了就合盖。移动设备不行，用户随手就拿起来。Android 的答案是 Opportunistic suspend——逮到机会就睡。检测到系统没事情做，就把整机挂起。判断依据只有一个：有没有正在处理或新产生的 wakeup event。

这套思路的代价也直白：判断不准，会在 suspend→resume→suspend 之间空转，一个设备在干活、其它设备陪着耗电。「没事情做」这个前提本身就模糊。

实现位于 kernel/power/autosleep.c，用户态入口 /sys/power/autosleep：

c
static ssize_t autosleep_show(struct kobject *kobj,
                              struct kobj_attribute *attr,
                              char *buf)
{
        suspend_state_t state = pm_autosleep_state();

        if (state == PM_SUSPEND_ON)
                return sprintf(buf, "off\n");

#ifdef CONFIG_SUSPEND
        if (state < PM_SUSPEND_MAX)
                return sprintf(buf, "%s\n", valid_state(state) ?
                                                pm_states[state] : "error");
#endif
#ifdef CONFIG_HIBERNATION
        return sprintf(buf, "disk\n");
#else
        return sprintf(buf, "error");
#endif
}

static ssize_t autosleep_store(struct kobject *kobj,
                               struct kobj_attribute *attr,
                               const char *buf, size_t n)
{
        suspend_state_t state = decode_state(buf, n);
        int error;

        if (state == PM_SUSPEND_ON
            && strcmp(buf, "off") && strcmp(buf, "off\n"))
                return -EINVAL;

        error = pm_autosleep_set_state(state);
        return error ? error : n;
}

power_attr(autosleep);

读返回六种字符串之一：freeze / standby / mem / disk / off / error。写接受五种：freeze / standby / mem / disk / off。off 的校验很别扭，decode_state 把 off 解成 PM_SUSPEND_ON，所以还要额外 strcmp 确认用户真的写了 off 而不是别的什么解出 0 的字符串。

初始化在 pm_autosleep_init()，pm_init() 里调用：

c
int __init pm_autosleep_init(void)
{
        autosleep_ws = wakeup_source_register("autosleep");
        if (!autosleep_ws)
                return -ENOMEM;

        autosleep_wq = alloc_ordered_workqueue("autosleep", 0);
        if (autosleep_wq)
                return 0;

        wakeup_source_unregister(autosleep_ws);
        return -ENOMEM;
}

两个全局对象：一个叫 autosleep 的 wakeup source（autosleep_ws），在执行关键操作时阻止休眠；一个叫 autosleep 的有序 workqueue。有序两个字是关键，第二十章讲。

状态切换：

c
int pm_autosleep_set_state(suspend_state_t state)
{

#ifndef CONFIG_HIBERNATION
        if (state >= PM_SUSPEND_MAX)
                return -EINVAL;
#endif

        __pm_stay_awake(autosleep_ws);

        mutex_lock(&autosleep_lock);

        autosleep_state = state;

        __pm_relax(autosleep_ws);

        if (state > PM_SUSPEND_ON) {
                pm_wakep_autosleep_enabled(true);
                queue_up_suspend_work();
        } else {
                pm_wakep_autosleep_enabled(false);
        }

        mutex_unlock(&autosleep_lock);
        return 0;
}

注意 __pm_stay_awake / __pm_relax 夹着 mutex_lock。这两个口子把 autosleep_ws 当一个 lock 用——此刻它的语义不是「有事件」，而是「我在改状态，别睡」。Android wakelocks 的影子在这里很清楚。

pm_wakep_autosleep_enabled() 遍历所有 wakeup source 改 autosleep_enabled 标志：

c
void pm_wakep_autosleep_enabled(bool set)
{
        struct wakeup_source *ws;
        ktime_t now = ktime_get();

        rcu_read_lock();
        list_for_each_entry_rcu(ws, &wakeup_sources, entry) {
                spin_lock_irq(&ws->lock);
                if (ws->autosleep_enabled != set) {
                        ws->autosleep_enabled = set;
                        if (ws->active) {
                                if (set)
                                        ws->start_prevent_time = now;
                                else
                                        update_prevent_sleep_time(ws, now);
                        }
                }
                spin_unlock_irq(&ws->lock);
        }
        rcu_read_unlock();
}

逐个源改标志，active 的源要顺手维护 start_prevent_time / prevent_sleep_time。全局遍历 + 每个源各存一份相同状态，代价不小；换成 4.x 之后的实现会好一些，改动点未验证。

queue_up_suspend_work() 是 queue_work(autosleep_wq, &suspend_work) 加一个 autosleep_state > PM_SUSPEND_ON 的判断，work 的处理函数是 try_to_suspend。

二十、autosleep 与 wakeup_count 的配合 #

try_to_suspend 是第十七章那套「读写 count 再挂起」的生产版：

c
static void try_to_suspend(struct work_struct *work)
{
        unsigned int initial_count, final_count;

        if (!pm_get_wakeup_count(&initial_count, true))
                goto out;

        mutex_lock(&autosleep_lock);

        if (!pm_save_wakeup_count(initial_count) ||
                system_state != SYSTEM_RUNNING) {
                mutex_unlock(&autosleep_lock);
                goto out;
        }

        if (autosleep_state == PM_SUSPEND_ON) {
                mutex_unlock(&autosleep_lock);
                return;
        }
        if (autosleep_state >= PM_SUSPEND_MAX)
                hibernate();
        else
                pm_suspend(autosleep_state);

        mutex_unlock(&autosleep_lock);

        if (!pm_get_wakeup_count(&final_count, false))
                goto out;

        /*
         * If the wakeup occured for an unknown reason, wait to prevent the
         * system from trying to suspend and waking up in a tight loop.
         */
        if (final_count == initial_count)
                schedule_timeout_uninterruptible(HZ / 2);

 out:
        queue_up_suspend_work();
}

阻塞式读 count → 拿锁 → 校验写入 → 挂起 → 非阻塞读一次 final_count → 重新排队。三个细节：autosleep_state == PM_SUSPEND_ON（用户在等锁期间关掉了 autosleep）时直接 return，不走 out，不重新排队；system_state != SYSTEM_RUNNING 也退出，关机流程中不该再挂起；final_count == initial_count 说明「没产生任何事件却醒了」，硬等 HZ / 2 防止 sleep→wakeup→sleep 空转把电耗光。

最后那句 queue_up_suspend_work() 和有序 workqueue 的配合最省事。pm_autosleep_set_state 不做状态去重，用户连写三次 mem 就往队列里扔三个 work。多核上普通 workqueue 会让它们并行，同时发起三次挂起——pm_mutex 的 trylock 挡掉后两个，它们各自重排，形成空转。有序 workqueue 保证同一时刻只有一个 work 在跑。内核用队列语义兜底，不在 set_state 里做判断。

和手动挂起的关系，回看第三章 state_store 开头那两行 pm_autosleep_lock() + pm_autosleep_state() > PM_SUSPEND_ON 的 -EBUSY。wakeup_count_store 里也是同样两行。

发起方 入口 与 autosleep 互斥 用 wakeup_count
用户态手动 /sys/power/state 是，-EBUSY 可选
用户态手动 wakeup_count + state 是，-EBUSY 是，两道闸齐全
autosleep /sys/power/autosleep — 是，内部强制

autosleep 内部强制用 wakeup_count，不是可选项。它挂起太频繁，没有同步机制会立刻出问题。

一个容易忘的点：try_to_suspend 在 pm_suspend() 之前持着 autosleep_lock，而 state_store 也要先拿这把锁。所以 autosleep 正在挂起时，想写 state 的进程卡在 pm_autosleep_lock() 上是阻塞，不是 -EBUSY。只有 autosleep 已开启但当前没在挂起，才轮得到那条 -EBUSY。

二十一、wakelocks：Android 的历史包袱 #

wakelocks 有两套，别混。

旧的 Android wakelocks 是 Android 给 Linux kernel 打的一整个补丁集，含一个 wakelocks 系统调用，允许调用者阻止系统进低功耗状态，还直接改写了 kernel/power/main.c 的 state_show / state_store。这种改法从来没被主线接受，源码在 drivers/android/power.c（旧内核路径）。它提供四样东西：/sys/power/wake_lock（写一个字符串创建 wakelock）、/sys/power/wake_unlock（写同一个字符串注销）、「所有 wakelock 都注销后系统可自动进低功耗」、以及给驱动的创建/注销接口。

新的 kernel wakelocks 在 kernel/power/wakelock.c，等 wakeup events framework 成熟之后才有，做法是复用 wakeup_source：

Android wakelocks 的诉求 kernel 的替代
驱动创建/注销 wakelock wakeup_source 本身，用 pm_stay_awake / pm_relax
全部注销后自动休眠 autosleep
/sys/power/wake_lock / wake_unlock kernel/power/wakelock.c，把 wakeup source 开到用户态

语义已经完全不是一回事。Android 的 wakelock 是锁：suspend 路径上有若干把锁，全解开才能睡。kernel 的 wakelock 是一次 wakeup event：写 wake_lock 等于 __pm_stay_awake，写 wake_unlock 等于 __pm_relax。

读 wake_lock 拿到当前所有 active 的 wakelock 名字，读 wake_unlock 拿到所有非 active 的。写 wake_lock 时格式是 名字 [timeout_ns]。

二十二、wakelocks 与 wakeup_source 的关系 #

核心结构：

c
struct wakelock {
        char *name;
        struct rb_node          node;
        struct wakeup_source    ws;
#ifdef CONFIG_PM_WAKELOCKS_GC
        struct list_head        lru;
#endif
};

四样：名字、红黑树节点、一个内嵌的 wakeup_source、GC 用的链表节点。内嵌是关键——ws 是 struct wakelock 的一部分，初始化走 wakeup_source_prepare() + wakeup_source_add()，不走 wakeup_source_register()。

pm_wake_lock()：

c
int pm_wake_lock(const char *buf)
{
        const char *str = buf;
        struct wakelock *wl;
        u64 timeout_ns = 0;
        size_t len;
        int ret = 0;

        if (!capable(CAP_BLOCK_SUSPEND))
                return -EPERM;

        while (*str && !isspace(*str))
                str++;

        len = str - buf;
        if (!len)
                return -EINVAL;

        if (*str && *str != '\n') {
                /* Find out if there's a valid timeout string appended. */
                ret = kstrtou64(skip_spaces(str), 10, &timeout_ns);
                if (ret)
                        return -EINVAL;
        }

        mutex_lock(&wakelocks_lock);

        wl = wakelock_lookup_add(buf, len, true);
        if (IS_ERR(wl)) {
                ret = PTR_ERR(wl);
                goto out;
        }
        if (timeout_ns) {
                u64 timeout_ms = timeout_ns + NSEC_PER_MSEC - 1;

                do_div(timeout_ms, NSEC_PER_MSEC);
                __pm_wakeup_event(&wl->ws, timeout_ms);
        } else {
                __pm_stay_awake(&wl->ws);
        }

        wakelocks_lru_most_recent(wl);
 out:
        mutex_unlock(&wakelocks_lock);
        return ret;
}

capable(CAP_BLOCK_SUSPEND) 是第一道关。电源是系统资源，把「能不能睡」的决定权交给用户态有风险，权限系统只能把矛盾转移到用户身上。带 timeout 走 __pm_wakeup_event()，不带走 __pm_stay_awake()。单位换算 (ns + NSEC_PER_MSEC - 1) / NSEC_PER_MSEC 向上取整，1ns 不会变成 0。

wakelock_lookup_add() 维护红黑树 wakelocks_tree：

c
static struct wakelock *wakelock_lookup_add(const char *name, size_t len,
                                            bool add_if_not_found)
{
        struct rb_node **node = &wakelocks_tree.rb_node;
        struct rb_node *parent = *node;
        struct wakelock *wl;

        while (*node) {
                int diff;

                parent = *node;
                wl = rb_entry(*node, struct wakelock, node);
                diff = strncmp(name, wl->name, len);
                if (diff == 0) {
                        if (wl->name[len])
                                diff = -1;
                        else
                                return wl;
                }
                if (diff < 0)
                        node = &(*node)->rb_left;
                else
                        node = &(*node)->rb_right;
        }
        if (!add_if_not_found)
                return ERR_PTR(-EINVAL);

        if (wakelocks_limit_exceeded())
                return ERR_PTR(-ENOSPC);

        /* Not found, we have to add a new one. */
        wl = kzalloc(sizeof(*wl), GFP_KERNEL);
        if (!wl)
                return ERR_PTR(-ENOMEM);

        wl->name = kstrndup(name, len, GFP_KERNEL);
        if (!wl->name) {
                kfree(wl);
                return ERR_PTR(-ENOMEM);
        }
        wl->ws.name = wl->name;
        wakeup_source_add(&wl->ws);
        rb_link_node(&wl->node, parent, node);
        rb_insert_color(&wl->node, &wakelocks_tree);
        wakelocks_lru_add(wl);
        increment_wakelocks_number();
        return wl;
}

wl->name[len] 那个判断处理前缀：用户写 my_wake，树里有 my_wakeup，strncmp(name, wl->name, len) 返回 0，得靠 wl->name[len] 非零判成「不等」。红黑树都用上了，说明 wakelocks 当年被用得有多频繁。

pm_wake_unlock() 走同一条查表路径，add_if_not_found 为 false：找不到就 -EINVAL，不会创建空 wakelock 再 relax。pm_show_wakelocks() 中序遍历红黑树，按 wl->ws.active == show_active 过滤，拼成空格分隔的名字串。

GC 是一笔折中账。wakelock 理论上只该活在 active 期间，deactive 就该销毁；但销毁后同名再写又要重建，来回切就亏了。全留下来又占内存。方案是留一部分，超时再收：

c
static void wakelocks_gc(void)
{
        struct wakelock *wl, *aux;
        ktime_t now;

        if (++wakelocks_gc_count <= WL_GC_COUNT_MAX)
                return;

        now = ktime_get();
        list_for_each_entry_safe_reverse(wl, aux, &wakelocks_lru_list, lru) {
                u64 idle_time_ns;
                bool active;

                spin_lock_irq(&wl->ws.lock);
                idle_time_ns = ktime_to_ns(ktime_sub(now, wl->ws.last_time));
                active = wl->ws.active;
                spin_unlock_irq(&wl->ws.lock);

                if (idle_time_ns < ((u64)WL_GC_TIME_SEC * NSEC_PER_SEC))
                        break;

                if (!active) {
                        wakeup_source_remove(&wl->ws);
                        rb_erase(&wl->node, &wakelocks_tree);
                        list_del(&wl->lru);
                        kfree(wl->name);
                        kfree(wl);
                        decrement_wakelocks_number();
                }
        }
        wakelocks_gc_count = 0;
}

每调一次 pm_wake_unlock 就调一次 wakelocks_gc()，但累计计数超过 WL_GC_COUNT_MAX（代码里 100，版本未验证）才真扫。倒序遍历 LRU，idle 时间 >= WL_GC_TIME_SEC（代码里 300 秒）且非 active 的才回收；遇到第一个 idle 不够的就 break，因为链表有序。CONFIG_PM_WAKELOCKS_GC 关掉时 struct wakelock 连 lru 字段都没有，所有 wakelock 永久保留。

二十三、/sys/power/wake_lock 与 wake_unlock #

实践里只需记住四条语义：

text
echo "my_lock" > /sys/power/wake_lock               # 创建，永不自动释放
echo "my_lock 1000000000" > /sys/power/wake_lock    # 创建，1 秒后自动释放（单位纳秒）
echo "my_lock" > /sys/power/wake_unlock             # 释放
cat /sys/power/wake_lock                           # 谁在阻止睡眠

active_wake_locks 是这套机制在水面上的可观察面：读 wake_lock 拿到所有 active 的名字，读 wake_unlock 拿到所有非 active 的名字。写 wake_unlock 一个从未 wake_lock 过的名字，返回 -EINVAL。

几个边界：

  • 需要 CONFIG_PM_WAKELOCKS。没这个宏两个文件都不存在，echo 报 No such file or directory。
  • 需要 CAP_BLOCK_SUSPEND。普通用户写不进去，返回 -EPERM。
  • 和 state 不冲突。wakelock 不阻止你写 state，它阻止系统真的睡下去——pm_wakeup_pending() 在 suspend_enter() 深处看到 in-progress 不为零就中止。现象是挂起「返回成功但立刻醒了」。
  • autosleep 才是主场景。手动挂起时 wakelock 也生效，但没有 autosleep，系统本来就要等你敲命令才睡。
  • 名字敏感，持有者不敏感。 没有「持有者」概念，一个进程创建的 wakelock，另一个进程写同一个名字就能解掉。这是这套机制最脆弱的地方——Android 在框架层用引用计数绕开了这个坑，kernel/power/wakelock.c 没做。

版本变化：/sys/power/wake_lock 与 /sys/power/wake_unlock 在 4.x 中期被移除过一段时间（Android 迁移到 wakeup_sources 框架后没有使用者），后来以 CONFIG_PM_WAKELOCKS + 新实现的形式回来，路径和写入格式有变化，比如是否还支持读 wake_unlock。具体版本节点未验证，用之前先确认目标内核里这两个文件在不在。

二十四、整条链路的三个关键窗口 #

前面二十多章讲的全是「顺序」。这一节只回答一个问题：事件从哪个缝里钻进去，谁把它挡住。整条链路上只有三个窗口。

窗口 区间 谁负责挡 挡不住会怎样
W1 用户态读完 wakeup_count 到写回它之前 pm_save_wakeup_count() 里的 cnt == count && inpr == 0 事件处理完了但用户态还没决定要不要睡，系统照睡
W2 写回成功到 arch_suspend_disable_irqs() suspend_enter() 深处的 pm_wakeup_pending() 事件落在内核里没处理完，被关中断闷住
W3 关中断到 suspend_ops->enter() 之间 关中断本身，加上最后一个 pm_wakeup_pending() 窗口极小，靠「关中断期间没有新中断」这个事实

W1 由 wakeup_count 负责，W2 由 pm_wakeup_pending() 负责，W3 靠硬件语义。三者串起来才是一条完整的同步链：

text
读 count → 写 count → 写 state → 冻结 → dpm_suspend → 关中断 → enter
   ↑W1 校验     ↑W2 校验                        ↑W3

W1 拦不住时，用户态拿到写失败，回读 count 重来。W2 拦不住时，*wakeup 置真，suspend_ops->enter() 被跳过，可 pm_suspend() 照样返回 0。两个窗口在用户态看来完全不同：一个是 write() 返回 -EINVAL，一个是 write() 返回 n 却没睡。

这也是为什么现场看到「写 state 成功但机器没睡」时，别急着翻设备驱动——先确认 W1 那道闸有没有真打开，也就是 events_check_enabled 是不是曾经被置位过。

再补几条不在表里的：

trylock 不是 lock。 enter_state 用 mutex_trylock(&pm_mutex)，第二个挂起请求立刻 -EBUSY，不排队。看到「偶发 -EBUSY」不是 bug，是两个进程抢着挂起。

wakeup 指针和返回值是两条通道。 suspend_enter() 用返回值报错、用 *wakeup 报「被事件中止」，suspend_devices_and_enter() 的 do/while 用 !error && !wakeup 决定 suspend_again()。所以「被唤醒打断」在错误码上不可见。

events_check_enabled 是全局开关。 它关着，pm_wakeup_pending() 完全不干活，整个 wakeup_count 同步机制退化成只检查 in-progress。不读 wakeup_count 直接写 state，就是这个状态。

device/.../power/wakeup_count 和 /sys/power/wakeup_count 不是一个东西。 前者是单设备的 event_count，后者是全局 registered events。名字撞了，别读错。

active_count 和 relax_count 不等就说明有驱动写错了。 前者大于后者是漏了 relax（系统会睡不着），后者大于前者是多调了 relax（被 relax_count != active_count 判据挡掉）。
