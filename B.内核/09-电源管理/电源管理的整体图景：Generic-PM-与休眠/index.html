一、电源管理要解决什么问题 #

任何计算系统的能量开销可以拆成三档：干活的开销、待命的开销、维持「活着」的开销。前两档是任务定的，第三档是架构定的，电源管理能动的主要是后两档。一颗 SoC 上能动的旋钮就这么几个：

  • 供电：哪些电源域（power domain）通电、哪几路 regulator 输出了多少电压。关掉一个域，域里的模块彻底不耗电，代价是重新上电要时间。
  • 时钟：哪些模块的时钟在跑、跑多快。门控省的是动态功耗，代价是恢复时要重新打开并等稳定。
  • 频率与电压：同一个模块跑 100MHz@0.9V 和 1GHz@1.2V，性能差十倍，功耗差远不止十倍（动态功耗正比于 C·V²·f）。这是 DVFS 的地盘。
  • 系统的整体状态：挂起（Suspend）、休眠（Hibernate）、关机（Power off）。这一档是「整个系统都不干了」，切换成本以秒计。

这里有两件事必须同时成立，缺一个电源管理就是失败的：

  1. 状态切换要省得回来。省下的能量必须大于切换本身的能量。为了省 1mW 付出 50ms 的退出延迟和一次 PLL 重锁，账是亏的。
  2. 恢复要够快，而且不能丢上下文。关掉的东西必须能被无损地打开，打开的速度要满足使用者的容忍度。做不到无损，就会出现「睡下去醒不来」或者「醒来设备全废」这两种经典事故。

从第一点能直接推出判据：功耗优化的单位是「驻留时间 × 省下的功率」，一个状态只在驻留够久时才值得进。这条判据在 cpuidle 的 governor 里被算成具体门限，在 Suspend 里被算成「你多久不用这台机器」。

二、三种省电思路：关机、睡眠、降耗 #

按「关掉什么」来分，思路只有三种。差别不在技术，在于你愿意付出多少恢复代价。

思路一：彻底关掉，需要时重建。 这是关机。重建成本极高：重新引导、重新初始化所有设备、重新拉起用户态，现场全没了。只适合「确实用完了」。

思路二：保留现场，关掉运算。 CPU 停、外设停，但内存继续供电，DRAM 里的东西一个字节没动。这是 Suspend to RAM。恢复时不用重建任何软件状态，把 CPU 拉出来、设备重新初始化即可，几百毫秒到几秒。代价是 DRAM 自刷新本身耗电，系统并没真断电。

思路三：保留现场，连内存也搬走。 把内存的全部内容写到断电不丢的介质上（swap 分区、Flash、磁盘），然后系统可以真断电。这就是 Hibernate，也就是 Suspend to Disk。恢复时把镜像读回来，覆盖内存，然后从当初挂起的位置继续跑。代价是几十 MB 到几 GB 的 I/O 时间、以及一份等于内存大小的存储空间。

除了这三种「整机级」的，还有第四类不属于 Generic PM 的做法：不改变整机状态，只把当前不用的部件关掉或降频。屏幕不亮时关背光、没有 USB 活动时挂起 USB 控制器、CPU 空闲时进 idle state、负载低时降频降压。这一类是 Runtime PM、cpuidle、cpufreq、Regulator、CCF 的地盘，特点是用户可以完全无感知，系统一直在「在线」，随时能响应事件。

这条线划出来就是 Generic PM 与 Runtime PM 的分界：

维度 Generic PM Runtime PM
触发者 用户态显式发起（写 sysfs、调 reboot） 内核自己判断（引用计数、空闲时长）
用户是否在线 不在线，系统不接受新事件 在线，随时响应
状态存放 内存或磁盘 不动，设备现场由驱动自己保
恢复时间量级 百毫秒 ~ 数十秒 微秒 ~ 毫秒
典型场景 笔记本合盖、嵌入式热关机 手机待机、USB 自动挂起

这条线也解释了为什么 Generic PM 在 PC 与服务器时代够用、在实时在线的移动设备上就不合时宜——那正是 Runtime PM 出现的原因。

对嵌入式还有一个用法值得记：很多产品用 Suspend 实现「热关机」，目的不是省电而是缩短下次开机时间。

三、Generic PM 的三种操作：Reboot、Suspend、Hibernate #

「Generic PM」不是内核里的正式术语，是对「传统整机级电源管理」的统称。它的桌面界面就是系统菜单里的三个选项，加上电源管理属性设置项。

三个操作选项是 Hibernate（休眠）、Restart（重启）、Shutdown（关机）。属性设置项则是「在 AC 供电 / 电池供电下，系统处于 Inactive 状态多少分钟后关闭显示器、多少分钟后进入 Sleep」。Auto Sleep 和 Auto put display to sleep 这两个属性的本质，是把「我不用了」这个判断自动化掉：机器在一段时间内没有输入事件，就认为 Inactive，然后替用户执行省电动作。

三种操作的对照：

操作 用户态入口 内核主路径 内存内容 恢复方式 恢复后现场
Shutdown poweroff / reboot(LINUX_REBOOT_CMD_POWER_OFF) kernel_power_off 丢失 冷启动 全部重建
Restart reboot / reboot(LINUX_REBOOT_CMD_RESTART) kernel_restart 丢失 冷启动 全部重建
Hibernate echo disk > /sys/power/state，或 reboot(LINUX_REBOOT_CMD_SW_SUSPEND) hibernate → swsusp_write → power_down 先写盘，后断电 引导时读回镜像 原样恢复
Suspend echo mem > /sys/power/state suspend_devices_and_enter 保持（DRAM 自刷新） 唤醒源中断 原样恢复

关键差别在第五列。Shutdown 和 Restart 之后，内核和用户态都是新的；Hibernate 和 Suspend 之后，内核还是那一个，用户态进程的 task_struct 还在原地，只是「暂停了一段时间」。所以对 Hibernate 而言，内核必须在恢复后能认出这是自己写的镜像，这就是后面第十一章要讲的 swsusp_info 头部和版本校验。

另一个容易混的点：Shutdown 和 Restart 在代码上是同一族，都走 reboot 系统调用，只是一个最终调 machine_power_off，一个调 machine_restart。

四、Generic PM 的软件层次 #

内核里这部分分三层。

API Layer：向用户空间提供接口。关机与重启的接口形式是系统调用（reboot(2)），Hibernate 和 Suspend 的接口形式是 sysfs（/sys/power/*），另有 debugfs 和字符设备 /dev/snapshot 作为辅助与测试通道。写 sysfs 这种「往文件里写字符串就切换整机状态」的做法看着奇怪，但它是 Generic PM 的标准形态，原因是切换动作需要复杂的参数（用哪个 state、哪种 hibernation mode），字符串比 ioctl 更好扩展。

PM Core：位于 kernel/power/，处理与硬件无关的核心逻辑。按子模块分：

  • 主功能（main.c），实现 /sys/power/state 等 global API 的分发；
  • STD（hibernate.c、snapshot.c、swap.c、block_io.c），实现 Suspend to Disk，与硬件无关的部分都在这；
  • STR 与 Standby（suspend.c、suspend_test.c），实现 Suspend to RAM。

PM Driver：分两半，一半是体系结构无关的驱动框架（drivers/base/power/），一半是体系结构相关的实现（arch/*/ 里的 machine_*、platform 的 hibernation_ops）。驱动工程师真正要写的代码都在这一层——设备的 ->suspend / ->resume / ->freeze / ->freeze_noirq / ->shutdown，以及 SoC 的 restart / poweroff 实现。

五、reboot 的完整流程 #

从用户敲 reboot 到机器真的复位，一共五步：

  1. 用户态命令。BusyBox 或 systemd 提供 reboot、halt、poweroff：poweroff 传 LINUX_REBOOT_CMD_POWER_OFF，reboot 传 RESTART，有的实现还会先 sync 并杀进程。
  2. 系统调用。用户态通过 reboot(2) 进内核，入口在 kernel/sys.c。它本身不 sync（源码注释：reboot doesn't sync: do that yourself before calling this.），所以 reboot -f 这种不经过 init 直接调系统调用的用法，丢数据风险由调用者承担。
  3. 内核分发。内核根据 cmd 选择 kernel_restart、kernel_halt 或 kernel_power_off。三个函数的骨架几乎一样。
  4. 关设备、关 syscore、收 CPU。发通知、关设备、关系统核心、把执行流收敛到单 CPU。
  5. machine 层收尾。machine_restart / machine_halt / machine_power_off，这里才是真正撬动硬件的地方。

三个 kernel_xxx 的对照（3.10 源码逐个核对过）：

步骤 kernel_restart(cmd) kernel_halt() kernel_power_off()
1. prepare kernel_restart_prepare(cmd) kernel_shutdown_prepare(SYSTEM_HALT) kernel_shutdown_prepare(SYSTEM_POWER_OFF)
2. 通知链事件 SYS_RESTART，带 cmd SYS_HALT SYS_POWER_OFF
3. system_state SYSTEM_RESTART SYSTEM_HALT SYSTEM_POWER_OFF
4. usermodehelper_disable() 有 有 有
5. device_shutdown() 有 有 有
6. pm_power_off_prepare() 无 无 有（如果注册了）
7. migrate_to_reboot_cpu() 有 有 有
8. syscore_shutdown() 有 有 有
9. 最后一条日志 Restarting system. System halted. Power down.
10. kmsg_dump KMSG_DUMP_RESTART KMSG_DUMP_HALT KMSG_DUMP_POWEROFF
11. machine 钩子 machine_restart(cmd) machine_halt() machine_power_off()

两处细节要注意。

第一，kernel_halt() 走完 machine_halt() 之后还会 panic("cannot halt")——正确的 machine_halt 不该返回。kernel_power_off() 里 machine_power_off() 后面跟的是 do_exit(0)，因为断电失败的后果比 halt 失败轻一些。

第二，pm_power_off_prepare 只有 power off 有，给板级代码一个「在真正断电前把某些器件切到安全状态」的机会，比如配好 PMIC 的关机时序。位置在 device_shutdown() 之后、syscore_shutdown() 之前。

device_shutdown() 是三条路径共用的重头戏，目标是「让每个设备都有机会体面地下电」。它遍历 devices_kset 的链表——也就是 /sys/devices/ 下所有设备——倒序处理：

c
void device_shutdown(void)
{
        struct device *dev;

        spin_lock(&devices_kset->list_lock);
        /* 从链表尾部开始，逐个关闭 */
        while (!list_empty(&devices_kset->list)) {
                dev = list_entry(devices_kset->list.prev, struct device,
                                kobj.entry);

                /* 拿住 parent 的引用计数，防止待会儿锁 parent 时它被释放 */
                get_device(dev->parent);
                get_device(dev);
                /* 先把设备摘出链表，防止 shutdown 回调自己不动手删 */
                list_del_init(&dev->kobj.entry);
                spin_unlock(&devices_kset->list_lock);

                /* 锁住 parent，避免与 probe/release 竞争 */
                if (dev->parent)
                        device_lock(dev->parent);
                device_lock(dev);

                /* 不允许再有 runtime suspend */
                pm_runtime_get_noresume(dev);
                pm_runtime_barrier(dev);

                if (dev->bus && dev->bus->shutdown) {
                        if (initcall_debug)
                                dev_info(dev, "shutdown\n");
                        dev->bus->shutdown(dev);
                } else if (dev->driver && dev->driver->shutdown) {
                        if (initcall_debug)
                                dev_info(dev, "shutdown\n");
                        dev->driver->shutdown(dev);
                }
                device_unlock(dev);
                if (dev->parent)
                        device_unlock(dev->parent);

                put_device(dev);
                put_device(dev->parent);

                spin_lock(&devices_kset->list_lock);
        }
        spin_unlock(&devices_kset->list_lock);
        async_synchronize_full();
}

读这段代码有四个要点：倒序（链表插入顺序大致「先注册的在前」，倒序遍历即「后注册的先关」，子设备与上层驱动先关、底层总线控制器后关；靠注册顺序而非设备树父子关系，算工程妥协）；bus 优先于 driver（if / else if，不是两个都调）；先 pm_runtime_get_noresume + pm_runtime_barrier（封死 runtime PM，否则出现「刚关掉又被唤醒」的循环）；async_synchronize_full() 放在最后（等所有异步 probe/初始化收敛）。

syscore_shutdown() 的结构与它神似：从链表里取 syscore 对象逐个调 ->shutdown。区别是它在中断基本关掉、单 CPU 的环境下执行，处理中断控制器、时钟控制器、定时器这类「系统核心」器件。细节留给专门讲 syscore 的篇目。

六、从用户态到 kernel_restart：reboot 系统调用的调用链 #

先看 cmd 的取值。它们是 include/uapi/linux/reboot.h 里的 #define，具体数字原文引用有错，按 3.10 源码为准：

c
/* include/uapi/linux/reboot.h, Linux 3.10 */
#define LINUX_REBOOT_CMD_RESTART        0x01234567
#define LINUX_REBOOT_CMD_HALT           0xCDEF0123
#define LINUX_REBOOT_CMD_CAD_ON         0x89ABCDEF
#define LINUX_REBOOT_CMD_CAD_OFF        0x00000000
#define LINUX_REBOOT_CMD_POWER_OFF      0x4321FEDC
#define LINUX_REBOOT_CMD_RESTART2       0xA1B2C3D4
#define LINUX_REBOOT_CMD_SW_SUSPEND     0xD000FCE2
#define LINUX_REBOOT_CMD_KEXEC          0x45584543

系统调用原型是 SYSCALL_DEFINE4(reboot, int, magic1, int, magic2, unsigned int, cmd, void __user *, arg)。magic1 必须是 0xfee1dead（"fee1 dead"）；magic2 可以是 672274793、85072278、369367448、537993216 四个之一，这四个数对应 Linus 及家人的生日；cmd 是上面的命令字；arg 在 RESTART2 时指向用户态字符串，上限 256 字节。

调用链（3.10，kernel/sys.c）：

text
sys_reboot(magic1, magic2, cmd, arg)
├─ ① ns_capable(pid_ns->user_ns, CAP_SYS_BOOT)   —— 权限检查，不通过返回 -EPERM
├─ ② magic1 / magic2 校验                          —— 不通过返回 -EINVAL
├─ ③ reboot_pid_ns(pid_ns, cmd)                    —— pid namespace 子命名空间直接 do_exit
├─ ④ cmd == POWER_OFF && !pm_power_off → cmd = HALT —— 没有断电能力就降级成 halt
├─ ⑤ mutex_lock(&reboot_mutex)
├─ ⑥ switch (cmd)
│    ├─ RESTART   → kernel_restart(NULL)
│    ├─ RESTART2  → strncpy_from_user 取 256 字节 cmd 串，kernel_restart(buffer)
│    ├─ CAD_ON    → C_A_D = 1
│    ├─ CAD_OFF   → C_A_D = 0
│    ├─ HALT      → kernel_halt(); do_exit(0); panic("cannot halt");
│    ├─ POWER_OFF → kernel_power_off(); do_exit(0);
│    ├─ KEXEC     → kernel_kexec()      （CONFIG_KEXEC）
│    ├─ SW_SUSPEND→ hibernate()          （CONFIG_HIBERNATION）
│    └─ default   → -EINVAL
└─ ⑦ mutex_unlock(&reboot_mutex); return ret

几个值得记的点。第 ① 步用的是 ns_capable 不是 capable，权限相对当前任务所在的 user namespace 判定，容器里带 CAP_SYS_BOOT 的 init 可以对自己的 pid namespace 做 reboot，不必全局 root。第 ④ 步是降级逻辑：pm_power_off 是板级注册的函数指针（void (*pm_power_off)(void)），没注册就说明平台没有软断电能力，此时 POWER_OFF 被改写成 HALT 而不是返回错误，用户看到的效果是「关机变成了停在某个画面」，嵌入式板子上很常见。reboot_mutex 是串行化用的，它是 mutex 不是 spinlock，因为整条路径要睡眠（关设备、等 I/O）。SW_SUSPEND 就是 Hibernate，它在系统调用层面是「持久到磁盘的挂起」，成功的话这个系统调用永远不返回——机器已经断电；恢复后回到的是当初写镜像的位置，而不是 sys_reboot 的返回处。

Ctrl-Alt-Del 走旁路：键盘驱动中断里调 ctrl_alt_del()，看 C_A_D 为真就把 work 排到工作队列、work 里调 kernel_restart(NULL)；为假就给 cad_pid 发 SIGINT 让用户态 init 决定。所以 CAD_ON / CAD_OFF 不改任何硬件状态，改的只是一个 int C_A_D。

七、reboot 通知链：谁需要在重启前收尾 #

kernel_restart_prepare 和 kernel_shutdown_prepare 的第一件事都是发通知：

c
/* kernel/sys.c, Linux 3.10 */
void kernel_restart_prepare(char *cmd)
{
        blocking_notifier_call_chain(&reboot_notifier_list, SYS_RESTART, cmd);
        system_state = SYSTEM_RESTART;
        usermodehelper_disable();
        device_shutdown();
}

/* kernel_shutdown_prepare 同构，只是事件码按 state 选 */

static void kernel_shutdown_prepare(enum system_states state)
{
        blocking_notifier_call_chain(&reboot_notifier_list,
                (state == SYSTEM_HALT) ? SYS_HALT : SYS_POWER_OFF, NULL);
        ...
}

事件码在 include/linux/reboot.h：SYS_DOWN 是 0x0001，SYS_RESTART 直接等于 SYS_DOWN（历史遗留：早期只有「系统要 down 了」这一个事件，后来才细分出 halt 和 power off），SYS_HALT 是 0x0002，SYS_POWER_OFF 是 0x0003。注册接口是 register_reboot_notifier() / unregister_reboot_notifier()，本质是 blocking_notifier_chain_register(&reboot_notifier_list, nb) 的薄封装，register 永远返回 0。名字里的 blocking 很重要：回调在进程上下文执行，可以睡眠、拿 mutex、等 I/O，和 atomic_notifier 是两码事。

这条链的语义是「最后一句话」。 挂在上面的回调有机会在系统失去响应之前把该落盘的东西落盘、该停的硬件停掉。典型使用者：watchdog 驱动（关狗，否则重启到一半被咬）、存储与文件系统（刷掉缓存里的元数据）、网络设备（通知对端断开）、板级与 PMIC 驱动（切到目标关机时序）、内核转储设施（记录最后状态）。

三个约束必须记牢：

  • 回调返回值被忽略。blocking_notifier_call_chain 的返回值在 kernel_restart_prepare 里没人看，所以这条链不能否决重启，只能做事。
  • 顺序由 notifier_block 的 priority 决定，越大越先被调。要排在某驱动之后，就把优先级调低。
  • 不能指望 usermodehelper（usermodehelper_disable() 就排在通知之后），也不要做长时间阻塞，否则拖住整条关机路径。

八、reboot 模式与它会做什么 #

前面讲的都是「内核侧怎么走」，还有一层要单独说：machine 层拿什么参数去做重启。ARM 上这个参数叫 reboot_mode。

在 3.10 的 arch/arm/kernel/process.c 里，它就是一个 char，默认值 'h'：

c
static char reboot_mode = 'h';

int __init reboot_setup(char *str)
{
        reboot_mode = str[0];
        return 1;
}
__setup("reboot=", reboot_setup);

也就是说，板子上电时传 reboot=c 就把它设成 'c'，传 reboot=w 就是 'w'。它唯一的用途是作为第一个参数交给 machine 钩子：

c
void (*arm_pm_restart)(char str, const char *cmd) = null_restart;
EXPORT_SYMBOL_GPL(arm_pm_restart);

void machine_restart(char *cmd)
{
        smp_send_stop();

        arm_pm_restart(reboot_mode, cmd);

        /* Give a grace period for failure to restart of 1s */
        mdelay(1000);

        /* Whoops - the platform was unable to reboot. Tell the user! */
        printk("Reboot failed -- System halted\n");
        local_irq_disable();
        while (1);
}

reboot_mode 的取值本身只是一堆约定，真正解释它的是板级注册的 arm_pm_restart 实现：

取值 惯常含义 做的事（具体实现因平台而异）
'w' warm reset，暖复位 复位 CPU 核心，不断电、不重初始化 DDR，靠引导程序的约定或保留内存恢复
'c' cold reset，冷复位 整颗 SoC 完整复位，DDR 重新训练，一切从头来
'g' gpio / external reset 通过外部复位引脚或 PMIC 复位芯片拉复位
'h' 3.10 的默认值 行为完全由平台决定，未注册钩子时是 null_restart，等于什么都不做

这张表里的「做的事」不是内核保证的语义。 3.10 的 ARM 主线上没有对这个 char 做任何解释，驱动拿到的就是一个字母。要确认自己板子的行为只有两条路：看 arm_pm_restart 的实现，或者做实验。任何「'w' 一定保留 DDR 内容」的说法都要在你的平台上验证——未验证。

另外，「warm reset 保留内存」这件事还有第 12 章的 SWSUSP 在用它：Hibernate 之后如果选择 reboot 模式下电（见 power_down()），重启回来的内核需要在内存里找到镜像的线索，swsusp_header 里的 flags 就是为这个准备的。

两个机器钩子的实现简单到不像话：

c
void machine_halt(void)
{
        smp_send_stop();
        local_irq_disable();
        while (1);
}

void machine_power_off(void)
{
        smp_send_stop();

        if (pm_power_off)
                pm_power_off();
}

machine_halt 就是「停掉别的 CPU，关中断，死循环」——中断关了、CPU 空转，确实就是 halt。machine_power_off 依赖板级注册的 pm_power_off，没注册就什么也不做然后返回，kernel_power_off 接着走 do_exit，机器停在那儿。

machine_restart 的注释讲的是设计要求：多 CPU 系统必须有硬件复位实现，保证所有 CPU 同时复位，否则复位后主 CPU 上跑的引导程序还得跟别的 CPU 协调「你们别再用那块 RAM 了」，这种协调做不到；单 CPU 系统可以用 soft_restart()。

顺便收一下架构与平台：arch/xxx/ 是体系结构（ARM、x86、RISC-V），arch/xxx/mach-xxx/ 或设备树的 compatible 是平台。machine_* 属于架构层，内部转手调平台层注册的钩子（arm_pm_restart、pm_power_off）。落到驱动工程师头上的活只有两件：给自己管的设备实现 ->shutdown，给平台实现正确的 restart / power off 钩子。

九、Sleep 与 Hibernate 不是一回事 #

先把词汇理清，这几个词在中文资料里被混用得最厉害。

Hibernate（冬眠）与 Sleep（睡眠） 是用户视角的两个功能。它们的共同动作序列是：暂停使用 → 保存上下文 → 关闭系统省电 → 恢复系统 → 恢复上下文 → 继续用。它们的不同点只有三个：上下文存到哪里、靠什么触发恢复、底层用哪套机制实现。

Suspend 有两层含义，混起来就乱：底层实现上的统称，指「挂起系统」这个动作，按上下文存放位置分为 Suspend to Disk（STD，就是 Hibernate） 和 Suspend to RAM（STR，Sleep 的一种）；代码层面则指 kernel/power/suspend.c 这个文件及其代表的 STR 实现。

Standby 是 Sleep 的一个特例，中文叫「打盹」。STR 最终会把 CPU 置于低功耗状态，但 CPU 提供的低功耗状态不止一种：有的深，有的浅。Standby 对应浅睡眠，任何中断都能把它唤醒，退出延迟极短，省的电也少。

Wakeup 是恢复动作在内核里的叫法。麻烦的不是「能不能醒」，而是「什么样的刺激才算数」。Hibernate 时整机断电，只有 Power 键能叫醒它；Sleep 时保留了一部分供电，键盘、电源键、RTC、USB、网卡这些被刻意保留供电的设备都能唤醒系统。这些设备统称唤醒源（wakeup source），怎么选、怎么防误唤醒，是 Sleep 设计工作的核心。

为了不再绕，下文统一用底层术语：STD、STR、Standby。两者并排对照：

维度 Sleep（STR） Hibernate（STD）
上下文位置 DRAM 断电不丢的存储介质（swap 分区 / swap 文件）
断电程度 除 DRAM 自刷新与唤醒源外基本断电 可以整机断电
待机功耗 有，DRAM 自刷新 + 唤醒源常供电 接近 0（只剩 RTC/PMIC 的漏电）
恢复时间 百毫秒 ~ 数秒量级，取决于设备和 DRAM 容量 十秒量级，取决于镜像大小和存储带宽
用户态入口 echo mem > /sys/power/state echo disk > /sys/power/state

一条实用结论：Hibernate 的收益主要在「断电」上，代价主要在「I/O」上。如果你的设备在待机时本来就靠电池扛、又希望秒级恢复，那 STR 是对的；如果你要的是彻底断电（换电池、长期存放、运输）并且能接受十几秒启动，那才轮到 Hibernate。

c
/* kernel/power/suspend.c, Linux 3.10 */

	[PM_SUSPEND_FREEZE]     = "freeze",
	[PM_SUSPEND_STANDBY]    = "standby",
	[PM_SUSPEND_MEM]        = "mem",
};

disk 的取值另有 hibernation_modes[]（kernel/power/hibernate.c）：platform 交给平台的 hibernation_ops（如 ACPI 的 SLEEP 状态，只有注册了 ops 才可用）；shutdown 写完镜像调 kernel_power_off()，是 hibernation_mode 的初值，也是没有平台 ops 时的默认值；reboot 写完镜像调 kernel_restart(NULL)，主要用于测试；suspend 用 STR 的路径「关机」，要 CONFIG_SUSPEND。

wakeup_count 是 STR 里最容易被忽略的竞态修复。唤醒 CPU 的唯一途径是唤醒源产生中断，问题出在中间窗口：系统已经睡了来事件——直接醒，没问题；系统正在睡的过程中（state 刚写入、进程还没冻结完）来事件——用户态已经处理并「后悔」了，但内核不知道，还是睡下去，这次唤醒白丢。wakeup_count 把这变成乐观并发控制：用户态写 state 前先读数、再写回，内核比对不一致就返回错误让它放弃；一致时记下快照，后续 suspend 过程中继续比对，不符就终止。这套约定要用户态配合，systemd-sleep 这类实现都会走。

十、Hibernate：把内存写进 swap #

Hibernate 的一种主流实现叫 SWSUSP（Swap Suspend）。swap 指的就是内存去了哪：镜像写进 swap 分区，恢复时从 swap 分区读回来。它从 2.6 起就在主线里，目标是「断电之后重新开机，还能回到断电前的现场」。

从开发角度看，要实现这个目标，系统必须保住三类信息：

  1. CPU 状态：各 CPU 的通用寄存器、PC、SP、CPSR，以及 MMU 的页表基址。
  2. 寄存器状态：外设寄存器的现场。这部分由驱动的 ->freeze / ->freeze_noirq 回调自行保存到内存里。
  3. Memory 状态：一整块 RAM 的内容。

Memory 的去处很明确：写 swap。那 CPU 和寄存器怎么办？有两条路：

  • 另开一块内存把 CPU / 寄存器状态存下，随内存镜像一起写盘。这条路在「用 U-Boot 实现 STF/STD」的方案里会被用到，因为 U-Boot 完全不了解内核的现场。
  • 借用内核既有的 CPU Suspend 框架：挂起时让 CPU 进入低功耗状态，恢复时从这个状态返回。寄存器由框架自己保存。

内核选第二条，省下的是「自己攒一套 CPU 上下文保存代码」的工作量。本质和第一条一样：寄存器被存进一块预留的内核栈，指针放在 sleep_save_sp，恢复时从那里取。

ARM 上的实现是全篇最「魔法」的一段。save_processor_state() / restore_processor_state() 是通用入口，落到 cpu_suspend()：__cpu_suspend_save()（arch/arm/kernel/suspend.c）先把三样东西压进保存块——恒等映射页表 idmap_pgd 的物理地址、虚拟栈指针、恢复函数 cpu_do_resume 的物理地址，再接 cpu_do_suspend() 存下的 CPU 专有寄存器，最后把保存块的物理地址写进 save_ptr。

__cpu_suspend（arch/arm/kernel/sleep.S）负责把 sleep_save_sp 对上当前 CPU：

armasm
	ldr	r3, =sleep_save_sp
#ifdef CONFIG_SMP
	ALT_SMP(mrc p15, 0, lr, c0, c0, 5)
	ALT_UP(mov lr, #0)
	and	lr, lr, #15
	add	r3, r3, lr, lsl #2
#endif
	bl	__cpu_suspend_save

sleep_save_sp:
	.rept	CONFIG_NR_CPUS
	.long	0			@ preserve stack phys ptr here
	.endr

每个 CPU 一个槽位，保存的是「该 CPU 保存块」的物理地址。恢复时 cpu_resume 靠同一套索引找到自己的栈，把 MMU 打开（cpu_resume_mmu）、跳回 cpu_resume_after_mmu，最后从栈上恢复 r4-r11 和 pc。pc 一旦恢复，执行流就回到了当初调 __cpu_suspend 的地方——这就是源码注释里那句 "Restore control flow magically appears here" 的真实含义。

所以「恢复」在代码层面不是从一个统一的入口进入的，而是各个 CPU 各自回到自己当初离开的那一行。这也是为什么 Hibernate 的恢复流程在代码上看起来如此割裂：一部分逻辑在 software_resume（新内核启动时跑的），一部分逻辑在 hibernate() 里接着跑（老现场继续执行）。

十一、SWSUSP 要保存的三类状态：CPU、寄存器、内存 #

把上一章的思路落成数据结构。

CPU 状态的去处已在 sleep_save_sp。这里补一句：sleep_save_sp 只在 CPU 进入 suspend 时被填充，所以它保存的是「物理地址」而不是虚拟地址——恢复时要靠它找到栈，而那时候 MMU 还没开。这是全篇最容易被忽略的一个细节。

寄存器状态没有统一的数据结构。每个驱动在自己的 dev_pm_ops 回调里处理：->suspend（可睡眠上下文）存，->resume 恢复；->freeze（Hibernate 专用，可睡眠）存，->thaw 恢复；->freeze_noirq（关中断后）存，->thaw_noirq 恢复；->poweroff / ->restore 是更深一档。Hibernate 走的是 freeze 这一族，所以从设备的角度看，它经历的就是一次 Suspend——只不过这次挂起时间长得多，中途还断了电。设备不需要知道背后发生了 Hibernate，恢复时照标准 PM resume 流程跑一遍就行。这是 SWSUSP 最省事的设计。

Memory 状态的去处是 swap，但要先解决一个问题：内存里有大量页不需要保存。空闲页不用存，内核标记为 nosave 的区域不用存，image 自身占用的页也不用存。把这些页剔掉，镜像才会远小于物理内存。

处理办法是位图。做法和内核启动期的 boot_mem 一模一样：一位代表一个页（按 pfn 偏移），用多层块结构覆盖整个 zone。kernel/power/snapshot.c 里为此维护了几张位图：

位图 语义
forbidden_pages_map 不在镜像里的页：nosave 区域，以及镜像自身分配的页
free_pages_map 空闲页；恢复阶段被复用为「unsafe 页」标记
orig_bm 需要保存的页（hibernate 阶段）；恢复阶段变成「镜像页」标记
copy_bm 镜像副本所在的页（hibernate 阶段）；恢复阶段先标镜像页，随后内容复制到 orig_bm 再释放

后两张是 struct memory_bitmap 的两个静态实例，声明处的注释直接说明了它们的双重身份（hibernate 阶段用一套语义，restore 阶段换成另一套）。具体怎么用，核心是 copy_data_pages()：

c
/* kernel/power/snapshot.c, Linux 3.10 */
static void
copy_data_pages(struct memory_bitmap *copy_bm, struct memory_bitmap *orig_bm)
{
	struct zone *zone;
	unsigned long pfn;

	for_each_populated_zone(zone) {
		unsigned long max_zone_pfn;

		mark_free_pages(zone);
		max_zone_pfn = zone->zone_start_pfn + zone->spanned_pages;
		for (pfn = zone->zone_start_pfn; pfn < max_zone_pfn; pfn++)
			if (page_is_saveable(zone, pfn))
				memory_bm_set_bit(orig_bm, pfn);
	}
	memory_bm_position_reset(orig_bm);
	memory_bm_position_reset(copy_bm);
	for (;;) {
		pfn = memory_bm_next_pfn(orig_bm);
		if (unlikely(pfn == BM_END_OF_MAP))
			break;
		copy_data_page(memory_bm_next_pfn(copy_bm), pfn);
	}
}

它做两件事。第一遍扫所有 zone，把可保存的页标进 orig_bm（page_is_saveable 剔掉 forbidden 页、free 页、reserved 页、guard 页）。第二遍同时遍历两张图，把原页复制到 copy_bm 标记的目标页。镜像的每一页都是副本，原页一个字节都不动。

为什么要复制而不原地写盘？写盘是「逐步进行、期间不能碰 swap」的原子区间，原页保持原样才能：写盘失败时干净回退；恢复时判断「这页是不是已经被恢复内核占用了」——被占用就走 PBE 机制换回来。

nr_copy_pages（镜像数据页数）和 nr_meta_pages（存原始 pfn 的元数据页数）在这之后才确定：nr_copy_pages = nr_pages，nr_meta_pages = DIV_ROUND_UP(nr_pages * sizeof(long), PAGE_SIZE)。元数据页每页装 PAGE_SIZE / sizeof(long) 个 pfn，恢复时靠它知道镜像第 N 页该放回哪个物理页。这也是镜像大小 = 1（头） + nr_meta_pages + nr_copy_pages 的由来。

create_image() 是全流程的核心，也是「魔法」发生的地方：

c
/* kernel/power/hibernate.c, Linux 3.10（节选） */
static int create_image(int platform_mode)
{
	int error;

	error = dpm_suspend_end(PMSG_FREEZE);
	...
	error = platform_pre_snapshot(platform_mode);
	...
	error = disable_nonboot_cpus();
	...
	local_irq_disable();
	error = syscore_suspend();
	...
	if (hibernation_test(TEST_CORE) || pm_wakeup_pending())
		goto Power_up;

	in_suspend = 1;
	save_processor_state();
	error = swsusp_arch_suspend();
	if (error)
		printk(KERN_ERR "PM: Error %d creating hibernation image\n", error);
	/* Restore control flow magically appears here */
	restore_processor_state();
	...
	dpm_resume_start(in_suspend ?
		(error ? PMSG_RECOVER : PMSG_THAW) : PMSG_RESTORE);
	return error;

几个变量承担了全部的状态传递：in_suspend（进入镜像创建前置 1，恢复成功后仍为 1，用来区分「这一行是恢复回来的」还是「这次没睡成正常返回」）、freezer_test_done（pm_test=freezer 测试时置位）、error（swsusp_arch_suspend() 的返回值，0 表示镜像已创建）。

swsusp_arch_suspend() 在 ARM 上就是 cpu_suspend(0, swsusp_save)：把 CPU 状态存进 sleep_save_sp 指向的栈，执行 swsusp_save() 造镜像，然后等断电或被唤醒。执行流的分裂点就在这里——同一个 create_image() 会被两个不同的上下文进入第二次：

  • 场景 A：这次没睡成（pm_wakeup_pending() 为真，或设备 freeze 失败），swsusp_arch_suspend() 返回非 0，函数正常往下走，dpm_resume_start 走 PMSG_RECOVER。
  • 场景 B：镜像写盘、整机断电、重新上电，新内核在 software_resume() 里读回镜像，swsusp_arch_resume() 覆盖内存并让 CPU 回到当初调 swsusp_arch_suspend() 的位置。create_image() 从 restore_processor_state() 之后继续跑，dpm_resume_start 走 PMSG_THAW。

resume_target_kernel() 里还有一句 touch_softlockup_watchdog()：从挂起到恢复这段时间对 watchdog 来说是「时间跳变」，时间戳一下前进几个小时，不告诉它一声就会误报 soft lockup。

另有几个和恢复相关的内核参数，排障时常用：

参数 作用
resume=/dev/sda2 或 resume=8:2 指定 resume 设备。CONFIG_PM_STD_PARTITION 编译时给了默认值
resume_offset= swap 文件场景下指定文件在分区内的起始块
noresume 跳过恢复，正常引导。镜像还在盘上，但这次不理它
hibernate=noresume / nocompress 同上；后者表示不压缩镜像（SF_NOCOMPRESS_MODE）
resumewait resume 设备没就绪就循环等
resumedelay= 读镜像前先延迟若干秒

其中 noresume 和 resumewait 处理的是同一类问题：设备枚举比 resume 流程慢。eMMC、USB 存储、RAID 在 late_initcall 阶段未必就绪，name_to_dev_t() 拿不到设备号，恢复就静默失败并正常引导——用户看到的是「休眠了一次，结果冷启动，还丢了一半文件系统日志」。

最后把两个函数钉死：swsusp_arch_suspend() 造镜像，swsusp_arch_resume() 覆盖内存并跳转。前者会正常返回，后者一旦成功就不返回——resume_target_kernel() 里的 BUG_ON(!error) 就是断言这一点。

十三、Hibernate 的落盘位置与镜像格式 #

镜像写到 swap 分区的哪一块？靠三个头信息串起来。

第一层：swap 分区头。 swap 分区的第一块（swsusp_resume_block，默认 0）本来是 swap 签名头，内容为 SWAP-SPACE 或 SWAPSPACE2。Hibernate 会把它换成自己的 swsusp_header：

c
/* kernel/power/swap.c, Linux 3.10 */
#define HIBERNATE_SIG	"S1SUSPEND"

struct swsusp_header {
	char reserved[PAGE_SIZE - 20 - sizeof(sector_t) - sizeof(int) -
	              sizeof(u32)];
	u32	crc32;
	sector_t image;
	unsigned int flags;	/* Flags to pass to the "boot" kernel */
	char	orig_sig[10];
	char	sig[10];
} __attribute__((packed));

static int mark_swapfiles(struct swap_map_handle *handle, unsigned int flags)
{
	hib_bio_read_page(swsusp_resume_block, swsusp_header, NULL);
	if (!memcmp("SWAP-SPACE", swsusp_header->sig, 10) ||
	    !memcmp("SWAPSPACE2", swsusp_header->sig, 10)) {
		memcpy(swsusp_header->orig_sig, swsusp_header->sig, 10);
		memcpy(swsusp_header->sig, HIBERNATE_SIG, 10);
		swsusp_header->image = handle->first_sector;
		swsusp_header->flags = flags;
		if (flags & SF_CRC32_MODE)
			swsusp_header->crc32 = handle->crc32;
		return hib_bio_write_page(swsusp_resume_block,
					swsusp_header, NULL);
	}
	printk(KERN_ERR "PM: Swap header not found!\n");
	return -ENODEV;
}
字段 作用
reserved 填充到整页，剩下的字节没用
crc32 镜像数据的 CRC32，SF_CRC32_MODE 下启用
image 镜像第一块（sector）在 swap 里的位置
flags 传给「引导内核」的 flag，见 SF_*
orig_sig[10] 被覆盖前的原始 swap 签名（SWAP-SPACE / SWAPSPACE2）
sig[10] HIBERNATE_SIG，即 "S1SUSPEND"

为什么要换头？正常运行时 swap 按内存语义用，冷启动时直接重置，标准 swap 头没必要记 offset；恢复时新内核拿着一个 swap 分区必须知道镜像放在哪，而 swap 头的位置永远固定在分区开头。mark_swapfiles() 先校验原签名，签名不对就不动，不会写坏普通分区。恢复成功后 swsusp_check() 把 orig_sig 写回去；走非恢复路径（如 hibernate=suspend）时 swsusp_unmark() 也会还原签名，否则这个 swap 分区下次 swapon 会被判为脏。

第二层：镜像头 swsusp_info。 镜像第 0 页，定义在 kernel/power/power.h。uts 存挂起时的 utsname，version_code 存 LINUX_VERSION_CODE，num_physpages 存物理页数，cpus 存 CPU 个数，image_pages 存数据页数（nr_copy_pages），pages 是镜像总页数（1 + nr_meta_pages + nr_copy_pages），size 是字节数。

c
struct swsusp_info {
	struct new_utsname	uts;
	u32			version_code;
	unsigned long		num_physpages;
	int			cpus;
	unsigned long		image_pages;
	unsigned long		pages;
	unsigned long		size;
} __attribute__((aligned(PAGE_SIZE)));

恢复的第一道闸是 check_header()：逐个比对 version_code、sysname、release、version、machine、num_physpages，任一不符就打 PM: Image mismatch: %s 并返回 -EPERM。它挡掉的典型事故是：换了内核版本、换了机器、加了内存条，却还拿旧镜像恢复。

第三层：pfn 元数据页 + 数据页。 逻辑布局：

text
逻辑页 0                          swsusp_info（镜像头）
逻辑页 1 .. nr_meta_pages         原页 pfn 列表，每页 PAGE_SIZE/sizeof(long) 个
逻辑页 nr_meta_pages+1 .. 末尾    数据页（copy_bm 标记的页，按顺序）

这些逻辑页在 swap 里物理上不连续——alloc_swapdev_block() 一页一页分配，落到哪里算哪里，中间还夹着系统正常运行时 swap out 的页。串联它们的是 swap map：

c
/* kernel/power/swap.c, Linux 3.10 */
#define MAP_PAGE_ENTRIES	(PAGE_SIZE / sizeof(sector_t) - 1)

struct swap_map_page {
	sector_t entries[MAP_PAGE_ENTRIES];
	sector_t next_swap;
};

一个 swap_map_page 占一页，装 MAP_PAGE_ENTRIES 个 sector 号，指向镜像的逻辑页；最后一个槽位 next_swap 指向下一个 map page，构成单向链表，头指针就是 swsusp_header.image。get_swap_reader() 顺着 next_swap 把所有 map page 读进列表，之后顺序取 entries[]；写入时 get_swap_writer() 先分配一页，swap_write_page() 边写边填，填满再换。原文把它叫 swap_page_map，源码里对应的类型名是 swap_map_page / swap_map_handle，口径差异记在勘误里。

swsusp_write() 的整体动作：拿到 swap writer，非压缩模式下先 enough_swap() 估空间，snapshot_read_next() 取第一页当镜像头用 swap_write_page() 写入，剩下的按 flag 分派给 save_image()（不压缩）或 save_image_lzo()（压缩）：

c
int swsusp_write(unsigned int flags)
{
	struct swap_map_handle handle;
	struct snapshot_handle snapshot;
	unsigned long pages;
	int error;

	pages = snapshot_get_image_size();
	error = get_swap_writer(&handle);
	if (flags & SF_NOCOMPRESS_MODE && !enough_swap(pages, flags))
		printk(KERN_ERR "PM: Not enough free swap\n");
	/* 简化：完整实现含大量 goto 清理路径 */
	memset(&snapshot, 0, sizeof(struct snapshot_handle));
	error = snapshot_read_next(&snapshot);
	error = swap_write_page(&handle, data_of(snapshot), NULL);
	error = (flags & SF_NOCOMPRESS_MODE) ?
		save_image(&handle, &snapshot, pages - 1) :
		save_image_lzo(&handle, &snapshot, pages - 1);
	error = swap_writer_finish(&handle, flags, error);
	return error;
}

关键在 snapshot_read_next() / snapshot_write_next() 这对接口。power.h 的注释说得很明白：它们把镜像抽象成「一串按 PAGE_SIZE 切分的连续字节」，写盘代码不许对镜像内部结构做任何假设。头、元数据页、数据页的区分全封在 snapshot.c 里：handle->cur == 0 返回 swsusp_info 头；cur <= nr_meta_pages 返回 pfn 元数据页（pack_pfns() 从 orig_bm 取 set bit 填满）；之后返回数据页，由 memory_bm_next_pfn(&copy_bm) 依次定位。

默认走 LZO 压缩，最多 3 个线程并行（LZO_THREADS），另加一个 CRC32 线程（crc32_threadfn 累积 crc32_le）。压缩单位 32 页（LZO_UNC_PAGES），压缩块头部存 8 字节实际长度（LZO_HEADER = sizeof(size_t)）。flag 三个：SF_PLATFORM_MODE（1）、SF_NOCOMPRESS_MODE（2）、SF_CRC32_MODE（4）。

hibernate() 选 flag 的逻辑：platform 模式加 SF_PLATFORM_MODE；nocompress 时加 SF_NOCOMPRESS_MODE，否则加 SF_CRC32_MODE——压缩和 CRC 二选一。load_image_lzo() 结束时比对 handle->crc32 与 swsusp_header->crc32，不符就打 PM: Invalid image CRC32! 并返回 -ENODATA。空间约束方面，enough_swap() 只在非压缩模式下检查，要求 free_swap > PAGES_FOR_IO + nr_pages（PAGES_FOR_IO 是 4MB 对应的页数）；压缩模式下写不下时返回 -ENOSPC。

十四、三类休眠方式的对照 #

把 Suspend、Hibernate、Standby 三条路并排放，差异就出来了。

维度 STR（mem） STD（disk） Standby
上下文存放 DRAM swap 分区/文件 DRAM
断电 否，DRAM 自刷新 可以整机断电 否，供电比 STR 更全
深睡硬件状态 CPU 进 SoC 提供的深睡眠 整机断电（或进平台休眠态） CPU 进浅睡眠
唤醒源 唤醒源中断（键盘、电源键、RTC、USB…） 只有 Power 键（断电后） 几乎任何中断
恢复时间 数百毫秒到数秒 十秒量级 毫秒级
省电效果 中 最高 低
需要的存储 无 等于镜像大小的 swap 空闲空间 无
用户态入口 echo mem > /sys/power/state echo disk > /sys/power/state echo standby > /sys/power/state
实现文件 kernel/power/suspend.c kernel/power/hibernate.c + snapshot.c + swap.c 同 suspend.c，走 PM_SUSPEND_STANDBY
典型场景 笔记本合盖、手机待机、嵌入式热关机 换电池、长期存放、运输、省电优先的设备 短暂停顿、要求零感知

四条总结：Standby → STR → STD 是「省电递增、恢复递增」的单调曲线，选谁取决于你能忍多久不响应；STD 与 STR 在设备回调层面是同一族（Hibernate 用 PMSG_FREEZE 那套，STR 用 PMSG_SUSPEND 那套，但 ->suspend / ->freeze 结构一致，这才是 SWSUSP 能复用整套 PM 框架的原因）；只有 STD 需要额外持久存储，也正因为要动块设备，它的失败面大得多（swap 不激活、resume 设备没就绪、空间不足、镜像版本不符）；freeze 严格说不算休眠，它只冻进程不碰硬件，属于 debug 和辅助手段。

两条横向的依赖关系值得记住：

  • 纵轴是「粒度」：整机（Generic PM）→ 电源域（PM domain / Regulator）→ 时钟（CCF）→ 器件（cpufreq / devfreq / Runtime PM）→ CPU（cpuidle）。上层的切换要按顺序调用下层的回调，顺序错了就是「先关时钟再关电源」这种典型 bug。
  • 横轴是「约束」：Thermal 和 PM QoS 不直接执行任何动作，它们给上层出约束（不许低于多少频率、不许进多深的 idle、唤醒延迟不能超过多少微秒）。执行者是 cpufreq、cpuidle、Runtime PM。
