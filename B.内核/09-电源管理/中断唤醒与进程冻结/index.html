一、系统睡下去之后，靠什么醒 #

一句话：靠一个没被 mask 掉、并且在 SoC 侧使能了唤醒路径的中断。

系统进 suspend 之后，CPU 断电，DRAM 自刷新，绝大多数外设断电。这时候还能动的东西只剩三类：电源管理单元（PMU / power controller）负责上电时序和复位；RTC 和少数 always-on 域里的逻辑；中断控制器里那些没被关掉的输入，以及它连到 PMU 的那根唤醒线。

所以「醒来」是一个硬件握手，跟内核调度没关系。设备拉中断线 → GIC 收到 → GIC 拉 wake_request → PMU 上电 → CPU 从复位向量起来 → 内核 resume 到一半，回头发现「哦是这个 IRQ 把我叫醒的」→ 把这个 IRQ 补一遍处理。

中间最反直觉的一步：唤醒系统的那次中断，你的 handler 根本不会被调用。它只负责把系统捅醒，然后被标记、被 disable、被延后。真正的 handler 要等到 resume 走完一大半、check_irq_resend() 把它重新踢进软中断队列之后才执行。这一点贯穿全篇，第二十二章讲冻结的时候还会再撞上它。

二、两个层面的唤醒：框架层与中断层 #

先把分工摆清楚，避免跟另一篇打架。

维度 框架层（《Suspend 流程与唤醒事件框架》） 中断层（本篇）
核心对象 struct wakeup_source、wakeup_count struct irq_desc、irq_chip、GIC
要回答的问题 谁有权阻止系统睡、睡下去之后谁算数 哪个 IRQ 能唤醒、硬件上怎么走通
关键接口 pm_stay_awake() / pm_relax()、/sys/power/wakeup_count enable_irq_wake() / disable_irq_wake()、irq_set_wake()
关键状态位 ws->active、ws->event_count IRQD_WAKEUP_STATE、IRQD_WAKEUP_ARMED、IRQS_SUSPENDED
生效时机 从设备 suspend 一直到系统真正断电 从 dpm_suspend_noirq 到 resume_device_irqs
失败后果 睡到一半被 abort，回滚 睡下去再也叫不醒，或者叫醒了 handler 跑不起来

两层的连接点是 pm_stay_awake()/pm_relax()。中断层负责把系统叫醒，叫醒之后 handler 是延后执行的，这段时间里必须有人告诉框架层「别急着再睡」，否则你 handler 还没跑完，系统又睡回去了。这笔账在第二十二章算。

三、GIC 对唤醒功能的支持 #

GIC-600 的 TRM 里有一个 wake_request 输出信号，这是硬件层面唤醒能力的落点。PMU 看到它就把对应 CPU 拉起来。

text
        设备中断线                       GIC                    PMU
   +----------+            +----------------------+      +-----------+
   |  sensor  |----------->| SPIs/PPIs            |      |           |
   +----------+            |   |                  |      |           |
                           | Redistributor        |      |           |
                           |   |                  |wake_ |           |
                           | CPU interface -------+ req  | 上电/复位 |
                           +----------------------+----->|           |
                                                          +-----------+

wake_request 只是「请求」，它不负责上电。上电、复位、时钟恢复全在 PMU 和 SoC 的 always-on 逻辑里。GIC 能做的事到「把信号送出去」为止。

GICv2 与 GICv3 在这个功能上的差别，能确认的只有架构手册层面：

项 GICv2 GICv3 / GIC-600
唤醒信号 SoC 集成侧引出，信号名随实现 wake_request，GIC-600 TRM 明确列出
电源域 多为整个 distributor 一个域 distributor 与 redistributor 可分域
每 CPU 粒度 无独立唤醒线 redistributor 可逐 CPU 上下电
内核对它的处理 drivers/irqchip/irq-gic.c 不实现 irq_set_wake drivers/irqchip/irq-gic-v3.c 同样不实现

最后一行是关键：两个 GIC 驱动都不实现 irq_set_wake。原因在第四章解释。

GIC 按「能不能断电」分两种形态，这个划分决定整条唤醒路径能不能成立：

  • GIC 在 always-on 电源域。断电时 GIC 还在工作，任何中断都能变成 wake_request，系统总能醒。省事，代价是功耗。
  • GIC 在可断电电源域。休眠时 GIC 一起断电，必须靠 SoC 另外一套唤醒逻辑，跟 GIC 没关系。各家实现千奇百怪，没有通用路径。

第三种情况是「GIC 断电且没有任何东西能唤醒」——这不是配置问题，是设计错误。Marc Zyngier 原话是 doing S2R is equivalent to committing suicide。

四、GIC power down 时中断控制器本身怎么办 #

GIC 被断电，寄存器上下文就没了。保存恢复分三处：驱动自己的 irq_chip 回调（GIC 驱动挂在 syscore_ops 上，suspend 时存 distributor 配置寄存器、resume 时写回；GICv3 在 drivers/irqchip/irq-gic-v3.c 里是 gic_suspend()/gic_resume()，函数名在 4.x 各版本有出入，具体点未验证；GICv2 在 irq-gic.c 里是 gic_suspend/gic_resume，3.x 就有）、内核的 genirq 状态（istate、irq_data.state_use_accessors 是纯软件状态，内存不断电就还在，这是 suspend 里能用标志位记账的物理基础）、SoC 平台自己（GIC 断电但唤醒靠别的硬件时，那套东西的保存恢复完全在平台代码里，内核不参与）。

再看 chip flag。定义和注释一起读：

c
/*
 * IRQCHIP_MASK_ON_SUSPEND: Mask non wake irqs in the suspend path
 * IRQCHIP_SKIP_SET_WAKE:     Skip chip.irq_set_wake(), for this irq chip
 */
enum {
	IRQCHIP_SET_TYPE_MASKED		= (1 << 0),
	IRQCHIP_EOI_IF_HANDLED		= (1 << 1),
	IRQCHIP_MASK_ON_SUSPEND		= (1 << 2),
	IRQCHIP_SKIP_SET_WAKE		= (1 << 3),
	IRQCHIP_ONOFFLINE_ENABLED	= (1 << 4),
	IRQCHIP_SELF_MASK_IRQ		= (1 << 5),
	IRQCHIP_EOI_THREADED		= (1 << 6),
	IRQCHIP_SUPPORTS_LEVEL_MSI	= (1 << 7),
	IRQCHIP_SUPPORTS_NMI		= (1 << 8),
};

IRQCHIP_SKIP_SET_WAKE 是 v3.2 加的（commit 60f96b41f71d，Santosh Shilimkar，2011-09-09），语义是「这个 chip 不需要 irq_set_wake 回调，直接当成功」，在 set_irq_wake_real() 里生效；IRQCHIP_MASK_ON_SUSPEND 的语义是「suspend 路径上把非唤醒中断在 chip 层额外 mask 掉」，在 suspend_device_irq() 里生效（见第十二章）。两者都不表示「GIC 会断电」。

c
static int set_irq_wake_real(unsigned int irq, unsigned int on)
{
	struct irq_desc *desc = irq_to_desc(irq);
	int ret = -ENXIO;
	if (irq_desc_get_chip(desc)->flags &  IRQCHIP_SKIP_SET_WAKE)
		return 0;
	if (desc->irq_data.chip->irq_set_wake)
		ret = desc->irq_data.chip->irq_set_wake(&desc->irq_data, on);
	return ret;
}

GIC 只要带上 IRQCHIP_SKIP_SET_WAKE，enable_irq_wake() 走到这儿就返回 0，什么硬件都不用碰。但现实是 arm-gic 连这个 flag 都没加——内核的立场是 GIC 不管休眠唤醒，这事儿归平台。Marc Zyngier 在邮件里把三种情况说过一遍：

text
There is (AFAIU) 3 cases when suspending:
- The GIC is in an always-on domain: SKIP_SET_WAKE is set, because
  there is nothing to do (we can always wake up). Problem solved.
- The GIC gets powered off, but we have additional HW that will take
  care of the wake-up: this is implemented by a stacked irqchip that will
  do the right thing: irq_set_wake only looks at the top level irqchip, so
  the GIC flag isn't observed, and this should work (maybe by luck...).
- The GIC gets powered off and nothing will wake us up. I'd say that in
  this case, having programmed a wake-up interrupt is a bit silly, and
  doing S2R is equivalent to committing suicide. Do we have any mechanism
  that would avoid getting in that situation?

第二段那句 irq_set_wake only looks at the top level irqchip 是钥匙。irq_desc_get_chip(desc) 返回链式 irqchip 的顶层，不是 GIC。平台套一个 sysirq 上去之后，irq_set_wake 落到平台的 chip 上，GIC 那个不实现也没关系。这就是 stacked irqchip 方案的全部动机。dts 里能看得很清楚：

dts
gic: interrupt-controller@58000000 {
	compatible = "arm,gic-v3";
	#interrupt-cells = <3>;
	reg = <0x0 0x58000000 0x0 0x10000>,	/* GICD  */
	      <0x0 0x58040000 0x0 0x100000>;	/* GICR0~7 */
	interrupts = <1 9 4>;
};
sysirq: sysirq@system {
	compatible = "xxx,XX-sysirq", "syscon";
	#interrupt-cells = <3>;
	interrupt-parent = <&gic>;
	interrupt-controller;
	services = <&tee_regmap>;
	irq-map = <48 2 0>,	/* GPIO      */
		  <29 4 1>,	/* AON RTC   */
		  <31 6 0>,	/* aon timer1*/
		  <9 10 0>,	/* eth0      */
		  <33 18 0>,	/* canfd0    */
		  <36 14 0>;	/* canfd1    */
	reg = <0x0 0x43060000 0x0 0x634>;
};

irq-map = <irq-number enable-bit polar-bit> 是平台私有约定：哪个 GIC 中断号、对应唤醒寄存器哪一位、极性。没有标准，换个 SoC 就得重写。

平台 irq domain 走 irq_domain_add_hierarchy()：先 irq_find_host(parent) 找父 domain，再挂自己。translate 是最要紧的回调，把 dts 三元组换成 hwirq：

c
static int XX_irq_domain_translate(struct irq_domain *d,
				   struct irq_fwspec *fwspec,
				   unsigned long *hwirq,
				   unsigned int *type)
{
	if (is_of_node(fwspec->fwnode)) {
		if (fwspec->param_count != 3)
			return -EINVAL;
		/* No PPI should point to this domain */
		if (fwspec->param[0] != GIC_SPI)
			return -EINVAL;
		*hwirq = fwspec->param[1];
		*type = fwspec->param[2] & IRQ_TYPE_SENSE_MASK;
		return 0;
	}
	return -EINVAL;
}

param[0] != GIC_SPI 那个判断很关键：只接受 SPI，PPI 不许指过来。PPI 是 per-CPU 私有中断，走 GIC 自己的分发路径，硬塞进平台 sysirq 语义就乱了。

再看 GIC 驱动自己的初始化 gic_dist_init()（drivers/irqchip/irq-gic.c）。它跟唤醒的关联点是「把所有中断先摆成一个已知的关闭状态」——因为跨过 suspend 之后，distributor 的使能位、优先级、触发类型全靠这份初始配置重放：

c
static void __init gic_dist_init(struct gic_chip_data *gic)
{
	unsigned int i;
	u32 cpumask;
	unsigned int gic_irqs = gic->gic_irqs;
	void __iomem *base = gic_data_dist_base(gic);

	cpumask = gic_get_cpu_id(gic);
	writel_relaxed(cpumask, base + GIC_DIST_TARGET);
	...
	/*
	 * Set all global interrupts to be level triggered, active low.
	 */
	for (i = 32; i < gic_irqs; i += 16)
		writel_relaxed(GICD_INT_ACTLOW_LVLTRIG, base + GIC_DIST_CONFIG + i / 4);

	/*
	 * Set priority on all global interrupts.
	 */
	for (i = 32; i < gic_irqs; i += 4)
		writel_relaxed(GICD_INT_DEF_PRI_X4, base + GIC_DIST_PRI + i);

	/*
	 * Deactivate and disable all the interrupts. This is required
	 * for the secondary boot path.
	 */
	...
	gic_dist_wait_for_rwp(gic);
	...
}

三个要点。GICD_INT_ACTLOW_LVLTRIG 把全部 SPI 默认设成低电平触发——之后每个设备的 dts 再覆盖成自己需要的类型。GICD_INT_DEF_PRI_X4 一次性写 4 个中断的优先级。最后那段「Deactivate and disable all the interrupts」是关键：所有中断先关掉、先清 active 位，这样无论是 normal boot 还是 secondary boot，起点都是确定的。

这一条和唤醒的关系在于：suspend 之前 wakeup source 打开的那些位，resume 时是靠 gic_resume() 从保存的寄存器值里写回去的，而不是靠 gic_dist_init() 重跑一遍。gic_dist_init() 只在 boot 阶段跑。你要是把 GIC 的 restore 搞丢了，症状就是「唤醒之后一堆外设中断不见了」。

启动时这条链的调用栈，出问题照这个顺序查：start_kernel → init_IRQ（arch/arm64/kernel/irq.c）→ irqchip_init → of_irq_init（drivers/of/irq.c）→ 平台的 XX_irq_of_init。of_irq_init 先初始化父节点再初始化子节点，所以平台 sysirq 的 of_init 被调用时 GIC 的 domain 一定建好了。

五、CPU Power Down 与 Power Up 的时序 #

Cortex-A55 的 TRM 里下电流程写得很死：

text
The Cortex-A55 core uses the following power down sequence.
To power down a core, perform the following programming sequence:
- Save all architectural state.
- Configure the GIC distributor to disable or reroute interrupts away
  from this core.
- Set the CPUPWRCTLR.CORE_PWRDN_EN bit to 1 to indicate to the power
  controller that a powerdown is requested.
- Execute an Instruction Synchronization Barrier (ISB) instruction.
- Execute a WFI instruction.
After executing WFI and then receiving a powerdown request from the power
controller, the hardware performs the following:
- Disabling and flushing of caches (L1 and L2).
- Removal of the core from coherency.

两个细节。CPUPWRCTLR.CORE_PWRDN_EN 置 1 只是「我下次执行 WFI 时想掉电」，是意向声明，不是立即掉电。真正的掉电要等电源控制器回应，WFI 之后到硬件动手之间有一个窗口，中断还能进来，进来就取消掉电。这就是关中断时机那么讲究的原因。

流程第二句「Configure the GIC distributor to disable or reroute interrupts away from this core」——CPU 下电前 GIC 里指向它的中断必须先掐掉。内核分两步：先把 nonboot CPU 全 offline（走 CPU hotplug，GIC 里对应的 redistributor/CPU interface 收拾干净），最后再关 boot CPU 的本地中断。

上电方向没有标准流程，纯 SoC 私有。能确认的只有一点：复位之后 CPU 从 RVBAR 指明的地址取指。RVBAR 是外部输入信号，A55 的 TRM 里没找到完整定义，用 A53 的凑数——复位地址可配，4 字节对齐（bit0、bit1 不可配，是 ARM 异常向量 32 字节对齐要求的延伸）。具体从哪起跳取决于 ATF/uboot 怎么配，未验证。

Linux 侧第一段指令是 cpu_resume（arch/arm64/kernel/sleep.S）。唤醒后先跑一段汇编恢复 MMU、页表基址、栈指针，再回到 psci_system_suspend_enter() 继续执行。

六、irq flags：一个中断的全部属性 #

一个中断的属性散在三个地方：irq_desc.action->flags（request 时传的 IRQF_*）、irq_desc.istate（运行时 IRQS_*）、irq_data.state_use_accessors（运行时 IRQD_*）。跟 suspend/唤醒相关的全在下表。

标志 类型 位置 与 suspend 的关系
IRQF_NO_SUSPEND request flag action->flags suspend 路径不 disable，handler 全程可跑
IRQF_COND_SUSPEND request flag action->flags 只在 IRQ 同时是唤醒源时 NO_SUSPEND 才生效；4.x 引入
IRQF_SHARED request flag action->flags 与 IRQF_NO_SUSPEND 冲突
IRQF_TIMER request flag action->flags 隐含 IRQF_NO_SUSPEND
IRQS_SUSPENDED 运行时 desc->istate 被 suspend 关掉的 IRQ 打这个标记
IRQS_PENDING 运行时 desc->istate 唤醒中断被延后执行时置位
IRQS_REPLAY 运行时 desc->istate 边沿中断重发时防递归
IRQD_WAKEUP_STATE 运行时 irq_data enable_irq_wake() 成功后置位
IRQD_WAKEUP_ARMED 运行时 irq_data suspend 时对唤醒源置位
IRQD_IRQ_INPROGRESS 运行时 irq_data hardirq handler 正在跑
IRQD_IRQ_DISABLED 运行时 irq_data IRQ 被 disable
IRQD_IRQ_MASKED 运行时 irq_data 硬件层被 mask
IRQCHIP_MASK_ON_SUSPEND chip flag irq_chip.flags suspend 时对非唤醒中断额外 mask
IRQCHIP_SKIP_SET_WAKE chip flag irq_chip.flags 跳过 irq_set_wake 回调

IRQF_TIMER 的定义是「我永远不下线」的典型：

c
#define IRQF_TIMER	(__IRQF_TIMER | IRQF_NO_SUSPEND | IRQF_NO_THREAD)

timer 中断既不能 suspend 也不能线程化，因为 suspend 期间很多等待逻辑靠 tick 兜底。

IRQF_COND_SUSPEND 是 4.x 中期才有的，3.x 完全没有这个概念。它堵的是一个漏洞：一个 IRQ 设了 IRQF_NO_SUSPEND 又被拿去当唤醒源，两套语义打架。IRQF_COND_SUSPEND 让 IRQF_NO_SUSPEND 变成有条件的。具体哪个版本进来的未验证，4.15 里已有。

七、IRQF_NO_SUSPEND：谁需要它 #

内核文档 power/suspend-and-interrupts.txt 点了三类：timer 中断（suspend 过程中 tick 逻辑还在跑）、IPI（唤醒后给其他 CPU 发 kick，nonboot CPU 拉回 online 靠它）、少数特殊设备中断（比如 PMIC 里负责叫醒系统的那部分输入）。

IRQF_NO_SUSPEND 的效果只有一条：suspend_device_irqs() 不会 disable 它，handler 照常执行。它不带来任何唤醒能力。 想唤醒系统必须另外调 enable_irq_wake()。素材原话：「这并不能保证该中断可以将系统唤醒。如果想要达到唤醒的目的，请调用 enable_irq_wake。」

坑写在明面上：IRQF_NO_SUSPEND 挂在 IRQ 上，不是挂在 handler 上。一个 IRQ 上注册了多个 handler（IRQF_SHARED），只要其中一个带了这个 flag，suspend 期间整条 IRQ 都不 disable，所有 handler 都会被调度到——包括没标这个 flag 的。那些 handler 所属的设备却已经 suspend 了，IO 地址空间未必还能访问。

所以 ARM 上一般不用 IRQF_SHARED（片子外设中断够多，没必要共享），但只要用了，这两个 flag 就别凑一块。

还有一点容易忽略：handler 能跑，不等于 handler 里拿得到资源。IRQF_NO_SUSPEND 只解决「中断不丢」，不解决「依赖还在」。

八、enable_irq_wake 的实现 #

驱动里最常写的一行是 enable_irq_wake(irq)，但它是个 wrapper（return irq_set_irq_wake(irq, 1)，disable_irq_wake 就是传 0），真活儿在 irq_set_irq_wake() 里（linux-4.15-rc3，kernel/irq/manage.c）：

c
int irq_set_irq_wake(unsigned int irq, unsigned int on)
{
	unsigned long flags;
	struct irq_desc *desc = irq_get_desc_buslock(irq, &flags,
						    IRQ_GET_DESC_CHECK_GLOBAL);
	int ret = 0;
	if (!desc)
		return -EINVAL;
	/* wakeup-capable irqs can be shared between drivers that
	 * don't need to have the same sleep mode behaviors.
	 */
	if (on) {
		if (desc->wake_depth++ == 0) {
			ret = set_irq_wake_real(irq, on);
			if (ret)
				desc->wake_depth = 0;
			else
				irqd_set(&desc->irq_data, IRQD_WAKEUP_STATE);
		}
	} else {
		if (desc->wake_depth == 0) {
			WARN(1, "Unbalanced IRQ %d wake disable\n", irq);
		} else if (--desc->wake_depth == 0) {
			ret = set_irq_wake_real(irq, on);
			if (ret)
				desc->wake_depth = 1;
			else
				irqd_clear(&desc->irq_data, IRQD_WAKEUP_STATE);
		}
	}
	irq_put_desc_busunlock(desc, flags);
	return ret;
}

四件事。拿 desc 要带 IRQ_GET_DESC_CHECK_GLOBAL，这是校验参数，要求目标 IRQ 全局可见（不是 per-CPU 内部中断），唤醒源必须是全局的东西。wake_depth 是引用计数，只有从 0 涨到 1 那一次才真正动硬件；desc->wake_depth++ == 0 是后置自增，比较自增前的值——第一次进来判真，后面进来判假直接返回，这是「谁先请求谁配硬件，后来的只管计数」。set_irq_wake_real() 才碰 SoC 寄存器，它调 irq_chip 的 irq_set_wake() 回调；chip 带 IRQCHIP_SKIP_SET_WAKE 就直接返回 0。这里就是「不使能的话，设备在那疯狂产中断信号，SoC 也不会理你」的地方——寄存器没配，PMU 那条线是断的。成功了才置 IRQD_WAKEUP_STATE，这一步是给 suspend 流程看的，suspend_device_irq() 判的就是 irqd_is_wakeup_set()。失败路径把 wake_depth 回滚到 0，不让计数器漂着；计数器一漂，后面 disable 就不平衡，WARN(1, "Unbalanced IRQ %d wake disable\n") 就炸出来。

struct irq_desc 里跟唤醒直接相关的字段：

c
struct irq_desc {
	struct irq_common_data	irq_common_data;
	struct irq_data		irq_data;	/* 含 state_use_accessors */
	unsigned int __percpu	*kstat_irqs;
	irq_flow_handler_t	handle_irq;
	struct irqaction	*action;	/* IRQ action list */
	unsigned int		status_use_accessors;
	unsigned int		core_internal_state__do_not_mess_with_it; /* istate */
	unsigned int		depth;		/* nested irq disables */
	unsigned int		wake_depth;	/* nested wake enables */
	unsigned int		threads_active;
	wait_queue_head_t	wait_for_threads;
	...
} ____cacheline_internodealigned_in_smp;
字段 用途
wake_depth enable_irq_wake() 的嵌套计数
irq_data.state_use_accessors 存 IRQD_WAKEUP_STATE、IRQD_WAKEUP_ARMED、IRQD_IRQ_INPROGRESS
istate 存 IRQS_SUSPENDED、IRQS_PENDING、IRQS_REPLAY
depth disable_irq() 的嵌套计数，跟 wake_depth 是两套账
threads_active threaded handler 活跃计数，synchronize_irq() 等它归零
wait_for_threads 上面那个等待用的 waitqueue

depth 和 wake_depth 别搞混：depth 管 enable/disable（中断能不能送达 CPU），wake_depth 管 wake enable/disable（中断能不能把系统叫醒）。两者独立变化。

九、disable_irq_wake 与它的引用计数 #

disable_irq_wake() 就是 irq_set_irq_wake(irq, 0)，逻辑是镜像，但坑更多。三种走向：

  1. wake_depth == 0 还来 disable → WARN，什么都不做。驱动里多调了一次。
  2. wake_depth 减完还大于 0 → 什么都不做。还有别的使用者没放手，硬件保持使能。
  3. wake_depth 减到 0 → 真正关硬件，清 IRQD_WAKEUP_STATE。

第三种情况硬件关失败就把 wake_depth 回滚成 1，保持「还有人用」的假象，IRQD_WAKEUP_STATE 不清。硬件还开着，软件就不能说它关了。引用计数的意义在那句注释里：wakeup-capable irqs can be shared between drivers that don't need to have the same sleep mode behaviors。一个 IRQ 可以被多个驱动同时当唤醒源用，A 调一次，B 调一次，wake_depth 变 2。A 先 suspend 完调 disable，计数降到 1，硬件不能关——B 还要靠它唤醒。等 B 也调了才真正关。现实问题：这俩函数必须严格成对，且在对称位置调。常见错误是在 suspend() 里开、resume() 里关，但 suspend() 中途失败返回错误码——PM core 会不会调 resume()？会，所以这条路安全。真正危险的是在 suspend() 里开了却在错误分支提前 return，这次 resume() 的 disable 就多了一次。返回值常被忽略，这习惯不好：平台 chip 的 irq_set_wake(desc, 0) 依赖某个时钟或寄存器组时，设备已 resume 完成就会返回 -EIO，至少打个 log。

十、唤醒源与中断号的绑定 #

「这个 IRQ 能唤醒系统」在代码里有三条表达路径，从旧到新。

路径一，驱动自己在 suspend() 里调：

c
static int smcdef_suspend(struct device *dev)
{
	return enable_irq_wake(irq);
}
static int smcdef_resume(struct device *dev)
{
	return disable_irq_wake(irq);
}

最原始最直白，也最容易出计数错误。

路径二，probe 里声明，PM core 代管：

c
device_init_wakeup(dev, true);
dev_pm_set_wake_irq(dev, irq);

顺序不能反：先 device_init_wakeup() 把 power.can_wakeup 置起来，再 dev_pm_set_wake_irq() 把 IRQ 挂到设备上。之后 suspend 流程里的 dev_pm_arm_wake_irq() 会替你把所有 wakeup source 的 enable_irq_wake() 打开，resume 时 dev_pm_disarm_wake_irq() 再关掉。计数由 PM core 统一管，不会漏。

路径三，dts 一个属性，i2c core 全包：

dts
&i2c1 {
	sensor@38 {
		compatible = "wowo,smcdef";
		reg = <0x38>;
		interrupt-parent = <&gpio1>;
		interrupts = <12 IRQ_TYPE_EDGE_FALLING>;
		wakeup-source;
	};
};

i2c core 在 probe 阶段看到 wakeup-source 就自动做 device_init_wakeup() + dev_pm_set_wake_irq()，代码一行不用写。这是 4.x 之后 i2c/spi 普遍支持的写法，具体版本未验证。

路径 代码量 计数由谁管 适用
enable_irq_wake() 手调 两行 驱动自己 老内核、非标准设备
dev_pm_set_wake_irq() 两行（probe） PM core 通用，推荐
dts wakeup-source 零行 子系统 core i2c/spi 等总线设备

选路径二或三。路径一唯一合理的场景是设备在 suspend 过程中要动态决定开不开唤醒，比如按某个状态位切唤醒源。一个致命细节：路径二/三生效后，你在驱动 suspend() 里再手调一次 enable_irq_wake()，wake_depth 就变 2 了，而 PM core 只 disable 一次，计数永远回不到 0，硬件唤醒路径一直开着。这是最典型的功耗异常——休眠电流比预期高几百微安，查半天查不出来。

十一、Suspend to RAM 的完整流程 #

以 echo mem > /sys/power/state 为例，中断这一侧的时间线：

text
user: echo mem > /sys/power/state
  |
  +- pm_suspend() / enter_state()
       +- suspend_prepare()          <- 冻结进程（第十七~二十一章）
       +- dpm_suspend()              <- 设备 suspend，default 阶段
       +- dpm_suspend_late()         <- 设备 late suspend
       +- platform_suspend_prepare_late()
       +- suspend_enter()
            +- suspend_device_irqs() ----+ 非唤醒中断：IRQS_SUSPENDED + disable
            |                            | 唤醒中断：IRQD_WAKEUP_ARMED
            +- dpm_suspend_noirq()  -----+ noirq 回调
            +- platform_suspend_prepare_noirq()
            +- disable_nonboot_cpus()   <- 非 boot CPU 全部 offline
            +- local_irq_disable()      <- boot CPU 不再响应中断
            +- syscore_suspend()        <- GIC 保存、gpio/clock 收尾
            +- suspend_ops->enter()     <- PSCI SYSTEM_SUSPEND，CPU 停在这

syscore_suspend() 是最后一个 suspend 的，syscore_resume() 是第一个 resume 的。原因很朴素：syscore 里注册的是「其他所有设备都依赖的东西」——时钟控制器、GPIO 控制器、中断控制器。它们得先活过来，别人的 resume_noirq() 才有东西可用。注册接口是 register_syscore_ops()，.suspend 和 .resume 两个回调。GIC 驱动、drivers/clk 里的一些控制器、drivers/gpio 的 irqchip 部分都挂在这。写普通驱动不该碰它。PSCI 那条路径的接口：

c
int psci_cpu_suspend(unsigned int power_state,
		     uintptr_t entrypoint,
		     u_register_t context_id);

entrypoint 是唤醒后的入口地址，必须是物理地址（PA）；虚拟化环境下是中间物理地址（IPA），由 hypervisor 负责 trap。context_id 原样传回来。ATF 里有 PSCI_CPU_SUSPEND_AARCH64 和 PSCI_CPU_SUSPEND_AARCH32 两个版本。内核侧实际用 psci_system_suspend() / psci_system_suspend_enter()，entrypoint 传 cpu_resume 的物理地址。

十二、suspend 阶段的设备 IRQ 处理 #

核心问题：什么时候把设备中断关掉。答案是 dpm_suspend_noirq() 之前。看 suspend_enter() 的骨架：

c
static int suspend_enter(suspend_state_t state, bool *wakeup)
{
	...
	error = dpm_suspend_late(PMSG_SUSPEND);		/* late suspend 阶段 */
	if (error)
		goto Platform_finish;
	error = platform_suspend_prepare_late(state);
	if (error)
		goto Platform_wake;
	error = dpm_suspend_noirq(PMSG_SUSPEND);	/* 进 noirq 阶段 */
	if (error)
		goto Platform_late_wake;
	error = platform_suspend_prepare_noirq(state);
	...
}

dpm_suspend_noirq() 里面先 suspend_device_irqs() 把所有设备 IRQ 收拾一遍，再逐个调 device_suspend_noirq()。顺序不能反：先把中断掐了，再让设备进 noirq 状态，否则设备在 noirq 回调里被中断打断，访问半死不活的硬件。四条理由：late suspend 之后设备都停了，理论上不该再出中断，但理论上不等于事实上，没正确 suspend 的设备还会漏；共享 IRQ 上挂多个设备，一个 suspend 了中断来了大家一起被调，那个设备的 handler 会去访问已经断电的 IO 地址，这类 bug 报出来是随机的总线错误，极难定位；noirq 回调本身关时钟、断电、写序列，被中断插一脚就完了；IRQS_SUSPENDED 标记让 resume 阶段知道「这个 IRQ 是我关的，我得负责打开」。核心函数：

c
static bool suspend_device_irq(struct irq_desc *desc)
{
	if (!desc->action || irq_desc_is_chip(desc))
		return false;
	if (irqd_is_wakeup_set(&desc->irq_data)) {
		irqd_set(&desc->irq_data, IRQD_WAKEUP_ARMED);
		/*
		 * We return true here to force the caller to issue
		 * synchronize_irq(). We need to make sure that the
		 * IRQD_WAKEUP_ARMED is visible before we return from
		 * suspend_device_irqs().
		 */
		return true;
	}
	desc->istate |= IRQS_SUSPENDED;
	__disable_irq(desc);
	/*
	 * Hardware which has no wakeup source configuration facility
	 * requires that the non wakeup interrupts are masked at the
	 * chip level. The chip implementation indicates that with
	 * IRQCHIP_MASK_ON_SUSPEND.
	 */
	if (irq_desc_get_chip(desc)->flags & IRQCHIP_MASK_ON_SUSPEND)
		mask_irq(desc);
	return true;
}

按 IRQ 类型归一下结果：

IRQ 类型 处理 结果
普通 IRQ 置 IRQS_SUSPENDED，__disable_irq() handler 不会再被调用
带 IRQCHIP_MASK_ON_SUSPEND 的 chip 上的普通 IRQ 上面之外再加 mask_irq() 硬件层也 mask
唤醒源（IRQD_WAKEUP_STATE） 置 IRQD_WAKEUP_ARMED 不 disable，等中断到来
带 IRQF_NO_SUSPEND 的 IRQ 在调用者层面被过滤 全程 enable，handler 可跑
irq_desc_is_chip() 的内部描述符 直接跳过 不动

IRQF_NO_SUSPEND 的过滤不在 suspend_device_irq() 里，在调用者 suspend_device_irqs() 里，判序是先看唤醒源再看 IRQF_NO_SUSPEND。这段我没逐行照抄上游，标注为未完全验证，以目标内核 kernel/irq/pm.c 为准。代码是 4.15 的形态；3.x 里直接调 disable_irq()，逻辑对应但行号全变。irq_pm_install_action() 是 4.x 才有的机制，给每个 action 装一个 PM 包装器，在 action->handler 前插一层 irq_pm_check_wakeup()，IRQF_COND_SUSPEND 那套语义在这儿落地，3.x 没这层。suspend_device_irqs() 对每个唤醒中断会 synchronize_irq()，确保 IRQD_WAKEUP_ARMED 已被硬件侧「看见」，避免「刚置位中断就冲进来」——suspend_device_irq() 在唤醒源分支 return true 就是为了触发这个同步。

十三、resume 阶段的中断恢复顺序 #

唤醒之后顺序严格镜像，中间多了几个「看起来不该在这」的步骤。

text
  CPU 从 cpu_resume 起来
  |
  +- syscore_resume()             <- GIC 恢复、gpio/clock 先活
  +- arch_suspend_enable_irqs()   <- local_irq_enable()，中断这一刻才能进
  |    +- 唤醒中断冲进来 -> handle_edge_irq() -> irq_may_run() 返回 false
  |       -> 置 IRQS_PENDING + IRQS_SUSPENDED，irq_disable()
  +- enable_nonboot_cpus()        <- 非 boot CPU 拉回 online
  +- platform_resume_noirq()
  +- dpm_resume_noirq()
  |    +- dpm_noirq_resume_devices()
  |    +- resume_device_irqs()    <- 关掉唤醒源、恢复 IRQ
  |         +- check_irq_resend() -> tasklet -> 你的 handler 终于跑了
  +- platform_resume_early()
  +- dpm_resume_early()
  +- dpm_resume() / dpm_complete()

syscore_resume()。 GIC 寄存器在这恢复，之后中断控制器才能正常接收分发。但 CPU 本地中断还没开，中断进来只 pending 在 GIC 里。arch_suspend_enable_irqs() 就是 local_irq_enable()，从这一刻起 GIC 里 pending 的唤醒中断冲进来，走 handle_edge_irq()：

c
void handle_edge_irq(struct irq_desc *desc)
{
	raw_spin_lock(&desc->lock);
	desc->istate &= ~(IRQS_REPLAY | IRQS_WAITING);
	if (!irq_may_run(desc)) {
		desc->istate |= IRQS_PENDING;
		mask_ack_irq(desc);
		goto out_unlock;
	}
	...

irq_may_run() 发现 IRQD_WAKEUP_ARMED 还在，调 irq_pm_check_wakeup()：清掉 IRQD_WAKEUP_ARMED，置 IRQS_SUSPENDED 和 IRQS_PENDING，disable_irq_nosync() 关中断。然后返回 false，直接 goto 出去。结果：这次中断的全部作用就是「记录了系统是被这个 IRQ 叫醒的」，然后什么都没干。 你的 handler 在这个上下文里一次都没被调用。

enable_nonboot_cpus()。 为什么不先开 nonboot CPU 再开中断？因为 dpm_resume_noirq() 要调设备回调，某些设备的 resume_noirq() 需要所有 CPU 在线做 per-CPU 状态恢复。

dpm_resume_noirq()。 先跑所有设备的 resume_noirq()，再 resume_device_irqs()。为什么先回调后开 IRQ？因为唤醒中断的 handler 还没跑，而它多半要通过 i2c/spi 读设备寄存器，控制器必须在 resume_noirq() 里恢复好。gpio 又要比 i2c 更早，所以 gpio 挂 syscore。resume_device_irqs() 只做一件事——把 IRQS_SUSPENDED 的 IRQ 重新打开：

c
void resume_device_irqs(void)
{
	struct irq_desc *desc;
	int irq;
	for_each_irq_desc(irq, desc) {
		unsigned long flags;
		if (!(desc->istate & IRQS_SUSPENDED))
			continue;
		raw_spin_lock_irqsave(&desc->lock, flags);
		__enable_irq(desc);
		raw_spin_unlock_irqrestore(&desc->lock, flags);
	}
}

中断重新使能，而 IRQS_PENDING 那个「欠账」还在。唤醒中断的 disable_irq_wake() 由 dev_pm_disarm_wake_irq() 在 dpm_resume_noirq 阶段代劳（前提是走了路径二/三），你在驱动 resume() 里手调的那个不算。

check_irq_resend()。 这一步才是真相：

c
void check_irq_resend(struct irq_desc *desc)
{
	/* 电平中断不重发，硬件自己会再报，清 pending 免得 suspend/resume 混淆 */
	if (irq_settings_is_level(desc)) {
		desc->istate &= ~IRQS_PENDING;
		return;
	}
	if (desc->istate & IRQS_REPLAY)
		return;
	if (desc->istate & IRQS_PENDING) {
		desc->istate &= ~IRQS_PENDING;
		desc->istate |= IRQS_REPLAY;
		if (!desc->irq_data.chip->irq_retrigger ||
		    !desc->irq_data.chip->irq_retrigger(&desc->irq_data)) {
			unsigned int irq = irq_desc_get_irq(desc);
			/* Set it pending and activate the softirq: */
			set_bit(irq, irqs_resend);
			tasklet_schedule(&resend_tasklet);
		}
	}
}

电平中断不重发。 只要信号还在，硬件会自己再报一次，软件重发就是重复，清掉 IRQS_PENDING 走人。这也是唤醒源最好用电平触发的原因。边沿中断要软件重发，边沿是「事件」，硬件不会再报。chip 实现了 irq_retrigger() 就让 chip 自己重发；没实现就 set_bit(irq, irqs_resend) + tasklet_schedule(&resend_tasklet)。irqs_resend 是 DECLARE_BITMAP(irqs_resend, IRQ_BITMAP_BITS)，一位对一个 IRQ。tasklet 的 callback resend_irqs() 挨个 find_first_bit() 找到置位的号，重新调一次 desc->handle_irq(desc)：

c
static DECLARE_BITMAP(irqs_resend, IRQ_BITMAP_BITS);
static void resend_irqs(unsigned long arg)
{
	struct irq_desc *desc;
	int irq;
	while (!bitmap_empty(irqs_resend, nr_irqs)) {
		irq = find_first_bit(irqs_resend, nr_irqs);
		clear_bit(irq, irqs_resend);
		desc = irq_to_desc(irq);
		local_irq_disable();
		desc->handle_irq(desc);
		local_irq_enable();
	}
}
static DECLARE_TASKLET(resend_tasklet, resend_irqs, 0);

这时 IRQD_WAKEUP_ARMED 已被 irq_pm_check_wakeup() 清了，IRQS_PENDING 和 IRQS_SUSPENDED 也都清了，irq_may_run() 这次返回 true，走到 handle_irq_event(desc)，你的 handler 终于被执行。tasklet 跑在软中断上下文。结论：唤醒中断的 handler 执行在软中断上下文，不是硬件中断上下文。这在边沿触发下成立。电平触发还有一条「硬件重报」的路径，那一次走完整流程，handler 在真正的硬中断上下文。同一个驱动，触发类型不同，handler 上下文竟然不同。写 handler 时按最严的来（不能睡眠）就没问题。

十四、中断进不去的时候：nobody cared 那句日志 #

text
irq 42: nobody cared (try booting with the "irqpoll" option)
Disabling IRQ #42

这句日志的意思不是「中断没人处理」，而是「我连着调了 N 次 handler，你的 handler 每次都返回 IRQ_NONE，我认为这个 IRQ 在乱报，我把它关了」。触发点在 note_interrupt()（kernel/irq/handle.c）：action_ret != IRQ_HANDLED 时累加 desc->irqs_unhandled，超过阈值就 __report_bad_irq() + irq_disable()。

跟 suspend 的关联在这里：唤醒中断从 suspend 到 resume 走的正是「handler 不执行」那条路，但 note_interrupt() 是在 handle_irq_event_percpu() 里调的，irq_may_run() 返回 false 时根本没走到那儿，所以唤醒那一次不给 irqs_unhandled 记账。设计上是干净的。

真正会炸的是另一种情况：用 IRQF_NO_SUSPEND 保住中断全程 enable，在 suspend 期间中断进来了。这时 irq_may_run() 返回 true（没有 IRQD_WAKEUP_ARMED），handler 被调用。但设备已 suspend，读寄存器回来全是 0xff，判断「不是我的中断」，返回 IRQ_NONE。反复几次 irqs_unhandled 就爆了，IRQ 被内核关掉，之后再也起不来。这是 IRQF_NO_SUSPEND 最隐蔽的失败模式，表现是「休眠几次之后某个中断彻底失灵」，重启后恢复。

排查三步：cat /proc/interrupts 看那个 IRQ 的计数是不是卡住了；dmesg | grep -i "nobody cared" 找 Disabling IRQ #N；确认这个 IRQ 在 suspend 期间还会不会来中断。会的话，要么加 IRQF_COND_SUSPEND，要么在 handler 开头检查设备电源状态后返回 IRQ_HANDLED。真要保住 interrupt，用 pm_stay_awake()，别用 IRQF_NO_SUSPEND。

十五、IRQF_NO_SUSPEND 与 enable_irq_wake 为什么不能同时用 #

两条需求摆在一起：

手段 表达的意思 期望的行为
IRQF_NO_SUSPEND 我要在 suspend 全程跑 handler interrupt handler 被调用
enable_irq_wake() 我要这个 IRQ 能唤醒系统 只要电平/边沿，不要 handler

一个要 handler 跑，一个不要 handler 跑（至少在唤醒那一刻不要）。语义直接冲突。IRQ 不共享时矛盾更直接：标了 IRQF_NO_SUSPEND，suspend_device_irqs() 不 disable 它，irq_may_run() 也就没有 IRQD_WAKEUP_ARMED 可清，handler 直接被执行，irq_pm_check_wakeup() 那条路走不到，IRQS_PENDING 不会置位，check_irq_resend() 没东西可重发。于是「唤醒」这个语义压根没有发生。

IRQ 共享时更糟。两个东西都是挂在 IRQ 上的，不是挂在 handler 上的。内核没法区分「必须能跑的 handler」和「只当唤醒源用的 handler」，只能选一种处理方式，另一种语义废掉。素材那句总结很准：「在一个 IRQ 上共享唤醒源以及 no suspend 中断源是比较荒谬的。」

代码不拦。__setup_irq() 不会因为这两个凑一起就返回 -EINVAL。IRQF_COND_SUSPEND 是目前最接近拦截的机制，但也是运行时的。非要在特殊场合这么干，需要满足：handler 能判断「现在是正常中断还是唤醒事件」，对后者返回 IRQ_HANDLED；handler 里不能访问已 suspend 的硬件；唤醒记账自己做，pm_stay_awake() / pm_relax() 成对；别指望 check_irq_resend() 帮你补一次——不会有了。这套约束基本只有 PMIC 驱动和 SoC 最底层的中断控制器驱动值得做。

十六、Interrupts and Suspend-to-Idle #

suspend-to-idle 也叫 freeze 状态（注意跟 freezer 的「冻结进程」名字撞了但机制完全不同）。它走的还是 suspend_enter()，只是在一个岔路口拐出去：

c
static int suspend_enter(suspend_state_t state, bool *wakeup)
{
	...
	各设备的 late suspend 阶段
	各设备的 noirq suspend 阶段
	if (state == PM_SUSPEND_FREEZE) {
		freeze_enter();
		goto Platform_wake;
	}
	...
}

goto Platform_wake 跳过了后面全部：disable_nonboot_cpus()、syscore_suspend()、suspend_ops->enter() 都不执行。取而代之的是 freeze_enter()——把 CPU 推进 idle，等中断。CPU 没断电，DRAM 没停，GIC 还在工作。

状态 CPU GIC 普通 IRQ 唤醒源 IRQ IRQF_NO_SUSPEND IRQ 唤醒路径
suspend-to-RAM 断电 视 SoC 而定 已 disable 不 disable，只唤醒 全程 enable，handler 可跑 PMU 专用路径
suspend-to-idle idle 在线 已 disable 不 disable，能唤醒 全程 enable，能唤醒 普通中断路径

关键差别在最后一行。suspend-to-idle 从 idle 醒过来走的是普通中断处理路径——中断进来走完 handle_edge_irq()，irq_may_run() 里清 IRQD_WAKEUP_ARMED，置 IRQS_PENDING，然后还是走 check_irq_resend() 那条老路。suspend-to-RAM 走的是 PMU 专用路径——PMU 收到 wake_request，上电，复位，CPU 从 cpu_resume 起来，中断处理逻辑根本没参与。IRQF_NO_SUSPEND 的 IRQ 在 suspend-to-idle 下有个特别行为：它在 suspend_device_irqs() 里没被 mask，所以能把 CPU 从 idle 拉出来，但它不是唤醒源，不会触发系统级唤醒（不会让 pm_wakeup_pending() 判 abort，只是让 CPU 跑一段）。素材原话：「这种信号并不会触发一个系统唤醒信号」。实际场景是标了 IRQF_NO_SUSPEND 的 timer 每秒报一次，CPU 每秒醒一下跑 tick 又睡。

版本说明：PM_SUSPEND_FREEZE 和 freeze_enter() 在 4.x 中期被重写，这条路径后来改成独立的 s2idle 状态机，suspend.c 里这段 goto 不再存在。具体版本点未验证。

十七、进程冻结要解决什么 #

进程冻结（freezing of tasks）：在 suspend 或 hibernate 之前，把用户进程和一部分内核线程推进一个「可控的暂停状态」。可控是关键——不是随机在某条指令上停住，而是在内核明确认可的位置停下，并且内核知道它停下了。

不冻结也能睡，但会出四个问题。文件系统会被写坏：从创建 hibernate image 到 CPU down 有一段时间，这期间还有进程写文件系统，镜像记录的不是一致状态，恢复之后对不上，fsck 都救不回来。hibernate image 会创建失败：做镜像要足够内存，这期间还有进程申请内存，可用页减少，镜像做不出来。干扰设备的 suspend 和 resume：cpu_down 之前是设备 suspend 阶段，这期间进程还在访问设备、抢竞争资源（同一个 i2c 总线、同一个 regulator），设备回调就会拿到不该拿的返回值，或者卡死。

第四个问题最容易忽略：进程会「感知」到休眠。理想状态是休眠对所有任务透明，但有些进程依赖系统状态——一个要所有 CPU online 才肯干活的进程，在 nonboot CPU 被 offline 的窗口里会跑出异常结果；一个依赖 monotonic clock 单调递增的进程，在 suspend 期间时钟停走会看到时间倒流。很多「睡一觉之后应用行为异常」的 bug 根因就在这儿。冻结把它变成「根本没运行」，比「运行了但结果不对」好处理。

十八、冻结的逻辑：fake signal 与 PF_FROZEN #

用户进程默认可以冻结，靠的是借信号机制的力。入口是 fake_signal_wake_up()，名字里的 fake 是字面意思：

c
void fake_signal_wake_up(struct task_struct *p)
{
	unsigned long flags;
	if (lock_task_sighand(p, &flags)) {
		signal_wake_up(p, false);
		unlock_task_sighand(p, &flags);
	}
}

signal_wake_up() 只做一件事：置 TIF_SIGPENDING，然后唤醒任务。不投递任何信号，sigpending 集合是空的。任务被唤醒后，返回用户态之前的内核出口（do_signal() 那段）发现 TIF_SIGPENDING 置位，进信号处理流程，get_signal() 里先调 try_to_freeze()。

为什么用信号机制而不是在调度器里插钩子？因为信号机制是「用户态可见」的唯一天然返回点。进程只有在这儿才处于内核认可的状态：系统调用都返回了、锁都释放了、没有任何内核内部状态挂着。在这儿停住是安全的。在内核任意位置强制停住，就要处理「它正拿着一把锁」，那是另一个复杂度量级。真正把任务停住的是 __refrigerator()（refrigerator 冰箱，内核里的戏称）：

c
bool __refrigerator(bool check_kthr_stop)
{
	unsigned int save = get_current_state();
	bool was_frozen = false;
	WARN_ON_ONCE(current->flags & PF_FROZEN);
	WARN_ON_ONCE(!current->mm && current->pid != 0);
	spin_lock_irq(&freezer_lock);
	current->flags |= PF_FROZEN;
	if (!freezing(current) ||
	    (check_kthr_stop && kthread_should_stop()))
		current->flags &= ~PF_FROZEN;
	spin_unlock_irq(&freezer_lock);
	if (!(current->flags & PF_FROZEN))
		goto out_reset;
	for (;;) {
		set_current_state(TASK_UNINTERRUPTIBLE);
		spin_lock_irq(&freezer_lock);
		current->flags |= PF_FROZEN;
		if (!freezing(current) ||
		    (check_kthr_stop && kthread_should_stop()))
			current->flags &= ~PF_FROZEN;
		spin_unlock_irq(&freezer_lock);
		if (!(current->flags & PF_FROZEN))
			break;
		was_frozen = true;
		schedule();
	}
	...
}

关键点：PF_FROZEN 在释放 freezer_lock 之前置位。这是防一个经典竞态——如果先置位再放锁，thaw 逻辑会在你真正睡下去之前把标志清掉，于是 schedule() 之后你以为被冻住，实际条件已经变了。所以循环里每次 schedule() 醒来都要重新查一遍。set_current_state(TASK_UNINTERRUPTIBLE) 决定了冻结的任务不响应信号——冻结期间不该被 kill -9 打断，否则 thaw 时状态对不上。WARN_ON_ONCE(!current->mm && current->pid != 0) 抓的是「内核线程走了用户进程冻结路径」这个错误，pid 0 是 swapper，本来就没 mm，豁免。

判断要不要冻结，两头看。快路径 freezing() 只判一句 if (likely(!atomic_read(&system_freezing_cnt))) return false;——system_freezing_cnt 是全局计数，系统没进冻结时是 0，这一句就把所有检查挡掉了，调度器热路径上不留额外开销。否则进慢路径：

c
bool freezing_slow_path(struct task_struct *p)
{
	if (p->flags & PF_NOFREEZE)
		return false;
	if (pm_nosig_freezing || cgroup_freezing(p))
		return true;
	if (pm_freezing && !(p->flags & PF_KTHREAD))
		return true;
	return false;
}

三条判定按顺序：PF_NOFREEZE 置位就是不冻（免死金牌）；pm_nosig_freezing 或 cgroup_freezing(p) 就是冻（前者是「连内核线程一起冻」，后者是「这个 cgroup 被要求冻结」）；pm_freezing 且不是内核线程就是冻（常规路径）。

标记系统冻结状态的三个全局变量：

变量 位置 含义 置位 清零
pm_freezing kernel/power/process.c 冻结用户进程 freeze_processes() thaw_processes()
pm_nosig_freezing kernel/power/process.c 连内核线程和 workqueue 一起冻 freeze_kernel_threads() thaw_kernel_threads()
system_freezing_cnt kernel/freezer.c 系统已进入冻结，快路径判据 随上面两个一起 对称的 thaw 路径

system_freezing_cnt 是快路径唯一判据，必须在 pm_freezing/pm_nosig_freezing 置位之前涨上去，在它们清零之后才降下来。顺序错了会有一个窗口：pm_freezing 已置位但计数还是 0，此时 freezing() 返回 false，任务跑掉了。

十九、freezer 的代码框架 #

冻结入口在 kernel/power/process.c，suspend_prepare() 里调 freeze_processes()，成功后再 suspend_freeze_processes()（freeze_kernel_threads() 的包装）。两步走：先冻用户进程，再冻内核线程。顺序有讲究——用户进程还在给内核线程派活，得先把生产者停了。freeze_processes() 的骨架：

c
int freeze_processes(void)
{
	int error, oom_kills_saved;
	error = __usermodehelper_disable(UMH_FREEZING);
	if (error)
		return error;
	/* Make sure this task doesn't get frozen */
	current->flags |= PF_SUSPEND_TASK;
	if (!pm_freezing)
		atomic_inc(&system_freezing_cnt);
	pm_wakeup_clear(true);
	pm_freezing = true;
	oom_kills_saved = oom_kill_disable;
	error = try_to_freeze_tasks(true);
	if (!error)
		__usermodehelper_set_disable_depth(UMH_DISABLED);
	BUG_ON(in_atomic());
	/* 冻结之后关 OOM killer，避免杀掉冻住的任务导致死锁 */
	if (!error && !oom_kills_saved && !sigs_found)
		pm_set_oom_killer_disabled(true);
	return error;
}

current->flags |= PF_SUSPEND_TASK：发起 suspend 的任务（一般是 systemd-sleep）不能被自己冻住，否则彻底卡死。__usermodehelper_disable(UMH_FREEZING)：usermode helper 是内核派出去跑用户态程序（/sbin/hotplug、/sbin/modprobe）的机制，冻进程时这些也得停，不然刚冻完又冒出来一个。pm_wakeup_clear(true) 清 wakeup_count 的记账，属于框架层。pm_set_oom_killer_disabled(true)：冻结期间关掉 OOM killer——冻结本身占内存，万一触发 OOM，内核会去杀一个已经冻住的任务，那任务没法响应，直接死锁；这个行为在 4.x 中期才加进来，3.x 没有，具体版本未验证。BUG_ON(in_atomic()) 抓「在原子上下文里调 suspend」的错误，调 freeze_processes() 时不能持锁、不能关中断。真正干活的是 try_to_freeze_tasks()：

c
static int try_to_freeze_tasks(bool user_only)
{
	struct task_struct *g, *p;
	unsigned long end_time;
	unsigned int todo;
	bool wq_busy = false;
	...
	end_time = jiffies + msecs_to_jiffies(freeze_timeout_msecs);	if (!user_only)
		freeze_workqueues_begin();
	while (true) {
		todo = 0;
		read_lock(&tasklist_lock);
		for_each_process_thread(g, p) {
			if (p == current || !freeze_task(p))
				continue;
			if (!freezer_should_skip(p))
				todo++;
		}
		read_unlock(&tasklist_lock);
		if (!user_only) {
			wq_busy = freeze_workqueues_busy();
			todo += wq_busy;
		}
		if (!todo || time_after(jiffies, end_time))
			break;
		if (pm_wakeup_pending()) {
			wakeup = true;
			break;
		}
		if (todo)
			cancel_freezing(p);
		usleep_range(sleep_usecs / 2, sleep_usecs);
		sleep_usecs <<= 1;	/* 指数退避，上限约 20ms */
	}
	...
	return todo ? -EBUSY : 0;
}

流程是「扫描—试冻—等—重扫」的循环：遍历所有任务，对可冻的调 freeze_task()（发 fake signal，任务在下次返回用户态时自己走进 __refrigerator()）；统计还欠多少个（todo）；非 0 就 usleep_range() 等一下再扫，等待时间从 1ms 起指数翻倍；超时或 pm_wakeup_pending() 判真就跳出。cancel_freezing() 在重试路径上把还在 pending 的任务撤回，避免已经决定放弃之后它才冻住。freezer_should_skip() 过滤掉「已经冻住且 TASK_UNINTERRUPTIBLE」的任务，不记欠账。那个「20 秒超时」来自 freeze_timeout_msecs，可以调（cat /sys/power/pm_freeze_timeout 看，echo 5000 > /sys/power/pm_freeze_timeout 调短）。卡住时内核打印 Freezing of tasks failed after 20.000 seconds (1 tasks refusing to freeze)，同时把那个任务的名字和栈打出来。这就是你要查的进程。

内核线程和 workqueue 那一半走另一条路。内核线程不经过 do_signal()，fake signal 对它无效，只能指望它自己配合：

c
static bool kthread_freezable_should_stop(bool *was_frozen)
{
	bool frozen = false;
	might_sleep();
	if (unlikely(freezing(current)))
		frozen = __refrigerator(true);
	if (was_frozen)
		*was_frozen = frozen;
	return kthread_should_stop();
}

内核线程主循环里调这个函数，发现系统在冻结就自己进冰箱。__refrigerator(true) 那个 true 是 check_kthr_stop，顺便检查 kthread 有没有被要求停止——这是它唯一能响应 kthread_stop() 的机会，因为它冻在 TASK_UNINTERRUPTIBLE 里不接受信号。只有创建时标了 freezable 的内核线程才会调这个，绝大多数内核线程靠 PF_NOFREEZE 保护自己。

workqueue 靠 max_active：freeze_workqueues_begin() 把所有 wq 的 max_active 设成 0，新 work 不能入队，待处理的延后；freeze_workqueues_busy() 检查有没有正在执行的 work，有就欠账继续等。这块在 4.x 也重构过，具体差异未验证。

二十、冻结的顺序与不可冻结的进程 #

text
suspend_prepare()
  +- freeze_processes()
  |    +- usermodehelper 停止接受新任务
  |    +- system_freezing_cnt++, pm_freezing = true
  |    +- try_to_freeze_tasks(user_only=true)
  |    +- OOM killer 关闭
  +- suspend_freeze_processes() -> freeze_kernel_threads()
  |    +- pm_nosig_freezing = true
  |    +- try_to_freeze_tasks(user_only=false)
  |    +- freeze_workqueues_begin()
  +- suspend_thaw_processes()  -> thaw_kernel_threads()

第一步和第二步之间不能有空档。用户进程冻住了内核线程还在跑是安全的；反过来内核线程冻住了用户进程还在跑，就会出现「用户态发起系统调用但没人处理」的僵局。顺序是死的。

不可冻结的进程分几类：

类别 靠什么免疫 说明
发起 suspend 的任务本身 PF_SUSPEND_TASK 冻住自己就再也醒不来
swapper / idle（pid 0） PF_NOFREEZE 每个 CPU 的 idle 任务
kthreadd（pid 2） PF_NOFREEZE 所有内核线程的父，得活着才能派新线程
部分 workqueue worker PF_NOFREEZE + WQ_FREEZABLE 未置位 明确声明不可冻的 wq
PM 相关内核线程 PF_NOFREEZE 一类
没标 freezable 的普通内核线程 默认不可冻 要冻得显式声明
带 PF_NOFREEZE 的任何任务 freezing_slow_path() 第一行 直接判据

PF_KTHREAD 和 PF_NOFREEZE 是两回事，别混。前者表明「我是内核线程」，用于区分冻结条件；后者表明「我不要被冻」。一个内核线程可以既有 PF_KTHREAD 又没有 PF_NOFREEZE（那就是 freezable 的），也可以两者都有。

PF_SUSPEND_TASK 给「执行 suspend 的那个任务」用，在 freeze_processes() 里置位，thaw_processes() 结束时清掉。规则是「谁开的口谁不下水」。更深的原因是：suspend_prepare() 之后整条调用链都跑在这个任务上，从 dpm_suspend() 一路到 suspend_ops->enter()。它要是冻在 __refrigerator() 里，suspend_ops->enter() 永远调不到，系统既没睡也没醒。

还有一对宏要单独讲，freezer_do_not_count() / freezer_count()：

c
#define freezer_do_not_count()		do { current->flags |= PF_FREEZER_SKIP; } while (0)
#define freezer_count()	do { \
		clear_bit(PF_FREEZER_SKIP, &current->flags); \
		if (unlikely(freezing(current))) \
			try_to_freeze(); \
	} while (0)

PF_FREEZER_SKIP 的语义不是「我不冻」，而是「暂时别把我算进冻结欠账」。try_to_freeze_tasks() 在统计 todo 时会把带这个位的任务跳过，于是它卡在一个不可中断睡眠里也不会拖慢冻结流程。

典型用法是 wait_for_completion() 一类的等待：进程要睡在一个不可中断的等待队列上，这段时间它本来就没法响应 fake signal。如果被计入欠账，冻结时间会被这个正常的等待拖长，甚至超时报 refusing to freeze。所以进等待前 freezer_do_not_count()，出来后 freezer_count()——后者在清位之后立刻补一次 try_to_freeze()，保证这段时间欠下的冻结请求不会漏掉。

注意这与 PF_NOFREEZE 的区别：PF_FREEZER_SKIP 是临时的、有进有出的，PF_NOFREEZE 是永久的。freezer_count() 里那句 if (unlikely(freezing(current))) try_to_freeze(); 就是补账，漏了它这个任务会一直跑到 thaw。

二十一、thaw 的逆过程 #

thaw 是冻结的镜像，方向反了：先解内核线程，再解用户进程。

c
void thaw_processes(void)
{
	struct task_struct *g, *p;
	struct task_struct *curr = current;
	if (pm_freezing)
		atomic_dec(&system_freezing_cnt);
	pm_freezing = false;
	pm_nosig_freezing = false;
	oom_killer_enable();
	pr_info("Restoring tasks ... ");
	/* clear the PF_SUSPEND_TASK flag set in freeze_processes() */
	curr->flags &= ~PF_SUSPEND_TASK;
	usermodehelper_enable();
	thaw_workqueues();
	read_lock(&tasklist_lock);
	for_each_process_thread(g, p) {
		/* No other threads should have PF_SUSPEND_TASK set */
		WARN_ON((p != curr) && (p->flags & PF_SUSPEND_TASK));
		__thaw_task(p);
	}
	read_unlock(&tasklist_lock);
	WARN_ON(!(curr->flags & PF_SUSPEND_TASK));
	WARN_ON(in_atomic());
	pr_cont("done.\n");
}

__thaw_task() 干两件事：

c
void __thaw_task(struct task_struct *p)
{
	unsigned long flags;
	spin_lock_irqsave(&p->sighand->siglock, flags);
	if (WARN_ON_ONCE(freezing(p)))
		goto unlock;
	if (lock_task_sighand(p, &flags)) {
		p->flags &= ~PF_FROZEN;
		wake_up_state(p, TASK_UNINTERRUPTIBLE);
		unlock_task_sighand(p, &flags);
	}
unlock:
	spin_unlock_irqrestore(&p->sighand->siglock, flags);
}

清 PF_FROZEN，然后 wake_up_state(p, TASK_UNINTERRUPTIBLE) 把任务唤醒。任务在 __refrigerator() 的 schedule() 里醒来，回到循环发现 PF_FROZEN 没了，break 出去，从 try_to_freeze() 返回 false，继续正常信号处理流程，最终返回用户态接着跑。WARN_ON(!(curr->flags & PF_SUSPEND_TASK)) 这个断言有点意外——保证进来 thaw 的确实是当初发起 freeze 的那个任务。thaw_workqueues() 恢复 max_active，让 work 重新能入队，位置在遍历任务之前。

冻结失败（20 秒超时）也要 thaw。已经冻住的那部分必须解冻，否则系统卡在半冻结状态，echo mem 失败但系统也不正常，suspend_prepare() 的 Thaw: 标签就是干这个的。为什么先内核线程后用户进程？用户进程解冻后会立刻发起系统调用，这些调用需要内核线程和 workqueue 处理。反过来先解用户进程，它会撞上还没解冻的 workqueue 卡在那儿。

二十二、冻结与中断唤醒的配合：为什么必须先冻结再睡 #

两件事在这儿才真正接上。三层顺序：冻结必须先于设备 suspend，设备 suspend 必须先于关中断。冻结在设备 suspend 之前，因为设备 suspend 阶段要访问硬件，有用户进程同时在用同一个设备就会争抢，冻结把「外部干扰」这个变量彻底消掉。设备 suspend 在关中断之前，因为设备回调（尤其 suspend_noirq）里要等待中断或 sleep。关中断在 CPU 下电之前，这是硬件要求，第五章那个 A55 流程写着。任何一层反了都会出问题。

真正的难点在唤醒之后。回忆第十三章：唤醒中断进来后 handler 被延后，走 check_irq_resend() → tasklet → 软中断上下文。这段时间里系统已经 resume 完、进程也 thaw 完，pm_wakeup_pending() 随时会判假，系统准备再睡一次。如果你的 handler 想做的事儿还没做完，系统睡回去，事情就丢了。这就是素材里那个问题的内核版：重压按键屏幕不亮，波形有，系统确实醒了，handler 也跑了，但 queue 的 delayed work 还没调度，系统又睡了。内核只保证两层：

保证层 机制 覆盖范围
hardirq handler IRQD_IRQ_INPROGRESS + synchronize_irq() handler 函数体执行完
threaded handler threads_active + synchronize_irq() thread_fn 执行完
workqueue 无 不保证

synchronize_irq() 的实现：

c
void synchronize_irq(unsigned int irq)
{
	struct irq_desc *desc = irq_to_desc(irq);
	if (desc) {
		__synchronize_hardirq(desc);
		/*
		 * We made sure that no hardirq handler is
		 * running. Now verify that no threaded handlers are
		 * active.
		 */
		wait_event(desc->wait_for_threads,
			   !atomic_read(&desc->threads_active));
	}
}

__synchronize_hardirq() 死等 IRQD_IRQ_INPROGRESS 归零（这个位在 handle_irq_event() 开头置位、结尾清除，所以循环返回意味着 hardirq handler 一定不在跑了），做法是 while (irqd_irq_inprogress(...)) cpu_relax(); 加锁复查，没干净就再来一轮。threaded handler 靠 threads_active，__handle_irq_event_percpu() 里调 __irq_wake_thread() 唤醒 irq 线程：

c
void __irq_wake_thread(struct irq_desc *desc, struct irqaction *action)
{
	/*
	 * In case the thread crashed and was killed we just pretend that
	 * we handled the interrupt. The hardirq handler has disabled the
	 * device interrupt, so no irq storm is lurking.
	 */
	if (action->thread->flags & PF_EXITING)
		return;
	/*
	 * Wake up the handler thread for this action. If the
	 * RUNTHREAD bit is already set, nothing to do.
	 */
	if (test_and_set_bit(IRQTF_RUNTHREAD, &action->thread_flags))
		return;
	desc->threads_oneshot |= action->thread_mask;
	atomic_inc(&desc->threads_active);
	wake_up_process(action->thread);
}

threads_active 加一，唤醒 irq_thread；irq_thread() 跑完 thread_fn 后减一；wait_event() 等到归零说明全跑完。irq 线程在 setup_irq_thread() 里创建，SCHED_FIFO，优先级 MAX_USER_RT_PRIO/2（secondary 的低一档），线程名 irq/<号>-<name>，ps 里直接能看到。所以 msleep(1000) 在 threaded handler 里不会导致没跑完就睡——synchronize_irq() 等 threads_active 归零，msleep() 期间它还是 1。

delayed work 就会。内核不管 workqueue，这是 mod_delayed_work() 型防抖驱动的经典坑。原始写法：

c
static void gpio_keys_gpio_work_func(struct work_struct *work)
{
	struct gpio_button_data *bdata =
		container_of(work, struct gpio_button_data, work.work);
	gpio_keys_gpio_report_event(bdata);
}
static irqreturn_t gpio_keys_gpio_isr(int irq, void *dev_id)
{
	struct gpio_button_data *bdata = dev_id;
	mod_delayed_work(system_wq,
			 &bdata->work,
			 msecs_to_jiffies(bdata->software_debounce));
	return IRQ_HANDLED;
}

software_debounce 设成 20ms，按下按键 → 中断 → 排 delayed work → synchronize_irq() 立刻返回（handler 已跑完）→ 系统睡回去 → 20ms 的 timer 永远不触发（CPU 断电）→ 键值丢了。第二次按键才报第一次的。普通 work 里 msleep() 也一样危险：work 已经跑起来，msleep() 期间系统判定「没有理由不睡」，睡下去，后面的代码等下次唤醒才执行。

解法是 pm_stay_awake() / pm_relax() 成对，即在上面两个函数里各加两行：

c
	/* work_func 尾部 */
	if (bdata->button->wakeup)
		pm_relax(bdata->input->dev.parent);
	/* isr 开头 */
	if (bdata->button->wakeup)
		pm_stay_awake(bdata->input->dev.parent);

handler 一进 pm_stay_awake()，设备对应的 wakeup_source 就 active，combined_event_count 变了，pm_wakeup_pending() 判真，系统不睡；work 里 pm_relax() 之后再放行。这两个函数的计数语义、combined_event_count 怎么变，全部在《Suspend 流程与唤醒事件框架》，这里只用不拆。实践原则：中断唤醒设备的 handler 里，凡是延后执行的部分，都要用 pm_stay_awake() 护住。 从 handler 进门到实际干完活，中间不能有窗口。搞不清护多久就护长一点，多醒几毫秒的功耗代价跟「按键丢了一次」不是一个量级。

二十三、一次完整的「按键唤醒」时序 #

设备是 gpio-keys，边沿触发，走 dev_pm_set_wake_irq() 路径。

text
[休眠态]  CPU 断电，DRAM 自刷新，GIC 保留唤醒输入，PMU 监听 wake_request
 1  用户按下按键，GPIO 引脚电平变化
 2  SoC 的 GPIO 控制器（或 sysirq）检测到边沿，唤醒寄存器已使能
      -> 向 GIC 输出中断信号
 3  GIC 收到该 SPI，判为已使能的唤醒中断，拉 wake_request
 4  PMU 收到 wake_request，上电：电源轨 -> 时钟 -> 释放 CPU 复位
 5  CPU 从 RVBAR 取指，跑 ATF 复位代码，跳 cpu_resume
      恢复 MMU、页表基址、栈、callee-saved 寄存器
 6  syscore_resume()：GIC 寄存器恢复、gpio/clk 控制器恢复
 7  arch_suspend_enable_irqs()   <- local_irq_enable()
 8  pending 中断冲进来：handle_edge_irq() -> irq_may_run() 看到 ARMED
      -> irq_pm_check_wakeup()：清 ARMED，置 SUSPENDED|PENDING，disable
      -> 返回 false，handler 未执行        <- 这次中断只负责"报信"
 9  enable_nonboot_cpus()
10  dpm_resume_noirq()：i2c/spi resume_noirq，然后 resume_device_irqs()
      -> __enable_irq() 清 SUSPENDED -> check_irq_resend()
           -> set_bit(irq, irqs_resend) -> tasklet_schedule()
11  tasklet 在软中断上下文执行 resend_irqs()
      -> handle_irq_event() -> gpio_keys_gpio_isr()   <- handler 终于跑了
           pm_stay_awake(dev) / mod_delayed_work()
12  dpm_resume_early() -> dpm_resume() -> dpm_complete()
13  thaw_processes()  解冻所有用户进程
14  delayed work 到期：report_event() -> input 上报 -> pm_relax(dev)
15  应用 read() 拿到键值

三个时间点记牢。第 8 步和第 11 步之间隔着 enable_nonboot_cpus() + dpm_resume_noirq()，这段时间 handler 一次都没跑。第 11 步在软中断上下文，不能 msleep()。第 13 步 thaw 在第 11 步之后，所以 handler 跑的时候用户进程还是冻住的——handler 里要依赖某个用户进程配合，那就说明设计有问题。

电平触发走另一条路：第 10 步的 check_irq_resend() 里 irq_settings_is_level() 判真，清 IRQS_PENDING 直接返回。因为电平还在，中断重新 enable 后硬件会再报一次，那一次走完整的 handle_edge_irq() → irq_may_run() 返回 true → handle_irq_event()，在真正的硬中断上下文。

排查「莫名自唤醒」的第一步是 /sys/power/pm_wakeup_irq：

bash
cat /sys/power/pm_wakeup_irq    # 最近一次醒来的唤醒源 IRQ 号

拿这个号去 /proc/interrupts 里对照，就知道是哪个设备把你叫醒的。

二十四、易错点速查 #

现象 原因 处理
休眠电流偏高几百微安 enable_irq_wake() 多调了一次，wake_depth 归不了零 只走 dev_pm_set_wake_irq() 一条路径
WARN: Unbalanced IRQ N wake disable disable_irq_wake() 比 enable 多调了 检查 suspend 的错误分支，early return 前补 disable
系统睡得下叫不醒 平台 chip 没实现 irq_set_wake，或 dts 少了唤醒配置 确认 IRQD_WAKEUP_STATE 有没有置位，看平台 sysirq
醒了但按键没反应 handler 里排的 delayed work 没等到就睡了 pm_stay_awake() / pm_relax() 成对
第二次按键才报第一次的值 同上，防抖时间越长越容易 同上
nobody cared (try booting with irqpoll) IRQF_NO_SUSPEND + suspend 期间 handler 返回 IRQ_NONE 加 IRQF_COND_SUSPEND，或 handler 里判电源状态
Freezing of tasks failed after 20.000 seconds 某进程卡在不可中断睡眠里不出来 看 dmesg 里的进程名，修那个驱动的可中断性
唤醒中断 handler 里 msleep() 报 BUG 边沿触发下 handler 在软中断上下文 用 request_threaded_irq()
加了 WARN_ON(1) 却没打出来 第一次唤醒中断不执行 handler 正常现象，见第十三章
/sys/power/pm_wakeup_irq 是 0 RTC 或 PMU 直接唤醒，没走 IRQ 路径 查 RTC alarm 配置
GIC 断电后中断全乱 平台没在 syscore_ops 里保存恢复 GIC 检查 GIC 驱动的 gic_suspend/gic_resume
suspend-to-idle 功耗下不去 IRQF_NO_SUSPEND 的定期中断把 CPU 一直捅醒 用 wakeup source 的 timer 精确算下次唤醒

几条驱动侧的原则收个尾。

唤醒源声明统一走一条路：probe 里 device_init_wakeup() + dev_pm_set_wake_irq()，i2c/spi 设备直接在 dts 加 wakeup-source。别在 suspend()/resume() 里手调 enable_irq_wake()，除非你有明确理由。

别在驱动 suspend() 里关中断、resume() 里开中断。suspend_device_irqs() / resume_device_irqs() 已经统管了，你自己再管一遍只会多一层嵌套。

触发类型从 dts 拿，别硬编码：

c
irq = platform_get_irq(pdev, 0);
flags = irqd_get_trigger_type(irq_get_irq_data(irq));
ret = request_threaded_irq(irq, NULL, my_thread_fn,
			   flags | IRQF_ONESHOT, "mydrv", priv);

4.x 后期更简单，irqflags 传 0，request_threaded_irq() 内部会自己调 irqd_get_trigger_type()。看内核版本决定。

中断下半部用 workqueue 就必须 pm_stay_awake()/pm_relax() 成对，这条没有例外。IRQF_NO_SUSPEND 是最后手段，只有 timer、IPI、PMIC 这类系统基础设施才考虑，外设驱动用它就是在赌「suspend 期间不会有中断进来」。
