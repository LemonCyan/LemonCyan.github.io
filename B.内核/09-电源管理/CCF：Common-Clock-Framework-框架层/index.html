一、CCF 解决什么问题：一颗 SoC 里成百上千个时钟 #

随便挑一颗能跑 Linux 的 SoC，翻开 spec 的 clock 章节，你会看到一张能贴满一面的树状图。图上的器件分这几类：

  • Oscillator：有源振荡器，自己起振。
  • Crystal：无源晶振，要配合 SoC 内部的振荡电路。
  • PLL：锁相环，把低频晶振倍到几百 MHz 到几 GHz。
  • Divider：分频器，把 PLL 的输出降下来。
  • Mux：多路选择器，从几个候选源里挑一个接到下游。
  • Gate：与门，实质就是开关，用来做 clock gating 省电。
  • 末端有具体功能的 HW block：UART、MMC、SPI、LCD、GPU……

在引入 CCF 之前，各个架构各干各的。ARM 有 mach-xxx/clock.c 里私有的 struct clk，一个平台一份实现，API 名称和语义都对不上，驱动没法跨平台复用，runtime PM 也接不进去。CCF 做的事情是：把这套东西统一成一棵由内核维护的时钟树，向上给驱动一套稳定的 API，向下给平台一套回调接口。

CCF 的管理对象，只有三件事（每一件事都不是所有 clock 都支持）：

能力 说明 对应 API
enable / disable 开和关，本质是 gate clk_enable / clk_disable
设置频率 改 rate，靠改分频比或改 parent clk_set_rate
选择 parent mux 换输入源 clk_set_parent

再加两条辅助能力：查询（clk_get_rate / clk_round_rate / clk_get_parent）和相位（clk_set_phase / clk_get_phase，很多平台不实现）。

CCF 的三个职能，可以这样切：

  1. 向其它 driver 提供操作 clock 的通用 API。
  2. 实现 clock 控制的通用逻辑，这部分和硬件无关。
  3. 把和硬件相关的控制逻辑抽象成函数集（clk_ops），由平台开发者填，由通用逻辑调用。

这是任何一个内核 framework 的标准三层切法，看懂一层就懂一片。

二、CCF 的四类参与者 #

CCF 的 block diagram 上有四类角色，缺一不可。

参与者 是什么 代码形态 谁负责写
HW clock device 真实的时钟器件：晶振、PLL、divider、mux、gate DTS 中的一个 node（或一个 controller node 掩藏多个器件） 硬件工程师描述拓扑，软件工程师写成 DTS
HW-specific clock provider driver 驱动这些器件、直接读写寄存器的那层 struct clk_hw + struct clk_ops 回调 平台/SoC clock driver 开发者
CCF 模块本体 与硬件无关的通用逻辑：建树、计数、传播、通知 drivers/clk/clk.c 里的 struct clk_core 内核维护者
clock consumer driver 用时钟的外设驱动：UART、MMC、I2C…… 调 clk_get / clk_prepare_enable 的普通驱动 各子系统驱动开发者

几个容易踩的概念点：

  • provider 和 consumer 不是互斥身份。 一个 PLL 既是 provider（输出 clock）又是 consumer（输入来自晶振）。只有树根（Oscillator / Crystal）是纯 provider。
  • clock controller 是个虚拟设备。 很多 SoC 把几百个 clock 塞进一个寄存器块，用一个 DTS node 表示，用 #clock-cells = <1> 加一个 ID 区分输出。这时这个 node 对应的 driver 一口气注册几百个 clock。
  • consumer 对 clock 没有控制权。 末端 HW block 只是「享用」这个时钟源。datasheet 里写的「本模块 clock gating」，那个 gate 在软件上要独立成一个中间节点，不是末端模块的一部分。这条在移植时最容易含糊。

四、HW clock device：设备树里的时钟描述 #

从硬件角度，系统的 clock distribution 是一棵树，但和文件系统树有两点不同：clock tree 有多个根（晶振、外部时钟输入各是一个根，所以实际上是森林），而且中间节点是 PLL / divider / mux / gate，叶节点是消耗时钟的外设。DTS 描述这套拓扑有两种写法，风格差得很远。

写法一：一个大 controller。 把整个 SoC 的 clock 子系统当成一个虚拟设备：

dts
/* arch/arm/boot/dts/exynos4210.dtsi */
clock: clock-controller@0x10030000 {
        compatible = "samsung,exynos4210-clock";
        reg = <0x10030000 0x20000>;
        #clock-cells = <1>;
};

#clock-cells = <1> 表示这个 provider 有多个输出，引用时必须额外给一个 ID，consumer 侧写 clocks = <&clock 3>、<&clock 344> 这样。这种写法 DTS 很短，driver 里一堆 clk_register_xxx 挨个注册，没什么结构可言。

写法二：一个器件一个 node。 每个能输出时钟的器件都是一个 node，既是 provider 又是 consumer（根节点除外）。全志 sun4i 是这种风格的代表：

dts
/* arch/arm/boot/dts/sun4i-a10.dtsi 节选 */
clocks {
    osc24M: osc24M@01c20050 {           /* 根节点，纯 provider */
        #clock-cells = <0>;
        compatible = "allwinner,sun4i-osc-clk";
        reg = <0x01c20050 0x4>;
        clock-frequency = <24000000>;
    };
    osc32k: osc32k {                    /* 另一个根，固定 32.768kHz */
        #clock-cells = <0>;
        compatible = "fixed-clock";
        clock-frequency = <32768>;
    };
    pll1: pll1@01c20000 {               /* 既是 provider 又是 consumer */
        #clock-cells = <0>;
        compatible = "allwinner,sun4i-pll1-clk";
        reg = <0x01c20000 0x4>;
        clocks = <&osc24M>;
    };
    apb1_mux: apb1_mux@01c20058 {       /* mux：三选一 */
        #clock-cells = <0>;
        compatible = "allwinner,sun4i-apb1-mux-clk";
        reg = <0x01c20058 0x4>;
        clocks = <&osc24M>, <&dummy>, <&osc32k>;
    };
    apb1_gates: apb1_gates@01c2006c {   /* 多输出：cell 为 1 */
        #clock-cells = <1>;
        compatible = "allwinner,sun4i-apb1-gates-clk";
        reg = <0x01c2006c 0x4>;
        clocks = <&apb1>;
        clock-output-names = "apb1_i2c0", "apb1_i2c1", "apb1_i2c2",
            "apb1_can", "apb1_scr", "apb1_ps20", "apb1_ps21",
            "apb1_uart0", "apb1_uart1", "apb1_uart2", "apb1_uart3",
            "apb1_uart4", "apb1_uart5", "apb1_uart6", "apb1_uart7";
    };
};

属性含义：

属性 挂在哪 含义
#clock-cells provider 节点 0 表示引用时只写 phandle；1 表示还要给一个输出 ID
clock-frequency 固定频率 provider 频率值（Hz），改板不用改代码，只改 DTS
clock-output-names 多输出 provider 给每个输出起名字，只给 provider driver 自己用，consumer 看不见
clock-indices 多输出 provider 输出 ID 不连续时把 ID 映射到 clock-output-names 的下标（4.x，具体版本未验证）
clocks provider 和 consumer 都有 输入时钟列表，每项是 phandle + 若干 cell
clock-names 基本只在 consumer 侧用 给 clocks 里每一项配名字，驱动按名字拿

clock-output-names 值得多说一句：它只服务于 provider 的编程便利。provider driver 注册 clock 时用这些名字去查 parent，从而把 DTS 上的拓扑连成 parent_names 字符串数组；consumer 引用该 provider 的输出，用的是 phandle + ID，不是字符串。搞混了会写出一堆查不到的 clock。另外 osc24M 这个命名被原作者自己吐槽过：名字里带频率，改板改频率就得改名字，consumer 引用也得跟着改，clock 命名用功能名才对。

五、HW-specific clock provider driver #

真正和寄存器打交道的一层。素材原文强调「provider drivers」，因为系统里往往有好几个：一个管 PLL，一个管 system clock，一个管外设 gate。

这一层的内核抽象是 struct clk_hw（Linux 4.4 定义，include/linux/clk-provider.h）：

c
struct clk_hw {
	struct clk_core *core;                  /* (1) */
	struct clk *clk;                        /* (2) */
	const struct clk_init_data *init;       /* (3) */
};

这个结构三个成员的语义分别是：core 指向 CCF 里对应的 struct clk_core（两者严格一一对应，clk_core 里也有 hw 指回来，由 clk_register() 填，provider 不碰）；clk 是 provider 自己持有的访问句柄，同样由 clk_register() 生成；init 是注册时带进来的静态描述数据，注册完成后内容被全部拷走，这个指针本身就没用了。

版本注意： 素材第 3 篇里的 clk_hw 只有 clk 和 init 两个成员，那是 3.x 中期的形态；core 成员是 CCF 把内部结构抽成 clk_core 之后才有的（4.x，具体版本未验证）。以 4.4 为准，三个成员。

struct clk_init_data 是 provider 唯一需要自己填的东西：

c
struct clk_init_data {
	const char		*name;            /* (1) */
	const struct clk_ops	*ops;             /* (2) */
	const char		* const *parent_names;  /* (3) */
	u8			num_parents;
	unsigned long		flags;            /* (4) */
};
  1. clock 的名字，全局唯一是硬性要求（of_clk_get_parent_name 和 clk_core_lookup 都靠字符串匹配）。
  2. 回调函数集，第十九章展开。
  3. 所有候选 parent 的名字。这是 CCF 建树的唯一依据：CCF 不认识指针关系，只认识名字，注册时拿这些字符串去树上查。
  4. framework 级 flags，CLK_SET_RATE_PARENT 之类。

struct clk_hw 是基类，具体器件从它派生，以固定频率晶振为例：

c
struct clk_fixed_rate {
	struct		clk_hw hw;             /* 基类，必须放第一个成员 */
	unsigned long	fixed_rate;            /* 派生类特有字段 */
	unsigned long	fixed_accuracy;
	u8		flags;
};

基类必须放第一个成员，因为 CCF 回调里拿到的永远是 struct clk_hw *，provider 要靠 container_of 或强转取回派生结构，to_clk_divider()、to_clk_mux() 这些宏干的就是这件事。写平台 clock driver 的第一原则是能用派生类就别用基类：clk_gate / clk_divider / clk_mux / clk_fixed_factor / clk_composite 已经把寄存器读写、位域计算、锁写好了，你只填参数；手搓一个 clk_ops 实现 gate，除了引入 bug 没有第二种结果。

六、CCF 模块本身 #

CCF 核心的全部状态，靠两个全局 hlist 头撑起来（drivers/clk/clk.c 4.4）：

c
static HLIST_HEAD(clk_root_list);
static HLIST_HEAD(clk_orphan_list);

clk_root_list 挂所有置了 CLK_IS_ROOT flag 的 clock，链表上每个节点往下一展就是一棵树——硬件上 clock 森林有多个根，这条链表正好对应。clk_orphan_list 挂注册时有 parent 名字但 parent 还没注册的 clock，叫孤儿。有合法 parent 的 clock 挂进 parent->children 这个 hlist。

孤儿不是永远孤儿。__clk_init() 末尾有一段「扫孤儿」逻辑：每注册一个新 clock，就遍历 clk_orphan_list，凡是 parent 名字能对上这个新 clock 的，立刻 clk_core_reparent() 认领回去。所以注册顺序不重要，最终拓扑会自动收敛。

CCF 的两个核心数据结构：

结构 粒度 谁持有 定义位置
struct clk_core 一个硬件 clock device 一个 CCF 核心 drivers/clk/clk.c（内部）
struct clk 一次访问一个，一个 device 多个 consumer 和 provider 同上，对外只是不透明指针

这个「一个 core 对多个 clk」的设计是整个框架的地基，第九章起细讲。

七、clock consumer driver #

consumer driver 干三件事：probe 时拿到 clock 句柄，按需要设定 rate 和 parent，然后 prepare + enable 让外设跑起来；运行期按用户需求改参数，典型场景是 UART 改波特率、I2S 改采样率走 clk_set_rate，相机切时钟源走 clk_set_parent；再就是配合电源管理，suspend 时 clk_disable_unprepare、resume 时 clk_prepare_enable，更深一层是 runtime PM 把 clock 的开关和 domain 的开关绑在一起。

一个最小可用的 probe 片段：

c
static int foo_probe(struct platform_device *pdev)
{
	struct clk *clk;
	int ret;

	clk = devm_clk_get(&pdev->dev, "baud");
	if (IS_ERR(clk))
		return PTR_ERR(clk);
	ret = clk_prepare_enable(clk);
	if (ret)
		return ret;

	/* ... 初始化外设 ... */
	clk_disable_unprepare(clk);
	return 0;
}

devm_clk_get 出错一定要 PTR_ERR 往上抛，不要统一返回 -ENODEV，否则 probe defer 机制就断了（provider 还没注册时 of_clk_get 返回 -EPROBE_DEFER，这是正常的重试信号）。

八、clock tree：为什么必须是树 #

结论：不是「必须是树」，而是硬件本来就是树，软件只是照抄。一颗晶振接 PLL，PLL 后面并出几条总线，总线上再分频给外设。信号单向扇出，一个输出能驱动多个输入，一个输入只接一个上游源（mux 是「多选一」，不属于一对多），这种拓扑天然无环，就是森林。

既然是树，三个性质自动成立：enable 自底向上，clk_core_enable(core) 先递归 clk_core_enable(core->parent) 再调 core->ops->enable，失败反向回滚，所以 UART 驱动只要 enable 自己的时钟，PLL 会被连带开起来；rate 自顶向下，parent 的 rate 一变，一批 children 跟着变，靠 __clk_recalc_rates() 往下遍历整棵子树重算；引用计数按节点算，每个 clk_core 各有 enable_count / prepare_count，两个驱动开同一个 gate 计数到 2，关一次只减到 1，硬件不动。

为什么不用「按名字直接操作 7 个 clock」的平铺模型？因为它处理不了级联：hw2_clk 和 hw3_clk 都关了，pll2_clk 才能关。这个「才能」只有树能表达。代价是改一个上游节点会影响一片下游节点，于是内核里有了 CLK_SET_RATE_GATE（改 rate 时必须 gated）、CLK_SET_PARENT_GATE（换 parent 时同理）和 rate change notifier。

九、struct clk：一个时钟节点的抽象 #

struct clk 在 4.4 里是严格 internal 的，定义在 drivers/clk/clk.c，不在任何公开头文件中：

c
struct clk {
	struct clk_core	*core;         /* 指向真正的 clock device */
	const char *dev_id;           /* 谁在用（clkdev 遗留） */
	const char *con_id;           /* 用的哪个输入（clkdev 遗留） */
	unsigned long min_rate;       /* 这个 user 要求的下限 */
	unsigned long max_rate;       /* 这个 user 要求的上限 */
	struct hlist_node clks_node;  /* 挂进 core->clks */
};

关键点：不同的 user 访问同一个 clock device，共用同一个 clk_core，但各自有一个 struct clk。clk_get() 每次都新分配一个，clk->core = hw->core，再 hlist_add_head(&clk->clks_node, &hw->core->clks) 挂进去，max_rate 初始化成 ULONG_MAX。

为什么这么设计？看 min_rate / max_rate 就懂了：它们是 per-user 的。UART 要求时钟不低于 10 MHz，LCD 要求不高于 200 MHz，这两个约束挂在各自的 struct clk 上，clk_core_get_boundaries() 遍历 core->clks 取交集算出合法区间。对 consumer 来说 struct clk 完全不透明，头文件里只有前置声明，拿到的指针除了传给 CCF 的 API 之外不能解引用、不能比较内容（要比就用 clk_is_match()）。clk_put() 干的事就是 hlist_del(&clk->clks_node) + kref_put(&core->ref) + kfree(clk)，所以 get / put 必须成对。

三层结构的关系一张图说清：

text
   consumer A              consumer B
   struct clk A           struct clk B        ← 每 user 一个，带各自 min/max
       └──────────┬────────────┘
                  ▼
           struct clk_core                   ← 每 device 一个，树节点
              │        ▲
        ops   │        │ hw
              ▼        │
           struct clk_hw                     ← provider 的派生结构基类
                  │
              struct clk_foo（如 clk_divider）  ← 真实寄存器信息

十、struct clk_core：CCF 内部的另一层 #

clk_core 才是真正的 clock device 节点，定义同样在 drivers/clk/clk.c（4.4），全部字段按功能分六组：

组 字段 说明
身份 const char *name clock 名字，注册时 kstrdup 一份
const struct clk_ops *ops 硬件操作回调，来自 clk_init_data
struct clk_hw *hw 反向指针，指回派生结构
struct module *owner 所属模块，用于 try_module_get
拓扑 struct clk_core *parent 当前生效的 parent
const char **parent_names 所有候选 parent 的名字（拷贝）
struct clk_core **parents 候选 parent 的缓存指针数组
u8 num_parents 候选 parent 个数
struct hlist_head children 所有子节点
struct hlist_node child_node 挂进 parent->children 或 root/orphan list
bool orphan 是否孤儿（上游还没注册）
状态 unsigned int enable_count 开关引用计数
unsigned int prepare_count prepare 引用计数
unsigned long rate 缓存的实际频率
unsigned long req_rate 用户请求的频率（不一定等于 rate）
unsigned long accuracy 精度，单位 ppb，0 表示无误差
int phase 相位，单位度
约束 unsigned long flags framework 级 flags
unsigned long min_rate / max_rate 硬件自身约束上下限

struct clk_core *new_child 变更期新增的子节点
关联 struct hlist_head clks 所有访问过它的 struct clk
unsigned int notifier_count 注册的 rate 变更通知者数量
struct kref ref 引用计数，最后一个 clk_put 时释放
调试 struct dentry *dentry / struct hlist_node debug_node 仅 CONFIG_DEBUG_FS 下存在

三个容易误解的字段：

  • rate vs req_rate：rate 是「硬件现在实际是多少」，clk_get_rate() 返回它；req_rate 是「上次用户要求多少」。两者可以不等，分频比是离散的，你要 115200 的波特率时钟，硬件给的是 115384。
  • parents 是缓存。注册时 num_parents > 1 才分配，查不到就留 NULL，下次访问时再懒加载（clk_core_get_parent_by_index）。缓存的原因很直接：clk_core_lookup 是遍历链表 + 字符串比较，mux 每次换路都查一遍太贵。
  • min_rate / max_rate 是硬件自身约束，per-user 的 clk->min_rate / clk->max_rate 是另一套，两者在 clk_core_get_boundaries() 里合并。

十一、clk 的父子关系与 rate 传播 #

父子关系不是「设」出来的，是查出来的。注册时你只给了 parent 的名字，CCF 自己去找，查找发生在 __clk_init_parent()（drivers/clk/clk.c 4.4）：

c
static struct clk_core *__clk_init_parent(struct clk_core *core)
{
	struct clk_core *ret = NULL;
	u8 index;

	if (!core->num_parents)
		return NULL;
	/* 只有一个候选 parent：按名字查，查不到就是孤儿 */
	if (core->num_parents == 1) {
		if (IS_ERR_OR_NULL(core->parent))
			core->parent = clk_core_lookup(core->parent_names[0]);
		return core->parent;
	}
	/* 多个候选 parent：必须由 provider 提供 .get_parent */
	if (!core->ops->get_parent) {
		WARN(!core->ops->get_parent,
		     "%s: multi-parent clocks must implement .get_parent\n", __func__);
		return NULL;
	}
	index = core->ops->get_parent(core->hw);
	if (!core->parents)
		core->parents = kcalloc(core->num_parents, sizeof(struct clk *),
					GFP_KERNEL);
	return clk_core_get_parent_by_index(core, index);
}

三条规则值得背下来。单 parent 靠名字查，所以 parent_names 必须和别的 clock 的 name 严格一致，一个字符都不能差。多 parent 必须实现 .get_parent，CCF 不知道硬件当前选的是哪一路，只能问硬件。查不到就是孤儿，但不是死局，__clk_init() 的扫孤儿逻辑会补上。clk_core_lookup() 先深度优先搜 clk_root_list 的每棵树，再搜 clk_orphan_list，而且只搜已经在树上的 clock，所以注册顺序是「先上游后下游」。

rate 传播的方向是自顶向下。__clk_recalc_rates() 从变更节点递归重算整棵子树：pll1 从 600 MHz 改到 900 MHz，下面 ÷3 的 axi_div（→300 MHz）、再往下 ÷2 的 ahb_div / gpu_div（→150 MHz）、旁路 ÷4 的 apb_div（→225 MHz），一路重算到底。反直觉的点在这：改了 parent 的 rate，语义上等于改了所有子节点的 rate，所以 CCF 走 PRE_RATE_CHANGE → 改 → POST_RATE_CHANGE 三段通知，失败还能 ABORT_RATE_CHANGE 回滚，想拒绝的驱动在 notifier 里返回 NOTIFY_STOP 就能拦。反方向的传播由 CLK_SET_RATE_PARENT 控制：子节点想改频率但分频比动不了，就把请求往上推给 parent，这是理解 round_rate 的关键，第十七章展开。

十二、时钟的三种操作：enable、set_rate、set_parent #

三种操作在 CCF 内部是三套完全不同的机制，混在一起想会绕晕，分开看就清楚：

操作 语义 是否睡眠 传播方向 失败回滚
enable / disable 开关时钟信号 不能睡眠 自底向上（先开 parent） 反向 disable parent
prepare / unprepare 开关前的准备/善后 可以睡眠 自底向上 反向 unprepare parent
set_rate 改频率 可以睡眠（持 prepare_lock） 自顶向下（重算子树） notifier 的 ABORT 路径
set_parent mux 换源 可以睡眠（持 prepare_lock） 改完重算子树 notifier 的 ABORT 路径

为什么 enable 不能睡眠而 set_rate 可以？enable 持 enable_lock（spinlock），中断上下文里也会被调用，比如驱动在中断里开一下时钟做一次性传输；set_rate 持 prepare_lock（mutex），它要遍历整棵树、调 kmalloc、等 PLL 锁定。

clk_set_rate 的本体就三行：clk_prepare_lock() → clk_core_set_rate_nolock(clk->core, rate) → clk_prepare_unlock()。真正干活的是 clk_core_set_rate_nolock()，六步：目标和当前一致就返回 0；置了 CLK_SET_RATE_GATE 且 prepare_count > 0 返回 -EBUSY；clk_calc_new_rates() 算出整条路径上的新 rate 和需要更换的 parent 并返回最顶端的变更节点；clk_propagate_rate_change(top, PRE_RATE_CHANGE) 逐节点通知，任何一个 notifier 返回 NOTIFY_STOP 就发 ABORT_RATE_CHANGE 并返回 -EBUSY；clk_change_rate(top) 真正写硬件，自顶向下递归；最后记下 core->req_rate = req_rate。最后这步记的是你要求的值，不是硬件实际给的值——rate 在 clk_change_rate() 里由 clk_recalc() 重新算，两个值分开存（第十章说过）。

clk_set_parent 的流程同构，但多两个坑。一是 CLK_SET_PARENT_GATE + 已 prepare → -EBUSY，想换路必须先 unprepare。二是注释里那句话：如果 clk 处于 prepared 状态，换 parent 期间它会被临时 enable，这对要求「换路时必须断电」的硬件是致命的。换路本身带着毛刺，硬件能不能忍，看 datasheet。

十三、prepare 与 enable 的两段式 #

结论：两套 API 的本质，是把 clock 的启动/停止拆成 atomic 和 non-atomic 两个阶段。 拆的理由有两个角度。

角度一，写给 provider 看。 实现 .prepare 时可以把会睡下去的操作放进去：启动 PLL 后 msleep() 等锁定、通过 I2C 配置外部时钟芯片、regulator_enable() 等电压稳定。这些操作一定不能放进 .enable，因为 .enable 在 spinlock 里、会在中断上下文被调，睡下去就是 scheduling while atomic。角度二，写给 consumer 看。 你调 clk_prepare() 时要知道它会睡，别在原子上下文调；调 clk_enable() 则可以放心，任何上下文都行。

为什么开关个时钟要睡觉？enable PLL 之后要等稳定，PLL 的 lock time 动辄几十上百微秒，在 CPU 看来是几万个周期，这段时间把 CPU 交出去（进程睡眠）比原地自旋划算得多。内核源码把这两个回调的约束写得很死（4.4 struct clk_ops 注释）：

回调 上下文 能否睡眠 谁调用时持锁
.prepare / .unprepare / .is_prepared 进程上下文 可以 prepare_lock（mutex）
.enable / .disable / .is_enabled 任意上下文 不能 enable_lock（spinlock）
.recalc_rate / .round_rate / .determine_rate / .set_rate / .set_parent / .get_parent 进程上下文 可以 prepare_lock

两段式的计数也是分开的：prepare_count 和 enable_count 各自独立累加。clk_enable 之前必须有对应的 clk_prepare，源码里直接校验 WARN_ON(core->prepare_count == 0) 并返回 -ESHUTDOWN；反过来 clk_unprepare 时 enable_count > 0 也会 WARN_ON。这两个 WARN 是初学者最常见的报错来源。至于为什么还要提供 clk_prepare_enable() / clk_disable_unprepare()：绝大多数场景就是「我在进程上下文，我就想把它开起来」，两步写两行纯属噪音，framework 封装了，前提是你确认自己在 non-atomic 上下文。

版本注意： CONFIG_HAVE_CLK_PREPARE 在 3.16 前后被清理掉了（具体版本未验证）。老内核里架构没实现 prepare 语义时，clk_prepare() 会被编成只有 might_sleep() 的空函数；4.x 里 CCF 是唯一实现，这个开关没意义了。

冷知识：clk_disable_unused() 在 late_initcall_sync 阶段跑，把系统里所有没人用的 clock 关掉省电。你的 clock 如果必须常开（总线、debug 串口、不能停的硬件），注册时置 CLK_IGNORE_UNUSED，否则开机后就被它关了，症状是「probe 正常，进用户态后某个外设失灵」。这个 initcall 可以用 clk_ignore_unused 内核参数整体关掉，调试时很好用。

十五、clk_get / devm_clk_get：怎么拿到一个时钟 #

四个查找 API 的分工：

text
clk_get(dev, id)              →  先看 DT（dev->of_node 的 clocks/clock-names），
                                 再回落 clkdev 表（dev_name + con_id）
clk_get_sys(dev_id, con_id)   →  直接查 clkdev 表
of_clk_get(np, index)         →  按 DTS 节点里 clocks 属性的下标取
of_clk_get_by_name(np, name)  →  按 clock-names 里的名字取

of_clk_get_by_name 的内部就是「在 clock-names 里找到 name 的下标，然后 of_clk_get(np, 下标)」，所以 devm_clk_get(&pdev->dev, "baud") 和 of_clk_get_by_name(pdev->dev.of_node, "baud") 等价，区别只是前者会回落 clkdev 表。

几个实战要点。devm_clk_get(dev, NULL) 表示「拿这个 device 的第一个 clock」，只适用于设备确实只有一个时钟、或者 clocks 里只填了一项的场景，写 NULL 之前先在 DT 里确认，否则拿到错误的时钟是很容易的事。出错必须用 PTR_ERR 透传：

c
clk = devm_clk_get(&pdev->dev, "pclk");
if (IS_ERR(clk))
	return PTR_ERR(clk);   /* 不要写成 return -ENODEV; */

provider 还没 probe 时 of_clk_get_from_provider 返回 -EPROBE_DEFER，整个错误码往上传，驱动核心会把你这个 consumer 排进延迟探测队列，等 provider 就绪了重试。改写成 -ENODEV，probe 就直接失败，症状是「明明有 clock，一开机就报找不到」。另外 clk_get 要配 clk_put，devm_clk_get 不用，devm 版本在 driver unbind 时自动 put。

clkdev 那套正在退场。老的 clk_register_clkdev() + clk_get() 靠下面这个结构在全局 clocks 链表里按字符串查：

c
struct clk_lookup {
	struct list_head	node;    /* 挂进 clocks 链表 */
	const char		*dev_id; /* device 名 */
	const char		*con_id; /* 连接名 */
	struct clk		*clk;
	struct clk_hw		*clk_hw;
};

引了 DT 之后，provider 的 DTS 节点本身就是稳定标识，与其维护一堆字符串映射，不如直接维护「节点 → clk」。provider 侧的组合因此从 clk_register + clk_register_clkdev 换成 clk_register + of_clk_add_provider，CCF 里多了一条全局链表 of_clk_providers。「正在退场」不等于「已经消失」：clkdev 代码到 4.4 还在，没 DT 的老 ARM 板子还在用，新平台别写就是了。

十六、clk_prepare_enable 与 clk_disable_unprepare #

这两个组合接口的实现就几行，值得逐字看：

c
/* include/linux/clk.h, Linux 4.4 */
static inline int clk_prepare_enable(struct clk *clk)
{
	int ret;

	ret = clk_prepare(clk);
	if (ret)
		return ret;
	ret = clk_enable(clk);
	if (ret)
		clk_unprepare(clk);   /* enable 失败，回滚 prepare */
	return ret;
}

static inline void clk_disable_unprepare(struct clk *clk)
{
	clk_disable(clk);
	clk_unprepare(clk);
}

关键是 clk_prepare_enable 里的失败回滚：clk_enable 挂了，必须把已经做过的 clk_prepare 撤销，否则 prepare_count 漏加一次。这个泄漏在长跑系统里表现为「suspend 时 unprepare 不干净」或者「regulator 关不掉」。顺序不能反：开是先 prepare 后 enable，关是先 disable 后 unprepare。源码注释写得很死：clk_disable must be called before clk_unprepare，反过来会触发 WARN_ON(core->enable_count > 0)。

什么时候必须拆开写？需要在原子上下文里开关时钟的时候——probe 里用 clk_prepare_enable() 一次搞定，中断里只调 clk_enable() / clk_disable()（因为已经在 probe 里 prepare 过了）。这就是两段式存在的实际价值：prepare 一次，enable/disable 随便多少次都很快。

probe 里多资源获取时按相反顺序回滚，下面是标准写法（devm 管 clk_get 的配对，你只管 prepare/enable）：

c
static int foo_probe(struct platform_device *pdev)
{
	struct clk *pclk, *fclk;
	int ret;

	pclk = devm_clk_get(&pdev->dev, "pclk");
	if (IS_ERR(pclk))
		return PTR_ERR(pclk);
	fclk = devm_clk_get(&pdev->dev, "func");
	if (IS_ERR(fclk))
		return PTR_ERR(fclk);       /* pclk 由 devm 管理，不用管 */

	ret = clk_prepare_enable(pclk);
	if (ret)
		return ret;
	ret = clk_prepare_enable(fclk);
	if (ret)
		goto err_fclk;

	/* ... 硬件初始化 ... */
	clk_disable_unprepare(fclk);
	clk_disable_unprepare(pclk);
	return 0;

err_fclk:
	clk_disable_unprepare(pclk);
	return ret;
}

十七、时钟速率的设置与传播 #

clk_set_rate 的传播算法，是 CCF 里最绕的一块。核心函数 clk_calc_new_rates() 的分支结构（4.4，去掉错误日志后的骨架）：

c
parent = old_parent = core->parent;
best_parent_rate = parent ? parent->rate : 0;
clk_core_get_boundaries(core, &min_rate, &max_rate);
if (core->ops->determine_rate) {
	req = { .rate = rate, .min_rate = min_rate, .max_rate = max_rate,
		.best_parent_hw = parent ? parent->hw : NULL,
		.best_parent_rate = parent ? parent->rate : 0 };
	if (core->ops->determine_rate(core->hw, &req) < 0)
		return NULL;
	best_parent_rate = req.best_parent_rate;
	new_rate = req.rate;
	parent = req.best_parent_hw ? req.best_parent_hw->core : NULL;
} else if (core->ops->round_rate) {
	new_rate = core->ops->round_rate(core->hw, rate, &best_parent_rate);
	if (new_rate < 0 || new_rate < min_rate || new_rate > max_rate)
		return NULL;
} else if (!parent || !(core->flags & CLK_SET_RATE_PARENT)) {
	core->new_rate = core->rate;
	return NULL;                    /* 请求丢弃 */
} else {
	top = clk_calc_new_rates(parent, rate);
	new_rate = parent->new_rate;
	goto out;                       /* 请求向上推 */
}
if (parent != old_parent && (core->flags & CLK_SET_PARENT_GATE) &&
    core->prepare_count)
	return NULL;                    /* 换 parent 时必须 gated */
if (parent && core->num_parents > 1)
	p_index = clk_fetch_parent_index(core, parent);
if ((core->flags & CLK_SET_RATE_PARENT) && parent &&
    best_parent_rate != parent->rate)         /* 传播扳机 */
	top = clk_calc_new_rates(parent, best_parent_rate);
out:
clk_calc_subtree(core, new_rate, parent, p_index);
return top;                             /* 最顶端的变更节点 */

四个分支分别对应：有 .determine_rate（首选，struct clk_rate_request 打包 rate / min_rate / max_rate 传下去，还能用 best_parent_hw 建议换 parent）；只有 .round_rate（老路径，返回 rounded rate，同时通过 &best_parent_rate 返回「我需要 parent 提供多少」）；两个都没有且没有 CLK_SET_RATE_PARENT（自己调不了，请求丢弃，clk_set_rate 得 -EINVAL）；两个都没有但有 CLK_SET_RATE_PARENT（请求原封不动推给 parent，递归找真正能调的那个节点）。最后那个 if 是传播的扳机：以 UART 改 115200 波特率、16 倍过采样为例，clk_set_rate(uart_clk, 1843200) 进来，uart_div.round_rate() 算出分频比 = pll/1843200 → 161.6 → 取 162，输出 1843200/162 ≈ 11378 附近的实际值；*parent_rate 原样返回 pll 当前值，best_parent_rate == parent->rate 成立，传播到此为止，pll 不动。如果 uart_div 置了 CLK_SET_RATE_PARENT 且 round_rate 修改了 *parent_rate（比如它想要 24 MHz 的 parent 而不是 48 MHz），CCF 就带着这个新值去调 pll.round_rate()，一路向上。

round_rate 和 determine_rate 的关系是版本演进的关键点：

项 round_rate determine_rate
出现时间 CCF 初始就有（3.x） 3.10 前后引入（具体版本未验证）
签名 long (*)(struct clk_hw *hw, unsigned long rate, unsigned long *parent_rate) int (*)(struct clk_hw *hw, struct clk_rate_request *req)
能否建议换 parent 不能，只能通过 *parent_rate 间接暗示 能，req->best_parent_hw 直接指定
能否表达区间约束 不能 能，min_rate / max_rate

写驱动时的选择原则：在新内核上，能写 .determine_rate 就写 .determine_rate。 4.4 的 clk_register 会校验：提供了 .recalc_rate 却没提供 .round_rate 也没提供 .determine_rate，直接打 warning 并返回 -EINVAL。

clk_set_rate 的另一半是 clk_change_rate()，负责真正写寄存器并处理换 parent。核心顺序是：先按 new_parent 定出 best_parent_rate；new_parent 和当前 parent 不同时，__clk_set_parent_before() 把旧 parent 的 enable 计数处理好，然后有 set_rate_and_parent 就一次调完（并置 skip_set_rate），否则调 set_parent(core->hw, core->new_parent_index)，再 __clk_set_parent_after() 收尾；没跳过就调 set_rate(core->hw, core->new_rate, best_parent_rate)；接着 core->rate = clk_recalc(core, best_parent_rate) 刷新缓存，rate 变了就发 POST_RATE_CHANGE；最后对所有 children 递归 clk_change_rate()（new_parent 指向别处的 child 跳过），new_child 单独处理一次。

set_rate_and_parent 这个回调值得单独说：它把「换 parent」和「改分频」合成一次寄存器写，专门给那些两者必须原子完成的硬件用（有些 PLL 换参考源的同时要同步改倍频系数，分两步写会输出一段非法频率）。4.4 的校验里要求：实现了 set_rate_and_parent，就必须同时实现 set_parent 和 set_rate。

最后一个常用的坑：clk_set_rate 不保证成功，也不保证给你要的值。标准做法是两步走——先 clk_round_rate(clk, want) 问「你能给多少」，自己判断够不够（不够就返回 -EINVAL），确认之后再 clk_set_rate(clk, round)。

十八、provider 侧：怎么注册一个 clock #

provider 要做的事就两件：填 clk_init_data，调注册接口。

c
/* 手工填 init_data 的最小骨架 */
static const struct clk_ops foo_ops = {
	.recalc_rate = foo_recalc_rate,  .round_rate = foo_round_rate,
	.set_rate    = foo_set_rate,     .enable     = foo_enable,
	.disable     = foo_disable,      .is_enabled = foo_is_enabled,
};

static struct clk_hw *foo_register(struct device *dev, const char *name,
				   const char *parent_name, void __iomem *base)
{
	struct foo_clk *fc = devm_kzalloc(dev, sizeof(*fc), GFP_KERNEL);
	int ret;

	if (!fc)
		return ERR_PTR(-ENOMEM);
	fc->reg = base;
	fc->hw.init = &(struct clk_init_data){
		.name		= name,
		.ops		= &foo_ops,
		.parent_names	= (const char *[]){ parent_name },
		.num_parents	= 1,
		.flags		= CLK_IGNORE_UNUSED,
	};
	ret = clk_hw_register(dev, &fc->hw);   /* 4.4 上没有这个函数，见下 */
	if (ret)
		return ERR_PTR(ret);
	return &fc->hw;
}

版本注意：clk_hw_register() 是 4.4 之后的接口。 素材原文（3.x/4.0 时代）用的是 struct clk *clk_register(struct device *dev, struct clk_hw *hw) 和 devm_clk_register()，4.4 里这两个还是主力，clk_hw_register() 尚未出现（上面那段代码在 4.4 上编译不过，要改成 clk_register() 再判 IS_ERR）。provider 侧全面改用 clk_hw_* 接口是 4.16 之后的事（未验证具体版本）。写代码前先看 include/linux/clk-provider.h 里到底有没有这个函数，别抄了新旧混搭的代码。4.4 里 clk_hw_get_name / clk_hw_get_rate / clk_hw_get_parent / clk_hw_round_rate / clk_hw_is_enabled 这批辅助函数已经存在，但 clk_unregister() 接受的是 struct clk *，这个混搭状态在 4.x 中期逐步收敛。

注册接口从粗到细九种选择：

接口 输入 适用场景
clk_register_fixed_rate() 名字、parent 名、频率 晶振、固定时钟
clk_register_fixed_factor() 名字、parent、mult、div 固定倍分频
clk_register_gate() 名字、parent、寄存器、bit 纯开关
clk_register_divider() / _table() 名字、parent、寄存器、shift/width（+查找表） 规则/不规则分频
clk_register_mux() / _table() 名字、parent 数组、寄存器、shift/width（+查找表） 规则/不规则选路
clk_register_composite() mux_hw + rate_hw + gate_hw 及其 ops 一寄存器多位域的综合 clock
clk_register() 自己填好的 clk_hw 上面都不合适时的兜底

优先级：先用现成的，实在不行才手搓。 clk_gate / clk_divider / clk_mux / clk_composite 这些通用实现里，寄存器读写有 clk_readl / clk_writel 处理大小端（PowerPC 上是 big-endian 变体），位运算有边界检查，锁有 spinlock 参数。手搓一遍，这些细节全是漏洞。

十九、clk_ops：provider 要实现的回调 #

struct clk_ops 在 4.4 里共 20 个回调成员（include/linux/clk-provider.h）。签名统一是 (struct clk_hw *hw, ...)，返回值见下表「必须性」列的约定：

c
/* 关键签名，其余回调是同构的 int/void (*)(struct clk_hw *hw) */
unsigned long	(*recalc_rate)(struct clk_hw *hw, unsigned long parent_rate);
long		(*round_rate)(struct clk_hw *hw, unsigned long rate,
					unsigned long *parent_rate);
int		(*determine_rate)(struct clk_hw *hw, struct clk_rate_request *req);
int		(*set_parent)(struct clk_hw *hw, u8 index);
u8		(*get_parent)(struct clk_hw *hw);
int		(*set_rate)(struct clk_hw *hw, unsigned long rate,
				    unsigned long parent_rate);
int		(*set_rate_and_parent)(struct clk_hw *hw, unsigned long rate,
				    unsigned long parent_rate, u8 index);
unsigned long	(*recalc_accuracy)(struct clk_hw *hw, unsigned long parent_accuracy);
int		(*debug_init)(struct clk_hw *hw, struct dentry *dentry);

另外 11 个是 prepare / unprepare / is_prepared / unprepare_unused / enable / disable / is_enabled / disable_unused / get_phase / set_phase / init，签名形如 int (*prepare)(struct clk_hw *hw)、void (*disable)(struct clk_hw *hw)。

逐项说清「什么时候必须实现」：

回调 必须性 说明
.prepare / .unprepare 有可睡眠的启动操作时必须 prepare_lock 下调用，可睡眠，PLL 等锁定写这里
.is_prepared / .is_enabled 可选 不实现则分别用 prepare_count / enable_count 判断
.unprepare_unused / .disable_unused 可选 只在 clk_disable_unused 里调，特殊硬件用
.enable / .disable 能开关的 clock 必须 不得睡眠，enable_lock 下调用
.recalc_rate 建议实现 不实现则退回 parent 的 rate，数值错但不报错
.round_rate / .determine_rate 二选一 能改 rate 的 clock 必须有其一，4.x 推荐后者
.set_parent / .get_parent 多 parent 的 clock 必须 单一 parent 不用，缺 get_parent 会 WARN
.set_rate 能改 rate 的 clock 必须 第二个参数是 round_rate 的返回值
.set_rate_and_parent 特殊硬件 二者必须原子完成时用，且必须同时实现 set_parent + set_rate
.recalc_accuracy 可选 不实现则继承 parent 的精度
.get_phase / .set_phase 可选 相位不向上传播，和 rate/accuracy 不一样
.init 慎用 注册末尾调一次，基础 clock 类型都不用，注释里明说「不推荐」
.debug_init 可选 给自己的 clock 加 debugfs 文件

clk_register() 的强制校验（4.4）：有 .set_parent 没 .get_parent → -EINVAL；有 .recalc_rate 但 .round_rate 和 .determine_rate 都没有 → 打 warning 并 -EINVAL；有 .set_rate_and_parent 但 .set_parent 或 .set_rate 缺 → -EINVAL；parent_names 里出现 NULL → 打 WARN。

recalc_rate 为什么「建议必须」？它在 __clk_init() 里用来算初始 rate：有实现就 core->ops->recalc_rate(core->hw, clk_core_get_rate_nolock(core->parent))，没实现就沿 parent 的 rate 兜底，没 parent 则置 0。你写了 .set_rate 改分频比，却没写 .recalc_rate 告诉 CCF 改完到底是多少，clk_get_rate 会一直返回 parent 的 rate——数值是错的，而且没有报错，这是移植时最常见的 bug 之一。

round_rate 和 set_rate 的契约关系：round_rate 问硬件「你能给多少」、不改硬件，set_rate 按 round_rate 的返回值真正去写。set_rate 的 rate 参数就是 round_rate 的返回值，别在里面再做一遍四舍五入，做两遍的结果是分频比偏一格。is_prepared / is_enabled 不实现时用软件计数兜底，如果硬件状态会被 bootloader 或固件改动，软件计数就和实际脱节，这时必须实现 is_enabled 让 CCF 去问硬件。

二十、clk_register 系列与 clk_hw #

注册接口按「谁填 clk_ops」分三层。第一层 CCF 全包，你什么都不用填：clk_register_fixed_rate()、clk_register_fixed_factor()、clk_register_gate()、clk_register_divider() / clk_register_divider_table()、clk_register_mux() / clk_register_mux_table()、clk_register_composite()。第二层半包，clk_register() / devm_clk_register()，你自己填完整的 clk_hw（含 init_data 和 ops）。第三层 DTS 全自动，连 driver 都不用写，靠 of_fixed_clk_setup() / of_fixed_factor_clk_setup() / of_gpio_clk_gate_setup() 这类 setup 函数处理 fixed-clock、fixed-factor-clock、gpio-gate-clock 三种 compatible。

第一层的典型用法，以及 composite（把 mux / divider / gate 三个位域打包）的签名：

c
/* 24MHz 晶振 */
clk = clk_register_fixed_rate(dev, "osc24m", NULL, CLK_IS_ROOT, 24000000);
/* gate：base+0x40 的 bit 3 控制开关，写 1 打开 */
clk = clk_register_gate(dev, "uart0_clk", "apb1", 0, base + 0x40, 3, 0, &ccu->lock);
/* divider：base+0x48 的 bit[2:0] 是分频比，1-based（写 0 表示 ÷1） */
clk = clk_register_divider(dev, "apb1", "ahb", 0, base + 0x48, 0, 3,
			   CLK_DIVIDER_ONE_BASED, &ccu->lock);

struct clk *clk_register_composite(struct device *dev, const char *name,
		const char * const *parent_names, int num_parents,
		struct clk_hw *mux_hw, const struct clk_ops *mux_ops,
		struct clk_hw *rate_hw, const struct clk_ops *rate_ops,
		struct clk_hw *gate_hw, const struct clk_ops *gate_ops,
		unsigned long flags);

composite 的参数多，逻辑简单：mux_hw / rate_hw / gate_hw 指向三个派生结构（clk_mux / clk_divider / clk_gate），*_ops 用 &clk_mux_ops / &clk_divider_ops / &clk_gate_ops，填几个组合几个。「一个寄存器里塞了三件事」的 SoC 全靠它。

第二层的完整签名（4.4）：clk_register() / devm_clk_register() 返回 struct clk *，clk_unregister() / devm_clk_unregister() 注销。clk_register() 内部七步：kzalloc 一个 clk_core；kstrdup_const 拷 name；拷 ops / flags / num_parents；hw->core = core 双向绑定；逐条 kstrdup_const 拷 parent_names；hw->clk = __clk_create_clk(hw, NULL, NULL)；最后 __clk_init(dev, hw->clk) 建树、定 parent、算 rate、扫孤儿、调 .init。两步 kstrdup_const 是个真实的坑：很多人把 clk_init_data 和 parent_names 数组放在 __initconst 或 probe 的栈上，现象是「clock 名字变成乱码」。CCF 帮你 copy 了字符串，但数组本身（const char *[]）必须活得够久——用 static const char * const xxx_parents[] = {...} 最省心。

clk_unregister() 的边界：它把 core->ops 换成 clk_nodrv_ops（所有回调返回 -ENXIO），把所有 children 扔回 orphan list，最后 kref_put。它不保证已经 open 的句柄立即失效，所以注销前自己确认没有 user。

clk_hw 与裸 struct clk 的演进：

版本 provider 拿到的句柄 说明
3.x 早期 struct clk * provider 和 consumer 用同一种句柄，职责混在一起
3.x 中期 struct clk_hw 出现 引入 hw 概念缓存（cachable）机制，provider 侧改用 clk_hw
4.x clk_hw + clk_core 双层 内部态彻底抽到 core，struct clk 退化为 per-user 句柄
4.16 之后（未验证） clk_hw_* 接口全面铺开 provider 侧不再直接接触 struct clk

素材原文写于 3.x 到 4.0 之间，里面「struct clk 对 provider 也透明」这句在 4.4 上是准确的历史描述，但当时 clk_register() 返回值仍是 struct clk *，provider 还得存一下；到 4.4，provider 可以只存 clk_hw，需要传给 of_clk_add_provider 时再用 hw->clk。

二十一、设备树绑定：clocks / clock-names / assigned-clocks #

三组属性，三件不同的事，混在一起记必错。第一组是「我的输入从哪来」，provider 和 consumer 都写；第二组是「我提供哪些输出」，只有 provider 写；第三组是「初始化时帮我把这几个 clock 配好」，consumer 侧可选，clk-conf.c 处理。

dts
/* 第一组：输入 */
clocks = <&osc24M>, <&pll2>;
clock-names = "ref", "bypass";

/* 第三组：初始化配置 */
&mmc0 {
	clocks = <&ccu CLK_MMC0>, <&ccu CLK_AHB_MMC0>;
	clock-names = "mmc", "ahb";
	assigned-clocks = <&ccu CLK_MMC0>;
	assigned-clock-parents = <&ccu CLK_PLL_PERIPH0>;
	assigned-clock-rates = <50000000>;
};

clocks 每一项是 phandle + N 个 cell，N 由被引用 provider 的 #clock-cells 决定。clock-names 给每一项配名字，顺序一一对应；只写 clocks 不写 clock-names，驱动只能按下标 of_clk_get(np, i) 取，可读性差且一改 DT 就错位。上面 assigned-* 那段的意思是：开机时把 CLK_MMC0 的 parent 切到 CLK_PLL_PERIPH0，频率设成 50 MHz。执行顺序是先 parent 后 rate（of_clk_set_defaults 的处理顺序，未逐行核对），因为换了 parent 之后可行频率集才确定。这套属性的好处是板级频率调整不用改驱动；坏处是驱动的 clk_set_rate 会覆盖它——assigned-* 在 device probe 前执行，驱动的设置在后，最终值以驱动为准。

完整对照表（clock-names 和 clock-output-names 长得很像但语义相反：前者是输入的名字，后者是输出的名字，同一节点上可以同时出现）：

属性 谁写 谁解析 对应 API / 作用
#clock-cells provider of_clk_get_from_provider 0 = 单输出只写 phandle；1 = 多输出还要给 ID
clock-output-names provider of_clk_get_parent_name 每个输出的名字，仅 provider 内部用，用于拼 parent_names
clock-indices provider 同上 输出 ID 不连续时的 ID→下标映射（4.x，未验证具体版本）
clocks 双方 of_parse_phandle_with_args of_clk_get / devm_clk_get
clock-names 双方 of_property_match_string of_clk_get_by_name
assigned-clocks consumer clk-conf.c 选定目标 clk
assigned-clock-rates consumer clk-conf.c clk_set_rate()
assigned-clock-parents consumer clk-conf.c clk_set_parent()

二十二、of_clk_get 与 of_clk_add_provider #

这一对是 DT 侧的全部机制：provider 注册「我管哪个节点」，consumer 拿着节点来问「给我一个 clock」。

provider 侧：注册。

c
int of_clk_add_provider(struct device_node *np,
			struct clk *(*clk_src_get)(struct of_phandle_args *args,
						   void *data),
			void *data);

np 是 provider 的 DTS 节点（pdev->dev.of_node）；clk_src_get 把「DTS 里写的 ID」翻译成 struct clk *；data 是透传上下文，一般是 clock 数组。

返回值陷阱（重要）： 素材原文把返回值写成 void * 或者省略不提。4.4 的实际签名是 int，必须检查：

c
ret = of_clk_add_provider(np, of_clk_src_onecell_get, &ccu->clk_data);
if (ret)
	return ret;

为什么必须查？4.4 的实现是 kzalloc 一个 of_clk_provider、填 node / data / get、list_add 进 of_clk_providers 链表，然后在返回前调 of_clk_set_defaults(np, true) 处理这个节点的 assigned-clocks；这一步 ret < 0 就 of_clk_del_provider(np) 把刚加进去的项删掉，并把错误码返回。这一步失败会自动撤销注册。你不查返回值，就会得到一个「注册过的假象」：链表里没这个 provider，consumer 全部 -EPROBE_DEFER，系统起不来，而且没有任何日志。

那个 get 回调。 clkspec->args[0] 就是 DTS 里 <&ccu CLK_UART0> 中 CLK_UART0 那个数。CCF 提供两个现成实现：

c
/* 单输出 provider：#clock-cells = <0>，data 直接就是 struct clk * */
struct clk *of_clk_src_simple_get(struct of_phandle_args *clkspec, void *data);
/* 多输出 provider：#clock-cells = <1>，data 是 struct clk_onecell_data * */
struct clk *of_clk_src_onecell_get(struct of_phandle_args *clkspec, void *data);

struct clk_onecell_data {
	struct clk **clks;       /* clock 指针数组，按 ID 下标存放 */
	unsigned int clk_num;    /* 数组长度 */
};

of_clk_src_onecell_get 的实现就一句：return clk_data->clks[clkspec->args[0]];，越界返回 -EINVAL。所以注册代码要保证 数组下标 == DTS 里的 ID，中间有空缺就填 NULL 占位，不要压缩数组。

consumer 侧：解析。 三个接口是 of_clk_get(np, index)、of_clk_get_by_name(np, name)、of_clk_get_from_provider(clkspec)，链路是：

text
DTS: clocks = <&ccu 12>;
  ├─ of_parse_phandle_with_args(np, "clocks", "#clock-cells", 0, &clkspec)
  │     clkspec.np = &ccu 节点, clkspec.args[0] = 12
  ├─ of_clk_get_from_provider(&clkspec)
  │     └─ 遍历全局 of_clk_providers 链表，找到 provider->node == clkspec.np
  │        └─ 调 provider->get(&clkspec, provider->data)
  │             └─ of_clk_src_onecell_get → clk_array[12]
  ├─ __clk_create_clk()  → 给你一个 per-user 句柄
  └─ 返回 struct clk *

这条链路上有三个可失败点：

现象 错误码 含义
clocks 属性不存在或 index 越界 -ENOENT DT 描述错了
phandle 指向的节点没有 provider 注册 -EPROBE_DEFER provider 还没 probe 完，重试
ID 超出 clk_num -EINVAL 数组没分配够

-EPROBE_DEFER 是 of_clk_get_from_provider 的初始值，不是从某个分支返回的——进来先 struct clk *clk = ERR_PTR(-EPROBE_DEFER)，然后遍历 of_clk_providers，只有 provider->node == clkspec->np 且 provider->get() 没出错才会被覆盖。所以「不在链表里」和「链表里但 get 失败」都是 -EPROBE_DEFER 起步，consumer 一律当成「再等等」。

provider / consumer 的配对清单，少任何一环，consumer 拿到的是 -EPROBE_DEFER 或者错位的 clock：

provider 做了什么 consumer 才能做什么
调 clk_register_*() 得到 struct clk * ——
存进数组，填 clk_onecell_data ——
调 of_clk_add_provider(np, get, data) of_clk_get(np, i) 能取到
plus：#clock-cells 与数组下标对齐 DTS 里的 ID 才能写对
plus：of_clk_set_defaults 成功 assigned-* 才生效

顺序问题的解法：of_clk_init()。 provider 之间也有依赖，按 DTS 顺序初始化，上游没注册下游就全是孤儿。of_clk_init(const struct of_device_id *matches) 把所有匹配节点收集成列表，遍历一遍，用 parent_ready() 检查每个节点的 clocks 是否都能取到，能取到就调它的 init 回调；一轮下来一个都没成功（有环，或者 parent 根本不是 clock provider），就 force = true 全量硬上。这个 force 兜底也是很多奇怪 bug 的来源：依赖链和 DTS 描述不一致时，第一批初始化顺序会乱，parent_names 查不到就成孤儿然后永久失联。

二十三、一个完整的 provider 实例骨架 #

把前面所有零件拼起来。这是一个虚构的 foo-ccu 平台 clock 驱动，风格接近真实 SoC clock driver：

c
/* drivers/clk/foo/clk-foo.c —— 虚构示例，仅演示结构 */
#include <linux/clk-provider.h>
#include <linux/of.h>
#include <linux/platform_device.h>
#include <linux/spinlock.h>

#define FOO_PLL_CFG	0x00
#define FOO_AXI_CFG	0x10
#define FOO_APB1_CFG	0x14
#define FOO_GATE_REG	0x40
#define FOO_CLK_NUM	8	/* 必须与 #clock-cells 的 ID 空间对齐 */

enum foo_clk_id {
	FOO_CLK_OSC = 0, FOO_CLK_PLL, FOO_CLK_AXI_DIV, FOO_CLK_AHB_DIV,
	FOO_CLK_APB1_MUX, FOO_CLK_APB1_DIV, FOO_CLK_UART0, FOO_CLK_MMC0,
};

struct foo_ccu {
	void __iomem		*base;
	spinlock_t		lock;
	struct clk_onecell_data	clk_data;
	struct clk		*clks[FOO_CLK_NUM];
};

static const char * const apb1_mux_parents[] = { "osc", "pll" };

/* 注册一个 clock 并查错：失败跳到 err 统一清理 */
#define FOO_REG(id, expr)						\
	do {								\
		ccu->clks[id] = (expr);					\
		if (IS_ERR(ccu->clks[id])) {				\
			ret = PTR_ERR(ccu->clks[id]);			\
			goto err;					\
		}							\
	} while (0)

static int foo_ccu_probe(struct platform_device *pdev)
{
	struct device *dev = &pdev->dev;
	struct foo_ccu *ccu;
	int i, ret;

	ccu = devm_kzalloc(dev, sizeof(*ccu), GFP_KERNEL);
	if (!ccu)
		return -ENOMEM;
	ccu->base = devm_ioremap_resource(dev,
			platform_get_resource(pdev, IORESOURCE_MEM, 0));
	if (IS_ERR(ccu->base))
		return PTR_ERR(ccu->base);
	spin_lock_init(&ccu->lock);

	FOO_REG(FOO_CLK_OSC, clk_register_fixed_rate(dev, "osc", NULL, CLK_IS_ROOT, 24000000));
	FOO_REG(FOO_CLK_PLL, foo_register_pll(dev, "pll", "osc", ccu->base + FOO_PLL_CFG));
	FOO_REG(FOO_CLK_AXI_DIV, clk_register_divider(dev, "axi_div", "pll", 0,
			ccu->base + FOO_AXI_CFG, 0, 4, CLK_DIVIDER_ONE_BASED, &ccu->lock));
	FOO_REG(FOO_CLK_AHB_DIV, clk_register_divider(dev, "ahb_div", "axi_div", 0,
			ccu->base + FOO_APB1_CFG, 8, 4, CLK_DIVIDER_ONE_BASED, &ccu->lock));
	FOO_REG(FOO_CLK_APB1_MUX, clk_register_mux(dev, "apb1_mux", apb1_mux_parents,
			ARRAY_SIZE(apb1_mux_parents), 0, ccu->base + FOO_APB1_CFG, 0, 2,
			CLK_MUX_INDEX_ONE, &ccu->lock));
	FOO_REG(FOO_CLK_APB1_DIV, clk_register_divider(dev, "apb1", "apb1_mux", 0,
			ccu->base + FOO_APB1_CFG, 4, 2, CLK_DIVIDER_POWER_OF_TWO, &ccu->lock));
	FOO_REG(FOO_CLK_UART0, clk_register_gate(dev, "uart0", "apb1", 0,
			ccu->base + FOO_GATE_REG, 0, 0, &ccu->lock));
	FOO_REG(FOO_CLK_MMC0, clk_register_gate(dev, "mmc0", "apb1", 0,
			ccu->base + FOO_GATE_REG, 1, 0, &ccu->lock));

	ccu->clk_data.clks = ccu->clks;
	ccu->clk_data.clk_num = FOO_CLK_NUM;
	ret = of_clk_add_provider(dev->of_node, of_clk_src_onecell_get,
				  &ccu->clk_data);
	if (ret) {
		dev_err(dev, "failed to add clock provider: %d\n", ret);
		goto err;
	}
	platform_set_drvdata(pdev, ccu);
	return 0;

err:
	for (i = 0; i < FOO_CLK_NUM; i++)
		if (!IS_ERR_OR_NULL(ccu->clks[i]))
			clk_unregister(ccu->clks[i]);
	return ret;
}

这 8 个注册调用的含义和各自的坑，逐条列在下面：

# clock 调用要点 坑
1 osc clk_register_fixed_rate(..., CLK_IS_ROOT, 24000000) 只有真根节点才置 CLK_IS_ROOT
2 pll foo_register_pll() 自定义 ops 等锁定放 .prepare，别放 .enable
3 axi_div clk_register_divider(..., 0, 4, CLK_DIVIDER_ONE_BASED) bit[3:0] 是分频比，1-based 表示写 0 是 ÷1
4 ahb_div clk_register_divider(..., 8, 4, CLK_DIVIDER_ONE_BASED) 同一寄存器 bit[11:8]，别和 3 撞位
5 apb1_mux clk_register_mux(..., 0, 2, CLK_MUX_INDEX_ONE) 寄存器值从 1 开始，0 不是有效 parent
6 apb1 clk_register_divider(..., 4, 2, CLK_DIVIDER_POWER_OF_TWO) 实际分频是 2^寄存器值
7 uart0 / mmc0 clk_register_gate(..., bit 0 / bit 1, 0, ...) gate flag 为 0 表示写 1 打开
8 —— of_clk_add_provider() #clock-cells = <1>，必须查返回值

对应的 DTS：

dts
ccu: clock-controller@1c20000 {
	compatible = "foo,ccu";
	reg = <0x01c20000 0x400>;
	#clock-cells = <1>;
	clock-output-names = "osc", "pll", "axi_div", "ahb_div",
			     "apb1_mux", "apb1", "uart0", "mmc0";
};

uart0: serial@1c28000 {
	compatible = "foo,uart";
	reg = <0x01c28000 0x400>;
	interrupts = <1>;
	clocks = <&ccu 6>;          /* ID 6 = uart0 */
	clock-names = "uart";
	status = "disabled";
};

consumer 侧消费这段 DT，就是 devm_clk_get(&pdev->dev, "uart") → clk_prepare_enable() → clk_set_rate(clk, 115200 * 16) → clk_disable_unprepare()，中间按实际 rate 算波特率分频，和第十六章的骨架一样。骨架里几个决策点：多输出必用 onecell（手写 get 回调容易越界）；数组下标严格等于 DTS ID；空位填 NULL 占位（压缩数组会导致 ID 错位）；一个 spinlock 共享同一寄存器块；CLK_IS_ROOT 只给晶振；失败清理要逆序 unregister（4.4 里 gate/divider/mux 都没有 devm 版本）；注册顺序从上游到下游（下游早注册会进 orphan，虽能自愈但日志难看）。

二十四、CCF 的调试接口 #

调 CCF 的问题，九成靠 debugfs。挂上 CONFIG_DEBUG_FS 和 CONFIG_COMMON_CLK_DEBUG（4.4 里 clk_debug 代码已在 clk.c 内部，配置项名未验证）。

/sys/kernel/debug/clk/clk_summary 是最有用的一张表，缩进就是树的层级：

text
   clock                enable_cnt  prepare_cnt        rate   accuracy   phase
osc24M                          4            4    24000000          0 0
   pll                          2            2   600000000          0 0
      axi_div                   2            2   200000000          0 0
         ahb_div                2            2   100000000          0 0
            apb1                1            1    50000000          0 0
               uart0            1            1    50000000          0 0
            mmc0                1            1   100000000          0 0

四个读法：缩进错了说明 parent_names 写错或 provider 注册顺序有问题；enable_cnt 和 prepare_cnt 不等说明有驱动漏了配对；rate 是 core->rate 缓存值，和硬件实际值不符说明 .recalc_rate 没实现好；某个 clock 本应出现却没出现，说明它还在 clk_orphan_list 里。

单个 clock 的目录在 /sys/kernel/debug/clk/<clock_name>/，含 clk_enable_count、clk_prepare_count、clk_rate、clk_flags、clk_phase、clk_accuracy、clk_notifier_count、clk_parent、clk_possible_parents，以及可写的 clk_prepare_enable / clk_disable_unprepare。clk_possible_parents 最有用：直接列出 parent_names 并标注当前选的是哪个。部分平台/版本还提供 clk_dump 和 clk_orphan_dump 输出 JSON 树（4.4 里代码在 clk.c，是否默认挂 debugfs 取决于配置，未验证）；clk.c 里另有 clk_enable / clk_disable / clk_set_rate / clk_set_parent 一整套 tracepoint，用 trace-cmd 或 perf 抓下来能看到每次操作的完整时序。bootargs 里加 clk_ignore_unused 则跳过 clk_disable_unused()，定位「开机后某外设失灵但 probe 明明成功」的第一步就是它。

二十五、易错点速查 #

按「症状 → 原因 → 修法」列出实战里反复出现的坑。

# 症状 原因 修法
1 provider 注册成功但 consumer 永远 -EPROBE_DEFER 没检查 of_clk_add_provider 返回值 检查返回值，assigned-clocks 配错也会导致失败
2 clk_get_rate 返回 0 或等于 parent .recalc_rate 没实现 实现 .recalc_rate，或确认 parent 链完整
3 clk_set_rate 返回 0 但频率没变 写了 .set_rate 没写 .recalc_rate，缓存没更新 两个回调必须一起实现
4 clk_set_rate 返回 -EINVAL 既没 .round_rate 也没 .determine_rate，且没 CLK_SET_RATE_PARENT 补回调或补 flag
5 多 parent clock 注册时 -EINVAL 有 .set_parent 没 .get_parent 两个必须成对
6 开机后串口/网卡失灵 clk_disable_unused() 关掉了不该关的 clock 注册时置 CLK_IGNORE_UNUSED
7 WARN_ON 报 prepare_count 为 0 只调 clk_enable 没 clk_prepare 用 clk_prepare_enable()
8 换 parent 时 -EBUSY 置了 CLK_SET_PARENT_GATE 且 clock 已 prepare 先 clk_unprepare() 再换
9 改 rate 时 -EBUSY 置了 CLK_SET_RATE_GATE 且 clock 已 prepare 先 gate 再改
10 clock 名字变成乱码 clk_init_data 或 parent_names 数组放在 __initdata/栈上被回收 用 static const char * const xxx[]
11 树是平的，但 clk_possible_parents 全是对的 parent 属于另一个还没注册的 provider 让 of_clk_init() 按依赖序初始化，或检查 compatible
12 某 clock 的 enable_cnt 只涨不落 驱动某个错误路径漏了 clk_disable 用 goto 统一清理
13 clk_put 后系统崩 重复 put，或 put 之后还在用 get/put 严格配对；用 devm_clk_get
14 notifier 回调里死锁 回调里又调了 CCF API，重复拿 prepare_lock notifier 里只做记录，不碰 clock API
15 相位设了没用 provider 没实现 .set_phase 补回调；相位不传播，每个节点单独设
16 DTS 改了没生效 assigned-clocks 被驱动里的 clk_set_rate 覆盖 只在驱动不设 rate 的 clock 上用 assigned-*
17 of_clk_get 返回错位的 clock clk_data 数组压缩过，下标与 ID 不匹配 保留空位填 NULL
18 mux 切了但输出频率没变 换 parent 后子树没重算 确认真没有被 CLK_SET_RATE_NO_REPARENT 之类干扰
19 编译报 implicit declaration of clk_hw_register 在 4.4 上用了 4.16 的 API 改回 clk_register()，先看头文件里有什么
20 clk_disable_unprepare 报 -ESHUTDOWN prepare_count 已经被别人减到 0 检查重复 unprepare 或 prepare/enable 计数不平衡
