一、两个约束型框架：事后保护与事前声明 #

thermal 是事后保护：温度已经上去了才动手，压频率、关核、开风扇。输入是传感器读数，输出是 cooling device 的 state。

PM QoS 是事前约束：设备或进程提前声明「最多能忍 200us 唤醒延迟」「这个场景至少要 1GHz」，内核汇总成一个边界值，摆在 cpuidle/cpufreq 面前当红线。

维度 thermal PM QoS
触发 轮询/中断读到温度越线 有人 add/update 一个 request
数据流 传感器 → core → cooling device requestor → core 聚合 → requestee 查询
决策者 governor（step_wise / IPA / fair_share） 无决策，只算极值
主要受害者 cpufreq、devfreq、cpuidle、风扇 cpuidle、cpufreq、pm domain
时机 事后 事前

注意「无决策」这句。PM QoS 只说「所有申请里最严格的那个是多少」，要不要听是 requestee 的事。所以它的核心代码短，thermal 要养一堆 governor。

二、Thermal 要解决什么：温度是硬约束 #

电流穿过导体，电子和原子碰撞，能量以热散出来。手机、手表贴着手掌，表面温度必须压在人体能接受的范围；座机、车机另有限值，性质一样。

硬件侧换低功耗器件、塞导热凝胶、贴石墨片、加散热片。软件侧只有一条路：减少发热。而发热基本正比于频率乘电压，所以软件控温最直接的手段是降频，其次是关核、限制工作速率。

struct thermal_zone_device 的注释交代得很清楚：polling_delay 为 0 表示中断驱动（interrupt driven）的 zone，不轮询。周期性查询只是默认模式。

实体 是什么 谁注册 关键数据
thermal sensor 真实传感器（LVTS、热敏电阻） 平台驱动 sensor id（u32）
thermal zone 抽象的一片温度区域 sensor 驱动 probe 时注册 温度、trip 数组、governor、poll work
trip point zone 上的温度档位 dts 或驱动内部初始化 temperature、hysteresis、type
cooling device 抽象的可降温手段 cpufreq/devfreq/cpuidle/风扇 max_state、cur_state、ops
thermal governor 决策算法 遍历 governor 表 manage / bind_to_tz / trip_crossed

三、thermal zone：一个测温区域 #

zone 不是硬件，是描述，粒度是「平台上某区域的温度」而不是「某个传感器芯片」。一颗 LVTS 报四个点位，一块板子上五颗，就有了十几个 zone：cpu0-thermal、gpu-thermal、vdec-thermal。

注册两条路。有设备树时 sensor 驱动调 OF 接口，framework 自己解析 zone 节点。注意改名：4.x~5.10 是 thermal_zone_of_sensor_register() / devm_thermal_zone_of_sensor_register()，ops 类型 thermal_zone_of_device_ops；5.10 起变成 devm_thermal_of_zone_register(dev, id, data, ops)，ops 换成 thermal_zone_device_ops（已核对 5.10 / 6.6 头文件）。无设备树时驱动自己填 ops 和 trips，调 thermal_zone_device_register_with_trips() 或 thermal_tripless_zone_device_register()。

注册接口签名变过三次，移植时必踩：

c
/* 5.10：多一个 mask */
thermal_zone_device_register_with_trips(type, trips, num_trips, mask,
                                        devdata, ops, tzp, passive_delay, polling_delay);
/* 6.11：mask 没了，trips 和 ops 变 const，delay 改 unsigned int */
thermal_zone_device_register_with_trips(type, trips, num_trips, devdata,
                                        ops, tzp, passive_delay, polling_delay);
/* 4.19：trip 是「个数 + bitmask + ops 回调」，没有 trip 数组 */
thermal_zone_device_register(type, trips, mask, devdata, ops, tzp,
                             passive_delay, polling_delay);

三代语义差别很大，读老代码别拿新结构体往里套。内部关系是：zone 管 trip 数组，trip 通过 thermal_instance 挂一个或多个 cooling device，一个 cdev 又能被多个 zone 的不同 trip 共享。

	struct thermal_trip trip;              /* 描述：温度、回差、类型、priv */
	struct thermal_trip_attrs trip_attrs;  /* 对应的 sysfs 属性 */

最后一行是重点：governor 判断用 td->threshold，不用裸的 temperature，很多人看漏。

五、温度传感器的读取与 polling #

读温度只有一条正规路：thermal_zone_get_temp() 转调 tz->ops->get_temp()。temperature 字段注释写明那是 core 的缓存，驱动不该直接读。

c
static int drv_get_temp(struct thermal_zone_device *tz, int *temp)
{
	int ret;

	ret = my_sensor_read_temperature(tz->devdata, temp);  /* 单位：毫摄氏度 */
	if (ret)
		return ret;

	if (*temp < -40000 || *temp > 150000)   /* 越界值别送进 governor */
		return -EINVAL;

	return 0;
}

85℃ 写成 85000。无效温度用 THERMAL_TEMP_INVALID，值 -274000，注释里说是故意选的「小于 0K」。

monitor 每次醒来做五件事：读温度更新 last_temperature/temperature；和每个 trip 的 threshold 比；有跨越就更新 trip 所在链表；调 governor 的 manage；按状态重排下次延迟（passive 还是 polling）。

两个 delay 都来自 dts，mt8195 是 polling-delay = <1000> / polling-delay-passive = <250>，单位 ms，注册时换算成 jiffies。

中断驱动也支持：set_trips 把温度窗口下到传感器硬件，温度离开窗口就中断，驱动再调 thermal_zone_device_update()。此时 polling-delay 写 0。

调试用温度注入，比拿打火机烤板子可靠：

bash
# 需要内核打开 CONFIG_THERMAL_EMULATION
echo 90000 > /sys/class/thermal/thermal_zone0/emul_temp
cat /sys/class/thermal/thermal_zone0/temp

六、trip point：温度阈值与它的类型 #

trip 就是温度档位。四种类型，enum thermal_trip_type 从 0 起（6.16 uapi；4.19 的 uapi 里还没有这个枚举）：

枚举 dts 字符串 语义 谁处理 动作
THERMAL_TRIP_ACTIVE "active" 主动散热档 governor 按档位算 state 风扇转速
THERMAL_TRIP_PASSIVE "passive" 必须降频降耗 governor 压 CPU 频率
THERMAL_TRIP_HOT "hot" 通知用户态 core 直接调 ops->hot() netlink 事件
THERMAL_TRIP_CRITICAL "critical" 再不管就烧 core 直接调 ops->critical() reboot / 关机

后两类不走 governor。step_wise 的 manage 一开头就把它们 continue 掉：

c
	if (trip->temperature == THERMAL_TEMP_INVALID ||
	    trip->type == THERMAL_TRIP_CRITICAL ||
	    trip->type == THERMAL_TRIP_HOT)
		continue;

理由直接：critical 和 hot 没有「降一档」的余地，要么通知要么关机。

c
struct thermal_trip {
	int temperature;              /* 毫摄氏度 */
	int hysteresis;               /* 相对回差，毫摄氏度 */
	enum thermal_trip_type type;
	u8 flags;                     /* 6.x：THERMAL_TRIP_FLAG_RW_TEMP / RW_HYST */
	void *priv;                   /* 驱动私有，ACPI 用它找回 acpi_thermal_trip */
};

hysteresis 是相对回差：trip 85000 加 hyst 2000，85℃ 触发降频，得降回 83℃ 以下才解除，避免阈值附近来回抖。比较值就是 td->threshold。

八、cooling device 的状态与 cpufreq 的对接 #

state 的语义不统一，方向必须去 ops 实现里看，别看数字：

注册者 type state 含义 到 max_state
cpufreq (cpu_cooling.c) thermal-cpufreq-N OPP 频率表倒序索引 最低频
devfreq devfreq 设备名 devfreq 档位 最低频
cpuidle idle 相关名 允许的 idle 深度 最浅 idle
PWM 风扇 风扇名 转速档 最高转速

CPU 侧的映射写在 cpu_cooling.c 注释里：最高 cooling state 对应最低频率，level 0 是最高频。所以 state 是频率表倒序索引。

注册时机是 cpufreq policy 初始化：

c
struct thermal_cooling_device *

{
	struct device_node *np = of_get_cpu_node(policy->cpu, NULL);

dynamic-power-coefficient 决定走不走 power cooling ops：给了才带 state2power/power2state，才会被 IPA 用上；不给就只有基础三件套。

从 state 落到频率是三跳。第一跳翻成 clipped_freq：

c
static int cpufreq_set_cur_state(struct thermal_cooling_device *cdev,
				 unsigned long state)
{
	...
	if (cpufreq_cdev->cpufreq_state == state)
		return 0;

	clip_freq = cpufreq_cdev->freq_table[state].frequency;
	cpufreq_cdev->cpufreq_state = state;
	cpufreq_cdev->clipped_freq = clip_freq;

第二跳触发 policy 重算，第三跳是 cpufreq policy notifier：thermal 在 CPUFREQ_ADJUST 事件里把 policy->max 压到 clipped_freq 之下：

看清这里的对象：改的是 policy->max，不是某个 governor 的偏好频率。这是 thermal 与 cpufreq 之间唯一的实质接口，第二十三章展开。

九、thermal governor：怎么决策 #

governor 拿到「温度 + 趋势 + trip 列表 + instance 列表」，要交出「每个 instance 的 target state」。

c
struct thermal_governor {
	const char *name;                     /* policy 字符串，sysfs 的 policy 节点 */
	int (*bind_to_tz)(struct thermal_zone_device *tz);
	void (*unbind_from_tz)(struct thermal_zone_device *tz);
	void (*trip_crossed)(struct thermal_zone_device *tz,
			     const struct thermal_trip *trip, bool crossed_up);
	void (*manage)(struct thermal_zone_device *tz);   /* 核心 */
	void (*update_tz)(struct thermal_zone_device *tz,
			  enum thermal_notify_event reason);  /* 绑定/解绑/权重变化 */
	struct list_head governor_list;
};

4.x 完全是另一个样子：char name[THERMAL_NAME_LENGTH]、int (*throttle)(tz, int trip)，没有 manage / update_tz / trip_crossed（已核对 4.19 thermal.h）。4.19 的 gov_step_wise.c 里只有 step_wise_throttle()。拿 4.x 的 governor 代码往 6.x 贴，改一百处都不够。

注册靠链接脚本的段：

c
#define THERMAL_TABLE(name)						\
	. = ALIGN(8);							\
	BOUNDED_SECTION_POST_LABEL(__##name##_thermal_table,		\
				   __##name##_thermal_table,, _end)

static struct thermal_governor thermal_gov_step_wise = {
	.name	= "step_wise",
	.manage	= step_wise_manage,
};
THERMAL_GOVERNOR_DECLARE(thermal_gov_step_wise);

这也是 6.x 的写法。4.19 是各自写 thermal_gov_xxx_register() 显式调 thermal_register_governor()——这些函数在新内核里根本不存在。

选谁当默认：core 初始化时拿 DEFAULT_THERMAL_GOVERNOR 和每个 name 比，相同就设为系统默认；再遍历所有 zone，名字对得上就绑定。运行时用 policy 节点换。

十、step_wise / power_allocator / fair_share 的差异 #

维度 step_wise power_allocator (IPA) fair_share
引入 早期（Durgadoss R, 2012） 3.19+（ARM Ltd., 2014 版权） 同 step_wise
依据 温度 vs trip + 趋势 温度误差 → PID → 功率预算 跨过了几个 trip
输出 每 tick 动一档 每 actor 的毫瓦额度 level × max_state / num_trips
cdev 要求 基础三件套 必须 power actor 基础三件套
弱项 锯齿，档位离散 参数不准就振荡 只看跨界次数，不看趋势

step_wise 的决策逻辑 #

注释把话说尽了：高于 trip 且趋势上升 → 提高一档；高于 trip 但趋势下降 → 不动；低于 trip 且趋势上升 → 不动；低于 trip 且趋势下降 → 降到下限，已在下限就 deactivate。

温度 ≥ threshold 温度 < threshold
RAISING cur_state + 1（clamp 到 lower..upper） 不动
DROPPING 不动 instance->lower（已在下限则 NO_TARGET）
STABLE 保持 instance->target 保持 
c
static unsigned long get_target_state(struct thermal_instance *instance,
				enum thermal_trend trend, bool throttle)
{
	struct thermal_cooling_device *cdev = instance->cdev;
	unsigned long cur_state;

	cdev->ops->get_cur_state(cdev, &cur_state);

	if (!instance->initialized) {
		if (throttle)
			return clamp(cur_state + 1, instance->lower, instance->upper);
		return THERMAL_NO_TARGET;
	}

	if (throttle) {
		if (trend == THERMAL_TREND_RAISING)
			return clamp(cur_state + 1, instance->lower, instance->upper);
	} else if (trend == THERMAL_TREND_DROPPING) {
		if (cur_state <= instance->lower)
			return THERMAL_NO_TARGET;
		return instance->lower;
	}

	return instance->target;
}

throttle 是「温度是否已达阈值」，trend 是趋势，两者一起定结果，THERMAL_NO_TARGET 表示无诉求、等同于放开。

4.19 比这复杂得多：多两个趋势值 THERMAL_TREND_RAISE_FULL / DROP_FULL 和一个 switch(trend) 四分支，RAISE_FULL 直接跳到 instance->upper，DROP_FULL 直接回 instance->lower。这两个枚举在 5.x 之后从 enum thermal_trend 里删了，老文章讲的「四条规则」实际是八条。

还有一处：4.19 的 thermal_zone_trip_update() 顺手维护 tz->passive 计数器，NO_TARGET ↔ 有值 的跳变会 ±1；6.x 把这段挪走了，update_passive_instance() 在 6.16 的 gov_step_wise.c 里已经搜不到。

三个 governor 怎么选 #

只有离散频率档、trip 写得密、没有可靠功率模型 → step_wise。有能量模型、OPP 电压齐全、能算 dynamic-power-coefficient → IPA，它给的是「预算 X 毫瓦，你自己挑频率」，比「降一档」精确。一个 zone 上挂好几个 cdev 且要按权重分摊 → fair_share，公式就是 new_state = P3 × P2 × P1，P3 = trip_level / num_trips，P2 = weight / total_weight，P1 = max_state。

fair_share 的 P3 拿 trip 数当分母，trip 写得随意估算就离谱。6.16 换了写法并加了 total_weight == 0 时按设备数平分的退化分支：

c
		dividend = trip_level;
		dividend *= cdev->max_state;
		divisor = tz->num_trips;
		if (total_weight) {
			dividend *= instance->weight;
			divisor *= total_weight;
		} else {
			divisor *= nr_instances;
		}
		instance->target = div_u64(dividend, divisor);

4.19 的 fair_share.c 没有这个分支，走的是 percentage = 100 / total_instance。

IPA 的骨架 #

两个关键 trip：第一个 passive 是开关点，不到它就全员满功率；最后一个 passive 是目标控制温度。

c
static void power_allocator_manage(struct thermal_zone_device *tz)
{
	struct power_allocator_params *params = tz->governor_data;
	const struct thermal_trip *trip = params->trip_switch_on;

	lockdep_assert_held(&tz->lock);

	if (trip && tz->temperature < trip->temperature) {
		reset_pid_controller(params);
		allow_maximum_power(tz);
		params->update_cdevs = false;
		return;
	}

	if (!params->trip_max)
		return;

	allocate_power(tz, params->trip_max->temperature);
	params->update_cdevs = true;
}

allocate_power() 的流程：每个 actor 报 get_requested_power，累出 max_allocatable_power，交 pid_controller() 算预算，divvy_up_power() 按权重分配，power_actor_set_power() 用 power2state 翻回 state。

PID 三项：

c
	err = control_temp - tz->temperature;
	p = mul_frac(err < 0 ? tz->tzp->k_po : tz->tzp->k_pu, err);
	i = mul_frac(tz->tzp->k_i, params->err_integral);
	d = mul_frac(tz->tzp->k_d, err - params->prev_err);
	d = div_frac(d, jiffies_to_msecs(tz->passive_delay_jiffies));

	power_range = sustainable_power + frac_to_int(p + i + d);
	power_range = clamp(power_range, (s64)0, (s64)max_allocatable_power);

k_po 和 k_pu 分开是因为「超过去」和「没烤热」两个方向的响应速度该不同。integral_cutoff 以下不再累积误差——系统大部分时间 idle 时累积正误差没意义。

dts 没给 sustainable_power 时 IPA 会估算，并在启动日志明说。这行别忽略：

text
thermal thermal_zone1: power_allocator: sustainable_power will be estimated

估算值来自每个 actor 在 lower 状态的功率之和，和真实散热能力差得远，PID 会明显跑偏。

绑定实现 thermal_bind_cdev_to_trip()：

c
static int thermal_bind_cdev_to_trip(struct thermal_zone_device *tz,
				     struct thermal_trip_desc *td,
				     struct thermal_cooling_device *cdev,
				     struct cooling_spec *cool_spec)
{
	/* lower default 0, upper default max_state */
	if (cool_spec->lower == THERMAL_NO_LIMIT)
		cool_spec->lower = 0;

	if (cool_spec->upper == THERMAL_NO_LIMIT) {
		cool_spec->upper = cdev->max_state;
		upper_no_limit = true;
	} else {
		upper_no_limit = false;
	}

	if (cool_spec->lower > cool_spec->upper || cool_spec->upper > cdev->max_state)
		return -EINVAL;

	dev->cdev = cdev;
	dev->trip = &td->trip;
	dev->upper = cool_spec->upper;
	dev->upper_no_limit = upper_no_limit;
	dev->lower = cool_spec->lower;
	dev->target = THERMAL_NO_TARGET;
	dev->weight = cool_spec->weight;

	dev->id = ida_alloc(&tz->ida, GFP_KERNEL);
	sprintf(dev->name, "cdev%d", dev->id);
	sysfs_create_link(&tz->device.kobj, &cdev->device.kobj, dev->name);
	snprintf(dev->attr_name, sizeof(dev->attr_name), "cdev%d_trip_point", dev->id);
	snprintf(dev->weight_attr_name, sizeof(dev->weight_attr_name), "cdev%d_weight", dev->id);
	device_create_file(&tz->device, &dev->attr);
	device_create_file(&tz->device, &dev->weight_attr);

	result = thermal_instance_add(dev, cdev, td);
	thermal_governor_update_tz(tz, THERMAL_TZ_BIND_CDEV);
	return 0;
}

四个要点：lower 默认 0、upper 默认 max_state；校验 lower <= upper <= max_state 差一个就 -EINVAL；instance id 来自 zone 自己的 ida，所以 cdevN 是 zone 内序号不是全局 cdev id；绑定完通知 governor（THERMAL_TZ_BIND_CDEV 这个事件值 4.19 的 thermal.h 里还没有）。一个挂两个 trip 的 zone 目录就是多出一组 cdev0/cdev1 的符号链接、cdevN_trip_point 和 cdevN_weight。

十三、PM QoS 要解决什么：性能与功耗的交换 #

省电的手段（进更深 idle、关时钟、断供电、降频）全都在抬高「从事件发生到被响应」的时间。串口控制器只有几字节 FIFO，CPU 或 DMA 必须在填满前读走，否则丢数据或降速；CPU 睡太深，醒来太慢，数据就没了。

所以系统里有一批「不能睡太死」的实体，PM QoS 收集它们的意见汇总成一条可查的红线。

它不做的三件事同样重要：不测量实际服务质量（内核不关心你实际多快，只关心你提了什么要求）；不做取舍（只算极值，不判断要求合不合理）；不强制执行（红线摆着，cpuidle/cpufreq 自己决定听不听）。

后果就是踩坑最多的地方：add 了 request 不等于生效，requestee 得真去查才行。

角色 干什么 典型成员
requestor 提约束 应用进程、GPU 驱动、net 驱动、flash 驱动
PM QoS core 汇总、算极值 kernel/power/qos.c、drivers/base/power/qos.c
requestee 查询并遵守 cpuidle、cpufreq、pm domain、runtime PM

源码自己的叫法是「Dependents on a QoS value」和「Watchers of QoS value」，写在两个 qos.c 的文件头。PM QoS 的哲学是「刚好够用」，没有留余量的概念：申请 200us 就给 200us，写小了白耗电，写大了出事。

十四、QoS 的两类约束：最小与最大 #

系统级 4 个（PM QoS class）：

class 单位 聚合 含义
PM_QOS_CPU_DMA_LATENCY us MIN 事件发生到 CPU/DMA 响应的最大允许延迟
PM_QOS_NETWORK_LATENCY us MIN 网络收发最大允许延迟
PM_QOS_NETWORK_THROUGHPUT kbit/s MAX 至少要保证的带宽
PM_QOS_MEMORY_BANDWIDTH kbit/s SUM 内存带宽需求总和

设备级 3 类（per-device PM QoS）：

类型 聚合 含义
DEV_PM_QOS_RESUME_LATENCY MIN 从 suspend 恢复到可用最多允许多久
DEV_PM_QOS_LATENCY_TOLERANCE MIN active 状态下能容忍多大响应延迟
DEV_PM_QOS_FLAGS 按位或 对设备行为的离散要求

5.x 又加了 DEV_PM_QOS_MIN_FREQUENCY / DEV_PM_QOS_MAX_FREQUENCY，见第二十一章。

framework 文件 管的范围
PM QoS classes kernel/power/qos.c 系统级 4 个 class
per-device PM QoS drivers/base/power/qos.c 每台设备一套
公共头文件 include/linux/pm_qos.h 数据结构与声明

两者目标一样（提供 add/update/remove、算极值、提供查询），差别只在作用域。

PM_QOS_SUM 要单独说。它在 enum pm_qos_type 里，注释写「return the sum」，但 5.10 的 pm_qos_get_value() 只实现 MIN 和 MAX，SUM 落进 default 打 WARN：

		return plist_first(&c->list)->prio;
	case PM_QOS_MAX:
		return plist_last(&c->list)->prio;
	default:
		WARN(1, "Unknown PM QoS type in %s\n", __func__);

所以 5.10 上没有任何在用的 constraint 是 SUM。老文章说「memory_bandwidth 用求和」，那是还有 PM_QOS_MEMORY_BANDWIDTH 这个 class 的年代；这个 class 在 5.x 重构里整个删了。

十六、struct pm_qos_constraints 与它的目标值 #

三层全建在它上面：

c
/*
 * Note: The lockless read path depends on the CPU accessing target_value
 * or effective_flags atomically.  Atomic access is only guaranteed on all CPU
 * types linux supports for 32 bit quantites
 */
struct pm_qos_constraints {
	struct plist_head list;         /* plist，按 prio 降序，取最小是 O(1) */
	s32 target_value;               /* 当前生效值，requestee 读的就是它 */
	s32 default_value;              /* 没有 request 时该用的值 */
	s32 no_constraint_value;        /* 链表为空时 pm_qos_get_value() 的返回 */
	enum pm_qos_type type;          /* 聚合方向 */
	struct blocking_notifier_head *notifiers;
};

用 plist 而不是普通 list，就是为了让「取最小」变成 plist_first()。三个「值」最容易混，拿全局 CPU latency 的实测数据对照：target_value、default_value、no_constraint_value 在 5.10 里都等于 PM_QOS_CPU_LATENCY_DEFAULT_VALUE（2 秒），恰好相等所以看着冗余。

但 per-device 上就不一样了：

c
	c = &qos->resume_latency;
	c->target_value = PM_QOS_RESUME_LATENCY_DEFAULT_VALUE;
	c->default_value = PM_QOS_RESUME_LATENCY_DEFAULT_VALUE;
	c->no_constraint_value = PM_QOS_RESUME_LATENCY_NO_CONSTRAINT;

	c = &qos->latency_tolerance;
	c->target_value = PM_QOS_LATENCY_TOLERANCE_DEFAULT_VALUE;
	c->default_value = PM_QOS_LATENCY_TOLERANCE_DEFAULT_VALUE;
	c->no_constraint_value = PM_QOS_LATENCY_TOLERANCE_NO_CONSTRAINT;

resume_latency 的两个宏都是 PM_QOS_LATENCY_ANY = S32_MAX，意思是「随便睡，没意见」；latency_tolerance 的 default 是 0，no_constraint 是 -1。所以 -1 在 latency_tolerance 上是「暂无约束」的哨兵，和「容忍 0 延迟」正好相反。

type 只有两个能用的取值：

enum pm_qos_type 聚合方式 用在
PM_QOS_MIN plist_first(&c->list)->prio latency 类（越小越严）
PM_QOS_MAX plist_last(&c->list)->prio throughput 类、min_freq
PM_QOS_UNITIALIZED 无效（源码就是这个拼写） 初始化前
PM_QOS_SUM 5.10 未实现，落 default 打 WARN 历史遗留

PM_QOS_UNITIALIZED 少一个 N，是源码里的拼写错误，不是我打错。

聚合在 pm_qos_update_target()：

c
	prev_value = pm_qos_get_value(c);
	if (value == PM_QOS_DEFAULT_VALUE)
		new_value = c->default_value;
	else
		new_value = value;

	switch (action) {
	case PM_QOS_REMOVE_REQ:
		plist_del(node, &c->list);
		break;
	case PM_QOS_UPDATE_REQ:
		plist_del(node, &c->list);
		fallthrough;
	case PM_QOS_ADD_REQ:
		plist_node_init(node, new_value);
		plist_add(node, &c->list);
		break;
	}

	curr_value = pm_qos_get_value(c);
	pm_qos_set_value(c, curr_value);

	if (prev_value == curr_value)
		return 0;

	if (c->notifiers)
		blocking_notifier_call_chain(c->notifiers, curr_value, NULL);

	return 1;

三件事：返回值 1 表示「聚合值变了」，会一路传到调用者；value == PM_QOS_DEFAULT_VALUE（-1）被替换成 default_value，是「走默认」不是「取消约束」；notifier 在解锁之后调，而且用 blocking_notifier_call_chain()，意味着回调里可以睡眠。

static void pm_qos_flags_remove_req(struct pm_qos_flags *pqf,
				    struct pm_qos_flags_request *req)
{
	s32 val = 0;

	list_del(&req->node);
	list_for_each_entry(req, &pqf->list, node)
		val |= req->flags;

	pqf->effective_flags = val;
}

删一个 request 要把剩下的重新或一遍，所以 flags 数量不该多。

十八、per-device PM QoS：latency 与 flags #

三块需求来源各不相同。

resume_latency：runtime PM 下引用计数归零就 suspend，而 suspend/resume 要花时间（信息在 pm domain 里），系统里其他实体对这个设备的响应时间有要求。framework 收集起来交给 runtime PM，由它决定是否 suspend。

latency_tolerance：复杂设备在 active 状态下为了省功耗也会自行进省电态，代价是响应变慢。设备提供了 .set_latency_tolerance 回调（在 dev_pm_info 里），上层就能告诉它「最多能忍多久」。framework 汇总后通过这个回调推下去。

flags：设备 suspend 之后 pm domain 还会切供电，切不切看两个 flag：

flag 宏 含义
不许断电 PM_QOS_FLAG_NO_POWER_OFF 这个设备不能掉电
需要唤醒 PM_QOS_FLAG_REMOTE_WAKEUP 要能当唤醒源

注意 4.19 的 pm_qos.h 里只有 NO_POWER_OFF，没有 REMOTE_WAKEUP（已核对）。素材写「当前有两种」，按 4.19 只能确认一种。

c
struct device    { ... struct dev_pm_info power; ... };
struct dev_pm_info { ... struct dev_pm_qos *qos; ... };

struct dev_pm_qos {
	struct pm_qos_constraints resume_latency;
	struct pm_qos_constraints latency_tolerance;
	struct pm_qos_flags flags;
	struct dev_pm_qos_request *resume_latency_req;      /* 用户态专属请求 */
	struct dev_pm_qos_request *latency_tolerance_req;
	struct dev_pm_qos_request *flags_req;
};

前三个是 constraint，后三个是 sysfs 提出来的请求单独存的句柄，便于节点移除时精准撤回。这个结构体懒分配：drivers/base/power/qos.c 文件头写明只有第一次 dev_pm_qos_add_request() 才分配，设备移除才释放，全程一把全局 mutex。power.qos 是 NULL 只代表「从来没被申请过」，不是坏了。5.10 还多一组频率：struct freq_constraints freq;（4.19 没有，已核对）。

二十、QoS 如何影响 cpuidle 的深度选择 #

链路三段。第一段，两条来源合成一个数：

c
s64 cpuidle_governor_latency_req(unsigned int cpu)
{
	struct device *device = get_cpu_device(cpu);
	int device_req = dev_pm_qos_raw_resume_latency(device);
	int global_req = cpu_latency_qos_limit();

	if (device_req > global_req)
		device_req = global_req;

	return (s64)device_req * NSEC_PER_USEC;
}

dev_pm_qos_raw_resume_latency(cpu_device) 是 per-device 那条路，cpu_latency_qos_limit() 是全局那条，取小——最严格的说了算。全局说 500us、CPU 设备说 100us，就按 100us。

第二段，governor 拿它当硬上限：

c
	idx = -1;
	for (i = 0; i < drv->state_count; i++) {
		struct cpuidle_state *s = &drv->states[i];

		if (dev->states_usage[i].disable)
			continue;

		if (idx == -1)
			idx = i; /* first enabled state */

		if (s->target_residency_ns > predicted_ns) {
			...
			break;
		}
		if (s->exit_latency_ns > latency_req)
			break;

		idx = i;
	}

latency_req 就是第一段的结果。循环按「越往后越深」扫，某个状态的 exit_latency_ns > latency_req 就立刻 break，绝不能选它和更深的状态。这就是 PM QoS 对 cpuidle 的全部影响力：一道单向闸门，只允许削减深度，不允许加深。它是上限，不是目标。

menu 还会再收紧一次，用「预测空闲时长 ÷ 性能乘数」，performance_multiplier() 是 1 + 10 * nr_iowaiters：

c
	interactivity_req = div64_u64(predicted_ns, performance_multiplier(nr_iowaiters));
	if (latency_req > interactivity_req)
		latency_req = interactivity_req;

QoS 给的是用户允许的最大值，governor 自己按负载又砍一刀，两个约束叠着取更小的。

第三段容易漏：约束变化要把 CPU 叫醒。

c
static void cpu_latency_qos_apply(struct pm_qos_request *req,
				  enum pm_qos_req_action action, s32 value)
{
	int ret = pm_qos_update_target(req->qos, &req->node, action, value);
	if (ret > 0)
		wake_up_all_idle_cpus();
}

ret > 0 表示聚合值真变了，这时必须 wake_up_all_idle_cpus()：某个进程刚提出「我要 50us」，而 CPU 已经睡在 2ms 才能醒的状态里，不叫醒就没人理这个请求。所以每次约束变化所有 idle CPU 都会被踢一脚，QoS 别乱刷。

二十一、QoS 如何影响 cpufreq 的下限 #

老内核里 cpufreq 上的 QoS 只有「用户态限制」一层，写 scaling_max_freq 直接改 policy。4.19 就是这样，用户态直接覆盖，没有 QoS 记账：

c
#define store_one(file_name, object)			\
{									\
	memcpy(&new_policy, policy, sizeof(*policy));			\
	new_policy.min = policy->user_policy.min;			\
	new_policy.max = policy->user_policy.max;			\
	ret = sscanf(buf, "%u", &new_policy.object);			\
	temp = new_policy.object;					\
	ret = cpufreq_set_policy(policy, &new_policy);			\
	if (!ret)							\
		policy->user_policy.object = temp;			\
}

5.x 之后彻底改了，scaling_min_freq / scaling_max_freq 从特权接口变成 QoS request：

c
#define store_one(file_name, object)			\
{									\
	ret = sscanf(buf, "%lu", &val);					\
	if (ret != 1)							\
		return -EINVAL;						\
	ret = freq_qos_update_request(policy->object##_freq_req, val);	\
	return ret >= 0 ? count : ret;					\
}

调的是 policy->min_freq_req / max_freq_req，用户态、驱动、thermal 现在站在同一条队列里。这两个 request 在 policy 初始化时创建：

c
		policy->min_freq_req = kzalloc(2 * sizeof(*policy->min_freq_req),
					       GFP_KERNEL);

		ret = freq_qos_add_request(&policy->constraints,
					   policy->min_freq_req, FREQ_QOS_MIN,
					   policy->min);

		policy->max_freq_req = policy->min_freq_req + 1;

		ret = freq_qos_add_request(&policy->constraints,
					   policy->max_freq_req, FREQ_QOS_MAX,
					   policy->max);

一次 kzalloc 出两个 request，max_freq_req = min_freq_req + 1 省一次分配。两条 constraint 分别是：

c
struct freq_constraints {
	struct pm_qos_constraints min_freq;
	struct blocking_notifier_head min_freq_notifiers;
	struct pm_qos_constraints max_freq;
	struct blocking_notifier_head max_freq_notifiers;
};

struct freq_qos_request {
	enum freq_qos_req_type type;
	struct plist_node pnode;
	struct freq_constraints *qos;
};

关键在初始化时的两个 type，它们决定聚合方向：

c
	c = &qos->min_freq;
	c->target_value = FREQ_QOS_MIN_DEFAULT_VALUE;   /* 0 */
	c->default_value = FREQ_QOS_MIN_DEFAULT_VALUE;
	c->no_constraint_value = FREQ_QOS_MIN_DEFAULT_VALUE;
	c->type = PM_QOS_MAX;        /* 下限取所有 request 的最大值 */

	c = &qos->max_freq;
	c->target_value = FREQ_QOS_MAX_DEFAULT_VALUE;   /* S32_MAX */
	c->default_value = FREQ_QOS_MAX_DEFAULT_VALUE;
	c->no_constraint_value = FREQ_QOS_MAX_DEFAULT_VALUE;
	c->type = PM_QOS_MIN;        /* 上限取所有 request 的最小值 */

「下限取最大，上限取最小」，所有区间类约束都是这个写法，和 class 层的 latency/throughput 完全同构。所以 thermal 压上限、进程托下限，两边不打架，各在自己的链表里挤。

scaling_min_freq / max_freq 现在可写任何值，freq_qos_update_request() 不拒绝。把 scaling_max_freq 写得比 scaling_min_freq 低不再返回 -EINVAL，两个 request 都进队列，由驱动在重算时消化。查询侧在 cpufreq_set_policy()：

c
	/*
	 * PM QoS framework collects all the requests from users and provide us
	 * the final aggregated value here.
	 */
	new_data.min = freq_qos_read_value(&policy->constraints, FREQ_QOS_MIN);
	new_data.max = freq_qos_read_value(&policy->constraints, FREQ_QOS_MAX);

policy->min / max 不再是「用户写进去的值」，是「QoS 聚合出来的值」。

约束变化到重算隔一次调度。policy 上的 notifier 只做一件事：

c
static int cpufreq_notifier_min(struct notifier_block *nb, unsigned long freq,
				void *data)
{
	struct cpufreq_policy *policy = container_of(nb, struct cpufreq_policy, nb_min);

	schedule_work(&policy->update);
	return 0;
}

worker 里 refresh_frequency_limits(policy) → cpufreq_set_policy()。热路径上疯狂改 QoS 会把这个 worker 淹掉。5.10 还有 cpufreq_update_limits()，把驱动上报的「硬件状态变了」和 QoS 变化接到同一条路上（有 update_limits 回调就调它，否则走 cpufreq_update_policy()）。per-device 那层也一样：DEV_PM_QOS_MIN_FREQUENCY / MAX_FREQUENCY 走 freq_qos_apply()，和 policy 上是同一套代码，只是挂在设备上。

二十三、两个框架在 cpufreq 上的会合 #

作用方 手段 落到哪里 生效时机
thermal cdev cpufreq_set_cur_state() → clipped_freq → cpufreq_update_policy() notifier 里 cpufreq_verify_within_limits(policy, 0, clipped_freq) 每次 monitor 判完温度
PM QoS 全局 freq_qos_update_request() policy->constraints 聚合 notifier → schedule_work(&policy->update)
PM QoS per-device dev_pm_qos_add_request(MIN/MAX_FREQUENCY) 设备上的 qos->freq notifier 触发重算
用户态 sysfs 写 scaling_min_freq / max_freq 就是上面第一个 QoS request 同上

4.19 里 thermal 是唯一直接改 policy->max 的人。它挂在 cpufreq_policy_notifier_list 上，CPUFREQ_ADJUST 事件里调 cpufreq_verify_within_limits()；而 cpufreq_set_policy() 在调 notifier 之前先把 new_policy.min/max 从 user_policy 拷过来，再 verify、再 ADJUST、再 verify，最后才写 policy->min/max。规矩就一句：policy->max = min(用户设的上限, thermal 允许的上限)。

5.10 里 policy->max 由 QoS 聚合，来自 freq_qos_read_value(&policy->constraints, FREQ_QOS_MAX)。thermal 的 notifier 仍然存在、仍然调 cpufreq_verify_within_limits()，但这次它改的是驱动 verify 之前的副本，最终值还要过一遍驱动。

于是有个边界必须记住：thermal 压的 max 和 QoS 的 max 谁赢，取决于驱动的 verify()。驱动的职责是「把不符合硬件规格的值修掉」，一般做 clamp(policy->max, cpuinfo.min, cpuinfo.max) 和 min <= max 的保证，但它不知道 thermal 和 QoS 是两个来源。两边都在往下压、没人往上抬，所以最后生效的是更小的那个。

cpuidle 那边只有一个约束源（thermal 不直接管 idle 深度）：

约束源 落到哪里 谁读
全局 CPU latency cpu_latency_constraints.target_value cpu_latency_qos_limit()
CPU 设备的 resume_latency cpu_dev->power.qos->resume_latency dev_pm_qos_raw_resume_latency()
二者合成 cpuidle_governor_latency_req() 取小 menu / teo 的 latency_req

二十四、易错点速查 #

thermal 侧：

  1. temperature 单位是毫摄氏度，85000 才是 85℃。写 85 会得到一个永不触发的 trip。
  2. cooling-map 的顺序是 <&cdev upper lower>，写反了 upper < lower，thermal_bind_cdev_to_trip() 返回 -EINVAL，整条 map 绑不上，现象是 zone 目录下没有 cdevN 链接。
  3. #cooling-cells = <2> 不能漏，漏了 CPU 不会被注册成 cdev，of_cpufreq_cooling_register() 静默返回。
  4. cdev 的 state 方向不统一：CPU 越大越省电，风扇越大越费电。看 ops 实现，别看数字。
  5. critical 和 hot 不走 governor。把它们写进 cooling-map 不报错，但永远不被处理，指望它降频是白等。
  6. hysteresis 是相对回差：trip 85000 + hyst 2000 的解除点是 83000，不是 85000。
  7. 4.x 的 governor 是 throttle(tz, trip)，5.x+ 是 manage(tz)。往新内核搬 4.x governor 代码，改一百处都不够。
  8. THERMAL_TREND_RAISE_FULL / DROP_FULL 在 5.x 之后已删，见到这两个符号就说明代码是 4.x 的。
  9. IPA 必须配 sustainable_power，否则启动日志出现 sustainable_power will be estimated，估算值来自每个 actor 最低档功率之和，和真实散热能力无关。
  10. IPA 要求所有挂上来的 cdev 都实现 power actor 接口，一个不支持就 power_allocator: binding failed。
  11. policy 节点只能写 available_policies 里有的名字。
  12. polling-delay 写 0 表示中断驱动，此时驱动必须实现 set_trips，否则没有温度更新来源。

PM QoS 侧：

  1. pm_qos_* 在 5.x 改名成 cpu_latency_qos_*，class 参数消失，旧代码在新内核编译不过。
  2. pm_qos_update_request_timeout() 与 struct pm_qos_request 里的 delayed_work 在 5.10 已删除。
  3. struct pm_qos_request 的成员从 int pm_qos_class 变成 struct pm_qos_constraints *qos。
  4. PM_QOS_DEFAULT_VALUE（-1）是「用 default_value」不是「取消约束」，取消要 remove。
  5. latency_tolerance 上 no_constraint_value 是 -1、default_value 是 0，一个表示「暂无约束」一个表示「一点延迟都不忍」，语义相反。
  6. enum pm_qos_type 里的 PM_QOS_UNITIALIZED 少一个 N，是源码拼写错误。
  7. PM_QOS_SUM 在 5.10 的 pm_qos_get_value() 里没实现，落 default 打 WARN。
  8. enum dev_pm_qos_req_type 在 5.10 插入 MIN/MAX_FREQUENCY 后 FLAGS 从 3 变 5，硬编码会错。
  9. dev->power.qos 懒分配，为 NULL 表示「从没人申请过」，不是错误状态。
  10. dev_pm_qos_read_value() 在 5.10 需要 type 参数，4.19 是单参数。
  11. dev_pm_qos_add_global_notifier() / remove_global_notifier() 在 5.10 头文件里已不存在。
  12. 提 LATENCY_TOLERANCE 要求设备实现了 power.set_latency_tolerance，否则 -EINVAL。
  13. 返回值 1 是「聚合值变了」、0 是「没变」，只有负数是错误。只看 < 0 会错过需要重新决策的时机。
  14. /dev/cpu_dma_latency 只有写 4 字节才按二进制解释，其他长度按十六进制解析。
  15. 打开 /dev/cpu_dma_latency 就 add 了一个 request，初值是默认值（2 秒）不是「无约束」，忘了 close 会一直挂着。
  16. cpu_latency_qos_apply() 在聚合值变化时 wake_up_all_idle_cpus()，热路径频繁 update 会带来调度开销。
  17. QoS 对 cpuidle 只是上限不是目标，它只保证「不比这个更深」。
  18. cpuidle_governor_latency_req() 是取小不是取大，两条来源谁严格听谁的。
  19. scaling_min_freq / max_freq 现在是 QoS request，写反了不返回 -EINVAL，要验证冲突得看 cpuinfo_cur_freq 或 trace。
  20. thermal 压 max 和 QoS 压 max 是两条独立的路，最终取更小的，中间隔着驱动的 verify()。别指望在 policy->max 上看到某个来源的原始值。

跨框架：

  1. 两个框架都不「执行」约束：thermal 的 governor 只改 instance->target，硬件写入由 thermal_cdev_update() 做；PM QoS 只改一个整数，cpuidle/cpufreq 得自己读。任何一环没接上，约束就是摆设。
  2. 调 idle 深度是 QoS 的事，thermal 插不上手；压频率两个都能干。排「为什么不进深 idle」先看 QoS，排「为什么频率上不去」两边都看。
