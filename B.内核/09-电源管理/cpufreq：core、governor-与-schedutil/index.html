这篇只讲一件事：CPU 跑多快。cpufreq framework 通过调电压和频率，在性能与功耗之间选一个点，这套动作叫 DVFS（Dynamic Voltage/Frequency Scaling）。它和《CPU 电源管理：topology、hotplug 与 cpuidle》是正交的两件事：那篇讲「跑不跑」（core 关不关、进不进 idle），这篇讲「跑多快」。两者只在「governor 与 cpuidle 的配合」「热插拔时 policy 的重建」这两处交叉，交叉点本文会指出来，细节回到那篇看。

讲什么：cpufreq core 的 policy 抽象与生命周期、frequency table、set_policy/set_target 的分工、通知链、per-policy 与 per-CPU 的同步；driver 侧怎么写 init/exit/target/get、target 与 target_index 两套接口的取舍；governor 的五个回调与五类策略；schedutil 的代码级流程（PELT 利用率怎么进来、怎么映射到频率、怎么限频、iowait boost 怎么算）；ARM big.LITTLE 的虚拟 frequency domain 与 cluster 切换。

不讲什么：regulator/OPP/clock framework 的内部实现（只当作可用接口）、cpuidle 的 idle state 选择、HMP 调度器本身、EAS 的能量模型数学推导。素材里的 energy-aware scheduling 只在必要处提一句。

版本边界先说清：素材是 3.x~4.x 的代码，schedutil 那篇用的是 5.10.61。cpufreq 的骨架从 3.18 到 5.x 变化不大，但 governor 的回调形态在 4.x~5.x 之间换过一轮，凡涉及版本差异的地方都单独标了版本；标了「未验证」的就是我没有对着该版本源码逐行核对过的。

一、cpufreq 要解决什么：在性能与功耗之间选点 #

对 CPU core 来说，功耗和性能是一对矛盾。动态功耗近似与频率成正比、与电压的平方成正比，而频率和电压又基本同向变化：想跑快，两个都得往上抬。cpufreq 要做的就是在运行过程中把这两个量放到位。

拆开看只有两个问题：

  1. 谁来控制频率和电压？
  2. 什么时候改？

针对这两问，硬件给得出两种实现。

实现一：CPU 自己调。 软件只需要告诉它一个频率范围（scaling_min_freq 到 scaling_max_freq，也就是 policy），core 内部根据自身负荷自行升降频。关键点 1 交给硬件，关键点 2 软件只给一个粗粒度的场景提示。软件参与度低，省电效率也就一般。

实现二：软件全管。 core 不做任何逻辑，OS 侧基于 clock framework 和 regulator framework 的接口去改频率改电压；改的时机由软件根据场景决定——用户手动切省电模式，或者内核根据负载自动调整。这条路的前提是频率切换要足够快，因为切换越频繁，切换开销本身占的比例就越大。

内核的 cpufreq framework 主要服务的是实现二，同时用 setpolicy 回调给实现一留了口子。整套框架的软硬件分层：

text
用户空间  /sys/devices/system/cpu/cpuX/cpufreq/*
   |  （sysfs 读写：governor 切换、min/max 限幅、setspeed）
cpufreq core（drivers/cpufreq/cpufreq.c）
   |-- cpufreq governor（策略：performance/powersave/ondemand/conservative/schedutil）
   |-- cpufreq stats（time_in_state / trans_table 统计）
   |-- 通知链（policy notifier + transition notifier）
cpufreq driver（平台相关：init/verify/target_index/get）
   |
cpu subsystem driver / OPP / clock framework / regulator framework
   |
硬件（PLL、供电域、CPU core）

对下，driver 通过 OPP 表、clock、regulator 把「某个频率 + 对应电压」真正写进硬件；对上，core 用 sysfs 和通知链把能力与事件暴露出去；内部，所有逻辑围绕三个数据结构打转：struct cpufreq_driver、struct cpufreq_policy、struct cpufreq_governor。

有个特例得先说明：arm_big_little 这个 driver 严格说不是 cpufreq 的常规用法，它借用 cpufreq 的接口去做 big/LITTLE cluster 切换。原因在第二十四章解释。读 core 和 driver 的部分时，可以直接把它当成普通 driver 看待，只在最后一章展开。

二、cpufreq 的四个角色：core / driver / governor / 用户态 #

cpufreq 里同时有四个角色在干活，职责边界清楚了，后面所有代码才读得下去。

角色 数据结构 谁实现 干什么 不干什么
core cpufreq_policy 及全局链表 内核框架（drivers/cpufreq/cpufreq.c） 创建 policy、维护 frequency table、调用 driver 回调、跑通知链、导出 sysfs 不做平台相关的频率写入，不决定具体频率
driver struct cpufreq_driver 平台/BSP 工程师 提供 frequency table、实现 init/verify/target_index/get，真正写寄存器 不关心「为什么」要这个频率
governor struct cpufreq_governor 通用策略代码 决定「跑多快」：从调度器或采样数据算出目标频率，再调 driver 不直接碰硬件，不越出 policy 的 min/max
用户态 sysfs 文件 用户空间程序 切 governor、设 min/max、userspace 模式下直接写频率 不能绕过 verify 与 policy 范围

关键的一句话分工：policy 定范围，governor 定数值，driver 定实现。policy 的 min/max 是一个「可调区间」，governor 在该区间内选一个具体频点，driver 把那个频点翻译成寄存器值。

sysfs 接口（/sys/devices/system/cpu/cpu0/cpufreq/）：

文件 含义 权限
affected_cpus / related_cpus 该 policy 影响的 online CPU / online+offline 全量 只读
cpuinfo_cur_freq 硬件当前真实频率（走 driver->get） 只读
cpuinfo_max_freq / cpuinfo_min_freq 硬件能力上下限 只读
cpuinfo_transition_latency 切换延迟，单位 ns 只读
scaling_available_frequencies 可用频点列表，来自 frequency table 只读
scaling_available_governors / scaling_driver 已注册 governor 列表 / 当前 driver 名 只读
scaling_governor 当前 governor 读写
scaling_max_freq / scaling_min_freq 调频范围 读写
stats/time_in_state / total_trans / trans_table 每频点累计时间 / 总切换次数 / 切换矩阵 只读

几个容易踩的坑：所有 core 统一调频时只有 cpu0 下有真实目录，其它 cpu 的 cpufreq 是符号链接，随便进一个都行；各 core 能独立调频时不同 cpu 目录下的内容就不一样。affected_cpus 不含 offline 的 core，related_cpus 含，排查热插拔问题时看后者。cpuinfo_cur_freq 问硬件，scaling_cur_freq 问软件，两者在 fast switch 路径下可能出现短暂不一致。

最简单的实战用法是 userspace 模式，用 shell 就能把频率钉死（scaling_cur_freq 是软件视角的当前频率，只读，常和 cpuinfo_cur_freq 对照看）：

bash
cd /sys/devices/system/cpu/cpu0/cpufreq/
cat scaling_governor                         # 当前用哪个
cat cpuinfo_cur_freq; cat scaling_cur_freq   # 硬件视角 vs 软件视角
echo userspace > scaling_governor            # 切到 userspace
echo 1200000 > scaling_max_freq              # 先把范围放开
echo 1200000 > scaling_min_freq
echo 1200000 > scaling_setspeed              # 最后写目标频点

注意顺序：如果目标频点落在 scaling_max_freq/scaling_min_freq 之外，写 scaling_setspeed 会被 verify 打回来，所以先把范围调好。这一点在调试时被误解过很多次——不是 setspeed 不生效，是范围不允许。

三、struct cpufreq_policy：一个调频域的完整状态 #

struct cpufreq_policy 是整个框架里最抽象的结构。它回答一个具体问题：cpufreq driver 对应的「设备」是什么？答案是 policy。内核把 CPU device 挂在 cpu_subsys 这个 bus 上，cpufreq 是 CPU device 的一项功能，被抽象成 subsys interface；当 CPU device 与 CPU driver 匹配时，bus core 回调 interface 的 add_dev，由 cpufreq core 造出代表「调频策略」的 policy，再和 cpufreq driver 配对——这一步等价于设备模型里的 probe。

也就是说，policy 是「一个调频域」的完整状态：哪些 CPU 共享它、频率范围是多少、当前是哪个 governor、表格在哪、锁怎么用。下面是 3.18 版本的字段全集（后续版本有增删，见文末勘误）。

c
struct cpufreq_cpuinfo {
	unsigned int	max_freq;
	unsigned int	min_freq;
	unsigned int	transition_latency;	/* ns */
};

struct cpufreq_real_policy {
	unsigned int	min, max;		/* kHz */
	unsigned int	policy;			/* CPUFREQ_POLICY_* */
	struct cpufreq_governor	*governor;
};

struct cpufreq_policy {
	cpumask_var_t		cpus;		/* 仅 online CPU */
	cpumask_var_t		related_cpus;	/* online + offline */
	unsigned int		shared_type;	/* ACPI: ANY 或 ALL */
	unsigned int		cpu, last_cpu;	/* 当前/上一个管理它的 CPU 号 */
	struct clk		*clk;
	struct cpufreq_cpuinfo	cpuinfo;	/* 硬件固定能力 */

	unsigned int		min, max;	/* 调频范围，kHz */
	unsigned int		cur;		/* 当前频率，kHz */
	unsigned int		restore_freq;	/* 切换前保存的频率 */
	unsigned int		suspend_freq;	/* suspend 期间要设的频率 */

	unsigned int		policy;		/* CPUFREQ_POLICY_PERFORMANCE/_POWERSAVE */
	struct cpufreq_governor	*governor;
	void			*governor_data;	/* governor 私有数据 */
	bool			governor_enabled;

	struct work_struct	update;		/* IRQ 上下文里的延迟处理 */
	struct cpufreq_real_policy	user_policy;	/* 用户设置快照 */
	struct cpufreq_frequency_table	*freq_table;

	struct list_head	policy_list;
	struct kobject		kobj;
	struct completion	kobj_unregister;
	struct rw_semaphore	rwsem;		/* 读加读锁，写/拆 policy 加写锁 */

	bool			transition_ongoing;
	spinlock_t		transition_lock;
	wait_queue_head_t	transition_wait;
	struct task_struct	*transition_task;

	void			*driver_data;	/* driver 私有 */
};

把字段按「谁写、能不能改」分成四组，比逐字段背诵有用：

分组 字段 写入者 运行时可改 说明
拓扑 cpus、related_cpus、shared_type、cpu、last_cpu driver->init 填，core 修剪 热插拔时变 cpus 只有 online，related_cpus 全量
硬件能力 cpuinfo.max_freq、cpuinfo.min_freq、cpuinfo.transition_latency、clk driver->init 不可改 能力上限，改不了
调频策略 min、max、cur、policy、restore_freq、suspend_freq core 与 governor 可改（sysfs/PM QoS） min/max 是 governor 的边界
运行时状态 governor、governor_data、governor_enabled、user_policy、freq_table、driver_data core + governor 切换 governor 时变 governor_data 是 governor 的私有数据

几组容易绕晕的字段单独说。

min/max 与 cpuinfo.min_freq/cpuinfo.max_freq 不是一回事。前者是「当前允许的策略范围」，用户可以随时改，热限频（thermal）也会往下压；后者是「硬件的物理能力」，driver init 时定死。所有 verify 的第一件事就是保证前者不越出后者。

policy 这个字段名字起得很费解，它和结构体同名，但它其实是 CPUFREQ_POLICY_PERFORMANCE 或 CPUFREQ_POLICY_POWERSAVE 二选一的枚举，只在 driver 提供 setpolicy 回调时才有意义——用来告诉那种「自己能调频」的硬件：现在要偏性能还是偏省电。名字是历史包袱，读代码时别被它误导。

user_policy 是 cpufreq_real_policy 的一份快照，保存用户设置的 min/max/policy/governor。热插拔或 resume 重建 policy 后，靠它把用户之前的设置恢复回来，否则一次 hotplug 就能把你的 scaling_max_freq 打回默认值。

rwsem 的规则在注释里写得很清楚：读 policy 结构的走 down_read；会写 policy 或可能整体拿走 policy 的（比如 CPU hotplug）走 down_write；并且锁不能跨越 CPUFREQ_GOV_POLICY_EXIT 持有，所以 cpufreq_set_policy 里会先 up_write 再调 governor exit，再 down_write 回来。

transition_* 四个字段是一组同步设施：transition_ongoing 标记有一次频率切换正在进行，transition_lock 保护它，transition_wait 让并发的切换请求排队，transition_task 记录是谁在切。这套东西存在的原因很实在——多个 CPU 上同时有人要改频率，硬件只有一个 PLL，必须串行化。

driver_data 留给 driver 挂私有数据，core 不碰。

struct cpufreq_policy 不直接对外暴露 API，用户空间只能通过 sysfs 的映射字段间接操作它。

四、policy 的分配与初始化 #

cpufreq 的初始化绕了一圈，因为「设备」和「驱动」的配对不是标准的 device/driver 匹配。路径是这样：driver 注册时调用 subsys_interface_register 注册一个 interface（.name = "cpufreq"、.subsys = &cpu_subsys、.add_dev = cpufreq_add_dev、.remove_dev = cpufreq_remove_dev），挂在 cpu bus 上。

cpu_subsys 下有 CPU device 被添加时，bus core 会回调该 bus 上所有 interface 的 add_dev，于是进了 __cpufreq_add_dev。这个函数是 policy 的出生地（3.18，省略了错误处理与部分锁细节）：

c
static int __cpufreq_add_dev(struct device *dev, struct subsys_interface *sif)
{
	unsigned int j, cpu = dev->id;
	bool recover_policy = cpufreq_suspended;
	struct cpufreq_policy *policy;

	if (cpu_is_offline(cpu))
		return 0;

#ifdef CONFIG_SMP
	/* 是否已有别的 CPU 代劳注册了这个 CPU（同一个调频域） */
	policy = cpufreq_cpu_get(cpu);
	if (unlikely(policy)) {
		cpufreq_cpu_put(policy);
		return 0;
	}
#endif
	if (!down_read_trylock(&cpufreq_rwsem))
		return 0;

#ifdef CONFIG_HOTPLUG_CPU
	/* 被热拔过、且兄弟还在某个 policy 里：只挂回去，不新建 */
	list_for_each_entry(tpolicy, &cpufreq_policy_list, policy_list) {
		if (cpumask_test_cpu(cpu, tpolicy->related_cpus)) {
			ret = cpufreq_add_policy_cpu(tpolicy, cpu, dev);
			up_read(&cpufreq_rwsem);
			return ret;
		}
	}
#endif
	/* resume 路径复用保存的 policy，失败走完整初始化 */
	policy = recover_policy ? cpufreq_policy_restore(cpu) : NULL;
	if (!policy) {
		recover_policy = false;
		policy = cpufreq_policy_alloc();
	}
	policy->cpu = cpu;
	cpumask_copy(policy->cpus, cpumask_of(cpu));
	init_completion(&policy->kobj_unregister);
	INIT_WORK(&policy->update, handle_update);

	/* 分水岭：等价于 probe。此后 core 可安全调 ->verify / ->setpolicy */
	ret = cpufreq_driver->init(policy);
	if (ret)
		goto err;

	cpumask_or(policy->related_cpus, policy->related_cpus, policy->cpus);
	cpumask_and(policy->cpus, policy->cpus, cpu_online_mask);

	if (!recover_policy) {
		policy->user_policy.min = policy->min;
		policy->user_policy.max = policy->max;
	}

	down_write(&policy->rwsem);
	for_each_cpu(j, policy->cpus)
		per_cpu(cpufreq_cpu_data, j) = policy;	/* 后续 cpufreq_cpu_get 查这张表 */

	if (cpufreq_driver->get && !cpufreq_driver->setpolicy)
		policy->cur = cpufreq_driver->get(policy->cpu);

	/* bootloader 可能把 CPU 设到表外频率，强制纠正 */
	if ((cpufreq_driver->flags & CPUFREQ_NEED_INITIAL_FREQ_CHECK) && has_target()) {
		if (cpufreq_frequency_table_get_index(policy, policy->cur) == -EINVAL) {
			pr_warn("CPU%d: Running at unlisted freq: %u KHz\n",
				policy->cpu, policy->cur);
			/* 传 cur - 1，否则 target 逻辑会因"目标等于当前"直接返回 */
			ret = __cpufreq_driver_target(policy, policy->cur - 1,
						      CPUFREQ_RELATION_L);
			BUG_ON(ret);
		}
	}

	blocking_notifier_call_chain(&cpufreq_policy_notifier_list,
				     CPUFREQ_START, policy);

	if (!recover_policy) {
		ret = cpufreq_add_dev_interface(policy, dev);	/* 建 sysfs + 符号链接 */
		if (ret)
			goto err;
		blocking_notifier_call_chain(&cpufreq_policy_notifier_list,
				CPUFREQ_CREATE_POLICY, policy);
	}

	list_add(&policy->policy_list, &cpufreq_policy_list);
	cpufreq_init_policy(policy);		/* 分配并启动 governor */

	if (!recover_policy) {
		policy->user_policy.policy = policy->policy;
		policy->user_policy.governor = policy->governor;
	}
	up_write(&policy->rwsem);
	kobject_uevent(&policy->kobj, KOBJ_ADD);
	up_read(&cpufreq_rwsem);
	return 0;
err:
	/* 出错时清 per_cpu 表、调 exit、释放 policy */
	...
}

逐段对上：

  1. 开头 cpu_is_offline 直接返回，offline 的 core 不建 policy。
  2. cpufreq_cpu_get(cpu) 命中说明同域的主 CPU 已经代劳过，直接退出。这是 SMP 多核共享一个 policy 的第一道去重。
  3. hotplug 段查 related_cpus：如果这个 CPU 曾经被热拔、且它的兄弟还在某个 policy 里，就只把它挂回那个 policy（cpufreq_add_policy_cpu），不新建。
  4. cpufreq_policy_alloc() 分配，policy->cpu = cpu 记录主 CPU，cpumask_copy(policy->cpus, cpumask_of(cpu)) 先只放自己。
  5. cpufreq_driver->init(policy) 是整个流程的分水岭——等价于 probe。driver 在这一次调用里填 cpus、clk、cpuinfo、min/max、freq_table。从这里往后，core 认为 ->verify/->setpolicy 已经可以被安全调用。
  6. related_cpus |= cpus，再把 cpus 与 cpu_online_mask 求交，剔掉 offline 的。
  7. 把 per_cpu(cpufreq_cpu_data, j) 指向这个 policy，后续 cpufreq_cpu_get 就是查这张表。这就是第 2 步判断的依据。
  8. 读一次当前频率填进 policy->cur（只有 driver 给了 ->get 且没给 ->setpolicy 时才做）。
  9. CPUFREQ_NEED_INITIAL_FREQ_CHECK 段：bootloader 设了非法频点时强制纠正。注意那个 policy->cur - 1 和 CPUFREQ_RELATION_L，目的是让 target 逻辑真的往下找最近频点；如果传 cur 本身，__cpufreq_driver_target 会因为「目标等于当前」而短路返回。BUG_ON(ret) 是刻意的：启动早期就在表外频率上跑，说明平台配置有硬伤。
  10. 创建 sysfs（cpufreq_add_dev_interface，顺便给同域其它 online CPU 建符号链接），挂进全局链表，最后 cpufreq_init_policy 分配并启动 governor。

SMP 与 hotplug 下多 CPU 共享 policy #

大多数平台所有 core 共用一路 PLL，改一个就改全部，于是只需要一个 policy。这套协作的完整链条：

a）主 CPU 的 __cpufreq_add_dev 调 driver->init，driver 按硬件实际情况填 policy->cpus，告诉 core 哪些 CPU 跟自己绑在一起； b）core 接着把 related_cpus 补上、把 offline 的从 cpus 里剔掉； c）core 创建 sysfs 目录，并为 cpus 里其它 CPU 建指向它的符号链接； d）次 CPU 枚举时进入 __cpufreq_add_dev，cpufreq_cpu_get 命中，直接返回； e）可热插拔的 core 回来时，符号链接已经不在（hotplug out 时被删），需要重新走一遍，这就是 cpufreq_add_policy_cpu 的位置。

这套流程和《CPU 电源管理：topology、hotplug 与 cpuidle》里 cpu control 的状态机是同一个事件的两种视角：那边管 core 上电与 online 状态，这边管 policy 的挂载与恢复。

五、cpufreq_register_driver 的流程 #

driver 的注册接口很薄，但要理解它在整个生命周期里的位置：除了 cpufreq_register_driver() / cpufreq_unregister_driver() 这一对，还有 cpufreq_get_current_driver()（取当前 driver 名）和 cpufreq_get_driver_data()（取 driver_data）。

cpufreq_register_driver 做的事：先做必要检查（name 不能空、init/verify 不能空、setpolicy 与 target/target_index 至少有一个），然后看全局指针 cpufreq_driver 是否已被占用——框架同一时刻只允许一个 cpufreq driver，重复注册返回 -EEXIST；接着把指针存好，最后调用 subsys_interface_register(&cpufreq_interface)，让 cpufreq_add_dev 开始对已经存在的每个 CPU device 生效。

顺序上要留意：先存 driver，再注册 interface。所以 interface 回调真正跑起来的时候，cpufreq_driver 一定已经可访问，__cpufreq_add_dev 里可以无脑解引用它。

cpufreq_unregister_driver 是反向操作：注销 interface，遍历所有 policy 调 driver->exit，把全局指针清空。

几个 driver flags 决定了 core 的行为分支，值得在这里一次说清（3.18 定义）：

c
/* flags */
#define CPUFREQ_STICKY			(1 << 0)	/* 即使所有 init 都失败也不 remove driver */
#define CPUFREQ_CONST_LOOPS		(1 << 1)	/* 频率切换不影响 loops_per_jiffy 等常量 */
#define CPUFREQ_PM_NO_WARN		(1 << 2)	/* suspend/resume 速度不匹配时不告警 */
#define CPUFREQ_HAVE_GOVERNOR_PER_POLICY (1 << 3)	/* 每个 policy 一套 governor 目录 */
#define CPUFREQ_ASYNC_NOTIFICATION	(1 << 4)	/* driver 自己发 POSTCHANGE */
#define CPUFREQ_NEED_INITIAL_FREQ_CHECK	(1 << 5)	/* 启动时检查频率是否在表内 */

CPUFREQ_HAVE_GOVERNOR_PER_POLICY 是多重调频域平台（手机 SoC 的每个 cluster）必须设的：它让 governor 的 sysfs 目录建在 cpu/cpuX/cpufreq/ 下，每个 cluster 可以有不同的 tunable，而不是全系统共用一份。CPUFREQ_ASYNC_NOTIFICATION 用于那种切换在中断里完成、需要自己补 POSTCHANGE 通知的驱动，它和 fast switch 不能同时用。CPUFREQ_NEED_INITIAL_FREQ_CHECK 就是上一章那个 BUG_ON 分支的开关，arm_big_little 也设了它。

六、频率表：cpufreq_frequency_table #

frequency table 是一组「CPU 能稳定跑」的频率/电压组合。工程上通常在项目初期用「试频点」的方式定下来，保证每个频点在全温度、全工艺角下都稳定。

这张表之所以成为框架的中心，是因为它把「频率」和「电压」绑成了一对一。core 和 governor 只谈频率，driver 在写频率时从表里取对应电压一起写——这样整套调频逻辑都只需要处理一个维度。

c
/* Special Values of .frequency field */
#define CPUFREQ_ENTRY_INVALID	~0u
#define CPUFREQ_TABLE_END	~1u
/* Special Values of .flags field */
#define CPUFREQ_BOOST_FREQ	(1 << 0)

struct cpufreq_frequency_table {
	unsigned int	flags;
	unsigned int	driver_data;	/* driver 私有，core 不用 */
	unsigned int	frequency;	/* kHz，不要求升序 */
};
  • frequency：kHz。两个保留值：CPUFREQ_ENTRY_INVALID 表示这一项无效（可以占位、后面动态填），CPUFREQ_TABLE_END 表示表结束。
  • driver_data：driver 自己解释，可以是电压（mV）、也可以是 OPP 的 index。
  • flags：3.18 只有 CPUFREQ_BOOST_FREQ，标记这一档属于 boost 频率（turbo）。

表不强制升序这一点要特别当心：所有基于索引的接口（target_index 拿到的 index）都依赖表和 driver 之间的索引约定，而不是「第几个就是第快」。cpufreq_table_validate_and_show() 之类接口会做校验与排序，这也是为什么新代码里很少直接手搓表。

如果设备树里已经描述过 OPP，driver 可以直接借 dev_pm_opp_init_cpufreq_table(struct device *dev, struct cpufreq_frequency_table **table) 生成 frequency table：遍历设备的 OPP 列表逐项转成表项，表尾补 CPUFREQ_TABLE_END。用它生成的表，driver_data 存的是 OPP 的 index，后面 dev_pm_opp_set_rate() 正好拿这个 index 去查电压。

七、频率的合法性检查：cpufreq_verify_within_limits #

框架里有四层「频率」，从上到下收窄：

text
frequency table       有限的离散频点，硬件真实能力
   ↓
policy->cpuinfo       {min_freq, max_freq}，driver init 时定死，之后不可改
   ↓
policy->{min, max}    当前调频范围，sysfs / PM QoS / thermal 可改
   ↓
policy->cur           实际运行频率

verify 就是保证这四层自洽。core 提供两个辅助接口：cpufreq_frequency_table_verify(policy, table) 检查 policy 的 {min, max} 有没有越出 cpuinfo 的范围、有没有越出 table 的频率范围，越界就夹回去；cpufreq_generic_frequency_table_verify(policy) 只是拿 policy->freq_table 当 table 再调一次，绝大多数 driver 直接把自己的 ->verify 指过去。

真正驱动这套检查的是 cpufreq_verify_within_limits 系列（内部实现，直接改 policy->min/max），逻辑主干如下（概念示意，3.18 的实际实现还经过几个辅助函数，见文末勘误）：

c
if (policy->min < min) policy->min = min;	/* 先抬下限 */
if (policy->max > max) policy->max = max;	/* 再压上限 */
if (policy->min > policy->max) {		/* 交叉了，拉回来并报错 */
	policy->min = policy->max;
	pr_err("min freq can't be higher than max freq: %u\n", policy->max);
}

这段逻辑的价值不在缩进而在顺序：先抬下限、再压上限，最后如果下限冲过了上限，把下限拉回来并喊一嗓子。第三种情况在实际系统中一定会出现——两个模块分别用 PM QoS 提了 min 和压了 max，交叉之后范围就空了。

verify 会被调用两次，这件事在 cpufreq_set_policy 里体现得很清楚：第一次在通知链之前，第二次在 CPUFREQ_ADJUST/CPUFREQ_INCOMPATIBLE 通知链之后。原因是通知链上的模块（thermal、cpuidle、厂商模块）可能把范围改得更窄，改完必须重新校验，否则会出现「通知链把 max 压到 min 之下」这种非法状态。

八、set_policy 与 set_target 的分工 #

这是 cpufreq 里最容易混淆的一对概念。一句话：set_policy 设置「范围」，set_target 设置「点」。

内核对这个分工有一张官方示意图（Documentation/cpu-freq/governors.rst，旧文件名 governors.txt）：

text
CPU 能自己调频                 |   CPU 只能在给定范围内选具体频率
                              |
      "CPUfreq policy"        |
  {min,max} + governor        |
        /          \          |
       /            \         |
      /   governor 决定(动态或静态) 在 policy->{min,max} 内选 target_freq
     /                        \
    /                          \
调用 ->setpolicy，设置范围    调用 ->target / ->target_index，
                              设置最接近 target_freq 的频点，
                              并保证在 policy->{min,max} 之内

落到代码上，两条路径在 cpufreq_set_policy 里分叉（3.18，省略了 pr_debug）：

c
static int cpufreq_set_policy(struct cpufreq_policy *policy,
			      struct cpufreq_policy *new_policy)
{
	struct cpufreq_governor *old_gov;
	int ret;

	memcpy(&new_policy->cpuinfo, &policy->cpuinfo, sizeof(policy->cpuinfo));
	if (new_policy->min > policy->max || new_policy->max < policy->min)
		return -EINVAL;

	ret = cpufreq_driver->verify(new_policy);			/* 第一次 verify */
	if (ret)
		return ret;

	blocking_notifier_call_chain(&cpufreq_policy_notifier_list,
			CPUFREQ_ADJUST, new_policy);			/* 任何原因都可调 */
	blocking_notifier_call_chain(&cpufreq_policy_notifier_list,
			CPUFREQ_INCOMPATIBLE, new_policy);		/* 硬件不兼容 */

	ret = cpufreq_driver->verify(new_policy);			/* 通知链改过，再验 */
	if (ret)
		return ret;

	blocking_notifier_call_chain(&cpufreq_policy_notifier_list,
			CPUFREQ_NOTIFY, new_policy);

	policy->min = new_policy->min;
	policy->max = new_policy->max;

	if (cpufreq_driver->setpolicy) {
		policy->policy = new_policy->policy;
		return cpufreq_driver->setpolicy(new_policy);		/* 只交范围 */
	}

	if (new_policy->governor == policy->governor)
		goto out;

	old_gov = policy->governor;
	if (old_gov) {
		__cpufreq_governor(policy, CPUFREQ_GOV_STOP);
		up_write(&policy->rwsem);	/* 锁不能跨 POLICY_EXIT */
		__cpufreq_governor(policy, CPUFREQ_GOV_POLICY_EXIT);
		down_write(&policy->rwsem);
	}

	policy->governor = new_policy->governor;
	if (!__cpufreq_governor(policy, CPUFREQ_GOV_POLICY_INIT)) {
		if (!__cpufreq_governor(policy, CPUFREQ_GOV_START))
			goto out;
		up_write(&policy->rwsem);
		__cpufreq_governor(policy, CPUFREQ_GOV_POLICY_EXIT);
		down_write(&policy->rwsem);
	}

	if (old_gov) {			/* 新 governor 起不来，把旧的拉回来 */
		policy->governor = old_gov;
		__cpufreq_governor(policy, CPUFREQ_GOV_POLICY_INIT);
		__cpufreq_governor(policy, CPUFREQ_GOV_START);
	}
	return -EINVAL;

 out:
	return __cpufreq_governor(policy, CPUFREQ_GOV_LIMITS);

几个调用时机：初始化时（__cpufreq_add_dev → cpufreq_init_policy → cpufreq_set_policy）；写 scaling_max_freq/scaling_min_freq 时（store_one → cpufreq_set_policy）；写 scaling_governor 时（store_scaling_governor → cpufreq_set_policy）。

走 setpolicy 分支的硬件，改频率这件事就到此为止了：范围交给硬件，软件不再介入。走 governor 分支的，范围改完还要通知 governor 重新看一遍限制，也就是末尾那个 CPUFREQ_GOV_LIMITS。

scaling_setspeed 是给 userspace governor 的单点入口：store_scaling_setspeed 先检查 policy->governor 和 policy->governor->store_setspeed 是否存在（没有就返回 -EINVAL），再 sscanf 解析一个 %u，最后调 policy->governor->store_setspeed(policy, freq) 并返回 count。它只判断回调在不在，频率合法性检查留给 governor 的实现（userspace governor 最终调 cpufreq_driver_target，走的是下一章那条链路）。

九、从请求到硬件：cpufreq_driver_target 的链路 #

一个调频请求从 governor 发起，到寄存器被写，经过的路径如下。这是全篇最需要背下来的一张图。

text
governor（例如 schedutil 的 sugov_work / sugov_fast_switch）
  │  给出 target_freq 或 index
  ├─(有 fast_switch 且已 enable)──> cpufreq_driver_fast_switch()
  │        └─> driver->fast_switch(policy, target_freq)   中断上下文，不阻塞
  │                                                      不发 PRECHANGE/POSTCHANGE
  └─(否则)──> __cpufreq_driver_target(policy, target_freq, relation)
                    │
                    ├─ 1. 夹到 policy->{min,max} 之间（关系运算受 relation 影响）
                    ├─ 2. 用 driver->target_index 时：
                    │     cpufreq_frequency_table_target() 把频率解析成 index
                    │     （CPUFREQ_RELATION_L / _H / _C）
                    ├─ 3. 若 driver 有 get_intermediate/target_intermediate：
                    │     先切到中间频率（get_intermediate 返回 0 则跳过）
                    ├─ 4. cpufreq_freq_transition_begin() → 发 CPUFREQ_PRECHANGE
                    │      等上一次切换完成（transition_lock/transition_wait）
                    ├─ 5. driver->target_index(policy, index) 或 driver->target(...)
                    │      真正 clk_set_rate + regulator_set_voltage
                    ├─ 6. policy->cur = 新频率（异步通知模式下由 driver 更新）
                    └─ 7. cpufreq_freq_transition_end() → 发 CPUFREQ_POSTCHANGE
                             更新 cpufreq-stats 的 time_in_state / total_trans

这条链上每个环节都有坑：

夹范围在解析索引之前。 如果先查表再夹，可能出现「表里选出来的频点被夹掉了，但 index 已经定了」的错位。所以顺序是先算有效目标频率，再解析。

relation 三种取值。 CPUFREQ_RELATION_L 取大于等于目标的最近频点，CPUFREQ_RELATION_H 取小于等于的最近频点，CPUFREQ_RELATION_C 取绝对差最小的。governor 要「至少够快」用 _L，要「不超过 X」用 _H。schedutil 用的是 _L，因为它算出的频率是「下限要求」。

同步。 硬件只有一个 PLL，多个 CPU 可能同时发起切换。cpufreq_freq_transition_begin 拿 transition_lock，发现 transition_ongoing 就把当前 task 挂 transition_wait 上睡；transition_end 唤醒下一个。这也是为什么 fast switch 和 transition notifier 互斥——fast switch 要跑在中断上下文，而这里会睡眠。

policy->cur 谁来更新。 同步模式下 core 在 target_index 返回后更新；设了 CPUFREQ_ASYNC_NOTIFICATION 的驱动自己更新，因为它可能还没切完就返回了。

中间频率。 get_intermediate/target_intermediate 是给「不能一步跳到目标频率」的硬件准备的（比如需要在两个 PLL 之间过渡）。get_intermediate 返回 0 表示这次不需要中间频率，core 直接调 target_index。新代码基本不用这套接口。

统计。 cpufreq_freq_transition_end 里会更新 cpufreq-stats：给旧频率累加 time_in_state，total_trans 加一，trans_table[old][new] 加一。所以频繁调频本身是有开销的（不只是硬件切换时间，还有这些簿记），这也是 governor 需要限频的原因之一。

十、通知链：谁关心频率变了 #

cpufreq 有两条通知链，性质完全不同。

通知链 类型 用途 谁注册 能阻塞
cpufreq_policy_notifier_list blocking notifier policy 变更协商：EDF 等模块可以调范围、cpuidle 要更新延迟假设 thermal、cpuidle、架构代码 能
cpufreq_transition_notifier_list srcu notifier 频率切换事件：PRECHANGE / POSTCHANGE 需要感知每次切频的驱动（如 loops_per_jiffy 相关、perf、厂商模块） 能，但与 fast switch 互斥

policy 通知链的事件（3.18）：

事件 何时发 注册者该做什么
CPUFREQ_ADJUST verify 之后、INCOMPATIBLE 之前 任何原因都可修改 new_policy->{min,max}，比如热限频往下压
CPUFREQ_INCOMPATIBLE ADJUST 之后 只处理硬件不兼容导致的调整
CPUFREQ_NOTIFY 第二次 verify 之后、应用之前 纯通知，不应再改范围
CPUFREQ_CREATE_POLICY 新建 policy 且 sysfs 建好之后 记录新 policy，比如 EAS 更新调度域
CPUFREQ_START driver->init 成功之后 早期钩子

transition 通知链的事件只有三个：CPUFREQ_PRECHANGE、CPUFREQ_POSTCHANGE，以及针对同一 policy 被替换时的 CPUFREQ_CREATE_POLICY 之外的辅助语义；驱动侧最常关心前两个。收到 PRECHANGE 时硬件频率还没变，收到 POSTCHANGE 时已经变完。

不使用 fast switch 的驱动，切换长得像这样：

c
cpufreq_freq_transition_begin(policy, &freqs);	/* 发 PRECHANGE */
/* 写寄存器，切频率、切电压 */
cpufreq_freq_transition_end(policy, &freqs, 0);	/* 发 POSTCHANGE */

cpufreq_freq_transition_begin 内部有 wait_event 来串行化，所以它只能在可以睡眠的上下文调用。这也是 fast switch 出现后无法复用 transition notifier 的根本原因：要做 atomic 版本的 notifier 就得改所有 callback，不现实，于是干脆让两者互斥。

十一、per-policy 与 per-CPU 的同步 #

多核调频的同步分三层，混在一起就会出 bug。

第一层，policy 粒度。cpus/related_cpus 定义的是一组「必须一起变」的 CPU。一个 policy 内的 CPU 共享同一个频率，因为它们共享 PLL 和供电域。

第二层，policy 内的串行化。transition_lock + transition_ongoing + transition_wait + transition_task 保证同一时刻只有一个人在写硬件。注意这套锁是 per-policy 的，两个不同 policy（两个 cluster）可以并行切换。

第三层，跨 CPU 发起的许可。某个 CPU 想改另一个 CPU 所在 policy 的频率，得看硬件允不允许——有些平台的调频寄存器是 per-CPU 的，只能改自己。这个许可在 5.x 里是 policy->dvfs_possible_from_any_cpu，schedutil 用 cpufreq_this_cpu_can_update() 检查。ARM 平台通常允许任意 CPU 改（因为写的是共享 PLL 寄存器），所以这个值是 true；即便如此，也要排除「发起方正在 offline」的情况，否则会在 CPU 下线的过程中留下悬空的 irq_work。

governor 侧的锁要和这三层对齐：sugov_update_single 只在一个 CPU 上跑（自然被 rq lock 串行化），所以 fast 路径不需要额外锁；sugov_update_shared 会被多个 CPU 并发进入，所以统一用 sg_policy->update_lock。慢速路径还要多一层 work_lock，因为真正的写入在 kthread 上下文里，跨上下文了。

have_governor_per_policy() 就是 !!(cpufreq_driver->flags & CPUFREQ_HAVE_GOVERNOR_PER_POLICY)，它决定 governor 的 tunable 是全局一份还是每 policy 一份。

不设时 get_governor_parent_kobj() 返回全局 kobject，所有 policy 共用一套参数（改一个就是改全部）；设了时返回 &policy->kobj，每个 cluster 各有一套。手机 SoC 一般都要 per-policy，否则给 little cluster 调的阈值会误伤 big cluster。

十二、cpufreq driver 该怎么写 #

写一个 cpufreq driver 的骨架步骤（以 3.18/4.x 的 API 为准）：

  1. 平台初始化：拿到 CPU core 的 clock 和 regulator，解析 OPP。
  2. 生成 frequency table，并把表存进 policy。
  3. 定义一个 struct cpufreq_driver，填必填字段，实现需要的回调；调 cpufreq_register_driver() 注册。
  4. core 在 CPU device 出现时回调 ->init，driver 在那里把 policy 填好。
  5. 运行期 core 根据情况调 ->setpolicy 或 ->target_index。
  6. suspend 前把频率钉到确定值（或实现 ->suspend），resume 后恢复（或实现 ->resume）。

struct cpufreq_driver 全字段：

c
struct cpufreq_driver {
	char		name[CPUFREQ_NAME_LEN];
	u8		flags;
	void		*driver_data;

	/* 所有 driver 必填 */
	int	(*init)(struct cpufreq_policy *policy);
	int	(*verify)(struct cpufreq_policy *policy);

	/* setpolicy 与 target/target_index 二选一 */
	int	(*setpolicy)(struct cpufreq_policy *policy);

	/* 失败时必须把频率恢复到 policy->restore_freq（切换前的旧频率） */
	int	(*target)(struct cpufreq_policy *policy,	/* Deprecated */
			  unsigned int target_freq, unsigned int relation);
	int	(*target_index)(struct cpufreq_policy *policy, unsigned int index);

	/*
	 * 仅用于实现了 target_index() 且未设 CPUFREQ_ASYNC_NOTIFICATION 的驱动。
	 * get_intermediate 返回平台能稳定切换到的中间频率，target_intermediate
	 * 负责把 CPU 切到那个频率；之后 core 负责发通知，driver 在这两个回调里
	 * 不用管通知。get_intermediate 返回 0 表示这次不走中间频率，core 直接
	 * 调 target_index。
	 */
	unsigned int (*get_intermediate)(struct cpufreq_policy *policy, unsigned int index);
	int	(*target_intermediate)(struct cpufreq_policy *policy, unsigned int index);

	unsigned int	(*get)(unsigned int cpu);		/* 尽量实现 */
	int	(*bios_limit)(int cpu, unsigned int *limit);	/* 以下可选 */
	int	(*exit)(struct cpufreq_policy *policy);
	void	(*stop_cpu)(struct cpufreq_policy *policy);
	int	(*suspend)(struct cpufreq_policy *policy);
	int	(*resume)(struct cpufreq_policy *policy);

	struct freq_attr	**attr;

	/* boost 相关 */
	bool			boost_supported;
	bool			boost_enabled;
	int	(*set_boost)(int state);
};

顺带一个概念问题：设备模型里 driver 用来驱动设备，那 struct cpufreq_driver 驱动的「设备」是什么？答案就是 struct cpufreq_policy——只是它不以 kobject 之外的任何实体形态存在，这也是第三章那个「抽象得难理解」的来源。

每个回调的实际含义：

回调 必填 调用时机 该做什么
init 是 policy 创建 填 cpus、clk、cpuinfo、min/max、freq_table
verify 是 每次 set_policy，两次 校验并夹住 {min,max}，通常直接指 cpufreq_generic_frequency_table_verify
setpolicy 二选一 硬件自己能调频 把范围告知硬件，不再管具体频率
target 二选一（已废弃） governor 请求频率 传的是频率 + relation，不推荐
target_index 二选一 governor 请求频率 传的是表索引，直接查表拿频率和电压
get_intermediate/target_intermediate 否 需要中间频率过渡时 新代码不要用
get 建议 读当前频率 有 policy->clk 时可指 cpufreq_generic_get
exit 否 policy 销毁 释放 init 申请的资源
stop_cpu 否 CPU 被 stop 停掉和该 CPU 相关的调频动作
suspend/resume 否 系统睡眠 用 suspend_freq/restore_freq 也能达到类似效果
attr 否 sysfs 创建 加私有 attribute 数组
set_boost 否 用户开关 boost 开/关超频

init 里最省事的写法是调通用初始化 cpufreq_generic_init(policy, table, transition_latency)：它用 table 推导出 cpuinfo.max_freq/min_freq，把表挂进 policy->freq_table，设置 transition_latency，并把 min/max 初始化为表的两端。除了 clk 要自己填，其余都能靠它搞定。

get 也有通用实现 unsigned int cpufreq_generic_get(unsigned int cpu)，前提是 init 里给 policy->clk 赋了值——它直接走 clock framework 把频率读回来。

需要给 driver 加私有 sysfs 文件时，用 freq_attr 结构加三个宏：

c
struct freq_attr {
	struct attribute attr;
	ssize_t (*show)(struct cpufreq_policy *, char *);
	ssize_t (*store)(struct cpufreq_policy *, const char *, size_t count);
};

#define cpufreq_freq_attr_ro(_name) \
static struct freq_attr _name = __ATTR(_name, 0444, show_##_name, NULL)
#define cpufreq_freq_attr_ro_perm(_name, _perm) \
static struct freq_attr _name = __ATTR(_name, _perm, show_##_name, NULL)
#define cpufreq_freq_attr_rw(_name) \
static struct freq_attr _name = __ATTR(_name, 0644, show_##_name, store_##_name)

这些 attribute 会出现在 driver 的 attr 数组里，最终挂到 cpufreq/ 目录下。

十三、driver 的 init / exit / target / get #

把四个最重要的回调拆开看，因为它们决定了驱动能不能正常工作。

init。 这是 driver 的 probe 等价物。要做的事就四件：告诉 core「哪些 CPU 跟我一起变」（policy->cpus）、给出 clock 指针、给出 frequency table、给出 cpuinfo。一个最小实现：

c
static int my_cpufreq_init(struct cpufreq_policy *policy)
{
	struct device *cpu_dev = get_cpu_device(policy->cpu);
	int ret;

	policy->clk = devm_clk_get(cpu_dev, NULL);
	if (IS_ERR(policy->clk))
		return PTR_ERR(policy->clk);

	ret = dev_pm_opp_init_cpufreq_table(cpu_dev, &freq_table);
	if (ret)
		return ret;

	ret = cpufreq_generic_init(policy, freq_table, transition_latency);
	if (ret)
		return ret;

	cpumask_copy(policy->cpus, topology_core_cpumask(policy->cpu));	/* 同 cluster 一起调 */
	return 0;
}

注意 policy->cpus 要按实际拓扑填。填错了会出现「A 核改了频率但 B 核以为没变」的现象，排查起来很费时间。

exit。 释放 init 里申请的东西。用 devm_* 系列接口的话这步会很轻，但 OPP 表的引用计数、put_cluster_clk_and_freq_table 这类成对操作别漏。

target_index。 最常实现的调频入口：

c
static int my_cpufreq_target_index(struct cpufreq_policy *policy, unsigned int index)
{
	struct cpufreq_frequency_table *entry = &freq_table[index];

	if (entry->frequency == CPUFREQ_ENTRY_INVALID)
		return -EINVAL;

	/* kHz -> Hz；dev_pm_opp_set_rate 内部保证升频先提压、降频后降压 */
	return dev_pm_opp_set_rate(get_cpu_device(policy->cpu),
				   entry->frequency * 1000);
}

dev_pm_opp_set_rate 会同时处理电压和频率，并且保证升频时先提压、降频时后降压。手写的话，这个顺序必须自己保证，反了就是死机。

get。 返回 kHz：拿到 cpufreq_cpu_get_raw(cpu) 的 policy，clk_get_rate(policy->clk) / 1000 返回，policy 为空或 clk 无效时返回 0。或者在 init 里填好 policy->clk 之后直接 .get = cpufreq_generic_get。

十四、target_index 与 target 两套接口 #

两套接口并存了很多年，新 driver 要写哪一个没有悬念，但老代码要读。

维度 target(policy, target_freq, relation) target_index(policy, index)
参数 目标频率 + 关系 frequency table 的索引
谁负责查表 driver 自己 core 已经查好
频率合法性 driver 要自己判断 core 保证 index 有效
是否废弃 是（3.x 起注释标 Deprecated） 推荐
典型实现 遍历表找最接近的 直接 freq_table[index]
中间频率支持 无 配 get_intermediate 可用
与 cpufreq-stats 的配合 需要 driver 回报实际频率 自然对齐

废弃的动力很直接：target 把「从频率找表项」这件事推给每个 driver 重复实现，而且不同 driver 的 relation 语义细节还未必一致；target_index 让 core 统一做解析，driver 只面对索引。

__cpufreq_driver_target 内部对两套接口的处理：

text
if (driver->target_index) {
	index = cpufreq_frequency_table_target(policy, target_freq, relation);
	→ 可选：get_intermediate / target_intermediate
	→ driver->target_index(policy, index)
} else if (driver->target) {
	→ driver->target(policy, target_freq, relation)
}

cpufreq_frequency_table_target() 是解析函数，按 relation 在表里挑。它在 3.18 里返回索引，后续版本签名有调整（改为填充 struct cpufreq_freqs 之类的输出参数，具体版本未验证）。写新代码时用 cpufreq_table_find_index_* 系列更稳。

fast_switch 是第三条路，但它不属于这两套接口的二选一，而是叠加在 target_index 之上的快捷方式：

路径 上下文 通知 谁调
target_index（同步） 进程上下文，可睡眠 PRECHANGE + POSTCHANGE core
target_index + CPUFREQ_ASYNC_NOTIFICATION 中断/异步 driver 自己发 POSTCHANGE core
fast_switch 任意上下文（含中断） 不发 governor 直接调

要开 fast switch，driver 必须实现 ->fast_switch，并且不能有 driver 注册 transition notifier——这两个限制是同一件事的两面：fast switch 不允许阻塞，而 transition notifier 的回调没有「不阻塞」的保证。schedutil 的 sugov_init 里第一件事就是 cpufreq_enable_fast_switch(policy)，能否真的用起来取决于 driver 侧的 fast_switch_possible。

十五、governor 的注册与选择 #

struct cpufreq_governor 的字段（3.18/4.x 形态）与含义：

c
struct cpufreq_governor {
	char	name[CPUFREQ_NAME_LEN];
	int	initialized;
	int	(*governor)(struct cpufreq_policy *policy, unsigned int event);
	ssize_t	(*show_setspeed)(struct cpufreq_policy *policy, char *buf);
	int	(*store_setspeed)(struct cpufreq_policy *policy, unsigned int freq);
	unsigned int max_transition_latency;	/* ns，超过就退回 performance */
	struct list_head governor_list;
	struct module *owner;
};

name 是全局唯一标识（scaling_governor 写的就是它）；initialized 记录是否完成 init；governor 是状态机回调，靠 event 区分动作；show_setspeed/store_setspeed 只有支持从用户空间直接设频的 governor（userspace）才提供；max_transition_latency 是能容忍的最大切换延迟，硬件比这慢就退回 performance；governor_list 挂进全局 cpufreq_governor_list；owner 是模块引用计数。

4.x 及以后这个结构换过形态。 从某个 4.x 版本起，governor 单回调被拆成 init/exit/start/stop/limits 五个回调，并加了一个 dynamic_switching 布尔（早期是 flags = CPUFREQ_GOV_DYNAMIC_SWITCHING）。5.10 的 schedutil_gov 就是这么定义的：

c
struct cpufreq_governor schedutil_gov = {
	.name			= "schedutil",
	.owner			= THIS_MODULE,
	.dynamic_switching	= true,
	.init			= sugov_init,
	.exit			= sugov_exit,
	.start			= sugov_start,
	.stop			= sugov_stop,
	.limits			= sugov_limits,
};

而 3.18 的 governor 是 .governor = cpufreq_gov_dbs 这一种形态，用 event 分发。具体是哪个版本完成的这次拆分，我没有逐 tag 核对，标记为未验证。 论文中凡是贴 governor 代码的地方都注明了内核版本，读的时候留意。

注册接口：

c
int cpufreq_register_governor(struct cpufreq_governor *governor)
{
	int err;

	if (!governor)
		return -EINVAL;
	if (cpufreq_disabled())
		return -ENODEV;

	mutex_lock(&cpufreq_governor_mutex);

	governor->initialized = 0;
	err = -EBUSY;
	if (__find_governor(governor->name) == NULL) {
		err = 0;
		list_add(&governor->governor_list, &cpufreq_governor_list);
	}

	mutex_unlock(&cpufreq_governor_mutex);
	return err;
}
EXPORT_SYMBOL_GPL(cpufreq_register_governor);

逻辑很直白：名字去重，挂链表。5.x 里对应的是 cpufreq_governor_init(schedutil_gov) 宏/接口，做同样的事。

默认 governor 怎么选。 cpufreq_init_policy() 决定：

c
static void cpufreq_init_policy(struct cpufreq_policy *policy)
{
	struct cpufreq_governor *gov;
	struct cpufreq_policy new_policy;

	memcpy(&new_policy, policy, sizeof(*policy));

	/* 恢复 hotplug 之前用的 governor */
	gov = __find_governor(per_cpu(cpufreq_cpu_governor, policy->cpu));
	new_policy.governor = gov ? gov : CPUFREQ_DEFAULT_GOVERNOR;

	/* 若 driver 有 setpolicy，用 governor 名推出 policy 枚举 */
	if (cpufreq_driver->setpolicy)
		cpufreq_parse_governor(new_policy.governor->name,
				       &new_policy.policy, NULL);

	if (cpufreq_set_policy(policy, &new_policy) && cpufreq_driver->exit)
		cpufreq_driver->exit(policy);
}

cpufreq_set_policy 里的 governor 切换顺序值得背一遍：停旧走 CPUFREQ_GOV_STOP → （放锁）→ CPUFREQ_GOV_POLICY_EXIT → （拿锁）；起新走 CPUFREQ_GOV_POLICY_INIT → CPUFREQ_GOV_START → CPUFREQ_GOV_LIMITS；起新失败则回滚到旧 governor，走 INIT → START。

放锁再拿锁那一对 up_write/down_write 是因为 rwsem 不能跨 POLICY_EXIT 持有（注释里明说了）。回滚分支的存在说明 governor 启动是会失败的（内存不足、线程创建失败），切换 governor 的调用者要能接住 -EINVAL。

十六、governor 的五个回调 #

governor 的状态机在 3.18 用五个 event 表达（CPUFREQ_GOV_START=1、_STOP=2、_LIMITS=3、_POLICY_INIT=4、_POLICY_EXIT=5）：

event 何时发 governor 该做什么
CPUFREQ_GOV_POLICY_INIT 新 governor 上线之前（policy 新建或切换 governor） 一次性准备：分配私有数据、初始化 timer/work、解析 tunable
CPUFREQ_GOV_START 准备完成，正式启用 注册回调、启动 timer，开始参与调频
CPUFREQ_GOV_LIMITS start 之后，以及 policy 的 min/max 变化时 检查当前频率是否还在范围内，不在就改
CPUFREQ_GOV_STOP 停用前 停止参与（注销回调、停 timer）
CPUFREQ_GOV_POLICY_EXIT 停用后 释放 POLICY_INIT 申请的资源

拆成五步而不是两步（start/stop），核心目的是区分「一次性资源」和「可反复启停的运行时状态」：hotplug 掉一个 CPU 时只需要 STOP/START（因为 policy 还在），整个 cluster 都掉光才需要 POLICY_EXIT 去释放资源。

4.x 之后这五个 event 变成五个独立回调（.init/.exit/.start/.stop/.limits），语义一一对应：governor(policy, CPUFREQ_GOV_START) 变成 gov->start(policy)。这次拆分让 governor 不用再写一个巨大的 switch，也顺带把 CPUFREQ_GOV_LIMITS 变成了显式的 .limits 回调。具体版本未验证，但从 5.9/5.10 的 schedutil_gov 定义可以确认 5.x 是回调形态。

挂到调度器上这一层在各版本也不同：3.x/4.x 早期靠 cpufreq_update_util 直接调 governor 的 ->governor；4.7 引入 schedutil 时同时引入了 cpufreq_add_update_util_hook() 这套 hook 机制，governor 注册自己的回调，调度器只管调 hook。

十七、ondemand 与 conservative：采样式调频 #

ondemand 和 conservative 是 cpufreq_governor_dbs（DBS，Demand-Based Switching）这套代码的两个实例，共享绝大部分逻辑，差别只在一个决策细节。

ondemand 的工作方式： 启动一个 per-policy 的延迟工作（delayed work），周期由 sampling_rate（微秒）决定；每次采样读取这段时间内 CPU 的 busy 时间比例得到「load」；load 超过 up_threshold（百分比，常见默认 80~95）时升频，而且不是小步走，而是按 sampling_down_factor 与比例关系一次跳到较高频点——设计意图就是「负载一上来就尽快跑满」；load 低于阈值时降频，可配 powersave_bias（0~1000 的千分比）让降频更保守。

conservative 的区别： 同样的采样框架，但升降频走「相邻档位」，一次只跳一级（freq_step 控制步长百分比）。负载高上一档，负载低下一档，慢慢逼近目标频率。

两者对照：

维度 ondemand conservative
采样 有，sampling_rate 有，sampling_rate
升降策略 大步跳，负载高直接冲高频 小步走，一次一档
参数 up_threshold、sampling_down_factor、powersave_bias、ignore_nice_load up_threshold、down_threshold、freq_step
频率轨迹 锯齿明显 相对平缓
适合场景 桌面/交互，要快速响应 功耗敏感、对频率抖动敏感
主要缺陷 采样窗口天然滞后；大步跳导致功耗尖峰 爬升慢，突发负载下响应不足

两者的共同缺陷是结构性的：它们看的是「刚刚过去的一个采样窗口里忙了多久」，不是「接下来要多快」。 采样窗口越长，判断越平滑但越滞后；窗口越短，判断越灵敏但开销越大，且容易在噪声上反复横跳。这个矛盾没有一个参数组合能同时解决，这也是 schedutil 出现的直接原因。

DBS 框架的 tunable 通过 governor_attr_set 暴露到 sysfs，路径在 /sys/devices/system/cpu/cpufreq/<governor>/ 或每 policy 目录下，取决于 have_governor_per_policy()。

十八、performance 与 powersave：两个端点策略 #

两个端点 governor 的实现加一起不到百行，但用途明确。

performance：启动时把频率钉到 policy->max，之后只响应 LIMITS 事件，scaling_max_freq 一改就跟着改。powersave：把频率钉到 policy->min，同样只响应 LIMITS。

细节在于 relation：performance 用 CPUFREQ_RELATION_H（不超过 max 的最大频点），powersave 用 CPUFREQ_RELATION_L（不低于 min 的最小频点）。这样即使用户把 max 设成一个表里没有的频率，也能落到合法的档位上。启动动作本质上就是 __cpufreq_driver_target(policy, policy->max, CPUFREQ_RELATION_H) 这类一行调用。

这两个 governor 的实战价值比名字听起来大：抓性能问题、跑 benchmark 时切 performance，排除「频率没跑满」这个变量；追功耗时切 powersave，测最低功耗基线；调 driver 时用它们做两端验证（能稳定钉在最高和最低频点，说明表和 target_index 是对的）；setpolicy 型硬件也靠它们把 CPUFREQ_POLICY_PERFORMANCE/CPUFREQ_POLICY_POWERSAVE 传给硬件。

max_transition_latency 这个字段在 performance 上有特殊意义：它是「兜底 governor」。如果某个 governor 声明的可容忍延迟比硬件的 cpuinfo.transition_latency 还小，说明它在这块硬件上没意义（切一次的成本比收益还高），框架会退回 performance。

十九、schedutil：从调度器利用率推频率 #

到这里进入本篇的重点。schedutil（下文简称 sugov）是 4.7 引入的 governor，代码在 kernel/sched/cpufreq_schedutil.c；本文这一部分基于 Linux 5.10.61 源码。它现在是标准内核的默认 governor（配置项 CONFIG_CPU_FREQ_DEFAULT_GOV_SCHEDUTIL）。

它和 ondemand 的本质差别，一句话说完：ondemand 看过去，schedutil 看现在并推将来。

维度 ondemand / conservative schedutil
数据来源 governor 自己采样 CPU 的忙闲时间 调度器 PELT 的 running/runnable 平均值
驱动方式 定时器轮询（polling） 调度事件驱动（context switch、enqueue、dequeue、tick）
时间视角 上一个采样窗口的历史负载 指数加权的当前负载，且阻塞任务仍计入（隐含未来）
天然延迟 至少一个采样周期 无固定周期，事件即触发（受 rate limit 约束）
RT/DL 处理 只能看到总 busy 比例 能分开看 cfs/rt/dl/irq，dl 还能用带宽模型
与调度器耦合 无 深度耦合（uclamp、util_est、EWMA、capacity）
可调参数 一堆 threshold 基本只有一个 rate_limit_us

PELT 的那套数学让「看现在」变得可行：每个调度实体的 running 值是 EWMA，周期 1024us、衰减按 y^32=0.5（即最近 32ms 的贡献占一半）。这个和式可组合（ewma(A)+ewma(B)=ewma(A+B)），所以任务迁移时平均值可以跟着搬走。更关键的是，阻塞的任务仍然对 cfs_rq 的聚合值有贡献，这正好反映了「它一旦被唤醒就要多少算力」——这就是「未来负载预测」的来源。

频率映射公式：

text
next_freq = C * max_freq * util / max        （频率不变性可用时）
next_freq = C * cur_freq * util_raw / max    （不变量不可用时用当前频率近似）
其中 C = 1.25

取 1.25 的意思是「留 20% 余量」：util 耗尽目标算力的 80% 时正好顶到目标频率，还有 20% 给突发。这个系数在 4.7 的 get_next_freq 里写成 (freq + (freq >> 2)) * util / max，也就是 freq * 1.25，与公式一致。

触发调频的三个时机（都是调度事件）：RT 或 deadline 任务入队/出队；CPU 上 CFS util 发生变化；处于 iowait 的任务被唤醒。

事件很密集——重载时任务可能只跑几微秒就切出去。所以并非每次事件都真的去算频率，sugov_should_update_freq 里有一道时间闸门（见第二十章）。

数据结构三件套：

结构 粒度 关键成员
struct sugov_tunables 每 policy 或全局一套 attr_set（含 policy_list，所有共享该 tunable 的 sugov policy 链表）；rate_limit_us（唯一可调参数，连续调频的最小间隔 us，改了会同步到链上所有 policy 的 freq_update_delay_ns）
struct sugov_cpu 每 CPU 一份 update_util（挂进调度器的回调描述符）、sg_policy（同 cluster 的 CPU 指向同一个）、cpu、iowait_boost_pending、iowait_boost（初值 128）、last_update（上次 util 变化驱动调频的时间，不是上次改频率的时间，配合 iowait boost 过滤零星 IO）、bw_dl、max、saved_idle_calls（仅单 CPU cluster，判断该 CPU 是否真的闲过）
struct sugov_policy 每 cluster 一份 policy、tunables、tunables_hook、update_lock、freq_update_delay_ns（调频间隔门限）、next_freq（上次决定的频点）、last_freq_update_time、cached_raw_freq（映射前的原始目标频率）、irq_work+work_in_progress、work/worker/thread（慢速路径 kthread）、work_lock、limits_changed、need_freq_update

注册与初始化。

c
struct cpufreq_governor schedutil_gov = {
	.name			= "schedutil",
	.owner			= THIS_MODULE,
	.dynamic_switching	= true,
	.init			= sugov_init,
	.exit			= sugov_exit,
	.start			= sugov_start,
	.stop			= sugov_stop,
	.limits			= sugov_limits,
};
cpufreq_governor_init(schedutil_gov);

dynamic_switching = true（早期形态是 flags = CPUFREQ_GOV_DYNAMIC_SWITCHING）是在告诉 core：这个 governor 会自己根据利用率动态改频率，不适合那些「要自己完全掌控频率」的硬件。

sugov_init 第一段四步：policy->governor_data 非空就返回 -EBUSY（旧 governor 得先 stop + exit 干净）；cpufreq_enable_fast_switch(policy)；sugov_policy_alloc(policy) 分配 sugov policy 并关联框架；sugov_kthread_create(sg_policy)。

fast switch 这一层要分清两个标志：policy->fast_switch_possible 由 driver 决定（硬件与驱动是否支持），fast_switch_enabled 才是「上下都打通了」。慢速路径那个线程是为了拿一个可阻塞的上下文——早期用 workqueue，后来因为整机重载时普通线程调度延迟太大会拖慢切频，改成优先级 50 的 RT kthread（SCHED_FIFO），最终改成 SCHED_DEADLINE，在 stop class 之下、其它一切之上。fast switch 场景下这个线程不创建。

sugov_init 第二段（per-policy tunable 场景）：

c
tunables = sugov_tunables_alloc(sg_policy);			/* A */
sg_policy->tunables = tunables;
tunables->rate_limit_us = cpufreq_policy_transition_delay_us(policy);	/* B */
policy->governor_data = sg_policy;				/* C */
ret = kobject_init_and_add(&tunables->attr_set.kobj, &sugov_tunables_ktype,
			   get_governor_parent_kobj(policy), "%s",
			   schedutil_gov.name);			/* D */

B 是三处调频间隔参数的汇集点：硬件的 cpuinfo.transition_latency（F1 切到 F2 并稳定所需时间）、driver 通过 policy->transition_delay_us 给的偏好、以及 sugov 自己的 rate_limit_us。初始化时 rate_limit_us 跟随 transition_delay_us；driver 没设的话按 transition_latency 乘 1000 估一个；对切换特别慢的平台这个估值会过大，所以下限夹到 10ms。

D 建 sysfs，父目录由 get_governor_parent_kobj(policy) 决定——设了 CPUFREQ_HAVE_GOVERNOR_PER_POLICY 就是每 policy 目录，否则是全局目录。

sugov_start：

c

sg_policy->last_freq_update_time = 0;
sg_policy->next_freq = 0;
sg_policy->work_in_progress = false;
sg_policy->limits_changed = false;
sg_policy->need_freq_update = false;
sg_policy->cached_raw_freq = 0;

for_each_cpu(cpu, policy->cpus) {
	struct sugov_cpu *sg_cpu = &per_cpu(sugov_cpu, cpu);

	memset(sg_cpu, 0, sizeof(*sg_cpu));
	sg_cpu->cpu = cpu;
	sg_cpu->sg_policy = sg_policy;
}

for_each_cpu(cpu, policy->cpus) {
	struct sugov_cpu *sg_cpu = &per_cpu(sugov_cpu, cpu);

	cpufreq_add_update_util_hook(cpu, &sg_cpu->update_util,
				     policy_is_shared(policy) ?
						sugov_update_shared : sugov_update_single);
}

最后那个二选一是关键分叉：policy 只含一个 CPU 用 sugov_update_single，含多个用 sugov_update_shared。两者逻辑相似但并发模型完全不同。版本注：5.9 的 sugov_start 里 need_freq_update 初始化为 cpufreq_driver_test_flags(CPUFREQ_NEED_UPDATE_LIMITS)，5.10 改成 false 并由 limits_changed 路径设置。

sugov_stop 三步：遍历 policy->cpus 调 cpufreq_remove_update_util_hook()；synchronize_rcu()（保证 sugov_exit 释放 update_util_data 时没有并发读者）；不支持 fast switch 时再 irq_work_sync() + kthread_cancel_work_sync() 排干慢速路径的待处理请求。

sugov_exit：断开 policy->governor_data、按引用计数决定是否释放 tunable、停 kthread、释放 sugov policy、cpufreq_disable_fast_switch。

限频路径（从 PM QoS 到 sugov）：模块 A（如检测到触摸，把 min freq 拉到 1.2GHz）→ freq_qos_add_request/freq_qos_update_request → PM QoS 综合所有请求算出新的实际限制，变了就 notifier 通知 cpufreq core → core 调 refresh_frequency_limits → cpufreq_set_policy → governor 的 limits 回调（sugov_limits）。

sugov_limits 只有两步：不支持 fast switch 时，在 work_lock 保护下立刻调 cpufreq_policy_apply_limits(policy) 用新 min/max 修正当前频率；无论哪条路径，最后都把 sg_policy->limits_changed 置为 true，保证下一次 util 更新时强制走一次调频。

二十、schedutil 的调频间隔与限频 #

get_next_freq 之前的第一个闸门是 sugov_should_update_freq：

c
static bool sugov_should_update_freq(struct sugov_policy *sg_policy, u64 time)
{
	s64 delta_ns;

	if (!cpufreq_this_cpu_can_update(sg_policy->policy))	/* A */
		return false;

	if (unlikely(sg_policy->limits_changed)) {		/* B */
		sg_policy->limits_changed = false;
		sg_policy->need_freq_update = true;
		return true;
	}

	delta_ns = time - sg_policy->last_freq_update_time;
	return delta_ns >= sg_policy->freq_update_delay_ns;	/* C */
}

A：当前 CPU 能不能改这个 policy 的频率。寄存器 per-CPU 的平台只能改自己，跨 CPU 请求即使算出频率也落不了地，不如早点退出，省掉后续计算。ARM 平台 dvfs_possible_from_any_cpu 为 true，不受此限，但仍要排除「自己正在 offline」的情况。 B：limits_changed 优先于时间间隔——上下限都变了还等什么 rate limit。 C：正常的时间闸门，delta_ns 不到 freq_update_delay_ns 就丢掉这次请求。

need_freq_update 是第二个闸门：为 true 时不忽略任何请求，一定下发给驱动。除 B 那条路径外，ignore_dl_rate_limit 也会间接打开它——deadline 带宽需求涨了同样不该被挡住，判据是 cpu_bw_dl(cpu_rq(sg_cpu->cpu)) > sg_cpu->bw_dl，成立就把 limits_changed 置位。

计算 CPU utilization。 主函数 schedutil_cpu_util 分三段，核心判断都在这段代码里（注释对应下面的解释）：

c
/* 第一段：快速饱和检查 */
if (!uclamp_is_used() && type == FREQUENCY_UTIL && rt_rq_is_runnable(&rq->rt))
	return max;				/* A：有 runnable RT 任务，直接满频 */
irq = cpu_util_irq(rq);
if (unlikely(irq >= max))
	return max;				/* B：中断负载吃满就满频 */

/* 第二段：累加与钳制 */
util = util_cfs + cpu_util_rt(rq);	/* C：PELT 窗口对齐，可直接相加 */
if (type == FREQUENCY_UTIL)
	util = uclamp_rq_util_with(rq, util, p);	/* uclamp 约束 boost/cap */
dl_util = cpu_util_dl(rq);		/* D：只用来判饱和 */
if (util + dl_util >= max)
	return max;
if (type == ENERGY_UTIL)
	util += dl_util;		/* E：算能耗时加真实 dl util */

/* 第三段：irq 缩放与 dl 带宽 */
util = scale_irq_capacity(util, irq, max);	/* F */
util += irq;
if (type == FREQUENCY_UTIL)
	util += cpu_bw_dl(rq);			/* G：dl 带宽作为下限 */
return min(max, util);

A：没有 uclamp 时，rq 上有 runnable 的 RT 任务就报满频——RT 的时延敏感度不值得用 PELT 平均值去赌；开了 uclamp 则走精细路径。 C：CFS 与 RT 的 utilization 在同一个 PELT 时间线、窗口对齐，可以直接相加。 D：dl 的 PELT util 在这里只用来判断「是否已经没有任何 idle 时间」。真饱和返回 max，否则后面用带宽视角的 cpu_bw_dl 取代 PELT 视角的 cpu_util_dl。 E：算能耗（EAS）时才把 dl 的 PELT util 真正加进去，因为它反映真实消耗。 F：IRQ 时间没算进 task clock（被 IRQ 偷走了），任务侧算出的 util 偏大，得按 U' = irq + (max - irq)/max * U 缩放再补上 irq。 G：dl 任务用带宽视角的 util 作为「CPU 至少要输出多少算力」的下限，直接累加。

起点 sugov_get_util 很简单：util = cpu_util_cfs(rq)、max = arch_scale_cpu_capacity(sg_cpu->cpu)，顺手把 max 和 bw_dl 存进 sg_cpu，最后调 schedutil_cpu_util(cpu, util, max, FREQUENCY_UTIL, NULL)。

cpu_util_cfs(rq) 让 util_est 和 PELT 取较大值：u_cfs = max(running, util_est)。这就是「任务刚被唤醒时不会因为平均值还没爬上来而卡在低频」的机制——util_est 在出队时用 running 的峰值做了 IIR 记录。

max 是 arch_scale_cpu_capacity() 的结果，和当前频率无关，所以 util/max 比较的是「占这个 CPU 总体算力的比例」，不是「占当前频率多少」。这正是频率不变性的用法。

compute cluster utility。 单 CPU cluster 下，CPU util 就是 cluster util。多 CPU 用 sugov_next_freq_shared 遍历 policy->cpus：对每个 cpu 取 sugov_get_util() 得到 j_util 与 j_max，套 sugov_iowait_apply()，然后用交叉相乘 j_util * max > j_max * util 挑「比值最大」的那个，最后 get_next_freq(sg_policy, util, max)。

比较的是 util/max 比值而不是 util 绝对值：同构 cluster 里两者等价（挑 util 最大的那个），异构 cluster 里必须用比值——否则一个大核的低 util 会压过一个小核的高 util。注意 max 在循环里被更新，比较基准也在变；同构场景没问题，异构场景的精确性依赖迭代细节。

二十一、iowait boost 与它的争议 #

schedutil 内嵌了一套 iowait boost，解决的是一类特定场景的吞吐塌陷：轻载、CPU 上只有一个重 IO 的任务。

问题链路：CPU 频率高 → 任务跑得快 → 两次 IO 之间大部分时间在等 IO → busy 时间占比低 → sugov 判定 util 低 → 降频 → 任务跑得慢 → 单位时间内下发的 IO 命令变少 → IO 吞吐下降。这是一个正反馈，会把频率一路压到最低。

机制：一个处于 iowait 状态的任务被 enqueue 时，通过 cpufreq_update_util 带上 SCHED_CPUFREQ_IOWAIT 标志通知 sugov；sugov_iowait_boost 更新该 CPU 的 boost 状态；sugov_iowait_apply 在算完 util 之后套用 boost，取较大值。

更新规则：

条件 iowait boost 的 util
第一次从 iowait 被唤醒 设为 IOWAIT_BOOST_MIN，即 128
已在 boost 中，但距上次更新超过一个 tick 才来新的 IO 唤醒 重置为 IOWAIT_BOOST_MIN
已在 boost 中，后续没有新的 IO 唤醒（IO 停了） 一个 tick 后清零，结束 boost
已在 boost 中，且 IO 唤醒密集（短时间内大量 IO） 翻倍（min(boost << 1, SCHED_CAPACITY_SCALE)），上限 1024 
c
static void sugov_iowait_boost(struct sugov_cpu *sg_cpu, u64 time, unsigned int flags)
{
	bool set_iowait_boost = flags & SCHED_CPUFREQ_IOWAIT;

	if (sg_cpu->iowait_boost && sugov_iowait_reset(sg_cpu, time, set_iowait_boost))
		return;				/* 已闲了超过一个 tick，重置 */
	if (!set_iowait_boost)
		return;				/* 只 boost 因 IO 唤醒的任务 */
	if (sg_cpu->iowait_boost_pending)
		return;				/* 每次请求只翻一倍 */
	sg_cpu->iowait_boost_pending = true;

	if (sg_cpu->iowait_boost) {
		sg_cpu->iowait_boost =
			min_t(unsigned int, sg_cpu->iowait_boost << 1, SCHED_CAPACITY_SCALE);
		return;
	}
	sg_cpu->iowait_boost = IOWAIT_BOOST_MIN;
}

iowait_boost（capacity scale 的 128~1024）和 util 量纲不同，apply 时要换算：

c
boost = (sg_cpu->iowait_boost * max) >> SCHED_CAPACITY_SHIFT;
return max(boost, util);

iowait_boost_pending 是「一次请求只能翻一倍」的闸门：置位后在 sugov_iowait_apply 里被消费（清掉）。若某次更新时它已是清零状态（说明上一个 boost 已被用掉，这一轮没有密集 IO），就衰减一半，低于 IOWAIT_BOOST_MIN 直接归零。

净效果：只有持续、密集的 IO 才能把 boost 顶到接近满频；零星 IO 会被时间闸门（一个 tick）和衰减逻辑过滤掉。

争议点。 这套机制被批评的地方很集中：它是全局、无差别的——不管 IO 来自前台交互还是后台预读，都触发同一套 boost，后台大量小 IO 会把频率抬高白烧电；boost 值和 max 的换算意味着在容量大的核上同样的 boost 数值对频率影响不同，行为不够可预测；参数不可调，只有一个 IOWAIT_BOOST_MIN 宏，用户空间没法按场景调整（ondemand 有一堆 threshold 可调）；它与 uclamp 语义重叠——用户空间想表达「这个任务要快」，uclamp 更精确，而 iowait boost 走的是另一条通路。

厂商的常见做法是直接改这部分代码（限制只在特定 cluster 生效、加 sysfs 开关、和 boost hint 联动）。上游在后续版本对这块有持续调整，具体在哪个版本有什么变化没有逐一核对，标为未验证。

二十二、cluster utility 如何映射到具体频率 #

拿到 cluster util 之后，get_next_freq 负责把它变成一个具体频点：

c
static unsigned int get_next_freq(struct sugov_policy *sg_policy,
				  unsigned long util, unsigned long max)
{
	struct cpufreq_policy *policy = sg_policy->policy;
	unsigned int freq = arch_scale_freq_invariant() ?
				policy->cpuinfo.max_freq : policy->cur;

	freq = map_util_freq(util, freq, max);			/* A */

	if (freq == sg_policy->cached_raw_freq && !sg_policy->need_freq_update)
		return sg_policy->next_freq;			/* B */

	sg_policy->need_freq_update = false;
	sg_policy->cached_raw_freq = freq;
	return cpufreq_driver_resolve_freq(policy, freq);	/* C */
}

A：map_util_freq(util, freq, max) 就是 freq * 1.25 * util / max。频率不变性可用时基数取 cpuinfo.max_freq，不可用时退化为 policy->cur（用当前频率近似出「假设满频时的 util」）。 B：映射出的原始目标频率和上次相同，说明底层能解析出的频点也相同，直接返回缓存的 next_freq，省掉一次 resolve_freq。need_freq_update 被置位时例外——上下限可能变了，必须重解析。 C：cpufreq_driver_resolve_freq(policy, freq) 把理想频率翻译成 driver 支持的档位。硬件不支持无级变速，映射方式可以是取不小于目标的最小频点、取不大于的最大频点、或取最接近的；具体策略由 core 决定，默认等价于 CPUFREQ_RELATION_L。

两段式设计（原始频率 → 档位频率）有个副作用值得注意：cached_raw_freq 缓存原始频率，next_freq 缓存档位频率，两者不一致时靠 need_freq_update 兜住。

get_next_freq 之后分两条路写硬件。fast switch 路径（单 CPU 且已在 rq lock 下，无需并发控制）调 sugov_fast_switch；慢速路径把请求交给 sugov_deferred_update。两者共用一个前置判断 sugov_update_next_freq()：频率没变就直接返回 false，什么都不做；变了才更新 next_freq 和 last_freq_update_time。注意 last_freq_update_time 只在频率真的变了时才更新——「算出来没变」的请求不会重置 rate limit 计时器。

fast switch 的下半段：cpufreq_driver_fast_switch 返回 0 表示这次切换被拒绝了，此时不能更新 policy->cur。这里没有任何通知链动作，trace 也是自己打的。

发起调频：sugov_update_single 的完整顺序是：sugov_iowait_boost() → 记 last_update → ignore_dl_rate_limit() → sugov_should_update_freq() 闸门 → sugov_get_util() → sugov_iowait_apply() → get_next_freq() → 二次修正 → 下发。中间那次修正很关键：

c
busy = !sg_policy->need_freq_update && sugov_cpu_is_busy(sg_cpu);
...
if (busy && next_f < sg_policy->next_freq) {
	next_f = sg_policy->next_freq;		/* 不降频，保持原值 */
	sg_policy->cached_raw_freq = 0;
}

sugov_cpu_is_busy 只在 CONFIG_NO_HZ_COMMON 下有效，判据是「两次轮询之间 idle 计数有没有变化」。计数没变 = 这个 CPU 一直在跑东西，即使 util 掉了（比如任务被迁走了）也不该立刻降频，否则会误降。这是对「单 CPU cluster 无法靠挑最大值来避免误判」的补偿。

慢速路径 sugov_deferred_update 只做一件事：置 work_in_progress 并 irq_work_queue。真正的写入在 sugov_work：

c
static void sugov_work(struct kthread_work *work)
{
	struct sugov_policy *sg_policy = container_of(work, struct sugov_policy, work);
	unsigned int freq;
	unsigned long flags;

	raw_spin_lock_irqsave(&sg_policy->update_lock, flags);
	freq = sg_policy->next_freq;
	sg_policy->work_in_progress = false;
	raw_spin_unlock_irqrestore(&sg_policy->update_lock, flags);

	mutex_lock(&sg_policy->work_lock);
	__cpufreq_driver_target(sg_policy->policy, freq, CPUFREQ_RELATION_L);
	mutex_unlock(&sg_policy->work_lock);
}

那个先拿锁读 next_freq、清 work_in_progress 再放锁的小段落有个明确目的：如果读 next_freq 之后、清标志之前有人更新了 next_freq，会出现「新请求被漏掉」。在锁内一起做，配合「放锁之后到来的 work 会被 kthread_work 重新调用」，就不漏。慢速路径走 CPUFREQ_RELATION_L，即取不小于目标的频点，与 fast switch 路径下 cpufreq_driver_resolve_freq 的默认语义一致。

多 CPU cluster（sugov_update_shared）结构相同，差别只有三处：整段在 update_lock 保护下（同一份 sg_policy 会被 cluster 里多个 CPU 并发进入）、用 sugov_next_freq_shared 取 cluster 最大值、没有 sugov_cpu_is_busy 判断（挑的是 util 最大的那个，本来就不会因为单个 CPU 的 util 掉了而误降）。

PELT 接口的完整调用关系：调度器事件（switch / enqueue / dequeue / tick / iowait wakeup）→ cpufreq_update_util(rq, flags) → 遍历 rq 上注册的 update_util hook（sugov_update_single / sugov_update_shared）→ sugov_iowait_boost() 更新 iowait 状态 → sugov_should_update_freq() 时间闸门 → sugov_get_util()（内部 cpu_util_cfs() 取 PELT 的 running 并与 util_est 取大，再进 schedutil_cpu_util()，后者依次经过 cpu_util_irq/cpu_util_rt/uclamp_rq_util_with/cpu_util_dl/cpu_bw_dl/scale_irq_capacity）→ sugov_iowait_apply() 套用 boost → get_next_freq()（map_util_freq() ×1.25，再 cpufreq_driver_resolve_freq() 落到档位）→ sugov_fast_switch 或 sugov_deferred_update。

二十三、schedutil 与 PELT 的接口 #

前面反复出现 PELT 的几个量，这里把它们和 cpufreq 的对应关系一次讲清。

PELT 量 来源 在 schedutil 里的角色
running（cpu_util_cfs） 实体在 CPU 上实际占用的时间比例，EWMA 频率选择的基础输入
runnable 实体在 runqueue 上等待 + 运行的时间比例 反映争抢程度，用于判断饱和
util_est 出队时的 running 峰值经 IIR 滤波，只升不降 与 running 取大，补偿唤醒时的爬升延迟
cpu_util_rt RT 调度类的 running 直接加到 util 上
cpu_util_dl / cpu_bw_dl dl 的 PELT util / 带宽模型算出的最小需求 前者判饱和，后者加进目标 util
cpu_util_irq 中断与 steal time 饱和检查 + 缩放补偿
arch_scale_cpu_capacity 微架构容量（归一化 1024） max，不同大小核之间可比
arch_scale_freq_invariant 频率不变性是否可用 决定 get_next_freq 的基数取 max_freq 还是 cur

两条关键的性质：

频率不变性（frequency invariance）。 在 1GHz 上跑 50% 和在 2GHz 上跑 50% 不是一回事。调度器在把时间增量喂进 PELT 之前，按 r_dvfs = f_cur / f_max 和 r_cpu（微架构比）缩放时间：r_tot = r_dvfs * r_cpu。缩放之后，不同频率、不同大小核上的 running 就变得可比可迁移。软件拥有完整 DVFS 控制权的简单架构用 f_cur/f_max 算；由硬件自己调 DVFS 的架构用硬件计数器（Intel 的 APERF/MPERF、ARMv8.4 的 AMU）。

阻塞任务仍然计入。 running 虽然是「实际占 CPU 的时间」，但对 cfs_rq 这一层聚合而言，阻塞的任务仍有贡献。这条性质是 schedutil 能「预测」的根本：一个刚被 IO 阻塞的重任务，它的历史贡献还留在 cfs_rq 的平均值里，所以频率不会立刻掉到底。

uclamp 是另一条独立通路：每个 CFS/RT 任务可设 u_min/u_max，runqueue 保存所有 runnable 任务的聚合值，uclamp_rq_util_with() 用它 boost 或 cap util。开了 uclamp 之后「有 RT 任务就报满频」的粗暴逻辑被绕过，改走精细路径。

ENERGY_UTIL 与 FREQUENCY_UTIL 的区别在一次调用里体现得很清楚：算频率时 dl 用带宽视角的 cpu_bw_dl（下限保证），算能耗时用 PELT 的 cpu_util_dl（真实消耗）。这说明 schedutil_cpu_util 不只为 cpufreq 服务，也是 EAS 的公共入口。

二十四、ARM big.LITTLE：异构多核的调频 #

为什么 big.LITTLE 的支持代码放在 cpufreq 目录下？因为内核调度器长期是为 SMP 设计的，而 SMP 假设所有核的性能和功耗一致。

big.LITTLE（也叫 HMP）在一个 chip 里放两类核：big（高性能高功耗）和 little（低性能低功耗），各自成 cluster。理想调度是「重活给 big，轻活给 little，重活变轻了迁回 little」，但上游调度器没有这种支持，芯片厂商又等不起。

ARM 提出的第一版方案靠 hypervisor：用虚拟化扩展把 4×A15 + 4×A7 虚拟成 4 个 A15，OS 只看得到 4 个核；需要时通过一条 hypervisor 指令让某个虚拟核在 A15 和 A7 之间切，所有切换动作（IRQ、timer 迁移）由 hypervisor 负责，对 OS 透明。两个硬伤：8 个核不能任意组合使用；必须存在 hypervisor，增加系统复杂度。

内核借鉴了这个思路，把 hypervisor 的逻辑搬进内核，并借用 cpufreq 框架来实现。理由三条：对调度器来说 big 与 little 的差别只在性能和功耗上，和 cpufreq 的关注点一致，于是 big/LITTLE 切换被嵌进频率调整里（低频段映射 little，高频段映射 big）；那 4 个可见核拥有较宽的频率范围，在 switcher 使能时按频率需求自动切换；结果是不对称的 HMP 被转化成了 SMP，现有调度器直接可用。

bL_cpufreq_init 是整个 driver 的核心：

c
/* Per-CPU initialization */
static int bL_cpufreq_init(struct cpufreq_policy *policy)
{
	u32 cur_cluster = cpu_to_cluster(policy->cpu);
	struct device *cpu_dev = get_cpu_device(policy->cpu);
	int ret;

	if (!cpu_dev)
		return -ENODEV;

	ret = get_cluster_clk_and_freq_table(cpu_dev);
	if (ret)
		return ret;

	ret = cpufreq_table_validate_and_show(policy, freq_table[cur_cluster]);
	if (ret) {
		put_cluster_clk_and_freq_table(cpu_dev);
		return ret;
	}

	if (cur_cluster < MAX_CLUSTERS) {
		int cpu;

		cpumask_copy(policy->cpus, topology_core_cpumask(policy->cpu));
		for_each_cpu(cpu, policy->cpus)
			per_cpu(physical_cluster, cpu) = cur_cluster;
	} else {
		per_cpu(physical_cluster, policy->cpu) = A15_CLUSTER;	/* 默认在 big */
	}
	policy->cpuinfo.transition_latency = arm_bL_ops->get_transition_latency ?
		arm_bL_ops->get_transition_latency(cpu_dev) : CPUFREQ_ETERNAL;
	if (is_bL_switching_enabled())
		per_cpu(cpu_last_req_freq, policy->cpu) = clk_get_cpu_rate(policy->cpu);
	return 0;
}

分叉点在 cpu_to_cluster() 的返回值：小于 MAX_CLUSTERS 说明还能分清物理 cluster（switcher disable），等于 MAX_CLUSTERS 说明已经是虚拟核（switcher enable）。

switcher disable 时，get_cluster_clk_and_freq_table 只为当前 CPU 所在的 cluster 建表（存 freq_table[cluster]），然后把同 cluster 的所有 CPU 塞进 policy->cpus 并设好它们的 physical_cluster——一个 cluster 一个 policy、一张表。switcher enable 时，同一个函数收集两个 cluster 的频率合并成升序的一张（存 freq_table[MAX_CLUSTERS]），同时找出 clk_big_min 与 clk_little_max，当前 CPU 的 physical_cluster 设为 A15_CLUSTER——一个 policy、一张表。

合并表那里有个小技巧：为了让「低频在前、高频在后」可靠成立，little 的频率被统一除以 2，用的时候再乘回来，这样 little 的频点稳定落在表的前半段。transition_latency 拿不到时填 CPUFREQ_ETERNAL（一个极大值），意思是「切换延迟不可知」，这个值会影响 governor 的 rate limit 估值。

二十五、bL_cpufreq 的 cluster 与虚拟 frequency domain #

switcher 的使能由 bL switcher 控制，两个时机：初始化时（bL_switcher_init，用 late_initcall 声明，所以时机靠后）和用户写 sysfs。如果 no_bL_switcher 参数不为 1（默认 0），bL_switcher_init 会直接调 bL_switcher_enable 打开它。

c
/* arch/arm/common/bL_switcher.c */
static int bL_switcher_enable(void)
{
	int cpu, ret;

	mutex_lock(&bL_switcher_activation_lock);
	lock_device_hotplug();
	if (bL_switcher_active) {
		unlock_device_hotplug();
		mutex_unlock(&bL_switcher_activation_lock);
		return 0;
	}

	ret = bL_activation_notify(BL_NOTIFY_PRE_ENABLE);	/* A */
	if (ret)
		goto error;

	ret = bL_switcher_halve_cpus();				/* B */
	if (ret)
		goto error;

	for_each_online_cpu(cpu) {				/* C */
		struct bL_thread *t = &bL_threads[cpu];

		spin_lock_init(&t->lock);
		init_waitqueue_head(&t->wq);
		init_completion(&t->started);
		t->wanted_cluster = -1;
		t->task = bL_switcher_thread_create(cpu, t);
	}

	bL_switcher_active = 1;
	bL_activation_notify(BL_NOTIFY_POST_ENABLE);		/* D */
	goto out;

error:
	pr_warn("big.LITTLE switcher initialization failed\n");
	bL_activation_notify(BL_NOTIFY_POST_DISABLE);
out:
	unlock_device_hotplug();
	mutex_unlock(&bL_switcher_activation_lock);
	return ret;
}

A：发 BL_NOTIFY_PRE_ENABLE。cpufreq driver 收到后调 cpufreq_unregister_driver 把自己注销掉——因为接下来可见核数要变，policy 必须重建。 B：bL_switcher_halve_cpus() 把 possible 的核配对并关掉不必要的那一半，这是整个机制的支点。 C：为每个 online 的虚拟核（此时已经是 big/little 对）建一个切换线程。 D：bL_switcher_active = 1 正式生效，发 BL_NOTIFY_POST_ENABLE，cpufreq driver 重新注册自己。重注册会重新走一遍 bL_cpufreq_init，这次 cpu_to_cluster() 返回 MAX_CLUSTERS，于是走合并表的路径。

也就是说：switcher 使能 = 注销 driver → 砍掉一半核 → 重建 → 重注册 driver。这个「推倒重来」的设计让初始化代码只需要处理两种静态场景，不用在运行期动态改 policy 结构。

bL_switcher_halve_cpus 的结果存在 bL_switcher_cpu_pairing 数组里。以 8 核为例（逻辑 ID 0~7，0~3 为 A7，4~7 为 A15），配对结果是 [0]=7、[1]=6、[2]=5、[3]=4；配对完成后把 core 4~7 关掉，系统只剩 4 个虚拟核，逻辑 ID 仍然是 0~3。每个虚拟核物理上对应两个核，同一时刻只有一个在跑，哪个在跑记录在 per_cpu(physical_cluster, cpu) 里。

这里有个先有鸡还是先有蛋的问题值得注意：bL_activation_notify(BL_NOTIFY_PRE_ENABLE) 发生在砍核之前，此时 driver 以 8 核的形态注销；重注册发生在砍核之后，driver 以 4 核的形态初始化。中间那段窗口里 cpufreq 是没有 driver 的，任何调频请求都会落空——所以这里要 lock_device_hotplug() 把整个设备热插拔锁住。

二十六、big.LITTLE 的频率切换流程 #

切换由 bL_cpufreq_set_target（也就是 driver 的 target_index）发起：

c
static int bL_cpufreq_set_target(struct cpufreq_policy *policy, unsigned int index)
{
	u32 cpu = policy->cpu, cur_cluster, new_cluster, actual_cluster;
	unsigned int freqs_new;

	cur_cluster = cpu_to_cluster(cpu);
	new_cluster = actual_cluster = per_cpu(physical_cluster, cpu);
	freqs_new = freq_table[cur_cluster][index].frequency;

	if (is_bL_switching_enabled()) {
		if ((actual_cluster == A15_CLUSTER) && (freqs_new < clk_big_min))
			new_cluster = A7_CLUSTER;	/* big 降不下去，换 little */
		else if ((actual_cluster == A7_CLUSTER) && (freqs_new > clk_little_max))
			new_cluster = A15_CLUSTER;	/* little 上不去，换 big */
	}

	return bL_cpufreq_set_rate(cpu, actual_cluster, new_cluster, freqs_new);
}

决策规则只有两条，靠两个边界值：当前在 big 且目标频率 < clk_big_min → 切 little；当前在 little 且目标频率 > clk_little_max → 切 big；其它情况不切，原地调频。

clk_big_min 是 big 的最小频率，clk_little_max 是 little 的最大频率。两个区间之间通常有一段重叠（big 的能效区间和 little 的性能区间交集），重叠区里不切——这是有意的：切一次 cluster 的代价（中断迁移、timer 迁移、核上下电）远大于在重叠区里多跑一点。

几个要点：switcher 使能时调度器只看得到 4 个核，逻辑 ID 固定（0~3），不关心物理归属；每个虚拟核的「当前状态」记在 physical_cluster；每次调频根据「当前状态 + 目标频率」判断要不要切；最终以 actual_cluster、new_cluster、freqs_new 调 bL_cpufreq_set_rate。

bL_cpufreq_set_rate 在 3.18 里有两个版本（早期朴素 clk_set_rate 版，和后来「配对核同步切频 + 电压域处理」版），实际代码未在素材中给出。按原文描述，逻辑主干是这样：

c
static int bL_cpufreq_set_rate(u32 cpu, u32 old_cluster, u32 new_cluster, u32 rate)
{
	/* 1. core 层一律 kHz，clock framework 要 Hz */
	rate *= 1000;

	/* 2. cluster 要变时，先把配对核的电压/频率处理好，避免切换瞬间越界 */
	if (old_cluster != new_cluster)
		other_cluster = (new_cluster == A15_CLUSTER) ? A7_CLUSTER : A15_CLUSTER;

	/* 3. 写频率（按 cluster 索引到对应 clock） */
	ret = clk_set_rate(clk[new_cluster], rate);
	if (ret)
		return ret;

	per_cpu(cpu_last_req_freq, cpu) = rate / 1000;
	per_cpu(physical_cluster, cpu) = new_cluster;	/* 逻辑状态已切 */

	/* 4. cluster 真的变了才请求切换 */
	if (old_cluster != new_cluster)
		bL_switch_request(cpu, new_cluster);
	return 0;
}

里面几处要看清：频率单位转换（kHz → Hz）在 driver 里做，core 层始终用 kHz；per_cpu(physical_cluster, cpu) 在写频率之后、切换之前更新，表示「逻辑状态已切」；bL_switch_request 不直接切，而是唤配对该 CPU 的 switcher 线程（bL_switcher_thread），由那个线程调 bL_switch_to 完成真正的切换——迁移当前物理核的中断和 timer，关掉当前核、打开目标 cluster 的核。这部分是平台相关的重活，本文不展开。

这条路径的性能特征决定了它在上游的命运：每次 cluster 切换都要迁移中断与 timer、上下电核，延迟是毫秒级甚至更高，远大于一次普通的频率切换。所以在重叠区里「不切」是硬性设计，不是优化。

big.LITTLE 平台上频率表看起来重复 switcher enable 时 little 频率被除以 2 合并进同一张表 freq_table[MAX_CLUSTERS]、is_bL_switching_enabled()
cluster 切换延迟大、卡顿 目标频率落在重叠区外，触发 cluster 切换 clk_big_min / clk_little_max

多条易错点的定论：只有 cpu0 下有 cpufreq 目录是正常的（所有核统一调频，其它 cpu 的目录是指向它的符号链接，查 affected_cpus 确认）；affected_cpus 和 related_cpus 对不上是因为有 offline 的核；cpuinfo_cur_freq 与 scaling_cur_freq 短暂不一致多半是 fast switch 路径下 policy->cur 由 driver 更新、两者采样时刻不同；某 cluster 改参数影响另一个 cluster 是 driver 没设 CPUFREQ_HAVE_GOVERNOR_PER_POLICY；启动日志里 "Running at unlisted freq" 是 bootloader 设了表外频率、被 CPUFREQ_NEED_INITIAL_FREQ_CHECK 自动纠正（BUG_ON 兜底）；sugov 线程创建失败多因 fast switch 未启用且 kthread 起不来；降频后性能卡住不回弹看 sugov_cpu_is_busy 判定与 util_est 是否启用；big.LITTLE 平台上频率表看起来重复是 switcher enable 时 little 频率被除以 2 合并进同一张表的正常结果。

几条编码层面的纪律：不在 ->target_index 里发通知（除非设了 CPUFREQ_ASYNC_NOTIFICATION，否则 PRECHANGE/POSTCHANGE 由 core 负责）；切换失败要恢复旧频率（->target 的注释明说必须恢复到 policy->restore_freq，->target_index 同理，否则上层以为切了但硬件没切）；policy->cpus 一定按真实拓扑填，填少了会出现「同域 CPU 各自以为自己是主」的重复 policy；->verify 里别做重活，它每次 set_policy 被调两次；governor_data 的进出必须配对，否则下次 init 撞上 -EBUSY；别在持有 policy->rwsem 写锁时调 governor 的 exit 路径。

勘误与修正 #

  1. cpufreq_set_policy 的第二个参数类型随版本变了。 3.18 是 struct cpufreq_policy *new_policy（整份 policy 的副本），后续版本改成只传 governor 名加 min/max。本篇按 3.18 呈现并标注。变更版本未验证。
  2. cpufreq_governor 的单回调在 4.x/5.x 被拆成五个回调。 素材（3.18/4.x）用 .governor = handler + event 分发；5.9/5.10 的 schedutil_gov 用 .init/.exit/.start/.stop/.limits。直接照抄 3.18 的 struct cpufreq_governor 去写 5.x governor 编译不过。拆分版本未验证。
  3. CPUFREQ_GOV_DYNAMIC_SWITCHING 变成了 dynamic_switching 布尔。 schedutil 素材写的是 .flags = CPUFREQ_GOV_DYNAMIC_SWITCHING，5.9 源码是 .dynamic_switching = true——这是素材内部的一处不一致（与其声明的 5.10.61 不符），本篇按源码字段名呈现并注明早期形态。
  4. sugov 慢速路径的执行体换过三代。 workqueue → RT kthread（SCHED_FIFO，优先级 50）→ SCHED_DEADLINE。5.9 源码里 sugov_kthread_create 用 sched_setattr_nocheck 设 deadline，失败才降级并警告，与素材描述一致。
  5. sugov_start 里 need_freq_update 的初值 5.9 与 5.10 不同（前者 cpufreq_driver_test_flags(CPUFREQ_NEED_UPDATE_LIMITS)，后者 false）。素材代码片段是 5.10 形态，正文解释沿用了更早的语义，本篇两者都写。
  6. struct sugov_policy 的 work 字段类型从 struct work_struct 变成 struct kthread_work（4.7 → 5.x），并多了 worker/thread 字段。素材按 5.10 呈现，与 4.7 原始实现不同。
  7. sugov_should_update_freq 在 4.7 有 work_in_progress 早退，5.9 没有。 4.7 开头是 if (sg_policy->work_in_progress) return false; 加 need_freq_update 分支；5.9 换成 cpufreq_this_cpu_can_update() 加 limits_changed 分支。这处差异影响快慢路径行为，读老代码时留意。
  8. get_next_freq 在 4.7 没有 cached_raw_freq 缓存，直接返回 (freq + (freq >> 2)) * util / max；缓存与 cpufreq_driver_resolve_freq 是后来加的。素材描述的缓存逻辑对应 5.x。
  9. cpufreq_verify_within_limits 的代码片段是概念示意。 3.18 的实际实现通过 __cpufreq_verify_within_limits/cpufreq_verify_within_cpu_limits 等辅助函数完成，与示意版不逐行一致，引用请以源码为准。
  10. bL_cpufreq_set_rate 的完整实现不在素材中。 big Little 篇只描述了它的行为。本篇代码是按描述重构的逻辑主干，不是 3.18 源码逐行复制，配对核预处理与电压域处理已省略，不要当成源码引用。
  11. CPUFREQ_HAVE_GOVERNOR_PER_POLICY 的副作用。 概述篇说它「为每一个 CPU 创建一个 cpufreq 调频接口」，这个说法不准确。准确语义是「每个 policy 一套 governor 目录与 tunable」，不是「每个 CPU 一个 policy」。本篇按 get_governor_parent_kobj() 的实际行为修正。
  12. policy->policy 字段名不是笔误，它是 CPUFREQ_POLICY_PERFORMANCE/_POWERSAVE 枚举，第三章已解释，避免读者按字面理解成「策略结构体」。
  13. sysfs 路径两套写法都对。 素材里 /sys/devices/system/cpu/cpufreq/policyX/ 与 /sys/devices/system/cpu/cpuX/cpufreq/ 分别来自不同版本（前者是较新的全局 policy 视图，后者是传统 per-CPU 视图）。本篇统一按后者描述，读者按自己的内核版本找对应路径。
  14. 「schedutil 是 4.7 引入」的核对依据：cregit 的 4.7 tag 下 kernel/sched/cpufreq_schedutil.c 已存在，作者 Rafael J. Wysocki，Copyright 2016 Intel。
  15. iowait boost 的常数值核对无误。 素材写「翻倍直到 1024」，源码是 min_t(unsigned int, boost << 1, SCHED_CAPACITY_SCALE)；素材写「第一次唤醒设 128」，IOWAIT_BOOST_MIN 定义为 SCHED_CAPACITY_SCALE / 8 即 128，两处都一致。
