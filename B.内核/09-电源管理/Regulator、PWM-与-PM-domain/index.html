先把边界划清。 这篇讲三个「硬件资源抽象框架」：Regulator（电压/电流调节器）、PWM（脉宽调制）、PM domain（电源域）。三个框架的共同点是——设备需要某个硬件资源，内核把它抽象成一个可以按名字申请、按句柄操作的物件，把「谁有资格改它、改到什么范围」这件事从驱动手里收归通用逻辑。

本文只讲这三套框架的软件结构：consumer 侧 API、provider 侧数据结构与注册流程、核心的协商与开关逻辑、设备树绑定。不讲：具体的 PMIC 驱动寄存器细节（TPS65913、RK808 之类各有 datasheet）、不推导 DCDC/LDO 的电路原理、不展开 PWM 在背光/风扇子系统里的调光算法、不讲 CPU 电源域与 cpuidle 的耦合（那部分在《CPU 电源管理：topology、hotplug 与 cpuidle》里）。

跨篇指路：时钟树的同构框架在《CCF：Common Clock Framework 框架层》里；PM domain 的开关挂在 Runtime PM 的引用计数上，引用计数那套在《Runtime PM 与驱动的电源管理》里；系统 suspend 时 PM domain 的最深状态选择与 QoS 约束在《Suspend 流程与唤醒事件框架》和《Thermal 与 PM QoS》里（后者同批）。三者常在一个设备树节点里配套出现：一个 &i2c 下的 codec 节点，同时要 clocks、power-domains、VDDA-supply 三样东西。

版本说明：Regulator 素材对应 3.x~4.x（struct regulator_desc 的正文字段与 4.4 一致，ena_gpiod 统一是 4.19 的事）；PWM 素材是 3.x 的 pwm_config/pwm_enable 老接口；PM domain 素材明写 3.18-rc4。三篇都逐处标了 4.x/5.x 的变化，没把握的地方写「未验证」。

一、三个框架的共同模式 #

三个框架的代码位置、抽象对象、能力完全不同，但骨架是同一张图。看懂一张，剩下两张只需要对照。

四个角色在三个框架里名字不同但职能一样：

  • consumer driver：用资源的普通驱动。uart 要 clock，codec 要电压，背光要 PWM，摄像头要 power domain。
  • provider driver：管资源的那层，读写寄存器。PMIC 驱动、SoC PWM 控制器驱动、SoC 电源域驱动。
  • framework core：与硬件无关的通用逻辑，建表、计数、协商、加锁。
  • machine description：DTS（或者老式的 board file）。它只描述拓扑和物理限制，不写逻辑。

一条贯穿三者的设计原则：consumer 永远不许直接碰寄存器，provider 永远不许自己决定上限。上限写在 DTS 里（regulator 的 regulator-max-microvolt、PWM 的周期上限由硬件决定、genpd 的 power_down_ok 由 governor 决定），由 core 负责在每次操作前检查。这条原则的来源是安全——配错 regulator 的输出电压可以直接烧掉负载芯片。

二、Regulator 要解决什么：电压不是随便给的 #

Regulator 在电子工程里是 voltage regulator（稳压器）或 current regulator（稳流器）的简称：能自动维持恒定电压或电流的装置。voltage regulator 最早用在功放电路里滤纹波、消噪声，避免「输出电压随负载变化」；IC 级 regulator 便宜下来之后，几乎每颗嵌入式设备上的每一种电压都是 regulator 出来的。current regulator 少见得多，主要活在电流源和 LED 照明里：一是别让驱动电流超过额定值把 LED 烧坏，二是保证各颗 LED 的亮度和色度一致。

从驱动角度看，regulator 的控制就三件事：使能/禁止、改输出电压（或限流值）、查状态。框架存在的理由不是「把这三件事包一层」，而是下面四个必须回答的问题：

  1. 安全。错误配置可以损毁硬件。consumer 和 provider 都不一定知道板级电气的真实限制，所以限制必须由 machine（产品+硬件设计）确定，写死在 DTS 里，运行期软件不得篡改。
  2. 大部分设备懒得管。很多设备只关心电源在不在，连 enable/disable 都不写。框架得让「什么都不做」成为合法状态，不能逼每个驱动都写一遍电压管理。
  3. 一路供电多个设备。两个 consumer 一个要 1.2V 一个要 1.8V，怎么办？框架要有一个仲裁规则。
  4. 级联。DCDC 输出喂给 LDO，LDO 再喂给负载。前级被关掉，后级全灭；后级要升压，前级得先跟上。这层父子关系必须显式建模。

内核 regulator 框架给出的答案是三层结构：

  • machine：struct regulator_init_data，静态描述板级现状——前级（supply）是谁、物理限制是什么、哪些 consumer 用它。
  • driver：struct regulator_desc（静态描述）+ struct regulator_config（运行期信息），一起喂给 regulator_register()，拿到 struct regulator_dev。
  • consumer：struct regulator，一个不透明句柄，等价于 CCF 里的 struct clk。

core 负责把三层粘起来，并额外吐一套 sysfs。和 CCF 的区别只有一处：regulator 的级联关系是静态的（板子焊死就定了），所以在注册时由 machine 描述，不像 clock 那样靠名字动态形成父子树。

三、regulator 的硬件模型：LDO、BUCK、PMIC #

看一个真实的拓扑。素材用的是 NVIDIA Tegra Dalmore A04（arch/arm/boot/dts/tegra114-dalmore.dts），够复杂，正好把几种形态凑齐：

器件 形态 怎么连 里面有什么
TI tps51632 单路降压控制器 i2c@7000d000 下的 tps51632@43 一路 vdd-cpu
TI tps65090 前端 PMIC（带充电） 同一 I2C 总线，tps65090@48 charger + dcdc1、dcdc2…
TI tps65913 PMIC + GPIO 同一 I2C 总线 vddio-ddr、vdd-core…
SoC 内部 fixed regulator regulators 节点，compatible = "simple-bus" vdd_ac_bat、dvdd_ts 等

物理上没有「regulators」这个实体，它是软件抽象。LDO（low dropout，低压差线性稳压器）只能降压，效率 = Vout/Vin，压差大就发热，但输出干净、响应快、成本低；BUCK（降压型 DC-DC 开关电源）靠电感储能，效率高（80%~95%），但输出有开关纹波、外围要电感电容，瞬态响应比 LDO 慢。实际 PMIC 里两种混着放：核心电压用 BUCK，模拟/IO 用 LDO。

这两条电气差异直接反映到软件字段上：BUCK 改电压后电压是「爬」上去的，需要 ramp_delay（单位 uV/us）算出延时；LDO 和 BUCK 都要配 enable_time（上电到输出稳定）；BUCK 在轻载时能切 PFM 省电、重载切 PWM 保纹波，这就是 operation mode。

DTS 怎么切分节点，取决于软件模块划分，不是硬件的物理边界。素材对此有三条注，条条都是踩过的坑：

  • i2c@7000d000 自己没写 compatible——它在 tegra114.dtsi 里写了，DTC 编译时把两个文件合并。
  • 内核只给二级节点（/ 的直接子节点，比如 i2c@7000d000）创建 platform device；三级节点（tps51632@43）由它的 bus（i2c core）创建。
  • regulators { } 这种既没 compatible 又被 MFD 驱动手工创建 platform device 的情况，要去看 drivers/mfd/tps65090.c；而 compatible = "simple-bus" 的 regulators 节点下的一堆 fixed regulator，则靠 of_platform_bus_create() 递归创建。

一张对照表，把「节点在哪一层、谁创建 device」说清：

DTS 位置 device 由谁创建 driver 是什么
/ 下（如 i2c@7000d000） of_platform_populate platform driver
i2c 从设备（tps51632@43） i2c core i2c driver
MFD 子设备（regulators） MFD 驱动 mfd_add_devices platform driver
simple-bus 子节点（regulator@0） of_platform_bus_create regulator-fixed

写 regulator 驱动的通用套路是固定的四步：初始化宿主（PMIC 的 I2C 通道等）、填 desc + config、调 regulator_register()、把剩下的 sysfs 和 attribute 交给 core。真正花时间的是第二步里那些寄存器位域。

四、struct regulator_desc：怎么描述一个 regulator #

regulator_desc 是静态描述：注册后不再改变，因此它的变量必须是全局/静态存储期，而不是 probe 里的栈变量。素材给出的字段（3.x~4.4）逐条列在这里：

c
/* include/linux/regulator/driver.h —— 3.x/4.4 字段全集 */
struct regulator_desc {
        const char *name;                       /* 唯一标识，必须给 */
        const char *supply_name;                /* 前级 regulator 名字 */
        const char *of_match;                   /* DTS 子节点匹配名 */
        const char *regulators_node;            /* 可选容器节点名 */
        int id;
        bool continuous_voltage_range;
        unsigned n_voltages;                    /* list_voltage() 可枚举个数 */
        const struct regulator_ops *ops;
        int irq;
        enum regulator_type type;               /* REGULATOR_VOLTAGE / _CURRENT */
        struct module *owner;

        unsigned int min_uV;                    /* 线性映射：v = min_uV + sel*uV_step */
        unsigned int uV_step;
        unsigned int linear_min_sel;
        int fixed_uV;                           /* 固定输出轨 */
        unsigned int ramp_delay;                /* uV/us，core 用它算换压延时 */

        const struct regulator_linear_range *linear_ranges;  /* 分段线性（4.x） */
        int n_linear_ranges;
        const unsigned int *volt_table;         /* 表驱动映射 */

        unsigned int vsel_reg, vsel_mask;       /* 电压选择位 */
        unsigned int apply_reg, apply_bit;      /* 「写这里才生效」的触发位 */
        unsigned int enable_reg, enable_mask, enable_val, disable_val;
        bool enable_is_inverted;
        unsigned int bypass_reg, bypass_mask, bypass_val_on, bypass_val_off;

        unsigned int enable_time;               /* 上电稳定时间 us */
        unsigned int off_on_delay;              /* 关后重开的最小间隔 us */
};

五、struct regulator_ops：provider 要实现什么 #

ops 是 provider 唯一需要写代码的地方。它不是必须全实现——core 会按你在 constraints 里声明的能力（valid_ops_mask）决定哪些操作允许走。

c
struct regulator_ops {
        /* enumerate supported voltages */
        int (*list_voltage) (struct regulator_dev *, unsigned selector);

        /* get/set regulator voltage */
        int (*set_voltage) (struct regulator_dev *, int min_uV, int max_uV,
                            unsigned *selector);
        int (*map_voltage)(struct regulator_dev *, int min_uV, int max_uV);
        int (*set_voltage_sel) (struct regulator_dev *, unsigned selector);
        int (*get_voltage) (struct regulator_dev *);
        int (*get_voltage_sel) (struct regulator_dev *);

        /* get/set regulator current  */
        int (*set_current_limit) (struct regulator_dev *,
                                 int min_uA, int max_uA);
        int (*get_current_limit) (struct regulator_dev *);

        /* enable/disable regulator */
        int (*enable) (struct regulator_dev *);
        int (*disable) (struct regulator_dev *);
        int (*is_enabled) (struct regulator_dev *);

        /* get/set regulator operating mode (defined in consumer.h) */
        int (*set_mode) (struct regulator_dev *, unsigned int mode);
        unsigned int (*get_mode) (struct regulator_dev *);

        /* Time taken to enable or set voltage on the regulator */
        int (*enable_time) (struct regulator_dev *);
        int (*set_ramp_delay) (struct regulator_dev *, int ramp_delay);
        int (*set_voltage_time_sel) (struct regulator_dev *,
                                     unsigned int old_selector,
                                     unsigned int new_selector);

        int (*get_status)(struct regulator_dev *);

        unsigned int (*get_optimum_mode) (struct regulator_dev *, int input_uV,
                                          int output_uV, int load_uA);

        /* control and report on bypass mode */
        int (*set_bypass)(struct regulator_dev *dev, bool enable);
        int (*get_bypass)(struct regulator_dev *dev, bool *enable);

        /* parent PMIC 进入 STANDBY/HIBERNATE 时的状态 */
        int (*set_suspend_voltage) (struct regulator_dev *, int uV);
        int (*set_suspend_enable) (struct regulator_dev *);
        int (*set_suspend_disable) (struct regulator_dev *);
        int (*set_suspend_mode) (struct regulator_dev *, unsigned int mode);
};

按「用不用得上」分档：

回调 必要性 干什么 典型实现
enable / disable 绝大多数要 打开/关闭输出 regmap_update_bits(rdev->regmap, desc->enable_reg, desc->enable_mask, desc->enable_val)
is_enabled 建议 回读开关状态 读 enable_reg 比对 enable_val
list_voltage 走 selector 时必须 sel → uV desc->min_uV + sel * desc->uV_step 或查 volt_table
set_voltage_sel 走 selector 时二选一 按 sel 写寄存器 写 vsel_reg，必要时再写 apply_reg
set_voltage 直接传电压时二选一 区间内挑一个最接近 min_uV 的档 driver 自己做除法
map_voltage 可选（core 能代劳） 电压区间 → sel 一般用 core 的 regulator_map_voltage_linear()
get_voltage_sel / get_voltage 可选 回读当前电压 读 vsel_reg 后查表

互斥约束（core 在注册时 WARN 或直接返回 -EINVAL）：

c
WARN_ON(regulator_desc->ops->get_voltage && regulator_desc->ops->get_voltage_sel);
WARN_ON(regulator_desc->ops->set_voltage && regulator_desc->ops->set_voltage_sel);

/* 用了 selector 就必须能枚举 */
if (ops->get_voltage_sel && !ops->list_voltage) return ERR_PTR(-EINVAL);
if (ops->set_voltage_sel && !ops->list_voltage) return ERR_PTR(-EINVAL);

这条规则的道理：get_voltage 返回 uV，get_voltage_sel 返回 sel，同时实现会让上层不知道拿到的数是什么单位。至于 4.19 里 ops 新增的 set_input_current_limit、set_over_current_protection、set_active_discharge、get_error_flags、set_load、set_soft_start、set_pull_down、resume、set_voltage_time，以及 get_status 位置的变化，都是逐个 patch 加的，写代码按你的内核头文件为准。

六、regulator_register 的流程 #

regulator_register(desc, config) 把静态描述和一个临时 config 合成一个 struct regulator_dev，挂进系统。素材给的是 3.x 版本，主干逻辑到 4.4 基本没动：

c
/* 3.x drivers/regulator/core.c。原文 187 行按语义段压掉空行，if 条件、goto、label 全部保留 */
struct regulator_dev *
regulator_register(const struct regulator_desc *regulator_desc,
                   const struct regulator_config *config)
{
        const struct regulation_constraints *constraints = NULL;
        const struct regulator_init_data *init_data;
        static atomic_t regulator_no = ATOMIC_INIT(0);
        struct regulator_dev *rdev;
        struct device *dev;
        int ret, i;
        const char *supply = NULL;

        /* 段1 参数（22~49）：name/ops 非空、type 合法、电压回调互斥 */
        if (regulator_desc == NULL || config == NULL)
                return ERR_PTR(-EINVAL);
        dev = config->dev;
        WARN_ON(!dev);
        if (regulator_desc->name == NULL || regulator_desc->ops == NULL)
                return ERR_PTR(-EINVAL);
        if (regulator_desc->type != REGULATOR_VOLTAGE &&
            regulator_desc->type != REGULATOR_CURRENT)
                return ERR_PTR(-EINVAL);
        WARN_ON(regulator_desc->ops->get_voltage && regulator_desc->ops->get_voltage_sel);
        WARN_ON(regulator_desc->ops->set_voltage && regulator_desc->ops->set_voltage_sel);
        if (regulator_desc->ops->get_voltage_sel && !regulator_desc->ops->list_voltage)
                return ERR_PTR(-EINVAL);
        if (regulator_desc->ops->set_voltage_sel && !regulator_desc->ops->list_voltage)
                return ERR_PTR(-EINVAL);
        /* 段2 分配 + DTS 解析回退（51~60） */
        rdev = kzalloc(sizeof(struct regulator_dev), GFP_KERNEL);
        if (rdev == NULL)
                return ERR_PTR(-ENOMEM);
        init_data = regulator_of_get_init_data(dev, regulator_desc, &rdev->dev.of_node);
        if (!init_data) {
                init_data = config->init_data;
                rdev->dev.of_node = of_node_get(config->of_node);
        }
        mutex_lock(&regulator_list_mutex);
        /* 段3 字段 + regmap 三级回退 config->自己->parent（64~77） */
        mutex_init(&rdev->mutex);
        rdev->reg_data = config->driver_data;
        rdev->owner = regulator_desc->owner;
        rdev->desc = regulator_desc;
        if (config->regmap)
                rdev->regmap = config->regmap;
        else if (dev_get_regmap(dev, NULL))
                rdev->regmap = dev_get_regmap(dev, NULL);
        else if (dev->parent)
                rdev->regmap = dev_get_regmap(dev->parent, NULL);
        INIT_LIST_HEAD(&rdev->consumer_list);
        INIT_LIST_HEAD(&rdev->list);
        BLOCKING_INIT_NOTIFIER_HEAD(&rdev->notifier);
        INIT_DELAYED_WORK(&rdev->disable_work, regulator_disable_work);
        /* 段4 machine 私有 init（79~84） */
        if (init_data && init_data->regulator_init) {
                ret = init_data->regulator_init(rdev->reg_data);
                if (ret < 0)
                        goto clean;
        }
        /* 段5 注册 device，名字 regulator.N（86~97） */
        rdev->dev.class = &regulator_class;
        rdev->dev.parent = dev;
        dev_set_name(&rdev->dev, "regulator.%d", atomic_inc_return(&regulator_no) - 1);
        ret = device_register(&rdev->dev);
        if (ret != 0) {
                put_device(&rdev->dev);
                goto clean;
        }
        dev_set_drvdata(&rdev->dev, rdev);
        /* 段6 enable GPIO（99~112） */
        if (config->ena_gpio && gpio_is_valid(config->ena_gpio)) {
                ret = regulator_ena_gpio_request(rdev, config);
                if (ret != 0) {
                        rdev_err(rdev, "Failed to request enable GPIO%d: %d\n",
                                 config->ena_gpio, ret);
                        goto wash;
                }
                if (config->ena_gpio_flags & GPIOF_OUT_INIT_HIGH)
                        rdev->ena_gpio_state = 1;
                if (config->ena_gpio_invert)
                        rdev->ena_gpio_state = !rdev->ena_gpio_state;
        }
        /* 段7 constraints + sysfs attribute（114~125） */
        if (init_data)
                constraints = &init_data->constraints;
        ret = set_machine_constraints(rdev, constraints);
        if (ret < 0)
                goto scrub;
        ret = add_regulator_attributes(rdev);
        if (ret < 0)
                goto scrub;
        /* 段8 建父子树（127~160）：-ENODEV 当根节点，查不到则 -EPROBE_DEFER */
        if (init_data && init_data->supply_regulator)
                supply = init_data->supply_regulator;
        else if (regulator_desc->supply_name)
                supply = regulator_desc->supply_name;
        if (supply) {
                struct regulator_dev *r;

                r = regulator_dev_lookup(dev, supply, &ret);
                if (ret == -ENODEV) {
                        ret = 0;
                        goto add_dev;
                } else if (!r) {
                        dev_err(dev, "Failed to find supply %s\n", supply);
                        ret = -EPROBE_DEFER;
                        goto scrub;
                }
                ret = set_supply(rdev, r);
                if (ret < 0)
                        goto scrub;
                if (_regulator_is_enabled(rdev)) {      /* 后级开着就顺手开前级 */
                        ret = regulator_enable(rdev->supply);
                        if (ret < 0)
                                goto scrub;
                }
        }
add_dev:
        /* 段9 consumer 映射（162~175） */
        if (init_data) {
                for (i = 0; i < init_data->num_consumer_supplies; i++) {
                        ret = set_consumer_device_supply(rdev,
                                init_data->consumer_supplies[i].dev_name,
                                init_data->consumer_supplies[i].supply);
                        if (ret < 0) {
                                dev_err(dev, "Failed to set supply %s\n",
                                        init_data->consumer_supplies[i].supply);
                                goto unset_supplies;
                        }
                }
        }
        /* 段10 挂全局链表 + debugfs（177~179） */
        list_add(&rdev->list, &regulator_list);
        rdev_init_debugfs(rdev);
out:
        mutex_unlock(&regulator_list_mutex);
        return rdev;
        /* 四个 label，撤销范围逐级递减（184~201） */
unset_supplies:
        unset_regulator_supplies(rdev);
scrub:
        if (rdev->supply)
                _regulator_put(rdev->supply);
        regulator_ena_gpio_free(rdev);
        kfree(rdev->constraints);
wash:
        device_unregister(&rdev->dev);          /* device core 负责 free rdev */
        rdev = ERR_PTR(ret);
        goto out;
clean:
        kfree(rdev);
        rdev = ERR_PTR(ret);
        goto out;
}
EXPORT_SYMBOL_GPL(regulator_register);

把这段拆成阶段看，每一段失败落到哪个 label 也要记：

阶段 行号（素材） 干什么 失败去向
参数校验 22~49 desc/config 非空、name/ops 非空、type 合法、电压/选择器回调互斥 直接 -EINVAL
内存 51~53 分配 regulator_dev -ENOMEM
DTS 解析 55~60 先试 regulator_of_get_init_data()，拿不到才用 config->init_data —
结构初始化 62~77 锁、regmap（config → 自己 → parent 三级回退）、consumer_list、notifier、disable_work —
machine 私有 init 80~84 init_data->regulator_init(rdev->reg_data) clean
注册 device 86~97 class = regulator_class、名字 regulator.N、device_register clean
enable GPIO 99~112 申请 GPIO、按 flags 定初值、处理反相 wash
应用 constraints 114~120 set_machine_constraints()，这是最重的一步 scrub
加 attribute 122~125 add_regulator_attributes() 按 ops 能力建 sysfs scrub
建 supply 关系 127~160 查前级 regulator_dev、set_supply()、必要时把前级也 enable scrub（找不到则 -EPROBE_DEFER）

收尾 177~179 挂 regulator_list、建 debugfs —

三条值得记住的细节：

  1. -EPROBE_DEFER 从这里来。前级 regulator 的 device 还没注册，regulator_dev_lookup() 拿不到 r，就返回 defer，让 probe 重来。PMIC 驱动链上这个 defer 会传导好几层。
  2. _regulator_is_enabled(rdev) 为真时要把前级也打开。这是「后级开、前级必须开」在注册阶段就落实的一次。
  3. 错误路径上的 rdev 归属不同。wash 之前的错误要 kfree(rdev)；进了 wash 说明 device 已注册，由 device core 释放，所以只写 rdev = ERR_PTR(ret)。照抄时别把 kfree 挪来挪去。

4.19 版本的差异（对照上游源码）：多了 regulator_resolve_coupling() 处理多路联调，config->ena_gpio/ena_gpio_invert/ena_gpio_flags 三个整数字段被合成一个 struct gpio_desc *ena_gpiod，rdev->mutex 从 struct mutex 换成 struct ww_mutex（多路联动要用，还得加 mutex_owner/ref_cnt）。这三处都会让老驱动编译不过。

七、constraints：电压与电流的约束条件 #

struct regulator_init_data 是 machine 层的载体，DTS 里的 regulator-* 属性全部落在这里：

c
struct regulator_init_data {
        const char *supply_regulator;        /* or NULL for system supply */

        struct regulation_constraints constraints;

        int num_consumer_supplies;
        struct regulator_consumer_supply *consumer_supplies;

        /* optional regulator machine specific init */
        int (*regulator_init)(void *driver_data);
        void *driver_data;      /* core does not touch this */
};
  • supply_regulator：前级名字，一般由 driver 直接给（也可以在 DTS 里给）。
  • constraints：所有物理限制，DTS 配，框架的 of_get_regulation_constraints() 解析。
  • num_consumer_supplies / consumer_supplies：哪些设备用这一路，每项是 (dev_name, supply) 对。
  • regulator_init / driver_data：machine 私有初始化，注册时回调一次。

struct regulation_constraints 才是重点：

c
struct regulation_constraints {
        const char *name;

        /* voltage output range (inclusive) - for voltage control */
        int min_uV;
        int max_uV;
        int uV_offset;

        /* current output range (inclusive) - for current control */
        int min_uA;
        int max_uA;

        /* valid regulator operating modes for this machine */
        unsigned int valid_modes_mask;

        /* valid operations for regulator on this machine */
        unsigned int valid_ops_mask;

        /* regulator input voltage - only if supply is another regulator */
        int input_uV;

        /* regulator suspend states for global PMIC STANDBY/HIBERNATE */
        struct regulator_state state_disk;
        struct regulator_state state_mem;
        struct regulator_state state_standby;
        suspend_state_t initial_state; /* suspend state to set at init */

        /* mode to set on startup */
        unsigned int initial_mode;

        unsigned int ramp_delay;
        unsigned int enable_time;

        /* constraint flags */
        unsigned always_on:1;   /* regulator never off when system is on */
        unsigned boot_on:1;     /* bootloader/firmware enabled regulator */
        unsigned apply_uV:1;    /* apply uV constraint if min == max */
        unsigned ramp_disable:1; /* disable ramp delay */
};
字段 保护的是什么 配错的后果
min_uV / max_uV 输出窗口 上界给高，consumer 要一个高电压就烧负载
uV_offset consumer 视角与实际电压的偏移（补线损） 补偿方向搞反，实际电压比请求值低
min_uA / max_uA 限流窗口（current regulator） 限流点过高，短路时保护不住
valid_ops_mask 允许哪些操作 放开 REGULATOR_CHANGE_VOLTAGE 却没人管窗口，电压可被乱调
valid_modes_mask 允许哪些 operation mode —
input_uV 前级给多少电压 前级不够，后级 LDO 掉出 dropout 区
state_disk / state_mem / state_standby 系统深度睡眠时该路的状态 休眠后该断电的没断，功耗超标
initial_mode 启动模式 该进省电模式的没进
ramp_delay / ramp_disable 换压延时 延时不足，换压期间负载欠压
enable_time 上电稳定时间 提前访问设备，读回全 0
always_on / boot_on / apply_uV 见第十四章 见第十四章

valid_ops_mask 的六个取值：

宏 含义
REGULATOR_CHANGE_VOLTAGE 允许 regulator_set_voltage()
REGULATOR_CHANGE_CURRENT 允许 regulator_set_current_limit()
REGULATOR_CHANGE_MODE 允许 regulator_set_mode()
REGULATOR_CHANGE_STATUS 允许 enable/disable
REGULATOR_CHANGE_DRMS 允许 Dynamic Regulator Mode Switching，即 regulator_set_optimum_mode()
REGULATOR_CHANGE_BYPASS 允许 regulator_allow_bypass()

素材里 rapm_delay 是 ramp_delay 的笔误，此处已更正。另注：enable_time 在 DTS 里没有对应属性，来自 driver 或 desc。

八、consumer 侧：regulator_get 与 devm_regulator_get #

consumer 拿句柄的接口一共六个 get 加两个 put：

c
struct regulator *__must_check regulator_get(struct device *dev, const char *id);
struct regulator *__must_check devm_regulator_get(struct device *dev, const char *id);
struct regulator *__must_check regulator_get_exclusive(struct device *dev, const char *id);
struct regulator *__must_check devm_regulator_get_exclusive(struct device *dev, const char *id);
struct regulator *__must_check regulator_get_optional(struct device *dev, const char *id);
struct regulator *__must_check devm_regulator_get_optional(struct device *dev, const char *id);
void regulator_put(struct regulator *regulator);
void devm_regulator_put(struct regulator *regulator);

三类语义：

系列 能否共享 能否重复 get 拿不到时 用在什么场景
regulator_get 可共享 可以 返回 -EPROBE_DEFER/错误 普通外设，默认就用这个
regulator_get_exclusive 独占 不行 错误 开关类 regulator（如 USB VBUS 控制）
regulator_get_optional 可共享 不行 返回 NULL 板子上没焊这一路的可选电源

id 对应 DTS 里的 <id>-supply 属性。id = "vdd" 就找 vdd-supply = <&ldo3>;。NULL 则取 dev 节点下的第一个 supply。

实际写驱动时，99% 的情况用 devm_regulator_get()，让设备释放时自动 put。批量电源用 bulk 版本：

c
static const struct regulator_bulk_data my_supplies[] = {
        { .supply = "vdd" },
        { .supply = "vddio" },
};
struct regulator_bulk_data supplies[ARRAY_SIZE(my_supplies)];

memcpy(supplies, my_supplies, sizeof(supplies));
ret = devm_regulator_bulk_get(dev, ARRAY_SIZE(supplies), supplies);
if (ret)
        return ret;
ret = regulator_bulk_enable(ARRAY_SIZE(supplies), supplies);
/* 失败时逐个回滚已成功的那几路；顺序由数组顺序决定，不是原子的 */

bulk 的实现是「逐个来，失败就回滚已成功的」，所以它并不原子——上电顺序的语义要靠数组顺序表达。

其余 consumer API（3.x）：regulator_force_disable（无视计数直接关，调试用）、regulator_disable_deferred(reg, ms)（塞进 rdev->disable_work 延时关，配合 last_off_jiffy）、regulator_can_change_voltage、regulator_count_voltages、regulator_list_voltage、regulator_is_supported_voltage、regulator_get_linear_step、regulator_set_voltage_time、regulator_sync_voltage、regulator_set_optimum_mode、regulator_allow_bypass、regulator_get_regmap、regulator_get_hardware_vsel_register、regulator_list_hardware_vsel，以及 supply alias 的 *_register_supply_alias / *_unregister_supply_alias 与 notifier 的 regulator_register_notifier / unregister_notifier。

supply alias 的用处：同一颗 codec 驱动在 A 板叫 vdd-audio、B 板叫 vdd-cp，与其改驱动，不如在 machine 初始化时注册一条 alias，把 "vdda" 重定向到真实名字。纯软件层翻译，不涉及电气。

supply alias 存在的意义：一颗 codec 驱动本来是给 max98090 写的，硬件上它挂到的板子叫 vdd-audio，而另一块板子叫 vdd-cp。打板的人不想改驱动，于是在 machine 初始化时注册一条 alias，把 dev 下的 "vdda" 重定向到真实的 "vdd-audio"。这是一个纯软件层的名字翻译，不涉及任何电气。

regulator_disable_deferred() 值得单独提：它把 disable 塞进 rdev->disable_work 延时执行，配合 rdev->last_off_jiffy，用于「短时间内反复开关会缩短电容寿命/增加纹波」的场景。任何一次新的 enable 都要把排队的 disable 取消掉。

九、regulator_enable 的引用计数 #

一路 regulator 可以被多个 consumer 同时用。谁 import 一次，use_count 加一；谁 release 一次，减一；只有减到 0 才真正写硬件关断。这个计数记在 regulator_dev 上：

字段 归属 含义
use_count regulator_dev 物理使能计数。0→1 才调 ops->enable，1→0 才调 ops->disable
open_count regulator_dev 共享 get 的次数（有多少个 struct regulator 句柄指向我）
bypass_count regulator_dev 有多少 consumer 请求了 bypass
exclusive regulator_dev 是否已被独占 get
consumer_list regulator_dev 所有挂在我身上的 struct regulator

regulator_enable(reg) 的语义：

  1. 检查 constraints->valid_ops_mask 有没有 REGULATOR_CHANGE_STATUS，没有就返回 -EPERM。
  2. 如果 rdev->use_count == 0，先确保前级 supply 已开（regulator_enable(rdev->supply)），再调 rdev->desc->ops->enable(rdev)。
  3. use_count++。之后按 constraints->enable_time（或 ops->enable_time）延时。
  4. 已经是 use_count > 0 时只做 use_count++，不碰硬件。

三个与它配合的坑：

  • 电源树倒挂。regulator_enable() 必须在 probe 里被显式调用，不会因为 consumer 拿到句柄就自动上电。忘了调，regulator_get() 一切正常，设备却读回全 0。
  • regulator_disable() 在 use_count == 0 时会 WARN。这就是 enable/disable 不成对，或者驱动在 error path 上多关了一次。
  • regulator_force_disable() 无视计数。它是给「系统就要挂了，别管谁在用」的场景准备的，不要在产品路径上用。

一个典型的成对写法：

c
static int foo_probe(struct platform_device *pdev)
{
        f->vdd = devm_regulator_get(&pdev->dev, "vdd");
        if (IS_ERR(f->vdd))
                return PTR_ERR(f->vdd);
        if (regulator_enable(f->vdd))           /* devm 不管 enable！ */
                return -EIO;
        ret = foo_hw_init(f);
        if (ret) {
                regulator_disable(f->vdd);      /* 错误路径必须成对回滚 */
                return ret;
        }
        return 0;
}
/* remove: foo_hw_exit(f); regulator_disable(f->vdd); —— 只有 put 是自动的 */

最后一行的注释值得刻在脑子里：devm_regulator_get() 只在内核自动回收时调用 regulator_put()，不会替你 regulator_disable()。enable/disable 永远要自己成对。

十、regulator_set_voltage 的完整链路 #

consumer 说「我要在 [min_uV, max_uV] 之间」，落到硬件是一个 selector。中间要过四道关：machine 窗口、selector 枚举、ops 调用、延时补偿。

text
regulator_set_voltage(reg, min_uV, max_uV)
  └─ regulator_set_voltage_unlocked()
       ├─ ① 与前级协商：必要时先把 supply 的电压抬上去
       ├─ ② 检查 constraints->valid_ops_mask & REGULATOR_CHANGE_VOLTAGE
       ├─ ③ 检查 [min_uV,max_uV] ∩ [constraints->min_uV, constraints->max_uV] 非空
       ├─ ④ 在当前 use_count / consumer 请求之间取交集
       ├─ ⑤ ops->set_voltage(rdev, min, max, &selector)     ← 或走 selector 路径
       │     └─ 内部 vsel 写寄存器
       ├─ ⑥ 若 constraints->ramp_delay 非 0，计算延时并 msleep
       └─ ⑦ 记录 rdev 当前电压，通知 notifier

第 ③ 步是安全底线，返回 -EINVAL 的典型信息就是「请求电压超出 machine 限制」。第 ④ 步是「一路多 consumer」的仲裁：框架把每个 consumer 的请求区间取交集，交集为空就失败——它不会去「折中」，因为没有物理上正确的折中点。

两条操作路径，driver 选一条：

路径 需要的 ops 请求单位 优点 缺点
直接电压 set_voltage + list_voltage（可选 get_voltage） uV driver 自己算档位，能处理非线性 每颗 PMIC 都要写一遍「就近取档」的除法
selector set_voltage_sel + list_voltage + 可选 map_voltage / get_voltage_sel 档位序号 可复用 core 的 regulator_map_voltage_linear() 等 helper 必须有 n_voltages 和枚举函数

注意 set_voltage 的语义：在 [min_uV, max_uV] 里挑一个最接近 min_uV 的值（不是最接近区间中点，也不是最大值）。这个约定由 regulator_ops 的注释明确规定；写反了，降压省电的场景会全部偏高。

延时怎么算。ramp_delay 单位是 uV/us（1us 能爬多少微伏），ramp_disable 非零则跳过：

c
/* core 的算法（伪代码，体现思路，非逐行引用） */
delta_uV = abs(new_uV - old_uV);

if (!constraints->ramp_disable && constraints->ramp_delay)
        delay_us = delta_uV / constraints->ramp_delay;   /* uV / (uV/us) */
else
        delay_us = 0;

/* 有 ops->set_voltage_time_sel 时优先用它给的更准的值 */
if (rdev->desc->ops->set_voltage_time_sel)
        delay_us = rdev->desc->ops->set_voltage_time_sel(rdev, old_sel, new_sel);

if (delay_us)
        usleep_range(delay_us, delay_us * 2);

usleep_range 用区间而不是精确值，是为了让高精度定时器能把这次唤醒和相邻的唤醒合并，省一次 idle 进出。这里踩过的坑：给 ramp_delay 填成了 datasheet 上的「最大爬升时间」而不是「速率」，算出来的延时会被放大几十倍，probe 时间肉眼可见地变长。

regulator_sync_voltage() 是补刀接口：某个 consumer 改了请求但当时无法生效（比如前级还没起来），之后调它让 core 重新把当前交集写下去。

十一、电压选择与硬件约束的协商 #

第 ④ 步「取交集」的具体形态值得单独拆。core 维护每个 regulator_dev 上所有 consumer 的请求，然后再跟 machine 限制求交：

参与方 来源 作用
consumer 请求 1 regulator_set_voltage(reg_a, 1150000, 1200000) 要 1.15~1.20V
consumer 请求 2 regulator_set_voltage(reg_b, 1180000, 1300000) 要 1.18~1.30V
machine 限制 constraints->min_uV / max_uV 例如 500mV~1.52V
交集结果 [max(所有 min), min(所有 max)] 1.18~1.20V

max(所有 min) 这一步会触发一个棘手的时序问题：两个 consumer 谁先请求？如果 A 先要 1.15V、core 已经把电压调到 1.15V 并延时，B 随后要 1.18V，core 再抬一次——这段时间窗口里 B 是欠压的。内核的处理办法是：consumer 侧正常只在自己 probe/工作点切换时改请求，并在改动前后配合自身的工作状态（先 idle 再请求，再唤醒）；电压 follower（如 CPU DVFS）则依赖 OPP 表和 cpufreq 的时序保证。框架本身不做「预留」，它只保证任何时刻硬件电压落在所有 active 请求的交集里。

另一条约束来自「consumer 视角偏移」uV_offset。core 在把 consumer 请求下发给 ops 之前要减去它：

text
硬件目标 = consumer 请求 - constraints->uV_offset

这个字段的存在是为了补偿从 PMIC 输出到负载引脚之间的 PCB 走线压降。如果板子上 vdd-cpu 走线很长、满载时掉 30mV，就配 regulator-microvolt-offset = <30000>，让 consumer 请求 1.0V 时 PMIC 实际输出 1.03V，负载引脚上才是 1.0V。方向搞反（写成加），满载时欠压，轻载时过压，两头都危险。

第四种参与协商的东西是联调（coupling）。多相 buck 或者「必须同步调整的两路轨」在 4.x 后期有 struct coupling_desc 支持，4.19 的 regulator_dev 里有 struct coupling_desc coupling_desc; 和一把 ww_mutex。素材（3.x）里没有这个机制，遇到多路联动需求要按你实际内核版本查 regulator_resolve_coupling()。

selector 与档位的映射，三种表都在 desc 里，core 提供了对应的 helper：

desc 里给的 用哪个 core helper 算 sel 用哪个 helper 枚举电压
min_uV + uV_step regulator_map_voltage_linear() regulator_list_voltage_linear()
linear_ranges[] regulator_map_voltage_linear_range() regulator_list_voltage_linear_range()
volt_table[] driver 自己遍历 regulator_list_voltage_table()

continuous_voltage_range = true 是特例：说明硬件在区间内连续可调，此时 n_voltages = 0，core 不做 sel→uV 的离散化，直接把 uV 交给 driver。这条只对少数用 DAC 而非分压电阻网络的 regulator 成立，普通 PMIC 不要乱填。

十二、regulator 的父子关系与 supply 传播 #

一路 regulator 的输入来自另一路 regulator，就形成了树。树根是「系统电源」（supply_regulator = NULL），叶子接负载。

text
vdd_ac_bat (fixed, 5.0V, always-on)
   └── dcdc1 (tps65090, vdd-sys-5v0)
         └── dcdc2 (tps65090, vdd-sys-3v3)
               ├── ldo1 (vddio-ddr)
               └── ldo2 (vdd-core)
                     └── vdd-cpu (tps51632, 0.5~1.52V)

regulator_dev 里表达这层关系的字段是 struct regulator *supply; /* for tree */。注意它的类型是 consumer 侧的 struct regulator，因为「把前级当成一个资源来操作」这件事，本身就是 consumer 视角——core 在这里扮演了一次 consumer。

注册时的建立顺序（对应第六章 127~160）：

  1. supply 名字先看 init_data->supply_regulator，没有再退到 regulator_desc->supply_name。
  2. regulator_dev_lookup(dev, supply, &ret) 在全局 regulator_list 里按名字找前级的 regulator_dev。
  3. 找不到且返回 -ENODEV（意思是这个 supply 永远不会有），直接跳过当根节点；找不到但「本来该有」，返回 -EPROBE_DEFER。
  4. set_supply(rdev, r) 分配一个 struct regulator 挂到 rdev->supply。
  5. 如果当前这路已经是使能状态（bootloader 开的），立刻 regulator_enable(rdev->supply)。

enable 时的传播方向是向上：后级要开，前级必须先开。disable 时方向也是向上——但只在前级的 use_count 归零后才真正关。这就是为什么 use_count 必须记在 regulator_dev 而不是 consumer 句柄上：前级根本不知道有几个后级在用它。

三处容易翻车：

  • DTS 循环引用。ldo1 的 supply 写 ldo2，ldo2 的 supply 写 ldo1。注册时两边都 -EPROBE_DEFER，然后无限重试。内核没有环检测。
  • 名字对不上。supply_name 匹配的是 regulator_desc.name，不是 sysfs 里的 regulator-name。两个名字可以不一样，这时只能靠 init_data->supply_regulator 指定。
  • 前级被 consumer 抢先改电压。如果前级也是一路可调轨道，后级 consumer 的请求不会自动传导到前级。要 regulator_set_voltage() 后级时顺带管前级，得靠 device tree 里给前级足够宽的窗口，或者 driver 自己显式调两路。

十三、设备树里的 regulator 描述 #

一个最朴素的 regulator 节点：

c
/* 方法一：driver 自己解析（drivers/regulator/of_regulator.c） */
struct regulator_init_data *of_get_regulator_init_data(struct device *dev,
                                                struct device_node *node)
{
        struct regulator_init_data *init_data;

        if (!node)
                return NULL;
        init_data = devm_kzalloc(dev, sizeof(*init_data), GFP_KERNEL);
        if (!init_data)
                return NULL;    /* Out of memory? */
        of_get_regulation_constraints(node, &init_data);   /* 逐属性填 constraints */
        return init_data;
}
EXPORT_SYMBOL_GPL(of_get_regulator_init_data);

属性到 constraints 字段的映射（硬件设计者唯一能动的手，值得背）：

DTS 属性 regulation_constraints 字段 说明
regulator-name name 描述性名字
regulator-min-microvolt min_uV 下界
regulator-max-microvolt max_uV 上界
regulator-min-microamp / -max-microamp min_uA / max_uA 限流窗口
regulator-microvolt-offset uV_offset 线损补偿
regulator-input-microvolt input_uV 前级期望输入
regulator-always-on always_on 见第十四章
regulator-boot-on boot_on 见第十四章
regulator-allow-set-load 允许 set_load 负载上报
regulator-allow-bypass REGULATOR_CHANGE_BYPASS 允许旁路
regulator-ramp-delay ramp_delay 爬升速率
regulator-enable-ramp-delay enable_time 上电延时

fixed regulator 是最常见的形态，靠通用驱动 drivers/regulator/fixed.c 就能跑，一行代码不用写：

dts
regulators {
        compatible = "simple-bus";
        #address-cells = <1>;
        #size-cells = <0>;

        vdd_ac_bat_reg: regulator@0 {
                compatible = "regulator-fixed";
                reg = <0>;

                reg = <1>;
                regulator-name = "dvdd_ts";

                enable-active-high;                                  /* -> ena_gpio_flags */
                gpio = <&gpio TEGRA_GPIO(H, 5) GPIO_ACTIVE_HIGH>;    /* -> ena_gpio      */
        };

compatible = "regulator-fixed" 加 gpio 就是「一个 GPIO 控制的开关电源」，这就是为什么 struct regulator_config 里要有 ena_gpio / ena_gpio_invert / ena_gpio_flags 三个字段——fixed regulator 的 ops 里 enable/disable 就是拉这个 GPIO。enable-active-high 落在 ena_gpio_flags 上。

DTS 的两种解析方式，driver 二选一：

方法一：自己调 of_get_regulator_init_data()。直白，适合单路器件：

c
struct regulator_init_data *of_get_regulator_init_data(struct device *dev,
                                                struct device_node *node)
{
        struct regulator_init_data *init_data;

        if (!node)
                return NULL;

        init_data = devm_kzalloc(dev, sizeof(*init_data), GFP_KERNEL);
        if (!init_data)
                return NULL; /* Out of memory? */

        of_get_regulation_constraints(node, &init_data);
        return init_data;
}
EXPORT_SYMBOL_GPL(of_get_regulator_init_data);

方法二：交给 core 的 regulator_of_get_init_data()。PMIC 有十几个 regulator 时省掉一大堆重复代码，代价是要理解它的匹配规则：

c
struct regulator_init_data *regulator_of_get_init_data(struct device *dev,
                                            const struct regulator_desc *desc,
                                            struct device_node **node)
{
        struct device_node *search, *child;
        struct regulator_init_data *init_data = NULL;
        const char *name;

        if (!dev->of_node || !desc->of_match)
                return NULL;
        /* 起点：desc->regulators_node 指定的容器，或 device 节点本身 */
        if (desc->regulators_node)
                search = of_get_child_by_name(dev->of_node, desc->regulators_node);
        else
                search = dev->of_node;
        if (!search) {
                dev_dbg(dev, "Failed to find regulator container node '%s'\n",
                        desc->regulators_node);
                return NULL;
        }
        /* 遍历子节点，用 regulator-compatible（优先）或节点名匹配 of_match */
        for_each_child_of_node(search, child) {
                name = of_get_property(child, "regulator-compatible", NULL);
                if (!name)
                        name = child->name;
                if (strcmp(desc->of_match, name))
                        continue;
                init_data = of_get_regulator_init_data(dev, child);
                if (!init_data) {
                        dev_err(dev, "failed to parse DT for regulator %s\n",
                                child->name);
                        break;
                }
                of_node_get(child);
                *node = child;          /* 回填给 regulator_register */
                break;
        }
        of_node_put(search);
        return init_data;
}

匹配逻辑梳理成三句话：

  • 起点 node：有 desc->regulators_node 就用 of_get_child_by_name() 找那个容器；没有就用 dev->of_node 本身。
  • 遍历起点 node 的所有子节点，用 regulator-compatible 属性（优先）或节点名跟 desc->of_match 比。
  • 命中就解析，并把该子节点回填给 regulator_register() 存进 rdev->dev.of_node。

两种方法的取舍：方法一直观但重复代码多，方法二简洁但要求 author 反推 DTS 结构和 desc 的配合关系。素材对这点的结论是「按实际情况灵活用」，落到工程上我给个更硬的建议——单路器件用方法一，PMIC 用方法二，理由只有一条：PMIC 的节点层级（regulators { dcdc1 {}; dcdc2 {}; }）本来就该由 regulators_node 描述。

regulator-compatible 这个属性是历史遗留的过渡产物：早期希望它替代 compatible 来做 regulator 级匹配（因为一个 PMIC node 下十几个 regulator 共用一个 compatible 显然不行），后来 4.x 的 of_parse_cb 方案出现后它就不推荐了。新写驱动直接让 of_match 等于子节点名即可。

十四、regulator-always-on 与 boot-on #

两个常被混用的属性，语义差得很远。

属性 constraints 字段 语义 核心动作 谁还能关它
regulator-always-on always_on 只要系统在运行，这路就不能关 regulator_disable() 直接返回 -EPERM 没人（除非 force_disable）
regulator-boot-on boot_on bootloader/固件已经打开了它，内核接手时视作已开 注册时 _regulator_is_enabled() 为真，于是 use_count 记 1 consumer 正常 disable 就能关
两者都不写 — 默认关 注册后 use_count = 0 一样只有 consumer 能动

always_on 的实现要点：它在 set_machine_constraints() 里被转成「注册阶段就 enable 一次」加上「后续 disable 请求一律拒绝」。所以一个 always_on 的 regulator 在 sysfs 里看到 num_users 是 1，但没有任何 consumer 对应——这个 1 是框架自己占的。

boot_on 更微妙：它不是「要求内核打开」，而是「承认它已经开着」。如果硬件上其实是关的，boot_on 什么也不做，也不会报错。

两者一起写（Tegra Dalmore 的 vdd-sys-5v0 就是这么写的）的意思是：这路电源 bootloader 开了，内核要维持，而且谁都不许关。

三个相关属性：

属性 作用
regulator-apply-at-boot（内部 apply_uV） min_uV == max_uV 时，注册阶段就把电压写下去；不给就只记请求不写硬件
regulator-ramp-delay（ramp_delay） 见第十章
regulator-off-on-delay（desc->off_on_delay） 关断后重开的最小间隔，防「电容没放完就重上电」导致浪涌

apply_uV 在 3.x 的 constraints 里叫 apply_uV 位域，DTS 侧的属性名各版本有变（素材没给），移植时按你内核的 Documentation/devicetree/bindings/regulator/regulator.txt 对齐，我不猜。

一个实战判断：always_on 是安全阀，不是省事符。见过不少板子为了不让某个模块掉电，把它整条电源链全标 always_on，结果整机待机功耗从 3mA 涨到 40mA。正确的做法是让 consumer 用引用计数管住它，而不是让框架永不关断。

十五、PWM 要解决什么：占空比与周期 #

PWM 是 Pulse Width Modulation，脉宽调制：用数字输出（只有高、低两态）去等效一个模拟电平。原理是面积等效——一个周期 T 内高电平持续 duty，那么负载上看到的平均电压就是 V * duty / T。风扇、背光、振动马达、蜂鸣器这类「惯性」负载会把方波平均掉，于是数字引脚就能调出连续的效果。

Linux PWM framework 的定位和 I2C/SPI 那类「总线框架」不同，它更像 CCF：对上给 consumer 一套操作脉冲参数的 API，对下给 controller 驱动一套回调，中间由 core 管状态机和资源分配。

consumer 只关心四个参数：

参数 硬件意义 说错会怎样
频率（= 1/周期） 决定了等效波形的平滑度 落进 20Hz~16KHz 人耳区间，电感/陶瓷电容会啸叫
占空比 一个周期内高低电平比例 直接决定平均电压，也就是亮度/转速
极性 高占空比对应输出高还是低 反了会出现「设 0% 最亮」的怪现象
开关 是否输出 关断期间引脚电平由 driver 决定，未必是 0

人脸感知区间那条不是玩笑：背光 PWM 频率放在 200Hz，笔记本合盖静音时能听见高频噪声；调到 20KHz 以上，或者干脆用 DC 调光，问题就没了。这也是 pwm-backlight 的 DTS 里周期一律给到音频段以上的原因。

3.x 的 consumer API 一共四个函数：

c
/* include/linux/pwm.h */
int pwm_config(struct pwm_device *pwm, int duty_ns, int period_ns);
int pwm_enable(struct pwm_device *pwm);
void pwm_disable(struct pwm_device *pwm);
int pwm_set_polarity(struct pwm_device *pwm, enum pwm_polarity polarity);
  • pwm_config()：同时给周期和占空比，单位 ns。频率不是直接给的，是 1e9 / period_ns。
  • pwm_enable() / pwm_disable()：开关输出。注意 pwm_disable() 返回 void——它没法失败，所以关断失败也不会告诉你。
  • pwm_set_polarity()：改极性，取值 PWM_POLARITY_NORMAL 或 PWM_POLARITY_INVERSED。

拿句柄的接口：

c
struct pwm_device *pwm_get(struct device *dev, const char *con_id);
struct pwm_device *of_pwm_get(struct device_node *np, const char *con_id);
void pwm_put(struct pwm_device *pwm);

struct pwm_device *devm_pwm_get(struct device *dev, const char *con_id);
struct pwm_device *devm_of_pwm_get(struct device *dev, struct device_node *np,
                                   const char *con_id);
void devm_pwm_put(struct device *dev, struct pwm_device *pwm);

老的 pwm_request(int pwm_id, const char *label) / pwm_free() 走的是全局编号 + radix tree 那一套，3.x 之后就在退场，新代码不要用。素材明写「本文只介绍基于 DTS 的新接口」，这也是本文的立场。

十六、struct pwm_device 与 pwm_chip #

pwm_chip 抽象一个 PWM 控制器。一颗 SoC 一般有 4~8 路 PWM 输出，它们的寄存器布局和操作方法一样，所以 framework 把它们归成一个 chip，chip 下的每一路是一个 pwm_device。

c
/* include/linux/pwm.h */
/**
 * struct pwm_chip - abstract a PWM controller
 * @dev: device providing the PWMs
 * @list: list node for internal use
 * @ops: callbacks for this PWM controller
 * @base: number of first PWM controlled by this chip
 * @npwm: number of PWMs controlled by this chip
 * @pwms: array of PWM devices allocated by the framework
 * @can_sleep: must be true if the .config(), .enable() or .disable()
 *             operations may sleep
 */
struct pwm_chip {
        struct device           *dev;
        struct list_head        list;
        const struct pwm_ops    *ops;
        int                     base;
        unsigned int            npwm;

        struct pwm_device       *pwms;

        struct pwm_device *     (*of_xlate)(struct pwm_chip *pc,
                                            const struct of_phandle_args *args);
        unsigned int            of_pwm_n_cells;
        bool                    can_sleep;
};
字段 必填 说明
dev 是 一般取 &pdev->dev
ops 是 回调表，见下一章
npwm 是 该 chip 支持的通道数，core 按它 kcalloc 出 pwms 数组
pwms 否 framework 分配，driver 不要碰
base 否 老 pwm_request() 用的全局起始编号，新接口下忽略
of_pwm_n_cells 用 DTS 就要 2 或 3，见第二十章
of_xlate 用 DTS 就要 解析 pwms = <&pwm ...> 里的参数
can_sleep 视实现 .config()/.enable()/.disable() 里会睡（如走 I2C 扩展芯片）就置 1
list 否 core 内部链表

can_sleep 不是一个锦上添花的字段，它决定 core 在持锁状态下能不能调你的回调。设错了（该置 1 却没置），在 spin_lock 里睡了，直接 BUG: scheduling while atomic。

pwm_device 是句柄，consumer 拿到的就是这个：

c
struct pwm_device {
        const char              *label;
        unsigned long           flags;
        unsigned int            hwpwm;
        unsigned int            pwm;
        struct pwm_chip         *chip;
        void                    *chip_data;

        unsigned int            period;         /* in nanoseconds */
        unsigned int            duty_cycle;     /* in nanoseconds */
        enum pwm_polarity       polarity;
};

pwm_device 里 provider 只看两个：hwpwm（通道在 chip 内的序号，寄存器寻址全靠它）和 chip（反指 chip，拿回自己上下文）；chip_data 是每通道私有数据。period/duty_cycle/polarity 是给 consumer 看的当前配置，pwm/label/flags 是老接口与 framework 内部遗留。3.x 的 pwm_device 里没有「使能」字段，开关状态记在 core 的计数里，4.x 才合进 pwm_state。

pwm_device 里没有「使能」字段这一点很容易看漏：3.x 的 struct pwm_device 记的是参数，开关状态记在 core 的 pwm_enable 计数里。4.x 把它们合进了新的 struct pwm_state，见下一章的版本对照。

注册 chip：

c
int pwmchip_add(struct pwm_chip *chip);
int pwmchip_remove(struct pwm_chip *chip);

pwmchip_add() 会做三件事：给 pwms 数组分配 npwm 个 pwm_device、把每个 pwm_device.kind 初始化为 PWM_CHIP、把 chip 挂进全局 pwm_chips 链表并按需建 sysfs（/sys/class/pwm/pwmchipN/）。driver 之后不用再操心。

十七、pwm_config 与 pwm_enable #

struct pwm_ops 是 provider 要实现的回调：

c
struct pwm_ops {
        int     (*request)(struct pwm_chip *chip, struct pwm_device *pwm);
        void    (*free)(struct pwm_chip *chip, struct pwm_device *pwm);
        int     (*config)(struct pwm_chip *chip,
                          struct pwm_device *pwm, int duty_ns, int period_ns);
        int     (*set_polarity)(struct pwm_chip *chip,
                          struct pwm_device *pwm, enum pwm_polarity polarity);
        int     (*enable)(struct pwm_chip *chip, struct pwm_device *pwm);
        void    (*disable)(struct pwm_chip *chip, struct pwm_device *pwm);
#ifdef CONFIG_DEBUG_FS
        void    (*dbg_show)(struct pwm_chip *chip, struct seq_file *s);
#endif
        struct module *owner;
};
回调 必要性 调用时机 要点
config 必须 pwm_config() 拿 duty_ns/period_ns 换算成 ticks 写寄存器
enable 必须 pwm_enable() 启动输出，一般还要顺手使能时钟/分频器
disable 必须 pwm_disable() 停输出，返回值被框架忽略
set_polarity 可选 pwm_set_polarity() 只有硬件支持反相才有意义
request / free 淘汰 老接口时代 新版不调
dbg_show 可选 CONFIG_DEBUG_FS 下读 /sys/kernel/debug/pwm 打印寄存器/寄存器值
owner 要有 模块引用计数 THIS_MODULE

pwm_config() 到 ops->config() 的链路，在 3.x 里是直连再加一层参数检查：

text
consumer: pwm_config(pwm, duty_ns, period_ns)
  └─ core: pwm_config()
       ├─ 参数检查：duty_ns > period_ns 直接 -EINVAL
       ├─ chip->ops->config(chip, pwm, duty_ns, period_ns)
       └─ 成功后缓存 pwm->period / pwm->duty_cycle

ops->config() 内部要做的换算：

c
static int foo_pwm_config(struct pwm_chip *chip, struct pwm_device *pwm,
                          int duty_ns, int period_ns)
{
        struct foo_pwm_chip *pc = to_foo_pwm_chip(chip);
        unsigned long long c;
        unsigned long period_cycles, duty_cycles, prescale;

        /* 定时器输入时钟 c，先求总周期 ticks */
        c = clk_get_rate(pc->clk);
        c = c * period_ns;
        do_div(c, 1000000000);
        period_cycles = c;

        /* 超出 16 位计数器就先分频 */
        prescale = period_cycles / 0x10000 + 1;
        period_cycles /= prescale;
        duty_cycles = (unsigned long long)period_cycles * duty_ns;
        do_div(duty_cycles, period_ns);

        /* 写寄存器：分频、周期、占空比、反相位 */
        writel(prescale, pc->base + FOO_PRESCALE);
        writel(period_cycles, pc->base + FOO_PERIOD);
        writel(duty_cycles, pc->base + FOO_DUTY);

        return 0;
}

这段是示意代码，不是任何具体芯片的原样：它想表达的是三个必须处理的问题——纳秒到 ticks 的定点换算、分频导致的分辨率损失、占空比必须按分频后的周期重算（顺序写反，亮度会跳）。

pwm_disable() 返回 void 这件事在工程上有个后果：关断失败静默。如果硬件关断需要等一个状态位，driver 只能自己做完（或在 ops->disable 里忽略返回值），上层拿不到任何错误。要严格的「关断确认」，得看你的内核里 core 是否已经改成 int pwm_disable()（4.x 后期改的，具体版本按你的树确认）。

十八、PWM 的极性、周期与占空比 #

极性是 PWM 里最容易被绕进去的一个。

c
enum pwm_polarity {
        PWM_POLARITY_NORMAL,    /* 高电平为真：duty 期间为高 */
        PWM_POLARITY_INVERSED,  /* 反相：duty 期间为低 */
};

PWM_POLARITY_NORMAL 下，duty_cycle 表示「一个周期里输出高电平的时长」；PWM_POLARITY_INVERSED 下，同一个 duty_cycle 表示「输出低电平的时长」。所以 100% 占空比：正常极性输出拉满，反相极性输出为 0。这就是为什么第二十章那个 DTS 里 PWMS 的第三个 cell 传 PWM_POLARITY_INVERTED 时，背光的行为会整个反过来。

关于「改极性」的时序约束，4.x 的 pwm.h 注释里说得很死：极性只能在 PWM 关闭时改。3.x 的 core 没有强制这一条，driver 自己要把 ops->set_polarity 写成「若当前使能则返回 -EBUSY」或者先临时关断。4.x 的 pwm_apply_state() 也是这么处理的。

周期和占空比的取值约束：

约束 谁保证 违反的后果
duty_ns <= period_ns core 的 pwm_config() 参数检查 直接 -EINVAL
period_ns 不为 0 core 除零
period_ns 落在硬件分频能力内 driver 超出 16 位计数器必须加分频，否则静默截断
占空比分辨率 硬件 亮度只能呈离散台阶，低亮度区尤其明显
duty_ns == 0 时算「常低」还是「关断」 硬件实现 两者语义不同：常低仍在输出波形，关断是彻底停

最后一条在背光调光里是个真实 bug 源：duty = 0 时用 pwm_config(pwm, 0, period) 会让输出恒定在低电平（如果极性正常），看起来是「全暗」，但芯片还在跑、时钟没关、功耗没省。正确做法是低于某个阈值时直接 pwm_disable()。

4.x 的变化（对照 5.4 的 include/linux/pwm.h 核过）：

c
struct pwm_state {                  /* 4.19 之后的状态聚合体，5.4 已确认存在 */
        unsigned int period;
        unsigned int duty_cycle;
        enum pwm_polarity polarity;
        bool enabled;
};

struct pwm_device {
        ...
        struct pwm_args args;   /* 板级参考配置：period + polarity */
        struct pwm_state state; /* 当前实际状态 */
};

int pwm_apply_state(struct pwm_device *pwm, const struct pwm_state *state);
int pwm_adjust_config(struct pwm_device *pwm);

pwm_config() / pwm_enable() / pwm_disable() / pwm_set_polarity() 在 5.4 里退化成了 static inline 包装：读 pwm->state、改一个字段、再调 pwm_apply_state()。这带来一个语义差异——老接口是「分别设参数」，新接口是「一次性提交整个状态」，后者才能保证「周期、占空比、极性、开关」四个值同时生效，避免中间态。pwm_ops 也换成了 .apply() + 可选的 .get_state()，.config()/.enable()/.disable() 被标注为「Only used by legacy drivers」。

pwm_apply_state() 具体是在哪个版本引入的、以及 pwm_config() 从「真函数」变成 inline 包装的确切版本，我没查到权威的 commit 号，标未验证。查证方法：翻你那份内核的 include/linux/pwm.h 看有没有 struct pwm_state，有就是新接口时代。

十九、PWM consumer 的用法 #

以 pwm-backlight 为例，consumer 侧的标准四步：

1）查 provider 的 binding，在 DTS 里写 pwms 和 pwm-names。

dts
/* arch/arm/boot/dts/imx23-evk.dts */
backlight {
        compatible = "pwm-backlight";
        pwms = <&pwm 2 5000000>;
        brightness-levels = <0 4 8 16 32 64 128 255>;
        default-brightness-level = <6>;
};

2）probe 里用 devm_pwm_get() 拿句柄。

c
bl->pwm = devm_pwm_get(&pdev->dev, "backlight");
if (IS_ERR(bl->pwm))
        return PTR_ERR(bl->pwm);

3）devm_pwm_get() 成功后 PWM 已经有初始周期和极性了（来自 DTS 的第 3、4 个 cell），接着按需要改参数：

c
static int bl_set_brightness(struct backlight_device *bd)
{
        struct my_bl *bl = bl_get_data(bd);
        int duty = bd->props.brightness * bl->period_ns / bl->max_brightness;

        return pwm_config(bl->pwm, duty, bl->period_ns);
}

4）按需 pwm_enable() / pwm_disable()。

c
if (bd->props.power != FB_BLANK_UNBLANK ||
    bd->props.fb_blank != FB_BLANK_UNBLANK ||
    bd->props.state & BL_CORE_SUSPENDED)
        pwm_disable(bl->pwm);
else
        pwm_enable(bl->pwm);

consumer 侧的三条经验：

  • 不要假设 pwm_config() 一定成功。分频后达不到指定周期时，有的 driver 会返回 0 且实际周期有偏差。要精确，就 pwm_config() 之后回读 pwm->period（新内核用 pwm_get_state()）。
  • pwm_put() 不会停输出。句柄还回去了，引脚照样在振。要关就先 pwm_disable()。devm_pwm_put() 同理。
  • 极性从 DTS 来，别在代码里硬写。板子上的背光驱动电路是不是反相，是硬件决定的，写死在驱动里换个板子就错。

二十、PWM 的设备树绑定 #

provider 侧的节点：

dts
/* arch/arm/boot/dts/imx23.dtsi */
pwm: pwm@80064000 {
        compatible = "fsl,imx23-pwm";
        reg = <0x80064000 0x2000>;
        clocks = <&clks 30>;
        #pwm-cells = <2>;
        fsl,pwm-number = <5>;
        status = "disabled";
};

/* arch/arm/boot/dts/imx23-evk.dts */
&pwm {
        pinctrl-names = "default";
        pinctrl-0 = <&pwm2_pins_a>;
        status = "okay";
};

注意 .dtsi 里 status = "disabled"，具体板子用 &pwm { status = "okay"; } 打开。这是 ARM DTS 的标准做法，PWM 节点尤其该这么写——没接外设的 PWM 通道开着就是白耗电。

#pwm-cells 决定 consumer 的 pwms 里有几个数：

dts
/* #pwm-cells = <3>，带极性 */
bl: backlight {
        pwms = <&pwm 0 5000000 PWM_POLARITY_INVERTED>;
        pwm-names = "backlight";
};

/* #pwm-cells = <2>，不带极性 */
pwms = <&pwm 2 5000000>;

四个 cell 的含义（以 3 为例）：

位置 内容 谁解析
第 1 个 &pwm，phandle 引用 provider 节点 OF core
第 2 个 channel 序号（hwpwm） of_xlate
第 3 个 默认周期，单位 ns of_xlate
第 4 个（可选） 极性 flag of_xlate

of_xlate 是两个可选实现的指针：

of_pwm_n_cells 推荐 of_xlate 行为
2 of_pwm_simple_xlate 只取 channel 和 period
3 of_pwm_xlate_with_flags 额外取第 3 个 cell 当极性

core 还有一层校验：of_pwm_xlate_with_flags() 会检查 args->args_count > 2，只有 3 个 cell 时才读极性。写自定义 of_xlate 时把 args_count 判断漏掉，#pwm-cells = <2> 的板子会读到栈上的垃圾。

con_id 匹配规则：devm_pwm_get(dev, NULL) 取 pwms 里第一个；devm_pwm_get(dev, "backlight") 按 pwm-names 找同名项，序号对到 pwms 的同一位置。

provider 写驱动的步骤，压成清单：

  1. DTS 节点：compatible、reg、clocks、#pwm-cells，板级 dts 里 status = "okay" 加 pinctrl。
  2. 定义 struct foo_pwm_chip { struct pwm_chip chip; void __iomem *base; struct clk *clk; };。
  3. probe 里 platform_get_resource + devm_ioremap_resource + devm_clk_get + clk_prepare_enable。
  4. 填 chip.dev / chip.ops / chip.npwm / chip.base = -1；要极性就把 of_pwm_n_cells = 3、of_xlate = of_pwm_xlate_with_flags。
  5. pwmchip_add(&pc->chip)，失败就回滚时钟。
  6. ops 里每个回调都通过 pwm->hwpwm 定位寄存器。
  7. remove 里 pwmchip_remove() + clk_disable_unprepare()。

base 在 5.4 里仍留着但已不参与新接口逻辑；早期设 base = -1 表示「动态分配」，现在这行可以删。

二十一、PM domain 要解决什么：一组设备共享电源开关 #

复杂 SoC 会把供电切成若干独立的 block，叫电源域（power domain）。好处有三条：

  1. 隔离。模拟和数字分开供电，互不干扰。
  2. 电压不同。CPU core 1.2V 就能跑，IO 要 3.3V。小电压省电但信号裕量差，大电压结实话费电。
  3. 选择性关断。系统跑着的时候大部分模块是闲置的，把它们的供电切掉，耗电直接归零。

但电源域不是越多越好——每个域在 PMU 里都要一套模拟开关，占面积、占成本。所以真实系统就切那么几刀：CPU core、GPU、NAND、DDR、USB、Display、Codec。

这引出了 PM domain 框架要解决的核心问题：多个模块共用一个域。

text
              ┌───────── power domain: PD_VPU ─────────┐
              │                                        │
   ┌──────────▼─────────┐            ┌─────────────────▼──┐
   │ vpu_core0 (device) │            │ vpu_core1 (device) │
   └────────────────────┘            └────────────────────┘

   规则：任一 device 在工作 → 域必须开
        全部 device 停止   → 域才能关

规则只有两条，但实现它要处理：谁在统计「还有几个设备在工作」、子系统 suspend 和 runtime PM 两套流程怎么共存、子域和父域的级联顺序、关断前要不要先问 governor（关了这个域能省多少电、唤醒要多久）。这些都在 drivers/base/power/domain.c 里。

素材明确写了内核版本是 3.18-rc4，并解释了为什么要点出版本：PM domain 里好用的 patch 大多只在最新版本才能看到。这一点在 4.x/5.x 里被验证得很彻底——后面几章会逐处对比。

关键的一层挂接点是 struct device 里的一个指针：

c
struct device {
        ...
        struct dev_pm_domain    *pm_domain;
        ...
};

struct dev_pm_domain 本身很薄，就是一组 struct dev_pm_ops：

c
struct dev_pm_domain {
        struct dev_pm_ops ops;
        void (*detach)(struct device *dev, bool power_off);
        int (*activate)(struct device *dev);
        void (*sync)(struct device *dev);
        void (*dismiss)(struct device *dev);
};

（detach/sync 这几个函数指针在 3.18 的 domain.c 里已经被用到，genpd_dev_pm_attach() 会写 dev->pm_domain->detach = genpd_dev_pm_detach;。素材给的 struct dev_pm_domain 定义为「只有 dev_pm_ops 一个成员」，那是更早的版本，此处按 3.18 补全。）

它的意义：PM core 在切换设备电源状态时，会按 device_type > class > bus > driver 的顺序选 dev_pm_ops，而优先级最高的恰恰是 dev->pm_domain->ops。所以把 pm_domain 指到一个 genpd 的 domain 成员上，这个设备的所有电源状态切换就自动绕道 genpd 了。设备自己的 driver 一行代码都不用改。

二十三、genpd 的开关流程 #

初始化。provider 为每个域定义一个 struct generic_pm_domain 变量，填好 name 和 power_on/power_off，然后调 pm_genpd_init()：

c
/**
 * pm_genpd_init - Initialize a generic I/O PM domain object.
 * @genpd: PM domain object to initialize.
 * @gov: PM domain governor to associate with the domain (may be NULL).
 * @is_off: Initial value of the domain's power_is_off field.
 */
void pm_genpd_init(struct generic_pm_domain *genpd,
                   struct dev_power_governor *gov, bool is_off)
{
    if (IS_ERR_OR_NULL(genpd))
        return;

    INIT_LIST_HEAD(&genpd->master_links);
    INIT_LIST_HEAD(&genpd->slave_links);
    INIT_LIST_HEAD(&genpd->dev_list);
    mutex_init(&genpd->lock);
    genpd->gov = gov;
    INIT_WORK(&genpd->power_off_work, genpd_power_off_work_fn);
    genpd->in_progress = 0;
    atomic_set(&genpd->sd_count, 0);
    genpd->status = is_off ? GPD_STATE_POWER_OFF : GPD_STATE_ACTIVE;
    init_waitqueue_head(&genpd->status_wait_queue);
    genpd->poweroff_task = NULL;
    genpd->resume_count = 0;
    genpd->device_count = 0;
    genpd->max_off_time_ns = -1;
    genpd->max_off_time_changed = true;

    /* 一整套 dev_pm_ops：runtime PM、系统 suspend、hibernate、poweroff 全覆盖 */
    genpd->domain.ops.runtime_suspend = pm_genpd_runtime_suspend;
    genpd->domain.ops.runtime_resume = pm_genpd_runtime_resume;
    genpd->domain.ops.prepare = pm_genpd_prepare;
    genpd->domain.ops.suspend = pm_genpd_suspend;
    genpd->domain.ops.suspend_late = pm_genpd_suspend_late;
    genpd->domain.ops.suspend_noirq = pm_genpd_suspend_noirq;
    genpd->domain.ops.resume_noirq = pm_genpd_resume_noirq;
    genpd->domain.ops.resume_early = pm_genpd_resume_early;
    genpd->domain.ops.resume = pm_genpd_resume;
    genpd->domain.ops.freeze = pm_genpd_freeze;
    genpd->domain.ops.freeze_late = pm_genpd_freeze_late;
    genpd->domain.ops.freeze_noirq = pm_genpd_freeze_noirq;
    genpd->domain.ops.thaw_noirq = pm_genpd_thaw_noirq;
    genpd->domain.ops.thaw_early = pm_genpd_thaw_early;
    genpd->domain.ops.thaw = pm_genpd_thaw;
    genpd->domain.ops.poweroff = pm_genpd_suspend;
    genpd->domain.ops.poweroff_late = pm_genpd_suspend_late;
    genpd->domain.ops.poweroff_noirq = pm_genpd_suspend_noirq;
    genpd->domain.ops.restore_noirq = pm_genpd_restore_noirq;
    genpd->domain.ops.restore_early = pm_genpd_resume_early;
    genpd->domain.ops.restore = pm_genpd_resume;
    genpd->domain.ops.complete = pm_genpd_complete;

    /* dev_ops 的默认实现，provider 可覆盖 */
    genpd->dev_ops.save_state = pm_genpd_default_save_state;
    genpd->dev_ops.restore_state = pm_genpd_default_restore_state;

    mutex_lock(&gpd_list_lock);
    list_add(&genpd->gpd_list_node, &gpd_list);
    mutex_unlock(&gpd_list_lock);
}

读这个函数只需要抓两点：

  1. genpd->domain.ops 那一大串全是框架提供的，不是 provider 写的。provider 只写 power_on/power_off。这串赋值的含义是「把这个域包装成一个覆盖全部电源状态的回调集合」——runtime PM 走 pm_genpd_runtime_suspend/resume，系统 suspend 走 suspend/prepare/noirq 全套，hibernate 走 freeze/thaw，关机走 poweroff/restore。
  2. is_off 决定初始状态。provider 必须告诉框架「我这域现在是开的还是关的」，说错了，第一次 genpd_poweron() 会因为 status == GPD_STATE_ACTIVE 直接返回、跳过一次真正的上电。

4.19 的 pm_genpd_init() 保留同样的签名，但做了几件事：genpd->accounting_time = ktime_get()（debugfs 统计用）、genpd->provider = NULL; genpd->has_provider = false;、device_initialize(&genpd->dev) 加 dev_set_name()（genpd 自己变成一个 device 了），以及 if (genpd_is_always_on(genpd) && !genpd_status_on(genpd)) return -EINVAL;（always-on 域不允许以 off 状态初始化），最后返回值从 void 变成 int。5.10 又加了 genpd_set_default_power_state()（没声明 idle state 时补一个）和 genpd_lock_init()（按 GENPD_FLAG_IRQ_SAFE 选 spinlock 还是 mutex）。

上电流程。3.18 里叫 genpd_poweron()，沿着 slave_links 往上找到所有 master，逐个拉起来：

c
static int __genpd_poweron(struct generic_pm_domain *genpd)
{
        struct gpd_link *link;
        int ret = 0;

        if (genpd->status == GPD_STATE_ACTIVE
            || (genpd->prepared_count > 0 && genpd->suspend_power_off))
                return 0;

        /* 先把所有 master 拉起来 */
        list_for_each_entry(link, &genpd->slave_links, slave_node) {
                genpd_sd_counter_inc(link->master);

                ret = genpd_poweron(link->master);
                if (ret) {
                        genpd_sd_counter_dec(link->master);
                        goto err;
                }
        }

        ret = genpd_power_on(genpd, true);
        if (ret)
                goto err;

        genpd->status = GPD_STATE_ACTIVE;
        return 0;

 err:
        /* 回滚：把已经拉起来的 master 再放回去 */
        list_for_each_entry_continue_reverse(link, &genpd->slave_links,
                                             slave_node) {
                genpd_sd_counter_dec(link->master);
                genpd_queue_power_off_work(link->master);
        }

        return ret;
}

genpd_power_on() 是薄薄的一层包装，负责计时：

c
static int genpd_power_on(struct generic_pm_domain *genpd, bool timed)
{
        ktime_t time_start;
        s64 elapsed_ns;
        int ret;

        if (!genpd->power_on)
                return 0;

        if (!timed)
                return genpd->power_on(genpd);

        time_start = ktime_get();
        ret = genpd->power_on(genpd);
        if (ret)
                return ret;

        elapsed_ns = ktime_to_ns(ktime_sub(ktime_get(), time_start));
        if (elapsed_ns <= genpd->power_on_latency_ns)
                return ret;

        genpd->power_on_latency_ns = elapsed_ns;
        genpd->max_off_time_changed = true;
        pr_debug("%s: Power-%s latency exceeded, new value %lld ns\n",
                 genpd->name, "on", elapsed_ns);

        return ret;
}

这段代码定义了一个持续自校准的行为：provider 给的 power_on_latency_ns 只是初值，实测值更大就往上调，并顺手置 max_off_time_changed 让 governor 重算。它不会往下调——宁可高估延迟，是多关一次域还是多等一会儿的选择题，框架选了后者。

关断流程。3.18 的 genpd_poweroff() 是一串「一票否决」：

c
static int genpd_poweroff(struct generic_pm_domain *genpd, bool is_async)
{
        struct pm_domain_data *pdd;
        struct gpd_link *link;
        unsigned int not_suspended = 0;

        /* 否决1：已关 / 系统 suspend 中；否决2：还有子域亮着 */
        if (genpd->status == GPD_STATE_POWER_OFF || genpd->prepared_count > 0)
                return 0;
        if (atomic_read(&genpd->sd_count) > 0)
                return -EBUSY;

        list_for_each_entry(pdd, &genpd->dev_list, list_node) {
                enum pm_qos_flags_status stat;

                /* 否决3：声明 NO_POWER_OFF / REMOTE_WAKEUP */
                stat = dev_pm_qos_flags(pdd->dev,
                        PM_QOS_FLAG_NO_POWER_OFF | PM_QOS_FLAG_REMOTE_WAKEUP);
                if (stat > PM_QOS_FLAGS_NONE)
                        return -EBUSY;
                /* 否决4：仍有设备未 suspend（irq_safe 一律算未 suspend） */
                if (!pm_runtime_suspended(pdd->dev) || pdd->dev->power.irq_safe)
                        not_suspended++;
        }
        if (not_suspended > 1 || (not_suspended == 1 && is_async))
                return -EBUSY;
        /* 否决5：governor 判断「关它不划算」 */
        if (genpd->gov && genpd->gov->power_down_ok) {
                if (!genpd->gov->power_down_ok(&genpd->domain))
                        return -EAGAIN;
        }

        if (genpd->power_off) {
                int ret;

                if (atomic_read(&genpd->sd_count) > 0)
                        return -EBUSY;
                ret = genpd_power_off(genpd, true);
                if (ret)
                        return ret;     /* provider 可拒绝 */
        }
        genpd->status = GPD_STATE_POWER_OFF;

        /* 传播：通知所有 master，看它们能否也关 */
        list_for_each_entry(link, &genpd->slave_links, slave_node) {
                genpd_sd_counter_dec(link->master);
                genpd_queue_power_off_work(link->master);
        }
        return 0;
}

五个否决点的语义要点：

否决 返回 什么时候会命中
状态/系统 suspend 中 0（静默） 重复关断、或正在走系统级 suspend
子域亮着（sd_count > 0） -EBUSY 有子域在用
NO_POWER_OFF / REMOTE_WAKEUP -EBUSY 设备是唤醒源，关了就叫不醒系统
有设备没 suspend -EBUSY 还有设备在跑
governor 拒绝 -EAGAIN 「关了省的电抵不上唤醒开销」

not_suspended 那个 > 1 || (== 1 && is_async) 的判断有讲究：从 ->runtime_suspend 回调里同步调过来时，当前这个设备的 runtime 状态还停在 RPM_SUSPENDING，不算 RPM_SUSPENDED，所以允许有 1 个「没 suspend」。从 work 里异步调过来就没这个豁免。

power_off 返回非 0 是 provider 的最后一道门：硬件侧还有未完成的 DMA、DDR 还在自刷新、PLL 还没锁……都可以在这里拒绝，框架会老实退出、维持 ACTIVE。

4.x 起 genpd_power_on() / genpd_power_off() 变成真的递归函数并带 depth 参数：

c
/* linux 5.10 —— 名字和参数都变了 */
static int genpd_power_on(struct generic_pm_domain *genpd, unsigned int depth);
static int genpd_power_off(struct generic_pm_domain *genpd, bool one_dev_on,
                           unsigned int depth);

one_dev_on 就是 3.18 is_async 的反面表达（4.x 反了一下语义，从 4.19 起固定叫 one_dev_on）。同时 genpd_power_off() 里的 genpd_lock_nested(link->parent, depth + 1) 换成按 lock_ops 走的 genpd_lock_nested()，GENPD_FLAG_IRQ_SAFE 的域用 spinlock、其余用 mutex——这就是 4.x「genpd 大量重构」里最实在的一块：把 genpd->lock 的全部用法抽象成 genpd_lock() / genpd_lock_nested() / genpd_unlock() 三个宏。

二十四、PM domain 与 Runtime PM 的配合 #

这条协作链是整个框架能「零成本」用起来的根本，从 platform_drv_probe() 开始：

c
static int platform_drv_probe(struct device *_dev)
{
        struct platform_driver *drv = to_platform_driver(_dev->driver);
        struct platform_device *dev = to_platform_device(_dev);
        int ret;

        ret = of_clk_set_defaults(_dev->of_node, false);
        if (ret < 0)
                return ret;

        ret = dev_pm_domain_attach(_dev, true);
        if (ret != -EPROBE_DEFER) {
                ret = drv->probe(dev);
                if (ret)
                        dev_pm_domain_detach(_dev, true);
        }

        if (drv->prevent_deferred_probe && ret == -EPROBE_DEFER) {
                dev_warn(_dev, "probe deferral not supported\n");
                ret = -ENXIO;
        }

        return ret;
}

注意 of_clk_set_defaults() 排在 dev_pm_domain_attach() 前面——先摆平时钟，再挂电源域。这个顺序不能反：attach 成功之后 PM core 就会去动电源，而那时候时钟还没配好。

dev_pm_domain_attach() 在 drivers/base/power/common.c：

                ret = genpd_dev_pm_attach(dev);

ACPI 走不通才落到 devicetree 的 genpd。3.18 的 genpd_dev_pm_attach()：

c
int genpd_dev_pm_attach(struct device *dev)
{
    struct of_phandle_args pd_args;
    struct generic_pm_domain *pd;
    int ret;

    if (!dev->of_node)
        return -ENODEV;
    if (dev->pm_domain)
        return -EEXIST;

    /* index 写死 0：3.18 一个设备只能挂一个域 */
    ret = of_parse_phandle_with_args(dev->of_node, "power-domains",
                    "#power-domain-cells", 0, &pd_args);
    if (ret < 0) {
        if (ret != -ENOENT)
            return ret;
        /* 兼容三星老绑定 */
        pd_args.args_count = 0;
        pd_args.np = of_parse_phandle(dev->of_node,
                        "samsung,power-domain", 0);
        if (!pd_args.np)
            return -ENOENT;
    }

    pd = of_genpd_get_from_provider(&pd_args);
    if (IS_ERR(pd)) {
        dev_dbg(dev, "%s() failed to find PM domain: %ld\n",
            __func__, PTR_ERR(pd));
        of_node_put(dev->of_node);
        return PTR_ERR(pd);
    }

    /* 域正在 prepare/remove 时返回 -EAGAIN，让一下再试 */
    while (1) {
        ret = pm_genpd_add_device(pd, dev);
        if (ret != -EAGAIN)
            break;
        cond_resched();
    }

    if (ret < 0) {
        dev_err(dev, "failed to add to PM domain %s: %d",
            pd->name, ret);
        of_node_put(dev->of_node);
        return ret;
    }

    dev->pm_domain->detach = genpd_dev_pm_detach;
    return 0;
}

四步走：解析 power-domains → 找 provider 并 xlate 出 genpd 指针 → pm_genpd_add_device() 把设备挂进 dev_list 并把 dev->pm_domain 指向 &genpd->domain → 注册 detach 回调。

of_genpd_get_from_provider() 遍历 of_genpd_providers 链表，按节点匹配后调 provider 提供的 xlate：

c
static struct generic_pm_domain *of_genpd_get_from_provider(
                                        struct of_phandle_args *genpdspec)
{
        struct generic_pm_domain *genpd = ERR_PTR(-ENOENT);
        struct of_genpd_provider *provider;

        mutex_lock(&of_genpd_mutex);

        list_for_each_entry(provider, &of_genpd_providers, link) {
                if (provider->node == genpdspec->np)
                        genpd = provider->xlate(genpdspec, provider->data);
                if (!IS_ERR(genpd))
                        break;
        }

        mutex_unlock(&of_genpd_mutex);

        return genpd;
}

xlate 的签名是 typedef struct generic_pm_domain *(*genpd_xlate_t)(struct of_phandle_args *args, void *data);。两个常用的现成实现：genpd_xlate_simple()（一个 node 对一个域，data 直接就是 genpd 指针）和 genpd_xlate_onecell()（一个 node 多个域，用一个 cell 当数组下标）。

attach 之后，开关就全交给 Runtime PM 了。驱动只需要：

c
/* 要用设备了 */
pm_runtime_get_sync(dev);     /* usage_count 0 -> 1，触发 runtime_resume，进而 genpd_power_on */

/* 用完了 */
pm_runtime_put(dev);          /* usage_count 1 -> 0，触发 runtime_suspend，进而 genpd_poweroff */

pm_genpd_runtime_resume() 干的事：先 genpd_power_on(genpd) 把域拉起来，再 genpd_start_dev()（调 provider 覆盖的 dev_ops.start）让设备本身开始工作，最后调 genpd_restore_dev() 恢复设备状态。pm_genpd_runtime_suspend() 反向：genpd_save_dev() 存状态 → genpd_stop_dev() 停设备 → genpd_poweroff() 尝试关域。中间的延迟都记在 struct gpd_timing_data 里（suspend_latency_ns / resume_latency_ns），超过历史值就更新并置 max_off_time_changed。

只要挂上了 genpd，子系统 suspend 那套也是自动的：pm_genpd_prepare()、pm_genpd_suspend_noirq()、pm_genpd_resume_noirq()、pm_genpd_complete() 都来自 genpd->domain.ops，in_progress、suspended_count、prepared_count 这些计数由 core 维护。系统 suspend 时 pm_genpd_sync_poweroff() 会选最深的 idle state（4.x 以后 genpd->state_idx = genpd->state_count - 1），而 runtime 关断默认选最浅的 state_idx = 0。

三处实战经验：

  1. pm_runtime_get_sync() 的返回值必须查。它返回负值时（-EACCES、-EINVAL、-EAGAIN）并不意味着「设备一定没上电」，它来自前一次异步操作的残留错误，但继续访问寄存器就会挂。
  2. 在 ->suspend 里再调 pm_runtime_get 会死锁。Runtime PM 的回调里禁止反向操作自己，要用 pm_runtime_get_noresume()。
  3. 只用 PM domain 不写 runtime PM，也是合法的。素材提到：在 probe 里 get 一次、remove 里 put 一次，效果就等于手动 power on/off。但代价是设备在拿到 handle 之后永不释放，省的功耗有限。真要省电，还是要接 OPP 和 runtime PM 的 autosuspend。

二十五、设备树里的 power-domains #

provider 侧（Documentation/devicetree/bindings/power/power_domain.txt 的格式）：

dts
powergate: power-domain@e012e000 {
        compatible = "xxx,xxx-pm-domains";
        reg = <0 0xe012e000 0 0x1000>;
        #power-domain-cells = <1>;
};

consumer 侧：

dts
power-domain-example@e028e000 {
        compatible = "xxx,xxx-dummy";
        reg = <0 0xe0280000 0 0x1000>;
        power-domains = <&powergate POWER_DOMAIN_USB>;
};

三个字段的职责：

字段 位置 含义 由谁解析
#power-domain-cells provider 每个引用带几个 cell。0 = 一节点一域，1 = 用下标选域 OF core 校验
power-domains consumer 引用列表，可写多个 of_parse_phandle_with_args()
samsung,power-domain consumer 三星老绑定，兼容用 兜底分支
power-domain-names consumer 多域时的名字（4.x 起 genpd_dev_pm_attach_by_name() 用） of_property_match_string()

POWER_DOMAIN_USB 这种宏一般定义在 include/dt-bindings/power/*.h 里，编号由 provider 驱动解释，框架不关心。

三个版本差异要注意：

  1. 3.18 一个设备只能挂一个域。genpd_dev_pm_attach() 只取 index 0 的引用，of_parse_phandle_with_args() 的第 4 个参数写死 0。写多个 power-domains 时后面的会被静默忽略。4.19 起 genpd_dev_pm_attach() 里加了 if (of_count_phandle_with_args(...) != 1) return 0; 明确「多域必须分开挂」，并配了 genpd_dev_pm_attach_by_id() / _by_name()，每个域创建一个虚拟 device 挂到 genpd bus 上。
  2. 没有域的板子不要写 power-domains。genpd_dev_pm_attach() 解析失败返回 -ENOENT，dev_pm_domain_attach() 把 -ENOENT 当「不需要」处理，probe 继续。但如果你写了引用而那个域还没注册，会走到 -EPROBE_DEFER 分支——注意 3.18 的实现里那个分支居然 return PTR_ERR(pd)（把 -ENOENT 原样返回），4.4 才改成 return -EPROBE_DEFER。同一份 DTS 在 3.18 和 4.4 上的 probe 行为不一样，这是我这次校对发现的实质差异，移植时要盯。
  3. 子域关系不在 consumer DTS 里。power-domains = <&genpd_a>; 描述的是「设备挂在 a 上」。域与域的父子关系由 provider 在自己的 DTS 里用 power-domains 引用另一个域节点表达，再由 of_genpd_add_subdomain() 建立 master_links/slave_links。同一套属性在两处语义不完全一样，读代码时容易混。

调试入口（CONFIG_PM_ADVANCED_DEBUG）：/sys/kernel/debug/pm_genpd/pm_genpd_summary 看全部域的 on/off、子域列表和每设备的 runtime 状态；pm_genpd/<域名>/ 下还有 status、subdomains、active_time、total_idle_time、devices。5.x 拆成每个域一个目录（current_state、idle_states、active_time、total_idle_time、devices、perf_state），pm_genpd_summary 保留，列名从 slaves 改 children。排查顺序永远是：先看域是不是 off，再看有没有设备的 runtime 卡在 active。

把三个框架串起来看一遍。假设板子上有一颗 codec，挂在 I2C 上，要供电、要时钟、要 PWM 驱动耳机功放的偏置、还要挂在音频子系统所在的电源域里。

dts
&i2c2 {
        codec: codec@1a {
                compatible = "vendor,xyz-codec";
                reg = <0x1a>;

                clocks = <&clks CLK_ID_AUDIO>;
                clock-names = "mclk";

                power-domains = <&powergate POWER_DOMAIN_AUDIO>;

驱动里发生的事，按时间排：

阶段 框架 调用 结论
probe 前 PM domain dev_pm_domain_attach() 挂上 PD_AUDIO，把 dev->pm_domain 指向 genpd
probe 前 PM domain genpd_power_on() 域（及其父域）上电，等待 power_on_latency_ns
probe 中 CCF devm_clk_get() + clk_prepare_enable() mclk 起来
probe 中 Regulator devm_regulator_bulk_get() 拿 3 个句柄，注意 VDDA/VDDD/VDDIO 与 .supply 名大小写对齐
probe 中 Regulator regulator_bulk_enable() 按数组顺序上电，每路等 enable_time
probe 中 Regulator regulator_set_voltage(vddd, 1200000, 1200000) 走协商链，落档、等 ramp_delay
probe 中 PWM devm_pwm_get(dev, "pa-bias") 拿到通道，周期已被 DTS 定为 1ms
probe 中 PWM pwm_config() + pwm_enable() 偏置电压输出
probe 后 「device 开始干活里」 pm_runtime_mark_last_busy() + pm_runtime_put_autosuspend() usage_count → 0
空闲超时 PM domain genpd_runtime_suspend() 域内所有设备都 suspend 后，genpd_poweroff() 关掉 PD_AUDIO

失败路径上的拆除顺序必须严格反过来：

c
static int xyz_codec_probe(struct i2c_client *i2c)
{
        struct xyz_codec *c;
        int ret;

        c = devm_kzalloc(&i2c->dev, sizeof(*c), GFP_KERNEL);
        if (!c)
                return -ENOMEM;
        c->mclk = devm_clk_get(&i2c->dev, "mclk");
        if (IS_ERR(c->mclk))
                return PTR_ERR(c->mclk);
        ret = devm_regulator_bulk_get(&i2c->dev, ARRAY_SIZE(c->supplies), c->supplies);
        if (ret)
                return ret;
        c->pa = devm_pwm_get(&i2c->dev, "pa-bias");
        if (IS_ERR(c->pa))
                return PTR_ERR(c->pa);

        /* 上电顺序：电源 -> 时钟 -> PWM；拆除必须反过来 */
        ret = regulator_bulk_enable(ARRAY_SIZE(c->supplies), c->supplies);
        if (ret)
                return ret;
        ret = clk_prepare_enable(c->mclk);
        if (ret)
                goto err_reg;
        ret = pwm_config(c->pa, 500000, 1000000);
        if (ret)
                goto err_clk;
        ret = pwm_enable(c->pa);
        if (ret)
                goto err_clk;
        return 0;

err_clk:
        clk_disable_unprepare(c->mclk);
err_reg:
        regulator_bulk_disable(ARRAY_SIZE(c->supplies), c->supplies);
        return ret;
}

这段的每个 goto 目标都对应「按相反顺序撤销已成功的部分」。三个框架都没有「事务」概念，回滚全得自己写。

协同时的四条铁律：

  1. 先时钟后电源域不会错，反过来会错。platform_drv_probe() 的顺序是有理由的。
  2. regulator 上电顺序由数组顺序决定，拆除顺序必须反过来。乱序关电会出现「数字先断，模拟还通着」的灌电流窗口。
  3. PWM 的周期和极性来自 DTS，代码只改占空比。把 DTS 里定的 1ms 改成 10us 会让功放偏置变成音频噪声源。
  4. 三个框架都靠 DTS 里 <name>-supply / clocks / power-domains 三套属性连起来，名字拼错不会报错，只会 probe defer 到超时。VDDA-supply 写成 vdda-supply，DT 属性名是大小写敏感的，框架按你 .supply = "VDDA" 精确匹配。这类问题占了新手调试时间的一大半，先看 /sys/kernel/debug/devices_deferred。

按框架分组，每条都写成「症状 → 原因 → 怎么查」。

Regulator

症状 原因 查法
probe 一直 -EPROBE_DEFER 到超时 前级 supply 名字对不上，或前级驱动没注册 cat /sys/kernel/debug/devices_deferred；ls /sys/class/regulator/ 看 regulator-name

PM domain

症状 原因 查法

三、未验证项 #

以下内容我无法在本轮核到确切 commit 或版本号，标为未验证，使用时请按你自己那份内核的源码确认：

  1. pwm_apply_state() 引入的确切版本。已确认 5.4 的 include/linux/pwm.h 里存在 struct pwm_state、pwm_apply_state()，且 pwm_config()/pwm_enable()/pwm_disable() 已是 inline 包装；4.19 的同一文件因源站限流未取到，所以「4.19 是否已完成这一迁移」未验证。
  2. struct pwm_ops 里 .config()/.enable()/.disable() 被标注「Only used by legacy drivers」的具体版本，只确认 5.4 如此。
  3. genpd_dev_pm_attach() 在 3.18 遇到 of_genpd_get_from_provider() 失败时返回 PTR_ERR(pd)（-ENOENT）而非 -EPROBE_DEFER。这一点由 3.18 与 4.4 源码对比得出，但「3.18 里这个行为是否对所有路径都成立」未逐分支验证。
  4. regulator_apply_uV（apply_uV 位域）对应的 DTS 属性名。素材未给，各版本 binding 文档有变，未验证。
  5. enable_time 在 DTS 侧的属性名（regulator-enable-ramp-delay 与 enable_time 的对应关系）按常见 binding 写，未逐版本核对。
  6. PWM 原文提到的「人耳 20Hz~16KHz」是通用声学常识，非内核文档表述。
  7. 4.19 struct regulator_desc 中 continuous_voltage_range 变为位域成员的位置（出现在 int id; 之前）依据 5.4 头文件，4.19 是否已如此未验证。
  8. 本篇「二十六」章的 codec 示例（compatible = "vendor,xyz-codec"）是为说明协作流程构造的示意设备，不对应任何真实芯片。
