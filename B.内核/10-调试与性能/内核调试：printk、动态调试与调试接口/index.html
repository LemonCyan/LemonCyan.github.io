内核出问题时，你手上其实只有三种动作：让它多说话、让它多自检、让它把现场摊开给你看。这篇把这三件事拆开讲透——printk 的日志去了哪、pr_debug() 为什么不出声、CONFIG_DEBUG_* 打开后内核多了哪些检查、以及不改代码就能读变量的 sys 节点。

一、内核调试的三条路：打日志、开选项、看现场 #

三条路的成本和适用场景完全不同，先摆在一起看：

路径 典型手段 改动量 生效时机 适合什么
打日志 printk / pr_* / dev_* 改源码、重编 下一次启动 第一次把「卡在哪」缩小到文件甚至行
开选项 CONFIG_DEBUG_*、DEBUG 宏、slub_debug 改配置、重编 下一次启动 让内核自己查内存越界、锁顺序、死锁
看现场 sysfs、debugfs、/proc 驱动里加几行注册代码 不用重启 版本已到测试部，偶现 bug 要现取变量

第一条路最熟悉，也最容易被误用：日志密度拉满之后，问题本身被日志掩盖，尤其是跟时序相关的 bug。第二条路的代价藏在细节里——有些选项会让内核变慢几倍，有些会让原本不 panic 的地方报错。第三条路是很多人忽略的：产品已经 release 到测试部，出问题不能再要「给我个 debug 版本重测」，只能靠现场能读的节点。把三者串起来的顺序是：先用日志定位到可疑子系统 → 用 CONFIG_DEBUG_* 让内核帮你查具体机制 → 剩下的边界情况靠 sys 节点现场取证。反过来做更慢。

二、printk 要解决什么：内核态的 printf 为什么不一样 #

内核里用不了 printf。printf 是 glibc 的函数，依赖用户态、依赖 stdio 缓冲、依赖文件描述符，而这些在内核里全都不存在，早期启动阶段连进程都没有。printk 要做两件事，而且这两件事必须分开：

  1. 把消息记进内核日志缓冲区（历史上就是 __log_buf）；
  2. 调用已注册的控制台驱动，把消息送到控制台。

分开的理由是上下文：printk 会在 NMI 里、会在关中断的临界区里、会持有 console 的半把锁。第一条只是往内存里写一段，第二条要碰硬件、要拿 console_lock、要等串口发完。合成一步就没法在中断里用了。顺带一个和 printf 的格式差异：%p 在内核里会对地址做 hash，防止泄漏内存布局；要看真实地址得用 %px。

printk 家族现在的层次是这样：

接口 头文件 特点
printk(KERN_xxx fmt, ...) <linux/printk.h> 最底层，要自己写级别
pr_emerg … pr_info <linux/printk.h> 级别固定，省掉手写 KERN_xxx
pr_devel <linux/printk.h> 只在 DEBUG 下展开
pr_debug <linux/printk.h> 受 DEBUG / CONFIG_DYNAMIC_DEBUG 控制
dev_*（含 dev_dbg） <linux/dev_printk.h> 额外打印设备名、驱动名，可被动态调试管到

pr_* 系列本质就是 printk(KERN_xxx pr_fmt(fmt), ...) 的封装，pr_fmt 让你能统一加模块前缀：

c
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt

dev_* 系列多出来的东西才是重点——设备名、驱动名，以及在动态调试下可被精确定位。现在的驱动代码里不该再直接写 printk(KERN_INFO ...)，用 dev_info / dev_err / dev_dbg。一个具体差别：dev_warn(&rtc->dev, "invalid alarm value: %ptR\n", &alarm->time) 的输出是 rtc rtc0: invalid alarm value: 1900-02-01T00:00:00——带上了设备名，%ptR 把时间结构体直接格式化出来。

三、日志级别与它的数字 #

内核提供 0~7 共 8 个级别，宏定义在 include/linux/kern_levels.h：

c
#define KERN_EMERG      KERN_SOH "0"    /* system is unusable */
#define KERN_ALERT      KERN_SOH "1"    /* action must be taken immediately */
#define KERN_CRIT       KERN_SOH "2"    /* critical conditions */
#define KERN_ERR        KERN_SOH "3"    /* error conditions */
#define KERN_WARNING    KERN_SOH "4"    /* warning conditions */
#define KERN_NOTICE     KERN_SOH "5"    /* normal but significant condition */
#define KERN_INFO       KERN_SOH "6"    /* informational */
#define KERN_DEBUG      KERN_SOH "7"    /* debug-level messages */

#define KERN_DEFAULT    ""              /* the default kernel loglevel */

KERN_SOH 是 "\001"，也就是 0x01 这个不可打印字符。级别不是字符串前缀那么简单，它在 ring buffer 里本来就是两个字节：\001 加一个数字字符。

宏 数值 含义 谁在用
KERN_EMERG 0 系统不可用，崩溃前 内核核心
KERN_ALERT 1 必须立刻处理 严重故障路径
KERN_CRIT 2 严重软硬件失败 核心子系统
KERN_ERR 3 错误状态 驱动报硬件问题
KERN_WARNING 4 警告，尚不构成故障 驱动最常见
KERN_NOTICE 5 正常但值得提示 安全相关
KERN_INFO 6 提示信息 驱动启动打硬件信息
KERN_DEBUG 7 调试信息 pr_debug / dev_dbg

数值越大，越不重要。 这条别记反。

判定规则只有一句：消息级别数值 小于 当前 console_loglevel 才上控制台。门槛是 7 时，级别 7 的 KERN_DEBUG 不满足 7 < 7，所以不出现在串口上。

没写级别时用 default_message_loglevel，这个值就是 /proc/sys/kernel/printk 里的第二个数字。

四、printk 的第一行代码：从调用到 ring buffer #

先看入口。kernel/printk/printk.c：

c
asmlinkage __visible int printk(const char *fmt, ...)
{
        va_list args;
        int r;

        va_start(args, fmt);
        r = vprintk_func(fmt, args);
        va_end(args);

        return r;
}

printk 自己什么都不做，转手给 vprintk_func。这个函数在 kernel/printk/printk_safe.c（5.2.8 的位置），它按当前上下文分三条路：

c
__printf(1, 0) int vprintk_func(const char *fmt, va_list args)
{
        if ((this_cpu_read(printk_context) & PRINTK_NMI_DIRECT_CONTEXT_MASK) &&
            raw_spin_trylock(&logbuf_lock)) {
                int len;

                len = vprintk_store(0, LOGLEVEL_DEFAULT, NULL, 0, fmt, args);
                raw_spin_unlock(&logbuf_lock);
                defer_console_output();
                return len;
        }

        /* Use extra buffer in NMI when logbuf_lock is taken or in safe mode. */
        if (this_cpu_read(printk_context) & PRINTK_NMI_CONTEXT_MASK)
                return vprintk_nmi(fmt, args);

        /* Use extra buffer to prevent a recursion deadlock in safe mode. */
        if (this_cpu_read(printk_context) & PRINTK_SAFE_CONTEXT_MASK)
                return vprintk_safe(fmt, args);

        /* No obstacles. */
        return vprintk_default(fmt, args);
}

四条分支：NMI 上下文且抢得到 logbuf_lock → 直接写主缓冲区并把控制台输出推迟（defer_console_output）；NMI 上下文但抢不到锁 → vprintk_nmi，用 per-CPU 的 NMI 缓冲区；safe 上下文（递归、关中断等危险位置）→ vprintk_safe，用 per-CPU 的 safe 缓冲区；其余 → vprintk_default，正常路径。正常路径继续往下：

c
int vprintk_default(const char *fmt, va_list args)
{
    int r;
#ifdef CONFIG_KGDB_KDB
    if (unlikely(kdb_trap_printk && kdb_print_cpu < 0)) {
        r = vkdb_printf(KDB_MSGRC_PRINTK, fmt, args);
    }
#endif
    r = vprintk_emit(0, LOGLEVEL_DEFAULT, NULL, 0, fmt, args);
    return r;
}

asmlinkage int vprintk_emit(int facility, int level, const char *dict, size_t dictlen,
                            const char *fmt, va_list args)
{
    int printed_len;
    bool in_sched = false, pending_output;
    unsigned long flags;
    u64 curr_log_seq;

    if (unlikely(suppress_printk))
        return 0;

    if (level == LOGLEVEL_SCHED) {
        level = LOGLEVEL_DEFAULT;
        in_sched = true;
    }
    boot_delay_ms(level);
    printk_delay();

    logbuf_lock_irqsave(flags);
    curr_log_seq = log_next_seq;
    printed_len = vprintk_store(facility, level, dict, dictlen, fmt, args);
    pending_output = (curr_log_seq != log_next_seq);
    logbuf_unlock_irqrestore(flags);

    if (!in_sched && pending_output) {
        preempt_disable();
        if (console_trylock_spinning())
            console_unlock();
        preempt_enable();
    }
    return printed_len;
}

原笔记这里的代码有多处笔误，我按逻辑改回来了：boot_delay_msce 应为 boot_delay_ms、prinkt_delay 应为 printk_delay、premmpt_enable 应为 preempt_enable、pending_output 那句缺分号、logbuf_lock_irqsave 的参数类型应一致。函数名和调用顺序是原文的，全部改正项见附录。

到这一步流程已经清楚了：vprintk_emit 先拿 logbuf_lock 把消息塞进缓冲区，放锁之后再看要不要立刻把缓冲区里的东西推到控制台。

vprintk_store 负责把可变参数格式化成一行文本，再从行首剥掉级别前缀：

c
int vprintk_store(int facility, int level, const char *dict, size_t dictlen,
                  const char *fmt, va_list args)
{
    static char textbuf[LOG_LINE_MAX];
    char *text = textbuf;
    size_t text_len;
    enum log_flags lflags = 0;

    text_len = vscnprintf(text, sizeof(textbuf), fmt, args);
    if (text_len && text[text_len - 1] == '\n') {
        text_len--;
        lflags |= LOG_NEWLINE;
    }

    if (facility == 0) {
        int kern_level;
        while ((kern_level = printk_get_level(text)) != 0) {
            switch (kern_level) {
                case '0' ... '7':
                    if (level == LOGLEVEL_DEFAULT)
                        level = kern_level - '0';
                    break;
                case 'c':
                    lflags |= LOG_CONT;
            }
            text_len -= 2;
            text += 2;
        }
    }

    if (level == LOGLEVEL_DEFAULT)
        level = default_message_loglevel;

    if (dict)
        lflags |= LOG_NEWLINE;

    return log_output(facility, level, lflags, dict, dictlen, text, text_len);
}

两个细节：textbuf 是 static，格式化缓冲区全局共享，并发安全靠外层 logbuf_lock 保证——所以这条路径绝不能重入；级别前缀剥掉之后 level 单独存进记录字段，不再占文本空间。

log_output 处理续行（KERN_CONT），log_store 才是真正落盘：

c
static int log_store(u32 caller_id, int facility, int level, enum log_flags flags,
                     u64 ts_nsec, const char *dict, u16 dict_len,
                     const char *text, u16 text_len)
{
    msg = (struct printk_log *)(log_buf + log_next_idx);
    memcpy(log_text(msg), text, text_len);
    msg->text_len = text_len;
    log_next_idx += msg->len;
    log_next_seq++;
    return msg->text_len;
}

记录变长：一条消息 = 头部结构 + 文本，紧挨着放下一条。

五、ring buffer 的组织方式 #

缓冲区本体定义在 kernel/printk/printk.c，CONFIG_LOG_BUF_SHIFT 决定大小，默认 17 也就是 2^17 = 128 KB，menuconfig 里的名字是 LOG_BUF_SHIFT：

c
/* record buffer */
#define LOG_ALIGN __alignof__(struct printk_log)
#define __LOG_BUF_LEN (1 << CONFIG_LOG_BUF_SHIFT)
#define LOG_BUF_LEN_MAX (u32)(1 << 31)
static char __log_buf[__LOG_BUF_LEN] __aligned(LOG_ALIGN);
static char *log_buf = __log_buf;
static u32 log_buf_len = __LOG_BUF_LEN;

注意这个结构：静态数组 __log_buf 是编译期的后备，log_buf 指针在启动时可以指向 memblock 分配出来的更大一块，log_buf_len 跟着变。启动参数 log_buf_len=2M 走的就是这条替换路径。记录头在 5.2.8 里是 ts_nsec / len / text_len / dict_len / facility / 位域 flags:5 / 位域 level:3，开了 CONFIG_PRINTK_CALLER 再加 u32 caller_id，最后按需 __packed __aligned(4)。flags:5 和 level:3 挤在同一个字节里，级别只占 3 bit——正好放得下 0~7 八个数。文本紧跟在头后面：log_text() 就是 (char *)msg + sizeof(struct printk_log)。

索引不是用 % size 算的，用的是环形偏移加边界检查。这套全局状态就是整个模型：

c
/* the next printk record to read by syslog(READ) or /proc/kmsg */
static u64 syslog_seq;
static u32 syslog_idx;

/* index and sequence number of the first record stored in the buffer */
static u64 log_first_seq;
static u32 log_first_idx;   /* 环形缓冲区里最老一条的索引 */

/* index and sequence number of the next record to store in the buffer */
static u64 log_next_seq;    /* 累计写入的日志条数 */
static u32 log_next_idx;    /* 下一条写入位置 */

/* the next printk record to write to the console */
static u64 console_seq;
static u32 console_idx;

/* the next printk record to read after the last 'clear' command */
static u64 clear_seq;
static u32 clear_idx;

三个游标（log_next_idx 写、console_idx 读给控制台、syslog_idx 读给 /proc/kmsg）配三组序号，是这套设计的核心：

变量 类型 作用
log_next_idx u32 下一条记录写入 log_buf 的偏移，回绕
log_next_seq u64 累计写入条数，单调递增不回绕
log_first_idx / log_first_seq u32 / u64 缓冲区里最老记录的位置
console_idx / console_seq u32 / u64 控制台已输出到的位置
syslog_idx / syslog_seq u32 / u64 /proc/kmsg、syslog(2) 读到哪
clear_idx / clear_seq u32 / u64 上次 dmesg -c 清空的位置

为什么要两组？idx 是偏移量，u32 够用但会回绕；seq 是绝对计数，u64 不回绕。判断「有没有被新日志覆盖」必须用 seq 比——两个 idx 差了半个缓冲区时，你没法只靠 idx 判断是超前还是落后。

LOG_BUF_MASK 是更早版本的写法：#define LOG_BUF_MASK (log_buf_len-1) 配 log_buf[idx & LOG_BUF_MASK]，做单条记录内的字符拷贝。2.6.24 之后记录改成变长结构、按 idx 线性游走，5.2.8 的 printk.c 已经没有这个宏，5.10 的 printk_ringbuffer.c 里也没有。在旧内核里看到 LOG_BUF_MASK，那是 2.6 时代的代码。

写满之后的行为：新记录继续往 log_next_idx 写，同时把 log_first_idx / log_first_seq 往前推，最老的记录被丢弃，并在记录里留下覆盖标记（宏名随版本变，未逐一核对）。早期启动日志被后面刷掉是常事，这就是 log_buf_len=2M 这类参数存在的原因。

六、dmesg 与 /proc/kmsg、/dev/kmsg #

用户态读日志有三条路，最后都落到 do_syslog：

text
dmesg          → syslog(2) 系统调用           → do_syslog(SYSLOG_ACTION_READ_ALL)
/proc/kmsg     → proc 文件读接口               → do_syslog(SYSLOG_ACTION_READ)
/dev/kmsg      → devtmpfs 字符设备读接口        → devkmsg_read()

三者的差别很实际：

接口 语义 能不能读多条 谁在用
dmesg（syslog(2)） 读缓冲区快照 能，READ_ALL 一次读完 人工排查、开机脚本
/proc/kmsg 流式，读一次少一次 读完就推进 syslog_seq klogd
/dev/kmsg 流式 + 可写 读同上；写进日志 systemd-journald

关键区别：/proc/kmsg 和 /dev/kmsg 是消费型的，多个读者会互相抢。dmesg 不消费，读的是一个快照范围。所以线上别再跑 cat /proc/kmsg——它会把 syslog_seq 往前推，把 klogd 的日志抢走。

cat /proc/kmsg 的原始输出带级别标记 <6>、<5>；同一行内容用 dmesg 看是不带 <n> 的：

text
[root@zy:/]# cat /proc/kmsg
<6>Booting Linux on physical CPU 0x0
<5>Linux version 5.2.8 (root@zhengyang) (gcc version 4.8.3 ...) #23 Sun Mar 26 14:53:14 CST 2023

[root@zy:/]# dmesg
Booting Linux on physical CPU 0x0
Linux version 5.2.8 (root@zhengyang) (gcc version 4.8.3 ...) #23 Sun Mar 26 14:53:14 CST 2023

dmesg 的常用参数值得记：

bash
dmesg -T                 # 时间戳换成可读的墙上时间
dmesg -l err,warn        # 只看错误和警告
dmesg -w                 # 跟随，等新日志（替代 cat /proc/kmsg）
dmesg -c                 # 读完后清空（推进 clear_seq）
dmesg | grep -i 'probe failed'

dmesg -c 清的是「已读位置」，不是真去 memset 缓冲区，所以内存不会立刻回来。/dev/kmsg 的写入端还有个用处：用户态程序可以自己往内核日志里插一条，journald 和 systemd 就是这么标记启动阶段的。写入格式是 PRIORITY=...,SUBSYSTEM=... 这种键值前缀加正文，具体字段随版本有扩充，未逐一核对。

七、console 与 printk 的关系：什么时候真的输出到串口 #

printk 只管往缓冲区写。真正往串口吐字符的是控制台驱动，而控制台是按链表组织、按注册顺序调用的。console_unlock 是推日志的那只手，它逐条取出缓冲区里的记录，转成文本后交给所有已注册的控制台：

c
void console_unlock(void)
{
    static char ext_text[CONSOLE_EXT_LOG_MAX];
    static char text[LOG_LINE_MAX + PREFIX_MAX];

    for (;;) {
        msg = log_from_idx(console_idx);
        len += msg_print_text(msg, console_msg_format & MSG_FORMAT_SYSLOG,
                              printk_time, text + len, sizeof(text) - len);
        console_idx = log_next(console_idx);
        console_seq++;
        call_console_drivers(ext_text, ext_len, text, len);
    }
}

static void call_console_drivers(const char *ext_text, size_t ext_len,
                                 const char *text, size_t len)
{
    struct console *con;
    trace_console_rcuidle(text, len);
    for_each_console(con) {
        if (con->flags & CON_EXTENDED)
            con->write(con, ext_text, ext_len);
        else
            con->write(con, text, len);
    }
}

for_each_console 遍历的是一条以 console_drivers 为头的链表。级别过滤在 msg_print_text 与 console_loglevel 的比较里，不满足的条目照样推进 console_idx，只是不往 text 里放。

所以「串口没打印」和「printk 没执行」完全是两件事，这是本章最要记住的一句。判断方法：dmesg 里有没有那条消息。有，说明写进缓冲区了，是控制台过滤掉了；没有，说明 printk 那条根本没跑（或者已经被覆盖）。

控制台的注册靠 register_console，它处理两类控制台（bootconsole 与「real」console）。骨架只保留匹配与入链两段，省略号处是原函数的其余检查：

c
void register_console(struct console *newcon)
{
        ...
        if (console_drivers && newcon->flags & CON_BOOT) {
                for_each_console(bcon) {
                        if (!(bcon->flags & CON_BOOT)) {
                                pr_info("Too late to register bootconsole %s%d\n",
                                        newcon->name, newcon->index);
                                return;
                        }
                }
        }
        ...
        for (i = 0, c = console_cmdline;
             i < MAX_CMDLINECONSOLES && c->name[0];
             i++, c++) {
                if (!newcon->match ||
                    newcon->match(newcon, c->name, c->index, c->options) != 0) {
                        if (strcmp(c->name, newcon->name) != 0)
                                continue;
                        if (newcon->index >= 0 && newcon->index != c->index)
                                continue;
                        if (newcon->index < 0)
                                newcon->index = c->index;
                        if (newcon->setup &&
                            newcon->setup(newcon, c->options) != 0)
                                break;
                }
                newcon->flags |= CON_ENABLED;
                if (i == preferred_console)
                        newcon->flags |= CON_CONSDEV;
                break;
        }

        if (!(newcon->flags & CON_ENABLED))
                return;

        console_lock();
        if ((newcon->flags & CON_CONSDEV) || console_drivers == NULL) {
                newcon->next = console_drivers;
                console_drivers = newcon;
        } else {
                newcon->next = console_drivers->next;
                console_drivers->next = newcon;
        }

        if (newcon->flags & CON_PRINTBUFFER) {
                logbuf_lock_irqsave(flags);
                console_seq = syslog_seq;
                console_idx = syslog_idx;
                exclusive_console = newcon;
                exclusive_console_stop_seq = console_seq;
                logbuf_unlock_irqrestore(flags);
        }
        console_unlock();
        console_sysfs_notify();
        pr_info("%sconsole [%s%d] enabled\n",
                (newcon->flags & CON_BOOT) ? "boot" : "",
                newcon->name, newcon->index);
        if (bcon &&
            ((newcon->flags & (CON_CONSDEV | CON_BOOT)) == CON_CONSDEV) &&
            !keep_bootcon) {
                for_each_console(bcon)
                        if (bcon->flags & CON_BOOT)
                                unregister_console(bcon);
        }
}

三个标志位决定了行为：

标志 含义
CON_ENABLED 该控制台已启用
CON_BOOT 启动期临时控制台，真控制台一来就摘掉
CON_PRINTBUFFER 注册时把缓冲区里已有的日志补印一遍
CON_CONSDEV 首选控制台，链表里放头部

匹配的基准是 console_cmdline[]——bootargs 里 console= 解析出来的东西：

c
#define MAX_CMDLINECONSOLES 8

static struct console_cmdline console_cmdline[MAX_CMDLINECONSOLES];

struct console_cmdline
{
        char    name[16];       /* Name of the driver */
        int     index;          /* Minor dev. to use */
        char    *options;       /* Options for the driver */
#ifdef CONFIG_A11Y_BRAILLE_CONSOLE
        char    *brl_options;   /* Options for braille driver */
#endif
};

数组只有 8 个槽。console=ttySAC0,115200 由 console_setup（挂 _setup("console=", console_setup)）解析成 name=ttySAC、index=0、options=115200，再由 __add_preferred_console 写进数组，同时记下 preferred_console 下标。register_console 里那个 newcon->match / strcmp 就是拿这个 name 在比。

注册成功的证据就是两行日志：

text
printk: bootconsole [earlycon0] enabled
printk: console [ttySAC0] enabled

在一个真实的 rk3588 板子上（Linux version 5.10.160）能看到完整切换过程：

text
[    0.895403] earlycon: uart8250 at MMIO32 0x00000000feb50000 (options '')
[    0.899526] printk: bootconsole [uart8250] enabled
[    1.359277] printk: console [ttyFIQ0] enabled
[    1.360047] printk: bootconsole [uart8250] disabled

earlycon / earlyprintk 是控制台注册之前唯一能出字的路。 上面的开关全部管不到那一刻。arm 上的老写法是 earlyprintk：

c
static struct console early_console_dev = {
        .name =         "earlycon",
        .write =        early_console_write,
        .flags =        CON_PRINTBUFFER | CON_BOOT,
        .index =        -1,
};

static int __init setup_early_printk(char *buf)
{
        early_console = &early_console_dev;
        register_console(&early_console_dev);
        return 0;
}

early_param("earlyprintk", setup_early_printk);

early_param 展开成 .init.setup 段里的 struct obs_kernel_param { const char *str; int (*setup_func)(char *); int early; }。start_kernel() → setup_arch() → parse_early_param() → do_early_param() 遍历 __setup_start 到 __setup_end，参数命中就调 setup_func。early_write 最后落到 printascii（arch/arm/kernel/debug.S），直接往 UART 寄存器写——前提是 bootloader 已经把串口初始化过。arm64 上已经没有 early_printk 这东西了，走的是设备树驱动的 earlycon，earlycon=uart8250,mmio32,0xfeb50000 这种参数格式。

补一个容易忽略的事实：pr_notice("%s", linux_banner) 在 setup_arch() 里就跑了，比 early console 早，却能在串口看到内核 banner——因为那条消息先躺在 __log_buf 里，等 early console 注册（带 CON_PRINTBUFFER）时才补印出来。缓冲区比控制台早存在，这是理解整条链路的关键。

八、loglevel 与 /proc/sys/kernel/printk 四个数字 #

/proc/sys/kernel/printk 一读就给四个数字，在 linux 5.2.8 的板子上是 7 4 1 7：

c
int console_printk[4] = {
        CONSOLE_LOGLEVEL_DEFAULT,       /* console_loglevel */
        MESSAGE_LOGLEVEL_DEFAULT,       /* default_message_loglevel */
        CONSOLE_LOGLEVEL_MIN,           /* minimum_console_loglevel */
        CONSOLE_LOGLEVEL_DEFAULT,       /* default_console_loglevel */
};
EXPORT_SYMBOL_GPL(console_printk);
位置 变量 作用
第 1 个 console_loglevel 当前控制台门槛，级别数值小于它的才上控制台
第 2 个 default_message_loglevel 没写级别时套用的值
第 3 个 minimum_console_loglevel 第一个数能被压到的最小值
第 4 个 default_console_loglevel 第一个数的出厂缺省值

三个常改的动作：

bash
cat /proc/sys/kernel/printk              # 看当前值：7  4  1  7
echo "8 4 1 7" > /proc/sys/kernel/printk  # 全开：级别 7 也能上控制台
echo "1 4 1 7" > /proc/sys/kernel/printk  # 只留级别 0 的紧急消息

8 不是合法日志级别，它是一个大于 7 的门槛值——正因如此级别 7 的 KERN_DEBUG 才能满足 7 < 8。原笔记里写「屏蔽所有打印只需把第一个数调到 1 或 0」，严格讲 1 会放过 KERN_EMERG，只有 0 才是全禁；minimum_console_loglevel 是 1 时你连 0 都写不进去。这条我按源码语义改了。

改 menuconfig 是另一条路，改完要重编。Kernel hacking → printk and dmesg options → (4) Default message log level (1-7) 对应 CONFIG_MESSAGE_LOGLEVEL_DEFAULT，也就是第二个数字。启动阶段 /proc 还没挂，只能靠 cmdline：

text
CONFIG_CMDLINE="earlycon=owl_serial loglevel=8"
CONFIG_CMDLINE_FORCE=y

CONFIG_CMDLINE_FORCE=y 不要漏，否则 bootloader 传进来的 cmdline 会盖掉内建的。判据是启动日志里能搜到 Kernel command line: earlycon=owl_serial loglevel=8。另一条等价的路是直接改 defconfig 里的 CONFIG_CONSOLE_LOGLEVEL_DEFAULT=8（原笔记排 rk3588 就这么干的），效果一样，只是编译期就定死。

还有一个绕过过滤的参数：ignore_loglevel。加上之后内核不比较级别，全往控制台推。这条来自 kernel-parameters 文档，我在素材的两台板子上没实测。改级别不一定立刻生效，这条坑写在 printk 的源码注释里：

text
 * One effect of this deferred printing is that code which calls printk() and
 * then changes console_loglevel may break. This is because console_loglevel
 * is inspected when the actual printing occurs.

原因在第七章的流程：printk 抢不到 console_lock 时只是把消息塞进缓冲区就返回，由持锁方在 console_unlock() 里补打，而 console_loglevel 是在实际打印那一刻才比对的。你 echo 完立刻看，中间那批还没推出去的消息仍按旧门槛处理。

九、printk 的安全问题：为什么它能在中断里调 #

printk 的注释第一句就是「It can be called from any context. We want it to work.」——能在任何上下文调用，是它的设计目标，也是它全部复杂度的来源。

要让它做到这一点，得解决四个冲突：

冲突 表现 解法
多核并发写 两个 CPU 同时改 log_next_idx logbuf_lock（5.10 前）/ 无锁 ring buffer（5.10 起）
重入 控制台驱动内部又调 printk 检测递归，走 per-CPU safe 缓冲区
NMI NMI 里拿不到被 NMI 打断的锁 per-CPU NMI 缓冲区
长时间关中断 遍历控制台、等串口发完 byte 把控制台输出推迟出临界区

前两条在第四章的 vprintk_func 里已经看到了，这里讲后两条的机制。递归死锁的具体形态：某个控制台驱动的 write() 内部调了 printk（比如驱动自己打了条错误日志）。这时外层 printk 已持有 logbuf_lock，内层再去拿就死锁。内核的应对是 printk_safe：

c
/* kernel/printk/printk_safe.c */
static DEFINE_PER_CPU(struct printk_safe_seq_buf, safe_print_seq);

vprintk_safe 把消息写进 safe_print_seq（per-CPU，无锁，因为关中断/递归上下文天然独占当前 CPU），然后通过 irq_work_queue 排一个软中断去刷。刷的时候会检查：如果当前已经处于 safe 上下文，就报 printk: N messages suppressed，宁可丢也不死锁。NMI 用的是同一套思路，vprintk_nmi 配 nmi_print_seq（5.2.8 的命名，后面版本合并进了 printk_safe 的统一框架）。

为什么会丢失消息：safe/NMI 缓冲区只有固定大小（几 KB 量级，PRINTK_SAFE_LOG_BUF_SHIFT），满了就丢并计数。看到串口输出「N messages suppressed」，说明当时上下文太危险或打印太频繁，不是日志系统坏了。

%p 为什么打不出地址：内核从 4.15 起对 %p 的输出做了 hash（密钥在启动时随机），防止从日志里反推内核地址来绕 KASLR。要真实地址用 %px。这是默认行为，不是开关，kptr_restrict 之类也改不了它。

日志本身的数据泄漏：%px、%pS（符号名）、寄存器值、时序信息，打到串口就等于把内核布局和运行时状态摆出来了。出厂镜像里等级开到 8、动态调试全开，难看只是次要问题。

十、printk 的历史演进：从 logbuf_lock 到 printk_safe #

素材横跨十几年，把关键节点列成表比读代码快。

内核版本 变化 判据
2.6.x 早期 LOG_BUF_MASK + log_buf[idx & MASK] 单条记录字符拷贝，固定长度 源码里有 LOG_BUF_MASK
2.6.24 附近 记录改成变长结构，printk_log 头 + 文本，log_first_idx / log_next_idx 游标 出现 struct printk_log
3.x ~ 4.x vprintk_func 引入 safe / NMI 分支，printk_safe.c 独立 有 kernel/printk/printk_safe.c
4.15 %p 输出加 hash，新增 %px 取真实值 Documentation/core-api/printk-formats.rst
5.x struct printk_log 改名 printk_record 方向演进，cont 续行缓冲 未逐一核对版本号
5.10 prb 无锁环形缓冲区（kernel/printk/printk_ringbuffer.c），logbuf_lock 移除 文件存在、logbuf_lock 搜不到
5.10+ 控制台输出推给 kthread，中断里不再直接吐串口 相关文档，未实测

5.10 这次改动的方向值得理解清楚，因为它是分水岭：

text
5.10 之前：printk 拿 logbuf_lock → 写 buffer → 放锁 → 抢 console_lock → 直接把字符推给串口
5.10 之后：printk 无锁写 prb 描述符 → 唤醒 printk kthread → kthread 拿 console_lock 慢慢推

「无锁」不是靠魔术，而是把环形缓冲区拆成「数据块 + 描述符数组」两部分，写者只改自己的描述符并做一次 atomic 发布，读者按 seq 判断有没有被覆盖。LOG_BUF_MASK 那套取模写法在新实现里彻底退场。

为什么这个改动重要：5.10 之前，一次 printk 在最坏情况下要把整个 __log_buf 里积压的内容全推给串口才返回，115200 波特率下这意味着毫秒级的停顿，而且在中断上下文里。5.10 之后打印挪到 kthread，printk 本身接近纯内存操作。代价是 panic 时必须有 console_flush_on_panic() 这种强制刷新的补救路径。版本边界要标清楚：你要改的代码是不是 5.10 之前，决定了 logbuf_lock 存不存在。 在 5.10 及以后的树上搜 logbuf_lock 搜不到，不是你的树被裁了，是它真的没了。

十一、pr_debug() 为什么默认不输出 #

改了设备树没生效、驱动 probe 卡住，串口上却一行日志都没有。多半不是代码没跑，是 pr_debug() 在编译期就被编成了空函数。

<linux/printk.h> 里的定义（dev_dbg 在 <linux/dev_printk.h>，结构一样）：

c
#if defined(CONFIG_DYNAMIC_DEBUG)
#define pr_debug(fmt, ...)            \
    dynamic_pr_debug(fmt, ##__VA_ARGS__)
#elif defined(DEBUG)
#define pr_debug(fmt, ...) \
    printk(KERN_DEBUG pr_fmt(fmt), ##__VA_ARGS__)
#else
#define pr_debug(fmt, ...) \
    no_printk(KERN_DEBUG pr_fmt(fmt), ##__VA_ARGS__)
#endif

三个分支：

条件 展开成 运行时行为
有 CONFIG_DYNAMIC_DEBUG dynamic_pr_debug(...) 查调用点是否启用，默认不启用
只有 DEBUG 宏 printk(KERN_DEBUG ...) 真打印，但仍受级别 7 过滤
两个都没有 no_printk(...) 编译期消失，只剩参数类型检查

dev_dbg 更彻底，兜底分支是 if (0) dev_printk(...)：

c
#if defined(CONFIG_DYNAMIC_DEBUG) || \
    (defined(CONFIG_DYNAMIC_DEBUG_CORE) && defined(DYNAMIC_DEBUG_MODULE))
#define dev_dbg(dev, fmt, ...)                        \
    dynamic_dev_dbg(dev, dev_fmt(fmt), ##__VA_ARGS__)
#elif defined(DEBUG)
#define dev_dbg(dev, fmt, ...)                        \
    dev_printk(KERN_DEBUG, dev, dev_fmt(fmt), ##__VA_ARGS__)
#else
#define dev_dbg(dev, fmt, ...)                        \
({                                    \
    if (0)                                \
        dev_printk(KERN_DEBUG, dev, dev_fmt(fmt), ##__VA_ARGS__); \
})
#endif

if (0) 的写法让编译器仍然做语法和类型检查，但生成代码里没有这条调用——所以 dev_dbg 里的变量在关掉之后不会引发「未使用变量」警告。pr_devel 的条件更窄，只认 DEBUG：

c
#ifdef DEBUG
#define pr_devel(fmt, ...) \
    printk(KERN_DEBUG pr_fmt(fmt), ##__VA_ARGS__)
#else
#define pr_devel(fmt, ...) \
    no_printk(KERN_DEBUG pr_fmt(fmt), ##__VA_ARGS__)
#endif

dev_vdbg 要 DEBUG 加 VERBOSE_DEBUG 才出现，是动态调试时代之前给「特别吵」的日志留的后门。

所以调试日志要出来，两个条件缺一不可：编译期让 pr_debug / dev_dbg 有实体（DEBUG 或 CONFIG_DYNAMIC_DEBUG）；运行时把 console_loglevel 提到 8，否则级别 7 的消息进不了控制台。原笔记两篇都卡在这：只做了第一条，看到「打开 DEBUG 宏是第一步，这个时候还是不能输出到控制台」就以为失败了。#define DEBUG 的位置有讲究，必须在所有 #include 之前，尤其 <linux/device.h>——因为 dev_dbg 的展开在头文件里就定死了，你后定义 DEBUG 对已经展开过的宏没用。

十二、dynamic debug：运行时开启的办法 #

前一种办法都要重编。CONFIG_DYNAMIC_DEBUG 的思路是：编译期把所有 pr_debug / dev_dbg 调用点登记成一张表，运行时按条件精确打开某几个。依赖 CONFIG_DYNAMIC_DEBUG=y 与 CONFIG_DEBUG_FS=y。

先看有哪些调用点、哪些已经开着（第三列 =p 表示启用，=_ 表示未启用），再往这个文件写查询串：

bash
mount -t debugfs none /sys/kernel/debug
head -n 7 /sys/kernel/debug/dynamic_debug/control
grep '=p' /sys/kernel/debug/dynamic_debug/control

echo 'file drivers/of/fdt.c +p' > /sys/kernel/debug/dynamic_debug/control
echo 'module drm +p'            > /sys/kernel/debug/dynamic_debug/control
echo 'file drivers/of/fdt.c -p' > /sys/kernel/debug/dynamic_debug/control

+p 启用，-p 停用（写成 p 也行），=p 是仅启用匹配项、把其他全部关掉。一次可以写多条，用 ; 或换行分隔。

路径有个版本差异：老内核只挂在 debugfs 下，新内核的官方文档入口是 /proc/dynamic_debug/control，挂了 debugfs 之后同样出现在 /sys/kernel/debug/dynamic_debug/control。先 ls 一下哪个存在，别照抄。

启动阶段没有用户态，用启动参数，语法一样：

text
dyndbg="file drivers/of/fdt.c +p"

模块用 模块名.dyndbg="+p"（模块名里 - 换成 _）。两条硬限制：dyndbg 在 early_initcall 阶段才被处理，这之前跑的代码开不了；查询串不能超过 1023 字符，bootloader 的限制还要更短。最容易忘的一步：动态调试打开的是调用点，能不能在串口看见还得回到 loglevel=8 或 ignore_loglevel。

ddebug_query 是另一条等效入口，它是 dyndbg 的早期别名（走 early_param 那一类注册），语义一致。老内核里你会看到有人写 ddebug_query="file fdt.c +p"。

dynamic_debug 的解析流程大致是：整个查询串按 ; 切分 → 每段按空白切 token → 每个 token 前面认关键字（file / func / line / module / format / + / - / =）→ 拼成查询条件 → 遍历 __start___dyndbg 到 __stop___dyndbg 之间的所有 struct _ddebug 描述符逐条比对 → 命中就改 flags。

struct _ddebug 大致是这么个形状（字段随版本变，这里给 5.x 的骨架）：

c
struct _ddebug {
    const char *modname;    /* 模块名 */
    const char *function;   /* 函数名 */
    const char *filename;   /* 文件名 */
    const char *format;     /* 格式串 */
    unsigned int lineno:18; /* 行号 */
    unsigned int flags:8;   /* 状态位 */
    ...
};

flags 里最低位就是启用位。dynamic_pr_debug 展开后就是「取描述符 → 测 flag → flag 置位才调 __dynamic_pr_debug」。所以静态关闭的开销只有一次内存读加一次比较，这是它相对老 DEBUG 宏最大的价值。

十三、/sys/kernel/debug/dynamic_debug/control 的格式 #

这个文件的每一行是一个调用点，结构固定五段：文件名:行号 [模块名]函数名 =标志 "格式串"。真实的行长这样（路径和模块名随内核变）：

text
drivers/of/fdt.c:1234 [fdt]unflatten_device_tree =_ "unflattening %pOF\n"
drivers/gpu/drm/drm_drv.c:88 [drm]drm_dev_register =p "drm: registered %s\n"
字段 例子 说明
文件名 drivers/of/fdt.c 编译时的相对路径，查询串里可直接用
行号 1234 line 匹配用，可写范围 line 1200-1300
模块名 [fdt] 内建代码这一栏是空的方括号或省略
函数名 unflatten_device_tree func 匹配用
标志 =_ / =p p 打印，f 带函数名，l 带行号，m 带模块名，t 带线程 ID
格式串 "unflattening %pOF\n" format 匹配用，会被转义显示

标志位可以叠加，=pflmt 就是全开。+pfl 之后输出会变成 unflatten_device_tree:1234: unflattening /chosen，多进程并发时能分清是谁打的，t 在多线程场景下很值得开。

bash
echo 'file fdt.c +pfl' > /sys/kernel/debug/dynamic_debug/control   # 带上函数名、行号
echo 'file fdt.c +pt'  > /sys/kernel/debug/dynamic_debug/control   # 带上线程 ID

查询串支持的关键字和通配：

关键字 匹配对象 通配
file 文件名（含路径） * ?
module 模块名 * ?
func 函数名 * ?
line 行号或范围 line 100-200
format 格式串 部分版本支持

几个实际写法：

bash
echo 'file drivers/of/* +p' > /sys/kernel/debug/dynamic_debug/control          # 整个目录
echo 'func unflatten_device_tree +p' > /sys/kernel/debug/dynamic_debug/control # 单个函数
echo 'file fdt.c line 1200-1300 +p' > /sys/kernel/debug/dynamic_debug/control  # 行号范围
printf 'file fdt.c +p\nfile fdt_ro.c +p\n' > /sys/kernel/debug/dynamic_debug/control  # 一次多条

file 匹配的是编译时的相对路径，所以 file fdt.c 和 file drivers/of/fdt.c 在不同版本上行为不一致——最稳的写法是把 control 文件里那行的第一段整个复制过来。

十四、dev_dbg / netdev_dbg 与 dynamic debug 的关系 #

dev_dbg、netdev_dbg、dev_vdbg、netdev_vdbg 这几个都不走 CONFIG_DYNAMIC_DEBUG 的 pr_debug 那条分支，而是各自的 dynamic_* 版本。共同点是描述符最终都挂在同一个 __dyndbg 段里，所以 control 文件能统一管到它们。netdev_dbg 的定义在 <linux/netdevice.h>（老版本在 netdevice.h 里直接写，新版本拆出去了）：

c
#if defined(CONFIG_DYNAMIC_DEBUG)
#define netdev_dbg(__dev, format, args...)            \
do {                                                  \
    dynamic_netdev_dbg(__dev, format, ##args);        \
} while (0)
#elif defined(NETIF_F_DEBUG) || defined(DEBUG)
#define netdev_dbg(__dev, format, args...)            \
({                                                    \
    netdev_printk(KERN_DEBUG, __dev, format, ##args); \
})
#else
#define netdev_dbg(__dev, format, args...)            \
({                                                    \
    if (0)                                            \
        netdev_printk(KERN_DEBUG, __dev, format, ##args); \
})
#endif

这里第二分支不是 DEBUG 而是 NETIF_F_DEBUG || DEBUG，这是网络子系统自己的宏。你只开 DEBUG 也能让 netdev_dbg 有实体，但反过来只开 NETIF_F_DEBUG 对 pr_debug 没用。netdev_dbg 的输出格式和 dev_dbg 不同——它带网络设备名和队列信息，类似 eth0: tx queue 0: ...。

dynamic debug 管到几个层次：

宏 在 control 文件出现 备注
pr_debug 是 最基础的调用点
dev_dbg 是 带设备名
netdev_dbg 是 带 netdev 名
pr_devel / dev_vdbg 是（若开了 CONFIG_DYNAMIC_DEBUG） 老宏，仍能管
裸 printk(KERN_DEBUG ...) 否 不能动态开关

最后一行是重点：裸 printk 不参与动态调试。这给了「别直接写 printk」一个硬理由，不只是风格问题。你用 pr_debug / dev_dbg，日后能运行时打开；你写裸 printk，只能改代码重编。

想让模块也能被管，还要注意 CONFIG_DYNAMIC_DEBUG_CORE：它把核心机制编进内核，模块自己用 DYNAMIC_DEBUG_MODULE 决定是否生成描述符。dev_dbg 的 #if 里那行 defined(CONFIG_DYNAMIC_DEBUG_CORE) && defined(DYNAMIC_DEBUG_MODULE) 就是为这个场景加的。

十五、CONFIG_DEBUG_* 选项打开了什么 #

pr_debug 那条线解决的是「我想让某处多打印」。CONFIG_DEBUG_* 那条线解决的是另一个问题：我不想在每个可疑位置都加打印，我想让内核自己去查。 这两件事经常被混成一个「开 DEBUG」，差别在谁产生判断逻辑：

手段 谁判断「有问题」 典型输出
pr_debug + dynamic debug 你自己写的打印 你填的格式串
CONFIG_DEBUG_* 内核里的 BUG / WARN / 自检代码 内核自己生成的报告

一个具体对比。你怀疑某个链表被破坏：做法 A 是在 list_add / list_del 前后加 pr_debug 自己看指针值；做法 B 是开 CONFIG_DEBUG_LIST，让 list_add 自己检测 prev/next 是否一致。A 需要你猜到问题在哪，B 不需要——它把所有 list_add 都变成带检查的版本。代价是每个链表操作多几条比较指令，以及一旦触发就 WARN 加栈回溯。

CONFIG_DEBUG_* 的实现套路基本一致：编译期换实现。以 CONFIG_DEBUG_LIST 为例，<linux/list.h> 里是这么切的：

c
#ifdef CONFIG_DEBUG_LIST
extern bool __list_add_valid(struct list_head *new,
                             struct list_head *prev,
                             struct list_head *next);
#else
static inline bool __list_add_valid(struct list_head *new,
                                    struct list_head *prev,
                                    struct list_head *next)
{
    return true;
}
#endif

else 分支返回恒真，关掉之后编译器直接常量折叠掉整段检查，一个字节都不多。

十六、DEBUG_KERNEL 与它的子选项树 #

CONFIG_DEBUG_KERNEL 自己什么都不干，它是个菜单开关。关掉它，下面那一整片选项在 menuconfig 里都看不着：

text
Kernel hacking  --->
    [*] Kernel debugging        # CONFIG_DEBUG_KERNEL
        printk and dmesg options  --->

分组大致这样（5.x 的分类，具体项随版本增删）：

menuconfig 里找不到某个选项，第一件事查它的父依赖。下面几条依赖关系很典型（CONFIG_KASAN 的依赖项随版本变过，以自己树的 Kconfig 为准）：

text

十七、几个最常用的 DEBUG 选项与它们的代价 #

下面这些是量产调试里真会用到的。代价一栏有依据的给依据，没实测的标出来。

选项 打开后内核多做什么 代价 适合什么
CONFIG_DEBUG_INFO 生成 DWARF 调试信息 镜像体积大增（几倍） 任何需要栈回溯/gdb 的场合
CONFIG_DEBUG_LIST 每次 list_add/del 校验前后指针 链表操作变慢，触发即 WARN 踩内存、链表错乱
CONFIG_DEBUG_ATOMIC_SLEEP 原子上下文里 might_sleep 报错 每个睡眠点加一次检查 在中断/持锁里睡眠
CONFIG_PROVE_LOCKING + LOCKDEP 记录锁依赖，检测 ABBA 死锁 内存占用明显，启动变慢（幅度未实测） 偶发死锁
CONFIG_DEBUG_SPINLOCK spinlock 增加 owner 记录与状态校验 每次加解锁多几次内存访问 自旋锁误用
CONFIG_DEBUG_MUTEXES 记录 mutex owner，检测重复解锁 同上 睡眠锁误用
CONFIG_KASAN 影子内存 + 对象红区，查越界/UAF 内存占用明显增加、性能明显下降（倍数未实测） 最难查的内存错误
CONFIG_DEBUG_PAGEALLOC 页释放后立即 unmap 分配释放变慢 UAF 定位
CONFIG_SLUB_DEBUG slub 的 P/Z/U 检查位 需要启动参数开启具体项 slab 对象越界
CONFIG_DEBUG_OBJECTS timer/work/tasklet 生命周期检查 每次操作加状态机检查 重复删除、释放后使用
CONFIG_PAGE_POISONING 已释放页填 0xaa 释放时要写整页 未初始化内存
CONFIG_PRINTK_TIME 日志带 [ 1.234567] 时间戳 每条多几次读取 时序分析（默认常开）

几个必须说清的点：

CONFIG_DEBUG_INFO 分两种。 DEBUG_INFO 生成完整 DWARF；DEBUG_INFO_REDUCED 砍到只剩栈回溯需要的部分，体积小很多；DEBUG_INFO_DWARF4 之类是格式选择。只想看栈回溯就用 reduced，几倍的体积差异不值得。

CONFIG_PROVE_LOCKING 会让「原本能跑」的系统报错。 lockdep 是静态分析式的：它找的是锁依赖环，不是实际发生的死锁。你的代码也许永远不会真的撞上那个环，但 lockdep 一开就报。这不是误报，是提前预警。

CONFIG_DEBUG_ATOMIC_SLEEP 的报错长这样：

text
BUG: sleeping function called from invalid context at kernel/locking/mutex.c:908
in_atomic(): 1, irqs_disabled(): 0, non_block: 0, pid: 1234, name: myapp

它挂在 might_sleep() 上——每个睡眠点在 debug 版本里都检查 in_atomic()，所以它在 DEBUG_KERNEL 下有依赖。slub_debug 是启动参数，不是固定的编译选项：开了 CONFIG_SLUB_DEBUG 之后，用 slub_debug=FZPU 控制开哪几项，也可以只对某个 slab 开：slub_debug=FZ,my_cache。

代价的量化：KASAN 的性能影响在不同负载上差异极大，我不给具体倍数，写「未实测」。任何要拿来评估性能数字的场景，别开这些选项——那正是同批《性能分析：从 CPU 占用率到 IO 延迟》的活。

十八、怎么打开、怎么确认打开 #

打开有四种粒度，代价从大到小：

粒度 做法 影响范围
整个内核 make menuconfig 或直接改 defconfig 全部代码，最慢
一个目录/模块 该目录 Makefile 加 subdir-ccflags-y := -DDEBUG 只这个目录
单个文件 文件开头 #define DEBUG 只这个文件
运行时 dynamic debug 往 control 文件写 只命中的调用点

前三种只影响 pr_debug 这类宏，第四种只影响已登记调用点，CONFIG_DEBUG_* 那些不走这四条路，必须改配置重编。subdir-ccflags-y 的写法，原笔记排 rk3588 的 PHY 问题时改的就是 drivers/phy/Makefile 和 drivers/gpu/drm/rockchip/Makefile，内容是 subdir-ccflags-y := -DDEBUG——注意 := 会覆盖目录里原有的 flags，要稳妥用 +=。全局注入宏则是编译时直接把宏灌进去：

bash
make -C /path/to/kernel ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
     O=/path/to/build KCFLAGS=-DDEBUG -j$(nproc)

原笔记的 Makefile diff 就是往编译命令里插了 KCFLAGS=-DDEBUG，但那份 diff 在 $(KERNEL_T、$(BOARD_ 处被截断了，照抄拼不出来，上面这条是补全的完整命令。

确认打开没有，三层都要查。

层次 命令 判据
配置生效 grep CONFIG_DYNAMIC_DEBUG /path/to/build/.config 看到 =y；只改 defconfig 没重新 make xxx_defconfig 的话 .config 还是旧的
调用点登记 grep -c 'fdt.c' /sys/kernel/debug/dynamic_debug/control 大于 0；为 0 说明路径写错或文件没编进内核
运行时放行 cat /proc/sys/kernel/printk 配 dmesg | grep 关键字 第一个数 ≥ 8，缓冲区里有这条

三层缺一层都是「看不到日志」，症状完全一样。这就是为什么很多人开了半天以为失败。

十九、sys 节点：不改代码查看现场 #

前面的手段都要重启。这一章换个方向：能不能不重启、不改代码，就在现场把变量的值读出来？ 能，这就是 sys 节点。素材里那篇随笔把它讲得很短，只给了「提供一个方向」——这一章往后是顺着这个方向补齐的实现细节，附录里标了哪些是补写。场景是真实现场：版本已经 release 到测试部集成测试，报了一个偶现 bug。你不能说「我马上回去给个 debug 版本，你重测吧」，测试人员会不高兴，而且偶现问题重编之后就未必复现。这时候你需要的是一组一直存在、随时能读的节点，把状态摊在 /sys 下。

sys 节点能承载的东西：

想看什么 用哪种节点 章节
单个模块的全局变量 module_param 二十
某个设备的状态、收发计数 device attribute 二十一
大量结构化调试信息 debugfs 二十二
只控制日志开关 全局变量 + module_param 二十

一个直接的用法就是素材里提到的那个：printk 不能滥用，常见做法是宏开关或全局变量决定是否输出，再把这个全局变量通过 sys 节点暴露出来，现场随时开关：

c
static int my_dbg_enable;
module_param(my_dbg_enable, int, 0644);
MODULE_PARM_DESC(my_dbg_enable, "enable verbose debug output");

#define my_dbg(fmt, ...)                                   \
    do {                                                   \
        if (my_dbg_enable)                                 \
            pr_info("mydrv: " fmt, ##__VA_ARGS__);         \
    } while (0)

现场一条命令就打开，不用重启：echo 1 > /sys/module/mydrv/parameters/my_dbg_enable。代价是 if 分支还在，只是走了空路径；比编译期宏多一次内存读，比 pr_debug 多不了多少。sys 节点在核心里随处可见，/sys/module、/sys/devices、/sys/class、/sys/kernel、/sys/firmware 下面全是。学着看别人的节点怎么写，比自己从零设计快得多。

二十、module_param：模块参数的三类权限 #

module_param 是最省事的做法：一行声明，/sys/module/<模块名>/parameters/<变量名> 自动出现。第三个参数是 sysfs 权限位，决定了这个节点能读能写：

权限 宏写法 读 写 适用
只读 S_IRUGO root + 所有人 不能 版本号、状态计数
只写 S_IWUSR 不能 仅 root 触发动作、清计数
读写 S_IRUGO | S_IWUSR root + 所有人 仅 root 调试开关、可调阈值

S_IRUGO 的本义是 S_IRUSR|S_IRGRP|S_IROTH，也就是 0444。S_IWUSR 是 0200。所以「读写」写全了是 0644：

c
static int dbg_level = 0;
module_param(dbg_level, int, S_IRUGO | S_IWUSR);   /* 0444 | 0200 = 0644 */
MODULE_PARM_DESC(dbg_level, "debug verbosity level, 0=quiet");

static unsigned int stat_rx, stat_tx;
module_param(stat_rx, uint, S_IRUGO);              /* 0444，只读 */
module_param(stat_tx, uint, S_IRUGO);

static int clear_stat;
module_param(clear_stat, int, S_IWUSR);            /* 0200，只写，写 1 触发清零 */

用数字 0644 直接写也行，但内核代码里习惯用宏，可读性好。只写节点怎么用：读它返回 EACCES，写进去的值在 set 回调里被消费。这是「触发动作」型节点的标准写法——写 1 清零计数，写别的忽略。注意这种节点不会自己复位，需要你在 set 里改回来，否则下次写同样的值看不到变化。

20.2 标准类型与自定义 set/get #

module_param 支持的类型：bool、invbool、charp、int、uint、long、ulong、ushort、short、u8~u64 等，都自动带 param_set_xxx / param_get_xxx。只做「查看/设置变量」时不需要提供任何函数，内核用通用实现。需要副作用时才上 module_param_cb：

c
static int notify_set(const char *val, const struct kernel_param *kp)
{
    int ret = param_set_int(val, kp);   /* 先完成常规赋值 */
    if (ret)
        return ret;
    schedule_work(&reconfig_work);      /* 副作用：重配硬件、清计数、唤醒工作队列 */
    return 0;
}

static const struct kernel_param_ops notify_ops = {
    .set = notify_set,
    .get = param_get_int,
};

static int reconfig_req;
module_param_cb(reconfig_req, &notify_ops, &reconfig_req, 0644);
MODULE_PARM_DESC(reconfig_req, "write 1 to trigger reconfiguration");

param_set_int 之类的通用 setter 可以复用，先套用再把副作用接在后面，这是最省事的写法。param_array 处理数组参数，module_param_array 是它的封装。

20.3 模块名与路径的坑 #

/sys/module/ 下的目录名是模块名，不是文件名：phy-rockchip-usbdp.c 编成模块后是 /sys/module/phy_rockchip_usbdp/，连字符变下划线；内建的 fdt.c 同样有 /sys/module/fdt/，因为 module_param 的实现在内建和模块两种情况下都会注册。module_param 写在 module_init 之前是可以的——参数在模块加载早期就被解析，所以启动参数 mydrv.dbg_level=1 mydrv.stat_rx=0 能生效。这也是「不改代码查看现场」的补充手段：能重启的时候直接从 cmdline 传，不能重启才靠 echo 写 sysfs。

二十一、device attribute：通过 /sys/devices 暴露变量 #

module_param 只能挂模块级。要挂到具体设备上——比如每个网口自己的收发计数——得用 device attribute。

21.1 需要什么前置条件 #

device_create_file() 要求传进来的 struct device * 已经注册过（device_register / device_add 完成）。在 probe() 里做最合适，那时设备已经在了：

c
struct device *dev = &pdev->dev;
int ret = device_create_file(dev, &dev_attr_rx_count);
if (ret)
    dev_err(dev, "failed to create rx_count attr: %d\n", ret);

21.2 三件套：show、store、ATTRIBUTE #

c
static ssize_t rx_count_show(struct device *dev,
                             struct device_attribute *attr, char *buf)
{
    struct my_dev *priv = dev_get_drvdata(dev);
    return sysfs_emit(buf, "%u\n", priv->rx_count);
}

static ssize_t rx_count_store(struct device *dev,
                              struct device_attribute *attr,
                              const char *buf, size_t count)
{
    struct my_dev *priv = dev_get_drvdata(dev);
    unsigned int val;
    int ret = kstrtouint(buf, 0, &val);

    if (ret)
        return ret;
    priv->rx_count = val;
    return count;
}

static DEVICE_ATTR_RW(rx_count);

DEVICE_ATTR_RW 展开成 dev_attr_rx_count，show / store 名字由宏拼出来，所以函数名必须是 rx_count_show / rx_count_store。只读和只写各有宏：

宏 需要实现的函数 生成的权限
DEVICE_ATTR_RO(name) name_show 0444
DEVICE_ATTR_WO(name) name_store 0200
DEVICE_ATTR_RW(name) 两个都要 0644

老代码里常见手写 DEVICE_ATTR(name, 0644, show_func, store_func)，效果一样，只是函数名不必按 name_show 拼。sysfs_emit() 是 5.10 引入的替代 scnprintf(buf, PAGE_SIZE, ...) 的写法，自带页边界检查。更早的树用 sprintf / scnprintf，那段代码就是经典的内核缓冲区溢出风险点。返回值必须小于 PAGE_SIZE（4096），这是 sysfs 的硬限制；想吐超过 4 KB 的数据，sysfs 不是合适的载体，用 debugfs 或 seq_file。

21.3 批量创建与清理 #

属性多的时候用 attribute_group 一次搞定：

c
static struct attribute *my_dev_attrs[] = {
    &dev_attr_rx_count.attr,
    &dev_attr_tx_count.attr,
    &dev_attr_status.attr,
    NULL,
};
ATTRIBUTE_GROUPS(my_dev);

/* probe 里：手动挂一组，或挂到 device_type 的 .groups 上自动创建 */
ret = sysfs_create_group(dev, &my_dev_group);

ATTRIBUTE_GROUPS(my_dev) 生成 my_dev_groups，配合 device_type 的 .groups 字段能让内核在设备注册时自动建、移除时自动删。手工建的必须手工删（device_remove_file(dev, &dev_attr_rx_count)）——这是最容易出事的地方：remove() 里漏删，设备反复插拔之后读到的是野指针。

21.4 路径怎么找 #

设备属性出现在 /sys/devices 下该设备的目录里，真实路径由总线决定——平台设备在 /sys/devices/platform/fed80000.phy/，PCI 设备在 /sys/devices/pci0000:00/0000:00:1f.2/，SPI 上的设备在 /sys/devices/platform/feb20000.spi/spi_master/spi2/spi2.0/。/sys/class/<class>/<dev>/ 和 /sys/bus/<bus>/devices/<dev>/ 都是符号链接，指回 /sys/devices 下同一个目录，三条路径访问到的是同一个属性。

驱动没有 struct device 怎么办？素材里说得直接：那就造一个。造出来的设备如果没父设备、不属于任何 class 或 bus，路径会落在 /sys/devices/virtual/。最小例子：

c
static int __init my_dbg_init(void)
{
    struct device *d = root_device_register("my_dbg");
    if (IS_ERR(d))
        return PTR_ERR(d);
    return device_create_file(d, &dev_attr_rx_count);
}

root_device_register() 造出来的设备没有父设备，路径就是 /sys/devices/virtual/my_dbg/。这条路适合「我有一堆全局状态想暴露，但没有设备对象」的场景，比为此虚构一个 platform_device 干净。

二十二、debugfs 与 sysfs 的取舍 #

两个都是内存文件系统，都能读写，但定位完全不同。

维度 sysfs debugfs
挂载点 /sys，启动时自动挂 /sys/kernel/debug，常要手工 mount -t debugfs none /sys/kernel/debug
ABI 稳定性 是，节点一旦出现在 /Documentation/ABI 里就不能随便改 不是，随版本随意增删
权限 精细到每一位，按 ABI 设计 默认只有 root
每文件大小 严格 PAGE_SIZE 无硬限制，可流式
一条属性多个值 一个文件一个值，多了要拆 一个文件随便格式化
适合 稳定接口、配置项、状态查询 内部调试、一次性信息倾泻
出厂镜像 保留 不挂载

素材里那句「以前 linux 常用的 debugfs，在使用时需要 mount 一个 debugfs，在 usb 驱动核心里就提供了该方式的使用」讲的就是这条差别——debugfs 用之前得先挂上去，这是它最大的不方便，也是它「内部工具」定位的体现。判断标准一句话：这个节点会不会被用户态程序长期依赖？ 会，走 sysfs；只是你调试时想看，走 debugfs。debugfs 的最小用法（single_open + seq_file，自动处理「一次打开多次 read」的续读问题）：

c
static int my_dbg_show(struct seq_file *s, void *unused)
{
    struct my_dev *priv = s->private;
    seq_printf(s, "rx=%u tx=%u\n", priv->rx_count, priv->tx_count);
    return 0;
}

static int my_dbg_open(struct inode *inode, struct file *file)
{
    return single_open(file, my_dbg_show, inode->i_private);
}

static const struct file_operations my_dbg_fops = {
    .owner   = THIS_MODULE,
    .open    = my_dbg_open,
    .read    = seq_read,
    .llseek  = seq_lseek,
    .release = single_release,
};

/* init 里 */
my_dbg_root = debugfs_create_dir("mydrv", NULL);
debugfs_create_file("stats", 0444, my_dbg_root, priv, &my_dbg_fops);

debugfs 的返回值坑：debugfs_create_file 在 CONFIG_DEBUG_FS 没开时返回 ERR_PTR(-ENODEV) 而非 NULL，debugfs_create_dir 失败时子文件也必须能安全调用。这些 API 被设计成「失败可以忽略」，所以正确写法是不检查返回值、尽力而为。要清理用 debugfs_remove_recursive(my_dbg_root)，传 NULL 也安全。seq_printf 的输出量不受 4 KB 限制，这正是 debugfs 相对 sysfs 的余地。

三者的完整关系：sysfs 在 /sys，稳定 ABI、一个文件一个值、PAGE_SIZE 限制；debugfs 在 /sys/kernel/debug，内部调试、需手工挂载、格式自由；procfs 在 /proc，老接口、进程与内核状态混在一起、有历史包袱。

二十三、易错点速查 #

按「症状 → 原因 → 处理」组织，方便现场查。串口一行都没有时按顺序排查：

检查顺序 命令 判读
1. 消息进缓冲区了吗 dmesg | grep 关键字 有 → 是过滤问题；没有 → 代码没跑到或已被覆盖
2. 门槛够高吗 cat /proc/sys/kernel/printk 第一个数 ≤ 7 时级别 7 出不来
3. 调用点有实体吗 grep -c <file> /sys/kernel/debug/dynamic_debug/control 0 → 编译期就没有描述符
4. 控制台注册了吗 dmesg | grep 'console \[' 只看到 bootconsole → 真控制台还没接管
5. 是不是在 earlycon 之前 dmesg | grep bootconsole 很早的日志要靠 earlycon=

pr_debug 开了不输出。 三个必查项：CONFIG_DYNAMIC_DEBUG 或 DEBUG 有没有生效（看 .config）、console_loglevel 是不是 ≥ 8、#define DEBUG 有没有排在 #include 之前。第二项最常被忽略。

日志被冲掉。 __log_buf 默认 128 KB，DEBUG 全开时早期日志会被后面的覆盖。启动参数 log_buf_len=2M（K/M/G 是二进制后缀，见 kernel-parameters 的 METRIC SUFFIXES），或编译时调 CONFIG_LOG_BUF_SHIFT。%p 打不出地址不是 bug，是 hash 保护，要真实地址用 %px，无法通过 sysctl 关闭。

改 console_loglevel 没立刻生效。 见第八章：级别是在实际打印那一刻检查的，缓冲区里积压的仍按旧门槛。

cat /proc/kmsg 把 klogd 的日志抢走了。 /proc/kmsg 和 /dev/kmsg 是消费型读取，会推进 syslog_seq。线上用 dmesg 或 dmesg -w。

dynamic debug 路径写错。 file 匹配编译时相对路径，不同版本前缀不同。最稳的方法：把 control 文件里那行第一段整段复制进查询串。另外 dyndbg 超过 1023 字符会被截，bootloader 更短。dyndbg 启动参数无效则是另一回事：它在 early_initcall 阶段才处理，之前跑的代码开不了；模块用 模块名.dyndbg= 必须等模块加载。

module_param 节点没出现。 查三件事：目录名是模块名（连字符换下划线）、/sys 挂了没有、module_param 有没有写在会被裁剪的 #ifdef 里。

device_create_file 返回失败。 多数是 dev 还没注册完就调了。放到 probe() 末尾，或者用 .groups 让内核自动建。设备反复插拔后读 sysfs 崩溃则是 remove() 里漏了 device_remove_file，用 attribute_group + .groups 可以根治。

debugfs_create_file 返回值判断错了。 CONFIG_DEBUG_FS 没开时返回 ERR_PTR(-ENODEV)，debugfs_create_dir 失败也要能安全往下走。这些 API 设计成失败可忽略，别写复杂的错误处理。

开了 CONFIG_DEBUG_* 之后问题不复现。 这些选项改变时序和内存布局，跟时序相关的竞态极易因此消失。CONFIG_DEBUG_ATOMIC_SLEEP 和 CONFIG_PROVE_LOCKING 还会额外加延迟。想复现就用最小改动。

调试开关带进了出厂镜像。 -DDEBUG、CONFIG_DYNAMIC_DEBUG、loglevel 8、debugfs 挂载，这四样都别带出去。串口刷屏只是难看，日志里的地址、寄存器值和时序信息外泄才是真问题。

版本口径。 素材不是同一套环境：printk 那篇声明 linux 5.2.8 / busybox 1.25.0 / u-boot 2016.05，里面的 rk3588 案例实机日志却是 Linux version 5.10.160、U-Boot SPL 2017.09，DEBUG 选项那篇的启动日志是 4.6.0-rc5+。宏定义、配置路径、control 文件位置都随版本动过，动手前在自己这棵树上核一遍。
