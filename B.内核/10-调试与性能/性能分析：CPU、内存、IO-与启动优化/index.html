一、性能分析的四个问题：量什么、怎么量、量到的是什么、怎么改 #

性能排查最容易滑向凭感觉。把顺序固定成四问，能省掉大半来回。

问题 要给出的东西 工具 典型错误
量什么 一个具体指标：CPU 用量、队列深度、IO 延迟、启动耗时 先想清楚指标定义 直接跑工具，数字一堆不知道信哪个
怎么量 采样方式、窗口长度、采样频率 top / perf / iostat / vmstat 窗口太短，把抖动当趋势
量到的是什么 这个数字在内核里是哪几个计数器算出来的 /proc/stat、/proc/diskstats 把 %util 当成磁盘带宽用了多少
怎么改 改动点、预期收益、验证方法 改代码 / 改参数 改完不重测，用「感觉快了」结案

第三问最容易被跳过，也是本篇重点。top 里那个 wa 不是「磁盘多忙」，iostat 里那个 %util 也不是「磁盘吞吐用了百分之多少」，这两个数字各有各的算法，认错一个方向就全错了。

CPU 用量的原始数据在 /proc/stat 的 cpu 行里（Linux v6.1，fs/proc/stat.c）：

text
cpu  user nice system idle iowait irq softirq steal guest guest_nice

十列，单位是 USER_HZ 的 tick。top、mpstat、sar、iostat -c 全都是拿两次读数相减再除总增量，区别只在分母取什么、把哪几列合并显示。搞不懂某个工具的百分比怎么来的，回到这一行自己算一遍：

bash
grep '^cpu ' /proc/stat

二、top 的 CPU 各字段含义 #

Cpu(s) 行在多核下显示的是所有 CPU 的平均值，不是最忙那个核。4 核机器上一个核跑满、其余空闲，top 显示 25%。这条要先记住，否则会得出「CPU 才 25%，不是瓶颈」的错误结论。

Tasks:   3 total,   0 running,   3 sleeping,   0 stopped,   0 zombie

跟性能判断直接相关的几处：

位置 字段 看什么
第一行 load average: 1/5/15 可运行 + 不可中断睡眠的任务数指数衰减平均
第二行 Tasks: running / zombie running 长期大于核数说明在排队
第三行 Cpu(s) 见第三章逐字段
第四行 Mem: used / free / buff/cache free 极低但 available 尚可，多半是 page cache 占着
进程表 %CPU 多核下可超 100%，200% 表示吃满两核
进程表 PR / NI PR 动态优先级，NI nice 值，NI<0 在抢 CPU
进程表 S R 运行、S 可中断睡眠、D 不可中断睡眠——D 多先查 IO

按 1 切单核视图，-H -p 展开某个进程的所有线程。top -H -p 用来找哪个线程在吃 CPU，最后那行 printf 把线程 TID 转成 16 进制，拿去和程序里打印的线程 ID 对照——这是从「哪个线程」落到「哪行代码」的桥。

bash
top
top -H -p 134
printf "0x%x\n" 74317

三、us / sy / ni / id / wa / hi / si / st 逐个说 #

字段含义本身不难，难的是每个字段在内核里到底减了哪一列。下表把 top 字段、/proc/stat 列、内核记账位置对上。

top 字段 全称 /proc/stat 列 记账位置（v6.1） 怎么读
us user user account_user_time()，nice≤0 进 CPUTIME_USER 用户态计算：加密、压缩、业务逻辑
sy system system+irq+softirq account_system_time() 按 hardirq_count()/in_serving_softirq() 分流 系统调用、内核态。top 把 irq/softirq 并进 sy，mpstat 分开
ni nice nice account_user_time()，nice>0 进 CPUTIME_NICE 被调低优先级的用户态时间
id idle idle account_idle_time()，nr_iowait==0 进 CPUTIME_IDLE 真空闲
wa iowait iowait account_idle_time()，nr_iowait>0 进 CPUTIME_IOWAIT 见第四章，别当磁盘指标
hi hardware irq irq account_system_time() 在硬中断上下文 网卡、磁盘、定时器中断
si software irq softirq account_system_time() 在软中断上下文 网络收发、BLOCK_SOFTIRQ
st steal steal account_steal_time()，paravirt_steal_clock() 提供 见第五章，虚拟机专属

ni 的判定条件是 task_nice(p) > 0。guest/guest_nice 两列不在 top 默认行里，并且已经包含在 user/nice 里：

c
/* 摘自 kernel/sched/cputime.c（Linux v6.1） */
	if (task_nice(p) > 0) {
		task_group_account_field(p, CPUTIME_NICE, cputime);
		cpustat[CPUTIME_GUEST_NICE] += cputime;
	} else {
		task_group_account_field(p, CPUTIME_USER, cputime);
		cpustat[CPUTIME_GUEST] += cputime;
	}

task_group_account_field(p, CPUTIME_USER, ...) 和 cpustat[CPUTIME_GUEST] += ... 改的是同一个 kernel_cpustat 的两个格子。所以 guest 是 user 的子集，算分母时不能再加一遍，否则时间会超。使用率公式（把 guest/guest_nice 排除）：

text
总时间 = user + nice + system + idle + iowait + irq + softirq + steal
us率   = user / 总时间
sy率   = (system + irq + softirq) / 总时间

iostat -c 的 avg-cpu 行用的就是这套分母（sysstat iostat.c 的 write_plain_cpu_stat()），只是它把 system+iowait+steal+idle 单独列。

组合起来就是诊断方向：

现象 先怀疑 下一步
us 高 业务代码计算密集 perf 采样看热点
sy 高且 si 也高 网络收发、软中断塞满一个核 /proc/softirqs、mpstat -P ALL 1 看单核
sy 高但 si 低 系统调用太频繁 strace -c -p、perf trace
wa 高 IO 慢，但先确认负载形态 读第四章
st 高 宿主机超卖 读第五章
id 高但响应慢 不是 CPU 瓶颈 查 IO 延迟和锁

四、wa 高不代表磁盘慢：iowait 的真实语义 #

iowait 的算法只有一行，在 account_idle_time() 里：

c
/* 摘自 kernel/sched/cputime.c（Linux v6.1） */
void account_idle_time(u64 cputime)
{
	u64 *cpustat = kcpustat_this_cpu->cpustat;
	struct rq *rq = this_rq();

	if (atomic_read(&rq->nr_iowait) > 0)
		cpustat[CPUTIME_IOWAIT] += cputime;
	else
		cpustat[CPUTIME_IDLE] += cputime;
}

读法：CPU 打算进 idle、并且这一时刻有任务处于「等 IO 的不可中断睡眠」状态（nr_iowait > 0），这段 idle 就记成 iowait，否则记成 idle。

nr_iowait 是 per-CPU 计数，不区分设备。CPU 在 idle 时只要这个 CPU 的 runqueue 上有 D 状态任务，时间就算 iowait。三个推论都能推翻一次错误判断：

直觉 实际情况
wa 高 = 磁盘慢 只说明「CPU 闲着 + 有任务在等 IO」，等什么设备不知道
wa 低 = 磁盘快 所有 CPU 都在忙计算时，没有一次 idle 落入 iowait，磁盘再慢 wa 也是 0
wa 能定位设备 不能，要定位得用 iostat -dx

原文有一段把机制说清楚了：系统里大多数进程是 CPU 密集型的，只有一小部分是 IO 密集型，所以即使磁盘跑到最大吞吐，wa 照样会很低。更极端的场景是「只有一个进程等 IO、其余核都在算」，iowait 只落在那个空闲等待的 CPU 上，被平均值稀释掉。

短窗口读数还有个坑。fs/proc/stat.c 里的 get_iowait_time() 会在 arch_idle_time 可用时把当前正在累积的 idle 补算进来（if (cpu_online(cpu) && nr_iowait_cpu(cpu)) iowait += arch_idle_time(cpu);）。「补算」让读数在时序上不完全一致，短窗口差分会有抖动，负值保护要写上。

wa 只当「值得继续查」的信号，不当结论。往下三层：

bash
mpstat -P ALL 1 5
iostat -dx 1 5
iotop -oP
pidstat -d 1 5

先看是不是个别核在等，再落到设备，再落到进程。

五、st 是什么：虚拟化环境下的偷时间 #

st 是运行在虚拟机里的内核被告知的「本该给你的 CPU 时间被别人拿走了」。数据不在内核自己的 tick 里，来自半虚拟化接口：

c
/* 摘自 kernel/sched/cputime.c（Linux v6.1） */
static __always_inline u64 steal_account_process_time(u64 maxtime)
{
#ifdef CONFIG_PARAVIRT
	if (static_key_false(&paravirt_steal_enabled)) {
		u64 steal;

		steal = paravirt_steal_clock(smp_processor_id());
		steal -= this_rq()->prev_steal_time;
		steal = min(steal, maxtime);
		account_steal_time(steal);
		this_rq()->prev_steal_time += steal;

		return steal;
	}
#endif
	return 0;
}

paravirt_steal_clock() 由 hypervisor 提供（x86 上是 KVM 的 MSR_KVM_STEAL_TIME 机制）。min(steal, maxtime) 那一步是关键：真实被偷的时间可以大于本时间片，内核截断到 maxtime，所以 st 是下限，不是精确值。

st 持续 > 5% 且 us+sy 都不高，说明宿主机 CPU 超卖，guest 在排队等物理 CPU；st 高且和业务高峰吻合，是邻居 VM 在抢，找云厂商或迁机器；st 为 0 但响应慢，那不是 steal，别往这里找。

容器里 st 看不出东西——容器共享宿主内核，没有独立 guest，读到的是宿主视角。要在容器里判断是否被 cgroup 限流，看 /sys/fs/cgroup/cpu.stat 的 nr_throttled 和 throttled_usec。这跟 st 是两套机制，不要混用。

六、perf 的采样原理 #

perf 不是插桩，是定时采样加栈回填。

步骤 谁做 做什么
触发 PMU 或软件定时器 采样事件计数到设定值就产生一次 PMI（performance monitor interrupt）
抓现场 内核 PMI 处理 记录当前指令指针、PID/TID、调用栈
汇总 userspace 按符号聚合，统计每条栈出现的次数

默认事件是 cycles（CPU 周期数）。-F 99 的意思就是每秒产生 99 个采样点。用 99 而不是 100 是工程习惯：100Hz 和 1000Hz/10ms 的定时器周期同步，采样点会一直落在同一相位，遇到周期性负载产生系统性偏差；99 是质数，能错开相位。

能代表时间占比的原因：每个采样点相当于在时间轴随机取一点，「某函数在栈顶」的采样点数正比于它占用的 CPU 时间。样本量足够时误差按 1/sqrt(n) 收敛。-F 99 采 30 秒是 2970 个样本——这是概率论结论，不是实测误差曲线，本文没有跑过。

频率越高越准，但代价也涨：-F 99 开销低、适合长时间跑，代价是短函数容易漏；-F 999 能抓短函数，开销明显，会干扰被测程序；-F 4999 以上逼近精确，采样中断本身成为负载，数据失真。按栈深度和频率算的精确开销需要实测，本文没有。

七、perf record / report 的完整用法 #

原文给的核心命令是这两条：

bash
perf record -F 99 -p $(pidof test1) -g -- sleep 300
perf report -g --stdio

逐参数拆开：

参数 含义 备注
-F 99 采样频率 99Hz 等价 --freq=99；也可以用 -c 按事件周期采样
-p $(pidof test1) 只采指定 PID 多个 PID 用逗号分隔；-a 采全系统
-g 记录调用栈 --call-graph 的简写
-- sleep 300 -- 之后是被测命令 sleep 300 只是采 300 秒的壳，perf 跟着它退出
report -g 报告里展开调用栈 不是「图形化」，是「按调用链展开」

-g 到底等价哪种展开模式，取决于 perf 版本和 perfconfig 里的 call-graph.record-mode，这一点本文未验证。保守做法是显式写出来：

写法 含义 前提
--call-graph fp 用帧指针回溯 目标要 -fno-omit-frame-pointer 编译，否则栈断
--call-graph dwarf 用 DWARF 调试信息展开 目标要 -g 编译
--call-graph lbr 用 Intel LBR 最后分支记录 CPU 支持且内核启用
-g graph,0.5,caller 图形化展开，阈值 0.5%，caller 视角 各发行版 perf 输出格式有出入

perf report --stdio 的输出结构：

text
# Samples: 2K of event 'cpu-clock'
# Event count (approx.): 20838464
#
# Children      Self  Command  Shared Object      Symbol
# ........  ........  .......  .................  ...........................
#
    99.87%     0.00%  test1    test1              [.] main
            |
            ---main
               functionb
               functiona

     0.13%     0.00%  test1    [kernel.kallsyms]  [k] entry_SYSCALL_64

（版式取自 perf report --stdio 的典型输出，数值为示意；本文没有该示例程序的真实采样结果，这里需要一个实测。）

Children 是该符号连同所有被调用者的采样占比，Self 是采样点正好落在该符号自身指令上的占比，Command 是进程名，Shared Object 是所属二进制或 DSO（[kernel.kallsyms] 是内核），Symbol 里 [.] 是用户态、[k] 是内核态。Self 高说明这个函数自身代码重；Children 高、Self 低说明它只是入口，在调别人。优化目标永远是 Self 高的那几行。

其他常用子命令：

子命令 用途
perf top -p PID 实时采样滚动显示热点符号，不落盘
perf stat -p PID sleep 5 只统计事件计数（cycles、instructions、cache-misses），不做栈采样
perf script 把 perf.data 转文本，喂给 FlameGraph
perf record -e sched:sched_switch 采 tracepoint 而不是 PMU 事件
perf list 列出当前内核暴露的全部事件
perf probe 动态加 kprobe/uprobe

perf top 和 perf stat 要分开用：想知道谁热用 top，想知道效率高不高用 stat。perf stat 的 IPC（instructions per cycle）低于 1 意味着在等内存，这时候 perf record 看到的热点会是一堆 cache miss，改代码不如改数据布局。

八、一次真实的 perf 分析过程 #

下面是完整链路，从一个空目录到一张火焰图。示例程序用原文给的 test1.c（两个死循环函数，functionb 的迭代次数是 functiona 的两倍）：

c
#include <stdio.h>

int functiona(void) {
    int count = 0;
    for (int c = 1; c < 20000; c++) count++;
    return count;
}

int functionb(void) {
    int count = 0;
    for (int c = 1; c < 40000; c++) count++;
    return count;
}

int main(int argc, char *argv[]) {
    for (;;) {
        functiona();
        printf("call function a\n");
        functionb();
        printf("call function b\n");
    }
    return 0;
}

编译，采样：

bash
gcc -g -o test1 test1.c
./test1 > /dev/null &
perf record -F 99 -p $(pidof test1) -g -- sleep 300
perf report --stdio --percent-limit 0.5

-g 必须加，不然 perf 只能给地址。> /dev/null 也不是可有可无的：这个程序无条件循环 printf，输出到终端会让 write() 占比飙升，采样结果测的是 tty，不是你的循环。--percent-limit 用来砍长尾，真实程序的报告动辄上万行，只看占比 > 0.5% 的就够。

这个示例能看出什么：

观察 结论
functionb 的 Self 约为 functiona 的两倍 循环 40000 vs 20000，正好两倍关系
printf 占比很低 输出被重定向到 /dev/null，write() 走空设备
main 的 Children 接近 100%、Self 接近 0 main 只是调用入口

原文结论「functionb 是主要资源消耗点」本身没错，但要补一句：这个程序没有真实的性能问题需要优化。它是死循环，functiona/functionb 都在做无副作用的 count++，-O2 以上编译器会直接把整个循环删掉。原文「优化建议」里那条 gcc -g -O3 恰恰会触发这个优化，改完再测热点就没了——不是优化生效，是代码被删了。验证前先看反汇编：

bash
objdump -d test1 | sed -n '/<functionb>:/,/ret/p'

这个坑的通则：用 -O3 验证优化效果前，先确认被测代码没被优化掉。

原文另外几条建议按可信度排一下：减少循环次数是改业务语义，只在循环次数本来就多余时成立；移除无用代码成立，但要确认真没被用；减少 printf 成立，日志是常见的隐形开销；并行化要看数据依赖，示例里两个函数无共享，能并行；-O3 成立但会妨碍后续采样，见上文。

九、火焰图与调用栈的读法 #

perf report 的文本报告够用，栈深了难读。火焰图把栈画成横条，一眼能看出时间花在哪。

bash
perf script > out.perf
./stackcollapse-perf.pl out.perf > out.folded
./flamegraph.pl out.folded > out.svg

stackcollapse-perf.pl 和 flamegraph.pl 来自 Brendan Gregg 的 FlameGraph 仓库，Perl 脚本，不需要编译。折叠后每行一条完整调用栈，分号分隔，最后一列是采样数（下面是 FlameGraph 仓库 README 的示例格式）：

text
main;functiona 1201
main;functionb 2400
main;printf 85

好处是 out.folded 是纯文本，可以直接 grep 出感兴趣的栈再单独出图：

bash
grep functionb out.folded | ./flamegraph.pl > functionb.svg

读图的规则：横轴宽度是采样占比而不是时间顺序（除非 --flamechart）；从下往上是调用深度，最底下是根；某个框很宽且上面没有更宽的框，它就是热点，宽度基本等于它的 Self；某个框很宽但上面全是同样的窄框，是链路开销，往下查；出现 [unknown] 说明栈断了。

栈断了是最常卡住的地方，三种原因对应三种修法：

现象 原因 修法
用户态栈只有一层 [unknown] 没编译进帧指针，fp 回溯失败 用 -fno-omit-frame-pointer 重编，或改 --call-graph dwarf
内核态栈显示 [kernel.kallsyms] 但没函数名 缺 debuginfo 装 kernel-debuginfo（RHEL 系）或 linux-image-*-dbgsym（Debian 系）
Java/Python 帧显示成地址 需要语言级栈展开 --call-graph dwarf，或配合 perf inject --jit

反转图、冰柱图、差分图：

bash
./flamegraph.pl --reverse out.folded > out-reverse.svg
./flamegraph.pl --inverted out.folded > out-icicle.svg
./difffolded.pl before.folded after.folded | ./flamegraph.pl > diff.svg

十二、IO 性能的三个指标：IOPS、吞吐、延迟 #

硬盘厂商的性能报告一般只给两个指标：响应时间（Response Time）和数据传输率（Data Transfer Rate，也叫吞吐率）。这两个加上 IOPS，就是 IO 性能的三根柱子。

指标 定义 单位 谁关心
IOPS 每秒完成的 IO 操作次数 次/秒 数据库、小文件、随机访问
吞吐（DTR） 每秒传输的数据量 MB/s、GB/s 大文件、备份、流式读写
延迟 单个请求从发出到完成的耗时 μs、ms 交互式应用、实时性要求

三者互斥。吞吐 = IOPS × 单次 IO 大小；队列饱和时延迟 = 队列深度 ÷ IOPS。想把吞吐拉满就得放大 IO，IOPS 会掉；想把延迟压低就得把队列深度降到 1，吞吐上不去。

接口带宽这个上限先算清楚：SATA 3.0 标称 6 Gb/s，换成字节是 600 MB/s 量级（b 是比特，除以 8 才是字节，600 已经去掉编码开销）；PCIe 3.0 x4 约 32 Gb/s，即约 4 GB/s 量级，NVMe 常见配置。

原文给的实测参考值（测试工具与设备型号原文未标注）：HDD（SATA 3.0）顺序吞吐 100~200 MB/s、IOPS 约 160；SSD（SATA）4K 随机读 36 MB/s，约 9000 IOPS；SSD 写入 65 MB/s，约 1.6 万 IOPS。

36MB / 4KB = 9000 这个换算是原文的算法：AS SSD 的 4K 指标给的是「每秒随机读 4KB 块能读多少 MB」，除以 4KB 就是 IOPS。任何工具只要给 4K 带宽，都能这么反推 IOPS，不需要额外字段。

延迟的量级差两三个数量级：SSD 几十微秒，HDD 几毫秒到十几毫秒。所以「换个盘」对随机 IO 的影响远大于「换个文件系统」。

IOPS 的细分口径，压测和买盘时必须对齐，否则测出来的数没法和指标比：

口径 负载 适用
Total IOPS 混合读写、顺序随机混合 贴近真实业务，一般以此为准
Random Read IOPS 100% 随机读 读密集业务
Random Write IOPS 100% 随机写 写密集业务、日志盘
Sequential Read IOPS 100% 顺序读 大文件扫描、备份恢复
Sequential Write IOPS 100% 顺序写 日志追加、数据落盘

服务端场景关心随机 IOPS。原因是服务器上的并发意味着很多进程和请求同时访问，它们的数据很难在磁盘上挨着放，随机读写才是核心指标。反过来单机跑一个大文件拷贝时顺序吞吐才是关键，用同一套指标评两块盘会得出相反结论。

数量级的落差值得摆出来：一块 HDD 约 160 IOPS，SSD 在 10000~75000，而 2GHz 以上的 CPU 每秒二十亿个周期。就算一条读写指令要几十个周期，CPU 的指令吞吐和设备的操作吞吐之间也差好几个数量级。这就是「瓶颈在 IO」成立的原因——不是 IO 慢，是 IO 和 CPU 差得太远，等不起。

十三、iostat 的输出怎么读 #

原文用的命令是：

bash
iostat -dx 1
iostat -dx 1 /dev/sdb
iostat -d -p ALL 1
iostat -dxm 1

-d 只要设备报告，-x 出扩展字段，1 是每秒一次，-m 单位换 MB/s。扩展字段来自 sysstat iostat.c 的 write_disk_stat_header()：

字段 含义 单位
r/s / w/s 每秒读 / 写请求数 次/秒
d/s / f/s 每秒 discard / flush 请求数 次/秒
rkB/s / wkB/s 每秒读 / 写数据量 kB/s
rrqm/s / wrqm/s 每秒被合并的读 / 写请求数 次/秒
%rrqm / %wrqm 合并率 %
r_await / w_await 读 / 写请求平均等待时间 ms
d_await / f_await discard / flush 平均等待时间 ms
rareq-sz / wareq-sz 读 / 写请求平均大小 kB
aqu-sz 平均队列长度（旧名 avgqu-sz） 请求数
avgrq-sz 平均请求大小（旧名，见下） 扇区数
%util 设备忙时间占比 %
svctm 平均服务时间（已废弃） ms

原文用的是老版列名 avgrq-sz/avgqu-sz/svctm。新版 sysstat 改成 rareq-sz/wareq-sz/aqu-sz，svctm 直接删掉了——不是无意义的折腾，因为它的算法本身有问题，留着会误导人。

三个重点字段的算法，都能和 sysstat 源码对上。r_await 是「累计 tick 增量 ÷ IO 次数增量」，%util 是「设备忙的 tick 增量 ÷ 间隔」：

c
/* 摘自 sysstat iostat.c，write_ext_stat() */
/* r_await */
xios.r_await = (ioi->rd_ios > ioj->rd_ios) ?
	       (ioi->rd_ticks - ioj->rd_ticks) /
	       ((double) (ioi->rd_ios - ioj->rd_ios)) : 0.0;

/* 摘自 sysstat rd_stats.c，compute_ext_disk_stats() */
xds->util  = sdc->tot_ticks < sdp->tot_ticks ?
	     0.0 :
	     S_VALUE(sdp->tot_ticks, sdc->tot_ticks, itv);

短格式 -s 给的 await 把读、写、discard 三类 tick 加一起：

c
/* 摘自 sysstat rd_stats.c，compute_ext_disk_stats() */
xds->await = (sdc->nr_ios > sdp->nr_ios) ?
	((sdc->rd_ticks - sdp->rd_ticks) + (sdc->wr_ticks - sdp->wr_ticks) + (sdc->dc_ticks - sdp->dc_ticks)) /
	((double) (sdc->nr_ios - sdp->nr_ios)) : 0.0;

tot_ticks 就是 /proc/diskstats 的 io_ticks 列，内核由 update_io_ticks() 维护，含义是这个块设备队列非空的时间，单位毫秒。所以 %util = 100% 的真实语义是「这段时间里设备队列一直有请求」，不是「设备吞吐达到额定值」。

由此有个必须记住的判断：对能并行的设备 %util 会误导。一块 NVMe 队列深度 64，8 个请求并发时 %util 就是 100%，但离满载还远；HDD 队列深度 1，%util 100% 就是真满了。判断饱和要看 aqu-sz 配合 await 是否上升，单看 %util 会误判。

-p ALL 和 -x 一起用时注意：分区的 rkB/s 加起来等于整盘，但 %util 不能加，会重复计算。

十四、块层的观测点：从 VFS 到设备队列 #

一次写请求往下走要过好几层，搞清楚在哪层观测，才知道看到的数字是什么。

text
应用 write() -> VFS -> 文件系统 -> page cache -> 块层提交 -> IO 调度器 -> 设备队列 -> 完成

各层的观测点：VFS 用 perf/strace/bpftrace；文件系统用 tracepoint ext4:*；page cache 看 /proc/meminfo 的 Dirty/Writeback；块层提交看 block:block_bio_queue；IO 调度器看 /sys/block/<dev>/queue/scheduler；设备队列看 block:block_rq_issue；完成看 block:block_rq_complete。

page cache 这层最容易误判：write() 返回时数据只到了 page cache，没到盘。应用层测出来的写延迟是内存延迟，跟磁盘无关。真实落盘时间要看 Dirty/Writeback 的变化，或者用 fsync() 把这一层打通再测。

%util 的数据源 update_io_ticks()，逻辑很短：

c
/* 摘自 block/blk-core.c（Linux v6.6） */
	stamp = READ_ONCE(part->bd_stamp);
	if (unlikely(time_after(now, stamp))) {
		if (likely(try_cmpxchg(&part->bd_stamp, &stamp, now)))
			__part_stat_add(part, io_ticks, end ? now - stamp : 1);
	}
	if (part->bd_partno) {
		part = bdev_whole(part);
		goto again;
	}

读法：bd_stamp 记上次队列从空变忙的时刻。end=true（一次 IO 结束）时若 now > stamp，把 now - stamp 记进 io_ticks；end=false（开始一次 IO）时先加 1，防止零宽度区间。最后的 if (part->bd_partno) 段是分区向上翻到整盘，所以分区的 IO 也会算进整盘的 io_ticks。

await 的分子来自 blk_account_io_done()，注意它最后加的那一项：

c
/* 摘自 block/blk-core.c（Linux v6.6） */
	if (blk_do_io_stat(req) && req->part &&
	    !(req->rq_flags & RQF_FLUSH_SEQ)) {
		const int sgrp = op_stat_group(req_op(req));

		part_stat_lock();
		update_io_ticks(req->part, jiffies, true);
		part_stat_inc(req->part, ios[sgrp]);
		part_stat_add(req->part, nsecs[sgrp], now - req->start_time_ns);
		part_stat_unlock();
	}
}

起点 req->start_time_ns 在请求分配时就打上了，不是提交给驱动时。这决定了 await 的语义：它包含了在块层排队的时间。设备服务时间要看另一个字段 io_start_time_ns，它在 blk_mq_start_request() 里打，并且只在 QUEUE_FLAG_STATS 置位时才打——这个标志由块层延迟统计控制，平时不开：

c
/* 摘自 block/blk-mq.c（Linux v6.6） */
	trace_block_rq_issue(rq);

	if (test_bit(QUEUE_FLAG_STATS, &q->queue_flags)) {
		rq->io_start_time_ns = ktime_get_ns();
		rq->stats_sectors = blk_rq_sectors(rq);
		rq->rq_flags |= RQF_STATS;
		rq_qos_issue(q, rq);
	}
	/* ... */
区间 从哪到哪 谁在用
now - start_time_ns 请求分配到完成 /proc/diskstats 的 nsecs[]，iostat 的 await
now - io_start_time_ns 交给驱动到完成 blk_stat 延迟桶，iostat 看不到

tracepoint 是这块最精确的观测点，block_rq_issue 和 block_rq_complete 一对就能算真实设备延迟：

bash
cd /sys/kernel/debug/tracing
echo 1 > events/block/block_rq_issue/enable
echo 1 > events/block/block_rq_complete/enable
echo global > trace_clock
cat trace_pipe

输出格式由 kernel/trace/trace_output.c 的 lat_print_timestamp() 决定（v6.1）。trace_pipe 每行前面的时间戳精度到微秒或纳秒，两次相减就是一次 IO 的真实耗时；trace_clock 切到 global 是为了避免 per-CPU 时钟之间的偏移。

块层相关的 tracepoint 一览：

tracepoint 触发点 能测什么
block:block_bio_queue bio 进入块层 文件系统交给块层的时刻
block:block_rq_insert 请求进调度器队列 排队开始
block:block_rq_issue 请求交给驱动 排队结束，设备开始干活
block:block_rq_complete 请求完成 设备干完
block:block_bio_complete bio 完成，回给文件系统 全链路结束

设备服务时间是 rq_complete 减 rq_issue；块层排队时间是 rq_issue 减 rq_insert。两个数合起来才是 iostat 里的 await，混着看就分不清该换盘还是该减并发。tracefs 的用法在《内核调试：printk、动态调试与调试接口》里更细。

十五、IO 延迟的构成：排队、寻道、传输 #

一次 IO 拆成三段：总延迟 = 排队时间 + 寻道/定位时间 + 传输时间。排队由队列深度、调度器、并发数决定，手段是降并发、增大队列、换调度器；寻道/定位由磁头移动距离和旋转延迟决定，手段是顺序化、预读、数据布局，只对 HDD 成立；传输是 IO 大小 ÷ 接口带宽，手段是放大 IO、升接口，对 SSD 也成立但很快不是瓶颈。

HDD 的寻道和旋转是主项。一次随机 4K 读，寻道几毫秒、旋转半圈几毫秒，传 4KB 只需微秒级，延迟几乎全在定位上。这解释了为什么 HDD 的 IOPS 只有 160 左右——机械结构每秒只能定位这么多次。顺序读时定位几乎为零，吞吐能到 100~200MB/s。

SSD 没有寻道，但有另外三样东西拖延迟：

机制 影响 观测方法
读-改-写 小粒度覆盖写要先擦再写，写放大 wkB/s 与实际写入量对比
垃圾回收（GC） 后台 GC 抢带宽，延迟出毛刺 await 的 P99 与 P50 差距
TRIM/discard d/s 不为零会占设备时间 iostat -dx 的 d/s、dkB/s

SSD 的延迟分布是双峰的：P50 几十微秒，P99 会到毫秒级。看平均 await 会把这个尾巴吃掉，判断体验要找 P99——用块层延迟桶或者自己从 tracepoint 算。

排队这段的定量关系是 Little's Law：aqu-sz = IOPS × r_await(秒)，即「平均队列长度 = 到达率 × 平均停留时间」。这个式子能在两个已知量之间推第三个。iostat 给出 r/s+w/s = 1000、aqu-sz = 4，那平均每个请求在块层待了 4ms。反过来 await 是 8ms、IOPS 还是 1000，aqu-sz 必然是 8 左右——对不上说明有请求没被统计（blk_account_io_done() 里那条 RQF_FLUSH_SEQ 判断会跳过 flush 序列），或者采样窗口错位。

区分五种延迟，落到不同工具：

想测的延迟 怎么测
应用感知延迟 应用自己打点，从 write() 进入到返回（只到 page cache）
应用感知落盘延迟 写完 fsync() 再打点
块层延迟（含排队） iostat 的 await，或 tracepoint rq_insert 到 rq_complete
设备服务延迟 tracepoint rq_issue 到 rq_complete
文件系统延迟 bpftrace 挂 vfs_write，或 tracepoint ext4_sync_file_enter

write() 快、fsync() 慢是典型特征，说明瓶颈在回写链路而非传输链路，往 vm.dirty_ratio、vm.dirty_background_ratio 方向查，机制在 03-内存管理。

十六、怎么判断瓶颈在 CPU 还是 IO #

用排除法，成本从低到高：

步骤 命令 判据 结论
1 uptime load 长期 > 核数 有排队，继续
2 vmstat 1 r 高 / b 高 r 高 → CPU；b 高 → IO 或锁
3 top 按 1 是否个别核 100% 其他核闲 单核瓶颈，查软中断或单线程热点
4 top wa 是否高 高 → 有等待，但不能据此定设备
5 iostat -dx 1 aqu-sz > 1 且 await 上升 设备侧饱和
6 pidstat -d 1 谁的 kB_wr/s 最大 定位到进程
7 perf record -F 99 -g Self 热点在业务还是内核 内核态多 → 系统调用/IO 路径
8 perf stat IPC < 1 在等内存，不是等 IO

load average 必须先澄清一次：它统计「可运行任务数 + 不可中断睡眠任务数」的指数衰减平均，两者权重相同。所以一个大 cp 能拉高 load，一堆等 IO 的 D 状态也能。

c
/* 摘自 kernel/sched/loadavg.c（Linux v6.6） */
/* The global load average is an exponentially decaying average of nr_running +
 * nr_uninterruptible.
 *
 * Once every LOAD_FREQ:
 *
 *   nr_active = 0;
 *   for_each_possible_cpu(cpu)
 *	nr_active += cpu_of(cpu)->nr_running + cpu_of(cpu)->nr_uninterruptible;
 *
 *   avenrun[n] = avenrun[0] * exp_n + nr_active * (1 - exp_n)
 */

exp_n 就是衰减系数：1 分钟对应的 EXP_1、5 分钟 EXP_5、15 分钟 EXP_15，所以三个数是同一个 nr_active 用不同衰减速度滤波的结果，不是三个独立的滑窗。

归一化后再判断。nproc 返回可用核数，受 cgroup cpuset 限制时会更小；/proc/cpuinfo 里数 processor 得到物理可见核数，两者不一致时按小的算：

bash
nproc
cat /proc/loadavg
load / 核数 解释
< 1 没有可运行任务排队（D 状态另算，但仍计入 load）
1~2 轻度排队
> 2 持续 有明显排队，往下分 CPU 还是 IO

把常见组合直接对号：

us sy wa r b aqu-sz 判断
高 低 低 高 低 低 纯计算瓶颈，看 perf
低 高 低 中 低 低 系统调用频繁，strace -c
低 中 高 低 高 高 IO 饱和，iostat -dx
高 高 中 高 高 高 混合瓶颈，先降并发

最后一行最容易踩：全核都在算时 CPU 从不 idle，iowait 没有机会累加，磁盘再慢 wa 也是 0。这时候看 b 和 iostat 的 await，不能看 wa。

十七、启动时间的测量：从哪个时刻算起 #

第一个问题是「从哪算到哪」。起止点不定死，后面所有数字都没法比。上电复位需要硬件层面（示波器或 GPIO 打点）观测，是最严格的口径，绝大多数场合测不了；bootloader 开始看串口第一行输出，uboot 和 kernel 都从这里往后算；kernel 第一条 printk 用 printk_time 打开后的首条日志时间戳，常用于内核内部优化；init 跑完、服务可用由业务探活脚本判定，是用户能感知的口径。

多数项目用第三个到第四个，即「kernel 时间戳到业务 ready」，因为这个区间完全在软件可控范围内。

方式一：printk_time（精度一般）

在 menuconfig 的 Kernel hacking -> printk and dmesg options -> [*] Show timing information on printks 打开，对应 CONFIG_PRINTK_TIME=y。开启后每条 printk 前面带上时间：

text
[    0.000000] Booting Linux on physical CPU 0x0
[    0.152341] Memory: 480000K/524288K available
[    0.301254] clocksource: Switched to clocksource arch_sys_counter

原文对这种方式的保留意见很明确：精度不太高，而且打开 printk_time 本身影响启动时间——每行多一次时间读取加格式化。粗筛可以用，最后的 10ms 级优化不行。

printk 走串口时本身就是最大开销之一。按 115200bps、8N1（每字节 10 bit）算，80 字符一行要 6.94ms，加上格式化约 10ms 量级。几十条日志就是几百毫秒。原文提到「优化 log 等级」正是在打这块。

原文的推荐是 ckermit 套 minicom，把 log 重定向到文件，由串口工具在每行打时间戳，这样时间戳不占内核时间。装好之后写 ~/.kermrc：

方式三：内核内的 initcall_debug

returned 0 after 104 usec 就是那段代码的耗时，不用自己算。代价是每条 initcall 两行日志，几千个 initcall 就是几千行串口输出。配套脚本 scripts/bootgraph.pl 能把它画成时序图，适合看整体分布，不适合看细节（dmesg | perl scripts/bootgraph.pl > boot.svg）。

十八、启动优化的常见瓶颈与手段 #

原文把 kernel 启动分成三段：uboot 引导 -> kernel 载入启动 -> 挂载文件系统(跑初始化脚本)。原文的硬件平台是理解后面所有数字的前提：nor flash 16MB 放 uboot 与 kernel，eMMC 4GB 放文件系统，SoC 是 ARM Cortex-A9 的 Freescale i.MX6 系列。在这个平台上 uboot 要把 uImage 从 nor flash 搬进 RAM。原文确认的进度是「从 2s 优化到 1.3s」这一段过程，最终目标 2s 以内。

第一段：bootloader #

原文对这段很坦率——作者本人对 uboot 不算熟，只给了几个方向：去掉 bootdelay（最低也是 1s，必做，收益确定）；去掉 uboot 里不必要的驱动初始化（看驱动数量，要确认不影响救援通道）；给 uboot 打开 MMU 和 cache（拷贝和解析都会快，需按平台确认支持）；跳过 kernel 头部 0~4KB 直接从主启动部分下内存（少读一段，但改了 uImage 格式，校验会失败，谨慎）。bootdelay 那 1s 是这段里最稳的收益，它纯粹是等待倒计时；其余几项的收益都要实测，原文没给数字。

原文还提到 uImage 裁剪后 2.9MB，从 nor flash 搬到 RAM 走的 memcpy/memset 换成手写汇编能省时间。思路对（汇编可以针对 cache line 和总线宽度优化），量级按「时间 = 数据量 ÷ 带宽」估：100MB/s 下 2.9MB 约 29ms，200MB/s 下约 14.5ms。原文没给 nor flash 实际带宽，所以 2.9MB 拷贝的绝对耗时本文没有实测。把 memcpy 优化 20%，在 29ms 里省约 6ms——原文说「优化几毫秒」，和这个量级一致。

第二段：kernel #

这段是最大头，拆成四件事。

（1）压缩算法。 uImage 是压缩过的，启动时要先解压到内存。原文的对比表：

text
Alogrithm          % remaining     MB/s Encoding  MB/s Decoding
gzip                         13.4                      21              %2
lzop                         20.5                     135               410
bz2                          XX                         XX                XX

（原文实测，测试平台与压缩级别未标注。）gzip 那一行解码速率栏写的是 %2，明显是录入错误，本文不猜具体值。bz2 那行原文自己标了 XX，并注明「由于历史悠久，已经忘却」。

能读出的结论：lzop 压缩率更低（剩余 20.5% vs 13.4%），但解码快将近 20 倍（410 vs 21）。原文选 lzop 的依据是「空间完全不用考虑，很足够」——16MB nor flash 放 2.9MB kernel 确实不紧张。

量化一下：假设解压后镜像 8MB，gzip 按 21MB/s 要 380ms，lzop 按 410MB/s 要 20ms。这里需要一个实测：本文没有 8MB 这个镜像大小的依据，也没在目标板上测过两种算法的实际启动耗时差。原文那句「解压速率是 gzip 的四倍不到」也和表里的 410/21 ≈ 19.5 倍对不上——要么是笔误，要么指另一组测量。

压缩算法由内核配置决定，对应 Kernel setup -> Kernel compression mode 里的 LZO / GZIP / XZ / LZ4 / ZSTD 选项。bz2 在较新内核里已被移除（原文自己也提到「貌似现在已经不支持 bz2 了」）：v6.1 的 lib/decompress_inflate.c 里只剩 zlib 解压路径，bunzip2 的实现不见了。

（2）lpj（loops_per_jiffy）校准。 lpj 是内核启动时校准出的「每个 jiffy 内 CPU 能跑多少轮空循环」，用于延时。校准本身有耗时，启动参数 lpj=395264 直接给已知值就能跳过。值因硬件而异，原文的做法是「通过打 log 去判断」，dmesg | grep -i 'Calibrating delay' 能看到形如 Calibrating delay loop... 790.52 BogoMIPS (lpj=395264) 的一行，把 lpj=395264 填进去。跳过校准能省多少取决于平台的校准实现，原文说「这货就是 kernel 启动时 check 一下子」，没给数字，本文也没有实测。

（3）initcall 逐个计时。 这是原文认为最值得做的一步，因为「占用时间最长的就是启动 kernel 时加载各个模块、跑各个 probe 所占用的时间」。原文给的办法是改 init/main.c 的 do_initcalls()：

c
static void __init do_initcalls(void)
{
	initcall_t *fn;

	for (fn = __early_initcall_end; fn < __initcall_end; fn++){
	//  printk("==========================now will call : %p\n",fn);
		do_one_initcall(*fn);
	}
}

把注释掉的 printk 打开就能打出每个 initcall 的函数地址，这行会调到所有注册在 module_init 段里的函数，也就是所有编译进内核的模块。办法能用，但有三个问题：打的是地址不是名字，要查 System.map 反查；只有开始没有结束，得自己算两地址之间的时间差；两条日志 × 几千个 initcall，串口输出把优化目标本身淹了。这三条都可以用 initcall_debug 内核参数绕过——它自带函数名和耗时，内核自己算差，而且可以只在可疑区间打开。

拿到 initcall_debug 的数据后，按耗时分档处理：单条 > 100ms 优先查（基本都是大驱动 probe），10~100ms 逐个看是不是必需的，< 10ms 先放过（除非数量极大）。

（4）裁剪和延后加载。

手段 原理 代价
裁掉用不到的驱动和子系统 减少 initcall 数量 功能缺失，要确认产品不需要
模块改成可加载，文件系统起来后 modprobe 从启动关键路径移出 依赖它的服务要延后
降低 log level 减少串口输出 出问题时看不到早期日志
去掉开机 logo 少一次 framebuffer 写 无
关掉 CONFIG_DEBUG_* 系列 这些选项会加校验和打印 调试能力下降

「把无用模块搬入文件系统启动」原文叫「类似于延时启动」，本质是把 initcall 从 kernel 阶段挪到文件系统阶段。它不减少总工作量，只挪位置——如果统计口径是「到文件系统挂载完成」，这么做没有收益，甚至因为多一次 modprobe 的进程开销而变慢。口径要先定死（见第十七章），否则会做出「看起来快了」的优化。

第三段：文件系统与 init #

原文在这段的自我评价是「水太深，老衲用的还是比较旧的」，只给了一条结论：业内公认启动最快的是 systemd，因为它是并发启动。

这条结论在通用发行版上成立，但原文的板子是嵌入式平台。sysvinit/inittab 串行跑 /etc/init.d/rcS，改动成本低，嵌入式常见；busybox init 同上但更轻，用于极简系统；systemd 按依赖关系并发加 socket 激活，功能完整但二进制和依赖较重；自己写的单进程 init 直接干完所有初始化，可控性最高。在资源受限的板子上，「自己写一个只跑必需步骤的 init」往往比换 systemd 更快，因为 systemd 自己加载和解析单元文件的耗时就能超过你的全部初始化。原文结论在通用发行版上对，在嵌入式上要自己量。

原文对文件系统部分的评价是「各个文件系统不同，启动 sequence 也不一样」，没展开。真要往这里做，能动的地方：

手段 收益 风险
rootfs 换 initramfs（cpio 直接解进内存） 省掉一次块设备挂载和读盘 占内存
ext4 换 squashfs（只读） 挂载快，读取有压缩 不能写
关掉 fsck 强制检查 省几秒 文件系统损坏时起不来

这些的收益都必须实测，原文没有数字，本文也没有。

十九、把优化做到 2 秒以内：每 10ms 的取舍 #

这一段是原文最有价值的部分，因为它描述的是从「还能优化点」进入到「每个 10ms 都要抠」的阶段。秒级优化是砍功能、换算法，心态是「这个不要了」；百毫秒级是调参数、换配置，「这个从 200ms 降到 150ms」；到了 10ms 级，就变成逐条日志、逐个 probe，「这条日志要不要打」。

10ms 级能动的具体动作：

动作 典型收益 怎么验证
删掉一条启动日志 约 7ms（80 字符 ÷ 11520 字节/秒） 数串口输出字符数 × 位宽 ÷ 波特率
printk 延后到 console 初始化之后 几百毫秒 对比 console_init 前后的时间戳间隙
probe 里加「设备不存在就早退」 该 probe 全部耗时 initcall_debug 的 after N usec
mdelay() 换 msleep() 取决于 delay 时长 看 probe 内部
合并两次 I2C/SPI 读 一个总线事务周期 逻辑分析仪或驱动内打点
关掉不必要 sensor 的轮询初始化 几十毫秒 initcall_debug

几条按「每 10ms 抠」的实操规则。

规则一：一次只改一处，改完立刻重测。 采样至少 5 次，取最小值和最大值：

bash
for i in 1 2 3 4 5; do
    grep -o '^\[ *[0-9.]*\]' ~/session | tail -1
done

看最小值比看平均值有用：抖动来自不可控因素（DDR 训练、flash 擦除、cache 状态），最小值才反映代码路径最短能到多少。

规则二：把测量和被测分开。 打开 initcall_debug 之后系统会慢几百毫秒，测出来的绝对值没意义，只能看相对排序——哪个 initcall 排前面。要找绝对值就得关掉调试重测，而这又回到「看不见细节」的矛盾。解法是二分：先看排序挑出可疑项，再针对单项做精细测量。

规则三：串口是最大的隐形开销。 115200bps、8N1 每字节 10 bit，即 11520 字节/秒，80 字符一行 = 800 bit = 6.94ms。这里有两个容易犯的算错法：把「字节/秒」当成「行/秒」会算成 69.4ms（正确是 80 字节 ÷ 11520 = 6.94ms）；忽略 printk 格式化开销（几百微秒，也计入启动时间）。

一次 80 字符日志约 7ms（计算值，非实测），加上格式化约 10ms 量级。一千条日志就是 7 秒，远超 2 秒目标。这也是「优化 log 等级」在原文里被列成手段而不是可选项的原因。串口输出的字符数不用估，数一下就行：

bash
awk '{print length($0)}' ~/session | awk '{s+=$1} END {print s " bytes" }'

规则四：区分「并行能省的」和「串行省不了的」。 独立设备的 probe（多个 I2C 传感器）能并行省时间，但要改 probe 框架；有依赖链的初始化（时钟 -> 电源 -> 总线 -> 设备）省不了，只能缩短每一环；同一 I2C 控制器上的设备省不了，总线本身串行。i.MX6 是双核或四核 Cortex-A9，理论上能并行化独立 probe，但内核的 do_initcalls() 是串行遍历的，要并行得自己改，还要处理「后一个 initcall 依赖前一个副作用」这种隐藏依赖。接近 2 秒目标时引入并行 initcall，增量收益和回归风险不成比例。

规则五：接受测不准。 到了 10ms 级，测量工具的不确定度已经和优化目标同量级：串口 FIFO 和 PC 侧缓冲带来毫秒级抖动，DDR 训练和初始化每次上电都不同，eMMC/nor flash 的擦除状态首次和之后不同，温度和电压则是慢变量、影响时钟稳定性。对策是多次采样取最小值，并记录测试条件（温度、上次断电时长、flash 是否有历史数据）。原文说「每 10ms 的优化太让人吐血了」，吐血的原因一半是优化难，一半是测不准。

二十、一个性能排查的通用顺序 #

把前面所有工具串成固定流程，遇到问题照着走：

序号 目的 工具 输出
1 确认现象 业务指标、日志 「什么操作慢了多少」
2 全局概览 uptime、vmstat 1、top 瓶颈大类：CPU / 内存 / IO / 锁
3 定位到核 top 按 1、mpstat -P ALL 1 单核还是全核
4 定位到进程 top -H -p、pidstat -u -t 哪个线程
5 定位到设备 iostat -dx 1 哪块盘，aqu-sz/await 什么水平
6 定位到代码 perf record -F 99 -g、perf report Self 热点函数
7 确认因果 对照实验：关模块/降并发/换参数后重测 指标变化
8 固化 测量脚本和基线数据入库 下次能比

每一步都有「该往下走还是该回退」的判断：第 2 步看不出瓶颈说明现象描述有问题，回第 1 步；第 4 步找不到热点线程说明时间在等不在算，改走 IO 路径或锁分析；第 5 步 %util 100% 但 aqu-sz 很低说明设备能并行、不是瓶颈，回第 6 步看 CPU；第 6 步热点全在内核说明是系统调用或中断路径，配合块层 tracepoint 往下追；第 7 步改完没变化说明判断错了，回退改动从第 2 步重来。

两条纪律。不要同时改两处——改两处后指标变好，你不知道是哪处起的作用；变差，你不知道该回退哪处。每次测量都记录环境——内核版本、CPU 型号、内存大小、负载情况、采样窗口，少一个都会让后续对比失效。原文那些实测数字之所以能对照，就是因为每段都写了「96 核」「251G 内存」这类环境信息。
