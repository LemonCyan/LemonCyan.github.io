一、为什么中断要分成上半部和下半部 #

先看场景。你用 U 盘拷大量数据，同时敲键盘，屏幕过半秒才出字符。根因在于中断 handler 是关中断执行的：它跑多久，本地 CPU 就对外设聋多久。

Linux 是多进程并发的系统，外设中断随时打断任务调度。中断函数耗时一长，实时性和并发性一起掉。为保证实时性，中断服务程序必须短；可现实中某些中断来了就是一堆活。两头堵，于是内核把中断服务程序劈成两段：

  • 顶半部（top half）：只做最少、最急的活。读中断状态、清中断标志、ack 设备、把数据从硬件 FIFO 搬到内存，然后「登记中断」——把下半部处理程序挂到队列里，返回。
  • 底半部（bottom half）：中断处理的大部分工作。几乎做了中断处理程序的所有事情，但是开着中断跑。

顶半部跑完，底半部就在内核调度下执行。有更高优先级的任务等着就先跑它，或者拖到系统空闲时补。前文分析过的 request_threaded_irq 注册的 primary handler 与 threaded handler 都属于顶半部（threaded 靠线程化把顶半部搬进进程上下文，本质仍是响应中断的第一现场）。本篇的三种下半部是：softirq、tasklet、workqueue。

补一段老历史，不然看不懂接口为什么叫 bh。早期 Linux 只有一个下半部机制，简称 BH（bottom half），简单好用但性能差：全局 32 个槽位、跑在一个 CPU 上要抢一把全局锁。2.5 开发系列里 BH 被拆掉，换成 softirq + tasklet；中间试过的 task queue 最后也没了。BH 这个缩写留在 local_bh_disable 这组接口名里——这就是你今天看到 bh 却找不到 BH 结构体的原因。

二、下半部的三种机制与选择依据 #

网卡例子能把三种机制的区别一次讲透。SMP 系统，网卡 FIFO 收到数据（半满时可由软件设定），通过 IRQ 信号送到中断控制器，控制器分发给 Processor A 或 B。三种机制下 NIC 的中断处理流程长这样：

text
纯 hardirq（没有下半部）：
  关中断：mask and ack interrupt controller -> ack NIC -> copy FIFO to ram
          -> handle Data in the ram -> unmask interrupt controller
softirq：
  关中断：mask and ack interrupt controller -> ack NIC -> copy FIFO to ram
          -> raise softirq -> unmask interrupt controller
  开中断：在 softirq 上下文中做 handle Data in the ram
tasklet：
  关中断：mask and ack interrupt controller -> ack NIC -> copy FIFO to ram
          -> schedule tasklet -> unmask interrupt controller
  开中断：在 softirq 上下文中（走 TASKLET_SOFTIRQ）做 handle Data in the ram

先看第一种。A 接了这个中断，handler 在 A 上跑，A 的本地中断是关的，网络数据还在源源不断到来。只要 handler 不去 ack NIC 寄存器，NIC 就不会触发下一次中断——还好它总在开头 ack。ack 之后 NIC 有再次触发的能力了，FIFO 又满、又触发，但中断控制器还没 unmask，就算旁边站着空闲的 B，中断也送不进去。结果是 FIFO 填满、数据溢出，或者朝对端发拥塞信号，系统整体性能被拖垮。（新控制器没有 mask/umask 那一套，原理一样，只是 handler 结束要发 EOI。）解法只有一个方向：尽快跑完 handler，尽快开中断、unmask（或发 EOI），把 handle Data in the ram 踢出 handler 扔给下半部。

第二种。A 很快做完硬件操作，raise softirq。返回中断现场前会检查软中断触发情况，于是网络数据的后续处理在 A 上跑。跑的过程中 NIC 又中断，控制器分给 B，B 的动作一样，于是软中断也跑到 B 上。为了性能，同一类型 softirq 可以在不同 CPU 上并发——代价是写回调的人得自己考虑重入、自己上锁。为了性能，只能这样。若 A、B 都在跑网络软中断，网卡第三次中断又来了（当它是 10G 网卡），中断分给 A，A 的 handler 照样 raise，但不会调度它执行——softirq 在单 CPU 上串行。此时瓶颈是 CPU 资源，只能加核。

第三种。A 处理中断、schedule tasklet（同时 raise 了 TASKLET_SOFTIRQ）。返回前检查到软中断待处理，进 TASKLET_SOFTIRQ 的 handler，取出 tasklet 在 A 上执行。执行中 NIC 又中断，分给 B。TASKLET_SOFTIRQ 在 B 上能跑，但检查 tasklet 状态时发现它已在别的 CPU 上运行，跳过，等 A 上跑完才能跑。一个 tasklet 在 A 上被调度执行，就绝不会同时在 B 上执行；不同 tasklet 之间仍可并发，同一个不行。串行化对驱动工程师是福利，对性能是损伤。（这个例子只做对比，真实网络栈用的是 softirq。）

三种机制的本质分野一句话：跑在什么上下文。softirq / tasklet 在中断上下文（准确说 softirq 上下文），不能睡眠；workqueue 在进程上下文（内核线程），能睡眠。所以「下半部要睡眠」只能上 workqueue、中断线程化，或自建 kernel thread（老驱动的做法，今天不推荐）。

三、preempt_count：内核如何知道自己在什么上下文 #

后面所有内容都建立在这一个成员上。task 的 thread_info（老内核）里：

c
struct thread_info {
    ……
    int            preempt_count;    /* 0 => preemptable, <0 => bug */
    ……
};

preempt_count 判断当前进程能不能被抢占：不等于 0 说明不能抢（要么显式 preempt_disable 了，要么人在中断上下文里）；等于 0 说明具备条件，抢不抢还要看 thread_info 的 flag 里有没有置 _TIF_NEED_RESCHED。

它是个 32 位整数，切成几段各管一件事。4.x 上的布局：

bit 区间 字段 宏 位宽 上限 谁在加
0–7 preempt count PREEMPT_MASK 8 255 preempt_disable / spin_lock
8 softirq 正在服务 SOFTIRQ_OFFSET 1 1 __do_softirq 入口
9–15 softirq 被禁止 SOFTIRQ_DISABLE_OFFSET 7 127 local_bh_disable
16–19 hardirq 嵌套深度 HARDIRQ_MASK 4 15 irq_enter
20 NMI NMI_MASK 1 1 NMI 入口

几点。preempt count 记录显式禁抢占的层数，一次 preempt_disable 加一，preempt_enable 减一，必须成对、可嵌套、最深 255。hardirq count 是中断 handler 嵌套深度，占 4 bit 所以最多 15 层；一个中断不会嵌套自己，只有不同中断之间才谈得上嵌套。softirq count 管两件事：进 softirq handler 前加一、退出减一（单 CPU 上 softirq 串行，bit 8 一位够用，能回答「是否在 softirq 上下文」）；进程上下文为同步要禁止 softirq，走 local_bh_disable/local_bh_enable，占 bit 9–15，最多 127 层。

老内核的 hardirq count 占过 12 bit（支持 4096 层），因为那时分 fast handler 和 slow handler，理论上最大嵌套层数等于系统 IRQ 个数。后来砍到 10 bit（general arch 是 10，各 arch 可自己 redefine）。等 slow handler 废弃，中断嵌套理论上已不发生，hardirq count 不是 0 就是 1。不过总有古董驱动在 handler 里开中断，所以留 4 bit，应付 15 个够用。

判断上下文的宏（这里把素材里被当成标题的那行 # define hardirq_count() 归位成代码块）：

c
#define preempt_count() (current_thread_info()->preempt_count)

#define hardirq_count() (preempt_count() & HARDIRQ_MASK)
#define softirq_count() (preempt_count() & SOFTIRQ_MASK)
#define irq_count()     (preempt_count() & (HARDIRQ_MASK | SOFTIRQ_MASK | NMI_MASK))

#define in_irq()             (hardirq_count())
#define in_softirq()         (softirq_count())
#define in_interrupt()       (irq_count())
#define in_serving_softirq() (softirq_count() & SOFTIRQ_OFFSET)

版本提醒：4.x 里 preempt_count 还是 thread_info 的成员，preempt_count() 直接读 current_thread_info()。5.x 起它挪进了 task_struct，current_thread_info()->preempt_count 这个写法在 5.x 上编不过（迁移版本未验证）。

四、四种上下文：进程、软中断、硬中断、NMI #

硬中断上下文，也叫 irq context。只要 hardirq count 大于 0 就是它——等于 1 表示没嵌套，大于 1 表示嵌了。

软中断上下文没这么直白。人说「softirq handler 在跑就是 softirq 上下文」，这话对：handler 执行期间 softirq count 加了一。但反过来不成立：进程上下文里因为同步调了 local_bh_disable，被这对函数夹住的代码也处在 softirq 上下文里，而此时根本没有 handler 在跑。要区分这两种情况用 in_serving_softirq，它看 bit 8。

中断上下文 = irq context + softirq context + NMI context，对应 in_interrupt()。进程上下文是剩下的情况：preempt_count 里没有中断相关的位。NMI 上下文最特殊，不响应中断屏蔽，可以打断上面任何一种上下文，包括硬中断；NMI_MASK 单独一位，算进 irq_count()，所以 NMI handler 里 in_interrupt() 也为真。

能否睡眠 能 不能 不能 不能

一段代码能不能睡，就看 in_interrupt() 和 preempt_count()：前者为真、或后者因 preempt_disable/spin_lock 非 0，都不能睡。这是死规则，违反的后果是「scheduling while atomic」告警，或者更糟。

五、softirq：编号、描述符与注册 #

softirq 和 hardirq 对应，机制照着 hardirq 理解，区别只在 softirq 纯软件。上限受 __softirq_pending 这一个 32 位变量限制，也就是 32 个。内核只实现 10 种，在 include/linux/interrupt.h：

c
/* PLEASE, avoid to allocate new softirqs, if you need not _really_ high
   frequency threaded job scheduling. For almost all the purposes
   tasklets are more than enough. F.e. all serial device BHs et
   al. should be converted to tasklets, not to softirqs.
 */

enum
{
        HI_SOFTIRQ=0,
        TIMER_SOFTIRQ,
        NET_TX_SOFTIRQ,
        NET_RX_SOFTIRQ,
        BLOCK_SOFTIRQ,
        IRQ_POLL_SOFTIRQ,
        TASKLET_SOFTIRQ,
        SCHED_SOFTIRQ,
        HRTIMER_SOFTIRQ, /* Unused, but kept as tools rely on the
                            numbering. Sigh! */
        RCU_SOFTIRQ,    /* Preferable RCU should always be the last softirq */

        NR_SOFTIRQS
};

softirq 静态定义：系统里有一个描述符数组，softirq number 就是下标。

c
struct softirq_action
{
    void    (*action)(struct softirq_action *);
};

static struct softirq_action softirq_vec[NR_SOFTIRQS] __cacheline_aligned_in_smp;

描述符只有一个成员：action 回调。__cacheline_aligned_in_smp 让数组对齐 cache line，免得相邻 entry 互踩缓存行。

硬件中断有 mask/ack 寄存器，softirq 没有，但有「软件寄存器」——per-CPU 的 pending 位图：

c
typedef struct {
        unsigned int __softirq_pending;
#ifdef CONFIG_SMP
        unsigned int ipi_irqs[NR_IPI];
#endif
} ____cacheline_aligned irq_cpustat_t;

irq_cpustat_t irq_stat[NR_CPUS] ____cacheline_aligned;

__softirq_pending 每个 bit 对应一种软中断，某 bit 置位就有活等着；ipi_irqs 是处理器间中断，属于另一个专题。为什么 per-CPU？因为 softirq 讲「谁触发，谁负责」：某驱动的硬中断分到某 CPU，该 CPU 的 handler 里 raise 了 softirq，就由这个 CPU 调对应 action 处理，跟硬件里的 banked register 一个思路。irq_stat 每个 entry 也对齐 cache line，同样为性能。

注册只有一句，在 kernel/softirq.c：

c
void open_softirq(int nr, void (*action)(struct softirq_action *))
{
        softirq_vec[nr].action = action;
}

往全局数组塞回调，不需要保护：所有注册都在系统初始化时完成，那时串行执行；每个 entry 固定分配，不存在抢同一个下标。softirq_init 装上两种 tasklet 的回调，顺手初始化 per-CPU 链表的尾指针：

c
void __init softirq_init(void)
{
        int cpu;

        for_each_possible_cpu(cpu) {
                per_cpu(tasklet_vec, cpu).tail = &per_cpu(tasklet_vec, cpu).head;
                per_cpu(tasklet_hi_vec, cpu).tail = &per_cpu(tasklet_hi_vec, cpu).head;
        }

        open_softirq(TASKLET_SOFTIRQ, tasklet_action);
        open_softirq(HI_SOFTIRQ, tasklet_hi_action);
}

其他 softirq 由各模块注册，比如 TIMER_SOFTIRQ 在 init_timers 里 open_softirq(TIMER_SOFTIRQ, run_timer_softirq)。这就是「驱动别自己加软中断」的技术原因：数组大小编译期定死，注册入口没对外导出，走 open_softirq 得改内核源码。

七、如何触发一个 softirq：raise_softirq 与 or_softirq_pending #

触发就是在 __softirq_pending 某个 bit 上置一。变量 per-CPU，关本地中断就够原子。

c
void raise_softirq(unsigned int nr)
{
        unsigned long flags;

        local_irq_save(flags);       // 关闭本地 cpu 中断
        raise_softirq_irqoff(nr);
        local_irq_restore(flags);    // 恢复 cpu 中断状态
}

local_irq_save 存下当前中断状态再关；local_irq_restore 恢复的是调用前那个状态，不是无条件开中断——这点比 local_irq_enable 安全。中断 handler 里本地中断已关，直接用 _irqoff 版本省一次 save/restore；其他上下文调 raise_softirq。

c
/*
 * This function must run with irqs disabled!
 */
inline void raise_softirq_irqoff(unsigned int nr)
{
        __raise_softirq_irqoff(nr);

        /* 在中断或 softirq 里（含 bh 被禁止的代码），置位就够了，
         * 退出中断/软中断时自然会处理；
         * 否则叫醒 ksoftirqd，保证这批 softirq 尽快被调度。 */
        if (!in_interrupt())
                wakeup_softirqd();
}

真正置位在下一层：

c
void __raise_softirq_irqoff(unsigned int nr)
{
    trace_softirq_raise(nr);
    or_softirq_pending(1UL << nr);
}

or_softirq_pending 把 1UL << nr 或进当前 CPU 的 pending 位图，展开后等价于：

text
((irq_stat[(current_thread_info()->cpu)].__softirq_pending) |= (1UL << nr));

注意要先按 CPU 索引 irq_stat 再取 __softirq_pending 字段，后者是 irq_cpustat_t 的成员。同类型软中断能在多 CPU 上并行跑，根子就在这：A 核置 bit 3 和 B 核置 bit 3 互不相干，各跑各自的 net_rx_action。

后半段是本函数的分工：在中断上下文（含被 local_bh_disable 夹住、或已在 softirq 里）只置位就完了，迟早要退出，那时统一处理；不在中断上下文，就必须叫醒守护线程。

c
static void wakeup_softirqd(void)
{
    struct task_struct *tsk = __this_cpu_read(ksoftirqd);

    if (tsk && tsk->state != TASK_RUNNING)
        wake_up_process(tsk);
}

tsk->state != TASK_RUNNING 省一次调度器交互——已经 runnable 的线程不用再叫。

八、softirq 的处理：do_softirq 与 __do_softirq #

调用层次三层，别混：

text
do_softirq()                 —— 通用入口：in_interrupt() 则早退，否则往下走
  └─ do_softirq_own_stack()  / __do_softirq()   —— 取决于 arch 有无独立软中断栈
__do_softirq()               —— 真正遍历 pending 位图干活的

__do_softirq 的骨架（5.2.8）：

c
asmlinkage __visible void __softirq_entry __do_softirq(void)
{
    struct softirq_action *h = softirq_vec;
    __u32 pending = local_softirq_pending();  // 获取 irq_stat[cpu].__softirq_pending
    __local_bh_disable_ip(_RET_IP_, SOFTIRQ_OFFSET);
    set_softirq_pending(0);        // Reset the pending bitmask before enabling irqs
    local_irq_enable();            // 开启当前 CPU 中断
    ...
    while ((softirq_bit = ffs(pending))) {
        h += softirq_bit - 1;
        h->action(h);
        h++;                       // 下一个软中断
        pending >>= softirq_bit;   // 下一个软中断状态标志位
    }
    ...
    local_irq_disable();           // 关闭当前 CPU 中断

    restart:
        pending = local_softirq_pending();   // 软中断执行期间，有新的软中断产生
        if (pending) {
                if (time_before(jiffies, end) && !need_resched() && --max_restart)
                        goto restart;
                wakeup_softirqd();  // 交给守护线程处理
        }

    __local_bh_enable(SOFTIRQ_OFFSET);
}

进出顺序是这函数最有信息量的部分：进来抓 pending 快照、__local_bh_disable_ip(..., SOFTIRQ_OFFSET) 把自己标成 softirq 上下文、清零 pending 位图、开本地中断；中间全程开中断；最后关中断重读 pending，看这轮执行期间有没有新软中断冒出来，决定要不要 goto restart；退出前 __local_bh_enable 摘掉标记。

为什么先清零再开中断？清零到开中断之间是关中断的，没有 raise 能钻进来；开中断之后的 raise 落在新位图上，由结尾那次重读收走。为什么全程开中断？__do_softirq 紧跟 hardirq 执行，这时该开中断了；代价是 softirq 会被 hardirq 抢占——正是设计意图，硬中断优先级永远高于软中断。所以一个 softirq 执行期间不会被同 CPU 上另一个 softirq 抢占（bh 关着），但会被硬中断抢占；不考虑实时特性和中断线程化的话，也不会被更高优先级的线程抢占。

遍历用 ffs：h += softirq_bit - 1 把指针挪到描述符，h->action(h) 执行，h++ 复位，pending >>= softirq_bit 丢掉已处理的低位。

2.6 时代的老版本循环部分长得不一样，还带一个 preempt_count 校验：

c
    h = softirq_vec;
    do {
        if (pending & 1) {
            int prev_count = preempt_count();
            h->action(h);
            if (unlikely(prev_count != preempt_count()))
                /* 中断计数异常处理 */ ;
            rcu_bh_qsctr_inc(cpu);
        }
        h++;
        pending >>= 1;
    } while (pending);

    local_irq_disable();
    pending = local_softirq_pending();
    if (pending && --max_restart)  goto restart;
    if (pending)                   wakeup_softirqd();

三点差异：遍历从逐位滚改成 ffs 跳位；重启条件从只看次数改成加时间闸和 need_resched() 闸；prev_count != preempt_count() 那个检查（handler 里不该动 preempt_count，动了就是 bug）新版挪到了别的宏里，版本未验证。

__do_softirq 跑在中断上下文，不能睡眠。就算它紧跟 hardirq、跟「hardirq 上下文」有区别，准确说法是「softirq 上下文」，同样禁睡。

栈的问题单独说。Linux 2.6.32 起中断处理不再借用被打断线程的栈，改用独立的 per-CPU 栈，softirq 和 hardirq 各有各的：

c
DEFINE_PER_CPU(struct irq_stack *, hardirq_stack);
DEFINE_PER_CPU(struct irq_stack *, softirq_stack);

softirq 被硬中断打断后，softirq_stack 记下当前上下文（入栈），CPU 转去跑 hardirq，栈指针切到 hardirq_stack。往返：task A 触发 interrupt 1 → 跑 hardirq 1 → 它 raise 了 softirq 1 → softirq 1 跑起来（softirq 栈）→ 被 interrupt 2 打断 → 跑 hardirq 2（hardirq 栈）→ irq_exit 时软中断条件不满足（还在 softirq 上下文）→ 跳回 softirq 1 继续，上下文出栈恢复 → 结束时按 pending 位图重新挑活，hardirq 2 期间置的位这时被处理。软中断连着来太多或超时，扔给 ksoftirqd。这就解释了 invoke_softirq 的两个栈分支（第九节给出代码）。

ARM 上 do_softirq_own_stack 就是直接调 __do_softirq。

九、irq_exit 里的那一句：什么时候真正执行下半部 #

generic handler 的进出被 irq_enter / irq_exit 夹住，__handle_domain_irq 是典型（irq_find_mapping、ack_bad_irq、generic_handle_irq 的细节属于前一篇的范围）：

c
int __handle_domain_irq(struct irq_domain *domain, unsigned int hwirq,
                        bool lookup, struct pt_regs *regs)
{
        struct pt_regs *old_regs = set_irq_regs(regs);
        int ret = 0;

        irq_enter();                  //  更新系统统计信息，禁止内核抢占
        if (lookup)
                irq = irq_find_mapping(domain, hwirq);   // 中断域 + 硬件号 -> IRQ 编号
        if (unlikely(!irq || irq >= nr_irqs))
                ack_bad_irq(irq), ret = -EINVAL;
        else
                generic_handle_irq(irq);        // 重点是这里
        irq_exit();                   // 退出时检查是否有软中断，有则调用

        set_irq_regs(old_regs);
        return ret;
}

irq_enter 在 kernel/softirq.c：

c
void irq_enter(void)
{
        rcu_irq_enter();
        if (is_idle_task(current) && !in_interrupt()) {
                /* Prevent raise_softirq from needlessly waking up ksoftirqd
                 * here, as softirq will be serviced on return from interrupt. */
                local_bh_disable();
                tick_irq_enter();   // 空函数
                _local_bh_enable();
        }

        __irq_enter();
}

idle 任务上、且不在中断上下文时，用 local_bh_disable/_local_bh_enable 包一下 tick_irq_enter：让这段里冒出来的 raise_softirq 不叫醒 ksoftirqd（bh 关着，!in_interrupt() 判成假），中断返回时软中断自然会处理，白唤醒一次是浪费。

真正标记「进硬中断上下文」的是 __irq_enter，它给 hardirq count 加一，从这一刻起 in_irq() 为真，top half 开始：

c
#define __irq_enter()                                   \
        do {                                            \
                account_irq_enter_time(current);        \
                preempt_count_add(HARDIRQ_OFFSET);      \
                trace_hardirq_enter();                  \
        } while (0)

（上游对 ->hardirq_context 的非原子操作有豁免：NMI handler 不能抢占，这对操作永远平衡，被打断的值必然恢复。）

出口：

c
void irq_exit(void)
{
#ifndef __ARCH_IRQ_EXIT_IRQS_DISABLED
        local_irq_disable();
#else
        lockdep_assert_irqs_disabled();
#endif
        account_irq_exit_time(current);
        preempt_count_sub(HARDIRQ_OFFSET);      // hardirq count - 1
        if (!in_interrupt() && local_softirq_pending())
                invoke_softirq();

        tick_irq_exit();
        rcu_irq_exit();
        trace_hardirq_exit(); /* must be last! */
}

顺序不能乱：先撤掉硬中断标记，再判断。两个条件——!in_interrupt() 表示不在任何中断上下文，local_softirq_pending() 表示本 CPU 有活。宏展开（素材原文的 3.x/4.x 形态）：

text
if (!((preempt_count() & (((1UL << (4))-1) << ((0 + 8) + 8)) | (((1UL << (8))-1) << (0 + 8)) | (((1UL << (1))-1) << (((0 + 8) + 8) + 4))))) && (irq_stat[(current_thread_info()->cpu)].__softirq_pending))

一堆移位看着晕，本质就是 preempt_count() & (HARDIRQ_MASK | SOFTIRQ_MASK | NMI_MASK) 为 0 且 pending 非 0。

!in_interrupt() 挡掉两种场景，每种对应一条设计约束：中断 handler 嵌套——本次 irq_exit 退回上一层中断 handler 而不是进程（新内核 handler 都关中断执行，基本不发生）；本次中断打断了 softirq handler——irq_exit 退回的是上一层 softirq 上下文，这条保证了单 CPU 上 softirq 串行。

条件成立就 invoke_softirq：

c
static inline void invoke_softirq(void)
{
        if (ksoftirqd_running(local_softirq_pending()))
                return;

        if (!force_irqthreads) {
#ifdef CONFIG_HAVE_IRQ_EXIT_ON_IRQ_STACK   // 该 arch 没定义
                /* 中断栈上跑：退出中断后它已接近空 */
                __do_softirq();
#else
                /* 任务栈可能已经很深，切到软中断自己的栈上跑，防溢出 */
                do_softirq_own_stack();
#endif
        } else {
                wakeup_softirqd();
        }
}

三件事。第一行 ksoftirqd_running()：ksoftirqd 已经在跑且会处理这批 pending，直接返回，别重复干——这个判断在 4.x 之前没有，见勘误。force_irqthreads 为真走 wakeup_softirqd，这个变量靠内核命令行 threadirqs 置一，默认 0；强制线程化主要给中断调试用，既然 handler 都在线程里跑了，softirq 也没理由留在中断上下文。剩下两条是栈路径，见上一节。

整条链闭合：

text
硬件中断 -> irq_enter (hardirq count +1) -> handler / top half
        -> raise_softirq_irqoff (置 pending 位；在中断里不唤醒)
        -> irq_exit (hardirq count -1)
             -> !in_interrupt() && local_softirq_pending()
                  -> invoke_softirq -> __do_softirq -> action()

触发时机一共三处，除 irq_exit 外还有两处：local_bh_enable（开软中断时检查 in_interrupt 和 local_softirq_pending，都满足就执行，链是 local_bh_enable -> __local_bh_enable_ip -> do_softirq）；raise_softirq（进程上下文里置完位唤醒 ksoftirqd）。

十、ksoftirqd：为什么需要一个内核线程 #

__do_softirq 已经带了 2ms 和 10 次的预算，为什么还要线程？预算一用完，剩余 pending 必须有人收尾，而中断上下文里没法长跑。ksoftirqd 就是收尾的人，随 CPU 热插拔为每核创建一个，nice 19，与用户任务共享调度器不抢占。

text
DEFINE_PER_CPU(struct task_struct *, ksoftirqd);

按 smp_hotplug_thread 注册，入口 run_ksoftirqd：

c
static struct smp_hotplug_thread softirq_threads = {
        .store                  = &ksoftirqd,
        .thread_should_run      = ksoftirqd_should_run,
        .thread_fn              = run_ksoftirqd,
        .thread_comm            = "ksoftirqd/%u",
};

static void run_ksoftirqd(unsigned int cpu)
{
        local_irq_disable();              // 关闭本地 CPU 中断，防止硬件中断抢占
        if (local_softirq_pending()) {    // 如果有要处理的软中断
                /*
                 * We can safely run softirq on inline stack, as we are not deep
                 * in the task stack here.
                 */
                __do_softirq();             // 处理软中断
                local_irq_enable();         // 开启本地 CPU 中断
                cond_resched();
                return;
        }
        local_irq_enable();                // 开启本地 CPU 中断
}

进门就 local_irq_disable()：先关中断再判 pending，再进 __do_softirq（后者进门自己开中断）。这个窗口必须关中断，否则 pending 可能在判断和执行之间变化。

bash
root@zhengyang:/work/linux-5.2.8-bak# ps -ef | grep ksoftirq
root          7      2  0 04:36 ?        00:00:00 [ksoftirqd/0]
root         16      2  0 04:36 ?        00:00:00 [ksoftirqd/1]
root         22      2  0 04:36 ?        00:00:00 [ksoftirqd/2]
root         28      2  0 04:36 ?        00:00:04 [ksoftirqd/3]

名字 ksoftirqd/n，n 是 CPU 编号。ksoftirqd/3 吃了 4 秒 CPU，说明 3 号核软中断压力不小。

老内核（2.6.x）是死循环写法，两层 while：

c
    while (!kthread_should_stop()) {
        preempt_disable();
        if (!local_softirq_pending()) {
            preempt_enable_no_resched();
            schedule();
            preempt_disable();
        }
        __set_current_state(TASK_RUNNING);
        while (local_softirq_pending()) {
            if (cpu_is_offline((long)__bind_cpu))
                goto wait_to_die;
            do_softirq();
            preempt_enable_no_resched();
            cond_resched();
            preempt_disable();
        }
        preempt_enable();
        set_current_state(TASK_INTERRUPTIBLE);
    }

四步：外层每轮先 preempt_disable() 再查 pending；没 pending 就 preempt_enable_no_resched() + schedule() 睡到有人叫；有 pending 就置 TASK_RUNNING 进内层 while 反复 do_softirq()，每轮 cond_resched() 让一下；内层还查 cpu_is_offline()，CPU 下线了就跳 wait_to_die 等 kthread_should_stop。新版把循环收敛进框架，热插拔和 _should_run 判断都交出去，run_ksoftirqd 只留核心动作。演进说明逻辑一直没变：有活就干、干完就让、CPU 没了就死。

为什么必须有这个线程，三条：避免长时间占用 CPU（中断处理拖长系统响应就掉，搬进线程其他任务才有插队机会）；处理中断上下文里做不了的事（软中断有中断上下文和进程上下文两种 context，中断上下文里禁用睡眠等 I/O 完成操作，内核线程能做）；高频场景需要泄压（网卡中断来了 ISR 搬数据扔给协议栈，协议栈耗时长，走软中断异步做；全在中断上下文里干，其他中断一直被压着）。

还有一层平衡：既「霸道」又「公平」。霸道是每轮处理时关抢占，公平是每处理一轮就 cond_resched()，超预算就主动让出 CPU。

十一、local_bh_enable / local_bh_disable #

先对齐命名。硬件中断用 local_irq_*；软中断没叫 local_softirq_*，叫 local_bh_*——bh 是 bottom half，因为这对函数关掉的不止 softirq，还有 tasklet。场景：线程被硬中断打断，如果希望执行完 hardirq 就直接返回原线程、不跑 pending 的 softirq，就 local_bh_disable。

c
local_bh_disable();
/* critical section */
local_bh_enable();

disable 一侧在 include/linux/bottom_half.h：

c
static inline void local_bh_disable(void)
{
    __local_bh_disable_ip(_THIS_IP_, SOFTIRQ_DISABLE_OFFSET);
}

static __always_inline void __local_bh_disable_ip(unsigned long ip, unsigned int cnt)
{
        preempt_count_add(cnt);
        barrier();
}

给 preempt_count 的 bit 9–15 加一，barrier() 防编译器把临界区访存重排到计数更新之前。SOFTIRQ_DISABLE_OFFSET 等于 2 * SOFTIRQ_OFFSET，4.x 上是 0x200，正好 bit 9——一次 disable 加的是 0x200 不是 1，看 preempt_count 数值时必须知道这点。

enable 一侧复杂得多：

c
void __local_bh_enable_ip(unsigned long ip, unsigned int cnt)
{
    WARN_ON_ONCE(in_irq() || irqs_disabled());

    preempt_count_sub(cnt - 1);

    if (unlikely(!in_interrupt() && local_softirq_pending())) {
        do_softirq();
    }

    preempt_count_dec();
    preempt_check_resched();
}

四步。第一步，WARN_ON_ONCE(in_irq() || irqs_disabled())。in_irq() 非 0 说明这对函数被 irq_enter/irq_exit 包围，也就是在中断 handler 里用了它们——错，softirq 抢不了 top half，保护是多余的。irqs_disabled() 返回 1 的代码长这样：

text
local_irq_disable();
……
local_bh_disable();
……
local_bh_enable();
……
local_irq_enable();

关本地中断比关 bh 更强，单看逻辑好像只是浪费。问题在 local_bh_enable -> do_softirq -> __do_softirq 里有一句无条件开当前中断，原本用 local_irq_disable/local_irq_enable 保护的临界区就漏了，别的中断 handler 能插进来，原子性没了。所以这个组合必须报警。

第二步，preempt_count_sub(cnt - 1)。为什么不一次减 cnt？临界区里可能有进程和 softirq 共享的数据，所以用这对函数保护。执行中中断随时会到（只关了 bh 没关中断），handler 抢占当前线程，handler 里 raise 的 softirq 因为 bh 关着不调度，代码回临界区接着跑，直到 local_bh_enable——一 enable，之前 raise 的软中断就得执行，这就是 enable 里要调 do_softirq 的原因。

问题是调 do_softirq 时当前 task 不能被抢占。一旦被抢占，下次调度上来可能跑在别的 CPU 上，而 pending 位图是 per-CPU 的，就找不着了。所以不能一次减完：一次减掉整个 SOFTIRQ_DISABLE_OFFSET 会让 preempt_count 归零，抢占就开了。减 cnt - 1 的效果是 bit 9–15 那层确实退掉，但 preempt count（bit 0–7）还留着 1，抢占仍关。

第三步，!in_interrupt() && local_softirq_pending() 成立就 do_softirq()。第四步，preempt_count_dec() 把故意留的 1 补掉，然后 preempt_check_resched()：softirq handler 里很可能唤醒了高优先级任务，这里检查要不要立刻调度。

三条守则：硬件中断 handler 里不要用这对函数保护共享数据（softirq 抢不了 top half）；它是给进程上下文用的，防 softirq 抢占临界区；softirq handler 也抢不了另一个 softirq handler，一个 handler 被调度后本地 softirq handler 都进不来，要等它跑完。

最后这句「本地」很重要。softirq handler 能在多 CPU 上同时跑，内核没有「disable 所有 softirq」的接口——就像没有「disable 所有 CPU 中断」的接口。local_bh_enable/disable 里的 local 就是这个意思。

三种 mask 强度排一下：

手段 挡住什么 加在哪 代价
preempt_disable 抢占（别的进程/线程） bit 0–7 最小
local_bh_disable 抢占 + softirq/tasklet bit 9–15 中
local_irq_disable 抢占 + softirq + 本 CPU 硬中断 关中断线 最大

原则是能少挡就少挡。线程上下文里防软中断用 local_bh_disable，别上 local_irq_disable，后者把中断延迟一起搭进去。

十二、softirq 的执行时机与时间预算 #

软中断被 raise 后，实际执行落在这几处：

时机 触发路径 上下文 场景
中断返回用户空间 irq_exit -> invoke_softirq -> __do_softirq softirq 最常见，延迟最低
中断返回内核态进程、不在 bh 临界区 同上，要求 !in_interrupt() softirq 与上条同机制
进程上下文退出 bh 临界区 local_bh_enable -> __local_bh_enable_ip -> do_softirq softirq bh 关着时攒的 pending 在这补
ksoftirqd 被调度 wakeup_softirqd -> run_ksoftirqd -> __do_softirq 进程（内核线程） 预算耗尽、或 threadirqs 强制线程化

反过来两个时刻不会执行，这是 !in_interrupt() 挡住的：中断嵌套场景（退回上一层中断 handler）；中断抢了 softirq 上下文（退回上一层 softirq handler）。第二点正是「单 CPU 上 softirq 串行」的实现方式。

时间预算三个闸门，全满足才 goto restart：

闸门 判据 值 目的
时间 time_before(jiffies, end) 2ms 给调度延迟上界
调度 !need_resched() — 有人等 CPU 就让
次数 --max_restart MAX_SOFTIRQ_RESTART = 10 防死循环

任一条不满足就 wakeup_softirqd()，剩下的交给线程。这三个数讲的是权衡：只谈调度延迟，handler 不该一直占着不放，否则内核没法保证「中断后多久内调度到某个进程」；只谈吞吐，刚跑完就再来最省事。2ms / 10 次就是在两者之间划的一条线。

这条线为什么必须有？因为 handler 的执行时间你控制不了，前面站着别人写的驱动。某个 handler 连跑不停，进程调度延迟会变得又长又不可预测，实时系统上这是硬伤。所以「越快越好型」的下半部在系统里不该太多，tasklet 回调也不能写长。

到这儿 softirq 闭环了：号怎么定、描述符怎么放、pending 位图怎么置、谁在什么时候消费、预算超了交给谁。下面 tasklet 整个建立在这条线上。

十三、tasklet：建立在 softirq 之上的封装 #

先说「为什么还要 tasklet」。softirq 两个硬伤：__softirq_pending 只有 32 位，总数不能超 32，而且内核没提供通用增加软中断的接口，加一个得改枚举（open_softirq 头上那段注释就在喊这事）；softirq 必须写成可重入函数，因为同类型能在多 CPU 上同时跑，你得自己上自旋锁。

tasklet 给这两条打补丁。特性三条：一种特定类型的 tasklet 只能在一个 CPU 上跑，不并行，串行执行；多个不同类型的 tasklet 可以在多 CPU 上并行；softirq 静态分配、编译完改不了，tasklet 运行时能变，加模块都能加。

一句话：tasklet 是 softirq 的一种特殊用法——延迟情况下的串行执行。它挂在两种软中断上，数量不受 32 限制，白拿串行化保证。

把「推迟执行」的完整分类摆出来，tasklet 才有坐标：

推迟到 机制 上下文 代表
top half 执行完毕 softirq、tasklet 中断 net_rx_action、驱动 tasklet
指定时间之后 低精度 timer、hrtimer（内部仍走 softirq） 中断 TIMER_SOFTIRQ、HRTIMER_SOFTIRQ
某个内核线程被调度时 threaded irq handler、workqueue、自建 kernel thread 进程 system_wq、kworker/*

第三种里的「自建 kernel thread」是旧驱动做法，今天一个理智的驱动厂商不会这么干——线程的创建销毁、生命周期全得自己扛。

再细分「没有具体时间要求」那类，劈成两种。越快越好型有性能要求，除了中断 top half，任何进程上下文（不管优先级多高）都影响不了它，对应 softirq 和 tasklet。随遇而安型没性能要求，执行时机全交给调度器，对应 workqueue 和 threaded irq handler。「越快越好型」不该有太多成员，tasklet callback 也不能跑长——否则进程调度延迟变大、变得不确定，实时系统上后果很坏。

历史交代一下。4.0 那年头就有人主张删掉 tasklet：grep 一遍内核，使用者是一张很长的清单，归个类就能全清——有性能需求的并进 softirq，其余换 workqueue。Steven Rostedt 试过（lwn.net/Articles/239484），patch 没进 mainline。真正落地的是另一条路：Linux 5.9 起 tasklet 相关接口被标注废弃，文档移入 legacy 并给出迁移建议（改 workqueue 或 threaded irq），但接口本身到 6.x 仍未删除。今天你还能用，新代码不该再用。这个版本节点素材里没有，来自上游记录，具体 commit 未验证。

十四、tasklet_struct 与 tasklet_schedule #

结构定义在 include/linux/interrupt.h。注释里那四条性质值得读：调过 tasklet_schedule 保证至少被执行一次；已调度但还没跑只执行一次；已在别的 CPU 上跑（或从自己回调里调度）就重新排到后面；对自己严格串行，对其他 tasklet 不串行，跨 tasklet 的同步自己用 spinlock。

c
struct tasklet_struct
{
        struct tasklet_struct *next;    // 将多个 tasklet 链接成单向链表
        unsigned long state;            // 状态标志位
        atomic_t count;                 // 0：激活 tasklet  其他：禁用
        void (*func)(unsigned long);    // 用户自定义函数
        unsigned long data;             // 函数入参
};

逐字段：next 指向本 CPU 链表的下一个节点，表尾用 tail（指向 next 字段的地址）维护。state 是 32 位，实际只用两个 bit——TASKLET_STATE_SCHED 置位表示已挂到某个 CPU 链表上等着跑，TASKLET_STATE_RUN 置位表示正跑在某个 CPU 上，后者只在 SMP 有意义，单核不校验。count 是引用计数，等于 0 才能执行，非 0 就是被 disable 了。func/data 是回调与入参，data 的含义由 func 自己解释，常见做法是塞私有结构体指针。

两个状态位靠枚举定义（TASKLET_STATE_SCHED 是 0，TASKLET_STATE_RUN 是 1）。per-CPU 链表头：

c
struct tasklet_head {
        struct tasklet_struct *head;
        struct tasklet_struct **tail;
};

static DEFINE_PER_CPU(struct tasklet_head, tasklet_vec);
static DEFINE_PER_CPU(struct tasklet_head, tasklet_hi_vec);

tail 是二级指针，指向「下一个待插入位置」，即最后一个节点的 next 字段地址（空链表时指向 head 本身）。入队 O(1)，不用遍历到表尾。

静态定义两版，动态初始化一个：

c
// 定义名字为 name 的激活 tasklet
#define DECLARE_TASKLET(name, func, data) \
struct tasklet_struct name = { NULL, 0, ATOMIC_INIT(0), func, data }

// 定义名字为 name 的非激活 tasklet
#define DECLARE_TASKLET_DISABLED(name, func, data) \
struct tasklet_struct name = { NULL, 0, ATOMIC_INIT(1), func, data }

void tasklet_init(struct tasklet_struct *t, void (*func)(unsigned long), unsigned long data)
{
        t->next = NULL;
        t->state = 0;
        atomic_set(&t->count, 0);
        t->func = func;
        t->data = data;
}

tasklet_init 只填字段，不挂链表。真正激活等 tasklet_schedule。

disable/enable 一对，支持嵌套，必须配对：

c
static inline void tasklet_disable(struct tasklet_struct *t)
{
        atomic_inc(&t->count);      // 即 tasklet_disable_nosync
        tasklet_unlock_wait(t);     // 该 tasklet 正跑在别的 CPU 上就等它跑完
        smp_mb();
}

static inline void tasklet_enable(struct tasklet_struct *t)
{
        smp_mb__before_atomic();
        atomic_dec(&t->count);
}

tasklet_disable 返回时保证真停了；_nosync 版只加计数不管同步，给「已确定跑完」的场景用。旧内核里这两个屏障叫 smp_mb__after_atomic_inc() / smp_mb__before_atomic_dec()，2.6 素材里就是旧名，改名在 3.x，具体版本未验证。为什么需要它们？有时候同步场景不需要关掉所有 softirq 和 tasklet，只想关某一个，local_bh_disable 颗粒度太粗。

调度入口：

c
static inline void tasklet_schedule(struct tasklet_struct *t)
{
        if (!test_and_set_bit(TASKLET_STATE_SCHED, &t->state))
                __tasklet_schedule(t);
}

static inline void tasklet_hi_schedule(struct tasklet_struct *t)
{
        if (!test_and_set_bit(TASKLET_STATE_SCHED, &t->state))
                __tasklet_hi_schedule(t);
}

test_and_set_bit 是原子操作：先置 TASKLET_STATE_SCHED，返回原值。原值已是 1 说明这个 tasklet 已经躺在某个 CPU 链表里，直接返回；原值 0 才往下走。这行解决重复调度：程序在多个上下文里可以多次 schedule 同一个 tasklet，也可能来自多个 CPU 核，实际上它只会挂到首次调度那个 CPU 的链表上，而且只挂一次。

走一遍时序。某驱动 top half 里调 tasklet_schedule，这次中断落在 CPU0，tasklet 挂进 CPU0 的 tasklet_vec，state 置上 TASKLET_STATE_SCHED。还没开跑，硬件又触发中断，这次落 CPU1，tasklet_schedule 再被调。但 TASKLET_STATE_SCHED 已置着，test_and_set_bit 返回 1，函数直接返回，不会挂进 CPU1 的链表。

真正入队是 __tasklet_schedule。5.2.8 抽了 _common：

c
static void __tasklet_schedule_common(struct tasklet_struct *t,
                                      struct tasklet_head __percpu *headp,
                                      unsigned int softirq_nr)
{
        struct tasklet_head *head;
        unsigned long flags;

        local_irq_save(flags);      // 关闭本地 cpu 中断
        head = this_cpu_ptr(headp);
        t->next = NULL;
        *head->tail = t;
        head->tail = &(t->next);
        raise_softirq_irqoff(softirq_nr);     // 唤起软中断
        local_irq_restore(flags);     // 恢复 cpu 中断
}

void __tasklet_schedule(struct tasklet_struct *t)
{
        __tasklet_schedule_common(t, &tasklet_vec,
                                  TASKLET_SOFTIRQ);
}

2.6/3.x 是各写一份，per-CPU 变量直接内联访问（*__this_cpu_read(tasklet_vec.tail) = t 等价于新版的 *head->tail = t）。素材 4 里那句 __cpu_raise_softirq() 是更老的写法，功能等价于 raise_softirq_irqoff()。 四个动作：local_irq_save 关中断（链表操作 per-CPU，禁掉本地中断就拦住所有并发）；三行挂表尾（*head->tail = t 让原表尾节点的 next 指向新节点，head->tail = &(t->next) 把尾指针挪到新节点的 next）；raise_softirq_irqoff raise 对应软中断（普通 tasklet 拉 TASKLET_SOFTIRQ 编号 6，高优先级拉 HI_SOFTIRQ 编号 0）；local_irq_restore 恢复。

注意 tasklet_schedule 不执行任何用户代码，它只做「登记」和「raise 软中断」两件事。真正执行要等 softirq 被调度，这就回到了第十二节那张时机表。

十五、tasklet 与 softirq 的关系：HI_SOFTIRQ 与 TASKLET_SOFTIRQ #

tasklet 不是和 softirq 并列的机制，它站在 softirq 上面：

text
    用户/驱动代码
        │  tasklet_schedule() / tasklet_hi_schedule()
        │    └─ test_and_set_bit(TASKLET_STATE_SCHED)
        │         未被调度过才 __tasklet_schedule()
        ▼
  per-CPU tasklet_head
        tasklet_vec     ──────┐ 普通
        tasklet_hi_vec  ──────┼──┐ 高优先级
                              │  │
  raise_softirq_irqoff() ◄────┘  │
        │ 置 __softirq_pending 的 bit
        ▼
  softirq_vec[NR_SOFTIRQS]
        [0] HI_SOFTIRQ       -> tasklet_hi_action
        [1] TIMER_SOFTIRQ    -> run_timer_softirq
        [6] TASKLET_SOFTIRQ  -> tasklet_action
        │
        │ irq_exit / local_bh_enable / ksoftirqd
        ▼
  __do_softirq() 遍历 pending 位图，调 h->action(h)
        ├─> tasklet_action()    遍历 tasklet_vec
        └─> tasklet_hi_action() 遍历 tasklet_hi_vec

对应关系两行：

tasklet 类别 挂的链表 借用的 softirq 编号 action 回调 注册点
普通 tasklet tasklet_vec TASKLET_SOFTIRQ 6 tasklet_action softirq_init
高优先级 tasklet tasklet_hi_vec HI_SOFTIRQ 0 tasklet_hi_action softirq_init

两种机理完全一样，只差挂哪条链、raise 哪个 bit、哪个 action 消费。下面只细讲 TASKLET_SOFTIRQ。

高优先级「高」在哪？高在 __softirq_pending 里的位置。bit 0 是最低位，ffs 从低位往高位找，多个软中断同时 pending 时 HI_SOFTIRQ 第一个执行，比 TIMER 还早。用错会挤掉定时器，所以 tasklet_hi_schedule 慎用。上面 /proc/softirqs 里 HI 一列全 0，也印证它几乎没人用。

十六、tasklet 的执行与 ksoftirqd 的协作 #

执行入口 tasklet_action，5.2.8 抽了 _common：

c
static void tasklet_action_common(struct softirq_action *a,
                                  struct tasklet_head *tl_head,
                                  unsigned int softirq_nr)
{
        struct tasklet_struct *list;

        local_irq_disable();  // 关闭本地 cpu 硬件中断
        list = tl_head->head;
        tl_head->head = NULL;
        tl_head->tail = &tl_head->head;
        local_irq_enable();   // 开启本地 cpu 硬件中断

        while (list) {
                struct tasklet_struct *t = list;

                list = list->next;

                if (tasklet_trylock(t)) { // 返回 false 说明已在其他 CPU 上运行，本轮跳过
                        if (!atomic_read(&t->count)) {    // 读到 0，激活状态
                                if (!test_and_clear_bit(TASKLET_STATE_SCHED, &t->state))
                                        BUG();
                                t->func(t->data); // 执行当前 tasklet 处理函数
                                tasklet_unlock(t);
                                continue;
                        }
                        tasklet_unlock(t);
                }

                local_irq_disable();
                t->next = NULL;
                *tl_head->tail = t;
                tl_head->tail = &t->next;
                __raise_softirq_irqoff(softirq_nr);
                local_irq_enable();
        }
}
/* tasklet_action 只是 this_cpu_ptr(&tasklet_vec) + TASKLET_SOFTIRQ 的薄封装，
 * tasklet_hi_action 换成 tasklet_hi_vec + HI_SOFTIRQ */

拆四段。第一段把本 CPU 整条链表摘给局部变量 list，然后把头指针置 NULL、尾指针指回 head，链表就空了。这几行必须关中断做——bottom half 本来是开中断执行的，不关就和 __tasklet_schedule 打架。摘完立刻开中断。第二段 while (list) 遍历这条私有链表，每轮先 t = list; list = list->next; 把当前节点和后续链表分开，后面把 t 塞回 per-CPU 链表时才不会把整串带回去。

第三段 tasklet_trylock(t)：

c
static inline int tasklet_trylock(struct tasklet_struct *t)
{
        return !test_and_set_bit(TASKLET_STATE_RUN, &(t)->state);
}

置 TASKLET_STATE_RUN，返回原值取反——「原来没在跑」才返回 true。这是「同一 tasklet 只在一个 CPU 上执行」的实现。

刚从自己链表里摘下来的 tasklet 也可能是 running 状态，时序是这样：CPU0 的驱动中断把 tasklet 挂进 CPU0 链表，合适时机开始执行 t->func；CPU0 上来一个更急的硬中断，抢占了 callback，此时 tasklet 仍 running；硬件又一次触发，这次落 CPU1，因为 TASKLET_STATE_SCHED 已被清，tasklet_schedule 会把同一个 tasklet 挂进 CPU1 链表；CPU0 忙着处理中断，CPU1 后发先至进了 tasklet_action。于是 CPU1 摘下来的这个 tasklet，实际正在 CPU0 上跑。tasklet_trylock 就是拦这个局面的闸。

第四段分两种情况。trylock 成功且 count == 0 是正常路径：test_and_clear_bit(TASKLET_STATE_SCHED) 清调度标记（原值若是 0 说明状态机坏了，BUG()），t->func(t->data) 执行回调，tasklet_unlock(t) 清 TASKLET_STATE_RUN，continue 走下一个。trylock 失败或 count != 0：这轮不能跑，把 t 挂回本 CPU 链表尾部，__raise_softirq_irqoff(softirq_nr) 再 raise 一次，等下一个执行时机重试——此时别的 CPU 上那个同款 tasklet 可能已经跑完了。

count != 0 的语义值得单说：说明这个 tasklet 在某次调度之后被 disable 了。挂回链表、重新 raise，等 tasklet_enable 之后的下一个时机执行。这就是 disable 期间不丢任务的实现。

tasklet_kill 是反向操作：

c
void tasklet_kill(struct tasklet_struct *t)
{
    if (in_interrupt())
        printk("Attempt to kill tasklet from interrupt\n");
    while (test_and_set_bit(TASKLET_STATE_SCHED, &t->state)) {
        do {
            yield();
        } while (test_bit(TASKLET_STATE_SCHED, &t->state));
    }
    tasklet_unlock_wait(t);
    clear_bit(TASKLET_STATE_SCHED, &t->state);
}

先看 in_interrupt()，中断里 kill 是错的，打个 warning。然后循环 test_and_set_bit + yield() 等到不再处于被调度状态，tasklet_unlock_wait 等正在跑的跑完，最后清标志。只能在进程上下文调，因为它 yield()。

一个完整用例（素材 4，drivers/usb/atm），四个生命周期动作：probe 里 tasklet_init(&instance->rx_channel.tasklet, usbatm_rx_process, (unsigned long)instance)；发送路径 tasklet_schedule(&instance->tx_channel.tasklet)；disconnect 里 tasklet_disable 再 tasklet_enable（素材未给出这样做的具体原因）；销毁接口里 tasklet_kill(&instance->rx_channel.tasklet)。

驱动的标准动作序列就在这里面：probe 里 init，硬中断末尾 schedule，断开时 disable/enable，销毁前 kill。少最后一步就是 use-after-free——模块卸了，tasklet 还挂在链表上，下次软中断一来跳到野指针。

tasklet 和 ksoftirqd 怎么协作？没有专门协作，全走 softirq 那条通用通道：tasklet 只在 tasklet_vec 上排队然后 raise TASKLET_SOFTIRQ；这个 bit 什么时候被消费取决于 __do_softirq 什么时候跑——可能是 irq_exit、local_bh_enable、或 ksoftirqd；预算耗尽时 wakeup_softirqd()，剩下的 tasklet 由 ksoftirqd/n 在进程上下文里消费。但注意：ksoftirqd 也是调 __do_softirq，所以 tasklet 回调仍然跑在 softirq 上下文里，仍然不能睡。换成线程执行不等于可以睡，这是常见误解。

十七、workqueue：能睡眠的下半部 #

绕回最初的问题。softirq 开中断执行，回调不能睡；tasklet 用 softirq 实现，自然也不能睡。如果某个延迟处理函数必须睡眠或阻塞呢？比如要 kmalloc(GFP_KERNEL)、等一个 mutex、发起同步 I/O。

workqueue 就是为这个存在的。本质：把工作交给内核线程执行。内核线程的创建销毁对编程者要求高，workqueue 把这层封装掉。

四个概念先立住：work（工作）是推后执行的任务，描述结构 work_struct；workqueue（工作队列）把 work 按队列组织起来，描述结构 workqueue_struct；worker（工作线程）负责执行 work，一个 worker 对应一个内核线程；worker_pool（工作线程池）管理 worker 的创建与释放，和 worker 一对多，可以类比线程池。

老内核一个 CPU 只允许一个工作线程，多个 work 排队、每个都可能睡，整体效率很低。后来引入 CMWQ（Concurrency Managed Workqueue），一个 CPU 上允许多个工作线程，又补一个概念 pwq（pool_workqueue）：中间人，把 workqueue 和 worker_pool 连起来。workqueue 和 pwq 一对多，pwq 和 worker_pool 一对一。为什么要这一层？一个 workqueue 在不同 CPU、不同 NUMA 节点上要用不同的 pool，pwq 就是这个「按位置选择」的绑定关系载体。

十八、work_struct 与 schedule_work #

c
struct work_struct {
        atomic_long_t data;
        struct list_head entry;  // 链表结构，链接同一工作队列上的工作
        work_func_t func;        // 工作函数
#ifdef CONFIG_LOCKDEP
        struct lockdep_map lockdep_map;
#endif
};

data 这字段被切碎了用：bit[3:0] 是 flags；bit[7:4] 是 color，给 flush 用的（flush 的语义是销毁 workqueue 之前等队列上的任务全处理完）；剩下高位含义随场景变，可以指向 work 所在的 workqueue 地址（低 8 位被挪用，所以 workqueue 地址要求按 256 字节对齐），也可以表示处理这个 work 的 worker 所在 pool 的 id。

静态/动态创建：

c
#define __WORK_INITIALIZER(n, f) {                                      \
        .data = WORK_DATA_STATIC_INIT(),                                \
        .entry  = { &(n).entry, &(n).entry },                           \
        .func = (f),                                                    \
        __WORK_INIT_LOCKDEP_MAP(#n, &(n))                               \
        }
#define DECLARE_WORK(n, f)  struct work_struct n = __WORK_INITIALIZER(n, f)

#define __INIT_WORK(_work, _func, _onstack)                             \
        do {                                                            \
                __init_work((_work), _onstack);                         \
                (_work)->data = (atomic_long_t) WORK_DATA_INIT();       \
                INIT_LIST_HEAD(&(_work)->entry);                        \
                (_work)->func = (_func);                                \
        } while (0)

#define INIT_WORK(_work, _func)   __INIT_WORK((_work), (_func), 0)

_onstack 标记这个 work 是不是分配在栈上，调试用。

提交工作：queue_work 挂到指定队列，schedule_work / schedule_work_on 挂到默认队列 system_wq。

c
static inline bool queue_work(struct workqueue_struct *wq, struct work_struct *work)
{
        return queue_work_on(WORK_CPU_UNBOUND, wq, work);
}

bool queue_work_on(int cpu, struct workqueue_struct *wq, struct work_struct *work)
{
        bool ret = false;
        unsigned long flags;

        local_irq_save(flags);
        if (!test_and_set_bit(WORK_STRUCT_PENDING_BIT, work_data_bits(work))) {
                __queue_work(cpu, wq, work);
                ret = true;
        }
        local_irq_restore(flags);
        return ret;
}

和 tasklet_schedule 一个套路：test_and_set_bit 抢 WORK_STRUCT_PENDING_BIT，抢到才继续，没抢到说明这个 work 已在队列里，返回 false。原子去重，防一个 work 被挂两次。WORK_CPU_UNBOUND 的意思是「不指定 CPU，交给 __queue_work 现算」；queue_work 的语义是「挂到提交时所在的那个 CPU 的队列上，但这个 CPU 死了别的 CPU 也能接手」。

schedule_work / schedule_work_on 是薄封装，把 wq 固定成 system_wq：

text
schedule_work(work)         ==  queue_work(system_wq, work)
schedule_work_on(cpu, work) ==  queue_work_on(cpu, system_wq, work)

素材只给了 queue_work_on 的实现，这两个内联函数体未逐行核对。它们的存在意义：绝大多数场景不需要自建队列，一把 system_wq 够了。和 queue_work_on 一样可以在中断上下文里调（内部 local_irq_save），区别只在提交到哪。

__queue_work 是真正的排队逻辑，五步走：

text
1. 定 pwq：per-CPU 队列取 per_cpu_ptr(wq->cpu_pwqs, cpu)；
   unbound 队列取 unbound_pwq_by_node(wq, cpu_to_node(cpu))。
2. 防重入：若 work 之前挂在别的 pool 且可能还在跑（get_work_pool +
   find_worker_executing_work 查得到它），必须排到那个 pool 的 pwq，
   否则同一个 work 可能同时在两个 pool 上执行。
3. 重试：unbound 的 pwq 可能正被释放（refcnt 归零），这时 cpu_relax() 后 goto retry。
4. 限额：nr_active < max_active 才进 pool->worklist；否则打上
   WORK_STRUCT_DELAYED，扔进 pwq->delayed_works 排队。
5. 入队：insert_work(pwq, work, worklist, work_flags)。

max_active 决定这个队列对应的 pool 上最多有多少 busy worker。整段在 rcu_read_lock 里，因为要访问可能正在被释放的 pwq/pool；lockdep_assert_irqs_disabled() 要求调用者已经关中断（queue_work_on 里 local_irq_save 过了）。

十九、工作队列的并发管理：per-cpu 与 unbound #

workqueue_struct 是对外可见的对象，在 kernel/workqueue.c。字段按用途分五组：

分组 字段 作用
链表 list / pwqs list 挂全局 workqueues；pwqs 是本队列所有 pwq
flush work_color / flush_color / nr_pwqs_to_flush / first_flusher / flusher_queue / flusher_overflow 销毁前等队列上的 work 全跑完
rescue maydays / rescuer pool 卡死时派救兵
绑定 cpu_pwqs / numa_pwq_tbl[] / unbound_attrs / dfl_pwq cpu_pwqs 是 per-CPU pwq 数组；numa_pwq_tbl[] 按 NUMA 节点索引，unbound 队列走它
标识 name / flags / mutex 队列名；WQ_UNBOUND、WQ_FREEZABLE、WQ_MEM_RECLAIM、WQ_HIGHPRI、WQ_CPU_INTENSIVE、WQ_SYSFS、WQ_POWER_EFFICIENT，内部还有 __WQ_DRAINING、__WQ_ORDERED、__WQ_LEGACY、__WQ_ORDERED_EXPLICIT

worker_pool 是线程池本体，关键字段五个：worklist 是本 pool 待处理的 work 列表；workers 是本 pool 管理着的所有 worker；nr_running 是当前并发度，单独 ____cacheline_aligned_in_smp 对齐一个 cache line，因为 try_to_wake_up() 会从其他 CPU 频繁读它；nr_workers / nr_idle 记数量；busy_hash（6 阶 hash，key 是正在处理的 work 的内存地址）管忙的 worker，idle_list 管闲的：

c
struct worker_pool {
        spinlock_t              lock;           /* the pool lock */
        int                     cpu;            /* I: the associated cpu */
        int                     node;           /* I: the associated node ID */
        int                     id;             /* I: pool ID */
        struct list_head        worklist;       /* L: list of pending works */
        int                     nr_workers;     /* L: total number of workers */
        int                     nr_idle;        /* L: currently idle workers */
        struct list_head        idle_list;      /* X: list of idle workers */
        DECLARE_HASHTABLE(busy_hash, BUSY_WORKER_HASH_ORDER);
        struct list_head        workers;        /* A: attached workers */
        atomic_t                nr_running ____cacheline_aligned_in_smp;
} ____cacheline_aligned_in_smp;

伸缩策略：本 CPU 上所有 worker 都睡死、但队列里还有 work，就 spawn 一个新 worker；反过来空闲 worker 太多就销毁一批省 CPU。本质是负载均衡，细节不展开。

CMWQ 下 pool 分两类：normal worker_pool 给通用 workqueue 用，per-CPU；unbound worker_pool 给 WQ_UNBOUND 的 workqueue 用，不绑 CPU。而且一个 CPU 对应两个 normal pool：一个普通优先级（nice=0），一个高优先级（nice = HIGHPRI_NICE_LEVEL）。同一 CPU 上同优先级的所有 worker 共同构成一个 pool。

worker 是执行体，两个字段结构值得记：entry（idle 链表节点）和 hentry（busy hash 节点）是 union，一个 worker 要么在 idle 链表、要么在 busy hash，不能同时在两处；current_work / current_func / current_pwq 是正在处理的东西和它所属的 pwq；task 是 worker 对应的内核线程，不管 idle 还是 busy 都存在；pool 是所属 pool。

pool_workqueue 是中间人。pool 指向连的 worker_pool，wq 指向连的 workqueue_struct；max_active / nr_active 是该队列最大允许、实际挂载的活跃 work 数；delayed_works 是超了限额排队的地方；nr_in_flight[WORK_NR_COLORS] 按颜色记在途数量，配合 flush 用：

c
struct pool_workqueue {
        struct worker_pool      *pool;          /* I: the associated pool */
        struct workqueue_struct *wq;            /* I: the owning workqueue */
        int                     refcnt;         /* I: reference count */
        int                     nr_in_flight[WORK_NR_COLORS];
        int                     nr_active;      /* L: nr of active works */
        int                     max_active;     /* L: max active works */
        struct list_head        delayed_works;  /* L: delayed works */
        struct work_struct      unbound_release_work;
        struct rcu_head         rcu;
} __aligned(1 << WORK_STRUCT_FLAG_BITS);

__aligned(1 << WORK_STRUCT_FLAG_BITS) 的来由：work_struct->data 低位当 flags、高位存 pwq 指针，所以 pwq 必须按 2^flag_bits 对齐。

建队列。create_workqueue 是老接口，alloc_workqueue 是主入口，前者就是后者的宏：

c
#define create_workqueue(name)                                          \
        alloc_workqueue("%s", __WQ_LEGACY | WQ_MEM_RECLAIM, 1, (name))

alloc_workqueue 的主干。flag 归一化先做两道：

c
        /* Unbound && max_active == 1 used to imply ordered, which is no
         * longer the case on NUMA machines due to per-node pools. */
        if ((flags & WQ_UNBOUND) && max_active == 1)
                flags |= __WQ_ORDERED;

        /* see the comment above the definition of WQ_POWER_EFFICIENT */
        if ((flags & WQ_POWER_EFFICIENT) && wq_power_efficient)
                flags |= WQ_UNBOUND;

第一道是历史兼容：以前「unbound + 单活跃」隐含有序，NUMA 上按节点分 pool 之后不成立了，为了不打破老驱动显式补上。第二道把省电标志翻译成 unbound。

然后是分配与初始化：

c
        if (flags & WQ_UNBOUND)
                tbl_size = nr_node_ids * sizeof(wq->numa_pwq_tbl[0]);

        wq = kzalloc(sizeof(*wq) + tbl_size, GFP_KERNEL);   // 动态分配 workqueue_struct
        if (!wq)
                return NULL;

        vsnprintf(wq->name, sizeof(wq->name), fmt, args);

        max_active = max_active ?: WQ_DFL_ACTIVE;
        max_active = wq_clamp_max_active(max_active, flags, wq->name);

        wq->flags = flags;
        wq->saved_max_active = max_active;
        mutex_init(&wq->mutex);
        INIT_LIST_HEAD(&wq->pwqs);

        if (alloc_and_link_pwqs(wq) < 0)      /* 建 pwq 并绑定 worker_pool */
                goto err_unreg_lockdep;
        if (wq_online && init_rescuer(wq) < 0)
                goto err_destroy;

        for_each_pwq(pwq, wq)
                pwq_adjust_max_active(pwq);

        list_add_tail_rcu(&wq->list, &workqueues); // 挂进全局 workqueue 列表
        return wq;

unbound 队列多分配 numa_pwq_tbl，大小是 nr_node_ids 个指针。max_active 归一化：传 0 用默认 WQ_DFL_ACTIVE，再 wq_clamp_max_active 夹到合法区间。最后 alloc_and_link_pwqs 建 pwq 绑 pool、init_rescuer 准备 rescue worker、挂全局链表。

二十、三种机制的正面对比与选型 #

你的需求 选它 理由
下半部要睡眠（等 mutex、GFP_KERNEL 分配、同步 I/O） workqueue 或 threaded irq softirq/tasklet 睡不得
下半部要延时指定时间再跑 workqueue + delayed_work / timer 复用定时器，不占中断上下文
必须在一个 tick 内处理完 softirq 或 tasklet 能抢占普通进程和内核线程，延迟最低
对延迟没要求，无关紧要的收尾 workqueue 交给调度器最省事
驱动里的小任务，不想自己上锁 tasklet 内核帮你串行化（5.9 起已废弃，新代码改 workqueue 或 threaded irq）
高频、可并行、内核核心路径（网络、块、RCU） softirq 唯一能跨 CPU 并行的下半部
已有线程化中断需求 request_threaded_irq 顶半部只判断，处理函数跑在专属线程

四条判断句背下来：要睡就 workqueue，没得选；要快就 softirq/tasklet，代价是不能睡、不能长跑；驱动里想省心就 workqueue，别为了一点延迟去碰 softirq；自己建 kernel thread 是最后手段，workqueue 已经封装好了。

三条容易忽略的：workqueue 的「不并行」是有条件的，同一个 work 同时只会有一个实例在跑（靠 WORK_STRUCT_PENDING_BIT 去重），但同一个 wq 上不同的 work 可以并行，并行度由 max_active 决定，想让队列严格串行用 alloc_ordered_workqueue；tasklet 的串行只针对「自己」，不同 tasklet 之间仍可跨 CPU 并行，共享数据该上锁还得上；softirq 的并行是无条件的，同一类型 softirq 能在多 CPU 上同时跑你的回调，重入防护是你的责任。

再加一句关于性能的冷静话。tasklet 相比 softirq 损失性能，这是买串行化要付的钱；workqueue 相比 tasklet 损失延迟，这是买可睡眠要付的钱。三者的排序不是「谁更强」，是「谁的约束更松」。选最松的那个能满足需求的。

二十一、易错点速查 #

第一，在 softirq/tasklet 里睡眠。mutex_lock、GFP_KERNEL 分配、wait_event、copy_from_user 都可能睡。in_interrupt() 为真时干这些，轻则 warning，重则死锁。回调里 WARN_ON(in_interrupt()) 能在运行时抓。

第二，以为 ksoftirqd 里跑就可以睡。错。ksoftirqd 也是调 __do_softirq，还是 softirq 上下文。想睡只能上 workqueue。

第三，tasklet_kill 忘了调。模块卸载前必须 kill，否则 tasklet 还挂在链表上，回调跳野指针。tasklet_disable 不够，它只是不执行，节点还在。

第四，把 local_bh_disable 当万能锁。它只挡本地 softirq/tasklet，挡不住硬中断，也挡不住别的 CPU。跨 CPU 共享数据要自旋锁。

第五，在硬中断 handler 里用 local_bh_disable/local_bh_enable 保护数据。softirq 抢不了 top half，这对操作多余，而且 __local_bh_enable_ip 里的 WARN_ON_ONCE(in_irq()) 会当场报警。

第六，local_irq_disable 里套 local_bh_enable。local_bh_enable -> do_softirq -> __do_softirq 有一句无条件开中断，你保护的临界区就漏了。WARN_ON_ONCE(irqs_disabled()) 就是拦这个的。

第七，误读 /proc/softirqs 的 HI 列。全 0 不代表 HI_SOFTIRQ 坏了，正常系统本来就没人用。

第八，以为 softirq 编号小就等于跑得勤。编号只决定同时 pending 时的执行次序，跟触发频率无关。看频率看 /proc/softirqs 的计数增量。

第九，算 __softirq_pending 时忘了 per-CPU。一个 CPU 上 raise 的软中断，另一个 CPU 不会替它处理（除非那个 CPU 自己也有 pending）。raise_softirq 只动本地。

第十，把 preempt_count_sub(cnt - 1) 改成 preempt_count_sub(cnt)。看着更对称，实际会开抢占窗口，让当前 task 可能被迁到别的 CPU，pending 位图就对不上了。

第十一，用 local_irq_enable 恢复中断状态。临界区里用它无条件开中断，覆盖调用者原本的关中断意图。要用 local_irq_restore。

第十二，tasklet 里调 tasklet_schedule 调度自己。合法（注释里那句 "or schedule is called from tasklet itself"），语义是重新排一次，不会立刻重入，也不会无限递归——TASKLET_STATE_SCHED 会去重。真正危险的是「每次执行都无条件 schedule 自己」，那就成了自激循环，一直占着软中断预算。

第十三，DECLARE_TASKLET 的 data 传了栈上的地址。tasklet 执行时机不确定，栈帧可能早没了。传堆上的或全局的。

第十四，cross-CPU 的性能预期错位。以为加核就能线性提升网络吞吐，但中断全压在 CPU0（没配 RPS/多队列），softirq 再多核也分不出去。看 /proc/softirqs 分布就知道。
