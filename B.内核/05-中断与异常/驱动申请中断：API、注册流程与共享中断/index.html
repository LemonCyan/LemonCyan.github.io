一、申请中断这件事，驱动要交给内核哪些信息 #

早期处理器存在 IRQ 编号共享问题，Linux 中断子系统从一开始就按「中断共享」模式设计，ISR 安装分两级：

  • 第一级针对这根 IRQ 线，叫 generic handler（也叫 highlevel irq-events handler），即 desc->handle_irq，管流控：ack、mask、EOI、unmask。
  • 第二级针对挂在这根线上的不同设备，叫 specific handler，挂在 desc->action 这条 irqaction 链表上。

驱动只碰第二级。第一级在中断控制器注册时初始化，s3c24xx_irq_map 里那句 irq_set_chip_and_handler 干的就是这活。驱动要交的四样东西全塞进一个 struct irqaction：

你要给的 落到哪个字段 干什么用
中断号 ->irq（__setup_irq 回填） 定位 irq_desc，找到 action 链表
处理函数 ->handler / ->thread_fn 硬中断上下文跑一个，内核线程里跑一个
触发类型与行为 ->flags 电平/边沿、共享、oneshot、可否线程化
名字与设备 ID ->name / ->dev_id /proc/interrupts 显示；共享中断里当识别码 
c
struct irqaction {
    irq_handler_t        handler;      /* 硬中断上下文的 primary handler */
    void                *dev_id;       /* 传回 handler 的参数，共享线上当识别码 */
    void __percpu       *percpu_dev_id;/* per-CPU 中断用的 dev_id */
    struct irqaction    *next;         /* 同一根 IRQ 线上的下一个 action */
    irq_handler_t        thread_fn;    /* 内核线程里跑的函数 */
    struct task_struct  *thread;       /* 该 action 专属的 irq 线程 */
    struct irqaction    *secondary;    /* 强制线程化时挂第二个 action，4.x 才有 */
    unsigned int         irq;
    unsigned int         flags;        /* IRQF_* 全在这里 */
    unsigned long        thread_flags; /* IRQTF_*，内核内部用 */
    unsigned long        thread_mask;  /* ONESHOT 在共享线上的位标识 */
    const char          *name;
    struct proc_dir_entry *dir;
} ____cacheline_internodealigned_in_smp;

三个字段单独记：thread_flags 存 IRQTF_RUNTHREAD、IRQTF_FORCED_THREAD、IRQTF_AFFINITY；thread_mask 只在 IRQF_ONESHOT 时有意义，非 oneshot 保持 0，irq_wake_thread 里省一次条件判断；secondary 是 4.x 形态，3.x 的 irq_setup_forced_threading 里没有它，引入版本未验证。

二、request_irq 与 request_threaded_irq 的关系 #

一句话：request_irq 就是 request_threaded_irq 把 thread_fn 写死成 NULL 的包装。内核里成千上万的旧驱动按老接口写，全改不现实，于是留这个壳。3.x 是 static inline，较新内核换成语句表达式宏，调用点写法不变：

c
/* 3.x */
static inline int __must_check
request_irq(unsigned int irq, irq_handler_t handler, unsigned long flags,
        const char *name, void *dev)
{
    return request_threaded_irq(irq, handler, NULL, flags, name, dev);
}
/* 较新内核：语句表达式宏 */
#define request_irq(irq, func, irqflags, devname, dev_id)          \
({                                                                 \
    int __ret = request_threaded_irq(irq, func, NULL, irqflags,    \
                                     devname, dev_id);             \
    __ret;                                                         \
})

宏化对驱动没影响，传参顺序、语义都一样。哪种形态从哪个 tag 开始，未验证。

对比项 request_irq request_threaded_irq
参数个数 5 6，多一个 thread_fn
中断线程 不创建（除非被强制线程化） thread_fn 非空就建
处理位置 全在硬中断上下文 硬中断 + 内核线程两段
能否睡 不能 thread_fn 里可以 msleep、可以走慢速总线
返回值语义 与右边完全一致 0 成功，负数失败
适合场景 极短、纯寄存器操作 要等待、要加锁、要走 I2C/SPI
共享中断 能用 能用，两段分离本身就是为共享设计的

kerneldoc 那句「This split handler design is necessary to support shared interrupts」说的就是最后一行：一根线被多个设备共享时，硬中断段必须先问「是不是你的中断」，问完立刻关掉设备侧中断，再唤醒线程做慢活。全在硬中断里做完，共享线的关中断时间会被最慢的设备拖死。

三、为什么要有中断线程化 #

Linux 把外设中断切成 top half 和 bottom half。三类 bottom half 的差别，驱动侧只关心运行上下文与能否阻塞：

机制 运行上下文 能不能阻塞
softirq 中断上下文（软中断） 不能
tasklet 中断上下文（基于 softirq） 不能
workqueue 进程上下文 能

问题在优先级：bottom half 被延迟执行，但它始终先于进程执行。一个驱动的 tasklet 再慢，普通进程也只能干等。凭什么？让这些耗时的 bottom half 去和普通进程抢 CPU 不好吗。

这就是中断线程化的出发点：把耗时的驱动 interrupt handler 线程化，让线程——内核线程、用户态线程、驱动的 interrupt thread——在同一调度舞台上按优先级竞争 CPU。对比 RTOS：我接触过一款 RTOS，中断 handler 简单到极点，发一个 inter-task message 给该驱动的 thread，任何驱动都这么处理。于是每个中断上下文都极短，行为一致，剩下的活交给系统设计师仔细分配 task 优先级。Linux 借鉴这个思路，但没走那么极端，理由见第六节。

四、非抢占式内核的实时性 #

Linux 2.4 之前不支持抢占。高优先级任务（图里橘色 block）等外部事件，比如网络数据，于是睡眠。调度器挑了某个低优先级任务（紫色 block）跑。它跑得正欢，直到触发一次系统调用——比如 read() 读磁盘——进了内核态。外部事件总在你不想让它来的时候来：T0 时刻，高优先级任务等的那个中断事件发生了。

中断发生了，软件不一定立刻响应。内核态某些操作不希望被打断，主动关了中断：要么关 CPU 中断，要么 MASK 掉这个 IRQ number。这期间中断信号没得到响应，软件还在跑低优先级任务的系统调用代码。

T1 时刻，内核态代码退出临界区，开中断。中断一开立刻跳到异常向量地址，interrupt handler 抢占低优先级任务，进入中断上下文。注意：此时 current 还是那个低优先级任务，但中断上下文和它没关系。

从 CPU 开始处理中断到具体服务程序被执行，中间还有分发过程：确定 HW interrupt ID、确定 IRQ Number、ack 或 mask 中断、调用中断服务程序。T0 到 T2 这段 delay 叫中断延迟（Interrupt Latency），两部分构成：硬件侧（中断系统识别外部事件并 signal 到 CPU）、软件侧（内核代码为保护临界区而关中断）。

T2 到 T3 是服务程序执行。执行中（T3）它唤醒高优先级任务，让后者从 sleep 进 runnable，然后返回低优先级任务的系统调用现场。关键：这时没有抢占点。低优先级任务必须把系统调用做完，在返回用户空间那一刻才有抢占点。漫长的等待之后，T4 时刻调度器才调度高优先级任务。T3 到 T4 的 delay 叫任务响应时间（Task Response Time）。原文两张时序图在抓取时丢了，这里照文字复原。

五、抢占式内核的实时性 #

2.6 与 2.4 的显著差别是多一个 CONFIG_PREEMPT。打开后内核代码可被抢占——临界区里不行。T0 到 T3 行为完全一样，差别全在 T4：2.4 只有返回用户空间时才有抢占点；抢占式内核从中断上下文返回内核空间的进程上下文时，只要不在临界区，就可以调度，让最高优先级任务立刻跑。

说准一点：非抢占式内核里「任务内核态不可被其他进程抢占」，指的是进程通过系统调用陷入内核时不能被别的进程抢。内核空间本身当然可被抢——中断上下文能抢占进程上下文（不管进程在用户态还是内核态），而且中断上下文权限最高，它甚至能抢占其他中断上下文。

引入抢占后平均任务响应时间缩短了。但实时性关心的不是平均，是「任何负载下响应时间都确定」，所以要盯 worst-case。两个因素在拖后腿：一是为同步，内核里总有些代码要持自旋锁或显式 preempt_disable()，这些区间不许抢；二是中断上下文（不只是 handler，还包括 softirq、timer、tasklet）永远能抢占进程上下文。

结论：即使开了 PREEMPT，任务响应时间依然不确定。一方面内核临界区太多，得找出「持锁或禁抢占」的最长时间片；另一方面 T4 那一刻能顺利调度高优先级任务并不容易，这时候有触发的软中断、有新来的中断、有某个驱动的 tasklet 要跑，只有全部 bottom half 清空了，调度器才启动调度。

六、进一步提高实时性：线程化的由来 #

由上两节能得出一个判断：中断是 Linux 实时性的头号对手。内核给两条路。

第一条，CONFIG_IRQ_FORCED_THREADING。打开这个配置，系统支持把能线程化的中断全部线程化——哪怕你只给了 primary handler。真正生效还要启动参数 threadirqs，bootloader 不传，force_irqthreads 就是 0，强制线程化什么也不做。

第二条，显式线程化，request_threaded_irq 传 thread_fn。这条路驱动自己选，可控。

线程化之后中断变成内核线程，可以被赋予不同的实时优先级。实时任务可以有比中断线程更高的优先级，于是即便重负载，最高优先级的实时任务依然能优先处理。但不是所有中断都能线程化。时钟中断是典型：它维护系统时间、驱动定时器，定时器是操作系统的脉搏，一旦被线程化就有可能被挂起，后果不堪设想。这类中断用 IRQF_NO_THREAD 标出来。

素材 4 说 request_threaded_irq 是 2.6.30 之后新增的 API。照实记录这个节点，未独立验证。

七、request_threaded_irq 的接口规格 #

原型（kernel/irq/manage.c）：

c
int request_threaded_irq(unsigned int irq, irq_handler_t handler,
                         irq_handler_t thread_fn, unsigned long irqflags,
                         const char *devname, void *dev_id);

kerneldoc 关键段（4.x）：

c
/**
 *  @handler:   Primary handler for threaded interrupts. If NULL and
 *              thread_fn != NULL the default primary handler is installed
 *  @thread_fn: If NULL, no irq thread is created
 *  @dev_id:    A cookie passed back to the handler function
 *
 *  @handler is still called in hard interrupt context and has to check
 *  whether the interrupt originates from the device. If yes it needs to
 *  disable the interrupt on the device and return IRQ_WAKE_THREAD which
 *  will wake up the handler thread and run @thread_fn. This split handler
 *  design is necessary to support shared interrupts.
 *
 *  If your interrupt is shared you must pass a non NULL dev_id as this is
 *  required when freeing the interrupt.
 */

两句硬约束，背下来比查文档快：handler 在硬中断上下文跑，职责是判断中断是不是自己设备的，是就关掉设备侧中断并返回 IRQ_WAKE_THREAD；dev_id 必须全局唯一，常规做法是传设备数据结构体的地址，释放时靠它认人。

irq_handler_t 的签名是 irqreturn_t (*)(int irq, void *dev_id)，两个 handler 一样，返回值语义见第九节。

参数 类型 说明
irq unsigned int 要注册 handler 的 IRQ number，primary 与 threaded 都挂它上面
handler irq_handler_t primary handler，硬中断上下文。可与 thread_fn 二选一，不能同时为 NULL
thread_fn irq_handler_t threaded handler。非 NULL 时内核为它建一个内核线程
irqflags unsigned long IRQF_*，见第十节
devname const char * 设备名，cat /proc/interrupts 能看到
dev_id void * 传回 handler 的参数；共享中断时不可为 NULL

八、输入参数逐个说 #

handler 和 thread_fn 的组合只有四种（素材 2 的表格抓取时被截断，这里补全）：

primary threaded 结果
NULL NULL 出错，返回 -EINVAL
设定 设定 正常。硬中断段做确认，线程段做剩下的
设定 NULL 正常，全部处理都在 primary 里完成（可能用 bottom half 兜底）
NULL 设定 装一个默认 primary handler，它只负责唤醒线程

第四种不是免费的。默认 primary 是：

c
static irqreturn_t irq_default_primary_handler(int irq, void *dev_id)
{
    return IRQ_WAKE_THREAD;
}

它只唤醒线程，不清中断。电平触发时外设的 asserted 电平还在，primary 执行完、CPU 一开中断，立刻又触发同一个中断，无限循环。所以内核设了闸：handler == NULL 且没设 IRQF_ONESHOT，直接 -EINVAL，日志是 Threaded irq requested with handler=NULL and !ONESHOT for irq %d。唯一豁免是底层 irq chip 本身 one shot safe，即带 IRQCHIP_ONESHOT_SAFE（MSI 类天生如此）——这种芯片上驱动设的 IRQF_ONESHOT 属于画蛇添足，内核会抹掉。

dev_id 有两副面孔，别混：释放时是身份识别码，free_irq(irq, dev_id) 得靠它精准定位要摘掉的那个 action；触发时是纯参数，流控层遍历链表，把 action->dev_id 原样传给 action->handler(irq, action->dev_id)，它不参与「该调哪个 handler」的决策。因为第二点，共享中断的识别责任落在驱动身上：handler 开头就得读寄存器判断「是不是我」，不是就立刻返回 IRQ_NONE。

devname 别乱填。/proc/interrupts 按名字区分设备，共享线那一行会并排列出所有 action 的 name。重名不影响功能，但排查问题时你会想抽自己。还有个细节来自 irq_settings_is_per_cpu_devid(desc)：如果描述符是 per-CPU 的，申请 handler 有两种方式——传统一的 dev_id，或每个 CPU 各传一个不同的 dev_id。后者必须走 request_percpu_irq，不能拿 request_threaded_irq 硬凑。

九、返回值的含义与错误码 #

0 成功，负数失败。request_irq 声明带 __must_check，不检查返回值编译器会告警。

返回值 出处 含义
0 正常返回 申请成功，中断已使能
-EINVAL (irqflags & IRQF_SHARED) && !dev_id 共享中断没给 dev_id
-EINVAL !desc IRQ number 查不到 irq_desc
-EINVAL !irq_settings_can_request(desc) 该 IRQ 标了 IRQ_NOREQUEST，不许驱动申请
-EINVAL WARN_ON(irq_settings_is_per_cpu_devid(desc)) per-CPU 中断走错接口，该用 request_percpu_irq
-EINVAL !handler && !thread_fn 两个 handler 都是 NULL
-ENOMEM kzalloc(sizeof(struct irqaction)) 失败 内存不足
-ENOTCONN irq == IRQ_NOTCONNECTED（4.x） 中断未连接
-EINVAL IRQF_COND_SUSPEND 与非共享或 IRQF_NO_SUSPEND 冲突（4.x） 睡眠标志组合非法
-EBUSY __setup_irq 的 mismatch 分支 共享中断标志位不匹配
-EBUSY thread_mask == ~0UL oneshot 线程位用完，共享线 action 太多

十、中断类型标志 flags 全表 #

定义在 include/linux/interrupt.h。IRQF_TRIGGER_* 属于电气属性：

c
/*
 * These correspond to the IORESOURCE_IRQ_* defines in
 * linux/ioport.h to select the interrupt line behaviour.  When
 * requesting an interrupt without specifying a IRQF_TRIGGER, the
 * setting should be assumed to be "as already configured", which
 * may be as per machine or firmware initialisation.
 */
#define IRQF_TRIGGER_NONE       0x00000000    /* 不指定 */
#define IRQF_TRIGGER_RISING     0x00000001    /* 上升沿 */
#define IRQF_TRIGGER_FALLING    0x00000002    /* 下降沿 */
#define IRQF_TRIGGER_HIGH       0x00000004    /* 高电平 */
#define IRQF_TRIGGER_LOW        0x00000008    /* 低电平 */
#define IRQF_TRIGGER_MASK       (IRQF_TRIGGER_HIGH | IRQF_TRIGGER_LOW | \
                                 IRQF_TRIGGER_RISING | IRQF_TRIGGER_FALLING)
#define IRQF_TRIGGER_PROBE      0x00000010

IRQF_TRIGGER_MASK 两个用处：判断调用者到底有没有指定触发类型（为假就继承默认值），共享中断时比对双方是否一致。

c
#define IRQF_SHARED             0x00000080  /* 多个设备共享一根 IRQ 线 */
#define IRQF_PROBE_SHARED       0x00000100  /* 预期会有共享不匹配，别打冗余日志 */
#define __IRQF_TIMER            0x00000200  /* 时钟中断 */
#define IRQF_PERCPU             0x00000400  /* 属于特定 CPU 的中断，非全局共享 */
#define IRQF_NOBALANCING        0x00000800  /* 不参与多 CPU 间的中断均衡 */
#define IRQF_IRQPOLL            0x00001000  /* 该中断用于轮询 */
#define IRQF_ONESHOT            0x00002000  /* 线程处理期间保持中断关闭，不重入 */
#define IRQF_NO_SUSPEND         0x00004000  /* suspend 时不 disable 该中断 */
#define IRQF_FORCE_RESUME       0x00008000  /* resume 时强制 enable */
#define IRQF_NO_THREAD          0x00010000  /* 该中断不可线程化 */
#define IRQF_EARLY_RESUME       0x00020000  /* 在 syscore 阶段提前 resume */
#define IRQF_COND_SUSPEND       0x00040000  /* 与 NO_SUSPEND 用户共存时的特殊处理 */
#define IRQF_TIMER              (__IRQF_TIMER | IRQF_NO_SUSPEND | IRQF_NO_THREAD)

逐个说人话。

IRQF_DISABLED 已废弃，新内核里没有任何作用。旧内核（2.6.35 之前）分 fast handler 和 slow handler：fast 注册时传它，保证处理期间关 CPU 中断，因为跑得快；外设中断不都那么快（磁盘典型），于是有 slow handler 一说，处理期间不关 CPU 中断，否则拖累 performance。新内核不再区分，全是 fast handler，全都关 CPU 中断，需要后续处理的活推到 threaded handler。素材列了它一整段，结论只有一句：别再用。

IRQF_SHARED 表示这根 line 允许多设备共享。前提是控制器支持足够多的 interrupt source——不够才不得不共享。共享有额外开销：中断来了要逐个 action 问过去，软件上就是遍历链表，所以 handler 开头必须判断「是不是我」，不是就返回 IRQ_NONE。早期 PC 用 8259，级联最多 15 个外部中断，外设那么多只能共享。ARM 平台很少这么干，SOC 的有中断功能的 GPIO 够多。真要让两个外设共享一根线，硬件上也不能把两个 interrupt request line 直接并到控制器的一个 source 引脚——低电平触发的情况，得用与门把控制器和外设隔开。

IRQF_PROBE_SHARED 配合 IRQF_SHARED 用。有些驱动只想扫一遍 irq table 看哪个能用，即便不能共享也无所谓，它已预见到 sharing mismatch。设上这个标志，内核就不打印 Flags mismatch irq... 那类冗余信息。它只压日志，不影响判定——mismatch 照样 -EBUSY。

IRQF_PERCPU 涉及 SMP 两种中断模式。全局中断在所有 processor 间共享：一旦产生，控制器可以送达多个处理器（实现上不会同时送，一般软硬协同只送一个，但一段时间内的中断可以按策略分摊到一组 CPU）。这类中断的 operational register 是 global 的，一套寄存器所有 CPU 都看得见，一个 CPU ack 了，别的 CPU 看到的状态也是已 ack。

per CPU 中断则专属某个 CPU。GIC 里 interrupt ID 为 30 的中断就是（各 CPU 的 local timer 用它）。中断号只有一个，但控制该 ID 的寄存器有 n 组（n 是 processor 数），每个 CPU 看到自己那份。寄存器组两种形态：banked——所有 CPU 操作同一地址，硬件按访问者定向；non-banked——每个 CPU 各有访问地址。per CPU 中断不适合线程化，8 核系统上一个 percpu 中断线程化就要建 8 个内核线程，得不偿失。所以 irq_setup_forced_threading 见到它直接放行。

IRQF_NOBALANCING 也与 SMP 相关。能在多 CPU 间共享的中断，送哪个 processor 有策略，可以做平衡。你不想让自己的中断参与 irq balancing，就设它。

IRQF_ONESHOT 是最需要理解的一个。one shot 意思是「只有一次」，落到中断场景就是一次性触发、不能嵌套。primary handler 天然不嵌套；有选择的是 threaded handler：处理期间要么 mask 中断源，要么 unmask。一旦 mask 住，整个 threaded handler 执行期间该中断源都不会再触发，这就是 one shot，这种 handler 不用考虑重入。

是否设 oneshot 取决于硬件。具体例子：电池驱动里有个电量计走 HDQ 协议通信，驱动注册 threaded handler 在里面跟电量计对话。这个对话需要完整交互过程，中间被打断就废了。所以该 handler 必须 one shot。IRQF_ONESHOT 在共享线上的实现是位图：每个 oneshot action 各占 thread_mask 的一个 bit，全处理完才 unmask 中断线。

IRQF_SHARED 与 IRQF_ONESHOT 能不能同时用？ 素材 4 说不能，理由是 oneshot 在线程期间禁用中断，处理时间长不适用。这说法与源码不符：__setup_irq 的共享检查明确要求双方 IRQF_ONESHOT 一致（(old->flags ^ new->flags) & IRQF_ONESHOT），并专门为共享的 oneshot 中断设计了多位 thread_mask。所以两者可以共存，条件是全线上所有 action 都设。本文按源码走，素材 4 这句判为错误。

IRQF_NO_SUSPEND：suspend 时不禁用该中断，禁用了可能导致系统醒不过来。IRQF_FORCE_RESUME 是它的补丁：resume 时强制 enable，即便设了 IRQF_NO_SUSPEND，跟具体硬件行为相关。

IRQF_NO_THREAD 标明该中断不能线程化。系统 timer 是典型；级联中断控制器对应的 IRQ 也不行（比如 secondary GIC 的 IRQ）——它一线程化，附着在这个控制器下的一大批外设中断响应延迟都受影响。

IRQF_EARLY_RESUME：在 syscore 阶段提前 resume，而不是等到 device resume。IRQF_COND_SUSPEND：当该中断与一个 IRQF_NO_SUSPEND 用户共享时，本 handler 在 suspend 中断之后才执行；系统唤醒设备需要在自己的 handler 里实现 wakeup 检测。

IRQF_TIMER 是组合宏，等于 __IRQF_TIMER | IRQF_NO_SUSPEND | IRQF_NO_THREAD。它把 IRQF_NO_THREAD 包进去了，所以 timer 中断天然免疫强制线程化。IRQF_IRQPOLL 用于轮询场景，共享中断里只有第一个注册的 action 参与，算性能考虑。

十一、request_threaded_irq 主流程代码分析 #

4.x 形态：

c
int request_threaded_irq(unsigned int irq, irq_handler_t handler,
                         irq_handler_t thread_fn, unsigned long irqflags,
                         const char *devname, void *dev_id)
{
    struct irqaction *action;
    struct irq_desc *desc;
    int retval;
    if (irq == IRQ_NOTCONNECTED)
        return -ENOTCONN;
    /* 共享中断必须给真 dev_id；IRQF_COND_SUSPEND 只对共享中断有意义，
     * 且不能与 IRQF_NO_SUSPEND 并存。
     */
    if (((irqflags & IRQF_SHARED) && !dev_id) ||
        (!(irqflags & IRQF_SHARED) && (irqflags & IRQF_COND_SUSPEND)) ||
        ((irqflags & IRQF_NO_SUSPEND) && (irqflags & IRQF_COND_SUSPEND)))
        return -EINVAL;
    desc = irq_to_desc(irq);                    /* (2) 按 IRQ 号取中断描述符 */
    if (!desc)
        return -EINVAL;
    if (!irq_settings_can_request(desc) ||      /* (3) IRQ_NOREQUEST 的不许申请 */
        WARN_ON(irq_settings_is_per_cpu_devid(desc)))
        return -EINVAL;
    if (!handler) {                             /* (4) 默认 primary handler */
        if (!thread_fn)
            return -EINVAL;
        handler = irq_default_primary_handler;
    }
    action = kzalloc(sizeof(struct irqaction), GFP_KERNEL);
    if (!action)
        return -ENOMEM;
    action->handler = handler;
    action->thread_fn = thread_fn;
    action->flags = irqflags;
    action->name = devname;
    action->dev_id = dev_id;
    retval = irq_chip_pm_get(&desc->irq_data);
    if (retval < 0) {
        kfree(action);
        return retval;
    }
    retval = __setup_irq(irq, desc, action);    /* (5) 真正干活的在这 */
    if (retval) {
        irq_chip_pm_put(&desc->irq_data);
        kfree(action->secondary);
        kfree(action);
    }
    return retval;
}

3.x 骨架一样，差别在两处：开头只有 (irqflags & IRQF_SHARED) && !dev_id 一道检查；收尾用 chip_bus_lock / chip_bus_sync_unlock 包住 __setup_irq，没有 irq_chip_pm_get/put，失败路径也不 kfree——那版 __setup_irq 自己负责释放。

（1）共享中断必须给 dev_id。 共享时一个 IRQ number 对应若干 irqaction，操作 action 时只给 IRQ number 不够，free_irq 就得两个参数：

c
void free_irq(unsigned int irq, void *dev_id)

那 dev_id 在中断处理中有没有用？看流控层的遍历：

c
irqreturn_t handle_irq_event_percpu(struct irq_desc *desc, struct irqaction *action)
{
    do {
        irqreturn_t res;
        res = action->handler(irq, action->dev_id);
        ...
        action = action->next;
    } while (action);
    ...
}

dev_id 只是被原样喂给 handler，不决定调哪个 handler。整条链会被全部走一遍——哪怕只有一个外设真产生了中断。这是共享的固有成本。

（2）按 IRQ number 取描述符。 引入 CONFIG_SPARSE_IRQ 之后这步不简单了。过去以 IRQ number 为下标从全局 irq_desc 数组直接取；配了 sparse 就得从 radix tree 里搜。irq_to_desc 把两种实现藏在后面。

（3）不是所有 IRQ 都能申请。 有些描述符标了 IRQ_NOREQUEST，不允许驱动申请。这类 IRQ 通常有特殊用途——用于级联的那个 IRQ number 就是典型，它只能当通道，不能挂 specific handler。irq_settings_is_per_cpu_devid 判断是否要传 per-CPU 的 device ID，这类中断得用 request_percpu_irq。

（4）handler 组合校验。 见第八节的表。

（5）分配 action、填字段、交给 __setup_irq。 注意锁。内核里有大量成对函数：需调用者加锁的和不加锁的，后者加 __ 前缀，例如 setup_irq 和 __setup_irq。3.x 在调用前已用 chip_bus_lock 保护：

c
static inline void chip_bus_lock(struct irq_desc *desc)
{
    if (unlikely(desc->irq_data.chip->irq_bus_lock))
        desc->irq_data.chip->irq_bus_lock(&desc->irq_data);
}

大部分控制器没实现 irq_bus_lock，这调用对它们毫无意义。例外是挂在慢速总线上的控制器，比如 I2C 接口的 IO expander（这类芯片往往也有若干有中断功能的 GPIO，所以它本身就是中断控制器）。访问这种控制器得先锁住 I2C bus，因为同一时刻只能有一个 client 用。3.x 把这层锁包在 request_threaded_irq 外面，4.x 挪进 __setup_irq 内部——读代码别拿一个版本套另一个。

十二、注册 irqaction：__setup_irq 做什么 #

它也在 kernel/irq/manage.c，是整个注册过程的真身。注释把锁规则写得很清楚：

text
 * desc->request_mutex    Provides serialization against a concurrent free_irq()
 *   chip_bus_lock        Provides serialization for slow bus operations
 *     desc->lock         Provides serialization against hard interrupts

三层锁从外到内：request_mutex 挡并发 free_irq，chip_bus_lock 保护慢速总线操作，desc->lock 挡硬中断。完整函数（4.x 形态，长注释压成单行，控制流一字未改）：

c
static int
__setup_irq(unsigned int irq, struct irq_desc *desc, struct irqaction *new)
{
    struct irqaction *old, **old_ptr;
    unsigned long flags, thread_mask = 0;
    int ret, nested, shared = 0;
    if (!desc)
        return -EINVAL;
    if (desc->irq_data.chip == &no_irq_chip)
        return -ENOSYS;
    if (!try_module_get(desc->owner))
        return -ENODEV;
    new->irq = irq;
    /* 调用者没指定触发类型，就继承该中断的默认配置 */
    if (!(new->flags & IRQF_TRIGGER_MASK))
        new->flags |= irqd_get_trigger_type(&desc->irq_data);
    /* 判断是否嵌套进另一个中断线程 */
    nested = irq_settings_is_nested_thread(desc);
    if (nested) {
        if (!new->thread_fn) {
            ret = -EINVAL;
            goto out_mput;
        }
        new->handler = irq_nested_primary_handler;
    } else {
        if (irq_settings_can_thread(desc)) {
            ret = irq_setup_forced_threading(new);
            if (ret)
                goto out_mput;
        }
    }
    /* 有 thread_fn 且不嵌套，才创建中断线程 */
    if (new->thread_fn && !nested) {
        ret = setup_irq_thread(new, irq, false);
        if (ret)
            goto out_mput;
        if (new->secondary) {
            ret = setup_irq_thread(new->secondary, irq, true);
            if (ret)
                goto out_thread;
        }
    }
    /* MSI 类芯片本身就 one shot safe：抹掉该标志，省掉线程末尾的 unmask */
    if (desc->irq_data.chip->flags & IRQCHIP_ONESHOT_SAFE)
        new->flags &= ~IRQF_ONESHOT;
    /* 防并发 __free_irq() 等待 synchronize_hardirq()，
     * 也防止复用仍被前人占用的 oneshot thread_mask 位
     */
    mutex_lock(&desc->request_mutex);
    chip_bus_lock(desc);
    /* 第一个装上的 action 负责申请资源 */
    if (!desc->action) {
        ret = irq_request_resources(desc);
        if (ret) {
            pr_err("Failed to request resources for %s (irq %d) on irqchip %s\n",
                   new->name, irq, desc->irq_data.chip->name);
            goto out_bus_unlock;
        }
    }
    /* 以下必须在 desc->lock 下原子执行 */
    raw_spin_lock_irqsave(&desc->lock, flags);
    old_ptr = &desc->action;
    old = *old_ptr;
    if (old) {
        unsigned int oldtype;
        if (desc->istate & IRQS_NMI) {
            pr_err("Invalid attempt to share NMI for %s (irq %d) on irqchip %s.\n",
                new->name, irq, desc->irq_data.chip->name);
            ret = -EINVAL;
            goto out_unlock;
        }
        /* 没人设过配置，就继承申请者提供的这份 */
        if (irqd_trigger_type_was_set(&desc->irq_data)) {
            oldtype = irqd_get_trigger_type(&desc->irq_data);
        } else {
            oldtype = new->flags & IRQF_TRIGGER_MASK;
            irqd_set_trigger_type(&desc->irq_data, oldtype);
        }
        /* 双方都得同意共享、触发类型一致、ONESHOT 一致 */
        if (!((old->flags & new->flags) & IRQF_SHARED) ||
            (oldtype != (new->flags & IRQF_TRIGGER_MASK)) ||
            ((old->flags ^ new->flags) & IRQF_ONESHOT))
            goto mismatch;
        /* 所有 handler 的 per-CPU 属性必须一致 */
        if ((old->flags & IRQF_PERCPU) !=
            (new->flags & IRQF_PERCPU))
            goto mismatch;
        /* 把新 action 挂到队列尾，同时 or 所有已有 thread_mask 位 */
        do {
            thread_mask |= old->thread_mask;
            old_ptr = &old->next;
            old = *old_ptr;
        } while (old);
        shared = 1;
    }
    /* ONESHOT 的 action 才分配 thread_mask 位；
     * 非 ONESHOT 保持 0，省掉 irq_wake_thread() 里一次条件判断
     */
    if (new->flags & IRQF_ONESHOT) {
        if (thread_mask == ~0UL) {      /* 一根线上 32/64 个 action，极小概率 */
            ret = -EBUSY;
            goto out_unlock;
        }
        /* 该位在线程被唤醒但未完成期间 or 进 desc->thread_active，
         * 线程完成后清掉；共享线上所有线程都做完，threads_active 归零
         * 才 unmask 中断线（见 handle.c:irq_wake_thread()）。
         */
        new->thread_mask = 1UL << ffz(thread_mask);
    } else if (new->handler == irq_default_primary_handler &&
           !(desc->irq_data.chip->flags & IRQCHIP_ONESHOT_SAFE)) {
        /* handler=NULL 用的是默认 primary，它只唤醒线程、不清中断。
         * 电平中断下中断线重新使能时电平仍 asserted：死循环。
         * 边沿其实没事，但触发标志不可靠（控制器可以覆盖），一刀切全拒。
         */
        pr_err("Threaded irq requested with handler=NULL and !ONESHOT for irq %d\n",
               irq);
        ret = -EINVAL;
        goto out_unlock;
    }
    if (!shared) {
        init_waitqueue_head(&desc->wait_for_threads);
        if (new->flags & IRQF_TRIGGER_MASK) {
            ret = __irq_set_trigger(desc,
                        new->flags & IRQF_TRIGGER_MASK);
            if (ret)
                goto out_unlock;
        }
        /* 激活必须独立于 IRQ_NOAUTOEN：request_irq() 可能失败，
         * 而 IRQ_NOAUTOEN 中断的 enable_irq() 不该失败
         */
        ret = irq_activate(desc);
        if (ret)
            goto out_unlock;
        desc->istate &= ~(IRQS_AUTODETECT | IRQS_SPURIOUS_DISABLED | \
                  IRQS_ONESHOT | IRQS_WAITING);
        irqd_clear(&desc->irq_data, IRQD_IRQ_INPROGRESS);
        if (new->flags & IRQF_PERCPU) {
            irqd_set(&desc->irq_data, IRQD_PER_CPU);
            irq_settings_set_per_cpu(desc);
        }
        if (new->flags & IRQF_ONESHOT)
            desc->istate |= IRQS_ONESHOT;
        if (new->flags & IRQF_NOBALANCING) {
            irq_settings_set_no_balancing(desc);
            irqd_set(&desc->irq_data, IRQD_NO_BALANCING);
        }
        if (irq_settings_can_autoenable(desc)) {
            irq_startup(desc, IRQ_RESEND, IRQ_START_COND);
        } else {
            /* 共享中断与「禁用自动使能」凑一起会出事：共享方可能在
             * 中断还关着时申请，然后永远等不到中断
             */
            WARN_ON_ONCE(new->flags & IRQF_SHARED);
            desc->depth = 1;    /* 撤销嵌套的 disable */
        }
    } else if (new->flags & IRQF_TRIGGER_MASK) {
        unsigned int nmsk = new->flags & IRQF_TRIGGER_MASK;
        unsigned int omsk = irqd_get_trigger_type(&desc->irq_data);
        if (nmsk != omsk)
            pr_warn("irq %d uses trigger mode %u; requested %u\n",
                irq, omsk, nmsk);
    }
    *old_ptr = new;
    irq_pm_install_action(desc, new);
    /* 装上新 handler 时重置坏中断检测 */
    desc->irq_count = 0;
    desc->irqs_unhandled = 0;
    /* 之前被 spurious handler 关过的话，重新使能给一次机会 */
    if (shared && (desc->istate & IRQS_SPURIOUS_DISABLED)) {
        desc->istate &= ~IRQS_SPURIOUS_DISABLED;
        __enable_irq(desc);
    }
    raw_spin_unlock_irqrestore(&desc->lock, flags);
    chip_bus_sync_unlock(desc);
    mutex_unlock(&desc->request_mutex);
    irq_setup_timings(desc, new);
    /* 严格说不用唤醒，但不唤醒 hung_task 会报警 */
    if (new->thread)
        wake_up_process(new->thread);
    if (new->secondary)
        wake_up_process(new->secondary->thread);
    register_irq_proc(irq, desc);
    new->dir = NULL;
    register_handler_proc(irq, new);
    return 0;
mismatch:
    if (!(new->flags & IRQF_PROBE_SHARED)) {
        pr_err("Flags mismatch irq %d. %08x (%s) vs. %08x (%s)\n",
               irq, new->flags, new->name, old->flags, old->name);
#ifdef CONFIG_DEBUG_SHIRQ
        dump_stack();
#endif
    }
    ret = -EBUSY;
out_unlock:
    raw_spin_unlock_irqrestore(&desc->lock, flags);
    if (!desc->action)
        irq_release_resources(desc);
out_bus_unlock:
    chip_bus_sync_unlock(desc);
    mutex_unlock(&desc->request_mutex);
out_thread:
    if (new->thread) {
        struct task_struct *t = new->thread;
        new->thread = NULL;
        kthread_stop(t);
        put_task_struct(t);
    }
    if (new->secondary && new->secondary->thread) {
        struct task_struct *t = new->secondary->thread;
        new->secondary->thread = NULL;
        kthread_stop(t);
        put_task_struct(t);
    }
out_mput:
    module_put(desc->owner);
    return ret;
}

按执行顺序拆六步。

第一步，触发类型兜底。 调用者没指定触发类型，就继承该中断的默认配置。irqd_get_trigger_type 在 include/linux/irq.h：

c
#define __irqd_to_state(d) ACCESS_PRIVATE((d)->common, state_use_accessors)
static inline u32 irqd_get_trigger_type(struct irq_data *d)
{
    return __irqd_to_state(d) & IRQD_TRIGGER_MASK;
}

irq_common_data.state_use_accessors 的低 4 位是触发类型，& 一下取出来。

第二步，nested 分支与强制线程化。 nested 判断在中断子系统初始化时完成——存在这类特殊控制器，就给相关的 irq desc 打 IRQ_NESTED_THREAD；irq_settings_is_nested_thread 只是读标志。nested IRQ 必须给 thread_fn，不给就 -EINVAL。primary handler 会被换成 irq_nested_primary_handler——一个不该被调到的空壳，真被调到时打点信息告诉你出事了。非 nested 走强制线程化：

c
static int irq_setup_forced_threading(struct irqaction *new)
{
    if (!force_irqthreads)
        return 0;
    if (new->flags & (IRQF_NO_THREAD | IRQF_PERCPU | IRQF_ONESHOT))   /* 1 */
        return 0;
    new->flags |= IRQF_ONESHOT;
    if (new->handler != irq_default_primary_handler && new->thread_fn) {  /* 2 */
        new->secondary = kzalloc(sizeof(struct irqaction), GFP_KERNEL);
        if (!new->secondary)
            return -ENOMEM;
        new->secondary->handler = irq_forced_secondary_handler;
        new->secondary->thread_fn = new->thread_fn;
        new->secondary->dev_id = new->dev_id;
        new->secondary->irq = new->irq;
        new->secondary->name = new->name;
    }
    set_bit(IRQTF_FORCED_THREAD, &new->thread_flags);
    new->thread_fn = new->handler;
    new->handler = irq_default_primary_handler;
    return 0;
}

素材 1、2 给的是 3.x 版本，返回 void，没有 secondary 那段，new->thread_fn = new->handler; new->handler = irq_default_primary_handler; 两行直达。上面是 4.x 形态。

force_irqthreads 的来路：CONFIG_IRQ_FORCED_THREADING 没开它恒为 0，函数直接 return；开了只是「支持」，真正生效还要启动参数 threadirqs。三种情况不强制线程化：

标志 为什么放过
IRQF_NO_THREAD 用户明确说不许线程化，得尊重
IRQF_PERCPU 要给每个 CPU 建线程，8 核就是 8 个，得不偿失
IRQF_ONESHOT 已经线程化了，而且是特殊的 oneshot 类型

IRQF_NO_THREAD 为什么在 irq_settings_can_thread 检查过后还要再查？因为线程化可行性有两个层面：底层看（描述符、硬件拓扑），用户层看（注册时的意图）。IRQF_XXX 全是用户层标志，用户说不线程化，强制机制也得让步。

强制线程化对「只注册了 primary」的中断动手：这类中断把所有处理压在 primary 里，而 primary 全程关 CPU 中断，实时性堪忧。于是 new->thread_fn = new->handler，原来 primary 的活整体挪进线程，新 primary 换成 default handler，再打上 IRQTF_FORCED_THREAD。对「handler 和 thread_fn 都给了」的中断，4.x 另分配一个 secondary action 承接用户传的 thread_fn，配 irq_forced_secondary_handler。这样线程自己再返回 IRQ_WAKE_THREAD 时还能唤醒 secondary，用户在硬中断段和线程段各留一部分处理的意图得以保留。

这里得说句实话：强制线程化从驱动作者角度看不是好设计。驱动工程师写代码时按「我的 primary 在中断上下文跑」选同步机制，强制线程化把它挪到进程上下文，能长出很难查的 bug。IRQF_ONESHOT 是强加的（保证旧模型下 top half 不重入），线程里还要 local_bh_disable（保证旧模型下 bottom half 不抢占 top half）——两条都在模拟旧语义。内核愿意收这个特性，我猜和旧驱动维护成本有关：中断子系统 API 一改，几万个驱动都要动。

第三步，建中断线程。

c
static int
setup_irq_thread(struct irqaction *new, unsigned int irq, bool secondary)
{
        struct task_struct *t;
        struct sched_param param = {
                .sched_priority = MAX_USER_RT_PRIO/2,
        };
        if (!secondary) {
                t = kthread_create(irq_thread, new, "irq/%d-%s", irq,
                                   new->name);
        } else {
                t = kthread_create(irq_thread, new, "irq/%d-s-%s", irq,
                                   new->name);
                param.sched_priority -= 1;
        }
        if (IS_ERR(t))
                return PTR_ERR(t);
        sched_setscheduler_nocheck(t, SCHED_FIFO, &param);
        /* 线程即使死掉也留着 task_struct 引用，避免中断代码访问已释放内存 */
        get_task_struct(t);
        new->thread = t;
        set_bit(IRQTF_AFFINITY, &new->thread_flags);
        return 0;
}

三个细节：线程名 irq/%d-%s，secondary 多一个 s 且优先级降 1，调度策略 SCHED_FIFO；get_task_struct 加引用计数，线程异常退出也不会释放 task_struct；IRQTF_AFFINITY 让线程自己设亲和性，共享中断的 secondary handler 不走 setup_affinity()，这步不能省。线程主体是 irq_thread，循环等 action->thread_flags 里的 IRQTF_RUNTHREAD，置位后调初始化时绑好的 handler_fn：

c
static int irq_thread(void *data)
{
        struct irqaction *action = data;
        struct irq_desc *desc = irq_to_desc(action->irq);
        irqreturn_t (*handler_fn)(struct irq_desc *desc,
                        struct irqaction *action);
        if (force_irqthreads && test_bit(IRQTF_FORCED_THREAD,
                                        &action->thread_flags))
                handler_fn = irq_forced_thread_fn;
        else
                handler_fn = irq_thread_fn;
        init_task_work(&on_exit_work, irq_thread_dtor);
        task_work_add(current, &on_exit_work, false);
        irq_thread_check_affinity(desc, action);
        while (!irq_wait_for_interrupt(action)) {
                irq_thread_check_affinity(desc, action);
                action_ret = handler_fn(desc, action);   /* 执行 thread_fn */
                if (action_ret == IRQ_WAKE_THREAD)
                        irq_wake_secondary(desc, action);
                wake_threads_waitq(desc);   /* 唤醒等这次中断做完的进程 */
        }
        task_work_cancel(current, irq_thread_dtor);
        return 0;
}

irq_wait_for_interrupt 里循环查 IRQTF_RUNTHREAD。没置位就让线程睡进 TASK_INTERRUPTIBLE；置位了设 TASK_RUNNING 返回 0。谁置的位？回到低层中断处理：

c
irqreturn_t __handle_irq_event_percpu(struct irq_desc *desc, unsigned int *flags)
{
    for_each_action_of_desc(desc, action) {
        irqreturn_t res;
        res = action->handler(irq, action->dev_id);   /* 执行 primary handler */
        switch (res) {
            case IRQ_WAKE_THREAD:
                __irq_wake_thread(desc, action);      /* 唤醒中断线程 */
        ...
        }
    }
}

不论普通还是线程化中断，action->handler 都会被调。线程化中断的 primary 返回 IRQ_WAKE_THREAD，__irq_wake_thread 置 IRQTF_RUNTHREAD 并 wake_up_process(action->thread)。线程醒来调的函数里，强制线程化走 irq_forced_thread_fn：

c
static irqreturn_t
irq_forced_thread_fn(struct irq_desc *desc, struct irqaction *action)
{
        irqreturn_t ret;
        local_bh_disable();   /* 关中断下半部 */
        ret = action->thread_fn(action->irq, action->dev_id);
        if (ret == IRQ_HANDLED)
                atomic_inc(&desc->threads_handled);
        irq_finalize_oneshot(desc, action);
        local_bh_enable();
        return ret;
}

irq_thread_fn（显式线程化走的这条）与它只差那对 local_bh_disable / local_bh_enable，其余一样。原因值得记住：用户用 request_irq 注册，心里认定自己的 handler 在中断上下文跑、优先级高于 bottom half，编码时也按这前提做同步。强制线程化把它挪进线程后，优先级反而低于 softirq/tasklet，死锁就来了。关下半部是在补这个坑。

还有个容易看漏的点：thread_fn 不是线程的执行函数。它只是「在线程上下文里会被调到的回调」，和 kthread_create 传的 thread function 不是一个概念。真正的线程函数是 irq_thread。

第四步，one shot safe 修正。 驱动作者写外设驱动未必了解底层控制器细节。有些控制器（MSI 类）本质就是 one shot 的，驱动再设 IRQF_ONESHOT 属于画蛇添足，内核抹掉，省掉线程结束时那套 unmask。

第五步，共享检查与 thread_mask 分配。 见第十三、十四节。

第六步，资源申请、激活、挂链、注册 proc。 request_mutex → chip_bus_lock → desc->lock 依次上。desc->action 为空说明这是第一个 action，由它去 irq_request_resources。非共享分支做四件事：init_waitqueue_head(&desc->wait_for_threads)（disable_irq 或 free_irq 要等最后一次中断做完时，等待的进程睡这上面）；__irq_set_trigger 设触发类型；irq_activate 之后按需 irq_startup 使能（ARM 上就是写控制器寄存器，走 irq_chip 回调）；IRQF_PERCPU、IRQF_ONESHOT、IRQF_NOBALANCING 三个标志分别落到 IRQD_PER_CPU、IRQS_ONESHOT、IRQD_NO_BALANCING。irq_settings_can_autoenable 为假走 else 分支，WARN_ON_ONCE(new->flags & IRQF_SHARED)，然后 desc->depth = 1。

共享分支只做一件事：触发类型对不上就 pr_warn，然后「希望你的 handler 能在现有触发模式下工作」。这里只是警告、不失败——共享线触发类型由第一个申请者定，后来者改不了。最后 *old_ptr = new 挂到链尾，irq_pm_install_action 装电源管理钩子，irq_count / irqs_unhandled 清零，之前被 spurious handler 关过就重新使能，再 irq_setup_timings、register_irq_proc 建 /proc/irq/N、register_handler_proc 建 /proc/irq/N/<name>。

错误路径。 out_thread 用 kthread_stop + put_task_struct 收拾已建线程，out_mput 里 module_put 还模块引用。out_unlock 里若 desc->action 还是空，说明资源刚申请上就得退，调 irq_release_resources。

十三、共享中断：IRQF_SHARED 的约束 #

共享中断的本质：一根物理 IRQ 线挂多个设备的 interrupt request line，中断来了软件不知道是谁，只能挨个问。

维度 非共享 共享（IRQF_SHARED）
dev_id 可为 NULL 必须非 NULL
action 链表 只有一个 action 多个 action 串成链
触发类型 自己说了算 必须与线上已有 action 一致
IRQF_ONESHOT 随意 必须全链一致
IRQF_PERCPU 随意 必须全链一致
handler 责任 处理自己设备的中断 先判断是否自己，不是返回 IRQ_NONE
中断开销 一次调用 遍历整条链，逐个调用
调度行为 可用 IRQ_NORESEND 等精细控制 不能与「禁用自动使能」共存
释放 free_irq(irq, dev_id) 同左，靠 dev_id 定位

第十二节那段 if (old) { ... } 就是共享检查的全部。old 非空说明这根线上已经有人，那就得谈共享，条件全满足才放行：

  1. 双方都得有 IRQF_SHARED。(old->flags & new->flags) & IRQF_SHARED 为假就 mismatch——你设了、人家没设，没法共享。
  2. 触发类型得一样。3.x 用 (old->flags ^ new->flags) & IRQF_TRIGGER_MASK；4.x 换成 oldtype != (new->flags & IRQF_TRIGGER_MASK)，因为 4.x 先确定 oldtype（没人设过配置就继承申请者这份，并写进描述符）。
  3. IRQF_ONESHOT 得一样。(old->flags ^ new->flags) & IRQF_ONESHOT 非零就 mismatch。
  4. IRQF_PERCPU 得一样。注释原话「All handlers must agree on per-cpuness」。

道理直白：一根线只有一个电气属性。一个设备要上升沿、一个要电平，物理上做不到两全。所以共享驱动必须在这四项上完全一致。也正因为类型由第一个申请者钉死，第三个申请者必须跟前两个对齐。

4.x 还多一道闸，NMI 线不许共享，见 desc->istate & IRQS_NMI 那个分支。mismatch 分支里 IRQF_PROBE_SHARED 只压日志，返回值还是 -EBUSY；开了 CONFIG_DEBUG_SHIRQ 会顺手 dump_stack()——排查「谁抢了我的中断线」很有用。条件全过之后，do-while 走完整条链，把每个 old->thread_mask 或进局部变量 thread_mask，同时让 old_ptr 停在链尾，然后把新 action 挂上去。

十四、共享中断的 action 链表匹配 #

内核只负责遍历，不负责识别。这是共享中断最容易踩错的地方。handle_irq_event_percpu 里那个 do-while 会把链上每个 action->handler 都调一遍，不管中断到底是谁产生的。所以每个 handler 开头必须问硬件：

c
static irqreturn_t my_handler(int irq, void *dev_id)
{
    struct my_dev *dev = dev_id;
    u32 status = readl(dev->base + REG_IRQ_STATUS);
    if (!(status & MY_IRQ_BIT))
        return IRQ_NONE;            /* 不是我的中断，尽快退出 */
    writel(MY_IRQ_BIT, dev->base + REG_IRQ_STATUS);
    return IRQ_HANDLED;
}

返回 IRQ_NONE 有两个后果：本次调用记为未处理；内核的坏中断检测记账（desc->irq_count / desc->irqs_unhandled）。一条线上连续大量中断没人认领，内核会把这个 IRQ 关掉。

thread_mask：oneshot 共享线上的位标识 #

IRQF_ONESHOT 的中断在共享线上还有一层机制。每个 oneshot action 从 thread_mask 里分一个 bit 标识自己，见第十二节 new->thread_mask = 1UL << ffz(thread_mask)。假设一根 oneshot 线上有 A、B、C 三个 action，注册顺序决定各自的 bit：A 拿 0x01，B 拿 0x02，C 拿 0x04，再来就是 0x08、0x10……thread_mask == ~0UL 说明位用完了，一根线塞 32 个（64 位系统上 64 个）oneshot action 概率极低，但代码还是防一手，返回 -EBUSY。

这个 bit 不是装饰。线程被唤醒时它被 or 进 desc->thread_active；线程处理完，bit 被清掉。整条线上所有线程都做完，threads_active 归零，中断线才 unmask。源码注释：

text
 * The thread_mask for the action is or'ed to desc->thread_active to
 * indicate that the IRQF_ONESHOT thread handler has been woken, but not
 * yet finished. The bit is cleared when a thread completes. When all
 * threads of a shared interrupt line have completed desc->threads_active
 * becomes zero and the interrupt line is unmasked.

这就是共享 oneshot 中断「谁也别想提前 unmask」的实现方式。只有一个 action 的 oneshot 线上，thread_mask 初值 0，ffz(0) 得 0，1UL << 0 就是 0x01，永远用第一个 bit。

默认 primary handler 的陷阱 #

非 oneshot 分支还有一道检查，就是第十二节那个 else if。注释把这坑讲透了：

text
 * ... the default primary handler just wakes the thread, then the irq
 * lines is reenabled, but the device still has the level irq asserted.
 * Rinse and repeat....

电平中断配「只 wakeup 不清中断」的默认 primary = 死循环。源码说得很克制：边沿触发其实没事，但内核没法确定底层真正用哪种触发类型（标志位不可靠，控制器实现可以覆盖），所以一刀切全拒。

十五、cascade IRQ 与 nested IRQ #

这两个词经常被混着用，实际是两种不同的级联处理方式。注册中断时内核要按中断控制器结构给中断分类，正是为了适配这两种硬件情景。

cascade IRQ：快总线的级联 #

两个 VIC 级联：VIC0 当 S3C2440 的中断控制器，VIC1 当它的外部中断扩展。VIC1 的 IRQ 编号是 EINT4~7，外设 1~4 分别用 EINT4/5/6/7。外侧控制器不能直接向 ARM 内核递交请求，但可以向相连的内层控制器请求服务。链路：外设 1 触发 → VIC1 → VIC0 → ARM 内核。所以最先执行的是 EINT4~7 描述符的 desc->handle_irq，即 s3c_irq_demux：

c
static void s3c_irq_demux(struct irq_desc *desc)
{
        struct irq_chip *chip = irq_desc_get_chip(desc);
        struct s3c_irq_data *irq_data = irq_desc_get_chip_data(desc);
        struct s3c_irq_intc *intc = irq_data->intc;
        struct s3c_irq_intc *sub_intc = irq_data->sub_intc;
        unsigned int n, offset, irq;
        unsigned long src, msk;
        /* non-dt 用各自的 domain；dt 情况用一个大 domain，
         * subintc 从 hwirq 32 开始
         */
        offset = irq_domain_get_of_node(intc->domain) ? 32 : 0;
        chained_irq_enter(chip, desc);
        src = readl_relaxed(sub_intc->reg_pending);
        msk = readl_relaxed(sub_intc->reg_mask);
        src &= ~msk;
        src &= irq_data->sub_bits;
        while (src) {
                n = __ffs(src);
                src &= ~(1 << n);
                irq = irq_find_mapping(sub_intc->domain, offset + n);
                generic_handle_irq(irq);
        }
        chained_irq_exit(chip, desc);
}

它读 EINTPEND 判断是哪个外部中断，用 irq_find_mapping 在中断域里翻译出外设 IRQ 编号，再 generic_handle_irq 调外设注册的处理函数。归纳两点：主中断 EINT4~7 的描述符被设定为不能注册 irqaction——就算注册也不会执行，因为 desc->handle_irq 是 s3c_irq_demux，它压根不走 action 链表；EINT4~EINT7 正常注册，用 request_threaded_irq，可选 threaded handler 或只注册 primary。内核把 EINT4~7 这类中断叫 cascade IRQ。

nested IRQ：慢总线的级联 #

IO expander 提供有中断功能的 GPIO，本身也是中断控制器，有自己的 irq domain 和 irq chip。外设 1、2 用 expander 上的 GPIO，各有 IRQ 编号和描述符；expander 的 IRQ line 接到 SOC 内部控制器。看起来和 VIC 级联一样，能照抄吗？不能。算关中断时间：VIC 级联时，外设 1 产生中断，以 handle_level_irq 为例它执行开始就关当前中断，整个关中断时间 = eint_4t7_desc->handle_irq + eint4->handle_irq + eint4->action 执行时间，VIC 寄存器访问快，不算长。IO expander 不行，外设 1 的描述符 handle_irq 涉及 I2C 操作，时间长得多，关中断时间被 I2C 事务拖长，对实时性致命。

内核的处理：

  • IRQ A（expander 的 IRQ）的 handle_irq 按实际情况设定，且允许注册 irqaction。
  • 在 IRQ A 的 threaded handler 里做 IRQ number 映射，在 expander 的 irq domain 上翻译出外设 IRQ number，直接调 handle_nested_irq。
  • IRQ B、C 的描述符设 IRQ_NESTED_THREAD，标明是 nested IRQ。
  • nested IRQ 没有 handle_irq，也没有 primary handler，它的 threaded handler 附着在 parent IRQ 的 threaded handler 上。

注意这里的 nested 不是「中断嵌套」，是针对某类特殊控制器做的兼容。接在 expander 上的外设没有实时要求（否则不会接到 expander 上），所以一般做线程化。threaded handler 涉及 I2C，必须设 IRQF_ONESHOT。

维度 cascade IRQ nested IRQ
典型硬件 两个 GIC 级联、两个 VIC 级联 IO expander、I2C GPIO 扩展
父中断能否注册 action 不能（IRQ_NOREQUEST） 能，父中断自己有 threaded handler
父中断 handle_irq demux 函数，翻译并分发 按实际情况设定，走正常流控
子中断描述符 正常，可挂 action 标 IRQ_NESTED_THREAD
子中断 primary handler 驱动自己给 被换成 irq_nested_primary_handler
子中断 handle_irq 有，正常流控 没有
子中断线程 自己的 附着在父 IRQ 的线程上
分发方式 generic_handle_irq handle_nested_irq
关中断时间 短（寄存器访问快） 父中断线程化后，I2C 慢操作不进关中断窗口
是否需要 IRQF_ONESHOT 否 是（父中断 threaded handler 涉及慢总线）

nested 分支的代码就是第十二节那个 if (nested) { ... }。描述符是 nested thread type 就必须给 thread_fn，否则 -EINVAL。内核不会为它单独建线程，它借父 IRQ 的中断线程执行——这就是后面那句 if (new->thread_fn && !nested) 的意义，它和普通线程化中断的关键差别在这。primary handler 被换成 irq_nested_primary_handler，本不该被调到；真被调到时打点信息，让你知道哪里出了问题。

十六、中断的释放：free_irq 与 devm_ 系列 #

申请了就得还，两个参数都得给，dev_id 在这里是身份识别码——共享线上得靠它把对应的 action 摘掉：

c
void free_irq(unsigned int irq, void *dev_id)

释放路径上必须知道的几点：

  • free_irq 会等这次中断处理真的结束，disable_irq 也是。等的就是 desc->wait_for_threads，初始化发生在 __setup_irq 的非共享分支。
  • 线程化中断要先把线程停掉。源码注释说明白：__free_irq 在 synchronize_hardirq() 之后用 kthread_stop() 停线程，所以常规退出路径上 IRQTF_RUNTHREAD 和 oneshot 的 mask 位都不可能还挂着。
  • 释放最后一个 action 时 irq_release_resources 把 __setup_irq 里 irq_request_resources 申请的东西还回去。

devm_ 系列是另一条路。devm_request_threaded_irq / devm_request_irq 把中断申请挂到设备的资源管理链表，驱动 detach 时自动释放，省掉手写 free_irq 和错误路径清理。规矩有三条：dev_id 传什么就一直是什么，devm_free_irq 得靠它反查；devm_ 只管释放不管顺序，handler 会访问的资源若比中断先被释放，照样炸，释放顺序是申请的逆序——这是约束，不是保护；共享中断用 devm_ 时，dev_id 依然要全局唯一。

手写 free_irq 时最容易漏的是错误路径：request_threaded_irq 成功之后再注册别的资源，若那一步失败，必须 free_irq(irq, dev) 再返回，否则中断一直挂着。换成 devm_request_threaded_irq，失败分支直接 return 就行。

十七、一个完整的使用示例 #

素材 4 给的是 AT91 平台的 GPIO 中断转 LED 控制例子。它用老式 at91_* / mach/* 接口，属于 3.x 之前的板级代码形态，拿到新内核上编不过。价值在于展示 request_threaded_irq 的调用位置和两个 handler 的分工。字符设备样板（cdev_init / register_chrdev_region / module_init / io_init）与中断无关，略去：

c
/* gpio_irqTest.c —— PB27 作 IRQ 输入，控制 PB17 上的 LED */
struct gpio_irq_desc {
    int pin;
    int irq;
    unsigned long flags;
    char *name;
};
static struct gpio_irq_desc gpio_irq = {
    AT91_PIN_PB27, AT91_PIN_PB27,
    IRQF_TRIGGER_FALLING | IRQF_TRIGGER_RISING | IRQF_ONESHOT,
    "PB27"
};
static irqreturn_t gpio_irqhandler(int irq, void *dev_id)
{
    printk(KERN_INFO "In hard irq handler.\n");
    return IRQ_WAKE_THREAD;      /* 唤醒线程，活交给 thread_fn */
}
static irqreturn_t gpio_threadhandler(int irq, void *dev_id)
{
    int rst = at91_get_gpio_value(gpio_irq.pin);
    if (rst == 0)
        led_on();
    else
        led_off();
    printk(KERN_INFO "sleep 3000ms\n");
    msleep(3000);                /* 线程上下文，可以睡 */
    printk(KERN_INFO "awake after sleep\n");
    return IRQ_HANDLED;
}
int light_open(struct inode *inode, struct file *filp)
{
    int err;
    /* 下面注释掉的是 handler + thread_fn 都给的那版 */
    /* err = request_threaded_irq(gpio_irq.irq, gpio_irqhandler,
     *                            gpio_threadhandler, gpio_irq.flags,
     *                            gpio_irq.name, (void *)0); */
    err = request_threaded_irq(gpio_irq.irq, NULL, gpio_threadhandler,
                               gpio_irq.flags, gpio_irq.name, (void *)0);
    if (err) {
        printk(KERN_DEBUG "request irq failed.\n");
        return -EBUSY;
    }
    return 0;
}
int light_release(struct inode *inode, struct file *filp)
{
    free_irq(gpio_irq.irq, (void *)0);
    return 0;
}

三个地方值得抠。第一，IRQF_ONESHOT 是必须的：它同时设了 IRQF_TRIGGER_FALLING 和 IRQF_TRIGGER_RISING，也就是双边沿；IRQF_TRIGGER_MASK 是四个触发位的或，两个边沿位同时置上，掩码校验能过。第二，handler 给 NULL 时中断段是关着的：这里用的是 handler = NULL 的版本，所以 threaded handler 执行期间该中断被 mask；换成注释掉那版（两个都给），处理 thread_fn 时中断是打开的——primary 已把设备侧中断确认并关掉，IRQF_ONESHOT 的语义是「线程做完再 unmask」。第三，msleep(3000) 是这段代码的重点：在 primary 里这么干是灾难，在 threaded handler 里可以——它跑在进程上下文。这正说明了线程化的价值：慢活有了合法去处。

可直接套用的两个回调：

c
static irqreturn_t my_hardirq(int irq, void *dev_id)
{
    struct my_dev *dev = dev_id;
    if (!my_dev_irq_pending(dev))
        return IRQ_NONE;                 /* 共享线上必须判断 */
    my_dev_irq_disable(dev);             /* 关掉设备侧中断 */
    return IRQ_WAKE_THREAD;              /* 唤醒线程 */
}
static irqreturn_t my_threaded_fn(int irq, void *dev_id)
{
    struct my_dev *dev = dev_id;
    my_dev_handle_event(dev);            /* 这里可以睡、可以走 I2C */
    my_dev_irq_enable(dev);
    return IRQ_HANDLED;
}

注册用 devm_request_threaded_irq(dev, irq, my_hardirq, my_threaded_fn, IRQF_TRIGGER_FALLING | IRQF_ONESHOT, name, dev)。IRQF_ONESHOT 是这套骨架的必需品：primary 只关设备侧中断，没有 mask 中断线，靠 oneshot 保证线程做完之前线不再触发。

十八、易错点速查 #

按踩坑频率排。

  1. handler 给 NULL 却没设 IRQF_ONESHOT。 直接 -EINVAL。原因是默认 primary 只 wakeup 不清中断，电平触发会死循环。
  2. 共享中断忘给 dev_id。 -EINVAL，更早退。它还是释放时的身份码。
  3. 共享中断 flags 跟线上已有 action 不一致。 -EBUSY，日志 Flags mismatch irq %d. %08x (%s) vs. %08x (%s)。四项必须一致：IRQF_SHARED、触发类型、IRQF_ONESHOT、IRQF_PERCPU。
  4. 共享中断的 handler 不判断中断源。 内核不帮识别，整条链都会被调。开头必须读寄存器确认，不是自己的返回 IRQ_NONE。长期无人认领，内核会关掉这个 IRQ。
  5. per-CPU 中断用错接口。 WARN_ON(irq_settings_is_per_cpu_devid(desc)) 告警并返回 -EINVAL。该用 request_percpu_irq。
  6. 给级联中断的 IRQ number 申请 handler。 那个 IRQ 标了 IRQ_NOREQUEST，irq_settings_can_request 直接拒。级联通道是给 handle_irq 用的。
  7. 以为 thread_fn 是线程的执行函数。 不是。线程函数是 irq_thread。
  8. 以为 request_irq 就是「不线程化」。 开了 CONFIG_IRQ_FORCED_THREADING 且启动参数带 threadirqs，request_irq 注册的 handler 也会被搬进线程，local_bh_disable 会补上，但你基于「中断上下文」写的同步逻辑已经变了。
  9. 在 primary handler 里睡。 不行。要睡就放 thread_fn。
  10. nested 中断给了 primary handler。 会被换成 irq_nested_primary_handler，你给什么都会被覆盖。活全在 thread_fn 里。
  11. 释放时 dev_id 传错。 共享线上就是摘错别人的 handler，或者找不到目标。
  12. 忘了 request_irq 带 __must_check。 不检查返回值，编译告警；运行时中断压根没注册上，硬件中断静默丢失。
