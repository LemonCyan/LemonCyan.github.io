一、ARM 的异常模型与七种异常 #

ARM 里没有「中断」这个独立概念。中断、缺页、未定义指令、系统调用，硬件眼里统统叫异常，共用同一套入口。异常发生那一瞬间 CPU 干四件事：

  1. 把 CPSR 抄进当前模式的 SPSR，这是被打断那一刻的完整快照。
  2. 把返回地址写进当前模式的 lr。
  3. 改 CPSR.M[4:0] 切模式，按异常类型动 I / A 位。
  4. 把 PC 强行改成该异常在向量表里的地址。

剩下全是软件的事。这四步就是「硬件现场」的全部，也是后面所有汇编在折腾的那点东西。八项向量对七种异常，复位占 0x00，ARMv7 的 hypervisor trap 挤在 0x14（老核上这格叫地址异常，属保留位）：

偏移 向量符号 异常 触发者 进入模式 硬件写进 lr 的值
0x00 vector_rst 复位 上电 / 复位引脚 SVC 无意义（不复返）
0x04 vector_und 未定义指令 非法编码、协处理器失败 UND 该指令地址 + 4，软件减 4 回到它
0x08 vector_swi 软中断 / SVC swi imm24 SVC 下一条（swi + 4），不减
0x0c vector_pabt 预取中止 取指时 MMU 报错 ABT 该指令地址 + 4，软件减 4
0x10 vector_dabt 数据中止 load/store 时 MMU 报错 ABT 访存指令地址 + 8，软件减 8
0x14 vector_addrexcptn 地址异常 / hyp trap 保留；ARMv7 虚拟化后是 HVC HYP 版本相关
0x18 vector_irq 普通中断 中断控制器 IRQ 中断指令地址 + 8，减 4 后落在 +4
0x1c vector_fiq 快速中断 中断控制器 FIQ 同 IRQ（不展开）

立一条规矩：硬件给的 lr 不一定是你要返回的地址，各异常差的那几个字节软件自己补。补多少是写死的常量，见 vector_stub 的 correction：IRQ 传 4，dabt 传 8，pabt 传 4，SWI 传 0。九种模式的 M[4:0] 编码如下，banked 只在带专属 sp / lr / SPSR 的模式里才有：

模式 缩写 M[4:0] 特权级 独立 sp/lr/SPSR
User usr 0b10000 PL0 否
FIQ fiq 0b10001 PL1 是（另加 r8–r12 私有）
IRQ irq 0b10010 PL1 是
Supervisor svc 0b10011 PL1 是
Monitor mon 0b10110 PL1 是
Abort abt 0b10111 PL1 是
Hyp hyp 0b11010 PL2 是
Undefined und 0b11011 PL1 是
System sys 0b11111 PL1 否（与 usr 共用）

中断处理只盯三个：usr（用户态被打断）、svc（内核态被打断）、irq（硬件刚进来的落脚点）。system 共用 usr 的寄存器组，这是内核线程不需要模拟返回用户态的原因。

二、异常向量表：那张 8 项的跳转表 #

armasm
	.section .vectors, "ax", %progbits
__vectors_start:
	W(b)	vector_rst
	W(b)	vector_und
	W(ldr)	pc, __vectors_start + 0x1000
	W(b)	vector_pabt
	W(b)	vector_dabt
	W(b)	vector_addrexcptn
	W(b)	vector_irq			@ IRQ 向量，0x18
	W(b)	vector_fiq

七项是 b（相对跳转，射程 ±32MB），只有 SVC 那一项是 ldr pc, ...。软中断用它是因为要跨到第二个 page，b 够不着——这条指令被编译成 ldr pc, [pc, #4080]，4080 正好是 4096 减 16。位置只有两个选项，SCTLR（CP15 c1）的 bit13 决定：

text
V = 0  →  0x00000000 ~ 0x0000001c   （Normal vectors / Low vectors）
V = 1  →  0xffff0000 ~ 0xffff001c   （High vectors）

Linux（开了 MMU 的 ARM）选 V = 1。理由不是审美，是地址空间：0~3GB 归用户态，向量表放 0x0 就落进用户空间，一个野指针就能写坏它。放 0xffff0000 落在内核空间，用户态够不着。用 low vectors 也行，但那块页必须做成只读，还得靠 MMU 域权限挡住用户态写入。选 high vectors 之后硬件跳转目标就固定了：

异常 Low vectors（V=0） High vectors（V=1）
复位 0x00000000 0xffff0000
未定义指令 0x00000004 0xffff0004
SVC / SWI 0x00000008 0xffff0008
预取中止 0x0000000c 0xffff000c
数据中止 0x00000010 0xffff0010
保留 / hyp 0x00000014 0xffff0014
IRQ 0x00000018 0xffff0018
FIQ 0x0000001c 0xffff001c

0xffff0018 记住，IRQ 的第一条指令在这儿。0xffff0008 也记住，SWI 的入口在那儿，是一条 ldr pc, ...，跳到 stub 页的 vector_swi。每项只有 4 字节，塞不下任何实现，所以条目全是「跳板」：跳到同页（或 stub 页）的 vector_xxx，真正的逻辑在那儿展开。这个「表 + 跳板」的两级结构，是 ARM 在 32 字节总预算下的唯一选择。

三、CPSR 与中断使能位：I bit 与 F bit #

CPSR 全局唯一（各模式看到的是同一个，只有 SPSR 是私有的）。有用的就这几位：

位 名字 作用 异常进入时硬件怎么动
[4:0] M 当前处理器模式 改成本异常对应的模式
[5] T 指令集状态（1 = Thumb） 进异常按 ARM 态跑，软件用 eor 翻成 0
[6] F FIQ 屏蔽 IRQ 不动它；FIQ 进入置 1
[7] I IRQ 屏蔽 IRQ 进入置 1；SWI 进入也置 1
[8] A 非精确中止屏蔽 进异常置 1
[9] E 大小端（= SCTLR.EE） 保持

I 位是中断总闸，I = 1 关 IRQ，I = 0 开 IRQ。这个位只有特权态（PL1 及以上）能改，用户态写它无效——这是「用户程序不能自己开中断」的硬件保证，不是内核的君子协定。进 IRQ 后 CPSR 的样子，照抄一份，这是你单步调试时该在 SPSR 里看到的：

text
CPSR[4:0] = 0b10010        @ 切到 IRQ 模式
CPSR[5]   = 0              @ ARM 态
CPSR[7]   = 1              @ 关 IRQ
CPSR[8]   = 1              @ 关非精确中止
CPSR[9]   = CP15_reg1_EEbit
SPSR_irq  = 中断前的 CPSR
R14_irq   = 返回地址（流水线 PC 快照，见第十章）
R13_irq   = IRQ 模式自己的栈指针

I 位的时序值得单说：硬件在跳向向量表之前就把它置 1 了，所以 vector_irq 第一条指令执行时中断已经关着。这套设计让「保存现场」天然不可被打断，省掉一次 disable_irq。代价是 IRQ 处理全程关中断，想边处理边响应得靠 local_irq_enable() 或者下半部。F 与 I 不对称：I=1 不影响 FIQ，所以 FIQ 能打断 IRQ 处理。

四、异常发生时的硬件动作：模式切换与现场保存 #

  1. 外设检测到事件，在中断请求线上给出电平或边沿。
  2. 中断控制器收下，在多核之间挑一个核，通过 IRQ 线分发过去。
  3. 该核在当前指令执行完毕后响应，不打断正在执行的指令。
  4. 硬件把 CPSR 存进 SPSR_irq，把流水线 PC 快照减 4 存进 lr_irq。
  5. 硬件把 CPSR.M 改成 0b10010，CPSR.I = 1。
  6. 硬件把 PC 改成 0xffff0018。

第 3 步藏在细节里：中断在指令边界生效，不在指令中间。已取指、已译码但未执行的指令全部作废，被打断的指令本身跑完。这个「指令原子性」是后面所有现场保存能成立的前提。第 4 步的寄存器视图是理解一切的钥匙：

text
        usr 模式看到          irq 模式看到
        ─────────────         ─────────────
r0-r12  同一组物理寄存器  ←→  同一组物理寄存器（不 banked！）
sp      sp_usr            ←→  sp_irq            （banked）
lr      lr_usr            ←→  lr_irq            （banked）
pc      同一个 PC         ←→  同一个 PC
cpsr    同一个 CPSR       ←→  同一个 CPSR
spsr    无                ←→  spsr_irq          （banked）

r0–r12 和 PC、CPSR 不 banked。切模式时它们原封不动暴露给 IRQ 代码，只有 lr 和 sp 换成了 IRQ 私有的。所以：r0–r12 还在寄存器里但后面每条指令都在覆盖它们，得赶紧存；sp 已经是 sp_irq，往栈上写是往 IRQ 栈写；被打断那一点的 sp_usr / sp_svc 和 lr_usr / lr_svc 现在看不见了，只有切回 SVC 才读得到——这就是 stmdb r0, {sp, lr}^ 那条带 ^ 的指令存在的理由。

PC 共享，而硬件马上要把它改成向量地址，所以必须先把返回地址存进 lr_irq。这份返回地址到底是哪条指令，取决于流水线：

text
指令 A        ← 被打断的指令，执行完毕
指令 A+4      ← 本应接着执行
指令 A+8      ← 执行 A 时，PC 读到的值
指令 A+12     ← A 执行完、异常生效时，PC 自增到的值

执行 A 时 PC 读作 A+8（ARM 的 PC 语义是「当前指令 + 8」）。A 执行完，PC 自增到 A+12，硬件保存 PC - 4 = A+8 到 lr_irq。所以硬件给你 A+8，你要的是 A+4，差 4 字节——这就是 vector_stub irq, IRQ_MODE, 4 里那个 4 的来历。

为什么硬件不干脆减 8 直接给 A+4？因为同一套入口要服务七种异常，各自期望的返回点不统一：data abort 要 A（重新执行访存），prefetch abort 要 A（重新取指），SWI 和 IRQ 要 A+4。硬件只做统一的那一下减 4，差值交给软件按异常类型补齐。

五、中断处理的准备之一：IRQ 模式的栈 #

r13 是 banked 的，切到 IRQ 模式后 sp 就是 sp_irq，得有人提前赋值，否则第一条 stmia sp, {r0, lr} 就是往野指针写。Linux 的 IRQ 模式只当跳板，真正干活都在 SVC 模式，所以 IRQ 栈小到不讲道理——每 CPU 12 字节：

c
struct stack {
	u32 irq[3];
	u32 abt[3];
	u32 und[3];
} ____cacheline_aligned;

static struct stack stacks[NR_CPUS];

三个数组分别给 IRQ、ABT、UND 当栈，每个 3 个字。为什么是 3 个？因为 vector_stub 在跳到 SVC 之前只需要存三样：r0、lr、SPSR。多一个字节都是浪费。____cacheline_aligned 让每个 struct stack 按 cacheline 对齐，三个数组各自躺在独立 cacheline 里，互不踩线，也避免多核伪共享。ABT 和 UND 走同一套策略：先在自己 12 字节栈上放 3 个字，再切到 SVC 把现场搬到当前进程内核栈。

设定这三个 sp 的代码在 cpu_init() 里，每个 CPU 跑一次（3.14）：

c
void notrace cpu_init(void)
{
	unsigned int cpu = smp_processor_id();
	struct stack *stk = &stacks[cpu];

#ifdef CONFIG_THUMB2_KERNEL
#define PLC	"r"		/* Thumb-2 下 msr 只吃寄存器，不能吃立即数 */
#else
#define PLC	"I"
#endif

	__asm__ (
	"msr	cpsr_c, %1\n\t"		/* 切到 IRQ 模式 */
	"add	r14, %0, %2\n\t"	/* r14 = stk + offsetof(irq[0]) */
	"mov	sp, r14\n\t"		/* sp_irq = &stk->irq[0] */
	"msr	cpsr_c, %3\n\t"		/* 切到 ABT 模式 */
	"add	r14, %0, %4\n\t"
	"mov	sp, r14\n\t"		/* sp_abt = &stk->abt[0] */
	"msr	cpsr_c, %5\n\t"		/* 切到 UND 模式 */
	"add	r14, %0, %6\n\t"
	"mov	sp, r14\n\t"		/* sp_und = &stk->und[0] */
	"msr	cpsr_c, %7"		/* 回 SVC 模式 */
		:
		: "r" (stk),
		  PLC (PSR_F_BIT | PSR_I_BIT | IRQ_MODE),
		  "I" (offsetof(struct stack, irq[0])),
		  PLC (PSR_F_BIT | PSR_I_BIT | ABT_MODE),
		  "I" (offsetof(struct stack, abt[0])),
		  PLC (PSR_F_BIT | PSR_I_BIT | UND_MODE),
		  "I" (offsetof(struct stack, und[0])),
		  PLC (PSR_F_BIT | PSR_I_BIT | SVC_MODE)
		: "r14");
}

语法是 asm(code : output : input : clobber)，这里 output 空着，全靠 input 的 %0~%7。两个约束符分清楚："r" 走通用寄存器，"I" 是立即数；(stk) 用 "r"，offsetof(...) 用 "I"（后者要求编译期常量，offsetof 满足）。clobber 写了 r14，因为汇编把它当草稿纸，得告诉编译器别指望它还留着原值。

msr cpsr_c 里的 _c 是「只改 control 字段」（M[4:0]、I、F、T 那一组），不是改整个 CPSR。每个 msr 都带 PSR_I_BIT，切模式的同时顺手关中断，避免在「sp 还没设好」的窗口里被中断打断——那时 sp_irq 还是垃圾。注意 mov sp, r14 设的是 irq[0] 的低地址，而 vector_stub 里 stmia sp, {r0, lr} 是向上写 [sp]、[sp+4]、[sp+8]，往上 12 字节正好用满 irq[3]。这是「满递减栈却从底部往上用」的反常写法，别按常规栈的直觉理解它。

六、中断处理的准备之二：SVC 模式的栈 #

SVC 模式的栈就是内核栈，是整个中断处理真正干活的地方——usr_entry / svc_entry 压的 72 字节、C 函数局部变量、调用链全长在这块栈上。创建进程时（用户进程和内核线程一样）分一个 page frame（或者两个，看配置）：低地址处是 struct thread_info，高地址往上到页框顶端是内核栈，sp_svc 从顶端往下长。thread_info 贴在页框底部，和栈在同一块连续内存里，所以从 sp 就能算出它：

armasm
	.macro	get_thread_info, rd
	mov	\rd, sp, lsr #13
	mov	\rd, \rd, lsl #13
	.endm

右移 13 再左移 13，等于把 sp 按 8KB 向下对齐（2^13 = 8192）。对齐后的地址就是页框基址，也就是 thread_info 地址。3.14 的 ARM 上这个 13 写死，前提是 THREAD_SIZE 为 8KB；换 4KB 栈配置这套移位就不对。后面用 tsk = r9 表示这个指针。内核栈每个进程各一份，进程切换时硬件上下文整体换血，sp_svc 跟着换成新进程的。所以「此刻 sp_svc 指向谁的内核栈」的答案是：当前进程。中断进来时 current 还没变，现场压在这儿天然不会串。

七、中断处理的准备之三：向量表的安装 #

向量表不能就地用。链接时它在 .vectors 段里有个 link-time 地址，运行时必须出现在 0xffff0000（high vectors）或 0x0（low vectors）。devicemaps_init() 负责分配和映射（3.14）：

c
static void __init devicemaps_init(const struct machine_desc *mdesc)
{
	...
	vectors = early_alloc(PAGE_SIZE * 2);	/* 要两个 page */
	early_trap_init(vectors);		/* 拷向量表 + stub + kuser helper */

	map.pfn = __phys_to_pfn(virt_to_phys(vectors));
	map.virtual = 0xffff0000;
	map.length = PAGE_SIZE;
#ifdef CONFIG_KUSER_HELPERS
	map.type = MT_HIGH_VECTORS;
#else
	map.type = MT_LOW_VECTORS;
#endif
	create_mapping(&map);			/* 第一页 → 0xffff0000 */

	if (!vectors_high()) {			/* SCTLR.V = 0 时还得映射 0 地址 */
		map.virtual = 0;
		map.length = PAGE_SIZE * 2;
		map.type = MT_LOW_VECTORS;
		create_mapping(&map);
	}

	map.pfn += 1;
	map.virtual = 0xffff0000 + PAGE_SIZE;
	map.length = PAGE_SIZE;
	map.type = MT_LOW_VECTORS;
	create_mapping(&map);			/* 第二页 → 0xffff1000 */
	...
}
页 虚拟地址 放什么
第 1 页 0xffff0000 8 项向量表 + kuser helper（__kuser_cmpxchg 之类）
第 2 页 0xffff1000 异常跳转的 stub（vector_irq、vector_swi 本体）

为什么非要把 stub 挪到第二页？向量表只有 32 字节，装不下 vector_stub 那一大坨。b 能跳 ±32MB，但 SVC 那一项是 ldr pc, [pc, #offset]，offset 只有 12 位有符号立即数、最多 ±4095。把 vector_swi 放在第二页开头，从 0xffff0008 起算偏移 4088，刚好落在 4095 内。这条约束反过来决定了 stub 区必须紧贴向量页。

early_trap_init() 做实际填充（3.14）：

c
void __init early_trap_init(void *vectors_base)
{
	unsigned long vectors = (unsigned long)vectors_base;
	extern char __stubs_start[], __stubs_end[];
	extern char __vectors_start[], __vectors_end[];
	unsigned i;

	vectors_page = vectors_base;

	/* 整页先填成未定义指令 */
	for (i = 0; i < PAGE_SIZE / sizeof(u32); i++)
		((u32 *)vectors_base)[i] = 0xe7fddef1;

	memcpy((void *)vectors, __vectors_start, __vectors_end - __vectors_start);
	memcpy((void *)vectors + 0x1000, __stubs_start, __stubs_end - __stubs_start);
	kuser_init(vectors_base);
	flush_icache_range(vectors, vectors + PAGE_SIZE * 2);
	modify_domain(DOMAIN_USER, DOMAIN_CLIENT);
}

四件事各有理由。先填 0xe7fddef1：向量表加 kuser helper 填不满一页，中间有缝隙，极端情况下（程序跑飞、硬件 issue）CPU 会从缝隙取指；填成未定义指令后误入立刻触发 UND 异常，至少能定位，0xe7fddef1 本身是一条 udf 编码。两次 memcpy：向量表拷到页首，stub 拷到第二个 page 的页首。flush_icache_range 是因为拷的是代码，D-cache 写进去的 I-cache 不认，得主动刷两页。modify_domain 放开 user domain 访问权限，否则用户态读 kuser helper 会被拦下。

「link-time 地址 ≠ run-time 地址」落到代码上就是位置无关性。b 天然位置无关（PC 相对），七项照抄不误。ldr pc, __vectors_start + 0x1000 被编译成 ldr pc, [pc, #4080]，也是 PC 相对、位置无关，但偏移只有 ±4095，所以 stub 必须放得近。2.6.x 的写法是另一套，有份素材抄的是那个年代：

c
/* 2.6.x 写法 */
void __init early_trap_init(void)
{
	unsigned long vectors = CONFIG_VECTORS_BASE;
	...
	memcpy((void *)vectors, __vectors_start, __vectors_end - __vectors_start);
	memcpy((void *)vectors + 0x200, __stubs_start, __stubs_end - __stubs_start);
	memcpy((void *)vectors + 0x1000 - kuser_sz, __kuser_helper_start, kuser_sz);
	memcpy((void *)KERN_SIGRETURN_CODE, sigreturn_codes, sizeof(sigreturn_codes));
	flush_icache_range(vectors, vectors + PAGE_SIZE);
	modify_domain(DOMAIN_USER, DOMAIN_CLIENT);
}

差异：2.6.x 无参、基址来自 CONFIG_VECTORS_BASE 常量、stub 在 vectors + 0x200、kuser helper 挤在 0x1000 - kuser_sz、手工拷 sigreturn_codes 到 KERN_SIGRETURN_CODE、只刷一页 icache；3.14 有参、基址来自 early_alloc()、stub 在 vectors + 0x1000、kuser_init() 单独调、不碰 sigreturn、刷两页。2.6.x 把 stub 塞在 +0x200 是因为那时 vector_swi 离向量表够近，页内偏移就够 ldr 够得着；后来 stub 区膨胀才整体挪到第二页。两版都自洽，混用必错。

八、中断处理的准备之四：中断控制器初始化 #

向量表和栈就位只说明「异常发生时 CPU 知道往哪跳」。中断要真能进来还差控制器这一环。3.14 上这部分拆得很干净：

层 谁负责 干什么
distributor 控制器驱动 使能每根中断线、设优先级与触发类型（电平/边沿）、决定路由到哪个 CPU
CPU interface 控制器驱动，每 CPU 一份 使能该 CPU 收中断、设优先级门限
分派函数指针 平台代码 set_handle_irq() 填 handle_arch_irq
全局总闸 local_irq_enable() 清 CPSR.I，CPU 才真正开始响应

第三项和向量表直接相关：handle_arch_irq 正是第十三章 irq_handler 宏里 ldr r1, =handle_arch_irq 要取的地址。向量表是入口，handle_arch_irq 是出口，两头都在启动阶段接好，中间那段 vector_stub 才有意义。第四项常被忽略：控制器全配好、指针也注册了，只要 CPSR.I 还是 1，中断线拉得再高 CPU 也不理。顺序不能乱：控制器没初始化就开中断，第一根线进来时 handle_arch_irq 还是空指针，ldr pc, [r1] 直接跳 0，而这个失败模式极难查——它崩在中断上下文里，栈回溯只有半截。具体寄存器序列和 gic_init_bases() 调用链归 GIC 那篇。

九、ARM 硬件对中断事件的响应细节 #

text
外设检测到事件 → 中断请求线上的电平 / 边沿（上升、下降、双边）
        ↓
中断控制器（GIC）在多核中挑一个核，通过 IRQ 线分发
        ↓
CPU 当前指令执行完毕 → 硬件存 SPSR_irq / lr_irq，切 IRQ 模式，关 I，跳 0xffff0018
        ↓
软件接管

IRQ 优先级低于 FIQ。 硬件层面 FIQ 排在前面，且 FIQ 一进来就把 CPSR.F 置 1 挡后续 FIQ；IRQ 进来只挡 IRQ（CPSR.I = 1），不挡 FIQ。所以 FIQ 能打断 IRQ 处理，反之不行。这个不对称是 ARM 给「低延迟」留的门：DMA 完成、看门狗这类必须马上响的放 FIQ，普通外设放 IRQ。

中断在指令边界生效。 被打断的指令一定跑完。这条约束让「现场」总处于干净状态：PC 总能对应到指令边界，栈指针总是 4 字节对齐的合法值。要是允许在指令中间打断，ldm / stm 这类多寄存器指令就没法恢复。

mask IRQ 的时机在跳转之前。 CPSR.I = 1 是硬件做的，不是 vector_irq 里的软件做的。这省掉「进入时先关中断」这一步，但也意味着整条 IRQ 链默认全程关中断，直到 svc_exit 或 restore_user_regs 用 movs pc, lr 把 SPSR 里那个 I=0 的旧值恢复回去。

多核分发由控制器决定。 CPU 完全被动，不知道自己是被选中还是被忽略。「中断在哪个 CPU 上跑」在硬件层就定了，软件只能读出来，改不了。

十、进入 IRQ 处理后的第一条指令 #

PC 被改成 0xffff0018，那儿躺着向量表第七项，扩展成 b vector_irq，跳到同在 stub 页的 vector_irq。它不是手写的，由 vector_stub 宏展开（3.14）：

armasm
	.macro	vector_stub, name, mode, correction=0
	.align	5
vector_\name:
	.if \correction
	sub	lr, lr, #\correction
	.endif

	@
	@ Save r0, lr_ (parent PC) and spsr_
	@ (parent CPSR)
	@
	stmia	sp, {r0, lr}		@ save r0, lr
	mrs	lr, spsr
	str	lr, [sp, #8]		@ save spsr

	@
	@ Prepare for SVC32 mode.  IRQs remain disabled.
	@
	mrs	r0, cpsr
	eor	r0, r0, #(\mode ^ SVC_MODE | PSR_ISETSTATE)
	msr	spsr_cxsf, r0

	@
	@ the branch table must immediately follow this code
	@
	and	lr, lr, #0x0f
 THUMB(	adr	r0, 1f			)
 THUMB(	ldr	lr, [r0, lr, lsl #2]	)
	mov	r0, sp
 ARM(	ldr	lr, [pc, lr, lsl #2]	)
	movs	pc, lr			@ branch to handler in SVC mode
ENDPROC(vector_\name)

	.align	2
	@ handler addresses follow this label
1:
	.endm

.align 5 是 32 字节对齐（2^5），对齐到这个粒度是给 ldr lr, [pc, lr, lsl #2] 做基址用的，PC 对齐后偏移才好算。

第一段 sub lr, lr, #4。 只有 correction 非 0 才执行。IRQ 传 4，所以 lr_irq = A+8 减 4 得 A+4，正好是「被打断指令的下一条」，这就是第四章那个差值的兑现。SWI 异常不这么修——它的 lr_svc 已正确指向 swi 下一条，correction 传 0，这段不生成。

第二段，把 3 个字塞进 IRQ 栈。 stmia 先存后增，sp 没 ! 后缀所以存完不动，三个字落在 [sp]、[sp+4]、[sp+8]，正好用满第五章那 12 字节：

text
sp_irq + 0  ┌────────────────┐
            │  r0（被打断时）  │
sp_irq + 4  ├────────────────┤
            │  lr（A+4）      │  ← 返回地址，修正后
sp_irq + 8  ├────────────────┤
            │  SPSR_irq       │  ← 被打断时的 CPSR
sp_irq + 12 └────────────────┘

为什么非存 r0？因为紧接着 mrs r0, cpsr 就把它覆盖了，r0–r12 不 banked，不存就永久丢失。为什么只存 r0？因为下面只污染 r0 一个，r1–r12 没人碰。mrs lr, spsr 又拿 lr 当草稿纸，但原始值已在 stmia 里存进 [sp+4]，覆盖没损失。

第三段，改 SPSR 准备切 SVC。

armasm
	mrs	r0, cpsr				@ r0 = 当前 CPSR（IRQ 模式）
	eor	r0, r0, #(\mode ^ SVC_MODE | PSR_ISETSTATE)
	msr	spsr_cxsf, r0				@ SPSR_irq = 改好的值

三行把「IRQ 模式」这个模式位换成「SVC 模式」，同时把 T 位按 PSR_ISETSTATE 处理掉，写回 SPSR_irq。eor 用异或而不是或，是刻意的：\mode ^ SVC_MODE 是常量，值等于 IRQ 编码和 SVC 编码的异或差，当前 CPSR 低 5 位就是 IRQ 编码，异或一下正好翻成 SVC 编码；PSR_ISETSTATE 同理，与 0 异或不变、与 1 异或翻转，写或运算做不到「翻转」。关键点：改的是 SPSR，不是 CPSR。写 SPSR 不引起模式切换，这一步只是「准备好一张票」，真正切换要等 movs pc, lr——s 后缀让硬件把 SPSR 拷进 CPSR，模式才翻过去。有份素材抄的是更早的写法，eor r0, r0, #(\mode ^ SVC_MODE)，没有 | PSR_ISETSTATE：前者显式把指令集状态钉在 ARM 态，后者不碰 T 位，靠「异常进入时硬件已经清 T」这个前提。在 IRQ 路径上两种写法结果一样（硬件保证进来就是 ARM 态），显式置位更抗造。

第四段，查表分派 + 切模式。 lr 此时装的是被打断那刻的 CPSR（mrs lr, spsr 的残留）：

armasm
	and	lr, lr, #0x0f		@ lr = 被打断时的 CPSR.M[3:0]
	mov	r0, sp			@ r0 = sp_irq，传给下一级
	ldr	lr, [pc, lr, lsl #2]	@ lr = 表[lr] → __irq_usr 或 __irq_svc
	movs	pc, lr			@ 跳过去，同时 SPSR→CPSR，切 SVC

用户态进来 M[3:0] = 0b0000 → lr = 0 → 表 + 0 → __irq_usr；内核态进来 M[3:0] = 0b0011 → lr = 3 → 表 + 12 → __irq_svc。lsl #2 是乘 4（每项一个 .long）。[pc, ...] 里的 pc 是 ARM 流水线语义下的「当前指令 + 8」，所以表基址必须紧跟在 movs pc, lr 之后——宏注释那句「the branch table must immediately follow this code」就是提醒这件硬约束。mov r0, sp 把 sp_irq 传给下一级，因为 usr_entry / svc_entry 要用它去 IRQ 栈上把刚才那 3 个字捞回来。

movs pc, lr 一条指令干两件事：写 PC（跳转）+ s 后缀触发 SPSR → CPSR（切模式）。跳转目标已在 SVC 模式下，所以目标代码里 sp 已经是 sp_svc——栈换了。这也解释了这段代码为什么不需要任何「切栈」指令：切模式等于切 sp，而切模式是 movs pc, lr 的副作用。

十一、三条进入路径：用户态 / 内核态 / IRQ 模式嵌套 #

vector_stub 展开后紧跟 16 个 .long，按 M[3:0] 索引。只有两项是真入口，这是「全表」不是「白名单」——每个模式一格，大部分格子放陷阱。漏一项的后果是索引越界后跳到随机地址；放陷阱的后果是跳到 __irq_invalid 打现场再 panic，后者调试价值高得多。

armasm
	vector_stub	irq, IRQ_MODE, 4

	.long	__irq_usr		@  0  (USR_26 / USR_32)
	.long	__irq_invalid		@  1  (FIQ_26 / FIQ_32)
	.long	__irq_invalid		@  2  (IRQ_26 / IRQ_32)
	.long	__irq_svc		@  3  (SVC_26 / SVC_32)
	.long	__irq_invalid		@  4  ... 以下全部 invalid
路径 被打断时模式 M[3:0] 表项 入口标签 现场存到哪
用户态被中断 usr 0 +0 __irq_usr 当前进程内核栈 sp_svc
内核态被中断 svc 3 +12 __irq_svc 当前进程内核栈，在已有帧之上再压一层
IRQ 态再被中断 irq 2 +8 __irq_invalid 不该发生

路径一：用户态被中断。

armasm
	.align	5
__irq_usr:
	usr_entry			@ 保存用户现场
	kuser_cmpxchg_check		@ 和本文主线无关
	irq_handler			@ 核心分派
	get_thread_info tsk		@ tsk = r9 = thread_info
	mov	why, #0			@ why = r8 = 0
	b	ret_to_user_from_irq	@ 返回用户态

四个动作：存现场、处理中断、取 thread_info、返回。why 置 0 是给返回路径的标记，表示「这次返回不是系统调用，没有返回值要传」。usr_entry 把用户现场压到内核栈上：

armasm
	.macro	usr_entry
	sub	sp, sp, #S_FRAME_SIZE
	stmib	sp, {r1 - r12}
	ldmia	r0, {r3 - r5}
	add	r0, sp, #S_PC
	mov	r6, #-1			@ orig_r0
	str	r3, [sp]		@ 保存中断那一刻的 r0
	stmia	r0, {r4 - r6}
	stmdb	r0, {sp, lr}^
	.endm

sub sp, sp, #S_FRAME_SIZE 一次留 18 个字（72 字节），stmib sp, {r1 - r12} 的 ib 是「先增后存」——先加 4 就是为了给 r0 留格子，sp 没 ! 所以存完不动。r0 在这里指向 IRQ 栈（vector_stub 里 mov r0, sp 传下来的），所以 ldmia r0, {r3 - r5} 捞出的是 IRQ 栈上那三个字：r3 是被打断时的 r0、r4 是返回地址、r5 是 CPSR。add r0, sp, #S_PC 让 r0 指到 pt_regs 的 ARM_pc 格，接下来 stmia r0, {r4 - r6} 往 PC / CPSR / orig_r0 三格写，stmdb r0, {sp, lr}^ 的 db 是「先减后存」，带 ^ 读用户态的 sp、lr，正好落在 ARM_sp、ARM_lr 两格。r0、PC、CPSR 三个值都是从 IRQ 栈搬过来的——这就是「从 IRQ 栈把现场搬到内核栈」的实际动作。

路径二：内核态被中断。

armasm
	.align	5
__irq_svc:
	svc_entry			@ 保存内核现场
	irq_handler			@ 同一个宏，同一段分派
#ifdef CONFIG_PREEMPT
	get_thread_info tsk
	ldr	r8, [tsk, #TI_PREEMPT]	@ 取 preempt count
	ldr	r0, [tsk, #TI_FLAGS]	@ 取 flags
	teq	r8, #0			@ preempt count != 0 ?
	movne	r0, #0			@ 非 0 就把 flags 清零，禁止抢占
	tst	r0, #_TIF_NEED_RESCHED
	blne	svc_preempt		@ 有调度需求，走抢占
#endif
	svc_exit r5, irq = 1		@ 返回内核态

和路径一的结构差异只有两处：svc_entry 换 usr_entry，svc_exit 换 ret_to_user_from_irq。中间那段 irq_handler 一模一样。CONFIG_PREEMPT 那段是内核抢占点：preempt_count 非 0 说明当前处在不可抢占区（关了抢占或正持锁），此时即便有 _TIF_NEED_RESCHED 也不能切，movne r0, #0 把 flags 清零、人为让 tst 失败。svc_entry 与 usr_entry 的差别在于「中断发生在 SVC 态，所以被打断时的 sp 就是当前 sp_svc」：

armasm
	.macro	svc_entry, stack_hole=0
	sub	sp, sp, #(S_FRAME_SIZE + \stack_hole - 4)
	stmia	sp, {r1 - r12}
	ldmia	r0, {r3 - r5}
	add	r7, sp, #S_SP - 4
	mov	r6, #-1			@ orig_r0
	add	r2, sp, #(S_FRAME_SIZE + \stack_hole - 4)
	str	r3, [sp, #-4]!		@ 先减后存，sp 落到栈顶
	mov	r3, lr			@ 保存 svc 模式的 lr
	stmia	r7, {r2 - r6}
	.endm

sub sp, sp, #(S_FRAME_SIZE + \stack_hole - 4) 少减 4，是为了让 sp 先停在 pt_regs 里 r1 的位置，配合后面的 str r3, [sp, #-4]!（先减 4 再存，sp 正好落到栈顶 r0 那格）。r2 记的是「进中断那一刻的 sp 原值」，一会儿要当 ARM_sp 存进去——因为这次被打断的是内核态，sp_svc 本身就是要保存的现场。r5 从 ldmia r0, {r3 - r5} 拿到 IRQ 栈上的 CPSR，一直活到 svc_exit 才用。

路径三：IRQ 模式再被中断——不该发生。 M[3:0] = 2 对应 +8，指向 __irq_invalid。理论上走不到：IRQ 一进来硬件就把 CPSR.I 置 1，IRQ 模式里收不到第二个 IRQ。真要走到了，说明有人在 IRQ 模式下 msr cpsr_c 清了 I 位，而 sp_irq 已经指向那块 12 字节。这时再进来一个 IRQ，第二轮 stmia sp, {r0, lr} 会把第一轮现场覆盖——现场全毁。__irq_invalid 的价值就在这儿：它不试图恢复，直接打印模式、寄存器现场，走 bad_mode。内核宁可 panic 也不带着被踩烂的现场继续跑。同类陷阱还有 M[3:0] = 1（FIQ 模式）：FIQ 处理期间若 I 位开着，一个 IRQ 插进来，被打断的是 FIQ 上下文，而 Linux 的 FIQ 处理不遵循这套 pt_regs 约定，存下来也没人认。

十二、中断退出：恢复现场与返回 #

从用户态返回：ret_to_user_from_irq。

armasm
ENTRY(ret_to_user_from_irq)
	ldr	r1, [tsk, #TI_FLAGS]
	tst	r1, #_TIF_WORK_MASK		@ A
	bne	work_pending
no_work_pending:
	asm_trace_hardirqs_on			@ irq flag trace，略
	/* perform architecture specific actions before user return */
	arch_ret_to_user r1, lr			@ 平台相关收尾
	ct_user_enter save = 0			@ context tracking，略
	restore_user_regs fast = 0, offset = 0	@ B
ENDPROC(ret_to_user_from_irq)
ENDPROC(ret_to_user)

A 处检查 thread_info->flags，三个 flag 一个意思：返回用户态之前还有事没办完：

c
#define _TIF_WORK_MASK	(_TIF_NEED_RESCHED | _TIF_SIGPENDING | \
			 _TIF_NOTIFY_RESUME)
flag 含义 不办会怎样
_TIF_NEED_RESCHED 该调度了 高优先级任务饿着，直到下次时钟中断
_TIF_SIGPENDING 有信号待投递 信号延迟送达，kill() 看起来「不灵」
_TIF_NOTIFY_RESUME 返回前要跑回调 rseq、seccomp 之类收尾丢失

任一为真就跳 work_pending，办完再回来。这也是「用户态返回是天然调度点」的由来。B 处 restore_user_regs：

armasm
	.macro	restore_user_regs, fast = 0, offset = 0
	ldr	r1, [sp, #\offset + S_PSR]	@ r1 = pt_regs->ARM_cpsr
	ldr	lr, [sp, #\offset + S_PC]!	@ lr = pt_regs->ARM_pc，sp 移到 PC 位置
	msr	spsr_cxsf, r1			@ SPSR = 被打断时的 CPSR
	clrex					@ 清 exclusive monitor

	.if	\fast
	ldmdb	sp, {r1 - lr}^			@ 恢复 r1-r14
	.else
	ldmdb	sp, {r0 - lr}^			@ 恢复 r0-r14
	.endif
	mov	r0, r0				@ ARMv5T 及更早需要这个 nop
	add	sp, sp, #S_FRAME_SIZE - S_PC	@ 内核栈回退，清干净
	movs	pc, lr				@ 返回用户态
	.endm

三条指令的配合很精。ldr lr, [sp, #S_PC]! 的 ! 让 sp 前进到 PC 那一格，为后面 ldmdb 用「先减后取」一次性捞回 r0–r14 铺路。ldmdb sp, {r0 - lr}^ 的 ^ 让 ldm 访问用户态寄存器组，也就是 sp_usr、lr_usr——同一组物理寄存器在 SVC 模式下看不到它们，加 ^ 才切过去，这是「用户现场回到用户寄存器」的唯一途径。movs pc, lr 把刚捞回来的用户 PC 写进 PC，同时 SPSR → CPSR，那个 I=0 恢复回来，中断重新打开，模式切回用户态。add sp, sp, #S_FRAME_SIZE - S_PC 必须在 movs pc, lr 之前执行：一旦 PC 跳到用户态，这条指令再没机会跑，sp_svc 会永久留一个残留帧，下次进内核栈就错位。clrex 是 ARMv7 加的，清 exclusive monitor——用户态被中断时若正卡在 ldrex / strex 序列中间，不清的话那个标记会一直挂着，影响后续 strex 的成功判定。

从内核态返回：svc_exit。

armasm
	.macro	svc_exit, rpsr, irq = 0
	.if	\irq != 0
	@ IRQs already off
	.else
	@ IRQs off again before pulling preserved data off the stack
	disable_irq_notrace
	.endif
	msr	spsr_cxsf, \rpsr	@ SPSR = 被打断时的 CPSR
	ldmia	sp, {r0 - pc}^		@ 异常返回：一次恢复 r0-r15 + CPSR
	.endm

比用户态版本简单得多，因为栈不用回退，也不需要 clrex。调用形态是 svc_exit r5, irq = 1，rpsr 传的是 r5——svc_entry 里 ldmia r0, {r3 - r5} 捞出来的那个 CPSR，一路从 IRQ 栈传到 svc_exit。irq = 1 表示「进来时中断是关的，别再多关一次」；irq = 0 分支会在恢复现场前补一次 disable_irq_notrace，防止 ldmia 半途被中断打断、把正要恢复的寄存器踩掉。ldmia sp, {r0 - pc}^ 是 ARM 的异常返回指令：列表含 pc 且带 ^ 时，硬件做的是「恢复 r0–r14、把 pc 设成栈上那个值、把 SPSR 拷进 CPSR」，一条指令完成整个返回。

恢复范围 r0–r14 + PC + CPSR r0–r15（含 sp、lr）+ CPSR
^ 的作用 访问用户态 banked 寄存器（sp_usr/lr_usr） 触发「SPSR → CPSR」的异常返回语义
栈回退 add sp, sp, #S_FRAME_SIZE - S_PC 不需要
前置检查 _TIF_WORK_MASK 三个 flag 无（内核态没有「返回前投递信号」这回事）
关中断处理 靠 SPSR 恢复 irq 参数控制是否补 disable_irq

最要紧的一条：restore_user_regs 里 ^ 是「换个寄存器组来看」，svc_exit 里 ^ 是「触发异常返回」。同一个符号两种语义，取决于列表里有没有 pc。

十三、从 IRQ 汇编到 C 处理函数：irq_handler 的衔接 #

__irq_usr 和 __irq_svc 都调 irq_handler，这个宏有两种配置（3.14）：

armasm
	.macro	irq_handler
#ifdef CONFIG_MULTI_IRQ_HANDLER
	ldr	r1, =handle_arch_irq
	mov	r0, sp				@ 参数：struct pt_regs *
	adr	lr, BSYM(9997f)			@ 返回地址
	ldr	pc, [r1]			@ 跳到平台注册的分派函数
#else
	arch_irq_handler_default
#endif
9997:
	.endm

配置一 CONFIG_MULTI_IRQ_HANDLER 的四行做一次「手工 C 函数调用」：ldr r1, =handle_arch_irq 取函数指针地址，mov r0, sp 传第一个参数 pt_regs *，adr lr, 9997f 设返回地址，ldr pc, [r1] 跳过去。不用 bl 是因为 bl 的跳转范围也是 ±32MB 相对偏移，而 handle_arch_irq 是运行时才填的指针，地址不固定，只能自己设 lr 再 ldr pc。这个配置的意义在「一个 image 支持多平台」：控制器不一样，取中断号的方式就不一样，编译期定不下来，运行时由平台代码用 set_handle_irq() 填好指针，汇编只管调。

配置二 arch_irq_handler_default（传统写法）：

armasm
	.macro	arch_irq_handler_default
	get_irqnr_preamble r6, lr
1:	get_irqnr_and_base r0, r2, r6, lr
	movne	r1, sp
	@
	@ asm_do_IRQ 需要两个参数：irq number（r0）和 struct pt_regs *（r1）
	@
	adrne	lr, BSYM(1b)			@ 返回地址回到 1，继续解析
	bne	asm_do_IRQ
	.endm

逻辑是循环：get_irqnr_preamble 做准备（读控制器基址之类，有些平台定义为空），然后 get_irqnr_and_base 问控制器「下一个待处理中断号」，结果在 r0；没有则条件码不成立、跳出循环，有的话 movne r1, sp 设第二个参数、adrne lr, 1b 把返回地址指回 1、bne asm_do_IRQ 调 C 函数，返回后落到 1b 再问一次。两个宏都是平台宏，由各 mach-* 头文件提供，后者四个参数：

参数 寄存器 作用
irqnr r0 输出：本次解析出的中断号
base r2 输出：状态寄存器值（供条件码判断有无中断）
base_addr r6 输入：控制器基址
tmp lr 草稿

这套宏的前提是「控制器能一次告诉你一个中断号，处理完还能再问下一个」。GIC 支持这种模式，所以能用一个循环把一次异常里挂着的所有中断都处理掉，避免退出再重进。asm_do_IRQ 是 C 函数，到这儿就和体系结构关系不大了，它接收 (irq, regs)，走 generic_handle_irq() 之类的通用路径，最终调到驱动 request_irq() 注册的 ISR，细节见 中断子系统综述：从外设到内核的分发链。

text
irq_handler
   ├─ CONFIG_MULTI_IRQ_HANDLER=y  →  handle_arch_irq(regs)     [平台函数指针]
   │                                   └→ 读 GIC 拿 irq → generic_handle_irq()
   └─ CONFIG_MULTI_IRQ_HANDLER=n  →  arch_irq_handler_default
                                       └→ 循环 get_irqnr_and_base
                                            └→ asm_do_IRQ(irq, regs) → generic_handle_irq()

两条路最后汇到同一个地方，差别只是「谁来读中断控制器」。3.14 时代新平台基本走第一条。irq_handler 的 r0 参数就是 sp 指向的那个 pt_regs，所以 C 处理函数拿到的现场和汇编压进去的现场是同一块内存——这也是为什么 regs->ARM_pc、regs->ARM_cpsr 在 ISR 里能直接读，它们就是被打断那刻的值。

十四、SWI 异常：系统调用的硬件入口 #

中断那条线走完了，换到 SWI。它的入口机制和 IRQ 一模一样，只是向量下标不同、目标模式不同。用户态执行 swi 指令（EABI 下永远是 swi 0，调用号走 r7），硬件动作（4.4.6，ARM 32 位）：

  1. 把 CPSR 存进 SPSR_svc。
  2. 把「swi 的下一条指令地址」存进 lr_svc。这里不减 4——SWI 期望的返回点本来就是下一条。
  3. 改 CPSR：
text
CPSR.M[4:0] = 0b10011      @ 切到 SVC 模式
CPSR.I      = 1            @ 关 IRQ
CPSR.IT     = 0b00000000
CPSR.J      = 0
CPSR.T      = SCTLR.TE     @ 指令集状态
CPSR.E      = SCTLR.EE     @ 大小端
  1. PC = 0xffff0008（high vectors 下 SVC 向量的地址）。

第 3 步里 CPSR.I = 1 值得注意：SWI 进来也关中断，所以系统调用前半段（保存现场、查表）是关中断跑的，后面 enable_irq 才开。模式上，SWI 直接进 SVC，没有 IRQ 模式那一跳：IRQ 是 usr/svc → irq → svc 两跳，SWI 是 usr → svc 一跳。少一跳的后果是「没有那块 12 字节过渡栈可用」，所有现场必须直接压在 sp_svc 上。0xffff0008 处的向量项是 W(ldr) pc, __vectors_start + 0x1000，编译成 ldr pc, [pc, #4080]，跳到 stub 页首，而 stub 页首第一个符号就是 vector_swi。

sp_svc 在进程切换时就设好了（切换硬件上下文时一并切换）：Task A 切到 Task B 时把 A 的硬件上下文（含 sp_svc）存进 A 的 task_struct，再从 B 的 task_struct 装回 B 的硬件上下文，其中就包括 sp_svc。所以 B 之后执行 swi，硬件进 SVC 模式时 sp 自动就是 B 的内核栈。由此「内核栈是空的」这个前提成立：刚进 vector_swi 时栈上没有残留帧（上一轮进出已清干净）。vector_swi 要做的就是把用户现场压满（4.4.6）：

armasm
ENTRY(vector_swi)
	sub	sp, sp, #S_FRAME_SIZE
	stmia	sp, {r0 - r12}			@ Calling r0 - r12
 ARM(	add	r8, sp, #S_PC		)
 ARM(	stmdb	r8, {sp, lr}^		)	@ Calling sp, lr
	mrs	r8, spsr			@ called from non-FIQ mode, so ok.
	str	lr, [sp, #S_PC]			@ Save calling PC
	str	r8, [sp, #S_PSR]		@ Save CPSR
	str	r0, [sp, #S_OLD_R0]		@ Save OLD_R0

七行，比 vector_stub 那套干净得多——不需要「IRQ 栈→内核栈」的搬运，寄存器可以直接往 sp_svc 上写。sub sp, sp, #S_FRAME_SIZE 一次预留 18 个字（72 字节）；stmia sp, {r0 - r12} 一口气存 r0–r12，sp 无 ! 所以存完不动；add r8, sp, #S_PC 让 r8 指向 pt_regs 里 ARM_pc 那一格；stmdb r8, {sp, lr}^ 的 ^ 让 stm 访问用户态的 sp_usr、lr_usr，db 是先减后存，两个值被写进 r8-8 和 r8-4，正好是 ARM_sp 和 ARM_lr 两格；mrs r8, spsr 取到用户执行 swi 时的 CPSR；最后三行分别把用户返回地址、用户 CPSR、原始 r0 写进 ARM_pc、ARM_cpsr、ARM_ORIG_r0。第 4 行和第 3 行的配合是关键：r8 先指到 ARM_pc，再往前减 8 字节，正好落在 ARM_lr、ARM_sp 两格——在 SVC 模式下直接读 sp/lr 拿到的是内核值，加 ^ 才能读到用户值。

r0 为什么存两次？ str r0, [sp, #S_OLD_R0] 和 stmia sp, {r0 - r12} 里的 r0 是同一个值，看起来冗余，但两个域后续角色不同：

域 写入时机 后续由谁改 用途
ARM_r0（S_R0） 进内核时 sys_xxx 返回值覆盖它 承载返回值
ARM_ORIG_r0（S_OLD_R0） 进内核时 谁都不改 保留原始第一个参数

r0 在系统调用里有两个身份：进来是第一个参数，出去是返回值。只有一格的话，参数值被覆盖后就查不到了。ptrace、syscall tracing、seccomp 这些要看「原始参数」的场合必须有不被改的副本。代价 4 字节，收益是事后还能知道用户传了什么。

十五、vector_swi 与内核栈上的用户现场构建 #

七行压完，内核栈上长出完整的 pt_regs。偏移在 asm-offsets.c 里用 offsetof 算出，汇编用 S_xxx 常量引用：

偏移常量 成员 内容 由谁写入
S_R0 + 0 ARM_r0 用户 r0 stmia sp, {r0-r12}
+4 … +40 ARM_r1 … ARM_r10 用户 r1–r10 同上
+44 ARM_fp r11，帧指针 同上
+48 ARM_ip r12，临时寄存器 同上
S_SP + 52 ARM_sp 用户 sp_usr stmdb r8, {sp, lr}^
S_LR + 56 ARM_lr 用户 lr_usr 同上
S_PC + 60 ARM_pc 返回地址（swi 下一条） str lr, [sp, #S_PC]
S_PSR + 64 ARM_cpsr 用户 CPSR str r8, [sp, #S_PSR]
S_OLD_R0 + 68 ARM_ORIG_r0 原始 r0 str r0, [sp, #S_OLD_R0]

18 个 4 字节 = 72 字节 = S_FRAME_SIZE。r0–r15 是 16 个，加 CPSR 是 17 个，第 18 个就是 ARM_ORIG_r0。sp + 0 指向表首 ARM_r0，sp + 68 是末尾的 ARM_ORIG_r0。注意 ARM_sp / ARM_lr 排在 ARM_pc 之前，不是 r0…r15 的自然序——r13、r14 被挪到 pc 前两位，原因是 stmdb r8, {sp, lr}^ 只能往前写两个连续格子，排在这儿正好让一条「先减后存」搞定。

栈上只有 core register，够不够？ 严格意义的「硬件上下文」是一大块内存，装着某时刻 CPU 的全部状态，不只是 r0–r15 加 CPSR，还包括 FPU 寄存器、状态位、一些内部 block 状态。pt_regs 只存了 core register 这一层。够不够取决于接口约定：Linux 的约定是内核态代码不许执行浮点指令，要用 FPU 得在用它的代码前后自己加保存/恢复，保证返回用户态时 FPU 上下文原样不变。有了这条约定，入口只需存 core register——内核不碰 FPU，FPU 里的东西自然还是用户的。这不是风格建议，是硬约束，kernel_fpu_begin() / kernel_fpu_end() 那一对存在的意义就是：临时借用 FPU 时先把用户上下文存起来，用完恢复。

压完现场，还有几个初始化动作：

armasm
	zero_fp
	alignment_trap r10, ip, __cr_alignment
	enable_irq
	ct_user_exit
	get_thread_info tsk
指令 作用 省略的后果
zero_fp 清 r11（帧指针） 调试器回溯会顺着用户 fp 走进用户空间，栈回溯全乱
alignment_trap 处理非对齐访问陷阱 硬件不支持非对齐访问时，用户的非对齐访存无法模拟
enable_irq 清 CPSR.I，开中断 整个系统调用期间中断全关，延迟飙高
ct_user_exit 通知 context tracking 已离开用户态 NO_HZ_FULL 之类特性记账错乱
get_thread_info tsk tsk = r9 = thread_info 后面所有 [tsk, #TI_xxx] 访问全错

zero_fp 的原理：fp（r11）为 0 是「调用链到根」的约定标记，清零后调试器往回追栈到 fp == 0 就停，不会误入用户空间的帧。enable_irq 单独强调：SWI 进来时硬件已把 I 置 1，所以到这儿必须主动开门。系统调用的绝大部分执行时间是开着中断的，这和 IRQ 路径正好相反，也是「系统调用可以睡、IRQ 不能睡」的物理基础——中断开着，才有被调度出去的机会。alignment_trap 牵扯一段 ARM 旧账：ARMv8 硬件全支持非对齐访问，仅限 normal memory，取指访问和 device type 内存访问必须对齐；ARMv7 及更早部分核不支持，硬件不支持时内核可开 CONFIG_ALIGNMENT_TRAP 用软件模拟，代价极大，一次非对齐访问变成一次异常加一段软件处理，所以能不开就不开。

十六、系统调用号查表：sys_call_table #

调用号从哪来取决于 ABI：

ABI 调用号在哪 内核配置 入口指令 兼容性
OABI（老） swi 编码的低 24 位 CONFIG_OABI_COMPAT swi 0x900000+n 能跑老二进制，内核变大、入口变慢
EABI（ARM ABI） r7 CONFIG_AEABI swi 0 现代 glibc，入口零开销

vector_swi 里对应这段（4.4.6）：

armasm
#if defined(CONFIG_OABI_COMPAT)

	USER(	ldr	r10, [lr, #-4]		)	@ get SWI instruction
 ARM_BE8(rev	r10, r10)			@ little endian instruction

#elif defined(CONFIG_AEABI)

	@ 空。系统调用号已经在 r7 里，无需任何代码

#else
	/* Legacy ABI only. */
	USER(	ldr	scno, [lr, #-4]		)	@ get SWI instruction
#endif

EABI 分支是空的，这是设计的胜利：零指令开销。OABI 分支要读 swi 指令本身，lr_svc 存的是 swi 的下一条地址，所以 [lr, #-4] 正好是那条指令的编码。取出来之后：

armasm
	uaccess_disable tbl

	adr	tbl, sys_call_table		@ tbl = 系统调用表基址

#if defined(CONFIG_OABI_COMPAT)
	bics	r10, r10, #0xff000000
	eorne	scno, r10, #__NR_OABI_SYSCALL_BASE
	ldrne	tbl, =sys_oabi_call_table
#elif !defined(CONFIG_AEABI)
	bic	scno, scno, #0xff000000		@ 掩掉 SWI 操作码
	eor	scno, scno, #__NR_SYSCALL_BASE	@ 校验 OS number
#endif

uaccess_disable tbl 把 tbl 从 uaccess 的「窗口」里摘出来——ARM 靠 addr_limit 做范围检查，tbl 是内核地址，不该被当成用户地址校验。adr tbl, sys_call_table 取表基址，adr 是 PC 相对的，适合取本 image 内的符号。OABI 兼容那三条是判断「这次要不要走 OABI 表」：bics r10, r10, #0xff000000 取 swi 低 24 位，结果非 0 就置标志；eorne 算出真正的调用号；ldrne 换成 sys_oabi_call_table。EABI 下用户永远发 swi 0，低 24 位是 0，所以「低 24 位非 0」就等于「这是 OABI 调用」。一次 bics 加两个条件执行就把两套 ABI 分流完了。到这一步，r7（scno）是调用号，r8（tbl）是表指针。

swi 的参数传递不能用栈——栈已经换了，用户栈上压的东西内核看不到（除非 copy_from_user）。只能走寄存器：r0–r3 传前四个参数，r4、r5 传第五、第六个。内核里的 sys_xxx 是正常 C 函数，超出 4 个的参数要在栈上，所以进 C 函数之前得把 r4、r5 压栈：

armasm
local_restart:
	ldr	r10, [tsk, #TI_FLAGS]		@ 检查 syscall tracing
	stmdb	sp!, {r4, r5}			@ 压第五、第六个参数

	tst	r10, #_TIF_SYSCALL_WORK		@ 在跟踪系统调用吗？
	bne	__sys_trace

	cmp	scno, #NR_syscalls		@ 检查调用号上界
	badr	lr, ret_fast_syscall		@ 返回地址
	ldrcc	pc, [tbl, scno, lsl #2]		@ 调用 sys_* 例程

四件事：stmdb sp!, {r4, r5} 的 ! 让 sp 真正下移 8 字节，这就是那个「偏移 8 字节」的来源，第十七章要补回来；cmp scno, #NR_syscalls 做越界检查，ldrcc（carry clear，即 scno < NR_syscalls）才跳转，越界就不跳、落空走 -ENOSYS；badr lr, ret_fast_syscall 手工设返回地址，不能用 bl，因为目标地址是运行时从表里取的；ldrcc pc, [tbl, scno, lsl #2] 查表跳转，lsl #2 是乘 4。badr 是 adr 的大范围版本。_TIF_SYSCALL_WORK 检查放在表查找之前，因为 ptrace / seccomp 需要在实际执行前介入，跳 __sys_trace 后由它决定放行还是改写调用号。

这张表本体由 arch/arm/kernel/calls.S 生成，每项指向一个 C 函数，索引就是调用号：

c
	sys_restart_syscall	/* 0 */
	sys_exit		/* 1 */
	sys_fork		/* 2 */
	...

ldrcc pc, [tbl, scno, lsl #2] 取第 scno 项直接跳过去。这几百行由 syscalls.tbl 脚本生成，编号和函数名的对应关系写死在 include/uapi/asm/unistd.h 的 __NR_xxx 里。ret_fast_syscall 是「快路径」：正常 sys_xxx 返回后 lr 指向它，前提是「返回用户态之前没什么事要办」，第十七章验证这个前提。

十七、系统调用的返回路径 #

返回前要办的事和中断返回高度重合——终点一样，起点也一样（都在 SVC 模式的 pt_regs 上）。

armasm
disable_irq_notrace			@ 关中断
ldr	r1, [tsk, #TI_FLAGS]		@ 再查一次 syscall tracing
tst	r1, #_TIF_SYSCALL_WORK | _TIF_WORK_MASK
bne	fast_work_pending

restore_user_regs fast = 1, offset = S_OFF

fast_work_pending:
	str	r0, [sp, #S_R0+S_OFF]!	@ 存下返回值 r0

三行判定：disable_irq_notrace 关门（恢复现场不能被中断打断）；tst 把「系统调用跟踪」和「待办工作」两组 flag 一起测；任一为真就绕道。_TIF_WORK_MASK 的三个成员和中断路径完全一样，最常被提起的是 _TIF_NEED_RESCHED——系统调用返回用户态是一个明确的调度点，一个 read() 返回的瞬间当前进程会被换出去。restore_user_regs 两个参数：

参数 值 含义
fast 1 走 ldmdb sp, {r1 - lr}^ 分支，只恢复 r1–r14
offset S_OFF（= 8） 补偿 local_restart 里 stmdb sp!, {r4, r5} 压的 8 字节

fast = 1 为什么不恢复 r0？因为这时 r0 里装的就是 sys_xxx 的返回值，马上要带给用户，不能拿栈上的旧值盖掉——这就是快路径快在哪，少恢复一个寄存器，且那个寄存器恰好是结果。offset = S_OFF 的补偿必须做：压 r4、r5 时 sp 下移了 8 字节，现在 pt_regs 的基址相对 sp 偏移 8，所有 [sp, #S_xxx] 访问都要加它。恢复现场的全文（4.4.6）：

armasm
	.macro	restore_user_regs, fast = 0, offset = 0
	mov	r2, sp
	ldr	r1, [r2, #\offset + S_PSR]	@ r1 = 用户 CPSR
	ldr	lr, [r2, #\offset + S_PC]!	@ lr = 用户 PC，r2 移到 PC 位置
	msr	spsr_cxsf, r1			@ SPSR = 用户 CPSR
	.if	\fast
	ldmdb	r2, {r1 - lr}^			@ 恢复 r1 - r14
	.else
	ldmdb	r2, {r0 - lr}^			@ 恢复 r0 - r14
	.endif
	mov	r0, r0				@ ARMv5T 及更早需要这个 nop
	add	sp, sp, #\offset + S_FRAME_SIZE
	movs	pc, lr				@ 返回用户空间
	.endm

和第十二章 IRQ 版本比，两处不同：这里用 r2 当工作寄存器（mov r2, sp 之后所有访问走 r2），IRQ 版直接用 sp，因为系统调用要保留 sp 到最后算 add sp, sp, #\offset + S_FRAME_SIZE；收尾是 #\offset + S_FRAME_SIZE，IRQ 版是 #S_FRAME_SIZE - S_PC（中间那个 ! 已让 sp 前进到 S_PC）。两版对 sp 的账要各算各的。

返回值的两种归宿。

情况 fast r0 在哪 谁负责送回去
无待办工作 1 物理 r0 寄存器 ldmdb {r1-lr}^ 不动 r0，原样带出
有待办工作 0 已被 str r0, [sp, #S_R0+S_OFF]! 存进 pt_regs->ARM_r0 ldmdb {r0-lr}^ 从栈上捞回

fast_work_pending 那句的 ! 很关键：不仅存值，还把 sp 下移到 ARM_r0 那一格。于是接下来走 restore_user_regs fast = 0, offset = 0 时 sp 已对齐到 pt_regs 起点，offset 不用再补——sp 下移的 8 字节正好抵消之前压参的 8 字节。这就是为什么「有 pending work 时 r0 会被装进 pt_regs」：返回值只能在栈上等着，因为从 bne fast_work_pending 到真正返回之间，r0 还要被信号处理、调度这些代码反复借用。两个 r0 域的互补关系到这儿才闭合：

text
进内核时        r0 = 参数1  ──┬─→ ARM_r0       （会被返回值覆盖）
                              └─→ ARM_ORIG_r0  （永久保留参数1）

出内核前        sys_xxx 返回 ──→ r0 = 返回值
                                  ├─ fast=1：r0 直接带走
                                  └─ fast=0：r0 → ARM_r0，再从栈上恢复

一个 pt_regs 两个 r0 域，一进一出各管一段，谁都不冗余。

共用的东西比重更多。 同一张向量表、同一套 banked 寄存器、同一个 sp_svc、同一份 pt_regs 布局、同一个 restore_user_regs 宏（只是参数不同）、同一组 _TIF_* flag、同一个 get_thread_info 宏、同一条 movs pc, lr 返回手法。这两条路不是「相似」，是同一套机制的两个实例。

本质差异只有一条。 IRQ 是被动、异步、不可预期的——不知道什么时候来，不知道从用户态还是内核态来，所以入口必须把所有分支都摆进那张 16 项表。SWI 是主动、同步、可预期的——用户显式执行一条指令，lr 天然正确，模式天然已知，所以入口可以写得极简，甚至做到「零代码取调用号」。连锁后果：中断上下文不能睡，系统调用可以。IRQ 路径整段关中断、被打断的是内核任意深度的代码，一睡就死锁；系统调用一进来就 enable_irq，跑在进程上下文，current 明确，能睡能调度。这一条决定了内核里哪些函数能调 kmalloc(GFP_KERNEL)、哪些只能用 GFP_ATOMIC。

十九、易错点速查 #

# 坑 正确认知
1 把 lr_irq = PC - 4 里的 PC 当成「被打断指令的地址」 执行 A 时 PC 读作 A+8，A 执行完自增到 A+12，硬件存 A+12-4 = A+8，软件再减 4 得 A+4。把 PC 当 A 算会推出「返回点 = A」，然后怀疑内核重入
2 把 correction 当成「硬件少减的那部分」 它是每类异常自己的常量，值 0/4/8，等于「硬件给的值」与「我要的返回点」之差。IRQ 4、pabt 4、dabt 8、SWI 0
3 以为 r0–r12 在 IRQ 模式里是 banked 的 不 banked，只有 sp、lr、SPSR 是（FIQ 额外有 r8–r12）。所以必须尽快存 r0，否则 mrs r0, cpsr 一执行用户 r0 就没了
4 以为 sp_irq 那块 12 字节是正常的递减栈 它从低地址往上用：stmia sp, {r0, lr} 写 [sp]、[sp+4]，str lr, [sp, #8] 写 [sp+8]。按递减栈直觉找「栈顶下面」会找错方向
5 以为 movs pc, lr 只是跳转 s 后缀让它同时把 SPSR 拷进 CPSR，这才是切模式的实现。写成 mov pc, lr 就只跳不切，栈留在 SVC 而代码以为切了
6 搞混 ^ 的两种语义 列表里没有 pc：访问用户态 banked 寄存器（sp_usr、lr_usr）。列表里有 pc：触发异常返回语义，SPSR → CPSR
7 把两个版本的 early_trap_init 混着引用 2.6.x 无参、stub 在 +0x200、kuser helper 挤页尾、刷一页；3.14 有参、stub 在 +0x1000、kuser_init() 单独调、刷两页
8 把 restore_user_regs 两个版本的 sp 账混算 IRQ 版 ldr lr, [sp, #\offset + S_PC]! 已让 sp 前进到 S_PC，收尾 #S_FRAME_SIZE - S_PC；系统调用版 sp 全程没动（用 r2），收尾 #\offset + S_FRAME_SIZE
9 忘了 S_OFF 那 8 字节 系统调用里 stmdb sp!, {r4, r5} 压了第五、六参数，sp 下移 8 字节，之后所有 [sp, #S_xxx] 都得加 S_OFF。忘了会从错误位置读 pc 和 cpsr，返回后直接跑飞
10 以为 ARM_ORIG_r0 是多余的 它是唯一没被返回值覆盖的 r0 副本，ptrace 读参数、seccomp 决策都要用
11 以为内核栈是「两个 page 各占一半」 单页配置下（THREAD_SIZE = 8192，占 2 页连续内存）底部是 thread_info、顶部是栈。换成 4KB 栈配置，那个写死的 13 就是错的
12 以为 FIQ 走同一套流程 Linux 的 FIQ 处理不遵循 pt_regs 约定。所以 M[3:0] = 1（FIQ）和 = 2（IRQ 嵌套）在 16 项表里都放 __irq_invalid
13 以为 enable_irq 是中断处理路径上的 不是。vector_stub 路径全程关中断，enable_irq 出现在 vector_swi 里，是系统调用路径的动作
14 以为 sys_call_table 的下标和 swi 立即数是一回事 EABI 下不对：调用号走 r7，swi 立即数恒为 0。混用会让查表索引错位，出现 open() 变成 write() 之类的灵异现象
