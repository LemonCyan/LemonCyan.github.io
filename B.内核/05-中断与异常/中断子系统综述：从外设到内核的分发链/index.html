一、为什么驱动工程师必须懂中断子系统 #

写驱动不是调 API。中断这条线上 API 只是最后一米，往前有流控、有硬件手册没写清的边角、有 SMP 下的并发。不搞清楚会怎样，三个具体后果：API 用错——request_threaded_irq 的 handler 在硬中断上下文跑，只能做「确认是我的中断 + 关掉设备侧中断 + 返回 IRQ_WAKE_THREAD」，thread_fn 才在 irq thread 里跑，IRQF_ONESHOT、IRQF_SHARED、IRQF_TRIGGER_* 各管一件事，混着填就是给自己埋雷；临界区保护错——你以为关中断就够了，代码在 SMP 上被另一个 CPU 并行进来，desc->lock 保护的是中断描述符不是你的设备状态，你的锁得自己拿；下半部选错——softirq、tasklet、workqueue 的上下文、并发度、能否睡眠完全不同，而它们全部由中断退出路径驱动，不懂退出路径就不知道它们什么时候跑。

还有一个很现实的理由：线上看到 irq 47: nobody cared (try booting with the "irqfixup" kernel parameter)，如果你不知道 note_interrupt 的判定条件就只能瞎猜；知道 10 万次触发 / 99900 次未处理这个阈值和 10 个 jiffies 的重置窗口，你就知道该去查谁没返回 IRQ_HANDLED。

二、一个中断从外设到 handler 的完整路径 #

先把骨架立起来。一次中断的处理分四步，四步分属四个不同的代码层：

步 谁在做 做什么 关键函数/位置
1 CPU 架构相关代码 现场保护，跳异常向量，最终进 C 代码 __vectors_start → vector_irq → vector_stub → __irq_usr/__irq_svc
2 machine 相关代码 + irq domain 从控制器读出 HW interrupt ID，翻译成 IRQ number gic_handle_irq → irq_find_mapping
3 generic irq 层 流控（嵌套、pending、SMP 竞争），遍历 action 链表 generic_handle_irq → desc->handle_irq → handle_irq_event
4 CPU 架构相关代码 现场恢复，检查抢占与信号 svc_exit / restore_user_regs

第 1、4 步是 ARM 汇编，第十章到第十三章拆开讲。第 2 步的关键是中断号翻译，第三章讲关系、第十四章讲衔接。第 3 步是本文主线，第八章逐个 handler 过。

text
外设 assert irq line
  -> Interrupt Controller 采样、锁存、按 target 分发
    -> CPU 核（ARM 的 nIRQ 信号）
      -> CPSR.M 切 IRQ mode，返回地址存进 lr_irq
        -> vector_irq（IRQ mode 的 12 字节栈）
          -> __irq_svc / __irq_usr（SVC mode，内核栈上搭 pt_regs）
            -> irq_handler
              -> handle_arch_irq（machine 层）
                -> gic_handle_irq  读 IAR 拿 hwirq
                  -> irq_find_mapping  hwirq -> IRQ number
                    -> generic_handle_irq
                      -> desc->handle_irq（flow handler）
                        -> handle_irq_event
                          -> action 链表里你的 handler

记住一句话：中断处理跨不过中断控制器这一层。CPU 只知道有人拉了它的 nIRQ，剩下的信息全在控制器寄存器里，得靠控制器驱动去读。

三、中断号：HW interrupt ID、IRQ number 与它们的关系 #

这是最容易糊掉的一节。一个中断在系统里至少有三个名字，用途完全不同：

名字 谁产生 取值范围（GIC 例子） 用途 代码里的样子
外设 irq line 硬件连线 板级连线，无编号 电气信号 原理图上的 NET 名
HW interrupt ID（hwirq） 中断控制器 GIC 下 0~1023 定位控制器内部哪个中断源 irq_data.hwirq
IRQ number（virq） 内核 irq domain 分配 全局 nr_irqs 以内 索引 irq_desc 数组 unsigned int irq
中断描述符 内核静态数组/树 与 IRQ number 一一对应 存状态、chip、action 链表 struct irq_desc *desc

转换发生在 machine 层，就两行：

c
irqnr = irqstat & ~0x1c00;                      /* 从 IAR 里剥出 interrupt ID */
irqnr = irq_find_mapping(gic->domain, irqnr);   /* hwirq -> IRQ number */
handle_IRQ(irqnr, regs);

hwirq 和 IRQ number 不是同一个数，也不需要相等。控制器级联时两个控制器的 hwirq 可以都是 5，但它们的 IRQ number 绝不重复，这是 irq domain 存在的全部理由。GIC 的 ID 空间按用途切片，gic_handle_irq 里的判断就是照着这个切法写的：

ID 区间 类型 含义 代码分支
0~15 SGI 软件产生，IPI 用 if (irqnr < 16) → handle_IPI
16~31 PPI 每 CPU 私有外设中断 走通用分支
32~1019 SPI 共享外设中断，外设都挂这儿 走通用分支
1020~1023 特殊 保留；1023 表示 spurious 不进 handler

原稿的判断写的是 irqnr > 15 && irqnr < 1021，覆盖 SPI + PPI；irqnr < 16 走 IPI。1020~1023 的特殊 ID 是 GIC 规范的定义，不在本文代码里体现，标为规范依据。

四、中断处理的三层分工：硬件 → 流控层 → handler #

generic irq 的设计哲学只有一句：把流的逻辑和芯片的细节切开。内核文档 genericirq.rst 开篇就写了这件事——旧时代的 __do_IRQ() 超级 handler 把两者揉在一起，i386 上于是出现了 ioapic_level_irq 和 ioapic_edge_irq 这种低层细节重复、流控不同的怪胎。切开之后是三层：

层 职责 代码实体 谁写
驱动 API 层 申请/释放/开关中断 request_threaded_irq、free_irq、disable_irq 你
flow handler 层 流控：mask/ack/unmask/EOI 的时序，遍历 action 链表 handle_level_irq 等 内核通用代码
chip 层 硬件寄存器操作 irq_chip 的一堆 callback 中断控制器驱动

对应四拨人：硬件无关的通用模块（kernel/irq/，不认识任何 CPU 和控制器）、CPU 架构相关代码（arch/arm/kernel/entry-armv.S 这类）、中断控制器驱动（GIC、GPIO 控制器各自一份）、普通外设驱动（用第一类的 API 写自己的逻辑）。数据结构把三层绑在一起，这是骨架，字段按主线 generic irq 整理、顺序做了简化：

c
struct irq_desc {                 /* 一个中断一份，IRQ number 就是它的下标 */
    struct irq_common_data irq_common_data;
    struct irq_data        irq_data;      /* 指向 chip 与 chip_data，含 hwirq */
    irq_flow_handler_t     handle_irq;    /* 流控层入口，第五章那个 desc->handle_irq */
    struct irqaction      *action;        /* 你的 handler 挂这条链表上，可共享 */
    unsigned int           irq_count;     /* note_interrupt 用的统计 */
    unsigned long          last_unhandled;
    unsigned int           irqs_unhandled;
};
struct irq_data {
    unsigned int      irq;          /* IRQ number */
    unsigned long     hwirq;        /* HW interrupt ID */
    struct irq_chip  *chip;         /* 芯片层 callback 表 */
    void             *chip_data;
    struct irq_domain *domain;
    struct irq_data  *parent_data;  /* 级联时的上一层 */
};
struct irq_chip {
    void (*irq_ack)(struct irq_data *);
    void (*irq_mask)(struct irq_data *);
    void (*irq_mask_ack)(struct irq_data *);   /* 可选，性能优化 */
    void (*irq_unmask)(struct irq_data *);
    void (*irq_eoi)(struct irq_data *);        /* 可选，fasteoi 类型必需 */
    int  (*irq_retrigger)(struct irq_data *);  /* 可选，resend 用 */
    int  (*irq_set_type)(struct irq_data *, unsigned int);
    int  (*irq_set_wake)(struct irq_data *, unsigned int);
};
struct irqaction {                /* 一次 request_irq 就是一个 irqaction */
    irq_handler_t     handler;    /* 硬中断上下文 */
    irq_handler_t     thread_fn;  /* 线程化后半段 */
    void             *dev_id;
    unsigned int      irq;
    unsigned long     flags;
    const char       *name;
    struct irqaction *next;       /* 共享中断靠这条链串起来 */
};

三层的关系一句话讲完：flow handler 只碰 irq_data.chip，绝不碰外设寄存器；外设寄存器只有你挂在 action 链表上的 handler 才碰。这条界线被打破，代码就再也理不清。

五、进入 high level handler 的路径 #

1、从 ARM 异常向量到 machine 层 #

irq_handler 宏只有两种形态，取决于 CONFIG_MULTI_IRQ_HANDLER：配了就直接跳 handle_arch_irq 这个函数指针（ldr r1, =handle_arch_irq；mov r0, sp 传 pt_regs；adr lr, BSYM(9997f) 设返回地址；ldr pc, [r1] 跳过去），没配就走 arch_irq_handler_default（完整汇编在第十二章第 6 小节再贴一次，两处是同一段代码）。运行期决定去哪的理由：一份 kernel image 要支持多个硬件平台，启动时认清平台再装 handler。原稿说这是「猜想」，我也照实标为理解，不是定论。函数指针不是 per-CPU 的，全局一份，初始化一次就够。单类型控制器（比如两个级联 GIC）在控制器初始化时设：

c
if (gic_nr == 0) {
    set_handle_irq(gic_handle_irq);
}

gic_nr 是 GIC 编号，第一个 GIC 是 0，第二个是 1。混用多种控制器时（例如 S3C2451 有 GPIO 型和 SOC 上两种），在 machine driver 里按平台设 handle_arch_irq = mdesc->handle_irq;。

2、控制器驱动这一层 #

以两个级联 GIC 为例，注释是本文补的（原稿把说明直接贴在语句后面）：

c
static asmlinkage void __exception_irq_entry gic_handle_irq(struct pt_regs *regs)
{
    u32 irqstat, irqnr;
    struct gic_chip_data *gic = &gic_data[0];      /* 只处理 root GIC */
    void __iomem *cpu_base = gic_data_cpu_base(gic);

    do {
        irqstat = readl_relaxed(cpu_base + GIC_CPU_INTACK);   /* ack + 拿 ID */
        irqnr = irqstat & ~0x1c00;
        if (likely(irqnr > 15 && irqnr < 1021)) {   /* SPI / PPI */
            irqnr = irq_find_mapping(gic->domain, irqnr);
            handle_IRQ(irqnr, regs);
            continue;
        }
        if (irqnr < 16) {                           /* IPI */
            writel_relaxed(irqstat, cpu_base + GIC_CPU_EOI);
#ifdef CONFIG_SMP
            handle_IPI(irqnr, regs);
#endif
            continue;
        }
        break;                                      /* 特殊 ID，退出 */
    } while (1);
}

读 GIC_CPU_INTACK 这一个动作干两件事：ack 中断、拿到 HW interrupt ID。循环是因为一次异常里常常有好几个中断排队。

3、从 IRQ number 到 high level handler #

ARM 这一层只有薄薄一层包装（中间略），真正干活的是 generic irq：

c
void handle_IRQ(unsigned int irq, struct pt_regs *regs)
{
    generic_handle_irq(irq);
}
int generic_handle_irq(unsigned int irq)
{
    struct irq_desc *desc = irq_to_desc(irq);   /* IRQ number -> 描述符 */
    if (!desc)
        return -EINVAL;
    generic_handle_irq_desc(irq, desc);
    return 0;
}
static inline void generic_handle_irq_desc(unsigned int irq, struct irq_desc *desc)
{
    desc->handle_irq(irq, desc);               /* 流控层入口 */
}

desc->handle_irq 指向哪一个 handle_xxx_irq，在控制器驱动初始化时按触发类型装好。装错了，中断要么丢，要么卡死。

六、理解 high level handler 需要的三个前置知识 #

flow handler 里全是 IRQS_PENDING、IRQS_REPLAY、IRQS_WAITING 这些位，因为它们背后是三个独立机制。不搞清这三个，读 handler 就是看天书。

1、自动探测 IRQ #

老硬件没有设备树，驱动得自己试出 IRQ 号，两个函数配一对：irqs = probe_irq_on(); 启动探测，让待探测的硬件产生一次中断，irq = probe_irq_off(irqs); 结束探测拿结果。probe_irq_on 返回一个 32 bit 掩码，标出备选的那几个 IRQ：

c
unsigned long probe_irq_on(void)
{
    unsigned long mask = 0;
    for_each_irq_desc_reverse(i, desc) {      /* 从 nr_irqs-1 倒着扫到 0 */
        raw_spin_lock_irq(&desc->lock);
        if (!desc->action && irq_settings_can_probe(desc)) {   /* (1) */
            desc->istate |= IRQS_AUTODETECT | IRQS_WAITING;
            if (irq_startup(desc, false))
                desc->istate |= IRQS_PENDING;
        }
        raw_spin_unlock_irq(&desc->lock);
    }
    msleep(100);                              /* (2) */
    for_each_irq_desc(i, desc) {
        raw_spin_lock_irq(&desc->lock);
        if (desc->istate & IRQS_AUTODETECT) {
            if (!(desc->istate & IRQS_WAITING)) {
                desc->istate &= ~IRQS_AUTODETECT;
                irq_shutdown(desc);
            } else if (i < 32)                /* (3) */
                mask |= 1 << i;
        }
        raw_spin_unlock_irq(&desc->lock);
    }
    return mask;
}
/* 之后驱动让硬件产生一次中断，再调 probe_irq_off 收结果：
 * 扫所有描述符，只处理还在 IRQS_AUTODETECT 里的；IRQS_WAITING 已被
 * high level handler 清掉的那个就是候选，其余 irq_shutdown；候选多于
 * 一个就把 irq_found 取负返回表示失败。 */

(1) 两个条件：没有 irqaction（没人申请过）、允许探测（没设 IRQ_NOPROBE）。(2) 这 100ms 里中断照常进来，任何一个 flow handler 执行时都会干这一行，把 IRQS_WAITING 清掉：desc->istate &= ~(IRQS_REPLAY | IRQS_WAITING);。(3) 探测范围封在 31 号以内，因为 mask 是 32 bit。返回值语义：一个候选就是 IRQ 号，多于一个返回负数表示失败，一个都没有返回 0。这套机制在设备树普及后基本退役，但 IRQS_WAITING 这个位还留在 flow handler 里，你得知道它的来历。

2、resend 一个中断 #

电平触发和边沿触发的差别在这里变成实打实的 bug 源。电平触发简单直接：硬件事件来了就 assert 电平，CPU ack 之后电平撤销。边沿触发只给一个跳变，状态不持续，软件一步没跟上就丢。丢中断的经典剧本：CPU A 正在处理外设 x 的中断；x 的中断又来了（A 已经 ack，硬件允许再触发），另一个 CPU 抢到它，mask + ack，然后在描述符上打 IRQS_PENDING，把活儿委托给 A；CPU B 因为同步需求 disable 了 x 的 IRQ，A 看到 disabled 就直接退出，pending 没人处理；等 enable 时必须查 pending，补发一次，不然这个中断永远消失。

c
void check_irq_resend(struct irq_desc *desc, unsigned int irq)
{
    if (irq_settings_is_level(desc)) {        /* 电平中断没这问题 */
        desc->istate &= ~IRQS_PENDING;
        return;
    }
    if (desc->istate & IRQS_REPLAY)           /* 已经安排过了，别重复 */
        return;
    if (desc->istate & IRQS_PENDING) {
        desc->istate &= ~IRQS_PENDING;
        desc->istate |= IRQS_REPLAY;
        if (!desc->irq_data.chip->irq_retrigger ||
            !desc->irq_data.chip->irq_retrigger(&desc->irq_data)) {
#ifdef CONFIG_HARDIRQS_SW_RESEND
            /* 硬件不会重触发，就走软件补发 */
#endif
        }
    }
}

优先让硬件重触发，硬件不支持时走 CONFIG_HARDIRQS_SW_RESEND 的软件补发。flow handler 里清 IRQS_REPLAY 就是宣告这次补发结束。

3、unhandled interrupt 与 spurious interrupt #

中断进来了但没人认领，两种情形：根本没注册 handler；注册了但所有 handler 都返回 IRQ_NONE。内核不会立刻 disable 这条线，因为中断线允许共享，一刀切太狠。它的策略是观察：触发 10 万次，其中 99900 次以上没人处理，才动手。

c
void note_interrupt(unsigned int irq, struct irq_desc *desc, irqreturn_t action_ret)
{
    if (desc->istate & IRQS_POLL_INPROGRESS || irq_settings_is_polled(desc))
        return;
    if (action_ret == IRQ_WAKE_THREAD)         /* 线程化中断的正常返回 */
        return;
    if (bad_action_ret(action_ret)) {          /* 返回值本身非法 */
        report_bad_irq(irq, desc, action_ret);
        return;
    }
    if (unlikely(action_ret == IRQ_NONE)) {
        if (time_after(jiffies, desc->last_unhandled + HZ/10))   /* (1) */
            desc->irqs_unhandled = 1;                            /* 重新计数 */
        else
            desc->irqs_unhandled++;
        desc->last_unhandled = jiffies;
    }
    if (unlikely(try_misrouted_irq(irq, desc, action_ret))) {    /* (2) */
        int ok = misrouted_irq(irq);
        if (action_ret == IRQ_NONE)
            desc->irqs_unhandled -= ok;
    }
    desc->irq_count++;
    if (likely(desc->irq_count < 100000))      /* (3) */
        return;
    desc->irq_count = 0;
    if (unlikely(desc->irqs_unhandled > 99900)) {
        __report_bad_irq(irq, desc, action_ret);
        desc->istate |= IRQS_SPURIOUS_DISABLED;
        desc->depth++;
        irq_disable(desc);                     /* 关掉这条线 */
        mod_timer(&poll_spurious_irq_timer,    /* (4) */
                  jiffies + POLL_SPURIOUS_IRQ_INTERVAL);
    }
    desc->irqs_unhandled = 0;
}

(1) 时间窗口为什么必要：硬件抽风时会在极短时间内疯狂触发，如果一次 unhandled 距离上次已经超过 10 个 jiffies（HZ=100 时是 100ms），就得清零重算，否则计数随时间长跑，迟早把一条正常中断送上审判台。(2) try_misrouted_irq 是「IRQ 路由接错」的补救，把所有 handler 都试一遍看谁能认领。(3) 每 10 万次为一个检查周期，到期清零重新统计。(4) 关掉之后还不放心，起个 timer 定期轮询（poll_spurious_irqs），它只碰挂了 IRQS_SPURIOUS_DISABLED 的描述符，遇到 0 号（x86 上是 timer）跳过，靠 irq_poll_active 保证全局只有一个 poller，一旦起来就靠 mod_timer 自我续命。命令行参数 noirqdebug 可以整体关掉这套机制，生产环境调性能时偶尔会用到。

七、中断控制器的硬件模型 #

1、三种角色与四个接口 #

中断硬件系统只有三种器件：外设、中断控制器、CPU。外设提供 irq request line，靠电气信号请求服务；中断控制器是两者的桥，外设线太多 CPU 需要中间人，线不够就级联；CPU 只管算数，不排优先级——那是控制器的事，它只认中断请求线：ARM 是 nIRQ 和 nFIQ，x86 是可屏蔽/不可屏蔽中断。

接口 方向 干什么 物理形态
触发信号 控制器 → CPU 通知有中断 ARM：nIRQ/nFIQ 线；x86：INT/NMI；PowerPC：MC/CRIT/NON-CRIT
ack 信号 CPU → 控制器 取走这次中断的信息 ARM+GIC：读 IAR；x86+8259：nINTA
EOI 信号 CPU → 控制器 宣告处理完毕 ARM+GIC：写 EOIR
控制/数据总线 双向 读写控制器寄存器 MMIO 或总线访问

Linux 只使用其中一条触发线，ARM 上只用 nIRQ，FIQ 不管（3.14 时代）。从 CPU 视角看，逻辑简单到极点：不区分优先级，线一 assert、中断没被 mask，就跳异常向量，处理完返回。控制器与外设之间只有一个接口：interrupt request 线，电平或边沿。

2、多控制器与多 CPU 的拓扑 #

控制器分两类：支持多核的（GIC、APIC），不支持的（S3C2410 的控制器、x86 的 PIC）。单 GIC 平台上，改 GIC 寄存器就能把任意外设中断送给任意核。多个 GIC 怎么办？假设 8 核、2000 个外设中断，GIC 一个能管 1024 个 ID，那就得两个：一个 root，一个 secondary。两条路：

方案 接法 好处 代价
一 8 核全挂 root，secondary 不接 CPU，其输出接到 root 的某个 SPI 软件简单，secondary 的 CPU interface 固定 secondary 的 PPI/SGI 全废；挂它上面的外设中断只能统一送往一个核
二 root 接 CPU0~3，secondary 接 CPU4~7 各管一段，中断可分担 单条中断只能在 4 个核里分，8 核的力气使不出来

3、中断送给哪个 CPU #

只有多核控制器才有这个烦恼。外设中断送一个核就够——送到多个核，实际也只有一个人能和外设打交道，其余的在 handler 里发现已经被处理，直接返回。IPI 例外，它本来就是核间通信，广播毫无压力。用户侧的需求可以很复杂：绑定到某个核、几个核轮流。把复杂策略扔给硬件不合理，多一个晶体管就多一份功耗，常见做法是给每个中断一个 target CPU 寄存器（GIC 叫 Interrupt Processor Target），几位对应几个核：置 1 就上报，置 0 就不报，剩下的交给软件。

轮流处理的算法就这么几行：CPU0 在 handler 里把自己对应的位清零、把 CPU1 的位打开；下次中断就送到 CPU1；CPU1 在 handler 里反过来操作。两个核的轮转就实现了。

八、几种典型的 high level irq event handler #

选哪个 handler，不取决于「外设是电平还是边沿」，而取决于控制器在这个场景下的行为。原稿强调过这一点，判据整理成表：

handler 触发类型 控制器必须干什么 代码里谁被调用 典型硬件
handle_edge_irq 边沿 锁存边沿状态，ack 才能再触发 irq_ack + 循环内 unmask GPIO 型控制器（写 1 清 pending）
handle_level_irq 电平 电平在，中断就一直 active irq_mask_ack 打头，末尾有条件 irq_unmask 多数 SoC 片上控制器
handle_fasteoi_irq 电平/边沿 流控全在硬件里，软件只 EOI 只调 irq_eoi GIC 之类现代控制器
handle_simple_irq 任意 不需要芯片操作 谁都不调 软件解复用的子中断
handle_percpu_irq per-CPU 每核各自控 可选 irq_ack/irq_eoi，不加锁 timer、IPI 之类
handle_bad_irq — 无 handler 只报 spurious 兜底

1、handle_edge_irq #

硬件行为：上升沿来了，控制器把 pending 状态锁进寄存器，同时拉中断线告 CPU。此时外设到控制器的 request 线保持高电平，控制器看不到新的沿，这个高电平一直保持到你调 irq_ack，ack 之后才能检测下一次沿。ARM+GIC 不属于这一类：GIC 有 IAR，但读 IAR 拿 HW ID 的动作发生在 flow handler 之前，所以 GIC 的 irq_chip 提供不了这个场景要的 irq_ack。很多 GPIO 型控制器符合：有 pending 状态寄存器，读它获取状态，写 1 清掉。

c
void handle_edge_irq(unsigned int irq, struct irq_desc *desc)
{
    raw_spin_lock(&desc->lock);                              /* (0) */
    desc->istate &= ~(IRQS_REPLAY | IRQS_WAITING);

    if (unlikely(irqd_irq_disabled(&desc->irq_data) ||       /* (1) */
                 irqd_irq_inprogress(&desc->irq_data) || !desc->action)) {
        if (!irq_check_poll(desc)) {
            desc->istate |= IRQS_PENDING;
            mask_ack_irq(desc);
            goto out_unlock;
        }
    }
    kstat_incr_irqs_this_cpu(irq, desc);
    desc->irq_data.chip->irq_ack(&desc->irq_data);            /* (2) */

    do {
        if (unlikely(!desc->action)) {                        /* (3) */
            mask_irq(desc);
            goto out_unlock;
        }
        if (unlikely(desc->istate & IRQS_PENDING)) {          /* (4) */
            if (!irqd_irq_disabled(&desc->irq_data) &&
                irqd_irq_masked(&desc->irq_data))
                unmask_irq(desc);
        }
        handle_irq_event(desc);                               /* (5) */
    } while ((desc->istate & IRQS_PENDING) &&                 /* (6) */
             !irqd_irq_disabled(&desc->irq_data));
out_unlock:
    raw_spin_unlock(&desc->lock);                             /* (7) */
}

(0) 锁不成对，这是故意的。 看上去 raw_spin_lock 和 (7) 是一对，实际不是，中间 (5) 调用的 handle_irq_event 自己先把锁放了：

c
irqreturn_t handle_irq_event(struct irq_desc *desc)
{
    raw_spin_unlock(&desc->lock);     /* 和 (0) 配对 */
    /* 遍历 action list，调你自己的 handler —— 不持锁 */
    raw_spin_lock(&desc->lock);       /* 和 (7) 配对 */
}

为什么不持锁跑 handler？action list 里跑多久没人知道，持着 desc->lock 会让其他 CPU 在这条中断上排队，SMP 上直接变成串行化瓶颈。

(1) 三条不该继续的理由：中断已被别的 CPU 处理；中断被别的 CPU disable；描述符上没有 irqaction。前两条走同一招——打 pending、mask_ack_irq、退出。正在处理的那个 CPU 会检查 pending 并接手；被 disable 的那次，等 enable 时由 check_irq_resend 补发。这里为什么用 mask + ack 而不是单纯 ack？单纯 ack 意味着后续中断还会来，那 pending 叠 pending 怎么算？记次数？有意义吗？中断完全异步，你算的时候另一个 CPU 已经把 pending 改成 replay 了。事情变复杂就是方向错了，所以一次 mask + ack 断掉嵌套的念头。irq_check_poll 的存在是因为 spurious 轮询流程有时正碰着这个描述符：

c
static bool irq_check_poll(struct irq_desc *desc)
{
    if (!(desc->istate & IRQS_POLL_INPROGRESS))
        return false;
    return irq_wait_for_poll(desc);
}

(2) ack：控制器一旦被 ack，硬件准备好接受下一次触发，而那次触发会被调度到别的核上。(3) handler 已注销：跑 action list 时不持锁，别的 CPU 会在这期间调用 free_irq，回来发现 desc->action 是 NULL，mask 掉走人。(4) pending 一定有别人下手：说明别的 CPU 又触发了这个中断源并把活儿委托给你，那就把之前 mask 住的 unmask 回来，unmask 之后新的中断继续由别的 CPU 接，它们继续打 pending 再委托给你。(6) 循环条件：还有 pending 就继续处理一轮，但只要有别的 CPU disable 了这个源，本轮到此为止。

2、handle_level_irq #

硬件行为：高电平期间控制器就一直认为这个中断 active。ack 控制器不改电平状态，电平要等你 handler 里清了外设的状态寄存器才落下，落之前不 mask，控制器就一直 assert CPU。

c
void handle_level_irq(unsigned int irq, struct irq_desc *desc)
{
    raw_spin_lock(&desc->lock);
    mask_ack_irq(desc);                                        /* (1) */

    if (unlikely(irqd_irq_inprogress(&desc->irq_data)))        /* (2) */
        if (!irq_check_poll(desc))
            goto out_unlock;
    desc->istate &= ~(IRQS_REPLAY | IRQS_WAITING);
    kstat_incr_irqs_this_cpu(irq, desc);

    if (unlikely(!desc->action || irqd_irq_disabled(&desc->irq_data))) {   /* (3) */
        desc->istate |= IRQS_PENDING;
        goto out_unlock;
    }
    handle_irq_event(desc);
    cond_unmask_irq(desc);                                     /* (4) */
out_unlock:
    raw_spin_unlock(&desc->lock);
}

(1) 一进来就 mask_ack，和上一节的做法正好相反，这是全文最值得记住的对比。 看这条链：CPU ← 控制器 ← 设备。flow handler 只跟控制器打交道，设备寄存器归 action list 里的 handler 管。电平触发的特点：只要 request 线上的电平没撤，控制器就认为这个中断还在。你 ack 了控制器、电平没撤，控制器马上又 assert CPU，一个中断变成死循环，所以必须 mask 住，让控制器停止转发这个源，等 handler 清完外设状态再 unmask。边沿触发正好相反：沿稍纵即逝，你 mask 了很容易丢事件，所以只 ack 不 mask。这里的 ack 是写给控制器的，为的是清它在控制器侧的状态寄存器，但外部电平还在，能不能清干净取决于控制器实现。

(2) 既然一进来就 mask 了，为什么还查 in progress？ 因为 spurious 轮询那条路会绕过正常流程直接调 handler，串行化假设不成立。(3) 两个出口：没注册 handler，保持 mask 加 pending（原稿作者说这个 pending 有什么用他也还没想明白，照实保留）；被别的 CPU disable，同样加 pending 退出，等 enable 时补发。(4) 为什么 unmask 要带条件？ 正常情况 unmask 就完了，但线程化中断（IRQF_ONESHOT）要求 one shot：specific handler 里放一枪唤醒 irq thread，如果允许嵌套就会放好几枪，one shot 就破了，所以 cond_unmask_irq 在那种情况下不 unmask。

3、handle_fasteoi_irq #

原稿这里是 TODO，只有一行小标题，我按内核文档补出流控，代码实现未逐行核对，标「未验证」。这类控制器的流控全在硬件里做完，软件只需在 handler 跑完之后说一声处理完了：不 mask、不 ack（进来前硬件已 ack 或不需要），跑 action list，然后 irq_eoi。判据是 irq_chip 的 irq_eoi 必须实现。GIC 用得上——读 IAR 时已经 ack，处理完写 EOIR 就行，这也解释了为什么 GIC 的 chip 上没有可用的 irq_ack。顺带说一个内核文档里的老坑：handle_edge_eoi_irq 是给 powerpc/cell 上一个残废控制器打的补丁，文档原话是「abnomination」（拼写错误，原文如此），只在那一处用。

4、handle_simple_irq / handle_percpu_irq / handle_bad_irq #

handle_simple_irq 不碰芯片，适用于软件解复用的子中断——上层控制器报了中断，软件再细分给哪个子源，调用者自己负责 ack、clear、mask、unmask，内核文档对此有一句明确提示。handle_percpu_irq 只存在于 SMP，因为每个核有自己的那份，不存在跨核竞争，所以省掉锁：有 irq_ack 就先 ack，跑 action list，有 irq_eoi 就 EOI。handle_bad_irq 是兜底，没装 handler 的中断落到这里只报 spurious，不是给你用的。flow handler 靠 irq_set_handler() 一类接口在启动或设备初始化时装到 desc->handle_irq 上，装它的人是架构代码或控制器驱动；装错了症状是「中断能进但行为怪」，比如电平中断用 edge handler，会看到中断风暴或者偶发丢中断。

九、handle_irq_event 与 action 链表 #

flow handler 把流控做完，最后一件事是把活儿交给具体设备，这一段就是遍历链表。

c
irqreturn_t handle_irq_event(struct irq_desc *desc)
{
    struct irqaction *action = desc->action;
    irqreturn_t ret;

    desc->istate &= ~IRQS_PENDING;                    /* 准备处理，清 pending */
    irqd_set(&desc->irq_data, IRQD_IRQ_INPROGRESS);   /* 打上 in progress */
    raw_spin_unlock(&desc->lock);
    ret = handle_irq_event_percpu(desc, action);      /* 遍历链表 */
    raw_spin_lock(&desc->lock);
    irqd_clear(&desc->irq_data, IRQD_IRQ_INPROGRESS); /* 处理完，清标记 */
    return ret;
}
/* percpu 版本：对链上每个节点调 action->handler(irq, dev_id)，
 * 处理 IRQ_WAKE_THREAD 唤醒 action->thread，把返回值或到 retval，
 * 最后 if (!noirqdebug) note_interrupt(irq, desc, retval); */

IRQD_IRQ_INPROGRESS 就是前面 irqd_irq_inprogress() 查的那个位，它保证 SMP 上同一条中断的 handler 不会有两个 CPU 同时跑——后到的那个看到 in progress，打 pending 走人。链表结构决定了共享中断的语义：

场景 链表状态 遍历行为
独占中断 一个 irqaction 调一次，返回 IRQ_HANDLED
共享中断 多个 irqaction，next 串起来 每个都调，谁认领谁返回 IRQ_HANDLED
线程化 handler + thread_fn 都在 handler 返回 IRQ_WAKE_THREAD 唤醒 thread
无人认领 全部返回 IRQ_NONE 汇总成 IRQ_NONE，进 note_interrupt 计数

retval 是「或」的关系：只要有一个 handler 认领，整条中断就算处理了，全是 IRQ_NONE 才进 spurious 计数。这也是为什么乱返回 IRQ_HANDLED 有害——你一个人吞掉了「没人认领」的信号。一个必须刻在脑子里的顺序是：IRQS_PENDING 清得比 IRQD_IRQ_INPROGRESS 置位早，IRQD_IRQ_INPROGRESS 清得比 raw_spin_unlock 早。这个时序保证别的 CPU 看到 in progress 时 pending 一定已经清干净，两边不会互相覆盖，改这几行的顺序就会造出偶发丢中断。

十、ARM 中断处理的准备工作：栈与向量表 #

一切在开机时就摆好了。ARM 上要备三样：IRQ mode 的栈、SVC mode 的栈、异常向量表。

1、IRQ mode 的栈：只有 12 字节 #

ARM 有多个 processor mode，中断一进来就在 IRQ mode，但那只是过路，很快就切到 SVC：

M[4:0] 模式 缩写 Linux 里的用途
0b10000 User usr 用户空间程序
0b10001 FIQ fiq 不用（3.14 ARM Linux）
0b10010 IRQ irq 中断入口的过路站
0b10011 Supervisor svc 内核态主体
0b10111 Abort abt 数据/预取异常
0b11011 Undefined und 未定义指令
0b11111 System sys 特权级 user mode
0b10110 Monitor mon 需 TrustZone，Linux 内核不用
0b11010 Hyp hyp 需虚拟化扩展，Linux 内核不用

Linux 的中断处理大部分时间在 SVC mode 里跑，所以 IRQ mode 的栈极小，只有 12 字节——正好够存 r0、lr、spsr 三个字。ABT 和 UND 用同一套策略：短暂停留，然后切到 SVC 的栈，也就是发生异常那个时刻 current thread 的内核栈。

c
struct stack {
    u32 irq[3];
    u32 abt[3];
    u32 und[3];
} ____cacheline_aligned;
static struct stack stacks[NR_CPUS];

void notrace cpu_init(void)
{
    unsigned int cpu = smp_processor_id();
    struct stack *stk = &stacks[cpu];
#ifdef CONFIG_THUMB2_KERNEL
#define PLC "r"        /* Thumb-2 下 msr 只能用寄存器，不能立即数 */
#else
#define PLC "I"
#endif
    __asm__ (
    "msr    cpsr_c, %1\n\t"        /* 进 IRQ mode */
    "add    r14, %0, %2\n\t"       /* r14 = &stk->irq[0] */
    "mov    sp, r14\n\t"           /* 设 IRQ mode 的 sp */
    "msr    cpsr_c, %3\n\t"        /* 同上，设 ABT mode 的 sp */
    "add    r14, %0, %4\n\t"
    "mov    sp, r14\n\t"
    "msr    cpsr_c, %5\n\t"        /* 同上，设 UND mode 的 sp */
    "add    r14, %0, %6\n\t"
    "mov    sp, r14\n\t"
    "msr    cpsr_c, %7"            /* 回 SVC mode */
        :
        : "r" (stk),                                            /* %0 */
          PLC (PSR_F_BIT | PSR_I_BIT | IRQ_MODE),               /* %1 */
          "I" (offsetof(struct stack, irq[0])),                 /* %2 */
          PLC (PSR_F_BIT | PSR_I_BIT | ABT_MODE),
          "I" (offsetof(struct stack, abt[0])),
          PLC (PSR_F_BIT | PSR_I_BIT | UND_MODE),
          "I" (offsetof(struct stack, und[0])),
          PLC (PSR_F_BIT | PSR_I_BIT | SVC_MODE)
        : "r14");
}

内联汇编四段结构：asm(code : 输出 : 输入 : clobber)。约束符 "I" 是立即数，"r" 走通用寄存器，clobber 里的 r14 告诉编译器「我改过它了」。cpu_init 有三个调用场景：引导 CPU 走 start_kernel → setup_arch → setup_processor → cpu_init；从核上线走 start_kernel → rest_init → kernel_init → kernel_init_freeable → smp_init → cpu_up → _cpu_up → __cpu_up，ARM 下再 __cpu_up → boot_secondary → smp_ops.smp_boot_secondary（SoC 代码）→ secondary_startup → __secondary_switched → secondary_start_kernel → cpu_init；第三是睡眠唤醒，前提是 suspend 会丢 sp/abt/und 的 sp 值。

2、SVC mode 的栈：内核栈 #

用户态用用户栈存局部变量，陷入内核后换内核栈，就是 SVC mode 的栈。开机时只有一个 kernel thread，PID 0，叫 swapper 或 idle，它的栈是静态定义的：

c
union thread_union init_thread_union __init_task_data =
    { INIT_THREAD_INFO(init_task) };
union thread_union {
    struct thread_info thread_info;
    unsigned long stack[THREAD_SIZE/sizeof(long)];
};
/* 新进程/内核线程都从 dup_task_struct 里 alloc_thread_info_node 拿一份 */

ARM 上 THREAD_SIZE 是 8192 字节，占两个 page frame（原稿注：一个或两个 page，和配置相关）。一个细节：32 位 ARM 上 thread_info 就放在栈底，sp 一压栈就和它擦肩而过，栈溢出会先把 thread_info 写坏然后才 crash。这是 32 位 ARM 内核栈的老毛病，排查时看到 thread_info 内容莫名其妙，八成是栈炸了。

3、异常向量表 #

异常发生时，CPU 暂停当前指令、保存现场、跳到对应向量处执行。8 个向量凑成一张表：

armasm
    .section .vectors, "ax", %progbits
__vectors_start:
    W(b)    vector_rst
    W(b)    vector_und
    W(ldr)  pc, __vectors_start + 0x1000
    W(b)    vector_pabt
    W(b)    vector_dabt
    W(b)    vector_addrexcptn
    W(b)    vector_irq                 /* IRQ Vector — 本文主角 */
    W(b)    vector_fiq
偏移 向量 异常 返回地址修正
0x00 vector_rst 复位 —
0x04 vector_und 未定义指令 按指令类型
0x08 软中断（经 ldr 跳转） 系统调用 +4
0x0C vector_pabt 预取中止 +4
0x10 vector_dabt 数据中止 +8
0x14 vector_addrexcptn 地址异常（几乎不用） —

装表位置有两个：0x0（Normal/Low vectors）和 0xffff0000（High vectors），由 SCTLR 的第 13 位（V bit）决定。开了 MMU 的 ARM Linux 用 high vectors——0~3G 是用户空间，用 low vector 就把向量表放进了用户能碰到的地方。物理地址放哪不重要，映射到 0xffff0000 就行： 
c
static void __init devicemaps_init(const struct machine_desc *mdesc)
{
    vectors = early_alloc(PAGE_SIZE * 2);   /* 两个 page */
    early_trap_init(vectors);               /* 拷向量表 + stub */
    map.pfn = __phys_to_pfn(virt_to_phys(vectors));

        map.virtual = 0;
        map.length = PAGE_SIZE * 2;
        map.type = MT_LOW_VECTORS;

    map.type = MT_LOW_VECTORS;

}
void __init early_trap_init(void *vectors_base)
{
    /* 整个 page 先填满未定义指令 0xe7fddef1，堵住向量表和 kuser helper
     * 之间的缝隙；不填的话 CPU 极端情况下会从缝隙取指执行。 */
    for (i = 0; i < PAGE_SIZE / sizeof(u32); i++)
        ((u32 *)vectors_base)[i] = 0xe7fddef1;
    memcpy((void *)vectors, __vectors_start, __vectors_end - __vectors_start);
    memcpy((void *)vectors + 0x1000, __stubs_start, __stubs_end - __stubs_start);
    kuser_init(vectors_base);
    flush_icache_range(vectors, vectors + PAGE_SIZE * 2);
    modify_domain(DOMAIN_USER, DOMAIN_CLIENT);
}

为什么两个 page？第一个放向量表和 kuser helper（内核提供、用户空间调用的函数），第二个放异常处理的 stub。拷贝一旦发生，就要面对链接地址和运行地址不一致的问题：向量表被拷到 0xffff0000，链接时算的是另一个地址，所以这段代码必须位置无关。b 指令天生位置无关，跳的是相对偏移；但不是所有向量都用 b——软中断那条用的是 W(ldr) pc, __vectors_start + 0x1000，编译成 ldr pc, [pc, #4080]，也是位置无关的，但偏移必须在 4K 内。这就是 stub section 存在的原因：把处理函数放到 4K 能勾到的范围内，再让它跳到远处。中断控制器的初始化原稿只有一句「参考 GIC 代码分析」，本文不展开。

十一、ARM 硬件对中断事件的响应 #

前提是全局中断已开。外设检测到事件，通过 request line 的电平或边沿通知它连着的控制器，控制器在多核里挑一个，通过 IRQ（FIQ 本文不谈）送给该核。ARM 硬件接着干四件事，软件一行都没参与：改 CPSR.M[4:0] 切到 IRQ mode；把中断那一刻的 CPSR 存进 SPSR_irq、把返回地址存进 lr_irq；置 CPSR.I = 1 mask 掉 IRQ；把 PC 设成 IRQ 异常向量地址跳过去。到这里硬件收工，后面全是软件。

第 2 步值得多说。ARM 的通用寄存器 R0~R15 在 9 种 mode 下看到的并不一样，每种 mode 从一整套 banked register 里挑。IRQ mode 下 R0~R12、PC、CPSR 和 usr/svc 是同一份，独有的是 R13（SP）、R14（LR）和 SPSR。CPSR 共用，中断发生在 usr 还是 svc 靠它区分，硬件把它存进 SPSR_irq。PC 也共用，而且马上要被改成向量地址，所以必须保存——存的不是 PC 值本身，而是返回地址：

text
thumb state:  lr_irq = PC
ARM   state:  lr_irq = PC - 4

为什么减 4？ARM 是流水线，执行某条指令时取指已经跑到前面，PC = 正在执行的指令地址 + 8：

text
        -> 发生中断的指令
           发生中断的指令 + 4
   PC  ->  发生中断的指令 + 8
           发生中断的指令 + 12

中断来了，当前指令执行完，已经取指译码的后续指令作废；当前指令执行完后，原本指向「+8」的 PC 会再加 4，所以硬件接手那一刻，PC 实际比「发生中断的指令」超前 12。减 4 之后，lr_irq 里存的是「发生中断的指令 + 8」，正是返回点。为什么硬件不干脆减 8，让软件省掉那个减法？因为 ARM 的异常硬件逻辑不只服务 IRQ，还要服务各种异常，而不同异常期望的返回地址并不统一，硬件只做一份公共的减 4，剩下的差异交给软件各自调整，IRQ 的 correction=4 就是这么来的。

十二、进入 ARM 中断处理的三条路径（用户态 / 内核态 / IRQ 模式） #

1、IRQ mode 里的过路动作：vector_stub #

armasm
    .macro  vector_stub, name, mode, correction=0
    .align  5
vector_\name:
    .if \correction
    sub     lr, lr, #\correction          /* (1) */
    .endif
    stmia   sp, {r0, lr}                   /* (2) 存 r0 和返回地址 */
    mrs     lr, spsr
    str     lr, [sp, #8]                   /* 存 spsr */
    mrs     r0, cpsr                       /* (3) 准备切 SVC，IRQ 仍关 */
    eor     r0, r0, #(\mode ^ SVC_MODE | PSR_ISETSTATE)
    msr     spsr_cxsf, r0
    and     lr, lr, #0x0f                  /* 取 CPSR.M[3:0] */
    mov     r0, sp                         /* 把 irq mode 的 sp 传给下家 */
THUMB( adr   r0, 1f            )
THUMB( ldr   lr, [r0, lr, lsl #2] )
ARM(   ldr   lr, [pc, lr, lsl #2] )       /* 按 mode 取 __irq_usr / __irq_svc */
    movs    pc, lr                         /* (4) 跳进 SVC mode */
ENDPROC(vector_\name)
    .align  2
1:                                         @ 跳转表紧跟在这里
    .endm

(1) 减 4，把 lr 修正成「发生中断的指令 + 4」（对 IRQ 来说 correction=4），保证返回点是中断之后的那条指令。(2) 当前是 IRQ mode，SP_irq 就是那 12 字节，依次压入 r0、PC、CPSR；为什么要存 r0？因为下面马上要用 r0，不存就恢复不了完整现场。(3) 改 SPSR 而不是 CPSR——这一步只是准备，还没真正切换。(4) movs pc, lr 的 s 后缀有个隐含动作：把 SPSR 拷回 CPSR，模式切换在这一刻完成，不是所有异常返回都用栈操作。

2、跳转表：16 个入口，只有 2 个有效 #

armasm
vector_stub  irq, IRQ_MODE, 4
    .long   __irq_usr        @ 0  (USR_26 / USR_32)   <- base + 0
    .long   __irq_invalid    @ 1  (FIQ_26 / FIQ_32)
    .long   __irq_invalid    @ 2  (IRQ_26 / IRQ_32)
    .long   __irq_svc        @ 3  (SVC_26 / SVC_32)   <- base + 12
    .long   __irq_invalid    @ 4                      @ 5~f 同

按 CPSR.M[3:0] 索引，and lr, lr, #0x0f 取出低 4 位，中断在用户空间则 lr=0，在内核空间则 lr=3。表里 16 项全要给，只有 usr 和 svc 两项有效。剩下 14 项指向 __irq_invalid 不是浪费——在别的模式里来了中断，系统能捕获到这个错误，dump 出来就有线索。

CPSR.M[3:0] 模式 入口 说明
0 usr __irq_usr 用户态被中断，最常见
1 fiq __irq_invalid FIQ 模式里来 IRQ，异常
2 irq __irq_invalid IRQ 模式里再来 IRQ
3 svc __irq_svc 内核态被中断
4~0xf abt/und/sys/mon/hyp 等 __irq_invalid 32 位内核不处理

3、路径一：中断发生时在用户空间 #

armasm
    .align  5
__irq_usr:
    usr_entry              /* 保存用户现场到内核栈 */
    kuser_cmpxchg_check    /* 和本文无关 */
    irq_handler            /* 核心处理，见第 6 小节 */
    get_thread_info tsk    /* tsk = r9 */
    mov     why, #0        /* why = r8，非系统调用 */
    b       ret_to_user_from_irq

why 就是 r8，用来传「本次返回用户空间对应哪个系统调用」，中断跟它无关，填 0。保存现场就是把硬件上下文搬上 SVC mode 的栈：

armasm
    .macro  usr_entry
    sub     sp, sp, #S_FRAME_SIZE      /* A */
    stmib   sp, {r1 - r12}             /* B */
    ldmia   r0, {r3 - r5}              /* C */
    add     r0, sp, #S_PC              /* D */
    mov     r6, #-1                    /* orig_r0 = -1 */
    str     r3, [sp]                   /* 存中断那刻的 r0 */
    stmia   r0, {r4 - r6}              /* E */
    stmdb   r0, {sp, lr}^              /* F */
    .endm

A：这时候已经在 SVC mode，sp 是 sp_svc，所以压的是被中断进程的内核栈；S_FRAME_SIZE 是 18 个寄存器——r0~r15 加 CPSR 只有 17 个，多出来一个，答案在最后。B：先压 r1~r12，跳过 r0 是因为它从 irq mode 切过来时被用脏了，原始值躺在 IRQ mode 的栈上；stmib 的 ib 是 increment before，压 r1 时先加 4 给 r0 预留位置，sp 后面没有 !，所以压完 sp 不动。C：r0 还指着 IRQ mode 的栈，所以 r3 是中断那刻的 r0，r4 是 PC，r5 是 CPSR。D：让 r0 指向 S_PC 的位置，struct pt_regs 就是内核栈上这份寄存器快照的布局：

偏移符号 内容 来自
ARM_r0 中断那刻的 r0 IRQ mode 栈（str r3, [sp]）
ARM_r1~ARM_r10 r1~r10 直接压栈
ARM_fp / ARM_ip r11 / r12 直接压栈
ARM_sp / ARM_lr 中断那刻的 sp / lr stmdb r0, {sp, lr}^
ARM_pc 中断那刻的 PC IRQ mode 栈 ← r0 指这儿
ARM_cpsr 中断那刻的 CPSR IRQ mode 栈
ARM_ORIG_r0 原始 r0（这里填 -1） 立即数

为什么给 r0 赋值而不是改 sp？内核要保持 sp 指着栈顶。E：把 r0、PC、CPSR、orig_r0 一次写进内核栈，这几个值来自 IRQ mode 的栈，这一步就是现场搬家。F：还剩 sp 和 lr 没存，db 是 decrement before，往 r0（PC 位置）前面的两个槽写，^ 表示访问 user mode 的寄存器——这里存的是用户态的 sp 和 lr。

4、路径二：中断发生时在内核空间 #

armasm
    .align  5
__irq_svc:
    svc_entry              /* 现场保存到内核栈 */
    irq_handler            /* 具体处理，同 user 路径 */
#ifdef CONFIG_PREEMPT
    get_thread_info tsk
    ldr     r8, [tsk, #TI_PREEMPT]     @ 取 preempt count
    ldr     r0, [tsk, #TI_FLAGS]       @ 取 flags
    teq     r8, #0                     @ preempt count != 0 ?
    movne   r0, #0                     @ 非 0 就强制清 flags
    tst     r0, #_TIF_NEED_RESCHED
    blne    svc_preempt
#endif
    svc_exit r5, irq = 1               @ 异常返回

thread_info 里和这段相关的两个成员：flags（low level flags）和 preempt_count（0 表示可抢占，小于 0 是 bug）。preempt_count != 0 说明现在不能抢占（显式 preempt_disable，或者本来就在中断上下文），非 0 直接把 flags 强制清零，跳过重调度；等于 0 才有资格抢占，还要看 _TIF_NEED_RESCHED——时间片用完，或者中断唤醒了更高优先级的进程，这个位就会被置上。

armasm
    .macro  svc_entry, stack_hole=0
    sub     sp, sp, #(S_FRAME_SIZE + \stack_hole - 4)   /* sp 指向 pt_regs 中 r1 */
    stmia   sp, {r1 - r12}                              /* r1~r12 入栈 */
    ldmia   r0, {r3 - r5}
    add     r7, sp, #S_SP - 4                           /* r7 指向 pt_regs 中 r12 */
    mov     r6, #-1                                     /* orig r0 = -1 */
    add     r2, sp, #(S_FRAME_SIZE + \stack_hole - 4)   /* r2 = 中断那刻的 sp */
    str     r3, [sp, #-4]!                              /* 存 r0，! 让 sp 前移到栈顶 */
    mov     r3, lr                                      /* 存 svc mode 的 lr */
    stmia   r7, {r2 - r6}                               /* 拼出 struct pt_regs */
    .endm

和 usr_entry 思路一样，差别在于这里没有 ^ 修饰——存的是 SVC mode 自己的 sp 和 lr，因为中断就发生在内核态。至此内核栈上有了完整的硬件上下文，完整到有点冗余：多了一个 orig_r0。

ARM_r0 和 ARM_ORIG_r0 都该是中断那刻的 r0，为什么存两份？为什么这里往 ARM_ORIG_r0 塞 -1？答案在系统调用，不在中断。系统调用和中断同属异常处理，区别是系统调用要传参数、要返回结果。ARM 上 r0~r7 各 mode 共享，传参方便，返回值也放 r0；返回时把结果写进 r0，原来通过 r0 传进来的参数就被覆盖了，多数场景无所谓，两个场合不行：ptrace、系统调用重启（signal 相关）。所以 r0 存两份：ARM_r0 是参数（返回时变成返回值），ARM_ORIG_r0 留原始值。回到中断：中断处理不用 ARM_ORIG_r0，但为了防止系统调用重启机制误判，赋值 -1——一个不可能是系统调用号的值。

5、路径三：IRQ mode 只是过路 #

严格说没有第三条路径。IRQ mode 是必经的过路站，三条路的分歧点在跳转表：usr 走 __irq_usr，svc 走 __irq_svc，其余走 __irq_invalid。

6、irq_handler：核心处理，两种配置 #

armasm
    .macro  irq_handler
#ifdef CONFIG_MULTI_IRQ_HANDLER
    ldr     r1, =handle_arch_irq
    mov     r0, sp                  /* 参数：pt_regs */
    adr     lr, BSYM(9997f)         /* 返回地址 */
    ldr     pc, [r1]
#else
    arch_irq_handler_default
#endif
9997:
    .endm

情况一：machine 代码设好 handle_arch_irq，这段汇编只负责传参和设返回地址，然后跳过去，第五章讲的就是这条路的后续。情况二 arch_irq_handler_default 是老 ARM SoC 的路子，代码在减少：

armasm
    .macro  arch_irq_handler_default
    get_irqnr_preamble r6, lr
1:  get_irqnr_and_base r0, r2, r6, lr
    movne   r1, sp
    @ asm_do_IRQ 需要两个参数：r0 = irq number，r1 = struct pt_regs *
    adrne   lr, BSYM(1b)            /* 返回地址指回 1，继续解析 */
    bne     asm_do_IRQ
    .endm

这段已经和 machine 绑死了。get_irqnr_preamble 做准备工作，不需要的平台直接定义成空；get_irqnr_and_base 四个参数：r0 存解析出的 irq number，r2 是状态寄存器值，r6 是控制器基地址，lr 是 scratch。两个平台的取舍：推荐第一种。逻辑上中断处理就该是「读硬件状态 → 转成 IRQ number → 调对应处理函数」；get_irqnr_and_base 这套宏的前提是「SoC 上就一个控制器，硬件状态和 IRQ number 一一对应」，而现实里的 ARM 平台早就级联了、有 irq domain 了，前提不成立。

十三、中断退出过程 #

不管中断发生在什么态，irq_handler 处理完（softirq、tasklet、workqueue 这些下半部另开文档讲），最后都得回现场。出口分两个。

1、返回用户空间 #

armasm
ENTRY(ret_to_user_from_irq)
    ldr     r1, [tsk, #TI_FLAGS]
    tst     r1, #_TIF_WORK_MASK        /* A */
    bne     work_pending
no_work_pending:
    asm_trace_hardirqs_on              /* irq flag trace，略 */
    arch_ret_to_user r1, lr            /* 部分平台返回用户空间前的特殊处理 */
    ct_user_enter save = 0             /* trace context，略 */
    restore_user_regs fast = 0, offset = 0   /* B */
ENDPROC(ret_to_user_from_irq)
ENDPROC(ret_to_user)

A：_TIF_WORK_MASK 是三个位的并集，分别对应要调度、有信号待处理、返回用户空间前要调 callback：

c
#define _TIF_WORK_MASK  (_TIF_NEED_RESCHED | _TIF_SIGPENDING | _TIF_NOTIFY_RESUME)

任意一个置位就进 work_pending，它要三个参数，第三个 why 标识哪个系统调用，这里是 0。B：恢复现场，movs pc, lr 再次承担模式切换，s 后缀让 SPSR 覆盖 CPSR：

armasm
    .macro  restore_user_regs, fast = 0, offset = 0
    ldr     r1, [sp, #\offset + S_PSR]   /* r1 = pt_regs 里的 spsr */
    ldr     lr, [sp, #\offset + S_PC]!   /* lr = PC，sp 前移到 PC 位置 */
    msr     spsr_cxsf, r1                /* 写 spsr，准备返回用户空间 */
    clrex                                /* 清 exclusive monitor */
    .if     \fast
    ldmdb   sp, {r1 - lr}^               /* 取 r1~lr */
    .else
    ldmdb   sp, {r0 - lr}^               /* 取 r0~r14 */
    .endif
    mov     r0, r0                       /* NOP，ARMv5T 之前需要 */
    add     sp, sp, #S_FRAME_SIZE - S_PC /* sp 挪回原位 */
    movs    pc, lr                       /* 返回用户空间 */
    .endm

2、返回内核空间 #

armasm
    .macro  svc_exit, rpsr, irq = 0
    .if     \irq != 0
    @ IRQs already off
    .else
    disable_irq_notrace                  @ 取栈上数据前再关一次中断
    .endif
    msr     spsr_cxsf, \rpsr            /* 中断现场的 CPSR 写回 spsr */
    ldmia   sp, {r0 - pc}^              /* 异常返回：顺带 spsr -> cpsr */
    .endm

ldmia sp, {r0 - pc}^ 是异常返回专用指令，^ 的隐含动作是把 SPSR 拷进 CPSR。这也解释了 __irq_svc 里那句 svc_exit r5, irq = 1 的 r5 是什么——就是 svc_entry 阶段留在 r5 里的中断现场 CPSR。

十四、从 ARM 到 generic irq：两套代码如何衔接 #

前面两条线是分开讲的：第八到九章讲 generic irq 的 C 代码，第十到十三章讲 ARM 汇编。它们的接缝只有一处，一条调用链：

text
irq_handler
  -> handle_arch_irq(regs)              /* 汇编跳到 C，machine 层 */
      -> gic_handle_irq(regs)           /* 读 IAR，拿 hwirq */
          -> irq_find_mapping()         /* hwirq -> IRQ number */
              -> handle_IRQ(irq)        /* ARM 包装层 */
                  -> generic_handle_irq(irq)
                      -> desc->handle_irq(irq, desc)   /* flow handler */
                          -> handle_irq_event(desc)
                              -> action->handler(irq, dev_id)  /* 你的代码 */
层 ARM 侧实体 generic irq 侧实体 交接物
异常入口 vector_irq → __irq_usr/__irq_svc — struct pt_regs *
现场 usr_entry/svc_entry，内核栈 — pt_regs 落在栈上
machine handle_arch_irq — regs
控制器 gic_handle_irq，readl_relaxed(IAR) irq_chip 的 callback hwirq → IRQ number
翻译 irq_find_mapping(gic->domain, irqnr) struct irq_domain unsigned int irq
分发 handle_IRQ generic_handle_irq struct irq_desc *
流控 — desc->handle_irq irq_desc + irq_chip
执行 — action->handler irqaction
收尾 svc_exit / restore_user_regs — 回现场

三个容易混的边界。边界一：ack 在汇编或 C 里。 GIC 的 ack 就是读 IAR，而读 IAR 同时把 hwirq 拿回来了，所以 gic_handle_irq 那一行读既是 ack 又是取 ID，这也解释了 GIC 的 irq_chip 为什么给不出 handle_edge_irq 要的那个 irq_ack——时机已经过去了。边界二：EOI 在谁手里。 中断源是 IPI（ID < 16）时，gic_handle_irq 自己写 EOI 再调 handle_IPI，根本不进 generic irq；普通外设中断走 flow handler，EOI 时机由 handler 类型决定——fasteoi 在 handler 之后，level 在 flow handler 内部。边界三：pt_regs 只往上递一层。 汇编辛苦搭出来的 pt_regs 到了 generic_handle_irq 就不带了，因为 flow handler 的签名是 (irq, desc)；regs 只给 machine 层用（GIC 那边需要它来识别被打断的是用户态还是内核态，某些场景还要改返回地址），你的 handler(irq, dev_id) 拿不到 pt_regs，想要就得走 get_irq_regs()。

CONFIG_MULTI_IRQ_HANDLER 这条配置把接缝挪到了运行期：编译期不知道跳哪，启动时由 machine 或控制器驱动填 handle_arch_irq；没配就是编译期定死走 arch_irq_handler_default 那套宏。

十六、易错点速查 #

按踩坑频率排，每条给出症状和定位方法。

# 坑 症状 怎么定位
1 handler 永远返回 IRQ_HANDLED（哪怕不是自己的中断） 共享中断上别的设备饿死；nobody cared 不出现但功能坏 查返回值是否真的判断了设备状态
2 共享中断返回 IRQ_NONE 却没检查 dev_id 别人的中断你也去读寄存器，读坏外设状态 dev_id 判空必须在最前面
3 电平中断配成 edge handler 中断风暴，或者偶发丢中断 看 flow handler 类型和控制器实际行为是否匹配
4 在 handler 里睡眠 BUG: scheduling while atomic 要睡就拆 thread_fn
5 用了线程化却漏了 IRQF_ONESHOT 中断嵌套，thread 被反复唤醒 threaded irq 一定带 oneshot（除特殊场景）
6 free_irq 前没关设备侧中断 free_irq 卡住，或 handler 访问已释放内存 free_irq 会等执行中的 handler 退出
7 IRQ 号硬编码 换平台就错位 用设备树或 platform_get_irq
8 以为 hwirq == IRQ number 级联平台上取错描述符 打印 irq_data.hwirq 和 irq 对比
9 disable_irq 在中断上下文调用 死锁（它要等 handler 退出） 中断里用 disable_irq_nosync
10 32 位 ARM 内核栈溢出 thread_info 内容错乱、莫名 crash 看栈底 thread_info 是否被写坏
11 spurious 计数误判成硬件故障 好中断被 disable，系统功能缺失 看是否有短时高频 unhandled，查 last_unhandled 时间窗
12 改动 flow handler 里 PENDING / INPROGRESS 的顺序 偶发丢中断，极难复现 别改，那是内核的时序契约
13 中断里调 msleep / mutex_lock 同第 4 条 换 spinlock 或挪到下半部
14 request_irq 的 dev_id 不唯一 共享中断 free_irq 释放错对象 dev_id 用设备结构体地址
15 高向量表被当成普通内存改写 中断进去就崩 向量表 page 只读，别映射成可写

最后一条工程建议：调中断问题，先用 cat /proc/interrupts 看计数走不走、哪个 CPU 在涨；再看 /proc/irq/<n>/ 下的 smp_affinity；还不行开 CONFIG_DEBUG_SHIRQ 或抓 spurious 日志。别一上来就翻汇编。
