这篇只讲一件事：一个地址从 CPU 指令里出来，到最终落到 DRAM 上某个字节，中间被谁改写了几次。范围是 x86 的段式与页式转换、i386 与 ARM64 的地址空间划分、VMA 怎么描述和查找、execve 到 load_elf_binary 的映射怎么建立、缺页的现场与处理路径，以及 32 位内核的 high memory 与 ioremap。

不讲的东西：伙伴系统与 slub 的内部分配算法、页回收与 swap、内核页表初始化和 KASLR、以及 mmap 在 ARM64 上的具体坑。这些拆到别处了：

  • 页表建立过程与 TLB 刷新 → ARM64 内存初始化：页表、memblock 与 KASLR
  • 页帧、zone、node 与内存模型 → 物理内存管理：页、zone 与内存模型
  • mmap 的行为陷阱与 TLB 一致性 → 页表、TLB 与 mmap 的坑
  • fork/exec 在进程生命周期里的位置 → 进程基础：标识、凭证与创建
  • 切进程时 CR3 与 TLB 的代价 → 进程切换：上下文、TLB 与切换开销

结构体字段与函数名以 5.x 为主线。6.1 之后有改动的地方（VMA 双轨制、mmap_sem 改名）都单独标了版本，别拿老代码对新内核。

一、三种地址：逻辑、线性、物理 #

先把名词钉死。这三个词在中文资料里被混用得最严重，混完之后所有讨论都会跑偏。

名称 别称 是谁产生的 在 x86 上怎么变成下一级 谁看得见
逻辑地址 段内偏移 编译器、链接器写进指令 段基址 + 偏移 = 线性地址 反汇编里只有它
线性地址 虚拟地址 段式转换的结果 多级页表 + CR3 = 物理地址 你 C 代码里所有指针的值
物理地址 — 页表翻译的结果 直接上内存总线 DMA 描述符里要填的、ioremap 的入参

一句话记住：在 Linux 上逻辑地址等于线性地址，因为所有段的基址都是 0。这一点决定了后面所有讨论的重心都在分页，而不在分段。

拿一个具体的东西看。写个 hello world 用 GCC 编出来，反汇编第一条取全局变量的指令长这样：

armasm
mov 0x80495b0, %eax

0x80495b0 在 CPU 眼里不是物理地址，它只是数据段内的偏移量。CPU 要拿 DS 的段基址加上它，才得到线性地址。这就是「逻辑地址」这个词的全部含义：一个相对于某个段的偏移。

二、x86 的段式转换与 Linux 为什么绕开它 #

x86 保护模式下，段不是一个寄存器能装下的东西。段的信息存在段描述符里：段基址、段界限、权限位，一个占 8 字节。段寄存器只有 2 字节，装不下描述符，所以它装的是索引：高 13 位是描述符在表里的下标，第 2 位（TI）选 GDT 还是 LDT，低 2 位是 RPL 请求特权级。

Intel 这么设计是为了兼容 8086 的段式寻址，代价是地址转换多了一级间接。Linux 的应对方式很干脆：把段基址全部设成 0，把段界限全部设成 4GB，于是段式转换退化成一个恒等映射。

段 基址 界限 效果
用户代码段 / 数据段 0x00000000 4GB 逻辑地址 = 线性地址
内核代码段 / 数据段 0x00000000 4GB 逻辑地址 = 线性地址

结果就是：Linux 只用 GDT，不用 LDT；用户任务和内核任务各有一套描述符，靠 DPL（描述符特权级）区分——内核段 DPL=0，用户段 DPL=3，用户态代码想跳到内核段，硬件直接拦下来。

GDB 里 info reg 能看到这几个寄存器的实际值：

armasm
cs 0x73 115
ss 0x7b 123
ds 0x7b 123
es 0x7b 123

ds = 0x7b 拆成二进制是 0000 0000 0111 1011：

  • bit 2（TI）= 0，走 GDT，不走 LDT
  • bit 15~3 = 01111，十进制 15，即 GDT 第 15 项
  • bit 1~0 = 11，RPL = 3，用户态

所以这条输出说明当前是用户态、数据走 GDT 第 15 项描述符。至于第 15 项到底是 __USER_DS 还是别的，取决于 GDT 布局。原文的说法是第 12~15 项依次为 __KERNEL_CS、__KERNEL_DS、__USER_CS、__USER_DS，这样 0x7b 正好落在 __USER_DS。但按当前内核 arch/x86/include/asm/segment.h 的 GDT_ENTRY_* 枚举（__USER_CS 由 GDT_ENTRY_DEFAULT_USER_CS*8+3 算出，__USER_DS 由 GDT_ENTRY_DEFAULT_USER_DS*8+3 算出），算出来的选择子是 0x33 和 0x2b，跟 0x73/0x7b 对不上。这一处未验证，位段的读法没问题，具体项号我不下断言。

结论不变：Linux 在 x86 上跑，但把分段机制架空了，内存管理的全部复杂度都压给了分页。这也是为什么后面讲地址翻译，几乎只讲页表。

三、页式转换与多级页表 #

分页的总开关在 CR0 的最高位 PG。PG=1 走页表，PG=0 线性地址直接当物理地址用（内核早期启动阶段就这么干）。

32 位 x86 用二级页表。一个线性地址被硬件切成三段：

text
 31              22 21              12 11                    0
+------------------+------------------+-----------------------+
|  页目录索引 10 位 |  页表索引 10 位   |   页内偏移 12 位       |
+--------+---------+--------+---------+-----------+-----------+
         |                  |                     |
         v                  |                     |
   CR3 寄存器               |                     |
         |                  v                     |
         |          +---------------+             |
         +--------> |   页目录表     |             |
                    | 4KB / 1024 项  |             |
                    +-------+-------+             |
                            |                     |
                            v                     |
                    +---------------+             |
                    |    页表        |             |
                    | 4KB / 1024 项  |             |
                    +-------+-------+             |
                            |                     |
                            v                     v
                    +---------------------------------+
                    |   物理页帧 4KB                   |
                    +---------------------------------+

三级下去的流程：

  1. CR3 存当前进程页目录表的物理基址（这里存的一定是物理地址，否则自己翻译自己就递归了）。
  2. 用线性地址最高 10 位做下标，在页目录表里取出页表的物理基址。
  3. 用中间 10 位做下标，在页表里取出物理页帧的首地址。
  4. 首地址 + 最低 12 位偏移，落到内存条上的具体字节。

拿前面那个 0x80495b0 走一遍。它在 Linux 上逻辑地址等于线性地址，所以直接当线性地址用。转成二进制：

text
0000 1000 0000 0100 1001 0101 1011 0000
  • 最高 10 位 0000 1000 00 = 32 → 页目录表第 32 项
  • 中间 10 位 00 0100 1001 = 73 → 页表第 73 项
  • 最低 12 位 0101 1011 0000 = 0x5b0 → 页内偏移

页目录表 4KB、1024 项、每项 4 字节；页表同样 4KB、1024 项、每项 4 字节。1024 × 4KB = 4MB，正好覆盖 32 位地址空间。

现在把两套体系分开讲，这一步不能省，混在一起讲的资料全是在糊人。

项目 i386（32 位 x86） ARM64
虚拟地址宽度 32 位（4GB 线性空间） 39 / 48 / 52 位可选
页表级数 2 级（开 PAE 变 3 级） 3 / 4 / 5 级
顶级表寄存器 CR3（物理地址） TTBR0_EL1（用户）、TTBR1_EL1（内核）
每级位宽 10 + 10 + 12 9 + 9 + … + 12
单个页表大小 4KB / 1024 项 4KB / 512 项
用户与内核 同一套页表，靠地址高低区分 两套页表基址寄存器，硬件分家

ARM64 常见的 4 级配置（CONFIG_ARM64_VA_BITS=48，4KB 页）位宽是 9 + 9 + 9 + 9 + 12 = 48，对应 PGD → PUD → PMD → PTE。VA_BITS=39 时折成 3 级。52 位要开 LVA 相关配置，顶级位宽随实现变化，这一项未逐项核对。

x86-64 侧是 9 + 9 + 9 + 9 + 12 = 48：PML4 → PDPT → PD → PT；开 LA57 后顶级再加 9 位变成 57 位虚拟地址。

所以「3G/1G」和「几级页表」是两个正交的问题：前者是地址空间怎么分，后者是地址怎么翻译。i386 是 3G/1G 配 2 级页表；ARM64 没有 3G/1G 这回事，它按 VA_BITS 切上下半区。

四、PTE 的标志位 #

页表项不只是个物理地址，低 12 位塞满了硬件要用的控制位。MMU 一边翻译一边做权限检查，越权就在翻译这一步失败，不用内核插手。

位 名称 含义 硬件行为
0 P（Present） 页是否在物理内存里 为 0 触发缺页异常
1 R/W 0 只读，1 可读写 写只读页触发保护异常
2 U/S 0 仅内核，1 用户可访问 用户态访问内核页触发保护异常
3 PWT 页级写透缓存 影响 cache 策略
4 PCD 页级禁用缓存 影响 cache 策略
5 A（Accessed） 被读过或被写过 硬件自动置 1，供 LRU 参考
6 D（Dirty） 被写过 硬件自动置 1，回写判据
7 PAT 页属性表索引 配合 PCD/PWT 选 cache 类型
8 G（Global） 全局页 进程切换刷 TLB 时不清这条
63 NX 禁止取指 在 NX 页上取指直接异常

D 位和 A 位是硬件帮你记的账。内核回收页面时不用自己维护「这页脏没脏」，读 PTE 就行——这是把记账工作推给 MMU 的典型做法。

G 位跟内核映射关系密切：内核空间那部分映射每个进程都一样，切进程时没必要刷，置上 G 位就能留下。TLB 刷新的取舍在 页表、TLB 与 mmap 的坑 里细讲。

五、进程地址空间长什么样：3G/1G 与 64 位布局 #

32 位系统的天花板是 2^32 = 4GB。这 4GB 不能全给应用，得留一块给内核，于是有了经典的三七开。

区域 范围 大小 装什么
用户空间 0x00000000 ~ 0xBFFFFFFF 3GB 代码、数据、堆、栈、共享库、mmap 区
内核空间 0xC0000000 ~ 0xFFFFFFFF 1GB 内核代码数据、直接映射区、vmalloc、页表、驱动

用户态那 3GB 内部的排布，从低到高：

text
低地址
+---------------------------+
|  .text      代码段         | 只读、可执行、可共享
+---------------------------+
|  .data      已初始化数据    | 全局变量、静态变量里带初值的
+---------------------------+
|  .bss       未初始化数据    | 启动前清零，不占文件空间
+---------------------------+
|  heap       堆             | malloc 来的，向高地址长
|            ↓ 增长          |
+---------------------------+
|                           |
|   mmap 区 / 共享库映射      | 动态库、文件映射、大块 malloc
|                           |
+---------------------------+
|  stack      栈             | 局部变量、调用帧，向低地址长
|            ↑ 增长          |
+---------------------------+
高地址（0xBFFFFFFF）

堆往上长、栈往下长，中间留一大片空洞给 mmap 用，两边谁先撞上谁死。动态库被 mmap 到中间那片区域，位置由内核选，这跟 PIE 有关。

64 位下这套数字全部作废：

项目 i386 x86-64 ARM64（VA_BITS=48）
用户空间上限 0xBFFFFFFF（3GB） 0x00007FFF_FFFFFFFF 0x0000_FFFF_FFFF_FFFF
内核空间起点 0xC0000000 0xFFFF8000_00000000 0xFFFF_0000_0000_0000
划分方式 定死 3:1 中间留巨大 hole 高半区 / 低半区
是否要 high memory 要 不要 不要

64 位之所以不要 high memory，是因为虚拟地址空间大到用不完，内核可以直接把所有物理内存线性映射进来，不需要「临时借地址」这套机制。

注意 ARM64 那两行的具体值跟 CONFIG_ARM64_VA_BITS 走，TASK_SIZE 是编译期常量。上面按 48 位 VA 给，实际跑之前先 cat /proc/self/maps 看一眼顶部地址。

/proc/<pid>/maps 就是这张图的运行时版本：

text
00400000-00452000 r-xp 00000000 08:01 123456   /usr/bin/app
00651000-00652000 r--p 00051000 08:01 123456   /usr/bin/app
00652000-00655000 rw-p 00052000 08:01 123456   /usr/bin/app
01aa2000-01ec3000 rw-p 00000000 00:00 0        [heap]
7ffdd9221000-7ffdd9242000 rw-p 00000000 00:00 0 [stack]

每行一个 VMA。权限那四位是 rwxp，最后一位 p 是 private、s 是 shared。这里的地址全是虚拟地址，跟物理内存没有对应关系——想看实际落到物理页的部分，去 smaps 找 RSS。

六、mm_struct：一个进程的内存总账 #

内核不靠页表去猜「这段是代码还是数据」。页表只认页，不认语义。要描述语义，得有一层数据结构，这就是 mm_struct。

每个 task_struct 持有一个 struct mm_struct *mm。线程组内所有线程共享同一个 mm_struct，这也是线程和进程在内核里的实质区别之一。

c
struct mm_struct {
    struct vm_area_struct *mmap;        /* VMA 链表头，按地址递增排序（6.1 前） */
    struct rb_root mm_rb;               /* VMA 红黑树根（6.1 前） */
    int map_count;                      /* VMA 总数 */

    unsigned long start_code, end_code; /* 代码段起止虚拟地址 */
    unsigned long start_data, end_data; /* 数据段起止虚拟地址 */
    unsigned long start_brk, brk;       /* 堆起点与当前堆顶 */
    unsigned long start_stack;          /* 栈起始虚拟地址 */
    unsigned long arg_start, arg_end;   /* 命令行参数字符串区 */
    unsigned long env_start, env_end;   /* 环境变量字符串区 */

    pgd_t *pgd;                         /* 指向该进程页全局目录（物理地址） */

    atomic_t mm_users;                  /* 共享该 mm 的线程数 */
    atomic_t mm_count;                  /* 主引用计数 */
    struct rw_semaphore mmap_lock;      /* 保护 VMA 拓扑的读写锁 */
    struct file *exe_file;              /* 正在执行的可执行文件 */
    unsigned long total_vm;             /* 已映射的页数，VmSize 的来源 */
};

字段里有两组容易搞混的：mm_users 和 mm_count。

  • mm_users 数的是线程。clone 时带 CLONE_VM，这个值加一。
  • mm_count 数的是mm 结构本身的引用。active_mm 借出去一次也加一。

mm_users 归零时，VMA 和页表要拆；mm_count 才归零时，mm_struct 这个壳子才释放。这个拆分是为了让内核线程能临时「借用」上一个进程的 mm（挂在 active_mm 上），只占壳子不占实质内容。

关于 pgd：mm->pgd 存的是页全局目录的内核虚拟地址，直接写进 CR3 之前要做一次 __pa()。ARM64 上更麻烦，TTBR0_EL1 里还要塞 ASID。

6.1 起 mmap 和 mm_rb 两个字段被一个 struct maple_tree mm_mt 取代了，map_count 也没了（改成节点计数）。老代码里的 mm->mmap 在新内核上编译不过，别照抄。

七、vm_area_struct：VMA 的字段与含义 #

mm_struct 管总账，vm_area_struct 管一笔：一段连续的、属性一致的虚拟地址区间。

c
struct vm_area_struct {
    unsigned long vm_start;              /* 区间起始地址，包含 */
    unsigned long vm_end;                /* 区间结束地址，不包含 */
    struct mm_struct *vm_mm;             /* 所属的 mm */

    pgprot_t vm_page_prot;               /* 页表项的权限模板 */
    unsigned long vm_flags;              /* VMA 级标志，决定能不能写、能不能执行 */

    struct rb_node vm_rb;                /* 红黑树节点 */
    struct vm_area_struct *vm_next;      /* 链表后继（6.1 前） */
    struct list_head vm_prev;            /* 链表前驱 */

    const struct vm_operations_struct *vm_ops; /* fault / open / close 等回调 */
    struct file *vm_file;                /* 文件映射时的 file 对象 */
    unsigned long vm_pgoff;              /* 文件内偏移，以页为单位 */
    void *vm_private_data;               /* 驱动私货 */
};

vm_start 包含、vm_end 不包含，半开区间 [start, end)。判断一个地址属于哪个 VMA 时，条件是 vm_start <= addr < vm_end，写测试的时候别把等号写错。

vm_page_prot 和 vm_flags 是两个层次：

  • vm_page_prot 是给页表用的权限模板，建 PTE 时把它拷进去。它是 pgprot 编码，硬件认。
  • vm_flags 是给内核用的语义标志，表示「这段允许写」「这段可以往下长」。软件认。

常用的 vm_flags：

标志 含义
VM_READ / VM_WRITE / VM_EXEC 当前映射允许读 / 写 / 取指
VM_SHARED 共享映射，改动对其他进程可见
VM_MAYREAD / VM_MAYWRITE / VM_MAYEXEC 允许通过 mprotect 升到对应权限
VM_GROWSDOWN 可以向下增长，栈和旧式 brk 区用
VM_GROWSUP 可以向上增长，少见，部分架构的栈
VM_IO 映射的是设备 I/O 空间
VM_PFNMAP 直接映射 PFN，页表项指向裸页帧，不走 struct page
VM_DONTEXPAND 禁止 mremap 扩展
VM_LOCKED 已锁页，不允许换出
VM_ACCOUNT 计入 overcommit 记账
VM_DONTCOPY fork 时不要复制这段

MAY* 这一组跟 mprotect 直接相关：想把一段只读区改成可写，光把 vm_page_prot 改了不够，VM_MAYWRITE 没置位的话 mprotect 直接返回 -EACCES。

vm_ops 是文件映射的灵魂。文件映射的页第一次访问时，内核不知道怎么填内容，就回调 vm_ops->fault，让文件系统自己去磁盘把页读进来。匿名映射没有 vm_file，走另一条路。

具体位值在 include/linux/mm.h 里，跨版本会动，这里不列十六进制值。

八、VMA 的双轨制：链表与红黑树 #

一个进程几百个 VMA 是常事，JVM 或大型服务跑到几万个也不稀奇。这么多 VMA 只有一套索引结构的话，两种操作必有一种很慢：

  • 顺序遍历全部 VMA：进程退出、fork 复制、/proc/maps 输出，都要走一遍全部的。
  • 按地址查某个 VMA：每次缺页都要做一次。

链表适合前者，红黑树适合后者。6.1 之前内核干脆两个都维护。

text
                  mm_struct
        +-----------------------------+
        |  mmap（链表头）  mm_rb（根） |
        +------+---------------+------+
               |               |
               v               v
        VMA 1 (vm_start 最小)   VMA 2  （红黑树按 vm_start 排序）
        +----------+            /    \
        | vm_next -+--->  VMA 2  VMA 1  VMA 3
        +----------+      /   \        \
                          VMA 0 VMA 3   VMA 4
结构 关键字段 遍历复杂度 查找复杂度 什么时候用
单向链表 mm->mmap + vm_next O(n) 顺序，缓存友好 O(n) 全量遍历
红黑树 mm->mm_rb + vm_rb O(n) 中序，跳转多 O(log n) 按地址定位

插入新 VMA 时要同时进两条轨道：vma_link() 负责把节点挂进链表和红黑树，两边的顺序必须一致，否则查出来和遍历出来的是两套东西。

按地址查找的入口是 find_vma(mm, addr)。注意它的语义：返回第一个满足 vm_end > addr 的 VMA，这个 VMA 的 vm_start 不一定小于等于 addr。所以调用方拿到结果后必须自己再判一次：

c
vma = find_vma(mm, address);
if (!vma)
    return -EFAULT;                 /* 地址在所有 VMA 之上 */
if (vma->vm_start > address)
    /* 落在两个 VMA 之间的空洞里 */;

这个「返回的 VMA 未必包含目标地址」的行为，是写内核代码时最常踩的坑之一。6.1 加了 vma_lookup(mm, addr)，严格返回包含 addr 的 VMA，找不到就返回 NULL，语义更干净。

6.1 之后这套双轨制整个换成了 maple tree（mm->mm_mt）。maple tree 是有序的 B 树变体，一个结构同时支持范围查找和顺序遍历，不用维护两份。find_vma() 作为兼容包装还留着，但 vm_next 和 vm_rb 已经没了。

九、VMA 的合并与分裂 #

VMA 不是建好就不动的。mmap、munmap、mprotect、mremap 每一次都可能改动邻接关系，内核得维护「相邻且属性相同就该合并」这个不变量，否则 VMA 数量会无限膨胀。

合并：新建或修改一段区域后，检查前后邻居。三者属性完全一致（vm_flags 相同、vm_page_prot 相同、文件映射时 vm_file 相同且 vm_pgoff 首尾相接），就调 vma_merge() 合成一个。

判断条件里最容易被忽略的是 vm_pgoff：两个 VMA 哪怕都映射同一个文件、权限也一样，如果文件偏移不连续，也不能合并——合了之后 vm_pgoff 就没法同时描述两段。

分裂：munmap 挖掉中间一截，或者 mprotect 只改中间一段的权限，一个 VMA 就得断开成两段或三段。

text
分裂前：
   [========== VMA A ==========]
   0x1000                    0x9000

munmap(0x4000, 0x1000) 之后：
   [== A ==]  [空洞]  [== A' ==]
   0x1000   0x4000   0x5000   0x9000

split_vma(mm, vma, addr, new_below) 每次只切一刀，所以「挖中间」要做两次：先在挖掉的起点切一刀，再把后半段在终点切一刀，中间那段才独立出来交给 unmap_region 拆页表。

分裂还牵扯到 anon_vma：匿名页的反向映射挂在 anon_vma 上，分裂时必须把 anon_vma 的引用分给两半，否则反向映射会漏掉一半地址。这块逻辑在 物理内存管理：页、zone 与内存模型 和反向映射相关的文章里。

VMA 数量有硬上限：/proc/sys/vm/max_map_count，默认 65530。到顶之后 mmap 返回 ENOMEM。有些内存分配器（比如老版本 glibc 的 arena 策略）会疯狂 mmap 小块，就是这个值先被打满。

十、execve 到 load_elf_binary #

用户在 shell 里敲一条命令回车，内核里走的是 execve。调用链大致这样：

text
sys_execve                      系统调用入口
 └─ do_execve                   收文件名、argv、envp
     └─ do_execveat_common
         └─ alloc_bprm          造 struct linux_binprm
             └─ exec_binprm
                 └─ search_binary_handler    遍历注册的二进制格式处理器
                     └─ load_elf_binary       fs/binfmt_elf.c，ELF 专用

search_binary_handler 这一步很关键：Linux 支持 ELF、脚本（binfmt_script）、binfmt_misc 等多种格式，内核不假设你 exec 的一定是 ELF。它挨个问注册过的 handler「你能不能处理这个文件」，第一个说能的就是它。

ELF 的 handler 里，load_elf_binary 干的事按顺序是（以 3.18 为基准，后续版本细节有出入）：

  1. 基本检查：e_phentsize 必须等于 sizeof(struct elf_phdr)，e_phnum 在合理范围。
  2. 遍历 program header，遇到 PT_INTERP 就 open_exec 把解释器打开，换掉 bprm->buf。
  3. 根据 PT_GNU_STACK 的 flag 决定栈要不要可执行。
  4. flush_old_exec() 拆掉旧的可执行文件状态。
  5. setup_new_exec() 设置新程序在内核里的状态。
  6. setup_arg_pages() 在栈上铺好 argv/envp 的内存页。
  7. 遍历 PT_LOAD，逐个 elf_map() 映射进地址空间，处理 BSS。
  8. 有解释器就把入口设成解释器的入口，没有就用 ELF 自己的 e_entry。
  9. install_exec_creds() 装权限（setuid 程序在这一步变身份）。
  10. create_elf_tables() 把 auxiliary vector 之类的东西压进栈。
  11. 收拾 current->mm 里的各个字段。

最后 start_thread(regs, elf_entry, bprm->p) 改掉保存的寄存器现场，sysret/iret 回用户态时 rip 就是 elf_entry。

注意第 8 步的分叉，这是理解动态链接的钥匙：

  • 静态链接程序 → elf_entry = 程序自己的 e_entry → 回用户态直接跑 _start。
  • 动态链接程序 → elf_entry = 解释器的入口 → 回用户态跑的是 ld.so，你的程序还没开始执行。

为什么不在内核里做动态链接？因为这会往内核里塞一个 ELF 解析器和符号解析器，内核体积和攻击面都涨，出问题还得换内核才能修。内核里对 ELF 的支持刻意做得很窄——只读它需要的几个字段，别的一概不认。

十一、ELF program header：内核只关心三个段 #

ELF 有两套表：Section Header Table 和 Program Header Table。内核只看 Program Header，Section 是给链接器和调试器看的。这个区别决定了很多事，包括 strip 之后程序照样能跑。

Elf64_Phdr 的定义：

c
typedef struct elf64_phdr {
    Elf64_Word  p_type;    /* 段类型，PT_LOAD / PT_INTERP / ... */
    Elf64_Word  p_flags;   /* 权限：PF_R / PF_W / PF_X 的组合 */
    Elf64_Off   p_offset;  /* 在文件内的偏移 */
    Elf64_Addr  p_vaddr;   /* 加载后的虚拟地址 */
    Elf64_Addr  p_paddr;   /* 物理地址，有 MMU 的 Linux 上等于 p_vaddr */
    Elf64_Xword p_filesz;  /* 在文件里占多少字节 */
    Elf64_Xword p_memsz;   /* 在内存里占多少字节 */
    Elf64_Xword p_align;   /* 对齐要求 */
} Elf64_Phdr;

内核实际处理的三类：

p_type 用途 内核动作 对应的 section
PT_LOAD 需要映射进内存的段 elf_map() 建 VMA，处理 BSS .text / .data / .bss 所在的那几段
PT_INTERP 动态链接器路径字符串 open_exec() 打开，记下路径 .interp
PT_GNU_STACK 栈属性（只有一个 p_flags 有意义） 决定栈是否可执行 无

PT_GNU_STACK 很特殊，它不占任何文件内容，p_filesz 和 p_memsz 都是 0，唯一有用的是 p_flags 里的 PF_X。有 PF_X 就调 elf_read_implies_exec()，把栈 VMA 加上可执行权限；没有就按 NX 处理。现代工具链默认不加，所以栈不可执行。老程序或者 -z execstack 编出来的东西才会有。

PT_DYNAMIC（.dynamic）内核不处理，它留给解释器。这一点在第十三节展开。

p_paddr 在裸机和 bootloader 场景下有意义，在有 MMU 的 Linux 上等于 p_vaddr，内核直接忽略它。

十二、PT_LOAD 的映射过程与 BSS #

每个 PT_LOAD 都对应一段 VMA。映射路径是：

text
load_elf_binary
 └─ elf_map
     └─ vm_mmap
         └─ do_mmap
             └─ mmap_region
                 ├─ vma = vm_area_alloc(mm)    从 slab 拿一个 vm_area_struct
                 ├─ vma->vm_start / vm_end     按 p_vaddr 和 p_memsz 算
                 ├─ vma->vm_page_prot          按 p_flags 转 pgprot
                 ├─ vma->vm_flags              加上 VM_READ/VM_WRITE/VM_EXEC
                 └─ vma_link(mm, vma, prev, rb_link, rb_parent)

vm_area_struct 本身只有两百来字节，从 slab 的 vm_area_struct 缓存里拿，不会为它专门去伙伴系统要整页。

三个 PT_LOAD 的典型划分（同一份可执行文件）：

段 p_flags 转出的 vm_flags 映射内容
代码段 `PF_R PF_X` `VM_READ
数据段 `PF_R PF_W` `VM_READ
只读数据段 PF_R VM_READ .eh_frame_hdr 之类

一个 PT_LOAD 可以包含多个 section，readelf -l 末尾的 Section to Segment mapping 就是这张对照表。文件到内存的映射关系一旦建立，访问就是懒的——mmap 只登记 VMA，物理页到第一次访问才分配。

BSS 是这里唯一需要额外动作的地方。BSS 在文件里不占空间（全零没必要存），但在内存里要占。表现为：

情况 p_filesz vs p_memsz 内核怎么处理
纯代码 / 已初始化数据 相等 直接按 p_filesz 映射文件页
段尾带 BSS p_memsz > p_filesz 先按 p_filesz 映射，尾部补零
尾部跨页 补齐量不足一页 padzero() 把最后一页的剩余字节清零

跨页那部分处理完还剩的，就是「整页的零」。这部分不能靠文件映射，得单独建匿名映射。load_elf_binary 里记了两个位置：elf_bss（文件数据结束处）和 elf_brk（BSS 结束处），差值就是需要 set_brk() 补的匿名页数量。

c
/* 流程示意，非逐行原文 */
if (elf_bss != elf_brk) {
    /* BSS 剩余部分建匿名私有映射，内容按需清零 */
    set_brk(elf_bss, elf_brk, 0);
}

set_brk 底层走的还是 mmap，映射出来的页带 VM_WRITE 且没有 vm_file，第一次写的时候由 do_anonymous_page() 分配物理页并清零。所以 BSS 的「自动清零」不是启动时一次性 memset 一整块，是缺页时一页一页清——省内存，代价是首次访问有缺页开销。

还有个容易忽略的：elf_map 之后要检查返回值是否等于期望的地址，不等就报错退出。内核不允许映射落到别的位置，因为 ELF 里的绝对地址引用是按 p_vaddr 算的。

ET_DYN（PIE）的地址是相对的，load_bias 记下实际加载基址，elf_map 传入的地址要加上这个偏移。ET_EXEC 的 load_bias 恒为 0。

十三、PT_INTERP 与动态链接器的接管 #

PT_INTERP 段的全部内容就是一个以 \0 结尾的路径字符串，比如：

text
/lib64/ld-linux-x86-64.so.2

内核拿到这个字符串只做三件事：open_exec() 打开它、校验它自己也是个合法 ELF、把它的入口地址加到 load_bias 上算成 elf_entry。至于这个文件里的代码要干什么，内核完全不管。

回用户态之后，跑的是 ld.so。以 glibc 2.27 为例，它依次做：

  1. 把真正的目标程序的内存段加载进当前进程（内核已经建好的 VMA 之外，它自己再 mmap 一次）。
  2. 按 DT_NEEDED 把依赖的动态库映射进来。
  3. 做重定位（relocation）。
  4. 调动态库的初始化函数（.preinit_array、.init、.init_array）。
  5. 把控制流交给目标程序的入口，让它以为自己是被内核直接启动的。

第 1 步值得停一下：动态链接的程序其实被映射了两次——第一次是内核按 PT_LOAD 建的，第二次是 ld.so 自己再建的。这也是为什么 /proc/pid/maps 里同一个文件会出现好几行。

驱动这一切的数据在 PT_DYNAMIC 段里，元素结构：

c
typedef struct {
    Elf64_Sxword d_tag;    /* 条目类型 */
    union {
        Elf64_Xword d_val; /* 整数值 */
        Elf64_Addr  d_ptr; /* 地址值 */
    } d_un;
} Elf64_Dyn;

d_tag 决定 d_un 怎么解释，常见几项：

d_tag 含义 用哪个字段
DT_NULL 动态数组结束 无
DT_NEEDED 依赖的库名 d_val，指向字符串表的偏移
DT_STRTAB 字符串表地址 d_ptr
DT_STRSZ 字符串表大小 d_val
DT_SYMTAB 符号表地址 d_ptr
DT_INIT / DT_FINI 初始化 / 收尾函数地址 d_ptr
DT_RPATH / DT_RUNPATH 库搜索路径 d_val
DT_SONAME 本库的逻辑名 d_val

这些东西在 section 视图里对应 .dynamic，两者指向文件里的同一块数据——readelf -d 和 readelf -x .dynamic 出来的内容能对上。自己解析动态段的时候别以为要读两遍。

符号查找用广度优先：先查主程序的符号表，再查它的 DT_NEEDED 列出的库，再查那些库的 DT_NEEDED。这也解释了同名符号为什么会被主程序「覆盖」——它先被搜到。

重定位之所以必要，是因为共享库是位置无关的，加载地址由 ld.so 随机选。程序里对某个符号的引用必须改成真实地址。R_X86_64_GLOB_DAT、R_X86_64_JUMP_SLOT、R_X86_64_RELATIVE 这些类型就是干这个的，改的位置分别是 .got 和 .got.plt。改成共享库直接依赖 vm_ops->fault 读文件，这部分在 页表、TLB 与 mmap 的坑 里。

至于拿 PT_INTERP 去做别的事——比如在没有执行权限的分区上跑代码、或者替换解释器路径让内核把控制权交出去——那是攻防话题，跟本文的地址翻译不是一条线，已移出到安全目录，这里不写。

十四、缺页异常是怎么发生的 #

虚拟内存的核心骗局：mmap 只登记 VMA，不分配物理页。所以 VMA 建好了，页表项还是空的。第一次访问时硬件发现 PTE 的 P 位是 0，当场触发异常。

这条指令本身没有错，错的是「还没给它物理页」。所以异常处理完之后，CPU 要重新执行刚才那条指令——不是执行下一条，是同一条。这就是缺页处理和普通信号处理的区别：出错指令的现场必须完整保留。

x86 的缺页异常进 #PF，硬件做两件事：把出错地址塞进 CR2，把错误类型编码进栈上的 error code。

位 名称 =0 含义 =1 含义
0 P 页不存在（要分配） 权限违规（页在但不许这么访问）
1 W/R 读操作触发 写操作触发
2 U/S 内核态访问 用户态访问
3 RSVD 保留位正常 页表项保留位被置了，硬件拒绝
4 I/D 数据访问 取指访问

第 0 位是最有用的一位，它直接分出两条路：0 是「懒分配，去补页」，1 是「你越权了，报段错误」。

还有一层划分跟性能有关：

类型 触发条件 代价
minor fault 页在内存里，只是没建 PTE（如 COW、共享页已缓存） 微秒级，纯内存操作
major fault 页不在内存，要读磁盘或 swap 毫秒级，等 I/O

/proc/vmstat 里的 pgfault 和 pgmajfault 分别是这两个的累计计数。pgmajfault 涨得快，说明内存不够或者访问模式对文件不友好。

十五、缺页处理流程源代码走读 #

x86 侧入口在 arch/x86/mm/fault.c。下面是整理过的流程，不是逐行原文，注释换成中文：

c
/* arch/x86/mm/fault.c，据 4.x/5.x 版本整理 */
static void do_page_fault(struct pt_regs *regs, unsigned long error_code)
{
    unsigned long address = read_cr2();      /* 出错地址由硬件填在 CR2 */
    struct task_struct *tsk = current;
    struct mm_struct *mm = tsk->mm;
    struct vm_area_struct *vma;
    unsigned int flags = FAULT_FLAG_DEFAULT;

    if (unlikely(in_atomic() || !mm)) {
        /* 中断上下文或内核线程没有 mm，走另一条路 */
        no_context(regs, error_code, address, 0, 0);
        return;
    }

    /* 读锁保护 VMA 拓扑，防止并发 mmap 改结构 */
    mmap_read_lock(mm);

    /* 按地址找 VMA */
    vma = find_vma(mm, address);
    if (unlikely(!vma)) {
        bad_area(regs, error_code, address);   /* 地址在所有 VMA 之上 */
        return;
    }
    if (unlikely(vma->vm_start > address)) {
        /* 落在两个 VMA 之间的空洞。栈可以往下长，别的就是野指针 */
        if (!(vma->vm_flags & VM_GROWSDOWN)) {
            bad_area(regs, error_code, address);
            return;
        }
        if (expand_stack(vma, address))
            return;
    }

    /* 写操作要求 VMA 本身可写 */
    if (unlikely((error_code & X86_PF_WRITE) && !(vma->vm_flags & VM_WRITE))) {
        bad_area(regs, error_code, address);
        return;
    }

    if (error_code & X86_PF_WRITE)
        flags |= FAULT_FLAG_WRITE;
    if (error_code & X86_PF_INSTR)
        flags |= FAULT_FLAG_INSTRUCTION;

    /* 交给与架构无关的公共层 */
    fault = handle_mm_fault(vma, address, flags);

    mmap_read_unlock(mm);
}

几个版本差异要记住：

  • 老内核写 down_read(&mm->mmap_sem)，5.8 起改名为 mmap_read_lock(mm) / mmap_lock。搜 mmap_sem 只能搜到老代码。
  • 老内核的 expand_stack(vma, address) 返回 void，新版本返回 int，失败要处理。
  • 新版本把 address 当第三个参数传，不再在函数体里读 CR2；上面的写法是 5.x 之前的形态。
  • 6.5 之后 handle_pte_fault() 被拆成了 do_pte_missing() / do_wp_page() / do_fault() 几个分支，函数名对不上是正常的。

handle_mm_fault() 之后是逐级补齐页表。页表本身也是按需分配的——一级页表常驻，中间几级和最后一级的 PTE 页都可能还没建：

c
/* mm/memory.c，流程示意 */
vm_fault_t handle_mm_fault(struct vm_area_struct *vma, unsigned long address,
                           unsigned int flags)
{
    pgd_t *pgd;
    p4d_t *p4d;
    pud_t *pud;
    pmd_t *pmd;
    pte_t *pte;

    pgd = pgd_offset(vma->vm_mm, address);            /* 一级，从不缺 */
    p4d = p4d_alloc(vma->vm_mm, pgd, address);        /* 缺就分配一张表 */
    if (!p4d) return VM_FAULT_OOM;

    pud = pud_alloc(vma->vm_mm, p4d, address);
    if (!pud) return VM_FAULT_OOM;

    pmd = pmd_alloc(vma->vm_mm, pud, address);
    if (!pmd) return VM_FAULT_OOM;

    /* pmd 可能直接映射大页，那条路先走 */
    if (pmd_none(*pmd) && ...) {
        return __handle_mm_fault(vma, address, flags);
    }

    pte = pte_alloc(vma->vm_mm, pmd);
    if (!pte) return VM_FAULT_OOM;

    return handle_pte_fault(vma, address, pte, pmd, flags);
}

p4d 这一级在很多架构上被折叠掉，p4d_alloc 变空操作，但代码得写，因为 x86-64 的 5 级页表需要它。

真正决定「这页怎么来」的是 handle_pte_fault：

PTE 状态 判断依据 走哪个函数 干什么
完全为空 pte_none() do_anonymous_page() 匿名映射，分配物理页并清零
有内容但不可写 pte_present() 且写操作 do_wp_page() 写时复制，复制一份再改 PTE 可写
有内容但不在内存 pte_none() 但有 swap 项 / 文件映射 do_fault() / do_swap_page() 从文件或 swap 读回来
设备映射 vma->vm_ops->fault 存在 do_fault() 回调驱动，让设备自己提供页

do_anonymous_page() 是 malloc 的落地点。它从伙伴系统要一个 order-0 的页，用 clear_page() 清零，再把 PFN 和权限编码进 PTE。这一步失败就返回 VM_FAULT_OOM，往上一直传，最后变成 OOM killer 或者 SIGKILL。

do_wp_page() 是 fork 的落地点。fork 之后父子共享物理页，PTE 都标成只读；子进程一写就触发缺页，这里分配新页、拷内容、改 PTE。

补完 PTE 之后，CR3 没变，但 TLB 里那条可能已经过期了。当前 CPU 上要 invlpg 或者干脆刷掉；多核情况下其他核的 TLB 还得靠 IPI 远程刷，这就是 TLB shootdown。这块的代价在 进程切换：上下文、TLB 与切换开销 里算。

十六、内核空间：high memory 与 896MB 的由来 #

i386 的内核空间只有 1GB，从 0xC0000000 起。内核访问物理内存最省事的做法是线性映射：

text
物理地址 = 内核虚拟地址 - 0xC0000000

这套映射只需要减法，连页表走查都能省（大页直接映射）。问题是 1GB 虚拟空间装不下 1GB 以上的物理内存——物理内存 4GB 的机器，0xC0000000 往上只有 1GB 的坑，剩下 3GB 物理内存在内核视野里没有地址可用。

解法是把这 1GB 切开：

区 虚拟范围 大小 用途
直接映射区（低端内存） 0xC0000000 ~ 0xF7FFFFFF 896MB 与物理 0~896MB 一一对应，减法换算
动态映射区（高端内存） 0xF8000000 ~ 0xFFFFFFFF 128MB vmalloc、kmap、fixmap 挤在这里

896 = 1024 − 128。这 128MB 要装 vmalloc 区、永久映射区（PKMAP_BASE 起）、固定映射区（FIXADDR_START 起）、模块空间等。各段的准确边界是编译期由宏算出来的，跟配置走，本文不逐个列数值。

物理地址超过 896MB 的页叫高端内存（high memory）。它们有 struct page，在 mem_map（现为 node_mem_map，按 node 组织）里有位置，但没有固定虚拟地址，内核不能直接解引用。

拿不到固定地址，就用三种借地址的手段：

手段 API 映射性质 能否睡眠 典型场景
vmalloc vmalloc() / vfree() 虚拟连续、物理离散 可以 大块缓冲区，如模块加载、大结构体数组
永久映射 kmap() / kunmap() 临时占用一个固定槽位 可以 需要多次访问同一个高端页
原子映射 kmap_atomic() / kunmap_atomic() 每 CPU 一个固定槽位 不可以 中断上下文里访问高端页

kmap_atomic 之所以不能睡眠，是因为它用的是 per-CPU 的固定槽位，一旦睡眠被调度走，别的代码在这个 CPU 上再 kmap_atomic 就会撞车。

对比一下同族 API，这几个名字天天被搞混：

API 物理连续 虚拟连续 最大尺寸 底层
kmalloc() 是 是 受限于伙伴系统最大阶，几 MB 量级 slab → 伙伴系统
vmalloc() 否 是 受 vmalloc 区大小限制 逐个 alloc_page 再拼页表
__get_free_pages() 是 是（直接映射区） 阶数受限 伙伴系统，直接返回线性映射地址

__get_free_pages 就是老资料里 get_free_page 的新名字，它返回的是直接映射区的虚拟地址，本质是伙伴系统给的物理页加个固定偏移。所以它拿不到高端内存——高端内存在直接映射区里没有地址。

这里把三个容易混的概念理顺：

概念 属于谁 单位 职责
struct page 全局物理内存 一个物理页帧 描述页帧状态（引用计数、标志、所属 zone）
伙伴系统 全局物理内存 2 的幂个连续页帧 物理页的分配与合并
slab 内核小对象 字节级对象 把整页切成小对象给内核用
用户堆 某个进程 虚拟地址区间 brk / mmap 出来的 VMA，物理页靠缺页补

用户态 malloc 拿到的是虚拟地址，背后是 VMA；物理页在第一次写的时候由缺页处理补上。struct page、mem_map、get_free_page 全是内核侧的物理页概念，跟用户堆不是一回事。原文把这几样并排讲，容易读成一条线，这里分开。

64 位系统上 CONFIG_HIGHMEM 根本不存在，因为虚拟地址空间足够把所有物理内存线性映射进来。所以「896MB」这个数字只在 32 位内核上成立。ARM64 上对应的概念是线性映射区（linear map），起点和大小由 PAGE_OFFSET 和实际内存决定。

十七、ioremap 与外设寄存器映射 #

SoC 的外设寄存器（GPIO、I2C、UART、PCIe 配置空间）都摆在物理地址空间的某一段。这类访问有两种编址方式：

方式 地址空间 访问指令 用在哪
MMIO 与内存统一编址 普通 load/store（readl/writel） ARM、MIPS、RISC-V、x86 的 PCI BAR
Port I/O 独立地址空间 专用指令（x86 的 in/out） x86 传统外设，如老式串口、键盘控制器

MMIO 是主流。但物理地址不能直接解引用——内核运行在保护模式下，而且那段物理地址根本不在当前页表里。要访问，先 ioremap() 把它映射进内核虚拟空间。

裸机时代大家习惯这么写：

c
*(volatile unsigned int *)0xC001A000 = 0x20;   /* 裸机上能跑，Linux 上不行 */

在 Linux 驱动里这么干必崩，原因不止一个：

  1. 那个虚拟地址压根没映射。内核页表里没有对应项，一写就缺页，内核态缺页直接 oops。
  2. 编译器会重排。volatile 只保证不把这次访问优化掉，不保证多次访问之间的顺序。外设寄存器写序代表状态机跳转，顺序一乱硬件就进死胡同。
  3. 缓存会吃掉写入。外设寄存器的内容由硬件实时改，走 cache 的话读到的是旧值，写也不一定到总线上。

readl() / writel() 解决的是后两个。它们内部带内存屏障（ARM 上是 dmb/dsb，x86 上依赖 mfence 或强序语义），并且作用在 ioremap 出来的、带 __iomem 标注的地址上，那个地址对应的 PTE 被设成非缓存。

看一个最小的映射例子：

c
#include <linux/io.h>
#include <linux/module.h>

#define REG_BASE_PHYS  0xC001A000UL   /* 示例值，实际看 SoC 手册 */
#define REG_SIZE       0x10

static void __iomem *reg_base;
static int __init demo_init(void)
{
    u32 val;

    /* 物理寄存器段映射到内核虚拟空间 */
    reg_base = ioremap(REG_BASE_PHYS, REG_SIZE);
    if (!reg_base)
        return -ENOMEM;

    /* 方向寄存器：把第 5 位置 1，配成输出 */
    val = readl(reg_base + 0x04);
    val |= BIT(5);
    writel(val, reg_base + 0x04);

    /* 数据寄存器：拉高，点亮 */
    val = readl(reg_base + 0x08);
    val |= BIT(5);
    writel(val, reg_base + 0x08);

    return 0;
}

static void __exit demo_exit(void)
{
    u32 val = readl(reg_base + 0x08);
    val &= ~BIT(5);
    writel(val, reg_base + 0x08);

    iounmap(reg_base);
}

几个细节：

  • __iomem 是个 sparse 标注，作用是让编译器在「把 I/O 地址当普通指针用」时报警。去掉它照样编得过，只是丢了检查。
  • ioremap 返回的地址在 vmalloc 区，所以它是「虚拟连续、物理离散」体系里的东西。ioremap 失败返回 NULL，别忘判。
  • 用完必须 iounmap，否则泄漏 vmalloc 区地址。驱动里更推荐 devm_ioremap_resource()，跟设备生命周期绑定，probe 失败或设备卸载时自动回收。
  • 还有 ioremap_wc()（写合并，适合显存、framebuffer）和 ioremap_uc()（强不可缓存），选错会导致性能差或者数据错。
  • 映射出来的区域要防越界，request_mem_region() 用来占住这段物理地址，避免两个驱动抢同一块寄存器。

ARM64 上 ioremap 的实现走的是 ioremap_prot() + __ioremap_caller()，从 vmalloc 区里切地址，页表属性设成 device 或 normal-nc，取决于传给它的 prot。这块的细节在 ARM64 内存初始化：页表、memblock 与 KASLR 里有更完整的铺垫。
