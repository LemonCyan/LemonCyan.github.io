一、mmap 到底省掉了什么 #

传统文件访问是 open → read/write/lseek。这条路的低效不在系统调用本身，而在两次拷贝和两份内存：磁盘 → 内核 page cache → 用户缓冲区。同一份文件被十个进程读，就是十份用户态副本。

mmap 换了个路子：把 page cache 里那些页直接挂进进程页表，用户态用普通内存访问指令读写，数据不再跨空间搬一次。

text
read() 路径：  磁盘 → page cache → （拷贝）→ 用户缓冲区
mmap() 路径：  磁盘 → page cache → （页表指向同一批页）

关键在「懒」这个字。mmap 返回的时候，一个物理页都还没分配，它只做了一件事：在进程的 VMA 链表里登记一段区间。第一次访问某个地址，硬件发现页表项是空的，触发缺页异常，内核这才去 page cache 找页（没有就去磁盘读），把页表填上。所以一个 1GB 的文件 mmap 进来，瞬间返回，实际占用的物理内存取决于你摸了多少页。

代价也随之而来：错误从「read 返回 -1」变成「访问时收到 SIGBUS」。这个区别是 mmap 所有坑的总根源，第七章展开。

二、用户态 API：六个参数逐个说 #

c
#include <sys/mman.h>

void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);
参数 含义 实践要点
addr 期望的起始地址 传 NULL 让内核选。传非 NULL 只是「建议」，内核可以不理，除非加了 MAP_FIXED
length 映射长度 内核按页向上取整。length = 1 实际映射一整页
prot 页级保护 PROT_READ / PROT_WRITE / PROT_EXEC / PROT_NONE，可或
flags 映射类型 必须且只能选 MAP_SHARED 或 MAP_PRIVATE 之一，其余可叠加
fd 文件描述符 匿名映射传 -1
offset 文件内偏移 必须是页大小的整数倍，否则返回 EINVAL

返回值是映射区起始地址，失败返回 MAP_FAILED（即 (void *)-1），错误码在 errno。判等要判 == MAP_FAILED，不能判 < 0，因为 MAP_FAILED 是 -1 而不是任意负数。

prot 和文件打开方式必须匹配，这条容易被忽略：文件以 O_RDONLY 打开，就不能建 PROT_WRITE 的 MAP_SHARED 映射，内核返回 EACCES。MAP_PRIVATE 加 PROT_WRITE 是可以的（写时复制，不回写文件）。

flags 里最常用的几个：

标志 作用
MAP_SHARED 改动对其他进程可见，最终回写文件
MAP_PRIVATE 写时复制，改动只在本进程可见，不回写
MAP_ANONYMOUS（MAP_ANON） 匿名映射，不对应文件，fd 传 -1
MAP_FIXED 强制用 addr，会覆盖该地址区间上的已有映射，危险
MAP_POPULATE 建映射时就把页表填好，避免后续缺页。大文件首次访问快，但 mmap 本身变慢
MAP_LOCKED 锁定不换出，等价于 mmap 后调 mlock
MAP_HUGETLB 用大页

MAP_FIXED 单独警告一次：它不是「尽量用这个地址」，而是「必须用这个地址，有冲突就把原有的映射拆掉」。老代码里 mmap(0x80000, ...) 这种不带 MAP_FIXED 的写法是安全的（只是建议），但一旦加上 MAP_FIXED，地址算错就会把栈或堆映射覆盖掉，现象是段错误发生在完全无关的位置。

三、mmap 系统调用在内核里做了什么 #

用户态调 mmap()，走 sys_mmap → ksys_mmap_pgoff → vm_mmap_pgoff → do_mmap → mmap_region。核心是 mmap_region，它做四件事：

text
① 查重与合并    这段地址区间有没有已存在的 VMA？能合并就合并，不能就新建
② 分配结构      kmem_cache_alloc(vm_area_cachep) 拿一个 vm_area_struct
③ 填字段        vm_start / vm_end / vm_flags / vm_page_prot / vm_file / vm_pgoff
④ 调文件系统的 mmap   file->f_op->mmap(file, vma)，这一步才和具体设备/文件系统打交道

第 ④ 步是驱动的入口。用户态的 mmap() 和驱动的 .mmap 回调是两次不同层次的调用：前者是系统调用，后者由 mmap_region 在内部调用。所以驱动 .mmap 的返回值不是给用户看的，返回负数会让整个 mmap() 系统调用失败并把这个负数作为错误码。

一个容易混淆的点：mmap_region 在调 .mmap 之前，VMA 已经建好并挂进进程了。所以驱动回调里 vma->vm_start 是有效值，不需要自己算地址。

内核版本差异：3.x 之前 mmap_region 用的是 file->f_op->mmap，5.x 之后引入 call_mmap() 包装，6.x 还在推动把 f_op->mmap 拆成更细的接口。功能等价，别对着行号找。

四、驱动侧 mmap：两种做法 #

设备驱动的 mmap 只有一个目标：把设备的一段物理地址（或驱动分配的一段内存）映射进用户地址空间。实现上有两条路，选错了要么性能差，要么直接不能工作。

一次性映射 缺页时映射
代表函数 remap_pfn_range() vm_insert_page() / vmf_insert_pfn()
建立时机 在 .mmap 回调里一次建完整段 在 vm_ops->fault 回调里，访问哪页建哪页
适用内存 物理地址连续，或设备 MMIO 物理页分散，或按需分配
典型场景 寄存器 BAR、framebuffer、预留的连续内存 vmalloc 出来的内存、动态分配的 DMA buffer
用户态感知不到差别 是 是

4.1 一次性映射：remap_pfn_range #

c
int remap_pfn_range(struct vm_area_struct *vma, unsigned long addr,
                    unsigned long pfn, unsigned long size, pgprot_t prot);

五个参数：

参数 填什么
vma 系统传进来的那个
addr 映射的虚拟起始地址，填 vma->vm_start
pfn 物理页号，不是物理地址。物理地址要 >> PAGE_SHIFT（4KB 页下右移 12）
size 长度，填 vma->vm_end - vma->vm_start
prot 页保护属性，填 vma->vm_page_prot；要调 cache 属性时改这里

最小可用版本：

c
static int mydev_mmap(struct file *filp, struct vm_area_struct *vma)
{
    struct mydev *dev = filp->private_data;
    unsigned long size = vma->vm_end - vma->vm_start;

    if (size > dev->size)
        return -EINVAL;

    return remap_pfn_range(vma, vma->vm_start,
                           dev->phys_addr >> PAGE_SHIFT,
                           size, vma->vm_page_prot);
}

就这么几行。返回 0 成功，返回负错误码失败。

关键的一条：不需要自己置 VM_IO、VM_PFNMAP、VM_DONTEXPAND、VM_DONTDUMP。 remap_pfn_range() 内部会把这些都设上。网上大量 2010 年前后的文章写着要先 vma->vm_flags |= VM_IO | VM_RESERVED，那是 2.6 时代的写法，VM_RESERVED 在 3.7 就被删了（commit 314e51b98「mm: kill vma flag VM_RESERVED」），现在写它连编译都过不去。

对照一下现代内核里那些正确的 mmap 实现，比如 drivers/gpu/drm/drm_vm.c 或 UIO 驱动，都是在 remap_pfn_range 之外自己额外设 VM_DONTEXPAND | VM_DONTDUMP，那是为了特定的语义需求，不是必须的仪式。

4.2 缺页时映射：给 vma 挂 vm_ops #

物理页不连续时，remap_pfn_range 帮不上忙，因为它的 pfn 是单个起点加连续长度。这时改成挂回调：

c
static vm_fault_t mydev_vm_fault(struct vm_fault *vmf)
{
    struct vm_area_struct *vma = vmf->vma;
    struct mydev *dev = vma->vm_private_data;
    unsigned long offset = vmf->address - vma->vm_start;
    struct page *page;

    page = dev->pages[offset >> PAGE_SHIFT];
    if (!page)
        return VM_FAULT_SIGBUS;

    get_page(page);
    vmf->page = page;
    return 0;
}

static const struct vm_operations_struct mydev_vm_ops = {
    .fault = mydev_vm_fault,
};

static int mydev_mmap(struct file *filp, struct vm_area_struct *vma)
{
    struct mydev *dev = filp->private_data;

    vma->vm_ops = &mydev_vm_ops;
    vma->vm_private_data = dev;     /* fault 回调里从这里取回上下文 */
    return 0;
}

四个要点：

一、用 fault，不是 nopage。 nopage 在 2.6.23 被 fault 取代，之后彻底移除了。看到 struct page *(*nopage)(struct vm_area_struct *, unsigned long, int *) 这种签名，直接判定资料是 2008 年以前的。新签名是 vm_fault_t (*fault)(struct vm_fault *vmf)，参数全打包进 struct vm_fault。

二、返回值是 vm_fault_t，不是 int。 成功返回 0，失败返回 VM_FAULT_SIGBUS（对应老代码的 NOPAGE_SIGBUS）、VM_FAULT_OOM 等。这些宏的数值和 errno 不是一回事，别混。

三、get_page(page) 不能省。 你把页交给用户态用，就得持有一个引用，否则页可能在你用的时候被回收。

四、vm_private_data 是自己传上下文的地方。 fault 回调只拿到 vm_fault，里面没有指向你私有结构的指针，所以必须在 .mmap 里把指针存进 vm_private_data。

4.3 什么时候两个都要 #

有些驱动的做法是：.mmap 里先尝试 remap_pfn_range，失败则挂 vm_ops 回退。这在物理页原本连续但可能被拆散（比如 CMA 迁移后）的场景里有用。但更常见的做法是直接判断内存性质：驱动自己分配的内存是 kmalloc（物理连续）还是 vmalloc（不连续）还是 alloc_pages 拿的一批页，判断完就知道该走哪条路。

kmalloc 出来的内存：物理连续，可以用 remap_pfn_range（virt_to_phys 转物理地址再取 pfn）。但要提醒一句，kmalloc 的内存不能用 vm_insert_page，因为 kmalloc 返回的不是 page，virt_to_page 拿到的 page 只覆盖所在的那一个物理页，跨页的部分是不合法的。

五、用户态那两段示例代码 #

原稿给的两段例子都是 2008 年的，而且粘贴有错。重写一版能直接跑的。

5.1 只读映射一个文本文件 #

c
#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char **argv)
{
    int fd;
    char *mapped;
    struct stat st;

    if (argc < 2) {
        fprintf(stderr, "usage: %s <file>\n", argv[0]);
        return 1;
    }

    fd = open(argv[1], O_RDONLY);
    if (fd < 0) {
        perror("open");
        return 1;
    }

    /* 先拿到文件大小。原稿用 lseek(fd, 1, SEEK_END) 再写一个 '\0'，
       那是在改文件长度，不是查长度 */
    if (fstat(fd, &st) < 0) {
        perror("fstat");
        close(fd);
        return 1;
    }
    if (st.st_size == 0) {
        fprintf(stderr, "%s: empty file\n", argv[1]);
        close(fd);
        return 1;
    }

    mapped = mmap(NULL, st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
    if (mapped == MAP_FAILED) {
        perror("mmap");
        close(fd);
        return 1;
    }

    /* 长度按 st_size 算，不要指望有 '\0' 可以配合 printf("%s") */
    fwrite(mapped, 1, st.st_size, stdout);

    munmap(mapped, st.st_size);
    close(fd);
    return 0;
}

原稿那版有三个 bug：用 lseek(fd, 1, SEEK_END) 当「取大小」（其实它返回的是位置，而且随后那句 write(fd, "\0", 1) 是在往文件末尾追加一个字节，把文件改长了）；用 printf("%s", mapped) 打整块内存（映射区末尾没有保证的 \0，除非你正好映射到一个以 \0 结尾且长度凑巧的文件）；flength = 1024 初始化后被 lseek 覆盖，属于废代码。

5.2 共享映射改写文件内容 #

c
#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>
#include <stdio.h>

int main(int argc, char **argv)
{
    int fd;
    char *mapped, *p;
    struct stat st;

    if (argc < 2) {
        fprintf(stderr, "usage: %s <file>\n", argv[0]);
        return 1;
    }

    /* 要共享映射且要写，必须 O_RDWR */
    fd = open(argv[1], O_RDWR);
    if (fd < 0) {
        perror("open");
        return 1;
    }
    if (fstat(fd, &st) < 0 || st.st_size == 0) {
        perror("fstat");
        close(fd);
        return 1;
    }

    mapped = mmap(NULL, st.st_size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (mapped == MAP_FAILED) {
        perror("mmap");
        close(fd);
        return 1;
    }

    /* 在映射区里就地替换 */
    p = mapped;
    while ((p = memmem(p, st.st_size - (p - mapped), "Hello", 5))) {
        memcpy(p, "Linux", 5);
        p += 5;
    }

    msync(mapped, st.st_size, MS_SYNC);
    munmap(mapped, st.st_size);
    close(fd);
    return 0;
}

和上一段比，差别就三处：O_RDWR、PROT_WRITE、MAP_SHARED。MAP_SHARED 是改动能落盘的前提，MAP_PRIVATE 下你在 memcpy 时会被复制出一份私有页，原文件一个字节都不变。

memmem 是 GNU 扩展（_GNU_SOURCE），原稿用 strstr 找 "Hello"，前提是映射区整体可当 C 字符串处理，这又回到 \0 的老问题。

六、munmap / msync / brk #

6.1 munmap #

c
int munmap(void *addr, size_t length);

把 [addr, addr+length) 上的映射拆掉。如果这段区间不对齐某个 VMA 的边界，内核会分裂 VMA：拆掉中间一段，前后各剩一块。所以 munmap 的代价不总是 O(1)，更不是零。

munmap 之后再访问那块地址就是 SIGSEGV，这是它和 msync 的区别。

6.2 msync：什么时候必须调 #

c
int msync(void *addr, size_t length, int flags);

把 MAP_SHARED 映射里改过的脏页回写。三个 flags：

flag 行为
MS_SYNC 等到真正写完才返回
MS_ASYNC 只调度回写，立刻返回
MS_INVALIDATE 让该文件的其他映射失效，下次访问重新读

原稿说「munmap 时并不保证页面回写，不调 msync 可能丢失修改」，这句话不准确，容易吓到人。准确的说法是：

  • 进程正常退出或 munmap 之后，脏页仍然留在 page cache 里，最终会被内核回写，数据不会丢。
  • 但什么时候落盘不受你控制。要立刻落盘（比如紧接着要断电、或者另一个进程马上要读），必须 MS_SYNC。
  • 真正会丢数据的是掉电：page cache 里的脏页还没回写，机器断电就没了。

所以 msync 的定位是「控制时机」，不是「防止丢失」。

6.3 brk #

brk 不是 mmap 的一部分，但和它同源：两者都是创建 VMA。brk 把数据段末尾往后推，内核做一个合法性检查（新地址不能撞上已有的 VMA），然后调整 VMA。glibc 的 malloc 小对象走 brk，大对象（默认阈值 128KB，M_MMAP_THRESHOLD）直接走 mmap。

这条机制的副作用：大量小 mmap 会把 VMA 数量打满。上限是 /proc/sys/vm/max_map_count，默认 65530，打满后 mmap 返回 ENOMEM。

七、五个必须知道的坑 #

现象 原因 处理
访问映射区收到 SIGBUS 访问位置超过了文件实际大小（映射长度按页取整，超出的部分没有后备） length 取文件真实大小；文件被 truncate 变小后访问也会触发
mmap 返回 EINVAL offset 不是页大小整数倍 用 offset & (sysconf(_SC_PAGESIZE) - 1) 检查
mmap 返回 EACCES prot 要写，但文件是 O_RDONLY 改打开方式
改了内容但文件没变 用了 MAP_PRIVATE 改 MAP_SHARED + O_RDWR
映射了 0 字节文件，一访问就 SIGBUS 没有后备页 先给文件写点内容，或用 ftruncate 扩到目标长度

SIGBUS 这条要展开一句，因为它是 mmap 版「段错误」最常见的来源。read 一个超出文件末尾的位置，内核只返回读到的字节数（可能为 0），是可控的返回值；mmap 同样的位置，是进程直接收到信号。所以移植 read 代码到 mmap 时，边界检查必须从「检查返回值」改成「访问前确认 offset < file_size」。

还有个更隐蔽的：mmap 一个文件之后，另一个进程把文件 truncate 短了，你这边访问被截掉的部分也是 SIGBUS。多进程共享 mmap 的场景要考虑到这一点。

八、mmap 和 System V 共享内存怎么选 #

两者都能做进程间共享内存，但机制完全不同。

mmap 映射文件 System V shm POSIX shm_open
后备存储 磁盘文件（或匿名内存） RAM（tmpfs/shmfs） tmpfs
有名字吗 靠文件名 靠 shmget 的 key 靠 /dev/shm/name
生命周期 跟随文件 跟随内核（shmctl IPC_RMID 或重启） 跟随文件系统
访问接口 普通指针 shmat 拿到指针 mmap 拿到指针
大容量 可以超过物理内存 不能超过可用内存 不能超过可用内存
跨机器 文件能传，映射不能 不能 不能

选型的实际判据就两条：

  • 数据要不要持久化？ 要，用 mmap 映射文件。不要，用匿名 mmap（MAP_ANONYMOUS | MAP_SHARED，fork 出的子进程共享）或 POSIX shm。
  • 数据量会不会超过物理内存？ 会，只能用文件映射，让内核去换页。

原稿说「mmap 保存到实际硬盘，实际存储并没有反映到主存上」、shm「直接映射到实际物理存储器里面」，这个二分过于绝对。准确的说法是：两者都是通过 page cache 访问物理内存，区别在于 mmap 有文件作为后备，页可以被回收后重新从文件读回；shm 的后备是 tmpfs，页被回收时进 swap（如果没有 swap 就 OOM）。所以「mmap 慢、shm 快」这个结论在首次访问时成立（mmap 要读磁盘），在重复访问时不成立（都在 page cache 里）。

还有一个原稿没提的现代替代：匿名共享映射。

c
/* 父子进程共享，不需要任何文件 */
void *p = mmap(NULL, size, PROT_READ | PROT_WRITE,
               MAP_SHARED | MAP_ANONYMOUS, -1, 0);

它比 shmget 干净得多，没有 key 冲突、没有 IPC_RMID 清理问题、不占 /proc/sysvipc/shm 的条目。新代码除非要兼容老系统，否则没必要用 System V shm。

九、从 2.4 到 5.x：老资料里的东西现在是什么 #

这一节是为了让读到 2008 年文章的人能对上号。

老写法 现状 什么时候变的
vm_area_struct 里 vm_avl_height / vm_avl_left / vm_avl_right 已删除，VMA 用红黑树 vm_rb 组织 2.6 早期
vm_next_share / vm_pprev_share 已删除，逆向映射改用 anon_vma / address_space->i_mmap 2.6 早期
vm_raend 已删除 2.6 早期
vma->vm_flags |= VM_RESERVED VM_RESERVED 已删除，语义拆成 VM_DONTEXPAND / VM_DONTDUMP / VM_PFNMAP 3.7，commit 314e51b98
struct page *(*nopage)(...) 已被 vm_fault_t (*fault)(struct vm_fault *) 取代，nopage 已移除 2.6.23 引入 fault
remap_page_range() 已被 remap_pfn_range() 取代 2.6.11
vma->vm_flags |= VM_IO 手动置位 用 remap_pfn_range 时不必手写，函数内部会设 VM_IO | VM_PFNMAP | VM_DONTEXPAND | VM_DONTDUMP 一直是这个行为，只是老文章没写清
mm->mmap 链表头 6.1 起换成 mm_mt（maple tree），mm->mmap 编不过 6.1
mm->mmap_sem 5.8 起改名 mmap_lock，down_read(&mm->mmap_sem) 编不过 5.8

VM_RESERVED 那个 commit 的说明值得引一句：作者指出这个 flag 早就丢了原意（v2.4 时代它是「阻止 VMA 被换出」），后来只剩一些零散副作用，所以干脆拆掉，让每个语义各归各的 flag。这也解释了为什么老代码里 VM_RESERVED 和 VM_IO 总是一起出现：它们确实是两件事，只是被塞进同一行写了。

十、诊断命令 #

bash
# 看进程的映射表（这是最常用的一个）
cat /proc/$(pidof myapp)/maps

# 输出格式：起始-结束 权限 偏移 设备 inode 路径
# 55f0a1c00000-55f0a1c21000 r-xp 00000000 08:01 1234567 /usr/bin/myapp
#            ^start  ^end   ^rwxp  ^offset

# 看某段映射的统计（RSS、共享、私有）
cat /proc/$(pidof myapp)/smaps | grep -A8 "my_lib"

# 看当前进程 VMA 数量，接近 max_map_count 就是泄漏迹象
wc -l < /proc/$(pidof myapp)/maps
cat /proc/sys/vm/max_map_count

# 看一个文件被哪些进程映射着（需要先找到 inode）
find /proc/*/maps -type f 2>/dev/null | xargs grep -l "my_file" 2>/dev/null

/proc/pid/maps 的权限字段是 rwxp 四位：读、写、执行、私有(Private)。第四位是 p 表示 MAP_PRIVATE，s 表示 MAP_SHARED。排查「改了不生效」的时候，这一位就是第一现场。
