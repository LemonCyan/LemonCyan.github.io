一、内核眼里的内存：从 CPU 到 Device 的三条数据流 #

内存管理复杂，不在于「分配」这个动作，而在于有太多人想以不同方式碰同一片内存。先把需求摊开。

CPU 有访问内存的需求：取指、取数据、写数据。设备也有访问内存的需求，它没 CPU 聪明，碰内存只有三条路：CPU 中转（本质还是 CPU 访问内存）、找个有脑子的第三方（DMA 控制器）中转、设备自己上场（中间可挂 IOMMU）。

text
CPU    <-----------> MMU(可选) <-----------> Memory
Device <-----------> CPU <-----------> Memory
Device <-----------> DMA Controller <-----------> Memory
Device <-----------> IOMMU(可选) <-----------> Memory

三条流搅在一起，加上内存本身的稀缺，才是 MM 子系统又大又难拆的原因。往下内核是一步步接住这些需求的：先看见内存，再管起来，再对外服务，最后处理高级需求。这条脉络就是下面几章的骨架。

看见内存这一步，在 MMU 使能之前没难度，物理地址直接跑。MMU 一开、内存管理机制还没 ready 的那段窗口最难受：内核眼里只有虚拟地址，它必须搞出一套简单能用的映射，把一部分物理内存拉进虚拟地址空间，够启动代码和早期分配器活着就行。identity mapping、early fixmap、memblock 都在这个窗口干活，过程见 ARM64 内存初始化：页表、memblock 与 KASLR，本篇从「已经看见内存」之后接着讲。管起来这一步，取决于内存长什么样：物理地址连不连续、有没有 NUMA、支不支持热插拔，形态不同模型不同，这是第六到第九章。对外服务这一步最显眼：给每个进程一套独立 VA、做保护和隔离、提供 mmap、提供公平高效的物理页分配、提供进程间共享虚拟内存。高级需求这一步是欲望膨胀的结果：内存热插拔、物理内存比虚拟地址能寻址的范围还大、hugetlbpage、swap、NUMA 下的 page migration、内存泄漏检查、碎片整理、OOM kill——本篇十三到十六章专攻碎片。

设备视角的需求单独拎出来，因为它和 CPU 视角不兼容。软件通过 CPU 视角拿到的内存，设备不一定能直接访问；就算能，也要按设备期望的形式组织。于是有了 DMA mapping：dma_alloc_* 拿一块设备能直接访问的内存（返回 dma_addr），dma_map_* 在 CPU 视角的虚拟地址和 dma_addr 之间来回转。多设备要共享同一份数据时又不能各拷一份，于是有了 DMA buffer sharing：老办法用 CPU 虚拟地址中转（scatterlist 那套），新办法是 drivers/dma-buf/dma-buf.c 里的 dma-buf framework。

落到代码上，三块分工很清：

模块 干什么 代码位置
VM 狭义内存管理：页框、zone、分配器、地址空间 mm/（平台无关）+ arch/xxx/mm/（平台相关）
DMA mapping 让设备能直接访问内存，做地址转换 drivers/base/（通用）+ arch/xxx/mm/（平台相关）
DMA buffer sharing 设备之间共享同一块 buffer drivers/dma-buf/dma-buf.c、scatterlist

本篇只走 VM 这条线，起点是物理页。

二、页框、PFN 与 struct page #

物理内存不按字节管，按页管。页大小由硬件和内核配置共同决定，4K 是最经典的设定。把物理内存按 page size 切成一格一格，每一格叫一个 page frame（页框）。

内核给每个 page frame 配一个 struct page，记这一页在干什么：内核正文段？进程页表？file cache？还是躺在 free 链表里没人要。4.x 的 struct page 精简下来长这样：

c
struct page {
    unsigned long flags;        /* 一组 PAGE_FLAG_*，原子位操作 */

    union {
        struct {                /* 在 page cache 或 anon 里时用这套 */
            struct list_head lru;
            struct address_space *mapping;
            pgoff_t index;
            unsigned long private;
        };
        struct {                /* 作为 slab 页时用这套 */
            struct kmem_cache *slab_cache;
            void *freelist;
            union { struct page *next; int pages; };
        };
        struct {                /* 复合页的尾页用这套 */
            unsigned long compound_head;
        };
    };

    union {
        atomic_t _mapcount;     /* 被几个页表项映射 */
        unsigned int active;
    };
    atomic_t _count;            /* 引用计数，0 表示可以回收 */
};

4.4 里引用计数是 atomic_t _count，4.18 之后换成 atomic_t _refcount，别照抄到新树。

页框要编号才管得动，这个号是 PFN（page frame number）。算法很直接：物理内存从 0 地址开始时，PFN 0 就是物理地址 0 那一页；物理内存从 x 地址开始时，第一个页框号是 x >> PAGE_SHIFT。顺带把物理地址空间和物理内存的区别钉死：物理地址空间从 0 开始到体系结构支持的最大值为止（ARM 32 位是 4G，ARM64 支持 48 bit 就是 256T），这么大的空间不是都给内存，I/O 也占一部分，内存只占其中一段有限区间。所以物理地址空间有空洞，物理内存没有。

struct page 和 PFN 之间靠 page_to_pfn / pfn_to_page 两个宏换算。这俩宏的实现就是内存模型的全部秘密——三种 memory model 的区别，说到底就是这两个宏怎么写，具体实现放第六到第八章。

先拆一个源材料里的混讲：struct page、mem_map[]、get_free_page 是物理页这一层；brk、malloc 是用户进程虚拟地址空间这一层。两者不在一个层面。malloc 在用户态堆上切字节，堆不够了调 brk 扩大，brk 按页大小的倍数调整进程堆边界。内核这边 __get_free_pages 直接要物理页，粒度是页不是字节。把 malloc 和 get_free_page 摆一张表里比「谁更灵活」是错的，它们解决两个层的问题，中间还隔着页表、VMA 和缺页异常。物理页怎么落到进程 VA 上，看 地址空间与地址翻译。

三、三个层级：node / zone / page #

物理内存组织成三级，从大到小：node、zone、page。

最上面是 node，用 struct pglist_data（别名 pg_data_t）描述。UMA 机器一个，NUMA 机器每个 node 一套。

c
typedef struct pglist_data {
    struct zone node_zones[MAX_NR_ZONES];           /* 本 node 的所有 zone */
    struct zonelist node_zonelists[MAX_ZONELISTS];  /* 分配时的 fallback 顺序 */
    int nr_zones;
    unsigned long node_start_pfn;                   /* 本 node 起始页框号 */
    unsigned long node_present_pages;               /* 实际存在的物理页数 */
    unsigned long node_spanned_pages;               /* 覆盖的页框范围，含空洞 */
    int node_id;
    struct page *node_mem_map;                      /* 本 node 的 struct page 数组 */
    struct bootmem_data *bdata;
    struct zoneref _zonerefs[MAX_ZONELISTS];
} pg_data_t;

中间是 zone，一个 node 里的内存按能力和用途切成几块：哪些地址设备 DMA 够得着、哪些只能靠内核页表临时映射、哪些留给可移动页。最下面是 page，就是第二章那个 struct page。

层级 描述结构 管什么 数量
node struct pglist_data 本地内存 + 访问延迟亲和性，NUMA 的分配单位 UMA 1 个，NUMA 每 node 1 个
zone struct zone 内存的能力与用途边界：能不能 DMA、能不能直接映射 每 node 若干
page struct page 单个页框的状态与引用计数 每个页框一个

为什么要有 zone 这一级？因为物理内存不均质。老式 ISA 设备的 DMA 只能碰低 16MB；32 位系统内核直接映射区装不下全部物理内存，超出的部分要临时映射才能访问。这些硬件差异必须体现在分配器里，否则给设备分了一块它够不着的内存，驱动就废了。zone 就是把这些差异编码进数据结构的结果。

zone 的核心字段（4.x）：

c
struct zone {
    unsigned long watermark[NR_WMARK];  /* MIN/LOW/HIGH 三条水位线 */
    long lowmem_reserve[MAX_NR_ZONES];  /* 给更低 zone 预留，防越界抢光 */
    struct per_cpu_pageset __percpu *pageset; /* per-cpu 页缓存 */
    spinlock_t lock;
    struct free_area free_area[MAX_ORDER];    /* 伙伴系统空闲链表，见第十一章 */
    spinlock_t lru_lock;
    struct lruvec lruvec;               /* LRU 链表，回收用 */
    atomic_long_t vm_stat[NR_VM_ZONE_STAT_ITEMS];
    int node;
    unsigned long zone_start_pfn;
    unsigned long spanned_pages;        /* 覆盖范围，含空洞 */
    unsigned long present_pages;        /* 实际存在 */
    atomic_long_t managed_pages;        /* 分配器真能管的，present 减预留 */
    const char *name;
};

managed_pages 和 present_pages 的差值就是被 early reservation 吃掉、永远进不了伙伴系统的页。三条水位线决定分配器什么时候醒 kswapd、什么时候自己动手回收，这条线在 页面回收与逆向映射 里接着讲。

四、zone 的划分与 ZONE_DMA / NORMAL / HIGHMEM / MOVABLE #

zone 类型定义在 include/linux/mmzone.h：

c
enum zone_type {
#ifdef CONFIG_ZONE_DMA
    ZONE_DMA,       /* 老设备 DMA 够得着的低地址，x86 上限定 16MB */
#endif
#ifdef CONFIG_ZONE_DMA32
    ZONE_DMA32,     /* 只能寻址 32 位物理地址的设备，上限 4GB */
#endif
    ZONE_NORMAL,    /* 内核能直接映射、正常使用的内存，主力 */
#ifdef CONFIG_HIGHMEM
    ZONE_HIGHMEM,   /* 32 位才有，超出直接映射范围，要 kmap */
#endif
    ZONE_MOVABLE,   /* 不绑定物理地址，只放可迁移页，见第十六章 */
#ifdef CONFIG_ZONE_DEVICE
    ZONE_DEVICE,    /* 设备内存挂进 MM，4.3 之后才有 */
#endif
    __MAX_NR_ZONES
};

枚举顺序有意义：越靠前地址越低，分配时的 fallback 也按这个顺序由低到高找。ZONE_MOVABLE 和 ZONE_DEVICE 排最后，因为它们不是「更低的地址」，是两种特殊切分。

zone 存在条件 用途
ZONE_DMA CONFIG_ZONE_DMA 给 DMA 够不着高地址的老设备，ISA 时代遗产，ARM64 上少见
ZONE_DMA32 CONFIG_ZONE_DMA32 给只能寻址 32 位物理地址的设备，64 位系统兜底
ZONE_NORMAL 总有 内核能直接映射、正常使用的内存，绝大多数分配落这里
ZONE_HIGHMEM CONFIG_HIGHMEM，只在 32 位 超出直接映射范围，要 kmap 才能碰
ZONE_MOVABLE 有 kernelcore/movablecore 只放可迁移页，为热拔插和减碎片服务
ZONE_DEVICE CONFIG_ZONE_DEVICE 设备内存（GPU 显存、持久内存）挂进 MM

ZONE_HIGHMEM 要单独解释，它最容易被误讲。它存在的唯一理由是 32 位系统的虚拟地址空间不够：内核把 4G 虚拟空间切走 1G 给自己（3G/1G 划分），这 1G 装不下机器上全部物理内存时，装不下的那部分就叫高端内存，内核不能给它建永久映射，只能临时 kmap/kunmap。到了 64 位，虚拟地址空间大到用不完，直接映射区能盖住全部物理内存，ZONE_HIGHMEM 就没有存在必要。ARM64 上 CONFIG_HIGHMEM 是关的，你在 /proc/zoneinfo 里看不到 HighMem。

zone 之间还有一层防越界机制：lowmem_reserve[]。低地址 zone 的页很少，普通分配要是把 ZONE_DMA 抢干净了，真正需要 DMA 的设备就没页可用。所以每个 zone 给比自己更低、且 fallback 顺序在前的 zone 预留一份页数，普通分配不能跨越这份预留。

五、NUMA 与非 NUMA 的差别 #

设计多处理器系统的内存架构有两条路。UMA（Uniform Memory Access）：所有 processor 共享一片统一的物理内存，从哪个 processor 发起访问延迟都一样。NUMA（Non-uniform Memory Access）：访问延迟跟 memory 与 processor 的相对位置有关，某个 node 上的 processor 访问 local memory 比访问 remote memory 快。

这两个概念和内存模型是两回事，但历史上一直被搅在一起，先把关系掰开：

系统 node 数 内存物理连续性 可选内存模型
UMA + 连续 1 连续无空洞 FLAT，或 SPARSEMEM
UMA + 有空洞 1 有空洞 Discontiguous，或 SPARSEMEM
NUMA + 每 node 连续 多 node 内连续，node 间不连续 Discontiguous，或 SPARSEMEM
NUMA + node 内有空洞（热插拔） 多 都不保证 SPARSEMEM

关键在最后一行。NUMA 从来没规定内存必须连续，Discontiguous 也不等于 NUMA——两者的共同点只是「多 node」。sparse memory 出现之后，连续性和 NUMA 才真正解耦：NUMA 系统可以是 FLAT 也可以是 SPARSE，SPARSE 系统可以是 NUMA 也可以是 UMA。

NUMA 对分配器的影响在于，分配时不只看「哪个 zone 有空页」，还要看「哪个 node 离当前 CPU 近」。node_zonelists[] 就是按距离排好序的候选列表，本地 node 的 zone 排前面，remote node 的排后面。__alloc_pages_nodemask 从列表头往后找，本地找得到就不去远端。只有本地紧张时才退到远端 node，这时候延迟就上去了。NUMA 平衡（把页搬到访问它的 CPU 所在 node）是 page migration 的活，属于高级需求那一档。

ARM64 上的 NUMA 靠 ACPI 的 SRAT 表或设备树描述，node_distance[][] 给出 node 间距离矩阵。这套信息在 ARM64 内存初始化：页表、memblock 与 KASLR 里建立。

六、三种内存模型：FLAT #

memory model 这个词，说的是「从 CPU 角度看物理内存的分布形态，内核用什么方式组织 struct page 来管理它」。内核支持三种：FLAT、Discontiguous、Sparse。前提是所有 CPU 共享同一片物理地址空间。

FLAT 最简单：从任意一个 processor 看过去，物理地址空间连续、没有空洞。每个页框配一个 struct page，全系统一个数组，叫 mem_map。PFN 和 mem_map 下标的换算是一条直线，只差一个固定偏移 ARCH_PFN_OFFSET：

c
#define __pfn_to_page(pfn)    (mem_map + ((pfn) - ARCH_PFN_OFFSET))
#define __page_to_pfn(page)    ((unsigned long)((page) - mem_map) + ARCH_PFN_OFFSET)

ARCH_PFN_OFFSET 与体系结构相关，也和内存占据的物理地址区间有关。物理内存从 0 开始时它是 0，PFN 就等于数组下标。

FLAT 下还有个容易忽略的细节：node 结构仍然存在，只是一个。struct pglist_data 照样分配，NODE_DATA(0) 照样能用。这么做不是为了好看，是为了让上层代码在 FLAT 和 Discontiguous 之间切换时不用改——上层永远走 NODE_DATA() 这一条路。

另一个细节：mem_map 这块数组本身占的内存，位于直接映射（directly mapped）区间。内核虚拟地址和物理地址只差一个固定偏移，页表在初始化时就建好了，不需要为 struct page 数组再建页表。这个性质在第八章会变成一个重要差异点——SPARSEMEM_VMEMMAP 恰恰放弃了它。

FLAT 的局限很明确：物理内存有空洞就管不了。空洞来自 I/O 空间占位，或者内存热插拔留下的缺口。一旦有洞，mem_map 数组就得为洞里的 PFN 也留位置，白烧内存；洞多的时候烧得离谱。这就是 Discontiguous 和 Sparse 要解决的问题。

七、三种内存模型：Discontiguous #

物理地址空间有空洞时 FLAT 顶不住。Discontiguous 的思路是：把物理内存按 node 切开，每个 node 内部是连续的一大块，node 之间允许有洞。node 内部仍按 FLAT 那套管，所以它本质上是 FLAT 的多 node 版本。

这种模型下 struct pglist_data 有多个，每个 node 自己维护一个 struct page 数组，挂在 node_mem_map 成员上——地位等同于 FLAT 里的 mem_map。PFN 换算不再是减法，得先找 node：

c
#define __pfn_to_page(pfn)                      \
({  unsigned long __pfn = (pfn);                \
    unsigned long __nid = arch_pfn_to_nid(__pfn);  \
    NODE_DATA(__nid)->node_mem_map + arch_local_page_offset(__pfn, __nid);\
})

#define __page_to_pfn(pg)                       \
({  const struct page *__pg = (pg);             \
    struct pglist_data *__pgdat = NODE_DATA(page_to_nid(__pg)); \
    (unsigned long)(__pg - __pgdat->node_mem_map) +         \
     __pgdat->node_start_pfn;                   \
})

__pfn_to_page 三步：arch_pfn_to_nid 把 PFN 换成 node id；NODE_DATA 拿到该 node 的 pglist_data；arch_local_page_offset 算出这一页在自己 node 里的偏移，加上 node_mem_map 基址。node_start_pfn 记本 node 第一个页框号，arch_local_page_offset 就是 pfn - node_start_pfn 那类算法。

__page_to_pfn 反着走：从 page 指针减去 node_mem_map 得到 node 内偏移，加上 node_start_pfn 得到全局 PFN。这里 page_to_nid(__pg) 依赖 struct page 里已经存了 node id——Discontiguous 下 node id 存在 page->flags 的节点位段里，这就是为什么 node 数受 NODES_SHIFT 限制。

多一层 node，代价是每次换算都要先查 node；好处是 struct page 数组不用为空洞留位置，一个 node 一块，洞白留着不花钱。

关键限制：node 之间不能交错。每个 node 的物理内存必须是单独一段连续区间，node_start_pfn 加长度就能覆盖完。一个 node 的内存要是有两段，这套模型就散架了，得上 Sparse。

八、三种内存模型：Sparse #

memory model 是一路演进过来的。最早 FLAT，一个 mem_map[] 管全部；NUMA 出现后连续空间切成若干 node，一个数组变成若干个；热插拔出现后，连 node 内部的连续性都保不住了。

Sparse memory 把物理地址空间按 SECTION 切开，每个 section 独立可热插拔。section 大小由体系结构定，x86_64 上常见 128MB，ARM64 上常见 1GB（SECTION_SIZE_BITS），具体看 arch/*/include/asm/sparsemem.h。section 内部连续，符合 FLAT 的特点。

因为切分单位换成了 section，struct page 数组不再依附 node，而是依附 section：

c
struct mem_section {
    unsigned long section_mem_map;  /* 低位存 flag，其余位存 page 数组指针 */
    DECLARE_BITMAP(pageblock_flags, MAX_NR_PAGEBLOCK);  /* 用 pageblock 时才有 */
};

section_mem_map 是个打包字段，低位当标记用（section 是否 online、是否 early），高位右移几位后才是 struct page 数组地址。这种「指针塞进 unsigned long」的做法在 sparse 里到处都是。

换算从两跳变成三跳：PFN <-> Section <-> page。

PFN 到 page：内核维护一个 mem_section 指针数组。PFN 右移 PFN_SECTION_SHIFT 得到 section number，拿它当数组下标找到 section 结构，顺着 section_mem_map 找到该 section 的 page 数组，再用 section 内偏移定位具体 page。

数组形态分两种，由 CONFIG_SPARSEMEM_EXTREME 决定。非 EXTREME 时是一维 memory_section 数组；一维数组对特别稀疏的系统浪费内存，空洞越多空指针占的空间越大。EXTREME 时改成指针数组，每个元素指向一个装着若干 struct mem_section 的页。指针的好处还在于热插拔：指针等于 NULL 就表示这个 section 压根不存在，不用额外标记位。

page 到 PFN 麻烦一点。PFN 拆两部分：section index 和 page 在 section 内的偏移。得先从 page 反推 section index，找到 memory_section，算出 page 在该 section 数组里的偏移，最后合成 PFN。

从 page 反推 section 有两种方案。第一种，经典方案，把 section id 塞进 page->flags（配 SECTION_IN_PAGE_FLAGS）。问题很硬：page->flags 里的 bit 已经承载了各种 page flag、node id、zone id，再塞一个 section id，位数未必够；不同体系结构的 flag 布局不同，凑不出一致的算法。

第二种，CONFIG_SPARSEMEM_VMEMMAP，绕开 flag 位数的死结。做法是在虚拟地址空间预留一整段连续的 vmemmap 区域，每个 PFN 都对应其中固定位置的一个 struct page。这样换算退化成纯指针减法，跟 FLAT 一样干净：

c
#define __pfn_to_page(pfn)    (vmemmap + (pfn))
#define __page_to_pfn(page)   (unsigned long)((page) - vmemmap)

ARM64 的 vmemmap 定义：

c
#define vmemmap            ((struct page *)VMEMMAP_START - \
                 SECTION_ALIGN_DOWN(memstart_addr >> PAGE_SHIFT))

VMEMMAP_START 是虚拟地址空间里划给 struct page 数组的那段起点，那个 SECTION_ALIGN_DOWN(memstart_addr >> PAGE_SHIFT) 是偏移修正，处理物理内存不从 0 开始的情况。

代价要明说：经典 sparse 的 page 数组内存来自直接映射区，页表在初始化时就建好，分配 page frame 等于分配了虚拟地址；SPARSEMEM_VMEMMAP 反过来——虚拟地址一开始就全部分好，每个 page 都有它的 virtual address，但没有物理页。等某个 section 被 hotplug 上来，才去分配物理页框、建页表。所以 VMEMMAP 多一个建映射的开销，换来换算宏的极简和 flag 位的解放。

三种模型摆一起：

九、内存模型的选择：配置项与代码路径 #

三种模型不是运行时可切，是编译期选的。配置项：

配置项 作用
CONFIG_FLATMEM 选 FLAT，要求全系统物理内存连续
CONFIG_DISCONTIGMEM 选 Discontiguous，要求 node 内连续
CONFIG_SPARSEMEM 选 Sparse，section 基础结构
CONFIG_SPARSEMEM_EXTREME section 用两级指针数组，省内存，支持更稀疏
CONFIG_SPARSEMEM_VMEMMAP 用预留虚拟地址段直接算 page，避开 page flags 位置限制

CONFIG_NODES_SPAN_OTHER_NODES 允许 node 交叉（稀疏场景）

上层代码看到的接口统一，都走 include/asm-generic/memory_model.h：

c
#if defined(CONFIG_FLATMEM)
#define __pfn_to_page(pfn)    (mem_map + ((pfn) - ARCH_PFN_OFFSET))
#define __page_to_pfn(page)   ((unsigned long)((page) - mem_map) + ARCH_PFN_OFFSET)
#elif defined(CONFIG_DISCONTIGMEM)
/* 走 node_mem_map，见第七章 */
#elif defined(CONFIG_SPARSEMEM_VMEMMAP)
#define __pfn_to_page(pfn)    (vmemmap + (pfn))
#define __page_to_pfn(page)   (unsigned long)((page) - vmemmap)
#elif defined(CONFIG_SPARSEMEM)
/* 走 section，从 section_mem_map 里取 */
#endif

往上一层再包一次，屏蔽差异：page_to_pfn 就是 __page_to_pfn，pfn_to_page 就是 __pfn_to_page。

pfn_valid() 值得单独说。它判断一个 PFN 是否对应真实存在的内存，三种模型下实现完全不同：FLAT 下是范围判断（pfn >= min_low_pfn && pfn < max_low_pfn）；Discontiguous 下要逐 node 查；Sparse 下要先看 section 在不在、再看 section 是否 online。分配器、virt_to_page、热插拔、内存错误处理都要调它，是选内存模型时最该先确认的接口。

ARM64 只支持 CONFIG_SPARSEMEM 加 CONFIG_SPARSEMEM_VMEMMAP，CONFIG_FLATMEM 和 CONFIG_DISCONTIGMEM 都不提供。原因直白：ARM64 的物理内存布局由固件给，段与段之间常有洞，还支持热插拔，前两种的要求都满足不了。x86_64 同样走 CONFIG_SPARSEMEM_VMEMMAP。32 位 ARM 和早期 x86 才会用 CONFIG_FLATMEM。

CONFIG_DISCONTIGMEM 在 5.1 内核周期被移除（具体 commit hash 未验证），剩余用户全部转向 SPARSEMEM。你读 4.x 的代码会看到它，读 5.1 以后看不到，别以为是漏了。

十、伙伴系统：为什么必须是 2 的幂 #

物理页从 memblock 交给伙伴系统之后，分配的最小单位就是一页。但内核从来不按页一页页分，它按 2 的幂分：1、2、4、8……直到 1024 页。

为什么非要 2 的幂？因为回收时要能合并。分配器把相邻的两个同样大小的空闲块合成一个大块，这个过程反复递归，才能把零散页重新拼成大块。要求「两个块能从地址上判断出是兄弟」——第 n 块和第 n+1 块是 buddy——唯一干净的判据是块大小对齐到 2 的幂次。任何非 2 的幂尺寸，兄弟关系都要靠额外元数据，合并逻辑立刻变复杂。

第二个理由是硬件层面的：物理连续的大块对 TLB 和 cache 友好。内核倾向分配连续内存，因为连续意味着页表项可以复用、TLB 刷新次数少。TLB 刷得越频繁，访存越慢。伙伴系统的对齐分块天然给出「大小连续且对齐」的块，正好满足这个偏好。

MAX_ORDER 默认 11，也就是 order 0 到 10，最大单块 1024 页（4K 页下 4MB）。这个值不好往上调，因为 MAX_ORDER 影响 free_area 数组大小、pageblock_order 取值、struct page 里 order 位段的宽度。

order 与块大小（4K 页）：

0 1 4 KB 单页分配、slab 的 slab 页、页表页
1 2 8 KB 小 slab 缓存、kmalloc-8k 的 backing
2 4 16 KB kmalloc-16k、小 vmalloc 的一块
3 8 32 KB 大块 kmalloc
4 16 64 KB 页表批量分配、驱动 buffer
5 32 128 KB 网络驱动的收包环

十一、free_area 与 order #

每个 zone 里有一个 free_area 数组，下标就是 order：

c
struct free_area {
    struct list_head free_list[MIGRATE_TYPES];  /* 按可移动性再分类 */
    unsigned long nr_free;                      /* 本 order 的空闲块数 */
};

struct zone {
    ...
    struct free_area free_area[MAX_ORDER];
    ...
};

初看会以为 free_area[order] 是一条链表，实际是 MIGRATE_TYPES 条链表。为什么要按可移动性再切一刀，第十五章讲；这里只看 free_list[0] 那一维，也就是「全部空闲块」。

nr_free 记的是本 order 下空闲块的个数，不是页数。要看页数得乘 1 << order。这个区别在算总量时最容易错：pages += free_area[i].nr_free << i，忘了移位就把块数当页数了。

空闲块靠 struct page 自己的 lru 成员串联，不额外分配节点。一页进了 free_list，它的 lru.next / lru.prev 就是链表指针，private 记 order。块的第一页代表整块，后续页的 private 不参与，因为查 order 只看头页。

这套「用 page 自身存链表指针」的省法有约束：page 一旦在空闲链表里，lru 就不能挪作他用。所以 struct page 那个 union 才要精心设计——lru、slab_cache/freelist、compound_head 三套互斥使用，靠状态位区分。

order 的读写是一对 inline：page_order(page) 直接返回 page->private，set_page_order(page, order) 则 set_page_private 之后 __SetPageBuddy。PG_buddy 标志标记「这页在伙伴系统里待着」，分配出去时必须清掉，否则释放路径会以为它还在空闲链表上，重复挂链。

zone 里还有一个 pageset，per-CPU 的页缓存。order 0 的分配释放大部分走 pageset，不进 free_area，这是后文的性能关键。

十二、分配与释放的路径 #

最外层入口是 alloc_pages，往下到 __alloc_pages_nodemask。这条路分快慢两半。

快路径 get_page_from_freelist：从 node_zonelists 里按顺序取 zone，检查水位线（zone_watermark_ok），够就调 rmqueue 从 free_area 摘块。

rmqueue 先试 per-CPU 的 pageset（order 0 专线），再试 __rmqueue_smallest：

c
static inline
struct page *__rmqueue_smallest(struct zone *zone, unsigned int order,
                        int migratetype)
{
    unsigned int current_order;
    struct free_area *area;
    struct page *page;

    /* 从请求的 order 往上找，找到第一个非空的 */
    for (current_order = order; current_order < MAX_ORDER; ++current_order) {
        area = &(zone->free_area[current_order]);
        page = list_first_entry_or_null(&area->free_list[migratetype],
                            struct page, lru);
        if (!page)
            continue;
        list_del(&page->lru);
        rmv_page_order(page);
        area->nr_free--;
        expand(zone, page, order, current_order, area, migratetype);
        return page;
    }

    return NULL;
}

逻辑一句：从 order 开始往上找，找到第一个有货的 order，把那块摘下来，多出来的部分拆开还回去。拆的过程叫 expand：

c
static inline void expand(struct zone *zone, struct page *page,
    int low, int high, struct free_area *area, int migratetype)
{
    unsigned long size = 1 << high;

    while (high > low) {
        area--;
        high--;
        size >>= 1;
        list_add(&page[size].lru, &area->free_list[migratetype]);
        area->nr_free++;
        set_page_order(&page[size], high);
    }
}

拿 order 10 的块分 1 页，就一路拆：1024 拆两半，后半挂 order 9；前 512 页再拆，后半挂 order 8……直到剩 1 页。这是同一个大块被拆散的全过程，也是碎片产生的现场。

快路径失败进慢路径 __alloc_pages_slowpath，顺序是：唤醒 kswapd → 直接回收（__alloc_pages_direct_reclaim）→ 直接 compact（__alloc_pages_direct_compact）→ 重试 → 还不行就 OOM。reclaim 和 compact 分工不同：一个回收不一定要占着的缓冲内存，一个把可挪页搬拢换来连续块（第十四章）。先回收再压缩有讲究——回收能腾出整页，压缩只是挪位置，先回收能少挪几下。

释放路径是 __free_pages 到 free_pages_prepare 再到 __free_one_page。核心是合并：

c
static inline void __free_one_page(struct page *page,
        unsigned long pfn, struct zone *zone, unsigned int order,
        int migratetype)
{
    unsigned long buddy_pfn;
    struct page *buddy;

    while (order < MAX_ORDER - 1) {
        buddy_pfn = __find_buddy_pfn(pfn, order);
        buddy = page + (buddy_pfn - pfn);

        if (!pfn_valid_within(buddy_pfn))
            goto done_merging;
        if (!page_is_buddy(page, buddy, order))
            goto done_merging;
        /* 和 buddy 合并，order 加一，继续往上试 */
        list_del(&buddy->lru);
        zone->free_area[order].nr_free--;
        rmv_page_order(buddy);
        pfn &= ~(1 << order);
        order++;
    }
done_merging:
    set_page_order(page, order);
    list_add(&page->lru, &zone->free_area[order].free_list[migratetype]);
    zone->free_area[order].nr_free++;
}

__find_buddy_pfn 是全部魔法的浓缩：buddy_pfn = pfn ^ (1 << order)。异或把第 order 位翻转，正好指向兄弟块。这一行能成立，唯一前提就是块大小是 2 的幂且自然对齐——回到第十章的问题。

合并只在同一 zone 内进行，不跨 zone。zone 的边界是硬边界，两个相邻页框分属不同 zone 时，即使地址连续也不会合并成跨 zone 的块。

十三、碎片是怎么产生的 #

碎片有两类，成因完全不同。

内部碎片：分配器给的块比你要的大，多出来的部分你用不上。伙伴系统分 8 页给你，你只要 5 页，3 页浪费。slab 缓解的就是这一类——把一页切成一堆小对象，按实际大小发。

外部碎片：总空闲内存足够，但没有足够大的连续块。系统有 100 页空闲，分布在 100 个不连续位置，你要 order 8（256 页），照样失败。伙伴系统缓解但消不干净这一类。

外部碎片怎么长出来的，跟第十二章那个 expand 直接相关。每次从大块拆小块，都会在某个 order 上留下一条孤立的链表项。反复拆、反复还，同一个 order 上就堆满大小相同但地址不相邻的碎片。

举个具体的：order 10 的一个块（1024 页），先分走 1 页，留下 order 9、8、7……各一个块，外加最后 1 页被占。此时再分 4 页（order 2），又从某个 order 3 的块里拆。来回几次，order 10 的空闲块数变成 0，order 0 到 9 都攒着零散块。这时要 order 10 就是失败，尽管总空闲页数还有 500。

更麻烦的一层是页面类型混住。内核分配的页（页表、slab、驱动 buffer）位置固定不能挪，用户页（匿名页、file cache）可以挪。两者交叉分布之后，即使可挪的部分很多，也被不可挪的页钉在原地，拼不出大块。第六章那句「物理内存不是均质的」，到碎片这里变成第二重不均质：不只是地址能力不均质，可移动性也不均质。

内核的反应分三个层次，对应后面三章：ZONE_MOVABLE 做粗粒度分区（2.6.24 前后），把可挪的和不可挪的物理隔开；migrate type 做 zone 内的细粒度分桶，让同类页聚集；compaction 在分配失败时做运行时搬迁，把可挪页搬到一起腾出连续块（2.6.35 前后）。三者不是替代关系，是叠加的。

十四、碎片防治之一：低内存时整合碎片（compaction） #

从 buddy 要内存要不到时，内核做两步调整：compact 和 reclaim。前者整合碎片，把零散的可挪页搬到一起腾出连续块；后者回收那些不一定要占着的缓冲内存。这章只看 compact。

调用链：

text
__alloc_pages_nodemask
-> __alloc_pages_slowpath
-> __alloc_pages_direct_compact
-> try_to_compact_pages
                -> compact_zone_order
                    -> compact_zone
                        -> isolate_migratepages
                        -> migrate_pages
                        -> release_freepages

不是所有分配失败都触发 compact，得同时满足几个条件：

条件 说明
order > 0 只要单页的分配，碎片不影响成败，没必要搬
gfp_mask 带 __GFP_FS 和 __GFP_IO 搬迁要写回脏页、要读文件，缺这两个标志没法搬
gfp_mask 不带 __GFP_NOCOMPACT 调用方显式拒绝压缩
碎片指数大于阈值 见下

碎片指数（fragmentation index）衡量「这次失败是内存不够还是碎片闹的」，取值 0 到 1000。默认阈值 500，碎片指数超过 500 才值得压缩；低于这个值说明是纯粹缺内存，压了也白压。阈值在 /proc/sys/vm/extfrag_threshold：

c
/*
 * Index is between 0 and 1000
 *
 * 0 => allocation would fail due to lack of memory
 * 1000 => allocation would fail due to fragmentation
 */
return 1000 - div_u64( (1000+(div_u64(info->free_pages * 1000ULL, requested))), info->free_blocks_total)

free_pages 是 zone 总空闲页，requested 是这次要的页数，free_blocks_total 是各 order 上空闲块的总数。free_pages / requested 表示「按页数算够不够」，free_blocks_total 越大说明块越碎，两项一除，碎得越厉害指数越接近 1000。

搬迁只在一个 zone 内部进行，不跨 zone。方向有讲究：把 zone 低地址的页尽量往 zone 末端挪，让空闲块在低地址端聚成大块。申请新位置由 compaction_alloc 负责，它从 zone 末尾往前找空闲页。

搬迁分同步和异步。内存申请失败后第一次 compact 走异步，后面 reclaim 之后再试的那次走同步。同步只搬当前没被使用的页，遇到正在用的就跳过；异步会遍历并等所有 MOVABLE 页用完之后再搬。异步搬得干净，但会卡住分配路径；同步快，但搬不动的页就跳过了。

搬一页不是拷内存就完了，页表项得跟着改。这套映射信息从哪来？从 page->mapping 出发，靠 rmap 找到所有映射了这页的页表项，逐个改写。匿名页挂在 anon_vma 上，文件页挂在 address_space 的 i_mmap 上。这套机制是 页面回收与逆向映射 的主体，compaction 只是它的一个使用者。反向映射要是坏了，compaction 会把页搬到新地址，页表还指着老地址，进程下次访问就崩。

十五、碎片防治之二：按可移动性组织页（migrate type） #

按可移动性，物理页分三类：

migrate type 含义 典型页
MIGRATE_UNMOVABLE 位置固定，不能随便挪 内核分配的内存：slab、页表、驱动 buffer、内核栈
MIGRATE_RECLAIMABLE 不能挪，但能删掉回收 文件映射页、可回收的 dentry/inode 缓存
MIGRATE_MOVABLE 可以随便挪 用户空间内存：匿名页、page cache

4.x 之后还多两个：MIGRATE_CMA（CONFIG_CMA，CMA 预留区专用）、MIGRATE_ISOLATE（CONFIG_MEMORY_ISOLATION，热拔插时临时隔离），再加 MIGRATE_RESERVE（预留区）。新版本还加了 MIGRATE_HIGHATOMIC（给原子分配留的高阶块，4.13 之后），MIGRATE_TYPES 总数随版本变，别写死。

思路直白：申请时按可移动性先在对应类型的空闲页里找，尽量让同类页聚集。聚集之后，可挪的那一片就真能挪，compaction 有活干。数据结构的体现就是 free_list 从一条变成 MIGRATE_TYPES 条（结构见第十一章）。

指定类型里找不到货怎么办？从备用类型挪用。挪用之后这块页归到新类型链表里，内核管这个动作叫「盗用」。备用类型的优先级是张静态表：

c
static int fallbacks[MIGRATE_TYPES][4] = {
    [MIGRATE_UNMOVABLE]   = { MIGRATE_RECLAIMABLE, MIGRATE_MOVABLE,     MIGRATE_RESERVE },
    [MIGRATE_RECLAIMABLE] = { MIGRATE_UNMOVABLE,   MIGRATE_MOVABLE,     MIGRATE_RESERVE },
#ifdef CONFIG_CMA
    [MIGRATE_MOVABLE]     = { MIGRATE_CMA,         MIGRATE_RECLAIMABLE, MIGRATE_UNMOVABLE, MIGRATE_RESERVE },
    [MIGRATE_CMA]         = { MIGRATE_RESERVE }, /* Never used */
#else
    [MIGRATE_MOVABLE]     = { MIGRATE_RECLAIMABLE, MIGRATE_UNMOVABLE,   MIGRATE_RESERVE },
#endif
    [MIGRATE_RESERVE]     = { MIGRATE_RESERVE }, /* Never used */
#ifdef CONFIG_MEMORY_ISOLATION
    [MIGRATE_ISOLATE]     = { MIGRATE_RESERVE }, /* Never used */
#endif
};

MIGRATE_MOVABLE 优先盗 MIGRATE_CMA，不是反过来。CMA 预留区本来就是给可移动页准备的，用户页借它用最合适；CMA 自己的分配直接用 MIGRATE_RESERVE，因为它不做 fallback 循环。表里第二维是 4，因为 MIGRATE_TYPES 是 5 的时候，除了自己还剩 4 个候选。

不是所有场景都适合按可移动性组织页。机器内存小到每种类型都分不到几个 pageblock 时，分组反而浪费——每类都留一块，块内又填不满。有个全局变量表示分组是否启用，内存初始化时定：

c

{
......

        page_group_by_mobility_disabled = 1;
    else
        page_group_by_mobility_disabled = 0;
......
}

总页数不够每类分一个 pageblock，就关掉分组。关掉之后 free_list 的索引全部退化为 0，所有页按 MIGRATE_UNMOVABLE 对待，migratetype 这套失效。

pageblock 是分组的最小单位，也就是「至少连续多少页才值得归一类」：

#endif /* CONFIG_HUGETLB_PAGE */

系统初始化时所有 pageblock 先全部标成 MIGRATE_MOVABLE。这段逻辑在 memmap_init_zone 里，判定条件写在一个 if 里：

十六、碎片防治之三：虚拟可移动内存域（ZONE_MOVABLE） #

在 migrate type 之前，内核先用了个更粗的办法：ZONE_MOVABLE。思路简单——把内存劈成两半，可移动的一半和不可移动的一半，物理上就隔开。

它是 zone 枚举里的一个成员（见第四章）。启用靠内核命令行参数：kernelcore= 指定不可移动内存的数量，movablecore= 指定可移动内存的大小。两个都给时，取不可移动内存数量较大的那一个——保守起见，先保证内核有地方站。都不给，ZONE_MOVABLE 不启用。

它和别的 zone 有个本质区别：ZONE_MOVABLE 不关联任何一段自己的物理地址范围。它的内存从高端内存域或者普通内存域划出来，不是独立的一段地址。所以 /proc/zoneinfo 里 ZONE_MOVABLE 的 pfn 范围和相邻 zone 重叠不奇怪——它借的是别人的地址，只是在分配器里另开了一本账。

划多少、从哪划，由 find_zone_movable_pfns_for_nodes 算每个 node 里 ZONE_MOVABLE 的页框范围和数量，find_usable_zone_for_movable 挑出该 node 里可以用来划的那个 zone。可用 zone 取每个 node 的最高内存域，理由是：高地址的页本来就不适合固定映射（32 位系统下 HighMem 尤其如此），拿去做可移动页最不浪费。

kernelcore 在多 node 间平均分：kernelcore_node = required_kernelcore / usable_nodes;。usable_nodes 是能划出 ZONE_MOVABLE 的 node 数，不是全部 node。内存特别小的 node 划不出来，会被跳过。

分配时怎么进这个域？看 gfp 标志：gfp_flag 同时带 __GFP_HIGHMEM 和 __GFP_MOVABLE，就从 ZONE_MOVABLE 申请。用户态的匿名页和 file cache 走的就是这条路——GFP_HIGHUSER_MOVABLE 里两个标志都在。

ZONE_MOVABLE 的直接用途是内存热拔插和热移除：整个 zone 里全是可挪页，拔之前把它们搬走就行，没有搬不动的钉子户。它顺带也降低碎片风险，但不解决「同一个 zone 内混住」的问题，那是 migrate type 的活。

手段 粒度 何时生效 解决什么

十七、从伙伴系统往上：slab / kmalloc / vmalloc 各自的位置 #

伙伴系统分到的是页，最小 4KB。内核实际要的东西大多比页小得多：一个 file 结构体、一个进程描述符、一个 VMA 描述符，几十到几百字节。要是每次都按页要，4KB 里用 64 字节，剩下 4032 字节全废——这是内部碎片。

层次先分清，不然容易乱：最上面是用户进程和它的虚拟地址空间（页表、VMA 管）；中间隔着缺页异常和系统调用这条线；跨过这条线，内核才开始碰物理页，用的是 vmalloc、kmalloc、__get_free_pages 三套接口；其中 kmalloc 底下垫着 slab 分配器，slab 和 __get_free_pages 再往下都落到伙伴系统，最终是物理页框 struct page。

用户态的 malloc 在内核里对应的是「扩大堆」——brk 调整进程堆边界，按页大小的倍数改。但 brk 只改了 VMA 范围，物理页要等真正访问、触发缺页异常时才分配。malloc 返回的地址背后一页物理内存都还没有。这条线和 __get_free_pages 完全不是一回事：后者直接要物理页，要到就有。

slab 坐在伙伴系统上面，干的事是「把一页切成很多小对象」。核心是个存储池：对象用完不还给伙伴系统，放回池子等下次复用。收益有两个——减少 buddy 调用次数（buddy 一调就是整页，容易加剧外部碎片），让对象在 cache line 上排布更规整。slab 不独立于伙伴系统存在，它的「页」还是从 buddy 拿的。对象级接口是 kmem_cache_alloc / kmem_cache_free。三种实现（slab / slub / slob）的取舍、per-cpu freelist、ctor、debug 选项，全在 slab 与 slub 分配器。

kmalloc 是 slab 的一个门面：小内存走 slab 缓存，超过一定大小直接找 buddy 要页。粒度从几字节到 128KB（KMALLOC_MAX_CACHE_SIZE）。它和 __get_free_pages 互补不是替代：前者按字节要不保证页对齐、走 slab；后者按 order 要、页对齐、直接给物理连续页。要 DMA、要页表、要自己管页的场合用后者。/proc/slabinfo 里能看到各类 slab 的统计，除专用结构体的缓存，还有一堆 kmalloc-*。

外部碎片的终局方案是「别要求物理连续」：在虚拟地址空间要一段连续区间，背后映射到散落的物理页。用户态的虚拟内存就这么干，内核借了同一招。vmalloc 给的虚拟地址连续、物理页不连续，能分配比 kmalloc 大得多（128K 以上）的空间，代价是必须动内核页表：

c
void *vmalloc(unsigned long size);
void vfree(const void *addr);

size 向上取整到页大小的倍数。每块 vmalloc 区间配一个 vm_struct 描述符，记起始地址和长度。别和 vm_area_struct 搞混——后者是用户进程的 VMA，前者是内核的 vmalloc 区间，页表也不同：vm_struct 靠内核页表（init_mm，根是 swapper_pg_dir），vm_area_struct 靠进程页表。vmalloc 区间之间留 4KB 空洞防越界。因为物理页散落，返回的地址和物理地址之间没有固定偏移，virt_to_phys() 对它无效，要拿物理地址得走页表。

十八、内核虚拟地址空间的划分 #

几套分配器能并存不打架，前提是内核虚拟地址空间做过分区，各自待在各自区间里，互不重叠。32 位 x86 是经典布局，讲它最好懂：

区间 范围 放什么
用户空间 0 到 3GB 进程自己的代码、数据、堆、栈、mmap
直接映射区 3GB 到 vmalloc_start 内核镜像、mem_map、所有物理页的直接映射
vmalloc 区 vmalloc_start 到 vmalloc_end vmalloc、ioremap、模块加载
保留区 4GB 附近 固定映射、高端内存临时映射

3GB 这个边界就是 PAGE_OFFSET，x86 32 位上是 0xC0000000。直接映射区从这开始，长度等于实际物理内存：机器有 64MB 内存（free 能看到），这段就映射 3GB 到 3GB+64MB。

vmalloc_start 在 3GB+64MB 附近，中间留约 8MB 空隙。这 8MB 是防护带：直接映射区按物理内存大小伸缩，物理内存多一点它就长一点，不隔开就会跟 vmalloc 区撞上。vmalloc_end 靠近 4GB，但要留尾巴：末尾保留 128KB 专用映射区（fixmap 那一片），再往下是高端内存的临时映射窗口。

直接映射区最讨人喜欢的性质：虚拟地址和物理地址只差一个固定偏移 PAGE_OFFSET。virt_to_phys() 就是干这个的：

c
#define __pa(x)     ((unsigned long)(x) - PAGE_OFFSET)
#define __va(x)     ((void *)((unsigned long)(x) + PAGE_OFFSET))

这个性质只在直接映射区成立。get_free_page 和 kmalloc 拿到的内存都在直接映射区，页表在初始化时就建好了，分配时不用动页表。vmalloc 拿到的在 vmalloc 区，地址和物理地址没有简单关系，__pa() 用上去就是错的，每次分配都要新建页表项——这是它慢的根源。

64 位平台这套布局就不适用了，虚拟地址空间太大，内核不用挤在 1GB 里：

平台 直接映射 vmalloc 区 vmemmap
x86_64 page_offset_base 起，覆盖全部物理内存 VMALLOC_START 到 VMALLOC_END VMEMMAP_START 一段
ARM64 PAGE_OFFSET 起，VA_BITS 决定大小 VMALLOC_START 独立区间 VMEMMAP_START 独立区间

64 位下没有 ZONE_HIGHMEM，因为直接映射区装得下全部物理内存。ARM64 的具体布局、VA_BITS 的取舍、线性映射的建立过程，在 ARM64 内存初始化：页表、memblock 与 KASLR 和 地址空间与地址翻译。

用一段模块代码把三个分配器落到的区间看一遍：

c
#include <linux/module.h>
#include <linux/slab.h>
#include <linux/vmalloc.h>
#include <linux/gfp.h>

static unsigned long pagemem;
static void *kmallocmem, *vmallocmem;

static int __init memdemo_init(void)
{
    pagemem = __get_free_page(GFP_KERNEL);
    if (!pagemem)
        return -ENOMEM;
    pr_info("page    va=%px\n", (void *)pagemem);

    kmallocmem = kmalloc(100, GFP_KERNEL);
    if (!kmallocmem)
        goto err_page;
    pr_info("kmalloc va=%px\n", kmallocmem);

    vmallocmem = vmalloc(1000000);
    if (!vmallocmem)
        goto err_kmalloc;
    pr_info("vmalloc va=%px\n", vmallocmem);
    return 0;

err_kmalloc:
    kfree(kmallocmem);
err_page:
    free_page(pagemem);
    return -ENOMEM;
}

static void __exit memdemo_exit(void)
{
    vfree(vmallocmem);
    kfree(kmallocmem);
    free_page(pagemem);
}

三段输出对比着看：page 和 kmalloc 的地址挨着，都在直接映射区，数值上减 PAGE_OFFSET 就是物理地址；vmalloc 的地址在另一片，跟物理地址没有任何简单关系。

实例：把 vmalloc 出来的内核虚拟地址映射给用户进程 #

这是个老例子，但把几层的关系串得很清楚：内核里 vmalloc 一段空间写点数据，再让用户进程通过 mmap 读到同样的内容。难点在于——vmalloc 的物理页是散的，映射给用户时没法用「物理地址 + 偏移」一把梭。

三方各是什么：用户侧 vm_area_struct，进程的 VMA；内核侧 vm_struct，vmalloc 区间描述符，不是 VMA；底下是物理页框，vmalloc 从 buddy 一页页要来，彼此不相邻。

做法是写个虚拟字符驱动，文件操作表里实现 mmap。mmap 被用户调 mmap() 时触发，那时内核已为用户建好 VMA，剩下的事是把 VMA 和物理页连起来。

不能一次把页表全建好，因为 vmalloc 的物理页在分配前不确定，只能挂一个 nopage（新内核里是 fault），等缺页时动态建。所以驱动里的 mmap 只干一件事：给 VMA 绑上 vm_operations_struct。

c
static int mapdrv_mmap(struct file *file, struct vm_area_struct *vma)
{
    vma->vm_ops = &mapdrv_vm_ops;
    vma->vm_flags |= VM_DONTEXPAND | VM_DONTDUMP;
    return 0;
}

nopage 里的活是「找到 vk 地址对应的内核逻辑地址」，三步：定位 vmalloc 虚拟地址所在的内核页表项（init_mm 的页表，走 pgd → pud → pmd → pte）；从页表项取出 struct page *；从 page 得到能直接访问的地址。这三步 vmalloc_to_page() 已经封装好，自己写 vaddr_to_kaddr() 没必要——老例子手写页表遍历，是因为当年没这个 helper。

c
static struct page *mapdrv_nopage(struct vm_area_struct *vma,
                                  unsigned long vaddr, int *type)
{
    unsigned long vk = vma->vm_private_data + (vaddr - vma->vm_start);
    struct page *page = vmalloc_to_page((void *)vk);

    if (!page)
        return NOPAGE_SIGBUS;      /* 新内核返回 VM_FAULT_SIGBUS */
    get_page(page);
    if (type)
        *type = VM_FAULT_MINOR;
    return page;
}

grep mapdrv /proc/devices                               # 查设备号
mknod /dev/mapfile c 254 0                              # 建设备文件

maptest 读到的内容应该就是驱动在 vmalloc 空间里写的那串字符。读到就说明用户页表成功指向了那段散落的物理页。

老例子的坑得指出来：get_free_page(0) 早没了（见附）；remap_page_range 在 2.6.11 之后被 remap_pfn_range 取代；nopage 在 4.6 之后统一成 fault（传 vm_fault 结构）；设备号别写死 254，按 grep mapdrv /proc/devices 的输出填；vmalloc 区的地址过 virt_to_phys() 是错的，得走 vmalloc_to_page() 再 page_to_phys()。

十九、易错点速查 #

按踩坑频率排，都是从上面内容里直接推出来的。

PFN 不是物理地址右移。 只有物理内存从 0 开始时 PFN 才等于 pa >> PAGE_SHIFT。内存从 PHYS_OFFSET 开始的话，第一个页框号是 PHYS_OFFSET >> PAGE_SHIFT，FLAT 下靠 ARCH_PFN_OFFSET 补差。ARM64 的 memstart_addr 起决定作用。

nr_free 是块数不是页数。 算总页数要 nr_free << order。漏了移位，算出来的空闲内存会小好几个数量级。

struct page 数组不一定在直接映射区。 FLAT 和经典 SPARSE 下它在直接映射区，页表初始化时就建好；SPARSEMEM_VMEMMAP 下它在一段预留虚拟地址里，物理页按 section 到位才分配。这直接影响「分配 page frame 是否等于分配虚拟地址」这个判断。

ZONE_HIGHMEM 在 64 位上不存在。 它的存在条件是虚拟地址空间装不下物理内存，这个前提在 64 位下不成立。ARM64 的 /proc/zoneinfo 里没有 HighMem 是正常的。

ZONE_MOVABLE 不是一段物理地址。 它不关联自己的地址范围，pfn 和相邻 zone 重叠也正常。别拿 /proc/zoneinfo 里的 pfn 范围去推算它的物理位置。

SECTION_SIZE 不是固定 1GB。 由各体系结构的 SECTION_SIZE_BITS 决定，x86_64 常见 128MB，ARM64 常见 1GB。判断 section 边界一律用 SECTION_SIZE / PFN_SECTION_SHIFT 宏，别写常量。

order 0 的分配不走 free_area。 单页分配优先走 per-CPU 的 pageset。看到 free_area[0].nr_free 为 0 不代表不能分配单页。

page->private 是复用的。 页在 buddy 里时它存 order，在 buffer_head 里时存别的，在 slab 页里另有用途。读它之前先确认页的状态，别当通用字段用。

migrate type 不是 zone。 migratetype 是 pageblock 级的逻辑标签，区分可移动性；zone 是物理能力边界，区分 DMA 能力和可映射性。两者正交，一个 zone 里可以有各种 migratetype 的页。

compaction 不跨 zone。 它只在一个 zone 内搬页。两个 zone 各自有 100MB 空闲但都不连续时，压缩不出跨 zone 的 200MB 块。

关闭分组的机器上 migratetype 全是摆设。 page_group_by_mobility_disabled = 1 时所有页按不可移动对待，fallsback 表和分桶都失效。小内存机器上看到 MIGRATE_MOVABLE 为 0 不奇怪。

__pa() 只能用在直接映射区。 vmalloc 区、ioremap 区的地址过 __pa() 得到的是垃圾，这些区要转物理地址得走页表。

malloc 和 __get_free_pages 不在一个层面。 前者是用户态堆管理器切字节，背后是 brk/mmap 加缺页异常；后者直接向 buddy 要物理页。拿两者比「粒度粗细」是把层次搞混了。

老接口名要认。 get_free_page → __get_free_page，get_free_pages → __get_free_pages，remap_page_range → remap_pfn_range，nopage → fault，page->_count → page->_refcount。看到老名字先确认内核版本。
