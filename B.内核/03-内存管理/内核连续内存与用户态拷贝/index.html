这篇只回答一个问题：内核跟「不连续的物理内存」和「用户态递过来的指针」打交道时，活是怎么干完的。三条线拧在一起：想要一大块物理连续内存，系统碎得给不出来，于是有 CMA；没有连续内存但设备能接受分散的段数组，于是有 scatterlist；用户给的地址不能拿来就解引用，于是有 copy_{to,from}_user()。

讲什么：4.4.6 的 CMA 全链路（struct cma、bitmap 记账、两种配置方式、与 memblock 和伙伴系统的初始化顺序、cma_alloc 的迁移路径、使用限制）；scatterlist 与 sg_table 的字段语义、链式组织、API；4.18.0 + ARM64 的 uaccess 实现、access_ok、.fixup 与 __ex_table、PAN/UAO、返回值语义。 不讲什么：伙伴系统内部的页框分裂与 pageblock 记账、huge page 的预留与拆分、IOMMU 页表格式、具体 SoC 的 DMA 通道能力。

一、连续内存为什么难得 #

伙伴系统只认 order。它给你 2^order 个物理连续页框：order=0 一个页，order=10 一片 4MB。分配器不关心你拿这片页干什么，只关心碎片够不够拼出这个 order。

碎片来源很朴素：系统跑久了，页被切碎、释放、再切碎。一个 order=10 的请求要成功，得有一整段没被占的 4MB 空窗。中间被塞进几个 order=0 分配，这个 order 就废了，只能等 compaction 或回收腾地方。回收能救一部分，被 pin 住的页救不回来。刚性需求主要两类：huge page，2MB 的页要求 512 个连续 4K 页框且首地址对齐到 2MB；驱动的大块 DMA buffer，摄像、视频、音频一次搬几十 MB，嵌入式板子上没 IOMMU，DMA 控制器也不支持 scatter-gather，那就只有一条路——物理地址必须连续。

难的是第二类。huge page 有 hugetlb 预留池顶着，驱动没有。启动时预留一块，可靠，但 camera 一年用不了几次，剩下时间内存白躺着；用的时候再分，省内存，但碎片化之后分不出来，camera 直接功能缺失。这就是 CMA 要填的坑：平时别人能用，要的时候让出来。第九章讲它怎么「让」。

二、三种拿到连续内存的办法：启动时预留、CMA、huge page #

第一条，启动时直接扣下来。走 device tree 的 reserved-memory 节点或 memblock_reserve()。这块内存从此不进伙伴系统。可靠、简单，代价是永远闲置。

第二条，CMA。启动时同样划一段，但这段的页最终交给伙伴系统并标成 MIGRATE_CMA。别人可以借用，只限可迁移页；驱动来要，就把借出去的搬走，腾出一整段连续的。

第三条，huge page。hugetlb 有独立预留池（hugepages=），也能运行时从伙伴系统凑。页大小固定（2MB、1GB），对齐要求苛刻，接口是另一套（hugetlbfs、mmap(MAP_HUGETLB)）。

维度 启动时预留 CMA huge page
谁在用 特定驱动、固件、共享内存 DMA mapping framework → 驱动 hugetlbfs、alloc_huge_page
能否复用 不能 空闲时可被内核借用（限可迁移页） 预留池闲置，surplus 页可由伙伴系统凑
对齐要求 无统一要求 由 cma_alloc 的 align 参数给 必须按页大小对齐（2MB 页要 2MB 对齐）
分配粒度 随便切 按 order_per_bit 记账，按 count 给页 整页给
失败典型原因 不会失败（已经扣下） 迁移不掉被 pin 的页 凑不出对齐的连续段
接口 memblock_reserve、dma_declare_coherent_memory cma_alloc / cma_release，驱动侧走 dma_alloc_coherent hugetlb_reserve_pages、alloc_huge_page

取舍一句话：能不能容忍「平时借给别人，用时被搬走」。能容忍就 CMA，不能就启动预留，要固定大页语义就 huge page。本篇只讲 CMA。

三、CMA 是什么，解决的是谁的困境 #

CMA，Contiguous Memory Allocator，内存管理子系统里负责物理地址连续内存分配的模块。职责边界很清楚，四件事：解析 device tree 或命令行参数确定 area 位置和大小；提供 cma_alloc 和 cma_release；用 bitmap 跟踪 area 内各页状态；需要真内存时调伙伴系统的 alloc_contig_range。

它是「需要连续内存的模块」和「内存管理模块」之间的中间层。最典型的调用方是 DMA mapping framework——驱动不直接调 cma_alloc，而是走 dma_alloc_coherent 之类，由 DMA 层决定要不要落到 CMA。困境长这样：摄像头 1300 万像素、一像素 3 字节，拍一张要 13M × 3B ≈ 39MB。（旧稿写 26MB，算错了，见文末勘误。）

  • 启动时把 39MB 扣下来：可靠，但 camera 大部分时间空闲，39MB 白躺，小内存板子上是硬伤。
  • 用时再分配：省内存，但跑久了碎片化，大块连续分配越来越难，一旦失败 camera 就没了。

Michal Nazarewicz 的 CMA 补丁来终结这个两难：不用的时候给内核别人用，驱动来要就把借出去的页搬走，拼成物理连续的一大块交出去。注意「搬走」这个词——全部魔法压在「这些页的数据可以被搬」这个前提上，第九、十章反复回到这一点。

四、struct cma 与 bitmap 管理 #

一个 CMA area 用一个 struct cma 抽象，4.4.6 的定义：

c
struct cma {
    unsigned long   base_pfn;
    unsigned long   count;
    unsigned long   *bitmap;
    unsigned int    order_per_bit; /* Order of pages represented by one bit */
    struct mutex    lock;
};
字段 含义 备注
base_pfn area 起始 page frame number 与 count 一起定位 area 在物理内存中的位置
count area 有多少个 page 和 order_per_bit 一起决定 bitmap 多大
bitmap 分配位图，0 空闲、1 已分配 cma_activate_area 里 kzalloc 出来
order_per_bit 一个 bit 代表 2^order_per_bit 个页 0 按单页记账，1 按 2 页一块记账
lock 保护 bitmap 与 area 状态 cma_alloc / cma_release 全程持锁

bitmap 粒度由 order_per_bit 决定，这是 CMA 唯一一处「算法设计」。粒度放大，bitmap 省内存，但小分配浪费；粒度单页，bitmap 占得多。4.4.6 里它由 cma_init_reserved_mem 的参数传进来。

多个 area 存在一个全局数组里：

c
struct cma cma_areas[MAX_CMA_AREAS];

MAX_CMA_AREAS 编译时定死。每个 struct cma 代表一段物理连续的 memory area，cma_alloc 分出来的连续内存就是从某个 area 里切的。几个区怎么划是系统设计问题：可以给某驱动独占，也可以只建一个通用区给多个驱动共享。本篇主攻共享的 Global CMA。

五、CMA area 的配置：命令行与 reserved-memory #

1、device tree 的 reserved-memory #

reserved-memory 的 child 里定义各种保留内存。compatible = "shared-dma-pool" 的 child 建 Global CMA area，其余 child 是 per-device CMA。

c
RESERVEDMEM_OF_DECLARE(cma, "shared-dma-pool", rmem_cma_setup);

RESERVEDMEM_OF_DECLARE 往一个专门的 section 塞 match 项，初始化时内核扫这个 section，compatible 对上了调 rmem_cma_setup。setup 不复杂：拿到起始地址和大小，调 cma_init_reserved_mem 注册。

两个属性必须盯住：reusable 要有，no-map 不能有。

  • reusable 的语义就是 CMA 的语义：驱动不用时 OS 能用（有条件），驱动来分配时 OS 要把页交出去。
  • no-map 和地址映射有关。没它，OS 建正常映射当普通内存用；有它，OS 不建映射，留给驱动自己 ioremap。问题是 OS 已映射、驱动又映射一次，同一物理地址对应两个虚拟地址，ARMv6 之后的 CPU 上后果不可预期。CMA 反着来：reserved memory 必须映射好，才能拿去做 page cache。

2、命令行与内核配置 #

bash
cma=nn[MG]@[start[MG][-end[MG]]]

cma=64M                              # 64MB，位置由内核挑
cma=64M@0x30000000                   # 64MB，固定在 0x30000000
cma=64M@0x30000000-0x40000000        # 64MB，在这个区间里找

初始化时解析这个参数，调 cma_declare_contiguous 注册，最后和 device tree 那条路一起汇到 cma_init_reserved_mem。per-device CMA 跟具体驱动绑定，最终落到 dma_declare_contiguous。

内核配置也能定 Global CMA 大小：CONFIG_CMA_SIZE_MBYTES（固定 MB 数）和 CONFIG_CMA_SIZE_PERCENTAGE（占内存百分比），二选一，由 CONFIG_CMA_SIZE_SEL_* 决定。

优先级记牢：device tree 优先于命令行。device tree 已经定了 Global CMA，命令行参数就不起作用，dma_contiguous_reserve 什么都不做。

六、Global CMA 与 per-device CMA #

两种 area，区别只在「谁能用」。

Global CMA 所有驱动共享，靠命令行、内核配置或 shared-dma-pool 节点建立；驱动走通用 DMA 路径、内存不够时就往这里落。per-device CMA 由一两个指定驱动独占，靠 reserved-memory 里带设备 phandle 的 child 节点建立，存在的理由是隔离——某些驱动不想跟别人抢，怕关键时刻分不到。

维度 Global CMA per-device CMA
建立方式 cma= 命令行、内核配置、shared-dma-pool 节点 reserved-memory 下带设备引用的 child 节点
注册入口 cma_declare_contiguous → cma_init_reserved_mem dma_declare_contiguous（驱动侧）
使用者 所有走通用 DMA 路径的设备 绑定的那个设备
典型场景 一堆小设备凑合用一块 camera、GPU、视频编解码这类吃大块的

per-device area 也占 MAX_CMA_AREAS 的名额。板子上设备多、area 划得碎，容易撞上限。撞了之后新 area 注册失败，只在启动日志里留一行，不会让系统起不来，很容易漏掉。

七、CMA、memblock、伙伴系统的初始化顺序 #

套一句广告词：CMA 不做内存管理，它只是内存管理机制的搬运工。area 的页最终必须并进伙伴系统，所以初始化要卡在合适的时机、用合适的方式插进 memblock 和伙伴系统的流程。

memblock 阶段先确定整个系统的内存布局：哪些 block 是 memory type，哪些是 reserved type。CMA area 属于 reserved type。

text
# 1) 建立 memory type 区间
setup_arch -> setup_machine_fdt -> early_init_dt_scan
  -> early_init_dt_scan_nodes -> memblock_add

# 2) 建立 reserved type 区间
setup_arch -> arm64_memblock_init -> early_init_fdt_scan_reserved_mem
  -> __fdt_scan_reserved_mem -> memblock_reserve

# 3) 调 handler：扫 RESERVEDMEM_OF_DECLARE 塞进去的那个 section
setup_arch -> arm64_memblock_init -> early_init_fdt_scan_reserved_mem
  -> fdt_init_reserved_mem -> __reserved_mem_init_node -> rmem_cma_setup

# 4) 命令行补位
setup_arch -> arm64_memblock_init -> dma_contiguous_reserve

# 5) 移交伙伴系统
start_kernel -> mm_init -> mem_init -> free_all_bootmem
  -> free_low_memory_core_early -> __free_memory_core

# 6) 激活 CMA area，把页挂进伙伴系统
core_initcall(cma_init_reserved_areas)

第 4 步经常什么都没干。没配命令行也没配内核配置 → 不建 Global CMA，直接返回；device tree 已经设了 → 不再 reserve。只有「配了命令行、device tree 没设」时才真干活，再分两种：参数给了确定地址就 memblock_reserve，只给了大小就 memblock_alloc_range 让 memblock 找一段。

第 5 步把 free memory 释放进伙伴系统，reserved memory 不进。CMA area 特殊：它的页必须进伙伴系统，否则别人借不到，所以有单独的第 6 步。顺序上一句话总结：

阶段 干什么 关键函数
memblock 建内存块 认领 memory type 区间 memblock_add
memblock 建保留区 把 reserved-memory 标成 reserved memblock_reserve
调 handler 匹配 shared-dma-pool，注册 area rmem_cma_setup → cma_init_reserved_mem
命令行补位 命令行/内核配置兜底 dma_contiguous_reserve
移交伙伴系统 free 页进伙伴系统 free_low_memory_core_early
激活 CMA area 的页进伙伴系统，标 MIGRATE_CMA core_initcall(cma_init_reserved_areas)

cma_activate_area 是 CMA 和伙伴系统接头的唯一位置：

c
static int __init cma_activate_area(struct cma *cma)
{
    int bitmap_size = BITS_TO_LONGS(cma_bitmap_maxno(cma)) * sizeof(long);
    unsigned long base_pfn = cma->base_pfn, pfn = base_pfn;
    unsigned i = cma->count >> pageblock_order;
    struct zone *zone;

    cma->bitmap = kzalloc(bitmap_size, GFP_KERNEL);
    zone = page_zone(pfn_to_page(pfn));

    do {
        unsigned j;

        base_pfn = pfn;
        for (j = pageblock_nr_pages; j; --j, pfn++) {
            if (page_zone(pfn_to_page(pfn)) != zone)
                goto err;
        }
        init_cma_reserved_pageblock(pfn_to_page(base_pfn));
    } while (--i);

    mutex_init(&cma->lock);
    return 0;

err:
    kfree(cma->bitmap);
    cma->count = 0;
    return -EINVAL;
}

四件事：按 cma_bitmap_maxno() 算 bitmap_size 并 kzalloc，i 是 area 含多少个 pageblock；按 pageblock 遍历 area，base_pfn 记每个 pageblock 的起始 pfn；内层循环校验整个 pageblock 都在同一个 zone 里，跨 zone 直接 goto err，这是 CMA 不能跨 zone 的根源；init_cma_reserved_pageblock 把 pageblock 交给伙伴系统并设 MIGRATE_CMA。

err 分支把 cma->count 清零，area 就这样废了，日志里只有一行。

八、cma_alloc 与 cma_release #

c
struct page *cma_alloc(struct cma *cma, size_t count, unsigned int align);
bool cma_release(struct cma *cma, const struct page *pages, unsigned int count);

count 要多少个页，align 按 2^align 个页对齐。返回 area 内第一个页的 struct page *，失败返回 NULL。页在 area 内物理连续，拿到首页指针就能算出整段。

cma_alloc 的骨架三段：

  1. 参数换算。count 按 order_per_bit 折成 bit 数（cma_bitmap_pages_to_bits），align 折成掩码。
  2. 在 bitmap 上找连续空闲位。bitmap_find_next_zero_area 从上一次位置扫，找到满足 count 和 align 的一段连续 0 位就 bitmap_set。
  3. 向伙伴系统要真内存。alloc_contig_range(pfn, pfn + count, MIGRATE_CMA)。返回 0 表示拿到了；返回 -EBUSY 表示这一段有页搬不走，清 bitmap 标记、换下一个位置继续扫，不是立刻失败；其他错误直接清标记返回 NULL。

-EBUSY 继续扫这一条很重要：一次没搬到不等于 area 里没位置，换个位置接着试。代价是单次 cma_alloc 的耗时不可预测，有时要扫很久。

cma_release 三步：校验 pages 落在本 area 的 [base_pfn, base_pfn + count) 内且 count 不超过总页数，否则返回 false；bitmap_clear；free_contig_range 还给伙伴系统，migrate type 还是 MIGRATE_CMA。它返回 bool 而不是错误码，传错 area、传错 count 都只是 false 加一行日志。

lock 护住 bitmap 的读改写，同一个 area 上的分配是串行的。上下文限制很硬：cma_alloc 会触发页迁移和回收，不能在 atomic context 里调——中断里、spinlock 里想分连续内存，只能提前分好。

九、CMA 页被占用时怎么办：migrate 走一遍 #

CMA 的核心场景：area 的页被人借走了，驱动现在要一大块连续的。alloc_contig_range 干的就是「把一段 pfn 范围清空、拼成连续块」，四步。

隔离。 start_isolate_page_range 把范围内的 pageblock 从伙伴系统 free list 上摘下来，标成 MIGRATE_ISOLATE。之后没人能从这段里分到新页，范围冻结。隔离按 pageblock 走，MIGRATE_ISOLATE 这个类型存在的意义就是「临时封存」。

扫描待迁移页。 isolate_migratepages_range 遍历范围内已分配的页，把可迁移的挑出来，从 LRU 摘下来，攒成待迁移链表。可迁移的判定关键是：属于 LRU（匿名页或 page cache）、没被 pin 住、不在写回中、不是内核自己的数据结构。slab 对象、页表页、vmalloc 的页、被 get_user_pages 长期钉住的页，全部不可迁移。

真正搬。 migrate_pages 给每个待迁移页分配新页、拷内容、改页表指向新页、释放旧页。硬约束：新页不能落在被隔离的范围里，得从别处的 MIGRATE_MOVABLE 页找。所以 CMA 迁移本质上是「拿自己的页换别人别处的页」，系统得有余量。

收尾。 全部搬走 → 范围内全空闲，返回 0。有页搬不走 → undo_isolate_page_range 撤隔离、putback_movable_pages 放回 LRU，返回 -EBUSY，cma_alloc 清标记换位置再试。

text
cma_alloc
  -> alloc_contig_range(pfn, pfn + count, MIGRATE_CMA)
       -> start_isolate_page_range        # pageblock -> MIGRATE_ISOLATE
       -> isolate_migratepages_range      # 可迁移页进链表
       -> migrate_pages                   # 分新页、拷数据、改页表
       -> 成功：范围内全空 | 失败：undo + putback

搬不走的典型来源：用户态 get_user_pages 长期钉住的页（某些 DMA 实现、vmsplice、O_DIRECT 的在途页）、被 pin 的 mlock 页、写回队列里的脏页。这些页在 CMA 里待着，这个 area 的大块分配就废了。

这就是第三章那个前提的分量：CMA 的前提是「这些页的数据可以被搬」。前提破了，CMA 退化成一块既不能给别人用、又拿不出连续内存的死内存。

十、CMA 的使用限制 #

  • 不能跨 zone。 cma_activate_area 就校验了这一点，一旦跨 zone 直接注册失败，count 清零。
  • 不能用于 atomic context。 cma_alloc 会迁移、会回收，睡眠是必须的。
  • 只有可迁移分配能借 area 的页。 MIGRATE_CMA 的 pageblock 只接受 MIGRATE_MOVABLE 请求，slab、页表、kmalloc 这类进不来。一旦混进不可迁移的东西，这个 area 永远拼不出大块。
  • 被 pin 住的页会卡死分配。 这是现场最常见的原因：cma_alloc 一直返回 NULL，日志里只有 -EBUSY。
  • 大小静态。 area 在启动阶段定死，运行期不能扩。
  • area 数量有上限。 MAX_CMA_AREAS 编译时定死，划太碎会撞上限。
  • order_per_bit 是记账粒度。 设成 1 就按两页一块记账，要一个页也占掉两个页的 bit。

落地建议：吃大块连续内存的设备单独给 per-device CMA，别和一堆小设备挤 Global CMA；关键 buffer 用 dma_alloc_coherent 并检查返回值，NULL 是会发生的。

十一、当连续内存拿不到时：scatterlist #

CMA 解决「必须有连续物理内存」。现实还有另一半：设备能接受分散的段，那就别硬要连续。这就是 scatterlist。

名字拆开看：scatter 是散开，list 是列表，合起来「散列表」太抽象。补上省略的主语——物理内存的散列表。把分散的物理内存用列表组织起来，就这一句。

为什么要这么组织？先看系统里几个能碰 memory 的角色。

text
CPU     -> MMU(可选)   -> Memory      CPU 用 VA
DMA     -------------> Memory         DMA 控制器用 PA
Device  -> IOMMU(可选) -> Memory      设备用 DA(设备地址)

某个软件实体分配了一片空间，CPU 视角（虚拟空间）连续，起始 va1，实际映射到三块不连续的物理内存 pa1、pa2、pa3。

  • 软件自己用 va1：没问题，MMU 把连续 VA 映射到不连续 PA，软件感知不到。
  • 交给 DMA 搬到外设：出问题。DMA 只认物理地址，理解不了「虚拟连续」，只能按不连续的物理块为单位递交。

scatterlist 就诞生在这个缺口上：用一个数据结构描述「一个物理连续的内存块」（起始地址、长度），一排这样的结构完整描述那三块。可以是 struct scatterlist 数组，也可以是内核抽象出的 struct sg_table。

本质一句话：scatterlist 是不同地址映射空间（PA、VA、DA）之间的媒介。物理地址是真实存在的那一层，可以当通用语言，靠它把各个映射空间串起来（比如 VA 转 DA）。

十二、struct scatterlist 与 struct sg_table #

struct scatterlist 描述一个物理连续的内存块，定义在 include/linux/scatterlist.h。

c
struct scatterlist {
#ifdef CONFIG_DEBUG_SG
    unsigned long   sg_magic;
#endif
    unsigned long   page_link;
    unsigned int    offset;
    unsigned int    length;
    dma_addr_t      dma_address;
#ifdef CONFIG_NEED_SG_DMA_LENGTH
    unsigned int    dma_length;
#endif
};
字段 含义 坑
page_link 块所在的页面 bit0、bit1 被借走当标志位，所以 page 指针至少 4 字节对齐
offset 块在页面内的偏移 不从页首开始时才非 0
length 块长度 不能跨页，一个 sg 只描述一页内的一段
dma_address 映射后的 DMA 地址（PA 或 DA） dma_map_sg 之前是未初始化值
dma_length 映射后的长度 只在 CONFIG_NEED_SG_DMA_LENGTH 下存在

page_link 被复用成标志位，是整个设计的枢纽。struct page 地址天然对齐，低两位始终是 0，正好塞标记。代价是任何拿到 page_link 的代码都得先屏蔽低两位再当指针用，sg_page() 干的就是这事。

单个 scatterlist 意义不大，实际是一排。两种组织形式，一是模块自己管指针和长度（MMC 的 struct mmc_data 就是 sg_len + sg 两个字段干这活），二是用内核抽象好的 struct sg_table：

c
struct sg_table {
    struct scatterlist *sgl;    /* the list */
    unsigned int nents;         /* number of mapped entries */
    unsigned int orig_nents;    /* original size of list */
};

sgl 是数组首地址，orig_nents 是数组容量，nents 是当前实际段数。两个值分开的理由：dma_map_sg 会把相邻段合并掉，合并后 nents 小于 orig_nents。所以 nents 在映射前后语义不同，读的人得清楚自己在哪个阶段；dma_unmap_sg 必须传 orig_nents，传 nents 会漏解映射，DMA 还在写内存，页就被回收了。

十三、sg 链表的组织方式 #

一个 scatterlist 数组能描述多少段，受限于这个数组本身怎么分配。用 kmalloc 分，段数被 slab 单次上限卡住；用 sg_alloc_table 分，它也是按页拼的。碰上几百 MB 的 buffer、几千个段，一个数组放不下。

解法是把多个数组链起来，page_link 的低两位就是干这个的。规则两条：

  1. 某个 scatterlist 的 page_link bit0 为 1 → 它不是实体块，是一个 chain（铰链），page_link 高位指向另一个 scatterlist 数组。
  2. 某个 scatterlist 的 page_link bit1 为 1 → 它是这个数组里最后一个实体块，后面的内容全部忽略。

这就是 chained scatterlist 这个名字的来历。

text
sg_table.sgl --> [ sg0 ][ sg1 ][ chain ]--+
                                         v
                            [ sg2 ][ sg3 ][ sg4/last ]

[chain] 那格的 page_link 是 &sg2 | 0x01，[sg4/last] 那格是 page | 0x02。

两个细节容易踩：链式数组的最后一格必须标 last，sg_mark_end 就干这个，漏标会让 for_each_sg 一直往下走、走出数组边界；数组尾部留一个冗余空槽有用，方便后续追加链，不留就得重新分配整个数组。

c
void sg_chain(struct scatterlist *prv, unsigned int prv_nents,
              struct scatterlist *sgl);

prv 是前一个数组，prv_nents 是这个数组的条目总数（含留出来的那一格），sgl 是后一个数组。实际写入位置是 prv[prv_nents - 1]，所以前一个数组的实体块数是 prv_nents - 1。

遍历别自己写循环，用 for_each_sg：

c
#define for_each_sg(sgl, sg, nents, i) \
    for (sg = sgl, i = 0; sg && i < nents; \
         sg = sg_next(sg), i++)

sg_next 内部处理三种情况：当前格是 chain 就跳到它指向的数组，是 last 就返回 NULL，否则返回下一格。所以链式结构对使用者基本透明。

一个反直觉的点：传给 for_each_sg 的 nents 是「预期遍历多少格实体块」，不是数组容量。给多了会在 last 处提前停（sg_next 返回 NULL），给少了会漏段。写驱动时按 sg_table.nents（映射后的）传，遍历出来正好是映射过的段。

十四、scatterlist 的 API 一览 #

都在 include/linux/scatterlist.h，按用途分四组。

1、字段读写 #

c
#define sg_dma_address(sg)      ((sg)->dma_address)

#ifdef CONFIG_NEED_SG_DMA_LENGTH
#define sg_dma_len(sg)          ((sg)->dma_length)
#else
#define sg_dma_len(sg)          ((sg)->length)
#endif

sg_dma_address / sg_dma_len 取的是映射后的 DMA 地址和长度。dma_length 只在 CONFIG_NEED_SG_DMA_LENGTH 打开时才有独立字段，否则退化成 length。这个配置项存在的理由是某些架构下 dma_map_sg 会把多段合成一段，合并后的长度和单段 length 不等。

2、标志判断 #

c
#define sg_is_chain(sg)         ((sg)->page_link & 0x01)
#define sg_is_last(sg)          ((sg)->page_link & 0x02)
#define sg_chain_ptr(sg)        \
        ((struct scatterlist *) ((sg)->page_link & ~0x03))

sg_is_chain 判链，sg_is_last 判尾，sg_chain_ptr 取出链指向的数组地址。三个宏都屏蔽低两位，因为那两位是标记不是地址。

sg_alloc_table_from_pages 是驱动里出现频率最高的一个。用户态传一组页进来（get_user_pages），或者 vmalloc 一片内存（vmalloc_to_page 逐页取），用它一次建表，相邻物理页自动合并，段数就下来了。它的引入版本我没核，手上的 4.x 树里都有，早期的树要自己逐页 sg_set_page。

顺序不能错：sg_mark_end 在 dma_map_sg 之前，dma_unmap_sg 传 orig_nents。下面这段是最小骨架：

c
struct sg_table sgt;
int ret, nents;

ret = sg_alloc_table(&sgt, 2, GFP_KERNEL);
if (ret)
    return ret;

sg_set_page(sgt.sgl, page0, PAGE_SIZE, 0);
sg_set_page(sg_next(sgt.sgl), page1, 1024, 128);
sg_mark_end(sg_last(sgt.sgl, 2));

nents = dma_map_sg(dev, sgt.sgl, sgt.orig_nents, DMA_TO_DEVICE);
if (!nents) {
    sg_free_table(&sgt);
    return -EIO;
}
/* 用 sgt.sgl 里每段的 sg_dma_address / sg_dma_len 填硬件描述符 */
dma_unmap_sg(dev, sgt.sgl, sgt.orig_nents, DMA_TO_DEVICE);
sg_free_table(&sgt);

十五、dma_map_sg 与 IOMMU 的关系 #

dma_map_sg 是把「CPU 视角的页」翻成「设备视角地址」的那一步。中间做多少事，取决于总线上有没有 IOMMU。

没 IOMMU。 设备看到的就是物理地址，dma_map_sg 退化成三件事：逐段算 dma_address = page_to_phys(sg_page(sg)) + sg->offset；合并物理地址相邻的段把 nents 压下来；按 dir 做 cache 维护，保证设备和 CPU 看到一致的数据。

合并值得单说。两段满足「前一段的结束物理地址 == 后一段的开始物理地址」就能并成一格，length 相加、dma_address 取前者。硬件描述符表跟着变短，在没有 IOMMU 的嵌入式平台上是实打实的收益。

有 IOMMU。 设备看到的是 DA，IOMMU 负责把 DA 翻成 PA。这时要建 IOTLB 映射：在 IOMMU 地址空间里找一段空闲 DA 窗口；把各段 PA 填进 IO page table 映射到窗口内的连续 DA；填 dma_address = 窗口基址 + 段内偏移。

关键效果：IOMMU 让设备「以为」内存是连续的。分散在多处的物理页可以映射成一段连续的 DA，硬件只需一个起始地址加总长度，描述符表能缩到一格。这也是带 IOMMU 的平台上 CMA 没那么紧张的原因——「设备要求连续物理内存」这个约束被 IOMMU 吃掉了。

是否真合并成 1 格取决于 IOMMU 驱动实现，不是 dma_map_sg 的核心保证。做驱动要按返回值 nents 遍历，不能假设它等于原段数，也不能假设它等于 1。

还有一种情况：设备只能访问某个地址范围（32 位设备挂 64 位总线），或者有对齐限制。DMA 层会把数据拷到一块落在合法范围内的 bounce buffer（swiotlb），dma_address 指向它。表现上和 IOMMU 一样是「多段变一段」，代价是两次拷贝。

dma_map_sg 返回 0 表示映射失败。只判 nents 不判 0 是常见 bug，后面拿着无效的 dma_address 配硬件。

阶段 该调什么
映射前，CPU 写完数据 dma_map_sg(dir) 内部处理，dir 要给对
传输中 CPU 别碰 buffer
传完，CPU 要读数据 dma_sync_sg_for_cpu(dev, sgl, nents, dir)
CPU 改完要再传 dma_sync_sg_for_device(...)
全部结束 dma_unmap_sg(dev, sgl, orig_nents, dir)

dir 给错是隐蔽 bug：DMA_TO_DEVICE 给成 DMA_FROM_DEVICE，cache 维护方向反了，数据在非一致缓存架构上会错，在 x86 上则看不出来。

十六、用户态指针为什么不能直接解引用 #

前面五章讲的都是「内存不连续」。这一章换成另一半：内存连续，但地址不属于你。场景：内核模块拿到一个用户态传下来的指针，想直接把数据抄过来。为什么不能直接 memcpy？先看网上流行的两种答案。

说法一：copy_{to,from}_user() 比 memcpy() 多了地址合法性校验。 大意是有 MMU 的平台上，用户传来的指针指向的虚拟地址还没建物理页映射，会缺页。用户态缺页内核会悄悄修好，内核态缺页必须显式处理，因为内核在内核态访问用户地址时不能装作什么都没发生。

说法二：只要保证用户传的指针是对的，memcpy() 完全可以替代。 有人做过测试，跑起来没问题。

两种说法都不算错，但都不完整。说法一只讲了「合法地址没建映射」这一种情况，说法二只在特定内核配置下成立。第十八章按四种情况拆开推。

先立一个前提：用户态的地址在你手里的那一刻，它指向什么不由你决定。合法但没映射的、非法的、映射到代码段的、跨界到内核空间的，都在候选里。内核不能假设来的是哪一种。

十七、copy_to_user / copy_from_user 做了什么 #

先看签名。两者参数几乎一样：目的地址、源地址、字节数。

c
static __always_inline unsigned long __must_check
copy_to_user(void __user *to, const void *from, unsigned long n);

static __always_inline unsigned long __must_check
copy_from_user(void *to, const void __user *from, unsigned long n);

void *memcpy(void *dest, const void *src, size_t len);

__user 是稀疏标注，sparse 会检查你把这个指针用到了不该用的地方。__must_check 保证返回值不被忽略。

差异有三层，一层比一层深。

第一层，地址校验。 memcpy 不校验，copy_*_user 校验 to/from 与 to + n/from + n 是否都落在用户空间地址范围内，另外还有 size 校验（check_copy_size）和对象大小校验（check_object_size），防内核栈或堆的越界读变成信息泄露渠道。机制见第十九章。

第二层，uaccess 开关。 ARM64 上有 PAN，开了之后内核态直接访问用户地址会触发异常，copy_*_user 在拷贝前后临时打开又关掉访问权限。这就是说法二在第二种测试里崩掉的原因：测试的板子没开 PAN，所以 memcpy 能跑；开了 PAN 的板子直接 oops。细节见第二十章。

第三层，异常修复表。 这是 memcpy 永远补不上的一层。调用链：

text
copy_to_user() -> _copy_to_user() -> raw_copy_to_user() -> __arch_copy_to_user()

__arch_copy_to_user() 在 ARM64 上是汇编：

armasm
    end .req x5

ENTRY(__arch_copy_to_user)
    uaccess_enable_not_uao x3, x4, x5
    add end, x0, x2
#include "copy_template.S"
    uaccess_disable_not_uao x3, x4
    mov x0, #0
    ret
ENDPROC(__arch_copy_to_user)

    .section .fixup,"ax"
    .align  2
9998:   sub x0, end, dst            // bytes not copied
    ret
    .previous

四段逐段看。uaccess_enable_not_uao / uaccess_disable_not_uao 是内核态访问用户空间的开关；copy_template.S 就是 memcpy 的实现主体，同一份文件被 arch/arm64/lib/memcpy.S 包含，所以拷贝本体和 memcpy() 是同一段汇编；mov x0, #0 + ret 表示正常路径返回 0，一个字节都没剩下；.section .fixup,"ax" 是单独的 section，权限 ax（可重定位、可执行），9998 这个标号就是「出事之后从哪继续跑」的地方，它算的是还剩多少字节没拷。

.fixup 段是全部答案。访问非法用户地址必然触发 page fault。内核态 page fault 的默认处理是 __do_kernel_fault()，结局是 oops 加给当前进程发 SIGSEGV。但 copy_*_user 走另一条路：查异常表，查到就把 do_page_fault() 的返回地址改到 9998，从修复路径继续跑，算出剩余字节数返回。

所以 __arch_copy_to_user() 可以近似等价成：

text
uaccess_enable_not_uao();
memcpy(ubuf, kbuf, size);       /* == __arch_copy_to_user(ubuf, kbuf, size) */
uaccess_disable_not_uao();

只是 memcpy 那一行外面套了两层保护：进来的地址校验、出事之后的修复表。

顺便解释 copy_template.S 为什么等于 memcpy。memcpy 本身也是汇编，在 arch/arm64/lib/memcpy.S：

armasm
    .weak memcpy
ENTRY(__memcpy)
ENTRY(memcpy)
#include "copy_template.S"
    ret
ENDPIPROC(memcpy)
ENDPROC(__memcpy)

memcpy 声明成 .weak，可以被重写。用汇编不用 lib/string.c 的通用版本，理由是速度：通用版按字节拷，ARM64 可以按 8 字节甚至 16 字节拷（考虑对齐），差距很大。

__ex_table 段的首尾是 __start___ex_table 和 __stop___ex_table（定义在 include/asm-generic/vmlinux.lds.h）。这段可以看成一个数组，每个元素是 struct exception_table_entry，记着「出异常的指令地址」和「该跳哪去修」。

text
__start___ex_table --> +---------+
                       |  entry  |
                       +---------+
                       |   ...   |
__stop___ex_table  --> +---------+

32 位处理器上的定义和查找：

c
struct exception_table_entry {
    unsigned long insn, fixup;
};

unsigned long search_fixup_addr32(unsigned long ex_addr)
{
    const struct exception_table_entry *e;

    for (e = __start___ex_table; e < __stop___ex_table; e++)
        if (ex_addr == e->insn)
            return e->fixup;
    return 0;
}

unsigned long 是 4 字节，insn 存异常指令地址，fixup 存修复地址，查找就是线性扫。

64 位处理器上照搬这套，每个 entry 要 16 字节，异常表体积翻倍。内核换了存法：

c
struct exception_table_entry {
    int insn, fixup;
};

unsigned long search_fixup_addr64(unsigned long ex_addr)
{
    const struct exception_table_entry *e;

    for (e = __start___ex_table; e < __stop___ex_table; e++)
        if (ex_addr == (unsigned long)&e->insn + e->insn)
            return (unsigned long)&e->fixup + e->fixup;
    return 0;
}

每个 entry 还是 8 字节，但 insn / fixup 存的不再是绝对地址，而是相对当前成员地址的偏移。省了一半空间，代价是算地址要先取成员地址。

原稿给了一个算 entry 的例子，指令地址是随手编的，只看算法：

text
0xffff000000000000: ldr  x1, [x0]         <- 访问用户地址，需要一条 entry
0xffff000000000004: add  x1, x1, #0x10    <- 不访问内存，不需要
0xffff000000000008: ldr  x2, [x0, #0x10]  <- 也要一条 entry
0xffff000040000000: mov  x0, #0xfffffffffffffff2    // -14

假设 x0 存用户地址、出异常要跳到 0xffff000040000000、__start___ex_table 是 0xffff000080000000：

insn = 0xffff000000000000 − 0xffff000080000000 = 0x80000000； fixup = 0xffff000040000000 − 0xffff000080000004（&e->fixup 是 entry 基址加 4）= 0xbffffffc。

两个都是负数，正好装进 int。这意味着异常表能覆盖的地址差不超过 ±2GB，对内核镜像够用。0xffff000000000008 那条指令同样要一条 entry——规则是汇编里每一处访问用户内存的指令都要有一条 entry，漏一条，那一处出错就是 oops。

访问非法用户地址的完整流程：

text
ldr x1, [x0]                            # x0 是非法用户地址
  MMU 触发异常
  CPU 调 do_page_fault()
  do_page_fault() 调 search_exception_table()（regs->pc == 那条 ldr 的地址）
    查 __ex_table，找到对应修复地址 0xffff000040000000
  do_page_fault() 改返回地址（regs->pc = 0xffff000040000000）后返回
  程序从修复地址继续跑，算出没拷完的字节数写进 x0 返回

search_exception_tables() 是 fixup_exception() 调的，fixup_exception() 又是 __do_kernel_fault() 的第一件事：

c
static void __do_kernel_fault(unsigned long addr, unsigned int esr,
                              struct pt_regs *regs)
{
    /*
     * Are we prepared to handle this kernel fault?
     * We are almost certainly not prepared to handle instruction faults.
     */
    if (!is_el1_instruction_abort(esr) && fixup_exception(regs))
        return;
    /* ... 走到这里就是死路：oops 或 panic ... */
}

is_el1_instruction_abort(esr) 那半个条件是排除取指异常——取指异常没法用数据访问的修复表救，直接往下走。救不回来就是 oops，严重程度看 CONFIG_PANIC_ON_OOPS。

十八、能不能用 memcpy 替代：三种后果的推演 #

把「用户传来的指针」拆成四种情况，逐种推。

情况一：地址合法，物理页已映射。 buf 是 read() 传进来的用户 buffer，四页大小，已经通过 cat 触发过映射。

c
static ssize_t test_read(struct file *file, char __user *buf,
                         size_t len, loff_t *offset)
{
    memcpy(buf, "test\n", 5);   /* 对照：copy_to_user(buf, "test\n", 5) */
    return 5;
}

没开 PAN 的内核上这段代码跑得通，cat 能读到 test。这就是说法二的实验基础。

情况二：地址合法，物理页还没映射。 用户态拿到了虚拟地址空间（mmap 了一块但还没写），页表项是空的。memcpy 一碰就缺页。地址在这个进程的 VMA 里、是合法用户地址 → 内核替它分配物理页、填页表、建映射，返回继续执行。原稿提到朋友实测过，代码正常运行。

所以情况二里 memcpy 和 copy_*_user 表现一样。这一条是说法二真正成立的地方，但它只覆盖了情况二。

情况三：地址非法。 用户传了野指针，或者故意传内核地址做提权尝试。

  • memcpy：页错误 → __do_kernel_fault() → fixup_exception() 查表查不到（memcpy 的汇编没生成 entry）→ oops，给进程发 SIGSEGV。
  • copy_*_user：页错误 → fixup_exception() 查到 entry → 跳修复地址 → 返回「还剩 n 字节没拷」→ read() 返回错误，进程收到 -EFAULT，内核干干净净。

原稿的实测结论就是这样：memcpy 触发 kernel oops，copy_*_user 只返回错误。

情况四：开了 PAN。 前三种都假设内核态能直接访问用户地址。开了 CONFIG_ARM64_SW_TTBR0_PAN 或 CONFIG_ARM64_PAN，这件事本身就不成立了。memcpy 访问用户地址，不管合不合法，第一脚就踩在 PAN 上直接 oops，情况一、情况二全部失效。

场景 memcpy copy_*_user
合法地址，已映射，未开 PAN 正常 正常
合法地址，未映射，未开 PAN 缺页自动修复，正常 正常
非法地址，未开 PAN kernel oops 返回剩余字节数，进程拿 -EFAULT
上述任一情况，开了 PAN kernel oops 正常

硬要用 memcpy 也行，把 PAN 开关自己补上：

c
uaccess_enable_not_uao();
memcpy(ubuf, kbuf, size);
uaccess_disable_not_uao();

这能过 PAN 那一关。但异常修复表那一层还是缺的：memcpy 的汇编没有 .fixup、没有 __ex_table entry，非法地址照样 oops。等于四行里补回三行，最后一行补不上。

结论摆在这：memcpy 在某些条件下能跑，但不该用。 用户态和内核态之间的数据交互，用 copy_{to,from}_user() 这类接口；这类接口不止两个，{get,put}_user() 也是，一次搬一个标量。

十九、access_ok 与地址范围校验 #

第一层保护是范围校验，落在 access_ok。4.18 的签名带 type 参数（后来的版本把它去掉了）：

c
#define access_ok(type, addr, size) \
    __access_ok((unsigned long)(addr), (size), get_fs())

它要确认三件事：addr 不在 0 附近（防止 NULL 解引用被当成合法用户地址）；addr + size 不溢出；addr + size 不超过用户地址空间上界。

上界来自 TASK_SIZE / user_addr_max()。ARM64 上由 CONFIG_ARM64_VA_BITS 和页大小决定（39 位 VA 是 0x0000008000000000，48 位是 0x0000800000000000）。实现思路是拿「地址 + 长度」和上界比，同时查没有回绕：

text
addr + size <= user_addr_max()   且   addr + size >= addr（无回绕）

朴素但够用。溢出检查那条最容易被忽略：addr = 0xfffffffffffffff0、size = 0x20 加起来回绕成一个小值，只判上界就漏了。

access_ok 之外还有两层：check_copy_size() 确认 n 不超过目标对象大小，防把内核栈或堆上的东西多抄出去；check_object_size() 配合 __builtin_object_size 在编译期能算出对象大小时做静态检查，CONFIG_HARDENED_USERCOPY 打开才生效。三层加起来的效果是：即使调用者算错了 n，也不至于把内核内存泄露给用户态。

一个容易混淆的点：access_ok 只检查「地址范围属于用户空间」，不检查「这段地址已映射」。后者是缺页处理的事，前者是入口把关，两者互补，缺一不可。

二十、ARM64 上的实现：uaccess 与 PAN/UAO #

ARM64 用两个页表基址寄存器：ttbr0_el1 放用户页表，ttbr1_el1 放内核页表。处理器看 64 位地址的高 16 位判断走哪个：全 0 是用户空间，全 1 是内核空间。

设计上带来一个便宜：进程切换只改 ttbr0_el1，ttbr1_el1 不用动，因为所有进程共享同一份内核页表。要阻止内核态访问用户地址，办法就是改 ttbr0_el1，指到一段废页表上。

SW_TTBR0_PAN 的做法。 准备一张 4K 的特殊页表，内容全 0（全 0 的页表项无效）。进内核态就把 ttbr0_el1 指过去。这段内存在链接脚本里分配：

c
#define RESERVED_TTBR0_SIZE (PAGE_SIZE)

text
SECTIONS
{
    reserved_ttbr0 = .;
    . += RESERVED_TTBR0_SIZE;
    swapper_pg_dir = .;
}

它和 swapper_pg_dir 紧挨着，正好差 4K，启动时被清零。Kconfig 解释得很直白：

text
config ARM64_SW_TTBR0_PAN
        bool "Emulate Privileged Access Never using TTBR0_EL1 switching"
        help
          Enabling this option prevents the kernel from accessing
          user-space memory directly by pointing TTBR0_EL1 to a reserved
          zeroed area and reserved ASID. The user access routines
          restore the valid TTBR0_EL1 temporarily.

开关是什么样：

armasm
.macro  __uaccess_ttbr0_disable, tmp1
    mrs \tmp1, ttbr1_el1                        // swapper_pg_dir
    bic \tmp1, \tmp1, #TTBR_ASID_MASK
    sub \tmp1, \tmp1, #RESERVED_TTBR0_SIZE      // reserved_ttbr0 在 swapper_pg_dir 前面
    msr ttbr0_el1, \tmp1                        // 设成 reserved TTBR0_EL1
    isb
    add \tmp1, \tmp1, #RESERVED_TTBR0_SIZE
    msr ttbr1_el1, \tmp1                        // 换上 reserved ASID
    isb
.endm

三步：ttbr1_el1 存的是内核页表基址 swapper_pg_dir；减掉 RESERVED_TTBR0_SIZE 得到那张全零页表的地址；写进 ttbr0_el1，之后访问用户地址全部非法。

__uaccess_ttbr0_enable 是反操作，把合法的用户页表基址写回去。copy_*_user 在拷贝前后各调一次，窗口里内核能访问用户地址。

UAO 与硬件 PAN。 CONFIG_ARM64_PAN 走硬件：ARMv8.1 的 PAN 位，一条 msr pan, #1 就够，不用切页表；硬件不支持时配了也没用，只能退回软件仿真。再往后 ARMv8.2 加了 UAO（User Access Override），语义反过来：PAN 打开时，UAO 可以让指定代码段访问用户地址，不用反复开关。这就是 uaccess_enable_not_uao / uaccess_disable_not_uao 这对宏名字的来历——它们处理的是「不用 UAO 的那种开关」；配套还有 uaccess_enable_uao / uaccess_disable_uao，只在确实支持 UAO 时展开成 msr uao, ...。

配置 机制 开关成本
都没开 内核态可以访问用户地址 零
CONFIG_ARM64_SW_TTBR0_PAN 切 ttbr0_el1 到全零页表 + ASID 切换 两次 msr + isb，还要 TLB 相关开销
CONFIG_ARM64_PAN 硬件 PAN 位 一条 msr pan
加 UAO（ARMv8.2） 用 UAO 位放行指定代码段 免开关，但要求硬件

CONFIG_ARM64_SW_TTBR0_PAN 在后续内核里被删掉了（UAO/PAN 的代码路径重构过），4.18 的树上还在。你要在 5.x 的树里找这段汇编，会找不到。

uaccess_enable_not_uao 在 C 里是薄封装，具体展开在 arch/arm64/include/asm/uaccess.h，按配置走三条分支：都没开的空实现、SW_TTBR0_PAN 的切页表版本、硬件 PAN 的 msr 版本。所以同一份 copy_*_user 源码在不同板子上行为完全不同，差别全在这些宏里。

二十一、copy_*_user 的返回值语义与常见误用 #

返回值是这套接口最容易搞错的地方。

copy_to_user / copy_from_user 返回「还有多少字节没拷过去」，0 表示全成功。 它不是错误码，不返回 -EFAULT。

-EFAULT 是 {get,put}_user() 的语义。copy_*_user 里 9998: sub x0, end, dst 算出来的是字节数，不是负数。原稿例子里写的 mov x0, #0xfffffffffffffff2 // -14 是演示用的假想修复代码，真实实现返回剩余字节数。

判断方式只有一种：

c
if (copy_to_user(buf, kbuf, n))
    return -EFAULT;

不能写 if (ret < 0)，也不能把 ret 当 errno 用。

误用 后果 正确做法
忽略返回值 用户态拿到半截数据或全零 __must_check 会警告，看警告
把返回值当错误码 剩余字节数被当成 -errno，用户态看到莫名其妙的错误 只判 != 0
部分成功就返回全成功 用户态拿到残缺数据，当作正常数据 返回失败，或返回实际拷贝量
先 copy_from_user 再校验 校验前已经用了不可信数据 先校验长度/范围，再拷
拷进来又直接再用用户指针 TOCTOU，两次读到的内容不同 拷一次，后面只用内核副本
大结构体直接覆盖 结构体新增字段时旧用户态传短数据，尾部是栈垃圾 copy_struct_from_user（5.x）或先清零
目标含 padding 未初始化填充字节泄露内核栈内容 先把内核侧结构体清零

最后一条值得展开：struct 有对齐填充，copy_to_user 会把填充字节一起抄出去，那里面常常是上一次函数调用留下的栈内容。做法是先 memset 整个结构体再填字段。

copy_struct_from_user 是 5.x 引入的，专门处理「用户态结构体比内核态小」的兼容问题，4.18 的树上没有。4.18 里的等价做法是「清零内核副本 + 按 min(ksize, usize) 拷贝」。

二十二、三者怎么选：一张决策表 #

回到开篇那条主线：连续内存、分散内存、用户指针，三种约束三种工具。

你的处境 用什么 入口 关键约束
设备要一大块物理连续内存，没 IOMMU，也不支持 sg CMA dma_alloc_coherent → cma_alloc 不能 atomic；不能跨 zone；页要可迁移
内存必须一直属于你，不能被搬 启动时预留 reserved-memory，或 dma_declare_coherent_memory 永远占着，不还

几条组合规则：

  • CMA 和 scatterlist 不互斥。走 dma_alloc_coherent 拿到 CMA 内存后，DMA 层给你的要么是单段 dma_addr_t，要么转成 sg。
  • 有 IOMMU 时优先用 scatterlist，别去挤 CMA——那个约束已经被硬件吃掉了。
  • 用户态 buffer 要走 DMA，先 get_user_pages 钉住再 sg_alloc_table_from_pages，别指望 copy_from_user 抄到内核 buffer 再 DMA，多一次拷贝，大 buffer 上开销明显。

二十三、易错点速查 #

CMA 侧：

  • cma_alloc 返回 NULL 先查是不是有页被 pin 住，别急着怀疑 area 太小。
  • 中断里调 cma_alloc 等于给自己埋雷，提前分配。
  • reserved-memory 节点 compatible 写了 shared-dma-pool 但漏 reusable，这段不进 CMA，变成纯 reserved。
  • 给 CMA 节点加 no-map，内核不建映射，后面当普通内存用会炸。
  • area 划太碎撞 MAX_CMA_AREAS，只在启动日志里留一行失败。

scatterlist 侧：

  • dma_unmap_sg 传 nents 而不是 orig_nents，映射泄漏。
  • sg_set_buf 用在 vmalloc 地址上，取到错的 page。
  • 忘了 sg_mark_end，for_each_sg 越界。
  • 一个 sg 只描述一页内的一段，长度跨页要拆成两格。
  • dma_map_sg 返回 0 没判，拿着垃圾 dma_address 配硬件。
  • dir 给反了，非一致缓存架构上数据出错，x86 上看不出来。

copy 侧：

  • 返回值当 errno 用。
  • 忽略返回值，用户态拿半截数据。
  • 同一个用户指针读两次（TOCTOU）。
  • 结构体 padding 没清零就 copy_to_user，泄露内核栈。
  • 开了 PAN 的内核上用 memcpy 碰用户地址，直接 oops。
  • 只做 access_ok 不处理缺页，或者反过来。
