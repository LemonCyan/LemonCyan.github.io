一、page frame reclaiming 要保证什么 #

在用户进程的内存使用上，Linux 内核没有严格限制。思路是：系统负荷小的时候，内存尽量躺在各种 cache 里换性能；系统负荷重（进程多、缺页多）的时候，cache 里的内存被收回，转成进程地址空间的页。

伙伴系统的 free list 是唯一的内存源头。分配路径一路从 free list 上取 page frame，交给用户进程或者 kernel cache。物理内存有限，free list 掉到某个水位以下，内核就得从用户进程和 kernel cache 里把 page frame 抠回来，还给伙伴系统。这个过程就是 page frame reclaiming。

一句话：page frame reclaiming 保证系统的空闲内存在一个指定水位之上。

这条定义里有两个词值得抠。

第一个是「保证」。它不是应急手段，是常态运行的调节器。系统跑得越久，page cache 越厚，空闲内存看起来越少，这是健康状态；回收要做的是把厚度控制在水位之上的合理范围，而不是把 page cache 清空。反过来，如果回收器清空 page cache 换出一片干净的 free list，系统的 IO 性能立刻塌下来——下次缺页全部变成磁盘访问。

第二个是「水位」。水位有三条线（min / low / high），算法在 物理内存管理：页、zone 与内存模型，这里只用结论：分配路径关心 min 和 low，高水位主要决定什么时候让 kswapd 停下来。

回收的页也不是只有一条出路。按页的后备存储不同，有三种处置方式：

处置方式 适用页 动作 代价
页回写 file mapped page、page cache 内容同步回块设备，页框直接重用 dirty 时要做磁盘 IO
页交换 匿名页（堆、栈、tmpfs） 写入 swap 分区，pte 改成 swap entry 换出换入都要 IO
页丢弃 只读的可执行文件映射、干净的 page cache 直接丢，下次缺页再从文件读 本次零 IO，下次缺页有代价

这张表是后面所有讨论的底：回收动作的代价差别，全部来自「数据要不要落盘」。第五节那条「尽量先回收不需要磁盘 IO 的页」，根就在这里。

二、为什么不能等内存用光了再回收 #

不能。三个理由，第三个最要命。

其一，回收自己也要吃内存。把匿名页换出去要构造 bio 写 swap 分区，路上要分配 buffer head 一类的小结构；把 dirty 的 page cache 回写同样要这类结构。free list 见底时，连辅助结构都分配不出来，回收流程在真正开始回收之前先被自己的内存需求卡死。这就是死锁的形状：回收是为了拿到内存，而回收需要内存。

其二，回收需要能睡、能发 IO。回收一个页要拿锁、要等磁盘、要遍历页表。中断上下文里不能睡，持锁之后发 IO 会拉着别人一起等。这类分配路径从一开始就不允许走完整回收，只能依赖别人（kswapd）提前把水位抬起来。

其三，回收有延迟。触发回收不等于内存立刻可用，中间隔着一整个磁盘往返。如果 free list 归零才动手，这期间任何一个分配都会失败，失败往上抛就是系统崩掉。内存分配是内核里最不能失败的调用之一，很多调用点没有失败路径可走。

所以水位是留给回收机制自己的周转金：

text
free list 水位（从高到低）
─────────────────────────────────────────
high  ──  kswapd 睡下
low   ──  kswapd 被唤醒，开始后台回收
min   ──  分配路径自己动手（直接回收），可睡眠的分配在此阻塞
0     ──  谁也不许走到这里：回收流程本身也要内存
─────────────────────────────────────────

三、四类触发场景与各自的约束 #

「分配失败就回收」是最直观的想法，但内核的实际场景比这乱。分配发生在中断上下文里，就不能阻塞当前进程；分配发生在持锁之后（为了排他访问某些资源），就不能启动 IO。约束不来自回收算法，来自调用点的上下文。

内核的整体思路是：分配时先检查水位，有需要就唤醒 kswapd，让空闲内存维持在水平线上，避免把自己逼进绝境；真进了绝境（分配失败），再做直接回收。

场景 触发入口 上下文约束 备注
synchronous page reclaim（同步/直接回收） __alloc_pages 分配失败 → try_to_free_pages；分配 page buffer 失败（alloc_page_buffers）→ free_more_memory 当前进程上下文，可睡眠，可发 IO free_more_memory 内部也是调 try_to_free_pages
Suspend to disk（休眠） shrink_all_memory，回收指定数目的 page frame 进程上下文，全局扫描 目标是一次凑够大块可用内存，不看单个 zone
kswapd 每个内存 node 一个内核线程，水位不满足时被唤醒 可睡眠，但受分配掩码与 zone 集合限制 常规回收的主力，见第六节
周期性 slab 回收 slab 分配器定时把 work 队列到 system_wq → cache_reap workqueue 上下文，只碰 slab 里的空闲对象 见第八节

四者的分工：kswapd 在后台慢慢做，把系统从 low 水位拉回 high；直接回收是最后一道闸，代价高，让分配者亲自等 IO；hibernation 是特例，它要的不是「一点空闲内存」而是「一大片连续可用」，所以主动指定回收数目；cache_reap 完全绕开页表，只收 slab 里的闲置对象。

为什么分配路径优先唤醒 kswapd 而不是自己动手？把苦活甩给一个可睡眠的线程，分配路径继续往前走；等 kswapd 也救不了，才 synchronous reclaim。这条「先异步、后同步」的分层决定了一件事：系统在压力下的表现是有梯度的——轻度压力只有 kswapd 在忙，分配延迟不变；压力上来出现直接回收，分配延迟突然变成「磁盘往返」的量级。性能曲线的拐点就在这里。

四、哪些内存可以回收：页缓存、匿名页、slab #

先把 page frame 分四类：

类别 典型对象 能否回收 回收方式
不可回收 空闲页（已在 free list）、保留页（PG_reserved，如内核正文段/数据段）、内核动态分配的页、用户进程内核栈的页、临时锁定页（PG_locked，正在做磁盘 IO）、mlock 锁定的页（VMA 带 VM_LOCKED） 否 不碰，LRU_UNEVICTABLE
可交换（swappable） 用户空间匿名映射页（堆、栈）、tmpfs 的页 是 写 swap 分区，pte 换成 swap entry
可同步（syncable） file mapped 页、page cache 页（内容对应某个磁盘文件）、块设备 buffer cache、disk cache 里的页（如 inode cache） 是 dirty 则先回写，干净则直接丢
可直接释放 各种内存 cache（slab 分配器里没用上的页）、没使用的 dentry cache 是 直接还给伙伴系统，不动页表

不可回收那一栏看着像杂物间，其实每条都有原因：空闲页已在 free list 上，不用管；保留页动了就是自杀；内核动态分配的页没有后备存储，也换不出去；内核栈的页收走等于收走执行环境；PG_locked 正在做磁盘 IO，内容此刻正在被改写；VM_LOCKED 是用户显式 mlock 过的承诺。六类共用一个特征：没有「可以被恢复」的路径。

第二类和第三类看着像，区别在数据的最终老家：

  • swappable：数据的最终地点是内存，后备磁盘只为延伸容量。回收时必须把内容存到后备存储，否则数据就丢了。
  • syncable：数据的最终地点是磁盘，内存只为加速。回收时看脏不脏，脏就回写，干净就直接丢。

这个区别决定回收动作：回收 swappable 页永远要做 IO，回收 syncable 页有机会零 IO。也决定了「什么页最值得先收」——干净的文件页，零成本，丢了还能再读回来。

第四类最便宜：slab 里没用上的对象、没使用的 dentry。回收它们不动页表、不发 IO，删掉引用就够了。代价是碎片——slab 缓存里空出来几个对象往往凑不满一整页，这一页就还回不了伙伴系统，收益不是线性的，见第八节。

候选对象圈定很容易，就是上面 2、3、4 类。难的是顺序。

五、回收策略：LRU 的两条链与激活/非激活 #

顺序靠 LRU（Least Recently Used）。近期最少使用的挂在链表末尾，从头取就对了：

c
#define lru_to_page(_head) \
    (list_entry((_head)->prev, struct page, lru))

prev 就是链尾，这个宏的语义是「取最久没被用过的那一页」。回收顺序不需要额外计算，链表顺序本身就是答案。

每个 zone 有 5 条 LRU 链表：

c
enum lru_list {
    LRU_INACTIVE_ANON = LRU_BASE,
    LRU_ACTIVE_ANON   = LRU_BASE + LRU_ACTIVE,
    LRU_INACTIVE_FILE = LRU_BASE + LRU_FILE,
    LRU_ACTIVE_FILE   = LRU_BASE + LRU_FILE + LRU_ACTIVE,
    LRU_UNEVICTABLE,
    NR_LRU_LISTS
};

前四条可回收，第五条是第四节那串不可回收页的收容所。ANON 是没有后备存储的匿名映射，FILE 是有后备文件的文件映射。回收时先扫 INACTIVE，INACTIVE 不够了才动 ACTIVE——ACTIVE 链上的页刚被用过，动它们等于把热数据换出去，换回来还要再 IO 一次。

匿名和文件分两条链，是因为回写代价不同：文件页干净时可以直接丢，匿名页必须换出。混在一条链上，回收器看到的是「最久没用的页」，却不知道收掉它的成本是 0 还是一次磁盘写；分开之后，可以按 zone 里两类页的比例决定往哪边出力。

接下来是最巧的一处：判断一个页「活不活跃」需要几个标志位。

假定只用一个 PG_active：页被访问时置位，那什么时候清？这就要为每个页维护定时器。系统里几十万到上百万个 page frame，每个挂一个定时器，光是定时器管理开销就超过收益，方案直接死在规模上。

内核用了两位：PG_referenced 表示「最近被引用过」，PG_active 表示「当前处于活跃态」。算法如下：

  1. 页活跃就置 PG_active，挂在 ACTIVE 链；否则挂 INACTIVE 链。
  2. 每次访问页置 PG_referenced，做这件事的是 mark_page_accessed。
  3. PG_referenced 加上逆向映射提供的信息，用来判断页的活跃程度；每次清这一位时都要检测活跃程度，做这件事的是 page_referenced。
  4. 再次进入 mark_page_accessed。如果发现 PG_referenced 已经置位，说明 page_referenced 还没来检查过——即 mark_page_accessed 的调用频率高于 page_referenced，页经常被访问。此时若页在 INACTIVE 链，把它挪到 ACTIVE，置 PG_active，清 PG_referenced。
  5. 反向转移同样存在：活跃度下降时，会出现连续两次 page_referenced 之间没有 mark_page_accessed，页从 ACTIVE 退回 INACTIVE。

第 3 步里那句「加上逆向映射提供的信息」值得停一下：page_referenced 要判断「这个页最近有没有被访问过」，就得把映射它的 pte 挨个看一遍（pte 里有 access/dirty 位）。这一步需要逆向映射。所以 LRU 的升降级是第二个依赖 rmap 的地方——第一个是 unmap 本身。

两位标志是怎么防抖动的？设想只有一位 PG_active：置位进 ACTIVE，清位回 INACTIVE，而清位靠定时器；定时器到期时页恰好被访问过一次就留下，没被访问就掉回，一次访问的差异就决定升降，页在两条链之间反复横跳，链表顺序失去意义。两位方案的效果是：单次访问只能把 PG_referenced 置上，要让页升级，得在 page_referenced 检查之前有第二次访问——这就是「两次访问才算热」的过滤器。而 page_referenced 的执行频率由回收压力决定，没有回收就没有检查，采样频率天然跟着负载走，不需要任何定时器。

六、kswapd 什么时候醒 #

kswapd 是内核为每个内存 node 创建的一个回收线程。

为什么有了直接回收还要它？因为有些分配根本不允许阻塞等待回收，比如中断和异常处理程序里的分配；还有些分配不允许启动 IO。能完整跑完回收流程的分配路径是少数，所以趁系统空闲先回收，非常必要。

唤醒以后干什么，素材的描述是：kswapd 记录上一次均衡操作时使用的分配 order，如果这次的 kswapd_max_order 比上次大，或者 classzone_idx 比上次小，就调用 balance_pgdat 重新均衡该内存域；否则短暂休眠，时长 HZ/10。balance_pgdat 一直做，直到该内存域满足 zone_watermark_ok。

有个容易看漏的点：kswapd 不是「醒一次回收 N 个页」的定量模型，而是「醒一次把 zone 拉回水位」的定性模型。两个入参的含义是：kswapd_max_order 是这次唤醒要求能分配到的最大 order，要求越大，需要腾挪的连续空间越多；classzone_idx 是允许使用的最高 zone 序号，越靠前（越低端、越紧张）的 zone 被要求，回收越难满足。同一个 zone 连续被唤醒而参数没变，说明上次已经尽力，再跑一遍没有意义，于是睡一小会儿——这是一条「无进展就退让」的规则。

休眠时长要注意换算：HZ/10 在 HZ=100 的系统上是 10 个 jiffy，即 100 毫秒。素材原文把它算成 1ms，见文末勘误。这个值在 HZ=250、HZ=1000 上同样是 100ms——HZ/10 的物理时长恒为 100ms，与 HZ 取值无关，是设计上刻意的常数。

kswapd 停在哪？终止条件是 zone_watermark_ok。它的目标是「回到水位」，不是「回到某个固定空闲量」。水位本身是 zone 大小与 min_free_kbytes 的函数，zone 越大，要求腾出的绝对量越大。这解释了一个常见现象：小内存机器上 kswapd 看起来很闲，大内存机器上一醒就干很久。

七、直接回收与 allocstall #

kswapd 拉不回来，或者分配路径等不及，就走直接回收：__alloc_pages 在慢路径里看到水位不满足、且当前上下文允许阻塞与 IO，就调 try_to_free_pages，由分配者本人同步回收。

三个特点：回收发生在分配者上下文里，回收多久，这次分配就阻塞多久；目标很窄，只凑够本次分配要的 order，不管全局；会重试，回收一轮不够就加压再收，收不动才进 OOM。

目标很窄这点容易被误解。直接回收不追求把系统恢复到舒服状态，它只关心「这一次分配能不能成功」。系统可以刚过完一轮直接回收、水位还在 min 附近，下一次分配又要再来一轮。这种「勉强够用」的状态会一直持续，直到有别的机制介入。

直接回收是「系统已经不舒服」的信号。现代内核在 vmstat 里用 allocstall 一类的计数暴露它——这个口径的具体字段名与统计方式素材没有标注，本文按未验证处理。看到这类计数持续增长，含义是两件事之一：kswapd 跟不上分配速度，或者水位参数配得偏紧。两者排查方向完全不同，前者看回收效率和内存增长速度，后者看 min_free_kbytes 一类参数；混在一起看，会把参数问题误判成容量问题。

这条路径还必须有上限。如果直接回收无限制重试，一个分配请求可以阻塞任意长时间；而回收能力受 IO 带宽限制，IO 卡住时回收卡住，分配者一起卡住。所以上限不是「收够为止」，是「收不动了就 OOM」。OOM 不是失败路径，它是这条路径唯一确定的出口。

八、周期性回收：cache_reap 与 slab 收缩 #

页框之外还有一大块可回收内存：slab。它的回收不走页表，走另一条路。

slab 回收比较灵活：所有注册到 shrinker_list 上的方法都会被执行一遍。素材给了两个例子：内核默认给每个文件系统都注册了 prune_super，用来回收该文件系统里不再使用的 dentry 和 inode 缓存；Android 的 lowmemorykiller 注册的是选择性杀进程，通过杀进程回收它占的内存。

这两个例子的差别有意思：前者回收「没人引用的对象」，后者回收「还活着的进程」。同一个 shrinker 接口，两种完全不同的语义——接口只约定「你能收缩」，怎么收缩由注册者决定。

cache_reap 是定时那一支：回收 slab 里的空闲对象，如果空闲对象能凑回一个整页，就把页还给伙伴系统。每次调用遍历一遍所有 slab_caches，然后休眠 2*HZ。这里的换算同样要注意：2*HZ 即 2 秒，与 HZ 取值无关。素材原文写「对 arm（HZ=100）来说周期就是 20ms」，见文末勘误。

为什么不走 LRU？slab 对象没有「页」这个粒度可供 LRU 管理。一个 slab 页里往往放着几十个对象，其中几个被引用、其余空闲；这个页既不能整体回收，也不能整体留在 LRU 上。所以 slab 的回收单位是「对象」而不是「页」：先尝试回收空闲对象，只有当整个 slab 页都空了，才谈得上把页还给伙伴系统。这条路径和页框回收唯一的交汇点是伙伴系统——两条路都往 free list 里还页。slab 侧的内部实现（怎么判断一个 slab 空了、怎么 kmem_cache_shrink）见 slab 与 slub 分配器。

九、回收一个页之前必须先做什么 #

到这里，「回收谁、按什么顺序」已经清楚了。剩下是执行。真正把一个页还给伙伴系统之前，必须完成五个动作：

  1. 找到所有映射到这个页的 pte。一个物理页可以被多个进程、多个虚拟地址映射，少找一个都不行。
  2. 逐个解除映射。匿名页要把 swap 分区号和页内 slot 号写进 pte；文件页直接把 pte 清零。
  3. 处理脏数据。匿名页走换出，文件页走回写；都是 IO，都要等。
  4. 处理不能动的页。PG_reserved、PG_locked（正在 IO）、mlock 锁定的页，遇到就放过。
  5. 确认引用计数归零。只要还有一个 pte 指着它，这个页就不能回伙伴系统。

第 1 步是全部工作的前提。第 2 步的正确性完全依赖第 1 步的完整性：漏掉一个 pte，页被回收重用之后，那个 pte 还指着它，进程读到的就是别人的数据，写的也是别人的数据。这不是性能问题，是数据损坏。这里没有「部分成功」的余地——找不到全部 pte 的方案，功能上就不成立，不管它多快。

于是问题收敛成一句话：已知一个 struct page，怎么找出所有映射它的 pte？

这就是逆向映射。本文后半段全部在讲它的历史。素材里那句话值得复述：如果回收的 page frame 在内核 cache 里（slab 之类），直接回收，没有页表操作；如果回收的是用户进程空间的 page frame，那么回收之前必须对该 page frame 做 unmapping。所以逆向映射只服务于用户页这一半，但这一半恰好是最难的。

十、逆向映射要解决的问题 #

先看正向映射，它每天都在发生。进程分配了一段 VMA，此时没有对应的 page frame；程序访问这段 VMA，触发缺页异常，内核分配物理页，逐级填好页表。正向映射就是「已知虚拟地址，建立到物理页的映射」。

逆向映射反过来：已知 page frame（可以是 PFN、可以是指向 page descriptor 的指针、也可以是物理地址，内核有一组宏在它们之间转换），找出映射到它的所有虚拟页。因为一个 page frame 可以被多个进程共享，逆向映射的任务就是把散落在各个进程地址空间里的 pte 全部找出来。

两个典型的共享场景：COW 的 fork，子进程没写之前父子共享同一批 page frame；公共库，c lib 被 file mapping 到大量进程的地址空间，它的正文段对应的 page frame 会挂上非常多的 pte。一个进程的地址空间内，同一个 page frame 被映射两次的情况很少；看到多个映射，基本就是跨进程共享。这句话是后面分析 rmap 优化路线的起点——共享的规模决定了索引该建在哪里。

为什么需要它？为了页面回收。回收内核 cache 里的页不需要动页表，直接还；回收用户进程的页必须先 unmap。具体到 swapping：释放一个匿名页时，要把 swap 区和 slot index 写进所有相关 pte；只有所有 pte 都改完，才能把这个页换出去、回收掉。demand paging 的场景一样，只是把 pte 清零而不是写 swap entry。

这里有个贯穿全史的硬约束：在页被真正标记为「可回收」之前，所有 pte 必须已经指向 swap entry。否则中间任何一次访问都会拿到一张已经被回收的页。这个约束在演进史里没变过，变的只是「怎么找到那些 pte」。

十一、史前文明：没有 rmap 的时代怎么做 #

这一节的分析基础是 2.4.18 源码（2.4.x 时代）。

2.4 的 struct page 里没有任何逆向映射数据。内核没法用简单方法从 page frame 走到 pte。那回收一个被多进程共享的页怎么办？

回收用户进程的页本身不复杂，靠 memory mapping 和 swapping 两套机制，原理类似，一个管 file mapped page，一个管 anonymous page。流程都是：把进程不常用的 page frame 换到磁盘，同时解除进程和这个 page frame 的一切关系；两步做完，页框自由，可以回伙伴系统。

问题在第二步。不常用的页很好找（INACTIVE LRU 链），断绝 page frame 和进程们的关系很难。2.4 的选择是：扫描整个系统的进程地址空间。

系统里所有进程地址空间（memory descriptor）串成一条链表，链表头是 init_mm。所谓 scan，就是沿着这条 mm 链表走。回收器尽量不走到这一步：先收缩内存 cache，再遍历 inactive_list 挑那些不和任何进程相关的页，凑够本轮数目就收工。凑不够，才启动进程物理页回收。这个分层说明当时的设计者很清楚代价——扫描是最后手段。问题在于压力越大越需要它，而它偏偏在大系统上最贵。

这一段由 swap_out 完成，结构是三层嵌套：

  1. 沿 init_mm，对每一个进程地址空间走一遍。
  2. 扫一个地址空间时，对属于它的每一个 VMA 走一遍。
  3. 扫一个 VMA 时，对属于该 VMA 的每一个页走一遍。

具体干活的是 try_to_swap_out：条件满足就解除这个 page frame 和这个进程的关系，做必要的 IO，页的引用计数减一，对应 pte 清零或写入 swap entry。

关键点落在共享页上。扫到进程 A 的 page frame 0，如果只被 A 映射，直接 unmap 加回收；共享页不行——扫 A 的时候把 A 和 page frame 1 的关系解了，但不能回收，因为进程 X 还在用；要一直扫到 X，完成 X 的 unmap，这个页框才回得了伙伴系统。

这就是「史前文明」的全部机制。没有索引，没有反查，只有暴力遍历。回收一个页的代价，等于「扫到所有映射它的进程」这个距离。

十二、地址空间扫描的代价与三个硬伤 #

扫描到哪儿停？两个终止条件：目标达成（本轮要 reclaim 32 个 page frame，收够就停，不必扫完整个虚拟地址空间）；或者扫完了整个系统的地址空间还是不够，那是 OOM 的边缘。

公平性怎么保证？swap out 影响进程性能，不能让少数进程被反复薅。所以每次扫完记录当前位置：进程级游标存在 swap_mm 里，下次从 swap_mm 继续；进程内部还有虚拟地址游标 mm->swap_address，下次从 swap_mm->swap_address 继续。两级游标，两级轮转。设计上是对的，代价是这套状态本身也要维护，而且游标的语义在多进程并发扫描时很难说清。

算一笔账：

维度 量级 说明
单次回收的扫描面 进程数 × 每进程 VMA 数 × 每 VMA 的页数 三层嵌套，最坏情况全系统
回收一个共享页 要扫到所有映射它的 mm 一个页可以拖垮一整轮
每轮的最小开销 与进程总数成正比 进程越多越慢，与目标页数无关
状态维护 两级游标 swap_mm 与 mm->swap_address

注意第三行：每轮最小开销与实际回收了多少页无关，只和系统规模有关。系统越大，回收的固定成本越高，而回收又恰恰在最需要它的时候被调用。

三个硬伤：

硬伤一，共享页要多次「相遇」才能收掉。一轮扫描只解除一层关系，回收一个被 N 个进程共享的页要扫到 N 次，而这 N 次之间没有任何协调。c lib 的正文段被几百个进程映射，收掉一个页就要扫几百次。

硬伤二，unmap 之后对方又访问，映射就重建了。扫 A 时解了 P，A 又访问 P，映射回来；扫 B 时解了 P，B 又访问，映射又回来。理论上这个页永远收不掉。素材原文对这段的吐槽是「理论上是这样的，别问我，其实我也很绝望」。这不是笑话，它说明系统缺少「定向」能力：回收器没法说「我要这个页，把它收掉」，只能一边扫一边希望对方不要再碰。

硬伤三，系统级扫描不可扩展，而且回收是被动的。回收器只能「扫过什么收什么」，不能「我要这个页，把它收掉」。服务器跑几百个进程，每轮回收的固定成本就压在那里；进程越多，单轮回收越慢，而分配路径恰恰在最忙的时候最需要它快。

三个硬伤指向同一个缺失：page 到 pte 的索引。谁把这张索引建起来，谁就把回收从「扫全世界」变成「顺着链子走」。

十三、开天辟地：pte_chain 的设计 #

时间回到 2002 年 1 月。VM 大神 Rik van Riel 维护的代码被一套全新的 VM 子系统取代，他没有消沉，转头做了一个东西：reverse mapping，下文简称 rmap。第一版 rmap 的代码基线是 Linux 2.6.0。

最直观的设计：给每个 page frame 维护一个链表，保存属于它的所有 pte 指针。于是 struct page 里加一个成员：

c
struct page {
    ……
    union {
        struct pte_chain *chain;
        pte_addr_t direct;
    } pte;
    ……
};

用 union 是有原因的：绝大多数页根本不共享，只有一个 pte，此时 direct 直接指向那个 pte；只有共享页才需要 chain 指向一条 struct pte_chain 链表。这个取舍符合实际分布：Linux 系统里大部分 page frame 是私有的（进程栈、堆、私有匿名页），共享页是少数。为多数情况优化，用一个指针解决多数场景，剩下的用链。

链表节点是这样设计的：

c
struct pte_chain {
    unsigned long next_and_idx;
    pte_addr_t ptes[NRPTE];
} ____cacheline_aligned;

只存一个 pte 指针太浪费，所以让整个结构对齐到一个 cache line、正好占满一个 cache line：除了 next_and_idx（指向下一个 pte_chain，串成链），剩下的空间全用来放 pte 指针数组。

____cacheline_aligned 不是装饰。它保证结构体不跨 cache line，一次访存就能读完，不会出现伪共享；同时对之后低位有富余，可以拿来存东西。

数组就需要一个下标记录「下一个空位在哪」。这里省下了一个字段：结构体按 cache line 对齐，next_and_idx 的低若干位必然是 0，于是把这几位复用成 index。这是典型的内核手法——用对齐保证出来的空闲位存元数据。收益是每个节点少一个字段、整个节点塞进一个 cache line；代价是可读性，读代码的人必须知道「那个指针低位不是地址」。

回收路径的改写很直接：unmap 一个页从「扫全世界」变成一次链表遍历。还多了一个便宜的分支——页没有被共享时（置了 PG_direct 标志），page->pte.direct 直接命中唯一的 pte，连链表都不用走。于是 try_to_unmap 的分派变成两级：置了 PG_direct 就走 page->pte.direct，调一次 try_to_unmap_one；否则沿 pte_chain 依次调 try_to_unmap_one。

十四、struct page 为此改了什么 #

改动只有一行 union，代价要算清楚。

常驻开销：每个 page frame 都有一个 struct page，加一个指针成员，32 位系统上是 4 字节。看着不多，但要乘以物理页总数——4G 内存、4K 页大小就是一百万个 page frame，4MB 常驻内存，全系统的 struct page 数组一次性涨这么多。而且这部分内存不可回收：struct page 数组在启动时按最大内存量预留，没有任何回收路径，它是纯税。

动态开销：共享页要建 pte_chain 链表，每个节点占一个 cache line，节点里装 NRPTE 个 pte 指针。共享越普遍，开销越大。最坏情况是公共库的正文段：几百个映射，每个映射一个 pte 指针，分散在几十个节点里，每个节点浪费掉一个 cache line 的绝大部分。

性能开销在 fork，这是最容易被忽略的。fork 时父子进程共享大量 page frame，copy_page_range 复制页表的过程中要同步维护 pte_chain——每一个共享页都要往链上挂节点。父子共享得越多，fork 越慢，而 fork 恰恰是网络服务器最热的那条路径。

回头对照第十二节：旧机制把成本放在回收路径上（扫地址空间），新机制把成本分摊到了 fork 和每个页的结构体上。成本没消失，只是换了位置。这个转移在当时是划算的，因为回收是偶发的、struct page 和 fork 是常驻的——直到常驻成本大到撑不住。

代价 性质 与什么成正比 什么时候痛
struct page 多一个指针 常驻、不可回收 物理页总数 大内存机器
pte_chain 节点 动态、只在共享时 共享映射数 共享密集的服务器
fork 时建链 每次 fork 都要付 共享页数 × 子进程数 靠 fork 处理请求的服务

这三层就是「女娲补天」要补的窟窿，第一层最硬。

十五、回收算法怎么跟着改 #

有了 rmap，回收算法的骨架变了。对照一下：

环节 无 rmap（2.4.x） 有 rmap（2.6 早期）
找 pte 沿 init_mm 扫全部地址空间 从 struct page 直接出发
入口 swap_out 三层嵌套 try_to_unmap
单页操作 try_to_swap_out try_to_unmap_one
共享页 要扫到每个 mm 才收得掉 一条链走完，当场收掉
回收目标 被动（扫到谁收谁） 主动（选中谁收谁）
成本与什么相关 进程数 × VMA 数 共享该页的映射数
扫描游标 swap_mm + mm->swap_address 不需要

差别最大的是「回收目标」那一行。旧机制下回收器没有选择权：它沿着链表扫，扫到什么符合条件的页就收什么，找到一个特定的页之后也没法从它出发找 pte。新机制下它可以指哪打哪——看中的 page frame，总能通过 try_to_unmap 解除和所有进程的关联，然后回伙伴系统。

这个能力上的变化，比速度上的变化影响更大。第十二节那三个硬伤，全是「没有选择权」导致的。

有了它，三个硬伤一起消失：共享页一次收掉（沿链走完）；不存在映射重建后收不掉的问题（unmap 是定向的、同步的）；没有系统级扫描的固定成本。代价换个地方出现——每个页都背了一个指针，共享越多链越长，fork 越慢。

十六、女娲补天：file mapped 的优化 #

第一版 rmap 的窟窿有多大，看它挡了谁的路。

1999 年 Linus 的态度是：32 位 Linux 内核永远不支持 2G 以上的内存。处理器厂商做了扩展寻址，高端服务器内存越来越大，这个结论被现实推翻，内核开始支持更大内存。

红帽的 Andrea Arcangeli 当时在让 32 位 Linux 跑在 32G 以上的服务器上。这类机器进程多、共享页多、内存消耗大，他很清楚元凶是谁：逆向映射模块吃掉了太多 low memory，导致系统各种崩。要把工作推下去，就必须解决 rmap 引入的内存可扩展性问题。

注意「low memory」这个限定。32 位内核里只有低端内存能被内核直接寻址，struct page 数组必须放在这一块。所以 rmap 的常驻开销不是「多用了 4MB 物理内存」这么简单，它挤占的是一块稀缺且无法挪动的地址空间——这是 32 位时代的特殊约束。

2.5 开发期间，IBM 的 Dave McCracken 已经提交过 patch，想在保住逆向映射功能的同时修掉 rmap 的问题。他的方案是基于对象的逆向映射，object-based reverse mapping，下文简称 objrmap。思路对调：过去是从 struct page 直接拿到 ptes；objrmap 借别的数据对象做中转，从 struct page 走到 VMA，再从 VMA 走到 pte。

对 file mapped page，中转站现成：struct page 里的 mapping 成员指向一个 struct address_space，它属于某个文件，保存该文件 page cache 的信息。我们关心的成员叫 i_mmap：一个文件可以被映射到多个进程的多个 VMA，这些 VMA 全挂在 i_mmap 指向的 Priority search tree 上。用树不用链表是因为规模——一个被广泛使用的文件（libc 这类）会有非常多的映射，链表遍历不可接受。

有了 VMA，还差虚拟地址：

c
static inline unsigned long
vma_address(struct page *page, struct vm_area_struct *vma)
{
    pgoff_t pgoff = page->index << (PAGE_CACHE_SHIFT - PAGE_SHIFT);
    unsigned long address;

    address = vma->vm_start + ((pgoff - vma->vm_pgoff) << PAGE_SHIFT);

    return address;
}

读法：page->index 是该页在文件内的偏移（字节为单位）；vma->vm_pgoff 是该 VMA 映射到文件内的偏移（页为单位）；先统一到页单位，相减得到该页在这个 VMA 里的页偏移；乘页大小加 vma->vm_start，就是这个 page frame 对应的虚拟地址。拿到虚拟地址和地址空间（vma->vm_mm），顺着各级页表就能取出 pte，再交给 try_to_unmap_one。

这条路换来了什么：

维度 pte_chain objrmap（file mapped）
查找路径长度 page → pte 链 → pte（短） page → address_space → i_mmap 树 → VMA → 页表 → pte（长）
每页常驻开销 一个指针 0（复用 mapping）
共享关系维护 显式建链、fork 时要维护 隐含在 VMA 与 i_mmap 里，天然存在
fork 开销 每共享页挂一个节点 无额外操作

省下的是「每个页的指针」和「共享关系的显式维护」，付出的是「每次 unmap 多走几层」。这笔交易成立的前提是：unmap 比 fork 和内存占用稀疏得多。回收是偶发的，struct page 数组和 fork 是常态的。用偶发路径上的一点延迟，换常态路径上的空间和速度，方向是对的。

十七、女娲补天：匿名页的优化 #

objrmap 只解决了 file mapped page。用户进程的页有两大类，匿名映射页还得另想办法，最终形成 full objrmap。这一段的代码基线是 2.6.11。

匿名页这一支的主线是 Andrea Arcangeli 的 full objrmap 方案。他的竞争对手 Hugh Dickins 也提交了一系列 full objrmap 补丁想并进主线；在匿名页这块，最后胜出的是 Andrea。同一个问题的两条路线，按合入主线的结果定了胜负。

匿名页的中转站不能是 address_space，因为匿名页没有后备文件。方案是造一个 anon_vma，让它承担 address_space 那份角色：从它出发能找到映射到该页的所有 VMA。

为了省内存，mapping 指针被复用了：file mapped page 的 mapping 指向文件的 address_space，anonymous page 的 mapping 指向 anon_vma。省了字段，牺牲可读性；内核还是这么干了，理由很实在——每个 page frame 都有一个 struct page，这里加 4 字节，全系统就是几十 MB 级别。上一节刚算过：32 位机器上，struct page 里省下的每一字节都值钱。这正是「女娲补天」这个词的由来，补的就是第十四节三层代价里最硬的第一层。

复用指针就得有区分手段，用最低位：

page->mapping 取值 含义
NULL 该 page frame 不在内存里，已被 swap out 到磁盘
非 NULL，最低位为 1 匿名映射页，指向一个 anon_vma
非 NULL，最低位为 0 文件映射页，指向该文件的 address_space

用最低位是因为 anon_vma 和 address_space 都按字对齐，最低位天然是 0，可以拿来打标记。第一位（NULL）值得单独说：它表示这个页被换出去了，swap 里有位置，struct page 还在，但内容不在内存。这在回收路径上很常见，判断时不能当匿名页或文件页处理。

数据结构选型按规模来：文件映射页的 VMA 数量会非常大，用 Priority search tree；匿名页的 VMA 数量一般不会太大，链表就够了。这句「一般不会太大」在第十八节被推翻——网络服务器靠 fork 打天下，匿名页的 VMA 数量可以大到离谱。当时的选择基于当时的负载认知。

从 VMA 到 pte 的算法和 file mapped 一样，还是 vma_address，只是基准点不同：file mapped 的基准点是文件起始位置；shared anonymous mapping 的基准点是 0；private anonymous mapping 的基准点是这段 mapping 的虚拟地址除以页大小。基准点不同，公式的语义不变。

到这里两条支流汇合：无论匿名还是文件映射，路径都是 page → 承载对象 → VMA → vma_address → 页表 → pte。差别只在承载对象是 anon_vma 还是 address_space，以及承载对象内部用红黑树还是 Priority search tree 管 VMA。一套算法覆盖两类页，这是 objrmap 方案最大的收获。

十八、卷土重来：从 pte_chain 到 anon_vma 与 rmap 树 #

full objrmap 进内核后，各项指标都好过它的前任。第一次把逆向映射带进内核的 Rik van Riel 挨了第二次打击，但他还盯着一个地方：objrmap 的天空里有一朵乌云——旧的 anon_vma 机制。这一节代码基线是 4.4.6。

先看旧机制怎么跑。VMA_P 是父进程的一个匿名映射 VMA，页 A 和 C 已经分配了 page frame，其他页还没分配。fork 之后子进程复制 VMA_P，因为 COW，父子进程的匿名页共享，两边对应 pte 标上 write protect。

不同进程的匿名页（栈、heap）本来该是私有的，但为了省内存，fork 之后、写之前，父子共享，这些 page frame 指向同一个 anon_vma。共享是短暂的：一旦写就触发异常，异常处理里分配新 page frame，解除共享。

问题在于，解除共享之后，两个页仍然指向同一个 anon_vma。不仅解共享的页如此，像 B 那样一开始就没共享的页，首次访问时由 do_anonymous_page 分配出来，同样指向这个 anon_vma。也就是父子进程的 VMA 共享一个 anon_vma。

现在 unmap page frame 1 会发生什么？它的 mapping 指向那个 anon_vma，遍历会命中 VMA_P 和 VMA_C，其中 VMA_C 是无关的，本来就不该匹配到。

c
static int try_to_unmap_anon(struct page *page)
{
    ……
    anon_vma = page_lock_anon_vma(page);
    list_for_each_entry(vma, &anon_vma->head, anon_vma_node) {
        ret = try_to_unmap_one(page, vma);
    }
    spin_unlock(&anon_vma->lock);
    return ret;
}

这段框架里藏了一个长临界区：遍历 VMA 链表时持着 anon_vma->lock。链上大量 VMA 跟要 unmap 的页无关，只能一个个试、一个个跳过，复杂度 O(N)，临界区被拉长；其他 CPU 抢这把锁时基本卡住。

Rik van Riel 给的例子很具体：系统里 1000 个进程都由 fork 生成，每个进程的 VMA 有 1000 个匿名页，于是 anon_vma 链表上有 1000 个 VMA 节点，而系统里有一百万个匿名页属于同一个 anon_vma。一百万个页共享一把锁，竞争有多激烈不用多说。更糟的是 unmap 不是唯一会这么干的路径，page_referenced 也持有同一把锁、遍历同一个链表。回想第五节：page_referenced 是 LRU 升降级的核心函数，被回收器高频调用。两把重活压在同一把锁上。

症结清楚了：anon_vma 承载了太多无关进程的 VMA。处方也清楚：把它变成 per-process 的，用一个中间结构把父子进程的 anon_vma（下称 AV）和 VMA 连起来。新结构叫 anon_vma_chain（下称 AVC）：

c
struct anon_vma_chain {
    struct vm_area_struct *vma;   /* 指向该 AVC 对应的 VMA */
    struct anon_vma *anon_vma;    /* 指向该 AVC 对应的 AV */
    struct list_head same_vma;    /* 链入 VMA 的 AVC 链表 */
    struct rb_node rb;            /* 链入 AV 的红黑树 */
    unsigned long rb_subtree_last;
};

一个 AVC 同时持有 VMA 和 AV 两个指针，于是它成了两棵树之间的桥：所有指向同一个 VMA 的 AVC 串成链表，链表头是 VMA 的 anon_vma_chain 成员；一个 AV 管理若干 VMA，所有相关 VMA（子进程、孙进程……）挂进红黑树，根是 AV 的 rb_root。同一份数据用两种索引——按 VMA 查是链表，按 AV 查是红黑树；AVC 同时是链表的节点和红黑树的节点，所以两个方向都通。

搭建过程从一次 exec 之后开始。子进程 exec 加载自己的 image，和父进程分道扬镳（flush_old_exec），此后它的匿名 VMA 第一次缺页、分配到第一个 page frame 时，建立的关系是：AV0 是这个进程的 anon_vma，它是顶级结构，root 和 parent 都指向自己；AVC0 是 VMA0 和 AV0 的桥，两个指针分别指向 VMA0 和 AV0，同时插入 AV0 的红黑树和 VMA0 的链表；新分配 page frame 的 mapping 指向 AV0，index 指向该页在 VMA0 内的偏移。后续 VMA0 里再分配多少页，结构都不变，只是每个页的 mapping 都指向 AV0。走这条路的代码看 do_anonymous_page、do_cow_fault。

fork 的时候，子进程复制父进程的 VMA（dup_mmap），有自己的 VMA，也分配自己的 AV——旧机制下多进程共享一个 AV，新机制里 AV 是 per-process 的。分两步：先 anon_vma_clone 建立子进程 VMA 和「父进程们」AV 的关系，再建立子进程 VMA 和自己的 AV 的关系。

所谓「建立 VMA 和 AV 的关系」，就是 anon_vma_chain_link 三步：分配一个 AVC，两个成员指针指向对应的 VMA 和 AV；把 AVC 加进 VMA 链表；把 AVC 加进 AV 红黑树。

先看两层。父进程创建子进程时，要连子进程 VMA1 和父进程 AV0：遍历 VMA0 的 anon_vma_chain 链表（此时链表里只有 AVC0，连的是 AV0），分配一个 AVC_x01 作为桥梁。命名规则是 x 表示连接，01 表示连接 level 0 和 level 1。它插入 AV0 的红黑树，于是父进程能找到子进程的 VMA；它插入 VMA1 的链表，于是子进程能找到父进程的 AV——一个结构，两个方向。自己的 AV 也要建：AV1 是子进程的 anon_vma，再分配 AVC1 连 VMA1 和 AV1，同样插进 VMA1 的链表和 AV1 的红黑树。父进程每 fork 一个子进程，AV0 的红黑树里就多一个起桥梁作用的 AVC。

子进程再 fork，就是三层。复制 VMA 时沿 VMA1 的 AVC 链表走，该链表有两个元素 AVC1 和 AVC_x01，分别关联自己的 AV 和父进程的 AV。于是在孙进程里分配 AVC_x02 和 AVC_x12，建立 level 2 与 level 0、level 1 的连接；再分配 AVC2 连 VMA2 和 AV2。层级关系靠 AV 的两个指针表达：parent 指向上层进程的 AV，root 指向 root AV（最顶层进程的 AV）。从任意一层都能往上走到根，从根也能往下找到所有后代。

page 什么时候进这座大厦？两种情况，最后都落到「把这个 page 的 mapping 指向它所属进程的 AV」：父子都没有 page frame 时，do_anonymous_page 分配页，调 page_add_new_anon_rmap 建立页与 VMA 的关系；父子共享匿名页、发生 write fault 时，分配新页，同样调 page_add_new_anon_rmap，代码在 do_wp_page。

这么绕的结构到底为什么？用一个例子回答：P 进程某个 VMA 里有两类页，有物理页的和还没分配物理页的，跟踪有物理页的 A 和没分配的 B；P fork 出 P1 和 P2；P1 fork 出 P12；P1 访问 A，分配 page frame 2；P12 访问 B，分配 page frame 3；P2 访问 B，分配 page frame 1；P2 fork 出 P21。

看共享范围：指向 AV_P 的页（mapping 指向 P 的 AV），会被任意 level 的子进程 VMA 共享，所以 AV_P 必须包含其子进程、孙进程的所有 VMA。而 AV_P1 只需要包含 P1 的子进程、孙进程的 VMA，可以肯定父进程 P 和兄弟进程 P2 的 VMA 不该在里面。大厦的结构正好符合这个范围：每一层的 AV 覆盖自己的子树，向上通过 parent 可达、向下通过红黑树可达，横向的兄弟关系不在同一棵树上。对比旧机制——所有进程的 VMA 都在一条链表上，父子兄弟一锅端；新机制下，树的结构就是共享范围的边界。

回收时用这套结构 unmap 一个页：从 struct page 的 mapping 找到 AV，遍历它的红黑树拿到所有与该页相关的 VMA，逐个调 try_to_unmap_one。回到开头那个长临界区：服务进程 A fork 了 999 个子进程，A 有一个 VMA、1000 个页。旧机制下每次 unmap 都要扫 1000 个 VMA；新机制下只有顶层 A 的 AV 里挂着 1000 个 VMA，其他子进程的 AV 里 VMA 数是 1，临界区长度大幅下降。一百万个页共享一个 anon_vma 的场景直接消失了。

两代方案摆在一起：

维度 pte_chain（2.6.0 基线） anon_vma + AVC（4.4.6 基线）
索引建在谁身上 每个 page 一条 pte 链表 每个进程一个 AV，AV 用红黑树管 VMA
每页常驻开销 一个指针（32 位 4B） 复用 mapping，零额外字段
共享关系表达 显式维护 pte_chain 链表 由 VMA/AV 层级隐式表达
unmap 路径 page → pte 链 → 全部 pte page → AV → 红黑树 → VMA → vma_address → pte
fork 成本 每个共享页都要往链上挂节点 每个 VMA 建若干个 AVC
单次 unmap 复杂度 与共享 pte 数成正比 与该 AV 红黑树里的 VMA 数成正比
主要弱点 内存开销、fork 变慢 无谓 VMA 仍要遍历，但范围收敛到子树

注意最后一行：新方案没有做到「精确」，它做到的是「范围收敛」。AV 的红黑树里仍然有与该页无关的 VMA（同一个 VMA 里的其他页没共享到），只是数量从「所有进程」降到了「同一棵子树」。精确性的保证仍然落在 pte 层。

十九、今天的样子：rmap_walk 与 try_to_unmap #

把历史拉平，现代内核的形态是三层。

第一层是统一入口。回收器只知道「我要 unmap 这个 page」，不关心它是匿名还是文件映射。分派靠 PageAnon 一类判断，落到两条实现上；这两条实现被一个统一的遍历框架 rmap_walk 包起来，调用方给出回调（单页回调、结束回调），遍历逻辑复用。素材只讲到 try_to_unmap_anon 这一层，rmap_walk 的分层命名与回调接口原文未标注，本文按未验证处理。

第二层是两条查找路径：

text
try_to_unmap(page)
│
├─ PageAnon(page) ──► rmap_walk_anon
│     page->mapping(低位=1) ──► anon_vma
│         └─ anon_vma 红黑树 ──► 候选 VMA 们
│               └─ vma_address(page, vma) ──► 虚拟地址
│                     └─ 页表逐级查找 ──► pte ──► try_to_unmap_one
│
└─ 否则 ────────────► rmap_walk_file
      page->mapping(低位=0) ──► address_space
          └─ i_mmap 树 ──► 候选 VMA 们
                └─ vma_address(page, vma) ──► 虚拟地址
                      └─ 页表逐级查找 ──► pte ──► try_to_unmap_one

两条路径的中段完全对称：

环节 anon 分支 file 分支
承载对象 anon_vma address_space
从 page 到承载对象 page->mapping，最低位为 1 page->mapping，最低位为 0

差别只在「承载对象是谁」和「承载对象内部用什么容器」——正好是第十七节留下的全部遗产。

第三层是单页操作。try_to_unmap_one 做四件事：验证 pte 确实指向目标 page（防止并发下已经改过）；改 pte（匿名页换成 swap entry，文件页清零）；清 TLB；减引用计数。

第 1 步是关键设计：候选 VMA 只是「候选」，不是「一定命中」。红黑树和 i_mmap 树给的是范围，最终确认靠「用 vma_address 算出地址，再看这个 pte 是不是真指着目标页」。这是在「索引精确但贵」和「索引粗但便宜」之间的取舍——索引只保范围，真相到 pte 层验证。

四代方案放在一张表里：

代际 方案 时间锚点（素材标注） 索引对象 主要代价
第 0 代 无 rmap，扫 init_mm 链 2.4.x 时代（2.4.18 源码） 无索引 与进程数成正比，共享页反复扫
第 1 代 pte_chain 2.6.0 源码基线，2002 年 1 月起 每个 page 一条 pte 链 每页一个指针，fork 变慢
第 2 代 objrmap（file: i_mmap 树 / anon: 旧 anon_vma 链表） 2.5 开发期提 patch，2.6.11 源码基线 文件用 address_space，匿名用进程级 anon_vma 匿名侧链表过长，长临界区

把四代看一遍，能看到一条摆动：第 1 代把索引从「全局扫描」搬到「每页一个指针」，代价从时间转成空间；第 2 代把索引从「每页」搬到「每个承载对象」，代价从空间转成路径长度；第 3 代把匿名侧的承载对象从「进程组共享」搬到「每进程一个」，代价从临界区长度转成树遍历的冗余。每一代都在解决上一代的代价，同时引入新的代价。没有终局方案，只有针对特定时代硬件与负载的局部最优。

二十、一个 page 的回收全过程 #

把前面所有零件串起来。假设回收器从 INACTIVE 链上取到了一个页，想把它还给伙伴系统：

text
1. 从 LRU 摘下候选页（lru_to_page 取链尾，即最久未使用）
        │
2. 判活：page_referenced 看 PG_referenced / PG_active
        │  还活跃 ──► 挪到 ACTIVE 链，放回，换下一个候选
        ▼
3. 检查硬性条件：PG_reserved / PG_locked / mlock / 引用计数
        │  命中 ──► 放过这个页
        ▼
4. try_to_unmap：解除所有映射（本文后半段的全部内容）
        │  page → mapping → anon_vma / address_space → VMA → pte
        │  每命中一个 pte 调一次 try_to_unmap_one
        ▼
5. 分类处置
        │  ├─ 文件页且干净 ──► 直接丢，零 IO
        │  ├─ 文件页且脏  ──► 回写，等 IO
        │  └─ 匿名页      ──► 写 swap 分区，pte 存 swap entry
        ▼
6. 引用计数归零 ──► 释放回伙伴系统（或 memcg 记账处）

真正执行这一串的是 shrink_page_list，素材对它的描述只有一句「真正回收页面的过程」，内部的分支（是否 unmap、是否 pageout、批量处理）原文没有展开，本文按未验证处理。

整条链路里只有第 4 步依赖逆向映射。前三步在有 rmap 之前就存在，第五、六步也是。这也是为什么逆向映射的演进能独立成一段历史：它解决的是回收流程里的一个子问题，而这个子问题恰好是最难的那个。

按代价排，三步最重：

步骤 代价 什么时候成为瓶颈
第 4 步 unmap 找 pte + 改 pte + 清 TLB 共享多、映射多
第 5 步 pageout 一次磁盘写 swap 慢、回写拥塞
第 2 步判活 遍历 pte 看访问位 映射多，且这是高频路径

第 2 步值得一提：page_referenced 也要遍历 pte，和 unmap 走的是同一套逆向映射索引。所以 rmap 的每一次优化，同时改善两条路径——回收和 LRU 升级。

最容易错的是第 4 步。漏一个 pte 是数据损坏，改错一个 pte 也是数据损坏。第 3 步容易错在判据不全：只查 PG_reserved 不查 PG_locked，就会在 IO 进行中把页交出去。
