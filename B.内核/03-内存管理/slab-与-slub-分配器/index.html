一、为什么在伙伴系统之上还要一层分配器 #

伙伴系统的最小单位是页，4KB 起步，order 到 11 是常见上限。内核里大量对象是几十字节到几百字节：一个 struct file、一个 struct dentry、一个 socket 的接收缓冲头。为这几十字节分一整页，剩下的部分就锁死了——既不能给别人用，也还不回伙伴系统。几条硬约束摞在一起，决定了这层分配器长什么样：

需求 对分配器的约束
对象从 8 字节到几 KB 都有 按大小分级，每级一个缓存池
同一大小的对象反复申请释放 释放的不回伙伴系统，留在池里复用
分配极其频繁（网络收发、路径查找） 路径要短，最好不拿锁
多核并发申请、NUMA 上远端内存慢 每 CPU 一份本地缓存，每 node 一份共享池
cache 行 64 字节，跨行代价高 对象首地址按 cache 行对齐（SLAB_HWCACHE_ALIGN）

名字来自 Solaris 2.4，90 年代初那边管它叫 slab，原意是大块的混凝土。SLAB 当了很多年主流，代码复杂到长时间没人愿意动。多核与 NUMA 铺开之后几个问题藏不住：满链、半满链、空链一堆队列要维护；每个 slab 一份元数据，开销大；节点间 slab 迁移规则难跟；调试时一串队列状态互相牵制。

Christoph Lameter 在 2.6.22 交了 SLUB。思路是简化：保留「一个缓存池由多个 slab 组成、每个 slab 装固定数量 object」这个基本盘，砍掉那堆队列，元数据尽量塞进 struct page，本地缓存做成 per-cpu 变量。对外 API 全保留，驱动代码一行不改就能跑。SLAB 还有个 slab 着色（cache coloring）机制，用错开起始偏移摊分 cache 冲突；SLUB 认为收益不明显，去掉了，改成按 cache 行对齐。这条常被误列成 SLAB 的缺点，它其实是 SLUB 的设计取舍。

二、slab / slub / slob 三个实现的关系 #

三个都是同一族分配器，对外同一套 API：kmem_cache_create / kmem_cache_alloc / kmem_cache_free / kmem_cache_destroy。编译期只选一个，靠 CONFIG_SLAB / CONFIG_SLUB / CONFIG_SLOB 决定。「slab」这个词有三层含义：机制名、SLAB 这个具体实现、三个实现的统称。素材里混用了，本文也照混——讲机制时说 slab 分配器，讲实现时写 SLUB 或 SLAB，讲内存池时写 slab 页。

维度 SLAB SLUB SLOB
元数据放哪 独立的 struct slab 管理区 复用 struct page 字段 全局一个 first-fit 链表
本地缓存 per-cpu array cache（三链队列） per-cpu 一个 kmem_cache_cpu 无
空闲对象组织 队列 + 位图/链表 object 内部嵌 freepointer 单链表 页内 first-fit
着色 / NUMA 有 / 支持但复杂 无 / kmem_cache_node 按 node 分 无 / 一般不关心
目标场景 通用（历史默认） 通用（新默认） 极小内存嵌入式

SLUB 从 2.6.23 起成为默认，之后 SLAB 被标为遗留并最终移出主线，SLOB 只在极小内存配置里出现过。这两个移除动作的确切版本号素材没给，本文未验证，动手前 grep CONFIG_SLAB 看你手上的源码树比较实在。

三、SLUB 的核心结构：kmem_cache #

一个 kmem_cache 描述一个缓存池：对象多大、一页切几个、从哪拿页、本地缓存指针在哪。下面是 4.15 的字段，按素材原样保留。

c
struct kmem_cache {
    struct kmem_cache_cpu __percpu *cpu_slab;

    /* Used for retriving partial slabs etc */
    slab_flags_t flags;
    unsigned long min_partial;
    int size;             /* The size of an object including meta data */
    int object_size;      /* The size of an object without meta data */
    int offset;           /* Free pointer offset. */

#ifdef CONFIG_SLUB_CPU_PARTIAL
    int cpu_partial;      /* Number of per cpu partial objects to keep around */
#endif

    struct kmem_cache_order_objects oo;

    /* Allocation and freeing of slabs */
    struct kmem_cache_order_objects max;
    struct kmem_cache_order_objects min;
    gfp_t allocflags;     /* gfp flags to use on each alloc */
    int refcount;         /* Refcount for slab cache destroy */
    void (*ctor)(void *);
    int inuse;            /* Offset to metadata */
    int align;            /* Alignment */
    int reserved;         /* Reserved bytes at the end of slabs */
    const char *name;     /* Name (only for display!) */
    struct list_head list;/* List of slab caches */
    struct kmem_cache_node *node[MAX_NUMNODES];
};

逐字段标出它在路径上的位置，这是后面所有章节的锚点：

字段 含义 谁写 谁读
cpu_slab per-cpu 结构指针 __kmem_cache_create 里 alloc_percpu fast path 第一件事就是 raw_cpu_ptr(s->cpu_slab)
flags 缓存属性，如 SLAB_HWCACHE_ALIGN 创建入参 calculate_sizes、合并判断、sysfs
min_partial node partial 链表要留住的 slab 下限 set_min_partial，取 ilog2(size)/2 释放路径判断 n->nr_partial >= s->min_partial
size / object_size 步长（含对齐与尾部元数据）/ 用户要的真实大小 calculate_sizes / 创建入参 切页、算 object 数、统计
offset freepointer 相对 object 首地址的偏移 calculate_sizes get_freepointer / set_freepointer
cpu_partial per-cpu partial 允许囤的空闲 object 总数上限 set_cpu_partial 释放慢路径比较 pobjects > cpu_partial
oo order 与 object 数打包，低 16 位 object 数，高 16 位 order calculate_order 结果 oo_objects() / oo_order()，new_slab 每次都用
max / min oo 的上界 / 「只装一个 object」的兜底 calculate_sizes / kmem_cache_open 要不到页时的回退判断
allocflags 向伙伴系统要页时带的 gfp 创建时 new_slab
refcount 销毁引用计数，被合并的 cache 由多个名字共用 sysfs 建删 kmem_cache_destroy 决定是否真释放
ctor 对象构造回调 创建时 setup_object，有 ctor 会让 freepointer 外置
inuse 对象区大小，按指针宽度对齐 calculate_sizes 外置 freepointer 时 offset == inuse
align / reserved 对齐字节数 / slab 尾部预留字节 calculate_alignment / calculate_sizes 切页起点、算 object 数
name / list sysfs 名字 / 全局 slab_caches 链表节点 创建时 合并、slabinfo 遍历
node[] 每个 node 一个 kmem_cache_node __kmem_cache_create 慢路径 get_node(s, nid)

oo 的编码要单独记住。kmem_cache_order_objects 就是一个 unsigned int，用 OO_SHIFT = 16 切开：

text
 31                16 15                 0
 +-------------------+-------------------+
 |      order        |   objects 数量     |
 +-------------------+-------------------+
 oo = (order << 16) + ((PAGE_SIZE << order) - reserved) / size
 oo_order(oo) == oo >> 16        oo_objects(oo) == oo & ((1 << 16) - 1)

一 slab 的 object 数就是 ((PAGE_SIZE << order) - reserved) / size，除不尽的余数丢在页尾，就是关系图里那块灰色。5.x 与 4.15 的字段差异：size / object_size / offset 从 int 改成 unsigned int；refcount 拆成 struct kref 加销毁计数；部分版本加了 users、random、kasan_info，random 是 freepointer 混淆种子（见第八章）。抓源码以 include/linux/slub_def.h 为准。

四、per-cpu 结构：kmem_cache_cpu 与 fast path #

分配要快就不能碰锁。SLUB 给每个 CPU 一个 kmem_cache_cpu，绝大部分分配释放只动这个结构里的指针。

c
struct kmem_cache_cpu {
    void **freelist;    /* Pointer to next available object */
    unsigned long tid;  /* Globally unique transaction id */
    struct page *page;  /* The slab from which we are allocating */
#ifdef CONFIG_SLUB_CPU_PARTIAL
    struct page *partial;   /* Partially allocated frozen slabs */
#endif
};

字段不多，每个都在热路径上：

字段 含义 分配路径读写 释放路径读写
freelist 本地空闲 object 单链表头 slab_alloc_node 读它取 object，cmpxchg_double 写回下一个 do_slab_free 把 object 塞回表头
tid 事务号，每成功改一次 freelist 就加一 作为 cmpxchg_double 的第二字一起比较交换 同上，防止并发写坏
page 当前正在服务的 slab 页 读来判断 node_match，页用完时换新页 读来判断 page == c->page 走不走快路径
partial per-cpu partial 链表，装 frozen 的半满 slab 当前页用完时从这里取下一页 满 slab 释放一个 object 后挂进来

tid 容易看懵。它给 per-cpu 数据做一次弱同步：抢占开着时，任务读走 c->freelist 之后被抢占、在另一个 CPU 上恢复，此期间别的任务改了同一个 c->freelist。单字比较交换挡不住这种撕裂，所以用 this_cpu_cmpxchg_double 一次比较 freelist 和 tid 两个字，两个都没变才算成功，失败就从头再来。CONFIG_SLUB_CPU_PARTIAL 决定有没有 partial 字段，关掉之后本 CPU 不再囤半满 slab，满 slab 释放出来的 object 直接进 node 的 partial 链表，跨 CPU 的锁竞争会上来。

五、per-node 结构：kmem_cache_node 与 partial 链表 #

本地缓存空了要往上一层找，这一层按 NUMA node 分。

c
struct kmem_cache_node {
    spinlock_t list_lock;
    unsigned long nr_partial;
    struct list_head partial;
};

list_lock 保护 partial 和 nr_partial，拿的是 spin_lock_irqsave；nr_partial 是当前 partial 链表的 slab 数量，增删都要跟着改；partial 是半满 slab 的双向链表，page->lru 做链接节点。5.x 在这个结构上加了 nr_slabs、total_objects，还有 struct list_head full（CONFIG_SLUB_DEBUG 下放全满 slab）。没开调试时全满 slab 不属于任何链表。

min_partial 的语义常被读反。名字叫 min，实际是 node partial 链表要留住的最小 slab 数；释放路径的判据是 n->nr_partial >= s->min_partial 才丢弃空 slab，所以它的行为看起来像个上限触发器——链表短于它就留着，够长就丢掉空的。set_min_partial 取 ilog2(size) / 2，夹在 MIN_PARTIAL(5) 与 MAX_PARTIAL(10) 之间。

六、三个结构怎么串起来：一张全图 #

左边是全局和 node，右边是 per-cpu。

text
   struct kmem_cache ("kmalloc-32")          kmem_cache_cpu（每 CPU 一份）
   +---------------------------+             +---------------------------+
   | size / object_size/offset |             | freelist --> [obj] -> ... |
   | oo = <order, objects>     |             | tid                       |
   | cpu_slab ------------------------------->| page --> 当前 slab 页     |
   | node[MAX_NUMNODES] -------+             | partial --> frozen 链     |
   | list -> slab_caches       |             +---------------------------+
   +---------------------------+                          |
                |                                         |
                v                                         v
       kmem_cache_node                     struct page（slab 页）
       +--------------------+              +---------------------------+
       | list_lock          |              | slab_cache = s            |
       | nr_partial         |              | freelist / inuse / frozen |
       | partial -> [page]  |              | pobjects / pages / objects|
       +--------------------+              +---------------------------+

三条边是关键：kmem_cache.cpu_slab 是 per-cpu 指针，取到哪个实例取决于当前 CPU，raw_cpu_ptr 一行定位；kmem_cache.node[nid] 是数组，索引就是 node id，get_node(s, nid) 拿的就是它；page->slab_cache 从页反查缓存池，释放时只给了 object 地址，靠 virt_to_head_page(obj) 拿到页，再从页拿到属于哪个 kmem_cache。牛奶箱的比喻还能用：kmem_cache 是品牌规格，slab 页是一箱奶，object 是一瓶，partial 链表是货架，伙伴系统是厂家，货架空了一次进一箱就是 new_slab。

七、object 在 slab 页里怎么排列 #

拿到 order 页连续内存之后，按 size 平分成 objects 份，除不尽的尾巴是 reserved，谁也不给。

text
order=0，一页 4096，size=32，objects=128
 +------+------+------+-----+--------+----------+
 | obj0 | obj1 | obj2 | ... | obj127 | reserved |
 +------+------+------+-----+--------+----------+
 ^      ^
 0     32                                     4096
 每个 object 内部（freelist 内置，offset=0）
 +------------------+-------------------+
 | next freepointer |      数据区        |
 |     8 字节        |                   |
 +------------------+-------------------+

reserved 由几件事凑出来：size 对齐后的余数、SLAB_RED_ZONE 的红区、SLAB_POISON 的填充区、freepointer 外置时多出来的 8 字节。calculate_sizes 的顺序大致是：先 size = ALIGN(size, sizeof(void *)) 保证放得下一个指针，再对齐到 align（SLAB_HWCACHE_ALIGN 时对齐到 cache 行），inuse = size 记下对象区大小；然后若带 SLAB_TYPESAFE_BY_RCU、SLAB_POISON 或有 ctor，则 offset = size; size += sizeof(void *) 把 freepointer 挤到尾部；最后按 SLAB_RED_ZONE 加前后红区、按 SLAB_POISON 加尾部填充字。

所以 size 永远大于等于 object_size，差额是对齐和调试用的。SLAB_HWCACHE_ALIGN 的代价也在这里：对象变大，一页切出来的个数变少，内存密度下降。拿 cache 命中换密度，值不值看对象大小。

八、freelist：空闲对象怎么串起来 #

SLUB 没有独立管理区。空闲 object 怎么连？把下一个空闲 object 的地址写进当前空闲 object 自己的内存里。申请者不关心分配之前这块内存是什么，拿它当链表节点没有副作用。这就是指针内置式，freepointer 存在 object + s->offset 处，offset 多数是 0。外置式则放在 object 尾部，offset == inuse。

text
 内置式 offset=0                   外置式 offset=inuse
 +--------+-------------+         +-------------+----+-------------+----+
 | fp(8B) |   数据区     |         |   数据区     | fp |   数据区     | fp |
 +--------+-------------+         +-------------+----+-------------+----+
 首地址就存下个指针                 尾部多占 8 字节，inuse 不变

什么时候外置：有构造函数（数据区在 ctor 之前不能动）、SLAB_POISON（毒化要把整块数据区填满）、SLAB_TYPESAFE_BY_RCU（对象会被 RCU 读者同时访问）。这三种情况内置式会把脏数据写进对方正在读的内存。

c
static inline void *get_freepointer(struct kmem_cache *s, void *object)
{
    return *(void **)(object + s->offset);
}

static inline void *freelist_ptr(const struct kmem_cache *s, void *ptr,
                                 unsigned long ptr_addr)
{
#ifdef CONFIG_SLAB_FREELIST_HARDENED
    return (void *)((unsigned long)ptr ^ s->random ^ ptr_addr);
#else
    return ptr;
#endif
}

static inline void set_freepointer(struct kmem_cache *s, void *object, void *fp)
{
    unsigned long freeptr_addr = (unsigned long)object + s->offset;
#ifdef CONFIG_SLAB_FREELIST_HARDENED
    BUG_ON(object == fp);   /* 朴素的 double free / 自环检测 */
#endif
    *(void **)freeptr_addr = freelist_ptr(s, fp, freeptr_addr);
}

CONFIG_SLAB_FREELIST_HARDENED 打开后 freepointer 不是裸指针，而是三个量异或：真实指针、s->random（每池随机种子）、ptr_addr（freepointer 自己所在地址）。同一个指针存在不同位置编码结果不同；把它抄到别处或伪造一个指向攻击目标的值，解出来全是垃圾。BUG_ON(object == fp) 顺手抓一次自己指向自己的释放。另一个开关 CONFIG_SLAB_FREELIST_RANDOM 在 new_slab 建链时打乱顺序，让「按分配顺序推地址」这种偏差利用失效。两个宏都属安全加固，默认开不开看发行版；素材两篇都没提，这两段按主线代码补的，引入版本未验证。

九、SLUB 的初始化：kmem_cache 的 kmem_cache #

第一个要解决的是先有鸡还是先有蛋：创建 struct kmem_cache 需要从一个 kmem_cache 里分配，可这时还没有 kmem_cache。内核用两个静态变量顶上，boot_kmem_cache 和 boot_kmem_cache_node 放在 .init.data，本身不需要动态分配。

c
void __init kmem_cache_init(void)
{
    // 声明静态变量，存储临时 kmem_cache 管理结构
    static __initdata struct kmem_cache boot_kmem_cache,
        boot_kmem_cache_node;

    /* ... */

    kmem_cache_node = &boot_kmem_cache_node;
    kmem_cache = &boot_kmem_cache;

    // 申请 slub 缓冲区，管理数据放在临时结构中
    create_boot_cache(kmem_cache_node, "kmem_cache_node",
        sizeof(struct kmem_cache_node), SLAB_HWCACHE_ALIGN);

    create_boot_cache(kmem_cache, "kmem_cache",
            offsetof(struct kmem_cache, node) +
                nr_node_ids * sizeof(struct kmem_cache_node *),
               SLAB_HWCACHE_ALIGN);

    // 从临时结构挂的缓冲区里申请 kmem_cache 的 kmem_cache，把管理数据拷进去
    kmem_cache = bootstrap(&boot_kmem_cache);
    // 同上，为 kmem_cache_node 建一个 kmem_cache
    kmem_cache_node = bootstrap(&boot_kmem_cache_node);

    /* ... */
}

create_boot_cache 给 kmem_cache 传的 size 是 offsetof(struct kmem_cache, node) + nr_node_ids * sizeof(ptr)，不是 sizeof(struct kmem_cache)。node[] 是尾巴上的柔性数组，长度按实际 node 数算，少一个 node 就少 8 字节，不该浪费。bootstrap() 的动作是：用临时结构当缓存池描述符去申请一个真正的 struct kmem_cache，把 boot_kmem_cache 的内容整块拷进新对象，返回新对象地址。两次 bootstrap 之后静态那两份只剩历史价值，.init.data 释放时一起丢掉。这一步完成后 slab_state = PARTIAL，等 sysfs 挂完变成 SYSFS，缓存合并才开始工作——__kmem_cache_alias 里查 slab_state < SYSFS 直接返回 NULL。

十、kmalloc 常规缓存的创建 #

第二件事是建一堆按大小分级的缓存，供 kmalloc 用。原则是每个 2 的幂建一个，但 8～192 这段间隙太大，浪费严重，于是补了 96 和 192 两个桶。

c
void __init create_kmalloc_caches(unsigned long flags)
{
    /* ... */
    /* 使用 SLUB 时 KMALLOC_SHIFT_LOW=3
     * 也就是说使用 kmalloc 能够申请的最小内存是 8B
     * 申请内存是向上对齐 2 的 n 次幂，创建对应大小缓存保存在 kmalloc_caches[n] */
    for (i = KMALLOC_SHIFT_LOW; i <= KMALLOC_SHIFT_HIGH; i++) {
        if (!kmalloc_caches[i]) {
            kmalloc_caches[i] = create_kmalloc_cache(NULL, 1 << i, flags);
        }
        /* Caches that are not of the two-to-the-power-of size.
         * These have to be created immediately after the
         * earlier power of two caches（两个例外：(64,96] 与 (128,192]） */
        if (KMALLOC_MIN_SIZE <= 32 && !kmalloc_caches[1] && i == 6)
            kmalloc_caches[1] = create_kmalloc_cache(NULL, 96, flags);
        if (KMALLOC_MIN_SIZE <= 64 && !kmalloc_caches[2] && i == 7)
            kmalloc_caches[2] = create_kmalloc_cache(NULL, 192, flags);
    }

    /* ... */
}

两个细节容易漏。索引 1 和 2 被 96 / 192 占了，所以 kmalloc_caches[1] 代表的不是 2 字节而是 96 字节；索引 0 留空，kmalloc_index(0) 返回 0 表示零长度申请。96 和 192 必须在 i == 6（64 字节）和 i == 7（128 字节）刚建好之后立刻建，原注释 These have to be created immediately after the earlier power of two caches 就是这个意思。

KMALLOC_SHIFT_HIGH 的值必须按源码核对。素材注释写 13（最大 8KB），这在老版本 #define KMALLOC_SHIFT_HIGH (PAGE_SHIFT + 1) 上成立；新一些的代码把它抬到 MAX_ORDER + PAGE_SHIFT - 1 并封顶 25，x86_64 上算出来是 22，此时 kmalloc-16k 到 kmalloc-4M 也会建出来。kmalloc_info[] 里列到 64MB，不代表默认建到 64MB。5.9 之后这套接口分成多种类型：create_kmalloc_caches(type)，kmalloc_caches[type][index]，type 有 KMALLOC_NORMAL / KMALLOC_DMA / KMALLOC_CGROUP / KMALLOC_RECLAIM，一张表变二维数组，kmalloc_type() 按 gfp 标志选行。

十一、缓存的创建与销毁 #

kmem_cache_create 是入口。它做的第一件事不是分配，而是去找能不能蹭别人的缓存。

步骤 动作 牵扯的结构
1 参数检查，size 超上限直接返回 NULL —
2 find_mergeable 按对齐后 size、align、flags 找可合并缓存 slab_caches 链表
3 命中则 sysfs_slab_alias 建别名，返回老 cache 老 cache 的 refcount
4 未命中则分配一个 kmem_cache 描述符 鸡生蛋已在第九章解决
5 __kmem_cache_create：calculate_sizes、set_min_partial、alloc_percpu(cpu_slab)、逐 node 分配 kmem_cache_node 三个结构全部出动
6 sysfs_slab_add 建节点，list_add 进 slab_caches kobject、全局链表

第 5 步里 alloc_percpu 是最贵的一笔：给每个 CPU 分一份 kmem_cache_cpu，128 核就是 128 份。别在热路径里反复 kmem_cache_create。销毁反过来走，前提是从该池分配出去的 object 全部还回来了；kmem_cache_destroy 检查 refcount，被合并的大于 1，这时只删自己那个 sysfs 别名，不动真正的池子。释放顺序是 shutdown_cache（遍历 node 把 partial 上的 slab 全部 discard_slab）→ free_percpu(s->cpu_slab) → 逐个释放 kmem_cache_node → sysfs_slab_remove → 释放 kmem_cache 本身。漏了某个 CPU 的 c->page 还挂着一页，CONFIG_SLUB_DEBUG 下会打出 kmem_cache_destroy called for cache that still has objects 之类的告警，接着就是野指针崩。

十二、分配对象：fast path #

kmem_cache_alloc 最终进到 slab_alloc_node。快路径的全部工作就是：从 c->freelist 摘一个下来，把 c->freelist 推到下一个。

c
static __always_inline void *slab_alloc_node(struct kmem_cache *s,
        gfp_t gfpflags, int node, unsigned long addr)
{
    void *object;
    struct kmem_cache_cpu *c;
    struct page *page;
    unsigned long tid;

redo:
    c = raw_cpu_ptr(s->cpu_slab);
    tid = c->tid;
    barrier();

    object = c->freelist;
    page = c->page;
    if (unlikely(!object || !node_match(page, node))) {
        object = __slab_alloc(s, gfpflags, node, addr, c);
    } else {
        void *next_object = get_freepointer_safe(s, object);

        if (unlikely(!this_cpu_cmpxchg_double(
                s->cpu_slab->freelist, s->cpu_slab->tid,
                object, tid,
                next_object, next_tid(tid)))) {
            note_cmpxchg_failure("slab_alloc", s, tid);
            goto redo;
        }
        prefetch_freepointer(s, next_object);
    }
    return object;
}

快路径命中要同时满足三条：

条件 检查位置 不满足时
c->freelist 非空 !object 进 __slab_alloc
c->page 的 node 与请求 node 一致 node_match(page, node) 进 __slab_alloc，先 deactivate 当前页
执行期间没人动过 c->freelist / c->tid cmpxchg_double 返回值 goto redo 重试

node_match 里有两个短路口：node 是 NUMA_NO_NODE 时不管页在哪个 node 都算匹配（这是 kmem_cache_alloc 不带 node 参数的情形）；指定的 node 没上线也算匹配。prefetch_freepointer 是有意为之：把下一个 object 的 freepointer 提前拉进 cache，分配连着发生时这次预热正好给下一次用。快路径全程不拿锁、不关中断，只在最后有一次 cmpxchg_double。核数越多，这个设计的价值越大。

十三、分配对象：slow path 与 new_slab #

__slab_alloc 负责三件事：把当前页交还、找一页能用的、把结果塞回 per-cpu。找页顺序是四级 fallback。

顺序 来源 代码位置 代价
1 当前 CPU 的 partial 链表 get_cpu_partial 无锁，最快
2 本 node 的 partial 链表 get_partial(s, node, ...) 拿 n->list_lock
3 其它 node 的 partial 链表 get_any_partial / get_node 拿远端锁，跨 NUMA
4 都没有，向伙伴系统要页 new_slab 最贵，alloc_pages

第 2、3 步都从链表尾部取（get_partial_node 里用 list_for_each_entry_safe_reverse），新挂上去的 slab 更空，容易一次多搬几个 object 到本地。交还当前页的动作叫 deactivate_slab，两步：把 c->freelist 上剩下的空闲 object 全部串回 page->freelist、page->inuse 同步更新；然后按页的状态决定去向——还有空闲且 node 认可，挂进 node（或 per-cpu）的 partial；全空且 n->nr_partial >= s->min_partial，直接 discard_slab 还给伙伴系统；全满且开了 CONFIG_SLUB_DEBUG，挂进 n->full 供 slabinfo 统计。

页的 frozen 标志在这里翻转：frozen 表示这页归某个 CPU 独占（在 c->page 或 c->partial 上），unfrozen 表示它挂在某个 node 的 partial 链表上等人来拿。这个标志是理解释放路径的关键，第十五章会再用一次。

new_slab 是唯一会向伙伴系统要内存的地方：

c
static struct page *allocate_slab(struct kmem_cache *s, gfp_t flags, int node)
{
    struct kmem_cache_order_objects oo = s->oo;
    ...
    page = alloc_slab_page(s, flags, node, oo);  /* 伙伴系统接口 */
    ...
    page->objects = oo_objects(oo);
    page->slab_cache = s;
    /* 建 freelist：obj0 -> obj1 -> ... -> NULL */
    start = page_address(page);
    page->freelist = start;
    for (idx = 0, p = start; idx < page->objects - 1; idx++) {
        next = p + s->size;
        set_freepointer(s, p, next);
        p = next;
    }
    set_freepointer(s, p, NULL);
    ...
}

oo 要不到页时退回 s->min（oo_objects(s->min) 只够装一个 object），高阶连续内存紧张时这条退路能救命。order 和 object 数怎么定，走 calculate_order；这两个量互相牵制，order 大了页多、object 多、碎片少，但连续内存难要，order 小了容易要页、碎片多。

c
static inline int calculate_order(int size, int reserved)
{
    /* ... */
    // 尝试找到 order 与 object 数量的最佳配合方案，期望碎片最小
    min_objects = slub_min_objects;
    if (!min_objects)
        min_objects = 4 * (fls(nr_cpu_ids) + 1);
    max_objects = order_objects(slub_max_order, size, reserved);
    min_objects = min(min_objects, max_objects);
    // fraction 是碎片因子，需满足 (slab_size - reserved) % size <= slab_size / fraction
    while (min_objects > 1) {
        fraction = 16;
        while (fraction >= 4) {
            order = slab_order(size, min_objects, slub_max_order, fraction, reserved);
            if (order <= slub_max_order)
                return order;
            fraction /= 2;          // 放宽条件，容忍的碎片大小增倍
        }
        min_objects--;
    }

    // 尝试一个 slab 只包含一个对象；再退到 MAX_ORDER 且只含一个对象
    order = slab_order(size, 1, slub_max_order, 1, reserved);
    if (order <= slub_max_order)
        return order;
    order = slab_order(size, 1, MAX_ORDER, 1, reserved);
    if (order < MAX_ORDER)
        return order;
    return -ENOSYS;
}

min_objects = 4 * (fls(nr_cpu_ids) + 1) 值得停一下。fls(nr_cpu_ids) 是 CPU 数的最高位序号，8 核是 4，128 核是 8，所以 8 核一页至少 20 个 object，128 核要 36 个。理由直白：核多，每个 CPU 都要一份本地 slab，一页里 object 太少，切给几个 CPU 就没了，反而不停地申请释放页。这条公式是「一页至少够所有 CPU 各抓一把」的近似。slub_min_objects 可由内核命令行 slub_min_objects= 覆盖，slub_max_order= 改上限（默认 3），落到的 oo 会写进 /sys/kernel/slab/<cache>/order 和 objs_per_slab。

十四、释放对象：fast path #

kmem_cache_free 只有一处需要判断：这个 object 是不是属于我当前 CPU 正在服务的那一页。

c

                int cnt, unsigned long addr)
{
    void *tail_obj = tail ? : head;
    struct kmem_cache_cpu *c;
    unsigned long tid;

    tid = c->tid;

                c->freelist, tid,
                head, next_tid(tid)))) {

            goto redo;
        }
    } else
        __slab_free(s, page, head, tail_obj, cnt, addr);

page == c->page 就是快路径的全部判断。命中就等价于往单链表头上插一个节点：set_freepointer(obj, c->freelist)，然后 cmpxchg_double 把表头换成自己的地址，和分配完全对称，一样无锁。head / tail / cnt 是为了支持批量释放（kmem_cache_free_bulk 一次还一批），单次释放时 tail 是 NULL，退化成 head。

进 do_slab_free 之前还有一步：从 object 地址反查页。virt_to_head_page(x) 处理了复合页——object 落在 order > 0 的页里时，要取头部页才能拿到 page->slab_cache。!PageSlab(page) 的分支是给 kfree 传进来的大块内存留的口子，那块内存不是 slab 管出来的，直接还给伙伴系统。

十五、释放对象：slow path #

不进快路径就进 __slab_free。这里判断比分配那边多，因为页有四种状态，每种状态的动作不同。

c
static void __slab_free(struct kmem_cache *s, struct page *page,
            void *head, void *tail, int cnt, unsigned long addr)
{
    void *prior;
    int was_frozen;
    struct page new;
    unsigned long counters;
    struct kmem_cache_node *n = NULL;
    do {
        prior = page->freelist;
        counters = page->counters;
        set_freepointer(s, tail, prior);
        new.counters = counters;
        was_frozen = new.frozen;
        new.inuse -= cnt;
        if ((!new.inuse || !prior) && !was_frozen) {
            if (kmem_cache_has_cpu_partial(s) && !prior) {
                new.frozen = 1;   /* 满 slab 变半满：冻结，进 per-cpu partial */
            } else {
                n = get_node(s, page_to_nid(page));
                spin_lock_irqsave(&n->list_lock, flags);
            }
        }
    } while (!cmpxchg_double_slab(s, page, prior, counters,
                head, new.counters, "__slab_free"));

    if (likely(!n)) {
        /* 快分支：只改了 page->inuse / freelist */
        ...
        return;
    }
    /* 慢分支：拿着 n->list_lock 处理 partial / 全空 / 全满 */
}

四个状态与对应动作：

释放前的页状态 判据 释放后的动作
半满、未冻结 prior != NULL，was_frozen == 0 直接串回 page->freelist，inuse 减一
全满、未冻结 prior == NULL，was_frozen == 0 冻结它（new.frozen = 1），挂进 c->partial
半满、已冻结 was_frozen == 1 不动链表，只减 inuse，页仍归原 CPU
释放后全空 new.inuse == 0 拿 n->list_lock，够长就 discard_slab 还给伙伴系统

第三行最反直觉：页已经冻结在某个 CPU 上，别的 CPU 往里释放 object 只能在原地改计数，不能挂到自己的链表上——挂走会破坏冻结它的那个 CPU 的账本。

per-cpu partial 的阈值判据，素材写成「所有 slab 的 free object 数量之和大于 cpu_partial」。实现上这两个数存在链表头那页的 struct page 字段里：page->pobjects 是这条链表上所有 slab 的空闲 object 总数，挂入时累加；page->pages 是链表上一共几个 slab。超过 s->cpu_partial 就 flush_all(s)，把整条 per-cpu partial 链表一次性挪到 n->partial，再把刚释放的这页挂进来。是整条清空，不是挪出去几个。cpu_partial 的默认值由 set_cpu_partial 按 oo_objects 算，大致是「两个 slab 的 object 数」量级，开了 CONFIG_SLUB_CPU_PARTIAL 才有这个成员。

参数 所属 管什么链表 触发动作
min_partial kmem_cache node 的 partial 空 slab 释放时，链表够长就丢弃这页
cpu_partial kmem_cache per-cpu 的 partial 空闲 object 总数超限，整条链表下放到 node

一个管「留多少」，一个管「囤多少」。前者越大，空 slab 留得越久，抗突发好、占内存多；后者越大，跨 CPU 抬锁越少，本 CPU 囤的碎页越多。

十六、kmalloc 与 kmem_cache_alloc 的关系 #

驱动代码里几乎不写 kmem_cache_alloc，都写 kmalloc。kmalloc 是把 size 映射到某个缓存池名字上的薄壳。

c
static __always_inline void *kmalloc(size_t size, gfp_t flags)
{
    if (__builtin_constant_p(size)) {
        if (size > KMALLOC_MAX_CACHE_SIZE)
            return kmalloc_large(size, flags);
        if (!(flags & GFP_DMA)) {
            int index = kmalloc_index(size);
            if (!index)
                return ZERO_SIZE_PTR;
            return kmem_cache_alloc_trace(kmalloc_caches[index], flags, size);
        }
    }
    return __kmalloc(size, flags);
}

四件事：__builtin_constant_p(size) 判断 size 是不是编译期常量，是常量时整个映射在编译期算完，运行时只剩一次 kmem_cache_alloc；size 超过 KMALLOC_MAX_CACHE_SIZE 走 kmalloc_large，也就是直接 alloc_pages，拿到的是一段连续页，不再是 slab 对象；kmalloc_index(size) 查表得到下标，kmalloc_caches[index] 拿到缓存池；size 为 0 返回 ZERO_SIZE_PTR，一个非 NULL 哨兵，kfree 认得它。

kmem_cache_alloc_trace 与 kmem_cache_alloc 的差别只在开了 CONFIG_TRACING 时前者会记下分配大小给 tracepoint 用，没开时前者直接内联成后者。kmalloc(17, GFP_KERNEL) 落到 kmalloc-32，浪费 15 字节。这不是缺陷，是分级分配的必然代价。想省这 15 字节，自己建一个 17 字节的缓存池。__kmalloc（非常量 size）走同样一张表，只是查表在运行时做，多几条指令。

对着下标读一遍：

index 缓存名 对象大小 覆盖的请求范围 默认是否创建
0 — 0 size == 0 返回 ZERO_SIZE_PTR
1 kmalloc-96 96 (64, 96] 是（KMALLOC_MIN_SIZE <= 32）

kmalloc_index 的实现是一串 if，编译器会折成位运算。size 是常量时这一串在编译期消掉，产物里只剩 mov 加 call kmem_cache_alloc。

c
static __always_inline int kmalloc_index(size_t size)
{
    if (!size)
        return 0;
    if (size <= KMALLOC_MIN_SIZE)
        return KMALLOC_SHIFT_LOW;
    if (KMALLOC_MIN_SIZE <= 32 && size > 64 && size <= 96)
        return 1;
    if (KMALLOC_MIN_SIZE <= 64 && size > 128 && size <= 192)
        return 2;
    if (size <= 8) return 3;    if (size <= 16) return 4;
    if (size <= 32) return 5;   if (size <= 64) return 6;
    if (size <= 128) return 7;  if (size <= 256) return 8;
    if (size <= 512) return 9;  if (size <= 1024) return 10;
    /* ... 各档 2 的幂，一路到 index 13 的 8KB ... */
    if (size <= 64 * 1024) return 16;
    if (size <= 128 * 1024) return 17;
    if (size <= 64 * 1024 * 1024) return 26;
    /* Will never be reached. Needed because the compiler may complain */
    return -1;
}

return -1 那句注释说了实话：走到这里说明快路径已经把它拦到 kmalloc_large 去了，留着是为了让编译器别抱怨「控制流有路径没返回值」。

十八、slab 合并（slab merging）与它的副作用 #

kmem_cache_create 在真正分配之前先试合并，判据是三个值全等：对齐后的 size、align、flags。带构造函数的不合并（find_mergeable 里 if (ctor) return NULL），标了 SLAB_NEVER_MERGE 的也不合并，后者包含 SLAB_POISON、SLAB_RED_ZONE、SLAB_STORE_USER 这些调试标志。收益实打实：内核里几百个缓存池，size 相同的很多，合并完省一批 slab 页和一批 kmem_cache 描述符。

副作用 表现 应对
归属混淆 slabinfo 里一个大数挂在某个小缓存名下 看 /sys/kernel/slab/<name>/aliases
越界连带 一个子系统的越界写踩到另一个子系统的对象 调试时关合并，或开 slub_debug
排查困难 崩溃现场的对象地址对不上子系统 slub_debug=U,<cache_name> 单点追踪
销毁不生效 kmem_cache_destroy 只删别名，池子还在 看 refcount，被共用是正常的

关闭方式三种：内核命令行加 slab_nomerge；slub_debug 打开时合并路径被绕过（判断点随版本，本文未验证）；编译期去掉 CONFIG_SLAB_MERGE_DEFAULT。折中做法是留着合并，但给关键缓存加 SLAB_NO_MERGE（5.x 的名字，4.x 用 SLAB_NEVER_MERGE 组合具体标志位），只钉住需要单独观察的那几个。

十九、调试手段：slabinfo / slabtop / slub_debug #

/proc/slabinfo 一行一个缓存池。active_objs 是已分配给调用者的 object 数，num_objs 是该池总共管着多少，objsize 是 object_size，objperslab 是一 slab 切出几个，pagesperslab 是 1 << order；limit / batchcount / sharedfactor 是 SLAB 时代的遗留调参项，SLUB 里基本无意义。active_objs 远小于 num_objs 且 num_slabs 一直涨，说明有泄漏或碎片化；objperslab 只有 1、pagesperslab 很大，说明 order 被抬得高，去看 min_objects 和 slub_max_order。

slabtop 是 slabinfo 的 top 版，按占用排序，-s c 按 cache 大小排，-d 3 三秒刷新。查「谁在吃内存」先看它。

slub_debug 是编译开关 CONFIG_SLUB_DEBUG 加运行时参数，选项字符有 F（一致性检查，每次分配释放都验 freelist，很慢）、Z（红区，对象前后加保护字节）、P（毒化，分配填 0x6b、释放填 0xa5，能看 use-after-free）、U（记录分配释放调用栈，内存涨很多），前缀 - 表示关闭某项。用法：slub_debug=FZPU 全局开，slub_debug=FZPU,kmalloc-32 只对指定缓存开，slub_debug=- 全关。开 U 后可读 /sys/kernel/slab/<cache>/alloc_calls 与 free_calls，这是查泄漏最直接的手段。sysfs 那边 /sys/kernel/slab/<cache>/ 下的文件随版本增减，常用的有 objects、slabs、cpu_slabs、partial、object_size、objs_per_slab、order、aliases，线上读这些比解析 slabinfo 稳。

二十、易错点速查 #

误区 事实
page->inuse 就是已分配的 object 数 对冻结页不成立。new_slab 建好页时 inuse 就置成 object 总数，冻结期间分配 object 不改它；页解冻、离开 c->page 时才重新算准
page->freelist == NULL 表示页满了 冻结页的 freelist 是 NULL，真正的空闲链在 c->freelist 上。满不满看 inuse
oo 高 16 位是页数 高 16 位是 order，页数是 1 << order
min_partial 是上限 名字是下限（node partial 要留几个），行为像上限触发器（nr_partial >= min_partial 才丢空页）
kmem_cache_destroy 一定能释放 还有 object 在外面只会告警，池子留着；被合并的还要等 refcount 落到 1
kmalloc 能申请任意大小 超过 KMALLOC_MAX_CACHE_SIZE（默认 8KB）走 alloc_pages，不再走 slab
一页可以混装不同缓存的对象 一个 slab 页只装它自己的 object，这也是合并会带来连带越界的原因
释放时给对指针就行 必须还到当初分配它的那个 kmem_cache，跨池释放会改错页的账本，后果是内存静默损坏
slabinfo 的 active_objs 是精确值 未开 CONFIG_SLUB_DEBUG 时部分统计是估算，别拿它做精确对账
关掉 per-cpu 缓存性能更好 反过来。CONFIG_SLUB_CPU_PARTIAL 关掉后跨 CPU 抢 node->list_lock 变多，高核数下退化明显
