这篇只讲一件事：内存账本怎么看、参数怎么调。范围是 /proc/meminfo 每个字段的内核来源、页缓存回写与水线、swap 与 zRAM、overcommit 与 OOM 的 sysctl 落点，最后串成一条能照着敲的排查路径。

不讲的东西拆到别处：回收算法内部怎么走（LRU 怎么分、逆向映射怎么找 PTE、shrink_node 的扫描循环）→ 页面回收与逆向映射；页、zone、node、memory model 的定义与初始化 → 物理内存管理：页、zone 与内存模型；copy_to_user / copy_from_user 的拷页与 fault-in → 内核连续内存与用户态拷贝。

边界一句话：回收算法为什么长这样在《页面回收与逆向映射》那篇，本文只讲观测与调参。代码基线：overcommit 与 OOM 取自 4.0 内核，zRAM 取自 4.4，meminfo 的取数宏在 3.x～5.x 之间换过，算法骨架没动。版本差异处单独标注，不确定的写「未验证」。命令输出保留真实字段名与格式，数值取自一台 8G x86 机器——别对着数字做结论，对着字段名做结论。

一、先看懂内存账本：/proc/meminfo #

cat /proc/meminfo 是内存观测的起点。三个约束先记住：单位是 kB（HugePages_* 与 Hugepagesize 除外）；字段顺序是历史包袱，按语义分组看；这是全系统的账，不是你进程的账，找进程用 smaps。

这份账由 fs/proc/meminfo.c 的 meminfo_proc_show() 拼出来，所有字段都走 show_val_kb()——它只干一件事，把页数左移 PAGE_SHIFT - 10 换成 KB。所以任何字段的内核原值都是页数，看到 204716 kB 就是在说 51179 个 4K 页。

text
$ cat /proc/meminfo
MemTotal:        7873756 kB      MemFree:          204716 kB
MemAvailable:    4160828 kB      Buffers:          128364 kB
Cached:          3721844 kB      SwapCached:            0 kB
Active:          3102504 kB      Inactive:        2481956 kB
SwapTotal:       2097148 kB      SwapFree:        2097148 kB
Dirty:               476 kB      Writeback:             0 kB
AnonPages:       2222632 kB      Mapped:           612408 kB
Shmem:             41280 kB      Slab:             386512 kB
SReclaimable:     298744 kB      SUnreclaim:        87768 kB
PageTables:        38916 kB      CommitLimit:     6034024 kB

四十几行字段，真正常看的就这一行表：

你要回答的问题 看哪个字段 判据
还有多少内存能用 MemAvailable 低于总量 10% 就要盯
内核自己吃掉多少 Slab + PageTables SUnreclaim 只涨不落是泄漏信号
回收有没有在干活 Active/Inactive、vmstat 的 pgscan/pgsteal pgscan 持续涨说明在扫
swap 是否参与 SwapTotal/SwapFree/SwapCached SwapFree 掉下去就是在换出
脏数据堆了多少 Dirty + Writeback Dirty 贴住限额就是写停顿前兆

MemFree 小不等于内存不够，新手最大的误判点，第三章算这笔账。

zone 这一层：有内存却分配不到 #

meminfo 是全系统视图，看不见「哪个 zone 空了」。NUMA 机器出现「总量还有 4G、进程却分配失败」时，账本要往下翻一层到 /proc/zoneinfo：每个 zone 一段，pages free 下面跟 min、low、high 三档水位，还有一行 protection: 记录 zone 间保护值。

水位 谁被唤醒 后果
free > high 没人 kswapd 睡回去
low < free < high kswapd 异步回收 分配顺畅，后台在扫
min < free < low kswapd 加速 分配走 slowpath，延迟上来
free < min 分配进程自己 direct reclaim 写入线程卡住，这就是卡顿

protection: 在 NUMA 下决定能不能从别的 node 抢页。出现多个 Node N, zone 段就是 NUMA，跨 node 延迟差异单独测：numastat -m 两个 node 的 MemFree 差一大截就是负载倾斜，配 numastat -p <pid> 看进程落在哪个 node。

二、七个关键字段逐个拆 #

MemTotal #

对应全局变量 totalram_pages：

c
unsigned long totalram_pages __read_mostly;

它数的是「内核能管的 page frame 个数」，不是内存条容量。来源是初始化时 memblock 把 memory type 的 page frame 逐个注入各 zone 的 free list，注入多少记多少，这个点就是伙伴系统初始内存量的起点。8G 机器对账：物理 8388608 KB，MemTotal 只有 7873756 KB，差 515852 KB（约 504 MB），差在内核正文段、数据段、initrd、页表、各 zone 裁剪与固件保留区，dmesg | grep -i memory 能看到分项。支持内存热插拔的机器上这个值会变，容器里看到的是宿主值。

MemFree #

c
freeram = global_page_state(NR_FREE_PAGES);

NR_FREE_PAGES 只统计挂在 buddy free list 上的页，page cache 与可回收 slab 一律不算。5.x 换成 global_zone_page_state(NR_FREE_PAGES)（该项挂在 zone 上），语义没变。这个字段小是设计使然，内核把空闲内存当浪费，该盯的是 MemAvailable。

MemAvailable #

定义只有一句：不引起额外磁盘 IO 就能拿到的内存量。取数在 si_mem_available()：

c
long si_mem_available(void)
{
    long available;
    unsigned long pagecache;
    unsigned long wmark_low = 0;
    unsigned long pages[NR_LRU_LISTS];
    struct zone *zone;
    int lru;

    for (lru = LRU_BASE; lru < NR_LRU_LISTS; lru++)
        pages[lru] = global_page_state(NR_LRU_BASE + lru);

    for_each_zone(zone)
        wmark_low += zone->watermark[WMARK_LOW];

    available = global_page_state(NR_FREE_PAGES) - totalreserve_pages;

    pagecache = pages[LRU_ACTIVE_FILE] + pages[LRU_INACTIVE_FILE];
    pagecache -= min(pagecache / 2, wmark_low);
    available += pagecache;

    available += global_page_state(NR_SLAB_RECLAIMABLE) -
                 min(global_page_state(NR_SLAB_RECLAIMABLE) / 2, wmark_low);

    if (available < 0)
        available = 0;
    return available;
}

四步读法：free 先减 totalreserve_pages；加上活跃与非活跃文件页；文件页扣掉「一半」与 wmark_low 的小者；可回收 slab 同样打折后加进来。这个字段 3.14 才进 meminfo，更老的内核没有，只能按 MemFree + Cached + Buffers 估，估出来偏乐观。

Buffers #

新内核没有独立的 buffer cache，全部并进 page cache 框架。Buffers 统计的是块设备自己的 page cache：

c
long nr_blockdev_pages(void)
{
    struct block_device *bdev;
    long ret = 0;
    spin_lock(&bdev_lock);
    list_for_each_entry(bdev, &all_bdevs, bd_list) {
        ret += bdev->bd_inode->i_mapping->nrpages;
    }
    spin_unlock(&bdev_lock);
    return ret;
}

块设备的 page cache 不挂在 /dev/aaa 那个 inode 上：同一块盘被 open 两次就有两个 inode，各管一份会乱，所以内核造了 bdev 文件系统统一存块设备 inode，page cache 挂在 bdev inode 的 i_mapping 下。数量偏小正常，产生路径只有三条：直接读写块设备节点（dd if=/dev/sda）、mount 时读超级块原始数据、读磁盘 inode 等元数据，日常主要是后两条。

Cached 与 SwapCached #

c
cached = global_page_state(NR_FILE_PAGES) -
            total_swapcache_pages() - i.bufferram;

NR_FILE_PAGES 里有三样：普通文件 page cache、块设备 page cache、swap cache。Cached 只要第一样，所以减掉后两样；total_swapcache_pages() 遍历 swapper_spaces[i].nrpages 求和。

swap cache 不为跑得快，为的是解决 page frame 与 swap area 的同步：进程要 swap in 一个页，回收模块正好要把它 swap out，两边撞上就乱。解法是页先塞进 swap cache，任何一方动手前都进 cache 看一眼，靠 page descriptor 的 PG_locked 挡竞态。实现仍借用 page cache 那套，每个 swap area 一个 address_space，swap cache 存在对应 address_space 的 radix tree 里。

字段 内核变量 / 函数 统计口径 易读错的地方
MemTotal totalram_pages buddy 能管的总页数 不等于内存条容量，容器里是宿主值
MemFree NR_FREE_PAGES 只在 buddy free list 上的页 小是常态，不是告警
MemAvailable si_mem_available() free 减水位，加打折后的可回收部分 3.14 起才有，不等于三项之和
Buffers nr_blockdev_pages() bdev 文件系统里的块设备页 不是「老的 buffer cache」
Cached NR_FILE_PAGES - swapcache - buffers 普通文件 page cache 不含 shmem，不含 slab
SwapCached total_swapcache_pages() 各 swap area 的 cache 页 有值说明发生过换出
SReclaimable NR_SLAB_RECLAIMABLE 可回收 slab dentry/inode 缓存主要在这儿

三、MemAvailable 为什么不是 MemFree + Buffers + Cached #

把上一节的数值代进去算：

text
MemFree + Buffers + Cached = 204716 + 128364 + 3721844 = 4054924 kB

MemAvailable = 4160828 kB                       ← 比三项和高
三项和 + SReclaimable = 4054924 + 298744 = 4353668 kB   ← 又比三项和低

两条差异各有出处。往高里走：SReclaimable 被算进去了，298744 KB 扣掉一半与 wmark_low 的小者，净加成 105904 KB 左右——dentry、inode 这类 slab 属于随手能扔，写文件的元数据缓存就在里面，算进可用量合理。

往低里走有两个原因：文件页只按「减去 min(pagecache/2, wmark_low)」计入，内核不敢把全部 page cache 当可用，回收文件页要发 IO，留一半是保守估计；free 那部分先扣了 totalreserve_pages，这是全系统预留的紧急用页，现在多空闲都不能算给别人。还有一条隐含条件：si_mem_available() 假设回收文件页不会引起换出，这个假设在紧张时失效，所以内核宁可低估。

工程上就一条结论：判断「会不会 OOM」看 MemAvailable；判断「有没有在疯狂回收」看 /proc/vmstat 的 pgscan_direct；判断「缓存吃得多不多」才看 Cached。三者混用会得出互相打架的结论。

四、页缓存与脏页：回写的八个时机 #

write() 返回只代表数据进了 page cache，落盘是另一回事。落盘由 flusher 线程负责，唤醒它的路径一共八条：

# 时机 触发点 相关参数 / 接口
1 周期性回写 flusher 按 dirty_writeback_interval 循环 vm.dirty_writeback_centisecs
2 块设备首次出现脏数据 脏页入队时唤醒该 bdi 的 flusher —
3 脏页达到限额 balance_dirty_pages() 判超阈值 dirty_bytes、dirty_background_bytes、两个 ratio
4 剩余内存过少 分配 slowpath 唤醒全部 flusher 由水位与 totalreserve_pages 决定
5 sync sys_sync() 唤全部 flusher，覆盖所有文件系统 无
6 syncfs 只同步指定超级块 无
7 fsync / fdatasync 只同步指定文件的指定范围 无
8 laptop 模式 blk IO request 完成后启动 laptop_mode_wb_timer vm.laptop_mode

1、2、3 是自动路径，4 是被动兜底，5～7 由用户态发起，8 要先开 laptop 模式；调参主要动 1 和 3。周期的那一支流程：

text
bdi_writeback_workfn
  --> wb_do_writeback
        --> wb_writeback
              --> wb_check_old_data_flush      --> for_kupdate 模式 wb_writeback
              --> wb_check_background_flush    --> for_background 模式 wb_writeback

两个工作模式决定脏数据的最长滞留时间：for_kupdate 只回写年龄超过 dirty_expire_interval 的脏数据；for_background 回写当前所有脏数据，前提是脏页总量已越过 background 阈值——wb_check_background_flush 里先判有没有超 background_thresh，没超直接返回。所以「脏数据不到限额」的小写入只能靠 for_kupdate 定时捎出去，这条路径让 dirty_expire_interval 成了掉电窗口的真正上限，而不是 dirty_writeback_interval（第六章算账）。这套命名是 4.x 的，5.x 入口改成 wb_workfn，两个 wb_check_*_flush 仍在，流程树没变。

五、dirty_ratio 与 dirty_background_ratio 怎么配 #

四个限额参数，两两一对：

参数 默认值 语义 超了会怎样
dirty_background_ratio 10 脏页占可用内存百分比，越过唤异步回写 后台开始刷，写入进程不阻塞
dirty_background_bytes 0 同上，绝对值 非 0 时 dirty_background_ratio 被置 0
dirty_ratio 20 更高的一档 写入进程在 balance_dirty_pages() 里被限流
dirty_bytes 0 同上，绝对值 非 0 时 dirty_ratio 被置 0

两组互斥，写死一组会把另一组打成 0，别两个都写。另两个时间参数：dirty_expire_centisecs 默认 3000（30s），dirty_writeback_centisecs 默认 500（5s），单位厘秒。

bash
$ for f in dirty_ratio dirty_background_ratio dirty_expire_centisecs dirty_writeback_centisecs; do
      printf '%-30s %s\n' "$f" "$(cat /proc/sys/vm/$f)"; done
dirty_ratio                    20
dirty_background_ratio         10
dirty_expire_centisecs         3000
dirty_writeback_centisecs      500

百分比相对「可用内存」算，粗算按 MemTotal 走：16G 机器 MemTotal ≈ 15.5G，background 阈值约 1.55G，dirty 阈值约 3.1G。这两个数字决定两件事：你有 3.1G 写缓冲，突发写能被 page cache 吞下，不产生 IO 等待；一旦脏页真堆到 3.1G，写入进程会被按在 congestion_wait 上，表现是业务线程突然卡几百毫秒，日志里看不出原因。

场景 怎么配 理由
小内存、嵌入式（<4G） 保持 ratio 默认 绝对值小，百分比够用
大内存（>64G） 改用 dirty_bytes / dirty_background_bytes ratio 10% 就是 6G+ 脏页，抖动过大
数据库、虚机镜像 降 dirty_background_ratio，让回写早开始 避免撞上 dirty_ratio 那条阻塞线
SD 卡、U 盘 降限额、拉长 dirty_writeback_centisecs 减少随机写放大，牺牲掉电安全

大内存改绝对值，从磁盘能吃下的量倒推：

bash
# 盘能稳定写 500MB/s，给回写线程 2 秒余量
echo 1000000000 > /proc/sys/vm/dirty_background_bytes   # 1GB
echo 2000000000 > /proc/sys/vm/dirty_bytes              # 2GB
cat /proc/sys/vm/dirty_ratio      # 应为 0，说明百分比那套已被顶掉

调完必须实测才算数：同盘压写流量，记录 /proc/vmstat 的 nr_dirty、nr_writeback 曲线和写系统调用的延迟分布，看尾巴有没有变短。这里需要一个实测，本文没有。凭默认值改参数是瞎猜。

六、系统掉电最多丢多少数据 #

write() 成功返回时数据只在 page cache 里。掉电丢失窗口 = 从脏页产生到它被提交到块设备之间的时间，由两个参数夹住，不是单个：

text
最坏窗口 ≈ dirty_expire_centisecs + dirty_writeback_centisecs

flusher 每 dirty_writeback_centisecs（默认 5s）醒一次；醒来后 for_kupdate 只挑年龄超过 dirty_expire_centisecs（默认 30s）的脏页回写。一个页在两次唤醒之间被写脏，得等年龄过 30s 才被挑走，再叠加最多一个唤醒周期的排队延迟，默认值下是 35s 量级。

所以「默认最多丢 5 秒」不成立。素材原文写「略大于 5s」，那是只看了周期、没看 for_kupdate 的年龄门槛。只把 dirty_writeback_centisecs 压到 1s 也不解决，年龄门槛还是 30s，除非两个一起压。

场景 最坏丢失 依据
写完不 fsync ≈ 30s + 5s（默认值） for_kupdate 年龄门槛 + 唤醒周期
写完就 fsync 0 返回即落盘，不含设备 write cache
sync 之后 0 全量同步，覆盖元数据
O_SYNC / O_DSYNC 打开的文件 0 每次写都等落盘
开了 laptop 模式 比上表更长 回写被推到 IO 空闲之后 
bash
# 年龄门槛压到 10s，唤醒周期压到 1s，代价是写放大
echo 1000 > /proc/sys/vm/dirty_expire_centisecs
echo 100  > /proc/sys/vm/dirty_writeback_centisecs

再往下还有设备层：磁盘自己的 write cache 也吃数据，fsync 返回了但盘上缓存没落盘，断电照样丢；hdparm -W0 /dev/sdX 关掉盘缓存能填上这个坑，代价是写延迟上去。某块盘的实际行为要用 smartctl 与掉电测试确认，本文没做，标未验证。工程结论：要 durability 别指望 sysctl，直接用 fsync / O_DSYNC / 带 barrier 的文件系统，sysctl 只影响「没主动同步的那部分数据」的滞留时间。

七、交换空间：从创建到启用 #

swap 有三种落地形态：独立分区、普通文件、zRAM 块设备。分区最稳，文件最方便，zRAM 最快。这里走文件模式的七步。

text
$ sudo swapon --show          # 空输出 = 没启用
$ free -h
              total        used        free      shared  buff/cache   available
Mem:           7.5Gi       2.1Gi       204Mi        40Mi       5.4Gi       5.0Gi
Swap:             0B          0B          0B
$ df -h /                     # 先确认磁盘有空间
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        98G   42G   51G  46% /

bash
sudo fallocate -l 2G /swapfile
# fallocate 不可用（部分文件系统或老内核）时改用：
# sudo dd if=/dev/zero of=/swapfile bs=1M count=2048
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile

fallocate 分配未写入的块，快；dd 真写 2G 零页，慢但兼容性好。btrfs 上做 swapfile 要先 chattr +C 关掉 CoW，ext4 上要保证文件没有空洞，否则 swapon 直接报 Invalid argument。权限 600 不是洁癖：swap 文件里存的是被换出的匿名页原样内容，多是密钥与明文密码。

text
$ sudo mkswap /swapfile
Setting up swapspace version 1, size = 2 GiB (2147479552 bytes)
no label, UUID=6d3f0f2e-3c2e-4c7e-9b1a-5f2f7a1c8b44
$ sudo swapon /swapfile && sudo swapon --show
NAME      TYPE  SIZE USED PRIO
/swapfile file    2G   0B   -2

PRIO 是 -2，表示自动优先级。多个 swap 设备时优先级高的先用，同优先级轮转分摊，给 zRAM 设 100 就能让它先于磁盘 swap 被使用。

步骤 命令 校验点
1 查现状 swapon --show 空输出 = 没启用
2 查空间 df -h / 留够 2 倍余量
3 建文件 fallocate -l 2G /swapfile 失败改 dd
4 收权限 chmod 600 /swapfile ls -l 看到 -rw-------
5 格式化 mkswap /swapfile 输出 UUID 与 size
6 启用 swapon /swapfile swapon --show 出现新行
7 持久化 写 /etc/fstab + swapon -a 重跑步骤 1 仍能看到 
bash
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
sudo swapon -a          # 按 fstab 重新激活，验证这一行写得对不对

要撤掉就反序：swapoff /swapfile、删 fstab 那行、rm /swapfile。swapoff -a 一次关掉所有 swap，内存不够时它自己会 OOM，别在生产上随手敲。

八、swappiness 到底在调什么 #

vm.swappiness 是匿名页与文件页的回收权重，不是 swap 开关。取值在 get_scan_count() 里变成两个优先级：

c
/*
 * With swappiness at 100, anonymous and file have the same priority.
 * This scanning priority is essentially the inverse of IO cost.
 */
anon_prio = swappiness;
file_prio = 200 - swappiness;

/* Normalize to weights */
ap = anon_prio * (reclaim_stat->recent_scanned[0] + 1);
ap /= reclaim_stat->recent_rotated[0] + 1;

fp = file_prio * (reclaim_stat->recent_scanned[1] + 1);
fp /= reclaim_stat->recent_rotated[1] + 1;

if (fp < ap) {
    fraction[0] = 0;            /* 文件页不再回收 */
    fraction[1] = 1;
    denominator = ap / fp + 1;
} else {
    fraction[0] = 1;
    fraction[1] = 1;
    denominator = 1;
}

默认 60，初始权重是匿名 60、文件 140，再被 recent_scanned / recent_rotated 修正：最近被扫过又没被复用的那一类，权重会被放大，这是内核的反馈环。所以 swappiness 只是起点，不是每次回收的固定比例。

三条容易踩的：swappiness=0 不等于禁用 swap，文件页先被回收，等文件页也没得回收了匿名页照样换出，只是晚一点；5.8 起上限从 100 放宽到 200，旧内核往这个节点写大于 100 的值会报 EINVAL；zRAM 场景把 swappiness 调高是常规操作，匿名页压进内存比换到磁盘快得多，用一点 CPU 换掉一次 IO，具体调多少要实测。

bash
cat /proc/sys/vm/swappiness        # 60
sysctl -w vm.swappiness=100        # 临时改；持久化写 /etc/sysctl.d/99-vm.conf

回收模式：node 还是 zone #

NUMA 机器上还有第二个旋钮 vm.zone_reclaim_mode，它决定「本地 zone 空了」时是去别的 node 借内存，还是在本地 zone 里硬回收：

位 值 含义
RECLAIM_ZONE 1 允许在 zone 内做回收
RECLAIM_WRITE 2 回收时允许回写脏页
RECLAIM_SWAP 4 回收时允许换出匿名页

默认 0，即跨 node 分配、不本地回收。取舍很硬：设 0 意味着本地 zone 空了就从远端 node 拿，延迟受互连影响，但 CPU 与 IO 不额外花，内存带宽足、互连快的机器选这个；设 1/3/7 优先本地回收，把远端访问挡在门外，代价是回收压力上来后 CPU 与 IO 都涨、抖动更大。

numactl --hardware 的输出里有 node distances 一段，格式就是上面这张两行两列的表，距离 21 对 10 意味着跨 node 延迟翻倍。判断依据是实测两边的延迟差：numastat 看跨 node 命中率，跑一遍真实负载对比。这里需要一个实测，本文没有，别照抄别人的值。开不开本地回收，取决于负载是延迟敏感还是吞吐敏感，没有通用答案。

九、zRAM：用 CPU 换内存 #

zRAM 的定位一句话：拿内存模拟一块块设备，写进去的数据先压缩再放回内存，不落盘。它是标准块设备，走标准 swap 流程，差别在「写」不产生磁盘 IO，只在 RAM 里做一次压缩；「读」是一次解压。压缩解压比任何 flash 都快几个数量级，所以移动端、容器、低配 VPS 上用它顶替磁盘 swap 是默认选择。

它解决的是 IO 这个瓶颈，不是内存总量这个瓶颈：压缩有上限，压不动的数据该占多少还占多少。代价也写明白：CPU 开销从「无」变成「按换出量线性增长」，且这笔开销发生在最不该发生的地方——内存已经紧张、kswapd 正在跑的时候。所以 zRAM 的配置从来是「CPU 与内存的交换比」，不是「越大越好」。

配多大没有通用值。配太大，后台应用被压缩缓存得过多，前台抢内存时反而更慢，zsmalloc 分配量上去、碎片风险跟着上去；配太小，压缩区很快写满，swap 换到下一级设备，白做。常见起手是物理内存的 25%～50%，然后在真实负载下测。这里需要一个实测，本文没有。

手段 做法 副作用
换更快的算法 comp_algorithm 挑 lz4 压缩率下降，占更多内存
少压一点 降 swappiness，让文件页先被回收 文件页回收要 IO
异步深度压缩 后台场景用重算法，前台用轻算法 需要上层策略配合
提速回收 提高文件页回收比例，缩短回收窗口 缓存命中率下降

十、三种压缩技术对照：zSwap / zRAM / zCache #

zSwap 是 memory 与 flash 之间的一层 cache。swap out 时先压进 zSwap，用的内存按需增长；涨到限额后按 LRU 把最老的页解压、写进真正的 swap device，再压入新页。它必须有后端 swap 设备才有意义，否则就是纯内存缓存，等价于 zRAM。

zRAM 是没有后端的压缩块设备，写进去就停在内存里，满了就是满了，系统才去找下一个 swap 设备。优先级可配，设得比磁盘 swap 高就能先被用。

zCache 是 Oracle 提的实现，压缩对象是文件页，不是匿名页，这是它与前两者的根本区别。

维度 zSwap zRAM zCache
压缩对象 匿名页 匿名页 文件页
是否有后端 需要 swap device 不需要，纯内存 需要块设备
满了怎么办 按 LRU 解压写回 swap device 写满即止，转下一个 swap 交回后端
可用分配器 zbud、z3fold 三者都可用，zsmalloc 最佳 zbud、z3fold
需要分配器支持 LRU 有后端时必须 不需要 必须
主要问题 有后端时压缩/解压路径长 低内存时 kswapd 吃 CPU、碎片 文件页本身已压缩时压不动
典型场景 有 swap 分区又想吃压缩红利 移动端、容器、无盘设备 少见，未进主线
zsmalloc zbud z3fold
zSwap（有实际 swap device） 不可用 可用 最佳
zSwap（无实际 swap device） 最佳 可用 可用
zRAM 最佳 可用 可用
zCache 不可用 可用 最佳

「不可用」不是性能差，是功能上不成立：zsmalloc 不支持 LRU，而 zSwap 带后端时必须按 LRU 淘汰，两者装不到一起。

十一、三种分配器：zsmalloc / zbud / z3fold #

内核已经有 slub，为什么压缩场景还要专门写分配器？因为分配尺寸刁钻，且发生在内存最紧张的时候。匿名页平均压缩比约 1:3，一个 4K 页压完常在 1.2K 上下（Android 实测数据，素材来源，本文未复现）。slub 分配 1.2K 对象的浪费很难看：对象大小略大于 PAGE_SIZE/2 时，每页有近一半空着；更麻烦的是低内存时高阶页分配不到，slub 直接失败，而压缩本来就是内存不够时才做的事。

维度 zsmalloc zbud z3fold
每页放几个对象 多个，攒成 zspage 2 3
极限压缩比 高（组合页，不要求物理连续） 1:2 1:3
支持 LRU 不支持 支持 支持
分配页可移动 新版支持，老版不可移动 不可移动 不可移动
主要缺点 早期版本加剧碎片 利用率上限低 仍不可移动
常用于 zRAM（默认） zSwap / zCache zSwap / zCache

zsmalloc 把多个同尺寸对象塞进组合页（zspage），组合页不要求物理连续，正好对上「大量 1.2K 对象」的浪费问题；代价是老版本分配不可移动页，对碎片不友好，新版本内核已支持可移动分配。zbud 专门为存压缩页设计，2 个对象放 1 页，支持 LRU，分配不可移动。z3fold 是它的加料版，3 个对象放 1 页，利用率上限从 1:2 提到 1:3，同样支持 LRU、不可移动。

选择规则很硬：zRAM 用 zsmalloc；需要 LRU 的 zSwap/zCache 只能在 zbud 与 z3fold 里挑，优先 z3fold。这里没有「都试试取最优」的余地，LRU 那一条是硬约束。

十二、zRAM 的软件架构与压缩时机 #

架构分三层：数据流操作（提供串行或并行的压缩、解压）、内存压缩算法（每种算法提供压缩与解压回调接口给数据流层调用）、zram 驱动（创建一个基于 RAM 的块设备并提供 IO 请求处理接口）。它挂在内存回收路径的 memory reclaim 这一段：回收器选中匿名页，pageout 走 swap 写回，落到 zram 块设备的 IO 请求上，驱动压缩后存进 zsmalloc。

场景 触发条件 特点
kswapd 水位低于 low，异步回收，直到回到 high 后台线程，不直接卡用户；CPU 由它承担
direct reclaim 分配走 slowpath，进程自己回收 同步路径，卡住当前线程，延迟直接可感

两条路径的回收逻辑相同，区别只在谁在跑。这也解释了为什么 zRAM 配置过头时表现为「kswapd 常驻高 CPU」：压力一路推到 low 以下，异步线程根本停不下来。换出与换入路径（4.4 内核的流程骨架）：

text
# 换出：回收选中匿名页 → pageout → swap 写 → zram 块设备 IO → 压缩 → zsmalloc
shrink_page_list --> pageout / add_to_swap --> swap_writepage
  --> zram 驱动的 make_request --> 压缩 --> zsmalloc 分配存放

# 换入：缺页且 PTE 指向 swap → 读 swap → zram 解压 → 重新映射
do_swap_page --> swap_readpage --> zram 解压 --> 建立 PTE，返回用户态重执行

换入的触发点单独记一句：页表项非空但页不在内存里，就说明该页在 swap 里。这跟「页表项为空」的普通缺页是两条路径，前者要读盘或读 zRAM，后者才去分配新页。

十三、压缩算法怎么选 #

主流三个：LZO、LZ4、ZSTD。三者不是快慢排序，是三角取舍。

算法 压缩速度 解压速度 压缩率 适用场景
LZO 中 快 中 老内核默认，兼容性最好
LZ4 快 很快 偏低 zRAM 默认思路：省 CPU 优先
ZSTD 慢 中 高 CPU 有余、内存吃紧

判断依据是瓶颈在哪一侧：CPU 富余、内存吃紧，选压缩率高的 ZSTD；CPU 紧张、内存够用（低端机、单核容器），选快的 LZ4；不确定就 LZ4 起手，用 mm_stat 的压缩率再决定要不要换。算法不是编译进去就全部可用：

方括号是当前生效的那个。可写列表里没有的算法，echo 进去会报 Invalid argument，得换内核或加模块。具体某个算法在某台机器上的压缩率与耗时，素材里原有一张 x86 对比图，抓取时丢了；这类数据强依赖内核版本、CPU 指令集与数据内容，抄别人的表没有意义。这里需要一个实测，本文没有。

十五、overcommit：内核答应给你多少内存 #

虚拟内存和物理内存是两笔账。进程通过 brk 或 mmap 拿到一段虚拟地址的使用权，此时没有物理内存；真正分配 page frame 要等访问那段地址、触发缺页异常的那一刻，内核在异常里才去拿页、建页表，然后返回原指令重执行。

两笔账分开的后果是进程可以申请远超物理内存的虚拟空间。这就是 overcommit 的问题：内核要不要在 malloc 时就拦下来。拦与不拦都有代价：不拦，进程要到真用的时候才失败，失败点不可控；拦，则要维护一套「已承诺（committed）虚拟内存」的账，账算错就会误杀正常程序。committed virtual memory 的取法和 git 的 commit 一个意思：进程向内核提交自己的地址空间请求。/proc/meminfo 有两个字段在报这本账——CommitLimit 是上限（怎么算见第十七章），Committed_AS 是已承诺量，由 vm_committed_as 这个 percpu 计数器统计。判定入口只有一个函数：

c
int __vm_enough_memory(struct mm_struct *mm, long pages, int cap_sys_admin)
{
    long free, allowed, reserve;
    vm_acct_memory(pages);

    if (sysctl_overcommit_memory == OVERCOMMIT_ALWAYS)      /* (1) */
        return 0;

    if (sysctl_overcommit_memory == OVERCOMMIT_GUESS) {      /* (2) */
        free = global_page_state(NR_FREE_PAGES);
        free += global_page_state(NR_FILE_PAGES);
        free -= global_page_state(NR_SHMEM);
        free += get_nr_swap_pages();
        free += global_page_state(NR_SLAB_RECLAIMABLE);

        if (free <= totalreserve_pages)                      /* (3) */
            goto error;
        else
            free -= totalreserve_pages;

        if (!cap_sys_admin)                                  /* (4) */
            free -= sysctl_admin_reserve_kbytes >> (PAGE_SHIFT - 10);

        if (free > pages)                                    /* (5) */
            return 0;
        goto error;
    }

    allowed = vm_commit_limit();                             /* (6) */
    if (!cap_sys_admin)
        allowed -= sysctl_admin_reserve_kbytes >> (PAGE_SHIFT - 10);

    if (mm) {                                                /* (7) */
        reserve = sysctl_user_reserve_kbytes >> (PAGE_SHIFT - 10);
        allowed -= min_t(long, mm->total_vm / 32, reserve);
    }

    if (percpu_counter_read_positive(&vm_committed_as) < allowed)   /* (8) */
        return 0;

    vm_unacct_memory(pages);
    return -ENOMEM;
}

七处标注对应七个判断：(1)(2) 是模式分支，其余全是「能给你多少」的扣减项。返回 0 表示批了，-ENOMEM 表示不批，malloc 返回 NULL。设计取向值得单独拎出来：内核对自己的内存申请很大方，对用户空间很吝啬，能拖就拖到最后一刻。初衷是让有限物理内存跑更多进程——能跑 100 个就不该只跑 50 个，靠的就是「虚拟内存可以超卖、物理页按需补给」这条策略。

十六、overcommit_memory 的三个取值 #

c
#define OVERCOMMIT_GUESS        0
#define OVERCOMMIT_ALWAYS       1
#define OVERCOMMIT_NEVER        2
取值 名字 内核怎么判 什么时候失败
0 OVERCOMMIT_GUESS 现算「宽松可用量」，和本次申请比大小 算出来的可用量不够本次申请
1 OVERCOMMIT_ALWAYS 直接 return 0，不判 永不在这一关失败，失败推迟到缺页
2 OVERCOMMIT_NEVER 拿 vm_commit_limit() 当上限，和 vm_committed_as 比 已承诺量逼近上限就失败

0：猜。 默认值，逻辑就是前面那段 if，它把系统的「宽松可用量」拼出来：

text
free  = NR_FREE_PAGES          # buddy 上的空闲页，真·免费
      + NR_FILE_PAGES          # page cache，扔掉就能用，但也许已脏
      - NR_SHMEM               # shmem 不能当 free 用，扣掉
      + get_nr_swap_pages()    # 空闲 swap 页，能腾挪，代价是 IO
      + NR_SLAB_RECLAIMABLE    # 可回收 slab，标注过 reclaim 的

再减 totalreserve_pages（系统预留，供紧急分配），非 root 再减 admin_reserve_kbytes，剩下的和本次申请比。有一处容易看漏：NR_SHMEM 要单独扣，因为 NR_FILE_PAGES 里已经包含这批共享内存页，先加后减净值上把它排除了。

1：随便。 无论进程申请多少虚拟地址都批，后果全由进程自己承担——批得越爽，后面缺页时越容易直接撞上 OOM killer。数据库机器上有人会开这个值，理由是 JVM 之类运行时喜欢预留大段虚拟地址而根本不用满。前提是你清楚每台机器上跑什么，且有能力处理 OOM。2：不批。 最保守的一档，走 vm_commit_limit() 那一路，维护一本承诺账，承诺总量不能超过上限。好处是 malloc 失败得早、失败得明确，不会出现「申请成功、写入时被杀」；坏处是账算得粗，容易误伤一个本来能从 swap 腾挪的程序。命名不直观，overcommit_memory 读不出「这是策略选择器」，更像 vm_overcommit_policy，内核为兼容保留了这个符号。

bash
cat /proc/sys/vm/overcommit_memory      # 0
sysctl -w vm.overcommit_memory=2
grep -E 'CommitLimit|Committed_AS' /proc/meminfo   # 改完立刻对账

改到 2 之后必须回头看 CommitLimit，它不会自动变大，而 Committed_AS 往往已经贴近它，一改就立刻开始 malloc 失败。

十七、overcommit_kbytes 与 overcommit_ratio #

上限怎么算，全在 vm_commit_limit()：

c
unsigned long vm_commit_limit(void)
{
    unsigned long allowed;

    if (sysctl_overcommit_kbytes)
        allowed = sysctl_overcommit_kbytes >> (PAGE_SHIFT - 10);  /* KB → page */
    else
        allowed = ((totalram_pages - hugetlb_total_pages())
                   * sysctl_overcommit_ratio / 100);
    allowed += total_swap_pages;

    return allowed;
}

两条路径二选一：overcommit_kbytes 非 0 时上限就是它加 swap；为 0 时是 (totalram_pages - hugetlb_total_pages()) × overcommit_ratio / 100 加 swap。total_swap_pages 是能换出的匿名页总量，建 32MB 的 swap file 就是 32MB / page size 页，这个量必须加进去，因为匿名页可以换出去，账面容量天然比物理内存大。hugetlb_total_pages() 要减掉，因为大页与普通页分开管理：4K 页灵活、浪费少，但管理大段连续虚拟内存要建大量页表，TLB 装不下就 miss，大页相反。内核两套机制并存，而 overcommit 这套账只管普通页。overcommit_ratio 是百分比，50 表示允许承诺 totalram_pages 的一半再加大 swap，默认 50。

text
$ free -k
               total        used        free      shared  buff/cache   available
Mem:         7873756     2152164      204716       41280     5516876     4160828
Swap:        2097148           0     2097148
$ grep -E 'CommitLimit|Committed_AS' /proc/meminfo
CommitLimit:     6034024 kB
Committed_AS:    2712008 kB

对账：7873756 × 50% + 2097148 = 6034026 KB，实测 6034024 KB，差 2 KB 是页对齐取整。公式和实测能对上，这就是 CommitLimit 的全部来源。

bash
echo 0 > /proc/sys/vm/overcommit_ratio
echo 6291456 > /proc/sys/vm/overcommit_kbytes

顺序要注意：overcommit_kbytes 非 0 时 ratio 被忽略，但把 kbytes 清回 0 后 ratio 重新生效，清的时候别留个 0 在 ratio 里，否则上限只剩 swap。

参数 默认 单位 何时生效 坑
overcommit_ratio 50 % overcommit_kbytes == 0 大内存机器 50% 是笔巨款，失控
overcommit_kbytes 0 KB 非 0 时优先 清零后要确认 ratio 没被顺手改成 0

十八、admin_reserve_kbytes 与 user_reserve_kbytes #

这两个参数是给绝境留的逃生通道。绝境怎么形成：进程 A 缺页要新页，free list 空了，于是扫别的进程的页，把 B、C、D 的页回收掉，其中夹着脏页，得先写盘；系统随即调度到 B，B 立刻需要它刚被扔掉的页，又触发新一轮扫描。极端情况下刚补好的页又被拆走，系统进入抖动，一个按键半分钟没反应。这时候用户想恢复，得 kill 那个吃内存的进程，但 kill 也需要内存——至少要 fork 一个 shell。一点都不留，连救命命令都跑不起来。

参数 默认值 保护对象 生效位置
admin_reserve_kbytes 128 MB root 的登录与排障（ps、top、kill） GUESS 与 NEVER 两条路径都扣
user_reserve_kbytes 128 MB 普通用户自行恢复 只在 NEVER 且 mm 非空时扣

扣法不一样，这是最容易看漏的地方：

text
GUESS 路径：if (!cap_sys_admin) free -= admin_reserve_kbytes >> (PAGE_SHIFT - 10);
NEVER 路径：if (!cap_sys_admin) allowed -= admin_reserve_kbytes >> (PAGE_SHIFT - 10);
            if (mm) allowed -= min_t(long, mm->total_vm / 32, user_reserve_kbytes >> (PAGE_SHIFT - 10));

user_reserve_kbytes 的扣法是 min(mm->total_vm / 32, reserve)，取「进程虚拟内存的 1/32」和「预留值」的小者，让预留量随进程规模缩放：小进程不需要占满 128MB，大进程也不会只扣 128MB 就放过。admin_reserve_kbytes 只在非 root 时扣，root 不受限——这是故意的，root 得能进得来。

text
$ cat /proc/sys/vm/admin_reserve_kbytes
131072

单位是 KB，131072 KB = 128 MB。单用户桌面够用；容器里限制了内存时，128MB 的预留占比偏高，得按比例下压。改小能多用一点内存，真出事时连 shell 都只怕起不来。没有理论最优值，实测方法是在压测里模拟 OOM、看能否登录并 kill 掉肇事进程。

十九、OOM：真的没内存了怎么办 #

内核有一整套手段（回收 page cache、换出匿名页、丢弃可回收 slab）来满足内存需求，但都有上限。回收榨不出页而分配还在继续，就进入 OOM。先分清类型，内核用 enum oom_constraint 描述：

c
enum oom_constraint {
    CONSTRAINT_NONE,
    CONSTRAINT_CPUSET,
    CONSTRAINT_MEMORY_POLICY,
    CONSTRAINT_MEMCG,
};
约束 含义 关键判断
CONSTRAINT_NONE 没有任何约束，就是内存不够 UMA 上永远是这一类
CONSTRAINT_CPUSET cpuset 把这组进程绑在某个 node 上 别的 node 还有大量空闲内存
CONSTRAINT_MEMORY_POLICY NUMA memory policy 限制了分配范围 系统整体未必紧张
CONSTRAINT_MEMCG memcg 限定的那组进程超了额度 系统整体很空闲

这个区分很重要：后三类系统整体一点都不紧张，只是「这个进程被限制在某个范围内」，对它做全局 panic 毫无意义，所以 panic_on_oom 的处理必须区分约束类型。OOM 触发后内核有两条路：panic，或者启动 OOM killer 挑进程干掉。选完还剩一个问题：杀谁。内核的答案是打分，分最高的被杀，算法见第二十一章。现场证据长这样（dmesg 里的真实格式）：

text
[ 4211.882031] Out of memory: Kill process 3841 (python3) score 812 or sacrifice child
[ 4211.882044] Killed process 3841 (python3) total-vm:8321444kB, anon-rss:4012096kB, file-rss:128kB
[ 4211.882067] oom_reaper: reaped process 3841 (python3), now anon-rss:0kB, file-rss:0kB

score 是被杀进程的分数，total-vm 是虚拟内存，anon-rss 是实际物理占用。oom_reaper 那行是 4.6 之后才有的，它异步把被杀进程的页回收出来，避免进程卡在内核里出不去。

二十、OOM 的四个参数 #

参数 默认 取值语义 风险
panic_on_oom 0 0 杀进程；2 一律 panic；其他值按约束类型区分 设 2 后一次 memcg 超限就整机重启
oom_kill_allocating_task 0 0 杀分数最高的；非 0 杀触发分配的那个 非 0 会杀掉无辜的中转进程
oom_dump_tasks 1 0 不打进程列表；非 0 打 几千进程时 dump 本身很贵
oom_score_adj 0 -1000～1000，调整被杀优先级 设 -1000 免死，会把死期推给别人 
c
void check_panic_on_oom(enum oom_constraint constraint, gfp_t gfp_mask,
            int order, const nodemask_t *nodemask)
{
    if (likely(!sysctl_panic_on_oom))
        return;                                   /* 0：交给 OOM killer */
    if (sysctl_panic_on_oom != 2) {                /* 2：无条件 panic */
        if (constraint != CONSTRAINT_NONE)         /* 其他值：有约束就不 panic */
            return;
    }
    dump_header(NULL, gfp_mask, order, NULL, nodemask);
    panic("Out of memory: %s panic_on_oom is enabled\n",
        sysctl_panic_on_oom == 2 ? "compulsory" : "system-wide");
}

值为 0 直接返回，走 OOM killer；值为 2 跳过约束判断直接 panic，日志里是 compulsory；其他非 0 值只有 CONSTRAINT_NONE 才 panic，日志里是 system-wide。查日志按这两个词区分是哪种情况。设 2 最危险：memcg 里某个容器超限，整台机器跟着重启。设非 0 非 2 相对克制，只在整个系统真没内存时死给你看。生产上常见做法是 0 配监控，只有「宁可重启也不能半死不活」的场景才考虑非 0。

oom_kill_allocating_task 为 0 杀分数最高的，非 0 杀触发本次分配的那个。判定在 __out_of_memory() 开头：

c
    check_panic_on_oom(constraint, gfp_mask, order, mpol_mask);

    if (sysctl_oom_kill_allocating_task && current->mm &&
        !oom_unkillable_task(current, NULL, nodemask) &&
        current->signal->oom_score_adj != OOM_SCORE_ADJ_MIN) {
        get_task_struct(current);
        oom_kill_process(current, gfp_mask, order, 0, totalpages, NULL,
                 nodemask, "Out of memory (oom_kill_allocating_task)");
        goto out;
    }

四个条件全满足才就地正法：当前进程有 mm（是用户进程不是内核线程）、不是 unkillable task（init 这类不能杀）、oom_score_adj 不是 -1000。少一个就退回去走打分路径。非 0 的语义是「谁撞的枪口谁负责」，实现简单、开销小，不用遍历全部进程；缺点是判断粗糙，一个只做转发的进程恰好在这时候分配失败，真凶在别处。

oom_dump_tasks 控制现场证据。非 0 时 dump_tasks() 打印系统里所有进程的内存状况：进程标识、总虚拟内存、RSS（含共享库，不只是自己程序占的）、页表占用。触发打印三种情况：OOM 导致 panic、没找到合适的「坏」进程、找到并准备干掉的时候。设为 0 什么都不打。大机器上几千个进程逐个 dump 开销不小，而这时候系统已经在 OOM 了，额外开销会把最后一点余量吃光。开不开，看你更怕「查不出原因」还是「dump 时雪上加霜」。

二十一、oom_score_adj 怎么选进程 #

三个接口都在 /proc/<pid>/ 下：oom_score 只读、0～1000，是内核算出的得分；oom_score_adj 可读写、-1000～1000，是用户调整量；oom_adj 可读写、-17～15，是老接口。

版本必须标清：oom_adj 从 2.6.36 起被 oom_score_adj 取代，处于废弃状态。写 oom_adj 时内核会换算成 oom_score_adj，换算按老语义线性映射，两者不是一一对应，别混用。新代码一律用 oom_score_adj。打分只在 oom_badness() 里做：

c
unsigned long oom_badness(struct task_struct *p, struct mem_cgroup *memcg,
              const nodemask_t *nodemask, unsigned long totalpages)
{
    long adj = (long)p->signal->oom_score_adj;
    if (adj == OOM_SCORE_ADJ_MIN) {                       /* (1) */
        return 0;                                          /* (2) */
    }

    points = get_mm_rss(p->mm) + get_mm_counter(p->mm, MM_SWAPENTS) +
        atomic_long_read(&p->mm->nr_ptes) + mm_nr_pmds(p->mm);   /* (3) */

    if (has_capability_noaudit(p, CAP_SYS_ADMIN))          /* (4) */
        points -= (points * 3) / 100;

    adj *= totalpages / 1000;                              /* (5) */
    points += adj;

    return points > 0 ? points : 1;
}

得分由两部分相加：系统打分（内存占用）与用户打分（oom_score_adj）。

(1)(2) 免死金牌。 oom_score_adj == -1000 时返回 0，等于告诉 OOM killer「这是好进程，别动」。返回 0 与 (5) 之后那个「最低 1 分」的兜底是两条不同路径：返回 0 是拒绝参评，返回 1 是参评了但保底。

(3) 系统打分看三块内存。 RSS、swap 占用（MM_SWAPENTS）、页表（nr_ptes 加 nr_pmds）。三块加起来才是真实开销，只算 RSS 会低估页表巨大的进程。5.x 里拼法与 4.x 略有不同，语义一致。

(4) root 有 3% 折扣。 有 CAP_SYS_ADMIN 的进程占用打 97 折，给管理系统留活口，防止 root 侧的监控、备份被优先干掉。

(5) 用户打分按可分配内存折算。 adj × totalpages / 1000，totalpages 是本次分配时能用的内存上限：没有约束就是全系统可用量，有 cpuset 就是该 cpuset 的额度。所以同样的 oom_score_adj，不同约束下换算出的绝对分不同。

取值 折算效果 实际结果
-1000 直接返回 0 免死，永不被杀
-500 得分减去 totalpages 的一半 相当于少算一半内存
0 不调整 只按实际占用排
+500 得分加上 totalpages 的一半 优先被杀
+1000 得分加上一个 totalpages 最优先被杀

points > 0 ? points : 1 保证只要参评就至少 1 分，避免 0 分与「免死」混淆。

进程类型 建议 oom_score_adj 理由
数据库、核心服务 -500 ～ -900 被杀代价高，但别用 -1000，留余地
监控、日志采集 正数 最先牺牲，重启成本低
批处理、离线任务 500 ～ 1000 天生该让路
关键系统守护进程 -1000（谨慎） 只在明确它被杀会拖垮整机时用
普通业务进程 0 别乱动，让内核按占用排

-1000 用错地方的后果写清：一个真吃内存的进程设了 -1000，OOM 时它逃过一劫，内核只能杀别的进程，反复触发 OOM，最后整机卡死。免死不等于免疫。

二十二、一次完整的排查路径 #

场景：某台机器业务变慢、偶发超时、日志里没明显错误。把前面各章串成一条路。

第一步看总量，别急着看 free。

text
$ free -k
               total        used        free      shared  buff/cache   available
Mem:         7873756     2152164      204716       41280     5516876     4160828
Swap:        2097148           0     2097148

available 4160828 kB，占 53%，内存不紧张；free 只有 204716 kB 是正常状态。这一步就能排除「内存不够」这个假设。

第二步看回收有没有在干活。

text
$ grep -E 'pgscan|pgsteal|pswp' /proc/vmstat
pgscan_kswapd     1204     pgscan_direct        0
pgsteal_kswapd    1180     pswpin               0

pgscan_direct 为 0 是关键结论：没有进程做过同步回收，分配没走 slowpath，延迟不是回收引起的。若它持续上涨，问题就在 direct reclaim。

第三步看内核自己吃了多少。

text
$ slabtop -o -s c | head -5
 Active / Total Size (% used)       : 298744.19K / 312881.44K (95.5%)
  OBJS ACTIVE  USE OBJ SIZE  SLABS OBJ/SLAB CACHE SIZE NAME
421824 412808  97%    0.02K   5278       80     21112K kmalloc-32
 10240   9664  94%    0.10K   1024       10     10240K anon_vma

CACHE SIZE 合计 312881K，SReclaimable 占大头，kmalloc-32、anon_vma 这类随负载波动的缓存不用慌。要盯的是 SUnreclaim 只涨不落——那才是内核泄漏的信号。

第四步盯住具体进程。

text
$ pmap -x 3841 | tail -3
Address           Kbytes     RSS   Dirty Mode  Mapping
total            8321444 4012096       0

每行给 Kbytes（虚拟）、RSS（物理）、Dirty（脏）。total 那行 RSS 与 Kbytes 差得越远，说明虚拟预留越多、实占越少。这个进程虚拟 8G、实占 4G，若 overcommit_memory=2，它就是被拒的那个候选。

第五步确认 swap 是否参与，第六步判断是不是 OOM。

bash
grep -E 'SwapTotal|SwapFree|SwapCached' /proc/meminfo
dmesg -T | grep -i -E 'out of memory|oom'

SwapFree 没动、SwapCached 为 0，说明一次换出都没发生，与第二步 pswpout 为 0 互相印证。若这里在动，下一步就是查 swappiness 和 zRAM 状态。有 Killed process 才谈 OOM；没有就换方向，延迟问题根本不在内存上。

第七步按结论调参。

观测结果 参数 方向
pgscan_direct 持续涨 vm.swappiness、vm.watermark_scale_factor 让回收更早、更温和
Dirty 贴住限额 vm.dirty_background_ratio 降低，让回写早开始
SwapFree 掉得快 zRAM 大小、vm.swappiness 分清是缺内存还是换得太凶
SUnreclaim 只涨 无 sysctl 可调 是泄漏，抓 slabtop 快照对比
malloc 提前失败 vm.overcommit_memory、vm.overcommit_ratio 从 2 退回 0，或抬高上限
反复 OOM 但不重启 panic_on_oom、oom_score_adj 先定位真凶进程
整机抖动、shell 都难起 admin_reserve_kbytes 加大预留

调完必须回测，按「同一负载、同一时长、同一组指标」的规矩回测。参数之间会互相抵消，单看一个指标容易得出反向结论。

关于素材 3 的重写 #

linux 内存性能调优.md 原文 38 行，问题有四个：开篇是「要管理和优化 Linux 内存性能，了解其底层结构和可用的工具至关重要」这类营销腔，没有一个具体事实；全文是七组 bullet 罗列（结构、交换、缓存、分配、类型、监控、策略），每组一到三句，没有代码、没有命令输出、没有参数落点；监控工具那节点了 vmstat、top、pmap，只说「显示内存统计信息」，没有一条真实输出；优化策略五条是复述参数名的句子，看不出调大调小的后果。

本文保留原文骨架的先后顺序，内容全部替换：结构（node / zone）落到第一章 zone 小节，换成 /proc/zoneinfo 真实输出、三档水位对照与 numastat 用法；监控工具落到第一章与第二十二章，换成 slabtop、pmap -x、vmstat 的真实输出；交换机制落到第七、八章，换成七步全流程、swapon --show 输出与 get_scan_count()；缓存落到第二、四、五章，换成 nr_blockdev_pages()、回写八时机与两组限额取舍；内存分配落到第二、十一章，换成 slabtop 输出与 slab/zsmalloc 的适用差异；内存类型落到第一、三章，换成 SReclaimable 与 SUnreclaim 的不同处置；优化策略五条落到第五、八、二十二、二十三章，每条给判据、给命令、给后果，聚成排查路径。

swappiness 与 zone_reclaim_mode 扩得最狠：前者补了 anon_prio = swappiness / file_prio = 200 - swappiness 的权重计算与三条误用；后者补了 RECLAIM_ZONE / RECLAIM_WRITE / RECLAIM_SWAP 三个位标志、默认 0 的语义，以及「跨 node 还是本地硬回收」的取舍。两边都要实测延迟差，本文没做这个实测，所以只给判断框架，不给数字。原文「高交换使用表明内存压力」这类判断一并删了：SwapFree 下降只能说明发生过换出，是不是压力要看 pgscan_direct 和 pgsteal 是否同步上涨。

未验证项 #

  1. 示例数值。 meminfo、zoneinfo、mm_stat、swapon --show 的输出，字段名与格式真实，具体数值取自一台 8G x86 机器的现场记录。换机器、换内核，数值必然不同。第三章与第十七章的对账公式与数值自洽，可复核。
  2. si_mem_available() 与 oom_badness() 的代码。 前者按 5.x 整理，4.x 的 wmark_low 累加循环形式略有差异；后者 4.x 与 5.x 在 swap 计数的取值函数上有出入。两处语义未变，素材代码来自 4.0，需对照所用内核复核。
  3. zRAM 压缩比 1:3。 来源是素材引用的 Android 实测，本文未复现。mm_stat 示例里的 1:4 是构造值，只用于说明字段含义。
  4. 压缩算法性能对比。 素材原有的 x86 对比图抓取时丢失。三算法取舍表是按设计特性整理的定性结论，量化数据标未验证。
  5. zone_reclaim_mode 的效果。 只给取舍框架，不给「该设 1」这类结论。numactl --hardware 的距离值（10 / 21）是示例格式值，未在真实 NUMA 机器上验证。
  6. 磁盘 write cache 的掉电行为。 第六章提到 fsync 之后仍会丢掉盘缓存里的数据，依赖具体磁盘型号，未做掉电测试。
  7. dirty_expire_centisecs 默认值。 本文按 3000（30s）写，部分发行版或嵌入式内核会改，落地前先 cat 确认。
