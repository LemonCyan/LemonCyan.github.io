一、交叉编译到底在做什么 #

1.1 为什么不能直接用 gcc #

主机 gcc 有三个身份绑定在 x86 上：产出的机器码是 x86 指令、链接的库是 x86 的 libc.so、可执行文件头写的是 EM_X86_64。目标板要的是 ARM 指令、ARM 的 libc、EM_ARM。所以需要一个「跑在 x86 上、产出 ARM」的编译器——它内部自带一整套 ARM 版 libc 与 binutils，与主机系统里的东西完全隔离。

这也解释了两个常见困惑：

  • 为什么工具链必须整包下载解压，而不是 apt install 一个就完事——因为它要带的是一整套自洽的库与工具；
  • 为什么用主机 gcc 编出来的程序拷到板子上跑不了——不是「没编译对」，而是架构根本不同（报 cannot execute binary file 或 Exec format error）。

1.2 四步与四个程序 #

hello.c
  │ cpp  （预处理：展开宏、包含头文件、去注释）
  ▼
hello.i
  │ cc1  （编译：C → 汇编，做优化与语法检查）
  ▼
hello.s
  │ as   （汇编：汇编 → 机器码目标文件）
  ▼
hello.o
  │ ld   （链接：合并目标文件与库，重定位）
  ▼
hello（ELF 可执行文件）
阶段 实际程序 对应 gcc 选项 停下来看什么
预处理 cpp -E .i 文件，能看到宏展开后的真实代码
编译 cc1（注意是 cc1，不是 ccl） -S .s 汇编
汇编 as -c .o 目标文件
链接 ld 不加 -c/-S/-E 就到这一步 可执行文件

arm-linux-gcc 这一个命令在前三步分别调起 cpp、cc1、as，最后调 ld（实际上调 collect2 再转 ld）。加 -v 能看到它到底执行了哪些命令行。

1.3 常用选项分为四类 #

类别 选项 说明
控制阶段 -E / -S / -c 停在预处理 / 编译 / 汇编之后
优化 -O0 ~ -O3、-Os 裸机与驱动调试期用 -O0 或 -O1；-O0 时变量不会被优化掉，但单步会跳
调试信息 -g 生成 DWARF，GDB 靠它映射源码行
预处理 -D、-U、-I 定义 / 取消宏，追加头文件搜索路径
链接 -L、-l、-static、-shared 库搜索路径、指定库、静态链接、生成共享库
报警 -Wall、-Werror 打开常用警告 / 把警告当错误
架构 -march、-mcpu、-mfloat-abi 交叉编译最容易错的一类，见下
⚠`-march` 与板子的 CPU 版本必须对得上

用 -march=armv5te 编出的代码里不会有 pld 一类新指令；反过来用了太新的 -march（如 armv7-a）却在 ARM9 上跑，会在执行到那条指令时抛 Illegal instruction。原文里那个 Error: selected processor does not support 'pld [r5,#0]' 就是反例——源码里用了 pld 但 -march 太低，汇编器直接拒绝。

验证方法：arm-linux-readelf -A hello，看 Tag_CPU_arch: v5TE 是否符合预期。

二、链接器与链接脚本 #

2.1 -Ttext 与位置相关码 #

裸机程序最常见的一句命令是：

bash
arm-linux-ld -Ttext 0x30000000 -o led.elf head.o main.o

它把代码段的链接地址定在 0x30000000。这个地址的意义在于：程序里所有「绝对跳转」与「取全局变量」都会按这个基址算好。所以链接地址 ≠ 运行地址时，绝对地址那部分就全错。

写法 是否位置相关 说明
b label 位置无关 编码的是相对偏移，搬到哪都能跳
ldr pc, =label 位置相关 会从文字池取绝对地址，地址不对就飞
bl func 位置无关 相对偏移，但范围限制 ±32MB
ldr r0, =0x56000010 位置相关（但目标是固定寄存器地址，无所谓） 常量地址不算代码地址

这就是 u-boot 早期必须「在 Flash 里按链接地址跑，或在 DDR 里按链接地址跑」的原因。现代 u-boot 用 -pie 与 GOT 让自身位置无关，代价是多了重定位表——Mini2440 那代为了压 4KB 限制，反而是把 -pie 去掉的。

2.2 一个最小链接脚本 #

OUTPUT_ARCH(arm)
ENTRY(_start)

SECTIONS
{
    . = 0x30000000;

    .text : {
        *(.text)
    }

    .rodata : {
        *(.rodata)
    }

    .data : {
        *(.data)
    }

    __bss_start = .;
    .bss : {
        *(.bss)
        *(COMMON)
    }
    _end = .;
}

-Ttext 相当于「只定 .text 起始地址」的简化版；需要精确控制段顺序、加符号（如 __bss_start）、把某些段放特殊位置时，必须写完整 lds。

⚠`.bss` 不进二进制文件

.bss 段在 ELF 里只记录「大小」，objcopy -O binary 出来的 bin 文件里根本没有它。所以裸机启动代码必须自己把 __bss_start 到 _end 清零，否则全局变量是随机值。这是「程序在仿真器里对、烧到板子上错」的头号原因。

2.3 链接脚本里的符号怎么被 C 用 #

c
extern char __bss_start, _end;      /* 注意：是符号，不是变量，别加取址之外的用法 */

void clear_bss(void)
{
    char *p = &__bss_start;
    while (p < &_end) *p++ = 0;
}

汇编里则是 ldr r0, =__bss_start（取地址），而不是 ldr r0, __bss_start（取值）。这个区别在链接脚本符号上是致命的。

三、objcopy 与 objdump #

3.1 objcopy：把 ELF 剥成裸二进制 #

选项 作用
-O binary 输出裸二进制（去掉 ELF 头与段表，只留段内容）
-S 去掉符号表与重定位信息
-R <section> 移除指定段
-g 去掉调试信息
-I binary -O elf32-littlearm -B arm 反向：把任意文件包成 ELF 对象（做资源嵌入用） 
bash
arm-linux-objcopy -O binary -S led.elf led.bin

u-boot 的 u-boot.bin、内核的 Image 都是这么来的。

3.2 objdump：反汇编与段信息 #

选项 作用
-d 反汇编可执行段
-D 反汇编所有段（含数据段，会看到一堆无意义指令）
-h 段头表：每段的 VMA/LMA/大小/属性
-f 文件头：架构、入口地址、标志
-b binary -m arm 反汇编裸二进制（没有 ELF 头时必须给这两个参数） 
bash
arm-linux-objdump -D u-boot > u-boot.dis    # 存一份全量反汇编，配合 grep 定位
arm-linux-objdump -h vmlinux               # 看各段 VMA 是否与链接脚本一致

3.3 读一条机器码 #

以 0xe3a0244e 为例，拆出来是 mov r2, #0x4e000000：

字段 位 值 含义
cond [31:28] 0xe = 1110 无条件执行（AL）
指令类型 [27:26] 00 数据处理
opcode [24:21] 1101 MOV
S [20] 0 不更新标志
Rd [15:12] 0010 r2
rotate [11:8] 0100 循环右移 2*4 = 8 位
immed_8 [7:0] 0x4e 0x4e 循环右移 8 位 = 0x4e000000

这条拆解解释了 ARM 立即数的那个著名限制：只能表示「8 位值循环右移偶数位」得到的数。所以 0x4e000000 可以，0x12345678 不行（编译器会改用 ldr r0, =0x12345678 从文字池取）。

4.2 tftp 与 nfs #

bash
sudo apt-get install tftpd-hpa tftp-hpa
sudo vim /etc/default/tftpd-hpa
# TFTP_USERNAME="tftp"
# TFTP_DIRECTORY="/tftpboot"
# TFTP_ADDRESS="0.0.0.0:69"
# TFTP_OPTIONS="-c -s -l"
sudo mkdir -p /tftpboot && sudo chmod 777 /tftpboot
sudo systemctl restart tftpd-hpa

bash
sudo apt-get install nfs-kernel-server
sudo vim /etc/exports
# /nfsroot/rootfs 192.168.1.0/24(rw,sync,no_root_squash)
sudo exportfs -ra && sudo systemctl restart nfs-kernel-server
showmount -e localhost              # 验证导出
⚠`portmap` 已经不存在了

老教程写 apt-get install nfs-kernel-server portmap，在 Ubuntu 12.04 之后 portmap 已被 rpcbind 取代，直接装会报「没有这个包」。现代系统 nfs-kernel-server 会自动拉 rpcbind，不用单独装。

4.3 静态 IP 的三种时代写法 #

时期 写法 备注
Ubuntu 16.04 及更早 /etc/network/interfaces 里写 iface eth0 inet static 现在默认不生效
Ubuntu 17.10~22.04 netplan：/etc/netplan/*.yaml 需要 netplan apply
Ubuntu 22.04+ 桌面版 NetworkManager（图形界面或 nmcli） 服务器版仍是 netplan 
yaml
# /etc/netplan/01-netcfg.yaml
network:
  version: 2
  ethernets:
    enp3s0:
      dhcp4: no
      addresses: [192.168.1.111/24]
      gateway4: 192.168.1.1
      nameservers:
        addresses: [8.8.8.8]
ℹ老教程改 `/etc/network/interfaces` 后没反应，不是你写错了

Ubuntu 20.04 起该系统默认用 netplan，/etc/network/interfaces 里写了也不会被读取。判断当前用哪套：ls /etc/netplan/ 有 yaml 就是 netplan；systemctl status NetworkManager 活着就是 NM。

4.4 工具链装在哪个 PATH 下，以及顺序问题 #

需要 PATH 的东西 建议位置 注意
交叉工具链 ~/.bashrc 里前置或后置都行 要切版本时靠前置覆盖
自建 gdb 必须前置（/usr/local/gdb/bin:$PATH） 否则会被系统 /usr/bin/gdb 抢先，用错版本
JDK（Eclipse 需要） 前置 同时设 JAVA_HOME 与 CLASSPATH 
bash
# 工具链
export PATH=$PATH:/usr/local/arm/4.3.2/bin
# 自建 gdb 必须在系统 gdb 之前
export PATH=/usr/local/gdb/bin:$PATH
# JDK
export JAVA_HOME=/usr/java/jdk1.7.0_04
export PATH=$JAVA_HOME/bin:$JAVA_HOME/jre/bin:$PATH

验证顺序对不对：which arm-linux-gdb 应指向 /usr/local/gdb/bin/arm-linux-gdb；which gdb 若指向自建版本，说明系统 gdb 被覆盖了——这通常不是你想要的。

五、GDB + JLink 调试链 #

6.1 四个角色 #

角色 本例中是谁 作用
调试器 arm-linux-gdb 解析 ELF 符号、下发命令、显示源码与寄存器
GDB Server JLinkGDBServer 把 GDB 的远程协议翻译成 JLink 的 USB 协议
调试代理 JLink 硬件 把 USB 命令翻译成 JTAG/SWD 时序
调试单元 S3C2440 片内 ICE 真正停 CPU、读写内存与寄存器

链路是：gdb --(tcp:2331)--> JLinkGDBServer --(usb)--> JLink --(jtag)--> S3C2440。

5.2 起服务 #

bash
cd /usr/local/JLink_Linux_V434a
./JLinkGDBServer              # 默认监听 2331

5.3 一份能用的 gdbinit（S3C2440 + Mini2440） #

这份脚本把「CPU 上电后没人给你初始化硬件」这件事补上，是裸机调试的核心。整份只在这里写一次，Eclipse 与 VS Code 都引用它。

target remote localhost:2331
monitor endian little
monitor speed 30

# 进 SVC 模式，关 IRQ/FIQ
monitor reg cpsr = 0xd3

# 关 MMU 与 D-Cache（CP15 c1）
monitor cp15 1 0x00000000
monitor cp15 7 0x00000000
monitor cp15 8 0x00000000

# 关看门狗
monitor memU32 0x53000000 = 0x00000000

# 屏蔽全部中断
monitor memU32 0x4A000008 = 0xFFFFFFFF
monitor memU32 0x4A00001C = 0x0007FFFF

# 时钟：MPLLCON / CLKDIVN / LOCKTIME
monitor memU32 0x4C000000 = 0xFFFFFFFF
monitor memU32 0x4C000014 = 0x00000005
monitor memU32 0x4C000004 = 0x0005C011

# SDRAM 控制器 13 个寄存器（Bank6，两片 32MB 组成 64MB）
monitor memU32 0x48000000 = 0x22111110
monitor memU32 0x48000004 = 0x00000700
monitor memU32 0x48000008 = 0x00000700
monitor memU32 0x4800000C = 0x00000700
monitor memU32 0x48000010 = 0x00000700
monitor memU32 0x48000014 = 0x00000700
monitor memU32 0x48000018 = 0x00018005
monitor memU32 0x4800001C = 0x00018005
monitor memU32 0x48000020 = 0x008C07A3
monitor memU32 0x48000024 = 0x000000B1
monitor memU32 0x48000028 = 0x00000030
monitor memU32 0x4800002C = 0x00000030
monitor memU32 0x48000030 = 0x00000030

monitor speed auto
load
⚠这些数值是「某一块 Mini2440 的实测值」

SDRAM 那 13 个寄存器与板子上的颗粒型号、PCB 走线强相关。换一块板子照抄，SDRAM 可能根本起不来。正确做法是照 S3C2440 裸机：时钟、存储器与 NAND 里的寄存器含义自己算，或从该板 u-boot 的 lowlevel_init 里抄。

5.4 地址差异：NAND 启动与 NOR 启动 #

启动方式 0x00000000 是什么 代码该下到哪
NOR NOR 本体 0x00000000
NAND 片内 4KB SRAM（Steppingstone） 0x00000000（且程序必须 < 4KB）
从 SDRAM 调试 SDRAM 首址在 0x30000000 0x30000000，需要在 gdbinit 里先初始化 SDRAM

5.5 常用 GDB 命令 #

命令 作用
load 把 ELF 下到板子
info registers 看全部寄存器
x/16wx 0x30000000 看内存（16 个字，十六进制）
break main / b *0x30000100 按符号 / 按地址下断点
stepi / nexti 单步一条汇编
disassemble 反汇编当前函数
monitor reset 通过 JLink 复位 CPU

六、IDE 落地 #

6.1 Eclipse #

步骤 操作
1 装 JDK，设 JAVA_HOME / PATH / CLASSPATH
2 装 Eclipse（Indigo 之后的任意 C/C++ 版均可）
3 装嵌入式调试插件：Eclipse Embedded CDT（原 Zylin CDT 已停止维护，更新站点长期不可用）
4 建 C Project，Toolchain 选 Cross GCC
5 Properties → C/C++ Build → Settings → Tool Settings：gcc、as、ld 三个都要换成交叉版本（原文只改了 gcc 与 as，链接会失败）
6 Run → Debug Configurations：选 ELF 文件，Commands 里贴 5.3 那份 gdbinit
7 先用外部工具拉起 JLinkGDBServer，再点 Debug

中文乱码：Properties → Resource → Text file encoding 改成 GBK（老工程是 GB2312/GBK 编码）。

三个配置文件，缺一不可：

json
// .vscode/c_cpp_properties.json  —— 让 IntelliSense 认出头文件与编译器
{
  "configurations": [{
    "name": "Linux",
    "includePath": [
      "${workspaceFolder}/**",
      "${workspaceFolder}/include",

    ],
    "defines": [],
    "compilerPath": "/usr/local/arm/4.3.2/bin/arm-linux-gcc",

    "cppStandard": "gnu++14",

json
// .vscode/tasks.json  —— 让 Ctrl+Shift+B 能编
{
  "version": "2.0.0",
  "tasks": [{
    "label": "build",
    "type": "shell",
    "command": "make",
    "args": ["ARCH=arm", "CROSS_COMPILE=arm-linux-", "-j8"],
    "group": { "kind": "build", "isDefault": true },
    "problemMatcher": ["$gcc"]
  }]
}

json
// .vscode/launch.json  —— 连上 GDB Server
{
  "version": "0.2.0",
  "configurations": [{
    "name": "(gdb) 启动",
    "type": "cppdbg",
    "request": "launch",
    "program": "${workspaceFolder}/u-boot",
    "cwd": "${workspaceFolder}",
    "MIMode": "gdb",
    "miDebuggerPath": "/usr/local/gdb/bin/arm-linux-gdb",
    "miDebuggerServerAddress": "localhost:2331",
    "setupCommands": [
      { "text": "file ${workspaceFolder}/u-boot" },
      { "text": "source ${workspaceFolder}/u-boot.gdbinit" }
    ]
  }]
}
字段 说明
miDebuggerPath 交叉版 gdb 的绝对路径
miDebuggerServerAddress GDB Server 地址；本机就是 localhost:2331，远程则是 IP:端口（端口范围 1~65535）
program 带符号的 ELF，不是 bin
setupCommands 启动前执行的 gdb 命令，用来 source gdbinit
ℹ三处过时写法

① "targetArchitecture": "arm" 自 VS Code 1.5x 起已废弃，删掉；② ${workspaceRoot} 已更名 ${workspaceFolder}；③ "intelliSenseMode": "linux-gcc-x64" 在 ARM 交叉工程里是错的，应为 linux-gcc-arm，否则补全会按 x86 的 sizeof 推断。

七、踩坑速查 #

现象 原因 处置
No such file or directory 但文件明明在 64 位主机缺 32 位库，或 ELF 解释器路径不存在 装 lib32z1 / lib32ncurses6；用 file 确认架构
Illegal instruction -march 比 CPU 新 降 -march，用 readelf -A 核对
Exec format error 把 x86 程序拷到 ARM 板 用交叉工具链重编
undefined reference to __aeabi_* 链接时缺 libgcc 加 -lgcc，或把编译器自带的 libgcc.a 路径带上
section .text will not fit in region 链接脚本里的区域太小 改 MEMORY 或压代码
Unknown symbol in module 符号未导出，或版本不匹配 检查 EXPORT_SYMBOL 与 Module.symvers
version magic ... should be ... 模块与运行内核不同源 KERDIR 指向正在跑的那份内核树
GDB 连不上 2331 JLinkGDBServer 没起，或被防火墙拦 先起服务器，telnet localhost 2331 试探
GDB 停不下来 / 一跑就飞 gdbinit 里的时钟、SDRAM 参数与本板不符 从本板 u-boot 的 lowlevel_init 抄参数
