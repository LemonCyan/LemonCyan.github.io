一、动手之前：硬件取证 #

驱动写错的绝大多数原因不是代码，而是引脚与地址搞错了。一条实用的取证顺序：

外围板丝印/原理图  →  核心板排针定义  →  SoC 数据手册  →  内核 dts/dtsi
   ↑ 网卡接哪个座       ↑ 座连到哪个引脚     ↑ 引脚复用与寄存器    ↑ 已有定义可反查

以 Exynos4412 板上的 DM9000 为例，每一步能得到什么：

步骤 得到的信息
外围板原理图 网卡挂 Xm0cs1 → 对应 SROM Bank1 → 基址 0x05000000
核心板引脚表 中断线接 GPX0_6，即外部中断 EINT6
内核 arch/arm/boot/dts/exynos4x12-pinctrl.dtsi gpx0 的 #interrupt-cells = <2>，中断号就是第 6 个
Documentation/devicetree/bindings/arm/gic.txt 触发类型四个合法值：1 上升沿、2 下降沿、4 高电平、8 低电平
✦触发类型先查 GIC 文档，别靠猜

电平与边沿选错，现象是「中断只来一次」或「一直进中断不出来」。上面那四个值是 ARM 平台通用编码，S3C2440、Exynos、ARM64 都适用。

二、把驱动接进内核的四种方式 #

移植期最常用的一张表，选错会导致「编了但没进镜像」或「进了但加载不了」。

方式 改哪里 产物 适用
① 直接编进 子目录 Makefile 加 obj-y += xxx.o built-in.o 临时验证，不过问配置
② Kconfig + 编进 Kconfig 加 bool 项，Makefile 加 obj-$(CONFIG_XXX) += xxx.o，menuconfig 选 * 同上 正式做法，可裁剪
③ Kconfig + 模块 同上但用 tristate，menuconfig 选 M xxx.ko 调试期，改一次编一次
④ 树外模块 自己写一个 obj-m 的 Makefile xxx.ko 不想污染内核树，或厂商只给了 tar 包

方式 ② 的两处改动（以 FS4412 的 LED 为例）：

# drivers/char/Kconfig
config FS4412_LED
    bool "FS4412 led device support"
    default n
    help
      support led device for FS4412 board

# drivers/char/Makefile
obj-$(CONFIG_FS4412_LED) += fs4412_led_drv.o

方式 ④ 的树外 Makefile（老内核用 KDIR，新内核惯例写 KERNELDIR 或 KERNEL_SRC）：

makefile
MODNAME = fs4412_led_drv
KERDIR  = /home/linux/system/test-kernel/linux-3.14/

all:
	$(MAKE) -C $(KERDIR) M=$(shell pwd) modules
clean:
	rm -rf *.ko *.o *.mod* *.symvers *.order

obj-m = $(MODNAME).o

板端加载与建节点：

bash
insmod fs4412_led_drv.ko
cat /proc/devices            # 查驱动实际拿到的主设备号，别硬编码
mknod /dev/led c 500 0       # c = 字符设备, 500 主设备号, 0 次设备号
rmmod fs4412_led_drv
⚠主设备号不要写死 500

原文直接写 mknod /dev/led c 500 0，但 500 是哪来的没说。正解是驱动里 register_chrdev_region 拿到什么号，板端 cat /proc/devices 就查什么号；用 alloc_chrdev_region 时号还是动态分配的，更必须查。

三、设备树侧：驱动能拿到什么 #

（语法细节见 设备树基础与语法，这里只列移植时最常写错的四件事。）

3.1 reg 与 #address-cells/#size-cells 必须对得上 #

父节点说地址用 1 个 cell、长度用 1 个 cell，子节点 reg 就必须是「地址 长度」成对出现。ARM64 上常见父节点 #address-cells = <2>; #size-cells = <2>;，reg 就要写 4 个数。写错不报错，只是 of_address_to_resource 拿到错的地址，表现为「ioremap 成功但读写全是 0」。

3.2 interrupt-parent 的继承链 #

子节点自己有 interrupt-parent 就用自己；没有就一级级往父节点找。ARM64 移植 ARM generic timer 时踩过的坑就是这条链断了：

arch_timer: No interrupt available, giving up
clocksource_probe: no matching clocksources found
Kernel panic - not syncing: Unable to initialise architected timer.

节点本身 compatible、clock-frequency 都对，只是根节点忘了 interrupt-parent = <&gic>;。看到「No interrupt available」先查父链，别去改 interrupts 里的数字。

3.3 一个完整的 timer 节点 #

dts
#include <dt-bindings/interrupt-controller/arm-gic.h>

/ {
    model = "Bubblegum-96 Development Board";
    compatible = "actions,s900-bubblegum", "actions,s900";
    interrupt-parent = <&gic>;
    #address-cells = <2>;
    #size-cells = <2>;

    timer {
        compatible = "arm,armv8-timer";
        interrupts = <GIC_PPI 13 IRQ_TYPE_LEVEL_LOW>,
                     <GIC_PPI 14 IRQ_TYPE_LEVEL_LOW>,
                     <GIC_PPI 11 IRQ_TYPE_LEVEL_LOW>,
                     <GIC_PPI 10 IRQ_TYPE_LEVEL_LOW>;
        clock-frequency = <24000000>;
    };
};

四个中断分别是 Non-secure PL1 physical（PPI 13）、Secure PL1 physical（PPI 14）、Non-secure PL2 physical（PPI 11）、virtual（PPI 10），全部低电平触发。24000000 来自板载 24MHz 晶振。

3.4 没有原理图时，用开源 dtsi 反推 #

去同 SoC 开源板子的 dtsi 里找同外设节点，比对 clock-frequency、中断号、reg 长度，是效率最高的取证方式。原文用这套办法反推出 24MHz 与四个 PPI，之后 u-boot 侧只需加一行 #define COUNTER_FREQUENCY (24000000)。

四、早期调试：串口还没通时怎么办 #

这是驱动移植里最硬的一段功夫。板子上电、串口一片黑，既没有 printk 也没有调试器，唯一可用的输出是一个 GPIO 上的 LED。

4.1 点灯二分法 #

原理：在可疑路径上插「点灯/灭灯」，用亮灭判断执行到哪一步。GPIO 的输出使能与数据寄存器都可以用 early_ioremap 在 MMU 打开前访问。

c
static void __iomem *gpioa_outen, *gpioa_outdat;

void led_on(void)
{
    writel(0xffffffff, gpioa_outen);   /* 全设成输出 */
    writel(0xffffffff, gpioa_outdat);  /* 全拉高 */
}

在 param_setup_earlycon → setup_earlycon → earlycon_owl_setup → earlycon_owl_write 这条链的每一级插一次点灯，就能定位卡在哪一级。原文用这个办法最终查出三个独立的坑：

坑 现象 修法
漏 select SERIAL_EARLYCON 驱动编进去了，但 earlycon.o 没链进来，earlycon=owl_serial 完全没反应 Kconfig 里给 SERIAL_OWL 补 select SERIAL_EARLYCON
漏 CONFIG_PRINTK 早期控制台注册成功，但没有任何输出 General setup → Enable support for printk
owl_serial_putc 把 while 写成 if 只出第一个字符，后面全丢 改回 while 轮询 TX FIFO 满标志

4.2 early console 的注册方式 #

ARM64 走 earlycon（不是 earlyprintk）。驱动侧注册一行：

c
EARLYCON_DECLARE(owl_serial, earlycon_owl_setup);

setup 里用 early_ioremap 映射 UART 寄存器（此时 MMU 还没建好正常映射，ioremap 不可用），再挂 write 回调；write 交给通用轮询函数：

c
static void earlycon_owl_write(struct console *con, const char *s, unsigned int n)
{
    uart_console_write(NULL, s, n, owl_serial_putc);
}

static void owl_serial_putc(struct uart_port *port, int ch)
{
    while (readl(uart5_base + UART_STAT) & UART_STAT_TFFU)
        ;                                  /* TX FIFO 满则等 */
    writel(ch, uart5_base + UART_TXDAT);
}

命令行写 earlycon=owl_serial，也可以 earlycon=owl_serial,0xe01b0000 显式给基址。成功标志是这两行：

earlycon: owl_serial0 at I/O port 0x0 (options '')
bootconsole [owl_serial0] enabled
⚠`early_ioremap(base, 4)` 只映射 4 字节，但你要访问多个寄存器

原文就是这么写的，能跑通是因为同一页内的地址恰好被覆盖。正确做法是按实际需要映射（例如 early_ioremap(base, 0x100)），否则一旦寄存器跨越页边界就会踩到未映射地址。

4.3 三个必备开关 #

开关 菜单 作用
CONFIG_PRINTK General setup → Enable support for printk 没有它 printk 是空函数
CONFIG_TTY Device Drivers → Character devices → Enable TTY 没有它 console 注册不上
CONFIG_SECTION_MISMATCH_WARN_ONLY Kernel hacking → Compile-time checks → Make section mismatch errors non-fatal 早期驱动把 __init 函数放错段时，modpost 会以 FATAL 拦下编译

五、三个真实案例 #

5.1 案例一：ARM64 新平台的内核最小闭环（Bubblegum-96 / Actions S900） #

步 动作 关键点
1 make ARCH=arm64 menuconfig，剪掉 Networking / Device Drivers / Firmware / File systems / Virtualization / Security / Crypto / Library routines 先做减法，能起再说
2 cp .config arch/arm64/configs/bubblegum_defconfig 存基线
3 arch/arm64/Kconfig.platforms 加 config ARCH_OWL（bool "Actions OWL 64-bit SoC Family"） 没有它 ARCH_OWL 选项根本不出现
4 建 arch/arm64/boot/dts/actions/，放 s900-bubblegum.dts 与 Makefile（dtb-$(CONFIG_ARCH_OWL) += s900-bubblegum.dtb） 上级 Makefile 登记（4.x 是 dts-dirs += actions，5.x 并入 dtb-y）
5 make ARCH=arm64 Image dtbs 产物 arch/arm64/boot/Image（约 4.5MB）与 Image.gz（约 2.0MB）
ℹARM64 只接受设备树，没有 ATAGS 这条路

流传的说法「u-boot 要么用 atags，要么用 device tree」只对 ARM32 成立。ARM64 内核从不支持 ATAGS，u-boot 不给 dtb 就直接罢工。

加载地址的坑：ARM64 内核的链接地址由 CONFIG_ARM64_VA_BITS 决定（39 → 0xffffffc000000000），启动早期 MMU 未开、代码位置无关，靠 adr_l 换算物理地址。但页表要从物理 0x0 开始占 TEXT_OFFSET（0x80000），所以 DRAM 从 0 起时要先把 Image 拷到 0x80000。

5.2 案例二：厂商 tar 包驱动（USB WiFi） #

厂商驱动不走内核 Kconfig，自成一套构建系统。以 Ralink RT2870/RT3070 系列为例，改两个文件即可：

# 顶层 Makefile
PLATFORM      = RALINK_2880            # 原为 PC
LINUX_SRC     = /home/xxx/kernel_kfb   # 你的内核源码
CROSS_COMPILE = /opt/freescale/.../bin/arm-none-linux-gnueabi-

# os/linux/config.mk
HAS_WPA_SUPPLICANT = y
CC := .../arm-none-linux-gnueabi-gcc
LD := .../arm-none-linux-gnueabi-ld
EXTRA_CFLAGS := -D__KERNEL__ -I$(LINUX_SRC)/include ... -march=armv5te

两个必踩的报错：

报错 原因 修法
*** CFLAGS was changed in ".../os/linux/Makefile". Fix it to use EXTRA_CFLAGS. 直接改了 CFLAGS，新版 kbuild 禁止 改 EXTRA_CFLAGS
Error: selected processor does not support 'pld [r5,#0]' -march 太低，pld 是 ARMv5TE 之后才有的预取指令 抬到 armv5te 以上，或干脆用内核同款 -march

流程：make → 得到 rt3070sta.ko → 拷 RT2870STA.dat 到 /etc/Wireless/RT2870STA/ → insmod → ifconfig ra0 192.168.1.5 → iwlist ra0 scanning → wpa_supplicant -Dwext -ira0 -c /etc/wpa_supplicant.conf -dd & → ping。

⚠这条路线在现代内核上基本走不通

2.6.31 内核 + wext + wireless_tools + 厂商 tar 包，是 2011 年的组合。现代内核走 cfg80211/mac80211 + nl80211，主线的 rt2800usb 已支持同一族芯片。厂商包只在你必须用它的私有特性时才有意义，否则直接开 CONFIG_RT2800USB。

5.3 案例三：CAN 收 500k 导致某核满载 #

现象：RK3568 板子 CAN 总线 500kbps 收包时，总是最后一颗核跑满，拔掉总线立刻恢复。

正确的排查顺序：

  1. cat /proc/interrupts 看该 CAN 中断落在哪颗核、每秒多少次；
  2. 看驱动里有没有做中断亲和设置；
  3. 看 NAPI 是否启用、quota 是多少；
  4. 用 ethtool -S can0 或 perf top 确认热点。

第 2 步就能直接命中原因。驱动里有这么一行：

c
irq_set_affinity_hint(irq, get_cpu_mask(num_online_cpus() - 1));

它把 CAN 中断钉死在最后一颗核（4 核机器即 CPU3）。于是无论 NAPI 还是硬中断，负载都只落在一颗核上——这才是「总是某颗核满载」的直接原因。

原文的处理办法是把 NAPI 全部注掉（netif_napi_add、napi_enable、napi_disable、netif_napi_del），改由硬中断里按 FIFO 计数循环收包。

⚠这是规避，不是修复

NAPI 的设计目的正是降低高包量下的中断风暴，「NAPI 导致 CPU 过载」这个论断与它的设计相反。把 NAPI 注掉后每个报文都进一次硬中断，看似「不在 poll 里空转」，实际是把成本从 poll 挪回中断。真正该做的是：① 去掉或改写亲和性绑核；② 提高 netif_napi_add 的 quota（原文写死 6，太小）；③ 用线程化中断把下半部挪到进程上下文。

相关寄存器速查（rockchip_canfd.c，compatible 为 rockchip,canfd-1.0 / rockchip,rk3568-can-2.0）：

寄存器 偏移 说明
CAN_MODE 0x00 RESET_MODE 0 / WORK_MODE BIT(0)
CAN_INT 0x0c RX_FINISH_INT BIT(0)、TX_FINISH_INT BIT(1)、RX_FIFO_FULL_INT BIT(7)、BUS_OFF_INT BIT(9)
CAN_INT_MASK 0x10 中断屏蔽
CAN_NBTP 0x100 位时序，`NSJW<<24
CAN_RXFC 0x118 接收 FIFO 计数
CAN_RXFRD(n) 0x400 + 0x48*n 接收 FIFO 数据

六、板级外设与烧写（S3C2440 侧） #

ARM9 板的移植还有一块「板子本身怎么用」的内容，驱动调试全程都依赖它。

6.1 地址空间 #

片选 起始地址 常见用途
nGCS0 0x00000000 NOR 启动时是 NOR 本体；NAND 启动时是片内 4KB SRAM（Steppingstone）
nGCS1 0x08000000 扩展
nGCS2 0x10000000 扩展
nGCS3 0x18000000 扩展
nGCS4 0x20000000 DM9000 常挂这
nGCS5 0x28000000 扩展
nGCS6/7 0x30000000 起 SDRAM（只有 6/7 支持）

Steppingstone 那 4KB 是理解 Mini2440 的关键：NAND 启动时硬件把 NAND 前 4KB 自动拷到片内 SRAM 并映射到 0 地址，CPU 从那开始跑。所以裸机程序小于 4KB 时可以直接跑在片内，超过就必须自己搬进 SDRAM（见 S3C2440 裸机：时钟、存储器与 NAND）。

6.2 三种烧写通道 #

通道 工具 说明
JTAG JLink / OpenJTAG 能断点、能读内存，救砖首选，但慢
USB DNW（三星）、MiniTools 走芯片自带 USB 下载协议，需要板子在特定启动模式
网络 tftp + u-boot 只有 u-boot 已经能跑时才可用

MiniTools 的前提是板子上跑着 Superboot/SuperVivi 一类出厂引导程序，它提供 USB 下载服务，把 u-boot、内核、rootfs 都通过它写进 NAND。这是「一键烧写」的本质。

七、移植后的验收清单 #

检查项 命令 通过标准
内核起来了 串口 看到 Booting Linux on physical CPU 0x0
时钟对了 dmesg 里 grep clk 无 could not find clock 一类告警
定时器在走 日志时间戳 有 [ 0.093281] 形式的时间，且两次启动一致
存储识别 cat /proc/mtd / ls /dev/mmcblk* 分区表与设计一致
网卡 probe dmesg 里 grep eth / ifconfig -a 有 MAC，无 -EPROBE_DEFER 死循环
中断分配正常 cat /proc/interrupts 目标外设的中断计数在涨，且没全落在一颗核
引脚复用对 逻辑分析仪 / 示波器 波形频率与占空比符合预期
模块可加载 insmod / lsmod / rmmod 无 Unknown symbol、无 version magic 不匹配
✦`version magic` 不匹配是跨内核版本的经典错误

报 insmod: ERROR: could not insert module xxx.ko: Invalid module format，dmesg 里会写 version magic '3.14.0 SMP ...' should be '5.2.8 SMP ...''。说明编模块时用的内核树与板子上跑的不是同一份——检查 KERDIR 指向。

八、踩坑速查 #

现象 优先怀疑
probe 函数根本没被调用 dts 的 compatible 与驱动 of_match_table 不一致；或节点 status = "disabled"
probe 反复重试（-EPROBE_DEFER） 依赖的 provider（时钟/pinctrl/regulator）还没注册，查 probe 顺序
ioremap 成功但读到全 0 reg 与父节点 #address-cells/#size-cells 不匹配，地址被切错
中断只来一次 没清中断标志；或触发类型设成边沿但硬件是电平
一直进中断出不来 电平触发但源没清；漏 EOI
串口能收不能发 只开了 RXD 没开 TXD（S3C2440 上两路必须同时使能）
早期控制台无输出 漏 CONFIG_PRINTK 或 select SERIAL_EARLYCON
模块加载报 Unknown symbol 依赖的符号没 EXPORT_SYMBOL，或加载顺序错
编译报 section mismatch __init 函数被非 __init 代码调用，改段或加 __ref
