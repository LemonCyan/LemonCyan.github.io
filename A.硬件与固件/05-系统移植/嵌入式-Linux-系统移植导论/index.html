一、嵌入式 Linux 是什么，边界在哪 #

1.1 一个够用的定义 #

以应用为中心、以计算机技术为基础、软硬件可裁剪、对功能/可靠性/成本/体积/功耗有严格要求的专用计算机系统。这个定义里真正决定工程行为的只有两个字：裁剪。裁剪意味着「同一份源码，配置不同就是两个产品」。

1.2 四层结构 #

┌─────────────────────────────────────────┐
│ 应用软件层   Qt / 业务程序 / 守护进程        │
├─────────────────────────────────────────┤
│ 系统软件层   内核 + C 库 + 根文件系统工具链   │
├─────────────────────────────────────────┤
│ 中间层       HAL / BSP（板级支持包）        │
├─────────────────────────────────────────┤
│ 硬件层       SoC + DDR + Flash + 外设      │
└─────────────────────────────────────────┘
ℹHAL 与 BSP 是同一层的两个叫法

老教材把中间层分成 HAL（硬件抽象层）与 BSP（板级支持包）两块，实际工程里它们是同一件事：把「这块板子的差异」隔离出来。Linux 里这一层就是 arch/arm/mach-xxx/ 与 arch/arm/boot/dts/。

1.3 内核的五大职责 #

职责 对应子系统 移植时是否常动
进程管理（创建/调度/销毁） kernel/sched/ 不动
内存管理（分配/映射/回收） mm/ + arch/*/mm/ 常动页表初始化
文件系统（VFS 抽象 + 具体实现） fs/ 选型要动配置
设备控制（驱动） drivers/ 主要工作量
网络控制（协议栈） net/ 一般不动

1.4 有 OS 与无 OS 的启动链对照 #

无 OS（裸机） 有 OS（Linux）
上电 CPU 从复位向量取指 同左
第一段代码 片内 ROM 或你写的 start.S 片内 BootROM（iROM/BL0）
中间阶段 无 BL1 → BL2 → u-boot
谁来初始化 DRAM 你的 start.S u-boot 的 lowlevel_init
谁把内核搬进 DDR 无 u-boot 的 bootm / tftp
最后一步 直接跑 main 挂根文件系统 → 跑 /sbin/init

这张表解释了一个高频疑问：为什么必须先有 Bootloader？ CPU 上电时只能访问片内 SRAM（S3C2440 是 4KB，S5PC100 是 96KB），而 DRAM 的时序参数必须先由软件写进存储控制器，DRAM 才「存在」。SRAM 放不下内核，所以必须有一个小程序先去把 DRAM 叫醒。

二、移植到底在移什么 #

2.1 两种「四步」说法，其实是同一件事 #

视角 四步 语境
移植视角（工程顺序） ① 搭交叉开发环境 → ② Bootloader 选择与移植 → ③ 内核配置编译移植 → ④ 根文件系统 手上已有板子，要把 Linux 跑起来
构建视角（产物顺序） ① 裁剪编译内核 → ② 构建 rootfs → ③ 制作烧写映像 → ④ 安装引导程序 教科书讲「系统由哪几部分组成」

两者是同一流程的两种切分：构建视角的 ④ 就是移植视角的 ②，只是叙述顺序倒了。实际干活按移植视角，因为省略不了「先有能启动的 bootloader」这一步。

2.2 四种典型场景，工作量差十倍 #

场景 要改的东西 工作量
换板子、同 SoC 只改 dts（引脚、外设、分区）与板级宏里的晶振/内存参数 半天~两天
换 SoC、同架构 新增 arch/arm/mach-xxx/、dts、时钟与 pinctrl 驱动 一周~数月
纯裁剪（板子不变，压体积/加快启动） 只改 .config 与 rootfs 内容 一两天
升级内核大版本 板级代码按新框架重写（ATAGS→DT、平台化） 取决于落后多少代

2.3 开发模式与产品模式 #

老教材讲「开发模式 vs 产品模式」，实质是启动介质的两种用法：

开发模式 产品模式
内核/rootfs 从哪来 TFTP + NFS，每次上电从主机拉 存在本地 eMMC/NAND，开机自读
改代码后要做什么 重编 → 拷到主机 TFTP 目录 → 板子重启 重编 → 烧写 → 板子重启
好处 秒级迭代，不用反复烧写 稳定、可量产、不依赖网络
坏处 依赖网络与主机，产品不能这么做 迭代慢

正常节奏是：全程用开发模式，功能冻结后再切产品模式。切换动作见 根文件系统的移植与调试。

三、交叉开发环境 #

3.1 为什么必须交叉编译 #

目标板是 ARM，主机的 gcc 产出 x86 机器码，两者指令集不通。所谓交叉工具链，就是「跑在 x86 上、产出 ARM 代码」的编译器。它内部自带一套 libc 与 binutils，与主机系统里装的东西完全无关——这也是为什么工具链必须整包下载、解压即用，而不是 apt install 一个就完事。

3.2 GCC 的四阶段 #

阶段 工具 输入 → 输出 常用选项
预处理 cpp .c → .i -E、-D、-I
编译 cc1 .i → .s -S、-O0~-O3、-g、-march
汇编 as .s → .o -c
链接 ld .o + 库 → elf -T（链接脚本）、-L、-l、-static

把四步串起来的就是 arm-none-linux-gnueabi-gcc 一个命令，它在前三步调子程序、最后统一交给 ld。想看清它到底调了什么，加 -v。

3.3 binutils 八件套 #

工具 作用 常用示例
readelf 读 ELF 结构 arm-linux-readelf -A hello → 看 Tag_CPU_arch: v5TE 验证 -march
size 看段大小 arm-linux-size vmlinux → text/data/bss
nm 列符号与地址 arm-linux-nm -A vmlinux → 找函数地址
strip 去符号 arm-linux-strip xxx → 缩体积
objcopy 格式转换 arm-linux-objcopy -O binary -S vmlinux Image
objdump 反汇编 arm-linux-objdump -D u-boot > u-boot.dis
addr2line 地址→源码行 arm-linux-addr2line -e vmlinux -f 0xc00xxxxx
strings 提取可打印串 arm-linux-strings xxx.ko

3.4 工具链安装与验证 #

bash
sudo mkdir -p /usr/local/arm
sudo tar xf arm-2010.09-50-arm-none-linux-gnueabi-i686-pc-linux-gnu.tar.bz2 -C /usr/local/arm/
echo 'export PATH=/usr/local/arm/arm-2010.09/bin:$PATH' >> ~/.bashrc
source ~/.bashrc
arm-none-linux-gnueabi-gcc -v    # 必须看到交叉编译器版本，而不是本机 gcc
⚠三处常见「验证方法错误」
  1. 敲 gcc -v 验证——验证的是主机 gcc，永远成功，什么也没证明；
  2. 报 -bash: .../arm-linux-gcc: No such file or directory 就以为没装上——文件其实在，是 64 位主机缺 32 位库（lib32ncurses5 / lib32z1）；
  3. 装完只开了当前终端，新开终端又找不到——写进了只在登录时读的文件，或忘了 source。

3.5 主机侧必备服务 #

服务 用途 关键配置
ssh 远程登录主机 默认 22
tftp-hpa 让板子 tftp 下内核与 dtb /etc/default/tftpd-hpa：TFTP_DIRECTORY="/tftpboot"、TFTP_OPTIONS="-c -s -l"、端口 69
nfs-kernel-server 让板子挂根文件系统 /etc/exports 加 /nfsroot/rootfs 192.168.1.0/24(rw,sync,no_root_squash)
samba 主机与 Windows 共享源码 /etc/samba/smb.conf

三个 tftp 选项的含义：-c 允许客户端上传新建文件；-s 指定服务根目录；-l 以独立守护进程方式监听（而不是由 inetd 拉起）。

✦NFS 导出根文件系统时 `no_root_squash` 不是可选项

板上的 init 以 root 身份运行，会往 rootfs 写文件。默认的 root_squash 把 root 映射成 nobody，于是开机报满屏 Permission denied。

3.6 网络规划：先定一套地址 #

素材里出现过三套网段（192.168.1.x / 192.168.9.x / 192.168.0.x），互相冲突。建议固定一套：

角色 地址示例
主机（Ubuntu） 192.168.1.111/24，网关 192.168.1.1
板子 192.168.1.233/24
u-boot 里的 ipaddr / serverip 192.168.1.233 / 192.168.1.111 
bash
setenv ipaddr    192.168.1.233
setenv serverip  192.168.1.111
setenv netmask   255.255.255.0
setenv gatewayip 192.168.1.1
saveenv

四、Bootloader：为什么是 U-Boot #

4.1 它到底干了什么 #

stage1（汇编，位置相关，跑在 SRAM/Flash 里）
  ├ 关看门狗、关中断
  ├ 设置 CPU 时钟与分频
  ├ 初始化存储控制器（把 DRAM 叫醒）
  ├ 把自己从 Flash 搬到 DRAM 高端
  └ 建栈、跳到 stage2

stage2（C 语言，跑在 DRAM 里）
  ├ 初始化串口、网卡、NAND、LCD 等外设
  ├ 进入命令行（或倒计时后自动执行 bootcmd）
  ├ 提供 tftp / nand / mmc / fatload 等加载能力
  └ 引导内核：bootm / bootz（+ dtb）

4.2 三星平台的四阶段启动 #

阶段 在哪跑 干什么
BL0（iROM） 片内 ROM，出厂固化 关看门狗、关中断与 MMU、设时钟、检测 OM 引脚决定从哪启动、把 BL1 搬到片内 SRAM
BL1 片内 SRAM 初始化运行环境，搬 BL2
BL2 片内 SRAM 基本硬件初始化（含 DRAM），搬 u-boot.bin
u-boot.bin DRAM 完整功能，引导内核

这里有个工程约束：u-boot.bin 是被 BL1/BL2 打包的，换 u-boot 必须用厂商工具重新生成 u-boot.bin（或直接把 u-boot 与 BL1/BL2 合并），不能只替换二进制。

4.3 启动介质与拨码开关 #

平台 开关 启动介质
FS4412 SW1=(1000) SD 卡
FS4412 SW1=(0110) eMMC
Mini2440 OM0/OM1 NAND（0 地址映射到片内 4KB SRAM）/ NOR（0 地址是 NOR 本体）

Mini2440 这两种启动方式对地址空间的影响，决定了 u-boot 里「向 0 地址写值再读回」的判断逻辑——详见 S3C2440 裸机：时钟、存储器与 NAND。

4.4 常用命令与环境变量 #

命令 用途
printenv / setenv / saveenv 看/改/存环境变量
tftp <addr> <file> 从 serverip 下载
nand erase / nand write / nand read NAND 擦写读
mmc write / fatload SD/eMMC 操作
bootm / bootz / go 引导内核（见下表）
md / mw 读/写内存
内核格式 正确命令 常见错误
uImage（有 64 字节头） bootm 0x41000000 用 go 会跳过头部解析
zImage（自解压） bootz 0x20008000 用 bootm 会报 Bad Magic Number
带设备树 bootm 0x41000000 - 0x42000000 忘写中间那个 -

4.5 移植一个 u-boot 的十步骨架 #

  1. 拿到与 SoC 同族的官方 u-boot（三星平台是厂商定制版，不是上游）；
  2. 加板级目录 board/<vendor>/<board>/ 与配置头 include/configs/<board>.h；
  3. 在 boards.cfg（老版本）或 configs/<board>_defconfig（新版本）里登记；
  4. make <board>_config 生成配置（新版是 make <board>_defconfig）；
  5. 改 lowlevel_init 里的时钟与 DRAM 参数；
  6. 打开串口输出，先让它能打出一行字；
  7. 加 NAND/MMC 驱动，让它能读到内核；
  8. 加网卡驱动，让它能从 tftp 取内核；
  9. 配 bootcmd 与 bootargs；
  10. saveenv，断电重启验证。
⚠`boards.cfg` 与 `make xxx_config` 是 2014.10 之前的老机制

现代 U-Boot 全面 Kconfig 化：configs/<board>_defconfig + make <board>_defconfig。看到老教程写 make origen_config 时，先确认手里的 u-boot 版本，否则会得到 *** No rule to make target。

五、内核与根文件系统：两句就到 #

内核侧是「配置 → 编译 → 板级适配」，根文件系统侧是「造骨架 → 塞 busybox → 打包 → 挂载验证」。这两块各有专文，这里只给与总纲有关的衔接点：

衔接点 说明
bootargs 里的 root= 决定挂哪个根：/dev/mtdblock3（NAND）、/dev/mmcblk0p2（eMMC）、/dev/nfs（网络）
init= busybox 体系里通常是 /linuxrc 或 /sbin/init
设备节点 静态 /dev 还是 devtmpfs 动态生成，影响「根挂上了但找不到 console」这类问题
分区一致性 u-boot 的 mtdparts、内核的 smdk_default_nand_part[]、rootfs 里的 /etc/fstab 三处必须对齐

六、调试与传输基础设施 #

6.1 串口是唯一的生命线 #

参数：115200 8N1，无流控（no hardware flow control）
工具：Windows 用 putty / SecureCRT，Linux 用 minicom / picocom

上电第一件事不是看能不能进系统，而是看串口有没有字。有字说明时钟、DRAM、串口这三件事都对；没字则后面所有步骤都不用谈。

6.2 网络三件套的排错顺序 #

现象 先查什么
tftp 超时 板子能不能 ping 通主机（先解决网络，再谈 tftp）
tftp 能下但报 File not found TFTP_DIRECTORY 与文件实际位置，以及权限
NFS 挂载卡住 主机 showmount -e 是否导出、防火墙、no_root_squash
NFS 挂上但开机 Permission denied no_root_squash 没写
ping 不通 网段、掩码、serverip 是否同网段；板子与主机是否接在同一交换机

6.3 gdbserver 远程调试 #

bash
# 板端（默认端口 2345，可自定义）
gdbserver 192.168.1.111:2345 ./hello
# 主机端
arm-none-linux-gnueabi-gdb ./hello
(gdb) target extended-remote 192.168.1.233:2345

八、一页流程 #

① 工具链      解压 → PATH → arm-none-linux-gnueabi-gcc -v 验证
② 主机服务    tftp(/tftpboot) + nfs(/nfsroot/rootfs,no_root_squash) + 串口
③ 网络        板子与主机同网段，u-boot 里 setenv ipaddr/serverip + saveenv
④ Bootloader  能出串口 → 能 tftp → 能 nand write → 能 bootm
⑤ 内核        改 ARCH/CROSS_COMPILE → defconfig → menuconfig → make uImage dtbs
⑥ 设备树      引脚/外设/分区，dtb 放在不打架的地址
⑦ rootfs      busybox 骨架 → inittab/fstab → 打包 ext4/yaffs2 → NFS 先跑通
⑧ 固化        切 eMMC/NAND 启动 → 分区对齐 → 量产工具烧写
