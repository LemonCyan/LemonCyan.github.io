一、先选型，再动手 #

1.1 六个工具各管一段 #

工具 层次 管什么 不管什么
Make 构建引擎 依赖关系与命令执行 不跨平台、不管理依赖包
CMake 跨平台构建生成器 生成 Makefile/Ninja，管编译选项与查找库 不管系统级依赖（rootfs、内核）
Meson 新一代构建生成器 比 CMake 快、语法更干净 同上，生态仍偏新
QMake Qt 专用 Qt 工程的构建 Qt 6 起官方主推 CMake，qmake 仅兼容保留
Buildroot 系统级 工具链 + 内核 + bootloader + rootfs 一站式 无包管理、不处理运行时升级、无 license 审计
Yocto 系统级 同上，额外有 layer 复用、license 清单、SDK 导出、增量构建 学习曲线陡，首次构建数小时

1.2 一句话判据 #

你的情况 选
单一产品、镜像要小、想半小时内看到结果 Buildroot
多条产品线共享 BSP、要交付 SDK 给第三方、需要 license 合规报告 Yocto
只要一个能跑的 rootfs 做验证 手工 busybox（见 根文件系统的制作）
只编内核 直接 make，不需要系统级构建系统

规模感：Buildroot 全量构建 15~30 分钟；Yocto 首次数小时，之后靠 sstate 缓存加速到十几分钟。

二、Buildroot 上手 #

2.1 目录结构 #

目录 内容
board/ 板级配置：<vendor>/<board>/ 下有 defconfig、rootfs overlay、post-build 脚本
configs/ 各板 defconfig，如 rockchip_rk3568_defconfig
package/ 上千个包的 .mk 与 Config.in
toolchain/ 工具链构建逻辑（自建或外部）
linux/、boot/、system/ 内核、bootloader、rootfs 骨架的构建规则
output/ 构建产物（build/ host/ images/ staging/ target/）

2.2 一次完整构建 #

bash
# 1) 导入板级配置（生成 output/<board>/.config）
make rockchip_rk3568_defconfig

# 2) 按需改配置
make menuconfig

# 3) 全量构建
make -j8

ls output/images/          # Image / rootfs.ext4 / sdcard.img 等

瑞芯微 SDK 多一层 envsetup 包装，效果等价：

bash
source envsetup.sh rockchip_rk3568     # 生成 output/rockchip_rk3568
make menuconfig && make

output/ 下五个子目录：

子目录 内容
build/ 每个包的解压与编译目录（<pkg>-<version>/）
host/ 在主机上运行的工具（含交叉工具链本身）
staging/ 交叉编译用的 sysroot（头文件 + 库）
target/ 最终 rootfs 的目录树（打包前）
images/ 最终产物

2.3 单包操作：比全量重编快一百倍 #

命令 作用
make <pkg> 构建并安装该包
make <pkg>-rebuild 只重编，不重新解压
make <pkg>-reconfigure 重新跑 configure 再编
make <pkg>-dirclean 删掉该包的 build 目录
make <pkg>-source / -extract / -patch 分步执行
make busybox-menuconfig 单独配 busybox
make busybox-update-config 把当前 busybox 配置存回 board 目录
make linux-menuconfig / make uboot-menuconfig 单独配内核 / u-boot
make graph-depends 生成依赖图（需要 graphviz）
✦改了包源码却不生效？先分清「改了 build 目录」还是「改了外部源码」

Buildroot 用 .stamp_* 文件记录每步是否完成。直接改 output/build/<pkg>/ 里的文件，重跑 make 会被覆盖回去或干脆不重编。要试一把必须 make <pkg>-rebuild；要永久生效，走 OVERRIDE_SRCDIR 或自己的 br2-external 包。

2.4 加一个自己的包 #

最小骨架：

package/firefly_demo/
├── Config.in          # 菜单项定义
├── firefly_demo.mk    # 构建规则
└── src/               # 源码（也可由 SITE 下载）

package/Config.in      # 顶层要 source 这一行，否则菜单里看不见
source "package/firefly_demo/Config.in"

# package/firefly_demo/Config.in
config BR2_PACKAGE_FIREFLY_DEMO
    bool "firefly_demo"
    help
      A demo application for Firefly boards.

# package/firefly_demo/firefly_demo.mk
FIREFLY_DEMO_VERSION = 1.0
FIREFLY_DEMO_SITE = $(TOPDIR)/package/firefly_demo/src
FIREFLY_DEMO_SITE_METHOD = local
FIREFLY_DEMO_INSTALL_TARGET = YES

define FIREFLY_DEMO_BUILD_CMDS
    $(TARGET_MAKE_ENV) $(MAKE) -C $(@D) CC="$(TARGET_CC)" CFLAGS="$(TARGET_CFLAGS)"
endef

define FIREFLY_DEMO_INSTALL_TARGET_CMDS
    $(INSTALL) -D -m 0755 $(@D)/firefly_demo $(TARGET_DIR)/usr/bin/firefly_demo
endef

$(eval $(generic-package))

几个关键变量：$(TARGET_CC) 是交叉编译器绝对路径，$(@D) 是该包解压目录，$(TARGET_DIR) 是 rootfs 目录树，$(STAGING_DIR) 是 sysroot。收尾的 $(eval $(generic-package)) 是必须的——它才是把上面变量变成真正 make 规则的那一步。

2.5 rootfs overlay：不改包就改根文件系统 #

bash
make menuconfig
#   System configuration → Root filesystem overlay directories
#   填 board/<vendor>/<board>/rootfs-overlay

overlay 里的目录会原样拷进最终 rootfs，覆盖同名文件。适合放 /etc/network/interfaces、自己的启动脚本、/etc/init.d/S99xxx。比维护一个 patch 简单得多。

三、Buildroot 的包管理机制 #

3.1 四类包 #

类型 文件 用途
generic-package package/pkg-generic.mk 绝大多数包：下载 → 解压 → 打补丁 → configure → build → install
autotools-package 复用 generic 有 configure 脚本的包，自动加 --host --prefix
cmake-package package/pkg-cmake.mk CMake 工程，自动传 -DCMAKE_TOOLCHAIN_FILE
virtual-package package/pkg-virtual.mk 只定义接口、实现由别的包提供（如 virtual/kernel、toolchain）

3.2 generic-package 干了什么 #

它把一个包拆成七个阶段，每阶段成功后在 output/build/<pkg>-<ver>/ 里写一个 .stamp_*：

.stamp_downloaded → .stamp_extracted → .stamp_patched → .stamp_configured
   → .stamp_built → .stamp_staging_installed → .stamp_target_installed

每阶段都有对应的 <PKG>_XXX_CMDS 宏可覆盖。依赖由 $(2)_DEPENDENCIES 决定，而 $(2)_ADD_TOOLCHAIN_DEPENDENCY ?= YES 会让几乎所有包自动依赖工具链——Config.in 里不必手工写。

3.3 外部工具链的封装 #

toolchain/toolchain-external/pkg-toolchain-external.mk 负责三件事：把外部工具链复制进 output/host/、生成 sysroot 软链、设置编译器路径。核心选择逻辑是：

ifeq ($(BR2_TOOLCHAIN_BUILDROOT),y)
TOOLCHAIN_DEPENDENCIES += toolchain-buildroot
else ifeq ($(BR2_TOOLCHAIN_EXTERNAL),y)
TOOLCHAIN_DEPENDENCIES += toolchain-external
endif
$(eval $(virtual-package))

外部工具链相关配置项（菜单 Toolchain → Toolchain type → External toolchain）：

配置项 含义
BR2_TOOLCHAIN_EXTERNAL_PATH 工具链解压目录
BR2_TOOLCHAIN_EXTERNAL_PREFIX 前缀，如 arm-buildroot-linux-gnueabihf
BR2_TOOLCHAIN_EXTERNAL_CUSTOM_PREFIX 自定义前缀（选 Custom toolchain 时用）
BR2_TOOLCHAIN_EXTERNAL_CUSTOM_GLIBC / _UCLIBC / _MUSL C 库类型，必须与实际一致
BR2_TOOLCHAIN_EXTERNAL_GCC_* / _HEADERS_* / _BINUTILS_* 版本声明，用于兼容性检查
BR2_TOOLCHAIN_EXTERNAL_HAS_SSP / _CXX / _FORTRAN 能力声明，决定能否编带栈保护 / C++ 的包
⚠这几个「声明」不是装饰

声明 HAS_SSP=n 却编了带 -fstack-protector 的库，运行时会缺 __stack_chk_fail；声明 glibc 却实际是 musl，会在链接期炸出一堆未定义符号。声明必须与实际工具链一致。

3.4 br2-external：把定制内容挪出 Buildroot 树 #

直接改 buildroot 目录的最大问题是升级困难。br2-external 把定制放在外面：

my-platform/
├── external.desc      # name: MYPLATFORM / desc: ...
├── external.mk        # 引入自己的 package/*.mk
├── Config.in          # 引入自己的 package/Config.in
├── configs/           # 自己的 defconfig
├── board/             # 自己的 board 目录
└── package/           # 自己的包

bash
make O=/path/to/out BR2_EXTERNAL=/path/to/my-platform my_board_defconfig
make O=/path/to/out BR2_EXTERNAL=/path/to/my-platform

构建时生成 output/br2-external.mk，里面定义 BR2_EXTERNAL_MKS、BR2_EXTERNAL_<NAME>_PATH、BR2_EXTERNAL_<NAME>_DESC 三个变量。

local.mk 是另一个口子：放在 BR2_EXTERNAL 根目录，用来覆盖内核/u-boot 的源码路径，例如 LINUX_OVERRIDE_SRCDIR = /home/me/linux。配合 OVERRIDE_SRCDIR 可以做到「改本地内核源码 → make linux-rebuild → 立刻出新镜像」，是内核调试期最顺手的做法。

3.5 两条重建快捷目标 #

makefile
rr:            # 重建 rootfs（保留已编译的包）
	rm -f $(BASE_DIR)/target/.stamp_target_installed
	rm -rf $(BASE_DIR)/target
	$(MAKE) -C $(BASE_DIR)

rp:            # 强制重跑 post-build / post-image
	rm -f $(BASE_DIR)/target/.stamp*
	$(MAKE) -C $(BASE_DIR)

四、Yocto 上手 #

4.1 六个名词 #

名词 含义
BitBake 构建引擎（类似 make，但面向「任务」）
Layer 一组 recipe 的集合，可叠加（meta-*）
Recipe（.bb） 一个软件包的构建配方
.bbappend 对已有 recipe 的补充/覆盖，不改原文件
Machine / Distro 目标硬件配置 / 发行版策略（libc、init 系统、特性开关）
Image 最终镜像配方（core-image-minimal 等）

4.2 七步跑起来 #

bash
# 1) 装依赖（Ubuntu 20.04/22.04）
sudo apt-get install gawk wget git diffstat unzip texinfo gcc build-essential \
     chrpath socat cpio python3 python3-pip python3-pexpect xz-utils debianutils \
     iputils-ping python3-git python3-jinja2 libegl1-mesa libsdl1.2-dev \
     pylint3 xterm file zstd liblz4-tool

# 2) 取 poky
git clone -b kirkstone git://git.yoctoproject.org/poky.git
cd poky

# 3) 初始化（创建并进入 build/）
source oe-init-build-env

# 4) 改 conf/local.conf，见 4.3

# 5) 加层
bitbake-layers add-layer ../meta-openembedded/meta-oe

# 6) 构建
bitbake core-image-minimal

# 7) 产物
ls tmp/deploy/images/<machine>/

4.3 local.conf 与 bblayers.conf 的分工 #

文件 放什么
conf/local.conf MACHINE、DISTRO、DL_DIR、SSTATE_DIR、BB_NUMBER_THREADS、PARALLEL_MAKE、IMAGE_INSTALL:append、DISTRO_FEATURES:append
conf/bblayers.conf BBLAYERS（层列表） 
MACHINE ?= "raspberrypi4"
DISTRO_FEATURES:append = " opengl x11"
IMAGE_INSTALL:append = " mesa mesa-gl mesa-demos"
BB_NUMBER_THREADS = "8"
PARALLEL_MAKE = "-j 8"
⚠kirkstone 起必须用冒号语法，下划线已弃用

老教程写 DISTRO_FEATURES_append、IMAGE_INSTALL_append、PACKAGECONFIG_append，在 kirkstone（3.4）之后会直接报错或不生效。正确写法是 DISTRO_FEATURES:append、IMAGE_INSTALL:append、PACKAGECONFIG:append。同理 BBLAYERS 不该写在 local.conf 里，它属于 conf/bblayers.conf。

4.4 常用命令 #

命令 作用
bitbake core-image-minimal 构建最小镜像
bitbake core-image-sato 带 Sato 桌面
bitbake virtual/kernel / virtual/bootloader 单独编内核 / bootloader
bitbake <recipe> 单编某个包
bitbake -s 列出所有可构建目标（注意是 -s，不是 s）
bitbake -c listtasks <recipe> 列出该 recipe 可单独跑的任务
bitbake -c cleanall <recipe> 清掉该包全部产物（含下载缓存）
bitbake-layers create-layer meta-xxx 新建层
bitbake-layers add-layer ../meta-xxx 加层
bitbake <image> -c populate_sdk 导出 SDK（现代做法，替代 meta-toolchain）

4.5 build 目录里都放了什么 #

路径 内容
tmp/deploy/images// 最终镜像（.wic、.ext4、Image、u-boot.bin）
tmp/deploy/sdk/ 导出的 SDK 安装脚本
tmp/work//// 每个包的解压、编译、安装目录
tmp/work-shared//kernel/ 共享的内核源码（多个 recipe 依赖时只有一份）
tmp/sysroots/ 交叉 sysroot
tmp/sstate-control/ 共享状态缓存的索引
tmp/cache/ 解析缓存（改了层要删，否则报 parse error 一直不变）

五、Yocto 的 recipe 怎么写 #

最小可用模板：

SUMMARY = "My demo application"
LICENSE = "MIT"
LIC_FILES_CHKSUM = "file://${COMMON_LICENSE_DIR}/MIT;md5=0835ade698e0bcf8506ecda2f7b4f302"

SRC_URI = "file://myapp.c \
           file://Makefile"
S = "${WORKDIR}"

do_compile() {
    oe_runmake
}

do_install() {
    install -d ${D}${bindir}
    install -m 0755 myapp ${D}${bindir}/myapp
}

配套的 files/myapp.c 与 files/Makefile 与本 .bb 放同一层，SRC_URI 里的 file:// 就是相对 recipe 目录找。

变量/函数 作用
SRC_URI 源码来源：file://（本地）、git://、https://
S 解压后的源码目录
D 安装目标（会被打包成 .ipk/.rpm）
bindir / sysconfdir / libdir /usr/bin、/etc、/usr/lib
inherit 引入通用类，如 inherit autotools pkgconfig systemd
DEPENDS / RDEPENDS: 构建期依赖 / 运行期依赖

扩展已有配方用 .bbappend：

# meta-opengl/recipes-graphics/mesa/mesa_%.bbappend
PACKAGECONFIG:append = " gallium"
GALLIUMDRIVERS:append = ",swrast"

注意 % 是通配版本号，这样升级 mesa 版本时 append 不用改。

六、两条路线的换算表 #

概念 Buildroot Yocto
一次配置 make <board>_defconfig 改 local.conf 的 MACHINE
包定义 package/<pkg>/<pkg>.mk + Config.in recipes-*/<pkg>/<pkg>_<ver>.bb
覆盖别人的包 patch 或自己的 .mk 替换 .bbappend
定制集合 br2-external 目录 layer（meta-*）
加文件进 rootfs BR2_ROOTFS_OVERLAY 自己的 recipe + do_install，或 IMAGE_INSTALL
单包重编 make <pkg>-rebuild bitbake -c compile -f <recipe>
产物位置 output/images/ tmp/deploy/images//
增量缓存 .stamp_* sstate（内容寻址，可跨机器共享）
✦想从 Buildroot 迁到 Yocto，先迁 layer 而不是 recipe

迁移成本主要在「把散落的定制整理成层」这件事上，而不是语法。先把「板级 BSP / 应用 / 发行版策略」分成三个 meta-，再逐个写 .bb，会顺得多。反向迁则简单：把 layer 里的补丁与源码抓出来，写成 package/.mk。

七、踩坑速查 #

症状 原因 处置
Buildroot 改了包源码不生效 .stamp_* 认为已完成，或 rsync 覆盖 make <pkg>-rebuild；永久生效走 OVERRIDE_SRCDIR
menuconfig 里看不到自己的包 忘了在 package/Config.in 里 source 补 source 一行
链接期缺 __stack_chk_fail 工具链声明与实际不符 核对 BR2_TOOLCHAIN_EXTERNAL_HAS_SSP
Yocto 报 parse error 且改配置无效 tmp/cache 是旧的 rm -rf tmp/cache 重跑
Yocto 报 _append 语法错误 kirkstone 起改用 :append 全文替换
bitbake -s 写成 bitbake s 少一个横线 加 -s
镜像烧到卡上启动不了 dd 没落盘 加 conv=fsync
Yocto 说找不到 zstd kirkstone 起是必需依赖 装 zstd、liblz4-tool
