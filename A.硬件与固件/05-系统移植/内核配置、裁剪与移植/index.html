零、移植到底在移什么 #

0.1 一颗芯片上的四层供应商 #

嵌入式 Linux 的「移植」被反复重做，根源是硬件是分层供货的，每一层都只交付自己那一段代码：

层 交付物 典型工作
IP 核厂（ARM） CPU 核设计、指令集手册 内核里 arch/arm/mm/、arch/arm/kernel/、arch/arm64/ 那一层由社区维护，一般不用自己动
SoC 厂（三星/瑞芯微/NXP） 参考板 BSP、mach-xxx 与 dts、时钟与引脚定义 把自己板子的差异补进 arch/arm/boot/dts/ 或 arch/arm/mach-xxx/
外设厂（DM9000、SSD1306…） 芯片手册与参考驱动 往往社区已有驱动，只需配置里选上、设备树节点写对
整机厂（你） 板级差异：晶振、内存、NAND 型号、按键与 LED 引脚、分区表 这四样几乎决定了 90% 的移植工作量
✦判断「这段代码该不该自己写」的简单办法

看内核源码树里有没有现成的同 SoC 目录。有 mach-xxx 或同族 dts，就只做差异适配；一个都没有，才需要从零写板级文件——那种情况通常是 SoC 太新或太小众。

0.2 内核与发行版的区别 #

内核（kernel） 发行版（distribution）
内容 只有内核与模块 内核 + libc + 工具 + 包管理 + 桌面
可裁剪 天生可裁剪，能压到几百 KB 动辄数百 MB
硬件支持 靠编译时选中的配置项决定 出厂配置「尽量全选」，能开机就能跑
嵌入式里的角色 必须自己编，因为配置决定了体积与启动时间 一般只拿来当编译主机，不装到目标板上

0.3 版本号怎么看，以及一条过时的传说 #

版本号 A.B.C.D 的语义：A 主版本（不兼容的大改）、B 次版本（新增特性）、C 发行版本（bugfix）、D 更新号（同一发行版上的补丁）。

⚠「次版本号偶数稳定、奇数开发」这条规则在 3.0 之后已废止

内核 2.6.39 之后直接跳到 3.0，从此不再用奇偶区分稳定线与开发线。看到老教程按奇偶选版本，直接忽略。

实际选型：跟着 SoC 厂 BSP 的版本走。BSP 给 3.14 就用 3.14，给 4.14 就用 4.14，别自作主张升小节号——板级代码与设备树绑定的是大版本。

0.4 源码目录结构 #

目录 内容
arch/ 体系结构相关。arch/arm/ 下再分 kernel/（启动、异常、系统调用）、mm/（页表、cache）、mach-xxx/（板级）、boot/dts/（设备树）、boot/（镜像生成）
drivers/ 驱动，按总线/子系统再分层：char/、block/、net/、mmc/、mtd/、i2c/、spi/、usb/、video/
init/ main.c 里的 start_kernel 就在这
kernel/ 调度、时间、中断框架、printk
mm/ 内存管理通用层
fs/ / net/ 文件系统 / 网络协议栈
lib/ 与体系结构无关的库函数
scripts/ 构建脚本：Kbuild.include、Makefile.build、Makefile.clean，以及 dtc、mkimage 相关工具
include/ 头文件，include/linux/ 通用；asm 是软链，指向 arch/xxx/include/asm
Documentation/ 文档；devicetree/bindings/ 下是设备树绑定说明，写节点前必看

一、构建体系：Makefile 如何决定一切 #

1.1 五个角色 #

文件 作用
顶层 Makefile 定义 ARCH、CROSS_COMPILE、版本号，包含 .config，把子目录编成 vmlinux
.config 由 make menuconfig 生成，形如 CONFIG_XXX=y/m
arch/$(ARCH)/Makefile 由顶层 Makefile 包含，定义本架构的目录分类与镜像生成规则
scripts/Makefile.*、scripts/Kbuild.include 通用规则库，if_changed 等宏在这里
各子目录 Makefile / Kconfig 决定本目录编哪些文件、配置项怎么显示
ℹ老教程写 `scripts/makefile.*`（小写 m）是 2.6 时代口径

现代内核是 scripts/Makefile.build / Makefile.clean / Makefile.lib（大写 M），另有 scripts/Kbuild.include。

1.2 Kconfig → .config → auto.conf 的三级传递 #

Kconfig 文件树（分散在 arch/ 与 drivers/ 各目录）
        │  make menuconfig
        ▼
项目根 .config                  ← 人看的，带注释 # CONFIG_X is not set
        │  make prepare（scripts/kconfig/conf）
        ▼
include/config/auto.conf        ← Makefile 看的，注释被剥掉，只剩 CONFIG_X=y
include/generated/autoconf.h    ← C 代码看的，#define CONFIG_X 1

三条推论：

  1. Makefile 里能用的配置宏，C 代码里不一定能用（反之亦然）：Makefile 写 ifeq ($(CONFIG_X),y)，C 写 #ifdef CONFIG_X。
  2. 改了 .config 却只跑 make，会出现「配置没生效」的假象——必须由 make oldconfig 或任一配置目标触发 auto.conf 重生成。
  3. 三档清理的分界：make clean 只删 .o；make mrproper 连生成的配置头一起删、保留 .config；make distclean 连 .config 都删。

1.3 顶层 Makefile 的三类变量 #

类别 例子 作用范围
全局 KBUILD_CFLAGS、KBUILD_AFLAGS、LDFLAGS、ARFLAGS 所有文件
局部 子目录 Makefile 里的 EXTRA_CFLAGS / ccflags-y 当前目录
个体 CFLAGS_foo.o 单个文件（「编译不过就降优化」的常用手段）

1.4 六类子目录与 built-in.o 的拼装 #

变量 典型内容
head-y arch/arm/kernel/head.o（必须是镜像第一个）
init-y init/
core-y kernel/ mm/ fs/ ipc/ security/ crypto/ block/
drivers-y drivers/ sound/ firmware/
net-y net/
libs-y lib/ 与 arch/arm/lib/（可能产出 lib.a 而不是 built-in.o）

每个子目录先被编成一个 built-in.o（patsubst 把 init/ 变成 init/built-in.o），最后与 head-y 一起链成 vmlinux。三条直接可用的推论：

  • 某个驱动莫名没进内核 → 先看它的目录有没有出现在这六个变量里；
  • 链接顺序就是 head-y → init-y → core-y → drivers-y → net-y → libs-y，init 代码因此总在镜像前部；
  • 链接脚本 arch/arm/kernel/vmlinux.lds 由 arch/arm/kernel/vmlinux.lds.S 预处理生成，段顺序在 .S 里写死。

1.5 一个驱动从「选中」到「进镜像」的完整链条 #

以字符驱动为例：drivers/char/Kconfig 里有配置项 → menuconfig 里选 * 或 M → .config 出现 CONFIG_XXX=y 或 =m → drivers/char/Makefile 中 obj-$(CONFIG_XXX) += xxx.o 生效 → 编出 xxx.o → 汇入 drivers/built-in.o（选 *）或单独产出 xxx.ko（选 M）。

✦加驱动文件时**两处都要改**

Kconfig 决定「菜单里看得见」，Makefile 决定「编不编」。漏 Kconfig 得到「编进去了但菜单里找不到」，漏 Makefile 得到「菜单里能选但文件没进镜像」。两处顺序无所谓，但必须成对。

二、make 目标全景与镜像生成链 #

2.1 配置类目标 #

命令 作用
make <board>_defconfig 从 arch/$(ARCH)/configs/<board>_defconfig 导入基线
cp arch/arm/configs/xxx_defconfig .config 等价的老写法
make menuconfig 文本菜单（最常用，需要 ncurses）
make config / oldconfig / gconfig / xconfig 逐项问答 / 只问新增项 / GTK 界面 / Qt 界面
make savedefconfig 把当前配置反推成最小 defconfig，便于存档与分享
make allyesconfig / allnoconfig 全选 / 全不选，一般只用于试探编译
make ARCH=arm help 列出本架构支持的所有目标

三态语义：< > 是「不选 / * 编进内核 / M 编成模块」，[ ] 是「不选 / *」两态。

2.2 镜像生成的四个台阶 #

vmlinux（ELF，带符号）
   │ objcopy -O binary
   ▼
arch/arm/boot/Image                ← 裸二进制，未压缩
   │ gzip
   ▼
arch/arm/boot/compressed/piggy.gzip ← 被放进压缩版内核里
   │ compressed/ 下的解压代码 + piggy 一起编成 compressed/vmlinux，再 objcopy
   ▼
arch/arm/boot/zImage               ← 自解压镜像，u-boot 用 bootz/go 启动
   │ mkimage 加 64 字节头
   ▼
arch/arm/boot/uImage               ← u-boot 用 bootm 启动
命令 产物 谁来启动
make Image arch/arm/boot/Image 直接跳到地址，少用
make zImage arch/arm/boot/zImage u-boot bootz 0x20008000
make uImage arch/arm/boot/uImage u-boot bootm 0x30000000
make dtbs arch/arm/boot/dts/*.dtb u-boot bootm <内核> - <dtb>
make modules 各目录 *.ko 板端 insmod
make modules_install + make install /boot/vmlinuz-* + initramfs x86 上的 GRUB（嵌入式不用）
⚠三条用错就「一点输出都没有」的搭配
  1. uImage 只能用 bootm；zImage 只能用 bootz（老 u-boot 没有 bootz 时才用 go，且要求已解压）。
  2. 有设备树的内核必须 bootm <内核> - <dtb>，中间那个 - 是 initrd 占位，省掉它内核会拿不到 dtb 而报 unrecognized/unsupported machine ID。
  3. go 启动 zImage 在老教程里能跑，是因为那代 u-boot 的 go 恰好不做镜像头解析；新 u-boot 上照抄会失败。

2.3 mkimage：那 64 字节头里有什么 #

uImage = 64 字节头 + zImage。关键字段：

字段 含义
ih_magic 固定 0x27051956，u-boot 靠它识别
ih_load 加载地址（-a）
ih_ep 入口地址（-e）
ih_time 生成时间戳
ih_size 载荷长度（不含头）
ih_dcrc / ih_hcrc 载荷 CRC / 头部 CRC

命令全文（-A 架构、-O 操作系统、-T 类型、-C 压缩方式、-a 加载地址、-e 入口地址、-n 镜像名、-d 输入输出）：

bash
mkimage -A arm -O linux -T kernel -C none \
        -a 0x30108000 -e 0x30108000 \
        -n "Linux-5.2.8" -d arch/arm/boot/zImage arch/arm/boot/uImage

用 make uImage 时这两个地址来自 LOADADDR 环境变量或 CONFIG_ZBOOT_ROM_TEXT 一类配置项。两套实测值：

平台 命令 结果
Mini2440（DDR 起 0x30000000） make uImage 头里 Load Address: 30108000、Entry Point: 30108000
itop4412（DDR 起 0x40000000） make uImage ARCH=arm CROSS_COMPILE=arm-none-linux-gnueabi- LOADADDR=0x40007000 -j4 偏移 0x7000 是留给 u-boot 头与页表的
ℹ这两个数值不用猜，`bootm` 自己会打印

## Booting kernel from Legacy Image at ... 之后依次是 Image Type、Data Size、Load Address、Entry Point、Verifying Checksum。这四行的值就是 mkimage 时写进去的，也是排查「加载地址和 u-boot 自己冲突」的第一手证据。

系统里没有 mkimage 时两种解法：把 u-boot/tools/mkimage 拷到 /usr/bin，或 sudo apt-get install u-boot-tools。

三、工具链与环境 #

3.1 三个前缀怎么选 #

前缀 含义 何时用
arm-none-linux-gnueabi- 裸厂（none）工具链，Linux 目标，GNU EABI 老 ARM9/ARM11/Cortex-A 板最常见；Mini2440、4412 的 BSP 都是它
arm-linux-gnueabi- 发行版（apt）出的 EABI 工具链 apt install gcc-arm-linux-gnueabi
arm-linux-gnueabihf- 带硬浮点的 EABI Cortex-A 且有 FPU（A9/A53 等），浮点性能更好
aarch64-linux-gnu- 64 位 ARM 工具链 ARM64 板（RK3399/RK3588/Bubblegum-96）

判定板子该用 gnueabi 还是 gnueabihf：看 SoC 有没有 VFP/NEON 且内核开了 CONFIG_VFP。混用两种 ABI 编出的库会得到「能编过、运行段错误」，这是最隐蔽的一类坑。

3.2 安装与生效 #

bash
sudo mkdir -p /usr/local/arm
sudo tar xf gcc-4.6.2-glibc-2.13-linaro-multilib-2011.12.tar.gz -C /usr/local/arm/
echo 'export PATH=/usr/local/arm/gcc-4.6.2-glibc-2.13-linaro-multilib-2011.12/bin:$PATH' >> ~/.bashrc
source ~/.bashrc
arm-none-linux-gnueabi-gcc -v      # 验证的是交叉编译器，不是本机 gcc

老 BSP 常要求把 arm-none-linux-gnueabi-* 软链成 arm-linux-*，因为顶层 Makefile 默认写 CROSS_COMPILE ?= arm-linux-：

bash
cd /usr/local/arm/4.8.3/bin
for f in arm-none-linux-gnueabi-*; do
    ln -sf $f arm-linux-${f#arm-none-linux-gnueabi-}
done

/etc/profile 与 ~/.bashrc 的取舍：前者对所有用户生效、登录时读；后者只对当前用户、每次交互 shell 都读。开发机用后者更不容易影响别人；同时装两套工具链时，靠 PATH 顺序或传全路径的 CROSS_COMPILE 切换，别指望改 Makefile。

3.3 版本匹配：一个真实的三方矛盾 #

Mini2440 这条线实际要求两个编译器并存：

组件 需要的版本 原因
u-boot 2010/2013 一代 arm-linux-gcc 4.3.2 新版编译器对小节对齐与 .got 的处理变了，老 u-boot 链不出来或运行即崩
linux 5.2.8 arm-linux-gcc 4.8.3 4.3.2 会报 cc1: error: unrecognized command line option 一类新语法不支持

这不是配置错误，是 ARM9 老平台的常态。64 位主机装 32 位工具链还会缺库：报 -bash: /usr/local/arm/4.8.3/bin/arm-linux-gcc: No such file or directory（文件明明在），实际缺的是 32 位 libz/libncurses，装 lib32z1 即可。

3.4 改顶层 Makefile #

makefile
ARCH          ?= arm        # 原为 $(SUBARCH)
CROSS_COMPILE ?= arm-linux- # 原为空，会误用本机 gcc

（新内核里这两行位置随版本变化，别照抄「第 251、252 行」这种写法。）

四、配置：从 defconfig 到产品配置 #

4.1 两条产品线，两套基线 #

平台 基线 defconfig 关键项
Exynos4412 / itop4412 / FS4412 exynos_defconfig System Type → Samsung EXYNOS；Kernel hacking → Kernel low-level debugging port → Use Samsung S3C UART 0 for low-level debug；Character devices → Serial drivers → Samsung SoC serial debug + Support for console on Samsung SoC serial port
Mini2440 / S3C2440 s3c2410_defconfig 其中已含 CONFIG_MACH_MINI2440=y、CONFIG_CPU_S3C2440=y；没有 mini2440_defconfig 这个文件
⚠别去找 `mini2440_defconfig`

S3C24xx 用的是 s3c2410_defconfig，Mini2440 的支持只是里面的一个 CONFIG_MACH_* 项。改完配置后 mv .config arch/arm/configs/s3c2440_defconfig 存成自己的基线，下次 make s3c2440_defconfig 直接复用——这才是「产品基线」的正确做法。

4.2 串口调试必须开 #

「串口一个字符都没有」绝大多数不是硬件问题，是这三项没做对：

  1. CONFIG_DEBUG_LL=y（低层调试输出）没开；
  2. 低层调试端口选错——S3C2440 是 UART0。老教程写「配置为串口 2」与所选项 Use Samsung S3C UART 0 自相矛盾，以选项为准；
  3. 没给 bootargs 加早期控制台参数，于是 Uncompressing Linux... 之后完全静默。
bash
set bootargs "console=ttySAC0,115200 earlyprintk root=/dev/mtdblock3 init=/linuxrc"

ARM64 上对应的是 earlycon（不是 earlyprintk），例如 earlycon=owl_serial——两者别混写，详见 驱动移植与环境搭建。

4.3 Exynos4412 线的取舍 #

除串口外，itop4412 的参考配置还做了三件事：

  • 勾 System Type → Samsung EXYNOS，关掉其它 SoC 家族，减少无关板级文件参与编译；
  • 移除 DMA Engine support：该板的 DMA 控制器驱动不完整，开着会在启动早期挂住；
  • 改 arch/arm/boot/dts/exynos4412-itop-scp-core.dtsi：注释掉 firmware 节点（地址 0x0203F000、compatible = "samsung,secure-firmware"，没有可信固件时访问它会触发 abort）、events 改成 event（与驱动注册的 key 名对齐）、补核心板电源芯片节点。
✦改 dts 优先用 `/include/` 或标签追加，不要直接改 SoC 公共的 `.dtsi`

「注释掉第 29~32 行、第 71 行」这种写法换一个版本就失效。正确姿势是在板级 dts 里用 &label { status = "disabled"; }; 覆盖，或 &i2c_0 { ... }; 追加节点。

4.4 x86 本机编译（另一条线，别混进来） #

偶尔要在 PC 上编一份内核验证驱动：装 Development Tools 与 Server platform development 包组 → 拷 /boot/config-$(uname -r) 为 .config → make menuconfig → make -j4 → make modules_install → make install → 改 GRUB。

这条线与嵌入式交叉编译没有交集：产物进 /boot 与 initramfs，靠 GRUB 引导，不产生 uImage，也不需要 mkimage。写文档必须分段，否则读者会拿 make install 到 ARM 板上试。

五、裁剪 #

5.1 六条原则 #

  1. 就近取基线：从同 SoC 的 defconfig 出发，别从 allyesconfig 往回删。
  2. 必须的先选足：串口、存储、根文件系统所在的总线，砍这三样等于自断退路。
  3. 不确定的不动：看不出作用的项先留着，用 ? 看 help，别赌。
  4. 可选的在 M 与 * 之间选：前者运行时才占内存，后者一直占。
  5. 渐进改动：一次只改一类，改完启动一次。批量改 50 项再启动，出错无法二分。
  6. 及时备份：cp .config .config.bak.$(date +%F-%H%M)，或用 make savedefconfig 存最小配置。

5.2 十二个功能模块的勾选清单 #

功能 配置项（菜单路径） 验证方式
GPIO 用户态 Device Drivers → GPIO Support ls /sys/class/gpio
LED 子系统 Device Drivers → LED Support（LED Class Support + 至少一个 Trigger） /sys/class/leds/
串口控制台 Character devices → Serial drivers + Console on ... bootargs 的 console= 能出字
USB Host + U 盘 USB support + USB Mass Storage + SCSI device support + SCSI disk support + VFAT lsusb、cat /proc/partitions
USB 键鼠 HID support + USB HID support + Event interface /dev/input/event*
USB Gadget USB Gadget Support + 具体 gadget（Mass Storage/Serial/Ethernet） /sys/class/udc/
SD/MMC MMC/SD/SDIO card support + MMC block device + 具体 Host + ext4 /dev/mmcblk0
网卡 先 Networking support 才会出现 Network device support；再 Ethernet driver support → DM9000 ifconfig -a
NFS 根 File systems → Network File Systems → NFS client support + Root file system on NFS bootargs 里 root=/dev/nfs
PPP Network device support → PPP support /dev/ppp
MTD / NAND Device Drivers → MTD → NAND + Samsung S3C NAND + MTD block devices + Command line partition table parsing cat /proc/mtd
UBIFS File systems → Miscellaneous filesystems → UBIFS，注意 UBI wear-leveling threshold 与预留坏块百分比必须与 u-boot 一致 ubiformat / ubiattach
CAN 在 Networking support → CAN bus subsystem support 下，不在 Device Drivers 下 ip link set can0 up

5.3 单板与文件系统裁剪（Mini2440 实例） #

s3c2410_defconfig 默认把 20 多个 S3C24xx 单板全打开，这是最大的浪费点：

  1. System Type → SAMSUNG S3C24XX SoCs Support：只留 S3C2440；
  2. 单板列表：只留 SMDK2440（Mini2440 与它共用板级代码）；
  3. File systems：去掉 Second extended fs support、Ext3、Ext4（根文件系统若是 yaffs2/jffs2 或走 NFS，这些全不需要）；
  4. CD-ROM/DVD Filesystems → ISO 9660：去掉。
⚠裁剪体积别信口口相传的「3.5M」

原文只写「默认配置编出来的内核大概 3.5M」，而启动日志里的 Data Size 分别是 3581192（3.4 MiB）与 3656464（3.5 MiB）——这是两次不同编译，不是裁剪前后对比。要给可信数字，自己记账：

bash
ls -l arch/arm/boot/uImage       # 64 字节头 + 载荷
arm-linux-size vmlinux           # text/data/bss 三段，最能说明问题

5.4 裁剪后必须回归的三件事 #

  1. 串口还在：console=ttySAC0 能出字；
  2. 存储还在：cat /proc/mtd 分区表正确，能挂根；
  3. 网络还在：网卡 probe 成功（dmesg | grep eth），否则第一次要传文件就得拆机重烧。

六、板级与驱动移植 #

6.1 machine_desc 与两个宏 #

内核靠 machine_desc 认识一块板子。老写法是 MACHINE_START（ATAGS 时代），新写法是 DT_MACHINE_START（设备树时代）：

c
DT_MACHINE_START(S3C2440_DT, "SMDK2440 (Flattened Device Tree)")
    /* Maintainer: Ben Dooks <ben-linux@fluff.org> */
    .dt_compat    = s3c2440_dt_compat,
    .map_io       = smdk2440_map_io,
    .init_machine = smdk2440_machine_init,
    .init_time    = smdk2440_init_time,
MACHINE_END

static const char *const s3c2440_dt_compat[] __initconst = {
    "samsung,s3c2440",
    "samsung,mini2440",
    NULL,
};
⚠列表结尾必须是那个 NULL 哨兵

dt_compat 交给 of_flat_dt_match_machine 后逐条比对，遇到第一个 NULL 才停。少写它，解析会一直往后读——表现为「机器匹配看着成功，后面莫名 panic」。

这个宏做三件事：把结构体放进 .arch.info.init 段；用 __arch_info_begin/__arch_info_end 把整段包起来（段即注册表）；用 .nr 或 .dt_compat 提供匹配依据。

6.2 两种机器识别方式 #

ATAGS 时代（ARM32 老内核） 设备树时代
依据 r1 传进来的 machid（Mini2440 早期是 193 = SMDK2410，后来是 168 = SMDK2440） 根节点 compatible 字符串打分
匹配函数 setup_machine_tags setup_machine_fdt → of_flat_dt_match_machine
失败表现 Error: unrecognized/unsupported machine ID unrecognized device tree list
改哪里 u-boot 的 machid 或内核 .nr dts 的 compatible

打分规则值得记住：遍历所有 machine_desc，score = of_flat_dt_match(dt_root, compat)，取「0 < score < best_score」中最小的——也就是匹配上的 compatible 条数最少者胜。所以板级 dts 应把最具体的 compatible 写在最前。

6.3 字符驱动两种编译形态 #

以 FS4412 的 LED 为例（LED 接 GPX2_7，寄存器 GPX2CON = 0x11000C40、GPX2DAT = 0x11000C44，CON 位域写 1<<28，DAT 写 1<<7）。

静态编进内核：驱动放 drivers/char/，在 Kconfig 的 menu "Character devices" 下加条目，Makefile 里写 obj-$(CONFIG_FS4412_LED) += fs4412_led_drv.o，menuconfig 里选 *，make uImage。板端起设备节点：

bash
mknod /dev/ledc c 500 0     # c = 字符设备，500 主设备号，0 次设备号

动态编译成模块：menuconfig 里选 M，make uImage modules，产物 drivers/char/fs4412_led_drv.ko，拷到板子根文件系统后 insmod。

ℹ原文这段代码有三处不能照抄
  1. 函数名是 s5pv210_led_* 却跑在 Exynos4412 上——整段从 S5PV210 教程搬来没改名；
  2. mknod /dev/ledc 5000 缺设备类型 c，且 5000 不是合法写法，正确是 mknod /dev/ledc c 500 0；
  3. 主设备号 500 不能硬编码——应取 register_chrdev_region 的返回值，或板端 cat /proc/devices 查。

6.4 板级文件里的三个必改项 #

项 改什么 不改的现象
晶振 s3c2440_init_clocks(12000000)（Mini2440 板载 12MHz） 时钟全错 → 串口波特率不对 → 全屏乱码
NAND 分区 smdk_default_nand_part[] 的 name/offset/size 找不到 rootfs，mtdblock3 挂不上
NAND ECC ecc_mode 从 NAND_ECC_SOFT 改 NAND_ECC_NONE u-boot 与内核 ECC 不一致 → 读内核报 -74（-EBADMSG）
⚠关 ECC 只是权宜，不是方案

原文自己都写了「在内核中明确说明是不建议这样做的」。正解是 u-boot 与内核用同一套 ECC（都软件或都硬件），布局一致后再谈关不关。关掉只适合验证阶段。

七、设备树：移植视角的三件事 #

语法、dtb 二进制布局、内核逐行解析、OF API 都在设备树专题里，这里只留「移植时真正会动手的三件事」。

7.1 dts 改动分三级 #

级别 动作 例子
属性级（最常见） 板级 dts 里 &label { ... }; 覆盖属性或 status = "okay" &uart_0 { status = "okay"; pinctrl-0 = <&uart0_data>; };
平台级 新建 arch/arm/boot/dts/<soc>-<board>.dts 并在同目录 Makefile 加 dtb-$(CONFIG_ARCH_XXX) += xxx.dtb s900-bubblegum.dts
目录级（新 SoC 家族） 新建 arch/arm64/boot/dts/<vendor>/ 并登记到上级 Makefile dts-dirs += actions（4.x 写法；5.x 已并入单个 Makefile 的 dtb-y）

7.2 interrupt-parent 忘写的后果 #

ARM64 上移植 ARM generic timer 时踩过：节点写对了 compatible = "arm,armv8-timer" 与 clock-frequency = <24000000>，但从父节点继承不到 interrupt-parent，中断号解析失败，日志依次出现：

arch_timer: No interrupt available, giving up
clocksource_probe: no matching clocksources found
Kernel panic - not syncing: Unable to initialise architected timer.

修法是在根节点补 interrupt-parent = <&gic>;。这类「节点本身没错、缺的是继承属性」的问题移植期极高发，排查顺序应是：先看 /proc/device-tree 里属性是否真进了内核，再查父链。

7.3 dtb 放哪里 #

三条硬约束（以 Mini2440 的 64MB DRAM 0x30000000~0x34000000 为例）：

  1. 不覆盖 u-boot 自己；
  2. 不压内核本体（内核装载在 0x30008000）；
  3. 不占用内核马上要用的内存——0x30004000~0x30008000 那 16KB 是页表区。

所以 0x30001000 是常用位置。启动日志会显示内核把它挪到别处，属正常：

## Flattened Device Tree blob at 30001000
Booting using the fdt blob at 0x30001000
Loading Device Tree to 33afa000, end 33afe521 ... OK
OF: fdt: Machine model: SMDK2440

7.4 设备树上车的最小验收 #

检查 命令/日志 通过标准
dtb 被识别 ## Flattened Device Tree blob at ... 有这行
机器匹配 OF: fdt: Machine model: ... 打印的正是你的板名
内存识别 Memory: 61036K/65536K available 接近物理内存
分区正确 板端 cat /proc/mtd 条数与 offset 对
外设可用 板端 dmesg 里 grep eth/mmc/i2c probe 成功、无 -EPROBE_DEFER 死循环

八、启动流程与内存管理 #

8.1 从 stext 到 init #

arch/arm/kernel/head.S  ENTRY(stext)
  ├ 关中断、进 SVC 模式
  ├ 取 CPU ID 校验（lookup_processor_type）
  ├ bl __vet_atags          校验 r2 处的 atags/dtb 合法性
  ├ __create_page_tables    建临时页表
  ├ __enable_mmu → __turn_mmu_on → __mmap_switched
  └ b start_kernel
        ├ setup_arch(&command_line)   → 解析 dtb / atags
        ├ local_irq_enable / console_init
        └ rest_init → kernel_thread(kernel_init)
              ├ kernel_init_freeable → do_basic_setup → do_initcalls（8 级 initcall）
              ├ prepare_namespace → mount_root
              └ run_init_process（/sbin/init → /etc/init → /bin/init → /bin/sh 依次回退）

所有 init 路径都失败时打印 Kernel panic - not syncing: No working init found.；若指定了 init=/linuxrc 而文件不存在，报 Requested init /linuxrc failed (error -2)——后者在「内核起来了、根文件系统还没做」阶段是正常现象，说明前四步全对。

8.2 MMU 与页表：移植时只需要懂三个数 #

ARM32 一级页表放 16KB 对齐地址，共 4096 项，每项 4 字节。描述符末两位决定类型：

末两位 类型 说明
0b10 段（Section） 1MB 粒度直接映射，最常用
0b01 粗页表（Coarse） 指向二级页表，支持 4KB/1KB 页
0b11 细页表（Fine） 1KB 页，ARMv6 之后基本不用

段描述符关键位：地址 [31:20]、访问权限 AP = 0b11 << 10（全访问）、域 [8:5]（16 个域）、C 位（Cache）、B 位（Write Buffer）。

一个实算例：页表基址 0x10000000，虚拟地址 0x00101000 → 段索引 0x001 → 页表项地址 0x10000004 → 该项内容 0x30000c12 → 物理地址 0x30000000 + 0x01000 = 0x30001000。

移植必须记住的一条：0x00000000 那一段要映射成 NCNB（Non-Cacheable、Non-Bufferable）。因为 ARM9 用「向 0 地址写值再读回」判断启动介质是 NOR 还是 NAND——NAND 启动时 0 地址是片内 4KB SRAM（可写），NOR 启动时 0 地址是 NOR 本体（写入无效）。这 1MB 段若开了 Cache，读回的是缓存，判断永远得到「NAND」。

Cache 三条纪律：改页表后 clean + invalidate TLB；DMA 前后 clean/invalidate 对应 D-Cache 范围；自修改代码（含 u-boot 搬自己）要 clean D-Cache、invalidate I-Cache。

8.3 加载地址与入口地址 #

平台 加载地址 说明
Mini2440 0x30008000（uImage 头里的 30108000 是 u-boot 重定位后的实际值） 0x30000000 起 64MB SDRAM，前 0x8000 留给页表与参数区
itop4412 0x40007000（LOADADDR） DDR 从 0x40000000 起，偏移 0x7000
S5PC100 0x20008000 DDR 从 0x20000000 起
ARM64（Bubblegum-96） 0x80000（TEXT_OFFSET） ARM64 内核位置无关，但页表区要从 0x0 起留 0x80000

九、烧写、启动与排错 #

9.1 分区与环境变量 #

Mini2440 的 256MB NAND 分区（mtdparts 与内核 smdk_default_nand_part[] 两处必须一致）：

mtdparts=Mini2440-0:256k(u-boot),128k(params),4m(kernel),-(rootfs);
MTDIDS_DEFAULT "nand0=Mini2440-0"

对应实测偏移：u-boot 0x00000000、params 0x00040000、kernel 0x00060000、rootfs 0x00460000。

环境变量 值 说明
CONFIG_ENV_IS_IN_NAND y 环境变量存 NAND
CONFIG_ENV_SIZE 0x20000 128KB，与 params 分区一致
CONFIG_ENV_OFFSET 0x40000 紧跟 u-boot 之后
⚠分区大小写错会得到一句很吓人的报错

把 u-boot 分区当 512k 而实际按 256k+128k 布局时，u-boot 读内核会去错地方，报 NAND read from offset 60000 failed -74。-74 是 -EBADMSG，看着像 ECC 错，实际是偏移算错。先核对分区，再怀疑 ECC。

9.2 三种烧写方式 #

方式 命令/工具 适用
tftp + nand write tftp 0x30000000 uImage → nand erase.part kernel → nand write 0x30000000 kernel → bootm 0x30000000 - 0x30001000 开发调试，最常用
MiniTools（USB） 图形界面选文件一键烧 NAND 量产、砖机救回
Fastboot fastboot flash boot uImage / fastboot flash dtb xxx.dtb 瑞芯微、Exynos 新板

9.3 bootargs 的六个版本与怎么选 #

素材里出现六种写法，按场景归成三类即可：

场景 bootargs
本地 NAND 根 console=ttySAC0,115200 root=/dev/mtdblock3 init=/linuxrc
NFS 根（开发期） console=ttySAC0,115200 root=/dev/nfs rw nfsroot=192.168.1.1:/nfsroot/rootfs ip=192.168.1.2::192.168.1.1:255.255.255.0::eth0:off init=/linuxrc
ramdisk 根 console=ttyS0,115200 init=/init root=/dev/ram0 rw

ip= 那七段别硬背，记顺序即可：本机 IP : 服务器 IP : 网关 : 掩码 : 主机名 : 网卡 : 自动配置方式，省略的段留空但冒号不能少。

9.4 错误字典 #

报错原文 根因 解法
NAND read from offset 60000 failed -74 -EBADMSG，ECC 失败或偏移错 核对分区；两侧 ECC 模式统一
VFS: Cannot open root device "mtdblock3" + __nand_correct_data: uncorrectable ECC error 内核侧 ECC 与 u-boot 不一致 两侧同时改 ecc_mode
Error: invalid dtb and unrecognized/unsupported machine ID 机器码不匹配 set machid 0xA8（168），或改 dts 的 compatible
Bad eraseblock 43 at 0x000000560000 连续出现 NAND 假坏块（ECC 错被当坏块） nand scrub.chip 全片擦除
cc1: error: unrecognized command line option 内核太新、编译器太老 升工具链（4.3.2 → 4.8.3）
找不到 mkimage / 无 uImage 目标 缺 u-boot-tools sudo apt-get install u-boot-tools
-bash: .../arm-linux-gcc: No such file or directory（文件存在） 64 位主机缺 32 位库 sudo apt-get install lib32z1

9.5 调试：oops 与 printk #

oops 定位：日志里出现 PC is at xxx+0x1c/0x40，拿同一次编译的 vmlinux 反查：

bash
arm-linux-addr2line -e vmlinux -f 0xc00xxxxx

两点注意：① 原教程说「最重要的是 EIP」是 x86 口径，ARM 上是 PC/R15；② vmlinux 必须与出错的那次编译一致，改一行 printk 都会错位。

printk 八级：

级别 宏 场景
0 KERN_EMERG 系统不可用
1 KERN_ALERT 必须立即处理
2 KERN_CRIT 严重
3 KERN_ERR 错误
4 KERN_WARNING 警告（DEFAULT_MESSAGE_LOGLEVEL 的默认值）
5 KERN_NOTICE 正常但重要
6 KERN_INFO 信息
7 KERN_DEBUG 调试

/proc/sys/kernel/printk 四个数的含义：控制台级别 / 未指定级别的默认级别 / 最小允许的控制台级别 / 引导时的默认值。小于控制台级别才上屏，例如控制台级别是 4 时，KERN_DEBUG（7）只进 dmesg 不上屏。

bash
echo 8 > /proc/sys/kernel/printk   # 临时让所有级别都上屏
dmesg | tail -n 30               # 不受控制台级别影响的环形缓冲
✦让日志带时间戳，直接看出卡在哪一步

开 Kernel hacking → printk and dmesg options → Show timing information on printks（CONFIG_PRINTK_TIME），日志变成 [ 0.093281] ...。两次启动对比时间戳，能量化「哪一段变慢了」。
