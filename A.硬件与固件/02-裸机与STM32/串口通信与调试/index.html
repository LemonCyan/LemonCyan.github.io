一、先分清四种「串口」 #

很多人说「串口不通」，其实是没分清自己手上是哪种电平。

标准 电平 逻辑 1 逻辑 0 传输距离 场景
TTL 0V / 3.3V（或 5V） 3.3V 0V < 1m 板内 MCU 之间
RS232 ±3~15V -3~-15V +3~+15V ~15m 老式 PC 串口、工控设备
RS485 差分 A/B A>B A<B 1200m 工业总线、多机
USB 差分 D+/D- — — 5m 接电脑

三个最容易误解的点：

  1. RS232 是负逻辑：逻辑 1 是负电压。所以 TTL 直连 RS232 不但不通，还可能烧接口。中间必须有 MAX232 之类的电平转换芯片。
  2. RS485 是半双工：收发共用一对线，切换方向需要控制 DE/RE 引脚，而且必须等最后一个字节真正发完（TC 标志，不是 TXE）再切回接收，否则最后一个字节会被截断。
  3. USB 转串口不是「USB 串口」：CH340/CP2102/FT232 之类的芯片内部做了 USB 到 UART 的转换，电脑上看到的是虚拟 COM 口，对 MCU 而言仍然是 TTL 串口。

二、乱码定位：一个固定的六步排查 #

串口乱码是最常见的现象，也最容易靠「瞎改代码」浪费时间。按下面顺序查，一般三步之内能定位。

第一步：看乱码的「形态」 #

现象 大概率原因
完全不乱，但字符全错位（比如发 "abc" 收 "`bc"） 起始位/停止位配错，或第一次接收丢了首字节
周期性出现乱码 波特率有误差，误差累积超过半个位宽
全是乱七八糟的符号（像 烫烫烫 或 锟斤拷） 波特率差得离谱、或电平不匹配
发得出去，收不回来 RX 引脚没配成输入 / 复用没开 / 中断没使能
短接 TX-RX 自测能通，接设备不通 电平标准不对（TTL 直连 RS232）或没有共地

第二步：确认时钟 #

这是最高频的根因，尤其 STM32 上：

  • STM32：HSE_VALUE 宏必须等于实际晶振。12MHz 的板子用默认 8MHz 宏，PLL 算出来 108MHz，波特率跟着错，全乱码。
  • S3C2440：PCLK 是多少？UBRDIV 是按 PCLK 算的，换了 MPLL 配置却没重算 UBRDIV，波特率必错。
  • 通用检查法：用示波器量一个字节的时间。9600 波特率下 1 位是 104us，一个 8N1 帧（10 位）是 1.04ms。量出来差多少就知道时钟错了多少。

第三步：确认分频值 #

平台 公式 常见错
S3C2440 UBRDIV = clk/(baud×16) - 1 忘了 -1
STM32 BRR = clk/(16×baud)，整数 4 位小数 小数部分乘错（该 ×16 却 ×0.15）
51 TH1 = 256 - fosc/(12×32×baud) 忘了 SMOD 位的影响

误差容限：总误差必须小于 2%（10 位帧、无校验时略宽松），超过就会出现「大部分字节对、偶尔错一个」。

第四步：确认引脚 #

  • TX 必须配成复用推挽输出（STM32 的 CNF=10），配成普通推挽发不出正确波形；
  • RX 必须配成输入（上拉或浮空），配成输出就永远收不到；
  • TX/RX 要交叉连接：A 的 TX 接 B 的 RX；
  • 必须共地。不共地时两边电平常识不同，现象是「有时能收，一碰就断」。

第五步：确认中断与标志 #

  • STM32：中断里必须「先读 SR 再读 DR」，顺序反了 RXNE 清不掉，中断会反复进；
  • S3C2440：RXD0 与 TXD0 两个子源必须同时使能（实测行为）；
  • 两边共同的坑：接收溢出必须读掉数据寄存器，只清标志没用，下次照样报溢出。

第六步：确认对端 #

最常见的乌龙是对端波特率根本不是 9600，或者对端发的是 8E1 而你配的是 8N1。设备手册上的「默认串口参数」经常与实际出厂设置不同，必要时逐个波特率试一遍。

三、printf 重定向：三条路 #

裸机调试最想干的事就是 printf("x=%d\n", x)。三条路各有取舍：

3.1 重定向 fputc（最简单） #

c
int fputc(int ch, FILE *f)
{
    while (!(USART1->SR & (1<<7)));   /* 等 TXE */
    USART1->DR = (u8)ch;
    return ch;
}

GCC 下对应的钩子是 _write：

c
int _write(int fd, char *ptr, int len)
{
    for (int i = 0; i < len; i++)
        uart_putchar(ptr[i]);
    return len;
}

Keil 下还需要 #pragma import(__use_no_semihosting) 四件套（见 STM32F103 基础与外设）。

缺点：阻塞式，发一个字节等一个字节。115200 下每字节约 87us，打一行 40 字符就是 3.5ms——在中断里调 printf 会直接卡死系统。

3.2 环形缓冲 + 中断发送（推荐） #

c
#define TX_BUF_SIZE 512

static u8  tx_buf[TX_BUF_SIZE];
static u16 tx_head = 0, tx_tail = 0;

void uart_send_buf(const u8 *data, u16 len)
{
    for (u16 i = 0; i < len; i++)
    {
        u16 next = (tx_head + 1) % TX_BUF_SIZE;
        if (next == tx_tail) break;        /* 缓冲满，丢弃 */
        tx_buf[tx_head] = data[i];
        tx_head = next;
    }
    USART1->CR1 |= 1<<7;                   /* 打开 TXE 中断，让中断去发 */
}

void USART1_IRQHandler(void)
{
    if (USART1->SR & (1<<7))               /* TXE */
    {
        if (tx_tail != tx_head)
        {
            USART1->DR = tx_buf[tx_tail];
            tx_tail = (tx_tail + 1) % TX_BUF_SIZE;
        }
        else
            USART1->CR1 &= ~(1<<7);        /* 发完了，关 TXE 中断 */
    }
    if (USART1->SR & (1<<5))               /* RXNE */
    {
        u8 ch = USART1->DR;
        /* 收到数据 */
    }
}

这个模式的关键是发完就关 TXE 中断。不关的话 TXE 会一直为 1，中断会无限触发，CPU 100%。

3.3 DMA 发送（最省 CPU） #

把缓冲区地址和长度丢给 DMA，发完触发一次传输完成中断。CPU 全程不参与。缺点是要处理「DMA 还在发，你又要发新数据」的冲突，通常要加个忙标志或双缓冲。

四、收一帧数据：三种状态机 #

裸机收数据最难的不是「收字节」，而是「判断一帧什么时候结束」。三种主流做法：

4.1 固定长度 #

最简单，数够 N 个字节就算一帧。适合定长协议（寄存器读写、Modbus RTU 的请求帧）。

4.2 结束符判定：一个 u16 状态字 #

适合「一行一条命令」的调试协议，结束符一般是 \r\n：

text
bit15      接收完成标志
bit14      已收到 0x0D
bit13~0    已收到的字节数

这套写法在 2440 和 STM32 上都能直接用，具体代码见 S3C2440 裸机：GPIO、中断与串口 第三节。

必踩的坑：主循环处理完必须把 bit15 清零，否则永远不会再接收下一帧。

4.3 空闲中断 + DMA（最优雅） #

STM32 的串口有一个 IDLE 中断：当 RX 线上超过一个字节时间没有新数据时触发。配合 DMA，可以实现「DMA 自动收，IDLE 中断告诉你这一帧结束了」：

c
void USART1_IRQHandler(void)
{
    if (USART1->SR & (1<<4))               /* IDLE */
    {
        USART1->SR;                        /* 读 SR 再读 DR 才能清 IDLE */
        USART1->DR;

        u16 len = BUF_SIZE - DMA1_Channel5->CNDTR;
        /* 处理 buf[0..len-1] */

        DMA1_Channel5->CCR &= ~1;          /* 关 DMA */
        DMA1_Channel5->CNDTR = BUF_SIZE;   /* 重置计数 */
        DMA1_Channel5->CCR |= 1;           /* 重新开 */
    }
}

这是工业项目里最常用的方案：CPU 占用接近 0，且不需要事先知道帧长。代价是要开 DMA 时钟、配通道，初始化代码长一些。

五、协议帧设计：四条实用规则 #

裸机调试协议不用搞得太复杂，但有四条规则能省掉后面大量麻烦：

5.1 有帧头，最好有两个 #

text
[0xAA][0x55][LEN][CMD][DATA...][CRC16_H][CRC16_L]

两个字节的帧头（0xAA 0x55）几乎不会在数据里连续出现，误同步概率极低。用单个 0xAA 作帧头的话，数据里出现 0xAA 就会误判。

5.2 长度字段一定要有 #

没有长度字段就只能靠结束符，而二进制数据里什么字节都可能出现。有了 LEN，接收方才能知道「还差几个字节」。

5.3 校验不能省 #

校验 强度 代价
累加和 弱（两字节互换检测不出） 1 字节
CRC16 强（工业标准） 2 字节 + 查表
CRC32 最强 4 字节

调试期建议直接上 CRC16-Modbus，网上现成的表，不差这点开销。

5.4 要有应答和超时 #

一问一答的协议必须定义：超时重发几次、重发间隔多少、连续失败多少次算断线。没有这套，一旦丢一个字节，两边状态机就永久错位了。

一个常用参数：超时 100ms、重发 3 次、连续 5 次失败报错。

六、一个最小可用的调试框架 #

把上面几块拼起来，就是一个不依赖任何 RTOS 的调试框架：

text
中断里：只做「收字节入环形缓冲」和「从发送缓冲取字节」两件事
主循环：从环形缓冲取数据 → 组帧 → 校验 → 分发 → 回包

核心原则：中断里绝不做耗时操作。中断里调 printf、做 CRC、动 I2C，都是「系统偶尔卡死」的经典原因。

七、踩坑清单 #

  1. TTL 直连 RS232 不通还可能烧，必须有电平转换。
  2. RS485 切回接收要等 TC 不是 TXE。
  3. 不共地会偶发不通。
  4. TX/RX 要交叉，不是同名对接。
  5. STM32 的 HSE_VALUE 必须等于实际晶振（乱码第一嫌疑）。
  6. S3C2440 换了 PCLK 必须重算 UBRDIV。
  7. 波特率总误差要 < 2%，否则周期性乱码。
  8. STM32 的 RX 引脚必须配成输入，TX 必须复用推挽。
  9. STM32 中断里要先读 SR 再读 DR，否则标志清不掉。
  10. S3C2440 的 RXD0 与 TXD0 要同时使能。
  11. 接收溢出必须读掉数据寄存器，只清标志无效。
  12. 发完要关 TXE 中断，否则 CPU 100%。
  13. 中断里不要调 printf，阻塞式输出会拖垮实时性。
  14. 状态机处理完必须清完成位，否则再也收不到。
  15. 单字节帧头会误同步，用双字节。

小结 #

串口本身极简单——一个起始位、八个数据位、一个停止位，剩下的都是工程问题。而工程问题的 90% 集中在三处：

  1. 物理层（电平标准、共地、交叉）；
  2. 时钟层（晶振频率 → 系统时钟 → 分频值，任何一环错都表现为「乱码」）；
  3. 软件层（标志清除顺序、缓冲设计、帧协议）。

按第一节的六步排查法走一遍，绝大多数「串口不通」都能在十分钟内定位。
