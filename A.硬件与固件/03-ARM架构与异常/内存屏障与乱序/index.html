一、问题的量级 #

2006 年的 CPU 每 ns 能执行 10 条指令，而从主存取一个数据项要几十 ns。差距超过两个数量级，于是有了几 MB 的 cache。

因果链是这样的：

text
CPU 比 memory 与 interconnect 快一个数量级以上
        ↓
重排内存访问能显著提升性能
        ↓
但某些代码（同步原语）的正确性依赖 program order
        ↓
只能由软件显式插 barrier

所以屏障是「性能与正确性」双方妥协的产物：对性能和扩展性有杀伤力，但在正确性上不可省。

二、Cache 结构与 miss 的五种成因 #

数据以 cache line 为单位在 cache 与 memory 之间流动，line 大小是 2 的幂，16~256 字节不等。

原文把 miss 分成五类，这套术语值得记住：

类型 成因
startup / warmup miss 首次访问，需要几百 cycle 填充
capacity miss cache 已满，必须驱逐（一般按 LRU）
associativity miss set 冲突被驱逐后再次访问被驱逐的那条 line
write miss 要写的数据在本 CPU cache 中但是只读（shared），必须先 invalidate 其他 CPU
communication miss 别的 CPU 为写而 invalidate 了本 CPU 的副本，导致本 CPU 后续访问 miss

最后一类最值得注意：lock 就是这种典型数据项——谁抢到锁，谁的 cache 副本就会被别人反复 invalidate，于是「抢锁热点」在硬件层表现为持续的 communication miss。

2.1 一个可以手算的 cache 模型 #

原文给的示例 cache 是全书唯一给出完整几何参数的一个：

text
16 个 set × 2 way = 32 条 line
每条 line 256 字节
即 two-way set-associative

可以类比成「16 个 bucket、每个桶最多 2 个元素」的哈希表。硬件哈希极简：从地址取 4 个 bit；因为 256 字节对齐，低 8 位恒为 0，所以 bit8~bit11 选 set。

算例：代码位于 0x43210E00~0x43210EFF，数据顺序访问 0x12345000~0x12345EFF，正好填满 set0~set14 的 way0 与 set15 的 way1。此时：

访问地址 落到的 set 结果
0x12345F00 set 0xF 两 way 全空，放得下
0x12330000 set 0x0 走 way1
0x1233E00 set 0xE 两 way 已满，必须驱逐 → 被驱逐者若再被访问即 associativity miss

一句值得记住的定性：「a shared-memory multiprocessor system really is a message-passing computer under the covers」——SMP 在两个层次（SMP 内部、SMP 机器之间）都是靠消息传递实现共享内存的。这句话是理解 MESI 与 invalidate queue 的心理准备。

三、MESI：四个状态与六条消息 #

3.1 四个状态 #

每条 line 除了物理地址和数据，还有 2 bit 的状态标签：

状态 含义 能直接写 memory 是否最新 丢弃时
M modified 近期被本 CPU store 过，其他 cache 中保证没有该 line；本 cache 拥有它 可以 否（最新只在 cache） 必须先写回或移交
E exclusive 与 M 类似，区别是本 CPU 尚未修改；memory 副本最新 可以，且不用通知别人 是 可直接丢
S shared 可能被至少一个其他 CPU 复制；写前必须协商 不可以 是 可直接丢
I invalid 空行；新数据优先放进 I 状态的 line — — —

3.2 六条协议消息 #

单共享总线场景下这六条就够：

消息 携带 说明
Read 物理地址 请求某条 line
Read Response 数据 可能来自 memory 或某个 cache；若某 cache 持有 M 状态副本，必须由它应答
Invalidate 物理地址 要求其他 cache 移除该 line
Invalidate Acknowledge — 移除后必须回送
Read Invalidate 物理地址 = Read + Invalidate；期望一个 read response + 一组 invalidate ack
Writeback 地址 + 数据 驱逐 M 状态的 line（写回 memory，或沿途被 snoop）

3.3 十二条状态迁移 #

编号 迁移 触发 关键点
(a) M → E writeback 写回 仍保留该 line 与修改权
(b) E → M 本 CPU store 不涉及任何 bus transaction
(c) M → I 收到 read invalidate 回 read response + invalidate ack
(d) I → M（原子 RMW） 发 read invalidate 必须收齐 read response 与全部 ack
(e) S → M（原子 RMW） 发 invalidate 收齐全部 ack 才完成
(f) M → S 收到 read 回 read response（可能伴随写回）
(g) E → S 收到 read 回 read response
(h) S → E 发 invalidate 收齐 ack；或他人自行驱逐 本 CPU 成为最后持有者
(i) M → I 他人对本 CPU 独占的 line 做原子 RMW 回 read response + ack
(j) I → M store 而 line 不在本 cache 发 read invalidate，收齐后经 (b) E→M
(k) I → S load miss 发 read
(l) S → I 被他人 invalidate 回 ack

原文的四 CPU 实例用了一个最小的 direct-mapped cache，address 0 与 address 8 落在同一个 set，因此每一步都在制造冲突。整条流水最后用 V / I 标记 memory 是否最新，值得照着推一遍：

text
CPU0 load  @0   → I→S，两 cache 都是 S，memory 仍 V
CPU3 load  @0   → 同上
CPU0 load  @8   → 同 set 冲突，shared 状态本地 invalidate 即可，不用通知别人
CPU2 load  @0   → 用 read invalidate，预取独占权；CPU3 的副本变 I，memory 仍 V
CPU2 store @0   → E→M，memory 变 I
CPU1 原子加 1   → read invalidate 从 CPU2 snoop 数据并 invalidate 它，CPU1 变 M，memory 仍 I
CPU1 load  @8   → 驱逐 address 0，触发 writeback，memory 的 addr0 恢复 V

四、store buffer：第一个乱序源头 #

4.1 为什么写会 stall #

CPU0 要写一条「在 CPU1 cache 里」的数据，必须先发 invalidate，等整条 bus transaction 完成才能真写。但问题是——CPU1 送回来的数据是什么根本无所谓，反正会被无条件覆盖。这是纯粹的无谓等待。

4.2 store buffer 的定位 #

项目 说明
位置 CPU 与 cache 之间
行为 CPU 把写放进 buffer 就继续执行；line 到位后数据从 buffer 进 cache
归属 per-CPU；硬件多线程下 per-core
访问性 一个 CPU 只能访问自己的 store buffer，看不到别人的
分工理由 buffer 提升连续写性能；CPU 间通信责任完全交给 cache-coherency 协议，硬件更简单

4.3 第一个坑：store forwarding #

c
a = 1;
b = a + 1;
assert(b == 2);

前置条件：a、b 初值 0；a 的 line 在 CPU1，b 的 line 在 CPU0。11 步走完 assert 失败：

  1. CPU0 执行 a = 1；
  2. cache miss；
  3. 发 read invalidate；
  4. 把 1 记进 store buffer；
  5. CPU1 回送 line 并清掉本地副本；
  6. CPU0 执行 b = a + 1；
  7. 收到 CPU1 的 line，其中 a 还是 0；
  8. 从 cache 载入 a = 0；
  9. 此时才把 store buffer 里的 1 应用到该 line；
  10. 0 + 1 = 1 存入 b；
  11. assert 失败，b == 1。

根因一句话：a 有两份副本，一份在 cache，一份在 store buffer。被破坏的保证是「每个 CPU 看自己的操作总是像按 program order 发生」。

修法叫 store forwarding：load 时同时查 cache 与 store buffer（snoop 自己的 store buffer），buffer 里有就用 buffer 的值。于是第 8 步读到 1，b == 2。

4.4 第二个坑：store-load 重排（经典案例） #

c
void foo(void) { a = 1; b = 1; }
void bar(void)  { while (b == 0) continue; assert(a == 1); }

前置：a、b 初值 0；a 的 line 只在 CPU1，b 的 line 由 CPU0 拥有。无屏障时的 9 步失败路径：

text
1  CPU0  a=1      miss → 值入 store buffer + 发 read invalidate
2  CPU1  while(b==0)  b miss → 发 read
3  CPU0  b=1      b 的 line 已在 M 或 E，直接写进 cache line
4  CPU0           收到 read，把【已更新的 b=1】回送，自身 b 转 S
5  CPU1           装入 b=1
6  CPU1           跳出循环
7  CPU1  assert(a==1)  本地还是旧值 → 失败
8         此时才收到 read invalidate，回送 a 并 invalidate
9         太晚

加上 smp_mb() 之后变成 18 步，机制是全文最有价值的部分：

  • smp_mb() 给当前 store buffer 中的所有项打上标记（marked entries）；
  • 此后来到的 store，即使在 M/E 状态、即使 line 已在本地，也必须进 store buffer 且是 unmarked（第 4 步）；
  • 于是第 5 步回送给 CPU1 的仍是旧值 b = 0，CPU1 继续 loop（第 7 步）；
  • marked entry 写完后（第 9 步），unmarked 的 b 才能进 cache line；但此时 b 的 line 是 S，于是要发 invalidate（第 11 步）；
  • 等 ack（第 14 步）转 E 之后才真正写入，再被 read 取走（第 15~17 步）；
  • 第 18 步 assert 时 a 已不在 CPU1 cache，需重新 read，取到 1，通过。

这就是屏障的真实语义：它不是「清空 store buffer」，而是「给已有项打标记，让之后的写不许插队」。 这一条能同时解释两件事：为什么屏障后性能必降，以及为什么读者一开始看到的还是旧值。

两种实现方式，原文并列给出：

  1. 直接 stall 到 store buffer 清空；
  2. 允许继续执行，但 store buffer 内严格按序提交——即便后来的 entry 对应 line 已 ready，也不能越过前面的 entry。

4.5 屏障之后为什么更慢 #

store buffer 必须很小（entry 数不多）。中等频率的 store（尤其全 miss）就能把它填满，CPU 又得等 invalidate 完成才能腾出空间。

而屏障之后情况更糟：一旦某个 entry 被 mark，其后所有 store 都必须等 invalidation 完成，不论是命中还是 miss。这是屏障性能代价的第二重来源。

五、invalidate queue：只加写侧屏障是不够的 #

5.1 为什么 ack 回得慢 #

invalidate ack 慢有两个原因：可能必须先真正完成 invalidate（本 CPU 正在密集 load/store 命中 cache，cache 忙）；短时间内大量 invalidate 会积压，把其他 CPU 一起拖住。

5.2 机制与它的「承诺」 #

收到 invalidate 时先入 invalidate queue 并立即回 ack，不必等真正失效完成。

代价是一个承诺：在处理完该 entry 之前，不发送任何涉及该 cache line 的 MESI 消息。所以本 CPU 要发某条 line 的 invalidate 前，必须先查自己的 invalidate queue，有相关 entry 就得等它处理完。

竞争不激烈时几乎无感，但它提供了新的乱序机会。

5.3 写侧屏障被「早回的 ack」吃掉 #

同一段代码，前置改成 a 在两个 CPU 都是 S 状态。10 步失败：

text
1  CPU0 a=1        S 状态 → 值入 store buffer + 发 invalidate（不是 read invalidate）
2  CPU1 读 b miss  → 发 read
3  CPU1           收到 invalidate，入队并立即回 ack
4  CPU0           收到 ack 就【越过 smp_mb()】，a 从 store buffer 进 cache，转 M
5  CPU0 b=1        b 在本地 M/E，直接入 cache line
6  CPU0           回送 b=1，b 转 S
7  CPU1           装入 b=1
8  CPU1           跳出循环
9  CPU1 assert(a==1)  本地 a 仍是旧值 0 → 失败
10        之后才处理队列里的 invalidate

结论很刺人：写侧的 smp_mb() 完全失效，因为读者 cache 里还留着旧副本。

5.4 修法：读侧也要屏障 #

c
void foo(void) { a = 1; smp_mb(); b = 1; }
void bar(void)  { while (b == 0) continue; smp_mb(); assert(a == 1); }

13 步的关键点：屏障执行时标记 invalidate queue 中现有的全部 entry，此后任何 load 都要等所有 marked entry 应用到 cache 之后才能进行。于是第 9 步 stall、第 10 步 a 被 invalidate、第 11 步重新发 read 得到 1、第 13 步 assert 通过。

六、三种屏障的准确语义与配对法则 #

屏障 标记什么 效果
read memory barrier 只标记 invalidate queue 屏障之前的 load 一定在屏障之后的任何 load 之前完成
write memory barrier 只标记 store buffer 屏障之前的 store 一定在屏障之后的任何 store 之前被看到
full memory barrier 两者都标记 同时约束 load 与 store

关键限定：以上三种只对执行屏障的那颗 CPU 有效。

6.1 为什么需要这么多「口味」 #

回头看那两节就明白了：第 4 节那个 foo() 根本不需要碰 invalidate queue，第 5 节那个 bar() 根本不需要碰 store buffer。各取所需，所以才有 rmb / wmb 之分。

6.2 配对法则（最重要的一条） #

搬运数据的 store 与读取数据的 load 之间，写侧屏障 + 读侧屏障缺一不可。

只做了一侧 后果
只有写侧 smp_wmb() / smp_mb() 读者 cache 有旧副本时失效（第 5 节）
只有读侧 写侧的 store 还躺在 store buffer 里没提交，读者可能看不到

还有一条：smp_read_barrier_depends() 用于「有数据依赖」的两个 load 之间（前一个 load 出地址，后一个 load 解引用）。除 Alpha 外全是空操作。

七、神话机器：为什么「正确使用屏障」也可能不够 #

7.1 五条规则 #

原文构造了一台「ordering-hostile」的理想机器，它必须服从：

  1. 每个 CPU 看自己的访存总是 program order；
  2. 只有当两个操作访问不同地址时，一个操作才能与一个 store 重排；
  3. 某 CPU 在 smp_rmb() 之前的所有 load，被所有 CPU 观察到早于该屏障之后的所有 load；
  4. 某 CPU 在 smp_wmb() 之前的所有 store，被所有 CPU 观察到早于该屏障之后的所有 store；
  5. 某 CPU 在 smp_mb() 之前的所有访问（load + store），被所有 CPU 观察到早于屏障之后的任何访问。

7.2 硬件模型：NUCA + per-CPU message queue #

non-uniform cache architecture（NUCA）；为了在节点内各 CPU 之间公平分配 interconnect 带宽，在 node 与 interconnect 的接口处放一组 per-CPU message queue。

后果很要命：单个 CPU 内部的顺序仍受自己的屏障约束，但一对 CPU 之间的相对顺序可以被严重重排。

7.3 Example 1：wmb 提供不了传递性 #

c
// CPU0            // CPU1            // CPU2
a = 1;             while (b == 0);    z = c;
smp_wmb();         c = 1;             smp_rmb();
b = 1;                                x = a;
                                      assert(z == 0 || x == 1);

失败设定：CPU0 近期大量 cache miss，它的 message queue 满了；CPU1 一直全 cache 命中（line 为 E），它的 queue 是空的。于是 CPU0 的 a、b 已进 Node0 cache（Node0 内的 CPU1 看得见），但通知其他 node 的消息堵在队列里；CPU1 的 c = 1 反而「轻舟已过万重山」。

结果：CPU2 先看到 c = 1、后看到 a = 1 → z == 1 且 x == 0 → assert 触发，尽管用了屏障。

7.4 Example 2：mb 也提供不了传递性 #

c
// CPU0            // CPU1                      // CPU2
a = 1;             while (a == 0);             y = b;
                   smp_mb();                   smp_rmb();
                   b = 1;                      x = a;
                                               assert(y == 0 || x == 1);

同样的「queue 满 / queue 空」设定下，CPU2 可能看到 y == 1 && x == 0。

原文的评语最危险：这个 assert 「works on most mainstream computer systems」——理论上是不可移植的依赖，实际上大多数机器上能跑。这类代码是最难发现的定时炸弹。

7.5 Example 3：为什么这一版的 assert 不会触发 #

代码在原文的 Figure 里，正文只留了文字推演。可还原的逻辑是：CPU0 执行 a = 1 → smp_wmb() → b = 1；CPU1、CPU2 各自 while 等 b，等到后执行 smp_mb()；CPU0 后面再执行一次 smp_mb()，然后赋 e。

  • CPU1 / CPU2 在看到 b = 1 之前无法越过自己那道 mb；
  • 执行完 mb 之后，二者保证看得到 CPU0 在 wmb 之前的全部赋值；
  • CPU0 后面那次 mb 与 CPU1 / CPU2 的 mb 配对，保证 CPU0 不会在 a 对二者可见之前去做后面的赋值；
  • 于是 CPU2 的 assert 保证不触发。

教学点：Example 1 / 2 失败、Example 3 成功，差别不在「屏障多了」，而在屏障是否在「信号量」这条共享变量两侧真正成对出现（release / acquire 配对）。

八、各架构的屏障指令 #

8.1 Linux 的最小公分母原语 #

原语 语义 备注
smp_mb() 排序 load + store SMP 内核生成指令；UP 下退化成编译器屏障
smp_rmb() 只排序 load 同上
smp_wmb() 只排序 store 同上
smp_read_barrier_depends() 排序有数据依赖的前后操作 除 Alpha 外全是空操作
mmiowb() 约束被 global spinlock 保护的 MMIO 写顺序 部分 IA64 / FRV / MIPS / SH 上非空
mb() / rmb() / wmb() UP 版本，UP 内核也生成真实指令 驱动必需

两件容易忽略的事：

  • smp_mb/rmb/wmb 同时阻止编译器跨越屏障重排（隐含 barrier() 的作用）；
  • 所有内核锁原语（spinlock、rwlock、semaphore、RCU…）都已内含所需屏障，用它们时不必再想屏障。

原语命名来自 Alpha 指令（mb / rmb / wmb），这是历史遗留。

这两组的分工也很实用：smp_* 在 UP 内核里只留下编译器屏障，而 mb/rmb/wmb 在 UP 下也发真实指令。原因很直白——驱动的 MMIO 顺序在单核上同样要保，否则「轻则设备行为异常、内核 crash，重则损伤硬件」。

8.2 Alpha：最弱，定义了语义下限 #

c
struct el *insert(long key, long data)
{
    struct el *p = kmalloc(sizeof(*p), GFP_ATOMIC);
    spin_lock(&mutex);
    p->next = head.next;
    p->key  = key;
    p->data = data;
    smp_wmb();
    head.next = p;
    spin_unlock(&mutex);
}

struct el *search(long key)
{
    struct el *p = head.next;
    while (p != &head) {
        /* BUG ON ALPHA!!! */
        if (p->key == key) return p;
        p = p->next;
    }
    return NULL;
}

Alpha 上 p->key 的读可能看到初始化前的旧垃圾值，尽管插入了 smp_wmb()。

机理：partitioned cache，交替 cache line 由不同 bank 处理（比如 head 在 bank0、新元素在 bank1）。smp_wmb() 只保证「分配新元素时产生的 invalidate 消息」先于「发布 head.next 的 invalidate 消息」到达 interconnect，完全不保证新值到达读者 core 的顺序。若读者 bank1 忙、bank0 闲，元素数据的 invalidate 被延迟 → 看到新指针 + 旧元素数据。

修法：在指针 fetch 与解引用之间加 smp_read_barrier_depends()。用 smp_rmb() 也能修，但会给 i386、IA64、PPC、SPARC 带来不必要开销（这些 CPU 读侧本来就尊重数据依赖），所以 2.6 才引入这个专门原语。

曾考虑过的软件方案是向所有 CPU 发 IPI，收到者执行 memory-barrier 指令（「memory-barrier shootdown」）。但它需要额外的防死锁逻辑，对 Alpha 这类极弱模型开销过大，被社区否决。

Alpha 是唯一把 smp_read_barrier_depends() 定义成 smp_mb() 的架构。

8.3 ARM：DMB / DSB / ISB #

指令 官方语义 通俗说
DMB（data memory barrier） 使指定类型的操作在任何后续同类型操作之前「看起来已完成」（appear to have completed） 拦一下
DSB（data synchronization barrier） 使指定类型的操作真正完成（actually complete）之后，才执行任何后续操作（任意类型） 等到位
ISB（instruction synchronization barrier） flush 流水线，ISB 之后的指令只在 ISB 完成后才取指 整条流水线重来

强度阶梯是 DMB < DSB < ISB，通俗比喻：DMB 只是「看起来」、DSB 像原子弹、ISB 像氢弹。

几个历史细节：

  • DSB 早期叫 DWB（「drain write buffer」或「data write barrier」），但这个名字不够准确——它要同步的包括 cache、TLB、分支预测以及显式的 load/store，所以改名 DSB 更贴切。
  • ARM 上的 rmb() 没有精确对应，只能用全功能 DMB（等同于 mb()）实现。这是 ARM 上读屏障比写屏障贵的根本原因。
  • DMB / DSB 的 before / after 定义是递归的，效果类似 POWER 的 cumulativity。
  • ISB 的典型用途是自修改代码（JIT）：生成代码与执行之间必须插一条 ISB，否则可能执行到指令 cache 里的旧内容。

8.4 DMB / DSB 的两个参数 #

DMB 和 DSB 都带两个参数：shareability domain + access type。

access type：

选项 约束范围 对应 Linux
sy（full system，默认） load + store 全约束 mb()
st 只约束 store wmb()
ld 只约束 load rmb()

shareability domain：

后缀 域 用在什么场景
nsh non-shareable（单处理器内部） 单核内部与外设
ish inner shareable（一个 SMP cluster） 内核最常用：dmb ish
osh outer shareable（跨 cluster / 到外设） DMA 与设备
sy full system 最保守

拼起来就是常见的四类写法：

text
dmb ish      内核里 smp_mb() 的实体，最常用
dmb ishst    只约束 store（release 语义）
dmb ishld    只约束 load（acquire 语义）
dsb sy       最重，改页表 / 改 MMU 相关寄存器后必用
isb          无域参数，改 system register 或自修改代码后用

注意 ISB 不接受域后缀——它作用于本核的流水线，本来就没有「跨核」的概念。

8.5 ARMv8 的 acquire / release 指令 #

ARMv8 引入了带内存序语义的访存指令，比「ldr + dmb」更省：

指令 语义 对应 Linux
LDAR load-acquire smp_load_acquire()
STLR store-release smp_store_release()
LDAPR 更弱的 acquire（ARMv8.3，只保证读到最新值，不建立完整 acquire 序） smp_load_acquire() 的弱化版
LDXR / STXR exclusive load/store，用于 LL/SC cmpxchg 系列
LDAXR / STLXR 带 acquire/release 的 exclusive 原子 RMW 的 acquire/release 版

用 STLR 发布、用 LDAR 获取，是 ARMv8 里唯一不需要额外 DMB 的配对方式。

8.6 ARM 的控制依赖：一条容易踩的不对称规则 #

c
r1 = x;
if (r1 == 0) nop();
y = 1;
r2 = z;
ISB();
r3 = z;
依赖类型 是否被尊重
load → store 的控制依赖 是（第 1 行的 load x 一定排在第 4 行的 store y 之前，效果类似 smp_mb）
load → load 的控制依赖 不是（第 5 行的 load z 可能先于第 1 行执行）

要补第 7 行的 r3 = z，靠「第 2 行条件分支 + 第 6 行 ISB」的组合就够；要连第 5 行也约束住，得在第 3 行与第 4 行之间再插一条 ISB。

这条不对称规则是 ARM 上最反直觉的地方之一：分支能挡住 store，挡不住 load。

8.7 其他架构一句话 #

架构 屏障指令 备注
IA64 mf（memory fence） 另有 acq / rel 半屏障：acq 禁止后面的访存跑到前面，允许前面的跑到后面；rel 反之
PA-RISC 无 架构允许全重排，但实际 CPU 完全有序，Linux 在此生成零代码，只用 gcc 的 memory attribute 挡编译器
x86 / POWER / SPARC / zSeries 见各架构手册 原文这几节整节标 TODO 未翻译

IA64 有个概念值得记住：它为 release 操作（含 mf）提供全局全序，这就是 transitivity（传递性）——若某段代码「看到」某次访问已发生，则更晚的代码段也会看到它已发生，前提是所有相关代码段都正确用了屏障。

原文译者在这一段直接标注「这段不是非常理解，TODO」。而 Example 1 / 2 又证明 smp_mb 不提供跨 CPU 传递性——这两处需要调和。现代表述是：smp_mb() 提供 A-cumulative + B-cumulative 的全局序，但缺少配对时不给跨线程传递性。

九、编译器重排：另一半战场 #

9.1 编译器只保证单线程语义 #

编译器假设代码是单线程的，在不改变单线程行为的前提下重排指令（as-if 规则的具体体现）。它不知道哪些代码需要 thread-safe，这个信息只有你有。

9.2 第一个实验：写入顺序被反转 #

c
a = b + 1;
b = 0;

用 aarch64-linux-gnu-gcc + objdump 看：

armasm
@ -O0，严格 program order
ldr  w0, [x0]        // load b
add  w1, w0, #0x1
str  w1, [x0]        // a = b + 1
str  wzr, [x0]       // b = 0

armasm
@ -O2，写入顺序与 program order 相反
ldr  w2, [x0]        // load b
str  wzr, [x0]       // b = 0      <-- 提前了
add  w0, w2, #0x1
str  w0, [x1]        // a = b + 1

等价的 C 写法是 register int reg = b; b = 0; a = reg + 1;。单线程下结果仍是 a == 1 && b == 0，所以编译器这么做完全合法。

9.3 什么时候会出事：flag / data 发布模式 #

c
int flag, data;
void write_data(int value) { data = value; flag = 1; }

若编译器让 flag = 1 先落地，即使在单核上也会出事：flag 置 1 之后、data 写 45 之前发生抢占，另一个进程见 flag == 1 就认为 data 就绪，实际读到旧值。

编译器不知道 data 与 flag 的依赖关系是人加强加的。

9.4 barrier() 的语义 #

c
#define barrier() __asm__ __volatile__("": : :"memory")

三句话把它讲全：

  1. 告诉编译器内存中的值已改变，之前缓存到寄存器的内存值全部作废；
  2. barrier() 之后的访存必须重新从内存 load，不能用寄存器缓存值；
  3. 阻止编译器把屏障前的 load/store 移到屏障后，也阻止屏障后的 load/store 移到屏障前。

插入后 -O2 恢复 program order：

armasm
ldr  w2, [x0]
add  w2, w2, #0x1
str  w2, [x1]        // a = b + 1
str  wzr, [x0]       // b = 0

9.5 隐式屏障的三个坑 #

情形 是不是屏障
含 barrier() 的函数 是，即使该函数被 inline
普通函数调用 多数情况表现为屏障，但被 inline 且内部不含 barrier() 时就不是
外部函数（如 printf） 副作用比 compiler barrier 更强——编译器不知道它干了什么，必须忘掉所有内存假设

外部函数为什么更强，看这个例子：

c
void foo(void) { a = 5; printf("smcdef"); b = a; }

armasm
@ -O2
mov  w2, #0x5
str  w2, [x19]        // a = 5（printf 之前必须落地）
bl   640 <__printf_chk@plt>
ldr  w1, [x19]        // 重新 load a（不知 printf 是否改过 a）
str  w1, [x0]         // b = a

结论：需要屏障时必须显式写 barrier()，不能依赖函数调用附带的隐式屏障——没人保证调用不被 inline。

9.6 第二个妙用：自旋等全局变量（实测对照最有说服力） #

c
int run = 1;
void foo(void) { while (run) ; }

无 barrier：编译器把 run 提升到寄存器，变成死循环。

armasm
748: adrp  x0, 10000
74c: f947e800  ldr x0, [x0, #4048]
750: b9400000  ldr w0, [x0]        // load run 到 w0
754: d503201f  nop
758: 35000000  cbnz w0, 758 <foo+0x10>   // if (w0) while(1);
75c: d65f03c0  ret

等价 C 就是 register int reg = run; if (reg) while (1) ;——判断只做一次。

加 barrier() 后每次迭代重新 load，能退出：

armasm
748: adrp  x0, 10000
74c: f947e800  ldr x0, [x0, #4048]
750: b9400001  ldr w1, [x0]
754: 34000061  cbz w1, 760 <foo+0x18>
758: b9400001  ldr w1, [x0]        // 每轮重载
75c: 35ffffe1  cbnz w1, 758 <foo+0x10>
760: d65f03c0  ret

9.7 三种正解写法 #

写法 实质
cpu_relax() ARM64 上定义为 asm volatile("yield" ::: "memory")——在 barrier 基础上再插一条 yield。内核自旋等全局变量时应在循环体里调用
READ_ONCE(run) 等价于 while (*(volatile int *)&run)
volatile int run 直接声明

另外记住一句：CPU 屏障指令本身也会阻止编译器重排，所以 smp_mb() 之类的宏不需要再套一层 barrier()。

十、给硬件设计者的六个坑（原文最后一章） #

这一节是写给硬件工程师的，但做驱动的人更该读，因为踩坑的是软件。

# 坑 后果
1 I/O 设备忽略 cache coherence DMA 读 buffer 可能读不到 cache 里的最新值；DMA 写回的可能被 CPU cache 内容覆盖。必须在交给设备前 flush、DMA 完成后再次 flush
2 外部总线不传 coherence 信息 更惨的变体，一组设备甚至 memory 本身都不遵守一致性
3 设备中断忽略 coherence split cache 的一个 bank 极忙、仍持有输入 buffer 的最后一个 cacheline，I/O 完成中断到达 → 读到旧数据 → 数据损坏，且在事后 crash dump 里看不见（等 dump 时 DMA 早已完成）
4 IPI 忽略 coherence IPI 必须先等 message buffer 的 cache line 全部提交到内存，才能送达目标 CPU
5 上下文切换抢在 coherence 之前 task 从一核迁到另一核，源核可见的访存没到目标核 → 同一变量「先读到新值、再读到旧值」，任何算法都扛不住
6 过分友善的模拟器 / 仿真器 难以模拟重排，仿真下正常的软件上真机必翻车

第 5 条值得单独记住：「同一变量先读到新值、再读到旧值」不是代码 bug，是迁移时序 bug。看到这种现场先查调度与 barriers，别查自己的循环。

十一、屏障会消失吗 #

这一章原文自己给了正反双方，结论只有一句：「We have no clue.」

立场 论据
会消失 海量硬件线程（几十/几百/几千），单线程等内存时别的线程继续跑，CPU 利用率不缺；或靠复杂 latency-hiding 硬件制造「完全顺序一致」的假象
不会消失 能扩展到上千线程的应用极少；实时性要求已到几十微秒量级，海量多线程下单线程吞吐极低，更难过实时约束；功耗与环保压力

十二、速查表 #

现象 / 需求 首先查
标志位发布了但数据是旧的 写侧缺 release 屏障，或读侧缺 acquire 屏障（第 5 节）
单核上偶尔也错 是编译器重排，加 barrier() 或改用 READ_ONCE
屏障加了还是错 检查是否只有一侧有屏障；是否依赖了传递性（Example 1/2）
屏障后性能暴跌 正常：一旦 store buffer 有条目被标记，其后 store 全要等 invalidation
想只挡 load dmb ishld 或 smp_rmb()（注意 ARM 上 rmb() 会退化成全 DMB）
想只挡 store dmb ishst 或 smp_wmb()
改完页表必须做什么 改描述符 → DSB → TLBI → DSB → ISB
改完 system register ISB（如 SCTLR / TCR / VBAR）
自修改代码不生效 生成码之后补 ISB
分支能挡住后续 store，挡不住后续 load 正常，ARM 的 load-load 控制依赖不被尊重（第 8.6 节）
DMA 数据不对 传输前 clean、传输后 invalidate；写回策略下主存可能是旧值

小结 #

  • 乱序有两个源头：硬件的 store buffer / invalidate queue 与 编译器，各用各的手段。
  • smp_mb() 的真实语义是「给 store buffer 打标记」，不是「清空 buffer」；这也解释了它的性能代价。
  • 写侧屏障 + 读侧屏障必须配对，只做一侧一定在某些时序下失效。
  • 屏障不提供跨 CPU 传递性；能传递是因为在共享变量两侧形成了 release / acquire 配对。
  • ARM 三件套：DMB 看起来完成、DSB 真正完成、ISB 冲刷流水线；rmb() 在 ARM 上要退化成全 DMB。
  • ARMv8 用 STLR 发布、LDAR 获取，是唯一不需要额外 DMB 的配对。
  • 控制依赖在 ARM 上挡 store 不挡 load，这是最容易误判的一条。
  • 编译器屏障与 CPU 屏障互不替代；函数调用带来的隐式屏障在被 inline 后可能消失。
