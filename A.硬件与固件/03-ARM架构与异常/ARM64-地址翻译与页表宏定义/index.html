零、先把两套页表格式分开 #

ARM 有两套完全不同的页表硬件格式，混在一起看必然糊涂：

AArch32（ARMv7） AArch64（ARMv8）
描述符宽度 4 字节 8 字节
描述符类型 短描述符（short descriptor） 长描述符（long descriptor）
顶层寄存器 TTBR0 / TTBR1 + TTBCR TTBR0_EL1 / TTBR1_EL1 + TCR_EL1
权限控制 Domain + DACR 无 Domain，全在描述符的 AP 位
大块映射叫法 section（1MB，0b10） block（最大 1GB，0b01）
页表级数 固定 2 级 2 ~ 4 级，由 CONFIG_PGTABLE_LEVELS 决定

所以在 0x3f000de2 这种值上讨论 bits[1:0] 的「section」，和在 PTE_TYPE_PAGE 上讨论的「page descriptor」，不是同一套规则。本篇主线是 AArch64；ARMv7 那套放在第十一节做对照实验。

一、translation regimes：地址翻译的四条通道 #

ARM64 把「谁在翻译、翻哪一段」拆成了若干个 translation regime，每个 regime 是一行独立的翻译流：

text
Secure EL3     VA  ---  Secure EL3 stage 1        ----------> PA（Secure 或 Non-secure）
Secure EL1&0   VA  ---  Secure EL1&0 stage 1      ----------> PA（Secure 或 Non-secure）
Non-Secure EL2 VA  ---  Non-Secure EL2 stage 1    ----------> PA（只能 Non-secure）
Non-Secure EL1&0   VA  -- stage 1 --> IPA -- stage 2 --> PA（只能 Non-secure）

三条结论：

  1. 一个 regime 可能只有 1 个 stage，也可能有 2 个 stage。全系统只有 Non-Secure EL1&0 是两级的——这正是虚拟化的落脚点：guest OS 管 stage 1（VA→IPA），hypervisor 管 stage 2（IPA→PA）。
  2. 每个 EL 有自己的一套页表基址寄存器与控制寄存器，互不干扰。
  3. 每个 stage 的页表可以独立 enable / disable。虚拟机创建时建 stage 2 页表，销毁时回收，这块内存还归 hypervisor。

二、三种地址：VA / IPA / PA #

类型 谁产生 由谁翻译 典型用途
VA（Virtual Address） 程序、编译器、链接器 MMU 的 stage 1 PC、LR、SP、ELR 里放的全是 VA
IPA（Intermediate Physical Address，也叫 PA of guest） guest 眼里它就是「物理地址」 hypervisor 的 stage 2 虚拟机场景
PA（Physical Address） — 不翻译，直接上线 总线上的地址信号

还有一个常被忽略的点：同一个 PA 数值，在 Secure world 和 Normal world 里是两个不同的存储单元。PA 只是「哪个世界的总线地址」，不是全局唯一的存储标识。

另外，看 x86 资料转过来时要做名词替换：x86 的 Linear Address 在 ARM64 语境下应读作 VA 或 IPA；x86 的 cr3 对应 ARM64 的 TTBRx。

三、页表级数是怎么算出来的 #

3.1 每级切走多少位 #

推导只有三步：

  1. 地址最低的 PAGE_SHIFT 位是页内偏移，不参与页表索引。
  2. 一张 translation table 占一页；ARM64 描述符 8 字节，所以一张表能放 2^(PAGE_SHIFT-3) 个 entry。
  3. 因此「一级能索引多少位」= PAGE_SHIFT - 3。

于是：

c
levels = DIV_ROUND_UP(va_bits - PAGE_SHIFT, PAGE_SHIFT - 3)
/* 展开成整数运算 */
       = ((va_bits - PAGE_SHIFT) + (PAGE_SHIFT - 3) - 1) / (PAGE_SHIFT - 3)

/* 内核里的最终形态 */
#define ARM64_HW_PGTABLE_LEVELS(va_bits) (((va_bits) - 4) / (PAGE_SHIFT - 3))

那个神秘的 4 不是「4 级」的意思，它是上面那串化简的残项；真正的物理常数是 3——来自「描述符 8 字节 = 2³」。看清这一点，公式就不用背了。

3.2 三种 page size 的实测参数 #

VA 都是 48 位：

Page Size PAGE_SHIFT offset 位 每级 index 位 每表 entry 数 级数
4 KB 12 12 9 512 4
16 KB 14 14 11 2048 4
64 KB 16 16 13 8192 3

代进公式核对：

  • 4K：(48-4)/9 = 44/9 = 4（整数除法）
  • 16K：(48-4)/11 = 4
  • 64K：(48-4)/13 = 44/13 = 3

3.3 64K 页的特例：PGD 与 PUD 重合 #

64K、48 位 VA、3 级时，顶层表不是 L0 而是 L1，于是 PGD 和 PUD 指同一张表。更细的一点：

c
#define PGDIR_SHIFT   ARM64_HW_PGTABLE_LEVEL_SHIFT(4 - CONFIG_PGTABLE_LEVELS)
#define PTRS_PER_PGD  (1 << (VA_BITS - PGDIR_SHIFT))
/* 64K / 3 级：PGDIR_SHIFT = ((16-3)*3) + 3 = 42 */
/* PTRS_PER_PGD = 1 << (48 - 42) = 64 */

所以 64K 页时顶层表虽然有 8192 个 entry 的位置，只有前 64 个是有效的。

四、各级 SHIFT 宏 #

c
#define ARM64_HW_PGTABLE_LEVEL_SHIFT(n) ((PAGE_SHIFT - 3) * (4 - (n)) + 3)

第 n 级（0 起算）的 shift，等于「它下面还有 4-n 级索引 + 页内偏移」。4K 页时 PAGE_SHIFT-3 = 9：

Level 内核宏 展开 4K/48bit 实值 符号意义上覆盖
L0 PGDIR_SHIFT 9*(4-0)+3 39 512 GB
L1 PUD_SHIFT 9*(4-1)+3 30 1 GB
L2 PMD_SHIFT 9*(4-2)+3 21 2 MB
L3 页内 offset — 12 4 KB

每级吃 9 位：[47:39] / [38:30] / [29:21] / [20:12]，最后 [11:0] 是偏移。这五段的切分图，是理解 ARM64 地址翻译的全部核心。

注意 PGDIR_SHIFT 的参数是 4 - CONFIG_PGTABLE_LEVELS，而不是写死的 0。意思是顶层表可能是 L0、L1、L2 三者之一，取决于配置级数：

配置级数 顶层表是 映射链
4 L0 PGD(L0) → PUD(L1) → PMD(L2) → Page table(L3) → page
3 L1 PGD(L1) → PMD(L2) → Page table(L3) → page
2 L2 PGD(L2) → Page table(L3) → page

五、size / mask / PTRS_PER_xxx #

c
#ifdef CONFIG_ARM64_64K_PAGES
#define PAGE_SHIFT  16
#elif defined(CONFIG_ARM64_16K_PAGES)
#define PAGE_SHIFT  14
#else
#define PAGE_SHIFT  12
#endif
#define PAGE_SIZE   (_AC(1, UL) << PAGE_SHIFT)
#define PAGE_MASK   (~(PAGE_SIZE - 1))

PMD 层是有条件的：

c
#if CONFIG_PGTABLE_LEVELS > 2
#define PMD_SHIFT     ARM64_HW_PGTABLE_LEVEL_SHIFT(2)
#define PMD_SIZE      (_AC(1, UL) << PMD_SHIFT)
#define PMD_MASK      (~(PMD_SIZE - 1))
#define PTRS_PER_PMD  PTRS_PER_PTE
#else
#define PMD_SHIFT     PUD_SHIFT
#define PTRS_PER_PMD  1
#define PMD_SIZE      (1UL << PMD_SHIFT)
#endif

PTRS_PER_PMD = 1 是「降级」的写法：级数不够时，这一级退化成上一层的一部分，一个 entry 直接对应整个上一级范围。PUD 同理（CONFIG_PGTABLE_LEVELS > 3 时才有真正的 PUD）。

几个量的含义：

  • PTRS_PER_PTE = 1 << (PAGE_SHIFT - 3)，PMD/PUD 都与之相等——因为所有表都是「一页、每项 8 字节」。
  • PGDIR_SIZE = TTBR 指向的顶层表里一个描述符覆盖的地址范围。
  • PTRS_PER_PGD 取决于 «global dir bits» 的长度 = VA_BITS - PGDIR_SHIFT。

六、描述符格式与合法性判定 #

四个类型的 t 都是 U64：

c
typedef u64 pte_t, pmd_t, pud_t, pgd_t;
typedef u64 pgprot_t;   /* 只用来装 flag 域 */

一个描述符只能是四种形态之一：table descriptor（指向下一级表）、page descriptor（指向一个 page）、block descriptor（指向一大块）、无效描述符。

6.1 L0 / L1 / L2：只有 block 和 table #

c
#define PUD_TYPE_TABLE   (_AT(pudval_t, 3) << 0)   /* 0b11 */
#define PUD_TABLE_BIT    (_AT(pgdval_t, 1) << 1)
#define PUD_TYPE_MASK    (_AT(pgdval_t, 3) << 0)
#define PUD_TYPE_SECT    (_AT(pgdval_t, 1) << 0)   /* 0b01 */

判定规则只有两条位：bit0 = 有效位，bit1 = 类型位。

bits[1:0] 含义
0b00 / 0b10 无效（fault）
0b01 block descriptor（大块映射）
0b11 table descriptor（指向下一级表）

L0 / L1 / L2 上的描述符不可能是 page descriptor——因为 page 只在最后一级。

6.2 L3：只有 page #

c
#define PTE_TYPE_MASK   (_AT(pteval_t, 3) << 0)
#define PTE_TYPE_FAULT  (_AT(pteval_t, 0) << 0)   /* 0b00 */
#define PTE_TYPE_PAGE   (_AT(pteval_t, 3) << 0)   /* 0b11 */
#define PTE_TABLE_BIT   (_AT(pteval_t, 1) << 1)

L3 上 0b01 是 reserved，不是 block。这是一个从 AArch32 转过来最容易踩的差异——ARMv7 的 0b01 是 coarse page table、0b10 是 section，而 ARM64 的 0b01 在 L3 什么都不是。

七、section / block 映射 #

c
#define SECTION_SHIFT  PMD_SHIFT
#define SECTION_SIZE   (_AC(1, UL) << SECTION_SHIFT)
#define SECTION_MASK   (~(SECTION_SIZE - 1))

「section」是 ARM 手册里 block 的旧称，内核代码沿用了这个老名字。4K/48bit 下：

  • SECTION_SHIFT = PMD_SHIFT = 21
  • SECTION_SIZE = 2 MB

做法是让 L2 的 entry 直接指向一块 2MB 物理内存，而不是再往下指一张表。动机很直白：省一次 TLB miss、少一级 walk，TLB 命中率提高。内核 image 这种「一大片连续、属性相同」的区域最适合这么映射。

八、48 位 VA 的地址空间划分 #

把 48 位 VA 摊开，最高 16 位决定「走哪个 TTBR」：

text
  63    48 47                  0
  +-------+--------------------+
  | 全 0  |   TTBR0 管这一段    |  --> [0x0000_0000_0000_0000, 0x0000_FFFF_FFFF_FFFF]
  +-------+--------------------+
  | 全 1  |   TTBR1 管这一段    |  --> [0xFFFF_0000_0000_0000, 0xFFFF_FFFF_FFFF_FFFF]
  +-------+--------------------+
  中间（最高 16 位既非全 0 也非全 1）--> 无效，访问即 fault

所以 48 位 VA 实际只有两段合法区间，中间是空的。内核把 user space 放低段（TTBR0）、kernel space 放高段（TTBR1），进程切换只换 TTBR0，内核那份映射不用动——这是 ARM64 相比 ARMv7「user/kernel 靠 3G 分界」的一大改进。

九、TCR_EL1 与 TTBRx_EL1 #

TCR_EL1 决定「MMU 的输入地址有多宽、页表怎么走」：

字段 作用 常见值
T0SZ / T1SZ TTBR0 / TTBR1 覆盖的 VA 位宽（VA_BITS = 64 - T0SZ） 16 → 48 位
TG0 / TG1 页粒度（0b00=4K、0b01=64K、0b10=16K） 随 PAGE_SHIFT
IPS 物理地址位宽（0b000=32 bit … 0b101=48 bit） 看 SoC
EPD0 / EPD1 关掉某一边的 walk（1=disable） 通常 0
SH0 / SH1 页表 walk 的 shareability（00 非共享、10 内共享、11 外共享） 11
ORGN0/1、IRGN0/1 页表 walk 的内/外层 cache 属性 01=WBWA

TTBRx_EL1 的低位里有两个容易漏的域：ASID（地址空间标识，进程切换时避免刷 TLB）和 CnP（Common not Private）。

这里有个「性能陷阱级」的细节：SH/ORGN/IRGN 决定的是页表遍历本身的 cache 属性。配错了功能照样跑得通，只是每次 walk 都去读内存，性能断崖式下跌，而且很难从现象反推原因。

十、MAIR_EL1：8 个 AttrIndx 与内存属性 #

描述符里没有「这是 normal 还是 device 内存」的完整编码，只有一个 3 bit 的 AttrIndx（[4:2]），真正的属性表放在 MAIR_EL1：

text
MAIR_EL1 被切成 8 个字节，每个字节是一种属性，AttrIndx 就是字节下标：
  attr0 -> bits[7:0]     normal, WBWA         0xFF
  attr1 -> bits[15:8]    normal, non-cacheable 0x44
  attr2 -> bits[23:16]   device-nGnRE         0x04
  attr3 -> bits[31:24]   device-nGnRnE        0x00
  ...

normal 内存的高 4 位是 outer 属性、低 4 位是 inner 属性：0b1111 = Write-Back Write-Allocate。device 用 0b0000 / 0b0100 这类值，其中 nGnRnE 最严格（不做任何合并、重排、early ack）。

写驱动时如果发现「寄存器读出来是旧值」「两次写被合并成一次」，问题往往在这里——不是代码写错了，而是这段地址被映射成了 normal cacheable。

十一、rpi2 裸机 MMU 实验：手工填一张页表 #

下面这套是 ARMv7 短描述符（Cortex-A7），放在这里是因为它能让你看见「页表项就是一个 32 位整数」这件事。

11.1 环境 #

c
#define PHYSICAL_IO_ADDR  0x3F000000   /* BCM2836 外设基址，注意不是 rpi1 的 0x20000000 */
#define VIRTUAL_IO_ADDR   0xC8000000
translation table base : 0x30700000

rpi2 的 1GB RAM 是 0x00000000 ~ 0x40000000，DDR 做一对一映射（地址 0 翻完还是 0）。顺带一句：不是所有 SoC 的 1GB 都从 0 起算，有的从 0x10000000 起，裸机移植必须核实。

11.2 实测打印 #

text
0 (IO) ## pte_addr: 30703200, pte: 3f000de2
1 (IO) ## pte_addr: 30703204, pte: 3f100de2
2 (IO) ## pte_addr: 30703208, pte: 3f200de2

pte_addr 是怎么来的？这一句原文没写，但必须看懂：

text
0xC8000000 >> 20 = 0xC80 = 3200        （取 1MB section 的索引）
3200 * 4        = 0x3200               （每项 4 字节）
0x30700000 + 0x3200 = 0x30703200       （表基址 + 偏移）

三个 entry 分别对应 VA 0xC8000000 / 0xC8100000 / 0xC8200000 → PA 0x3F000000 / 0x3F100000 / 0x3F200000。整张表里只为这 3MB IO 区建了描述符。

11.3 逐位拆 0x3F000DE2 #

text
0x3F000DE2 = 0011 1111 0000 0000 0000 1101 1110 0010
             |         |    |  | || |  | |   |   |
             |         |    |  | || |  | |   |   +-- bits[1:0] = 10 -> 1MB section

bits[31:20] = 0x3F000     section base -> PA 0x3F000000（1MB 对齐）
bits[19:12] = 0x0         nG=0（global）、S=0、AP2=0、TEX[14:12]=000
bits[11:10] = 0b11        AP = 特权/用户全模式 read/write
bit[9]      = 0           IMPP，实现相关，忽略
bits[8:5]   = 0b1111      Domain = 15
bit[4]      = 0           XN = 0（这一段可执行）
bits[3:2]   = 0b00        C=0, B=0 -> Strongly-ordered

Domain=15 必须和 DACR = 0x55555555（每个 domain 都是 0b01 client）成对看，否则权限判定会出乎意料。

11.4 生成描述符的那段汇编 #

armasm
        LDR   r0, =||Image$$TTB$$ZI$$Base||
        LDR   r1, =0xFFF                        ; 4095
        LDR   r2, =2_00000000000000000000110111100010   ; 低 20 位模板 = 0x0DE2
init_ttb_1
        ORR   r3, r2, r1, LSL #20               ; 拼上 section base
        ORR   r3, r3, #2_0000000010000          ; 置 bit4 = XN
        STR   r3, [r0, r1, LSL #2]              ; 表基址 + 索引*4
        SUBS  r1, r1, #1
        BPL   init_ttb_1

循环 0xFFF → 0 共 4096 个 entry，覆盖整个 4GB 空间（flat translation table），写入方向是从 0x3FFC 递减到 0x0。

然后把代码段所在的 1MB 单独改成可 cache：

armasm
        LDR   r1, =||Image$$VECTORS$$Base||
        LSR   r1, #20                           ; 按 1MB 对齐取索引
        ORR   r3, r2, r1, LSL #20
        ORR   r3, r3, #2_0000000001100          ; CB bits[3:2] = 11
        ORR   r3, r3, #2_1000000000000          ; TEX[14:12] = 001
        STR   r3, [r0, r1, LSL #2]

TEX=001 + CB=11 = Outer & Inner write-back, write-allocate normal memory；其余 4095 项仍是 strongly-ordered。

注意一处矛盾：汇编里 ORR ..., #0x10 置了 XN，按此逻辑应打印 0x3f000df2，但实测打印的是 0x3f000de2（XN=0）。说明打印来自未置 XN 的那版代码，或该行是后来加的。复现时要说明这一点。

11.5 怎么证明 MMU 真的生效了 #

这是整个实验最漂亮的设计：同一个 UART，两次访问用不同地址。

text
物理：0x3F000000 + 0x215040 = 0x3F215040   AUX_MU_IO_REG（写字符）
物理：0x3F000000 + 0x215054 = 0x3F215054   AUX_MU_LSR_REG（& 0x20 判 TX empty）
虚拟：0xC8000000 + 0x215040/0x215054 = 0xC8215040 / 0xC8215054

notmain() 在 init_sys_mmu(); start_mmu(); 之前用 PA 打 123，之后用 VA 打 ABC。minicom 实测输出：

text
123
ABC

如果 MMU 没生效，第二次访问 0xC8215054 必然 fault（那个物理地址上什么都没有）。所以 ABC 出现这件事本身，就是 VA→PA 翻译正确的证据。

顺手验算习题：0xC8215040 → 0xC8215040 >> 20 = 0xC82 = 3202 → 取第 2 个 entry（0x3f200de2，base 0x3F200000）→ 加页内偏移 0x215040 → 0x3F215040 ✔

11.6 startup.s 里几个容易漏的寄存器 #

操作 寄存器 / 指令 值 为什么要做
清 I/C/M/Z SCTLR（cp15 c1,c0,0） 清 bit12/2/0/11 上电状态不可信，先回到已知态
开 MMU 同上的 bit0 M=1 最后一步，只置这一位
SMP 位 ACTLR（cp15 c1,c0,1）bit6 置 1 必须在使能 cache/MMU 或做 cache/TLB 维护之前
刷 TLB MCR p15,0,r0,c8,c7,0 — I/D-TLB 全失效
刷分支预测 MCR p15,0,r0,c7,c5,6 — BPIALL
向量表基址 VBAR（cp15 c12,c0,0） 新表地址 重定位向量表
选 TTBR0 TTBCR（cp15 c2,c0,2） 0 N=0，TTBR0 管全 4GB
页表缓属性 TTBR0 低位 `base 0x08
Domain DACR（cp15 c3,c0,0） 0x55555555 每个 domain 都是 client
NEON/VFP CPACR bit20-23、FPEXC 0xF<<20、0x40000000 放开 CP10/CP11

还有一条只在裸机里出现的「流水线安全」结论：使能 MMU 的那两条指令在 MMU 生效前就已被取指，之后 BX r12 跳走之所以安全，前提是这段代码 VA == PA（flat mapping）。这也是「一开 MMU 就飞」最常见的原因。

十二、速查表 #

现象 / 疑问 结论
页表该建几级？ ((VA_BITS)-4)/(PAGE_SHIFT-3)；4K→4 级、16K→4 级、64K→3 级
为什么是 4 和 3？ 3 = log2(描述符 8 字节)；4 是化简残项，不是级数
bits[1:0]=0b01 是什么？ L0/L1/L2 上是 block；L3 上是 reserved
bits[1:0]=0b11 是什么？ L0/L1/L2 上是 table；L3 上是 page
2MB 大页怎么来的？ SECTION_SHIFT ≡ PMD_SHIFT = 21，L2 entry 直接指物理块
48 位 VA 中间那段为什么不能用？ 最高 16 位既非全 0 也非全 1，不属于任何 TTBR 的区间
页表 walk 很慢 查 TCR_EL1 的 SH/ORGN/IRGN，配错会退化成 non-cacheable
寄存器读写被合并 查 MAIR_EL1 里这段地址的 AttrIndx 是否为 device
64K 页为什么只有 64 个有效 PGD 项 PTRS_PER_PGD = 1 << (48 - 42) = 64
一开 MMU 就飞 代码段 VA 与 PA 不一致，或 ACTLR.SMP 没先置位

小结 #

  • 页表级数不是拍的，是从「描述符 8 字节 + 一页装多少项」推出来的。
  • 每级吃 9 位（4K 页），五段切分 [47:39][38:30][29:21][20:12][11:0] 要能背下来。
  • 判定描述符只看 bit0（有效）与 bit1（类型），且在 L3 上 0b01 非法。
  • 顶层表可能是 L0/L1/L2，由 CONFIG_PGTABLE_LEVELS 决定，不是永远 L0。
  • 属性有两处：描述符里的 AttrIndx 是索引，真正的属性表在 MAIR_EL1。
  • 裸机验证 MMU 的最好办法不是 dump 寄存器，而是同一个设备用 PA 和 VA 各访问一次。
