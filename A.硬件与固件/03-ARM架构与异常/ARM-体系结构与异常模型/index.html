零、先建立坐标系 #

刚接触 ARM 时最容易混乱的，是产品名、架构版本、内核名三套命名同时在用。先把它们对上一遍：

你听到的名字 是什么 例子
Cortex-A9 / ARM926EJ-S 具体内核 IP，ARM 公司卖给芯片厂的设计 S5PV210 用 Cortex-A8，i.MX6 用 Cortex-A9
ARMv7-A / ARMv5TE 架构版本，规定指令集与特权模型的规格 Cortex-A9 实现 ARMv7-A
S3C2440 / RK3399 SoC，芯片厂拿内核 IP 加上一堆外设做成的芯片 S3C2440 = ARM920T + 存储控制器 + LCD + ...

调用关系是：架构版本 → 内核 IP → SoC。写驱动时你关心 SoC 的寄存器手册，写移植代码时你关心内核是 ARMv7 还是 ARMv8，写汇编时你关心是 ARM 状态还是 Thumb 状态。

一、ARM 产品线与架构演进 #

1.1 三条产品线 #

系列 定位 关键特征 典型场景
Cortex-A（Application） 跑操作系统的应用处理器 有 MMU（虚拟内存）、可选 NEON、高级浮点、TrustZone 手机、平板、路由器、开发板（RK3399 / i.MX6）
Cortex-R（Real-time） 实时控制 有 MPU（内存保护，无虚实映射）、低延迟中断 汽车 ECU、硬盘控制器、基带
Cortex-M（Microcontroller） 微控制器 无 MMU/MPU 或简化版、门数极少、确定性中断 STM32、nRF52、各类小家电

记住这一条就够了：A 系列有 MMU 所以能跑 Linux；M 系列没有 MMU 所以只能跑裸机或 RTOS。你手上的 Mini2440（ARM920T）、Exynos4412（Cortex-A9）、RK3399（Cortex-A72/A53）都属 A 系列。

1.2 架构版本演进 #

版本 引入的关键特性 代表内核
ARMv4T 16 位 Thumb 指令集 + 32 位 ARM 指令集并存，代码量可缩 35% ARM7TDMI
ARMv5TE(J) DSP 算术扩展（饱和运算）、Jazelle Java 字节码硬件执行 ARM926EJ-S、ARM968E-S
ARMv6 SIMD 扩展（视频/音频编解码提速约 4 倍）、Thumb-2 与 TrustZone 雏形 ARM1136EJ、ARM1176JZ
ARMv6-M 最小门数的 Thumb 指令集，面向 8 位机替代市场 Cortex-M0、Cortex-M1
ARMv7（分 A/R/M 三个 profile） Thumb-2（16/32 位混合）、NEON（DSP 与媒体吞吐提升最高 400%）、统一特权模型 Cortex-A8/A9/A15、Cortex-R4、Cortex-M3
ARMv8-A 引入 AArch64（64 位通用寄存器、64 位寻址），同时保留 AArch32 Cortex-A53/A57/A72/A76

ARMv8 的两种执行状态是重点：

  • AArch64：64 位执行状态，有自己的异常模型、内存模型、程序员模型与指令集（A64）。
  • AArch32：32 位执行状态，兼容 A32（原 ARM 指令集）与 T32（Thumb，Thumb-2 后是 16/32 位混合）。

一个 ARMv8 内核可以在两个状态间切换，但同一条执行流不会混用：进入 AArch64 后就是 64 位那套寄存器与异常模型，这与 ARMv7 的 ARM/Thumb 切换是两码事。

1.3 NEON 是什么 #

NEON 是 Cortex-A 上的 128 位 SIMD 引擎，寄存器文件是 32 个 64 位寄存器（也可看作 16 个 128 位寄存器的双视图）。它把寄存器当成同类型元素的向量，一条指令对所有通道做同一操作。

支持的数据类型：有符号/无符号 8/16/32/64 位整数、单精度浮点。典型收益：

  • 复杂视频编解码提升 60~150%；
  • 单个简单 DSP 算法（如 FIR、点积）提升 4~8 倍；
  • 处理器能更快进入睡眠，整体降低动态功耗。

写内核/驱动时基本不用碰 NEON；但如果你在 SoC 上做图像处理、音频重采样，编译器 -mfpu=neon 加上自动向量化就能吃到这部分性能。

1.4 ARMv8-A 为什么必须出现 #

新架构立项一般要满足三条前提：对上兼容、解决现存架构的已知问题、具备优势明显的新特性（哪怕软件从不用它）。ARMv8 三条都占。

它要解决的核心问题是 Large Memory，因果链很硬：

text
单个应用需要的内存 > 32 位可支持的最大值（4 GB）
        ↓
Cortex-A15（ARMv7）引入 LPAE，把物理地址扩到 40 bit
        ↓
但 32 位指令集让虚拟地址仍锁死在 32 bit（4 GB）
        ↓
只能在架构层面定义 64 位指令集

注意中间那一步：物理地址扩了、虚拟地址没扩，等于白扩。这就是为什么 A15 之后必须换架构，而不是继续打补丁。

顺带纠正一个常见误解：ARMv7 分 A/R/M 三个 profile，本质是三块细分市场，不是三种技术。同一个 ARMv7 架构按市场裁剪，才有三套 profile。

ARMv8 的六个关键点：

  1. 新增 64 位指令集 A64；
  2. 兼容 A32（原 ARM 指令集）与 T32（Thumb）；
  3. 定义 AArch64 / AArch32 两套 Execution State，软件可按需切换；
  4. AArch64 用 Exception Level 重新解释了「处理器模式 + 特权等级」；
  5. 在 ARMv7 security extension 之上重构了安全模型；
  6. 在 ARMv7 virtualization extension 之上给出完整虚拟化框架。

1.5 Exception Level：把「模式」和「特权」合成一个数 #

ARMv7 里「模式」和「特权等级」是两套东西；ARMv8 把它们合成一个 EL0 ~ EL3 的层级，数字越大特权越高。

EL 承载的软件实体 特权 是否必须实现
EL0 Application 非特权 必须
EL1 Guest OS（Linux kernel、Windows） 特权 必须
EL2 Hypervisor 特权 可选
EL3 Security Monitor 特权 可选

切换规则只有三条，但都很硬：

  1. 只有发生异常或从异常返回时才能切 EL，普通指令切不了；
  2. 发生异常时只能「留在当前 EL」或「跳到更高的 EL」，EL 不能降级；
  3. 返回时只能「留在当前 EL」或「跳到更低的 EL」。

这几条合起来解释了一件事：AArch64 里没有 User/SVC/ABT 这些模式概念了，模式被 EL 取代。那 AArch32 为什么还在？因为 AArch32 的那套模式被映射到了四个 EL 上：

AArch32 模式 映射到的 EL
usr EL0
svc / abt / und / irq / fiq / sys EL1
hyp EL2
mon EL3

还有一处版本细节值得记：ARMv7-A 把特权级叫 PL0 / PL1，虚拟化扩展之后多出 PL2。另外常有人写「ARMv7 增加了 Monitor 和 Supervisor 两个模式」——这是错的：Supervisor（SVC）自古就有，虚拟化扩展真正新增的是 Hyp 模式，而 Monitor 模式属于 Security Extension。

跨 EL 的入口指令也就这几条：

armasm
svc  #imm      @ 从 EL0 陷入 EL1（系统调用）
hvc  #imm      @ 从 EL1 陷入 EL2（调用 hypervisor）
smc  #imm      @ 陷入 EL3（请求 secure monitor）
eret           @ 从异常返回，ELR_ELx -> PC、SPSR_ELx -> PSTATE

eret 是「模拟一次异常返回」，在《ARM64 内核启动与页表建立》里 el2_setup 用它把自己从 EL2 降到 EL1。

1.6 AArch64 的程序员模型 #

从 AArch32 转过来，寄存器的变化比想象中大：

项目 AArch64
通用寄存器 31 个 64 位 X0 ~ X30（AArch32 只有 R0~R15）
32 位别名 W0 ~ W30，写 Wn 会把 Xn 高 32 位清零（不是保留）
栈指针 SP_EL0、SP_EL1、SP_EL2、SP_EL3，每级一个
PC 不是通用寄存器，不能直接读（AArch32 的 R15 可以直接 MOV）
状态 PSTATE 取代 CPSR，是一个字段化视图，不是一个可整体读写的寄存器
返回地址 不再用 LR 约定，X30 也只是「建议」

PSTATE 的字段：

字段 含义
N / Z / C / V 条件标志，与 AArch32 同义
SS 软件单步（Software Step）
IL Illegal Execution State，置 1 时取下一条指令即异常
D / A / I / F 调试 / SError / IRQ / FIQ 屏蔽
M[3:0] 当前 EL 与栈指针选择（EL0t / EL1h / EL1t …）

两个容易踩的点：

  • AArch32 在 EL0 用 CPSR，但在 EL1 及以上要用 SPSR 保存——因为 CPSR 在 AArch64 里根本不存在了，只有进 AArch32 状态时才「临时存在」。
  • PC 不可直接读，所以「读 PC 算当前位置」这类技巧在 AArch64 上要用 ADR / ADRP 实现。

大内存的落地方案也在这里定下来：48 位虚拟地址 + 40 位物理地址，用 TTBR0_EL1 / TTBR1_EL1 两套页表基址把用户空间与内核空间彻底分开，页粒度可选 4KB / 16KB / 64KB。细节见《ARM64 地址翻译与页表宏定义》。

1.7 Security State 不是逻辑保护，是物理区隔 #

ARMv8 有两个 Security State：Secure 与 Non-secure。它们的差别不是「权限高低」，而是能不能摸到另一套物理地址空间：

状态 能访问的 physical address space 能否访问 Secure 的系统控制资源
Secure Secure 和 Non-secure 两套 能
Non-secure 只有 Non-secure 一套 不能

所以同一个 PA 数值在两个世界里是两个不同的存储单元，不是同一块内存的两种视角。这一点在理解「PA 不是全局唯一标识」时很关键，后面的《内存模型与一致性基础》还会用到。

二、处理器模式与寄存器 #

2.1 七种模式 #

模式 缩写 特权 用途
用户 usr 非特权 普通应用程序
系统 sys 特权 特权级的「用户模式」，寄存器与 usr 相同
管理 svc 特权 复位后默认模式、SWI 系统调用进入
中止 abt 特权 预取中止、数据中止
未定义 und 特权 未定义指令
中断 irq 特权 普通中断
快速中断 fiq 特权 快速中断

5 种特权模式 + 1 种非特权 + 1 种系统模式。系统模式不是通过异常进入的，而是主动用 MSR CPSR_c, #0x1F 切过去，目的是让特权代码拥有和用户模式一样的寄存器组——这一点在讲可重入中断时会用到。

七个模式的 CPSR.M[4:0] 编码（做裸机时天天要写这些数）：

模式 M[4:0] 二进制 特权级
usr 0x10 0b10000 PL0
fiq 0x11 0b10001 PL1
irq 0x12 0b10010 PL1
svc 0x13 0b10011 PL1
abt 0x17 0b10111 PL1
und 0x1B 0b11011 PL1
sys 0x1F 0b11111 PL1

sys 是 0b11111 而不是 0b10000，这一位是新手最容易错的地方。写 MSR CPSR_c, #0xD3 切到 svc 时，0xD3 = 0b1101_0011：高 4 位是 I=1、F=1、T=0，低 5 位 0b10011 才是 svc。

二级分类树（比记七个名字有用）：

text
7 个模式
├── usr          非特权
└── 其余 6 个     特权
    ├── sys       特权但「不是异常模式」——不通过任何异常进入，
    │             且与用户模式共享同一组物理寄存器
    └── svc/abt/und/irq/fiq   五个异常模式

「sys 与 usr 共享同一组物理寄存器」这条定义比「特权模式」精确得多，也是可重入中断里必须切到 sys 的原因。

寄存器总量 37 个 = 31 个（R0~R15 共 16 + CPSR 1 + 各异常模式的私有 R13/R14/SPSR 等）+ 6 个 PSR（1 个 CPSR + 5 个 SPSR）。换个说法：37 = 31 个通用 + 6 个状态。

CPSR 位图：

text
31 30 29 28 27        7  6  5  4        0
 N  Z  C  V  Q   ...  I  F  T  M[4:0]
位 名字 含义
31~28 N Z C V 负数 / 零 / 进位借位 / 溢出
27 Q 饱和运算溢出标志（DSP 扩展）
7 I IRQ 屏蔽
6 F FIQ 屏蔽
5 T Thumb 状态（很多人画位图时会漏掉这一位）
4~0 M[4:0] 当前模式

ARMv4 之前还有一套 26 位模式编码，看老资料时会遇到：

老编码 模式
0b00000 User26
0b00001 FIQ26
0b00010 IRQ26
0b00011 SVC26

注意 abt / und 只在 32 位组里才有，26 位时代没有这两个模式。

2.2 寄存器分组（banked registers） #

ARM 有 16 个通用寄存器 R0~R15 加 1 个状态寄存器 CPSR，但每个异常模式有自己私有的 R13、R14 和 SPSR，这就是「分组寄存器」：

寄存器 别名 说明
R0~R12 — 通用，所有模式共享同一份物理寄存器
R13 SP 栈指针，每个异常模式一份
R14 LR 链接寄存器（保存返回地址），每个异常模式一份
R15 PC 程序计数器
CPSR — 当前程序状态寄存器
SPSR_<mode> — 保存被中断时的 CPSR，每个异常模式一份

FIQ 的额外特权：FIQ 模式额外拥有 R8_fiq~R12_fiq 五个私有寄存器。所以 FIQ 的中断服务程序如果只用 R8~R12 做运算，完全不需要压栈保存现场——这是 FIQ 比 IRQ 快的第一个原因。

2.3 FIQ 为什么比 IRQ 快 #

三个原因，缺一不可：

  1. 分组寄存器多：FIQ 有私有的 R8~R12，处理时无需保存这 5 个寄存器；
  2. 优先级更高：FIQ 可以打断 IRQ，反之不行；
  3. 向量表位置最优：FIQ 向量在 0x1C，是向量表的最后一项，可以直接在向量表末尾放中断服务程序本体，省掉一次跳转（其余异常只能放一条跳转指令）。

三、异常模型 #

3.1 七类异常与优先级 #

从高到低：

优先级 异常 向量地址 触发方式 返回指令
1（最高） 复位 Reset 0x00 上电/复位/看门狗 不返回
2 未定义指令 Undefined 0x04 执行了 CPU 不认识的指令 MOVS PC, LR
3 软中断 SWI 0x08 SWI #n 指令 MOVS PC, LR
4 预取中止 Prefetch Abort 0x0C 取指时地址非法 SUBS PC, LR, #4
5 数据中止 Data Abort 0x10 访存时地址非法 SUBS PC, LR, #8
6 中断 IRQ 0x18 外设中断 SUBS PC, LR, #4
7（最低） 快速中断 FIQ 0x1C 外设快速中断 SUBS PC, LR, #4

注意表里 0x14 是空着的，这是历史遗留（早期 ARM 在此处放过地址异常），别去用。

3.2 进入异常时 CPU 自动做的事 #

这是面试高频题，前四步全由硬件完成，一行代码都不用写：

  1. 把当前模式的 CPSR 复制到目标模式的 SPSR（保存返回时的状态）；
  2. 修改 CPSR 的模式位，切到目标模式，同时按需屏蔽中断（IRQ 进入时置 CPSR 的 I 位）；
  3. 把被打断的下一条指令地址保存到目标模式的 LR；
  4. 把 PC 设为对应的向量表地址（如 IRQ 是 0x18）。

之后的全部工作由软件负责：装跳转指令、保存现场、判断中断源、清中断标志、恢复现场、返回。

为什么「进入靠硬件、返回靠软件」？因为 CPU 只知道「异常发生了」，只有程序员知道「处理什么时候算真的结束」。

3.3 返回地址为什么要减 4 或减 8 #

根因是流水线。ARM 状态下 PC 总是指向「当前执行指令 + 8」（正在取指的那条），所以异常发生时 LR 里存的并不一定是正确的返回点：

异常 LR 里实际是什么 修正方式
未定义指令 / SWI 下一条指令（PC-4 已经由硬件调好） MOVS PC, LR 直接用
IRQ / FIQ 被打断指令的下一条 SUBS PC, LR, #4 回到被打断指令的下一条
预取中止 出错指令地址 + 4 SUBS PC, LR, #4
数据中止 出错指令地址 + 8 SUBS PC, LR, #8

所以会看到 IRQ 的标准返回写法是 SUBS PC, LR, #4——它一条指令同时完成「LR 减 4 写回 PC」和「SPSR 恢复 CPSR」。

3.4 向量中断 vs 非向量中断 #

类型 地址分配 优点 缺点 例子
向量中断 每个中断源一个独立入口地址 响应最快，直接跳进 ISR 中断源一多就吃掉大量地址空间 S3C6410
非向量中断 所有中断源共用一个入口 地址开销小 需要在总 ISR 里读寄存器判断中断源 S3C2440、Exynos4412

非向量中断的通用处理流程（以 S3C2440 的 IRQ 为例）：

text
0x18:  B  ISR_IRQ               ← 向量表里装一条跳转
ISR_IRQ:
        STMFD SP!, {R0-R12, LR}  ← 保存现场
        BL    find_int_source    ← 读 INTPND 判断是哪个中断
        BL    eint1_isr          ← 跳到具体中断处理
        ...                      ← 清 SRCPND / INTPND
        LDMFD SP!, {R0-R12, PC}^ ← 恢复现场并返回

CPU 只在每条指令执行前检测中断，指令执行过程中不会被打断。这是「返回地址要减 4」的物理原因，也是所有中断延迟分析的起点。

3.5 中断嵌套的坑：BL 会冲掉 LR_irq #

在 IRQ 处理函数里再开中断（可重入中断）时，如果用 BL 调用子程序，第二次中断进来会把 LR_irq 覆盖掉，子程序返回时跳到错误地址，表现为死循环或跑飞。

标准解法：调用前切到系统模式（MSR CPSR_c, #0x1F），此时 BL 保存的是 LR_usr，LR_irq 就安全了。处理完再切回 IRQ 模式返回。

四、CP15 与 MMU #

CP15 是 ARM 的系统控制协处理器，只能通过 MCR（写）/ MRC（读）访问，且必须在特权模式下操作。三项职责：

  1. 管理内存访问权限：区分特权/非特权访问。Linux 里这是单向收紧的——用户态永远不能提权。
  2. 管理物理地址到虚拟地址的映射：写页表基址寄存器、开 MMU。
  3. 管理中断向量表基址：Cortex 系列可以通过 CP15 的 c12 寄存器把向量表搬走（ARM7/9 只能固定在 0x0 或 0xFFFF0000）。

4.1 为什么要虚拟地址 #

核心动机是进程隔离：每个进程都以为自己独占整个地址空间，互相访问不到对方。

问题 答案
CPU 知道虚拟地址和物理地址的区别吗？ 不知道。CPU 只管发地址，是 MMU 在中间翻译
怎么开？ 硬件上开 MMU；软件上建页表（Linux 用多级页表，Windows 用段页结合）
可以随便映射吗？ 原则上可以，只要你保证映射和解映射成对出现

4.2 链接地址 vs 运行地址 #

这两个概念不是虚拟/物理地址之分，它们都是软件概念：

  • 链接地址：链接器认为程序「应该」位于的地方（lds 里的 . = 0x30008000）；
  • 运行地址：程序此刻真正在的地方。

嵌入式开发里两者经常不一致：程序存在 NAND 里，通过串口或 TFTP 下载到 SDRAM 的另一个地址运行。解决办法是「一切照硬件行为办」——要么写位置无关码（用 B/BL/ADR），要么在启动时做重定位（把代码从运行地址拷到链接地址）。U-Boot 的 relocate_code 干的就是这件事。

位置无关码的三条铁律：能用 B/BL/ADR（相对 PC 取指），不能用 LDR =（绝对地址），不能访问全局变量。

五、存储层次与 Cache #

5.1 三级存储系统 #

引入 Cache 的根本原因是速度与成本的矛盾，可行性依据是程序运行的局部性（时间局部性 + 空间局部性）。

Cache—主存 与 主存—辅存 两个层次的对比（这是操作系统课的经典考点）：

维度 Cache—主存 主存—辅存（虚拟存储）
出发点 相同：用分层存储逼近高速存储器的速度、低速存储器的价格 同左
原理 相同：利用局部性把常用信息块调入高速小容量存储器 同左
侧重点 解决 CPU 与主存的速度差 解决 主存容量不足
数据通路 CPU 与 Cache、主存都有直接通路，不命中可直接访主存 辅存与 CPU 无直接通路，不命中只能调页
透明性 完全硬件管理，对所有人透明 软硬件共同管理，对系统程序员不透明
未命中损失 主存约为 Cache 的 5~10 倍慢 主存比辅存快上千倍，损失大得多

5.2 写策略 #

  • Write Through（写穿）：写 Cache 的同时写主存。实现简单、一致性好，但总线流量大。
  • Write Back（写回）：只写 Cache，置脏位，替换时才写回主存。性能好，但存在数据不一致窗口。

这直接引出两个嵌入式开发中的经典约束：

① 更新内核页表后必须关 Cache 或做 Cache 维护，否则 CPU 读到的是旧页表项的缓存副本。 ② DMA 传输要显式处理 Cache 一致性：外设直接写内存绕过了 Cache，CPU 读到的可能是旧数据；CPU 写的数据可能还在 Cache 里没落到内存，DMA 搬走的就是旧值。做法是 DMA 前后 clean/invalidate 对应区间。

5.3 哈佛结构 #

哈佛结构把指令存储与数据存储分开：两套独立的存储器、两套独立的总线（各自的地址线与数据线）。

带来的好处：一个机器周期内可以同时取指令和取操作数，取指与执行能完全重叠，吞吐率显著提高；指令和数据还可以有不同的位宽。

体现到 ARM 上就是 I-Cache 与 D-Cache 分离。这也解释了为什么很多启动代码里要分开处理两个 Cache：

armasm
mrc p15, 0, r0, c1, c0, 0
bic r0, r0, #0x00000087   @ 关 MMU(bit0)、关 D-Cache(bit2)、关 I-Cache(bit12 之外的部分)
mcr p15, 0, r0, c1, c0, 0

六、总线与地址空间 #

6.1 三类总线 #

总线 传什么 方向
数据总线 DB 真正要处理/存储的数据 双向
地址总线 AB 数据在主存中的地址 单向（CPU 发出）
控制总线 CB 读写信号、中断、时钟等控制信号 双向/单向混合

DB + AB + CB 合称系统总线。此外还有扩展总线（连扩展槽）和局部总线（更高速的扩展总线）。

6.2 AMBA：ARM 的片上总线标准 #

AMBA 是 ARM 提出的开放片上总线标准，独立于处理器和工艺，定义了三种总线：

总线 全称 连接对象
AHB Advanced High-performance Bus 高带宽元件：CPU、DMA 控制器、片上存储器、LCD 控制器
ASB Advanced System Bus AHB 的前身，现已少用
APB Advanced Peripheral Bus 低速外设：UART、I2C、GPIO、看门狗

AHB 与 APB 之间通过桥接器（Bridge） 互联。SoC 内部因此可以分成三部分理解：高速外设挂在 AHB、低速外设挂在 APB、中间是核。看芯片手册的时钟树与地址映射图时，这个分层是理解的总纲。

6.3 DMA #

DMA 让数据传输不需要 CPU 参与，但总线使用权仍由 CPU 控制。四个阶段：

  1. DMA 请求：外设或软件向 DMA 控制器发请求；
  2. DMA 响应：DMA 控制器向 CPU 申请总线（总线仲裁）；
  3. DMA 传输：控制器直接在内存与外设间搬数据，CPU 期间可继续执行不占总线的指令；
  4. DMA 结束：通过中断通知 CPU 收回总线控制权。

6.4 内存类接口 vs 协议类接口 #

看原理图时最有用的一个分类：

类型 特征 例子
内存类接口 地址线直接接到 CPU（或存储控制器），统一编址，像访问内存一样访问 NOR Flash、SRAM、SDRAM、网卡（DM9000）
协议类接口 CPU 不能直接寻址，必须通过对应控制器发命令/读写寄存器 NAND Flash、LCD、UART、I2C、SPI

这个区分解释了为什么 NOR Flash 可以直接 *(volatile unsigned char *)0x0 读，而 NAND Flash 必须经过 NAND 控制器发命令序列。

NOR 位宽与地址线：NOR 的位宽不同，接到 CPU 上的地址线根数也不同——16 位 NOR 的 A0 接的是 CPU 的 A1，所以写代码算地址时要按位宽换算。理解了字节对齐这一节就能想明白原因。

七、流水线与 PC #

7.1 PC 为什么等于「当前指令 + 8」 #

无论处理器处于什么状态，PC(R15) 总是指向正在取指的那条指令，而不是正在执行或正在译码的。三级流水线（取指 / 译码 / 执行）下，PC 指向当前执行指令之后 2 条 指令的地址，即 当前地址 + 8。

内核 流水线级数
ARM7 3 级
ARM9 5 级
ARM11 8 级
Cortex-A9 13 级超标量

互锁（interlock）：一条指令的结果被下一条指令当作操作数时，流水线必须等待，这叫互锁。级数越深，互锁与分支预测失败的代价越大。

7.2 一个具体的返回地址推导 #

假设指令 A 在 0x8000，此时 PC = 0x8008（指向 C）。A 若是 BL 指令，硬件先把 PC 存进 LR（得到 0x8008），再自动做一次 LR = LR - 4，最终 LR = 0x8004，正好是 B 的地址——函数返回时才能正确回到 B。

这套「自动减 4」的修正机制在所有 LR 保存操作中都存在，包括进入中断时。

八、函数调用栈帧 #

这一节把 AAPCS 的「寄存器分工」落到具体的内存布局上。看懂一张栈帧图，backtrace、core dump、栈溢出排查才有落脚点。

8.1 一个真实的调用 #

被调函数 callfunctionA(int aa, int bb, int c, int d, int e, int f)，参数超过 4 个。反汇编（ARM 状态）：

armasm
00008480 <callfunctionA>:
    8480: e92d4800  push  {fp, lr}        @ 存旧 fp 与返回地址
    8484: e28db004  add   fp, sp, #4      @ 建立帧指针
    8488: e24dd018  sub   sp, sp, #24     @ 开 24 字节局部区
    848c: e50b0010  str   r0, [fp, #-16]  @ aa
    8490: e50b1014  str   r1, [fp, #-20]  @ bb
    8494: e50b2018  str   r2, [fp, #-24]  @ c
    8498: e50b301c  str   r3, [fp, #-28]  @ d
    849c: e3a03000  mov   r3, #0
    84a0: e50b3008  str   r3, [fp, #-8]   @ a = 0
    84a4: e3a03000  mov   r3, #0
    84a8: e50b300c  str   r3, [fp, #-12]  @ b = 0
    84ac: e59f001c  ldr   r0, [pc, #28]   @ 取格式串地址
    84b0: e51b1008  ldr   r1, [fp, #-8]   @ 取 a
    84b4: e51b200c  ldr   r2, [fp, #-12]  @ 取 b
    84b8: ebffff89  bl    82e4 <printf@plt>
    84bc: ebffffe0  bl    8444 <callfunctionB>
    84c0: e3a03000  mov   r3, #0
    84c4: e1a00003  mov   r0, r3        @ 返回值 0
    84c8: e24bd004  sub   sp, fp, #4    @ 复位 sp 到 saved fp
    84cc: e8bd8800  pop   {fp, pc}      @ 恢复 fp，用 PC 出栈即返回

调用侧在 main 里：

armasm
    mov r3, #5
    str r3, [sp]        @ 第 5 个参数 e 放在 [sp]
    mov r3, #6
    str r3, [sp, #4]    @ 第 6 个参数 f 放在 [sp, #4]
    mov r0, #1          @ aa
    mov r1, #2          @ bb
    mov r2, #3          @ c
    mov r3, #4          @ d
    bl  8480 <callfunctionA>

于是记法就清楚了：前 4 个参数走 R0~R3，第 5 个放在调用者的 [sp]、第 6 个放在 [sp, #4]，依次往上。

8.2 栈帧布局 #

设调用者执行 bl 之前的 sp 为 S：

text
        高地址
   +------------+
   |    ...     |
   +------------+  fp+8    第 6 参 f（= S+4）
   |     f      |
   +------------+  fp+4    第 5 参 e（= S，调用者的 sp）
   |     e      |
   +------------+  fp+0    返回地址 lr（= S-4），fp 指向此处
   |  saved lr  |
   +------------+  fp-4    旧 fp（= S-8）  <-- fp 链指针
   |  saved fp  |
   +------------+  fp-8    局部变量 a
   |     a      |
   +------------+  fp-12   b
   |     b      |
   +------------+  fp-16   aa（r0 溢出落栈）
   +------------+  fp-20   bb（r1）
   +------------+  fp-24   c（r2）
   +------------+  fp-28   d（r3）= sp，帧底
   |     d      |
   +------------+
        低地址

帧总长 = 8（push）+ 24（sub）= 32 字节，sp 从 S-8 走到 S-32。

8.3 为什么是 fp = sp + 4 #

这一点原文只给结论，不解释成因。关键在于 push {fp, lr} 展开成 STMDB sp!, {r11, r14}，而 STMDB 的规则是「编号小的寄存器落在低地址」：

  • r11（fp）存于 sp+0；
  • r14（lr）存于 sp+4。

此时 sp = S-8，所以：

  • fp = sp + 4 = S - 4 正好指向 saved lr；
  • [fp - 4] 自然就是 saved fp（链指针）；
  • 局部变量落在 [fp - 8] 往下（负偏移）；
  • 压栈实参落在 [fp + 4] 往上（正偏移）。

「fp 指向 saved lr」才是这套约定的本质，+4 不是随手取的。这么设计的好处是参数与局部变量关于 fp 对称，而且返回前只需一条 sub sp, fp, #4 就能把栈复位。

8.4 顺着 fp 链做 backtrace #

c
fp_cur = 当前 fp;
while (fp_cur 合法) {
    lr_i = *(fp_cur);          /* [fp+0] 是这一帧的返回地址 */
    pc_i = lr_i - 4;           /* 回到执行 bl 的那条指令（可选） */
    fp_next = *(fp_cur - 4);   /* [fp-4] 是上一帧的 fp */
    if (fp_next == 0) break;
    if (fp_next 不在 [stack_bottom, stack_top)) break;
    if (fp_next 非 4 字节对齐) break;
    if (fp_next <= fp_cur) break;   /* 必须单调递减（向上走） */
    fp_cur = fp_next;
}

四个停止条件一个都不能省，尤其区间合法性 + 单调性：栈被破坏时缺了它们就是死循环或读野地址。

这条链依赖 -fno-omit-frame-pointer。ARM EABI 允许 r11 当通用寄存器用，gcc -O2 默认就会省掉 fp，此时只能靠 .ARM.exidx / .debug_frame 展开表回溯；内核态则走 unwind_frame()。调试时看到「backtrace 只有一层」，先查这里。

九、字节对齐 #

8.1 为什么要对齐 #

两个原因：

  1. 平台原因（移植性）：不是所有硬件都能访问任意地址上的任意数据，某些平台会在非对齐访问时抛硬件异常。
  2. 性能原因：非对齐访问要拆成两次内存访问，对齐访问只需一次。

8.2 ARM 与 Thumb 的对齐要求 #

状态 指令宽度 PC 递增 对齐要求
ARM 32 位 +4 地址低 2 位为 0b00，即 4 的倍数
Thumb 16 位 +2 地址低 1 位为 0b0，即 2 的倍数

地址布局示例（ARM 状态）：

text
指令1：0x0000_0000 ~ 0x0000_0003
指令2：0x0000_0004 ~ 0x0000_0007
指令3：0x0000_0008 ~ 0x0000_000B
指令4：0x0000_000C ~ 0x0000_000F

理解这个就理解了为什么不同位宽的 Flash 地址线接法不同：16 位 NOR 每个地址单元放 2 字节，所以 CPU 的 A1 要接到 NOR 的 A0，低位地址在 NOR 内部由字节选择信号处理。

十、速查表 #

现象 / 问题 首先检查
中断进不去 向量表地址是否正确（Cortex 下 CP15 c12）、CPSR 的 I/F 位、中断控制器是否 unmask、外设是否使能
中断返回后跑飞 返回指令是否用了正确的 SUBS PC, LR, #n（IRQ/FIQ 是 4，Data Abort 是 8）
中断嵌套后死循环 BL 冲掉了 LR_irq，改为在系统模式下调用
开 MMU 后立刻挂 页表映射是否覆盖了当前执行的代码、栈、以及 MMU 打开后的下一条指令
DMA 数据不对 Cache 一致性：传输前 clean、传输后 invalidate
代码搬到 SDRAM 后跑飞 用了绝对地址（LDR = 或全局变量），不是位置无关码；或没做重定位
访问外设寄存器读到全 0 或全 F 时钟没开（AHB/APB 门控）、或地址映射写错

小结 #

  • 架构版本 → 内核 IP → SoC，三套命名要对上；A 系列有 MMU 才能跑 Linux。
  • 七种模式里 5 种特权 + 系统模式；异常模式下 R13/R14/SPSR 是私有的，FIQ 还多 5 个 R8~R12。
  • 七类异常有固定优先级和固定向量地址；进入靠硬件四步，返回靠软件；返回地址按流水线规则减 4 或减 8。
  • CP15 管三件事：访问权限、虚实映射、向量表基址。链接地址 ≠ 运行地址，两者不一致时要么写位置无关码，要么重定位。
  • 存储层次的核心是局部性；写回策略带来 Cache 一致性问题，体现在页表更新和 DMA 两处。
  • 总线分 AHB（高速）/APB（低速）；接口分内存类（统一编址）与协议类（走控制器）。
