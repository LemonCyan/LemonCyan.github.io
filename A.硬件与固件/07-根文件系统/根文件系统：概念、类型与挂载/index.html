一、根文件系统是什么 #

1.1 内核其实可以不要文件系统 #

理论上，只要内核能跑起来、又不需要任何用户态进程，就不需要文件系统。现实里这种场景极少——内核跑完自我初始化后必须执行一个用户态程序（/sbin/init 或 /init），而这个程序本身就得放在某个文件系统里。

所以「根文件系统」不是可选项，是内核把控制权交给用户空间的唯一通道。

1.2 定义：第一个挂载点 #

Linux 整个操作系统看起来是一棵目录树，最顶层是 /。所有已安装的文件系统都作为这棵树的枝叶，通过挂载点接上去。

  • 根文件系统 = 挂在 / 上的那个，也就是内核启动时挂载的第一个文件系统
  • 普通文件系统 = 后来挂上去的，必须挂在某个已存在的目录（挂载点）上

这个定义带来一条硬约束：必须先有一个 /，才谈得上挂载别的。而挂载点本身必须在某个已挂载的文件系统里——鸡生蛋问题。

1.3 虚拟 rootfs：内核自己先造一个 #

解法是内核先造一个假根：

概念 谁创建 在哪 生命周期
虚拟 rootfs 内核自己（init_mount_tree()） 只在内存里，类型是 ramfs/tmpfs 从 start_kernel 开始，一直存在
真实 rootfs 你做的镜像 存储设备（eMMC / NAND / SD / 网络） 挂到虚拟 rootfs 上，然后 / 切过去

启动早期，mnt_init() 会注册 rootfs（本质是 ramfs）并建立初始挂载树。之后内核去解 initramfs、找真实根设备，最终把 / 的挂载点从虚拟 rootfs 换成真实设备上的文件系统。虚拟 rootfs 不会消失，它退到后面成为那个"空壳"。

ℹ笔记

这就是为什么 mount 命令永远有地方挂：无论真实根挂没挂上，虚拟 rootfs 提供的 / 节点树始终存在。也是为什么内存紧张时 df 会看到 rootfs 占了一小块——那是初始挂载树的残留。

二、目录规范：一个都不能少的，和可以省的 #

2.1 FHS 关键目录 #

目录 放什么 嵌入式能否省
/bin 用户和管理员都用得上的基本命令（ls、cp、sh） 不能
/sbin 系统管理命令（init、ifconfig、mdev） 不能
/lib 共享库、内核模块（/lib/modules）、固件（/lib/firmware） 不能（动态链接时）
/etc 配置文件：inittab、fstab、profile、init.d/ 不能
/dev 设备节点 不能，但应挂 devtmpfs 而非做进镜像
/proc 内核与进程信息 不能，挂 procfs
/sys 设备模型 不能，挂 sysfs
/tmp 临时文件 需要，但应挂 tmpfs
/usr 二级层次：/usr/bin、/usr/lib、/usr/share 可以合并进 /
/var 可变数据：日志、锁、缓存 建议挂 tmpfs（保护 Flash）
/root root 用户主目录 可省
/home、/opt、/mnt 多用户、第三方、临时挂载点 通常可省
/boot 内核与 bootloader 文件 看引导方式：bootloader 自己从 Flash 读内核就不需要

2.2 最小可用集合 #

用 busybox 手搓 rootfs 时，真正不能少的是：

/
├── bin/       # busybox 的符号链接
├── sbin/      # init → busybox
├── etc/       # inittab / fstab / init.d/rcS / profile
├── lib/       # ld-linux-*.so、libc.so*、modules/
├── dev/       # 空目录，启动时挂 devtmpfs 或由 mdev 填充
├── proc/      # 空目录，挂 procfs
├── sys/       # 空目录，挂 sysfs
├── tmp/       # 空目录，挂 tmpfs
└── root/      # 空目录

缺 /etc/inittab，busybox 的 init 会退化到默认行为；缺 /dev/console，第一个用户态进程拿不到标准输入输出，屏幕上什么都看不到——这是新手最常见的"启动成功但黑屏"。

2.3 裁剪论文给出的取舍 #

早期几篇嵌入式裁剪论文（2006~2015）反复验证过同一条结论：

  • 面向单用户设备的 rootfs，/home、/mnt、/opt、/root 基本可以省
  • 库的选择直接决定体积：glibc → uClibc / musl 能省一半以上，代价是某些预编译二进制要重编
  • 静态链接 busybox 省掉了部署动态库的麻烦，但自己写的程序就没法在这个 rootfs 里跑了——因为那些程序需要动态库
  • 一个 14.1 MB 的 busybox 系统，Ext2 + gzip 后能压到 2.3 MB

三、文件系统类型：按介质分四族 #

选型的第一原则不是"哪个性能好"，而是介质是什么。块设备和 Raw Flash 的差别决定了哪些文件系统根本用不了。

3.1 块设备族（eMMC / SD / U 盘 / 硬盘） #

这些设备自带 FTL（Flash Translation Layer）或本身就是磁盘，屏蔽了擦除块和坏块，上层看到的是扇区。

类型 压缩 可写 特点 用途
ext2 否 是 无日志，简单；断电易损 早期 ext 镜像、initrd
ext3 否 是 ext2 + 日志 逐步被 ext4 替代
ext4 否 是 延迟分配、extent、兼容性好 大分区默认选择
f2fs 是 是 为 NAND/闪存设计，利用块设备特性 手机、eMMC 读写分区
btrfs 是 是 快照、子卷、校验和 桌面/服务器，嵌入式少见
xfs / jfs / reiserfs 否 是 某些读写场景更优 服务器
squashfs 是 否 只读、挂载快、压缩比高 只读根的最佳选择

3.2 Raw Flash 族（裸 NAND / NOR，走 MTD） #

裸 Flash 有擦除块、坏块、写前必须擦除、擦写寿命有限。必须有专门的文件系统做坏块管理与磨损均衡。

类型 压缩 介质 特点 坑
jffs2 是 NOR 为主 日志型、掉电安全、写平衡 挂载要扫全片；接近满盘时垃圾回收导致速度骤降；大容量 NAND 上内存占用暴涨
yaffs / yaffs2 否 NAND 专为 NAND 设计、挂载快、内存占用小、自带 NAND 驱动 不支持压缩；yaffs 只支持小页(512B)，yaffs2 支持大页(2KB)
ubifs 是 NAND 读写性能好、全局磨损均衡 小分区元数据开销过大（该用 jffs2）；挂载要扫全部擦除块
ubiblock + squashfs 是 NAND 在 UBI 卷上跑只读 squashfs 需要 CONFIG_MTD_UBI_BLOCK

两个值得记住的实测数字：

  • UBI Fastmap：216 MB UBI 空间、80 MB 根文件系统，平均挂载时间从 968 ms 降到 238 ms。原理是把 UBI 元数据存进几个闪存块，避免每次启动扫描全部擦除块；Fastmap 失效（非正常关机）会退回扫描模式，下次启动恢复。
  • JFFS2 summary（CONFIG_JFFS2_SUMMARY）：128 MB 分区挂载时间从 16 s 降到 0.8 s。

3.3 内存族（ramfs / tmpfs / ramdisk / initramfs） #

类型 本质 能否限定大小 掉电
ramfs VFS 层的纯内存文件系统，不能格式化 不能，会一直吃内存 丢
tmpfs ramfs + 大小限制 + 可换出 能（size=） 丢
ramdisk 一块固定内存当块设备用，上面再放 ext2 等 固定 丢
initramfs 压缩的 cpio 归档，解压进 rootfs 受内存限制 丢

用途分工很清楚：/tmp、/var、/run 用 tmpfs（避免写 Flash，也避免磨损）；initramfs 用作过渡根；ramdisk 现在基本只剩兼容老平台。

3.4 网络族（NFS） #

根文件系统放在开发主机上，开发板通过 root=/dev/nfs 挂过去。改代码不用重新烧写，重启即生效——这是开发阶段最省时间的方式，量产绝不能用（网络一断系统就起不来）。具体配置见同目录的移植实战篇。

3.5 选型速查 #

场景 选择
eMMC 上的读写根 ext4（稳）或 f2fs（闪存友好）
eMMC 上的只读根 squashfs（+ overlay 承接写入）
裸 NAND，要压缩 ubifs（大分区）/ jffs2（小分区）
裸 NAND，要快、不要压缩 yaffs2
裸 NAND，只读根 ubiblock + squashfs
极小系统、几 MB 闪存 initramfs 直接编进内核
开发调试 NFS 根
✦提示

读写性能都关键的系统，把根文件系统和数据分区分开：根用只读 squashfs 保启动时间，数据用 ext4/f2fs 保运行时性能。这一条比"选一个全能文件系统"实际得多。

四、ramdisk、initrd、initramfs：三种过渡根 #

三者都是"先挂一个临时的根，再由它把真正的根挂上"，但机制差别很大。

4.1 关系一览 #

名称 格式 内核处理 入口文件 现状
ramdisk / image-initrd 一个 ext2 镜像 读进 /dev/ram0 再挂载 /linuxrc 老平台兼容
cpio-initrd cpio + gzip 归档 直接释放进 rootfs /init 仍在用（外部 initramfs）
initramfs cpio + gzip，编进内核 内核启动时自动解压 /init 现代默认

4.2 image-initrd（ramdisk）的制作 #

dd if=/dev/zero of=../initrd.img bs=512k count=5
mkfs.ext2 -F -m0 ../initrd.img
mount -t ext2 -o loop ../initrd.img /mnt
cp -r * /mnt
umount /mnt
gzip -9 ../initrd.img

内核必须配置：

text
Device Drivers  --->
     [*] Block devices  --->
          <*>   RAM block device support
          (1)     Default number of RAM disks
        (131072) Default RAM disk size (kbytes)

General setup  --->
    [*] Initial RAM filesystem and RAM disk (initramfs/initrd) support

对应 .config：

makefile
CONFIG_BLK_DEV_RAM=y
CONFIG_BLK_DEV_RAM_COUNT=1
CONFIG_BLK_DEV_RAM_SIZE=131072
CONFIG_BLK_DEV_INITRD=y

注意 RAM disk size：比压缩包解压后的大小还小，就会报 RAMDISK: image too small 之类的错误。这也是后面扩展 rootfs 内容（比如塞进整个 /lib/firmware）时必须同步调大的三个参数之一，另外两个是 Buildroot 的 exact size 和分区表。

bootloader 把镜像读到内存固定地址，然后通过 bootargs 告知地址和长度：

makefile
initrd=0x42000000,0x14000000

格式是「地址,长度」，长度只要大于压缩包即可。也可以在设备树 chosen 节点里给：

text
chosen {
	linux,initrd-start = <0x42000000>;
	linux,initrd-end   = <0x56000000>;
}

4.3 cpio-initrd / initramfs 的制作 #

text
find . | cpio -c -o > ../initrd.img
gzip ../initrd.img

现代写法更明确：

bash
cd rootfs
find . | cpio -H newc -o | gzip -9 -n > ../initramfs.gz

-H newc 指定 newc 格式（内核认的那种），-n 表示 gzip 不写时间戳——这样同样的内容每次打包出来的字节完全一致，便于做版本比对。

内核配置只需：

text
General setup  --->
    [*] Initial RAM filesystem and RAM disk (initramfs/initrd) support

4.4 两者的处理流程差异 #

image-initrd（root=/dev/ram0 时与否则不同）：

  1. bootloader 把 image-initrd 读进内存，内核把镜像存成 rootfs 下的 /initrd.image，再读入 /dev/ram0
  2. 若 root == /dev/ram0：直接把这个内存里的文件系统当最终根，正常启动，执行 /sbin/init
  3. 若 root != /dev/ram0：先执行 initrd 里的 /linuxrc（通常是个脚本，负责加载访问真实根所需的驱动并把真实根挂上），返回内核；真实根若存在 /initrd 目录，/dev/ram0 移到那里，否则卸载；最后在真实根上执行 /sbin/init

cpio-initrd / initramfs：

  1. bootloader（或内核自带）把 cpio 归档读进内存
  2. 内核判断是 cpio 格式，直接释放到 rootfs（不需要额外的文件系统支持，省掉挂载/卸载）
  3. 执行归档里的 /init，内核的工作到此结束，完全交给它
对比项 image-initrd cpio-initrd / initramfs
制作难度 要 dd + mkfs + mount 一条 `find
内核流程 挂载 → 卸载 → 再挂真实根 释放即用
依赖 需要 ext2 等具体文件系统 不需要
入口 /linuxrc /init
收尾 /linuxrc 返回后内核还要继续收尾 交出控制权即结束
❢重要

定制镜像时最容易犯的错：做的是 cpio-initrd，却往里塞 /linuxrc；做的是 image-initrd，却只放 /init。结果就是内核找不到入口，报 No working init found。

五、内核怎么把它挂上：一条完整调用链 #

5.1 建立虚拟根 #

text
start_kernel()                        // init/main.c
  └─ setup_arch(&command_line)        // arch/arm64/kernel/setup.c
  │    └─ setup_machine_fdt()         // 解析设备树
  └─ vfs_caches_init()                // fs/dcache.c
       └─ mnt_init()                  // fs/namespace.c
            ├─ init_rootfs()          // 注册 rootfs_fs_type
            ├─ init_ramfs_fs()        // 注册 ramfs_fs_type
            └─ init_mount_tree()      // 建立初始挂载树，rootfs 成为 /
  └─ rest_init()                      // 创建 kernel_init 内核线程

5.2 解 initramfs、挂真实根、起 init #

text
kernel_init()                         // 内核线程，后来的 PID 1
  └─ kernel_init_freeable()
       ├─ do_basic_setup()
       │    └─ do_initcalls()         // 各驱动 probe
       └─ prepare_namespace()
            ├─ populate_rootfs()      // 若内核自带 initramfs
            │    └─ unpack_to_rootfs(initrd_start, initrd_end - initrd_start)
            ├─ mount_root()           // 按 root= 挂真实根，切 / 
            └─ ...
  └─ run_init_process(ramdisk_execute_command ?: "/sbin/init")

5.3 相关启动参数 #

参数 作用 解析位置
root= 根设备：/dev/mmcblk0p3、PARTUUID=...、/dev/nfs、/dev/ram0 root_dev_setup()（__setup("root=")）
rootfstype= 强制根文件系统类型 同上
rootwait 无限等根设备就绪（USB/MMC 等异步探测必需） rootwait_setup()
rw / ro 读写或只读挂载 —
init= 覆盖最终执行的首个用户态程序 init_setup()（__setup("init=")）
rdinit= 覆盖 initramfs 里的入口程序 rdinit_setup()（__setup("rdinit=")）
initrd= initrd 的物理地址与长度 early_initrd()（early_param("initrd")）

两个真实例子：

text

bootargs=earlycon=uart8250,mmio32,0xff1a0000 console=tty0 console=ttyS2,115200n8          root=PARTUUID=B921B045-1D rw rootwait rootfstype=ext4 init=/sbin/init

# Mini2440，NFS 根
bootargs=noinitrd console=ttySAC0,115200 root=/dev/nfs rw          nfsroot=192.168.0.200:/work/nfs_root/rootfs ip=192.168.0.105:192.168.0.200:192.168.0.1:255.255.255.0::eth0:off

5.4 三种 panic 分别意味着什么 #

报错 含义 先查什么
VFS: Cannot open root device 根设备根本没找到 root= 写的设备名/PARTUUID 对不对；驱动是否编进内核（不是模块）
Kernel panic - not syncing: No working init found 根挂上了，但里面没有可执行的 init /sbin/init 在不在、有没有可执行位、是不是架构/动态库不匹配
Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block 设备找到了，文件系统类型不认识 rootfstype= 是否拼错；对应文件系统是否编进内核

第二条最容易误判：把一个 arm64 的 busybox 放进 x86 的镜像里，或者用了动态链接但 /lib 里没库，现象完全一样。

六、一个系统里并存多种文件系统 #

即便根文件系统是 ubifs，也不代表全系统只有 ubifs。实际挂载表大概长这样：

挂载点 类型 谁提供 为什么
/ ubifs / ext4 / squashfs 你的镜像 根
/dev devtmpfs 内核 设备节点随硬件自动生成
/proc procfs 内核 进程与内核信息
/sys sysfs 内核 设备模型、驱动属性
/dev/pts devpts 内核 伪终端（ssh 必需）
/tmp、/var、/run tmpfs 内核 避免写 Flash
/mnt/usb vfat/exfat 内核 + mdev 热插拔
ℹ笔记

/proc 是纯内存的伪文件系统，不占任何外部存储；/sys 则把内核里的设备与驱动信息映射到用户空间。两者职责经常被混为一谈——前者偏"进程与内核状态"，后者偏"设备模型"。

七、速查与坑位表 #

现象 原因 处理
启动成功但控制台无输出 /dev/console 不存在，或 /etc/inittab 里没给 console 起 shell 建 /dev/console（mknod c 5 1）或在 inittab 里加 ttyS0::askfirst:-/bin/sh
No working init found init 缺失 / 无执行位 / 架构或动态库不匹配 file init 看架构；静态链接试一次
ramdisk 挂不上 CONFIG_BLK_DEV_RAM_SIZE 小于解压后大小 调大，同时检查 initrd= 长度参数
NAND 上 jffs2 越用越慢 接近满盘时垃圾回收 预留空间；或换 ubifs
ubifs 挂载慢 扫描全部擦除块 开 CONFIG_UBI_FASTMAP，先以 ubi.fm_autoconvert=1 正常重启一次
小分区用 ubifs 反而更占空间 元数据开销 小分区（几 MB）改用 jffs2/yaffs2
/var/log 把 Flash 写坏 日志直接落盘 /var 挂 tmpfs，或日志转内存环形缓冲
只读根无法改配置 squashfs 只读 上 overlayfs：下层 squashfs，上层 tmpfs 或数据分区
