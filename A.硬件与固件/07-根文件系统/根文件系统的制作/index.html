零、全景：两条路线，选一条 #

路线 适合谁 时间成本 可复现性 体积控制
A. busybox 手搓 想搞懂每个文件从哪来；板子资源极小 半天到两天 靠脚本，容易漂移 极佳，精确到 KB
B. Buildroot 构建 要交付、要维护、要加软件包 首次配置 1~2 小时 完全靠 defconfig，可复现 好，靠 menuconfig 调

两条路线的产物是一样的：一棵目录树 + 一个文件（ext4 镜像 / yaffs2 镜像 / cpio.gz）。先学会 A，再看 B——否则 Buildroot 出问题时你不知道该看哪里。

一、busybox 手搓：从零到可启动 #

1.1 版本与工具链必须对齐 #

第一条铁律：交叉编译器要和编译内核时用的完全一致。内核用 aarch64-none-linux-gnu-gcc 12.2，busybox 也必须用它，否则动态库版本对不上，板子上会看到 not found 或 GLIBC_2.xx not found。

本文以 busybox 1.36.0 与 arm-gnu-toolchain-12.2.rel1 为例（RK3399，aarch64）；Mini2440 用的是 busybox 1.25.0 与 arm-linux-gcc，流程完全一样。

bash
mkdir rootfs && cd rootfs
wget https://busybox.net/downloads/busybox-1.36.0.tar.bz2
tar -jxf busybox-1.36.0.tar.bz2
cd busybox-1.36.0

1.2 配置：静态还是动态 #

bash
make defconfig
make menuconfig

Busybox Settings ---> 下：

text
    (/usr/local/arm/12.2.1/bin/arm-linux-) Cross compile prefix
    ( -march=armv8-a) additional CFLAGS
    ( ) Path to sysroot
    [ ] Build static binary (no shared libs)
    [*] Build Shared libbusybox
    (./_install) Destination path for 'make install'
选择 优点 缺点
静态（勾上 Build static binary） 不用部署动态库，镜像里只有 busybox 一个文件 体积大（约 1 MB+）；自己写的动态链接程序在这个 rootfs 里跑不了
动态（默认） 体积小，能跑自己交叉编译的程序 必须把工具链里的 ld-linux-*.so、libc.so*、libm.so*、libstdc++.so* 一起部署

第一次做建议先静态跑通，确认能起 init，再换动态补库。

1.3 需要开的常用项 #

text
Linux System Utilities --->
    [*] mdev (17 kb)
    [*] hexdump
Linux Module Utilities --->
    [*] depmod (27 kb)
    [*] Support module.aliases file
    [*] Support module.symbols file
    (/lib/modules) Default directory containing modules
    (modules.dep) Default name of modules.dep
Networking Utilities --->
    [*] Support /etc/networks
    [*] udhcpc (24 kb)
    (/usr/share/udhcpc/default.script) Absolute path to config script

mdev 决定能不能热插拔 U 盘/SD 卡；depmod 决定能不能用内核模块；udhcpc 决定能不能自动拿 IP。

1.4 编译与安装 #

bash
make
ll busybox            # -rwxr-xr-x 1 root root 1119768 ... busybox
make install

make install 装到 _install/：

text
_install/
├── bin/      # 符号链接：ls、cp、sh、cat …
├── sbin/     # 符号链接：init、ifconfig、mdev …
├── usr/      # bin/ sbin/ 的二级层次
├── lib64/    # 动态库（aarch64）
└── linuxrc -> bin/busybox

这还不是根文件系统，只是二进制集合。缺 /etc、/dev、/proc、/sys、/root、/tmp、/mnt 等。

二、拼目录树 #

2.1 复制二进制并补库 #

bash
mkdir ../busybox_install
cp -a _install/* ../busybox_install/
cd ../busybox_install
mkdir -p dev etc/init.d home lib lib64 mnt proc root sys tmp usr var

动态编译时把工具链的库拷进来（-a 保留权限与软链接本身）：

bash
cp -a /usr/local/arm/12.2.1/aarch64-none-linux-gnu/libc/lib/*so*   ./lib/
cp -a /usr/local/arm/12.2.1/aarch64-none-linux-gnu/libc/lib64/*so* ./lib64/
cp -a /usr/local/arm/12.2.1/aarch64-none-linux-gnu/libc/usr/lib/*so*   ./lib/
cp -a /usr/local/arm/12.2.1/aarch64-none-linux-gnu/libc/usr/lib64/*so* ./lib64/

不要整个 libc/ 目录照抄——里面有 *.a 静态库和调试符号，白占几 MB。只拷 *so*。

2.2 内核模块与固件 #

bash
# 内核编译输出里拷模块
make ARCH=arm64 INSTALL_MOD_PATH=/path/to/rootfs modules_install

# 或从同版本板子上直接 scp
scp -r pi@192.168.0.100:/lib/modules  ./lib
scp -r pi@192.168.0.100:/lib/firmware ./lib
⚠警告

模块和固件是体积膨胀的主因，而且会连锁影响三个参数：内核的 RAM disk size、Buildroot 的 exact size、分区表的 parameter.txt。三者任一不够，启动就会看到 BUG: Bad page state 或 no space left。加内容前先算体积，别等启动失败再回头查。

2.3 设备节点 #

现代内核用 devtmpfs 自动生成，/dev 保持空目录即可。只有两种情况下需要手动 mknod：

bash
# 内核没开 CONFIG_DEVTMPFS
mknod -m 600 dev/console c 5 1
mknod -m 666 dev/null    c 1 3
mknod -m 666 dev/zero    c 1 5

不开 devtmpfs 又没建 /dev/console，结果就是串口一行输出都没有——内核已经起来了，但第一个用户态进程没有标准输出。

三、四个必备配置文件 #

busybox 提供了范例，在 examples/bootfloppy/etc/ 下（fstab、inittab、profile、init.d/）。直接抄过来改比从零写好。

3.1 /etc/inittab #

ini
# /etc/inittab
# 格式: <id>:<runlevels>:<action>:<process>

# 系统初始化脚本：挂虚拟文件系统、建目录、跑 mdev
::sysinit:/etc/init.d/rcS

# 串口控制台：askfirst 表示等用户敲回车再起 shell（可改成 respawn 免登录）
ttyS2::askfirst:-/bin/sh
tty1::askfirst:-/bin/sh

# 崩溃自动重启的守护进程
::respawn:/usr/sbin/sshd -D
::respawn:/usr/sbin/syslogd -n -O /var/log/messages

# 关机/重启时的清理：同步卸载，防止写坏 Flash
::ctrlaltdel:/sbin/reboot
::shutdown:/bin/umount -a -r
::shutdown:/sbin/swapoff -a
action 含义
sysinit 最先执行，仅一次
wait 执行一次，init 等它结束
once 执行一次，不等
respawn 退出就重启（守护进程用）
askfirst 显示提示，等回车后启动
shutdown / ctrlaltdel 关机 / 重启时执行

ttyS2 这个名字必须和实际串口设备名一致（RK3399 是 ttyS2，Mini2440 是 ttySAC0，树莓派是 ttyAMA0）。写错就是"起来了但没 shell"。

3.2 /etc/init.d/rcS #

bash
#!/bin/sh

# 挂载 /etc/fstab 中定义的所有文件系统
/bin/mount -a

# 挂载虚拟的 devpts，ssh 等伪终端需要
/bin/mkdir -p /dev/pts
/bin/mount -t devpts devpts /dev/pts

# 扫描并创建设备节点
/sbin/mdev -s

# 加载网卡驱动
/sbin/modprobe r8125

# 自动配置网络（DHCP）
/sbin/udhcpc

# 按顺序执行所有 init 脚本
for i in /etc/init.d/S??* ; do
     [ ! -f "$i" ] && continue
     case "$i" in
        *.sh) ( trap - INT QUIT TSTP; set start; . $i ) ;;
        *)    $i start ;;
     esac
done

别忘了执行位：

bash
chmod 755 etc/init.d/rcS
chmod -R 755 etc/init.d/

3.3 /etc/fstab #

ini
# <file system>  <mount point>  <type>   <options>       <dump> <pass>
proc             /proc          proc     defaults        0      0
sysfs            /sys           sysfs    defaults        0      0
devpts           /dev/pts       devpts   defaults        0      0
tmpfs            /tmp           tmpfs    defaults        0      0
tmpfs            /var           tmpfs    size=16m        0      0

把 /tmp 和 /var 挂 tmpfs 是嵌入式的基本操作：日志和临时文件不落 Flash，寿命能延长很多。

3.4 /etc/profile #

bash
#!/bin/sh
export PATH=/bin:/sbin:/usr/bin:/usr/sbin
export PS1='[\u@\h \w]\$ '
export HOSTNAME=$(hostname)
export LD_LIBRARY_PATH=/lib:/lib64:/usr/lib

LD_LIBRARY_PATH 写错是"busybox 能跑、自己程序跑不了"的常见原因。

四、动态设备管理：mdev #

4.1 三种机制，选哪个 #

机制 工作方式 建议
静态 /dev 预先在镜像里放死设备节点 不推荐
devtmpfs 内核自动在 /dev 生成节点 默认就够用
mdev / eudev 在 devtmpfs 之上跑用户态守护，热插拔时触发脚本 需要"插上 U 盘自动挂载"时才上

4.2 mdev.conf 规则 #

ini
# /etc/mdev.conf
# 格式: <device regex> <uid>:<gid> <octal permissions> [=|>path] [@|*|!command]

# 串口：只允许 dialout 组访问
ttyS[0-9]*    0:20   660
ttyAMA[0-9]*  0:20   660

# 声卡设备放进 snd 子目录，属主 audio
snd/.*        0:18   660

# U 盘/SD 卡热插拔时执行挂载脚本
sd[a-z][0-9]* 0:0    660  * /lib/mdev/usb_hotplug

# 网口热插拔
(eth|wlan)[0-9]* 0:0 660  * /lib/mdev/net_hotplug

符号含义：* 在设备插入和移除时都执行；= 改节点名；> 创建符号链接；! 只执行不创建设备节点。

4.3 热插拔脚本 #

bash
#!/bin/sh
# /lib/mdev/usb_hotplug
# mdev 自动注入 $MDEV（设备名）和 $ACTION（add/remove）

LOG_FILE="/var/log/usb_hotplug.log"
echo "[$(date)] Hotplug event: ${ACTION} on ${MDEV}" >> ${LOG_FILE}

case "${ACTION}" in
    add|ADD)
        MOUNT_POINT="/mnt/usb_${MDEV}"
        mkdir -p ${MOUNT_POINT}
        if mount -o noatime,sync,utf8 /dev/${MDEV} ${MOUNT_POINT} 2>>${LOG_FILE}; then
            echo "[*] mounted /dev/${MDEV} -> ${MOUNT_POINT}" >> ${LOG_FILE}
        else
            echo "[!] mount failed: /dev/${MDEV}" >> ${LOG_FILE}
            rmdir ${MOUNT_POINT}
        fi
        ;;
    remove|REMOVE)
        umount /mnt/usb_${MDEV} 2>/dev/null
        rmdir  /mnt/usb_${MDEV} 2>/dev/null
        ;;
esac

五、最简实验：不要 busybox，手写一个 init #

想彻底搞懂"内核怎么把控制权交给用户空间"，最快的办法是写一个几十行的 init，打成 initramfs 跑一次。

5.1 一个会回显的 init #

c
#include <stdio.h>

int main(void)
{
    char ch;

    printf("Test /sbin/init main....\n");
    printf("0123456789abcdefghijklmnopqrstuvwxyz\n");
    printf("ABCDEFGHIJKLMNOPQRSTUVWXYZ9876543210\n");

    while ((ch = getchar()) != 'q')
        printf("%c", ch);

    return 0;
}

关键前提：内核启动时会打开 /dev/console，把 stdin(0)、stdout(1)、stderr(2) 都指向它，然后执行 init 并把这三个描述符继承下去。所以：

  • init 里的 printf → 走 stdout → 串口 TX
  • init 里的 getchar → 走 stdin → 串口 RX

这就是"没有任何驱动、没有文件系统，也能在串口上看到输出"的全部秘密。

bash
aarch64-linux-gnu-gcc -static -o init init.c     # 必须静态
file init                                        # ELF 64-bit LSB, statically linked
mkdir -p out/rootfs/sbin
cp init out/rootfs/sbin/init

5.2 打包 #

makefile
initramfs:
	mkdir -p $(OUT_DIR)
	cd $(ROOTFS_OUT_DIR); find . | cpio -H newc -o | gzip -9 -n > $(OUT_DIR)/initramfs.gz

内核配置（两项）：

text
General setup  --->
    [*] Initial RAM filesystem and RAM disk (initramfs/initrd) support
Userspace binary formats  --->
    [*] Kernel support for ELF binaries

启动参数：

text
CONFIG_CMDLINE="earlycon=owl_serial console=ttyS5 loglevel=8 root=/dev/ram0 init=/sbin/init"

5.3 这个实验最容易踩的两个坑 #

现象 真实原因
printf 输出不完整、getchar 没反应 GIC 没配好，串口中断进不来。ARM64 的 GIC 部分寄存器必须在 EL3 配置，而内核运行在 EL1 改不了 → 要在 bootloader 里打开（如 U-Boot 加 CONFIG_GICV2 与 GICD_BASE/GICC_BASE）
完全没有输出 init 没静态链接，或没放对位置（cpio-initrd 的入口是 /init，不是 /sbin/init）

六、Buildroot：把上面所有步骤变成一个 defconfig #

busybox 路线的问题不是难，而是不可复现——换个同事、换台机器，结果就不一样。Buildroot 用一份 defconfig 描述整个系统，make 一把梭。

6.1 与 Yocto 的分工 #

对比项 Buildroot Yocto
学习曲线 低，Kconfig + Makefile 高，layer/recipe/bitbake
构建速度 快 慢，但支持 sstate 缓存
扩展能力 弱，靠 post-build 脚本 强，官方 BSP 多
典型产物 十几 MB 的定制镜像 几十到几百 MB 的发行版级镜像
代表项目 OpenWrt 各大芯片厂商 SDK

一句话：镜像要小、要快要简单 → Buildroot；要维护几百个包、要长期演进 → Yocto。

6.2 最小系统必须确认的几项 #

bash
make menuconfig
配置项 位置 要点
Target Architecture Target options aarch64 / arm，必须与工具链一致
Target ABI Target options 决定 glibc 还是 musl
Toolchain Toolchain 内置工具链或外部预编译工具链
System configuration System configuration 主机名、root 密码、/dev 管理方式、init 系统
Kernel Kernel 是否由 Buildroot 编译内核、defconfig 名、设备树
Target packages Target packages 要哪个包就在这勾
Filesystem images Filesystem images ext2/3/4、squashfs、cpio、ubi 等，勾哪个出哪个

6.3 输出目录里都是什么 #

text
output/
├── build/          # 各包的源码与构建中间产物
├── host/           # 主机侧工具（交叉编译器、mkimage、mkenvimage…）
├── images/         # 最终产物：rootfs.ext4、zImage、Image、*.dtb
├── staging/        # 头文件与库的"安装暂存区"，供其它包编译时用
├── target/         # 目标 rootfs 的完整目录树（还没打包）
└── .config

排查问题时最有用的两个：output/target/（看最终 rootfs 里到底有什么）和 output/build/<包名>-<版本>（看某个包为什么编译失败）。

6.4 配置持久化——最容易丢的东西 #

make clean 会删掉 output/，.config 也跟着没了。必须导出成 defconfig：

bash
make savedefconfig                       # 生成精简版 defconfig
cp defconfig configs/myboard_defconfig   # 放到 configs 下，才能 build.sh 引用

内核侧的修改（menuconfig 改的选项、打的补丁）同样会丢，得靠：

bash
# 方式一：自定义内核 fragment
BR2_LINUX_KERNEL_CONFIG_FRAGMENT_FILES="board/myboard/kernel.fragment"

# 方式二：打补丁目录
BR2_GLOBAL_PATCH_DIR="board/myboard/patches"
⚠警告

只改 output/build/linux-*/ 里的代码是无效的，下次 make clean 后全部还原。所有内核/驱动修改必须落到 fragment 或 patch 目录。

6.5 三个进阶定制点 #

需求 手段 说明
往 rootfs 里塞自己的文件 BR2_ROOTFS_OVERLAY 指向一个目录，构建时原样覆盖到 rootfs
构建后跑脚本改东西 BR2_ROOTFS_POST_BUILD_SCRIPT 加用户、删文件、改权限
生成可烧写的 SD/eMMC 整盘镜像 BR2_ROOTFS_POST_IMAGE_SCRIPT 调 genimage，自动分区与烧写
权限与用户定制 BR2_ROOTFS_DEVICE_TABLE / BR2_ROOTFS_USERS_TABLES 声明式配置 SUID、属主，不用手写 chmod
自研软件包 package/<name>/<name>.mk generic-package 或 cmake-package 范式
本地改包源码 OVERRIDE_SRCDIR 让某个包直接用你本地 git 目录编译，改一行重编一次

overlay 的最小用法：

bash
# board/myboard/rootfs_overlay/etc/inittab
# board/myboard/rootfs_overlay/etc/init.d/S99myapp
# 在 defconfig 里：
BR2_ROOTFS_OVERLAY="board/myboard/rootfs_overlay"

6.6 初始化系统的三种选择 #

Buildroot 里 System configuration → Init system 可选：

方案 配置入口 特点
BusyBox init /etc/inittab 极轻（几百 ms），无运行级别，全部手写
SystemV init /etc/init.d/S??* 有运行级别概念，脚本以 S/K + 两位数字排序
systemd .service + target 现代、并行启动、依赖管理，体积大

SystemV 风格的服务脚本范式：

bash
#!/bin/sh
# /etc/init.d/S50sshd

case "$1" in
    start)
        echo -n "Starting sshd: "
        start-stop-daemon -S -q -p /var/run/sshd.pid -x /usr/sbin/sshd -- -D &
        [ $? -eq 0 ] && echo "OK" || echo "FAIL"
        ;;
    stop)
        echo -n "Stopping sshd: "
        start-stop-daemon -K -q -p /var/run/sshd.pid
        [ $? -eq 0 ] && echo "OK" || echo "FAIL"
        ;;
    restart|reload) $0 stop; sleep 1; $0 start ;;
    *) echo "Usage: $0 {start|stop|restart}"; exit 1 ;;
esac

systemd 服务范式：

ini
[Unit]
Description=Geek Core Business Application
After=network.target syslog.target

[Service]
Type=simple
ExecStart=/usr/bin/geek_app --config /etc/geek_app.conf
Restart=on-failure
RestartSec=5
User=www
WorkingDirectory=/var/www
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target

七、打包成镜像 #

目录树做完，最后一步是变成"能烧的东西"。格式取决于介质。

7.1 ext4（eMMC / SD，最常用） #

bash
# 1. 建空镜像，count 取目录大小的 2 倍左右
du -sh busybox_install
dd if=/dev/zero of=rootfs.img bs=1M count=300
mkfs.ext4 rootfs.img

# 2. 挂上来灌内容
mkdir -p mnt_rootfs
mount rootfs.img mnt_rootfs
cp -a busybox_install/* mnt_rootfs/
df mnt_rootfs                 # 确认占用
umount mnt_rootfs

# 3. 检查并压缩到最小
e2fsck -p -f rootfs.img
resize2fs -M rootfs.img       # -M 缩到最小

# 4. 看最终大小
ll rootfs.img && du -sh rootfs.img

一个真实数字：300 MB 的空镜像，灌进 busybox rootfs 后 resize2fs -M 压到 114 MB。

7.2 gzip 成 ramdisk #

bash
gzip -v9 rootfs.img
mv rootfs.img.gz ramdisk.gz

同时要保证内核开了 CONFIG_BLK_DEV_RAM，且 CONFIG_BLK_DEV_RAM_SIZE 大于解压后大小。启动时 bootloader 把 ramdisk.gz 读到内存固定地址，bootargs 里 root=/dev/ram0 initrd=<地址>,<长度>。

7.3 yaffs2（裸 NAND） #

适合 Mini2440 这类 256 MB NAND 的板子（型号 K9F2G08U0C）。

bash
git clone git://www.aleph1.co.uk/yaffs2
# 把 yaffs2 目录放进内核源码 fs/ 下，改 fs/Kconfig 与 fs/Makefile，编译内核得到 yaffs2 支持

# 用 mkyaffs2image 打包
./mkyaffs2image rootfs/ rootfs-yaffs2.img

yaffs 与 yaffs2 的区别只有一条：yaffs 只支持小页（512B+16B）NAND，yaffs2 支持大页（2KB+64B）。256 MB 的板子必须用 yaffs2。

7.4 cpio.gz（initramfs） #

bash
cd rootfs
find . | cpio -H newc -o | gzip -9 -n > ../rootfs.cpio.gz

这个产物既可以编进内核（CONFIG_INITRAMFS_SOURCE），也可以由 bootloader 单独加载。

7.5 格式对照 #

目标介质 格式 打包工具 内核要求
eMMC / SD ext4 dd + mkfs.ext4 + mount + resize2fs CONFIG_EXT4_FS
eMMC 只读 squashfs mksquashfs CONFIG_SQUASHFS
裸 NAND yaffs2 mkyaffs2image yaffs2 补丁

八、裁剪：体积从哪来，砍哪里 #

8.1 裁剪论文给出的排序 #

几篇 2006~2015 的裁剪论文结论高度一致，按收益排序：

  1. 库：glibc → uClibc / musl，或改静态链接，省几 MB
  2. 命令集：busybox 里关掉用不到的命令（tar/gzip/vi 是大户）
  3. 内核模块：只保留板子实际硬件需要的 .ko
  4. 文档与 locale：/usr/share/doc、/usr/share/locale 全删
  5. 调试符号：strip 所有二进制
  6. 文件系统压缩：squashfs / ubifs 的压缩选项

8.2 实战：OK3568 从 1.28 GB 砍到 0.7 GB #

飞凌 OK3568 的官方 Buildroot 镜像初始 1.28 GB，目标 0.7 GB。整个编译链路由根目录 build.sh 驱动：

text
build.sh rootfs
  └─ build_rootfs()                 # 按参数选 yocto / debian / distro / buildroot
       └─ build_buildroot()
            └─ device/rockchip/common/mk-buildroot.sh
                 └─ buildroot/build/envsetup.sh
                      └─ 读取 buildroot/configs/OK3568_defconfig
                           └─ 覆盖 buildroot/.config

所以要改配置，正确做法是改 OK3568_defconfig（或改 .config 后再 savedefconfig 回写），而不是临时手动改 .config——下次 build.sh 会覆盖它。

❢重要

取消一个包不等于镜像变小。 取消 BR2_PACKAGE_TENSORFLOW 只影响"是否编译该包"，已安装的库文件、依赖它的其它包、以及固件仍会留在 rootfs 里。真正减体积要靠：① 连依赖一起清（make graph-depends 看依赖树）；② 清 /usr/share 下的文档、locale、示例；③ 用 BR2_TARGET_ROOTFS_EXT2_SIZE 压到实际需要；④ 最后 squashfs 上压缩。

8.3 启动时间优化（顺带） #

rootfs 太大也会拖慢启动。常见手段：

手段 做法 效果
bootchart busybox 开 CONFIG_BOOTCHARTD，init=/sbin/bootchartd 启动，导出 /var/log/bootlog.tgz，主机上 java -jar bootchart.jar bootlog.tgz 出图 定位时间花在哪
systemd-analyze systemd 系统直接 systemd-analyze blame 列出各服务耗时
减少 fork 把要最先启动的程序直接做成 init（或 inittab 里第一个 respawn） 省掉多次 /bin/sh 调用
并行启动 SysV 脚本改成按依赖并行；systemd 天然并行 明显
只读根 + overlay squashfs 挂载快，写入走 overlay 挂载阶段从秒级到百毫秒级
