一、先把启动时间拆开 #

不看分段的优化都是瞎猜。嵌入式板子从上电到应用起来，大致五段：

阶段 执行者 典型耗时 能砍到什么程度
BootROM 片内 ROM 固化代码 10~50ms 不可改
SPL / BL1 片内 SRAM 里的第一段 20~80ms 可裁剪，可跳过主 U-Boot
主 U-Boot DDR 里的完整 U-Boot 200ms~1s 裁剪 + 静默 + 去校验
内核解压与初始化 Linux 1~5s 内核裁剪、驱动异步 probe
用户态 init / 应用 差别巨大 与本文无关

主 U-Boot 这一段最容易下手——它的大部分时间花在探测硬件和打印日志上，而不是真在干活。

二、配置层能砍的五刀 #

2.1 干掉 bootdelay 停顿 #

bash
setenv bootdelay 0
saveenv

但只设 0 会有个副作用：万一启动失败，你没有任何机会按 Ctrl+C 进命令行，只能重新烧。所以还要配合打开：

c
/* include/configs/<board>.h */
#define CONFIG_ZERO_BOOTDELAY_CHECK

它的作用是：bootdelay 为 0 时仍然短暂轮询控制台，只要检测到有键按下就跳回交互 Shell。量产日志里看不到任何延迟，研发手里却能随时打断。

2.2 静默控制台 #

c
#define CONFIG_SILENT_CONSOLE

运行时配合环境变量 silent=yes 生效，把引导期间的所有打印吞掉。省下的不只是串口带宽——每一条 printf 都是同步轮询发送，波特率 115200 时一行 80 字符要 7ms，几十行就是几百毫秒。

排查问题时把 silent 设成空即可恢复输出，比重新编译快得多。

2.3 关掉镜像校验 #

bash
setenv verify no

bootm 默认会算一遍 CRC32。对 8MB 的 uImage 来说这一步通常几十到上百毫秒。开发阶段留着，量产可以关——前提是你的加载通道本身可信（片内 eMMC/NAND 读取，而不是网络）。

2.4 裁掉用不到的命令 #

命令是 CONFIG_CMD_* 宏控制的，关掉一个就少一个 .o。真正影响启动时间的不是代码体积，而是初始化函数：每个还活着的子系统都要在 init_sequence_r 里跑一遍 probe。

量产固件里通常可以关掉：USB、CONFIG_CMD_FS_* 系列、CONFIG_CMD_DATE、各种 CONFIG_CMD_*TEST。裁完记得 bdinfo 看一眼 mon_len 少了多少。

2.5 别让 SPL 重复做一遍主 U-Boot 要做的事 #

常见错误：SPL 里已经把 DDR 初始化好了，主 U-Boot 又初始化一遍。确认 CONFIG_SKIP_LOWLEVEL_INIT 与 lowlevel_init 的实际内容，别让同一段代码跑两遍。

三、消除内核的二次搬移 #

bootm 加载 uImage 的默认流程是「读到临时地址 → 读 64 字节头部 → 把内核搬到最终运行地址」。如果临时地址和最终地址不同，这一趟 memmove 就白费了。

uImage 头部固定 64 字节（IH_SIZE），所以只要把加载地址算准，内核落地时就已经在目标位置上：

text
加载地址 = 内核运行地址 - 64 字节（uImage 头）

举例：内核运行地址 0x20008000，那就把 uImage 直接读到 0x20007FC0。U-Boot 在 bootm 里会发现 images->os.load 已经等于目标地址，自动跳过搬移。

bash
=> tftp 0x20007FC0 uImage
=> bootm 0x20007FC0

省下的是几十毫秒到几百毫秒（取决于内核大小与 DDR 带宽）。代价是可读性变差——地址不再整齐，写进启动脚本时务必加注释。

四、Falcon 模式：让 SPL 直接起内核 #

前面所有优化加起来，主 U-Boot 这一段的固定开销（重定位、板级 probe、控制台初始化）还是消不掉。想再往下走，只能把它整个跳过。

Falcon 模式的思路：SPL 本来就已经初始化好了 DDR，那它完全可以直接加载内核并跳过去，主 U-Boot 一次都不运行。

4.1 配置 #

c
#define CONFIG_SPL_OS_BOOT

4.2 导出启动参数 #

SPL 不知道内核需要什么 bootargs、加载到哪里、设备树在哪。这些信息要靠主 U-Boot 跑一次来生成并固化进 Flash：

bash
# 主 U-Boot 命令行里
=> tftp 0x48000000 uImage
=> tftp 0x49000000 s5p6818-nanopi3.dtb
=> spl export fdt 0x48000000 - 0x49000000

spl export fdt <kernel> <ramdisk|-> <fdt> 会把「内核该放哪、参数是什么、FDT 放哪」打包成一段结构，写到 Flash 的固定位置。

4.3 下次上电 #

SPL 启动后先看那段参数在不在：在 → 直接加载内核跳过去（主 U-Boot 完全不执行）；不在 → 正常启动主 U-Boot。所以第一次烧写后仍要走一次完整流程，导出过之后才是 Falcon。

4.4 代价 #

失去的能力 影响
命令行 现场没法 tftp 换内核、没法 printenv 排障
环境变量 改动必须重新 spl export
网络启动 SPL 里的网络栈是极简版，只有 UDP
调试可见性 出问题只能看 SPL 的日志

结论：Falcon 适合定型后的量产，开发阶段别开。切换成本是把主 U-Boot 保留在 Flash 里、只是不让它默认运行。

五、两个和优化无关但绕不开的机制 #

5.1 X-Macro：gd->jt 跳转表怎么来的 #

gd_t 里有个 void **jt，这是个函数跳转表，printf、malloc、udelay 这类基础函数都通过它间接调用。它是 X-Macro 生成的：

c
/* include/_exports.h —— 清单文件，只列名字 */
EXPORT_FUNC(get_version)
EXPORT_FUNC(getc)
EXPORT_FUNC(tstc)
EXPORT_FUNC(putc)
EXPORT_FUNC(puts)
EXPORT_FUNC(printf)
EXPORT_FUNC(install_hdlr)
EXPORT_FUNC(free_hdlr)
EXPORT_FUNC(malloc)
EXPORT_FUNC(free)
EXPORT_FUNC(udelay)

c
/* include/exports.h —— 第一重展开：变成结构体成员 */
struct jt_funcs {
#define EXPORT_FUNC_ENTRY(sym)  void (*sym)(void);
#include <_exports.h>
#undef EXPORT_FUNC_ENTRY
};

c
/* common/exports.c —— 第二重展开：变成初始化语句 */
static void **jt;
#define EXPORT_FUNC_ENTRY(sym)  jt[i++] = (void *)sym;
int jumptable_init(void)
{
    int i = 0;
    jt = malloc(sizeof(struct jt_funcs) + 4);
#include <_exports.h>
    gd->jt = jt;
    return 0;
}
#undef EXPORT_FUNC_ENTRY

同一份清单，include 两次、宏定义换两次，就同时生成了「声明」和「赋值」。加一个函数只需在 _exports.h 里加一行——这就是它在 U-Boot 里活到现在的原因。

这类「清单 + 多态 include」的写法在本仓库其他地方也出现过：.u_boot_list 段注册表、of_device_id 表、CLK_OF_DECLARE，本质都是用编译期结构替代运行期注册代码。

5.2 网卡驱动的双轨制 #

老驱动和新驱动在同一个 U-Boot 里共存，靠 CONFIG_DM_ETH 区分：

Legacy 模式 DM 模式
结构体 struct eth_device struct udevice + eth_ops
注册方式 手写 eth_register() 挂进全局链表 U_BOOT_DRIVER 声明，按设备树匹配自动实例化
初始化入口 <drv>_initialize(bd_t *bis) .probe 回调
典型例子 rtl8139_initialize、dm9000_initialize U_BOOT_DRIVER(mcs7830_eth)

老写法一眼能认出来：

c
int rtl8139_initialize(bd_t *bis)
{
    struct eth_device *dev = malloc(sizeof(*dev));
    memset(dev, 0, sizeof(*dev));
    sprintf(dev->name, "RTL8139#%d", card_number);
    dev->iobase = bus_to_phys(iobase);
    dev->init   = rtl8139_probe;
    dev->halt   = rtl_disable;
    dev->send   = rtl_transmit;
    dev->recv   = rtl_poll;
    eth_register(dev);        /* 手动挂进链表 */
    return 1;
}

新写法：

c
static const struct eth_ops mcs7830_eth_ops = {
    .start        = mcs7830_eth_start,
    .send         = mcs7830_eth_send,
    .recv         = mcs7830_eth_recv,
    .free_pkt     = mcs7830_free_pkt,
    .stop         = mcs7830_eth_stop,
    .write_hwaddr = mcs7830_write_hwaddr,
};

U_BOOT_DRIVER(mcs7830_eth) = {
    .name  = "mcs7830_eth",
    .id    = UCLASS_ETH,
    .probe = mcs7830_eth_probe,
    .ops   = &mcs7830_eth_ops,
};

移植老驱动到新框架时最常踩的坑：以为 board_eth_init 还要留着。DM 模式下 eth_initialize() 会自己遍历 UCLASS_ETH 设备，board_eth_init 只在没有 DM 时才需要。

六、优化完怎么验证 #

别靠秒表掐串口。开 CONFIG_BOOTSTAGE，它会在关键节点打时间戳，进命令行后 bootstage report 直接出分段耗时表。没有这个宏时，退一步的做法是在 board_init_f、board_init_r、bootm 前后各打一行带 get_timer(0) 的打印，差值就是耗时。

小结 #

  • 优化顺序：先测量（bootstage）→ 再去掉无用 probe（裁命令）→ 再压固定开销（bootdelay/silent/verify）→ 最后才考虑 Falcon。
  • 消除内核二次搬移是性价比最高的一招：改一个加载地址，省几十上百毫秒，不改任何代码。
  • Falcon 模式的本质是「把主 U-Boot 变成只跑一次的配置工具」，适合定型产品，不适合开发板。
  • gd->jt、.u_boot_list、of_device_id、CLK_OF_DECLARE 是同一个套路：用链接期数据结构替代运行期注册代码，既省代码又省启动时间。
