一、先看地图：顶层目录怎么分工 #

u-boot 顶层二十来个子目录，按性质分三类：

类别 目录 说明
与处理器/板级强相关 arch 体系结构相关（arm、m68k、mips、powerpc、x86…）。用 ARM 只看 arch/arm
arch/arm/cpu CPU 核相关初始化，起始代码 start.S 在这里
board 板级目录，含 SDRAM、FLASH 驱动，如 board/samsung/smdk2410
configs 板级配置文件，统一命名 xxx_defconfig
通用函数与驱动 common 硬件无关的通用代码，主力是 cmd*（命令系统）与 env*（环境变量）
drivers 从 Linux 抠出来的驱动：网卡、MMC/SD、NAND、GPIO、pinctrl
fs 文件系统（FAT、EXT4、UBIFS、YAFFS2…），同样移植自 Linux
net tftp、nfs、ping、BOOTP 协议实现
lib 架构相关库（lib/strto.c、lib/vsprintf.c）
dts 设备树源码与编译产物 dt.dtb
应用/工具/文档 cmd 命令相关（新版本已并入 common）
disk 磁盘分区相关
include 所有头文件集中存放，不跟随 .c，包含路径要到这里找
tools 宿主工具，最常用的是 mkimage
scripts 构建脚本：Kbuild.include、Makefile.build、kconfig/
post 加电自检
doc 文档，doc/README.* 是移植时的第一手资料

移植一块新板子，真正要碰的就是 arch/arm/cpu/<cpu>、board/<vendor>/<board>、configs/<board>_defconfig、include/configs/<board>.h 这四处，其余都是共用的。

二、配置体系的两代：mkconfig 与 Kconfig #

这一点必须先分清，否则看老教程会全线错位。u-boot 的配置方式在 2014 年前后换过一次代：

老版本（≤ 2013.10） 新版本（≥ 2014.04）
板子清单 boards.cfg 一张表 configs/*_defconfig 每板一个文件
配置入口 make <board>_config make <board>_defconfig
执行脚本 mkconfig + %_config 规则 scripts/kconfig/conf + Kconfig
板级头文件 include/configs/<board>.h 同左（新老都留）
生成的中间物 include/config.mk .config、include/config/auto.conf、include/generated/autoconf.h

2.1 老版：mkconfig 的六个参数 #

make fs4412_config 在 u-boot-2013.01 的顶层 Makefile 里匹配到这条规则：

makefile
%_config: unconfig
    @$(MKCONFIG) $(@:_config=) arm armv7 fs4412 samsung exynos

$(@:_config=) 是 GNU make 的替换引用，把目标名 fs4412_config 里的 _config 去掉，得到 fs4412。所以这条规则实际执行的是：

bash
$ ./mkconfig  fs4412  arm  armv7  fs4412  samsung  exynos

六个参数按位置对应：

位置 值 含义 落到哪儿
$1 fs4412 BOARD_NAME，板子名 生成的 include/config.mk 里的 BOARD
$2 arm ARCH，体系结构 arch/arm/
$3 armv7 CPU，CPU 核 arch/arm/cpu/armv7/
$4 fs4412 BOARD，板级目录名 board/samsung/fs4412/
$5 samsung VENDOR，厂商 board/samsung/
$6 exynos SOC，片上系统 arch/arm/include/asm/arch-exynos

mkconfig 是个 shell 脚本，干三件事：

  1. 解析 boards.cfg，按板名查出这一行的 ARCH CPU BOARD VENDOR SOC 五个字段，确认板子已登记；
  2. 建符号链接，把 arch/arm/include/asm/arch-<soc> 链到 arch/arm/include/asm/arch，这样驱动里统一写 #include <asm/arch/xxx.h> 就能自动指到对应 SoC；
  3. 生成 include/config.mk，内容是 ARCH/CPU/BOARD/VENDOR/SOC 五个变量，被顶层 Makefile 直接 include，于是 $(CPU) 展开成 armv7、$(BOARDDIR) 展开成 samsung/fs4412。

boards.cfg 是纯文本表，列用空格或制表符分隔：

text
# Status  Arch  CPU      SoC      Vendor    Board    Target       Options
Active    arm   armv7    exynos   samsung   origen   -            -
Active    arm   armv7    exynos   samsung   fs4412   -            -
Active    arm   arm920t  s3c24x0  samsung   smdk2410 -            -

加自己的板子就是在 board/samsung/ 下建目录、include/configs/ 下建头文件、再在 boards.cfg 里加一行。这也是为什么老教程里全是「复制 origen 改名 fs4412」这种操作。

2.2 新版：make smdk2410_defconfig 的三步 #

以 u-boot-2016.05 为例。加 V=1 看完整命令：

bash
make smdk2410_defconfig V=1

展开成三步：

bash
# 第一步：编出 fixdep，用于后续每个目标的依赖跟踪
make -f ./scripts/Makefile.build obj=scripts/basic
# 第二步：编出 conf 配置工具
make -f ./scripts/Makefile.build obj=scripts/kconfig smdk2410_defconfig
# 第三步：用 conf 把 defconfig 展开成 .config
scripts/kconfig/conf --defconfig=configs/smdk2410_defconfig Kconfig

规则是怎么匹配到的。顶层 Makefile 里只有这么一条通用规则（第 476 行附近）：

makefile
%config: scripts_basic outputmakefile FORCE
    $(Q)$(MAKE) $(build)=scripts/kconfig $@

$(build) 定义在 scripts/Kbuild.include：

makefile
build := -f $(srctree)/scripts/Makefile.build obj

所以规则展开成 make -f scripts/Makefile.build obj=scripts/kconfig smdk2410_defconfig。scripts/Makefile.build 按 obj= 推出 src=（并负责剥离 spl/、tpl/ 前缀），再包含对应目录的 Kbuild 或 Makefile——Kbuild 优先于 Makefile：

makefile
# The filename Kbuild has precedence over Makefile
kbuild-dir := $(if $(filter /%,$(src)),$(src),$(srctree)/$(src))
kbuild-file := $(if $(wildcard $(kbuild-dir)/Kbuild),$(kbuild-dir)/Kbuild,$(kbuild-dir)/Makefile)
include $(kbuild-file)

scripts/kconfig/Makefile 里的 defconfig 规则：

makefile
%_defconfig: $(obj)/conf
    $(Q)$< $(silent) --defconfig=arch/$(SRCARCH)/configs/$@ $(Kconfig)

三个依赖各有分工：

  • scripts_basic：编出 scripts/basic/fixdep。它的作用是为每个生成目标维护一个 .xxx.cmd 依赖文件，记录上次用的完整命令行。增量编译判断「参数变了没」就靠它。
  • outputmakefile：只在 make ... O=out 指定独立输出目录时才动作，导出一个 source 软链接和一层 makefile。源码内编译时它是空目标。
  • FORCE：空目标（FORCE: 后面不跟命令）。任何依赖它的目标每次都会被判定「需要更新」，于是 smdk2410_defconfig 的命令总会执行——这就是配置命令能反复跑的原因。

conf 的行为一句话概括：从根目录开始树状解析 Kconfig，建出完整符号表，再用 configs/smdk2410_defconfig 里的值覆盖默认值，最后把结果写成 .config。

configs/smdk2410_defconfig 本身很短，就是个 CONFIG_xxx=y 清单：

text
CONFIG_ARM=y
CONFIG_TARGET_SMDK2410=y
CONFIG_SYS_PROMPT="SMDK2410 # "
CONFIG_CMD_USB=y
# CONFIG_CMD_SETEXPR is not set
CONFIG_CMD_DHCP=y
CONFIG_CMD_PING=y
CONFIG_CMD_CACHE=y
CONFIG_CMD_EXT2=y
CONFIG_CMD_FAT=y

注意 configs/ 里没有 smdk2440_defconfig。要给 S3C2440 编译，只能借最接近的 smdk2410_defconfig 起步，再改板级头文件和 CPU 目录——这是 Mini2440 移植的第一步。

三、编译链路：从 _all 到 u-boot.bin #

3.1 默认目标链 #

makefile
PHONY := _all
_all:

makefile
PHONY += all
ifeq ($(KBUILD_EXTMOD),)
_all: all
else
_all: modules
endif

没有编译外部模块（没给 M=）时，_all 依赖 all；all 依赖 $(ALL-y)（第 803 行）：

makefile
# Always append ALL so that arch config.mk's can add custom ones
ALL-y += u-boot.srec u-boot.bin u-boot.sym System.map u-boot.cfg binary_size_check

ALL-$(CONFIG_SPL) += spl/u-boot-spl.bin
ALL-$(CONFIG_SPL_FRAMEWORK) += u-boot.img       # 加了 0x40 字节头的镜像
ALL-$(CONFIG_TPL) += tpl/u-boot-tpl.bin
ALL-$(CONFIG_OF_SEPARATE) += u-boot.dtb         # 设备树分离编译
ALL-$(CONFIG_REMAKE_ELF) += u-boot.elf          # 带调试信息，可 gdb

第一条是永远会编的通用产物，后面每一条都由 CONFIG_xxx 门控。通用产物里除了 u-boot.cfg，全部依赖 u-boot——那是链接出来的 ELF。

3.2 V=1 到底改了什么 #

makefile
ifeq ("$(origin V)", "command line")
  KBUILD_VERBOSE = $(V)
endif
ifndef KBUILD_VERBOSE
  KBUILD_VERBOSE = 0
endif

ifeq ($(KBUILD_VERBOSE),1)
  quiet =
  Q =
else
  quiet=quiet_
  Q = @
endif

V=1 时 quiet 和 Q 都为空，命令整条回显；V=0（默认）时 Q=@ 抑制回显，只剩 quiet_cmd_xxx 里的短标签，比如 CC lib/vsprintf.o、 LD u-boot。三种形态由 $(quiet)cmd_$(1) 决定：空 = 全打印，quiet_ = 短版本，silent_ = 不打印。

真正干活的是 scripts/Kbuild.include 里的 if_changed：

makefile
if_changed = $(if $(strip $(any-prereq) $(arg-check)),   \
    @set -e;                                            \
    $(echo-cmd) $(cmd_$(1));                            \
    printf '%s\n' 'cmd_$@ := $(make-cmd)' > $(dot-target).cmd)

两个职责：回显（走 $(quiet)cmd_*）、执行（走 cmd_*）。末尾那句 printf 把完整命令行写进 .u-boot.cfg.cmd 这类文件——刚才说的 fixdep 体系就落在这里。想知道某个目标上次是怎么编的，直接看它的 .cmd 文件。

3.3 prepare 家族：编译前的「造文件」阶段 #

prepare 不是单个目标，而是一串伪目标，按依赖顺序排：

makefile
PHONY += prepare archprepare prepare0 prepare1 prepare2 prepare3

prepare3: include/config/uboot.release
prepare2: prepare3 outputmakefile
prepare1: prepare2 $(version_h) $(timestamp_h) include/config/auto.conf
archprepare: prepare1 scripts_basic
prepare0: archprepare FORCE
    $(Q)$(MAKE) $(build)=.
prepare: prepare0

依赖树画出来是这样：

text
prepare
└── prepare0  (执行 make -f scripts/Makefile.build obj=.)
    └── archprepare
        ├── prepare1
        │   ├── prepare2
        │   │   ├── prepare3 → include/config/uboot.release
        │   │   │              └── include/config/auto.conf
        │   │   │                  ├── .config
        │   │   │                  └── include/config/auto.conf.cmd
        │   │   └── outputmakefile
        │   ├── include/generated/version_autogenerated.h
        │   ├── include/generated/timestamp_autogenerated.h
        │   └── include/config/auto.conf
        └── scripts_basic → scripts/basic/fixdep

这一阶段到底产出什么，一句话总结成七件事：

  1. fixdep 工具（用于全系统依赖跟踪）；
  2. .config（配置阶段已生成）；
  3. include/config/auto.conf、auto.conf.cmd、tristate.conf、include/generated/autoconf.h；
  4. include/config.h（filechk_config_h 宏生成）；
  5. include/autoconf.mk 与 autoconf.mk.dep；
  6. include/config/uboot.release、version_autogenerated.h、timestamp_autogenerated.h；
  7. arch/arm/include/asm/arch 符号链接（create_symlink）。

prepare0 那句 make -f ./scripts/Makefile.build obj=. 本身不生成任何目标，它只是把当前目录走一遍 Makefile.build 的流程，确保依赖关系闭包完整。

3.4 u-boot 目标：链接出 ELF #

makefile
u-boot: $(u-boot-init) $(u-boot-main) u-boot.lds FORCE
    $(call if_changed,u-boot__)

三部分输入：

makefile
u-boot-init := $(head-y)
u-boot-main := $(libs-y)

$(libs-y) 是一长串目录，最后统一换成 built-in.o：

makefile
libs-y += lib/ board/$(BOARDDIR)/ fs/ net/ disk/ drivers/
libs-y += drivers/mtd/ drivers/net/ drivers/mmc/ drivers/gpio/ drivers/i2c/
libs-y := $(sort $(libs-y))
libs-y := $(patsubst %/, %/built-in.o, $(libs-y))

每个目录的 built-in.o 由该目录下所有 obj-y 归并而来，空列表时退化成 ar rcs 建一个空归档：

makefile
ifdef builtin-target
quiet_cmd_link_o_target = LD      $@
cmd_link_o_target = $(if $(strip $(obj-y)),\
    $(LD) $(ld_flags) -r -o $@ $(filter $(obj-y), $^),\
    rm -f $@; $(AR) rcs$(KBUILD_ARFLAGS) $@)
$(builtin-target): $(obj-y) FORCE
    $(call if_changed,link_o_target)
endif

反查某个 built-in.o 由哪些 .o 组成，看同目录的 .built-in.o.cmd 文件即可。

真正的链接命令：

bash
arm-linux-ld -pie --gc-sections -Bstatic -Ttext 0x0 -o u-boot -T u-boot.lds \
    arch/arm/cpu/arm920t/start.o \
    --start-group arch/arm/cpu/built-in.o ... --end-group \
    -Map u-boot.map

--start-group ... --end-group 是因为各 built-in.o 之间有循环依赖，必须让链接器反复扫表直到收敛。

3.5 u-boot.lds 从哪来 #

它是预处理出来的，不是源码原件：

makefile
quiet_cmd_cpp_lds = LDS     $@
cmd_cpp_lds = $(CPP) -Wp,-MD,$(depfile) $(cpp_flags) $(LDPPFLAGS) \
    -D__ASSEMBLY__ -x assembler-with-cpp -P -o $@ $<

u-boot.lds: $(LDSCRIPT) prepare FORCE
    $(call if_changed_dep,cpp_lds)

$(LDSCRIPT) 按四级顺序找：

makefile
ifndef LDSCRIPT
    ifdef CONFIG_SYS_LDSCRIPT      # 1. 板级显式指定（需去掉双引号）
        LDSCRIPT := $(srctree)/$(CONFIG_SYS_LDSCRIPT:"%"=%)
    endif
endif
ifndef LDSCRIPT
    ifeq ($(wildcard $(LDSCRIPT)),)
        LDSCRIPT := $(srctree)/board/$(BOARDDIR)/u-boot.lds   # 2. 板级目录
    endif
    ifeq ($(wildcard $(LDSCRIPT)),)
        LDSCRIPT := $(srctree)/$(CPUDIR)/u-boot.lds           # 3. CPU 目录
    endif
    ifeq ($(wildcard $(LDSCRIPT)),)
        LDSCRIPT := $(srctree)/arch/$(ARCH)/cpu/u-boot.lds     # 4. 兜底
    endif
endif

所以想定制定 lds，最稳的做法是在 board/<vendor>/<board>/ 下放一个 u-boot.lds，它会被第二级命中。

四、链接脚本里到底写了什么 #

S3C2440 用兜底的 arch/arm/cpu/u-boot.lds，骨架长这样：

OUTPUT_FORMAT("elf32-littlearm", "elf32-littlearm", "elf32-littlearm")
OUTPUT_ARCH(arm)
ENTRY(_start)
SECTIONS
{
    . = 0x00000000;
    . = ALIGN(4);
    .text :
    {
        *(.__image_copy_start)
        arch/arm/cpu/arm920t/start.o (.text*)
        *(.text*)
    }
    . = ALIGN(4);
    .rodata : { *(SORT_BY_ALIGNMENT(SORT_BY_NAME(.rodata*))) }
    . = ALIGN(4);
    .data : { *(.data*) }
    . = ALIGN(4);
    .u_boot_list : {
        KEEP(*(SORT(.u_boot_list_*)))             // 命令、驱动、CLK_OF_DECLARE 全在这段
    }
    . = ALIGN(4);
    __image_copy_end = .;                         // 需要被重定位搬走的内容到此为止
    .rel.dyn : { *(.__rel_dyn_start) *(.rel.dyn) }
    .bss : { *(.bss*) }
    . = ALIGN(4);
    __image_binary_end = .;                       // objcopy 出来的 bin 文件结束位置
}

三个链接符号是全流程的关节：

符号 作用
__image_copy_start 重定位时搬运的起点
__image_copy_end 重定位时搬运的终点；之后是 .rel.dyn 和 .bss，不需要搬
__image_binary_end 镜像实际结束位置，binary_size_check 用它校验

ENTRY(_start) 指定入口符号，而 _start 必然在 start.o 里——这就是 head-y := arch/arm/cpu/$(CPU)/start.o 那一行把 start.o 硬塞在链接输入最前面的原因。

4.1 .u_boot_list 段：段即注册表 #

KEEP(*(SORT(.u_boot_list_*))) 这一行是 u-boot 最漂亮的设计。它把散落在各文件里的注册项按链接顺序摆进同一段，运行时当数组遍历即可，不需要任何中心化的注册表文件。四类东西用它：

宏 段名后缀 用途
U_BOOT_CMD(name, maxargs, repeatable, cmd, usage, help) .u_boot_list_2_cmd_2_<name> 注册一条命令
U_BOOT_DRIVER(x) / U_BOOT_LEGACY_DRIVER .u_boot_list_2_driver_2_<x> 注册一个 DM 驱动
CLK_OF_DECLARE / TIMER_OF_DECLARE 各自专用段 设备树驱动的早期注册
UCLASS_DRIVER / U_BOOT_DEVICE 各自专用段 uclass 与静态设备

U_BOOT_CMD 展开后是一个 struct cmd_tbl_s 变量，用 __attribute__((section(...))) 钉进指定段。命令解析时 find_cmd 只要在 __u_boot_list_2_cmd_1 到 __u_boot_list_2_cmd_3 之间二分/线性查找即可。

这也解释了一个常见现象：用 if (0) 包住 U_BOOT_CMD 并不能去掉命令，因为段注册发生在编译期，运行期判断管不到。要去掉命令只能改 CONFIG_CMD_xxx。

五、产物清单 #

文件 生成方式 用途
u-boot ld -T u-boot.lds ... -Map u-boot.map ELF 格式，可 objdump、可 gdb
u-boot.bin objcopy -O binary（无 CONFIG_OF_SEPARATE 时等于 u-boot-nodtb.bin） 烧到板子上的就是这个
u-boot-nodtb.bin objcopy --gap-fill=0xff -j .text -j .rodata ... -O binary 不含设备树的纯二进制
u-boot.img mkimage，给 bin 加 0x40 字节头 头部含加载地址、运行地址、CRC；仅 CONFIG_SPL_FRAMEWORK 时生成
u-boot.srec objcopy -O srec Motorola S-record 格式，早期烧写器用
u-boot.map ld -Map 含每个函数名及其所在文件，定位函数归属第一选择
u-boot.sym objdump -t u-boot 符号表（含局部符号）
System.map nm u-boot | grep -v ... | sort 最终符号地址表，查重定位、查函数地址
u-boot.cfg cpp -dM -E include/config.h 本次编译生效的全部宏，判断某宏到底有没有定义
u-boot.elf objcopy 加调试信息 仅 CONFIG_REMAKE_ELF，用于 gdb 源码级调试
spl/u-boot-spl.bin SPL 单独链接 一级引导（DDR 初始化）
tpl/u-boot-tpl.bin TPL 单独链接 更早的一级（SRAM 太小放不下 SPL 时）
dts/dt.dtb make dtbs 设备树二进制

两个最实用的：

  • 不确定某个宏有没有定义 → 看 u-boot.cfg，比翻头文件快十倍。
  • 不确定某个函数在哪个文件 → 查 u-boot.map。

binary_size_check 这个目标值得一提，它用 map 里的链接符号反算镜像大小，再和实际字节数比对，对不上就 exit 1：

makefile
binary_size_check: u-boot-nodtb.bin FORCE
    @file_size=$(shell wc -c u-boot-nodtb.bin | awk '{print $$1}') ; \
    map_size=$(shell cat u-boot.map | \
        awk '/_image_copy_start/ {start = $$1} /_image_binary_end/ {end = $$1} \
             END {if (start != "" && end != "") print "ibase=16; " toupper(end) " - " toupper(start)}'); \
    ...

六、三个必须分清的头文件 #

文件 谁生成 给谁用
.config scripts/kconfig/conf 人看、make menuconfig 编辑
include/config/auto.conf scripts/Makefile.autoconf 给 Makefile 用，子目录靠它裁剪 obj-y
include/generated/autoconf.h 同上 给 C 代码用，CONFIG_xxx 宏
include/config.h filechk_config_h 宏 板级配置的「胶水」，把五层头文件串起来

两者内容一致、载体不同，记住这句就不会混：auto.conf 是变量，给 Makefile；autoconf.h 是宏，给 C。

include/config.h 是自动生成的，内容是固定的五条 include：

c
/* Automatically generated - do not edit */
#define CONFIG_BOARDDIR board/samsung/smdk2410
#include <config_defaults.h>
#include <config_uncmd_spl.h>
#include <configs/smdk2410.h>
#include <asm/config.h>
#include <config_fallbacks.h>

这段的头注释写得很直白：# Prior to Kconfig, it was generated by mkconfig. Now it is created here. —— 这是全仓库唯一一处提到 mkconfig 的地方，而且是在宣布它已经退休。

auto.conf 被顶层 Makefile 直接 include：

makefile
ifeq ($(dot-config),1)
-include include/config/auto.conf

于是每个子目录的 Makefile 都能按宏裁剪，比如 common/Makefile：

makefile
ifndef CONFIG_SPL_BUILD
obj-y += init/
obj-y += main.o
obj-y += exports.o
ifdef CONFIG_SYS_HUSH_PARPARSER
obj-y += cli_hush.o
endif
endif

新建驱动时照这个写法：写 obj-$(CONFIG_XXX) += xxx.o，宏不开就不编，天然支持裁剪。

七、真编一次：S3C2440 #

环境：Mini2440 / S3C2440，u-boot 2016.05，NAND K9F2G08U0C，网卡 DM9000A，SDRAM HY57V561620FTP。

bash
tar -jxvf u-boot-2016.05.tar.bz2      # 需要先 apt install bzip2
cd u-boot-2016.05

# 方案一：命令行指定
make ARCH=arm CROSS_COMPILE=arm-linux- smdk2410_defconfig
make ARCH=arm CROSS_COMPILE=arm-linux- -j4

# 方案二：写进顶层 Makefile，之后直接 make
# CROSS_COMPILE = arm-linux-
# ARCH = arm

ARCH 决定 arch/$(ARCH)/ 这串路径的展开；CROSS_COMPILE 是前缀，派生全套工具：

makefile
AS      = $(CROSS_COMPILE)as
LD      = $(CROSS_COMPILE)ld.bfd   # 有 bfd 就用 bfd
CC      = $(CROSS_COMPILE)gcc
OBJCOPY = $(CROSS_COMPILE)objcopy
OBJDUMP = $(CROSS_COMPILE)objdump

想用 arm-linux-gcc，就必须让 CROSS_COMPILE = arm-linux-（结尾的横杠不能丢）。

完整编译日志（V=1）有近 400 行，头尾长这样：

text
  CHK     include/config.h
  UPD     include/config.h
  GEN     include/autoconf.mk
  CHK     include/config/uboot.release
  CC      lib/asm-offsets.s
  ...
  CC      board/samsung/smdk2410/smdk2410.o
  AS      board/samsung/smdk2410/lowlevel_init.o
  LD      board/samsung/smdk2410/built-in.o
  AS      arch/arm/cpu/arm920t/start.o
  ...
  LDS     u-boot.lds
  LD      u-boot
  OBJCOPY u-boot.srec
  OBJCOPY u-boot-nodtb.bin
  COPY    u-boot.bin
  SYM     u-boot.sym
  CFG     u-boot.cfg

日志本身就是一张移植检查表：所有带 s3c24x0、smdk2410 字样的行，就是与你的 CPU 和板子强相关的文件。移植新板时先按这几行定位，再看哪些要改，比全文搜索快得多。

反汇编：

bash
arm-linux-objdump -D u-boot > u-boot.dis

配合 start.S 读启动流程时，u-boot.dis 能把 C 代码和汇编对上号。

八、镜像尺寸：4KB 的硬约束 #

S3C2440 上电后，NAND 控制器自动把 NAND 前 4KB 搬到片内 Steppingstone（4KB SRAM） 并从 0x0 开始执行。这只是个引导块，完整 u-boot 有几百 KB，根本放不下。

所以 start.S 最前面那段汇编干的第一件重活是：自己把剩余部分从 NAND 搬到 SDRAM，再跳过去继续跑（重定位）。配套的两个宏：

c
#define CONFIG_SYS_TEXT_BASE    0x0            // 链接地址，从 0 开始
#define CONFIG_SYS_MONITOR_LEN  (448 * 1024)   // u-boot 自身长度上限，留出余量

网上不少老文章说「u-boot 必须小于 256KB 才能被 Steppingstone 载入」，这个说法对 S3C2440 是错的——2440 的 Steppingstone 只有 4KB。256KB 那个数字更可能来自 S3C2410 NAND 前 256KB 保留区的混淆。真正卡住的是「前 4KB 里必须放完整搬运代码」，与整个 u-boot 的大小无关（上限于 CONFIG_SYS_MONITOR_LEN）。

裁剪体积时的常规手段：

c
// include/configs/<board>.h 里关掉不用的压缩库和命令
#undef CONFIG_BZIP2
#undef CONFIG_LZO
#undef CONFIG_LZMA

关掉这三个压缩库通常能省下几十 KB。

九、踩坑速查 #

现象 原因与处理
arm-linux-gcc: command not found CROSS_COMPILE 结尾少了横杠，或工具链不在 PATH
改了驱动但没生效 obj-y 没加、或 CONFIG_xxx 没开；看 u-boot.cfg 确认宏
Could not find linker script. prepare1 的 $(wildcard $(LDSCRIPT)) 为空，四级搜索全落空
加了 U_BOOT_CMD 但命令不出现 宏没编进 built-in.o，或 if (0) 包住无效（段注册发生在编译期）
u-boot.map shows a binary size of X but ... shows Y binary_size_check 失败；改过 lds 段序或加了 ALIGN 导致符号与实际不符
Unknown command 'xxx' 但源码里有 检查 .u_boot_list 是否被 --gc-sections 裁掉，需要 KEEP
配置改了但编译行为没变 include/config/auto.conf 没更新，touch .config 或 make oldconfig
想看某目标上次的完整命令 打开同目录的 .<target>.cmd 文件

小结 #

  • u-boot 的配置在 2014 年换了代：老版 mkconfig + boards.cfg + include/config.mk，新版 Kconfig + configs/*_defconfig + auto.conf/autoconf.h。看教程先看版本。
  • 编译链路是 _all → all → $(ALL-y) → u-boot，u-boot = head-y(start.o) + libs-y(各 built-in.o) + u-boot.lds。
  • prepare 家族负责编译前所有「造文件」动作，fixdep 维护的 .cmd 文件是增量编译的判断依据。
  • 链接脚本里 .u_boot_list 段用 KEEP 收集散落的注册项，是「段即注册表」；__image_copy_start/end 界定重定位范围。
  • 宏到底开没开看 u-boot.cfg，函数在哪个文件看 u-boot.map，某目标怎么编的看 .cmd。
