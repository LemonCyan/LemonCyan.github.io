零、全景 #

text
上电
 │
 ├─ _start        arch/arm/lib/vectors.S        向量表，第一条指令 b reset
 │   └─ reset     arch/arm/cpu/<cpu>/start.S    设 SVC、关看门狗、关中断、关 MMU/Cache
 │        ├─ cpu_init_crit                       flush cache/TLB，关 MMU
 │        └─ lowlevel_init                       初始化 SDRAM 控制器（板级）
 │
 ├─ _main         arch/arm/lib/crt0.S           设栈 → 分配 GD → board_init_f
 │   ├─ board_init_f(0)   common/board_f.c       init_sequence_f[]：时钟/串口/DRAM/内存规划
 │   ├─ relocate_code     arch/arm/lib/relocate.S 把自身搬到 DDR 顶端，修 .rel.dyn
 │   ├─ relocate_vectors                         向量表搬到新地址
 │   └─ 清 BSS → board_init_r
 │
 ├─ board_init_r   common/board_r.c             init_sequence_r[]：Flash/NAND/网卡/环境变量
 │
 └─ main_loop      common/main.c                倒计时 → bootcmd 或 cli_loop
      └─ bootm → do_bootm_states → boot_jump_linux → kernel_entry(0, machid, r2)

一句话记住三段的分工：_start/reset 是「让 CPU 能跑 C」，_main 是「让 u-boot 跑在自己的最终地址上」，board_init_r 之后是「让外设能用」。

一、框架：board → machine → arch → cpu #

u-boot 解决跨平台的方式，和 device tree 普及之前的 Linux 内核完全一致——按硬件拓扑分层：

text
board      整块板子（屏幕、按键、网卡、Flash…）
 └── machine   SoC（arch/arm/mach-xxx 或 arch/arm/cpu/armv8/<soc>）
      ├── arch   体系结构大类（arch/arm，**arm32 和 arm64 都归这里**）
      └── cpu    CPU 核（armv7、armv8、arm920t…）

注意 u-boot 的抽象和 ARM 官方定义不一致：ARM 把 ARMv8 叫架构，u-boot 把 arm 当 ARCH、把 armv8 当 CPU。有点怪，记住就行。

基于这个框架，初始化是自内向外四步：

  1. 先跑 CPU 的初始化代码（如 arch/arm/cpu/armv8/start.S）；
  2. CPU 代码调用 ARCH 公共代码（arch/arm/lib/）；
  3. ARCH 公共代码在合适时机调用 board 的接口；u-boot 的功能逻辑大多在 common/，平台相关的部分由公共代码声明、board 实现；
  4. board 代码按需调用 machine 提供的接口。machine 只提供基础支持，不参与功能逻辑。

移植就是找自己该从哪一层开始写：ARCH 已被上游支持就从 CPU 层开始，CPU 也被支持就从 machine 层开始，以此类推。Mini2440 是从 board 层（board/samsung/smdk2440）开始，Bubblegum-96 是从 machine 层（S900）开始。

二、入口在哪：链接脚本与向量表 #

u-boot.lds 用 ENTRY(_start) 指定入口（上一篇讲过它的四级搜索和段排列），而 _start 在 arch/arm/lib/vectors.S 里：

armasm
.globl _start
    .section ".vectors", "ax"
_start:
#ifdef CONFIG_SYS_DV_NOR_BOOT_CFG
    .word   CONFIG_SYS_DV_NOR_BOOT_CFG
#endif
    b   reset                        /* ← 上电后执行的第一条指令 */
    ldr pc, _undefined_instruction
    ldr pc, _software_interrupt
    ldr pc, _prefetch_abort
    ldr pc, _data_abort
    ldr pc, _not_used
    ldr pc, _irq
    ldr pc, _fiq

八个字（0x00~0x1C）就是 ARM 的异常向量表。以 0x04 为例，ldr pc, _undefined_instruction 的机器码是「把 [pc, #20] 处的值装进 PC」，即跳到 0x20 处取出真正的处理函数地址再跳。中间那一级 .word 表让处理函数可以被重定位，也让用户能整体替换。

⚠️ 原文此处配有一幅 u-boot 多平台架构示意图，在网页抓取过程中丢失。按正文描述：最大方块是 board，内含 machine（SoC），SoC 内部再分 ARCH 与 CPU 两层——即本节开头那个四层嵌套结构。

2.1 用零长度数组造「位置标签」 #

arch/arm/lib/sections.c 里只有几个零长度数组：

c
char __bss_start[0]        __attribute__((section(".__bss_start")));
char __bss_end[0]          __attribute__((section(".__bss_end")));
char __image_copy_start[0] __attribute__((section(".__image_copy_start")));
char __image_copy_end[0]   __attribute__((section(".__image_copy_end")));
char __rel_dyn_start[0]    __attribute__((section(".__rel_dyn_start")));
char __rel_dyn_end[0]      __attribute__((section(".__rel_dyn_end")));

它们不占空间，只是把「某个段的边界」变成一个可以从 C 里取地址的符号。汇编里用 ldr r0, =__bss_start 拿到的就是这个地址。三个最关键的：

符号 含义
__image_copy_start / __image_copy_end 重定位时要搬运的范围
__rel_dyn_start / __rel_dyn_end .rel.dyn 重定位表范围
__bss_start / __bss_end BSS 清零范围

三、汇编阶段：reset 与 lowlevel_init #

3.1 ARM64：arch/arm/cpu/armv8/start.S #

armasm
.globl  _start
_start:
    b   reset

reset 里做的事按顺序：

armasm
reset:
#ifdef CONFIG_SYS_RESET_SCTRL
    bl reset_sctrl
#endif
    /*
     * Could be EL3/EL2/EL1, Initial State:
     * Little Endian, MMU Disabled, i/dCache Disabled
     */
    adr x0, vectors
    switch_el x1, 3f, 2f, 1f
3:  msr vbar_el3, x0              /* 当前在 EL3，设异常向量基址 */
    mrs x0, scr_el3
    orr x0, x0, #0xf              /* SCR_EL3.NS|IRQ|FIQ|EA */
    msr scr_el3, x0
    msr cptr_el3, xzr             /* Enable FP/SIMD */
#ifdef COUNTER_FREQUENCY
    ldr x0, =COUNTER_FREQUENCY
    msr cntfrq_el0, x0            /* 初始化架构定时器频率 */
#endif
    b   0f
2:  msr vbar_el2, x0
    mov x0, #0x33ff
    msr cptr_el2, x0
    b   0f
1:  msr vbar_el1, x0
    mov x0, #3 << 20
    msr cpacr_el1, x0
0:
    bl  apply_core_errata          /* 按 CONFIG_ARM_ERRATA_xxx 打补丁 */
    bl  lowlevel_init              /* 处理器相关初始化，通常为空 */
    bl  _main                      /* 进入 C 世界 */

switch_el 是个宏，按当前异常级别跳到 3f/2f/1f 三个标号之一。初始状态写得很明白：小端、MMU 关闭、I/D-Cache 关闭。

lowlevel_init 这个函数很多人栽跟头，u-boot 自带的 README 说得很清楚：

purpose: essential init to permit execution to reach board_init_f() ——没有 global_data、没有 BSS、没有栈、不能初始化 SDRAM、不能用控制台，只能做「让程序能继续跑到 board_init_f」的绝对最小动作，且几乎从来不需要实现。

3.2 ARM32：arch/arm/cpu/arm920t/start.S #

ARM32 这边的东西实在得多，Mini2440 真正干的活都在这。第一件事是把 CPU 切到 SVC 模式：

armasm
reset:
    mrs r0, cpsr
    bic r0, r0, #0x1f        /* 清 M[4:0] */
    orr r0, r0, #0xd3        /* SVC 模式(0x13) + 关 FIQ/IRQ(0xc0) */
    msr cpsr, r0

0xd3 这个魔数展开就是 0b11010011：低 5 位 10011 = SVC 模式，bit6/bit7 = 1 表示禁止 FIQ/IRQ。

接着按 SoC 分支做三件事（以 S3C24X0 为例）：

armasm
# if defined(CONFIG_S3C2400)
#  define pWTCON    0x15300000
#  define INTMSK    0x14400008
#  define CLKDIVN   0x14800014
#else
#  define pWTCON    0x53000000   /* 看门狗控制寄存器 */
#  define INTMSK    0x4A000008   /* 中断屏蔽寄存器 */
#  define INTSUBMSK 0x4A00001C
#  define CLKDIVN   0x4C000014   /* 时钟分频寄存器 */
# endif
    ldr r0, =pWTCON
    mov r1, #0x0
    str r1, [r0]             /* 关看门狗 */

    mov r1, #0xffffffff
    ldr r0, =INTMSK
    str r1, [r0]             /* 屏蔽全部主中断 */
# if defined(CONFIG_S3C2410)
    ldr r1, =0x3ff
    ldr r0, =INTSUBMSK
    str r1, [r0]             /* 屏蔽子中断 */
# endif

    ldr r0, =CLKDIVN
    mov r1, #3
    str r1, [r0]             /* 只设分频，还没设 PLL 频率 */

然后进 cpu_init_crit——名字里的 crit 是 critical 的意思，它做两件事：

armasm
cpu_init_crit:
    mov r0, #0
    mcr p15, 0, r0, c7, c7, 0   /* flush v3/v4 cache */
    mcr p15, 0, r0, c8, c7, 0   /* flush v4 TLB */

    mrc p15, 0, r0, c1, c0, 0
    bic r0, r0, #0x00002300     /* 清 bit13, bit9:8 (V, RS) */
    bic r0, r0, #0x00000087     /* 清 bit7, bit2:0 (B, CAM)**关 MMU 就在这 */
    orr r0, r0, #0x00000002     /* 置 bit1 (A) 地址对齐检查 */
    orr r0, r0, #0x00001000     /* 置 bit12 (I) 打开 I-Cache */
    mcr p15, 0, r0, c1, c0, 0

#ifndef CONFIG_SKIP_LOWLEVEL_INIT_ONLY
    mov ip, lr
    bl  lowlevel_init           /* 板级 SDRAM 控制器初始化 */
    mov lr, ip
#endif
    mov pc, lr

CP15 c1 的 bit0（M 位）就是 MMU 开关，bic #0x87 一次清掉 B、C、M 三位——MMU 与 D-Cache 在这里关闭，I-Cache 在下一行又重新打开。这正是 ARM 引导协议要求的「I-Cache 可开可关、D-Cache 必须关」。

lowlevel_init 在 board/samsung/smdk2410/lowlevel_init.S 里，用一张 SMRDATA 表把 S3C2440 的 13 个存储控制器寄存器一次性写下去：BWSCON → BANKCON0~7 → REFRESH → BANKSIZE → MRSRB6/7。Mini2440 上要改的就三项：REFCNT（刷新计数，按 HCLK 算）、BANKSIZE 和 SMRDATA 末尾三个字。

四、_main：三步环境 #

_main（arch/arm/lib/crt0.S 或 crt0_64.S）是唯一同时看得见 board_init_f、relocate_code、board_init_r 三个函数的地方，所以它是理解整条启动链的枢纽。

4.1 第一步：搭初始 C 环境 #

armasm
#if defined(CONFIG_SPL_BUILD) && defined(CONFIG_SPL_STACK)
    ldr sp, =(CONFIG_SPL_STACK)            /* SPL 用片内 SRAM 当栈 */
#else
    ldr sp, =(CONFIG_SYS_INIT_SP_ADDR)     /* Mini2440: 0x30000f50 */
#endif
    bic sp, sp, #7                         /* 8 字节对齐（ABI 要求）*/
    mov r0, sp
    bl  board_init_f_alloc_reserve         /* 在栈下面抠出 GD 的空间 */
    mov sp, r0
    mov r9, r0                             /* gd 指针固定放 r9 */
    bl  board_init_f_init_reserve          /* 把 gd 清零 */

CONFIG_SYS_INIT_SP_ADDR 在板级头文件里：

c
#define PHYS_SDRAM_1           0x30000000
#define CONFIG_SYS_SDRAM_BASE  PHYS_SDRAM_1
#define CONFIG_SYS_INIT_SP_ADDR  (CONFIG_SYS_SDRAM_BASE + 0x1000 - \
                                  GENERATED_GBL_DATA_SIZE)

也就是说初始栈放在 SDRAM 起始 + 4KB 的地方，故意贴着低端——因为后面内核要占低端，u-boot 早晚要搬到顶端去。

4.2 第二步：board_init_f 规划内存 #

armasm
    mov r0, #0
    bl  board_init_f          /* 参数是 boot_flags，固定传 0 */

这个函数的注释把「为什么要有 global data」讲透了：调用它的时候 RAM 可能还不能用（DDR 没初始化完），所以它必须把所有要传给后续阶段的数据存进 GD——重定位目标地址、未来的栈地址、未来的 GD 位置。

4.3 第三步：重定位，然后换到最终环境 #

armasm
    ldr sp, [r9, #GD_START_ADDR_SP]   /* sp = gd->start_addr_sp，新栈 */
    bic sp, sp, #7
    ldr r9, [r9, #GD_BD]              /* r9 = gd->bd */
    sub r9, r9, #GD_SIZE              /* 新 GD 在 bd 下方 */

    adr lr, here
    ldr r0, [r9, #GD_RELOC_OFF]       /* r0 = gd->reloc_off */
    add lr, lr, r0                    /* 返回地址也要加上偏移 */
    ldr r0, [r9, #GD_RELOCADDR]       /* r0 = gd->relocaddr，目的地 */
    b   relocate_code
here:
    bl  relocate_vectors              /* ARM32 才有这一步 */
    bl  c_runtime_cpu_setup

    /* 清 BSS */
    ldr r0, =__bss_start
    ldr r1, =__bss_end
    mov r2, #0
clbss_l:
    cmp r0, r1
    strlo r2, [r0]
    addlo r0, r0, #4
    blo clbss_l

    mov r0, r9                        /* gd_t *id */
    ldr r1, [r9, #GD_RELOCADDR]       /* ulong dest_addr */
    ldr pc, =board_init_r             /* 不返回 */

这里有个精巧的地方：adr lr, here 之后再 add lr, lr, reloc_off。因为 relocate_code 会把代码搬到新地址，返回时必须返回到新地址里的 here，而不是旧地址。

ARM32 与 ARM64 的差别只有一处：ARM32 在 relocate_code 返回后额外调一次 relocate_vectors（把向量表搬到新地址），ARM64 由 arch 代码在 c_runtime_cpu_setup 里处理。

4.4 GD 相关常量 #

编译时由 scripts/Makefile.build 生成到 include/generated/asm-offsets.h，汇编里直接用：

c
#define GD_SIZE          168   /* sizeof(struct global_data) */
#define GD_BD            0     /* offsetof(struct global_data, bd) */
#define GD_RELOCADDR     44    /* offsetof(struct global_data, relocaddr) */
#define GD_RELOC_OFF     64    /* offsetof(struct global_data, reloc_off) */
#define GD_START_ADDR_SP 60    /* offsetof(struct global_data, start_addr_sp) */

五、global_data：为什么非得有这么个结构体 #

u-boot 最初可能运行在只读的 NOR Flash 里，在把自己拷到 RAM 之前有两个死结：

  1. 没有可写的栈 → 不能做函数调用 → C 环境不可用。
  2. 没有正确初始化的 data 段 → 全局变量读写不可靠。

解法很直接：在「不需要任何初始化就能用的可读写区域」（多数 ARM 平台用自己的片内 SRAM）开辟栈；用一个结构体 + 一个固定寄存器代替全局变量传数据。这就是 struct global_data，指针塞进 r9（ARM32）或 x18（ARM64）：

c
#define DECLARE_GLOBAL_DATA_PTR   register volatile gd_t *gd asm ("r9")
// ARM64:
#define DECLARE_GLOBAL_DATA_PTR   register volatile gd_t *gd asm ("x18")

register ... asm("r9") 除了告诉编译器「gd 在这儿」，还阻止编译器把 r9 分配给其他变量。任何要用 gd 的 C 文件，开头加一行 DECLARE_GLOBAL_DATA_PTR 就行。

5.1 三个必须认识的字段 #

字段 结构体注释 谁赋值
gd->ram_size RAM size dram_init()：gd->ram_size = PHYS_SDRAM_1_SIZE;
gd->mon_len monitor len，u-boot 自身长度 setup_mon_len()：gd->mon_len = (ulong)&__bss_end - (ulong)_start;
gd->relocaddr Start address of U-Boot in RAM setup_dest_addr() 起逐级向下压

relocaddr 的压制过程就是内存规划的全过程，全部发生在 init_sequence_f 里：

c
setup_dest_addr();    // gd->relocaddr = gd->ram_top = 0x34000000（64MB 顶端）
reserve_round_4k();   // 4KB 对齐
reserve_mmu();        // 减 16KB（PGTABLE_SIZE），再 64KB 对齐
reserve_trace();      // 减 trace buffer
reserve_uboot();      // 减 mon_len，4KB 对齐；start_addr_sp = relocaddr
reserve_malloc();     // start_addr_sp 减 4MB
reserve_board();      // start_addr_sp 减 sizeof(bd_t)
reserve_global_data();// start_addr_sp 减 sizeof(gd_t)
reserve_fdt();        // start_addr_sp 减 dtb 大小 + 4KB
reserve_stacks();     // 再减 16 字节并对齐

所以 64MB 的 DRAM 被这样切开（从高到低）：

text
0x34000000 ┬─────────────────────────
           │  保留区（TLB、trace…）
           ├─────────────────────────  gd->relocaddr
           │  u-boot 代码 + 数据 + BSS  （gd->mon_len）
           ├─────────────────────────
           │  malloc 区（4MB）
           ├─────────────────────────
           │  bd_t
           ├─────────────────────────
           │  gd_t（new_gd）
           ├─────────────────────────
           │  dtb（new_fdt）
           ├─────────────────────────  gd->start_addr_sp
           │  ↓ 栈向下生长
           │
0x30000000 ┴─────────────────────────  内核将来在低端解压运行

5.2 bd_t：专门给内核看的那块信息 #

gd->bd 指向另一块结构，由 reserve_board() 在栈下面抠出来。它装的是板级信息，最终要交给内核：

c
int board_init(void)
{
    gd->bd->bi_arch_number = MACH_TYPE_SMDK2410;   /* 机器码 193 */
    gd->bd->bi_boot_params = 0x30000100;           /* ATAGS 起始地址 */
    icache_enable();
    dcache_enable();
    return 0;
}
结构 给谁用 内容
gd_t u-boot 自己 运行期全局状态：时钟、串口、重定位地址、FDT…
bd_t 内核（经 ATAGS / bi_arch_number） 机器码、内存 bank、Flash 大小、MAC

六、board_init_f 与 init_sequence_f #

c
void board_init_f(ulong boot_flags)
{
    gd->flags = boot_flags;
    gd->have_console = 0;

    if (initcall_run_list(init_sequence_f))
        hang();
}

initcall_run_list 就是一个 for 循环遍历函数指针数组，遇到非 0 返回值就打印 initcall sequence %p failed at call %p 并返回 -1。数组以 NULL 结尾。

init_sequence_f[] 完整条目很长（30 多个函数，被十几个 #ifdef 切来切去），SMDK2410 上实际生效的只有这些：

c
static const init_fnc_t init_sequence_f[] = {
    setup_mon_len,          /* gd->mon_len = __bss_end - _start */
    initf_malloc,           /* 早期 malloc */
    initf_console_record,
    arch_cpu_init,          /* 架构级初始化，弱函数 */
    initf_dm,               /* 驱动模型扫描设备树 */
    arch_cpu_init_dm,
    mark_bootstage,
    board_early_init_f,     /* ← 板级：PLL 与 GPIO */
    timer_init,             /* ← 定时器，为后续延时做准备 */
    env_init,               /* 环境变量（此时可能在 Flash 里）*/
    init_baud_rate,         /* 115200 */
    serial_init,            /* ← 串口 0，第一句打印从这开始 */
    console_init_f,
    display_options,        /* 打印 U-Boot 版本 */
    display_text_info,      /* DEBUG 时打印代码段地址 */
    print_cpuinfo,          /* 打印 CPUID 与 FCLK/HCLK/PCLK */
    announce_dram_init,     /* puts("DRAM:  ") */
    dram_init,              /* gd->ram_size = 64MB */
    setup_dest_addr,        /* 从这开始规划内存 */
    reserve_round_4k,
    reserve_mmu,
    reserve_trace,
    reserve_uboot,
    reserve_malloc,
    reserve_board,
    setup_machine,
    reserve_global_data,
    reserve_fdt,
    reserve_arch,
    reserve_stacks,
    setup_dram_config,      /* 填 gd->bd->bi_dram[] */
    show_dram_config,       /* 打印 Bank #0: 30000000 64 MiB */
    display_new_sp,
    reloc_fdt,              /* 把 dtb 拷到新位置 */
    setup_reloc,            /* 算 reloc_off，拷 gd 到 new_gd */
    NULL,
};

注意最后几行：setup_reloc() 里干了两件事——

c
gd->reloc_off = gd->relocaddr - CONFIG_SYS_TEXT_BASE;
memcpy(gd->new_gd, (char *)gd, sizeof(gd_t));

算好偏移、把 GD 复制到新位置，board_init_f 的任务就结束了，控制权回到 _main 去做真正的物理搬移。

一个容易踩的细节：init_sequence_f[] 末尾的 jump_to_copy 被 #if !defined(CONFIG_ARM) && !defined(CONFIG_SANDBOX) 包着——ARM 上根本不编译它。ARM 的重定位全靠 _main 里的 relocate_code，看到这个宏就能确认。

七、relocate_code：搬自己，还要修地址 #

7.1 为什么非搬不可 #

u-boot 的链接地址可以是 0（CONFIG_SYS_TEXT_BASE 0x0，从 NOR 直接 XIP 执行），也可以是 SDRAM 里的某个地址。重定位之后，运行地址 ≠ 链接地址。

函数调用用的是 b/bl 相对跳转，搬完照样对。但全局变量用的是绝对地址：反汇编里能看到 ldr r3, [pc, #80] 去读一个 .word 0x3000564c，搬完之后这个 0x3000564c 还是旧地址，就指错了。

7.2 .rel.dyn 是干什么的 #

编译时加 -pie，链接器把所有「需要修的绝对地址」记进 .rel.dyn 段：

text
30006660:  30001854    ← .rel.dyn 里记着：0x30001854 这个位置存了一个绝对地址
30001854:  3000564c    ← 而 0x30001854 处确实存着全局变量的地址 0x3000564c

于是重定位时按三步修：① 取 label 地址 0x30001854，加 reloc_off 得到新位置；② 取出那里的值 0x3000564c，也加 reloc_off；③ 写回。

7.3 relocate_code 全文 #

armasm
ENTRY(relocate_code)
    ldr r1, =__image_copy_start    /* r1 ← 源起始 */
    subs    r4, r0, r1             /* r4 ← 偏移 = 目的地 - 源 */
    beq relocate_done              /* 偏移为 0，不用搬 */
    ldr r2, =__image_copy_end      /* r2 ← 源结束 */

copy_loop:
    ldmia   r1!, {r10-r11}         /* 一次搬 2 个字 */
    stmia   r0!, {r10-r11}
    cmp r1, r2
    blo copy_loop

    /* 修 .rel.dyn */
    ldr r2, =__rel_dyn_start
    ldr r3, =__rel_dyn_end
fixloop:
    ldmia   r2!, {r0-r1}           /* (r0, r1) ← (位置, 修正类型) */
    and r1, r1, #0xff
    cmp r1, #23                    /* 23 = R_ARM_RELATIVE，才是相对修正 */
    bne fixnext
    add r0, r0, r4                 /* 位置加偏移 */
    ldr r1, [r0]
    add r1, r1, r4                 /* 值也加偏移 */
    str r1, [r0]
fixnext:
    cmp r2, r3
    blo fixloop

relocate_done:
    bx  lr                         /* 返回新地址里的 here */
ENDPROC(relocate_code)

搬运范围是 .text + .rodata + .data（由 __image_copy_start/end 界定），不包括 .rel.dyn 和 .bss——前者是修表本身，后者马上要被清零。

八、board_init_r 与 init_sequence_r #

进了 board_init_r，u-boot 已经在 SDRAM 顶端跑，可以放心初始化各种外设了。

c

{
    if (initcall_run_list(init_sequence_r))
        hang();
    /* NOTREACHED - run_main_loop() does not return */
    hang();
}

initr_env 那个 bad CRC 警告是新手最常见的困惑来源。链路是：env_relocate() 发现 gd->env_valid == 0（Flash 里那块区域还没写过环境变量），于是 set_default_env("!bad CRC")，以 ! 开头的字符串会走警告分支。它不是错误，是「还没存过环境变量」的正常提示，saveenv 一次就消失。

九、main_loop：倒计时与命令行 #

c
void main_loop(void)
{
    const char *s;

    bootstage_mark_name(BOOTSTAGE_ID_MAIN_LOOP, "main_loop");
    cli_init();                            /* hush 解析器初始化 */
    run_preboot_environment_command();     /* preboot 环境变量 */
    s = bootdelay_process();               /* 读 bootdelay 与 bootcmd */
    if (cli_process_fdt(&s))
        cli_secure_boot_cmd(s);
    autoboot_command(s);                   /* ← 倒计时，超时执行 bootcmd */
    cli_loop();                            /* ← 按键打断，进命令行 */
    panic("No CLI available");
}

9.1 这两个函数不是并列关系 #

很多人以为「倒计时」和「命令行」是两个分支、程序会判断走哪条。看 autoboot_command 就明白：

c
void autoboot_command(const char *s)
{
    debug("### main_loop: bootcmd=\"%s\"\n", s ? s : "<UNDEFINED>");

    if (stored_bootdelay != -1 && s && !abortboot(stored_bootdelay)) {
        run_command_list(s, -1, 0);        /* 执行 bootcmd，成功就再也不回来 */
    }
}
  • 倒计时正常结束 → abortboot() 返回 0 → 执行 bootcmd（通常是 bootm）→ boot 成功后永不返回；
  • 倒计时被按键打断 → abortboot() 返回非 0 → if 不成立 → 函数直接返回 → 顺序走到下一行 cli_loop() 进命令行。

所以「进了命令行」不是 u-boot 主动选择的，而是「bootcmd 没执行」的副产品。串口上那两行 ### main_loop entered: bootdelay=5 / ### main_loop: bootcmd="<UNDEFINED>" 就是 debug() 打的，bootcmd 没定义时显示 <UNDEFINED>，于是倒计时一结束什么也不做，直接掉进命令行。

9.2 cli_loop 的两条实现 #

c
void cli_loop(void)
{
#ifdef CONFIG_SYS_HUSH_PARSER
    parse_file_outer();        /* 完整 shell：支持 ; && || 变量 等 */
    for (;;);
#elif defined(CONFIG_CMDLINE)
    cli_simple_loop();         /* 极简：一行一条命令 */
#else
    printf("## U-Boot command line is disabled. Please enable CONFIG_CMDLINE\n");
#endif
}

smdk2410 默认走 hush。完整调用链：

text
parse_file_outer
 └─ parse_stream_outer(FLAG_PARSE_SEMICOLON)
     └─ parse_stream            逐字符扫描，遇 ; && || $ 引号分别处理
         └─ done_word / done_pipe
             └─ run_list
                 └─ run_list_real   遍历命令链表
                     └─ run_pipe_real
                         └─ cmd_process
                             ├─ find_cmd(argv[0])   查表
                             └─ cmd_call(...)       真正执行

hush 用三个结构体描述一条命令：

结构 作用
struct p_context 解析上下文，list_head 指向命令链表头
struct pipe 一个命令节点，next 指向下一条，followup 记 PIPE_SEQ/PIPE_AND/PIPE_OR/PIPE_BG
struct child_prog 一个程序：argv 存词，argc 记个数，group 指向子 shell

cmd1 option1; cmd2 option2 会被解析成：链表头 progs->argv = {cmd1, option1}，next->progs->argv = {cmd2, option2}。

十、命令是怎么注册进去的 #

cmd_process 只有三步，核心是第一句：

c
enum command_ret_t cmd_process(int flag, int argc, char * const argv[],
                               int *repeatable, ulong *ticks)
{
    cmd_tbl_t *cmdtp;

    cmdtp = find_cmd(argv[0]);            /* ① 查表 */
    if (cmdtp == NULL) {
        printf("Unknown command '%s' - try 'help'\n", argv[0]);
        return 1;
    }
    if (argc > cmdtp->maxargs)            /* ② 校验 */
        rc = CMD_RET_USAGE;
    else if (cmdtp->cmd == do_bootd) { ... }

    if (!rc) {
        if (ticks) *ticks = get_timer(0);
        rc = cmd_call(cmdtp, flag, argc, argv);   /* ③ 执行 */
        *repeatable &= cmdtp->repeatable;
    }
    if (rc == CMD_RET_USAGE)
        rc = cmd_usage(cmdtp);
    return rc;
}

cmd_call 内部就是 (cmdtp->cmd)(cmdtp, flag, argc, argv)。那么 find_cmd 查的是什么表？

10.1 段即注册表 #

c
cmd_tbl_t *find_cmd(const char *cmd)
{
    cmd_tbl_t *start = ll_entry_start(cmd_tbl_t, cmd);
    const int len = ll_entry_count(cmd_tbl_t, cmd);
    return find_cmd_tbl(cmd, start, len);
}

没有全局数组，没有初始化函数。ll_entry_start 和 ll_entry_count 是两个宏，靠链接脚本里两个零长度标记圈出一段区间：

c
#define ll_entry_start(_type, _list)                    \
({                                                      \
    static char start[0] __aligned(4) __attribute__((unused,  \
        section(".u_boot_list_2_"#_list"_1")));        \
    (_type *)&start;                                    \
})

#define ll_entry_declare(_type, _name, _list)                    \
    _type _u_boot_list_2_##_list##_2_##_name __aligned(4)        \
            __attribute__((unused,                               \
            section(".u_boot_list_2_"#_list"_2_"#_name)))

于是内存里排成三段：

text
.u_boot_list_2_cmd_1            ← 长度为 0 的标记，find_cmd 的起点
.u_boot_list_2_cmd_2_base       ← 每条命令一个，0x18 字节
.u_boot_list_2_cmd_2_bdinfo
.u_boot_list_2_cmd_2_bootm
.u_boot_list_2_cmd_2_...
.u_boot_list_2_cmd_3            ← 长度为 0 的标记，find_cmd 的终点

end - start 就是命令个数，start 就是数组首地址。不需要任何初始化代码，链接器一摆好，表就存在了。

10.2 U_BOOT_CMD 的三级宏展开 #

以 U_BOOT_CMD(env, CONFIG_SYS_MAXARGS, 1, do_env, "environment handling commands", env_help_text) 为例：

text
① U_BOOT_CMD
   → U_BOOT_CMD_COMPLETE(env, ..., NULL)
② U_BOOT_CMD_COMPLETE
   → ll_entry_declare(cmd_tbl_t, env, cmd)
     = U_BOOT_CMD_MKENT_COMPLETE(env, ..., NULL);
③ ll_entry_declare
   → cmd_tbl_t _u_boot_list_2_cmd_2_env __aligned(4)
     __attribute__((unused, section(".u_boot_list_2_cmd_2_env")))
④ U_BOOT_CMD_MKENT_COMPLETE
   → { "env", CONFIG_SYS_MAXARGS, 1, do_env,
       "environment handling commands", env_help_text, NULL }

最终结果就是一条「带段属性的结构体初始化语句」。这也解释了一个常见现象：用 if (0) 包住 U_BOOT_CMD 是删不掉命令的，因为段注册发生在编译期，运行期判断管不到，只有 CONFIG_CMD_xxx 能裁掉它。

十一、bootm：把控制权交出去 #

11.1 镜像的三种形态 #

形态 特点 用什么命令
Image 未压缩原生二进制 booti（ARM64）
zImage 压缩 + 内嵌自解压代码 bootz
Legacy uImage zImage 前面加 64 字节头 bootm
FIT uImage kernel + dtb + ramdisk 打成**.itb** bootm

Legacy 那 64 字节头解决了「u-boot 怎么知道往哪加载、从哪跳、要不要解压、校验对不对」这四个问题：

c
typedef struct image_header {
    __be32  ih_magic;   /* 0x27051956，认这个魔数 */
    __be32  ih_hcrc;    /* 头部 CRC */
    __be32  ih_time;
    __be32  ih_size;    /* 数据大小 */
    __be32  ih_load;    /* 加载地址（mkimage -a）*/
    __be32  ih_ep;      /* 入口地址（mkimage -e）*/
    __be32  ih_dcrc;    /* 数据 CRC */

    uint8_t ih_arch;    /* CPU 架构 */
    uint8_t ih_type;    /* 镜像类型 */

bash

11.2 do_bootm 与它的一张状态表 #

do_bootm 先把 argv 里的 bootm 去掉，然后调用 do_bootm_states，传一串状态位：

c
return do_bootm_states(cmdtp, flag, argc, argv,
    BOOTM_STATE_START | BOOTM_STATE_FINDOS | BOOTM_STATE_FINDOTHER |
    BOOTM_STATE_LOADOS |
    BOOTM_STATE_OS_PREP | BOOTM_STATE_OS_FAKE_GO |
    BOOTM_STATE_OS_GO, &images, 1);

do_bootm_states 就是一个状态机，每满足一个状态位就走一段：

text
images->state |= states
 ├─ BOOTM_STATE_START    → bootm_start()      清 images，读 verify 环境变量
 ├─ BOOTM_STATE_FINDOS   → bootm_find_os()    解析头，填 type/comp/os/load/arch/entry
 ├─ BOOTM_STATE_FINDOTHER→ bootm_find_other() 找 dtb 与 ramdisk
 ├─ BOOTM_STATE_LOADOS   → bootm_disable_interrupts() + bootm_load_os()
 │                        解压 zImage 到 images.os.load，flush_cache
 ├─ BOOTM_STATE_OS_PREP  → boot_fn(..., PREP) → do_bootm_linux → boot_prep_linux()
 │                        构造 ATAGS 或往 dtb 的 /chosen 塞 bootargs
 └─ BOOTM_STATE_OS_GO    → boot_selected_os() → boot_jump_linux() → 跳内核

每一段都靠 if (!ret && (states & BOOTM_STATE_xxx)) 串起来，任何一步失败就跳 err。

11.3 boot_prep_linux：ATAGS 还是 dtb #

c
static void boot_prep_linux(bootm_headers_t *images)
{
    char *commandline = getenv("bootargs");

    if (IMAGE_ENABLE_OF_LIBFDT && images->ft_len) {
        /* 有 dtb：把 bootargs 写进 /chosen/bootargs */
        image_setup_linux(images);
    } else if (BOOTM_ENABLE_TAGS) {
        /* 没 dtb：在 bi_boot_params 处依次摆 tag */
        setup_start_tag(gd->bd);           /* ATAG_CORE   0x54410001 */
        setup_commandline_tag(gd->bd, commandline);  /* ATAG_CMDLINE */
        setup_memory_tags(gd->bd);         /* ATAG_MEM    0x54410002 */
        setup_initrd_tag(...);
        setup_end_tag(gd->bd);             /* ATAG_NONE   0x00000000 */
    } else {
        printf("FDT and ATAGS support not compiled in - hanging\n");
        hang();
    }
}

ATAGS 是老路：在固定内存地址上一段段摆结构体，内核按 0x54410001 这样的魔数顺序解析出来。SMDK2410 上起始地址是 bi_boot_params = 0x30000100，bootargs 内容形如 noinitrd root=/dev/mtdblock3 init=/linuxrc console=ttySAC0,115200。

有设备树之后就走新路：bootargs 直接写进 dtb 的 /chosen 节点，内核从 dtb 里读。这也解释了为什么移植设备树时要往 dts 里塞 chosen { bootargs = "..."; };。

11.4 boot_jump_linux：最后一跳 #

这是整条启动链上唯一真正交接控制权的地方，值得逐字看：

c
static void boot_jump_linux(bootm_headers_t *images, int flag)
{
    unsigned long machid = gd->bd->bi_arch_number;      /* 机器码 */
    void (*kernel_entry)(int zero, int arch, uint params);
    unsigned long r2;
    int fake = (flag & BOOTM_STATE_OS_FAKE_GO);

    kernel_entry = (void (*)(int, int, uint))images->ep;  /* 入口地址 */

    s = getenv("machid");
    if (s) {
        if (strict_strtoul(s, 16, &machid) < 0)   /* 环境变量可覆盖 */
            return;
        printf("Using machid 0x%lx from environment\n", machid);
    }

    announce_and_cleanup(fake);      /* 关中断、flush cache 等收尾 */

    if (IMAGE_ENABLE_OF_LIBFDT && images->ft_len)
        r2 = (unsigned long)images->ft_addr;      /* 有 dtb 就传 dtb 地址 */
    else
        r2 = gd->bd->bi_boot_params;              /* 否则传 ATAGS 地址 */

    if (!fake)
        kernel_entry(0, machid, r2);   /* ← 从此不再返回 */
}

kernel_entry(0, machid, r2) 这三个参数就是 ARM32 引导协议的全部约定。

十二、u-boot 与内核的交接约定 #

这一段是移植时最容易出错的地方——错一条，内核就在 Starting kernel ... 之后静默死掉，没有任何提示。

12.1 ARM32 #

项 要求 谁保证
r0 0 kernel_entry(0, ...) 第一个参数
r1 machine id（S3C2440 常用 362，SMDK2410 是 193） gd->bd->bi_arch_number，可被环境变量 machid 覆盖
r2 ATAGS 起始地址，或 dtb 地址 bi_boot_params（0x30000100）或 images->ft_addr
CPU 模式 SVC，禁止 IRQ/FIQ reset 一开始就设成 0xd3 且不再改回
MMU 必须关闭 全程没开（cpu_init_crit 清 M 位）
D-Cache 必须关闭 announce_and_cleanup() 里 flush 并关
I-Cache 开或关都行 u-boot 在 board_init() 里开了
DMA 设备 必须停止 bootm_disable_interrupts() 与网卡驱动的 cleanup
PC 内核入口地址 images->ep

12.2 ARM64 #

项 要求
x0 dtb 的物理地址（没有 machine id 这个概念了）
x1/x2/x3 全 0
异常级别 EL2 或非安全 EL1，推荐 EL2
PSTATE.DAIF 全部屏蔽
dtb 8 字节对齐，不超过 2MB

详细的 ARM64 约定见 启动流程通识：从 BIOS 到 init 第七节。

十三、FIT uImage：把 kernel、dtb、ramdisk 打成包 #

13.1 为什么还要一个新格式 #

Legacy uImage 一次只能装一个内核，dtb 得在命令行上另外传地址：

bash
bootm 0x30008000 - 0x30001000     # 地址、地址、地址，全靠人记

ARM 引入 device tree 时有个「Unify Kernel」的梦想：同一个 Kernel Image 支持多个平台，bootloader 按手里这块板子的硬件挑对应的 dtb。这要求镜像里能放多个 dtb，还能按名字选。这就是 FIT（Flattened Image Tree）。

13.2 its 与 itb #

文件 类比 角色
.its dts image source file，人写的源文件
.itb dtb 最终镜像，u-boot 直接解析
mkimage dtc 把 its + 各数据文件打包成 itb

原文此处配有一幅 FIT image 生成步骤示意图，抓取时丢失。它的内容就是下面这条流水线：

text
image source file (.its)   ┐
                           ├─ mkimage ─→ image file (.itb) ─→ 下载到板子 ─→ bootm
image data file(s)         ┘
  zImage / dtb / ramdisk

一个完整的 its：

dts
/dts-v1/;

/ {
    description = "U-Boot uImage source file for X project";
    #address-cells = <1>;

    images {
        kernel@tiny210 {
            description = "Linux kernel";
            data = /incbin/("./out/linux/arch/arm/boot/zImage");
            type = "kernel";
            arch = "arm";
            os = "linux";
            compression = "none";
            load = <0x20008000>;
            entry = <0x20008000>;
            hash@1 { algo = "sha1"; };
        };
        fdt@tiny210 {
            description = "Flattened Device Tree blob";
            data = /incbin/("./out/linux/arch/arm/boot/dts/s5pv210-tiny210.dtb");
            type = "flat_dt";
            arch = "arm";
            compression = "none";
        };
        ramdisk@tiny210 {
            data = /incbin/("./out/rootfs/initramfs.gz");
            type = "ramdisk";
            arch = "arm";
            os = "linux";
            compression = "gzip";
        };
    };

    configurations {
        default = "conf@tiny210";
        conf@tiny210 {
            description = "Boot Linux kernel with FDT blob";
            kernel = "kernel@tiny210";
            fdt = "fdt@tiny210";
            ramdisk = "ramdisk@tiny210";
        };
    };
};

images 里每个节点支持这些属性：

属性 说明
data 数据文件路径，格式 /incbin/("path")
type "kernel" / "ramdisk" / "flat_dt"
arch "arm" / "arm64" / "x86"…
os "linux" / "vxworks"…
compression "none" / "gzip" / "bzip2"
load 加载地址，u-boot 会 copy 过去
entry 入口地址，u-boot 跳到这里
hash 校验算法（写了就得真有 hash，否则启动时报 Bad Data Hash）

configurations 是「组合」：一个 conf 可以把某个 kernel + 某个 dtb + 某个 ramdisk 绑在一起，多个 conf 就能让同一个 itb 适配多块板子。

bash
mkimage -f kernel_fdt.its kernel_fdt.itb     # 打包
mkimage -l kernel_fdt.itb                    # 查看内容

bootm 0x6400000                    # 用 default 配置启动
bootm 0x6400000#conf@tiny210       # 指定配置
bootm 0x6400000:kernel@tiny210     # 只加载某个子镜像

13.4 三个常见坑 #

现象 原因 处理
Bad hash value for 'hash@1' its 里写了 hash 节点但没算 删掉 hash 节点，或让 mkimage 重算
Unsupported Architecture arch = "arm" 用在 AArch64 内核上 改成 arch = "arm64"
new format image overwritten - must RESET itb 所在地址与 kernel 的 load 地址重叠 重新规划内存，把 itb 放到 kernel 区之外

最后一条尤其容易中：load = <0x00080000> 表示内核要搬到 0x80000，而如果 itb 本身放在 0x0，加载时就会把自己压掉。

小结 #

  • 启动链是一条直线：_start → reset → cpu_init_crit → lowlevel_init → _main → board_init_f → relocate_code → board_init_r → main_loop → bootm，中间没有分支。
  • _main 是枢纽：它唯一同时看得见三个阶段，靠 r9（ARM32）/x18（ARM64）里的 gd 指针把状态一路带下去。
  • board_init_f 干两件事：初始化时钟/串口/DRAM，然后从 DRAM 顶端往下规划内存，把 relocaddr、start_addr_sp、new_gd 一步步算出来。
  • relocate_code 搬 .text/.rodata/.data 并按 .rel.dyn 修正所有绝对地址——不加 -pie 就没有这张表，搬完必然跑飞。
  • board_init_r 才轮得到外设：Flash、NAND、网卡、环境变量依次初始化，最后进 main_loop。
  • 命令表靠 .u_boot_list 段在编译期生成，find_cmd 只是算了个区间；if (0) 删不掉命令。
  • 最后一跳是 kernel_entry(0, machid, r2)，三个参数就是全部交接约定；ARM64 换成 x0 = dtb 物理地址，不再有 machine id。
