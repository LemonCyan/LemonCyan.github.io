ARM 软中断指令SWI

ARM 软中断指令 SWI 运作机制与 Linux 系统调用底层实现 #

在 ARM 体系结构中，处于用户模式（User Mode，无特权模式）下的应用程序是没有权限直接读写硬件寄存器、或者切换处理器模式的。如果应用程序想要使用外设，必须将控制权安全地交给操作系统内核（特权模式），由内核代为执行。

这一“跨越边界”的通道，在硬件层面上就是由 SWI（Software Interrupt，软件中断） 指令提供的。

一、 什么是软件中断 (SWI) #

软中断利用了硬件中断的概念，在软件中通过执行一条特殊的 CPU 指令来触发异常处理。

  • 硬件中断：由外部引脚电平变化触发，具有异步性。
  • 软件中断：由 CPU 执行到特定的 SWI 指令时自发同步触发。

一旦 CPU 执行到 SWI 指令，会无条件地强制切入管理模式（Supervisor Mode，即 SVC 模式），保存当前现场，并跳转到异常向量表中的软中断入口（通常是 0x08 处的向量）。

1. SWI 指令格式 #

SWI{cond} immed_24
  • immed_24：24 位的立即数，范围为 0 ~ 16777215。
  • 作用：这个 24 位立即数在用户态和内核态之间充当“接头暗号”。用户程序用它来标识自己请求的操作系统服务类型（即系统调用号）。

2. 软中断参数传递规则（基于 ATPCS） #

按照 ARM-Thumb 过程调用标准（ATPCS）：

  • 函数的前 4 个参数放入 R0 ~ R3 寄存器中。
  • 返回值放回 R0 中。
  • 系统调用号的传递方式：
    1. 直接编码在指令中：如 SWI 12，系统调用号就是 12。
    2. 放入寄存器中：立即数填 0，用 R0（或 R7）传递系统调用号，如：
      MOV R0, #12   ; 12 号系统调用
SWI 0

二、 裸机环境下手搓 SWI 中断处理 #

我们用点亮 LED 灯为例，看一下在没有操作系统的情况下，如何手搓 SWI 机制。

1. 应用程序层 (C + 汇编混合编程) #

在用户态下，C 语言无法直接生成 SWI 指令，必须嵌入内联汇编：

c
#define __led_on_swi_no 1  /* 亮灯的软中断号为 1 */

int led_on(int led_no) {
    int ret;
    __asm {
        MOV R0, led_no          /* 第一个参数装入 R0 */
        SWI __led_on_swi_no     /* 触发软中断 1 */
        MOV ret, R0             /* 取得返回值 */
    }
    return ret;
}

2. 异常向量表配置 #

当 SWI 触发后，CPU 硬件自动强制 PC 指向 0x08：

; 异常向量表
b Reset          ; 0x00: 复位
b HandleUndef    ; 0x04: 未定义异常
b HandleSWI      ; 0x08: 软件中断异常入口
...

3. 软中断服务程序 (HandleSWI) #

在特权模式下，我们需要保护寄存器、提取 SWI 指令中的立即数，并执行相应的硬件操作。

IMPORT do_led_on
IMPORT do_led_off

HandleSWI:
    ; 1. 保护现场：将 R0-R12 和返回地址 LR (此时 LR_irq/LR_svc 指向 SWI 下一条指令) 压栈
    STMFD   SP!, {R0-R12, LR}
    
    ; 2. 提取 24 位立即数 (接头暗号)
    ; 由于 LR 保存的是 SWI 下一条指令的地址，所以 LR - 4 就是 SWI 指令本身的内存地址。
    LDR     R4, [LR, #-4]
    ; 剥离出低 24 位立即数（ARM 指令高 8 位为条件码和 SWI 机器码 0xEF）
    BIC     R4, R4, #0xFF000000 
    
    ; 3. 根据软中断号分发执行
    CMP     R4, #1
    LDREQ   LR, =swi_return     ; 预设返回地址
    LDREQ   PC, =do_led_on      ; 跳转执行亮灯 C 函数 (R0 自动作为 led_no 参数)
    
    CMP     R4, #2
    LDREQ   LR, =swi_return
    LDREQ   PC, =do_led_off     ; 跳转执行灭灯 C 函数
    
    MOVNE   R0, #-1             ; 未知软中断号，返回错误 -1

swi_return:
    ; 4. 恢复现场并返回用户态
    ; '^' 符号非常关键：它会在恢复 R0-R12 和 PC 的同时，自动把 SPSR 拷贝回 CPSR，恢复模式和中断状态。
    LDMIA   SP!, {R0-R12, PC}^

三、 Linux 内核中的系统调用底层实现 #

在 Linux 系统中，著名的库函数 open()、read() 底层就是通过 SWI 触发系统调用的。我们以较早的 ARM Linux 内核为例扒一下流程。

1. 系统调用号定义与宏展开 #

在 include/asm-arm/unistd.h 中定义了系统调用号：

c
#define __NR_SYSCALL_BASE   0x900000  /* 内核系统调用基地址 */
#define __NR_open           (__NR_SYSCALL_BASE + 5) /* open 对应的中断号为 0x900005 */

应用层调用 open() 时，glibc 库函数会将其展开为如下汇编：

  • ARM 模式： 直接将系统调用号编入 SWI 指令中：
    SWI 0x900005   ; 触发 open 系统调用
  • Thumb 模式： 由于 Thumb 指令只有 16 位，放不下 24 位立即数，所以系统调用号必须放入寄存器 R7 中：
    PUSH {R7}
MOV  R7, #5    ; open 偏移号
SWI  0         ; 立即数填 0
POP  {R7}

2. 内核软中断入口 vector_swi #

当应用层触发 SWI 后，内核会跳转到 arch/arm/kernel/entry-common.S 中的 vector_swi：

ENTRY(vector_swi)
    save_user_regs              @ 1. 保存用户态所有寄存器到内核栈 (pt_regs)
    get_scno                    @ 2. 获取系统调用号 (System Call Number)
                                @    如果是 ARM 模式，读取 [LR, #-4] 处的指令并 BIC 提取；
                                @    如果是 Thumb 模式，直接从 R7 寄存器获取。

    bic     scno, scno, #0xff000000 @ 过滤高 8 位
    eor     scno, scno, #0x900000   @ 减去 0x900000 基址。如 0x900005 变成 5

    adr     tbl, sys_call_table     @ 3. 加载系统调用表基指针
    
    adrsvc  al, lr, ret_fast_syscall @ 预设系统调用执行完后的返回处理函数
    cmp     scno, #NR_syscalls      @ 检查系统调用号是否超出上限
    ldrcc   pc, [tbl, scno, lsl #2] @ 4. 【核心】：查表跳转！
                                    @    跳转到 sys_call_table[5] 即 sys_open 执行！

3. 系统调用表 sys_call_table #

内核在 arch/arm/kernel/entry-common.S 中定义了系统调用表，并将 calls.S 顺序包含进来：

.type sys_call_table, #object
ENTRY(sys_call_table)
#include "calls.S"

在 calls.S 中，第 5 项正好是：

/* 5 */   .long sys_open

所以 ldrcc pc, [tbl, scno, lsl #2] 查表跳转后，直接进入了内核的 sys_open() C 函数执行。执行完毕后，程序通过 ret_fast_syscall 恢复用户态现场，并返回用户空间继续执行。
