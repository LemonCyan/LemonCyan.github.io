AWorks软件篇 — 实时内核（任务管理与信号量）

ZLG AWorks OS 实时内核开发指南：多任务管理与三大信号量深度解析 #

在传统的单片机裸机开发中，系统主逻辑通常被强行塞进 main() 函数里的 while(1) 死循环。这种模式一旦面对复杂的周期性任务、异步通信和多外设管理，代码的逻辑耦合度就会直线上升，极难维护。

周立功致远电子的 AWorks 框架定义了一套通用的 实时内核（OS） 接口，默认搭载其自主研发的极简原生内核：RTK (Real-Time Kernel)。RTK 最小仅需 1KB RAM 和 2KB ROM 即可流畅运行，支持高达 1024 个优先级，并允许全部组件静态实例化。

今天咱们就扒一扒 AWorks 实时内核的两个核心：任务管理 与 信号量 的使用逻辑。

一、 任务管理 #

1. 多任务相较于裸机主循环的爽点 #

裸机开发中，如果需要控制两个 LED 以不同的频率闪烁（例如 LED0 每 250ms 翻转，LED1 每 500ms 翻转），主循环就得使用各种软件计数器和定时状态机，写起来非常恶心。

在多任务环境下，每一个任务都拥有自己独立的 while(1) 循环：

+-------------------------------------------------------+
|                 AWorks 任务调度器 (RTK)                |
+---------------------------+---------------------------+
                            |
         +------------------+------------------+
         |                                     |
  +------v------+                       +------v------+
  |   任务 0     |                       |   任务 1     |
  | (LED0 闪烁)  |                       | (LED1 闪烁)  |
  | while(1) {  |                       | while(1) {  |
  |   翻转;     |                       |   翻转;     |
  |   延时250ms;|                       |   延时500ms;|
  | }           |                       | }           |
  +-------------+                       +-------------+

由于每个任务的逻辑是完全独立的，LED 闪烁频率的变化互不干扰，实现了经典的“高内聚、低耦合”。

2. 创建任务的三部曲 #

在 AWorks 中，创建并跑起一个任务主要分为三步，全部通过 aw_task.h 中定义的宏来完成：

第一步：声明任务实体（分配栈内存）

使用静态或全局声明宏。声明必须在任务生命周期内持续有效，建议使用 static 版本限制作用域：

c
#include "aw_task.h"

#define TASK_LED0_STACK_SIZE  512

/* 静态声明一个任务实体，名称为 task_led0，为其分配 512 字节栈空间 */
AW_TASK_DECL_STATIC(task_led0, TASK_LED0_STACK_SIZE);
第二步：初始化任务

调用初始化宏将任务实体与入口函数绑定，并指定优先级（0 为最高优先级）：

c
aw_task_id_t  g_task_led0_id;

/* 入口函数原型 */
static void __task_led0_entry(void *p_arg)
{
    while (1) {
        aw_gpio_toggle(LED0_PIN);
        aw_task_delay(250); /* 延时 250 个 ticks，释放 CPU */
    }
}

void app_task_init(void)
{
    /* 初始化任务，名字为 "task_led0"，优先级为 5 */
    g_task_led0_id = AW_TASK_INIT(task_led0, 
                                  "task_led0", 
                                  5, 
                                  TASK_LED0_STACK_SIZE, 
                                  __task_led0_entry, 
                                  NULL);
}
✦提示

系统的最低优先级数字可以通过 aw_task_lowest_priority() 动态获取。

第三步：启动任务
c
void app_task_start(void)
{
    /* 启动任务，使其加入就绪队列等待调度 */
    AW_TASK_START(task_led0);
}

3. 任务终止与长延时 #

  • 终止任务：当事务处理完毕后，可以使用 AW_TASK_TERMINATE(task) 将其强行终止以回收资源。
  • 任务延时：调用 aw_task_delay(ticks)。它会主动挂起当前任务、释放 CPU 使用权，等延时到期后再由调度器重新唤醒。千万不要在不需要 CPU 时用忙等待，否则会导致低优先级任务饿死。

4. 任务栈空间动态监测 #

合理的栈分配很难把控：分多了浪费，分少了溢出崩溃。AWorks 提供了两个辅助宏检查栈水位：

  • AW_TASK_STACK_CHECK(task, p_total, p_free)：在外部检查指定任务的栈使用情况。
  • AW_TASK_STACK_CHECK_SELF(p_total, p_free)：在任务体内自检。
⚠警告

自检宏在运行过程中，检测函数本身的压栈操作会占用一定的栈，所以测量出的空闲字节数会有轻微偏差。推荐在实际测量的最高栈使用量的基础上，保留 20%~50% 的余量，且将栈空间设置为 2 的整数次幂（128、256、512 字节）。

二、 信号量：三大内核对象的机制对决 #

信号量是解决任务间同步与互斥的轻量级内核对象。AWorks 提供了三种类型的信号量：互斥信号量（Mutex）、二进制信号量（Binary Sem）、计数信号量（Counting Sem）。

1. 互斥信号量 (Mutex) #

互斥信号量主要用于解决共享资源的独占式访问（如保护同一个串口打印输出）。

(1) 基本使用流程
c
#include "aw_sem.h"

/* 1. 声明互斥锁 */
AW_MUTEX_DECL_STATIC(mutex_uart);

void mutex_demo_init(void)
{
    /* 2. 初始化互斥锁，排队方式为按优先级排队 */
    AW_MUTEX_INIT(mutex_uart, AW_SEM_Q_PRIORITY);
}

void task_print_data(const char *str)
{
    /* 3. 获取互斥锁（上锁） */
    if (AW_MUTEX_LOCK(mutex_uart, AW_SEM_WAIT_FOREVER) == AW_OK) {
        // 临界区：独占式访问串口
        printf("%s", str);
        
        /* 4. 释放互斥锁（解锁） */
        AW_MUTEX_UNLOCK(mutex_uart);
    }
}
(2) 互斥信号量的特性
  • 递归支持：互斥锁支持在同一个任务内递归获取。只要该任务已经占有锁，再次 LOCK 不会死锁，直接成功返回。但解锁必须成对出现，LOCK 几次就要 UNLOCK 几次。
  • 锁的归属权限制：互斥锁只能由上锁的任务自己解锁。外部任务或中断处理程序（ISR）无权释放。

2. 二进制信号量 (Binary Semaphore) #

二进制信号量的值只能是 0 或 1。主要用于任务间的一对一同发与同步。

              +------------------------------------------+
              |           二进制信号量 (0 / 1)           |
              +---------^----------------------^---------+
                        |                      |
            (GIVE)      |                      |  (TAKE)
       +----------------+----+            +----+---------------+
       | 任务A / 中断 (ISR)   |            |       任务 B        |
       | 触发按键 -> 释放信号 |            | 接收信号 -> 闪烁LED |
       +---------------------+            +--------------------+
(1) 同步使用范例
c
AW_SEMB_DECL_STATIC(semb_sync);

void sync_demo_init(void)
{
    /* 初始化二进制信号量，初始状态为 0 (空) */
    AW_SEMB_INIT(semb_sync, AW_SEM_EMPTY, AW_SEM_Q_PRIORITY);
}

/* 按键中断服务程序中释放信号量 */
void button_isr_handler(void)
{
    AW_SEMB_GIVE(semb_sync); /* 中断中可以释放二进制信号量 */
}

/* 接收同步的任务 */
void task_led_blink(void *p_arg)
{
    while (1) {
        /* 挂起等待按键中断的同步信号 */
        if (AW_SEMB_TAKE(semb_sync, AW_SEM_WAIT_FOREVER) == AW_OK) {
            aw_gpio_toggle(LED0_PIN);
            aw_task_delay(500);
        }
    }
}
(2) 局限与排坑：信号丢失

由于二进制信号量只有 0 和 1 状态。如果 task_led_blink 正在闪烁（耗时 500ms），此时用户连续按下了 3 次按键：

  • 中断会释放 3 次信号量。
  • 第一次释放将信号量设为 1。
  • 第二次和第三次释放时，由于信号量已经是 1，释放操作直接失效并丢失。
  • 最终，LED 只会额外多闪烁 1 次，后面的信号全部丢失了。

3. 计数信号量 (Counting Semaphore) #

为了完美解决二进制信号量在频繁触发时的“信号丢失”问题，我们需要引入计数信号量。

计数信号量内部维护一个无符号的计数值：

  • GIVE：计数值加 1。
  • TAKE：计数值减 1（若为 0 则阻塞）。
(1) 计数信号量使用范例

与二进制信号量的 API 极为相似，仅需将 SEMB 更换为 SEMC：

c
AW_SEMC_DECL_STATIC(semc_count);

void count_demo_init(void)
{
    /* 初始化计数信号量，初始计数值为 0 */
    AW_SEMC_INIT(semc_count, 0, AW_SEM_Q_PRIORITY);
}

void button_isr_handler(void)
{
    AW_SEMC_GIVE(semc_count); /* 每次按键，计数值递增 */
}

void task_led_blink(void *p_arg)
{
    while (1) {
        if (AW_SEMC_TAKE(semc_count, AW_SEM_WAIT_FOREVER) == AW_OK) {
            /* 每次按键触发的闪烁都会被排队依次处理，绝不漏包 */
            aw_gpio_toggle(LED0_PIN);
            aw_task_delay(500);
        }
    }
}

三、 总结：如何选型信号量？ #

  • 用于资源排他性保护（临界区锁）： 👉 选用 互斥信号量 (Mutex)。支持重入、防优先级翻转，且有归属权限制。
  • 用于任务间的一对一简单同步（不关心触发频次）： 👉 选用 二进制信号量 (Binary Semaphore)。支持在中断中释放。
  • 用于事件计数或生产者-消费者模型（不能漏掉每一次触发）： 👉 选用 计数信号量 (Counting Semaphore)。
